# Лінза «Наскрізний приклад Digital Homes» — проєкт наскрізного прикладу для курсу progarch (~500 кроків)

**Статус:** пропозиція для синтезу; у репозиторії нічого не змінено.
**Роль прикладу:** Digital Homes (DH) — платформа розумного дому — **ілюструє** архітектурні теми, а **не організує** курс. Структура курсу — за доменно-нейтральними темами; DH з'являється точково там, де він показовий, і поступається місцем грі/платіжці/data-пайплайну там, де вони чесніші (див. §7). Проєкт «Квиток» вилучено; DH — його заміна як наскрізна нитка, але з іншим договором: **не кожен модуль відкривається DH-болем** — DH-кроки вплітаються туди, де рішення реально багатоваріантне або конфлікт показовий.

**Чому саме розумний дім — сильний наскрізний приклад для універсального курсу:** одна система природно містить embedded (прошивка сенсора), edge (хаб), бекенд (хмара на мільйони домів), клієнти (мобайл/веб/десктоп), медіа (відео камер), data (телеметрія й аналітика), операції (флот OTA, підтримка) — тобто торкається всіх типів програмування, які курс мусить покрити, не підміняючи собою жоден.

## 1. Система Digital Homes: підсистеми і мапа контекстів

### 1.1 Підсистеми (bounded contexts)

| # | Контекст | Що всередині | Де живе |
|---|---|---|---|
| C1 | **Пристрій** | прошивка сенсора/актуатора/камери: конективіті-FSM, локальний failsafe, буфер | залізо в домі |
| C2 | **Хаб** | драйвери/інтеграції (Zigbee/BLE/Wi-Fi/Matter), локальний реєстр пристроїв, локальний рушій правил, локальний API, буфер телеметрії (store-and-forward) | edge, embedded Linux |
| C3 | **Флот-доступ** (connection edge) | термінація мільйонів довгих конектів хабів, автентифікація пристроїв, маршрутизація команд/подій | хмара, периметр |
| C4 | **Твін / стан дому** | цифровий двійник: reported/desired стан кожного пристрою, presence, останні значення | хмара |
| C5 | **Автоматизації** | правила/сцени користувача: тригер–умова–дія; розкладка виконання хаб/хмара | хаб + хмара |
| C6 | **Телеметрія** | інжест часових рядів, retention, downsampling; історія «температура за тиждень» | хмара |
| C7 | **Відео** | сигналінг, live-шлях (P2P/relay), запис подій, сховище кліпів, плейбек | камера + хмара + CDN |
| C8 | **Ідентичність і доступ** | користувачі, доми, ролі (власник/член сім'ї/гість/орендар), сертифікати пристроїв, шаринг | хмара |
| C9 | **Сповіщення** | push/email/SMS: «двері відчинено о 14:32» | хмара |
| C10 | **Клієнти** | мобільний, веб, десктоп: стан дому, керування, відео, offline/LAN-режим | телефони/браузери |
| C11 | **OTA / прошивки** | збірка образів, хвилі розкатки, health-гейти, відкати | хмара + CDN + пристрій |
| C12 | **Аналітика розробників** | fleet health, crash-репорти, продуктові метрики, приватність-aware агрегати | хмара, offline |
| C13 | **Підтримка / ремонт** | діагностика конкретного дому, remote logs за згодою, RMA-процес | хмара, read-only проєкції |

### 1.2 Мапа стосунків (DDD-лайт)

- **C2 Хаб ← C1 Пристрої:** драйвери = **антикорупційний шар** проти зоопарку протоколів (кожен вендор бреше по-своєму; хаб нормалізує в канонічну модель «пристрій-можливості-стан»).
- **C3 Флот-доступ агрегує:** хмара бачить **один конект на дім**, а не 20 конектів на кожен девайс — ключова архітектурна вигода хаба (× менше стану на краю, менший шторм реконектів; чесна ціна — хаб = єдина точка відмови дому).
- **C4 Твін ← C2:** контракт reported/desired (bidirectional, але кожен напрям має власника: reported пише лише хаб, desired — лише хмара).
- **C5 Автоматизації ↔ C4:** читають стан, пишуть desired; НЕ ходять напряму в C1/C2 (інакше правила залежать від транспорту).
- **C7 Відео ✂ C4:** великі потоки **навмисно не через твін** — найкращий у курсі приклад «різні профілі трафіку = різні шляхи» (кілобайтний стан і мегабітний потік не живуть в одному каналі).
- **C13 Підтримка — read-only проєкції** всього: чудова ілюстрація CQRS-читань без права запису.
- **C8 Ідентичність — upstream для всіх;** усі conformist.

**Own-крок:** `[own:dh-contexts-map]` — «Мапа контекстів Digital Homes» (якір: фаза «архітектура застосунку», розділ про межі/контексти; аналог kvytok-contexts). Працює довідником до кінця курсу.

## 2. Еволюція v0→v10 по дузі курсу

Прив'язка — до **фаз дуги** (синтез розкладе по своїх модулях): Ф1 принципи → Ф2 патерни → Ф3 архітектура застосунку → Ф4 дані → Ф5 паралельність → Ф6 мережа/API → Ф7 розподілені дані → Ф8 сервіси/події → Ф9 високе навантаження → Ф10 експлуатація; плюс фази універсального курсу: ФК клієнти, ФМ медіа/відео, ФД data/аналітика, ФЕ embedded/edge, ФБ безпека (як синтез їх не виділить — кроки лягають у найближчі класичні фази).

| v | Фаза | Масштаб | Біль → що вводимо | Own-кроки (slug) |
|---|---|---|---|---|
| v0 | Ф1 | 1 дім, 1 сенсор, 0 хмари | скрипт на хабі читає температуру, поріг зашито; кожна зміна ламає все | `dh-v0-one-sensor` (+ proj-dh-v0.md — робочий однофайловий «хаб») |
| v1 | Ф2 | 1 дім, 5 типів пристроїв | зоопарк вендорів → adapter; події → observer; дії → command; політики → strategy | `dh-v1-device-abstractions` (+ proj-dh-v1.md) |
| v2 | Ф3 | 1 дім, 30 пристроїв | хаб = клубок → шари/порти-адаптери; правила → плагінний рушій; життєвий цикл пристрою → FSM | `dh-v2-hub-hexagon` (+ proj-dh-v2.md), `dh-device-lifecycle-fsm`, `dh-contexts-map` |
| v3 | Ф4 | те саме, але переживає рестарт | реєстр і телеметрія в SQLite на хабі; WAL; retention-буфер | `dh-v3-hub-storage` (+ proj-dh-v3.md) |
| v4 | Ф5 | 30 пристроїв «одночасно» | радіо-івенти + таймери правил + API-запити в одному процесі: event loop проти потоків; актор-на-пристрій | `dh-v4-hub-concurrency` |
| v5 | Ф6 | + мобільна апка в LAN | хабу потрібен API → **варіантний сет D6**; апка в тій самій мережі | (сет D6, §3) |
| v6 | Ф6→Ф7 | + хмара, 10 тис. домів | доступ з-поза дому: NAT → **сет D12**; канал пристрій↔хмара → **сет D1**; перший твін | `dh-v6-cloud-link`, (сети D1, D12) |
| v7 | Ф7 | 500 тис. домів | стан дому в хмарі → **сет D3**; чиї дані в яких таблицях → **сет D5**; хто правий після reconnect | `dh-hub-cloud-reconcile`, (сети D3, D5) |
| v8 | Ф8 | хмара не влазить в один деплой | розпил на сервіси (C3–C9); журнал подій; сага передачі володіння; ідентичність пристроїв | `dh-v8-services-map`, `dh-lock-exactly-once`, `dh-handover-saga`, `dh-device-identity`, (сет D2) |
| v9 | Ф9 | 5 млн домів, 100 млн пристроїв | вечірній пік 18:00; блекаут → шторм реконектів; пріоритети «замки > лампочки» | `dh-fleet-envelope`, `dh-evening-peak`, `dh-blackout-reconnect` |
| v10 | Ф10 | той самий флот, роками | OTA-хвилі → **сет D10**; спостережність флоту; інцидент поганої прошивки; видалення даних | `dh-fleet-observability`, `dh-bad-firmware-incident`, `dh-privacy-deletion`, (сет D10) |
| — | ФК | клієнти | синк стану в апці → **сет D9** | (сет D9) |
| — | ФМ | відео | шлях відео → **сет D4**; онбординг камери за хвилину | `dh-camera-onboarding`, (сет D4) |
| — | ФД | аналітика | сховище телеметрії → **сет D8**; аналітика для розробників | `dh-dev-analytics`, (сет D8) |
| — | ФЕ | прошивка | архітектура прошивки сенсора: конективіті-FSM, буфер, failsafe (ref-и в guide/embedded: watchdog done, failsafe done, ota-slots done) | `dh-sensor-firmware-arch`, (сет D7 — якір Ф3 або ФЕ) |

**Цифри для `dh-fleet-envelope`** (прикидка на серветці, якір Ф9): 5 млн домів × 20 пристроїв = 100 млн пристроїв, але конектів до хмари ~5 млн (хаб агрегує). Телеметрія: повідомлення/30–60 с з дому ≈ 80–170 тис. msg/s середнє, вечір ×3. Блекаут-район на 100 тис. домів: реконект усіх за хвилини + холодні кеші твіна. Відео: 1–2% камер live одночасно × 2 Мбіт/с ≈ 200–400 Гбіт/с через relay — звідси вся драма сету D4; безперервний запис 24/7 у хмару фізично не летить (10 млн камер × 1 Мбіт/с ≈ 10 Тбіт/с) → запис лише за подіями.

## 3. ВАРІАНТНІ СТАТТІ — 12 рішень (головна вимога)

Формат сету: 2–3 own-статті-варіанти + own-стаття-вибір. Варіант — **чесна адвокатура**: де це рішення виграє, хто так робить у проді, чим платиш. Стаття-вибір — **рамка критеріїв**, не «правильна відповідь»; де в реальності беруть композицію варіантів — вибір це прямо каже. Сети D1–D6 — з ТЗ користувача; D7–D10 — додані; D11–D12 — опційні (перші кандидати під ніж).

### D1. Канал пристрій↔хмара (якір: Ф6 мережа/API, міст у Ф8)
- `[own:dh-uplink-longconn]` — **Довгий двобічний конект** (MQTT/WebSocket поверх TLS). Виграє: команди за мс, presence з keepalive задарма, push без опитувань. Платиш: мільйони відкритих з'єднань = стан на краю (пам'ять, балансування, драма реконектів), NAT-таймаути, battery-ворог для Wi-Fi-девайсів. Ref: `communications/protocols/mqtt` (done/done).
- `[own:dh-uplink-polling]` — **Полінг / long-poll / «відзвітував і заснув»**. Виграє: stateless-сервер, працює крізь будь-який NAT/proxy, ідеально для батарейного сенсора, що прокидається раз на годину (99% сну). Платиш: latency = період опитування, марний трафік, presence «востаннє бачили», команди чекають наступного пробудження.
- `[own:dh-uplink-broker]` — **Керований брокер + shadow** (модель AWS IoT / Azure IoT Hub). Виграє: offline-стан розв'язано за тебе (desired/reported/delta), fan-out підписок, автентифікація з коробки. Платиш: vendor lock-in, цінник на мільярдах повідомлень, стелі брокера (розмір повідомлення, порядок, QoS-семантика — його, не твоя). · hist-aws-shadow.md · proj-device-shadow.md (мінімальний shadow: desired/reported/delta руками).
- `[own:dh-uplink-choice]` — **Вибір:** клас пристрою (mains vs battery), потрібна latency команд, presence, вартість, хто оперує брокером. Чесний фінал: у реальному флоті — ВСІ три (замок на довгому конекті, датчик вологості ґрунту — полінг, стартап без ops-команди — керований брокер).

### D2. Де живуть автоматизації (якір: Ф8; перша поява теми — Ф3 рушій правил)
- `[own:dh-auto-on-hub]` — **На хабі.** Виграє: дім живий без інтернету (спіраль S2), latency мс («вимикач → світло» без відчутної паузи), приватність — рухи по дому не покидають дім. Платиш: ресурси хаба обмежені, деплой логіки = проблема флоту (мільйон хабів ≠ один сервер), крос-домашні/ML-правила недосяжні, дебаг у полі. · hist-home-assistant.md (local-first як філософія архітектури).
- `[own:dh-auto-in-cloud]` — **У хмарі.** Виграє: один деплой, версіонування, A/B, необмежені обчислення, інтеграції (погода/календар/голос). Платиш: без інтернету дім тупий; 100–500 мс на «ввімкни світло» — користувач ФІЗИЧНО стоїть біля вимикача і чекає; вартість виконання на мільйонах домів. · hist-smartthings-groovy-edge.md (хмарні Groovy SmartApps → аварії → міграція на локальні Edge-драйвери: маятник у живій компанії).
- `[own:dh-auto-hybrid]` — **Гібрид: хмара компілює — хаб виконує.** Правило редагується в хмарі, компілюється в план, план їде на хаб і виконується локально; хмара — лише для правил, що потребують зовнішніх даних. Виграє: автономність + централізоване керування. Платиш: два рушії = дві семантики (те саме правило поводиться по-різному), конфлікт версій «що зараз на хабі», найскладніший дебаг «де виконалось і чому».
- `[own:dh-auto-choice]` — **Вибір:** критичність offline-сценаріїв (безпека/замки — тільки локально), тип правила (реактивне мс-правило vs аналітичне), парк хабів (найслабший хаб визначає стелю), зрілість ops.

### D3. Стан дому (твін) на боці хмари (якір: Ф7→Ф8)
- `[own:dh-twin-actor]` — **Актор-на-дім.** Дім = актор з in-memory станом; команди серіалізуються поштовою скринькою (замок каже дякую). Виграє: природна ізоляція, локальність, жодних гонок у межах дому за побудовою. Платиш: відновлення після падіння вузла (звідки стан? — тягне event log або снапшоти), гарячі доми, supervision-дерева, рідший стек. Ref-місток: actor-model (nb Ф5), Erlang/WhatsApp-кейс уже в дузі.
- `[own:dh-twin-shardeddb]` — **Шардована БД: стан = рядки.** Виграє: звичні транзакції, зрозумілий failover, SQL-аналітика по стану, будь-яка команда розробників це вміє. Платиш: кожна команда = запит-запис у БД (latency, contention на активних домах), presence/ефемерний стан у БД незграбний, «стан на 100 млн пристроїв» = серйозний шардинг.
- `[own:dh-twin-eventlog]` — **Журнал подій + проєкції.** Істина = лог подій дому; твін, історія для підтримки, аналітика — різні проєкції. Виграє: повна історія (діагностика C13: «що бачив дім за хвилину до»), перебудова стану, кілька читальних моделей. Платиш: eventual consistency читань, компакція/снапшоти, найвища планка для команди. 
- `[own:dh-twin-choice]` — **Вибір:** профіль доступу (команд/с vs читань/с), чи потрібна історія як продукт (підтримка! ремонт!), досвід команди. Чесно: багато реальних платформ = B для довгого стану + A-подібний шар з'єднань + E-log для аудиту.

### D4. Відео з камер (якір: ФМ медіа; спирається на Ф6/Ф9)
- `[own:dh-video-p2p]` — **P2P WebRTC** (камера↔апка напряму, TURN як fallback). Виграє: майже нульова вартість серверів, найнижча latency, потік не торкається хмари (приватність як архітектурна властивість). Платиш: NAT-успішність не 100% → TURN однаково будуй; запису/історії немає «сама собою»; N глядачів = ×N вихідних потоків камери; P2P без автентифікації = катастрофа. · hist-ilnkp2p.md (2 млн камер з вгадуваними UID і без auth — CVE-2019-11219). Nb-кандидат: `nb:communications/protocols/webrtc`.
- `[own:dh-video-relay]` — **Relay/SFU через сервер.** Виграє: передбачувано працює скрізь, один потік від камери на N глядачів, запис знімається збоку, контроль якості. Платиш: трафік-цінник (200–400 Гбіт/с на флоті з §2 — це вже CDN-масштабна інфраструктура), +hop latency, потік у хмарі = довіра і регуляції.
- `[own:dh-video-cloudrec]` — **Хмарний запис + плейбек** (сегменти → object storage → HLS/CDN). Виграє: історія/кліпи/шаринг як продукт, ML-аналітика збоку, перегляд масштабується CDN-ом. Платиш: live-latency в секундах, безперервний upload їсть канал юзера і сховище (звідси запис за подіями, pre-roll буфер на камері), приватність максимально гаряча. · hist-ring-privacy.md · hist-eufy-local-lie.md.
- `[own:dh-video-choice]` — **Вибір:** live vs історія — це ДВА різні продукти з різними шляхами; вартість на камеру; приватність/регуляторика; батарейні камери (wake-on-event ламає «завжди на зв'язку»). Чесний фінал: продакшн = A для live з fallback B + C для запису; або HomeKit-шлях (аналіз на хабі, шифровані кліпи) як четверта філософія. · hist-homekit-hsv.md.

### D5. Мультиарендність даних (якір: Ф7; повертається у ФБ/приватність)
- `[own:dh-tenancy-shared]` — **Спільна схема + home_id.** Виграє: найдешевше, один деплой/міграція, аналітика по всіх. Платиш: радіус вибуху (один запит без WHERE home_id — і сусід бачить чужі камери), noisy neighbor, точкове видалення дому (GDPR, спіраль S5) — боляче.
- `[own:dh-tenancy-perhome]` — **База-на-орендаря.** Виграє: ізоляція за побудовою, просте видалення/бекап/перенос дому, B2B-вимоги (готель хоче СВОЮ базу). Платиш: мільйони домів = мільйони БД в лоб не летить (тільки пули/schema-per-tenant), міграції флоту баз, вартість.
- `[own:dh-tenancy-choice]` — **Вибір (гібрид всередині):** масові доми — спільна схема з дисципліною (RLS, tenant-scoped репозиторії з Ф3!), B2B-інсталяції (забудовник на 5000 квартир) — виділені пули. Критерії: регуляторика, розмір найбільшого орендаря, вартість видалення. Сет свідомо 2+1: гібрид — це і є стаття-вибір.

### D6. Локальний API хаба (якір: Ф6; перша поява — v5)
- `[own:dh-localapi-rest]` — **REST+JSON.** Виграє: curl-дебаг, вебапка напряму, звична документація, найнижчий поріг для інтеграторів. Платиш: події доклеюй окремо (SSE/WebSocket), verbose для дрібних викликів, слабка типізація контракту. · hist-hue-bridge.md (локальний REST API мосту Hue — легендарно дружній до розробників; і беклеш 2023, коли Signify зажадала хмарні акаунти).
- `[own:dh-localapi-grpc]` — **gRPC.** Виграє: схема + кодоген на 5 клієнтських платформ, стріми вбудовані, версіонування полів. Платиш: браузер лише через grpc-web/proxy, бінарний дебаг, вага рантайму на хабі з 64 МБ RAM.
- `[own:dh-localapi-binary]` — **Власний бінарний** (TLV/CBOR поверх TCP/WebSocket). Виграє: мінімальний футпринт, повний контроль (embedded-стиль), працює на найдешевшому залізі. Платиш: уся екосистема твоя — кодогени, дебагери, версії, security-ревю; onboarding кожного нового розробника. Чесний referent: Matter — це «власний бінарний TLV», який консорціум будував за мільярди — ось скільки коштує зробити його добре. · hist-matter.md (тут або в D7).
- `[own:dh-localapi-choice]` — **Вибір:** хто клієнти (свої апки чи сторонні інтегратори), скільки платформ, ресурси хаба, культура команди. Місток до api-design/api-versioning з дуги.

### D7. Модель інтеграції пристроїв на хабі (якір: Ф3 плагіни; повернення у ФЕ)
- `[own:dh-drivers-inprocess]` — **Драйвери в процесі (плагіни).** Виграє: швидко, дешевий обмін станом, один деплой. Платиш: краш драйвера = краш хаба, пекло залежностей, довіра сторонньому коду в своєму процесі. · hist-home-assistant.md (2000+ інтеграцій в одному процесі — і що з цього вийшло; якщо hist уже в D2 — тут згадка).
- `[own:dh-drivers-bridges]` — **Окремі процеси-мости через шину** (zigbee2mqtt-стиль). Виграє: ізоляція крашів, будь-яка мова на міст, незалежний рестарт/оновлення. Платиш: IPC-оверхед, зоопарк процесів у деплої, спільний стан лише через шину. · hist-zigbee2mqtt.md (коротко: спільнотна екосистема мостів як доказ життєздатності).
- `[own:dh-drivers-standard]` — **Лише стандартний протокол (Matter-only).** Виграє: жодних драйверів — стандарт нормалізує за тебе, сумісність = сертифікація. Платиш: реальний парк (2026) далеко не весь Matter; стандарт відстає від продукту (камери у стандарті з'явились лише в пізніх версіях — письменнику звірити поточний стан); ти заручник темпу консорціуму. · hist-matter.md (CHIP 2019 → Matter 1.0 жовтень 2022; чому стандартизація повільна і що вона дає).
- `[own:dh-drivers-choice]` — **Вибір:** швидкість підтримки нового заліза vs стабільність ядра; чий код у твоєму процесі; горизонт (стандарт наздожене — а ти доживеш?).

### D8. Сховище телеметрії (якір: ФД; перша поява retention — Ф4 на хабі)
- `[own:dh-tsdb-relational]` — **Реляційна з партиціями.** Виграє: один стек, JOIN з реєстром пристроїв, транзакційність поруч. Платиш: об'єм і write-шлях на мільярдах точок, retention через DROP PARTITION — ок, але індекси/vacuum/компресія — ручна праця.
- `[own:dh-tsdb-timeseries]` — **Спеціалізована TSDB.** Виграє: стиснення дельт 10–20×, downsampling і retention вбудовані, віконні запити рідні. Платиш: ще одна система в проді, кардинальність тегів як міна (device_id × metric — уже мільярди рядів), ad-hoc JOIN слабший. Промоушн із запасу БД: `time-series-databases` (був у «Запас +10» базового плану → підняти в курс).
- `[own:dh-tsdb-objectlake]` — **Сирі події в object storage + колонковий батч** (Parquet-клас). Виграє: найдешевший байт, необмежена ad-hoc аналітика, ML-датасети задарма. Платиш: не realtime (хвилини–години), каталог/компакція/схема — твоя робота.
- `[own:dh-tsdb-choice]` — **Вибір за формою запиту:** «останнє значення» — взагалі не сховище телеметрії, це твін (D3!); «графік за тиждень в апці» — TSDB; «білінг/ML по флоту» — lake. Три запити — три системи, і це нормально.

### D9. Синхронізація стану в клієнтах (якір: ФК клієнти)
- `[own:dh-appsync-pull]` — **Запит-відповідь + pull-to-refresh.** Виграє: тупо просто, stateless, кешовність HTTP. Платиш: «світло вже горить, а в апці ні» — для домашньої апки це смертний гріх; полінг б'є батарею і сервер.
- `[own:dh-appsync-push]` — **Push по WebSocket/SSE: сервер — істина, клієнт — проєкція.** Виграє: живий UI, один канал подій, сервер контролює послідовність. Платиш: reconnect/backfill (пропустив 30 с — що доганяти?), стан з'єднань на сервері, offline — милиці.
- `[own:dh-appsync-localfirst]` — **Локальна репліка + синк** (local-first: апка живе з локальної БД, синк у фоні, optimistic updates). Виграє: миттєвий UI, офлайн-режим і — унікально для DH — **LAN-режим: апка вдома говорить прямо з хабом, навіть коли хмара лежить** (спіраль S2 у клієнті). Платиш: конфлікти/злиття (два телефони перейменували кімнату), складність на порядок, дебаг «чому в тебе інший стан».
- `[own:dh-appsync-choice]` — **Вибір:** частота змін стану, вимога офлайн/LAN, бюджет складності. DH-специфіка чесно штовхає в C — і це рідкісний домен, де local-first виправданий не ідеологією, а фізикою (хаб поруч).

### D10. OTA-флот: як котити прошивку на мільйон пристроїв (якір: Ф10; дзеркало deployment-strategies у залізо)
- `[own:dh-ota-waves]` — **Хвилі з health-гейтами** (0.1% → 1% → 10% → 100%, автостоп за метриками флоту). Виграє: ловить погану прошивку до масштабу. Платиш: тижні на повну розкатку; потрібна телеметрія здоров'я — а її ламає саме погане оновлення (курка/яйце: канал діагностики має переживати оновлення).
- `[own:dh-ota-consent]` — **Вікна за згодою** (нічні; «не під час запису»; користувач тисне «пізніше»). Виграє: довіра, не ламає активні сценарії (OTA замка, коли господар у відпустці?). Платиш: хвости версій живуть місяцями → матриця сумісності протоколів росте (N і N−3 у одному домі). · hist-tesla-ota.md (staged + підтвердження водія; гальмівний шлях Model 3 −6 м за тиждень після Consumer Reports, 2018 — письменнику звірити цифри).
- `[own:dh-ota-slots-rollback]` — **A/B-слоти + автовідкат на пристрої.** Виграє: безпека на рівні одиниці — нова не піднялась → стара вантажиться сама. Платиш: 2× flash = BOM-цінник кожного сенсора; відкат не рятує від «піднялась, але шкодить». Ref-и: `programming/embedded-systems/ota-slots` (done), `ota-update` (done), `ota-rollback`/`delta-ota`/`ota-image-signing` (pending — підняти пріоритет). · hist-lockstate-bricked.md (2017: оновлення не тієї моделі поклало ~500 замків офлайн — фізичний ключ лишався; Airbnb-хости постраждали — письменнику звірити деталі).
- `[own:dh-ota-choice]` — **Вибір-композиція:** продакшн = A+B+C шарами; стаття показує, що різати першим на дешевому сенсорі (2× flash під ніж? — тоді компенсуй хвилями і golden-image recovery). Місток: deployment-strategies (софт) ↔ це саме, але відкат коштує flash, а «сервер» стоїть у чужій спальні.

### D11 (опційний). Мова правил автоматизацій (якір: Ф3 плагіни/DSL)
- `[own:dh-rules-declarative]` — **Декларативні тригер-умова-дія** (IFTTT/HA-automations-стиль). Виграє: просто, статично аналізовно (конфлікти правил можна знайти до запуску). Платиш: стеля виразності — «хочу цикл» → милиці.
- `[own:dh-rules-dataflow]` — **Візуальні вузли-потоки** (Node-RED-стиль). Виграє: доступно не-програмістам, композиція. Платиш: дифи/версіонування болять, спагеті на 200 вузлів.
- `[own:dh-rules-scripting]` — **Скриптинг у пісочниці** (Lua/JS). Виграє: повна виразність. Платиш: пісочниця (ресурси, безпека, таймаути) — окремий інженерний проєкт; користувацький код = довічна сумісність API.
- `[own:dh-rules-choice]` — **Вибір:** аудиторія (споживач/ентузіаст/інтегратор), аналізовність проти виразності. Не-DH дзеркало: моди ігор і розширення редакторів — та сама драбина.

### D12 (опційний). Віддалений доступ до хаба (якір: Ф6, поруч із NAT)
- `[own:dh-remote-relay]` — **Все через хмару-релей.** Виграє: одна кодова путь, працює скрізь. Платиш: удома трафік їде через континент; хмара лягла — апка сліпа навіть у своєму Wi-Fi; приватність.
- `[own:dh-remote-nat]` — **NAT-траверсаль + прямий тунель** (STUN/hole punching, relay-fallback). Виграє: latency/вартість/приватність. Платиш: складність, реальність CGNAT, відсоток неуспіху → relay однаково будуй. Ref-и: `communications/networks/nat` (pending), `communications/protocols/nat-traversal` (pending — підняти пріоритет).
- `[own:dh-remote-choice]` — **Вибір** (2+1: VPN-оверлей WireGuard-класу розібрати всередині вибору як третій шлях для ентузіастів/B2B). · hist-ha-remote.md (Home Assistant: порт-форвардинг небезпечний → Nabu Casa relay як бізнес-модель open-source).

**Бюджет сетів:** D1–D10 = 29 варіантів + 10 виборів = 39 own; D11–D12 = +7. Разом 46 максимум, 39 у ядрі.

## 4. Наскрізні конфлікти-спіралі (замість «останнього квитка»)

Спіраль = конфлікт, що повертається на вищих поверхах дуги. Станції — здебільшого ВСЕРЕДИНІ тем і DH-кроків (не окремі кроки), кульмінації — виділені own.

### S1. «Замок дверей — команда рівно раз»
Фізичний актуатор робить exactly-once гострішим за платіжку: гроші можна компенсувати, відчинені о 3-й ночі двері — ні. Станції: Ф1 контракти (що означає «виконано»? підтвердження від залізяки, не від черги) → Ф2 command (ідентичність команди) → Ф4 журнал команд + дедуп → Ф6 ретраї/ідемпотентність/delivery-guarantees (at-least-once + дедуп на пристрої; команда з TTL — «відчини» не має виконатись через годину) → Ф8 **кульмінація `[own:dh-lock-exactly-once]`**: черга команд у твіні, offline-хаб (чекає? скасовується?), аудит → Ф10 постмортем «замок клацнув, коли ніхто не просив» — трейс команди крізь усі шари.

### S2. «Інтернет упав — дім живий»
Головна DH-спіраль, обґрунтовує пів курсу. Станції: Ф3 D2 (де правила) → Ф4 store-and-forward буфер телеметрії на хабі → Ф7 **`[own:dh-hub-cloud-reconcile]`**: тиждень офлайн — хто правий, хаб чи твін; напрямки правди (reported/desired), протилежні зміни → ФК D9-C (LAN-режим апки) → Ф10 моніторинг «дір» у даних (офлайн ≠ інцидент). Кейси: hist-insteon-wink.md і hist-revolv-shutdown.md — що буває, коли «дім живий» не було вимогою.

### S3. «18:00 всі вдома + блекаут-відновлення флоту»
Станції: Ф5 з'єднання = стан → Ф9 **`[own:dh-evening-peak]`** (добовий патерн передбачуваний — автоскейл за розкладом, не за метрикою) і **`[own:dh-blackout-reconnect]`**: район увімкнувся — 100 тис. хабів реконектяться одночасно, thundering herd, холодні кеші твіна, метастабільність. Унікальний DH-урок, якого немає у веб-доменах: **backoff+jitter мусить бути в прошивці з першого дня** — клієнтів не оновиш за годину, якщо джитера нема — ти приречений на роки. · proj-reconnect-storm.md (симуляція шторму з/без джитера «в прошивці»; перекликається з proj-backoff-jitter базової дуги — там веб-клієнти, тут неоновлювані). Пріоритети деградації: замки/безпека > опалення > лампочки > статистика (load shedding за класами).

### S4. «Нова камера за хвилину»
Онбординг як архітектурна тема, не UX-дрібниця. Станції: Ф3 FSM пристрою (`dh-device-lifecycle-fsm`) → Ф6 discovery (mDNS/BLE-провіжн; nb-кандидат запасу: `communications/networks/mdns`) → ФБ довіра з першого рукостискання: QR+сертифікат, TOFU проти PKI, Matter-комішенінг як еталон → Ф8 реєстрація в хмарі (`dh-device-identity`) → Ф10 day-0 OTA просто з коробки (прошивка річної давнини має спершу безпечно оновитись). Кульмінація: **`[own:dh-camera-onboarding]`** (ФМ) — весь шлях за 60 секунд, і що в них вміщається.

### S5. «Сім'я продає дім — передача володіння»
Безпека + дані + довгі операції в одному сюжеті. Станції: Ф4 модель володіння (user↔home↔devices; хто «власник» — людина чи дім?) → Ф8 **кульмінація `[own:dh-handover-saga]`**: сага «передати дім» — відкликати доступи й сесії, перевипустити сертифікати пристроїв, стерти персональні дані, зберегти/не зберегти конфіг автоматизацій, factory-reset за вимогою; компенсації на кожному кроці → ФБ «старий власник без бекдорів» (б/у камери зі збереженим доступом попереднього власника — неодноразові кейси в пресі, письменнику підібрати перевірені) → Ф10 `[own:dh-privacy-deletion]`: GDPR-видалення проти бекапів/логів/архівів телеметрії, retention за призначенням.

## 7. Де DH — НЕ найкраща ілюстрація (чесний список для синтезу)

| Тема | Чому DH слабший | Чесніший домен |
|---|---|---|
| Гонка за обмежений ресурс (інвентар, останній квиток/товар) | у DH немає природного дефіциту | flash sale / ticketing (лишити rozbir-flash-sales, Ticketmaster×Swift) |
| Fan-out стрічки, «проблема зірки», гарячий ключ | дім не має мільйона фоловерів | соцмережа (Twitter fan-out — уже в дузі) |
| Компенсація лагу, client prediction, rollback, tick-симуляція | DH-відео — потік, а не спільна симуляція | гра (multiplayer netcode) — для ігрової фази універсального курсу |
| Грошові саги з компенсаціями | замок — кейс БЕЗ компенсації (двері не «відвідчиниш»); гроші — кейс З компенсацією; потрібні обидва | платіжка (Stripe idempotency — вже в дузі) як пара до dh-lock-exactly-once |
| PB-масштаб OLAP, трильйони рядків | DH-телеметрія чесно живе в TB-діапазоні | клікстрім / Discord-повідомлення (вже в дузі) |
| Пошук/ранжування/рекомендації | у DH пошук тривіальний | e-commerce / пошуковик |
| Мікросекундна latency, mechanical sympathy | DH-стелі — мілісекунди | трейдинг (LMAX — вже в дузі) |
| Рендер-пайплайни, GPU | апка DH — форми і графіки | гра / медіаредактор |
| Колаборативне редагування, CRDT глибоко | конфлікти в DH дрібні (перейменування кімнати) | спільний редактор документів (згадати в D9-C як сусідній світ) |

І навпаки — де DH **сильніший за будь-яку альтернативу:** фізичні актуатори (exactly-once без компенсацій), офлайн-автономія (S2), неоновлювані клієнти (S3: джитер у прошивці), онбординг заліза (S4), передача володіння фізичного об'єкта (S5), agregating edge (хаб як природний приклад gateway/edge-обчислень), приватність як архітектурна властивість (D4).

## 8. Бюджет і драбина скорочення

**Повний пакет DH:** 46 варіантних own (12 сетів) + ~21 own еволюції/спіралей/синтезу = **~67 own-кроків** + ~23 вставки. Для курсу ~500 кроків це ~13% — порівнянно з часткою «Квитка» в базовому плані (61/264 ≈ 23%), тобто DH ЛЕГШИЙ за квиток відносно, як і просив користувач («ілюструє, не організує»).

**Ядро (якщо синтезу тісно, ~52):** сети D1–D10 (39) + 13 ключових own: dh-v0, dh-v1, dh-v2-hub-hexagon, dh-contexts-map, dh-v3-hub-storage, dh-v6-cloud-link, dh-hub-cloud-reconcile, dh-v8-services-map, dh-lock-exactly-once, dh-handover-saga, dh-blackout-reconnect, dh-camera-onboarding, dh-fleet-envelope.

**Драбина різання далі:** (1) D11, D12 → у статті-вибори сусідніх сетів; (2) dh-device-lifecycle-fsm злити з dh-v2; dh-evening-peak злити з dh-fleet-envelope; (3) у сетах D5/D12 уже 2+1; так само можна стиснути D7 (standard-only → у вибір) і D1 (polling → у вибір) до 2+1, −2 кроки кожен; (4) dh-dev-analytics і dh-sensor-firmware-arch — перші кандидати на «згадку всередині теми» замість окремого кроку. Нижня межа осмисленого DH ≈ 40 own.

**Правило вплетення для синтезу:** DH-крок ставиться ПІСЛЯ тем, які він збирає (як kvytok-кроки в базовому плані); варіантний сет — одним розділом «Рішення: …» усередині відповідного модуля (розділ = одна мета: ухвалити ЦЕ рішення); спіралі S1–S5 НЕ отримують окремих кроків на ранніх станціях — лише абзаци-повернення в тілі тем (маркер для письменників у scope кроку).
