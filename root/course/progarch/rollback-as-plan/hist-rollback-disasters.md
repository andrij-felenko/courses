# 📜 Історія катастрофічних відкатів: від ручного DDL до незворотних втрат

Історичний аналіз фундаментальних аварій у розподілених системах доводить: спроба застосувати зворотний деплой коду як спонтанну реакцію на збій без заздалегідь спроектованого плану сумісності даних майже завжди перетворює тимчасову несправність на незворотну катастрофу.

Упродовж перших двох десятиліть розбудови високонавантажених веб-систем (1995–2015 роки) операційні інженери та розробники сприймали відкат (rollback) як чарівну «аварійну кнопку». Вважалося, що якщо нова версія застосунку демонструє помилки або деградацію продуктивності, достатньо повернути попередній бінарний збірник чи Docker-образ, і система миттєво відновиться до працездатного стану. Проте фізика розподілених даних та незворотний характер DDL-операцій у реляційних базах даних регулярно руйнували цю ілюзію, залишаючи після себе зруйнований стан та втрачені транзакції.

## 1. Сліпий відкат коду: катастрофа Knight Capital (2012)

Найвідомішим і найдорожчим прикладом катастрофічного відкату в історії програмної інженерії стала аварія на фондовому ринку американської компанії **Knight Capital Group** 1 серпня 2012 року, яка коштувала підприємству \$440 мільйонів доларів за 45 хвилин і призвела до його негайного банкрутства.

Аналіз інциденту Комісією з цінних паперів і бірж США (SEC) виявив, що корінням катастрофи був саме **непропланований, частковий відкат коду** на тлі зміни внутрішніх прапорів стану та невикористання ідемпотентних контрактів:

```
[Початковий стан]
Вузли 1..8: Код v1 (Використовує прапор Power Peg для старої логіки розрахунку)

[Крок 1: Часткове розгортання v2]
Вузли 1..7: Успішно оновлено до коду v2 (Прапор Power Peg перепризначено під новий алгоритм RETAIL)
Вузол 8:    Оновлення ПРОПУЩЕНО через помилку інженера (Залишився код v1)

[Крок 2: Запуск торгів]
Вузол 8 (v1) отримує нові ордери з прапором Power Peg -> сприймає його за СТАРОЮ логікою
-> впадає в безкінечний цикл генерації мільйонів безглуздих заявка-купівель.

[Крок 3: Сліпий відкат (Спонтанна реакція)]
Інженери бачать аномальну поведінку -> поспіхом ВІДКОЧУЮТЬ вузли 1..7 НАЗАД до коду v1.
Результат: УСІ 8 вузлів тепер працюють на коді v1, але прапори v2 вже змінили стан ринку!
Каскадна генерація невалідних ордерів зросла у 8 разів, знищивши капітал фірми.
```

Механізм цієї катастрофи полягав у тому, що новий код v2 повторно використав старий внутрішній прапор (Bit Flag) `Power Peg`, який у версії v1 відповідав за відключений тестовий режим автоматичної торгівлі. Коли сервіс v1 на 8-му вузлі отримав нові повідомлення, він сприйняв прапор `Power Peg` не як атрибут нового роздрібного алгоритму, а як сигнал виконувати безкінечний цикл виклику тестових ордерів без обмеження ціни.

Головна помилка інженерів сталася на етапі реакції: побачивши мільйони помилкових транзакцій, вони вирішили, що новий код v2 зламаний, і відкотили решту 7 вузлів назад на версію v1. Це перетворило проблему одного некоректного вузла на загальний каскадний колапс: усі 8 вузлів почали генерувати шторм невалідних ордерів. Повернення бінарних файлів v1 відбулося без відкату стану даних та без зупинки обробки невалідних прапорів, що призвело до повної втрати ліквідності компанії.

## 2. Руйнівний DDL та злам сумісності схем (2005–2015)

Зі зростанням обсягів даних у реляційних базах (PostgreSQL, MySQL, Oracle) другою головною пасткою став ручний виклик DDL-команд під час розгортання оновлень.

У класичній монолітній архітектурі 2000-х років стандартний сценарій міграції передбачав єдиний SQL-скрипт з операціями `ALTER TABLE users DROP COLUMN legacy_pass_hash` або `ALTER TABLE orders RENAME COLUMN price TO total_amount`. 

Коли під час викачування нового коду виявлявся баг (наприклад, вичерпання пулу з'єднань або збій у бізнес-логіці), інженери виконували автоматичний відкат застосунку. Протім старий код v1, повернений у виробниче середовище, негайно падав з помилкою `Fatal: unknown column legacy_pass_hash in field list`.

```
           Прямий реліз                                   Сліпий відкат
   +---------------------------+                   +---------------------------+
   |  Застосунок v2 (Новий)    |                   |  Застосунок v1 (Відкочений)|
   +---------------------------+                   +---------------------------+
                |                                                |
        Викликає DDL:                                     Очікує на поле:
     DROP COLUMN legacy_field                           `legacy_field`
                |                                                |
                v                                                v
   +---------------------------+                   +---------------------------+
   |  База даних (Схема v2)    |                   |  База даних (Схема v2)    |
   |  Поле `legacy_field`      |                   |  Поле `legacy_field`      |
   |  ЗНИЩЕНО НАЗАВЖДИ         |                   |  ВІДСУТНЄ                 |
   +---------------------------+                   +---------------------------+
                                                                 |
                                                          💥 ПОВНИЙ КРАШ
                                                        (CRASH ON STARTUP)
```

Спроби інженерів створити зворотні скрипти міграцій (Down-migrations) у вигляді `ALTER TABLE users ADD COLUMN legacy_pass_hash VARCHAR(255)` демонстрували нерозуміння фізики даних. Такий DDL-скрипт створював порожню колонку, заповнену значеннями `NULL`. Усі нові користувачі, які зареєструвалися під час 15-хвилинного вікна роботи версії v2, втратили свої парольні геші або дані про оплати. Відкат схеми відбувся, але дані були незворотно втрачені.

Інший драматичний випадок стався під час аварії у сервісі електронної комерції у 2014 році, коли міграція додавала суворе обмеження `NOT NULL` без значення за замовчуванням (Default Value) на нову колонку `tax_jurisdiction_id`. Коли систему відкотили через баг у платіжному шлюзі, старий код v1 продовжував виконувати оператори `INSERT INTO orders` без зазначення цього поля. База даних відхиляла 100% нових замовлень із помилкою `IntegrityConstraintViolation`. Наївна спроба повернутися до v1 зупинила роботу бізнесу на 4 години, доки інженери вручну не зняли обмеження `NOT NULL`.

## 3. Операційні аварії відкату в хмарній інфраструктурі

З появою хмарних платформ та інфраструктури як коду (IaC) аварії відкату перемістилися з рівня баз даних на рівень конфігурацій мережі та оркестрації контейнерів.

У лютому 2017 року під час планової процедури технічного обслуговування підсистеми індексації **AWS S3** в регіоні US-EAST-1 інженер намагався відкотити конфігурацію серверів метаданих. Через помилку в аргументах скрипта автоматизований процес вимкнув значно більшу кількість серверів підсистеми Placement Index, ніж планувалося. 

Спроба автоматичного відновлення та відкату конфігурації призвела до того, що підсистема метаданих була змушена виконувати повне перезбирання стану з первинних логів (Cold Restart). Через величезний обсяг накопиченого стану (accumulated state) процес запуску відкоченої конфігурації тривав понад 4 години, спричинивши каскадне падіння тисяч залежних сервісів по всьому світу. Ця аварія довела, що **часова затримка запуску відкоченого стану (Warm-up / Recovery Time)** є критичним фактором безпеки відкату.

Додатковим уроком стала аварія на платформі **GitHub** у листопаді 2018 року під час масштабної міграції топології MySQL. Спроба скасувати деплой та відкотити майстер-вузол бази даних під час мережевого розщеплення (Network Partition) призвела до ситуації Split-Brain: відкочений старий майстер та новий майстер одночасно приймали записи від різних частин веб-фронтендів. У результаті інженерам знадобилося понад 24 години на процедуру виявлення та ручного розплутування конфліктів у логах транзакцій (Data Reconciliation).

## 4. Досвід Stripe та Netflix: автоматичне Хаос-тестування відкату

На тлі постійних ризиків зламу продакшену платіжна платформа **Stripe** розробила одну з найсуворіших у галузі систем безпеки розгортання змін. Інженери Stripe сформулювали концепцію, згідно з якою **будь-яка міграція баз даних повинна перевірятися статичним аналізатором (Migration Linter) ще на етапі Pull Request**.

Лінтер Stripe автоматично блокує розгортання, якщо PR містить принаймні одну з наступних небезпечних операцій:

- `DROP TABLE` або `DROP COLUMN` у єдиному релізі з кодом.
- `RENAME COLUMN` або `RENAME TABLE` (замість цього вимагається створення нового поля та дублювання запису).
- Додавання колонки з обмеженням `NOT NULL` без зазначення `DEFAULT`.
- Створення нових індексів без прапора `CONCURRENTLY` у PostgreSQL (що блокує операції `WRITE` під час побудови дерева).

Stripe запровадив обов'язкову двофазну схему згортання: старі колонки та таблиці маркуються як `deprecated`, але залишаються недоторканими в базі даних протягом як мінімум 30 днів після 100% викачування нового коду. Лише після того, як автоматизовані монітори підтверджують відсутність жодного SQL-запиту до застарілих полів, окремий асинхронний процес виконує фазу Contract (фізичне видалення).

У компанії **Netflix** концепцію відкату перетворили на автоматизований процес суцільного хаос-тестування (Chaos Engineering & Automated Canary Analysis). Інструмент **Kayenta**, розроблений спільно з Google, безперервно порівнює метрики канарейки v2 із контрольним середовищем v1. Якщо у канарейці спостерігається деградація продуктивності або сплеск помилок понад заданий поріг, Kayenta автоматично зупиняє розгортання та ініціює відкат трафіку без участі людини.

## 5. Перехід від Flyway/Liquibase до декларативних систем міграції

Еволюція інструментарію управління міграціями пройшла важливий шлях від імперативних SQL-файлів до декларативних моторів сумісності схем:

- **Перше покоління (Flyway, Liquibase, Active Record Migrations)**: Базувалося на парних SQL-файлах `V1__init.sql` та `U1__undo_init.sql`. Головна вада цього підходу полягала у припущенні, що ручний файл `undo` здатен коректно відкотити стан бази даних. На практиці інженери рідко тестували `undo`-скрипти на реальних обсягах даних, а самі скрипти часто містили руйнівні оператори `DROP`.
- **Друге покоління (Atlas, Bytebase, Schemahero)**: Сучасні інструменти декларативної еволюції схем сприймають базу даних як стан (Infrastructure as Code). Замість виконання списку ручних SQL-команд інженер описує бажану цільову схему. Мотор міграції автоматично порівнює поточний стан бази даних із цільовим, генерує план переходу та оцінює коефіцієнт небезпеки (Risk Score). Якщо згенерований план містить руйнівну операцію, яка зламає зворотно-сумісний відкат коду v1, система відхиляє міграцію на стадії CI/CD pipeline.

## 6. Еволюція інструментів та виникнення патерну Expand-Contract

Регулярні збої та втрати даних у великих технологічних компаніях підштовхнули індустрію до перегляду фундаментальних принципів зміни схем даних та розгортання.

1. **Ера pt-online-schema-change та gh-ost (2010–2015)**: Інженери MySQL у GitHub та Percona довели, що DDL-операції не повинні блокувати таблиці й мають виконуватися у фоні через створення тіньових таблиць із тригерами дзеркалювання трафіку. Це дозволило перервати міграцію в будь-який момент без шкоди для основної таблиці.
2. **Формалізація фаз Expand-Contract (2013–2016)**: Праці з еволюційного дизайну баз даних (Martin Fowler, Pramod Sadalage) обґрунтували залізне правило: **жодна DDL-операція не повинна видаляти або перейменовувати існуючі елементи схеми в одному релізі з викачуванням нового коду**. Будь-яка зміна розділяється на дві незалежні фази, розділені часовим вікном безпеки.
3. **Виникнення Schema Registry та суворого контракту (2015–дотепер)**: Розвиток подійних систем (Apache Kafka, Confluent) приніс розуміння, що відкат коду в подійній архітектурі вимагає сумісності повідомлень уперед та назад (Full Compatibility). Якщо новий сервіс v2 публікує подію в брокер, відкочений сервіс v1 повинен безпечно прочитати її без аварійного завершення (патерн Tolerant Reader).

Сучасна архітектурна парадигма остаточно відмовилася від сприйняття відкату як відмотування часу назад. Відкат у сучасних розподілених системах — це **контрольований рух уперед за заздалегідь підготовленим та протестованим планом сумісності**.
