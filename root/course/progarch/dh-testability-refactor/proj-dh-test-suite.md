# ⚙️ Набір тестів DH: три шари, дві мови, жодного заліза

Стаття показала зерно — по одному рядку на кожен рівень. Тут повний набір, який можна вставити в репозиторій і запустити: таблиця істинності чистої `decide`, батарея тестів проводки на фейку й шпигуні, і окремо — розбір того, як фейк, що бреше про залізо, робить зелений тест порожнім. Мов дві: `pytest` для Python і `vitest` для TypeScript, кожна ідіоматична сама по собі, а не переписана з іншої.

Щоб набір справді запускався, спершу зафіксуймо, **що** саме він перевіряє. Це той самий код v1, у тих самих формах; тут він лише зібраний в одному місці як предмет тестів.

:::tabs
```py
# home.py — код під тестом (форми v1, без змін)
from dataclasses import dataclass
from enum import Enum, auto
from typing import Protocol

@dataclass(frozen=True)
class Reading:
    celsius: float
    ok: bool = True          # False ⇒ числу вірити не можна

@dataclass(frozen=True)
class Config:
    threshold: float = 20.0

class Command(Enum):
    HEAT = auto()
    IDLE = auto()

class Sensor(Protocol):
    def read(self) -> Reading: ...

class Heater(Protocol):
    def on(self)  -> None: ...
    def off(self) -> None: ...

def decide(r: Reading, cfg: Config) -> Command:      # чиста: вхід-значення → вихід-значення
    if not r.ok:
        return Command.IDLE
    return Command.HEAT if r.celsius < cfg.threshold else Command.IDLE

def tick(sensor: Sensor, heater: Heater, cfg: Config) -> None:   # рівно один оберт
    match decide(sensor.read(), cfg):
        case Command.HEAT: heater.on()
        case Command.IDLE: heater.off()
```
```ts
// home.ts — код під тестом (форми v1, без змін)
export interface Reading { celsius: number; ok: boolean; }   // ok=false ⇒ числу не вірити
export interface Config  { threshold: number; }
export type Command = "HEAT" | "IDLE";

export interface Sensor { read(): Reading; }
export interface Heater { on(): void; off(): void; }

export function decide(r: Reading, cfg: Config): Command {    // чиста: значення → значення
  if (!r.ok) return "IDLE";
  return r.celsius < cfg.threshold ? "HEAT" : "IDLE";
}

export function tick(sensor: Sensor, heater: Heater, cfg: Config): void {  // один оберт
  const cmd = decide(sensor.read(), cfg);
  if (cmd === "HEAT") heater.on();
  else heater.off();
}
```
:::

Одна деталь тут вирішальна для всього набору, тож назвімо її вголос: поріг **виключний знизу**. `decide` гріє, лише поки `celsius < threshold` — рівно на порозі (`20.0` при `threshold=20.0`) вона вже мовчить. Це не дрібниця стилю: це рівно той рядок, який тест зафіксує, щоб наступний, хто його зачепить, зробив це навмисно, а не випадково.

## Шар перший — таблиця істинності чистої decide

Почнімо з найдешевшого. `decide` не читає термометра й не смикає розетки; вона перетворює двійко значень на третє. А отже, її вся поведінка вкладається в таблицю: стовпці — вхід (`celsius`, `ok`) і `Config`, останній стовпець — очікувана команда. Кожен рядок — окремий приклад «за таких умов — така відповідь», і жоден із них не торкається світу поза процесом.

Обидві мови мають для цього рідну форму параметризації, тож таблиця в коді буквально виглядає таблицею — рядок даних окремо, тіло перевірки одне на всіх:

:::tabs
```py
# test_decide.py
import pytest
from home import Reading, Config, Command, decide

CFG = Config(threshold=20.0)

@pytest.mark.parametrize("r, expected", [
    pytest.param(Reading(5.0),            Command.HEAT, id="глибокий-холод→HEAT"),
    pytest.param(Reading(19.0),           Command.HEAT, id="нижче-порога→HEAT"),
    pytest.param(Reading(19.999),         Command.HEAT, id="на-волосину-нижче→HEAT"),
    pytest.param(Reading(20.0),           Command.IDLE, id="рівно-на-порозі→IDLE"),
    pytest.param(Reading(20.001),         Command.IDLE, id="на-волосину-вище→IDLE"),
    pytest.param(Reading(25.0),           Command.IDLE, id="тепло→IDLE"),
    pytest.param(Reading(5.0,  ok=False), Command.IDLE, id="холод+мовчить→IDLE"),
    pytest.param(Reading(25.0, ok=False), Command.IDLE, id="тепло+мовчить→IDLE"),
])
def test_decide_covers_every_branch(r, expected):
    assert decide(r, CFG) == expected
```
```ts
// decide.test.ts
import { describe, it, expect } from "vitest";
import { decide, type Reading, type Config, type Command } from "./home";

const CFG: Config = { threshold: 20.0 };
const R = (celsius: number, ok = true): Reading => ({ celsius, ok });

describe("decide покриває кожну гілку", () => {
  const cases: Array<[Reading, Command]> = [
    [R(5.0),         "HEAT"],   // глибокий холод
    [R(19.0),        "HEAT"],   // нижче порога
    [R(19.999),      "HEAT"],   // на волосину нижче
    [R(20.0),        "IDLE"],   // рівно на порозі
    [R(20.001),      "IDLE"],   // на волосину вище
    [R(25.0),        "IDLE"],   // тепло
    [R(5.0,  false), "IDLE"],   // холод, але давач мовчить
    [R(25.0, false), "IDLE"],   // тепло, і давач мовчить
  ];
  it.each(cases)("decide(%o) → %s", (r, expected) => {
    expect(decide(r, CFG)).toBe(expected);
  });
});
```
:::

Придивіться, скільки тут вкрито однією обоймою. Дві справжні гілки політики — «холодно, грій» і «тепло, не грій» — з парою прикладів на кожну. Стик між ними, де плутанина найдорожча: `19.999` ще гріє, `20.0` уже ні. І поперечний зріз через обидві: коли `ok=false`, температура не важить зовсім — і холод, і тепло дають спокій, бо `decide` спершу питає «а чи вірю я цьому числу?». Вісім рядків описують **усю** політику дому, і жодному з них не потрібне залізо.

Ціна цього — головне, заради чого форму v1 різали чистою. Уся ця таблиця відпрацьовує за мікросекунди: немає драйвера, що піднімається, немає таймера на тридцять секунд, немає розетки, яку відкочувати після тесту. Таких перевірок можна мати не вісім, а вісімсот, і ганяти їх на кожне збереження файлу, навіть не помітивши затримки. Це і є [найширша, найдешевша основа піраміди](root:progarch/test-boundaries) — дрібні миттєві перевірки чистої логіки, яких багато.

> 🔧 **Навіщо це.** Політика порогів у справжньому домі не лишається двома гілками. Додається нічний поріг, гістерезис проти сіпання реле, окремі кімнати, режим «нікого немає — не грій». Кожне таке правило — новий рядок таблиці, і кожен коштує рівно один рядок, поки `decide` чиста. Таблична форма ще й змушує думати межами: щойно вписуєш «нижче порога → HEAT», рука сама тягнеться дописати «рівно на порозі → ?», і ти ловиш дірку в специфікації **до** того, як вона поїде в прод. Таблиця — це не просто тести, це виконуваний опис політики, який неможливо лишити напівпорожнім непомітно.

Один рядок вартий окремого слова — той, де `19.999` і `20.0` розходяться. Це не декоративна прискіпливість. Знак порівняння в `decide` (`<`, не `<=`) — це рішення, і без прикладу воно живе тільки в голові автора. Рядок «рівно на порозі → IDLE» перетворює його на факт: якщо завтра хтось поміняє `<` на `<=`, цей рядок почервоніє, і зміна поведінки стане видимою, а не тихою. Тест межі — це спосіб примусити наступного програміста зачепити межу **навмисно**.

## Шар другий — проводка: tick, фейк, шпигун

Чиста `decide` каже, **що** робити. Але дім ще має **докрутити** сказане до заліза: холодний вимір мусить увімкнути саме розетку, а не переплутати `on` з `off`; мертвий давач мусить її погасити. Ця проводка живе у збірці, а збірка тягнеться до справжнього термометра й реле. Здавалося б, тут офлайн-тест і впирається в стіну.

Не впирається — бо між політикою й розкладом ми проклали шов. Нагадаю форму: `run` крутить нескінченний цикл `while True: … sleep(30)`, і в ньому проводка одного обороту зрощена з розкладом. Розклад тестові не потрібен — ніхто не чекатиме тридцять секунд на оберт. Тож **один оберт** живе окремою функцією `tick`, а `run` лише повторює її за годинником:

:::tabs
```py
from time import sleep

def run(sensor: Sensor, heater: Heater, cfg: Config) -> None:
    while True:
        tick(sensor, heater, cfg)   # логіка обороту — те, що тестуємо
        sleep(30)                   # розклад — те, що тестові не потрібне
```
```ts
function run(sensor: Sensor, heater: Heater, cfg: Config): void {
  while (true) {
    tick(sensor, heater, cfg);   // логіка обороту — те, що тестуємо
    sleep(30_000);               // розклад — те, що тестові не потрібне
  }
}
```
:::

Тепер `tick` можна викликати рівно раз, згодувавши йому не справжнє залізо, а два дублери. **Фейк** давача віддає наперед задані виміри — стільки, скільки їх треба обороту. **Шпигун** розетки нічого не гріє, а тихо записує, що його просили ввімкнути чи вимкнути. Обидва тримають той самий інтерфейс, що й справжні порти, тож `tick` не бачить різниці:

:::tabs
```py
# doubles.py
from home import Reading, Sensor, Heater

class FakeSensor:                       # фейк: віддає задані виміри, один за одним
    def __init__(self, *readings: Reading):
        self._q = list(readings)
    def read(self) -> Reading:
        return self._q.pop(0)           # порожня черга → IndexError, і це добре (див. пастки)

class SpyHeater:                        # шпигун: нічого не гріє, лише пам'ятає виклики
    def __init__(self):
        self.calls: list[str] = []
    def on(self):  self.calls.append("on")
    def off(self): self.calls.append("off")
```
```ts
// doubles.ts
import type { Reading, Sensor, Heater } from "./home";

export class FakeSensor implements Sensor {   // фейк: віддає задані виміри, один за одним
  private q: Reading[];
  constructor(...readings: Reading[]) { this.q = readings; }
  read(): Reading {
    const r = this.q.shift();
    if (r === undefined) throw new Error("FakeSensor вичерпано");  // інакше — тихий undefined
    return r;
  }
}

export class SpyHeater implements Heater {    // шпигун: нічого не гріє, лише пам'ятає виклики
  calls: string[] = [];
  on()  { this.calls.push("on"); }
  off() { this.calls.push("off"); }
}
```
:::

Тепер батарея тестів проводки. Кожен вставляє фейк і шпигуна в `tick`, крутить один оберт (або кілька) і питає шпигуна, що той запам'ятав. Точка ввімкнення — рядок, де ми обираємо, кого підставити, — стоїть у тесті, поза перевіреним кодом:

:::tabs
```py
# test_wiring.py
from home import Reading, Config, tick
from doubles import FakeSensor, SpyHeater

CFG = Config(threshold=20.0)

def test_cold_reading_turns_heater_on():
    heater = SpyHeater()
    tick(FakeSensor(Reading(18.0)), heater, CFG)
    assert heater.calls == ["on"]       # холодний вимір докрутив саме розетку

def test_warm_reading_turns_heater_off():
    heater = SpyHeater()
    tick(FakeSensor(Reading(22.0)), heater, CFG)
    assert heater.calls == ["off"]      # теплий — вимкнув, а не забув

def test_dead_sensor_turns_heater_off():
    heater = SpyHeater()
    tick(FakeSensor(Reading(5.0, ok=False)), heater, CFG)
    assert heater.calls == ["off"]      # холодно, та вірити нема чому → не грій

def test_each_turn_drives_the_heater():
    heater = SpyHeater()
    sensor = FakeSensor(Reading(18.0), Reading(22.0), Reading(19.0))
    for _ in range(3):
        tick(sensor, heater, CFG)
    assert heater.calls == ["on", "off", "on"]   # кожен оберт докрутив свою команду
```
```ts
// wiring.test.ts
import { describe, it, expect } from "vitest";
import { tick, type Config } from "./home";
import { FakeSensor, SpyHeater } from "./doubles";

const CFG: Config = { threshold: 20.0 };

describe("tick докручує проводку", () => {
  it("холодний вимір вмикає розетку", () => {
    const heater = new SpyHeater();
    tick(new FakeSensor({ celsius: 18.0, ok: true }), heater, CFG);
    expect(heater.calls).toEqual(["on"]);
  });

  it("теплий вимір вимикає розетку", () => {
    const heater = new SpyHeater();
    tick(new FakeSensor({ celsius: 22.0, ok: true }), heater, CFG);
    expect(heater.calls).toEqual(["off"]);
  });

  it("мертвий давач вимикає розетку", () => {
    const heater = new SpyHeater();
    tick(new FakeSensor({ celsius: 5.0, ok: false }), heater, CFG);
    expect(heater.calls).toEqual(["off"]);   // холодно, та вірити нема чому
  });

  it("кожен оберт докручує свою команду", () => {
    const heater = new SpyHeater();
    const sensor = new FakeSensor(
      { celsius: 18.0, ok: true },
      { celsius: 22.0, ok: true },
      { celsius: 19.0, ok: true },
    );
    for (let i = 0; i < 3; i++) tick(sensor, heater, CFG);
    expect(heater.calls).toEqual(["on", "off", "on"]);
  });
});
```
:::

Тут криється тонкість, через яку варто зупинитися. На перший погляд ці тести дублюють таблицю з шару першого: там теж був холодний вимір, теплий, мертвий давач. Але вони питають **інше**. Таблиця перевіряла **політику** — «за 18 °C команда має бути HEAT». Ці тести перевіряють **проводку** — «команда HEAT докручується саме до `heater.on()`, а не до `off`, і не тоне десь між `decide` і розеткою». Це дві різні можливі поломки. Можна мати бездоганну `decide` й переплутати гілки в `tick` — тоді таблиця зелена, а дім у мороз вимикає грілку. Саме цю поломку ловить шар другий, і саме тому він дивиться на `heater.calls`, а не на команду.

Звідси випливає дисципліна, яку легко порушити: **не ганяй усю таблицю істинності через `tick`**. Спокуса є — додати сюди рядки на `19.999` і `20.0`, «щоб уже напевно». Не треба. Кожен такий рядок піднімає фейк і шпигуна там, де досить було б викликати чисту функцію, тобто платить за проводку, щоб перевірити політику, вже перевірену дешевше. Гірше — він розмиває сенс тесту: коли `test_wiring` червоніє, ти хочеш одразу знати «проводка порвалася», а не гадати, чи це знову межа порога. Кожен шар відповідає на **своє** питання: політику пришпилюють до чистої `decide`, проводку — до `tick`. Три-чотири тести проводки на всю збірку — досить, бо гілок докручування рівно дві.

## Шар третій — коли зелений тест бреше

Тепер найпідступніше. Тільки-но з'явився `FakeSensor`, з'явилася й змога згодувати `decide` вимір, якого справжнє залізо **не породжує ніколи**. І тест на такому вимірі буде зелений — та порожній.

Ось він, у всій невинності:

:::tabs
```py
def test_scorching_room_stays_idle():        # ← зелений, і нічого не вартий
    assert decide(Reading(500.0, ok=True), Config(threshold=20.0)) == Command.IDLE
```
```ts
it("розпечена кімната лишається в спокої", () => {   // ← зелений, і нічого не вартий
  expect(decide({ celsius: 500.0, ok: true }, { threshold: 20.0 })).toBe("IDLE");
});
```
:::

Логіка бездоганна: `500 ≥ 20`, отже `IDLE`. Тест проходить. Автор задоволений: «покрив дуже гарячу кімнату». Але `Reading(500.0, ok=True)` — це стан, якого межа дому **не випускає**. Пригадаймо контракт драйвера: усе поза паспортним діапазоном давача (−40…85 °C) він переводить у чесне `Reading(0.0, ok=False)`, бо 500 °C — це не «дуже спекотно», а збій електроніки. Отже, `decide` у проді ніколи не бачить `500` разом із `ok=True`. Тест перевіряє світ, якого не буває.

Чому це гірше за червоний тест? Червоний кричить. А цей дає **впевненість без покриття** — найдорожчий вид брехні в наборі. Уяви, що завтра в `decide` додають справжню перемичку безпеки: «якщо число зашкалило вгору — не просто спокій, а тривогу». Її природно перевірити тим самим фейком на 500 °C — зелено, їде в прод. І там вона **мертва**: значення, що мало б її запустити, не доходить до `decide` живим, драйвер гасить його в `ok=False` на межі. Зелений тест засвідчив функцію, якої в проді немає.

Корінь у тім, що `Reading(...)` — конструктор без совісті: він збере будь-яку пару чисел, і правдоподібну, і неможливу. Ліки — зробити неможливе **неможливим до збирання**. Запишімо контракт межі один раз, окремою фабрикою, і будуймо всі виміри тільки через неї:

:::tabs
```py
# honest.py — контракт межі, витягнутий у фабрику
from home import Reading

SENSOR_MIN, SENSOR_MAX = -40.0, 85.0        # паспортний діапазон давача

def reading(celsius: float, ok: bool = True) -> Reading:
    """Той самий контракт, що й драйвер: правдиве число ⇒ у паспортних межах."""
    if ok and not (SENSOR_MIN <= celsius <= SENSOR_MAX):
        raise ValueError(f"{celsius} °C поза −40…85: справжній давач такого з ok=True не дасть")
    return Reading(celsius, ok)
```
```ts
// honest.ts — контракт межі, витягнутий у фабрику
import type { Reading } from "./home";

const SENSOR_MIN = -40.0, SENSOR_MAX = 85.0;   // паспортний діапазон давача

export function reading(celsius: number, ok = true): Reading {
  // той самий контракт, що й драйвер: правдиве число ⇒ у паспортних межах
  if (ok && !(celsius >= SENSOR_MIN && celsius <= SENSOR_MAX))
    throw new Error(`${celsius} °C поза −40…85: справжній давач такого з ok=true не дасть`);
  return { celsius, ok };
}
```
:::

Тепер брехливий тест **не збереться**. Спроба `reading(500.0)` кине помилку в мить побудови даних — у Python під час збору параметрів, у TypeScript під час завантаження модуля, тобто **до** першої перевірки. Неможливий вхід із тихого зеленого перетворюється на гучний червоний, і саме там, де його видно:

:::tabs
```py
# перебудована таблиця шару першого — усі виміри через reading()
CASES = [
    pytest.param(reading(19.0),          Command.HEAT, id="нижче-порога→HEAT"),
    pytest.param(reading(20.0),          Command.IDLE, id="рівно-на-порозі→IDLE"),
    pytest.param(reading(25.0),          Command.IDLE, id="тепло→IDLE"),
    pytest.param(reading(5.0, ok=False), Command.IDLE, id="давач-мовчить→IDLE"),
    # pytest.param(reading(500.0),       Command.IDLE, id="розпечена"),  # ← ValueError уже ТУТ
]
```
```ts
// перебудована таблиця шару першого — усі виміри через reading()
const cases: Array<[Reading, Command]> = [
  [reading(19.0),        "HEAT"],   // нижче порога
  [reading(20.0),        "IDLE"],   // рівно на порозі
  [reading(25.0),        "IDLE"],   // тепло
  [reading(5.0, false),  "IDLE"],   // давач мовчить
  // [reading(500.0),    "IDLE"],   // ← кине ще при завантаженні модуля
];
```
:::

А як тоді чесно висловити «давачу здалося 500 °C»? Рівно так, як це бачить дім: не як гарячу правду, а як недовіру. Єдиний законний спосіб — `reading(0.0, ok=False)`, бо саме це віддасть драйвер, і саме це `decide` уже вкрито в рядку «давач мовчить → IDLE». Неможливий стан не втрачається — він **потрапляє у свою справжню гілку**, а не вигадує собі окрему.

![Дві вкладені області. Зовнішня, амбра з червоним обрідом, — усе, що можна вписати в Reading вручну, разом із неможливими станами на кшталт Reading(500 °C, ok=True), де зелений тест бреше. Внутрішня, зелена, — те, що межа реально породжує: ok=True разом із діапазоном −40…85 °C, або ж ok=False. Синя стрілка від фабрики reading() веде всередину зеленої області, показуючи, що фабрика будує фейки лише туди](img/contract-space.svg)
*Контракт межі, витягнутий у фабрику, замикає простір, з якого будуються фейки: усе, що можна вписати в `Reading` вручну, ширше за те, що межа реально породжує, і в зазорі між ними живе зелений тест, який бреше.*

> 🔧 **Навіщо це.** Дублер вартий рівно стільки, наскільки чесно він імітує оригінал. Фейк, що вміє віддати стан, неможливий для справжнього заліза, — це не помічник, а джерело хибної впевненості: він зеленить тести, яких прод не підтвердить. Виписаний контракт межі — те, що тримає фейк у рамках реальності. Витягнути його у фабрику варто саме тоді, коли пишеш перший дублер: у цю мить питання «а що тут узагалі можливо?» стоїть найгостріше, і відповідь на нього, закладена в код один раз, стереже кожен майбутній фейк від тієї самої брехні.

## Складність і пастки

Набір короткий, але кожен його шар має свій спосіб тихо зіпсуватися. Ось ті, що коштують найдорожче.

**Межа порога — знак, а не «десь там».** Різниця між `<` і `<=` — це ціла гілка поведінки на самому порозі, і без рядка «рівно на порозі» вона мовчазна. Тримай цей рядок завжди й будуй його на точному значенні (`20.0` при `threshold=20.0`), а не на «приблизно двадцять». І стережися порогів, що **обчислюються**: якщо `threshold` приходить із перетворення (скажімо, з фаренгейтів), рівність із плавною крапкою може схибити на один найменший розряд, і тест на самій межі почне мерехтіти. Правило просте: перевіряй `трохи-нижче` і `трохи-вище` окремими рядками, а точну межу став лише там, де обидва боки — точні константи. У справжньому домі цю гостру грань згладжують гістерезисом (грій до 20, вимикай на 21), щоб реле не сіпалося на порозі, — але це вже нова гілка політики, і їй місце в новому рядку таблиці, а не в мовчанні тесту.

**Порожня черга фейка: гучно чи тихо.** Дві мови поводяться протилежно, і це не дрібниця. Python `list.pop(0)` на порожній черзі кидає `IndexError` — тест, що крутнув `tick` більше разів, ніж заготовлено вимірів, падає одразу й показує пальцем, де саме. TypeScript `Array.shift()` на порожньому масиві повертає `undefined` **мовчки**, і без перевірки цей `undefined` поповзе далі — до `decide`, де `undefined.ok` вибухне вже деінде, за кілометр від причини. Тому у TS-фейку `shift()` **обов'язково** обгорнутий явним кидком: краще чесна помилка «FakeSensor вичерпано» тут, ніж загадкове падіння там. Дублер має ламатися голосно.

**Шпигун: перевіряй послідовність, а не «чи викликали».** Спокуса написати `assert "on" in heater.calls` або `expect(heater.on).toHaveBeenCalled()`. Це слабша перевірка, ніж здається: вона пройде, навіть якщо `tick` смикнув `on` двічі, або смикнув спершу `off`, потім `on`, або докрутив зайвий виклик, якого не мало бути. Порівняння **всього списку** (`== ["on"]`, `toEqual(["on"])`) фіксує і що викликали, і скільки разів, і в якому порядку — а саме порядок і кратність ламаються, коли проводку зачепили. Дивися на повний слід, не на факт дотику.

**Не змішуй шари.** Це варте повтору, бо порушується найчастіше. Політику (`19.999` гріє, `20.0` — ні) перевіряй на чистій `decide`; проводку (HEAT іде в `on`, IDLE в `off`, мертвий давач гасить) — на `tick`. Коли ці питання течуть в один тест, червоне перестає показувати пальцем: ти бачиш «щось зламалося», але не знаєш, політика чи докручування. Один тест — одне питання; тоді колір несе адресу поломки, а не лише її факт.

**Фейк, що розійшовся з портом.** І `Protocol` у Python, і структурний інтерфейс у TypeScript перевіряють відповідність за **формою**, а не за оголошеним родом. Це зручно — фейк не мусить нічого наслідувати, — але має пастку: якщо в `SpyHeater` написати `of()` замість `off()`, качина типізація Python цього не помітить, поки `tick` не покличе `off` і не впаде на `AttributeError` уже під час тесту. TypeScript спіймає це раніше — на `implements Heater` компілятор нагадає про метод, — тому `implements` тут не формальність, а рання сітка: він прив'язує фейк до порту в мить оголошення. У Python ту саму роль грає перевірка типів (`mypy`) і, за потреби, `@runtime_checkable`. Фейк, що лише **схожий** на порт, — така сама брехня, як фейк, що порушує діапазон, лише виявляється пізніше.

**Неможливий вхід — це не лише 500 °C.** Розібраний у шарі третьому фокус узагальнюється: **будь-який дублер, здатний зобразити стан, який справжня межа забороняє, рано чи пізно зеленить тест, що його прод спростує.** 500 °C із `ok=True` — очевидний випадок; менш очевидні — від'ємна тривалість, порядковий номер зі скіпнутим значенням, дата з 30 лютого, відповідь сервера без обов'язкового поля. Ліки скрізь одні: не лови ці стани по одному в кожному тесті, а витягни контракт межі один раз у фабрику й будуй усі дублери **через** неї. Тоді неможливий вхід не проходить у тест тихцем — він падає в мить побудови, гучно й на видноті.

Озирнімося, скільки це коштувало. Три файли тестів, два коротких дублери, одна фабрика на десяток рядків — і **жодної нової абстракції** понад те, що вже стояло у формі v1. Кожен шар відповідає на власне питання, яких не варто плутати: чи правильна **політика** (таблиця чистої `decide`), чи правильно вона **докручена** до заліза (проводка на фейку й шпигуні), і чи взагалі **можливий** той вхід, на якому все це зелено (контракт межі у фабриці). Набір не робить дім розумнішим. Він робить так, що кожну наступну зміну спершу видно зеленою — і зелене справді щось означає.
