# ⚙️ Вартовий свіжості крок за кроком: як пришпилена вада червоніє рівно там, де треба

Крок-огляд показав цю хореографію в мініатюрі: пришпилити те, що є → змінити структуру → упіймати червоне там і тільки там → закріпити бажане. Гарний ескіз — але ескіз легко прийняти за фокус, доки не зробиш рух пальцями. Тут ми робимо його **повільно**, на єдиній зміні робочого коду, яку дім ще винен собі: навчити застиглий давач переставати гріти наосліп. І не заради охайного фіналу, а заради двох речей, яких з ескізу не видно, — **відчуття кроку** й **точної потактової арифметики**. Бо саме арифметику тут не можна вгадати оком; її можна лише порахувати, такт за тактом.

Дублери — той самий фейк давача й шпигун розетки, що [ми зібрали під цей дім](root:progarch/test-doubles-when), — уже лежать напоготові; тестове гніздо давно прорізав [шов порту](root:progarch/seams-and-boundaries). Усе, чого бракує, — дисципліни руху. Її й розкладемо.

## Задача: давач, що завис на правдоподібному числі

Пригадаймо точну форму вади. `Reading` несе два поля — число й прапорець `ok`. Прапорець ловить давач, що **замовк**: таймаут, `CRC=NO`, обрив — драйвер чесно перекладає це на `ok=false`, і `decide` обирає спокій. Але є інша поломка, тонша й підступніша: 1-Wire **застряг** і вперто віддає те саме правдоподібне число — скажімо, 19.9 °C, рівно під порогом. Кожен такий `Reading` має `ok=true` — число ж на вигляд свіже. `decide` йому чесно вірить, бачить `19.9 < 20.0`, повертає `HEAT`, і дім гріє. Наступного такту — те саме. І наступного. Дім гріє **вічно**, бо ніхто в ланцюгу не питає: а число взагалі ще ворушиться?

`ok` відповідає на питання «чи **цей** дотик до заліза дав достовірне число». Він не відповідає на питання «чи давач ще **живий**». Це різні питання, і живуть вони на різних шарах. Наша задача — вправити друге питання, не зачепивши коду, що вже чесно відповідає на перше. Тобто — правка робочого коду. А над правкою робочого коду діє [залізна дисципліна модуля](root:progarch/refactoring-safe): **не чіпай поведінку без сітки під нею.** Тож перш ніж додати бодай рядок вартового — накидаємо сітку.

## Крок 0: пришпилити те, що Є

Сітку дає [характеризаційний тест](root:progarch/characterization-tests). Його хитрість — він фіксує не бажане, а **нинішнє**: те, як код поводиться прямо зараз, навіть якщо це вада. Ми беремо застиглий давач — фейк, що п'ять разів поспіль віддає ті самі 19.9 °C, — і пришпилюємо цвяхом те, що дім із ним робить сьогодні.

:::tabs
```py
# test_freshness.py — характеризація: пришпилюємо ВАДУ, зелену вже сьогодні
from hub import Reading, Config, tick          # той самий дім за швами

class FakeSensor:                               # фейк: віддає задані виміри, один за одним
    def __init__(self, *readings): self._q = list(readings)
    def read(self) -> Reading: return self._q.pop(0)

class SpyHeater:                                # шпигун: нічого не гріє, лише пам'ятає виклики
    def __init__(self): self.calls = []
    def on(self):  self.calls.append("on")
    def off(self): self.calls.append("off")

def test_stuck_sensor_heats_forever_TODAY():    # що Є, не що має бути
    heater = SpyHeater()
    stuck = FakeSensor(*[Reading(19.9)] * 5)    # давач завис на 19.9 °C — під порогом
    for _ in range(5):
        tick(stuck, heater, Config(threshold=20.0))
    assert heater.calls == ["on"] * 5           # v1 гріє безкінечно — задокументовано
```
```ts
// freshness.test.ts — характеризація: пришпилюємо ВАДУ, зелену вже сьогодні
import { test, expect } from "vitest";
import { Reading, Config, tick } from "./hub";

class FakeSensor {                              // фейк: віддає задані виміри, один за одним
  private q: Reading[];
  constructor(...readings: Reading[]) { this.q = readings; }
  read(): Reading { return this.q.shift()!; }
}
class SpyHeater {                               // шпигун: нічого не гріє, лише пам'ятає виклики
  calls: string[] = [];
  on()  { this.calls.push("on"); }
  off() { this.calls.push("off"); }
}

test("застиглий давач гріє вічно — TODAY", () => {
  const heater = new SpyHeater();
  const stuck = new FakeSensor(...Array(5).fill({ celsius: 19.9, ok: true }));
  for (let i = 0; i < 5; i++) tick(stuck, heater, { threshold: 20.0 });
  expect(heater.calls).toEqual(["on", "on", "on", "on", "on"]);  // v1 гріє вічно
});
```
:::

Порахуймо руками, чому цей тест **зелений** уже сьогодні. На кожному з п'яти тактів фейк віддає `Reading(19.9, ok=true)`. `decide` читає `ok` — правда; порівнює `19.9 < 20.0` — правда; повертає `HEAT`. `tick` виконує `heater.on()`. Шпигун (він, на відміну від справжньої розетки, **не** ідемпотентний — записує кожен виклик) додає `"on"` до списку. П'ять тактів — п'ять `"on"`. Список збігається з очікуваним — зелено.

Навіщо документувати те, що збираєшся зламати? Бо зелений характеризаційний тест перетворює ваду на **пришпилену**. Ім'я з хвостиком `_TODAY` — не забаганка: це мітка, що кричить читачеві «тут зафіксовано те, що Є, а не те, що має бути». Поки поведінка прибита цвяхом, будь-яка зміна, що її торкнеться, стане **видимою** — тест почервоніє. Без цвяха зміна тихо поповзе, і ти дізнаєшся про неї не тут, а через місяць у чужому домі.

## Крок 1: вартовий, що не чіпає рішення

Тепер — і тільки тепер, коли сітка натягнута, — додаємо вартового. `FreshnessGuard` — обгортка над портом `Sensor`, що тримає **той самий інтерфейс** (`read() -> Reading`), а всередині рахує, чи не застигло число. Вставляється вона в `hub.py`, поряд із портами, і нічого в `decide` чи `tick` не чіпає:

:::tabs
```py
class FreshnessGuard:                    # обгортка над портом Sensor — той самий інтерфейс
    def __init__(self, inner: Sensor, stale_after: int = 3):
        self._inner = inner
        self._stale_after = stale_after
        self._last: float | None = None  # останнє число, якому повірили
        self._same = 0                   # скільки разів ПОСПІЛЬ воно повторилось

    def read(self) -> Reading:
        r = self._inner.read()
        if not r.ok:                     # уже чесний збій — не наша турбота, лічильник з нуля
            self._same = 0
            return r
        self._same = self._same + 1 if r.celsius == self._last else 0
        self._last = r.celsius
        if self._same >= self._stale_after:          # застій переріс дозволене → «не вірю»
            return Reading(celsius=r.celsius, ok=False)
        return r
```
```ts
class FreshnessGuard implements Sensor {   // обгортка над портом Sensor — той самий інтерфейс
  private last: number | null = null;      // останнє число, якому повірили
  private same = 0;                        // скільки разів ПОСПІЛЬ воно повторилось
  constructor(private inner: Sensor, private staleAfter = 3) {}

  read(): Reading {
    const r = this.inner.read();
    if (!r.ok) { this.same = 0; return r; }   // уже чесний збій — лічильник з нуля
    this.same = r.celsius === this.last ? this.same + 1 : 0;
    this.last = r.celsius;
    if (this.same >= this.staleAfter)         // застій переріс дозволене → «не вірю»
      return { celsius: r.celsius, ok: false };
    return r;
  }
}
```
:::

Уся логіка — в одному лічильнику `_same`. Він рахує, **скільки разів поспіль** число повторило попереднє. Перша поява числа — це нуль повторів (`_same = 0`). Кожен наступний однаковий вимір додає один. Щойно повторів набирається `stale_after`, вартовий перестає вірити й повертає той самий градус, але з `ok=false` — доводить застиглість до чесного «не вірю», яке `decide` уже вміє читати.

### Точна потактова семантика `stale_after = 3`

Ось де око обманює, а рахунок ні. «`stale_after=3`» — це на якому вимірі вартовий уперше скаже «не вірю»? Не на третьому. Пройдімо застиглий давач (усі 19.9 °C) такт за тактом і подивімось на лічильник:

```
такт  вимір   celsius == _last?    _same після   вартовий віддає           decide  розетка
 1    19.9    ні (перше число)         0          Reading(19.9, ok=true)     HEAT    on
 2    19.9    так                      1          Reading(19.9, ok=true)     HEAT    on
 3    19.9    так                      2          Reading(19.9, ok=true)     HEAT    on
 4    19.9    так                      3  ≥ 3      Reading(19.9, ok=FALSE)    IDLE    off   ← перше «не вірю»
 5    19.9    так                      4  ≥ 3      Reading(19.9, ok=FALSE)    IDLE    off
```

Перший вимір задає базу — порівнювати ще нема з чим, `_same` лишається нулем. Другий однаковий вимір — це перший **повтор**, `_same` стає 1. Третій — другий повтор, `_same` стає 2. І аж четвертий вимір дає третій повтор, `_same` доростає до 3, вперше досягає порога `stale_after`, і вартовий уперше каже «не вірю». Тобто **перше «не вірю» падає на 4-й вимір**, а не на 3-й: три однакові числа поспіль ще можуть бути правдою, і лише той, що робить їх чотирма, переважує шальку.

![Стовпчики лічильника повторів по п'яти тактах: 0, 1, 2, 3, 4. Пунктирний поріг на рівні 3; стовпчики на такті 4 і 5 переростають поріг і стають червоними. Над кожним тактом чип розетки: on, on, on, off, off. Вертикальна межа між тактами 3 і 4 позначає мить спрацювання](/root/course/progarch/dh-testability-refactor/img/tick-freshness.svg)
*Лічильник `_same` дереться з нуля; поки він нижче за `stale_after`, вартовий пропускає число як свіже, а на 4-му вимірі перший раз доростає до порога — і застиглий градус вперше проходить за шов уже як «не вірю».*

Чому взагалі треба **чекати** три однакові, а не гасити гріння на другому ж повторі? Бо застиглий давач і по-справжньому **стабільна кімната** з одного виміру нерозрізненні: обидва дають 19.9 з `ok=true`. Єдине, що їх ділить, — **час**. Живий 1-Wire (той самий DS18B20 із курсу) квантує температуру кроком 0.0625 °C у 12-бітному режимі, і кімната біля рівноваги, де ворушиться повітря, майже завжди сіпається бодай на один такий крок за десятки секунд. Застиглий — ні: він віддає **байт-у-байт** те саме мілі-градусне число раз за разом. Тобто довгий ряд **точно** однакових вимірів — сам по собі аномалія, підпис застигання. `stale_after` — це рівно ручка «скільки доказів (який завдовжки ряд) треба, перш ніж назвати давач застиглим». Замала — вартовий сіпатиметься на чесно спокійній кімнаті; завелика — довго не помічатиме мертвий давач. Троє поспіль — розумний компроміс, не магічне число.

Тепер під'єднуємо вартового — **у корені збірки**, одним рядком, як перехідник між двома розетками:

```py
run(FreshnessGuard(OneWireThermometer(), stale_after=3), SmartPlug(), Config())
```

`decide` не знає про його існування. `tick` не знає. Порти — ті самі. Ми не розтинали жодної наявної конструкції; ми **вставили ланку** в наперед прорізаний шов. Це і є структурний рух: форма змінилась, а рядок, де ухвалюється рішення «гріти чи ні», лишився незайманий.

## Крок 2: той самий тест червоніє — рівно там

Тепер найважливіша мить. Прогонимо **той самий** характеризаційний тест, не змінивши в ньому ані символу, — тільки тепер фейк застиглого давача обгорнуто вартовим:

```
FAILED test_freshness.py::test_stuck_sensor_heats_forever_TODAY

  assert  ['on', 'on', 'on', 'off', 'off'] == ['on', 'on', 'on', 'on', 'on']
  розбіжність на індексі 3:  'off' != 'on'    ← саме там, де вартовий сказав «не вірю»
```

Порахуймо новий результат руками, звіряючись із таблицею вище. Такти 1–3: `_same` ще нижче за 3, вартовий пропускає 19.9 із `ok=true`, `decide` → `HEAT`, розетка `on`. Такт 4: `_same` доріс до 3, вартовий віддає `ok=false`, `decide` читає `not ok` → `IDLE`, розетка `off`. Такт 5: те саме — `off`. Виходить `["on", "on", "on", "off", "off"]`, і воно не збігається з пришпиленим `["on"]*5` починаючи з індексу 3 — четвертого такту.

Це червоне — **не прикрість, а доказ**. Придивіться, чого воно НЕ зробило: воно не розсипалось по всьому набору. Тест «холодна кімната докручує розетку» лишився зеленим — свіжий вимір 18 °C і далі дає `HEAT`. Тест «збій давача → безпечний спокій» лишився зеленим — `ok=false` від драйвера й далі дає `IDLE`. Червоним став **рівно один** тест, і **рівно на тому рядку**, який ми пришпилили. Це і є те, заради чого існує характеризація: червоне засвідчує, що зміна дотяглася **саме до пришпиленої поведінки й нікуди більше**. Якби зайняло пів набору — вартовий протік би туди, куди не мав, і ми б це побачили тут-таки, а не в проді. А позаяк почервонів один тест — рух точний, як скальпель.

## Крок 3: переписати пін на бажане й додати регресію

Пришпилений тест зробив свою роботу — засвідчив, що зміна влучила в ціль. Тепер, і аж тепер, ми свідомо переписуємо його очікування з **вади** на **бажане**. Дім тепер має гріти, поки може розумно вірити давачеві, а тоді — переставати:

:::tabs
```py
def test_stuck_sensor_stops_heating_blind():    # тепер БАЖАНЕ, не пришпилена вада
    heater = SpyHeater()
    stuck = FreshnessGuard(FakeSensor(*[Reading(19.9)] * 5), stale_after=3)
    for _ in range(5):
        tick(stuck, heater, Config(threshold=20.0))
    assert heater.calls == ["on", "on", "on", "off", "off"]   # гріє, поки вірить; тоді спокій

def test_guard_flips_on_fourth_identical():     # регресія: вартовий пильнує саме 4-й вимір
    guard = FreshnessGuard(FakeSensor(*[Reading(19.9)] * 4), stale_after=3)
    assert [guard.read().ok for _ in range(4)] == [True, True, True, False]
```
```ts
test("вартовий гасить сліпе гріння після 3 застиглих", () => {   // БАЖАНЕ, не вада
  const heater = new SpyHeater();
  const stuck = new FreshnessGuard(
    new FakeSensor(...Array(5).fill({ celsius: 19.9, ok: true })), 3);
  for (let i = 0; i < 5; i++) tick(stuck, heater, { threshold: 20.0 });
  expect(heater.calls).toEqual(["on", "on", "on", "off", "off"]);   // гріє, поки вірить
});

test("вартовий перемикається саме на 4-му однаковому вимірі", () => {   // регресія
  const guard = new FreshnessGuard(
    new FakeSensor(...Array(4).fill({ celsius: 19.9, ok: true })), 3);
  const oks = [0, 1, 2, 3].map(() => guard.read().ok);
  expect(oks).toEqual([true, true, true, false]);
});
```
:::

Перший тест переставлено із задокументованої вади на бажану поведінку — і він зелений, бо код уже такий. Другий — **регресійний**, і він вартий окремої уваги: він шпигує за вартовим **впритул**, поза `tick` і `decide`, і пришпилює найтоншу деталь — що перемикання падає рівно на четвертий однаковий вимір (`[True, True, True, False]`). Саме цю цифру найлегше зсунути ненароком, поправивши `>=` на `>` чи скинувши лічильник не там; регресійний тест стереже її окремим цвяхом, щоб майбутнє «дрібне прибирання» не посунуло 4 на 3 чи 5 тихцем.

![Матриця тестів по трьох стадіях. Рядки: характеризація (пін), холодна кімната, збій давача, регресія вартового. Стовпці: v1 до вартового, FreshnessGuard у збірці, пін переписано плюс регресія. Усі клітини зелені, окрім однієї червоної — характеризація на стадії з вартовим; регресія існує лише на третій стадії](/root/course/progarch/dh-testability-refactor/img/green-except-one-red.svg)
*Крізь увесь структурний рух набір тримає зелене — червоніє рівно одна клітина, навмисно, і рівно там, де ми пришпилювали; це і є підпис того, що зміна не розповзлась.*

Озирнімося на весь рух одним поглядом — саме так, як його малює матриця. Зелено → додали вартового в збірку (структура змінилась, решта тестів тримає зелене) → **один** навмисний червоний рівно на піні → переписали пін на бажане й додали регресію → знову зелено. Жоден крок не був хоробрим; хоробрість тут зайва, бо після кожного руху видно, де ти стоїш. І пришпилений `_TODAY`-тест, відслуживши, більше не потрібен під тим ім'ям — його роль тепер несе `test_stuck_sensor_stops_heating_blind`, що стереже вже **правильну** поведінку.

## Складність і пастки

**Вікно терпимості — це справжня затримка, а не безкоштовність.** `stale_after=3` означає, що навіть геть мертвий давач ще тричі докрутить розетку, перш ніж вартовий зробить висновок. У циклі зі `sleep(30)` це півтори хвилини сліпого гріння. Це не недогляд — це ціна того, щоб не зчиняти фальшиву тривогу на чесно стабільній кімнаті. Хочеш коротше вікно — плати частішими хибними спрацюваннями; хочеш нуль хибних — плати повільнішою реакцією на застигання. Ручка `stale_after` не усуває цей компроміс, вона лише дає його **назвати вголос і виставити свідомо**, а не наосліп.

**Точна рівність чисел із рухомою комою — гостре лезо з двох боків.** Вартовий порівнює `r.celsius == self._last` **точно**. Для живого 1-Wire це саме те, що треба: він майже ніколи не віддасть двічі поспіль байт-у-байт однакове мілі-градусне число, тож рівність — сама по собі сигнал застигання. Але той самий рядок стає пасткою, якщо драйвер грубо квантує — округляє, скажімо, до цілого градуса. Тоді спокійна кімната законно віддасть `20.0` кілька разів поспіль, і вартовий хибно оголосить її застиглою. Мораль: `stale_after` та поняття «те саме число» треба калібрувати під **роздільність конкретного давача**; де крок квантування грубий, чесніше порівнювати не точну рівність, а «зсув менший за очікуваний шум» чи стежити за дисперсією ряду. Один розмір не пасує всім давачам.

**Скидання лічильника на `ok=false` — навмисне, і його легко проґавити.** Коли приходить чесний збій (`ok=false` від драйвера), вартовий обнуляє `_same` і пропускає `Reading` як є. Це означає, що давач, який **блимає** — то збій, то застигле правдоподібне число, — щоразу починає лічити застій наново й може так і не набрати трьох поспіль. І це правильно: вартовий рахує тільки **ті виміри, яким уже повірили**, бо застигання — властивість саме потоку правдоподібних чисел, а не мішанини зі збоями. Але цю межу треба тримати в голові: `FreshnessGuard` ловить чистий застій, а не всяку ненадійність узагалі.

**Не пришпилюй і не переписуй пін одним махом.** Найспокусливіша економія — додати вартового й одразу переписати очікування тесту на бажане, одним комітом. Тоді все зелено, і здається, наче морочитися з проміжним червоним було дарма. Але так ти **ніколи не побачиш**, як червоне падає рівно на пришпилений рядок, — а це і є єдиний доказ, що зміна влучила туди, куди хотіла, і нікуди більше. Пропустивши його, ти зміняв доказ на надію. Дисципліна тверда: зелено → структурна зміна → **побач той один червоний** → перепиши пін → знову зелено. Проміжне червоне — не тяганина, а квитанція.

**Характеризація пришпилює поведінку, а не правильність.** Пін `["on"]*5` був зеленим, документуючи **ваду**. Це нормально рівно доти, доки мітка кричить «тут зафіксовано те, що Є, а не що має бути»: ім'я з `_TODAY`, коментар, розділ у наборі. Без такої мітки наступний читач сумлінно «захистить» ваду як фічу — побачить зелений тест і вирішить, що вічне гріння задумане. Тому, щойно вада виправлена, пришпилений тест **знімають або перейменовують** у справжню специфікацію; лишати задокументовану ваду зеленою назавжди — значить забетонувати її під виглядом перевіреної поведінки.

**Вартовий — не заміна прод-спостережності.** Офлайн ми довели одне: **логіка** вартового спрацьовує — за трьома однаковими вимірами `ok` перекидається в `false`. Ми **не** довели, що реальний давач у полі справді колись застигне саме так; фейк відтворює лише нашу модель застигання. Чи трапиться воно наживо, о третій ночі, під реальним навантаженням, — питання не офлайн-тесту, а [зонда в проді](root:progarch/observability-as-testability): лічильник підряд однакових мілі-градусів, тривога на довгий застій. А те, чого й зонд поки не покриває, чесніше записати рядком у [реєстр боргу як свідоме рішення](root:progarch/debt-as-decision), ніж вдавати, ніби зелений набір уже все стереже. Вартовий полагодив **сліпе гріння в логіці**; надійність справжнього заліза він не полагодив і не обіцяв.
