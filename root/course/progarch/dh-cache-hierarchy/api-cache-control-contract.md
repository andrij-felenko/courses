# 📋 Контракт кеш-заголовків та Edge Purge API

Контракт кешування між платформою Digital Homes (DH), мережею доставки вмісту (Edge CDN) та клієнтськими застосунками регулюється двома чіткими поверхнями:
1. **HTTP-заголовками відповіді (Response Headers Contract):** Визначають правила зберігання, термін придатності (TTL), дозволи на використання прострочених даних (Stale-While-Revalidate, Stale-If-Error) та простір тегів інвалідації (`Surrogate-Key`).
2. **Внутрішнім REST API інвалідації (Edge Purge API):** Забезпечує миттєве зрізання простроченого або зміненого кешу на Edge-вузлах CDN за тегом будинку чи пристрою.

Нижче наведено вичерпний довідник параметрів, профілів, семантики та ендпойнтів цієї поверхні.

## 1. Детальна специфікація HTTP-заголовків кешування

Кожен ендпойнт платформи Digital Homes повертає детермінований набір HTTP-заголовків залежно від рівня чутливості даних та частоти їх оновлення.

### Семантика директив Cache-Control та Surrogate-Control

Часта помилка розробників полягає у невірному тлумаченні стандартних директив HTTP-кешування. Наведемо суворий опис кожного заголовка у системі DH:

- **`Cache-Control: public`** — Повідомляє проміжним проксі-серверам та мережам CDN, що відповідь є спільною й може бути збережена у кеші для багатьох користувачів. Використовується для списків пристроїв та загальної телеметрії.
- **`Cache-Control: private`** — Вказує, що відповідь призначена виключно для одного конкретного користувача й містить персональні дані. Проміжні Edge CDN зобов'язані пропустити таку відповідь без збереження на своїх дисках. Кешування дозволено лише у локальній пам'яті браузера чи мобільного застосунку.
- **`Cache-Control: no-cache`** — **Не означає «не кешувати»**. Ця директива дозволяє кешувати відповідь, але зобов'язує клієнта або CDN відправляти умовний запит перевірки (`If-None-Match` з `ETag`) до Origin API перед кожним використанням закешованого об'єкта. Якщо ETag не змінився, сервер повертає `304 Not Modified` без повторної передачі тіла.
- **`Cache-Control: no-store`** — **Сувора заборона кешування**. Забороняє зберігати відповідь на будь-яких накопичувачах (RAM, SSD) клієнта чи проміжних проксі. Застосовується для списків охоронних замків, токенів доступу та секретних ключів.
- **`Cache-Control: max-age=<sec>`** — Тривалість у секундах, протягом якої відповідь вважається повністю свіжою для кінцевого мобільного або веб-клієнта.
- **`Surrogate-Control: max-age=<sec>`** — Спеціальний заголовок (RFC 4791 / CDN Standard), який інтерпретується виключно Edge CDN. Він задає термін зберігання об'єкта на Edge-сервері, який може бути значно довшим за клієнтський `max-age`. Перед відправкою відповіді клієнту Edge CDN автоматично видаляє заголовок `Surrogate-Control` з HTTP-пакета.
- **`stale-while-revalidate=<sec>`** — Директива RFC 5861. Вказує вікно часу у секундах, протягом якого Edge CDN може повернути прострочений об'єкт клієнту миттєво, паралельно запускаючи фоновий асинхронний запит до Origin для оновлення кешу.
- **`stale-if-error=<sec>`** — Директива RFC 5861. Вказує вікно часу, протягом якого Edge CDN повертає застарілу копію з кешу, якщо Origin DB недоступна чи повертає помилку `5xx`.
- **`Surrogate-Key` (або `Cache-Tags`)** — Набір текстових тегів, розділених пробілами, що прив'язуються до закешованого об'єкта на Edge CDN. Застосовується для групової інвалідації тисяч сторінок одного будинку одним викликом Purge API.

### Зведена матриця заголовків відповідей

| Заголовок / Директива | Напрямок / Ціль | Семантика та призначення в DH |
| :--- | :--- | :--- |
| `Cache-Control: public` | Браузер та Edge CDN | Дозволяє кешувати відповідь будь-яким проміжним вузлам (CDN, проксі, браузер). |
| `Cache-Control: private` | Тільки Браузер | Забороняє CDN кешувати відповідь. Застосовується для приватних токенів та персональних налаштувань. |
| `Cache-Control: max-age=<sec>` | Браузер / Клієнт | Тривалість у секундах, протягом якої клієнт вважає відповідь повністю свіжою без повторних мережевих запитів. |
| `Surrogate-Control: max-age=<sec>` | Тільки Edge CDN | Тривалість у секундах, протягом якої Edge CDN тримає об'єкт у кеші. Перекриває `max-age` з `Cache-Control` для Edge. |
| `stale-while-revalidate=<sec>` | CDN та Браузер | Вікно часу в секундах (RFC 5861), протягом якого прострочений кеш повертається миттєво, а оновлення з Origin виконується асинхронно у фоні. |
| `stale-if-error=<sec>` | CDN та Браузер | Вікно часу (RFC 5861), протягом якого прострочений кеш повертається клієнту, якщо Origin DB недоступна чи віддала 5xx. |
| `Surrogate-Key` (або `Cache-Tags`) | Тільки Edge CDN | Простір тегів для групової інвалідації. Містить ID дому, ID tenant та типи пристроїв. |
| `ETag` | Браузер та CDN | Хеш-сума вмісту (наприклад, `"W/\"v102-a4f8\""`). Використовується для умовної перевірки `If-None-Match` (статус `304 Not Modified`). |
| `Vary` | Браузер та CDN | Задає список заголовків запиту, які впливають на унікальність кеш-ключа (наприклад, `Accept-Encoding, Authorization`). |

## 2. Глибока механіка Stale-While-Revalidate (SWR) та Stale-If-Error

Застосування стандартних директив RFC 5861 вирішує дві найгостріші проблеми веб-інтерфейсів розумного дому: підвищення швидкості відгуку та забезпечення аварійної стійкості.

### А. Алгоритм роботи Stale-While-Revalidate (SWR)

Розглянемо послідовність дій Edge CDN при отриманні запиту `GET /homes/101/devices`, коли заголовок відповіді містить `max-age=5, stale-while-revalidate=30`:

1. **Перші 5 секунд (Свіжий кеш):** Edge CDN повертає закешований JSON миттєво (`Cache-Hit`, затримка 20 ms).
2. **Інтервал від 5 до 35 секунд (Вікно SWR):** Кеш вважається простроченим, але підпадає під дію вікна SWR.
   - Edge CDN **негайно** віддає наявний застарілий JSON клієнту (`Cache-Hit-Stale`, затримка 20 ms). Користувач отримує миттєвий відгук інтерфейсу.
   - Одночасно Edge CDN асинхронно відправляють фоновий HTTP-запит `revalidate` до Origin API DH.
   - Отримавши свіжу відповідь від Origin, Edge CDN оновлює об'єкт у своїй пам'яті для наступних читачів.
3. **Після 35 секунд (Повний Miss):** Об'єкт вважається повністю застарілим. Запит блокується й очікує повної відповіді від Origin API.

### Б. Алгоритм роботи Stale-If-Error (Стійкість до аварій)

Якщо Origin DB або backend-сервіс DH повністю падають або повертають помилку `500 Internal Error` / `503 Service Unavailable`:

1. Edge CDN отримує помилку `5xx` від backend-сервера.
2. Перевіряється наявність заголовка `stale-if-error=300`.
3. Якщо вік закешованого об'єкта не перевищує `max-age + 300` секунд, Edge CDN ігнорує помилку backend і повертає мобільному застосунку закешований стан з додатковим заголовком `Warning: 110 Response is Stale`.
4. Мобільний застосунок користувача продовжує функціонувати у режимі читання, а клієнт навіть не помічає короткочасного падіння бази даних.

## 3. Пропроєктовані профілі кешування за ендпойнтами DH

Нижче наведено підсумкову конфігурацію заголовків для чотирьох основних класів ендпойнтів системи:

### Профіль А. Список пристроїв будинку (`GET /api/v1/homes/{home_id}/devices`)
- **Опис:** Перелік пристроїв, кімнат та їхніх можливостей. Висока частота читання, середня частота змін.
- **Приклад HTTP-відповіді:**
  ```http
  HTTP/2 200 OK
  Content-Type: application/json; charset=utf-8
  Cache-Control: public, max-age=5, stale-while-revalidate=30, stale-if-error=300
  Surrogate-Control: max-age=60, stale-while-revalidate=120
  Surrogate-Key: home-101 tenant-42 devices-list
  ETag: W/"devlist-101-v14"
  Vary: Accept-Encoding, Authorization
  X-DH-Cache-Tier: L3-Hit
  ```

### Профіль Б. Поточна телеметрія давачів (`GET /api/v1/homes/{home_id}/telemetry/live`)
- **Опис:** Показання температури, вологості, поточного енергоспоживання. Динаміка оновлення щосекунди.
- **Приклад HTTP-відповіді:**
  ```http
  HTTP/2 200 OK
  Content-Type: application/json; charset=utf-8
  Cache-Control: public, max-age=1, stale-while-revalidate=2
  Surrogate-Control: max-age=3, stale-while-revalidate=5
  Surrogate-Key: home-101 telemetry
  ETag: W/"telem-101-9982"
  Vary: Accept-Encoding, Authorization
  X-DH-Cache-Tier: L1-Hit
  ```

### Профіль В. Стан охорони та замків (`GET /api/v1/homes/{home_id}/security/state`)
- **Опис:** Охоронний контур, дверні замки, датчики протікання води. **Критичний інваріант безпеки.** Кешування на Edge CDN суворо заборонене.
- **Приклад HTTP-відповіді:**
  ```http
  HTTP/2 200 OK
  Content-Type: application/json; charset=utf-8
  Cache-Control: private, no-cache, no-store, must-revalidate
  Pragma: no-cache
  Expires: 0
  Vary: Authorization
  X-DH-Cache-Tier: Bypass
  ```

### Профіль Г. Агрегована добова аналітика (`GET /api/v1/homes/{home_id}/stats/daily`)
- **Опис:** Важкі графіки енергоспоживання за добу. Обчислюються асинхронними фоновими задачами.
- **Приклад HTTP-відповіді:**
  ```http
  HTTP/2 200 OK
  Content-Type: application/json; charset=utf-8
  Cache-Control: public, max-age=3600, stale-while-revalidate=86400
  Surrogate-Control: max-age=86400
  Surrogate-Key: home-101 stats
  ETag: W/"stats-2026-08-18"
  Vary: Accept-Encoding, Authorization
  X-DH-Cache-Tier: L3-Hit
  ```

## 4. Простір тегів інвалідації (Surrogate-Key Topology)

Для того щоб інвалідація на Edge CDN була вибірковою й не вимагала повного очищення кешу всього сайту (Full Flush), платформа DH застосовує ієрархічну топологію тегів `Surrogate-Key`:

1. **Глобальний тег дому:** `home-{home_id}` (наприклад, `home-101`). Прикріплюється до **всіх** відповідей, що стосуються даного будинку. Дозволяє інвалідувати геть увесь кеш даного дому одним запитом при видаленні акаунта або зміні власника.
2. **Тег орендаря (Tenant):** `tenant-{tenant_id}` (наприклад, `tenant-42`). Дозволяє інвалідувати кеш усіх будинків конкретної управляючої компанії або корпоративного клієнта.
3. **Тег типізованої підсистеми:** `devices-list`, `telemetry`, `stats`. Дозволяє інвалідувати лише список пристроїв, не чіпаючи закешовані графіки аналітики.
4. **Тег окремого пристрою:** `dev-{device_id}` (наприклад, `dev-992`). Дозволяє зрізати кеш лише того конкретного будинку, де змінився конкретний давач.

## 5. Специфікація Edge Purge REST API

Внутрішній сервіс інвалідації `EdgePurgeClient` надсилає HTTP POST запити до платформи CDN для миттєвого зрізання кешу за тегами.

### Схема ендпойнта інвалідації

- **Метод:** `POST`
- **Шлях:** `/api/v1/internal/cdn/purge-keys`
- **Мережевий доступ:** Суворо внутрішній (Internal VPC / Private Gateway).

### Обов'язкові заголовки запиту

```http
POST /api/v1/internal/cdn/purge-keys HTTP/1.1
Host: cdn-control.internal.dh.io
Content-Type: application/json
X-DH-Internal-Token: secret_purge_token_991823a4f
X-Correlation-Id: req-purge-101-88492
```

### Специфікація тіла запиту (Payload Schema)

```json
{
  "keys": [
    "home-101",
    "devices-list"
  ],
  "domain": "api.dh.io",
  "soft": true,
  "executionPriority": "high"
}
```

#### Поля структури запиту:
- `keys` (масив рядків, обов'язкове): Список тегів `Surrogate-Key` для інвалідації. Максимум 256 тегів за один виклик.
- `domain` (рядок, обов'язкове): Цільовий домен платформи.
- `soft` (булеве, опціонально, за замовчуванням `true`): При `true` виконується **Soft Purge** (об'єкти позначаються як stale для подальшого SWR-оновлення). При `false` виконується **Hard Purge** (негайне видалення байтів з диска Edge).
- `executionPriority` (значення `"high" | "normal"`, опціонально): Пріоритет обробки у черзі інвалідацій CDN.

### Специфікація відповідей Edge Purge API

#### Статус 202 Accepted (Успішне прийняття інвалідації)
```json
{
  "status": "accepted",
  "purgeId": "p-8871239912",
  "purgedKeysCount": 2,
  "estimatedPropagationMs": 150,
  "timestamp": "2026-08-18T09:40:00Z"
}
```

#### Статус 400 Bad Request (Невірна структура запиту)
```json
{
  "type": "https://api.dh.io/errors/invalid-purge-payload",
  "title": "Схема тіла інвалідації недійсна",
  "status": 400,
  "code": "invalid_purge_payload",
  "detail": "Масив 'keys' перевищує максимально допустимий розмір у 256 елементів.",
  "requestId": "req-purge-101-88492"
}
```

#### Статус 401 Unauthorized (Помилка автентифікації)
```json
{
  "type": "https://api.dh.io/errors/unauthorized",
  "title": "Недійсний токен внутрішнього виклику Purge API",
  "status": 401,
  "code": "invalid_internal_token",
  "requestId": "req-purge-101-88492"
}
```

#### Статус 429 Rate Limited (Перевищення квоти викликів)
```json
{
  "type": "https://api.dh.io/errors/rate-limited",
  "title": "Перевищено ліміт викликів Purge API",
  "status": 429,
  "code": "purge_rate_limit_exceeded",
  "detail": "Дозволено не більше 500 purge-запитів на секунду для даного tenant.",
  "retryAfter": 1,
  "requestId": "req-purge-101-88492"
}
```

## 6. Діагностика та CLI-інструменти

Для оперативного налагодження стану кешу на Edge CDN інженери DH використовують наступні CLI-команди:

### Перевірка проходження кеш-заголовків та стану HIT/MISS

```bash
curl -i -H "Accept-Encoding: gzip" \
     -H "X-DH-Debug: 1" \
     https://api.dh.io/api/v1/homes/home-101/devices
```

Очікувані діагностичні заголовки у відповіді:
```http
HTTP/2 200 OK
cache-control: public, max-age=5, stale-while-revalidate=30
surrogate-key: home-101 devices-list
x-cache: HIT-L3
x-cache-hits: 412
x-serve-from-datacenter: fra-edge-01
age: 3
```

### Ручний виклик інвалідації за тегом будинку через curl

```bash
curl -X POST https://cdn-control.internal.dh.io/api/v1/internal/cdn/purge-keys \
  -H "Content-Type: application/json" \
  -H "X-DH-Internal-Token: secret_purge_token_991823a4f" \
  -H "X-Correlation-Id: manual-debug-101" \
  -d '{
    "keys": ["home-101"],
    "domain": "api.dh.io",
    "soft": true
  }'
```

Цей довідник визначає сувору контрактну межу, за дотриманням якої стежать автоматизовані фітнес-функції та контрактні тести у CI/CD платформі Digital Homes.
