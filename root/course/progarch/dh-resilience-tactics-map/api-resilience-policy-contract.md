# 📋 Контракт сигналізації та специфікація метаданих стійкості

Стандартизований інтерфейсний контракт сигналізації та метаданих стійкості для платформи Digital Homes (DH) визначає HTTP-заголовки атрибуції пріоритетів, форматовані конверти помилок відкидання трафіку (RFC 9457 Problem Details), контракт спостережуваності й інспекції автомата Circuit Breaker, а також повну специфікацію обгортки подій у черзі отруйних повідомлень (Dead-Letter Queue, DLQ).

Цей контракт живе на межі між зовнішніми пристроями (домашніми хабами, мобільними застосунками, настінними панелями) та внутрішньою мікросервісною інфраструктурою хмари. Головна мета контракту — забезпечення однакового розуміння стану системи всіма учасниками розподіленого середовища без додаткових кустарних узгоджень.

---

## 1. Заголовки атрибуції пріоритетів та контролю потоку

Для того щоб шлюз Admission Control та внутрішні сервіси ухвалювали рішення про прийом чи відкидання запитів без розбору тіла (payload), кожен вхідний HTTP/gRPC запит мусить нести метадані пріоритету та ідентифікації.

### 1.1. Вхідні заголовки запиту (Client / Gateway Request)

Заголовки атрибуції передаються в кожному вхідному HTTP-запиті. Якщо запит іде через проксі-сервери чи сервісну мережу (Service Mesh), ці заголовки зобов'язані зберігатися та прокидатися крізь усі проміжні шари без змін.

```
+------------------------+-------------------+---------------------------------------------------------+
| Заголовок              | Формат / Значення | Опис та призначення                                      |
+------------------------+-------------------+---------------------------------------------------------+
| X-DH-Priority          | P0 | P1 | P2 | P3 | P4 | Клас пріоритету запиту (P0 — найвищий, P4 — фоновий).   |
| X-DH-Client-Class      | hub | app | panel | dev | Клас клієнтського пристрою чи джерела запиту.           |
| X-DH-Tenant-ID         | UUIDv4            | Ідентифікатор домогосподарства для ізоляції квот.       |
| X-Correlation-ID       | string (alphanumeric) | Наскрізний ідентифікатор запиту для трасування.    |
+------------------------+-------------------+---------------------------------------------------------+
```

Якщо заголовок `X-DH-Priority` відсутній у вхідному запиті від мобільного застосунку чи зовнішнього партнера, шлюз Edge Gateway виставляє дефолтний пріоритет залежно від URI ендпойнта згідно з загальною матрицею пріоритетів платформи:
- Запити до `/api/v2/locks/*` або `/api/v2/alarms/*` автоматично отримують категорію **P0 (Critical)**.
- Запити до `/api/v2/devices/state` або `/api/v2/scenes/execute` отримують категорію **P1 (High)**.
- Запити до `/api/v2/presence/heartbeat` отримують категорію **P2 (Medium)**.
- Запити до `/api/v2/telemetry/*` отримують категорію **P3 (Low)**.
- Запити до `/api/v2/media/upload/*` або `/api/v2/firmware/download` отримують категорію **P4 (Background)**.

## 2. Заголовки сигналізації про відмову та керування штормом (Response)

Коли шлюз або сервіс змушений відмовити в обробці запиту через Rate Limiting (429) або Priority Shedding (503), відповідь **зобов'язана** містити заголовки, які вказують клієнту, як поводитися далі і скільки часу чекати перед наступним викликом.

### 2.1. Специфікація вихідних заголовків відмови

```
+------------------------+-------------------+---------------------------------------------------------+
| Заголовок              | Формат / Значення | Опис та призначення                                      |
+------------------------+-------------------+---------------------------------------------------------+
| Retry-After            | Integer (seconds) | Мінімальна пауза у секундах перед наступним повтором.   |
| X-DH-Brownout-Level    | L0 | L1 | L2 | L3 | L4 | Поточний рівень деградації системи на момент відмови.   |
| X-RateLimit-Limit      | Integer           | Ліміт дозволених запитів у вікні аналізу.               |
| X-RateLimit-Remaining  | Integer           | Залишок токенів у кошику клієнта.                        |
| X-RateLimit-Reset      | Unix Timestamp (s)| Час відновлення токенів кошика.                         |
+------------------------+-------------------+---------------------------------------------------------+
```

Заголовок `Retry-After` є обов'язковим згідно зі специфікацією HTTP RFC 9110 для відповідей 429 та 503. Клієнтські бібліотеки SDK та прошивки хабів зобов'язані зчитувати значення цього заголовка й додавати до нього випадковий джитер (Full Jitter), запобігаючи одночасному повторному виходу сотень тисяч пристроїв у мережу.

## 3. Конверти відмови RFC 9457 Problem Details

Для уникнення неоднозначностей та створення єдиного машинно-зчитуваного стандарту помилок платформа Digital Homes використовує специфікацію RFC 9457 Problem Details (`application/problem+json`). Усі сервіси повертають однакову базову структуру з розширеними полями для діагностики стійкості.

### 3.1. Відповідь 429 Too Many Requests (Rate Limit Exceeded)

Згенерована Token Bucket або Per-Tenant Quotas при перевищенні дозволеного ліміту інтенсивності викликів для конкретного домогосподарства чи IP-адреси.

```json
{
  "type": "https://api.digitalhomes.io/errors/rate-limit-exceeded",
  "title": "Rate Limit Exceeded",
  "status": 429,
  "detail": "Tenant 't-88412' has exceeded the allocated limit of 100 req/sec for tier 'standard'.",
  "instance": "/api/v2/homes/h-102/devices/lock-1/state",
  "code": "RATE_LIMIT_EXCEEDED",
  "retry_after_ms": 5000,
  "correlation_id": "req-99812-abc"
}
```

Розбір полів конверта:
- `type`: унікальний URI, що веде на документацію даного типу помилки. Клієнтські парсери сортують помилки за цим полем.
- `title`: короткий людсько-зчитуваний опис класу помилки.
- `status`: вихідний HTTP-код відповіді.
- `detail`: деталізоване повідомлення з вказівкою конкретного контексту (наприклад, перевищеного ліміту).
- `instance`: URI конкретного ендпойнта, на якому сталася відмова.
- `code`: машино-зчитуваний внутрішній код помилки для швидкого розбору в гілках `switch/case` у коді SDK.
- `retry_after_ms`: рекомендована пауза перед повтором у мілісекундах (доповнює HTTP-заголовок `Retry-After`).
- `correlation_id`: наскрізний ідентифікатор трасування, що збігається з логами сервера для подальшого аудиту.

### 3.2. Відповідь 503 Service Unavailable (Priority Load Shedding)

Згенерована шлюзом або внутрішнім перехоплювачем при виникненні перевантаження системи (Brownout state) для другорядного трафіку.

```json
{
  "type": "https://api.digitalhomes.io/errors/load-shedded",
  "title": "Service Load Shedding Active",
  "status": 503,
  "detail": "Request P3 dropped: platform is operating under Brownout Level L2 (Telemetry Throttling).",
  "instance": "/api/v2/telemetry/historical",
  "code": "PRIORITY_LOAD_SHEDDED",
  "current_brownout_level": "L2",
  "minimum_allowed_priority": "P1",
  "retry_after_ms": 15000,
  "correlation_id": "req-77142-xyz"
}
```

Додаткові поля стійкості:
- `current_brownout_level`: поточний активний рівень деградації системи (L1..L4).
- `minimum_allowed_priority`: мінімальний клас пріоритету (наприклад, P1), який зараз пропускається шлюзом. Дозволяє клієнту згорнути другорядні запити й не надсилати їх взагалі.

## 4. Контракт стану та телеметрії Circuit Breaker

Внутрішні сервіси платформи надають адмін-інтерфейс для спостереження за станом усіх вбудованих автоматах розмикачів ланцюга (Circuit Breakers). Цей інтерфейс використовується системами моніторингу (Prometheus / Grafana) та автоматичними панелями оперативного реагування.

### 4.1. Специфікація опитування стану (GET /admin/circuit-breakers)

```
GET /admin/circuit-breakers
Content-Type: application/json
```

```json
{
  "timestamp": "2026-08-18T18:02:15Z",
  "service": "device-command-service",
  "breakers": [
    {
      "name": "postgres-primary-db",
      "state": "CLOSED",
      "metrics": {
        "total_requests": 14200,
        "failed_requests": 12,
        "error_rate_pct": 0.08,
        "p99_latency_ms": 14.2
      },
      "config": {
        "error_threshold_pct": 50.0,
        "sliding_window_sec": 10,
        "sleep_window_sec": 5
      }
    },
    {
      "name": "external-weather-api",
      "state": "OPEN",
      "opened_at": "2026-08-18T18:01:50Z",
      "metrics": {
        "total_requests": 450,
        "failed_requests": 310,
        "error_rate_pct": 68.8,
        "p99_latency_ms": 5000.0
      },
      "config": {
        "error_threshold_pct": 40.0,
        "sliding_window_sec": 10,
        "sleep_window_sec": 15
      }
    }
  ]
}
```

### 4.2. Контракт ручного керування та примусового скидання (Admin Actuation API)

У разі проведення аварійних робіт або регламентного обслуговування інженери чергової зміни можуть примусово змінити стан Circuit Breaker за допомогою команд керування:

- `POST /admin/circuit-breakers/{name}/force-open` — примусово розімкнути ланцюг і перевести сервіс у режим виконання Fallback.
- `POST /admin/circuit-breakers/{name}/force-closed` — примусово замкнути ланцюг для перевірки працездатності після усунення аварії.
- `POST /admin/circuit-breakers/{name}/reset` — обнулити ковзне вікно метрик помилок і повернути автомат у вихідний стан `CLOSED`.

Кожна дія ручного втручання генерує запис у журналі аудиту з вказівкою авторизованого інженера та обов'язковим журналюванням підстави операції.

## 5. Специфікація обгортки подій у Dead-Letter Queue (DLQ Envelope)

Повідомлення, які не вдалося обробити після серії ретраїв із дшитером через отруйну структуру (poison message) чи стійкий збій залежності, відправляються в чергу DLQ. Повідомлення запаковується в спеціальний конверт `DLQ Envelope`, що містить оригінальне тіло, метадані джерела та повну діагностичну метрику відмови.

### 5.1. JSON Schema специфікація конверта DLQ (`application/vnd.dh.dlq.v1+json`)

Конверт запаковки отруйного повідомлення має наступний вигляд:

```json
{
  "$schema": "https://schemas.digitalhomes.io/messaging/dlq-envelope-v1.json",
  "dlq_message_id": "dlq-msg-550192",
  "original_topic": "dh.events.telemetry.v1",
  "original_partition": 3,
  "original_offset": 884102,
  "first_received_at": "2026-08-18T18:00:10.120Z",
  "failed_at": "2026-08-18T18:00:45.890Z",
  "attempts_count": 5,
  "last_error": {
    "exception_class": "JsonParseException",
    "message": "Unexpected end-of-input: expected close marker for Object at offset 410",
    "stack_trace_hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
  },
  "metadata": {
    "producer_id": "hub-7741",
    "firmware_version": "v3.2.1-legacy",
    "schema_version": "v1"
  },
  "payload_base64": "eyAiZXZlbnQiOiAibW90aW9uX2RldGVjdGVkIiwgImRldmljZV9pZCI6ICJzZW5zLTkxIiwgInRlbXA...=="
}
```

### 5.2. Правила збереження та повторного програвання (DLQ Replay Pipeline)

Збереження оригінального payload у вигляді `payload_base64` гарантує, що жоден байт первинних даних не буде пошкоджений під час запаковки чи перетворення форматів. Поля `stack_trace_hash` та `exception_class` дозволяють інструментам спостереження групувати тисячі відпаркованих повідомлень за єдиним типом помилки.

Після виправлення багу у прошивці чи коді обробника інженери запускають консольну утиліту `dh-dlq-replay`, яка прочитує повідомлення з DLQ, кодує їх назад у первинний топік `original_topic` і видаляє з черги відпаркованих подій. Такий підхід робить процес розбору отруйних повідомлень прозорим, детермінованим та безпечним для основної виробничої лінії.
