# pymavlink

Уяви апарат, яким керують ніби з пульта: увесь «розум» сидить на землі, у наземній станції, а до борту по радіо летять лише команди. Цей розум можна винести **на сам апарат** — хай маленький комп'ютер на борту читає [потік MAVLink](book:communications/mavlink-packet) і керує польотом за власною програмою, без участі землі. Інструмент, яким це роблять у Python, — **pymavlink**; архітектура, у якій він живе, — **бортовий комп'ютер** поряд із польотним контролером. Тут радіозв'язок як система й переростає в справжню автономність.

Назва **MAVLink** (англ. *Micro Air Vehicle Link* — «зв'язок для мікроапаратів») — це формат кадру й набір повідомлень, якими апарат і станція говорять між собою. **pymavlink** — бібліотека, що дає цьому формату живе втілення в Python.

### MAVLink у Python кількома рядками

Уся практична робота з [читанням потоку й відправкою команд](root:embedded/mavlink-commands) спирається на одну бібліотеку — **pymavlink**.

![Зліва мінімальний код, що вже читає потік апарата; справа — що бере на себе бібліотека](/root/course/embedded/pymavlink/img/library.svg)
*pymavlink дає з'єднання (serial, UDP чи TCP), розбір і пакування всіх повідомлень усіх діалектів — згенеровані з тих самих XML, що задають [структуру кадру MAVLink](book:communications/mavlink-packet). Кілька рядків — і код уже читає потік апарата.*

**pymavlink** — це низькорівнева, загального призначення реалізація MAVLink для Python: вона відкриває з'єднання (серійний порт, [UDP чи TCP](book:communications/tcp-vs-udp)), приймає й розбирає кадри, пакує команди й знає **всі** діалекти, бо її код **згенеровано** з тих самих XML-описів, що задають [сам кадр MAVLink](book:communications/mavlink-packet). Працює і з MAVLink 1, і з MAVLink 2. Через це бібліотека не «розуміє» повідомлення наперед закладеним кодом — вона будує класи повідомлень із опису, тож щойно в діалекті з'являється нове повідомлення, pymavlink уміє його читати без жодних правок.

Найменша корисна програма виглядає так:

```python
from pymavlink import mavutil

# відкриваємо лінію: слухаємо UDP-порт, куди апарат шле потік
m = mavutil.mavlink_connection('udpin:localhost:14550')

m.wait_heartbeat()                        # чекаємо першого heartbeat
while True:
    msg = m.recv_match(blocking=True)     # читаємо потік підряд
    # …реагуй, шли команди, веди власну логіку…
```

Розберімо кожен рядок, бо в цих трьох викликах — увесь кістяк роботи з апаратом.

`mavutil.mavlink_connection(device)` відкриває **лінію**. Рядок `device` каже, куди під'єднатися: `'udpin:localhost:14550'` — слухати UDP-порт (типово так приймають потік від симулятора чи від моста на борту); `'/dev/ttyUSB0'` або `'/dev/serial0'` — серійний порт (саме так комп'ютер на борту під'єднано до контролера дротом); `'tcp:...'` — поверх TCP. Один і той самий код працює з будь-яким із цих каналів — змінюється лише рядок підключення.

`wait_heartbeat()` блокує виконання, доки з лінії не прийде перше повідомлення **heartbeat** (англ. «серцебиття») — кадр, який апарат шле раз на секунду, щоб показати: я живий, ось мій тип і стан. Цей виклик робить ще одну важливу річ: він **запам'ятовує, хто на тому кінці лінії** — заповнює `m.target_system` і `m.target_component` (номери системи й вузла відправника). Без цих номерів неможливо адресувати команду назад апарату, тож heartbeat — не просто ознака життя, а ще й «знайомство», після якого можна звертатися.

`recv_match()` читає наступне повідомлення з потоку. Без аргументів він повертає будь-який кадр; із `type='ATTITUDE'` — лише повідомлення цього типу, а решту пропускає; `blocking=True` каже чекати, доки потрібне повідомлення прийде. Так із суцільного потоку дістають саме те, що цікавить цієї миті.

> 🔧 **Навіщо це.** Той самий API — підключення, очікування heartbeat, фільтрований прийом — лежить в основі будь-якої взаємодії з апаратом: чи ти пишеш діагностичний скрипт на ноутбуці, чи бортову логіку. Вивчивши ці три виклики, ти вже вмієш і слухати телеметрію, і слати команди.

### Робочий приклад: злетіти за командою

Покажемо повне коло — підключитися, дочекатися апарата, прочитати телеметрію й **надіслати команду**. Команди в MAVLink передають кадром `COMMAND_LONG`: у ньому номер команди (одна з констант `MAV_CMD_…`) і до семи числових параметрів. Бібліотека дає для цього метод `mav.command_long_send(...)`.

**Умова: під'єднатися до апарата на UDP-порту, дочекатися heartbeat, прочитати висоту з телеметрії, перевести апарат у режим GUIDED, дати arm і команду злетіти на 10 метрів.**

```python
from pymavlink import mavutil

m = mavutil.mavlink_connection('udpin:localhost:14550')
m.wait_heartbeat()
print("апарат на лінії: system %d, component %d"
      % (m.target_system, m.target_component))

# 1) прочитати одну порцію телеметрії — глобальну позицію з висотою
msg = m.recv_match(type='GLOBAL_POSITION_INT', blocking=True)
print("висота над рівнем моря: %.1f м" % (msg.alt / 1000.0))   # alt у міліметрах

# 2) перевести у GUIDED (для ArduPilot режим має номер у таблиці режимів)
m.set_mode('GUIDED')

# 3) arm: команда MAV_CMD_COMPONENT_ARM_DISARM, param1 = 1 (увімкнути)
m.mav.command_long_send(
    m.target_system, m.target_component,
    mavutil.mavlink.MAV_CMD_COMPONENT_ARM_DISARM,
    0,            # confirmation
    1, 0, 0, 0, 0, 0, 0)
m.motors_armed_wait()                       # дочекатися, поки мотори озброєно

# 4) злетіти на 10 м: param7 = цільова висота
m.mav.command_long_send(
    m.target_system, m.target_component,
    mavutil.mavlink.MAV_CMD_NAV_TAKEOFF,
    0,
    0, 0, 0, 0, 0, 0, 10)

# 5) дочекатися підтвердження виконання команди
ack = m.recv_match(type='COMMAND_ACK', blocking=True)
print("відповідь апарата:", ack.result)
```

Що тут відбувається крок за кроком. Спершу `wait_heartbeat()` дає нам `target_system`/`target_component` — адресу, без якої наступні команди нікуди не підуть. Далі `recv_match(type='GLOBAL_POSITION_INT')` витягає з потоку одне повідомлення з позицією; поле `alt` у ньому — у міліметрах, тому ділимо на 1000, щоб дістати метри. Команди `command_long_send` адресуємо тому самому апарату: у `MAV_CMD_COMPONENT_ARM_DISARM` перший параметр `1` означає «озброїти», а в `MAV_CMD_NAV_TAKEOFF` сьома координата — бажана висота. Нарешті `COMMAND_ACK` — це відповідь апарата «прийняв / не можу», без якої ми не знали б, чи команда взагалі виконана. Це і є повний цикл «прочитав → вирішив → скомандував», з якого складається будь-яка автоматизація.

Показово, що **pymavlink написав Ендрю Тридджелл** — той самий, хто розвинув ArduPilot, — і написав саме тому, що бібліотека була потрібна йому для **MAVProxy**, наземної станції на Python (обидва проєкти він зробив близько 2011 року). Відкрита, колективна праця тут працює на кожного, хто бере бібліотеку в руки. А головне — **той самий код** може бігти не лише на ноутбуці, а й на самому апараті.

### Бортовий комп'ютер: розум прямо на апараті

Ось ключова ідея бортової автономності — **бортовий комп'ютер** (англ. *companion computer* — «комп'ютер-супутник», що ставлять у пару до контролера).

![Маленький Linux-комп'ютер поряд із польотним контролером, з'єднаний коротким UART](/root/course/embedded/pymavlink/img/companion.svg)
*Маленький Linux-комп'ютер (Raspberry Pi, NVIDIA Jetson) ставлять на сам апарат, поряд із польотним контролером, і з'єднують коротким UART — без жодного радіо. На ньому біжить твій pymavlink-код, а MAVLink летить дротом.*

Замість того щоб «думати» на землі й слати команди по ненадійному радіо, маленький Linux-комп'ютер (Raspberry Pi, NVIDIA Jetson тощо) ставлять прямо **на апарат**, поряд із польотним контролером, і з'єднують їх **коротким дротом UART**. MAVLink тоді тече не через ефір, а по сантиметровому проводі — без втрат, без [затримки й ненадійності радіо](book:communications/latency-reliability), без страху перед спрацюванням failsafe. На цьому комп'ютері біжить твій **pymavlink-код**, що читає телеметрію й шле команди контролеру **локально**. Апарат дістає власний розум на борту, незалежний від зв'язку з землею. Це і є місток від «дистанційного керування» до автономності.

### Поділ праці: політ окремо, розум окремо

Постає природне питання: навіщо **два** комп'ютери — контролер і бортовий? Бо в них різні ролі, і змішувати їх було б помилкою.

![Дві ролі поряд: контролер у реальному часі й комп'ютер для важкого думання, між ними MAVLink](/root/course/embedded/pymavlink/img/architecture.svg)
*Політний контролер відповідає за політ у реальному часі: стабілізацію, давачі, мотори, надійність — проста, перевірена логіка. Бортовий комп'ютер — за «думання»: комп'ютерний зір, ШІ, складні рішення, важкі обчислення, зв'язок. Між ними — MAVLink.*

Поділ глибокий і правильний. **Польотний контролер** — це «спинний мозок»: він тримає апарат у повітрі в реальному часі, читає давачі, крутить мотори, і його логіка має бути простою, перевіреною й надійною понад усе, бо [керування важливіше за будь-яку телеметрію](book:communications/control-telemetry). **Бортовий комп'ютер** — це «головний мозок»: він робить важке й складне — комп'ютерний зір, машинне навчання, прокладання маршрутів, зв'язок через LTE, — те, що контролеру не під силу й не можна довіряти, бо складне за природою ненадійне. Вони **розмовляють MAVLink** через дріт: комп'ютер радить (шле команди), а контролер виконує, не перестаючи стабілізувати політ. Якщо «розумний» комп'ютер зависне, контролер просто далі тримає апарат і за потреби виконає failsafe. Розумний, безпечний поділ.

### Повне коло: початкова мета здійснюється

Тут історія MAVLink складається в досконале коло. [Народилася вона](book:communications/control-telemetry) зі studentського проєкту: 2008 року Лоренц Маєр у ETH Zürich хотів зробити дрон **із комп'ютерним зором**, що сам літає в приміщенні й обминає перешкоди, — а MAVLink створив **між іншим**, як допоміжний інструмент (сам протокол вийшов 2009 року).

![Початкова мета 2008-го й сьогодення: той самий зір тепер живе на борту через pymavlink](/root/course/embedded/pymavlink/img/full-circle.svg)
*2008 року мета була — дрон, що сам бачить і літає (комп'ютерний зір), а MAVLink був лише побічним інструментом. Сьогодні бортовий комп'ютер із pymavlink і зором дає ту саму автономність. «Побічний» MAVLink став містком, що уможливив початкову мрію.*

І через роки коло замкнулося: **бортовий комп'ютер** із камерою, машинним зором і **pymavlink** дає апарату саме ту автономність, заради якої все й починалося. «Побічний» інструмент — MAVLink — виявився тим самим **містком**, що уможливив початкову мету. Це не лише гарна історія, а й урок про те, як у техніці допоміжне часом стає головним, а наполеглива робота над «нудною» інфраструктурою врешті відчиняє двері до амбітної мети.

### Що можна автоматизувати

Що ж конкретно дає розум на борту? Будь-який сценарій «читай → вирішуй → командуй», тепер без людини.

![Чотири типові сценарії бортової автоматизації, кожен — той самий цикл читай-вирішуй-командуй](/root/course/embedded/pymavlink/img/scenarios.svg)
*Розумний failsafe (сів заряд — сам шле RTL). Слідкування за ціллю (зір бачить об'єкт — коригує курс). Геозона (наблизився до межі — не пускає далі). Авто-картографування (облітає площу за планом і знімає).*

Можливості широкі. **Розумний failsafe**: код стежить за зарядом і сам шле RTL (повернення додому), коли пора. **Слідкування за ціллю**: камера й зір розпізнають об'єкт, а pymavlink коригує курс, щоб утримувати його в кадрі. **Геозона**: бортовий розум не пускає апарат за дозволену межу. **Авто-картографування**: облетіти площу за планом, роблячи знімки. Усе це — той самий простий цикл «читай телеметрію → ухвали рішення → [надішли команду](root:embedded/mavlink-commands)», тільки замкнений на самому апараті, без затримок і ризиків радіоканалу. Так дрон із дистанційно керованого стає по-справжньому автономним.

### Екосистема над pymavlink

pymavlink — не стеля, а **фундамент**. Над ним зведено інструменти на будь-який смак.

![Рівні над pymavlink: MAVProxy, MAVSDK/DroneKit і MAVROS як міст у ROS](/root/course/embedded/pymavlink/img/ecosystem.svg)
*MAVProxy — командна наземна станція й проксі на pymavlink. MAVSDK і DroneKit — вищі рівні API для зручнішої автоматизації. MAVROS — міст MAVLink ↔ ROS, що відчиняє двері у велику робототехніку. Усе це стоїть на тому самому MAVLink.*

Над MAVLink виросла ціла екосистема. **MAVProxy** — командна наземна станція й проксі (теж робота Тридджелла). **MAVSDK** — сучасна бібліотека вищого рівня, що ховає дрібниці заради зручнішої автоматизації; старіший **DroneKit** робив те саме, але вже майже не розвивається, тож для нового коду беруть MAVSDK. А **MAVROS** — це **міст** між MAVLink і **ROS** (англ. *Robot Operating System* — «операційна система для роботів»), офіційний шлюз, який уводить апарат у велику екосистему робототехніки з її готовими блоками сприйняття, планування й керування. Усе це стоїть на **тому самому MAVLink**, що задає [структуру кадру](book:communications/mavlink-packet) до останнього байта, — тож ці потужні інструменти для тебе не магія, а зрозуміла надбудова над тим, що вже всередині.
