# ⚙️ Рушій ініціалізації за таблицею: одна машина на всі панелі

**Задача.** У [статті](root:embedded/gram-init-sequence) ми написали `st7789_init()` — лінійне простирадло з `send_cmd`, `send_data` і `delay_ms`, рядок за рядком. Воно працює, але має дві вади, які болять не сьогодні, а на другому-третьому проєкті. Перша: під кожну нову панель (а їх у вашій шухляді буде кілька — ST7789 на одній платі, ILI9341 на іншій) ви копіюєте все простирадло й правите команди вручну, плодячи майже однаковий код, у якому легко загубити одну паузу чи переставити крок. Друга: послідовність вшита в **логіку** програми, а не лежить **даними**, тож її не можна ні прочитати з файлу, ні згенерувати, ні просто окинути оком як таблицю. Треба зробити інакше: винести послідовність у компактну **таблицю-даних** у флеші, а в прошивці лишити **один невеликий інтерпретатор**, що цю таблицю прокручує — тримає лінії D/C і CS, відпрацьовує паузи, коректно смикає ніжку RST, ловить збій шини й безпечно відновлюється. І тоді нова панель — це не новий драйвер, а новий масив байтів. Усе на реальному C, без псевдокоду.

**Ідея.** Придивімося, з чого насправді складається будь-яка init-послідовність. Кожен її крок — це завжди одне й те саме: послати **байт-команду**, послати за нею **нуль або кілька байтів-аргументів**, інколи **зачекати** скільки треба кремнію. Команди різні, аргументи різні, паузи різні — а **форма кроку незмінна**. А коли форма у всіх кроків однакова, її гріх лишати кодом: краще описати один крок **структурою з трьох полів** — код команди, скільки аргументів, скільки чекати після, — а саму послідовність викласти **масивом** таких структур. Тоді «виконати ініціалізацію» зводиться до циклу: візьми запис, вилий команду, вилий його аргументи, витримай паузу, перейди до наступного, доки не кінець таблиці. Це той самий хід, що перетворює мову програми на дані: замість того щоб **писати** кроки, ми **описуємо** їх, а одна крихітна машина їх **виконує**.

Чому це не передчасне ускладнення, а ощадливість — видно, щойно панелей стає більше за одну. Лінійний `st7789_init()` несе всю послідовність у вигляді коду: щоб додати ILI9341, треба написати другу таку саму функцію й вручну провести в ній ту саму нитку reset → sleep-out → формат → показ, не загубивши жодної паузи. Дві панелі — дві копії, три — три, і кожна правка (скажімо, ви вирішили збільшити паузу після `SLPOUT` із запасом) тягне обхід усіх копій. Табличний рушій розриває цей зв'язок: машина-інтерпретатор пишеться **раз** і не залежить від панелі, а кожна панель — це лише свій масив байтів. Додати панель — додати таблицю; виправити логіку пауз — виправити одну функцію. Ціна — десяток рядків інтерпретатора й одна структура; виграш — лінійне зростання коду замість копіювання простирадел.

*Атом таблиці. Кожен крок ініціалізації — це трійка: код команди, скільки байтів-аргументів іде слідом, і скільки мілісекунд чекати після. Запис без аргументів (як `SLPOUT 0x11`) має `n_args = 0`, але може мати паузу; запис формату (`COLMOD 0x3A`) несе один аргумент `0x55`. Уся послідовність — масив таких трійок у флеші, який інтерпретатор прокручує згори вниз.*

## Крок 1. Формат запису — трійка в флеші

Опишімо один крок структурою. Нам потрібні три речі: код команди, кількість аргументів і пауза після кроку в мілісекундах. Самі аргументи зручно тримати не всередині структури фіксованого розміру (бо їх буває від нуля до десятка), а вказівником на масив у флеші — так запис лишається маленьким і однаковим, хай скільки в нього аргументів.

```c
#include <stdint.h>

// Один крок init-послідовності. Лежить у флеші (const) — не їсть RAM.
typedef struct {
    uint8_t        cmd;       // код команди (напр. 0x11 SLPOUT)
    uint8_t        n_args;    // скільки байтів-аргументів іде слідом
    const uint8_t *args;      // вказівник на аргументи у флеші (NULL, якщо n_args == 0)
    uint16_t       delay_ms;  // пауза ПІСЛЯ кроку, мс (0 — без паузи)
} init_cmd_t;
```

Чому поля саме такі. `cmd` і `n_args` — це мінімум, без якого крок не послати: контролер чекає байт у режимі «команда», а тоді рівно стільки байтів у режимі «дані», скільки наказує таблиця. `delay_ms` окремим полем — бо пауза прив'язана **до кроку**, а не до команди взагалі: та сама команда на одній панелі вимагає паузи, на іншій ні, і це різниця **таблиць**, а не коду. А `args` вказівником, а не вкладеним масивом, тримає структуру компактною й вирівняною: запис `SLPOUT` без аргументів і запис гами з п'ятнадцятьма аргументами займають у масиві **однаково** мало місця, бо великий хвіст аргументів живе окремо у флеші, а в записі лежить лише адреса.

> 🔧 **Навіщо це.** Тримати послідовність даними, а не кодом, — це не академічна краса, а пряма економія флешу й нервів. Масив `const init_cmd_t[]` лягає в секцію `.rodata` (у флеш), не з'їдаючи дорогоцінну RAM мікроконтролера; та сама послідовність кодом роздула б `.text` і розповзлася б копіями під кожну панель. А головне — таблицю можна **прочитати очима** як специфікацію: видно весь старт панелі на одному екрані, з паузами й аргументами, без блукання по тілу функції.

Тепер аргументи й сама таблиця для ST7789. Аргументи виносимо в окремі маленькі масиви (теж `const`, теж у флеші), а в записах посилаємося на них. Команди й значення беремо ті самі, що в робочому `st7789_init()` зі статті, плюс ті, що в лінійному коді ми лишили згорнутими.

```c
// Аргументи окремими масивами у флеші (на них дивляться поля .args).
static const uint8_t ST_COLMOD[] = { 0x55 };        // 16 біт/піксель, RGB565
static const uint8_t ST_MADCTL[] = { 0x00 };        // портрет, RGB (інверт? спробуй 0x08)

// Таблиця-даних для ST7789. Прокручується згори вниз.
static const init_cmd_t st7789_table[] = {
    { 0x01, 0, NULL,      150 },   // SWRESET  — програмне скидання, ≥120 мс
    { 0x11, 0, NULL,      120 },   // SLPOUT   — вихід зі сну, найважливіша пауза
    { 0x3A, 1, ST_COLMOD,  10 },   // COLMOD   — формат пікселя
    { 0x36, 1, ST_MADCTL,   0 },   // MADCTL   — орієнтація й порядок кольору
    { 0x21, 0, NULL,       10 },   // INVON    — інверсія (ST7789 її потребує)
    { 0x13, 0, NULL,       10 },   // NORON    — нормальний режим розгортки
    { 0x29, 0, NULL,       20 },   // DISPON   — увімкнути показ, аж тепер
};
```

Зверніть увагу на дві дрібниці, що несуть зміст. По-перше, апаратного скидання ніжкою RST у таблиці **немає** — і це навмисно: смикання ніжки відбувається **до** таблиці, окремою дією, бо воно про *залізо плати* (є та ніжка чи ні, куди розведена), а не про *логіку панелі*; до цього повернемося в кроці 3. По-друге, тут уже з'явилися рядки `INVON` (`0x21`) і `NORON` (`0x13`), яких не було у скороченому прикладі статті: ST7789 у типовій збірці вмикає інверсію кольору — це не помилка, а особливість саме цих панелей, [підтверджена референсним драйвером Adafruit](https://github.com/adafruit/Adafruit-ST7735-Library/blob/master/Adafruit_ST7789.cpp). Запам'ятайте цей рядок — за хвилину він стане ключовою відмінністю від ILI9341.

## Крок 2. Інтерпретатор — серце рушія

Тепер машина, що прокручує таблицю. Вона приймає масив записів і їхню кількість, і для кожного робить рівно те, що ми описали словами: команда, аргументи, пауза. Поки що — без перевірки помилок (її додамо кроком далі, щоб не змішувати дві думки).

```c
// Низькорівневі примітиви платформи — ті самі, що й у статті.
void send_cmd(uint8_t c);                        // D/C = 0, вилити байт-команду
void send_data(const uint8_t *buf, uint32_t n);  // D/C = 1, вилити n байтів даних
void delay_ms(uint32_t ms);                      // блокувальна пауза

// Прокрутити таблицю згори вниз. n — кількість записів.
void run_init_table(const init_cmd_t *tab, uint32_t n) {
    for (uint32_t i = 0; i < n; i++) {
        send_cmd(tab[i].cmd);                     // 1) команда: D/C опускає примітив
        if (tab[i].n_args > 0) {                  // 2) аргументи, якщо є
            send_data(tab[i].args, tab[i].n_args);
        }
        if (tab[i].delay_ms > 0) {                // 3) пауза, якщо крок її вимагає
            delay_ms(tab[i].delay_ms);
        }
    }
}
```

Ось і весь двигун. Прочитаймо, що тут важливо. Цикл **не знає жодної конкретної команди** — для нього `SLPOUT` і `DISPON` нерозрізненні, він лише бере трійку «команда / аргументи / пауза» й виконує її. Уся специфіка панелі лежить у таблиці, а не в машині; машина — універсальна. Перемикання лінії D/C сховане в `send_cmd`/`send_data`: перший опускає D/C перед байтом (контролер читає його як команду), другий піднімає (контролер читає як дані) — рушієві про це думати не треба, бо примітиви вже тримають правильний рівень. Порядок усередині кроку — команда, потім аргументи, потім пауза — і він критичний: пауза стоїть **після** аргументів, бо чекати треба, поки відпрацює вся команда з її даними, а не лише її код.

Запустити старт ST7789 тепер — один рядок:

```c
run_init_table(st7789_table, sizeof(st7789_table) / sizeof(st7789_table[0]));
```

Цей `sizeof(масив)/sizeof(елемент)` — звична в C ідіома «довжина масиву»: повний розмір таблиці в байтах, поділений на розмір одного запису, дає кількість записів. Тримати її так, а не вписувати число вручну, — щоб додавання чи видалення рядка таблиці **само** оновлювало довжину, і ви ніколи не прокрутили б на запис менше чи більше, ніж реально є.

> 🔧 **Навіщо це.** Інтерпретатор, що не знає команд, — це і є та межа, яка дає переносність. Доки машина оперує абстрактною трійкою, а не конкретними `SLPOUT`/`DISPON`, та сама функція годиться будь-якій панелі, чий старт зводиться до «команда + аргументи + пауза», — а так влаштований старт майже всіх дрібних SPI-контролерів. Ви пишете цей цикл раз і більше не торкаєтесь; усе подальше різноманіття живе в таблицях.

## Крок 3. Ніжка RST — окремий, точний ритуал

Апаратне скидання я свідомо лишив поза таблицею, і тепер час пояснити чому та зробити його правильно. Смикання ніжки **RST** — це не «ще одна команда», а інша фізична дія: не байт по шині, а рівень на окремому проводі, з власним точним таймінгом. Загнати її в таблицю команд означало б змішати два різні світи — байти шини й рівні GPIO; чистіше винести reset в окрему функцію, що йде **перед** прокруткою таблиці.

```c
void rst_pin(int level);   // керувати ніжкою RST: 1 — високо, 0 — активний нуль

// Апаратне скидання контролера ніжкою RST.
void hw_reset(void) {
    rst_pin(1); delay_ms(5);     // переконатися, що стартуємо з високого
    rst_pin(0); delay_ms(10);    // активний нуль: datasheet вимагає ≥10 мкс, беремо з запасом
    rst_pin(1); delay_ms(120);   // відпустити — і дати матриці час прокинутися
}
```

Тут кожне число — не з повітря. Скидання активне **низьким** рівнем: щоб скинути, ніжку притискають до нуля. Тривалість цього нуля датшити дають крихітну — порядку **10 мікросекунд**, — але затягнути її безпечно, тому беремо з запасом і не дрібнимося. А от пауза **після** відпускання — інша річ: це ті самі ~120 мс, які потрібні матриці, щоб піднятися після скидання, точно як після `SLPOUT`. Послідовність рівнів — високо, низько, високо — не випадкова: перший «високо» гарантує відомий початковий стан (раптом ніжка висіла невизначено), середній «низько» і є саме скидання, фінальний «високо» виводить контролер у робочий режим.

Повний старт панелі тепер читається як дві природні фази — спершу залізо, тоді логіка:

```c
void st7789_start(void) {
    hw_reset();                   // 1) фізичне скидання ніжкою (про залізо плати)
    run_init_table(st7789_table,  // 2) прокрутити таблицю команд (про логіку панелі)
                   sizeof(st7789_table) / sizeof(st7789_table[0]));
}
```

А якщо ніжка RST **не розведена** — а на дрібних модулях це звична економія, контакт RST там просто притягнутий до живлення резистором? Тоді апаратного скидання нема чим зробити, і вся надія на **програмне** — `SWRESET` (`0x01`), що першим рядком стоїть у таблиці. Саме тому ми лишили його в таблиці навіть за наявності `hw_reset()`: подвійне скидання не від надмірності, а щоб той самий код працював і там, де ніжка є, і там, де її нема. Коли RST не розведено, `hw_reset()` смикне неприєднаний пін у порожнечу (нешкідливо), а реально скине контролер уже `SWRESET` із таблиці. Це і є переносність на ділі: один код, дві різні плати.

> 🔧 **Навіщо це.** Найпідступніший дефект саме тут: «на тій платі драйвер працює, на цій — мертвий екран». Часта причина — RST не розведено, а ви покладалися лише на апаратне скидання. Тримайте в таблиці `SWRESET` завжди — і драйвер переживе плату без ніжки reset. І не вкорочуйте паузу після reset «бо швидко»: матриця після скидання піднімається ті самі десятки мілісекунд, що й після sleep-out, незалежно від того, ніжкою ви скидали чи командою.

## Крок 4. Перевірка помилок шини й безпечне відновлення

Дотепер наш інтерпретатор вірив, що кожен байт долетів. На SPI це часто справді так — лінія коротка, ведений завжди слухає, — але «часто» не означає «завжди»: примітив `send_cmd` повертає код, бо передача може не вдатися (зайнятий контролер шини, тайм-аут DMA, збій периферії). Зрілий рушій цей код **перевіряє** й на збої не суне далі наосліп, а зупиняється — бо ініціалізація це ланцюг, де кожна ланка спирається на попередню, і слати `DISPON` після того, як `SLPOUT` не долетів, — гарантована біла пляма.

Нехай примітиви повертають статус: `0` — успіх, інакше — код помилки. Тоді інтерпретатор передає цей статус нагору, а на першому ж збої припиняє прокрутку.

```c
typedef enum { DISP_OK = 0, DISP_ERR_BUS, DISP_ERR_ARGS } disp_status_t;

// Примітиви тепер звітують про збій шини.
int send_cmd_checked(uint8_t c);                        // 0 — успіх, інакше — збій
int send_data_checked(const uint8_t *buf, uint32_t n);  // 0 — успіх, інакше — збій

disp_status_t run_init_table_checked(const init_cmd_t *tab, uint32_t n) {
    for (uint32_t i = 0; i < n; i++) {
        if (send_cmd_checked(tab[i].cmd) != 0) {
            return DISP_ERR_BUS;             // команда не долетіла — далі йти безглуздо
        }
        if (tab[i].n_args > 0) {
            if (send_data_checked(tab[i].args, tab[i].n_args) != 0) {
                return DISP_ERR_BUS;         // аргументи не долетіли — теж стоп
            }
        }
        if (tab[i].delay_ms > 0) {
            delay_ms(tab[i].delay_ms);
        }
    }
    return DISP_OK;                          // уся таблиця пройшла чисто
}
```

Логіка проста, але правильна: на будь-якому невдалому байті ми **негайно** виходимо з кодом помилки, а не докручуємо решту таблиці в надії, що «якось обійдеться». Чому саме так — бо init-послідовність не терпить дір. Якщо `COLMOD` не долетів, наступний `MADCTL` ляже на контролер із невідомим форматом пікселя, а `DISPON` наприкінці ввімкне показ казна-чого. Краще чесно зупинитися й сказати «старт не вдався», ніж лишити екран у напівнастроєному стані, де дефект плаває й ловиться годинами.

Тепер — **безпечне відновлення**. Зупинитися мало; треба дати викличному коду спосіб спробувати ще раз із чистого аркуша. Природний хід — кілька спроб повного старту з апаратним скиданням між ними: збій шини часто разовий (наводка, недосип живлення на старті), і другий захід нерідко вдається.

```c
// Спробувати оживити панель до `tries` разів. Кожна спроба — повне скидання + таблиця.
disp_status_t st7789_start_safe(int tries) {
    for (int t = 0; t < tries; t++) {
        hw_reset();                                   // чистий аркуш щоразу
        disp_status_t st = run_init_table_checked(
            st7789_table,
            sizeof(st7789_table) / sizeof(st7789_table[0]));
        if (st == DISP_OK) {
            return DISP_OK;                           // ожила — виходимо
        }
        // не вдалося — даємо залізу видихнути й заходимо знову
        delay_ms(50);
    }
    return DISP_ERR_BUS;                              // усі спроби марні — хай вирішує вище
}
```

Ключ безпечного відновлення — **апаратне скидання перед кожною спробою**. Не можна просто «продовжити з місця збою»: контролер міг лишитися в півстані, з частково записаними регістрами, і повторити пів-таблиці означало б накласти нове на сміття. Скидання повертає кремній у відомий стартовий стан, і кожна спроба починає з нуля — це і є «безпечно». Якщо ж і після кількох заходів панель мовчить, рушій чесно повертає `DISP_ERR_BUS`, і вже застосунок вирішує, що робити: блимнути світлодіодом діагностики, записати в лог, спробувати пізніше. Рушій свою справу зробив — він не вдає, ніби все добре, коли все погано.

> 🔧 **Навіщо це.** Перевірка статусу перетворює «екран чомусь не працює» на «старт повернув `DISP_ERR_BUS` на кроці N». Це різниця між зрозумілою діагностикою й сліпим перепаюванням. А спроби з повним скиданням рятують від разових збоїв живлення на старті — поширеної біди, коли пристрій вмикається й шина ще «брудна»; без повтору ви списали б панель на брак, маючи цілу.

## Крок 5. Одна машина — інша панель: ILI9341 лише таблицею

Тепер — заради чого все будувалося. Підключімо геть інший контролер, ILI9341, **не торкаючись жодного рядка інтерпретатора**. Усе, що для цього треба, — нова таблиця-даних. ILI9341 близький родич ST7789, але має свої відмінності, і вони лягають **виключно в таблицю**: інше значення `MADCTL`, відсутність інверсії (на відміну від ST7789 він зазвичай працює **без** `INVON`), і кілька векторів живлення та гами, специфічних саме для нього.

```c
// Аргументи ILI9341 — свої масиви у флеші.
static const uint8_t ILI_PWCTRL1[] = { 0x23 };               // керування живленням 1
static const uint8_t ILI_PWCTRL2[] = { 0x10 };               // керування живленням 2
static const uint8_t ILI_VMCTRL1[] = { 0x3E, 0x28 };         // VCOM 1 (два байти!)
static const uint8_t ILI_COLMOD[]  = { 0x55 };               // RGB565, як і в ST7789
static const uint8_t ILI_MADCTL[]  = { 0x48 };               // інша орієнтація + BGR

// Таблиця для ILI9341 — той самий формат, інші байти.
static const init_cmd_t ili9341_table[] = {
    { 0x01, 0, NULL,        150 },   // SWRESET
    { 0x11, 0, NULL,        120 },   // SLPOUT — та сама важлива пауза
    { 0xC0, 1, ILI_PWCTRL1,   0 },   // PWCTRL1   — живлення (нема в ST7789)
    { 0xC1, 1, ILI_PWCTRL2,   0 },   // PWCTRL2
    { 0xC5, 2, ILI_VMCTRL1,   0 },   // VMCTRL1   — два аргументи
    { 0x3A, 1, ILI_COLMOD,   10 },   // COLMOD    — формат пікселя
    { 0x36, 1, ILI_MADCTL,    0 },   // MADCTL    — орієнтація (своя для ILI)
    { 0x29, 0, NULL,         20 },   // DISPON    — БЕЗ INVON: ILI його не вмикає
};
```

Тепер уся різниця між двома панелями зведена до **вибору таблиці** — одного рядка:

```c
disp_status_t panel_start(const init_cmd_t *tab, uint32_t n, int tries) {
    for (int t = 0; t < tries; t++) {
        hw_reset();
        if (run_init_table_checked(tab, n) == DISP_OK) {
            return DISP_OK;
        }
        delay_ms(50);
    }
    return DISP_ERR_BUS;
}

// ST7789:
panel_start(st7789_table, sizeof(st7789_table)/sizeof(st7789_table[0]), 3);
// ILI9341 — той самий виклик, інша таблиця:
panel_start(ili9341_table, sizeof(ili9341_table)/sizeof(ili9341_table[0]), 3);
```

![Дві таблиці-даних (ST7789 та ILI9341) ведуть в одну функцію-інтерпретатор, що оживляє обидві панелі; код машини не змінюється](/root/course/embedded/gram-init-sequence/img/one-machine.svg)
*Сенс рушія в одному кадрі. Дві геть різні панелі описані двома таблицями байтів, але виконує їх та сама функція `run_init_table()` — вона тримає D/C і CS, відпрацьовує паузи й ловить збій шини незалежно від того, чий старт прокручує. Нова панель не додає коду — лише масив. Це і є переносність: специфіка живе в даних, машина лишається однією.*

Придивіться до того, що сталося. Дві панелі, чиї послідовності різняться й командами (`PWCTRL1`/`PWCTRL2`/`VMCTRL1` є в ILI9341 і нема в ST7789), і значеннями (`MADCTL` `0x00` проти `0x48`), і навіть наявністю кроку (`INVON` є в ST7789, нема в ILI9341), — оживають **тим самим кодом**. Жодного `if (panel == ILI9341)`, жодної другої копії інтерпретатора. Уся відмінність, до останнього байта, виражена **даними** в таблицях, а машина, що їх виконує, лишилася однією. Саме це й означає «переносний рушій»: додаєте панель — пишете таблицю, а не драйвер. І зверніть увагу на `VMCTRL1` з **двома** аргументами `{ 0x3E, 0x28 }` — формат запису це проковтнув без жодної зміни, бо `n_args` і вказівник `args` від початку готові до будь-якої кількості; за хвилину побачимо, чому саме порядок цих двох байтів — пастка.

> 🔧 **Навіщо це.** Це окупається не на першій панелі, а на третій-четвертій. Коли в портфоліо назбирується ST7789, ILI9341, ST7735, GC9A01, кожна зі своєю обв'язкою, табличний рушій тримає весь цей зоопарк на **одному** інтерпретаторі: правка логіки (додали ретраї, змінили обробку пауз) лягає одразу на всі панелі, а не копіюється в кожен драйвер. Це різниця між «підтримую один файл» і «синхронізую п'ять майже однакових».

## Складність і пастки

Рушій вийшов невеликий, але кілька місць у ньому — це класичні граблі, на які наступають усі, хто пише драйвер дисплея вперше. Розберімо їх із механізмом, бо саме розуміння *чому* рятує від багатогодинного полювання на привид.

**Блокувальний `delay` — лише на старті, ніде більше.** Наш інтерпретатор паузить головний цикл намертво: `delay_ms(120)` зупиняє весь мікроконтролер на 120 мілісекунд. Тут це нормально — ініціалізація йде **один раз**, при старті, коли робити все одно ще нічого, екран темний і жоден інший процес не страждає. Але спокуса перенести цей самий блокувальний стиль у **робочий** код — фатальна. Якщо ви присипляєте/будите дисплей на льоту під час роботи (а саме це робить [керування життєвим циклом дисплея](root:embedded/display-lifecycle)) тим самим `delay_ms(120)`, ви на ці 120 мс глушите все: не читаються давачі, не крутиться керування, завмирає зв'язок. Правило різке: блокувальна пауза дозволена **тільки** в ініціалізації; усе, що відбувається під час роботи, мусить чекати неблокувально — через таймер чи скінченний автомат, не зупиняючи цикл. Init — єдиний виняток, і саме тому ми звели всі паузи в таблицю старту, а не розсіяли по коду.

**Порядок байтів аргументу: старший чи молодший перший.** Гляньте на `VMCTRL1` з двома аргументами `{ 0x3E, 0x28 }`. Контролер чекає їх у **строго визначеному** порядку — який саме, диктує його datasheet, і це майже завжди **старший байт перший** (big-endian), бо так історично шлють параметри більшість дисплейних контролерів. Переплутаєте порядок — пошлете `{ 0x28, 0x3E }` — і регістр отримає геть інше число: замість потрібного рівня VCOM матриця дістане якесь стороннє значення, екран зблідне, потемніє або піде смугами. Та сама пастка чигає на двобайтові координати в `CASET`/`RASET` (адреси стовпців і рядків): там байти теж ідуть старший-перший, і переставлені місцями дадуть зсунуте чи обрізане зображення. Підступність у тому, що компілятор тут **нічим не допоможе** — для нього `{ 0x3E, 0x28 }` і `{ 0x28, 0x3E }` однаково законні масиви байтів; помилку видно лише на склі. Тому єдиний захист — звіряти порядок із datasheet **під час** набивання таблиці, а не вгадувати; і пам'ятати, що це порядок **аргументів** контролера, окремий від того, у якому порядку ваша платформа кладе байти в пам'ять.

**RST не розведено — апаратне скидання в порожнечу.** Ми вже торкнулися цього, але повторити варто, бо це чи не найчастіша причина «на одній платі працює, на іншій ні». На дрібних модулях ніжку RST часто не виводять окремо, а просто притягують резистором до живлення — і тоді ваш `hw_reset()` сумлінно смикає **неприєднаний** контакт мікроконтролера, нічого не скидаючи в самій панелі. Якщо ви покладалися **лише** на апаратне скидання, контролер так і лишиться в тому стані, в якому прокинувся, і таблиця ляже на ненульований кремній — звідси плаваючі дефекти старту. Захист — той самий, що ми вже вбудували: тримати в таблиці `SWRESET` (`0x01`) **завжди**, навіть коли ніжка RST начебто є. Тоді на платі з розведеним RST спрацює апаратне скидання, на платі без нього — програмне з таблиці, і драйвер переживе обидві без жодної правки коду. Зворотна осторога: не плутайте «ніжка RST» із загальним reset мікроконтролера — це різні лінії, і смикати треба саме reset **дисплея**, а не свій власний.

**Запис із аргументами, але `args == NULL`.** Дрібна, але болюча описка: поставили `n_args = 1`, а вказівник `args` забули заповнити (лишили `NULL` чи сміття). Інтерпретатор слухняно покличе `send_data(NULL, 1)` — і прочитає байт за нульовою адресою, що на мікроконтролері без захисту пам'яті або дасть випадкове значення, або впаде. Тому в зрілому рушії варто додати дешеву перевірку узгодженості перед прокруткою: якщо `n_args > 0`, то `args` мусить бути не `NULL`. Ось її кістяк, що повертає вже знайомий код помилки:

```c
// Перевірити таблицю на узгодженість ПЕРЕД прокруткою. 0 — все добре.
disp_status_t validate_table(const init_cmd_t *tab, uint32_t n) {
    for (uint32_t i = 0; i < n; i++) {
        if (tab[i].n_args > 0 && tab[i].args == NULL) {
            return DISP_ERR_ARGS;     // обіцяв аргументи, а вказівника нема
        }
    }
    return DISP_OK;
}
```

Така перевірка коштує копійки (один прохід таблиці на старті), а ловить цілий клас описок ще до того, як вони перетворяться на загадковий збій під час прокрутки. Це загальний принцип табличних рушіїв: **дані теж бувають криві**, і дешева звірка таблиці на вході надійніша за відлагодження наслідків кривих даних потім.

Підсумуймо нитку рушія. Ми помітили, що всі кроки init-послідовності мають однакову форму — команда, аргументи, пауза, — і виклали цю форму структурою, а саму послідовність таблицею у флеші. Один невеликий інтерпретатор прокручує таблицю, тримаючи за нас D/C і CS у примітивах, відпрацьовуючи паузи й перевіряючи кожен байт на збій шини, а на невдачі чесно зупиняючись і даючи відновитися повним скиданням. Ніжку RST ми лишили окремим точним ритуалом перед таблицею, бо вона про залізо плати, а `SWRESET` тримаємо в таблиці завжди — щоб драйвер пережив і плату без розведеного reset. І найголовніше: коли всю специфіку панелі винесено в дані, та сама машина оживляє і ST7789, і ILI9341 лише іншою таблицею — нова панель коштує масиву байтів, а не нового драйвера. Це і є та форма, в якій варто тримати старт дисплея в будь-якому серйозному проєкті: специфіка — даними, логіка — однією переносною машиною.
