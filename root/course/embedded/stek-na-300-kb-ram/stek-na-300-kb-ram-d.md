Коли мікроконтролер класу STM32F407 (192 КБ SRAM), STM32F746 (320 КБ SRAM) або ESP32 (320 КБ доступної внутрішньої SRAM) підключається до локальної мережі через Ethernet або Wi-Fi, розробник стикається з фундаментальним обмеженням архітектури. Універсальна операційна система на кшталт Linux виділяє під кожен відкритий сокет системні буфери прийому й передачі розміром від 128 КБ до кількох мегабайтів, а заголовок одного пакета `sk_buff` займає понад 200 байтів службових метаданих. У вбудованих системах мережевий стек розглядається не як абстрактний шар сокетів, а як жорстко обмежений бюджет пам'яті. Легковажні реалізації — зокрема стек **lwIP** (*Lightweight IP*) та підсистема **Zephyr Native IP** — вирішують цю суперечність через нульове копіювання між рівнями, статичні пули блоків фіксованого розміру та спеціалізовані структури пакетних буферів (`pbuf`). Щоб побудувати надійний мережевий вузол, інженер мусить точно розрахувати, скільки паралельних TCP-з'єднань фізично вміщує наявний обсяг RAM, як зв'язати апаратні дескриптори Ethernet DMA без дублювання даних і що захищає систему від фатального вичерпання пулів під мережевим навантаженням.

## 1. Проблема TCP/IP на мікроконтролерах: чому Linux-стек не влазить у 300 КБ

Класичний мережевий стек операційних систем загального призначення проектувався для серверів та робочих станцій, де оперативна пам'ять вимірюється гігабайтами, а ядро має апаратний блок керування пам'яттю (MMU) з віртуальною адресацією та підкачуванням сторінок.

У моделі Linux кожен мережевий кадр проходить тривалий шлях крізь шари ядра:
1. Драйвер мережевої карти виділяє структуру `sk_buff`, що містить десятки вказівників, лічильників і прапорців (розмір самого дескриптора перевищує 220 байтів без урахування даних).
2. Заголовки кожного рівня (Ethernet, IP, TCP) обробляються окремими модулями підсистеми ядра з динамічним виділенням додаткових структур.
3. Коли прикладний процес викликає системний виклик `recv()`, ядро копіює корисне навантаження з адресного простору ядра в буфер користувача в user-space через контекстне перемикання CPU.
4. Під кожен TCP-сокет виділяється пара черг `sk_rcvbuf` та `sk_sndbuf`, типовий розмір яких за замовчуванням становить від 128 КБ до 4 МБ для забезпечення високого значення BDP (*Bandwidth-Delay Product*).

Якщо на мікроконтролері з 300 КБ RAM половина пам'яті (150 КБ) зайнята стеками задач операційної системи реального часу (FreeRTOS, Zephyr), змінними `.bss` та буферами дисплея чи зовнішніх інтерфейсів, під усю мережу залишається близько 120–150 КБ. Один класичний Linux-сокет із двома буферами по 128 КБ миттєво викликає переповнення пам'яті.

Рішення, закладене Адамом Данкельсом під час створення lwIP, базується на трьох архітектурних принципах:
* **Усунення копіювання між рівнями (Zero-Copy inside Stack):** Пакет, прийнятий апаратним драйвером, залишається в тому самому буфері пам'яті під час проходження крізь IP, ICMP, UDP або TCP.
* **Маніпуляція заголовками через зсув вказівника:** Замість копіювання корисних даних рівні протоколів просто пересувають вказівник `payload` вперед або назад.
* **Статичні фіксовані пули (`memp`):** Усі внутрішні структури (керуючі блоки TCP TCB, черги сегментів, таймери) мають фіксований розмір і виділяються за константний час O(1) без використання фрагментованої системної купи.

## 2. Пам'ять та буфери pbuf у lwIP: ланцюжки без зайвого копіювання

Головною одиницею збереження та передачі даних у lwIP є пакетний буфер `struct pbuf`. Він замінює важкі структури сокетів і надає механізм безпечної роботи як з динамічними даними в RAM, так і зі статичними константами у Flash-пам'яті чи апаратними буферами DMA.

:::tabs

@tab C (Анатомія структури pbuf)
```c
struct pbuf {
    struct pbuf *next;     /* Вказівник на наступний буфер у зв'язному списку */
    void *payload;         /* Вказівник на початок корисних даних у цьому буфері */
    u16_t tot_len;         /* Сумарна довжина даних у цьому буфері та всіх наступних */
    u16_t len;             /* Довжина даних безпосередньо в цьому буфері */
    u8_t  type_internal;   /* Тип буфера: PBUF_RAM, PBUF_POOL, PBUF_ROM, PBUF_REF */
    u8_t  flags;           /* Прапорці стану буфера */
    u16_t ref;             /* Лічильник посилань для безпечного вивільнення */
};
```

@tab C++ (Обгортка PbufView)
```cpp
#include <span>
#include <cstdint>

namespace embedded::net {

struct PbufView {
    struct pbuf* raw{nullptr};

    [[nodiscard]] std::span<const uint8_t> payload() const noexcept {
        if (raw == nullptr || raw->payload == nullptr) {
            return {};
        }
        return {static_cast<const uint8_t*>(raw->payload), raw->len};
    }

    [[nodiscard]] uint16_t totalLength() const noexcept {
        return raw != nullptr ? raw->tot_len : 0;
    }

    [[nodiscard]] bool isChained() const noexcept {
        return raw != nullptr && raw->next != nullptr;
    }
};

} // namespace embedded::net
```

### Чотири типи буферів `pbuf`

У lwIP передбачено 4 типи буферів, кожен з яких оптимізований під конкретну фазу життя пакета:

1. **`PBUF_RAM` (Динамічна купа):**
   Заголовок `struct pbuf` і область корисного навантаження розташовані в одному безперервному блоці пам'яті, що виділяється з внутрішньої купи стека (`mem_malloc`). Використовується головним чином для вихідних пакетів, коли довжина повідомлення заздалегідь відома, а перед даними потрібно динамічно сформувати заголовки TCP/IP.

2. **`PBUF_POOL` (Фіксований пул для прийому):**
   Виділяється за час O(1) з попередньо скомпільованого масиву `memp`. Кожен блок має фіксований розмір `PBUF_POOL_BUFSIZE` (типово 512 або 1536 байтів). Якщо вхідний Ethernet-кадр розміром 1514 байтів надходить у пул з блоками по 512 байтів, стек автоматично зв'язує три буфери в ланцюжок (`pbuf_chain`). Поле `p->next` вказує на наступний фрагмент, а поле `p->tot_len` у першому буфері тримає загальний розмір кадру (1514 Б).

3. **`PBUF_ROM` (Прямий вказівник на Flash):**
   Заголовок `struct pbuf` виділяється з пулу `memp`, але вказівник `payload` направляється безпосередньо в постійну пам'ять (Flash/ROM). Це дозволяє веб-серверу або сервісу оновлення віддавати статичні HTML-сторінки, файли JavaScript, стилі CSS або криптографічні сертифікати без копіювання жодного байта корисного навантаження в оперативну пам'ять!

4. **`PBUF_REF` (Вказівник на статичну RAM):**
   Аналогічний до `PBUF_ROM`, але вказівник `payload` дивиться на буфер у системній оперативній пам'яті, яким володіє прикладний код. Додаток гарантує, що пам'ять не змінюватиметься, поки lwIP не надішле сегмент і не отримає підтвердження ACK.

### Маніпуляція заголовками: функція `pbuf_header()`

Коли мережевий кадр рухається вгору по стеку, кожен рівень протоколу повинен видалити свій заголовок і передати залишок наступному шару:
* Драйвер Ethernet приймає 1514 байтів і передає буфер у функцію `ip_input()`.
* IP-рівень перевіряє адресу та викликає `pbuf_header(p, -14)`: вказівник `p->payload` зміщується вперед на 14 байтів (розмір заголовка Ethernet), а поле `p->len` зменшується на 14.
* TCP-рівень перевіряє порт і викликає `pbuf_header(p, -20)`: вказівник зсувається ще на 20 байтів.
* Прикладний код отримує вказівник `payload`, що дивиться безпосередньо на корисні байти повідомлення.

При передачі пакета вниз процес відбувається у зворотному порядку: буфер виділяється з запасом під заголовки (`PBUF_RAM`), і виклики `pbuf_header(p, +20)` та `pbuf_header(p, +14)` відкривають місце під запис заголовків TCP та Ethernet перед даними. Увесь конвеєр працює з нульовим копіюванням.

Детальний перелік усіх макросів конфігурації пулів, розмірів буферів та їхній вплив на загальну пам'ять стека наведено у [довіднику конфігурації пам'яті та буферів lwIP](root:embedded/stek-na-300-kb-ram/api-lwip-config.md).

## 3. Тріада API: Raw Callback, Netconn та BSD Sockets

Мережевий стек lwIP надає розробнику три різні рівні інтерфейсу програмування (API). Вибір між ними є прямим компромісом між витратами оперативної пам'яті, швидкодією та простотою написання коду.

![Порівняння трьох API стека lwIP](/root/course/embedded/stek-na-300-kb-ram/img/api-triad-comparison.svg)
*Архітектурні рівні API в lwIP: однопотоковий Raw Callback, багатопотоковий послідовний Netconn та стандартний BSD Sockets POSIX*

### 1. Raw Callback API (Подієва модель)
Стек і прикладний код виконуються в одному спільному контексті виконання (або в головному циклі `while(1)` bare-metal системи, або в одній задачі RTOS). Прикладний код реєструє функції зворотного виклику:
* `tcp_recv()`: викликається стеком при надходженні нових даних у буфері `pbuf`.
* `tcp_sent()`: сигналізує, що віддалений вузол підтвердив прийом переданих байтів.
* `tcp_accept()`: повідомляє про нове вхідне з'єднання на прослуховуваному порту.
* `tcp_err()`: сповіщає про фатальну помилку або розрив з'єднання через RST.

*Переваги:* Нульові витрати пам'яті на додаткові стеки RTOS-задач; відсутність черг повідомлень та семафорів; найвища пропускна здатність на такт CPU.
*Ціна:* Асинхронний код на машинах станів (FSM); категорична заборона виклику блокуючих функцій (`delay`, очікування Flash/EEPROM) всередині зворотних викликів, оскільки це зупиняє весь мережевий стек.

### 2. Netconn API (Послідовна блокуюча модель)
Стек lwIP працює в окремій задачі RTOS (`tcpip_thread`). Прикладний код виконується у власних незалежних задачах. Взаємодія між задачами та стеком відбувається через поштові скриньки `sys_mbox` (черги FreeRTOS) та бінарні семафори.

Виклики функцій стають блокуючими: `netconn_accept()` присипляє задачу додатку, доки не надійде клієнтський SYN, а `netconn_recv()` чекає на появу пакета в черзі прийому.

*Переваги:* Простий, лінійний послідовний код.
*Ціна:* Пам'ять під стек задачі `tcpip_thread` (1.5–2 КБ), стеки клієнтських задач (1.5–3 КБ на кожен потік), структури керування `struct netconn` та системні черги IPC.

### 3. BSD Sockets API (POSIX-сумісний рівень)
Шар абстракції над Netconn API, що реалізує стандартні функції `socket()`, `bind()`, `listen()`, `accept()`, `send()`, `recv()`, `select()`, `poll()`.

*Переваги:* Максимальна портативність коду; можливість перенесення існуючих мережевих бібліотек (MQTT-клієнти, HTTP-парсери, mbedTLS) з Linux на мікроконтролер без змін у бізнес-логіці.
*Ціна:* Найвищі накладні витрати пам'яті. Виклик `recv()` вимагає копіювання даних з ланцюжка `pbuf` у плоский масив `char*`, наданий користувачем. Додатково створюється масив дескрипторів `sockets[]` та структури блокувань під механізми вибору `select()`.

### Порівняльна таблиця характеристик API

| Критерій | Raw Callback API | Netconn API | BSD Sockets API |
| :--- | :--- | :--- | :--- |
| **Потреба в RTOS** | Ні (Bare-Metal / RTOS) | Обов'язково (FreeRTOS / Zephyr) | Обов'язково |
| **Додаткові задачі RTOS** | 0 | 1 (`tcpip_thread`) + клієнти | 1 (`tcpip_thread`) + клієнти |
| **Накладна RAM на 1 сокет** | ≈ 160 Б (`struct tcp_pcb`) | ≈ 300 Б + стек задачі | ≈ 450 Б + стек задачі |
| **Копіювання даних (RX)** | 0 (пряма робота з `pbuf`) | 0 (через `netbuf`) | 1 копіювання (`pbuf` → масив) |
| **Складність коду** | Висока (State Machine) | Низька (Блокуючі виклики) | Низька (POSIX стандарт) |

Нижче наведено практичний приклад створення простого TCP-ехо сервера на Raw Callback API мовами C та ідіоматичному C++.

:::tabs

@tab C (Raw Callback API)
```c
#include "lwip/opt.h"
#include "lwip/tcp.h"
#include <string.h>

static err_t echo_recv_callback(void *arg, struct tcp_pcb *tpcb, struct pbuf *p, err_t err) {
    if (p == NULL) {
        /* Віддалений клієнт закрив з'єднання (FIN) */
        tcp_close(tpcb);
        return ERR_OK;
    }

    if (err != ERR_OK) {
        pbuf_free(p);
        return err;
    }

    /* Підтверджуємо отримання даних стеку для розширення вікна TCP_WND */
    tcp_recved(tpcb, p->tot_len);

    /* Відправляємо отримані дані назад (Ехо) */
    tcp_write(tpcb, p->payload, p->len, TCP_WRITE_FLAG_COPY);
    tcp_output(tpcb);

    pbuf_free(p);
    return ERR_OK;
}

static err_t echo_accept_callback(void *arg, struct tcp_pcb *newpcb, err_t err) {
    if (err != ERR_OK || newpcb == NULL) {
        return ERR_VAL;
    }

    /* Призначаємо зворотний виклик для обробки вхідних даних */
    tcp_recv(newpcb, echo_recv_callback);
    return ERR_OK;
}

void echo_server_init(void) {
    struct tcp_pcb *server_pcb = tcp_new();
    if (server_pcb != NULL) {
        if (tcp_bind(server_pcb, IP_ADDR_ANY, 7) == ERR_OK) {
            server_pcb = tcp_listen(server_pcb);
            tcp_accept(server_pcb, echo_accept_callback);
        } else {
            memp_free(MEMP_TCP_PCB, server_pcb);
        }
    }
}
```

@tab C++ (Ідіоматичний Raw Server)
```cpp
#include <span>
#include <cstdint>
#include <concepts>
#include <memory>

extern "C" {
#include "lwip/opt.h"
#include "lwip/tcp.h"
}

namespace embedded::net {

class TcpEchoServer {
public:
    TcpEchoServer() noexcept = default;
    ~TcpEchoServer() noexcept { stop(); }

    TcpEchoServer(const TcpEchoServer&) = delete;
    TcpEchoServer& operator=(const TcpEchoServer&) = delete;

    [[nodiscard]] bool start(uint16_t port = 7) noexcept {
        struct tcp_pcb* raw_pcb = tcp_new();
        if (raw_pcb == nullptr) {
            return false;
        }

        if (tcp_bind(raw_pcb, IP_ADDR_ANY, port) != ERR_OK) {
            memp_free(MEMP_TCP_PCB, raw_pcb);
            return false;
        }

        listenPcb_ = tcp_listen(raw_pcb);
        tcp_arg(listenPcb_, this);
        tcp_accept(listenPcb_, &TcpEchoServer::onAcceptThunk);
        return true;
    }

    void stop() noexcept {
        if (listenPcb_ != nullptr) {
            tcp_close(listenPcb_);
            listenPcb_ = nullptr;
        }
    }

private:
    static err_t onAcceptThunk(void* arg, struct tcp_pcb* newpcb, err_t err) noexcept {
        if (err != ERR_OK || newpcb == nullptr) {
            return ERR_VAL;
        }
        auto* self = static_cast<TcpEchoServer*>(arg);
        return self->onAccept(newpcb);
    }

    err_t onAccept(struct tcp_pcb* newpcb) noexcept {
        tcp_arg(newpcb, this);
        tcp_recv(newpcb, &TcpEchoServer::onRecvThunk);
        return ERR_OK;
    }

    static err_t onRecvThunk(void* arg, struct tcp_pcb* tpcb, struct pbuf* p, err_t err) noexcept {
        auto* self = static_cast<TcpEchoServer*>(arg);
        return self->onRecv(tpcb, p, err);
    }

    err_t onRecv(struct tcp_pcb* tpcb, struct pbuf* p, err_t err) noexcept {
        if (p == nullptr) {
            tcp_close(tpcb);
            return ERR_OK;
        }

        if (err != ERR_OK) {
            pbuf_free(p);
            return err;
        }

        tcp_recved(tpcb, p->tot_len);

        std::span<const uint8_t> payload{
            static_cast<const uint8_t*>(p->payload),
            p->len
        };

        tcp_write(tpcb, payload.data(), static_cast<u16_t>(payload.size()), TCP_WRITE_FLAG_COPY);
        tcp_output(tpcb);

        pbuf_free(p);
        return ERR_OK;
    }

    struct tcp_pcb* listenPcb_{nullptr};
};

} // namespace embedded::net
```

## 4. Розрахунок пам'яті на TCP-сокет: буфери вікон та ліміти системи

Щоб визначити, скільки паралельних сокетів може підтримувати система на 300 КБ SRAM, необхідно детально підсумувати всі накладні витрати на одне з'єднання.

Пам'ять одного TCP-з'єднання складається з таких компонентів:
1. **Блок керування протоколу (`struct tcp_pcb` / TCB):**
   Займає **160–196 байтів** у пулі `MEMP_TCP_PCB`. Зберігає стан з'єднання, IP-адреси, порти, поточні номери послідовностей `snd_nxt`, `rcv_nxt`, виміри RTT та змінні таймерів повторної передачі.
2. **Вікно прийому (`TCP_WND`):**
   Визначає обсяг байтів, які віддалений клієнт може надіслати без підтвердження. Якщо `TCP_WND` налаштовано як 4 × MSS (тобто 4 × 1460 = 5840 байтів), під час інтенсивного прийому це вікно заповнюється буферами з пулу `PBUF_POOL`. За загального пулу в 16 буферів одне з'єднання може тимчасово захопити до 4–6 буферів (≈ 6–9 КБ).
3. **Буфер передачі (`TCP_SND_BUF`):**
   Обсяг черги вихідних сегментів, що очікують підтвердження ACK. За налаштування `TCP_SND_BUF = 4380` (3 × MSS) дані виділяються з купи `MEM_SIZE` (до 4.5 КБ на активний сокет під час передачі).
4. **Черга сегментів передачі (`MEMP_NUM_TCP_SEG`):**
   Кожен фрагмент черги потребує структури `struct tcp_seg` (≈ 32 байти в пулі `MEMP_TCP_SEG`).
5. **Стек задачі RTOS (у разі використання Netconn/Sockets):**
   Якщо кожне з'єднання обслуговується окремим потоком FreeRTOS, кожна задача потребує від **1.5 до 3 КБ** пам'яті під власний стек викликів.

### Розрахунок бюджету пам'яті системи на 300 КБ SRAM

```
+-------------------------------------------------------------------------------+
|              Бюджет пам'яті для STM32F746 / ESP32 (300 КБ SRAM)               |
+-------------------------------------------------------------+-----------------+
| Компонент системи                                           | Виділена пам'ять|
+-------------------------------------------------------------+-----------------+
| Системне ядро, змінні .data/.bss, стеки системних задач RTOS| 120 КБ          |
| Дескриптори та апаратні буфери Ethernet MAC DMA             | 24 КБ           |
| Статичні пули lwIP (memp: PCB, сегменти, черги повідомлень) | 16 КБ           |
```

### Скільки сокетів витримує система?

Кількість доступних з'єднань залежить від архітектури обробки:

```
[Розрахунок кількості сокетів за трьома архітектурними моделями]

1. Модель «Один потік на один сокет» (BSD Sockets + RTOS):
   Витрати на сокет = PCB (160 Б) + Стек задачі (2048 Б) + Черги IPC (512 Б) ≈ 2.7 КБ
   Максимальна кількість одночасних з'єднань = 76 КБ / 2.7 КБ ≈ 20–25 сокетів
   (Практичний ліміт з урахуванням сплесків вікон — 8–12 активних сокетів).

2. Модель «Пул потоків + Worker Threads» (Netconn / Sockets з чергою задач):
   Витрати на сокет = PCB (160 Б) + структура netconn (128 Б) ≈ 300 Б
   Фіксований пул із 4 робочих задач = 4 * 2048 Б = 8 КБ
   Максимальна кількість підтримуваних з'єднань = (76 КБ - 8 КБ) / 300 Б ≈ 200 сокетів
   (Обмежено лише лімітом пулів MEMP_NUM_TCP_PCB та пам'яттю під буфери вікон).

3. Модель «Подієвий цикл» (Raw Callback API без блокувань):
   Витрати на сокет = лише struct tcp_pcb (160 Б)
   Максимальна кількість з'єднань = 76 КБ / 160 Б ≈ 400+ пасивних TCP-з'єднань.
```

## 5. Оптимізація Zero-Copy з апаратним Ethernet DMA

У стандартній реалізації драйверів Ethernet (наприклад, базових шаблонах STM32 HAL) передача даних здійснюється за схемою подвійного копіювання:

```
+-------------------------------------------------------------------------------+
|          Традиційна схема: подвійне копіювання даних (Double Copy)            |
|                                                                               |
|   +--------------+      +-------------------+      +----------------------+   |
|   | Кабель PHY   | ───► | Статичний буфер   | ───► | Пакетний буфер       |   |
|   | 100 Мбіт/с   |      | DMA MAC (SRAM)    |      | pbuf (lwIP Pool)     |   |
|   +--------------+      +-------------------+      +----------------------+   |
|                                  │                            │               |
|                                  └───── memcpy() #1 ──────────┘               |
|                                                                               |
|   +----------------------+      +-------------------+                         |
|   | Пакетний буфер       | ───► | Буфер додатку     |                         |
|   | pbuf (lwIP Pool)     |      | app_rx_buffer[]   |                         |
|   +----------------------+      +-------------------+                         |
|              │                            │                                   |
|              └───── memcpy() #2 ──────────┘                                   |
+-------------------------------------------------------------------------------+
```

За швидкості 100 Мбіт/с на процесорне ядро Cortex-M4 (168 МГц) лягає необхідність двічі скопіювати 12 мегабайтів даних за секунду, що забирає до 70% доступних обчислювальних циклів.

![Конвеєр Zero-Copy з апаратним контролером DMA](/root/course/embedded/stek-na-300-kb-ram/img/zerocopy-dma-pipeline.svg)
*Конвеєр нульового копіювання: дескриптори Ethernet DMA зв'язуються безпосередньо з вказівниками payload буферів PBUF_POOL*

### Принцип роботи Zero-Copy RX/TX

1. **Прийом кадру (Zero-Copy RX):**
   Під час ініціалізації драйвера вказівник адреси буфера кожного апаратного дескриптора DMA (`Buffer1Addr`) налаштовується безпосередньо на адресу `pbuf->payload` свіжого буфера, виділеного з пулу `PBUF_POOL`.
   Коли контролер DMA закінчує прийом кадру з лінії RMII, він скидає біт володіння `OWN` дескриптора та генерує переривання. Драйвер вилучає заповнений `pbuf` із дескриптора, передає його в lwIP викликом `netif->input(p, netif)`, а на місце вилученого буфера в дескриптор DMA негайно підставляє новий порожній `pbuf` з пулу `PBUF_POOL`. Жодного виклику `memcpy` не відбувається.

2. **Передача кадру (Zero-Copy TX):**
   При надсиланні пакета через `tcp_write()` з прапорцем `TCP_WRITE_FLAG_COPY = 0` (або для `PBUF_ROM`/`PBUF_REF`) адреса `pbuf->payload` записується прямо в дескриптор передачі DMA. Драйвер збільшує лічильник посилань `pbuf_ref(p)`, щоб попередити вивільнення пам'яті стеком, і передає керування контролеру DMA. Після фізичного завершення відправлення кадру в лінію драйвер викликає `pbuf_free(p)`.

Повну реалізацію низькорівневого драйвера Zero-Copy Ethernet з урахуванням інвалідації та очищення кеша даних (ARM Cortex-M7 D-Cache) наведено у [проєкті драйвера Ethernet MAC Zero-Copy](root:embedded/stek-na-300-kb-ram/proj-zerocopy-eth.md).

## 6. Захист від вичерпання пулів пам'яті та мережевих атак

В умовах обмеженої пам'яті мережевий стек вразливий до перевантажень та аномального трафіку. Якщо пул `PBUF_POOL` повністю вичерпано, система потрапляє у стан блокування (*Pool Starvation*): контролер DMA не може прийняти нові пакети, відкидаються пакети керування ACK/ARP, таймери TCP вичерпують ліміти, і всі активні сокети аварійно розриваються.

### Стратегії запобігання відмові під навантаженням

```
+-------------------------------------------------------------------------------+
|                 Рівні захисту пам'яті вбудованого TCP/IP                      |
|                                                                               |
|  1. Квотування PBUF_POOL  ──► Заборона одному сокету займати > 25% пулу       |
|  2. Динамічний TCP_WND    ──► Звуження вікна при падінні запасу RAM           |
|  3. SYN Backlog & Cookies ──► Захист від SYN-Flood атак без виділення PCB     |
|  4. Агресивні таймаути    ──► Примусове закриття «завислих» з'єднань (FIN)    |
+-------------------------------------------------------------------------------+
```

1. **Динамічне керування вікном прийому (`TCP_WND` Throttle):**
   Якщо кількість вільних буферів у `PBUF_POOL` опускається нижче безпечного порогу (наприклад, менше 4 буферів), прикладний код або стек тимчасово повідомляє віддаленому вузлу вікно `TCP_WND = 0` у наступному пакеті ACK. Віддалений передавач негайно припиняє передачу нових сегментів, дозволяючи мікроконтролеру спокійно вичитати накопичені дані з пам'яті.
2. **Захист від SYN-Flood (Ліміт черги прослуховування):**
   Макрос `TCP_LISTEN_BACKLOG` обмежує кількість напіввідкритих з'єднань у стані SYN_RECEIVED (типово не більше 2–4 на порт). При спробі атаки чергові пакети SYN відхиляються пакетом RST без виділення структур `struct tcp_pcb` у пам'яті.
3. **Контроль затримки ACK та таймери бездіяльності (TCP Keep-Alive):**
   Якщо віддалений клієнт припинив надсилати дані або розірвав зв'язок без відправлення FIN (обрив кабелю, аварія живлення), сокет без налаштованого Keep-Alive може залишатися у пам'яті мікроконтролера нескінченно. Активація `SO_KEEPALIVE` з таймаутом перевірки в 5–10 секунд гарантує своєчасне закриття завислих з'єднань і повернення їхніх керуючих блоків у пул `MEMP_TCP_PCB`.
