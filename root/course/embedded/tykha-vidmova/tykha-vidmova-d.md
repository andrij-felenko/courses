# Тиха відмова: пристрій, що звітує «все добре»

<preknowlist>
- [Перевірки живості й готовності](root:sf-distributed/health-checks) — чому пінг і статус HTTP 200 ловлять лише факт виконання коду в пам'яті, але сліпі до змістовної деградації джерела даних.
- [Калібрування АЦП](root:embedded/adc-reference-calibration) — опорна напруга, шуми квантування, електричні крайні точки шкали (rail-to-rail).
- [Зчитування сигналу](root:embedded/signal-acquisition) — дискретизація, природний шум сенсорного тракту й частота опитування.
- [Часові ряди](root:sf-data/chasovi-riady) — темп надходження відліків, віконна агрегація та дисперсія телеметрії.
</preknowlist>

Серверний монітор показує рівне зелене світло: промисловий контролер клімату щосекунди надсилає MQTT-пакет із телеметрією, брокер справно підтверджує отримання, мережевий сокет відкритий, а вбудований сторожовий таймер (*watchdog*) регулярно перезавантажується основним циклом прошивки. У графіку температури застигло ідеальне число: 21.4 °C. Проте через три години в приміщенні серверної спрацьовує пожежна сигналізація — реальна температура силових трансформаторів перетнула 95 °C, вентилятори охолодження не ввімкнулися, а система керування продовжувала вважати, що все гаразд. Пристрій не завис, зв'язок не зник, прошивка не впала в обробник апаратного виключення (*HardFault*). Відбулася **тиха відмова** (англ. *silent failure* або *silent data corruption*) — стан, за якого вся цифрова й мережева інфраструктура вузла функціонує бездоганно, але фізичний зміст переданих даних повністю втрачено.

![Анатомія тихої відмови: розрив між життям вузла та валідністю даних](/root/course/embedded/tykha-vidmova/img/silent-failure-anatomy.svg)
*Анатомія тихої відмови. Цифровий мікроконтролер, операційна система реального часу й радіомодуль зв'язку працюють у штатному режимі, малюючи на пульті диспетчера зелений статус, тоді як чутливий кристал давача застряг або деградував.*

У традиційній вбудованій розробці інженерів вчать боротися з гучними збоями: відсутністю живлення, переповненням буфера, дедлоками в [RTOS](root:sf-os/scheduler) або зависанням шини зв'язку. Проти них збудовано цілі арсенали апаратних і програмних засобів — від багаторівневих сторожових таймерів до механізмів підтвердження доставки TCP/QoS. Але тиха відмова проходить крізь усі ці фільтри. Вона підступна тим, що руйнує базову аксіому спостережності: «якщо пристрій на зв'язку й не повідомляє про помилку, отже, вимірювання вірне». Розберімо докладно, які фізичні та схемотехнічні процеси призводять до тихої брехні справної електроніки, якими алгоритмічними метриками її викрити на самому пристрої та як організувати перехресну верифікацію телеметрії в реальному часі.

## Причини тихих відмов: як залізо завмирає без помилок шини

Щоб розпізнати тиху відмову, треба простежити повний шлях перетворення сигналу — від фізичного явища через кристалічну ґратку сенсора, аналоговий підсилювач, [АЦП](root:embedded/adc-reference-calibration), внутрішній цифровий кінцевий автомат до вихідного буфера інтерфейсу. Збій може статися на будь-якому з цих кроків, причому попередні та наступні ланки навіть не дізнаються про аномалію.

### 1. Зависання внутрішнього ядра цифрового сенсора (Stuck Sensor Value)

Сучасний цифровий давач температури, тиску чи прискорення (з інтерфейсом I2C або SPI) — це не просто пасивна деталь, а повноцінна спеціалізована інтегральна мікросхема (ASIC, англ. *Application-Specific Integrated Circuit*). Усередині неї працюють два незалежні функціональні блоки:
- **Аналогово-цифрове вимірювальне ядро:** мікроелектромеханічний вузол (MEMS) або чутливий елемент, комутатор каналів, генератор опорної напруги та внутрішній секвенсор АЦП.
- **Цифровий інтерфейсний контролер шини:** модуль логіки, який декодує адресу I2C, приймає тактові імпульси SCL та віддає вміст внутрішніх регістрів на лінію SDA.

Якщо плата зазнає короткочасного просідання напруги живлення (*brownout*) нижче робочого порогу аналогової частини, але вище порогу утримання цифрової пам'яті, або якщо на корпус сенсора потрапляє електростатичний розряд (ESD), внутрішній секвенсор АЦП зависає чи скидається в неробочий стан. Проте інтерфейсна логіка I2C продовжує отримувати живлення.

Коли мікроконтролер надсилає запит на читання регістру результату, I2C-контролер сенсора справно видає біт підтвердження (ACK) і передає байти, які зберігаються у вихідному регістрі. Проблема в тому, що це значення **застигло в момент збою**. 

:::tabs
```c
/* Типова наївна перевірка в драйвері C */
uint8_t raw_buf[2];
if (i2c_read_registers(SENSOR_ADDR, REG_TEMP_OUT, raw_buf, 2) == I2C_OK) {
    /* Драйвер вважає, що все гаразд, бо шина повернула ACK */
    float temp = decode_temperature(raw_buf);
    send_telemetry(temp);
}
```
```cpp
// Типова наївна перевірка в об'єктно-орієнтованому драйвері C++
std::array<uint8_t, 2> raw_buf{};
if (i2c_bus.read_registers(sensor_addr, reg_temp_out, std::span{raw_buf}) == I2cStatus::Ok) {
    // Помилки шини нема, але байти можуть бути замороженими
    const float temp = decode_temperature(raw_buf);
    telemetry_publisher.publish(temp);
}
```
:::

З погляду мікроконтролера помилки немає: I2C-транзакція завершилася з кодом успіху, контрольна сума протоколу (якщо вона є на рівні I2C) сходиться, бо передано саме той байт, що лежав у регістрі. Але сенсор перетворився на цифровий пам'ятник — він вічно віддає одне й те саме число.

Особливо підступним є явище тиристорного замикання (CMOS Latch-up). Внаслідок електростатичного імпульсу на кристалі сенсора відмикається паразитна чотиришарова структура p-n-p-n між шинами живлення та землі. Чип починає споживати підвищений струм, його цифрова логіка блокується, але напруга на виходах утримується. Звичайний програмний перезапуск мікроконтролера (*software reset*) не скидає latch-up у периферійному сенсорі — для цього потрібне повне фізичне зняття напруги живлення.

### 2. Деградація чутливості, старіння та хімічне отруєння (Sensor Drift & Aging)

Фізичні властивості чутливих елементів не вічні. Під дією температури, вібрації, циклічних деформацій та хімічно агресивного середовища відбувається деградація первинного перетворювача:
- **Газові сенсори (MOX та електрохімія):** металооксидні напівпровідникові шари деградують через адсорбцію силіконових парів, сірки або сполук хлору. Це явище має назву *отруєння сенсора* (англ. *sensor poisoning*). Чутливий шар втрачає здатність вступати в окисно-відновні реакції, його опір стабілізується, і давач газу починає показувати нульову концентрацію навіть у перенасиченій метаном атмосфері.
- **П'єзорезистивні мембрани барометрів та тензодавачів:** механічна втома кремнію або клею викликає повільний зсув нульової точки (*zero-point drift*) та зміну масштабу шкали (*span drift*). Давач тиску повертає цифри, що змінюються разом із погодою, але його вимірювання зміщені на 20–50 гПа від істини.
- **Оптичні сенсори (NDIR, фотометрія, пиломіри):** запилення захисних лінз чи деградація випромінювального світлодіода спричиняє поступове падіння інтенсивності світлового потоку, яке мікроконтролер інтерпретує як «постійно високу концентрацію диму/пилу» або навпаки — зсуває динамічний діапазон у мертву зону.
- **Платинові термометри опору (Pt100/Pt1000):** при тривалій вібрації тонкий платиновий дріт зазнає мікродеформацій, що збільшує його опір і створює стабільне позитивне зміщення температури на +5…+15 °C.

При тихому дрейфі сенсор не зависає на одній константі — його покази коливаються, мають правдоподібний вигляд і не виходять за електричні межі АЦП, що робить їх виявлення складнішим за банальний збій шини.

### 3. Залипання дискретних входів (Stuck Dry Contacts)

Дискретні канали телеметрії (кінцеві вимикачі, поплавкові рівнеміри, геркони дверей, кнопки аварійного зупину) здаються найпростішими елементами системи. Проте вони також схильні до специфічних тихих відмов:
- **Мікрозварювання контактів геркона:** комутація навіть слабких індуктивних або ємнісних навантажень без захисного діода/демпфера викликає мікроіскріння. З часом контакти зварюються між собою. Вхід мікроконтролера фіксує постійний логічний нуль (або одиницю), ніби датчик ніколи не спрацьовує.
- **Витік та деградація опторозв'язок:** у важких промислових умовах світлодіод оптопари з часом втрачає коефіцієнт передачі струму (CTR, англ. *Current Transfer Ratio*). Вхідний польовий транзистор або тригер Шмітта перестає впевнено перемикатися, застрягаючи у стані, визначеному резистором внутрішньої підтяжки.
- **Окислення та потрапляння вологи на клемники:** утворення струмопровідного сольового містка між клемою входу та шиною живлення 24 В / 3.3 В створює постійний струм витоку, який пересилює опір підтяжки й утримує вхід у фіксованому стані незалежно від положення механічного перемикача.

### 4. Розсинхронізація годинника й спотворення часових міток (Clock Drift)

Окрема форма тихої відмови стосується просторово-часової прив'язки телеметрії. Якщо годинник реального часу (RTC) на борту пристрою дрейфує через температурну нестабільність кварцового резонатора (типовий кварц 32.768 кГц без термокомпенсації відхиляється на ±20 ppm, що дає понад 1 хвилину похибки на місяць) або після збою живлення скидається на епоху `1970-01-01 00:00:00`, пристрій продовжує генерувати валідні за структурою пакети.

Серверна база даних [часових рядів](root:sf-data/chasovi-riady), приймаючи пакети з некоректними мітками часу, може мовчки відкидати їх як «застарілі» або записувати в далеке минуле. Для оператора на моніторі поточний графік застигає, хоча сам вузол передає дані без жодного збою мережевого стека.

> 🔧 **Навіщо це.** Якщо система керування (наприклад, алгоритм терморегуляції чи автопілот) орієнтується виключно на код повернення функції читання сенсора `ret == OK`, вона принципово вразлива до катастрофічних наслідків. Справжній промисловий драйвер повинен перевіряти не «чи відповів інтерфейс», а «чи відповідає прийняте значення фізичним законам нашого світу».

## Метрики виявлення на пристрої: три рівні перевірки здоров'я сигналу

Для виявлення тихої відмови всередині мікроконтролера сигнал проходить крізь три послідовні математичні фільтри. Кожен фільтр перевіряє конкретну фізичну властивість вимірюваного процесу.

![Три рівні локальної перевірки здоров'я сенсорного сигналу](/root/course/embedded/tykha-vidmova/img/sensor-health-metrics.svg)
*Три рівні локальної перевірки здоров'я сигналу. Рівень 1 відсікає електричні та фізичні крайнощі; рівень 2 перевіряє обмеження швидкості наростання за інерцією процесу; рівень 3 аналізує спектр природного шуму, виявляючи мертві цифрові регістри.*

### Рівень 1. Валідація фізичних меж (Plausibility Checks)

Найперший бар'єр — перевірка того, чи значення взагалі можливе в контексті фізики процесу та схемотехніки підключення:

1. **Електричні крайні точки (*Rail-to-Rail Clipping*):**
   При аналоговому вимірюванні через АЦП значення, що впритул наближаються до `0 В` (код `0` для 12-бітного АЦП) або до `Vref` (код `4095`), майже завжди вказують на апаратну поломку:
   - Код `0` — обрив сигнального проводу (якщо вхід підтягнутий резистором *pull-down* до землі) або коротке замикання входу на GND.
   - Код `4095` — коротке замикання на шину живлення 3.3 В або обрив сенсора (при підтяжці *pull-up*).
   
   Правильно спроєктована вимірювальна схема масштабує робочий діапазон сенсора так, щоб він займав, наприклад, від 5 % до 95 % шкали АЦП (від 0.16 В до 3.14 В при опорі 3.3 В). Будь-яке попадання в діапазони 0–5 % або 95–100 % негайно маркується як апаратна відмова лінії зв'язку.

2. **Фізичні межі вимірюваного середовища:**
   - Відносна вологість повітря не може бути меншою за 0 % або більшою за 100 %.
   - Атмосферний тиск у житловій зоні не може впасти нижче 500 гПа (це тиск на вершині гори заввишки 5500 м) чи піднятися вище 1100 гПа.
   - Температура охолоджувальної рідини двигуна не може бути -50 °C у розігрітому стані.

### Рівень 2. Градієнтні ліміти (Rate-of-Change / dY/dt Limits)

Будь-який реальний фізичний об'єкт має інерцію — теплоємність, гідравлічний опір чи механічну масу. Температура 100-літрового бака з водою не може змінити свій стан на 20 °C за 100 мілісекунд, хоч би якої потужності був нагрівач: швидкість теплопередачі обмежена першим законом термодинаміки.

Градієнтний фільтр перевіряє миттєву швидкість зміни величини між двома послідовними відліками:

```
|y[k] − y[k-1]| / Δt ≤ MAX_SLEW_RATE
```

де `y[k]` — поточний відлік, `y[k-1]` — попередній відлік, `Δt` — проміжок часу між відліками в секундах, а `MAX_SLEW_RATE` — максимальна фізично можлива швидкість зміни для цієї системи.

Якщо давач температури раптово видає стрибок на +30 °C за один такт опитування (10 мс), це свідчить не про раптове потепління, а про:
- Проскакування імпульсної завади по шині живлення в момент увімкнення реле;
- Тріщину пайки на ніжці підтяжки лінії зв'язку;
- Помилку в декодуванні старшого байта числа (наприклад, зсув бітів при збої тактування SPI/I2C).

### Рівень 3. Дисперсія та моніторинг природного шуму (Zero-Variance Detection)

Це фундаментальний принцип сенсорної електроніки: **у живому фізичному світі ідеально нерухомих сигналів не існує**.

Коли аналогова величина перетворюється на цифровий код, на неї завжди накладаються кілька неминучих джерел шуму:
1. **Тепловий шум Джонсона-Найквіста** в резистивних елементах сенсора та вхідних ланцюгах підсилювача: `Vn = √(4 · k_B · T · R · Δf)`.
2. **Шум квантування АЦП**, дисперсія якого визначається кроком квантування молодшого значущого розряду (LSB, від англ. *Least Significant Bit*):
```
σ²_quant = LSB² / 12
```
3. **Мікротурбулентність та мікрофлуктуації середовища** (конвекційні потоки повітря біля термодатчика, механічні мікровібрації будівлі біля акселерометра).

Навіть якщо прилад стоїть у закритій камері з термостатом, молодші 1–2 біти чесного 12- чи 16-бітного АЦП постійно тремтять (*флікер-шум*).

Якщо ж обчислити вибіркову дисперсію сигналу на ковзному вікні з 50–100 відліків:
```
σ² = (1 / (N − 1)) · ∑ (y[i] − y_mean)²
```
і отримати **ідеальний нуль** (`σ² = 0.000000`), це неспростовний доказ того, що ми вимірюємо не фізичний світ. Це означає, що аналогове ядро відключилося, АЦП не перетворює сигнал, а мікроконтролер циклічно читає з пам'яті заморожене значення константи (*Stuck-at-Fault*).

Критерій виявлення завислого давача формулюється просто:
```
σ²(вікно) < σ²_min_noise
```
де `σ²_min_noise` вибирається як частка від теоретичного шуму квантування (наприклад, `0.25 · LSB² / 12`). Якщо протягом `N` циклів сигнал не зробив жодного найменшого коливання на рівні молодшого біта — сенсор вважається мертвим.

## Однопрохідний алгоритм Уелфорда: дисперсія в реальному часі без масивів

Обчислення дисперсії на вбудованих мікроконтролерах із малою пам'яттю RAM (наприклад, STM32C0 або ATmega328P) пов'язане з двома класичними пастками:
- Наївна двопрохідна формула вимагає збереження всього масиву з `N` відліків у пам'яті, щоб спочатку знайти середнє `mean`, а потім підсумувати квадрати різниць `(y[i] - mean)²`. Для вікна в 100 чисел типу `float` це 400 байтів цінної оперативної пам'яті на кожен сенсорний канал.
- Наївна однопрохідна формула через суму квадратів:
```
σ² = (∑ y[i]² − (∑ y[i])² / N) / (N − 1)
```
страждає від катастрофічного скасування значущих цифр (*catastrophic cancellation*) при вирахуванні двох близьких великих чисел у форматі з плаваючою комою IEEE 754, що призводить до втрати точності й навіть до отримання від'ємної дисперсії.

Стандартним рішенням для прошивок є **алгоритм Б. П. Уелфорда** (*B. P. Welford*, 1962). Він дозволяє оновлювати середнє значення та суму квадратів відхилень `M2` ітеративно, на кожному новому відліку `x_k`, зберігаючи лише три змінні: лічильник `k`, поточне середнє `mean_k` та акумулятор `M2_k`.

### Математичний висновок формул Уелфорда

Позначимо `k`-й відлік як `x_k`. Нехай `mean_k` — середнє перших `k` елементів:
```
mean_k = mean_{k-1} + (x_k − mean_{k-1}) / k
```
Акумулятор суми квадратів відхилень `M2_k = ∑ (x_i - mean_k)²` оновлюється за один крок:
```
M2_k = M2_{k-1} + (x_k − mean_{k-1}) · (x_k − mean_k)
```
Незсунена вибіркова дисперсія `s²` на будь-якому кроці `k ≥ 2` становить:
```
s² = M2_k / (k − 1)
```

Цей метод потребує лише `O(1)` пам'яті (12 байтів для `float`) і `O(1)` часу обчислення на кожен вимір, повністю захищаючи прошивку від переповнення розрядної сітки.

## Перехресна верифікація та надлишковість (Cross-Checking & Redundancy)

Окремо взятий сенсор, навіть із валідацією меж і шуму, може тихо дрейфувати, не порушуючи градієнтних лімітів. Єдиний спосіб викрити такий дрейф до настання аварії — **перехресна верифікація** (зіставлення з незалежними джерелами інформації).

![Перехресна верифікація та аналітична надлишковість проти тихого дрейфу](/root/course/embedded/tykha-vidmova/img/cross-checking-voting.svg)
*Перехресна верифікація та аналітична надлишковість. Зліва: апаратна надлишковість 2oo3 виявляє канал, що відхилився від кворуму. Справа: аналітична модель зіставляє струм і температуру середовища, виявляючи відпадання первинного датчика.*

### 1. Апаратна надлишковість і мажоритарний кворум 2oo3 (Two-Out-Of-Three)

У критичних системах (авіоніка, керування тяговими батареями електромобілів, системи пожежогасіння) встановлюють три однакові фізичні давачі (канали `S1`, `S2`, `S3`). Мажоритарний селектор (*voter*) порівнює їхні покази за попарною різницею:
```
|S_i − S_j| ≤ ALLOWED_SPREAD
```

Можливі стани кворуму:
1. **Повна згода:** `|S1 - S2| ≤ ε`, `|S2 - S3| ≤ ε`, `|S3 - S1| ≤ ε`. Вихідне значення — медіана або середнє арифметичне трьох показників. Стан системи: `OK`.
2. **Одинична деградація:** `S1` та `S2` близькі між собою, але `|S1 - S3| > ε` та `|S2 - S3| > ε`. Кворум ізолює канал `S3`, виставляючи прапорець апаратного збою конкретного сенсора, а керування продовжується на середньому значенні `(S1 + S2) / 2`.
3. **Втрата кворуму:** усі три канали показують значення, різниця між якими перевищує допустимий розкид. Система не може визначити істину голосуванням і зобов'язана перейти в аварійний безпечний стан (*Safe State* / *Failsafe*).

### 2. Аналітична надлишковість (Heterogeneous / Analytical Redundancy)

Встановлення трьох однакових давачів здорожчує виріб і збільшує габарити друкованої плати. Більш витончений інженерний підхід полягає у використанні **аналітичної надлишковості** — перевірці сигналу через непрямі фізичні взаємозв'язки між різнорідними датчиками.

Приклади аналітичних пар:
- **Струм заряду акумулятора ⇄ Температура осередків:**
  Якщо струмовий шунт фіксує швидкий заряд струмом 50 А, опір батареї `R_int` неминуче виділяє теплову потужність `P = I² · R_int`. Згідно з рівнянням теплового балансу:
  ```
  dT/dt = (P_heat − (T_cell − T_amb) / R_th) / C_th
  ```
  температура батареї `T_cell` **зобов'язана зростати**. Якщо датчик струму показує заряд 50 А протягом 10 хвилин, а NTC-терморезистор на акумуляторі показує стабільні 20.0 °C без жодного наростання — один із двох датчиків зазнав тихої відмови.
- **Оберти електродвигуна ⇄ Тиск у гідравлічній магістралі:**
  Якщо давач струму та тахометр підтверджують роботу насоса на номінальній швидкості 3000 об/хв, а мембранний давач тиску показує нуль — або в системі витік, або давач тиску відірвався від шини.
- **Барометричний висотомір ⇄ Вертикальна швидкість за акселерометром:**
  Швидкість зміни барометричного тиску `dP/dt` має збігатися з інтегралом вертикального прискорення за акселерометром. Будь-яка розбіжність сигналізує про забиття трубки статичного тиску.

### 3. Фільтрація Калмана та інноваційний аналіз (Residual / Innovation Monitoring)

У складних динамічних системах (наприклад, системах орієнтації БПЛА або роботів) фізична модель об'єкта та покази сенсорів об'єднуються фільтром Калмана. Фільтр на кожному кроці розраховує прогноз стану `x̂_{k|k-1}` та зіставляє його з фактичним вимірюванням `z_k`.

Різниця між вимірюванням і прогнозом називається **інновацією** або **нев'язкою** (*residual / innovation*):
```
ỹ_k = z_k − H · x̂_{k|k-1}
```
Якщо всі сенсори справні, послідовність `ỹ_k` є випадковим білим шумом із нульовим математичним сподіванням. Якщо ж сенсор починає повільно дрейфувати, інновація набуває постійного ненульового зміщення:
```
E[ỹ_k] ≠ 0
```
Моніторинг нормованого квадрата інновації (NIS, англ. *Normalized Innovation Squared*):
```
NIS = ỹ_kᵀ · S_k⁻¹ · ỹ_k
```
(де `S_k` — коваріаційна матриця інновації) дає змогу виявити відхилення сенсора від фізичної поведінки об'єкта задовго до того, як показники вийдуть за межі грубих статичних коридорів.

```c
#include <stdbool.h>

typedef enum {

    SENSOR_ERR_RANGE_LOW       = 0x01, /* Нижче фізичного мінімуму (обрив / 0 В) */

} sensor_guard_cfg_t;

/* Робочий контекст (стан) одного сенсорного каналу */
typedef struct {
    sensor_guard_cfg_t cfg;
    float prev_val;
    uint32_t prev_ts_ms;
    bool has_history;

    /* Стан накопичувача Уелфорда */
```

```cpp
#include <cstdint>
#include <cmath>
#include <optional>
#include <span>
#include <concepts>

enum class SensorError : uint8_t {
    Ok             = 0x00,
    RangeLow       = 0x01,
    RangeHigh      = 0x02,
    SlewRate       = 0x04,
    ZeroVariance   = 0x08,
    CrossCheck     = 0x10
};

[[nodiscard]] constexpr SensorError operator|(SensorError a, SensorError b) noexcept {
    return static_cast<SensorError>(static_cast<uint8_t>(a) | static_cast<uint8_t>(b));
}

[[nodiscard]] constexpr bool has_error(SensorError mask, SensorError err) noexcept {
    return (static_cast<uint8_t>(mask) & static_cast<uint8_t>(err)) != 0;
}

struct SensorGuardConfig {
    float min_valid;
    float max_valid;
    float max_gradient_per_s;
    float min_noise_variance;
    uint32_t variance_window;
};

class SensorGuard {
public:
    explicit constexpr SensorGuard(const SensorGuardConfig& cfg) noexcept
        : cfg_(cfg) {}

    SensorError process(float sample, uint32_t now_ms) noexcept;

    [[nodiscard]] float mean() const noexcept { return mean_; }
    [[nodiscard]] float variance() const noexcept;
    [[nodiscard]] SensorError status() const noexcept { return status_; }
    [[nodiscard]] bool is_valid() const noexcept { return status_ == SensorError::Ok; }

private:
    SensorGuardConfig cfg_;
    float prev_val_{0.0f};
    uint32_t prev_ts_ms_{0};
    bool has_history_{false};

    uint32_t count_{0};
    float mean_{0.0f};
    float m2_{0.0f};

    SensorError status_{SensorError::Ok};
};
```

### Реалізація алгоритму обробки відліку

На кожному кроці функція перевіряє фізичні межі, розраховує градієнт і оновлює статистику дисперсії в один прохід:

:::tabs
```c
void sensor_guard_init(sensor_guard_t *g, const sensor_guard_cfg_t *cfg) {
    if (!g || !cfg) return;
    g->cfg = *cfg;
    g->prev_val = 0.0f;
    g->prev_ts_ms = 0;
    g->has_history = false;
    g->count = 0;
    g->mean = 0.0f;
    g->m2 = 0.0f;
    g->status_flags = SENSOR_OK;
}

uint8_t sensor_guard_process(sensor_guard_t *g, float sample, uint32_t now_ms) {
    if (!g) return SENSOR_ERR_RANGE_LOW;

    uint8_t flags = SENSOR_OK;

    /* 1. Перевірка фізичних меж */
    if (sample < g->cfg.min_valid) {
        flags |= SENSOR_ERR_RANGE_LOW;
    } else if (sample > g->cfg.max_valid) {
        flags |= SENSOR_ERR_RANGE_HIGH;
    }

    /* 2. Градієнтний контроль (швидкість наростання) */
    if (g->has_history) {
        uint32_t dt_ms = now_ms - g->prev_ts_ms;
        if (dt_ms > 0) {
            float dt_s = (float)dt_ms / 1000.0f;
            float gradient = fabsf(sample - g->prev_val) / dt_s;
            if (gradient > g->cfg.max_gradient_per_s) {
                flags |= SENSOR_ERR_SLEW_RATE;
            }
        }
    }

    /* 3. Ітеративний розрахунок дисперсії Уелфорда */
    g->count++;
    float d1 = sample - g->mean;
    g->mean += d1 / (float)g->count;
    float d2 = sample - g->mean;
    g->m2 += d1 * d2;

    /* Перевірка нульової дисперсії після накопичення базового вікна */
    if (g->count >= g->cfg.variance_window) {
        float var = g->m2 / (float)(g->count - 1);
        if (var < g->cfg.min_noise_variance) {
            flags |= SENSOR_ERR_ZERO_VARIANCE;
        }
    }

    g->prev_val = sample;
    g->prev_ts_ms = now_ms;
    g->has_history = true;
    g->status_flags = flags;

    return flags;
}
```
```cpp
SensorError SensorGuard::process(float sample, uint32_t now_ms) noexcept {
    auto flags = SensorError::Ok;

    // 1. Фізичні межі
    if (sample < cfg_.min_valid) {
        flags = flags | SensorError::RangeLow;
    } else if (sample > cfg_.max_valid) {
        flags = flags | SensorError::RangeHigh;
    }

    // 2. Градієнтний контроль (dY/dt)
    if (has_history_) {
        const uint32_t dt_ms = now_ms - prev_ts_ms_;
        if (dt_ms > 0) {
            const float dt_s = static_cast<float>(dt_ms) / 1000.0f;
            const float gradient = std::abs(sample - prev_val_) / dt_s;
            if (gradient > cfg_.max_gradient_per_s) {
                flags = flags | SensorError::SlewRate;
            }
        }
    }

    // 3. Алгоритм Уелфорда
    count_++;
    const float d1 = sample - mean_;
    mean_ += d1 / static_cast<float>(count_);
    const float d2 = sample - mean_;
    m2_ += d1 * d2;

    if (count_ >= cfg_.variance_window) {
        const float var = m2_ / static_cast<float>(count_ - 1);
        if (var < cfg_.min_noise_variance) {
            flags = flags | SensorError::ZeroVariance;
        }
    }

    prev_val_ = sample;
    prev_ts_ms_ = now_ms;
    has_history_ = true;
    status_ = flags;

    return status_;
}

float SensorGuard::variance() const noexcept {
    if (count_ < 2) {
        return 0.0f;
    }
    return m2_ / static_cast<float>(count_ - 1);
}
```

## Апаратне та програмне відновлення після тихої відмови

Коли фільтр фіксує нульову дисперсію або неприпустимий стрибок, просто відкинути відлік недостатньо. Система повинна спробувати реанімувати завислий сенсорний вузол.

### 1. Апаратне скидання живлення сенсорної шини (Power Cycling)

Якщо внутрішній мікроконтролер сенсора перейшов у стан тиристорного замикання (*Latch-Up*) або його секвенсор завис, програмні команди ініціалізації по I2C не допоможуть. Єдиний спосіб вивести чип із коми — **повністю зняти з нього живлення**.

У надійних схемах живлення сенсорної периферії подається не напряму від шини 3.3 В, а через верхній ключ на P-канальному польовому транзисторі (або мікросхему розподілу живлення *load switch*), керований виводом GPIO мікроконтролера. 

:::tabs
```c
void sensor_hardware_reset(void) {
    /* 1. Вимкнути живлення сенсорів (відпустити затвор P-MOSFET) */
    gpio_set_level(PIN_SENSOR_POWER_EN, 1);
    
    /* 2. Притягнути SDA та SCL до нуля, щоб уникнути паразитного живлення через ESD-діоди */
    gpio_set_direction(PIN_I2C_SDA, GPIO_MODE_OUTPUT);
    gpio_set_direction(PIN_I2C_SCL, GPIO_MODE_OUTPUT);
    gpio_set_level(PIN_I2C_SDA, 0);
    gpio_set_level(PIN_I2C_SCL, 0);
    
    /* 3. Витримати паузу для повного розряду блокувальних конденсаторів */
    delay_ms(50);
    
    /* 4. Відновити живлення та повернути режим I2C */
    gpio_set_level(PIN_SENSOR_POWER_EN, 0);
    delay_ms(20);
    i2c_bus_reinit();
}
```
```cpp
void reset_sensor_hardware(GpioPin power_en, GpioPin sda, GpioPin scl, I2cDriver& i2c) noexcept {
    // 1. Зняти живлення
    power_en.write(PinState::High);

    // 2. Скинути лінії у нуль проти паразитного живлення через ESD-захист
    sda.set_mode(PinMode::Output);
    scl.set_mode(PinMode::Output);
    sda.write(PinState::Low);
    scl.write(PinState::Low);

    // 3. Пауза на розряд ємностей обв'язки
    system_sleep_ms(50);

    // 4. Подати живлення та реініціалізувати шину
    power_en.write(PinState::Low);
    system_sleep_ms(20);
    i2c.reinitialize();
}
```

:::

### 2. Розблокування затиснутої лінії I2C (Bus Clear Sequence)

Якщо збій стався під час передачі байта від веденого пристрою, сенсор може застрягти у стані утримання лінії SDA в низькому рівні (0 В), чекаючи чергового тактового імпульсу. Якщо мікроконтролер перезавантажиться, апаратний I2C-периферійний блок зависне, бо шина вважається зайнятою (*Bus Busy*).

Стандартна процедура відновлення вимагає перевести пін `SCL` у режим ручного перемикання GPIO та видати 9 тактових імпульсів: на кожному спадному фронті ведений пристрій виштовхує наступний біт, поки не звільнить лінію SDA, після чого генерується умова `STOP`.

### 3. Автомат станів деградації (Graceful Degradation FSM)

При виявленні збою контур керування переходить через послідовні захисні фази:
1. `STATE_HEALTHY`: усі діагностичні прапорці чисті (`SENSOR_OK`). Контур керування використовує прямий вимір сенсора.
2. `STATE_SUSPECT`: зафіксовано поодинокий градієнтний викид або короткочасне пропадання шуму. Контур тимчасово використовує лінійну екстраполяцію попередніх значень (`y[k] = 2 · y[k-1] − y[k-2]`), очікуючи підтвердження збою.
3. `STATE_DEGRADED`: апаратний збій підтверджено протягом `N` послідовних тактів. Прошивка запускає апаратний перезапуск живлення сенсора, виставляє біт деградації в телеметрії та перемикає регулятор на аналітичну модель (наприклад, теплову модель за струмом).
4. `STATE_FAILSAFE`: всі сенсори та моделі вийшли за допустимі межі. Контролер вимикає силові виходи, переводить актуатори в безпечний стан і сигналізує аварію.

## Серверний моніторинг та аномальний детекшн телеметрії

Локальні перевірки на пристрої відсікають грубі збої та мертві регістри. Проте повільний систематичний дрейф (наприклад, щорічне старіння сенсора на 0.2 % на місяць) часто виявляється лише на стороні хмарного бекенду, де є доступ до статистики всього парку пристроїв (*fleet-wide analytics*).

### 1. Когортний аналіз та порівняння з сусідами (Fleet Peer Comparison)

Якщо в одній географічній зоні або в одному виробничому цеху встановлено 50 вузлів моніторингу температури та вологості, їхні покази мають бути просторово скорельованими.

Серверний аналізатор розраховує середнє значення та стандартне відхилення по всій когорті пристроїв:
```
Z_score[i] = (y[i] − μ_cohort) / σ_cohort
```
Якщо для 49 пристроїв значення лежать у межах норми `Z_score ∈ [-1.5; +1.5]`, а один пристрій систематично показує `Z_score = +4.8` протягом кількох діб поспіль, сервер автоматично позначає цей вузол прапорцем *«підозра на дрейф калібрування»* та ставить задачу сервісній бригаді на його заміну.

### 2. Лічильники послідовності та «привиди шлюзів»

У розподілених мережах (LoRaWAN, Zigbee, BLE Mesh) існує небезпека тихого зависання проміжного шлюзу (*gateway*). Якщо шлюз кешує останній прийнятий пакет і при обриві радіозв'язку продовжує транслювати його вгору на хмарний сервер по Ethernet/MQTT, сервер бачить регулярний потік повідомлень.

Щоб запобігти цьому, телеметричний протокол зобов'язаний містити:
- **Монотонний лічильник послідовності (*Frame Sequence Counter*):** кожне нове вимірювання збільшує лічильник на 1 (`seq_num++`). Якщо сервер отримує два пакети з однаковим `seq_num`, він знає, що нових фізичних даних немає.
- **Мітку часу генерації на кристалі (*Origin Timestamp* / *Uptime*):** час, виміряний локальним монотонним таймером мікроконтролера в мілісекундах від старту, передається всередині підписаного пакета, що виключає маніпуляції з боку проміжних ретрансляторів.

### 3. Контракт телеметрії з бітовою маскою достовірності

Найбільша помилка при проектуванні протоколу обміну — передавати лише числове значення:
```json
{"temp": 23.4}
```
Якщо на пристрої спрацював фільтр нульової дисперсії або градієнтний ліміт, прошивка не має права «придумати» число чи мовчки приховати помилку. Контракт повинен містити явну оцінку достовірності (*Data Quality*):

```json
{
  "seq": 14205,
  "uptime_s": 84201,
  "temp": 23.4,
  "quality": {
    "plausible": true,
    "noise_ok": false,
    "cross_check": true,
    "degraded": true
  }
}
```

Прапорець `degraded: true` сигналізує алгоритмам верхнього рівня (SCADA чи хмарній аналітиці), що пристрій на зв'язку, але його вимірюванню більше не можна довіряти для автоматичного замкненого контуру керування (*Closed-Loop Control*). Контур перемикається на резервну модель або сповіщає оператора.

## Підсумок: золоті правила боротьби з тихими відмовами

1. **Код повернення `OK` перевіряє дріт, а не кристал.** Отримання байтів по шині I2C/SPI без помилок кадрування означає лише працездатність інтерфейсного блоку сенсора. Фізичний стан чутливого елемента потребує окремої валідації.
2. **Відсутність шуму — це тривога.** Справжній аналоговий світ завжди шумить на рівні молодших розрядів АЦП. Ідеально плоска пряма лінія в цифровому потоці — вірна ознака мертвого регістру чи завислого секвенсора.
3. **Обмежуй похідну фізичною інерцією.** Будь-який стрибок сигналу, швидкість якого перевищує теплову, механічну чи гідравлічну постійну часу системи, є апаратною завадою або дефектом монтажу.
4. **Порівнюй із фізичною моделлю.** Якщо прямий давач суперечить закономірностям процесу (струм тече, а тепла немає), система повинна ізолювати збійний канал та перейти на аналітичну модель.
5. **Ніколи не приховуй деградацію.** Прошивка зобов'язана маркувати сумнівні дані діагностичними бітами якості, а не підставляти останнє збережене значення замість пошкодженого.
