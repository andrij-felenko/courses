Коли трансивер мікроконтролера виставляє біти в антену або на диференційну пару RS-485, цей сигнал фізично доступний кожному провіднику в радіусі досяжності. Підключення дешевого логічного аналізатора за п'ять доларів до клем або радіоприймача SDR (від англ. *Software Defined Radio*) до ефіру дає зловмиснику повний дамп обміну. Перша наївна реакція інженера — «замаскувати» байти: закодувати в Base64, переставити байти місцями або накласти фіксовану маску операцією XOR. Такий захист не витримує й кількох секунд: Base64 є лише форматом представлення двійкових даних, а фіксована маска XOR розкривається миттєво через аналіз частоти байтів або зіставлення з відомим заголовком пакета (англ. *known-plaintext attack*). 

Інша поширена ілюзія — покладатися на контрольну суму [CRC-32](root:com-modulation/crc). Контрольна сума розрахована виключно на виявлення випадкових фізичних завад (шум, наведення від сусідніх двигунів, брязкіт контактів). Вона повністю відкрита й детермінована. Якщо ворог перехоплює пакет, змінює команду `VALVE_CLOSE` на `VALVE_OPEN`, перераховує поліном CRC за відомою формулою та відправляє пакет далі, приймач слухняно виконає підроблену команду, адже контрольна сума зійдеться ідеально.

Справжній криптографічний захист будується не на приховуванні алгоритму, а на строгому математичному розподілі ролей між криптографічними примітивами. У вбудованих системах цей захист обмежений жорсткими рамками: лічені кілобайти оперативної пам'яті, десятки міліампер струму живлення та обмежені тактові частоти ядра. Щоб побудувати надійний зв'язок і не перетворити плату на відкриту мішень, потрібен чіткий алгоритмічний мінімум.

## Тріада безпеки: чому автентичність важливіша за шифрування

Класична теорія інформаційної безпеки спирається на три фундаментальні вимоги, відомі як тріада CIA (від англ. *Confidentiality, Integrity, Authenticity/Availability*):

1. **Конфіденційність** (від латинського *confidentia* — «довіра»): інформація доступна лише авторизованим сторонам і прихована від стороннього спостерігача. Досягається симетричним або асиметричним шифруванням.
2. **Цілісність** (від латинського *integritas* — «неушкодженість»): гарантія того, що передані або збережені дані не зазнали змін, випадкових чи навмисних.
3. **Автентичність** (від грецького *authentikos* — «справжній, первинний»): неспростовне підтвердження авторства повідомлення — впевненість у тому, що пакет відправив саме заявлений вузол, а не зловмисник, який видає себе за нього.

У світі веб-серверів конфіденційність часто ставлять на перше місце, ховаючи номери банківських карток чи паролі користувачів. Проте у світі вбудованої електроніки, автоматизації та робототехніки пріоритети кардинально змінюються: **автентичність і цілісність критично важливіші за конфіденційність**.

Розгляньмо вузол керування польотним контролером квадрокоптера або сервоприводом високовольтного роз'єднувача. Якщо сторонній спостерігач перехопить телеметрію з поточною напругою батареї `12.6 V` або висотою `45 m`, це рідко призводить до аварії (конфіденційність порушено, але система керована). Але якщо зловмисник впровадить у радіоканал власну фальшиву команду `MOTOR_CUT_OFF` або підмінить цільовий кут нахилу, літальний апарат миттєво впаде на землю. Якщо система не перевіряє автентичність відправника, навіть найскладніше шифрування не врятує від деструктивних дій.

Криптографія (від грецького *kryptos* — «прихований» + *graphein* — «писати») надає конкретний набір інструментів під кожну вимогу. Якщо шифрування розв'язує задачу конфіденційності, то коди автентичності повідомлень (MAC) та цифрові підписи гарантують автентичність і цілісність.

> 🔧 **Навіщо це.** Якщо бюджет пам'яті та обчислень мікроконтролера настільки мізерний, що виконати повний цикл шифрування неможливо, відмовтеся від конфіденційності (передавайте відкритий текст), але **ніколи не відмовляйтеся від автентичності**. Відкритий пакет із валідним криптографічним підписом HMAC або Poly1305 гарантує, що пристрій не виконає підроблену команду ворога.

## Симетричне блокове шифрування: AES та небезпека режимів

Коли конфіденційність необхідна, базовим робочим стандартом в інженерній практиці є симетричний блоковий шифр **AES** (англ. *Advanced Encryption Standard*, алгоритм *Rijndael*, стандартизований NIST у 2001 році). «Симетричний» означає, що відправник і отримувач використовують один і той самий секретний ключ `K`.

### Внутрішній устрій AES: перестановки й нелінійні заміни

AES є блоковим шифром: він працює з фіксованим блоком даних розміром **128 біт (16 байтів)**. Розмір ключа може становити 128, 192 або 256 біт. У вбудованих пристроях де-факто стандартом є **AES-128** (рідше AES-256).

Всередині AES 16 байтів відкритого тексту розташовуються у вигляді матриці 4×4 байтів, яка називається матрицею стану (англ. *State*). Обчислення організовані за схемою мережі підстановок-перестановок (SPN, англ. *Substitution-Permutation Network*) і складаються з послідовності раундів (10 раундів для ключа 128 біт, 14 раундів для 256 біт). Кожен раунд виконує чотири суворі математичні перетворення:

1. `SubBytes`: нелінійна заміна кожного байта за фіксованою таблицею S-Box, побудованою на операціях інверсії в полі Галуа `GF(2⁸)` та афінному перетворенні. Це забезпечує конфузію (заплутування зв'язку між ключем і шифротекстом).
2. `ShiftRows`: циклічний зсув рядків матриці стану ліворуч на 0, 1, 2 та 3 байти відповідно.
3. `MixColumns`: множення кожного стовпця матриці на фіксований поліном у полі Галуа `GF(2⁸)`. Разом із `ShiftRows` це дає дифузію (розсіювання: зміна одного вхідного біта вже за 2 раунди змінює майже половину бітів усього 128-бітного блоку — лавинний ефект).
4. `AddRoundKey`: побайтове додавання за модулем 2 (операція XOR) матриці стану з раундовим ключем, отриманим із головного ключа через алгоритм Key Schedule.

Більшість сучасних 32-бітних мікроконтролерів (STM32 сімейств F4/F7/G4/L4/H7, ESP32, nRF52840) мають апаратний криптографічний співпроцесор (наприклад, модуль `CRYP` або `AES Accelerator`). Апаратний блок виконує повне 128-бітне перетворення за 12–40 тактів процесора без навантаження на ядро Cortex-M або Xtensa.

```formula
E_K(P) = AddRoundKey(MixColumns(ShiftRows(SubBytes(State))), K_round)
```

### Пастка режиму ECB: чому його категорично заборонено

Сам по собі блоковий шифр вміє шифрувати лише рівно 16 байтів. Якщо пакет має довжину 64 або 100 байтів, постає питання: як застосувати 16-байтний шифр до послідовності блоків? Для цього слугують режими роботи (англ. *modes of operation*).

Найпростіший і найнебезпечніший режим — **ECB** (англ. *Electronic Codebook* — «електронна кодова книга»). У режимі ECB кожен 16-байтний блок відкритого тексту `P[i]` шифрується абсолютно незалежно одним і тим самим ключем:

```formula
C[i] = AES_K(P[i])
```

Головна вразливість ECB полягає в тому, що **однакові блоки відкритого тексту завжди перетворюються на однакові блоки шифротексту**. 

Якщо в пакеті телеметрії перші 16 байтів — це заголовок `DEVICE_ID=0x01;CMD=IDLE;`, то зашифрований блок `C[0]` буде незмінним у кожній передачі. Зловмисник, спостерігаючи за ефіром, бачить регулярні патерни. Навіть не знаючи ключа, він може:
- Точно фіксувати стан пристрою (наприклад, коли датчик передає нульові значення або стан спокою).
- Здійснювати атаку підміни блоків (англ. *block swapping*): вирізати зашифрований блок із команди `AUTH_SUCCESS` і вставити його замість блоку `AUTH_FAIL`. Приймач розшифрує валідний блок і надасть несанкціонований доступ.

> ⚠️ **Вирок інженерної практики:** Режим **ECB суворо заборонений** для використання в будь-яких мережевих протоколах, радіоканалах чи для збереження даних у Flash-пам'яті.

### Режими CBC та CTR: перехід до потоку

Щоб приховати повторювані структури, блоки шифротексту треба зв'язати між собою або перетворити блоковий шифр на потоковий:

1. **CBC (Cipher Block Chaining — зчеплення блоків шифру):**
   Перед шифруванням поточний блок відкритого тексту додається операцією XOR із попереднім зашифрованим блоком:
   ```formula
   C[0] = AES_K(P[0] ⊕ IV)
   C[i] = AES_K(P[i] ⊕ C[i-1])      [для i ≥ 1]
   ```
   Для першого блоку використовується випадковий **вектор ініціалізації** (IV, від латинського *vector* — «носій, перевізник» та *initialis* — «початковий»). IV не є секретом і передається у відкритому вигляді на початку пакета, але він **мусить бути непередбачуваним** для кожного нового повідомлення.
   
   *Недоліки CBC в embedded:*
   - Потребує вирівнювання довжини даних (падінгу, наприклад PKCS#7) до кратності 16 байтам. Якщо пакет має довжину 17 байтів, доведеться шифрувати 32 байти.
   - Вразливий до атак підміни бітів (англ. *bit-flipping attack*): інвертування біта в блоці `C[i-1]` призводить до точної інверсії відповідного біта у відкритому тексті `P[i]` після розшифрування.
   - Вразливий до атак типу *Padding Oracle*, якщо пристрій повідомляє про помилку формату падінгу.

2. **CTR (Counter Mode — режим лічильника):**
   Режим перетворює блоковий шифр на швидкісний потоковий генератор гами (англ. *keystream*). Шифрується не сам відкритий текст, а комбінація одноразового числа (**Nonce**, від англійського *number used once* — «число, вжите один раз») та монотонно зростаючого лічильника:
   ```formula
   Keystream[i] = AES_K(Nonce || Counter[i])
   C[i] = P[i] ⊕ Keystream[i]
   ```
   
   *Переваги CTR:*
   - Немає падінгу: шифрує масив будь-якої довжини байт-у-байт (17 байтів відкритого тексту дають рівно 17 байтів шифротексту).
   - Розшифрування ідентичне шифруванню: використовується лише пряма функція `AES_Encrypt`, що економить до 40% пам'яті мікроконтролера на таблицях розшифрування.
   - Повна паралелізація обчислень та можливість попереднього розрахунку гами в моменти простою ядра.

   *Фатальна небезпека CTR:* Якщо значення `Nonce` повториться двічі з одним і тим самим ключем `K`, то для двох різних повідомлень згенерується однакова гама:
   ```formula
   C_1 ⊕ C_2 = (P_1 ⊕ KS) ⊕ (P_2 ⊕ KS)
             = P_1 ⊕ P_2      [гама KS повністю скорочується]
   ```
   Знаючи відкритий текст одного повідомлення (або його структуру), зловмисник миттєво розкриває відкритий текст другого повідомлення без застосування криптоаналізу.

### Автентифіковане шифрування (AEAD): GCM та CCM

Головний урок криптографії останніх двох десятиліть: **шифрування без автентифікації не працює**. Зловмисник завжди може маніпулювати бітами шифротексту в каналі зв'язку.

Спроби інженерів самостійно поєднати шифрування з гешем (наприклад, спочатку зашифрувати, а потім приклеїти MAC, або навпаки) породили десятки вразливостей. Тому сучасний криптографічний стандарт вимагає використання схеми **AEAD** (англ. *Authenticated Encryption with Associated Data* — автентифіковане шифрування з асоційованими даними).

AEAD виконує дві дії за одну операцію:
1. Конфіденційно шифрує корисне навантаження (Payload).
2. Обчислює криптографічний **тег автентичності** (Auth Tag, зазвичай 16 байтів), який захищає від підробки як зашифровані дані, так і відкриті заголовки пакета (**AAD** — *Additional Authenticated Data*, наприклад: адреса відправника, номер пакета, біти конфігурації).

Два головні алгоритми AEAD у мікроконтролерах:
- **AES-GCM (Galois/Counter Mode):** Поєднує швидкісне шифрування в режимі CTR із множенням у полі Галуа `GF(2¹²⁸)` (хеш-функція GHASH) для формування тегу. Дуже швидкий, підтримується апаратними прискорювачами STM32 та ESP32.
- **AES-CCM (Counter with CBC-MAC):** Стандарт для радіоканалів Bluetooth Low Energy (BLE), Zigbee (IEEE 802.15.4) та Wi-Fi WPA2/WPA3. Обчислює CBC-MAC по всьому повідомленню, після чого шифрує дані та MAC у режимі CTR. Потребує менше апаратних ресурсів на чипі, але складніший у паралелізації.

```
+-------------------------------------------------------------------+
|                        ПАКЕТ AEAD (AES-GCM)                       |
+-------------------+-----------------------+-----------------------+
|  AAD (Заголовок)  |  Ciphertext (Дані)   |    Auth Tag (16 B)    |
| (відкритий текст) | (зашифровано AES-CTR) | (обчислено GHASH/CCM) |
+-------------------+-----------------------+-----------------------+
|   Автентифіковано  |  Зашифровано + Автентифіковано               |
+-------------------------------------------------------------------+
```

Якщо приймач під час розшифрування виявляє, що обчислений тег не збігається з отриманим хоча б в одному біті, **пакет негайно відкидається**, а зашифровані дані навіть не потрапляють в обробник програми.

## Криптографічна цілісність та автентичність: геші та MAC

Якщо шифрувати дані не потрібно (наприклад, загальнодоступні покази датчика температури або широкомовний маяк), але критично важливо унеможливити їхню підміну чи фальсифікацію, застосовують криптографічні геш-функції та коди автентичності повідомлень.

### Односторонні геш-функції: SHA-256

Криптографічна геш-функція `H(M)` приймає повідомлення `M` довільної довжини та стискає його у фіксований дайджест (для **SHA-256** — рівно 256 біт / 32 байти). Вона гарантує три математичні властивості:
1. **Стійкість до відновлення прообразу (Preimage resistance):** Маючи геш `h`, неможливо за прийнятний час знайти вхідне повідомлення `M` таке, що `H(M) = h` (складність `2²⁵⁶`).
2. **Стійкість до другого прообразу (Second preimage resistance):** Маючи `M₁`, неможливо знайти інше `M₂ ≠ M₁` таке, що `H(M₁) = H(M₂)`.
3. **Стійкість до колізій (Collision resistance):** Неможливо знайти будь-яку пару довільних повідомлень `(M₁, M₂)` з однаковим гешем (за парадоксом днів народження складність становить `2¹²⁸`).

SHA-256 побудована за структурою Меркла–Дамґорда: вхідне повідомлення розбивається на блоки по 512 біт (64 байти), які послідовно змінюють внутрішній вектор ініціалізації через 64 раунди бітових зсувів, операцій XOR та логічних функцій `Ch` і `Maj`.

#### Чому не можна робити `Hash(Key || Data)`: атака подовженням

Типова помилка інженерів-початківців, які намагаються перевірити автентичність: склеїти секретний ключ і повідомлення та порахувати звичайний геш: `Tag = SHA256(Key || Message)`.

Ця конструкція фатально зламана через **атаку подовженням повідомлення** (англ. *Length Extension Attack*). Оскільки вихідний геш SHA-256 є точним відображенням внутрішнього стану функції після обробки останнього блоку, зловмисник, перехопивши `Message` та `Tag`, може:
1. Взяти `Tag` як початковий внутрішній стан геш-функції.
2. Дописати в кінець повідомлення власний шкідливий блок: `Message || Padding || EvilCommand`.
3. Отримати валідний підпис `Tag_Evil = SHA256(Key || Message || Padding || EvilCommand)`, взагалі не знаючи секретного ключа `Key`!

![Структура обчислення HMAC](/root/course/embedded/kryptominimum-prystroiu/img/hmac-construction.svg)
*Двоетапна конструкція HMAC за RFC 2104: каскадне хешування внутрішньої та зовнішньої масок ключа, що унеможливлює атаку подовженням повідомлення.*

### HMAC: надійний стандарт (RFC 2104)

Для захисту від атак подовження стандартизовано алгоритм **HMAC** (англ. *Keyed-Hash Message Authentication Code*). Він використовує двоетапне вкладене хешування з двома фіксованими масками: внутрішньою `ipad = 0x36` та зовнішньою `opad = 0x5C`.

Математичне визначення HMAC для блоку довжиною `B = 64` байти:

```formula
K_0 = PadKey(Key, B)                   [якщо довжина K > 64, то K_0 = SHA256(K), інакше доповнюємо нулями]
InnerKey = K_0 ⊕ (0x36 repeated 64B)   [побайтовий XOR ключа з внутрішньою маскою ipad]
OuterKey = K_0 ⊕ (0x5C repeated 64B)   [побайтовий XOR ключа з зовнішньою маскою opad]
InnerHash = SHA256(InnerKey || Message) [перший прохід гешування]
HMAC = SHA256(OuterKey || InnerHash)   [другий прохід: блокує атаку подовженням]
```

Оскільки вихід першого гешу закривається другим викликом `SHA256(OuterKey || ...)`, зловмисник не має прямого доступу до внутрішнього стану першого гешу, і атака подовженням стає математично неможливою.

### CMAC та Poly1305: оптимізація під обмежені мікроконтролери

У вбудованих системах є дві визначні альтернативи HMAC-SHA256:

1. **AES-CMAC (Cipher-based MAC, RFC 4493 / NIST SP 800-38B):**
   Використовує блоковий шифр AES у спеціальному режимі CBC-MAC із захистом від атак різної довжини через похідні підключі `K₁` та `K₂`.
   *Головна перевага:* Якщо в мікроконтролері вже є апаратний модуль AES (наприклад, у чипі Bluetooth nRF52), використання AES-CMAC дає надійну автентифікацію взагалі **без включення коду SHA-256 у прошивку**, заощаджуючи 8–15 КБ Flash-пам'яті.

2. **Poly1305:**
   Одноразовий швидкісний MAC, створений Деніелом Бернштейном (Daniel J. Bernstein). Працює як обчислення полінома над скінченним полем простих чисел за модулем `2¹³⁰ − 5`.
   *Головна перевага:* Працює в рази швидше за SHA-256 на мікроконтролерах без апаратних криптоприскорювачів (Cortex-M0+/M3). Зазвичай застосовується в парі з потоковим шифром **ChaCha20** (комбінація ChaCha20-Poly1305 за RFC 8439).

| Алгоритм MAC | Базовий примітив | Довжина тегу | Апаратні вимоги | Сфера застосування в Embedded |
| :--- | :--- | :--- | :--- | :--- |
| **HMAC-SHA256** | Геш SHA-256 | 32 байти (256 біт) | Вимагає рушій SHA-256 | TLS 1.3, автентифікація прошивки OTA |
| **AES-CMAC** | Шифр AES-128 | 16 байтів (128 біт) | Вимагає лише рушій AES | Стек Bluetooth Low Energy, Secure Boot |
| **AES-GCM Tag** | AES-CTR + GHASH | 16 байтів (128 біт) | Апаратний AES + множник GF | Шифровані канали зв'язку, радіоканал |
| **Poly1305** | Поліном `mod 2¹³⁰−5` | 16 байтів (128 біт) | Мінімальні (базова арифметика) | Швидкісний обмін на чипах без AES |

## Генерація випадкових чисел: TRNG проти PRNG

Будь-який криптографічний протокол розвалюється, якщо секретні ключі, вектори ініціалізації чи одноразові числа Nonce згенеровані передбачувано.

### Катастрофа функції `rand()` у криптографії

Стандартні функції мов C/C++ `rand()`, `random()` або `lrand48()` побудовані на лінійних конгруентних генераторах (LCG, від латинського *congruens* — «відповідний»):

```formula
X_{n+1} = (A · X_n + C) mod M
```

LCG володіє нульовою криптографічною стійкістю: перехопивши всього 2–3 послідовних значення `X_n`, зловмисник розв'язує лінійне рівняння, відновлює поточний внутрішній стан генератора та наперед розраховує всі майбутні «випадкові» числа.

Якщо таким генератором створити сеансовий ключ для радіоканалу, ворог згенерує точно такий самий ключ і безперешкодно розшифрує трафік.

![Тракт апаратного генератора випадкових чисел TRNG](/root/course/embedded/kryptominimum-prystroiu/img/trng-entropy-pipeline.svg)
*Апаратний конвеєр генерації випадкових чисел: від фізичного джерела теплового шуму та дерандомізатора фон Неймана до неперервного тестування якості та криптостійкого CSPRNG.*

### Фізична ентропія та апаратний TRNG

Для отримання справжньої випадковості потрібен **TRNG** (англ. *True Random Number Generator* — апаратний генератор справжніх випадкових чисел). Його робота базується на квантових або теплових фізичних процесах всередині кремнію:

1. **Тепловий шум (шум Джонсона–Найквіста):** квантові флуктуації електронів у p-n переході діода Зенера (стабілітрона) у режимі зворотного пробою.
2. **Фазовий джитер кільцевих генераторів (Ring Oscillators):** кілька непарних кілець інверторів працюють на високій частоті; через нерівномірність температури та флуктуації живлення між ними виникає випадковий фазовий зсув, що фіксується тригером.
3. **Метастабільність:** переведення RS-тригера або комірки SRAM у нестійкий стан під час подачі живлення.

#### Алгоритм дерандомізації Джона фон Неймана

Фізичний аналоговий шум завжди має невелике апаратне зміщення (англ. *bias*): наприклад, через дрейф напруги виходить 53% одиниць і 47% нулів. Для отримання абсолютно рівномірного розподілу застосовують дерандомізатор фон Неймана (1951 рік):

Біти з квантувача зчитуються парами:
- Пара `00` → відкидається (виходу немає).
- Пара `11` → відкидається (виходу немає).
- Пара `01` → на вихід записується біт `0`.
- Пара `10` → на вихід записується біт `1`.

Оскільки ймовірність випадання комбінації `01` дорівнює `P(0) · P(1)`, а комбінації `10` — `P(1) · P(0)`, вони математично абсолютно рівні за будь-якого вихідного перекосу:

```formula
P(01) = P(0) · P(1) = P(1) · P(0) = P(10)      [імовірності симетричні, bias усунуто]
```

### Криптостійкі генератори (CSPRNG / DRBG)

Апаратний TRNG працює відносно повільно: типова швидкість становить від 50 кбіт/с до 2 Мбіт/с. Якщо пристрою треба генерувати тисячі сеансових ключів або великі масиви псевдовипадкових чисел для захисту протоколів, ентропію з TRNG засипають у криптостійкий генератор псевдовипадкових чисел — **CSPRNG** (англ. *Cryptographically Secure Pseudo-Random Number Generator*, стандартизований NIST SP 800-90A як **CTR-DRBG** або **HMAC-DRBG**).

TRNG використовується для ініціалізації (англ. *seed*) внутрішнього 256-бітного стану DRBG та його періодичного оновлення (англ. *reseed*). Генератор на базі AES-CTR генерує випадкові послідовності зі швидкістю сотень мегабайтів на секунду, зберігаючи повну криптографічну непередбачуваність.

## Захист ключів у кремнії: пам'ять, RDP та Secure Elements

Найстійкіший криптографічний алгоритм стає марним, якщо секретний ключ можна вичитати з пристрою фізично.

### Як викрадають ключі з Flash-пам'яті

Типова конфігурація мікроконтролера на етапі прототипу: прошивка компілюється із константним масивом `const uint8_t aes_key[16] = {0x12, 0x34, ...};` і прошивається у внутрішню Flash-пам'ять.

Зловмисник отримує фізичний доступ до плати (наприклад, краде датчик або безпілотник):
1. Підключає програматор ST-Link або J-Link до контактів інтерфейсу `SWD` (`SWCLK`, `SWDIO`, `GND`).
2. Запускає команду вичитування пам'яті через утиліту OpenOCD:
   ```bash
   openocd -f interface/stlink.cfg -f target/stm32f4x.cfg -c "init; dump_image flash.bin 0x08000000 0x80000; exit"
   ```
3. За 3 секунди отримує повний бінарний дамп прошивки, відкриває його в дизасемблері Ghidra або шукає блоки високої ентропії утилітою `binwalk` і забирає ключ.

![Ієрархія захисту криптографічних ключів у мікроконтролерах](/root/course/embedded/kryptominimum-prystroiu/img/key-storage-security-levels.svg)
*Рівні ізоляції секретних ключів: від вразливої відкритої Flash-пам'яті та апаратного захисту RDP до фізично захищених крипточипів Secure Element.*

### Апаратні рівні блокування: STM32 RDP та ESP32 eFuse

Для блокування інтерфейсів зневадження мікроконтролери містять спеціальні апаратні конфігураційні байти ([Option Bytes](root:embedded/fiuzy-option-bytes-i-iak-ne-zrobyty-tsehlynku)):

1. **RDP Level 0 (Readout Protection Level 0):** Режим розробки. Повний доступ через JTAG/SWD, відкрите читання та запис Flash/SRAM.
2. **RDP Level 1:** Захист пам'яті. Якщо налагоджувач підключається до порту SWD, контролер апаратно забороняє доступ до Flash (спроба читання повертає помилку шини або нулі). Контролер виконує прошивку тільки самостійно при завантаженні з Flash.
   - *Механізм відкату:* Можна повернути RDP Level 1 назад у Level 0, але цей перехід викликає **обов'язкове апаратне масове стирання** (англ. *Mass Erase*) всієї Flash-пам'яті та SRAM. Секретні дані гинуть разом із поверненням доступу.
   - *Вразливість:* RDP Level 1 часто піддається атакам впровадженням збоїв живлення (**Voltage Glitching**). Короткочасне (10–20 нс) просідання напруги на виводі живлення ядра під час перевірки Option Bytes змушує процесор пропустити інструкцію захисту й залишити порт відкритим без стирання.
3. **RDP Level 2:** Незворотне блокування. Спеціальний бітовий патерн фізично випалює або блокує логіку SWD/JTAG назавжди. Процесор більше ніколи неможливо підключити до налагоджувача. Завантаження дозволено лише з основної Flash. Перехід у Level 0 або 1 неможливий.

В інших архітектурах, таких як **ESP32**, захист будується на випалюванні апаратних одноразових перемичок **eFuse**:
- `FLASH_CRYPT_CNT`: вмикає апаратне прозоре шифрування зовнішньої SPI Flash ключем AES-256, що зберігається в заблокованому блоці eFuse.
- `JTAG_DISABLE`: перманентне спалювання апаратного порту JTAG.
- `ABS_DONE_0` (Secure Boot): перевірка цифрового підпису RSA-3072 / ECDSA перед кожним запуском bootloader.

### Апаратні крипточипи безпеки: Secure Elements

Для пристроїв найвищого рівня критичності (платіжні термінали, смарт-лічильники, автомобільні блоки, військові системи) захисту всередині загального мікроконтролера недостатньо через можливість атак побічними каналами (DPA, аналіз електромагнітного випромінювання DEMA) або фізичного зняття шарів кремнію (англ. *decapping*).

Рішенням є виділений крипточип безпеки — **Secure Element** (наприклад, **Microchip ATECC608A / ATECC608B**, **NXP SE050**, **Infineon OPTIGA Trust**).

```
+-------------------+                      +------------------------------------+
|  Головний MCU     |                      |       Secure Element (ATECC608)    |
| (STM32 / ESP32)   |                      |                                    |
|                   |  I2C / SPI (Запит)   |  +------------------------------+  |
| Відправляє дані M | -------------------> |  | Апаратний рушій AES / ECC    |  |
| на підпис / обмін |                      |  +------------------------------+  |
|                   |  Отримує ТІЛЬКИ Tag  |  | Захищена EEPROM (Секретні К) |  |
| Отримує результат | <------------------- |  | (активна захисна сітка)      |  |
+-------------------+                      +------------------------------------+
                                           Ключ К НІКОЛИ не виходить назовні!
```

*Принцип роботи Secure Element:*
1. Секретні ключі прошиваються на захищеній фабриці у внутрішню EEPROM чіпа, яка захищена активною мікропровідною сіткою (при спробі спилювання чи свердління лазером чіп миттєво самознищує ключі).
2. Ключ **фізично ніколи не передається по шині I2C/SPI**.
3. Головний мікроконтролер надсилає чіпу відкрите повідомлення `M`. Крипточип самостійно рахує підпис (ECDSA) або код автентичності (HMAC/AES-GCM) всередині свого ізольованого кристала й повертає лише результат (Tag або Signature).
4. Чіп містить вбудовані генератори випадкового струму та маскування живлення, що робить неможливим зняття ключа через вимірювання споживання струму (DPA).

## Безпека в оперативній пам'яті: пастки компілятора та таймінгові атаки

Навіть якщо ключі правильно завантажені, помилки в сирцевому коді на мовах C та C++ здатні повністю зруйнувати безпеку.

### Пастка 1: Видалення `memset` оптимізатором

Типовий код очищення буфера з ключем перед виходом із функції:

:::tabs
```c
void process_secret(void) {
    uint8_t key[16];
    read_key_from_storage(key);
    use_key_for_crypto(key);
    memset(key, 0, sizeof(key)); // Компілятор видаляє цей виклик як мертвий код!
}
```
```cpp
void process_secret() {
    uint8_t key[16];
    read_key_from_storage(key);
    use_key_for_crypto(key);
    std::fill_n(key, sizeof(key), 0); // Оптимізатор так само викидає цей запис!
}
```
:::

Компілятор GCC / Clang з увімкненою оптимізацією `-O2` або `-O3` застосовує правило усунення мертвого коду (англ. *Dead Store Elimination*). Оскільки масив `key` розташований на стеку і після виклику `memset` функція завершується, компілятор знає, що ці нулі ніколи більше не будуть прочитані програмою. Він **повністю викидає виклик `memset`** під час компіляції!

Секретний ключ залишається лежати у відкритому вигляді в комірках SRAM на стеку. Будь-який подальший збій, виклик core dump або переповнення буфера (Buffer Overflow) у сусідній функції віддає цей ключ зловмиснику.

*Правильне рішення:* Використовувати спеціальні функції гарантованого очищення пам'яті, які оптимізатор не має права видаляти: `explicit_bzero` (POSIX), `memset_s` (C11 Annex K) або запис через покажчик `volatile`.

### Пастка 2: Таймінгові атаки на порівняння MAC (`memcmp`)

Коли мікроконтролер отримує пакет і звіряє 16-байтний Auth Tag із розрахованим:

:::tabs
```c
// Небезпечно: memcmp переривається на першому незбігу (витік часу виконання)
if (memcmp(received_tag, computed_tag, 16) == 0) {
    execute_command();
}
```
```cpp
// Небезпечно: std::equal / memcmp переривається на першому незбігу
if (std::equal(received_tag.begin(), received_tag.end(), computed_tag.begin())) {
    execute_command();
}
```
:::

Функція `memcmp` перевіряє байти по черзі і **завершує роботу на першому незбігу**. Якщо перший байт неправильний, функція виконується за 4 такти; якщо збіглися перші 5 байтів — за 20 тактів.

Вимірюючи час відповіді мікроконтролера за допомогою точного таймера або аналізатора протоколів, ворог побайтово підбирає правильний Auth Tag (всього 256 спроб на байт замість `2¹²⁸`).

*Правильне рішення:* Порівняння за постійний час (англ. *Constant-Time Comparison*), де цикл завжди перевіряє всі 16 байтів незалежно від місця виникнення незбігу.

## Робочий код: надійний обробник пакетів із постійним часом перевірки

Нижче наведено практичну реалізацію криптографічного захисту: безпечне очищення пам'яті, константне порівняння та формування кадру AEAD.

:::tabs
```c
#include <stdint.h>
#include <stddef.h>
#include <stdbool.h>

// Гарантоване занулення пам'яті, яке не видаляється оптимізатором (-O2/-O3)
void secure_memzero(void *ptr, size_t len) {
    volatile uint8_t *p = (volatile uint8_t *)ptr;
    while (len--) {
        *p++ = 0;
    }
}

// Порівняння масивів за постійний час: захист від таймінгових атак
bool constant_time_memcmp(const void *a, const void *b, size_t len) {
    const uint8_t *pa = (const uint8_t *)a;
    const uint8_t *pb = (const uint8_t *)b;
    uint8_t result = 0;

    for (size_t i = 0; i < len; i++) {
        result |= (pa[i] ^ pb[i]);
    }

    return (result == 0);
}

// Дерандомізатор фон Неймана для потоку бітів з аналогового TRNG
// Повертає кількість отриманих чистих бітів (0 або 1)
bool von_neumann_step(uint8_t bit_pair, uint8_t *out_bit) {
    uint8_t b0 = (bit_pair >> 1) & 0x01;
    uint8_t b1 = bit_pair & 0x01;

    if (b0 == 0 && b1 == 1) {
        *out_bit = 0;
        return true;
    } else if (b0 == 1 && b1 == 0) {
        *out_bit = 1;
        return true;
    }
    // Пари 00 та 11 відкидаються для усунення bias
    return false;
}
```
```cpp
#include <cstdint>
#include <cstddef>
#include <span>
#include <array>
#include <optional>

namespace crypto {

// RAII-обгортка для гарантованого занулення пам'яті при виході зі скоупу
template <size_t N>
class SecureBuffer {
public:
    std::array<uint8_t, N> data{};

    ~SecureBuffer() {
        volatile uint8_t *p = data.data();
        for (size_t i = 0; i < N; ++i) {
            p[i] = 0;
        }
    }

    constexpr size_t size() const { return N; }
    uint8_t* raw() { return data.data(); }
    const uint8_t* raw() const { return data.data(); }
    std::span<const uint8_t, N> span() const { return std::span<const uint8_t, N>(data); }
};

// Порівняння за постійний час для std::span
bool constant_time_equal(std::span<const uint8_t> a, std::span<const uint8_t> b) {
    if (a.size() != b.size()) {
        return false;
    }

    uint8_t result = 0;
    for (size_t i = 0; i < a.size(); ++i) {
        result |= (a[i] ^ b[i]);
    }

    return (result == 0);
}

// Дерандомізатор фон Неймана на C++
constexpr std::optional<uint8_t> von_neumann_decorrelate(uint8_t bit_pair) {
    const uint8_t b0 = (bit_pair >> 1) & 0x01;
    const uint8_t b1 = bit_pair & 0x01;

    if (b0 == 0 && b1 == 1) return 0;
    if (b0 == 1 && b1 == 0) return 1;
    return std::nullopt; // 00 та 11 відкидаються
}

} // namespace crypto
```

## Інженерний чекліст криптомінімуму пристрою

Підсумовуючи вимоги до надійного проєктування вбудованого вузла, зведемо базові правила до інженерного чекліста:

1. **Режими шифрування:** Категорична заборона на ECB. Для будь-якого шифрування каналів обирати автентифіковані режими **AEAD (AES-128-GCM, AES-128-CCM або ChaCha20-Poly1305)**.
2. **Автентичність понад усе:** Якщо шифрування не потрібне, використовувати **HMAC-SHA256** або **AES-CMAC**. Не будувати власних конструкцій на базі `Hash(Key || Data)`.
3. **Унікальність Nonce:** Для кожного нового повідомлення в режимах CTR/GCM/CCM використовувати унікальний лічильник або Nonce. Повтор Nonce з одним ключем повністю компрометує конфіденційність.
4. **Якісна ентропія:** Заборонено використовувати `rand()`. Усі ключі, Nonce та солі генерувати лише через **апаратний TRNG** у зв'язці з **CSPRNG (CTR-DRBG)**.
5. **Захист від налагоджувача:** У фінальній прошивці обов'язково активувати **Flash Readout Protection (RDP Level 1 або 2)**, відключати невикористовувані інтерфейси JTAG/SWD та стирати налагоджувальні буфери.
6. **Ізоляція майстер-ключів:** Для критичних пристроїв використовувати зовнішні апаратні крипточипи **Secure Elements (ATECC608, SE050)**, щоб ключі ніколи не перебували у відкритій Flash-пам'яті загального мікроконтролера.
7. **Гігієна коду:** Усі криптографічні порівняння тегів виконувати виключно функціями **постійного часу (`constant_time_memcmp`)**, а буфери з ключами очищати за допомогою **`secure_memzero` / `explicit_bzero`**, блокуючи оптимізацію компілятора.
