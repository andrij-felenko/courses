У мить, коли лінія скидання NRST мікроконтролера переходить із низького логічного рівня у високий, а напруга внутрішнього стабілізатора стабілізується на позначці 3.3 В, центральний процесор ще не знає про існування мов C або C++, глобальних змінних чи функції `main()`. Регістри загального призначення містять випадковий апаратний стан, статична оперативна пам'ять (SRAM) заповнена хаотичним тепловим шумом після подачі живлення, стек викликів не виділений, а всі глобальні структури даних існують лише у вигляді пасивних масивів байтів, записаних у нелеткій Flash-пам'яті.

Щоб програма на мові високого рівня могла виконати хоча б один рядок утилітарного коду, процесор повинен пройти суворий апаратний та програмний ритуал. Цей міст між кремнієвими тригерами ядра та першою фігурною дужкою функції `main()` будує **стартовий код** (англ. *startup code*, або історично `crt0` — *C Runtime Zero*).

## Перший такт процесора: апаратна вибірка векторів

Будь-який запуск процесора починається з події скидання (Reset). Це може бути первинна подача напруги живлення (Power-On Reset — POR), плавне просідання напруги нижче допустимого порогу (Brown-Out Reset — BOR), зовнішній імпульс на фізичному виводі NRST, спрацювання апаратного сторожового таймера (Watchdog) або програмна команда перезавантаження.

У класичних процесорах загального призначення (наприклад, архітектури x86 або класичних ARM7TDMI/ARM9) після зняття сигналу скидання лічильник команд (Program Counter, `PC`) примусово встановлювався на фіксовану апаратну адресу, наприклад `0x00000000` або `0xFFFF0000`. За цією адресою мала лежати перша інструкція асемблера — як правило, безумовний перехід (`JMP` або `B reset_handler`). Покажчик стека при цьому взагалі не був ініціалізований, тому програміст мусив найпершою асемблерною командою вручну завантажити адресу вершини оперативної пам'яті в регістр стека `SP`.

Архітектура ARM Cortex-M докорінно змінила цей механізм: ядро містить апаратний кінцевий автомат, який бере на себе підготовку стека та зчитування точки входу ще до того, як буде декодована перша машинна інструкція.

### Зчитування нульової та першої адрес

Коли ядро Cortex-M виходить зі стану скидання (Reset), внутрішній секвенсер пам'яті звертається до шини інструкцій (I-Code) і послідовно читає два 32-бітних слова з нульового зміщення адресного простору (за замовчуванням це початок Flash-пам'яті `0x08000000`, відображений на нульову адресу `0x00000000` через апаратні перемички BOOT):

1. **Зсув 0x00 (перші 4 байти):** Значення автоматично завантажується в апаратний головний покажчик стека `MSP` (Main Stack Pointer). Це значення обчислюється лінкером і зазвичай вказує на самий кінець оперативної пам'яті (`_estack = ORIGIN(RAM) + LENGTH(RAM)`), оскільки стек в архітектурі ARM росте згори донизу (Full Descending Stack).
2. **Зсув 0x04 (наступні 4 байти):** Значення завантажується в лічильник команд `PC` (Program Counter). Це абсолютна адреса функції `Reset_Handler` — точки входу стартового коду.

> 🔧 **Навіщо це.** Апаратне завантаження покажчика стека гарантує, що процесор стає здатним обробляти будь-які апаратні винятки (наприклад, збій живлення NMI або BusFault під час старту) негайно, на першому ж такті, оскільки механізм збереження контексту переривань ARM Cortex-M вимагає валідного стека для збереження регістрів `R0–R3`, `R12`, `LR`, `PC` та `xPSR`.

```
Адреса      Вміст у Flash-пам'яті             Призначення ядра Cortex-M
0x00000000: 0x20020000 (Вершина SRAM)    ──>  Апаратно завантажується в MSP (R13)
0x00000004: 0x0800018D (Адреса Reset)    ──>  Апаратно завантажується в PC (R15)
```

Також під час ініціалізації регістр зв'язку `LR` (`R14`) примусово заповнюється значенням `0xFFFFFFFF`, що сигналізує про відсутність попереднього контексту виклику, а системний контролер скидає регістр керування `CONTROL` у `0`, переводячи ядро в привілейований режим (Privileged Thread Mode) із використанням головного стека `MSP`.

### Молодший біт адреси та Thumb-режим

Якщо поглянути на реальний файл дампа пам'яті або лістинг лінкера, адреса функції `Reset_Handler` у векторній таблиці завжди є **непарним числом** (наприклад, `0x0800018D` замість `0x0800018C`). При цьому апаратні інструкції ядра Cortex-M завжди вирівняні в пам'яті по парних адресах (кратні 2 або 4 байтам).

Причина полягає в архітектурній специфіці ARM. У традиційних процесорах ARM молодший нульовий біт адреси переходу визначав набір інструкцій: біт `0` означав виконання 32-бітних інструкцій режиму ARM, а біт `1` вмикав 16/32-бітний компактний режим Thumb. Процесори лінійки Cortex-M апаратно підтримують **виключно набір команд Thumb-2** і не містять декодера класичного ARM-режиму.

Коли процесор завантажує адресу з вектором `Reset_Handler` у лічильник команд `PC`, біт 0 адреси апаратно переноситься в прапорець `T` (Thumb) системного регістра стану `xPSR` (Extended Program Status Register), а сам `PC` очищує цей біт і починає вибірку інструкцій із парної адреси:

```
Значення у векторі скидання: 0x0800018D
= 0x0800018C | 0x1 (Thumb-біт)

xPSR.T ──> 1 (Ядро залишається в режимі Thumb-2)
PC     ──> 0x0800018C (Фізична адреса першої машинної інструкції)
```

Якщо компілятор або лінкер згенерує парну адресу у векторі скидання (біт `0` дорівнює `0`), ядро спробує перейти в неіснуючий режим ARM. У результаті на першому ж такті процесор зафіксує апаратну помилку недійсного стану (`INVSTATE` у регістрі `UFSR`) і негайно звалиться у фатальний виняток `UsageFault` або `HardFault`.

### Порівняння з архітектурою RISC-V

В архітектурі RISC-V (наприклад, ядра RV32I або RV32EC) логіка першого такту побудована простіше, але вимагає більше програмної дисципліни. Процесор не має апаратного автомата читання стека. При скиданні регістр `PC` примусово встановлюється на апаратно зашиту адресу вектора скидання (наприклад, `0x00001000` для внутрішнього ROM або `0x20000000` для Flash).

Покажчик стека `sp` (`x2`) після скидання містить сміття. Тому першою інструкцією стартового коду RISC-V завжди має бути пряме завантаження адреси вершини стека асемблерною командою:

```asm
/* Стартовий асемблерний код для RISC-V */
.section .init
.global _start
_start:
    la sp, _estack             /* Встановлення покажчика стека sp */
    la gp, __global_pointer$   /* Ініціалізація покажчика глобальних даних */
    la t0, trap_vector         /* Встановлення адреси обробника пасток */
    csrw mtvec, t0             /* Запис у системний регістр mtvec */
    tail Reset_Handler         /* Перехід до ініціалізації середовища */
```

У RISC-V регістр `mtvec` (Machine Trap-Vector Base-Address) визначає адресу переходу при виникненні будь-яких переривань та пасток. Молодші два біти `mtvec` задають режим роботи: `0b00` (Direct mode — усі винятки переходять на єдину адресу `trap_vector`) або `0b01` (Vectored mode — адреса переривання обчислюється як `BASE + 4·CAUSE`).

## Анатомія векторної таблиці ARM Cortex-M

Таблиця векторів переривань (Vector Table) — це суцільний масив 32-бітних адрес, розміщений на самому початку виконуваного образу пам'яті. 

![Анатомія векторної таблиці ARM Cortex-M](/root/course/embedded/startovyi-kod/img/cortex-vector-table.svg)
*Розподіл системних векторів у пам'яті Flash та призначення обов'язкового Thumb-біта точки входу*

Перші 16 елементів таблиці зарезервовані самою архітектурою ARM для системних винятків ядра (Core Exceptions). Усі наступні записи відповідають перериванням периферійних пристроїв конкретного виробника чипа (IRQ — Interrupt Requests).

```
Індекс  Зсув     Назва вектора         Призначення
0       0x00     Initial SP            Початкова вершина стека MSP (_estack)
1       0x04     Reset_Handler         Точка входу стартового коду
2       0x08     NMI_Handler           Немасковане переривання (збій кварцу, живлення)
3       0x0C     HardFault_Handler     Критичний системний збій
4       0x10     MemManage_Handler     Порушення блоку захисту пам'яті MPU
5       0x14     BusFault_Handler      Помилка шини при читанні/записі
6       0x18     UsageFault_Handler    Невірна інструкція, INVSTATE, ділення на 0
7..10   0x1C     Reserved              Зарезервовано архітектурою ARM
11      0x2C     SVC_Handler           Системний виклик (Supervisor Call)
12      0x30     DebugMon_Handler      Монітор налагодження
13      0x34     Reserved              Зарезервовано архітектурою ARM
14      0x38     PendSV_Handler        Відкладений виклик для перемикання задач RTOS
15      0x3C     SysTick_Handler       Системний таймер квантування часу
16+     0x40+    WWDG, RTC, TIM...     Переривання периферії виробника чипа
```

Повний список адресних зсувів, пріоритетів та бітових полів регістрів керування системними винятками наведено у вставці [Регістри SCB та вектори винятків ARM Cortex-M](root:embedded/startovyi-kod/api-cortex-vector-table.md).

### Секція `.isr_vector` та атрибути компілятора

Щоб компілятор не оптимізував таблицю векторів як «невикористовуваний масив» і розмістив її строго за нульовою адресою Flash-пам'яті, у коді використовують спеціальні атрибути секцій:

:::tabs
```c
/* Оголошення векторної таблиці мовою C */
__attribute__((section(".isr_vector"), used))
void (* const g_pfnVectors[])(void) = {
    (void (*)(void))(&_estack), /* 0x00: Initial SP */
    Reset_Handler,              /* 0x04: Reset Handler */
    NMI_Handler,                /* 0x08: NMI Handler */
    HardFault_Handler,          /* 0x0C: HardFault Handler */
    MemManage_Handler,          /* 0x10: MPU Fault Handler */
    BusFault_Handler,           /* 0x14: Bus Fault Handler */
    UsageFault_Handler,         /* 0x18: Usage Fault Handler */
    0, 0, 0, 0,                 /* 0x1C..0x28: Reserved */
    SVC_Handler,                /* 0x2C: SVCall Handler */
    0,                          /* 0x30: Debug Monitor */
    0,                          /* 0x34: Reserved */
    PendSV_Handler,             /* 0x38: PendSV Handler */
    SysTick_Handler,            /* 0x3C: SysTick Handler */
    /* Далі розміщуються вектори периферії: WWDG_IRQHandler, PVD_IRQHandler... */
};
```
```cpp
/* Оголошення векторної таблиці мовою C++ з суворою типізацією */
using VectorHandler = void (*)(void);

extern "C" {
    __attribute__((section(".isr_vector"), used))
    const VectorHandler g_pfnVectors[] = {
        reinterpret_cast<VectorHandler>(&_estack), /* 0x00: Initial SP */
        Reset_Handler,                            /* 0x04: Reset Handler */
        NMI_Handler,                              /* 0x08: NMI Handler */
        HardFault_Handler,                        /* 0x0C: HardFault Handler */
        MemManage_Handler,                        /* 0x10: MPU Fault Handler */
        BusFault_Handler,                         /* 0x14: Bus Fault Handler */
        UsageFault_Handler,                       /* 0x18: Usage Fault Handler */
        nullptr, nullptr, nullptr, nullptr,       /* 0x1C..0x28: Reserved */
        SVC_Handler,                              /* 0x2C: SVCall Handler */
        nullptr,                                  /* 0x30: Debug Monitor */
        nullptr,                                  /* 0x34: Reserved */
        PendSV_Handler,                           /* 0x38: PendSV Handler */
        SysTick_Handler,                          /* 0x3C: SysTick Handler */
    };
}
```
:::

Атрибут `__attribute__((used))` наказує компілятору зберегти символ у результуючому об'єктному файлі, навіть якщо до нього немає явних звернень з інших функцій C. У скрипті лінкера директива `KEEP(*(.isr_vector))` забороняє лінкеру викидати цю секцію під час оптимізації невикористаного коду (`--gc-sections`).

### Механізм слабких символів (`weak`)

Якщо програміст не використовує в проекті переривання таймера `TIM2_IRQHandler`, але векторна таблиця містить покажчик на цю функцію, лінкер за замовчуванням видасть помилку нерозв'язаного символу (*undefined reference*).

Щоб уникнути ручного опису десятків порожніх функцій, у стартовому коді застосовують механізм **слабких зв'язків** (weak aliases). Усі обробники оголошуються як слабкі синоніми єдиного універсального обробника за замовчуванням `Default_Handler`:

:::tabs
```c
/* Оголошення слабких обробників переривань */
void Default_Handler(void) {
    /* Нескінченна пастка: якщо ми потрапили сюди, переривання було
       увімкнено в NVIC, але для нього не написали реальний обробник */
    while (1) {
    }
}

void NMI_Handler(void)        __attribute__((weak, alias("Default_Handler")));
void HardFault_Handler(void)  __attribute__((weak, alias("Default_Handler")));
void SysTick_Handler(void)    __attribute__((weak, alias("Default_Handler")));
void USART1_IRQHandler(void)  __attribute__((weak, alias("Default_Handler")));
```
```cpp
/* Оголошення слабких обробників мовою C++ */
extern "C" {
    void Default_Handler() {
        while (true) {
        }
    }

    void NMI_Handler()        __attribute__((weak, alias("Default_Handler")));
    void HardFault_Handler()  __attribute__((weak, alias("Default_Handler")));
    void SysTick_Handler()    __attribute__((weak, alias("Default_Handler")));
    void USART1_IRQHandler()  __attribute__((weak, alias("Default_Handler")));
}
```
:::

Якщо користувач у будь-якому місці проекту створить власну звичайну функцію `void USART1_IRQHandler(void)`, лінкер виявить сильний символ (*strong symbol*) і автоматично замінить адресу `Default_Handler` у таблиці векторів на адресу користувацької функції.

### Релокація векторів через регістр `SCB->VTOR`

За замовчуванням процесор очікує знайти таблицю векторів за адресою `0x00000000`. Проте у складних системах із завантажувачами (Bootloader) або прошивками, що оновлюються «по повітрю» (OTA), основна програма розміщується зі зсувом у Flash (наприклад, за адресою `0x08010000`), або таблицю векторів переносять у швидку оперативну пам'ять (RAM) для динамічної зміни обробників переривань «на льоту».

Для зміни адреси таблиці використовується регістр зміщення векторів `VTOR` (Vector Table Offset Register), розташований у системному блоці керування ядра за адресою `SCB->VTOR` (`0xE000ED08`):

:::tabs
```c
/* Перенесення таблиці векторів на нову адресу у Flash або RAM */
void relocate_vector_table(uint32_t new_vector_base_address) {
    volatile uint32_t *scb_vtor = (volatile uint32_t *)0xE000ED08UL;
    
    /* Нова адреса має бути строго вирівняна по ступеню двійки (мінімум 128 або 512 байт) */
    *scb_vtor = new_vector_base_address;
    
    /* Бар'єри пам'яті гарантують завершення операції запису до наступного переривання */
    __asm volatile("dsb\n\tisb" ::: "memory");
}
```
```cpp
#include <cstdint>

/* Безпечна релокація таблиці векторів у C++ */
namespace mcu::system {
    inline void relocate_vector_table(std::uintptr_t new_base_address) noexcept {
        constexpr auto vtor_reg_addr = static_cast<std::uintptr_t>(0xE000ED08UL);
        auto* const scb_vtor = reinterpret_cast<volatile std::uint32_t*>(vtor_reg_addr);
        
        *scb_vtor = static_cast<std::uint32_t>(new_base_address);
        asm volatile("dsb\n\tisb" ::: "memory");
    }
}
```
:::

## Секції `.data` та `.bss`: створення робочого простору змінних

Після виклику `Reset_Handler` стек уже працездатний, проте жодна глобальна чи статична змінна програми ще не має коректного значення. Якщо в коді написано `int counter = 42;` або `char rx_buffer[128];`, пам'ять RAM під цими змінними після ввімкнення живлення містить залишкове сміття.

### LMA проти VMA: парадокс енергонезалежної пам'яті

Щоб зрозуміти необхідність стартового копіювання, потрібно розрізняти два поняття адрес у скрипті лінкера:

- **LMA (Load Memory Address — адреса завантаження):** Фізична адреса, куди дані записуються програматором під час прошивки чіпа. Це енергонезалежна Flash-пам'ять (`0x08000000`).
- **VMA (Virtual/Execution Memory Address — адреса виконання):** Адреса, за якою процесор звертається до змінної під час виконання інструкцій `LDR` та `STR`. Для змінних це виключно оперативна пам'ять SRAM (`0x20000000`).

Константи та код функцій (`.rodata`, `.text`) мають однакові LMA та VMA, оскільки процесор може виконувати інструкції та читати константи безпосередньо з Flash завдяки механізму виконання на місці (XIP — eXecute In Place).

Глобальні змінні з початковим значенням (секція `.data`) створюють парадокс: їхнє початкове значення має **зберігатися при вимкненому живленні** (тобто лежати у Flash), але під час роботи програми процесор повинен мати змогу **змінювати їхні значення на льоту** (тобто вони мусять жити в RAM).

У двійковому форматі ELF (Executable and Linkable Format) секція `.data` позначається типом `SHT_PROGBITS` (секція містить реальні дані в образі файлу). Лінкер записує її тіло у Flash-пам'ять одразу після секцій коду (це адреса `_sidata`), але всі змінні в коді лінкуються з абсолютними адресами в RAM (діапазон від `_sdata` до `_edata`).

### Чому `.bss` не зберігається у прошивці

Секція `.bss` (історично: *Block Started by Symbol*) містить глобальні та статичні змінні, які не мають явного початкового значення або ініціалізовані нулями:

:::tabs
```c
/* Приклади розміщення змінних у C */
int target_voltage = 3300;     /* Секція .data: початкове значення 3300 зберігається у Flash */
int current_reading = 0;       /* Секція .bss: початкове значення 0 */
uint8_t dma_buffer[16384];     /* Секція .bss: 16 КБ пам'яті без ініціалізації */
```
```cpp
#include <cstdint>
#include <array>

/* Приклади розміщення змінних у C++ */
int target_voltage = 3300;                         /* Секція .data */
int current_reading = 0;                           /* Секція .bss */
std::array<std::uint8_t, 16384> dma_buffer{};      /* Секція .bss */
```
:::

У форматі ELF секція `.bss` має спеціальний тип `SHT_NOBITS` (секція не займає байтів у файлі прошивки). Якби 16-кілобайтний масив `dma_buffer` зберігався у файлі образу, це безглуздо збільшило б розмір бінарного файлу `.bin` на 16 КБ і зайняло дорогоцінну Flash-пам'ять мікроконтролера.

Замість цього лінкер виділяє під секцію `.bss` лише віртуальний діапазон адрес у RAM між символами `_sbss` та `_ebss`. У самій Flash-пам'яті секція `.bss` займає **рівно 0 байтів**. Обов'язок заповнити цю ділянку пам'яті нулями перед стартом програми покладається на стартовий код `Reset_Handler`.

### Реалізація циклу копіювання та обнулення

У функції `Reset_Handler` стартовий код виконує два послідовні цикли обходу пам'яті:

:::tabs
```c
/* Класична реалізація ініціалізації пам'яті мовою C */
extern uint32_t _sidata; /* Початок початкових значень .data у Flash (LMA) */
extern uint32_t _sdata;  /* Початок секції .data в RAM (VMA) */
extern uint32_t _edata;  /* Кінець секції .data в RAM (VMA) */
extern uint32_t _sbss;   /* Початок секції .bss в RAM (VMA) */
extern uint32_t _ebss;   /* Кінець секції .bss в RAM (VMA) */

void init_memory_sections(void) {
    /* 1. Копіювання секції .data з Flash у RAM */
    uint32_t *p_src = &_sidata;
    uint32_t *p_dst = &_sdata;
    while (p_dst < &_edata) {
        *p_dst++ = *p_src++;
    }

    /* 2. Заповнення секції .bss нулями в RAM */
    uint32_t *p_bss = &_sbss;
    while (p_bss < &_ebss) {
        *p_bss++ = 0;
    }
}
```
```cpp
#include <cstdint>

/* Типізована реалізація ініціалізації пам'яті мовою C++ */
extern "C" {
    extern std::uint32_t _sidata;
    extern std::uint32_t _sdata;
    extern std::uint32_t _edata;
    extern std::uint32_t _sbss;
    extern std::uint32_t _ebss;
}

namespace mcu::startup {
    inline void init_memory_sections() noexcept {
        /* 1. Копіювання ініціалізованих змінних */
        const std::uint32_t* src = &_sidata;
        std::uint32_t* dst = &_sdata;
        while (dst < &_edata) {
            *dst++ = *src++;
        }

        /* 2. Обнулення неініціалізованих змінних */
        std::uint32_t* bss = &_sbss;
        while (bss < &_ebss) {
            *bss++ = 0;
        }
    }
}
```
:::

### Вирівнювання по 4 байти (Word Alignment)

Зверніть увагу, що покажчики мають тип `uint32_t*`, тобто копіювання та запис нулів відбуваються 32-бітними машинними словами (по 4 байти за одну ітерацію). Це у 4 рази швидше, ніж побайтовий цикл `uint8_t*`.

Проте така оптимізація вимагає абсолютної гарантії, що всі символи `_sidata`, `_sdata`, `_edata`, `_sbss`, `_ebss` **строго вирівняні в пам'яті на межу 4 байтів**. Якщо розмір секції `.data` складе, наприклад, 13 байтів, а лінкер не вирівняє кінцевий символ `_edata`, 32-бітний покажчик на останній ітерації вийде за межі секції і затре перший байт сусідньої секції `.bss`. 

Тому в скрипті лінкера кожне визначення символу обов'язково супроводжується командою вирівнювання `. = ALIGN(4);`:

```ld
.data :
{
  . = ALIGN(4);
  _sdata = .;
  *(.data)
  *(.data*)
  . = ALIGN(4);
  _edata = .;
} >RAM AT> FLASH
```

## Підготовка рантайму C та C++

Коли пам'ять RAM набула коректного початкового стану, процесор переходить до конфігурації апаратних блоків ядра та середовища виконання мови програмування.

### Виклик `SystemInit()`: первинне налаштування тактування

У більшості SDK (зокрема CMSIS від ARM для STM32, NXP, Microchip) наступним кроком є виклик функції `SystemInit()`. Її завдання — перевести процесор із початкового низькочастотного стану внутрішнього RC-генератора (HSI, наприклад 16 МГц) у стабільний робочий режим:

1. Скидання конфігураційних регістрів модуля тактування (RCC) до базового заводського стану.
2. Вимкнення всіх активних переривань на рівні периферії.
3. Налаштування кількості тактів очікування доступу до Flash-пам'яті (Flash Latency / Wait States). Якщо процесор планується розігнати до 168 МГц, а Flash-пам'ять фізично здатна читатися лише на частоті до 30 МГц, контролеру Flash необхідно встановити 5 тактів затримки (`FLASH_ACR_LATENCY_5WS`), інакше ядро почне читати сміття замість коду інструкцій.

### Увімкнення апаратного співпроцесора FPU (`SCB->CPACR`)

На мікроконтролерах із процесорними ядрами Cortex-M4F, Cortex-M7 або Cortex-M33, що містять апаратний блок обчислень із рухомою комою (FPU), після скидання співпроцесори `CP10` та `CP11` (відповідальні за одинарну та подвійну точність) **апаратно вимкнені** з міркувань енергозбереження.

![Конфігурація регістра SCB->CPACR для увімкнення FPU](/root/course/embedded/startovyi-kod/img/fpu-init-register.svg)
*Формат бітових полів регістра CPACR для надання повного доступу до математичного співпроцесора FPU*

Якщо компілятор зібрав проект із прапорцями апаратного FPU (`-mfloat-abi=hard -mfpu=fpv4-sp-d16`), будь-яка математична операція або завантаження числа з рухомою комою породжує інструкції на кшталт `vldr.32` або `vadd.f32`.

Якщо процесор зустріне таку інструкцію при вимкненому FPU, ядро моментально згенерує апаратний виняток `UsageFault` із встановленням прапорця `NOCP` (No Coprocessor) у регістрі `UFSR`.

Увімкнення FPU здійснюється записом комбінації бітів `0b11` (Full Access) у бітові поля `CP10` (біти 21:20) та `CP11` (біти 23:22) системного регістра `SCB->CPACR` (`0xE000ED88`):

:::tabs
```c
/* Увімкнення FPU у стартовому коді */
void enable_fpu_coprocessor(void) {
    volatile uint32_t *scb_cpacr = (volatile uint32_t *)0xE000ED88UL;
    
    /* Встановлюємо біти 20..23 у значення 0b1111 (0xF) */
    *scb_cpacr |= (0xFUL << 20);
    
    /* Інструкції синхронізації шин і конвеєра */
    __asm volatile("dsb\n\tisb" ::: "memory");
}
```
```cpp
#include <cstdint>

/* Увімкнення FPU у стилі C++ */
namespace mcu::hardware {
    inline void enable_fpu() noexcept {
        constexpr auto cpacr_addr = static_cast<std::uintptr_t>(0xE000ED88UL);
        auto* const scb_cpacr = reinterpret_cast<volatile std::uint32_t*>(cpacr_addr);
        
        constexpr std::uint32_t full_access_mask = (0xFUL << 20);
        *scb_cpacr |= full_access_mask;
        
        asm volatile("dsb\n\tisb" ::: "memory");
    }
}
```
:::

Інструкція `dsb` (Data Synchronization Barrier) змушує шину пам'яті завершити транзакцію запису в регістр `CPACR`, а `isb` (Instruction Synchronization Barrier) повністю очищує конвеєр команд процесора, гарантуючи, що наступні інструкції з рухомою комою будуть декодовані вже увімкненим FPU.

### Глобальні конструктори C++: секція `.init_array`

У мові C всі глобальні змінні мають константне початкове значення, яке просто копіюється з Flash у RAM. Проте в C++ глобальні та статичні об'єкти класів можуть мати **конструктори**, які виконують довільний код (виділення ресурсів, конфігурація апаратних периферійних модулів, розрахунок таблиць):

```cpp
/* Глобальний об'єкт C++ з нетривіальним конструктором */
class UartDriver {
public:
    UartDriver(uint32_t baudrate) {
        /* Код конструктора, який має виконатися ДО виклику main() */
        this->init_hardware(baudrate);
    }
private:
    void init_hardware(uint32_t baudrate);
};

UartDriver g_console_uart(115200); /* Хто викличе цей конструктор? */
```

Компілятор `g++` знаходить усі такі об'єкти в проекті, створює для кожного з них невелику анонімну функцію-ініціалізатор і складає покажчики на ці функції у спеціальну таблицю — секцію `.init_array` у Flash-пам'яті.

Стартовий код або стандартна бібліотека (функція `__libc_init_array` зі складу `newlib`) повинні пройти цей масив покажчиків від початку (`__init_array_start`) до кінця (`__init_array_end`) і послідовно викликати кожну функцію:

:::tabs
```c
/* Ручна ініціалізація C++ конструкторів у стартовому коді C */
typedef void (*constructor_fn_t)(void);

extern constructor_fn_t __init_array_start[];
extern constructor_fn_t __init_array_end[];

void invoke_global_constructors(void) {
    size_t count = (size_t)(__init_array_end - __init_array_start);
    for (size_t i = 0; i < count; ++i) {
        if (__init_array_start[i] != NULL) {
            __init_array_start[i]();
        }
    }
}
```
```cpp
#include <cstddef>
#include <span>

/* Ідіоматичний виклик списку конструкторів у C++ */
using InitFunction = void (*)(void);

extern "C" {
    extern InitFunction __init_array_start[];
    extern InitFunction __init_array_end[];
}

namespace mcu::runtime {
    inline void call_global_constructors() noexcept {
        const std::span<InitFunction> constructors(
            __init_array_start,
            static_cast<std::size_t>(__init_array_end - __init_array_start)
        );

        for (const auto ctor : constructors) {
            if (ctor != nullptr) {
                ctor();
            }
        }
    }
}
```
:::

> ⚠️ **Пастка статичної ініціалізації (Static Initialization Order Fiasco):** Стандарт мови C++ суворо гарантує, що всі глобальні конструктори відпрацюють до першого рядка функції `main()`. Проте стандарт **не визначає порядок** виклику конструкторів, розташованих у різних файлах вихідного коду (`.cpp`). Якщо конструктор класу `Display` у файлі `display.cpp` спробує надіслати дані через об'єкт `g_console_uart` із файлу `uart.cpp`, а `g_console_uart` ще не був сконструйований, система зависне або впаде у HardFault.
>
> Надійним архітектурним вирішенням цієї проблеми є патерн «ініціалізація за першим зверненням» (Meyers' Singleton): замість глобального об'єкта створюють функцію `UartDriver& get_uart()`, всередині якої оголошено локальну статичну змінну `static UartDriver instance(115200); return instance;`. Вона буде гарантовано сконструйована саме в момент першого виклику.

## Передача керування у `main()` та наслідки повернення

Коли стек налаштовано, секцію `.data` скопійовано, секцію `.bss` занулено, базове тактування та FPU активовано, а конструктори C++ відпрацювали — середовище виконання повністю готове.

Стартовий код передає керування прикладній програмі викликом звичайної функції `main()`. За стандартом ARM AAPCS виклик `main` здійснюється інструкцією `BL main` (Branch with Link), при цьому в регістр `R0` за замовчуванням передається `0` (значення `argc`), а в регістр `R1` — `NULL` (значення `argv`).

### Що відбувається, коли `main()` повертає значення

У класичних операційних системах (Linux, Windows, macOS) функція `main()` завжди завершується командою `return 0;` або викликом `exit()`. Код повернення передається батьківському процесу через операційну систему, яка звільняє виділену віртуальну пам'ять процесу та видаляє його дескриптор із таблиці планувальника.

На голому залізі (bare-metal) операційної системи **не існує**.

Якщо функція `main()` завершить своє виконання оператором `return` або добіжить до кінцевої фігурної дужки, процесор виштовхне зі стека адресу повернення (Link Register, `LR`), яка була збережена перед викликом `main()`. Проте в стартовому коді після `main()` зазвичай нічого немає.

Якщо не вжити спеціальних заходів, лічильник команд `PC` попрямує далі по лінійній пам'яті, намагаючись виконувати довільні байти, розташовані за межами функції (байти таблиць констант, дані сусідніх секцій або невикористані комірки пам'яті, заповнені `0xFFFFFFFF`). Це негайно спричинить виконання недійсної інструкції та викличе `UsageFault` / `HardFault`.

### Архітектура захисної пастки

Щоб захистити систему від неконтрольованого виконання пам'яті у разі випадкового виходу з `main()`, стартовий код організовує термінальну пастку. 

Існує три основні інженерні стратегії обробки виходу з `main()`:

```
Стратегія 1: Енергозберігаюче зациклення (Sleep Trap)
┌────────────────────────────────────────────────────────┐
│  while (1) { __asm volatile("wfi"); }                  │
│  → Процесор спить до приходу переривань, не гріє чіп   │
└────────────────────────────────────────────────────────┘

Стратегія 2: Точка зупину налагоджувача (Debug Trap)
┌────────────────────────────────────────────────────────┐
│  __asm volatile("bkpt #0"); while(1);                  │
│  → Налагоджувач (OpenOCD/J-Link) зупиняє ядро для аналізу│
└────────────────────────────────────────────────────────┘

Стратегія 3: Апаратне самоперезавантаження (Auto-Reset)
┌────────────────────────────────────────────────────────┐
│  NVIC_SystemReset();                                   │
│  → Генерація імпульсу SYSRESETREQ через SCB->AIRCR     │
└────────────────────────────────────────────────────────┘
```

Реалізація надійного циклу завершення:

:::tabs
```c
/* Захисна пастка після виходу з main мовою C */
void Reset_Handler(void) {
    /* 1. Ініціалізація даних та рантайму */
    init_memory_sections();
    enable_fpu_coprocessor();
    SystemInit();
    invoke_global_constructors();

    /* 2. Запуск основної програми */
    main();

    /* 3. Якщо main() повернув значення — переходимо в режим очікування */
    while (1) {
        /* Команда Wait For Interrupt: вимикає тактування ядра до переривання */
        __asm volatile("wfi");
    }
}
```
```cpp
/* Захисна пастка після виходу з main мовою C++ */
extern "C" void Reset_Handler() {
    /* 1. Ініціалізація даних та рантайму */
    mcu::startup::init_memory_sections();
    mcu::hardware::enable_fpu();
    SystemInit();
    mcu::runtime::call_global_constructors();

    /* 2. Запуск основної програми */
    static_cast<void>(main());

    /* 3. Термінальний енергозберігаючий цикл */
    while (true) {
        asm volatile("wfi");
    }
}
```
:::

Інструкція `wfi` (Wait For Interrupt) переводить процесорне ядро в режим низького енергоспоживання, зупиняючи лічильник тактів процесора до приходу наступного апаратного переривання або сигналу скидання від сторожового таймера (Watchdog).

### Підсумковий таймлайн запуску мікроконтролера

Нижче наведено зведену послідовність кроків, які мікроконтролер проходить від зняття сигналу скидання до першого рядка коду користувача:

| Етап | Хто виконує | Дія та стан апаратного заліза |
|---|---|---|
| 1. Power-On Reset | Апаратне залізо | Стабілізація напруги живлення, зняття сигналу NRST. |
| 2. Завантаження MSP | Апаратний секвенсер | Читання адреси `0x00000000`, запис значення вершини стека в `MSP`. |
| 3. Завантаження PC | Апаратний секвенсер | Читання адреси `0x00000004`, біт 0 переноситься в `xPSR.T`, перехід на `Reset_Handler`. |
| 4. Копіювання `.data` | Стартовий код | Перенесення блоків по 4 байти з Flash LMA (`_sidata`) у RAM VMA (`_sdata.._edata`). |
| 5. Занулення `.bss` | Стартовий код | Запис нулів у діапазон оперативної пам'яті від `_sbss` до `_ebss`. |
| 6. Апаратна ініціалізація | `SystemInit()` | Скидання конфігурації RCC, налаштування тактів очікування Flash Latency. |
| 7. Увімкнення FPU | Стартовий код | Запис `0x00F00000` у регістр `SCB->CPACR` для розблокування блоків `CP10`/`CP11`. |
| 8. C++ конструктори | `__libc_init_array` | Послідовний виклик конструкторів глобальних класів із секції `.init_array`. |
| 9. Виклик `main()` | Стартовий код | Передача керування прикладній логіці через команду `BL main`. |
| 10. Захисна пастка | Стартовий код | Перехід у нескінченний сон `wfi` у разі повернення з `main()`. |
