# 📋 Довідник: прапорці компілятора, змінні середовища та схема маніфесту фіксації

У цій довідковій специфікації наведено стандартизовані параметри трансляторів, конфігураційні змінні оточення та повну схему маніфесту фіксації, необхідні для досягнення бінарного детермінізму, аудиту ланцюжка постачання та довгострокової консервації вбудованого інструментарію.

### 1. Прапорці компілятора, лінкера та утиліт

Для досягнення повної двійкової ідентичності компілятор повинен позбутися будь-якої прив'язки до локальної файлової системи хоста, поточного часу запуску процесу та випадкових внутрішніх станів оптимізатора. У наведеній нижче таблиці зібрано обов'язкові параметри трансляції для сучасних крос-компіляторів сімейств GCC та Clang/LLVM.

| Прапорець / Опція | Інструмент | Семантика та вплив на бінарний результат |
|---|---|---|
| `-ffile-prefix-map=OLD=NEW` | GCC 8+, Clang 10+ | Замінює абсолютний шлях `OLD` на відносний `NEW` як у препроцесорних макросах (`__FILE__`), так і в налагоджувальних записах DWARF. Усуває хостові шляхи розробника. |
| `-fmacro-prefix-map=OLD=NEW` | GCC 8+, Clang 10+ | Замінює абсолютний шлях виключно у макросах препроцесора, не змінюючи таблиць відлагодження. Застосовується, коли DWARF має містити інші префікси. |
| `-fdebug-prefix-map=OLD=NEW` | GCC 4.3+, Clang 3.8+ | Замінює абсолютний шлях лише у таблицях DWARF (`.debug_info`, `.debug_line`). Працює навіть у старих версіях GCC 4.x, де `-ffile-prefix-map` ще не існував. |
| `-Wl,--build-id=none` | GNU ld, LLD | Повністю вимикає генерацію секції `.note.gnu.build-id`. Запобігає вбудовуванню псевдовипадкового або залежного від часу 160-бітного ідентифікатора. |
| `-Wl,--build-id=sha1` | GNU ld, LLD | Формує ідентифікатор збірки як детермінований криптографічний хеш SHA-1 від усіх скомпільованих секцій коду й константних даних. |
| `-frandom-seed=STRING` | GCC | Фіксує псевдовипадковий генератор символів для анонімних просторів імен, випадкових імен локальних міток та оптимізацій міжмодульного компонування LTO. |
| `-Werror=date-time` | GCC 4.9+, Clang 3.5+ | Перетворює на фатальну помилку компіляції будь-яку спробу використання макросів `__DATE__`, `__TIME__` або `__TIMESTAMP__`. |
| `ar D` | GNU binutils | Вмикає детермінований режим архіватора статичних бібліотек `.a`: зануляє часові мітки створення файлу, виставляє UID=0, GID=0 та маску прав 0644. |

#### Механізм перепризначення префіксів (`-ffile-prefix-map`)

Прапорець `-ffile-prefix-map` працює на етапі лексичного та синтаксичного аналізу вихідного тексту програми. Якщо вихідний файл передано компілятору як абсолютний шлях `/workspace/project/src/main.c`, а опцію задано у вигляді `-ffile-prefix-map=/workspace/project=.`, компілятор під час створення дерева абстрактного синтаксису (AST) відрізає вказаний префікс `/workspace/project` і замінює його на відносну точку `.`.

Цей механізм гарантує два критично важливі для довгострокової підтримки результати:

1. **Очищення текстових рядків у секції констант (`.rodata`):** Макрос `__FILE__`, який розгортається у викликах `assert()` або системах журналювання помилок, отримує короткий рядок `"./src/main.c"` замість унікального для робочої станції інженера рядка `"/home/developer/work/device-v2/src/main.c"`. Це запобігає витоку структури каталогів хостової машини та усуває розбіжності контрольних сум Flash-пам'яті між різними робочими комп'ютерами.
2. **Стандартизація таблиць відлагодження (DWARF):** Записи заголовків компіляційних одиниць у секції `.debug_info` містять нормалізований атрибут робочого каталогу `DW_AT_comp_dir`. Завдяки цьому налагоджувач GDB та утиліта `addr2line` безпомилково зіставляють адреси збоїв із файлами сирців незалежно від того, де саме розгорнуто проєкт під час посмертного аналізу.

Якщо проєкт збирається за допомогою старіших компіляторів (наприклад, GCC 4.8–7.x), де універсальний прапорець `-ffile-prefix-map` ще не був реалізований, застосовують роздільну комбінацію двох опцій: `-fdebug-prefix-map` для таблиць DWARF та препроцесорне перевизначення базового каталогу через параметр збірки `-D__FILENAME__=...`.

#### Керування випадковістю оптимізатора (`-frandom-seed`)

Під час глибокої оптимізації коду та об'єднання функцій компілятор GCC генерує внутрішні унікальні імена для символів в анонімних просторах імен C++, а також для локальних статичних міток у модулях C. За замовчуванням генератор псевдовипадкових чисел GCC ініціалізується внутрішньою контрольною сумою компілятора та часом запуску процесу. Через це дві компіляції того самого модуля можуть отримати різні внутрішні імена міток, що змінює вихідний двійковий код. Опція `-frandom-seed=$(SOURCE_DATE_EPOCH)` або передача хешу вмісту вхідного файлу повністю фіксує послідовність псевдовипадкового генератора, гарантуючи детермінованість кодогенерації.

### 2. Змінні середовища детермінованого оточення

Для інструментів, які не мають власних прапорців командного рядка для керування часовими мітками, стандартом індустрії є використання уніфікованих системних змінних оточення. Усі ці змінні мають експортуватися складальним скриптом до виклику компілятора чи інтерпретатора.

| Змінна середовища | Очікуване значення | Обов'язковість та механізм дії |
|---|---|---|
| `SOURCE_DATE_EPOCH` | Ціле число (UNIX timestamp, наприклад `1700000000`) | Обов'язкова. Перевизначає системний виклик `time()` для GCC, Clang, Doxygen, Sphinx, генераторів образів та пакувальників файлових систем (LittleFS, FAT). |
| `TZ` | `UTC` | Обов'язкова. Фіксує часовий пояс. Без цієї змінної компіляція одного й того самого коду в Лондоні (UTC+0) та Києві (UTC+2) дасть зміщені на 2 години текстові дати. |
| `LC_ALL` / `LANG` | `C.UTF-8` або `C` | Обов'язкова. Визначає правила порівняння та сортування рядків утилітами `sort`, `find` та скриптами. Запобігає мовному дрейфу порядку об'єктних файлів. |
| `PYTHONHASHSEED` | `0` або фіксоване ціле число | Обов'язкова при використанні Python. Вимикає рандомізацію хеш-функції SipHash для рядків, гарантуючи стабільний порядок ітерації по `dict` та `set`. |
| `ZERO_AR_DATE` | `1` | Допоміжна. Змушує застарілі версії архіватора `ar` та утиліти `ranlib` записувати нульову мітку часу у заголовки статичних архівів `.a`. |

#### Специфікація стандарту `SOURCE_DATE_EPOCH`

Змінна `SOURCE_DATE_EPOCH` повинна містити ціле десяткове число без знаку, що відповідає кількості секунд з 1 січня 1970 року (UNIX Epoch). Значення зазвичай витягується з дати останнього коміту в репозиторії Git за допомогою команди:

```bash
SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)
export SOURCE_DATE_EPOCH
```

Якщо інструмент виявляє наявність змінної `SOURCE_DATE_EPOCH`, він зобов'язаний діяти за такими правилами:
- Ігнорувати поточний системний годинник реального часу операційної системи;
- Форматувати дату у будь-яких згенерованих заголовках на основі значення цієї змінної у часовому поясі UTC;
- При створенні бінарних образів файлових систем (наприклад, образів LittleFS, SPIFFS або FAT для зовнішньої Flash-пам'яті) встановлювати час створення та модифікації всіх вкладених файлів рівним або не більшим за значення `SOURCE_DATE_EPOCH`. Це запобігає появі випадкових часових міток у двійковому образі сховища параметрів пристрою.

#### Вплив рандомізації хешів у Python (`PYTHONHASHSEED`)

Починаючи з Python 3.3, для захисту від мережевих атак типу "відмова в обслуговуванні" (Hash DoS) інтерпретатор застосовує випадкову сіль під час ініціалізації внутрішньої хеш-функції рядків SipHash. В результаті порядок елементів під час ітерації по словниках `dict` та множинах `set` стає випадковим і змінюється між різними запусками інтерпретатора.

Якщо допоміжний скрипт генерує C-код таблиці ініціалізації периферії або карту констант шляхом обходу словника Python:
```python
# Без PYTHONHASHSEED=0 порядок виводу рядків буде випадковим при кожному запуску
for reg_name, reg_addr in peripheral_map.items():
    emit_header_line(reg_name, reg_addr)
```
це призводить до того, що функції та константи у згенерованому заголовковому файлі записуються в іншому порядку. Компілятор розміщує змінні у пам'яті відповідно до черговості їхнього оголошення, через що фінальний бінарник щоразу змінює свою структуру. Встановлення `PYTHONHASHSEED=0` повністю усуває цю проблему, роблячи поведінку інтерпретатора суворо детермінованою.

#### Нормалізація прав доступу та маски файлової системи (`umask`)

Ще одним прихованим джерелом відмінностей між машинами розробників є маска створення файлів (`umask`). Якщо на одній машині встановлено `umask 0022`, а на іншій `umask 0002`, об'єктні файли та статичні бібліотеки створюються з різними правами доступу (`0644` проти `0664`). Під час пакування архівів або створення ELF-файлів деякі утиліти лінкера переносять ці атрибути у заголовки секцій. Для запобігання цьому у релізному конвеєрі завжди явно задається команда `umask 0022` перед початком будь-яких операцій збірки.

### 3. Специфікація маніфесту релізу: `build-manifest.json`

Маніфест релізу є обов'язковим криптографічним паспортом виробу. Він формалізує всі змінні складального рівняння у вигляді структурованого JSON-документа, що підписується закритим ключем реліз-інженера.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "project": "telemetry-node",
  "release_tag": "v1.4.2",
  "source_date_epoch": 1700000000,
  "git": {
    "commit": "a1b2c3d4e5f60718293a4b5c6d7e8f9012345678",
    "dirty": false,
    "submodules": [
      {
        "path": "components/freertos",
        "commit": "8f7e6d5c4b3a210987654321fedcba0987654321"
      }
    ]
  },
  "builder_environment": {
    "type": "oci-container",
    "image_name": "registry.internal.net/embedded/builder-arm",
    "image_digest": "sha256:3fbc632167424a6d997e7492beeb788b8aa9cc52c80309995537e477e54f073e",
    "archive_filename": "builder-arm-v1.4.2.tar.gz",
    "archive_sha256": "4a5b6c7d8e9f0123456789abcdef0123456789abcdef0123456789abcdef0123"
  },
  "toolchain": {
    "compiler": "arm-none-eabi-gcc",
    "version": "13.2.Rel1",
    "c_standard": "c17",
    "cpp_standard": "c++20",
    "flags": [
      "-ffile-prefix-map=/workspace=.",
      "-fdebug-prefix-map=/workspace=.",
      "-O2",
      "-g3"
    ]
  },
  "artifacts": [
    {
      "name": "firmware.elf",
      "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
      "size_bytes": 524288
    },
    {
      "name": "firmware.bin",
      "sha256": "ca978112ca1bbdcafac231b39a23dc4da786eff8147c4e72b9807785afee48bb",
      "size_bytes": 491520
    }
  ]
}
```

#### Правила валідації полів маніфесту

1. **Поле `git.dirty`:** Мусить мати суворе значення `false`. Будь-яка наявність незбережених змін, локальних файлів чи змінених субмодулів робить реліз недійсним.
2. **Поле `builder_environment.image_digest`:** Обов'язково містить префікс `sha256:` і 64-символьний шістнадцятковий хеш маніфесту OCI-образу. Використання символічних імен без дайджесту заборонено.
3. **Поле `artifacts[].sha256`:** Розраховується безпосередньо над готовими файлами за алгоритмом SHA-256 (FIPS 180-4).

### 4. Інструкція швидкої верифікації бінарників

Для перевірки детермінованості скомпільованого бінарника перед випуском релізу виконується стандартний протокол діагностики:

```bash
# 1. Пошук випадкових хостових шляхів у ELF-файлі
# Очікуваний результат: порожній вивід. Будь-який знайдений шлях означає відсутність -ffile-prefix-map
strings build/firmware.elf | grep -E "/home/|/Users/|/workspace/src"

# 2. Аудит структури статичних архівів бібліотек
# Очікуваний результат: права rw-r--r--, UID 0, GID 0, мітка дати Jan 1 1970
ar tv build/libdrivers.a

# 3. Перевірка відсутності динамічних часових міток препроцесора
# Очікуваний результат: відсутність англомовних трибуквених назв місяців у двійковому образі
strings build/firmware.bin | grep -E "(Jan|Feb|Mar|Apr|May|Jun|Jul|Aug|Sep|Oct|Nov|Dec) [0-9]{1,2} [0-9]{4}"
```

Якщо всі три перевірки повертають очікувані результати, двійковий образ визнається детермінованим і готовим до підписання та довгострокового архівування.
