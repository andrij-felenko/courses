# ⚙️ Практика: компактний рушій анімацій LED на ESP32

## Задача

У темі ми домовилися про головне: анімація — це **функція часу**, описана безрозмірною фазою, а коли ефектів багато, треба **відділити дані ефекту від коду, що його рухає**. Там же ми накидали скелет — структуру `Anim` і єдиний `animTick(millis())`, що проходить масив і посуває кожен ефект. Скелет показує ідею, але до робочого рушія йому ще кілька кроків, і кожен з них — це окрема пастка, на якій ламаються реальні прошивки.

Зберімо тепер рушій по-справжньому. Не «ще один приклад дихання», а маленький рушій, який можна взяти у проєкт і яким керують **ззовні**: запустив ефект на піні, перервав його, поставив усе на паузу, поставив у чергу другий ефект «після того, як добіжить перший». Усе це — неблокувально, для багатьох каналів одночасно, з кадровим часом, що не пливе від кількості ефектів. Конкретно доведеться розв'язати п'ять задач, які скелет лишив відкритими:

- **пінг-понг** — як розвернути фазу назад, не зламавши плавності й не подвоївши код;
- **паузу й відновлення** — як заморозити ефект так, щоб після `resume` він пішов саме з того місця, а не стрибнув уперед на весь час простою;
- **чергу ефектів** — як сказати «спершу блимни тривогою тричі, потім перейди в спокійне дихання» без жодного `delay`;
- **таблиці форм** — як прибрати `sinf`/`powf` із гарячого циклу, щоб сотня каналів вкладалася в кадр;
- **пастки заліза** — переповнення `millis()`, float у циклі, узгодження з гамма-таблицею, активно-низьке підключення.

Усе спирається на фазовий підхід і табличну ідею з теми; гамму-перерахунок ми вже маємо готовим [конвеєром яскравості](root:embedded/pwm-power-control/proj-gamma.md) і тут лише викликаємо.

## Ідея: рушій нічого не знає про конкретний ефект

Стрижень — той самий, що тримає всю вбудовану архітектуру: **рушій тупий, дані розумні**. Рушій уміє рівно одне — взяти запис ефекту, порахувати з мілісекундного лічильника його поточну фазу, прогнати фазу через **форму** (функцію чи таблицю), через **гамму** й виштовхнути готовий duty у ШІМ-канал (в Arduino-ESP32 це `ledcWrite`, в ESP-IDF — `ledc_set_duty`, у STM32 — регістр порівняння таймера). Він не знає, дихання це чи тривожне блимання; усю індивідуальність ефекту несуть **дані** в записі: на якому піні, коли почався, скільки триває, якою формою, що робити на кінці фази. Додати новий вид анімації — це додати запис або нову функцію форми, а не нову гілку в рушії.

З цього випливає головне рішення про **тип фази**. У скелеті фаза була `float` — `(now - start) / (float)duration`. Для одного-двох каналів це ідеально читається. Але float-ділення в циклі, що крутиться для сотні каналів сотні разів на секунду, — рівно та сама вада, що й `powf` у [гаммі](root:embedded/pwm-power-control/proj-gamma.md): десятки тактів там, де має бути один. Тому в робочому рушії фазу ми вестимемо в **цілих** — як ціле число від `0` до `4095` (12 біт, той самий діапазон, що й duty), а float лишимо тільки там, де без нього ніяк. Це не передчасна оптимізація заради краси: на ESP32 з апаратним float різниця помітна вже від кількох десятків каналів, а на ядрах без FPU (RISC-V ESP32-C3, дрібні AVR) float у гарячому циклі — це вирок кадровому часу.

> 🔧 **Навіщо це.** «Тупий рушій + розумні дані» — це не абстрактна краса, а пряма економія праці. Коли замовник скаже «а зробіть, щоб при втраті зв'язку всі індикатори синхронно пульсували червоним», ви не лізете в логіку рушія — ви заповнюєте кілька записів і викликаєте `animStart`. Рушій, написаний один раз правильно, переживає десятки змін вимог, не змінюючись сам.

## Крок 1. Запис ефекту й цілочисельна фаза

Почнімо зі структури. Проти скелета вона підросла — додалися поля для паузи й для пінг-понгу, — але кожне поле має причину, яку ми зараз і розкриємо.

```c
#include <stdint.h>

typedef enum {
    ANIM_OFF = 0,   // слот вільний
    ANIM_ONCE,      // один прохід 0→1 і стоп
    ANIM_LOOP,      // 0→1, стрибок на 0, нескінченно
    ANIM_PINGPONG   // 0→1→0→1… нескінченно, дзеркально
} AnimMode;

typedef uint16_t (*ShapeFn)(uint16_t phase);   // фаза 0..4095 → яскравість 0..4095

typedef struct {
    uint8_t       pin;        // канал LEDC
    AnimMode      mode;
    ShapeFn       shape;      // форма руху
    uint32_t      start;      // millis() запуску (база відліку фази)
    uint32_t      duration;   // тривалість одного проходу фази, мс
    uint32_t      pausedAt;   // millis() моменту паузи; 0 = біжить
    bool          invert;     // активно-низьке підключення
} Anim;

#define ANIM_SLOTS 16
static Anim anims[ANIM_SLOTS];
```

Зверніть увагу на тип форми: `ShapeFn` приймає й повертає `uint16_t` у діапазоні `0..4095`. Жодного float у сигнатурі — форма дістає цілу фазу й віддає цілу яскравість. Це навмисно: уся гаряча дорога «фаза → форма → гамма → duty» тепер ціла наскрізь.

Тепер — **як із мілісекундного лічильника дістати цілу фазу**. Лічильник, що сам собою біжить від старту, є на будь-якому МК: в Arduino це `millis()`, в ESP-IDF — `esp_timer_get_time() / 1000`, у STM32 HAL — `HAL_GetTick()`. Далі в коді ми пишемо `millis()`; на іншій платформі це однорядкова обгортка (крок 6). Скелетна формула `(now - start) / duration` у float давала `0.0..1.0`. Цілий аналог дає `0..4095`:

```c
// скільки мс минуло від старту цього проходу, з урахуванням паузи
static uint32_t elapsed(const Anim *a, uint32_t now) {
    uint32_t ref = (a->pausedAt != 0) ? a->pausedAt : now;
    return ref - a->start;          // беззнакова різниця — переповнення millis безпечне
}

// фаза 0..4095 у межах одного проходу; >4095 означає «прохід скінчився»
static uint32_t phaseRaw(const Anim *a, uint32_t now) {
    uint32_t e = elapsed(a, now);
    return (e << 12) / a->duration;   // e/duration · 4096, цілими
}
```

Розберімо `(e << 12) / a->duration` — це серце цілочисельної фази. Ми хочемо `e / duration`, помножене на `4096`, але в цілих ділення-першим знулило б усе («`5 / 4000 = 0`»). Тому **спершу множимо**: `e << 12` — це `e · 4096`, а вже тоді ділимо на `duration`. Доки `e < duration`, результат лежить у `0..4095`; коли `e` дорівняв `duration`, результат `= 4096` — і це наш сигнал «прохід завершився». Один цілий зсув і одне цілe ділення замість float-операції — і весь діапазон точний до одиниці duty.

Чому саме `<< 12`, тобто множник `4096`? Бо в нас 12-бітний ШІМ і 256-вхідна гамма-таблиця: фаза `0..4095` лягає на duty без втрат і чисто індексує форму. Якби ШІМ був 8-бітний, узяли б `<< 8`. Розрядність фази має збігатися з розрядністю виходу — інакше десь з'явиться зайве масштабування, а з ним і похибка округлення.

**Тиха чесність про переповнення множення.** `e << 12` мусить уміститися в 32 біти. `e` — це мілісекунди від старту проходу; `e << 12` переповнить `uint32_t` приблизно за `2³²/4096 ≈ 1 048 576` мс, тобто за ~17 хвилин одного проходу. Для анімації це нескінченність: жоден ефект не триває 17 хвилин одним проходом (а цикл і пінг-понг рахують фазу в межах одного короткого проходу, не від старту світу). Але якщо колись задумаєте «дуже повільний» ефект на десятки хвилин — рахуйте фазу в `uint64_t` або зменшіть розрядність. Назвати цю межу важливо: мовчазне переповнення — класична причина того, що ефект раптом «смикається» рівно на якійсь тривалості.

## Крок 2. Серце рушія — `animTick` із трьома кінцями фази

Тепер єдина функція, що рухає всі ефекти. У темі вона була накидана; зберімо повну, з усіма трьома поведінками на кінці фази й з акуратним пінг-понгом.

Уся хитрість — у тому, що `phaseRaw` повертає число `0..4096`, де `4096` означає «прохід вийшов за край». Що робити з цим краєм — і є різниця між `ONCE`, `LOOP` та `PINGPONG`.

```c
extern uint16_t gammaLUT[256];     // готова таблиця гамми з конвеєра яскравості

void animTick(uint32_t now) {
    for (int i = 0; i < ANIM_SLOTS; i++) {
        Anim *a = &anims[i];
        if (a->mode == ANIM_OFF) continue;       // вільний слот — пропустити
        if (a->pausedAt != 0) continue;          // на паузі — нічого не рухаємо

        uint32_t raw = phaseRaw(a, now);         // 0..4096
        uint16_t phase;                          // підсумкова фаза 0..4095

        if (raw <= 4095) {
            phase = (uint16_t)raw;               // прохід ще триває
        } else {
            // прохід дійшов до кінця — розгалуження за режимом
            switch (a->mode) {
                case ANIM_ONCE:
                    phase = 4095;                // зафіксувати кінець…
                    a->mode = ANIM_OFF;          // …і звільнити слот
                    break;
                case ANIM_LOOP:
                    a->start = now;              // новий прохід від нуля
                    phase = 0;
                    break;
                case ANIM_PINGPONG: {
                    // два проходи на період: парний — вперед, непарний — назад
                    uint32_t cycle = (elapsed(a, now)) / a->duration;   // 0,1,2,…
                    uint32_t pos   = (elapsed(a, now)) % a->duration;   // у межах проходу
                    uint32_t fwd   = (pos << 12) / a->duration;         // 0..4095
                    phase = (cycle & 1) ? (uint16_t)(4095 - fwd)        // назад: дзеркало
                                        : (uint16_t)fwd;               // вперед
                    break;
                }
                default:
                    phase = 0;
            }
        }

        uint16_t bright = a->shape(phase);       // форма руху: 0..4095
        uint8_t  idx    = (uint8_t)(bright >> 4);// 0..4095 → 0..255 для гамми
        uint16_t duty   = gammaLUT[idx];         // корекція ока
        if (a->invert) duty = 4095 - duty;       // активно-низьке підключення
        ledcWrite(a->pin, duty);
    }
}
```

Тепер найважливіше — **пінг-понг**, бо саме його найчастіше пишуть з помилкою. Наївний підхід: дійшли до кінця, поміняли місцями `0` і `1` і пустили назад. Він майже працює, але має дві біди — стик і дублювання логіки кінця. Тому ми робимо інакше й чистіше: **дзеркалимо фазу**, а не перезапускаємо ефект.

Думка така. Один «період» пінг-понгу — це **два** проходи фази: туди (`0→1`) і назад (`1→0`). Поділивши повний час від старту на `duration`, дістаємо номер проходу: парний (`0, 2, 4…`) — рух уперед, непарний (`1, 3, 5…`) — рух назад. Остача від ділення дає положення **всередині** поточного проходу. Для парного проходу фаза — це просто `fwd`; для непарного — її **дзеркало** `4095 - fwd`. Усе. Жодного перезапуску, жодного окремого стану «напрямок»: напрямок **обчислюється** з часу. Це той самий стиль, що й уся анімація — «не зберігай стан, обчислюй його з годинника».

Чому дзеркало плавне, а не сіпається на стику? Бо на межі проходів `fwd` плавно доходить до `4095` (кінець руху вперед), і відразу наступний прохід — непарний — стартує з `4095 - 0 = 4095` (початок руху назад). Значення збігається: ефект **доходить** до піку й **звідти ж** іде вниз, без стрибка й без подвоєного кадру на вершині. Якби ми перезапускали `start = now`, ми б отримали або зайвий кадр на піку, або мікророзрив — типову «гикавку» дихання.

**Окрема нотатка про `ONCE`.** Помітьте: `ANIM_ONCE` на кінці виставляє `phase = 4095` (щоб останній кадр був саме фінальним рівнем, а не нулем) і відразу гасить слот — `a->mode = ANIM_OFF`. Тут легко помилитися двічі. Якщо звільнити слот **до** виставлення фінального кадру — діод смикнеться в нуль на останньому кроці. Якщо не звільнити зовсім — слот залишиться «зайнятим назавжди», і за кілька подій усі 16 слотів забʼються мертвими ефектами. Самозвільнення `ONCE` — це і є те, що робить чергу ефектів можливою (про неї — нижче).

Перетворення `bright >> 4` теж не випадкове: `bright` має 12 біт (`0..4095`), а гамма-таблиця 256-вхідна, тож беремо старші 8 біт. Це той самий компроміс, що в [гаммі](root:embedded/pwm-power-control/proj-gamma.md): 256 вузлів кривої — більше ніж досить для ока, а таблиця на 4096 значень коштувала б 8 кБ замість 512 байт. Якщо колись захочете повної 12-бітної гамми без проміжного звуження — зробите таблицю на 4096 і приберете зсув; для світлодіодів це майже ніколи не потрібно.

## Крок 3. Форми як передраховані таблиці

Тепер форми. У темі дихання робив `cosf`, easing — `smoothstep` через `3t²−2t³`. Обидві — float, обидві гарячі. Лік той самий, що й для гамми: **порахувати форму один раз у `setup()` і далі лише читати**. Різниця в тому, що тут таблиця індексується **фазою**, а не рівнем, і повертає вже форму руху.

```c
#include <math.h>

// таблиці форм: фаза-індекс 0..255 → яскравість 0..4095
static uint16_t breatheTbl[256];   // плавне дихання (косинус)
static uint16_t easeTbl[256];      // smoothstep — живий розгін-гальмування

void buildShapeTables(void) {
    for (int i = 0; i < 256; i++) {
        float t = i / 255.0f;                       // фаза 0..1
        // дихання: (1 - cos(2πt)) / 2 → 0→1→0 за один прохід
        float b = (1.0f - cosf(t * 2.0f * (float)M_PI)) * 0.5f;
        breatheTbl[i] = (uint16_t)lroundf(b * 4095.0f);
        // smoothstep: повільно на краях, швидше всередині
        float s = t * t * (3.0f - 2.0f * t);
        easeTbl[i]   = (uint16_t)lroundf(s * 4095.0f);
    }
}

// функції форми, які кладемо в Anim.shape — лише індексація, жодного float
uint16_t shapeBreathe(uint16_t phase) { return breatheTbl[phase >> 4]; }
uint16_t shapeEase(uint16_t phase)    { return easeTbl[phase >> 4]; }
uint16_t shapeLinear(uint16_t phase)  { return phase; }            // форма = фаза
uint16_t shapeBlink(uint16_t phase)   { return (phase < 2048) ? 4095 : 0; }  // прямокутник
```

Дрібниця, на якій спотикаються: індекс у таблицю — `phase >> 4`, бо фаза має 12 біт, а таблиця 256-вхідна. Той самий зсув, що й для гамми, з тієї ж причини. `shapeLinear` і `shapeBlink` навіть таблиці не потребують — вони й так цілі й дешеві; таблиця потрібна лише там, де інакше був би `sin`/`pow`/`exp`.

Тут варто чесно зважити, **коли таблиця форми справді потрібна**. Для одного діода `cosf` раз на кадр — копійки, і таблиця лише ускладнює код. Виграш зʼявляється, коли каналів багато: сто діодів × `cosf` на кадр × 60 кадрів/с — це вже тисячі float-операцій щосекунди, і вони конкурують за такти з усім іншим у пристрої. Правило просте: **один-два канали — рахуй на льоту, десятки-сотні — таблиця**. Це дзеркало того самого рішення, що ми зробили в гаммі, лише застосоване до форми руху.

Чому 256 вузлів вистачає й для дихання? Бо око все одно бачить дихання через гамму, а 256 рівнів фази дають крок ~0.4% — дрібніше, ніж людина здатна вловити в плавному русі. Якщо комусь привидиться «сходинка», її дає не таблиця форми, а замала розрядність **виходу** (про що — у [гаммі](root:embedded/pwm-power-control/proj-gamma.md)), і лікується вона більшою розрядністю ШІМ, а не більшою таблицею.

> 🔧 **Навіщо це.** Передрахована форма — це фіксований **кадровий бюджет**, що не залежить від виду ефекту. Дихання, easing, складна крива з `exp` — у гарячому циклі всі коштують однаково (одна індексація), бо вся їхня складність уже з'їдена один раз у `setup()`. Це дає передбачуваний час кадру навіть для стрічки на сотні каналів — а передбачуваність часу і є те, заради чого існує неблокувальний підхід.

## Крок 4. Керування ефектом: запуск, пауза, відновлення

Рушій крутиться сам; тепер дамо назовні ручки, якими ним керують. Перша — запуск ефекту в перший вільний слот:

```c
// повертає індекс слота або -1, якщо всі зайняті
int animStart(uint8_t pin, AnimMode mode, ShapeFn shape,
              uint32_t durationMs, bool invert) {
    for (int i = 0; i < ANIM_SLOTS; i++) {
        if (anims[i].mode == ANIM_OFF) {
            anims[i] = (Anim){ .pin = pin, .mode = mode, .shape = shape,
                               .start = millis(), .duration = durationMs,
                               .pausedAt = 0, .invert = invert };
            return i;
        }
    }
    return -1;   // слотів немає — ефект не запущено (а не «тихо проковтнуто»)
}
```

Тепер **пауза й відновлення** — і саме тут ховається пастка, через яку «пауза» у багатьох прошивках працює неправильно. Наївно: на паузі просто не викликати `animTick`. Але фаза рахується від `start` через `millis()`, а `millis()` **не зупиняється**. Тож коли ви відновите ефект, він порахує фазу від реального часу — і **стрибне** вперед рівно на стільки, скільки тривала пауза. Поставили дихання на паузу на хвилину — після `resume` воно перескочить на хвилину вперед, наче паузи й не було.

Лік — **зсунути базу відліку**. Заморожуючи, запам'ятовуємо момент паузи (`pausedAt`). Відновлюючи, **посуваємо `start` уперед** рівно на тривалість простою — і фаза продовжиться з того самого місця, де її спинили:

```c
void animPause(int idx) {
    if (idx < 0 || anims[idx].mode == ANIM_OFF) return;
    if (anims[idx].pausedAt == 0)
        anims[idx].pausedAt = millis();      // зафіксували момент заморозки
}

void animResume(int idx) {
    if (idx < 0 || anims[idx].mode == ANIM_OFF) return;
    if (anims[idx].pausedAt != 0) {
        uint32_t frozen = millis() - anims[idx].pausedAt;  // скільки простояли
        anims[idx].start += frozen;          // посунули базу — фаза не стрибне
        anims[idx].pausedAt = 0;             // знову біжить
    }
}

void animStop(int idx) {
    if (idx >= 0) anims[idx].mode = ANIM_OFF;   // звільнити слот негайно
}
```

Зверніть увагу, як це узгоджено з `elapsed()` з кроку 1: поки `pausedAt != 0`, `elapsed` рахує час **до моменту паузи**, тож навіть якщо хтось випадково викличе `phaseRaw` на паузі, фаза стоятиме. А `animResume` зсувом `start` робить так, що `now - start` після відновлення дорівнює тому ж `elapsed`, що був до паузи. Дві частини — заморозка в `elapsed` і зсув у `resume` — тримають фазу нерухомою разом; прибери одну, і пауза «потече».

Це той самий прийом, що й скрізь у безперервному часі: ти не зупиняєш годинник (його не зупинити), ти **зміщуєш точку відліку**. Так само працює пауза в секундомірах, у відеоплеєрах, у будь-якому таймері поверх монотонного лічильника.

## Крок 5. Черга ефектів — «спершу це, потім те»

Найкорисніше для реального пристрою: послідовності. «Блимни тривогою тричі, **потім** перейди в спокійне дихання». «Засвіти індикатор зарядки, **коли** добіжить заставка». Зробити це через `delay` — знову вбити цикл; зробити правильно — поставити ефекти **в чергу** й перемикати їх у тому ж `animTick`, нічого не блокуючи.

Ідея спирається на властивість `ANIM_ONCE`, яку ми вже заклали: одноразовий ефект сам **звільняє** слот, дійшовши кінця. Отже, черга — це список ефектів, з якого рушій бере наступний щоразу, коли поточний звільнив слот. Опишімо крок черги й саму чергу:

```c
typedef struct {
    AnimMode mode;
    ShapeFn  shape;
    uint32_t durationMs;
    uint8_t  repeats;     // скільки разів повторити цей крок (для ONCE)
} AnimStep;

typedef struct {
    uint8_t        pin;
    bool           invert;
    const AnimStep *steps;   // масив кроків (зазвичай у флеш, const)
    uint8_t        count;    // скільки кроків
    uint8_t        cur;      // поточний крок
    uint8_t        left;     // скільки повторів поточного кроку лишилось
    int            slot;     // який слот зайнято (-1 = нічого не грає)
} AnimQueue;

static AnimQueue queues[4];   // до чотирьох незалежних послідовностей
```

Тепер двигун черги. Раз на цикл ми дивимося на кожну чергу: якщо її слот звільнився (ефект добіг), беремо наступний крок або наступний повтор. Жодного чекання — лише перевірка стану:

```c
static void queueAdvance(AnimQueue *q) {
    if (q->cur >= q->count) return;              // черга вичерпана

    bool slotFree = (q->slot < 0) || (anims[q->slot].mode == ANIM_OFF);
    if (!slotFree) return;                        // поточний ще грає — чекаємо без блокування

    if (q->left == 0) {                           // повтори поточного кроку скінчились
        q->cur++;                                 // → наступний крок
        if (q->cur >= q->count) { q->slot = -1; return; }  // черга добігла
        q->left = q->steps[q->cur].repeats;
    }

    const AnimStep *s = &q->steps[q->cur];
    q->slot = animStart(q->pin, s->mode, s->shape, s->durationMs, q->invert);
    if (q->left > 0) q->left--;                    // зарахували один повтор
}

void queueTick(void) {
    for (int i = 0; i < 4; i++) queueAdvance(&queues[i]);
}

// запустити послідовність
void queueStart(int i, uint8_t pin, bool invert,
                const AnimStep *steps, uint8_t count) {
    queues[i] = (AnimQueue){ .pin = pin, .invert = invert, .steps = steps,
                             .count = count, .cur = 0,
                             .left = count ? steps[0].repeats : 0, .slot = -1 };
}
```

І типова послідовність-сценарій — у флеш-пам'яті, бо вона стала:

```c
// тривога: 3 коротких блимання → перехід у спокійне дихання назавжди
const AnimStep alarmThenCalm[] = {
    { ANIM_ONCE,     shapeBlink,   200,  3 },   // блимнути 200 мс, тричі
    { ANIM_PINGPONG, shapeBreathe, 3000, 1 },   // далі дихати (нескінченно)
};
```

Як це грає в часі: `queueAdvance` бачить вільний слот, запускає перше блимання (`ONCE`, 200 мс). Через 200 мс блимання саме гасить слот; на наступному `queueTick` `queueAdvance` бачить вільний слот, `left` ще `> 0`, тож запускає **те саме** блимання знову. Так тричі. Коли `left` дійде нуля, `cur` зростає до кроку дихання — `PINGPONG`, який слот **не звільняє** (він нескінченний), тож черга на ньому й застигає назавжди, спокійно дихаючи. Жодного `delay`, жодного блокування — лише перевірки стану раз на цикл.

Тонкість, яку легко проґавити: для `PINGPONG`/`LOOP` поле `repeats` втрачає сенс (вони не кінчаються самі), тож такий крок має бути **останнім** у черзі — після нього нічого не зіграє, бо слот не звільниться. Якщо потрібна послідовність із нескінченним кроком посередині, додають **зовнішній** сигнал переходу (подія, таймаут) і викликають `queueStart` наново — але це вже логіка застосунку, а не рушія.

## Крок 6. Складання докупи

Лишилося показати, як усе живе разом у головному циклі. Увесь код вище — звичайний C, він не знає нічого про плату; із платформою рушій стикається рівно у двох точках: `millis()` (звідки час) і `ledcWrite()` (куди duty). Тому порт зводиться до двох обгорток плюс власного способу крутити цикл. Звертаю увагу: **обидва** тіки — і `animTick`, і `queueTick` — викликаються щоразу, безумовно, і цикл лишається вільним для всього іншого пристрою.

## Складність і пастки на МК

Рушій маленький, але кожна з пасток нижче колись комусь коштувала вечора з осцилографом. Пройдімося прицільно.

**Переповнення лічильника часу — і чому наш код його переживає.** Будь-який 32-бітний лічильник мілісекунд обнуляється раз на ~49.7 діб (`2³²` мс): так поводиться і `millis()` (що прямо зафіксовано в документації Arduino-ядра ESP32), і `HAL_GetTick()` у STM32. Уся наша арифметика часу — `now - start`, `now - pausedAt`, `millis() - pausedAt` — це **різниці беззнакових** `uint32_t`. Беззнакова різниця коректна **через** момент обнулення: якщо `start` був перед обнуленням, а `now` після, `now - start` за модульною арифметикою дає правильний інтервал. Пастка зʼявляється рівно тоді, коли хтось пише «зрозуміліше» — `now >= start + duration`. На переповненні `start + duration` теж переповнюється, нерівність бреше, і ефект або застигає, або смикається раз на 49 діб. Правило залізне: **порівнюй і віднімай різниці, ніколи не складай момент із інтервалом**. Це той самий урок, що проходить крізь усю неблокувальну логіку.

**Float у гарячому циклі.** Ми прибрали його двічі: з фази (цілий зсув-ділення замість float-ділення) і з форм (таблиці замість `cosf`/`powf`). Лишилося єдине ціле ділення на канал у `phaseRaw` — і навіть його при потребі (десятки тисяч оновлень/с) можна замінити, якщо `duration` зробити степенем двійки й ділення стане зсувом. Для типового пристрою це зайве, але знати межу варто. Загальне правило: у циклі, що крутиться сотні разів на секунду × десятки каналів, **кожна float-операція множиться на цей добуток** — і те, що для одного діода непомітне, для стрічки зʼїдає кадр. На ядрах без FPU (ESP32-C3 на RISC-V, AVR) float ще й емулюється програмно — там це не сповільнення, а катастрофа.

**Узгодження з гамма-таблицею.** Три числа мусять збігатися: розрядність ШІМ (12 біт — `ledcAttach(…, 12)` в Arduino, `LEDC_TIMER_12_BIT` в ESP-IDF, `ARR = 4095` у таймері STM32), верх діапазону фази/форми (`4095`) і вхід гамми (`>> 4` до `0..255`). Розійдуться — отримаєте або обрізану яскравість (форма дає `4095`, а ШІМ 8-бітний — усе вище `255` злипнеться в максимум), або тьмяний максимум (форма дає `255`, а ШІМ 12-бітний чекає `4095`). І порядок незмінний: **фаза → форма (easing) → гамма → duty**, як ми розвели в темі. Гамма стоїть **останньою**, бо вона калібрує око під уже сформований рух; поставите її перед формою — і easing зігне вже спотворену криву, рух стане неприродним. `shape` віддає «скільки світла за відчуттям», `gammaLUT` перекладає це в «скільки duty», і тільки в цьому порядку.

**Активно-низьке підключення.** Якщо діод висить катодом до піна (ключ замикає на землю, активний рівень — низький), повна шкала світить навпаки: `duty = 0` дає максимум, `4095` — темряву. Прапорець `invert` у записі й рядок `duty = 4095 - gammaLUT[idx]` це лагодять — але **інверсія йде після гамми**, на готовому duty, а не до неї. Інвертуєте до гамми — крива перекинеться неправильно, бо гамма несиметрична (`gammaLUT[255-x] ≠ 4095-gammaLUT[x]`), і «дихання» вийде кособоким: швидко гасне, повільно світить. Дрібниця в один знак, а наслідок видно оком одразу. Те, з якого боку підключений діод, диктує сама [схема ввімкнення](root:embedded/pwm-power-control), і прапорець `invert` лише відображає її в коді.

**Скінченність слотів і витоки.** Слотів `ANIM_SLOTS` рівно стільки, скільки заклали; `animStart` чесно повертає `-1`, коли вільних немає, — і це краще, ніж тихо нічого не зробити. Класичний витік: запускати `ANIM_ONCE` на кожну подію, але мати десь у логіці `ANIM_LOOP`/`ANIM_PINGPONG`, що **ніколи** не звільняє слот. За кілька подій вільні слоти скінчаться, нові ефекти мовчки не запустяться (якщо не перевіряти `-1`). Тому: нескінченні ефекти — лічені й керовані явним `animStop`; одноразові — самозвільняються; повернення `-1` — перевіряти бодай у налагодженні (`if (animStart(…) < 0)` і рядок у лог: `Serial.println` в Arduino, `ESP_LOGW` в ESP-IDF).

**Скидання при перезапуску анімації того самого піна.** Якщо запустити новий ефект на піні, де вже грає старий (у іншому слоті), обидва писатимуть у той самий `ledcWrite` — і виграє той, чий слот пізніший у масиві. Видно як «мерехтіння» чи «боротьбу» двох ефектів. Рушій навмисно не веде мапи «пін → слот» заради простоти; якщо вам потрібен суворий «один ефект на пін», або зупиняйте старий перед запуском нового (знайти його слот і `animStop`), або додайте перевірку в `animStart`. Для більшості пристроїв досить дисципліни «не пускати два на один пін».

**Апаратний fade поряд із рушієм.** Як ми розібрали в темі, ESP32 уміє апаратний перехід duty (`ledcFade`/`ledc_set_fade_with_time`), але з жорстким обмеженням: **поки апаратний fade на каналі триває, програмний `ledcWrite` на цьому ж каналі чекатиме його кінця** (це прямо зафіксовано в ESP-IDF: для ESP32 зміна duty під час fade на тому ж каналі неможлива). Тому **не змішуйте** на одному піні апаратний fade і наш рушій: або канал «залізний» (простий перехід, ваш рушій його не чіпає), або «програмний» (рушій рахує форму сам). Змішаєте — отримаєте `ledcWrite` рушія, що тихо ігнорується посеред fade, і ефект, який «залипає». Розподіл «який пін — чий» робіть на старті, як і весь вибір «залізо чи код».

## Підсумок

Рушій вийшов маленький — структура, `animTick`, дрібні ручки керування й черга, — але він закриває всі п'ять задач, що скелет із теми лишив відкритими, і робить це **без жодного `delay`**, для багатьох каналів, з кадровим часом, що не пливе від кількості ефектів. Кожне рішення тут — пряме продовження двох наскрізних думок курсу: **дивись на годинник, не чекай** (уся фаза рахується з `millis()` беззнаковими різницями, переповнення безпечне) і **відділяй дані від рушія** (вид ефекту несуть запис і функція форми, рушій лишається тупим і незмінним).

Три речі винесіть як готові прийоми, що переживуть цей конкретний код. **Пінг-понг — це дзеркало фази, а не перезапуск**: напрямок обчислюється з номера проходу, тож стик виходить плавним сам собою. **Пауза — це зсув бази відліку, а не зупинка годинника**: заморозив у `elapsed`, посунув `start` на відновленні — і фаза не стрибне. **Черга — це ланцюг самозвільнень `ONCE`**: кожен одноразовий ефект, гаснучи, звільняє слот для наступного, і послідовність грає сама, нічого не блокуючи. Ці три прийоми — дзеркало того самого способу мислення, що й по всьому курсу: стан не зберігай, де можна **обчислити** його з часу; час не зупиняй, а **зміщуй** точку відліку; складне збирай із простих самодостатніх частин, що знають лише свій маленький обовʼязок.
