# П'ять способів, якими канал псує дані

<preknowlist>
- [Надійність даних](root:embedded/data-reliability) — чому фізичний рівень ніколи не дає стовідсоткової гарантії і як будується багатошаровий захист.
- [Кадр UART](root:com-devices/uart-frame) — як передаються окремі байти, старт- і стоп-біти, чому шина не знає меж повідомлень.
- [Контрольні суми CRC](root:com-modulation/crc) — поліноміальне ділення у скінченних полях та виявлення помилок.
- [Пакетна помилка](root:com-modulation/burst-error) — чому завади вбивають не поодинокі біти, а цілі пачки.
- [Стратегії ARQ](root:embedded/arq-strategies) — підтвердження, таймери повтору та віконні протоколи передачі.
- [Ідемпотентність](root:sf-distributed/idempotency) — чому виконання повтореної команди не повинно ламати стан виконавчого вузла.
</preknowlist>

На лабораторному столі зв'язок між двома мікроконтролерами по UART чи радіомодулю виглядає ідеальним: дроти короткі, живлення чисте від лабораторного джерела, ефір спокійний. Байти, записані у передавач функцією відправки, байт у байт зчитуються приймачем. Але варто перенести той самий пристрій у реальні польові умови — у шафу автоматики поруч із 15-кіловатним частотним інвертором двигуна або на раму квадрокоптера — як ілюзія «надійної труби для байтів» миттєво руйнується. Електромеханічний клапан раптом відкривається двічі на одну команду оператора, польотний контролер зависає через пошкоджені координати, пакети телеметрії склеюються у нерозбірливу суміш, а критичні кадри аварійної зупинки безслідно зникають.

Розробники-початківці зазвичай намагаються вирішити всі негаразди каналу єдиною дією — додаванням простої контрольної суми наприкінці повідомлення. Проте фізичний канал зв'язку деградує не в один, а в **п'ять принципово різних способів**. Кожен із цих режимів має власну фізичну природу, породжує специфічні збої в логіці прошивки й вимагає свого окремого математичного та алгоритмічного механізму захисту. Якщо канальний протокол не закриває хоча б один із п'яти векторів, система залишається вразливою до важких відмов.

![П'ять руйнівних режимів фізичного каналу зв'язку](/root/course/embedded/piat-sposobiv-iakymy-kanal-psuie-dani/img/five-channel-modes.svg)
*П'ять руйнівних режимів фізичного каналу зв'язку: спотворення бітів, втрата пакетів, дублювання повідомлень, перевпорядкування та фрагментація байтового потоку.*

## 1. Анатомія п'яти руйнівних режимів каналу

Коли сигнал залишає вихідний буфер передавача, він перетворюється з дискретної абстракції на неперервний аналоговий процес — напругу на мідній крученій парі або електромагнітне поле в ефірі. На цьому шляху потік даних потрапляє під вплив фізичних явищ, які призводять до п'яти руйнівних режимів:

1. **Спотворення бітів (Bit Flipping & Burst Errors)**. Окремі нулі перетворюються на одиниці й навпаки. Це трапляється через тепловий шум приймача, падіння відношення сигнал/шум (SNR) на великих дистанціях, а також через потужні комутаційні наводки від силових ключів (імпульси `dI/dt`), які спотворюють цілі пачки сусідніх бітів поспіль.
2. **Втрата пакетів (Packet Loss / Drop)**. Повідомлення надсилається передавачем, але приймач не реєструє взагалі нічого. Причиною стає або глибоке радіозавмирання, коли амплітуда сигналу падає нижче чутливості демодулятора, або колізія в напівдуплексному ефірі, або апаратне скидання кадру через переповнення черги вхідного буфера FIFO мікроконтролера під час виконання важкого переривання.
3. **Дублювання повідомлень (Packet Duplication)**. Приймач успішно отримує повідомлення й виконує дію, проте зворотний кадр підтвердження (ACK) губиться на зворотному шляху. Передавач за таймаутом вважає кадр втраченим і надсилає його повтор. Якщо приймач не має спеціального механізму дедуплікації, він приймає повторний кадр як нову унікальну команду, що призводить до подвійного виконання небезпечних дій (наприклад, повторного кроку крокового двигуна).
4. **Перевпорядкування (Out-of-Order Delivery)**. Послідовність пакетів `[1, 2, 3]` надходить на приймач як `[1, 3, 2]`. Таке явище виникає у комірчастих мережах (mesh-топологіях), де пакети подорожують різними фізичними маршрутами з різною затримкою, або в каналах із паралельними повторними спробами (ARQ), коли повторений старий пакет надходить пізніше за щойно надісланий новий.
5. **Розрізання та склеювання байтового потоку (Stream Fragmentation & Coalescing)**. Потокові шини (UART, RS-485, USB-CDC або сокети TCP) не мають вбудованого поняття «межа повідомлення». Байти передаються неперервно. Якщо передавач відправив кадр довжиною 64 байти, приймач може прочитати його двома частинами (16 байтів у першому перериванні DMA й 48 байтів у другому) або, навпаки, вичитати два склеєних пакети по 30 байтів за один спільний системний виклик `read()`.

Розгляньмо кожен із цих п'яти режимів, їхній фізико-математичний механізм та побудову надійного захисту.

## 2. Спотворення бітів: математична стійкість CRC проти сплесків

Найперший ворог даних — фізичний шум. У реальних провідних лініях та радіоканалах спотворення рідко бувають поодинокими й рівномірно розподіленими. Перемикання реле, робота колекторного двигуна або розряд статичної електрики породжують високочастотний сплеск тривалістю від одиниць до сотень мікросекунд. На швидкості шини 115200 бод один байт передається за 86.8 мікросекунд. Отже, навіть короткочасна завада тривалістю 200 мікросекунд спотворює від двох до трьох байтів поспіль — це явище має назву **пакетна помилка (burst error)**.

### Чому проста адитивна сума (Checksum) не рятує

Широко вживана початківцями 8-бітна або 16-бітна сума додавання (наприклад, побайтове додавання за модулем 256):

```
S = (b[0] + b[1] + ... + b[n-1]) mod 256
```

має дві критичні математичні вразливості:

1. **Комутативність операції додавання**. Адитивна сума не залежить від порядку байтів: сума `[0x12, 0x34]` абсолютно тотожна сумі `[0x34, 0x12]`. Якщо внаслідок наводки або зсуву покажчиків байти поміняються місцями, сума зійдеться, і пошкодження залишиться непоміченим.
2. **Парні компенсуючі інверсії бітів**. Якщо завада збільшила значення одного байта на величину `+k` (наприклад, перевернула біт 0 у 1) і водночас зменшила значення сусіднього байта на `-k` (перевернула біт 1 у 0), загальна сума блоку залишиться незмінною. Ймовірність пропуску подвійних бітових помилок у таких контрольних сум неприпустимо висока.

### Математика циклічного надлишкового коду (CRC)

Надійним інженерним стандартом контролю цілісності є **циклічний надлишковий код (Cyclic Redundancy Check, CRC)**. Математично CRC базується на операції ділення многочленів у скінченному полі `GF(2)` (полі Галуа з двох елементів 0 і 1), де операції додавання та віднімання збігаються з порозрядним виключним АБО (`XOR`), а перенесення розрядів відсутнє.

Блок даних розглядається як двійковий поліном `M(x)`, коефіцієнтами якого є біти повідомлення. Передавач множить `M(x)` на `x^r` (зсуває дані ліворуч на `r` бітів, де `r` — ступінь твірного полінома `G(x)`) і ділить отриманий поліном на фіксований стандартизований твірний поліном `G(x)`. Остача від цього ділення `R(x)` є контрольним кодом CRC:

```
M(x) * x^r = Q(x) * G(x) + R(x)   [ділення многочленів у GF(2)]
R(x) = (M(x) * x^r) mod G(x)      [контрольна сума CRC ступеня r]
```

Кадр, що надсилається в лінію, має вигляд `T(x) = M(x) * x^r + R(x)`. Оскільки у полі `GF(2)` додавання еквівалентне відніманню, поліном переданого кадру `T(x)` ділиться на твірний поліном `G(x)` **націло без остачі**:

```
T(x) mod G(x) = (Q(x) * G(x) + R(x) + R(x)) mod G(x)   [підстановка кадру T(x) = M(x)*x^r + R(x)]
              = (Q(x) * G(x) + 0) mod G(x)              [у полі GF(2) додавання R(x) + R(x) дає 0]
              = 0                                       [перший доданок ділиться на G(x) націло]
```

Якщо під час проходження каналом до кадру додається вектор помилок `E(x)`, прийнятий сигнал стає `T'(x) = T(x) + E(x)`. Приймач обчислює остачу від ділення `T'(x)` на `G(x)`:

```
T'(x) mod G(x) = (T(x) + E(x)) mod G(x)   [прийом сигналу разом із вектором завади E(x)]
               = (0 + E(x)) mod G(x)      [оскільки неушкоджений кадр T(x) ділиться націло]
               = E(x) mod G(x)            [залишок залежить суто від структури завади]
```

Помилка залишиться непоміченою приймачем лише в одному випадку: якщо сам вектор помилки `E(x)` ділиться на `G(x)` без остачі. Грамотний вибір полінома `G(x)` ступеня `r` гарантує суворі математичні властивості виявлення спотворень:

- **100% поодиноких бітових помилок**: якщо поліном `G(x)` містить щонайменше два ненульові члени (що виконується для всіх стандартних CRC), жоден однобітний вектор `E(x) = x^k` не ділиться на `G(x)`.
- **100% подвійних бітових помилок**: за умови, що довжина блоку даних не перевищує період твірного полінома.
- **100% будь-яких непарних кількостей бітових помилок**: якщо поліном `G(x)` містить у собі множник `(x + 1)`.
- **100% будь-яких пакетних спалахів (bursts) довжиною `L <= r`**: якщо довжина пакета спотворених бітів не перевищує ступінь полінома (16 бітів для CRC-16 або 32 біти для CRC-32), помилка виявляється завжди без винятків.
- **Для спалахів довжиною `L = r + 1`**: ймовірність пропуску становить лише `2^(-(r - 1))` (для CRC-16 це `1 / 32768 = 0.003%`, для CRC-32 — `1 / 2^31 = 4.65 * 10^(-10)`). Для спалахів довжиною `L > r + 1` ймовірність пропуску становить `2^(-r)`.

Для вбудованих систем промислової автоматики й польотних контролерів стандартом де-факто є поліном **CRC-16-CCITT** (`G(x) = x^16 + x^12 + x^5 + 1`, шістнадцяткове представлення `0x1021`) або **CRC-32-IEEE 802.3** (`0x04C11DB7`).

### Детекція (CRC) проти прямого виправлення (FEC)

Коли контрольна сума виявляє пошкодження, система має два шляхи: **попросити повторну передачу (ARQ)** або **виправити пошкоджені біти на місці без перепитування (Forward Error Correction, FEC)**.

- **Коди Хеммінга**: додають логічні біти парності за геометричним принципом матриць розбиття простору, дозволяючи однозначно локалізувати й інвертувати назад один пошкоджений біт (SECDED — Single Error Correction, Double Error Detection). Вони вкрай ефективні для захисту пам'яті SRAM/Flash від космічних часток (SEU), проте безсилі проти пакетних спалахів на лініях зв'язку, де спотворюються кілька сусідніх бітів.
- **Коди Ріда-Соломона (Reed-Solomon, RS)**: оперують не окремими бітами, а символами (байтами) у полі Галуа `GF(2^8)`. Додавання `2t` надлишкових перевірочних байтів дозволяє гарантовано виправити до `t` довільно пошкоджених байтів у блоці. Якщо спалах завади повністю спотворює 4 байти поспіль, код `RS(255, 247)` з `2t = 8` надлишковими байтами відновить вихідне повідомлення на 100%.

**Інженерний вибір між CRC та FEC**: пряме виправлення (FEC) вимагає суттєвих обчислювальних витрат мікроконтролера та постійно споживає від 5% до 30% пропускної здатності каналу під надлишкові байти корекції. Тому у двосторонніх мережах із низькою затримкою (UART, RS-485, CAN, локальний радіоканал) застосовують зв'язку **CRC + повторний запит (ARQ)**: кадр передається чистим із крихітним оверхедом CRC (2 байти), а повтор запитується лише за потреби. FEC стає безальтернативним лише тоді, коли зворотний канал зв'язку відсутній (односпрямований радіомаяк), або затримка поширення сигналу RTT настільки велика, що очікування повтору ламає контур керування в реальному часі.

## 3. Втрата та дублювання: детерміноване квитування

Другий і третій руйнівні режими каналу нерозривно пов'язані між собою через механізм зворотного зв'язку.

### Чому пакети губляться

Втрата пакета — це ситуація, коли передавач виконав трансляцію, але на стороні приймача не виникло жодної валідної події прийому. Фізичні причини:
1. **Згасання рівня сигналу нижче порогу чутливості (Sensitivity Threshold)**. У радіоефірі напруженість поля спадає пропорційно квадрату або четвертому ступеню відстані, а також зазнає багатопроменевого завмирання Релея. Якщо енергія сигналу на біт падає нижче рівня шумів, демодулятор не здатний зафіксувати преамбулу.
2. **Колізії в напівдуплексній шині**. На шині RS-485 або в ефірі Wi-Fi/LoRa при одночасній спробі двох вузлів почати передачу рівні сигналів накладаються, перетворюючи корисні пакети на нерозпізнаваний шум для всіх учасників мережі.
3. **Апаратне скидання черги FIFO (Buffer Overflow)**. Мікроконтролер приймача обслуговує тривале критичне переривання інвертора чи запису у Flash-пам'ять. Якщо в цей час UART FIFO апаратного модуля заповнюється до краю (наприклад, 16 або 64 байти), наступні вхідні байти безповоротно скидаються апаратурою з встановленням прапорця `Overrun Error (OE)`.

### Парадокс дублювання повідомлень

Для боротьби з втратою пакетів застосовують механізм **підтвердження доставки (Acknowledgement, ACK)** та **таймаут повтору (Retry Timeout)**. Проте наївна реалізація квитування породжує найпідступніший баг розподілених систем — **дублювання команд**.

Уявімо послідовність подій:
1. Керівний контролер надсилає на виконавчий вузол команду: `Крок двигуна вперед на 10 мм`.
2. Виконавчий вузол успішно приймає пакет, CRC сходиться, мотор виконує переміщення.
3. Виконавчий вузол генерує і відправляє у відповідь короткий кадр `ACK`.
4. На зворотному шляху кадр `ACK` потрапляє під імпульсну заваду і гине.
5. Керівний контролер не отримує `ACK` за час очікування таймауту `T_timeout`. Він припускає, що команда не дійшла, і **надсилає той самий пакет удруге**.
6. Виконавчий вузол отримує повторний пакет. Якщо в його прошивці немає механізму розпізнавання дублікатів, він сприймає його як наступну команду й переміщує двигун ще на 10 мм.

У результаті втрата службового байта `ACK` призвела до аварії виконавчого механізму.

### Монотонні ідентифікатори (Sequence Numbers)

Єдиним надійним захистом від дублювання є додавання до заголовка кожного кадру монотонно зростаючого **порядкового номера (Sequence Number)**.

Приймач зберігає у своєму внутрішньому стані змінну `expected_seq` — номер кадру, на який він очікує. Логіка приймача підпорядковується фундаментальному правилу:

```
ЯКЩО (seq_num == expected_seq):
    1. Передати корисні дані кадру застосунку.
    2. Інкрементувати expected_seq.
    3. Надіслати назад ACK(seq_num).
ІНАКШЕ ЯКЩО (seq_num < expected_seq):   [Це ДУБЛІКАТ!]
    1. Відкинути корисні дані кадру (НЕ передавати застосунку).
    2. ОБОВ'ЯЗКОВО надіслати назад ACK(seq_num).
```

> ⚠️ **Критичний інваріант квитування**: на дублікат кадру **завжди необхідно надсилати ACK повторно**. Якщо проігнорувати дублікат і не надіслати `ACK`, передавач ніколи не дізнається, що його повтор дійшов, і продовжуватиме спамити тим самим старим кадром до вичерпання ліміту спроб, після чого розірве зв'язок аварійно.

Для найпростішого протоколу **Stop-and-Wait** (де відправник не шле новий кадр, доки не отримає ACK на попередній) достатньо однобітного лічильника послідовності `seq_num` з чергуванням значень `0, 1, 0, 1...`.

Для протоколів із **рухомим вікном (Sliding Window)**, де у польоті без підтвердження може одночасно перебувати `W` неквитованих кадрів, розмір простору номерів `S = 2^k` (де `k` — розрядність поля `seq_num` у бітах) повинен строго задовольняти математичну теорему вікна:

```
S >= 2 * W   [для протоколу Selective Repeat]
S >= W + 1   [для протоколу Go-Back-N]
```

Якщо простір номерів буде меншим за `2 * W`, приймач при переповненні лічильника не зможе відрізнити новий свіжий кадр після повного оберту лічильника від старого затриманого в дорозі дубліката з попереднього вікна.

## 4. Перевпорядкування та фрагментація потоку

Четвертий і п'ятий руйнівні режими виникають через мережеву маршрутизацію та потокову природу апаратних інтерфейсів.

### Перевпорядкування пакетів (Out-of-Order Delivery)

У простих лініях «точка-точка» (наприклад, прямий кабель RS-485) пакети не можуть фізично обігнати один одного в дроті. Проте перевпорядкування миттєво з'являється у двох дуже поширених випадках:

1. **Маршрутизація в mesh-мережах (Thread, Zigbee, ESP-NOW Mesh)**. Якщо вузол А надсилає пакети до вузла Б, кадр №1 може піти довгим шляхом через 3 ретранслятори, а кадр №2 — коротким шляхом через 1 ретранслятор. Пакет №2 надійде на приймач раніше, ніж пакет №1.
2. **Вибірковий повтор (Selective Repeat ARQ)**. Якщо у пачці з 4 кадрів `[0, 1, 2, 3]` кадр №1 був спотворений завадою, приймач буферизує кадри №2 і №3, очікуючи повторної передачі кадру №1. Застосунок у жодному разі не повинен отримувати кадри у послідовності `[0, 2, 3, 1]`.

Для захисту від порушення порядку приймач організовує **буфер впорядкування (Reordering Buffer)**. Кадри, номери яких випереджають `expected_seq`, тимчасово складаються у кільцевий масив слотів і утримуються там. Щойно відсутній кадр надходить із лінії, приймач "вистрілює" застосунку всю накопичену неперервну пачку в строго правильному порядку: `1 -> 2 -> 3`.

### Розрізання та склеювання байтового потоку

У мікроконтролерах інтерфейси UART, SPI у режимі веденого, USB-CDC або TCP-сокети передають не «пакети», а **потік октетів**. Апаратний драйвер UART складає прийняті байти в кільцевий буфер DMA. Коли програма робить запит на вичитування буфера, вона отримує стільки байтів, скільки встигло прийти на цей момент.

- Якщо передавач надіслав пакет розміром 50 байтів, приймач через кванти часу операційної системи RTOS або таймінги DMA може отримати його трьома шматками: `14 байтів -> 20 байтів -> 16 байтів` (**фрагментація потоку**).
- Якщо передавач швидко відправив два пакети по 25 байтів, приймач вичитає один суцільний масив на 50 байтів (**склеювання потоку**).

Щоб відновити дискретні пакети з неперервного потоку байтів, необхідний надійний механізм **демаркації меж кадру (Framing)**.

### Порівняння методів кадрування: Чому COBS перевершує аналоги

Існує три класичні підходи до виділення кадрів у потоці:

1. **Префікс фіксованої довжини в заголовку (Length Prefix)**. На початку кадру передається байт або слово довжини `len`.
   *Критичний недолік*: якщо байт довжини спотворюється шумом у каналі (наприклад, значення `12` перетворюється на `250`), приймач чекатиме наступні 250 байтів, перш ніж перевірити CRC. Весь цей час лінія перебуває у стані фатальної розсинхронізації, пропускаючи всі наступні валідні кадри.
2. **Маркери меж із байт-стафінгом (SLIP / HDLC)**. Початок і кінець кадру позначаються унікальним байтом-прапорцем (наприклад, `0xC0` у протоколі SLIP). Якщо байт `0xC0` випадково зустрічається всередині корисних даних або CRC, передавач замінює його двобайтовою послідовністю екранування (`0xDB 0xDC`).
   *Критичний недолік*: нестабільний розмір кадру (Worst-Case Overhead). Якщо блок даних складається суцільно з байтів `0xC0` чи `0xDB`, розмір закодованого кадру подвоюється (+100% оверхеду), що вимагає виділення подвійного розміру буферів пам'яті в мікроконтролері.
3. **COBS (Consistent Overhead Byte Stuffing — байт-стафінг із постійним оверхедом)**. Сучасний еталон кадрування для вбудованих систем.

COBS кодує блок довільних двійкових даних будь-якої довжини таким чином, що символ `0x00` **гарантовано ніколи не з'являється всередині закодованого тіла кадру**. Завдяки цьому нульовий байт `0x00` використовується як однозначний, абсолютний роздільник меж кадру в потоці.

![COBS-кадрування](/root/course/embedded/piat-sposobiv-iakymy-kanal-psuie-dani/img/cobs-framing.svg)
*Принцип роботи COBS: вихідні нулі замінюються ланцюжком зміщень до наступного нуля. Байт 0x00 використовується виключно як роздільник меж кадру.*

Алгоритм COBS розбиває потік байтів на групи, розділені нулями. Перший байт кожної групи замінюється на **покажчик зміщення (offset)** — відстань у байтах до наступного нульового символу. Оскільки зміщення завжди щонайменше дорівнює `1`, байт `0x00` ніколи не потрапляє у вихідний потік. Максимальна довжина групи становить 254 байти (зсув `0xFF` позначає групу з 254 ненульових байтів без нуля наприкінці).

**Переваги COBS**:
- Гарантований максимальний оверхед становить лише **рівно 1 байт на 254 байти даних** (менше ніж 0.4% надлишковості).
- Миттєва самосинхронізація: якщо лінія була розірвана, зловила важкий шум або приймач увімкнувся посеред передачі пакета, приймач просто відкидає сміття і миттєво починає збирати новий кадр з першого ж зустрінутого байта `0x00`.

## 5. Модульний конвеєр надійного приймача

Об'єднаємо захист від усіх п'яти руйнівних режимів у єдиний послідовний архітектурний конвеєр (Pipeline). Приймач будується як детермінований скінченний автомат (FSM), де кожен рівень відповідає рівно за один вектор деградації.

![Модульний конвеєр канального приймача](/root/course/embedded/piat-sposobiv-iakymy-kanal-psuie-dani/img/rx-pipeline.svg)
*Послідовний конвеєр обробки вхідного потоку: від сирих байтів UART через демаркацію, COBS, CRC-16 та фільтр дедуплікації до чистого корисного навантаження.*

### Архітектура кадру в каналі

Кожен логічний пакет перед відправкою упаковується у стандартизовану структуру:

```
[Порядковий номер (1Б)] [Корисне навантаження (N байт)] [CRC-16 CCITT (2Б)]
```

Далі весь цей блок кодується за алгоритмом **COBS** і завершується байтом-роздільником `0x00`:

```
[COBS-закодоване тіло пакета (N + 3 + оверхед байт)] [0x00 - Роздільник кадру]
```

### Конвеєрна обробка на приймачі

1. **Демаркація меж**: FSM приймає байти з кільцевого буфера UART по одному. Байти накопичуються в сирому буфері прийому. Щойно надходить байт `0x00`, накопичений шматок оголошується завершеним кадром і передається на стадію 2. Якщо буфер переповнюється без зустрічі `0x00`, стан скидається (захист від сміття).
2. **COBS-декодування**: функція декодера розгортає покажчики зміщень назад у вихідні нулі. Якщо зміщення виходить за межі реального розміру буфера, кадр визнається структурно пошкодженим і миттєво відкидається.
3. **Контроль цілісності CRC-16**: обчислюється CRC-16 над відновленим пакетом (включно з прийнятими двома байтами CRC наприкінці). Якщо залишок не дорівнює нулю, кадр пошкоджено шумом у лінії — лічильник помилок інкрементується, кадр скидається.
4. **Дедуплікація та контроль послідовності**: вичитується поле `seq_num`. Якщо `seq_num` відповідає старому або вже обробленому кадру, генерується повторний `ACK(seq_num)`, а дані відкидаються. Якщо номер валідний — `expected_seq` оновлюється.
5. **Диспетчеризація застосунку**: чисте корисне навантаження без службових заголовків передається у функцію зворотної сумісності (callback) застосунку.

## 6. Реалізація повного конвеєра на C та C++

Наведемо повний, самодостатній виробничий код канального приймача. Він не використовує динамічного виділення пам'яті (`malloc`/`new`), працює у статичних буферах і підходить для роботи на будь-якому мікроконтролері від 8-бітного AVR до 32-бітного ARM Cortex-M / ESP32.

```c
// Повний модульний конвеєр надійного канального приймача на C99
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>
#include <string.h>

#define LINK_MAX_PAYLOAD      128U
#define LINK_HEADER_SIZE      1U   // 1 байт Sequence Number
#define LINK_CRC_SIZE         2U   // 2 байти CRC-16
#define LINK_MAX_FRAME_SIZE   (LINK_HEADER_SIZE + LINK_MAX_PAYLOAD + LINK_CRC_SIZE)
#define LINK_COBS_MAX_SIZE    (LINK_MAX_FRAME_SIZE + (LINK_MAX_FRAME_SIZE / 254U) + 2U)
#define LINK_FRAME_DELIMITER  0x00U

// Статуси результату конвеєра
typedef enum {
    LINK_OK = 0,
    LINK_FRAME_PENDING,
    LINK_ERR_BUFFER_OVERFLOW,
    LINK_ERR_COBS_CORRUPTED,
    LINK_ERR_CRC_MISMATCH,
    LINK_ERR_DUPLICATE_FRAME
} link_status_t;

// Тип функції зворотного виклику для передачі валідного корисного навантаження
typedef void (*link_payload_handler_t)(const uint8_t *payload, size_t len, void *user_ctx);
// Тип функції відправки ACK-квитанцій
typedef void (*link_ack_sender_t)(uint8_t seq_num, void *user_ctx);

// Контекст стану приймача
typedef struct {
    uint8_t rx_raw_buf[LINK_COBS_MAX_SIZE];
    size_t  rx_raw_idx;
    uint8_t decode_buf[LINK_MAX_FRAME_SIZE + 2U];
    uint8_t expected_seq;
    link_payload_handler_t on_payload;
    link_ack_sender_t      send_ack;
    void                  *user_ctx;
} link_receiver_t;

// Обчислення CRC-16-CCITT (поліном 0x1021, початкове значення 0xFFFF)
uint16_t link_crc16_ccitt(const uint8_t *data, size_t len) {
    uint16_t crc = 0xFFFFU;
    for (size_t i = 0; i < len; ++i) {
        crc ^= ((uint16_t)data[i]) << 8U;
        for (uint8_t bit = 0; bit < 8U; ++bit) {
            if (crc & 0x8000U) {
                crc = (crc << 1U) ^ 0x1021U;
            } else {
                crc = crc << 1U;
            }
        }
    }
    return crc;
}

// Декодування COBS у вихідний двійковий масив
static bool link_cobs_decode(const uint8_t *src, size_t src_len, uint8_t *dst, size_t *dst_len) {
    if (src_len == 0 || src == NULL || dst == NULL) {
        return false;
    }
    
    size_t src_idx = 0;
    size_t dst_idx = 0;
    
    while (src_idx < src_len) {
        uint8_t code = src[src_idx++];
        if (code == 0) {
            return false; // Нуль всередині тіла COBS неприпустимий
        }
        
        for (uint8_t i = 1; i < code; ++i) {
            if (src_idx >= src_len) {
                return false; // Вихід покажчика за межі вхідних даних
            }
            dst[dst_idx++] = src[src_idx++];
        }
        
        if (code < 0xFFU && src_idx < src_len) {
            dst[dst_idx++] = 0x00U; // Відновлюємо замінений нуль
        }
    }
    
    *dst_len = dst_idx;
    return true;
}

// Ініціалізація приймача
void link_receiver_init(link_receiver_t *rx,
                        link_payload_handler_t on_payload,
                        link_ack_sender_t send_ack,
                        void *user_ctx) {
    memset(rx, 0, sizeof(*rx));
    rx->expected_seq = 0U;
    rx->on_payload = on_payload;
    rx->send_ack = send_ack;
    rx->user_ctx = user_ctx;
}

// Обробка одного отриманого байта з фізичного інтерфейсу (UART/DMA)
link_status_t link_receiver_feed_byte(link_receiver_t *rx, uint8_t byte) {
    // 1. Пошук демаркатора меж кадру 0x00
    if (byte == LINK_FRAME_DELIMITER) {
        if (rx->rx_raw_idx == 0) {
            return LINK_FRAME_PENDING; // Порожній кадр між послідовними нулями
        }
        
        size_t decoded_len = 0;
        // 2. COBS-декодування кадру
        if (!link_cobs_decode(rx->rx_raw_buf, rx->rx_raw_idx, rx->decode_buf, &decoded_len)) {
            rx->rx_raw_idx = 0;
            return LINK_ERR_COBS_CORRUPTED;
        }
        rx->rx_raw_idx = 0; // Скидаємо буфер для наступного кадру
        
        // Кадр мусить містити щонайменше 1Б Seq + 2Б CRC
        if (decoded_len < (LINK_HEADER_SIZE + LINK_CRC_SIZE)) {
            return LINK_ERR_CRC_MISMATCH;
        }
        
        // 3. Перевірка контрольної суми CRC-16
        uint16_t calculated_crc = link_crc16_ccitt(rx->decode_buf, decoded_len - LINK_CRC_SIZE);
        uint16_t received_crc = ((uint16_t)rx->decode_buf[decoded_len - 2U] << 8U) |
                                ((uint16_t)rx->decode_buf[decoded_len - 1U]);
                                
        if (calculated_crc != received_crc) {
            return LINK_ERR_CRC_MISMATCH;
        }
        
        // 4. Перевірка порядкового номера та дедуплікація
        uint8_t seq_num = rx->decode_buf[0];
        if (rx->send_ack != NULL) {
            rx->send_ack(seq_num, rx->user_ctx); // Квитуємо отримання
        }
        
        if (seq_num != rx->expected_seq) {
            // Це дублікат уже прийнятого раніше кадру!
            return LINK_ERR_DUPLICATE_FRAME;
        }
        
        // Оновлюємо очікуваний номер
        rx->expected_seq = (uint8_t)(rx->expected_seq + 1U);
        
        // 5. Передача корисного навантаження застосунку
        size_t payload_len = decoded_len - LINK_HEADER_SIZE - LINK_CRC_SIZE;
        if (rx->on_payload != NULL) {
            rx->on_payload(&rx->decode_buf[LINK_HEADER_SIZE], payload_len, rx->user_ctx);
        }
        
        return LINK_OK;
    }
    
    // Накопичення байтів у сирому буфері
    if (rx->rx_raw_idx >= LINK_COBS_MAX_SIZE) {
        rx->rx_raw_idx = 0; // Захист від переповнення при шумі
        return LINK_ERR_BUFFER_OVERFLOW;
    }
    
    rx->rx_raw_buf[rx->rx_raw_idx++] = byte;
    return LINK_FRAME_PENDING;
}
```

```cpp
// Ідіоматичний модульний конвеєр надійного приймача на C++20
#include <array>
#include <span>
#include <cstdint>
#include <cstddef>
#include <expected>
#include <functional>

namespace embedded::net {

enum class LinkError : std::uint8_t {
    BufferOverflow,
    CobsCorrupted,
    CrcMismatch,
    DuplicateFrame,
    FrameIncomplete
};

template <std::size_t MaxPayloadSize = 128>
class ReliableLinkReceiver {
public:
    static constexpr std::size_t HeaderSize = 1;  // 1 байт Sequence Number
    static constexpr std::size_t CrcSize = 2;     // 2 байти CRC-16
    static constexpr std::size_t MaxFrameSize = HeaderSize + MaxPayloadSize + CrcSize;
    static constexpr std::size_t CobsMaxSize = MaxFrameSize + (MaxFrameSize / 254) + 2;
    static constexpr std::uint8_t FrameDelimiter = 0x00;

    using PayloadCallback = std::function<void(std::span<const std::uint8_t>)>;
    using AckCallback = std::function<void(std::uint8_t)>;

    constexpr ReliableLinkReceiver(PayloadCallback on_payload, AckCallback on_ack) noexcept
        : on_payload_(std::move(on_payload)), on_ack_(std::move(on_ack)) {}

    // Обробка чергового байта потоку. Повертає std::expected з розміром корисних даних або кодом помилки
    [[nodiscard]] std::expected<std::size_t, LinkError> feed_byte(std::uint8_t byte) noexcept {
        if (byte == FrameDelimiter) {
            if (raw_idx_ == 0) {
                return std::unexpected(LinkError::FrameIncomplete);
            }

            auto decode_res = decode_cobs(std::span{raw_buf_.data(), raw_idx_});
            raw_idx_ = 0;

            if (!decode_res) {
                return std::unexpected(LinkError::CobsCorrupted);
            }

            const std::size_t decoded_len = *decode_res;
            if (decoded_len < (HeaderSize + CrcSize)) {
                return std::unexpected(LinkError::CrcMismatch);
            }

            // Перевірка CRC-16
            const std::uint16_t calculated_crc = compute_crc16(
                std::span{decoded_buf_.data(), decoded_len - CrcSize});
            const std::uint16_t received_crc = static_cast<std::uint16_t>(
                (decoded_buf_[decoded_len - 2] << 8) | decoded_buf_[decoded_len - 1]);

            if (calculated_crc != received_crc) {
                return std::unexpected(LinkError::CrcMismatch);
            }

            // Дедуплікація за Sequence Number
            const std::uint8_t seq = decoded_buf_[0];
            if (on_ack_) {
                on_ack_(seq); // Завжди підтверджуємо отримання
            }

            if (seq != expected_seq_) {
                return std::unexpected(LinkError::DuplicateFrame);
            }

            expected_seq_ = static_cast<std::uint8_t>(expected_seq_ + 1);

            const std::size_t payload_len = decoded_len - HeaderSize - CrcSize;
            if (on_payload_) {
                on_payload_(std::span{decoded_buf_.data() + HeaderSize, payload_len});
            }

            return payload_len;
        }

        if (raw_idx_ >= CobsMaxSize) {
            raw_idx_ = 0;
            return std::unexpected(LinkError::BufferOverflow);
        }

        raw_buf_[raw_idx_++] = byte;
        return std::unexpected(LinkError::FrameIncomplete);
    }

    constexpr void reset() noexcept {
        raw_idx_ = 0;
        expected_seq_ = 0;
    }

    [[nodiscard]] constexpr std::uint8_t expected_sequence() const noexcept {
        return expected_seq_;
    }

private:
    [[nodiscard]] static constexpr std::uint16_t compute_crc16(
        std::span<const std::uint8_t> data) noexcept {
        std::uint16_t crc = 0xFFFF;
        for (const std::uint8_t b : data) {
            crc ^= static_cast<std::uint16_t>(b) << 8;
            for (std::uint8_t bit = 0; bit < 8; ++bit) {
                if (crc & 0x8000) {
                    crc = static_cast<std::uint16_t>((crc << 1) ^ 0x1021);
                } else {
                    crc = static_cast<std::uint16_t>(crc << 1);
                }
            }
        }
        return crc;
    }

    [[nodiscard]] std::expected<std::size_t, LinkError> decode_cobs(
        std::span<const std::uint8_t> src) noexcept {
        if (src.empty()) {
            return std::unexpected(LinkError::CobsCorrupted);
        }

        std::size_t src_idx = 0;
        std::size_t dst_idx = 0;

        while (src_idx < src.size()) {
            const std::uint8_t code = src[src_idx++];
            if (code == 0) {
                return std::unexpected(LinkError::CobsCorrupted);
            }

            for (std::uint8_t i = 1; i < code; ++i) {
                if (src_idx >= src.size() || dst_idx >= decoded_buf_.size()) {
                    return std::unexpected(LinkError::CobsCorrupted);
                }
                decoded_buf_[dst_idx++] = src[src_idx++];
            }

            if (code < 0xFF && src_idx < src.size()) {
                if (dst_idx >= decoded_buf_.size()) {
                    return std::unexpected(LinkError::CobsCorrupted);
                }
                decoded_buf_[dst_idx++] = 0x00;
            }
        }

        return dst_idx;
    }

    std::array<std::uint8_t, CobsMaxSize> raw_buf_{};
    std::size_t raw_idx_{0};
    std::array<std::uint8_t, MaxFrameSize + 2> decoded_buf_{};
    std::uint8_t expected_seq_{0};
    PayloadCallback on_payload_;
    AckCallback on_ack_;
};

} // namespace embedded::net
```

## 7. Практичні висновки для інженера

Коли розробник проєктує канальний рівень вбудованого пристрою, він має тримати в голові просту матрицю відповідності між фізичними дефектами каналу та необхідними алгоритмічними інструментами:

| Дефект каналу | Фізична першопричина | Інженерний механізм захисту |
| :--- | :--- | :--- |
| **Спотворення бітів** | Шум, наводки від моторів і силових ключів | Контрольні суми **CRC-16/32** або блоковий **FEC (Reed-Solomon)** |
| **Втрата пакетів** | Завмирання сигналу, колізії, переповнення FIFO | **Квитування (ACK/NACK)** та таймаути повтору (ARQ) |
| **Дублювання** | Втрата зворотного ACK при успішному прийомі | Монотонні **порядкові номери (Sequence Numbers)** та дедуплікація |
| **Перевпорядкування** | Багатошляхова маршрутизація, асинхронні повтори | **Приймальне вікно** та буфер впорядкування пакетів |
| **Фрагментація/Склеювання** | Потоковий характер шин (UART/TCP) без меж | Демаркація меж через **COBS-кадрування** (байт `0x00`) |

Спроба зекономити й побудувати протокол зв'язку без будь-якої з цих ланок неминуче призведе до того, що на виробництві або в польових умовах система дасть збій, який надзвичайно важко відтворити на налагоджувальному столі. Надійність розподіленої вбудованої системи досягається не сподіваннями на «ідеальний дріт», а суворим модульним конвеєром обробки, де кожен можливий дефект середовища зустрічає свій детермінований математичний бар'єр.
