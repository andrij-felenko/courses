# 📋 Інтерфейс завантажувача польотного контролера: дескриптори DFU, магічні маркери RTC та команди GCS

Процес перепрограмування польотного контролера без підключення апаратного відлагоджувача (SWD/JTAG) спирається на суворий протокольний контракт між хост-утилітою (Betaflight Configurator, QGroundControl, Mission Planner, `dfu-util`) та вбудованим завантажувачем мікроконтролера. Цей контракт визначає способи переведення робочої прошивки в режим програмування, формат сигнальних маркерів у енергонезалежній пам'яті (RTC Backup Registers), послідовність зміни станів кінцевого автомата DFU, геометрію пам'яті в рядкових дескрипторах USB та команди стандартного класу USB DFU (Device Firmware Upgrade).

Коли польотний контролер під'єднується до комп'ютера, хост взаємодіє з двома різними програмними сутностями: спершу з основною прошивкою (яка підтримує високорівневий інтерфейс телеметрії або віртуальний COM-порт), а після ініціації оновлення — з низькорівневим завантажувачем. Щоб цей перехід відбувся безшовно, обидві сторони використовують стандартизовані апаратні та програмні точки сполучення.

## 1. Програмні тригери входу в завантажувач

Якщо плата польотного контролера запаяна всередині герметичного корпусу дрона, фізичний доступ до апаратної кнопки `Boot0` відсутній. Перехід у режим оновлення ініціюється програмно одним із трьох стандартизованих методів, кожен з яких розрахований на свій клас прикладного програмного забезпечення.

### Метод 1: Зміна швидкості USB CDC (1200 bps Touch)

Цей метод є стандартом де-факто для пристроїв з емуляцією віртуального послідовного порту (USB CDC-ACM). Хост-утиліта відкриває активний порт контролера, налаштовує термінальну лінію на магічну швидкість 1200 біт/с і скидає лінію керування `DTR` (Data Terminal Ready). Драйвер USB CDC усередині польотної прошивки перехоплює цей запит і розуміє, що користувач ініціював процедуру прошивки:

```
Хост (Configurator)                 Польотний контролер (CDC Driver)
       │                                            │
       ├──── SET_LINE_CODING (1200 baud) ──────────>│  (Перехоплення колбеку)
       ├──── SET_CONTROL_LINE_STATE (DTR=0) ───────>│  (Встановлення прапорця DFU)
       ├──── Закриття порту USB ───────────────────>│  (Запис маркеру в RTC)
       │                                            │  (NVIC_SystemReset)
       │                                            ▼
   [USB Disconnect]                         [Перезавантаження]
       │                                            │
   [USB Re-Enumeration: ST DFU Device] <────────────┘
```

### Метод 2: Магічні маркери в регістрах RTC Backup

Оскільки звичайний системний перезапуск процесора (`NVIC_SystemReset()`) скидає більшість комірок оперативної пам'яті (SRAM) до невизначеного стану або ініціалізує їх нулями при старті C-runtime, сигнальний прапорець не можна передати через глобальну змінну.

Для збереження стану між перезапусками використовують регістри резервного домену RTC (Backup Data Registers), які не втрачають свій вміст при програмному скиданні ядра:

| Регістр / Адреса | Магічне значення (Hex) | ASCII / Призначення | Цільовий польотний стек |
|---|---|---|---|
| `RTC->BKP0R` (STM32F4/F7) | `0x424C6F6F` | `"BLoo"` (Bootloader Force) | PX4 / ArduPilot Bootloader |
| `RTC->BKP0R` (STM32F4/F7) | `0x42465400` | `"BFT\0"` (Betaflight DFU) | Вхід у системну ROM ST DFU |
| `TAMP->BKP0R` (STM32H7) | `0x544F5543` | `"TOUC"` (1200 Touch) | Скидання завантажувача USB |
| `RTC->BKP1R` | `0x524F4C4C` | `"ROLL"` (Rollback Force) | Аварійний відкат на Bank B |

Перед викликом скидання прошивка знімає захист від запису з резервного домену (встановлює біт `DPB` у регістрі `PWR->CR`), записує магічне значення у відповідний регістр `BKPxR` і викликає системний перезапуск. При перших тактах після виходу зі скидання завантажувач перевіряє значення в цьому регістрі. Якщо знайдено збіг, завантажувач негайно очищає регістр (щоб запобігти зацикленню входів) і залишається в режимі оновлення замість переходу до основної програми.

### Метод 3: MAVLink команда перезавантаження

У професійних польотних стеках PX4 та ArduPilot перехід у завантажувач здійснюється за допомогою стандартного протокольного повідомлення `COMMAND_LONG` з ідентифікатором команди `MAV_CMD_PREFLIGHT_REBOOT_SHUTDOWN` (ID #246). Це дозволяє оновлювати прошивку через будь-який наявний канал телеметрії:

| Байт / Поле | Тип даних | Значення | Опис дії |
|---|---|---|---|
| `param1` | float | `1.0` | Перезавантаження польотного контролера (звичайний старт) |
| `param1` | float | `3.0` | Перезавантаження безпосередньо в режим **Bootloader (DFU)** |
| `param2` | float | `0.0` | Скидання бортового комп'ютера Companion Computer (0 = ігнорувати) |
| `param3` | float | `0.0` | Зарезервовано |
| `param4` | float | `0.0` | Зарезервовано |
| `param5` | float | `0.0` | Зарезервовано |
| `param6` | float | `0.0` | Зарезервовано |
| `param7` | float | `0.0` | Цільовий компонент системи (1 = Autopilot) |

## 2. Специфікація протоколу класу USB DFU 1.1

При вході в режим завантажувача контролер реініціалізує USB-периферію як пристрій класу DFU (`bDeviceClass = 0x00`, `bInterfaceClass = 0xFE`, `bInterfaceSubClass = 0x01`). Обмін інформацією відбувається виключно через нульову кінцеву точку керування (Endpoint 0 Control Transfer).

### Класові запити керування (Setup Requests)

Хост керує процесом стирання та запису пам'яті через набір стандартних запитів, закодованих у полі `bRequest` пакета `SETUP`:

| Запит (bRequest) | Код (Hex) | Напрямок передачі | Опис операції та поведінка пристрою |
|---|---|---|---|
| `DFU_DETACH` | `0x00` | Host → Dev | Команда виходу з робочого режиму застосунку в завантажувач |
| `DFU_DNLOAD` | `0x01` | Host → Dev | Передача блоку прошивки для запису або команди адресації |
| `DFU_UPLOAD` | `0x02` | Dev → Host | Зчитування блоку Flash пам'яті для контрольної верифікації |
| `DFU_GETSTATUS` | `0x03` | Dev → Host | Отримання стану автомата та таймауту очікування (`bwPollTimeout`) |
| `DFU_CLRSTATUS` | `0x04` | Host → Dev | Очищення стану помилки та скидання прапорця `dfuERROR` |
| `DFU_GETSTATE` | `0x05` | Dev → Host | Отримання ідентифікатора поточного стану автомата DFU |
| `DFU_ABORT` | `0x06` | Host → Dev | Переривання поточної транзакції та повернення в стан `dfuIDLE` |

### Структура відповіді на запит `DFU_GETSTATUS` (6 байтів)

Після відправки кожного блоку даних через `DFU_DNLOAD` хост зобов'язаний надіслати запит `DFU_GETSTATUS`. Відповідь містить точний розрахунок затримки, необхідної мікроконтролеру для фізичного завершення операції:

```
Байт 0: bStatus          — Статус виконання останньої операції (0x00 = OK, 0x0E = errVENDOR)
Байти 1-3: bwPollTimeout — Мінімальний час у мілісекундах (24-бітний формат Little-Endian), 
                            який хост зобов'язаний зачекати перед відправкою наступного запиту
Байт 4: bState           — Поточний стан кінцевого автомата DFU (наприклад, 0x02 = dfuIDLE)
Байт 5: iString          — Рядковий індекс детального опису помилки (0 = рядок відсутній)
```

Значення `bwPollTimeout` є критично важливим: для звичайного запису блоку розміром 1 КБ воно становить 2–5 мс, але при виконанні команди повного стирання сектора Flash (Mass Erase або Sector Erase) контролер повертає таймаут до 1000–4000 мс. Якщо хост проігнорує це поле і надішле наступний запит завчасно, мікроконтролер перерве операцію з помилкою `dfuERROR`.

### Кінцевий автомат станів завантажувача DFU (`bState`)

Послідовність зміни станів під час циклу прошивки регламентується специфікацією USB-IF:

| Стан (bState) | Код (Hex) | Фізичний процес у мікроконтролері |
|---|---|---|
| `appIDLE` | `0x00` | Контролер виконує звичайний польотний код |
| `appDETACH` | `0x01` | Отримано команду переходу, очікування скидання шини USB Reset |
| `dfuIDLE` | `0x02` | Завантажувач готовий приймати команди та нові блоки прошивки |
| `dfuDNLOAD-SYNC` | `0x03` | Синхронізація після прийому блоку даних через Control Transfer |
| `dfuDNBUSY` | `0x04` | Контролер апаратно стирає сектор або програмує комірки Flash |
| `dfuDNLOAD-IDLE` | `0x05` | Блок успішно зафіксовано, очікування наступного блоку від хоста |
| `dfuMANIFEST-SYNC`| `0x06` | Завершено передачу останнього блоку нульової довжини |
| `dfuMANIFEST` | `0x07` | Фіналізація образу (перевірка контрольних сум, перепрошивка Option Bytes) |
| `dfuERROR` | `0x0A` | Виник збій запису або порушено захист від читання/запису (RDP) |

## 4. Специфікація адресації та команд розширення ST DFU (DfuSe)

Оскільки стандартна специфікація USB DFU 1.1 спочатку розроблялася без явної передачі цільової адреси пам'яті, компанія STMicroelectronics розробила сумісний протокол **DfuSe** (DFU with ST Extensions). 

У протоколі DfuSe початкова адреса запису передається хостом у спеціальній команді `Set Address Pointer`, яка надсилається всередині першого виклику `DFU_DNLOAD` з нульовим номером транзакції (`wValue = 0`):

```
Байт 0: Команда = 0x21 (Set Address Pointer)
Байти 1-4: 32-бітна абсолютна адреса Flash пам'яті (Little-Endian)
           Наприклад: 0x00, 0x00, 0x01, 0x08 для адреси 0x08010000
```

Для стирання конкретного сектора хост надсилає команду `Erase Page`:

```
Байт 0: Команда = 0x41 (Erase Sector)
Байти 1-4: 32-бітна базова адреса сектора Flash, що підлягає очищенню
```

Після передачі команди `Erase Sector` хост обов'язково опитує `DFU_GETSTATUS` і витримує паузу `bwPollTimeout`, поки апаратний контролер пам'яті мікроконтролера фізично очищає сектор. Лише після повернення статусу `dfuDNLOAD-IDLE` хост починає поблокове передавання бінарного тіла прошивки.

## 5. Опис карти секторів у рядкових дескрипторах (Memory Layout String)

Щоб хост-програма автоматично визначала структуру секторів та адресні простори конкретного мікроконтролера (наприклад, різницю між секторами по 16 КБ, 64 КБ та 128 КБ у STM32F405 або рівномірними секторами по 128 КБ у STM32H743), завантажувач передає спеціальний рядковий дескриптор USB (Interface String Descriptor) для кожного альтернативного налаштування інтерфейсу (Alternate Setting):

```
Формат рядка карти пам'яті:
@<Назва_пам'яті> /<Початкова_адреса>/<Кількість_секторів>*<Розмір_сектора><Тип_доступу>,...

Приклад для STM32F405 (1 МБ Flash):
"@Internal Flash  /0x08000000/04*016Kg,01*064Kg,07*128Kg"

Розшифровка:
- 04*016Kg: 4 сектори по 16 КБ (Сектори 0..3: 0x08000000 - 0x0800FFFF)
- 01*064Kg: 1 сектор по 64 КБ  (Сектор 4:     0x08010000 - 0x0801FFFF)
- 07*128Kg: 7 секторів по 128 КБ (Сектори 5..11: 0x08020000 - 0x080FFFFF)
- Прапорець 'g': доступ на читання, запис та стирання (readable, writable, erasable)
```

Завдяки цьому рядку хост-утиліта точно знає, які сектори Flash-пам'яті займає завантажувач (наприклад, перші два сектори по 16 КБ), які сектори підлягають стиранню під нову прошивку, і де розташовані захищені сектори збереження калібрувальних параметрів, запобігаючи випадковому затиранню службових областей.
