Натискання кнопки «Підготовка до старту» на пульті автоклава чи операторському терміналі насосної станції виглядає для користувача як елементарна одинична подія. Проте за цим єдиним сигналом криється ланцюг із кількох фізичних операцій: відкрити дренажний клапан, зачекати 500 мілісекунд для вирівнювання тиску, увімкнути циркуляційну помпу на 30% обертів, дочекатися сигналу від датчика протоку рідини щонайменше 4 літри на хвилину протягом не більше 3 секунд, закрити дренаж, підняти тиск у магістралі до 3.5 бар і лише після цього подати напругу на силовий нагрівальний елемент. Якщо розробник реалізує таку послідовність лінійно через ланцюжок викликів `delay()`, перший же апаратний збій — заклинювання штока помпи або тріщина в шлангу подачі — перетворює систему на катастрофу: головний цикл мікроконтролера наглухо зависає в очікуванні сигналу сенсора, сторожовий таймер скидає процесор, а напіввідкриті клапани залишаються під тиском, виливаючи хімічний розчин у корпус або перегріваючи сухий ТЕН.

Щоб високорівнева дія користувача («Підготовка до старту», «Промивка магістралей», «Аварійна евакуація вантажу») виконувалася надійно, вона розгортається у таймований граф підкоманд із явним контролем передумов, постумов, неблокуючим виконанням та гарантованим механізмом відкату.

## Чому лінійна послідовність руйнує вбудовану систему

Наївний підхід до автоматизації складних процедур полягає у послідовному виклику функцій керування актуаторами упереміж із блокуючими затримками та циклами очікування:

:::tabs
```c
/* НАЇВНИЙ БЛОКУЮЧИЙ ПІДХІД — ДЖЕРЕЛО КАТАСТРОФ */
void prepare_start_sequence_blocking(void) {
    valve_open(VALVE_DRAIN);
    delay_ms(500);                        /* Зависання CPU на 500 мс */

    pump_set_power(PUMP_MAIN, 30);
    uint32_t t0 = get_system_ms();
    while (sensor_get_flow() < 4.0f) {    /* Блокуюче опитування датчика */
        if ((uint32_t)(get_system_ms() - t0) > 3000) {
            system_panic();               /* Аварійне скидання */
        }
        delay_ms(10);
    }

    valve_close(VALVE_DRAIN);
    pump_set_power(PUMP_MAIN, 80);
    while (sensor_get_pressure() < 3.5f) { /* Ще одне зависання до 4 секунд */
        delay_ms(10);
    }

    heater_enable(HEATER_PRIMARY);
}
```
```cpp
#include <chrono>
#include <thread>

/* НАЇВНИЙ БЛОКУЮЧИЙ ПІДХІД НА C++ — ДЖЕРЕЛО КАТАСТРОФ */
void prepare_start_sequence_blocking() {
    using namespace std::chrono_literals;

    valve_open(ValveId::Drain);
    std::this_thread::sleep_for(500ms);   /* Блокування потоку */

    pump_set_power(PumpId::Main, 30);
    auto t0 = std::chrono::steady_clock::now();
    while (sensor_get_flow() < 4.0f) {    /* Блокуюче опитування */
        if (std::chrono::steady_clock::now() - t0 > 3000ms) {
            system_panic();               /* Аварійне скидання */
        }
        std::this_thread::sleep_for(10ms);
    }

    valve_close(ValveId::Drain);
    pump_set_power(PumpId::Main, 80);
    while (sensor_get_pressure() < 3.5f) {
        std::this_thread::sleep_for(10ms);
    }

    heater_enable(HeaterId::Primary);
}
```
:::

Така реалізація має чотири системні дефекти, несумісні з надійними вбудованими пристроями:

1. **Втрата реактивності та «сліпота» до подій:** Поки процесор витрачає 500 мс у виклику затримки або крутиться у циклі `while`, мікроконтролер не здатний обробляти пакети телеметрії з інтерфейсів UART/CAN/Ethernet, оновлювати екран інтерфейсу та реагувати на натискання користувачем фізичної кнопки аварійного стопу.
2. **Спрацьовування сторожового таймера (Watchdog Timeout):** Якщо сумарна тривалість очікування сенсорів перевищує апаратний інтервал сторожового таймера (наприклад, 1000–2000 мс), процесор зазнає примусового апаратного перезавантаження посеред незавершеної процедури.
3. **Невизначений фізичний стан при відмові (State Inconsistency):** Якщо на третьому етапі датчик тиску фіксує аварію (лопнула магістраль), прямий вихід через `return` чи аварійне скидання `system_panic()` залишає помпу увімкненою на 80% потужності, а дренажний клапан закритим. Помпа починає працювати на закриту засувку (гідроудар), грітися і виходити з ладу.
4. **Неможливість масштабування та паралелізму:** Якщо системі потрібно паралельно виконувати іншу процедуру (наприклад, калібрувати датчик кута чи заряджати буферний конденсатор), лінійний код виключає будь-яке суміщення дій без переходу на багатопотокову RTOS із важкими стеками пам'яті під кожну задачу.

### Скінченний автомат режимів проти рушія сценаріїв

Слід чітко розрізняти дві архітектурні концепції керування у прошивці:

| Критерій | Автомат станів (State Machine / FSM) | Рушій макросценаріїв (Action Sequence Engine) |
|---|---|---|
| **Призначення** | Опис глобального стаціонарного режиму системи (`IDLE`, `MANUAL`, `AUTO`, `FAILSAFE`). | Опис динамічного транзитного процесу (процедури переходу). |
| **Ініціатор дій** | Пасивно очікує зовнішніх асинхронних подій (кнопки, мережа, аварії). | Активно ініціює послідовність кроків за власним розкладом. |
| **Часова структура** | Перебуває у стані невизначено довго, поки немає події. | Кожен крок має суворий дедлайн, затримку стабілізації та таймаут. |
| **Реакція на збій** | Перемикається на глобальний стан аварії (Failsafe). | Розгортає локальний стек компенсацій (LIFO Rollback) для повернення назад. |

Сценарій є інструментом, за допомогою якого автомат станів переводить керований апарат із одного стаціонарного режиму в інший без створення десятків проміжних псевдостанів у глобальній FSM.

## Анатомія макросценарію: декларативний граф підкоманд

Замість жорстко закодованих інструкцій макрокоманда представляється як масив або зв'язний граф кроків (**Scenario Steps**), де кожен крок є декларативною структурою даних.

![Граф виконання багатоетапного сценарію: прямий хід, бар'єри та відкат](/root/course/embedded/stsenarii/img/macro-scenario-graph.svg)
*Граф виконання багатоетапного сценарію: прямий хід із верифікацією передумов та постумов на кожному кроці, часовими бар'єрами та гілками аварійного відкату*

Кожен крок сценарію визначається шістьма базовими атрибутами:

1. **Дія активації (`action`):** Функція, яка надсилає керівний вплив на виконавчий механізм (увімкнути реле, змінити шпаруватість ШІМ, надіслати команду по шині CAN).
2. **Передумова (`precondition`):** Булева функція-предикат, яка перевіряє фізичну безпеку та готовність підсистем *до* початку дії. Якщо передумова не виконується, дія навіть не ініціалізується.
3. **Постумова (`postcondition`):** Булева функція-предикат, яка підтверджує, що фізичний процес досяг цільового значення (шток гідроциліндра дійшов до кінцевика, тиск перевищив поріг).
4. **Таймаут виконання (`timeout_ms`):** Граничний астрономічний час, виділений на досягнення постумови. Якщо час вичерпано, а постумова повертає `false`, крок вважається аварійно проваленим.
5. **Час технологічної витримки (`settle_delay_ms`):** Мінімальний час стабілізації після активації дії, протягом якого постумова не перевіряється, щоб відсікти перехідні процеси, пускові струми або гідравлічні коливання.
6. **Дія компенсації / відкату (`rollback_action` / `undo`):** Функція, яка повертає підсистему в безпечний стан, якщо цей або будь-який наступний крок сценарію зазнає аварії.

### Класифікація типів кроків

Залежно від фізичної природи взаємодії з апаратурою кроки сценарію поділяються на чотири функціональні класи:

```
┌──────────────────────────────────────────────────────────────────────────┐
│                         ТИПИ КРОКІВ СЦЕНАРІЮ                             │
├────────────────────┬─────────────────────────────────────────────────────┤
│ 1. МИТТЄВИЙ        │ Подача команди без очікування зворотного зв'язку     │
│    (Fire-and-forget)│ (наприклад, перемикання світлодіода індикації).      │
├────────────────────┼─────────────────────────────────────────────────────┤
│ 2. ТАЙМОВАНА       │ Фіксована пасивна пауза для фізичних процесів       │
│    ПАУЗА (Dwell)   │ (прогрів датчика газу, затримка на заспокоєння).    │
├────────────────────┼─────────────────────────────────────────────────────┤
│ 3. ОПИТУВАННЯ З    │ Активне очікування досягнення порогового значення   │
│    ТАЙМАУТОМ (Poll)│ сенсора (набір тиску, досягнення цільової позиції). │
├────────────────────┼─────────────────────────────────────────────────────┤
│ 4. СИНХРОНІЗАЦІЙНИЙ│ Одночасний запуск кількох підсистем із очікуванням  │
│    БАР'ЄР (Barrier)│ готовності всіх учасників перед переходом далі.     │
└────────────────────┴─────────────────────────────────────────────────────┘
```

1. **Миттєвий крок (Fire-and-forget):** Виконує дію (наприклад, встановлення логічного рівня на піні мікроконтролера) і миттєво переходить до наступного кроку без очікування зворотного зв'язку. Постумова відсутня або повертає `true` за замовчуванням.
2. **Таймована витримка (Dwell / Settle Step):** Потрібна для процесів, де після ввімкнення пристрою необхідно витримати технологічну паузу перед зчитуванням показань (наприклад, 200 мс на розряд конденсатора, 500 мс на прогрів оптичного детектора). У цьому випадку дія активується на вході, а постумова повертає `true` лише після спливання часу витримки.
3. **Опитування сенсора з таймаутом (Polling Step):** Крок активує силовий орган і періодично перевіряє фізичні параметри. Якщо за час `timeout_ms` датчик підтвердив виконання умови, крок завершується успішно; якщо час вичерпано — фіксується відмова.
4. **Синхронізаційний бар'єр (Barrier Step):** Використовується для синхронізації паралельних апаратних процесів (наприклад, одночасне висування двох гідроопор або прогрів двох незалежних камер екструдера). Бар'єр очікує, поки всі паралельні умови не стануть істинними одночасно.

## Неблокуюче асинхронне виконання в суперциклі

Щоб сценарій не блокував роботу решти підсистем мікроконтролера, його рушій реалізується за принципом квантування часу (Time-Slicing) всередині головного суперциклу прошивки або періодичної задачі RTOS.

Функція оновлення рушія `scenario_engine_tick(now_ms)` викликається з фіксованим періодом (наприклад, кожні 10 мс) або на кожній ітерації головного циклу. Вона не містить жодних затримок `delay()` і виконується за лічені мікросекунди, перевіряючи поточний статус активного кроку.

![Життєвий цикл асинхронного кроку в неблокуючому суперциклі](/root/course/embedded/stsenarii/img/asynchronous-step-lifecycle.svg)
*Внутрішні переходи станів окремого кроку: від верифікації передумов до періодичного опитування сенсорів і завершення*

### Життєвий цикл кроку

Усередині рушія кожен крок проходить чітко визначені фази:

1. `STEP_PENDING`: Крок очікує своєї черги в масиві сценарію.
2. `STEP_PRECHECK`: Рушій викликає функцію `precondition()`. Якщо повертається `false`, виконання сценарію негайно зупиняється з кодом помилки `ERR_PRECONDITION_FAILED`, і запускається відкат.
3. `STEP_ACTION_ENTER`: Викликається функція `action()`. Фіксується системний час старту кроку (`start_time_ms = now_ms`). Покажчик на дію компенсації (`rollback_action`) зберігається у внутрішньому стеку відкату. Крок переходить у стан `STEP_EXECUTING`.
4. `STEP_EXECUTING`: На кожному виклику `scenario_engine_tick()` виконуються три послідовні перевірки:
   - **Перевірка наскрізних інваріантів безпеки:** Якщо глобальний захист (наприклад, датчик відкриття кришки або кнопка E-Stop) сигналізує аварію, крок переводиться в `STEP_ABORTED`.
   - **Перевірка таймауту:** Якщо `(now_ms - start_time_ms) >= timeout_ms`, крок переводиться в `STEP_TIMED_OUT`.
   - **Перевірка постумови:** Якщо час технологічної витримки минув `(now_ms - start_time_ms) >= settle_delay_ms`, викликається функція `postcondition()`. Якщо вона повертає `true`, крок вважається успішним і переходить у `STEP_COMPLETED`.
5. `STEP_COMPLETED`: Рушій інкрементує індекс поточного кроку та переходить до наступного елемента сценарію.

### Математично коректний розрахунок таймаутів

Вбудовані системи часто працюють місяцями без перезавантаження. 32-бітний лічильник мілісекунд (на базі системного таймера SysTick) переповнюється і скидається в нуль через 49.7 діб безперервної роботи (2^32 мілісекунд = 4 294 967 296 мс).

Порівняння абсолютного часу із сумою є критичною помилкою:

:::tabs
```c
/* КРИТИЧНИЙ БАГ: ПРИ ПЕРЕПОВНЕННІ УМОВА СТАНЕ FALSE НА 49 ДНІВ */
if (now_ms >= start_time_ms + timeout_ms) {
    /* Неправильно: сума start_time_ms + timeout_ms переповниться */
}
```
```cpp
#include <cstdint>

/* КРИТИЧНИЙ БАГ НА C++: АБСОЛЮТНЕ ПОРІВНЯННЯ */
bool check_timeout_buggy(uint32_t now_ms, uint32_t start_time_ms, uint32_t timeout_ms) {
    return now_ms >= (start_time_ms + timeout_ms);
}
```
:::

Якщо `start_time_ms = 4294967000`, а `timeout_ms = 1000`, сума `start_time_ms + timeout_ms` через переповнення стане рівною `704`. Оскільки поточний час `now_ms` до переповнення становить близько `4294967100`, вираз `4294967100 >= 704` миттєво поверне `true`, і крок обірветься хибним таймаутом через 0 мілісекунд.

Математично коректний варіант у мовах C та C++ спирається на властивість арифметики беззнакових цілих чисел (`uint32_t`) за модулем 2^32:

:::tabs
```c
/* БЕЗПЕЧНЕ ОБЧИСЛЕННЯ: ПРАЦЮЄ НАВІТЬ ПРИ ПЕРЕХОДІ ЧЕРЕЗ НУЛЬ */
if ((uint32_t)(now_ms - start_time_ms) >= timeout_ms) {
    /* Таймаут дійсно минув */
}
```
```cpp
#include <cstdint>
#include <chrono>

/* БЕЗПЕЧНЕ ОБЧИСЛЕННЯ НА C++ */
bool check_timeout_safe(uint32_t now_ms, uint32_t start_time_ms, uint32_t timeout_ms) {
    return (now_ms - start_time_ms) >= timeout_ms;
}
```
:::

При беззнаковому відніманні `(uint32_t)(100 - 4294967200)` результат дорівнює точно `196` мілісекунд, що повністю усуває проблему переповнення таймера.

## Контроль проміжних умов: передумови, постумови та інваріанти

Фізичний світ, з яким взаємодіє мікроконтролер, є стохастичним і нестаціонарним. Перевірити стан датчиків лише один раз перед стартом сценарію недостатньо: клапан може заклинити на середині ходу, тиск у системі живлення може просісти через увімкнення потужного навантаження на сусідній платі, а оператор може випадково зняти захисний кожух прямо під час руху актуатора.

Надійний сценарій опирається на тріаду контролю умов:

```
                     ┌─────────────────────────────────────────┐
                     │     1. ПЕРЕДУМОВИ (Preconditions)       │
                     │  Чи безпечно починати конкретний крок?   │
                     └────────────────────┬────────────────────┘
                                          │
                                          ▼
                     ┌─────────────────────────────────────────┐
                     │    2. ІНВАРІАНТИ (Continuous Invariants)│
                     │  Чи не виникла аварія під час руху?     │
                     └────────────────────┬────────────────────┘
                                          │
                                          ▼
                     ┌─────────────────────────────────────────┐
                     │      3. ПОСТУМОВИ (Postconditions)      │
                     │  Чи досягнуто цільовий фізичний стан?   │
                     └─────────────────────────────────────────┘
```

### 1. Передумови (Preconditions)
Предикати передумов запобігають увімкненню механізмів у конфліктних або небезпечних конфігураціях:
- Не вмикати нагрівач, якщо рівень рідини в баку нижче критичного сенсора (`sensor_level_ok() == false`).
- Не запускати компресор, якщо магістральний випускний клапан закритий (запобігання вибуху ресивера).
- Не починати рух сервоприводу маніпулятора, якщо напруга живлення силової шини нижче 21.5 В (запобігання просіданню логічної частини MCU під навантаженням).

### 2. Постумови (Postconditions)
Постумови перетворюють «сліпі» команди на керовані операції зі зворотним зв'язком:
- Після команди «Увімкнути реле вентилятора» постумова чекає появи сигналу тахометра (`fan_rpm > 1200`).
- Після подачі сигналу на кроковий двигун постумова чекає замикання оптичного кінцевика домашньої позиції (`limit_switch_hit() == true`).
- Після відкриття електромагнітного клапана постумова перевіряє падіння тиску на вході та зростання на виході через диференційний манометр.

### 3. Наскрізні інваріанти (Continuous Invariants)
Інваріант — це логічна умова, яка мусить бути істинною на кожному такті виконання всього сценарію:
- Аварійний шлейф безпеки (E-Stop loop) замкнений і цілісний.
- Температура силових ключів драйвера двигуна нижче 85 °C.
- Канал бездротового зв'язку з пультом не втрачено (вік останнього пакету < 500 мс).

Порушення будь-якого інваріанта негайно скасовує пряме виконання сценарію та ініціює процедуру аварійного відкату.

## Відкат і компенсація збоїв: механізм LIFO-стека

Коли сценарій зазнає аварії на середині виконання (наприклад, на кроці 4 із 6), просто зупинити виконання програми або скинути мікроконтролер неприпустимо:

- Якщо в системі дозування хімічних реагентів відкрили клапан подачі кислоти (крок 1), увімкнули насос розчинника (крок 2), а на кроці 3 вийшов з ладу змішувач — просте знеструмлення залишить нерозведену кислоту в реакторі, що зруйнує корпус.
- Якщо в гідравлічному приводі стріли маніпулятора розтиснули гальмо (крок 1) і почали підйом (крок 2), а на кроці 3 зник тиск мастила — миттєве скидання живлення призведе до некерованого падіння стріли під дією сили тяжіння.

Система вимагає впорядкованої **процедури компенсації (Rollback / Compensation Sequence)**.

![Стек компенсацій: розгортання дій у порядку LIFO](/root/course/embedded/stsenarii/img/rollback-compensation-stack.svg)
*Стек компенсацій: реєстрація зворотних дій під час прямого ходу та їх покрокове виконання у зворотному порядку (LIFO) при виникненні аварії*

### Принцип LIFO (Last-In, First-Out) для відкату

Під час успішного проходження кожного кроку сценарію рушій реєструє відповідну компенсаційну дію у внутрішньому стеку відкату (**Rollback Stack**). Якщо крок під номером N завершується аварією:

1. Прямий хід сценарію негайно блокується.
2. Рушій переходить у службовий стан `SCENARIO_ROLLING_BACK`.
3. Рушій витягує зі стека компенсацій покажчик на зворотну дію для кроку N-1, виконує її, потім для кроку N-2, і так далі до кроку 1.
4. Якщо дія компенсації сама вимагає часу (наприклад, закрити засувку і чекати скидання тиску), відкат виконується як окрема неблокуюча послідовність кроків.
5. Після завершення всіх компенсаторів система переходить у безпечний термінальний стан `SCENARIO_ABORTED_SAFE`.

## Паралелізм, розгалуження та синхронізаційні бар'єри

У промислових установках та автономних роботах багато підсистем повинні готуватися одночасно, щоб не витрачати зайвий час:
- Одночасне висування чотирьох аутригерів мобільної платформи з контролем тиску на кожній опорі.
- Паралельний розігрів трьох зон паяльної станції або зон екструдера 3D-принтера.
- Одночасне позиціювання двох осей маніпулятора (X та Y) з очікуванням прибуття обох у цільові координати.

### Реалізація бар'єрів Fork-Join без RTOS

У неблокуючому суперциклі паралельні підкроки реалізуються через бітові маски стану (**Join Masks**) та таблицю незалежних таймерів:

```
                  ┌───────────────────────────────┐
                  │   КРОК N: FORK (Розгалуження) │
                  │  Старт підсистеми A, B та C   │
                  └───────────────┬───────────────┘
                                  │
         ┌────────────────────────┼────────────────────────┐
         │                        │                        │
         ▼                        ▼                        ▼
┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
│  Підкрок A       │    │  Підкрок B       │    │  Підкрок C       │
│  Розгін помпи 1  │    │  Нагрів зони 1   │    │  Відкриття шлюзу │
│  (Таймаут 2.5 с) │    │  (Таймаут 5.0 с) │    │  (Таймаут 1.0 с) │
└────────┬─────────┘    └────────┬─────────┘    └────────┬─────────┘
         │                        │                        │
         │ (Біт 0 = 1)            │ (Біт 1 = 1)            │ (Біт 2 = 1)
         └────────────────────────┼────────────────────────┘
                                  │
                                  ▼
                  ┌───────────────────────────────┐
                  │   КРОК N+1: JOIN (Бар'єр)     │
                  │  Маска готовності == 0b111?   │
                  │  Всі 3 підсистеми готові      │
                  └───────────────────────────────┘
```

1. **Фаза Fork:** Рушій надсилає команди активації усім трьом підсистемам одночасно і скидає бітову маску завершення: `join_mask = 0`.
2. **Фаза Execution:** На кожному такті `scenario_tick()` рушій опитує датчики кожної підсистеми незалежно. Коли підсистема A досягає цільового тиску, встановлюється біт 0 (`join_mask |= (1 << 0)`). Коли підсистема B досягає температури, встановлюється біт 1 (`join_mask |= (1 << 1)`).
3. **Фаза Join (Бар'єр):** Постумова кроку-бар'єра перевіряє рівність `join_mask == target_mask` (наприклад, `0b0111`). Лише коли всі учасники підтвердили готовність у межах спільного таймауту, сценарій переходить до наступного етапу. Якщо хоча б одна підсистема провалює свій таймаут — активується відкат для всіх запущених вузлів.

## Наскрізні інженерні приклади сценаріїв

Для глибшого розуміння розглянемо два контрастні сценарії: промисловий технологічний цикл із гідравлікою та передпольотний чеклист безпілотного апарата.

### 1. Технологічний цикл парового автоклава

У медичному або лабораторному автоклаві процедура «Стерилізація інструментів» складається із 7 послідовних кроків із різними фізичними процесами:

```
[1. Герметизація камери]
- Дія: Подати напругу на електрозамок дверей.
- Постумова: Спрацьовування двох незалежних кінцевиків замка. Таймаут: 2000 мс.
- Відкат: Знеструмити електрозамок.

[2. Первинне вакуумування (попереднє видалення повітря)]
- Передумова: Двері заблоковані.
- Дія: Запуск вакуумної помпи, відкриття відкачного клапана.
- Постумова: Абсолютний тиск у камері P <= 0.2 бар (-0.8 бар манометричного). Таймаут: 45 000 мс.
- Відкат: Закрити відкачний клапан, зупинити помпу, відкрити аварійний клапан впуску повітря.

[3. Нагнітання перегрітої пари]
- Передумова: Вакуум досягнуто (відсутні повітряні кишені).
- Дія: Відкриття парового клапана від парогенератора, увімкнення ТЕНів камери.
- Постумова: Тиск у камері досяг 2.2 бар, температура датчика дренажу T >= 134.0 °C. Таймаут: 60 000 мс.
- Відкат: Закрити паровий клапан, знеструмити ТЕНи, відкрити дренажний клапан конденсату.

[4. Стерилізаційна експозиція (фаза витримки)]
- Дія: Активація ПІД-регулятора нагріву для утримання 134.0–135.5 °C.
- Постумова: Таймер експозиції досяг 300 секунд (5 хвилин) без виходу температури за межі 133.5 °C.
- Відкат: Знеструмити ТЕНи, повільний плавний дренаж пари через теплообмінник.

[5. Швидке скидання тиску]
- Дія: Повне відкриття магістрального скидного клапана.
- Постумова: Тиск у камері опустився нижче 1.1 бар. Таймаут: 30 000 мс.

[6. Вакуумна сушка]
- Дія: Повторний запуск вакуумного насоса для випаровування залишків конденсату з пористого матеріалу.
- Постумова: Таймер сушки 180 секунд при тиску P < 0.3 бар.

[7. Аерація та вирівнювання тиску]
- Дія: Впуск стерильного повітря через бактеріальний HEPA-фільтр.
- Постумова: Тиск у камері дорівнює атмосферному (1.00 ± 0.05 бар).
- Фініш: Подача звукового сигналу, зняття блокування з електрозамка дверей.
```

Кожен крок цього сценарію має власну специфіку: якщо на кроці 3 лопне паропровід, рушій не може просто кинути систему — він зобов'язаний зняти напругу з ТЕНів (запобігання прогару на сухому ходу) і закрити впускний клапан, після чого чекати безпечного скидання тиску перед розблокуванням дверей.

### 2. Передпольотний чеклист безпілотного апарата (Preflight & Arming)

В автопілотах безпілотних комплексів команда «Зведення моторів» (`Arming`) ніколи не виконується як прямий запис у регістри ШІМ. Вона розгортається у багатоетапний сценарій перевірок та калібрувань:

```
[1. Верифікація шин датчиків (Bus Health Check)]
- Дія: Опитування регістрів WhoAmI для основного та резервного IMU по шині SPI.
- Постумова: Обидва сенсори відповідають, помилки CRC на шині == 0. Таймаут: 100 мс.

[2. Прогрів та оцінка нульових зміщень (IMU Bias & Thermal Settle)]
- Передумова: Датчики відповідають.
- Дія: Пасивне очікування стабілізації внутрішньої температури гіроскопа до 45 °C.
- Постумова: Дисперсія шуму акселерометра < 0.05 g (апарат не рухається на вітрі). Таймаут: 5000 мс.

[3. Верифікація супутникової навігації (GNSS Lock & EKF Convergence)]
- Дія: Опитування навігаційного приймача.
- Постумова: 3D Fix захоплено, кількість супутників >= 10, HDOP < 1.3, інновації швидкості EKF < 0.3. Таймаут: 15 000 мс.

[4. Тестовий прогін рульових поверхонь (Servo Sweep Test)]
- Передумова: Живлення бортової мережі 5.2 ± 0.2 В.
- Дія: Послідовне відхилення елеронів та керма висоти на ±25° із вимірюванням споживаного струму сервоприводів.
- Постумова: Струм сервоприводів не перевищив 1.8 А (відсутнє механічне заклинювання тяг). Таймаут: 1200 мс.
- Відкат: Повернення всіх рульових поверхонь у нейтральне положення (0°).

[5. Холостий розгін моторів (Motor Spin-up Check)]
- Передумова: Рульові поверхні в нормі, оператор зняв блокування ручки газу.
- Дія: Подача мінімального газу (Spin When Armed, 12% тяги) по протоколу DShot.
- Постумова: Зворотна телеметрія регуляторів ESC підтверджує обертання всіх 4 моторів без зриву синхронізації. Таймаут: 1000 мс.
- Відкат: Миттєва подача команди DShot Motor Stop (0% тяги).

[6. Завершення: Стан ARMED]
- Зміна глобального режиму FSM на ARMED, увімкнення бортового реєстратора чорної скриньки (Blackbox).
```

## Повна реалізація рушія макросценаріїв

Нижче наведено повну промислову реалізацію рушія виконання макросценаріїв мовами C та C++.

Код реалізує:
- Декларативний опис масиву кроків.
- Неблокуюче квантування часу з контролем переповнення лічильника мікроконтролера.
- Перевірку передумов, постумов та наскрізних інваріантів.
- Динамічний стек LIFO для гарантованої компенсації збоїв.

:::tabs
```c
#include <stdbool.h>
#include <stdint.h>
#include <stddef.h>

#define SCENARIO_MAX_STEPS       16
#define SCENARIO_ROLLBACK_STACK  16

/* Статуси виконання сценарію */
typedef enum {
    SCENARIO_IDLE = 0,
    SCENARIO_RUNNING,
    SCENARIO_SUCCESS,
    SCENARIO_FAILED,
    SCENARIO_ROLLING_BACK,
    SCENARIO_ABORTED_SAFE
} ScenarioState;

/* Коди помилок виконання */
typedef enum {
    SCENARIO_ERR_NONE = 0,
    SCENARIO_ERR_PRECONDITION,
    SCENARIO_ERR_TIMEOUT,
    SCENARIO_ERR_INVARIANT,
    SCENARIO_ERR_USER_ABORT
} ScenarioError;

/* Фази життєвого циклу окремого кроку */
typedef enum {
    STEP_STATE_IDLE = 0,
    STEP_STATE_PRECHECK,
    STEP_STATE_ENTER,
    STEP_STATE_EXECUTING,
    STEP_STATE_DONE
} StepState;

/* Типи функціональних покажчиків */
typedef void (*ActionFn)(void* ctx);
typedef bool (*PredicateFn)(void* ctx);

/* Структура декларативного кроку сценарію */
typedef struct {
    const char*   name;              /* Назва кроку для логування */
    ActionFn      action;            /* Дія активації */
    PredicateFn   precondition;      /* Передумова (може бути NULL) */
    PredicateFn   postcondition;     /* Постумова (може бути NULL) */
    ActionFn      rollback;          /* Компенсаційна дія при відкаті (може бути NULL) */
    uint32_t      timeout_ms;        /* Таймаут досягнення постумови */
    uint32_t      settle_delay_ms;   /* Затримка стабілізації перед перевіркою */
} ScenarioStep;

/* Дескриптор рушія сценаріїв */
typedef struct {
    const ScenarioStep* steps;
    size_t              step_count;
    size_t              current_step_idx;
    ScenarioState       state;
    ScenarioError       last_error;
    StepState           step_phase;
    uint32_t            step_start_ms;
    void*               context;
    PredicateFn         invariant_checker; /* Наскрізний інваріант безпеки */

    /* Стек дій відкату (LIFO) */
    ActionFn            rollback_stack[SCENARIO_ROLLBACK_STACK];
    size_t              rollback_count;
    size_t              rollback_current_idx;
} ScenarioEngine;

/* Ініціалізація рушія */
void scenario_init(ScenarioEngine* engine, void* context, PredicateFn invariant_checker) {
    if (!engine) return;
    engine->steps = NULL;
    engine->step_count = 0;
    engine->current_step_idx = 0;
    engine->state = SCENARIO_IDLE;
    engine->last_error = SCENARIO_ERR_NONE;
    engine->step_phase = STEP_STATE_IDLE;
    engine->step_start_ms = 0;
    engine->context = context;
    engine->invariant_checker = invariant_checker;
    engine->rollback_count = 0;
    engine->rollback_current_idx = 0;
}

/* Запуск сценарію на виконання */
bool scenario_start(ScenarioEngine* engine, const ScenarioStep* steps, size_t count, uint32_t now_ms) {
    if (!engine || !steps || count == 0 || count > SCENARIO_MAX_STEPS) {
        return false;
    }
    if (engine->state == SCENARIO_RUNNING || engine->state == SCENARIO_ROLLING_BACK) {
        return false; /* Захист від повторного входу (Reentrancy) */
    }

    engine->steps = steps;
    engine->step_count = count;
    engine->current_step_idx = 0;
    engine->state = SCENARIO_RUNNING;
    engine->last_error = SCENARIO_ERR_NONE;
    engine->step_phase = STEP_STATE_PRECHECK;
    engine->step_start_ms = now_ms;
    engine->rollback_count = 0;
    engine->rollback_current_idx = 0;
    return true;
}

/* Примусове скасування сценарію з відкатом */
void scenario_abort(ScenarioEngine* engine, ScenarioError error) {
    if (!engine || engine->state != SCENARIO_RUNNING) return;
    engine->state = SCENARIO_ROLLING_BACK;
    engine->last_error = error;
    engine->rollback_current_idx = engine->rollback_count;
}

/* Періодичний неблокуючий тік рушія */
void scenario_tick(ScenarioEngine* engine, uint32_t now_ms) {
    if (!engine) return;

    /* Обробка фази відкату (Rollback Execution) */
    if (engine->state == SCENARIO_ROLLING_BACK) {
        if (engine->rollback_current_idx > 0) {
            engine->rollback_current_idx--;
            ActionFn undo_action = engine->rollback_stack[engine->rollback_current_idx];
            if (undo_action) {
                undo_action(engine->context);
            }
        } else {
            engine->state = SCENARIO_ABORTED_SAFE;
        }
        return;
    }

    if (engine->state != SCENARIO_RUNNING) {
        return;
    }

    /* 1. Перевірка наскрізних інваріантів безпеки */
    if (engine->invariant_checker && !engine->invariant_checker(engine->context)) {
        scenario_abort(engine, SCENARIO_ERR_INVARIANT);
        return;
    }

    const ScenarioStep* step = &engine->steps[engine->current_step_idx];

    switch (engine->step_phase) {
        case STEP_STATE_PRECHECK:
            if (step->precondition && !step->precondition(engine->context)) {
                scenario_abort(engine, SCENARIO_ERR_PRECONDITION);
                return;
            }
            engine->step_phase = STEP_STATE_ENTER;
            /* Продовжуємо виконання без затримки на наступний блок */
            __attribute__((fallthrough));

        case STEP_STATE_ENTER:
            if (step->action) {
                step->action(engine->context);
            }
            /* Реєстрація компенсатора у LIFO стеку */
            if (step->rollback && engine->rollback_count < SCENARIO_ROLLBACK_STACK) {
                engine->rollback_stack[engine->rollback_count++] = step->rollback;
            }
            engine->step_start_ms = now_ms;
            engine->step_phase = STEP_STATE_EXECUTING;
            break;

        case STEP_STATE_EXECUTING: {
            uint32_t elapsed_ms = (uint32_t)(now_ms - engine->step_start_ms);

            /* Перевірка таймауту виконання кроку */
            if (step->timeout_ms > 0 && elapsed_ms >= step->timeout_ms) {
                scenario_abort(engine, SCENARIO_ERR_TIMEOUT);
                return;
            }

            /* Перевірка витримки часу стабілізації */
            if (elapsed_ms < step->settle_delay_ms) {
                return; /* Очікуємо завершення перехідного процесу */
            }

            /* Перевірка постумови */
            bool step_done = true;
            if (step->postcondition) {
                step_done = step->postcondition(engine->context);
            }

            if (step_done) {
                engine->current_step_idx++;
                if (engine->current_step_idx >= engine->step_count) {
                    engine->state = SCENARIO_SUCCESS;
                    engine->rollback_count = 0; /* Очищення стека після повного успіху */
                } else {
                    engine->step_phase = STEP_STATE_PRECHECK;
                }
            }
            break;
        }

        default:
            engine->state = SCENARIO_FAILED;
            break;
    }
}
```

```cpp
#include <cstdint>
#include <cstddef>
#include <string_view>
#include <vector>
#include <span>
#include <functional>
#include <expected>
#include <chrono>

/* Типізовані стани та коди результатів сценарію */
enum class ScenarioStatus : uint8_t {
    Idle,
    Running,
    Success,
    Failed,
    RollingBack,
    AbortedSafe
};

enum class ScenarioError : uint8_t {
    None,
    PreconditionFailed,
    Timeout,
    InvariantViolated,
    UserAborted,
    EngineBusy
};

/* Декларативний крок сценарію на базі C++20 */
struct ScenarioStep {
    std::string_view             name;
    std::function<void()>        action;
    std::function<bool()>        precondition;      /* Може бути порожнім */
    std::function<bool()>        postcondition;     /* Може бути порожнім */
    std::function<void()>        rollback;          /* Компенсатор LIFO */
    std::chrono::milliseconds    timeout{0};
    std::chrono::milliseconds    settle_delay{0};
};

class ScenarioEngine {
public:
    using InvariantChecker = std::function<bool()>;

    explicit ScenarioEngine(InvariantChecker invariant_fn = nullptr)
        : invariant_checker_(std::move(invariant_fn)) {}

    /* Запуск сценарію на виконання */
    std::expected<void, ScenarioError> start(std::span<const ScenarioStep> steps,
                                            std::chrono::milliseconds now) {
        if (steps.empty()) {
            return std::unexpected(ScenarioError::PreconditionFailed);
        }
        if (status_ == ScenarioStatus::Running || status_ == ScenarioStatus::RollingBack) {
            return std::unexpected(ScenarioError::EngineBusy);
        }

        steps_ = steps;
        current_step_idx_ = 0;
        status_ = ScenarioStatus::Running;
        last_error_ = ScenarioError::None;
        step_phase_ = StepPhase::Precheck;
        step_start_time_ = now;
        rollback_stack_.clear();
        return {};
    }

    /* Примусове скасування з ініціалізацією компенсацій */
    void abort(ScenarioError error) {
        if (status_ != ScenarioStatus::Running) return;
        status_ = ScenarioStatus::RollingBack;
        last_error_ = error;
    }

    /* Періодичний неблокуючий тік рушія */
    void tick(std::chrono::milliseconds now) {
        if (status_ == ScenarioStatus::RollingBack) {
            process_rollback();
            return;
        }

        if (status_ != ScenarioStatus::Running) {
            return;
        }

        /* 1. Наскрізні інваріанти безпеки */
        if (invariant_checker_ && !invariant_checker_()) {
            abort(ScenarioError::InvariantViolated);
            return;
        }

        const auto& step = steps_[current_step_idx_];

        switch (step_phase_) {
            case StepPhase::Precheck:
                if (step.precondition && !step.precondition()) {
                    abort(ScenarioError::PreconditionFailed);
                    return;
                }
                step_phase_ = StepPhase::Enter;
                [[fallthrough]];

            case StepPhase::Enter:
                if (step.action) {
                    step.action();
                }
                if (step.rollback) {
                    rollback_stack_.push_back(step.rollback);
                }
                step_start_time_ = now;
                step_phase_ = StepPhase::Executing;
                break;

            case StepPhase::Executing: {
                auto elapsed = now - step_start_time_;

                /* Перевірка таймауту */
                if (step.timeout > std::chrono::milliseconds::zero() && elapsed >= step.timeout) {
                    abort(ScenarioError::Timeout);
                    return;
                }

                /* Витримка технологічної затримки стабілізації */
                if (elapsed < step.settle_delay) {
                    return;
                }

                /* Перевірка постумови */
                bool done = true;
                if (step.postcondition) {
                    done = step.postcondition();
                }

                if (done) {
                    current_step_idx_++;
                    if (current_step_idx_ >= steps_.size()) {
                        status_ = ScenarioStatus::Success;
                        rollback_stack_.clear();
                    } else {
                        step_phase_ = StepPhase::Precheck;
                    }
                }
                break;
            }
        }
    }

    [[nodiscard]] ScenarioStatus status() const noexcept { return status_; }
    [[nodiscard]] ScenarioError last_error() const noexcept { return last_error_; }
    [[nodiscard]] size_t current_step() const noexcept { return current_step_idx_; }

private:
    enum class StepPhase : uint8_t { Precheck, Enter, Executing };

    void process_rollback() {
        if (!rollback_stack_.empty()) {
            auto undo = rollback_stack_.back();
            rollback_stack_.pop_back();
            if (undo) {
                undo();
            }
        } else {
            status_ = ScenarioStatus::AbortedSafe;
        }
    }

    std::span<const ScenarioStep> steps_{};
    size_t                        current_step_idx_{0};
    ScenarioStatus                status_{ScenarioStatus::Idle};
    ScenarioError                 last_error_{ScenarioError::None};
    StepPhase                     step_phase_{StepPhase::Precheck};
    std::chrono::milliseconds     step_start_time_{0};
    InvariantChecker              invariant_checker_{nullptr};
    std::vector<std::function<void()>> rollback_stack_{};
};
```

## Практичні пастки та крайові випадки у вбудованих системах

Під час перенесення концепції сценаріїв у реальне апаратне середовище розробник стикається з низкою критичних крайових ситуацій.

### 1. Захист від повторного входу (Reentrancy Protection)
Якщо користувач повторно натискає кнопку старту або наземна станція надсилає дублюючий пакет по мережі, коли сценарій уже перебуває на кроці 2, рушій повинен детерміновано відхилити повторний запуск із поверненням статусу зайнятості (`ScenarioError::EngineBusy`). Спроба перезаписати покажчики активного сценарію на ходу призведе до втрати стека компенсацій і залишить раніше активовані актуатори у «підвішеному» стані.

### 2. Граничні випадки датчиків: брязкіт і фальшиві спрацьовування
Фізичні сенсори (механічні кінцевики, реле тиску) мають брязкіт контактів і високочастотний шум. Якщо постумова `sensor_is_triggered()` поверне `true` на 100 мікросекунд через електромагнітну наводку від увімкнення сусіднього контактора, сценарій передчасно перейде на наступний крок.
*Правило проектування:* постумова мусить інтегрувати цифровий фільтр або підтверджувати стабільність сигналу протягом 2–3 послідовних викликів `scenario_tick()` (Debounce Window).

### 3. Раптова втрата живлення (Power-cut Recovery)
Якщо мікроконтролер повністю знеструмлюється на кроці 3, оперативна пам'ять (RAM) і стек компенсацій обнуляються. При наступному вмиканні живлення система завантажиться у стані `IDLE`, тоді як фізичні бістабільні клапани або мотори можуть залишитися у напіввідкритому положенні.
*Правило проектування:* критичні кроки повинні записувати монотонний індекс активної фази в енергонезалежну пам'ять (EEPROM / FRAM). Під час ініціалізації після зняття скидання (`Reset Handler`) прошивка перевіряє маркер незавершеного сценарію і за потреби запускає процедуру початкового зведення (Homing & Safe Initialization Sequence).

### 4. Розмежування аварійного відкату та апаратної відсічки (Kill-Switch)
Програмний відкат через LIFO-стек є надійним інструментом ліквідації штатних збоїв (таймаутів, відмов датчиків). Проте він не замінює апаратний захист: якщо в системі виникає коротке замикання, загоряння або механічне заклинювання, що загрожує життю людини, спрацьовує фізичний розмикач аварійної зупинки, який апаратно знеструмлює силові шини живлення в обхід будь-якого програмного коду.

### 5. Джиттер періоду виклику та витіснення перериваннями
У неблокуючих системах функція `scenario_tick()` викликається у головному суперциклі. Якщо сусідня задача (наприклад, розрахунок криптографічного підпису або збереження великого блоку у Flash) затримає цикл на 50 мс, крок сценарію не отримає виклику точно в очікуваний момент.
*Правило проектування:* таймаути кроків та інтервали витримки стабілізації завжди розраховуються за абсолютним монотонним годинником `millis()`, а не за кількістю викликів функції `tick()`. Завдяки цьому джиттер суперциклу впливає лише на дискретність перевірки умови (±1 такт), але не спотворює реальний фізичний час експозиції.
