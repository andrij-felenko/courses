# 📋 Специфікація маніфесту кампанії оновлення та протоколу звітування парку

Маніфест кампанії оновлення визначає правила, за якими сервер керування розгортає нову версію прошивки на парк із тисячі пристроїв: склад когорт, часові вікна рандомізованого очікування, порогові критерії аварійної зупинки та формат повідомлень телеметрії стану кожного вузла. Без чітко специфікованої схеми даних клієнтський стек не зможе детерміновано обчислити власну належність до когорти, а бекенд оркестрації втратить можливість автоматично виявляти аномалії та зупиняти розгортання до настання масових відмов.

Специфікація складається з двох взаємопов'язаних частин: **маніфесту кампанії** (англ. *rollout campaign manifest*), який сервер публікує через захищений канал розповсюдження конфігурацій, та **протоколу звітування стану пристрою** (англ. *device state report protocol*), за яким кожен мікроконтролер передає поточну фазу власного життєвого циклу оновлення на сервер телеметрії.

## 1. Архітектурні вимоги до контракту оновлення

Під час проектування взаємодії між сервером оркестрації та тисячею польових контролерів контракт оновлення повинен гарантувати виконання чотирьох фундаментальних інваріантів:

1. **Криптографічна автентичність.** Маніфест не може передаватися як відкритий непідписаний JSON. Будь-яка модифікація полів (підміна URL, зниження порогу когорти чи зміна хешу) має призводити до відхилення маніфесту на етапі перевірки цифрового підпису асиметричним ключем виробника.
2. **Ідемпотентність та стійкість до повторів.** У бездротових мережах зі слабким покриттям пристрій може отримати один і той самий маніфест кілька разів або отримати застарілий маніфест попередньої кампанії. Ідентифікатор кампанії `campaign_id` у форматі UUIDv4 разом із семантичною версією `firmware_version` дозволяє вузлу однозначно відрізнити нове завдання від уже виконаного або скасованого.
3. **Апаратна прив'язка.** Прошивка, скомпільована для ревізії плати `rev_C` (наприклад, із чипом Flash на 16 МБ та іншою розпіновкою інтерфейсу SPI), не повинна завантажуватися на плати ревізії `rev_A` (де встановлено чип на 4 МБ). Поле `target_hw_rev` забезпечує жорстку фільтрацію на рівні клієнта ще до початку завантаження двійкових блоків.
4. **Автономність обчислення когорт.** Бекенд не зберігає списки ідентифікаторів пристроїв для кожної фази. Розподіл на когорти здійснюється детерміновано на самому мікроконтролері на основі криптографічного гешу від унікального ідентифікатора чипа та солі `campaign_salt`.

### Детальний опис полів маніфесту

- **`campaign_id`**: унікальний глобальний ідентифікатор сесії оновлення. Використовується клієнтом для тегування всіх журналів, повідомлень про помилки та звітів про прогрес. Якщо сервер перезапускає кампанію з новим бінарником, генерується новий `campaign_id`.
- **`target_hw_rev`**: ідентифікатор апаратної сумісності. Вбудована прошивка перед початком будь-яких мережевих операцій зчитує апаратну ревізію з одноразово програмованих регістрів (OTP/eFuses) або резистивного дільника на платі. У разі невідповідності маніфест ігнорується зі збереженням помилки `ERR_HW_REV_MISMATCH`.
- **`firmware_digest_sha256`**: контрольна сума файлу прошивки. Обчислюється як побайтовий SHA-256 повного двійкового файлу `firmware.bin`. Мікроконтролер виконує потокове обчислення гешу під час запису блоків у Flash і фінальну верифікацію перед перезавантаженням.
- **`signature_ed25519`**: цифровий підпис Ed25519 (довжиною 64 байти, представлений 128 шістнадцятковими символами). Підпис створюється на закритому ключі реліз-сервера над хешем образу. Відкритий ключ для перевірки вшивається в постійну пам'ять завантажувача під час заводського програмування плати.
- **`campaign_salt`**: 16-байтний випадковий вектор ініціалізації. Забезпечує статистичну незалежність вибірки пристроїв у канаркових когортах між різними кампаніями. Завдяки цьому пристрої фази 1% щоразу обираються випадково серед усього парку.
- **`stages`**: масив фаз поетапного розгортання. Сервер відкриває фази послідовно. Поле `cohort_percent_cutoff` задає верхню межу процентиля: наприклад, значення `5` допускає до оновлення всі пристрої з хешем у межах `[0..4]`.
- **`abort_policy`**: політика безпеки, що визначає автоматичні дії сервера та клієнта у разі виникнення аномалій. Якщо частка відмов перевищує `max_failure_rate_percent`, сервер блокує розгортання для решти парку.

## 4. Протокол звітування стану пристрою (Telemetry Reports)

Кожен пристрій зобов'язаний інформувати бекенд оркестрації про кожну зміну внутрішнього стану оновлення за протоколом MQTT (з якістю обслуговування QoS 1 на тему `devices/{device_id}/ota/status`) або через періодичний HTTP/2 POST-запит на ендпоінт `/api/v1/campaigns/{campaign_id}/status`.

### Схема повідомлення звіту пристрою

```json
{
  "device_id": "dev-mcu-00482",
  "campaign_id": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
  "timestamp_utc": 1724810400,
  "calculated_cohort_bucket": 17,
  "state": "TESTING_HEALTH",
  "boot_bank": "BANK_B",
  "active_version": "2.0.0",
  "previous_version": "1.8.4",
  "progress_percent": 100,
  "battery_millivolts": 4120,
  "rssi_dbm": -68,
  "error_code": 0,
  "watchdog_boot_count": 0,
  "self_test_flags": {
    "flash_integrity_ok": true,
    "sensor_i2c_bus_ok": true,
    "radio_uplink_ok": true,
    "crypto_element_ok": true
  }
}
```

### Словник станів пристрою (`state`)

| Стан пристрою | Значення та поведінка вузла | Наступний очікуваний перехід |
|---|---|---|
| `IDLE` | Пристрій отримав маніфест, але за значенням `calculated_cohort_bucket` ще не допущений до поточної активної фази. Перебуває у штатному режимі роботи. | `COHORT_WAIT` або завершення кампанії |
| `COHORT_WAIT` | Пристрій допущений до оновлення, але очікує випадковий час у межах вікна `jitter_window_seconds` для запобігання перевантаженню сервера. | `DOWNLOADING` |
| `DOWNLOADING` | Виконується секційне завантаження блоків двійкового образу з CDN. Поточний прогрес записується у неактивний Bank B. | `FLASH_STAGED` або помилка мережі |
| `FLASH_STAGED` | Образ повністю записано у Flash, контрольний хеш SHA-256 та цифровий підпис Ed25519 успішно перевірено. Встановлено прапорець пробного запуску. | `REBOOT_PENDING` |
| `REBOOT_PENDING` | Пристрій очікує безпечного технологічного моменту для перезавантаження (відсутність відкритих клапанів, завершення сеансу телеметрії). | `TESTING_HEALTH` |
| `TESTING_HEALTH` | Пристрій завантажився в Bank B. Працює тестове вікно самодіагностики (Health Window), сторожовий таймер працює в посиленому режимі контролю. | `COMMITTED` або `ROLLBACK_TRIGGERED` |
| `COMMITTED` | Випробувальний термін успішно пройдено, Bank B зафіксовано як постійний завантажувальний розділ, лічильник збоїв скинуто в 0. | `IDLE` |
| `ROLLBACK_TRIGGERED` | Нова прошивка спричинила збій самодіагностики або спрацювання апаратного Watchdog. Виконано апаратний відкат на Bank A. | `IDLE` (із заблокованим оновленням) |
| `ERROR_ABORTED` | Завантаження чи встановлення скасовано сигналом сервера через аварійну зупинку всієї кампанії. Тимчасові блоки у Bank B очищено. | `IDLE` |


## 5. Обробка крайових випадків та зворотний зв'язок

У реальній експлуатації виникають нестандартні сценарії, які повинні коректно оброблятися протоколом:

1. **Втрата живлення під час завантаження (`DOWNLOADING`).** Якщо живлення зникає під час запису 45-го блоку прошивки, контролер після перезапуску не повинен починати завантаження з нуля. Завдяки збереженню бітової карти отриманих блоків у незалежному секторі EEPROM пристрій відновлює сесію HTTP Range і довантажує лише відсутні блоки.
2. **Розсинхронізація годинника (Clock Skew).** В автономних вузлах без синхронізації часу за NTP або GNSS системний годинник реального часу (RTC) може мати зсув на кілька діб. Тому тривалість вікна джитера `jitter_window_seconds` та вікна спостереження `soak_time_seconds` інтерпретуються клієнтом як відносні інтервали монотонного таймера (`uptime`), а не як абсолютні мітки часу UTC.
3. **Аварійний сигнал переривання кампанії (Server Override).** Якщо моніторинг виявляє аномалії в метриках когорти, сервер оркестрації транслює на тему MQTT `devices/fleet/control/campaign` або надсилає у відповідь на черговий статус-звіт керуючу директиву:

```json
{
  "command": "CAMPAIGN_OVERRIDE",
  "campaign_id": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
  "target_action": "FREEZE_AND_ROLLBACK",
  "reason": "Abort trigger tripped: watchdog reset rate 4.2% exceeds threshold 2.0%"
}
```

При отриманні цієї директиви пристрої, які перебувають у станах `COHORT_WAIT` чи `DOWNLOADING`, негайно скасовують завантаження та звільняють ресурси; пристрої у стані `TESTING_HEALTH` ініціюють контрольований відкат на стабільний Bank A.
