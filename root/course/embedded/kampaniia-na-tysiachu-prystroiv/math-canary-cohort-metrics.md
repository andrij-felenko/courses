# 🧮 Математична модель канаркових когорт та оцінка ризику відмов

Вибір розмірів когорт (1%, 5%, 25%, 100%) для парку з 1000 пристроїв підпорядковується законам біноміального розподілу й теорії статистичних рішень. Інженерне завдання полягає у визначенні мінімального розміру канаркової групи, достатнього для виявлення дефекту з заданою ймовірністю прояву `p`, за умови мінімізації кількості вузлів, які можуть вийти з ладу в разі критичної помилки.

## 1. Ймовірність виявлення дефекту у вибірці

Нехай у новій прошивці присутній прихований дефект (наприклад, гонка потоків при нестабільному радіосигналі або переповнення буфера), що призводить до перезавантаження вузла з ймовірністю `p` на одному пристрої протягом вікна спостереження.

Якщо випробувальна когорта містить `n` незалежних пристроїв, випадкова величина `X` (кількість вузлів, що зазнали збою) описується біноміальним розподілом `B(n, p)`.

Ймовірність зафіксувати хоча б один збій `P(X ≥ 1)` виводиться як протилежність події, коли жоден із `n` пристроїв не зазнав аварії:

```
P(X ≥ 1)
= 1 - P(X = 0)                       [закон протилежної події]
= 1 - (n! / (0! · (n - 0)!)) · p⁰ · (1 - p)ⁿ  [формула Бернуллі для k = 0]
= 1 - 1 · 1 · (1 - p)ⁿ               [спрощення факторіалів і нульових степенів]
= 1 - (1 - p)ⁿ                       [підсумкова ймовірність виявлення]
```

### Обчислення ймовірності виявлення для різних когорт

Розглянемо три класи дефектів за ймовірністю прояву `p`:
1. **Масовий критичний баг (`p = 0.30`, 30%):** проявляється майже на кожному третьому вузлі (наприклад, збій ініціалізації драйвера Flash).
2. **Помірний дефект (`p = 0.05`, 5%):** виникає лише за певних умов зв'язку або рівня сигналу.
3. **Рідкісна гранична аномалія (`p = 0.01`, 1%):** проявляється лише раз на сотню пристроїв (наприклад, витік пам'яті за добу активного обміну).

Підставимо розміри когорт у формулу `P(X ≥ 1) = 1 - (1 - p)ⁿ`:

**Для фази 1% (`n = 10` пристроїв з 1000):**
```
Критичний баг (p = 0.30):
P(X ≥ 1)
= 1 - (1 - 0.30)¹⁰                   [підстановка n = 10, p = 0.30]
= 1 - (0.70)¹⁰                       [обчислення степеня]
= 1 - 0.0282                         [результат піднесення]
= 0.9718 ≈ 97.2%                     [ймовірність виявлення]

Помірний баг (p = 0.05):
P(X ≥ 1)
= 1 - (1 - 0.05)¹⁰                   [підстановка n = 10, p = 0.05]
= 1 - (0.95)¹⁰                       [обчислення степеня]
= 1 - 0.5987                         [результат піднесення]
= 0.4013 ≈ 40.1%                     [ймовірність виявлення]

Рідкісний баг (p = 0.01):
P(X ≥ 1)
= 1 - (1 - 0.01)¹⁰                   [підстановка n = 10, p = 0.01]
= 1 - (0.99)¹⁰                       [обчислення степеня]
= 1 - 0.9044                         [результат піднесення]
= 0.0956 ≈ 9.6%                      [ймовірність виявлення]
```

**Для фази 5% (`n = 50` пристроїв з 1000):**
```
Помірний баг (p = 0.05):
P(X ≥ 1)
= 1 - (1 - 0.05)⁵⁰                   [підстановка n = 50, p = 0.05]
= 1 - (0.95)⁵⁰                       [обчислення степеня]
= 1 - 0.0769                         [результат піднесення]
= 0.9231 ≈ 92.3%                     [ймовірність виявлення]

Рідкісний баг (p = 0.01):
P(X ≥ 1)
= 1 - (1 - 0.01)⁵⁰                   [підстановка n = 50, p = 0.01]
= 1 - (0.99)⁵⁰                       [обчислення степеня]
= 1 - 0.6050                         [результат піднесення]
= 0.3950 ≈ 39.5%                     [ймовірність виявлення]
```

**Для фази 25% (`n = 250` пристроїв з 1000):**
```
Рідкісний баг (p = 0.01):
P(X ≥ 1)
= 1 - (1 - 0.01)²⁵⁰                  [підстановка n = 250, p = 0.01]
= 1 - (0.99)²⁵⁰                      [обчислення степеня]
= 1 - 0.0811                         [результат піднесення]
= 0.9189 ≈ 91.9%                     [ймовірність виявлення]
```

Ці розрахунки демонструють математичну необхідність східчастої структури:
- Когорта **1% (10 вузлів)** гарантовано (97.2%) відсікає фатальні системні помилки, ризикуючи лише десятьма пристроями.
- Когорта **5% (50 вузлів)** з імовірністю понад 92% виявляє помірні баги (5%-ві збої).
- Когорта **25% (250 вузлів)** виявляє навіть тонкі дефекти частотою 1% з надійністю майже 92% до того, як оновлення отримає решта 75% парку.

## 2. Розрахунок необхідного розміру вибірки під задану довірчу ймовірність

Якщо інженерна вимога вимагає виявити дефект з частотою `p` з надійністю не менше ніж `1 - β` (де `1 - β` — статистична потужність тесту, наприклад 0.95 або 95%), мінімальний розмір когорти `n` обчислюється логарифмуванням:

```
1 - (1 - p)ⁿ ≥ 1 - β                 [вихідна нерівність потужності]
(1 - p)ⁿ ≤ β                         [віднімання одиниці та зміна знака]
ln((1 - p)ⁿ) ≤ ln(β)                 [логарифмування обох частин]
n · ln(1 - p) ≤ ln(β)                [властивість логарифма степеня]
n ≥ ln(β) / ln(1 - p)                [ділення на від'ємний ln(1 - p)]
```

Для малих значень `p` можна скористатися наближенням `ln(1 - p) ≈ -p`:

```
n
≈ ln(β) / (-p)                       [підстановка першого члена ряду Тейлора]
= -ln(β) / p                         [винесення знака мінус]
= ln(1 / β) / p                      [властивість логарифма оберненого числа]
```

Для довірчої ймовірності 95% (`β = 0.05`, `ln(1 / 0.05) ≈ 2.9957 ≈ 3.0`):

```
n_95%
≈ 3 / p                              [правило трьох для 95% довіри]
```

Наприклад, для гарантованого (95%) виявлення багу, що вражає `p = 2%` пристроїв:
```
n
≈ 3 / 0.02                           [підстановка p = 0.02]
= 150                                [необхідний розмір вибірки]
```

## 3. Час спостереження (Soak Time) та моделювання часу до відмови

Розмір когорти `n` визначає лише просторову вибірку, тоді як тривалість спостереження `T_soak` визначає часову вибірку. Багато вбудованих дефектів (витоки пам'яті, переповнення 32-розрядних лічильників мілісекунд `SysTick`, фрагментація динамічної купи) проявляються не в момент старту, а після накопичення певної кількості робочих циклів.

Нехай час безвідмовної роботи вузла описується експоненційним розподілом з інтенсивністю збоїв `λ` (середній час між збоями `MTBF = 1 / λ`). Ймовірність того, що дефект проявиться протягом вікна спостереження тривалістю `t`, становить:

```
F(t) = 1 - e^(-λ · t)
```

Якщо дефект спричиняє падіння в середньому раз на 72 години роботи (`λ = 1 / 72` год⁻¹), то за скороченого вікна спостереження `t = 12` годин імовірність зафіксувати збій на одному вузлі становить лише:

```
F(12)
= 1 - e^(-12 / 72)                   [підстановка t = 12, λ = 1/72]
= 1 - e^(-0.1667)                    [обчислення експоненти]
= 1 - 0.8465
= 0.1535 ≈ 15.4%                     [ймовірність прояву на окремому вузлі]
```

Сукупна ймовірність зловити такий дефект у когорті з `n = 50` пристроїв за 12 годин:

```
P_detect(12 год, n = 50)
= 1 - (1 - 0.1535)⁵⁰                 [біноміальна ймовірність для p = 0.1535]
= 1 - (0.8465)⁵⁰
= 1 - 0.00024
= 0.99976 ≈ 99.98%                   [висока ймовірність виявлення завдяки розміру когорти]
```

Звідси випливає фундаментальний інженерний висновок: **збільшення розміру когорти частково компенсує скорочення часу спостереження**. Якщо компанія прагне скоротити релізний цикл, вона повинна збільшити розмір канаркової когорти, щоб сукупний обсяг напрацювання в приладо-годинах (`n · t`) залишався достатнім для виявлення дефектів із низькою інтенсивністю `λ`.

## 4. Байєсівська оцінка надійності релізу за результатами випробувального вікна

Коли канаркова когорта розміром `n` відпрацювала вікно спостереження `T_soak` і зафіксувала `k = 0` збоїв, інженер має оцінити: яка верхня межа реальної ймовірності відмови `p` для всього парку?

Застосуємо теорему Байєса з рівномірним апріорним розподілом ймовірності дефекту `p ∈ [0, 1]`. Апостеріорна густина ймовірності описується бета-розподілом `Beta(1, n + 1)`:

```
f(p | k = 0)
= (n + 1) · (1 - p)ⁿ                 [апостеріорний розподіл для k = 0]
```

Ймовірність того, що справжній рівень дефектів у прошивці не перевищує порогового значення `p_max`:

```
P(p ≤ p_max | k = 0)
= ∫ [0..p_max] (n + 1) · (1 - p)ⁿ dp [інтегрування апостеріорної густини]
= -(1 - p)ⁿ⁺¹ | [0..p_max]           [первісна функція]
= 1 - (1 - p_max)ⁿ⁺¹                 [результат інтегрування]
```

Якщо на фазі 5% (`n = 50`) за 48 годин не сталося жодного збою, довірча ймовірність того, що реальний рівень дефектів прошивки `p ≤ 5%`:

```
P(p ≤ 0.05 | n = 50, k = 0)
= 1 - (1 - 0.05)⁵¹                   [підстановка n = 50, p_max = 0.05]
= 1 - (0.95)⁵¹                       [обчислення степеня]
= 1 - 0.0731
= 0.9269 ≈ 92.7%                     [висока довіра до безпеки переходу до наступної фази]
```

## 5. Вплив офлайн-вузлів на ефективний розмір когорти (Effective Sample Size)

У реальному парку з 1000 пристроїв певна частка вузлів `p_offline` завжди перебуває поза зв'язком (вимкнені рубильником, розряджені або перебувають у зоні тимчасової відсутності стільникового покриття). Якщо номінальний розмір когорти становить `n = 50`, а частка офлайн-вузлів дорівнює `10%`, реальний ефективний розмір вибірки зменшується:

```
n_eff = n_nominal · (1 - p_offline)
```

Для `n = 50` та `p_offline = 0.10`:

```
n_eff = 50 · 0.90 = 45 пристроїв
```

Якщо система моніторингу інтерпретує відсутність звіту від офлайн-вузла як успішне проходження оновлення, знаменник розрахунку викривляється, штучно занижуючи розрахований відсоток аварій. Тому в розрахунку рівня відмов `R_crash` у знаменник підставляються виключно ті пристрої, які успішно завантажили образ і підтвердили початок виконання фази випробування:

```
R_failure = (k_crashes + k_watchdog_resets) / n_confirmed_started
```

## 6. Модель споживання бюджету помилок (Error Budget Consumption)

Нехай для сервісу встановлено цільовий рівень доступності парку (Service Level Objective, SLO) `99.5%` за місяць. Це означає, що допустимий бюджет відмов становить `0.5%` від сукупного часу роботи парку:

```
SLO = 99.5%
Error_Budget = 100% - 99.5% = 0.5%
```

Для парку з `N = 1000` пристроїв сукупний місячний бюджет помилок у приладо-годинах (`T_month = 720` годин):

```
Total_Device_Hours
= N · T_month                        [загальний фонд часу парку]
= 1000 · 720
= 720000 приладо-годин

Allowed_Downtime_Hours
= Total_Device_Hours · Error_Budget  [допустимий простий за бюджетом]
= 720000 · 0.005
= 3600 приладо-годин
```

Якщо під час розгортання на когорту `n = 50` пристроїв 3 пристрої зависли на 24 години до спрацювання відкату, вони спожили:

```
Consumed_Downtime
= 3 · 24                             [3 пристрої по 24 години]
= 72 приладо-години

Consumed_Budget_Percent
= (72 / 3600) · 100%                 [частка витраченого місячного бюджету]
= 2.0%                               [лише 2% від допустимої норми]
```

Якби оновлення викотили на всі 1000 пристроїв одночасно без канарки, дефект на 6% пристроїв (60 вузлів) за добу згенерував би:

```
Disaster_Downtime
= 60 · 24                            [60 вузлів по 24 години]
= 1440 приладо-годин                 [40% від усього місячного бюджету відмов компанії]
```

Цей розрахунок кількісно підтверджує, що канаркове розгортання з ранніми тригерами скасування зменшує втрати бюджету надійності у 20 разів порівняно з одномоментним глобальним релізом.
