Сервопривод промислового клапана високого тиску раптово перестає реагувати на команди оператора. Електродвигун продовжує обертати редуктор у крайній механічний упор, обмотки нагріваються понад сто градусів, але пристрій не перезавантажується ні через секунду, ні через годину. У прошивці мікроконтролера увімкнено апаратний сторожовий таймер (Watchdog Timer, WDT) з періодом спрацьовування 1.0 с, і під час лабораторних тестів штучне введення коду в порожній цикл `while (1) {}` бездоганно викликало апаратний ресет. Проте в реальному виробі система зависла намертво, а сторож жодного разу не спрацював.

Причина цієї аварії криється в архітектурній підміні понять: розробники перевіряли не життєздатність алгоритму керування, а факт виконання процесором хоч якихось інструкцій.

## Ілюзія захисту: три пастки «годування собаки»

У переважній більшості вбудованих систем сторожовий таймер налаштовують за найпростішим шаблоном: ініціалізувати периферійний блок на старті та періодично записувати магічне число в регістр перезаряджання (`kick the dog` або `watchdog reload`). Коли прошивка ускладнюється, виклики функції скидання починають конфліктувати з тривалими операціями (обчисленням фільтрів, записом у флеш-пам'ять, очікуванням мережевих пакетів). Замість перегляду архітектури інженер вдається до одного з трьох хибних рішень.

![Анатомія фальшивого скидання сторожа](/root/course/embedded/storozh-iakyi-spravdi-lovyt-zavysannia/img/wdt-failure-modes.svg)
*Три типові сценарії, де тривіальне скидання апаратного сторожа маскує повну відмову бізнес-логіки.*

### 1. Скидання всередині апаратного переривання (ISR)

Найпоширеніша й найнебезпечніша помилка — виклик скидання WDT з обробника періодичного переривання: системного таймера операційної системи (`SysTick_Handler` у FreeRTOS) або апаратного таймера загального призначення (`TIMx_IRQHandler`).

```
Процесорний контекст:
[ Головний потік ] ─── (Застряг у Deadlock / чекає I2C) ─── [ Зависання ]
       │
       ▼ (Апаратне переривання SysTick кожні 10 мс)
[ Обробник ISR   ] ─── IWDG->KR = 0xAAAA; (WDT скинуто) ─── [ Працює ]
```

Апаратні переривання мають вищий пріоритет виконання, ніж звичайні користувацькі потоки. Якщо потік керування застряг у нескінченному очікуванні готовності заблокованої шини зв'язку або два потоки схопили спільні м'ютекси у зворотному порядку (взаємне блокування, Deadlock), апаратний контролер переривань (NVIC) продовжує регулярно витісняти завислий потік, передавати керування функції обробника й успішно годувати сторожа. З погляду апаратного таймера система працює бездоганно, хоча корисна робота повністю паралізована.

### 2. Холостий цикл помилки (Runaway Loop)

Друга пастка виникає, коли виклик скидання розташований у головному нескінченному циклі `while (1)`, але поруч із кодом обробки збоїв:

:::tabs
```c
while (1) {
    status_t res = sensor_read_all();
    if (res != STATUS_OK) {
        // Помилка шини: пропускаємо розрахунок, але продовжуємо цикл
        wdt_refresh();
        continue;
    }
    control_step();
    wdt_refresh();
}
```
```cpp
while (true) {
    if (auto res = sensor.readAll(); !res) {
        // Помилка шини: пропускаємо розрахунок, але крутимо цикл
        watchdog.refresh();
        continue;
    }
    controller.step();
    watchdog.refresh();
}
```
:::

Якщо під час роботи відвалюється лінія живлення давача, функція `sensor_read_all()` миттєво повертає помилку `ERR_BUS_FAIL` без жодної затримки на читання даних. Цикл замість нормального періоду 20 мс починає крутитися на повній тактовій частоті процесора, виконуючи 500 000 ітерацій на секунду. Сторож отримує команду оновлення в тисячі разів частіше за штатний режим. Система не виконує стабілізації об'єкта, черги повідомлень переповнюються, але сторож не бачить у цьому жодної проблеми.

### 3. Процесорне голодування в RTOS (CPU Starvation)

У багатозадачних операційних системах реального часу (FreeRTOS, Zephyr, embOS) скидання сторожа нерідко прив'язують до окремого високопріоритетного завдання. Якщо інше критичне завдання безпеки (наприклад, потік контролю температури силового каскаду) має нижчий пріоритет або зависає на черзі повідомлень, високопріоритетне завдання продовжує отримувати кванти часу від планувальника і регулярно скидати WDT.

> 🔧 **Навіщо це.** Справжня мета сторожового таймера — перевіряти не факт тактування процесора, а **детерміноване просування бізнес-логіки вперед** із дотриманням усіх часових дедлайнів (liveness property).

Історично концепція сторожа виникла саме з потреби автоматичного виходу з непередбачених станів у критичних системах, від перших радарних комплексів до місії посадки на Місяць. Детальніше про це розповідає [Історія появи сторожових таймерів](root:embedded/storozh-iakyi-spravdi-lovyt-zavysannia/hist-watchdog-timer.md) (як реле та фазовий розподіл завдань у комп'ютері Apollo AGC рятували апарати від перевантаження).

## Внутрішній арсенал MCU: Незалежний (IWDG) проти Віконного (WWDG)

Сучасні мікроконтролери архітектури ARM Cortex-M містять щонайменше два принципово різних вбудованих сторожових модулі: незалежний сторож (Independent Watchdog, IWDG) та віконний сторож (Window Watchdog, WWDG). Вони призначені для виявлення різних типів апаратних і програмних відмов.

![Порівняння часових характеристик IWDG та WWDG](/root/course/embedded/storozh-iakyi-spravdi-lovyt-zavysannia/img/iwdg-vs-wwdg-timing.svg)
*Різниця зон скидання: IWDG дозволяє оновлення в будь-який момент до таймауту, WWDG карає ресетом за передчасне скидання.*

### Незалежний сторож (IWDG): захист від зупинки генераторів

Незалежний сторож спроектовано за принципом максимальної автономності від решти периферії кристала.

Головна особливість IWDG — власне виділене джерело тактування: внутрішній низькочастотний RC-генератор (Low-Speed Internal, LSI) із номінальною частотою 32–40 кГц. Лічильник IWDG є 12-бітним і рахує вниз від заданого значення перезавантаження (Reload Value, `RLR`) до нуля. Будь-який запис магічного ключа `0xAAAA` в регістр керування `IWDG->KR` перезавантажує лічильник початковим значенням.

Якщо основний кварцовий резонатор (HSE) пошкоджено вібрацією, фазове автопідстроювання частоти (PLL) збилося або ядро заснуло в нештатному режимі з блокуванням системної шини, лічильник IWDG на власному генераторі неминуче дійде до нуля і згенерує апаратний сигнал `MCU Reset`.

Проте IWDG має два серйозні обмеження:
1. **Низька точність RC-генератора:** частота LSI залежить від температури кристала та напруги живлення. Технологічний розкид для більшості мікроконтролерів становить від -40% до +50% (реальна частота в діапазоні від -40°C до +85°C може коливатися від 20 кГц до 50 кГц). Якщо сторож налаштований на номінальний таймаут 1000 мс, реальне спрацьовування на морозі або при нагріванні може відбутися як через 600 мс, так і через 1600 мс.
2. **Сліпота до занадто частого скидання:** IWDG фіксує лише подію «лічильник дійшов до нуля». Якщо внаслідок збою покажчик інструкцій процесора (`PC`) стрибнув у випадкову область пам'яті й зациклився на ділянці, яка безперервно пише ключ `0xAAAA` в регістр керування, IWDG ніколи не виявить аномалії.

### Віконний сторож (WWDG): контроль часового вікна та збоїв виконання

Віконний сторож створювався спеціально для боротьби з неконтрольованим виконанням коду (runaway code / PC corruption), спричиненим електромагнітними завадами або руйнуванням стека.

На відміну від IWDG, модуль WWDG тактується від основної системної шини периферії (APB1) через подільник частоти. Його лічильник є 7-бітним (`T[6:0]`) і рахує вниз від стартового значення (не більше `0x7F`) до `0x3F`.

Ключовий механізм WWDG полягає в тому, що запис нового значення в лічильник дозволено **виключно у визначеному часовому вікні**: коли поточне значення лічильника вже опустилося нижче за запрограмований поріг вікна (Window Value, `W[6:0]`), але ще не досягло критичного значення `0x3F`.

Спроба оновити WWDG породжує один із трьох наслідків:
* **Занадто раннє скидання (Window Violation):** прошивка намагається перезаписати лічильник, коли `T[6:0] > W[6:0]`. WWDG миттєво генерує апаратне скидання мікроконтролера. Це ловить ситуації, коли код через помилку логіки або збій стека викликає функцію оновлення завчасно.
* **Своєчасне скидання (Correct Refresh):** значення оновлюється в інтервалі `0x3F < T[6:0] ≤ W[6:0]`. Лічильник безпечно перезавантажується початковим значенням.
* **Запізніле скидання (Underflow):** лічильник опускається до значення `0x3F` (біт `T6` скидається в 0). WWDG генерує апаратний ресет. Це класична реакція на повне зависання або блокування процесора.

Розрахунок тривалості вікна WWDG базується на частоті шини APB1:

```
t_WWDG = t_PCLK1 · 4096 · 2^(WDGTB) · (T[5:0] + 1)
```

де `t_PCLK1` — період тактової частоти шини APB1, `WDGTB` — коефіцієнт попереднього дільника (прескалер 1, 2, 4 або 8), а `T[5:0]` — шість молодших бітів лічильника.

Розрахуємо межі допустимого вікна оновлення для типової конфігурації: частота шини `f_PCLK1 = 42 МГц`, прескалер `WDGTB = 3` (ділення на 8), початкове значення лічильника `T = 0x7F` (127), поріг вікна `W = 0x50` (80).

1. Базовий квант часу лічильника:
```
t_tick = (1 / 42 000 000 Гц) · 4096 · 2³
       = (1 / 42 000 000) · 4096 · 8
       = 0.00078019 с (≈ 780.2 мкс)
```

2. Мінімальний час до дозволу скидання (поки лічильник зменшується від 127 до 80, тобто на 47 кроків):
```
t_min = t_tick · (127 - 80)
      = 780.19 мкс · 47
      = 36.67 мс
```

3. Максимальний час до настання аварійного скидання (поки лічильник зменшується від 127 до 63, тобто на 64 кроки):
```
t_max = t_tick · (127 - 63)
      = 780.19 мкс · 64
      = 49.93 мс
```

У цій конфігурації прошивка зобов'язана виконувати скидання сторожа строго в проміжку між **36.67 мс** та **49.93 мс** після попереднього скидання. Якщо код зациклиться й викличе скидання через 10 мс — процесор негайно перезавантажиться.

| Параметр порівняння | Незалежний сторож (IWDG) | Віконний сторож (WWDG) |
|---|---|---|
| Джерело тактування | Власний низькочастотний RC (LSI ~32–40 кГц) | Системна шина периферії (APB1) |
| Залежність від збоїв HSE/PLL | Повна незалежність | Зупиняється при збої шини APB |
| Реакція на раннє скидання | Ігнорує (перезавантажує лічильник) | Миттєвий `MCU Reset` (Window fault) |
| Точність часових інтервалів | Низька (розкид до ±40–50%) | Прецизійна (визначається системним кварцом) |
| Основне призначення | Вихід із глибоких зависань ядра та збоїв тактування | Контроль детермінізму та захист від збоїв лічильника команд |

## Зовнішні апаратні супервізори: фізична незалежність

Хоч би якими досконалими були внутрішні модулі IWDG та WWDG, вони мають одну спільну вразливість: вони розташовані на **тому самому кремнієвому кристалі**, що й процесорне ядро.

![Зовнішній апаратний супервізор](/root/course/embedded/storozh-iakyi-spravdi-lovyt-zavysannia/img/hardware-watchdog-supervisor.svg)
*Зовнішня мікросхема супервізора забезпечує фізичну ізоляцію логіки скидання від кристала мікроконтролера.*

Існують три фізичні явища, за яких внутрішній сторож мікроконтролера виявляється безсилим:
1. **Тиристорне замикання (Latch-up):** при впливі високовольтних наведених імпульсів на виводи вводу-виводу (ESD або зворотний сплеск від контактора) всередині структури КМОН відкриваються паразитарні біполярні p-n-p-n структури. Мікроконтролер входить у режим короткого замикання шини живлення на землю. Внутрішня цифрова логіка паралізується, струм споживання зростає в десятки разів, а генератор LSI зупиняється. Внутрішній IWDG фізично не може згенерувати сигнал скидання.
2. **Сіра зона напруги живлення (Brownout Trap):** при повільній просадці живлення акумулятора напруга на шині `VDD` може опуститися нижче мінімального робочого порогу ядра (наприклад, 1.9 В при номіналі 3.3 В), але залишатися вище порогу апаратного детектора збою живлення (BOD). У цій зоні транзистори флеш-пам'яті та регістрів починають перемикатися з фатальними помилками, код спотворюється, а регістри IWDG можуть випадково заблокуватися або вимкнутися.
3. **Зависання на етапі запуску (Boot Failure):** якщо під час оновлення прошивки пошкоджено сектор завантажувача або апаратний кристал кварцу тріснув і не може запустити генерацію, мікроконтролер зависає до того, як код дійшов до інструкції конфігурації IWDG. Якщо IWDG не налаштовано через захищені апаратні ф'юзи (Option Bytes у режимі Hardware Watchdog), пристрій залишиться мертвим назавжди.

Для систем підвищеної надійності (автомобільних блоків керування, авіоніки, промислових контролерів) стандарти вимагають застосування **зовнішньої інтегральної мікросхеми супервізора** (наприклад, TPS3823, STWD100 або MAX6369).

Така мікросхема реалізує фізично відокремлений контур захисту:
* Вона живиться від вхідної шини та має власний апаратний компаратор напруги з лазерним підганянням порогу (точність ±1%).
* Її вихід `/RESET` з відкритим стоком підключається безпосередньо до виводу апаратного скидання мікроконтролера (`NRST`).
* Вхід сторожа (`WDI`) очікує регулярних перепадів рівня (фронтів). Якщо вивід GPIO мікроконтролера застрягне в постійній одиниці або постійному нулі (типовий наслідок зависання або Latch-up), супервізор сприйме це як відсутність сигналу і через фіксований час (наприклад, 1.6 с) примусово притягне лінію `NRST` до землі на 200 мс, гарантовано перезапустивши кристал.

Детальний схемотехнічний розбір цього класу компонентів, розрахунок фільтрації лінії WDI та правила захисту від брязкання розкрито у вставці [Узагальнений апаратний супервізор: схемотехніка підключення](root:embedded/storozh-iakyi-spravdi-lovyt-zavysannia/comp-hardware-watchdog.md).

## Дворівнева архітектура диспетчера сторожа (Supervisor Pattern)

Щоб перетворити сторожовий таймер на надійний діагностичний інструмент, необхідно розділити систему на два рівні:
1. **Апаратний рівень (Hardware Watchdog):** фізичний таймер (IWDG, WWDG або зовнішній IC). До його регістрів має доступ **лише один** системний компонент.
2. **Програмний рівень (Task Watchdog Supervisor):** диспетчер завдань, що відстежує стан усіх потоків прошивки та приймає рішення про оновлення апаратного таймера.

![Дворівнева архітектура диспетчера сторожового таймера](/root/course/embedded/storozh-iakyi-spravdi-lovyt-zavysannia/img/task-watchdog-architecture.svg)
*Дворівнева схема контролю: робочі потоки звітують диспетчеру, а диспетчер скидає апаратний WDT лише за умови повної готовності кожного критичного завдання.*

### Принцип роботи диспетчера

1. **Реєстрація завдань:** під час старту системи кожне критичне завдання (Task) реєструється в диспетчері, передаючи свій унікальний ідентифікатор та індивідуальний граничний таймаут (дедлайн). Наприклад:
   * Задача опитування сенсорів: період 20 мс, максимальний допустимий таймаут 50 мс.
   * Задача ПІД-регулятора моторів: період 2 мс, максимальний таймаут 10 мс.
   * Задача телеметрії: період 100 мс, максимальний таймаут 500 мс.
2. **Звітування про просування (Check-in / Heartbeat):** у кінці кожної успішної ітерації робочого циклу потік викликає функцію `watchdog_task_checkin(TASK_ID)`. Ця функція оновлює мітку часу останньої активності потоку.
3. **Контроль послідовності станів (Execution Checkpoints):** щоб запобігти ситуації, коли потік проскакує цикл через помилку, завдання оновлює контрольне значення хешу стану (checkpoint):
   ```
   Етап 1: Зчитування АЦП      ──→ checkpoint = 0x01
   Етап 2: Розрахунок матриці  ──→ checkpoint = (0x01 << 1) ^ 0xA5
   Етап 3: Вивід сигналу ШІМ   ──→ checkpoint = (prev << 1) ^ 0x5A
   ```
   Диспетчер перевіряє не лише час виклику, але й те, чи завершилися всі три етапи обчислення.
4. **Централізований арбітраж:** потік диспетчера наглядача (Watchdog Task) періодично перевіряє таблицю зареєстрованих завдань. Якщо **хоча б одне** завдання перевищило свій дедлайн або передало некоректний хеш стану:
   * Диспетчер негайно **припиняє скидання апаратного WDT**.
   * Записує діагностичний знімок (ідентифікатор винного завдання, значення лічильника тіків, стан стека) у спеціально виділену область пам'яті, що не скидається при перезапуску (`.noinit` RAM або RTC Backup registers).
   * Апаратний сторож дораховує до нуля і скидає процесор.

> 🔧 **Пріоритет диспетчера в RTOS.** Потік наглядача повинен мати **найнижчий пріоритет серед усіх критичних завдань** (або запускатися як частина фонового завдання Idle Hook). Якщо високопріоритетна задача зациклиться й забере 100% часу процесора (CPU Starvation), диспетчер просто не отримає квант часу від планувальника, не зможе скинути апаратний WDT, і мікроконтролер безпечно перезавантажиться за апаратним таймаутом.

## Робочий модуль Task Watchdog Supervisor на C та C++

Нижче наведено закінчену реалізацію багатозадачного диспетчера здоров'я потоків для мікроконтролерів. Вона підтримує індивідуальні таймаути, контроль послідовності фаз та потокобезпечне оновлення без блокувальних м'ютексів.

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

#define WDT_MAX_TASKS          8
#define WDT_MAGIC_VALID        0x5A5AA5A5U
#define WDT_CHECKPOINT_FINAL   0x3C69A55AU

typedef struct {
    uint32_t task_id;
    uint32_t timeout_ms;
    uint32_t last_checkin_tick;
    uint32_t expected_checkpoint;
    uint32_t current_checkpoint;
    bool is_registered;
    bool is_active;
} wdt_task_entry_t;

// Діагностичний блок у незатертій секції RAM (.noinit)
typedef struct {
    uint32_t magic;
    uint32_t fault_task_id;
    uint32_t fault_tick;
    uint32_t fault_reason; // 1 = Timeout, 2 = Checkpoint error
} wdt_crash_dump_t;

__attribute__((section(".noinit"))) static volatile wdt_crash_dump_t g_crash_dump;

static wdt_task_entry_t g_tasks[WDT_MAX_TASKS];
static uint32_t g_registered_count = 0;

// Апаратна функція скидання конкретного WDT (наприклад IWDG)
static inline void hw_watchdog_reload(void) {
    // Для STM32: IWDG->KR = 0x0000AAAAU;
    volatile uint32_t *iwdg_kr = (volatile uint32_t *)0x40003000U;
    *iwdg_kr = 0xAAAAU;
}

// Отримання системного часу в мілісекундах
extern uint32_t sys_get_tick_ms(void);

bool wdt_supervisor_init(void) {
    for (size_t i = 0; i < WDT_MAX_TASKS; ++i) {
        g_tasks[i].is_registered = false;
        g_tasks[i].is_active = false;
    }
    g_registered_count = 0;
    return true;
}

int32_t wdt_register_task(uint32_t task_id, uint32_t timeout_ms) {
    if (g_registered_count >= WDT_MAX_TASKS) {
        return -1;
    }
    for (size_t i = 0; i < g_registered_count; ++i) {
        if (g_tasks[i].task_id == task_id) {
            return (int32_t)i; // Вже зареєстровано
        }
    }
    size_t idx = g_registered_count++;
    g_tasks[idx].task_id = task_id;
    g_tasks[idx].timeout_ms = timeout_ms;
    g_tasks[idx].last_checkin_tick = sys_get_tick_ms();
    g_tasks[idx].expected_checkpoint = WDT_CHECKPOINT_FINAL;
    g_tasks[idx].current_checkpoint = WDT_CHECKPOINT_FINAL;
    g_tasks[idx].is_registered = true;
    g_tasks[idx].is_active = true;
    return (int32_t)idx;
}

void wdt_task_checkpoint(uint32_t task_handle, uint32_t phase_step) {
    if (task_handle >= g_registered_count || !g_tasks[task_handle].is_active) {
        return;
    }
    // Оновлюємо хеш контрольних точок: перестановка бітів + фазовий крок
    uint32_t cp = g_tasks[task_handle].current_checkpoint;
    g_tasks[task_handle].current_checkpoint = (cp << 3) ^ (cp >> 29) ^ phase_step;
}

void wdt_task_checkin(uint32_t task_handle) {
    if (task_handle >= g_registered_count || !g_tasks[task_handle].is_active) {
        return;
    }
    // Атомарно фіксуємо час оновлення
    g_tasks[task_handle].last_checkin_tick = sys_get_tick_ms();
    g_tasks[task_handle].current_checkpoint = WDT_CHECKPOINT_FINAL;
}

bool wdt_supervisor_process(void) {
    uint32_t now = sys_get_tick_ms();

    for (size_t i = 0; i < g_registered_count; ++i) {
        if (!g_tasks[i].is_active) {
            continue;
        }

        // 1. Перевірка таймауту виконання
        uint32_t elapsed = now - g_tasks[i].last_checkin_tick;
        if (elapsed > g_tasks[i].timeout_ms) {
            // Зависання задачі: зберігаємо діагностику та зупиняємо оновлення WDT
            g_crash_dump.magic = WDT_MAGIC_VALID;
            g_crash_dump.fault_task_id = g_tasks[i].task_id;
            g_crash_dump.fault_tick = now;
            g_crash_dump.fault_reason = 1; // Timeout
            return false; // НЕ скидаємо апаратний WDT
        }

        // 2. Перевірка контрольної точки
        if (g_tasks[i].current_checkpoint != g_tasks[i].expected_checkpoint) {
            g_crash_dump.magic = WDT_MAGIC_VALID;
            g_crash_dump.fault_task_id = g_tasks[i].task_id;
            g_crash_dump.fault_tick = now;
            g_crash_dump.fault_reason = 2; // Bad Checkpoint
            return false;
        }
    }

    // Усі задачі здорові — скидаємо апаратний сторож
    hw_watchdog_reload();
    return true;
}

bool wdt_get_crash_report(wdt_crash_dump_t *out_report) {
    if (g_crash_dump.magic == WDT_MAGIC_VALID) {
        *out_report = g_crash_dump;
        g_crash_dump.magic = 0; // Очищуємо після зчитування
        return true;
    }
    return false;
}
```
```cpp
#include <cstdint>
#include <cstddef>
#include <span>
#include <array>
#include <optional>

namespace embedded::safety {

enum class FaultReason : uint32_t {
    None = 0,
    Timeout = 1,
    BadCheckpoint = 2
};

struct CrashReport {
    uint32_t magic;
    uint32_t faultTaskId;
    uint32_t faultTick;
    FaultReason reason;
};

// Секція оперативної пам'яті, що не ініціалізується при старті
#if defined(__GNUC__)
[[gnu::section(".noinit")]]
#endif
static volatile CrashReport g_sharedCrashDump;

template <size_t MaxTasks = 8>
class TaskWatchdogSupervisor {
public:
    static constexpr uint32_t MagicValid = 0x5A5AA5A5U;
    static constexpr uint32_t CheckpointFinal = 0x3C69A55AU;

    struct TaskConfig {
        uint32_t taskId{0};
        uint32_t timeoutMs{1000};
        uint32_t lastCheckinTick{0};
        uint32_t expectedCheckpoint{CheckpointFinal};
        uint32_t currentCheckpoint{CheckpointFinal};
        bool isRegistered{false};
        bool isActive{false};
    };

    constexpr TaskWatchdogSupervisor() = default;

    std::optional<size_t> registerTask(uint32_t taskId, uint32_t timeoutMs, uint32_t currentTick) noexcept {
        for (size_t i = 0; i < taskCount_; ++i) {
            if (tasks_[i].taskId == taskId) {
                return i;
            }
        }
        if (taskCount_ >= MaxTasks) {
            return std::nullopt;
        }

        size_t handle = taskCount_++;
        tasks_[handle] = TaskConfig{
            .taskId = taskId,
            .timeoutMs = timeoutMs,
            .lastCheckinTick = currentTick,
            .expectedCheckpoint = CheckpointFinal,
            .currentCheckpoint = CheckpointFinal,
            .isRegistered = true,
            .isActive = true
        };
        return handle;
    }

    void checkpoint(size_t handle, uint32_t phaseStep) noexcept {
        if (handle < taskCount_ && tasks_[handle].isActive) {
            uint32_t cp = tasks_[handle].currentCheckpoint;
            tasks_[handle].currentCheckpoint = (cp << 3) ^ (cp >> 29) ^ phaseStep;
        }
    }

    void checkin(size_t handle, uint32_t currentTick) noexcept {
        if (handle < taskCount_ && tasks_[handle].isActive) {
            tasks_[handle].lastCheckinTick = currentTick;
            tasks_[handle].currentCheckpoint = CheckpointFinal;
        }
    }

    bool evaluateAndReload(uint32_t currentTick) noexcept {
        for (size_t i = 0; i < taskCount_; ++i) {
            if (!tasks_[i].isActive) {
                continue;
            }

            const uint32_t elapsed = currentTick - tasks_[i].lastCheckinTick;
            if (elapsed > tasks_[i].timeoutMs) {
                recordCrash(tasks_[i].taskId, currentTick, FaultReason::Timeout);
                return false;
            }

            if (tasks_[i].currentCheckpoint != tasks_[i].expectedCheckpoint) {
                recordCrash(tasks_[i].taskId, currentTick, FaultReason::BadCheckpoint);
                return false;
            }
        }

        reloadHardware();
        return true;
    }

    static std::optional<CrashReport> extractCrashReport() noexcept {
        if (g_sharedCrashDump.magic == MagicValid) {
            CrashReport report = const_cast<const CrashReport&>(g_sharedCrashDump);
            g_sharedCrashDump.magic = 0;
            return report;
        }
        return std::nullopt;
    }

private:
    std::array<TaskConfig, MaxTasks> tasks_{};
    size_t taskCount_{0};

    static void reloadHardware() noexcept {
        volatile auto* iwdgKr = reinterpret_cast<volatile uint32_t*>(0x40003000U);
        *iwdgKr = 0xAAAAU;
    }

    static void recordCrash(uint32_t taskId, uint32_t tick, FaultReason reason) noexcept {
        g_sharedCrashDump.magic = MagicValid;
        g_sharedCrashDump.faultTaskId = taskId;
        g_sharedCrashDump.faultTick = tick;
        g_sharedCrashDump.reason = reason;
    }
};

} // namespace embedded::safety
```

## Крайові випадки та пастки експлуатації

### 1. Тривалі операції запису та оновлення (Flash Erase / OTA)

Стирання великого сектора флеш-пам'яті (Flash Sector Erase) у мікроконтролерах може займати від 500 мс до 2–3 секунд. Під час операції стирання шина пам'яті блокується, виконання коду з флеш призупиняється, а процесор не може виконувати обробники переривань. Якщо сторож налаштований на 1.0 с, відбудеться помилкове скидання.

Хибне рішення — вимкнути сторож перед записом флеш (більшість апаратних WDT взагалі не підтримують програмного вимкнення після старту з міркувань безпеки).

Правильні інженерні підходи:
* **Стирання дрібними сторінками:** якщо контролер підтримує посторінкове стирання (Page Erase по 2 КБ за 20 мс), операція розбивається на цикл, де після кожної сторінки викликається `wdt_checkin()`.
* **Виконання критичного коду з RAM:** функція стирання та диспетчер сторожа розміщуються в оперативній пам'яті (`__attribute__((section(".ramfunc")))`), що дозволяє оновлювати лічильник під час стирання сусідніх банків флеш.

### 2. Режими низького енергоспоживання (Stop / Standby)

Коли пристрій переходить у глибокий сон (Deep Sleep), системні тактові генератори вимикаються для економії заряду акумулятора. Проте незалежний IWDG на генераторі LSI продовжує рахувати і розбудить пристрій ресетом через 1 секунду.

Для коректної роботи зі сном використовують два механізми:
1. **Апаратне заморожування лічильника (Debug / Freeze Mode):** у регістрах конфігурації мікроконтролера (`DBGMCU_CR` або `FLASH_OBR`) виставляється прапорець `IWDG_STOP` / `IWDG_STDBY = 1`. Лічильник сторожа автоматично ставиться на паузу, поки ядро перебуває в стані сну, і відновлює відлік у момент пробудження.
2. **Періодичне пробудження за таймером RTC:** якщо апаратний WDT не підтримує заморожування (або використовується зовнішній супервізор), процесор налаштовує пробудження від годинника реального часу (RTC Alarm) кожні 800 мс, виконує коротку перевірку здоров'я, генерує імпульс WDI й знову засинає.

### 3. Точки зупинки під зневаджувачем (SWD / JTAG Breakpoints)

Під час підключення апаратного відлагоджувача (ST-Link, J-Link) розробник зупиняє виконання коду на точці зупинки (Breakpoint). Якщо сторожовий таймер продовжує рахувати, через кілька сотень мілісекунд він перезавантажить мікроконтролер, повністю зірвавши сесію зневадження.

Щоб запобігти цьому, блок ініціалізації повинен конфігурувати регістри зупинки лічильників при налагодженні:

:::tabs
```c
// Зупинити IWDG та WWDG, коли ядро зупинено налагоджувачем (Cortex-M)
DBGMCU->APB1FZ |= DBGMCU_APB1_FZ_DBG_IWDG_STOP | DBGMCU_APB1_FZ_DBG_WWDG_STOP;
```
```cpp
// Конфігурація заморожування лічильників при зупинці ядра зневаджувачем
constexpr uint32_t DbgFreezeMask = DBGMCU_APB1_FZ_DBG_IWDG_STOP | DBGMCU_APB1_FZ_DBG_WWDG_STOP;
DBGMCU->APB1FZ |= DbgFreezeMask;
```
:::

Якщо використовується зовнішня мікросхема супервізора, лінія `WDI` на час налагодження переводиться у високоімпедансний стан (High-Z) або апаратно відключається джампером, як описано у вставці про схемотехніку зовнішніх сторожів.

Послідовність обробки діагностичного дампу після перезапуску розглядається в суміжних матеріалах курсу: [Причина скидання як діагноз](root:embedded/prychyna-skydannia-iak-diahnoz) та [Послідовність graceful reset](root:embedded/reset-sequence).

## Чеклист проектування сторожової архітектури

П'ять обов'язкових правил побудови сторожового захисту у відповідальних пристроях:

1. **Жодного скидання в ізольованих ISR:** заборонено викликати команди перезаряджання таймера з обробників SysTick або таймерних переривань.
2. **Контроль часового вікна та послідовності:** використовувати WWDG або програмний контроль контрольних точок (checkpoints) для виявлення занадто швидкого холостого зациклення коду.
3. **Дворівневий нагляд:** кожен робочий потік звітує в локальну таблицю здоров'я; апаратний WDT перезаряджає виключно центральний диспетчер з найнижчим пріоритетом за 100% готовності всіх критичних задач.
4. **Збереження діагностичного сліду:** перед допущенням апаратного скидання фіксувати ідентифікатор винного завдання та причину відмови в незатерту оперативну пам'ять (`.noinit` RAM) для аналізу в журналі відмов.
5. **Зовнішній апаратний супервізор:** для автономних та промислових пристроїв застосовувати окрему мікросхему нагляду для гарантованого перезапуску при просадках напруги, тиристорних замиканнях (latch-up) та збоях тактування кристала.
