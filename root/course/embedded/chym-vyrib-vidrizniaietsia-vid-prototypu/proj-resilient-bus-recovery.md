# ⚙️ Промислове розблокування апаратних шин і сторожовий контроль у прошивці

Найпідступніша апаратна відмова лабораторного макета виникає у момент, коли мікроконтролер несподівано перезавантажується через короткочасну просадку живлення або спрацювання сторожового таймера саме під час транзакції читання з периферійного чипа по шині I2C. Якщо в момент аварійного рестарту ведений пристрій (наприклад, цифровий термодатчик, акселерометр, годинник реального часу або мікросхема EEPROM) передавав біт логічного нуля, його внутрішній вихідний польовий транзистор залишається відкритим і продовжує притискати фізичну лінію даних `SDA` до потенціалу землі (GND).

Коли мікроконтролер перезавантажується і запускає початкову ініціалізацію апаратного периферійного блоку I2C, контролер шини фіксує на лінії стан `SDA = 0`. Відповідно до специфікації протоколу I2C, такий стан інтерпретується апаратурою як «шина зайнята іншим ведучим» (Bus Busy). У наївному коді прототипу ця ситуація призводить до повного й безповоротного зависання: прошивка нескінченно очікує звільнення лінії, сторожовий таймер перезапускає мікроконтролер, але після старту все повторюється знову, утворюючи нескінченну петлю перезавантажень (англ. *bootloop*).

```
                  КЛІНЧ ШИНИ I2C ПІСЛЯ СПОНТАННОГО СКИДАННЯ MCU
                  
               Транзакція читання перервана на 5-му біті даних (біт = 0)
                                            │
                                            ▼  [СКИДАННЯ MCU]
SCL  ───┐   ┌───┐   ┌───┐   ┌───┐   ┌───┐
        └───┘   └───┘   └───┘   └───┘   └──────────────────────────────── (SCL вільний = 1)
        
SDA  ───────┐                           ┌────────────────────────────────
            └───────────────────────────┴──────────────────────────────── (SDA затиснутий веденим = 0)
                                        ▲
                                        │
             Ведений чекає тактових імпульсів для завершення передачі байта
```

### Фізичний механізм аварійного вибивання шини з клінчу

Оскільки ведений пристрій є пасивним автоматом станів, він не знає про перезапуск головного процесора і терпляче очікує чергових тактових імпульсів на лінії `SCL`, щоб виштовхнути залишок поточного 8-бітного байта та отримати біт підтвердження (NACK) або умову `STOP`.

Для відновлення працездатності шини прошивка серійного виробу реалізує детермінований алгоритм **апаратного розблокування шини** (англ. *bus unjamming sequence*):

1. **Тимчасове перепризначення виводів:** апаратний блок I2C програмно вимикається, а виводи мікроконтролера `SCL` та `SDA` конфігуруються як універсальні цифрові лінії вводу-виводу (GPIO) у режимі відкритого стоку (Open-Drain) з увімкненими підтягуючими резисторами.
2. **Діагностика лінії тактування:** перевіряється рівень на виводі `SCL`. Якщо лінія `SCL` утримується в нулі зовнішньою мікросхемою довше допустимого таймауту розтягування такту (Clock Stretching), це свідчить про фізичне коротке замикання на землю або апаратний вихід веденого чипа з ладу.
3. **Генерація серії з 9 тактових імпульсів:** мікроконтролер вручну по черзі опускає та піднімає рівень на лінії `SCL` із затримкою у 5 мікросекунд (що відповідає стандартній частоті 100 кГц). Максимальна кількість імпульсів дорівнює дев'яти: 8 тактів гарантують передачу найдовшого залишку байта, а 9-й такт відповідає слоту підтвердження ACK.
4. **Контроль звільнення лінії даних:** після кожного такту мікроконтролер зчитує стан `SDA`. Щойно ведений чип передасть свій нульовий біт або завершить байт, лінія `SDA` підтягується резистором до напруги живлення (логічна одиниця).
5. **Формування умови STOP:** при високому рівні на лінії `SCL` мікроконтролер генерує перехід лінії `SDA` з низького рівня у високий. Це повертає автомати станів усіх ведених пристроїв на шині у вихідний стан очікування адреси (IDLE).
6. **Реініціалізація апаратного блоку:** виводи повертаються під керування апаратного контролера I2C, скидаються внутрішні прапорці помилок, і шина стає готовою до виконання бойових транзакцій.

```
                  ПРОЦЕДУРА ГЕНЕРАЦІЇ 9 ТАКТІВ ТА УМОВИ STOP
SCL  ──┐   ┌──┐   ┌──┐   ┌──┐   ┌──┐   ┌──┐   ┌──┐   ┌──┐   ┌─────────┐
       └───┘  └───┘  └───┘  └───┘  └───┘  └───┘  └───┘  └───┘         └───
       Такт:  1      2      3      4      5      6      7      8      9      [STOP]

SDA  ──────┐ (утримується веденим)                 ┌───────────────────────┐
           └───────────────────────────────────────┘ (звільнено веденим)  └────
```

### Робоча реалізація драйвера розблокування на C та C++

Нижче наведено виробничий драйвер відновлення шини, який ізолює апаратні особливості мікроконтролера через шар абстракції та гарантує повернення статусу виконання без нескінченних блокувань.

```c
#include <stdint.h>
#include <stdbool.h>

/* Абстракція апаратної платформи для керування ніжками GPIO */
typedef struct {
    void (*set_scl)(bool high);
    void (*set_sda)(bool high);
    bool (*read_scl)(void);
    bool (*read_sda)(void);
    void (*delay_us)(uint32_t us);
    void (*reinit_i2c_hardware)(void);
} i2c_bus_hal_t;

typedef enum {
    BUS_OK = 0,
    BUS_RECOVERED,
    BUS_ERROR_SCL_STUCK_LOW,
    BUS_ERROR_SDA_STUCK_LOW
} bus_status_t;

/* Виробнича функція вибивання шини з клінчу */
bus_status_t i2c_bus_recover(const i2c_bus_hal_t *hal) {
    if (!hal) {
        return BUS_ERROR_SCL_STUCK_LOW;
    }

    /* 1. Відпускаємо обидві лінії у високий стан */
    hal->set_scl(true);
    hal->set_sda(true);
    hal->delay_us(5);

    /* Якщо SCL притиснутий до землі — це апаратне КЗ або завислий Clock Stretch */
    if (!hal->read_scl()) {
        return BUS_ERROR_SCL_STUCK_LOW;
    }

    /* Якщо лінія SDA вже вільна — відновлення не потрібне */
    if (hal->read_sda()) {
        return BUS_OK;
    }

    /* 2. Генеруємо до 9 тактових імпульсів для завершення передачі веденим */
    bool sda_released = false;
    for (uint8_t i = 0; i < 9; ++i) {
        hal->set_scl(false);
        hal->delay_us(5);
        hal->set_scl(true);
        hal->delay_us(5);

        if (hal->read_sda()) {
            sda_released = true;
            break;
        }
    }

    if (!sda_released) {
        return BUS_ERROR_SDA_STUCK_LOW;
    }

    /* 3. Формуємо коректну умову STOP: перехід SDA 0 -> 1 при SCL = 1 */
    hal->set_sda(false);
    hal->delay_us(5);
    hal->set_scl(true);
    hal->delay_us(5);
    hal->set_sda(true);
    hal->delay_us(5);

    /* 4. Повертаємо виводи під контроль апаратного периферійного блока I2C */
    hal->reinit_i2c_hardware();

    return BUS_RECOVERED;
}
```
```cpp
#include <cstdint>
#include <concepts>
#include <expected>
#include <chrono>

enum class BusError {
    SclStuckLow,
    SdaStuckLow,
    InvalidHardwareConfig
};

enum class RecoveryResult {
    AlreadyClean,
    SuccessfullyRecovered
};

template <typename HalPolicy>
concept I2cHalPolicy = requires(HalPolicy hal, bool state, uint32_t us) {
    { hal.set_scl(state) } -> std::same_as<void>;
    { hal.set_sda(state) } -> std::same_as<void>;
    { hal.read_scl() }     -> std::same_as<bool>;
    { hal.read_sda() }     -> std::same_as<bool>;
    { hal.delay_us(us) }   -> std::same_as<void>;
    { hal.reinit_hardware() } -> std::same_as<void>;
};

template <I2cHalPolicy Hal>
class ResilientI2cBus {
public:
    explicit ResilientI2cBus(Hal hal) : hal_(hal) {}

    [[nodiscard]] std::expected<RecoveryResult, BusError> recover_bus() noexcept {
        hal_.set_scl(true);
        hal_.set_sda(true);
        hal_.delay_us(5);

        // Якщо SCL на нулі — лінія фізично пошкоджена або ведений затиснув Clock Stretch
        if (!hal_.read_scl()) {
            return std::unexpected(BusError::SclStuckLow);
        }

        // Лінія SDA чиста — відновлення не потрібне
        if (hal_.read_sda()) {
            return RecoveryResult::AlreadyClean;
        }

        bool sda_released = false;
        constexpr uint8_t max_clocks = 9;

        for (uint8_t i = 0; i < max_clocks; ++i) {
            hal_.set_scl(false);
            hal_.delay_us(5);
            hal_.set_scl(true);
            hal_.delay_us(5);

            if (hal_.read_sda()) {
                sda_released = true;
                break;
            }
        }

        if (!sda_released) {
            return std::unexpected(BusError::SdaStuckLow);
        }

        // Генерація апаратної умови STOP для завершення стану транзакції
        hal_.set_sda(false);
        hal_.delay_us(5);
        hal_.set_scl(true);
        hal_.delay_us(5);
        hal_.set_sda(true);
        hal_.delay_us(5);

        // Повернення контролю апаратному блоку I2C
        hal_.reinit_hardware();

        return RecoveryResult::SuccessfullyRecovered;
    }

private:
    Hal hal_;
};
```

### Розтягування такту (Clock Stretching) проти мертвого зависання

Окремим крайовим випадком у роботі шини I2C є механізм **розтягування такту** (англ. *clock stretching*). Повільний ведений чип (наприклад, мікроконтролер-супутник або спеціалізований криптопроцесор) має право примусово утримувати лінію `SCL` у нулі після прийому байта, сигналізуючи ведучому, що він зайнятий внутрішніми обчисленнями й ще не готовий прийняти наступний байт.

У лабораторному коді розтягування такту нерідко викликає фатальну плутанину:
- Якщо таймаут очікування `SCL = 1` відсутній або реалізований як нескінченний цикл `while(!read_scl())`, будь-який внутрішній збій веденого чипа перетворюється на вічне зависання всієї системи.
- Якщо таймаут занадто короткий (наприклад, менше 100 мікросекунд), ведучий мікроконтролер обриває законну транзакцію повільного чипа під час запису в енергонезалежну пам'ять, пошкоджуючи дані.

Серійний виріб встановлює жорсткий, але фізично обґрунтований ліміт очікування лінії `SCL`: для більшості стандартних мікросхем час розтягування не перевищує 25 мілісекунд (стандарт SMBus). Якщо лінія не звільняється після закінчення цього інтервалу, стан трактується як апаратна відмова вузла.

### Стратегія ескалації помилок у промисловій архітектурі

У надійному виробі виклик процедури відновлення шини інтегрується у багаторівневу ієрархію системного захисту:

1. **Превентивний запуск під час старту:** процедура розблокування обов'язково виконується у функції `main()` до будь-якої спроби ініціалізації датчиків. Це гарантує, що пристрій вийде на робочий режим навіть після раптового зникнення живлення.
2. **Локальна ескалація при таймауті драйвера:** якщо під час чергового опитування датчика апаратний контролер I2C повертає помилку таймауту або лінія залишається у стані зайнятості понад 25 мс, драйвер датчика не зависає, а викликає `recover_bus()` і повторює транзакцію.
3. **Ескалація на рівень живлення датчиків (Power Cycling):** якщо 9 тактів не змогли звільнити лінію `SDA` (повернуто код помилки `BUS_ERROR_SDA_STUCK_LOW`), це свідчить про внутрішнє зависання цифрової логіки самого сенсора. Якщо на платі передбачено ключ керування живленням периферії (Load Switch), мікроконтролер вимикає живлення шини датчиків на 50 мс для повного холодного перезапуску мікросхем.
4. **Реєстрація інциденту в журналі відмов:** кожна спроба розблокування шини фіксується лічильником у діагностичній структурі пам'яті. Якщо кількість відновлень за годину перевищує порогове значення, система сигналізує про деградацію апаратури або надмірний рівень електромагнітних завад на об'єкті.
5. **Верифікація на тестовому стенді:** під час конвеєрного тестування (ICT) стенд примусово замикає лінію `SDA` на землю за допомогою керованого реле, ініціює перезапуск плати та перевіряє за логами, чи зміг мікроконтролер успішно розблокувати шину за нормативний час.
