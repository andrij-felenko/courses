Автономний гусеничний робот-маніпулятор виконує інспекцію промислового колектора. На тестовому стенді пристрій бездоганно пройшов пів сотні коротких приймальних випробувань тривалістю по двадцять-тридцять секунд. Проте під час першого ж реального виїзду на об'єкті трапляється катастрофа: рівно на шістдесят п'ятій секунді руху зв'язок із пультом оператора раптово зникає, сервоприводи силового шарніра на мить блокуються, після чого бортовий мікроконтролер іде в аварійне перезавантаження, а маніпулятор під власною вагою падає на бетонний лоток і деформує редуктор.

Перший звіт польового інженера містив стандартний поверховий висновок: «Втрата радіозв'язку внаслідок екранування стінами колектора, після чого через стрибок напруги стався збій живлення». Команда розробників негайно замінила антену на модель із вищим коефіцієнтом підсилення та встановила вдвічі більший електролітичний конденсатор на лінію живлення радіомодуля. Наступний виїзд завершився абсолютно ідентичною аварією рівно на 65.5 секунді після старту.

Симптоматичний ремонт провалився, тому що розробники намагалися лікувати видимий наслідок, не розуміючи фізичного ланцюга подій. Справжня причина аварії ховалася не в радіохвилях і не в дефекті батареї, а в одному рядку коду таймерної арифметики, який запустив невідворотний каскад апаратних та програмних відмов.

## Методологія Root Cause Analysis (RCA) у вбудованих системах

Аналіз першопричин (англ. *Root Cause Analysis*, RCA — від латинського *radix*, корінь) — це структурований інженерний процес пошуку вихідної точки відмови, усунення якої гарантовано унеможливлює повторення аварії за будь-яких умов експлуатації.

У складних програмно-апаратних комплексах головна небезпека полягає у плутанині між трьома рівнями події:
1. **Симптом (Symptom):** зовнішній прояв аварії, який бачить користувач або фіксує телеметрія (робот упав, зв'язок обірвався, світлодіод блимає кодом помилки).
2. **Проміжний механізм відмови (Proximate Failure Mode):** безпосереднє фізичне або логічне явище, що спричинило симптом (скидання ядра через спрацювання детектора зниження напруги Brownout Reset, переповнення черги повідомлень, блокування шини I2C).
3. **Першопричина (Root Cause):** базовий дефект у схемотехніці, коді чи процесі верифікації, без якого весь подальший ланцюг руйнування не зміг би розпочатися.

### Техніка «5 чому» на стику заліза та коду

Класичний метод «5 чому» (5 Whys), народжений у виробничій системі Toyota, у сфері вбудованих систем вимагає суворої опори на фізичні вимірювання та код, а не на суб'єктивні припущення:

```
[ Симптом: Маніпулятор упав на 65.5 с ]
  │
  ├─ 1. Чому знеструмилися мотори?
  │     └─► Мікроконтролер перезавантажився й вимкнув ШІМ.
  │
  ├─ 2. Чому мікроконтролер пішов у ресет?
  │     └─► Апаратний регістр RCC_CSR зафіксував прапорець BOR (Brownout Reset, VDD < 2.7 В).
  │
  ├─ 3. Чому просіла напруга VDD цифрової частини?
  │     └─► Моторний контролер миттєво зняв напругу з обмоток під струмом 14 А,
  │         індуктивний викид і перерозподіл струмів просадили спільну шину,
  │         а завдання стабілізації не виконало плавний спуск (derating).
  │
  ├─ 4. Чому потік стабілізації раптово зупинив керування?
  │     └─► Потік завис на блокуючому виклику аварійного логування в UART,
  │         бо автомат зв'язку зафіксував фатальну втрату серцебиття (heartbeat timeout).
  │
  └─ 5. Чому автомат вирішив, що зв'язок втрачено, коли пульт надсилав пакети кожні 10 мс?
        └─► ПЕРШОПРИЧИНА: 16-бітний таймер SysTick переповнився (65535 -> 0),
            а перевірка таймауту містила дефект неявного знакового приведення (Integer Promotion),
            який перетворив різницю часу у від'ємне число й викликав хибний таймаут.
```

Якщо зупинитися на кроці 1 — інженер замінить блок живлення. Якщо на кроці 3 — поставить більший конденсатор або варистор. Лише дохід до кроку 5 розкриває справжній дефект і назавжди закриває вразливість.

### Діаграма Ісікави (Fishbone Diagram) для електронного пристрою

Коли пристрій виходить із ладу в польових умовах, підозра зазвичай падає на випадкові зовнішні фактори. Щоб систематизувати пошук і не пропустити взаємодію між компонентами, використовують діаграму Ісікави (причинно-наслідкову діаграму «риб'ячої кістки»), адаптовану для вбудованих систем за шістьма головними категоріями.

![Діаграма Ісікави причин аварії приводу](/root/course/embedded/rozbir-spravzhnoho-padinnia/img/rca-fishbone-diagram.svg)
*Діаграма Ісікави: структурування факторів відмови від апаратних явищ до дефектів таймерної арифметики.*

Кожна гілка діаграми перевіряється виключно інструментальними фактами:
- **Прошивка / Код:** ревізія арифметичних виразів із часовими типами, контроль знакових переповнень у C99, аналіз блокуючих викликів усередині критичних секцій та переривань (ISR).
- **Живлення / Схематика:** зняття осцилограм напруги безпосередньо на виводах VDD/VSS мікроконтролера в момент комутації максимальних струмів інвертора, перевірка перехідних процесів і зворотної ЕРС.
- **Протокол / Зв'язок:** перевірка стану черг повідомлень, глибини буферів приймача UART/CAN, коректності обробки втрати пакетів і таймаутів серцебиття.
- **Кристал / Таймери:** конфігурація переддільників, розрядність лічильників (16 проти 32 біт), поведінка регістрів `CNT` під час переходу через нуль.
- **Середовище / Механіка:** вплив механічної вібрації на контакти роз'ємів, нагрів силових транзисторів MOSFET, електромагнітні наводки від ШІМ-трактів на чутливі лінії зв'язку.
- **Процес / Тестування:** тривалість лабораторних тестів (чому тести тривали лише 30 секунд і не досягли 65.5 с), відсутність автоматизованих стрес-тестів та імітації граничних станів.

> 🔧 **Навіщо це.** Діаграма Ісікави запобігає «тунельному зору» інженера, коли вся увага фокусується на знайомій галузі (наприклад, програміст шукає баг у протоколі, а схемотехнік звинувачує завади по живленню).

## Від симптому до факту: синхронізація журналів та осцилограм

Розслідування аварії вбудованого пристрою не може спиратися на здогадки. Єдиний надійний базис — це зіставлення трьох незалежних джерел даних: апаратних осцилограм, стану регістрів мікроконтролера після скидання та часових логів в енергонезалежній пам'яті.

### Чорна скринька в оперативній пам'яті (noinit RAM Dump)

Коли мікроконтролер зазнає апаратного скидання (Watchdog або Brownout), звичайна пам'ять SRAM не втрачає свій вміст, якщо напруга не опускалася нижче напруги утримання тригерів (~1.2 В). Проте стандартна процедура ініціалізації середовища виконання C (секція `startup`) за замовчуванням занулює всю область `.bss`.

Щоб зберегти життєво важливий зріз системи перед падінням, у лінкері виділяють спеціальну секцію `.noinit`:

:::tabs
```c
/* Оголошення аварійного буфера в noinit секції пам'яті */
typedef struct {
    uint32_t magic_header;       /* 0xDEADBEEF для перевірки валідності */
    uint32_t reset_flags;        /* Копія регістра RCC_CSR / MCUSR */
    uint16_t last_timer_ticks;   /* Останнє зафіксоване значення таймера */
    uint16_t last_heartbeat;     /* Час останнього валідного пакету */
    uint8_t  active_task_id;     /* ID поточного завдання RTOS */
    uint8_t  last_error_code;    /* Код останнього аварійного стану */
    uint32_t crc32;              /* Контрольна сума цілісності */
} __attribute__((section(".noinit"))) crash_dump_t;

volatile crash_dump_t g_crash_dump;
```
```cpp
#include <cstdint>
#include <span>

/* Типізована C++20 структура діагностичного дампу пам'яті */
struct alignas(4) CrashDump {
    static constexpr uint32_t MagicHeader = 0xDEADBEEF;

    uint32_t magicHeader{0};
    uint32_t resetFlags{0};
    uint16_t lastTimerTicks{0};
    uint16_t lastHeartbeat{0};
    uint8_t  activeTaskId{0};
    uint8_t  lastErrorCode{0};
    uint32_t crc32{0};

    [[nodiscard]] bool isValid() const noexcept {
        return magicHeader == MagicHeader;
    }
};

// Розміщення в спеціальній секції пам'яті без ініціалізації нулями
[[gnu::section(".noinit")]] volatile CrashDump g_crashDump;
```
:::

Під час кожного старту прошивка перевіряє магічне число `magic_header`. Якщо це «гарячий» ресет — дані дампу негайно копіюються у виділений журнал або передаються на діагностичний порт, вказуючи точний стан системи за частку мікросекунди до аварії.

### Зіставлення часових шкал (Timeline Reconstruction)

Для встановлення причинно-наслідкового зв'язку сигнали логічного аналізатора та осцилографа синхронізують із програмними подіями за допомогою апаратних виводів налагодження (Debug Toggle Pins). Зміна логічного рівня на такому піні виконується за одну процесорну інструкцію (`GPIOB->BSRR = GPIO_PIN_0`) і додає нульову затримку в роботу прошивки.

![Хронологія аварійного каскаду](/root/course/embedded/rozbir-spravzhnoho-padinnia/img/rca-timeline-cascade.svg)
*Хронологія розвитку аварії: від переповнення 16-бітного таймера до просадки шини та скидання мікроконтролера.*

| Часова мітка | Підсистема | Зафіксована подія | Фізичний / логічний стан |
|---|---|---|---|
| `t = 65.500 с` | Системний таймер | `timer_ms = 65500` (0xFFDC) | Штатний обмін, серцебиття надходить кожні 10 мс, струм моторів 14 А. |
| `t = 65.535 с` | Лічильник часу | `timer_ms = 65535` (0xFFFF) | Межа розрядності 16-бітного регістра перед переходом у 0x0000. |
| `t = 65.536 с` | Модуль зв'язку | `timer_ms = 0` (Rollover) | Обчислення різниці дає від'ємне значення -> хибний таймаут зв'язку! |
| `t = 65.537 с` | Автомат зв'язку | Перехід у стан `LINK_LOST` | Виклик `panic_dump()`: спроба вивести 512 байт дампу в блокуючий UART. |
| `t = 65.540 с` | Планувальник RTOS | Блокування черги задач | Пріоритетне зависання: потік керування моторами не отримує процесорного часу. |
| `t = 65.542 с` | Драйвер інвертора | Пропуск 3 тактів ШІМ | Захист мотора вважає керування втраченим і миттєво розмикає всі MOSFET. |
| `t = 65.545 с` | Силова шина | Кидок струму `-dI/dt` | Індуктивність кабелів генерує викид напруги; шина VDD падає до 2.45 В. |
| `t = 65.546 с` | Ядро MCU | Спрацювання Brownout | Апаратне скидання процесора (BOR), падіння маніпулятора. |

Кореляція показала: мотор і живлення були повністю справними. Їхній колапс став лише закономірною реакцією заліза на панічну поведінку софту, викликану помилкою в один такт таймера. Детальніше методологію розмежування причини та наслідку в журналі розглядає [Кореляція сигналів у журналі](root:embedded/log-signal-correlation).

## Механізм першопричини: як мікроскопічний баг руйнує систему

Щоб зрозуміти, чому таймер переповнився саме на 65.5 секунді, необхідно проаналізувати розрядність лічильників та стандарт мови C щодо цілочисельних операцій.

Лічильник мілісекунд, оголошений як 16-бітне беззнакове число `uint16_t`, має максимальне значення:

```
2¹⁶ - 1 = 65535 мілісекунд = 65.535 секунди
```

На 65 536-й мілісекунді значення лічильника переходить із `65535` у `0`. У беззнаковій модульній арифметиці (Modulo `2¹⁶`) різниця між новим часом `now = 10` та попереднім часом отримання пакету `last_heartbeat = 65530` має дорівнювати рівно 16 мілісекундам:

```
(10 - 65530) mod 65536
= -65520 mod 65536    [віднімання у кільці цілих чисел]
= 16                  [додавання модуля 65536 до від'ємного залишку]
```

Оскільки 16 мс значно менше за встановлений поріг таймауту 100 мс, система мала б спокійно продовжити рух. Проте код містив одну з двох критичних пасток.

![Анатомія переповнення таймера](/root/course/embedded/rozbir-spravzhnoho-padinnia/img/timer-overflow-arithmetic.svg)
*Порівняння безпечного модульного віднімання та пасток неявного приведення типів при переповненні лічильника.*

### Пастка 1. Неявне розширення типів (Integer Promotion у C99)

Згідно зі стандартом C99/C11 (§6.3.1.1), будь-який цілочисельний тип, менший за `int` (зокрема `uint16_t` та `int16_t`), у будь-якому арифметичному виразі на 32-бітній архітектурі ARM Cortex-M автоматично підвищується до знакового 32-бітного типу `int` (`int32_t`).

Розглянемо вираз, написаний розробником:

:::tabs
```c
uint16_t now = get_ticks_16();           /* 10 */
uint16_t last_heartbeat = 65530;          /* 65530 */
#define TIMEOUT_MS 100U                   /* uint32_t */

/* Фатальний рядок з неявним приведенням до знакового int32_t: */
if ((now - last_heartbeat) > TIMEOUT_MS) {
    trigger_link_loss_panic();
}
```
```cpp
uint16_t now = getTicks16();             // 10
uint16_t lastHeartbeat = 65530;          // 65530
constexpr uint32_t TimeoutMs = 100U;

// Аналогічна пастка в C++ при порівнянні з uint32_t без явної типізації:
if ((now - lastHeartbeat) > TimeoutMs) {
    triggerLinkLossPanic();
}
```
:::

Що насправді робить компілятор під час генерації машинного коду:
1. `now` (10) розширюється до знакового `int32_t`: `+10`.
2. `last_heartbeat` (65530) розширюється до знакового `int32_t`: `+65530`.
3. Виконується знакове віднімання: `10 - 65530 = -65520` (значення `-65520` типу `int32_t`).
4. Далі відбувається порівняння знакового `int32_t` (-65520) та беззнакового `uint32_t` (100). За правилами узгодження типів мови C (Usual Arithmetic Conversions), знаковий операнд приводиться до беззнакового `uint32_t`!
5. Число `-65520` у 32-бітному двійковому доповняльному коді перетворюється на:

```
(uint32_t)(-65520) = 0xFFFF0010 = 4 294 901 776
```

6. Порівняння `4 294 901 776 > 100` повертає **TRUE**!

У результаті, замість істинної дельти в 16 мілісекунд, процесор отримує затримку в 4.29 мільярда мілісекунд і негайно оголошує фатальну втрату зв'язку.

### Пастка 2. Порівняння з точкою дедлайну в майбутньому

Другий поширений різновид тієї ж помилки — спроба зберегти не час останньої події, а абсолютний час дедлайну:

:::tabs
```c
/* Помилковий розрахунок абсолютної точки */
uint16_t deadline = last_heartbeat + TIMEOUT_MS; /* 65530 + 100 = 65630 -> 94 */

if (now > deadline) {
    trigger_timeout();
}
```
```cpp
// Помилковий розрахунок абсолютного дедлайну
uint16_t deadline = static_cast<uint16_t>(lastHeartbeat + TimeoutMs);

if (now > deadline) {
    triggerTimeout();
}
```
:::

Якщо `last_heartbeat = 65530`, а `TIMEOUT_MS = 100`, у 16-бітній змінній значення дедлайну обрізається до `94` (`0x005E`).
Поки `now` перебуває в діапазоні від 65530 до 65535, умова `now (65534) > deadline (94)` стає істинною за 96 мс **ДО** настання реального таймауту.

Якщо ж розрахунок дедлайну виконувався у 32-бітній змінній (`65630`), то після переходу `now` у нуль умова `now (10) > 65630` залишатиметься хибною протягом наступних **65.5 секунд**! Сторож повністю «сліпне», ігноруючи реальні розриви зв'язку.

### Каскадний перехід до апаратного колапсу

Коли умова помилково спрацювала, система увійшла в режим аварійної обробки:
1. **Захлинання діагностичного буфера:** функція паніки почала виводити повний дамп пам'яті через блокуючу функцію `UART_Transmit()` на швидкості 115 200 бод. Передача 512 байт забрала понад 44 мілісекунди блокуючого очікування в циклі `while (!(UART->SR & TXE))`.
2. **Пріоритетне голодування (Priority Inversion):** поки потік зв'язку тримав процесор у блокуючому виведенні, критичний потік розрахунку кутів стабілізації (період 10 мс) пропустив чотири цикли регулювання.
3. **Аварійний розрив інвертора:** сторожовий таймер силового моста зафіксував пропуск циклів керування та розімкнув усі шість MOSFET-транзисторів на піковому струмі 14 А.
4. **Індуктивний удар і Brownout:** струм у дротах живлення довжиною 1.5 метра миттєво впав до нуля. Згідно із законом самоіндукції (`V = L · dI/dt`), паразитна індуктивність джгута (~2 мкГн) викликала різкий провал напруги на вході стабілізатора. Напруга живлення мікроконтролера впала нижче порогу 2.7 В, викликавши апаратне скидання ядра. Подробиці виявлення таких надшвидких аномалій описано в темі [Побачити 200 мікросекунд, що вбивають пристрій](root:embedded/pobachyty-200-mikrosekund-shcho-vbyvaiut-prystrii).

## Фізика перехідного процесу в силовій підсистемі

Щоб зрозуміти, чому просте програмне вимкнення ШІМ призвело до фізичного перезавантаження мікроконтролера, слід розрахувати енергетику комутаційного перехідного процесу.

Джгут живлення від акумулятора до силового інвертора мав довжину `l = 1.5 м`. Погонна індуктивність витої пари становить приблизно `1.2 мкГн/м`, що дає сумарну паразитну індуктивність лінії живлення:

```
L = 1.5 · 1.2 мкГн = 1.8 мкГн
```

Перед аварійним відключенням електродвигун працював під навантаженням, споживаючи струм `I = 14 А`. Енергія магнітного поля, накопичена в індуктивності проводів живлення, дорівнює:

```
E = 0.5 · L · I²
= 0.5 · (1.8 · 10⁻⁶) · 14²    [формула енергії магнітного поля котушки]
= 0.5 · 1.8 · 10⁻⁶ · 196      [піднесення струму 14 до квадрата]
= 1.764 · 10⁻⁴ Дж = 176.4 мкДж [кінцевий розрахунок накопиченої енергії]
```

Коли драйвер через аварійний виняток миттєво закрив силові транзистори за час `dt ≈ 200 нс`, швидкість зміни струму склала:

```
dI/dt = 14 А / (200 · 10⁻⁹ с) = 70 · 10⁶ А/с
```

Електрорушійна сила самоіндукції, згенерована в проводах, склала:

```
V_spike = L · (dI/dt)
= (1.8 · 10⁻⁶) · (70 · 10⁶)   [підстановка індуктивності та швидкості струму]
= 126 В                       [розрахунок амплітуди перенапруги]
```

Цей імпульс перенапруги вдарив по вхідних керамічних конденсаторах. Але одразу слідом за викидом настав зворотний коливальний провал (Ringdown Sag): струм із батареї різко обірвався, а ємності вхідного фільтра (всього 47 мкФ) не вистачило для утримання шини 12 В під час перехідного процесу. Вхідна напруга лінійного стабілізатора 3.3 В опустилася нижче мінімальної напруги падіння (Dropout Voltage), внаслідок чого шина живлення цифрової частини VDD просіла до 2.45 В на час 14 мікросекунд.

Внутрішній детектор напруги мікроконтролера (Brownout Reset, налаштований на поріг BOR Level 3 = 2.7 В) зреагував на провал менш ніж за 2 мікросекунди і згенерував апаратний ресет ядра, заблокувавши роботу всієї плати.

## Комплексні корекційні та запобіжні дії (CAPA Framework)

Для усунення наслідків інциденту та запобігання подібним відмовам у майбутньому застосовують міжнародну інженерну методологію 8D / CAPA (Corrective and Preventive Actions — корекційні та запобіжні дії).

```
                 [ CAPA Framework ]
                         │
        ┌────────────────┴────────────────┐
        ▼                                 ▼
[ Корекція (Correction) ]       [ Запобігання (Prevention) ]
  • Явне приведення типів         • 64-бітний монотонний час
  • Безпечний макрос дельти       • Неблокуючий Ring Buffer
  • Плавний спуск мотора          • HIL Time-Warp тести в CI
```

### Рівень 1. Пряме виправлення коду (Correction)

Математично правильне віднімання у беззнаковому кільці вимагає **явного приведення результату віднімання назад до беззнакового типу** тієї ж розрядності перед порівнянням із таймаутом:

:::tabs
```c
/* Безпечна макро-функція модульної перевірки дедлайну для будь-якої розрядності */
#define TIME_AFTER_16(now, last, timeout) \
    (((uint16_t)((uint16_t)(now) - (uint16_t)(last))) > ((uint16_t)(timeout)))

#define TIME_AFTER_32(now, last, timeout) \
    (((uint32_t)((uint32_t)(now) - (uint32_t)(last))) > ((uint32_t)(timeout)))
```
```cpp
#include <concepts>
#include <cstdint>

/* Безпечна C++20 концептуальна функція перевірки переповнення */
template <std::unsigned_integral T>
[[nodiscard]] constexpr bool isTimeoutElapsed(T now, T lastEvent, T timeout) noexcept {
    return static_cast<T>(now - lastEvent) > timeout;
}
```
:::

Коли `now = 10`, а `last = 65530`, вираз `(uint16_t)(10 - 65530)` явно відсікає старші біти після знакового розширення, залишаючи чисте число `16`, яке коректно порівнюється з `100`.

### Рівень 2. Архітектурні корективи (Preventive Actions)

1. **Єдиний 64-бітний монотонний час:** відмова від 16-бітних таймерів для бізнес-логіки. Використання 64-бітного лічильника мілісекунд гарантує роботу без переповнення протягом 584 мільйонів років.
2. **Неблокуюче логування (Drop-Oldest Circular Buffer):** якщо діагностичний буфер заповнений, нові логи або перезаписують найстаріші записи, або відкидаються. Жодна діагностична операція не має права блокувати виконання системи більше ніж на 5 мікросекунд.
3. **Плавне аварійне зниження потужності (Soft Torque Derating):** у разі виникнення помилки зв'язку силові ключі не розмикаються миттєво, а плавно знижують шпаруватість ШІМ зі швидкістю 10% за 10 мс, усуваючи кидки зворотної ЕРС на шині живлення.
4. **Апаратний захист супервізором напруги:** встановлення зовнішнього прецизійного супервізора живлення для запобігання зависанню логіки, як показано в [Супервізор напруги: коли внутрішнього BOD мало](root:hw-power/voltage-supervisor-ic).

## Модуль безпечного обліку часу та захисту від відмов на C та C++

Нижче наведено закінчений модуль захисту каналу зв'язку та керування приводом, який реалізує монотонний облік часу, захист від переповнення та безпечне аварійне відключення навантаження.

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>

#define HEARTBEAT_TIMEOUT_TICKS  100U  /* Таймаут зв'язку: 100 мс */
#define MOTOR_DERATE_STEP_PCT     10U  /* Крок плавного скидання струму */

typedef enum {
    DRIVE_STATE_INIT = 0,
    DRIVE_STATE_RUNNING,
    DRIVE_STATE_FAULT_DERATING,
    DRIVE_STATE_SAFE_STOP
} drive_state_t;

typedef struct {
    uint32_t last_heartbeat_tick;
    uint32_t current_power_pct;
    drive_state_t state;
    uint32_t fault_code;
} drive_controller_t;

/* Апаратна заглушка керування ШІМ */
extern void hw_motor_set_pwm(uint32_t power_pct);
extern uint32_t hw_get_monotonic_ticks_ms(void);

void drive_controller_init(drive_controller_t *ctrl) {
    ctrl->last_heartbeat_tick = hw_get_monotonic_ticks_ms();
    ctrl->current_power_pct = 0;
    ctrl->state = DRIVE_STATE_INIT;
    ctrl->fault_code = 0;
    hw_motor_set_pwm(0);
}

void drive_controller_feed_heartbeat(drive_controller_t *ctrl) {
    ctrl->last_heartbeat_tick = hw_get_monotonic_ticks_ms();
    if (ctrl->state == DRIVE_STATE_FAULT_DERATING || ctrl->state == DRIVE_STATE_INIT) {
        ctrl->state = DRIVE_STATE_RUNNING;
    }
}

/* Періодичний крок керування (викликається кожні 10 мс) */
void drive_controller_update(drive_controller_t *ctrl, uint32_t target_power_pct) {
    uint32_t now = hw_get_monotonic_ticks_ms();

    /* Безпечна беззнакова перевірка різниці часу (modulo 2^32) */
    uint32_t elapsed = now - ctrl->last_heartbeat_tick;
    bool link_lost = (elapsed > HEARTBEAT_TIMEOUT_TICKS);

    switch (ctrl->state) {
        case DRIVE_STATE_RUNNING:
            if (link_lost) {
                ctrl->state = DRIVE_STATE_FAULT_DERATING;
                ctrl->fault_code = 0xE001; /* Помилка: розрив лінка */
            } else {
                ctrl->current_power_pct = target_power_pct;
                hw_motor_set_pwm(ctrl->current_power_pct);
            }
            break;

        case DRIVE_STATE_FAULT_DERATING:
            /* Плавний спуск струму для усунення індуктивного викиду */
            if (ctrl->current_power_pct > MOTOR_DERATE_STEP_PCT) {
                ctrl->current_power_pct -= MOTOR_DERATE_STEP_PCT;
            } else {
                ctrl->current_power_pct = 0;
                ctrl->state = DRIVE_STATE_SAFE_STOP;
            }
            hw_motor_set_pwm(ctrl->current_power_pct);
            break;

        case DRIVE_STATE_SAFE_STOP:
        case DRIVE_STATE_INIT:
        default:
            hw_motor_set_pwm(0);
            break;
    }
}
```
```cpp
#include <cstdint>
#include <chrono>
#include <algorithm>

using namespace std::chrono_literals;

class DriveController {
public:
    enum class State : uint8_t {
        Init,
        Running,
        FaultDerating,
        SafeStop
    };

    struct HardwareInterface {
        void (*setMotorPwm)(uint32_t powerPct);
        std::chrono::milliseconds (*getMonotonicTime)();
    };

    explicit DriveController(HardwareInterface hw) noexcept
        : hw_{hw}, lastHeartbeat_{hw_.getMonotonicTime()} {
        hw_.setMotorPwm(0);
    }

    void feedHeartbeat() noexcept {
        lastHeartbeat_ = hw_.getMonotonicTime();
        if (state_ == State::FaultDerating || state_ == State::Init) {
            state_ = State::Running;
        }
    }

    void update(uint32_t targetPowerPct) noexcept {
        const auto now = hw_.getMonotonicTime();
        const auto elapsed = now - lastHeartbeat_;
        const bool linkLost = (elapsed > HeartbeatTimeout);

        switch (state_) {
            case State::Running:
                if (linkLost) {
                    state_ = State::FaultDerating;
                    faultCode_ = 0xE001;
                } else {
                    currentPowerPct_ = std::clamp(targetPowerPct, 0U, 100U);
                    hw_.setMotorPwm(currentPowerPct_);
                }
                break;

            case State::FaultDerating:
                // Плавне зниження шпаруватості без кидків напруги
                if (currentPowerPct_ > DerateStepPct) {
                    currentPowerPct_ -= DerateStepPct;
                } else {
                    currentPowerPct_ = 0;
                    state_ = State::SafeStop;
                }
                hw_.setMotorPwm(currentPowerPct_);
                break;

            case State::SafeStop:
            case State::Init:
            default:
                hw_.setMotorPwm(0);
                break;
        }
    }

    [[nodiscard]] State state() const noexcept { return state_; }
    [[nodiscard]] uint32_t faultCode() const noexcept { return faultCode_; }

private:
    static constexpr auto HeartbeatTimeout = 100ms;
    static constexpr uint32_t DerateStepPct = 10;

    HardwareInterface hw_;
    std::chrono::milliseconds lastHeartbeat_{0};
    uint32_t currentPowerPct_{0};
    State state_{State::Init};
    uint32_t faultCode_{0};
};
```

## Підсумковий синтез: культура аналізу відмов

Будь-яка складна вбудована система падає не через одну ізольовану помилку, а через резонанс між програмними дефектами та фізичними обмеженнями апаратної частини. Поодинокий баг переповнення таймера сам по собі не спалив би драйвер і не скинув би мікроконтролер, якби панічний обробник помилки не заблокував планувальник задач, а інвертор не скинув 14 ампер за одну мікросекунду на довгих проводах живлення.

Інженерна зрілість команди визначається не відсутністю збоїв під час розробки, а глибиною їхнього аналізу. Справжній Root Cause Analysis завершується лише тоді, коли:
1. Знайдено й математично доведено першопричину на найнижчому рівні абстракції.
2. Проведено повну хронологічну реконструкцію каскаду з підтвердженням осцилограмами та логами пам'яті.
3. Впроваджено багаторівневий захист: усунено баг у коді, додано плавне демпфування в силовий тракт і налаштовано автоматичний регресійний стенд у CI/CD, що гарантує неможливість повторення катастрофи у серійному виробництві.
