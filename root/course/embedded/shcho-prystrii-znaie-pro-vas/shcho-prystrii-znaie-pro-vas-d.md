Компактний польовий пристрій — автономний трекер логістики, агротехнічний сенсорний вузол, промисловий лічильник електроенергії чи бортовий контролер безпілотного апарата — під час повсякденної роботи накопичує колосальний масив конфіденційної інформації. У його енергонезалежній пам'яті осідають паролі від корпоративних точок доступу Wi-Fi, приватні ключі шифрування та клієнтські сертифікати TLS, довготривалі токени доступу до хмарних серверів, повна історія координат і переміщень із супутникового приймача GNSS та часові ряди вимірювань датчиків.

Доки прилад перебуває на захищеному об'єкті або під безпосереднім наглядом оператора, розробники часто почуваються в безпеці завдяки мережевим протоколам TLS та захищеним тунелям зв'язку. Проте щойно пристрій втрачено в полі, викрадено чи вилучено сторонніми особами під час інциденту, ситуація докорінно змінюється. Нападник отримує необмежений у часі фізичний доступ до апаратної частини. Якщо мікросхеми пам'яті не захищені належним чином, а прошивка не має апаратних механізмів екстреного знищення даних, зняття прямого дампа з мікросхеми Flash-пам'яті за допомогою звичайного USB-програматора за кілька доларів розкриває не лише секрети самого виробу, але й компрометує всю корпоративну інфраструктуру, до якої він мав доступ.

Фізична безпека польового вузла спирається на три взаємопов'язані інженерні бар'єри: точну інвентаризацію точок зберігання секретів, усунення залишкової інформації в напівпровідниковій структурі пам'яті та автономний ланцюг екстреного знищення даних. На рівні кремнію звичайне програмне перезаписування файлу чи змінної не гарантує зникнення бітів: механізми вирівнювання зносу (wear leveling) та блокова організація Flash-пам'яті залишають старі копії ключів у невичищених секторах. Коли зловмисник розбирає корпус і підключає логічний аналізатор безпосередньо до шин SPI чи ліній живлення, захистити дані здатне лише апаратне виявлення вторгнення: сенсорний контур фіксує несанкціоноване відкриття й миттєво запускає апаратний каскад самоочищення (Zeroization) — від скидання ключів у захищеному батарейному домені за частки мікросекунди до повного випалювання або стирання масивів енергонезалежної пам'яті.

## 1. Інвентаризація та карта чутливих даних у польовому пристрої

Щоб побудувати надійну систему захисту, інженер насамперед повинен скласти вичерпну карту того, де саме, в якому форматі та які конкретно секрети циркулюють усередині виробу під час його життєвого циклу.

```
 ┌────────────────────────────────────────────────────────────────────────┐
 │                   КАРТА ЧУТЛИВИХ ДАНИХ ПРИСТРОЮ                        │
 ├────────────────────────────┬───────────────────────────────────────────┤
 │ 1. Мережеві облікові дані  │ WPA2/WPA3 PSK, EAP-TLS, APN/PIN модема   │
 │ 2. Хмарні секрети та сесії │ JWT Bearer, AWS/Azure X.509, API-токени   │
 │ 3. Журнали й геолокація    │ GNSS треки, NMEA логи, часові ряди датчиків│
 │ 4. Криптографічні корені   │ Майстер-ключі AES-XTS, Ed25519 / ECDSA    │
 └────────────────────────────┴───────────────────────────────────────────┘
```

Усі конфіденційні дані автономного пристрою поділяються на чотири фундаментальні категорії:

### 1. Мережеві облікові дані (Network Credentials)

Для виходу на зв'язок пристрій зберігає параметри доступу до фізичних і канальних середовищ передачі:
- **Паролі бездротових мереж Wi-Fi (WPA2/WPA3 Pre-Shared Key):** Відкритий текстовий пароль або згенерований із нього 256-бітний парний майстер-ключ PMK (Pairwise Master Key). Витік цього пароля дає змогу нападнику проникнути у внутрішню локальну мережу підприємства, перехоплювати чужий трафік або розгортати атаки на сусідні мережеві вузли.
- **Сертифікати корпоративного Wi-Fi (802.1X / EAP-TLS):** Приватний ключ клієнта та сертифікат CA для корпоративної авторизації на радіусі дії точок доступу.
- **Параметри стільникових модемів (Cellular APN / PIN / PUK):** Рядок точки доступу APN (Access Point Name), логін і пароль для авторизації у закритих корпоративних VPN-мережах мобільних операторів (наприклад, для лічильників газу чи електрики), а також PIN-код SIM-картки. Володіючи цими даними, нападник може підключити свій комп'ютер до закритої стільникової підмережі телеметрії компанії.

### 2. Хмарні та сервісні секрети (Cloud & Session Identity)

Для передачі телеметрії та отримання команд пристрій проходить автентифікацію на хмарних серверах:
- **Клієнтські сертифікати та приватні ключі TLS (X.509):** Пари ключів (RSA-2048 або ECC secp256r1), за якими брокери MQTT (AWS IoT Core, Azure IoT Hub, Mosquitto) розпізнають конкретний екземпляр обладнання.
- **Токени авторизації OAuth2 та JWT (JSON Web Tokens):** Довготривалі Refresh Tokens або короткоживучі Access Tokens. Маючи витягнутий токен, зловмисник може надсилати фальшиву телеметрію від імені пристрою або зчитувати команди керування, призначені для пристрою.
- **Паролі локального адміністрування:** Хеші або відкриті паролі веб-інтерфейсу налаштування, панелі Bluetooth BLE чи внутрішнього сервісного меню.

### 3. Користувацька історія, журнали та геолокація (User Data, Logs & Telemetry)

Навіть якщо пристрій не містить мережевих паролів, самі дані його роботи становлять величезну цінність:
- **GNSS/GPS треки та координати бази:** Точки зльоту й посадки безпілотника, точні координати маршруту патрулювання, координати розташування польових датчиків. Зчитавши дамп пам'яті вилученого модуля, нападник дізнається точне місце дислокації бази оператора або прихованого спостережного пункту.
- **Журнали вимірювань датчиків (Telemetry Logs):** Часові ряди температур, акустичних сигналів, вібраційних спектрів або фотокадрів, збережених у кеші перед відправкою.
- **Калібрувальні матриці сенсорів:** Індивідуальні зміщення нулів та коефіцієнти чутливості акселерометрів, гіроскопів і магнітометрів. Ці коефіцієнти утворюють унікальний апаратний «відбиток» (Hardware Fingerprint) конкретного фізичного чипа.

### 4. Майстер-ключі криптографії та цілісності (Cryptographic Roots)

На найглибшому рівні знаходяться симетричні та асиметричні криптографічні ключі:
- **Ключі шифрування локального сховища (AES-128/256-XTS або AES-GCM):** Секрети, якими шифруються розділи Flash-пам'яті чи зовнішньої SD-картки.
- **Ключі автентифікації повідомлень (HMAC Secret Keys):** Секрети для контролю незмінності локальних журналів та підпису пакетів протоколів обміну.

| Категорія таємниці | Типове місце зберігання | Ризик у разі вилучення дампа |
|---|---|---|
| Паролі Wi-Fi / APN | NVS / LittleFS / EEPROM | Проникнення нападника в локальну або стільникову мережу підприємства |
| Клієнтські сертифікати TLS | Flash (захищений розділ) | Перехоплення черги MQTT, генерація фальшивих аварійних телеметрій |
| Токени сесій OAuth2 / JWT | NVS / оперативна пам'ять | Неавторизований доступ до хмарного API від імені пристрою |
| GPS-треки та NMEA-логи | Файлова система Flash / SPIFFS | Розкриття бази базування, маршрутів руху та прихованих об'єктів |
| Калібрувальні коефіцієнти | OTP / EEPROM / Flash | Клонування апаратного профілю пристрою для обходу автентифікації |
| Майстер-ключ AES-XTS | Backup SRAM / eFuse | Повна компрометація всіх зашифрованих розділів пам'яті виробу |

> 🔧 **Навіщо це.** Складання таблиці інвентаризації таємниць — обов'язковий перший крок розробки архітектури безпеки (Threat Modeling). Якщо інженер чітко знає, які саме байти є критичними, він може застосувати диференційований підхід: не намагатися затерти 16 мегабайтів важкої Flash-пам'яті за 5 мікросекунд, а зосередити апаратне миттєве очищення на 32-байтному мастер-ключі, що робить увесь масив Flash миттєво нерозшифровним.

## 2. Залишкова пам'ять у Flash: чому просте «видалення» лишає дані у фізичних комірках

Найпоширеніша ілюзія серед розробників полягає у переконанні, що виклик функції видалення запису або запис нулів поверх файлу призводить до фізичного знищення інформації на напівпровідниковому кристалі. На практиці фізика кремнієвих комірок Flash та алгоритми вбудованих файлових систем діють геть інакше.

### Фізичні обмеження комірок NOR Flash

Енергонезалежна пам'ять Flash будується на польових транзисторах із плаваючим затвором (Floating Gate) або пасткою заряду (Charge Trap):

```
         Управлінський затвор (Control Gate)
       ───────────────────────────────────────
             Діелектрик (Верхній оксид)
       ───────────────────────────────────────
         Плаваючий затвор (Floating Gate) ◄── [Електрони в пастці: біт 0]
       ───────────────────────────────────────
             Тунельний оксид (SiO2, 8-10 нм)
       ───────────────────────────────────────
         Кремнієва підкладка (Substrate)
```

Властивості комірок NOR Flash мають жорстку фізичну асиметрію:
1. **Стертий стан (Erased State):** Усі комірки фізично не мають накопиченого заряду на плаваючих затворах, що відповідає логічній одиниці (`1` або байту `0xFF`).
2. **Операція запису (Program):** Можлива побайтово або постірінково (зазвичай порціями по 256 байтів). Запис полягає в інжекції гарячих електронів (Channel Hot Electron Injection) крізь тунельний оксид на плаваючий затвор і може змінювати біти **виключно в один бік — із `1` в `0`**.
3. **Операція стирання (Erase):** Повернути окремий біт чи байт назад із `0` в `1` фізично неможливо. Щоб видалити електрони з плаваючого затвора, необхідно подати високу зворотну напругу тунелювання Фаулера-Нордгейма (порядка 12–20 В) на всю спільну підкладку блоку. Тому стирання виконується лише великими блоками — секторами по `4 КБ` (4096 байтів) або блоками по `32 КБ / 64 КБ`.

```
  Стертий стан (0xFF)  ──[ Запис сторінки ]──►  Записаний стан (0x4A)
     (усі біти = 1)        (тільки 1 → 0)         (з'явилися нулі)
           ▲                                             │
           │                                             ▼
           └───────────[ СТИРАННЯ СЕКТОРА 4 КБ ]─────────┘
                       (тільки 0 → 1 для всього блоку,
                        тривалість: 50–100 мс)
```

Операція стирання сектору триває дуже довго за мірками мікроконтролера — від **40 до 150 мілісекунд**, а стирання всього кристала (Chip Erase) — від **5 до 30 секунд**. Крім того, кожна комірка витримує лише обмежену кількість циклів стирання (від 10 000 до 100 000 циклів), після чого тонкий підзатворний діелектрик зазнає незворотного пробою.

### Пастка Log-Structured сховищ та Copy-On-Write (NVS, LittleFS, SPIFFS)

Щоб мікроконтролер не зависав на сотні мілісекунд при кожному збереженні налаштувань і не зношував один сектор до дірок, усі сучасні вбудовані файлові системи та сховища ключ-значення (Non-Volatile Storage / NVS в ESP-IDF, LittleFS, SPIFFS, UBIFS) проектуються як **лог-структуровані системи з механізмом Copy-On-Write (CoW)** та вирівнюванням зносу (Wear Leveling).

Розгляньмо, що відбувається під час виклику функції оновлення значення:

:::tabs
```c
// Оновлення пароля Wi-Fi через NVS API
nvs_handle_t my_handle;
nvs_open("storage", NVS_READWRITE, &my_handle);
nvs_set_str(my_handle, "wifi_pass", "NewSecretPass2026");
nvs_commit(my_handle);
nvs_close(my_handle);
```
```cpp
// Оновлення пароля Wi-Fi через ідіоматичний C++ інтерфейс NVS
#include <memory>
#include <string_view>

class NvsStorage {
public:
    explicit NvsStorage(std::string_view ns) noexcept {
        // Ініціалізація дескриптора NVS
    }
    
    bool setString(std::string_view key, std::string_view value) noexcept {
        // Запис нового значення у лог NVS
        return true;
    }
};

void updateCredentials(std::string_view newPass) {
    NvsStorage storage("storage");
    storage.setString("wifi_pass", newPass);
}
```
:::

Файлова система діє за таким алгоритмом:
1. Вона **не стирає** сектор, де лежав старий пароль `"OldPass123"`.
2. Вона шукає наступну вільну сторінку в поточному або сусідньому секторі Flash, де байти ще мають незаписаний стан `0xFF`.
3. Вона записує туди новий запис із ключем `"wifi_pass"` та новим значенням `"NewSecretPass2026"`, виставляючи прапорець валідності запису в `0xFE` (Valid).
4. У старій сторінці файлова система знаходить заголовок попереднього запису і записує туди кілька нулів, змінюючи прапорець валідності з `0xFE` на `0xFC` (Written/Invalid) або `0xF8` (Deleted).

![Фрагментація Flash та залишкові дані при оновленні ключів](/root/course/embedded/shcho-prystrii-znaie-pro-vas/img/flash-retention-fragmentation.svg)
*Механізм збереження залишкових даних у Flash: при зміні пароля чи видаленні токена файлова система лише переводить біти прапорця заголовка з 1 у 0, позначаючи старий блок недійсним. Фізичні байти секрету на плаваючих затворах залишаються неушкодженими і легко зчитуються зовнішнім програматором.*

Фізичні байти рядка `"OldPass123"` або видаленого токена JWT **взагалі не змінюються**. Вони залишаються закодованими зарядами на плаваючих затворах кремнієвих транзисторів. Сектор буде фізично очищений лише тоді, коли весь лог переповниться, і фоновий процес збирання сміття (Garbage Collector) вирішить скопіювати активні записи в інше місце й подати команду стирання на старий блок.

### Чому перезапис файлу нулями не рятує?

Якщо розробник наївно відкриє файл у файловій системі та спробує «затерти» його нулями:

:::tabs
```c
// Наївна спроба затерти файл нулями на рівні C
FILE *f = fopen("/spiffs/token.dat", "r+");
if (f) {
    uint8_t zeros[64] = {0};
    fwrite(zeros, 1, sizeof(zeros), f);
    fclose(f);
}
```
```cpp
// Наївна спроба затерти файл нулями на рівні C++
#include <fstream>
#include <array>

void naiveSanitizeFile() {
    std::fstream file("/spiffs/token.dat", std::ios::in | std::ios::out | std::ios::binary);
    if (file.is_open()) {
        std::array<uint8_t, 64> zeros{};
        file.write(reinterpret_cast<const char*>(zeros.data()), zeros.size());
        file.close();
    }
}
```
:::

Механізм Copy-On-Write виділить під ці нулі **новий фізичний сектор**, а старий сектор із даними токена просто позначить як застарілий блок!

У результаті, якщо нападник випаяє мікросхему SPI Flash у корпусі SOIC-8 або підключиться до неї кліпсою-прищіпкою і прочитає повний бінарний образ (Flash Dump), він побачить у дампі **всю історію змін кожного пароля та всі видалені місяць тому файли**. Детальний аналіз схем захисту наведено у [довідці апаратних датчиків розкриття корпусу](root:embedded/shcho-prystrii-znaie-pro-vas/comp-tamper-sensors.md).

> 🔧 **Навіщо це.** Розуміння лог-структури Flash доводить: безпечне видалення даних неможливе на рівні стандартних викликів файлових систем POSIX. Щоб гарантовано знищити секрет у Flash, потрібно або виконати низькорівневе фізичне стирання всього сектора (Sector Erase `4 КБ`), або використовувати наскрізне шифрування розділів, де знищується сам сесійний ключ дешифрування.

## 3. Апаратна детекція фізичного злому корпусу (Anti-Tamper Detection)

Оскільки Flash-пам'ять повільна, а захист даних вимагає своєчасного реагування, пристрій повинен мати органи чуття, які зафіксують спробу фізичного проникнення до того, як зловмисник встигне підключити зонди до ліній зв'язку або знеструмити плату.

Комплексна система анти-темпер моніторингу будується на чотирьох фізичних бар'єрах:

![Апаратні сенсори анти-темпер моніторингу в захищеному корпусі](/root/course/embedded/shcho-prystrii-znaie-pro-vas/img/anti-tamper-sensors-enclosure.svg)
*Чотири лінії оборони захищеного корпусу: активна струмопровідна сітка на кришці, позолочені мікроперемикачі розкриття, оптичний детектор світла у замкненій порожнині та центральний апаратний RTC/Backup домен із незалежним резервним живленням VBAT.*

### 1. Механічні кінцевики розкриття (Tamper Push-Buttons)

Підпружинені мікроперемикачі з позолоченими контактами встановлюються на платі так, щоб кришка корпусу в закритому стані утримувала їх натиснутими:
- **Нормально замкнена струмова петля (NC Loop):** Доріжка опитування проходить через кнопку й підтягується до резервного живлення `VBAT`. Відкручування навіть одного гвинта послаблює тиск кришки, контакти розмикаються, і на вході мікроконтролера формується фронт сигналу тривоги за час менше `50 мкс`.
- **Захист від шунтування резистором EOL:** Щоб зловмисник не міг просвердлити мікроотвір і підпаяти паралельну перемичку, кнопка включається у резистивний подільник, а внутрішній АЦП перевіряє точне значення опору кола.

### 2. Активна струмопровідна сітка на кришці (Active Conductive Mesh)

Для захисту від локального свердління чи пропилювання корпусу внутрішня поверхня кришки покривається суцільним звивистим шлейфом провідників із кроком 0.1–0.2 мм:
- Спроба зробити отвір діаметром навіть 0.5 мм перерізає принаймні одну доріжку або закорочує сусідні витки.
- Контролер постійно сканує сітку змінними імпульсами або контролює баланс моста Уїтстона, фіксуючи зміну ємності, опору чи обрив за лічені наносекунди.

### 3. Оптичні сенсори в замкненій порожнині (Dark Cavity Sensing)

Усередині повністю непрозорого закритого корпусу панує абсолютна темрява:
- На платі біля критичних мікросхем встановлюється кремнієвий PIN-фотодіод або високочутливий фототранзистор, включений у режимі зворотного зміщення.
- У темряві темновий струм становить менше `100 пА` (`0.0001 мкА`).
- Поява навіть мізерної щілини (шириною 0.1 мм), крізь яку проникає розсіяне світло інтенсивністю понад `0.5 лк`, генерує фотострум у кілька мікроамперів. Цей струм подається на швидкодіючий аналоговий компаратор мікроконтролера, що перекидає тригер тривоги за час, менший за `1 мкс`.

### 4. Сенсори умов експлуатації (Out-of-Bounds Detection)

Зловмисники нерідко намагаються обійти захист без розкриття корпусу:
- **Кріогенна заморозка:** Охолодження приладу нижче `-30 °C` за допомогою рідкого газу для збереження вмісту оперативної пам'яті (Cold Boot Attack) фіксується вбудованим терморезистором або термодатчиком кристала, викликаючи превентивне самоочищення.
- **Детектори імпульсів живлення (Voltage Glitching):** Швидкісні компаратори стежать за формою напруги живлення ядра, ловлячи спроби збити виконання інструкцій короткочасними просадками напруги.

Усі сенсори підключаються до спеціального апаратного периферійного блоку мікроконтролера — **Tamper / Backup Domain** (наявного в STM32, NXP LPC, ESP32), який живиться від окремого резервного виводу `VBAT` (літієва батарейка-таблетка або іоністор) і функціонує безперервно навіть за повної відсутності основного живлення приладу.

## 4. Протокол миттєвого знешкодження (Zeroization) та знищення криптоключів

Згідно зі стандартом захисту криптографічних модулів FIPS 140-3, процедура гарантованого стирання (**Zeroization**) визначається як метод знищення ключів і конфіденційних даних, що унеможливлює їх відновлення будь-якими відомими фізичними чи програмними засобами.

Якщо корпус розкрито, у пристрою є лічені мілісекунди до того, як нападник від'єднає акумулятор або встромить щупи в шини. Тому процедура стирання будується як **жорсткий часовий ешелонований каскад**:

![Хронологія та каскад гарантованого знешкодження Zeroization](/root/course/embedded/shcho-prystrii-znaie-pro-vas/img/zeroization-cascade.svg)
*Чотири рівні часового каскаду Zeroization: від миттєвого апаратного скидання Backup SRAM за 100 нс (криптографічне стирання) до повного затирання RAM, стирання секторів Flash та незворотного випалювання eFuse захисту.*

### Рівень 1: Миттєве апаратне знищення летких ключів (Час: < 100 наносекунд)

Це найважливіший крок усієї системи оборони, відомий як **криптографічне стирання (Crypto-Shredding)**:
- Усі конфіденційні розділи Flash-пам'яті шифруються на льоту стійким алгоритмом (наприклад, AES-256-XTS).
- Майстер-ключ шифрування зберігається виключно в енергозалежних регістрах резервного домену (STM32 RTC Backup Registers або Backup SRAM).
- При спрацюванні будь-якого тампер-входу (TAMP pin) внутрішня апаратна логіка мікроконтролера **автоматично, на рівні кремнієвих транзисторів**, зануляє всі регістри Backup SRAM за один такт або миттєво розмикає ключ живлення `VBAT`.
- Навіть якщо нападник відключить живлення через 5 мілісекунд, відновити майстер-ключ із розряджених конденсаторів SRAM неможливо. Без цього ключа весь гігабайтний масив Flash-пам'яті перетворюється на математично нерозшифровний білий шум.

### Рівень 2: Гарантоване очищення оперативної пам'яті (RAM Sanitization, Час: ≈ 50 мікросекунд)

Якщо головний процесор активний, сигнал тампера викликає немасковане апаратне переривання з найвищим пріоритетом (Preemption Priority 0):
- Обробник переривання запускає функцію очищення оперативної пам'яті ядра, стеків викликів та робочих буферів mbedTLS.
- **Пастка оптимізатора:** Звичайний `memset()` викидається компілятором як мертвий запис (dead store elimination). Очищення зобов'язане використовувати бар'єри пам'яті або `volatile`-покажчики (функція `secure_memzero`).

### Рівень 3: Фізичне стирання та затирання Flash (Час: 50 мс – 2 с)

Якщо на платі є відкриті розділи (наприклад, системні журнали або нешифровані конфігураційні файли):
- Контролер Flash-пам'яті видає низькорівневу команду стирання секторів (Sector Erase `0x20`) або команду масового стирання чипа (Chip Erase `0xC7`).
- Для надійності перед стиранням у всі сторінки записуються байти `0x00`, що переводить плаваючі затвори в заряджений стан, після чого подається команда повного стирання в `0xFF`.

### Рівень 4: Незворотне перетворення на «цеглину» (eFuse Burning, Час: ≈ 100–200 мс)

Щоб унеможливити відновлення та повторне використання пристрою через сервісні інтерфейси:
- Прошивка активує внутрішній генератор високої напруги eFuse і перепалює плавки біти:
  - Біт `JTAG_DISABLE` / `SWD_DISABLE` — назавжди відключає інтерфейси налагодження кристала.
  - Біт `FLASH_CRYPT_CNT` / `SECURITY_LEVEL_3` — переводить процесор у режим незворотного апаратного блокування.
- Контролер ініціює апаратний перезапуск у стан вічного блокування (Permanent Lockup).

Робочу реалізацію драйвера з конфігурацією регістрів розібрано у [проєкті контролера анти-темпер захисту на C/C++](root:embedded/shcho-prystrii-znaie-pro-vas/proj-zeroization-controller.md).

## 5. Повний модуль анти-темпер моніторингу та захищеного сховища на C/C++

Нижче наведено промисловий модуль захищеного буфера та контролера самоочищення. Модуль містить захист від компіляторних оптимізацій dead-store, механізм аварійного затирання та ідіоматичну обгортку C++20 на основі RAII.

```c
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

#define SECURE_KEY_BYTES        32U
#define FLASH_SECTOR_SIZE_BYTES 4096U

typedef enum {
    TAMPER_STATUS_SAFE = 0,
    TAMPER_STATUS_TRIGGERED,
    TAMPER_STATUS_ZEROIZED
} TamperStatus;

typedef struct {
    uint8_t master_key[SECURE_KEY_BYTES];
    TamperStatus status;
    volatile bool is_compromised;
} SecureVault;

// Низькорівневі апаратні виклики до периферії МК
extern void bsp_wipe_backup_registers(void);
extern void bsp_flash_erase_sector(uint32_t address);
extern void bsp_efuse_burn_permanent_lock(void);
extern void bsp_system_hard_reset(void);

/**
 * Гарантоване затирання пам'яті, захищене від dead store elimination.
 */
void secure_zeroize_memory(void *dest, size_t len) {
    if (dest == NULL || len == 0) {
        return;
    }
    volatile uint8_t *vptr = (volatile uint8_t *)dest;
    while (len--) {
        *vptr++ = 0x00U;
    }
    // Інструкційний бар'єр: компілятор не має права переставляти операції
    __asm__ __volatile__("" : : "r"(dest) : "memory");
}

void secure_vault_init(SecureVault *vault) {
    if (!vault) return;
    vault->status = TAMPER_STATUS_SAFE;
    vault->is_compromised = false;
    secure_zeroize_memory(vault->master_key, SECURE_KEY_BYTES);
}

bool secure_vault_set_key(SecureVault *vault, const uint8_t *key_data, size_t key_len) {
    if (!vault || !key_data || key_len != SECURE_KEY_BYTES) {
        return false;
    }
    if (vault->status != TAMPER_STATUS_SAFE || vault->is_compromised) {
        return false;
    }

    for (size_t i = 0; i < SECURE_KEY_BYTES; ++i) {
        vault->master_key[i] = key_data[i];
    }
    return true;
}

/**
 * Асинхронний обробник переривання Tamper ISR.
 * Виконується з нульовим пріоритетом (найвищий у системі).
 */
void Tamper_Hardware_IRQHandler(SecureVault *vault) {
    if (!vault) return;

    // 1. Апаратне занулення Backup SRAM за один такт
    bsp_wipe_backup_registers();

    // 2. Гарантоване занулення ключів у RAM ядра
    secure_zeroize_memory(vault->master_key, SECURE_KEY_BYTES);
    vault->status = TAMPER_STATUS_TRIGGERED;
    vault->is_compromised = true;

    // 3. Затирання секторів Flash-пам'яті
    for (uint32_t addr = 0x08040000U; addr < 0x08080000U; addr += FLASH_SECTOR_SIZE_BYTES) {
        bsp_flash_erase_sector(addr);
    }

    // 4. Незворотне спалювання eFuse
    bsp_efuse_burn_permanent_lock();

    // 5. Перезапуск у безпечний стан блокування
    bsp_system_hard_reset();
}
```

```cpp
#include <cstdint>
#include <cstddef>
#include <span>
#include <atomic>
#include <concepts>
#include <utility>

namespace security {

enum class VaultStatus : uint8_t {
    Safe = 0,
    Triggered,
    Zeroized
};

template <size_t KeySize>
class alignas(uint32_t) ScopedSecureBuffer {
public:
    constexpr ScopedSecureBuffer() noexcept {
        zeroize();
    }

    explicit ScopedSecureBuffer(std::span<const uint8_t, KeySize> src) noexcept {
        load(src);
    }

    ~ScopedSecureBuffer() noexcept {
        zeroize();
    }

    ScopedSecureBuffer(const ScopedSecureBuffer&) = delete;
    ScopedSecureBuffer& operator=(const ScopedSecureBuffer&) = delete;

    ScopedSecureBuffer(ScopedSecureBuffer&& other) noexcept {
        load(std::span<const uint8_t, KeySize>(other.storage_, KeySize));
        other.zeroize();
    }

    ScopedSecureBuffer& operator=(ScopedSecureBuffer&& other) noexcept {
        if (this != &other) {
            zeroize();
            load(std::span<const uint8_t, KeySize>(other.storage_, KeySize));
            other.zeroize();
        }
        return *this;
    }

    void load(std::span<const uint8_t, KeySize> src) noexcept {
        zeroize();
        for (size_t i = 0; i < KeySize; ++i) {
            storage_[i] = src[i];
        }
    }

    void zeroize() noexcept {
        volatile uint8_t* ptr = storage_;
        for (size_t i = 0; i < KeySize; ++i) {
            ptr[i] = 0x00U;
        }
        std::atomic_signal_fence(std::memory_order_seq_cst);
    }

    [[nodiscard]] std::span<const uint8_t, KeySize> span() const noexcept {
        return std::span<const uint8_t, KeySize>(storage_, KeySize);
    }

private:
    uint8_t storage_[KeySize]{};
};

template <typename PlatformHw>
class AntiTamperController {
public:
    static constexpr size_t KeyLength = 32;

    explicit AntiTamperController(PlatformHw& hw) noexcept
        : hw_(hw), status_(VaultStatus::Safe), breached_(false) {}

    ~AntiTamperController() noexcept {
        triggerEmergencyZeroize();
    }

    [[nodiscard]] bool setMasterKey(std::span<const uint8_t, KeyLength> key) noexcept {
        if (breached_.load(std::memory_order_relaxed) || status_ != VaultStatus::Safe) {
            return false;
        }
        keyBuffer_.load(key);
        return true;
    }

    void onTamperInterrupt() noexcept {
        breached_.store(true, std::memory_order_seq_cst);
        triggerEmergencyZeroize();
    }

    void triggerEmergencyZeroize() noexcept {
        // 1. Апаратне скидання регістрів
        hw_.wipeBackupRegisters();

        // 2. Гарантоване затирання RAM за принципом RAII
        keyBuffer_.zeroize();
        status_ = VaultStatus::Zeroized;

        // 3. Затирання Flash
        hw_.eraseSensitiveFlashSectors();

        // 4. Фіксація eFuse та скидання
        hw_.burnPermanentSecurityLock();
        hw_.hardReset();
    }

    [[nodiscard]] VaultStatus getStatus() const noexcept { return status_; }

private:
    PlatformHw& hw_;
    ScopedSecureBuffer<KeyLength> keyBuffer_{};
    VaultStatus status_;
    std::atomic<bool> breached_{false};
};

} // namespace security
```

## 6. Інженерний чекліст захисту конфіденційних даних у виробі

Для побудови надійного польового пристрою перевірте схему та прошивку за такими правилами:

1. **Повна інвентаризація та шифрування розділів Flash (Crypto-Shredding).** Усі конфіденційні дані (паролі, сертифікати, GNSS-треки, NVS-сховища) повинні зберігатися у зашифрованих розділах Flash. Майстер-ключ шифрування повинен зберігатися виключно в енергозалежній Backup SRAM під резервним живленням `VBAT`.
2. **Ніколи не покладатися на логічне видалення файлів.** Пам'ятайте, що функції `unlink()` або `nvs_erase_key()` змінюють лише біти заголовків. Для фізичного видалення застосовуйте команду секторного стирання `Sector Erase` або робіть дамп нерозшифровним через скидання мастер-ключа.
3. **Апаратна детекція розкриття корпусу.** Оснащуйте корпус позолоченими мікроперемикачами зі струмовою петлею, активною захисною сіткою на кришці та фотодіодом темної порожнини, підключеними до домену `TAMP` мікроконтролера.
4. **Захист пам'яті від оптимізацій компілятора.** Ніколи не використовуйте стандартний `memset()` для очищення ключів у RAM перед виходом із функцій. Застосовуйте `volatile`-покажчики, бар'єри пам'яті або спеціалізовані RAII-класи із зануленням у деструкторі.
5. **Незворотне блокування eFuse.** У релізній версії пристрою спалюйте eFuse-біти постійного вимкнення інтерфейсів JTAG/SWD та захисту від зчитування пам'яті (RDP Level 2 у STM32, Security Level 3 у ESP32).
