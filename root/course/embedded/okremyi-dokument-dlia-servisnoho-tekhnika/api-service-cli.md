# 📋 Специфікація діагностичного інтерфейсу та команд сервісного CLI

Діагностичний інтерфейс командного рядка (англ. *Command Line Interface*, CLI) сервісного режиму надає інженеру прямий стандартизований доступ до внутрішнього стану прошивки, апаратних регістрів, первинних вимірювань сенсорів та механізмів примусового керування виконавчими вузлами вбудованої системи. Цей протокол є технічним контрактом між сервісним стендом або терміналом техніка та цільовим мікроконтролером. Він забезпечує повноцінну діагностику відмови без необхідності підключення інвазивного апаратного відлагоджувача JTAG/SWD.

---

## 1. Фізичний рівень, електричні параметри та швидкість каналу

Сервісна консоль підключається до виділеного апаратного порту UART мікроконтролера або емульованого віртуального COM-порту (USB CDC / USB Serial JTAG). Інтерфейс функціонує в режимі повного дуплексу (Full Duplex), де прийом та передача байтів відбуваються незалежними сигнальними лініями `RX` і `TX`.

| Параметр каналу зв'язку | Значення за замовчуванням | Допустимі відхилення | Примітки та вимоги |
| :--- | :--- | :--- | :--- |
| **Швидкість (Baud Rate)** | `115200 bps` | `±1.5%` | Опційно: `921600 bps` для швидкого зливання дампів Flash |
| **Формат кадру** | `8N1` | Фіксовано | 8 бітів даних, без біта парності (None), 1 стоп-біт |
| **Логічні рівні** | `3.3 V LVCMOS` | `0.0 V .. 3.3 V` | **Суворо заборонено** пряме підключення RS-232 (`±12 V`) |
| **Керування потоком** | Відсутнє (None) | XON/XOFF опційно | Апаратні лінії RTS/CTS за наявності сервісного роз'єму |
| **Символ закінчення рядка** | `\r\n` (CR+LF, `0x0D 0x0A`) | `\n` (LF) | Термінал зобов'язаний відправляти пару CR+LF |
| **Символ підказки (Prompt)** | `SRV> ` | `BOOT> ` (DFU) | З'являється після готовності процесора приймати команду |

Швидкість 115200 бодів обрана як базовий промисловий компроміс між стійкістю до завад на довгих сервісних кабелях (до 3 метрів без екранування) та достатньою пропускною здатністю для виведення текстових таблиць у реальному часі. Для зняття повних двійкових дампів зовнішньої Flash-пам'яті об'ємом від 4 МБ швидкість каналу може програмно перемикатися на 921600 бодів за допомогою команди `sys baud 921600`.

## 2. Формат команд, синтаксис та кадрування

Протокол підтримує два взаємозамінні режими передачі: текстовий людиночитаний командний рядок (ASCII CLI) для безпосередньої роботи техніка через термінальні програми (PuTTY, Minicom, Serial Monitor) та бінарні кадри з контрольною сумою CRC-16 для автоматизованих заводських стендів.

### Текстовий синтаксис ASCII

Кожна команда складається з назви функціональної підсистеми, назви виконуваної дії, обов'язкових позиційних параметрів та опційних ключів конфігурації у форматі `--ключ=значення`. Між аргументами використовується один або кілька пробільних символів:

```
<підсистема> <дія> [аргумент_1] [аргумент_2] [--флаг]
```

Регістр символів команд є нечутливим (команди нормалізуються до нижнього регістру перед парсингом), однак рядкові аргументи паролів та шістнадцяткові ключі чутливі до регістру.

Приклад виклику команди читання датчика:
```
diag sensor read --id=0x01 --raw
```

Формат стандартної успішної відповіді пристрою:
```
+OK: <результат або корисне навантаження>
```

Формат повідомлення про помилку з кодом несправності:
```
-ERR: <код_помилки_hex> <текстовий_опис_причини>
```

### Бінарний діагностичний кадр

Для автоматизованих комплексів вихідного контролю текстовий парсинг є надлишковим. Бінарний протокол використовує структуру фіксованого кадру з байт-стафінгом та перевіркою цілісності:

| Поле кадру | Розмір (байти) | Опис та призначення поля |
| :--- | :--- | :--- |
| `SOF` | 1 | Початок кадру (Start of Frame): фіксований байт `0xAA` |
| `SEQ` | 1 | Порядковий номер пакета (`0x00` .. `0xFF`) для відстеження втрат |
| `CMD_ID` | 2 | 16-бітний ідентифікатор команди (Little-Endian формат) |
| `LEN` | 2 | Довжина корисного навантаження `PAYLOAD` (0 .. 1024 байти) |
| `PAYLOAD` | `LEN` | Бінарні байти параметрів команди або тіла відповіді |
| `CRC16` | 2 | Контрольна сума CRC-16/CCITT (поліном `0x1021`, ініціалізація `0xFFFF`) |
| `EOF` | 1 | Кінець кадру (End of Frame): фіксований байт `0x55` |

Якщо всередині тіла `PAYLOAD` або поля `CRC16` зустрічається байт, що збігається з маркерами `SOF` (`0xAA`), `EOF` (`0x55`) або символом екранування `ESC` (`0x7D`), передавач замінює його парою байтів: `0x7D (Байт XOR 0x20)`. Приймач на боці мікроконтролера автоматично виконує зворотне розгортання кадру перед обчисленням контрольної суми.

## 3. Протокол автентифікації та захист від несанкціонованого доступу

Для виключення випадкового пошкодження калібрувальних констант користувачем або зловмисного втручання в алгоритми захисту застосовується дворівнева схема криптографічної перевірки прав доступу на основі запиту та відповіді (англ. *Challenge-Response Authentication*):

1. **Ініціалізація запиту:** Сервісний технік або автоматизований стенд надсилає текстову команду `auth challenge`.
2. **Генерація одноразового числа (Nonce):** Апаратний генератор випадкових чисел мікроконтролера (TRNG) створює 64-бітне псевдовипадкове значення `Nonce`, яке повертається у відкритому вигляді: `+OK: CHALLENGE 0x4F8A12B9C0DE3311`. Одночасно запускається апаратний таймер очікування відповіді на 30 секунд.
3. **Обчислення підпису:** На захищеному комп'ютері техніка спеціалізована сервісна утиліта обчислює підпис `HMAC-SHA256(Nonce, Master_Service_Key)`. Головний ключ `Master_Service_Key` зберігається в захищеному модулі TPM або на смарт-картці техніка й ніколи не передається лінією зв'язку у відкритому вигляді.
4. **Верифікація підпису:** Технік відправляє результат командного рядка: `auth verify 0x8E5A91...`.
5. **Активація сесії:** Вбудований криптографічний рушій мікроконтролера перевіряє отриманий геш. У разі успішного збігу внутрішній скінченний автомат перемикається в стан `STATE_SERVICE_UNLOCKED`, знімає програмні блокування з силових приводів та запускає таймер неактивності сесії тривалістю 900 секунд (15 хвилин). Будь-яка валідна команда скидає цей таймер. Якщо протягом 15 хвилин команд не надходить, сесія автоматично закривається зі скиданням прав до рівня `STATE_LOCKED`.

## 4. Реєстр системних та діагностичних команд

### Група системної ідентифікації та базового стану (`sys`)

Ця група команд дозволяє ідентифікувати точну апаратну конфігурацію зібраного пристрою, перевірити цілісність прошивки та загальний тепловий стан кристала.

| Команда | Параметри | Опис функціоналу | Приклад повертаної відповіді |
| :--- | :--- | :--- | :--- |
| `sys info` | Немає | Виводить заводський P/N, S/N, ревізію плати, версію FW та час напрацювання | `+OK: SN=GW500-2026-00412 HW=REV_C FW=v2.4.1 UPTIME=418293s` |
| `sys health` | Немає | Загальний статус напруг, температури кристала та стану динамічної пам'яті | `+OK: VCC=3.31V VBAT=3.85V T_MCU=42.1C HEAP_FREE=48120B` |
| `sys reboot` | `[dfu/norm]` | Перезавантажує пристрій у робочий режим або в системний DFU-завантажувач | `+OK: REBOOTING TO DFU...` |
| `sys lock` | Немає | Примусово завершує сервісну сесію та скидає права авторизації | `+OK: SERVICE LOCKED` |

### Група апаратного самотестування та сканування периферії (`diag test`)

Команди групи `diag test` реалізують вбудоване діагностичне тестування (BIST) для перевірки цілісності фізичних шин даних і блоків оперативної пам'яті.

| Команда | Параметри | Опис функціоналу | Приклад повертаної відповіді |
| :--- | :--- | :--- | :--- |
| `diag selftest` | `[all/pwr/mem/bus]` | Запуск комплексного BIST-тесту: шини I2C/SPI, пам'ять RAM та CRC Flash | `+OK: BIST PASSED (I2C:OK, SPI:OK, RAM_MARCH_C:OK, FLASH_CRC:OK)` |
| `diag bus scan` | `[i2c1/i2c2/spi]` | Сканування шини та виведення 7-бітних адрес виявлених пристроїв | `+OK: I2C1 ADDRS: 0x38(SHT40), 0x68(DS3231), 0x50(EEPROM)` |
| `diag ram test` | `--size=KB` | Недеструктивне тестування внутрішньої пам'яті алгоритмом March-C | `+OK: RAM 128KB TESTED 0 ERRORS` |

### Група аналогових вимірювань та сенсорних каналів (`diag sensor`)

Команди прямого опитування датчиків дозволяють інженеру відокремити фізичну відмову чутливого напівпровідникового елемента або вимірювального підсилювача від помилки програмних калібрувальних коефіцієнтів у пам'яті.

| Команда | Параметри | Опис функціоналу | Приклад повертаної відповіді |
| :--- | :--- | :--- | :--- |
| `diag adc raw` | `--ch=<0..7>` | Зчитування прямого 12/16-бітного коду АЦП без калібрувальних поправок | `+OK: CH=2 RAW=0x0B42 (V_CALC=2.321V)` |
| `diag sensor dump` | Немає | Виведення повної таблиці сенсорів із зазначенням статусу валідності | `+OK: S1=24.5C(VALID), S2=1.013BAR(VALID), S3=OPEN_CIRCUIT(FAULT)` |
| `diag sensor calib` | `<id> <ref_val>` | Запис нової калібрувальної константи в захищену область пам'яті NVS | `+OK: SENSOR 0x01 CALIBRATED OFFSET=0.04 GAIN=1.002` |

### Група безпечного ручного керування навантаженнями (`diag act`)

Під час перевірки реле, електромагнітних клапанів, вентиляторів охолодження та насосів сервісний рушій застосовує жорсткі обмеження тривалості увімкнення. Технік зобов'язаний явно вказати час активності каналу в секундах. Якщо термінал від'єднається або програма зависне, внутрішній апаратний таймер примусово знеструмить силовий вихід.

:::tabs
```c
/* Структура безпечного керування навантаженням у сервісному режимі */
#include <stdint.h>
#include <stdbool.h>

typedef enum {
    ACT_RELAY_1      = 0x01,
    ACT_RELAY_2      = 0x02,
    ACT_VALVE_PWM    = 0x03,
    ACT_FAN_OUT      = 0x04
} act_channel_t;

typedef struct {
    act_channel_t channel;
    uint16_t      duration_sec;  /* Максимальний тайм-аут увімкнення (1..60 с) */
    uint16_t      pwm_permille;  /* ШІМ: 0..1000 (0.0% .. 100.0%) */
    bool          force_override;/* Ігнорування аварійних сенсорів (потребує прав інженера) */
} act_command_t;

/* Функція виконання сервісної команди: автоматично знеструмлює канал при завершенні тайм-ауту */
int srv_actuate_channel(const act_command_t *cmd);
```
```cpp
/* Об'єктний інтерфейс безпечного сервісного керування периферією */
#include <cstdint>
#include <chrono>
#include <expected>
#include <span>

enum class ActChannel : uint8_t {
    Relay1   = 0x01,
    Relay2   = 0x02,
    ValvePwm = 0x03,
    FanOut   = 0x04
};

struct ActCommand {
    ActChannel channel;
    std::chrono::seconds duration{5}; /* Захисний тайм-аут за замовчуванням 5 с */
    uint16_t pwmPermille{1000};       /* 1000 = 100% заповнення */
    bool forceOverride{false};
};

enum class ActError : uint16_t {
    TimeoutExceeded = 0x4001,
    ThermalLockout  = 0x4002,
    InvalidChannel  = 0x4003,
    SafetyInterlock = 0x4004
};

class ServiceActuatorController {
public:
    static std::expected<void, ActError> execute(const ActCommand& cmd) noexcept;
    static void emergencyAllOff() noexcept;
};
```

## 5. Діагностичні коди несправностей (DTC)

Кожен зареєстрований збій системи кодується стандартизованим 16-бітним числом DTC (англ. *Diagnostic Trouble Code*). Структура коду розбита на три бітові зони для швидкої фільтрації в логах:

```
+---------------------------+---------------------------+---------------------------------------+
| Біти [15..12]: Підсистема | Біти [11..8]: Критичність | Біти [7..0]: Унікальний номер помилки |
+---------------------------+---------------------------+---------------------------------------+
```

1. **Клас підсистеми (4 біти):** Визначає апаратний домен виникнення несправності (`0x1` — Живлення, `0x2` — Сенсори, `0x3` — Зв'язок, `0x4` — Приводи, `0x5` — Пам'ять та ядро).
2. **Рівень критичності (4 біти):** `0x1` — Інформаційне попередження (Warning), `0x2` — Порушення метрологічної точності (Degraded), `0x3` — Критична відмова вузла з переходом у безпечний стан (Critical Fault), `0x4` — Фатальна апаратна поламка з повним блокуванням (Fatal Emergency).
3. **Ідентифікатор збою (8 бітів):** Конкретна причина поламки згідно з інженерною специфікацією виробу.

| Префікс | Код підсистеми | Найменування вузла | Приклад коду DTC | Опис фізичної першопричини |
| :--- | :--- | :--- | :--- | :--- |
| `PWR` | `0x1` | Шини живлення | `0x1201` | Знижена напруга на шині 3.3V (Under-Voltage на TP_3V3) |
| `SEN` | `0x2` | Сенсори та АЦП | `0x2304` | Обрив сигнальної лінії термодатчика (Open Circuit Fault) |
| `COM` | `0x3` | Шини CAN/RS-485 | `0x3102` | Відсутність термінації CAN (стан Bus-Off контролера) |
| `ACT` | `0x4` | Силові ключі й реле | `0x4408` | Спрацювання апаратного захисту за струмом (Over-Current) |
| `MEM` | `0x5` | Пам'ять та NVS | `0x5203` | Помилка контрольної суми CRC калібрувального сектору |

## 6. Зчитування, інтерпретація та експорт аварійних дампів (Crash Log)

Під час виникнення критичного апаратного винятку мікроконтролера (наприклад, HardFault, MemoryManagement Fault або BusFault на процесорах ARM Cortex-M) обробник аварії виконує миттєвий знімок регістрів процесора та верхівки системного стека, зберігаючи їх у виділеній зарезервованій області NOR Flash або батарейного SRAM:

Команда експорту аварійного журналу через сервісну консоль:
```
diag log crash --format=hex
```

Текстовий дамп виводиться у стандартизованому блоковому форматі, що містить значення лічильника команд `PC` (Program Counter), регістра зв'язку `LR` (Link Register), покажчика стека `SP`, регістрів причини збою `CFSR/HFSR` та 64 байти вмісту пам'яті стека:

```
--- CRASH LOG BEGIN ---
DTC: 0x5101 (HARDFAULT_UNALIGNED_ACCESS)
PC:  0x080041F2 (main.c:184)
LR:  0x080039A8
SP:  0x20007FC0
R0:  0x00000000  R1: 0x20001004  R2: 0x00000020  R3: 0xE000ED28
CFSR: 0x00010000 (UNALIGNED_TRAP)
HFSR: 0x40000000 (FORCED)
STACK DUMP (64 bytes):
20007FC0: 00000001 080012A0 20001200 08004120
20007FD0: 00000000 00000000 20000400 08000104
UPTIME AT FAULT: 81402 ms
CRC32: 0xFA4B9201
--- CRASH LOG END ---
```

Отриманий текстовий блок копіюється у звіт про дефектацію. За допомогою утиліти командного рядка `addr2line` інженер співвідносить шістнадцяткову адресу `PC = 0x080041F2` з точним файлом і рядком вихідного коду програми в символьному ELF-файлі збірки, точно визначаючи програмний збій, що передував зупинці пристрою.
