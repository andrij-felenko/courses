# ⚙️ Автоматизований стендовий декодер та валідатор готовності до зльоту

Перед першим польотом інженер повинен однозначно переконатися, що польотний стек готовий до роботи, відсутні приховані блокування армінгу, а реакція моторів на ручний нахил є від'ємною (компенсаційною). Цей проєкт містить практичну реалізацію автономної стендової утиліти мовами C та C++, яка отримує бітові маски телеметрії польотного контролера (протоколи MSP та MAVLink), виконує побітове декодування активних прапорців блокування та автоматично генерує інженерний діагностичний звіт з рекомендаціями для очищення кожного прапорця.

---

## 1. Архітектура стендового діагноста та протокольний тракт

Стендовий діагностичний модуль призначений для інтеграції в автоматизовані тестові стенди лабораторій або як портативна консольна утиліта на комп'ютері розробника.

### Приймання та розбір телеметричного кадру MSP

У прошивках Betaflight зв'язок з конфігураційними інструментами здійснюється за протоколом MultiWii Serial Protocol (MSP v1 та v2). Кадр запиту статусу має вигляд бінарного пакета:

```
[Запит MSP_STATUS (ID = 101)]:
  '$' 'M' '<' [len=0] [cmd=101] [crc]
  -> 0x24 0x4D 0x3C 0x00 0x65 0x65
```

У відповідь польотний контролер повертає кадр даних `MSP_STATUS`, де після полів тривалості циклу (`cycleTime`), лічильника помилок I2C та бітової маски сенсорів передається 32-бітне беззнакове ціле поле `armingDisableFlags`:

```
[Відповідь MSP_STATUS]:
  '$' 'M' '>' [len] [cmd=101] [cycleTime: 2B] [i2cErrors: 2B] [sensors: 2B]
  [mode: 4B] [profile: 1B] [armingDisableFlags: 4B (Little-Endian)] [crc]
```

Діагностична утиліта виділяє молодші 4 байти поля `armingDisableFlags`, контролює контрольний байт XOR CRC кадру, транслює двійкові розряди у символічні ідентифікатори та проводить перевірку логіки зворотного зв'язку.

### Декодування телеметрії MAVLink (SYS_STATUS та STATUSTEXT)

Для платформ на базі ArduPilot та PX4 стендовий діагност слухає потік MAVLink-пакетів через віртуальний COM-порт UART/USB. Основними джерелами діагностичних даних є три повідомлення:

1. **`HEARTBEAT` (ID = 0)**: поле `base_mode` містить прапорець `MAV_MODE_FLAG_SAFETY_ARMED` (біт 7). Якщо польотний контролер відхиляє команду переходу в Armed, стан прапорця залишається нульовим.
2. **`SYS_STATUS` (ID = 1)**: містить три 32-бітні маски підсистем:
   - `onboard_control_sensors_present`: бітова маска фізично присутніх на борту датчиків (гіроскоп, акселерометр, компас, барометр, GPS);
   - `onboard_control_sensors_enabled`: бітова маска сенсорів, які активовані в конфігурації;
   - `onboard_control_sensors_health`: бітова маска справності сенсорів. Якщо сенсор активований у `sensors_enabled`, але його біт у `sensors_health` скинутий у нуль — це однозначно свідчить про апаратну відмову або зависання шини I2C/SPI.
3. **`STATUSTEXT` (ID = 253)**: текстовий рядок, який передається ядром ArduPilot при відмові армінгу (наприклад, `PreArm: Gyros inconsistent`). Утиліта парсить текстовий буфер і зіставляє його з базою знань типових несправностей.

### Потокова обробка та кільцевий буфер зв'язку

Під час отримання сирого бінарного потоку через UART/USB можливі спотворення та розриви пакетів через переривання операційної системи. Стендовий парсер реалізує потоковий автомат скінченних станів (FSM):

- Стан 0 (`WAIT_MAGIC`): очікування заголовка `$M<` або стартового байта MAVLink v2 `0xFD`.
- Стан 1 (`READ_HEADER`): зчитування довжини корисного навантаження та коду команди.
- Стан 2 (`READ_PAYLOAD`): накопичення байтів тіла повідомлення в кільцевий буфер.
- Стан 3 (`VERIFY_CRC`): перевірка контрольної суми. Лише при успішній верифікації CRC розпакована бітова маска передається в аналітичний модуль.

### Математичний алгоритм перевірки знака зворотного зв'язку (Negative Feedback Validator)

Для програмної верифікації правильності реакції контуру стабілізації утиліта порівнює вектори кутової швидкості з гіроскопа `ω = (ω_x, ω_y, ω_z)` та відповідні диференціальні команди мікшера двигунів `Δu = (u_1, u_2, u_3, u_4)`.

Для квадрокоптера схеми Quad-X з нумерацією моторів 1 (RR), 2 (FR), 3 (RL), 4 (FL) диференціальний момент крену `ΔM_roll` обчислюється як:

```
ΔM_roll = (u_2 + u_1) - (u_4 + u_3)
```

де `(u_2 + u_1)` — сумарна тяга моторів правого борту, а `(u_4 + u_3)` — лівого борту.

Критерій правильного (від'ємного) зворотного зв'язку: при примусовому нахилі праворуч (`ω_roll > 0`) контур стабілізації зобов'язаний сформувати компенсаційний момент вліво, тобто збільшити тягу правих моторів:

```
ΔM_roll > 0  при  ω_roll > +ω_threshold
ΔM_roll < 0  при  ω_roll < -ω_threshold
```

Якщо добуток `ω_roll · ΔM_roll < 0`, у системі діє додатний зворотний зв'язок (Positive Feedback), що сигналізує про перевернуту вісь гіроскопа або переплутані канали моторів. Поріг `ω_threshold = 5.0 °/с` відсікає власний шум сенсора IMU у стані спокою та випадкове мікротремтіння рук оператора під час утримання рами.

/* Результати стендового аналізу */
typedef struct {
    uint32_t raw_mask;
    uint8_t active_count;
    bool is_arm_allowed;
} bench_diag_result_t;

/* Функція аналізу бітової маски */
bench_diag_result_t bench_decode_arming_mask(uint32_t mask) {
    bench_diag_result_t res;
    res.raw_mask = mask;
    res.active_count = 0;
    res.is_arm_allowed = (mask == 0);

    for (uint8_t i = 0; i < MAX_DIAGNOSTIC_ITEMS; ++i) {
        if ((mask & (1U << BENCH_FLAGS[i].bit_index)) != 0) {
            res.active_count++;
        }
    }
    return res;
}

/* Друк інженерного звіту */
void bench_print_report(const bench_diag_result_t *diag) {
    printf("\n=======================================================\n");
    printf("     СТЕНДОВИЙ ЗВІТ ГОТОВНОСТІ ДО АРМІНГУ (PRE-ARM)    \n");
    printf("=======================================================\n");
    printf("Бітова маска прапорців: 0x%08X\n", diag->raw_mask);

    if (diag->is_arm_allowed) {
        printf("СТАТУС: [ УСПІХ ] Усі блокування знято. Армінг дозволено.\n");
    } else {

                printf("      ДІЯ: %s\n", BENCH_FLAGS[i].action_required);
            }

}

/* Перевірка знака зворотного зв'язку PID (Negative Feedback Test) */
bool bench_verify_pid_negative_feedback(float gyro_rate_dps, float delta_motor_throttle) {
    if (gyro_rate_dps > NOISE_THRESHOLD_DPS && delta_motor_throttle > 0.01f) {

    if (gyro_rate_dps < -NOISE_THRESHOLD_DPS && delta_motor_throttle < -0.01f) {
        return true;
    }
    return false;
}

## 3. Зразок стендового тестування та інтеграція в конвеєр перевірки

Під час підключення польотного контролера до випробувального стенда тестовий сценарій автоматично виконує опитування та зчитування поточного стану прапорців за трьома послідовними контрольними точками:

1. **Контрольна точка 1 (Холодний старт від USB)**:
   - Перевіряється наявність обов'язкових захисних блокувань `MSP`, `FAILSAFE`, `THROTTLE`.
   - Контролюється повна відсутність апаратних відмов сенсорів `NO_GYRO` або непройденого калібрування `ACC_CAL`.
2. **Контрольна точка 2 (Підключення батареї через SmokeStopper)**:
   - Перевіряється ініціалізація симетричного живлення 4-in-1 ESC.
   - Знімається прапорець `RPMFILTER` після успішного встановлення двостороннього зв'язку DShot RPM telemetry.
3. **Контрольна точка 3 (Увімкнення пульта керування)**:
   - Фіксується зняття прапорців `FAILSAFE` та `RX_FAILSAFE`.
   - Відпрацьовується 1-секундний інтервал захисту `BAD_RX_RECOVERY`.
   - Контролер досягає стану повної готовності з нульовою маскою `0x00000000`.

### Приклад виконання та аналіз виводу

При підключенні польотного контролера лише через USB-кабель без увімкненого пульта радіокерування та з відкритою вкладкою CLI, функція `bench_decode_arming_mask(0x00088062)` формує наступний вивід:

```text
=======================================================
     СТЕНДОВИЙ ЗВІТ ГОТОВНОСТІ ДО АРМІНГУ (PRE-ARM)    
=======================================================
Бітова маска прапорців: 0x00088062
СТАТУС: [ ЗАБЛОКОВАНО ] Виявлено активних перешкод: 5
-------------------------------------------------------
Деталізація блокувань:
  [!] Біт  1: FAILSAFE         | Активний аварійний режим Failsafe
      ДІЯ: Увімкнути радіопульт, перевірити живлення RX
  [!] Біт  5: THROTTLE         | Стік газу перевищує безпечний нуль (min_check)
      ДІЯ: Опустити стік газу в крайнє нижнє положення
  [!] Біт  6: CLI              | Контролер утримується в режимі CLI термінала
      ДІЯ: Ввести команду exit або закрити термінал
  [!] Біт 15: MSP              | USB-конфігуратор утримує монопольний зв'язок
      ДІЯ: Від'єднатися від конфігуратора
  [!] Біт 19: RPMFILTER        | Відсутній зв'язок двостороннього DShot RPM
      ДІЯ: Подати живлення на ESC від силового акумулятора
=======================================================
```

Після виконання запропонованих дій повторний виклик `bench_decode_arming_mask(0x00000000)` повертає статус готовності:

```text
=======================================================
     СТЕНДОВИЙ ЗВІТ ГОТОВНОСТІ ДО АРМІНГУ (PRE-ARM)    
=======================================================
Бітова маска прапорців: 0x00000000
СТАТУС: [ УСПІХ ] Усі блокування знято. Армінг дозволено.
=======================================================
```

Це дає інженеру документальне підтвердження того, що всі бортові підсистеми функціонують штатно, і дозволяє безпечно перейти до перевірки напрямків обертання двигунів на холостому ході.
