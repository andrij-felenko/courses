# ⚙️ Одна плата, дві шини: спільна обгортка пристрою

**Задача.** На платі живуть обидві шини: давачі сидять на [I2C](topic:communications/i2c-bus), а дисплей і SD-картка — на [SPI](topic:communications/spi-bus). Кожна шина адресує пристрій по-своєму: I2C називає його семибітною адресою в кадрі, SPI опускає окрему лінію вибору кристала (CS). Якщо протягти цю різницю крізь увесь код, верхні шари обростуть розгалуженнями «якщо це I2C, то…, а якщо SPI, то…». Треба зробити так, щоб драйвер давача й драйвер флешу зверталися до «свого» пристрою **однаково** — читали й писали регістри, не знаючи, на якій шині той пристрій насправді висить. Усе на реальному C, без псевдокоду.

**Ідея.** Обидві шини, попри різну механіку, дають драйверу той самий набір дій: вибрати пристрій, обміняти з ним байти, відпустити. Відмінність — лише в тому, **як** виконати «вибрати» і «обміняти»: I2C кладе адресу в кадр і квитує кожен байт, SPI смикає CS і жене повний дуплекс. Якщо сховати цю механіку за **одним описом пристрою** — структурою, що каже «ось як саме говорити з цим чіпом», — то весь код вище працюватиме з пристроєм, а не з шиною. Це той самий хід, що й драйвери пристроїв в операційній системі: верх знає інтерфейс, низ знає залізо.

Чому це не передчасне ускладнення, а ощадливість. Без обгортки кожен драйвер, який має працювати з пристроями на обох шинах, носить у собі по гілці на кожну шину. Доки шина одна, гілок немає — але щойно на платі співіснують I2C і SPI (а це звична ситуація: давачі на одній, дисплей і пам'ять на другій), розгалуження розповзаються. Додати третю шину означає знайти **всі** ці місця й допиляти кожне; забути одне — отримати тихий збій саме там, де не глянув. Обгортка стягує всю різницю шин в одну точку: новий тип шини додається правкою двох функцій, а не ревізією всього коду. Ціна — кілька рядків структури й одне розгалуження; виграш — лінійне зростання складності замість квадратичного.

## Крок 1. Опис пристрою, що ховає шину

Заведімо тип, який тримає все потрібне, щоб дістатися до конкретного чіпа, незалежно від його шини. Поле `bus` каже, котра це шина; решта полів — параметри саме для неї (адреса для I2C, ніжка CS для SPI). Драйвер вище триматиме такий опис і передаватиме його у дві універсальні операції — читання й запис регістра.

```c
#include <stdint.h>

typedef enum { BUS_I2C, BUS_SPI } bus_kind_t;

typedef struct {
    bus_kind_t bus;
    uint8_t    i2c_addr;   // чинне для BUS_I2C: 7-бітна адреса в кадрі
    uint8_t    spi_cs;     // чинне для BUS_SPI: ніжка вибору кристала
} bus_device_t;
```

Опис пристрою свідомо малий: він не дублює налаштування шини (швидкість, режим — це робить ініціалізація плати один раз), а тримає лише те, що відрізняє **цей** чіп від сусіда на тій самій шині. Для I2C сусіди різняться адресою, для SPI — лінією CS; саме ці два поля й несе структура. Поля для «чужої» шини в кожному описі просто не задіяні — у пристрою на I2C байдуже значення `spi_cs`, і навпаки. Це маленька, але типова угода такого підходу: одна структура покриває обидва випадки, а зайве поле коштує лиш кілька байтів пам'яті, тоді як розводити два окремі типи коштувало б другої копії всього коду навколо них.

## Крок 2. Дві реалізації під одним дахом

Тепер — ключові функції «прочитати регістр» і «записати регістр». Зверху в них один підпис: дай опис пристрою, номер регістра, буфер. Усередині — розгалуження за `bus`, але воно тут **єдине на всю програму**, а не розсіяне по драйверах. Кожна гілка користується низькорівневими примітивами своєї шини (їхню механіку розібрано окремо: [обмін байтом по SPI](topic:communications/spi-bus/proj-spi-transfer.md) і [транзакція I2C](topic:communications/i2c-transaction)).

```c
// Прочитати n байтів із регістра reg пристрою dev. 0 — успіх, інакше — код помилки.
int dev_read(const bus_device_t *dev, uint8_t reg, uint8_t *buf, int n) {
    if (dev->bus == BUS_I2C) {
        return i2c_read_reg(dev->i2c_addr, reg, buf, n);   // адреса в кадрі, ACK на кожен байт
    } else {
        gpio_set(dev->spi_cs, 0);          // опустити CS — почали обмін саме з цим чіпом
        spi_transfer(reg | 0x80);          // біт «читання» у старшому розряді (звичай багатьох чіпів)
        for (int i = 0; i < n; i++) {
            buf[i] = spi_transfer(0x00);   // висуваємо порожнє, забираємо корисне
        }
        gpio_set(dev->spi_cs, 1);          // підняти CS — відпустили шину
        return 0;                          // SPI не квитує — помилку ловить рівень вище
    }
}

int dev_write(const bus_device_t *dev, uint8_t reg, uint8_t val) {
    if (dev->bus == BUS_I2C) {
        return i2c_write_reg(dev->i2c_addr, reg, val);
    } else {
        gpio_set(dev->spi_cs, 0);
        spi_transfer(reg & 0x7F);          // старший біт нуль → запис
        spi_transfer(val);
        gpio_set(dev->spi_cs, 1);
        return 0;
    }
}
```

Тут добре видно ту саму різницю, що й у статті, але вже в коді. I2C-гілка повертає чесний код помилки, бо шина квитує кожен байт і збій (немає ACK) видно одразу. SPI-гілка повертає нуль беззастережно, бо SPI не підтверджує нічого — якщо дріт відвалився, апарат цього не помітить, і цілісність доводиться перевіряти вище (контрольним числом чи звіркою сталого регістра). Це не недогляд обгортки, а чесне відображення того, що одна шина має вбудований контроль, а друга — ні.

## Крок 3. Драйвер, якому байдуже до шини

Тепер найголовніше — заради чого все робилося. Драйвер давача звертається до пристрою через `dev_read`/`dev_write` і **жодного разу** не згадує, I2C це чи SPI. Той самий код працює і для акселерометра на I2C, і для гіпотетичного давача на SPI — різниця лишається тільки в одному рядку, де пристрій описують.

```c
// Давач на I2C: різнить його адреса.
static const bus_device_t imu  = { .bus = BUS_I2C, .i2c_addr = 0x68 };
// Флеш на SPI: різнить його лінія CS.
static const bus_device_t flash = { .bus = BUS_SPI, .spi_cs = 17 };

// Звірка ID — однакова для обох, бо говорить через обгортку, а не через шину.
int check_id(const bus_device_t *dev, uint8_t who_am_i_reg, uint8_t expected) {
    uint8_t id = 0;
    if (dev_read(dev, who_am_i_reg, &id, 1) != 0) {
        return -1;                 // I2C повідомив про збій; для SPI завжди 0
    }
    return (id == expected) ? 0 : -2;
}
```

Виклик `check_id(&imu, 0x75, 0x68)` піде по I2C, а `check_id(&flash, 0x9F, /*…*/)` — по SPI, і функція про це навіть не знатиме. Саме в цьому суть: **вибір шини під пристрій зроблено один раз, у його описі**, а вся логіка вище від цього вибору відв'язана.

## Де обгортка чесно не рятує

Спокусливо думати, що тепер пристрій на SPI й пристрій на I2C повністю взаємозамінні. Це не так, і межу варто знати. Обгортка ховає **механіку доступу до регістра** — і лише її. Усе, що випливає з фізики самої шини, крізь неї не сховається.

Найперше — **швидкість**. Пакетне читання шести байтів виміру з давача на SPI на десятках мегагерц і те саме читання по I2C на 400 кілогерцах різняться на порядок за часом. Якщо верхній код опитує пристрій у жорсткому циклі керування, він мусить знати реальний бюджет часу — а він залежить від шини, хоч виклик і однаковий. Обгортка робить код **однаковим на вигляд**, але не **однаковим за швидкістю**.

Друге — **контроль помилок**, про який уже йшлося: I2C-гілка повертає чесний код, SPI-гілка завжди нуль. Це не дефект, який можна «доробити» в обгортці, а пряме відображення того, що I2C квитує кожен байт, а SPI — ні. Тож код, якому потрібна гарантія доставлення, для пристроїв на SPI муситиме будувати власну перевірку поверх обгортки.

Третє — **тонкі особливості конкретних чіпів**: розтягування такту веденим на I2C, потреба тримати CS опущеним через кілька транзакцій на SPI, нестандартний порядок біт. Такі речі живуть нижче рівня «прочитати регістр» і просочуються в драйвер хоч-не-хоч. Обгортка покриває **типовий** випадок; виняткові пристрої однаково потребують уваги до своєї шини. Правило тут просте: ховай за обгорткою спільне, але не вдавай, що спільне — це все.

## Пастки

**Спокуса проштовхнути різницю шин нагору.** Найчастіша помилка — почати писати `if (i2c) … else …` у самому драйвері давача чи, гірше, у прикладному коді. Тоді кожен новий пристрій множить розгалуження, і додати третю шину (скажімо, [UART](topic:communications/async-serial)) стає переробкою всього. Правило просте: розгалуження за шиною живе **лише** в `dev_read`/`dev_write`, більше ніде.

**Мовчазний SPI присипляє пильність.** Оскільки SPI-гілка завжди повертає нуль, легко звикнути, що «помилок не буває», і не додати перевірку цілісності для пристроїв на SPI. Для критичних даних на SPI потрібен власний контроль — повторне читання сталого регістра, контрольне число чи звірка діапазону; обгортка тут нічим не зарадить, бо самій шині немає чим підтвердити байт.

**Спільний CS у спокої.** Усі лінії CS на SPI мусять стояти високими (пристрій не вибрано), поки до пристрою не звертаються; інакше два чіпи водночас вважатимуть, що говорять із ними, і поб'ють дані на спільних лініях. Опис пристрою цього не гарантує — про підняття CS дбає ініціалізація плати й кожна операція, що чесно повертає лінію в спокій після обміну.
