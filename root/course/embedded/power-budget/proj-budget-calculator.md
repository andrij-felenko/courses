# ⚙️ Калькулятор бюджету потужності на C

У самій темі ми звели бюджет на папері й побачили головне: з однієї таблиці споживачів треба дістати **два** числа під два різні рішення — найгірший одночасний попит на джерело (за ним сайзять блок, роз'єм, батарею за піком) і середнє за цикл (за ним рахують час життя). Рахувати їх вручну на кожній зміні компонування набридає на третьому варіанті, а помилитися — легко: то струми з різних шин складуться наосліп, то хтось сайзитиме блок за середнім. Логічний наступний крок — закласти ту саму таблицю в код, який рахує обидва числа сам і відразу каже, сходиться бюджет чи ні.

Це не той самий калькулятор, що [бюджет енергії одного вузла](root:embedded/duty-cycle-current/proj-energy-budget-table.md). Той брав **один** профіль фаз у часі й давав середній струм та час життя — погляд углиб одного споживача. Тут погляд **ушир**: багато шин, багато споживачів на різних напругах, кожен зі своїм перетворювачем, і питання не «скільки протримається один вузол», а «чи витримає **джерело всіх разом** у найгіршу хвилину». Це різні зрізи, і вони доповнюють один одного: спершу цей калькулятор каже, що джерела вистачить, тоді той — на скільки вистачить заряду.

## Задача

Дано таблицю системи. Кожна **шина** (англ. *rail*, «рейка живлення») має напругу й перетворювач із якимось ККД, що живить її від спільного входу. Кожен **споживач** сидить на якійсь шині й описаний трьома числами: піковий струм, частка часу, коли він цей струм бере (робочий цикл), і ця сама шина. Дано ще стелю джерела на вході — скільки воно може дати стало.

Треба дістати три речі й нічого не наплутати дорогою:

```
1. Найгірший одночасний попит на вході джерела   → для сайзингу джерела/роз'єму
2. Середнє споживання на вході за цикл            → для часу життя батареї
3. Вердикт запасу: попит ≤ стеля × 0.8 ?          → сходиться / ні
```

Складність не в арифметиці — вона тривіальна. Складність у тому, щоб **кожне число рахувалося в правильних одиницях і на правильному боці перетворювача**, бо саме там ховаються всі чотири класичні помилки бюджету, які ми зараз і закладемо в код так, щоб їх не можна було зробити випадково.

## Ідея

Уся будова тримається на трьох фізичних фактах, кожен з яких диктує один рядок майбутнього коду.

Перший: **складати можна лише ватами, не амперами**. Ампер на 12-вольтовій шині й ампер на трьохвольтовій — це різні видатки, бо P = U × I. Тому перше, що робить код із кожним споживачем, — переводить його струм у потужність на **його** напрузі. Далі вся арифметика йде у ватах (точніше — у зручній цілій частці вата), де доданки нарешті співмірні.

Другий: **джерело платить за вхід, а не за вихід**. Між споживачем і джерелом стоїть перетворювач, і він з'їдає частину потужності в тепло. Корисні 500 мВт на виході коштують джерелу 500 / ККД на вході. Тому одразу після переведення в потужність код **відбиває її через ККД шини**: P_вх = P_вих / ККД. Забути цей крок — недолічити саме той ват, що гріє плату.

Третій: **пік і середнє — це та сама потужність, помножена на різні множники часу**. Найгірший одночасний попит бере пік споживача **як є** (множник 1: він увімкнений у ту хвилину). Середнє бере той самий пік, помножений на робочий цикл (множник «частка часу»). Один прохід таблицею набирає **обидві** суми паралельно — те саме число лягає в дві скриньки з різними вагами.

> 🔧 **Навіщо це.** Розведення «пік як є» проти «пік × цикл» — це і є той рядок коду, що рятує від двох дзеркальних помилок одразу: сайзингу джерела за середнім (тоді блок просяде в першому ж піку) і розрахунку автономності за піком (тоді час життя занизиш у десятки разів). У коді вони стають двома накопичувачами в одному циклі, і сплутати їх уже нема як.

### Одиниці: чому не ампери й вати у float

Спокуса написати все у вольтах, амперах і ватах із `double` велика — формули виглядали б як у підручнику. Але на малому МК це двічі погана ідея. По-перше, ядро без апаратного блока для дробів (а таких більшість дешевих мікроконтролерів) емулює кожну дію над `float` десятками інструкцій — дорого там, де код може крутитися в діагностиці. По-друге, дроби тягнуть похибку округлення, а нам потрібен передбачуваний результат, який можна перевірити до одиниці в тесті.

Тому беремо цілі одиниці, природні для даташита:

```
напруга  — у мілівольтах (мВ):     3300 = 3.3 В
струм    — у міліамперах (мА):      300  = 0.3 А
ККД      — у відсотках, ціле:       90   = 90 %
цикл     — у проміле (0..1000):     8    = 0.8 % часу
```

Добуток напруги на струм дає зручну одиницю потужності сам собою:

```
P[мкВт] = U[мВ] × I[мА]
       бо  (10⁻³ В) × (10⁻³ А) = 10⁻⁶ Вт = мікроват
```

Мікроват — гарний внутрішній масштаб: дрібний настільки, що навіть струм спокою в одиниці мікроампер не округлюється в нуль, і водночас не такий дрібний, щоб числа вибухали (як було б із нановатами від мВ×мкА). Ват для людини отримаємо діленням наприкінці. Розплата та сама, що завжди з цілими: проміжні добутки ростуть, тож рахуємо у 64 бітах і ділимо **в останню чергу** — про це нижче в пастках.

## Робочий код

Спершу опишемо систему двома таблицями — шин і споживачів. Споживач посилається на шину за індексом, тож одна шина обслуговує скільки завгодно споживачів, а ККД для них прописаний один раз — там, де він фізично й живе.

```c
#include <stdint.h>
#include <stddef.h>
#include <stdbool.h>

// Шина живлення: напруга й перетворювач, що її живить від спільного входу.
typedef struct {
    uint32_t mv;       // напруга шини, мВ           (3300 = 3.3 В)
    uint16_t eff_pct;  // ККД перетворювача, %       (90 = 90 %; 100 = напряму)
} rail_t;

// Споживач: на якій шині сидить, скільки бере в піку й яку частку часу.
typedef struct {
    uint8_t  rail;     // індекс у масиві шин
    uint32_t peak_ma;  // піковий струм, мА          (300 = 0.3 А)
    uint16_t duty_pm;  // робочий цикл, проміле      (1000 = завжди ON)
} load_t;
```

Тепер сам розрахунок. Один прохід таблицею споживачів набирає обидві суми; джерело й вердикт лягають у ту саму структуру результату.

```c
typedef struct {
    uint64_t worst_uw;    // найгірший одночасний попит на вході, мкВт
    uint64_t avg_uw;      // середнє за цикл на вході, мкВт
    uint64_t source_uw;   // стеля джерела, мкВт
    uint64_t headroom_uw; // робоча межа = стеля × 0.8, мкВт
    bool     fits;        // worst ≤ headroom ?
    uint16_t load_pct;    // worst як % стелі (для звіту)
} budget_t;

// rails[], loads[] — таблиці системи; nr, nl — їхні розміри.
// src_mv, src_ma   — стеля джерела на вході (напр. 5000 мВ × 500 мА для USB).
// headroom_pct     — частка стелі, у яку дозволяємо лізти (звичайно 80).
budget_t power_budget(const rail_t *rails, size_t nr,
                      const load_t *loads, size_t nl,
                      uint32_t src_mv, uint32_t src_ma,
                      uint16_t headroom_pct) {
    budget_t b = {0, 0, 0, 0, false, 0};

    for (size_t i = 0; i < nl; i++) {
        const load_t *L = &loads[i];
        if (L->rail >= nr) continue;             // захист від кривого індексу
        const rail_t *R = &rails[L->rail];
        if (R->eff_pct == 0) continue;           // ділення на нуль: пропускаємо

        // 1) потужність на ВИХОДІ шини: U[мВ] × I[мА] = P[мкВт]
        uint64_t p_out = (uint64_t)R->mv * L->peak_ma;

        // 2) відбиваємо на ВХІД через ККД: P_вх = P_вих / ККД
        //    ділимо в кінці кроку, але множник 100 беремо в 64 бітах
        uint64_t p_in = (p_out * 100u) / R->eff_pct;

        // 3) пік іде у worst-case як є; у середнє — помножений на цикл
        b.worst_uw += p_in;
        b.avg_uw   += (p_in * L->duty_pm) / 1000u;
    }

    // стеля джерела й робоча межа
    b.source_uw   = (uint64_t)src_mv * src_ma;            // мВ × мА = мкВт
    b.headroom_uw = (b.source_uw * headroom_pct) / 100u;
    b.fits        = (b.worst_uw <= b.headroom_uw);
    if (b.source_uw)
        b.load_pct = (uint16_t)((b.worst_uw * 100u) / b.source_uw);
    return b;
}
```

Функція навмисне чиста: нічого не читає з апаратури, не пише в журнал, лише бере таблиці й повертає числа. Це робить її перевірною на звичайному комп'ютері — той самий код, що крутитиметься в прошивці, ганяється юніт-тестом без жодного МК. Повертає вона структуру, а не одне число, бо бюджет — це саме набір чисел під різні рішення: `worst_uw` піде у вибір джерела, `avg_uw` — у час життя, `fits`/`load_pct` — людині у звіт «сходиться, завантаження 75 %».

Зверни увагу, як будова таблиць глушить дві помилки ще до арифметики. ККД прописаний **на шині**, а не на споживачі, — тож фізично неможливо випадково «забути ККД» для одного з десяти давачів на спільному buck'у: він один на всіх. А напруга береться теж із шини, не з вільного числа біля споживача, — тож не можна порахувати потужність давача на «5 В», коли він насправді на 3.3 В. Правильні зв'язки зашиті в структуру даних, не лишені на уважність того, хто заповнює таблицю.

### Виклик: пристрій від USB 500 мА

Зберемо ту саму систему, що рахували в темі на папері: три шини за перетворювачами, живлення від звичайного порту USB (5 В, 500 мА після узгодження — стеля 2.5 Вт), запас 80 %.

```c
void check_usb_budget(void) {
    static const rail_t rails[] = {
        { 3300, 90 },   // 0: шина 3.3 В через buck, ККД 90 %
        { 5000, 100 },  // 1: шина 5 В напряму з входу (ККД 100 %)
    };
    static const load_t loads[] = {
        { 0, 300, 1000 },  // МК + радіо в TX:  300 мА на 3.3 В, завжди в піку
        { 0,  50, 1000 },  // давачі:            50 мА на 3.3 В
        { 1, 120, 1000 },  // дисплей з підсвіткою: 120 мА на 5 В
    };

    budget_t b = power_budget(rails, 2, loads, 3,
                              5000, 500,   // джерело: USB 5 В × 500 мА
                              80);         // запас 80 %

    // Очікувано: worst ≈ 1.88 Вт, стеля 2.50 Вт, межа 2.00 Вт → fits = true, 75 %.
    ESP_LOGI("pwr", "пік %llu мкВт / межа %llu мкВт → %s (%u %% стелі)",
             b.worst_uw, b.headroom_uw, b.fits ? "OK" : "ПЕРЕВАНТАЖЕННЯ",
             b.load_pct);
}
```

Прокрутимо числа в голові, щоб звірити з папером із теми. Шина 3.3 В: (300 + 50) мА × 3.3 В = 1.155 Вт на виході, поділити на 0.90 = 1.283 Вт на вході. Шина 5 В: 120 мА × 5 В = 0.60 Вт, ККД 100 %, лишається 0.60 Вт. Разом пік на вході = 1.283 + 0.60 ≈ **1.88 Вт**. Стеля 2.50 Вт, межа 2.00 Вт — попит лягає під межу, `fits = true`, завантаження 75 %. Збігається з аркушем теми до сотих, але тепер це функція, яку прикладаєш до кожного варіанта компонування за секунди.

### Друге число: середнє для часу життя

У виклику вище кожен споживач стоїть із `duty_pm = 1000` — «завжди в піку». Це правильно для **worst-case**: саме так сайзять джерело. Але та сама таблиця з реальними робочими циклами дає **друге** число — середнє, з якого рахують батарею. Перепишемо цикли під реальність (радіо передає частку секунди на хвилину, давачі прокидаються зрідка, дисплей світиться на вимогу):

```c
static const load_t loads_real[] = {
    { 0, 300,  8 },   // радіо TX: 0.8 % часу (0.5 с на хвилину)
    { 0,  50, 50 },   // давачі:   5 % часу
    { 1, 120, 30 },   // дисплей:  3 % часу
};
```

Той самий `power_budget` тепер поверне `worst_uw` так само ≈ 1.88 Вт (пік не залежить від циклу — він про «коли все збіглося»), а от `avg_uw` впаде більш ніж на порядок: кожен пік увійде зі своєю крихітною часткою. Це і є те, про що в темі сказано «один аркуш, дві суми»: **та сама таблиця**, прочитана з множником 1, дає попит на джерело; прочитана з множником-циклом — дає попит на батарею. У коді обидва читання вже зроблені одним проходом, лишається взяти потрібне поле.

Час життя дістається з середнього вже знайомою дією — поділити заряд батареї на середній струм. Тільки середнє в нас у ватах, тож і ділити треба енергію батареї на потужність:

```c
// Час життя від батареї: енергія[мВт·год] / середня потужність[мВт].
// avg_uw у мкВт; energy_mwh у мВт·год. Переводимо узгоджено.
uint32_t life_hours(uint64_t avg_uw, uint32_t energy_mwh) {
    if (avg_uw == 0) return 0;                    // нескінченне життя
    // мВт·год / мВт = год;  avg_mw = avg_uw/1000.  Множимо чисельник у 64 бітах.
    return (uint32_t)(((uint64_t)energy_mwh * 1000u) / avg_uw);
}
```

Прокрутимо середнє в голові так само, як пік, — щоб і це число можна було звірити рукою. Кожен споживач дає в `avg_uw` свою вхідну потужність (ту саму, що йшла в пік), помножену на робочий цикл:

```
avg_uw — сума (вхідна потужність × робочий цикл) по споживачах:

  радіо TX :  1 100 000 × 8/1000   =   8 800 мкВт
  давачі   :    183 333 × 50/1000  =   9 166 мкВт
  дисплей  :    600 000 × 30/1000  =  18 000 мкВт
                                       ───────────
  avg_uw                           =  35 966 мкВт   ≈ 36 мВт

life = 5 000 000 / 35 966  ≈  139 год  ≈  5.8 доби
```

Вхідні потужності — ті самі 1.10 / 0.18 / 0.60 Вт, що склали пік вище, лише тепер кожна взята зі своєю часткою часу, а не як є. Ось і два числа з однієї таблиці: 1.88 Вт сказали, що порту USB вистачить, а 36 мВт — що від невеликого акумулятора на 5000 мВт·год пристрій протягне близько 139 годин, майже шість діб.

## Складність і пастки

Арифметика тут шкільна, і саме тому небезпечна: код не падає від помилки в одиницях — він тихо повертає неправду. Чотири місця, де це стається найчастіше, і як код вище кожне глушить.

**Перша — складання струмів різних шин.** Найдавніша помилка бюджету: скласти 300 мА логіки на 3.3 В і 120 мА дисплея на 5 В у «420 мА» й порівняти з амперами блока. Виходить нісенітниця — ампер на 5 В важчий за ампер на 3.3 В. Код її не може зробити структурно: він ніколи не додає `peak_ma` між собою, а лише `p_in` у мікроватах, де доданки вже співмірні. Сам тип проміжної суми — потужність, не струм — і є запобіжником.

**Друга — забути ККД або відбити не туди.** Якщо порахувати попит на **виході** перетворювача, недолічиш ват, що пішов у тепло; джерело виявиться перевантаженим там, де таблиця показувала запас. Або ще тонше — помножити на ККД замість поділити (P_вх = P_вих × ККД), тоді втрати «зменшать» попит, що повна дурниця. У коді ділення `(p_out * 100u) / R->eff_pct` стоїть один раз і в один бік; ККД живе на шині, тож його не забудеш для окремого споживача. Контроль на пальцях: вхід **завжди більший** за вихід (P_вх > P_вих), бо перетворювач не може віддати більше, ніж узяв. Якщо в розрахунку вхід вийшов менший — знак ділення переплутаний.

**Третя — переповнення проміжного добутку.** Тут воно ближче, ніж здається. Візьми потужну шину: 12 000 мВ × 5000 мА = 6·10⁷ мкВт уже на виході; помнож на 100 для відбиття через ККД — 6·10⁹, а це за стелею 32-бітного `uint32_t` (≈4.29·10⁹). Якби множники були 32-бітні, добуток мовчки обрізався б і попит вийшов би абсурдно малим — найгірший різновид помилки, бо схожий на «о, з запасом усе гаразд». Рятує приведення `(uint64_t)` **перед** множенням: воно змушує рахувати в 64 бітах. Тому і `p_out`, і `source_uw` беруть `(uint64_t)` на першому множнику, а проміжне `p_out * 100u` живе у вже 64-бітній змінній. Деталі того, як саме мовчазно обрізається ціле, — у [переповненні й обгортанні](book:programming/overflow-wraparound).

**Четверта — сайзинг не за тим числом.** Поведінкова, не арифметична, і найдорожча. Узяти `avg_uw` для вибору блока — блок просяде в першому ж одночасному піку й МК перезавантажиться. Узяти `worst_uw` для часу життя — занизиш автономність у десятки разів і даремно поставиш удвічі більшу батарею. Код тримає **обидва** числа окремими полями саме щоб ця помилка вимагала свідомо взяти не те поле, а не сталася сама собою через те, що «число одне». Правило просте, як у темі: `worst_uw` → джерело/роз'єм/піковий струм батареї; `avg_uw` → час життя.

> 🔧 **Навіщо це.** Усі чотири запобіжники — це не педантизм, а різниця між калькулятором, якому можна вірити, й тим, що тихо бреше. Бюджет рахують **до** паяння саме щоб ловити проблеми на папері; калькулятор, що сам обрізає число при переповненні чи плутає вхід з виходом, гірший за відсутній — він дає хибну впевненість там, де її найнебезпечніше мати.

## Як перевірити, що калькулятор не бреше

Цілочисельний код перевіряють двома незалежними способами, перш ніж вірити йому, — бо, повторюся, він не падає, а тихо віддає неправду.

Перший — груба прикидка порядку. Пристрій на кількох сотнях міліампер від 5-вольтового джерела має давати попит у одиниці ватів, не в мілі- й не в кіловатах. Якщо `worst_uw` вийшов 1 880 000 (1.88 Вт) — порядок той; якщо мільярди чи десятки — десь загубили чи додали тисячу, сплутавши мікро- з мілі-. Найдешевший фільтр від найгрубших промахів: число мусить збігатися з прикидкою на пальцях, інакше далі дивитися марно.

Другий — крайні випадки прямо як юніт-тести, бо в них ховаються діленя на нуль і переповнення:

```c
// 1) ККД 100 % нічого не змінює: вхід дорівнює виходу.
//    Одна шина 1000 мВ × 1000 мА = 1 000 000 мкВт; ККД 100 % → worst = 1 000 000.
// 2) ККД 50 % подвоює попит: той самий вузол → worst = 2 000 000.
// 3) duty 0 ‰ → avg = 0 при будь-якому worst (споживач ніколи не ввімкнений).
// 4) duty 1000 ‰ → avg == worst (завжди в піку).
// 5) eff_pct 0 → споживача пропущено, без ділення на нуль (worst не змінився).
// 6) rail поза межами → споживача пропущено (без читання за масивом).
// 7) потужна шина 12000 мВ × 5000 мА × ККД 90 % → ~6.67e7 мкВт без обрізання:
//    якби множення лишилось 32-бітним, результат був би абсурдно малим.
```

Кожен із цих тестів — кілька рядків, а вкупі вони закріплюють, що одиниці зійшлися, ділення йде в правильний бік і 64-бітна арифметика справді включилася. Випадок (1) ловить переплутаний знак ККД, (3)–(4) — переплутані worst/avg, (5)–(6) — захист від кривих даних, (7) — переповнення. Це рівно ті чотири пастки з попереднього розділу, замкнені в перевірки, що спрацюють самі, якщо хтось колись «спростить» математику й зламає одиниці.

Калькулятор бюджету тим і цінний, що перетворює аркуш на функцію, яку не набридає застосовувати: міняєш рядок таблиці — за секунду бачиш новий попит, новий запас і новий час життя. Аркуш питав «чи влізе задум у джерело» один раз; функція ставить це питання на кожній зміні компонування, поки плата ще не замовлена.
