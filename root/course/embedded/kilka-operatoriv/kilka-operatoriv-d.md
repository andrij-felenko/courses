Розвідувальний безпілотний літак веде спостереження за об'єктом на висоті двохсот метрів. За пультом пілота оператор здійснює доворот літака ліворуч, утримуючи крен у двадцять градусів, щоб уникнути зіткнення з високовольтною лінією передач. Одночасно на сусідній станції оператор корисного навантаження помічає рух у тепловізорі, вмикає режим автоматичного супроводу цілі на оптичному підвісі та активує функцію автоматичного спрямування носа літака на ціль — команду, яка відправляє автопілоту вимогу створити правий крен на п'ятнадцять градусів. Обидва пульти працюють в єдиній польовій радіомережі через спільний модем і транслюють керівні кадри з частотою п'ятдесят герців. Автопілот на борту отримує суперечливі команди впереміш: рулі висоти та елерони починають несамовито смикатися між крайніми положеннями з частотою каналу, струм сервоприводів злітає до критичних значень, повітряний потік зривається з крила, і літак звалюється у штопор.

Ця катастрофа сталася не через відмову датчиків чи помилку в розрахунках аеронавігації — це системний колапс архітектури нерозділених повноважень, де кілька станцій мають рівний неконтрольований доступ до виконавчих контурів апарата.

*Конфлікт нерозділених повноважень: одночасна відправка суперечливих команд ручного керування та автоматичного наведення в єдиний радіоканал призводить до зриву стабілізації та катастрофи.*

## 1. Проблема розділення повноважень у польовій мережі

Сучасне застосування безпілотних комплексів давно вийшло за межі схеми «один пілот — один дрон». Для виконання складних завдань розгортається повноцінний розподілений екіпаж, де кожен фахівець працює за власним автоматизованим робочим місцем (Ground Control Station, GCS):
* **Зовнішній пілот (Remote Pilot in Command):** відповідає за безпеку польоту, траєкторію, швидкість, висоту, зліт, маневрування та посадку;
* **Оператор корисного навантаження (Payload / Sensor Operator):** керує стабілізованою оптико-електронною станцією, тепловізором, лазерним далекоміром або модулями скидання;
* **Командир місії / Офіцер управління (Mission Commander):** контролює тактичну обстановку, затверджує зміну зон патрулювання, взаємодіє із суміжними підрозділами та має повноваження припинити місію в аварійній ситуації;
* **Додаткові термінали спостереження (Observers / Intel Terminals):** штабні планшети та термінали аналітиків, які лише спостерігають за потоком відео та мапою розташування сил.

Усі ці вузли підключені до спільної польової радіомережі — наприклад, радіомодемів топології «точка — багатоточка» (Point-to-Multipoint), військових радіостанцій з підтримкою передачі IP-даних або бездротових MESH-мереж. У таких мережах трафік стандартно передається через широкомовні UDP-пакети (Broadcast/Multicast), що дозволяє будь-якому терміналу слухати загальну телеметрію.

Проте зворотний бік цієї простоти — відсутність вбудованого контролю доступу на рівні транспорту. Якщо застосунок на планшеті спостерігача згенерує команду зміни польотного режиму, мережевий комутатор безперешкодно доставить цей пакет на радіомодем борту.

```
                  Польова радіомережа (Shared RF Link)
 ┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
 │ Пульт Пілота    │      │ Пульт Сенсора   │      │ Пульт Командира │
 │ GCS ID: 255     │      │ GCS ID: 254     │      │ GCS ID: 253     │
 └────────┬────────┘      └────────┬────────┘      └────────┬────────┘
          │                        │                        │
          │ Manual Sticks (50 Hz)  │ Gimbal Track (10 Hz)   │ RTL Abort (1 Hz)
          ▼                        ▼                        ▼
 ═════════════════════════════════════════════════════════════════════
                      Спільний ефірний канал
 ═════════════════════════════════════════════════════════════════════
                                   │
                                   ▼
                     ┌───────────────────────────┐
                     │ Бортовий автопілот        │
                     │ Кому підкорятися?         │
                     │ Хто зараз головний?       │
                     └───────────────────────────┘
```

Без централізованого арбітражу виникають три фундаментальні проблеми:

### 1.1. Змагання за частоту оновлення (Update Rate Race)
Пульт пілота надсилає пакети бажаного крену з частотою 50 Гц, а станція оператора підвісу намагається підкоригувати курс літака з частотою 10 Гц. Якщо автопілот не знає, хто з них є авторизованим джерелом навігації, він починає виконувати команди по черзі в міру їх надходження з кільцевого буфера послідовного порту UART. Виникає ефект «перетягування каната» (Tug of War): протягом десяти мілісекунд літак намагається повернути вліво, наступні десять мілісекунд — вправо. Результатом стають високочастотні гармонійні коливання рульових поверхонь, що призводить до механічного зрізання шестерень у сервоприводах та зриву ламінарного обтікання крила.

### 1.2. Плутанина станів та незворотні деструктивні дії
Типові універсальні програми наземного контролю (такі як QGroundControl або Mission Planner) спроєктовані для роботи з одним апаратом і за замовчуванням мають повний доступ до всіх службових функцій. Якщо оператор корисного навантаження хоче перезавантажити камеру після зависання відеопотоку, але випадково натискає кнопку системного перезавантаження в загальному меню (`MAV_CMD_PREFLIGHT_REBOOT_SHUTDOWN`), радіокадр летить на бортовий автопілот. Автопілот, отримавши валідний за формою пакет від `sysid = 255`, чесно вимикає живлення процесора та глушить мотори посеред польоту.

### 1.3. Відсутність аудиту та втрата ситуаційної обізнаності
Якщо безпілотник несподівано змінює маршрут або починає екстрене повернення на базу, пілот не має можливості швидко визначити причину події. Чи це апаратний збій системи супутникової навігації (GPS Glitch), чи спрацював внутрішній таймер розряду батареї, чи офіцер управління віддав наказ на відхід з іншого пульта? Відсутність ідентифікації джерела команди в контурі реального часу руйнує злагодженість екіпажу в критичний момент місії.

Глибокий аналіз того, як подібні конфлікти дубльованого керування вирішувалися на світанку авіації та в електродистанційних системах fly-by-wire пасажирських літаків, розкрито в історичній довідці [історія спарених органів керування та перемикання пріоритету](root:embedded/kilka-operatoriv/hist-dual-cockpit-control.md).

## 2. Механізм токена авторитету (Authority Token)

Щоб усунути хаос паралельного доступу, архітектура зв'язку зобов'язана розділити потік команд на функціональні площини (Control Planes) та запровадити модель ексклюзивного володіння правами за допомогою **токена авторитету** (лат. *auctoritas* — влада, вплив; англ. *Authority Token*).

Токен авторитету — це динамічний дозвільний мандат у пам'яті бортового контролера, який закріплюється за унікальним системним ідентифікатором станції (`gcs_id`). Наявність активного токена є обов'язковою перепусткою для проходження команди крізь бортовий фільтр до виконавчого контуру. Усі станції, які не володіють токеном певної категорії, автоматично перебувають у стані спостереження (Read-Only).

![Архітектура токена авторитету](/root/course/embedded/kilka-operatoriv/img/authority-token-architecture.svg)
*Архітектура токена авторитету: розділення каналів керування польотом, навантаженням та наглядом під контролем бортового арбітра.*

### 2.1. Розподіл площин керування

Протокол арбітражу жорстко розмежовує чотири функціональні площини:

1. **Площина польотного контролю (Flight Control Plane):**
   * **Токен:** `AUTH_TOKEN_PILOT`.
   * **Призначення:** Формування просторової траєкторії, пряме ручне керування стіками (`MANUAL_CONTROL`), зміна польотних режимів автопілота (`SET_MODE`), корекція висоти, швидкості та передача списку маршрутних точок (`MISSION_ITEM`).
   * **Правило ексклюзивності:** Рівно одна станція пілота на весь апарат. Будь-які навігаційні команди від інших адрес відкидаються бортом на рівні парсера.
2. **Площина цільового навантаження (Payload Control Plane):**
   * **Токен:** `AUTH_TOKEN_PAYLOAD`.
   * **Призначення:** Керування кутами наведення оптико-електронного підвісу (`DO_MOUNT_CONTROL`), зміна фокусної відстані та оптичного зуму, активація лазерного підсвічувача, спуск затвора камери, перемикання кольорових палітр тепловізора, скидання вантажу.
   * **Правило ексклюзивності:** Закріплюється за робочим місцем оператора сенсорів. Не має права прямого доступу до зміни кутів крену, тангажу чи курсу літака.
3. **Площина моніторингу та нагляду (Monitor Plane):**
   * **Токен:** Не потрібен (пасивний режим за замовчуванням).
   * **Призначення:** Прийом та десеріалізація загального широкомовного потоку телеметрії (координати, стан акумулятора, висота, швидкість, відеотрансляція).
   * **Правило:** Дозволено довільній кількості абонентів у польовій мережі.
4. **Площина командира (Commander Plane):**
   * **Токен:** `AUTH_TOKEN_COMMANDER`.
   * **Призначення:** Аварійне припинення місії, екстрене переведення дрона в режим повернення на базу (`RTL`) або зависання на місці (`BRAKE / LOITER`), примусове відкликання токена пілота в разі неадекватних дій.
   * **Правило:** Суперкористувач із найвищим пріоритетом в ієрархії арбітражу.

### 2.2. Життєвий цикл токена та модель оренди (Heartbeat Lease)

Токен не надається станції безстроково. Якщо пульт пілота раптово втратить живлення, зависне або потрапить у зону глибокої радіотіні, система не повинна залишатися заблокованою під мертвою адресою. Для цього застосовується модель оренди за часом (Lease Time):

```
 Станція Пілота (GCS #255)                     Бортовий арбітр (FCU)
 ┌──────────────────────┐                    ┌────────────────────────────┐
 │ Стан: PILOT_ACTIVE   │                    │ Стан: PILOT_ACTIVE         │
 └──────────────────────┘                    └────────────────────────────┘
            │                                               │
            │ 1. HEARTBEAT(Role: PILOT, Nonce: 0x4A1F)     │ Скидання таймера:
            ├──────────────────────────────────────────────►│ T_lease = 1000 ms
            │                                               │
            │ [ 250 мс інтервал ]                           │
            │                                               │
            │ 2. HEARTBEAT(Role: PILOT, Nonce: 0x4A1F)     │ Скидання таймера:
            ├──────────────────────────────────────────────►│ T_lease = 1000 ms
            │                                               │
            X  <<< Обрив радіозв'язку з пілотом >>>         │
            │                                               │ Таймер цокає:
            │                                               │ 1000 мс минуло!
            │                                               ▼
            │                                ┌────────────────────────────┐
            │                                │ Стан: LINK_LOST            │
            │                                │ Блокування старих стіків   │
            │                                │ Автопілот: перехід у LOITER│
            │                                └────────────────────────────┘
```

1. **Захоплення токена (Acquisition):** Станція надсилає запит `MSG_AUTH_TOKEN_REQ`. Якщо відповідна роль вільна, бортовий арбітр генерує криптографічно стійке псевдовипадкове 32-бітне число `token_nonce`, фіксує ідентифікатор станції та повертає квитанцію `MSG_AUTH_TOKEN_GRANT` із зазначенням тривалості оренди (за замовчуванням `lease_ms = 1000`).
2. **Періодичне поновлення оренди (Keepalive):** Станція зобов'язана регулярно транслювати серцебиття `MSG_AUTH_HEARTBEAT` з інтервалом не більше ніж 250 мс, вказуючи свій активний `token_nonce`. Кожен валідний пакет від діючого володаря скидає системний таймер борту `T_lease` назад на 1000 мс.
3. **Прострочення оренди (Lease Expiration):** Якщо протягом 1000 мс борт не отримує жодного пакета серцебиття від активного пілота:
   * Автопілот блокує виконання останніх отриманих значень стіків (Stale Control Lock), усуваючи ризик «залипання» рулів у крайніх положеннях;
   * Бортовий контролер автоматично активує аварійний режим утримання позиції (`LOITER`) або повернення на точку старту (`RTL`);
   * Статус токена переводиться у стан `LINK_LOST`, що відкриває можливість швидкого перехоплення керування резервним пультом.

Повний двійковий опис полів заголовка, форматів повідомлень та кодів помилок арбітражу наведено у довідковій вставці [бінарний протокол делегування та арбітражу повноважень](root:embedded/kilka-operatoriv/api-authority-protocol.md).

## 3. Безпечна передача зміни (Shift Handover)

Під час виконання довготривалих розвідувальних або патрульних місій тривалість перебування апарата в повітрі може сягати 4–12 годин. Через фізичну та когнітивну втому пілот втрачає гостроту реакції приблизно через 90–120 хвилин безперервного ручного пілотування. Виникає необхідність планової передачі зміни на резервний пульт безпосередньо у польоті.

Найнебезпечніша інженерна помилка при реалізації зміни пілота — це **ударний стрибок керування** (Control Bump). Розглянемо фізичну сутність цього явища.

Нехай перший пілот (Pilot A) утримує літак у розвороті проти бокового вітру:
* Стік елеронів (Roll) відхилений вправо на +20%;
* Стік керма висоти (Pitch) підтягнутий на себе на -8% для компенсації втрати висоти у віражі;
* Стік газу (Throttle) виставлений на 60% тяги.

У цей момент другий пілот (Pilot B) бере в руки свій пульт, на якому пружинні механізми тримають стіки в нульовому центрі (Roll = 0%, Pitch = 0%), а важіль газу опущений в упор донизу (Throttle = 0%). Якщо система здійснить миттєве перемикання активного джерела без попередньої підгонки, вхідні сигнали регуляторів за один такт таймера (20 мс) зазнають східчастого розриву:

```
ΔThrottle = 0% - 60% = -60%         [миттєве падіння тяги двигуна]
ΔRoll     = 0% - (+20%) = -20%      [різкий переклад елеронів у протилежний бік]
ΔPitch    = 0% - (-8%) = +8%        [скидання кута атаки та пікірування]
```

Фізичні наслідки такого перемикання катастрофічні: регулятори обертів безколекторних моторів скидають тягу, літак зазнає різкого перевантаження за креном, крило втрачає підйомну силу, а інерційні датчики автопілота фіксують перевантаження, що може призвести до збою фільтра Калмана (EKF).

```
       Поточне значення в контурі:       Фізичний стан змінного пульта:
       ┌───────────────────────────┐     ┌────────────────────────────┐
       │ Газ (Throttle): 60%       │     │ Газ (Throttle): 0% (Упор)  │
       │ Крен (Roll): +20%         │ ≠   │ Крен (Roll): 0% (Центр)    │
       │ Тангаж (Pitch): -8%       │     │ Тангаж (Pitch): 0% (Центр) │
       └───────────────────────────┘     └────────────────────────────┘
                                     ▼
                Миттєве перемикання без підгонки =
         Катастрофічний ударний стрибок керування (Control Bump)
```

Щоб гарантувати абсолютно плавний та безударний перехід (Bumpless Transfer), процедура передачі зміни організовується як сувора чотирифазна транзакція.

![Безпечна процедура передачі зміни](/root/course/embedded/kilka-operatoriv/img/shift-handover-sequence.svg)
*Безпечна 4-фазна процедура передачі зміни: запит, звірка стіків у мертвій зоні, атомарний світч токена та підтвердження нової ролі.*

### 3.1. Фаза 1: Запит передачі (Handover Request)
Діючий пілот (GCS #1) обирає в меню станції номер змінного пульта (GCS #2) і натискає кнопку «Передати керування». Станція формує та відправляє борту повідомлення `HANDOVER_REQUEST`. Бортовий арбітр переходить у стан `HANDOVER_WAIT_STICK`, блокує прийом запитів від сторонніх вузлів, запускає 5-секундний захисний таймер і транслює на пульт GCS #2 повідомлення `HANDOVER_OFFER`.

### 3.2. Фаза 2: Візуальна підгонка та верифікація мертвої зони (Deadband Match)
Отримавши оферту, інтерфейс станції GCS #2 блокує всі навігаційні кнопки та виводить на екран діалогове вікно підгонки органів керування.

Вимоги до положення фізичних стіків змінного пульта:
* **Канали крену, тангажу та рискання (Roll, Pitch, Yaw):** Змінний пілот зобов'язаний повністю прибрати руки з ручок керування, дозволивши внутрішнім пружинам виставити їх у центр. Бортовий арбітр перевіряє, щоб нормалізоване значення кожної осі потрапляло в мертву зону (Deadband) ±3% від нейтралі:

```
-30 ≤ roll_axis ≤ +30        [перевірка нейтралі крену: ±3% від шкали 1000]
-30 ≤ pitch_axis ≤ +30       [перевірка нейтралі тангажу: ±3% від шкали 1000]
-30 ≤ yaw_axis ≤ +30         [перевірка нейтралі рискання: ±3% від шкали 1000]
```

* **Канал газу (Throttle):** Якщо апарат перебуває в режимах стабілізації висоти (`ALT_HOLD / POSHOLD`), стік газу виставляється у центральну нейтраль (50% ±3%). Якщо дрон летить у прямому ручному режимі (`MANUAL`), інтерфейс показує цільову шкалу поточної бортової тяги, і змінний пілот підганяє свій важіль газу у вікно толерантності ±2% від поточного бортового значення.

### 3.3. Фаза 3: Атомарне перемикання дескриптора (Atomic Ownership Flip)
Коли всі датчики пульта GCS #2 фіксують потрапляння осей у зелену зону, змінний пілот натискає кнопку «Прийняти зміну». Пульт надсилає борту пакет `MSG_HANDOVER_STICK_CHECK`.

Бортовий арбітр перевіряє значення осей. Якщо умови нейтралі дотримано:
1. Дескриптор активного пілота атомарно перезаписується: `pilot_gcs_id = candidate_id`;
2. Генерується нове число `token_nonce`, що миттєво знецінює будь-які старі кадри від GCS #1, які могли затриматися в мережевих буферах;
3. Таймер оренди перезапускається для нової станції;
4. Борт повертає квитанцію `HANDOVER_COMPLETED`.

### 3.4. Фаза 4: Фіксація статусів
* Станція старого пілота отримує повідомлення про передачу повноважень: її інтерфейс деактивує віртуальні джойстики та перемикається в пасивний режим моніторингу (`Read-Only`);
* Станція нового пілота стає повноцінним господарем каналу пілотування. Оскільки стіки перебували в нейтралі або були підігнані заздалегідь, перемикання відбувається без найменшого стрибка кутів стабілізації чи струму двигунів.

## 4. Ієрархія та аварійне перехоплення (Commander Override)

У бойових умовах та під час критичних інцидентів трапляються ситуації, коли пілот впадає в паніку, втрачає просторову орієнтацію через засліплення або коли його пульт перестає адекватно функціонувати. У таких сценаріях чекати мирної процедури передачі зміни неприпустимо.

Для вирішення цієї проблеми протокол реалізує механізм **аварійного перехоплення командиром** (Commander Override).

![Ієрархія авторитету та аварійне перехоплення](/root/course/embedded/kilka-operatoriv/img/commander-override-arbitration.svg)
*Ієрархія авторитету: командир місії має найвищий пріоритет і право миттєвого анулювання повноважень пілота без його згоди.*

### 4.1. Драбина рівнів авторитету

Кожен тип повідомлення та кожна роль мають суворий пріоритет (Authority Level):

```
       Рівень 3: КОМАНДИР МІСІЇ (Authority Level: 255)
       ▲  • Аварійне перехоплення (Commander Override)
       │  • Безумовне відкликання токенів
       │
       Рівень 2: ПІЛОТ АПАРАТА (Authority Level: 128)
       ▲  • Ручне пілотування, навігаційні точки
       │  • Ініціація планової передачі зміни
       │
       Рівень 1: ОПЕРАТОР НАВАНТАЖЕННЯ (Authority Level: 64)
       ▲  • Керування підвісом, камерою, лазером
       │
       Рівень 0: СПОСТЕРІГАЧ (Authority Level: 1)
          • Тільки прийом телеметрії
```

**Фундаментальне правило:** Команда з нижчим або рівним рівнем авторитету ніколи не може перервати дію вищого рівня. Проте вищий рівень має право безумовного асинхронного переривання будь-яких процесів нижчих рівнів.

### 4.2. Алгоритм аварійного втручання

1. **Ініціація командиром:** Командир місії натискає спеціальну захищену кнопку `[ EMERGENCY OVERRIDE ]` на своєму терміналі.
2. **Генерація криптографічного пакета:** Станція командира формує пакет `MSG_COMMANDER_OVERRIDE`, завірений цифровим підписом MAVLink v2 на основі закритого ключа командира. Це гарантує, що ворожий передавач РЕБ не зможе зімітувати сигнал перехоплення.
3. **Бортова обробка:**
   * Отримавши валідний наказ командира, бортовий арбітр негайно анулює діючий токен пілота (`pilot_gcs_id = 0`);
   * Автопілот скидає ручне керування та переходить у режим стабілізованого зависання на місці (`BRAKE / LOITER`) або повернення додому (`RTL`);
   * Арбітр переходить у захисний стан `COMMANDER_LOCKED`, блокуючи будь-які подальші спроби пілота відправити навігаційні пакети.
4. **Оповіщення екіпажу:** Усі вузли мережі отримують системне сповіщення про факт перехоплення місії командиром.

## 5. Програмна реалізація бортового арбітра

Бортовий арбітр будується навколо детермінованого скінченного автомата станів (FSM). Автомат гарантує, що за будь-яких комбінацій вхідних пакетів, радіозавад чи обривів зв'язку система завжди перебуватиме в одному з відомих безпечних станів.

```
                  ┌────────────────────────┐
                  │          IDLE          │
                  │   (Токен вільний)      │
                  └───────────┬────────────┘
                              │
                    TOKEN_REQ │ TOKEN_GRANT
                              ▼
                  ┌────────────────────────┐
      ┌──────────►│      PILOT_ACTIVE      │◄──────────┐
      │           │ (Пілот керує польотом) │           │
      │           └─────┬────────────┬─────┘           │
      │                 │            │                 │
      │   T_lease > 1 c │            │ HANDOVER_REQ    │ STICK_CHECK (OK)
      │                 ▼            ▼                 │
      │     ┌───────────────┐    ┌───────────────────┐ │
      │     │   LINK_LOST   │    │HANDOVER_WAIT_STICK│ │
      │     │(Failsafe Hold)│    │(Очікування стіків)│ │
      │     └───────────────┘    └───────────┬───────┘ │
      │                 ▲                    │         │
      │                 │                    └─────────┘
      │                 │              HANDOVER_TIMEOUT
      │                 │
      │       COMMANDER_OVERRIDE (З будь-якого стану)
      │                 │
      │                 ▼
      │   ┌───────────────────────────┐
      └───│     COMMANDER_LOCKED      │
          │ (Заблоковано командиром)  │
          └───────────────────────────┘
```

Нижче наведено базовий інтерфейсний скелет фільтрації команд на рівні автопілота на мовах C та C++20:

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>

typedef struct {
    uint8_t  active_pilot_gcs_id;
    uint32_t token_nonce;
    uint32_t lease_deadline_ms;
    bool     commander_locked;
} flight_arbiter_t;

static flight_arbiter_t g_flight_arbiter;

/* Швидкий фільтр вхідних 50 Гц пакетів ручного керування */
bool is_manual_control_packet_valid(uint8_t src_gcs_id, uint32_t nonce, uint32_t now_ms) {
    if (g_flight_arbiter.commander_locked) {
        return false; /* Заблоковано командиром */
    }
    if (now_ms > g_flight_arbiter.lease_deadline_ms) {
        return false; /* Оренда прострочена */
    }
    if (src_gcs_id != g_flight_arbiter.active_pilot_gcs_id) {
        return false; /* Джерело не є активним пілотом */
    }
    if (nonce != g_flight_arbiter.token_nonce) {
        return false; /* Недійсний або застарілий токен */
    }
    return true;
}
```

        uint8_t src_gcs_id,

            return false;
        }
        if (now_ms > lease_deadline_ms_) {

            return false;
        }

        }
        return true;
    }

private:
    uint8_t  active_pilot_gcs_id_{0};
    uint32_t token_nonce_{0};
    uint32_t lease_deadline_ms_{0};
    bool     commander_locked_{false};
};

} // namespace auth

## 6. Практичні висновки та інженерний чекліст

Побудова надійного багатооператорського комплексу вимагає неухильного виконання семи базових інженерних правил:

1. **Принцип заборони за замовчуванням (Deny-by-Default):** Жоден пакет ручного пілотування, зміни польотного режиму чи наведення камери не повинен передаватися у виконавчі контури без попередньої верифікації активного токена відповідної ролі.
2. **Строге розділення площин керування:** Оператор корисного навантаження повинен мати апаратну та програмну ізоляцію від навігаційних каналів літака. Його команди не мають права прямо змінювати курс чи висоту апарата.
3. **Жорсткі таймери оренди (Heartbeat Lease):** Усі токени доступу повинні автоматично анулюватися за тайм-аутом (1000 мс) у разі припинення отримання пакетів серцебиття від керуючої станції.
4. **Безударна передача зміни (Bumpless Handover):** Перемикання токена пілота дозволяється лише після підтвердження встановлення органів керування змінного пульта у мертву зону (±3%) або попереднього вирівнювання поточної тяги двигунів.
5. **Захист від атак повторного відтворення через Nonce:** Кожне перемикання або перезахоплення токена генерує нове 32-бітне псевдовипадкове число сесії, що миттєво знецінює будь-які застарілі пакети в мережевих буферах.
6. **Криптографічний захист команд суперкористувача:** Аварійне перехоплення командиром обов'язково перевіряється за допомогою цифрового підпису MAVLink v2 для унеможливлення перехоплення апарата засобами радіоелектронної боротьби.
7. **Автономна безпека при втраті зв'язку:** У разі відсутності валідного пілота автопілот зобов'язаний самостійно активувати режим зависання або повернення на базу, не очікуючи зовнішніх вказівок.
