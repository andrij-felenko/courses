# ⚙️ Бюджет енергії таблицею у прошивці

Розрахунок середнього струму інженер робить раз — на серветці чи в електронній таблиці. Але є випадок, коли той самий розрахунок корисно тримати прямо в прошивці: коли пристрій сам має оцінювати залишок свого життя й доповідати його — «батареї стане ще на 47 діб». Тоді профіль фаз і ділення ємності на середній струм перетворюються на маленьку, але дуже ходову структуру даних і пару функцій. Розберімо її від задачі до робочого коду й пасток.

## Коли це справді треба

Спокуса покласти такий калькулятор у кожен пристрій є, та здебільшого вона зайва: якщо профіль фіксований і відомий наперед, час життя порахований ще до паяння, і прошивці нема чого його перераховувати. Користь з'являється рівно тоді, коли профіль не фіксований, а пристрій має сам собі дати раду. Логер, що міняє інтервал замірів за порою року, не знає наперед свого середнього струму — а отже й залишку. Шлюз, що під час бурі шле телеметрію втричі частіше, проїдає батарею швидше, ніж за паспортом. Сенсор, який показує власнику смужку заряду й число «ще ~40 діб», мусить це число звідкись брати. У всіх трьох випадках профіль складається динамічно, і той самий розрахунок із серветки доводиться вшити в код. Тому функцію нижче варто розуміти не як обов'язкову частину кожної прошивки, а як інструмент для пристроїв, чий апетит залежить від обставин.

## Задача

Дано: набір фаз циклу, у кожної свій струм і своя тривалість; повний період циклу; ємність батареї. Треба: середній струм за цикл і очікуваний час життя. Бажано так, щоб профіль легко правити (додати фазу, змінити струм) без переписування математики, і щоб усе рахувалося в цілих числах там, де можна, — на маленькому МК краще не тягнути float без потреби, а часто й нема за що: ядро без апаратного блока для дробів емулює кожну операцію десятками інструкцій.

## Ідея

Профіль — це просто таблиця рядків «струм × час». Заряд за цикл — сума добутків плюс заряд сну за решту періоду. Середній струм — заряд поділити на період. Час життя — ємність поділити на середній струм. Уся арифметика тримається на одному фізичному факті: заряд адитивний. Кулони, що витекли в boot, у вимір, у передачу й у сон, просто додаються — байдуже, в якому порядку й наскільки різні фази за висотою. Саме тому профіль будь-якої складності зводиться до однієї суми, а та сума — до одного ділення.

Уся хитрість — в одиницях. Тримати струм в амперах, а час у секундах означало б дроби, а отже float. Натомість беремо струм у мікроамперах, а час у мікросекундах — обидва цілі числа, бо такою є природна роздільність і даташита, і таймера. Добуток виходить в одиницях мкА·мкс; це не звичний кулон, а зручний внутрішній масштаб, у якому все ціле. Розплата за зручність — числа ростуть стрімко: один лише boot дає двісті мільярдів таких одиниць, а це вже за стелею 32 бітів. Тому заряд накопичуємо у 64-бітному цілому, а ділення на період лишаємо на самий кінець: що пізніше ділиш, то менше точності губиш на відкинутих дробах і то пізніше ризикуєш зловити [переповнення](book:programming/overflow-wraparound).

## Робочий код

```c
#include <stdint.h>
#include <stddef.h>

// Одна фаза циклу: струм у мікроамперах, тривалість у мікросекундах.
typedef struct {
    uint32_t current_uA;   // напр. 180000 = 180 мА
    uint32_t duration_us;  // напр. 300000 = 0.3 с
} phase_t;

// Підсумок розрахунку.
typedef struct {
    uint32_t avg_current_uA;   // середній струм за цикл, мкА
    uint32_t life_hours;       // оцінка часу життя, год
} budget_t;

// active[] — активні фази (boot, вимір, TX...). Решту періоду чіп спить.
// period_us  — повна тривалість циклу, мкс.
// sleep_uA   — струм глибокого сну, мкА.
// cap_mAh    — ємність батареї, мА·год.
budget_t energy_budget(const phase_t *active, size_t n,
                       uint64_t period_us, uint32_t sleep_uA,
                       uint32_t cap_mAh) {
    budget_t out = {0, 0};
    if (period_us == 0) return out;            // захист від ділення на нуль

    // Заряд активних фаз, накопичуємо в 64 бітах: мкА·мкс росте дуже швидко.
    uint64_t active_us = 0;
    uint64_t charge_uA_us = 0;                  // заряд в одиницях мкА·мкс
    for (size_t i = 0; i < n; i++) {
        charge_uA_us += (uint64_t)active[i].current_uA * active[i].duration_us;
        active_us    += active[i].duration_us;
    }

    // Сон займає решту періоду (якщо активні фази довші за період — сну нема).
    uint64_t sleep_us = (active_us < period_us) ? (period_us - active_us) : 0;
    charge_uA_us += (uint64_t)sleep_uA * sleep_us;

    // Середній струм = заряд / період (мкА·мкс / мкс = мкА). Округлення до найближчого.
    uint64_t avg_uA = (charge_uA_us + period_us / 2) / period_us;
    out.avg_current_uA = (uint32_t)avg_uA;

    if (avg_uA == 0) return out;                // нескінченне життя — лишаємо 0 як «дуже довго»

    // Час життя: ємність / середній струм. cap у мА·год = cap*1000 мкА·год.
    // life_h = cap_mAh * 1000 / avg_uA.  cap*1000 множимо в 64 бітах.
    out.life_hours = (uint32_t)(((uint64_t)cap_mAh * 1000u) / avg_uA);
    return out;
}
```

Функція навмисне зроблена чистою: вона нічого не читає з апаратури й нічого не пише в журнал, лише бере аргументи й повертає результат. Це не дрібниця стилю, а умова перевірності — таку функцію можна ганяти юніт-тестами на звичайному комп'ютері, без жодного МК, бо її поведінка цілком визначена входом. Повертає вона маленьку структуру, а не одне число, бо середній струм і час життя потрібні зазвичай разом: перший — для діагностики й порівняння сценаріїв, другий — щоб показати людині. Профіль приходить окремим масивом, тож той самий код обслуговує і метеостанцію з трьох фаз, і складніший пристрій з десятка — міняється лише таблиця, не математика.

Виклик для метеостанції з основної статті виглядає так:

```c
void report_battery_life(void) {
    static const phase_t cycle[] = {
        { 120000u, 1200000u },   // boot + Wi-Fi конект: 120 мА, 1.2 с
        {  25000u,  200000u },   // вимір:                25 мА, 0.2 с
        { 180000u,  300000u },   // TX:                  180 мА, 0.3 с
    };
    budget_t b = energy_budget(cycle, sizeof(cycle)/sizeof(cycle[0]),
                               600ull * 1000000ull,  // період 600 с у мкс
                               8u,                    // сон 8 мкА
                               2000u);                // батарея 2000 мА·год

    // Очікувано: avg ≈ 346 мкА, life ≈ 5775 год (≈ 8 місяців).
    ESP_LOGI("pwr", "I_сер = %u мкА; залишок ≈ %u год (%u діб)",
             b.avg_current_uA, b.life_hours, b.life_hours / 24);
}
```

## Пастки

Перша й найболючіша — **переповнення проміжного добутку**. 180000 мкА × 1200000 мкс = 2.16·10¹¹ — це вже далеко за межами 32-бітного `uint32_t` (максимум ~4.29·10⁹). Якби множення лишилося 32-бітним, результат мовчки обрізався б і середній струм вийшов би абсурдним. Рятує саме приведення `(uint64_t)` перед множенням: воно змушує компілятор рахувати добуток у 64 бітах. Забути це приведення — класична помилка, і компілятор про неї не попередить.

Друга — **округлення цілочисельного ділення**. Звичайне `a / b` у C відкидає дробову частину, тож довгий ланцюжок ділень систематично занижує результат. Додавання `period_us / 2` перед діленням дає округлення до найближчого, а не вниз, — дрібниця, але на оцінці залишку днів вона помітна.

Третя — **припущення, що сон заповнює решту періоду**. Формула вважає, що поза активними фазами чіп спить зі струмом `sleep_uA`. Якщо насправді між фазами є проміжки на іншому струмі (скажімо, очікування відповіді сервера при 30 мА), їх треба внести окремими рядками таблиці, інакше оцінка вийде надто оптимістичною. Таблиця гарна саме тим, що такий проміжок додається одним рядком.

Четверта — **жорсткий поділ на "активне" і "сон"**. Реальна ємність батареї падає від саморозряду, холоду й того, що під піковим струмом вона віддає менше, ніж за паспортом. Ця функція дає верхню, оптимістичну оцінку; на точніший бюджет із поправками дивись [математику бюджету батареї](book:programming/battery-budget/math-battery-math.md). Для «скільки ще протримаюсь» у польових умовах варто закладати запас — оцінку сміливо ділити на коефіцієнт 1.2–1.5.

## Як перевірити, що число не бреше

Цілочисельний код підступний тим, що він не падає — він тихо повертає неправду, якщо одиниці десь не зійшлися. Тому результат варто перевіряти двома незалежними способами, перш ніж вірити йому.

Перший — груба оцінка в голові. Якщо середній струм у сотнях мікроампер, а батарея на дві тисячі мА·год, то час життя — це 2000 мА·год поділити на 0.3 мА, тобто щось близько шести-семи тисяч годин, себто рік чи менше. Якщо функція повертає мільйон годин або, навпаки, десять, — десь загубили тисячу: переплутали мікро- й мілі-, ампери й міліампери. Порядок величини мусить збігтися з прикидкою на пальцях; це найдешевший фільтр від найгрубших помилок.

Другий — перевірка крайніх випадків прямо в коді, як юніт-тест. Період нуль має повертати нулі, а не ділення на нуль. Профіль із самого лише сну має давати середній струм, рівний струмові сну, — точно, до одиниці. Активні фази, довші за весь період (помилка введення), не повинні давати від'ємний час сну й завертати число. Один масив фаз із наперед відомою відповіддю — як метеостанція з основної статті, де очікуємо близько 346 мкА, — закріплює, що формула й одиниці зійшлися, і ловить регресію, якщо хтось колись поправить математику. Кілька таких перевірок коштують десяток рядків, а бережуть від найгіршого роду помилок — тих, що не виказують себе збоєм, а лише тихо брешуть у звіті про залишок батареї.
