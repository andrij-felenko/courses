# Відтворення інциденту з трьох джерел

<preknowlist>
- [Журналювання на борту](root:embedded/zhurnaliuvannia-na-bortu) — кільцеві секторні буфери у Flash-пам'яті, рівні логів та вивантаження діагностичних подій без блокування основного потоку.
- [Формати бортових логів: ULog і DataFlash](root:sys-dron/flight-log-formats) — структура бінарного потоку, частоти запису каналів, таблична та самоописова розмітка повідомлень.
- [Запис і відтворення телеметрії](root:sys-dron/telemetry-logging) — структура файлів `.tlog`, таймкоди прибуття пакетів MAVLink та протокол обміну з наземною станцією.
- [Дрейф годинників](root:sf-distributed/clock-offset-drift) — відхилення частоти кварцових генераторів, фазовий зсув і накопичення похибки в частинах на мільйон (ppm).
- [Підписи типових відмов у логу](root:embedded/pidpysy-typovykh-vidmov-u-lohu) — сигнатури зриву комутації ESC, вібраційного кліпінгу та розбіжності інновацій EKF.
- [Журнал дій оператора](root:embedded/zhurnal-dii-operatora) — фіксація команд пілота, перемикання польотних режимів та аудит дій на станції керування.
- [Спільна шкала часу](root:embedded/spilna-shkala-chasu) — методи прив'язки монотонного часу мікроконтролера до абсолютного стінного часу UTC.
</preknowlist>

Автономний дрон під час інспекції високовольтної лінії електропередач на швидкості 22 м/с раптово зривається в крен, зачіпає нижній захисний трос і розбивається об землю. Бортовий бінарний лог у флеш-пам'яті контролера обривається за 350 мс до удару через просідання живлення процесора при екстремальному гальмуванні двигунами; журнал наземної станції керування містить 18% втрачених пакетів і радіозатримку в 240 мс, показуючи плавний політ аж до моменту втрати зв'язку; а відеозапис 4K-камери з окремого акумулятора фіксує перекидання рами в повітрі, але не містить жодних показів напруги, струмів чи помилок внутрішніх автоматів стабілізації.

Якщо аналітик розглядає кожен із цих трьох журналів окремо, він отримує три взаємовиключні та хибні версії катастрофи: бортовий лог вказує на раптове зависання процесора, телеметрія станції звинувачує пілота в запізнілій реакції на вітровий порив, а відеоряд створює враження механічного відриву пропелера. Без алгоритмічного злиття трьох модальностей даних неможливо встановити істинний причинно-наслідковий ланцюг: чи пілот скерував апарат у дріт, чи магнітна завада від ЛЕП спровокувала колапс фільтра Калмана, чи втрата радіоканалу викликала передчасне спрацювання аварійного алгоритму повернення додому.

Мультимодальне відтворення інциденту (англ. *multimodal incident reconstruction*) — це інженерна методологія та алгоритмічний апарат об'єднання високочастотного бортового логу, телеметрії наземного пункту керування та відеопотоку на єдиній детермінованій шкалі часу для беззаперечного розкриття першопричини аварії вбудованої системи.

## Три джерела правди: взаємне доповнення модальностей

Жодне окремо взяте джерело інформації на борту або на землі не володіє повнотою спостереження за фізичним станом літального апарата та діями оператора. Надійний пост-аналіз спирається на три незалежні модальності, кожна з яких має власну частоту дискретизації, шкалу часу та специфічні вразливості.

![Порівняння трьох джерел даних для реконструкції інцидентів](/root/course/embedded/vidtvorennia-intsydentu-z-trokh-dzherel/img/three-sources-truth.svg)
*Три незалежні модальності спостереження: високочастотний бортовий лог, телеметрія станції керування та оптичний відеозапис*

### 1. Бортовий бінарний лог високої частоти (.bin / .ulg)

Бортовий логер записує стан внутрішніх підсистем безпосередньо в мікросхему SPI NOR/NAND Flash або на карту microSD із частотою від 50 до 400 Гц (для сирих показів гіроскопа — до 1–2 кГц). Цей потік містить:
- первинні покази інерційного блоку IMU (`IMU.GyrX..Z`, `IMU.AccX..Z`);
- стан інновацій та матриць коваріації розширеного фільтра Калмана (`XKF1..4`, `estimator_innovations`);
- похибки та виходи контурів кутового й навігаційного регулювання PID (`RATE.R/P/Y`, `PIDR.P/I/D/FF`);
- цифрову телеметрію регуляторів швидкості за протоколом DShot (`ESC.RPM`, `ESC.Current`, `ESC.Temp`);
- стан напруги силової шини та споживання струму датчиком струму (`BAT.Volt`, `BAT.Curr`);
- стан завантаження процесора та переповнення черг повідомлень RTOS (`PM.Load`, `perf_counters`).

Головна перевага бортового логу — субмілісекундна деталізація та повна внутрішня спостережуваність алгоритмів прошивки. Проте він має фундаментальні обмеження: відлік ведеться в локальному монотонному часі мікроконтролера `t_boot` (мікросекунди від увімкнення живлення), лог позбавлений інформації про радіоефір і дії людини на землі, а при раптовому знеструмленні останній буфер у RAM обсягом від 4 до 64 КБ безповоротно втрачається без запису на диск.

В архітектурах ArduPilot (формат DataFlash BIN) та PX4 (формат ULog) потік формується асинхронно через кільцеві буфери DMA. Якщо швидкість запису на карту microSD тимчасово падає через затримки внутрішнього контролера карти (англ. *garbage collection stall*), логер скидає пакети повідомлень, залишаючи в логу характерні часові прогалини (англ. *dropouts*).

### 2. Телеметричний журнал наземної станції (.tlog)

Наземна станція керування (QGroundControl, Mission Planner) зберігає весь вхідний та вихідний трафік протоколу MAVLink у файл `.tlog`. Кожен пакет супроводжується 64-бітним штампом абсолютного часу прибуття на комп'ютер (Unix Epoch у мікросекундах). Цей журнал фіксує:
- команди оператора: перемикання польотних режимів (`MAV_CMD_DO_SET_MODE`), завантаження точок місії, коригування параметрів;
- прямі положення стіків пульта керування (`RC_CHANNELS`);
- якість бездротового зв'язку: потужність сигналу RSSI, відношення сигнал/шум SNR, відсоток втрачених пакетів і частоту повторних запитів (`RADIO_STATUS`);
- текстові діагностичні сповіщення системи (`STATUSTEXT`);
- стан геозон та команд аварійної зупинки двигунів (`MAV_CMD_COMPONENT_ARM_DISARM`).

Лог станції зберігається на накопичувачі оператора і гарантовано виживає при повному фізичному знищенні або втраті дрона. Однак його частота обмежена пропускною здатністю радіоканалу (зазвичай 2–10 Гц), пакети зазнають нерівномірної мережевої затримки (100–300 мс), а радіозавади призводять до випадання критичних відрізків траєкторії.

Крім того, наземна станція не отримує сирі високочастотні сигнали давачів. Усі значення кутів та швидкостей у телеметрії MAVLink є результатом попередньої фільтрації та даунсемплінгу на борту. Це означає, що швидкі вібраційні осциляції частотою понад 5 Гц або короткочасні збої комутації моторів тривалістю 10–20 мс у телеметрії станції взагалі не відображаються.

### 3. Відеозапис камери з таймкодами (MP4 / MKV)

Оптичний відеозапис (курсова FPV-камера, тепловізор або зовнішня камера спостереження) ведеться з частотою 30, 60 або 120 кадрів на секунду. Відео містить:
- просторове положення апарата відносно земних орієнтирів, дерев, ліній електропередач та інших перешкод;
- накладену екранну телеметрію OSD (якщо використовується запис аналогового або цифрового відеолінка);
- аудіодоріжку зі звуком обертання двигунів та аеродинамічного шуму;
- момент фізичного контакту з перешкодою, руйнування конструкції рами чи відриву лопатей;
- поведінку підвісу камери та вібраційне тремтіння зображення (ефект «желе», англ. *jell-o effect*).

Відео надає об'єктивну картину зовнішнього середовища, яку не здатні зафіксувати бортові давачі. Завдяки незалежному живленню камери запис триває навіть після повної загибелі силового акумулятора дрона. Проте сам по собі відеоряд не містить внутрішніх числових значень кутових помилок регулятора, струмів фаз двигунів чи інновацій фільтрації.

Особливу цінність має аудіодоріжка: спектральний аналіз звуку пропелерів дозволяє безпосередньо виміряти швидкість обертання двигунів за частотою проходження лопатей гвинта (англ. *blade passing frequency*), що забезпечує незалежну перевірку телеметрії ESC.

```
Зіставлення властивостей трьох джерел інформації:

Властивість               Бортовий лог (.bin)          Лог станції (.tlog)          Відеозапис (MP4)
────────────────────────────────────────────────────────────────────────────────────────────────────────
Частота дискретизації     50–400 Гц (до 2 кГц)         2–10 Гц                      30–60 кадрів/с (+ 48 кГц аудіо)
Базова шкала часу         t_boot (монотонна, мкс)      t_utc (стінна епоха, мс)     t_pts (таймкоди кадрів)
Вразливість до аварії     Втрата фінального буфера     Низька (пишеться на землі)   Низька (автономне живлення)
Латентність каналу        0 мс (внутрішня шина)        100–300 мс (радіомодем)      0–35 мс (затримка матриці)
Спостережуваність         Внутрішній стан автоматів    Дії пілота, радіоефір        Фізичне середовище, геометрія
```

> 🔧 **Навіщо це.** Спроба аналізу аварії без відео не дозволяє відрізнити зіткнення з невидимою гілкою від зриву синхронізації мотора; аналіз без бортового логу не дає зрозуміти, чому апарат нахилився; а розбір без логу станції приховує той факт, що оператор увімкнув аварійний режим за дві секунди до катастрофи, але команда застрягла в буфері радіомодема.

## Алгоритм злиття та вирівнювання шкал (Timeline Alignment)

Головна технічна перешкода реконструкції — відсутність спільного генератора тактових імпульсів. Три пристрої використовують різні кварцові резонатори, які мають довільний початковий зсув `β` та постійно розходяться зі швидкістю відносного дрейфу `α = 1 + (Δf / f)`.

Для точного зшивання застосовують двоступеневий алгоритм: спершу грубе дискретне зіставлення за опорними подіями (англ. *anchor events*), а потім точне неперервне узгодження взаємною кореляцією та лінійною регресією найменших квадратів.

![Вирівнювання часових шкал за опорними подіями](/root/course/embedded/vidtvorennia-intsydentu-z-trokh-dzherel/img/timeline-alignment-anchors.svg)
*Вирівнювання трьох несинхронізованих шкал часу (t_boot, t_gcs, t_pts) за спільними дискретними опорними маркерами*

### Етап 1. Пошук дискретних опорних маркерів

Опорна подія — це фізичний або логічний стан системи, який одночасно і недвозначно відображається у всіх трьох потоках:

1. **Армінг моторів (Arming State Transition):**
   - *Бортовий лог:* біт армінгу в регістрі стану переходить у `1`, з'являється запис `STATUSTEXT: "Arming motors"`, завдання на мотори `RCOU` зростає від 1000 до 1150 мкс.
   - *Лог станції:* надходить пакет `HEARTBEAT` із прапорцем `MAV_MODE_FLAG_SAFETY_ARMED`, GCS видає звукове сповіщення.
   - *Відеозапис:* на аудіодоріжці з'являється тональний сплеск розкрутки моторів (наприклад, 180 Гц), пропелери в кадрі розмиваються в суцільний диск, на OSD напис `DISARMED` змінюється на `ARMED`.

2. **Зміна польотного режиму (Flight Mode Switch):**
   - *Бортовий лог:* зміна поля `MODE.Mode` (наприклад, перехід із `PosHold` у `RTL` або `Manual`).
   - *Лог станції:* фіксація команди `COMMAND_LONG (MAV_CMD_DO_SET_MODE)` та відповіді `COMMAND_ACK`.
   - *Відеозапис:* зміна текстового маркеру режиму на накладеному OSD або характерний ривок рами за тангажем.

3. **Втрата радіозв'язку та перехід у Failsafe:**
   - *Бортовий лог:* повідомлення `FS.State = 1` або `EV: 10` (Radio Failsafe).
   - *Лог станції:* тайм-аут пакета `HEARTBEAT` (припинення оновлення телеметрії на екрані).
   - *Відеозапис:* OSD виводить блимаюче попередження `FAILSAFE` або відеолінк переходить у режим шуму.

4. **Фізичний удар / катастрофічний струс (Crash Shockwave):**
   - *Бортовий лог:* зашкалювання акселерометра `IMU.AccZ` понад 16g, миттєве блокування обертів двигунів `ESC.RPM = 0`.
   - *Лог станції:* повне припинення прийому телеметрії.
   - *Відеозапис:* різкий зсув або обрив кадру, звук механічного удару в аудіотракті.

### Етап 2. Взаємна кореляція та лінійна регресія дрейфу

Маючи набір опорних подій `(t_boot[i], t_gcs[i], t_pts[i])`, виконують аналітичне вирівнювання:

![Взаємна кореляція сигналів та лінійна регресія дрейфу кварцу](/root/course/embedded/vidtvorennia-intsydentu-z-trokh-dzherel/img/clock-drift-cross-correlation.svg)
*Двоступенева синхронізація: пошук зсуву за максимумом взаємної кореляції R_xy(τ) та усунення дрейфу методом найменших квадратів*

1. **Взаємна кореляція сигналів кутової швидкості:**
   Для компенсації затримки передачі телеметрії обчислюють нормовану кореляцію між бортовим сигналом гіроскопа `GyroX(t_boot)` та телеметричним каналом `ATTITUDE.rollspeed(t_gcs)`:
   
   ```
   R_xy[k] = (1 / (N · σ_x · σ_y)) · ∑ (x[n] - μ_x) · (y[n + k] - μ_y)
   k_opt = argmax_k ( R_xy[k] )    [знаходження оптимального фазового зсуву]
   ```

2. **Компенсація дрейфу кварцу:**
   Зв'язок між шкалами описується лінійним перетворенням `t_gcs = α · t_boot + β`. Коефіцієнти `α` (масштаб дрейфу) та `β` (початкове зміщення) обчислюють за методом найменших квадратів:
   
   ```
   α = ( ∑ (t_boot[i] - t̄_boot) · (t_gcs[i] - t̄_gcs) ) / ( ∑ (t_boot[i] - t̄_boot)² )
   β = t̄_gcs - α · t̄_boot
   ```

Детальне математичне виведення взаємної кореляції, субдискретної інтерполяції піка та розрахунку спектрального зв'язку між аудіодоріжкою й обертами ESC наведено у вставці [🧮 математичне виведення взаємної кореляції та регресії дрейфу](root:embedded/vidtvorennia-intsydentu-z-trokh-dzherel/math-cross-correlation-time-sync.md).

## Типові патерни відмов у синхронізованих логах

Коли часові шкали вирівняні з мілісекундною точністю, кожна фізична або програмна аварія демонструє чіткий мультимодальний підпис.

### Патерн 1. Раптовий обрив живлення проти зависання процесора

Найпоширеніша дилема при розслідуванні апаратних відмов: чи завис мікроконтролер через помилку у коді (HardFault / Kernel Panic), чи відбулося механічне розімкнення силового кола батареї (відрив роз'єму XT60/XT90, згоряння перетворювача BEC 5V).

![Мультимодальна сигнатура раптового знеструмлення](/root/course/embedded/vidtvorennia-intsydentu-z-trokh-dzherel/img/power-loss-signature.svg)
*Синхронний відгук трьох систем на раптове знеструмлення силової шини*

```
Мультимодальні ознаки обриву живлення проти зависання процесора:

Критерій перевірки       Раптове знеструмлення (Power Loss)        Програмне зависання (CPU Lockup / Panic)
───────────────────────────────────────────────────────────────────────────────────────────────────────────
Бортовий лог (.bin)      Раптовий обрив запису посеред сектора,    Останній запис містить стек-трейс або 
                         відсутній прапорець завершення файлу;     `CRASH_DUMP` у Flash; Watchdog викликає
                         напруга падає до 0 за 0.5–2 мс            перезавантаження та новий файл логу
Лог станції (.tlog)      Телеметрія обривається при 100% якості    Перед обривом зростає CPU Load > 99%,
                         зв'язку (RSSI) без попереджень            можлива серія повідомлень `Internal Error`
Відеозапис (камера)      Автономна камера фіксує перекидання;      Камера фіксує некерований політ із
                         звук моторів миттєво зникає               працюючими моторами до удару об землю
```

При апаратному знеструмленні конденсатори фільтра живлення розряджаються за час `t = C · (V_in - V_min) / I_load`. Для типового польотного контролера (`C = 220` мкФ, `I = 350` мА) цей інтервал становить від 1.5 до 3 мілісекунд. Процесор встигає зафіксувати стрімке падіння напруги в повідомленні `BAT`, після чого робота флеш-контролера апаратно блокується схемою Brownout Reset (BOR). На відеозаписі в цей же момент чутно повне зникнення інверторного гулу двигунів, а пропелери миттєво зупиняються набігаючим потоком повітря.

Якщо ж стався програмний збій ядра (наприклад, нескінченний цикл обробника переривань або пошкодження стека RTOS), апаратний таймер Watchdog спрацьовує через 500–1000 мс і виконує скидання мікроконтролера. При цьому живлення залишається в нормі, а в лог записується статусний код перезавантаження з прапорцем `WDG_RESET`.

### Патерн 2. Зрив давача та EKF-розбіжність («унітазинг»)

Коли польотний контролер перебуває в автоматичному режимі утримання позиції (`PosHold` або `Auto Mission`), розширений фільтр Калмана безперервно порівнює вимірювання магнітометра, акселерометра та супутникового приймача GPS. Якщо компас зазнає спотворення від магнітного поля силових проводів або залізобетонних конструкцій, виникає геометрична неузгодженість між вектором курсу за магнітометром і вектором шляхової швидкості за GPS.

![Сигнатура розбіжності EKF та виникнення спіралі унітазингу](/root/course/embedded/vidtvorennia-intsydentu-z-trokh-dzherel/img/ekf-divergence-toilet-bowl.svg)
*Синхронне розгортання спіралі «унітазингу» в просторі та стрімке зростання інновацій EKF у логу*

Розвиток відмови відбувається за ланцюгом:
1. Магнітометр передає спотворений курс зі зсувом на `Δψ = 35°`.
2. Автопілот вважає, що апарат зносить убік, і видає завдання на крен для компенсації уявного зносу.
3. Фізичний рух утворює реальну швидкість за GPS, яка суперечить оцінці інерціального блоку.
4. В інноваціях швидкості фільтра Калмана (`XKF4.SV`) виникає стрімке зростання нев'язки. Щойно нормалізований інноваційний індекс перевищує одиницю (`SM_Ratio > 1.0`), фільтр відкидає вимірювання GPS як недостовірні.
5. Дрон входить у розбіжну спіраль із постійно зростаючим радіусом та швидкістю (явище «унітазингу», англ. *toilet-bowling*).
6. *На відео:* камера фіксує обертання по колу з креном 30–45°, тоді як на OSD штучний горизонт показує абсолютно рівний політ.

Якщо фільтр EKF налаштований на автоматичне перемикання смуг оцінки (англ. *lane switching*), у логу з'являється серія повідомлень `EKF primary changed from 0 to 1`. Якщо всі доступні магнітометри зазнали однакової магнітної завади, система оголошує аварійний режим `EKF Failsafe` і переходить у ручне керування або екстремальну посадку.

### Патерн 3. Команда пілота проти відмови автопілота

При розслідуванні зіткнень із землею або спорудами (англ. *Controlled Flight Into Terrain, CFIT*) ключове завдання — визначити, чи сталася аварія через помилкову команду людини, чи через збій контуру стабілізації автопілота.

![Диференціація провини: команда пілота проти збою регулятора](/root/course/embedded/vidtvorennia-intsydentu-z-trokh-dzherel/img/pilot-vs-autopilot-collision.svg)
*Зіставлення сигналів стіків RCIN, цільової кутової швидкості RATE.Des та реального руху рами*

Розслідування будується на порівнянні трьох сигналів у часі:
- **Вхідний стік пілота (`RCIN.C1..C4`):** бажання оператора (наприклад, стік крену відхилено вправо на 1850 мкс).
- **Цільова швидкість регулятора (`RATE.RDes`):** математичне завдання, сформоване прошивкою на основі стіка.
- **Фактична кутова швидкість гіроскопа (`RATE.R` або `IMU.GyrX`):** фізична реакція апарата в просторі.
- **Виходи на мотори (`RCOU.C1..C4` або `MOT.Mot1..4`):** реакція мікшера.

*Сценарій А (Помилка пілота):* стік відхилено → `RATE.RDes` зростає → `RATE.R` точно повторює завдання з лагом 25–40 мс → виходи моторів пропорційно навантажують відповідний бік рами → дрон нахиляється і врізається в перешкоду. Висновок: автопілот повністю контролював апарат і справно виконав команду людини, яка не помітила перешкоду.

*Сценарій Б (Відмова силовика / ESC Desync):* стік стоїть у нейтралі (1500 мкс) → `RATE.RDes = 0` → фактичний гіроскоп `RATE.R` демонструє раптовий неконтрольований сплеск 400 °/с → мікшер викручує мотор №1 на 100% (`RCOU = 2000` мкс), намагаючись скомпенсувати перекидання → апарат продовжує обертатися і падає. Висновок: мотор не створив необхідної тяги внаслідок зриву комутації або руйнування лопаті (пілот не винен).

## Інструменти візуалізації та автоматичної діагностики

Для практичного розслідування інцидентів застосовують спеціалізовані програмні комплекси, що підтримують інтеграцію мультимодальних потоків:

1. **PlotJuggler з плагіном відеосинхронізації:** відкриває бінарні логи ULog/DataFlash разом із відеофайлом MP4. Переміщення курсора по осі часу на графіках одночасно позиціонує відповідний відеокадр, підсвічуючи миттєві значення сигналів у точці спостереження.
2. **MAVExplorer та FlightPlot:** потужні консольні інструменти з підтримкою виразів на Python для швидкої фільтрації інновацій EKF та розрахунку FFT-спектрів вібрацій.
3. **QGroundControl / Mission Planner Replay:** дозволяють завантажити `.tlog` і «переграти» політ у реальному часі на віртуальній карті місцевості з тривимірним відображенням орієнтації апарата.

Для повної автоматизації розслідування формують стандартизований звіт у форматі JSON, який містить усі часові трансформації, знайдені опорні маркери та класифіковані аномалії. ## Консольний інструмент злиття та аналізу трьох логів

Нижче наведено базовий модуль синхронізації та експертної діагностики утиліти `incident_fuser`, реалізований мовами C++20 та Python:

:::tabs
```cpp
#include <iostream>
#include <vector>
#include <string>
#include <cmath>
#include <numeric>
#include <span>

struct AnchorEvent {
    std::string name;
    uint64_t t_boot_us;
    uint64_t t_gcs_ms;
};

struct AlignmentModel {
    double alpha_drift;
    double beta_offset_ms;
    double residual_rms_ms;
};

class LogFusionEngine {
public:
    static AlignmentModel calculate_time_warp(std::span<const AnchorEvent> anchors) {
        const size_t p = anchors.size();
        if (p < 2) return {1.0, 0.0, 0.0};

        double sum_tb = 0.0, sum_tg = 0.0;
        for (const auto& a : anchors) {
            sum_tb += static_cast<double>(a.t_boot_us) / 1000.0;
            sum_tg += static_cast<double>(a.t_gcs_ms);
        }

        const double mean_tb = sum_tb / p;
        const double mean_tg = sum_tg / p;

        double cov = 0.0, var_tb = 0.0;
        for (const auto& a : anchors) {
            double tb = (static_cast<double>(a.t_boot_us) / 1000.0) - mean_tb;
            double tg = static_cast<double>(a.t_gcs_ms) - mean_tg;
            cov += tb * tg;
            var_tb += tb * tb;
        }

        const double alpha = (var_tb > 1e-9) ? (cov / var_tb) : 1.0;
        const double beta = mean_tg - alpha * mean_tb;

        double sum_sq = 0.0;
        for (const auto& a : anchors) {
            double tb = static_cast<double>(a.t_boot_us) / 1000.0;
            double diff = static_cast<double>(a.t_gcs_ms) - (alpha * tb + beta);
            sum_sq += diff * diff;
        }

        return {alpha, beta, std::sqrt(sum_sq / p)};
    }
};
```
```py
import math
from dataclasses import dataclass
from typing import List

@dataclass
class AnchorEvent:
    name: str
    t_boot_us: int
    t_gcs_ms: int

@dataclass
class AlignmentModel:
    alpha_drift: float
    beta_offset_ms: float
    residual_rms_ms: float

class LogFusionEngine:
    @staticmethod
    def calculate_time_warp(anchors: List[AnchorEvent]) -> AlignmentModel:
        p = len(anchors)
        if p < 2:
            return AlignmentModel(1.0, 0.0, 0.0)

        tb_list = [a.t_boot_us / 1000.0 for a in anchors]
        tg_list = [float(a.t_gcs_ms) for a in anchors]

        mean_tb = sum(tb_list) / p
        mean_tg = sum(tg_list) / p

        cov = sum((tb - mean_tb) * (tg - mean_tg) for tb, tg in zip(tb_list, tg_list))
        var_tb = sum((tb - mean_tb) ** 2 for tb in tb_list)

        alpha = (cov / var_tb) if var_tb > 1e-9 else 1.0
        beta = mean_tg - alpha * mean_tb

        sum_sq = sum((tg - (alpha * tb + beta)) ** 2 for tb, tg in zip(tb_list, tg_list))
        return AlignmentModel(alpha, beta, math.sqrt(sum_sq / p))
```
