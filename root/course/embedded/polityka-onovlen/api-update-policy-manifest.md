# 📋 Специфікація маніфесту політики оновлень та критеріїв допуску

Маніфест політики оновлення — це машинозчитуваний контракт між хмарним сервером оркестрації та локальним агентом оновлення на кінцевому пристрої. Він визначає не лише двійковий образ для запису у Flash-пам'ять, але й суворий набір фізичних, енергетичних, часових та криптографічних правил, за яких дозволено модифікацію мікропрограми.

Відокремлення метаданих політики від самого двійкового коду прошивки є критичним архітектурним рішенням. Без маніфесту пристрій змушений завантажувати повний образ розміром у кілька мегабайтів лише для того, щоб під час перевірки заголовка виявити несумісність апаратної ревізії чи недостатній рівень заряду акумулятора. Маніфест передається першим компактним пакетом (зазвичай від 500 байтів до 2 кілобайтів), що дозволяє кінцевому вузлу ухвалити рішення про допуск до оновлення ще до початку тривалої та енергоємної передачі основного коду.

## Життєвий цикл обробки маніфесту на пристрої

Обробка вхідного маніфесту вбудованим агентом оновлення виконується за строго детермінованим конвеєром:

1. **Синтаксичний розбір та валідація схеми:** Перевірка цілісності структури, наявності обов'язкових числових ключів та версії схеми `manifest_version`. Якщо версія маніфесту новіша за підтримувану завантажувачем, запит відхиляється.
2. **Криптографічна верифікація підпису:** Обчислення хешу від канонічного бінарного представлення маніфесту та перевірка асиметричного цифрового підпису Ed25519 за допомогою публічного ключа виробника, прошитого в захищеній пам'яті OTP/eFuse. Помилка верифікації негайно зупиняє конвеєр без розбору подальших полів.
3. **Апаратна ідентифікація та анти-відкат:** Звірення рядка сімейства плати `hardware_family`, бітової маски підтримуваних ревізій друкованої плати `hardware_revision_mask` та перевірка монотонного лічильника безпеки `security_version` для захисту від атак зниження версії (*Anti-Rollback Protection*).
4. **Оцінка фізичних передумов (Preconditions):** Вимірювання напруги живлення під активним навантаженням радіомодуля, перевірка залишкового відсотка заряду батареї, температури кристала та поточного операційного стану виконавчих механізмів.
5. **Планування виконання та відповідь хмарі:** Якщо всі критерії задоволено, агент переводить систему в стан очікування регламентного вікна або негайно розпочинає завантаження основного образу, відправляючи серверу телеметричний звіт зі статусом `STATUS_ACCEPTED_PENDING_WINDOW` або `STATUS_INSTALLING_NOW`.

## Структура маніфесту (формат JSON / CBOR)

Нижче наведено повну декларацію схеми маніфесту версії 2.0. У польових пристроях з обмеженою пропускною здатністю текстовий JSON транслюється в бінарний компактний формат CBOR (RFC 8949) зі збереженням числових ідентифікаторів ключів для мінімізації накладних витрат пам'яті.

## Довідник полів та типів даних

### Секція ідентифікації та сумісності (`target`)

Ця секція містить апаратні обмеження, що унеможливлюють запис образу в несумісну мікросхему або плату іншої ревізії:

- `hardware_family` (`string`): Унікальний текстовий ідентифікатор платформи. Звіряється з апаратним рядком, зашитим у постійній пам'яті OTP (One-Time Programmable) мікроконтролера на етапі виробництва.
- `hardware_revision_mask` (`uint32` / `hex string`): Бітова маска сумісних ревізій плати. Кожен біт відповідає номеру схемної ревізії (`bit 0` — ревізія 1.0, `bit 1` — ревізія 1.1 тощо). Якщо біт, що відповідає поточному стану апаратних пінів вибору ревізії (*HW Strapping Pins*), дорівнює нулю, пристрій повертає `REJECT_HW_MISMATCH`.
- `min_bootloader_version` (`string`): Мінімальна версія первинного завантажувача (Bootloader), необхідна для коректного перемикання векторів переривань, керування лініями живлення та підтримки поточної таблиці розмітки Flash-пам'яті.
- `target_bank` (`enum`): Вказує цільовий сектор або банк пам'яті: `BANK_A`, `BANK_B` або `AUTO_INACTIVE`. Опція `AUTO_INACTIVE` вказує завантажувачу обрати банк, протилежний до поточного виконуваного, що є стандартом для безшовного A/B-оновлення.

### Секція класифікації релізу (`classification`)

Параметри терміновості та юридичного пріоритету оновлення:

- `severity` (`enum`): Рівень важливості випуску. Визначає поведінку таймерів відкладення та пороги енергетичних бар'єрів:
  - `CRITICAL_SECURITY` (Пріоритет 4): Критичний Zero-Day патч. Ігнорує поточні завдання (крім аварійних), знижує поріг заряду АКБ до 30%, блокує можливість користувацького відкладення.
  - `SECURITY_STANDARD` (Пріоритет 3): Плановий патч безпеки. Дозволяє обмежену кількість відкладень (1..3 рази), після чого виконується примусово.
  - `MAINTENANCE` (Пріоритет 2): Планове технічне обслуговування. Вимагає суворого дотримання нічного регламентного вікна та заряду АКБ понад 50%.
  - `FEATURE` (Пріоритет 1): Новий функціонал. Вимагає явної згоди оператора та повної зупинки технологічного процесу.
- `cvss_score` (`float`): Числова оцінка вразливості за стандартом CVSS v3.1 (від 0.0 до 10.0). Використовується для аудиту та автоматичної класифікації.
- `requires_user_consent` (`boolean`): Прапорець обов'язкового підтвердження від людини через локальний HMI (екран, кнопки) або мобільний застосунок оператора.
- `max_postpone_count` (`uint8`): Максимальна кількість разів, яку локальний користувач може натиснути кнопку «Відкласти на 1 годину». При досягненні ліміту наступне оновлення запускається директивно.

### Секція апаратних передумов (`preconditions`)

Фізичні критерії безпеки, що перевіряються локальним мікроконтролером перед початком сесії стирання та запису пам'яті:

- `power_source_required` (`array of enum`): Список дозволених джерел живлення: `AC_MAINS` (стаціонарна електромережа), `BATTERY_CHARGING` (йде активний процес заряджання), `BATTERY_HEALTHY` (автономна батарея без ознак внутрішньої деградації).
- `min_battery_soc_pct` (`uint8`): Мінімальний відсоток заряду акумулятора (State of Charge, 0..100%). Забезпечує запас енергії на завантаження, запис Flash, виконання самотестування та аварійний відкат у разі збою.
- `min_battery_voltage_mv` (`uint16`): Абсолютна мінімальна напруга на виводах живлення в мілівольтах, виміряна під час пікового навантаження (активний радіопередавач). Запобігає спрацьовуванню детектора просідання живлення (*Brownout Reset — BOR*) під час імпульсів струму стирання Flash-пам'яті.
- `temperature_range_c` (`array of int8`): Допустимий інтервал температури навколишнього середовища та кристала `[T_min, T_max]`. Блокує оновлення на сильному морозі (нижче -10 °C) або під час перегріву (вище +55 °C), коли фізика тунелювання електронів у Flash-комірках стає нестабільною.
- `required_operating_state` (`array of enum`): Дозволені стани кінцевого автомату системи (`STATE_IDLE`, `STATE_STANDBY`, `STATE_SAFE_STOP`). Забороняє оновлення, якщо пристрій перебуває в стані активної місії (`STATE_ACTIVE_MISSION`) або аварії (`STATE_EMERGENCY`).
- `allowed_network_bearers` (`array of enum`): Маска дозволених інтерфейсів передачі даних: `ETHERNET`, `WIFI`, `CELLULAR_UNMETERED`, `CELLULAR_METERED`. Дозволяє заборонити завантаження великих функціональних оновлень через дорогі канали супутникового або роумінгового зв'язку.

### Секція лімітів часу та бюджету виконання (`execution_budget`)

- `max_download_time_sec` (`uint16`): Максимальний час на приймання всього бінарного образу. Якщо через нестабільний радіоканал завантаження триває довше, сесія скидається для запобігання виснаженню батареї.
- `max_flash_write_time_sec` (`uint16`): Граничний час на стирання секторів та посторінковий запис образу у Flash-пам'ять.
- `self_test_timeout_sec` (`uint16`): Час, який завантажувач виділяє новій прошивці після першого старту для успішного проходження самодіагностики та встановлення прапорця `BOOT_SUCCESS`. Якщо за цей час прошивка впаде або зависне, завантажувач виконає автоматичний апаратний відкат на попередній банк.
- `watchdog_timeout_sec` (`uint16`): Період спрацьовування апаратного сторожового таймера (Watchdog) під час процедури оновлення.

## Коди результатів валідації маніфесту (Status Codes)

Після обробки маніфесту агент оновлення надсилає на сервер телеметричний пакет із числовим кодом статусу рішення:

```
0x00: STATUS_ACCEPTED_PENDING_WINDOW  — Маніфест верифіковано, очікування регламентного вікна
0x01: STATUS_INSTALLING_NOW           — Усі умови виконано, розпочато завантаження та прошивання
0x10: REJECT_SIGNATURE_INVALID        — Помилка перевірки підпису Ed25519 (підробка або пошкодження)
0x11: REJECT_HW_MISMATCH              — Невідповідність апаратного сімейства або маски ревізії
0x12: REJECT_ANTI_ROLLBACK            — Спроба встановлення образу зі старішим індексом безпеки
0x20: REJECT_INSUFFICIENT_BATTERY     — Рівень заряду або напруга АКБ нижчі за встановлений поріг
0x21: REJECT_TEMPERATURE_OUT_OF_BOUNDS — Температура плати виходить за межі безпечного інтервалу
0x30: POSTPONE_BUSY_STATE             — Пристрій зайнятий виконанням критичного техпроцесу
0x31: POSTPONE_USER_REQUESTED         — Користувач скористався правом тимчасового відкладення
0x40: ERROR_FLASH_WRITE_TIMEOUT       — Перевищено ліміт часу на запис Flash-пам'яті
0x41: ERROR_SELF_TEST_FAILED          — Новий образ не пройшов вбудований тест (виконано відкат A/B)
```

## Правила бінарної серіалізації в CBOR

Для передавання каналами з високою вартістю байта (LoRaWAN, NB-IoT, супутниковий зв'язок) застосовується нормалізований профіль CBOR. Усі текстові рядкові ключі замінюються цілими числами:

```
1: manifest_version (uint)
2: release_id (text string)
3: target (map) -> 1: hardware_family, 2: hardware_revision_mask, 3: min_bootloader_version, 4: target_bank
4: classification (map) -> 1: severity, 2: cvss_score, 3: max_postpone_count
5: preconditions (map) -> 1: power_source, 2: min_soc, 3: min_mv, 4: temp_range, 5: allowed_bearers
6: payload (map) -> 1: version, 2: size, 3: sha256 (byte string, 32 bytes)
7: signatures (array of maps) -> 1: key_id, 2: sig (byte string, 64 bytes)
```

Така бінарна компресія зменшує розмір повного маніфесту з 1400 байтів у текстовому JSON до 210 байтів у CBOR, дозволяючи передати повну специфікацію політики оновлення в межах одного радіокадру.
