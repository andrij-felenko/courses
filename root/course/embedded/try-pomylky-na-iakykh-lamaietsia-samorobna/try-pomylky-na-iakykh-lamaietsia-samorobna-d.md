# Три помилки, на яких ламається саморобна криптографія

<preknowlist>
- [Ключований хеш і код автентичності (MAC)](root:sf-security/keyed-hash-mac) — контроль цілісності та перевірка авторства на спільному секреті.
- [Блоковий і потоковий шифр](root:sf-security/block-cipher) — режими роботи шифрів, перетворення блоків та формування ключової гами.
- [AEAD: шифрування, що водночас доводить автентичність](root:sf-security/authenticated-encryption) — об'єднання конфіденційності та контролю цілісності в єдиний криптографічний примітив.
- [Повтор, nonce й плаваючий код](root:sf-security/replay-protection) — чому повідомлення вимагають унікального лічильника й захисту від перехоплення.
- [Чого варта команда без підпису](root:embedded/choho-varta-komanda-bez-pidpysu) — загрози підробки й маніпуляцій у відкритому бездротовому ефірі.
</preknowlist>

Коли розробник вбудованої системи вперше стикається з потребою захистити канал зв'язку — наприклад, радіолінк між пультом і приводом замка, канал оновлення прошивки чи телеметрію промислового контролера, — виникає сильна спокуса «не тягнути важких бібліотек». Пам'ять мікроконтролера обмежена ліченими десятками кілобайтів, процесорний час на рахунку, а криптографічні стандарти на зразок TLS здаються надлишковими монстрами для передачі пакета на тридцять два байти. 

У цей момент народжується фатальне рішення: написати простий власний протокол. Інженер бере відомий симетричний шифр (або, що ще гірше, вигадує власний «незламний» XOR із секретною таблицею), загортає його в саморобний формат кадру й додає перевірку контрольної суми. На тестовому стенді все працює бездоганно: байти в радіоефірі виглядають суцільним білим шумом, дані передаються швидко, пам'яті витрачено лічені кілобайти. 

Проте під час першого ж практичного аудиту такий захист розсипається за лічені хвилини. Нападникові не потрібно факторизувати тисячорозрядні числа чи підбирати 256-бітний ключ перебором. Саморобна криптографія майже ніколи не ламається через математичну слабкість фундаментальних шифрів — вона руйнується через три класичні інженерні пастки реалізації: повторне використання одноразового вектора ініціалізації, кустарні алгоритми та витоки інформації через час виконання функцій.

### Пастка перша: повторне використання Nonce

Більшість сучасних симетричних шифрів, що застосовуються у вбудованих пристроях, належать або до суто потокових алгоритмів (як-от ChaCha20), або до блокових шифрів у режимі лічильника (AES-CTR) чи автентифікованого лічильника (AES-GCM). Принцип їхньої роботи єдиний: секретний ключ `K` разом із числовим параметром перетворюється шифром на псевдовипадкову послідовність байтів — **ключову гаму** (англ. *keystream*) `S`. 

Зашифрування відкритого тексту `P` полягає у звичайному побітовому додаванні за модулем 2 (операція XOR, позначається як `⊕`) тексту `P` та згенерованої гами `S`:

```
C = P ⊕ S
```

Цей числовий параметр, що подається на вхід генератора гами разом із ключем, зветься **одноразовим числом** або **нонсом** (англ. *nonce* — від виразу *number used once*, число, що використовується рівно один раз; інша назва у блокових шифрах — **вектор ініціалізації**, англ. *Initialization Vector*, IV). 

Головна вимога безпеки потокового шифрування звучить категорично: **одна й та сама комбінація пари (Ключ, Nonce) ніколи, за жодних обставин, не повинна використовуватися для шифрування двох різних повідомлень**. Якщо це правило порушено, криптографічний захист знищується миттєво без будь-якого знання секретного ключа `K`.

#### Математика знищення таємниці при повторі гами

Припустимо, мікроконтролер відправив два різних пакети `P₁` та `P₂`, використавши однаковий Nonce на тому самому сеансовому ключі. Оскільки вхідні параметри генератора гами збіглися, генератор виробив абсолютно ідентичну гаму `S` для обох пакетів:

```
C₁ = P₁ ⊕ S
C₂ = P₂ ⊕ S
```

Нападник перехоплює обидва шифротексти `C₁` та `C₂` з радіоефіру й виконує операцію XOR між ними. Погляньмо на покроковий результат цього перетворення:

```
C₁ ⊕ C₂
= (P₁ ⊕ S) ⊕ (P₂ ⊕ S)     [підстановка формул шифрування]
= P₁ ⊕ P₂ ⊕ (S ⊕ S)       [асоціативність та комутативність операції XOR]
= P₁ ⊕ P₂ ⊕ 0             [властивість самознищення однакових операндів: S ⊕ S = 0]
= P₁ ⊕ P₂                 [додавання нейтрального елемента: x ⊕ 0 = x]
```

Сталася повна криптографічна катастрофа: секретна гама `S` повністю скоротилася. Нападник отримав чисте значення `P₁ ⊕ P₂` — результат побітового додавання двох відкритих повідомлень.

![Катастрофа повторного використання Nonce: побітовий XOR двох шифротекстів знищує ключову гаму й оголює відкриті тексти](/root/course/embedded/try-pomylky-na-iakykh-lamaietsia-samorobna/img/nonce-reuse-xor.svg)
*При повторному використанні одного Nonce генератор шифру видає однакову псевдовипадкову гаму S для обох пакетів. Побітовий XOR двох перехоплених шифротекстів повністю знищує гаму й залишає чисту суму відкритих текстів P₁ ⊕ P₂.*

У протоколах вбудованих пристроїв повідомлення рідко бувають випадковими. Зазвичай пакети мають сувору структуру: перші байти займає фіксований заголовок протоколу, магічне число (англ. *magic number*), ідентифікатор команди або назви полів у JSON-рядку на зразок `{"cmd":"status",`.

Якщо нападникові відомий або вдалося вгадати відкритий текст першого пакета `P₁` (наприклад, стандартний заголовок відповіді датчика), розкриття другого пакета `P₂` стає тривіальною дією:

```
(C₁ ⊕ C₂) ⊕ P₁
= (P₁ ⊕ P₂) ⊕ P₁          [оскільки C₁ ⊕ C₂ = P₁ ⊕ P₂]
= P₂ ⊕ (P₁ ⊕ P₁)          [перегрупування доданків]
= P₂ ⊕ 0
= P₂                      [повне відновлення другого повідомлення]
```

Навіть якщо відкритий текст невідомий повністю, відновлення обох повідомлень із `P₁ ⊕ P₂` здійснюється частотним аналізом, евристиками перекриття слів (англ. *crib dragging*) або пошуком друкованих ASCII-символів за частки секунди. Ба більше: відновивши відкритий текст `P₁`, нападник обчислює саму гаму `S = C₁ ⊕ P₁` і тепер може самостійно зашифрувати будь-яке фальшиве повідомлення `P_fake` з тим самим Nonce: `C_fake = P_fake ⊕ S`.

#### Пластичність шифротексту (Malleability)

У потокових шифрах без автентифікації шифротекст має властивість **пластичності** (англ. *malleability*): зміна біта в шифротексті призводить до точної зміни відповідного біта у відкритому тексті після розшифрування. 

Нехай пакет містить команду відкриття дверей: `P = [0x00]` (закрито). Зашифрований байт `C = 0x00 ⊕ S = S`. Нападник, не знаючи ключа `K` і гами `S`, просто інвертує молодший біт у перехопленому шифротексті: `C' = C ⊕ 0x01`. 

Коли пристрій розшифрує модифікований шифротекст `C'`, він виконає операцію:

```
P' = C' ⊕ S = (C ⊕ 0x01) ⊕ S = (P ⊕ S ⊕ 0x01) ⊕ S = P ⊕ 0x01 = [0x01]
```

Пристрій слухняно інтерпретує значення `0x01` як команду «відкрито» і розблокує замок. Нападникові не знадобилося розшифровувати пакет — він маніпулював логікою пристрою наосліп.

#### Катастрофа повтору Nonce в AES-GCM

Якщо у звичайному AES-CTR повтор Nonce розкриває лише зміст конкретних перехоплених повідомлень, то в режимі автентифікованого шифрування AES-GCM (англ. *Galois/Counter Mode*) наслідки є значно глибшими: **нападник повністю відновлює ключ автентифікації**.

В основі механізму автентифікації GCM лежить геш-функція GHASH, яка обчислює значення полінома у полі Галуа `GF(2¹²⁸)`. Коефіцієнтами цього полінома виступають блоки додаткових даних (AAD) та шифротексту (C), а невідомою змінною — геш-ключ `H = AES_K(0¹²⁸)`. Фінальний автентифікаційний тег `T` формується додаванням до результату GHASH зашифрованого нульового лічильника:

```
T = GHASH(H, AAD, C) ⊕ AES_K(J₀)
```

де `J₀` — початковий 128-бітний блок лічильника, сформований із 96-бітного Nonce.

Якщо два різних повідомлення зашифровано з однаковим Nonce, значення маскувального блока `AES_K(J₀)` є однаковим для обох тегів `T₁` та `T₂`. Додавши ці два теги, нападник отримує:

```
T₁ ⊕ T₂ = GHASH(H, AAD₁, C₁) ⊕ GHASH(H, AAD₂, C₂)
```

Оскільки GHASH є лінійною функцією відкритого аргументу в полі `GF(2¹²⁸)`, вираз праворуч перетворюється на поліноміальне рівняння відносно єдиної невідомої `H`. Розв'язавши це поліноміальне рівняння (знаходженням коренів над скінченним полем `GF(2¹²⁸)`), нападник обчислює секретний ключ `H`. 

Маючи `H`, нападник отримує можливість самостійно обчислювати дійсні автентифікаційні теги для будь-яких довільних шифротекстів. Режим автентифікованого шифрування повністю втрачає свою цілісність, а шифр перетворюється на незахищений канал.

#### Чому це постійно стається у мікроконтролерах

Розробники рідко використовують однаковий Nonce навмисно. У вбудованих пристроях повтор трапляється через фізичні обмеження мікроконтролерних платформ:

1. **Скидання лічильника при перезавантаженні.** Найпростіший спосіб сформувати унікальний Nonce — звичайний 32- або 64-бітний інкрементний лічильник `counter++` в оперативній пам'яті (SRAM). Проте мікроконтролер періодично перезавантажується — через короткочасні просадки живлення (англ. *brownout*), спрацювання сторожового таймера (WDT) або перезапуск користувачем. Після рестарту оперативна пам'ять обнуляється, лічильник знову починає рахувати з нуля, і всі згенеровані Nonce повторюються.
2. **Відсутність енергонезалежного годинника реального часу (RTC).** Використання системного часу як Nonce не працює на платах без резервної літієвої батарейки живлення RTC: після кожного ввімкнення годинник стартує з фіксованої епохи (наприклад, `00:00:00 01.01.1970`).
3. **Псевдовипадкові числа з детермінованого генератора.** Спроба генерувати випадковий Nonce стандартною функцією `rand()` без апаратного генератора істинно випадкових чисел (TRNG) призводить до того, що після кожного старту процесор видає ту саму послідовність чисел через однакове початкове значення ініціалізації (seed).

> 🔧 **Навіщо це.** Щоб гарантувати унікальність Nonce у вбудованій системі, застосовують три надійні інженерні стратегії:
> - **Складений Nonce (Composite Nonce):** 96-бітний вектор конструюють із трьох частин: старші 32 біти — лічильник завантажень (Boot Count), що зберігається в захищеному секторі Flash/EEPROM або регістрах Backup-домену; середні 32 біти — унікальний апаратний ідентифікатор чипа (UID); молодші 32 біти — лічильник повідомлень поточного сеансу в RAM.
> - **Збереження лічильника блоками:** Щоб не зношувати Flash-пам'ять записом на кожен пакет, лічильник у Flash інкрементують наперед із запасом (наприклад, на `+10000`), а поточні значення відраховують у RAM. При перезавантаженні лічильник у RAM виставляється у збережене у Flash значення `+10000`, що виключає перекриття діапазонів.
> - **Алгоритми з розширеним нонсом (Extended Nonce):** Застосування XChaCha20-Poly1305 із 192-бітним Nonce (24 байти). При довжині нонса 192 біти його можна генерувати суто випадково за допомогою апаратного TRNG: імовірність колізії двох випадкових значень становить `2⁻⁹⁶`, що математично виключає повтор протягом усього життєвого циклу пристрою.

### Пастка друга: саморобні та застарілі алгоритми

Друга фатальна помилка — спроба винайти власний шифр або спростити стандартний алгоритм «для економії ресурсів процесора». Найпоширеніший прояв цієї помилки — циклічний XOR із секретним ключем, псевдовипадкові перестановки байтів або застосування некриптографічних контрольних сум для перевірки цілісності.

#### Чому «простий XOR із ключем» ламається за секунди

Нехай повідомлення шифрується побайтовим додаванням із секретним ключем довжини `L` байтів: `C[i] = P[i] ^ Key[i % L]`. 

Така схема є прямим еквівалентом багаторазового шифру Віженера (англ. *Vigenère cipher*), зламаного ще в XIX столітті Фрідріхом Касіскі та Чарльзом Беббіджем. Злам складається з двох автоматизованих кроків:

1. **Визначення довжини ключа `L`:** Обчислюється **індекс збігів** (англ. *index of coincidence*) для різних зсувів шифротексту. Оскільки бінарні протоколи та структури даних мають нерівномірний розподіл байтів (ентропія значно нижча за 8 біт на байт), при зсуві на величину, кратну `L`, кількість однакових байтів різко зростає.
2. **Розбиття на незалежні потоки:** Шифротекст розбивається на `L` незалежних колонок, кожна з яких зашифрована рівно одним незмінним байтом `Key[j]`. Однобайтовий XOR зламується миттєвим частотним аналізом: байт ключа перебирається серед 256 можливих варіантів, і обирається той, що максимізує правдоподібність байтів відкритого тексту.

#### Лінійні регістри зсуву (LFSR)

Інша улюблена конструкція розробників апаратури — лінійні регістри зсуву зі зворотним зв'язком (англ. *Linear Feedback Shift Register*, LFSR). Вони надзвичайно швидкі, реалізуються на ПЛІС (FPGA) або мікроконтролері кількома машинними інструкціями й генерують послідовності з періодом `2ⁿ - 1`.

Однак LFSR є суто **лінійною** математичною системою. [Алгоритм Берлекампа–Мессі](root:sf-security/keyed-hash-mac) дозволяє нападникові повністю відновити початковий стан регістра та всі коефіцієнти зворотного зв'язку довжини `n`, перехопивши всього лише `2n` послідовних бітів вихідної гами. Якщо у пристрої використано 64-бітний LFSR, перехоплення всього 16 байтів відкритого тексту та відповідного шифротексту повністю компрометує весь генератор назавжди.

#### Помилка використання CRC для захисту від підробки

Часто розробники намагаються захистити шифротекст від спотворення за допомогою звичайної контрольної суми CRC32:

```
Пакет = [ Шифротекст C ] [ CRC32(C) ]
```

Це фундаментальна помилка. Контрольна сума CRC розроблена для виявлення **випадкових спотворень** (шум на лінії, перешкоди в радіоефірі), а не дій зловмисника. CRC32 є лінійною функцією над полем `GF(2)`:

```
CRC(A ⊕ B) = CRC(A) ⊕ CRC(B)
```

Якщо нападник хоче змінити шифротекст `C` на `C' = C ⊕ Δ` (наприклад, змінити команду), він легко обчислює зміну контрольної суми `CRC(Δ)` і оновлює поле CRC у пакеті:

```
CRC(C') = CRC(C ⊕ Δ) = CRC(C) ⊕ CRC(Δ)
```

Приймач обчислює CRC від отриманого шифротексту, бачить ідеальний збіг і передає сфальшовану команду на виконання. Для захисту від навмисних маніпуляцій придатні **виключно криптографічні коди автентичності (MAC)**, обчислені з використанням спільного секретного ключа.

#### Принцип Керкгоффза та лавинний ефект

У криптографії діє фундаментальний **принцип Керкгоффза** (англ. *Kerckhoffs's principle*, сформульований Огюстом Керкгоффзом 1883 року): **безпека криптосистеми повинна залежати виключно від секретності ключа, а не від таємниці самого алгоритму**.

Спроба приховати слабкий алгоритм (підхід «безпека через неясність», англ. *security through obscurity*) завжди зазнає краху, щойно бінарний файл прошивки зчитується з Flash-пам'яті через інтерфейс налагодження SWD/JTAG або витягується з оновлення по повітрю.

Головна відмінність криптостійкого блокового шифру (як-от AES) від аматорської перестановки полягає в наявності **лавинного ефекту** (англ. *avalanche effect*): зміна навіть одного вхідного біта відкритого тексту або ключа повинна з імовірністю 50% змінювати кожен біт вихідного шифротексту вже після кількох раундів нелінійних замін (S-Box) та дифузійних перестановок. Саморобні шифри не мають строгого математичного доказу стійкості проти лінійного та диференційного криптоаналізу, тому зламуються за лічені хвилини.

### Пастка третя: атаки за часом виконання (Timing Attacks)

Навіть якщо пристрій використовує надійний алгоритм AES або ChaCha20 і коректно генерує Nonce, система може бути повністю скомпрометована на етапі перевірки автентичності повідомлення.

Для перевірки цілісності відправник обчислює код автентичності повідомлення (MAC, наприклад, 16-байтовий тег Poly1305 або HMAC-SHA256) і додає його до кадру. Отримувач обчислює очікуваний тег над отриманими даними й порівнює його з тегом, переданим у пакеті.

Типова фатальна помилка розробника виглядає так:

:::tabs
```c
// КАТАСТРОФА ДЛЯ БЕЗПЕКИ: перевірка тегу через memcmp
if (memcmp(calculated_tag, received_tag, 16) == 0) {
    process_secure_command();
} else {
    send_error_response();
}
```
```cpp
#include <cstring>
#include <span>
#include <cstdint>

// КАТАСТРОФА ДЛЯ БЕЗПЕКИ: оператор == або std::memcmp виконують ранній вихід
bool is_tag_valid_vulnerable(std::span<const std::uint8_t, 16> calc,
                             std::span<const std::uint8_t, 16> recv) noexcept {
    return std::memcmp(calc.data(), recv.data(), 16) == 0;
}
```
:::

#### Анатомія витоку в memcmp()

Функція стандартної бібліотеки C `memcmp()` оптимізована для максимальної швидкості роботи. Її класична реалізація порівнює масиви байт за байтом і виконує **ранній вихід** (англ. *early exit*) одразу на першому байті, що не збігся:

:::tabs
```c
// Класична реалізація memcmp з раннім виходом
int naive_memcmp(const void *s1, const void *s2, size_t n) {
    const unsigned char *p1 = s1, *p2 = s2;
    for (size_t i = 0; i < n; i++) {
        if (p1[i] != p2[i]) {
            return p1[i] - p2[i]; // НЕГАЙНИЙ ВИХІД при першій розбіжності!
        }
    }
    return 0;
}
```
```cpp
#include <cstddef>
#include <span>

// Еквівалентний C++ цикл із раннім перериванням
[[nodiscard]] int naive_compare(std::span<const std::byte> s1, 
                                std::span<const std::byte> s2) noexcept {
    const std::size_t n = s1.size() < s2.size() ? s1.size() : s2.size();
    for (std::size_t i = 0; i < n; ++i) {
        if (s1[i] != s2[i]) {
            return static_cast<int>(s1[i]) - static_cast<int>(s2[i]);
        }
    }
    return 0;
}
```
:::

Погляньмо, що відбувається під час перевірки 16-байтового тегу нападника:

1. Якщо перший байт підробленого тегу не збігається (`received_tag[0] != calculated_tag[0]`), цикл переривається на нульовій ітерації. Функція виконується за умовний час `T₀ + 1·Δt`.
2. Якщо перший байт випадково вгадано правильно, але другий хибний (`received_tag[1] != calculated_tag[1]`), функція виконує дві ітерації і завершується за час `T₀ + 2·Δt`.
3. Якщо нападник правильно підібрав перші 5 байтів, перевірка триватиме `T₀ + 6·Δt`.

![Анатомія таймінг-атаки: ранній вихід у memcmp() проти захищеного порівняння з константним часом](/root/course/embedded/try-pomylky-na-iakykh-lamaietsia-samorobna/img/timing-attack-early-exit.svg)
*Ранній вихід у функції memcmp() дозволяє нападникові виміряти точний час відповіді пристрою. Затримка корелює з кількістю вгаданих початкових байтів, що дозволяє відновити весь автентифікаційний тег байт за байтом.*

Нападник надсилає пакети на мікроконтролер через UART, SPI, CAN або локальну мережу Ethernet/Wi-Fi і високоточним таймером вимірює час до отримання відповіді про помилку відхилення кадру.

Він фіксує всі байти тегу нулями, змінюючи лише перший байт від `0x00` до `0xFF` (256 спроб). Те значення байта, яке дало статистично більшу затримку відповіді мікроконтролера, є правильним першим байтом!

Після цього нападник фіксує перший знайдений байт і починає перебирати другий байт (`0x00` .. `0xFF`), шукаючи наступний сплеск часу затримки.

#### Математичне знецінення простору пошуку

Для криптографічного тегу довжиною 16 байтів (128 бітів) теоретичний простір повного перебору становить:

```
2¹²⁸ ≈ 3.4 · 10³⁸ комбінацій
```

Перебрати таку кількість варіантів неможливо за весь час існування Всесвіту. Проте завдяки витоку інформації через час виконання в `memcmp()` експоненційна складність перетворюється на **лінійну**:

```
16 байтів × 256 варіантів = 4096 запитів
```

За швидкості відправки 100 пакетів на секунду повний підпис 16-байтового MAC відновлюється нападником за **40 секунд**. Після цього нападник може змусити пристрій виконати будь-яку критичну команду (відкрити замок, перепрошити шкідливий образ, скинути заводські налаштування), обійшовши криптографічну автентифікацію.

Цей клас атак зветься **атаками сторонніми каналами за часом виконання** (англ. *timing side-channel attacks*).

### Принципи програмування з константним часом

Щоб унеможливити витоки через сторонні канали, весь код, який опрацьовує секретні дані (ключі, відкритий текст, автентифікаційні теги), повинен виконуватися за **константний час** (англ. *constant-time execution*).

Це означає, що час виконання функції та послідовність виконуваних інструкцій процесора повинні бути суворо незмінними незалежно від значень секретних байтів.

#### Три залізні правила Constant-Time програмування

1. **Жодних розгалужень за секретними даними.** 
   У коді не повинно бути операторів `if`, `switch`, `while`, `for` або тернарного оператора `? :`, умова яких залежить від значення секрету. Будь-яке розгалуження транслюється в інструкції умовного переходу процесора (наприклад, `BNE`, `BEQ` на архітектурі ARM), час виконання яких залежить від блоку передбачення переходів (branch predictor) або скидання конвеєра.
2. **Жодних звернень до пам'яті за секретними індексами.**
   Операція читання з масиву `table[secret_value]` неприпустима. На сучасних мікроконтролерах із кеш-пам'яттю (Cortex-M7, ESP32) час доступу до адреси залежить від того, чи потрапила лінія в кеш (Cache Hit/Miss). Вимірюючи час читання, нападник визначає значення `secret_value`. Саме так класичні табличні реалізації AES (T-Tables) компрометуються кеш-атаками.
3. **Жодних інструкцій із неконстантним часом виконання.**
   На багатьох процесорних архітектурах (зокрема Cortex-M0/M3) операції апаратного ділення (`UDIV`/`SDIV`) та зсуву на змінну кількість бітів займають різну кількість тактів залежно від значень операндів.

#### Реалізація константного порівняння

Для безпечної перевірки масивів автентифікації використовується побітове накопичення різниці через операцію OR. Цикл завжди проходить усі без винятку байти масиву, не перериваючись завчасно.

:::tabs
```c
#include <stdint.h>
#include <stddef.h>

/**
 * @brief Безпечне порівняння двох буферів фіксованої довжини за константний час.
 * @return 0, якщо буфери ідентичні; ненульове значення, якщо є хоча б один відмінний біт.
 */
int crypto_verify_ct(const uint8_t *a, const uint8_t *b, size_t len) {
    // volatile запобігає спробам оптимізатора розгорнути або скоротити обчислення
    volatile uint8_t diff = 0;
    
    for (size_t i = 0; i < len; i++) {
        diff |= (a[i] ^ b[i]);
    }
    
    // diff == 0 тоді й тільки тоді, коли кожен байт a[i] == b[i]
    return (int)diff;
}
```
```cpp
#include <cstdint>
#include <cstddef>
#include <span>

/**
 * @brief Безпечне порівняння двох буферів за константний час (C++20).
 * @return true, якщо вміст буферів повністю збігається.
 */
[[nodiscard]] bool crypto_verify_ct(std::span<const std::uint8_t> a, 
                                    std::span<const std::uint8_t> b) noexcept {
    if (a.size() != b.size()) {
        return false;
    }
    
    volatile std::uint_fast8_t diff = 0;
    for (std::size_t i = 0; i < a.size(); ++i) {
        diff |= static_cast<std::uint_fast8_t>(a[i] ^ b[i]);
    }
    
    return diff == 0;
}
```
:::

Зверніть увагу на використання ключового слова `volatile`. Без нього оптимізатори компілятора (`gcc -O3` або `clang -O2`) здатні розпізнати семантику циклу й замінити його назад на оптимізований виклик `memcmp()` із раннім виходом.

#### Константний умовний вибір (Constant-Time Selection)

Коли в алгоритмі необхідно вибрати одне з двох значень `a` або `b` залежно від секретної умови `condition` (0 або 1), замість конструкції `result = condition ? a : b` використовують побітові маски:

:::tabs
```c
#include <stdint.h>

/**
 * @brief Константний вибір: повертає a, якщо condition == 1; повертає b, якщо condition == 0.
 * condition має бути строго 0 або 1.
 */
uint32_t ct_select_u32(uint32_t condition, uint32_t a, uint32_t b) {
    // Створюємо маску: якщо condition == 1 -> mask = 0xFFFFFFFF; якщо condition == 0 -> mask = 0x00000000
    uint32_t mask = (uint32_t)(-(int32_t)condition);
    return (mask & a) | (~mask & b);
}
```
```cpp
#include <cstdint>
#include <type_traits>

/**
 * @brief Константний вибір без розгалужень (C++).
 */
template <typename T>
[[nodiscard]] constexpr T ct_select(bool condition, T a, T b) noexcept {
    static_assert(std::is_integral_v<T>, "Потрібен цілочисельний тип");
    const auto mask = static_cast<T>(-static_cast<std::int64_t>(condition));
    return static_cast<T>((mask & a) | (~mask & b));
}
```
:::

### Надійний криптографічний модуль для вбудованих пристроїв

Щоб побудувати по-справжньому захищений канал зв'язку на мікроконтролері, необхідно дотримуватися суворого архітектурного шаблону:

1. **Не винаходити власні примітиви.** Використовувати компактні, перевірені та математично верифіковані криптобібліотеки, розроблені спеціально для вбудованих систем:
   - **Monocypher** — надзвичайно компактна (один `.c` і один `.h` файл), константна за часом бібліотека, що реалізує ChaCha20, Poly1305, Curve25519 та Ed25519.
   - **BearSSL** — бездоганно структурована бібліотека від Томаса Порніна, повністю ізольована від динамічної пам'яті (без `malloc`), розроблена з акцентом на захист від таймінг-атак.
   - **mbedTLS** — стандарт де-факто в екосистемах ARM та Espressif ESP-IDF із підтримкою апаратних прискорювачів.
2. **Використовувати лише парадигму AEAD (Authenticated Encryption with Associated Data).**
   Автентифікація та шифрування повинні бути нерозривно пов'язані. Заголовок пакета (включно з лічильником і адресою) передається відкрито, але входить у розрахунок автентифікаційного тегу як **асоційовані дані** (AAD, англ. *Associated Authenticated Data*).
3. **Золоте правило обробки вхідного кадру:** **Жоден байт шифротексту ніколи не повинен передаватися в прикладний код або розшифровуватися до того, як автентифікаційний тег буде повністю перевірено в константному часі.** Якщо тег не зійшовся — пакет негайно й безшумно відкидається.

![Структура захищеного пакета AEAD та послідовність обробки](/root/course/embedded/try-pomylky-na-iakykh-lamaietsia-samorobna/img/aead-packet-structure.svg)
*Формат безпечного пакета: відкритий заголовок із лічильником захищений від модифікацій через автентифікацію (AAD), корисне навантаження зашифроване, а хвіст містить 16-байтовий тег. Приймач спершу перевіряє лічильник та валідує тег у константному часі, і лише за умови успіху розшифровує дані.*

Нижче наведено практичну реалізацію модуля безпечного кодування та декодування кадрів на базі примітивів ChaCha20-Poly1305.

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

#define SECURE_FRAME_MAGIC     0xA55A
#define TAG_SIZE               16
#define MAX_PAYLOAD_SIZE       128

#pragma pack(push, 1)
typedef struct {
    uint16_t magic;           // Сигнатура протоколу (0xA55A)
    uint32_t sequence_num;    // Монотонний лічильник пакета (захист від повторів)
    uint16_t payload_len;     // Довжина зашифрованого навантаження
} SecureHeader_t;

typedef struct {
    SecureHeader_t header;
    uint8_t payload[MAX_PAYLOAD_SIZE];
    uint8_t tag[TAG_SIZE];
} SecureFrame_t;
#pragma pack(pop)

// Прототипи зовнішніх перевірених функцій шифрування (наприклад, із Monocypher або mbedTLS)
extern void crypto_aead_encrypt(uint8_t *cipher, uint8_t *tag,
                                const uint8_t *key, const uint8_t *nonce,
                                const uint8_t *aad, size_t aad_len,
                                const uint8_t *plain, size_t plain_len);

extern void crypto_aead_decrypt(uint8_t *plain,
                                const uint8_t *key, const uint8_t *nonce,
                                const uint8_t *aad, size_t aad_len,
                                const uint8_t *cipher, size_t cipher_len);

extern int crypto_verify_ct(const uint8_t *a, const uint8_t *b, size_t len);

typedef struct {
    uint8_t session_key[32];
    uint32_t tx_counter;
    uint32_t rx_last_counter;
} CryptoSession_t;

/**
 * @brief Пакування та шифрування вихідного пакета.
 */
bool secure_frame_encode(CryptoSession_t *session,
                         const uint8_t *plain, size_t plain_len,
                         SecureFrame_t *out_frame, size_t *out_frame_len) {
    if (!session || !plain || !out_frame || plain_len > MAX_PAYLOAD_SIZE) {
        return false;
    }

    out_frame->header.magic = SECURE_FRAME_MAGIC;
    out_frame->header.sequence_num = ++(session->tx_counter);
    out_frame->header.payload_len = (uint16_t)plain_len;

    // Формуємо 12-байтовий Nonce з лічильника відправки
    uint8_t nonce[12] = {0};
    memcpy(nonce, &(out_frame->header.sequence_num), sizeof(uint32_t));

    // Шифруємо корисні дані та обчислюємо тег автентифікації над заголовком (AAD) і шифротекстом
    crypto_aead_encrypt(out_frame->payload, out_frame->tag,
                        session->session_key, nonce,
                        (const uint8_t*)&out_frame->header, sizeof(SecureHeader_t),
                        plain, plain_len);

    *out_frame_len = sizeof(SecureHeader_t) + plain_len + TAG_SIZE;
    return true;
}

/**
 * @brief Перевірка автентичності та безпечне розшифрування вхідного пакета.
 */
bool secure_frame_decode(CryptoSession_t *session,
                         const uint8_t *frame_bytes, size_t frame_len,
                         uint8_t *out_plain, size_t *out_plain_len) {
    if (!session || !frame_bytes || !out_plain || frame_len < sizeof(SecureHeader_t) + TAG_SIZE) {
        return false;
    }

    const SecureFrame_t *frame = (const SecureFrame_t*)frame_bytes;

    // 1. Перевірка цілісності структури заголовка
    if (frame->header.magic != SECURE_FRAME_MAGIC) {
        return false;
    }

    size_t expected_payload_len = frame->header.payload_len;
    if (frame_len != sizeof(SecureHeader_t) + expected_payload_len + TAG_SIZE) {
        return false;
    }

    // 2. Суворий захист від повторів (Replay Protection)
    if (frame->header.sequence_num <= session->rx_last_counter) {
        return false; // Старий або повторно відправлений пакет — відхиляємо
    }

    // 3. Формуємо Nonce для перевірки
    uint8_t nonce[12] = {0};
    memcpy(nonce, &(frame->header.sequence_num), sizeof(uint32_t));

    // 4. Обчислюємо очікуваний тег
    uint8_t calculated_tag[TAG_SIZE];
    uint8_t dummy_plain[MAX_PAYLOAD_SIZE];
    
    // Розшифровуємо в тимчасовий буфер для отримання тегу або викликаємо суто перевірку тегу
    crypto_aead_encrypt(dummy_plain, calculated_tag,
                        session->session_key, nonce,
                        (const uint8_t*)&frame->header, sizeof(SecureHeader_t),
                        frame->payload, expected_payload_len);

    // 5. ПЕРЕВІРКА В КОНСТАНТНОМУ ЧАСІ
    if (crypto_verify_ct(calculated_tag, frame->payload + expected_payload_len, TAG_SIZE) != 0) {
        // ТЕГ ХИБНИЙ: Негайно повертаємо відмову!
        // Жоден байт не копіюється у вихідний буфер застосунку!
        return false;
    }

    // 6. Лише після успішної автентифікації розшифровуємо відкритий текст
    crypto_aead_decrypt(out_plain,
                        session->session_key, nonce,
                        (const uint8_t*)&frame->header, sizeof(SecureHeader_t),
                        frame->payload, expected_payload_len);

    *out_plain_len = expected_payload_len;
    session->rx_last_counter = frame->header.sequence_num;
    return true;
}
```

```cpp
#include <cstdint>
#include <cstddef>
#include <array>
#include <span>
#include <optional>
#include <cstring>

constexpr std::uint16_t SECURE_FRAME_MAGIC = 0xA55A;
constexpr std::size_t TAG_SIZE = 16;
constexpr std::size_t MAX_PAYLOAD_SIZE = 128;

#pragma pack(push, 1)
struct SecureHeader {
    std::uint16_t magic{SECURE_FRAME_MAGIC};
    std::uint32_t sequence_num{0};
    std::uint16_t payload_len{0};
};
#pragma pack(pop)

// Прототипи верифікованих криптопримітивів
extern void crypto_aead_encrypt(std::uint8_t *cipher, std::uint8_t *tag,
                                const std::uint8_t *key, const std::uint8_t *nonce,
                                const std::uint8_t *aad, std::size_t aad_len,
                                const std::uint8_t *plain, std::size_t plain_len);

extern void crypto_aead_decrypt(std::uint8_t *plain,
                                const std::uint8_t *key, const std::uint8_t *nonce,
                                const std::uint8_t *aad, std::size_t aad_len,
                                const std::uint8_t *cipher, std::size_t cipher_len);

[[nodiscard]] bool crypto_verify_ct(std::span<const std::uint8_t> a, 
                                    std::span<const std::uint8_t> b) noexcept;

class SecureChannelSession {
public:
    explicit SecureChannelSession(std::span<const std::uint8_t, 32> key) noexcept {
        std::memcpy(session_key_.data(), key.data(), 32);
    }

    [[nodiscard]] std::optional<std::size_t> encode_frame(
        std::span<const std::uint8_t> plaintext,
        std::span<std::uint8_t> out_buffer) noexcept 
    {
        if (plaintext.size() > MAX_PAYLOAD_SIZE) {
            return std::nullopt;
        }

        const std::size_t total_size = sizeof(SecureHeader) + plaintext.size() + TAG_SIZE;
        if (out_buffer.size() < total_size) {
            return std::nullopt;
        }

        SecureHeader header{};
        header.magic = SECURE_FRAME_MAGIC;
        header.sequence_num = ++tx_counter_;
        header.payload_len = static_cast<std::uint16_t>(plaintext.size());

        std::array<std::uint8_t, 12> nonce{};
        std::memcpy(nonce.data(), &header.sequence_num, sizeof(header.sequence_num));

        std::memcpy(out_buffer.data(), &header, sizeof(header));

        auto ciphertext_span = out_buffer.subspan(sizeof(SecureHeader), plaintext.size());
        auto tag_span = out_buffer.subspan(sizeof(SecureHeader) + plaintext.size(), TAG_SIZE);

        crypto_aead_encrypt(
            ciphertext_span.data(), tag_span.data(),
            session_key_.data(), nonce.data(),
            reinterpret_cast<const std::uint8_t*>(&header), sizeof(header),
            plaintext.data(), plaintext.size()
        );

        return total_size;
    }

    [[nodiscard]] std::optional<std::size_t> decode_frame(
        std::span<const std::uint8_t> frame_bytes,
        std::span<std::uint8_t> out_plaintext) noexcept 
    {
        if (frame_bytes.size() < sizeof(SecureHeader) + TAG_SIZE) {
            return std::nullopt;
        }

        SecureHeader header{};
        std::memcpy(&header, frame_bytes.data(), sizeof(header));

        if (header.magic != SECURE_FRAME_MAGIC) {
            return std::nullopt;
        }

        const std::size_t expected_payload_len = header.payload_len;
        if (frame_bytes.size() != sizeof(SecureHeader) + expected_payload_len + TAG_SIZE) {
            return std::nullopt;
        }

        // Захист від атак повторного відтворення (Replay Attack)
        if (header.sequence_num <= rx_last_counter_) {
            return std::nullopt;
        }

        if (out_plaintext.size() < expected_payload_len) {
            return std::nullopt;
        }

        std::array<std::uint8_t, 12> nonce{};
        std::memcpy(nonce.data(), &header.sequence_num, sizeof(header.sequence_num));

        auto ciphertext_span = frame_bytes.subspan(sizeof(SecureHeader), expected_payload_len);
        auto received_tag_span = frame_bytes.subspan(sizeof(SecureHeader) + expected_payload_len, TAG_SIZE);

        std::array<std::uint8_t, TAG_SIZE> calculated_tag{};
        std::array<std::uint8_t, MAX_PAYLOAD_SIZE> dummy_buffer{};

        crypto_aead_encrypt(
            dummy_buffer.data(), calculated_tag.data(),
            session_key_.data(), nonce.data(),
            reinterpret_cast<const std::uint8_t*>(&header), sizeof(header),
            ciphertext_span.data(), expected_payload_len
        );

        // ПЕРЕВІРКА В КОНСТАНТНОМУ ЧАСІ
        if (!crypto_verify_ct(calculated_tag, received_tag_span)) {
            return std::nullopt; // Тег недійсний — кадр відхилено без розшифрування
        }

        crypto_aead_decrypt(
            out_plaintext.data(),
            session_key_.data(), nonce.data(),
            reinterpret_cast<const std::uint8_t*>(&header), sizeof(header),
            ciphertext_span.data(), expected_payload_len
        );

        rx_last_counter_ = header.sequence_num;
        return expected_payload_len;
    }

private:
    std::array<std::uint8_t, 32> session_key_{};
    std::uint32_t tx_counter_{0};
    std::uint32_t rx_last_counter_{0};
};
```

### Підсумок: правила надійної вбудованої криптографії

Безпека вбудованої системи не з'являється від додавання випадкового шифрування поверх готового пакета. Вона вимагає дотримання п'яти непорушних інженерних принципів:

1. **Ніколи не повторювати Nonce.** Для потокових шифрів та лічильникових режимів (ChaCha20, AES-CTR, AES-GCM) повтор вектора ініціалізації знищує конфіденційність через операцію XOR та розкриває ключі автентифікації.
2. **Використовувати тільки стандартизовані AEAD-примітиви.** Шифрування без криптографічної автентифікації не захищає від підміни та ін'єкцій команд через пластичність шифротексту.
3. **Порівнювати секретні масиви виключно в константному часі.** Застосування `memcmp()` або `==` для перевірки MAC-тегів відкриває двері для таймінг-атак, що відновлюють підпис за лічені секунди.
4. **Не розшифровувати до перевірки цілісності.** Будь-яка спроба розпарсити або обробити шифротекст до валідації тегу наражає систему на атаки типу Padding Oracle або переповнення буфера.
5. **Опиратися на перевірені відкриті бібліотеки.** Monocypher, BearSSL або mbedTLS написані провідними криптографами з урахуванням специфіки мікроконтролерів і містять захист від витоків на рівні машинних інструкцій.
