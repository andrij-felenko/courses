Коли розробка вбудованого комерційного пристрою добігає кінця, перед командою постає завдання захистити інтелектуальну власність. Усередині Flash-пам'яті мікроконтролера розташовані пропрієтарні алгоритми фільтрації, математичні моделі керування двигунами, параметри калібрування сенсорів або криптографічні ключі доступу до хмарної інфраструктури. Якщо передати у виробництво незахищену друковану плату, будь-який конкурент чи дослідник може підпаяти чотири провідники до контактних майданчиків налагодження, запустити утиліту OpenOCD або фірмовий програматор і за лічені секунди отримати точний двійковий образ усієї пам'яті кристала.

Першою інтуїтивною дією інженера зазвичай є пошук штатного перемикача в документації на мікроконтролер. У більшості популярних родин (STM32, NXP Kinetis/LPC, Microchip SAM, Silicon Labs EFM32) передбачено вбудований апаратний механізм захисту від зчитування — Readout Protection (RDP). Розробник програмує відповідний біт у конфігураційних реєстрах Option Bytes, додає на початку програми виклик функції перемикання виводів SWD/JTAG у режим звичайних цифрових портів і вважає, що пристрій замкнений надійно.

Проте в лабораторіях апаратного реверс-інжинірингу такі чипи віддають свій вміст без знання паролів і без руйнування кристала за лічені хвилини. Апаратні прапорці захисту виявляються не криптографічним сейфом, а лише логічним вимикачем на внутрішній цифровій шині, вразливим до фізичних впливів і дефектів мікропрограмного коду. Щоб збудувати справді надійну систему, інженер повинен розуміти точну фізику взаємодії дебагера з кремнієм, механіку блокування шин, фізичні принципи ін'єкції збоїв та межі, де апаратний захист мікроконтролера втрачає стійкість.

## Механіка RDP: як кремній відрізає дебагер від шини

Щоб розібратися у вразливостях захисту від зчитування, необхідно простежити шлях проходження сигналів між зовнішнім програматором і масивом комірок Flash-пам'яті. В архітектурі ARM Cortex-M налагодження не виконується ядром процесора через спеціальні інструкції чи переривання. Це повністю незалежний апаратний блок на кристалі — CoreSight Debug Access Port (DAP).

Блок DAP складається з двох ключових рівнів:
1. **Debug Port (DP):** зовнішній інтерфейсний модуль, що перетворює фізичні рівні сигналів на лініях SWD (дводротовий інтерфейс: SWCLK, SWDIO) або JTAG (чотиридротовий інтерфейс: TCK, TMS, TDI, TDO) у внутрішні цифрові пакети. Порт DP містить регістри керування живленням налагоджувального домену (`CTRL/STAT`), ідентифікатор (`DPIDR`) та мультиплексор вибору цільового модуля (`SELECT`).
2. **Access Port (AP):** внутрішній модуль взаємодії із системою. Найважливішим серед них є Memory Access Port (MEM-AP). Модуль MEM-AP виступає повноцінним господарем (Master) на внутрішній матриці шин AHB/AXI кристала поряд із процесорним ядром і контролером прямого доступу до пам'яті (DMA).

Коли дебагер надсилає команду прочитати 32-бітне слово за адресою `0x08000000`, модуль MEM-AP записує цю адресу у свій внутрішній регістр Transfer Address Register (`TAR`), після чого ініціює транзакцію читання через регістр Data Read/Write (`DRW`). Ця транзакція надходить безпосередньо до арбітра шини Flash-контролера. Процесор у цей час може виконувати основну програму або перебувати в стані апаратного зупину (Halt), але MEM-AP продовжує зчитувати комірки пам'яті автономно.

![Рівні апаратного захисту RDP: стани та переходи](/root/course/embedded/zamknuty-chyp/img/rdp-levels.svg)
*Три стани захисту від зчитування (RDP). Рівень 0 надає повний доступ дебагеру. Рівень 1 блокує звернення MEM-AP до Flash, а спроба відкату в Рівень 0 викликає апаратне стирання всієї пам'яті кристала. Рівень 2 фізично відключає порт налагодження на кремнієвому рівні без можливості повернення.*

Конфігураційні байти Option Bytes зберігаються в спеціальному енергонезалежному блоці (Flash Information Block або OTP-секторі). Під час кожного виходу зі стану скидання (Power-On Reset, POR або Brown-Out Reset, BOR) апаратний кінцевий автомат контролера Flash вичитує Option Bytes і завантажує їх у спеціальні тіньові регістри (Shadow Latches), підключені до комбінаційної логіки селектора шин.

У мікроконтролерах STM32 та споріднених архітектурах захист поділяється на три стани:

### RDP Рівень 0 (0xAA або 0xAA55): режим відкритого доступу

У цьому стані чип надходить із заводу. Логічний компаратор розпізнає константу `0xAA` і тримає відкритими всі мости матриці шин AHB. Модуль MEM-AP дебагера має необмежений доступ на читання та запис до Flash-пам'яті, системного завантажувача (System ROM), оперативної пам'яті (SRAM) і регістрів периферійних модулів.

### RDP Рівень 1 (будь-яке значення, крім 0xAA та 0xCC): захист від неавторизованого читання

Це основний робочий режим захисту для більшості пристроїв. Логіка арбітра шини аналізує джерело кожної адресної транзакції:
- Якщо транзакція до Flash надходить від центрального процесора (CPU), який сам виконує код із захищеної Flash-пам'яті, арбітр підтверджує запит. Програма працює на повній швидкості без обмежень.
- Якщо транзакція ініційована модулем MEM-AP дебагера, апаратний декодер шини негайно генерує сигнал помилки `HRESP = ERROR` (Bus Fault) або повертає нульовий результат `0x00000000`. Зчитати дані чи інструкції з Flash через SWD/JTAG неможливо.
- Якщо процесор виконує код з оперативної пам'яті SRAM чи системного ROM, доступ до Flash також блокується апаратурою. Це запобігає завантаженню невеликого дампера в SRAM через дебагер для подальшого зчитування Flash.

Головною особливістю Рівня 1 є можливість зворотного переходу (Regression). Якщо розробнику потрібно оновити прошивку на заводському стенді або розблокувати чип, у конфігураційний регістр через дебагер записується значення `0xAA` (Рівень 0). 

У той самий момент, коли апаратура фіксує команду переходу `1 → 0`, контролер Flash блокує інтерфейс і запускає апаратну процедуру масового стирання (Mass Erase). Апаратний секвенсор стирає всі сектори користувацької Flash-пам'яті, очищає збережені дані в Backup SRAM і встановлює всі комірки в стан `0xFF`. Тільки після повного завершення стирання арбітр шини відновлює доступ дебагера до пам'яті. У такий спосіб виробник гарантує, що повернення до відкритого режиму знищує будь-які секрети, які намагався захистити розробник.

### RDP Рівень 2 (0xCC або 0xCC33): незворотне апаратне блокування кристала

Коли в Option Bytes прошивається значення `0xCC`, цифровий контролер захисту активує незворотний режим блокування (Silicon Lock):
- Лінії інтерфейсу SWD/JTAG апаратно відсікаються від внутрішнього порту DAP. Кристал перестає відповідати на будь-які зовнішні цифрові послідовності скидання чи ідентифікації через виводи налагодження.
- Апаратно забороняється вибір завантаження з оперативної пам'яті SRAM або заводського System Memory (Bootloader ROM). Кристал здатний стартувати виключно з головного масиву Flash-пам'яті.
- Контролер Flash блокує будь-які операції модифікації регістру `FLASH_OPTCR` або його аналогів — навіть сама виконувана програма більше не має змоги переписати Option Bytes чи скинути рівень захисту.

Рівень 2 перетворює мікроконтролер на «чорну скриньку». Повернути такий чип у режим розробки неможливо — команда масового стирання не може бути подана через відсутність зв'язку з дебагером.

## Програмне вимкнення SWD/JTAG: чому це не рятує від зчитування

Багато розробників намагаються додати власний програмний бар'єр: у перших рядках функції `main()` переконфігурувати регістри мультиплексора вводу-виводу (GPIO Alternate Function Registers), відключивши лінії SWCLK та SWDIO або перевівши їх у стан аналогових входів чи звичайних цифрових виходів.

З боку коду це виглядає як надійне рішення: якщо виводи мікроконтролера фізично перемкнено на іншу периферію (наприклад, керування світлодіодами чи інтерфейс SPI), дебагер не зможе передати жодного біта інформації. Проте в такій схемі криється фундаментальна апаратна вразливість, пов'язана з часовою послідовністю запуску кристала.

```text
Послідовність апаратного старту мікроконтролера:
[Скидання NRST] ──> [Старт HSI] ──> [Option Bytes: RDP] ──> [GPIO: Default AF (SWD)] ──> [Вектор Reset_Handler] ──> [SystemInit] ──> [main(): вимкнення SWD]
                      ▲                                          ▲
                      │                                          │
                      └────────── ВІКНО АТАКИ ДЕБАГЕРА ──────────┘
```

Коли з лінії скидання `NRST` знімається нульовий рівень або на чип подається живлення, кремнієвий автомат проходить чітко визначену послідовність кроків:
1. Запускається внутрішній високочастотний RC-генератор (HSI).
2. Автомат скидання зчитує конфігурацію живлення та Option Bytes.
3. Усі виводи GPIO встановлюються в початковий апаратний стан за замовчуванням. Для ліній PA13/PA14 (SWDIO/SWCLK) це завжди стан альтернативної функції налагодження з увімкненими внутрішніми підтяжками.
4. Ядро зчитує початкове значення покажчика стека (MSP) за адресою `0x08000000` та адресу вектора обробника скидання `Reset_Handler` за адресою `0x08000004`.
5. Процесор починає вибірку інструкцій: копіює дані з Flash в RAM для секції `.data`, заповнює нулями секцію `.bss`, викликає функцію налаштування тактової системи `SystemInit()`, конфігурує системний таймер і лише через сотні чи тисячі машинних тактів доходить до коду користувача у функції `main()`.

Протягом цього стартового вікна лінії SWD залишаються повністю функціональними. Професійні дебагери реалізують апаратний режим підключення під скиданням (Connect Under Reset).

Дебагер апаратно притискає лінію `NRST` до землі, подає на лінію SWCLK синхросигнал, передає через лінію SWDIO команду перемикання інтерфейсу, після чого записує в регістр ядра `DHCSR` (Debug Halting Control and Status Register) біти зупинки:

```text
DHCSR = C_DEBUGEN (біт 0) | C_HALT (біт 1) | DBGKEY (0xA05F << 16)
```

Після цього дебагер відпускає лінію `NRST`. Процесор виходить зі стану скидання, але апаратура CoreSight миттєво заморожує тактування ядра на першому ж циклі вибірки інструкцій — ще до того, як виконається хоча б одна команда стартового асемблерного файлу. Код вимкнення портів у `main()` просто ніколи не отримує керування.

Другий шлях нейтралізації програмного вимкнення портів — апаратне керування виводами вибору режиму завантаження `BOOT0` та `BOOT1`. Якщо лінію `BOOT0` з'єднати з шиною `VDD`, мікроконтролер після скидання спрямує вектор старту не на сектор Flash, а на заводський системний ROM. Усередині заводського завантажувача виводи SWD не вимикаються взагалі, а програма користувача в Flash залишається збереженою для аналізу.

Програмне перепризначення виводів у коді захищає лише від випадкового підключення дебагера під час нормальної роботи, але не створює жодної перешкоди для нападника з фізичним доступом до плати.

## Межі стійкості: як фізичні збої та вади ROM ламають апаратний захист

Якщо програмні методи не працюють, а RDP Рівня 1 чи Рівня 2 закладено в кремній, постає питання: чому ці механізми не гарантують абсолютної безпеки?

Причина полягає в тому, що всі цифрові механізми захисту спираються на припущення: кристал працює в ідеальних умовах, визначених специфікацією (номінальна напруга живлення, дозволений діапазон температур, стабільна тактова частота, відсутність сторонніх електромагнітних полів). Щойно нападник порушує ці умови, цифрова логіка починає працювати з фатальними помилками.

### Атака збоєм живлення (Voltage Glitching / Fault Injection)

Атака збоєм живлення є найбільш руйнівним і доступним методом обходу апаратного захисту RDP. Вона базується на фізиці роботи КМОН-транзисторів.

Логічна перевірка байта RDP всередині кристала під час старту зводиться до зчитування значення з комірок пам'яті Flash Information Block у внутрішній регістр та виконання перевірки за допомогою логічного компаратора або мікропрограми завантажувача.

```text
// Логіка перевірки прапорця RDP у кремнії
IF (FLASH_OPTION_BYTES.RDP == 0xAA) THEN
    DAP_BUS_ACCESS_ALLOW();
ELSE
    DAP_BUS_ACCESS_BLOCK();
END IF;
```

На рівні машинного коду процесорного ядра або внутрішнього кінцевого автомата це відповідає вибірці байта, інструкції порівняння `CMP` та інструкції умовного переходу `BNE` (Branch if Not Equal).

![Механізм ін'єкції збою за живленням (Voltage Glitching)](/root/course/embedded/zamknuty-chyp/img/glitch-bypass.svg)
*Короткочасне падіння напруги живлення ядра на 30 нс призводить до того, що транзистори логічних вентилів не встигають перемкнутися за один такт. Інструкція перевірки прапорця RDP зчитується або декодується з помилкою, відкриваючи шину налагодження без стирання Flash.*

Динамічна затримка поширення сигналу крізь логічний вентиль КМОН залежить від напруги живлення ядра VDD і порогової напруги відкриття транзисторів Vth. Час заряду та розряду ємностей затворів транзисторів (постійна часу τ = R · C) різко збільшується через падіння напруги керування.

Якщо на лінію живлення ядра `VCORE` або шину живлення кристала `VDD` подати ультракороткий імпульс просадки напруги (тривалістю 20–60 наносекунд із падінням напруги з 3.3 В до 0.6–0.8 В) саме в той такт, коли процесор чи логічний автомат виконує перевірку Option Bytes, виникає збій часу встановлення сигналу (Setup Time Violation):
- Транзистори шини даних не встигають розрядити паразитні ємності провідників до моменту фіксації тактового фронту.
- Інструкція умовного переходу `BNE` зчитується процесорним конвеєром зі спотвореним двійковим кодом і декодується як інструкція `NOP` (No Operation, код `0xBF00` для архітектури Thumb-2).
- Або значення, зчитане з Option Bytes, помилково інтерпретується внутрішнім компаратором як `0xAA` (Рівень 0).

Наслідок цього збою фатальний для безпеки: арбітр матриці шин переводить модуль MEM-AP дебагера в стан дозволеного доступу (Level 0), але автомат масового стирання пам'яті (Mass Erase) не активується, оскільки фізичної команди запису в Option Bytes не надходило. 

Нападник, заздалегідь підключений через SWD-дебагер, миттєво перехоплює контроль над шиною і зчитує весь вміст Flash-пам'яті у файл на комп'ютері. Для реалізації такої атаки достатньо простого інструменту (наприклад, відкритої плати PicoEMP або ChipWhisperer) та ключа на польовому транзисторі (Crowbar circuit), що закорочує лінію живлення на землю на кілька десятків наносекунд.

### Електромагнітна ін'єкція збоїв (EMFI) та лазерні атаки

Якщо шини живлення захищені внутрішніми стабілізаторами чи потужними фільтрами, збій викликають безконтактно.

Під час електромагнітної ін'єкції (EMFI) мініатюрний зонд із конічним наконечником підносять упритул до пластикового корпусу мікроконтролера. Через зонд пропускають високовольтний розряд тривалістю 2–5 наносекунд. Сильне змінне магнітне поле пронизує корпус мікросхеми та індукує вихрові струми у внутрішніх металевих шарах кристала. Ці струми змінюють потенціали на провідниках шин, змушуючи тригери регістра захисту RDP скинутися в стан нуля під час тактового імпульсу.

У спеціалізованих лабораторіях застосовують лазерну ін'єкцію збоїв (Laser Fault Injection, LFI):
1. Корпус мікроконтролера піддають хімічному травленню димлячою азотною кислотою для оголення кремнієвого кристала.
2. Мікроскоп фокусує імпульс інфрачервоного лазера (довжина хвилі 1064 нм, яка вільно проходить крізь кремнієву підкладку) безпосередньо на чутливих транзисторах блоку перевірки Option Bytes.
3. Лазерний імпульс генерує локальний фотострум, який примусово перемикає логічний стан лінії дозволу налагодження на виході компаратора, повністю ігноруючи реальні значення, записані у Flash.

### Дефекти та експлойти заводських ROM-завантажувачів

Навіть якщо апаратний захист RDP Рівня 2 повністю вимкнув інтерфейс налагодження, поверхнею атаки залишається системний завантажувач (Bootloader ROM).

Цей код записується у маскове ПЗП кристала на етапі фотолітографії на кремнієвій фабриці. Виробник не може оновити чи виправити цей код після відвантаження партії мікроконтролерів. Відомі численні вразливості фабричних завантажувачів:
- **Переповнення буфера в стеку USB DFU:** передача нестандартного пакета дескриптора більшої довжини, ніж розмір буфера в оперативній пам'яті, призводить до перезапису адреси повернення у стеку. Нападник отримує можливість виконати в оперативній пам'яті довільний двійковий код, який вичитує вміст захищеної Flash і транслює його на вивід UART.
- **Вразливості перевірки команд у протоколах UART/I2C:** наявність недокументованих інженерних команд тестування пам'яті, які забули вимкнути перед релізом кремнію.
- **Ефект залишкової пам'яті (SRAM Remanence):** якщо мікроконтролер перезавантажується перемиканням виводу `BOOT0` без повного зняття живлення, у комірках оперативної пам'яті SRAM залишаються незанулені конфіденційні дані, розшифровані ключі або таблиці векторів, які потім вичитуються через інтерфейс завантажувача.

## Ешелонований захист: як будувати безпеку без ілюзій

Неможливість побудувати абсолютний захист на одному кремнієвому прапорці веде до фундаментального правила інженерії безпеки: **надійність створюється виключно ешелонуванням рубежів оборони (Defense in Depth)**. Кожен шар захисту проектується з розрахунку на те, що попередній шар може бути зламаний або скомпрометований.

![Концепція ешелонованого захисту вбудованого пристрою](/root/course/embedded/zamknuty-chyp/img/defense-in-depth.svg)
*Три рівні ешелонованого захисту: схемотехнічний захист від фізичних впливів, апаратні криптографічні бар'єри кремнію та алгоритмічні контрзаходи в самій прошивці.*

### 1. Схемотехнічний та фізичний рівень захисту

Схемотехніка пристрою повинна запобігати спробам створити контрольований збій живлення:
- **Конфігурація Brown-Out Reset (BOR):** під час прошивання Option Bytes обов'язково встановлюється найвищий апаратний поріг скидання за низькою напругою (BOR Level 3, типово 2.7 В). Якщо нападник спробує просадити напругу живлення до 1.5–2.0 В для створення збою логіки, вбудований швидкодіючий компаратор BOR миттєво переведе мікроконтролер у стан апаратного скидання.
- **Низькоімпедансна розв'язка живлення:** блокувальні керамічні конденсатори ємністю 0.1 мкФ (типорозмір 0402) разом із танталовими або полімерними конденсаторами 4.7–10 мкФ розпаюються впритул до кожної пари виводів `VDD`/`VSS` з мінімальною довжиною перехідних отворів. Локальний запас енергії в конденсаторах значно ускладнює формування наносекундних провалів напруги зовнішнім транзисторним ключем.
- **Фільтрація лінії скидання:** встановлення RC-фільтра та швидкого зовнішнього супервізора живлення на лінію `NRST` перешкоджає точній часовій синхронізації імпульсу атаки за фронтом зняття скидання.
- **Фізичний захист плати (Potting):** заливка чутливої ділянки плати непрозорим високотемпературним компаундом на основі епоксидної або поліуретанової смоли унеможливлює підключення вимірювальних щупів до ліній SWD, живлення ядра та виводів `BOOT0` без руйнування компонентів.

### 2. Апаратні та криптографічні бар'єри

- **Активація RDP Рівня 2:** для кінцевих серійних виробів увімкнення Рівня 2 є базовою гігієнічною вимогою, що відсікає всі спроби зняття дампу через звичайні дебагери.
- **Шифрування пам'яті «на льоту» (Encrypted XIP / OTFDEC):** сучасні мікроконтролери (STM32H7, STM32L5/U5, ESP32-S3, NXP LPC55S) містять апаратний блок On-The-Fly Decryption (OTFDEC) на базі алгоритму AES-CTR або AES-XTS. Код у внутрішній або зовнішній Flash-пам'яті зберігається виключно в зашифрованому вигляді. Контролер пам'яті розшифровує інструкції під час вибірки процесором за один такт. Навіть якщо нападник обійде захист RDP за допомогою глітчингу й вичитає дамп, він отримає лише нечитабельний псевдовипадковий масив байтів.
- **Зберігання ключів в одноразовій пам'яті OTP (eFuse):** кореневий ключ розшифрування Flash записується в апаратні комірки eFuse, читання яких через будь-які інтерфейси апаратно заблоковано. Ключ подається безпосередньо в криптографічний блок по внутрішніх закритих лініях.
- **Захищене завантаження (Secure Boot):** верифікація цифрового підпису кожного оновлення прошивки за допомогою асиметричної криптографії (ECDSA P-256 або RSA-3072). Неможливо модифікувати Flash і запустити скомпрометований код.

### 3. Алгоритмічний захист у прошивці

Програмний код повинен містити активні засоби виявлення та нейтралізації збоїв під час виконання критичних операцій.

Нижче наведено порівняння захищеної логіки подвійної комплементарної перевірки мовами C та C++:

:::tabs
```c
// Захищена перевірка стану безпеки з подвійним комплементарним кодуванням на C
#include <stdint.h>
#include <stdbool.h>

#define SEC_STATE_LOCKED    0x5AA55AA5U
#define SEC_STATE_INV_LOCK  0xA55AA55AU

volatile uint32_t g_security_marker     = SEC_STATE_LOCKED;
volatile uint32_t g_security_marker_inv = SEC_STATE_INV_LOCK;

void tamper_safe_reaction(void);

bool verify_security_integrity(void) {
    // Подвійна перевірка значення та його бітового доповнення
    if ((g_security_marker != SEC_STATE_LOCKED) || 
        (g_security_marker_inv != SEC_STATE_INV_LOCK) ||
        ((g_security_marker ^ g_security_marker_inv) != 0xFFFFFFFFU)) {
        
        // Збій цілісності або успішний глітч: запускаємо захисну реакцію
        tamper_safe_reaction();
        return false;
    }
    return true;
}
```
```cpp
// Захищена перевірка стану безпеки з подвійним комплементарним кодуванням на C++20
#include <cstdint>
#include <concepts>

namespace security {

class HardenedSecurityState {
public:
    static constexpr uint32_t StateLocked    = 0x5AA55AA5U;
    static constexpr uint32_t StateInvLocked = 0xA55AA55AU;

    [[nodiscard]] static bool is_valid_and_locked() noexcept {
        const uint32_t direct = marker_;
        const uint32_t inverse = marker_inv_;

        if (direct != StateLocked || inverse != StateInvLocked || ((direct ^ inverse) != 0xFFFFFFFFU)) {
            trigger_tamper_wipe();
            return false;
        }
        return true;
    }

private:
    static inline volatile uint32_t marker_{StateLocked};
    static inline volatile uint32_t marker_inv_{StateInvLocked};

    static void trigger_tamper_wipe() noexcept;
};

} // namespace security
```

- **Рандомізація часових затримок (Random Jitter):** перед перевіркою критичних умов прошивка зчитує випадкове число з апаратного генератора TRNG і виконує цикл затримки випадкової довжини. Це унеможливлює точну часову синхронізацію ін'єкції збою нападником.
- **Контроль цілісності потоку виконання (Control Flow Integrity, CFI):** по мірі проходження важливих функцій у контрольний регістр додаються підписи стадій. На фінальному етапі перевіряється, чи не перескочив процесор проміжні інструкції перевірки внаслідок глітчу.
- **Очищення оперативної пам'яті (RAM Zeroization):** при виявленні нештатного перезапуску, спрацьовуванні детектора Tamper або виході з критичної криптографічної функції вся область SRAM із ключами примусово затирається нулями за допомогою захищеної функції, яку компілятор не може оптимізувати чи викинути.

## Драйвер налаштування Option Bytes та верифікації захисту

Розглянемо повну промислову реалізацію драйвера керування Option Bytes для мікроконтролерів архітектури ARM Cortex-M (на прикладі сімейства STM32).

Драйвер забезпечує:
1. Безпечне зняття апаратного блокування Option Bytes через послідовність запису авторизаційних ключів у регістр `OPTKEYR`.
2. Комплементарну верифікацію поточного рівня захисту RDP, стійку до ін'єкцій збоїв.
3. Безпечне програмування RDP Рівня 1 або Рівня 2 з обов'язковою одночасною активацією найвищого порогу супервізора живлення BOR Level 3.
4. Контроль часу очікування прапорця зайнятості контролера `FLASH_SR_BSY` з захистом від нескінченного зависання.

:::tabs
```c
// rdp_driver.h — Драйвер апаратного захисту Option Bytes (C99 / C11)
#ifndef RDP_DRIVER_H
#define RDP_DRIVER_H

#include <stdint.h>
#include <stdbool.h>

// Магічні ключі авторизації для доступу до Option Bytes
#define FLASH_OPTKEY1         0x08192A3BU
#define FLASH_OPTKEY2         0x4C5D6E7FU

// Базові адреси та регістри Flash Controller
#define FLASH_BASE_ADDR       0x40023C00U
#define FLASH_OPTKEYR_REG     (*(volatile uint32_t *)(FLASH_BASE_ADDR + 0x08U))
#define FLASH_SR_REG          (*(volatile uint32_t *)(FLASH_BASE_ADDR + 0x0CU))
#define FLASH_CR_REG          (*(volatile uint32_t *)(FLASH_BASE_ADDR + 0x10U))
#define FLASH_OPTCR_REG       (*(volatile uint32_t *)(FLASH_BASE_ADDR + 0x14U))

// Бітові маски стану контролера Flash
#define FLASH_SR_BSY_BIT      (1U << 16)

// Бітові маски регістра керування FLASH_OPTCR
#define FLASH_OPTCR_OPTLOCK   (1U << 0)
#define FLASH_OPTCR_OPTSTRT   (1U << 1)
#define FLASH_OPTCR_BOR_LEV_3 (0U << 2) // Найвищий поріг скидання за напругою (2.7 В)
#define FLASH_OPTCR_RDP_POS   8U
#define FLASH_OPTCR_RDP_MASK  (0xFFU << FLASH_OPTCR_RDP_POS)

// Константи рівнів захисту RDP
typedef enum {
    RDP_LEVEL_0 = 0xAAU, // Відкрито для налагодження
    RDP_LEVEL_1 = 0x55U, // Захист Flash (відкат виконує Mass Erase)
    RDP_LEVEL_2 = 0xCCU  // Незворотне апаратне блокування кристала
} rdp_level_t;

typedef enum {
    RDP_STATUS_OK = 0,
    RDP_STATUS_BUSY,
    RDP_STATUS_UNLOCK_FAILED,
    RDP_STATUS_VERIFY_ERROR,
    RDP_STATUS_ALREADY_LOCKED
} rdp_status_t;

// Інтерфейс драйвера
rdp_status_t rdp_get_level(rdp_level_t *out_level);
rdp_status_t rdp_set_level(rdp_level_t target_level);
bool rdp_is_hardened(void);

#endif // RDP_DRIVER_H
```
```cpp
// rdp_driver.hpp — Драйвер апаратного захисту Option Bytes (Modern C++20)
#pragma once

#include <cstdint>
#include <concepts>
#include <expected>
#include <span>

namespace security {

enum class RdpLevel : uint8_t {
    Level0 = 0xAA, // Відкрито для налагодження
    Level1 = 0x55, // Захищено від читання
    Level2 = 0xCC  // Незворотне блокування кремнію
};

enum class ProtectionError : uint8_t {
    ControllerBusy,
    UnlockFailed,
    WriteError,
    VerificationFailed,
    AlreadyAtLevel2
};

class ReadoutProtection {
public:
    ReadoutProtection() = delete;

    [[nodiscard]] static std::expected<RdpLevel, ProtectionError> get_current_level() noexcept;
    [[nodiscard]] static std::expected<void, ProtectionError> set_level(RdpLevel target) noexcept;
    [[nodiscard]] static bool is_fully_hardened() noexcept;

private:
    static constexpr uintptr_t FlashBase = 0x40023C00U;
    
    struct FlashRegisters {
        volatile uint32_t acr;
        volatile uint32_t keyr;
        volatile uint32_t optkeyr;
        volatile uint32_t sr;
        volatile uint32_t cr;
        volatile uint32_t optcr;
    };

    static inline auto* regs() noexcept {
        return reinterpret_cast<FlashRegisters*>(FlashBase);
    }

    static constexpr uint32_t OptKey1 = 0x08192A3BU;
    static constexpr uint32_t OptKey2 = 0x4C5D6E7FU;
    
    static constexpr uint32_t SrBusyBit   = 1U << 16;
    static constexpr uint32_t OptcrLock   = 1U << 0;
    static constexpr uint32_t OptcrStart  = 1U << 1;
    static constexpr uint32_t OptcrBorLv3 = 0U << 2; // Максимальний поріг BOR
    static constexpr uint32_t OptcrRdpPos = 8U;
    static constexpr uint32_t OptcrRdpMsk = 0xFFU << OptcrRdpPos;

    [[nodiscard]] static std::expected<void, ProtectionError> wait_ready() noexcept;
    [[nodiscard]] static std::expected<void, ProtectionError> unlock_options() noexcept;
    static void lock_options() noexcept;
};

} // namespace security
```

Нижче наведено реалізацію логіки запису та перевірки Option Bytes. Зверніть увагу на використання циклів очікування прапорця зайнятості контролера `FLASH_SR_BSY` та комплементарну перевірку результату.

:::tabs
```c
// rdp_driver.c — Реалізація драйвера Option Bytes на C
#include "rdp_driver.h"

static rdp_status_t flash_wait_ready(void) {
    uint32_t timeout = 500000U;
    while ((FLASH_SR_REG & FLASH_SR_BSY_BIT) != 0U) {
        if (--timeout == 0U) {
            return RDP_STATUS_BUSY;
        }
    }
    return RDP_STATUS_OK;
}

static rdp_status_t rdp_unlock_options(void) {
    if ((FLASH_OPTCR_REG & FLASH_OPTCR_OPTLOCK) == 0U) {
        return RDP_STATUS_OK; // Вже розблоковано
    }

    // Запис магічної послідовності ключів
    FLASH_OPTKEYR_REG = FLASH_OPTKEY1;
    FLASH_OPTKEYR_REG = FLASH_OPTKEY2;

    if ((FLASH_OPTCR_REG & FLASH_OPTCR_OPTLOCK) != 0U) {
        return RDP_STATUS_UNLOCK_FAILED;
    }
    return RDP_STATUS_OK;
}

static void rdp_lock_options(void) {
    FLASH_OPTCR_REG |= FLASH_OPTCR_OPTLOCK;
}

rdp_status_t rdp_get_level(rdp_level_t *out_level) {
    if (out_level == (void *)0) {
        return RDP_STATUS_VERIFY_ERROR;
    }

    uint32_t optcr_val = FLASH_OPTCR_REG;
    uint8_t rdp_byte = (uint8_t)((optcr_val & FLASH_OPTCR_RDP_MASK) >> FLASH_OPTCR_RDP_POS);

    if (rdp_byte == (uint8_t)RDP_LEVEL_0) {
        *out_level = RDP_LEVEL_0;
    } else if (rdp_byte == (uint8_t)RDP_LEVEL_2) {
        *out_level = RDP_LEVEL_2;
    } else {
        *out_level = RDP_LEVEL_1;
    }

    return RDP_STATUS_OK;
}

rdp_status_t rdp_set_level(rdp_level_t target_level) {
    rdp_level_t current_level;
    rdp_status_t status = rdp_get_level(&current_level);
    if (status != RDP_STATUS_OK) {
        return status;
    }

    if (current_level == RDP_LEVEL_2) {
        return RDP_STATUS_ALREADY_LOCKED; // З 2-го рівня відкату немає
    }

    if (current_level == target_level) {
        return RDP_STATUS_OK; // Вже в потрібному стані
    }

    status = flash_wait_ready();
    if (status != RDP_STATUS_OK) {
        return status;
    }

    status = rdp_unlock_options();
    if (status != RDP_STATUS_OK) {
        return status;
    }

    // Формуємо нове значення OPTCR: виставляємо RDP та активуємо максимальний BOR
    uint32_t optcr = FLASH_OPTCR_REG;
    optcr &= ~FLASH_OPTCR_RDP_MASK;
    optcr &= ~(3U << 2); // Скидаємо біти BOR
    optcr |= ((uint32_t)target_level << FLASH_OPTCR_RDP_POS);
    optcr |= FLASH_OPTCR_BOR_LEV_3; // Вмикаємо апаратний захист від просадок

    FLASH_OPTCR_REG = optcr;

    // Запускаємо запис Option Bytes
    FLASH_OPTCR_REG |= FLASH_OPTCR_OPTSTRT;

    status = flash_wait_ready();
    rdp_lock_options();

    if (status != RDP_STATUS_OK) {
        return status;
    }

    // Перевірка результату запису
    rdp_level_t verified_level;
    rdp_get_level(&verified_level);
    if (verified_level != target_level) {
        return RDP_STATUS_VERIFY_ERROR;
    }

    return RDP_STATUS_OK;
}

bool rdp_is_hardened(void) {
    rdp_level_t lvl;
    if (rdp_get_level(&lvl) != RDP_STATUS_OK) {
        return false;
    }
    // Комплементарна перевірка проти глітчингу
    volatile uint32_t check_a = (lvl == RDP_LEVEL_2) ? 0x3CA5U : 0x0000U;
    volatile uint32_t check_b = (lvl != RDP_LEVEL_2) ? 0xC35AU : 0x0000U;

    return (check_a == 0x3CA5U) && (check_b == 0x0000U);
}
```

```cpp
#include "rdp_driver.hpp"

namespace security {

std::expected<void, ProtectionError> ReadoutProtection::wait_ready() noexcept {
    uint32_t timeout = 500000U;
    while ((regs()->sr & SrBusyBit) != 0U) {
        if (--timeout == 0U) {
            return std::unexpected(ProtectionError::ControllerBusy);
        }
    }
    return {};
}

std::expected<void, ProtectionError> ReadoutProtection::unlock_options() noexcept {
    if ((regs()->optcr & OptcrLock) == 0U) {
        return {}; // Вже відкрито
    }

    regs()->optkeyr = OptKey1;
    regs()->optkeyr = OptKey2;

    if ((regs()->optcr & OptcrLock) != 0U) {
        return std::unexpected(ProtectionError::UnlockFailed);
    }
    return {};
}

void ReadoutProtection::lock_options() noexcept {
    regs()->optcr |= OptcrLock;
}

std::expected<RdpLevel, ProtectionError> ReadoutProtection::get_current_level() noexcept {
    const uint32_t optcr = regs()->optcr;
    const uint8_t rdp_byte = static_cast<uint8_t>((optcr & OptcrRdpMsk) >> OptcrRdpPos);

    if (rdp_byte == static_cast<uint8_t>(RdpLevel::Level0)) {
        return RdpLevel::Level0;
    }
    if (rdp_byte == static_cast<uint8_t>(RdpLevel::Level2)) {
        return RdpLevel::Level2;
    }
    return RdpLevel::Level1;
}

std::expected<void, ProtectionError> ReadoutProtection::set_level(RdpLevel target) noexcept {
    auto current = get_current_level();
    if (!current.has_value()) {
        return std::unexpected(current.error());
    }

    if (*current == RdpLevel::Level2) {
        return std::unexpected(ProtectionError::AlreadyAtLevel2);
    }

    if (*current == target) {
        return {};
    }

    auto wait_res = wait_ready();
    if (!wait_res.has_value()) return wait_res;

    auto unlock_res = unlock_options();
    if (!unlock_res.has_value()) return unlock_res;

    uint32_t optcr_val = regs()->optcr;
    optcr_val &= ~OptcrRdpMsk;
    optcr_val &= ~(3U << 2); // Скидання конфігурації BOR
    optcr_val |= (static_cast<uint32_t>(target) << OptcrRdpPos);
    optcr_val |= OptcrBorLv3; // Активація найвищого порогу BOR

    regs()->optcr = optcr_val;
    regs()->optcr |= OptcrStart;

    auto write_wait = wait_ready();
    lock_options();

    if (!write_wait.has_value()) return write_wait;

    auto verified = get_current_level();
    if (!verified.has_value() || *verified != target) {
        return std::unexpected(ProtectionError::VerificationFailed);
    }

    return {};
}

bool ReadoutProtection::is_fully_hardened() noexcept {
    auto lvl = get_current_level();
    if (!lvl.has_value()) return false;

    // Стійка до глітчингу подвійна перевірка
    const bool is_l2 = (*lvl == RdpLevel::Level2);
    volatile uint32_t token_direct  = is_l2 ? 0x5A5AA5A5U : 0x00000000U;
    volatile uint32_t token_inverse = (!is_l2) ? 0xA5A55A5AU : 0x00000000U;

    return (token_direct == 0x5A5AA5A5U) && (token_inverse == 0x00000000U);
}

} // namespace security
```

## Підсумок: формула надійної безпеки

Замикання мікроконтролера — це не разова дія виставлення біта в програматорі, а комплексна інженерна стратегія побудови захищеної системи.

1. **RDP Рівень 1** надійно рятує від зчитування через відкритий порт налагодження, але дозволяє відкат ціною апаратного стирання всієї прошивки.
2. **RDP Рівень 2** назавжди відрізає дебагер на кремнієвому рівні, але не захищає від фізичного збою живлення (Voltage Glitching), електромагнітного імпульсу (EMFI) або вразливостей вшитого Bootloader ROM.
3. **Програмне вимкнення виводів SWD/JTAG** не діє проти підключення під скиданням (Connect Under Reset) або зміни конфігурації завантаження пінами `BOOT0`.
4. **Справжня стійкість** досягається лише поєднанням апаратного блокування (RDP2), схемотехнічного захисту (максимальний рівень BOR, фільтрація живлення, компаунд), шифрування Flash-пам'яті (OTFDEC) та відмовостійкої прошивки з подвійними перевірками й рандомізацією затримок.
