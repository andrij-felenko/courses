# Тестування прошивки: тест-дублі, упровадження залежностей у C, Unity/CMock, час і переривання, HIL, покриття на цілі

Прошивку перевіряють шарами — маса дешевих юніт-тестів на ПК, посередині підроблене залізо, нагорі жменя прогонів на справжньому чипі. Це каркас. Але щойно беруться за діло, виявляється: каркас тримається на кількох неочевидних механізмах, і саме в них криється різниця між набором тестів, який щось доводить, і набором, що лише створює відчуття безпеки. Чим стаб відрізняється від мока — і чому це не педантизм. Як у мові без класів, без рефлексії, де все вирішено на етапі компіляції, узагалі підставити підробку замість драйвера. Як зробити детермінованим тест таймауту, не чекаючи реальних секунд. Як перевірити логіку переривання, не маючи переривання. І чому сто відсотків покриття можуть співіснувати з грубим багом. Ось другий шар — не «що таке тести прошивки», а як вони влаштовані всередині.

## Тест-дублі: не одне слово на п'ять різних речей

Коли логіку відривають від заліза, на місце справжнього драйвера в тесті стає **підробка**. Та слово «підробка» накриває п'ять різних звірів, які роблять зовсім різне, і плутати їх — означає писати крихкі, неінформативні тести. Спільна назва для всіх — **тест-дублі** (англ. *test double*, за аналогією з дублером актора: підставна особа, що грає замість справжньої). Поділ між ними йде за однією віссю: від геть пасивного, що лише заповнює місце, до активного, що сам виносить вердикт.

![П'ять тест-дублів за зростанням активності: dummy заповнює параметр, stub віддає готову відповідь, fake — спрощена робоча реалізація, spy записує виклики, mock несе очікування й сам судить](/root/course/embedded/firmware-testing/img/doubles.svg)
*П'ять тест-дублів, упорядкованих від пасивного до активного. Стаб відповідає на питання коду; мок навпаки — ставить коду питання й сам судить відповідь. Між ними — фейк (спрощена робоча реалізація) і шпигун (записує виклики для перевірки опісля).*

**Пустушка** (англ. *dummy*) — найбезневинніший дубль: об'єкт чи значення, яке передають лише тому, що цього вимагає сигнатура, але насправді ним не користуються. Функція бере вказівник на буфер логів, а наш тест перевіряє геть інше — туди йде пустушка, аби компілятор не лаявся. Її не викликають, її поведінка нічого не важить.

**Заглушка** (англ. *stub*, букв. «обрубок, корінець») робить наступний крок: вона **віддає готову відповідь**. Код просить «дай мені температуру» — заглушка незмінно повертає 25, не читаючи жодного давача. Вона нічого не перевіряє й нічого не пам'ятає; її єдина робота — годувати код під тестом потрібним входом, щоб ми могли подивитися, як код на цей вхід зреагує.

```c
// драйвер давача за швом — лише оголошення:
int sensor_read_temp(void);   // у бою читає I2C; у тесті — заглушка

// ЗАГЛУШКА: завжди віддає одне число, нічого не питаючи в заліза
int sensor_read_temp(void) {
    return 25;   // готова відповідь — годуємо нею логіку під тестом
}
```

**Фейк** (англ. *fake*) — це вже **спрощена, але справді робоча реалізація**. Не готова відповідь, а зменшена діюча модель. Найчастіший приклад у прошивці — підмінити роботу з [Flash-пам'яттю](book:programming/flash-vs-ram) звичайним масивом у RAM: той самий інтерфейс «запиши блок», «прочитай блок», «зітри сторінку», та замість справжнього стирання й обмежень на витривалість — простий масив байтів. Фейк поводиться правильно (записав — прочитав те саме), але без фізики справжнього носія. Він дає змогу ганяти логіку, що активно щось зберігає й дістає, без жодного чипа й на величезній швидкості.

```c
// ФЕЙК енергонезалежного сховища: масив у RAM замість справжньої Flash.
// Інтерфейс той самий — логіка вгорі не бачить різниці.
#define FAKE_SIZE 4096
static uint8_t fake_mem[FAKE_SIZE];

int storage_write(uint32_t addr, const uint8_t *buf, uint32_t len) {
    if (addr + len > FAKE_SIZE) return -1;   // та сама перевірка меж
    for (uint32_t i = 0; i < len; ++i) fake_mem[addr + i] = buf[i];
    return 0;
}
int storage_read(uint32_t addr, uint8_t *buf, uint32_t len) {
    if (addr + len > FAKE_SIZE) return -1;
    for (uint32_t i = 0; i < len; ++i) buf[i] = fake_mem[addr + i];
    return 0;
}
```

**Шпигун** (англ. *spy*) додає до поведінки заглушки **пам'ять про виклики**: він робить що належить, але дорогою занотовує, скільки разів його кликали, з якими аргументами, у якому порядку. Після прогону тест зазирає в ці нотатки й перевіряє: «правда ж, мене викликали двічі, і другого разу з кодом 0x40?» Тут перевірка стоїть **після** дії, у самому тесті, а дубль лишається пасивним записувачем.

```c
// ШПИГУН за драйвером шини: робить вигляд, що шле байт, але запам'ятовує що й скільки
static uint8_t spy_bytes[64];
static int     spy_count = 0;

int bus_send(uint8_t b) {
    if (spy_count < 64) spy_bytes[spy_count++] = b;   // нотуємо
    return 0;                                          // ніби успішно надіслали
}
// ...пізніше в тесті:
//   assert(spy_count == 2);
//   assert(spy_bytes[0] == 0xA0 && spy_bytes[1] == 0x01);
```

**Мок** (англ. *mock*, букв. «удавання, підробка») — найактивніший дубль, і саме його найчастіше плутають з усіма попередніми. Мок **несе очікування наперед**: ще до того, як викличуть код під тестом, ми озброюємо мок сценарієм — «тебе мають викликати з аргументом X і ти повернеш Y; потім викликати з Z». Якщо реальний хід виконання розійшовся з цим сценарієм — мок **сам завалює тест** на місці. Принципова різниця: заглушка чи шпигун відповідають на питання коду, а мок навпаки — **ставить коду питання й одразу судить відповідь**. Перевірка взаємодії вбудована в сам дубль, а не дописана в тесті опісля.

> 🔧 **Навіщо це.** Розрізнення стаб/мок — не словникарство, а вибір **що саме перевіряти**. Заглушка перевіряє **результат**: «при −40 від давача логіка пішла в безпечний режим». Мок перевіряє **взаємодію**: «драйвер давача надіслав команду START, дочекався готовності й лише тоді читав». Перше доречне для чистої логіки; друге — для драйверів і протоколів, де баг ховається саме в послідовності дій, а не в поверненому числі. Узяти мок там, де досить заглушки, — отримати тест, що ламається від будь-якого безневинного рефакторингу всередині; узяти заглушку там, де потрібен мок, — проґавити саме той клас багів, заради якого тест писали.

Корисний контроль-тест, який дубль вам потрібен: спитайте, **що зламається, якщо код помилиться**. Якщо помилку видно з поверненого значення чи кінцевого стану — досить заглушки. Якщо помилка — це «зробив правильні дії в неправильному порядку» або «забув один крок», а число на виході при цьому могло лишитися правильним, — потрібен мок або шпигун, бо лише вони бачать самі дії.

## Упровадження залежностей у C: три шви

Уся ця гра з дублями тримається на одній передумові: код під тестом має **не знати**, з ким він насправді розмовляє — зі справжнім драйвером чи з підробкою. Місце, де можна непомітно підставити одне замість іншого, звуть **швом** (англ. *seam* — шов у тканині, місце, де її можна розпороти й зшити інакше, не псуючи решти). А загальний прийом «не зашивай залежність усередину, а подавай її ззовні» — це **упровадження залежностей** (англ. *dependency injection*, буквально «впорскування залежності»).

У мовах із класами це звична річ: передав інший об'єкт — дістав іншу поведінку. Та C не має ні класів, ні віртуальних методів, ні рефлексії, і все, що ми хочемо підмінити, часто вирішено ще компілятором. Тому в C шов доводиться робити руками, і є рівно три місця, де його можна прокласти: у **рантаймі** (під час виконання), на **етапі лінкування** (під час збірки) і в самому **вихіднику** (препроцесором). Вони дають дуже різну якість тесту.

![Три шви для підміни заліза в C: вказівники на функції (шов у рантаймі), підміна на лінкуванні (шов у збірці), препроцесор #ifdef (шов у вихіднику — найгірший)](/root/course/embedded/firmware-testing/img/seams.svg)
*Три способи прокласти шов у C і момент, коли обирається підміна. Чим пізніше це відбувається — рантайм, потім збірка, потім вихідник — тим краще: вказівники й лінкування лишають у чипі рівно той код, що його ганяв тест, а препроцесор підсовує в чіп ІНШИЙ код, ніж перевіряли.*

### Шов перший: вказівники на функції

Найгнучкіший шов — зібрати залежність у **структуру з полями-функціями** й передавати її коду. Це віртуальна таблиця, зроблена вручну (англ. *vtable*, *virtual table* — таблиця віртуальних викликів, те, що компілятор C++ робить за лаштунками; тут ми будуємо її явно). Код кличе не конкретну функцію, а поле структури: `drv->read()`. У бою в це поле кладуть справжній драйвер, у тесті — підробку. Підміна стається **під час виконання** — найпізніше з можливого.

```c
// інтерфейс давача — vtable вручну:
typedef struct {
    int  (*read_temp)(void *ctx);    // повертає температуру
    void *ctx;                       // стан конкретної реалізації (за потреби)
} TempSensor;

// логіка залежить від ІНТЕРФЕЙСУ, не від конкретного давача:
bool overheat(const TempSensor *s) {
    return s->read_temp(s->ctx) > 80;
}

// у бою — справжній драйвер:
static int i2c_temp(void *ctx) { (void)ctx; return read_i2c_sensor(); }
// у тесті — заглушка під тим самим інтерфейсом:
static int fake_temp(void *ctx) { return *(int *)ctx; }

// тест без жодного чипа:
int scenario = 95;
TempSensor mock = { .read_temp = fake_temp, .ctx = &scenario };
assert( overheat(&mock) == true );    // 95 > 80 → перегрів
scenario = 30;
assert( overheat(&mock) == false );   // 30 → норми
```

Ціна гнучкості — дрібниці: структура займає місце, а виклик через вказівник трохи дорожчий за прямий і його не вбудувати (англ. *inline*). На гарячому шляху, де кожна наносекунда на рахунку, це інколи відчутно; на більшості коду — ні. Зате той самий бінар, що його ганяли тести, їде в чіп без жодної зміни, а підміняти можна точково — окрему функцію, не цілий модуль.

### Шов другий: підміна на етапі лінкування

Другий шов спирається на те, як збирається програма. Оголошення функції живе в заголовку (`.h`), а її тіло — в окремому файлі реалізації (`.c`). Нічого не заважає мати **два** файли реалізації під один заголовок: `sensor_hw.c` зі справжнім драйвером для бойової збірки й `sensor_fake.c` із підробкою для тестової. Який саме під'єднати, вирішує [лінкер](book:programming/linking) під час збірки: бойова ціль бере перший, тестова — другий. Сам код під тестом викликає функцію **напряму**, без жодного вказівника, і навіть не здогадується про підміну. Цей шов так і звуть — **шов на етапі лінкування** (англ. *link-time seam*).

```c
// sensor.h — спільний контракт для обох збірок:
int sensor_read_temp(void);

// sensor_hw.c — лінкуємо в бойову прошивку:
int sensor_read_temp(void) { return read_i2c_sensor(); }   // справжнє залізо

// sensor_fake.c — лінкуємо в тест замість sensor_hw.c:
static int g_next;
void sensor_set_temp(int t) { g_next = t; }                // тест задає сценарій
int sensor_read_temp(void) { return g_next; }              // підроблена відповідь
```

Саме так працює **Ceedling** — збірковий рушій для тестів прошивки: для кожного тесту він збирає окремий бінар, у який лінкує тестований модуль разом зі згенерованими підробками решти, а справжні драйвери просто не потрапляють у збірку. Перевага шва в тому, що в бойовому коді не лишається **анічогісінько** зайвого: ні структури, ні непрямого виклику — драйвер кличеться прямо й вбудовується. Платня — грубість підміни: міняється **цілий файл**, не окрема функція. Якщо в одному модулі є і те, що хочеться підмінити, і те, що хочеться лишити справжнім, доведеться їх розділяти.

Тонкий різновид цього шва — **слабкі символи** (англ. *weak symbol*): драйвер позначають як «слабке» означення, і якщо в збірці трапиться звичайне («сильне») означення тієї самої функції, лінкер мовчки візьме сильне, відкинувши слабке. Так у тесті можна перекрити окрему функцію, не чіпаючи решти файлу. Механізм зручний, але менш явний, ніж два окремі файли: підміна стається «сама собою» за правилом лінкера, і недосвідчене око не одразу побачить, котре означення переможе.

### Шов третій: препроцесор — і чому він найгірший

Третій шов — найпростіший на вигляд і найгірший по суті. Можна обгорнути код умовною компіляцією: `#ifdef TEST` — одна гілка, `#else` — інша. Препроцесор виріже непотрібну гілку ще **до** компіляції, і в бінар потрапить лише одна з них.

```c
// ПРЕПРОЦЕСОРНИЙ шов — так робити НЕ варто:
int sensor_read_temp(void) {
#ifdef TEST
    extern int g_fake_temp;
    return g_fake_temp;        // у тестовій збірці
#else
    return read_i2c_sensor();  // у бойовій збірці
#endif
}
```

Корінь біди видно одразу: тестова й бойова збірки — це **два різні вихідники**. Усе під `#else` компілятор у тестовому прогоні навіть не бачить — не перевіряє ні синтаксис, ні типи. Виходить парадокс: ви старанно ганяєте тести, вони зеленіють, а перевіряли ви **не той код**, що поїде в чіп. У бойову гілку можна непомітно внести помилку, і жоден тест її не зачепить, бо в тесті її просто не існувало. Що рясніше `#ifdef`-ів, то далі розповзаються дві версії — аж доки «протестовано» перестає означати бодай щось про прошивку в полі. Препроцесорну підміну тримають хіба для випадків, де іншого шва справді не прокласти (наприклад, прибрати на хості асемблерну вставку, якої там не існує), і тримають мінімально.

Спільне правило, що впорядковує всі три: **що пізніше обирається підміна, то ближчий тест до правди**. Рантайм (вказівники) і збірка (лінкування) лишають у чипі рівно той машинний код, який бачив тест, — різниця лише в тому, кого під'єднали. Вихідник (препроцесор) підсовує в чіп **інший** код, тож висновок тесту вже не про бойову прошивку. Тому в живій практиці прошивок переважають перші два шви, а третій — крайній захід.

## Unity, CMock, Ceedling: як це працює всередині

Робити дублі й перевірки руками щоразу — марнування часу, тож для C склалася стала трійця інструментів, і варто розуміти не лише що вони роблять, а **як** улаштовані, бо саме механіка пояснює їхні межі.

### Unity: перевірки й раннер

**Unity** — крихітний фреймворк самих перевірок, написаний чистою ANSI C (один `.c` і пара `.h`), тому компілюється навіть під голий мікроконтролер. Серце Unity — родина макросів-перевірок (англ. *assertion*, твердження, яке мусить справдитися): `TEST_ASSERT_EQUAL_INT(очікуване, дійсне)` для цілих, `TEST_ASSERT_EQUAL_HEX8` для байтів у шістнадцятковому, `TEST_ASSERT_EQUAL_PTR` для вказівників, `TEST_ASSERT_TRUE`, `TEST_ASSERT_EQUAL_STRING` для рядків, `TEST_ASSERT_EQUAL_MEMORY` для блоків пам'яті. Окремі макроси замість одного універсального — не примха: вони знають **тип** і тому при провалі друкують зрозуміле «очікував 25, дістав −40 у рядку 47», а не голе «не дорівнює».

Чому окремий макрос на кожен тип, а не один на все? Бо C не має узагальнень (англ. *generics*) і під час виконання нічого не знає про тип значення — лише його байти. Якби макрос був один, він не зміг би відрізнити число від вказівника й надрукувати їх по-людськи. Тому Unity «зашиває» тип у саму назву макроса: `_INT` форматує як знакове десяткове, `_HEX8` — як два шістнадцяткові розряди, `_PTR` — як адресу. Тип, відомий у момент написання тесту, компенсує те, чого C не знає в рантаймі.

Тіло тесту тримається ладу «дано — коли — тоді»: підготуй стан, виконай дію один раз, звір результат. Унаслідок цього тест читається як виконуваний опис наміру:

```c
#include "unity.h"
#include "thermostat.h"

void test_overheat_triggers_safe_mode(void) {
    Thermostat t;
    thermostat_init(&t);              // дано: свіжий стан
    thermostat_feed_temp(&t, 95);     // коли: прийшла температура 95
    TEST_ASSERT_TRUE(t.safe_mode);    // тоді: пристрій у безпечному режимі
    TEST_ASSERT_EQUAL_INT(0, t.heater_pwm);  // і нагрівач вимкнено
}
```

А як ці окремі функції стають програмою, що бігає? Раннер (англ. *runner*, «бігач» — те, що по черзі запускає тести) — це звичайна `main`, яку обрамляють макросами: `UNITY_BEGIN()` на початку, по `RUN_TEST(...)` на кожен тест, `UNITY_END()` наприкінці, аби підбити підсумок. `RUN_TEST` не просто викликає функцію: перед кожним тестом він кличе `setUp()`, а після — `tearDown()`. Ці дві функції пишете ви, і в них кладуть спільну підготовку й прибирання — щоб **кожен** тест стартував з чистого аркуша й не успадковував сміття від сусіда. Ізоляція тестів — не випадковість, а робота `setUp`/`tearDown`, які раннер чесно викликає навколо кожного прогону.

```c
static Thermostat t;
void setUp(void)    { thermostat_init(&t); }   // перед КОЖНИМ тестом
void tearDown(void) { /* нічого звільняти */ }

int main(void) {
    UNITY_BEGIN();
    RUN_TEST(test_overheat_triggers_safe_mode);
    RUN_TEST(test_normal_temp_keeps_running);
    return UNITY_END();   // ненульовий код = були провали (для CI)
}
```

Писати цей перелік `RUN_TEST` руками нудно й легко забути новий тест, тому Unity має скрипт-генератор `generate_test_runner.rb`, який сам сканує файл за угодою про назви (`test_...`) і пише раннер за вас. Важлива деталь: **Ruby тут не обов'язковий** — генератор лише зручність; за бажання раннер пишуть руками, і Unity від цього працює так само. Це й тримає Unity придатним для найскромнішого заліза: жодних зовнішніх залежностей у самому фреймворку.

### CMock: мок із заголовка

Писати дублі руками для кожної функції HAL — нудно й помилконебезпечно. **CMock** автоматизує це: він читає **заголовок** вашого інтерфейсу (`.h`) і **сам генерує** з кожного оголошення мок з повним набором керувальних функцій. Сам CMock — утиліта мовою Ruby, але працює вона **на етапі збірки**, а згенерований мок — це звичайний C, що лінкується в тест. Тобто Ruby бере участь у виробленні коду, а в самому тесті на чипі чи на хості його немає.

З оголошення `int i2c_write(uint8_t addr, uint8_t reg, uint8_t val);` CMock породжує сімейство функцій, кожна з яких керує моком по-своєму:

- `i2c_write_ExpectAndReturn(addr, reg, val, retval)` — «очікую, що `i2c_write` викличуть саме з цими аргументами, і тоді поверну `retval`». Це і заглушка (диктує відповідь), і мок (перевіряє аргументи) в одному.
- `i2c_write_Expect(addr, reg, val)` — те саме для функції, що нічого не повертає.
- `i2c_write_IgnoreAndReturn(retval)` — «не зважай, з чим кличуть, скільки разів, просто завжди повертай це»; так роблять із функціями, що не в фокусі тесту.
- `i2c_write_ReturnThruPtr_...` — для аргументів-вказівників, куди функція має щось **записати**: задає значення, яке мок підсуне у вказану комірку (бо у справжньому драйвері відповідь приходить через вихідний параметр).

Дві властивості згенерованого мока роблять його по-справжньому сильним. Перша — **перевірка порядку**: якщо виставити кілька `ExpectAndReturn` поспіль, CMock запам'ятовує їх **як чергу** й вимагає, щоб реальні виклики йшли **рівно в тому самому порядку**. Зайвий виклик, пропущений виклик, переставлені місцями — усе це провалює тест. Друга — **точкове послаблення вимог**: `i2c_write_IgnoreArg_val()` каже «з цього очікування звіряй адресу й регістр, а на третій аргумент не зважай» — корисно, коли одне поле непередбачуване (скажімо, мітка часу), а решту перевірити треба. Це тонше за грубе «ігноруй усі аргументи»: ви слабшаєте контроль рівно на одне поле, лишаючи решту під наглядом.

CMock іде в парі з **CException** — крихітним механізмом винятків для C поверх `setjmp`/`longjmp` (стандартні засоби «стрибнути» по стеку з глибини назад у заздалегідь поставлену точку). Прошивці винятки рідко потрібні в бою, але в тестах CException дає мокам спосіб **перервати** виконання, коли очікування порушено, — викинути виняток замість того, щоб мовчки повертати й сподіватися, що тест колись помітить негаразд.

### Ceedling: складач, що зшиває все

Окремо Unity, CMock і CException — деталі. Зшиває їх у конвеєр **Ceedling** — збірковий рушій під тести C. Для кожного тестового файлу він робить рутину, яку інакше робили б руками: знаходить, які заголовки той файл підключає, генерує CMock-моки на потрібні інтерфейси, генерує Unity-раннер, компілює тестований модуль укупі з моками в **окремий бінар** і запускає його. Саме звідси береться **підміна на лінкуванні**: справжні драйвери в цю збірку просто не входять — їхнє місце займають моки, тож код під тестом викликає мок напряму, не знаючи про це. Один прогін `ceedling test:all` — і кожен модуль перевірено в ізоляції, з власним набором підробок.

### Робочий приклад: мок драйвера давача й перевірка послідовності

Зведімо це в один правдоподібний випадок. Багато давачів на шині I2C працюють за протоколом «спершу запиши номер регістра, потім читай дані звідти». Логіка читання мусить зробити **дві дії в правильному порядку**: написати в давач адресу потрібного регістра, тоді прочитати з нього байт. Найгірший баг тут — не криве число, а **переставлений** чи **пропущений** крок: код, що читає, не написавши спершу регістр, дістане сміття або зависне, хоча на стенді з конкретним давачем інколи «випадково працює». Перевірити треба саме **взаємодію** — тут потрібен мок, не заглушка.

```c
// драйвер давача залежить від інтерфейсу шини (заголовок i2c.h):
//   int i2c_write_reg(uint8_t dev, uint8_t reg);   // обрати регістр
//   int i2c_read_byte(uint8_t dev, uint8_t *out);  // прочитати байт

#include "unity.h"
#include "mock_i2c.h"      // CMock згенерував це з i2c.h
#include "sensor.h"

#define DEV  0x40
#define REG_TEMP 0x07

void test_read_temp_writes_register_then_reads(void) {
    uint8_t fake = 25;

    // 1) очікуємо: спершу драйвер ОБЕРЕ регістр температури і дістане OK
    i2c_write_reg_ExpectAndReturn(DEV, REG_TEMP, 0);

    // 2) ПОТІМ прочитає байт; підсунемо 25 у вихідний параметр
    i2c_read_byte_ExpectAndReturn(DEV, NULL, 0);
    i2c_read_byte_IgnoreArg_out();          // адресу буфера наперед не знаємо
    i2c_read_byte_ReturnThruPtr_out(&fake); // у *out мок покладе 25

    // дія під тестом:
    int t = sensor_read_temp(DEV);

    // CMock уже перевірив, що обидва виклики були, з тими аргументами,
    // і саме в цьому порядку. Лишилось звірити результат логіки:
    TEST_ASSERT_EQUAL_INT(25, t);
}
```

Цінність прикладу — у тому, що він **ловить помилку, невидиму з результату**. Якби `sensor_read_temp` прочитала байт, забувши спершу написати регістр, чи зробила це у зворотному порядку, число на виході могло б навіть випадково збігтися, — але CMock завалить тест, бо реальна черга викликів розійдеться з очікуваною. `IgnoreArg_out` тут навмисний: адресу буфера, куди драйвер захоче читати, ми наперед не знаємо й не маємо до неї діла, тож знімаємо контроль рівно з цього аргументу, лишаючи під наглядом і адресу пристрою, і факт виклику, і порядок. Ось де окупається тонке розрізнення дублів: грубша заглушка пропустила б цей клас багів повз себе.

## Час і переривання: межа хоста й як її посунути

Найкаверзніше в прошивці — те, що пов'язане з часом і [перериваннями](book:programming/interrupts). Воно опирається тестам глибше за будь-яку логіку, і причини варто розкласти, бо для кожної є свій прийом, а одна межа лишається непереборною на хості.

### Чому час так важко тестувати

Логіка таймаутів дивиться на годинник: «якщо відповідь не прийшла за 5 секунд — оголосити збій». Якщо така перевірка читає **справжній** лічильник часу всередині себе, то єдиний прямий спосіб дочекатися спрацювання — **просидіти реальні 5 секунд**. Тест, що чекає секунди, перетворює швидкий набір на черепаху, а головне — стає **хистким** (англ. *flaky*, мерехтливий): під навантаженням системи перевірка то встигає, то ні, межа спрацьовує то так, то інакше, і зелений колір перестає щось гарантувати. Корінь біди — те, що годинник став **невидимою залежністю**, зашитою всередину логіки.

### Прийом: інжектувати джерело часу

Ліки — той самий шов, але навколо часу. Логіка не читає годинник сама, а **отримує поточний час ззовні** — через подану функцію `now()` чи прямим параметром-тіком. У бою за `now()` стоїть справжній [апаратний лічильник](book:programming/timer-counter); у тесті — звичайна змінна, якій **тест сам підкручує** значення. Тоді «минуло 6 секунд» настає **миттєво** й **однаково щоразу**: не чекаємо реального часу, а ставимо його, як стрілки на годиннику.

![Інжекція джерела часу: ліворуч код читає справжній millis() усередині й у тесті треба чекати реальні секунди (повільно, хистко); праворуч now() подається ззовні, тест задає now=0, крок, now=6000 — таймаут настає миттєво й детерміновано](/root/course/embedded/firmware-testing/img/time-injection.svg)
*Ліворуч годинник зашитий у логіку — щоб настав таймаут, тест мусить ЧЕКАТИ справжні секунди, і результат хисткий. Праворуч джерело часу винесене за шов — тест підкручує `now` стрибком, і межа спрацьовує миттєво й повторювано. Винесений годинник стає кермом, а не секундоміром.*

```c
// БУЛО: годинник зашитий усередину — тест мусить чекати реальний час
bool timed_out_bad(uint32_t start) {
    return millis() - start > 5000;   // millis() — справжній лічильник
}

// СТАЛО: час подають ззовні — у бою справжній, у тесті керований
bool timed_out(uint32_t now, uint32_t start) {
    return now - start > 5000;
}

// тест — без жодного реального чекання, миттєво й детерміновано:
void test_timeout_boundary(void) {
    uint32_t t0 = 1000;
    TEST_ASSERT_FALSE( timed_out(t0 + 5000, t0) );  // рівно на межі — ще ні
    TEST_ASSERT_TRUE ( timed_out(t0 + 5001, t0) );  // на мілісекунду далі — так
}
```

Зверніть увагу на пару перевірок навколо **самої межі** (5000 проти 5001): саме тут живуть помилки «на одиницю» (англ. *off-by-one*) — `>` проти `>=`, увімкнена чи вимкнена гранична мить. Доки час чекали по-справжньому, дослідити межу так точно було неможливо; щойно час став керованим, гранична мить перевіряється двома рядками. Це той самий виграш, що й від підміни заліза, тільки застосований до годинника: винісши залежність за шов, ви дістаєте над нею повну владу в тесті.

Окрема пастка часу — **переповнення лічильника**: апаратний таймер рано чи пізно дійде до максимуму й [обнулиться](book:programming/timer-counter), і наївне `target = now + delay` зламається на стику. Інжектований час дає це перевірити прямо: задайте `now` біля самого краю діапазону, тоді — після обнулення, і подивіться, чи логіка витримала перехід. На реальному залізі чекати того стику довелося б десятки хвилин або й годин.

### Логіка з переривання — без самого переривання

[Обробник переривання](book:programming/isr) (англ. *ISR*, *interrupt service routine*) важко тестувати з тієї ж причини, що й час: його **не викликають** напряму з програми — його смикає залізо в непередбачувану мить. Спинити цей момент чи відтворити його на замовлення хост не вміє. Та частіше за все всередині обробника сидить звичайна **логіка** — розкласти прийнятий байт, перекласти лічильник стану, вирішити, що робити з подією. І от її від самого механізму переривання можна **відірвати**.

Прийом простий: тіло корисної роботи виносять в окрему звичайну функцію, а сам обробник стає тоненькою обгорткою, яка лише гукає цю функцію.

```c
// ВСЕ в обробнику — логіку не дістати тестом окремо:
volatile uint8_t rx_state;
void UART_ISR_bad(void) {
    uint8_t b = UART_DATA;        // читаємо залізний регістр
    if (b == 0x7E) rx_state = 1;  // ...а тут уже чиста логіка, замурована в ISR
    else if (rx_state == 1) { /* ... */ }
}

// ВІДОКРЕМЛЕНО: логіка — звичайна функція, обробник лише годує її байтом
uint8_t frame_step(uint8_t state, uint8_t b) {
    if (b == 0x7E) return 1;      // початок кадру
    if (state == 1) return 2;     // перший байт тіла
    return state;
}
void UART_ISR(void) {             // тонка обгортка: лише міст до заліза
    rx_state = frame_step(rx_state, UART_DATA);
}

// тепер логіку ганяємо на хості як завгодно ретельно:
void test_frame_sync(void) {
    TEST_ASSERT_EQUAL_UINT8(1, frame_step(0,    0x7E)); // маркер → синхронізувалися
    TEST_ASSERT_EQUAL_UINT8(2, frame_step(1,    0x10)); // далі — перший байт тіла
    TEST_ASSERT_EQUAL_UINT8(0, frame_step(0,    0x10)); // байт без маркера → стоїмо
}
```

Лишивши в обробнику **лише** дотик до заліза (прочитати регістр, скинути прапорець), а всю кмітливість винісши в чисту функцію, ви робите найскладнішу частину переривання звичайною тестовною логікою. Сам обробник стає таким тонким, що дивитися в ньому вже майже нема на що, і його лишають на тести на залізі.

### Гонки — непереборна межа хоста

Та один клас багів навколо переривань хост **не зловить за визначенням** — це **гонки** (англ. *race condition*, «стан перегонів»: результат залежить від того, хто кого випередив у часі). Класична гонка прошивки — основний код читає [багатобайтну змінну](book:programming/atomicity-races), а посеред читання влітає переривання й міняє її; код дістає половину старого значення, половину нового. Чи прокинеться обробник саме в ту мікроскопічну щілину між двома інструкціями — питання **реального таймінгу**, а його хост не відтворює: на ПК немає ні справжніх переривань вашого чипа, ні його тактів, ні його конвеєра.

Логіку **захисту** від гонки перевірити на хості ще можна — наприклад, що критична ділянка [правильно вимикає переривання](book:programming/atomicity-races) на час доступу. Але саму гонку **спровокувати**, довести, що без захисту воно справді рветься саме тут, — лише на залізі, де є справжній недетермінізм. Це і є природна стеля нижніх шарів піраміди: усе, що тримається на реальному збігу моментів у часі — гонки, тонкощі затримок обробника, [просідання живлення](book:programming/brownout) рівно на стику операцій, — лишається роботою тестів на справжньому чипі. Хост і моки прибирають усе, що **можна** відірвати від фізики часу; те, що **не можна**, чесно віддають нагору.

## Стенд для тестів на залізі: з чого він складається

Коли баг живе лише в реальному таймінгу й електриці, тест переїжджає на справжній чіп. Підхід «залізо просто в тестовій петлі» (англ. *hardware-in-the-loop*, HIL) — не одна плата на столі, а **стенд** із кількох частин, і кожна з'явилася, щоб закрити свою діру.

Серце стенда — **тест-раннер на ПК**: він роздає завдання, збирає звіти й виносить вердикт. Перед ним — **плата під тестом** (англ. *device under test*, DUT) з тестовою прошивкою. Але плата сама по собі мало що доводить: щоб перевірити цікаве, потрібна **керована оснастка** навколо неї, і саме вона відрізняє серйозний стенд від «увімкнув і дивлюся».

Першою постає **керована живленням оснастка** — релейна чи електронно-керована плата, якою раннер вмикає, вимикає й **просаджує** живлення DUT. Без неї годі чесно перевірити [реакцію на просідання](book:programming/brownout): як прошивка переживає падіння напруги, чи коректно [перезапускається](book:programming/reset-causes), чи не псує збереженого стану, коли її «вбивають» посеред запису. Просто висмикувати дріт руками щоразу й у потрібну мить неможливо — тому подачу живлення віддають під команду.

Далі — **програмований генератор і вимірювач** (генератор сигналів та аналого-цифровий перетворювач під керуванням раннера). Генератор подає на входи DUT задані сигнали — рівні, частоти, форми, — імітуючи давачі й зовнішні події; вимірювач читає виходи DUT і звіряє, що пристрій видав, що мусив. Так перевіряють реальні аналогові ланцюги, яких симуляція не відтворює.

І ще один простий, але плідний прийом — **петля назад** (англ. *loopback*): вихід DUT з'єднують прямо з його ж входом. Пристрій щось видає, сам це приймає, а тест звіряє послане з прийнятим. Так одна плата перевіряє власні шини й порти без жодного зовнішнього приладу: передавач шле — приймач ловить — раннер порівнює.

Як же стенд дізнається вердикт? Найчастіше — **через послідовний порт** (англ. *serial*). Тестова прошивка проганяє перевірки прямо на чипі (тим самим Unity, лише зібраним під ціль) і **друкує** підсумок у порт: які тести пройшли, які впали, рядки провалів. Раннер на ПК читає цей потік, розбирає його й перетворює на загальний «пройдено / провалено». Так само це лягає в [безперервну інтеграцію](book:programming/static-analysis): на кожен внесок код прошивається на реальні плати, стенд ловить serial-лог і повертає вердикт автоматично — тестування на залізі стає не ручним обрядом, а ланкою конвеєра.

### Чому HIL «мерехтить» і як із цим живуть

За реалістичність HIL платить **крихкістю**: апаратні тести легше за всіх інших стають хисткими — то проходять, то ні **без жодної зміни коду**. Причини фізичні: тонкий контакт у роз'ємі, наведення на дроті, дрейф від температури, нестабільне USB, дрібні розбіжності таймінгу від прогону до прогону. Один і той самий тест, прогнаний десять разів, може дати дев'ять зелених і одне червоне — і це не баг прошивки, а мерехтіння стенда.

З мерехтінням не «борються» наскоком, а **загороджуються** дисципліною. Стенд роблять механічно надійним — якісні роз'єми, короткі екрановані дроти, чисте живлення, бо більшість мерехтіння родом саме з фізики з'єднань. Кожен тест перед роботою **приводить DUT у відомий стан** (скидання, чиста конфігурація), щоб не успадкувати наслідків попереднього. Хистку перевірку, яку поки не приборкали, чесно **позначають** хисткою й виносять з блокувального набору, щоб вона не валила збірку наосліп, — але не викидають і не ховають, бо інколи за «мерехтінням» ховається справжній рідкісний баг, який тільки так і виявляється. А коли тестів і плат стає багато, будують **ферму плат** (англ. *board farm*) — десятки DUT під одним керуванням, де прогони розкидані по багатьох однакових пристроях; це і пришвидшує, і допомагає відрізнити дефект однієї плати від справжньої вади прошивки: баг коду впаде **скрізь**, а кепський контакт — лише на одному екземплярі.

> 🔧 **Навіщо це.** Поділ роботи між стендом і нижніми шарами — питання грошей і нервів, не чистоти заради чистоти. HIL дорогий (залізо, оснастка, обслуговування) і повільний, тож на нього виносять **лише** те, що інакше не перевірити: реальний таймінг, гонки, аналогові ланцюги, поведінку при [просіданні живлення](book:programming/brownout). Усе, що можна відірвати від фізики, давно вже перевірено внизу за секунди. Стенд — не заміна юніт-тестам, а їхнє доповнення на тому вузькому фронті, де правду каже лише кремній.

## Покриття на цілі: скільки коду торкнулися тести

Природне питання до набору тестів — **скільки** коду вони насправді зачіпають. Відповідь дає **покриття** (англ. *coverage*): інструмент рахує, які рядки й гілки виконалися під час прогону, і показує, що лишилося неторканим. На хості це дешево й звично; на самій цілі — окрема історія, і варто розуміти і види покриття, і чому на чипі за нього доводиться платити.

### Три глибини: рядки, гілки, MC/DC

**Рядкове покриття** (англ. *statement coverage*) — найгрубіше: чи виконався кожен рядок бодай раз. Легко набрати, легко й обманутися: рядок `if (a && b) safe();` зараховується виконаним, навіть якщо `safe()` жодного разу не спрацював — сам рядок умови ж пройшли.

**Гілкове покриття** (англ. *branch coverage*) суворіше: для кожного розгалуження вимагає пройти **обидва** боки — і коли умова правдива, і коли хибна. Тепер замало, щоб керування дійшло до `if`; треба, щоб воно і **зайшло** в гілку, і **обійшло** її. Це ловить цілий клас прогалин, де небезпечний бік розгалуження ні разу не випробували.

**MC/DC** (англ. *modified condition/decision coverage*, покриття модифікованих умов і рішень) — найсуворіший рівень, якого вимагають у критичній до безпеки авіоніці (стандарт DO-178C). Він вимагає показати, що **кожна окрема умова** в складеному рішенні **самостійно** впливає на результат: для `if (a && b && c)` треба добрати такі набори входів, де по черзі видно вплив кожного з `a`, `b`, `c` нарізно, не лише різних комбінацій разом. Це різко піднімає число потрібних тестів, зате доводить, що жодна під-умова не висить мертвим вантажем.

### Чому на цілі покриття дороге

Як інструмент дізнається, що рядок виконався? Компілятор **вставляє лічильники**: біля кожного рядка чи гілки додається невидимий код, що при проходженні смикає лічильник у пам'яті (типовий механізм — `gcov` із набору GCC). На великому ПК це дрібниця. На мікроконтролері — ні, і одразу з двох боків. По-перше, лічильники **роздувають код**: кожна гілка обростає зайвими інструкціями, і прошивка з покриттям помітно більшає — а [місця у Flash](book:programming/firmware-image) на МК і так у обріз, інструментована збірка може просто **не влізти**. По-друге, лічильники **сповільнюють** виконання: зайвий код на кожному кроці краде такти, а на чипі, де ресурс і так скромний, це збиває реальний таймінг — і тести, чутливі до часу, починають поводитися інакше, ніж бойова прошивка.

Звідси два практичні наслідки. Найчастіше покриття міряють **у хост-збірці**: та сама логіка, скомпільована під ПК, інструментується дешево, рахується швидко й не тисне ні на Flash, ні на такти — а покриття логіки нас і цікавить найбільше. Коли ж покриття треба зняти **саме на цілі** (бо так вимагає сертифікація або бо код не відірвати від заліза), лічильники тримають окремо: їх збирають у виділену **секцію пам'яті** й періодично **вивантажують** на ПК через [послідовний порт](root:embedded/jtag-swd-tools) чи [відлагоджувальний канал](root:embedded/jtag-swd-tools), не намагаючись утримати все в тісній пам'яті чипа. Так знімають реальне покриття цільового коду, не вимагаючи, щоб уся бухгалтерія вмістилася поряд із самою прошивкою.

### Чому 100% не дорівнює коректності

Найважливіше про покриття — те, чого воно **не** означає. Сто відсотків покриття кажуть лише, що тести **торкнулися** всього коду, а не що вони **перевірили** його як слід. Різниця глибока: покриття міряє, куди дійшло виконання, а не чи правильні були твердження про результат.

```c
// функція з багом: ділення, що впаде при d == 0
int scale(int v, int d) {
    return v / d;        // d == 0 → ділення на нуль (HardFault на МК)
}

// тест дає 100% рядкового І гілкового покриття — рядок єдиний, гілок нема:
void test_scale(void) {
    TEST_ASSERT_EQUAL_INT(5, scale(10, 2));   // 10/2 = 5 ✓
}
```

Цей єдиний тест **повністю** покриває `scale` — рядок один, розгалужень немає, лічильник зелений на сто відсотків. А найгрубіший баг — падіння при `d == 0` — лишається непоміченим, бо такого входу тест просто не подав. Покриття показало, що рядок **виконали**; воно й не думало перевіряти, що його випробували **небезпечним** значенням. Тому сто відсотків — стеля **охоплення**, а не свідоцтво **правильності**: вони кажуть «неперевіреного коду не лишилося», але нічого — про якість самих перевірок.

Звідси здорове ставлення: покриття цінне як **підказка прогалин**, а не як мета. Низьке покриття чесно тицяє пальцем — «ось ці гілки логіки ще ніхто не випробував, тут небезпечно». Високе ж не дає права заспокоїтися: воно лише знімає одне просте питання («чи всюди дійшли тести») і не торкається складного («чи правильні самі тести й чи добрані каверзні входи»). Гнатися за цифрою заради цифри — дописувати порожні тести, що проходять рядки без жодного осмисленого твердження, — означає роздути показник, не додавши ні крихти впевненості.

## Рівні перевірки: де юніт, де інтеграція, де система

Усе наведене вище — це переважно **юніт-тести**: перевірка окремої одиниці (функції, модуля) в **ізоляції**, де всі сусіди підмінені дублями. Це підніжжя піраміди й найбільший за обсягом шар. Та над ним стоять ще два рівні дисципліни, і варто бачити, коли який доречний, бо застосований не на своєму місці тест дорого коштує й мало доводить.

**Інтеграційний тест** (англ. *integration*, об'єднання) перевіряє, як модулі працюють **разом**, уже **без** підміни стику між ними. Юніт-тест драйвера давача мокає шину; інтеграційний бере **справжній** драйвер укупі зі **справжнім** стеком шини й перевіряє, що вони стикуються — що формати збігаються, що порядок викликів узгоджений, що припущення одного боку справджуються на іншому. Сюди добре лягає [емулятор цілої плати](root:embedded/firmware-testing/proj-emulators.md): він виконує справжній код драйвера на справжніх (хай і підроблених) адресах регістрів, тож перевіряє саме **зчеплення** драйвера із залізним рівнем, а не лише логіку над ним.

**Системний тест** (англ. *system*) піднімається ще вище: перевіряє **поведінку пристрою як цілого**, ззовні, очима користувача чи сусідньої системи. Не «чи правильна функція» і не «чи стикуються модулі», а «чи робить готовий пристрій те, що обіцяно» — увімкнули, подали вхід, поспостерігали вихід. Це здебільшого парафія HIL-стенда (готова прошивка на реальній платі) або, коли прошивка керує цілим апаратом, [симуляції всього апарата](book:programming/sitl-simulation), де модель фізики заступає і чіп, і світ навколо.

Чому не зробити все системними тестами — вони ж найреалістичніші? Бо вони й найдорожчі, найповільніші й найгірше вказують **де** саме поламалося: системний тест червоніє «пристрій повівся не так», а в якому з десятків модулів причина — мовчить. Юніт-тест навпаки: дешевий, миттєвий і б'є точно в винну функцію. Тому дисципліни розкладають за тією ж логікою піраміди — масу перевірок робити юнітами (дешево, точно, багато), менше інтеграційними (зчеплення вузлів), і зовсім трохи системними (поведінка цілого). Кожен рівень бере на себе те, що йому до снаги, і не вдає, ніби може все: юніт не доведе, що пристрій загалом працює, а системний не скаже, який саме рядок винен. Сила — у їхній сукупності, де нижні шари відсівають масу багів дешево, а верхні ловлять лише те, що прослизнуло крізь усі сита нижче.
