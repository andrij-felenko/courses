Партія з п'ятисот автономних телеметричних контролерів для зрошувальних систем успішно проходить усі лабораторні тести на столі: прошивка стабільно надсилає телеметрію через LoRaWAN, зчитує показання тиску й відкриває 24-вольтовий електромагнітний клапан за командою. Проте вже на третій місяць експлуатації в полі чотирнадцять контролерів заклинюють клапан у постійно відкритому стані, затоплюючи насосну станцію через тепловий пробій силового MOSFET-транзистора від індуктивного викиду котушки. Ще вісім пристроїв назавжди втрачають зв'язок: внутрішня шина I²C кліматичного сенсора блокується на рівні логічного нуля через електростатичний розряд (англ. *electrostatic discharge*, ESD), підхоплений довгим зовнішнім дротом, що призводить до нескінченного циклу очікування в драйвері та вичерпання заряду акумулятора.

Жоден функціональний тест не зміг попередити цю аварію, оскільки перевірка працездатності оцінює лише номінальну поведінку справного виробу за нормальних умов. Інженерна матриця FMEA (англ. *Failure Mode and Effects Analysis*, від лат. *modus* — спосіб, вид) розвертає мислення розробника у протилежний бік: замість питання «як пристрій має працювати» вона систематично досліджує «якими фізичними способами кожен вузол зламається і що в цей момент відчує система». Складання власної таблиці відмов — це перехід від наївного сподівання на надійність деталей до побудови ешелонованої оборони, де кожен виявлений ризик перетворюється на конкретну схемну доробку чи рядок діагностичного коду.

> 🔧 **Навіщо це.** У розробці вбудованих систем вартість виправлення дефекту зростає на порядок на кожному етапі життєвого циклу: зміна схемотехніки на стадії проєктування коштує години роботи за САПР, переробка друкованої плати після виготовлення зразків — тисячі доларів, а польовий відклик тисячі загерметизованих приладів через вигорання транзистора або зависання шини перетворюється на банкрутство компанії. Матриця FMEA — це інструмент, який примушує знайти слабкі місця за кресленням до виготовлення першого зразка.

## Анатомія інженерної матриці: від декомпозиції до ланцюга наслідків

Складання таблиці відмов починається з функціональної декомпозиції виробу (лат. *decompositio* — розділення цілого на частини). Пристрій розбивають на окремі функціональні домени зверху вниз: від макрорівня системи до окремих мікросхем, пасивних компонентів, контактних роз'ємів і програмних задач операційної системи реального часу (англ. *Real-Time Operating System*, RTOS).

```
[ Повний вбудований виріб ]
 ├── 1. Підсистема живлення (Вхідний фільтр, захист від переполюсовки, DC-DC Buck, LDO)
 ├── 2. Обчислювальне ядро (MCU, тактовий генератор, ланцюг скидання NRST, Flash/EEPROM)
 ├── 3. Інтерфейсні шини й давачі (Шина I²C, SPI, АЦП, вхід 4–20 мА, захист портів GPIO)
 ├── 4. Силові актуатори й комутація (MOSFET-ключі, драйвери реле, захисні діоди)
 ├── 5. Бездротовий зв'язок (Тракт LoRaWAN/Wi-Fi, антена, узгоджувальний контур)
 └── 6. Конструктив і механіка (Кабельні вводи, тактові кнопки, ущільнення корпусу IP67)
```

Кожен виділений блок стає об'єктом аналізу в інженерній матриці. Структура рядка FMEA фіксує строгий причинно-наслідковий зв'язок, що складається з шести послідовних елементів:

1. **Вузол або компонент:** позиційне позначення на схемі та функціональне призначення (наприклад, `Q1: N-канальний MOSFET керування клапаном 24 В`).
2. **Потенційний вид відмови (англ. *Failure Mode*):** фізичне явище, через яке вузол втрачає працездатність (обрив ланцюга, коротке замикання між виводами, дрейф номіналу, зависання шини, некероване відкриття).
3. **Механізм або причина (англ. *Root Cause*):** першопричина збою (індуктивний сплеск `L·(di/dt)`, статичний розряд на клему, механічна втома пайки від температурних коливань, переповнення стека задачі).
4. **Локальний наслідок (англ. *Local Effect*):** що відбувається безпосередньо на виводах компонента (пробій переходу стік-витік, коротке замикання лінії живлення на землю).
5. **Системний наслідок (англ. *End Effect*):** вплив на поведінку всього виробу та користувача (клапан залишається постійно відкритим, відбувається затоплення об'єкта, пристрій перегрівається та виходить з ладу).
6. **Заходи запобігання та виявлення (англ. *Controls & Mitigations*):** схемотехнічні бар'єри (TVS-супресори, опторозв'язка, струмові шунти) та алгоритми прошивки (тайм-аути шини, періодичний опит АЦП, автоскидання).

![Структура інженерної матриці FMEA](/root/course/embedded/tablytsia-vidmov-svoho-prystroiu/img/fmea-matrix-structure.svg)
*Анатомія інженерної матриці FMEA: декомпозиція виробу на схемні блоки, ідентифікація фізичних механізмів відмов та їхня трансляція у конкретні контрзаходи.*

Головна помилка інженера-початківця — записувати в колонку наслідку стан самої деталі (наприклад, «транзистор згорів»). Справжній наслідок завжди описує стан кінцевої системи: втрату функції, пошкодження майна, ризик загоряння або неможливість зупинити привід. Оцінка небезпеки формується виключно на рівні кінцевого наслідку.

## Кількісні шкали оцінки: тяжкість (S), поява (O), виявлення (D)

Щоб ранжувати сотні виявлених режимів відмови за рівнем загрози, кожен рядок матриці оцінюють трьома незалежними ранговими показниками за шкалою від 1 до 10. Розділення цих осей є критичним: вони вимірюють принципово різні аспекти надійності.

### Тяжкість наслідків (Severity, S)

Тяжкість відображає ступінь шкоди для системи, оточення та людини, **якщо відмова вже виникла**. Цей показник розраховується виключно на правому кінці ланцюга (біля системного наслідку) і не залежить від того, наскільки рідкісною є несправність:

- **1 — Непомітний вплив:** користувач не помічає відхилень; незначне спотворення логу в пам'яті.
- **2–3 — Незначний вплив:** погіршення другорядних характеристик; перегорання допоміжного світлодіода індикації, що не заважає основній роботі.
- **4–6 — Помірний вплив:** часткова деградація функціональності; давач температури перестає відповідати, пристрій переходить на резервний консервативний режим роботи.
- **7–8 — Критичний вплив:** повна втрата основної функції без загрози життю; прилад вимикається, клапан блокується, потрібен виїзд сервісної бригади.
- **9–10 — Катастрофічний вплив:** загроза життю людей, виникнення пожежі, руйнування дорогого технологічного обладнання або некерований рух силового механізму.

### Частота виникнення (Occurrence, O)

Частота оцінює ймовірність появи конкретної фізичної причини за весь розрахунковий термін служби виробу (наприклад, 5 років або 50 000 годин роботи). Вона спирається на статистику дефектів на мільйон операцій (англ. *parts per million*, ppm), показник середнього напрацювання на відмову (англ. *Mean Time Between Failures*, MTBF) та закони фізики напівпровідників:

- **1 — Вкрай низька:** відмова практично неможлива (менше 1 відмови на 1 000 000 виробів); наприклад, пробій конденсатора з чотирикратним запасом за напругою.
- **2–3 — Низька:** поодинокі відмови протягом життєвого циклу (1:100 000 – 1:10 000); високоякісні компоненти, що працюють у номінальних теплових режимах.
- **4–6 — Помірна:** періодичні випадки у польових умовах (1:1 000 – 1:100); деградація електролітичних конденсаторів від нагріву, знос контактів реле при регулярній комутації струму.
- **7–8 — Висока:** часті відмови у важких умовах (1:50 – 1:10); окислення негерметичних клемних колодок на відкритому повітрі, електростатичні збої на довгих незахищених лініях зв'язку.
- **9–10 — Неминуча:** відмова майже гарантовано станеться (понад 1:10); тепловий розгін транзистора через відсутність тепловідводу або зависання прошивки через гарантоване переповнення 16-бітного лічильника мілісекунд через 65 секунд після старту.

### Здатність до виявлення (Detection, D)

Виявлення оцінює ймовірність того, що наявні засоби самодіагностики, тестування на виробництві або алгоритми прошивки **вчасно зафіксують дефект** до того, як він призведе до кінцевої катастрофи.

> ⚠️ **Зворотний характер шкали D:** значення 1 означає ідеальне миттєве виявлення (дефект гарантовано фіксується прошивкою за мікросекунди), тоді як значення 10 означає абсолютно латентну (приховану) відмову, яку неможливо виявити жодним існуючим методом.

- **1 — Миттєве виявлення вбудованою діагностикою:** апаратний компаратор або супервізор фіксує аварію струму за 50 нс і вимикає ШІМ; прошивка миттєво переводить систему в безпечний стан.
- **2–3 — Висока здатність:** драйвер періодично перевіряє діапазон аналогового сигналу або контрольні суми CRC пакетів кожні 10 мс; відмова ізолюється до накопичення шкоди.
- **4–6 — Помірна здатність:** несправність виявляється непрямими методами під час планового циклу опитування або фіксується під час автоматизованого тестування на заводському стенді (EOL-тест).
- **7–8 — Низька здатність:** дефект може бути виявлений лише за вторинними симптомами або оператором після погіршення роботи вузла.
- **9–10 — Виявлення неможливе:** латентна відмова (відпадання дублюючого фільтруючого конденсатора або деградація варистора захисту), яка нічим не проявляє себе, доки наступний імпульс перенапруги не знищить плату.

## Розрахунок критичності: вади чистого RPN та перехід до пріоритету дій (Action Priority)

Класична методика FMEA обчислює узагальнене число пріоритету ризику (англ. *Risk Priority Number*, RPN) шляхом простого множення трьох балів:

```
RPN = S · O · D
```

Оскільки кожна величина змінюється від 1 до 10, теоретичний діапазон RPN становить від 1 до 1000. Десятиліттями інженерні команди використовували спрощене правило: «будь-який рядок із RPN > 100 вимагає термінового доопрацювання, решта — допустимий ризик».

### Математичні вади та небезпеки класичного RPN

Сучасні стандарти функціональної безпеки (ISO 26262, IEC 61508, а також спільний стандарт AIAG & VDA 2019 року) відмовилися від чистого використання RPN через три фундаментальні математичні та інженерні дефекти:

1. **Нелінійність і порожнечі шкали:** із 1000 можливих цілих чисел у діапазоні `[1..1000]` операція множення трьох чисел `1..10` може дати лише **120 унікальних значень**. Понад 88% шкали залишається порожньою, а розподіл добутків має колосальний перекіс у бік малих значень.
2. **Множення порядкових (рангових) величин:** бали 1..10 є порядковими категоріями, а не фізичними величинами. Різниця між `S=9` (смертельна загроза) та `S=8` (зупинка без жертв) якісно не еквівалентна різниці між `S=2` та `S=3`. Множення таких рангових оцінок є некоректним з точки зору теорії вимірювань.
3. **Пастка маскування тяжкості:** множення робить показники взаємозамінними. Розглянемо два реальні випадки:
   - **Випадок А (пробій ключа клапана):** `S = 10, O = 2, D = 9` → `RPN = 10 · 2 · 9 = 180`. Відмова трапляється рідко, але призводить до повної втрати контролю над об'єктом.
   - **Випадок Б (перегорання службового LED):** `S = 3, O = 6, D = 10` → `RPN = 3 · 6 · 10 = 180`. Світлодіод часто перегорає і прошивка цього не бачить.

За формальним критерієм RPN обидва випадки мають однаковий пріоритет (180). Але випадок А створює катастрофічну аварію з першого ж спрацьовування, тоді як випадок Б є звичайною експлуатаційною незручністю.

![Матриця Action Priority проти чистого RPN](/root/course/embedded/tablytsia-vidmov-svoho-prystroiu/img/rpn-vs-ap-matrix.svg)
*Порівняння пріоритету дій (Action Priority) та пастки множення RPN: однаковий добуток 180 відповідає протилежним за рівнем загрози випадкам.*

### Методологія Action Priority (AP) за стандартом AIAG & VDA

Щоб подолати вади RPN, було впроваджено матричну класифікацію пріоритету дій (англ. *Action Priority*, AP). Вона ранжує ризики за трьома рівнями:

- **Високий пріоритет (High Priority, H):** обов'язкове впровадження апаратних змін у схему, додавання захисних компонентів або переписування архітектури безпеки. Проєкт не може бути переданий у виробництво без закриття цього ризику.
- **Середній пріоритет (Medium Priority, M):** необхідне впровадження додаткових діагностичних алгоритмів у прошивку, покращення технологічного контролю або додавання фільтрації сигналів.
- **Низький пріоритет (Low Priority, L):** ризик вважається прийнятним; достатньо штатного логування та моніторингу.

Логіка визначення AP будується на послідовній ієрархічній перевірці:

1. **Перший фільтр — Тяжкість (S):** якщо `S ∈ [9..10]`, режим відмови **автоматично** отримує статус High Priority при будь-якому `O ≥ 2`. Навіть при рідкісній імовірності катастрофічний наслідок не дозволяє ігнорувати захист.
2. **Другий фільтр — Частота (O):** при помірній тяжкості `S ∈ [7..8]` статус High призначається за високої частоти `O ≥ 4` та низької виявності `D ≥ 7`.
3. **Третій фільтр — Виявність (D):** показник `D` слугує тонким регулятором: якщо `S=7` і `O=4`, але прошивка гарантовано фіксує збій за мікросекунди (`D=1`), пріоритет знижується з High до Medium або Low.

## Класифікація відмов у вбудованих системах: фізика заліза та пастки прошивки

Розробка надійного пристрою вимагає глибокого розуміння фізичних процесів, що відбуваються на платі та в кристалі мікроконтролера під час аварійних режимів. У вбудованих системах відмови класифікують за трьома основними доменами.

![Класифікація типових відмов у вбудованих системах](/root/course/embedded/tablytsia-vidmov-svoho-prystroiu/img/embedded-failure-taxonomy.svg)
*Класифікація критичних режимів відмов у вбудованих пристроях за трьома інженерними доменами: схемотехнічним, програмним та конструктивним.*

### 1. Апаратні та електричні відмови

Електричні дефекти виникають через перевищення граничних експлуатаційних параметрів компонентів (Absolute Maximum Ratings) або деградацію матеріалів:

- **Ефект замикання (CMOS Latch-up):** статичний розряд або викид напруги вище `VDD + 0.3 В` на вході GPIO відкриває внутрішню паразитна чотиришарову структуру p-n-p-n (тиристор) у кристалі CMOS. Виникає пряме коротке замикання між шиною живлення та землею, струм зростає до сотень міліампер, і кристал вигорає за частки секунди, якщо живлення не буде негайно знято.
- **Тепловий розгін (англ. *Thermal Runaway*):** нагрів силового MOSFET-ключа призводить до зростання опору відкритого каналу `R_DS(on)`, що згідно з законом Джоуля-Ленца `P = I² · R` викликає ще більше виділення тепла. Якщо тепловідвід недостатній, температура кристала лавиноподібно досягає критичних `+150 °C` з наступним пробоєм.
- **Тріщини в багатошарових керамічних конденсаторах (MLCC):** механічний вигин плати при монтажі в корпус або температурні деформації призводять до виникнення мікротріщин у кераміці. Конденсатор у ланцюзі живлення перетворюється на низькоомний резистор, що спричиняє локальне нагрівання, обвуглювання текстоліту та коротке замикання шини живлення.
- **Індуктивний викид напруги:** при розмиканні струму в котушці реле або клапана зникаюче магнітне поле генерує ЕРС самоіндукції `V = -L · (di/dt)`. Імпульс амплітудою в сотні вольт миттєво пробиває стік комутуючого транзистора, якщо паралельно обмотці не встановлено захисний зворотний діод (англ. *flyback diode*) або TVS-супресор.

### 2. Програмні та системні відмови

Програмні дефекти у прошивці мікроконтролера часто маскуються під апаратні проблеми, оскільки блокують периферійні вузли та процесорне ядро:

- **Переповнення стека задачі (Stack Overflow):** виклик вкладених функцій з великими локальними буферами всередині задачі FreeRTOS виходить за межі виділеного стека і затирає сусідній блок керування задачею (англ. *Task Control Block*, TCB). Наслідок — збій диспетчера, стрибок за випадковою адресою (HardFault) або тихе пошкодження даних.
- **Апаратне блокування шини I²C (Bus Lockup):** якщо мікроконтролер скидається або перериває транзакцію саме в момент, коли ведений пристрій (slave) виставляє біт відповіді ACK (притягуючи лінію SDA до землі), лінія даних залишається заблокованою в низькому рівні. Жоден наступний запуск модуля I²C у мікроконтролері не може розпочати передачу, оскільки шина сприймається як зайнята.
- **Взаємне блокування (Deadlock) та інверсія пріоритетів:** дві RTOS-задачі захоплюють два м'ютекси у різному порядку, назавжди зупиняючи виконання обчислювального контуру без активації HardFault.
- **Пошкодження секторів Flash/EEPROM при зниженні живлення (Brown-out Write Corruption):** якщо напруга живлення мікроконтролера просідає нижче допустимого порогу під час запису сторінки енергонезалежної пам'яті, внутрішня помпа заряду Flash-пам'яті нездатна завершити тунелювання електронів. Результат — пошкодження заголовків файлової системи або калібрувальних коефіцієнтів у пам'яті.

### 3. Механічні та середовищні дефекти

- **Фретинг-корозія контактів (англ. *Fretting Corrosion*):** постійна мікровібрація від працюючого двигуна або вітрового навантаження спричиняє мікрозсуви контактів у роз'ємах. Тонкий шар позолоти стирається, оголюючи нікель або мідь, які швидко окислюються на повітрі, створюючи плаваючий контакт із високим перехідним опором.
- **Утворення конденсату під захисним лаком:** неправильне нанесення конформного покриття (англ. *conformal coating*) без попереднього сушіння та дегазації призводить до утворення мікропорожнин. При перепадах температури через точку роси в них конденсується волога, викликаючи електрохімічну міграцію металів (утворення дендритів) і коротке замикання високовольтних доріжок.
- **Зрив генерації кварцового резонатора:** накопичення бруду та флюсу біля виводів кварцу створює паразитну ємність і витік, зриваючи генерацію тактової частоти за високої вологості.

## Ієрархія інженерних контрзаходів: що лагодити першим

Отримавши список режимів відмов із високим пріоритетом (High AP), інженер постає перед вибором: як саме усувати виявлену небезпеку. Усі контрзаходи підпорядковуються суворій ієрархії ефективності (Safety Engineering Hierarchy).

![Ієрархія інженерних контрзаходів FMEA](/root/course/embedded/tablytsia-vidmov-svoho-prystroiu/img/mitigation-hierarchy.svg)
*Інженерна ієрархія контрзаходів FMEA: пріоритет віддається фізичному усуненню дефекту на рівні схеми та апаратним бар'єрам перед програмними підпорками.*

1. **Рівень 1 (Найвищий) — Усунення на рівні схемотехніки (Inherent Elimination):** фундаментальна зміна архітектури, яка робить відмову фізично неможливою. Заміна реле на твердотільний комутатор без рухомих контактів; вибір транзистора з напругою пробою `V_DS = 60 В` для лінії 24 В (дератинг); розв'язка чутливої аналогової землі від силової.
2. **Рівень 2 — Апаратні захисні бар'єри (Hardware Interlocks):** встановлення спеціалізованих захисних компонентів, що беруть удар на себе. Діоди TVS (супресори), самовідновні запобіжники PTC, мікросхеми «ідеальних діодів» для захисту від переполюсовки, зовнішні апаратні супервізори живлення.
3. **Рівень 3 — Апаратна надлишковість і резервування (Redundancy):** дублювання критичних вузлів. Використання двох незалежних давачів тиску різного принципу дії (тензорезистивний + п'єзорезистивний) або резервного барометра; плаваюче резервне джерело живлення.
4. **Рівень 4 — Активна самодіагностика та програмне відновлення:** реалізація алгоритмів контролю в прошивці. Моніторинг граничних значень АЦП (Range Check), періодичний розрахунок контрольних сум Flash (CRC32), програмна процедура розблокування шини I²C (генерація 9 тактів SCL через GPIO bit-banging), використання сторожового таймера (Watchdog) з незалежним генератором.
5. **Рівень 5 (Найслабший) — Пасивна сигналізація та експлуатаційні інструкції:** запис коду помилки в енергонезалежний лог, увімкнення червоного світлодіода несправності, вимога щомісячного регламентного огляду техніком.

> 💡 **Правило надійності:** програмна перевірка (Рівень 4) ніколи не повинна компенсувати відсутність обов'язкового апаратного захисту (Рівні 1–2). Якщо силовий транзистор згорає від індуктивного викиду за 200 наносекунд, жодна прошивка не встигне зреагувати, хоч би якою швидкою вона була.

### Аналіз результатів оптимізації

1. **Вузол живлення (PWR-01):** тяжкість наслідків `S=10` залишилася незмінною, оскільки пробій 24 В на лінію 3.3 В фізично смертельний для мікросхем. Проте додавання вхідного TVS-супресора зменшило ймовірність пробою з `O=3` до `O=1`, а вихідний eFuse унеможливив пожежу. Пріоритет дії знизився з High до Medium.
2. **Силовий ключ клапана (ACT-01):** додавання струмового шунта дозволило прошивці за кілька мікросекунд помітити, що струм через клапан тече навіть тоді, коли сигнал керування вимкнено (`D` знизилося з 8 до 2). Контролер негайно знеструмлює загальне реле аварійного живлення та відправляє тривожне повідомлення диспетчеру.
3. **Шина I²C (BUS-01):** завдяки впровадженню апаратно-програмного автоскидання (9 тактів SCL) показник виявлення та ізоляції дефекту досяг `D=1` — шина відновлюється автоматично без перезавантаження всього контролера.

Кожен критичний режим відмови отримує свій запис у постійній пам'яті (Flash/ROM), що містить порогові значення, пріоритет дії та вказівник на функцію апаратної самоперевірки.

fmea_action_priority_t fmea_calculate_ap(uint8_t s, uint8_t o, uint8_t d) {
    if (s >= 9) {
        if (o >= 2) return FMEA_AP_HIGH;
        return (d >= 5) ? FMEA_AP_HIGH : FMEA_AP_MEDIUM;
    }
    if (s >= 7) {
        if (o >= 8) return FMEA_AP_HIGH;
        if (o >= 6) return (d >= 5) ? FMEA_AP_HIGH : FMEA_AP_MEDIUM;
        if (o >= 4) return (d >= 7) ? FMEA_AP_HIGH : FMEA_AP_MEDIUM;
        return (d >= 7) ? FMEA_AP_MEDIUM : FMEA_AP_LOW;
    }
    if (s >= 4) {
        if (o >= 8) return (d >= 7) ? FMEA_AP_HIGH : FMEA_AP_MEDIUM;
        if (o >= 6) return FMEA_AP_MEDIUM;
        return (d >= 7) ? FMEA_AP_MEDIUM : FMEA_AP_LOW;
    }
    return (o >= 8 && d >= 7) ? FMEA_AP_MEDIUM : FMEA_AP_LOW;
}

void fmea_init(void) {
    for (int i = 0; i < FMEA_ID_COUNT; ++i) {
        g_fmea_state[i].fail_count = 0;
        g_fmea_state[i].last_fail_timestamp_ms = 0;
        g_fmea_state[i].is_active = false;
    }
}

void fmea_run_diagnostics(uint32_t current_time_ms) {
    for (int i = 0; i < FMEA_ID_COUNT; ++i) {
        const fmea_record_t *rec = &g_fmea_registry[i];
        if (rec->diag_func == NULL) continue;

        bool is_ok = rec->diag_func();
        if (!is_ok) {
            g_fmea_state[i].fail_count++;
            g_fmea_state[i].last_fail_timestamp_ms = current_time_ms;
            g_fmea_state[i].is_active = true;

            /* Спроба локального відновлення */
            if (rec->recovery_func != NULL) {
                rec->recovery_func();
            }
        } else {
            g_fmea_state[i].is_active = false;
        }
    }
}

bool fmea_is_system_safe(void) {
    for (int i = 0; i < FMEA_ID_COUNT; ++i) {
        if (g_fmea_state[i].is_active && g_fmea_registry[i].severity >= 8) {
            return false; /* Активна критична відмова */
        }
    }
    return true;
}

// FMEARegistry.hpp / FMEARegistry.cpp — Типобезпечний реєстр відмов на C++20
#pragma once

#include <cstdint>
#include <string_view>
#include <span>
#include <array>
#include <functional>

namespace embedded::fmea {

enum class ActionPriority : uint8_t {
    Low = 0,
    Medium,
    High
};

enum class FailureId : uint8_t {
    PowerSupply = 0,
    ValveMosfet,
    PressureSensor,
    I2cBus,
    FlashMemory,
    StackOverflow,
    Count
};

struct Record {
    FailureId           id;
    std::string_view    name;
    uint8_t             severity;
    uint8_t             occurrence;
    uint8_t             detection;
    ActionPriority      ap;
    bool (*diag_func)() = nullptr;
    void (*recovery_func)() = nullptr;

    [[nodiscard]] constexpr uint16_t rpn() const noexcept {
        return static_cast<uint16_t>(severity * occurrence * detection);
    }
};

struct RuntimeState {
    uint32_t fail_count{0};
    uint32_t last_fail_timestamp_ms{0};
    bool     is_active{false};
};

[[nodiscard]] constexpr ActionPriority calculate_ap(uint8_t s, uint8_t o, uint8_t d) noexcept {
    if (s >= 9) {
        if (o >= 2) return ActionPriority::High;
        return (d >= 5) ? ActionPriority::High : ActionPriority::Medium;
    }
    if (s >= 7) {
        if (o >= 8) return ActionPriority::High;
        if (o >= 6) return (d >= 5) ? ActionPriority::High : ActionPriority::Medium;
        if (o >= 4) return (d >= 7) ? ActionPriority::High : ActionPriority::Medium;
        return (d >= 7) ? ActionPriority::Medium : ActionPriority::Low;
    }
    if (s >= 4) {
        if (o >= 8) return (d >= 7) ? ActionPriority::High : ActionPriority::Medium;
        if (o >= 6) return ActionPriority::Medium;
        return (d >= 7) ? ActionPriority::Medium : ActionPriority::Low;
    }
    return (o >= 8 && d >= 7) ? ActionPriority::Medium : ActionPriority::Low;
}

class Supervisor {
public:
    static constexpr size_t RecordCount = static_cast<size_t>(FailureId::Count);

    Supervisor(std::span<const Record, RecordCount> registry) noexcept
        : m_registry(registry) {}

    void run_diagnostics(uint32_t current_time_ms) noexcept {
        for (size_t i = 0; i < RecordCount; ++i) {
            const auto& rec = m_registry[i];
            if (!rec.diag_func) continue;

            if (!rec.diag_func()) {
                m_state[i].fail_count++;
                m_state[i].last_fail_timestamp_ms = current_time_ms;
                m_state[i].is_active = true;

                if (rec.recovery_func) {
                    rec.recovery_func();
                }
            } else {
                m_state[i].is_active = false;
            }
        }
    }

    [[nodiscard]] bool is_system_safe() const noexcept {
        for (size_t i = 0; i < RecordCount; ++i) {
            if (m_state[i].is_active && m_registry[i].severity >= 8) {
                return false;
            }
        }
        return true;
    }

    [[nodiscard]] const RuntimeState& get_state(FailureId id) const noexcept {
        return m_state[static_cast<size_t>(id)];
    }

private:
    std::span<const Record, RecordCount> m_registry;
    std::array<RuntimeState, RecordCount> m_state{};
};

} // namespace embedded::fmea

## Інженерний висновок: життєвий цикл матриці надійності

Таблиця FMEA не є статичним звітом, який здають замовнику на стадії затвердження технічного завдання та ховають у архів. Вона живе разом із виробом упродовж усього його життєвого циклу:

1. **Етап проєктування схемотехніки:** матриця FMEA формує перелік вимог до апаратного захисту (номінали TVS-діодів, дератинг транзисторів, розведення полігонів заземлення).
2. **Етап написання прошивки:** FMEA визначає перелік діагностичних процедур, тайм-аутів периферійних шин, меж валідації аналогових сигналів та алгоритмів переходу в безпечний аварійний стан (Failsafe).
3. **Етап заводських випробувань та експлуатації:** кожен повернений із поля несправний екземпляр звіряється з матрицею. Якщо виявлено новий режим відмови, якого не було в таблиці, це свідчить про прогалину в аналізі: матриця оновлюється, розраховується новий пріоритет AP, додається схемний захист або діагностичний колбек у прошивці, після чого оновлена версія надсилається у серійне виробництво.
