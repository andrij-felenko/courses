Автономний ґрунтовий сенсор на літій-тіонілхлоридній батареї (LiSOCl2, 2400 мА·год) спроєктовано для безперервної п'ятирічної роботи в полі. Раз на 15 хвилин пристрій вимірює вологість і температуру ґрунту (два числа: 23.45 °C і 58.2 %) та передає ці дані на хмарний сервер. Лабораторний прототип, протестований в офісі через Wi-Fi на платформі ESP32, надсилав звичний JSON-запит через HTTPS-клієнт і працював бездоганно. Проте після встановлення в польовий модем NB-IoT перший змонтований масив датчиків вимикається вже через 48 днів замість запланованих п'яти років. Батареї повністю виснажені, а наприкінці місяця оператор стільникового зв'язку виставляє рахунок на 28 мегабайтів трафіку на кожну SIM-карту замість очікуваних 350 кілобайтів.

Цей збій виникає через фундаментальну різницю між локальними високошвидкісними мережами та польовими радіоканалами LPWAN. У дротовій мережі або Wi-Fi накладні витрати транспортного стека нічого не коштують: передача додаткових 5 кілобайтів службових даних триває кілька мікросекунд і забирає мізерну частку енергії від розетки. У стільникових мережах NB-IoT або LTE-M кожен байт транслюється в радіоефір на високій потужності передавача (+23 дБм / 200 мВт), вимагає тривалого узгодження частот і станів із базовою станцією, а тарифна сітка оператора округлює кожну окрему радіосесію до фіксованих квантів (1, 5 або 10 КБ). Щоб автономний пристрій вижив у полі, інженер мусить детально порахувати ланцюг витрат на всіх трьох рівнях: фізичному обсязі байтів, спожитій енергії в міліампер-годинах та фінансовій вартості SIM-трафіку для масового парку.

## Ланцюг накладних витрат: від сенсорного байта до радіохвилі

Сенсор зчитує 4 байти фізичних даних: два 16-бітних цілих числа. Щоб ці 4 байти опинилися в базі даних сервера за класичною архітектурою вебсервісів (JSON поверх HTTPS/TCP), системі доводиться наростити довкола них кілька шарів протокольних оболонок.

```text
4 байти вимірювань
  └─► 110 байтів: JSON-об'єкт із назвами полів {"temp":23.45,"hum":58.2}
        └─► 380 байтів: Заголовки HTTP POST (Host, User-Agent, Content-Type, Content-Length)
              └─► 4800–6000 байтів: Рукостискання TLS 1.2 (ClientHello, сертифікати X.509, обмін ключами)
                    └─► 120 байтів: Рукостискання TCP (SYN, SYN-ACK, ACK) + заголовки IP/TCP
                          └─► Разом: ~6400 байтів радіотрафіку заради 4 байтів вимірювання
```

Кожен рівень стека виконує свою ізольовану функцію, проте в сукупності вони створюють гігантський баласт.

### 1. Транспортний рівень TCP та безпека TLS

Протокол TCP гарантує доставку зі збереженням порядку байтів, але вимагає попереднього встановлення сесії через тристороннє рукостискання (3-Way Handshake). Клієнт надсилає пакет `SYN` (40 байтів з IP-заголовком), сервер відповідає `SYN-ACK` (40 байтів), клієнт підтверджує через `ACK` (40 байтів). Навіть до початку передачі будь-яких даних у радіоефір уже пішло 120 байтів і два повних цикли кругової затримки (Round Trip Time, RTT). У стільникових мережах NB-IoT затримка RTT може складати від 300 мс до 2–3 секунд залежно від якості покриття та рівня повторів (Coverage Enhancement Level).

Після встановлення TCP починається захищений сеанс TLS. У стандартному режимі TLS 1.2 без оптимізацій:
1. Клієнт надсилає `ClientHello` (~200–300 байтів), де вказує підтримувані шифрокомплекти (Cipher Suites) та розширення SNI (Server Name Indication).
2. Сервер повертає `ServerHello`, свій ланцюжок сертифікатів X.509 та параметри обміну ключами Diffie-Hellman (`ServerKeyExchange`). Ланцюжок із двох або трьох RSA-сертифікатів важить від 3.5 до 6.0 кілобайтів. Для NB-IoT зі швидкістю передачі 16–30 кбіт/с завантаження цього сертифіката займає 2–4 секунди суцільного радіоефіру.
3. Клієнт перевіряє сертифікат, генерує сесійні ключі, надсилає `ClientKeyExchange` та `Finished` (~200 байтів).
4. Сервер відповідає своїм повідомленням `Finished` (~80 байтів).

Лише після цього пристрій надсилає прикладний запит HTTP POST. Закриття TCP-з'єднання вимагає ще одного обміну пакетами `FIN` / `ACK` (ще 160 байтів). Загальний обсяг трафіку на один вимір перевищує 6 кілобайтів, з яких корисне навантаження становить менше ніж 0.1 %.

### 2. Оптимізація сесій: TLS Session Resumption та DTLS Connection ID

Якщо не змінювати прикладний рівень, першим кроком скорочення оверхеду є відновлення раніше узгодженої криптографічної сесії. Механізм TLS Session Tickets (RFC 5077) або TLS 1.3 Pre-Shared Key (PSK) дозволяє зберегти зашифрований стан сесії в пам'яті модема чи мікроконтролера. При повторному підключенні клієнт надсилає у `ClientHello` збережений тікет, і сторони одразу переходять до шифрування без повторної передачі багатокілобайтних сертифікатів X.509. Це скорочує рукостискання з 5 КБ до ~300–450 байтів.

Проте базовий TCP-оверхед залишається: тристороннє рукостискання, підтвердження сегментів `ACK` на кожному кроці та збереження стану з'єднання в стеку пам'яті модема. Радикальним кроком для вбудованих польових систем є відмова від з'єднань на користь датаграмного транспорту UDP із використанням протоколу CoAP (Constrained Application Protocol) та захисту DTLS 1.3.

Механізм DTLS Connection ID (RFC 9146) усуває необхідність повторного рукостискання при зміні IP-адреси пристрою або тривалому сні. Модем надсилає одиничну датаграму UDP, у якій після 13-байтового заголовка DTLS одразу міститься зашифроване тіло CoAP-повідомлення. Сумарний накладний обсяг усього стека (IP + UDP + DTLS + CoAP) падає до 50–70 байтів на транзакцію.

## Серіалізація даних: JSON проти бінарних упаковок

Текстовий формат JSON став стандартом інтернет-сервісів завдяки простоті читання людиною та підтримці в усіх мовах програмування. Проте в мікроконтролерах із батарейним живленням JSON породжує три критичні проблеми: надлишковий розмір, високу ціну парсингу та фрагментацію пам'яті.

### Анатомія текстової надлишковості

Розглянемо типове повідомлення з чотирьох вимірювань (мітка часу Unix, температура, напруга батареї, вологість):

```json
{"ts":1724673600,"temperature":23.45,"battery_voltage":3.612,"humidity":58.4}
```

Текстовий рядок містить 78 символів (78 байтів). Понад 70% цього обсягу займають повторювані назви ключів (`"temperature"`, `"battery_voltage"`) та синтаксичні роздільники (`"`, `:`, `,`, `{`, `}`).

Крім надлишковості в ефірі, робота з JSON виснажує процесор мікроконтролера:
- Форматування чисел з плаваючою комою у текст через `snprintf()` або `dtostrf()` вимагає сотень машинних тактів і затягує активний стан ядра.
- Десеріалізація на приймальному боці (або при отриманні команд конфігурації пристроєм) вимагає динамічного виділення пам'яті в купі (`malloc`) для побудови дерева об'єктів DOM (наприклад, у бібліотеці `cJSON`). На чипах із 16–32 КБ RAM це створює ризик фрагментації купи та подальшого аварійного перезавантаження.

### Порівняльна таблиця форматів

| Формат | Розмір кадру | Опис схеми | Робота з пам'яттю на МК | Навантаження на CPU |
|---|---|---|---|---|
| **JSON** | 78–110 Б | Текстова, динамічна | Динамічна купа (`malloc`) | Дуже високе (парсинг тексту, float) |
| **CBOR** | 32–45 Б | Бінарна, динамічна | Статичний або потоковий буфер | Середнє (парсинг бінарних тегів) |
| **MessagePack** | 30–42 Б | Бінарна, динамічна | Статичний буфер | Середнє (розбір префіксів) |
| **Protocol Buffers (nanopb)** | 16–22 Б | Жорстка `.proto` схема | Статичні C-структури (нуль купи) | Низьке (кодування varint/zig-zag) |
| **Користувацький Bit-Packed кадр** | **12–14 Б** | Жорсткий бінарний контракт | Статичний буфер фіксованого розміру | Мінімальне (побітові зсуви) |

### Фіксована кома та бітові поля

У 99% польових телеметричних задач фізичні сенсори мають обмежений діапазон та кінцеву апаратну точність. Немає жодного інженерного сенсу передавати покази 12-бітного АЦП як 64-бітне число з плаваючою комою `double` чи текстовий дріб `"3.612"`.

Застосування цілочисельного масштабування (фіксованої коми):
1. **Температура**: діапазон від −40.00 °C до +85.00 °C з точністю 0.01 °C потребує 12 501 дискретного значення. Це ідеально вміщується у 16-бітне ціле число зі знаком `int16_t` (множимо температуру на 100). Замість 5–7 байтів у тексті ми витрачаємо рівно 2 байти.
2. **Напруга батареї**: діапазон 0..5000 мВ вміщується в `uint16_t` (2 байти).
3. **Вологість**: діапазон 0.0..100.0% з кроком 0.5% містить 201 значення та вміщується в `uint8_t` (1 байт) як подвоєний відсоток вологості.
4. **Статусні прапорці**: 8 незалежних дискретних сигналів (тривога зламу, стан реле, аварія сенсора, статус зарядки тощо) упаковуються в 1 байт бітової маски замість 8 окремих JSON-полів.

Повна реалізація нуль-алокаційного пакера з обчисленням контрольної суми CRC16 наведена у вставці [проєкт компактного серіалізатора](root:embedded/tsina-odnoho-povidomlennia/proj-compact-frame-packer.md).

## Енергетичний профіль передавача та ціна підключення

У паспортних даних стільникових модулів (наприклад, Quectel BG95, SimCom SIM7080G, Nordic nRF9160) виробники зазначають привабливі цифри: «струм у режимі PSM — 3.5 мкА», «струм передачі — 250 мА». Проте реальне споживання енергії визначається не статичним значенням струму, а інтегралом профілю споживання за часом протягом усього сеансу зв'язку.

![Хронограма споживання струму модема](/root/course/embedded/tsina-odnoho-povidomlennia/img/cellular-energy-timeline.svg)
*Хронограма споживання струму модема: пробудження, синхронізація, TX та RRC-хвіст*

Сеанс передачі повідомлення у мережах NB-IoT/LTE-M складається з шести послідовних фаз:

```text
1. Пробудження (Wakeup & Init)
   ├─ Тривалість: 100–300 мс
   └─ Струм: 20–30 мА (запуск внутрішнього DC-DC, опитування SIM-карти)
2. Синхронізація та RRC Setup (Random Access)
   ├─ Тривалість: 1.0–3.0 с (до 10 с при слабкому сигналі)
   └─ Струм: 60–90 мА (сканування ефіру, надсилання PRACH-преамбул)
3. Випромінювання корисних даних (TX Uplink)
   ├─ Тривалість: t = Розмір_пакета / Швидкість
   └─ Струм: 220–350 мА (робота підсилювача потужності PA при +23 дБм)
4. Прийом підтвердження (RX Downlink)
   ├─ Тривалість: 100–300 мс
   └─ Струм: 50–70 мА (робота малошумливого вхідного підсилювача LNA)
5. Таймер неактивності мережі (RRC Inactivity Tail Timer)
   ├─ Тривалість: 10–20 секунд (задається базовою станцією!)
   └─ Струм: 20–35 мА (модем перебуває в режимі RRC Connected і чекає команд)
6. Глибокий сон (PSM / eDRX)
   ├─ Тривалість: решта періоду між вимірюваннями
   └─ Струм: 2.5–4.0 мкА
```

### Пастка таймера RRC Inactivity та порятунок через RAI

Головна невидима пастка стільникового зв'язку полягає у фазі 5 — таймері неактивності RRC. Коли пристрій завершив передачу пакета й отримав відповідь, модем **не має права самостійно вимкнути радіоканал**. За стандартами 3GPP рішення про переведення термінала в стан `RRC IDLE` приймає виключно базова станція (eNodeB).

Базова станція не знає намірів пристрою: можливо, через секунду прийде новий пакет. Тому eNodeB тримає канал відкритим протягом стандартного таймера неактивності — зазвичай від 10 до 20 секунд. Протягом усього цього часу приймач модема залишається увімкненим, спалюючи від 20 до 35 мА струму на холостому ходу.

Якщо сеанс передачі короткого пакета тривав 0.5 секунди й спожив близько 0.02 мА·год заряду, то наступні 15 секунд холостого очікування заберуть:

```text
Q_tail = 25 мА · 15 с
       = 375 мА·с
       = 375 / 3600
       ≈ 0.104 мА·год   [втрата заряду на хвості RRC]
```
Хвіст таймера забирає в 5 разів більше енергії, ніж сама корисна передача!

Для вирішення цієї проблеми консорціум 3GPP стандартизував механізм **Release Assistance Indication (RAI)** (підтримується починаючи з 3GPP Release 14/15). Під час відправки останнього пакета стек пристрою додає в інформаційний елемент канального рівня прапорець RAI: «після цього пакета подальшої передачі/прийому не буде». Отримавши цей прапорець, базова станція негайно надсилає команду `RRCConnectionRelease`, і модем засинає в PSM за 100–200 мс, скорочуючи енерговитрати на 80%.

Детальний аналітичний розрахунок добового споживання та строку служби наведено у вставці [математичну модель розрахунку енергії та строку служби](root:embedded/tsina-odnoho-povidomlennia/math-cellular-energy-model.md), а практичний перелік AT-команд керування цими режимами зібрано у вставці [довідник AT-команд енергоощадних режимів](root:embedded/tsina-odnoho-povidomlennia/api-cellular-power-at.md).

## Економіка IoT-трафіку: парк 10 000 пристроїв

В інженерії масових виробів помилка в архітектурі протоколу множиться на кількість пристроїв у серії. Розглянемо економіку розгортання парку з 10 000 автономних вузлів обліку чи моніторингу на 5 років експлуатації.

![Економіка парку 10 000 пристроїв](/root/course/embedded/tsina-odnoho-povidomlennia/img/fleet-cost-projection.svg)
*Економіка парку 10 000 пристроїв: витрати на трафік проти сервісних виїздів*

### Тарифне квантування стільникових операторів

M2M/IoT тарифи стільникових операторів суттєво відрізняються від призначених для смартфонів. Головний фактор вартості — це **квант округлення сесії (Data Session Billing Increment)**:
- Якщо пристрій розриває сесію PDP Context / IP bearer після кожного пакета, оператор округлює переданий обсяг до 1 КБ, 5 КБ або 10 КБ.
- Передавши 110 байтів JSON-пакета в новій сесії при округленні 10 КБ, система оплачує повні 10 КБ трафіку.
- 96 відправок на добу (раз на 15 хв) = 2 880 відправок на місяць.
- Розрахунковий трафік оператора: 2880 × 10 КБ = 28.8 МБ/місяць на один пристрій.

Для парку з 10 000 пристроїв сумарний трафік складає 288 гігабайтів на місяць. За базового тарифу M2M у 0.10–0.25 долара за 1 МБ у міжнародному роумінгу щомісячний платіж оператору становитиме від 1 500 до 3 000 доларів (90 000–180 000 доларів за 5 років).

Якщо ж перейти на 28-байтовий бінарний UDP-кадр у режимі пулу даних (Data Pooling) або NIDD без розриву контексту:
- Щомісячний трафік одного датчика: 2880 × 28 байтів ≈ 80.6 КБ/місяць.
- Сумарний трафік усього парку 10 000 пристроїв: лише **806 мегабайтів на місяць** на весь флот.
- Витрати на SIM-карти падають до мінімального фіксованого абонентського пулу (100–150 доларів на місяць за всю систему).

### Вартість польового сервісу (Truck Roll)

Проте прямі витрати на стільниковий трафік є лише вершиною айсберга. Справжньою фінансовою катастрофою для виробника стає передчасне виснаження батарей.

Вартість заміни батареї в польових умовах (виїзд сервісної бригади, демонтаж герметичного корпусу, заміна елемента, герметизація, повторний тест зв'язку) становить у середньому від 30 до 80 доларів за одну точку. 
- При наївному стеку батарея розряджається за 48–50 днів. За 5 років експлуатації кожен пристрій потребуватиме понад 30 замін елементів живлення.
- Для 10 000 пристроїв це означає понад 300 000 сервісних виїздів вартістю понад 10 000 000 доларів, що повністю руйнує будь-яку бізнес-модель проєкту.
- Оптимізований бінарний стек забезпечує 6–8 років автономної роботи на одній батареї, зводячи планові виїзди сервісних інженерів до абсолютного нуля.

## Практичний інструмент: пакетна буферизація та дельта-стиснення

Окрім побайтового пакування окремих полів, кардинальне зниження енергетичних витрат досягається двома системними архітектурними прийомами: **пакетною буферизацією (Batching)** та **дельта-стисненням (Delta Compression)**.

### 1. Пакетна буферизація

Замість вмикання модема та виходу в ефір щоразу після зняття вимірювання (96 разів на добу), мікроконтролер зберігає точки вимірювань у локальній оперативній пам'яті або енергонезалежній енергоощадній FRAM/Flash-пам'яті. Модем вмикається лише один раз на 4 або 6 годин і надсилає накопичений блок із 16–24 вимірювань у єдиному радіопакеті.

Це дозволяє сплачувати фіксовані витрати енергії на пробудження, пошук базової станції та синхронізацію PRACH лише 4–6 разів на добу замість 96 разів, що знижує витрати заряду ще в 3–4 рази.

### 2. Дельта-компресія часових рядів

Оскільки фізичні процеси (температура ґрунту, тиск у трубі, рівень води) мають значну інерційність, абсолютні значення між сусідніми вимірами змінюються незначно. У першому записі блока передається повна 32-бітна мітка часу та повне 16-бітне значення base_temp. Усі наступні N вимірів записуються як відносні зміщення delta_temp = temp[i] - temp[i-1], які вміщуються у 4 або 8 бітів замість 16.

Нижче наведено повну реалізацію пакетного буфера телеметрії з дельта-стисненням на C та C++.

```c
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

#define BATCH_MAX_SAMPLES 16
#define BATCH_MAGIC       0xD7

typedef struct {
    uint32_t timestamp;  /* Повний Unix-час */
    int16_t  temperature; /* T * 100 */
    uint16_t voltage_mv;  /* Напруга в мВ */
} SamplePoint;

typedef struct {
    SamplePoint samples[BATCH_MAX_SAMPLES];
    size_t count;
} BatchBuffer;

void batch_init(BatchBuffer *buf) {
    if (buf) {
        buf->count = 0;
    }
}

bool batch_add(BatchBuffer *buf, uint32_t ts, int16_t temp, uint16_t mv) {
    if (!buf || buf->count >= BATCH_MAX_SAMPLES) {
        return false;
    }
    buf->samples[buf->count].timestamp = ts;
    buf->samples[buf->count].temperature = temp;
    buf->samples[buf->count].voltage_mv = mv;
    buf->count++;
    return true;
}

/* Пакування батчу з дельта-стисненням:
   - Байт 0: Magic + Count
   - Байти 1..4: Base Timestamp
   - Байти 5..6: Base Temperature
   - Байти 7..8: Base Voltage
   - Наступні точки (i > 0):
     - int8_t delta_temp = (temp[i] - temp[i-1])
     - uint8_t delta_ts_div_10 = (ts[i] - ts[i-1]) / 10
     - int8_t delta_v_div_10 = (v[i] - v[i-1]) / 10
*/
size_t batch_serialize_delta(const BatchBuffer *buf, uint8_t *out, size_t out_max) {
    if (!buf || !out || buf->count == 0 || out_max < 9) {
        return 0;
    }

    out[0] = (BATCH_MAGIC & 0xF0) | ((uint8_t)buf->count & 0x0F);

    /* Базова точка */
    uint32_t base_ts = buf->samples[0].timestamp;
    out[1] = (uint8_t)(base_ts >> 24);
    out[2] = (uint8_t)(base_ts >> 16);
    out[3] = (uint8_t)(base_ts >> 8);
    out[4] = (uint8_t)(base_ts);

    int16_t base_temp = buf->samples[0].temperature;
    out[5] = (uint8_t)(base_temp >> 8);
    out[6] = (uint8_t)(base_temp);

    uint16_t base_v = buf->samples[0].voltage_mv;
    out[7] = (uint8_t)(base_v >> 8);
    out[8] = (uint8_t)(base_v);

    size_t offset = 9;

    for (size_t i = 1; i < buf->count; ++i) {
        if (offset + 3 > out_max) {
            return 0; /* Переповнення вихідного буфера */
        }

        uint32_t dt = buf->samples[i].timestamp - buf->samples[i-1].timestamp;
        int16_t  dtemp = buf->samples[i].temperature - buf->samples[i-1].temperature;
        int32_t  dv = (int32_t)buf->samples[i].voltage_mv - (int32_t)buf->samples[i-1].voltage_mv;

        /* Обмеження дельт до розміру int8_t */
        int8_t dt_byte = (dt <= 2550) ? (int8_t)(dt / 10) : 127;
        int8_t dtemp_byte = (dtemp >= -128 && dtemp <= 127) ? (int8_t)dtemp : (dtemp > 0 ? 127 : -128);
        int8_t dv_byte = (dv >= -1280 && dv <= 1270) ? (int8_t)(dv / 10) : (dv > 0 ? 127 : -128);

        out[offset++] = (uint8_t)dt_byte;
        out[offset++] = (uint8_t)dtemp_byte;
        out[offset++] = (uint8_t)dv_byte;
    }

    return offset;
}
```

```cpp
#include <cstdint>
#include <cstddef>
#include <span>
#include <array>
#include <algorithm>

namespace telemetry {

inline constexpr uint8_t BatchMagic = 0xD0;
inline constexpr size_t  MaxBatchCapacity = 16;

struct SamplePoint {
    uint32_t timestamp{0};
    int16_t  temperature{0};
    uint16_t voltage_mv{0};
};

class BatchCompressor {
private:
    std::array<SamplePoint, MaxBatchCapacity> samples_{};
    size_t count_{0};

public:
    constexpr BatchCompressor() noexcept = default;

    constexpr bool add(uint32_t ts, int16_t temp, uint16_t mv) noexcept {
        if (count_ >= MaxBatchCapacity) {
            return false;
        }
        samples_[count_++] = SamplePoint{ts, temp, mv};
        return true;
    }

    [[nodiscard]] constexpr size_t count() const noexcept { return count_; }
    constexpr void clear() noexcept { count_ = 0; }

    [[nodiscard]] size_t serialize_delta(std::span<uint8_t> out) const noexcept {
        if (count_ == 0 || out.size() < 9 + (count_ - 1) * 3) {
            return 0;
        }

        out[0] = static_cast<uint8_t>((BatchMagic & 0xF0) | (count_ & 0x0F));

        const auto& base = samples_[0];
        out[1] = static_cast<uint8_t>(base.timestamp >> 24);
        out[2] = static_cast<uint8_t>(base.timestamp >> 16);
        out[3] = static_cast<uint8_t>(base.timestamp >> 8);
        out[4] = static_cast<uint8_t>(base.timestamp);

        out[5] = static_cast<uint8_t>(base.temperature >> 8);
        out[6] = static_cast<uint8_t>(base.temperature);

        out[7] = static_cast<uint8_t>(base.voltage_mv >> 8);
        out[8] = static_cast<uint8_t>(base.voltage_mv);

        size_t offset = 9;
        for (size_t i = 1; i < count_; ++i) {
            const auto& curr = samples_[i];
            const auto& prev = samples_[i - 1];

            const uint32_t dt = curr.timestamp - prev.timestamp;
            const int16_t dtemp = curr.temperature - prev.temperature;
            const int32_t dv = static_cast<int32_t>(curr.voltage_mv) - static_cast<int32_t>(prev.voltage_mv);

            const auto dt_byte = static_cast<int8_t>(std::clamp<uint32_t>(dt / 10, 0, 255));
            const auto dtemp_byte = static_cast<int8_t>(std::clamp<int16_t>(dtemp, -128, 127));
            const auto dv_byte = static_cast<int8_t>(std::clamp<int32_t>(dv / 10, -128, 127));

            out[offset++] = static_cast<uint8_t>(dt_byte);
            out[offset++] = static_cast<uint8_t>(dtemp_byte);
            out[offset++] = static_cast<uint8_t>(dv_byte);
        }

        return offset;
    }
};

} // namespace telemetry
```

## Інженерний висновок

Оптимізація вартості одного повідомлення — це не передчасна мікрооптимізація, а фундаментальна умова життєздатності будь-якого польового IoT-виробу. Перехід від наївного вебстека до польового інженерного підходу базується на п'яти непорушних принципах:

1. **Компактні формати**: Відмова від текстового JSON на користь бінарного пакування з фіксованою комою скорочує розмір даних у 4–8 разів і усуває витрати CPU на парсинг та динамічну пам'ять.
2. **Датаграмний транспорт**: Використання CoAP/UDP або захищених кадрів поверх DTLS 1.3 Connection ID усуває рукостискання TCP та багатокілобайтний трафік сертифікатів TLS.
3. **Керування станами модема**: Застосування сигнального прапорця RAI (Release Assistance Indication) змушує базову станцію негайно скидати радіоз'єднання, заощаджуючи 80% заряду на кожному сеансі.
4. **Сон у PSM**: Налаштування таймерів T3324 (Active Time = 0..2 с) та T3412 (TAU = 12..24 год) переводить модем у глибокий мікроамперний сон без втрати мережевої реєстрації.
5. **Буферизація та дельта-стиснення**: Об'єднання вимірювань у пачки скорочує кількість виходів на зв'язок і робить вартість обслуговування парку нульовою на весь розрахунковий термін служби пристрою.
