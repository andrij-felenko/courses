# Бінарний протокол передачі діагностичного знімка інциденту

Бінарний протокол передачі діагностичного знімка інциденту (англ. *incident telemetry protocol*) визначає публічний контракт структури даних, бітових масок помилок, форматів пакетів та команд сервісного інтерфейсу (UART, CAN, BLE або MQTT/HTTP), за допомогою яких пристрій передає накопичену діагностику збою на сервер збору телеметрії або діагностичну консоль техніка. 

У вбудованих системах діагностичний канал зв'язку часто функціонує в умовах апаратної деградації системи: пристрій може перебувати у стані після аварійного перезавантаження сторожового таймера, мати пошкоджену динамічну пам'ять або працювати з обмеженою швидкістю резервного радіоканалу. Тому протокол діагностичного знімка проєктується з жорсткими обмеженнями: фіксований компактний розмір кадру, відсутність динамічного виділення пам'яті під час серіалізації, детерміноване вирівнювання полів та обов'язковий контроль цілісності за допомогою контрольної суми CRC32.

### Специфікація кадру діагностичного знімка (Snapshot Frame)

Кадр має фіксовану довжину 64 байти, вирівняний по 4-байтовій межі (Little-Endian) та захищений поліномом CRC32 (IEEE 802.3). Такий фіксований формат дозволяє відправляти знімок як єдиний атомарний пакет через більшість фізичних інтерфейсів без необхідності складної фрагментації на транспортному рівні (наприклад, у межах одного кадру CAN-FD на 64 байти або у двох стандартних 32-байтових транзакціях SPI).

```
+--------+--------+------------------------+-------------------------------------------------------+
| Зсув   | Розмір | Поле                   | Опис та семантика                                     |
+--------+--------+------------------------+-------------------------------------------------------+
| 0x00   | 4 B    | `magic_tag`            | Сигнатура `0xDEADBEEF`                                |
| 0x04   | 2 B    | `protocol_version`     | Версія схеми кадру (наприклад, `0x0100` для v1.0)     |
| 0x06   | 2 B    | `payload_length`       | Довжина корисного навантаження (байти)                |
| 0x08   | 8 B    | `device_uid`           | 64-бітний унікальний серійний номер мікроконтролера   |
| 0x10   | 4 B    | `boot_count`           | Монотонний лічильник завантажень пристрою             |
| 0x14   | 4 B    | `uptime_seconds`       | Час роботи системи до моменту інциденту (секунди)     |
| 0x18   | 4 B    | `reset_flags_raw`      | Бітова маска регістрів скидання живлення / WDT        |
| 0x1C   | 4 B    | `fault_code`           | Системний числовий код відмови (Fault Category)       |
| 0x20   | 4 B    | `fault_pc`             | Значення Program Counter у момент виникнення збою    |
| 0x24   | 4 B    | `fault_lr`             | Значення Link Register у момент виникнення збою       |
| 0x28   | 4 B    | `fault_cfsr`           | Configurable Fault Status Register (Cortex-M)         |
| 0x2C   | 2 B    | `v_bat_mv`             | Напруга первинного живлення (мілівольти)              |
| 0x2E   | 2 B    | `v_core_mv`            | Напруга ядра процесора (мілівольти)                   |
| 0x30   | 2 B    | `temp_die_c`           | Температура кристала (цілі градуси Цельсія)           |
| 0x32   | 2 B    | `temp_pcb_c`           | Температура плати / навколишнього середовища          |
| 0x34   | 2 B    | `bus_err_i2c`          | Кількість таймаутів та помилок шини I2C               |
| 0x36   | 2 B    | `bus_err_spi`          | Кількість помилок переповнення / CRC шини SPI         |
| 0x38   | 4 B    | `task_active_id`       | Ідентифікатор активного завдання FreeRTOS / Zephyr    |
| 0x3C   | 4 B    | `task_min_stack_words` | Мінімальний запас стека активного завдання (слова)    |
| 0x40   | 4 B    | `crc32`                | Контрольна сума CRC32 байтів від `0x00` до `0x3F`     |
+--------+--------+------------------------+-------------------------------------------------------+
```

#### Семантика та правила обробки ключових полів

1. **Сигнатура валідності (`magic_tag`):** фіксована 32-бітна константа `0xDEADBEEF`. Якщо при зчитуванні з енергонезалежного сховища перший подвійний байт містить значення `0xFFFFFFFF` (стерта пам'ять) або випадковий шум, кадр вважається неініціалізованим і відкидається приймачем без подальшої обробки.
2. **Монотонний лічильник перезапусків (`boot_count`):** інкрементується на одиницю при кожному успішному проходженні функції ініціалізації ядра. Зіставлення лічильника з часом безперервної роботи `uptime_seconds` дозволяє діагностичному серверу миттєво визначити циклічний перезапуск (англ. *bootloop*): якщо `boot_count` стрімко зростає, а `uptime_seconds` не перевищує кількох секунд, пристрій перебуває у фатальному циклі збою ініціалізації периферії.
3. **Апаратна бітова маска скидання (`reset_flags_raw`):** містить пряме відображення апаратного регістра скидання мікроконтролера (наприклад, `RCC_CSR` для архітектури STM32 або `RST_REASON` для ESP32). Маска дозволяє чітко розрізнити п'ять фізичних сценаріїв завершення роботи:
   - Спрацьовування сторожового таймера IWDG / WWDG (програмне зависання або взаємне блокування потоків).
   - Спрацьовування детектора падіння напруги Brown-out Reset (просідання первинного живлення нижче допустимого порогу стабілізації).
   - Програмне скидання ядра `NVIC_SystemReset()` (штатне або аварійне програмне завершення).
   - Зовнішнє апаратне скидання по виводу NRST (натискання кнопки скидання користувачем або зовнішній супервізор).
   - Подача живлення Power-On Reset (холодний старт після повного знеструмлення).

### Класифікація системних кодів відмов (Fault Category Codes)

Поле `fault_code` категоризує природу виникнення збою за 32-бітною ієрархією. Розподіл бітів структуровано так, щоб хостова система могла виконувати швидку групову фільтрацію відмов за маскою старшого байта без повного парсингу всього дампа:

```
Біти [31:24] — Основний домен несправності (Subsystem Domain)
Біти [23:16] — Специфічний механізм збою (Failure Mechanism)
Біти [15:0]  — Детальний числовий субіндекс / код помилки драйвера
```

```
+--------------+-----------------------+-----------------------------------------------------------+
| Код (HEX)    | Категорія             | Технічний зміст відмови                                   |
+--------------+-----------------------+-----------------------------------------------------------+
| `0x01010001` | `FAULT_HARDFAULT_PRE` | Спроба читання за недійсною адресою (Precise Data Access) |
| `0x01010002` | `FAULT_HARDFAULT_IMPR`| Помилка запису через асинхронну шину (Imprecise Bus Fault)|
| `0x01020001` | `FAULT_MEMMANAGE`     | Спроба виконання коду з регіону пам'яті без дозволу MPU   |
| `0x01030001` | `FAULT_USAGE_DIV0`    | Ділення на нуль або невалідна інструкція ядра             |
| `0x02010001` | `FAULT_WDT_TASK_STALL`| Зависання основного циклу обробки повідомлень             |
| `0x02010002` | `FAULT_WDT_ISR_FLOOD` | Зациклення в обробнику переривання (ISR Deadlock)         |
| `0x03010001` | `FAULT_PWR_BROWNOUT`  | Спрацьовування апаратного детектора просідання BOR        |
| `0x03020001` | `FAULT_PWR_OVERTEMP`  | Аварійний перегрів силового каскаду або процесора         |
| `0x04010001` | `FAULT_BUS_I2C_STUCK` | Лінія SDA затиснута зовнішнім датчиком у стані '0'        |
| `0x04020001` | `FAULT_BUS_SPI_LOCK`  | Відсутність сигналу Ready / Busy від зовнішньої пам'яті   |
+--------------+-----------------------+-----------------------------------------------------------+
```

### Транспортні рівні інкапсуляції та фрагментація

Залежно від фізичного інтерфейсу зв'язку, через який пристрій передає дамп, застосовуються різні правила обрамлення (framing) та сегментації:

#### 1. Послідовний інтерфейс UART / USB CDC (SLIP Framing)
Для передачі через серійний порт застосовується протокол SLIP (Serial Line Internet Protocol, RFC 1055). Байт `0xC0` (`SLIP_END`) позначає межі кадру. Якщо всередині корисного навантаження зустрічається байт `0xC0`, він замінюється на послідовність з двох байтів `0xDB 0xDC`. Байт `0xDB` замінюється на `0xDB 0xDD`. Це забезпечує надійне відновлення синхронізації парсера навіть за умови випадкового підключення термінала посеред передачі.

#### 2. Промислова шина CAN / CAN-FD
У класичній мережі CAN 2.0B максимальний розмір корисного навантаження одного кадру становить 8 байтів. Для передачі 64-байтового знімка застосовується спрощений транспортний протокол ISO-TP (ISO 15765-2):
- **Перший кадр (First Frame):** ідентифікатор `0x7E0`, довжина `64`, містить перші 6 байтів діагностики.
- **Кадр керування потоком (Flow Control):** приймач надсилає відповідь `0x7E8` із дозволом на передачу блоку без затримок (`Block Size = 0`, `STmin = 0`).
- **Послідовні кадри (Consecutive Frames):** передаються 8 пакетів по 7 корисних байтів із монотонним лічильником послідовності `Sequence Number (0..7)`.

У мережах з підтримкою CAN-FD знімок передається повністю в одному єдиному 64-байтовому кадрі з найвищим пріоритетом арбітражу шини (`CAN ID 0x080`), що повністю усуває витрати часу на фрагментацію та узгодження потоку.

#### 3. Бездротовий інтерфейс Bluetooth Low Energy (BLE GATT)
Пристрій оголошує спеціалізований первинний сервіс діагностики `Diagnostic Service UUID: 0000FE40-0000-1000-8000-00805F9B34FB` із двома характеристиками:
- **Snapshot Trigger Characteristic (UUID 0xFE41, Write):** запис байта `0x01` ініціює зчитування останнього аварійного кадру з пам'яті Backup SRAM.
- **Snapshot Stream Characteristic (UUID 0xFE42, Notify/Indicate):** при MTU за замовчуванням (23 байти, корисне навантаження ATT 20 байтів) знімок надсилається чотирма послідовними сповіщеннями `Notification` із 1-байтовим індексом сегмента (`[Seg_0: 19 байтів]`, `[Seg_1: 19 байтів]`, `[Seg_2: 19 байтів]`, `[Seg_3: 7 байтів]`). Якщо клієнт підтримує розширений MTU (`Data Length Extension`, MTU >= 67 байтів), знімок передається одним пакетом.

### Сервісні RPC команди опитування (Command Set)

Діагностичний порт підтримує двійковий набір команд типу «запит-відповідь» через послідовні інтерфейси зв'язку. Кожна команда супроводжується байтом довжини та контрольною сумою:

```
+----------+-----------------------+-----------------------------------------------------------+
| Код дії  | Назва команди         | Опис відповіді пристрою                                   |
+----------+-----------------------+-----------------------------------------------------------+
| `0x10`   | `CMD_GET_LAST_CRASH`  | Повертає 64-байтовий `telemetry_incident_frame_t`         |
| `0x11`   | `CMD_CLEAR_CRASH_LOG` | Скидає прапори аварії в Backup SRAM після вивантаження   |
| `0x12`   | `CMD_GET_BUS_HEALTH`  | Повертає статистику лічильників збоїв I2C/SPI/CAN         |
| `0x13`   | `CMD_FORCE_ASSERT`    | Тестова генерація аварії для верифікації конвеєра збору   |
+----------+-----------------------+-----------------------------------------------------------+
```

#### Процедура гарантованої доставки на сервер телеметрії

1. **Критерій пріоритетної передачі:** під час відновлення зв'язку після збою пакет `CMD_GET_LAST_CRASH` передається поза чергою з найвищим пріоритетом (англ. *Expedited Forwarding*) перед передачею звичайної періодичної телеметрії.
2. **Квитування та очищення буфера:** мікроконтролер не затирає енергонезалежний запис у Backup SRAM доти, доки від сервера або сервісного інструмента не надійде підписана команда підтвердження прийому `CMD_CLEAR_CRASH_LOG` із зазначенням контрольної суми успішно збереженого кадру. Це гарантує збереження діагностичного факту навіть при обриві радіозв'язку в момент відправлення пакета.
3. **Агрегація у хмарній базі дефектів:** після отримання бекендом бінарні поля декодуються, зіставляються з таблицею символів прошивки (ELF-файлом відповідної версії білду) за допомогою утиліти `addr2line` та реєструються у статистиці відмов за конкретними партіями друкованих плат і датами випуску.
