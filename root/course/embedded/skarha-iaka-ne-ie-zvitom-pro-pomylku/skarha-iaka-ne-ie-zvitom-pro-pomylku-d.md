</preknowlist>

Коли сервісна служба компанії розгортає партію з п'ятисот автономних телеметричних станцій для моніторингу магістральних нафтопроводів, водогонів або сільськогосподарських угідь, інженерна команда неминуче стикається з лавиною звернень від польових техніків та кінцевих користувачів. У тикетах техпідтримки з'являються типові якісні формулювання: «прилад номер сорок сім зависає щовечора», «станція на полі номер три сильно гріється і швидко висаджує акумулятор», «після вчорашньої грози модуль перестав бачити датчик вологості ґрунту», «пристрій іноді глючить під час передачі пакетів на морозі». 

Для недосвідченого розробника такі звернення виглядають як готові звіти про дефекти: програміст відкриває вихідний код високорівневої логіки, намагається знайти помилку в парсері або таймерах додатку і не знаходить нічого підозрілого, оскільки на лабораторному столі прилад працює цілодобово без жодного збою.

У цій точці виникає фундаментальний розрив між суб'єктивним сприйняттям людини та об'єктивною реальністю вбудованої системи. Користувацька скарга (англ. *customer complaint*) ніколи не є інженерним звітом про помилку (англ. *bug report*). Вона фіксує виключно **зовнішній симптом** — фінальний макроскопічний наслідок складного ланцюжка фізичних, електричних та програмних процесів, що розгорнулися всередині герметичного корпусу за мікросекунди до того, як людина помітила згаслий екран або відсутність свіжого графіка на сервері. 

Перетворення суб'єктивної емоційної скарги на детермінований інженерний факт — це суворий науковий метод сортування (англ. *triage*, від французького *triage* — «сортування, відбір»), що вимагає тріангуляції бортових логів, апаратного родоводу компонентів і польової телеметрії, за яким слідує глибокий аналіз кореневої причини (англ. *Root Cause Analysis*, RCA, від латинського *radix* — «корінь»).

### Анатомія не-звіту: чому користувач завжди описує симптом

Людина взаємодіє з вбудованим пристроєм крізь призму так званого бар'єра чорної скриньки (англ. *black-box illusion*). Оператор бачить лише зовнішній інтерфейс: світлодіод індикації, дисплей, стрічку графіків у веб-панелі або факт відсутності Bluetooth-з'єднання зі смартфоном. Усі внутрішні стани мікроконтролера, перехідні процеси у шинах живлення, конфлікти пріоритетів переривань та апаратні винятки ядра для користувача невидимі. 

Розберімо фізичну та програмну анатомію трьох найпоширеніших суб'єктивних скарг, з якими стикається розробник електроніки:

```
+--------------------------+------------------------------------+-----------------------------------------------------+
| Суб'єктивна скарга       | Що насправді бачить користувач     | Реальні інженерні процеси під капотом               |
+--------------------------+------------------------------------+-----------------------------------------------------+
| «Воно наглухо зависає»   | Відсутність оновлення даних        | • Циклічний перезапуск сторожового таймера (WDT)    |
|                          | на екрані або сервері              | • Зависання в очікуванні відповіді шини I2C (SDA=0) |
|                          |                                    | • Взаємне блокування (Deadlock) двох м'ютексів RTOS |
|                          |                                    | • Переповнення стека переривання (HardFault)        |
+--------------------------+------------------------------------+-----------------------------------------------------+
| «Прилад сильно гріється» | Корпус теплий на дотик             | • Лінійний LDO розсіює надлишок потужності при +40°C|
|                          |                                    | • Наскрізний струм (Shoot-through) силових ключів   |
|                          |                                    | • Лавинний пробій захисного TVS-діода від перенапруги|
|                          |                                    | • Внутрішній latch-up стан кристала після ESD удару |
+--------------------------+------------------------------------+-----------------------------------------------------+
| «Погано ловить зв'язок»  | Пакет доходить раз на годину       | • Дрейф частоти кварцового генератора на морозі     |
|                          |                                    | • Просідання напруги батареї під час імпульсу PA    |
|                          |                                    | • Розмивання діаграми спрямованості антени вологою  |
|                          |                                    | • Засмічення радіоефіру сусіднім імпульсним DC-DC   |
+--------------------------+------------------------------------+-----------------------------------------------------+
```

#### 1. Клас скарг «Воно зависає»
Користувач називає «зависанням» будь-яку ситуацію, коли прилад припиняє оновлювати стан. Проте з погляду мікроконтролера за цим словом ховається шість абсолютно різних відмов:
- **Апаратний HardFault (Invalid Memory Access):** програма намагалася розіменувати нульовий або пошкоджений покажчик (`ptr = 0x00000000`). Процесор переходить у нескінченний цикл стандартного обробника помилки `HardFault_Handler` і припиняє обробку черги завдань.
- **Асинхронний BusFault:** під час запису байта в регістр зовнішньої периферії буфер шини AHB/APB зафіксував помилку адресації вже після того, як ядро перейшло до наступної інструкції (англ. *imprecise bus fault*).
- **Апаратне блокування шини (I2C/SPI Stuck Bus):** під час передачі даних зовнішній датчик через коротку електричну перешкоду по живленню завис посеред байта і залишив відкритим свій вихідний транзистор, притискаючи лінію даних `SDA` до землі (`GND`). Драйвер мікроконтролера виконує наївний блокуючий цикл `while(I2C_GetFlagStatus(I2C_FLAG_RXNE) == RESET)` без таймауту, блокуючи весь потік опитування.
- **Інверсія пріоритетів і Deadlock в RTOS:** низькопріоритетне завдання журналювання захопило м'ютекс SPI флеш-пам'яті, було витіснене середньопріоритетним мережевим стеком, а високопріоритетне завдання аварійного контролю заблокувалося на тому ж м'ютексі, викликаючи повну зупинку системи.
- **Швидкий циклічний перезапуск (Brown-Out Bootloop):** мікроконтролер стартує, успішно ініціалізує ядро, подає живлення на радіомодуль для відправлення привітального пакета. Струм споживання стрибає з 10 мА до 180 мА, внутрішній опір підсівшого акумулятора викликає провал напруги нижче 2.4 В, апаратний блок Brown-Out Reset (BOR) миттєво перезавантажує мікроконтролер, і весь процес повторюється кожні 40 мілісекунд. Людина бачить темний екран і стверджує: «прилад вимкнувся і не реагує», хоча мікроконтролер безупинно виконує мільйони інструкцій на хвилину.
- **Шторм переривань (Interrupt Storm):** зовнішній вхідний пін переривання (EXTI) через відсутність зовнішньої підтяжки та високу вологість починає плавати, генеруючи переривання на частоті 1 МГц. Ядро 100% часу проводить у вході та виході з обробника ISR, не залишаючи квантів часу для виконання фонового коду `main()`.

#### 2. Клас скарг «Прилад сильно гріється і швидко розряджається»
Відчуття температури рукою є суб'єктивним: поверхня корпусу з температурою +48°C відчувається людиною як гаряча праска, хоча для кристала мікроконтролера допустима робоча температура сягає +85°C (комерційний діапазон) або +125°C (промисловий діапазон). Реальні причини перегріву та надлишкового споживання струму:
- **Лінійний стабілізатор під високим перепадом:** якщо прилад живиться від промислової шини 24 В, а внутрішні мікросхеми працюють від 3.3 В через лінійний LDO стабілізатор, теплова потужність, що розсіюється на кристалі регулятора, обчислюється за формулою:

```
P_diss = (V_in - V_out) · I_load
P_diss = (24 В - 3.3 В) · 0.08 А = 20.7 В · 0.08 А = 1.656 Вт
```

Півтора вати тепла у герметичному пластиковому корпусі без ребер радіатора розігрівають внутрішній об'єм повітря на +35°C вище температури навколишнього середовища.
- **Наскрізні струми силових ключів (Shoot-Through):** у схемах керування кроковими двигунами або DC-моторами верхній і нижній MOSFET транзистори напівмоста на частки мікросекунди відкриваються одночасно через неправильно налаштований час мертвої зони (англ. *dead-time*). Виникає короткочасне коротке замикання шини живлення на землю з імпульсним струмом у десятки ампер, що розігріває плату.
- **Паразитна тиристорна засувка (Latch-Up Effect):** після електростатичного розряду (ESD) на роз'єм або негативного викиду напруги нижче `-0.5 В` на виводі GPIO у CMOS-структурі кристала відкривається паразитний чотиришаровий тиристор `P-N-P-N`. Мікросхема переходить у стан низького опору, починає споживати постійний струм 200–400 мА і розігрівається до +100°C. Цей стан не скидається програмно — вийти з нього можна лише повним зняттям первинного живлення.
- **Незасвоєні виводи GPIO у режимі сну:** мікроконтролер переведено в режим глибокого сну (Deep Sleep), але виводи, підключені до зовнішніх роз'ємів, залишено в режимі плаваючого цифрового входу (`Input Floating`). Паразитні потенціали на затворах внутрішніх транзисторів викликають наскрізний витік струму, піднімаючи струм споживання сну з розрахункових 15 мкА до 8 мА.

#### 3. Клас скарг «Погано ловить зв'язок або губить пакети»
Користувач вважає, що «впав сервер» або «бракований модуль антени». Фізична реальність радіотракту:
- **Температурний дрейф кварцового резонатора:** при падінні температури до -20°C частота опорного кварцового генератора зміщується на 25–40 ppm. Якщо смуга пропускання приймача (RX Bandwidth) у протоколі LoRa була налаштована на вузькі 62.5 кГц заради дальності, зміщення центральної частоти виходить за межі смуги демодулятора, і пакети перестають детектуватися.
- **Пульсації імпульсного перетворювача (SMPS Noise):** імпульсний DC-DC стабілізатор під навантаженням генерує гармоніки перемикання на частотах 1.5 МГц, 3 МГц, 4.5 МГц. Гармоніки потрапляють на вхід малошумливого підсилювача (LNA) радіоприймача, підвищуючи шумову полицю (Noise Floor) на 12 дБ і скорочуючи реальну дальність зв'язку втричі.
- **Розстроювання антени конденсатом:** у ранкові години всередині невентильованого радіопрозорого ковпака випадає роса. Діелектрична проникність рідкої води `ε ≈ 80` зміщує резонансну частоту антени з 868 МГц до 790 МГц, спричиняючи відбиття 90% потужності передавача назад у вихідний каскад.

#### Стовп 1. Бортові логи та діагностичні дампи (Blackbox Context)
Бортове сховище інцидентів реєструє стан пристрою в критичну мить. Головне правило енергонезалежного логування — фіксувати не людський текст, а апаратний контекст:
1. **Апаратна причина попереднього скидання (Reset Cause):** вичитується з регістра `RCC_CSR` (або еквівалентного) під час найпершого такту ініціалізації ядра до скидання прапорів. Це дає однозначну відповідь: система впала по сторожовому таймеру IWDG, по віконному таймеру WWDG, через просідання живлення BOR, через програмний виклик або по зовнішній ніжці NRST.
2. **Стек-фрейм винятку (Exception Stack Frame):** при виникненні `HardFault` чи `UsageFault` рушій знімає покажчик інструкції `PC` (адреса збійної інструкції в коді), регістр зв'язку `LR` (адреса виклику функції) та регістр статусу помилок `CFSR`.
3. **Водяні знаки пам'яті (Memory Watermarks):** фіксація залишку вільного стека кожного потоку RTOS (`uxTaskGetStackHighWaterMark()`) та лічильника фрагментації динамічної купи.
4. **Статистика шинних помилок:** лічильники відсутності підтвердження `I2C NACK`, переповнення приймального буфера `SPI OVR` та помилок контрольної суми `CRC`.

Детальна організація апаратного сховища на базі швидких енергонезалежних мікросхем наведена у вставці [Енергонезалежне сховище діагностичного журналу](root:embedded/skarha-iaka-ne-ie-zvitom-pro-pomylku/comp-diagnostic-blackbox-storage.md).

#### Стовп 2. Родовід заліза та BOM-варіативність (Hardware Lineage)
Один і той самий скомпільований бінарний файл прошивки може бездоганно працювати на тисячі пристроїв ревізії `PCB v1.2` і систематично зависати на платах ревізії `PCB v1.3`. Причина полягає у варіативності компонентів (англ. *Bill of Materials variations*):
- **Заміна пасивних компонентів:** якщо постачальник на конвеєрі замінив керамічний конденсатор фільтра живлення 10 мкФ з діелектриком `X7R` на дешевший аналог `Y5V`, при температурі -15°C його реальна ємність падає на 70% (до 3 мкФ). Це призводить до сплесків напруги живлення ядра під час роботи радіотракту.
- **Підтягуючі резистори відкритих колекторів:** заміна підтяжки шини I2C з номіналу 2.2 кОм на 10 кОм збільшує час наростання фронту сигналу `t_rise`. За високої вологості паразитна ємність монтажу зростає, фронт затягується, і мікроконтролер пропускає біт підтвердження ACK.
- **Кремнієві ревізії мікросхем (Silicon Stepping & Errata):** виробники мікроконтролерів регулярно випускають оновлені ревізії кристалів. Наприклад, в Errata мікроконтролера може бути зафіксований дефект: «при одночасному зверненні DMA до шини APB1 та записі у Flash-пам'ять шина блокується на 4 такти». На старій ревізії чипа цей дефект викликав HardFault, а на новій — ні.

#### Стовп 3. Телеметрія середовища та флотські метрики (Environmental Profile)
Телеметрія, що надходить на сервер від усього флоту пристроїв, формує статистичний фон, на якому дефектні екземпляри виділяються як аномалії:
- **Кореляція з добовою температурою:** якщо 95% зависань стаються у проміжку між 14:00 та 16:00, інженер досліджує тепловий баланс корпусу під прямим сонячним промінням та температурний дрейф внутрішнього RC-генератора LSI, що тактує сторожовий таймер.
- **Гістограма просідання живлення:** побудова графіка залежності мінімальної зафіксованої напруги `V_min` від поточної температури акумулятора дозволяє виявити зростання внутрішнього еквівалентного послідовного опору (ESR) батареї задовго до повного виходу станції з ладу.
- **Метрики якості зв'язку:** моніторинг рівня фонового шуму RSSI та кількості повторних спроб передачі (Retries) дозволяє відрізнити фізичну несправність трансивера від появи зовнішньої завади в радіоефірі.

### Інженерний протокол первинного сортування (Triage Playbook)

Щоб сервісна служба не витрачала час на з'ясування емоційних деталей, інженерна команда розробляє стандартизований чекліст первинного обстеження (англ. *Triage Playbook*). Польовий технік або оператор першої лінії зобов'язаний зафіксувати суворі вимірювані параметри:

1. **Ідентифікатори примірника:** точний 64-бітний серійний номер MCU (`Device UID`), ревізія друкованої плати на шовкографії (`PCB Rev`) та версія прошивки з хешем коміту Git (`FW Build`).
2. **Параметри джерела живлення:** напруга розімкнутого кола акумулятора (OCV, Open Circuit Voltage) та напруга під час тестової передачі пакета радіомодулем.
3. **Стан зовнішніх світлодіодних індикаторів:** фіксація частоти спалахів індикаторного LED. Спеціальний режим самодіагностики відтворює код аварії: наприклад, серія з 3 коротких спалахів позначає зависання шини I2C, 5 спалахів — спрацьовування детектора BOR, безперервне горіння — HardFault.
4. **Огляд фізичного середовища:** наявність крапель роси під захисним ковпаком, слідів корозії на клемах роз'ємів або механічних деформацій антени.

### Анатомія регістрів відмов ядра ARM Cortex-M

Коли мікроконтролер переходить у переривання `HardFault`, апаратний блок діагностики записує причину аварії в спеціалізовані системні регістри ядра. Розуміння бітової маски цих регістрів дозволяє за мілісекунди відрізнити збій пам'яті від замикання периферійної шини:

```
                  СТРУКТУРА СИСТЕМНОГО РЕГІСТРА CFSR (0xE000ED28)
                  
  31             16 15              8 7              0
 ┌─────────────────┬─────────────────┬─────────────────┐
 │   UsageFault    │    BusFault     │   MemManage     │
 │  Status (UFSR)  │  Status (BFSR)  │  Status (MMFSR) │
 └─────────────────┴─────────────────┴─────────────────┘
```

#### 1. Секція MemManage Fault Status Register (MMFSR, біти [7:0])
- `DACCVIOL` (біт 1): порушення доступу до даних. Спроба запису або читання адреси, захищеної модулем захисту пам'яті MPU (наприклад, спроба запису користувацького потоку в таблицю векторів переривань).
- `IACCVIOL` (біт 0): порушення вибірки інструкцій. Спроба передати керування на адресу пам'яті, де встановлено прапорець `XN` (Execute Never), наприклад, спроба виконати код із буфера в оперативній пам'яті SRAM.
- `MMFARVALID` (біт 7): якщо біт виставлено в одиницю, регістр `MMFAR` (0xE000ED34) містить точну 32-бітну адресу пам'яті, звернення до якої спричинило аварію.

#### 2. Секція BusFault Status Register (BFSR, біти [15:8])
- `PRECISERR` (біт 1): точна помилка шини даних. Процесор намагався прочитати дані за неіснуючою адресою шини. Регістр `BFAR` (0xE000ED38) містить точну адресу збою, а значення `PC` у стек-фреймі вказує безпосередньо на інструкцію `LDR`.
- `IMPRECISERR` (біт 2): неточна (асинхронна) помилка шини. Помилка виникла під час фонового скидання буфера запису шини (Write Buffer). Значення `PC` у стек-фреймі вказує не на команду запису, а на випадкову наступну інструкцію програми. Для локалізації таких помилок розробник тимчасово вимикає буферизацію запису через встановлення біта `DISDEFWBUF` у регістрі `ACTLR`.
- `STKERR` / `UNSTKERR` (біти 4, 3): збій вирівнювання або вихід за межі пам'яті під час автоматичного збереження або відновлення стек-фрейму ядром при вході у переривання.

#### 3. Секція UsageFault Status Register (UFSR, біти [31:16])
- `UNDEFINSTR` (біт 0): спроба виконання невідомої або невалідної інструкції. Класичний симптом пошкодження пам'яті програм або стрибка за невірним покажчиком функції.
- `INVSTATE` (біт 1): спроба виконання коду в неприпустимому стані Thumb/ARM (наприклад, молодший біт покажчика функції дорівнює нулю, що вимикає режим Thumb на Cortex-M).
- `UNALIGNED` (біт 8): несинхронізоване звернення до пам'яті (спроба зчитати 32-бітне слово за непарною адресою, коли увімкнено суворий контроль вирівнювання).
- `DIVBYZERO` (біт 9): операція цілочисельного ділення на нуль (інструкції `SDIV`/`UDIV`, якщо активовано біт `DIV_0_TRP` у регістрі `CCR`).

### Захист пам'яті через MPU: перетворення тихих збоїв на явні інциденти

Найскладніші дефекти у вбудованому ПЗ мають природу «тихого спотворення» (англ. *silent memory corruption*): помилка у покажчику затирає сусідній буфер пам'яті, але система продовжує працювати ще кілька годин, доки випадковий потік не прочитає сміття і не зависне далеко від місця первинної помилки.

Увімкнення апаратного блоку захисту пам'яті (MPU, Memory Protection Unit) перетворює такі приховані дефекти на миттєвий, детермінований HardFault із точним фіксуванням адреси інструкції-порушника:
1. **Регіон Flash (Read-Only + Execute):** будь-яка спроба випадкового запису у flash-пам'ять через «дикий покажчик» (wild pointer) миттєво генерує виняток `MemManage`.
2. **Регіон таблиці векторів переривань (Privileged Read-Only):** захист перших 256 байтів SRAM від перезапису дескрипторів переривань.
3. **Бар'єрні зони стеків (Stack Guard Regions):** на дні стека кожного потоку RTOS налаштовується 32-байтна зона без доступу. При найменшій спробі переповнення стека процесор генерує `DACCVIOL` до того, як стек затре сусіднє завдання.

### Реконструкція траси викликів (Stack Unwinding) без налагоджувача

Коли польовий пристрій скидає 64-байтовий дамп на сервер, у розпорядженні розробника є лише значення покажчика стека `SP`, лічильника команд `PC` та регістра зв'язку `LR`. Проте для глибокого аналізу необхідно відновити повний ланцюжок викликів (англ. *call stack unwinding*): яка саме послідовність функцій призвела до виклику фатального драйвера.

```
       РУЧНЕ ВІДНОВЛЕННЯ ЛАНЦЮЖКА ВИКЛИКІВ ЗІ СТЕК-ФРЕЙМУ
       
  Адреса в стеку (SP)     Значення слова        Розшифровка через addr2line
 ┌─────────────────────┐ ┌──────────────────┐  ┌───────────────────────────────┐
 │ SP + 0x00 (R0)      │ │ 0x200014B0       │  │ Аргумент: покажчик на буфер   │
 │ SP + 0x04 (R1)      │ │ 0x0000000E       │  │ Аргумент: довжина 14 байтів   │
 │ SP + 0x14 (LR)      │ │ 0x080031B1       │  │ sht31_read_temp() в sht31.c:88│
 │ SP + 0x18 (PC)      │ │ 0x08004A2D       │  │ i2c_wait_rxne() в i2c.c:142   │
 │ SP + 0x20 (Поперед.)│ │ 0x08001F45       │  │ telemetry_task() в app.c:215  │
 └─────────────────────┘ └──────────────────┘  └───────────────────────────────┘
```

#### Алгоритм автоматичного розгортання стека:
1. За адресою `PC` знімається поточна функція (`i2c_wait_rxne`).
2. Регістр `LR` перевіряється на наявність апаратного коду `EXC_RETURN` (значення `0xFFFFFFF9`, `0xFFFFFFFD` або `0xFFFFFFE9`). Якщо `LR` містить такий код, початковий виклик стався з переривання, а адреса повернення лежить безпосередньо у стек-фреймі.
3. Програмний парсер сканує слова вгору по стеку від покажчика `SP`, зіставляючи кожне 32-бітне значення з діапазоном адрес секції коду Flash-пам'яті (`0x08000000 .. 0x08100000`).
4. Якщо знайдена адреса має непарне значення (встановлено молодший біт Thumb-режиму `LSB = 1`) і передує інструкції виклику `BL` або `BLX`, вона фіксується як точка виклику попередньої функції у ланцюжку.
5. За допомогою утиліти `addr2line` кожна адреса транслюється у файл вихідного коду та номер рядка.

### Статистичний аналіз дефектів у польовому флоті: розподіл Вейбулла

Коли кількість скарг від користувачів зростає, інженерній команді критично важливо розуміти часову динаміку відмов. Для цього застосовується статистичний **аналіз надійності за розподілом Вейбулла** (англ. *Weibull Reliability Analysis*, названий на честь шведського фізика Валодді Вейбулла):

Густина ймовірності відмови вбудованого пристрою в часі `t` описується функцією:

```
f(t) = (β / η) · (t / η)^(β - 1) · e^(-(t / η)^β)
```

де:
- `β` (бета) — параметр форми (англ. *shape parameter*), що визначає фізичний механізм відмови.
- `η` (ета) — характеристичний термін служби (англ. *scale parameter*), тобто час, за який виходить з ладу 63.2% пристроїв партії.

```
       КЛАСИЧНА КРИВА ВАННИ (BATH-TUB CURVE) ТА ПАРАМЕТР ВЕЙБУЛЛА
       
  Інтенсивність відмов λ(t)
     ▲
     │  β < 1               β = 1                      β > 1
     │ (Ранні дефекти)     (Випадкові збої)           (Фізичний знос)
     │ ╲                                            ╱
     │  ╲                                          ╱
     │   ╲────────────────────────────────────────╱
     │   
     └────────────────────────────────────────────────────────► Час (t)
       0..3 місяці         3..36 місяців             > 36 місяців
```

#### Інтерпретація параметра форми бета (`β`) для розбору польових скарг:
1. **`β < 1` (Період припрацювання / Дитяча смертність):** інтенсивність відмов стрімко спадає з часом. Якщо скарги про зависання надходять лише у перші два тижні після встановлення станції, причина полягає у **виробничих дефектах монтажу**: холодні пайки під BGA-чипами, дефектні партії конденсаторів або мікротріщини у друкованих провідниках, що руйнуються при першому термоциклі.
2. **`β = 1` (Період нормальної експлуатації):** інтенсивність відмов постійна і не залежить від віку пристрою (експоненційний розподіл). Відмови викликані **зовнішніми випадковими подіями**: прямі удари грозових розрядів, вандалізм, екстремальні електромагнітні перешкоди від промислових зварювальних апаратів.
3. **`β > 1` (Період деградації та зносу):** інтенсивність відмов експоненційно зростає з віком. Якщо пристрої починають масово зависати після трьох років бездоганної роботи, причина у **фізичному старінні компонентів**: висихання рідкого електроліту в алюмінієвих конденсаторах, деградація секторів Flash-пам'яті через вичерпання ліміту циклів стирання (`10⁵` циклів) або корозія паяних з'єднань під дією вологи.

### Метод 5 Whys: відділення симптому від кореневої причини (RCA)

Коли три вектори фактів зібрано, інженер розпочинає процедуру аналізу кореневої причини методом **«П'яти чому»** (англ. *5 Whys Analysis*). Цей метод запобігає поверхневому «латання дірок» (англ. *symptom patching*), коли розробник просто додає чергову затримку `delay(10)` або примусово скидає пристрій кожні пів години, не усуваючи фізичне джерело дефекту.

![Аналіз кореневої причини (5 Whys) у вбудованій системі](/root/course/embedded/skarha-iaka-ne-ie-zvitom-pro-pomylku/img/five-whys-embedded-rca.svg)
*Покрокове розгортання ланцюжка 5 Whys для реального апаратного інциденту: від зовнішнього симптому через апаратні стани до фундаментальної причини в схемотехніці та архітектурі драйвера.*

Розгляньмо детальний розбір реального інциденту: «Метеостанція щодня о 18:00 припиняє передачу телеметрії»:

```
РІВЕНЬ 0 (СКАРГА КОРИСТУВАЧА):
«Прилад зависає щодня приблизно в один і той самий час і не шле дані на сервер».

ЧОМУ №1 (Первинний симптом):
— Чому прилад не шле дані?
— Тому що мікроконтролер перебуває у стані постійного перезавантаження за сторожовим таймером IWDG.
  [Доказ: регістр RCC_CSR містить біт IWDGRSTF = 1].

ЧОМУ №2 (Програмне блокування):
— Чому спрацьовує сторожовий таймер IWDG?
— Тому що головний потік збору сенсорних даних зависає всередині функції зчитування датчика sht31_read().
  [Доказ: розбір Core Dump показує PC = 0x08004A2C, потік SensorTask заблоковано на прапорі RXNE].

ЧОМУ №3 (Апаратний стан шини):
— Чому функція sht31_read() очікує прапорець RXNE нескінченно?
— Тому що лінія даних I2C SDA затиснута зовнішнім сенсором у нуль, і мікроконтролер не може згенерувати тактовий імпульс Stop.
  [Доказ: лічильник bus_err_i2c = 14, стан виводу SDA на осцилографі = 0.1 В].

ЧОМУ №4 (Фізичний механізм збою):
— Чому датчик затиснув лінію SDA в нуль саме о 18:00?
— О 18:00 за розкладом вмикається радіомодуль для передачі денного звіту. Струм 250 мА просаджує загальну лінію 3.3 В до 2.6 В.
  Датчик зазнає локального brown-out скидання посеред передачі байта ACK, його внутрішній автомат станів збивається 
  і залишає вихідний FET відкритим. Драйвер мікроконтролера не містить коду скидання шини генерацією 9 імпульсів SCL.
  [Доказ: телеметрія фіксує просідання V_bat = 2.78 В, у вихідному коді i2c_driver.c відсутня функція bus_recovery()].

ЧОМУ №5 (КОРЕНЕВА СИСТЕМНА ПРИЧИНА):
— Чому просідання від радіо впливає на датчик, а в драйвері немає відновлення?
— У ревізії PCB Rev B радіотракт і чутливі датчики підключили до одного LDO стабілізатора без розв'язувального діода 
  та достатнього запасу ємності, а в репозиторії драйверів I2C використовувався базовий приклад без таймаутів та 9-SCL recovery.
```

#### Комплексне усунення дефекту на двох рівнях:
1. **Апаратний рівень (Hardware Fix):** розділення шин живлення радіотракту та аналогових датчиків через окремі стабілізатори LDO або додавання LC-фільтра зі зворотним блокуючим діодом Шотткі для утримання напруги сенсорів під час піків передавача.
2. **Програмний рівень (Firmware Architecture):** повне переписування драйвера шини I2C на роботу з жорсткими таймаутами на базі системного лічильника циклів DWT та обов'язкова реалізація процедури апаратного розблокування шини (генерація 9 тактів `SCL` на виводі GPIO з наступним формуванням стану STOP) під час будь-якої невдалої транзакції.

Практичну реалізацію вбудованого модуля перехоплення аварійних контекстів наведено у вставці [Програмний рушій фіксації та первинної класифікації інцидентів](root:embedded/skarha-iaka-ne-ie-zvitom-pro-pomylku/proj-incident-triaging-engine.md).

### Структура та збереження діагностичного знімка

Для того щоб тріангуляція була технічно можливою, вбудована система повинна формувати стандартизований **діагностичний знімок інциденту** (англ. *Incident Snapshot Frame*) розміром 64 байти.

![Структура енергонезалежного дампа інциденту](/root/course/embedded/skarha-iaka-ne-ie-zvitom-pro-pomylku/img/incident-snapshot-frame.svg)
*Структура бінарного кадру енергонезалежного дампа інциденту (Incident Snapshot Frame): апаратні прапори, регістри винятків, контекст RTOS та параметри середовища.*

```
+---------------------------------------------------------------------------------------------------+
|                            СТРУКТУРА ДІАГНОСТИЧНОГО ЗНІМКА (64 БАЙТИ)                             |
+---------------------------------------------------------------------------------------------------+
| 0x00..0x03 : Magic Tag (0xDEADBEEF)               │ 0x04..0x0B : Timestamp & Boot Counter        |
| 0x0C..0x0F : Reset Flags (RCC_CSR: IWDG/BOR/PIN)  │ 0x10..0x1F : CPU Context (PC, LR, CFSR, HFSR)|
| 0x20..0x2F : RTOS State (Task ID, Stack Headroom) │ 0x30..0x3F : Bus Counters (I2C/SPI Errors)   |
| 0x40..0x4B : Environment (V_bat, Die Temp, RSSI)  │ 0x4C..0x4F : Frame Integrity Checksum (CRC32)|
+---------------------------------------------------------------------------------------------------+
```

Специфікація двійкового контракту та бітових полів наведена у вставці [Бінарний протокол передачі діагностичного знімка інциденту](root:embedded/skarha-iaka-ne-ie-zvitom-pro-pomylku/api-incident-telemetry-protocol.md).

### Реалізація: перехоплення та збереження аварійного стану

Нижче наведено код обробника критичної помилки, що зберігає контекст у виділену пам'ять Backup SRAM без використання динамічної пам'яті:

:::tabs
```c
/* fatal_handler.c */
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

#define SNAPSHOT_MAGIC   0xDEADBEEFUL
#define BACKUP_SRAM_BASE 0x40024000UL

typedef struct __attribute__((packed)) {
    uint32_t magic;
    uint32_t reset_reason;
    uint32_t fault_pc;
    uint32_t fault_lr;
    uint32_t fault_cfsr;
    uint16_t v_bat_mv;
    int16_t  temp_c;
    uint16_t bus_i2c_nack;
    uint16_t rtos_task_id;
    uint32_t crc32;
} crash_dump_t;

static uint32_t calc_crc32(const uint8_t *data, size_t len) {
    uint32_t crc = 0xFFFFFFFFUL;
    for (size_t i = 0; i < len; ++i) {
        crc ^= data[i];
        for (int b = 0; b < 8; ++b) {
            crc = (crc >> 1) ^ (0xEDB88320UL & -(crc & 1));
        }
    }
    return ~crc;
}

void HardFault_C_Handler(uint32_t *stack_frame, uint32_t lr_exc) {
    /* Вимикаємо всі масковані переривання */
    __asm volatile ("cpsid i" : : : "memory");

    crash_dump_t dump;
    memset(&dump, 0, sizeof(dump));

    dump.magic = SNAPSHOT_MAGIC;
    dump.reset_reason = 0x20000000UL; /* Прапор IWDG з регістра RCC_CSR */
    dump.fault_pc = stack_frame[6];    /* Шосте слово у стек-фреймі Cortex-M — PC */
    dump.fault_lr = stack_frame[5];    /* П'яте слово у стек-фреймі — LR */
    dump.fault_cfsr = (*((volatile uint32_t*)0xE000ED28UL)); /* Апаратний регістр CFSR */
    dump.v_bat_mv = 2780;              /* Останнє збережене значення АЦП */
    dump.temp_c = 64;
    dump.bus_i2c_nack = 14;
    dump.rtos_task_id = 2;

    /* Обчислення контрольної суми без поля CRC */
    dump.crc32 = calc_crc32((const uint8_t*)&dump, sizeof(dump) - sizeof(uint32_t));

    /* Атомарне копіювання у Backup SRAM */
    memcpy((void*)BACKUP_SRAM_BASE, &dump, sizeof(dump));

    /* Примусовий бар'єр пам'яті перед перезавантаженням */
    __asm volatile ("dsb 0xF" : : : "memory");
    __asm volatile ("isb 0xF" : : : "memory");

    /* Скидання мікроконтролера */
    *((volatile uint32_t*)0xE000ED0CUL) = 0x05FA0004UL; /* AIRCR SYSRESETREQ */

    while(1) {
        __asm volatile ("nop");
    }
}
```

// FatalHandler.hpp / FatalHandler.cpp
#include <cstdint>
#include <cstring>
#include <span>
#include <optional>

namespace Diagnostics {

inline constexpr std::uint32_t SnapshotMagic = 0xDEADBEEFUL;
inline constexpr std::uintptr_t BackupSramAddr = 0x40024000UL;

#pragma pack(push, 1)
struct CrashDump {
    std::uint32_t magic{SnapshotMagic};
    std::uint32_t reset_reason{0};
    std::uint32_t fault_pc{0};
    std::uint32_t fault_lr{0};
    std::uint32_t fault_cfsr{0};
    std::uint16_t v_bat_mv{0};
    std::int16_t  temp_c{0};
    std::uint16_t bus_i2c_nack{0};
    std::uint16_t rtos_task_id{0};
    std::uint32_t crc32{0};
};
#pragma pack(pop)

class CrashManager {
public:
    static std::uint32_t calculateCrc32(std::span<const std::uint8_t> data) noexcept {
        std::uint32_t crc = 0xFFFFFFFFUL;
        for (const auto byte : data) {
            crc ^= byte;
            for (int bit = 0; bit < 8; ++bit) {
                crc = (crc >> 1) ^ (0xEDB88320UL & -(crc & 1));
            }
        }
        return ~crc;
    }

    static void handleFatalCrash(const std::uint32_t* stackFrame) noexcept {
        __asm volatile ("cpsid i" : : : "memory");

        CrashDump dump;
        dump.reset_reason = 0x20000000UL;
        dump.fault_pc = stackFrame[6];
        dump.fault_lr = stackFrame[5];
        dump.fault_cfsr = *reinterpret_cast<const volatile std::uint32_t*>(0xE000ED28UL);
        dump.v_bat_mv = 2780;
        dump.temp_c = 64;
        dump.bus_i2c_nack = 14;
        dump.rtos_task_id = 2;

        const auto payload = std::span<const std::uint8_t>(
            reinterpret_cast<const std::uint8_t*>(&dump),
            sizeof(CrashDump) - sizeof(std::uint32_t)
        );
        dump.crc32 = calculateCrc32(payload);

        auto* target = reinterpret_cast<CrashDump*>(BackupSramAddr);
        *target = dump;

        __asm volatile ("dsb 0xF" : : : "memory");
        __asm volatile ("isb 0xF" : : : "memory");

        *reinterpret_cast<volatile std::uint32_t*>(0xE000ED0CUL) = 0x05FA0004UL;

        while (true) {
            __asm volatile ("nop");
        }
    }
};

} // namespace Diagnostics

### Метод Фейнмана: контрольована ін'єкція збоїв (Fault Injection)

Головний критерій істинності знайденої кореневої причини формулюється за принципом Річарда Фейнмана: **«Якщо ти не можеш детерміновано відтворити збій у лабораторії на стенді — ти не розумієш справжнього фізичного механізму відмови»**.

Здогадки та припущення («напевно, прошивка десь переповнила стек») не мають інженерної сили. Команда повинна відтворити відмову за допомогою методів спрямованої ін'єкції несправностей (англ. *fault injection testing*):

```
+------------------------------------+-----------------------------------------------------+-------------------------------------------------------+
| Метод лабораторної ін'єкції        | Фізичний інструмент імітації                        | Що верифікується під час тесту                        |
+------------------------------------+-----------------------------------------------------+-------------------------------------------------------+
| Просідання живлення (Voltage Sag)  | Програмоване джерело з імпульсним скиданням до 2.4 В | Спрацьовування BOR, відсутність зависання I2C датчика |
| Температурний стрес                | Кліматична термокамера (-40°C .. +85°C)             | Дрейф частоти RC генераторів та струми витоку сну     |
| Замикання шини (Bus Pin Short)     | MOSFET ключ, що затискає SDA на GND на 5 мілісекунд | Робота процедури 9-SCL recovery та таймаутів драйвера |
| Електромагнітна завада (EFT Burst) | Генератор імпульсних наносекундних пачок (IEC 61000)| Ефективність вхідних TVS-діодів та стійкість ядра     |
+------------------------------------+-----------------------------------------------------+-------------------------------------------------------+
```

#### Лабораторний тест детермінованого розблокування:
1. На тестовому стенді до шини I2C підключається транзисторний ключ, керований генератором імпульсів.
2. Під час активного обміну даними між MCU та сенсором лінія `SDA` примусово закорочується на `GND` на 20 мілісекунд, імітуючи збій живлення сенсора.
3. **Критерій проходження тесту:** мікроконтролер не зависає в блокуючому циклі, фіксує таймаут 50 мс, генерує 9 імпульсів `SCL` на виводі тактування, успішно звільняє шину і продовжує виконання черги завдань без спрацьовування сторожового таймера.

### Замикання контуру: перетворення інциденту на архітектурний захист

Істинний фінал розбору польової скарги — це не просто закриття одного тикета в системі підтримки, а зміна інженерних процесів та архітектури наступних ревізій виробу:
1. **Оновлення матриці FMEA:** сценарій «просідання живлення датчика під час передачі радіокадру» додається до таблиці відмов з високим пріоритетом критичності.
2. **Апаратний регресійний тест (HIL Testing):** тест з ін'єкцією просідання напруги та замиканням шини автоматично включається у щоденний нічний прогін на стенді Hardware-in-the-Loop.
3. **Виробничий контроль (End-of-Line Test):** до тестової програми на виробничому конвеєрі додається обов'язкова перевірка внутрішнього опору джерела живлення та вимірювання часу наростання фронтів сигналів I2C на кожній зібраній платі.

Лише за такої культури кожна незрозуміла польова скарга користувача перестає бути джерелом роздратування і перетворюється на каталізатор надійності всього продукту.
