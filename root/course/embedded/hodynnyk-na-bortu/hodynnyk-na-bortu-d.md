# Годинник на борту: RTC, дрейф, монотонність

<preknowlist>

- [Генератор П'єрса](root:hw-analog/pierce-oscillator) — інверторна схема збудження кварцу та вплив навантажувальної ємності `C_L`.
- [Монотонний проти настінного часу](root:sf-apps/monotonic-vs-wall-time) — чому вимірювання інтервалів вимагає неперервної шкали, а настінний годинник стрибає від синхронізацій.
- [Дрейф годинників](root:sf-distributed/clock-offset-drift) — як накопичується фазова похибка від різниці частот генераторів.
</preknowlist>

Автономний прилад у полі — логер вібрацій, лічильник тепла чи телеметричний вузол — живе у двох вимірах часу одночасно. З одного боку, сервер і людина вимагають календаря: «записати подію за 14 жовтня 2026 року, 03:15:02 UTC», а протокол захищеного зв'язку відхилить з'єднання, якщо системний час виявиться поза вікном дії криптографічного сертифіката. З іншого боку, локальний цикл керування мотором чи фільтр вимірювань вимагає точного інтервалу: обчислити крок інтегрування `dt` між двома опитуваннями давача.

Коли ці два завдання наївно покладають на один і той самий годинниковий регістр мікроконтролера, пристрій неминуче ламається. Якщо прошивка отримує від сервера поправку часу й безпосередньо записує новий час у регістр, перевівши стрілки назад на три секунди, вираз `dt = t_now - t_prev` повертає від'ємне число. У беззнаковій 32-бітній арифметиці мікросекунд різниця `(uint32_t)(97 - 100)` миттєво перетворюється на `4 294 967 293` мікросекунди — понад 71 хвилину очікування. Таймери задач зависають, сторожовий пес не отримує скидання, а регулятор положення видає катастрофічний ривок.

Щоб бортовий час не руйнував роботу пристрою, мікроконтролер повинен розділяти час на дві незалежні системи координат: суворо монотонну внутрішню шкалу без стрибків і календарний настінний час. Крім того, інженер має компенсувати неминучий фізичний дрейф годинникового кварцу та захистити хід часу від раптового знеструмлення.

## Фізика та схемотехніка бортового RTC: кварц 32.768 кГц і температурний дрейф

Годинник реального часу (англ. *Real-Time Clock*, RTC) — це спеціалізований периферійний блок мікроконтролера, спроєктований для неперервного відліку секунд, хвилин, годин і календарної дати за мінімального споживання енергії.

Серцем будь-якого класичного RTC є низькочастотний кварцовий резонатор із номінальною частотою 32 768 Гц. Це число обрано не випадково:

```
2¹⁵ = 32768
```

Степінь двійки дає змогу побудувати дільник частоти на найпростішому 15-розрядному двійковому асинхронному лічильнику (ланцюжку з 15 T-тригерів). Кожен тригер ділить частоту навпіл, і на виході 15-го каскаду утворюється рівно 1 імпульс на секунду (1 Гц, 1 PPS — *pulse per second*). Така схема не вимагає складних цифрових помножувачів або енергоємних блоків PLL, споживаючи менш ніж 300–500 наноампер струму.

```
+--------------------------------------------------------------------------------+
|  Кварц 32.768 кГц  -->  [ : 2¹⁵ (15 T-тригерів) ]  -->  1.000 Гц (1 PPS)       |
|                             споживання < 0.5 мкА                               |
+--------------------------------------------------------------------------------+
```

### Геометрія камертонного кристала

На відміну від високочастотних мегагерцових кварців (які працюють на зсувній моді коливань пластини, так званий AT-зріз), кварц на 32.768 кГц виготовляють у формі крихітного камертона (англ. *tuning fork crystal*, XY-зріз). Дві паралельні ніжки кварцового камертона здійснюють згинні коливання назустріч одна одній під дією прикладеного електричного поля.

Камертонна форма забезпечує малі габарити резонатора при низькій частоті, але має принципову фізичну особливість — квадратичну (параболічну) залежність резонансної частоти від температури.

Відносне відхилення частоти камертонного кварцу описується формулою:

```
Δf / f₀ = -β · (T - T₀)²
```

де:
- `Δf / f₀` — відносний дрейф частоти, виражений у частинах на мільйон (англ. *parts per million*, ppm, `1 ppm = 10⁻⁶`);
- `β` — параболічний температурний коефіцієнт (зазвичай `β ≈ 0.034 ... 0.040 ppm/°C²`, типово беруть `-0.04 ppm/°C²`);
- `T₀` — температура вершини параболи (англ. *turnover temperature*), на якій частота максимальна; для більшості годинникових кварців `T₀ = +25 °C ± 5 °C`;
- `T` — поточна температура навколишнього середовища (°C).

Зверніть увагу на знак мінус перед коефіцієнтом `β`: парабола спрямована гілками **суворо вниз**. Це означає, що за будь-якого відхилення температури від кімнатної (+25 °C) — як у бік сильного морозу, так і в бік спеки — частота камертонного кварцу **завжди зменшується**. Відповідно, некомпенсований годинник за відхилення температури завжди **відстає**.

![Температурний дрейф годинникового кварцу 32.768 кГц](/root/course/embedded/hodynnyk-na-bortu/img/quartz-temp-drift.svg)
*Параболічна залежність відносного відхилення частоти камертонного кварцу 32.768 кГц від температури. Вершина кривої лежить при 25 °C. За температури -20 °C дрейф сягає -81 ppm (-7.0 с на добу), а при +60 °C — -49 ppm (-4.2 с на добу).*

### Розрахунок добового накопичення похибки

Переведемо величину дрейфу в ppm у реальний час відставання годинника. В одній астрономічній добі міститься:

```
86400 секунд = 24 · 3600 с
```

Похибка ходу годинника за добу обчислюється як:

```
Δt_доба = (Δf / f₀) · 86400 с
```

Навіть за ідеальної кімнатної температури (+25 °C) стандартний годинниковий кварц має початковий виробничий допуск (англ. *frequency tolerance*) близько `±20 ppm`. Порахуємо добову похибку:

```
Δt_доба = 20 · 10⁻⁶ · 86400 с
= 1.728 с/добу
```

За один місяць (30 діб) годинник із похибкою 20 ppm піде вперед або назад на `1.728 · 30 ≈ 51.8 секунди`. За рік похибка перевищить 10.5 хвилин.

Якщо ж пристрій встановлено на вулиці, де взимку температура падає до -20 °C, температурний складник похибки складе:

```
Δf_temp / f₀
= -0.04 · (-20 - 25)²       [підстановка T = -20 °C та вершини параболи T₀ = 25 °C]
= -0.04 · (-45)²            [обчислення різниці температур ΔT = -45 °C]
= -0.04 · 2025              [піднесення до квадрата: (-45)² = 2025]
= -81 ppm                   [множення на параболічний коефіцієнт β]
```

Додавши до цього початкову виробничу похибку резонатора (-20 ppm), отримуємо сумарний дрейф близько `-101 ppm`. Обчислимо відставання годинника за добу на морозі:

```
Δt_доба
= -101 · 10⁻⁶ · 86400 с     [множення відносного дрейфу на кількість секунд у добі]
= -8.726 с/добу             [накопичена похибка ходу за одну добу]
```

За місяць експлуатації на морозі -20 °C некомпенсований RTC відстане на **4 хвилини 22 секунди**. Для пристрою обліку електроенергії чи газу, що використовує зонні тарифи «день/ніч», таке зміщення межі тарифу призведе до фінансових штрафів або викривлення балансу мережі.

### Узгодження навантажувальної ємності (Load Capacitance)

Частота коливань кварцу залежить не лише від температури, а й від електричної ємності зовнішніх конденсаторів у схемі [генератора П'єрса](root:hw-analog/pierce-oscillator). Виробник кварцу вказує в паспорті номінальну навантажувальну ємність `C_L` (типові значення для 32.768 кГц: 6.0 пФ, 9.0 пФ або 12.5 пФ).

Реальна ємність схеми складається з двох дискретних конденсаторів `C₁` і `C₂`, підімкнених до виводів кварцу та землі, а також паразитної ємності друкованих провідників і виводів мікроконтролера `C_stray`:

```
C_L = (C₁ · C₂) / (C₁ + C₂) + C_stray
```

Зазвичай обирають `C₁ = C₂ = C_ext`, тоді:

```
C_L = C_ext / 2 + C_stray
```

Звідки необхідна ємність дискретних конденсаторів:

```
C_ext = 2 · (C_L - C_stray)
```

Паразитна ємність монтажу `C_stray` на якісно розведеній друкованій платі становить від 2 до 5 пФ. Якщо обрати кварц із паспортом `C_L = 12.5 пФ` і припустити `C_stray = 3 пФ`, номінал кожного зовнішнього конденсатора має становити:

```
C_ext = 2 · (12.5 - 3.0) = 19 пФ  (обирають стандартний номінал 18 або 20 пФ)
```

Якщо помилитися з вибором `C_ext` (наприклад, поставити конденсатори на 33 пФ для кварцу на 6 пФ), робоча точка зміститься вниз за частотою, створивши додатковий постійний дрейф у десятки ppm ще до впливу температури.

### Запас підсилення генератора (Gain Margin) та стійкість запуску на морозі

Ще одна неочевидна пастка низькочастотних камертонних кварців — їхній гігантський **еквівалентний послідовний опір** (англ. *Equivalent Series Resistance*, ESR, або `R₁` у [моделі Баттерворта–ван Дайка](root:hw-components/quartz-rlc-model)). Якщо у мегагерцових кварців (8–25 МГц) ESR становить лише 20–50 Ом, то у годинникового кварцу 32.768 кГц через крихітний розмір пластини та низьку частоту коливань ESR досягає **30–80 кОм** (типово 50–70 кОм).

Щоб генератор П'єрса взагалі збудився після подачі живлення або виходу зі сну, крутизна вбудованого інвертора мікроконтролера `g_m` (transconductance) повинна перевищувати критичну величину `g_{m,crit}`:

```
g_{m,crit} = 4 · ESR · (2π · f₀)² · (C₀ + C_L)²
```

де:
- `ESR` — максимальний послідовний опір кварцу (з урахуванням зростання на морозі);
- `f₀` — частота (32 768 Гц);
- `C₀` — шунтуюча статична ємність електродів кварцу (зазвичай 1.0–1.5 пФ);
- `C_L` — номінальна навантажувальна ємність схеми.

Для надійної роботи в промисловому діапазоні температур від -40 °C до +85 °C інженерний критерій вимагає **запасу підсилення** (Gain Margin):

```
Gain_Margin = g_m / g_{m,crit} ≥ 5
```

Якщо `Gain_Margin < 3`, виникає типова аномалія «прилад зависає на морозі»: за кімнатної температури RTC стартує нормально, але на морозі -30 °C ESR кварцу зростає в півтора раза, крутизни інвертора не вистачає для подолання втрат, генератор зриває коливання, і лічильник часу мертво зупиняється.

З іншого боку, генератор не можна перезбуджувати. Потужність розсіювання на кристалі (англ. *Drive Level*, `DL`) для годинникових кварців суворо обмежена величиною **0.5–1.0 мкВт** (`DL = I_q² · ESR`). Якщо інвертор подає занадто високу амплітуду, механічна напруга розбиває тонкі ніжки камертона або викликає прискорений незворотний дрейф старіння (aging). Сучасні мікроконтролери дають змогу обирати потужність драйвера LSE програмно (наприклад, біти `RCC_BDCR_LSEDRV[1:0]` у STM32 мають 4 градації струму), що дозволяє точно збалансувати надійний пуск на морозі з безпечним рівнем збудження.

> 🔧 **Навіщо це.** Якщо бортовий прилад має локальний термодавач (наприклад, усередині самого мікроконтролера або на платі), прошивка може періодично вимірювати температуру `T` і програмно компенсувати дрейф кварцу за формулою `Δf = -0.04 · (T - 25)²`. Більшість сучасних RTC (наприклад, STM32 RTC або окремі чипи DS3231) містять апаратний регістр калібрування, куди раз на хвилину записують поправковий коефіцієнт, знижуючи річний дрейф із 10 хвилин до кількох секунд.

## Монотонний час проти настінного часу (Wall Clock): усунення небезпечних часових стрибків

У вбудованому ПЗ розрізняють два принципово різні типи годинників:

1. **Настінний час (Wall Clock / Real Time Clock):** відображає астрономічний час (UTC або локальний пояс: рік, місяць, день, година, хвилина, секунда). Його призначення — маркування подій для людини, ведення журналів, перевірка терміну придатності TLS-сертифікатів і запуск дій за розкладом.
2. **Монотонний годинник (Monotonic Clock):** неперервний лічильник фізичного часу, який стартує від моменту ввімкнення живлення пристрою (uptime). Він має сувору математичну властивість: для будь-яких двох моментів часу `t₁` та `t₂`, якщо `t₂` настав пізніше `t₁`, то значення монотонного лічильника гарантовано задовольняє умову:

```
monotonic_now(t₂) ≥ monotonic_now(t₁)
```

Монотонний годинник **ніколи не повертається назад** і не зазнає миттєвих розривів (стрибків) при коригуванні часу оператором або сервером синхронізації.

![Стрибок настінного часу проти неперервності монотонного](/root/course/embedded/hodynnyk-na-bortu/img/monotonic-vs-wall-step.svg)
*Порівняння поведінки настінного та монотонного часу під час коригування. При коригуванні назад настінний час стрибає вниз, створюючи зону з від'ємною або помилковою тривалістю `Δt`. Монотонний годинник продовжує зростати лінійно, гарантуючи коректне вимірювання інтервалів.*

### Анатомія збою при стрибку настінного часу

Розглянемо типовий фрагмент коду, де розробник припустився фатальної помилки — використав настінний годинник для перевірки таймауту очікування відповіді від радіомодема:

:::tabs
```c
// НЕПРАВИЛЬНО: використання настінного часу для таймаутів
uint32_t deadline = get_wall_time_seconds() + 5; // Таймаут 5 секунд

send_request_to_modem();

while (get_wall_time_seconds() < deadline) {
    if (check_modem_response()) {
        return STATUS_OK;
    }
    vTaskDelay(pdMS_TO_TICKS(10));
}
// Якщо час перевели назад — цикл крутитиметься не 5 секунд, а годинами!
```
```cpp
// НЕПРАВИЛЬНО: використання настінного часу для таймаутів
auto deadline = std::chrono::system_clock::now() + std::chrono::seconds(5);

send_request_to_modem();

while (std::chrono::system_clock::now() < deadline) {
    if (check_modem_response()) {
        return Status::Ok;
    }
    std::this_thread::sleep_for(std::chrono::milliseconds(10));
}
// Стрибок system_clock назад блокує потік на весь час зсуву
```
:::

Уявімо послідовність подій:
1. О 12:00:00 задача відправляє запит модему та призначає дедлайн: `deadline = 12:00:05`.
2. О 12:00:02 фонова служба NTP отримує перший пакет від сервера синхронізації та виявляє, що бортовий RTC поспішав на 10 секунд.
3. Служба синхронізації виконує миттєве переведення часу (step adjustment): годинник примусово встановлюється на `11:59:52`.
4. У наступній ітерації циклу перевірка `get_wall_time_seconds() < deadline` порівнює `11:59:52` з `12:00:05`.
5. Замість 3 секунд, що залишалися до таймауту, тривалість очікування раптово зростає до `13 секунд`. Якщо ж корекція була на 1 годину (наприклад, перехід на зимовий час чи зміна поясу), задача заблокується на **3600 секунд**.

Ще небезпечніша ситуація виникає в цифрових регуляторах зворотного зв'язку (наприклад, PID-регуляторі швидкості двигуна чи стабілізації напруги):

:::tabs
```c
// НЕПРАВИЛЬНО: обчислення dt через настінний час
void pid_update(float target, float current) {
    uint32_t now_ms = get_wall_time_ms();
    float dt = (float)(now_ms - last_time_ms) / 1000.0f;
    last_time_ms = now_ms;

    // Якщо час стрибнув назад, dt < 0 або dt == 0 (ділення на нуль!)
    float error = target - current;
    integral += error * dt;
    float derivative = (error - prev_error) / dt; // Вибух значення при dt -> 0
    prev_error = error;

    apply_actuator_output(Kp * error + Ki * integral + Kd * derivative);
}
```
```cpp
// НЕПРАВИЛЬНО: обчислення dt через настінний час
void pid_update(float target, float current) {
    auto now = std::chrono::system_clock::now();
    std::chrono::duration<float> dt_duration = now - last_time;
    last_time = now;

    float dt = dt_duration.count();
    // При коригуванні назад dt від'ємне, що інвертує знак інтегратора й похідної
    float error = target - current;
    integral += error * dt;
    float derivative = (error - prev_error) / dt;

    apply_actuator_output(Kp * error + Ki * integral + Kd * derivative);
}
```
:::

Якщо під час роботи регулятора `dt` стає від'ємним, похідна складова `Kd · derivative` миттєво змінює знак на протилежний, перетворюючи негативний зворотний зв'язок на позитивний — мотор йде в рознос на повній потужності.

### Фундаментальне правило архітектури часу

Усі часові операції у вбудованій системі підпорядковуються залізному правилу:

- **Інтервали, затримки, таймаути, вимірювання швидкості та кроки чисельного інтегрування вимірюються виключно через монотонний годинник (`CLOCK_MONOTONIC`, `std::chrono::steady_clock`, `esp_timer_get_time()`, лічильник SysTick).**
- **Настінний час обчислюється як сума монотонного часу та базового зсуву епохи:**

```
wall_time_utc = monotonic_time_us + epoch_base_offset_us
```

При такій архітектурі будь-яка зовнішня синхронізація часу змінює лише значення `epoch_base_offset_us`. Сам лічильник `monotonic_time_us` продовжує монотонно зростати без жодного мікросекундного збою, гарантуючи абсолютну стабільність усіх таймерів і процесів керування.

## Алгоритм плавного підтягування часу: Slew замість Step (Time Slew & PLL Discipline)

Навіть якщо монотонний лічильник захищений від стрибків, настінний час у журналах і подіях теж небажано переводити різкими стрибками. Якщо змістити календар назад, у файлі журналу на Flash-пам'яті з'являться записи, час яких іде у зворотному порядку, що ускладнює діагностику інцидентів або ламає індексацію бази даних часових рядів.

Існує два способи коригування бортового часу:

1. **Стрибок (Step Adjustment):** миттєвий запис нового значення в лічильник. Дозволяється **виключно під час холодного старту** приладу, коли після увімкнення бортовий час відрізняється від реального на місяці чи роки.
2. **Плавне підтягування (Time Slew):** поступова ліквідація розбіжності шляхом тимчасової зміни *темпу ходу* (частоти) годинника.

![Корекція часу: миттєвий крок проти плавного підтягування (Slew)](/root/course/embedded/hodynnyk-na-bortu/img/time-slew-vs-step.svg)
*Принцип плавного підтягування часу (Slew). Замість миттєвого стрибка на -2 секунди частота генератора тимчасово сповільнюється на 500 ppm, завдяки чому накопичена похибка фази плавно зменшується до нуля без розривів неперервності.*

### Математична модель фазового автопідстроювання (PLL / PI-регулятор)

Нехай у момент чергової синхронізації (через NTP, GPS/GNSS або LoRaWAN-сервер) виявлено похибку фази (зсув часу) `θ` між еталонним часом `t_ref` та локальним настінним часом `t_loc`:

```
θ = t_ref - t_loc
```

Якщо `|θ| > θ_threshold` (наприклад, понад 2 секунди), алгоритм виконує одноразовий крок (step). Якщо ж похибка мала (`|θ| ≤ 2.0 с`), вмикається режим плавного підтягування (slew).

Для усунення похибки частоту локального віртуального годинника коригують на відносну величину `u(t)` (виражену у відносних одиницях або ppm):

```
f_corr = f_nom · (1 + u(t))
```

Швидкість зміни фазової похибки описується диференціальним рівнянням:

```
dθ / dt = -u(t) + δf_drift
```

де `δf_drift` — власний дрейф кварцу пристрою.

Щоб система швидко ліквідувала помилку без статичного відставання, застосовують пропорційно-інтегральний (PI) регулятор темпу:

```
u(t) = K_p · θ(t) + K_i · ∫ θ(τ) dτ
```

де:
- `K_p` — пропорційний коефіцієнт (відповідає за швидкість ліквідації поточної різниці фази);
- `K_i` — інтегральний коефіцієнт (оцінює та нейтралізує постійний температурний дрейф частоти кварцу).

Керівний сигнал обов'язково обмежують жорстким порогом максимальної швидкості підтягування `U_max` (стандартна межа slew rate для NTP становить `±500 ppm`, тобто `±0.05%` від номінальної швидкості):

```
-U_max ≤ u(t) ≤ +U_max      (U_max = 500 · 10⁻⁶ = 0.5 мс/с)
```

При швидкості підтягування 500 ppm годинник виправляє похибку величиною **1.0 секунда** за:

```
t_вирівнювання = 1.0 с / (500 · 10⁻⁶)
= 2000 секунд ≈ 33.3 хвилини
```

Протягом цих 33 хвилин час продовжує безперервно і монотонно рухатися вперед, не створюючи жодного збою в системних чергах і таймерах, але при цьому кожної секунди скорочує відставання на 0.5 мілісекунди.

### Апаратне та програмне застосування корекції Slew

Застосувати коефіцієнт `u(t)` можна двома шляхами:

1. **Апаратно (через регістр плавного калібрування RTC):**
   У мікроконтролерах сімейства STM32 блок RTC містить регістр `RTC_CALR` (Smooth Digital Calibration Register). Він дозволяє додавати або маскувати імпульси базової частоти 32.768 кГц на фіксованому вікні тривалістю 32 секунди.
   
   За 32 секунди годинниковий кварц видає рівно:
   
   ```
   N_імпульсів = 32 с · 32768 Гц = 1 048 576 імпульсів
   ```
   
   Маскування (вилучення) рівно одного імпульсу за це вікно змінює ефективну частоту на:
   
   ```
   Δf_step = -1 / 1048576 ≈ -0.953674 ppm
   ```
   
   Регістр `RTC_CALR` містить два ключових поля:
   - Біт `CALP` (Calibration Positive): при `CALP = 1` схема додає 512 імпульсів на вікні 32 с (+488.28125 ppm до частоти);
   - Поле `CALM[8:0]` (Calibration Mask): маскує від 0 до 511 імпульсів (від 0 до -487.327 ppm із кроком 0.9537 ppm).

   Якщо виміряний сумарний дрейф кварцу становить, наприклад, `Δf_meas = -35.2 ppm` (годинник відстає), прошивка має додати частоту. Алгоритм розрахунку бітових полів `RTC_CALR`:
   
   ```
   // Потрібно компенсувати +35.2 ppm:
   CALP = 1                      // Додаємо +488.28 ppm
   Залишок = 488.28 - 35.2 = 453.08 ppm
   CALM = round(453.08 / 0.953674) = 475
   // Підсумкова поправка: +488.28125 - (475 · 0.953674) = +35.286 ppm (похибка менше 0.09 ppm!)
   ```

2. **Програмно (через дробовий лічильник віртуального монотонного часу):**
   Якщо апаратний RTC не має цифрового калібратора, прошивка множить сирі апаратні тіки таймера на 64-бітний фіксовано-точковий коефіцієнт темпу ходу `rate_multiplier`.

### Джерела еталонного часу: апаратний 1 PPS GNSS проти мережевого SNTP

Якість синхронізації залежить від фізичної природи джерела еталонного часу:

- **Мережевий SNTP (через Wi-Fi, Ethernet або LTE):**
  Клієнт відправляє UDP-датаграму на NTP-сервер і фіксує 4 мітки часу (`T₁` — відправка запиту, `T₂` — прийом сервером, `T₃` — відправка відповіді, `T₄` — прийом клієнтом). Зсув часу розраховується як `θ = ((T₂ - T₁) + (T₃ - T₄)) / 2`.
  Ця формула припускає, що затримка передачі пакета туди й назад є строго симетричною. Однак у стільникових мережах LTE/NB-IoT або завантаженому Wi-Fi буферизація в чергах маршрутизаторів створює асиметрію від 10 до 150 мс. Одноразовий замір SNTP дає значний шум, тому поправку не можна застосовувати миттєвим кроком — її обов'язково фільтрують у петлі PI-PLL.

- **Апаратний сигнал 1 PPS від супутникового приймача (GPS/Galileo/GNSS):**
  Супутниковий модуль видає дискретний логічний імпульс (1 PPS), передній фронт якого синхронізований зі шкалою UTC з точністю до 10–30 наносекунд. Цей сигнал заводять на вивід входу захоплення таймера мікроконтролера (Timer Input Capture). Апаратний таймер миттєво зберігає значення свого лічильника в регістрі захоплення без затримок на виконання коду ядра чи обробку переривань. Це дає змогу виміряти реальну частоту бортового кварцу з роздільною здатністю в частки ppm за один вимірювальний інтервал.

## Апаратне резервування живлення RTC та збереження часу при відключенні основного акумулятора

Більшість автономних пристроїв періодично втрачають основне живлення: користувач замінює розряджений головний акумулятор, на щитку вимикають напругу мережі 220 В, або плата перебуває на складі перед інсталяцією. Якщо RTC скинеться в нуль (01.01.1970 або 01.01.2000), пристрій втратить можливість співвідносити події до першого сеансу зв'язку з сервером.

### Архітектура доменів живлення мікроконтролера

Сучасні мікроконтролери (STM32, NXP LPC, ESP32-S3 тощо) фізично розділяють кристал на два незалежні домени живлення:

1. **Головний домен (Main VDD Domain):** живить ядра CPU, високошвидкісну Flash/SRAM пам'ять, шини DMA та периферію. При знеструмленні вся інформація в ньому втрачається.
2. **Резервний домен (Backup Domain / Always-On Domain, AON):** живиться від окремого виводу `VBAT` мікроконтролера. Цей домен містить лише:
   - Схему генератора LSE (Low Speed External) 32.768 кГц;
   - Лічильники секунд, субсекунд і календар RTC;
   - Енергонезалежні регістри збереження стану (Backup Registers / Backup SRAM розміром від 32 байт до кількох кілобайт);
   - Схему детектора падіння напруги резервного живлення (Power-On Reset / Tamper detection).

Струм споживання резервного домену в режимі живлення від `VBAT` є надзвичайно малим і становить усього **300–800 нА** за кімнатної температури.

![Розділення доменів живлення мікроконтролера та живлення RTC](/root/course/embedded/hodynnyk-na-bortu/img/rtc-power-domains.svg)
*Схема внутрішнього перемикача живлення RTC. Коли напруга VDD перевищує поріг перемикання (зазвичай 2.0 В), схема живиться від VDD, не витрачаючи енергію батареї. При знеструмленні головної шини домен RTC миттєво перемикається на вхід VBAT.*

### Джерела резервного живлення: літієва батарейка проти іоністора

Для резервування виводу `VBAT` застосовують два типи накопичувачів:

| Параметр | Літієва таблетка (CR2032) | Іоністор (Supercapacitor / EDLC) |
| :--- | :--- | :--- |
| **Номінальна ємність** | 220 мА·год (792 Кл) | 0.22 ... 1.5 Ф (при 3.3 В: ~0.7 ... 5 Кл) |
| **Термін служби** | 5–10 років (обмежений саморозрядом) | > 15–20 років (> 500 000 циклів заряду) |
| **Необхідність заміни** | Потребує заміни після вичерпання | Не потребує обслуговування |
| **Час автономного ходу RTC** | 10–25 років (теоретично) | Від 5 діб до 4 тижнів |
| **Діапазон температур** | -30 °C ... +60 °C (ємність падає на морозі) | -40 °C ... +85 °C |
| **Екологічність та герметичність** | Вимагає батарейного відсіку або паяння | Паяється на плату (SMD), герметичний корпус |

#### Розрахунок часу утримання часу іоністором

Іоністор є ідеальним вибором для приладів, які штатно живляться від мережі або сонячної панелі, але мають витримувати блекаути тривалістю від кількох днів до місяця.

Обчислимо час, протягом якого іоністор ємністю `C = 0.47 Ф` зможе підтримувати роботу RTC мікроконтролера.

Нехай:
- Початкова напруга заряду іоністора: `V_max = 3.3 В`;
- Мінімальна робоча напруга домену RTC ( retention voltage `V_min`): `1.8 В`;
- Струм споживання RTC разом зі струмом витоку конденсатора: `I_RTC = 600 нА = 600 · 10⁻⁹ А`.

Час розряду обчислюється за формулою ємності:

```
Q = C · ΔV = I · t
```

Звідки тривалість збереження ходу часу:

```
t_backup
= (C · (V_max - V_min)) / I_RTC           [формула розряду ємності постійним струмом]
= (0.47 · (3.3 - 1.8)) / (600 · 10⁻⁹)     [підстановка C = 0.47 Ф, V_max = 3.3 В, V_min = 1.8 В, I = 600 нА]
= (0.47 · 1.5) / (600 · 10⁻⁹)             [обчислення робочого перепаду напруги ΔV = 1.5 В]
= 0.705 / (600 · 10⁻⁹)                    [добуток корисного заряду Q = 0.705 Кл]
= 1 175 000 с ≈ 13.6 доби                 [ділення та переведення секунд у доби]
```

Тобто іоністор розміром із копійчану монету забезпечує майже **два тижні** безперервного точного відліку часу при повному знеструмленні приладу.

### Схема ввімкнення та захист від падіння напруги

Якщо мікроконтролер не має вбудованого автоматичного перемикача живлення для виводу `VBAT`, застосовують схему об'єднання на двох діодах Шотткі з низьким зворотним витоком (наприклад, здвоєний діод BAT54C або BAS70-04).

```
Головне живлення VDD (3.3V) ---->|----+
                               (D1)   |
                                      +----> Вхід живлення RTC (V_RTC)
                                      |
Батарея VBAT (3.0V / CR2032) -->|----+
                               (D2)
```

При виборі діодів для мікроспоживаючих ланцюгів звертають увагу на **зворотний струм витоку** (reverse leakage current `I_R`). За високої температури (+85 °C) звичайний діод Шотткі може мати зворотний витік до 10–50 мкА, що швидко розрядить резервну батарейку навіть за наявності основного живлення. Для надійних промислових схем обирають діоди з наднизьким витоком або спеціалізовані мікросхеми ідеальних діодів (наприклад, TPS2113 або LTC4412).

## Повний драйвер монотонного часу та синхронізації RTC на C та C++

Об'єднаємо розглянуті принципи в архітектуру повнофункціонального виробничого драйвера бортового часу.

Драйвер забезпечує:
1. **64-бітний монотонний мікросекундний таймер:** розширює стандартний 32-бітний апаратний лічильник (що переповнюється кожні 71.5 хвилини) до 64 біт без ризику переповнення протягом 584 000 років.
2. **Абсолютний настінний час UTC:** обчислюється як сума монотонного часу та каліброваного зміщення епохи.
3. **Двошвидкісну синхронізацію:** підтримку миттєвого кроку (step) для холодного старту та плавного PI-регульованого підтягування (slew) зі швидкістю не більше `±500 ppm` для робочого режиму.
4. **Потокобезпечність і безпеку в перериваннях:** атомарне читання 64-бітних значень за допомогою механізму Sequence Lock (Seqlock).

### Безпека 64-бітного читання: пастка розірваного читання (Torn Read) та Seqlock

Більшість мікроконтролерів (ARM Cortex-M0+/M3/M4/M7, RISC-V RV32, ESP32 Xtensa) мають 32-бітну архітектуру. Це означає, що 64-бітне число (`uint64_t` або `int64_t`) фізично зберігається у двох окремих 32-бітних регістрах або комірках пам'яті (молодше слово `low` та старше слово `high`). Процесор не здатний прочитати або записати 64 біти за одну неподільну машинну інструкцію.

Якщо фонова задача або обробник переривання (ISR) оновлює час якраз у мить, коли інший потік зчитує 64-бітне значення, виникає катастрофічна ситуація **розірваного читання** (англ. *torn read*):

1. Нехай поточний час становить `0x00000000_FFFFFFFF` мкс (мить перед переповненням молодших 32 біт).
2. Потік читача встигає прочитати молодше слово: `low = 0xFFFFFFFF`.
3. У цей момент виникає переривання таймера, яке додає 1 мкс: значення в пам'яті стає `0x00000001_00000000`.
4. Переривання завершується, читач повертається до виконання й зчитує старше слово: `high = 0x00000001`.
5. Читач склеює результат: `(0x00000001 << 32) | 0xFFFFFFFF = 0x00000001_FFFFFFFF` (8 589 934 591 мкс).

Замість істинного часу `4 294 967 296` мкс (71.5 хвилини) потік отримав значення `8 589 934 591` мкс (143 хвилини) — час миттєво стрибнув у майбутнє на **71.5 хвилини**!

Захищати читання часу класичним м'ютексом ОСРЧ не можна: по-перше, системний годинник запитують десятки тисяч разів на секунду (накладні витрати на блокування неприпустимі); по-друге, м'ютекси не можна захоплювати всередині обробників апаратних переривань (ISR).

Ідеальним рішенням є патерн **Seqlock** (Sequence Lock, запозичений із ядра Linux):
- Структура часу супроводжується цілочисельним лічильником версії `sequence`.
- Перед зміною структури письменник інкрементує `sequence` на 1 (роблячи його **непарним**).
- Після завершення запису письменник знову інкрементує `sequence` на 1 (роблячи його **парним**).
- Читач зчитує `sequence` до початку читання даних і після нього. Якщо початковий `sequence` був непарним (тривав запис) або якщо кінцевий `sequence` не збігається з початковим (посеред читання відбулося оновлення), читач просто повторює цикл читання.

У 99.999% випадків читач проходить цикл з першої спроби за лічені такти ядра, без жодного блокування шини та в повній безпеці від розірваного читання.

*Архітектура драйвера часу. Апаратні лічильники надходять у ядро, де накопичується 64-бітний монотонний час. Модуль Slew контролює частотну підгонку, а суматор зсуву епохи формує безпечний настінний час UTC.*

```c
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

#define TIME_SLEW_MAX_PPM        500     // Максимальний зсув частоти slew (+-500 ppm = +-0.05%)
#define TIME_STEP_THRESHOLD_US   2000000 // Поріг 2 секунди: більше -> step, менше -> slew
#define PPM_SCALE                1000000

typedef struct {
    // Атомарна версія для блокування читання без блокувань (Seqlock)
    volatile uint32_t sequence;

    // Стан апаратного монотонного лічильника
    uint32_t last_hw_ticks;
    uint64_t monotonic_accum_us;

    // Зсув настінного часу відносно монотонного (UTC epoch)
    int64_t epoch_offset_us;

    // Стан плавного підтягування (Slew)
    int64_t  slew_remaining_us;    // Залишок похибки, яку треба плавно вибрати
    int32_t  slew_rate_ppm;        // Поточна швидкість підтягування (+-500 ppm)
    uint64_t last_slew_update_us;  // Час останнього перерахунку slew

    // Коефіцієнти калібрування дрейфу кварцу
    int32_t  static_drift_ppm;
} system_time_engine_t;

static system_time_engine_t g_time_engine;

// Зовнішня функція апаратного таймера (наприклад, SysTick або TIMx 1 МГц)
extern uint32_t hw_timer_get_32bit_ticks(void);

void time_engine_init(int64_t initial_utc_us, int32_t quartz_drift_ppm) {
    g_time_engine.sequence = 0;
    g_time_engine.last_hw_ticks = hw_timer_get_32bit_ticks();
    g_time_engine.monotonic_accum_us = 0;
    g_time_engine.epoch_offset_us = initial_utc_us;
    g_time_engine.slew_remaining_us = 0;
    g_time_engine.slew_rate_ppm = 0;
    g_time_engine.last_slew_update_us = 0;
    g_time_engine.static_drift_ppm = quartz_drift_ppm;
}

// Оновлення накопичувача (викликається періодично або перед читанням)
static void time_engine_update_internal(void) {
    uint32_t current_ticks = hw_timer_get_32bit_ticks();
    uint32_t delta_ticks = current_ticks - g_time_engine.last_hw_ticks;
    g_time_engine.last_hw_ticks = current_ticks;

    // Додаємо дельту до монотонного лічильника
    g_time_engine.monotonic_accum_us += (uint64_t)delta_ticks;
    uint64_t now_mono = g_time_engine.monotonic_accum_us;

    // Обробка плавного підтягування (Slew)
    if (g_time_engine.slew_remaining_us != 0) {
        uint64_t dt = now_mono - g_time_engine.last_slew_update_us;
        if (dt > 0) {
            // Скільки мікросекунд коригування набігло за проміжок dt
            int64_t delta_slew = ((int64_t)dt * g_time_engine.slew_rate_ppm) / PPM_SCALE;

            // Перевірка на досягнення цілі
            if ((g_time_engine.slew_remaining_us > 0 && delta_slew >= g_time_engine.slew_remaining_us) ||
                (g_time_engine.slew_remaining_us < 0 && delta_slew <= g_time_engine.slew_remaining_us)) {
                g_time_engine.epoch_offset_us += g_time_engine.slew_remaining_us;
                g_time_engine.slew_remaining_us = 0;
                g_time_engine.slew_rate_ppm = 0;
            } else {
                g_time_engine.epoch_offset_us += delta_slew;
                g_time_engine.slew_remaining_us -= delta_slew;
            }
            g_time_engine.last_slew_update_us = now_mono;
        }
    }
}

// Отримання строго монотонного часу (ніколи не йде назад)
uint64_t time_get_monotonic_us(void) {
    uint32_t seq;
    uint64_t mono;

    do {
        seq = g_time_engine.sequence;
        // Seqlock: непарне число означає, що триває оновлення структури
        while (seq & 1) {
            seq = g_time_engine.sequence;
        }
        
        // Враховуємо поточний стан лічильника
        uint32_t current_ticks = hw_timer_get_32bit_ticks();
        uint32_t delta = current_ticks - g_time_engine.last_hw_ticks;
        mono = g_time_engine.monotonic_accum_us + delta;

    } while (g_time_engine.sequence != seq);

    return mono;
}

// Отримання настінного часу UTC
int64_t time_get_wall_clock_utc_us(void) {
    uint32_t seq;
    int64_t wall;

    do {
        seq = g_time_engine.sequence;
        while (seq & 1) {
            seq = g_time_engine.sequence;
        }
        
        uint64_t mono = time_get_monotonic_us();
        wall = (int64_t)mono + g_time_engine.epoch_offset_us;

    } while (g_time_engine.sequence != seq);

    return wall;
}

// Синхронізація часу від сервера (NTP / GPS)
void time_sync_adjust(int64_t target_utc_us) {
    // Вхід у критичну секцію Seqlock
    g_time_engine.sequence++;
    __asm__ volatile("" ::: "memory"); // Бар'єр пам'яті

    time_engine_update_internal();

    int64_t current_utc = (int64_t)g_time_engine.monotonic_accum_us + g_time_engine.epoch_offset_us;
    int64_t phase_error = target_utc_us - current_utc;

    // Якщо похибка величезна — робимо миттєвий крок (Step)
    if (phase_error > TIME_STEP_THRESHOLD_US || phase_error < -TIME_STEP_THRESHOLD_US) {
        g_time_engine.epoch_offset_us += phase_error;
        g_time_engine.slew_remaining_us = 0;
        g_time_engine.slew_rate_ppm = 0;
    } else {
        // Плавне підтягування (Slew): обмежуємо темп +-500 ppm
        g_time_engine.slew_remaining_us = phase_error;
        g_time_engine.slew_rate_ppm = (phase_error > 0) ? TIME_SLEW_MAX_PPM : -TIME_SLEW_MAX_PPM;
        g_time_engine.last_slew_update_us = g_time_engine.monotonic_accum_us;
    }

    __asm__ volatile("" ::: "memory");
    g_time_engine.sequence++; // Завершення критичної секції (число знову парне)
}

```cpp
#include <chrono>
#include <atomic>
#include <cstdint>
#include <algorithm>

class TimeEngine {
public:
    using Microseconds = std::chrono::microseconds;
    using TimePointUtc = std::chrono::time_point<std::chrono::system_clock, Microseconds>;
    using TimePointMono = std::chrono::time_point<std::chrono::steady_clock, Microseconds>;

    static constexpr int32_t MaxSlewPpm = 500;
    static constexpr Microseconds StepThreshold = std::chrono::seconds(2);
    static constexpr int64_t PpmScale = 1'000'000;

    explicit TimeEngine(Microseconds initial_utc, int32_t quartz_drift_ppm = 0) noexcept
        : sequence_(0),
          last_hw_ticks_(read_hw_ticks()),
          monotonic_accum_us_(0),
          epoch_offset_us_(initial_utc.count()),
          slew_remaining_us_(0),
          slew_rate_ppm_(0),
          last_slew_update_us_(0),
          static_drift_ppm_(quartz_drift_ppm) {}

    // Отримання неперервного монотонного часу для вимірювань і дедлайнів
    [[nodiscard]] TimePointMono get_monotonic_time() const noexcept {
        uint32_t seq;
        uint64_t mono_us;
        do {
            seq = sequence_.load(std::memory_order_acquire);
            while (seq & 1) {
                seq = sequence_.load(std::memory_order_acquire);
            }

            uint32_t current_ticks = read_hw_ticks();
            uint32_t delta = current_ticks - last_hw_ticks_;
            mono_us = monotonic_accum_us_ + delta;

        } while (sequence_.load(std::memory_order_relaxed) != seq);

        return TimePointMono(Microseconds(mono_us));
    }

    // Отримання настінного часу (календар UTC)
    [[nodiscard]] TimePointUtc get_wall_clock_utc() const noexcept {
        uint32_t seq;
        int64_t wall_us;
        do {
            seq = sequence_.load(std::memory_order_acquire);
            while (seq & 1) {
                seq = sequence_.load(std::memory_order_acquire);
            }

            auto mono = get_monotonic_time();
            wall_us = mono.time_since_epoch().count() + epoch_offset_us_;

        } while (sequence_.load(std::memory_order_relaxed) != seq);

        return TimePointUtc(Microseconds(wall_us));
    }

    // Синхронізація від джерела еталонного часу (NTP/GNSS)
    void sync_time(TimePointUtc target_utc) noexcept {
        uint32_t seq = sequence_.load(std::memory_order_relaxed);
        sequence_.store(seq + 1, std::memory_order_release);

        update_internal();

        int64_t target_us = target_utc.time_since_epoch().count();
        int64_t current_utc_us = monotonic_accum_us_ + epoch_offset_us_;
        int64_t phase_error = target_us - current_utc_us;

        if (std::abs(phase_error) > StepThreshold.count()) {
            // Велике відхилення: стрибок (step)
            epoch_offset_us_ += phase_error;
            slew_remaining_us_ = 0;
            slew_rate_ppm_ = 0;
        } else {
            // Мале відхилення: плавне підтягування (slew)
            slew_remaining_us_ = phase_error;
            slew_rate_ppm_ = (phase_error > 0) ? MaxSlewPpm : -MaxSlewPpm;
            last_slew_update_us_ = monotonic_accum_us_;
        }

        sequence_.store(seq + 2, std::memory_order_release);
    }

private:
    static uint32_t read_hw_ticks() noexcept {
        extern uint32_t hw_timer_get_32bit_ticks(void);
        return hw_timer_get_32bit_ticks();
    }

    void update_internal() noexcept {
        uint32_t current_ticks = read_hw_ticks();
        uint32_t delta = current_ticks - last_hw_ticks_;
        last_hw_ticks_ = current_ticks;

        monotonic_accum_us_ += delta;
        uint64_t now_mono = monotonic_accum_us_;

        if (slew_remaining_us_ != 0) {
            uint64_t dt = now_mono - last_slew_update_us_;
            if (dt > 0) {
                int64_t delta_slew = (static_cast<int64_t>(dt) * slew_rate_ppm_) / PpmScale;

                if ((slew_remaining_us_ > 0 && delta_slew >= slew_remaining_us_) ||
                    (slew_remaining_us_ < 0 && delta_slew <= slew_remaining_us_)) {
                    epoch_offset_us_ += slew_remaining_us_;
                    slew_remaining_us_ = 0;
                    slew_rate_ppm_ = 0;
                } else {
                    epoch_offset_us_ += delta_slew;
                    slew_remaining_us_ -= delta_slew;
                }
                last_slew_update_us_ = now_mono;
            }
        }
    }

    mutable std::atomic<uint32_t> sequence_;
    uint32_t last_hw_ticks_;
    uint64_t monotonic_accum_us_;
    int64_t  epoch_offset_us_;
    int64_t  slew_remaining_us_;
    int32_t  slew_rate_ppm_;
    uint64_t last_slew_update_us_;
    int32_t  static_drift_ppm_;
};

Їх можна безпечно викликати як із будь-якої задачі FreeRTOS/Zephyr, так і безпосередньо зсередини обробників високопріоритетних переривань (ISR).

## Підсумок інженерних рішень

Побудова стабільного бортового часу в автономному мікроконтролері спирається на чотири обов'язкові правила:

1. **Фізика кварцу:** камертонний кварц 32.768 кГц має параболічний температурний коефіцієнт `-0.04 ppm/°C²` і за будь-якого відхилення від +25 °C сповільнює свій хід (до -7 с/добу при -20 °C). Для точності потрібна термокомпенсація через апаратний регістр калібрування.
2. **Розділення годинників:** монотонний лічильник вимірює інтервали, затримки й таймаути і ніколи не переводиться назад. Настінний час обчислюється додаванням зсуву епохи і служить виключно для календаря й логів.
3. **Корекція Slew:** робоча синхронізація від NTP чи GPS повинна підтягувати час плавною зміною частоти (до ±500 ppm), уникаючи розривів неперервності.
4. **Резервування живлення:** домен RTC живиться від виводу `VBAT` зі споживанням < 800 нА. Іоністор ємністю 0.47 Ф забезпечує автономний хід годинника протягом 2 тижнів без необхідності заміни батарейки протягом усього життєвого циклу виробу.
