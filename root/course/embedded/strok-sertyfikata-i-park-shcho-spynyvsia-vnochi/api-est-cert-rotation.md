# 📋 Протокол ротації сертифікатів EST (RFC 7030) для вбудованих систем

Стандарт **EST** (англ. *Enrollment over Secure Transport*, «реєстрація через захищений транспорт», RFC 7030) визначає легкий криптографічний протокол керування повним життєвим циклом сертифікатів X.509 поверх стандартного захищеного з'єднання HTTPS/TLS. На відміну від складних і ресурсомістких протоколів CMP (RFC 4210) та застарілого SCEP, протокол EST спроєктовано спеціально для автоматизованого використання у вбудованих пристроях, промислових шлюзах та автономних вузлах Інтернету речей (IoT), де обчислювальні ресурси мікроконтролера та обсяг Flash-пам'яті суворо обмежені.

Протокол базується на повторному використанні наявних криптографічних примітивів: транспортний рівень TLS забезпечує конфіденційність, цілісність та автентифікацію сторін, а прикладний рівень передає структуровані запити PKCS#10 та відповіді PKCS#7 через звичайні виклики HTTP REST.

---

### Специфікація точок доступу (REST Endpoints)

Усі операції протоколу EST виконуються через строго стандартизовані відносні шляхи з єдиним кореневим префіксом `/.well-known/est/`. За замовчуванням запити спрямовуються на стандартний TCP-порт HTTPS `443` або на виділений порт інфраструктури відкритих ключів (PKI) `8443`.

| Точка доступу | HTTP Метод | Вхідний MIME-тип | Вихідний MIME-тип | Обов'язковість | Призначення операції |
|---|---|---|---|---|---|
| `/.well-known/est/cacerts` | `GET` | Порожньо | `application/pkcs7-mime; smime-type=certs-only` | Обов'язкова | Отримання повного актуального ланцюга кореневих (Root CA) та проміжних сертифікатів |
| `/.well-known/est/simplereenroll` | `POST` | `application/pkcs10` | `application/pkcs7-mime; smime-type=certs-only` | Обов'язкова | Планова ротація сертифіката пристрою з автентифікацією за чинним mTLS-з'єднанням |
| `/.well-known/est/simpleenroll` | `POST` | `application/pkcs10` | `application/pkcs7-mime; smime-type=certs-only` | Обов'язкова | Первинна реєстрація нового пристрою за заводським сертифікатом IDevID або одноразовим паролем |
| `/.well-known/est/serverkeygen` | `POST` | `application/pkcs10` | `multipart/mixed` | Опціональна | Випуск сертифіката з генерацією закритого ключа на стороні сервера (для чипів без апаратного TRNG) |
| `/.well-known/est/csrattrs` | `GET` | Порожньо | `application/csrattrs` | Рекомендована | Запит криптографічних вимог сервера до структури CSR (дозволені еліптичні криві, поля OID) |

### Детальна структура протокольних повідомлень

#### 1. Синхронізація кореневих довірчих якорів (`/cacerts`)
Операція дозволяє мікроконтролеру перевірити наявність нових центрів сертифікації та завантажити оновлений ланцюг CA перед початком генерації власних ключів.
- **Запит клієнта:**
  ```http
  GET /.well-known/est/cacerts HTTP/1.1
  Host: pki.device.cloud.local
  Accept: application/pkcs7-mime
  User-Agent: EmbeddedEST/2.1 (STM32H7; FreeRTOS)
  Connection: close
  ```
- **Відповідь сервера:**
  ```http
  HTTP/1.1 200 OK
  Content-Type: application/pkcs7-mime; smime-type=certs-only
  Content-Transfer-Encoding: base64
  Content-Length: 2840

  MIIHYwYJKoZIhvcNAQcCoIIHVDCCB1ACAQExADALBgkqhkiG9w0BAQswggS3Bgkq...
  ```
  Тіло відповіді містить структуру PKCS#7 `SignedData` без цифрового підпису (`certs-only`), усередині якої упаковано сертифікати Root CA та Intermediate CA у двійковому форматі ASN.1 DER, закодовані у Base64. Мікроконтролер парсить цю структуру та зберігає нові сертифікати у резервний слот Flash-пам'яті `Slot B`.

#### 2. Запит атрибутів та вимог сертифікації (`/csrattrs`)
Перед створенням запиту на підпис пристрій може звернутися до ендпойнта `/.well-known/est/csrattrs`, щоб отримати список обов'язкових об'єктних ідентифікаторів (OID), які центр сертифікації вимагає включити у запит CSR:
- Дозволені криптографічні набори (наприклад, обов'язкове використання еліптичної кривої ECDSA SECP256R1 або Ed25519);
- Обов'язкові розширення (поля `Subject Alternative Name` з ідентифікатором пристрою, прапорці `Extended Key Usage` для `clientAuth`);
- Специфічні службові атрибути підприємства (ідентифікатор партії, версія апаратної ревізії плати).

#### 3. Планова ротація сертифіката пристрою (`/simplereenroll`)
Клієнт ініціює запит у межах поточної сесії TLS, що вже автентифікована чинним сертифікатом пристрою (mTLS).
- **Запит клієнта:**
  ```http
  POST /.well-known/est/simplereenroll HTTP/1.1
  Host: pki.device.cloud.local
  Content-Type: application/pkcs10
  Content-Transfer-Encoding: base64
  Content-Length: 1024

  MIICvDCCAaQCAQAwdzELMAkGA1UEBhMCVUExDzANBgNVBAgMBkt5aXZzczEOMAwG...
  ```
  Тіло містить запит на підпис сертифіката PKCS#10 (CSR, RFC 2986). Пристрій самостійно генерує новий закритий ключ у захищеному криптографічному чипі або Flash, формує відкритий ключ, додає свій ідентифікатор (серійний номер чи MAC-адресу) та підписує весь CSR новим закритим ключем. Це гарантує серверу доказ володіння ключем (англ. *Proof-of-Possession*).
- **Відповідь сервера при успіху:**
  ```http
  HTTP/1.1 200 OK
  Content-Type: application/pkcs7-mime; smime-type=certs-only
  Content-Transfer-Encoding: base64
  Content-Length: 1420

  MIIE6wYJKoZIhvcNAQcCoIIE3DCCBNgCAQExADALBgkqhkiG9w0BAQswggTIBgkq...
  ```

### Скінченний автомат клієнта EST (State Machine)

Вбудований клієнт EST функціонує як детермінований скінченний автомат із захистом від раптового зникнення живлення:

```
[СТАН: IDLE]
       │
       │ (Таймер системного часу сягнув 70% строку дії сертифіката)
       ▼
[СТАН: CACERTS_SYNC] ────────────(Помилка мережі)──────────► [СТАН: BACKOFF_RETRY]
       │                                                               ▲
       │ (Ланцюг CA успішно верифіковано та збережено)                 │
       ▼                                                               │
[СТАН: KEY_PAIR_GEN] ────────────(Збій генератора TRNG)────────────────┤
       │                                                               │
       │ (Новий ключ згенеровано в захищеній пам'яті Slot B)           │
       ▼                                                               │
[СТАН: CSR_GEN_AND_POST] ────────(HTTP 4xx / 5xx / Відмова TLS)────────┤
       │                                                               │
       │ (HTTP 200 OK: отримано новий сертифікат PKCS#7)               │
       ▼                                                               │
[СТАН: VALIDATE_CERT] ───────────(Помилка ланцюга чи ключа)────────────┘
       │
       │ (Криптографічна валідація успішна)
       ▼
[СТАН: ATOMIC_COMMIT] ──► (Slot Swap: Slot B -> ACTIVE) ──► [СТАН: IDLE]
```

#### Опис фаз автомата:
1. `IDLE` (Очікування): пристрій виконує прикладний код, вимірює фізичні величини та порівнює поточний час із порогом `T_renew = notBefore + 0.7 · (notAfter - notBefore)`.
2. `CACERTS_SYNC` (Синхронізація CA): завантаження та перевірка актуальності кореневих сертифікатів із `/cacerts`.
3. `KEY_PAIR_GEN` (Генерація пари): створення нового закритого та відкритого ключів безпосередньо в апаратному модулі безпеки (Secure Element) або виділеній захищеній зоні пам'яті.
4. `CSR_GEN_AND_POST` (Формування та відправка): створення PKCS#10 CSR і надсилання запиту `/simplereenroll` через mTLS.
5. `VALIDATE_CERT` (Верифікація): мікроконтролер перевіряє, що відкритий ключ у повернутому сертифікаті точно збігається з новим згенерованим ключем, а ланцюг підписів сходиться до одного з локальних довірчих якорів.
6. `ATOMIC_COMMIT` (Атомарна фіксація): модифікація бітового прапорця стану слота у Flash-пам'яті (Slot B переводиться в стан `ACTIVE`, старий Slot A стає `STANDBY`).
7. `BACKOFF_RETRY` (Відступ при збоях): перехід у режим очікування з експоненційним зростанням інтервалу.

### Матриця кодів помилок та регламент відновлення

| Код HTTP | Стан операції | Причина виникнення | Алгоритм дій мікроконтролера |
|---|---|---|---|
| `200 OK` | Успіх | Сертифікат випущено | Зберегти в Flash, провести валідацію, активувати новий слот |
| `202 Accepted` | Відкладено | Центр сертифікації обробляє чергу або очікує підтвердження | Зчитати заголовок `Retry-After: <секунди>` і повторити запит через вказаний інтервал |
| `400 Bad Request` | Фатальна помилка | Непідтримуваний формат CSR або невідомий алгоритм підпису | Звернутися до `/csrattrs`, скоригувати параметри генерації CSR |
| `401 Unauthorized` | Відмова доступу | Поточний клієнтський сертифікат відкликано або прострочено | Перервати штатну ротацію, перейти до аварійного відновлення через заводський IDevID |
| `403 Forbidden` | Заборона | Пристрій заблоковано в системі диспетчеризації | Зафіксувати код помилки в журналі аварій, вимкнути радіомодем на фіксований час |
| `503 Service Unavailable` | Тимчасовий збій | Перевантаження сервера або технічні роботи | Виконати експоненційний відступ з джиттером: `T_delay = min(86400, 2^attempt · 60) ± rand(30)` |

### Потоковий парсинг PKCS#7 на мікроконтролерах

Вбудовані системи з обмеженим обсягом оперативної пам'яті (SRAM 32–128 КБ) не можуть дозволити собі виділення великих динамічних буферів для завантаження повного ASN.1 дерева PKCS#7 структури, яка у форматі Base64 може займати 3–6 кілобайтів.

Для мінімізації накладних витрат застосовується потоковий розбір ASN.1 TLV (англ. *Tag-Length-Value*):
1. **Декодування Base64 «на льоту»:** байти з сокета TCP передаються безпосередньо через потоковий декодер Base64 у кільцевий буфер розміром 256 байтів.
2. **Фільтрація за тегом ASN.1:** парсер пропускає зовнішні обгортки `ContentInfo` та `SignedData` (теги `0x30`), відшукуючи внутрішній блок сертифікатів з контекстним тегом `[0]` (`0xA0`).
3. **Прямий запис у Flash:** кожен знайдений внутрішній сертифікат X.509 (послідовність `SEQUENCE` з тегом `0x30`) записується блоками по 64 байти безпосередньо у відповідний сектор Flash-пам'яті, минаючи динамічну пам'ять heap.

### Інваріанти збереження та захист від збою живлення

Для гарантування надійності енергонезалежного сховища довіри прошивка забезпечує виконання наступних обов'язкових інваріантів:
- **Незмінність активного слота до повного успіху:** старий робочий сертифікат у Slot A не стирається і не перезаписується, поки новий сертифікат у Slot B не пройде повну перевірку цілісності (CRC32/SHA-256) та пробне встановлення тестового TLS-з'єднання.
- **Атомарність зміни стану:** статус слота змінюється записом одного 32-бітного слова у спеціальний сектор керування Flash-пам'яті, що виключає появу проміжних невизначених станів при раптовому вимкненні живлення.
- **Резервування за замовчуванням:** якщо після перезавантаження мікроконтролер виявляє пошкодження активного слота, завантажувач автоматично відкочується до резервного слота (Slot A) або активує заводський аварійний профіль зв'язку на базі IDevID.
