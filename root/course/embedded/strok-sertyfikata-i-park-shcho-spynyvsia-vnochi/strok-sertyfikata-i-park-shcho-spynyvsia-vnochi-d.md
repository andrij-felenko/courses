О третій годині ночі в муніципальній енергомережі зупиняється збір показників із п'ятдесяти тисяч розумних лічильників електроенергії. Прилади залишаються під напругою, вимірювальні трансформатори струму справно рахують кіловат-години, а стільникові модеми NB-IoT успішно реєструються на базових станціях мобільного оператора. Проте жоден пакет телеметрії не доходить до хмарного диспетчерського центру, а сервери оновлення прошивки сигналізують про повну відсутність з'єднань. Інженери намагаються надіслати терміновий пакет конфігурації через бездротовий канал оновлення по повітрю (OTA, англ. *Over-the-Air*), але шлюзи безпеки миттєво відхиляють кожне підключення. Причина аварії — не обрив кабелю, не збій живлення і не хакерська атака, а настання дати `notAfter` у полі терміну дії кореневого сертифіката X.509, зашитого у Flash-пам'ять пристроїв п'ять років тому під час заводського програмування.

Вбудовані системи не мають користувача, який міг би натиснути кнопку «Продовжити попри попередження» у браузері або встановити новий кореневий сертифікат через графічний інтерфейс операційної системи. Якщо закінчується термін дії сертифіката сервера або клієнтського ключа самого приладу, захищений канал TLS блокується на рівні криптографічного рукостискання. Оскільки канал дистанційного оновлення прошивки сам працює поверх цього ж заблокованого TLS-з'єднання, весь парк пристроїв потрапляє в стан повної ізоляції (англ. *bricked fleet*). Фізичний виїзд сервісних бригад із діагностичними кабелями для ручного перепрошивання десятків тисяч лічильників у зачинених трансформаторних підстанціях коштує мільйони доларів і триває місяцями.

Розберімо фізику та криптографічні механізми закінчення строку дії цифрових сертифікатів у вбудованому світі: від алгоритмів перевірки ланцюгів довіри X.509 та парадоксів синхронізації часу годинників реального часу (RTC) до архітектури дводжерельних сховищ довіри, протоколів автоматичної ротації EST/ACME та ешелонованих драбин аварійного відновлення.

### Асиметрія строків і анатомія сертифіката X.509

Цифровий сертифікат стандарту **X.509** (англ. *public key certificate*) є структурою даних у двійковому форматі ASN.1 DER (англ. *Distinguished Encoding Rules*), яка криптографічно пов'язує відкритий ключ пристрою або сервера з його ідентифікатором за допомогою цифрового підпису довіреного центру сертифікації (CA, англ. *Certificate Authority*, від латинського *certus* — «певний, вірний» та *facere* — «робити»). Правила DER вимагають однозначного канонічного двійкового кодування кожного поля, що гарантує: один і той самий сертифікат завжди породжує ідентичний масив байтів, а отже, його криптографічний хеш і цифровий підпис залишаються стабільними.

Кожен сертифікат X.509 містить обов'язковий блок часової валідності `Validity`, що складається з двох часових міток:
- `notBefore` — дата й час у форматі UTC, до настання яких сертифікат вважається недійсним;
- `notAfter` — дата й час у форматі UTC, після перетину яких сертифікат вважається простроченим.

Для дат до 2050 року ці поля кодуються у форматі `UTCTime` (формат `YYMMDDhhmmssZ`, де фіксуються дві останні цифри року). Для сертифікатів із терміном дії після 2050 року стандарт RFC 5280 вимагає використання розширеного формату `GeneralizedTime` (`YYYYMMDDhhmmssZ` із чотиризначним числом року), щоб запобігти апаратній проблемі 2050 року при парсингу дат вбудованими криптобібліотеками.

```
+-------------------------------------------------------------------------+
| Структура сертифіката X.509 (ASN.1 DER / RFC 5280)                     |
| ├── Версія (Version: v3 = 0x02)                                         |
| ├── Серійний номер (Serial Number: унікальне ціле число до 20 байтів)  |
| ├── Алгоритм підпису (Signature Algorithm: ECDSA-SHA256 / RSA-2048)     |
| ├── Центр видачі (Issuer DN: C=UA, O=GridPKI, CN=Grid Root CA 1)        |
| ├── Термін дії (Validity):                                              |
| │   ├── notBefore: 2021-01-01 00:00:00 UTC (Початок дії)                |
| │   └── notAfter:  2026-01-01 00:00:00 UTC (КРИТИЧНА МЕЖА ЕКСПІРАЦІЇ)   |
| ├── Власник (Subject DN: C=UA, O=GridOperator, CN=meter-uuid-04829)     |
| ├── Відкритий ключ (Subject Public Key Info: алгоритм + байти ключа)   |
| ├── Стандартні розширення (Extensions):                                 |
| │   ├── Basic Constraints (cA=FALSE для кінцевого вузла, cA=TRUE для CA)|
| │   ├── Key Usage (digitalSignature, keyEncipherment, keyCertSign)      |
| │   ├── Extended Key Usage (clientAuth, serverAuth)                     |
| │   └── Subject Alternative Name (SAN: DNS, IP, URI пристрою)           |
| └── Цифровий підпис центру сертифікації (Digital Signature Value)       |
+-------------------------------------------------------------------------+
```

В архітектурі вбудованого зв'язку діє сувора ієрархічна асиметрія тривалості життя сертифікатів:

1. **Кореневий сертифікат (Root CA):** вершина ланцюга довіри, самопідписаний сертифікат (англ. *self-signed certificate*). Його закритий ключ зберігається в ізольованому апаратному модулі безпеки (HSM) в захищеному бункері без доступу до Інтернету. Типовий термін дії становить від 10 до 25 років.
2. **Проміжний сертифікат (Intermediate CA):** видається кореневим центром для операційного підпису кінцевих вузлів або регіональних шлюзів. Строк дії становить 3–7 років.
3. **Серверний TLS-сертифікат:** засвідчує справжність хмарного сервера або брокера MQTT. За сучасними стандартами CA/Browser Forum строк його дії обмежений 90–398 днями.
4. **Клієнтський сертифікат пристрою (Device Certificate / LDevID):** засвідчує особу конкретного приладу у схемі взаємної автентифікації (mTLS). Строк дії становить від 1 до 5 років.

Головна небезпека полягає у розриві між плановим терміном експлуатації апаратної частини та строком дії її сертифікатів. Промисловий контролер, лічильник або сонячний інвертор встановлюється на опорі чи в шафі на 15–20 років. Проте сертифікати, закладені в нього під час виготовлення, гарантовано завершаться набагато раніше, ніж деградують конденсатори в блоці живлення чи кремній мікроконтролера.

### Обчислювальна та енергетична ціна криптографії у вузьких каналах

Вибір криптографічного алгоритму для сертифікатів X.509 безпосередньо впливає на час життя батареї та надійність доставки пакетів вбудованих пристроїв. Порівняймо два домінуючі класи асиметричної криптографії: класичний RSA та еліптичні криві (ECC / ECDSA):

```
+--------------------------+---------------------+-----------------------+
| Параметр                 | RSA-2048            | ECDSA SECP256R1       |
+--------------------------+---------------------+-----------------------+
| Рівень криптостійкості   | 112 бітів           | 128 бітів             |
| Довжина відкритого ключа | 256 байтів          | 64 байти (нестиснутий)|
| Розмір сертифіката X.509 | 1200–1800 байтів    | 400–600 байтів        |
| Розмір ланцюга (3 ланки) | 4000–5500 байтів    | 1200–1800 байтів      |
| Час верифікації (Cortex-M4)| ~1.2 мс           | ~8.5 мс               |
| Споживання RAM при парсингу| > 4 КБ            | < 1.5 КБ              |
+--------------------------+---------------------+-----------------------+
```

У бездротових мережах із низькою пропускною здатністю (NB-IoT зі швидкістю 20–50 кбіт/с або стільникових мережах 2G) передача ланцюга сертифікатів RSA розміром 5 кілобайтів вимагає фрагментації на 4–5 TCP-сегментів. Якщо рівень сигналу на межі стільника слабкий (високий відсоток втрати пакетів BLER), повторне пересилання фрагментів рукостискання триває 10–25 секунд. У цей час радіомодем споживає струм 150–250 мА від батареї, скорочуючи автономний ресурс датчика з десяти років до кількох місяців.

Перехід на сертифікати еліптичних кривих (ECDSA SECP256R1 або Ed25519) скорочує розмір рукостискання більш ніж утричі, що дозволяє вмістити весь обмін у мінімальну кількість кадрів канального рівня.

### Дві сторони перевірки: перехресний глухий кут TLS

При встановленні захищеного каналу зв'язку за протоколом TLS 1.2 або TLS 1.3 виконується двостороння криптографічна перевірка валідності. Збій на будь-якій стороні призводить до негайного розриву з'єднання.

![Замкнене коло закінчення строку дії сертифіката у вбудованому парку](/root/course/embedded/strok-sertyfikata-i-park-shcho-spynyvsia-vnochi/img/cert-expiration-deadlock.svg)
*Замкнене коло закінчення строку дії сертифіката. Коли локальне сховище довіри або годинник мікроконтролера виходять за межі notAfter, рукостискання TLS переривається аварійним повідомленням Alert. Хмарний бекенд не має змоги надіслати оновлені сертифікати через заблокований канал OTA.*

#### Сторона 1: Клієнт валідує сервер (Server Verification)
Вбудований пристрій ініціює TCP-з'єднання й надсилає повідомлення `ClientHello`. Сервер відповідає повідомленням `ServerHello` та надсилає свій ланцюг сертифікатів (Certificate Chain).

Мікроконтролер запускає внутрішній рушій перевірки (Mbed TLS, wolfSSL або BearSSL), який виконує алгоритм валідації шляху за стандартом RFC 5280:
1. **Побудова шляху (Path Building):** від кінцевого сертифіката сервера через проміжні ланки до кореневого якоря (Trust Anchor), збереженого у Flash-пам'яті пристрою.
2. **Перевірка криптографічних підписів:** для кожного сертифіката обчислюється хеш тіла `TBSCertificate` (англ. *To Be Signed Certificate*) за алгоритмом SHA-256 і перевіряється відкритим ключем сертифіката вищого рівня:
   ```
   Verify_Signature(TBSCertificate[i], Signature[i], PublicKey[i+1]) == SUCCESS
   ```
3. **Перевірка часових рамок:** для кожного сертифіката в ланцюгу перевіряється виконання суворої нерівності:
   ```
   notBefore ≤ Current_Time ≤ notAfter
   ```
4. **Перевірка базових обмежень (Basic Constraints):** для кожного проміжного сертифіката прапорець `cA` повинен мати значення `TRUE`, а глибина ланцюга не повинна перевищувати значення `pathLenConstraint`.
5. **Перевірка імені вузла (Subject Alternative Name, SAN):** доменне ім'я сервера збігається із записом у розширенні SAN кінцевого сертифіката.

Якщо хмарні адміністратори оновили сертифікат сервера, випустивши його від нового кореневого центру сертифікації, якого немає у зашитому Flash-пам'яті пристрою сховищі довіри, мікроконтролер відкидає з'єднання з помилкою `MBEDTLS_X509_BADCERT_NOT_TRUSTED`. Якщо ж системний час пристрою перетнув `notAfter` зашитого старого кореня, повертається помилка `MBEDTLS_X509_BADCERT_EXPIRED`.

#### Сторона 2: Сервер валідує пристрій (Mutual TLS / mTLS)
У критичних інфраструктурах використовується взаємна автентифікація: сервер вимагає від пристрою пред'явити власний клієнтський сертифікат (`CertificateRequest`).

Пристрій надсилає свій сертифікат `LDevID` та підписує тимчасовий дайджест рукостискання закритим ключем (`CertificateVerify`). Хмарний балансувальник або брокер перевіряє сертифікат пристрою за власним списком довірених клієнтських центрів. Якщо строк дії сертифіката пристрою вичерпався хоча б на одну секунду, сервер надсилає TLS Alert `certificate_expired (45)` і закриває TCP-сокет.

Хроніка реальних інцидентів у світовій інфраструктурі, наведена у вставці про [катастрофи закінчення строку дії кореневих сертифікатів](root:embedded/strok-sertyfikata-i-park-shcho-spynyvsia-vnochi/hist-fleet-expiration-incidents.md), доводить: навіть найбільші технологічні корпорації та мобільні оператори неодноразово стикалися з раптовою зупинкою мільйонів пристроїв через некоректну валідацію застарілих коренів довіри.

#### Ризики жорсткого закріплення сертифікатів (Certificate Pinning)
Іншою небезпечною пасткою у вбудованих пристроях є некоректна реалізація закріплення сертифікатів (англ. *Certificate Pinning* або *Public Key Pinning*). Бажаючи захистити прилад від підміни серверного сертифіката скомпрометованими публічними центрами сертифікації, розробники жорстко прописують у коді прошивки SHA-256 хеш відкритого ключа конкретного кінцевого сертифіката сервера.

Коли термін дії серверного сертифіката закінчується або його достроково відкликають через витік ключа, системні адміністратори випускають новий сертифікат. Навіть якщо новий сертифікат видано тим самим довіреним коренем, зміна відкритого ключа сервера призводить до того, що функція пінінгу в мікроконтролері відхиляє з'єднання:
```
SHA-256(Server_Public_Key_New) ≠ Pinned_Hash_In_Firmware
```
Якщо прошивка містила лише один закріплений хеш без резервного резервування (Backup Pin) або механізму динамічного оновлення хешів через захищений канал, прилад назавжди втрачає доступ до сервера. Тому в сучасних вбудованих архітектурах пінінг застосовують виключно до проміжних або кореневих центрів сертифікації (CA Pinning) із обов'язковою наявністю щонайменше двох альтернативних відкритих ключів у сховищі довіри.

### Пастка жадібної валідації та перехресні підписи

Особливо підступною проблемою у вбудованих системах є поведінка застарілих алгоритмів побудови ланцюга довіри при використанні перехресного підпису (англ. *cross-signing*).

Коли створюється новий кореневий центр сертифікації `Root CA 2`, він відсутній у сховищах старих пристроїв. Щоб пристрої довіряли йому, старий авторитетний `Root CA 1` видає проміжний сертифікат для `Root CA 2` (перехресний підпис). У результаті утворюється граф довіри, де кінцевий сертифікат сервера може бути перевірений двома різними шляхами:

```
                  ШЛЯХ А (Короткий):
             [Root CA 2] (Новий, діє до 2038)
                  │
                  ▼
          [Intermediate CA]
                  │
                  ▼
         [Серверний сертифікат]

                  ШЛЯХ Б (Перехресний):
             [Root CA 1] (Старий, закінчився у 2021)
                  │ (перехресний підпис)
                  ▼
             [Root CA 2] (Виступає як проміжний)
                  │
                  ▼
          [Intermediate CA]
                  │
                  ▼
         [Серверний сертифікат]
```

#### Алгоритмічна помилка
Сучасні криптографічні стеки будують граф сертифікатів і перевіряють усі можливі шляхи. Якщо один шлях веде до простроченого кореня `Root CA 1`, рушій відкидає цей шлях, перевіряє альтернативний шлях А до `Root CA 2` і успішно встановлює з'єднання.

Проте застарілі бібліотеки у прошивках (OpenSSL 1.0.2 без прапорця `X509_V_FLAG_PARTIAL_CHAIN`, старі версії Mbed TLS, AxTLS, BearSSL) реалізують «жадібний лінійний пошук»:
1. Отримують від сервера повний набір сертифікатів, де передано перехресний сертифікат.
2. Знаходять у своєму сховищі сертифікат `Root CA 1` за збігом поля `Issuer DN`.
3. Фіксують цей ланцюг і перевіряють термін дії `Root CA 1`.
4. Бачать, що `notAfter` минув, і негайно переривають сесію з помилкою `CERT_HAS_EXPIRED`.
5. Бібліотека навіть не намагається перевірити, що `Root CA 2` вже є в її сховищі довіри як самостійний корінь.

Ця вада призвела до масового виходу з ладу польових приладів під час закінчення строків сертифікатів AddTrust у 2020 році та Let's Encrypt DST Root CA X3 у 2021 році.

### Чому традиційне відкликання (CRL та OCSP) не працює в IoT

У класичних вебсерверах та браузерах компрометація або дострокова зміна сертифікатів контролюється двома механізмами:
1. **Списки відкликаних сертифікатів (CRL, Certificate Revocation List):** підписаний файл, що містить перелік серійних номерів анульованих сертифікатів. У великих PKI розмір CRL-файлу досягає 10–50 мегабайтів. Завантаження та парсинг такого файлу на мікроконтролері з 64 КБ RAM є фізично неможливим.
2. **Протокол онлайнового статусу (OCSP, Online Certificate Status Protocol):** при кожному з'єднанні клієнт надсилає окремий HTTP-запит до сервера перевірки статусу (OCSP Responder). Для батарейного IoT-пристрою це подвоює витрати енергії радіомодуля та створює точку повної відмови: якщо OCSP-сервер недоступний, пристрій не може оцінити статус сертифіката.

Через ці обмеження сучасна індустрія вбудованих пристроїв відмовилася від перевірки CRL/OCSP на мікроконтролерах на користь концепції **короткоживучих сертифікатів (Short-Lived Certificates)** із тривалістю життя 30–90 днів у поєднанні з автоматизованою регулярною ротацією за протоколом EST або ACME. Якщо ключ пристрою скомпрометовано, сервер PKI просто припиняє його планову ротацію, і через кілька тижнів сертифікат стає недійсним природним шляхом.

### Генерація випадкових чисел: прихована пастка створення ключів

Під час локальної генерації нової пари асиметричних ключів у польових умовах мікроконтролер критично залежить від якості джерела ентропії.

Якщо прошивка використовує програмний псевдовипадковий генератор (PRNG), не ініціалізований апаратним шумом (True Random Number Generator, TRNG), виникає фатальна вразливість:
- Після одночасного ввімкнення підстанції тисячі лічильників стартують з однаковим початковим станом генератора (Seed).
- У результаті різні фізичні прилади генерують **ідентичні закриті ключі RSA або ECDSA**.
- При підписанні запитів CSR за алгоритмом ECDSA повторне використання одного й того самого випадкового числа `k` (nonce) дозволяє зловмиснику миттєво обчислити закритий ключ пристрою за двома підписами за допомогою простого лінійного рівняння.

Тому коректна архітектура вбудованої криптографії вимагає використання апаратного вузла TRNG, що збирає ентропію теплового шуму кремнієвих переходів або джитера внутрішніх RC-генераторів, із обов'язковою безперервною перевіркою якості за стандартом NIST SP 800-90B.

### Парадокс системного часу: замкнене коло RTC та NTP

Перевірка сертифіката спирається на одне неявне припущення: **мікроконтролер знає поточний точний час**. У світі персональних комп'ютерів та серверів це забезпечується батарейкою на материнській платі та службою NTP. У вбудованих пристроях це припущення ламається першим.

#### Анатомія розсинхронізації часу у мікроконтролерах
1. **Відсутність резервного живлення годинника (Battery-less RTC):** заради здешевлення конструкції більшість датчиків, розеток і лічильників не мають літієвої батарейки типу CR2032 для живлення вбудованого модуля RTC під час відключення основної мережі.
2. **Скидання до базової епохи (Epoch Reset):** після вимкнення живлення або перезавантаження за сторожовим таймером (Watchdog) регістри RTC ініціалізуються нульовим значенням або апаратною константою прошивки (наприклад, `1970-01-01 00:00:00 UTC` або `2015-01-01 00:00:00 UTC`).
3. **Температурний дрейф кварцового резонатора:** частота коливань годинникового кварцу на 32.768 кГц описується параболічною залежністю від температури навколишнього середовища:
   ```
   Δf / f = -k · (T - T₀)²      [параболічна температурна характеристика кварцу]
   ```
   де `k ≈ 0.035 ppm/°C²` — коефіцієнт кривини параболи, `T₀ ≈ 25 °C` — точка нульового дрейфу. За температури лічильника на вулиці −15 °C відхилення становить:
   ```
   Δf / f = -0.035 · (-15 - 25)² = -0.035 · 1600 = -56 ppm
   ```
   За таких умов годинник відстає на `56 · 10⁻⁶ · 86400 ≈ 4.84 с/добу`, що дає похибку понад пів години за рік без зовнішньої синхронізації.

#### Замкнене коло синхронізації
Коли прилад із розрядженим або скинутим годинником вмикається, виникає патовий цикл залежностей:
- Щоб отримати точний час через захищений протокол безпечного мережевого часу (NTS, *Network Time Security*) або через захищений HTTPS-запит, пристрій зобов'язаний встановити TLS-сесію.
- Щоб встановити TLS-сесію, бібліотека криптографії перевіряє `notBefore` сертифіката сервера (наприклад, `2024-05-01`).
- Оскільки на годиннику пристрою встановлено `1970-01-01`, умова `Current_Time ≥ notBefore` не виконується.
- Рушій TLS відкидає сертифікат із помилкою `certificate_not_yet_valid`, з'єднання розривається, і пристрій ніколи не отримує точний час.

```
       [Старт мікроконтролера: RTC = 1970-01-01]
                         │
                         ▼
        [Спроба встановити TLS до хмари]
                         │
                         ▼
  [Перевірка: 1970-01-01 < notBefore (2024-05-01)]
                         │
                         ▼
   [Помилка TLS: Сертифікат ще не набув чинності]
                         │
                         ▼
    [З'єднання розірвано: Час не синхронізовано] ──┐
                         ▲                         │
                         │ (Замкнене коло)         │
                         └─────────────────────────┘
```

> 🔧 **Навіщо це.** Щоб розірвати це замкнене коло, надійні прошивки використовують багаторівневий механізм відновлення часу: (1) зчитування приблизного часу з широкомовних повідомлень стільникових базових станцій NITZ (англ. *Network Identity and Time Zone*) або супутникових приймачів GPS/GNSS, які не вимагають TLS; (2) читання незахищеного HTTP-заголовка `Date` з фіксованих довірених IP-адрес із перевіркою монотонності; (3) збереження останньої відомої мітки часу в енергонезалежній Flash-пам'яті при кожному сеансі зв'язку (monotonic timestamp threshold). При старті пристрій гарантовано знає, що поточний час не може бути меншим за мітку останнього успішного підключення.

### Архітектура безперервної довіри: Dual-Root та A/B ротація

Щоб парк пристроїв ніколи не зупинився через закінчення строків сертифікатів, інженерна архітектура прошивки повинна виключати концепцію «єдиного статичного сертифіката». Надійне рішення будується на трьох стовпах: дводжерельних сховищах довіри, симетричних слотах ключів та перекритті часових вікон.

#### 1. Дводжерельне сховище довіри (Dual-Root Trust Store)
Пристрій повинен мати у Flash-пам'яті сховище довіри, здатне одночасно вміщувати щонайменше два кореневі сертифікати:
- **Active Root CA:** чинний центр сертифікації, який використовується серверами зараз.
- **Standby / Next-Gen Root CA:** наступний центр сертифікації, чиї ключі згенеровані на 10–15 років уперед і вже завантажені у пристрій, але сервери перейдуть на нього лише через 3–5 років.

![Часова шкала безперервної ротації довірених кореневих центрів](/root/course/embedded/strok-sertyfikata-i-park-shcho-spynyvsia-vnochi/img/dual-root-rollover-timeline.svg)
*Часова шкала ротації кореневих центрів сертифікації (Dual-Root Rollover). Завдяки вікну перекриття тривалістю у кілька років, перехід серверів на новий корінь CA-2 відбувається безшовно для всіх пристроїв у полі.*

Програмна реалізація такого сховища, алгоритми безпечного перемикання слотів та конфігурація зворотних викликів бібліотеки Mbed TLS детально розібрані у проєктній вставці про [дводжерельний валідатор довіри](root:embedded/strok-sertyfikata-i-park-shcho-spynyvsia-vnochi/proj-dual-root-verifier.md).

#### 2. Математика правила 70% для ротації клієнтських сертифікатів
Пристрій ніколи не повинен чекати останнього дня чи останнього тижня дії свого сертифіката для його поновлення. Якщо прилад у полі опиниться поза зоною покриття мережі під час сильної грози чи ремонтних робіт оператора, затримка зв'язку на кілька днів призведе до його безповоротної втрати.

Момент ініціації планової ротації сертифіката розраховується за формулою детермінованого порогу:

```
T_duration = notAfter - notBefore           [повна тривалість життя сертифіката]
T_renew    = notBefore + 0.70 · T_duration  [поріг початку спроб ротації]
```

Якщо сертифікат видано на 365 днів (1 рік), прилад починає процедуру автоматичного оновлення рівно через `365 · 0.70 = 255.5` діб (за 110 днів до завершення строку). Це створює запас часу майже у чотири місяці на подолання тимчасових мережевих збоїв, повторні спроби за алгоритмом експоненційного відступу та планове технічне обслуговування бекенда.

### Автоматизована ротація: протокол EST (RFC 7030)

Для регулярного безшовного оновлення клієнтських сертифікатів пристроїв без втручання людини застосовується протокол **EST** (англ. *Enrollment over Secure Transport*, RFC 7030).

![Послідовність автоматичної ротації сертифіката пристрою за протоколом EST](/root/course/embedded/strok-sertyfikata-i-park-shcho-spynyvsia-vnochi/img/est-rotation-flow.svg)
*Послідовність автоматичної ротації сертифіката за протоколом EST (RFC 7030). Оновлення відбувається в межах поточної чинної mTLS сесії без передачі закритого ключа по мережі.*

Повний протокольний інтерфейс, формати повідомлень MIME, структуру заголовків та клієнтський скінченний автомат описано в довіднику з [протоколу ротації сертифікатів EST](root:embedded/strok-sertyfikata-i-park-shcho-spynyvsia-vnochi/api-est-cert-rotation.md).

#### Покрокова послідовність ротації:
1. **Локальна генерація ключів:** мікроконтролер викликає апаратний генератор випадкових чисел (TRNG) або апаратний модуль безпеки (Secure Element) і генерує нову пару асиметричних ключів (наприклад, еліптична крива ECDSA SECP256R1 або Ed25519) у тимчасовому секторі пам'яті (Slot B). Закритий ключ **ніколи не залишає кристала пристрою**.
2. **Створення запиту на підпис (CSR):** пристрій формує структуру PKCS#10, вказуючи свій ідентифікатор (UUID/MAC), додає новий відкритий ключ і підписує запит новим закритим ключем як доказ володіння (Proof-of-Possession).
3. **Захищений запит через mTLS:** використовуючи свій **старий чинний сертифікат із Slot A**, пристрій встановлює mTLS-з'єднання з сервером реєстрації EST і відправляє CSR методом `POST /.well-known/est/simplereenroll`.
4. **Автентифікація та випуск:** сервер PKI перевіряє чинність старого сертифіката пристрою в сесії TLS, перевіряє цифровий підпис у CSR і випускає новий сертифікат X.509, повертаючи його у відповіді `200 OK` (PKCS#7).
5. **Атомарне перемикання (Atomic Commit):** пристрій записує новий сертифікат у Slot B, перевіряє його цілісність і проводить тестове TLS-з'єднання. Лише після підтвердження зв'язку статус Slot B стає `ACTIVE`, а Slot A переводиться в резерв.

### Ешелонована драбина аварійного відновлення (Defense-in-Depth)

Що робити, якщо всі превентивні механізми відмовили: пристрій пролежав на складі у вимкненому стані п'ять років, усі його робочі сертифікати прострочилися, а сервер перейшов на нову інфраструктуру?

Для запобігання втраті приладу архітектура прошивки повинна містити чотирирівневу ешелоновану драбину відновлення зв'язку та довіри.

![Ешелонована драбина відновлення зв'язку та довіри](/root/course/embedded/strok-sertyfikata-i-park-shcho-spynyvsia-vnochi/img/fallback-recovery-ladder.svg)
*Чотири рівні аварійного відновлення довіри. При відмові штатного mTLS пристрій послідовно ескалує спроби зв'язку до резервного кореня, виділеного завантажувального сервера та позасмугових криптографічних пакетів відновлення.*

```
+-------------------------------------------------------------------------+
| Рівень 1: Штатний захищений канал (Primary mTLS)                        |
| ├── Робочий сертифікат пристрою (Slot A, термін дії 1-3 роки)           |
| └── Автоматична ротація за таймером 70% (EST / ACME / SCEP)             |
+-------------------------------------------------------------------------+
                                     │ (Відмова / Прострочено)
                                     ▼
+-------------------------------------------------------------------------+
| Рівень 2: Резервний довірчий якір (Dual-Root Rollover)                   |
| ├── Автоматичне перемикання на резервний Root CA 2 (Slot B у Flash)     |
| └── Спроба встановити зв'язок з оновленим бекендом                      |
+-------------------------------------------------------------------------+
                                     │ (Відмова / Скомпрометовано)
                                     ▼
+-------------------------------------------------------------------------+
| Рівень 3: Виділений аварійний Bootstrap-канал                            |
| ├── Незмінний заводський сертифікат IDevID (IEEE 802.1AR у Secure Elem) |
| ├── Ізольований аварійний сервер: bootstrap.device-recovery.cloud       |
| └── Перевипуск робочих сертифікатів LDevID та оновлення Trust Store      |
+-------------------------------------------------------------------------+
                                     │ (Відмова / Повна ізоляція)
                                     ▼
+-------------------------------------------------------------------------+
| Рівень 4: Позасмугове відновлення (Offline Signed Rescue Payload)        |
| ├── Аварійний пакет відновлення (через BLE, USB, UART або SMS)          |
| ├── Підпис незмінним асиметричним Master Key виробника                  |
| └── Апаратний захист від відкату версій (Anti-Rollback Monotonic Counter)|
+-------------------------------------------------------------------------+
```

#### Рівень 3: Заводський ідентифікатор IDevID (IEEE 802.1AR)
Стандарт **IEEE 802.1AR** розділяє ідентичність пристрою на дві сутності:
- **LDevID (Locally Significant Device Identifier):** експлуатаційний сертифікат, який видається оператором мережі й регулярно оновлюється за протоколом EST.
- **IDevID (Initial Device Identifier):** незмінний заводський сертифікат, який записується на етапі виробництва кремнієвого кристала або плати (наприклад, у криптографічний чип ATECC608 або OTP-пам'ять SoC).

Закритий ключ IDevID апаратно захищений від зчитування й ніколи не видаляється. Сертифікат IDevID має термін дії 30–50 років і підписаний спеціальним довговічним кореневим центром виробника *Manufacturer Root CA*. Якщо всі робочі сертифікати LDevID прострочені або пошкоджені, пристрій переходить в аварійний режим (Recovery Bootstrap Mode) і підключається до спеціального ізольованого сервера відновлення, використовуючи свій незмінний заводський IDevID для отримання нового пакета сертифікатів.

#### Рівень 4: Позасмуговий рятувальний пакет із захистом від відкату
Якщо мережевий тракт недоступний, відновлення здійснюється через локальні інтерфейси (сервісний роз'єм UART, оптичний порт лічильника стандарту IEC 62056-21, NFC, BLE або канал бінарних SMS).

Аварійний пакет оновлення містить новий масив кореневих сертифікатів та нову конфігурацію зв'язку. Безпека такого пакета базується на трьох принципах:
1. **Підпис кореневим ключем розробника (Master Offline Key):** пакет підписано закритою парою асиметричного ключа, відкрита частина якого жорстко зашита в апаратному завантажувачі (ROM Bootloader). Цей підпис валідується математично незалежно від системного часу пристрою.
2. **Апаратний монотонний лічильник (Anti-Rollback Counter):** щоб зловмисник не міг відкотити пристрій на старий скомпрометований сертифікат, пакет містить порядковий номер версії `Sequence_Number`. Мікроконтролер перевіряє, що номер у пакеті строго більший за значення, зафіксоване в апаратних одноразових ф'юзах (eFuses / OTP) або захищеному секторі Flash:
   ```
   Sequence_Number_New > Sequence_Number_Hardware
   ```
3. Після успішної перевірки підпису та лічильника новий номер фіксується спалюванням ф'юза, а нові сертифікати записуються у Flash-пам'ять.

### Порівняльний аналіз стратегій керування сертифікатами

Підсумуємо розглянуті інженерні підходи до забезпечення життєвого циклу криптографічної довіри у вбудованих пристроях:

```

| та обсяг Flash    | (< 2 КБ Flash)    | структури, CRC32)  | клієнт, CSR ASN.1) |
```
