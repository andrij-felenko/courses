# ⚙️ Скрипти конфігурації та відновлення чіпа при першому контакті

Коли свіжозмонтована плата відмовляється виходити на зв'язок зі стандартними налаштуваннями графічного IDE, єдиним надійним інструментом діагностики залишається командний рядок утиліт налагодження. Графічні середовища часто приховують точні помилки шини CoreSight за загальними повідомленнями «Target not found». Конфігураційні файли OpenOCD, сценарії J-Link, налагоджувальні макроси GDB та виклики CLI-програматорів дозволяють напряму керувати лінією апаратного скидання, виставляти безпечні тактові частоти SWD, аналізувати стан регістрів аварійного завершення та примусово скидати захищені регістри конфігурації кристала.

Нижче наведено перевірені конфігурації для чотирьох найпоширеніших сімейств апаратних інструментів: OpenOCD (для ST-Link, CMSIS-DAP та J-Link), фірмової утиліти SEGGER JLinkExe, STM32_Programmer_CLI та низькорівневих скриптів GDB.

## 1. Конфігурація OpenOCD для режиму Connect under Reset

Стандартний конфігураційний файл OpenOCD для мікроконтролерів Cortex-M зазвичай намагається виконати програмне скидання (`soft_reset_halt`). Якщо на платі активний режим глибокого сну або вимкнено тактування інтерфейсу налагодження, OpenOCD не може підключитися.

Щоб примусово тримати лінію `nRESET` у низькому рівні під час ініціалізації порту налагодження (SW-DP), створюють спеціальний конфігураційний файл `bringup.cfg`. Цей файл явно налаштовує роботу з апаратною лінією скидання ще до надсилання перших тактових імпульсів на шину.

```cfg
# bringup.cfg — Конфігурація OpenOCD для першого пуску та відновлення плати

# 1. Вибір апаратного інтерфейсу (stlink, cmsis-dap або jlink)
source [find interface/stlink.cfg]

# Якщо підключено кілька однакових адаптерів, явно задаємо серійний номер:
# hla_serial "066EFF535055877267153724"

# 2. Вибір протоколу передачі (SWD)
transport select hla_swd

# 3. Зниження початкової частоти SWCLK до безпечних 500 кГц
# Це усуває проблеми з дзвоном на довгих шлейфах та паразитною ємністю монтажу
adapter speed 500

# 4. Підключення конфігурації цільового чіпа (наприклад, STM32F4x / STM32G4x)
source [find target/stm32f4x.cfg]

# 5. КРИТИЧНЕ НАЛАШТУВАННЯ: Утримання лінії скидання під час ініціалізації
# srst_only: використовується лише лінія апаратного скидання nRESET
# srst_nogate: тактування DP не блокується під час утримання скидання
# connect_assert_srst: притиснути nRESET до землі ДО початку SWD-транзакцій
reset_config srst_only srst_nogate connect_assert_srst

# 6. Збільшення тайм-аутів для роботи з нестабільним живленням або виходу з глибокого сну
adapter srst delay 100
adapter srst pulse_width 100

# 7. Обробник події ініціалізації: зупинка ядра на першій інструкції
$_TARGETNAME configure -event reset-init {
    echo "=== Ядро успішно перехоплено в стані Reset ==="
    # Зупиняємо ядро та скасовуємо виконання будь-якого завантаженого коду
    halt
}
```

Запуск сесії перевірки та відновлення через термінал:

```bash
openocd -f bringup.cfg -c "init; reset init; targets; halt"
```

Якщо підключення пройшло успішно, OpenOCD видасть рядок стану з ідентифікатором ядра (`IDCODE 0x2ba01477` для Cortex-M4) та зупинить процесор у стані `halted`.

## 2. Скидання захисту Flash (RDP) та повне очищення через OpenOCD

Якщо чіп було заблоковано на рівні Readout Protection (RDP Level 1), читання пам'яті через AHB-AP завершується апаратною помилкою шини. Для повернення кристала у відкритий стан (RDP Level 0) виконують скидання байтів конфігурації (Option Bytes), що автоматично викликає апаратне очищення всієї пам'яті (Mass Erase).

Операція розблокування вимагає подачі спеціальної послідовності ключів розблокування у внутрішній контролер Flash-пам'яті перед тим, як регістри Option Bytes дозволять модифікацію. Утиліта OpenOCD автоматизує введення ключів через внутрішній драйвер цільового чіпа.

Команди виконують через вбудований телнет-сервер OpenOCD (порт 4444):

```bash
# Підключення до керуючого порту OpenOCD
telnet localhost 4444
```

У вікні telnet-сесії вводять послідовність команд розблокування:

```text
> reset halt
target halted due to debug-request, current mode: Thread 
xPSR: 0x01000000 pc: 0x08000180 msp: 0x20020000

> # Розблокування для сімейства STM32F4 / F2
> stm32f4x unlock 0
target halted due to breakpoint, current mode: Handler
stm32f4x unlocked.
INFO: a reset or power cycle is required for the new settings to take effect.

> # Повне стирання всіх секторів Flash
> flash erase_sector 0 0 last
erased sectors 0 through 11 on chip 0 in 1.428s

> # Фіксація скидання та повторна ініціалізація
> reset init
```

## 3. Пакетний скрипт для SEGGER J-Link (JLinkExe)

Утиліти SEGGER J-Link славляться своєю стійкістю до апаратних збоїв та наявністю швидких низькорівневих команд. Скрипт командного інтерфейсу `JLinkExe` дозволяє повністю автоматизувати процес підключення під скиданням, перевірки життєздатності пам'яті та очищення Flash.

Перед початком транзакцій утиліта J-Link відправляє спеціальну послідовність перемикання JTAG-to-SWD: понад 50 тактів із високим рівнем на `SWDIO`, магічне 16-бітне слово `0x79E7` та ще одну послідовність скидання лінії. Зниження частоти до 400 кГц гарантує, що жоден перехідний процес у шлейфі не зіб'є розпізнавання цієї послідовності.

Створимо файл сценарію `recover_target.jlink`:

```text
// recover_target.jlink — Автоматичне перехоплення та стирання чіпа
// Встановлюємо інтерфейс SWD
si 1

// Знижуємо частоту тактування до безпечних 400 кГц
speed 400

// Вибираємо цільовий пристрій
device STM32F401RE

// Вмикаємо апаратний Connect under Reset (тип скидання 2 = Hardware pin reset)
SetResetType 2

// Притискаємо nRESET, подаємо такти та зчитуємо DP-IDCODE
R0
R1

// Зупиняємо ядро
Halt

// Перевіряємо поточні значення регістрів процесора
Regs

// Перевіряємо читання пам'яті SRAM за адресою 0x20000000 (читаємо 4 слова)
mem32 0x20000000 4

// Повне апаратне розблокування Option Bytes та стирання Flash
Unlock STM32F4
Erase

// Скидання чіпа для застосування змін конфігурації
R0
R1
Halt

// Завершення сесії
Exit
```

Виклик скрипту в операційній системі:

```bash
JLinkExe -CommandFile recover_target.jlink
```

Вивід утиліти містить виміряну напругу `VTref` (наприклад, `VTref = 3.312V`), ідентифікатор точки доступу до налагодження (DP-ID) та звіт про повне стирання секторів Flash-пам'яті.

## 4. Відновлення через STM32_Programmer_CLI

Фірмова консольна утиліта від STMicroelectronics є стандартом для роботи з чіпами сімейства STM32 через ST-Link або системний USB-DFU завантажувач. Вона має прямий доступ до внутрішніх регістрів Option Bytes без необхідності писати складні скрипти ініціалізації GDB.

Це особливо корисно при роботі на автоматизованих лініях збирання або під час відновлення плат із пошкодженою таблицею векторів переривань.

### Команда 1: Підключення під скиданням та читання унікального ідентифікатора UID

```bash
STM32_Programmer_CLI -c port=SWD mode=UR freq=500 -r32 0x1FFF7A10 3
```

Параметри:
- `-c port=SWD`: вибір інтерфейсу Serial Wire Debug.
- `mode=UR`: режим **Under Reset** (утримує апаратний пін NRST в нулі перед тактуванням SWCLK).
- `freq=500`: знижена частота 500 кГц.
- `-r32 0x1FFF7A10 3`: читання трьох 32-бітних слів унікального 96-бітного UID мікроконтролера з системної області пам'яті.

### Команда 2: Зняття захисту RDP Level 1 (скидання Option Bytes у 0xAA)

Якщо чіп захищений, запис значення `0xAA` у біти RDP повертає його у відкритий режим Level 0 і запускає повний Mass Erase:

```bash
STM32_Programmer_CLI -c port=SWD mode=UR freq=500 -ob RDP=0xAA
```

### Команда 3: Повне стирання та прошивання перевірочного бінарника з верифікацією

```bash
STM32_Programmer_CLI -c port=SWD mode=UR freq=2000 -e all -w blinky_test.bin 0x08000000 -v -rst
```

Параметри:
- `-e all`: масове стирання всієї Flash-пам'яті перед записом.
- `-w blinky_test.bin 0x08000000`: запис файлу прошивки з базової адреси Flash.
- `-v`: побайтова верифікація записаних даних (читання назад і порівняння CRC).
- `-rst`: апаратне скидання чіпа після завершення прошивання для негайного запуску програми.

## 5. Скрипти автоматизації GDB для діагностики аварійних станів

Коли мікроконтролер перехоплено відлагоджувачем, але він відразу потрапляє в HardFault після першого кроку виконання, причину збою з'ясовують через читання системних регістрів System Control Space (SCS).

Архітектура ARM Cortex-M надає деталізовані статусві регістри помилок: Configurable Fault Status Register (`CFSR`), HardFault Status Register (`HFSR`) та регістри адрес збоїв `MMFAR` / `BFAR`. Автоматизація їх читання через GDB дозволяє миттєво локалізувати причину падіння ядра (спроба виконання інструкції з непарною адресою, помилка вирівнювання шини або звернення до нетактованого периферійного блоку).

Створимо файл конфігурації `.gdbinit` для швидкого аналізу стану ядра:

```gdb
# .gdbinit — Сценарій діагностики першого старту в GDB

# 1. Підключення до локального GDB-сервера OpenOCD
target extended-remote :3333

# 2. Налаштування формату виводу
set print pretty on
set pagination off

# 3. Команда для відображення регістрів аварійного стану ARM Cortex-M
define show_faults
    printf "\n=== АНАЛІЗ РЕГІСТРІВ АВАРІЇ CORTEX-M ===\n"
    set $cfsr  = *(uint32_t *)0xE000ED28
    set $hfsr  = *(uint32_t *)0xE000ED2C
    set $mmfar = *(uint32_t *)0xE000ED34
    set $bfar  = *(uint32_t *)0xE000ED38
    
    printf "CFSR  (Configurable Fault Status): 0x%08X\n", $cfsr
    printf "HFSR  (HardFault Status):          0x%08X\n", $hfsr
    printf "MMFAR (MemManage Fault Address):   0x%08X\n", $mmfar
    printf "BFAR  (BusFault Address):          0x%08X\n", $bfar

    if ($hfsr & (1 << 30))
        printf " -> HardFault викликаний примусово (FORCED) вкладеним винятком!\n"
    end
    if ($cfsr & (1 << 8 + 7))
        printf " -> BFAR дійсний! Адреса помилки шини: 0x%08X\n", $bfar
    end
    if ($cfsr & (1 << 16 + 0))
        printf " -> Спроба виконання невалідної інструкції (UNDEFINSTR)!\n"
    end
end

# 4. Команда перевірки стабільності пам'яті SRAM
define test_sram
    printf "\n[*] Тестування запису та читання SRAM за адресою 0x20000000...\n"
    set *(uint32_t *)0x20000000 = 0x55AA55AA
    set $read1 = *(uint32_t *)0x20000000
    set *(uint32_t *)0x20000000 = 0xAA55AA55
    set $read2 = *(uint32_t *)0x20000000

    if ($read1 == 0x55AA55AA && $read2 == 0xAA55AA55)
        printf "[+] SRAM працює стабільно, бітових залипань не виявлено.\n"
    else
        printf "[!] ПОМИЛКА: Несправність SRAM або шини даних!\n"
    end
end
```

## 6. Діагностичний скрипт на Python з використанням pyOCD

Для автоматизованого стендового тестування щойно виготовлених плат зручно використовувати бібліотеку `pyocd`. Бібліотека підтримує пряму взаємодію з адаптерами CMSIS-DAP та ST-Link через API Python без потреби у сторонніх утилітах.

Наведений нижче скрипт самостійно встановлює з'єднання в режимі `connect_mode=under-reset`, перевіряє стан напруг, вичитує регістри ядра та записує тестовий бінарник.

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-
"""Автоматизована верифікація першого контакту плати через pyOCD."""

import sys
import time
from pyocd.core.helpers import ConnectHelper
from pyocd.core.target import Target
from pyocd.flash.file_programmer import FileProgrammer

def verify_board(target_override="stm32f401re", firmware_path=None):
    print(f"[*] Пошук підключеного відлагоджувача...")
    
    # Налаштовуємо сесію: Connect under Reset, безпечна частота 1 МГц
    session = ConnectHelper.session_with_chosen_probe(
        target_override=target_override,
        options={
            "connect_mode": "under-reset",
            "frequency": 1000000,          # 1 МГц
            "reset_type": "hw",            # Апаратне скидання через NRST
            "auto_unlock": True            # Автоматичне зняття RDP
        }
    )
    
    if session is None:
        print("[!] Помилка: Апаратний відлагоджувач (DAPLink/ST-Link) не знайдено на USB.")
        sys.exit(1)

    with session:
        board = session.board
        target = session.target
        
        print(f"[+] Відлагоджувач: {board.name}")
        print(f"[+] Цільовий процесор: {target.part_number}")
        
        # Читання ідентифікатора CoreSight DP IDCODE
        dp_id = target.dp.dpidr.read()
        print(f"[+] CoreSight DP IDCODE: 0x{dp_id:08X}")
        
        # Зупиняємо ядро та читаємо поточні регістри
        target.halt()
        pc = target.read_core_register("pc")
        sp = target.read_core_register("sp")
        print(f"[+] Стан ядра: HALTED | PC = 0x{pc:08X} | SP = 0x{sp:08X}")
        
        if firmware_path:
            print(f"[*] Прошивання тестового бінарника: {firmware_path}...")
            programmer = FileProgrammer(session)
            programmer.program(firmware_path, base_address=0x08000000)
            print("[+] Прошивку успішно записано та перевірено!")
            
            # Апаратний перезапуск для виконання прошивки
            print("[*] Перезапуск плати...")
            target.reset()
            print("[+] Плата працює.")

if __name__ == "__main__":
    fw = sys.argv[1] if len(sys.argv) > 1 else None
    verify_board(firmware_path=fw)
```

## 7. Розшифровка типових помилок логів OpenOCD

Під час запуску OpenOCD детальний лог часто містить точну вказівку на те, яка саме ділянка ланцюга зв'язку або мікроконтролера дала збій:

| Рядок у лозі OpenOCD | Фізична причина несправності | Метод усунення |
|---|---|---|
| `Error: open failed` | Відлагоджувач не розпізнано операційною системою по USB (відсутній драйвер WinUSB/libusb або конфлікт прав у Linux udev). | Встановити драйвер через утиліту Zadig у Windows або додати правило `/etc/udev/rules.d/` у Linux. |
| `Error: Target not examined yet` | Відлагоджувач не отримав коректного значення `DP-IDCODE` у відповідь на послідовність ініціалізації SWD. | Перевірити наявність 3.3 В на `V_target`, напругу 1.2 В на пінах `VCAP` та цілісність провідника `GND`. |
| `Error: CMSIS-DAP command DAP_Transfer failed (ACK fault)` | Зрив бітової синхронізації через дзвін на лінії `SWCLK` або відсутність підтяжки на `SWDIO`. | Знизити `adapter speed` до 100–500 кГц та перевірити наявність демпфуючих резисторів `R_s = 22–47 Ом`. |
| `Error: MEM-AP transfer error` | Точка доступу до пам'яті CoreSight заблокована внутрішнім захистом кристала. | Активовано захист Flash RDP Level 1. Виконати процедуру `unlock` або скидання Option Bytes. |
| `Polling target stm32f4x.cpu failed` | Зв'язок із ядром раптово обірвався після виходу зі скидання. | Прошивка вимкнула піни SWD або ввела ядро в глибокий сон (WFI). Застосувати режим `connect_assert_srst`. |

Застосування цих скриптів гарантує, що жоден стан внутрішнього завантажувача, залишкової прошивки чи активованого захисту Option Bytes не завадить встановити контакт із новим мікроконтролером.
