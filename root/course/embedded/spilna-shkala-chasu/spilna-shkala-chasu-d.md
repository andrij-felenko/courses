Під час розслідування аварійної посадки безпілотного апарата інженер відкриває три незалежні журнали: бортовий бінарний лог польотного контролера (ULog/DataFlash), журнал подій наземної станції керування (QGroundControl) та відеозапис курсової камери. На бортовому лозі акселерометр фіксує руйнівне перевантаження `18.4 g` на позначці `100.054` с. У журналі станції оператор віддав команду «Аварійна зупинка моторів» о `100.220` с, а на відеозаписі зіткнення з перешкодою відбувається на позначці `100.350` с. Якщо зіставити ці записи «в лоб», виникає абсурдний висновок: апарат спочатку зламав крило, через 166 мілісекунд оператор зреагував на небезпеку, а ще через 130 мілісекунд камера нарешті показала наближення дерева.

Причина цієї плутанини полягає в тому, що кожен із трьох вузлів розподіленої системи відлічує час за власним фізичним резонатором, а передача даних між ними зазнає випадкових мережевих і конвеєрних затримок. Бортовий мікроконтролер працює від локального кварцового генератора, наземна станція — від годинника x86-процесора, а камера — від власного генератора відеоенкодера. Без спеціального протоколу синхронізації та вшивання апаратних міток часу жодне зіставлення подій між бортом, станцією та відеопотоком не є достовірним.

## Проблема трьох розбіжних годинників

Будь-який автономний комплекс складається щонайменше з трьох гетерогенних (грец. *heterogenes* — різнорідний) вузлів: польотного контролера реального часу, наземної станції та підсистеми відеофіксації. Кожен із них живе у власній замкненій системі координат часу.

```
+-----------------------------------------------------------------------------------+
|  Польотний контролер (FC)   |  Кварц 16 МГц      |  Дрейф: +30 ppm (+2.59 с/добу) |
|  Наземна станція (GCS)      |  x86 RTC / OS Time |  Дрейф: -15 ppm (-1.30 с/добу) |
|  Відеоенкодер камери (CAM)  |  SoC Кварц 24 МГц  |  Дрейф: +50 ppm (+4.32 с/добу) |
+-----------------------------------------------------------------------------------+
```

### Фізика кварцового дрейфу

Частота кварцового резонатора визначається його геометричними розмірами та п'єзоелектричними властивостями кристала. Проте під дією температури, механічних вібрацій і старіння матеріалу реальна частота генерації неминуче відхиляється від номіналу. Цю розбіжність вимірюють у частинах на мільйон (англ. *parts per million*, ppm, `1 ppm = 10⁻⁶`).

Типовий промисловий кварцовий генератор польотного контролера має температурну нестабільність у діапазоні від `±10` до `±50 ppm`. Відносне часове зміщення `Δt` за інтервал спостереження `T` розраховується за формулою:

```
Δt = T · (f_real - f_nominal) / f_nominal   [означення відносного зміщення частоти]
   = T · ppm · 10⁻⁶                        [підстановка одиниць вимірювання: 1 ppm = 10⁻⁶]
```

Якщо бортовий контролер має похибку `+30 ppm`, а станція керування — `-15 ppm`, відносна швидкість розходження їхніх годинників становить `45 ppm`. За добу автономної роботи ці годинники розійдуться на відчутну величину:

```
Δt_доба = 86400 с · 45 · 10⁻⁶               [інтервал доби 86400 секунд та сумарний дрейф 45 ppm]
        = 3.888 секунди                    [накопичена фазова похибка за 24 години]
```

Навіть за короткий 30-хвилинний політ розбіжність сягає:

```
Δt_30хв = 1800 с · 45 · 10⁻⁶                [інтервал 30 хвилин (1800 с) та дрейф 45 ppm]
        = 0.081 секунди (81 мілісекунда)   [накопичений часовий зсув]
```

За частоти відеозйомки 60 кадрів на секунду інтервал між сусідніми кадрами становить лише `16.67 мс`. Отже, зміщення на 81 мс означає, що відеокадр розходиться з телеметрією польотного контролера майже на 5 повних кадрів. Для алгоритмів візуально-інерційної одометрії (VIO), де положення дрона оцінюється сумісним фільтром Калмана за зміщенням пікселів оптичного потоку та показаннями гіроскопа, похибка навіть у 5 мс є фатальною і призводить до розходження просторової оцінки.

![Проблема трьох годинників: дрейф генераторів і затримка каналу](/root/course/embedded/spilna-shkala-chasu/img/time-divergence-asymmetry.svg)
*Проблема трьох годинників. Згори — фізична розбіжність автономних генераторів через дрейф кварцу. Знизу — ілюзія спотворення послідовності подій під час аварії, якщо кожен вузол ставить мітку часу в момент прибуття пакета чи кадру.*

### Ілюзія затримки прийому (Arrival Timestamping)

Найпоширеніша помилка початківців — маркувати телеметрію та відеокадри локальним часом наземної станції в момент надходження байтів із мережевого сокета. Цей підхід руйнує причинно-наслідковий зв'язок з таких причин:

1. **Недетерміновані затримки радіоканалу**: пакети телеметрії проходять крізь буфери передавача, черги повторної передачі (ARQ) у разі завад та інтерфейсні мости UART-to-USB. Затримка коливається від 5 до 250 мс (явище джитера, англ. *jitter*).
2. **Конвеєр стиснення відео**: відеосенсор експонує кадр, процесор обробки сигналів зображення (ISP) формує матрицю YUV, апаратний енкодер H.264 формує I/P-кадри, а пакетувальник RTSP/RTP відправляє потік у мережу. Загальна затримка конвеєра становить від 80 до 350 мс.
3. **Буферизація операційної системи**: мережеві стеки Linux та Windows акумулюють пакети в сокетних буферах для оптимізації контекстних перемикань ядра, додаючи непередбачувану затримку від 10 до 50 мс.

Якщо подія сталася на борту в момент `t_real = 100.000` с, станція отримає телеметрію о `100.220` с, а відеокадр з'явиться на моніторі о `100.350` с. Щоб відновити істину, кожен вузол повинен зафіксувати момент народження даних за локальним таймером, а система має вміти перераховувати ці локальні мітки в єдину спільну шкалу часу.

## Джерела еталонного часу: ієрархія та інтерфейси

Щоб узгодити час між вузлами, системі потрібне абсолютне первинне джерело (стратум 0/1) або високоточний протокол двостороннього узгодження шкал.

```
+-----------------------------------------------------------------------------------+
| Джерело / Протокол  | Точність     | Джитер     | Інтерфейс     | Рівень штампу   |
+---------------------+--------------+------------+---------------+-----------------+
| GNSS / GPS PPS      | < 50 нс      | < 5 нс     | GPIO / TIM IC | Апаратний (PHY) |
| PTP (IEEE 1588)     | < 1 мкс      | 10–100 нс  | Ethernet MII  | Апаратний MAC   |
| MAVLink TIMESYNC    | 0.5–5 мс     | 1–10 мс    | UART / Radio  | Драйвер/Пакет   |
| NTP / SNTP          | 1–20 мс      | 5–50 мс    | UDP / Wi-Fi   | Сокет ОС (L7)   |
+---------------------+--------------+------------+---------------+-----------------+
```

### 1. GNSS 1 PPS (Pulse Per Second)

Супутниковий приймач (GPS/Galileo/BeiDou) формує строгий прямокутний імпульс тривалістю 100 мс на початку кожної астрономічної секунди шкали UTC. Точність наростаючого фронту імпульсу відносно шкали UTC становить менш ніж 30–50 наносекунд.

```
                  1 PPS фронт (точність < 50 нс)
                         │
        ─────────────────┐       ┌─────────────────┐       ┌───────
                         │       │                 │       │
                         └───────┘                 └───────┘
                         ◄─────── 1.000 000 с ─────►
```

Для використання цього сигналу мікроконтролер не повинен обробляти імпульс у звичайному програмному перериванні GPIO, оскільки латентність входу в ISR (англ. *Interrupt Service Routine*) та блокування критичних секцій іншими драйверами дають розкид у 2–15 мікросекунд. 

Імпульс 1 PPS подають безпосередньо на вивід таймера з функцією апаратного захоплення (англ. *Input Capture*). Наростаючий фронт сигналу миттєво копіює поточне значення 32-бітного лічильника таймера в регістр `CCR` (англ. *Capture/Compare Register*) на апаратному рівні кремнію з похибкою в 1 такт процесора (наприклад, 4.5 нс при частоті 216 МГц).

Потім прошивка зіставляє номер секунди з NMEA-повідомлення `$GPRMC` або бінарного пакету `UBX-NAV-PVT`, отримуючи бездоганну прив'язку:

```
T_epoch_utc = NMEA_seconds_utc · 1 000 000 + (TIM_cnt - TIM_captured_pps) · tick_period_us
```

### 2. Промисловий протокол PTP (IEEE 1588)

Якщо на борту встановлено кілька обчислювачів (наприклад, польотний контролер STM32, процесор технічного зору NVIDIA Jetson та лідар), об'єднаних мережею Ethernet, стандартом синхронізації є PTP (англ. *Precision Time Protocol*, IEEE 1588-2008 / IEEE 1588-2019).

PTP досягає субмікросекундної точності завдяки апаратному штампуванню пакетів (англ. *hardware timestamping*). Фізичний рівень Ethernet (PHY) або контролер MAC фіксує значення високочастотного лічильника в момент проходження преамбули Ethernet-кадру крізь інтерфейс MII/RMII, повністю виключаючи затримки стека TCP/IP, черг ядра Linux та перемикання процесів.

Головний годинник (англ. *Grandmaster Clock*, зазвичай GPS-приймач) розсилає повідомлення `Sync` та `Follow_Up`, а підпорядковані вузли періодично відправляють запит `Delay_Req` та отримують `Delay_Resp`.

### 3. Мережевий протокол SNTP (RFC 4330)

Для наземних станцій та мобільних додатків поверх стандартних каналів Wi-Fi та Ethernet застосовують SNTP (англ. *Simple Network Time Protocol*). Він базується на обміні UDP-пакетами з серверами стратуму 1/2 через порт 123. Точність SNTP обмежена мілісекундним діапазоном (1–10 мс) через асиметрію бездротового середовища та затримки програмних сокетів.

## Синхронізація MAVLink: розрахунок RTT та зміщення годинника

У дронових та робототехнічних системах базовим каналом зв'язку між автопілотом і зовнішнім світом є протокол MAVLink. Для узгодження часу в ньому передбачено два комплементарні повідомлення:

1. `SYSTEM_TIME` (Повідомлення #2): передає абсолютний настінний час Unix в мікросекундах (`time_unix_usec`) та час із моменту старту системи (`time_boot_ms`). Використовується для синхронізації календаря та створення файлів логів.
2. `TIMESYNC` (Повідомлення #111): високочастотний протокол пінг-понгу для динамічного вимірювання зміщення шкал (англ. *Clock Offset*) та часу кругового обігу пакетів (англ. *Round-Trip Time*, RTT).

### Протокол чотирьох міток часу (Two-Way Time Transfer)

Синхронізація базується на симетричному обміні часовими мітками між Клієнтом (наприклад, наземною станцією) та Сервером (польотним контролером).

```
Клієнт (GCS)                                            Сервер (FC)
    │                                                        │
    │  t₁ (відправка запиту: tc1 = 0, ts1 = t₁)             │
    ├───────────────────────────────────────────────────────►│  t₂ (прийом запиту)
    │                                                        │  t₃ (відправка відповіді: tc1 = t₁, ts1 = t₂)
    │◄───────────────────────────────────────────────────────┤
    │  t₄ (прийом відповіді)                                 │
    │                                                        │
```

Послідовність роботи протоколу:
1. Клієнт фіксує поточний локальний монотонний час `t₁` і відправляє повідомлення `TIMESYNC`, де поле `tc1` встановлено в `0`, а поле `ts1` містить `t₁` (у наносекундах або мікросекундах).
2. Сервер приймає пакет у момент власного монотонного часу `t₂`.
3. Сервер негайно формує відповідь `TIMESYNC`, де повертає початкову мітку клієнта `tc1 = t₁`, а у поле `ts1` записує власний час прийому `t₂`. Пакет відправляється в момент `t₃` (якщо обробка миттєва, `t₃ ≈ t₂`).
4. Клієнт отримує відповідь у момент власного локального часу `t₄`.

![Двосторонній обмін мітками часу: розрахунок RTT і зміщення годинника](/root/course/embedded/spilna-shkala-chasu/img/ptp-mavlink-four-timestamps.svg)
*Двосторонній обмін чотирма мітками часу за схемою MAVLink TIMESYNC та PTP. Виведення формул RTT, Offset та вплив асиметрії каналу зв'язку.*

### Математичне виведення RTT та зміщення (Offset)

Позначимо зміщення годинника сервера відносно клієнта як `θ` (англ. *offset*), а час проходження сигналу в прямому та зворотному напрямках — як `d_fwd` та `d_rev`.

Зв'язок між мітками часу виражається рівняннями:

```
t₂ = t₁ + d_fwd + θ
t₄ = t₃ + d_rev - θ
```

Час кругового обігу сигналу (RTT, `δ`) без урахування часу обробки на сервері дорівнює:

```
δ = (t₄ - t₁) - (t₃ - t₂)
```

Якщо сервер формує відповідь у тому самому перериванні, час обробки наближається до нуля (`t₃ ≈ t₂`), і формула набуває спрощеного вигляду:

```
δ = t₄ - t₁
```

Припускаючи, що канал зв'язку є симетричним (`d_fwd = d_rev = δ / 2`), знаходимо оцінку зміщення годинника `θ`:

```
θ = t₂ - t₁ - d_fwd               [визначення затримки прямого каналу: t₂ = t₁ + d_fwd + θ]
  = t₂ - t₁ - δ / 2               [припущення симетрії затримок: d_fwd = δ / 2]
  = t₂ - t₁ - (t₄ - t₁) / 2       [підстановка RTT для миттєвої відповіді: δ = t₄ - t₁]
  = t₂ - (t₁ + t₄) / 2            [зведення подібних доданків: -t₁ + t₁/2 = -t₁/2]
```

Для загального випадку з ненульовим часом обробки на сервері `(t₃ > t₂)` формула розрахунку зміщення має вигляд:

```
θ = ((t₂ - t₁) + (t₃ - t₄)) / 2
```

### Пастка асиметрії каналу зв'язку

Головне вразливе місце протоколу двостороннього обміну мітками часу — припущення про симетрію затримок. Якщо прямий канал має затримку `d_fwd`, а зворотний — `d_rev = d_fwd + Δd`, похибка обчислення зміщення становить:

```
θ_calculated = θ_true + Δd / 2
```

В ефірі швидкість поширення радіохвиль є строго однаковою в обидва боки. Проте в цифрових радіомодемах (наприклад, Sik Telemetry, ELRS, Wi-Fi) асиметрія виникає через різний розмір пакетів, черги буферизації та механізм повторних спроб канального рівня (MAC retransmissions). Якщо пакет запиту пройшов за 10 мс, а відповідь затрималася в черзі модема на 50 мс (`Δd = 40 мс`), розраховане зміщення годинника зміститься від істинного значення на `20 мс`.

Саме тому сирі вимірювання `TIMESYNC` ніколи не застосовують напряму: їх пропускають крізь робастний статистичний фільтр.

## Вшивання таймкодів у відеокадри: H.264 SEI Metadata

Найскладніший елемент єдиної шкали часу — прив'язка відеоряду. Відеопотік не є набором ізольованих картинок: це стиснена послідовність NAL-юнітів (англ. *Network Abstraction Layer*), що складається з ключових IDR-кадрів (I-frames) та різницевих кадрів (P/B-frames).

Якщо таймкод накладати як графічний текст на пікселі кадру (OSD, англ. *On-Screen Display*), його неможливо автоматично прочитати в коді без ненадійного та ресурсомісткого оптичного розпізнавання символів (OCR). Єдине професійне інженерне рішення — вбудовування бінарних метаданих безпосередньо в структуру стисненого відеопотоку H.264/H.265 за допомогою повідомлень SEI.

```
NAL Unit 7: SPS ──► NAL Unit 8: PPS ──► NAL Unit 6: SEI ──► NAL Unit 5: IDR Slice
                                       ┌────────────────┐
                                       │ UUID (16 байт) │
                                       │ UTC Timestamp  │
                                       │ Monotonic Time │
                                       │ IMU Quaternion │
                                       └────────────────┘
```

### Анатомія SEI User Data Unregistered

Стандарт H.264 (ITU-T H.264 / ISO/IEC 14496-10) визначає спеціальний тип NAL-юніта — `NAL_UNIT_TYPE_SEI` (`значення 6`). Усередині нього поле `payloadType = 5` відповідає типу `user_data_unregistered` (незареєстровані користувацькі дані).

Будь-який стандартний відеоплеєр (VLC, браузер, GStreamer), зустрівши NAL типу 6 із типом навантаження 5, просто пропускає його й безперешкодно декодує наступний відеокадр. Натомість спеціалізований аналізатор витягує з цього блоку точні параметри польоту, що відповідають моменту відкриття затвора камери.

![Конвеєр відеопотоку та вшивання метаданих SEI у кадри H.264](/root/course/embedded/spilna-shkala-chasu/img/video-sei-pipeline.svg)
*Конвеєр формування відеопотоку. Апаратний сигнал FSYNC фіксує точний час початку експозиції сенсора, енкодер упаковує бінарну структуру телеметрії в NAL-блок SEI (тип 6), а плеєр на землі зіставляє відео з логом польоту.*

Структура бінарного корисного навантаження SEI кадру:

```
+──────────────────────────────────────────────────────────────────────────────────+

|  timestamp_utc_us       | uint64_t     | 8 B     | Абсолютний час UTC (мкс)      |

|  exposure_duration_us   | uint32_t     | 4 B     | Тривалість експозиції (мкс)   |
|  frame_sequence         | uint32_t     | 4 B     | Порядковий номер кадру        |
|  attitude_quaternion[4] | float[4]     | 16 B    | Орієнтація дрона (qw,qx,qy,qz)|
|  geo_lat_lon_alt[3]     | int32/int32/f| 12 B    | Широта, довгота, висота       |
```

### Апаратний строб сенсора (FSYNC / Strobe)

Енкодер SoC не знає точного моменту, коли фотони потрапили на кремнієву матрицю. Процес зчитування пікселів сенсора (Rolling Shutter) триває від 10 до 30 мс, після чого кадр передається по шині MIPI CSI-2 в буфер пам'яті.

Щоб досягти мікросекундної точності, використовують лінію `STROBE` або `FSYNC` камери. На початку експозиції першого рядка матриці сенсор генерує апаратний логічний перепад на виводі `STROBE`. Цей імпульс заведено на вхід апаратного захоплення таймера мікроконтролера. 

У момент імпульсу мікроконтролер записує поточний час `t_sensor_trigger` та інтерполює значення кутів орієнтації з буфера IMU (що опитується на частоті 400–1000 Гц). Коли кадр доходить до енкодера, ці дані вшиваються в SEI-блок саме цього кадру.

## Алгоритм робастної фільтрації: Min-RTT, оцінка дрейфу та Slewing

Сирі спостереження зміщення часу `(Offset_i, RTT_i)`, отримані через MAVLink або PTP, містять викиди через мережевий джитер. Пряме застосування сирого зміщення призведе до постійних стрибків системного часу. Для забезпечення надійної синхронізації застосовують чотириетапний конвеєр обробки.

![Архітектура робастного фільтра зміщення часу](/root/course/embedded/spilna-shkala-chasu/img/timesync-filter-architecture.svg)
*Архітектура фільтрації зміщення часу. Відбір вибірок за мінімальним RTT у ковзному вікні, згладжування фази фільтром EWMA та плавне підтягування годинника (Slewing).*

### 1. Фільтрація за мінімальним RTT (Min-RTT Filter)

Головний принцип теорії синхронізації розподілених систем (алгоритм Крістіана, англ. *Cristian's algorithm*): **що менший час кругового обігу RTT, то менша затримка в чергах і то ближчий канал до ідеальної симетрії**.

Фільтр підтримує кільцевий буфер останніх `K` успішних вимірювань (типово `K = 16` або `32`). Серед усіх зразків у вікні обирається не середнє арифметичне, а вибірка з мінімальним значенням `RTT_min`:

```
RTT_min = min(RTT_1, RTT_2, ..., RTT_K)
θ_best  = Offset_idx_of_min_RTT
```

Вибірка з мінімальним RTT пройшла крізь стек мережі в момент найменшої завантаженості черг, тому її похибка асиметрії `ε` мінімальна.

### 2. Експоненційне згладжування фази (EWMA)

Після вибору найкращого значення `θ_best` результат фільтрують експоненційним ковзним середнім (англ. *Exponentially Weighted Moving Average*, EWMA):

```
θ_filtered(k) = (1 - α) · θ_filtered(k-1) + α · θ_best
```

Коефіцієнт згладжування `α` обирають у діапазоні `0.05 ... 0.15`. Це забезпечує повільну реакцію на випадкові поодинокі збурення й надійне відстеження постійного зсуву.

### 3. Оцінка дрейфу частоти (Clock Skew)

Різниця частот генераторів призводить до того, що зміщення лінійно зростає з часом зі швидкістю `ppm`:

```
dθ / dt = Skew
```

Фільтр обчислює нахил прямої (лінійну регресію) за вибірками у вікні. Знаючи поточний дрейф `Skew`, клієнт може екстраполювати поточний час сервера навіть у проміжках між прийомом пакетів `TIMESYNC`:

```
t_server_est(t_now) = t_now + θ_filtered + Skew · (t_now - t_last_sync)
```

### 4. Плавне підтягування (Slewing) проти миттєвого стрибка (Stepping)

Існує дві стратегії корекції локального годинника:

1. **Миттєвий стрибок (Stepping)**: прямий запис нового значення в лічильник часу `t_local = t_new`. 
   > [!CAUTION]
   > Стрибок годинника назад під час польоту смертельно небезпечний для алгоритмів керування! Якщо регулятор обчислює крок інтегрування як `dt = t_now - t_prev`, переведення годинника назад на 10 мс призведе до того, що `dt` стане від'ємним числом або перетвориться на гігантське додатне число у беззнаковій арифметиці `uint32_t`. Інтегратор PID-регулятора видасть миттєвий максимальний стрибок на сервоприводи, що спричинить зрив потоку та катастрофу.

2. **Плавне підтягування (Slewing)**: темп ходу локального годинника тимчасово змінюють на невелику фіксовану величину (наприклад, `±500 ppm` або `±0.5 мс/с`), поки похибка `θ` не компенсується повністю. При цьому похідна часу завжди залишається строго додатною: `dt/dt_real > 0`.

Правило застосування: **Стрибок (Stepping) дозволений лише один раз під час ініціалізації системи при холодному старті, якщо розбіжність перевищує 1 секунду. Усі наступні корекції виконуються виключно плавним підтягуванням (Slewing)**.

## Повна бібліотека фільтрації зміщення часу на C та C++

Нижче наведено промислову реалізацію клієнта синхронізації часу, що здійснює відбір вибірок за мінімальним RTT, згладжування зміщення та монотонний перерахунок шкал.

```c
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

#define TIMESYNC_WINDOW_SIZE 16
#define TIMESYNC_MAX_RTT_US  200000ULL /* 200 мс максимальний прийнятний RTT */
#define TIMESYNC_ALPHA_FP    10        /* Коефіцієнт згладжування 0.10 у фіксованій комі (x100) */

typedef struct {
    uint64_t t1_client_us;
    uint64_t t2_server_us;
    uint64_t t3_server_us;
    uint64_t t4_client_us;
    int64_t  offset_us;
    uint64_t rtt_us;
    bool     valid;
} timesync_sample_t;

typedef struct {
    timesync_sample_t samples[TIMESYNC_WINDOW_SIZE];
    size_t   head;
    size_t   count;
    int64_t  filtered_offset_us;
    int64_t  skew_ppm_x1000;      /* Дрейф частоти в ppm, помножений на 1000 */
    uint64_t last_sync_local_us;
    uint64_t min_rtt_us;
    bool     is_synchronized;
} timesync_filter_t;

void timesync_filter_init(timesync_filter_t *filter) {
    if (!filter) return;
    filter->head = 0;
    filter->count = 0;
    filter->filtered_offset_us = 0;
    filter->skew_ppm_x1000 = 0;
    filter->last_sync_local_us = 0;
    filter->min_rtt_us = UINT64_MAX;
    filter->is_synchronized = false;

    for (size_t i = 0; i < TIMESYNC_WINDOW_SIZE; ++i) {
        filter->samples[i].valid = false;
    }
}

bool timesync_filter_update(timesync_filter_t *filter, 
                            uint64_t t1_us, uint64_t t2_us, 
                            uint64_t t3_us, uint64_t t4_us) {
    if (!filter || t4_us < t1_us) return false;

    /* Обчислення RTT та часу обробки */
    uint64_t proc_time_us = (t3_us >= t2_us) ? (t3_us - t2_us) : 0;
    uint64_t total_roundtrip = t4_us - t1_us;
    
    if (total_roundtrip < proc_time_us) return false;
    uint64_t rtt_us = total_roundtrip - proc_time_us;

    /* Відкидання аномальних сплесків затримки мережі */
    if (rtt_us > TIMESYNC_MAX_RTT_US) {
        return false;
    }

    /* Зміщення: θ = ((t2 - t1) + (t3 - t4)) / 2 */
    int64_t diff1 = (int64_t)t2_us - (int64_t)t1_us;
    int64_t diff2 = (int64_t)t3_us - (int64_t)t4_us;
    int64_t raw_offset_us = (diff1 + diff2) / 2;

    /* Запис у кільцевий буфер */
    timesync_sample_t *s = &filter->samples[filter->head];
    s->t1_client_us = t1_us;
    s->t2_server_us = t2_us;
    s->t3_server_us = t3_us;
    s->t4_client_us = t4_us;
    s->offset_us = raw_offset_us;
    s->rtt_us = rtt_us;
    s->valid = true;

    filter->head = (filter->head + 1) % TIMESYNC_WINDOW_SIZE;
    if (filter->count < TIMESYNC_WINDOW_SIZE) {
        filter->count++;
    }

    /* Пошук вибірки з мінімальним RTT у поточному вікні */
    uint64_t best_rtt = UINT64_MAX;
    int64_t  best_offset = 0;

    for (size_t i = 0; i < TIMESYNC_WINDOW_SIZE; ++i) {
        if (filter->samples[i].valid && filter->samples[i].rtt_us < best_rtt) {
            best_rtt = filter->samples[i].rtt_us;
            best_offset = filter->samples[i].offset_us;
        }
    }

    filter->min_rtt_us = best_rtt;

    /* Фільтрація EWMA */
    if (!filter->is_synchronized) {
        /* Перше захоплення: ініціалізація значенням найкращої вибірки */
        filter->filtered_offset_us = best_offset;
        filter->is_synchronized = true;
    } else {
        /* Плавне згладжування фази */
        int64_t delta = best_offset - filter->filtered_offset_us;
        filter->filtered_offset_us += (delta * TIMESYNC_ALPHA_FP) / 100;
    }

    filter->last_sync_local_us = t4_us;
    return true;
}

uint64_t timesync_local_to_server_us(const timesync_filter_t *filter, uint64_t local_now_us) {
    if (!filter || !filter->is_synchronized) {
        return local_now_us;
    }

    /* Базове зміщення */
    int64_t res = (int64_t)local_now_us + filter->filtered_offset_us;

    /* Екстраполяція дрейфу, якщо відомий skew */
    if (filter->last_sync_local_us > 0 && local_now_us > filter->last_sync_local_us) {
        uint64_t dt_us = local_now_us - filter->last_sync_local_us;
        int64_t skew_correction = (int64_t)((dt_us * filter->skew_ppm_x1000) / 1000000000LL);
        res += skew_correction;
    }

    return (res > 0) ? (uint64_t)res : 0ULL;
}

uint64_t timesync_server_to_local_us(const timesync_filter_t *filter, uint64_t server_time_us) {
    if (!filter || !filter->is_synchronized) {
        return server_time_us;
    }

    int64_t res = (int64_t)server_time_us - filter->filtered_offset_us;
    return (res > 0) ? (uint64_t)res : 0ULL;
}
```

```cpp
#include <array>
#include <chrono>
#include <cstdint>
#include <limits>
#include <optional>
#include <algorithm>

namespace embedded::time {

using namespace std::chrono_literals;

struct TimesyncSample {
    std::chrono::microseconds t1_client{0};
    std::chrono::microseconds t2_server{0};
    std::chrono::microseconds t3_server{0};
    std::chrono::microseconds t4_client{0};
    std::chrono::microseconds offset{0};
    std::chrono::microseconds rtt{0};
    bool valid{false};
};

template <std::size_t WindowSize = 16>
class TimesyncFilter {
public:
    static constexpr std::chrono::microseconds MAX_VALID_RTT = 200ms;
    static constexpr double ALPHA = 0.10;

    constexpr TimesyncFilter() noexcept {
        reset();
    }

    void reset() noexcept {
        head_ = 0;
        count_ = 0;
        filtered_offset_ = std::chrono::microseconds{0};
        last_sync_local_ = std::chrono::microseconds{0};
        min_rtt_ = std::chrono::microseconds::max();
        synchronized_ = false;
        samples_.fill(TimesyncSample{});
    }

    [[nodiscard]] bool update(std::chrono::microseconds t1,
                              std::chrono::microseconds t2,
                              std::chrono::microseconds t3,
                              std::chrono::microseconds t4) noexcept {
        if (t4 < t1) {
            return false;
        }

        const auto proc_time = (t3 >= t2) ? (t3 - t2) : std::chrono::microseconds{0};
        const auto total_roundtrip = t4 - t1;

        if (total_roundtrip < proc_time) {
            return false;
        }

        const auto rtt = total_roundtrip - proc_time;
        if (rtt > MAX_VALID_RTT) {
            return false;
        }

        const auto diff1 = t2 - t1;
        const auto diff2 = t3 - t4;
        const auto raw_offset = (diff1 + diff2) / 2;

        samples_[head_] = TimesyncSample{
            .t1_client = t1,
            .t2_server = t2,
            .t3_server = t3,
            .t4_client = t4,
            .offset = raw_offset,
            .rtt = rtt,
            .valid = true
        };

        head_ = (head_ + 1) % WindowSize;
        if (count_ < WindowSize) {
            count_++;
        }

        // Пошук вибірки з мінімальним RTT
        auto best_rtt = std::chrono::microseconds::max();
        auto best_offset = std::chrono::microseconds{0};

        for (const auto& s : samples_) {
            if (s.valid && s.rtt < best_rtt) {
                best_rtt = s.rtt;
                best_offset = s.offset;
            }
        }

        min_rtt_ = best_rtt;

        if (!synchronized_) {
            filtered_offset_ = best_offset;
            synchronized_ = true;
        } else {
            const auto delta = best_offset - filtered_offset_;
            filtered_offset_ += std::chrono::duration_cast<std::chrono::microseconds>(delta * ALPHA);
        }

        last_sync_local_ = t4;
        return true;
    }

    [[nodiscard]] std::chrono::microseconds to_server_time(std::chrono::microseconds local_now) const noexcept {
        if (!synchronized_) {
            return local_now;
        }
        return local_now + filtered_offset_;
    }

    [[nodiscard]] std::chrono::microseconds to_local_time(std::chrono::microseconds server_now) const noexcept {
        if (!synchronized_) {
            return server_now;
        }
        return server_now - filtered_offset_;
    }

    [[nodiscard]] bool is_synchronized() const noexcept {
        return synchronized_;
    }

    [[nodiscard]] std::chrono::microseconds filtered_offset() const noexcept {
        return filtered_offset_;
    }

    [[nodiscard]] std::chrono::microseconds min_rtt() const noexcept {
        return min_rtt_;
    }

private:
    std::array<TimesyncSample, WindowSize> samples_{};
    std::size_t head_{0};
    std::size_t count_{0};
    std::chrono::microseconds filtered_offset_{0};
    std::chrono::microseconds last_sync_local_{0};
    std::chrono::microseconds min_rtt_{std::chrono::microseconds::max()};
    bool synchronized_{false};
};

} // namespace embedded::time
```

## Пастки практики та крайові випадки

Побудова єдиної шкали часу в польових умовах сповнена тонких нюансів, які рідко згадуються в теоретичних підручниках, але щодня ламають роботу реальних систем.

### 1. Високосна секунда (Leap Second): GPS проти UTC

Міжнародна служба обертання Землі періодично додає або віднімає «високосну секунду» (англ. *leap second*), щоб узгодити астрономічний час обертання планети UT1 з атомною шкалою TAI. 

- Шкала **GPS-часу** (англ. *GPS Time*) є безперервною атомною шкалою без стрибків, відлік якої розпочато 6 січня 1980 року.
- Шкала **UTC** містить регулярні стрибки на `±1 секунду`.

Станом на 2026 рік різниця між шкалою GPS та шкалою UTC становить рівно **18 секунд** (GPS випереджає UTC). Якщо наземна станція працює за системним часом UTC, а бортовий контролер використовує сирий час GPS без урахування зміщення високосних секунд, уся телеметрія виявиться зсунутою рівно на 18 секунд. 

> [!IMPORTANT]
> Прошивка повинна зчитувати поле `leap_seconds` із бінарного навігаційного повідомлення GNSS (наприклад, пакет `UBX-NAV-TIMEUTC`) і явно транслювати GPS-час у UTC перед записом у бінарні логи ULog та відеопотік SEI.

### 2. Переповнення беззнакових таймерів (Timer Rollover)

У мікроконтролерах системний таймер часто працює як 32-бітний беззнаковий лічильник мікросекунд (`uint32_t`):

```
Максимальний час = 2³² - 1 мікросекунд
                 = 4 294 967 295 мкс
                 ≈ 4294.96 секунди (71.58 хвилини)
```

Через кожні 71.5 хвилини 32-бітний мікросекундний лічильник скидається в 0. Якщо обчислювати різницю часу як звичайне порівняння чисел із плаваючою комою, політ на 72-й хвилині зазнає критичного збою. 

Проте беззнакова модульна арифметика мови C/C++ гарантує коректність різниці за умови використання одного й того самого цілочисельного беззнакового типу:

:::tabs
```c
uint32_t t_prev = 4294967200U; /* За 95 мкс до переповнення */
uint32_t t_now  = 50U;          /* Через 50 мкс після переповнення */
uint32_t dt = t_now - t_prev;   /* Рівно 145 мкс! Модульне переповнення враховано */
```
```cpp
#include <cstdint>
#include <chrono>

using namespace std::chrono_literals;

// Беззнакове модульне віднімання переповнення
constexpr std::uint32_t t_prev = 4'294'967'200U;
constexpr std::uint32_t t_now  = 50U;
constexpr std::uint32_t dt_raw = t_now - t_prev; // Рівно 145 мкс
const auto dt = std::chrono::microseconds(dt_raw);
```
:::

Для збереження часових шкал тривалих місій у пам'яті завжди використовують 64-бітні змінні (`uint64_t` у мікросекундах). Лічильник `uint64_t` переповнюється лише через 584 942 роки безперервної роботи.

### 3. Режими енергозбереження Wi-Fi (DTIM Sleep)

Якщо телеметрія передається через стандартний Wi-Fi адаптер, операційна система може вводити радіомодуль у стан сну Power Save Mode (PSM). Передавач прокидається лише під час надходження сигнальних маяків точки доступу (англ. *Delivery Traffic Indication Map*, DTIM).

Це створює штучну періодичну затримку зворотного каналу на 100–300 мс (інтервал DTIM-маяка), роблячи канал критично асиметричним. Для безпілотних систем керування енергозбереження бездротових інтерфейсів на боці станції та дрона обов'язково вимикають:

```bash
sudo iwconfig wlan0 power off
```

Коли просторовий кватерніон орієнтації, координата GNSS, вибірка струму двигуна та кадр оптичної камери прив'язані до спільної шкали з похибкою менш ніж 1 мс, оператор бачить об'єктивну фізичну реальність польоту, комп'ютерний зір працює без розмиття просторових оцінок, а будь-яка аномалія розшифровується за секунди.
