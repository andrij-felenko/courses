# 📜 Від спагеті 8051 до модульних стандартів: як народжувалася шарувата архітектура прошивок

Цей історичний екскурс розкриває, чому вбудоване програмування відмовилося від монолітного стилю з прямим записом у регістри та як інженерна криза переносності 1990-х років сформувала сучасні стандарти шаруватої архітектури.

На світанку мікроконтролерної ери у 1970-х та 1980-х роках апаратні обмеження не залишали простору для абстракцій. Легендарний 8-бітний чип Intel 8051 (випущений 1980 року) мав лише 128 байтів оперативної пам'яті (RAM) та 4 кілобайти маскового ПЗП (ROM). Програми писалися мовою асемблера або першими діалектами вбудованого C (наприклад, Keil C51). Кожен виклик підпрограми через стек забирав дорогоцінні байти пам'яті даних, а непрямий виклик через покажчик на функцію вимагав додаткових машинних циклів, яких бракувало при тактовій частоті кварца 12 МГц (де одна машинна інструкція виконувалася за 12 тактів, тобто рівно 1 мікросекунду).

У таких умовах єдино можливим інженерним підходом був монолітний лінійний код. Розробник безпосередньо звертався до апаратних регістрів через магічні адреси спеціальних регістрів функцій (Special Function Registers, SFR):

:::tabs
```c
// Типовий монолітний C51 на мікроконтролері Intel 8051
void main(void) {
    TMOD = 0x20;    // Таймер 1 у 8-бітному автоперезавантаженні
    TH1 = 0xFD;     // Швидкість 9600 бод при кварці 11.0592 МГц
    SCON = 0x50;    // Режим 1, 8-бітний UART, увімкнено прийом
    TR1 = 1;        // Запуск таймера 1
    
    while (1) {
        if (RI) {
            RI = 0;
            P1 = SBUF; // Прямий запис прийнятого байта в порт вводу-виводу
        }
    }
}
```
```cpp
// Еквівалентний прямий доступ у стилі низькорівневого C++
namespace mcu::sfr {
    inline volatile uint8_t& tmod = *reinterpret_cast<uint8_t*>(0x89);
    inline volatile uint8_t& th1  = *reinterpret_cast<uint8_t*>(0x8D);
    inline volatile uint8_t& scon = *reinterpret_cast<uint8_t*>(0x98);
    inline volatile uint8_t& p1   = *reinterpret_cast<uint8_t*>(0x90);
    inline volatile uint8_t& sbuf = *reinterpret_cast<uint8_t*>(0x99);
}

int main() {
    using namespace mcu::sfr;
    tmod = 0x20;
    th1  = 0xFD;
    scon = 0x50;
    
    while (true) {
        if (scon & 0x01) { // Біт RI (Receive Interrupt)
            scon &= ~0x01;
            p1 = sbuf;
        }
    }
}
```
:::

Увесь проєкт складався з одного або двох файлів, де константи апаратної плати, алгоритми обробки сигналів і логіка переривань були нерозривно сплетені в єдиний клубок. Поки розмір коду не перевищував кількох сотень рядків, один розробник міг тримати в голові повну карту пам'яті й часову діаграму роботи процесора.

### Криза 1990-х: вибух складності 32-бітних чипів

На початку 1990-х років технологічний перехід на кремнієві техпроцеси 0.5–0.35 мкм відкрив шлях 16-бітним і 32-бітним мікроконтролерам: Motorola 68332, Hitachi H8/300, а згодом — архітектурі ARM7TDMI. Обсяг флеш-пам'яті на кристалі зріс від кількох кілобайтів до 256–512 КБ, а тактові частоти сягнули 20–60 МГц. 

Разом із продуктивністю зросла складність інтегрованої периферії: мікроконтролери отримали апаратні контролери шин CAN, USB, складної ШІМ із комплементарними виходами для керування двигунами, багатоканальні АЦП із прямим доступом до пам'яті (DMA). Обсяг коду комерційної прошивки перевищив 50 000–100 000 рядків, а над проєктом почали працювати великі команди інженерів.

Монолітний підхід зазнав нищівного фіаско. Проєкти опинилися в глухому куті через три критичні фактори:
1. **Каскадні відмови при зміні заліза**: коли виробник мікроконтролера випускав нову ревізію чипа зі зміненим бітовим полем у таймері або іншою картою переривань, прошивка вимагала тотального переписування. Прямі звернення до регістрів `TIM1->CR1` чи магічні константи масок були розкидані по сотнях функцій бізнес-логіки.
2. **Неможливість модульного тестування**: оскільки бізнес-логіка (наприклад, розрахунок кривої заряду батареї) містила всередині виклики зчитування регістрів конкретного АЦП, код неможливо було скомпілювати та протестувати на комп'ютері розробника (Host PC). Будь-яка перевірка вимагала прошивання фізичної плати та зняття сигналів осцилографом.
3. **Хаос у перериваннях**: відсутність чітких меж між апаратними драйверами та застосунком призводила до того, що розробники запускали важкі обчислення та обмін по шинах безпосередньо всередині обробників переривань (ISR), блокуючи інші критичні процеси системи.

Стало очевидно: вбудованому програмуванню терміново потрібна структурна дисципліна.

### Народження стандартів: OSEK/VDX, MISRA та AUTOSAR

Першими удар відчули виробники автомобільної електроніки (Automotive). Наприкінці 1990-х років автомобіль середнього класу містив уже понад 30 електронних блоків керування (ECU), об'єднаних шиною CAN. Кожен постачальник писав прошивку у власному пропрієтарному стилі, що робило інтеграцію систем у єдиний автомобіль кошмаром для автоконцернів.

У 1995 році німецький консорціум автовиробників (BMW, Bosch, Daimler-Benz, Volkswagen) та французький VDX об'єдналися у спільну ініціативу **OSEK/VDX** (*Offene Systeme und deren Schnittstellen für die Elektronik im Kraftfahrzeug* — Відкриті системи та інтерфейси для автомобільної електроніки). Вони стандартизували:
- компактну статичну операційну систему реального часу (OSEK OS);
- комунікаційний стек для шини CAN (OSEK COM);
- мережевий менеджмент (OSEK NM).

У 1998 році асоціація британської автоіндустрії випустила першу редакцію правил **MISRA C** (*Motor Industry Software Reliability Association*). Стандарт заборонив неявні перетворення типів, пряму неконтрольовану роботу з покажчиками та вимагав суворої модульності коду й використання закритих заголовків.

Кульмінацією цього руху став альянс **AUTOSAR** (*Automotive Open System Architecture*), заснований у 2003 році. AUTOSAR вперше формально закріпив три фундаментальні шари прошивки:
- **BSW (Basic Software)**: базове програмне забезпечення, що включає драйвери мікроконтролера (MCAL), абстракцію апаратної плати (ECU Abstraction) та системні служби (Services — ОС, діагностика, пам'ять);
- **RTE (Real-Time Environment)**: шар віртуальної шини, що повністю ізолює прикладний код від апаратних викликів за допомогою підходу «порти та інтерфейси»;
- **Application Layer**: програмні компоненти (SWC), що реалізують виключно алгоритми керування (наприклад, роботу ABS або клімат-контролю) і спілкуються виключно через типізовані порти RTE.

Хоча AUTOSAR виявився занадто важким і ресурсоємним для дрібних автономних IoT-пристроїв, його концептуальний поділ на **HAL → BSP → Services → Application** став золотим стандартом у всій інженерії вбудованих систем.

### Революція Cortex-M та стандартизація CMSIS (2008)

Справжнім поворотним моментом для масового ринку мікроконтролерів стала поява сімейства процесорних ядер **ARM Cortex-M** (Cortex-M3 у 2004 році, Cortex-M0/M4 у 2009–2010 роках). 

До появи Cortex-M кожен виробник мікроконтролерів (STMicroelectronics, NXP, Atmel, Texas Instruments) створював власну пропрієтарну архітектуру ядра та власні механізми переривань. Перенесення коду між чипом LPC2148 від NXP та AT91SAM7 від Atmel означало повну заміну асемблерного файлу запуску (`startup.s`), переписування таблиці векторів переривань та зміну коду системного таймера.

У 2008 році корпорація ARM зробила фундаментальний крок — представила стандарт **CMSIS** (*Cortex Microcontroller Software Interface Standard*).

```
┌─────────────────────────────────────────────────────────────┐
│ CMSIS Core: Стандартизовано для всіх Cortex-M               │
│ - Регістри ядра: NVIC, SysTick, MPU, SCB                    │
│ - Функції доступу до інструкцій: __disable_irq(), __WFI()   │
│ - Уніфікована таблиця векторів переривань                   │
├─────────────────────────────────────────────────────────────┤
│ Рівень постачальника кремнію (Silicon Vendor):               │
│ - Структури регістрів периферії: GPIO_TypeDef, SPI_TypeDef  │
│ - Карта пам'яті адрес: RCC_BASE, I2C1_BASE                  │
│ - Бітові маски та зміщення полів регістрів                  │
└─────────────────────────────────────────────────────────────┘
```

CMSIS розділив апаратний рівень на дві строго ізольовані частини:
1. **CMSIS-CORE**: апаратні засоби самого процесорного ядра (системний таймер SysTick, контролер вкладених векторних переривань NVIC, блок захисту пам'яті MPU та спеціальні інструкції асемблера). Ця частина однакова на будь-якому чипі Cortex-M незалежно від вендора.
2. **Device Header**: заголовний файл конкретного виробника, де апаратні регістри зовнішньої периферії описуються як структури C з модифікатором `volatile` та прив'язуються до фіксованих адрес у пам'яті через макроси бази.

Завдяки CMSIS виробники ОС реального часу (FreeRTOS, ThreadX, Zephyr) змогли написати **один універсальний порт планувальника завдань**, який працює на будь-якому чипі Cortex-M без найменших змін у викликах `SysTick_Handler` та `PendSV_Handler`.

### Сучасна парадигма: компоненти, Zephyr та сучасний C++

У 2010–2020-х роках еволюція вбудованої архітектури перейшла на рівень абстракцій сучасних мов програмування та декларативного опису апаратури.

З появою операційної системи **Zephyr RTOS** (проєкт під егідою Linux Foundation) у світ вбудованих систем прийшов механізм **Device Tree (DTS)**, запозичений з ядра Linux. Конфігурація підключення сенсорів, призначень пінів і шин описується в окремому текстовому дереві пристроїв, а драйвери зв'язуються з апаратурою автоматично на етапі компіляції. Бізнес-логіка оперує абстрактним покажчиком на `struct device`, навіть не знаючи, чи сенсор BME280 підключений до апаратного I2C1 на ніжках PB6/PB7, чи до програмного емулятора шини на випадкових виводах GPIO.

Паралельно стандарти **C++17/C++20** та мова **Rust** принесли концепцію **абстракцій нульової вартості** (Zero-Cost Abstractions). Шаблони, концептури (Concepts) та статичний поліморфізм дозволяють створювати суворі шаруваті межі між модулями без витрати оперативної пам'яті на таблиці віртуальних методів (`vtable`) і без затримок непрямих викликів.

Історія вбудованої архітектури довела головний закон: **прямий доступ до регістрів є виправданим лише всередині ізольованого HAL-модуля**. Будь-яке змішування апаратних викликів із бізнес-логікою неминуче перетворює проєкт на спагеті, яке гине при першій же зміні апаратної ревізії плати.
