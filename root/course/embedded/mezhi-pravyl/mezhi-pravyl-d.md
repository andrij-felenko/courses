Автономний інспекційний ровер масою 18 кг рухається заводським периметром зі швидкістю 2.2 м/с під керуванням набору з двадцяти ретельно вивірених інженерних правил `IF-THEN`. На полігоні в штиль зі свіжим акумулятором машина бездоганно долає перешкоди, зупиняється перед воротами й знижує швидкість на поворотах. Але в реальному виїзді трапляється потрійне збурення: порив бокового вітру 12 м/с штовхає апарат убік якраз у момент, коли напруга 4S-батареї просідає нижче критичних 13.8 В, а лідар виявляє металеву огорожу за 3.8 метра попереду. Правило обходу перешкоди вимагає негайного різкого довороту ліворуч на максимальній кутовій швидкості; правило захисту батареї примусово обмежує струм моторів до 40% номіналу для збереження осередків; а правило утримання курсу намагається компенсувати знос додаванням газу в правий борт.

У підсумку система застрягає в катастрофічному конфлікті: знижений струм не дає створити потрібний момент повороту проти вітру, апарат не встигає змінити курс і продовжує нестися на огорожу. Рушій рішень починає брязкати між гілками `EVADE_OBSTACLE` та `CONSERVE_POWER` на частоті 20 Гц, розгойдуючи сервоприводи, марно висаджуючи залишки міліампер-годин у високочастотні стрибки струму й завершуючи місію ударом об паркан.

Ця аварія — не помилка калібрування окремого коефіцієнта. Це прояв фундаментальної інженерної стіни, у яку впирається будь-яка система, побудована виключно на дискретних правилах та скінченних автоматах умов. Правила бездоганно захищають окремі межі, але стають сліпими й небезпечними, коли потрібно керувати неперервним рухом у багатовимірному просторі зі зв'язаними фізичними обмеженнями.

## Комбінаторний вибух простору станів

Головна причина, чому системи дискретних правил втрачають надійність зі зростанням складності апарата, полягає в арифметиці розмірності простору станів.

Якщо система оперує `N` незалежними бінарними прапорцями (наприклад: `is_obstacle_near`, `is_battery_low`, `is_gps_valid`, `is_rc_lost`), кількість можливих унікальних конфігурацій становить `2^N`. Для чотирьох змінних це всього 16 комбінацій — таку таблицю істинності розробник легко тримає в голові й може повністю покрити модульними тестами. Але реальний фізичний світ складається не з бінарних прапорців, а з неперервних величин: дистанції, швидкості, напруги, струму, кута нахилу, поривів вітру, температури силових ключів.

Щоб застосувати до неперервної величини правило `IF-THEN`, інженер змушений її **дискретизувати** — розбити на скінченну кількість діапазонів або квантів (наприклад, дистанція: «критично близько», «близько», «середня», «вільно»; батарея: «критична», «низька», «номінальна», «повна»). Якщо кожну з `N` змінних розбити на `k` квантованих рівнів, загальна кількість можливих станів середовища зростає за експонентою:

```
S = k^N
```

Порахуймо реальний масштаб для невеликого безпілотного апарата. Нехай на борту враховуються лише вісім ключових фізичних параметрів, кожен із яких розбито лише на п'ять інтервалів:

```
N = 8     (дистанція до перешкоди, швидкість руху, напруга акумулятора,
           струм споживання, кут нахилу, швидкість вітру, якість навігації, кут до цілі)
k = 5     (п'ять градацій на кожну величину)

S = 5^8 = 390 625 унікальних станів
```

![Комбінаторний вибух простору станів k^N і неможливість ручного покриття](/root/course/embedded/mezhi-pravyl/img/combinatorial-explosion.svg)
*Зростання кількості станів при збільшенні вимірів системи. Навіть детальна база з кількох сотень ручних правил покриває менше одного відсотка можливих фізичних конфігурацій. Решта 99% станів потрапляють у непередбачені комбінації та дефолтні гілки, створюючи приховані зони аварій.*

Щоб система поводилася детерміновано в кожній точці свого робочого діапазону, інженер мав би явно прописати поведінку для майже чотирьохсот тисяч ситуацій. На практиці ж розробник чи команда здатні вручну написати, обговорити та верифікувати від 100 до 300 правил. 

Це означає, що **понад 99.9% реального простору станів лишаються непокритими явними правилами**. Вони звалюються в гілки за замовчуванням (`else`), неявні пріоритети операторів або випадкові збіги умов. Коли апарат потрапляє в один із таких неописаних «темних кутів» багатовимірного простору, його поведінка перестає бути результатом свідомого проєктування — вона стає побічним ефектом того, у якому порядку компілятор або інтерпретатор обчислює вкладені блоки `if-else`.

### Зв'язаність фізичних змінних проти припущення про незалежність

Найбільша омана при створенні правил полягає в неявному припущенні, що змінні в умовах `IF-THEN` можна аналізувати окремо. У реальній динамічній системі всі фізичні канали жорстко зв'язані між собою через закони механіки та електротехніки:

1. **Кінематичний зв'язок:** Диференційний поворот колісної платформи або рискання мультикоптера вимагає створення різниці тяги між бортами чи пропелерами. Це неминуче споживає спільний струмовий бюджет і відбирає потужність у поздовжнього руху.
2. **Електромеханічний зв'язок:** Напруга на клемах літієвого акумулятора під навантаженням описується моделлю з внутрішнім опором: `V_term = E_emf − I_total · ESR`. Спроба додати струм для маневру обходу перешкоди збільшує `I_total`, що негайно просаджує `V_term` і активує правило захисту батареї.
3. **Аеродинамічний зв'язок:** Боковий вітер створює силу дрейфу, для компенсації якої апарат мусить іти з кутом випередження (крабом). Це збільшує лобовий опір, вимагає більшої тяги для утримання швидкості й швидше виснажує батарею.

Спроба «дописати правила для всіх комбінацій» призводить до замкненого кола. Додавання нового правила для обробки рідкісного поєднання (наприклад, «якщо батарея низька, але вітер попутний, то дозволити вищу швидкість») вимагає перегляду всіх уже наявних правил, щоб уникнути конфліктів. Детально про те, як ця криза поховала першу хвилю промислового штучного інтелекту в 1980-х роках, розповідає [історичний екскурс про крах експертних систем та архітектуру сабсампшн](root:embedded/mezhi-pravyl/hist-subsumption-and-expert-systems.md).

## Крихкість правил і катастрофа накладання збурень

Друга фундаментальна вада систем на правилах — їхня **крихкість** (*brittleness*). На відміну від неперервного регулятора, який плавно масштабує зусилля пропорційно помилці, дискретне правило розтинає простір станів жорсткою гіперплощиною.

Розгляньмо типову охоронну умову в коді автопілота:

:::tabs
```c
if (obstacle_distance < 2.0f && battery_voltage > 14.0f) {
    execute_evasive_turn();
} else if (battery_voltage <= 14.0f) {
    engage_power_saving();
}
```
```cpp
if (obstacle_distance < 2.0f && battery_voltage > 14.0f) {
    motion_controller.execute_evasive_turn();
} else if (battery_voltage <= 14.0f) {
    power_manager.engage_power_saving();
}
```
:::

У цій конструкції закладено дві приховані міни:

1. **Гранична гіперчутливість:** Якщо дистанція становить 1.99 м, а напруга 14.01 В — система виконує енергійний обхід. Якщо ж через шум АЦП напруга на наступному такті виміряна як 13.99 В при тій самій дистанції 1.99 м — логіка миттєво перемикається на режим економії, скидаючи кутову швидкість і спрямовуючи апарат прямо в перешкоду. Дві точки, розділені мілівольтами вимірювального шуму, породжують діаметрально протилежні фізичні дії.
2. **Ізольованість гіпотез розробника:** Кожне правило проєктується під певну ментальну модель типового випадку. Правило обходу перешкоди неявно припускає, що мотори мають повний запас потужності для створення моменту. Правило економії енергії неявно припускає, що простір довкола вільний для плавного дрейфу. Коли ці фактори накладаються одночасно, жодне з ізольованих правил не володіє повною картиною фізики процесу.

![Крихкість ізольованих правил при накладанні збурень у реальному полі](/root/course/embedded/mezhi-pravyl/img/rule-brittleness-traps.svg)
*Порівняння поведінки на правилах в ідеальних умовах та при накладанні факторів. На стенді ізольоване правило обходу успішно повертає машину. У реальному полі поєднання бокового вітру, обмеження струму та геометрії перешкоди призводить до зриву керування та зіткнення через взаємну нейтралізацію команд.*

### Механіка брязкання (Chattering) та автоколивань

Коли фізичні контури стикаються з дискретними перемиканнями на межах правил, виникає явище **брязкання (chattering)** або **граничних циклів (limit cycles)**:

* На такті `k` спрацьовує правило `A` («Повернути вліво від лівої межі геозони»).
* Дія правила зміщує апарат праворуч, де на такті `k+1` сенсор фіксує перешкоду й активує правило `B` («Повернути вправо від стіни»).
* Дія правила `B` повертає апарат назад у зону дії правила `A`.

Частота перемикання між правилами підскакує до частоти виконання основного циклу (50–100 Гц). Апарат фізично не встигає відпрацьовувати такі команди через механічну інерцію, але виконавчі механізми (сервоприводи, ключі інверторів) починають вібрувати з високою амплітудою.

Простежити це явище в польотному лозі (`ulog` або `tlog`) дуже просто за трьома характерними ознаками:

1. **Спектральний пік на половині частоти циклу:** Швидке перетворення Фур'є (FFT) сигналу уставки на мотори показує потужний гармонійний пік біля `f_loop / 2`, якого немає в нормальному спектрі польоту.
2. **Стрибки фазного струму без руху:** Струмові шунти фіксують різке зростання споживання (нагрів MOSFET-мостів через динамічні втрати на перезаряд затворів), тоді як середня швидкість машини падає до нуля.
3. **Кутові мікровібрації:** Гіроскоп фіксує высокочастотний дрижачий шум, що забиває низькочастотні фільтри оцінювача орієнтації.

Введення гістерезису ([поріг із гістерезисом](root:sf-devices/umova-diia-i-chomu-prystrii-klatsaie)) та мінімального часу утримання стану ([антидребезг рішення](root:sf-devices/minimalnyi-chas-stanu-zatrymka-i-antydrebezh)) успішно лікує однопараметричні перемикання (наприклад, увімкнення охолодження за температурою). Проте воно виявляється безсилим у багатовимірних циклах із трьох чи більше правил: гістерезис лише розтягує період автоколивань, але не усуває сам конфлікт цілей.

## Локальні евристики та сліпота до глобального оптимуму

Будь-яке дискретне правило за своєю природою є **жадібною локальною евристикою**: воно оцінює стан апарата в поточний момент часу `t` і вибирає дію, яка здається найкращою прямо зараз, маючи нульовий горизонт передбачення вперед у часі (`H = 0`).

Класичною ілюстрацією цієї сліпоти є навігація на основі штучних потенційних полів (*Artificial Potential Fields, APF*) або реактивних правил відштовхування. Апарат притягується вектором сили до цілі та відштовхується від виявлених давачами перешкод:

```
F_total = F_att(ціль) + Σ F_rep(перешкоди)
```

Поки перешкоди опуклі й ізольовані, реактивне правило працює задовільно. Але щойно апарат залітає в увігнуту перешкоду (U-подібну огорожу, глухий кут коридору, групу дерев), настає геометричний тупик: вектор відштовхування від стін точно врівноважує вектор притягання до цілі:

```
F_att + F_rep = 0
```

Сумарна сила обнуляється, і апарат зупиняється намертво в точці **локального мінімуму**, вважаючи, що досяг рівноваги, хоча до справжньої цілі лишається ще сотня метрів. Жодне локальне правило не здатне підказати машині рушити *назад*, віддаляючись від цілі, щоб обійти U-подібну кишеню. Для цього потрібен просторовий пошук на графі або розрахунок шляху на глобальній карті ([планування шляху на сітці та A*](root:embedded/path-planning-grid), [обхід перешкод](root:embedded/obstacle-avoidance)).

![Пастка локального мінімуму в увігнутій перешкоді та автоколивання в коридорі](/root/course/embedded/mezhi-pravyl/img/local-minima-oscillation.svg)
*Сліпота локальних реакцій. Ліворуч: увігнута перешкода створює локальний мінімум, де вектор притягання до цілі компенсується відштовхуванням стін — реактивне правило застрягає. Праворуч: у вузькому коридорі протилежні правила безпеки породжують брязкіт і граничний цикл перемикань.*

Та сама сліпота проявляється в динаміці керування енергією та швидкістю. Розгляньмо задачу подолання пагорба колісним роботом з обмеженим запасом потужності:

* **Локальне правило:** «Тримати задану швидкість 2 м/с. Якщо швидкість падає — додати струм». Коли робот в'їжджає на крутий підйом, правило викручує струм на максимум, нагріває драйвер моторів, просаджує батарею й зрештою зупиняється через спрацьовування теплового захисту посеред схилу.
* **Оптимізаційне планування:** Алгоритм оптимізації траєкторії на горизонті `T` розглядає профіль висоти попереду: він заздалегідь розганяє апарат на рівній ділянці перед пагорбом, накопичує кінетичну енергію, плавно знижує швидкість на вершині й долає підйом з мінімальним піковим струмом без перегріву електроніки.

### Математична постановка неперервної оптимізації траєкторії

Оптимізація формулює задачу не як набір дискретних перемикачів, а як пошук керуючого впливу `u(t)`, що мінімізує інтегральний функціонал вартості на рухомому горизонті `[0, T]` за наявності системи диференціальних та алгебраїчних обмежень:

```
мінімізувати J = ∫ [ w₁ · ||p(t) − p_goal||² + w₂ · ||u(t)||² + w₃ · R_risk(p(t)) ] dt
при обмеженнях:
  dx/dt = f(x(t), u(t))       [диференційна модель динаміки апарата]
  v_min ≤ v(t) ≤ v_max         [ліміти лінійної швидкості]
  ||a(t)|| ≤ a_max             [ліміти прискорення за зчепленням]
  dist(p(t), перешкоди) ≥ d_safe [геометричний зазор безпеки]
  I_motor(t) ≤ I_max           [тепловий струмовий ліміт]
```

Такий розрахунок неможливо замінити жодною кількістю статичних умов `if-else`. Там, де правила намагаються вгадати складний неперервний компроміс через набір розрізнених евристик, чисельний оптимізатор знаходить математично точний баланс між швидкістю, безпекою та енерговитратами.

## Де пролягає вододіл: правила проти оптимізації

Усвідомлення меж правил не означає, що від них слід повністю відмовитися на користь чисельних оптимізаторів чи нейромереж ([правило чи модель](root:sf-ml/pravylo-chy-model)). Навпаки: намагатися вирішувати оптимізатором задачі, для яких призначені правила, настільки ж згубно, як і планувати траєкторії через `if-else`.

Інженерний вододіл між цими двома парадигмами визначається характером простору рішень, вимогами до часу реакції та ціною помилки:

| Властивість задачі | Домен жорстких правил (Interlocks / FSM) | Домен оптимізації та пошуку (Planners / Solvers) |
|---|---|---|
| **Характер простору** | Дискретний, топологічний, якісний (стани, фази, дозволи) | Неперервний, геометричний, багатовимірний (траєкторії, профілі тяги) |
| **Час реакції** | Детермінований, мікросекунди — одиниці мілісекунд (`O(1)`) | Змінний, десятки — сотні мілісекунд (ітераційні солвери) |
| **Гарантія збіжності** | 100% за фіксовану кількість тактів процесора | Можливий тайм-аут, локальний мінімум або незбіжність матриць |
| **Ціна порушення** | Катастрофічна (пожежа, струмовий удар, механічне руйнування) | Субоптимальність (довший шлях, більша витрата батареї) |
| **Приклади задач** | Струмовий захист, E-Stop, автомат озброєння, валідація пакетів | Траєкторії A*/DWA, розподіл тяги моторів, MPC-навігація |

### Задачі, де правила незамінні

1. **Апаратні інтерлоки та захисти:** Відсічка живлення при короткому замиканні або струмовому перевантаженні силових ключів мусить спрацьовувати за 5–50 мікросекунд. Тут неприпустимі жодні чисельні ітерації — це виключно домен апаратних компараторів або найпростіших обробників переривань ([блокування й умови допуску](root:sf-devices/blokuvannia-i-umovy-dopusku-interlock)).
2. **Життєвий цикл і дискретні фази системи:** Перехід між станами `INIT → STANDBY → ARMED → IN_FLIGHT → EMERGENCY_LANDING` керується строгою логікою умов допуску ([автомат режимів](root:embedded/avtomat-rezhymiv)). Апарат не має права подавати напругу на мотори, доки не пройдено калібрування гіроскопа та фіксацію домашньої точки GPS.
3. **Безумовні охоронні бар'єри (Hard Failsafes):** Якщо пропав зв'язок і вийшов тайм-аут сторожового таймера — активується режим повернення або парашут ([безпечний стан](root:sf-devices/safe-mode)). Це імперативний наказ, що скасовує будь-які оптимізаційні розрахунки.
4. **Валідація цілісності протоколів та меж датчиків:** Відкидання зіпсованого CRC-пакета, детектування `NaN` у потоці далекоміра, фільтрація неприпустимих у ставок.

### Задачі, де оптимізатори безальтернативні

1. **Просторове планування та обхід динамічних перешкод:** Побудова плавної гладкої кривої в тривимірному просторі з урахуванням кінематики повороту апарата.
2. **Оптимальний розподіл керуючих зусиль (Control Allocation):** Розподіл тяги між вісьмома моторами гексакоптера або поворотними соплами VTOL-апарата при частковій відмові одного з приводів.
3. **Багатосенсорне оцінювання стану:** Поєднання даних акселерометра, барометра та GNSS з урахуванням коваріації шумів ([фільтр Калмана](root:embedded/kalman-filter)).
4. **Керування на основі прогнозних моделей (Model Predictive Control):** Одночасне утримання траєкторії та оптимізація витрати пального/заряду з урахуванням динаміки прискорення.

Спроба змішати ці ролі завжди веде до катастрофи:
* Якщо оптимізатором намагатися приймати рішення про аварійне вимкнення мотора при перевищенні струму, апарат згорить у момент, коли матричний солвер потрапить у погано обумовлену матрицю й перевищить ліміт ітерацій.
* Якщо сотнею правил `if-else` намагатися описати рух ровера між деревами, машина буде смикатися, зупинятися перед кожним кущем і регулярно врізатися в перешкоди через брязкіт гілок.

## Архітектура гібридної системи: оптимізатор під наглядом бар'єра правил

Єдиний надійний спосіб побудови складної автономної системи — це **гібридна дворівнева архітектура**, де оптимізаційний планувальник генерує бажаний рух, а детермінований бар'єр правил безпеки наглядає за кожним його кроком і має право вето.

![Гібридна архітектура: оптимізаційний планувальник під наглядом детермінованого бар'єра правил](/root/course/embedded/mezhi-pravyl/img/hybrid-architecture.svg)
*Архітектура гібридного контуру прийняття рішень. Повільний оптимізаційний планувальник (10–50 Гц) формує уставку-кандидата, а швидкий детермінований бар'єр безпеки (100–500 Гц) верифікує її за фізичними інваріантами й безумовно обмежує в разі небезпеки.*

Система працює за чітким регламентом взаємодії двох контурів:

1. **Високорівневий планувальник (Deliberative / Optimizer Tier):**
   * Частота: 10–50 Гц (запускається як фоновий потік у RTOS або на супутньому бортовому комп'ютері під Linux/ROS).
   * Вхід: глобальна ціль, статична та динамічна карта зайнятості, історія руху.
   * Вихід: вектор уставки-кандидата `u_cand = [vx, vy, yaw_rate]`.
   * Задача: розв'язати інтеграл вартості, оминути U-подібні кишені, мінімізувати час і витрату енергії.

2. **Детермінований фільтр безпеки (Reactive Safety Barrier / Interlock Tier):**
   * Частота: 100–500 Гц (жорсткий мікроконтролерний цикл керування).
   * Вхід: кандидат `u_cand`, миттєві сирі покази далекомірів, струмових датчиків, напруги та кутів нахилу.
   * Алгоритм: аналітична перевірка інваріантів безпеки за час `O(1)`.
   * Вихід: остаточна безпечна уставка `u_safe`, що передається на внутрішній контур ПІД-стабілізації моторів.

### Математичний принцип фільтрації безпеки та функції бар'єра

У сучасній теорії керування такий фільтр базується на концепції **функцій бар'єра керування** (*Control Barrier Functions, CBF*) та ядра життєздатності (*Viability Kernel*).

Нехай безпечна область простору станів задається як множина рівня неперервної функції `h(x) ≥ 0` (наприклад, дистанція до стіни мінус гальмівний шлях: `h(x) = d_obs − v² / (2·a_max)`).

Команда-кандидат `u_cand` вважається допустимою лише тоді, коли похідна функції бар'єра вздовж траєкторії системи задовольняє умову стійкості множини:

```
dh/dt + γ · h(x) ≥ 0,  де γ > 0 — коефіцієнт строгості наближення до межі
```

Якщо `u_cand` задовольняє цю умову, вона передається на приводи без найменших спотворень:

```
u_safe = u_cand,  якщо умова безпеки виконана
```

Якщо ж кандидат вимагає надмірного прискорення, що веде до порушення бар'єра (`dh/dt + γ·h(x) < 0`), фільтр розв'язує миттєву квадратичну задачу найменших квадратів (*Quadratic Program, QP*), яка для одновимірних обмежень швидкості зводиться до прямої замкненої формули насичення:

```
u_safe = argmin ||u − u_cand||²   при умові dh/dt + γ · h(x) ≥ 0
```

Це гарантує, що рух лишається максимального наближеним до задуму планувальника, але ні за яких обставин не порушує фізичні ліміти апарата. Перехід між режимами здійснюється без ривків ([безударне перемикання регулятора](root:com-signal/bumpless-transfer)).

### Реалізація інтерфейсу бар'єра безпеки

Нижче наведено фрагмент ядра системи прийняття рішень, що реалізує розмежування між генерацією команди-кандидата та її детермінованою фільтрацією. Повний робочий проєкт із тестовими сценаріями наведено у [вставці практичної реалізації безпечного фільтра](root:embedded/mezhi-pravyl/proj-safety-supervisor.md).

:::tabs
```c
#include <stdbool.h>
#include <math.h>

typedef struct {
    float vx;       /* м/с */
    float yaw_rate; /* рад/с */
} ControlSetpoint;

typedef struct {
    float range_ahead_m;
    float max_brake_accel_mps2;
    float safety_margin_m;
    float loop_dt_sec;
} DynamicObstacleEnvelope;

/* Детермінований бар'єр безпеки гальмівного шляху: O(1), без виділення пам'яті */
ControlSetpoint apply_stopping_barrier(
    ControlSetpoint candidate,
    const DynamicObstacleEnvelope *env,
    bool *was_clamped
) {
    ControlSetpoint safe = candidate;
    *was_clamped = false;

    if (safe.vx <= 0.0f) {
        return safe; /* Рух назад або стоп перешкодою спереду не обмежується */
    }

    /* Доступна дистанція до фізичного контакту з урахуванням запасу */
    float d_avail = env->range_ahead_m - env->safety_margin_m;
    if (d_avail <= 0.0f) {
        safe.vx = 0.0f;
        *was_clamped = true;
        return safe;
    }

    /* Максимальна швидкість, з якої апарат гарантовано зупиниться: v = sqrt(2 * a * d) */
    float v_max_allowed = sqrtf(2.0f * env->max_brake_accel_mps2 * d_avail);

    if (safe.vx > v_max_allowed) {
        safe.vx = v_max_allowed;
        *was_clamped = true;
    }

    return safe;
}
```
```cpp
#include <cmath>
#include <algorithm>
#include <expected>

namespace Control {

struct Setpoint {
    float vx{0.0f};       // м/с
    float yaw_rate{0.0f}; // рад/с
};

struct ObstacleEnvelope {
    float range_ahead_m{0.0f};
    float max_brake_accel_mps2{3.0f};
    float safety_margin_m{0.4f};
};

enum class BarrierStatus {
    PassThrough,
    SpeedClamped,
    EmergencyHalt
};

class SafetyBarrier {
public:
    [[nodiscard]] static constexpr std::pair<Setpoint, BarrierStatus> enforce(
        const Setpoint& candidate,
        const ObstacleEnvelope& env
    ) noexcept {
        if (candidate.vx <= 0.0f) {
            return {candidate, BarrierStatus::PassThrough};
        }

        const float d_avail = env.range_ahead_m - env.safety_margin_m;
        if (d_avail <= 0.02f) {
            return {Setpoint{0.0f, candidate.yaw_rate}, BarrierStatus::EmergencyHalt};
        }

        // Аналітичний розрахунок граничної безпечної швидкості v = sqrt(2 * a * d)
        const float v_max_allowed = std::sqrt(2.0f * env.max_brake_accel_mps2 * d_avail);

        if (candidate.vx > v_max_allowed) {
            return {Setpoint{v_max_allowed, candidate.yaw_rate}, BarrierStatus::SpeedClamped};
        }

        return {candidate, BarrierStatus::PassThrough};
    }
};

} // namespace Control
```
:::

Якщо оптимізаційний планувальник з будь-якої причини зависає, видає некоректний вектор чи не враховує раптову появу перешкоди — фільтр безпеки гарантує зупинку апарата на апаратному рівні. Якщо ж усе чисто — система отримує всі переваги оптимальної плавної траєкторії без ризику застрягання в евристичних глухих кутах.

## Інженерний підсумок

Правила перестають тягнути там, де закінчується топологія станів і починається неперервна фізика руху в реальному просторі:

1. **Комбінаторна межа:** Простір станів реального світу зростає експоненційно (`k^N`). Спроба описати рух апарата через мережу правил `IF-THEN` залишає понад 99% ситуацій у сліпій зоні необроблених винятків.
2. **Крихкість взаємодії:** Окремо протестовані евристики катастрофічно руйнуються при накладанні непередбачених фізичних збурень (вітер + розряд батареї + геометрія перешкоди), породжуючи високочастотний брязкіт і вихід з ладу приводів.
3. **Сліпота до майбутнього:** Реактивне правило не має часового горизонту планування й неминуче застрягає в локальних мінімумах складного рельєфу.
4. **Архітектурний синтез:** Жорсткі правила мусять охороняти **зовнішні межі безпечного всесвіту** (струмові захисти, інтерлоки, аварійні зупинки, автомати станів). Усередині ж цього захищеного простору керування траєкторією та ресурсами має належати чисельним оптимізаторам і планувальникам.
