# 📜 Від телеметрії SCADA до суверенного Edge: як пристрої здобували автономію

У 1970-х роках перші системи диспетчерського керування та збору даних (SCADA, англ. *Supervisory Control and Data Acquisition*) проєктувалися за строго централізованою топологією «господар—слуга» (англ. *master-slave*). Віддалений термінальний блок (RTU, англ. *Remote Terminal Unit*), встановлений на насосній станції або електричній підстанції за десятки кілометрів від оператора, складався з 8-бітного мікропроцесора (як-от Intel 8080 чи Motorola 6800), масиву релейних виходів та аналого-цифрових перетворювачів. Цей апаратний вузол був повністю позбавлений власної бізнес-логіки: він працював як віддалений мультиплексор портів. Раз на кілька секунд або хвилин центральний комп'ютер диспетчерського пункту надсилав через виділену телефонну лінію або радіомодем запит опитування (англ. *polling*), зчитував байти станів контактів і окремою командою давав наказ замкнути контактор насоса чи перемкнути масляний вимикач.

Ця схема працювала рівно доти, доки мідна пара не зазнавала обриву через бурю, а радіоканал не глушився індустріальними завадами. Коли зв'язок зникав, перші примітивні RTU переходили в так званий стан «зависання виходів» (англ. *freeze outputs*) або скидали всі сигнали в нуль. Насос, що наповнював резервуар, або продовжував качати воду до аварійного переливу, або зупинявся, залишаючи технологічний процес без тиску. Інженери промислової автоматизації швидко збагнули: **контроль фізичного процесу ніколи не повинен залежати від наявності телекомунікаційного каналу**.

```
Еволюція автономії:
1975 (RTU SCADA)     : Датчик ──> [ Тупий RTU ] ════(Опитування)════> [ Мейнфрейм / Диспетчер ]
1985 (PLC / DCS)     : Датчик ──> [ Локальний PLC з PID ] ──(Звіт)──> [ SCADA / HMI ]
2015 (Хмарний IoT)   : Датчик ──> [ ESP8266 / Реле ] ════(MQTT)═════> [ Cloud API ] (Крах при обриві)
2025 (Offline-First) : Датчик ──> [ Edge-контролер + NVM ] ──(Sync)─> [ Cloud Twin ] (Повний суверенітет)
```

### Народження програмованих логічних контролерів і розподілених систем

Відповіддю на кризу «тупого заліза» наприкінці 1970-х та на початку 1980-х років стала поява програмованих логічних контролерів (PLC, англ. *Programmable Logic Controller*) від компаній Modicon (винахід Річарда Морлі, Dick Morley) та Allen-Bradley, а також концепції розподілених систем керування (DCS, англ. *Distributed Control System*) від Honeywell та Yokogawa.

У цих системах лінію розділу між автономією та зв'язком провели безкомпромісно:
- **Локальний детермінований контур (Loop 0):** Програма на мові драбинкової логіки (Ladder Logic, LD) або структурованого тексту (ST) виконувалася циклічно з фіксованим періодом від 1 до 50 мілісекунд прямо в мікроконтролері біля датчика. Якщо тиск у трубопроводі перевищував уставку аварійного клапана, локальний процесор відкривав скидний вентиль за лічені мілісекунди без жодного запиту до центрального комп'ютера.
- **Диспетчерський контур (Supervisory Loop):** Мережа Modbus чи Profibus передавала лише узагальнені звіти про стан процесу, аварійні прапорці та приймала планові зміни уставок від оператора. Обрив кабелю зв'язку викликав лише попередження на екрані диспетчера, тоді як сам технологічний вузол продовжував штатно працювати за локально зашитими правилами.

Ця парадигма забезпечила десятиліття надійної роботи нафтопереробних заводів, електростанцій та автоматизованих конвеєрів. Проте з початком споживчого буму «Інтернету речей» (IoT, англ. *Internet of Things*) у 2010-х роках індустрія забула цей фундаментальний урок.

### Ілюзія «хмароцентричності» та крах споживчого IoT 1.0

Поява дешевих мікроконтролерів із вбудованим радіоінтерфейсом Wi-Fi (насамперед сімейства Espressif ESP8266 у 2014 році вартістю менше двох доларів) породила хибну інженерну моду: всю бізнес-логіку виносити в хмару (AWS IoT Core, Google Cloud IoT, Azure IoT Hub), а мікроконтролер перетворювати на тонкий клієнт протоколів MQTT або HTTP REST.

Розробники мотивували це простотою: прошивку не треба ускладнювати локальними базами даних, складними автоматами станів чи розкладами — достатньо надіслати JSON із температурою в тему брокера, а хмарна лямбда-функція вирішить, чи вмикати нагрівач, і надішле зворотне повідомлення.

Реальність виявилася нищівною для користувачів:
1. **Інцидент із Revolv Hub (2016 рік):** Компанія Nest (підрозділ Alphabet) закрила хмарні сервери хабів розумного будинку Revolv. Оскільки пристрої не мали автономного рушія правил і локального API, тисячі клієнтів отримали повністю непрацездатні пластикові коробки вартістю сотні доларів, які не могли навіть увімкнути лампочку через домашній вимикач.
2. **Збої хмарних провайдерів:** Масштабні відмови регіонів AWS us-east-1 у 2017 та 2021 роках призвели до того, що власники розумних замків і гаражних воріт не могли потрапити у власні будинки, а системи поливу та обігріву зупинялися на десятки годин через неможливість отримати відповідь від віддаленого сервера авторизації.
3. **Затримки в контурах безпеки:** Спроба перевіряти RFID-карту на прохідній через запит до хмарної бази даних спричиняла черги при затримці мобільного модема понад дві секунди, а при повному зникненні стільникового лінка паралізувала рух персоналу.

### Ренесанс Edge Computing та суверенна філософія Offline-First

Провал першої хвилі хмароцентричного IoT змусив індустрію повернутися до класичних принципів розподілених систем, але вже на сучасній апаратній базі. З'явилися стандарти та ініціативи (зокрема протокол Matter, розроблений альянсом CSA, та платформенно-незалежні рушії локальної автоматизації типу Home Assistant і EdgeX Foundry), які закріпили архітектурний принцип **Offline-First**.

Сучасний вбудований пристрій розглядається як повноправний **суверенний вузол** (англ. *sovereign node*). Його постійна Flash-пам'ять містить актуальну копію правил, розкладів, таблиць доступу та конфігурацій, а оперативна пам'ять забезпечує автономний замкнений цикл прийняття рішень. Хмара перестала бути «мозком» пристрою; вона повернулася до своєї природної ролі — координатора глобальних оновлень, сховища довготривалої аналітики та платформи для дистанційного моніторингу за наявності каналу.
