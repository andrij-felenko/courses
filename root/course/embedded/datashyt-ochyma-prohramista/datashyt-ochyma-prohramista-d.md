Коли розробник вбудованого ПЗ підключає новий цифровий акселерометр або комбінований датчик тиску та температури, відкриває офіційний технічний опис на вісімдесят сторінок і поспіхом виписує зі зведеної таблиці адреси регістрів, перша ж спроба запустити опитування на частоті 100 Гц зазвичай закінчується незрозумілою поведінкою системи. Датчик повертає валідне число рівно один раз, після чого лінія апаратного переривання назавжди зависає в нулі; виміри по осі Z раптово роблять стрибок від нуля до -32768 через випадкове переставлення старшого й молодшого байтів місцями; а спроба скинути прапорець готовності даних класичним виразом `status &= ~FLAG` призводить до того, що прошивка мовчки втрачає критичні сповіщення про переповнення внутрішнього буфера. Усі ці збої виникають не через дефекти кремнію і не через помилки компілятора — вони трапляються тому, що програміст сприйняв карту регістрів як звичайний масив байтів у пам'яті, проігнорувавши суворі апаратні контракти взаємодії з цифровою логікою чипа.

Даташит *(англ. datasheet)* для інженера вбудованих систем — це детальна специфікація апаратного контракту (Hardware Interface Specification), що визначає правила цифрового діалогу між обчислювальним ядром мікроконтролера та напівпровідниковим кінцевим автоматом периферійного чипа. Якщо схемотехнік шукає в документації вольт-амперні характеристики, рівні шумів та теплові опори корпусів, то програміст вивчає карту регістрів, типи доступу до окремих бітів, протоколи часових діаграм транзакцій та перелік офіційно зафіксованих виробником апаратних помилок (Errata).

## Анатомія документації: чотири документи замість одного

Сучасна напівпровідникова мікросхема ніколи не описується одним універсальним файлом. Поширена помилка розробника-початківця — спроба знайти всі відповіді в першому-ліпшому PDF, знайденому через пошуковик. Виробники кремнію (STMicroelectronics, Texas Instruments, Analog Devices, Bosch Sensortec, NXP) публікують цілу родину спеціалізованих технічних документів, кожен із яких має свого адресата.

У практиці розробки вбудованого ПЗ документація чітко поділяється на чотири категорії:

1. **Hardware Datasheet (Апаратний паспорт компонента):** електричний та механічний документ. Він фіксує фізичну розпіновку *(pinout)*, діапазони напруги живлення, максимальні струми, рівні логічних порогів, часові вимоги до шинних сигналів (Setup/Hold Times) та стислу карту регістрів. Це документ першого знайомства: він потрібен для перевірки адреси шини, базових констант і допустимої швидкості обміну.
2. **Reference Manual / Programmer's Guide (Технічний довідник програміста):** головна робоча книга автора драйвера. Тут детально розписано роботу внутрішніх цифрових автоматів периферійних блоків, бітові карти кожного регістра, формати передачі кадрів, механізми черг FIFO, логіку вбудованих цифрових фільтрів (Low-Pass, High-Pass) та точні покрокові послідовності ініціалізації модулів.
3. **Application Notes (Прикладні настанови та рекомендації):** практичні інструкції від інженерів виробника. Вони містять алгоритми математичної обробки сирих даних (калібрування нульового зміщення акселерометра, компенсація температурного дрейфу гіроскопа, обчислення орієнтації через кватерніони), а також готові шаблони конфігурації під типові сценарії (автомобільний трекер, крокомір, безпілотний апарат).
4. **Errata Sheet (Листок апаратних помилок):** офіційний реєстр дефектів проєктування кремнію для конкретних ревізій чипа. Він описує некоректну поведінку схем за певних умов і наводить обов'язкові програмні обхідні шляхи *(workarounds)*, без реалізації яких неможливо гарантувати безвідмовну роботу пристрою.

Програміст будує роботу навколо чотирьох фундаментальних розрізів документації: карти регістрів і семантики доступу, структури бітових масок, часових діаграм транзакцій шини та перевірки наявності апаратних багів у розділі Errata.

## Карта регістрів: семантика доступу та апаратні пастки

Карта регістрів *(Register Map)* описує внутрішній адресний простір мікросхеми. Для периферійних чипів на шинах I2C або SPI кожен регістр адресується за допомогою 7- або 8-бітного зміщення (Address Offset). Проте на відміну від звичайної оперативної пам'яті (RAM), комірка апаратного регістра — це не просто пасивний масив тригерів, а безпосередній інтерфейс взаємодії з цифровою логікою чипа, де кожна операція читання або запису може змінювати внутрішній стан апаратури.

![Спектр типів доступу до регістрів та поведінка бітів при зверненні](/root/course/embedded/datashyt-ochyma-prohramista/img/register-access-types.svg)
*Спектр типів доступу до регістрів: відмінності між R/W, RO, W1C та COR, а також наслідки некоректного вибору операцій.*

Даташит чітко класифікує кожен регістр і кожне бітове поле за типом дозволеного доступу:

### 1. R/W (Read / Write) — Конфігураційні регістри
Регістри, значення яких можна як записувати, так і зчитувати назад. Вони використовуються для налаштування режимів роботи: вибору темпу генерації вибірок (ODR), діапазону повної шкали (FSR), активації ліній переривань або ввімкнення внутрішніх дільників тактової частоти.

Для зміни окремого бітового поля в R/W регістрі використовують патерн **Read-Modify-Write (RMW)**:
1. Зчитати поточне значення байта з чипа.
2. Очистити цільові біти за допомогою порозрядної маски: `val &= ~MASK`.
3. Встановити нові значення бітів: `val |= NEW_BITS`.
4. Записати модифікований байт назад у чип.

> 🔧 **Навіщо це.** Сліпий запис байта без RMW затирає значення сусідніх бітових полів, скидаючи паралельно налаштовані осі або перемикаючи внутрішній дільник тактової частоти в непередбачуваний стан.

### 2. RO (Read-Only) — Регістри даних та статусів
Регістри, доступні виключно для читання. Спроба запису в такий регістр або ігнорується кремнієм, або призводить до формування сигналу помилки шини (NACK в I2C або Bus Error на системній шині MMIO). У цих регістрах зберігаються результати вимірювання АЦП (`OUT_X_L`, `OUT_X_H`), постійні ідентифікатори виробника (`WHO_AM_I`, `CHIP_ID`) та поточний стан апаратних вузлів.

Значення RO-регістрів даних оновлюються внутрішнім тактовим генератором датчика незалежно від того, що в цей момент робить мікроконтролер. Якщо вичитувати 16-бітний вимір (два байти: молодший `OUT_L` та старший `OUT_H`) двома окремими нескоординованими транзакціями, нове значення АЦП може записатися прямо між читанням першого і другого байтів, що призведе до катастрофічного спотворення результату.

### 3. W1C / W1TC (Write-1-to-Clear) — Прапорці переривань та подій
Один із найважливіших і водночас найбільш небезпечних для новачка типів доступу. Регістри W1C використовуються для фіксації апаратних подій: готовності нової вибірки (Data Ready), переповнення буфера (FIFO Overrun), перевищення порогу прискорення або виявлення вільного падіння.

Апаратна логіка біта W1C працює за такими правилами:
- Коли датчик фіксує подію, внутрішній тригер встановлюється в `1`.
- Якщо мікроконтролер записує в цей біт **`1`**, тригер **скидається в `0`**.
- Якщо мікроконтролер записує в цей біт **`0`**, тригер **залишається у попередньому стані**.
- Читання регістра повертає поточний стан прапорців (активні `1`, неактивні `0`).

**Фатальна помилка Read-Modify-Write:**
Якщо програміст намагається скинути один конкретний прапорець за звичним патерном `reg &= ~FLAG`, код виконує такі дії:

:::tabs
```c
/* ФАТАЛЬНИЙ АНТИПАТЕРН ДЛЯ W1C РЕГІСТРА (C): */
uint8_t status = read_reg(STATUS_REG);  /* status = 0b01000100 (FLAG_A і FLAG_B активні) */
status &= ~FLAG_A;                      /* status стає 0b01000000 (FLAG_B = 1, FLAG_A = 0) */
write_reg(STATUS_REG, status);          /* Запис 0b01000000 назад скидає FLAG_B і залишає FLAG_A! */
```
```cpp
/* ФАТАЛЬНИЙ АНТИПАТЕРН ДЛЯ W1C РЕГІСТРА (C++): */
auto status = bus.read_register(Reg::Status); // status = 0b01000100 (FlagA та FlagB активні)
status &= ~static_cast<uint8_t>(StatusFlag::A); // status = 0b01000000 (FlagB = 1, FlagA = 0)
bus.write_register(Reg::Status, status);        // Запис скидає FlagB і залишає FlagA нескинутим!
```
:::

Результат виконання: запис `0` в біт `FLAG_A` **не скидає** його (він залишається `1`), тоді як запис `1` у біт `FLAG_B` **апаратно скидає подію B**, яка ще навіть не була оброблена в коді. Подія B безповоротно втрачається.

:::tabs
```c
/* Правильний спосіб скидання прапорця в регістрі W1C:
   Записуємо виключно бітову маску тих прапорців, які ми щойно обробили */
void clear_data_ready_flag(uint8_t dev_addr) {
    uint8_t ack_mask = STATUS_DRDY_BIT;
    i2c_write_byte(dev_addr, REG_STATUS, ack_mask);
}
```
```cpp
/* Ідіоматичний C++ варіант з типізованими бітовими масками */
namespace driver {

enum class StatusFlag : uint8_t {
    DataReady     = (1 << 0),
    FifoWatermark = (1 << 1),
    FifoOverrun   = (1 << 2)
};

void clear_status_flag(BusInterface& bus, uint8_t dev_addr, StatusFlag flag) noexcept {
    const auto ack_byte = static_cast<uint8_t>(flag);
    bus.write_register(dev_addr, Reg::Status, std::span<const uint8_t, 1>{&ack_byte, 1});
}

} // namespace driver
```
:::

### 4. COR / RC (Clear-on-Read) — Автоматичне скидання під час читання
У таких регістрах прапорець переривання або лічильник помилок скидається в `0` апаратно в той момент, коли мікроконтролер виконує транзакцію читання байта з шини.

Головна небезпека регістрів COR полягає у взаємодії з апаратними налагоджувачами (JTAG / SWD). Якщо у середовищі розробки (IDE) відкрити панель спостереження за регістрами периферії *(Peripheral Registers View)* або додати адресу в список Watch, налагоджувач під час зупинки процесора автоматично вичитуватиме пам'ять чипа для оновлення вікна. Одне таке фонове зчитування скине апаратний статус переривання, і після відновлення виконання програми драйвер пропустить подію, оскільки регістр уже буде чистим.

### 5. Тіньові регістри та регістри з подвійною поведінкою (Shadow Registers)
Деякі апаратні регістри мають різне фізичне значення залежно від напрямку доступу:
- Читання за адресою повертає поточне значення лічильника таймера або виміряний рівень сигналу.
- Запис за тією ж адресою записує уставку перезавантаження (Auto-Reload Value) або поріг спрацьовування компаратора.

Такі регістри називають тіньовими *(Shadow Registers)* або реєстрами з подвійною поведінкою. Спроба виконати над ними операцію Read-Modify-Write призведе до того, що випадково зчитане поточне значення лічильника перезапише постійну уставку таймера.

### 6. Зарезервовані біти (Reserved / Do Not Modify)
У таблицях регістрів часто трапляються біти з позначкою `Reserved`, `RES`, `0` або `Must be kept at reset value`. Даташити вимагають строго дотримуватися правил роботи з ними:
- **Write 0 only:** у цей біт завжди повинен записуватися `0`, інакше чип може перейти в недокументований тестовий режим фабричного калібрування.
- **Maintain reset value:** біт має фабричну уставку, яку не можна змінювати; модифікація регістрів навколо нього повинна обов'язково виконуватися виключно через Read-Modify-Write, зберігаючи первинне значення.

### 7. Вирівнювання та розрядність звернення (MMIO vs Bus Registers)
Якщо для зовнішніх чипів на I2C/SPI доступ завжди здійснюється побайтово через адресний потік, то для внутрішньої периферії мікроконтролера (таймери, контролери шин, DMA), підключеної безпосередньо до системних шин AHB/APB, діє правило алігнменту *(Memory-Mapped I/O — MMIO)*.

Спроба виконати 32-бітний запис за адресою 8-бітного регістра або неалігноване 16-бітне читання за непарною адресою на ядрі ARM Cortex-M може спровокувати апаратний виняток `HardFault` або записати сміття в сусідні керуючі регістри периферійного блоку. Даташит завжди вказує допустимий розмір доступу: `8-bit`, `16-bit` або `32-bit aligned access only`.

## Бітові поля, прапорці стану та масштабування даних

Цифрові сенсори передають виміряну інформацію у вигляді бітових послідовностей, де фізичні величини закодовані в цілочисельних відліках АЦП. Даташит визначає точні правила перетворення цих сирих чисел на фізичні значення Міжнародної системи одиниць (SI).

### Прапорці готовності та переповнення
Перед зчитуванням результатів вимірювання драйвер повинен перевірити стан апаратних прапорців:
- **DRDY (Data Ready):** свідчить про завершення нового циклу перетворення АЦП і наявність свіжих даних у вихідних регістрах.
- **FIFO Watermark / Threshold:** буфер черги містить задану кількість незчитаних вибірок, готову для пакетного передавання через DMA.
- **FIFO Overrun / Overwrite:** вимірювальний конвеєр переповнився, і старі дані були перезаписані новими без вичитування процесором.

### Діапазон вимірювання (FSR) та частота опитування (ODR)
Кожен вимірювальний чип має два базові параметри налаштування:
1. **Output Data Rate (ODR):** темп генерації вибірок (наприклад, 12.5 Гц, 100 Гц, 800 Гц). Зі збільшенням ODR зростає енергоспоживання мікросхеми та збільшується смуга пропускання цифрового антиаліасингового фільтра.
2. **Full Scale Range (FSR):** максимальний вимірюваний діапазон (наприклад, для акселерометра: `±2g`, `±4g`, `±8g`, `±16g`; для гіроскопа: `±250 dps`, `±2000 dps`).

Вибір FSR безпосередньо визначає **ціну молодшого розряду** *(Sensitivity / Scale Factor / LSB weight)*. Чим вужчий діапазон FSR, тим вища роздільна здатність вимірювання (менше значення фізичної величини припадає на 1 LSB).

```
Ціна молодшого розряду для 16-бітного знакового діапазону (±2g):
S = (2 · 2g) / 2¹⁶
= 4g / 65536
= 0.000061035 g/LSB    [0.061 мг на один відлік]
```

![Збирання багатобайтового виміру з регістрів, знакове розширення та переведення в одиниці SI](/root/course/embedded/datashyt-ochyma-prohramista/img/endianness-and-sensor-fusion.svg)
*Процес збирання 16-бітного значення: склеювання байтів OUT_L та OUT_H, знакове розширення та множення на коефіцієнт чутливості.*

### Формат доповняльного коду (Two's Complement) та знакове розширення
Більшість датчиків повертає дані у форматі **двійкового доповняльного коду** *(Two's Complement)*. Для 16-бітного числа старший біт (біт 15) є знаковим: `0` відповідає додатному числу, `1` — від'ємному.

Складна пастка виникає в чипах із роздільною здатністю 12 або 14 біт, де дані пакуються у два 8-бітні регістри одним із двох способів:
1. **Left-Justified (вирівняно ліворуч):** 12 біт даних розташовані у бітах `[15:4]`, а молодші біти `[3:0]` заповнені нулями. Для отримання правильного значення 16-бітне число зсувають вправо на 4 розряди: `raw = raw_16 >> 4`.
2. **Right-Justified (вирівняно праворуч):** 12 біт даних розташовані у бітах `[11:0]`, а біти `[15:12]` містять нулі. У цьому випадку старший знаковий біт розташований на позиції 11, а не 15. Просте приведення до типу `int16_t` не виконає знакове розширення, і від'ємне число `0x0FE0` (-32 у 12-бітній шкалі) буде прочитане як додатне `+4064`.

:::tabs
```c
/* Правильне знакове розширення (Sign Extension) для 12-бітного Right-Justified числа */
int16_t sign_extend_12bit(uint16_t raw_12) {
    if (raw_12 & 0x0800) {  /* Якщо 11-й біт дорівнює 1 (число від'ємне) */
        raw_12 |= 0xF000;   /* Заповнюємо старші 4 біти одиницями */
    }
    return (int16_t)raw_12;
}

/* Альтернативний швидкий варіант через знаковий арифметичний зсув */
int16_t sign_extend_12bit_shift(uint16_t raw_12) {
    return (int16_t)(raw_12 << 4) >> 4;
}
```
```cpp
/* C++ constexpr реалізація знакового розширення довільної розрядності */
#include <cstdint>
#include <concepts>

namespace driver {

template <size_t Bits>
requires (Bits > 0 && Bits < 16)
[[nodiscard]] constexpr int16_t sign_extend(uint16_t raw) noexcept {
    constexpr uint16_t SignMask = 1U << (Bits - 1);
    constexpr uint16_t FillMask = ~((1U << Bits) - 1U);
    
    if ((raw & SignMask) != 0) {
        return static_cast<int16_t>(raw | FillMask);
    }
    return static_cast<int16_t>(raw & ~FillMask);
}

} // namespace driver
```
:::

### Чому заборонено використовувати C-структури з бітовими полями (Bitfields)
Поширена помилка програмістів-початківців — спроба накласти структуру C з бітовими полями безпосередньо на апаратний регістр:

:::tabs
```c
/* НЕБЕЗПЕЧНИЙ АНТИПАТЕРН (C): Порядок полів implementation-defined */
struct ctrl_reg_t {
    uint8_t enable : 1;
    uint8_t odr    : 3;
    uint8_t fsr    : 2;
    uint8_t bdu    : 1;
    uint8_t rsvd   : 1;
};
```
```cpp
/* НЕБЕЗПЕЧНИЙ АНТИПАТЕРН (C++): Компілятор не гарантує порядок та атомарність доступу */
struct CtrlRegBitfields {
    bool enable   : 1;
    uint8_t odr   : 3;
    uint8_t fsr   : 2;
    bool bdu      : 1;
    uint8_t rsvd  : 1;
};
```
:::

Стандарт мов C та C++ прямо вказує, що порядок розташування бітових полів усередині байта (від молодшого до старшого чи навпаки) є **визначеним реалізацією (implementation-defined)**. Один компілятор розмістить поле `enable` у нульовому біті, а інший — у сьомому. Крім того, операція доступу до бітового поля не гарантує атомарного розміру шинної транзакції (компілятор може згенерувати 32-бітне читання замість 8-бітного).

Надійний підхід — використання чітких бітових констант, масок та зсувів (`#define` або `constexpr uint8_t`).

:::tabs
```c
/* Надійний патерн маніпуляції бітовими полями в C */
#define CTRL_ODR_POS       4
#define CTRL_ODR_MASK      (0x07 << CTRL_ODR_POS)
#define CTRL_ODR_100HZ     (0x03 << CTRL_ODR_POS)

#define CTRL_BDU_BIT       (1 << 3)
#define CTRL_ENABLE_BIT    (1 << 0)

uint8_t configure_reg(uint8_t current_val) {
    uint8_t val = current_val;
    val &= ~CTRL_ODR_MASK;      /* Очищаємо біти ODR */
    val |= CTRL_ODR_100HZ;      /* Встановлюємо нову частоту */
    val |= CTRL_BDU_BIT;        /* Вмикаємо BDU */
    val |= CTRL_ENABLE_BIT;     /* Активуємо чип */
    return val;
}
```
```cpp
/* Типобезпечний C++ підхід з constexpr бітовими помічниками */
#include <cstdint>
#include <cstddef>

namespace driver {

namespace ctrl_bits {
    inline constexpr uint8_t OdrPos   = 4;
    inline constexpr uint8_t OdrMask  = 0x07 << OdrPos;
    inline constexpr uint8_t Odr100Hz = 0x03 << OdrPos;
    inline constexpr uint8_t BduBit   = 1 << 3;
    inline constexpr uint8_t EnableBit = 1 << 0;
}

[[nodiscard]] constexpr uint8_t configure_register(uint8_t current_val) noexcept {
    using namespace ctrl_bits;
    auto val = static_cast<uint8_t>(current_val & ~OdrMask);
    val |= Odr100Hz | BduBit | EnableBit;
    return val;
}

} // namespace driver
```

## Діаграми протоколів обміну та таймінги шин (I2C / SPI)

Щоб надіслати команду або вичитати вибірку, мікроконтролер повинен сформувати на шині послідовність сигналів, яка відповідає часовій діаграмі *(Timing Diagram)* з розділу інтерфейсів даташита.

![Анатомія транзакцій передачі та пакетного читання для шин I2C та SPI](/root/course/embedded/datashyt-ochyma-prohramista/img/i2c-spi-transaction-anatomy.svg)
*Анатомія транзакцій на шинах I2C та SPI: послідовність адрес, біти автоінкременту та полярність сигналів.*

### Порядок бітів і байтів (Bit/Byte Order)
При читанні даташита обов'язково розрізняють два рівні порядку:
1. **Порядок передачі бітів у каналі:** практично всі протоколи I2C та SPI передають біти, починаючи зі старшого — **MSB First** (Most Significant Bit First).
2. **Порядок байтів у багатобайтних величинах:** більшість датчиків організовані за схемою **Little-Endian** (молодший байт лежить за меншою адресою `0x28: OUT_L`, старший — за більшою `0x29: OUT_H`). Проте трапляються пристрої (наприклад, деякі датчики температури або мікросхеми енергомоніторингу), де байти передаються у форматі **Big-Endian** (спочатку `MSB`, потім `LSB`). Помилка у визначенні порядку байтів перетворює число `0x0001` на `0x0100` (256 замість 1).

### Адресація I2C: 7-бітна адреса проти 8-бітного пакета
Класична причина, через яку мікроконтролер отримує NACK на перший же запит до датчика — плутанина між 7-бітною адресою та 8-бітним адресним фреймом I2C.

Стандарт I2C використовує 7-бітну адресу пристрою. Під час передачі по шині ця адреса зсувається вліво на 1 біт, а нульовий біт визначає напрямок операції: `0` — запис (Write), `1` — читання (Read).
- Одні виробники (наприклад, Texas Instruments, NXP) вказують у даташиті чесну **7-бітну адресу** (наприклад, `0x68`).
- Інші виробники (наприклад, деякі китайські постачальники та старі даташити ST) наводять відразу готові **8-бітні байти** для запису та читання: `0xD0` (Write) та `0xD1` (Read).

Якщо передати значення `0xD0` у функцію I2C драйвера, яка очікує 7-бітну адресу, бібліотека зсуне її ще раз вліво, надіславши на шину некоректний байт `0xA0`, і пристрій не відповість.

### Автоінкремент адреси (Burst Read) та атомарне блокування (BDU)
Щоб вичитати виміри всіх трьох осей акселерометра (6 байтів: `X_L`, `X_H`, `Y_L`, `Y_H`, `Z_L`, `Z_H`), вкрай неефективно надсилати шість окремих I2C-транзакцій. Замість цього використовують **пакетне зчитування** *(Burst Read)*: майстер вказує початкову адресу `OUT_X_L` і продовжує тактувати шину, вичитуючи всі 6 байтів поспіль, поки внутрішній адресний лічильник чипа автоматично інкрементується після кожного байта.

У даташитах різних виробників механізм автоінкременту активується по-різному:
- **STMicroelectronics:** вимагає встановлення старшого біта (біт 7) в адресному байті (`reg_addr | 0x80`). Якщо цей біт не встановити, чип під час Burst-читання повертатиме значення одного й того самого регістра `OUT_X_L` шість разів поспіль.
- **Texas Instruments / Analog Devices:** часто використовують спеціальний біт автоінкременту в командному слові або мають постійно увімкнений автоінкремент за замовчуванням.

**Функція BDU (Block Data Update):**
Коли активовано режим BDU (`BDU = 1`), внутрішня логіка сенсора блокує оновлення вихідних регістрів новими даними АЦП з моменту, коли процесор зчитав молодший байт `OUT_L`, доти, доки не буде вичитано старший байт `OUT_H`. Це повністю усуває небезпеку «розірваного виміру», коли старший байт належить новому відліку, а молодший — попередньому.

### Діаграма SPI: вибір режимів CPOL та CPHA
Для шини SPI даташит обов'язково наводить графік сигналів `CS`, `SCK`, `MOSI` та `MISO`, за яким визначається один із чотирьох стандартних режимів роботи:
- **CPOL (Clock Polarity):** стан лінії тактування `SCK` у режимі спокою (коли `CS` неактивний). `CPOL=0` — низький рівень, `CPOL=1` — високий рівень.
- **CPHA (Clock Phase):** фаза фіксації даних. `CPHA=0` — дані зчитуються за першим перепадом тактового сигналу, `CPHA=1` — за другим перепадом.

Якщо режим SPI в мікроконтролері налаштовано неправильно, бітовий потік зсунеться рівно на півтакту або один такт: кожне зчитане значення буде зсунуте на 1 біт вліво або вправо, перетворюючи координати на хаотичний шум.

### Часові обмеження шини (Timing Specifications)
У таблицях часових параметрів програміст перевіряє критичні затримки:
- `t_startup` / `t_boot`: час від появи живлення до готовності цифрового автомата чипа відповідати на шині (зазвичай від 1 до 50 мс). Звернення до чипа до закінчення цього часу закінчиться помилкою.
- `t_conversion`: час формування першого валідного виміру після виходу зі сплячого режиму або зміни ODR.
- `t_recovery` / `t_buf`: мінімальна пауза між сигналом STOP і наступним START на шині I2C (наприклад, 1.3 мкс для Fast Mode 400 кГц).

## Розділ Errata: коли кремній бреше і як із цим жити

Жоден складний напівпровідниковий чип не виходить у серійне виробництво абсолютно ідеальним. Обмеження часу верифікації, паразитна ємність внутрішніх трас кристала та гонки асинхронних сигналів призводять до виникнення апаратних дефектів *(Silicon Bugs)*.

Офіційний документ, що описує ці проблеми — **Errata Sheet** (або розділ *Device Limitations* у даташиті).

![Життєвий цикл апаратного дефекту від опису в Errata Sheet до програмного обходу в коді](/root/course/embedded/datashyt-ochyma-prohramista/img/errata-workaround-flow.svg)
*Життєвий цикл апаратного бага: ідентифікація ревізії кремнію та застосування програмного обхідного шляху (Workaround).*

### Типові апаратні дефекти та їхні програмні обхідні шляхи (Workarounds)

1. **Зависання шинного автомата I2C при аварійному перезавантаженні процесора:**
   Якщо мікроконтролер перезавантажується під час виконання операції читання I2C, периферійний чип залишається в стані очікування такту і утримує лінію даних `SDA` в низькому рівні (`0`). Оскільки лінія `SDA` притиснута до землі, апаратний I2C-контролер мікроконтролера вважає шину зайнятою і зависає під час першої ж спроби ініціалізації.
   *Обхідний шлях (Bus Clear Workaround):* перед ініціалізацією I2C перевести пін `SCL` у режим GPIO і вручну згенерувати 9 тактових імпульсів. Це змушує ведений пристрій завершити передачу поточного байта, відпустити лінію `SDA` і повернутися в стан очікування сигналу STOP.

:::tabs
```c
/* Програмне розблокування шини I2C (Bus Recovery) мовою C */
void i2c_bus_recovery(void) {
    gpio_set_mode_output_od(PIN_SCL);
    gpio_set_mode_input_pullup(PIN_SDA);

    /* Генеруємо 9 тактових імпульсів на лінії SCL */
    for (int i = 0; i < 9; i++) {
        if (gpio_read(PIN_SDA) == 1) {
            break; /* Чип відпустив SDA, шина розблокована */
        }
        gpio_write(PIN_SCL, 0);
        delay_us(5);
        gpio_write(PIN_SCL, 1);
        delay_us(5);
    }

    /* Формуємо сигнал STOP: перехід SDA з 0 в 1 при SCL = 1 */
    gpio_set_mode_output_od(PIN_SDA);
    gpio_write(PIN_SDA, 0);
    delay_us(5);
    gpio_write(PIN_SCL, 1);
    delay_us(5);
    gpio_write(PIN_SDA, 1);
    delay_us(5);
}
```
```cpp
/* Ідіоматичний C++ клас відновлення шини I2C через RAII пін-маніпулятор */
#include <cstdint>

namespace driver {

template <typename GpioDriver>
class I2cBusRecovery {
public:
    static bool recover(GpioDriver& gpio, uint8_t scl_pin, uint8_t sda_pin) noexcept {
        gpio.set_open_drain_output(scl_pin);
        gpio.set_input_pullup(sda_pin);

        for (int i = 0; i < 9; ++i) {
            if (gpio.read(sda_pin) == 1) {
                break;
            }
            gpio.write(scl_pin, 0);
            gpio.delay_us(5);
            gpio.write(scl_pin, 1);
            gpio.delay_us(5);
        }

        gpio.set_open_drain_output(sda_pin);
        gpio.write(sda_pin, 0);
        gpio.delay_us(5);
        gpio.write(scl_pin, 1);
        gpio.delay_us(5);
        gpio.write(sda_pin, 1);
        gpio.delay_us(5);

        return gpio.read(sda_pin) == 1;
    }
};

} // namespace driver
```

2. **Пропуск переривань при швидкому виході зі сплячого режиму:**
   Деякі ревізії чипів не встигають коректно зафіксувати фронт внутрішнього сигналу `DRDY`, якщо перехід з режиму низького споживання у робочий відбувається менш ніж за 500 мкс.
   *Обхідний шлях:* драйвер повинен програмно додавати обов'язкову затримку `delay_us(500)` після зміни бітів живлення перед опитуванням лінії переривань.

3. **Вимога фіктивного читання (Dummy Read):**
   При роботі через SPI на високих частотах (понад 10 МГц) внутрішньому буферу чипа потрібен додатковий такт для вибірки даних із регістра. Перший зчитаний байт повертає сміття, і лише наступний байт містить реальний результат.

### Перевірка ревізії кремнію в коді драйвера (Probe)
Щоб драйвер залишався сумісним як зі старими, так і з виправленими новими партіями мікросхем, під час запуску виконують динамічну ідентифікацію ревізії:

:::tabs
```c
/* Перевірка ревізії кремнію та вибір обхідного шляху (C) */
#define REG_REVISION_ID     0x0C
#define SILICON_REV_A       0x01
#define SILICON_REV_B       0x02

void sensor_probe_workaround(uint8_t dev_addr) {
    uint8_t rev_id = 0;
    i2c_read_byte(dev_addr, REG_REVISION_ID, &rev_id);

    if (rev_id == SILICON_REV_A) {
        /* Активуємо спеціальний обхідний шлях для дефектної ревізії А */
        apply_errata_workaround_es042();
    }
}
```
```cpp
/* Типобезпечна перевірка ревізії кремнію (C++) */
#include <cstdint>
#include <expected>

namespace driver {

enum class SiliconRev : uint8_t {
    RevA = 0x01,
    RevB = 0x02

        if (static_cast<SiliconRev>(rev_raw) == SiliconRev::RevA) {

    }
}
```

## Покроковий алгоритм розбору нового даташита

Щоб структурувати процес роботи з новою документацією, професійні розробники прошивок дотримуються чіткого алгоритму дій:

1. **Ідентифікація та живлення:**
   - Знайти в даташиті адресу `WHO_AM_I` (або `CHIP_ID`) та очікуване значення константи.
   - Перевірити таблицю Recommended Operating Conditions: визначити час запуску чипа після подачі живлення (`t_startup` / `t_boot`).
2. **Конфігурація шини:**
   - З'ясувати 7-бітну I2C адресу та стан апаратних пінів конфігурації (`AD0`, `SA0`).
   - Для SPI: визначити режим роботи (`CPOL`, `CPHA`) та максимальну тактову частоту шини.
3. **Аналіз карти регістрів:**
   - Скласти таблицю конфігураційних регістрів (R/W), визначити біти вибору ODR, FSR та увімкнення осей.
   - Обов'язково знайти біт блокування оновлення блоків (`BDU`) і активувати його.
   - Визначити тип доступу до статусних регістрів (RO, W1C або COR).
4. **Вичитування даних:**
   - З'ясувати формат автоінкременту (наявність маски `0x80` для ST або спеціальних прапорців).
   - Перевірити порядок байтів (Little-Endian vs Big-Endian) та розрядність (12, 14, 16 біт).
   - Розрахувати ціну молодшого розряду (Scale Factor) для вибраного діапазону FSR.
5. **Вичитка Errata Sheet:**
   - Знайти розділ виявлених дефектів для вашої ревізії кремнію.
   - Додати в код необхідні затримки, фіктивні читання або процедуру відновлення шини.

Такий системний підхід перетворює роботу з даташитом із хаотичного вгадування на чіткий інженерний процес, гарантуючи стабільну роботу пристрою в будь-яких польових умовах.
