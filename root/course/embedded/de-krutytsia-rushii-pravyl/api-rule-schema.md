# 📋 Специфікація бінарного формату правил та реєстру дескрипторів

Цей документ описує двійковий інтерфейс опису правил автоматизації, структуру таблиці дескрипторів, реєстр змінних і протокол передачі оновлень для детермінованого виконання на 32-бітних мікроконтролерах. Використання бінарних дескрипторів фіксованого розміру замість текстових форматів (JSON або YAML) усуває потребу в динамічному виділенні пам'яті (`malloc`), запобігає фрагментації оперативної пам'яті (SRAM) та гарантує виконання повного циклу перевірки за строго передбачуваний час `O(N)`, де `N` — кількість активних правил.

## Принципи побудови бінарної схеми

У вбудованих системах реального часу інтерпретація правил стикається з трьома апаратними обмеженнями: жорстким лімітом пам'яті, ризиком невирівняного доступу до шини процесора та вимогою нульового динамічного виділення ресурсів під час обчислень. Якщо на рівні локального хаба конфігурація може зберігатися у вигляді гнучких словників Python або документів YAML, то мікроконтролер архітектури ARM Cortex-M або RISC-V повинен отримувати структури, готові до прямої адресації в пам'яті.

Бінарний формат дескриптора проектується під пряме накладання масиву структур на буфер пам'яті без проміжних перетворень чи копіювань. Кожен елемент має розмір, кратний 4 байтам, що виключає генерацію винятків `UsageFault` при читанні 32-бітних полів на процесорах без апаратної підтримки невирівняного доступу (наприклад, Cortex-M0/M0+).

## Структура дескриптора правила (RuleDescriptor)

Кожне правило автоматизації або захисту кодується 16-байтною структурою. Порядок байтів у всіх багатобайтних полях — Little-Endian (молодший байт за меншою адресою), що відповідає нативному порядку пам'яті більшості сучасних мікроконтролерів.

```
Байт    0       1       2       3       4       5       6       7
      ┌───────┬───────┬───────┬───────┬───────┬───────┬───────┬───────┐
      │    rule_id    │     flags     │ cond  │ in_reg│   reserved    │
      ├───────┴───────┴───────┴───────┼───────┼───────┼───────┴───────┤
      │           threshold           │  act  │out_reg│ action_param  │
      └───────────────────────────────┴───────┴───────┴───────────────┘
        8       9      10      11      12      13      14      15
```

### Поля структури

| Поле | Тип | Зсув | Призначення |
|---|---|---|---|
| `rule_id` | `uint16_t` | 0 | Унікальний числовий ідентифікатор правила в таблиці (0x0001–0xFFFF). Нульовий ідентифікатор зарезервовано як маркер порожнього гнізда. |
| `flags` | `uint16_t` | 2 | Бітова маска параметрів виконання, пріоритету та захисту правила. |
| `cond_op` | `uint8_t` | 4 | Код операції умови перевірки (`ConditionOpcode`). Визначає спосіб порівняння значення регістра з порогом. |
| `input_reg` | `uint8_t` | 5 | Індекс вхідного регістра в карті пам'яті (`StateRegisterMap`), значення якого аналізується. |
| `reserved` | `uint16_t` | 6 | Резервне поле для вирівнювання структури за межею 4 байтів. Заповнюється нулями при передачі. |
| `threshold` | `int32_t` | 8 | Значення порогу для умови. Для фізичних величин використовується знаковий формат із фіксованою точкою Q16.16. |
| `action_op` | `uint8_t` | 12 | Код виконуваної дії (`ActionOpcode`), що активується при істинності умови. |
| `output_target`| `uint8_t` | 13 | Індекс цільового регістра виходу, уставки або таймера, на який спрямовано дію. |
| `action_param` | `int16_t` | 14 | Числовий параметр дії (значення цільової уставки, шпаруватість ШІМ або затримка таймера в мілісекундах). |

### Бітові прапорці конфігурації (flags)

- `BIT(0)` — `RULE_FLAG_ENABLED`: дозвіл на обробку правила інтерпретатором у поточному системному такті.
- `BIT(1)` — `RULE_FLAG_SAFETY_CRITICAL`: маркер критичного інваріанта безпеки. Правила з цим прапорцем мають найвищий пріоритет виконання і не можуть бути видалені, вимкнені чи замінені через мережеві команди локального хаба.
- `BIT(2)` — `RULE_FLAG_LATCHING`: тригерний режим (із самоблокуванням). Після спрацьовування правило залишає вихідний стан зафіксованим навіть після повернення вхідної величини в норму. Скидання можливе лише явною системною командою скидання аварії.
- `BIT(3)` — `RULE_FLAG_INVERT_ACTION`: автоскидання дії. Якщо умова стає хибною, інтерпретатор автоматично виконує зворотну дію (наприклад, вимикає реле, якщо воно вмикалося цим правилом).
- `BIT(4)` — `RULE_FLAG_FALLBACK_ACTIVE`: правило активується виключно в режимі втрати зв'язку (*Fallback Safe Mode*), коли лічильник серцебиття від хаба обнулився.

## Таблиця кодів операцій (Opcodes)

### Коди умов (ConditionOpcode)

Інтерпретатор обчислює умову за один прохід без розгалужених рекурсивних викликів:

- `0x01` (`OP_ALWAYS`): умова завжди вважається істинною. Застосовується для безумовних періодичних дій або примусових скидань.
- `0x02` (`OP_LESS_THAN`): перевірка `registers[input_reg] < threshold`. Використовується для контролю мінімального тиску або падіння напруги.
- `0x03` (`OP_GREATER_THAN`): перевірка `registers[input_reg] > threshold`. Застосовується для захисту від перегріву чи струмового перевантаження.
- `0x04` (`OP_EQUAL`): точний збіг значення регістра з порогом `registers[input_reg] == threshold`.
- `0x05` (`OP_NOT_EQUAL`): перевірка відсутності рівності `registers[input_reg] != threshold`.
- `0x06` (`OP_BIT_SET`): побітова перевірка `(registers[input_reg] & threshold) == threshold`. Використовується для аналізу бітових масок помилок сенсорів.
- `0x07` (`OP_BIT_CLEAR`): перевірка очищення бітів `(registers[input_reg] & threshold) == 0`.
- `0x08` (`OP_TIMER_EXPIRED`): перевірка вичерпання системного таймера з індексом `input_reg`. Умова стає істинною, коли різниця поточного системного часу та мітки запуску перевищує `threshold` мілісекунд з урахуванням переповнення лічильника `systick`.

### Коди дій (ActionOpcode)

- `0x10` (`ACT_OUTPUT_SET`): встановлення стану дискретного реле чи виходу `output_target` у значення `action_param` (0 або 1).
- `0x11` (`ACT_SET_SETPOINT`): запис нового значення уставки в регістр `output_target`. Дозволяє правилам вищого пріоритету динамічно коригувати роботу ПІД-регуляторів або лімітів потужності.
- `0x12` (`ACT_ARM_TIMER`): запуск зворотного відліку програмного таймера `output_target` на тривалість `action_param` мілісекунд.
- `0x13` (`ACT_DISARM_TIMER`): негайна зупинка та обнулення лічильника таймера `output_target`.
- `0x14` (`ACT_EMERGENCY_STOP`): аварійне апаратне роззброєння. Здійснює прямий скид бітів дозволу виходів таймерів ШІМ, знеструмлює силові реле та переводить рушій у режим блокування аварії.
- `0x15` (`ACT_INHIBIT_REMOTE`): блокування приймання дистанційних уставок для регістра `output_target`. Захищає локальний контур від зовнішнього втручання під час перехідних процесів.

## Карта регістрів стану (StateRegisterMap)

Для уніфікації роботи рушія правил усі джерела даних та виконавчі вузли відображаються на єдиний лінійний простір 32-бітних знакових регістрів. Це дозволяє використовувати однакові операції порівняння як для аналогових вимірів АЦП, так і для стану дискретних входів чи віртуальних прапорців зв'язку.

```
Діапазон індексів   Група регістрів            Режим доступу   Опис та формат даних
─────────────────────────────────────────────────────────────────────────────────────────────
0x00 .. 0x0F        Sensors (Фізичні давачі)   Read-Only       Температура, тиск, протік, струм (Q16.16 або ціле)
0x10 .. 0x1F        Actuators (Виконавці)      Read / Write    Стан силових реле, шпаруватість ШІМ, клапани
0x20 .. 0x2F        Setpoints (Цільові уставки)Read / Write    Бажані значення температури, тиску, ліміти потужності
0x30 .. 0x37        Lease & Watchdog Timers    System / R/W    Лічильники життя оренди керування та серцебиття від Хаба
0x38 .. 0x3F        Status & Error Flags       Read / Write    Бітові маски апаратних збоїв, аварійних блокувань
```

## Протокол передачі та двоетапна валідація правил

Передача нових правил із локального хаба або шлюзу здійснюється через захищений бінарний фрейм по інтерфейсу UART, SPI або CAN. Щоб запобігти переходу мікроконтролера в некоректний стан під час прийому неповного або пошкодженого пакета, процедура оновлення реалізує двоетапну фіксацію (*Two-Phase Commit*) із використанням тіньового буфера.

### Структура комунікаційного кадру

```
┌────────┬────────┬────────┬──────────────────────────┬────────┐
│  SOF   │ Length │ Type   │  Payload (N * 16 bytes)  │ CRC-16 │
│ 0xAA55 │ 2B     │ 0x01   │  Масив дескрипторів      │ 2B     │
└────────┴────────┴────────┴──────────────────────────┴────────┘
```

1. **Синхробайтом початку кадру (SOF)** є фіксована послідовність `0xAA55`.
2. **Довжина (`Length`)** вказує точну кількість байтів у блоці `Payload`. Вона повинна бути строго кратною 16 байтам.
3. **Тип повідомлення (`Type = 0x01`)** позначає завантаження повної таблиці правил.
4. **Контрольна сума (`CRC-16-CCITT`)** обчислюється над полями `Length`, `Type` та `Payload` за поліномом `0x1021` із початковим значенням `0xFFFF`.

### Процедура валідації на стороні мікроконтролера

Після прийому фрейму мікроконтролер виконує перевірку за таким детермінованим алгоритмом:

1. **Перевірка цілісності:** Обчислюється CRC-16 прийнятого кадру. Якщо сума не збігається, пакет відкидається, а хабу повертається кадр `NACK (0x15)` із кодом помилки `ERR_CRC_MISMATCH`.
2. **Перевірка лімітів пам'яті:** Кількість правил `N = Length / 16` не повинна перевищувати константу `MAX_RULES_COUNT`. При перевищенні повертається помилка `ERR_BUFFER_OVERFLOW`.
3. **Семантична верифікація дескрипторів:** Кожне правило у проміжному буфері перевіряється на коректність:
   - Значення `cond_op` та `action_op` мають належати до переліку підтримуваних кодів операцій.
   - Індекси `input_reg` та `output_target` не повинні виходити за межі карти регістрів (`< TOTAL_REGISTERS_NUM`).
   - Нові правила не мають права модифікувати або вимикати існуючі правила з прапорцем `RULE_FLAG_SAFETY_CRITICAL`.
4. **Атомарне перемикання:** Якщо всі перевірки пройдено успішно, вхідний потік копіюється в робочу таблицю правил у критичній секції із тимчасово забороненими перериваннями або шляхом атомарного оновлення покажчика на активний буфер (*Double Buffering*). Хабу надсилається підтвердження `ACK (0x06)`.
