# 📋 Регістри та CMSIS-інтерфейс маскування переривань Cortex-M

Архітектура процесорів ARM Cortex-M містить спеціалізовану підсистему апаратного керування виключеннями та перериваннями. На відміну від класичних мікроконтролерів із простим глобальним прапорцем дозволу переривань (наприклад, прапорець `I` у регістрах статусу AVR або PIC), ядро Cortex-M пропонує багаторівневу ієрархію маскування, реалізовану через групу спеціальних регістрів ядра (англ. *Core Special Registers*).

Цей довідник містить технічний аналіз регістрів маскування, інструкцій асемблера Thumb-2, інтерфейсу CMSIS (англ. *Cortex Microcontroller Software Interface Standard*) та архітектурних нюансів їхньої взаємодії з конвеєром процесора, кеш-пам'яттю, підсистемою групування пріоритетів та вкладеним векторним контролером переривань (NVIC).

## Спеціальні регістри ядра: призначення та бітові поля

Доступ до спеціальних регістрів процесора Cortex-M не відображається у загальний адресний простір пам'яті (Memory-Mapped I/O). Робота з ними можлива виключно за допомогою спеціалізованих інструкцій процесора `MRS` (читання спеціального регістра в регістр загального призначення) та `MSR` (запис значення з регістра загального призначення у спеціальний регістр). 

Будь-яка спроба виконати інструкції `MRS` чи `MSR` у непривілейованому режимі (англ. *Unprivileged / User Mode*) ігнорується або викликає апаратне виключення захисту пам'яті чи помилку виконання (`UsageFault`).

| Регістр | Розрядність | Доступні бітові поля | Підтримка архітектурою | Функціональне призначення |
| :--- | :--- | :--- | :--- | :--- |
| **`PRIMASK`** | 32 біти | Біт `0`: `PM` (Priority Mask) | ARMv6-M (Cortex-M0/M0+), ARMv7-M (M3/M4/M7), ARMv8-M (M23/M33) | **Глобальна пріоритетна маска.** Якщо біт `PM = 1`, процесор блокує всі апаратні переривання та системні виключення з настроюваним пріоритетом (від 0 до 255). Активними залишаються лише немасковане переривання `NMI` (фіксований пріоритет -2) та обробник критичної аварії `HardFault` (фіксований пріоритет -1). При скиданні в `0` усі дозволені переривання обслуговуються у штатному режимі. |
| **`BASEPRI`** | 32 біти | Біти `[7:0]`: `BASEPRI` (старші біти залежать від реалізації NVIC) | ARMv7-M (Cortex-M3/M4/M7), ARMv8-M Mainline (Cortex-M33) | **Базовий поріг пріоритету.** Якщо значення відмінне від нуля, процесор маскує всі переривання, чий рівень пріоритету є чисельно **більшим або рівним** за встановлений поріг (менш термінові). Переривання з вищим пріоритетом (чисельно меншим значенням) продовжують виконуватися без затримок. Значення `0` повністю вимикає фільтрацію за порогом. Відсутній у Cortex-M0/M0+. |
| **`BASEPRI_MAX`** | 32 біти | Біти `[7:0]`: `BASEPRI_MAX` (псевдорегістр для запису) | ARMv7-M (Cortex-M3/M4/M7), ARMv8-M Mainline (Cortex-M33) | **Умовне маскування порогу.** Працює як цільовий псевдорегістр для інструкції `MSR`. Оновлює фізичний регістр `BASEPRI` лише тоді, коли нове значення встановлює суворіше маскування (тобто є чисельно меншим за поточне ненульове значення або якщо поточне значення `BASEPRI` дорівнювало 0). Запобігає випадковому розмаскуванню переривань у вкладеному коді. |
| **`FAULTMASK`** | 32 біти | Біт `0`: `FM` (Fault Mask) | ARMv7-M (Cortex-M3/M4/M7), ARMv8-M Mainline (Cortex-M33) | **Маска аварійних помилок ядра.** Якщо біт `FM = 1`, процесор підвищує поточний базовий пріоритет виконання до `-1`, блокуючи всі виключення, включаючи `HardFault`, `MemManage`, `BusFault` та `UsageFault`. Єдине активне джерело переривань — `NMI`. Апаратура автоматично скидає `FAULTMASK` у `0` під час повернення з будь-якого обробника виключення (окрім NMI). |
| **`IPSR`** | 32 біти | Біти `[8:0]`: `ISR_NUMBER` | Усі процесори Cortex-M | **Регістр статусу поточного переривання (частина xPSR).** Зчитується тільки для читання. Містить номер поточного активного виключення: `0` — фоновий потік (Thread Mode), `1..15` — системні виключення (Reset, NMI, HardFault, SysTick, PendSV), `>= 16` — номер зовнішнього апаратного переривання периферії (IRQ0, IRQ1 тощо). |

## Асемблерні інструкції керування масками

Архітектура Thumb-2 надає прямі та високоефективні інструкції для модифікації масок переривань, більшість із яких виконуються за один такт процесора:

```asm
; --- 1. Швидке глобальне керування через CPS (Change Processor State) ---
CPSID   i             ; Встановити PRIMASK = 1 (вимкнути всі масковані переривання)
CPSIE   i             ; Скинути PRIMASK = 0   (увімкнути всі переривання)

CPSID   f             ; Встановити FAULTMASK = 1 (вимкнути всі виключення, крім NMI)
CPSIE   f             ; Скинути FAULTMASK = 0   (дозволити аварійні виключення)

; --- 2. Універсальний доступ до спеціальних регістрів через MRS / MSR ---
MRS     r0, PRIMASK   ; Зчитати PRIMASK у регістр r0 (1 такт)
MSR     PRIMASK, r0   ; Записати значення r0 у PRIMASK (1 такт)

MRS     r0, BASEPRI   ; Зчитати поточний поріг BASEPRI в r0
MSR     BASEPRI, r0   ; Записати новий поріг у BASEPRI

MSR     BASEPRI_MAX, r0 ; Умовний запис: оновлює BASEPRI тільки якщо r0 підвищує пріоритет маски

MRS     r0, FAULTMASK ; Зчитати поточний стан FAULTMASK
MSR     FAULTMASK, r0 ; Відновити FAULTMASK

MRS     r0, IPSR      ; Зчитати номер поточного виключення для діагностики контексту
```

## Розрахунок зміщення бітів у BASEPRI та конфігурація NVIC

Один із найпоширеніших підводних каменів при роботі з `BASEPRI` полягає в тому, як саме апаратний контролер NVIC трактує значення пріоритету.

У специфікації ARM Cortex-M регістри пріоритетів NVIC та регістр `BASEPRI` є 8-бітними, але виробники мікроконтролерів (STMicroelectronics, NXP, Microchip, Renesas) реалізують лише фіксовану кількість старших бітів пріоритету (зазвичай 4 біти для STM32, що дає 16 рівнів пріоритету від 0 до 15, або 3 біти для NXP LPC, що дає 8 рівнів). 

Невикористані молодші біти апаратно зафіксовані в нуль і вирівнюються за лівим краєм байта:

```
Формат байта пріоритету (для 4 біт NVIC, __NVIC_PRIO_BITS = 4):
┌───────────┬───────────┬───────────┬───────────┬───────────┬───────────┬───────────┬───────────┐
│ Біт 7     │ Біт 6     │ Біт 5     │ Біт 4     │ Біт 3     │ Біт 2     │ Біт 1     │ Біт 0     │
│ [ PRIO3 ] │ [ PRIO2 ] │ [ PRIO1 ] │ [ PRIO0 ] │     0     │     0     │     0     │     0     │
└───────────┴───────────┴───────────┴───────────┴───────────┴───────────┴───────────┴───────────┘
 ◄──────── Реалізовані біти пріоритету ────────► ◄── Невикористані апаратні біти (завжди 0) ──►
```

Тому для маскування переривань із пріоритетом `5` (двійкове `0101_2`) не можна просто записати число `5` у регістр `BASEPRI`. Значення пріоритету необхідно змістити ліворуч на кількість нереалізованих молодших бітів:

:::tabs
```c
/* Формула розрахунку байта для BASEPRI */
#define NVIC_PRIO_BITS  4U // Для більшості чіпів Cortex-M3/M4/M7
#define CALC_BASEPRI(prio) ((uint8_t)((prio) << (8U - NVIC_PRIO_BITS)))

/* Пріоритет 5 стає значенням 0x50 */
uint8_t basepri_val = CALC_BASEPRI(5U); // 5 << 4 = 0x50
__set_BASEPRI(basepri_val);
```
```cpp
#include <cstdint>

constexpr std::uint32_t kNvicPrioBits = 4U;

[[nodiscard]] constexpr std::uint8_t calc_basepri(std::uint8_t priority) noexcept {
    return static_cast<std::uint8_t>(priority << (8U - kNvicPrioBits));
}

// Пріоритет 5 перетворюється на 0x50 під час компіляції
constexpr std::uint8_t kBasepriThreshold = calc_basepri(5U);
```
:::

Якщо записати в `BASEPRI` сире значення `0x05`, процесор відкине молодші біти (вони дорівнюють нулю) і вважатиме, що в регістр записано нуль. У результаті маскування взагалі не увімкнеться, і система залишиться повністю незахищеною.

### Вплив групування пріоритетів (PRIGROUP) на BASEPRI

У системному контролері SCB регістр `AIRCR` містить бітове поле `PRIGROUP` (Priority Grouping). Це поле розділяє біти пріоритету NVIC на дві складові:
1. **Витісняючий пріоритет (Preempt Priority):** визначає здатність одного обробника переривати виконання іншого.
2. **Підпріоритет (Subpriority):** визначає черговість запуску обробників, якщо дві події надійшли одночасно.

Важливий інженерний факт: **регістр `BASEPRI` повністю ігнорує конфігурацію PRIGROUP**. Апаратне маскування в ядрі порівнює значення `BASEPRI` з повним 8-бітним представленням пріоритету вхідного виключення без розділення на групи. 

Саме тому операційна система FreeRTOS суворо вимагає, щоб усі біти пріоритету були налаштовані як витісняючі (конфігурація `NVIC_PRIORITYGROUP_4` у бібліотеках HAL, де всі 4 біти віддані під Preempt Priority, а Subpriority відсутній). Якщо конфігурація `PRIGROUP` змішана, виклик системних функцій з обробників переривань може викликати спрацювання захисного макросу `configASSERT()`.

## Ескалація помилок ядра при активному PRIMASK

Особливу увагу слід звернути на поведінку мікроконтролера у випадку виникнення системних помилок (Faults) під час перебування всередині критичної секції.

Якщо під час активного прапорця `PRIMASK = 1` код програми здійснює помилкову операцію (наприклад, звернення за неіснуючою адресою шини пам'яті `BusFault`, спробу виконання недійсної інструкції чи ділення на нуль `UsageFault` або порушення прав доступу MPU `MemManage`), процесор опиняється у критичному стані:
1. Настроювані обробники помилок (`BusFault_Handler`, `UsageFault_Handler`) заблоковані бітом `PRIMASK`.
2. Ядро не може відкласти виконання фатальної помилки, тому апаратура ініціює **ескалацію помилки** (англ. *Fault Escalation*).
3. Процесор примусово генерує виключення **`HardFault`**, оскільки `HardFault` має пріоритет `-1` і не блокується регістром `PRIMASK`.

Якщо ж помилка шини виникає під час активного регістра `FAULTMASK = 1` (який блокує навіть `HardFault`), процесор переходить у стан незворотного апаратного блокування — **Lockup State**. У цьому режимі ядро повністю припиняє вибірку інструкцій, шина зависає, і повернути систему до життя може лише зовнішнє апаратне скидання (Reset) або спрацювання сторожового таймера Watchdog.

## Взаємодія з конвеєром процесора та бар'єри пам'яті

На сучасних конвеєрних ядрах (особливо Cortex-M7 із суперскалярним подвійним виконанням інструкцій та кешами L1) зміна регістрів маски має кілька критичних аспектів виконання:

1. **Затримка дії маски:** Інструкція `CPSID i` або `MSR PRIMASK, rX` змінює стан конвеєра ядра негайно. Наступна за нею інструкція гарантовано виконується в захищеному контексті.
2. **Буфер запису пам'яті (Store Buffer):** Якщо перед входом у критичну секцію або перед виходом із неї виконувався запис у пам'ять (`STR`), дані можуть тимчасово затриматися в буфері запису системної шини. Для гарантії того, що всі операції збереження фізично завершилися в пам'яті до зміни маски, застосовують апаратну інструкцію бар'єра даних:
   ```asm
   DSB    ; Data Synchronization Barrier: чекає завершення всіх операцій на шині
   ISB    ; Instruction Synchronization Barrier: скидає конвеєр інструкцій
   ```
3. **Бар'єр оптимізації компілятора:** CMSIS-функції `__disable_irq()` та `__set_PRIMASK()` у сучасних версіях CMSIS містять внутрішній клоббер пам'яті, проте в явному коді критичних секцій рекомендується дублювати `__asm volatile("" ::: "memory")`, щоб запобігти спекулятивному перенесенню коду оптимізатором GCC/Clang.

## Інтерфейс CMSIS Core Intrinsics

Стандарт CMSIS уніфікує доступ до спеціальних регістрів для компіляторів GCC, Arm Clang, IAR та Keil. Усі функції оформлені як інлайнові інструкції ядра:

:::tabs
```c
#include "cmsis_compiler.h"
#include <stdint.h>
#include <stdbool.h>

/*
 * Приклад опитування та безпечного маскування переривань через CMSIS
 */
void cmsis_demonstration(void) {
    /* 1. Глобальне маскування через PRIMASK */
    uint32_t saved_primask = __get_PRIMASK();
    __disable_irq();
    
    // Перевірка, чи активні переривання в системі
    bool interrupts_were_enabled = (saved_primask == 0U);
    (void)interrupts_were_enabled;
    
    __set_PRIMASK(saved_primask); // Точне відновлення

    /* 2. Селективне маскування через BASEPRI (лише Cortex-M3/M4/M7/M33) */
#if (__CORTEX_M >= 3U)
    uint32_t saved_basepri = __get_BASEPRI();
    
    // Маскуємо переривання з пріоритетом 4 і нижче (0x40 для 4 біт NVIC)
    __set_BASEPRI(0x40U);
    
    // Безпечне вкладене маскування
    __set_BASEPRI_MAX(0x20U); // Підвищуємо поріг до пріоритету 2
    
    __set_BASEPRI(saved_basepri); // Відновлюємо початковий стан
#endif

    /* 3. Перевірка контексту виконання */
    uint32_t active_exception = __get_IPSR();
    if (active_exception == 0U) {
        // Код виконується у фоновому потоці (Thread Mode / main / RTOS task)
    } else {
        // Код виконується всередині ISR з номером active_exception
    }
}
```
```cpp
#include "cmsis_compiler.h"
#include <cstdint>

namespace embedded::cpu {

enum class CpuMode {
    Thread,  // Головний потік або завдання RTOS
    Handler  // Обробник переривання (ISR)
};

[[nodiscard]] inline CpuMode current_mode() noexcept {
    return (__get_IPSR() == 0U) ? CpuMode::Thread : CpuMode::Handler;
}

[[nodiscard]] inline std::uint32_t get_active_irq_number() noexcept {
    const std::uint32_t ipsr = __get_IPSR();
    return (ipsr >= 16U) ? (ipsr - 16U) : 0U;
}

[[nodiscard]] inline std::uint32_t read_primask() noexcept {
    return __get_PRIMASK();
}

inline void write_primask(std::uint32_t value) noexcept {
    __set_PRIMASK(value);
}

#if (__CORTEX_M >= 3U)
[[nodiscard]] inline std::uint32_t read_basepri() noexcept {
    return __get_BASEPRI();
}

inline void write_basepri(std::uint32_t threshold) noexcept {
    __set_BASEPRI(threshold);
}

inline void write_basepri_max(std::uint32_t threshold) noexcept {
    __set_BASEPRI_MAX(threshold);
}
#endif

} // namespace embedded::cpu
```
:::

## Зневадження та діагностика стану регістрів у GDB та OpenOCD

Під час пошуку помилок взаємного блокування або з'ясування причин, чому мікроконтролер перестав реагувати на апаратні події, стан масок переривань можна безпосередньо зчитати через інтерфейс налагоджувача GDB:

```gdb
# Вивід значень спеціальних регістрів ядра
(gdb) info registers primask basepri faultmask ipsr
primask        0x1                 1
basepri        0x50                80
faultmask      0x0                 0
ipsr           0x0                 0

# Перевірка наявності активного переривання:
# Якщо ipsr == 0, процесор виконує потік main() або завдання RTOS
# Якщо ipsr == 15, активне системне переривання SysTick
# Якщо ipsr == 54, активне переривання периферії IRQ38 (наприклад, USART1 на STM32)

# Увімкнення режиму маскування переривань під час покрокового налагодження в OpenOCD:
(gdb) monitor cortex_m maskisr on
```

Команда `monitor cortex_m maskisr on` є вкрай корисною: вона автоматично маскує переривання під час виконання покрокових інструкцій (`step` / `next`) у GDB, запобігаючи нескінченним стрибкам у таймерний обробник `SysTick_Handler` під час зневадження фонового алгоритму.

## Архітектурні відмінності між профілями Cortex-M

| Архітектурний профіль | Сімейство ядер | Підтримка `BASEPRI` | Підтримка `FAULTMASK` | Підтримка `LDREX`/`STREX` | Особливості обробки критичних секцій |
