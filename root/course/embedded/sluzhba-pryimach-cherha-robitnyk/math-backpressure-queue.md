# 🧮 Математична модель демпферної черги та динаміка зворотного тиску

Математичне моделювання черги прийому телеметрії дає інженерну відповідь на питання, якого розміру має бути буфер, скільки паралельних воркерів необхідно для стабільної системи та на яких порогових рівнях вмикати зворотний тиск, щоб уникнути колапсу сервера під час пікового шторму підключень.

Цей аналіз базується на класичній теорії масового обслуговування (моделі M/M/1/K та M/D/1/K), законі Літтла, диференціальному рівнянні балансу буфера під час імпульсного навантаження та критеріях стійкості гістерезисного керування зворотним тиском.

---

## 1. Баланс потоків та закон Літтла

Розглянемо конвеєр прийому як систему масового обслуговування зі скінченною місткістю черги `K`.

Позначимо основні параметри системи:
- `λ` (лямбда) — середня швидкість надходження кадрів від мережевих приймачів (кадрів за секунду, кадр/с або eps).
- `μ_воркер` — середня швидкість обробки одного кадру одним потоком воркера: `μ_воркер = 1 / T_обробки`, де `T_обробки` — час розбору, валідації та упаковки події.
- `N` — кількість паралельних робочих потоків у пулі.
- `μ` (мю) — сумарна продуктивність пулу робітників: `μ = N · μ_воркер`.
- `ρ` (ро) — коефіцієнт завантаження системи (інтенсивність трафіку): `ρ = λ / μ`.

### Умова стаціонарності та стійкості черги

```
ρ = λ / μ < 1.0
```

Якщо `ρ < 1.0`, математичне сподівання кількості заявок у системі залишається обмеженим, і черга в середньому не зростає до нескінченності. Якщо `ρ ≥ 1.0`, система переходить у нестаціонарний перевантажений режим, і черга лінійно заповнюється зі швидкістю накопичення `dQ(t)/dt = λ - μ`.

### Закон Літтла (Little's Law)

У стаціонарному стаціонарному режимі середня кількість елементів у черзі `L_q` прямо пропорційна інтенсивності вхідного потоку `λ` та середньому часу очікування повідомлення в буфері `W_q`:

```
L_q = λ · W_q
```

Звідси середній час затримки доставки телеметрії (Ingestion Lag), що вноситься демпферною чергою:

```
W_q = L_q / λ
```

Для системи масового обслуговування з детермінованим часом обробки (модель M/D/1, де час роботи парсера фіксований завдяки фіксованому розміру кадру 24 байти), середня довжина черги `L_q` виражається через формулу Поллачека — Хінчина:

```
L_q = (ρ²) / (2 · (1 - ρ))
```

При завантаженні системи `ρ = 0.70` (70% утилізації пулу воркерів) середня черга становить лише `0.7² / (2 · 0.3) ≈ 0.82` кадри, тобто затримка в буфері практично відсутня. Проте при наближенні `ρ → 0.95` середня довжина черги експоненційно зростає до `0.95² / (2 · 0.05) ≈ 9.0` кадрів.

## 2. Модель розрахунку місткості демпферного буфера під час залпового піку

У реальних IoT-системах трафік не є пуассонівським стаціонарним процесом. Найнебезпечнішим сценарієм є залповий пік (Thundering Herd), коли після відновлення живлення в районі або перезапуску польового концентратора `M` пристроїв одночасно надсилають накопичені пакети протягом короткого інтервалу `T_burst`.

Нехай:
- `M` — кількість одночасно активованих пристроїв (наприклад, 50 000 вузлів).
- `T_burst` — тривалість пікового залпу (наприклад, 2.0 с).
- `λ_peak` — пікова швидкість прийому під час залпу: `λ_peak = M / T_burst = 25 000 кадр/с`.
- `μ` — сумарна пропускна здатність пулу робітників: `μ = 5 000 кадр/с` (наприклад, 10 воркерів із продуктивністю 500 кадр/с кожен).

Під час інтервалу `[0, T_burst]` швидкість надходження перевищує швидкість обробки: `λ_peak > μ`.

### Динаміка накопичення черги

Швидкість накопичення кадру в черзі є різницею швидкостей входу та виходу:

```
dQ(t)/dt = λ_peak - μ
```

Максимальна глибина черги `Q_max`, яка досягається в момент завершення імпульсу `t = T_burst`:

```
Q_max
= ∫ (λ_peak - μ) dt      [інтегрування різниці швидкостей від 0 до T_burst]
= (λ_peak - μ) · T_burst [винесення постійної різниці за знак інтеграла]
= M - μ · T_burst        [підстановка визначення λ_peak = M / T_burst]
```

### Числовий розрахунок для пікового шторму

Підставимо параметри промислової інсталяції:
```
M = 50 000 кадрів
T_burst = 2.0 с
λ_peak = 25 000 кадр/с
μ = 5 000 кадр/с

Q_max
= (25 000 - 5 000) · 2.0 [різниця швидкостей помножена на час сплеску]
= 20 000 · 2.0          [чисте перевищення вхідного потоку]
= 40 000 кадрів         [максимальна глибина черги наприкінці сплеску]
```

### Час повного розвантаження черги (Drain Time)

Після завершення залпу (`t > T_burst`) вхідний потік повертається до нормального фонового значення `λ_normal = 500 кадр/с`. Час `T_drain`, необхідний воркерам для повного спустошення демпферного буфера до нульового рівня:

```
T_drain
= Q_max / (μ - λ_normal) [баланс швидкості вичитування залишкового буфера]
= 40 000 / (5 000 - 500) [підстановка обчисленого піку та швидкостей]
= 40 000 / 4 500         [чиста швидкість спустошення черги]
≈ 8.89 с                 [ділення: час повного розвантаження демпфера]
```

Отже, буфер місткістю не менше 40 000 елементів дозволяє системі повністю поглинути піковий удар без втрати жодного кадру, розвантаживши чергу за 8.9 с.

## 3. Розрахунок порогових рівнів ватерпостів (Watermarks Hysteresis)

Щоб керувати зворотним тиском без паразитного брязкоту (частого перемикання станів читання/паузи на дескрипторах сокетів `epoll`), використовується гістерезис із двома ватерпостами:
- `W_high` (High Watermark) — поріг активації зворотного тиску (пауза вичитування сокетів або звуження вікна TCP).
- `W_low` (Low Watermark) — поріг деактивації зворотного тиску (відновлення вичитування сокетів).

```
Місткість буфера: K
W_high = K · α_high    (де α_high ≈ 0.80 .. 0.85)
W_low  = K · α_low     (де α_low  ≈ 0.50 .. 0.60)
```

### Запас надійності до переповнення (Headroom)

Коли рівень заповнення черги досягає `W_high`, сигнал зворотного тиску не зупиняє вхідний трафік миттєво. У системних буферах сокетів ядра ОС (`SO_RCVBUF`), чергах мережевих карт (NIC Ring) та транзитних маршрутизаторах ще перебувають кадри в польоті (*In-Flight Packets*).

Обсяг залишкового буфера (Headroom):

```
H = K - W_high = K · (1 - α_high)
```

Цей обсяг повинен гарантовано вміщувати вхідний потік за час сумарної реакції транспортного рівня `T_react` (RTT мережі + час реакції TCP на отримання пакета зі звуженим вікном):

```
H ≥ λ_peak · T_react
```

Якщо піковий потік `λ_peak = 25 000 кадр/с`, а час реакції мережевого стека `T_react = 200 мс = 0.2 с`:

```
H_min = 25 000 · 0.2 = 5 000 кадрів
```

Розрахунок необхідної мінімальної місткості `K` при обраному коефіцієнті `α_high = 0.85`:

```
K · (1 - 0.85) ≥ 5 000
= 0.15 · K ≥ 5 000     [спрощення коефіцієнта запасу]
= K ≥ 5 000 / 0.15     [ділення на частку запасу]
≈ K ≥ 33 334 кадри     [мінімальна місткість для уникнення переповнення]
```

Це суворе математичне обґрунтування того, чому при місткості `K = 50 000` вибір `W_high = 42 500 (85%)` та `W_low = 30 000 (60%)` гарантує повну відсутність переповнення буфера до моменту спрацювання механізму TCP Flow Control на стороні відправника.

## 4. Алгоритм обмеження частоти: Маркерний кошик (Token Bucket)

Для захисту від окремих несправних вузлів або апаратних збоїв прошивки, що починають генерувати спам-пакети з частотою 10 000 кадр/с, на рівні приймача застосовується алгоритм Token Bucket для кожного ідентифікатора пристрою `device_id`.

Параметри кошика:
- `r` — швидкість поповнення маркерів (маркерів за секунду, тобто дозволена середня частота телеметрії для одного вузла, наприклад 1.0 маркер/с).
- `B` — максимальна місткість кошика (максимальний дозволений розмір локального спалаху, наприклад B = 5 маркерів).
- `tokens(t)` — поточна доступна кількість маркерів у момент часу `t`.

### Динаміка маркерів

При надходженні пакета в момент `t` від попереднього прийому в момент `t_last`:

```
Δt = t - t_last
tokens(t) = min(B, tokens(t_last) + r · Δt)
```

Правило фільтрації:
1. Якщо `tokens(t) ≥ 1.0`: пакет вважається легітимним і приймається в чергу. Стан оновлюється: `tokens(t) = tokens(t) - 1.0`, `t_last = t`.
2. Якщо `tokens(t) < 1.0`: ліміт вичерпано (Rate Limit Exceeded). Пакет негайно відкидається на рівні приймача без постановки в основну чергу, що зберігає ресурси процесора та пам'яті воркерів.
