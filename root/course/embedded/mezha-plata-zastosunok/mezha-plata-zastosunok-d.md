</preknowlist>

Команда інженерів запускає в серійне виробництво автономний радіотрекер для моніторингу рефрижераторних контейнерів. Перша ревізія друкованої плати (Rev A) побудована на мікроконтролері STM32F401, де аварійний світлодіод підключено до виводу `PB12` за схемою Active-High, комутація живлення давача температури виконується польовим транзистором N-MOSFET на виводі `PA8`, а сам давач SHT30 сидить на шині `I2C1` за 7-бітною адресою `0x44`. Через пів року світова криза постачання напівпровідників змушує фабрику терміново випустити ревізію Rev B: мікроконтролер змінюють на ESP32-S3, для зменшення струму витоку ключ живлення сенсорів замінюють на P-MOSFET з інверсною логікою на піні `GPIO15`, а замість дефіцитного SHT30 встановлюють BME280 на шині `I2C0` за адресою `0x76`.

Прошивка першої ревізії виявляється повністю непридатною: виклики `HAL_GPIO_WritePin(GPIOB, GPIO_PIN_12, 1)`, прямі звернення до регістрів шини та магічні константи `0x44` розкидані по сорока файлах бізнес-логіки, кінцевих автоматів та обробки телеметрії. Заміна одного схемотехнічного ключа перетворюється на повне переписування проєкту та три місяці затримки поставок. Спроба локально протестувати алгоритм ухвалення рішення про перегрів вантажу вимагає паяльника та осцилографа, оскільки код неможливо навіть скомпілювати на робочому комп'ютері під керуванням x86-64 Linux чи macOS через відсутність файлів `stm32f4xx.h`.

Ця системна вразливість виникає через відсутність фундаментального архітектурного бар'єра — **межі між платою та застосунком**. Єдиний спосіб убезпечити комерційний продукт від апаратних змін та забезпечити стовідсоткове автоматизоване модульне тестування — це перенесення всіх схемотехнічних знань у спеціалізований ізолюючий шар: **пакет підтримки плати** (*Board Support Package*, BSP), побудований за строгим абстрактним контрактом.

### Анатомія апаратного протікання: чому прямий доступ до заліза руйнує прошивку

У процесі швидкого створення прототипів розробники часто обирають найкоротший шлях: прямий виклик функцій вендорного HAL або маніпулювання регістрами безпосередньо з високорівневих алгоритмів. Типовий фрагмент обробки аварії в такому моноліті виглядає оманливо простим:

:::tabs
```c
// Антипатерн: бізнес-логіка знає схемотехніку плати
void process_temperature_alert(float current_temp) {
    if (current_temp > 45.0f) {
        // Засвітити червоний світлодіод на піні PB12
        HAL_GPIO_WritePin(GPIOB, GPIO_PIN_12, GPIO_PIN_SET);
        // Знеструмити зовнішній радіомодуль через ключ PE3
        HAL_GPIO_WritePin(GPIOE, GPIO_PIN_3, GPIO_PIN_RESET);
    }
}
```
```cpp
// Антипатерн: бізнес-логіка на C++ із прямим викликом вендорного HAL
void process_temperature_alert(float current_temp) noexcept {
    if (current_temp > 45.0f) {
        // Пряма прив'язка до конкретних пінів MCU та вендорних типів
        HAL_GPIO_WritePin(GPIOB, GPIO_PIN_12, GPIO_PIN_SET);
        HAL_GPIO_WritePin(GPIOE, GPIO_PIN_3, GPIO_PIN_RESET);
    }
}
```
:::

Цей короткий фрагмент створює одразу п'ять невидимих залежностей, які жорстко прив'язують чистий математичний алгоритм до конкретного зразка текстоліту:
1. **Залежність від сімейства мікроконтролера**: тип `GPIO_PIN_SET` та функція `HAL_GPIO_WritePin` існують лише в екосистемі STM32Cube. Портування на Nordic nRF52 чи Espressif ESP32 вимагає ручного редагування кожного такого виклику.
2. **Залежність від трасування друкованої плати**: прив'язка до портів `GPIOB` та `GPIOE` означає, що будь-яке перерозведення доріжок схемотехніком ламає логіку.
3. **Залежність від схемотехнічної полярності (Active-High / Active-Low)**: якщо світлодіод підключений катодом до піна MCU (Active-Low), для його вмикання потрібен `GPIO_PIN_RESET`, а не `GPIO_PIN_SET`. Якщо в ревізії Rev B світлодіод перепаяли анодом до піна (Active-High), індикатор почне сигналізувати з точністю до навпаки.
4. **Залежність від типу транзисторного ключа**: пряме встановлення низького рівня на `PE3` для вимкнення живлення передбачає наявність N-канального MOSFET. Якщо для зменшення струму витоку інженери встановили P-MOSFET, низький рівень на затворі навпаки відкриє транзистор і подасть напругу.
5. **Неможливість модульного тестування на хості**: скомпілювати цей файл звичайним компілятором `gcc` на комп'ютері розробника неможливо, оскільки компілятор вимагає апаратні структури пам'яті ядра ARM Cortex-M.

Коли такі виклики розчиняються у тисячах рядків коду, система втрачає гнучкість. Спроба оновити апаратну ревізію вимагає суцільного регресійного тестування кожного рядка прошивки.

> 🔧 **Навіщо це.** Межа «плата ↔ застосунок» формулює залізне правило інформаційного приховування (за Девідом Парнасом): **високорівневий код повинен виражати семантичний намір, а не спосіб його електричної реалізації**. Застосунок каже «увімкни попереджувальний індикатор», а шар BSP вирішує, чи для цього треба виставити логічний нуль на пін `PB12`, надіслати байт через розширювач портів I2C чи змінити скважність ШІМ-каналу.

### Що таке BSP: пакет підтримки плати як непорушний контракт

Для побудови надійної межі необхідно чітко розмежовувати два поняття, які розробники-початківці часто плутають: вендорний HAL чипа та BSP конкретної плати.

| Критерій | Апаратний рівень чипа (Silicon HAL / LL) | Пакет підтримки плати (BSP) |
| :--- | :--- | :--- |
| **Що абстрагує** | Внутрішню периферію кристала MCU (регістри UART, I2C, таймери) | Конкретну друковану плату з усіма розпаяними мікросхемами |
| **Хто розробляє** | Виробник мікроконтролера (STMicroelectronics, Espressif, NXP) | Розробник конкретного пристрою / схемотехнічна команда |
| **Знання плати** | Нульове (HAL не знає, де світлодіод, а де ключ живлення) | Повне (знає піни, полярності, затримки стабілізації, дільники) |
| **Рівень даних** | Байти, регістрові маски, прапорці готовності DMA | Фізичні величини (мВ, °C, Па), логічні стани системи |
| **Переносність** | Працює лише на мікроконтролерах даного виробника | Працює як адаптер між будь-яким HAL та бізнес-кодом |

BSP є перекладачем між абстрактним світом бізнес-правил та фізичним світом мідних доріжок. Він бере на себе всю низькорівневу роботу з апаратурою:
- Конфігурацію режимів тактування (HSE, PLL, вибір внутрішнього генератора HSI при збої кварцу);
- Встановлення вихідних рівнів на лініях GPIO до того, як увімкнеться силова частина;
- Послідовну подачу живлення на каскади схеми з дотриманням часових інтервалів (*Power Sequencing*);
- Калібрування та лінеаризацію показань аналогових каналів за вбудованим джерелом опорної напруги `Vrefint`;
- Відновлення заблокованих шин зв'язку (наприклад, генерація 9 тактів SCL для звільнення завислої лінії I2C SDA).

Детальний опис структур даних, кодів повернення та сигнатур функцій дивіться у вставці [Еталонний контракт інтерфейсу BSP (Board Support Package API)](root:embedded/mezha-plata-zastosunok/api-bsp-contract.md).

### Канонічний набір абстракцій BSP: анатомія функцій плати

Щоб межа була повною, BSP повинен надавати замкнений набір функцій, які покривають весь життєвий цикл плати. Розглянемо ключові групи цих абстракцій та їхню внутрішню механіку.

```
┌─────────────────────────────────────────────────────────────────────────┐
│ Канонічний набір інтерфейсів BSP (bsp_interface.h):                     │
│                                                                         │
│ ┌────────────────────────┐  ┌─────────────────────────────────────────┐ │
│ │ Життєвий цикл платформи│  │ board_init(), board_enter_low_power()   │ │
│ ├────────────────────────┤  ├─────────────────────────────────────────┤ │
│ │ Керування актуаторами  │  │ board_led_set(), board_buzzer_tone()    │ │
│ ├────────────────────────┤  ├─────────────────────────────────────────┤ │
│ │ Комутація живлення     │  │ board_power_domain_set(DOMAIN, bool)    │ │
│ ├────────────────────────┤  ├─────────────────────────────────────────┤ │
│ │ Аналоговий моніторинг  │  │ board_get_battery_voltage_mv(&mv)       │ │
│ ├────────────────────────┤  ├─────────────────────────────────────────┤ │
│ │ Кліматичні сенсори     │  │ board_read_environment(&metrics)        │ │
│ └────────────────────────┘  └─────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 1. Життєвий цикл платформи: `board_init()` та `board_enter_low_power()`

Функція `board_init()` викликається першим рядком у точці входу `main()`. Вона відповідає за переведення «голого» мікроконтролера в стабільний робочий стан. 

Типова помилка — залишати виводи невикористаної периферії у стані за замовчуванням (Floating Input). На платі вхідний опір виводів сягає гігаомів; електромагнітні наводки змушують вхідний тригер Шмітта перемикатися з високою частотою, що викликає наскрізні струми в польових транзисторах буфера вводу і збільшує струм споживання на сотні мікроамперів. Функція `board_init()` зобов'язана сконфігурувати всі вільні піни в аналоговий режим (Analog Mode / High-Z), де вхідні цифрові буфери фізично знеструмлені.

При переході в сон функція `board_enter_low_power()` переводить мікроконтролер у стан мінімального енергоспоживання (Stop / Standby / DeepSleep), залишаючи активними лише лінію пробудження від тактового генератора реального часу (RTC) або зовнішнього переривання від кнопки чи акселерометра.

#### 2. Керування індикаторами: `board_led_set()`

Застосунок оперує логічними призначеннями світлодіодів (`BOARD_LED_ID_SYSTEM_STATUS`, `BOARD_LED_ID_WARNING`), а не фізичними пінами.

:::tabs
```c
// bsp_board_rev_a.c: Реалізація для ревізії Rev A (Active-High на PB12)
bsp_status_t board_led_set(board_led_id_t led, board_led_state_t state) {
    switch (led) {
        case BOARD_LED_ID_SYSTEM_STATUS:
            HAL_GPIO_WritePin(GPIOB, GPIO_PIN_12, 
                (state == BOARD_LED_STATE_ON) ? GPIO_PIN_SET : GPIO_PIN_RESET);
            return BSP_STATUS_OK;
        case BOARD_LED_ID_WARNING:
            HAL_GPIO_WritePin(GPIOA, GPIO_PIN_4, 
                (state == BOARD_LED_STATE_ON) ? GPIO_PIN_SET : GPIO_PIN_RESET);
            return BSP_STATUS_OK;
        default:
            return BSP_STATUS_ERR_INVALID_PARAM;
    }
}
```
```cpp
// bsp_board_rev_a.cpp: Реалізація для ревізії Rev A на C++
#include "bsp_interface.hpp"

namespace bsp {

class Stm32BoardRevA final : public IBoardSupport {
public:
    Status led_set(LedId led, LedState state) noexcept override {
        const auto pin_state = (state == LedState::On) ? GPIO_PIN_SET : GPIO_PIN_RESET;
        switch (led) {
            case LedId::SystemStatus:
                HAL_GPIO_WritePin(GPIOB, GPIO_PIN_12, pin_state);
                return Status::Ok;
            case LedId::Warning:
                HAL_GPIO_WritePin(GPIOA, GPIO_PIN_4, pin_state);
                return Status::Ok;
            default:
                return Status::InvalidParam;
        }
    }
    // Інші методи інтерфейсу...
};

} // namespace bsp
```
:::

Якщо в ревізії Rev B полярність індикатора інвертується, зміна вноситься виключно у файл `bsp_board_rev_b.c`. Жоден файл застосунку не зазнає модифікацій.

#### 3. Комутація живлення периферійних доменів: `board_power_domain_set()`

Сучасні автономні пристрої використовують силові перемикачі навантаження (*Load Switches*) або польові транзистори P-MOSFET для повного знеструмлення зовнішніх сенсорів та радіомодулів у паузах між сеансами зв'язку.

Увімкнення живлення периферії — це фізичний процес заряду конденсаторів фільтрації на шині живлення. При замиканні ключа виникає імпульс пускового струму (*Inrush Current*), величина якого визначається сумарною ємністю навантаження `C_load` та швидкістю наростання напруги:

```
I_inrush = C_load · (dV / dt)                [фізичний зв'язок струму та швидкості зміни напруги]
```

Якщо ключ відкривається миттєво (за 1–2 мікросекунди), імпульс струму заряду ємностей 10–47 мкФ може сягати 2–5 амперів. Це викликає різку просадку напруги живлення мікроконтролера нижче порогу скидання Brown-out Reset (BOR) і призводить до спонтанного перезавантаження системи. Крім того, мікросхеми давачів потребують часу на запуск внутрішніх стабілізаторів (Power-On Reset time, зазвичай 5–20 мс).

Шар BSP бере на себе забезпечення безпечного керування цими процесами:
```
Запит від застосунку: board_power_domain_set(SENSORS, true)
  │
  ├─ 1. Відкрити затвор P-MOSFET (виставити логічний 0 на PE3)
  ├─ 2. Витримати калібровану затримку стабілізації (15 мс)
  ├─ 3. Відновити конфігурацію ліній шини I2C (SCL/SDA з аналогового режиму в Alternate Function)
  └─ 4. Повернути керування застосунку зі статусом BSP_STATUS_OK
```

Якщо застосунок вимикає домен живлення (`enable = false`), BSP спочатку переводить лінії I2C/SPI у стан високого імпедансу (High-Z) і лише потім розмикає транзисторний ключ.

#### 4. Аналогові вимірювання: `board_get_battery_voltage_mv()`

Високорівнева логіка ніколи не повинна знати про розрядність АЦП, опорну напругу чи номінали резисторів дільника напруги. Застосунок цікавить виключно одне число: **поточна напруга батареї в мілівольтах**.

Реалізація цієї функції всередині BSP виконує точний математичний перерахунок з урахуванням апаратних похибок:
1. Зчитування коду внутрішнього каналу `VREFINT` мікроконтролера для розрахунку реальної поточної напруги живлення ядра `Vdda`:
```
Vdda = 3300 · VREFINT_CAL / ADC_raw_vref     [калібрування опорної напруги за заводською константою]
```
2. Зчитування коду аналогового каналу батареї `ADC_raw_bat`.
3. Розрахунок напруги на вході виводу мікроконтролера:
```
V_pin = Vdda · ADC_raw_bat / 4095            [переведення 12-бітного коду АЦП у напругу на піні]
```
4. Компенсація коефіцієнта передачі резистивного дільника `R1` (наприклад, 100 кОм) та `R2` (наприклад, 200 кОм):
```
V_bat = V_pin · (R1 + R2) / R2               [формула зворотного перерахунку резистивного дільника]
= V_pin · (100 + 200) / 200                  [підстановка значень R1 = 100 кОм, R2 = 200 кОм]
= V_pin · 1.5                                [спрощення розрахункового коефіцієнта]
```

Застосунок отримує готову фізичну величину `3850 мВ`. Якщо в наступній версії пристрою номінали дільника змінять на `470 кОм` та `1 МОм` для зменшення постійного струму витоку дільника, формула зміниться тільки всередині одного файлу BSP.

### Інженерний компроміс вибору номіналів дільника напруги

Розробка аналогової частини BSP вимагає глибокого розуміння компромісу між статичним енергоспоживанням та часом вибірки вхідного каскаду АЦП.

#### Проблема статичного витоку струму
Підключення резистивного дільника безпосередньо до акумулятора створює постійний шлях витоку струму на землю через резистори `R1 + R2`. При напрузі літієвої батареї `4.2 В`:
- Якщо обрати низькоомні резистори `R1 = 10 кОм`, `R2 = 20 кОм` (сума `30 кОм`):
```
I_leak = 4.2 В / 30000 Ом = 140 мкА          [струм витоку через низькоомний дільник]
```
Для автономного реєстратора зі струмом сну `10 мкА` такий дільник збільшує споживання системи у 15 разів, скорочуючи термін служби батареї з 5 років до 4 місяців.

- Якщо обрати високоомні резистори `R1 = 1 МОм`, `R2 = 2 МОм` (сума `3 МОм`):
```
I_leak = 4.2 В / 3000000 Ом = 1.4 мкА        [струм витоку через високоомний дільник]
```
Струм витоку падає до безпечних `1.4 мкА`, проте виникає проблема динамічної похибки оцифрування АЦП.

#### Фізика заряду вибіркового конденсатора АЦП
Вхідний каскад SAR АЦП містить комутатор та вибірковий конденсатор `C_sample` (типово 5–10 пФ) із внутрішнім опором перемикача `R_switch` (1–5 кОм). Еквівалентний вихідний опір дільника становить паралельне з'єднання резисторів:

```
R_out = (R1 · R2) / (R1 + R2)
= (1000 кОм · 2000 кОм) / 3000 кОм ≈ 667 кОм [вихідний опір дільника]
```

Для заряду ємності `C_sample` до точності 12-бітного АЦП (похибка < 0.5 LSB, що вимагає витримки часу `t > 9 · tau`) необхідний мінімальний час вибірки `T_sample`:

```
tau = (R_out + R_switch) · C_sample
= 670 кОм · 8 пФ ≈ 5.36 мкс                  [постійна часу заряду ємності АЦП]

T_sample_min = 9 · tau
= 9 · 5.36 мкс ≈ 48.2 мкс                    [мінімальний необхідний час вибірки]
```

Якщо BSP сконфігурує стандартний швидкий час вибірки АЦП (наприклад, 1.5 такти при частоті 14 МГц, що дорівнює 0.1 мкс), конденсатор не встигне зарядитися до реального рівня напруги. Результат вимірювання виявиться заниженим на 20–40%.

Шар BSP повністю приховує цю складність: драйвер плати знає реальні номінали дільника на даній ревізії і автоматично встановлює збільшений час вибірки `ADC_SAMPLETIME_480CYCLES` у регістрах конфігурації АЦП, гарантуючи застосунку абсолютну точність без потреби у зовнішніх схемотехнічних розрахунках.

### Переносимість та хостове тестування через Dependency Injection

Ізоляція коду плати відкриває головну перевагу сучасної архітектури: можливість запуску та тестування прошивки на персональному комп'ютері розробника або на серверах безперервної інтеграції (CI/CD) під керуванням Linux, Windows чи macOS.

Для цього використовується патерн **впровадження залежностей** (*Dependency Injection*, DI). Замість того, щоб жорстко викликати глобальні функції, модуль бізнес-логіки отримує інтерфейс BSP ззовні під час ініціалізації.

```
       ┌─────────────────────────────────────────────────────────┐
       │             Ядро застосунку (Application)               │
       │     (Алгоритми, FSM, фільтри, бізнес-правила)           │
       └────────────────────────────┬────────────────────────────┘
                                    │ Залежить ТІЛЬКИ від інтерфейсу
                                    ▼
       ┌─────────────────────────────────────────────────────────┐
       │                 Контракт BSP (IBoardSupport)            │
       └────────────────────────────┬────────────────────────────┘
                                    │
                  ┌─────────────────┴─────────────────┐
                  ▼                                   ▼
┌───────────────────────────────────┐ ┌───────────────────────────────────┐
│     Цільова плата (Target BSP)    │ │      Хостовий мок (Mock BSP)      │
│  bsp_target_stm32.c / esp32.cpp   │ │   bsp_mock_host.c / mock.cpp      │
│  - STM32 HAL / ESP-IDF            │ │   - Фіктивні змінні напруги       │
│  - Фізичні регістри та шини       │ │   - Запис логів викликів          │
│  - Реальний мікроконтролер        │ │   - GoogleTest / Unity на x86-64  │
└───────────────────────────────────┘ └───────────────────────────────────┘
```

Повний практичний приклад побудови модуля супервізора з мок-об'єктом та набором модульних тестів на C та C++ наведено у вставці [Впровадження залежностей (Dependency Injection) для тестування вбудованої логіки на хості](root:embedded/mezha-plata-zastosunok/proj-bsp-hal-di.md).

![Впровадження залежностей для хостових тестів](/root/course/embedded/mezha-plata-zastosunok/img/dependency-injection-host-vs-target.svg)
*Впровадження залежностей (DI): компіляція тієї самої бізнес-логіки для цільового мікроконтролера та для хостових юніт-тестів.*

Переваги такого підходу:
- **Миттєвий зворотний зв'язок**: повний набір із 500 модульних тестів виконується на x86 процесорі за 0.05 секунди замість хвилин прошивання через SWD-програматор.
- **Емуляція граничних та аварійних станів**: мок-об'єкт дозволяє легко змоделювати рідкісні апаратні збої — падіння напруги батареї до 2.9 В під час запису у флеш, відсутність відповіді (NACK) від термодатчика через обрив шини, або затискання лінії SDA на землю. У реальному залізі створення таких умов вимагає підключення лабораторних блоків живлення та закорочування доріжок щупами.

### Апаратні підводні камені та паразитарне живлення (Phantom Powering)

При проєктуванні межі BSP програмні інженери нерідко припускаються фатальної помилки, ігноруючи фізичні закони взаємодії мікросхем. Найнебезпечнішим явищем у низькоспоживаючих системах є **паразитарне живлення** (*Phantom Powering* або *Back-powering*).

#### Фізика виникнення паразитарного живлення

Усі цифрові виводи сучасних інтегральних мікросхем (CMOS) містять вбудовані діоди захисту від електростатичного розряду (ESD Protection Diodes). Один діод підключений анодом до виводу та катодом до внутрішньої шини живлення мікросхеми `VDD`, а другий — анодом до `GND` та катодом до виводу.

```
       Внутрішня шина VDD мікросхеми (знеструмлена: 0 В)
                         ▲
                         │
                        ─┴─  ESD діод захисту
                        ▲ ▲
                         │
Зовнішній вивід ─────────┼─────── Сигнал від MCU (SCL/SDA = 3.3 В)
(наприклад, SCL/SDA)     │
                        ─┴─  ESD діод захисту
                        ▲ ▲
                         │
                         ▼
                        GND
```

Якщо шар BSP знеструмлює датчик (вимикає транзистор у колі `VDD`), але залишає виводи шини I2C (`SCL` та `SDA`) у стані логічної одиниці (3.3 В завдяки підтягувальним резисторам `Pull-Up`), виникає паразитарний струм:
```
3.3 В від шини MCU ──> Підтягувальний резистор ──> Вхід SCL сенсора ──> Внутрішній ESD діод ──> Знеструмлена шина VDD сенсора
```

У результаті:
1. Знеструмлена мікросхема сенсора починає живитися мікрострумом (~0.5–2 мА) через власний цифровий вхід і захисний діод.
2. Внутрішня схема сенсора зависає у невизначеному напівзаживленому стані (*Latch-up*), оскільки напруга живлення становить близько 2.6 В (3.3 В мінус пряме падіння 0.7 В на діоді).
3. При наступній спробі штатно подати живлення сенсор не відповідає на запити шини I2C і блокує лінію `SDA`, закорочуючи її на землю.
4. Пристрій, розрахований на роботу від батарейки протягом 5 років зі струмом сну 10 мкА, споживає 1500 мкА і повністю розряджає акумулятор за два тижні.

#### Програмне правило межі BSP

Пакет підтримки плати зобов'язаний інкапсулювати безпечну послідовність комутації ліній:
- **Перед вимкненням живлення домену**: перевести всі лінії інтерфейсів, підключені до цього домену (I2C SCL/SDA, SPI MOSI/SCK/CS, UART RX/TX), у режим аналогового входу (`GPIO_MODE_ANALOG`) без підтяжки (No-Pull).
- **Після увімкнення живлення домену**: витримати затримку наростання напруги живлення (Power Ramp-Up), і лише після цього реконфігурувати лінії зв'язку в режим альтернативної функції периферійного блоку.

Застосунок ніколи не повинен думати про ESD-діоди та стан ліній шини — це виключна відповідальність реалізації BSP для даної плати.

### Організація вихідного коду проєкту в репозиторії

Для забезпечення повної модульності дерево вихідного коду проєкту поділяється на ізольовані каталоги з чіткими кордонами компіляції:

```
project_root/
├── app/                        # Ядро застосунку (100% переносний C/C++ код)
│   ├── app_main.c
│   ├── state_machine.c
│   └── telemetry.c
│
├── bsp/                        # Пакет підтримки плати
│   ├── include/
│   │   ├── bsp_interface.h     # Відкритий контракт інтерфейсу (IBoardSupport)
│   │   └── bsp_types.h         # Фізичні типи даних та статуси
│   │
│   ├── boards/                 # Конкретні апаратні реалізації
│   │   ├── board_rev_a/        # Реалізація для STM32F401 (Rev A)
│   │   │   └── bsp_rev_a.c
│   │   ├── board_rev_b/        # Реалізація для ESP32-S3 (Rev B)
│   │   │   └── bsp_rev_b.c
│   │   └── board_mock_host/    # Мок-реалізація для юніт-тестів на ПК
│   │       └── bsp_mock.c
│   │
│   └── drivers/                # Драйвери мікросхем плати (BME280, SHT30)
│       ├── bme280.c
│       └── bme280.h
│
├── tests/                      # Модульні тести для хоста (x86-64 / ARM64)
│   ├── test_state_machine.cpp
│   └── test_telemetry.cpp
│
└── CMakeLists.txt              # Скрипт подвійної збірки (Target vs Host)
```

При такому структуруванні папка `app/` не містить жодного шляху пошуку заголовків (`include_directories`), що веде до бібліотек конкретного виробника MCU чи внутрішніх файлів драйверів. Спроба додати прямий виклик вендорної функції негайно блокується системою збірки на етапі компіляції.

### Правила побудови чистої межі BSP

Для збереження чистоти архітектури впродовж усього життєвого циклу продукту команда має дотримуватися семи фундаментальних правил:

1. **Заборона вендорних заголовків у домені застосунку**: Файли бізнес-логіки не повинні містити жодного `#include "stm32f4xx.h"`, `#include "driver/gpio.h"` чи `#include "pico/stdlib.h"`. Єдиний дозволений заголовок для взаємодії з платформою — `bsp_interface.h` (або `bsp_interface.hpp`).
2. **Передача тільки фізичних одиниць**: Жодних сирих кодів АЦП, невідфільтрованих бітових масок чи апаратних регістрових значень. BSP повертає мілівольти, соті градуса Цельсія, гектопаскалі або логічні переліки станів.
3. **Інкапсуляція схемотехнічної полярності**: Застосунок передає намір `BOARD_LED_STATE_ON`, а BSP знає, чи треба встановити високий рівень, низький рівень чи перемкнути відкритий колектор.
4. **Гарантія безпечного живлення**: Будь-яка функція комутації живлення самостійно керує супутніми лініями вводу-виводу для усунення паразитарного живлення через ESD-діоди та витримує необхідні часові затримки стабілізації напруги.
5. **Незмінність бізнес-коду при редизайні друкованої плати**: Зміна піна, перенесення лінії на інший порт, заміна мікросхеми датчика на аналог з іншою адресою I2C вимагає створення нового файлу `bsp_board_v2.c`, але не змінює жодного байта у високорівневій логіці.
6. **Обов'язкова підтримка мок-реалізації для хоста**: Контракт BSP проектується так, щоб для кожної його функції можна було написати легковажну імітацію на C або C++ для миттєвого проходження юніт-тестів у CI/CD пайплайнах.
7. **Контекстна безпека викликів**: Функції BSP, що використовують блокуючі очікування шин або комутацію живлення, викликаються виключно з основного потоку програми і суворо заборонені до виклику з обробників переривань.
