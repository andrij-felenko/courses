Автономний польотний контролер безпілотника виконує контур стабілізації орієнтації з частотою рівно 1000 Гц: кожен крок обчислень має тривати не більше 1000 мікросекунд, інакше накопичення кутових швидкостей моменту інерції викличе неконтрольоване перекидання апарата. Для оцінки висоти та вертикальної швидкості конструктор підключає прецизійний цифровий барометр по шині I2C і додає до прошивки готову відкриту бібліотеку з популярного репозиторію. На лабораторному столі все функціонує бездоганно: значення тиску надходять раз на секунду, а висота обчислюється з точністю до сантиметрів. Але під час першого ж польового випробування, коли силові ключі регуляторів двигунів починають комутувати струми силою 45 А, виникає електромагнітна завада, яка спотворює один тактовий імпульс на лінії `SCL`. Бібліотечна функція зчитування даних викликає цикл `while (!I2C_GetFlagStatus(I2C_FLAG_RXNE))`, очікуючи на прапорець, який апаратний контролер мікроконтролера вже ніколи не виставить через порушення послідовності бітів. Не маючи захисного таймауту, процесор намертво застрягає всередині бібліотечного виклику. Контур стабілізації розривається: ШІМ-сигнали моторів фіксуються в останньому стані, і через 40 мілісекунд безпілотник на повній швидкості падає на землю.

Ця аварія розкриває головну проблему сторонніх драйверів для вбудованих систем: більшість із них розроблені для швидкого створення прототипів на макетних платах в ідеальних лабораторних умовах. Вони приховують у собі блокуючі затримки, приховані виклики динамічного виділення пам'яті, мовчазне ігнорування апаратних помилок шини, неперевірені припущення про порядок байтів та повну відсутність механізмів виходу із зависань. Коли готової надійної бібліотеки немає або наявна поводиться нестабільно, єдиний шлях інженера — спроєктувати власний, повністю контрольований низькорівневий драйвер.

### Анатомія вад аматорського коду: що приховано за простотою `begin()` та `read()`

Коли розробник завантажує сторонній драйвер із відкритих джерел, він зазвичай оцінює лише зручність виклику: один метод `sensor.begin()` в ініціалізації та `sensor.readPressure()` у циклі. Проте під капотом таких функцій криється низка системних пасток, кожна з яких є міною сповільненої дії для надійності пристрою.

#### 1. Блокуючі затримки (`delay()`, `HAL_Delay()`, `vTaskDelay()`)
Більшості сенсорів (термометрам, барометрам, газовим аналізаторам, АЦП високого розрізнення) після подачі команди старту вимірювання потрібен фізичний час на накопичення заряду чи прогрів чутливого елемента — від 5 до 80 мілісекунд. Типова аматорська бібліотека розв'язує це найпростішим шляхом:

:::tabs
@tab C
```c
/* Типова блокуюча затримка всередині сторонньої бібліотеки */
void start_measurement_blocking(void) {
    i2c_write_byte(REG_CTRL, START_CMD);
    delay_ms(25); /* Процесор на 25 мс повністю заморожується */
    i2c_read_bytes(REG_DATA, buffer, 6);
}
```
@tab C++
```cpp
/* Блокуючий антипатерн на C++ */
void Sensor::startMeasurementBlocking() {
    writeRegister(REG_CTRL, START_CMD);
    std::this_thread::sleep_for(std::chrono::milliseconds(25)); // CPU випадає з роботи
    readRegisters(REG_DATA, m_buffer);
}
```
:::

У системі з тактовою частотою ядра 168 МГц затримка тривалістю 25 мс означає безповоротне марнування 4 200 000 машинних тактів. У цей час процесор не може обслуговувати інші давачі, фільтрувати сигнали, обробляти пакети радіозв'язку чи розраховувати контури зворотного зв'язку. Якщо таких сенсорів на шині три, цикл опитування розтягується на 75 мс, знижуючи максимальну частоту роботи всієї системи до мізерних 13 Гц. Ба більше, у разі використання RTOS блокуючий виклик викликає позаплановий перемикач контексту (Context Switch), що вносить джитер (фазове тремтіння) у виконання високопріоритетних завдань.

#### 2. Динамічне виділення пам'яті (`malloc`, `free`, `new`, `std::vector`)
Багато авторів бібліотек, що прийшли з високорівневого програмування, використовують виділення пам'яті на купі для тимчасових буферів або конфігураційних структур:

:::tabs
@tab C
```c
/* Фрагментація купи та небезпека витоку пам'яті */
sensor_result_t *get_readings_leaky(void) {
    sensor_result_t *res = (sensor_result_t *)malloc(sizeof(sensor_result_t));
    if (!res) return NULL;
    if (i2c_read_bytes(REG_DATA, res->raw, 6) != 0) {
        /* Катастрофа: забули free(res) перед аварійним виходом */
        return NULL;
    }
    return res;
}
```
@tab C++
```cpp
/* Неконтрольоване використання купи на C++ */
std::unique_ptr<SensorResult> Sensor::getReadingsDynamic() {
    auto res = std::make_unique<SensorResult>();
    if (readRegisters(REG_DATA, res->raw) != BusStatus::Ok) {
        return nullptr;
    }
    return res;
}
```
:::

У мікроконтролерах з оперативною пам'яттю 32–128 КБ неперервне виділення та звільнення блоків пам'яті різного розміру неминуче призводить до фрагментації купи вже за кілька годин або діб роботи. Рано чи пізно черговий виклик `malloc()` або `new` повертає `NULL` через відсутність неперервного фрагмента пам'яті потрібної довжини. Якщо у прикладі бібліотеки забули перевірити цей вказівник або викликати `free()` у гілці обробки помилки шини, пристрій зазнає витоку пам'яті та падає з винятком `HardFault`.

#### 3. Нескінченні цикли очікування прапорців без таймаутів
Апаратні інтерфейси I2C та SPI піддаються впливу шумів, перехідних процесів і збоїв живлення. Якщо лінія `SDA` під час опитування замкнеться на землю або ведений чип проігнорує такт через збій внутрішнього генератора, апаратний модуль мікроконтролера ніколи не перейде в стан завершення передачі:

:::tabs
@tab C
```c
/* Нескінченне зависання при апаратній аварії на шині */
void wait_bus_naive(void) {
    while (I2C1->SR2 & I2C_SR2_BUSY) {
        /* Якщо шину заблоковано, система зависає тут назавжди */
    }
}
```
@tab C++
```cpp
/* Безкінечне очікування апаратного прапорця на C++ */
void I2cDriver::waitBusNaive() {
    while (isBusyHardware()) {
        // Відсутність таймауту гарантує зависання ядра
    }
}
```
:::

Будь-який цикл очікування апаратної події в промисловому драйвері зобов'язаний мати строго обмежений таймаут, що вимірюється не кількістю ітерацій (бо оптимізація компілятора `-O2` чи `-O3` змінює швидкість циклу в рази), а монотонним системним таймером (`SysTick` або апаратний таймер).

#### 4. Неперевірені припущення про порядок байтів (Endianness) та знакове розширення
Більшість чипів передають 16-бітні або 24-бітні виміри у форматі Big-Endian (спочатку старший байт MSB, потім молодший LSB). Недосвідчені розробники часто пишуть пряме приведення буфера:

:::tabs
@tab C
```c
/* Фатальна помилка: пряме приведення буфера та хибний порядок байтів */
int16_t parse_raw_bad(const uint8_t *buf) {
    return *(const int16_t *)buf; /* Працює ТІЛЬКИ на Little-Endian шинах! */
}
```
@tab C++
```cpp
/* Небезпечний reinterpret_cast на C++ */
int16_t parseRawBad(std::span<const uint8_t> buf) {
    return *reinterpret_cast<const int16_t*>(buf.data()); // UB та хибний порядок
}
```
:::

На процесорах ARM Cortex-M такий код прочитає байти задом наперед, перетворивши значення `0x01` `0x00` (256 відліків) на `0x0001` (1 відлік). Ба більше, при роботі з 20-бітними або 24-бітними значеннями у доповняльному коді (Two's Complement) наївний зсув `(buf[0] << 16) | (buf[1] << 8) | buf[2]` без збереження знакового біта призводить до того, що від'ємна температура -0.5 °C раптово перетворюється на велетенське додатне число +65535.5 °C.

#### 5. Жорстке прив'язування до конкретного фреймворку (Vendor Lock-in)
Якщо бібліотека напряму викликає функції Arduino (`Wire.read()`) або жорстко використовує генератор коду CubeMX (`HAL_I2C_Master_Transmit(&hi2c1, ...)`), ви не зможете перенести цей драйвер на інший мікроконтролер (наприклад, з STM32 на ESP32 чи Nordic nRF52) без повного переписування коду. Ба більше, такий драйвер неможливо скомпілювати на комп'ютері розробника для швидких Unit-тестів.

### Трьохрівнева архітектура драйвера: відокремлення логіки від шини

Надійний драйвер проєктується за принципом чіткого розмежування відповідальності. Архітектура ділиться на три незалежні шари:

1. **Шар карти регістрів (Register Map):** суто константний опис адрес регістрів, бітових масок, зсувів та значень за замовчуванням. Не містить жодної виконуваної логіки.
2. **Шар ядра драйвера (Driver Core):** містить усю бізнес-логіку сенсора: автомат станів, калібрувальні поліноми, формули перерахунку відліків у фізичні величини SI, перевірку контрольних сум CRC-8. Цей шар не має жодного уявлення про те, який саме мікроконтролер ним керує.
3. **Шар абстракції шини (Bus Transport Interface):** стандартизований контракт на виконання базових транзакцій читання й запису.

![Трьохрівнева архітектура надійного драйвера](/root/course/embedded/koly-biblioteky-nemaie-abo-vona-breshe/img/driver-layer-architecture.svg)
*Шар ядра драйвера повністю ізольований від фізичного заліза через стандартизований транспортний контракт, що дозволяє запускати Unit-тести на ПК без мікроконтролера.*

#### Транспортний контракт на мові C та C++

У мові C контракт шини оформлюється як структура функціональних покажчиків:

:::tabs
@tab C
```c
#include <stdint.h>
#include <stddef.h>
#include <stdbool.h>

typedef enum {
    BUS_OK          =  0,
    BUS_ERR_TIMEOUT = -1,
    BUS_ERR_NACK    = -2,
    BUS_ERR_IO      = -3
} bus_status_t;

/* Інтерфейс функціональних покажчиків для шини */
typedef struct {
    /* Читання масиву байтів із вказаного субрегістра */
    bus_status_t (*read_reg)(void *user_ctx, uint8_t dev_addr, uint8_t reg_addr, uint8_t *data, size_t len);
    /* Запис масиву байтів у вказаний субрегістр */
    bus_status_t (*write_reg)(void *user_ctx, uint8_t dev_addr, uint8_t reg_addr, const uint8_t *data, size_t len);
    /* Отримання поточного монотонного часу в мікросекундах */
    uint32_t (*get_time_us)(void);
} bus_interface_t;
```
@tab C++
```cpp
#include <cstdint>
#include <cstddef>
#include <span>
#include <concepts>
#include <expected>

namespace driver {

enum class BusStatus : int8_t {
    Ok = 0,
    Timeout = -1,
    Nack = -2,
    IoError = -3
};

/* C++20 концепт, що гарантує сумісність транспортного рівня */
template <typename T>
concept I2cBus = requires(T bus, uint8_t dev, uint8_t reg, std::span<uint8_t> rx, std::span<const uint8_t> tx) {
    { bus.read_reg(dev, reg, rx) } -> std::same_as<BusStatus>;
    { bus.write_reg(dev, reg, tx) } -> std::same_as<BusStatus>;
    { bus.get_time_us() } -> std::same_as<uint32_t>;
};

} // namespace driver
```
:::

Завдяки такій абстракції ядро драйвера не викликає безпосередньо функцій HAL чи регістрів периферії. Повний робочий проєкт еталонного драйвера разом із хостовим стендом моків та юніт-тестами наведено у вставці [Еталонний безблокуючий драйвер датчика](root:embedded/koly-biblioteky-nemaie-abo-vona-breshe/proj-sensor-driver.md).

### Безблокуюча модель: скінченний автомат опитування (FSM)

Головний ворог продуктивності системи — блокуюче очікування фізичного перетворення датчика. Наприклад, датчик вологості й температури SHT31 потребує 15 мс на повний замір, а барометр BMP280 у режимі високої точності — до 23 мс.

Замість одного виклику `read_all_blocking()`, драйвер організовується як скінченний автомат (**Finite State Machine, FSM**) із чітко рознесеними в часі фазами:

1. `STATE_IDLE` — драйвер очікує команди на запуск або планового інтервалу часу.
2. `STATE_TRIGGER` — відправка команди на старт заміру (транзакція I2C займає лічені мікросекунди). Фіксація часової мітки старту `t_start`.
3. `STATE_AWAIT_CONVERSION` — неблокуючий стан очікування. Процесор **повністю звільняється** для виконання інших завдань. При кожному виклику функції опитування перевіряється умова: `(now_us - t_start) >= CONV_TIME_US` або стан апаратного піна `DRDY` (Data Ready).
4. `STATE_READ_BURST` — пакетне вичитування сирих регістрів через DMA або апаратний буфер FIFO.
5. `STATE_PROCESS_DATA` — розрахунок контрольної суми CRC, знаків, масштабних коефіцієнтів та оновлення вихідної структури даних.

![Часова діаграма неблокуючого опитування сенсора](/root/course/embedded/koly-biblioteky-nemaie-abo-vona-breshe/img/sensor-fsm-timeline.svg)
*Часова діаграма неблокуючого драйвера: процесор витрачає лічені мікросекунди на старт і вичитування даних, лишаючись на 100% вільним протягом усього 20-мілісекундного циклу конверсії.*

У таблиці наведено порівняння часових витрат процесорного ядра для двох підходів:

| Параметр роботи | Блокуючий драйвер (`delay`) | Подійно-орієнтований FSM |
|---|---|---|
| **Час блокування CPU** | 20 000 мкс (100% завантаження) | 0 мкс (сон або інші задачі) |
| **Витрати на запуск** | 100 мкс (увесь цикл разом) | 4 мкс (відправка команди) |
| **Витрати на вичитування** | всередині загального блоку | 6 мкс (старт DMA / переривання) |
| **Час на розрахунок SI** | 12 мкс | 12 мкс |
| **Реакція на аварії** | Блокується до кінця delay() | Миттєва (переривання обробляються) |

### Обробка аварійних ситуацій: таймаути та розблокування шини I2C (Bus Clear)

Фізичні шини у польових умовах піддаються деградації: окислення контактів, вібрація кабелю, імпульсні сплески напруги. Надійний драйвер ніколи не розраховує на бездоганну передачу даних і реалізує два рівні самозахисту.

#### 1. Монотонні дедлайни замість ітераційних лічильників
Якщо апаратний блок шини очікує звільнення лінії або прийому байта, умова виходу з циклу повинна перевіряти монотонний час:

:::tabs
@tab C
```c
sensor_status_t wait_for_bus_ready(bus_interface_t *bus, uint32_t timeout_us) {
    uint32_t start_time = bus->get_time_us();
    while (is_hardware_bus_busy()) {
        if ((bus->get_time_us() - start_time) >= timeout_us) {
            return SENSOR_ERR_BUS_TIMEOUT;
        }
    }
    return SENSOR_OK;
}
```

#### 2. Зависання лінії SDA (I2C SDA Lockup) та алгоритм 9 тактів
Найбільш підступний апаратний збій на шині I2C виникає, коли мікроконтролер перезавантажується (через Watchdog або просідання живлення Brown-out) у той момент, коли ведений сенсор передавав біт логічного «0». 

Сенсор тримає вихідний транзистор відкритим, намертво притискаючи лінію `SDA` до землі (LOW). Після перезапуску апаратний модуль I2C мікроконтролера бачить лінію `SDA = 0` і вважає, що шина зайнята іншим майстром (`Bus Busy`). У результаті контролер відмовляється генерувати умову `START`, і зв'язок втрачається назавжди, доки пристрій повністю не знеструмлять.

![Сценарій зависання SDA та алгоритм відновлення шини](/root/course/embedded/koly-biblioteky-nemaie-abo-vona-breshe/img/i2c-bus-lockup-recovery.svg)
*Механізм блокування веденим чипом лінії SDA та процедура примусового скидання веденого автомата генерацією 9 тактових імпульсів.*

Алгоритм апаратного відновлення шини (**I2C Bus Clear Sequence**):
1. Вимкнути апаратний периферійний блок I2C мікроконтролера.
2. Сконфігурувати піни `SCL` та `SDA` як звичайні виходи GPIO у режимі відкритого стоку (**Open-Drain**).
3. Якщо лінія `SDA` притиснута до нуля, згенерувати на лінії `SCL` до 9 тактових імпульсів із частотою приблизно 50–100 кГц.
4. Ведений чип, отримуючи тактові імпульси, виштовхує залишок свого 8-бітного регістра. Оскільки мікроконтролер не підтверджує прийом (лінія SDA лишається HIGH через зовнішню підтяжку, що еквівалентно сигналу `NACK`), сенсор розуміє, що транзакцію перервано, і відпускає вихідний транзистор.
5. Щойно `SDA` підніметься до логічної «1», сформувати умову `STOP` (перепад SDA з LOW на HIGH при високому рівні SCL).
6. Перевести піни назад у режим альтернативної функції I2C та виконати повторну ініціалізацію апаратного модуля.

:::tabs
@tab C
```c
void i2c_bus_recovery_clear(void) {
    /* 1. Переведення пінів у GPIO Open-Drain */
    gpio_set_mode_open_drain(PIN_SCL);
    gpio_set_mode_open_drain(PIN_SDA);
    gpio_write(PIN_SCL, 1);
    gpio_write(PIN_SDA, 1);

    /* 2. Якщо SDA утримується веденим пристроєм у нулі */
    if (gpio_read(PIN_SDA) == 0) {
        for (uint8_t i = 0; i < 9; i++) {
            gpio_write(PIN_SCL, 0);
            delay_us(5);
            gpio_write(PIN_SCL, 1);
            delay_us(5);
            /* Якщо ведений відпустив лінію — виходимо достроково */
            if (gpio_read(PIN_SDA) == 1) {
                break;
            }
        }
        /* 3. Генерація умови STOP */
        gpio_write(PIN_SDA, 0);
        delay_us(5);
        gpio_write(PIN_SCL, 1);
        delay_us(5);
        gpio_write(PIN_SDA, 1);
        delay_us(5);
    }

    /* 4. Повернення до апаратної периферії */
    i2c_peripheral_reinit();
}
```
@tab C++
```cpp
namespace hardware {

class I2cRecovery {
public:
    static void recover_bus(auto& gpio_scl, auto& gpio_sda, auto& i2c_driver) noexcept {
        gpio_scl.set_open_drain();
        gpio_sda.set_open_drain();
        gpio_scl.write(true);
        gpio_sda.write(true);

        if (!gpio_sda.read()) {
            for (uint8_t i = 0; i < 9; ++i) {
                gpio_scl.write(false);
                delay_us(5);
                gpio_scl.write(true);
                delay_us(5);
                if (gpio_sda.read()) {
                    break;
                }
            }
            // Генерація STOP умови
            gpio_sda.write(false);
            delay_us(5);
            gpio_scl.write(true);
            delay_us(5);
            gpio_sda.write(true);
            delay_us(5);
        }

        i2c_driver.reinit();
    }
};

} // namespace hardware
```

### Математика розбору відліків: знакове розширення та контроль цілісності CRC

Отримані з шини сирі байти — це не числа з рухомою комою, а апаратні відліки АЦП. Для перетворення їх у стандартні одиниці SI (Паскалі, градуси Цельсія, метри на секунду в квадраті) необхідна точна математична обробка.

#### 1. Знакове розширення (Sign Extension) без невизначеної поведінки
Багато датчиків видають відліки нестандартної розрядності: наприклад, 12, 14, 20 або 24 біти. Якщо значення є знаковим (доповняльний код), 20-бітний відлік `0xFFFFF` означає число `-1`, а не `1 048 575`. Якщо просто зберегти його у 32-бітну змінну `int32_t`, старші 12 бітів залишаться нулями, і число стане додатним.

Коректне знакове розширення виконується за допомогою перевірки біта знака:

```
Знакове розширення 20-бітного числа:
Якщо біт 19 дорівнює 1 (від'ємне число):
  value_32 = value_20 | 0xFFF00000
Якщо біт 19 дорівнює 0 (додатне число):
  value_32 = value_20 & 0x000FFFFF
```

У мовах C та C++ це реалізується через арифметичний зсув або явне бітове маскування:

:::tabs
@tab C
```c
int32_t sign_extend_20bit(uint32_t raw_20) {
    if (raw_20 & (1u << 19)) {
        return (int32_t)(raw_20 | 0xFFF00000u);
    }
    return (int32_t)(raw_20 & 0x000FFFFFu);
}
```
@tab C++
```cpp
constexpr int32_t sign_extend_20bit(uint32_t raw_20) noexcept {
    if ((raw_20 & (1u << 19)) != 0) {
        return static_cast<int32_t>(raw_20 | 0xFFF00000u);
    }
    return static_cast<int32_t>(raw_20 & 0x000FFFFFu);
}
```

#### 2. Цілочисельна арифметика з фіксованою точкою (Fixed-Point)
Для мікроконтролерів без апаратного блоку FPU (наприклад, ядра ARM Cortex-M0/M0+/M3) операції з типом `float` або `double` виконуються програмною емуляцією, що збільшує час обчислень у 20–50 разів і роздуває розмір коду flash-пам'яті на кілька кілобайтів.

Промисловий стандарт для драйверів базового рівня — передача фізичних значень у цілих числах з фіксованим масштабом:
- Температура: у **міліградусах Цельсія** (`25150` замість `25.15 °C`).
- Тиск: у **Паскалях** (`101325` Па замість `1013.25` гПа).
- Прискорення: у **мікро-g** або **мм/с²** (`9810` замість `9.81` м/с²).

#### 3. Перевірка контрольної суми CRC-8
Сучасні сенсори передають 1 байт CRC після кожних двох байтів даних. Найбільш поширений поліном у сенсорах Sensirion, Bosch та Texas Instruments — `0x31` (x⁸ + x⁵ + x⁴ + 1 з початковим значенням `0xFF`).

Якщо під час передачі байта даних стається спотворення хоча б одного біта (внаслідок завади), обчислений драйвером CRC-8 не співпаде з прийнятим контрольним байтом. Драйвер зобов'язаний відкинути цей замір і повернути статус помилки цілісності `SENSOR_ERR_CRC`.

### Верифікація на живому залізі: що бачить логічний аналізатор

Програмний налагоджувач GDB та виведення логів у UART не здатні виявити більшість проблем цифрових шин:
- Точка зупинки (Breakpoint) зупиняє ядро процесора, але не зупиняє роботу веденого сенсора, що ламає часові діаграми шини.
- Виклики `printf()` спотворюють часові інтервали реального часу на сотні мікросекунд.
- Налагоджувач бачить лише вміст регістрів мікроконтролера, але не бачить, що коїться на фізичних дротах.

Єдиний об'єктивний інструмент верифікації драйвера — цифровий **логічний аналізатор** (наприклад, USB-аналізатор під керуванням відкритого ПЗ PulseView / Sigrok).

![Верифікація I2C транзакції логічним аналізатором](/root/course/embedded/koly-biblioteky-nemaie-abo-vona-breshe/img/logic-analyzer-verification.svg)
*Захоплення реальної транзакції I2C у програмі PulseView: декодування адреси, регістрів, підтвердження ACK та перевірка цілісності сигналів.*

#### Чек-лист інспекції транзакції логічним аналізатором:
1. **Форма умови START та STOP:** перепад `SDA` з HIGH на LOW повинен відбуватися строго при високому рівні `SCL`.
2. **Наявність біта підтвердження (ACK):** на 9-му такті кожного байта лінія `SDA` повинна впевнено притискатися до землі веденим пристроєм (рівень `U < 0.3 · V_DD`). Якщо на 9-му такті фіксується високий рівень (NACK), це свідчить про хибну адресу, непідтримуваний регістр або перевантаження внутрішнього автомата сенсора.
3. **Повторний старт (Repeated Start):** при читанні регістра послідовність повинна виглядати як:
   ```
   [START] -> [Addr + W] -> [ACK] -> [Reg] -> [ACK] -> [REPEATED START] -> [Addr + R] -> [ACK] -> [Data Byte] -> [NACK] -> [STOP]
   ```
   Якщо драйвер замість `Repeated Start` генерує повний `STOP` і новий `START`, інший майстер або внутрішній автомат сенсора може скинути вказівник адреси.
4. **Час наростання фронтів (t_r) та підтягувальні резистори:** якщо фронти імпульсів на лініях виглядають пологими або заокругленими, номінал підтягувальних резисторів (`R_pullup`) завеликий для поточної ємності лінії та частоти шини.
