# ⚙️ Безпечне затирання секретів у пам'яті: боротьба з оптимізаціями компілятора

Коли криптографічний ключ, пароль користувача або сесійний токен завершують свою роботу в оперативній пам'яті мікроконтролера, інженер за звичкою викликає функцію `memset(secret, 0, sizeof(secret))`. Проте в дев'яти випадках із десяти під час компіляції прошивки з прапорцями оптимізації `-O2`, `-O3` або `-Os` оптимізатор компілятора (GCC, Clang чи IAR) **повністю видаляє цей виклик**. У результаті приватні ключі залишаються лежати у відкритому вигляді в стеку чи статичній пам'яті SRAM, звідки їх легко витягти при зчитуванні аварійного дампу пам'яті (Core Dump), через уразливості переповнення буфера або за допомогою апаратного зондування шин.

---

### Механізм помилки: Dead Store Elimination

Компілятори мов C та C++ оптимізують програмний код на основі концепції «абстрактної машини» стандарту. Оптимізаційний прохід компілятора, який відповідає за видалення непотрібних збережень пам'яті (англ. *Dead Store Elimination*, DSE у конвеєрі SSA-форм), аналізує граф потоку керування програми. 

Якщо значення записується в змінну пам'яті, але після цієї точки в межах поточної функції чи області видимості значення більше ніколи не зчитується програмою, компілятор класифікує такий запис як «мертвий» (Dead Store). Оскільки занулення масиву перед виходом із функції ніяк не впливає на кінцевий обчислювальний результат програми, оптимізатор вилучає інструкцію запису нулів заради економії тактів процесора та зменшення розміру бінарного файлу.

```
void process_crypto_operation(void) {
    uint8_t session_key[32];
    derive_key(session_key);
    encrypt_payload(session_key, data);

    // ПОМИЛКА: компілятор бачить, що session_key є локальним масивом у стеку,
    // і після memset() пам'ять вивільняється. Компілятор повністю видаляє цей рядок!
    memset(session_key, 0, sizeof(session_key));
}
```

Якщо скомпілювати цей фрагмент і подивитися на вихідний асемблерний код за допомогою утиліти `objdump -d`, ви виявите, що інструкцій запису нулів у стек взагалі немає: функція просто відновлює вказівник стека `sp` і виконує інструкцію повернення `bx lr`. Байти секретного ключа залишаються лежати у фізичних комірках пам'яті стека доти, доки інша функція випадково не перетре їх своїми локальними змінними.

### Як гарантувати затирання: бар'єри пам'яті та кваліфікатор `volatile`

Щоб змусити компілятор гарантовано згенерувати реальні інструкції запису нулів у фізичну пам'ять, необхідно повідомити оптимізатору, що дана ділянка пам'яті має непередбачувані сторонні ефекти.

В інженерній практиці застосовують три надійні підходи:

1. **Побайтовий запис через `volatile` вказівник:** кваліфікатор `volatile` є контрактом із компілятором: доступ до пам'яті через такий вказівник розглядається як взаємодія з апаратним регістром. Компілятору суворо заборонено видаляти, кешувати або переставляти операції читання та запису `volatile`.
2. **Асемблерний бар'єр пам'яті (Compiler Memory Barrier):** спеціальна інструкція препроцесора `__asm__ __volatile__ ("" : : "r"(ptr) : "memory")` вказує компілятору, що в цій точці невідомий шматок асемблерного коду може прочитати або змінити будь-яку ділянку оперативної пам'яті. Оптимізатор змушений зберегти всі попередні записи нулів, оскільки вважає, що пам'ять буде прочитана.
3. **Стандартизовані системні функції:** виклик `explicit_bzero()` у POSIX-сумісних операційних системах (Linux, FreeRTOS із бібліотекою newlib), `memset_s()` у стандарті C11 (додаток K) або `SecureZeroMemory()` у середовищі Windows. Ці функції реалізовані так, що оптимізатор не має права видаляти виклики.

### Небезпека порівняння секретів через `memcmp`: атаки за часом

Друга критична помилка під час роботи з секретами в пам'яті — використання стандартної бібліотечної функції `memcmp()` для перевірки паролів, токенів автентифікації або цифрових підписів HMAC.

Функція `memcmp()` оптимізована під максимальну швидкість: вона порівнює байти по порядку зліва направо і **перериває виконання відразу на першому ж незбіжному байті**:

```
Еталонний токен:  [ 0x4A, 0x9B, 0x12, 0xF4, ... 32 байти ]
Спроба 1 (0x00): [ 0x00, 0x00, 0x00, 0x00, ... ] -> Відхилено за 4 такти процесора
Спроба 2 (0x4A): [ 0x4A, 0x00, 0x00, 0x00, ... ] -> Відхилено за 8 тактів процесора (довше!)
```

Якщо підключити осцилограф або точний апаратний таймер до лінії відповіді мікроконтролера, зловмисник може виміряти час обробки запиту з точністю до наносекунд. Перебираючи перший байт від `0x00` до `0xFF`, атакуючий зафіксує, що на значенні `0x4A` час відповіді трохи збільшився (оскільки процесор перейшов до порівняння другого байта). Цей клас атак називається **атаками за часом виконання** (англ. *Timing Attacks*). Таким способом 256-бітний ключ підбирається не за 2²⁵⁶ операцій, а всього за `32 · 256 = 8192` спроби!

Щоб запобігти цьому, порівняння секретних масивів має виконуватися за **строго константний час**: алгоритм зобов'язаний пройти всі байти масиву від першого до останнього незалежно від того, де сталася розбіжність, накопичуючи результат через побітове «АБО».

### Робоча реалізація надійного очищення та константного порівняння

Нижче наведено бібліотечний модуль для вбудованих систем двома мовами: на чистому C з використанням асемблерних бар'єрів пам'яті та на ідіоматичному C++ з автоматичним очищенням у деструкторі за шаблоном RAII (Resource Acquisition Is Initialization).

:::tabs
```c
#include <stdint.h>
#include <stddef.h>

/**
 * Гарантоване затирання пам'яті без ризику видалення оптимізатором.
 * Використовує volatile вказівник та асемблерний бар'єр пам'яті.
 */
void secure_zero_memory(void *v, size_t n) {
    if (v == NULL || n == 0) {
        return;
    }
    
    // Крок 1: побайтовий запис через volatile вказівник
    volatile uint8_t *p = (volatile uint8_t *)v;
    while (n--) {
        *p++ = 0x00;
    }

    // Крок 2: бар'єр пам'яті для гарантії завершення всіх операцій запису
    #if defined(__GNUC__) || defined(__clang__)
    __asm__ __volatile__("" : : "r"(v) : "memory");
    #endif
}

/**
 * Порівняння двох буферів секретів за константний час (Constant-Time).
 * Запобігає витоку секретів через аналіз часу виконання (Timing Attacks).
 * 
 * Повертає:
 *   1 — якщо буфери повністю ідентичні;
 *   0 — якщо є бодай один незбіжний байт або некоректні параметри.
 */
int constant_time_memcmp(const void *a, const void *b, size_t n) {
    if (a == NULL || b == NULL) {
        return 0;
    }

    const volatile uint8_t *pa = (const volatile uint8_t *)a;
    const volatile uint8_t *pb = (const volatile uint8_t *)b;
    volatile uint8_t diff = 0;

    // Цикл проходить ВСІ n байтів завжди, без дострокового виходу
    for (size_t i = 0; i < n; i++) {
        diff |= (pa[i] ^ pb[i]);
    }

    // Повертаємо 1 лише тоді, коли diff == 0
    return (diff == 0);
}
```
```cpp
#include <cstdint>
#include <cstddef>
#include <span>
#include <array>
#include <concepts>
#include <algorithm>

namespace embedded::crypto {

/**
 * Гарантоване затирання ділянки пам'яті в стилі C++.
 */
inline void secure_zero_memory(std::span<uint8_t> buffer) noexcept {
    if (buffer.empty()) {
        return;
    }

    auto* ptr = static_cast<volatile uint8_t*>(buffer.data());
    for (size_t i = 0; i < buffer.size(); ++i) {
        ptr[i] = 0x00;
    }

    #if defined(__GNUC__) || defined(__clang__)
    __asm__ __volatile__("" : : "r"(buffer.data()) : "memory");
    #endif
}

/**
 * Порівняння двох блоків пам'яті за строго константний час.
 */
[[nodiscard]] inline bool constant_time_compare(
    std::span<const uint8_t> a, 
    std::span<const uint8_t> b) noexcept 
{
    if (a.size() != b.size()) {
        return false;
    }

    volatile uint8_t diff = 0;
    const auto* pa = static_cast<const volatile uint8_t*>(a.data());
    const auto* pb = static_cast<const volatile uint8_t*>(b.data());

    for (size_t i = 0; i < a.size(); ++i) {
        diff |= (pa[i] ^ pb[i]);
    }

    return (diff == 0);
}

/**
 * Безпечний буфер фіксованого розміру для криптографічних ключів (RAII).
 * Гарантовано затирає свій вміст нулями при виході з області видимості.
 */
template <size_t N>
class SecureKeyBuffer {
public:
    constexpr SecureKeyBuffer() noexcept {
        data_.fill(0x00);
    }

    explicit SecureKeyBuffer(std::span<const uint8_t, N> source) noexcept {
        std::copy(source.begin(), source.end(), data_.begin());
    }

    ~SecureKeyBuffer() noexcept {
        secure_zero_memory(std::span<uint8_t>(data_));
    }

    // Заборона небезпечного копіювання секретів у пам'яті
    SecureKeyBuffer(const SecureKeyBuffer&) = delete;
    SecureKeyBuffer& operator=(const SecureKeyBuffer&) = delete;

    // Дозвіл безпечного переміщення
    SecureKeyBuffer(SecureKeyBuffer&& other) noexcept {
        std::copy(other.data_.begin(), other.data_.end(), data_.begin());
        secure_zero_memory(std::span<uint8_t>(other.data_));
    }

    SecureKeyBuffer& operator=(SecureKeyBuffer&& other) noexcept {
        if (this != &other) {
            secure_zero_memory(std::span<uint8_t>(data_));
            std::copy(other.data_.begin(), other.data_.end(), data_.begin());
            secure_zero_memory(std::span<uint8_t>(other.data_));
        }
        return *this;
    }

    [[nodiscard]] std::span<const uint8_t, N> view() const noexcept {
        return std::span<const uint8_t, N>(data_);
    }

    [[nodiscard]] std::span<uint8_t, N> mutable_view() noexcept {
        return std::span<uint8_t, N>(data_);
    }

    [[nodiscard]] constexpr size_t size() const noexcept {
        return N;
    }

private:
    std::array<uint8_t, N> data_;
};

} // namespace embedded::crypto
```

### Гігієна пам'яті та крайові випадки у складних системах

Окрім компіляторних оптимізацій, у складних вбудованих системах (на базі процесорів ARM Cortex-A або високопродуктивних Cortex-M7/M33) існують додаткові апаратні фактори, що можуть затримати секрети в системі:

1. **Кеш-пам'ять даних (Data Cache L1/L2):**
   При записі нулів у буфер секрету процесор може оновити лише рядок у кеші даних (у режимі зворотного запису — Write-Back), відклавши фізичний запис в оперативну пам'ять SRAM на невизначений час. Якщо в цей момент мікроконтролер переходить у режим глибокого сну (Deep Sleep) із вимкненням живлення кешу, дані можуть бути втрачені або збережені у залишковій ємності. Тому після виклику `secure_zero_memory()` рекомендується виконати примусове очищення та інвалідацію кеш-рядків процесора.
2. **Буфери прямого доступу до пам'яті (DMA):**
   Якщо криптографічні дані передаються між апаратним прискорювачем AES та оперативною пам'яттю за допомогою контролера DMA (Direct Memory Access), буфер DMA також має бути очищений після завершення транзакції.
3. **Методика верифікації прошивки:**
   Ніколи не покладайтеся на припущення, що компілятор виконав інструкції затирання. Завжди перевіряйте фінальний скомпільований бінарний файл за допомогою дизасемблера (`arm-none-eabi-objdump -d firmware.elf | grep -A 10 secure_zero_memory`), щоб особисто переконатися в наявності асемблерних інструкцій побайтового запису.
