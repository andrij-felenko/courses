Радіомодуль пристрою приймає з ефіру шість байтів: `[0xAA, 0x01, 0x00, 0x5A, 0x1B, 0xE4]`. Перший байт — маркер початку кадру, другий — ідентифікатор команди повороту сервоприводу, далі два байти цільового кута в 90 градусів, а останні два — циклічна контрольна сума CRC-16. Апаратний блок мікроконтролера за два мікросекунди перераховує поліном, звіряє значення `0x1BE4`, бачить повний збіг і передає команду на драйвер мотора. Вал сервоприводу слухняно повертається. Прошивка відпрацювала штатно, але в системі щойно сталася критична аварія безпеки: цю команду надіслав не законний пульт оператора, а сторонній генератор із копійчаним SDR-передавачем, який підслухав попередній сеанс зв'язку.

Контрольна сума в бінарному кадрі гарантує лише одну річ: біти в дорозі не спотворилися випадковим тепловим шумом або завадою від сусіднього реле. Вона не відповідає і принципово не здатна відповісти на два головні запитання безпечного керування: **хто** створив цю команду і **коли саме** вона була створена. Без криптографічного підтвердження авторства та механізму контролю свіжості будь-яка лінія зв'язку — чи то радіоефір на 868 МГц, шина RS-485 на заводі, чи протокол UART між двома платами — перетворюється на відкриті двері для зловмисника.

### Анатомія загроз відкритого каналу: підміна та повтор

Коли розробник залишає канал керування відкритим, він неявно припускає, що середовище передачі ізольоване від чужих очей. У реальному світі ця ізоляція руйнується миттєво. Достатньо дешевого USB-сніфера шини CAN, логічного аналізатора на дротах UART або радіоприймача вартістю в кілька доларів, щоб отримати повний доступ до бінарного потоку.

![Атака повтору: перехоплення та відтворення валідного кадру](/root/course/embedded/choho-varta-komanda-bez-pidpysu/img/replay-attack.svg)
*Зловмиснику не потрібно розшифровувати протокол чи обчислювати криптографічні ключі: достатньо записати сирий радіосигнал валідної команди з правильною CRC і відтворити його в потрібний момент. Приймач без перевірки свіжості виконає команду вдруге.*

Перша очевидна загроза — **підміна даних** (англ. *spoofing* або *tampering*). Якщо зловмисник знає формат пакетів або просто спостерігає за реакцією пристрою, він може перехопити кадр у проміжному вузлі (атака посередника, *Man-in-the-Middle*), змінити значення байтів цільової швидкості чи стану силового контактора, перерахувати відкритий алгоритм CRC-16 за таблицею й відправити пакет далі. Приймач перевірить поліном, побачить математичний збіг і виконає підроблену дію.

Друга, значно підступніша загроза — **атака повтору** (англ. *replay attack*). Її головна небезпека полягає в тому, що нападнику взагалі **не потрібно розуміти зміст кадру** чи ламати алгоритми шифрування. Якщо канал передає зашифровані статичним ключем або відкриті пакети без прив'язки до монотонного стану, нападник просто записує правильний пакет «Відчинити гаражні ворота» чи «Вимкнути аварійне блокування» у файл. Коли легітимний оператор іде, нападник випромінює в ефір той самий бітовий запис. Для мікроконтролера цей пакет виглядає бездоганно: біти цілі, шифротекст коректний, контрольна сума збігається. Команда виконується знову.

> 🔧 **Навіщо це.** Спроби боротися з атакою повтору простим приховуванням формату чи саморобною перестановкою байтів завжди зазнають поразки (принцип Керкгоффза: безпека системи має визначатися виключно секретністю ключа, а не таємницею алгоритму). Єдиний надійний інженерний бар'єр — розділити захист на два незалежні шари: криптографічний доказ цілісності й авторства (MAC / підпис) та математичний доказ свіжості повідомлення (лічильники та одноразові коди).

### Доказ свіжості: лічильники, ковзні вікна та часові мітки

Щоб приймач міг відрізнити щойно створену команду від записаного дубліката, кожне повідомлення зобов'язане містити маркер свіжості, значення якого ніколи не повторюється в межах життєвого циклу ключа. У вбудованих системах застосовують три механізми захисту від повтору: монотонні лічильники, одноразові випадкові коди та часові мітки.

#### Монотонний лічильник повідомлень (Sequence Number)

Найпростіший підхід полягає у введенні в заголовок кадру беззнакового лічильника `seq_num`. Передавач збільшує лічильник на одиницю для кожного нового кадру:

```
seq_tx = seq_tx + 1
```

Приймач зберігає в пам'яті останнє отримане значення `last_seq`. Якщо приходить пакет із номером `seq_rx`:

```
seq_rx > last_seq    [умова прийняття кадру]
```

Якщо умова виконується, приймач оновлює `last_seq = seq_rx` і передає команду на виконання. Якщо `seq_rx <= last_seq`, пакет безумовно відкидається як дублікат або атака повтору.

Розмірність лічильника має критичне значення. Використання 16-бітного поля — класична пастка: за швидкості потоку 100 пакетів на секунду лічильник переповниться і скинеться в нуль через:

```
T_wrap = 65536 / 100
= 655.36 с          [переповнення за 10.9 хвилин]
```

Після переповнення зв'язок заблокується, доки не відбудеться переініціалізація ключів, або система відкриється для повтору старих пакетів із молодшими номерами. Тому стандартом є використання **64-бітних лічильників** (`uint64_t`). Навіть при передачі одного мільярда пакетів на секунду 64-бітне число переповниться лише через 584 роки:

```
T_wrap_64 = 2⁶⁴ / (10⁹ · 86400 · 365.25)
≈ 584.5 років       [гарантія невичерпності простору лічильника]
```

#### Ковзне вікно валідності (Sliding Replay Window)

В ідеальному каналі (провідний SPI між двома чипами на одній платі) пакети завжди надходять у строгому порядку черги FIFO. Проте в бездротових мережах (Wi-Fi, Bluetooth Mesh, 802.15.4, LoRaWAN) або розгалужених польових шинах пакети регулярно губляться, ретранслюються або приходять із порушенням хронологічного порядку через різну затримку на проміжних вузлах.

Якщо перевіряти суворе зростання `seq_rx > last_seq`, трапляється неприпустиме: прихід випереджального пакета `Seq = 5` (наприклад, через швидший прямий маршрут) змусить приймач виставити `last_seq = 5`. Коли запізнілий пакет `Seq = 4` нарешті дістанеться приймача через повільніший ретранслятор, його буде викинуто як застарілий (`4 <= 5`), хоча це легітимна первинна команда.

Для вирішення цієї проблеми застосовують алгоритм **ковзного вікна на бітовій масці** (RFC 6479, IPsec Anti-Replay). Приймач підтримує змінну максимального отриманого лічильника `max_seq` та 64-бітну маску `bitmap`, де кожен `k`-й біт позначає факт прийому пакета з номером `(max_seq - k)`.

![Ковзне вікно захисту від повтору](/root/course/embedded/choho-varta-komanda-bez-pidpysu/img/sliding-window.svg)
*Ковзне вікно шириною 64 біти дозволяє безпечно приймати запізнілі пакети, що прийшли поза чергою (out-of-order), водночас миттєво відсікаючи як застарілі пакети лівіше вікна, так і повторні копії вже оброблених пакетів усередині вікна.*

Алгоритм обробки вхідного лічильника `seq` складається з чотирьох гілок:

```
diff = max_seq - seq

1) seq > max_seq:
   shift = seq - max_seq
   якщо shift >= 64:
       bitmap = 1
   інакше:
       bitmap = (bitmap << shift) | 1
   max_seq = seq
   [пакет прийнято як новий лідер]

2) diff >= 64:
   [пакет відхилено: безнадійно застарілий]

3) (bitmap & (1 << diff)) != 0:
   [пакет відхилено: повторна спроба раніше обробленого кадру]

4) (bitmap & (1 << diff)) == 0:
   bitmap = bitmap | (1 << diff)
   [пакет прийнято: запізнілий, але раніше не оброблений кадр]
```

Цей алгоритм виконується за кілька тактів процесора, не потребує динамічної пам'яті (займає рівно 16 байтів у RAM під `max_seq` та `bitmap`) і повністю розв'язує проблему втрат та перевпорядкування пакетів у радіомережах.

#### Одноразові коди (Nonce) у протоколах «запит-відповідь»

Якщо передавач і приймач не мають спільної синхронізованої шкали лічильників (наприклад, пульт увімкнули вперше, або пристрій вийшов із глибокого сну без збереження стану в енергонезалежній пам'яті), застосовують протокол типу **Challenge-Response** на основі одноразових кодів (англ. *nonce* — *number used once*):

1. Ініціатор надсилає запит: «Хочу виконати команду `CMD_DISARM`».
2. Виконавець генерує криптографічно стійке випадкове число `N_R` (64 біти) і повертає його ініціатору як виклик (*challenge*), зберігаючи `N_R` у короткочасному буфері сесії.
3. Ініціатор обчислює криптографічний код над зв'язкою `(CMD_DISARM || N_R)` і надсилає назад.
4. Виконавець перевіряє код, переконується у збігу `N_R` зі своїм збереженим значенням, стирає `N_R` із пам'яті (унеможливлюючи повтор) і виконує команду.

Ціною такого підходу є додатковий цикл обміну (Round-Trip Time, RTT) та затримка реакції, проте він не залежить від збереження монотонного лічильника при раптових перезавантаженнях.

#### Часові мітки та вікна валідності

Коли вбудована система має джерело абсолютного часу (модуль годинника реального часу RTC з резервною батареєю, супутниковий приймач GNSS або синхронізацію по NTP/PTP), до повідомлення додають часову мітку `timestamp` (UTC-секунди або мілісекунди).

Приймач звіряє різницю між часом кадру `t_cmd` та поточним системним часом `t_local`:

```
|t_cmd - t_local| <= Δt    [умова потрапляння в часове вікно]
```

> [!WARNING]
> Часова мітка **сама по собі не захищає від атаки повтору**. Якщо часове вікно валідності `Δt` становить 3 секунди (для компенсації дрейфу кварцу та затримок передачі), зловмисник може перехопити кадр і повторити його сотні разів протягом цих трьох секунд! Часова мітка повинна обов'язково комбінуватися з лічильником `seq_num` або кешем використаних одноразових кодів усередині активного часового вікна.

#### Проблема збереження лічильника у Flash-пам'яті (Flash Wear vs Rollback)

Якщо мікроконтролер перезавантажується по сторожовому таймеру або внаслідок збою живлення, значення `last_seq` у RAM втрачається. Якщо після старту лічильник скинеться в нуль, система стає вразливою до відкату (*rollback attack*) та повтору старих пакетів.

Записувати кожен отриманий `seq_num` безпосередньо в комірки Flash або EEPROM заборонено фізикою напівпровідників: нормативний ресурс Flash-пам'яті становить від 10 000 до 100 000 циклів стирання. При частоті 10 команд на секунду Flash деградує за лічені години.

Інженерне рішення полягає у **блоковому виділенні лічильників з кроком уперед** (англ. *step-ahead counter allocation*):

1. При старті чи досягненні межі контролер записує у Flash значення, збільшене на фіксований крок резерву (наприклад, `flash_seq = current_seq + 1000`).
2. Під час поточної роботи мікроконтролер веде лічильник виключно в оперативній пам'яті RAM.
3. Якщо поточний лічильник наближається до межі `flash_seq`, контролер робить наступний запис у Flash (`flash_seq += 1000`).
4. Якщо трапляється раптове скидання живлення, під час завантаження система вичитує `flash_seq` і починає роботу саме з нього. Приймач втрачає можливість прийняти максимум 1000 пропущених номерів (що не заважає передавачу, якщо той швидко підлаштує свій лічильник), але захищає пристрій від повтору давніх команд, а Flash-пам'ять витримує десятиліття безперервної експлуатації.

### Симетрична автентифікація: HMAC, AES-GMAC та Poly1305

Навіть якщо пакет містить монотонний лічильник `seq_num = 1054`, без криптографічного доказу цілісності зловмисник може просто підставити будь-який більший номер `seq_num = 1055` у фальшивий пакет. Щоб заблокувати підробку, пакет захищають **кодом автентичності повідомлення** (англ. *Message Authentication Code*, MAC).

MAC — це криптографічна контрольна сума, обчислена над даними повідомлення за допомогою секретного ключа `K`, відомого лише відправнику та одержувачу. Не знаючи ключа `K`, неможливо згенерувати валідний тег автентичності для зміненого або нового повідомлення.

```
Tag = MAC(Key, Header || Payload)
```

Розглянемо три головні симетричні алгоритми, що застосовуються у вбудованих системах.

![Порівняння: Симетричний MAC проти Асиметричного підпису](/root/course/embedded/choho-varta-komanda-bez-pidpysu/img/auth-comparison.svg)
*Симетричні алгоритми автентифікації виконуються за мікросекунди й мають компактні теги, але вимагають спільного секрету на обох кінцях. Асиметричний підпис усуває ризик витоку приватного ключа з пристрою, проте коштує на порядки більше обчислювальних ресурсів процесора.*

#### 1. HMAC-SHA256 (RFC 2104)

HMAC будується на основі стандартних криптографічних хеш-функцій (SHA-256). Конструкція створена для запобігання атакам подовження повідомлення (англ. *length extension attack*), яким піддаються наївні схеми на кшталт `Hash(Key || Message)`.

HMAC використовує два проходи хешування з внутрішнім та зовнішнім доповненням ключа константами `ipad = 0x36` та `opad = 0x5C`:

```
HMAC(K, M) = SHA256( (K ⊕ opad) || SHA256( (K ⊕ ipad) || M ) )
```

- **Розмір вихідного тегу:** 32 байти (256 бітів). Для економії каналу тег часто скорочують до перших 16 або 8 байтів.
- **Обчислювальна складність:** приблизно 15–25 тактів процесора на байт входу. На контролері ARM Cortex-M4 (STM32F405 @ 168 МГц) програмне обчислення HMAC-SHA256 для короткого 32-байтного кадру триває приблизно **25–40 мікросекунд**.
- **Переваги:** абсолютна стандартизація, наявність у будь-якому криптографічному стеку (mbedTLS, wolfSSL, tinycrypt), стійкість перевірена десятиліттями.

#### 2. AES-GMAC (NIST SP 800-38D)

AES-GMAC — це режим автентифікації на основі блокового шифру AES та множення в полі Галуа `GF(2¹²⁸)`. Фактично це режим автентифікованого шифрування AES-GCM, у якому довжина шифрованого тексту дорівнює нулю, а всі дані кадру передаються як додаткові автентифіковані дані (англ. *Additional Authenticated Data*, AAD).

- **Розмір вихідного тегу:** 16 байтів (128 бітів).
- **Обчислювальна складність:** на мікроконтролерах із вбудованим апаратним прискорювачем криптографії (STM32L4+, STM32H7, ESP32, NXP LPC5500) обчислення GMAC займає **менше 5–8 мікросекунд**.
- **Переваги:** максимальна швидкість за наявності апаратного блоку AES/GHASH; мінімальні накладні витрати на обчислення.
- **Критична вимога безпеки:** GMAC вимагає унікального вектора ініціалізації (IV/Nonce) для кожного виклику з тим самим ключем. Повторне використання пари (Key, IV) призводить до компрометації ключа автентифікації.

#### 3. Poly1305 (RFC 8439)

Poly1305 — високоефективний одноразовий автентифікатор, розроблений Деніелом Бернштейном (Daniel J. Bernstein). Він обчислює поліноміальний хеш над вхідними блоками у скінченному простому полі:

```
p = 2¹³⁰ - 5
```

Число `2¹³⁰ - 5` обрано завдяки винятковій зручності для 32-бітних процесорів: редукція за цим модулем зводиться до швидких операцій зсуву та додавання без повільного ділення.

- **Розмір вихідного тегу:** 16 байтів (128 бітів).
- **Обчислювальна складність:** у чистому програмному коді на C (бібліотека Monocypher або TweetNaCl) Poly1305 працює в 3–5 разів швидше за SHA-256, споживаючи лише **1.5–3.5 тактів на байт**.
- **Переваги:** не використовує таблиць підстановок (S-box), що робить його за замовчуванням стійким до атак за часом виконання через кеш процесора (англ. *cache-timing attacks*), навіть на чипах без апаратних криптоприскорювачів (Cortex-M0+/M3).

#### Інженерне порівняння симетричних алгоритмів на платформі ARM Cortex-M

| Параметр | HMAC-SHA256 | AES-GMAC | Poly1305 (ChaCha20) |
| :--- | :--- | :--- | :--- |
| **Розмір повного тегу** | 32 байти (256 біт) | 16 байтів (128 біт) | 16 байтів (128 біт) |
| **Мінімально безпечний тег** | 8–16 байтів | 12–16 байтів | 16 байтів |
| **Час на Cortex-M4 (168 МГц, софт)** | ~30–45 мкс | ~80–120 мкс (без AES) | ~10–18 мкс |
| **Час з апаратним блоком** | ~15–20 мкс | **~4–8 мкс** | Немає у залізі |
| **Вимоги до RAM стеку** | ~200–300 байтів | ~150–250 байтів | **< 100 байтів** |
| **Чутливість до повтору IV/Nonce** | Немає Nonce | **Критична (злам ключа)** | **Критична (злам ключа)** |

### Асиметричний цифровий підпис: Ed25519 та ECDSA

Симетрична автентифікація має одну фундаментальну архітектурну ваду, яку називають **пасткою спільного секрету**. Якщо для захисту парку з тисячі датчиків чи сервоприводів у всі пристрої зашити один і той самий симетричний ключ `K`, зловмиснику достатньо вичитати Flash-пам'ять одного пристрою на столі за допомогою апаратного відлагоджувача JTAG/SWD або методу оптичного інжектування збоїв. Отримавши ключ `K`, нападник може підробляти команди для **всіх інших пристроїв у системі**.

Якщо ж призначити кожному пристрою унікальний симетричний ключ `K_i`, центральний пульт чи сервер змушений зберігати величезну базу ключів. Але головне: симетричний ключ дозволяє як перевіряти, так і створювати підпис. Одержувач команди володіє всім необхідним, щоб самому згенерувати фальшиву команду від імені відправника (відсутність невідмовності, *non-repudiation*).

Асиметрична криптографія на еліптичних кривих розв'язує цю проблему за допомогою розділення ключів на пару:

- **Приватний ключ (Private Key / Secret Key, `SK`):** зберігається виключно на захищеному сервері керування, у апаратному модулі безпеки (HSM) або довіреному анклаві пульта оператора. Він використовується для генерації цифрового підпису.
- **Відкритий ключ (Public Key, `PK`):** зашивається у Flash-пам'ять чи пропалюється в одноразові комірки eFuse мікроконтролера. Він дозволяє виключно **перевіряти підпис**, але не дає математичної можливості згенерувати новий.

Навіть якщо зловмисник повністю зчитає прошивку виконавчого мікроконтролера через інженерні роз'єми, він отримає лише відкритий ключ `PK`. З його допомогою неможливо підробити жодної нової команди керування.

#### Ed25519 проти ECDSA (secp256r1 / NIST P-256)

Серед асиметричних алгоритмів цифрового підпису для вбудованих систем фактичним стандартом стали дві схеми:

1. **ECDSA (Elliptic Curve Digital Signature Algorithm):** класичний стандарт на кривій NIST P-256 (secp256r1). Використовується в захищених завантажувачах багатьох виробників мікросхем (STM32, NXP).
   - *Головна небезпека:* вимагає генерації нового криптографічно стійкого випадкового числа `k` для кожного підпису. Якщо генератор випадкових чисел (RNG) на боці передавача дасть збій або повторить `k` для двох різних повідомлень (як сталося в сумнозвісному зломі консолі PlayStation 3), приватний ключ розраховується з двох підписів за допомогою елементарної арифметики.
2. **Ed25519 (EdDSA на скрученій кривій Едвардса Curve25519, RFC 8032):** сучасний стандарт високонадійної криптографії.
   - *Детермінованість:* підпис генерується без використання випадкових чисел (`k = SHA512(SK || Message)`), що повністю виключає вразливості поганого RNG.
   - *Повна безпека операцій:* математика кривих Едвардса позбавлена особливих точок (точок нескінченності), що спрощує реалізацію без умовних переходів і захищає від атак побічними каналами (Side-Channel Attacks).
   - *Розміри:* відкритий ключ займає **32 байти**, цифровий підпис — **64 байти**.

#### Обчислювальна ціна асиметрії на мікроконтролері

Асиметрична криптографія спирається на множення точок еліптичної кривої над великими числами (256 бітів), що створює колосальне навантаження на 32-бітне ядро Cortex-M:

```
HMAC-SHA256 (весь кадр):   ~0.03 мс  (30 мкс)
Ed25519 (верифікація):     ~25.00 мс (25000 мкс)
[Ed25519 у 800 разів важчий за симетричний HMAC!]
```

На процесорі STM32F4 (ARM Cortex-M4 @ 168 МГц) програмна перевірка одного підпису Ed25519 через оптимізовану бібліотеку (Monocypher або micro-ecc) займає від **20 до 45 мілісекунд** і споживає 1.5–3 КБ стеку RAM.

Якщо система керує квадрокоптером чи сервоприводом робота з частотою оновлення 500 Гц (період 2 мс), процесор фізично не здатний перевіряти асиметричний підпис для кожної мікрокоманди зміни тяги двигуна.

#### Гібридна архітектура довіри

Невідповідність між швидкістю та захищеністю розв'язується через **дворівневу гібридну архітектуру**:

```
+-----------------------------------------------------------------------------------------+
| РІВЕНЬ 1: Асиметричний підпис (Ed25519)                                                 |
| Частота: рідко (раз на сеанс / при зміні конфігурації / при оновленні OTA)              |
| Задачі:                                                                                 |
| 1. Автентифікація образу нової прошивки перед записом у Flash.                          |
| 2. Передача одноразового сесійного симетричного ключа K_sess (ECDH / X25519).           |
| 3. Критичні команди найвищого пріоритету (заводське скидання, аварійна зупинка).        |
+-----------------------------------------------------------------------------------------+
                                           │
                                           ▼ генерує тимчасовий ключ K_sess
+-----------------------------------------------------------------------------------------+
| РІВЕНЬ 2: Симетричний код автентичності (HMAC-SHA256 / Poly1305 / AES-GMAC)            |
| Частота: висока (100–1000 Гц)                                                           |
| Задачі:                                                                                 |
| 1. Миттєва верифікація потокових команд руху та положення валів (10–30 мкс).            |
| 2. Захист від повтору на основі 64-бітного ковзного вікна.                              |
| 3. При компрометації K_sess шкода обмежена тривалістю поточного сеансу.                 |
+-----------------------------------------------------------------------------------------+
```

### Формат бінарного кадру та захист від часових атак

Щоб об'єднати всі елементи захисту в єдину систему, спроєктуємо канальний формат захищеного бінарного кадру.

![Формат захищеного бінарного кадру керування](/root/course/embedded/choho-varta-komanda-bez-pidpysu/img/secure-frame-structure.svg)
*Кожен байт заголовка, лічильника та корисного навантаження входить до діапазону даних, над якими обчислюється код автентичності. Будь-яка модифікація хоча б одного біта унеможливлює збіг тегу.*

Кадр має фіксовану бінарну розкладку:

```
Поле            Розмір      Призначення
-------------------------------------------------------------------------
Magic           2 байти     Преамбула синхронізації кадру (0xA55A)
MsgType         1 байт      Тип повідомлення (0x01 = Motion, 0x02 = Config)
Reserved        1 байт      Вирівнювання структури до 4 байтів
SeqNum          8 байтів    Монотонний лічильник захисту від повтору
Timestamp       4 байти     Час відправлення (UNIX Epoch UTC, секунди)
PayloadLen      2 байти     Довжина корисного навантаження N (у байтах)
Payload         N байтів    Дані команди (кути, координати, напруги)
AuthTag         16/32 байти Код автентичності (HMAC/Poly1305) або підпис (Ed25519)
```

Загальний розмір службового заголовка становить 18 байтів. Разом із 16-байтним тегом Poly1305 криптографічні накладні витрати складають лише 34 байти на кадр.

#### Конвеєр верифікації та пастка TOCTOU

Порядок перевірки полів у коді приймача має вирішальне значення. Порушення послідовності відкриває критичні вразливості:

![Конвеєр безпечної обробки кадру керування](/root/course/embedded/choho-varta-komanda-bez-pidpysu/img/verification-pipeline.svg)
*Суворий порядок дій гарантує, що жоден байт корисного навантаження не передається бізнес-логіці до проходження криптографічної перевірки, а стан лічильника не пошкоджується підробленими пакетами.*

1. **Перевірка фізичних меж:** перевірити, що довжина буфера не менша за суму `sizeof(Header) + PayloadLen + TagSize`.
2. **Автентифікація всього блоку (Крок 1):** обчислити очікуваний тег над усім діапазоном від байта `Magic` до останнього байта `Payload` включно. Порівняти отриманий тег з еталонним.
   - *Якщо тег не зійшовся:* **негайно відкинути пакет**. Не змінювати стан вікна лічильників! Якщо змінити стан вікна до перевірки тегу, зловмисник зможе заблокувати зв'язок (DoS), надіславши сміттєвий пакет із великим номером `SeqNum = 0xFFFFFFFFFFFFFFFF`.
3. **Перевірка часового вікна (Крок 2):** переконатися, що `|t_cmd - t_local| <= Δt`.
4. **Перевірка та оновлення ковзного вікна (Крок 3):** перевірити лічильник `SeqNum` за бітовою маскою. Якщо це не повтор — зафіксувати біт у масці.
5. **Диспетчеризація команди (Крок 4):** передати корисне навантаження обробнику бізнес-логіки.

#### Фатальна помилка: розбір до перевірки (Parse-before-Verify)

Класична помилка розробників прошивок — починати читання корисного навантаження (виділяти пам'ять, розбирати JSON чи protobuf, налаштовувати вказівники) до повної верифікації MAC-тегу. Будь-яка вразливість переповнення буфера чи помилка парсера в неперевіреному коді дозволяє нападнику захопити контроль над чипом за допомогою спеціально сформованого пакету, навіть якщо криптографічний тег наприкінці не зійдеться.

Залізне правило вбудованої безпеки: **жоден біт корисного навантаження не повинен інтерпретуватися чи парситися доти, доки криптографічний тег не підтверджено на 100%.**

#### Захист від атак за часом виконання (Constant-Time Verification)

Для порівняння отриманого тегу з обчисленим початківці часто викликають стандартну бібліотечну функцію `memcmp()`:

:::tabs
```c
// СМЕРТЕЛЬНО НЕБЕЗПЕЧНО: витік через різний час виконання
if (memcmp(received_tag, computed_tag, 32) == 0) {
    // підпис валідний
}
```
```cpp
// СМЕРТЕЛЬНО НЕБЕЗПЕЧНО: витік через різний час виконання
if (std::memcmp(received_tag.data(), computed_tag.data(), 32) == 0) {
    // підпис валідний
}
```
:::

Функція `memcmp()` оптимізована на максимальну швидкість: вона порівнює байти по порядку і **перериває роботу на першому ж незбігу**.

Якщо перший байт тегу неправильний, `memcmp()` повертає результат за 5 тактів. Якщо перший байт правильний, а другий ні — за 8 тактів. Зловмисник, підключивши осцилограф до лінії живлення чи аналізуючи час відповіді мікроконтролера, може підібрати правильний 32-байтний тег байт за байтом усього за `256 × 32 = 8192` спроби замість перебору `2²⁵⁶` варіантів!

Порівняння криптографічних тегів та ключів зобов'язане виконуватися **виключно в константному часі** (англ. *constant-time comparison*), де час виконання не залежить від позиції помилки:

:::tabs
```c
int crypto_verify_32(const uint8_t *a, const uint8_t *b) {
    uint8_t diff = 0;
    for (size_t i = 0; i < 32; ++i) {
        diff |= (a[i] ^ b[i]);
    }
    return (diff == 0) ? 0 : -1;
}
```
```cpp
#include <cstdint>
#include <cstddef>
#include <span>

namespace embedded::security {

[[nodiscard]] bool constant_time_verify(std::span<const uint8_t> a, 
                                        std::span<const uint8_t> b) noexcept {
    if (a.size() != b.size()) {
        return false;
    }
    uint8_t diff = 0;
    for (size_t i = 0; i < a.size(); ++i) {
        diff |= (a[i] ^ b[i]);
    }
    return diff == 0;
}

} // namespace embedded::security
```
:::

У цій функції цикл завжди виконує всі 32 ітерації незалежно від вмісту буферів, унеможливлюючи витік інформації через сторонні канали часу.

Повна, модульна та перевірена реалізація безпечного парсера бінарних команд із захистом від повтору та тестовим стендом винесена в [модуль криптографічної перевірки команд із захистом від повтору](root:embedded/choho-varta-komanda-bez-pidpysu/proj-secure-command-parser.md).

### Інженерний чекліст: захист каналу керування

Перед випуском пристрою в серійне виробництво перевірте реалізацію за контрольним списком критичних правил:

1. **Контрольна сума CRC використовується лише для виявлення шуму:** жодне рішення безпеки не спирається на CRC чи прості хеші (MD5/SHA-1).
2. **Розмірність лічильника повідомлень не менше 64 бітів:** унеможливлено переповнення лічильника в межах життєвого циклу пристрою.
3. **Автентифікація перед розбором (Verify-then-Parse):** жодне поле корисного навантаження не обробляється до успішної перевірки автентичності тегу.
4. **Константний час звірки тегів:** виклики `memcmp` для криптографічних гешів замінені на `crypto_verify`.
5. **Оновлення стану вікна лічильників тільки після перевірки тегу:** невалідні пакети не зсувають вікно і не спричиняють DoS.
6. **Ізоляція ключів:** симетричні сесійні ключі зберігаються в захищеній пам'яті (RAM) та затираються перед звільненням буфера (`explicit_bzero` / `memset_s`); довготривалі кореневі ключі зашиті в eFuse або безпечному елементі (Secure Element).
7. **Обмеження швидкості невдалих спроб (Rate Limiting):** у разі надходження серії невалідних підписів приймач вводить експоненційну затримку, щоб запобігти вичерпанню заряду батареї під атакою лавинного флуду.
