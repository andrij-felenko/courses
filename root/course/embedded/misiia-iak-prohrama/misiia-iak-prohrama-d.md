Безпілотний розвідник моніторить сонячну електростанцію за масивом із двох сотень вейпойнтів. На сорок сьомому вейпойнті зустрічний порив вітру 18 м/с різко збільшує споживання струму ходових моторів, а тепловізійна камера виявляє локальний перегрів панелі. Якщо польотне завдання зашито як звичайний лінійний список координат, в апарата немає вибору: він або тупо продовжуватиме політ за списком далі до повного розряду батареї й аварійної посадки в лісі, або просто пролетить повз аномалію, не зробивши повторного детального проходу. Лінійний список точок позбавлений здатності ухвалювати локальні рішення — він сліпий до динаміки довкілля й внутрішнього стану апарата.

Щоб польотне завдання могло реагувати на світ, воно має трансформуватися зі статичного масиву координат у повноцінну виконувану **програму**. У такій програмі вейпойнти стають просторовими інструкціями переміщення, між якими з'являються команди керування потоком: умовні переходи, цикли повторення ділянок, очікування за подіями сенсорів і аварійні відгалуження.

## Провал лінійного масиву: перехід до графа дій

Традиційний погляд на місію як на одновимірний масив точок `[WP_0, WP_1, ..., WP_N]` спирається на тривіальний автомат переходу:

```
поточний_індекс := поточний_індекс + 1
```

Цей перехід спрацьовує виключно за просторовим критерієм — коли відстань до поточної цілі стає меншою за радіус прийняття. Але реальні задачі автономного комплексу вимагають значно гнучкішої поведінки:

1. **Багаторазове повторення траєкторії (цикли):** очікування коридору посадки над точкою, патрулювання периметра або пошарове зняття карти місцевості. Складати для цього список із тисячі однакових точок — нераціонально через ліміт пам'яті польотного контролера (типово 500–2000 пунктів у Flash/EEPROM).
2. **Динамічні затримки та очікування (блокування потоку дій):** відкриття затвора скидання корисного навантаження не в момент прольоту точки, а рівно за 30 метрів до неї або після розвороту апарата на заданий курс за вітром.
3. **Реактивні розгалуження за станом давачів:** перевірка залишку заряду акумулятора, наявності сигналу супутників, температури силових ключів або оптичного контакту з мішенню з переходом на іншу гілку місії.

![Еволюція структури місії від простого списку точок до графа потоку керування](/root/course/embedded/misiia-iak-prohrama/img/mission-graph.svg)
*Еволюція структури місії. Ліворуч — лінійний список із послідовним інкрементом вказівника. Праворуч — орієнтований граф дій, де з'являються зворотні ребра циклів (DO_JUMP) та аварійні переходи за порогом сенсорів.*

Коли до списку додаються переходи за довільними мітками, місія перетворюється на **орієнтований граф дій**. Вершинами цього графа є просторові уставки або команди виконавчим механізмам, а ребрами — умови переходу: просторове влучання, таймери, лічильники повторів або булеві предикати бортової телеметрії.

## Граматика польотних команд: NAV, DO та CONDITION

У стандарті протоколу MAVLink і в архітектурі прошивок (ArduPilot, PX4) елементи місії чітко розбиті на три ортогональні класи, кожен із яких має свою специфіку виконання в часі.

| Клас команди | Префікс у MAVLink | Вплив на рух апарата | Блокування черги виконання | Приклади команд |
| :--- | :--- | :--- | :--- | :--- |
| **Навігаційні** | `MAV_CMD_NAV_*` | Змінюють позицію у просторі, формують уставку для регуляторів | **Блокувальні**: наступна команда не починається, поки не досягнуто критерію поточної | `NAV_WAYPOINT`, `NAV_TAKEOFF`, `NAV_LAND`, `NAV_LOITER_TIME`, `NAV_RTL` |
| **Миттєві дії** | `MAV_CMD_DO_*` | Керують периферією, параметрами польоту та потоком коду | **Неблокувальні**: виконуються за 1 такт, не зупиняючи просторовий рух | `DO_SET_SERVO`, `DO_SET_RELAY`, `DO_CHANGE_SPEED`, `DO_JUMP`, `DO_SET_ROI` |
| **Умовні** | `MAV_CMD_CONDITION_*` | Не рухають апарат, очікують зміни внутрішнього стану чи таймера | **Блокувальні для DO-черги**: призупиняють виконання наступних `DO_*` дій | `CONDITION_DELAY`, `CONDITION_DISTANCE`, `CONDITION_YAW`, `CONDITION_GATE` |

Розподіл на ці три класи розв'язує фундаментальну проблему керування: як поєднати неперервний рух із дискретними подіями. Навігаційний контур не може бути «поставлений на паузу» звичайною функцією очікування на зразок `delay()`, бо апарат миттєво втратить стабілізацію й розіб'ється. Навігація продовжує вести дрон за активною `NAV`-командою, тоді як допоміжний диспетчер умов паралельно перевіряє стан `CONDITION`-елементів і запускає відповідні `DO`-дії.

### Взаємодія черг усередині польотного контролера

В архітектурі автопілота диспетчер місії тримає два паралельних показники стану:
1. **`_nav_cmd` (активна навігаційна команда):** визначає поточну просторову траєкторію (вейпойнт, політ по колу, зліт чи посадка). Вона утримується доти, доки оцінювач навігації EKF не підтвердить вхід у радіус прийняття або завершення процедури посадки.
2. **`_do_cmd_queue` (конвеєр допоміжних дій):** черга з інструкцій налаштування обладнання та переходів. Коли навігаційний пункт стає активним, диспетчер за один такт прочитує всі наступні `DO_*` команди аж до наступної `NAV_*` або `CONDITION_*` команди.

Якщо автопілот зустрічає `CONDITION_DELAY(5)`, він блокує просування по черзі `DO`-команд на 5 секунд, проте апарат **не зупиняється в повітрі** — він продовжує рух до активного `NAV_WAYPOINT`. Після вичерпання 5 секунд наступна команда `DO_SET_SERVO` спрацьовує прямо під час польоту між точками.

### Семантика прапорця autocontinue

Поле `autocontinue` (0 або 1) в заголовку елемента місії визначає, чи повинен автопілот автоматично переходити до наступного пункту після досягнення поточного:
- `autocontinue = 1`: класичний автономний режим. Досягнувши радіуса прийняття вейпойнта, система негайно бере наступний індекс.
- `autocontinue = 0`: режим покрокового виконання (Step-by-Step Execution). Апарат переходить у режим зависання (Loiter) на досягнутій точці й чекає від наземної станції явної команди `MAV_CMD_MISSION_START` або `MISSION_SET_CURRENT`. Це незамінно при налагодженні складних місій із корисним навантаженням або на етапі льотних випробувань нової прошивки.

## Механіка циклів: DO_JUMP, лічильники повторів та стан у RAM

Найпростішою формою нелінійного керування потоком у місії є команда `MAV_CMD_DO_JUMP` (код ID 177). Її структура в пакеті `MISSION_ITEM_INT` містить два ключових параметри:

- **`param1` (`target_seq`):** номер пункту місії (0-індексований або 1-індексований залежно від реалізації автопілота), куди здійснюється безумовний стрибок.
- **`param2` (`repeat_count`):** кількість повторів переходу.

### Чому лічильник циклу не можна зберігати у Flash/EEPROM

Поширена помилка розробників-початківців — зберігати декрементований залишок повторів прямо в масиві місії в енергонезалежній пам'яті. Це неприпустимо з двох причин:

1. **Деградація кремнію (Flash Wear):** польотна місія з циклом на 100 ітерацій при частоті переходу раз на кілька секунд призведе до сотень циклів перезапису одного сектора EEPROM/NOR Flash за політ. Нормований ресурс комірок вбудованого Flash становить від 10 000 до 100 000 циклів стирання, після чого сектор необоротно деградує, викликаючи відмову пам'яті бортового комп'ютера.
2. **Неможливість повторного запуску:** якщо лічильник у флеш-пам'яті зменшиться до 0, повторний старт тієї самої місії з землі без повторного заливання по радіоканалу виявиться зламаним — цикли просто пропускатимуться, оскільки `repeat_count` вже обнулений.

Тому автопілоти розділяють **статичне визначення місії** (яке зберігається в Flash без змін) та **динамічний стан виконання** (runtime state), що живе виключно в оперативній пам'яті (SRAM).

![Механіка DO_JUMP та таблиця лічильників циклів у RAM](/root/course/embedded/misiia-iak-prohrama/img/do-jump-state.svg)
*Взаємодія Flash і RAM при обробці DO_JUMP. Статичний масив місії у Flash лишається незмінним. У RAM створюється динамічна таблиця лічильників, яка декрементується при кожному стрибку й скидається при перезапуску місії.*

### Алгоритм роботи диспетчера DO_JUMP

Коли вказівник поточної інструкції `pc` доходить до `DO_JUMP`, диспетчер виконує наступну послідовність дій:

1. Перевіряє, чи існує запис для поточного `pc` у таблиці `jump_table` в RAM.
2. Якщо запису немає: створює новий запис, копіюючи `repeat_count` із Flash-інструкції в поле `remaining`.
3. Якщо `remaining > 0`:
   - зменшує `remaining := remaining - 1`;
   - змінює програмний лічильник `pc := target_seq`;
   - перемикає активну ціль навігаційного контуру на пункт `target_seq`.
4. Якщо `remaining == 0`:
   - інвалідує або очищає запис у RAM-таблиці;
   - інкрементує `pc := pc + 1`, дозволяючи місії вийти з циклу й продовжити виконання наступних інструкцій.

Розглянемо трасування виконання циклу для місії з трьох точок (пункти 1, 2, 3) і команди `DO_JUMP(target=1, repeats=2)` у пункті 4:

```
Старт місії:
Крок 1: NAV_WAYPOINT A  --> досягнуто
Крок 2: NAV_WAYPOINT B  --> досягнуто
Крок 3: NAV_WAYPOINT C  --> досягнуто
Крок 4: DO_JUMP(1, 2)   --> Ініціалізація в RAM: rem=2. Декремент: rem=1. Стрибок на seq=1.

Ітерація 1:
Крок 1: NAV_WAYPOINT A  --> досягнуто
Крок 2: NAV_WAYPOINT B  --> досягнуто
Крок 3: NAV_WAYPOINT C  --> досягнуто
Крок 4: DO_JUMP(1, 2)   --> Запис у RAM знайдено: rem=1. Декремент: rem=0. Стрибок на seq=1.

Ітерація 2:
Крок 1: NAV_WAYPOINT A  --> досягнуто
Крок 2: NAV_WAYPOINT B  --> досягнуто
Крок 3: NAV_WAYPOINT C  --> досягнуто
Крок 4: DO_JUMP(1, 2)   --> Запис у RAM: rem=0. Очищення запису. Перехід на seq=5.

Вихід із циклу:
Крок 5: NAV_LAND        --> Посадка
```

Разом контур тричі пройшов точки A, B, C (перший прохід + 2 повтори), після чого коректно вийшов на посадку.

### Вкладені цикли та керування стеком переходів

Коли одна циклічна ділянка вкладена в іншу (наприклад, багаторазовий прохід сканування окремого поля всередині великого циклу обльоту кількох полів), проста скалярна змінна не підходить — потрібна таблиця слотів.

Якщо внутрішній цикл `DO_JUMP_inner` завершує свої ітерації й скидає лічильник у нуль, зовнішній цикл `DO_JUMP_outer` знову переводить `pc` на початок блоку. При повторному вході у внутрішній цикл диспетчер фіксує відсутність активного запису в RAM-таблиці й **повторно ініціалізує** внутрішній лічильник повним значенням `repeat_count`. Завдяки цьому вкладені цикли працюють детерміновано без взаємного блокування.

## Умовні переходи й реакція на сенсори: CONDITION-команди

На відміну від безумовних циклів, умовне керування потоком вимагає періодичного опитування сенсорного контексту в навігаційному циклі: щотакту з періодом 20–100 мс (частота 10–50 Гц) перевіряється активна умова. У стандарті MAVLink визначено три класичні умовні інструкції:

1. **`MAV_CMD_CONDITION_DELAY` (112):** затримує виконання наступних дій на `param1` секунд. При цьому апарат продовжує рух за попередньою навігаційною командою (наприклад, летить до наступного вейпойнта).
2. **`MAV_CMD_CONDITION_DISTANCE` (114):** блокує потік дій доти, доки відстань до наступного вейпойнта не стане меншою або рівною `param1` метрів. Це дозволяє, наприклад, увімкнути лазерний сканер або опустити підвіс камери точно за 50 метрів до об'єкта інспекції.
3. **`MAV_CMD_CONDITION_YAW` (115):** повертає апарат на заданий кут курсу `param1` з кутовою швидкістю `param2` град/с і блокує наступні дії до завершення розвороту.

![Конвеєр неблокуючої оцінки умов у польотному циклі](/root/course/embedded/misiia-iak-prohrama/img/condition-evaluation.svg)
*Неблокуючий конвеєр оцінки умов. Щотакту (період такту 20–100 мс, частота 10–50 Гц) диспетчер перевіряє булевий предикат умови. Навігаційний та стабілізаційний контури працюють паралельно без затримок.*

### Розрахунок умов без блокування та плаваючої коми

Розглянемо практичні нюанси обчислення предикатів:

- **Перевірка часу (`CONDITION_DELAY`):** обчислюється через безнакові різниці таймера мікроконтролера `(uint32_t)(now_ms - start_ms) >= target_ms`. Такий підхід захищений від переповнення 32-бітного лічильника мілісекунд (яке настає кожні 49.7 діб безперервної роботи).
- **Перевірка кута курсу (`CONDITION_YAW`):** кутова похибка між поточним кутом рискання ψ та цільовим ψ_target повинна нормалізуватися на інтервал [-π, +π] або [-180°, +180°]. Без нормалізації перехід через нульовий меридіан (північ: 359° → 1°) спричинить хибний розворот на 358° у зворотний бік.
- **Перевірка відстані (`CONDITION_DISTANCE`):** для локальних відрізків маршруту (до кількох кілометрів) замість повільної тригонометричної формули гаверсинуса обчислюють проєкцію на пласку дотичну площину:

```
dX = (lon_target - lon_cur) * 1e-7 * 111320 * cos(lat_cur * 1e-7)
dY = (lat_target - lat_cur) * 1e-7 * 111320
dist_sq = dX * dX + dY * dY
```

Порівняння квадрата відстані `dist_sq <= target_dist * target_dist` усуває важку операцію добування квадратного кореня `sqrtf()`, зберігаючи мікросекунди процесорного часу в кожному такті.

- **Перевірка батареї (`JUMP_IF_BAT_LOW`):** пряме читання напруги дає хибні спрацьовування через динамічне просідання напруги на внутрішньому опорі акумулятора при різкому збільшенні тяги. Тому умова повинна спиратися або на фільтрований State of Charge (SoC у відсотках із кулонівського лічильника), або на напругу, згладжену низькочастотним фільтром із постійною часу τ ≈ 2–5 с.

:::tabs
=== "C"
```c
#include <stdbool.h>
#include <stdint.h>
#include <math.h>

typedef enum {
    COND_NONE,
    COND_WAIT_DELAY,
    COND_WAIT_DISTANCE,
    COND_WAIT_BATTERY
} condition_type_t;

typedef struct {
    condition_type_t type;
    uint32_t         start_timestamp_ms;
    uint32_t         target_duration_ms;
    float            target_distance_m;
    float            min_battery_soc_pct;
} active_condition_t;

bool evaluate_condition_tick(const active_condition_t *cond,
                             uint32_t current_time_ms,
                             float current_dist_m,
                             float current_battery_pct)
{
    switch (cond->type) {
        case COND_WAIT_DELAY:
            return (current_time_ms - cond->start_timestamp_ms) >= cond->target_duration_ms;

        case COND_WAIT_DISTANCE:
            return (current_dist_m <= cond->target_distance_m);

        case COND_WAIT_BATTERY:
            return (current_battery_pct < cond->min_battery_soc_pct);

        case COND_NONE:
        default:
            return true;
    }
}
```

## Пастка Тюрінга: проблема нескінченних циклів та Loop Guards

Додавання до польотної місії переходів `DO_JUMP` та умовних операторів формально наближає мову місій до класу **Тюрінг-повних систем**. Це створює класичну проблему інформатики — **проблему зупинки (Halting Problem)**: неможливо статично довести для довільної програми, чи завершить вона роботу за скінченний час.

Для літального апарата чи мобільного робота нескінченний цикл є критичною загрозою: якщо машина зациклиться на ділянці маршруту й спалить усю енергію, вона неминуче впаде або втратить зв'язок.

### Типові пастки виконання циклів

1. **Нескінченний стрибок із неможливою умовою виходу:**
   Задано `DO_JUMP` із параметром повторів `-1` (або `65535`, що в MAVLink позначає нескінченний цикл), а всередині циклу відсутня перевірка батареї чи сигналу оператора.
2. **Вкладені перехресні цикли (Oscillating Jumps / Livelock):**
   Пункт 3 стрибає на пункт 1, а пункт 2 за певної сенсорної умови стрибає на пункт 4. Утворюється ситуація змагання станів, де лічильники скидаються або блокують один одного, унеможливлюючи вихід до термінальної точки.
3. **Зависання на недосяжній умові (Deadlock / Unreachable Condition):**
   Команда `CONDITION_DISTANCE(1.0 м)` поставлена перед точкою, але через сильний вітер регулятор наближається щонайбільше на 1.8 м. Черга дій зависає назавжди, якщо немає таймауту.

### Багаторівневий захист: Loop Guards та Timeouts

Щоб запобігти аваріям, інтерпретатор місій на мікроконтролері обладнується трирівневою системою захисту:

```
Рівень 1: Статичний верифікатор при завантаженні (Static Linter)
          |--> Перевірка цілей переходів (target_seq < total_items)
          |--> Обмеження глибини вкладеності стрибків (max 2 рівні)
          v
Рівень 2: Динамічний бюджет стрибків у RAM (Jump Budget Watchdog)
          |--> Лічильник total_jumps <= MAX_TOTAL_JUMPS (наприклад, 256)
          |--> Таймаут на перебування в одному пункті (item_watchdog_sec)
          v
Рівень 3: Пріоритет системних аварійних захистів (Failsafe Supervisor)
          |--> Низький заряд АКБ / Втрата зв'язку переривають VM
          |--> Аварійний перехід на RTL / Land
```

1. **Статичний аналіз при завантаженні (Upload Verification):** коли наземна станція надсилає місію по MAVLink, автопілот перед відправкою `MISSION_ACK(MAV_MISSION_ACCEPTED)` перевіряє коректність індексів переходу. Якщо `target_seq >= total_items`, пакет відхиляється з кодом помилки `MAV_MISSION_INVALID_PARAM1`.
2. **Глобальний ліміт стрибків (Dynamic Jump Budget):** у RAM виділяється лічильник `total_jumps_executed`. Якщо сумарна кількість стрибків за політ перевищує поріг (наприклад, 256), віртуальна машина перериває цикл і примусово переходить до наступного лінійного блоку або RTL.
3. **Пріоритетний супервізор Failsafe:** будь-яка апаратна аварія (відмова GNSS, перегрів ESC, критичний розряд АКБ) має вищий пріоритет над місією. Супервізор скидає контекст віртуальної машини й перехоплює керування самітним контуром повернення.

## Байткод місії та формат віртуальної інструкції

Зберігання місії у форматі MAVLink `MISSION_ITEM_INT` (38 байтів на пункт) створює надлишкове навантаження на обмежену оперативну пам'ять мікроконтролерів (STM32F4/F7/H7 або ESP32-S3), де сотні пунктів місії вимагають кілобайти статичного ОЗП.

Для оптимізації бортовий інтерпретатор транслює завантажену місію у внутрішній компактний **байткод** фіксованого розміру (20 байтів на інструкцію), де опкод упаковано в 1 байт, а параметри мають строгу типізацію.

```
Структура 20-байтної інструкції Mission Bytecode:
+---------+---------+-------------------+-------------------+-------------------+-------------------+-----------------+
| Opcode  | Flags   | Param 1 (int16_t) | Param 2 (int16_t) | Lat * 1e7 (int32) | Lon * 1e7 (int32) | Alt_m (float32) |
| 1 байт  | 1 байт  | 2 байти           | 2 байти           | 4 байти           | 4 байти           | 4 байти         |
+---------+---------+-------------------+-------------------+-------------------+-------------------+-----------------+
```

### Регістрова модель проти стекової

Для вбудованих польотних інтерпретаторів **пряма адресація аргументів** (регістрово-операційний підхід) значно переважає стекову модель (на зразок Java Virtual Machine чи Forth):
- Немає ризику переповнення стека операндів (Stack Overflow) при помилці в коді місії.
- Декодування інструкції відбувається за один прохід без необхідності циклів `PUSH`/`POP`.
- Повна детермінованість часу виконання (Zero Dynamic Allocation, O(1) час такту).

## Порівняння реалізацій: ArduPilot vs PX4

У реальних автопілотах відкритих екосистем підхід до виконання місій має свої архітектурні відмінності:

- **ArduPilot (`AP_Mission`):** використовує класичну модель подвійного покажчика. Місія зберігається в зарезервованій області EEPROM/Flash (Storage Manager). У пам'яті RAM утримуються структури `_nav_cmd` та `_do_cmd`, а переходи `DO_JUMP` відстежуються через динамічний масив лічильників розміром до 16 слотів. Цикл виконання прив'язаний до виклику `AP_Mission::update()` з частотою 10–50 Гц.
- **PX4 Autopilot (`Navigator` / `MissionBlock`):** спирається на мікросервісну архітектуру навколо шини публікацій/підписок uORB. Місія зберігається у вбудованій базі даних `dataman` на файловій системі SD-карти або SPI Flash. Модуль `navigator` зчитує пункти місії порціями (блоками по 2–3 елементи) і публікує уставки в топік `position_setpoint_triplet`, що дозволяє безшовно інтегрувати згладжування траєкторій (spline waypoints) між переходами.

## Архітектура інтерпретатора Mission VM

Бортова віртуальна машина організована як автономний модуль із чітким інтерфейсом до решти системи.

![Архітектура бортової віртуальної машини місій](/root/course/embedded/misiia-iak-prohrama/img/mission-vm-architecture.svg)
*Архітектура віртуальної машини Mission VM. Вхід — статичний байткод і телеметрія давачів. Ядро виконує 4 фази: Fetch, Decode, Evaluate, Guard. Вихід — уставки в контур навігації та PWM-команди приводам.*

Життєвий цикл виконання кожної інструкції складається з чотирьох фаз:

1. **FETCH (Вибірка):** зчитування структури інструкції за індексом `pc`. Перевірка межі програми (`pc < len`).
2. **DECODE (Декодування):** аналіз опкоду, видобування аргументів (координати, таймери, пороги).
3. **EVALUATE & DISPATCH (Оцінка та виконання):**
   - Якщо це `NAV`: оновлення глобальної уставки навігаційного контуру.
   - Якщо це `DO`: негайна видача сигналу периферії (`PWM`, `GPIO`) або зміна швидкості.
   - Якщо це `CONDITION`: перевірка сенсорного предиката. Якщо `false` — вихід із такту без інкременту `pc`.
   - Якщо це `JUMP`: обчислення залишку в RAM-таблиці та модифікація `pc`.
4. **GUARD CHECK (Контроль безпеки):** верифікація лічильника стрибків і перевірка таймауту поточної інструкції.

## Збірка ядра віртуальної машини на C та C++

Наведемо базовий каркас виконання інструкцій віртуальної машини з захистом від зациклення та обробкою переходів:

:::tabs
=== "C"
```c
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

#define MAX_ITEMS        64
#define MAX_TOTAL_JUMPS  128

typedef enum {
    OP_HALT          = 0,
    OP_WAYPOINT      = 1,
    OP_JUMP          = 2,
    OP_CHECK_BATTERY = 3
} opcode_t;

typedef struct {
    opcode_t opcode;
    uint16_t target;
    uint16_t param;
    float    lat;
    float    lon;
    float    alt;
} instr_t;

typedef struct {
    instr_t  code[MAX_ITEMS];
    uint16_t code_len;
    uint16_t pc;
    uint16_t jump_counts[MAX_ITEMS];
    uint16_t total_jumps;
    bool     finished;
    bool     error_infinite_loop;
} vm_core_t;

void vm_init(vm_core_t *vm, const instr_t *program, uint16_t len) {
    memset(vm, 0, sizeof(vm_core_t));
    if (len > MAX_ITEMS) len = MAX_ITEMS;
    memcpy(vm->code, program, len * sizeof(instr_t));
    vm->code_len = len;
    vm->pc = 0;
}

void vm_tick(vm_core_t *vm, float bat_soc_pct, bool wp_reached) {
    if (vm->finished || vm->error_infinite_loop || vm->pc >= vm->code_len) {
        vm->finished = true;
        return;
    }

    const instr_t *curr = &vm->code[vm->pc];

    switch (curr->opcode) {
        case OP_HALT:
            vm->finished = true;
            break;

        case OP_WAYPOINT:
            if (wp_reached) {
                vm->pc++;
            }
            break;

        case OP_CHECK_BATTERY:
            if (bat_soc_pct < (float)curr->param) {
                vm->pc = curr->target; /* Стрибок на аварійну гілку */
            } else {
                vm->pc++;
            }
            break;

        case OP_JUMP:
            if (vm->total_jumps >= MAX_TOTAL_JUMPS) {
                vm->error_infinite_loop = true;
                break;
            }

            if (vm->jump_counts[vm->pc] < curr->param) {
                vm->jump_counts[vm->pc]++;
                vm->total_jumps++;
                vm->pc = curr->target;
            } else {
                vm->jump_counts[vm->pc] = 0; /* Скидання для наступних входів */
                vm->pc++;
            }
            break;
    }
}
```
=== "C++"
```cpp
#include <cstdint>
#include <array>
#include <span>
#include <algorithm>

namespace mission {

enum class Opcode : uint8_t {
    Halt         = 0,
    Waypoint     = 1,
    Jump         = 2,
    CheckBattery = 3
};

struct Instruction {
    Opcode   opcode{Opcode::Halt};
    uint16_t target{0};
    uint16_t param{0};
    float    lat{0.0f};
    float    lon{0.0f};
    float    alt{0.0f};
};

class SimpleMissionVm {
public:
    static constexpr size_t   kMaxItems = 64;
    static constexpr uint16_t kMaxTotalJumps = 128;

    explicit SimpleMissionVm(std::span<const Instruction> program) {
        const size_t copy_len = std::min(program.size(), kMaxItems);
        for (size_t i = 0; i < copy_len; ++i) {
            code_[i] = program[i];
        }
        code_len_ = copy_len;
        jump_counts_.fill(0);
    }

    void tick(float bat_soc_pct, bool wp_reached) noexcept {
        if (finished_ || error_infinite_loop_ || pc_ >= code_len_) {
            finished_ = true;
            return;
        }

        const auto& curr = code_[pc_];

        switch (curr.opcode) {
            case Opcode::Halt:
                finished_ = true;
                break;

            case Opcode::Waypoint:
                if (wp_reached) {
                    pc_++;
                }
                break;

            case Opcode::CheckBattery:
                if (bat_soc_pct < static_cast<float>(curr.param)) {
                    pc_ = curr.target; // Аварійний перехід
                } else {
                    pc_++;
                }
                break;

            case Opcode::Jump:
                if (total_jumps_ >= kMaxTotalJumps) {
                    error_infinite_loop_ = true;
                    break;
                }

                if (jump_counts_[pc_] < curr.param) {
                    jump_counts_[pc_]++;
                    total_jumps_++;
                    pc_ = curr.target;
                } else {
                    jump_counts_[pc_] = 0; // Скидання лічильника
                    pc_++;
                }
                break;
        }
    }

    [[nodiscard]] bool is_finished() const noexcept { return finished_; }
    [[nodiscard]] bool has_error() const noexcept { return error_infinite_loop_; }
    [[nodiscard]] size_t program_counter() const noexcept { return pc_; }

private:
    std::array<Instruction, kMaxItems> code_{};
    std::array<uint16_t, kMaxItems>    jump_counts_{};
    size_t   code_len_{0};
    size_t   pc_{0};
    uint16_t total_jumps_{0};
    bool     finished_{false};
    bool     error_infinite_loop_{false};
};

} // namespace mission
```

## Підсумок

Програмована місія перетворює безпілотний апарат із пасивного виконавця списку координат на адаптивну автономну систему. 

Ключові інженерні принципи побудови таких систем:

- **Розділення команд за часовою моделлю:** блокувальні навігаційні команди `NAV_*` рухають дрон у просторі, тоді як миттєві `DO_*` та умовні `CONDITION_*` діють паралельно, не заморожуючи контури стабілізації.
- **Ізоляція стану виконання в RAM:** статичний опис місії зберігається в постійній пам'яті (Flash/EEPROM), а лічильники циклів і таймери оновлюються виключно в оперативній пам'яті (SRAM), усуваючи зношування чипів.
- **Багаторівневий захист від Тюрінг-пасток:** кожна виконувана місія повинна мати глобальний ліміт кількості переходів (Jump Budget), таймаути на окремі кроки та безумовний пріоритет системного Failsafe-супервізора над користувацьким кодом місії.
- **Компактний детермінований байткод:** використання простої регістрово-параметричної моделі інструкцій гарантує виконання кожного такту за O(1) часу та захищає мікроконтролер від переповнення стека.
