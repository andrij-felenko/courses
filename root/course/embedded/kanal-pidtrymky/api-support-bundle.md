# 📋 Специфікація структури даних діагностичного знімка (Support Bundle)

Діагностичний знімок (англ. *support bundle* або *crash snapshot*) — це стандартизований двійковий та текстовий пакет даних, який вбудований пристрій формує в момент аварійного завершення роботи (паніки ядра, спрацьовування апаратного винятку `HardFault` чи сторожового таймера) або на запит сервісного техніка. Головне призначення цієї структури — зафіксувати повний контекст стану апаратного забезпечення, регістрів мікроконтролера, кільцевого буфера подій та телеметрії живлення без залучення динамічної пам'яті (купи) та зберегти його в незалежній пам'яті для подальшого аналізу інженерами другої та третьої ліній підтримки.

---

## 1. Загальна компоновка двійкового кадру

Двійковий образ знімка розміщується у виділеному секторі Flash-пам'яті (розділ `coredump` або `diagnostics`) чи в енергонезалежній пам'яті FRAM/MRAM. Структура вирівняна по 4-байтовій межі (32 біти) для прямого відображення в пам'ять процесора без накладних витрат на десеріалізацію.

Усі числові значення записуються у форматі зі прямим порядком байтів (англ. *little-endian*), що відповідає архітектурі ARM Cortex-M. Загальний розмір пакета знімка складає фіксовані 512 або 1024 байти (залежно від глибини кільцевого буфера подій), що дозволяє записувати його за одну сторінкову операцію у внутрішню або зовнішню SPI Flash-пам'ять.

```
+-------------------------------------------------------------------+
|  1. Заголовок пакета (Header & Device Identity) — 64 байти        |
+-------------------------------------------------------------------+
|  2. Аварійний контекст ядра та регістри (Fault Context) — 64 байти|
+-------------------------------------------------------------------+
|  3. Телеметрія живлення та сенсорного оточення — 48 байтів        |
+-------------------------------------------------------------------+
|  4. Лічильники помилок периферійних шин — 32 байти                |
+-------------------------------------------------------------------+
|  5. Кільцевий журнал останніх подій (Event Log Buffer) — N байтів |
+-------------------------------------------------------------------+
|  6. Контрольна сума цілісності пакета (CRC32) — 4 байти           |
+-------------------------------------------------------------------+
```

## 2. Заголовок пакета та цифрова ідентифікація виробу

Заголовок містить магічні байти для швидкої перевірки формату, версію структури, унікальні апаратні ідентифікатори екземпляра та мітку часу виникнення інциденту.

### Специфікація полів заголовка (`bundle_header_t`)

| Зсув (байти) | Поле | Тип | Опис та семантика |
|---|---|---|---|
| `0x00..0x03` | `magic` | `uint32_t` | Фіксована константа `0x4442554E` (символи ASCII `'DBUN'` — Device Bundle). |
| `0x04..0x05` | `version` | `uint16_t` | Версія формату знімка. Старший байт — мажорна версія (`0x02`), молодший — мінорна (`0x00`). |
| `0x06..0x07` | `header_size`| `uint16_t` | Розмір заголовка в байтах (завжди `64`). |
| `0x08..0x0B` | `payload_size`| `uint32_t`| Повний розмір даних після заголовка (включно з логом та CRC). |
| `0x0C..0x17` | `device_uid` | `uint8_t[12]`| Унікальний 96-бітний ідентифікатор кристала (MCU Unique ID). |
| `0x18..0x1B` | `serial_num` | `uint32_t` | Серійний номер виробу, внесений під час заводського провізіонування. |
| `0x1C..0x1D` | `hw_revision`| `uint16_t` | Ревізія друкованої плати: старший байт — ревізія (наприклад, `'C'`), молодший — BOM-варіант. |
| `0x1E..0x1F` | `reset_reason`| `uint16_t`| Бітова маска причини останнього перезапуску (розшифровка нижче). |
| `0x20..0x23` | `fw_git_hash`| `uint32_t` | Перші 4 байти комбінації Git commit hash робочої прошивки. |
| `0x24..0x27` | `boot_git_hash`| `uint32_t`| Перші 4 байти Git commit hash первинного завантажувача (Bootloader). |
| `0x28..0x2F` | `uptime_ms`  | `uint64_t` | Час безперервної роботи від останнього запуску в мілісекундах. |
| `0x30..0x37` | `unix_epoch` | `uint64_t` | Реальний час за шкалою UTC (якщо доступний RTC/NTP), інакше `0`. |
| `0x38..0x3B` | `boot_count` | `uint32_t` | Сумарний лічильник перезапусків за весь життєвий цикл плати. |
| `0x3C..0x3F` | `reserved`   | `uint32_t` | Зарезервовано для розширення (заповнюється нулями `0x00000000`). |

### Бітова маска причини скидання (`reset_reason`)

Поле `reset_reason` фіксує фізичне джерело останнього перезапуску мікроконтролера, зчитане з системних регістрів (наприклад, `RCC_CSR` у STM32 або `RTC_CNTL_RESET_STATE` в ESP32):

- `0x0001` (`RESET_POR`): Холодний старт при первинній подачі напруги живлення (Power-On Reset).
- `0x0002` (`RESET_PIN`): Зовнішній фізичний імпульс на піні апаратного скидання `NRST` або кнопці Reset.
- `0x0004` (`RESET_BOR`): Спрацьовування схеми контролю просадки живлення (Brownout Reset).
- `0x0008` (`RESET_IWDG`): Таймаут незалежного сторожового таймера (Independent Watchdog).
- `0x0010` (`RESET_WWDG`): Спрацьовування віконного сторожового таймера (Window Watchdog).
- `0x0020` (`RESET_SOFT`): Програмне перезавантаження через виклик `NVIC_SystemReset()`.
- `0x0040` (`RESET_LPWR`): Пробудження з глибокого енергозберігаючого сну (Deep Sleep / Standby).
- `0x0080` (`RESET_FAULT`): Аварійний перезапуск після перехоплення винятку `HardFault` чи паніки ядра.

## 3. Аварійний контекст ядра та регістри збою (`fault_context_t`)

Цей блок формується автоматично в обробнику винятків процесора (наприклад, `HardFault_Handler` або Panic Supervisor) і містить зріз регістрів процесорного ядра в момент аварії.

### Структура регістрів ARM Cortex-M

:::tabs
```c
typedef struct __attribute__((packed)) {
    uint32_t r0;          /* Регістр загального призначення R0 */
    uint32_t r1;          /* Регістр загального призначення R1 */
    uint32_t r2;          /* Регістр загального призначення R2 */
    uint32_t r3;          /* Регістр загального призначення R3 */
    uint32_t r12;         /* Внутрішньопроцедурний регістр виклику R12 */
    uint32_t lr;          /* Регістр зв'язку (Link Register — адреса повернення) */
    uint32_t pc;          /* Лічильник команд (Program Counter — адреса падіння) */
    uint32_t xpsr;        /* Стан процесора (Program Status Register) */
    uint32_t msp;         /* Вказівник основного стека (Main Stack Pointer) */
    uint32_t psp;         /* Вказівник стека процесів (Process Stack Pointer) */
    uint32_t cfsr;        /* Configurable Fault Status Register (UFSR + BFSR + MMFSR) */
    uint32_t hfsr;        /* HardFault Status Register */
    uint32_t mmfar;       /* Memory Management Fault Address Register */
    uint32_t bfar;        /* BusFault Address Register */
    uint32_t active_task; /* Числовий ID або перші 4 літери імені таски FreeRTOS */
    uint32_t stack_high_water; /* Мінімальний залишок пам'яті стека в байтах */
} fault_context_t;
```

### Розшифровка діагностичних бітів регістра CFSR

Регістр `CFSR` (Configurable Fault Status Register) об'єднує три підсистеми апаратної діагностики Cortex-M:

1. **UsageFault (старші 16 бітів `0xFFFF0000`):**
   - Біт 25 (`DIVBYZERO`): спроба ділення цілого числа на нуль при увімкненому біті `DIV_0_TRP`.
   - Біт 24 (`UNALIGNED`): незрівняний доступ до пам'яті (наприклад, читання 32-бітного слова за непарною адресою).
   - Біт 18 (`NOCP`): спроба виконати інструкцію співпроцесора FPU, коли блок плаваючої коми вимкнено.
   - Біт 16 (`UNDEFINSTR`): процесор зустрів невідому інструкцію (помилка вказівника на функцію або спотворення Flash).
2. **BusFault (середні 8 бітів `0x0000FF00`):**
   - Біт 15 (`BFARVALID`): адреса у регістрі `BFAR` є достовірною та вказує на точну адресу шини, де виник збій.
   - Біт 10 (`PRECISERR`): точна помилка шини даних (доступ до неіснуючого периферійного регістра).
   - Біт 9 (`IMPRECISERR`): неточна помилка шини (виникає при асинхронному записі з буферизацією).
3. **MemManageFault (молодші 8 бітів `0x000000FF`):**
   - Біт 7 (`MMARVALID`): адреса у регістрі `MMFAR` є дійсною адресою порушення доступу.
   - Біт 1 (`DACCVIOL`): спроба читання або запису в пам'ять із порушенням прав MPU (Memory Protection Unit).
   - Біт 0 (`IACCVIOL`): спроба виконати код з пам'яті, позначеної як XN (Execute Never, наприклад з RAM чи периферії).

## 4. Блок телеметрії живлення та середовища (`environment_telemetry_t`)

Фіксує фізичні умови, за яких працював пристрій перед збоєм.

| Поле | Тип | Одиниці | Опис |
|---|---|---|---|
| `v_in_mv` | `uint16_t` | мВ | Напруга основної лінії живлення (наприклад, `23850` мВ для лінії 24 В). |
| `v_3v3_mv` | `uint16_t` | мВ | Напруга внутрішньої цифрової шини 3.3 В (контроль LDO/DC-DC). |
| `v_bat_mv` | `uint16_t` | мВ | Напруга резервної акумуляторної батареї або іоністора RTC. |
| `mcu_temp_c10`| `int16_t` | 0.1 °C | Температура кристала процесора (наприклад, `+485` = +48.5 °C). |
| `board_temp_c10`| `int16_t`| 0.1 °C | Температура плати біля вхідних силових ключів. |
| `current_ma` | `uint16_t` | мА | Поточне споживання струму платою. |
| `brownout_count`| `uint16_t`| лічильник | Кількість зафіксованих спрацьовувань детектора просадки живлення. |
| `flash_bad_blocks`| `uint16_t`| лічильник | Кількість збійних секторів у файловій системі Flash (LittleFS/FAT). |

## 5. Лічильники збоїв периферійних інтерфейсів (`bus_health_t`)

Лічильники дозволяють відрізнити програмну помилку від апаратного обриву лінії або електромагнітної завади на сигнальних шинах:

- `i2c_nack_errors` (`uint16_t`) — кількість невідповідей від зовнішніх датчиків за шиною I2C.
- `i2c_bus_lockups` (`uint16_t`) — кількість примусових скидань тактової лінії `SCL` через зависання веденого чипа.
- `spi_crc_timeouts` (`uint16_t`) — кількість тайм-аутів при роботі з зовнішньою Flash/FRAM.
- `uart_framing_errors` (`uint16_t`) — помилки синхронізації та зміщення бітів (наслідок невідповідності baud rate або шуму).
- `can_bus_off_count` (`uint16_t`) — переходи трансивера CAN у стан вимкнення через лавину помилок передачі.
- `lora_or_cellular_reconnects` (`uint16_t`) — кількість аварійних перезапусків радіомодема по живленню.

## 6. Кільцевий буфер подій (Circular Event Log)

Журнал складається з масиву фіксованих записів по 16 байтів кожен. Це забезпечує швидкий доступ без парсингу рядків.

:::tabs
```c
typedef struct __attribute__((packed)) {
    uint32_t timestamp_ms; /* Час події від моменту старту */
    uint8_t  subsystem_id; /* ID підсистеми (1: POWER, 2: SENSORS, 3: NET, 4: STORAGE, 5: CONTROL) */
    uint8_t  severity;     /* Рівень (1: DEBUG, 2: INFO, 3: WARN, 4: ERROR, 5: CRITICAL) */
    uint16_t event_code;   /* Унікальний числовий код події за каталогом */
    uint32_t argument;     /* Числовий аргумент (помилкове значення, адреса або статус-код) */
    uint32_t caller_pc;    /* Значення Program Counter, з якого здійснено логування */
} log_entry_t;
```
```cpp
#include <cstdint>

namespace diagnostic {

struct [[gnu::packed]] LogEntry {
    std::uint32_t timestamp_ms{};
    std::uint8_t  subsystem_id{};
    std::uint8_t  severity{};
    std::uint16_t event_code{};
    std::uint32_t argument{};
    std::uint32_t caller_pc{};
};

} // namespace diagnostic
```
:::

### Каталог числових ідентифікаторів підсистем (`subsystem_id`)

- `0x01` (`SUBSYS_POWER`): Джерела живлення, супервізори напруги, чарджери акумуляторів.
- `0x02` (`SUBSYS_SENSORS`): Датчики температури, тиску, струму, вібрації, АЦП.
- `0x03` (`SUBSYS_NET`): Мережеві інтерфейси (Ethernet, Wi-Fi, BLE, LTE Cat-M1/NB-IoT, LoRaWAN).
- `0x04` (`SUBSYS_STORAGE`): Енергонезалежна пам'ять Flash, FRAM, файлові системи LittleFS/FATFS.
- `0x05` (`SUBSYS_CONTROL`): Виконавчі приводи, ШІМ-генератори, реле, алгоритми зворотного зв'язку PID.

## 8. Інтерфейс сервісного вивантаження через консоль CLI

Для ручного вилучення знімка через сервісний UART або USB-CDC консоль реалізує стандартизований набір команд:

- `diag dump` — виводить повний двійковий дамп у шістнадцятковому вигляді (Intel HEX або Base64).
- `diag json` — виводить структурований текстовий звіт JSON для копіювання в заявку підтримки.
- `diag clear` — очищає аварійний сектор незалежної пам'яті після успішної передачі на сервер.
- `diag verify` — виконує перевірку контрольної суми CRC32 збереженого знімка.

### Коди відповідей та обробка помилок консолі

При виконанні діагностичних команд пристрій повертає стандартизований числовий статус:

| Код повернення | Назва | Значення та коригувальні дії |
|---|---|---|
| `0` (`DIAG_OK`) | Успіх | Знімок успішно вичитано або очищено. |
| `-1` (`DIAG_ERR_EMPTY`) | Порожньо | В аварійному секторі Flash немає збереженого знімка (магічні байти відсутні). |
| `-2` (`DIAG_ERR_CRC`) | Помилка CRC | Контрольна сума CRC32 не сходиться; дані пам'яті частково пошкоджені. |
| `-3` (`DIAG_ERR_LOCKED`) | Заблоковано | Flash-контролер заблоковано бітом захисту запису; потрібне зняття захисту. |
| `-4` (`DIAG_ERR_BUSY`) | Зайнято | Підсистема логування зайнята паралельним записом нової події. |
