# 🧮 Розрахунок дрейфу кварцового резонатора та динаміки спустошення черги

Математичний апарат розрахунку часової похибки автономного вузла, ймовірності колізій контрольних сум та балансу пропускної здатності черги повторів під час тривалого обриву зв'язку.

## 1. Температурний дрейф годинникового кварцу 32.768 кГц

Низькочастотні камертонні резонатори (tuning fork crystals), які живлять апаратні годинники реального часу (RTC), мають параболічну залежність відхилення частоти від температури навколишнього середовища:

```
Δf / f₀ = −B · (T − T₀)²
```

де:
- `f₀ = 32768` Гц — номінальна резонансна частота при кімнатній температурі;
- `T₀ ≈ 25` °C — точка перегину параболи (нульового температурного коефіцієнта);
- `B ≈ (0.035 ± 0.005)` ppm/°C² — параболічний коефіцієнт кристала;
- `T` — поточна температура корпусу в °C.

Початкова виробнича похибка калібрування при `T₀ = 25` °C становить `δ_cal = ±20` ppm (parts per million, `10⁻⁶`).

### Розрахунок відносного відхилення при екстремальних температурах

**Приклад 1: Зимові польові умови при `T = −15` °C**

```
ΔT = T − T₀ = −15 − 25 = −40 °C

Δf_temp / f₀ = −0.035 · (−40)²
             = −0.035 · 1600
             = −56.0 ppm

Сумарне найгірше відхилення:
δ_total = δ_cal + Δf_temp / f₀
        = −20 ppm + (−56 ppm)
        = −76.0 ppm
```

**Приклад 2: Літній нагрів закритого щитка при `T = +65` °C**

```
ΔT = 65 − 25 = +40 °C

Δf_temp / f₀ = −0.035 · (+40)² = −56.0 ppm
δ_total = +20 ppm + (−56 ppm) = −36.0 ppm
```

### Накопичена часова похибка за 24 години обриву зв'язку

Кількість секунд у добі: `S_day = 24 · 3600 = 86400` с.
Абсолютне зміщення астрономічного годинника вузла `Δt_drift` за час відсутності NTP-сервера `T_offline`:

```
Δt_drift = δ_total · T_offline
```

При стабільній температурі `−15` °C протягом доби (`T_offline = 86400` с):

```
Δt_drift = −76.0 · 10⁻⁶ · 86400 с
         = −6.5664 с
```

Якщо вузол перебуває в неопалюваному промисловому корпусі з добовим синусоїдним коливанням температури `T(t) = T_mean + A · sin(2π · t / 86400)`:

```
Δt_drift = ∫₀^{T_offline} [ δ_cal − B · (T(t) − T₀)² ] dt
```

При `T_mean = 5` °C та амплітуді `A = 20` °C (діапазон від −15 °C до +25 °C):
- Середній квадрат відхилення: `⟨(T − T₀)²⟩ = (T_mean − T₀)² + A² / 2 = (−20)² + 400 / 2 = 400 + 200 = 600` °C²;
- Середній дрейф: `δ_avg = −20 ppm − 0.035 · 600 = −20 − 21 = −41 ppm`;
- Накопичений зсув за 24 год: `Δt_drift = −41 · 10⁻⁶ · 86400 ≈ −3.54` с.

Без синхронізації годинник відстає на понад 3.5 секунди щодо абсолютного UTC, що призводить до порушення порядку записів у розподіленій базі даних, якщо сервер індексує події за штампом пристрою, а не за монотонним лічильником `seq_id`.

## 2. Динаміка переповнення та час спустошення кільцевого буфера

Вузол генерує локальні записи телеметрії зі сталою швидкістю `R_gen` (записів за секунду), кожен розміром `S_rec` байтів.

### Розрахунок необхідного обсягу енергонезалежної пам'яті

Нехай сенсорний вузол фіксує виміри кожні `Δt_sample = 2` с (`R_gen = 0.5` Гц).
Розмір бінарного кадру:
- Заголовок (Magic, `seq_id`, `mono_ts`, `flags`): 16 байтів;
- Корисне навантаження (температура, вологість, напруга, статус): 16 байтів;
- Контрольна сума CRC32 + маркер фіксації: 8 байтів;
- Разом `S_rec = 40` байтів.

За 24 години повної ізоляції мережі (`T_blackout = 86400` с):

```
N_records = R_gen · T_blackout
          = 0.5 · 86400 = 43200 записів

V_raw = N_records · S_rec
      = 43200 · 40 байтів
      = 1728000 байтів ≈ 1.648 МБ
```

З урахуванням службових метаданих журналу LittleFS (оверхед покажчиків блоків ≈ 15%):

```
V_flash_required = 1.648 МБ · 1.15 ≈ 1.895 МБ
```

Для надійного зберігання 24-годинного буфера потрібен виділений розділ Flash розміром не менше 2 МБ (512 секторів по 4 КБ).

### Час відновлення та обмеження швидкості спустошення черги

Після відновлення мережевого лінка вузол одночасно передає поточний потік вимірів `R_live = R_gen = 0.5` пакт/с та викачує накопичений архів із черги `R_replay`.

Щоб не перевантажити MQTT-брокер і вузький радіоканал, швидкість викачування архіву лімітується алгоритмом маркерного кошика (Token Bucket) зі стелею `R_drain_max = 10` повідомлень/с.

Ефективна швидкість спустошення черги:

```
R_effective = R_drain_max − R_live
            = 10 − 0.5 = 9.5 записів/с
```

Час повного викачування накопиченого добового буфера `T_drain`:

```
T_drain = N_records / R_effective
        = 43200 / 9.5
        = 4547.37 с ≈ 75.8 хвилин (1 год 16 хв)
```

## 3. Ймовірність колізії контрольних сум у потоці пошкоджених пакетів

Під час активного мережевого хаосу та torn writes у Flash контролер обробляє велику кількість пошкоджених послідовностей байтів. Якщо для перевірки цілісності використовується поліноміальний код CRC32, виникає питання ймовірності пропуску пошкодженого кадру (хибнопозитивне підтвердження цілісності).

Для полінома IEEE 802.3 довжина контрольної суми становить `k = 32` біти. Простір можливих хеш-значень дорівнює `2³² ≈ 4.295 · 10⁹`.

Для випадкового шуму (коли всі біти пошкоджено випадковим чином) ймовірність того, що довільний некоректний набір байтів випадково співпаде з очікуваним 32-бітним CRC32, становить:

```
P_single_collision = 1 / 2³² ≈ 2.328 · 10⁻¹⁰
```

Якщо за час проведення інтенсивного стрес-тестування стенд генерує `N = 10⁶` (один мільйон) пошкоджених кадрів, сумарна ймовірність зафіксувати бодай одну невиявлену помилку розраховується за формулою парадоксу днів народження:

```
P_undetected = 1 − (1 − P_single_collision)ᴺ
             ≈ 1 − exp(−N / 2³²)
             = 1 − exp(−10⁶ / 4.295 · 10⁹)
             ≈ 1 − (1 − 2.328 · 10⁻⁴)
             ≈ 0.0233 %
```

Це доводить, що 32-бітної контрольної суми CRC32 повністю достатньо для ізоляції локальних пошкоджень Flash і мережевих кадрів. Натомість прості 16-бітні суми (CRC16) при `N = 10⁶` дають `P_undetected ≈ 100%`, що призводить до регулярного потрапляння сміттєвих даних у базу.

## 4. Зношення Flash-пам'яті в циклічному режимі

Якщо розмір кільцевого буфера `V_buf = 2` МБ, а сектор NOR Flash витримує `C_erase = 100000` циклів перезапису.
За добу записується `V_raw = 1.728` МБ, тобто буфер робить `K_turn` повних обертів:

```
K_turn = 1.728 МБ / 2.0 МБ = 0.864 оберти/добу
```

Розрахунковий термін служби розділу пам'яті до появи збійних блоків (з ідеальним вирівнюванням зносу wear leveling):

```
Life_days = C_erase / K_turn
          = 100000 / 0.864
          ≈ 115740 діб ≈ 317 років
```

Математичний запас зносостійкості Flash є достатнім навіть за умови щоденних тривалих блекаутів зв'язку, якщо прошивка використовує посторінковий лог без повторного стирання секторів на кожен окремий вимір.

## 5. Вплив температури на деградацію заряду Flash (Модель Арреніуса)

Окрім прямого зносу від циклів стирання, на тривалість збереження даних у Flash під час знеструмлення впливає витік електронів крізь оксидний шар плаваючого затвора. Швидкість витоку експоненційно зростає з підвищенням температури відповідно до закону Арреніуса:

```
AF(T) = exp[ (E_a / k_B) · (1 / T_ref − 1 / T_op) ]
```

де:
- `E_a ≈ 1.1` еВ — енергія активації деградації тунельного діелектрика SiO₂;
- `k_B = 8.617 · 10⁻⁵` еВ/К — стала Больцмана;
- `T_ref = 298.15` К (+25 °C) — базова кімнатна температура;
- `T_op` — фактична температура кристала в Кельвінах.

При роботі в промисловому шафі при `T_op = +85` °C (`358.15` К):

```
1 / T_ref − 1 / T_op = 1 / 298.15 − 1 / 358.15
                     = 0.003354 − 0.002792
                     = 0.000562 К⁻¹

AF(85°C) = exp[ (1.1 / 8.617 · 10⁻⁵) · 0.000562 ]
         = exp[ 12765.47 · 0.000562 ]
         = exp[ 7.174 ]
         ≈ 1305
```

Коефіцієнт прискорення старіння `AF ≈ 1305` означає, що при нагріві до +85 °C заряд у комірці Flash стікає в 1300 разів швидше, ніж при кімнатній температурі. Час гарантованого збереження даних падає з 20 років до кількох місяців. Тому для промислових вузлів регламент випробувань обов'язково включає стрес-тест високотемпературного зберігання (High-Temperature Data Retention Test).
