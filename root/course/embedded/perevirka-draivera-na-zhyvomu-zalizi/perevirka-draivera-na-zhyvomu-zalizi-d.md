Партія зі ста промислових логерів вібрації успішно проходить синтетичні тести в емуляторі та без жодної помилки транслює показники на налагоджувальний комп'ютер через інтерфейс SWD. Проте після встановлення плат на компресорну установку починається лавиноподібна відмова: при кожному запуску трифазного електродвигуна імпульсна завада в мережі викликає мікросекундне просідання шини 3.3 В; цифровий акселерометр зазнає короткочасного збою внутрішнього автомата і намертво затискає лінію даних SDA в низький рівень; мікроконтролер входить у нескінченний цикл очікування готовності апаратного блоку I2C, а лінія переривання готовності даних залишається заблокованою у високому стані. За три доби сорок пристроїв зі ста повністю припиняють збір телеметрії, вимагаючи примусового знеструмлення всієї системи.

Причина цієї катастрофи полягає в тому, що драйвер розроблявся виключно під «ідеальний шлях» (англ. *happy path*), коли напруга живлення є абсолютно стабільною, провідники шини ніколи не втрачають контакт, а підключений сенсор завжди миттєво відповідає на запити. На реальній друкованій платі драйвер стикається з фізичним світом: паразитними ємностями, дзвоном фронтів, перехідними процесами, втратою тактування, переповненням черг та витоками струму через вхідні каскади мікросхем. Єдиний спосіб гарантувати надійність пристрою — провести стрес-тестування (англ. *stress testing* — випробування під екстремальним навантаженням) та верифікацію з примусовим введенням апаратних несправностей (лат. *injicere* — впорскувати, вкидати; англ. *fault injection*).

## 1. Межі модульного тестування та потреба у фізичній верифікації

У класичній програмній інженерії домінує підхід модульного тестування (англ. *unit testing*), коли інтерфейс шини підміняється абстрактним програмним макетом (англ. *mock / stub*). Макети повертають наперед задані масиви байтів або заздалегідь підготовлені коди помилок. Такий підхід дозволяє перевірити математичну коректність перерахунку сирих шістнадцятибітних чисел у прискорення чи тиск, але він абсолютно безсилий перед фізичними явищами на друкованій платі.

### Що не здатні виявити симулятори та програмні макети

1. **Асинхронні перехідні процеси:** Короткочасний провал живлення тривалістю 5 мікросекунд здатний частково скинути внутрішню цифрову логіку сенсора, залишивши його аналоговий тракт увімкненим. Програмний макет ніколи не відтворить ситуацію, коли регістр конфігурації повернувся до заводського стану, а вихідні регістри даних продовжують видавати застигле ненульове значення.
2. **Апаратні блокування кремнієвих автоматів:** Внутрішні кінцеві автомати (англ. *Finite State Machine, FSM*) апаратних контролерів I2C або SPI у мікроконтролері мають власні апаратні прапорці зайнятості шини (наприклад, прапорець `BUSY` у контролерах STM32 або NXP). Якщо лінія зв'язку зазнає спотворення сигналу посеред транзакції, цей прапорець залишається виставленим в 1 на апаратному рівні. Будь-який подальший виклик стандартних бібліотечних функцій опитування повертає помилку зайнятості, навіть якщо зовнішня шина вже вільна.
3. **Паразитичні електричні зв'язки:** Захисні діоди від електростатичного розряду (англ. *Electrostatic Discharge, ESD*), вбудовані в кожен пін мікросхеми, здатні непомітно живити знеструмлений чіп через лінії зв'язку. Програмний симулятор покаже, що сенсор вимкнено, тоді як на фізичній платі він споживатиме півтора міліампера, спотворюючи рівні на спільній шині.

```
+---------------------+      +---------------------+      +---------------------+
|   Unit Testing      |  ->  |   HIL Simulation    |  ->  | Live Hardware Test  |
|  (Чиста логіка,     |      |  (Імітація логічних |      | (Фізичні глітчі,    |
|   макети шин)       |      |   рівнів та касет)  |      |  ESD, Brownout)     |
+---------------------+      +---------------------+      +---------------------+
  Перевіряє: формули           Перевіряє: протокол          Перевіряє: фізику плати
```

Фізична верифікація драйвера на живій платі вимагає створення спеціального тестового середовища, здатного автоматизовано порушувати цілісність ліній зв'язку, формувати контрольовані провали живлення, перевантажувати черги вибірок та вимірювати мікроамперні струми в динаміці.

## 2. Граничні стани комунікаційних шин: I2C та SPI

Комунікаційні шини між мікроконтролером та зовнішніми чипами є найбільш вразливими ділянками друкованої плати. Доріжки діють як антени, сприймаючи електромагнітні завади від імпульсних перетворювачів, двигунів та радіопередавачів. Випробування драйвера повинно довести, що жодне фізичне спотворення сигналу не здатне зациклити процесорне ядро або заблокувати роботу сусідніх пристроїв на тій самій шині.

### Фізичний розрив ліній під час активної транзакції

Найпростіший і водночас найбільш руйнівний тест — це розмикання сигнального провідника (SDA, SCL, MISO, MOSI або CS) за допомогою швидкодіючого аналогового ключа безпосередньо в момент передачі чергового байта даних.

```
Нормальна передача:
SCL:  __П_П_П_П_П_П_П_П_П_    (9 тактів: 8 біт + ACK)
SDA:  --[D7][D6]...[D0]-[ACK]

Обрив SCL під час передачі:
SCL:  __П_П_П_---------------- (Лінія зависла у High-Z / 1)
SDA:  --[D7][D6]============== (Ведений чекає тактування, тримаючи 0)
Результат без таймауту:        Процесор назавжди зависає у while(!RxNE)
```

Типова помилка початкових реалізацій драйверів полягає у використанні нескінченних блокувальних циклів очікування апаратних прапорців:

:::tabs
```c
/* Катастрофічна вразливість: зависання при апаратному розриві лінії */
driver_status_t i2c_poll_byte_naive(I2C_TypeDef *i2c, uint8_t *byte) {
    while (!(i2c->SR1 & I2C_SR1_RXNE)) {
        /* Якщо тактовий імпульс не дійшов до сенсора, процесор назавжди зависає тут */
    }
    *byte = (uint8_t)i2c->DR;
    return DRIVER_OK;
}

/* Захищена реалізація з апаратним таймаутом */
driver_status_t i2c_poll_byte_guarded(I2C_TypeDef *i2c, uint8_t *byte, uint32_t timeout_us) {
    uint32_t start_tick = get_microsecond_tick();
    while (!(i2c->SR1 & I2C_SR1_RXNE)) {
        if ((get_microsecond_tick() - start_tick) >= timeout_us) {
            return DRIVER_ERR_TIMEOUT;
        }
    }
    *byte = (uint8_t)i2c->DR;
    return DRIVER_OK;
}
```
```cpp
// Захищена реалізація опитування шини I2C на C++ з обмеженням за часом
#include <cstdint>
#include <chrono>
#include <expected>

enum class BusError { Timeout, HardwareFault };

template <typename Predicate>
[[nodiscard]] std::expected<void, BusError> waitForCondition(
    Predicate&& pred, 
    std::chrono::microseconds timeout) noexcept 
{
    const auto start = std::chrono::steady_clock::now();
    while (!pred()) {
        if (std::chrono::duration_cast<std::chrono::microseconds>(
                std::chrono::steady_clock::now() - start) >= timeout) {
            return std::unexpected(BusError::Timeout);
        }
    }
    return {};
}
```
:::

Будь-яке опитування апаратного прапорця зобов'язане мати жорсткий захисний інтервал (англ. *guard timeout*), розрахований на основі робочої частоти шини та максимального допустимого утримання тактування веденим пристроєм (англ. *clock stretching*):

```
t_byte = (9 біт) / f_scl
t_timeout = t_byte + t_clock_stretch_max + t_guard_margin
```

Для стандартної шини I2C на частоті 100 кГц час передачі одного байта становить 90 мікросекунд. Якщо максимальний час розтягування такту для конкретного датчика за даташитом становить 1 мілісекунду, таймаут драйвера повинен становити від 2 до 5 мілісекунд. Перевищення цього часу має негайно переривати транзакцію, скидати апаратний периферійний модуль та повертати статус помилки `DRIVER_ERR_TIMEOUT`.

### Апаратне зависання шини I2C (Bus Lockup) та процедура відновлення

Специфіка протоколу I2C базується на виходах типу «відкритий колектор / відкритий стік» (англ. *Open-Drain*) з підтягувальними резисторами до шини живлення. Це дозволяє реалізувати двонаправлений зв'язок по одній лінії даних SDA. Проте якщо мікроконтролер скинеться (наприклад, через спрацьовування сторожового таймера) або зазнає збою в той момент, коли сенсор передавав нульовий біт інформації, сенсор залишається чекати наступних тактів SCL, продовжуючи притягувати лінію SDA до землі (`SDA = 0`).

У цьому стані апаратний I2C-контролер мікроконтролера виявляє, що лінія SDA зайнята, і відмовляється генерувати початкову умову START. Шина повністю паралізується (англ. *bus lockup* — блокування шини), і жоден інший пристрій на цій лінії не може вийти на зв'язок.

![Алгоритм відновлення шини I2C](/root/course/embedded/perevirka-draivera-na-zhyvomu-zalizi/img/i2c-bus-recovery-sequence.svg)
*Послідовність відновлення шини I2C при зависанні веденого пристрою (Bus Lockup): тактування SCL через GPIO Open-Drain, формування умови STOP та повторна ініціалізація регістрів.*

Для ліквідації цього стану драйвер повинен містити вбудований алгоритм аварійного прочищення шини (англ. *I2C Bus Clear / Clocking Out*):

1. **Деініціалізація I2C:** Вимкнути апаратний периферійний модуль I2C у мікроконтролері, щоб звільнити керування фізичними пінами. У мікроконтролерах із відомими кремнієвими помилками апаратного блоку (наприклад, STM32F1/F4) необхідно додатково виконати апаратне скидання периферії через регістри скидання тактування шини (наприклад, біт `I2C1RST` у регістрі `RCC_APB1RSTR`).
2. **Переконфігурація в GPIO:** Перевести виводи SCL та SDA в режим GPIO Open-Drain з підтяжкою до живлення.
3. **Генерація дев'яти тактів:** Програмно згенерувати на лінії SCL до дев'яти імпульсів із частотою близько 100 кГц. Кожен фронт тактового сигналу змушує внутрішній зсувний регістр сенсора виштовхувати наступний біт. Найпізніше на дев'ятому такті сенсор дійде до біта ACK/NACK і відпустить лінію SDA у високий рівень (`SDA = 1`).
4. **Формування умови STOP:** Зафіксувати лінію SCL у високому рівні та перевести SDA з низького рівня у високий. Це формує стандартний апаратний кадр STOP, який примусово повертає автомат веденого чіпа в стан спокою.
5. **Реініціалізація I2C:** Повернути піни під керування апаратного блоку I2C та продовжити нормальну роботу.

```
Алгоритм розблокування лінії:
SCL (GPIO):  __П_П_П_П_П_П_П_П_П_   (Генерація тактів)
SDA (Slave): =====---------________  (Сенсор відпускає лінію)
                             ^
                             | SDA звільнено -> формування STOP
```

### Розсинхронізація кадрів та зсув бітів на шині SPI

На відміну від I2C, шина SPI (англ. *Serial Peripheral Interface*) використовує односпрямовані лінії з push-pull виходами та окрему лінію вибору кристала (англ. *Chip Select, CS* або *Slave Select, SS*). Основна апаратна вразливість SPI — випадання або поява зайвого тактового імпульсу на лінії SCK внаслідок електричного дзвону (англ. *ringing*) чи перехресної завади (англ. *crosstalk*).

Якщо лінія SCK отримала зайвий імпульс, зсувний регістр сенсора зсувається на 1 біт ліворуч (англ. *bit slip* — бітовий зсув). Усі наступні зчитані шістнадцятибітні значення виявляються помноженими на 2 або зміщеними, що призводить до отримання повністю спотворених фізичних показників.

```
Очікуваний потік SPI:
Байт 1: [B7 B6 B5 B4 B3 B2 B1 B0]
Байт 2: [D7 D6 D5 D4 D3 D2 D1 D0]

Зсув через заваду (+1 такт SCK):
Отримано: [B6 B5 B4 B3 B2 B1 B0 D7] -> Байт спотворено!
```

Надійна реалізація драйвера зобов'язана використовувати апаратну лінію CS як жорсткий синхронізатор кадру:
- Кожна транзакція повинна починатися зі спадного фронту CS (`CS: 1 → 0`) і завершуватися висхідним фронтом (`CS: 0 → 1`).
- Переведення лінії CS у високий рівень апаратно скидає внутрішній лічильник бітів веденого сенсора, гарантуючи, що наступний кадр почнеться строго зі старшого біта (MSB).
- Якщо драйвер підтримує пакети фіксованої довжини через DMA, обробник завершення передачі зобов'язаний перевіряти статусний регістр переповнення (прапорець `OVR / MODF`) та підтверджувати цілісність зчитаного масиву за контрольними сумами або відомими сигнатурами заголовків.

## 3. Аномалії живлення: короткочасний Brownout Glitch та скидання чіпа

Під час роботи реального пристрою напруга на шині живлення сенсорів рідко залишається ідеальною прямою лінією. Підключення потужного радіопередавача, спрацьовування електромагнітного реле, старт сервоприводу або імпульсна завада на клемах акумулятора викликають короткочасні провали напруги (англ. *brownout glitch* — часткове падіння напруги нижче гарантованого порогу функціонування).

```
Напруга VDD:
3.3 В ------------------+          +----------------- (Нормальна робота)
                        |  провал  |
1.5 В - - - - - - - - - \__________/ - - - - - - - - - (Поріг Brownout Reset)
                           15 мс
Стан чипа:          [ Працює ] [ Збій FSM ] [ Скинуто в дефолт ]
```

### Фізичний механізм збою при короткочасному знеструмленні

Сучасні цифрові сенсори мають вбудовані схеми скидання за зниження напруги (англ. *Power-On Reset, POR / Brownout Reset, BOR*). Проте ці схеми оптимізовані під плавні перехідні процеси при першому вмиканні. Коли напруга живлення падає з 3.3 В до 1.2–1.8 В на час від 500 мікросекунд до 20 мілісекунд і потім миттєво повертається до 3.3 В, виникає небезпечний стан:

1. **Внутрішній автомат FSM частково втрачає стан:** Компаратор POR не встигає повністю розрядити внутрішній тригер скидання, оскільки блокувальні конденсатори на виводах сенсора утримують залишковий потенціал.
2. **Втрата конфігурації регістрів:** Регістри конфігурації (діапазон вимірювання, частота оновлення ODR, фільтри низьких частот) скидаються до заводських значень за замовчуванням (англ. *power-on default*), які зазвичай відповідають режиму глибокого сну (Power-Down) або мінімальній швидкості.
3. **Мовчання на шині:** Драйвер у мікроконтролері продовжує вважати, що сенсор налаштований на опитування через переривання з частотою 800 Гц. Проте сенсор перейшов у режим сну, лінія переривання мовчить, а виклики функцій читання повертають нульові або некоректні дані.

### Алгоритм динамічного відновлення без перезавантаження мікроконтролера

Надійно спроєктований драйвер не повинен вимагати повного перезапуску всієї плати при збої одного периферійного вузла. Алгоритм відновлення реалізується через трирівневу систему контролю:

```
[ Потік вибірок ] -> [ Перевірка Device ID та таймауту ]
                             |
                   Помилка / Невірний ID?
                             |
                            TAK
                             v
             [ Програмне скидання: Soft Reset ]
                             v
             [ Затримка стабілізації: t_startup ]
                             v
             [ Повторне завантаження регістрової карти ]
                             v
             [ Відновлення конвеєра даних ]
```

1. **Періодична верифікація ідентифікатора (Heartbeat Check):** Якщо драйвер фіксує таймаут отримання переривання або виявляє застиглі вибірки (наприклад, три послідовні зчитування повертають строго нульові вектори прискорення), він виконує читання регістру ідентифікатора чіпа (наприклад, `WHO_AM_I`, `CHIP_ID`, `DEVID`).
2. **Програмне скидання чіпа (Soft Reset):** Якщо ідентифікатор читається некоректно або чіп не реагує на команди зміни режимів, драйвер надсилає команду програмного перезапуску через спеціальний біт скидання (наприклад, `SW_RESET = 1` у регістрі керування живленням).
3. **Пауза на завантаження кремнієвого завантажувача (Boot Time):** Після подачі команди скидання сенсор потребує фіксованого часу (від 1 до 50 мілісекунд залежно від моделі) для зчитування внутрішніх калібрувальних коефіцієнтів із вбудованої пам'яті OTP/ROM. Спроба звернутися до чіпа раніше цього інтервалу призведе до помилки NACK.
4. **Повна реконфігурація регістрової карти:** Драйвер повторно записує повний набір конфігураційних параметрів: дільники частоти, пороги FIFO, налаштування фільтрів та полярність переривань, після чого очищує буфери і продовжує штатне функціонування.

## 4. Переповнення FIFO та залипання лінії переривання (INT/DRDY)

Високопродуктивні сенсори (акселерометри, гіроскопи, комбіновані IMU, прецизійні аудіо-АЦП) генерують дані з високою частотою — від сотень герц до десятків кілогерц. Щоб розвантажити процесорне ядро від необхідності опитувати шину на кожен відлік, у кремній сенсора інтегрують апаратний буфер FIFO (англ. *First-In, First-Out* — перший зайшов, перший вийшов) ємністю від 32 до 512 байтів.

Сенсор накопичує вибірки і виставляє логічний рівень на спеціальному виводі переривання (INT або DRDY — Data Ready), повідомляючи мікроконтролер про досягнення заданого рівня заповнення буфера (англ. *Watermark*).

![Матриця граничних випробувань драйвера](/root/course/embedded/perevirka-draivera-na-zhyvomu-zalizi/img/fault-injection-matrix.svg)
*Матриця стрес-тестування драйвера: класифікація апаратних впливів, фізичний механізм збою та критерії успішного відновлення без перезапуску системи.*

### Механізм залипання переривання при перевантаженні системи

У реальній операційній системі реального часу (RTOS) або складній системі обробки подій процесор може тимчасово заблокувати переривання (наприклад, під час запису сторінки у Flash-пам'ять або виконання критичної криптографічної операції). Якщо затримка обслуговування переривання перевищує час заповнення апаратного FIFO, виникає стан переповнення (англ. *FIFO Overrun / Overflow*).

```
Часова діаграма переповнення:
Вибірки в чіпі:  |||||||||||||||||||||||||||||||||||||||| (Генерація 1 кГц)
FIFO заповнення: [ 10% ][ 50% ][ 90% ][ 100% OVERRUN! ]
Лінія INT:       ________/----------------------------- (Залипла у HIGH)
Обробник МК:     [ Заблокований записом Flash ] -> [ Старт читання ]
```

При переповненні FIFO виникає низка критичних проблем:
1. **Зависання лінії переривання в активному стані:** Лінія INT залишається намертво притягнутою до високого рівня (або до низького, залежно від конфігурації). Якщо контролер переривань мікроконтролера (наприклад, EXTI в STM32) налаштований на спрацьовування за фронтом (англ. *Edge Triggered*), повторний фронт більше ніколи не з'явиться, і драйвер назавжди перестане отримувати нові дані.
2. **Зсув фази багатоосьових вибірок:** При переповненні старі дані можуть або відкидатися, або перезаписуватися новими. Якщо драйвер почне вичитувати буфер без попереднього скидання, він зчитає частину застарілих байтів осі X у парі з новими байтами осі Y, що створить катастрофічну помилку в алгоритмах просторової орієнтації (наприклад, у фільтрі Калмана).
3. **Різниця в механізмах скидання прапорців (Clear on Read vs Write-1-to-Clear):** Різні виробники чіпів використовують різні способи деактивації переривання:
   - *Clear on Read:* прапорець скидається автоматично при читанні регістру статусу або даних.
   - *Write-1-to-Clear (W1TC):* для скидання переривання драйвер зобов'язаний явно записати одиницю у відповідний бітовий розряд регістру статусу. Якщо драйвер спробує записати туди 0, прапорець не скинеться, і лінія INT залишиться заблокованою.

### Методика верифікації обробника переповнення

Для стрес-тестування драйвера на стенді реалізується сценарій примусового переповнення черги:

## 5. Енергетичний аудит та вимірювання струмів у режимах сну

Для автономних пристроїв, що живляться від дискових літієвих батарей або акумуляторів, здатність драйвера коректно переводити сенсори в режим глибокого сну (англ. *Deep Sleep / Standby / Power-Down*) є критичним показником якості. Якщо за даташитом струм сну мікросхеми становить 0.8 мкА, а на зібраній платі прилад споживає 450 мкА, батарея ємністю 220 мА·год сяде за три тижні замість розрахованих п'яти років.

### Паразитичне фантомне живлення через виводи GPIO

Найбільш підступний дефект, який регулярно виникає на етапі написання драйверів власного заліза, — це фантомне живлення (грец. *phantasma* — привид, уявний образ; англ. *phantom / parasitic powering*).

Для економії енергії апаратні розробники часто ставлять силовий P-канальний MOSFET-ключ, який повністю відключає шину живлення VDD сенсора під час глибокого сну. Проте якщо програміст драйвера просто розімкнув ключ живлення і не змінив стан цифрових виводів мікроконтролера, виникає паразитний струмовий контур.

![Паразитичне живлення через захисні ESD-діоди](/root/course/embedded/perevirka-draivera-na-zhyvomu-zalizi/img/parasitic-powering-gpio.svg)
*Паразитичне фантомне живлення: витік струму з виходів мікроконтролера через внутрішні захисні ESD-діоди знеструмленого сенсора, що блокує перехід у глибокий сон.*

Фізичний механізм витоку:
1. Виводи мікроконтролера (SCL, SDA, CS, MOSI) залишаються сконфігурованими як цифрові виходи з високим логічним рівнем 3.3 В або підтягнутими через зовнішні резистори 4.7 кОм до невимкненої шини 3.3 В.
2. Кожен пін зовнішнього сенсора містить верхній захисний діод ESD, катод якого з'єднаний із внутрішньою шиною живлення кристала VDD_INT.
3. Струм від піна мікроконтролера тече через відкритий ESD-діод прямо у внутрішню шину живлення сенсора:

```
U_sens_int = U_gpio - V_diode_drop = 3.3 В - 0.6 В = 2.7 В
```

4. Знеструмлений сенсор отримує напругу 2.7 В в обхід розімкненого силового ключа. Цього потенціалу недостатньо для повноцінної роботи, але цілком достатньо, щоб утримувати цифрову логіку в напівскинутому стані. Струм витоку становить від 300 мкА до 2 мА, безперервно спалюючи енергію батареї.

### Правило безпечної конфігурації пінів у стані сну

Перед переведенням пристрою в стан сну або розмиканням ключа живлення сенсора драйвер зобов'язаний виконати повну ізоляцію інтерфейсу:

```
Кроки ізоляції інтерфейсу перед сном:
1. Надіслати команду переходу в Sleep за протоколом (якщо VDD не знімається).
2. Перевести всі піни зв'язку (SCL, SDA, MOSI, MISO, CS) у стан Analog Mode (High-Z без підтяжок).
3. Програмно вимкнути внутрішні підтягувальні резистори (No Pull-up / No Pull-down).
4. Зняти напругу з ключа живлення VDD_SENS (якщо використовується комутація).
```

:::tabs
```c
/* Коректне переведення шини SPI в енергозберігаючий режим на C (STM32 HAL) */
void sensor_enter_low_power_gpio_c(void) {
    GPIO_InitTypeDef gpio_init = {0};
    
    /* Деініціалізація апаратного блоку SPI */
    HAL_SPI_DeInit(&hspi1);
    
    /* Переведення сигнальних ліній у режим Analog Input для усунення витоків */
    gpio_init.Pin = GPIO_PIN_5 | GPIO_PIN_6 | GPIO_PIN_7; /* SCK, MISO, MOSI */
    gpio_init.Mode = GPIO_MODE_ANALOG;
    gpio_init.Pull = GPIO_NOPULL;
    HAL_GPIO_Init(GPIOA, &gpio_init);
    
    /* Лінію CS притягуємо до 0 або також переводимо в Analog */
    gpio_init.Pin = GPIO_PIN_4;
    HAL_GPIO_Init(GPIOA, &gpio_init);
}
```

```cpp
// Коректне переведення інтерфейсу в енергозберігаючий стан на C++ з RAII-вартою
class LowPowerPinGuard {
public:
    LowPowerPinGuard() noexcept {
        isolatePins();
    }
    ~LowPowerPinGuard() noexcept {
        restorePins();
    }
    LowPowerPinGuard(const LowPowerPinGuard&) = delete;
    LowPowerPinGuard& operator=(const LowPowerPinGuard&) = delete;

private:
    void isolatePins() noexcept {
        // Переведення ліній SCK, MISO, MOSI, CS у режим Analog High-Z
        setPinModeAnalog(Pin::SCK | Pin::MISO | Pin::MOSI | Pin::CS);
    }
    void restorePins() noexcept {
        // Відновлення апаратних функцій SPI
        setPinModeAlternate(Pin::SCK | Pin::MISO | Pin::MOSI | Pin::CS);
    }
};
```

### Замір часу встановлення сигналу (Settling Time)

Після пробудження сенсора з режиму сну драйвер не може миттєво зчитувати фізичні величини. Аналогова частина сенсора (підсилювачі заряду, генератори опорної напруги bandgap, ємнісні мости MEMS-структур) потребує часу для встановлення робочого режиму (англ. *settling time* — час перехідного процесу).

```
Подача живлення / Wakeup:
VDD / Sleep bit:  ______/----------------------------- (Старт пробудження)
Аналоговий тракт: ~~~~~~\________/\____/-------------- (Перехідний процес)
                                       |
                                       v  t_settling (10–50 мс)
Готовність даних: _____________________/-------------- (Валідні вибірки)
```

Якщо драйвер вичитає дані через 1 мілісекунду після пробудження, він отримає нульові значення або значення з максимальною похибкою зміщення нуля (англ. *Zero-g offset / Bias drift*). Верифікація драйвера вимагає обов'язкової перевірки затримки встановлення сигналу: зчитування серії відліків після пробудження та зіставлення їх зі стаціонарним шумом датчика для підтвердження того, що перша отримана вибірка вже є метрологічно достовірною.

## 6. Побудова автоматизованого стенда випробувань

Фінальним етапом розробки драйвера є його інтеграція у виробничий або верифікаційний випробувальний стенд. Ручне перемикання проводів і випадкове вимикання живлення дозволяють зловити грубі помилки, проте вони не забезпечують повторюваності результатів (англ. *reproducibility*).

Автоматизований стенд складається з трьох основних вузлів:
1. **Програмований комутатор несправностей (Fault Injection Board):** плата на базі мультиплексорів (наприклад, ADG714 або 74HC4066) та швидкодіючих N/P-MOSFET ключів, які за командами керуючого мікроконтролера вставляють розриви ліній тривалістю від 100 наносекунд або замикають провідники на землю.
2. **Прецизійний вимірювач профілю струму:** інструменти класу Nordic Power Profiler Kit II (PPK2), Qoitech Otii Arc або лабораторні джерела-вимірювачі (SMU, наприклад Keithley 2450), синхронізовані з логічним аналізатором. Вони фіксують точний профіль споживання з частотою дискретизації до 100 кГц, дозволяючи бачити як субмікроамперні витоки в режимі сну, так і мілісекундні сплески прийому-передачі.
3. **Програмний тестовий раннер:** спеціальна збірка прошивки, яка послідовно запускає матрицю стрес-тестів, збирає статистику збоїв та передає структурований звіт через налагоджувальний інтерфейс UART/RTT.

Повний вихідний код стендового модуля ін'єкції несправностей, механізмів розблокування шин та тестового раннера представлено у практичному проекті з [набором стрес-тестів та тест-раннером верифікації драйвера](root:embedded/perevirka-draivera-na-zhyvomu-zalizi/proj-driver-stress-suite.md).

## Підсумкова інженерна таблиця верифікації драйвера

Перед передачею написаного драйвера до складу основної прошивки виробу інженер зобов'язаний заповнити протокол верифікації за наступною формою:

| Перевірка | Фізичний вплив | Очікувана реакція драйвера | Критерій браку |
|---|---|---|---|
| **Обрив шини I2C/SPI** | Розмикання SDA/SCL або MISO на 100 мс | Повернення `ERR_TIMEOUT` за час ≤ 5 мс; збереження працездатності ядра | Зависання в циклі `while()`, сторожовий таймер перезавантажує МК |
| **Зависання SDA=0** | Примусове замикання SDA на GND | Генерація 9 тактів SCL, формування STOP, відновлення зв'язку після зняття КЗ | Відмова апаратного блоку I2C генерувати START після звільнення лінії |
| **Brownout глітч** | Зняття VDD сенсора на 10–20 мс | Виявлення невідповідності Device ID, Soft Reset, повне відновлення конфігурації | Драйвер видає нулі/застиглі дані, вважаючи, що сенсор налаштований |
| **Переповнення FIFO** | Блокування переривань на 500 мс | Фіксація прапорця OVERRUN, вичитування буфера, скидання лінії INT до 0 | Лінія INT залишається затиснутою в 1, нові переривання не надходять |
| **Аудит сну (Deep Sleep)** | Переведення сенсора в Standby | Споживання вузла ≤ 1.5 мкА; піни МК у режимі Analog (High-Z) | Струм витоку > 10 мкА через діоди ESD залишених у HIGH виводів |
| **Час готовності** | Запуск після сну (Wakeup) | Перша зчитана вибірка валідна та відповідає паспортній похибці шуму | Зчитування нулів або викидів через ігнорування `t_settling` аналогового тракту |

Лише після проходження всіх шести пунктів матриці верифікації драйвер вважається придатним для експлуатації в реальних умовах промислового та комерційного обладнання.
