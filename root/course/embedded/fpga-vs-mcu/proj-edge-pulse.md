# ⚙️ Чотири канали детектора фронту: МК проти FPGA

> Та сама задача — зловити наростальний фронт на кількох незалежних входах і видати по одному імпульсу на виходах — на мікроконтролері й на FPGA, від коду до пасток. Це найкоротший спосіб **відчути** різницю між послідовним ядром і паралельним залізом: не на словах «FPGA швидша», а на тому, що саме в коді міняється, коли каналів стає багато, а вимоги до затримки — жорсткими.

## Задача

На **N незалежних входах** (візьмемо N = 4) ловимо **наростальний фронт** — перехід рівня з 0 в 1 — і на відповідних N виходах видаємо рівно **один короткий імпульс** на кожен спійманий фронт. Вимоги, що й роблять задачу показовою:

- **канали незалежні** — фронт на одному не повинен затримувати чи спотворювати реакцію на іншому;
- **реакція швидка й передбачувана** — затримка «вхід → вихід» мала й по змозі **однакова** від разу до разу (детермінована);
- **одночасність** — якщо два-три входи смикнулися майже водночас, усі вони мусять відреагувати, а не стати в чергу.

Саме поєднання «багато каналів + жорсткий таймінг» розводить два інструменти по різні боки. Поки канал один і реакція потрібна неспішна — різниці майже немає. Щойно каналів багато й кожна наносекунда на рахунку — вони поводяться принципово по-різному.

## Ідея

Детектор фронту сам по собі тривіальний: фронт є там, де **зараз 1, а попереднього разу був 0**. У бітовій формі для цілого порту це один вираз `rise = now & ~prev`: біт виставлений там, де відбувся перехід 0 → 1. Уся сіль не в цьому виразі, а в тому, **хто і як його виконує**.

На мікроконтролері процесор один. Хоч би скільки було каналів, він обробляє їх **одним потоком інструкцій**: прочитав порт, порівняв із попереднім, а далі — перебрав канали по черзі, видаючи імпульси. «Одночасності» тут немає навіть теоретично: є дуже швидке чергування. Поки ядро заходить в обробник переривання (зберегти контекст, стрибнути за вектором — десятки-сотні тактів), фронт уже фізично минув; реакція прив'язана до тактів ядра й «плаває» залежно від того, чим воно було зайняте.

На FPGA немає «процесора, що виконує `rise = now & ~prev`». Є **фізична схема**, у якій цей вираз — просто вентилі й тригери, прокладені в кремнії. Опис каналу копіюється N разів, і всі N копій — це **різні ділянки кристала**, що працюють **буквально водночас**. Затримка від фронту до виходу — прохід крізь кілька вентилів і один такт синхронізації, тобто наносекунди, і вона **не залежить** від того, скільки каналів спрацювало: серіалізувати нема чого, бо немає спільного ядра, через яке все протискається.

> 🔧 **Навіщо це.** Це різниця між «швидше крутити чергу» і «прибрати чергу». На МК кожен зайвий канал додає тактів до найгіршої затримки; на FPGA десятий канал реагує так само швидко, як перший. Тому в захисті, синхронному керуванні моторами й обробці швидких давачів, де відмова «спізнитися» неприпустима, беруть саме залізо.

## Мікроконтролер: одне ядро, канали по черзі

Найчесніший спосіб — переривання на зміну входів, щоб не марнувати такти на безперервне опитування. Уся поведінка — у короткому обробнику:

```c
#include <stdint.h>

#define NCH 4
volatile uint8_t prev;                  /* попередній стан входів IN0..IN3 */

/* read_inputs(): біти 0..3 = рівні IN0..IN3; pulse_out(ch): імпульс на OUTch */
extern uint8_t read_inputs(void);
extern void    pulse_out(int ch);

void EXTI_IRQHandler(void) {             /* викликається на зміну будь-якого входу */
    uint8_t now  = read_inputs();
    uint8_t rise = now & ~prev;          /* де 0 -> 1: наростальні фронти */
    prev = now;

    for (int ch = 0; ch < NCH; ch++)     /* канали обробляються ПО ЧЕРЗІ */
        if (rise & (1u << ch))
            pulse_out(ch);
}
```

Вузьке місце видно прямо в коді: цикл `for` перебирає канали **послідовно**. Якщо `pulse_out` не миттєвий (а смикнути пін, можливо, через драйвер — це такти), то четвертий канал чекає, доки відпрацюють перші три. Додайте сюди затримку входу в переривання — і найгірша затримка стає сумою «вхід у обробник + позиція каналу в черзі». Для кнопок, енкодерів, повільних давачів це абсолютно нормально й навіть надмірно точно. Для фронтів, що йдуть раз на сотні наносекунд, — запізно.

### Пастки на МК

- **Брязкіт і шум.** Механічний контакт дає не один фронт, а пачку; швидкий аналоговий сигнал на порозі — теж. `now & ~prev` чесно зловить **кожен** дрижик. Для кнопки потрібен антибрязкот (часовий або підрахунком стабільних відліків), для шумного сигналу — гістерезис на вході.
- **Втрачені фронти між читаннями.** Якщо два переходи відбулися швидше, ніж ядро встигло обробити перший, проміжний стан можна не побачити: ви читаєте **рівень**, а не лічите **події**. Де це критично — потрібен апаратний лічильник чи захоплення таймером.
- **`prev` як `volatile` і атомарність.** `prev` ділять переривання й, можливо, головний цикл; без `volatile` компілятор може закешувати його в регістрі. А читання порту й оновлення `prev` мусять бути узгоджені, інакше частина фронтів «розмажеться» між викликами.
- **Джитер від інших переривань.** Поки виконується вищопріоритетний обробник, ваш чекає. Саме звідси береться «плавання» затримки, якого на МК принципово не уникнути.

## FPGA: N однакових каналів, усі водночас

Той самий детектор, але як **схема**. Параметр `N` задає число каналів; опис застосовується до всіх розрядів **паралельно**:

```verilog
// Детектор наростального фронту на кожен канал.
// N копій логіки = N ділянок кремнію, що працюють одночасно.
module edge_pulse #(parameter N = 4) (
    input  wire         clk,
    input  wire [N-1:0] din,            // IN0..IN3 (вже синхронізовані, див. нижче)
    output reg  [N-1:0] pulse           // OUT0..OUT3: імпульс на 1 такт
);
    reg [N-1:0] prev;
    always @(posedge clk) begin
        pulse <= din & ~prev;           // усі N розрядів рахуються ПАРАЛЕЛЬНО
        prev  <= din;
    end
endmodule
```

Те, що на МК було циклом `for (ch...)`, тут зникло: `din & ~prev` над вектором `[N-1:0]` — це N незалежних логічних схем, а не перебір. Збільште `N` до 32 — затримка кожного каналу не зміниться; зросте лише кількість зайнятих вентилів. Імпульс тут триває рівно один такт; якщо потрібен довший або рівно заданої довжини — додають невеликий лічильник на канал (знову ж таки, **по копії на канал**, усі паралельно).

### Пастки на FPGA

- **Метастабільність на асинхронному вході.** Зовнішній сигнал не прив'язаний до `clk`; якщо він зміниться в момент фіксації тригера, той може на такт зависнути в невизначеному стані. Будь-який вхід **зобов'язаний** пройти синхронізатор — два-три послідовні тригери на `clk` — **перш ніж** потрапити в `din`. Це не опція, а умова коректності.
- **Брязкіт нікуди не дівся.** Залізо так само зловить кожен дрижик механічного контакту — лише ще швидше. Антибрязкот реалізують лічильником стабільності на `clk`, по копії на канал.
- **Метастабільність ≠ детермінізм.** Сама схема детермінована **відносно свого такту**; невизначеність переноситься на межу «асинхронний світ → синхронний домен», і саме там її гасить синхронізатор. Плутати ці дві речі — типова помилка новачка.
- **Ширина імпульсу й тактова частота.** «Один такт» — це різний фізичний час за різної `clk`. Якщо приймач очікує імпульс певної тривалості, його задають **явно** лічильником, а не покладаються на період такту.

## Що з цього випливає

Код обох рішень крихітний, але різниця структурна, а не косметична. На МК масштаб по каналах і жорсткість таймінгу впираються в **одне ядро** — додатковий канал коштує тактів, а затримка завжди трохи «плаває». На FPGA канали — це **окреме залізо**, тож вони незалежні й однаково швидкі за побудовою, ціною складнішого входу (синхронізація, [потік синтезу](root:embedded/fpga-flow), [мислення схемами](topic:hw-digital/hdl)). Звідси й практичне правило: поки каналів мало й мікросекунд досить — МК простіший і дешевший; щойно потрібні **наносекунди й справжня одночасність** — задача природно лягає на [програмовну логіку](topic:hw-digital/programmable-logic).
