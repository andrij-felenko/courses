# ⚙️ Прошивкова частина аудиту струму спокою

Полювання діленням навпіл і перелік шляхів витоку дали нам *теорію* аудиту. Та коли доходить до плати, виявляється, що половина роботи — це не паяльник і не прилад, а **прошивка**: саме вона заводить пристрій у відтворюваний сон, саме вона лишає (або не лишає) ніжку в небезпечному стані, і саме вона може зробити ділення навпіл за тебе, гасячи гілки по черзі й рапортуючи струм. Тут — робочий код для ESP32 на ESP-IDF, який закриває всі чотири задачі: безпечно приспати, заморозити стан, самотужки поділити плату навпіл і записати базове число, нижче якого більше не падаємо.

Код реальний — це уривки прошивки, які компілюються під ESP-IDF, а не псевдокод «для ілюстрації». Де є типова пастка, я зупиняюся й показую, як саме вона стріляє.

## Задача: чому «просто заснути» недостатньо

Здавалося б, увесь сон ESP32 — це один виклик:

```c
esp_deep_sleep_start();   // і все?
```

І ось тут плата підносить сюрприз. Ми бачили в статті-власниці головний механізм витоку — [зворотне живлення крізь сигнальну ніжку](root:embedded/sleep-current-audit): чип іде в сон, але один його вихід лишився у HIGH і дивиться у вузол, якому ти щойно зняв живлення; струм тече з ніжки крізь внутрішній захисний діод того вузла прямо в мертву шину. Виклик `esp_deep_sleep_start()` про це нічого не знає. Він зупинить процесор — але **стан ніжок лишить таким, яким ти його покинув**. Якщо хоч одна лишилася HIGH над знеструмленим давачем, ти заснув із відкритим краном.

Більше того: на ESP32 цифрові ніжки під час самого глибокого сну поводяться не так, як можна очікувати. Навіть якщо ти акуратно звів усе в LOW і викликав звичайний `gpio_hold_en()` для кожної, **цифрова ніжка все одно скине стан** на час deep-sleep і повернеться до неї лише на пробудженні. Це не баг, а задокументована поведінка: у керівництві ESP-IDF прямо сказано, що для ESP32 функція `gpio_hold_en()` *«не може утримати стан цифрового GPIO під час Deep-sleep; навіть якщо її ввімкнено, цифровий GPIO скинеться до стану за замовчуванням при пробудженні»*. Тобто наївний код, який «все звів у LOW і заморозив», на ESP32 під час сну краном так само цідить.

Тому прошивкова частина аудиту — це не один рядок, а маленька дисципліна з чотирьох кроків:

```
1. Звести ВСІ ніжки в безпечний рівень    (один прохід, нічого не забути)
2. Засинати в ПРАВИЛЬНОМУ порядку         (сигнали → потім VDD вузла)
3. Заморозити рівні на час deep-sleep      (hold + deep_sleep_hold + isolate)
4. Перевірити себе self-test-ом і          (автоматичне ділення навпіл
   записати baseline                         + захист від регресій)
```

Розберімо кожен крок із кодом.

> 🔧 **Навіщо це.** Один HIGH-пін у знеструмлений вузол з'їдає весь виграш від глибокого сну — пристрій, що мав жити рік, сяде за тижні. Знайти його приладом можна, але дорого (півгодини ділення навпіл щоразу). Дешевше — щоб прошивка *за конструкцією* не лишала такого піна й сама ловила регресію числом. Цей код — і є та конструкція.

## Крок 1: один прохід зводить усі ніжки в безпечний рівень

Перша спокуса — гасити ніжки точково, по одній, там, де згадав: «о, тут давач, треба DATA в LOW». Це й є джерело помилок: рано чи пізно якусь ніжку забудеш, і саме вона лишиться HIGH над мертвим вузлом. Надійніше — **один прохід по всіх ніжках**, що зводить кожну в наперед визначений безпечний стан. Забути неможливо: цикл проходить геть усе.

Що таке «безпечний стан»? Залежить від ніжки, і тут є рівно дві правильні відповіді:

- **LOW (вихід, що тримає 0 В)** — коли ніжка дивиться у вузол, якому ми зніматимемо живлення. Нуль вольт на ніжці означає нуль різниці потенціалів на захисному діоді вузла — діод замкнений, струму немає. Це наш головний інструмент проти зворотного живлення.
- **Hi-Z (вхід без підтяжок, високий опір)** — коли ніжка нікуди не «штовхає» струм і ми не хочемо, щоб вона сама щось тягла. Вхід без внутрішньої підтяжки — це майже розрив: крізь нього майже нічого не тече.

Помилка новачка — лишити ніжку «як є» (часто це вхід із увімкненою внутрішньою підтяжкою) або, ще гірше, вихід у HIGH «бо так було в робочому режимі». Обидва стани течуть.

Опишемо безпечний профіль сну **таблицею**, а не розкиданими по коду викликами. Таблиця — це список ніжок із бажаним станом кожної; один цикл її застосовує. Так додавання нової ніжки на платі — це один рядок, а не полювання по всьому коду, де її «теж треба не забути».

```c
#include "driver/gpio.h"
#include "driver/rtc_io.h"
#include "esp_sleep.h"

// Безпечний стан ніжки уві сні.
typedef enum {
    SLEEP_LOW,   // вихід, що тримає 0 В (дивиться у вузол, якому знімемо VDD)
    SLEEP_HIZ,   // вхід без підтяжок, високий опір (нічого не тягне)
} sleep_state_t;

typedef struct {
    gpio_num_t    pin;
    sleep_state_t state;
    const char   *name;   // для зрозумілих логів
} sleep_pin_t;

// Єдине джерело правди: який стан безпечний для кожної ніжки уві сні.
// Додав ніжку на платі — додав сюди рядок, і прохід її не забуде.
static const sleep_pin_t SLEEP_PROFILE[] = {
    { SENSOR_DATA_PIN, SLEEP_LOW, "sensor_data" },   // дивиться у давач → 0 В
    { SENSOR_CLK_PIN,  SLEEP_LOW, "sensor_clk"  },
    { DISPLAY_DC_PIN,  SLEEP_LOW, "display_dc"  },
    { RADIO_CS_PIN,    SLEEP_LOW, "radio_cs"    },
    { SPARE_GPIO_PIN,  SLEEP_HIZ, "spare"       },   // нікуди не штовхає → Hi-Z
};
#define SLEEP_PROFILE_LEN (sizeof(SLEEP_PROFILE) / sizeof(SLEEP_PROFILE[0]))
```

Тепер один прохід застосовує профіль. Для LOW ми робимо ніжку виходом і виставляємо 0; для Hi-Z — входом і **знімаємо обидві внутрішні підтяжки** (інакше «вхід» все одно тягтиме струм крізь підтяжку):

```c
static void apply_sleep_profile(void)
{
    for (size_t i = 0; i < SLEEP_PROFILE_LEN; i++) {
        const sleep_pin_t *s = &SLEEP_PROFILE[i];

        if (s->state == SLEEP_LOW) {
            gpio_set_direction(s->pin, GPIO_MODE_OUTPUT);
            gpio_set_level(s->pin, 0);                 // 0 В: діод вузла замкнений
        } else { // SLEEP_HIZ
            gpio_set_direction(s->pin, GPIO_MODE_INPUT);
            gpio_set_pull_mode(s->pin, GPIO_FLOATING); // зняти обидві підтяжки
        }
    }
}
```

Один виклик `apply_sleep_profile()` — і **жодна** ніжка з таблиці не лишилася в небезпечному стані. Це той самий «один прохід», про який каже стаття: не точкові правки, а суцільний обхід, який нічого не пропускає.

> 🔧 **Навіщо це.** Точкові `gpio_set_level(X, 0)`, розкидані по коду, — це борг, який віддаси витоком. Таблиця + прохід коштують двадцять рядків раз, але прибирають цілий клас помилок «забув ніжку»: рев'ю плати тепер зводиться до питання «чи всі ніжки в таблиці?», а не «чи всюди в коді я її загасив?».

### Пастка: Hi-Z не означає «нуль струму», якщо лишилася підтяжка

Найтонша помилка цього кроку — вважати, що `GPIO_MODE_INPUT` сам собою безпечний. Вхід **із увімкненою внутрішньою підтяжкою** — це резистор (на ESP32 — близько 45 кОм) від ніжки до шини. Якщо підтяжка вгору, а зовнішнє коло тримає ніжку в LOW, крізь неї постійно тече:

```
I = 3.3 В / 45 кОм ≈ 73 мкА
```

Сімдесят три мікроампери з однієї забутої підтяжки — це втричі більше за весь бюджет із прикладу в статті (25 мкА). Тому для Hi-Z ми **явно** ставимо `GPIO_FLOATING`: знімаємо обидві підтяжки, лишаючи справжній високий опір. «Вхід» і «високий опір» — не синоніми, поки не прибрав підтяжки.

## Крок 2: правильний порядок засинання — спершу сигнали, потім VDD вузла

Звести ніжки в LOW — півділа. Друга половина — **коли** це зробити відносно зняття живлення вузла. Порядок тут не косметичний; помінявши два рядки місцями, ти на коротку мить відкриваєш той самий кран, який намагався закрити.

Уяви неправильний порядок: спершу зняли давачу VDD, потім почали зводити сигнали в LOW. У проміжку між цими діями давач уже мертвий (VDD = 0), а сигнальна ніжка ще тримає 3.3 В — рівно та сама конфігурація зворотного живлення, від якої ми лікуємось. Навіть якщо проміжок короткий, він є, і на ньому крізь діод тече струм. А якщо між зняттям VDD і зведенням сигналів устигне статися помилка чи довге очікування — кран відкритий надовго.

Правильний порядок випливає прямо з механізму діода: **різниці потенціалів не повинно бути в жоден момент**. Отже, спершу прибираємо потенціал із сигналів (зводимо в LOW), і **тільки потім** знімаємо живлення вузла:

```c
// ПРАВИЛЬНО: спершу зняти сигнали, потім гасити живлення вузла
static void sensor_power_down(void)
{
    // 1) Знімаємо потенціал із усіх ліній, що дивляться в давач.
    gpio_set_level(SENSOR_DATA_PIN, 0);
    gpio_set_level(SENSOR_CLK_PIN,  0);
    gpio_set_level(SENSOR_CS_PIN,   0);

    // 2) Лише тепер гасимо VDD вузла через його load switch.
    //    На момент зняття живлення на жодній ніжці немає 3.3 В →
    //    діод давача замкнений → зворотного струму немає.
    gpio_set_level(SENSOR_LOADSW_EN, 0);
}
```

І дзеркально на пробудженні — порядок **зворотний**: спершу подаємо живлення вузлу, даємо йому стабілізуватися, і **лише потім** піднімаємо сигнали. Бо якщо підняти CS у HIGH, поки VDD вузла ще наростає (скажімо, 1.5 В), ми знову маємо різницю потенціалів не в той бік — і знову струм крізь діод, тепер уже на ввімкненні:

```c
static void sensor_power_up(void)
{
    gpio_set_level(SENSOR_LOADSW_EN, 1);   // 1) подати VDD вузлу
    vTaskDelay(pdMS_TO_TICKS(2));          // 2) дати живленню стабілізуватися
    gpio_set_direction(SENSOR_DATA_PIN, GPIO_MODE_OUTPUT);
    gpio_set_level(SENSOR_CS_PIN, 1);      // 3) лише тепер піднімати сигнали
}
```

Правило, яке варто закарбувати: **сигнали йдуть за живленням, а не попереду нього**. Гасимо — сигнали раніше за VDD; вмикаємо — VDD раніше за сигнали. У будь-який момент перехідного процесу не повинно бути ніжки під напругою над вузлом, чия шина нижча. Це і є та «черга засинання», на яку посилається стаття.

> 🔧 **Навіщо це.** Зворотне живлення на коротку мить так само реальне, як постійне, — просто його важче спіймати приладом (воно миготить). Але якщо ця мить розтягнеться через помилку в коді чи очікування відповіді, миттєвий струм стане постійним. Правильний порядок робить кран закритим *за конструкцією* в кожен момент, а не лише в усталеному сні.

## Крок 3: заморозити рівні на час deep-sleep

Тепер найхитріше, заради чого окрема функція й існує. Ми звели ніжки в LOW і заснули в правильному порядку — але, як я казав на початку, на ESP32 цифрова ніжка під час deep-sleep **не зберігає** твій рівень сама собою. Потрібно явно сказати залізу: «заморозь те, що зараз на ніжках, і тримай уві сні».

Тут три засоби, і кожен закриває свою діру. Сплутати їх — типова помилка, тож розберімо, що саме робить кожен.

**`gpio_hold_en(pin)` — заморозити стан конкретної ніжки.** Викликаєш для ніжки — і її поточний стан (напрям, рівень, підтяжки, сила драйва) **залочується**: подальші зміни конфігурації на неї не діють, поки не зробиш `gpio_hold_dis()`. Сам по собі цей виклик тримає стан у робочому режимі й у light-sleep. Але на ESP32, як ми бачили, для *deep-sleep* цього **замало**.

**`gpio_deep_sleep_hold_en()` — увімкнути утримання всіх цифрових ніжок саме на deep-sleep.** Це і є та відсутня ланка. У документації ESP-IDF дослівно: *«Вмикає утримання всіх цифрових gpio-ніжок під час Deep-sleep; з цим увімкненим усі цифрові gpio-ніжки перебувають у стані утримання під час Deep-sleep»*. Без цього виклику навіть `gpio_hold_en()` на ESP32 не врятує: ніжка скинеться на час сну.

Тобто правильна пара для ESP32 — це **обидва**: `gpio_hold_en()` на кожну ніжку, чий рівень треба втримати, плюс **один** загальний `gpio_deep_sleep_hold_en()` перед самим сном:

```c
static void freeze_pins_for_deep_sleep(void)
{
    // 1) Заморозити рівень кожної цифрової ніжки з профілю.
    for (size_t i = 0; i < SLEEP_PROFILE_LEN; i++) {
        gpio_hold_en(SLEEP_PROFILE[i].pin);   // залочити поточний (LOW/Hi-Z) стан
    }

    // 2) Увімкнути утримання цифрових ніжок саме на час deep-sleep.
    //    Без цього рядка на ESP32 п.1 не діє у глибокому сні!
    gpio_deep_sleep_hold_en();
}
```

**`rtc_gpio_isolate(pin)` — окрема ізоляція RTC-ніжки.** Це третій, найтонший засіб, і він про інший клас ніжок. Частина ніжок ESP32 належить RTC-домену (вони лишаються живими в deep-sleep, ними будять чип тощо). Для такої ніжки буває, що зовнішня підтяжка на платі **конфліктує** з внутрішньою підтяжкою протилежного напрямку — і крізь цю пару резисторів постійно тече струм, навіть коли ніжка нікуди логічно не приєднана. Класичний приклад — GPIO12 (MTDI) на модулях WROVER: зовні підтягнутий угору, а всередині чипа має підтяжку вниз. У документації прямо радять для такого модуля викликати `rtc_gpio_isolate(GPIO_NUM_12)` перед сном, щоб скинути зайвий струм. Функція *«від'єднує внутрішні кола від RTC-ніжки: вимикає вхід, вихід, підтяжку вгору, підтяжку вниз і вмикає утримання»* — тобто робить ніжку справді ізольованою, без жодного шляху для струму:

```c
static void isolate_rtc_pins(void)
{
    // RTC-ніжки, де зовнішня й внутрішня підтяжки конфліктують,
    // ізолюємо повністю: жодного входу/виходу/підтяжки → жодного струму.
    rtc_gpio_isolate(GPIO_NUM_12);   // напр. MTDI на WROVER: зовні вгору, всередині вниз
}
```

Складаємо весь крок засинання в одну функцію — і це фінал прошивкової частини: профіль, порядок, заморозка, ізоляція, сон.

```c
void enter_audited_deep_sleep(void)
{
    apply_sleep_profile();          // 1) усі ніжки → безпечний рівень (один прохід)
    sensor_power_down();            // 2) правильний порядок: сигнали → потім VDD
    display_power_down();           //    (так само для решти вузлів за load switch)
    radio_power_down();

    freeze_pins_for_deep_sleep();   // 3) заморозити цифрові ніжки на deep-sleep
    isolate_rtc_pins();             //    + ізолювати конфліктні RTC-ніжки

    esp_deep_sleep_start();         // тепер кран закритий з усіх боків
}
```

> 🔧 **Навіщо це.** Три засоби — три різні діри: `gpio_hold_en` тримає рівень, `gpio_deep_sleep_hold_en` вмикає це утримання саме в deep-sleep на ESP32, `rtc_gpio_isolate` прибирає струм крізь конфліктні підтяжки RTC-ніжок. Пропустиш `deep_sleep_hold` — рівні «попливуть» уві сні; пропустиш `isolate` на проблемній ніжці — лишиться десяток-другий мкА «нізвідки». Кожен виклик закриває свій конкретний шлях, тому в робочому коді вони майже завжди йдуть разом.

### Пастка: заморозив — не забудь розморозити на пробудженні

Заморозка **переживає** deep-sleep навмисне — щоб ніжки тримали рівень і вві сні, і на самому пробудженні, поки прошивка ще не встигла їх переналаштувати (інакше була б ще одна мить хаосу). Зворотний бік: після пробудження, коли ти знову хочеш керувати ніжкою, вона **й далі залочена** — твої `gpio_set_level()` мовчки не діятимуть, бо стан заморожено. Лагодиться явним зняттям утримання на старті:

```c
// На самому початку app_main() після пробудження з deep-sleep:
if (esp_sleep_get_wakeup_cause() != ESP_SLEEP_WAKEUP_UNDEFINED) {
    for (size_t i = 0; i < SLEEP_PROFILE_LEN; i++) {
        gpio_hold_dis(SLEEP_PROFILE[i].pin);   // розморозити — тепер ніжкою можна керувати
    }
    gpio_deep_sleep_hold_dis();
}
```

Симптом, за яким упізнаєш цю пастку: після пробудження ніжка «застрягла» в тому рівні, що був перед сном, і не реагує на запис. Це не зламана ніжка — це не знята заморозка.

## Крок 4: self-test, що ділить плату навпіл сам

Дотепер прошивка готувала пристрій до сну. Тепер змусимо її **робити сам аудит** — те ділення навпіл, що в статті ми робили руками, відрізаючи гілки приладом. Якщо кожна гілка живиться через свій load switch, прошивка може гасити їх по черзі сама, а ти лише читаєш струм на лічильнику й дивишся, де велике падіння. Це перетворює півгодинне ручне полювання на процедуру, яку запускаєш однією командою.

Ідея проста й випливає прямо зі статті: дерево живлення = корінь і гілки за ключами; самотест по черзі **лишає ввімкненою рівно одну** конфігурацію й тримає її стільки, щоб ти встиг зняти усталене число. Спершу — всі гілки погашені (нижня межа, сам чип); потім по одній вмикаємо й бачимо її внесок. Так розклад струму по гілках видно з одного прогону.

Опишемо гілки тією ж табличною ідеєю, що й ніжки: кожна гілка — це її `EN`-пін load switch-а й людська назва.

```c
typedef struct {
    gpio_num_t  en_pin;     // EN load switch-а гілки (1 = гілка під живленням)
    const char *name;
} power_branch_t;

static const power_branch_t BRANCHES[] = {
    { SENSOR_LOADSW_EN,  "sensor"  },
    { RADIO_LOADSW_EN,   "radio"   },
    { DISPLAY_LOADSW_EN, "display" },
};
#define BRANCH_LEN (sizeof(BRANCHES) / sizeof(BRANCHES[0]))

static void all_branches_off(void)
{
    for (size_t i = 0; i < BRANCH_LEN; i++)
        gpio_set_level(BRANCHES[i].en_pin, 0);
}
```

Тепер сам прохід. Він спершу гасить усе (отримуємо «підлогу» — струм самого сплячого чипа), а далі по черзі піднімає одну гілку, витримує паузу на стабілізацію й **зупиняється**, лишаючи цю одну гілку ввімкненою рівно настільки, щоб ти зняв показ. Між кроками самотест друкує підказку в лог — щоб у терміналі було видно, *яку саме* конфігурацію зараз міряєш:

```c
// Самотест ділення навпіл: лишає по одній гілці й чекає зняття струму.
// Запускати з пристроєм у розриві живлення під лічильником/профілювальником.
void sleep_self_test(void)
{
    const TickType_t SETTLE = pdMS_TO_TICKS(3000);  // час зняти усталене число

    apply_sleep_profile();   // ніжки — у безпечний стан, як перед справжнім сном
    all_branches_off();
    ESP_LOGI("AUDIT", "усі гілки OFF — зніми струм (це ПІДЛОГА: сам чип)");
    vTaskDelay(SETTLE);

    for (size_t i = 0; i < BRANCH_LEN; i++) {
        all_branches_off();
        gpio_set_level(BRANCHES[i].en_pin, 1);       // лишаємо рівно одну гілку
        ESP_LOGI("AUDIT", "увімкнено ТІЛЬКИ '%s' — зніми струм; "
                          "внесок гілки = показ − підлога", BRANCHES[i].name);
        vTaskDelay(SETTLE);
    }

    all_branches_off();
    ESP_LOGI("AUDIT", "self-test завершено — усі гілки OFF");
}
```

Прочитати результат просто: записуєш «підлогу» (усе off), тоді кожне число «тільки гілка X», віднімаєш підлогу — і маєш внесок кожної гілки окремо. Велике число — винна гілка, далі ділиш уже **всередині** неї (вимикаєш у ній окремі мікросхеми тим самим прийомом). Це дослівно той розклад, що в worked-прикладі статті: радіо ~6 мкА, дисплей ~22 мкА, давач-гілка ~440 мкА — винний видно з першого прогону.

### Self-test чесніший, якщо чип сам міряє свій струм

Дотепер струм читає зовнішній лічильник, а прошивка лише перемикає гілки. Можна піти далі: якщо на платі є **монітор струму** на шині (давач струму на I²C — клас INA-подібних мікросхем), прошивка зчитає число сама й одразу впише його в лог поряд із назвою гілки. Тоді весь аудит — це один прогін без людини з мультиметром:

```c
void sleep_self_test_auto(void)
{
    const TickType_t SETTLE = pdMS_TO_TICKS(500);

    apply_sleep_profile();
    all_branches_off();
    vTaskDelay(SETTLE);
    float floor_uA = power_monitor_read_uA();      // підлога: сам чип
    ESP_LOGI("AUDIT", "підлога (сам чип): %.1f мкА", floor_uA);

    for (size_t i = 0; i < BRANCH_LEN; i++) {
        all_branches_off();
        gpio_set_level(BRANCHES[i].en_pin, 1);
        vTaskDelay(SETTLE);
        float total = power_monitor_read_uA();
        ESP_LOGI("AUDIT", "гілка '%-8s': %.1f мкА  (внесок %.1f мкА)",
                 BRANCHES[i].name, total, total - floor_uA);
    }
    all_branches_off();
}
```

Тут є чесне обмеження, яке варто назвати: **сам монітор струму на шині теж споживає** і теж має свою точність. Він добре бачить десятки-сотні мкА (внески гілок), але на самій підлозі в одиниці мкА його похибка вже відчутна. Тому вбудований монітор — інструмент *грубого* ділення навпіл (знайти гілку-винуватця), а фінальне число одиниць мкА однаково знімають зовнішнім [профілювальником](root:embedded/measure-consumption/comp-current-profiler.md), який тримає п'ять-сім порядків струму одним трактом. Вбудований self-test не заміняє чесний прилад — він економить години на грубому етапі, доводячи пошук до конкретної гілки автоматично.

> 🔧 **Навіщо це.** Ручне ділення навпіл — це людина, прилад і півгодини перепаювань-перемикань на кожну ітерацію. Self-test зводить це до однієї команди й кількох секунд: прошивка сама перебирає гілки, ти лише дивишся на число (або й число знімається само). На платі, яку аудитуєш не вперше, це різниця між «знову сідати з мультиметром» і «прогнати self-test між справами».

## Крок 4-біс: baseline як захист від регресій

Останнє — і концептуально найважливіше. Аудит, який закінчився «стало 26 мкА, добре», не захищає тебе від **завтрашнього** коміту. Хтось (можливо, ти сам) додасть фічу, ненароком лишить ніжку в HIGH перед сном — і струм тихо повернеться до сотень мкА. У лабораторії все добре: пристрій працює, тести зелені. Помилка випливе **в полі**, через тижні, коли батареї почнуть сідати втричі швидше за обіцяне. Це найгірший клас регресій: дорогий, відкладений у часі, невидимий на столі.

Лік — **записаний базовий струм спокою** (baseline): одне число, зняте тоді, коли аудит зійшовся, проти якого звіряється кожна наступна збірка. Регресія тепер видно не через тижні розрядки, а одразу — як стрибок числа проти записаного.

Найпростіша реалізація — тримати baseline прямо в прошивці як константу й мати «режим аудиту», що знімає поточний струм вбудованим монітором і порівнює з нею. Перевищив поріг — гучна помилка ще на столі:

```c
// Записане базове число — оновлюємо ВРУЧНУ лише коли аудит свідомо зійшовся.
#define SLEEP_BASELINE_UA   26.0f    // зняте після фіксу (див. worked-приклад статті)
#define SLEEP_TOLERANCE_UA  10.0f    // допуск на розкид плат/температуру

// Режим аудиту: завести в сон, зняти струм, звірити з baseline.
void assert_sleep_baseline(void)
{
    apply_sleep_profile();
    sensor_power_down();
    display_power_down();
    radio_power_down();
    vTaskDelay(pdMS_TO_TICKS(1000));     // дати струму усталитися

    float now = power_monitor_read_uA();
    if (now > SLEEP_BASELINE_UA + SLEEP_TOLERANCE_UA) {
        ESP_LOGE("AUDIT", "РЕГРЕСІЯ струму спокою: %.1f мкА проти baseline %.1f мкА "
                          "(+%.1f). Хтось лишив ніжку в HIGH?",
                 now, SLEEP_BASELINE_UA, now - SLEEP_BASELINE_UA);
    } else {
        ESP_LOGI("AUDIT", "струм спокою OK: %.1f мкА (baseline %.1f)",
                 now, SLEEP_BASELINE_UA);
    }
}
```

Два дисциплінарні правила, без яких baseline не працює.

**Перше: baseline оновлюють лише руками й лише свідомо.** Спокуса «хай код сам перезапише baseline поточним числом» руйнує весь сенс: якщо baseline тихо повзе за фактом, він завжди «сходиться», і регресію він уже не спіймає — він її *приймає*. Тому `SLEEP_BASELINE_UA` — константа, яку міняє людина в окремому коміті з поясненням «чому струм спокою тепер інший» (додали потрібну периферію, замінили стабілізатор). Кожна зміна baseline має бути видимою подією в історії, а не побічним ефектом.

**Друге: допуск (tolerance) — не нуль, але й не безмежний.** Різні екземпляри плат, температура, розкид стабілізаторів дають законний розкид у кілька мкА — нульовий допуск даватиме хибні тривоги. Та якщо поставити допуск у сотні мкА «щоб не чіпало», він пропустить саме ту регресію, заради якої існує. Орієнтир — допуск близько половини самого бюджету: достатньо широкий для чесного розкиду, достатньо вузький, щоб зайвий HIGH-пін (а це десятки-сотні мкА) гарантовано пробив поріг.

> 🔧 **Навіщо це.** Без baseline аудит — разова перемога, яку наступний коміт мовчки відбирає. З baseline кожна збірка проходить той самий тест на струм спокою, що й перша; регресія коштує одну гучну помилку на столі замість тижнів загадкової розрядки в полі. Це той самий зсув, що й у тестуванні коду: ловити поломку при збірці, а не у користувача.

## Куди це лягає в реальному проєкті

Зведімо чотири кроки в картину їхньої взаємодії, бо порядок викликів тут не випадковий — він повторює фізику засинання.

![Прошивковий конвеєр аудиту: профіль зводить усі ніжки в безпечний рівень, далі вузли гасяться в порядку «сигнали → VDD», тоді заморозка тримає рівні на deep-sleep і ізоляція прибирає струм RTC-ніжок; збоку — self-test, що ділить плату навпіл, і baseline, що ловить регресію.](img/firmware-pipeline.svg)
*Прошивкова частина аудиту як конвеєр. Зліва направо — обов'язковий шлях у сон: профіль ніжок, порядок гасіння вузлів, заморозка й ізоляція. Збоку — два інструменти контролю: self-test автоматизує ділення навпіл, baseline вартує проти регресій. Стрілки порядку відбивають фізику: потенціал знімається раніше за живлення вузла, заморозка — останньою перед самим сном.*

У живому коді ці шматки розходяться по двох місцях. Шлях у сон (`enter_audited_deep_sleep`) кличеться щоразу перед `esp_deep_sleep_start()` — це штатна частина прошивки. А self-test і `assert_sleep_baseline` — це **режим обслуговування**: окрема гілка в `app_main()`, яку вмикаєш джампером, командою по UART чи прапорцем у NVS, щоб прогнати аудит на конкретному екземплярі плати без перепрошивання основної логіки.

Що варто запам'ятати з усього коду, якщо стиснути до трьох тверджень:

- **Безпечний стан — таблицею, не точково.** Один прохід по профілю не дасть забути ніжку; кожна або LOW (над вузлом, що гасне), або справді Hi-Z (без підтяжок).
- **Порядок — фізичний, не косметичний.** Сигнали в LOW *перед* зняттям VDD вузла й *після* його подачі; інакше відкриваєш кран на перехідному процесі.
- **Заморозка й baseline — два різні захисти.** `gpio_deep_sleep_hold_en` + (де треба) `rtc_gpio_isolate` тримають рівні вві сні *сьогодні*; записаний baseline ловить того, хто зламає їх *завтра*.

Усе це не екзотика, а звичайна гігієна прошивки під батарею. Та сама плата без цих чотирьох кроків і з ними відрізняється не на відсотки, а в рази автономності — і вся різниця живе не в залізі, а в кількох десятках рядків, що зводять ніжки в правильний стан і вартують, щоб вони такими лишилися.
