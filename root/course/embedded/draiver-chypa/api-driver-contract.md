# 📋 Специфікація інтерфейсу та контракт вбудованого драйвера

Чистий драйвер апаратного чипа у вбудованих системах підпорядковується суворому архітектурному контракту. Цей контракт визначає правила взаємодії між трьома незалежними сторонами: застосунком предметної області, внутрішньою регістровою логікою драйвера та апаратно-залежним транспортним рівнем мікроконтролера. Порушення будь-якого з пунктів контракту перетворює портативну бібліотеку на жорстко прив'язаний до заліза фрагмент коду, що створює приховані блокування, взаємні блокування потоків (deadlocks) або псування пам'яті в багатозадачному середовищі реального часу.

У промисловій розробці драйвер не створюється під конкретну друковану плату чи певне сімейство мікроконтролерів. Він проєктується як самодостатній абстрактний автомат, здатний працювати з будь-яким джерелом вводу-виводу: від апаратного контролера I2C на кристалі ARM Cortex-M або RISC-V до програмного емулятора шини на сервері безперервної інтеграції (CI). Нижче наведено детальний опис контрактних угод, інваріантів пам'яті, сигнатур функцій, вимог до прямого доступу до пам'яті (DMA) та правил обробки виняткових ситуацій.

---

## 1. Інваріанти пам'яті та керування ресурсами

Будь-який вбудований драйвер, призначений для систем критичного призначення (автомобільна електроніка, авіоніка, медичне обладнання, автономні роботи, промислова автоматика), зобов'язаний дотримуватися жорстких обмежень щодо використання системної пам'яті.

| Параметр | Вимога контракту | Інженерне обґрунтування |
| :--- | :--- | :--- |
| **Динамічна пам'ять** | `malloc()` / `free()` / `new` / `delete` суворо заборонені. | Запобігання фрагментації купи (heap fragmentation), витокам пам'яті та недетермінованому часу виділення ресурсів в ОС реального часу (RTOS). |
| **Розподіл дескриптора** | Статичний або на стеку викликача (`caller-allocated`). | Викликач самостійно вирішує, де розмістити `struct chip_dev_t`: у статичній пам'яті `.bss`, у пулі об'єктів чи на стеку ініціалізатора. |
| **Глобальні змінні** | Нуль статичних чи глобальних змінних стану всередині драйвера. | Забезпечує повну реентерабельність та незалежне опитування довільної кількості однакових мікросхем на різних шинах. |
| **Розмір дескриптора** | Фіксований на етапі компіляції (`sizeof(dev_t) <= 128` байтів). | Мінімізація накладних витрат ОЗП для мікроконтролерів із жорстким лімітом пам'яті (Cortex-M0+, AVR, RISC-V). |
| **Вирівнювання пам'яті** | Усі внутрішні структури вирівняні за 32-бітною межею. | Запобігання апаратним помилкам невирівняного доступу (UsageFault / Alignment Trap) на процесорах без підтримки unaligned memory access. |

Драйвер гарантує, що він не створює прихованих фонових потоків виконання, не перехоплює вектори апаратних переривань напряму і не блокує переривання глобально через інструкції процесора на зразок `__disable_irq()`. Усі критичні секції синхронізації делегуються викликаючому рівню або платформенній обгортці шини.

### Детальні контрактні зобов'язання платформного шару

1. **Непрозорий контекст платформи (`user_ctx`):**
   * Вказівник `user_ctx` передається платформою в дескриптор під час виклику `chip_init()`.
   * Драйвер чипа ніколи не розіменовує `user_ctx` безпосередньо, не змінює його значення і не робить припущень щодо його типу чи розміру структури, на яку він вказує.
   * Платформа використовує цей вказівник для передачі апаратного хендла (наприклад, покажчика на структуру `I2C_HandleTypeDef*` у бібліотеці STM32 HAL, файлового дескриптора сокета в Linux чи покажчика на м'ютекс шини у FreeRTOS).
2. **Атомарність шинних операцій:**
   * Функція `bus_read` зобов'язана реалізовувати неподільну шинну транзакцію: формування сигналу START, передача адреси пристрою з бітом запису, надсилання адреси цільового регістру, формування повторного старту (Repeated Start), надсилання адреси пристрою з бітом читання, зчитування вказаної кількості байтів та формування фінального сигналу STOP.
   * Якщо на одній фізичній шині перебуває кілька пристроїв, захоплення та звільнення апаратного м'ютекса (Bus Mutex / Lock) покладається на реалізацію транспортного шару платформи, а не на драйвер конкретного датчика.
3. **Гарантія детермінованих тайм-аутів:**
   * Платформна функція вводу-виводу не має права залишатися в нескінченному циклі опитування апаратних регістрів мікроконтролера при фізичному обриві лінії SDA чи SCL. Вона зобов'язана містити апаратний або програмний тайм-аут і повертати від'ємний код помилки при втраті зв'язку.

## 4. Контракт прямого доступу до пам'яті (DMA) та кеш-когерентності

Коли транспортний рівень використовує контролер прямого доступу до пам'яті (DMA) для високошвидкісного зчитування пакетних даних (наприклад, вичитування 128-байтного FIFO-буфера сенсора на частоті SPI 10 МГц), діють спеціальні правила щодо буферів пам'яті:

1. **Розташування буферів в ОЗП:** Буфер зчитування зобов'язаний бути розміщений в області оперативної пам'яті, доступній для шини DMA (наприклад, у звичайному SRAM, а не у внутрішній пам'яті ядра DTCM або CCM, до якої контролер DMA на деяких архітектурах ARM Cortex-M не має доступу).
2. **Кеш-когерентність (на процесорах Cortex-M7 / Cortex-A):** Якщо на мікроконтролері увімкнено кеш даних (D-Cache), транспортний шар зобов'язаний виконати операцію інвалідації кешу (`SCB_InvalidateDCache_by_Addr`) після завершення транзакції DMA перед тим, як повернути керування логіці драйвера. Інакше процесор прочитає застарілі дані з кешу замість свіжих байтів, щойно завантажених контролером DMA з шини.
3. **Вирівнювання буферів під розмір рядка кешу:** Для запобігання пошкодженню сусідніх змінних (Cache Line False Sharing) розмір та початкова адреса буфера DMA повинні бути вирівняні за 32-байтною межею рядка кешу.

## 5. Контракт потокобезпеки, блокування та повторного входження

1. **Реентерабельність для різних дескрипторів:**
   * Драйвер є повністю **повторно вхідним (reentrant)**. Це означає, що два незалежні завдання RTOS можуть одночасно викликати функцію `chip_read_sample()` для двох різних екземплярів `chip_dev_t` без виникнення перегонів за ресурси (Race Conditions).
2. **Потокобезпека для одного дескриптора:**
   * Драйвер **не містить внутрішніх м'ютексів** усередині структури дескриптора, щоб не накладати штучних залежностей від конкретної RTOS (FreeRTOS, Zephyr, ThreadX чи bare-metal суперциклу).
   * Якщо кілька потоків вимагають доступу до одного й того самого фізичного датчика, відповідальність за синхронізацію покладається на рівень прикладного застосунку.
3. **Обмеження на виклики з обробників переривань (ISR):**
   * Жодна публічна функція драйвера не може викликатися з контексту переривання (ISR), якщо вона виконує блокуючі операції вводу-виводу по I2C/SPI або затримки `delay_ms()`.
   * Для обслуговування переривань від лінії готовності даних (DRDY Interrupt) драйвер надає окрему швидку функцію перевірки стану прапорців без шинних транзакцій або формує подію для передачі в чергу RTOS.

## 7. Чекліст валідації архітектурної чистоти драйвера

Перед інтеграцією драйвера чипа в базову кодову базу проєкту переконайтеся у дотриманні наступних критеріїв:

1. [ ] У заголовних файлах відсутні `#include` конкретних HAL (наприклад, `stm32f4xx_hal.h`, `esp_log.h`, `avr/io.h`).
2. [ ] Драйвер успішно збирається x86_64 компілятором під час юніт-тестування без емуляції регістрів мікроконтролера.
3. [ ] Дескриптор `dev_t` зберігає повну конфігурацію, дозволяючи створити 4 екземпляри драйвера для 4 однакових мікросхем на двох різних шинах I2C.
4. [ ] Жодна помилка апаратної передачі не маскується: при виникненні NACK функція негайно повертає код помилки вищому рівню.
5. [ ] Усі вихідні дані вимірювань представлені у стандартних одиницях системи SI (`м/с²`, `Па`, `°C`), звільняючи прикладну бізнес-логіку від обчислення ціни молодшого розряду (LSB) за даташитом.
6. [ ] Кожен крок ініціалізації та опитування статусів захищений скінченним квантованим тайм-аутом.
7. [ ] Усі операції з багатобайтовими регістрами виконуються пакетом (Burst Read) з увімкненим блокуванням BDU для захисту від розриву відліків.
