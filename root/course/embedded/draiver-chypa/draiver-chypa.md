# Драйвер чипа: Базові концепції

Вбудовані системи (embedded systems) оточують нас усюди: від простих мікрохвильових печей до складних систем керування космічними апаратами. В основі кожної такої системи лежить апаратне забезпечення — мікроконтролери (MCU) та різноманітні периферійні мікросхеми (сенсори, актуатори, дисплеї, модулі зв'язку). Щоб програмне забезпечення могло ефективно та безпечно взаємодіяти з цим апаратним забезпеченням, використовується спеціалізований прошарок коду — **драйвер чипа** (або драйвер пристрою).

Ця стаття глибоко занурюється у базові концепції розробки драйверів для мікросхем, розглядає архітектурні підходи для bare-metal систем та операційних систем реального часу (RTOS), а також детально пояснює механізми взаємодії з апаратними регістрами та обробки переривань. Ми також розглянемо математичні основи, необхідні для роботи з апаратними інтерфейсами, та наведемо практичні приклади коду мовами C/C++.

## Що таке драйвер чипа?

Драйвер чипа — це програмний компонент, який абстрагує деталі низькорівневої апаратної реалізації певного пристрою (мікросхеми) та надає зручний, стандартизований інтерфейс прикладного програмування (API) для вищих рівнів програмного забезпечення. 

Основні завдання драйвера:
1. **Ініціалізація та конфігурація**: Налаштування початкового стану мікросхеми, вибір режимів роботи, встановлення швидкостей передачі даних тощо.
2. **Абстракція регістрів**: Приховування складних бітових маніпуляцій з регістрами за зрозумілими функціями (наприклад, замість `SPI->CR1 |= (1 << 6)` драйвер надає функцію `spi_enable()`).
3. **Обробка даних**: Перетворення сирих даних з пристрою у фізичні величини (наприклад, перетворення кодів АЦП у градуси Цельсія) та навпаки.
4. **Керування станом**: Відстеження поточного стану пристрою (готовий, зайнятий, помилка) та керування енергоспоживанням.
5. **Обробка переривань**: Швидке реагування на апаратні події без постійного опитування (polling) стану.

## Архітектура драйвера

Архітектура драйвера суттєво залежить від середовища виконання. Загалом можна виділити два основних підходи: для bare-metal систем (без операційної системи) та для систем з RTOS.

### Bare-metal системи

У bare-metal середовищі програма виконується безпосередньо на апаратному забезпеченні, маючи повний та ексклюзивний доступ до всіх ресурсів процесора та периферії. Архітектура драйвера в такому випадку зазвичай простіша, але вимагає обережного поводження з блокуючими операціями.

У bare-metal системах драйвери часто будуються на основі двох парадигм:
- **Polling (Опитування)**: Процесор періодично перевіряє стан регістра (наприклад, прапорець завершення перетворення АЦП або готовності даних UART). Це найпростіший, але найменш ефективний спосіб, оскільки процесор витрачає час на очікування (busy waiting).
- **Interrupt-driven (На основі переривань)**: Процесор продовжує виконувати інші завдання, а пристрій генерує переривання, коли потребує уваги. Драйвер містить обробник переривання (ISR), який швидко виконує необхідні дії.

### Системи реального часу (RTOS) та ОС загального призначення

Коли використовується RTOS (наприклад, FreeRTOS, Zephyr, ThreadX), архітектура драйвера стає складнішою. Драйвер повинен бути потокобезпечним (thread-safe) та інтегруватися з механізмами синхронізації ОС.

Особливості драйверів під RTOS:
- **Блокуючі виклики**: Замість busy waiting (як у bare-metal), драйвер використовує примітиви синхронізації (семафори, черги, м'ютекси) для блокування потоку, поки дані не будуть готові. Це дозволяє процесору виконувати інші потоки під час очікування I/O.
- **Розділення ISR та Task**: Обробник переривання (ISR) має бути максимально коротким. Він лише очищає прапорець переривання та сигналізує (наприклад, через семафор або чергу повідомлень) відповідному потоку (Task) драйвера про те, що відбулася подія. Подальша, більш складна обробка даних відбувається в контексті потоку.
- **М'ютекси для доступу**: Якщо кілька потоків намагаються одночасно отримати доступ до одного апаратного ресурсу (наприклад, спільної шини I2C), драйвер використовує м'ютекс для забезпечення ексклюзивного доступу.

## Робота з апаратними регістрами

Взаємодія мікропроцесора з периферійними пристроями найчастіше відбувається через механізм **Memory-Mapped I/O (MMIO)**.

### Memory-Mapped I/O (MMIO)

У MMIO апаратні регістри відображаються у загальний адресний простір пам'яті процесора. Це означає, що читання або запис у певні адреси пам'яті фізично призводить до зчитування або зміни стану тригерів у контролері периферійного пристрою, а не до звернення до оперативної пам'яті (RAM).

### Визначення регістрів у C/C++

Мова C ідеально підходить для написання драйверів завдяки можливості прямого доступу до пам'яті за допомогою вказівників. Однак, при роботі з MMIO критично важливо використовувати ключове слово `volatile`. Воно повідомляє компілятору, що значення за цією адресою може змінитися в будь-який момент часу (наприклад, апаратним забезпеченням), і тому компілятор не повинен кешувати це значення в регістрах процесора або оптимізувати операції читання/запису.

Існує два основні підходи до визначення регістрів: за допомогою макросів та за допомогою структур.

**Підхід 1: Використання макросів**

```c
#define UART0_BASE       0x4000C000
#define UART0_DR         (*((volatile uint32_t*)(UART0_BASE + 0x00)))
#define UART0_FR         (*((volatile uint32_t*)(UART0_BASE + 0x18)))

#define UART_FR_TXFF     (1 << 5) // Transmit FIFO full

void uart_write_char(char c) {
    // Очікуємо, поки FIFO не звільниться (busy waiting)
    while (UART0_FR & UART_FR_TXFF) {
        // Нічого не робимо
    }
    UART0_DR = c; // Записуємо символ у Data Register
}
```

**Підхід 2: Використання структур**

Цей підхід вважається більш сучасним та безпечним з точки зору типізації, і широко використовується в бібліотеках виробників (наприклад, CMSIS для ARM Cortex-M).

```c
#include <stdint.h>

// Визначаємо структуру, що описує розташування регістрів
typedef struct {
    volatile uint32_t DR;       // Data Register, зміщення 0x00
    volatile uint32_t RSR;      // Receive Status Register, зміщення 0x04
    uint32_t reserved0[4];      // Зарезервований простір 
    volatile uint32_t FR;       // Flag Register, зміщення 0x18
    volatile uint32_t ILPR;     // IrDA Low-Power Register, зміщення 0x20
    volatile uint32_t IBRD;     // Integer Baud Rate Register, зміщення 0x24
    volatile uint32_t FBRD;     // Fractional Baud Rate Register, зміщення 0x28
    volatile uint32_t LCRH;     // Line Control Register, зміщення 0x2C
    volatile uint32_t CR;       // Control Register, зміщення 0x30
} UART_TypeDef;

#define UART0 ((UART_TypeDef*)0x4000C000)

void uart_init(void) {
    // Вимикаємо UART перед налаштуванням
    UART0->CR &= ~(1 << 0);
    
    // Встановлюємо Baud Rate та інші параметри...
    
    // Вмикаємо UART, передавач та приймач
    UART0->CR |= (1 << 0) | (1 << 8) | (1 << 9);
}
```

### Математика та бітові операції

Розробка драйверів вимагає розуміння бітової математики для налаштування масок регістрів та обчислення параметрів, таких як частота або затримки.

Наприклад, розрахунок значення для регістра дільника частоти (Baud Rate Register) часто описується формулами у специфікації мікроконтролера. Якщо ми налаштовуємо шину I2C (або TWI), частота тактування шини $f_{SCL}$ може обчислюватися за формулою:

$$ f_{SCL} = \frac{f_{CPU}}{16 + 2 \cdot TWBR \cdot 4^{TWPS}} $$

Де:
- $f_{CPU}$ — частота процесора.
- $TWBR$ — значення регістра TWI Bit Rate Register (те, що ми маємо розрахувати та записати).
- $TWPS$ — значення прескейлера (TWI Prescaler bits).

Щоб знайти значення $TWBR$, драйвер має виконати обернене математичне перетворення:

$$ TWBR = \frac{\frac{f_{CPU}}{f_{SCL}} - 16}{2 \cdot 4^{TWPS}} $$

При написанні коду на C ми маємо враховувати цілочисельне ділення та можливі помилки заокруглення.

Ще один приклад — перетворення сирих значень Аналого-цифрового перетворювача (АЦП) у фізичні величини, наприклад, температуру. Якщо датчик температури підключено до 12-бітного АЦП ($N = 12$) з опорною напругою $V_{REF}$, то напруга на датчику обчислюється як:

$$ V_{sensor} = \frac{ADC\_VALUE \cdot V_{REF}}{2^{N} - 1} $$

А значення температури $T$ може залежати від напруги лінійно з коефіцієнтом $k$ та зміщенням $T_0$:

$$ T = V_{sensor} \cdot k + T_0 $$

У коді драйвера ці обчислення можна виконувати як з використанням чисел з рухомою комою (float/double), так і за допомогою математики з фіксованою комою (fixed-point math), якщо процесор не має FPU (Floating Point Unit), щоб заощадити ресурси.

## Обробка переривань

Переривання (Interrupts) — це критично важливий механізм для апаратних драйверів. Коли периферійний пристрій потребує обслуговування (наприклад, завершилося зчитування блоку даних через SPI або спрацював таймер), він посилає апаратний сигнал процесору. Процесор призупиняє виконання поточної програми, зберігає свій контекст і переходить до виконання спеціальної функції — Обробника переривань (Interrupt Service Routine, ISR).

### Концепція ISR

Правила написання ISR:
1. **Швидкість**: ISR має виконуватися максимально швидко. Виконуйте там лише найнеобхідніше: очищення прапорця переривання в регістрі статусу мікросхеми, копіювання байта даних у буфер, та пробудження потоку в RTOS, який виконає решту роботи.
2. **Ніяких блокувань**: У ISR категорично заборонено використовувати блокуючі функції (наприклад, `delay()`, очікування м'ютекса, або функції виводу на екран/термінал на кшталт `printf()`).
3. **Глобальні змінні**: Якщо ISR модифікує глобальну змінну, до якої звертається основна програма, ця змінна має бути оголошена як `volatile`. Крім того, доступ до неї з основної програми повинен бути атомарним (захищеним забороною переривань на час доступу).

```c
#define BUFFER_SIZE 128

volatile uint8_t rx_buffer[BUFFER_SIZE];
volatile uint16_t rx_head = 0;
volatile uint16_t rx_tail = 0;

// Обробник переривання UART (сигнатура залежить від компілятора та MCU)
void __attribute__((interrupt)) UART_RX_ISR(void) {
    // Перевіряємо, чи переривання викликано отриманням даних
    if (UART0->FR & (1 << 4)) { 
        // Зчитуємо байт з регістра даних
        uint8_t data = UART0->DR;
        
        // Зберігаємо в кільцевий буфер
        uint16_t next_head = (rx_head + 1) % BUFFER_SIZE;
        if (next_head != rx_tail) {
            rx_buffer[rx_head] = data;
            rx_head = next_head;
        }
        // Очищаємо прапорець переривання
        UART0->ICR |= (1 << 4);
    }
}
```

## Дизайн інтерфейсу драйвера (API)

Якісний драйвер повинен бути самодостатнім та надавати чіткий абстрактний інтерфейс. Хорошою практикою є використання об'єктно-орієнтованого підходу в C, створюючи структуру (контекст драйвера), яка зберігає стан конкретного екземпляра пристрою. Це дозволяє використовувати один і той же код драйвера для керування кількома однаковими мікросхемами (наприклад, кількома датчиками на різних шинах I2C).

### Ініціалізація та конфігурація

Функція ініціалізації приймає вказівник на об'єкт драйвера та структуру з конфігурацією.

```c
typedef struct {
    I2C_Bus* i2c_bus;       // Вказівник на апаратну шину
    uint8_t device_address; // Адреса пристрою на шині
    float calibration_offset;
} BME280_Config;

typedef struct {
    I2C_Bus* i2c_bus;
    uint8_t device_address;
    float calibration_offset;
    bool is_initialized;
    // Інші змінні стану...
} BME280_Device;

// Функція ініціалізації
int bme280_init(BME280_Device* dev, const BME280_Config* config) {
    if (dev == NULL || config == NULL || config->i2c_bus == NULL) {
        return -1; // Помилка: невірні аргументи
    }
    
    dev->i2c_bus = config->i2c_bus;
    dev->device_address = config->device_address;
    dev->calibration_offset = config->calibration_offset;
    dev->is_initialized = false;
    
    // Перевірка зв'язку з пристроєм (читання регістра Chip ID)
    uint8_t chip_id;
    if (i2c_read_reg(dev->i2c_bus, dev->device_address, 0xD0, &chip_id, 1) != 0) {
        return -2; // Помилка комунікації
    }
    
    if (chip_id != 0x60) {
        return -3; // Помилка: невідомий пристрій
    }
    
    dev->is_initialized = true;
    return 0; // Успіх
}
```

## Синхронізація та конкурентний доступ

Коли система має кілька потоків (в RTOS), може виникнути ситуація, коли два потоки одночасно намагаються викликати функцію драйвера, яка звертається до того самого апаратного інтерфейсу (наприклад, обидва потоки хочуть відправити дані через один UART). Це призведе до змішування даних або збою кінцевого автомата (state machine) в мікросхемі.

Для вирішення цієї проблеми використовуються механізми синхронізації:
1. **М'ютекси (Mutexes)**: Використовуються на рівні потоків. Перед початком транзакції з мікросхемою потік "захоплює" м'ютекс, працює з пристроєм, а потім "відпускає" м'ютекс. Якщо інший потік спробує захопити м'ютекс, він буде заблокований ОС до моменту його вивільнення.
2. **Критичні секції (Critical Sections)**: Використовуються для захисту даних від переривань. Критична секція тимчасово забороняє всі апаратні переривання на короткий час, поки модифікуються спільні змінні (наприклад, покажчики `rx_head` та `rx_tail` кільцевого буфера).

## Практичний приклад: Драйвер температурного сенсора

Наведемо цілісний приклад структури драйвера простого I2C датчика температури на C++. Використання класів інкапсулює стан та методи.

```cpp
#include <cstdint>

// Абстракція шини I2C (залежить від платформи)
class I2CBus {
public:
    virtual bool writeRegister(uint8_t devAddr, uint8_t regAddr, uint8_t data) = 0;
    virtual bool readRegister(uint8_t devAddr, uint8_t regAddr, uint8_t* data) = 0;
    virtual bool readRegisters(uint8_t devAddr, uint8_t regAddr, uint8_t* data, size_t len) = 0;
};

// Драйвер датчика
class TempSensorTMP102 {
private:
    I2CBus& bus;
    uint8_t address;
    bool initialized;

    // Регістри TMP102
    static constexpr uint8_t REG_TEMP = 0x00;
    static constexpr uint8_t REG_CONF = 0x01;

public:
    TempSensorTMP102(I2CBus& i2cBus, uint8_t i2cAddress) 
        : bus(i2cBus), address(i2cAddress), initialized(false) {}

    bool begin() {
        // Прочитаємо конфігураційний регістр для перевірки зв'язку
        uint8_t conf[2];
        if (!bus.readRegisters(address, REG_CONF, conf, 2)) {
            return false;
        }
        
        // Налаштуємо роздільну здатність 12-біт та нормальний режим
        conf[0] &= ~0x01; // Вимикаємо shutdown mode
        conf[1] |= 0x60;  // Встановлюємо Conversion Rate
        
        if (!bus.writeRegister(address, REG_CONF, conf[0])) {
            return false;
        }
        
        initialized = true;
        return true;
    }

    bool getTemperatureC(float& tempOut) {
        if (!initialized) return false;

        uint8_t rawData[2];
        if (!bus.readRegisters(address, REG_TEMP, rawData, 2)) {
            return false;
        }

        // Об'єднуємо байти
        int16_t digitalTemp = (rawData[0] << 4) | (rawData[1] >> 4);
        
        // Обробка від'ємних температур (додатковий код)
        if (digitalTemp > 0x7FF) {
            digitalTemp |= 0xF000;
        }

        // TMP102 має роздільну здатність 0.0625°C на LSB
        // T = digitalTemp * 0.0625
        tempOut = static_cast<float>(digitalTemp) * 0.0625f;
        
        return true;
    }
};
```

## Висновок

Розробка драйверів для вбудованих систем — це комплексна задача, що вимагає глибокого розуміння як апаратного, так і програмного забезпечення. Якісний драйвер повинен приховувати складність роботи з регістрами та шинами за зрозумілим API, ефективно обробляти переривання, уникати блокувань системи та забезпечувати безпечний конкурентний доступ у багатопотокових середовищах.

Незалежно від того, розробляєте ви систему bare-metal чи використовуєте RTOS, дотримання правильної архітектури, використання `volatile` для MMIO та правильний розподіл обов'язків між ISR та основним потоком виконання є ключем до створення стабільного, розширюваного та надійного програмного забезпечення для вбудованих систем.
