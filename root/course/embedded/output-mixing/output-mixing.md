# Узгодження сигналів керування

Мультикоптер керує собою самою лише **тягою** — змінюючи оберти моторів. Але літак нахиляє елерони, руль висоти й напряму; гелікоптер змінює крок лопатей; ровер повертає колеса; камера висить на стабілізованому підвісі. Кожну з цих поверхонь рухає окремий виконавець, а контролер усередині мислить не «напруга на цьому піні», а **бажаним рухом апарата** — накренитися, підняти ніс, дати газ. Між цим бажанням і фізичним залізом лежить останній каскад прошивки, що його звуть **узгодженням сигналів керування**: він бере абстрактну команду й розкладає її на конкретні сигнали конкретним виконавцям. Це і є предмет теми — не сам серворушій, а той шар, що робить так, аби «нахилися ліворуч» правильно лягло на оце серво, цей мотор і саме цей апарат.

Виконавці тут двох сортів, і плутати їх не можна: моторові командують **швидкість** (він крутиться безперервно), а [серворушієві](book:electronics/hobby-servo) — **кут**, який його внутрішній [замкнений контур](book:electronics/servo) утримує проти зовнішніх сил. Серво у цій темі цікавить лише як один із виходів контролера поряд із мотором — уся його конкретика (внутрішній контур, межі ходу, момент, мертва зона) розібрана окремо.

### Спільна мова: ширина імпульсу

Перш ніж розкладати команди по виходах, варто знати, якою фізичною мовою контролер розмовляє з виконавцями, бо вона в них спільна. І серво, і простий [регулятор обертів](book:electronics/esc) розуміють той самий **класичний RC-сигнал** — короткий додатний імпульс, у якому кут (чи газ) кодує **ширина**:

![Три імпульси різної ширини й положення качалки: 1000 мкс — один край, 1500 — центр, 2000 — інший; кадр повторюється кожні ~20 мс](/root/course/embedded/output-mixing/img/signal.svg)
*Мова серво — ширина імпульсу. Імпульс ~1000 мкс ставить качалку в один край, ~1500 мкс — у центр (нейтраль), ~2000 мкс — в інший край; кадр повторюється кожні ~20 мс (≈50 Гц). Носій кута — сама ширина; кадр лише визначає, як часто значення оновлюють.*

Те, що положення несе **ширина** імпульсу, а не його частота, робить цей сигнал [широтно-імпульсним](book:programming/pwm-on-mcu) лише за формою: тут важлива не середня потужність, як у керуванні яскравістю, а тривалість одного імпульсу як число. Кадр ~20 мс (≈50 Гц) — спадок аналогових приймачів, що по черзі роздавали імпульси кільком серво в межах одного кадру. Цей «1.5 мс — нейтраль» десятиліттями лишається спільним стандартом виконавчих механізмів моделей — тому той самий вихід однаково розуміють і серво, і регулятор обертів.

Сформувати такий сигнал самому неважко — досить раз на кадр підняти ногу контролера на потрібну кількість мікросекунд:

**Умова.** Один вивід, до нього під'єднано серво. Поставити вал у центр: кадр 20 мс (50 Гц), імпульс 1500 мкс. Перевести довільний кут 0…180° у ширину.

:::tabs
```arduino
const int   SERVO_PIN = 9;
const int   FRAME_US  = 20000;        // кадр 20 мс = 50 Гц

// кут 0..180°  →  ширина 1000..2000 мкс (лінійна підстановка)
int angle_to_us(int deg) {
    if (deg < 0)   deg = 0;
    if (deg > 180) deg = 180;
    return 1000 + (long)deg * 1000 / 180;   // 0°→1000, 90°→1500, 180°→2000
}

// один кадр: імпульс заданої ширини + добивання паузи до 20 мс
void servo_frame(int pin, int width_us) {
    digitalWrite(pin, HIGH);
    delayMicroseconds(width_us);             // ширина = кут
    digitalWrite(pin, LOW);
    delayMicroseconds(FRAME_US - width_us);  // решта кадру — пауза
}
```

// HAL_Delay() рахує лише мілісекунди, тож мікросекунди беремо
// з вільного лічильника таймера, налаштованого на тік 1 мкс
extern TIM_HandleTypeDef htim2;
static void delay_us(uint32_t us) {
    uint32_t t0 = __HAL_TIM_GET_COUNTER(&htim2);
    while ((uint32_t)(__HAL_TIM_GET_COUNTER(&htim2) - t0) < us) { }
}

    HAL_GPIO_WritePin(SERVO_PORT, SERVO_PIN, GPIO_PIN_SET);
    delay_us(width_us);                           // ширина = кут
    HAL_GPIO_WritePin(SERVO_PORT, SERVO_PIN, GPIO_PIN_RESET);

Перевірмо ключові точки підстановки в думці:

```
deg = 0    → 1000 + 0            = 1000 мкс   (один край)
deg = 90   → 1000 + 90·1000/180  = 1500 мкс   (центр, нейтраль)
deg = 180  → 1000 + 180·1000/180 = 2000 мкс   (інший край)
```

Спосіб «у лоб» добрий, щоб ворухнути серво на столі, але мікросекундна пауза в циклі — байдуже, чим вона зроблена (`delayMicroseconds()`, `esp_rom_delay_us()`, лічильник таймера) — **блокує** ядро на весь кадр. У справжній прошивці ширину тримає апаратний таймер: ти лише записуєш число в регістр, а вузол сам формує і частоту, і тривалість, поки ядро зайняте керуванням. Принцип той самий — змінив ширину, змінився кут.

Варто знати й межі цього сигналу. Ширину 1000–2000 мкс апаратура розрізняє приблизно з кроком у мікросекунду — звідси близько тисячі градацій кута (≈0.18° на крок): для керма цього з головою, але тонше класичним RC-сигналом не задаси. До того ж аналоговий імпульс трохи дрижить від шуму й оновлюється лише ~50 разів на секунду. Сучасні цифрові протоколи виходу (рідня тих, що в [регуляторах обертів](book:electronics/esc)) поступово приходять і до серво — але «півтори мілісекунди» досі лишається спільною мовою.

> 🔧 **Навіщо це.** «1–2 мс, 50 Гц, центр 1.5 мс» — спільна мова контролера, приймача й серво. Зник сигнал — серво або обм'якне, або триматиме останній кут (залежно від моделі); це прямо впливає на те, що робити за відмови. А сигнальний провід несе лише імпульс, тож виконавець і контролер **обов'язково** мають спільну землю: без неї імпульсові «нема відносно чого» бути, і серво смикається хаотично — класична причина «все підключив, а воно сіпається».

### Механічне узгодження: качалка й тяга

Перший рівень узгодження — ще до всякої електроніки, суто механічний. Оберт серво треба **передати** на поверхню, і робить це проста механіка важелів:

![Серво повертає качалку, жорстка тяга штовхає качалку керма, поверхня відхиляється на шарнірі; довжини качалок задають хід](/root/course/embedded/output-mixing/img/linkage.svg)
*Від оберту до відхилення. Серво повертає свій важіль (качалку), жорстка тяга (пушрод) передає рух на качалку керма, і поверхня відхиляється на шарнірі. Довша качалка серво або коротша качалка керма дають більший хід поверхні — але меншу силу на ній.*

Довжини качалок задають передачу між кутом серво й ходом поверхні, і це знову заміна сили на відстань: збільшив хід довшою качалкою серво — зменшив доступну на поверхні силу. Тому хід (throw) підбирають під апарат: замалий — мляве керування, завеликий — апарат смикається й може зірватися в потік, а серво лишається без моменту під навантаженням. Окремо псує точність **люфт** (backlash) — будь-яка слабина в качалках, тягах і кріпленнях: поверхня тоді трохи «гуляє» незалежно від серво, додаючи шум і неточність у самому кінці контуру. Тому тяги роблять жорсткими, а з'єднання — щільними.

Нейтраль виставляють так, щоб за сигналу 1500 мкс поверхня стояла рівно: спершу механічно (серво в центр, тоді кріплять качалку й тягу), а дрібний залишок прибирають уже програмно — тримом. Це й підводить до головного: більшість узгодження живе не в механіці, а у вихідному каскаді прошивки.

> 🔧 **Навіщо це.** Якщо в чужого апарата кермо стоїть не по центру в нейтралі або ходить замало чи забагато — дивись на механіку тяг і на налаштування ходу та триму, а не на «зламане серво». І пам'ятай про навантаження: серво на великому кермі швидкого літака відчуває потужний потік, і його момент має той потік перебороти, інакше керма «віддме».

### Виходи як абстракція: мотор і серво — однакові

Тепер головне узагальнення, заради якого тема й існує. Для контролера **мотори й серво — це однакові «виходи»**. Він не мислить «ШІМ на пін 3»; він мислить бажаним рухом апарата — і спеціальний каскад розкладає це бажання по фізичних виходах:

![Вихідний каскад: бажаний рух (крен/тангаж/курс/тяга) через мікшер у виходи (мотори через ESC і серво) з масштабом, реверсом, тримом, failsafe](/root/course/embedded/output-mixing/img/outputs.svg)
*Як бажаний рух стає сигналами виконавцям. Контролер видає бажані крен, тангаж, курс і тягу; [мікшер](book:algorithms/motor-mixer) розкладає їх по фізичних виходах за геометрією апарата; а кожен вихід проходить узгодження — масштаб, реверс, трим, положення failsafe — і йде до свого виконавця: мотора через ESC або серво. Для контролера обидва типи — просто пронумеровані «виходи».*

Узгодження сигналів — це і є цей останній крок: зробити так, щоб абстрактна команда контролера правильно лягла на **конкретний** виконавець. Воно охоплює п'ять речей, і кожну варто розуміти окремо:

- **мікшування** — розклад бажаного руху по поверхнях за схемою апарата (літак, крило, V-подібний хвіст, мультиротор);
- **масштаб і межі** (endpoints) — щоб повний хід команди дав потрібний, але не надмірний хід поверхні;
- **реверс** — якщо серво стоїть «дзеркально», напрям перевертають програмно, не перебираючи тягу;
- **трим** — зсув нейтралі, щоб за команди «центр» поверхня стояла рівно;
- **положення failsafe** — куди стати виходу, якщо зв'язок чи система відмовлять.

Сила цієї абстракції в тому, що логіка апарата оперує **функціями**, а не пінами. У зрілій прошивці кожному фізичному виходу призначають функцію (цей пін — елерон, той — руль висоти, той — мотор 1), і завдяки цьому **та сама прошивка** літає геть різними апаратами: щоб зробити з мультикоптера літак, не переписують код — лише перепризначають виходи й вибирають інший мікшер. Залізо інше, стек той самий — рівно та переносність, яку дає [шарувата архітектура](book:programming/ardupilot-layers); у ній за цей вихідний каскад відповідає окремий шар (`SRV_Channels`).

### Мікшування: коли поверхонь менше, ніж осей

Найвиразніше мікшування видно там, де одна поверхня несе **кілька** команд керування одразу. Класичний приклад — **елевони** «літаючого крила», де немає окремих елеронів і руля висоти: дві поверхні роблять і те, й те разом:

![Елевони: обидві поверхні вгору — підняти ніс (тангаж); різнойменно — накренити (крен); ті самі дві поверхні несуть дві осі](/root/course/embedded/output-mixing/img/mixing.svg)
*Мікшування елевонів. Лівий елевон = тангаж + крен, правий = тангаж − крен. Обидві поверхні вгору піднімають ніс (тангаж); різнойменно — кренять апарат (крен). Дві поверхні несуть дві осі керування, а мікшер розв'язує цю систему за геометрією крила.*

Той самий принцип — V-подібний хвіст (руль напряму плюс висоти на двох поверхнях), диференціал коліс ровера, де поворот — це різниця обертів лівого й правого боку. Доведений до краю, мікшер стає **автоматом перекосу** (swashplate) гелікоптера: три (а то й більше) серво разом нахиляють тарілку, що змінює крок лопатей. Підняти ніс — серво рухаються в одній комбінації; дати загальний крок угору — синхронно; накренити — в іншій. Жодне серво тут не відповідає за «один» канал: кожне є **сумою** кількох команд за тригонометрією механізму. Скрізь та сама ідея — мікшер ховає геометрію апарата, тож решта стека лишається однаковою.

> 🔧 **Навіщо це.** Мікшер пояснює, чому на крилі чи V-хвості «одне серво слухає дві ручки» — це не поломка, а розв'язок системи. Якщо апарат на елевонах кренить замість підіймати ніс (чи навпаки), причина майже завжди в мікшері або реверсі однієї поверхні, а не в самому серво.

### Масштаб, реверс і трим: підгонка одного виходу

Розклавши команди мікшером, кожен вихід ще доводять окремо — трьома простими підгонками. **Масштаб і межі** (endpoints) задають, який хід поверхні відповідає повній команді: одне крило може вимагати відхилення більшого, інше меншого, тож межі ходу затискають у потрібний коридор (типово від 1000 до 2000 мкс, але вужче, якщо повний хід завеликий). **Реверс** перевертає напрям одного виходу: коли серво фізично стоїть дзеркально й на команду «вгору» тягне поверхню вниз, його не перемонтовують і не перебирають тягу — просто ставлять прапорець реверсу (0 — як є, 1 — навпаки). **Трим** зсуває нейтраль: якщо за команди «центр» поверхня стоїть трохи косо, центральну точку підправляють (скажімо, з 1500 на ~1504 мкс), і поверхня сідає рівно без жодної механіки.

Усі троє — це проста арифметика над числом, що йде до виходу: спершу мікшер дає сире значення, далі його масштабують у межі, за потреби перевертають реверсом і зсувають тримом. Те, що це робиться **на виході**, а не в логіці керування, і дає переносність: сама модель апарата не знає й не мусить знати, яким боком прикручене конкретне серво.

> 🔧 **Навіщо це.** Це найпрактичніша трійця всього розділу. Перше, що перевіряють на новому апараті, — **узгодження виходів**: чи туди їде кожна поверхня (реверс), чи правильний хід (межі), чи стоїть нейтраль (трим). Переплутаний реверс однієї поверхні — і апарат розіб'ється на першій секунді, керуючи «навпаки». Тому перед першим польотом завжди роблять перевірку: ворухнув апарат — подивився, чи поверхні реагують у правильний бік.

### Положення failsafe: куди стати, коли все погано

Останнє узгодження — найважливіше для безпеки. На відміну від мультикоптера, який при втраті зв'язку виконує наперед задану дію (залежно від налаштувань — повернення додому, посадку чи навіть «нічого не робити»; а як супутникова навігація непридатна, повернення зазвичай переходить у посадку), апарат із кермами мусить знати, **куди поставити кожну поверхню**, якщо все піде не так. Газ — на нуль (чи в режим планування), керма — у безпечне положення: часто легкий крен і набір висоти по колу, поки зв'язок не відновиться.

Ці положення задають наперед, у тому ж вихідному каскаді: кожному виходу прописують, куди йому стати за відмови зв'язку. Один вихід може триматися останнього значення, інший — переходити в нейтраль; вибір залежить від ролі поверхні. Як і всюди в [політному контролері](book:programming/flight-controller), реакція на відмову має бути зашита заздалегідь, а не вигадуватися в аварії, — тож failsafe-положення виходів є частиною узгодження так само, як масштаб чи реверс.

Окремо, суто практичне про живлення цього каскаду: серво (а надто кілька) можуть тягти чималий струм ривками, особливо під навантаженням. Тому їх живлять від окремої шини (стабілізатора чи BEC, як у [регуляторі обертів](book:electronics/esc)), **не** від тонкого логічного живлення контролера, — інакше різкий ривок серво «просадить» напругу й перезавантажить усю електроніку в найгірший момент. Це впирається в загальну тему [живлення складних систем](book:electronics/power-rails).

> 🔧 **Навіщо це.** Failsafe-положення — це план на найгірше, і складати його треба тверезо. Спитай про кожен вихід: куди йому стати, якщо зник зв'язок або відмовив давач? Газ — у безпеку, керма — у керований стан. А над усім каскадом виходів стоїть окреме питання — що буде, коли якийсь виконавець **сам** відмовить; на нього відповідає [надлишковість](book:programming/redundancy).

### Підсумок

Узгодження сигналів керування — це останній каскад прошивки, що перетворює абстрактний «бажаний рух» апарата на конкретні сигнали конкретним виконавцям. Для контролера мотори (через ESC) і серво — однакові пронумеровані «виходи», і кожному призначено функцію, а не пін, — звідси переносність: та сама прошивка літає різними апаратами. Спільна фізична мова виходів — класичний RC-сигнал (1–2 мс, ~50 Гц, центр 1.5 мс), де кут несе ширина імпульсу. Узгодження складають п'ять речей: мікшування (розклад руху по поверхнях за геометрією — від елевонів до автомата перекосу), масштаб і межі ходу, реверс, трим і положення failsafe. Механічна частина — качалки й тяги — задає хід і силу та боїться люфту; решта живе в арифметиці виходу. А серворушій у всьому цьому — лише один із виконавців: виконавець **кута**, чий внутрішній замкнений контур розібрано окремо.
