# 🧮 Response Time Analysis: аналітичний розрахунок гарантованого часу відгуку в RTOS

У системах жорсткого реального часу (англ. *Hard Real-Time Systems*) емпіричного тестування недостатньо для гарантії стабільності: навіть мільйон успішних прогонів не доводять, що за рідкісного збігу фаз періодичних задач високопріоритетне витіснення не призведе до пропуску дедлайну найповільнішою задачею. Щоб математично довести своєчасність виконання кожного потоку в операційній системі реального часу (RTOS) із фіксованими пріоритетами та витісненням (англ. *Fixed-Priority Preemptive Scheduling*), застосовують метод аналізу часу відгуку (англ. *Response Time Analysis*, RTA), вперше формалізований М. Джозефом та П. Пандьєю у 1986 році.

Аналіз часу відгуку обчислює найгірший можливий час `R_i` (англ. *Worst-Case Response Time*, WCRT) від моменту виникнення запиту на виконання задачі `τ_i` до моменту повного завершення її роботи з урахуванням усіх можливих затримок, блокувань та витіснень з боку процесів вищого пріоритету.

## Математична модель задачі та джерела затримок

Нехай система складається з набору `n` періодичних задач `Γ = {τ_1, τ_2, ..., τ_n}`, упорядкованих за спаданням пріоритету (де `τ_1` має найвищий пріоритет, а `τ_n` — найнижчий). Кожна задача `τ_i` характеризується вектором сталих параметрів:

* `C_i` — найгірший час виконання на самоті (WCET);
* `T_i` — період активації задачі (або мінімальний інтервал між спорадичними подіями);
* `D_i` — часовий дедлайн відносно моменту активації (вважаємо `D_i ≤ T_i`);
* `B_i` — максимальний час блокування задачі процесами нижчого пріоритету через спільні ресурси та критичні секції (англ. *Blocking Time*);
* `hp(i)` — множина індексів задач із пріоритетом, вищим за `τ_i`: `hp(i) = {j | Priority(τ_j) > Priority(τ_i)}`.

Гарантія працездатності системи полягає у виконанні умови для кожної задачі:

```
R_i ≤ D_i,  ∀ i ∈ {1, ..., n}
```

## Рівняння Джозефа і Пандьї

Повний час відгуку задачі `τ_i` складається з трьох компонентів: власного часу виконання `C_i`, часу очікування звільнення спільних ресурсів `B_i` та сумарного часу витіснення (англ. *Interference*) з боку всіх активних задач вищого пріоритету:

```
R_i = C_i + B_i + ∑_{j ∈ hp(i)} ⌈R_i / T_j⌉ · C_j
```

де `⌈x⌉` — функція округлення вгору (стеля), що визначає максимальну кількість разів, яку задача `τ_j` встигне активуватися і витіснити задачу `τ_i` за проміжок часу тривалістю `R_i`.

Оскільки невідома величина `R_i` входить як у ліву, так і в праву частину рівняння (під оператор округлення), рівняння є трансцендентним і розв'язується методом послідовних наближень (ітерацій з фіксованою точкою).

Ітераційний процес для задачі `τ_i` будується за рекурентною формулою:

```
R_i^(0) = C_i + B_i
R_i^(m+1) = C_i + B_i + ∑_{j ∈ hp(i)} ⌈R_i^(m) / T_j⌉ · C_j
```

Послідовність монотонно зростає: `R_i^(0) ≤ R_i^(1) ≤ R_i^(2) ≤ ...`. Ітерації завершуються в одному з двох випадків:

1. **Збіжність (успіх):** `R_i^(m+1) = R_i^(m)`. Знайдене значення є точним WCRT задачі. Якщо `R_i ≤ D_i`, задача гарантовано вкладається в дедлайн.
2. **Розбіжність (порушення дедлайну):** `R_i^(m+1) > D_i`. Подальші ітерації зупиняють, оскільки задача порушує дедлайн у найгіршому сценарії критичного моменту (англ. *Critical Instant*).

## Врахування часу блокування B_i

Якщо задачі використовують спільні ресурси (м'ютекси, черги, SPI/I2C транзакції), високопріоритетна задача `τ_i` може бути затримана задачею нижчого пріоритету `τ_k` (`k ∉ hp(i)`), яка встигла захопити ресурс до активації `τ_i`.

За умови використання протоколу успадкування пріоритетів (англ. *Priority Inheritance Protocol*, PIP) або протоколу стелі пріоритетів (англ. *Priority Ceiling Protocol*, PCP), час блокування обмежений тривалістю найдовшої критичної секції серед усіх низькопріоритетних задач, що використовують спільний ресурс із стелею пріоритету не меншою за пріоритет `τ_i`:

```
B_i = max { CS(k, r) | k ∉ hp(i), Ceiling(r) ≥ Priority(τ_i) }
```

де `CS(k, r)` — тривалість критичної секції задачі `τ_k` під захистом ресурсу `r`. За використання PCP кожна задача може зазнати блокування не більше ніж один раз за період.

## Покроковий числовий приклад розрахунку

Розглянемо систему керування мобільним роботом під керуванням RTOS на мікроконтролері ARM Cortex-M4 (168 МГц). У системі працюють три задачі:

1. **`τ_1` (Motor Control Loop):** період `T_1 = 1000` мкс, дедлайн `D_1 = 500` мкс, час виконання `C_1 = 150` мкс. Спільних ресурсів немає, тому `B_1 = 0` мкс.
2. **`τ_2` (Sensor Fusion / IMU EKF):** період `T_2 = 2500` мкс, дедлайн `D_2 = 2000` мкс, час виконання `C_2 = 400` мкс. Може блокуватися задачею `τ_3` на `B_2 = 80` мкс через м'ютекс доступу до шини I2C.
3. **`τ_3` (Telemetry / Radio Protocol):** період `T_3 = 10000` мкс, дедлайн `D_3 = 10000` мкс, час виконання `C_3 = 1200` мкс, час блокування `B_3 = 0` мкс (найнижчий пріоритет ніким не блокується знизу).

Загальне завантаження процесора:

```
U = (150 / 1000) + (400 / 2500) + (1200 / 10000)   [сума часток завантаження U_i = C_i / T_i]
  = 0.15 + 0.16 + 0.12                             [розрахунок часток кожної задачі]
  = 0.43                                           [сумарне завантаження ядра: 43%]
```

Завантаження становить лише 43%, що значно менше за класичну теоретичну межу Лю і Лейланда `3 · (2^(1/3) - 1) ≈ 77.9%`. Проте чи дотримуються дедлайни за найгіршого збігу фаз? Перевіримо за RTA.

### 1. Розрахунок для задачі τ_1 (найвищий пріоритет)

Оскільки над `τ_1` немає задач вищого пріоритету (`hp(1) = ∅`), витіснення відсутнє:

```
R_1 = C_1 + B_1
    = 150 + 0              [hp(1) порожня: немає вищих задач]
    = 150 мкс              [R_1 = 150 ≤ D_1 = 500: дедлайн виконано]
```

### 2. Розрахунок для задачі τ_2

Задача `τ_2` витісняється задачею `τ_1`. Застосовуємо ітераційну формулу:

```
R_2^(0)
= C_2 + B_2                [початкове наближення]
= 400 + 80
= 480 мкс

R_2^(1)
= C_2 + B_2 + ⌈R_2^(0) / T_1⌉ · C_1
= 480 + ⌈480 / 1000⌉ · 150  [480/1000 = 0.48, стеля = 1]
= 480 + 1 · 150
= 630 мкс

R_2^(2)
= 480 + ⌈630 / 1000⌉ · 150  [630/1000 = 0.63, стеля = 1]
= 480 + 1 · 150
= 630 мкс                  [R_2^(2) = R_2^(1): ітерації зійшлися]
```

Отримано `R_2 = 630` мкс. Оскільки `630 мкс ≤ D_2 (2000 мкс)`, дедлайн задачі `τ_2` гарантовано дотримується із запасом надійності `2000 - 630 = 1370` мкс.

### 3. Розрахунок для задачі τ_3 (найнижчий пріоритет)

Задача `τ_3` витісняється одночасно задачами `τ_1` та `τ_2`:

```
R_3^(0)
= C_3 + B_3                [початкове наближення]
= 1200 + 0
= 1200 мкс

R_3^(1)
= C_3 + B_3 + ⌈R_3^(0) / T_1⌉ · C_1 + ⌈R_3^(0) / T_2⌉ · C_2
= 1200 + ⌈1200 / 1000⌉ · 150 + ⌈1200 / 2500⌉ · 400
= 1200 + 2 · 150 + 1 · 400 [стелі: 1.2 -> 2, 0.48 -> 1]
= 1200 + 300 + 400
= 1900 мкс

R_3^(2)
= 1200 + ⌈1900 / 1000⌉ · 150 + ⌈1900 / 2500⌉ · 400
= 1200 + 2 · 150 + 1 · 400 [стелі: 1.9 -> 2, 0.76 -> 1]
= 1900 мкс                 [R_3^(2) = R_3^(1): ітерації зійшлися]
```

Отримано `R_3 = 1900` мкс. Оскільки `1900 мкс ≤ D_3 (10000 мкс)`, телеметрична задача також завжди встигає завершитися до кінця свого періоду.

## Вплив накладних витрат планувальника (Context Switch & Tick Overhead)

У реальних мікроконтролерах перемикання контексту RTOS не є безкоштовним: воно забирає час на збереження регістрів, роботу планувальника та завантаження контексту нової задачі. Позначимо час одного повного перемикання як `C_ctx` (зазвичай від 1.5 до 4 мкс на Cortex-M4).

Оскільки кожне витіснення задачею `τ_j` призводить до двох перемикань контексту (зі старої задачі на `τ_j` і назад після її завершення), узагальнене рівняння RTA набуває вигляду:

```
R_i = C_i + B_i + 2 · C_ctx + ∑_{j ∈ hp(i)} ⌈R_i / T_j⌉ · (C_j + 2 · C_ctx)
```

Врахування `C_ctx` підтверджує: навіть якщо чистий час виконання задачі малий, висока частота активації вищих задач (малий період `T_j`) може швидко вичерпати бюджет часу через накопичення накладних витрат планувальника.
