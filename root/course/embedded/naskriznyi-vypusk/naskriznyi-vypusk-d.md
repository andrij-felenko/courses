# Наскрізний випуск: від тегу в git до підписаного релізу у сховищі

<preknowlist>
- [CI для прошивки](root:embedded/firmware-ci) — алгебра вердикту, крос-збірка під кілька апаратних ревізій та автоматичний запуск тестів.
- [Семантичне версіонування](root:sf-release/semantic-versioning) — правила маркування версій `MAJOR.MINOR.PATCH` та їх зв'язок із сумісністю апаратури.
- [Відтворювані збірки](root:sys-bsystem/reproducible-builds) — усунення недетермінізму компілятора й фіксація середовища заради побайтової ідентичності.
- [Криптографія з відкритим ключем](root:sf-security/public-key-crypto) — асиметричні цифрові підписи (ECDSA, Ed25519) для перевірки цілісності образу завантажувачем.
</preknowlist>

Коли інженер збирає прошивку на власному ноутбуці, копіює отриманий файл `firmware.bin` на флешку або відправляє в чат цеху, виріб опиняється на межі катастрофи. На машині розробника міг стояти інший мінорний випуск компілятора, у локальному дереві міг випадково залишитися налагоджувальний коментар або незбережений прапорець оптимізації, а для підпису використано локальний ключ розробника замість виробничого. Результат такого «ручного релізу» — партія з десяти тисяч контролерів керування двигунами, що заблокувалися на етапі перевірки Secure Boot через помилку у зміщенні заголовка або отримали прошивку без захисту від збоїв живлення. Реліз у промисловій вбудованій системі — це не просто успішна компіляція коду; це неподільна транзакція, яка перетворює зафіксований стан репозиторію на підписаний, верифікований і задокументований пакет оновлення з повним обліком компонентів.

Наскрізний випуск (англ. *end-to-end release pipeline*) об'єднує всі розрізнені стадії розробки в єдиний детермінований ланцюг. Цей процес починається зі створення криптографічно засвідченого тегу в системі контролю версій, проходить крізь герметичну крос-компіляцію для всієї матриці апаратних ревізій, піраміду автоматичних тестів, взаємодію з апаратним модулем безпеки для накладання підпису, автоматичне формування цифрового паспорта компонентів (SBOM) і завершується публікацією в захищеному сховищі артефактів.

## Подія випуску: чому реліз починається з підписаного тегу

Звичайна щоденна збірка в гілці розробки запускається кожним новим комітом, перевіряючи працездатність змін. Випуск готового продукту підпорядковується іншій логіці: він вимагає свідомого рішення уповноваженого реліз-інженера, однозначної фіксації номера версії та захисту від несанкціонованої підміни коду в репозиторії.

Легковажний тег (англ. *lightweight tag*) у git — це лише пересувний покажчик на хеш коміту, який будь-хто з правом запису може змістити або створити заново. Натомість анотований і підписаний тег (англ. *annotated signed tag*, що створюється командою `git tag -s v2.4.0 -m "Release 2.4.0"`) є повноцінним криптографічним об'єктом у базі даних git. Він містить ім'я автора, мітку часу, повідомлення випуску та цифровий GPG- або SSH-підпис усього цього вмісту. У внутрішній базі об'єктів git такий тег зберігається як незмінний запис із прямим посиланням на цільовий коміт:

```
object 7a8f9c4b12d3e4f5a6b7c8d9e0f1a2b3c4d5e6f7
type commit
tag v2.4.0
tagger Olena Koval <o.koval@embedded-systems.ua> 1724803200 +0300

Production release v2.4.0 for Hardware Rev B and Rev C
-----BEGIN PGP SIGNATURE-----
iQIzBAABCAAdFiEEn5s8v2...
-----END PGP SIGNATURE-----
```

Коли сервер автоматизації фіксує подію появи нового тегу, спрацьовує перший бар'єр конвеєра — **ворота валідації тригера** (G1):

1. **Перевірка криптографічного підпису тегу.** Конвеєр витягує відкритий ключ автора тегу через команду `git tag -v v2.4.0` або `ssh-keygen -Y verify` й звіряє його з білим списком відкритих ключів реліз-інженерів компанії, зафіксованим у захищеному сховищі конфігурацій CI. Якщо тег створено без підпису або підписано ключем звичайного контриб'ютора, конвеєр негайно завершується з помилкою безпеки.
2. **Семантичний розбір версії.** Номер тегу має суворо відповідати специфікації [семантичного версіонування](root:sf-release/semantic-versioning) `v<MAJOR>.<MINOR>.<PATCH>`. Конвеєр розбирає рядок версії на складові числа: зміна `MAJOR` означає несумісність апаратури чи протоколу, `MINOR` додає нову функціональність зі збереженням сумісності, `PATCH` несе виправлення дефектів. Префікси на зразок `-rc1` або `-beta` переводять конвеєр у режим випуску тестового кандидата з іншим набором цільових сховищ.
3. **Перевірка захищеності гілки.** Конвеєр перевіряє, чи коміт, на який вказує тег, справді належить захищеній стабільній гілці (наприклад, `main` або `release/v2.x`), а не випадковій експериментальній гілці розробника. Для цього виконується перевірка предків коміту через `git merge-base --is-ancestor <commit-hash> origin/main`.
4. **Статус робочого дерева.** Вихідний код перевіряється на відсутність локальних непідтверджених змін (*dirty tree check*): утиліти на зразок `git describe --exact-match --dirty` мають повертати чистий рядок версії без суфіксів `-dirty` або додаткових зміщень комітів. Будь-який невідстежуваний файл або модифікований підмодуль git негайно блокує прогін.

Під час цієї фази система збірки генерує детермінований заголовочний файл версії `version_autogen.h`. Цей файл містить числові константи версії, розібрані з тегу, та хеш коміту, які вшиваються у бінарник як структуровані константи:

:::tabs
```c
#ifndef VERSION_AUTOGEN_H
#define VERSION_AUTOGEN_H

#define FW_VERSION_MAJOR 2
#define FW_VERSION_MINOR 4
#define FW_VERSION_PATCH 0
#define FW_COMMIT_HASH   0x7a8f9c4b
#define FW_VERSION_STR   "2.4.0"

#endif /* VERSION_AUTOGEN_H */
```
```cpp
#pragma once
#include <cstdint>
#include <string_view>

namespace version {

inline constexpr uint32_t Major = 2;
inline constexpr uint32_t Minor = 4;
inline constexpr uint32_t Patch = 0;
inline constexpr uint32_t CommitHash = 0x7a8f9c4b;
inline constexpr std::string_view String = "2.4.0";

} // namespace version
```
:::

Генерація такого заголовка не порушує відтворюваність збірки, оскільки його вміст є строгою математичною функцією від підписаного тегу та хешу коміту, а не від випадкового часу запуску сервера збірки.

> 🔧 **Навіщо це.** Якщо дозволити збирання релізів з довільного коміту чи гілки, у польові пристрої неминуче потрапить прошивка зі статусом «майже готово», зібрана з гілки функціоналу, яка ще не пройшла аудит. Підписаний тег зв'язує персональну відповідальність інженера, стан коду й номер версії в єдиний неподільний ланцюжок довіри.

## Герметична матрична крос-збірка для апаратних цілей

Промисловий виріб рідко існує в єдиній апаратній ревізії. За час життя продукту виробник змінює ревізії друкованих плат (наприклад, перехід із ревізії `rev_B` на `rev_C` через заміну застарілої мікросхеми Flash-пам'яті або зміну пінів UART на SPI), використовує різні типи мікроконтролерів для базових і розширених моделей або збирає окремі образи для завантажувача (Bootloader), основної програми (Application) та заводського тестування.

Релізний конвеєр виконує збірку для повної **матриці конфігурацій** (англ. *build matrix*). Для кожної комбінації цільової плати та компонента запускається ізольована крос-компіляція [закріпленим тулчейном](root:sys-bsystem/cross-compilation) (наприклад, `arm-none-eabi-gcc 13.2.rel1`). Конфігурація матриці описується у файлі пресетів CMake (`CMakePresets.json`), де кожен пресет інкапсулює прапорці компіляції під конкретний процесорний сердечник:

```json
{
  "version": 3,
  "configurePresets": [
    {
      "name": "prod-revB",
      "displayName": "Production Hardware Rev B",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/revB",
      "cacheVariables": {
        "CMAKE_TOOLCHAIN_FILE": "cmake/toolchain-arm-none-eabi.cmake",
        "HW_REVISION": "2",
        "TARGET_MCU": "STM32G474RE",
        "CMAKE_BUILD_TYPE": "MinSizeRel"
      }
    }
  ]
}
```

```
Матриця випуску:
├── Hardware Rev B (STM32G474RE, 512 KB Flash, 128 KB SRAM)
│   ├── bootloader-revB.bin
│   └── app-revB.bin
└── Hardware Rev C (STM32G484RE з апаратним криптомодулем)
    ├── bootloader-revC.bin
    └── app-revC.bin
```

Щоб гарантувати повну [відтворюваність збірки](root:sys-bsystem/reproducible-builds) (англ. *reproducible build*), середовище виконання примусово очищається від усіх джерел недетермінізму:

- **Фіксація часової мітки.** Змінна оточення `SOURCE_DATE_EPOCH` встановлюється в значення часу створення git-коміту (кількість секунд з 1 січня 1970 року). Компілятор, лінкер і пакувальники архівів використовують це значення замість поточного системного годинника раннера. Будь-які макроси `__DATE__` і `__TIME__` у коді забороняються прапорцем компілятора `-Werror=date-time`, щоб унеможливити випадкове потрапляння часу збірки у бінарний образ.
- **Нейтралізація файлових шляхів.** Прапорці компілятора `-fdebug-prefix-map=$PWD=.`, `-fmacro-prefix-map=$PWD=.` та `-ffile-prefix-map=$PWD=.` замінюють абсолютні шляхи до вихідних файлів на раннері відносними шляхами у налагоджувальних символах DWARF та макросах `__FILE__`. Два бінарники, зібрані в різних каталогах (`/builds/runner-01/repo` та `/builds/runner-02/repo`), стають побайтово ідентичними.
- **Стабільний порядок компонування.** Списки об'єктних файлів передаються лінкеру в строго відсортованому за алфавітом порядку. У скриптах лінкера застосовується директива `SORT_BY_NAME(.text*)` і `SORT_BY_ALIGNMENT(.rodata*)`, щоб порядок розміщення функцій і сталих не залежав від структури файлової системи раннера.
- **Очищення службових секцій.** Прапорці лінкера `-Wl,--build-id=none` або фіксація детермінованого build-id запобігають генеруванню випадкових хешів у заголовках ELF. Секції з відлагоджувальними символами відокремлюються у файл `.elf`, тоді як для пристрою генерується чистий бінарний образ `.bin` утилітою `arm-none-eabi-objcopy -O binary`.

Після генерації файлів `.elf` спрацьовують **ворота бюджету пам'яті** (G2). Утиліта `arm-none-eabi-size` або спеціальний скрипт аналізу розбирає карту пам'яті за секціями:

```
$ arm-none-eabi-size build/app-revB.elf
   text    data     bss     dec     hex filename
 184320    2048   24576  210944   33800 build/app-revB.elf
```

Конвеєр зіставляє розмір сегментів Flash (`text + data`) і RAM (`data + bss`) із жорсткою картою пам'яті цільового мікроконтролера. Якщо Flash-пам'ять пристрою має обсяг 256 КБ (262144 байти), а завантажувач займає перші 32 КБ, для програми залишається рівно 224 КБ (229376 байтів). Конвеєр перевіряє не лише загальний обсяг, але й мінімальний запас під стек (`_Min_Stack_Size = 0x2000`) та купу (`_Min_Heap_Size = 0x1000`). Якщо обсяг коду та сталих перевищує ліміт бодай на 1 байт, конвеєр падає з червоним вердиктом, не допускаючи формування дефектного образу.

Додатково проводиться статичний аналіз використання стеку (прапорець компілятора `-fstack-usage`). Скрипт перевірки обчислює максимальну глибину графа викликів функцій (*Call Graph Worst-Case Stack Depth*) для кожного потоку FreeRTOS. Якщо найгірший сценарій споживання стека перетинає позначку 80% від виділеного розміру стека завдання, конвеєр формує попередження або зупиняє збірку. Динамічне виділення пам'яті (`malloc`/`free`) у релізних конфігураціях для вбудованих систем повністю забороняється прапорцями лінкера, щоб унеможливити фрагментацію пам'яті під час тривалої автономної роботи.

## Піраміда верифікації перед воротами релізу

Релізний бінарник не може бути підписаний і опублікований без проходження багаторівневої піраміди перевірок. У CI-конвеєрі для вбудованих систем ця піраміда складається з трьох послідовних рівнів перевірки:

```
        /  HIL-тести на реальному залізі  \       (повільні, вичерпні)
       /   Емуляція чипа (QEMU / Renode)   \      (середня швидкість)
      / Модульні тести на хості (Ceedling)  \     (швидкі, ізольовані)
```

1. **Модульні тести на хост-системі (Unit Tests).** Збираються нативним компілятором `gcc` під архітектуру x86-64 з використанням мок-фреймворків (Unity/CMock). Вони перевіряють чисту бізнес-логіку: парсери пакетів, обчислення CRC/гешів, матричну математику та переходи кінцевих автоматів. Моки замінюють апаратні інтерфейси (регістри I2C, SPI, таймери), дозволяючи симулювати збої зв'язку, пошкодження даних та тайм-аути. Цей рівень відпрацьовує за секунди й ловить алгоритмічні дефекти.
2. **Емуляція системи на рівні команд (Emulator Integration).** Повний релізний двійковий образ для Cortex-M завантажується у віртуальний емулятор (Renode або QEMU). Емулятор запускає виконання з вектора скидання `Reset_Handler`, ініціалізує віртуальну Flash-пам'ять, SRAM та периферійні контролери (UART, SPI, таймери). Тест перевіряє поведінку системи на рівні машинних інструкцій: чи не виникає апаратного винятку `HardFault` під час ініціалізації стека, чи коректно працює релокація таблиці векторів переривань через регістр `SCB->VTOR`, чи своєчасно скидається сторожовий таймер (Watchdog) і чи відповідає прошивка на початкові команди протоколу через емульований послідовний порт. Скрипти Renode (`.resc`) автоматично створюють віртуальні периферійні давачі та перевіряють відповіді за протоколом Modbus чи CAN.
3. **Апаратний димовий тест (Hardware-in-the-Loop Smoke Test).** Образ автоматично прошивається у контрольний зразок плати на спеціальному стенді з апаратним програматором (J-Link / ST-Link) і керованим реле живлення. Конвеєр керує циклом живлення плати через протокол Modbus/SCPI, виконує прошивання через інтерфейс SWD утилітою OpenOCD або pyOCD і перехоплює телеметрію з виходу UART. Плата проходить повний цикл передачі керування від завантажувача до застосунку: завантажувач перевіряє цілісність Flash, копіює вектор скидання за адресою `0x08008004` в лічильник команд (PC), встановлює головний покажчик стека (MSP) зі значення за адресою `0x08008000` і передає керування. Стенд фіксує імпульси на контрольному виводі (Heartbeat Pin) через логічний аналізатор, підтверджуючи коректний запуск тактування PLL, і зчитує діагностичні логи самотестування (POST).

Лише коли всі три рівні повертають код виходу 0, відкриваються **ворота якості тестування** (G3), і збірка допускається до етапу криптографічного підпису. Детальна реалізація автоматизованого скрипту, який оркеструє цей прогін, наведена в [практичному конвеєрі випуску](root:embedded/naskriznyi-vypusk/proj-pipeline.md).

## Межа довіри та ізоляція ключів підпису

Ключовий парадокс автоматизованого випуску полягає у безпеці: конвеєр має автоматично підписувати реліз виробничим ключем, але приватний ключ підпису ні за яких умов не повинен потрапляти у відкрите середовище раннера збірки.

Раннер CI — це динамічне, потенційно вразливе середовище. Він завантажує сторонні залежності з інтернету, виконує скрипти компіляції та взаємодіє з багатьма сервісами. Якщо зберегти приватний ключ у змінних оточення раннера (`CI_PRIVATE_KEY`), будь-яка скомпрометована залежність або шкідливий коміт зможуть викрасти цей ключ. Компрометація кореневого ключа підпису прошивки означає повну втрату довіри до всього парку пристроїв: зловмисник зможе випускати шкідливі оновлення, які завантажувач пристроїв вважатиме легітимними.

Для розв'язання цього парадоксу застосовують **протокол підпису без передачі ключа** (англ. *isolated hash-and-sign protocol*).

![Ізоляція ключів підпису](/root/course/embedded/naskriznyi-vypusk/img/signing-isolation.svg)
*Межа довіри між недовіреним раннером збірки та апаратним модулем безпеки HSM/KMS. Раннер обчислює лише SHA-256 хеш двійкового образу, а HSM накладає підпис після перевірки OIDC-токенів.*

Механізм працює за суворим протоколом:

1. Раннер збірки створює скомпільований двійковий файл образу `firmware.raw.bin`.
2. Раннер самостійно обчислює криптографічний дайджест цього файлу за алгоритмом SHA-256:
   ```
   Digest = SHA-256(firmware.raw.bin)
   ```
3. Раннер генерує короткоживучий криптографічний OIDC-токен (OpenID Connect), який підтверджує: запит надходить саме з офіційного захищеного конвеєра, для захищеної гілки, від імені верифікованого тегу `v2.4.0`.
4. Раннер надсилає мережевий запит до захищеного сервісу підпису (апаратного модуля безпеки HSM, хмарного AWS KMS або HashiCorp Vault). У запиті передається **тільки 32-байтний дайджест** (хеш) та OIDC-токен через стандартизований інтерфейс PKCS#11 (Cryptoki) або REST API.
5. HSM перевіряє права доступу за токеном і накладає цифровий підпис на отриманий дайджест за допомогою закритого асиметричного ключа (ECDSA з кривою secp256r1 або Ed25519), що зберігається в захищеній кремнієвій матриці чипа. Приватний ключ фізично неможливо витягнути з HSM.
6. HSM повертає раннеру 64-байтний цифровий підпис `Signature`.
7. Утиліта пакування на раннері формує фінальний підписаний бінарник `firmware.signed.bin`, вшиваючи підпис і метадані у спеціальний заголовок Secure Boot перед початком коду або в кінець файлу.

Вибір криптографічного алгоритму визначається можливостями цільового завантажувача. Алгоритм ECDSA на еліптичній кривій NIST P-256 (secp256r1) підтримується апаратними криптоприскорювачами більшості сучасних мікроконтролерів (STM32, NXP LPC, ESP32-S3), забезпечуючи перевірку за 15–25 мілісекунд без суттєвого навантаження на процесор. Алгоритм Ed25519 забезпечує вищу математичну стійкість проти атак побічними каналами й компактніший розмір програмного коду верифікації в завантажувачі (менше 4 КБ Flash для бібліотеки ed25519-donna). Обчислення гешу для образу розміром 256 КБ займає близько 20 мс при тактовій частоті 168 МГц, що гарантовано вкладається у тайм-аут апаратного сторожового таймера (IWDG) під час першого запуску.

## Генерація цифрового паспорта компонентів (SBOM)

Сучасні міжнародні стандарти кібербезпеки вбудованих систем (зокрема директива ЄС Cyber Resilience Act та стандарт ETSI EN 303 645) вимагають обов'язкової наявності цифрового паспорта компонентів — **SBOM** (англ. *Software Bill of Materials*).

SBOM — це машиночитний структурний документ (у форматах CycloneDX або SPDX JSON), який фіксує повну інвентаризацію всіх складових частин прошивки:

- Версія ядра операційної системи реального часу (наприклад, `FreeRTOS v10.5.1`).
- Версії вендорських бібліотек драйверів апаратного рівня (STM32 HAL / LL v1.11.0 або ESP-IDF v5.2.1).
- Сторонні криптографічні та мережеві бібліотеки (mbedTLS v3.4.0, lwIP v2.1.3).
- Точна назва та хеш компілятора й стандартної бібліотеки мови C (`newlib-nano v4.3.0`).
- Відомі ідентифікатори ліцензій (MIT, BSD-3-Clause, Apache-2.0).

Під час випуску спеціальний сканер конвеєра аналізує файл проекту CMake, файл блокування залежностей і таблицю символів зібраного ELF-файлу, генеруючи файл `firmware.sbom.json`. Наявність SBOM дозволяє автоматизованим сканерам безпеки миттєво ідентифікувати пристрої у полі, щойно у публічній базі CVE з'являється інформація про нову вразливість у використаній версії mbedTLS чи FreeRTOS.

Поруч зі SBOM генерується **атестація походження артефакту** за стандартом SLSA (англ. *Supply-chain Levels for Software Artifacts*). Атестація містить криптографічний доказ того, що бінарник із конкретним хешем було зібрано саме в цьому репозиторії, на довіреному сервері збірки, із зафіксованими вхідними параметрами, що захищає ланцюг постачання ПЗ від атак підміни бінарників третіми сторонами. Документ атестації підписується за допомогою інструментів Sigstore / Cosign і публікується в прозорому журналі аудиту (Rekor).

## Анатомія криптографічного пакета випуску

Випуск не може бути «голим» файлом із розширенням `.bin` чи `.hex`. Пристрій у полі або сервер оновлень повинен отримати цілісний криптографічний бандл, який містить усі необхідні елементи для безпечної верифікації та встановлення.

![Анатомія пакета випуску](/root/course/embedded/naskriznyi-vypusk/img/release-bundle.svg)
*Структура релізного бандла: двійковий образ із заголовком Secure Boot, криптографічний маніфест сумісності та паспорт компонентів SBOM.*

Пакет випуску формується у вигляді єдиного архіву або підписаного контейнера, що містить такі артефакти:

1. **Підписаний двійковий образ (`firmware.signed.bin`).** Містить префіксний заголовок Secure Boot:
   - Магічне число (Magic Word), наприклад `0x53424F54` ("SBOT").
   - Номер версії прошивки (32 біти), закодований у форматі `(MAJOR << 24) | (MINOR << 16) | (PATCH << 8)`.
   - Лічильник захисту від відкату версії (англ. *anti-rollback security counter*). Якщо у пристрої апаратні одноразові запобіжники eFuse прошиті значенням 3, завантажувач відхилить будь-який підписаний образ із лічильником менше 3, навіть якщо криптографічний підпис бездоганний. Це захищає парк від атак типу «відкат до відомої вразливої версії».
   - Розмір корисного навантаження (Payload Size) у байтах.
   - Маска сумісності апаратних ревізій (Hardware Compatibility Mask).
   - Прапорці конфігурації (шифрування Flash, режим A/B банку).
   - 32-байтний SHA-256 дайджест тіла програми.
   - 64-байтний криптографічний підпис заголовка й тіла.
2. **Криптографічний маніфест випуску (`manifest.json`).** Зовнішній документ, що описує сумісність: ідентифікатор продукту, сумісні ревізії друкованих плат (`["rev_B", "rev_C"]`), розмір і контрольні суми всіх бінарників, адреси цільових розділів Flash-пам'яті, посилання на нотатки релізу. Сам файл `manifest.json` додатково підписується окремим цифровим підписом.
3. **Паспорт компонентів (`firmware.sbom.json`).** Цифровий перелік бібліотек і ліцензій.
4. **Налагоджувальні символи (`firmware.elf` / `firmware.map`).** Зберігаються у захищеному сховищі символів інженерної команди для подальшого аналізу аварійних дампів пам'яті (HardFault coredump), але ніколи не передаються кінцевому користувачу.

У системах з двома банками Flash-пам'яті (Dual-Bank A/B Boot) маніфест також визначає цільовий слот для запису нової прошивки. Завантажувач спочатку записує образ у неактивний банк пам'яті (Slot 1), перевіряє підпис, встановлює прапорець тестування `BOOT_STATE_TESTING` і перезавантажує пристрій. Якщо нова прошивка успішно запускається, проходить внутрішню самодіагностику й скидає таймер підтвердження викликом `boot_confirm()`, статус змінюється на `BOOT_STATE_CONFIRMED`. Якщо ж виникає `HardFault` або зависання, апаратний Watchdog перезавантажує контролер, і завантажувач автоматично повертається до стабільного попереднього образу в Slot 0. Завдяки апаратній підтримці перемикання банків (наприклад, біт `nDBANK` у конфігураційних регістрарах Flash мікроконтролера STM32) зміна активного банку виконується миттєво без ризику пошкодження при раптовому вимкненні живлення під час оновлення.

Повна схема полів маніфесту та бінарного заголовка стандартизована у [специфікації маніфесту релізу](root:embedded/naskriznyi-vypusk/api-manifest.md).

## Клієнтська верифікація маніфесту на стороні пристрою

Перед тим як записати нові байти у Flash-пам'ять, завантажувач або агент оновлення пристрою зобов'язаний виконати валідацію маніфесту та образу. Зчитування виконується потоковими блоками (наприклад, по 512 байтів), щоб не перевантажувати обмежену оперативну пам'ять мікроконтролера, а SHA-256 дайджест оновлюється інкрементально через криптографічний контекст.

Ось як виглядає еталонна логіка перевірки сумісності апаратури, лічильника безпеки та контрольної суми перед застосуванням оновлення:

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

#define SECURE_BOOT_MAGIC 0x53424F54
#define HW_REV_CURRENT    0x0002 /* Hardware Rev B */

typedef struct {
    uint32_t magic;
    uint32_t version_code;
    uint32_t security_counter;
    uint32_t hw_compatibility_mask;
    uint32_t payload_size;
    uint8_t  sha256_digest[32];
    uint8_t  signature[64];
} __attribute__((packed)) ImageHeader;

typedef enum {
    VERIFY_OK = 0,
    ERR_BAD_MAGIC,
    ERR_HW_INCOMPATIBLE,
    ERR_ROLLBACK_DETECTED,
    ERR_IMAGE_TOO_LARGE,
    ERR_DIGEST_MISMATCH
} VerifyResult;

VerifyResult verify_release_header(const ImageHeader *hdr,
                                   uint32_t current_efuse_counter,
                                   uint32_t max_flash_size) {
    if (hdr->magic != SECURE_BOOT_MAGIC) {
        return ERR_BAD_MAGIC;
    }

    /* Перевірка сумісності з поточною апаратною ревізією */
    if ((hdr->hw_compatibility_mask & (1U << HW_REV_CURRENT)) == 0) {
        return ERR_HW_INCOMPATIBLE;
    }

    /* Захист від відкату версії (anti-rollback) */
    if (hdr->security_counter < current_efuse_counter) {
        return ERR_ROLLBACK_DETECTED;
    }

    /* Перевірка лімітів пам'яті */
    if (hdr->payload_size > max_flash_size) {
        return ERR_IMAGE_TOO_LARGE;
    }

    return VERIFY_OK;
}
```

#include <cstdint>
#include <span>
#include <expected>
#include <array>

namespace release {

inline constexpr uint32_t SecureBootMagic = 0x53424F54;
inline constexpr uint32_t CurrentHwRevision = 0x0002; // Hardware Rev B

struct alignas(4) ImageHeader {
    uint32_t magic;
    uint32_t versionCode;
    uint32_t securityCounter;
    uint32_t hwCompatibilityMask;
    uint32_t payloadSize;
    std::array<uint8_t, 32> sha256Digest;
    std::array<uint8_t, 64> signature;
};

enum class VerifyError {
    BadMagic,
    HwIncompatible,
    RollbackDetected,
    ImageTooLarge,
    DigestMismatch
};

[[nodiscard]] std::expected<void, VerifyError> verifyReleaseHeader(
    const ImageHeader& hdr,
    uint32_t currentEfuseCounter,
    uint32_t maxFlashSize) noexcept {
    
    if (hdr.magic != SecureBootMagic) {
        return std::unexpected(VerifyError::BadMagic);
    }

    if ((hdr.hwCompatibilityMask & (1U << CurrentHwRevision)) == 0) {
        return std::unexpected(VerifyError::HwIncompatible);
    }

    if (hdr.securityCounter < currentEfuseCounter) {
        return std::unexpected(VerifyError::RollbackDetected);
    }

    if (hdr.payloadSize > maxFlashSize) {
        return std::unexpected(VerifyError::ImageTooLarge);
    }

    return {};
}

} // namespace release

## Атомна публікація та дистрибуція релізу

Останній етап конвеєра — публікація готового пакету у корпоративне сховище релізів (AWS S3 з увімкненим Object Lock, JFrog Artifactory або внутрішній MinIO-кластер).

Головна вимога до публікації — **атомність операції**. Неприпустима ситуація, коли бінарник уже завантажився у сховище, а завантаження маніфесту обірвалося через збій мережі: пристрої почнуть опитувати сервер оновлень і отримуватимуть пошкоджену інформацію.

Публікація реалізується за чотирифазним протоколом:

1. **Фаза підготовки (Staging Phase).** Усі файли релізного бандла (`firmware.bin`, `manifest.json`, `firmware.sbom.json`) завантажуються у тимчасовий каталог сховища з унікальним префіксом ідентифікатора прогону:
   ```
   s3://releases-bucket/staging/run-84920-v2.4.0/
   ```
2. **Фаза верифікації сховища (Integrity Verification).** Скрипт конвеєра зчитує завантажені файли безпосередньо зі сховища через незалежне з'єднання, перераховує їхні SHA-256 хеші та звіряє їх із локальними значеннями, зафіксованими у маніфесті.
3. **Фаза фіксації (Commit Phase).** Виконується атомарне переміщення (або перемикання символічного покажчика/маніфесту) у постійне виробниче дерево релізів:
   ```
   s3://releases-bucket/products/device-node/v2.4.0/
   ```
   На рівні бакета активується політика `Object Lock Compliance Mode`: видалити чи перезаписати файли у каталозі `v2.4.0/` стає неможливо навіть для адміністратора хмари протягом встановленого терміну збереження (наприклад, 5 років).
4. **Сповіщення платформи оновлень (OTA Trigger).** Конвеєр викликає захищений webhook системи керування парком пристроїв (наприклад, Eclipse hawkBit, RAUC або власного бекенду), передаючи підписаний URL нового маніфесту.

Для зменшення мережевого трафіку під час оновлення парку пристроїв через стільникові канали зв'язку (LTE-M / NB-IoT) на цьому етапі може додатково генеруватися **дельта-патч** (бінарна різниця між попередньою стабільною версією `v2.3.9` та новою `v2.4.0` за алгоритмом Courgette або BSDiff). Дельта-патч підписується окремим цифровим підписом і додається до маніфесту як альтернативний компактний варіант оновлення, що дозволяє зменшити розмір завантаження на 80–90%.

Порівняння різних топологій організації сховищ і підпису прошивок наведено в [порівнянні архітектур підпису](root:embedded/naskriznyi-vypusk/comp-signing-topologies.md).

## Крайові випадки, збої та аварійне скасування

Промисловий конвеєр повинен передбачати нештатні ситуації на кожній ланці процесу:

- **Збій зв'язку з HSM під час підпису.** Якщо апаратний модуль підпису тимчасово недоступний (мережевий тайм-аут або вичерпання квоти запитів), конвеєр не повинен намагатися підписати файл резервним локальним ключем. Єдина правильна дія — аварійна зупинка конвеєра, очищення тимчасових файлів і сповіщення чергового інженера.
- **Спроба повторного пушу тегу.** Якщо хтось видалив старий git-тег `v2.4.0` і створив його знову на іншому коміті, сховище артефактів завдяки політиці незмінності (англ. *immutability / Object Lock*) заблокує перезапис вже наявних файлів версії `v2.4.0`. Версія, що одного разу потрапила у сховище, ніколи не може бути замінена або модифікована — будь-яке виправлення вимагає нового тегу `v2.4.1`.
- **Екстрений відклик релізу (Revocation).** Якщо після публікації в прошивці виявлено критичну вразливість або апаратну несумісність, реліз не видаляється зі сховища (щоб не ламати історію аудиту). Натомість сервер оновлень публікує оновлений список відкликаних версій (CRL / Revocation List), а наступний патч `v2.4.1` збільшує лічильник anti-rollback, назавжди блокуючи встановлення відкликаної версії на пристроях.
- **Невідповідність апаратної ревізії на виробництві.** Якщо заводський тест-стенд виявляє спробу прошити образ `app-revB.bin` на друковану плату з маркуванням `rev_C`, завантажувач завдяки масці сумісності відхиляє прошивку до початку стирання Flash-пам'яті, запобігаючи перетворенню плати на непрацездатний модуль.
- **Термінові хотфікси (Hotfix Pipeline).** Якщо в польових пристроях виявлено критичний дефект, що зупиняє роботу, реліз-гілка `hotfix/v2.4.1` відгалужується безпосередньо від підписаного тегу `v2.4.0`. Вона містить виключно мінімальний точковий патч без нових функцій. Конвеєр випуску проходить повний цикл перевірок G1–G5 з ідентичною суворістю, зберігаючи безперервний аудиторський ланцюжок довіри. У разі екстреного випуску хотфіксу конвеєр автоматично генерує новий SBOM та SLSA-атестацію для виправленої версії `v2.4.1`, зберігаючи в маніфесті посилання на батьківський реліз `v2.4.0` та ідентифікатор інциденту. Це гарантує, що навіть у стані кризи процес випуску залишається прозорим, керованим і захищеним від несанкціонованих правок.

Наскрізний випуск перетворює реліз із ризикованої ручної процедури на повністю детермінований інженерний конвеєр. Кожен бінарник, що потрапляє у пристрій, отримує повний родовід: від підтвердженого підписом коміту в git до криптографічного сертифіката безпеки у сховищі.
