# 🔌 Порівняння топологій підпису прошивки та сховищ релізів

Безпека вбудованої системи тримається на надійності закритого ключа, яким підписуються образи прошивки. Якщо цей ключ потрапляє до рук зловмисника, всі криптографічні бар'єри Secure Boot втрачають сенс: зловмисник отримує можливість створювати шкідливі оновлення, які завантажувач мікроконтролера сприйматиме як офіційні та легітимні.

Вибір архітектури підпису визначає баланс між швидкістю автоматизованого випуску в конвеєрах CI/CD та рівнем захисту кореневих секретів. Нижче наведено детальний аналіз чотирьох основних топологій організації підпису та сховищ релізів у промисловій розробці.

## 1. Повністю ізольована офлайн-станція (Air-Gapped Workstation)

У цій топології приватний ключ зберігається на фізичному криптографічному токені (наприклад, YubiKey або Nitrokey HSM), підключеному до комп'ютера, який фізично відрізаний від будь-яких локальних та глобальних комп'ютерних мереж (Air-Gap).

Процедура випуску вимагає ручної участі двох уповноважених офіцерів безпеки (принцип Four-Eyes):

1. Конвеєр CI збирає бінарний образ `firmware.raw.bin` та обчислює його SHA-256 хеш.
2. Інженер переносить хеш на ізольовану станцію за допомогою одноразового оптичного носія (CD-R) або USB-накопичувача з апаратним захистом від запису.
3. Офіцери безпеки вводять персональні PIN-коди на апаратному токені, генеруючи цифровий підпис.
4. Підпис переноситься назад у конвеєр для фінального пакування релізного бандла.

**Переваги:** абсолютний захист від дистанційних мережевих атак та витоків через скомпрометовані залежності конвеєра CI.

**Недоліки:** високі операційні витрати, неможливість частого нічного випуску проміжних збірок, людський фактор при копіюванні файлів.

## 2. Хмарний модуль безпеки з OIDC-довірою (Cloud KMS / HSM)

Сучасний стандарт для розподілених команд. Закритий ключ генерується всередині хмарного модуля безпеки з сертифікацією FIPS 140-3 Level 3 (наприклад, AWS KMS, Google Cloud KMS або Azure Key Vault) і апаратно захищений від експорту.

Раннер збірки під час спрацювання git-тегу отримує короткоживучий OIDC-токен (OpenID Connect), що засвідчує його ідентичність. Раннер надсилає 32-байтний SHA-256 хеш прошивки через REST API до сервісу KMS. Модуль KMS перевіряє claims у токені (ім'я репозиторію, посилання на тег, статус перевірки GPG-підпису) і повертає криптографічний підпис без передачі закритого ключа на раннер.

**Переваги:** повна автоматизація без участі людини, миттєве накладання підпису (менше 200 мс), строгий аудит кожного виклику в журналах AWS CloudTrail або Cloud Logging.

**Недоліки:** залежність від хмарного провайдера, необхідність постійного доступу до інтернету для серверів збірки.

## 3. Локальний мережевий апаратний HSM (On-Premises Network HSM)

Використовується на оборонних, медичних та критичних інфраструктурних підприємствах, де політика безпеки забороняє винесення криптографічних операцій у публічні хмари. Апаратний модуль (наприклад, Thales Luna HSM або Utimaco CryptoServer) встановлюється в захищеній серверній стійці в ізольованому сегменті локальної мережі (VLAN).

Конвеєр збірки взаємодіє з HSM через стандартизований інтерфейс PKCS#11 (Cryptoki) по зашифрованому каналу TLS з двосторонньою автентифікацією за сертифікатами (mTLS).

**Переваги:** повний контроль над фізичним обладнанням, висока продуктивність (тисячі підписів на секунду), відповідність найсуворішим галузевим стандартам (Common Criteria EAL4+).

**Недоліки:** дуже висока вартість обладнання та ліцензій, необхідність власної команди сертифікованих адміністраторів безпеки.

## 4. Відкладений підпис на виробничій лінії (Factory-Floor Provisioning)

У цій схемі центральний конвеєр випускає лише базові тестові образи або прошивки з проміжним ключем розробки. Фінальний підпис виробничим ключем накладається безпосередньо на заводському стенді програмування під час фінального складання друкованої плати.

Стенд прошивки під'єднується до заводського захищеного сервера ініціалізації (Provisioning Server), який генерує унікальні сертифікати пристрою, записує відкритий ключ у захищені одноразові запобіжники eFuse мікроконтролера та накладає підпис на виробничий образ.

**Переваги:** можливість персоналізації кожного окремого екземпляра пристрою унікальними криптографічними ключами та сертифікатами під час виробництва.

**Недоліки:** висока складність оркестрації на сторонніх контрактних виробництвах, ризик фізичного викрадення заводського програматора з авторизованими правами.

## Порівняльна матриця архітектурних топологій

| Критерій оцінки | Офлайн Air-Gap | Хмарний KMS (OIDC) | Мережевий HSM (LAN) | Заводський підпис |
|:---|:---|:---|:---|:---|
| **Рівень захисту ключа** | Найвищий (ізоляція) | Високий (FIPS 140-3 L3) | Найвищий (FIPS/CC) | Середній (ризик фабрики) |
| **Швидкість випуску** | Години / дні | Секунди (<1 с) | Мілісекунди (<50 мс) | Хвилини на партію |
| **Ступінь автоматизації** | Ручний (Four-Eyes) | Повна (CI/CD) | Повна (CI/CD) | Автоматична на стенді |
| **Стійкість до компрометації CI** | Абсолютна | Висока (через OIDC) | Висока (через mTLS) | Висока |
| **Капітальні витрати (CapEx)** | Мінімальні (<$1000) | Нульові (Pay-as-you-go) | Дуже високі (>$30,000) | Високі (оснащення лінії)|
| **Відповідність CRA / IEC 62443** | Повна | Повна | Повна | Потребує аудиту цеху |

## Рекомендації щодо вибору топології

Для більшості сучасних комерційних пристроїв Інтернету речей (IoT) та промислової автоматики оптимальним вибором є **хмарний KMS з OIDC-автентифікацією**: він забезпечує максимальну швидкість випуску регулярних оновлень безпеки при збереженні гарантій захисту ключа від викрадення.

Для виробів вищого класу критичності (авіоніка, автомобільні блоки керування за стандартом ISO 21434, медичне обладнання) рекомендується гібридна схема: хмарний або локальний мережевий HSM для випуску тестових і проміжних кандидатур, та ізольована станція **Air-Gap** для затвердження фінальних сертифікаційних релізів.
