# Втрата ключа підпису: парк, який більше ніколи не оновиш

<preknowlist>
- [Криптографія з відкритим ключем](root:sf-security/public-key-crypto) — асиметричні пари ключів, математика перевірки цифрового підпису та ланцюг довіри.
- [Де живе приватний ключ](root:sf-security/de-zhyve-pryvatnyi-kliuch) — апаратні модулі безпеки (HSM), токени та наслідки фізичної втрати чи компрометації закритого ключа.
- [Церемонія ключів](root:embedded/tseremoniia-kliuchiv) — розділений секрет (схема Шаміра), офлайн-генерація кореня довіри та процедури резервування.
- [Замкнути зневаджувач: фьюзи й рівні захисту](root:sys-ide/avr-fuses) — одноразово програмовані біти (eFuses / OTP), незворотне спалювання та блокування апаратних інтерфейсів зневадження (JTAG/SWD).
</preknowlist>

Компанія випускає у промислову експлуатацію партію з 50 000 автономних вуличних лічильників газу або контролерів сонячних електростанцій, розсіяних по всій території країни. Під час фінального заводського тестування на кожному мікроконтролері активують апаратний захист: у комірки одноразово програмованої пам'яті eFuse (від англ. *electronic fuse* — електронний запобіжник) фізично перепалюють кремнієві перемички, зашиваючи 256-бітний криптографічний хеш SHA-256 відкритого ключа виробника. Щоб захистити комерційну прошивку від зчитування конкурентами, апаратні лінії інтерфейсів зневадження JTAG та SWD намертво блокують тим самим механізмом eFuse. Від цієї миті пристрій готовий приймати оновлення коду виключно через радіоканал (OTA, англ. *Over-The-Air*), якщо новий бінарний образ засвідчено відповідним цифровим підписом.

Минає три роки бездоганної роботи. Стається побутова технічна подія: єдиний захищений ноутбук головного архітектора безпеки виходить із ладу внаслідок відмови накопичувача, а апаратний USB-токен із закритим ключем губиться під час переїзду офісу. Резервні копії або не створювалися, або були зашифровані паролем, який знала лише одна людина, що вже звільнилася з компанії. Водночас у мережевій бібліотеці TLS або стеку обробки протоколу виявляють критичну вразливість нульового дня (RCE, Remote Code Execution), яка дозволяє перехоплювати керування над лічильниками, або в хмарного бекенду спливає термін дії кореневого сертифіката X.509, що вимагає негайного оновлення адрес та сертифікатів у прошивці.

Інженерна команда швидко виправляє код, генерує нову пару криптографічних ключів, компілює свіжий релізний образ і запускає конвеєр бездротового оновлення. Проте всі 50 000 пристроїв одночасно відхиляють оновлення: внутрішній апаратний завантажувач у кремнії зчитує новий відкритий ключ із заголовка пакета, обчислює його хеш, порівнює його з незмінним значенням в eFuse і фіксує невідповідність. Завантажувач миттєво відкидає образ і повертається до виконання старого коду. Парк перетворюється на «живих мерців» (англ. *unpatchable orphaned fleet*): пристрої продовжують працювати, але жоден біт коду в них більше неможливо змінити дистанційно. Щоб повернути контроль над системою, залишається єдиний шлях — фізичний демонтаж кожного приладу, зняття пломб, випаювання мікроконтролера феном гарячого повітря та заміна його на новий чіп, вартість чого багаторазово перевищує весь бюджет проекту.

### Анатомія кремнієвого замка: чому компроміс неможливий

Щоб зрозуміти, чому завантажувач у полі відмовляється від будь-яких компромісів, необхідно простежити фізичний ланцюг перевірки, закладений у кремнієву структуру чіпа на етапі виробництва напівпровідникової пластини.

У сучасних 32-бітних мікроконтролерах (наприклад, STM32 із захистом SBSFU, NXP i.MX із High Assurance Boot, ESP32-S3 із Secure Boot v2 або чіпах Nordic nRF53) першим кодом, який отримує керування після зняття сигналу скидання (Reset), є нульовий завантажувач — ROM Bootloader. Цей код фізично замаскований у металевих шарах кремнію (Mask ROM). Його неможливо переписати, стерти чи модифікувати жодною програмною командою.

```
+-----------------------------------------------------------------------------+
|                                КРЕМНІЙ MCU                                  |
|                                                                             |
|  +--------------------+        +--------------------+                       |
|  |     Mask ROM       |------->|  Апаратний SHA-256 |                       |
|  |   (Zero-Stage)     |        +--------------------+                       |
|  +--------------------+                  |                                  |
|            |                             | Digest_PK                        |
|            v                             v                                  |
|  +--------------------+        +--------------------+      +-------------+  |
|  |     eFuse OTP      |------->|     Апаратний      |----->|  Успіх /    |  |
|  | SHA-256(PK_root)   |        |    компаратор      |      |  Блокування |  |
|  +--------------------+        +--------------------+      +-------------+  |
+-----------------------------------------------------------------------------+
```

Коли активується режим безпечного завантаження (Secure Boot), поведінка ROM Bootloader визначається комірками одноразово програмованої пам'яті OTP (англ. *One-Time Programmable*), реалізованими у вигляді матриці eFuse. Фізично комірка eFuse являє собою мікроскопічну кремнієву або полікремнієву перемичку, захищену оксидним шаром. У заводському стані перемичка проводить струм (логічний `0`). Під час операції програмування на комірку подається калібрований високовольтний імпульс струму від вбудованого генератора підкачування заряду (Charge Pump, наприклад, 2.5 В або 3.3 В). Перемичка фізично розплавляється і випаровується, створюючи незворотний розрив електричного кола (логічна `1`).

Фізика напівпровідників робить зворотний процес — перетворення спаленого розриву назад у суцільний провідник — абсолютно неможливим. Жодне опромінення ультрафіолетом, перепад температур чи зміна напруги не здатні відновити розплавлений полікремній.

![Кремнієвий замок апаратної верифікації прошивки в ROM та eFuse OTP](/root/course/embedded/vtrata-kliucha-pidpysu/img/hardware-boot-lock.svg)
*Кремнієвий замок апаратної верифікації: порівняння хешу відкритого ключа з незмінним еталоном в eFuse OTP.*

Під час кожного старту або спроби оновлення ROM Bootloader виконує жорстко заданий алгоритм:
1. Завантажувач зчитує з Flash-пам'яті заголовок нової прошивки, де розташований відкритий криптографічний ключ підписувача `PK_image`.
2. За допомогою вбудованого апаратного криптографічного прискорювача обчислюється 256-бітний дайджест: `Digest_PK = SHA-256(PK_image)`.
3. Апаратний компаратор побайтово порівнює обчислений `Digest_PK` зі значенням `Digest_eFuse`, намертво записаним у комірки eFuse чіпа.
4. Якщо виявлено невідповідність хоча б в одному біті, виконання програми апаратно блокується: процесор або переходить у нескінченний цикл очікування переривань (`WFI` / `HLT`), або викликає безпечне апаратне скидання (Secure Reset), відмовляючись передавати керування на вектор скидання Flash.

Така безапеляційність є фундаментальною вимогою моделі загроз. Якби в завантажувачі існувала будь-яка інженерна шпарина — «сервісний пароль», резервна комбінація сигналів на ніжках GPIO або недокументована команда UART, що дозволяє обійти перевірку хешу відкритого ключа, — цей механізм миттєво став би головною мішенню для зловмисників. Знайшовши цей бекдор, атакуючий зміг би завантажити шкідливу прошивку в будь-який пристрій без наявності закритого ключа виробника. Захищаючи пристрій від чужих, Secure Boot робить його беззахисним перед людською недбалістю своїх творців.

Крім того, апаратні модулі сучасних мікроконтролерів містять захист від атак за сторонніми каналами та збійних ін'єкцій (Fault Injection / Glitching). Коли процесор виконує компаратор хешів, апаратні схеми повторюють порівняння кілька разів із випадковими часовими затримками (Jittered Delays) та перевіряють інвертовані копії регістрів. Тому спроби підкинути збій живлення (Voltage Glitch) або тактового сигналу (Clock Glitch), щоб примусити умовний перехід пропустити перевірку `Digest_PK == Digest_eFuse`, блокуються кремнієвою логікою на апаратному рівні.

### Дві грані катастрофи: Втрата доступу проти Витоку ключа

Криптографічний ключ підпису володіє двома критичними властивостями: доступністю (Availability) та конфіденційністю (Confidentiality). Порушення будь-якої з них призводить до катастрофи, проте механіка руйнування бізнесу в цих випадках відрізняється.

```
                           +-------------------------------+
                           |     ЗАКРИТИЙ КЛЮЧ ПІДПИСУ     |
                           +-------------------------------+
                                          |
                   +----------------------+----------------------+
                   |                                             |
                   v                                             v
       +-----------------------+                     +-----------------------+
       |   ВТРАТА ДОСТУПНОСТІ  |                     |  ВИТІК КОНФІДЕНЦІЙНОСТІ|
       |  (Знищення / Втрата)  |                     |   (Крадіжка / Злам)   |
       +-----------------------+                     +-----------------------+
                   |                                             |
                   v                                             v
       • Замок назавжди замкнено                     • Замок відкрито для всіх
       • Парк неможливо оновити                      • Фальшиві оновлення від ворога
       • Вразливості накопичуються                   • Перехоплення контролю / ботнет
       • «Цифровий дефолт» парку                     • Необхідність відкликання ключа
```

#### 1. Втрата доступності (Key Unavailability)
Закритий ключ знищено, диск пошкоджено, токен утрачено, або пароль забуто. Ключ не дістався ворогу — його просто більше немає у природі.

Наслідки:
- **Неможливість доставки виправлень (Zero-Day Trap):** Будь-яка виявлена вразливість у драйвері Wi-Fi, стеку BLE або протоколі шифрування стає довічною.
- **Закінчення терміну дії сертифікатів (Certificate Expiration Death):** Якщо пристрій з'єднується з хмарою через протокол TLS, кореневі сертифікати серверів (наприклад, Let's Encrypt або власного CA) мають кінцевий термін придатності (типово від 1 до 5 років). Коли термін дії сертифіката спливає, пристрій більше не може встановити захищене з'єднання з сервером, а оновити сертифікат у прошивці неможливо.
- **Календарні та протокольні збої:** Зміни у протоколах мобільних операторів (відключення мереж 2G/3G), переповнення лічильників епохи GPS (GPS Week Number Rollover) або проблема 2038 року (Year 2038 Unix epoch overflow) призводять до одночасної масової зупинки всього парку.

#### 2. Витік конфіденційності (Key Compromise)
Закритий ключ викрадено з незахищеного сервера збірки (CI/CD), опубліковано у відкритому репозиторії GitHub разом із вихідним кодом або скопійовано інсайдером.

Наслідки:
- **Втрата автентичності коду:** Зловмисник отримує можливість компілювати власні модифіковані образи прошивок (із бекдорами, шпигунськими модулями чи шифрувальниками-вимагачами), підписувати їх викраденим ключем і масово розсилати через штатні механізми оновлення.
- **Пастка відсутності відкликання:** Якщо в завантажувачі не було завчасно закладено механізм відкликання ключів (Key Revocation), виробник опиняється в тій самій безпорадності, що й при втраті ключа. Навіть якщо розробники згенерують новий безпечний ключ, вони не можуть змусити парк відхиляти прошивки, підписані старим вкраденим ключем, доки фізичний зв'язок між старим ключем та eFuse не буде апаратно розірвано.

Історичний досвід великих технологічних екосистем, від пастки першої версії підпису пакетів Android до криптографічного переходу UEFI 2026 року та зламу калькуляторів Texas Instruments, детально розібрано у вставці [катастрофи та уроки втрати ключів підпису](root:embedded/vtrata-kliucha-pidpysu/hist-key-loss-disasters.md).

### Архітектура порятунку 1: Багатослотовий корінь довіри (Multi-Slot RoT)

Головна помилка інженерів-початківців полягає у спалюванні в eFuse єдиного відкритого ключа. Якщо цей єдиний ключ втрачається або компрометується, зв'язок із пристроєм втрачається назавжди.

Правильне проектування апаратного забезпечення вимагає створення **багатослотового кореня довіри (Multi-Slot Root of Trust)**. Сучасні чіпи високого рівня безпеки (наприклад, лінійка NXP i.MX із архітектурою SRK — Super Root Keys, або ESP32-S3 із підтримкою трьох незалежних слотів Secure Boot v2) резервують у кремнії місце для таблиці з трьох або чотирьох хешів публічних ключів одночасно.

![Багатослотовий корінь довіри з апаратними бітами відкликання](/root/course/embedded/vtrata-kliucha-pidpysu/img/multi-slot-rot.svg)
*Багатослотовий Root of Trust: таблиця хешів 4 ключів та бітова маска відкликання в кремнії.*

#### Механіка роботи багатослотової таблиці
Під час первинної підготовки виробництва (Provisioning) у матрицю eFuse записується масив із чотирьох 256-бітних хешів: `SRK0`, `SRK1`, `SRK2`, `SRK3`. Поруч із таблицею виділяється окремий регістр eFuse — **маска відкликання (Revocation Mask)** розміром 4 біти (`REVOKE0`, `REVOKE1`, `REVOKE2`, `REVOKE3`), де кожен біт спочатку дорівнює `0` (не відкликано).

1. **Нормальний режим експлуатації:** Прошивки збираються й підписуються закритим ключем, що відповідає слоту `SRK0`. Приватні ключі для слотів `SRK1`, `SRK2` та `SRK3` ніколи не потрапляють на сервери збірки чи робочі комп'ютери. Їх генерують під час захищеної процедури — церемонії ключів — і зберігають на ізольованих апаратних токенах або у вигляді розділених часток секрету в банківських сейфах.
2. **Сценарій катастрофи:** Якщо ключ `SRK0` втрачено або скомпрометовано, уповноважені особи збирають кворум, вилучають із сейфа резервний закритий ключ слота `SRK1` і підписують ним екстрений реліз оновлення.
3. **Апаратне відкликання:** У заголовку екстреної прошивки виставляється інструкція спалювання eFuse. Завантажувач, успішно перевіривши підпис ключем `SRK1`, подає імпульс напруги на комірку `REVOKE0`, переводячи її в стан `1`.

Від цієї миті апаратна логіка ROM Bootloader при будь-якій спробі перевірки коду ігнорує слот `SRK0`. Будь-яка стара прошивка або зловмисний образ, підписаний скомпрометованим ключем `SRK0`, відхиляється на рівні кремнію. Система продовжує штатну роботу на слоті `SRK1`, зберігаючи в резерві ще два незалежні слоти `SRK2` та `SRK3`.

### Архітектура порятунку 2: Ієрархія центрів сертифікації (PKI) замість пласких ключів

Безпосереднє підписання бінарних файлів прошивки кореневим закритим ключем (Root Private Key) — це грубе порушення архітектури безпеки. Корінь довіри не повинен торкатися повсякденних операцій.

У промислових системах управління пристроями застосовують ієрархічну інфраструктуру відкритих ключів (PKI, англ. *Public Key Infrastructure*), що розділяє повноваження на три рівні.

![Трирівнева ієрархія центрів сертифікації для ізоляції ризиків](/root/course/embedded/vtrata-kliucha-pidpysu/img/pki-trust-chain.svg)
*Ієрархія сертифікатів PKI: офлайн Root CA, проміжний Sub-CA та релізний ключ білд-сервера.*

#### 1. Кореневий центр сертифікації (Root CA)
- **Призначення:** Єдине джерело істини. Його відкритий ключ або сертифікат X.509 зашитий у кремній eFuse пристрою.
- **Зберігання:** Суворо офлайн (Air-gapped). Комп'ютер без мережевих адаптерів, що зберігається в сейфі. Ключ активується лише раз на кілька років для підписання сертифіката проміжного центру.
- **Термін дії:** 15–25 років.

#### 2. Проміжний центр сертифікації (Intermediate CA / Sub-CA)
- **Призначення:** Отримує сертифікат від Root CA. Використовується відділом реліз-інжинірингу для випуску та відкликання робочих ключів підпису.
- **Зберігання:** Локальний апаратний модуль безпеки HSM у захищеному периметрі компанії.
- **Термін дії:** 2–5 років.

#### 3. Релізний ключ збірки (Release Signing Key)
- **Призначення:** Безпосереднє накладання підпису на виконувані бінарні файли прошивок у конвеєрі автоматизованої збірки (CI/CD).
- **Зберігання:** Мережевий HSM або захищений модуль ключів хмарного провайдера (Cloud KMS).
- **Термін дії:** 6–12 місяців (регулярна планова ротація).

#### Як це захищає від катастрофи
Заголовок прошивки супроводжується повним ланцюжком сертифікатів (Certificate Chain). Завантажувач у мікроконтролері перевіряє ланцюг знизу вгору:
1. Підпис прошивки перевіряється відкритим ключем `Release Key`.
2. Сертифікат `Release Key` перевіряється відкритим ключем `Intermediate CA`.
3. Сертифікат `Intermediate CA` перевіряється відкритим ключем `Root CA`.
4. Хеш відкритого ключа `Root CA` звіряється з еталоном в eFuse чіпа.

Якщо сервер автоматичної збірки було скомпрометовано, а його `Release Key` викрадено, Root CA залишається неушкодженим у сейфі. Служба безпеки за допомогою Root CA випускає новий сертифікат проміжного центру або оновлений список відкликання (CRL, Certificate Revocation List). Пристрої завантажують оновлення, перевіряють його через непорушний Root CA, відкликають старий `Release Key` і продовжують отримувати безпечні релізи без заміни eFuse.

Для обмежених за пам'яттю мікроконтролерів (де парсер повного стандарту ASN.1/X.509 зайняв би забагато Flash-пам'яті) замість громіздких сертифікатів часто застосовують компактні криптографічні конверти на базі бінарного стандарту CBOR Object Signing and Encryption (COSE, RFC 9052) або спрощені структури C-маніфестів із фіксованим зміщенням полів. Це дозволяє здійснювати перевірку багаторівневого ланцюга підписів із використанням усього кількох сотень байтів стека без динамічного виділення пам'яті.

Повна структура полів двійкового заголовка прошивки, конфігураційні прапорці, таблиця алгоритмів та формат пакування ланцюжка сертифікатів наведені у [специфікації маніфесту захищеної прошивки](root:embedded/vtrata-kliucha-pidpysu/api-manifest-format.md).

### Архітектура порятунку 3: Перехідні прошивки («Містки» / Bridge Firmware)

Якщо мікроконтролер має просту архітектуру без апаратної підтримки множинних слотів eFuse та повноцінного PKI, планову заміну ключа підпису реалізують через механізм **перехідних прошивок (Bridge Firmware)**.

Криптографічний місток — це спеціальний реліз прошивки, мета якого полягає не у зміні бізнес-логіки пристрою, а у безпечній передачі повноважень від старого ключа (`Key_A`) до нового ключа (`Key_B`).

![Чотири фази міграції парку через перехідну прошивку](/root/course/embedded/vtrata-kliucha-pidpysu/img/bridge-firmware-flow.svg)
*Фази міграції парку: розгортання прошивки-містка зі старим підписом та активація нового завантажувача.*

#### Чотири фази міграції парку
1. **Фаза 1: Підготовка нового покоління ключів:** Поки старий ключ `Key_A` залишається повністю доступним і працездатним, інженери генерують нову пару ключів `Key_B`.
2. **Фаза 2: Складання прошивки-містка:** Створюється бінарний образ, який містить новий завантажувач (Bootloader v2) або оновлену таблицю довірених ключів у Flash, де новим довіреним коренем призначено відкритий ключ `Public_Key_B`. Цей перехідний образ **підписується старим ключем `Key_A`**.
3. **Фаза 3: Доставка та встановлення містка:** Парк пристроїв завантажує образ через OTA. Старий завантажувач Bootloader v1 перевіряє підпис старим ключем `Key_A`, успішно валідує його і записує новий Bootloader v2 у пам'ять Flash.
4. **Фаза 4: Активація нового довіреного стану:** Після перезавантаження керування переходить до Bootloader v2. Відтепер завантажувач ігнорує старий `Key_A` і вимагає підпис виключно новим ключем `Key_B`. Усі наступні оновлення підписуються тільки `Key_B`.

> [!WARNING]
> **Критична часова залежність:** Схема з перехідною прошивкою працює **лише тоді, коли стара пара ключів ще є в наявності**. Якщо ключ `Key_A` уже втрачено, а прошивку-місток не було завчасно підписано й поширено, побудувати криптографічний міст стає математично неможливо: старий завантажувач відхилить будь-який образ, не підписаний `Key_A`.

### Захист від відкату (Anti-Rollback) і його смертельні пастки

Криптографічний підпис гарантує автентичність коду, але сам по собі не захищає від атак типу **Downgrade Attack (повернення на стару версію)**.

Уявімо ситуацію: версія прошивки `v1.0.0` містила вразливість, що дозволяє обійти авторизацію. У версії `v2.0.0` помилку виправили. Обидва образи підписані легітимним ключем виробника. Зловмисник, перехопивши зв'язок із пристроєм або під'єднавшись до шини Flash, примусово записує старий легітимний образ `v1.0.0`. Оскільки підпис версії `v1.0.0` математично бездоганний, завантажувач визнає його дійсним і запустить вразливу версію, відкриваючи доступ до системи.

Для захисту від таких атак у кремній вбудовують **монотонні апаратні лічильники версій безпеки (Anti-Rollback Counters)** у вигляді лінійки eFuse.

```
eFuse Monotonic Counter (Security Version):
Початковий стан (v1):   [ 1 ][ 0 ][ 0 ][ 0 ][ 0 ][ 0 ][ 0 ][ 0 ]  -> Лічильник = 1
Після оновлення (v2):   [ 1 ][ 1 ][ 0 ][ 0 ][ 0 ][ 0 ][ 0 ][ 0 ]  -> Лічильник = 2
Після оновлення (v3):   [ 1 ][ 1 ][ 1 ][ 0 ][ 0 ][ 0 ][ 0 ][ 0 ]  -> Лічильник = 3
```

Оскільки біти eFuse можна лише спалювати (`0 → 1`), апаратний лічильник може тільки зростати. Завантажувач порівнює поле `security_version` із заголовка образу з апаратним значенням eFuse:
```
Якщо (image.security_version >= efuse.security_version) -> ДОЗВОЛИТИ
Якщо (image.security_version <  efuse.security_version) -> ЗАБЛОКУВАТИ
```

#### Смертельна пастка невчасної фіксації (Premature Counter Commit)
Під час ротації ключів та оновлення версії безпеки виникає критичний стан гонитви (Race Condition), здатний перетворити пристрій на «цеглину» без участі зловмисників.

Якщо завантажувач спалює біти eFuse анти-відкату або біти відкликання ключів *до того*, як нова прошивка повністю перевірила власну працездатність, будь-який збій під час першого запуску стає фатальним:
1. Завантажувач перевірив новий образ у Банку B Flash-пам'яті, визнав його валідним і спалив eFuse, заблокувавши версію `v1` та старий ключ `Key_A`.
2. Завантажувач передає керування новій прошивці `v2`.
3. У коді `v2` виявляється баг ініціалізації апаратного таймера або паніка ядра (Kernel Panic), яка викликає миттєвий HardFault і спрацьовування сторожового таймера (Watchdog).
4. Мікроконтролер перезавантажується. Завантажувач намагається виконати аварійний відкат (Fallback) на перевірений робочий Банк A зі старою версією `v1`.
5. Але завантажувач зчитує eFuse і бачить, що версія `v1` тепер вважається забороненою через щойно збільшений лічильник анти-відкату, а ключ `Key_A` відкликано.
6. Завантажувач відхиляє і Банк B (бо він падає), і Банк A (бо він відкликаний). Пристрій назавжди зависає у стані зупинки.

#### Правило двофазного комміту (Two-Phase Commit for Anti-Rollback)
Щоб уникнути самоблокування парку, апаратні біти eFuse дозволяється спалювати виключно за двофазним протоколом:

```
[ Етап 1: OTA Завантаження ] -> Запис образу в Банк B (Dual-Bank Flash)
                                       |
                                       v
[ Етап 2: Верифікація Boot ] -> Перевірка підпису та хешу (БЕЗ спалювання eFuse)
                                       |
                                       v
[ Етап 3: Пробний старт ]    -> Запуск Банку B у режимі тестування (Self-Test)
                                       |
                   +-------------------+-------------------+
                   |                                       |
             (Тест успішний)                         (Збій / WDT)
                   |                                       |
                   v                                       v
[ Етап 4: Фіксація в eFuse ]                 [ Аварійний відкат ]
• Спалювання бітів відкликання                • Перемикання на Банк A
• Збільшення лічильника версії                • Старий eFuse залишається чинним
• Переведення Банку B в Active               • Пристрій відновлює роботу
```

Повний програмний код завантажувача з підтримкою багаторівневої перевірки слотів, захистом від атак за часом виконання (`constant-time memcmp`) та безпечним двофазним протоколом фіксації eFuse наведений у [практикумі реалізації захищеного завантажувача з відкликанням ключів](root:embedded/vtrata-kliucha-pidpysu/proj-key-rotation-bootloader.md).

### Що робити, якщо катастрофа вже сталася: анатомія інженерного відчаю

Коли єдиний ключ підпису безповоротно втрачено, а парк пристроїв уже знаходиться в експлуатації в замовників, інженерна команда постає перед вибором із чотирьох сценаріїв порятунку, кожен із яких має свою ціну та обмеження.

```
+-----------------------------------------------------------------------------+
|                     СЦЕНАРІЇ ПОРЯТУНКУ ВТРАЧЕНОГО ПАРКУ                     |
+-----------------------------------------------------------------------------+
| 1. Апаратний зневаджувач | Якщо JTAG/SWD не спалено в eFuse:                |
|    (SWD / JTAG Recovery) | перепрошивка програматором на заводі / сервісі.  |
+--------------------------+--------------------------------------------------+
| 2. Сервісний інтерфейс   | Якщо в ROM/Bootloader закладено аварійний порт   |
|    (Rescue Trapdoor)     | UART/USB із окремим фабричним ключем розблокув.  |
+--------------------------+--------------------------------------------------+
| 3. «Білий» джейлбрейк    | Експлуатація вразливості в старій прошивці (RCE) |
|    (In-Field Jailbreak)  | для перезапису завантажувача у відкритій Flash.  |
+--------------------------+--------------------------------------------------+
| 4. Заміна чіпів          | Якщо JTAG вимкнено, а багів немає:               |
|    (Silicon Replacement) | випаювання чіпів або повне списання всього парку.|
+-----------------------------------------------------------------------------+
```

#### Варіант 1: Відновлення через апаратний інтерфейс зневадження (SWD / JTAG)
Якщо під час заводського програмування біти блокування налагодження в eFuse помилково або навмисно не було спалено, доступ до пам'яті чіпа залишається відкритим через контактні майданчики SWD/JTAG на друкованій платі.
- **Як реалізується:** Пристрої збираються в сервісні центри або інженери виїжджають на об'єкти з апаратними програматорами (ST-Link, J-Link). Програматор зупиняє ядро, стирає Flash-пам'ять і записує новий завантажувач із новою таблицею ключів.
- **Ціна:** Логістичний колапс, необхідність фізичного розкриття корпусів, втрата вологозахисту та гарантійних пломб.

#### Варіант 2: Запасний аварійний інтерфейс (Rescue Trapdoor)
Якщо архітектор безпеки завчасно заклав у завантажувач аварійний протокол відновлення, пристрій можна перевести в сервісний режим через апаратні інтерфейси UART, SPI або USB за допомогою спеціального інженерного протоколу «виклик-відповідь» (Challenge-Response).
- **Як реалізується:** Завантажувач генерує випадкове 256-бітне число (Nonce). Сервісна утиліта підписує цей Nonce за допомогою окремого резервного **Майстер-ключа фабрики (Master Factory Key)**, який ніколи не використовується для звичайних OTA-релізів і зберігається у головному сейфі компанії. Завантажувач перевіряє підпис відповіді та відкриває доступ до разового оновлення таблиці відкритих ключів.

#### Варіант 3: Експлуатація власної вразливості («Білий» джейлбрейк парку)
Якщо закритий ключ втрачено, JTAG намертво замкнено, а сервісного бекдору немає, останнім програмним шансом стає пошук і експлуатація критичної вразливості у власному старому коді (Whitehat In-field Jailbreak).
- **Як реалізується:** Дослідники безпеки шукають помилку переповнення буфера (Buffer Overflow) або виходу за межі пам'яті в мережевому демоні, обробнику AT-команд модему або локальному інтерфейсі конфігурації. Через знайдений експлойт у пам'ять інжектується корисне навантаження (Shellcode) з правами ядра, яке отримує прямий доступ до контролера Flash-пам'яті, обходить захист і перезаписує вторинний завантажувач або конфігураційні сектори з новим відкритим ключем.
- **Ризик:** Помилка в експлойті під час масової розсилки перетворює пристрої на незворотні цеглини безпосередньо в руках користувачів.

#### Варіант 4: Апаратна заміна мікроконтролерів або списання парку
Якщо чіп захищено коректно (JTAG замкнено, Secure Boot активний, вразливостей немає), математика та фізика кремнію не залишають шансів. Жоден суперкомп'ютер у світі не здатний за прийнятний час факторизувати 3072-бітний ключ RSA або підібрати 256-бітний закритий ключ еліптичної кривої Ed25519.
- **Єдиний вихід:** Повний відклик продукції, фізичне випаювання мікроконтролерів із плати, утилізація заблокованих чіпів, монтаж нових мікросхем із чистою пам'яттю eFuse або повне списання проекту як безнадійного збитку.

---

> 🔧 **Навіщо це.**
> У реальній розробці захищених пристроїв вартість проектування Root of Trust визначає життєздатність бізнесу. Впровадження чотирьох слотів eFuse замість одного коштує рівно 0 доларів додаткової собівартості компонентів на платі, але рятує компанію від збитків у мільйони доларів при першій же компрометації чи втраті робочого ключа збірки. Архітектура безпеки полягає не в тому, щоб зробити замок максимально жорстким, а в тому, щоб зберегти повний контроль над його відкриттям за будь-яких кризових сценаріїв людського фактора.

### Підсумкові правила проектування життєвого циклу ключів

Щоб захищений парк пристроїв ніколи не опинився у стані мертвого блокування, розробка вбудованої системи повинна спиратися на залізні інженерні принципи:

1. **Ніколи не спалювати один відкритий ключ без резерву:** Завжди конфігурувати мінімум 3 або 4 незалежні слоти Root of Trust в eFuse чіпа з підтримкою апаратних бітів відкликання.
2. **Розділяти корінь довіри та релізний підпис:** Кореневий ключ (Root CA) зобов'язаний зберігатися в ізольованому офлайн-сейфі, а підписання щоденних бінарних релізів має здійснюватися через тимчасові сертифікати проміжних ключів (Intermediate Sub-CAs).
3. **Використовувати схему розділеного секрету:** Генерація та резервне копіювання головних ключів повинні здійснюватися під час офіційної церемонії ключів із розподілом секрету за схемою Шаміра (`m-of-n`), що виключає втрату ключа внаслідок звільнення чи загибелі одного співробітника.
4. **Реалізовувати двофазний комміт для анти-відкату:** Апаратні лічильники eFuse та біти відкликання дозволено спалювати лише після успішного тестового завантаження та самодіагностики нової версії прошивки.
5. **Тестувати процедуру ротації ключів до запуску серійного виробництва:** Алгоритм переходу на резервний слот eFuse та обробка прошивок-містків повинні проходити повне автоматизоване тестування на інженерних зразках до спалювання першого чіпа комерційної партії.
