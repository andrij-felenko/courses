Коли розробник створює драйвер для класичного цифрового давача — тривісного акселерометра, барометра або термометра на шинах I2C чи SPI, — взаємодія підпорядкована суворому детермінізму. Головний мікроконтролер виступає безапеляційним господарем шини *(Master)*: він виставляє адресу регістра, формує серію тактових імпульсів і через заздалегідь відомі мікросекунди гарантовано отримує байт у відповідь. Пасивна мікросхема не має власної волі: її внутрішній апаратний автомат зчитує комірку пам'яті або результат перетворення АЦП і миттєво повертає дані на лінію.

Проте варто підключити до плати так званий смарт-модуль — стільниковий модем LTE Cat-M/NB-IoT (Quectel BG96, SIMCom SIM7000), Wi-Fi/Bluetooth мікроконтролер ESP32 з AT-прошивкою, супутниковий приймач GNSS (u-blox NEO-M8/M10) чи людино-машинний інтерфейс Nextion, — як уся синхронна модель розбивається вщент.

Смарт-модуль — це повноцінний автономний комп'ютер на одній друкованій платі. Під його металевим екраном працює високопродуктивне процесорне ядро (ARM Cortex-A7, RISC-V або DSP), функціонує власна операційна система реального часу (FreeRTOS, ThreadX або комерційна RTOS базової смуги), динамічно виділяється пам'ять під мережеві буфери, а також виконуються важкі обчислювальні процеси: математичні алгоритми цифрової фільтрації сигналів супутників, узгодження параметрів радіоканалу з базовими станціями стільникової мережі за специфікаціями 3GPP або криптографічне шифрування сесій TLS 1.3.

Фізичним каналом зв'язку між хост-мікроконтролером і таким модулем зазвичай є послідовний інтерфейс UART, через який передаються текстові AT-команди або потокові NMEA-речення. Якщо підійти до створення драйвера такого пристрою наївно — відправити в UART текстовий рядок `AT+CSQ\r\n`, заблокувати процесор жорсткою затримкою `delay_ms(100)` і спробувати прочитати відповідь через `scanf()` або `strstr()`, — пристрій перетвориться на джерело неперервних аварій у польових умовах.

Час виконання операцій смарт-модулем принципово невизначений: проста перевірка зв'язку `AT` повертає `OK` за 2 мілісекунди, тоді як реєстрація в роумінгу або сканування радіоефіру `AT+COPS=?` може тривати від 30 до 120 секунд. 

Більше того, смарт-модуль генерує спонтанні непередбачувані повідомлення *(англ. Unsolicited Result Codes, URC)*: інформацію про вхідний дзвінок `RING`, надходження SMS `+CMTI`, аварійне закриття сокета віддаленим сервером `+QIURC: "closed",0` чи втрату сигналу базової станції `+CREG: 0`. Якщо таке сповіщення надійде саме тоді, коли хост чекає на відповідь на інший запит, наївний парсер зіб'ється з пантелику, переповнить апаратний буфер UART і назавжди зависне.

> 🔧 **Навіщо це.** Надійний драйвер інтелектуального периферійного модуля проектується як асинхронний диспетчерський комплекс. Він ізолює прийом байтів через кільцевий буфер на базі прямого доступу до пам'яті (DMA), миттєво розщеплює вхідний потік на синхронні відповіді та спонтанні URC-події, керує чергою неблокуючих задач із динамічними таймаутами та забезпечує повний цикл апаратного скидання пристрою при глибоких системних збоях.

## Специфіка смарт-модулів: асинхронність та непередбачувані затримки

Взаємодія двох мікропроцесорних систем через вузький послідовний міст принципово відрізняється від роботи з регістровою пам'яттю звичайних мікросхем.

![Архітектура взаємодії хост-мікроконтролера та смарт-модуля з власним процесором](/root/course/embedded/draiver-modulia-z-vlasnym-mozkom/img/smart-module-arch.svg)
*Архітектура взаємодії хост-мікроконтролера та інтелектуального модуля: незалежні обчислювальні ядра, асинхронний фізичний UART-канал, паралельні потоки команд, відповідей та спонтанних сповіщень URC.*

### 1. Джерела часової недетермінованості

У пасивному чипі тривалість реакції строго прив'язана до частоти тактування інтерфейсу SPI або I2C. У смарт-модулі шлях запиту від контакту RX до формування відповіді на контакті TX перетинає численні програмно-апаратні рівні:

1. **Планувальник внутрішньої RTOS модуля:** UART-драйвер модуля складає байти в системну чергу повідомлень. Якщо в цей час ядро модема зайняте високопріоритетним процесом обробки радіоканалу (наприклад, декодуванням сигнальних блоків LTE або інтерполяцією доплерівського зсуву в GNSS), задача інтерпретатора AT-команд витісняється на десятки мілісекунд;
2. **Протокольні затримки бездротової мережі:** операція активації PDP-контексту `AT+QIACT=1` або відкриття TCP-сокета `AT+QIOPEN` вимагає узгодження з вишкою стільникового оператора: проходження процедури випадкового доступу *(RACH — Random Access Channel)*, виділення радіоблоків, проходження автентифікації на сервері ядра мережі та маршрутизації пакетів через інтернет;
3. **Операції з Flash-пам'яттю та збирання сміття:** збереження сертифікатів TLS, телефонних книг або конфігураційних профілів ініціює цикли стирання сторінок Flash-пам'яті (50–300 мс) та роботу алгоритмів вирівнювання зносу *(Wear Leveling)*, під час яких контролер Flash-пам'яті блокує внутрішню шину модуля;
4. **Режими енергозбереження:** якщо модуль перебував у режимі глибокого сну *(PSM або eDRX)*, йому потрібен час (від 10 до 150 мс) на відновлення генерації опорного кварцового резонатора PLL, стабілізацію напруг внутрішніх LDO та пробудження інтерфейсу UART.

### 2. Мультиплексування трьох типів потоків

Через єдиний фізичний канал UART одночасно циркулюють три абсолютно різні інформаційні потоки:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                       ЄДИНИЙ ПОТІК UART RX                                  │
└─────────────────────────────────────────────────────────────────────────────┘
       │                                 │                              │
       ▼                                 ▼                              ▼
1. Синхронні відповіді           2. Спонтанні події             3. Прозорі дані
   на активні команди:              (URC):                         (Raw Stream):
   "OK", "ERROR",                   "+CREG: 1",                    Байтовий потік TCP,
   "+CSQ: 24,99"                    "+QIURC: closed",              NMEA-потік GNSS,
                                    "RING", "+CMTI"                символ-запрошення ">"
```

Коли хост надсилає команду опитування якості сигналу `AT+CSQ`, він очікує отримати рядок параметрів `+CSQ: 19,99` та статус завершення `OK`. Проте базова станція саме в цей момент може примусово розірвати радіоз'єднання через перевантаження сектору. 

Модуль миттєво видасть у потік два рядки: `+CEREG: 2` *(пошук мережі)* та `+QIURC: "closed",0` *(розрив активного сокета)*. Якщо драйвер хоста очікує суто відповіді на `AT+CSQ` і не підтримує паралельного розпізнавання URC, виникне розсинхронізація: рядок розриву сокета буде помилково відкинутий як невідомий формат відповіді, сокетний менеджер хоста вважатиме з'єднання відкритим, а при спробі передачі чергового пакету система отримає фатальну помилку тайм-ауту.

## Потоковий парсинг: кільцеві буфери на DMA та диспетчер URC-подій

Обробка потоку UART на типових для смарт-модулів швидкостях 115200 або 921600 бод за допомогою класичних побайтових переривань (`USART_IT_RXNE`) є тупиковим архітектурним шляхом. За швидкості 921600 бод один байт надходить кожні 10.8 мікросекунд. Процедура входу в обробник переривання, збереження регістрового контексту в стек, запис байта в пам'ять та вихід забирають 30–60 тактів. Якщо модуль надсилає пакет розміром 1500 байтів, процесор витратить більшість своєї обчислювальної потужності виключно на обслуговування переривань порту.

### 1. Кільцевий буфер на базі UART DMA з IDLE Line Detection

Єдиний надійний інженерний підхід полягає у використанні контролера прямого доступу до пам'яті (DMA) у циклічному режимі *(Circular Buffer Mode)* у комбінації з апаратним перериванням виявлення простою лінії — **UART IDLE Line Interrupt**.

![Принцип роботи кільцевого буфера на UART DMA з диспетчером рядків](/root/course/embedded/draiver-modulia-z-vlasnym-mozkom/img/dma-ring-buffer-parser.svg)
*Схема потокового прийому: кільцевий буфер на прямому доступі до пам'яті (DMA), детекція пауз на шині через IDLE Line Interrupt, zero-copy виділення рядків та паралельна маршрутизація відповідей і URC-подій.*

Контролер DMA самостійно, без жодної участі процесорного ядра, переносить прийняті байти з регістра `USART_RDR` у виділений статичний масив оперативної пам'яті. Коли модуль завершує передачу чергового рядка або пакета, лінія RX переходить у стан високого логічного рівня (пасивний стан лінії). Після витримки паузи тривалістю рівно в один фрейм (10 бітових інтервалів) апаратний блок UART формує переривання IDLE.

У момент переривання IDLE хост-процесор визначає поточний індекс запису в буфер *(Head)* за лічильником залишкових передач DMA:

```
Head = BUFFER_SIZE - DMA_CNDTR
```

Драйвер підтримує власний програмний індекс зчитування *(Tail)*. Кількість доступних для обробки байтів обчислюється з урахуванням кільцевого завороту масиву:

```
Available_Bytes = (Head >= Tail) ? (Head - Tail) : (BUFFER_SIZE - Tail + Head)
```

### 2. Виділення рядків без динамічного копіювання (Zero-Copy Line Extraction)

Оскільки протокол AT-команд та формат NMEA складаються з рядків, розділених символами `\r\n` (CRLF, ASCII 0x0D 0x0A), парсер першого рівня повинен нарізати сирий потік на ізольовані нуль-терміновані рядки.

Щоб не витрачати ресурси на копіювання та не викликати фрагментацію пам'яті, екстрактор рядків працює безпосередньо в кільцевому буфері: виявляючи послідовність `\r\n`, він замінює перший роздільник на `\0`, створюючи валідний C-рядок *(Null-terminated string)* або конструюючи об'єкт `std::string_view` без алокацій у динамічній купі.

### 3. Диспетчеризація URC через статичну таблицю префіксів

Кожен виділений рядок перевіряється на відповідність зареєстрованим сигнатурам спонтанних подій. Драйвер містить таблицю зіставлення префіксів:

Якщо виділений рядок починається з одного з префіксів таблиці (`+CREG:`, `+QIURC:`, `+CMTI:`, `RING`, `+QMTRECV:`), він негайно перенаправляється у відповідний підсистемний обробник (Network Manager, Socket Pool Manager або SMS Handler). Усі інші рядки (зокрема `OK`, `ERROR`, `+CME ERROR:`, або змістовні відповіді на зразок `+CSQ: 18,99`) передаються в поточний активний автомат виконання команд.

Нижче наведено повну реалізацію кільцевого буфера на базі DMA та диспетчера рядків:

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

#define UART_RX_RING_SIZE    1024U

typedef struct {
    uint8_t  buffer[UART_RX_RING_SIZE];
    uint16_t tail;
} uart_dma_ring_t;

/* Отримання поточного положення апаратного запису DMA (наприклад, для STM32) */
static inline uint16_t get_dma_head(uint16_t dma_cndtr_val) {
    return (uint16_t)(UART_RX_RING_SIZE - dma_cndtr_val);
}

/* Вичитка повного рядка, завершеного \r або \n, без копіювання */
bool uart_ring_get_line(uart_dma_ring_t *ring, uint16_t dma_cndtr_val, 
                        char *out_line, size_t max_out_len) {
    uint16_t head = get_dma_head(dma_cndtr_val);
    uint16_t tail = ring->tail;
    
    if (head == tail) {
        return false; /* Немає нових даних */
    }

    /* Пошук символу кінця рядка \n */
    uint16_t scan_idx = tail;
    bool line_found = false;
    size_t line_len = 0;

    while (scan_idx != head) {
        uint8_t b = ring->buffer[scan_idx];
        if (b == '\n') {
            line_found = true;
            break;
        }
        scan_idx = (uint16_t)((scan_idx + 1U) % UART_RX_RING_SIZE);
        line_len++;
        if (line_len >= max_out_len - 1U) {
            /* Захист від переповнення вихідного буфера: скидаємо пошкоджений рядок */
            ring->tail = scan_idx;
            return false;
        }
    }

    if (!line_found) {
        return false; /* Рядок ще не надійшов повністю */
    }

    /* Копіюємо сформований рядок у вихідний буфер, відкидаючи \r і \n */
    size_t out_idx = 0;
    while (ring->tail != scan_idx) {
        uint8_t b = ring->buffer[ring->tail];
        if (b != '\r' && b != '\n') {
            if (out_idx < max_out_len - 1U) {
                out_line[out_idx++] = (char)b;
            }
        }
        ring->tail = (uint16_t)((ring->tail + 1U) % UART_RX_RING_SIZE);
    }
    
    /* Пропускаємо сам символ '\n' */
    ring->tail = (uint16_t)((ring->tail + 1U) % UART_RX_RING_SIZE);
    out_line[out_idx] = '\0';

    return (out_idx > 0); /* Повертаємо true, якщо рядок не порожній */
}
```
```cpp
#include <cstdint>
#include <cstddef>
#include <string_view>
#include <array>
#include <optional>

template <size_t RingSize = 1024>
class UartDmaRingBuffer {
public:
    constexpr UartDmaRingBuffer() : tail_{0} {}

    [[nodiscard]] uint8_t* data() noexcept { return buffer_.data(); }
    [[nodiscard]] static constexpr size_t capacity() noexcept { return RingSize; }

    /* Виділення наступного доступного рядка зі зсувом Tail покажчика */
    [[nodiscard]] std::optional<size_t> extract_line(uint16_t dma_cndtr, 
                                                     char* out_buf, 
                                                     size_t max_len) noexcept {
        const uint16_t head = static_cast<uint16_t>(RingSize - dma_cndtr);
        if (head == tail_) {
            return std::nullopt;
        }

        uint16_t scan_idx = tail_;
        bool found = false;
        size_t raw_len = 0;

        while (scan_idx != head) {
            if (buffer_[scan_idx] == '\n') {
                found = true;
                break;
            }
            scan_idx = (scan_idx + 1U) % RingSize;
            if (++raw_len >= max_len - 1U) {
                tail_ = scan_idx; // Скидання некоректного рядка
                return std::nullopt;
            }
        }

        if (!found) {
            return std::nullopt;
        }

        size_t written = 0;
        while (tail_ != scan_idx) {
            const char c = static_cast<char>(buffer_[tail_]);
            if (c != '\r' && c != '\n' && written < max_len - 1U) {
                out_buf[written++] = c;
            }
            tail_ = (tail_ + 1U) % RingSize;
        }

        tail_ = (tail_ + 1U) % RingSize; // Пропуск '\n'
        out_buf[written] = '\0';

        if (written == 0) {
            return std::nullopt; // Порожній рядок
        }
        return written;
    }

private:
    std::array<uint8_t, RingSize> buffer_{};
    uint16_t tail_{0};
};
```

## Скінченний автомат драйвера: черга команд, таймаути та сесії

Драйвер смарт-модуля повинен гарантувати прикладним задачам повну неблокуючу поведінку: системний потік ставить команду в чергу і продовжує виконання, а результат обробляється через зворотний виклик *(Callback)* або прапорець події в RTOS.

![Скінченний автомат обробки AT-команд та ескалації помилок](/root/course/embedded/draiver-modulia-z-vlasnym-mozkom/img/at-command-fsm.svg)
*Граф станів скінченного автомата драйвера: асинхронна відправка команд із черги, очікування відповідей із динамічним таймаутом, політика повторних спроб та багаторівнева ескалація відновлення.*

### 1. Дескриптор команди та черга задач

Кожна транзакція описується статичною структурою даних:

:::tabs
```c
typedef enum {
    AT_RES_OK = 0,
    AT_RES_ERROR,
    AT_RES_TIMEOUT,
    AT_RES_BUSY
} at_result_t;

typedef void (*at_cmd_cb_t)(at_result_t result, const char *resp_data, void *user_ctx);

typedef struct {
    const char    *cmd_str;         /* Текст команди, наприклад "AT+CSQ\r\n" */
    const char    *expect_prefix;   /* Очікуваний префікс даних, наприклад "+CSQ:" */
    uint32_t       timeout_ms;      /* Індивідуальний таймаут виконання */
    uint8_t        max_retries;     /* Ліміт повторних спроб при збої */
    uint8_t        current_retry;   /* Поточна спроба */
    at_cmd_cb_t    callback;        /* Функція зворотної реакції */
    void          *user_ctx;        /* Контекст користувача */
} at_cmd_desc_t;
```
```cpp
#include <string_view>
#include <functional>
#include <cstdint>

enum class AtResult : uint8_t {
    Ok = 0,
    Error,
    Timeout,
    Busy
};

struct AtCommandDescriptor {
    std::string_view cmd_str;
    std::string_view expect_prefix;
    uint32_t         timeout_ms{1000};
    uint8_t          max_retries{0};
    uint8_t          current_retry{0};
    std::function<void(AtResult, std::string_view)> callback{};
};
```

Команди від різних прикладних завдань (передача сенсорних відліків, синхронізація часу NTP, запит балансу SIM) додаються в кільцеву чергу FIFO. Автомат драйвера послідовно вибирає елементи, забезпечуючи сувору атомарність транзакцій.

### 2. Динамічні таймаути та безпека лічильника SysTick

Різні типи AT-команд вимагають кардинально різних таймаутів:

| Категорія команди | Приклади операцій | Типовий таймаут | Поведінка при спливанні таймауту |
|---|---|---|---|
| **Швидкі локальні** | `AT`, `ATE0`, `AT+CPIN?`, `AT+CSQ` | **300 – 1000 мс** | Швидкий повтор (до 3 спроб) |
| **Середні транзакційні** | `AT+QISTATE`, `AT+QHTTPURL`, `AT+QGNSSC?` | **2000 – 5000 мс** | Повтор або м'яке скидання сесії |
| **Важкі мережеві** | `AT+COPS=?` (сканування ефіру), `AT+QIOPEN` | **30 000 – 120 000 мс** | Розрив сесії, ескалація до апаратного перезапуску |

Перевірка таймауту повинна спиратися виключно на беззнакову арифметику 32-бітного лічильника мілісекунд (SysTick). Це гарантує безпомилкову роботу під час апаратного переповнення лічильника (кожні 49.7 діб):

:::tabs
```c
/* Безпечна перевірка спливання таймауту без ризику помилок при wrap-around */
bool is_timeout_expired(uint32_t start_tick, uint32_t timeout_ms, uint32_t current_tick) {
    return ((uint32_t)(current_tick - start_tick) >= timeout_ms);
}
```
```cpp
#include <cstdint>

[[nodiscard]] constexpr bool is_timeout_expired(uint32_t start_tick, 
                                                 uint32_t timeout_ms, 
                                                 uint32_t current_tick) noexcept {
    return static_cast<uint32_t>(current_tick - start_tick) >= timeout_ms;
}
```
:::

### 3. Режим передачі сирих даних: очікування символу запрошення Data Prompt

Під час передачі бінарних пакетів у TCP/UDP сокети (наприклад, за допомогою команди `AT+QISEND=<socket>,<length>`) модуль не повертає підтвердження `OK`. Натомість він перемикає свій вхідний буфер у режим прозорого прийому і видає єдиний символ-запрошення: `>` *(ASCII 0x3E)*.

Драйвер фіксує перехід у стан `STATE_WAIT_PROMPT`. Щойно байт `>` виявлено в потоці, драйвер негайно запускає передачу корисного навантаження через UART DMA TX без очікування символів переводу рядка `\r\n`.

Повна структура неблокуючого рушія команд детально реалізована у вставці [Практикум: повнофункціональний неблокуючий AT-рушій](root:embedded/draiver-modulia-z-vlasnym-mozkom/proj-at-command-engine.md).

## Апаратні лінії керування та енергозбереження

Спроба взаємодіяти зі смарт-модулем виключно через дві лінії послідовного порту (TX і RX) є грубою інженерною помилкою, яка робить пристрій повністю беззахисним перед апаратними зависаннями. Надійна друкована плата вимагає щонайменше 5–7 допоміжних ліній керування.

![Схема апаратного підключення ліній керування смарт-модулем](/root/course/embedded/draiver-modulia-z-vlasnym-mozkom/img/hardware-control-lines.svg)
*Апаратна обв'язка смарт-модуля: силовий ключ живлення верхнього плеча, транзисторні каскади з відкритим колектором для PWRKEY та RESET_N, лінії енергозбереження DTR і зворотного зв'язку STATUS/RI.*

### 1. Лінія запуску ядра PWRKEY

Більшість стільникових модулів (Quectel, SIMCom, Telit) після появи напруги на виводах `VBAT` залишаються у вимкненому стані. Для старту внутрішнього стабілізатора напруги та завантаження ядра необхідно сформувати активний низький імпульс на вході `PWRKEY`.

- **Увімкнення модуля:** вивід `PWRKEY` притягується до землі через біполярний транзистор NPN або N-MOSFET ключ із відкритим стоком на час від 500 до 1500 мс;
- **Штатне програмне вимкнення:** утримання `PWRKEY` на землі понад 2000–3000 мс ініціює коректне завершення роботи: модуль надсилає в базову станцію пакет дереєстрації *(IMSI Detach)*, скидає кеші файлової системи у Flash і безпечно відключає живлення ядра.

### 2. Лінія аварійного скидання RESET_N

Вхід `RESET_N` підключається до транзисторного ключа з відкритим колектором і слугує для екстреного апаратного скидання при повному зависанні внутрішнього процесора модуля.

> ⚠️ **Застереження щодо RESET_N:** Категорично заборонено використовувати пін `RESET_N` для щоденного штатного перезавантаження модема. Раптове апаратне скидання під час запису сторінок Flash-пам'яті руйнує внутрішню файлову систему модуля та калібрувальні таблиці NVRAM, перетворюючи модем на невідновну «цеглину».

### 3. Лінія сну та пробудження DTR (Data Terminal Ready)

Для автономних акумуляторних датчиків вкрай важливо переводити модуль у режим глибокого сну *(PSM — Power Saving Mode або eDRX)*, коли струм споживання падає з 30 мА до 3–10 мікроамперів зі збереженням реєстрації на вежі зв'язку.

- При `DTR = HIGH` модуль отримує апаратний дозвіл зупинити тактування UART і заснути;
- При переході `DTR = LOW` модуль прокидається за 10–20 мс і активує приймач UART для прийому чергової порції телеметрії.

### 4. Індикація статусу та лінія переривання RI (Ring Indicator)

- **`STATUS` / `VDD_EXT`:** вихідний логічний рівень, сформований внутрішнім LDO модуля. Дозволяє мікроконтролеру достовірно фіксувати, чи запущене ядро модема (високий рівень), чи воно перебуває у вимкненому стані. Це запобігає помилковим повторним імпульсам на `PWRKEY`;
- **`RI` (Ring Indicator):** апаратний сигнал події. Коли модем перебуває в режимі очікування, а головний мікроконтролер спить у режимі глибокого енергозбереження *(Deep Sleep)*, надходження вхідного SMS, виклику або сокетного пакета формує низький імпульс (120 мс) на лінії `RI`. Це переривання миттєво будить мікроконтролер для вичитки даних.

## Стратегії відновлення після зависання модуля: три рівні ескалації

У реальній експлуатації смарт-модулі стикаються з непереборними зовнішніми збоями: збій базової станції під час хендоверу, накопичення витоків пам'яті у внутрішньому TCP/IP стеку або зависання процесора базової смуги від імпульсних наведень на антену.

Драйвер промислового рівня зобов'язаний реалізовувати **драбину ескалації відновлення** *(Recovery Escalation Ladder)*:

```
[Збій транзакції / Тайм-аут]
            │
            ▼ (Рівень 1: Програмне скидання)
  AT+CFUN=1,1 або перезапуск радіотракту AT+CFUN=0 -> AT+CFUN=1
            │ 
            │ (Немає реакції на UART)
            ▼ (Рівень 2: Апаратний імпульс)
  Імпульс на лінію PWRKEY (1.5 с) або RESET_N (300 мс)
            │ 
            │ (Лінія STATUS не піднялася)
            ▼ (Рівень 3: Повне знеструмлення)
  Скидання живлення через силовий P-MOSFET ключ (Power Cycling)
```

### Пастка паразитарного живлення (Phantom Powering)

Найтяжча схемотехнічна помилка при реалізації скидання живлення — просте вимкнення силового ключа `VBAT` без переведення цифрових ліній мікроконтролера у безпечний стан.

Кожен цифровий вивід смарт-модуля захищений внутрішніми діодами від електростатичного розряду (ESD Clamping Diodes), підключеними до його внутрішньої шини живлення `VDD_INTERNAL`:

```
Хост-МК TX (3.3 В) ────► [ ESD Захисний діод ] ────► Внутрішня шина VDD модуля
```

Якщо розімкнути силовий ключ `VBAT`, але залишити виводи мікроконтролера (TX, RTS, DTR, RESET) у стані логічної одиниці (3.3 В або 1.8 В), струм піде через захисні діоди всередину модуля. 

**Фізичні наслідки:**
1. Напруга живлення ядра не падає до нуля, а залишається на рівні 1.2–1.8 В;
2. Внутрішній компаратор початкового скидання (Power-On Reset, POR) не спрацьовує;
3. Кристал модема зависає у паразитарному стані тиристорного замикання *(Latch-Up)*;
4. Після повторного ввімкнення ключа `VBAT` модуль залишається наглухо заблокованим і не запускається.

### Алгоритм безпечного скидання по живленню (Safe Power Cycle)

Повна послідовність гарантованого апаратного перезапуску зі знеструмленням:

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>

/* Прототипи апаратних функцій плати */
void hw_power_switch_set(bool enable);
void hw_gpio_set_mode_analog(void);
void hw_gpio_restore_uart_and_ctrl(void);
void hw_pwrkey_pulse(uint32_t duration_ms);
bool hw_get_status_pin(void);
void delay_ms(uint32_t ms);

/* Повна послідовність апаратного знеструмлення та безпечного перезапуску */
bool smart_module_hard_power_cycle(void) {
    /* Крок 1: Ізоляція ліній. Переводимо ВСІ підключені піни МК в стан High-Z (Analog Input) */
    hw_gpio_set_mode_analog();

    /* Крок 2: Знеструмлюємо модуль через розмикання High-Side P-MOSFET ключа */
    hw_power_switch_set(false);

    /* Крок 3: Витримуємо паузу для повного розряду блокувальних конденсаторів */
    delay_ms(1000);

    /* Крок 4: Подаємо напругу VBAT назад на модуль */
    hw_power_switch_set(true);

    /* Крок 5: Очікуємо стабілізації перехідних процесів живлення (t_ramp) */
    delay_ms(200);

    /* Крок 6: Відновлюємо конфігурацію GPIO (UART TX/RX, DTR, PWRKEY) */
    hw_gpio_restore_uart_and_ctrl();

    /* Крок 7: Генеруємо імпульс увімкнення на PWRKEY (наприклад, 1000 мс) */
    hw_pwrkey_pulse(1000);

    /* Крок 8: Очікуємо підйому лінії STATUS (до 5 секунд) */
    bool ready = false;
    for (uint32_t i = 0; i < 50; ++i) {
        delay_ms(100);
        if (hw_get_status_pin()) {
            ready = true;
            break;
        }
    }

    return ready;
}
```
```cpp
#include <cstdint>
#include <chrono>
#include <concepts>

// Концепт апаратної платформи керування живленням та виводами
template <typename T>
concept HardwareBoardOps = requires(T hw, bool en, uint32_t ms) {
    { hw.set_power_rail(en) } -> std::same_as<void>;
    { hw.isolate_all_gpios() } -> std::same_as<void>;
    { hw.restore_all_gpios() } -> std::same_as<void>;
    { hw.pwrkey_pulse(ms) } -> std::same_as<void>;
    { hw.is_status_active() } -> std::same_as<bool>;
    { hw.delay_ms(ms) } -> std::same_as<void>;
};

template <HardwareBoardOps HwImpl>
class SmartModulePowerController {
public:
    explicit constexpr SmartModulePowerController(HwImpl& hw) : hw_{hw} {}

    [[nodiscard]] bool hard_power_cycle() noexcept {
        // 1. Повна ізоляція пінів хоста для виключення паразитарного живлення
        hw_.isolate_all_gpios();

        // 2. Відключення силового живлення VBAT
        hw_.set_power_rail(false);

        // 3. Гарантована витримка для розряду ємностей декаплінгу
        hw_.delay_ms(1000);

        // 4. Подача напруги живлення
        hw_.set_power_rail(true);
        hw_.delay_ms(200);

        // 5. Відновлення цифрових функцій інтерфейсу
        hw_.restore_all_gpios();

        // 6. Імпульс запуску ядра PWRKEY
        hw_.pwrkey_pulse(1000);

        // 7. Опитування лінії підтвердження апаратної готовності
        for (int i = 0; i < 50; ++i) {
            hw_.delay_ms(100);
            if (hw_.is_status_active()) {
                return true;
            }
        }
        return false;
    }

private:
    HwImpl& hw_;
};
```

## Зведені інженерні правила побудови надійного драйвера

1. **Сувора асинхронність:** жодних блокуючих затримок `delay_ms()` у головній нитці виконання; драйвер повинен бути неблокуючим автоматом стану;
2. **Апаратний прийом через DMA + IDLE interrupt:** обробка побайтових переривань на високих швидкостях призводить до фатальних переповнень буфера `UART Overrun`;
3. **Ізоляція відповідей від URC-подій:** спонтанні сповіщення модема маршрутизуються у фонові колбеки і ніколи не повинні порушувати контекст активної команди;
4. **Диференційовані таймаути:** локальні команди очікуються сотні мілісекунд, мережеві процедури — десятки секунд;
5. **Апаратна обв'язка ліній контролю:** промисловий вузол вимагає ліній `PWRKEY`, `RESET_N`, `DTR`, `STATUS` та силового ключа живлення;
6. **Захист від фантомного живлення:** при знеструмленні модуля всі підключені лінії мікроконтролера обов'язково переводяться у стан високого імпедансу (High-Z / Analog).
