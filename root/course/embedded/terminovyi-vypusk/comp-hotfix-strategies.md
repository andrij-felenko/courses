# 🔌 Стратегії екстреного оновлення: монолітний образ, FOTA-дельта чи конфігураційний карантин

<preknowlist>
- [Наскрізний випуск](root:embedded/naskriznyi-vypusk) — структура релізного конвеєра та артефактів випуску.
- [OTA-сервер](root:embedded/ota-server) — протоколи доставки прошивок та управління парком пристроїв.
- [Оцінювання вразливості: CVSS](root:sf-security/vulnerability-scoring-cvss) — градація критичності загроз та оцінка часу експозиції до атаки.
</preknowlist>

Коли у розгорнутому парку вбудованих пристроїв виявляється критична вразливість нульового дня (0-day) або блокуючий апаратний дефект, інженерна команда постає перед вибором методу доставки виправлення. У лабораторних умовах із прямим підключенням через налагоджувальний інтерфейс SWD/JTAG або високошвидкісний локальний Ethernet найпростішим рішенням здається повна заміна монолітного бінарного файлу. Проте у реальному світі, де десятки тисяч контролерів працюють через вузькосмугові або дорогі канали зв'язку (NB-IoT, LoRaWAN, супутниковий зв'язок Iridium), а вартість передачі кожного мегабайта вимірюється тисячами доларів, спосіб доставки визначає, чи встигне система закрити дірку до початку масової експлуатації зловмисниками.

Існує три основні архітектурні стратегії екстреного реагування:
1. **Повний монолітний образ (Monolithic Binary Replacement)**;
2. **Побайтове різницеве оновлення (FOTA Binary Delta Patching)**;
3. **Конфігураційний карантин та апаратний вимикач (Configuration Quarantine / Remote Kill-Switch)**.

## Порівняльний аналіз стратегій доставки

| Критерій | Монолітний образ (Monolithic) | FOTA-дельта (Binary Delta) | Конфігураційний карантин (Kill-Switch) |
|---|---|---|---|
| **Розмір корисного навантаження** | Великий (300 КБ – 4 МБ) | Мінімальний (5 КБ – 35 КБ) | Мікроскопічний (100 Б – 1 КБ) |
| **Час доставки на парк (NB-IoT / 2G)** | Години або дні (високий ризик таймаутів) | Хвилини (висока ймовірність успіху) | Секунди (миттєве блокування загрози) |
| **Залежність від поточної версії** | Відсутня (самодостатній образ) | Сувора (побайтовий збіг базового образу) | Мінімальна (наявність прапорця в конфігу) |
| **Вимоги до RAM завантажувача** | Низькі (потоковий запис у Flash) | Високі (буфер реконструкції дельти) | Нульові (запис у сховище налаштувань) |
| **Вплив на функціональність** | 100% збереження або покращення | 100% збереження або покращення | Тимчасова деградація/відключення сервісу |
| **Стійкість до збоїв живлення** | Максимальна (при Dual-Bank A/B) | Середня (вимагає контролю цілісності дельти) | Максимальна (атомарний запис конфігурації) |
| **Захист від атак відкату (Rollback)** | Спалювання eFuse monotonic counter | Спалювання eFuse monotonic counter | Не застосовується (тимчасовий захід) |

## 1. Повний монолітний образ: золотий стандарт надійності

Повний бінарний образ містить повний скомпільований код застосунку, вектор таблиці переривань, бінарний заголовок та цифровий підпис виробника.

```
+-----------------------------------------------------------------------+
|  Emergency Header (256 B)  |  Application Code & Data (384 KB)        |
+-----------------------------------------------------------------------+
```

**Механізм дії:** Агент OTA завантажує весь бінарний файл у пасивний банк пам'яті (Flash Bank B), перевіряє хеш SHA-256 і передає керування завантажувачу. Завантажувач виконує звірку підпису й перемикає активний розділ.

**Переваги:**
- **Абсолютна детермінованість:** прошивка не залежить від того, в якому стані знаходилися сектори пам'яті до початку оновлення. Будь-які пошкоджені байти в старому коді перезаписуються новим чистим образом.
- **Мінімальні вимоги до оперативної пам'яті завантажувача:** байти записуються блоками безпосередньо у Flash, що дозволяє виконувати оновлення навіть на мікроконтролерах із 8 КБ SRAM.

**Недоліки та обмеження:**
- **Великий обсяг трафіку:** оновлення 50,000 пристроїв файлом розміром 500 КБ вимагає передачі понад 25 ГБ даних через стільникову мережу, що створює пікове навантаження на базові станції та призводить до високих фінансових витрат.

## 2. FOTA-дельта: порятунок для обмежених каналів

Різницеве оновлення використовує спеціалізовані алгоритми стиснення двійкових відмінностей (наприклад, модифіковані версії *bsdiff*, *detools* або *Courgette*). Замість усього бінарника сервер генерує компактний файл латки (patch file), який містить лише додані або змінені інструкції та зміщення відносно базової версії.

```
[ Базовий образ v2.4.0 (у Flash) ]  +  [ Дельта-патч (12 KB) ]  ==>  [ Hotfix v2.4.1 (у Bank B) ]
```

**Механізм дії:** Мікроконтролер приймає компактний пакет дельти. Завантажувач зчитує байти з чинного образу в Bank A, накладає двійкові зміни згідно з інструкціями дельти і записує відновлений монолітний образ у Bank B. Лише після повної реконструкції виконується класична перевірка SHA-256 та цифрового підпису відновленого образу.

**Критичні ризики та обмеження:**
- **Чутливість до зміщень адрес (Address Drift):** Якщо компілятор під час збирання hotfix змінив розташування функцій у пам'яті, дельта розростається до 70–80% від розміру повного образу. Для ефективної дельти потрібна сувора фіксація адрес за допомогою детерміністичних скриптів компонувальника.
- **Вимоги до ОЗП:** Алгоритми реконструкції дельти потребують від 16 до 64 КБ оперативної пам'яті для ковзних вікон і буферів, що робить цей метод непридатним для ультрабюджетних контролерів Cortex-M0+.

## 3. Конфігураційний карантин: тактичне вигравання часу

Конфігураційний карантин (англ. *quarantine flag / feature kill-switch*) — це не заміна прошивки, а миттєва зміна стану системи за допомогою компактної підписаної керуючої команди.

```
{
  "command": "DISABLE_FEATURE",
  "target_subsystem": "mqtt_payload_fragmentation",
  "quarantine_ttl_sec": 86400,
  "signature": "MEYCIQD..."
}
```

**Механізм дії:** Коли про критичну дірку безпеки стає відомо, але підготовка, компіляція та верифікація бінарного патчу триватиме ще 3–4 години, сервер надсилає до всіх пристроїв підписану команду відключення вразливого мережевого сервісу (або переведення його у режим обмеженого функціоналу). Пристрій вимикає парсер, ізолюючи вектор атаки за лічені секунди.

**Коли застосовувати:**
- Необхідно заблокувати активну масову експлуатацію вразливості (0-day in the wild) протягом перших 15 хвилин після виявлення загрози.
- Пристрій може продовжувати виконувати свої базові функції життєзабезпечення або збору критичних показників без вразливого модуля до моменту завантаження повноцінного бінарного hotfix.

## 4. Вибір оптимальної стратегії під час інциденту

На практиці зрілі інженерні команди комбінують ці підходи у вигляді двофазного реагування:
1. **Фаза 0 (перші 15 хвилин):** розсилка команди конфігураційного карантину для негайної зупинки атаки.
2. **Фаза 1 (наступні 2 години):** складання та доставка точкового бінарного hotfix (через FOTA-дельту для каналів NB-IoT або монолітний образ для Ethernet/Wi-Fi) з наступним відновленням повноцінної функціональності системи.
