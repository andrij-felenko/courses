# ⚙️ Контур керування в коді: один такт від давача до мотора

**Задача.** Абстрактна схема «давачі → оцінювач → керування → виконання → апарат → і знову давачі» гарна на папері. Та щоб апарат справді тримався в повітрі, цей контур треба втілити в **код, що крутиться з фіксованою частотою** — скажімо, 400 разів на секунду, без пропусків і без «плавання» кроку. Напишімо такий такт мовою прошивки (C), складемо чотири ланки в одну функцію `control_tick()` і подивимося, де тут легко все зіпсувати. Мета — не повний автопілот, а **скелет реального контуру**: рівно стільки коду, щоб видно було, як абстракція лягає в залізо.

## Каркас: фіксований темп понад усе

Перше рішення — **звідки береться ритм**. Контур орієнтації мусить спрацьовувати точно через рівні проміжки: якщо такти «плавають», то й [інтеграл та похідна в ПІД](root:embedded/pid-tuning-cascade) рахуються з кривого Δt, і апарат починає сіпатися. Тому такт запускає не `delay()` у циклі (він накопичує дрейф), а **апаратний таймер** або очікування рівного строку за годинником.

Найпростіший надійний каркас — чекати наступного кратного строку за `micros()`:

```c
#define LOOP_HZ   400
#define DT_US     (1000000UL / LOOP_HZ)   // 2500 мкс = 2.5 мс
#define DT_S      (1.0f / LOOP_HZ)        // 0.0025 с — крок для ПІД

static uint32_t next_tick;                // строк наступного такту, мкс

void control_loop_init(void) {
    estimator_init();
    pid_init();
    next_tick = micros() + DT_US;
}

void control_loop_run(void) {
    for (;;) {
        // 1. дочекатися РІВНОГО строку (не «через 2.5 мс від кінця роботи»)
        while ((int32_t)(micros() - next_tick) < 0) { /* короткий простій */ }
        next_tick += DT_US;               // наступний строк — від попереднього

        control_tick();                   // увесь контур за один прохід

        // 2. сторож: чи ми взагалі вклалися в Δt?
        if ((int32_t)(micros() - next_tick) > 0) {
            stats.overruns++;             // такт не вліз — це тривога, не дрібниця
        }
    }
}
```

Зверни увагу на два місця. `next_tick += DT_US` (а не `= micros() + DT_US`) — строки відраховуються **від ідеальної сітки**, тож дрібні запізнення не накопичуються. А приведення різниці до `int32_t` коректно переживає переповнення `micros()` кожні ~71 хвилину: порівнюємо **знаковий проміжок**, а не самі лічильники. Це той самий прийом, що й у [неблокуючому часі на `millis()`](book:programming/nonblocking-time), лише на мікросекундах.

> 🔧 **Навіщо це.** Лічильник `overruns` — найдешевша діагностика реального часу, яку можна мати. Поки він нуль, контур устигає; щойно він росте — десь з'явилася задача, що з'їдає такт, і апарат на межі зриву стабілізації. У справжній прошивці цей лічильник шлють у телеметрію й перевіряють у передпольотних чеках.

## Чому фіксований темп, а не «коли прийдуть дані»

Може виникнути думка: навіщо взагалі сітка строків, чому не рахувати контур щоразу, **коли давач віддав свіжий вимір**? Адже так ми б ніколи не працювали зі «старими» даними. Біда в тому, що ПІД — не просто множення помилки на коефіцієнт. Його інтегральна й похідна складові **залежать від часу між тактами**: інтеграл накопичує `e·Δt`, похідна ділить зміну на `Δt`. Якщо такти приходять то через 2 мс, то через 4 мс, то ці дві складові щоразу рахуються з іншим Δt — і навіть при ідеально точних коефіцієнтах вихід контуру починає тремтіти на рівному місці. Можна підставляти в кожен такт **виміряний** Δt замість сталого — і це робить контур стійким до дрібного джитера, — але рівна сітка все одно бажана: вона робить поведінку **передбачуваною**, а передбачуваність — це і є те, заради чого існує реальний час.

Друга причина — давачів **кілька, і кожен зі своїм ритмом**. Гіроскоп готовий тисячі разів на секунду, барометр — лічені десятки, GNSS — кілька разів. Якби контур «прокидався» на кожне нове число від будь-якого давача, він би смикався з хаотичною частотою й годував ПІД то одним підмножиною даних, то іншим. Фіксований темп розв'язує це чисто: контур сам диктує ритм, а **бере найсвіжіше, що є** від кожного давача на момент такту. Старіший вимір — не біда: оцінювач для того й існує, щоб тримати модель стану між рідкими оновленнями повільних давачів і поправляти її, коли свіже число нарешті прийде.

## Чотири ланки в одній функції

Тепер сам такт. Він дослівно повторює чотири блоки схеми — і порядок тут не випадковий: спершу **виміряти**, тоді **оцінити стан**, тоді **порівняти з уставкою й порахувати команду**, і лише наприкінці **вивести** її на мотори.

```c
void control_tick(void) {
    // ── ЛАНКА 1: давачі — сирі, шумні, часткові виміри ────────────────
    imu_sample_t imu;
    imu_read(&imu);                       // гіро (рад/с) + акселерометр (g)

    // ── ЛАНКА 2: оцінювач — з шумних вимірів один чистий СТАН ──────────
    //   поєднує швидкий гіроскоп і повільний акселерометр (доповняльний
    //   фільтр); на виході — кут, якому можна вірити, а не сирий давач
    state_t st;
    estimator_update(&imu, DT_S, &st);    // st.roll, st.pitch, st.yaw_rate ...

    // ── ЛАНКА 3: керування — неузгодженість і команда ─────────────────
    setpoint_t sp;
    setpoint_get(&sp);                    // бажаний стан: від пілота АБО від місії

    float err_roll = sp.roll - st.roll;           // КЛЮЧОВЕ: від ОЦІНКИ, не від давача
    float u_roll   = pid_step(&pid_roll, err_roll, DT_S);
    float err_pitch = sp.pitch - st.pitch;
    float u_pitch   = pid_step(&pid_pitch, err_pitch, DT_S);

    // ── ЛАНКА 4: виконавчі механізми — команда у фізичну дію ───────────
    motor_cmd_t m = mixer(sp.throttle, u_roll, u_pitch, /*u_yaw=*/0.0f);
    motors_write(&m);                     // ESC ← мотори; апарат рухається
}
```

Уся арифметика контуру — кілька віднімань і викликів `pid_step`; це **мікросекунди роботи**, а не мілісекунди. Левова частка часу такту йде на читання давача по шині та на запис у регулятор обертів. Це типово: керування дешеве, дорогий — обмін із залізом.

> 🔧 **Навіщо це.** Цей кістяк — карта для читання чужої прошивки. Знайшов цикл, що крутиться на сталій частоті, а в ньому послідовність «read → estimate → control → output» — ти знайшов серце автопілота. Усе інше (режими, failsafe, журнал) нарощується **навколо** цих чотирьох рядків.

## Пастка перша: керування від сирого давача замість оцінки

Найспокусливіша «оптимізація» новачка — викинути оцінювач і годувати ПІД прямо з давача:

```c
// НЕ РОБИ ТАК:
float err_roll = sp.roll - accel_to_roll(&imu);   // кут просто з акселерометра
```

Виглядає коротше — і працює рівно доти, доки апарат стоїть на столі. У польоті акселерометр домішує до гравітації **лінійні прискорення** маневру й **вібрацію** моторів, тож «горизонт» із нього дрижить і кривиться. ПІД чесно відпрацьовує цей шум — і апарат трясе. Узяти натомість лише гіроскоп — інша крайність: його кут [дрейфує](book:algorithms/complementary-filter), і апарат поволі «лягає» набік, бо контур вважає крен нульовим. Саме тому між давачем і керуванням **обов'язково** стоїть оцінювач: він зводить швидкий гіроскоп і абсолютний акселерометр в один кут, якому можна довіряти. Рядок `sp.roll - st.roll` коштує стільки ж, скільки `sp.roll - accel_to_roll(...)`, але перший тримає апарат, а другий — трясе.

## Пастка друга: робота в ISR таймера

Спокусливо повісити `control_tick()` прямо на переривання таймера — таймер же й так цокає рівно. Але читання IMU по шині (I²C/SPI) — **повільне** й може блокувати; тримати шину всередині [обробника переривання](book:programming/isr) означає надовго заблокувати всі інші переривання. Правильніше — щоб ISR таймера лише **піднімав прапорець** «час такту настав», а важку роботу робив головний цикл:

```c
volatile bool tick_due = false;
void TIMER_ISR(void) { tick_due = true; }     // коротко: лише відмітка

void control_loop_run(void) {
    for (;;) {
        if (tick_due) {
            tick_due = false;
            control_tick();                    // довга робота — поза ISR
        }
    }
}
```

Так контур зберігає рівний темп від таймера, але читання давача й арифметика не паралізують решту системи. Якщо `tick_due` уже стояв, коли прийшов новий такт, — це той самий **overrun**: попередній такт не встиг завершитися. Прапорець `volatile` — бо його міняє ISR, а читає головний код; без нього компілятор може закешувати значення в регістрі й цикл «не побачить» зміни.

## Пастка третя: різні ланки — різні темпи

Не все треба крутити на 400 Гц. Магнітометр і [GNSS](book:communications/gnss) оновлюються в десятки разів повільніше за гіроскоп, а навігація — лічені рази на секунду. Ганяти їх щотакту — марно палити час такту. Тому зовнішні, повільні ланки запускають **раз на N тактів**, лишаючи швидкий внутрішній контур орієнтації недоторканим:

```c
static uint32_t n = 0;
void control_tick(void) {
    fast_attitude_loop();             // щотакту: 400 Гц — не впасти
    if (++n % 8 == 0) position_loop();      // кожен 8-й такт: ~50 Гц — тримати траєкторію
    if (n % 80 == 0)  navigation_loop();    // кожен 80-й: ~5 Гц — куди летіти
}
```

Це та сама **каскадна** вкладеність контурів, що й на схемі апарата, лише виражена дільниками такту: швидкий контур стабілізує, повільні — ведуть, і кожен зовнішній задає уставку внутрішньому. Головне правило незмінне: **внутрішній контур не має права спізнюватися ніколи**, бо саме він тримає апарат від перекидання, а решта може й зачекати свого 8-го чи 80-го такту.

> 🔧 **Навіщо це.** Дільники такту — найпростіший спосіб зібрати каскад без окремих таймерів на кожен контур. Але стеж, щоб повільні ланки не «збиралися» в один такт: якщо `position_loop()` і `navigation_loop()` випадуть на той самий прохід, такт роздується. Тому строки часто розносять (`n % 8 == 0` і `n % 80 == 3`), щоб важкі ланки не накладалися.

## Що лишилося поза кадром

Цей скелет навмисно голий: у ньому немає обмеження виходу `u`, антивіндапу інтеграла, плавного arming, переходів між режимами й failsafe — усе те, без чого справжній апарат піднімати не можна. Але **каркас** уже правильний: фіксований темп від таймера, чотири ланки в строгому порядку, керування від оцінки стану, а не від сирого давача, і каскад через дільники такту. Нарости на цей кістяк захист виходу, перевірки й журнал — і вийде те, що в реальних прошивках називають головним контуром керування [політного контролера](book:programming/flight-controller).
