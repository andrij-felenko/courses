# 📜 Як народився constinit: боротьба з катастрофою порядку ініціалізації

Невизначений порядок ініціалізації глобальних об'єктів у C++ був джерелом важковиправних дефектів від самого створення мови на початку 1980-х років. Коли програма розростається на десятки одиниць трансляції, поява глобального стану, що залежить від іншого глобального стану, неминуче призводить до ситуації, коли один об'єкт намагається використати інший до виклику його конструктора. Ця проблема отримала назву катастрофи порядку статичної ініціалізації (англ. *Static Initialization Order Fiasco*, SIOF).

## Катастрофа, закладена в архітектуру роздільної компіляції

Модель компіляції C++, успадкована від мови C, базується на незалежній обробці кожної одиниці трансляції. Компілятор перетворює кожен вихідний файл `.cpp` на окремий об'єктний модуль, не знаючи нічого про порядок, у якому системний компонувальник зв'яже ці модулі в остаточний бінарний файл.

Для мови C це не створювало небезпеки: глобальні змінні в C могли ініціалізуватися лише константними виразами під час компіляції, а нульова пам'ять виділялася операційною системою при завантаженні бінарника (секція `.bss`). Проте Б'ярне Струструп, додаючи до C класи з конструкторами, ввів концепцію динамічної ініціалізації глобальних об'єктів: перед передачею керування у функцію `main()` середовище виконання C++ зобов'язане виконати конструктори всіх глобальних об'єктів.

Стандарт установив суворе правило для одного файлу: всередині однієї одиниці трансляції глобальні змінні ініціалізуються точно в порядку їхнього оголошення. Проте порядок між різними одиницями трансляції стандарт оголосив невизначеним (англ. *unspecified*). На практиці цей порядок залежав від порядку передачі файлів компонувальнику, алгоритму завантажувача динамічних бібліотек операційної системи і навіть від випадкових змін конфігурації в системі збірки.

Якщо модуль `logger.cpp` визначав глобальний об'єкт журналу, а модуль `database.cpp` у конструкторі глобального клієнта бази даних намагався записати повідомлення про запуск у цей журнал, результат залежав виключно від збігу обставин:

```cpp
// logger.cpp
Logger g_logger("app.log"); // Динамічний конструктор: відкриває файл

// database.cpp
DatabaseClient g_db(&g_logger); // Динамічний конструктор: викликає g_logger.log(...)
```

Якщо компонувальник ставив `logger.o` першим, програма стартувала успішно. Якщо ж першим опинявся `database.o`, клієнт бази звертався до сирої, ще не сконструйованої пам'яті: внутрішні покажчики `g_logger` містили сміття або нулі, що спричиняло аварійне завершення через збій сегментації (англ. *segmentation fault*) або пошкодження пам'яті ще до того, як виконувався перший рядок функції `main()`.

## Спроби порятунку: ідіома Мейєрса та її прихована ціна

У 1990-х роках Скотт Мейєрс у книзі *Effective C++* популяризував практичний обхідний шлях, відомий як ідіома «ініціалізація під час першого використання» (англ. *construct on first use idiom*), або синглтон Мейєрса:

```cpp
Logger& get_logger() {
    static Logger instance("app.log");
    return instance;
}
```

Локальна статична змінна ініціалізується під час першого проходження потоку керування через її оголошення. Це гарантувало, що `instance` буде створено в момент першого виклику `get_logger()`, незалежно від порядку завантаження об'єктних файлів операційною системою.

Однак у міру розвитку багатопотокових архітектур цей підхід виявив серйозні системні вади:

1. **Накладні витрати синхронізації:** До стандарту C++11 така ініціалізація не була потокобезпечною. У C++11 комітет прийняв папір N2660, зробивши ініціалізацію локальних статичних змінних строго потокобезпечною за рахунок неявного захисту. Компілятори почали генерувати навколо кожного звернення до функції приховані виклики функцій середовища виконання (наприклад, `__cxa_guard_acquire` та `__cxa_guard_release` в ABI Itanium). Для високопродуктивних систем, телеметрії та гарячих циклів це означало зайві операції читання бар'єрів пам'яті (англ. *memory fences*) та умовні переходи при кожному доступі до об'єкта.
2. **Проблема порядку знищення (Static Destruction Order Fiasco):** Якщо порядок створення об'єктів вдавалося розв'язати через виклики функцій, то їхнє знищення відбувалося у зворотному порядку після виходу з `main()`. Якщо деструктор одного статичного об'єкта намагався звернутися до іншого, який уже завершив свій життєвий цикл і знищив внутрішні ресурси, виникала катастрофа порядку знищення, яка призводила до аварій при коректному завершенні процесу.
3. **Неможливість застосування для низькорівневих систем:** Синхронізаційні примітиви (наприклад, спінлоки чи базові атомарні лічильники), глобальні пули пам'яті ядра та апаратні реєстри вбудованих систем часто не можуть дозволити собі виклик функцій з умовними переходами під час старту програми.

## Поява constexpr у C++11 і прихована пастка оптимізатора

У стандарті C++11 з'явилося ключове слово `constexpr`, розроблене Ґабріелем Дос Реїсом та Б'ярне Струструпом (папір N2235). Воно дозволило виконувати конструктори об'єктів на етапі компіляції: якщо тип мав `constexpr`-конструктор і створювався зі статичною тривалістю зберігання, стандарт дозволяв компілятору здійснити *константну ініціалізацію* (англ. *constant initialization*).

Об'єкти, що пройшли константну ініціалізацію, записуються безпосередньо у бінарний файл (у секцію `.data` або `.rodata`) і вже повністю готові до використання в момент завантаження програми в адресний простір. Для таких об'єктів катастрофа порядку статичної ініціалізації неможлива в принципі: їхній початковий стан уже сформовано до запуску першого рядка будь-якого машинного коду.

Проте тут виникла фундаментальна семантична суперечність. У C++11 специфікатор `constexpr` на змінній автоматично накладав вимогу незмінності (`const`). Тобто змінна, оголошена як `constexpr`, не могла змінювати свій стан у процесі роботи програми.

Якщо ж розробнику був потрібен глобальний об'єкт, який гарантовано ініціалізується до запуску, але має змінюватися під час виконання (наприклад, глобальний `std::atomic<uint64_t>`, м'ютекс із `constexpr`-конструктором, буфер трасування чи голова зв'язного списку), написати `constexpr` було заборонено компілятором.

Залишалося створювати звичайну глобальну змінну і розраховувати на те, що конструктор є `constexpr`:

```cpp
struct AtomicCounter {
    std::atomic<int> value;
    constexpr AtomicCounter(int v) : value(v) {}
};

AtomicCounter g_counter{0}; // Сподіваємося на константну ініціалізацію
```

Програміст сподівався, що компілятор самостійно обчислить початковий стан на етапі збірки. Але жодної гарантії мова не надавала. Якщо через рік інший розробник змінював аргумент `0` на виклик звичайної допоміжної функції, компілятор мовчки й без жодного попередження перемикав ініціалізацію з константної на динамічну. Програма продовжувала успішно компілюватися, але глобальний об'єкт знову ставав мішенню для катастрофи порядку ініціалізації, яка несподівано проявлялася лише під навантаженням або на іншому сервері.

## Атрибути компіляторів: Clang і GCC прокладають шлях

Усвідомивши критичність цієї прогалини у масштабних кодових базах, інженери Google та автори компілятора Clang у 2013 році запропонували вендорний атрибут:

```cpp
[[clang::require_constant_initialization]] AtomicCounter g_counter{0};
```

Цей атрибут наказував компілятору примусово перевірити, чи ініціалізується змінна зі статичною (`static`) або потоковою (`thread_local`) тривалістю зберігання виключно константним виразом. Якщо ініціалізатор містив хоча б одну операцію, яку неможливо обчислити під час збірки, Clang переривав компіляцію з детальною діагностикою.

Невдовзі аналогічну підтримку під назвою `__attribute__((require_constant_initialization))` додав і компілятор GCC.

Цей механізм став де-факто стандартом безпеки у великих інфраструктурних проектах, таких як Chromium, LLVM та кодова база Google (зокрема в бібліотеці Abseil). Він дозволяв гарантувати безпеку глобального стану без накладних витрат функцій-обгорток. Проте нестандартний синтаксис був непереносним, створював макросні нашарування та був відсутній у компіляторі MSVC.

## Шлях до стандарту: пропозиція P1143 та ключове слово constinit

Усвідомивши переваги та стабільність атрибута в Clang та GCC, інженер Ерік Фізельє (*Eric Fiselier*) у червні 2018 року подав до комітету ISO C++ пропозицію **P1143R0: "Adding the constinit keyword"**.

Автор обґрунтував, що константна ініціалізація є фундаментальною властивістю оголошення об'єкта, яка потребує власного ключового слова мови.

У ході тривалих дискусій у робочій групі з еволюції мови (EWG) виникли три основні суперечки:

1. **Ключове слово чи стандартний атрибут?** Частина комітету пропонувала зберегти атрибутивну форму (наприклад, `[[const_init]]` або `[[constant_initialization]]`). Проте згідно з дизайн-принципами C++, стандартні атрибути не повинні змінювати валідність чи семантику вихідного тексту програми (видалення атрибута має залишати програму синтаксично коректною). Оскільки невиконання вимоги константності має робити програму синтаксично некоректною (англ. *ill-formed*) і зупиняти компіляцію, специфікатор оголошення був єдино правильним рішенням.
2. **Розширення constexpr замість нового слова?** Пропонувалися варіанти зняття вимоги `const` із `constexpr` або введення конструкцій на кшталт `mutable constexpr`. Але це призвело б до руйнування ключового інваріанта: `constexpr`-змінні можуть використовуватися у виразах часу компіляції (`static_assert`, розміри масивів, параметри шаблонів). Змінний об'єкт не може бути константним виразом у наступних обчисленнях, тому змішування цих понять заплутало б модель мови.
3. **Підтримка thread_local:** Вирішальним аргументом на користь нового ключового слова стала оптимізація змінних із потоковою тривалістю зберігання (`thread_local`). Звичайні `thread_local` змінні з динамічною ініціалізацією змушують компілятор генерувати приховані перевірки прапорця ініціалізації при кожному зверненні потоку. Натомість `constinit thread_local` дає змогу розмістити початковий образ безпосередньо в секції `.tdata` образу потоку, перетворюючи кожне звернення на швидку операцію адресації через сегментний регістр без викликів підсистеми TLS у рантаймі.

У 2018–2019 роках Ерік Фізельє за підтримки робочої групи з еволюції мови підготував оновлені редакції документа P1143.

Остаточна редакція **P1143R2** була винесена на голосування комітету ISO C++ на літньому засіданні в Кельні (Німеччина) у липні 2019 року. Пропозиція була прийнята одноголосно і увійшла до фінального міжнародного стандарту C++20.

## Підсумок стандартизації

Поява `constinit` у C++20 заповнила останню системну прогалину в управлінні глобальним і потоковим станом:

- `const` гарантує незмінність значення під час роботи, але дозволяє як статичну, так і динамічну ініціалізацію;
- `constexpr` вимагає константної ініціалізації та примусово накладає незмінність;
- `constinit` вимагає константної ініціалізації, але залишає об'єкт повністю відкритим для запису під час виконання.

Завдяки цьому розробники високопродуктивного та системного програмного забезпечення отримали надійний засіб повного захисту від катастрофи порядку статичної ініціалізації без жодного компромісу в швидкодії.
