# ⚙️ Побудова безконфліктного реєстру підсистем на constinit

У масштабних програмних комплексах — високопродуктивних веб-серверах, рушіях комп'ютерних ігор, розподілених базах даних та вбудованому системному програмному забезпеченні — однією з головних архітектурних вимог є децентралізована модульність. Кожен окремий модуль або підсистема (наприклад, менеджер розподілу пам'яті, мережевий стек, драйвер графічного прискорювача, система криптографії чи модуль збору телеметрії) повинен мати можливість оголосити про своє існування та зареєструватися в глобальному реєстрі програми в момент завантаження відповідного бінарного образу.

Головна вимога до такого реєстру — повна автономність: додавання нового вихідного файлу чи динамічного модуля до проекту не повинно вимагати ручного редагування функції `main()` чи внесення змін до глобальних конфігураційних списків. Модуль повинен реєструвати себе автоматично.

До появи стандарту C++20 створення таких децентралізованих систем незмінно наражалося на фундаментальну інженерну дилему між безпекою та швидкодією. Використання специфікатора `constinit` у поєднанні з інтрузивними структурами даних та атомарними операціями дозволяє вперше вирішити цю задачу з абсолютною гарантією відсутності аварій та нульовими накладними витратами.

## Архітектурний конфлікт: три невдалі підходи минулого

Перш ніж перейти до реалізації на C++20, проаналізуємо, чому класичні архітектурні патерни C++ виявилися непридатними для високонавантажених систем.

Якщо компонувальник операційної системи вирішить спочатку виконати конструктор `NetworkRegistrar`, метод `add_module` звернеться до сирої пам'яті `g_registry` ще до виклику її конструктора. Це спричиняє аварійне завершення процесу (SIGSEGV) ще до старту `main()`.

### Підхід 2: Синглтон Мейєрса (Ціна бар'єрів пам'яті)

Для подолання катастрофи SIOF традиційно застосовували синглтон Мейєрса:

```cpp
Registry& get_registry() {
    static Registry instance;
    return instance;
}
```

Стандарт C++11 гарантує потокобезпеку ініціалізації локальних статичних змінних. Проте за цю гарантію доводиться платити під час виконання. Для реалізації захисту компілятор генерує прихований 64-бітний прапорець ініціалізації (`guard variable`) та обгортає доступ до `instance` системними викликами `__cxa_guard_acquire` та `__cxa_guard_release`.

При кожному зверненні до `get_registry()` процесор змушений виконувати операцію атомарного читання з бар'єром пам'яті (англ. *acquire fence*) та умовний перехід. У гарячих шляхах виконання, де підсистеми записують тисячі метрик за секунду, такі накладні витрати стають відчутним вузьким місцем. Крім того, при завершенні програми порядок знищення синглтонів залишається неконтрольованим, що часто призводить до збоїв при виході з процесу.

### Підхід 3: Двоетапна ручна ініціалізація

Третій поширений варіант — повна відмова від глобальних конструкторів на користь ручного виклику `init_all_subsystems()` на самому початку функції `main()`. Цей підхід усуває проблеми SIOF та витрат на бар'єри, але повністю руйнує децентралізацію: додавання будь-якого модуля вимагає модифікації головного файлу програми, що унеможливлює створення модульних плагінів та відкритих бібліотек.

## Рішення C++20: constinit, інтрузивні списки та безблокувальна синхронізація

Специфікатор `constinit` дозволяє поєднати найкращі риси всіх трьох підходів:

1. **Гарантія готовності пам'яті:** Завдяки `constinit` голова реєстру та його базові структури гарантовано проходять константну ініціалізацію під час компіляції. Вони готові приймати звернення в момент завантаження двійкового образу, виключаючи SIOF.
2. **Нульова вартість доступу:** Немає жодних прихованих викликів `__cxa_guard_acquire` чи перевірок прапорців. Звернення до реєстру перетворюється на пряму інструкцію адресації пам'яті в секції `.data`.
3. **Повна децентралізація:** Модулі продовжують реєструватися автоматично через власні глобальні дескриптори.
4. **Висока продуктивність завдяки thread_local:** Для локального накопичення метрик потоку використовується `constinit thread_local`, що усуває потребу в міжпотокових блокуваннях.

## Крок 1: Проектування вузлів інтрузивного списку

Традиційні контейнери на зразок `std::vector` або `std::list` виділяють пам'ять у купі (динамічній пам'яті). Під час глобальної ініціалізації виділення динамічної пам'яті є небажаним, оскільки системний розподілювач пам'яті (наприклад, `malloc` або `tcmalloc`) сам може перебувати в процесі ініціалізації.

Інтрузивний зв'язний список розв'язує цю проблему елегантно: вказівник на наступний елемент (`next`) зберігається безпосередньо всередині самого дескриптора модуля. Пам'ять під дескриптор виділяється статично у відповідній одиниці трансляції модуля.

:::code proj-safe-registry/cpp/krok-1-proektuvannia.cpp

Використання `std::string_view` замість `const char*` або `std::string` надає зручний інтерфейс із збереженням інформації про довжину рядка без динамічного виділення пам'яті. Конструктор позначено як `constexpr` та `noexcept`, що дозволяє компілятору повністю обчислити стан вузла на етапі компіляції.

Завдяки цьому кожен вузол розміщується безпосередньо в статичній пам'яті відповідного вихідного файлу. Відсутність динамічного виділення пам'яті робить цю структуру придатною для застосування в найбільш жорстких умовах — від мікроконтролерів без динамічної купи до ядер операційних систем.

## Модель пам'яті та апаратна синхронізація

Реалізований реєстр спирається на стандартизовану модель пам'яті C++ (папір N2429). Розглянемо детально, як упорядкування пам'яті гарантує коректність роботи на різних процесорних архітектурах:

На архітектурах зі строгою моделлю пам'яті (x86-64 / AMD64) апаратне забезпечення автоматично підтримує порядок записів і читань (Total Store Order, TSO). Операція `load(memory_order_acquire)` та `store(memory_order_release)` транслюються у звичайні інструкції `MOV`, не вимагаючи спеціальних інструкцій бар'єрів пам'яті на кшталт `MFENCE`.

На архітектурах зі слабкою моделлю пам'яті (ARM64, RISC-V) процесор вільний переставляти незалежні операції доступу до пам'яті. У цьому випадку компілятор генерує інструкції `LDAR` (Load-Acquire) та `STLR` (Store-Release) на ARM64. Це гарантує, що новий потік спочатку побачить повністю заповнені поля `SubsystemNode` у кеш-пам'яті, і лише потім — оновлений покажчик `head_`. Початкова статична константна ініціалізація `g_registry` виключає потребу в синхронізації створення самого реєстру.

## Поведінка у вбудованих системах (Bare-Metal мікроконтролери)

Для розробників прошивок мікроконтролерів (наприклад, архітектури ARM Cortex-M або RISC-V) застосування `constinit` відкриває унікальні переваги при старті пристрою:

У класичному циклі запуску мікроконтролера вектор скидання `Reset_Handler` виконує дві фундаментальні процедури:

1. Копіювання початкових значень глобальних змінних із енергонезалежної Flash-пам'яті в оперативну пам'ять SRAM (секція `.data`).
2. Занулення блоку пам'яті невизначених статичних змінних у SRAM (секція `.bss`).

Після цього традиційне середовище виконання C++ викликає функцію `__libc_init_array`, яка послідовно обходить таблицю покажчиків на конструктори глобальних об'єктів. Якщо в системі використовуються лише змінні з `constinit`, таблиця конструкторів `.init_array` залишається порожньою!

Це означає, що пристрій готовий до негайного виконання коду обробників переривань без жодної затримки на виклик конструкторів. Усі регістри периферії, таблиці дескрипторів та структури драйверів уже перебувають у валідному початковому стані безпосередньо після завершення базового апаратного копіювання пам'яті. Це критично для систем реального часу з жорсткими обмеженнями часу готовності після подачі живлення (англ. *power-on reset latency*).

## Сигнал-безпека та обробка збоїв до запуску main()

У критичних серверних системах важливо мати можливість перехопити аварійні сигнали операційної системи (SIGSEGV, SIGABRT, SIGFPE), якщо помилка сталася ще на етапі динамічної ініціалізації сторонніх бібліотек.

Традиційні реєстри на синглтонах Мейєрса не є сигнал-безпечними (англ. *async-signal-safe*): виклик функції з локальною статичною змінною зсередини обробника сигналу призводить до взаємного блокування (англ. *deadlock*), якщо сигнал виник у процесі захоплення `__cxa_guard_acquire`.

Натомість реєстр на базі `constinit` володіє властивістю повної сигнал-безпеки:

1. Пам'ять реєстру вже гарантовано ініціалізована на етапі завантаження.
2. Обхід списку через `head_.load(std::memory_order_relaxed)` не викликає жодних блокувань і не виділяє пам'ять у купі.
3. Обробник критичного збою може безпечно пройти по зв'язному списку `g_registry`, зчитати імена всіх зареєстрованих підсистем та зберегти детальний звіт про стан системи в енергонезалежний журнал або аварійний дамп пам'яті.

## Поведінка при динамічному завантаженні бібліотек (dlopen / LoadLibrary)

Важливою перевагою наведеної архітектури є повна сумісність із динамічними модулями, що завантажуються в процесі роботи програми через `dlopen` (Linux) або `LoadLibrary` (Windows).

Коли спільна бібліотека (.so або .dll) відображається в адресний простір працюючого процесу:

1. Завантажувач операційної системи знаходить спільний символ `g_registry` (завдяки `inline` та зовнішньому зв'язуванню) і прив'язує його до вже існуючого екземпляра в пам'яті головного процесу.
2. Виконуються динамічні конструктори статичних об'єктів завантаженої бібліотеки (функція `.init` або масив `.init_array`).
3. Викликається конструктор `AutoRegister` нового плагіна, який виконує CAS-додавання до списку.
4. Оскільки `g_registry` вже давно існує і функціонує, новий модуль безпечно додається до списку без потреби перезапуску чи зупинки робочих потоків.

## Взаємодія з оптимізаціями міжмодульного компонування (LTO)

При використанні оптимізацій компонування (Link-Time Optimization, LTO / Whole Program Optimization) компілятор аналізує граф викликів усієї програми цілком:

- Змінні, позначені як `constinit`, розглядаються оптимізатором як такі, що мають константну початкову базу даних.
- Оптимізатор може повністю вбудувати (inline) методи `register_subsystem` у динамічні конструктори модулів.
- Якщо список зареєстрованих підсистем залишається незмінним після старту програми, компілятор здатен розгорнути цикл `start_all()` у пряму послідовність прямих викликів функцій, усуваючи накладні витрати на розіменування покажчиків зв'язного списку.

## Інженерний аналіз: асемблерний вивід та оптимізації

Щоб переконатися у відсутності накладних витрат, порівняємо згенерований асемблерний код для доступу до `constinit` об'єкта та синглтона Мейєрса на архітектурі x86-64 (GCC 13, прапорець `-O2`).

### Звернення через constinit:

```nasm
; Звернення до g_registry:
movq    g_registry(%rip), %rax      ; Пряме завантаження покажчика з секції .data
testq   %rax, %rax

```

## Тестування та діагностика в інженерній практиці

Для підтвердження надійності архітектури в сучасних конвеєрах неперервної інтеграції (CI) застосовують спеціалізовані інструменти динамічного аналізу:

1. **ThreadSanitizer (TSan):** Запуск програми під керуванням прапорця `-fsanitize=thread` перевіряє відсутність гонитви даних (англ. *data race*) під час одночасної реєстрації вузлів та ітерації списку. Безблокувальний алгоритм CAS у поєднанні з `memory_order_release` успішно проходить усі тести TSan без зауважень.
2. **AddressSanitizer (ASan):** Прапорець `-fsanitize=address` верифікує відсутність витоків пам'яті та коректність роботи зі статичними адресами дескрипторів `SubsystemNode`.
3. **Статична верифікація через static_assert:** Оскільки дескриптори підсистем є константними виразами, коректність їхніх полів (наприклад, валідність діапазону пріоритетів чи ненульова довжина імені) може бути перевірена на етапі збірки:
   ```cpp
   static_assert(!s_mem_node.name.empty(), "Ім'я підсистеми не може бути порожнім");
   static_assert(s_mem_node.priority > 0, "Пріоритет підсистеми повинен бути додатним");
   ```

## Практичні рекомендації та висновки

Розглянутий патерн інтрузивного реєстру демонструє, як сучасний стандарт C++20 дозволяє будувати безкомпромісні системні архітектури:

- **Абсолютна безпека старту:** Специфікатор `constinit` перетворює ризик аварій SIOF на перевірку часу компіляції.
- **Ефективність пам'яті:** Інтрузивні списки виключають виділення динамічної пам'яті в купі на етапі ініціалізації.
- **Масштабованість:** Поєднання `inline constinit` для глобального стану та `constinit thread_local` для локальних буферів забезпечує максимальну пропускну здатність у багатопотокових середовищах.
