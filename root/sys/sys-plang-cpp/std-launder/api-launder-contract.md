# 📋 Повний контракт і межі застосування std::launder

Специфікація функції `std::launder` визначає точні правила отримання валідного вказівника на об'єкт, створений у попередньо зайнятому сховищі, запобігаючи помилковим оптимізаціям доступу до незмінних даних та таблиць віртуальних методів.

## Сигнатура та оголошення

Функція визначена в стандартному заголовковому файлі `<new>` і доступна, починаючи зі стандарту C++17:

```cpp
namespace std {
    template <class T>
    [[nodiscard]] constexpr T* launder(T* p) noexcept;
}
```

Атрибут `[[nodiscard]]` додано в C++20 для запобігання викликам, результат яких відкидається (оскільки функція не має побічних ефектів у пам'яті, її виклик без збереження значення є беззмістовним).

### Обмеження на параметри шаблону (Template Constraints)

Стандарт C++ накладає жорсткі обмеження на тип `T`, з яким може бути інстанційовано шаблон `std::launder`:

1. `T` не може бути типом функції (англ. *function type*). Наприклад, виклик `std::launder(&func)` призводить до помилки компіляції.
2. `T` не може бути типом `void` (з будь-якими `cv`-кваліфікаторами: `void`, `const void`, `volatile void`). Вираз `std::launder(static_cast<void*>(ptr))` є синтаксично некоректним.
3. `T` може бути типом масиву або об'єктним типом (англ. *object type*). Якщо `T` є масивом відомого розміру `U[N]`, `std::launder` повертає вказівник на перший елемент масиву або на весь масив відповідно до типу вказівника.

Формальна перевірка обмежень мовою концептів (C++20) або SFINAE еквівалентна наступному виразу:

```cpp
template <typename T>
requires (!std::is_function_v<T> && !std::is_void_v<T>)
[[nodiscard]] constexpr T* launder(T* p) noexcept;
```

## Формальні передумови (Preconditions)

Згідно з пунктом `[ptr.launder]` міжнародного стандарту ISO/IEC 14882, виклик `std::launder(p)` має чітко визначену поведінку тоді й тільки тоді, коли виконуються всі наступні передумови:

1. **Існування об'єкта**: Вказівник `p` повинен представляти адресу в пам'яті, де на момент виклику реально існує живий об'єкт `X` типу `T` (або `X` є об'єктом типу, що збігається з `T` з точністю до `cv`-кваліфікаторів). Це означає, що час життя `X` уже розпочався (конструктор успішно завершився або тип є тривіальним) і ще не закінчився (деструктор ще не розпочато).
2. **Байтове охоплення**: Кожен байт ділянки пам'яті від адреси `p` до `p + sizeof(T)` повинен бути частиною виділеного сховища об'єкта `X`.
3. **Досяжність через походження**: Об'єкт `X` має бути досяжним із вказівника `p` (англ. *reachable through p*). Якщо `p` вказує на підоб'єкт або елемент масиву, `std::launder(p)` повертає вказівник саме на цей підоб'єкт або елемент, а не на весь охоплюючий об'єкт.

Порушення хоча б однієї з цих передумов робить виклик `std::launder(p)` **невизначеною поведінкою (Undefined Behavior)**.

## Семантичний ефект і повернене значення

Функція `std::launder(p)` повертає значення типу `T*`, яке:
- Чисельно дорівнює адресі, переданій у параметрі `p` (значення вказівника як адреси в адресному просторі не змінюється).
- Має новий ланцюжок походження (англ. *provenance*) в моделі оптимізатора, що зв'язує вказівник із конкретним живим об'єктом `X`, розташованим за цією адресою.
- Анулює всі попередні припущення оптимізатора щодо константності полів (`const`), незмінності прив'язки посилань (`&`) та таблиць віртуальних методів (`vptr`), які могли бути сформовані на основі попередніх операцій за цією адресою.

## Робота в константних виразах (constexpr evaluation)

Починаючи з C++17, функція `std::launder` позначена специфікатором `constexpr`. Це дозволяє використовувати її під час обчислень на етапі компіляції:

```cpp
constexpr int evaluate_at_compile_time() {
    struct Item {
        const int value;
    };

    alignas(Item) std::byte storage[sizeof(Item)];
    
    // Створення об'єкта в constexpr-контексті (C++20 через std::construct_at)
    Item* p = std::construct_at(reinterpret_cast<Item*>(storage), 42);
    
    // Отримання через launder у constexpr
    Item* clean_p = std::launder(reinterpret_cast<Item*>(storage));
    return clean_p->value;
}

static_assert(evaluate_at_compile_time() == 42);
```

Під час компіляції інтерпретатор `constexpr`-виразів компілятора (наприклад, у Clang та GCC) суворо перевіряє дотримання передумов `[ptr.launder]`. Якщо виклик `std::launder` спрямовано на неініціалізоване сховище або неіснуючий об'єкт, компілятор миттєво зупиняє компіляцію з детальною помилкою трасування, виявляючи помилки пам'яті ще до запуску програми.

## Детальний розбір роботи з підоб'єктами та масивами

Особливу увагу стандарт приділяє ситуаціям, коли об'єкти створюються всередині масивів або як члени більших структур.

### 1. Елементи масивів і адресна арифметика

Розглянемо випадок, коли масив байтів або масив структур перевикористовується для створення послідовності нових об'єктів:

```cpp
struct Element {
    const int val;
};

void array_example() {
    alignas(Element) std::byte storage[sizeof(Element) * 2];

    auto* e0 = new (storage + 0 * sizeof(Element)) Element{10};
    auto* e1 = new (storage + 1 * sizeof(Element)) Element{20};

    // Отримання вказівника на перший елемент
    Element* p0 = std::launder(reinterpret_cast<Element*>(storage));
    
    // Чи можна робити p0 + 1 для доступу до другого елемента?
    // За стандартом C++: так, якщо p0 вказує на елемент масиву Element[2].
    // Але якщо об'єкти створювалися окремо у сирому буфері std::byte[],
    // вони формально не утворюють єдиний масив Element[2] до C++20!
    // Безпечний підхід:
    Element* p1 = std::launder(reinterpret_cast<Element*>(storage + sizeof(Element)));
}
```

У C++17 окремі виклики розміщувального `new` створюють окремі повні об'єкти `Element`, а не єдиний об'єкт-масив `Element[2]`. Тому адресна арифметика `p0 + 1` формально виходить за межі першого об'єкта `Element`. Щоб отримати валідний вказівник на другий об'єкт, необхідно явно застосувати `std::launder` до адреси другого елемента.

### 2. Підоб'єкти та базові класи

Якщо об'єкт `Derived` розміщується в пам'яті, де раніше жив інший об'єкт `Derived`, а ми маємо вказівник на його базовий клас `Base*`:

```cpp
struct Base {
    int x;
};

struct Derived : Base {
    const int y;
};

void subobject_example() {
    alignas(Derived) std::byte buf[sizeof(Derived)];
    
    auto* d1 = new (buf) Derived{{1}, 2};
    Base* b = d1; // вказівник на підоб'єкт Base

    d1->~Derived();
    new (buf) Derived{{10}, 20};

    // Виклик std::launder(b) повертає Base*, що вказує на підоб'єкт Base нового Derived.
    Base* new_b = std::launder(b);
    
    // Чи можна робити static_cast<Derived*>(new_b)?
    // Так! Оскільки new_b тепер легально зв'язаний із новим об'єктом.
    Derived* new_d = static_cast<Derived*>(new_b);
    std::cout << new_d->y << '\n'; // 20
}
```

## Внутрішня взаємодія з бекендом компілятора (LLVM і GCC)

Функція `std::launder` не є звичайною функцією C++ — це вбудований інтринсик компілятора. Подивимося, як вона транслюється в проміжне представлення LLVM IR.

У LLVM для підтримки оптимізації девіртуалізації та усунення завантажень існує механізм інваріантних груп (англ. *invariant groups*). Компілятор Clang позначає завантаження віртуальних таблиць метаданими `!invariant.group`:

```llvm
; Звичайне читання vptr з інваріантною групою
%vtable = load ptr, ptr %obj, !invariant.group !0

; Виклик std::launder транслюється у спеціальну інструкцію
%laundered = call ptr @llvm.launder.invariant.group.p0(ptr %obj)

; Наступне читання vptr використовує новий SSA-вказівник
%new_vtable = load ptr, ptr %laundered, !invariant.group !0
```

Інтринсик `@llvm.launder.invariant.group` повідомляє оптимізаторам LLVM (зокрема проходам `EarlyCSE`, `GVN` та `Devirtualization`), що значення, асоційоване з цією інваріантною групою, за вказаною адресою змінилося. У результаті прохід усунення спільних підвиразів не видаляє друге читання, а прохід девіртуалізації не виконує помилкову підстановку методу старого класу.

Якщо оптимізації вимкнено або якщо клас не містить констант чи віртуальних методів, бекенд компілятора просто згортає `@llvm.launder.invariant.group(p)` у значення самого `p`.

## Матриця діагностики та валідності використання

Таблиця нижче деталізує різні патерни виклику `std::launder`, їхній статус за стандартом та обґрунтування з точки зору моделі пам'яті:

| Патерн використання у вихідному коді | Статус | Пояснення механізму |
| :--- | :--- | :--- |
| `std::launder(reinterpret_cast<T*>(aligned_buf))` після `new (aligned_buf) T(...)` | **Коректно** | Базовий канонічний патерн: отримання валідного вказівника з масиву `std::byte[]`. |
| `auto* p = new (buf) T(...); auto* p2 = std::launder(p);` | **Коректно, але надлишково** | `new` уже повертає валідний вказівник з чистим походженням. `p2 == p`. |
| `std::launder(static_cast<void*>(buf))` | **Помилка компіляції** | Тип `void` заборонено стандартом у шаблоні `std::launder`. |
| `std::launder(p)` на неініціалізованому буфері (до виклику placement `new`) | **Невизначена поведінка (UB)** | Порушено передумову: об'єкт типу `T` ще не існує за вказаною адресою. |
| `std::launder(p)` після `p->~T()` (до нового створення) | **Невизначена поведінка (UB)** | Порушено передумову: час життя об'єкта завершено. |
| `std::launder(reinterpret_cast<float*>(int_ptr))` де лежить `int` | **Невизначена поведінка (UB)** | Порушення Strict Aliasing: у пам'яті немає живого об'єкта типу `float`. |
| `std::launder(&Derived)` після заміни базового класу | **Коректно** | Оновлює інформацію про динамічний тип і `vptr` для девіртуалізатора. |
| `std::launder(ptr_to_element + 1)` для виходу за межі масиву | **Невизначена поведінка (UB)** | Недопустима адресна арифметика та відсутність живого об'єкта. |

## Інтеграція зі стандартною бібліотекою

Реалізація стандартних узагальнених контейнерів і типів-обгорток спирається на `std::launder` у ключових операціях доступу до пам'яті.

### 1. `std::optional<T>`

Стандартний клас `std::optional` зберігає значення у внутрішньому вирівняному буфері `std::byte storage_[sizeof(T)]` (або `union`).

Коли користувач викликає метод `emplace()` чи оператор присвоєння `operator=(T&&)`:
1. Якщо об'єкт уже існував, викликається деструктор старого об'єкта.
2. Конструюється новий об'єкт через розміщувальний `new`.
3. Методи доступу `operator*()`, `operator->()` та `value()` зобов'язані використовувати `std::launder`:

```cpp
template <typename T>
class optional_storage {
    alignas(T) std::byte data_[sizeof(T)];
    bool init_ = false;

public:
    constexpr T& value() & {
        if (!init_) throw std::bad_optional_access{};
        return *std::launder(reinterpret_cast<T*>(data_));
    }

    constexpr const T& value() const& {
        if (!init_) throw std::bad_optional_access{};
        return *std::launder(reinterpret_cast<const T*>(data_));
    }
};
```

### 2. `std::variant<Types...>`

У разі зміни активної альтернативи у варіативному контейнері `std::variant` стара альтернатива руйнується, а на її місці будується нова. Якщо обидві альтернативи містять спільний тип або тип із константними полями, звернення до активного значення через спільне сховище обов'язково фільтрується через `std::launder`.

### 3. `std::any` та оптимізація малих об'єктів (SSO)

Клас `std::any` використовує внутрішній статичний буфер для типів, розмір яких не перевищує місткість SSO. Під час перезапису значення об'єктом іншого типу з тією самою структурою або константними полями `std::any_cast` використовує `std::launder` для повернення безпечного посилання.

## Співвідношення з іншими низькорівневими функціями керування пам'яттю

C++ розвиває модель пам'яті від стандарту до стандарту. Важливо розрізняти сфери відповідальності споріднених функцій:

```text
               Створення об'єкта                   Отримання вказівника
┌──────────────────────────────────────────────┐ ┌───────────────────────────┐
│ placement new (buf) T(...)  [C++98]          │ │ std::launder(p)  [C++17]  │
│ std::construct_at(p, ...)   [C++20]          │ │ (оновлює походження,     │
│ std::start_lifetime_as<T>(p) [C++23]         │ │  не створює об'єкт)       │
└──────────────────────────────────────────────┘ └───────────────────────────┘
```

- **`std::construct_at` (C++20)**: Викликає конструктор за вказаною адресою і *одразу повертає* валідний вказівник. Якщо результат виклику зберігається, `std::launder` не потрібен.
- **`std::start_lifetime_as` (C++23)**: Не викликає конструктор, але формально розпочинає час життя об'єкта неявного типу в заповненому буфері байтів і повертає вже очищений (laundered) вказівник.
- **`std::launder` (C++17)**: Не викликає конструктор і не починає час життя; він лише відновлює валідність вказівника на об'єкт, чий час життя *вже* розпочато іншим шляхом.

## Поведінка в інструментах статичного й динамічного аналізу

1. **UndefinedBehaviorSanitizer (UBSan)**: Прапорець `-fsanitize=undefined` (зокрема підгрупа `-fsanitize=vptr`) відстежує коректність динамічного типу об'єктів. Якщо об'єкт у сховищі було замінено без `std::launder`, а виклик віртуального методу пішов через старий вказівник, UBSan фіксує помилку `member call on address which does not point to an object of type Base`.
2. **Clang / GCC Warn Flags**: Сучасні компілятори мають попередження `-Wplacement-new` та `-Wstrict-aliasing`, які допомагають виявляти підозрілі перетворення адрес сирих буферів без очищення через `std::launder`.
