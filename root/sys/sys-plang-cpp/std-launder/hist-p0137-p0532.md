# 📜 Історія появи std::launder: від дефекту Core 1776 до P0137 і P0532

Поява функції `std::launder` у стандарті C++17 стала результатом тривалого протистояння між розробниками компіляторних оптимізаторів та авторами стандартної бібліотеки, у якому виявилося, що базовий контейнер `std::optional` формально породжував невизначену поведінку з першого дня свого проектування.

## Витік проблеми: криза навколо std::optional

На початку 2010-х років, після прийняття революційного стандарту C++11, комітет ISO C++ (робоча група WG21) активно працював над розширенням стандартної бібліотеки в межах технічної специфікації *Library Fundamentals TS*. Одним із найбільш очікуваних нововведень був клас `std::optional<T>` (автори пропозиції — Фернандо Каччола та Анджей Кшеменський).

Контейнер `std::optional` покликаний представляти об'єкт, який може бути присутнім або бути відсутнім (`std::nullopt`), без використання динамічної пам'яті в купі.

На відміну від звичайного `std::unique_ptr`, ключовою перевагою `std::optional` мала бути безкомпромісна швидкодія: значення типу `T` розміщувалося безпосередньо всередині самого об'єкта `optional` у вирівняному буфері байтів через розміщувальний оператор `new` (англ. *placement new*).

Коли користувач виконував операцію присвоєння нової конфігурації:

```cpp
struct ServerConfig {
    const int port;
    const std::string host;
};

std::optional<ServerConfig> opt;
opt.emplace(ServerConfig{8080, "localhost"});

// Перезапис значення новою конфігурацією:
opt.emplace(ServerConfig{9090, "127.0.0.1"});
```

Реалізація `std::optional` знищувала старий об'єкт викликом деструктора і створювала новий об'єкт у тому самому буфері пам'яті через `placement new`.

Проте виявилася фундаментальна проблема: згідно з пунктом `[basic.life]` стандарту C++11 та C++14, якщо клас містить константні поля або посилання, автоматичне прозоре заміщення об'єкта в пам'яті **заборонялося**.

Це означало, що будь-який наступний виклик `opt->port` або `opt.value()` формально розіменовував вказівник на старий, знищений об'єкт і був класичною невизначеною поведінкою (Undefined Behavior). Стандартна бібліотека C++ пропонувала контейнер, який фізично неможливо було реалізувати за правилами самої мови C++.

## Дефект Core Issue 1776 та аналіз оптимізаторів

У листопаді 2013 року розробники зафіксували офіційний звіт про дефект у робочій групі стандартизації ядра мови (Core Working Group, CWG) під назвою **Core Issue 1776**: *«Replacement of class objects containing const or reference members»* (Заміщення об'єктів класів, що містять константні або посилальні члени).

Суть дефекту полягала в конфлікті двох базових принципів мови:
1. Модель пам'яті C++ надавала компілятору право вважати, що значення `const`-поля або адреса поля-посилання ніколи не змінюються протягом існування пам'яті, де вони розташовані.
2. Компілятори (зокрема LLVM Clang та GCC) використовували це право для агресивного кешування значень констант у регістрах під час оптимізацій `Constant Propagation` та `Global Value Numbering` (GVN).
3. Якщо дозволити прозоре заміщення для таких типів автоматично, оптимізаторам довелося б відмовитися від кешування констант у всьому коді програми, оскільки будь-який запис у пам'ять міг потенційно означати знищення старого об'єкта через деструктор і створення нового.

Комітет опинився перед вибором між двома неприйнятними варіантами:
- **Варіант А**: Послабити правила оптимізації компіляторів. Це призвело б до значного падіння продуктивності коду C++ у світовому масштабі. Розробники компіляторів (зокрема інженери Google, Apple, Red Hat та Microsoft) виступили категорично проти.
- **Варіант Б**: Заборонити використання `std::optional`, `std::variant` та алокаторів пам'яті з типами, що містять `const`-поля. Це зробило б стандартні контейнери неповноцінними й незручними для практичного програмування.

## Пропозиція P0137: народження концепції «відмивання»

Розв'язання кризи запропонував Річард Сміт (Richard Smith), головний архітектор компілятора Clang у компанії Google та редактор стандарту мови C++.

На засіданні комітету в місті Кона (Гаваї) у жовтні 2015 року Річард Сміт представив документ **P0137R0** (а згодом його фінальну редакцію **P0137R1** у березні 2016 року в Джексонвіллі) під назвою: *«Replacement of class objects containing const, reference, or variant members»*.

Ідея Річарда Сміта полягала у компромісі:
- Зберегти агресивні оптимізації компілятора за замовчуванням. Для 99% звичайного коду оптимізатор продовжує вважати константи абсолютними інваріантами.
- Для низькорівневих бібліотек, які дійсно повторно використовують пам'ять під нові об'єкти, надати спеціальну функцію-бар'єр, яка явно скидає припущення оптимізатора щодо конкретної адреси пам'яті.

Цю функцію було названо `std::launder` (від англійського терміна *pointer laundering* — відмивання вказівника).

Під час обговорення назви розглядалися варіанти `std::refresh_pointer`, `std::strip_invariants` та `std::reuse_storage`. Комітет обрав `std::launder` за аналогією з усталеним терміном компіляторних розробників: «відмивання» вказівника від його минулої історії та походження.

Функція мала нульову вартість у машинному коді: вона не генерувала жодної процесорної інструкції, а слугувала виключно вказівкою для графа залежностей в оптимізаторі під час компіляції.

## Уточнення P0532: підтримка union і варіантів

Паралельно з роботою над P0137 виникло питання щодо об'єднань (`union`) та нового типу `std::variant`.

Коли в `std::variant` змінюється активний тип (наприклад, з `std::string` на `int`), відбувається руйнування старого підоб'єкта й створення нового. Якщо структура варіанта використовує спільний буфер, виникали сумніви, чи достатньо семантики P0137 для всіх сценаріїв доступу через підоб'єкти.

Г'юберт Тонг (Hubert Tong) з компанії IBM спільно з учасниками робочої групи ядра мови підготував документ **P0532R0** (*«Support for variant member access»*), який було розглянуто на засіданні в Іссаква (Вашингтон) у листопаді 2016 року.

P0532R0 уточнив формальні правила досяжності об'єктів у пункті `[ptr.launder]`:
- Чітко визначено поняття досяжності байтів сховища (`reachable bytes`).
- Зафіксовано правила для вказівників на підоб'єкти та масиви.
- Закріплено вимогу, що `std::launder` не створює новий об'єкт, а лише відновлює зв'язок із уже існуючим живим об'єктом.

## Прийняття до C++17 і наслідки

На засіданні WG21 у місті Кона в березні 2017 року пропозицію P0137R1 разом із виправленнями P0532R0 було офіційно включено до фінального проекту міжнародного стандарту **C++17 (ISO/IEC 14882:2017)**.

Це рішення мало такі історичні наслідки:
1. **Легітимізація `std::optional` та `std::variant`**: Реалізації бібліотек `libc++` (LLVM), `libstdc++` (GCC) та `MSVC STL` отримали легальний інструмент для підтримки типів із `const`-полями без порушення вимог стандарту.
2. **Формалізація графа походження**: Компілятори отримали чітку основу для впровадження SSA-оптимізацій на основі інваріантних груп (`llvm.launder.invariant.group`), що дозволило розвивати девіртуалізацію викликів без остраху зламати сторонній низькорівневий код.
3. **Фундамент для майбутніх стандартів**: Рішення проблеми Core 1776 заклало основу для появи `std::construct_at` у C++20 та `std::start_lifetime_as` у C++23, які продовжили вдосконалення низькорівневої моделі пам'яті C++.
