# ⚙️ Три роботи явного об'єкта в одному файлі

Один компільований файл на C++23, у якому явний параметр об'єкта робить три різні речі — заміняє чотири рукописні аксесори одним тілом, дає базі-домішці бачити нащадка без CRTP і навчає лямбду кликати саму себе, — і чотири місця, де все це тихо ламається. Тихо — бо жодна з чотирьох пасток не дає ні помилки компіляції, ні попередження.

## Що будуємо

Тип `Note` тримає заголовок прямим членом, а текст — за `unique_ptr`. Довкола нього три домішки: одна друкує, друга порівнює, третя чіпляє мітку й дозволяє ланцюжок викликів. Плюс обхід дерева вкладених вузлів.

Написане звичайним способом, це вісім тіл аксесорів (чотири кваліфікації на два члени), бази, параметризовані нащадком, і рекурсія через `std::function` або винесену назовні функцію. Нижче кожен із трьох пунктів займає по три-чотири рядки.

Вісім копій — це не просто вісім рядків. Щойно в аксесорі з'явиться бодай перевірка («тексту ще не завантажено — підвантажити»), копії починають розходитися, і розійдеться найпершою `const&&`-версія: її кличуть раз на рік, тестів на неї не пишуть, і виправлення в неї не переносять. Одна шаблонна функція розходитися не вміє за побудовою — тому далі йдеться не про економію символів, а про кількість місць, де живе одна й та сама думка.

## Перевірка, чи риса взагалі є

Рік стандарту тут поганий орієнтир. Явний параметр об'єкта випустили з різних боків у різний час: MSVC — у Visual Studio 2022 17.2 (компілятор 19.32), ще до самого стандарту; GCC й Clang — у 14-му та 18-му випусках, обидва вже після. Тому питаємо не про `__cplusplus`, а про саму рису:

```cpp
// notes.cpp — усе, що нижче, лежить у цьому файлі в такому ж порядку
#include <algorithm>
#include <concepts>
#include <iostream>
#include <memory>
#include <string>
#include <type_traits>
#include <utility>
#include <vector>

#if !defined(__cpp_explicit_this_parameter) || __cpp_explicit_this_parameter < 202110L
#  error "нема явного параметра об'єкта: треба GCC 14+, Clang 18+ або MSVC 19.32+"
#endif
#if !defined(__cpp_lib_forward_like) || __cpp_lib_forward_like < 202207L
#  error "нема std::forward_like: треба стандартна бібліотека C++23"
#endif
```

Два макроси незалежні: перший — про мову (P0847R7), другий — про бібліотеку (P2445R1). Компілятор може вміти перше й не мати другого, якщо його поставили поруч зі старою стандартною бібліотекою.

## Домішки, які бачать нащадка

```cpp
struct Printable {
    void print(this const auto& self) {          // self — тип НАЩАДКА
        std::cout << self.label() << '\n';       // label() оголошує нащадок
    }
};

struct Comparable {
    template <class Self>
    bool operator==(this const Self& self, const Self& other) {
        return self.key() == other.key();
    }
};

struct Taggable {
    std::string tag;

    template <class Self>
    auto&& with_tag(this Self&& self, std::string t) {
        self.tag = std::move(t);
        return std::forward<Self>(self);         // віддає НАЩАДКА, не Taggable
    }
};
```

Жодна з трьох — не шаблон від нащадка. Це звичайні класи, які можна успадкувати всі три одразу, і кожна всередині бачить справжній тип об'єкта, бо `Self` виводиться з виразу виклику.

Форма параметра в кожній домішці різна, і різниця не стилістична. `print` лише читає, тож бере `this const auto&`: одна константна інстанція на нащадка замість чотирьох, і жодного `forward` у тілі. `with_tag` мусить віддати об'єкт далі в ланцюжок, тому їй потрібен саме `this Self&&` — інакше вона перетворила б rvalue на lvalue й обірвала переміщення на першому ж кроці. Правило просте: передавальне посилання беруть тоді, коли категорію треба **передати далі**, а не просто прочитати.

В `operator==` обидва операнди оголошені тим самим `Self` навмисно. Виведення мусить дати один тип із двох місць — з об'єкта й з аргументу; якщо типи різні, кандидат просто відпадає, і порівняти `Note` з чимось стороннім не вийде. Другий параметр із власним `auto` цю перевірку скасував би.

Одне обмеження тут варто назвати відразу, бо його легко прийняти за ваду: домішка не стає другом нащадка. `self.label()` працює, поки `label` **публічний**; до приватного члена база не дістанеться, хоч `Self` і правильного типу. Перевірка доступу не змінилася ні на йоту — змінилося лише те, звідки береться тип.

## Клас із двома різними членами

```cpp
class Note : public Printable, public Comparable, public Taggable {
    std::string title_;
    std::unique_ptr<std::string> body_;

public:
    Note(std::string t, std::string b)
        : title_(std::move(t)), body_(std::make_unique<std::string>(std::move(b))) {}

    // прямий член: категорію несе сам вираз доступу
    template <class Self>
    auto&& title(this Self&& self) { return std::forward<Self>(self).title_; }

    // член за вказівником: розіменування кваліфікаторів не пам'ятає
    template <class Self>
    auto&& body(this Self&& self) { return std::forward_like<Self>(*self.body_); }

    std::string label() const { return title_ + " [" + tag + ']'; }
    const std::string& key() const { return title_; }
};
```

Два аксесори виглядають майже однаково, але роблять різне, і саме тут найчастіше помиляються.

Для `title_` вистачає [`std::forward`](root:sys-plang-cpp/perfect-forwarding): вираз `self.title_` бере категорію й константність від `self`, тобто від об'єкта, і сам стає тим, чим треба.

Для `body_` цей ланцюжок обривається на розіменуванні. `self.body_` для константного об'єкта справді буде `const std::unique_ptr<std::string>&` — але константність [`unique_ptr`](root:sys-plang-cpp/unique-ptr) неглибока: його `operator*` навіть у константному вигляді віддає звичайне змінюване `std::string&`, і завжди lvalue. Вказівник не пам'ятає, звідки він узявся, і кваліфікатори власника далі не проходять. `std::forward_like<Self>` накладає їх назад на довільний вираз: якщо `std::remove_reference_t<Self>` константний — додає `const`; якщо `Self&&` — rvalue-посилання, робить результат rvalue. Знімати `const` він не вміє, тож зіпсувати ним чужу гарантію не вийде.

> 🔧 **Навіщо це.** Обійти `forward_like` тут просто нічим. `return std::forward<Self>(self).body_` віддасть сам вказівник, а не текст. `return *self.body_` віддасть текст — але як змінюване `std::string&` навіть тоді, коли `Note` константний: компілюється мовчки, попереджень нема, і викликач із `const Note&` дістає право переписати те, що обіцяли не чіпати. Це не хиба реалізації, а те, як розумний вказівник улаштований за стандартом.

Тип результату в обох аксесорах — `auto&&`, і для `title` це не взаємозамінне з `decltype(auto)`, хоч рука й тягнеться. `decltype(auto)` бере буквально `decltype` від виразу після `return`, а `std::forward<Self>(self).title_` — звертання до члена без дужок; на такому виразі `decltype` дає **оголошений тип члена**, тобто `std::string` без жодного посилання. Аксесор тихо почав би повертати копію рядка на кожному виклику. Найпідступніше, що в `body` та сама заміна нешкідлива: там після `return` стоїть виклик функції, а `decltype` виклику — це його тип результату, посилання. Тому `auto&&` тримають скрізь: він виводиться за категорією виразу й не залежить від того, як саме той вираз записаний.

Що з цього вийшло — видно без запуску:

```cpp
struct Node { std::string name; std::vector<Node> kids; };

int main() {
    Note n{"Список", "молоко, хліб"};
    n.with_tag("побут").print();          // Taggable віддав Note&, далі Printable
                                          // друкує: Список [побут]
    Note m{"Список", "інше"};
    std::cout << std::boolalpha << (n == m) << '\n';   // true: ключі збігаються

    // ОДНЕ тіло аксесора — чотири різні сигнатури
    static_assert(std::is_same_v<decltype(n.title()),                std::string&>);
    static_assert(std::is_same_v<decltype(std::as_const(n).title()), const std::string&>);
    static_assert(std::is_same_v<decltype(std::move(n).title()),     std::string&&>);
    static_assert(std::is_same_v<decltype(std::as_const(n).body()),  const std::string&>);
    static_assert(std::is_same_v<decltype(std::move(n).body()),      std::string&&>);
```

`static_assert` тут не прикраса: він і є доказом, що з одного рядка постали чотири підписи, які інакше довелося б виписувати руками.

## Лямбда, що кличе себе

```cpp
    // ── те саме main, продовження ──
    Node root{"root", {{"a", {{"a1", {}}}}, {"b", {}}}};

    auto depth = [](this auto&& self, const Node& x) -> int {
        int deepest = 0;
        for (const Node& k : x.kids) deepest = std::max(deepest, self(k));
        return deepest + 1;
    };
    std::cout << depth(root) << '\n';                       // 3

    std::string taken = Note{"чернетка", "текст"}.body();   // ✔ безпечно: переміщення
    std::cout << taken << '\n';                             // ДО смерті тимчасового Note
}
```

`self` — саме це замикання, тож `self(k)` — прямий рекурсивний виклик: ні стирання типу, ні виділення пам'яті, ні змінної, яку можна забути ініціалізувати.

Зібране й запущене, це друкує чотири рядки:

```
Список [побут]
true
3
текст
```

Найцікавіше в цьому виводі те, чого не видно: жодного `static_cast` до типу нащадка, жодного параметра-шаблона в оголошенні домішок і жодного дубльованого тіла аксесора.

## Що ламається

**1. Нащадок затінює член бази.** Найдорожча пастка, і вона перейшла у спадок від [CRTP](root:sys-plang-cpp/crtp) без жодних змін:

```cpp
struct Reminder : Taggable {
    std::string tag;                               // затінює Taggable::tag
    void show() const { std::cout << '[' << Taggable::tag << "]\n"; }
};

Reminder r;
r.with_tag("терміново");   // Self = Reminder& → пише Reminder::tag
r.show();                  // друкує «[]»: член бази лишився порожній
```

`self` має тип нащадка, тому `self.tag` у тілі бази означає член нащадка. Компілюється, попереджень немає, розходяться два поля з однією назвою. Ліки прості: у домішці називати члени так, щоб нащадок не влучив випадково (`tag_` замість `tag`), або взагалі не тримати в домішці стану — хай його оголошує нащадок, а домішка лише пише.

**2. Посилання переживає власника.**

```cpp
const std::string& oops = Note{"a", "b"}.body();   // Note помирає в кінці виразу
std::cout << oops;                                 // читання звільненої пам'яті
```

Явний параметр об'єкта нічого не додає до [часу життя](root:sys-plang-cpp/dangling-references): те саме сталося б і з написаною руками `&&`-версією. Різниця з безпечним рядком у `main` — одна: там результат **забирають у значення** в тому ж повному виразі, тут — лише прив'язують до нього посилання.

Друга подоба тієї самої пастки ховається в ланцюжку. `Note{"a","b"}.with_tag("x").print()` цілком безпечне: усе відбувається в одному повному виразі. А от `auto&& kept = Note{"a","b"}.with_tag("x");` — уже ні: `with_tag` віддала `Note&&`, і продовження життя тимчасового на такий випадок не поширюється (воно працює лише тоді, коли посилання прив'язують до тимчасового **напряму**, а не до того, що повернула функція). Порятунок той самий: писати `auto kept = …` і забрати об'єкт собі.

**3. `this auto self` за значенням копіює захоплення.**

```cpp
auto count = [seen = 0](this auto self, const Node& x) -> int {   // ← БЕЗ &&
    ++seen;                                     // seen — член КОПІЇ замикання
    for (const Node& k : x.kids) self(k);
    return seen;
};
count(root);   // 1, а не 4
```

Усередині лямбди з явним об'єктом ім'я захоплення означає член того об'єкта, який названо параметром. Оголошений за значенням, він щоразу копія — приріст лягає в неї й гине разом із нею. Гірше: код компілюється **саме тому**, що об'єкт за значенням не константний, і `mutable` тут не потрібне (а разом із явним параметром воно й заборонене). Правильна форма — `this auto&& self`: тоді `seen` — член оригіналу, і функція повертає 4.

**4. Родина інстанцій.** Виведений `Self` робить функцію шаблоном, і тіло інстанціюється на кожну категорію виклику **й на кожного нащадка**: чотири варіанти легко стають дванадцятьма. [Ціна](root:sys-plang-cpp/instantiation-cost) лягає на час збірки й розмір бінарника. [Обмеження](root:sys-plang-cpp/concepts-constraints) звужує родину до одного типу й переносить помилку з глибини тіла на місце виклику:

```cpp
    template <class Self>
        requires std::same_as<std::remove_cvref_t<Self>, Note>
    auto&& title(this Self&& self) { return std::forward<Self>(self).title_; }
```

Зверніть увагу на `remove_cvref_t`: `Self` часто виводиться як `Note&`, і концепт, написаний прямо на `Self`, не спрацював би ніколи. Але сам концепт кількість інстанцій не зменшує — чотири кваліфікації лишаються чотирма. Зменшує її інше: тримати в шаблоні тільки тонке приведення, а важке тіло винести в одну звичайну функцію.

```cpp
    void validate() const;                     // не шаблон: одне тіло на весь клас
    template <class Self>
    auto&& body(this Self&& self) {
        self.validate();
        return std::forward_like<Self>(*self.body_);
    }
```

Тепер інстанцій усе ще чотири, але кожна — один рядок приведення й виклик; уся вага лежить в одному місці. Побачити це можна не на око: у справжньому проєкті зберіть об'єктний файл без оптимізації і полічіть тіла аксесора —

```
g++ -std=c++23 -O0 -c notes.cpp && nm -C --defined-only notes.o | grep -c 'Note::body'
```

Кожне з них до винесення `validate` містило б усю перевірку цілком.

## Збірка

```
g++     -std=c++23 -Wall -Wextra -o notes notes.cpp     # GCC 14+
clang++ -std=c++23 -stdlib=libc++ -o notes notes.cpp    # Clang 18+
cl      /std:c++latest /EHsc /permissive- notes.cpp     # MSVC 19.32+ (VS 2022 17.2)
```

Одна несподіванка саме тут: Clang разом із libstdc++ довго не збирав `std::forward_like` — libstdc++ оголошувала її з виведеним типом результату, а Clang тримає її за вбудовану, і одне на одне не лягало (усунуто в libstdc++ у серпні 2024-го заміною виведеного типу на рису). Тому в парі Clang + старший libstdc++ або беруть `-stdlib=libc++`, або оновлюють бібліотеку — [прапорці й підтримка стандартів](root:sys-plang-cpp/compiler-support) тут вирішують більше, ніж номер стандарту.
