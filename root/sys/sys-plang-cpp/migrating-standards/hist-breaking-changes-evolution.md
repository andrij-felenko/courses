# Історія розривних змін у C++: від недоторканності C++98 до регулярного очищення

Коли у 1998 році міжнародний комітет ISO затвердив перший офіційний стандарт мови C++ (ISO/IEC 14882:1998), фундаментальним інженерним законом системи проголосили принцип абсолютної зворотної сумісності: будь-який синтаксично коректний код, скомпільований у 1998 році, мав без змін збиратися новими версіями компіляторів через десять чи двадцять років. Цей принцип (англ. *backwards compatibility*) дозволив мові завоювати корпоративний світ, фінансову інфраструктуру, телекомунікаційні мережі та рушії операційних систем, утворивши мільярди рядків робочого програмного забезпечення. Проте зі зростанням складності мови та зміною апаратної архітектури процесорів абсолютна недоторканність застарілих рішень перетворилася на тягар технічного боргу, що стримував розвиток системи.

Еволюція мови сформувала чіткий прецедент: якщо певна конструкція порушує інваріанти безпеки пам'яті, блокує фундаментальні оптимізації або суперечить базовій моделі мови, комітет WG21 вдається до контрольованих розривних змін (англ. *breaking changes*). Історія цих рішень демонструє, як змінювалися пріоритети спільноти протягом чверті століття.

## Трагедія export template та перший розрив у C++11

Найгучнішою помилкою дизайну оригінального C++98 було ключове слово `export`, призначене для роздільної компіляції шаблонів. За задумом авторів, розробник мав оголошувати шаблон функції або класу в заголовному файлі з ключовим словом `export`, а повне тіло з реалізацією ховати у файл вихідного коду `.cpp`. Компілятор мав самостійно зберігати внутрішнє абстрактне синтаксичне дерево (AST) або проміжне представлення та інстанціювати шаблон у будь-якій іншій одиниці трансляції без повторного парсингу тексту.

На практиці ідея виявилася технічною катастрофою:
1. Вимоги до компіляторів були настільки складними, що за перші десять років існування стандарту лише один рушій компіляції у світі — фронтенд компанії Edison Design Group (EDG) під керівництвом Дейва Едріса (Daveed Vandevoorde) — спромігся повністю реалізувати цю можливість у комерційному продукті Comeau C++.
2. Жоден із масових трансляторів — ні GCC, ні Microsoft Visual C++, ні Clang — так і не впровадив `export template`, оскільки архітектурна ціна підтримки серіалізації AST перевищувала будь-яку потенційну користь для часу збірки.
3. Реальний виграш у швидкості лінкування виявився мінімальним або від'ємним через колосальні накладні витрати на синхронізацію інстанціацій між об'єктними файлами.

На засіданні комітету WG21 у 2008 році під час підготовки C++11 було ухвалено історичне рішення: повністю вилучити ключове слово `export` для шаблонів з нормативного тексту стандарту (папір N1426 / N2387). Це був перший випадок, коли ISO C++ відмовився від задекларованої раніше фундаментальної можливості мови. Ключове слово лишилося зарезервованим у пам'яті граматики й повернулося до життя лише через дев'ять років у C++20 як частина зовсім іншої підсистеми — модулів мови (`export module`).

## Помилка швидкого проектування: падіння std::auto_ptr

Наприкінці 1990-х років, коли стандарт C++98 готувався до фінального балотування, у мові була відсутня семантика переміщення (англ. *move semantics*). Існували лише конструктори копіювання, які приймали посилання на константу `const T&`. Водночас індустрія гостро потребувала засобу RAII (англ. *Resource Acquisition Is Initialization*, захоплення ресурсу є ініціалізація) для автоматичного звільнення динамічної пам'яті під час виходу з області видимості чи генерації винятків.

У поспіху комітет стандартизував шаблон `std::auto_ptr`. Оскільки тип не міг виразити передачу прав власності через rvalue-посилання, розробники реалізували нетиповий конструктор копіювання, що приймав неконстантне lvalue-посилання:

```cpp
// Історична сигнатура C++98
template<class Y>
auto_ptr(auto_ptr<Y>& rhs) throw();
```

Копіювання `auto_ptr` призводило до тихої модифікації джерела: вихідний вказівник обнулявся, а ресурс переходив до нового власника. Це порушувало математичну семантику копіювання, згідно з якою операція `a = b` залишає `b` незмінним.

Наслідки виявилися руйнівними:
- Передача `std::auto_ptr` за значенням у функцію або алгоритм призводила до того, що викликаючий код несподівано втрачав доступ до об'єкта (`nullptr`).
- Спроба зберегти `std::auto_ptr` у стандартних контейнерах STL (`std::vector<std::auto_ptr<Widget> >`) перетворювала алгоритми сортування на мінне поле: під час виконання `std::sort` опорні елементи переприсвоювалися, вказівники обнулялися, а пам'ять передчасно видалялася деструкторами тимчасових змінних.

З появою rvalue-посилань та шаблону `std::unique_ptr` у C++11 `auto_ptr` негайно оголосили застарілим (англ. *deprecated*). Проте величезний обсяг наявного промислового коду вимагав перехідного періоду. Тип проіснував у статусі попередження шість років, і лише в C++17 комітет повністю видалив `std::auto_ptr` зі стандартної бібліотеки (папір N4190). Проєкти, які ігнорували попередження компілятора протягом багатьох років, зіткнулися з повною зупинкою збірки при оновленні прапорця стандарту.

## Битва за триграфи: конфлікт між мейнфреймами та сучасною мовою

Один із найбільш запеклих ідеологічних конфліктів у WG21 розгорнувся довкола вилучення триграфів (англ. *trigraphs*). Триграфи з'явилися в мові C наприкінці 1980-х років (стандарт ISO 646) для терміналів і клавіатур, у яких були відсутні символи `#`, `[`, `]`, `{`, `}`, `\`, `^`, `~` та `|` (наприклад, у німецьких чи скандинавських національних розкладках або в кодуванні IBM EBCDIC на мейнфреймах). Компілятор замінював комбінації з двох знаків питання та третього символу на відповідний знак пунктуації на першій фазі трансляції:

```
??=  ->  #
??(  ->  [
??/  ->  \
```

У XXI столітті всі інженерні системи перейшли на стандарт Unicode та ASCII-сумісні клавіатури, проте триграфи залишалися обов'язковими для компіляторів C++. Це породжувало небезпечні приховані баги у звичайному коді:

```cpp
// Текст містить послідовність ??/
// Компілятор C++98 сприймає ??/ як символ зворотного слеша '\'
// Наступний рядок стає продовженням коментаря і тихо видаляється препроцесором!
// Відповідає на запит клієнта??/
execute_critical_business_logic();
```

Коли у 2014 році на засіданні комітету в Урбані-Шампейн Річард Сміт (Richard Smith) подав пропозицію N4086 про видалення триграфів у C++17, делегація корпорації IBM виступила з категоричним протестом. Інженери IBM аргументували, що мільйони рядків коду на системах IBM z/OS і OS/400 використовують EBCDIC і вимагатимуть ручної адаптації.

Відбулося кілька раундів формальних голосувань. Комітет провів детальний аудит і з'ясував, що навіть на сучасних компіляторах IBM XL C++ більшість розробників використовують прапорці відключення триграфів, щоб уникнути пошкодження регулярних виразів та рядкових літералів. Більшістю голосів триграфи були офіційно вилучені з мови в C++17. Компілятори отримали право видавати фатальну помилку, якщо в тексті програми зустрічається послідовність, схожа на застарілий триграф.

## Вилучення Copy-On-Write у std::string

У стандартах C++98/03 внутрішня реалізація класу `std::string` не була суворо регламентована. Більшість стандартних бібліотек (зокрема GNU `libstdc++`) використовували оптимізацію копіювання при записі (англ. *Copy-On-Write*, CoW). Кілька рядків могли спільно володіти одним динамічним буфером із лічильником посилань, а виділення нової пам'яті відбувалося лише в момент виклику неконстантного оператора індексації `operator[]` або методу `append()`.

З появою стандарту C++11 та формальної багатопотокової моделі пам'яті (англ. *Memory Model*) ця оптимізація перетворилася на проблему:
- Стандарт C++11 вимагав, щоб одночасне читання одного об'єкта з кількох потоків було потокобезпечним без синхронізації (`const`-методи не мають викликати гонок даних).
- У схемі CoW будь-яка спроба отримати неконстантне посилання на символ вимагала атомарної перевірки лічильника посилань або блокування м'ютекса, що сповільнювало операції на багатоядерних процесорах.
- Метод `std::string::size()` у C++11 зобов'язаний виконуватися за строгий константний час `O(1)`, а ітератори не мали права інвалідуватися при виклику читаючих операцій.

Комітет WG21 змінив вимоги до інтерфейсу `std::string`, фактично заборонивши реалізації CoW на користь оптимізації малих рядків (англ. *Small String Optimization*, SSO). Для розробників на Linux це призвело до найбільшого розриву бінарної сумісності (ABI break) в історії GCC: у версії GCC 5.1 одночасно існували стара реалізація `std::string` (CoW) та нова (SSO), що розділило екосистему на два несумісних світи макросом `_GLIBCXX_USE_CXX11_ABI`.

## Очищення C++17 та C++20: вилучення накопиченого баласту

Починаючи з C++17, комітет перейшов від політики накопичення до регулярного трирічного аудиту та видалення застарілих компонентів.

У C++17 з мови остаточно вилучили:
1. **Ключове слово `register`:** колись воно слугувало підказкою компілятору розмістити змінну в регістрі процесора. У сучасних оптимізуючих трансляторах (SSA-форми, лінійний розподіл регістрів) це слово втратило сенс і лише заважало аналізаторам.
2. **Динамічні специфікації винятків `throw(X, Y)`:** механізм перевірки списку винятків під час виконання створював величезні накладні витрати на таблиці розгортання стека і призводив до виклику `std::unexpected()`. Його повністю замінили на специфікатор `noexcept`.
3. **Старі функціональні адаптери:** `std::bind1st`, `std::bind2nd`, `std::ptr_fun`, `std::mem_fun`, базові класи `std::unary_function` та `std::binary_function`. Лямбда-вирази та `std::bind` повністю перебрали на себе їхню функціональність.
4. **Алгоритм `std::random_shuffle`:** через використання небезпечної функції `std::rand()` алгоритм поступився місцем `std::shuffle`, що приймає сучасні генератори псевдовипадкових чисел.

У C++20 масштабна чистка продовжилася:
- **Перегляд агрегатної ініціалізації:** історично агрегатом вважався тип без оголошених конструкторів. У C++20 додавання конструктора `= default` або `= delete` офіційно дискваліфікує структуру з категорії агрегатів, що зламало ініціалізацію вигляду `Point p{10, 20};` у багатьох бібліотеках.
- **Вилучення `std::is_pod`:** поняття POD (Plain Old Data) виявилося надто розмитим для сучасної системи типів. Його розділили на два точних трейти: `std::is_standard_layout` (гарантія C-сумісного розташування полів у пам'яті) та `std::is_trivial` (гарантія безпечного копіювання через `memcpy`).
- **Спрощення алокаторів:** вилучено метод `std::allocator::allocate(size_type, const void*)`, структуру `std::raw_storage_iterator` та спеціалізацію `std::allocator<void>`.

## Двофазний цикл WG21: від попередження до вилучення

Сучасний комітет дотримується суворого двофазного регламенту управління життєвим циклом компонентів:

```
[Повноцінний засіб]
       │
       ▼  Крок 1 (Реліз N): Оголошення застарілим
[[deprecated("причина")]] у стандарті + компілятор генерує warning
       │
       ▼  Крок 2 (Реліз N+1 або N+2): Фізичне видалення
Вилучення з тексту стандарту ISO + компілятор видає fatal error
```

Цей механізм захищає індустрію від раптових потрясінь: між моментом, коли компілятор починає попереджати про застарілість конструкції, і днем, коли код перестане збиратися, минає від 3 до 6 років. Усвідомлення цього графіка дозволяє інженерним командам своєчасно планувати рефакторинг і не накопичувати технічний борг до моменту, коли оновлення стандарту стане критичною виробничою необхідністю.
