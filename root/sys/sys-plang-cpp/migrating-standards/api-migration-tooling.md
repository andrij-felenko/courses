# Довідник інструментів міграції: Clang-Tidy, прапорці компіляторів та макроси сумісності

Автоматизована та надійна міграція кодової бази на новіші стандарти C++ спирається на три взаємодоповнюючі інженерні рівні: інструменти трансформації абстрактного синтаксичного дерева (Clang-Tidy), прапорці діагностики та контролю стандартів компіляторів (GCC, Clang, MSVC) і нормативні макроси тестування можливостей (Feature Test Macros за стандартом SD-6). Нижче наведено детальний опис контрактів, опцій конфігурації, перевірок та правил взаємодії компонентів.

## Модуль Clang-Tidy modernize: архітектура та каталог правил

Інструмент `clang-tidy` є частиною екосистеми LLVM. На відміну від текстових утиліт пошуку та заміни (таких як `sed` чи регулярні вирази), `clang-tidy` виконує повноцінний синтаксичний і семантичний аналіз вихідного тексту. Він компілює кожну одиницю трансляції за допомогою фронтенду Clang, будує типізоване абстрактне синтаксичне дерево (англ. *Abstract Syntax Tree*, AST) і зіставляє його вузли з декларативними правилами (англ. *AST Matchers*).

Коли збіг знайдено, перевірка генерує виправлення у вигляді структур `FixItHint`, які вказують точні байти у файлі (діапазон вихідного тексту) для заміни, видалення або вставки. Завдяки цьому інструмент не чіпає макроси поза контекстом розгортання, коректно враховує видимість імен та правила виведення типів.

### Правила модернізації для переходу на C++11

Перехід із застарілих діалектів C++98/03 на C++11 вимагає заміни низки базових конструкцій мови, які раніше спиралися на угоди програміста або макроси препроцесора:

1. **`modernize-use-nullptr`**
   - *Механізм:* перевірка знаходить усі цілочисельні літерали `0` та макроси `NULL`, які використовуються у контексті вказівників (ініціалізація вказівників, порівняння з вказівниками, передача у функції, що приймають типи вказівників).
   - *Трансформація:* літерал замінюється на ключове слово `nullptr` типу `std::nullptr_t`.
   - *Крайові випадки:* якщо у проєкті визначено власні макроси для нульового вказівника, їх слід передати в опцію `NullMacros`. Перевірка не чіпає нулі в арифметичних виразах або бітових масках.

2. **`modernize-use-override`**
   - *Механізм:* інструмент аналізує ієрархії поліморфних класів. Якщо метод у похідному класі перевизначає віртуальний метод базового класу, перевірка переконується у наявності специфікатора `override`.
   - *Трансформація:* додає ключове слово `override` до оголошення методу та видаляє надлишкове ключове слово `virtual`, яке в сучасному стилі вважається шумом.
   - *Крайові випадки:* якщо сигнатура методу у похідному класі випадково відрізняється за константністю або типами параметрів від базового, метод є прихованим перевантаженням, а не перевизначенням; `clang-tidy` не додасть `override`, що дозволяє розробнику знайти приховані логічні дефекти.

3. **`modernize-use-using`**
   - *Механізм:* виявляє старі C-подібні оголошення типів через ключове слово `typedef`.
   - *Трансформація:* замінює `typedef Type Alias;` на синтаксис `using Alias = Type;`.
   - *Значення:* синтаксис `using` є візуально узгодженим із присвоєнням і, на відміну від `typedef`, безпосередньо підтримує параметризацію шаблонами (`template<typename T> using TypeAlias = ...`).

4. **`modernize-use-auto`**
   - *Механізм:* шукає оголошення локальних змінних, де тип змінної явно повторює тип виразу ініціалізації (наприклад, явний виклик `new`, ітератори стандартних контейнерів, явне приведення типів `static_cast`).
   - *Трансформація:* замінює довгу назву типу на ключове слово `auto`.
   - *Крайові випадки:* за замовчуванням правило налаштоване консервативно: воно не замінює фундаментальні типи (`int`, `double`) та проксі-об'єкти (наприклад, вирази шаблонів виразів бібліотеки Eigen або `std::vector<bool>::reference`), щоб не викликати небажаного продовження життя тимчасових об'єктів або збереження висячих посилань.

5. **`modernize-loop-convert`**
   - *Механізм:* аналізує цикли `for`, що ітерують масиви за індексом `for (size_t i = 0; i < v.size(); ++i)` або контейнери за допомогою ітераторів `for (auto it = v.begin(); it != v.end(); ++it)`.
   - *Трансформація:* перетворює конструкцію на цикл на основі діапазону (англ. *range-based for loop*) виду `for (const auto& item : v)`.
   - *Крайові випадки:* якщо всередині тіла циклу викликаються методи, що додають або видаляють елементи контейнера (`push_back`, `erase`), перетворення не виконується, оскільки зміна розміру контейнера інвалідує ітератори та призводить до невизначеної поведінки.

6. **`modernize-pass-by-value`**
   - *Механізм:* виявляє конструктори або сетери, які приймають об'єкти за константним посиланням `const T&`, а всередині копіюють їх у поле класу через оператор присвоєння або список ініціалізації.
   - *Трансформація:* змінює тип аргументу на передачу за значенням `T` та огортає використання параметра у виклик `std::move(param)`.
   - *Крайові випадки:* застосовується лише до типів, які мають конструктор переміщення. Якщо тип є некопійованим або його переміщення дороге (наприклад, масив фіксованого розміру `std::array`), трансформація вимикається.

7. **`modernize-use-default-member-init`**
   - *Механізм:* знаходить повторювану ініціалізацію полів класу константними значеннями у списках ініціалізації декількох конструкторів.
   - *Трансформація:* переносить ініціалізацію за замовчуванням безпосередньо у тіло оголошення класу (`int count_{0};`), спрощуючи конструктори.

### Правила модернізації для переходу на C++14 та C++17

Ці перевірки ліквідують конструкції, які стали небезпечними або були офіційно вилучені з тексту стандарту ISO C++17:

1. **`modernize-replace-auto-ptr`**
   - *Механізм:* шукає всі згадки забороненого типу `std::auto_ptr<T>`.
   - *Трансформація:* замінює тип на `std::unique_ptr<T>`. Додає `#include <memory>`, якщо заголовок відсутній.
   - *Крайові випадки:* оскільки `std::auto_ptr` неявно передавав володіння при звичайному копіюванні, заміна на `std::unique_ptr` може вимагати явного обертання аргументів у `std::move()`. Перевірка намагається виявити місця копіювання і вставити `std::move`, проте вимагає обов'язкового ручного аудиту точок виклику.

2. **`modernize-make-unique` та `modernize-make-shared`**
   - *Механізм:* шукає явні виклики оператора `new` всередині конструкторів розумних вказівників, такі як `std::unique_ptr<Widget>(new Widget(arg1, arg2))`.
   - *Трансформація:* перетворює код на фабричні функції `std::make_unique<Widget>(arg1, arg2)` та `std::make_shared<Widget>(arg1, arg2)`.
   - *Крайові випадки:* функція `make_shared` об'єднує блок керування лічильника посилань і сам об'єкт у єдину алокацію пам'яті, що суттєво прискорює створення об'єкта. Проте вона не працює з типами, що мають приватні конструктори (навіть якщо клас оголосив фабрику другом), оскільки `make_shared` створює об'єкт усередині власного простору імен STL.

3. **`modernize-deprecated-headers`**
   - *Механізм:* знаходить застарілі заголовні файли мови C, підключені без префікса `c` (наприклад, `<stdio.h>`, `<stdlib.h>`, `<math.h>`, `<assert.h>`).
   - *Трансформація:* замінює директиви на відповідні C++ версії `<cstdio>`, `<cstdlib>`, `<cmath>`, `<cassert>`.
   - *Значення:* поміщає стандартні ідентифікатори у простір назв `std::` відповідно до вимог стандарту ISO, усуваючи конфлікти глобальної видимості імен.

4. **`modernize-unary-static-assert`**
   - *Механізм:* знаходить твердження часу компіляції `static_assert(condition, "")`, де другим аргументом передано порожній рядковий літерал.
   - *Трансформація:* видаляє порожній рядок, використовуючи одноаргументний синтаксис `static_assert(condition)` зі стандарту C++17.

5. **`modernize-use-transparent-functors`**
   - *Механізм:* знаходить інстанціювання функторів порівняння STL із явним зазначенням типу аргументу у контейнерах, наприклад `std::map<std::string, int, std::less<std::string>>`.
   - *Трансформація:* замінює функтор на прозорий еквівалент без параметрів шаблону: `std::less<>()`.
   - *Значення:* дозволяє асоціативним контейнерам використовувати гетерогенний пошук (пошук за `std::string_view` або `const char*` без виділення пам'яті для тимчасового об'єкта `std::string`).

### Правила модернізації для переходу на C++20

Стандарт C++20 відкриває можливості для значного підвищення виразності та безпеки інтерфейсів:

1. **`modernize-use-nodiscard`**
   - *Механізм:* аналізує методи класів та вільні функції. Якщо функція не має побічних ефектів (наприклад, константний гетер), повертає значення за копією або повертає код помилки (наприклад, статус `bool` чи `std::error_code`), перевірка пропонує захистити результат.
   - *Трансформація:* додає стандартний атрибут `[[nodiscard]]` перед оголошенням функції.
   - *Значення:* змушує компілятор генерувати попередження, якщо викликаючий код випадково ігнорує повернуте значення, що ліквідує типові помилки перевірки статусів.

2. **`modernize-use-starts-ends-with`**
   - *Механізм:* виявляє старі ідіоми перевірки префіксів або суфіксів рядків через методи пошуку `s.find(prefix) == 0` або `s.rfind(suffix) == (s.size() - suffix.size())`.
   - *Трансформація:* замінює складні вирази на прямі виклики методів C++20 `s.starts_with(prefix)` та `s.ends_with(suffix)`.

3. **`modernize-use-ranges`**
   - *Механізм:* шукає стандартні алгоритми STL, які приймають пари ітераторів одного контейнера (`std::sort(v.begin(), v.end())`, `std::find(v.begin(), v.end(), val)`).
   - *Трансформація:* замінює виклики на алгоритми з простору назв діапазонів `std::ranges::sort(v)` та `std::ranges::find(v, val)`.

### Конфігурація .clang-tidy та керування масштабом

Файл `.clang-tidy` розміщується у корені проєкту та автоматично підхоплюється всіма підкаталогами. Його формат підтримує точне налаштування правил та фільтрацію:

```yaml
---
# Кореневий конфігураційний файл Clang-Tidy для поетапної модернізації
Checks: >
  -*,
  modernize-use-nullptr,
  modernize-use-override,
  modernize-use-using,
  modernize-replace-auto-ptr,
  modernize-make-unique,
  modernize-make-shared,
  modernize-deprecated-headers,
  modernize-unary-static-assert,
  modernize-use-nodiscard,
  modernize-use-starts-ends-with

# Перелік перевірок, порушення яких блокує компіляцію як фатальна помилка
WarningsAsErrors: 'modernize-replace-auto-ptr,modernize-use-override'

# Регулярний вираз для обробки заголовних файлів проєкту (ігнорує системні та сторонні заголовки)
HeaderFilterRegex: '^(src|include|lib)/.*'

# Стиль форматування для виправлень
FormatStyle: file

# Додаткові параметри індивідуальних перевірок
CheckOptions:
  - key: modernize-use-nullptr.NullMacros
    value: 'NULL,MY_CUSTOM_NULL'
  - key: modernize-pass-by-value.IncludeStyle
    value: 'llvm'
  - key: modernize-use-override.AllowOverrideAndVirtual
    value: 'false'
...
```

## Прапорці компіляторів: контроль стандартів та діагностика

Компілятори надають багатий набір ключів командного рядка для увімкнення відповідного стандарту, виявлення застарілих API та форсування суворого дотримання стандартної поведінки ISO. Робота з ними є фундаментом для чистого переходу.

### Прапорці діагностики GCC та Clang

Компілятори GCC та Clang мають спільну систему керування діагностикою, що дозволяє виявляти потенційні проблеми заздалегідь:

- **`-std=c++11`, `-std=c++14`, `-std=c++17`, `-std=c++20`, `-std=c++23`**
  Встановлює цільовий мовний рівень. Компілятор вмикає відповідний набір синтаксичних правил та визначає макрос `__cplusplus` (наприклад, `201703L` для C++17 або `202002L` для C++20).
- **`-std=gnu++17`, `-std=gnu++20`**
  Вмикає відповідний стандарт ISO разом із фірмовими розширеннями GNU (вбудований асемблер `typeof`, вкладені функції, специфічні атрибути). У кросплатформних проєктах рекомендується уникати розширень GNU на користь чистих прапорців `-std=c++*`.
- **`-Wall -Wextra -Wpedantic`**
  Базова тріада попереджень. Прапорець `-Wpedantic` вимагає суворого дотримання стандарту ISO C++ і забороняє розширення компілятора, які можуть зламати сумісність при перенесенні коду на інший компілятор.
- **`-Wdeprecated` та `-Wdeprecated-declarations`**
  Прапорець `-Wdeprecated` попереджає про використання застарілих можливостей самої мови (наприклад, ключового слова `register` чи неявного конструктора копіювання за наявності деструктора). Прапорець `-Wdeprecated-declarations` контролює звернення до функцій та типів, позначених атрибутом `[[deprecated]]`.
- **`-Werror=deprecated-declarations`**
  Перетворює попередження про використання застарілих оголошень на фатальну помилку компіляції. Це ключовий прапорець для конвеєрів безперервної інтеграції (CI), який гарантує, що новий застарілий код більше не потрапить у репозиторій.
- **`-Wsuggest-override`**
  Попереджає, якщо віртуальний метод перевизначає функцію базового класу, але не має явного специфікатора `override`. Це дозволяє усунути розриви поліморфізму до того, як вони призведуть до збоїв у рантаймі.
- **`-Wzero-as-null-pointer-constant`**
  Генерує попередження щоразу, коли ціле число `0` або макрос `NULL` використовується замість нульового вказівника. Прапорець дозволяє виявити всі місця для міграції на `nullptr`.

### Прапорці компілятора MSVC (Visual Studio)

Компілятор Microsoft Visual C++ історично мав суттєві відхилення від стандарту ISO, що вимагає специфічного налаштування прапорців:

- **`/std:c++14`, `/std:c++17`, `/std:c++20`, `/std:c++latest`**
  Встановлює мовний діалект MSVC. Прапорець `/std:c++latest` відкриває експериментальні можливості майбутнього стандарту (C++26).
- **`/permissive-`**
  Найважливіший прапорець сучасної розробки на MSVC. Він вимикає всі нестандартні історичні розширення Microsoft і вмикає строгий двофазний пошук імен у шаблонах (Two-phase name lookup). Без цього прапорця код, скомпільований на MSVC, може не збиратися на GCC чи Clang через приховані помилки зв'язування залежних імен у шаблонах.
- **`/Zc:__cplusplus`**
  Історично MSVC повертав у макросі `__cplusplus` застаріле значення `199711L` для збереження сумісності зі старими бібліотеками. Прапорець `/Zc:__cplusplus` змушує компілятор повертати реальне значення стандарту (`201703L` для C++17 тощо).
- **`/we4996`**
  Перетворює попередження компилятора C4996 (використання застарілих POSIX-функцій або компонентів STL) на помилку.
- **`/external:W0` та `/external:anglebrackets`**
  Дозволяє розділити власний код та сторонні бібліотеки. Компілятор вважає всі файли, підключені через кутові дужки `#include <...>`, зовнішніми і повністю пригнічує у них попередження, дозволяючи тримати найвищий рівень суворості у власному коді.

## Нормативні макроси тестування можливостей (Feature Test Macros, SD-6)

До появи стандартизованих макросів тестування розробники перевіряли версії компіляторів за допомогою крихких конструкцій виду `#if defined(__GNUC__) && __GNUC__ >= 7`. Це призводило до помилок, оскільки різні компілятори впроваджували можливості стандарту в різному порядку.

Комітет WG21 стандартизував макроси тестування можливостей (документ SD-6, закріплений у стандарті C++20 у заголовку `<version>`). Кожен макрос розгортається у ціле число у форматі `YYYYMM` (рік і місяць ухвалення ревізії фічі).

### Макроси ядра мови

Макроси мови доступні автоматично без підключення заголовних файлів і визначають наявність синтаксичних конструкцій у поточному режимі компіляції:

- **`__cpp_rvalue_references >= 200610L`** — підтримка rvalue-посилань та семантики переміщення.
- **`__cpp_variadic_templates >= 200704L`** — підтримка шаблонів зі змінною кількістю аргументів.
- **`__cpp_constexpr`** — еволюція обчислень часу компіляції:
  - `200704L` (C++11) — базові одновиразові функції `constexpr`;
  - `201304L` (C++14) — цикли, локальні змінні та розгалуження у `constexpr`;
  - `201603L` (C++17) — лямбда-вирази у `constexpr`;
  - `201907L` (C++20) — виділення динамічної пам'яті (`std::vector`, `std::string`) під час компіляції.
- **`__cpp_structured_bindings >= 201606L`** — структуровані прив'язки `auto [x, y] = point;`.
- **`__cpp_guaranteed_copy_elision >= 201606L`** — обов'язкове опущення копіювання для виразів prvalue (C++17).
- **`__cpp_inline_variables >= 201606L`** — можливість оголошувати змінні `inline` у заголовних файлах без порушення ODR.
- **`__cpp_concepts >= 201907L`** — підтримка концептів та виразів обмежень `requires`.
- **`__cpp_impl_three_way_comparison >= 201907L`** — оператор тристороннього порівняння `<=>` (Spaceship).
- **`__cpp_coroutines >= 201902L`** — безстекові корутини (`co_await`, `co_yield`, `co_return`).
- **`__cpp_designated_initializers >= 201707L`** — іменована ініціалізація полів агрегатів `.x = 10`.

### Макроси стандартної бібліотеки

Макроси бібліотеки оголошуються у спеціалізованому заголовку `<version>` (або всередині відповідних заголовків компонентів):

- **`__cpp_lib_make_unique >= 201304L`** — наявність функції `std::make_unique` у `<memory>`.
- **`__cpp_lib_string_view >= 201606L`** — тип неволодіючого рядкового перегляду `std::string_view`.
- **`__cpp_lib_optional >= 201606L`** — словниковий тип `std::optional` для представлення опціональних значень.
- **`__cpp_lib_variant >= 201606L`** — типобезпечне об'єднання `std::variant`.
- **`__cpp_lib_span >= 202002L`** — неперервний перегляд масивів пам'яті `std::span`.
- **`__cpp_lib_ranges >= 201911L`** — алгоритми та конвеєри діапазонів `<ranges>`.
- **`__cpp_lib_format >= 201907L`** — типобезпечне та високопродуктивне форматування тексту `std::format`.
- **`__cpp_lib_expected >= 202202L`** — тип обробки помилок за значенням `std::expected` (C++23).
- **`__cpp_lib_print >= 202207L`** — прямий вивід у консоль `std::print` (C++23).

## Архітектура перехідних прошарків (Compatibility Shims)

Для бібліотек, які повинні одночасно збиратися у середовищах із різними стандартами (наприклад, відкрита бібліотека, що надає інтерфейси для клієнтів C++11, C++17 та C++20), створюється єдиний заголовок сумісності. Він інкапсулює перевірку макросів і надає уніфіковані типи у власному просторі назв `compat::`.

```cpp
#pragma once

// 1. Безпечне підключення заголовка версій стандарту
#if defined(__has_include)
    #if __has_include(<version>)
        #include <version>
    #else
        #include <cstddef>
    #endif
#endif

// 2. Атрибути безпеки та діагностики
#if defined(__has_cpp_attribute)
    #if __has_cpp_attribute(nodiscard) >= 201603L
        #define COMPAT_NODISCARD [[nodiscard]]
    #else
        #define COMPAT_NODISCARD
    #endif

    #if __has_cpp_attribute(maybe_unused) >= 201603L
        #define COMPAT_UNUSED [[maybe_unused]]
    #elif defined(__GNUC__) || defined(__clang__)
        #define COMPAT_UNUSED __attribute__((unused))
    #else
        #define COMPAT_UNUSED
    #endif

    #if __has_cpp_attribute(fallthrough) >= 201603L
        #define COMPAT_FALLTHROUGH [[fallthrough]]
    #elif defined(__clang__)
        #define COMPAT_FALLTHROUGH [[clang::fallthrough]]
    #elif defined(__GNUC__) && (__GNUC__ >= 7)
        #define COMPAT_FALLTHROUGH __attribute__((fallthrough))
    #else
        #define COMPAT_FALLTHROUGH ((void)0)
    #endif
#else
    #define COMPAT_NODISCARD
    #define COMPAT_UNUSED
    #define COMPAT_FALLTHROUGH ((void)0)
#endif

// 3. Аліаси та резервні реалізації для std::string_view
#if defined(__cpp_lib_string_view) && (__cpp_lib_string_view >= 201606L)
    #include <string_view>
    namespace compat {
        using string_view = std::string_view;
    }
#else
    #include <string>
    namespace compat {
        // Резервна спрощена реалізація неволодіючого рядка для C++11/14
        class string_view {
            const char* data_;
            std::size_t size_;
        public:
            constexpr string_view() noexcept : data_(nullptr), size_(0) {}
            constexpr string_view(const char* str, std::size_t len) noexcept : data_(str), size_(len) {}
            string_view(const std::string& str) noexcept : data_(str.data()), size_(str.size()) {}
            constexpr const char* data() const noexcept { return data_; }
            constexpr std::size_t size() const noexcept { return size_; }
            constexpr bool empty() const noexcept { return size_ == 0; }
        };
    }
#endif
```

## Інтеграція керування стандартами в сучасний CMake

У системі збірки CMake керування стандартами має здійснюватися виключно на рівні властивостей таргетів (англ. *Target-Centric CMake*), що гарантує ізоляцію налаштувань і правильне поширення вимог транзитивним залежностям.

### Прив'язка стандарту до таргету

```cmake
# Оголошення таргету бібліотеки
add_library(core_engine
    src/engine.cpp
    src/memory.cpp
)

# Вимога підтримки функціоналу C++17 для компіляції цієї бібліотеки
target_compile_features(core_engine PUBLIC cxx_std_17)

# Суворе закріплення стандарту та відключення нестандартних вендорних розширень
set_target_properties(core_engine PROPERTIES
    CXX_STANDARD 17
    CXX_STANDARD_REQUIRED ON
    CXX_EXTENSIONS OFF
)
```

Властивість `CXX_STANDARD_REQUIRED ON` змушує CMake негайно завершити генерацію з помилкою, якщо поточний компілятор не підтримує вказаний стандарт, замість тихого відкату до старішої версії. Властивість `CXX_EXTENSIONS OFF` відключає прапорці розширень (`-std=gnu++17`) на користь чистого стандарту (`-std=c++17`).

### Автоматизований лінтинг Clang-Tidy у процесі компіляції

CMake дозволяє запускати `clang-tidy` як внутрішній крок компіляції кожного вихідного файлу:

```cmake
# Пошук виконуваного файлу Clang-Tidy
find_program(CLANG_TIDY_EXE NAMES "clang-tidy" "clang-tidy-17" "clang-tidy-16")

if(CLANG_TIDY_EXE)
    set_target_properties(core_engine PROPERTIES
        CXX_CLANG_TIDY "${CLANG_TIDY_EXE};--config-file=${CMAKE_CURRENT_SOURCE_DIR}/.clang-tidy;--warnings-as-errors=*"
    )
    message(STATUS "Clang-Tidy успішно підключено до таргету core_engine")
else()
    message(WARNING "clang-tidy не знайдено, перевірки modernize вимкнено")
endif()
```

### Інтерфейсний таргет для уніфікованих прапорців діагностики

Щоб не дублювати прапорці суворої діагностики у кожному `CMakeLists.txt`, створюють інтерфейсний таргет:

```cmake
add_library(strict_warnings INTERFACE)

target_compile_options(strict_warnings INTERFACE
    $<$<CXX_COMPILER_ID:MSVC>:
        /W4
        /permissive-
        /Zc:__cplusplus
        /we4996
    >
    $<$<OR:$<CXX_COMPILER_ID:GNU>,$<CXX_COMPILER_ID:Clang>>:
        -Wall
        -Wextra
        -Wpedantic
        -Wdeprecated
        -Werror=deprecated-declarations
        -Wsuggest-override
    >
)

# Підключення до цільових бібліотек
target_link_libraries(core_engine PRIVATE strict_warnings)
```
