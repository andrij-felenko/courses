# 📋 Довідник правил спеціалізації та часткового впорядкування

Цей довідник містить нормативні правила стандарту ISO/IEC 14882 (C++20/C++23) щодо синтаксису, вимог зв'язування (ODR), обмежень та формальних алгоритмів вибору повної спеціалізації, часткової спеціалізації та перевантаження шаблонів.

---

## 1. Синтаксична класифікація шаблонів і спеціалізацій

Стандарт C++ розрізняє первинні шаблони (англ. *primary templates*), повні (явні) спеціалізації (англ. *explicit/full specializations*) та часткові спеціалізації (англ. *partial specializations*).

```
Сутність C++                 Первинний шаблон    Повна спец.    Часткова спец.   Перевантаження
─────────────────────────────────────────────────────────────────────────────────────────────────
Шаблони класів/структур      Дозволено           template<>     template<...>    Неможливо
Шаблони змінних (C++14)      Дозволено           template<>     template<...>    Неможливо
Шаблони функцій              Дозволено           template<>*    ЗАБОРОНЕНО       Дозволено
Шаблони псевдонімів (using)  Дозволено           ЗАБОРОНЕНО     ЗАБОРОНЕНО       Неможливо
Концепти (Concepts, C++20)   Дозволено           ЗАБОРОНЕНО     ЗАБОРОНЕНО       Неможливо
```
*\* Повна спеціалізація шаблонів функцій є синтаксично валідною, проте визнана шкідливою практикою (антипаттерном).*

**Нормативні вимоги до аргументів часткової спеціалізації:**
- Список аргументів часткової спеціалізації (`<T*, Allocator>`) повинен залежати від параметрів, оголошених у заголовку `template<typename T, typename Allocator>`.
- Спеціалізація не може містити параметрів за замовчуванням: значення за замовчуванням успадковуються виключно з первинного шаблону.
- Типи нетипових параметрів шаблону (non-type template parameters, NTTP) у частковій спеціалізації повинні точно відповідати типу в первинному шаблоні.

### Чому заборонено спеціалізувати шаблони псевдонімів (Alias Templates)

Спроба написати спеціалізацію для `template<typename T> using Ptr = T*;` є грубою синтаксичною помилкою:

```cpp
template<typename T>
using TypeHandler = T;

// ПОМИЛКА КОМПІЛЯЦІЇ: explicit specialization of alias template is not allowed
template<>
using TypeHandler<int> = double; 
```

**Причина стандарту**: Псевдоніми типів не створюють нових типів у системі компілятора — вони є прозорими синонімами на рівні синтаксичного дерева. Якби псевдоніми підтримували спеціалізацію, властивість прозорості (англ. *transparency*) була б зруйнована: компілятор не міг би перевірити еквівалентність двох типів без повного розгортання всіх можливих спеціалізацій. Для кастомізації псевдонімів застосовують делегування до вкладеного типу структури `typename detail::TypeHandlerHelper<T>::type`.

## 3. Правила видимості, просторів імен та зв'язування (ODR)

### Порядок оголошення та контекст простору імен

Стандарт ISO C++ (§13.9.3 [temp.expl.spec]) встановлює суворі вимоги до точки розміщення спеціалізацій:

1. **Оголошення після первинного шаблону**: Спеціалізація повинна з'являтися у коді строго *після* оголошення первинного шаблону. Якщо компілятор зустріне використання первинного шаблону для типу `X` до того, як побачить оголошення спеціалізації для `X`, він згенерує екземпляр із первинного шаблону. Наступна поява спеціалізації в тій самій одиниці трансляції призведе до фатальної помилки компіляції.
2. **Простір імен спеціалізації**: Повна або часткова спеціалізація повинна оголошуватися в тому самому просторі імен, що й первинний шаблон (або у просторі імен, який безпосередньо огортає простір первинного шаблону):

3. **Заборона спеціалізації всередині класу (Class Scope)**: Спеціалізувати шаблонний метод або вкладений шаблон структури безпосередньо всередині тіла класу заборонено:

:::code api-specialization-rules/cpp/poriadok-oholoshennia-ta-2.cpp

### Пастка правила єдиного визначення (ODR) для повних спеціалізацій

Повна спеціалізація шаблону функції або шаблону змінної **перестає бути шаблоном** з точки зору моделі лінкування: вона перетворюється на звичайну функцію чи змінну.

Якщо повна спеціалізація поміщена у заголовочний файл (`.hpp`), який підключається до кількох одиниць трансляції (`.cpp`), виникає порушення правила одного визначення (англ. *One Definition Rule*, ODR). Компілятор згенерує машинний код для цієї функції в кожному об'єктному файлі, що призведе до помилки лінкера `multiple definition of ...` (LNK2005 у MSVC).

:::code api-specialization-rules/cpp/pastka-pravyla-iedynoho.cpp

Часткові спеціалізації класів та змінних завжди залишаються шаблонами, тому вони не генерують безпосередніх символів у таблиці лінкера і не потребують специфікатора `inline` у заголовках.

## 4. Ієрархія пріоритетів під час вибору перевантаження (Overload Resolution)

Коли у програмі викликається функція за іменем, компілятор формує набір кандидатів та обирає єдиного переможця за строгою ієрархією пріоритетів:

```
Пріоритет   Категорія кандидата                             Приклад відповідності аргументу
─────────────────────────────────────────────────────────────────────────────────────────────
1 (Найвищий) Нешаблонна функція з точним збігом типів        void render(int val); для int
2           Більш спеціалізований шаблон функції            template<class T> void render(T*); для int*
3           Загальний шаблон функції                        template<class T> void render(T); для int
4           Нешаблонна функція з неявним приведенням типів  void render(double val); для int
```

Зверніть увагу: повні спеціалізації функцій (`template<>`) взагалі відсутні в цій таблиці! Вони не є кандидатами перевантаження.

## 5. Формальний алгоритм часткового впорядкування (Partial Ordering)

Коли у наборі кандидатів перевантаження присутні декілька шаблонів функцій, компілятор застосовує алгоритм **часткового впорядкування** (англ. *Partial Ordering of Function Templates*, стандарт C++ §13.7.6.2 [temp.func.order]), щоб визначити, чи є один із шаблонів більш спеціалізованим за інший.

### Процедура тестування за стандартом ISO C++

Нехай маємо два кандидати: Шаблон 1 (`F1`) та Шаблон 2 (`F2`). Щоб визначити, чи `F1` є як мінімум настільки ж спеціалізованим, як `F2`:

1. **Крок 1 (Синтез унікальних типів)**: Для кожного параметра шаблону `F1` створюється фіктивний унікальний тип або константа (наприклад, `U1`, `U2`, ...), які не збігаються з жодним існуючим типом програми.
2. **Крок 2 (Створення списку синтезованих аргументів)**: Параметри шаблону `F1` замінюються синтезованими типами. Отримуємо синтезований список типів аргументів `A1`, `A2`, ...
3. **Крок 3 (Спроба виведення типів для F2)**: Компілятор намагається виконати стандартне виведення аргументів шаблону (Template Argument Deduction) для шаблону `F2`, передаючи йому як фактичні аргументи синтезований список `A1`, `A2`, ...
4. Якщо виведення завершилося успішно, то `F1` вважається **щонайменше настільки ж спеціалізованим**, як `F2`.
5. Процедура дзеркально повторюється у зворотному напрямку: синтезуються типи для параметрів `F2`, і компілятор перевіряє, чи можна підставити їх у `F1`.

### Правило вибору переможця

- Якщо `F1` є настільки ж спеціалізованим, як `F2`, але `F2` **НЕ** є настільки ж спеціалізованим, як `F1`, то **`F1` є БІЛЬШ СПЕЦІАЛІЗОВАНИМ**, ніж `F2` (`F1 < F2`).
- Якщо виведення успішне в обидва боки — шаблони еквівалентні за спеціалізацією.
- Якщо виведення невдале в обидва боки — шаблони непорівнювані.
- Якщо серед усіх кандидатів перевантаження є єдиний шаблон, який є більш спеціалізованим за всі інші, він стає переможцем. Якщо такого єдиного кандидата немає — компілятор фіксує неоднозначність (англ. *ambiguous call*).

### Покроковий приклад виконання алгоритму

Розглянемо два шаблони функцій:
- Шаблон 1: `template<typename T> void process(T);`
- Шаблон 2: `template<typename T> void process(T*);`

**Напрямок 1: Чи є Шаблон 2 як мінімум настільки ж спеціалізованим, як Шаблон 1?**
1. Синтезуємо тип для параметра Шаблону 2: `T -> UniqueType_U`.
2. Аргумент Шаблону 2 стає: `UniqueType_U*`.
3. Підставляємо `UniqueType_U*` у параметр Шаблону 1 `process(T)`:
   - Відбувається виведення `T = UniqueType_U*`.
   - Виведення успішне! Шаблон 2 є щонайменше настільки ж спеціалізованим, як Шаблон 1.

**Напрямок 2: Чи є Шаблон 1 як мінімум настільки ж спеціалізованим, як Шаблон 2?**
1. Синтезуємо тип для параметра Шаблону 1: `T -> UniqueType_V`.
2. Аргумент Шаблону 1 стає: `UniqueType_V`.
3. Підставляємо `UniqueType_V` у параметр Шаблону 2 `process(T*)`:
   - Компілятор намагається зіставити `T*` із `UniqueType_V`.
   - Оскільки `UniqueType_V` — це атомарний штучний тип, а не вказівник, виведення неможливе!
   - Виведення провалилося.

**Результат**: Шаблон 2 (`T*`) є **більш спеціалізованим** за Шаблон 1 (`T`), тому при виклику `process(ptr)` компілятор гарантовано обере Шаблон 2.

## 6. Впорядкування посилань, кваліфікаторів та варіативних шаблонів

### Правила для посилань (References) та const-кваліфікаторів

Під час аналізу параметрів за посиланням компілятор знімає посилання з синтезованих типів, проте враховує константність і тип посилання (lvalue проти rvalue):

```cpp
template<typename T> void handle(const T&); // Шаблон A
template<typename T> void handle(T&);       // Шаблон B
template<typename T> void handle(T&&);      // Шаблон C (універсальне посилання)
```

- Для неконстантного lvalue-виразу типу `int x; handle(x)`:
  - Шаблон B (`T&`) точніше відповідає типу `int&`, ніж шаблон A (`const T&`), оскільки не вимагає додавання кваліфікатора `const`.
- Для rvalue-виразу `handle(42)`:
  - Шаблон B відкидається (lvalue-посилання не зв'язується з rvalue).
  - Шаблон C (`T&&`) зв'язується напряму як rvalue reference.

### Впорядкування нетипових параметрів шаблонів (NTTP)

Для шаблонів із нетиповими параметрами (числа, покажчики, константи) впорядкування порівнює точність діапазону типів:

```cpp
template<auto N>
void set_flag(); // Шаблон 1: приймає довільний тип NTTP (C++17)

template<int N>
void set_flag(); // Шаблон 2: приймає виключно цілочислове значення int
```

Синтезована константа Шаблону 2 має точний тип `int`. Її можна передати в Шаблон 1 (`auto` виводиться як `int`). Проте синтезована константа Шаблону 1 може мати довільний тип (наприклад, `char` або `enum`), який не завжди зіставляється з `int` без звуження. Тому Шаблон 2 є **більш спеціалізованим**.

### Впорядкування варіативних шаблонів (Variadic Templates)

У разі перевантаження шаблонів із пакетами параметрів фіксована кількість параметрів завжди вважається **більш спеціалізованою**, ніж довільний пакет:

```cpp
// Шаблон 1: приймає один або більше аргументів (голова + хвіст)
template<typename Head, typename... Tail>
void print_all(Head h, Tail... tail);

// Шаблон 2: приймає нуль або більше аргументів
template<typename... Args>
void print_all(Args... args);
```

При виклику `print_all(1, 2, 3)` синтезовані аргументи для Шаблону 1 мають вигляд `(U1, U2, U3)`. Вони успішно підставляються у `print_all(Args...)` Шаблону 2 (пакет виводиться як `Args = [U1, U2, U3]`). Проте синтезовані аргументи Шаблону 2 для випадку порожнього виклику `()` не можуть бути підставлені у Шаблон 1, оскільки Шаблон 1 вимагає як мінімум один обов'язковий аргумент `Head`. Тому Шаблон 1 є **більш спеціалізованим** для непорожніх списків аргументів.

### Невивідні контексти (Non-deduced Contexts)

Якщо параметр шаблону використовується всередині оператора дозволу видимості `::` (наприклад, `typename T::type` або `std::type_identity_t<T>`), такий параметр потрапляє у **невивідний контекст**:

```cpp
template<typename T>
void execute(T val, std::type_identity_t<T> opt);
```

Компілятор не може вивести `T` з другого аргументу, оскільки нескінченна кількість типів може містити вкладений псевдонім з однаковим ім'ям. Невивідні контексти повністю виключаються з алгоритму часткового впорядкування, що дозволяє авторам бібліотек навмисно вимикати виведення типів для другорядних параметрів.

У C++20 механізм часткового впорядкування було розширено поняттям **поглинання обмежень** (англ. *Constraint Subsumption*, §13.7.6.1 [temp.constr.order]):

Коли сигнатури функцій є повністю ідентичними (`void compute(T)`), компілятор нормалізує логічні вирази у виразах `requires`. Концепт `SignedIntegral` логічно тягне за собою (англ. *subsumes*) концепт `Integral` завдяки кон'юнкції `&&`. Тому друге перевантаження визнається **більш обмеженим** (англ. *more constrained*) і перемагає в overload resolution без виникнення помилки неоднозначності.

## 8. Діагностика типових помилок компілятора та методи їх виправлення

| Помилка (Clang / GCC / MSVC) | Причина дефекту | Коректне виправлення |
| :--- | :--- | :--- |
| `error: function template partial specialization is not allowed` | Спроба написати `template<class T> void f<T*>()`. Функції не підтримують часткову спеціалізацію. | Перевантажити функцію `template<class T> void f(T*)` або делегувати у структуру. |
| `error: explicit specialization after instantiation` | Первинний шаблон був інстанційований у коді до точки, де компілятор зустрів `template<> struct Foo<int>`. | Перенести оголошення `template<>` у заголовочний файл вище першого виклику. |
| `error: duplicate symbol / multiple definition of void f<int>()` | Повна спеціалізація шаблону функції визначена у `.hpp` файлі без специфікатора `inline`. | Додати ключове слово `inline` до спеціалізації або винести її визначення у `.cpp`. |
| `error: explicit specialization of non-template class` | Спроба спеціалізувати звичайний (нешаблонний) клас або структуру. | Переконатися, що базовий клас оголошений як `template<...>`. |
| `error: call to 'f' is ambiguous` | Кілька перевантажень шаблонів однаково добре підходять під виклик, і жодне не є більш спеціалізованим. | Додати більш точне перевантаження, використати концептуальні обмеження або явні типи при виклику `f<Exact>(...)`. |
