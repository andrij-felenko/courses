# 📜 Еволюція спеціалізації та перевантаження у C++

Розуміння того, чому шаблони функцій у C++ принципово відрізняються від шаблонів класів у правилах спеціалізації, неможливе без простеження тридцятирічної історії спроб об'єднати дві незалежні системи мови: перевантаження функцій та компіляційну генерацію коду.

## Походження шаблонів і перші конфлікти з перевантаженням (1989–1994)

Коли Б'ярн Страуструп (дан. *Bjarne Stroustrup*) у 1989–1990 роках у лабораторіях Bell Labs проєктував першу версію шаблонів для C++ (описану в книзі *The Annotated C++ Reference Manual*, ARM), шаблони задумувалися як суворо типізований засіб узагальненого програмування без накладних витрат у пам'яті. У початковій моделі компілятора Cfront 3.0 шаблон був просто генератором коду: транслятор брав визначення `template<typename T>` і при виклику підставляв тип-аргумент, створюючи копію структури або функції.

Проте майже одразу з'явилася практична потреба адаптувати алгоритми під специфічні типи. Найпростіший випадок — порівняння або копіювання масивів. Для загального типу `T` операція порівняння `a == b` викликає оператор рівності, проте для `const char*` пряме порівняння вказівників порівнює лише адреси в пам'яті замість вмісту рядків, тому вимагає виклику `std::strcmp`.

Щоб розв'язати цю проблему, до робочих чернеток майбутнього стандарту C++98 було введено поняття **повної (явної) спеціалізації** (англ. *explicit specialization*):

```cpp
// Первинний шаблон
template<typename T>
bool are_equal(T a, T b) {
    return a == b;
}

// Повна спеціалізація для const char*
template<>
bool are_equal<const char*>(const char* a, const char* b) {
    return std::strcmp(a, b) == 0;
}
```

У цей же час, у 1993–1994 роках, Александер Степанов (англ. *Alexander Stepanov*) та Менґ Лі (англ. *Meng Lee*) створювали Standard Template Library (STL) у лабораторіях Hewlett-Packard. Вони зіткнулися з тим, що алгоритмам на кшталт `std::distance` або `std::advance` необхідно було знати категорію ітератора та його тип різниці (`difference_type`). Для класів ітераторів це поле можна було оголосити всередині класу (`using difference_type = std::ptrdiff_t;`), проте звичайні сирі вказівники `int*` не є класами й не можуть містити вкладених псевдонімів типів.

Через відсутність у тогочасних компіляторах можливості спеціалізувати шаблони для цілих родин типів (зокрема для всіх вказівників `T*`), ранні експериментальні релізи STL змушені були генерувати окремі перевантаження для кожного примітивного типу вручну або вимагати від користувачів передавати додаткові допоміжні аргументи-диспатчери при кожному виклику алгоритму.

## Введення часткової спеціалізації класів у C++98

У відповідь на виклики розробки STL комітет стандартизації ISO C++ схвалив концепцію **часткової спеціалізації** (англ. *partial specialization*) для шаблонів класів і структур. Це дозволило створити знамениту ідіому `std::iterator_traits`:

```cpp
// Первинний шаблон для класів-ітераторів
template<typename Iterator>
struct iterator_traits {
    using value_type = typename Iterator::value_type;
    using difference_type = typename Iterator::difference_type;
};

// Часткова спеціалізація для будь-яких вказівників T*
template<typename T>
struct iterator_traits<T*> {
    using value_type = T;
    using difference_type = std::ptrdiff_t;
};
```

Однак для шаблонів функцій часткову спеціалізацію стандартизувати відмовилися. Причиною стало те, що функції у C++, на відміну від класів, уже володіли потужним вбудованим механізмом вибору альтернативних реалізацій — **перевантаженням функцій** (англ. *function overloading*).

Страуструп та члени робочої групи Core Language аргументували відмову тим, що перевантаження функціональних шаблонів є більш природним і гнучким інструментом, оскільки воно підтримує неявні приведення типів (наприклад, перетворення неконстантного вказівника на константний) та виведення типів аргументів:

```cpp
// Перевантаження замість часткової спеціалізації:
template<typename T>
void process(T val);   // Варіант 1: загальний

template<typename T>
void process(T* ptr);  // Варіант 2: перевантаження для вказівників
```

Це рішення здавалося елегантним і лаконічним, але воно заклало приховану архітектурну пастку: у мові одночасно залишилися і перевантаження шаблонів функцій, і їхня повна спеціалізація через синтаксис `template<>`.

## Трагедія std::swap та приклад Дімова-Абрагамса (2001)

Першою практичною жертвою цього дуалізму стала функція `std::swap`. У C++98 єдиним легальним способом оптимізувати обмін значеннями для користувацького класу `MyVector` вважалася повна спеціалізація `template<> void std::swap(MyVector&, MyVector&)` у просторі імен `std`. Проте якщо користувацький тип сам був шаблоном `MyVector<T>`, спеціалізувати `std::swap<MyVector<T>>` було неможливо: це вимагало б часткової спеціалізації функції, яку стандарт забороняв, а перевантаження функцій у просторі імен `std` прямо заборонялося стандартом як невизначена поведінка (UB).

У липні 2001 року Герб Саттер (англ. *Herb Sutter*) опублікував у журналі *C/C++ Users Journal* статтю під назвою «Why Not Specialize Function Templates?» («Чому не слід спеціалізувати шаблони функцій?»), підготовлену у тісній співпраці з авторами бібліотеки Boost Пітером Дімовим (болг. *Петър Димов*) та Девідом Абрагамсом (англ. *David Abrahams*).

Стаття викликала справжній шок у спільноті C++, оскільки довела, що поєднання перевантаження функціональних шаблонів із їхньою повною спеціалізацією створює неочевидні, майже неможливі для ручного відлагодження дефекти.

Дімов і Абрагамс продемонстрували класичний контрприклад:

```cpp
// 1. Первинний шаблон для довільного типу
template<typename T>
void f(T);

// 2. Повна спеціалізація первинного шаблону для вказівника на int
template<>
void f<int*>(int*);

// 3. Нове перевантаження первинного шаблону для довільних вказівників
template<typename T>
void f(T*);

int main() {
    int* p = nullptr;
    f(p); // Яка функція буде викликана?
}
```

Інтуїтивно розробник очікує, що для аргументу `int*` компілятор викличе повну спеціалізацію `f<int*>(int*)`, оскільки вона ідеально відповідає типу аргументу. Проте стандарт C++98 приписував компілятору виконати зовсім іншу послідовність дій:

1. **Фаза перевантаження (Overload Resolution)** розглядає лише первинні шаблони (`template<typename T> void f(T)` та `template<typename T> void f(T*)`). Спеціалізації на цьому етапі взагалі відсутні в наборі кандидатів!
2. Компілятор обирає найбільш спеціалізований первинний шаблон за правилами Partial Ordering. Шаблон `f(T*)` є більш спеціалізованим, ніж `f(T)`, тому перемагає `f(T*)`.
3. Після вибору базового шаблону компілятор перевіряє, чи є у *цього конкретного* обраного шаблону спеціалізація для `T = int`.
4. Оскільки спеціалізація `f<int*>` була записана раніше і була прив'язана до першого шаблону `f(T)`, а не до другого `f(T*)`, компілятор ігнорує її й генерує тіло з другого базового шаблону `f(T*)`!

Спеціалізація `template<> void f<int*>` виявилася безслідно «загубленою» лише через порядок оголошень у коді.

Публікація Саттера сформулювала фундаментальне правило проєктування C++: **«Ніколи не спеціалізуйте шаблони функцій — перевантажуйте їх»**.

## Спроба стандартизації часткової спеціалізації функцій: N1520 (2003)

У жовтні 2003 року Девід Вандевурд (англ. *David Vandevoorde*), провідний експерт комітету ISO C++ та автор книги *C++ Templates: The Complete Guide*, подав офіційну пропозицію до комітету стандартизації — документ **N1520: Function template partial specialization** (і супровідний N1521).

Метою пропозиції було гармонізувати правила мови: дозволити розробникам писати часткові спеціалізації функцій за тим самим синтаксисом, що й для класів:

```cpp
template<typename T>
void serialize(T x);

// Пропонована часткова спеціалізація для вказівників (N1520):
template<typename T>
void serialize<T*>(T* x);
```

Вандевурд запропонував об'єднати фазу вирішення перевантажень та фазу пошуку спеціалізацій в єдине дерево вибору.

Проте комітет стандартизації після тривалих дискусій на робочих групах у Редмонді та Франкфурті відхилив N1520. Основними аргументами проти стали:

1. **Експоненційне ускладнення правил перевантаження**: Поєднання аргументно-залежного пошуку імен (ADL), конверсій типів, неявних приведень аргументів та часткової спеціалізації функцій призводило до нерозв'язних неоднозначностей. Наприклад, як порівнювати нешаблонну функцію `void serialize(const Base*)` з частковою спеціалізацією `template<typename T> void serialize<Derived<T>*>(Derived<T>*)` за наявності неявного приведення типів вказівників?
2. **Зворотна несумісність**: Зміна правил вибору функцій могла непомітно змінити семантику мільйонів рядків чинного коду в критичних банківських, телекомунікаційних та операційних системах.
3. **Наявність працездатних альтернатив**: Завдання вибору алгоритму вже успішно вирішувалося через допоміжні структури (Traits) та селектори тегів (Tag Dispatching).

## Еволюція ідіом: від Tag Dispatching до SFINAE

Відмова від часткової спеціалізації функцій змусила розробників бібліотек шукати надійні архітектурні патерни.

Першим стандартизованим рішенням стала ідіома **делегування у статичні методи структур** (англ. *helper struct delegation*). Оскільки класи та структури підтримують часткову спеціалізацію без жодних конфліктів із перевантаженням, функціональний шаблон перетворювався на тонку обгортку, яка делегувала роботу внутрішній структурі:

```cpp
template<typename T>
struct ProcessorHelper {
    static void execute(const T& value) { /* Загальна реалізація */ }
};

template<typename T>
struct ProcessorHelper<T*> {
    static void execute(const T* value) { /* Для вказівників */ }
};

template<typename T>
void process(const T& value) {
    ProcessorHelper<T>::execute(value);
}
```

Другим підходом став **Tag Dispatching** (диспетчеризація за тегами), що ліг в основу алгоритмів STL (`std::advance`, `std::distance`) та бібліотеки Boost.Serialization. Публічна функція викликала внутрішню перевантажену функцію, передаючи додатковий фіктивний аргумент-тег, створений через виклик конструктора `typename std::iterator_traits<It>::iterator_category()`. Компілятор обирав потрібне перевантаження через стандартний алгоритм overload resolution.

У C++11 поява метафункцій у заголовку `<type_traits>` та формалізація правила **SFINAE** (англ. *Substitution Failure Is Not An Error*) дозволили керувати доступністю перевантажень безпосередньо у сигнатурі через `std::enable_if`:

```cpp
template<typename T, typename = std::enable_if_t<std::is_pointer_v<T>>>
void process(T ptr);
```

Це усунуло потребу у фіктивних структурах-хелперах, проте перевантажило компілятор складним аналізом типів і призвело до появи велетенських, малозрозумілих повідомлень про помилки компіляції при невдалій підстановці.

## Фінал еволюції: if constexpr та Концепти C++20

Остаточну крапку в тридцятилітній суперечці довкола спеціалізації та перевантаження поставили стандарти C++17 та C++20.

У стандарті C++17 з'явилася конструкція `if constexpr`, яка дозволила писати умовне розгалуження за властивостями типів всередині єдиного тіла функції без потреби у спеціалізації чи множинних перевантаженнях:

```cpp
template<typename T>
void process(T&& val) {
    if constexpr (std::is_pointer_v<std::decay_t<T>>) {
        // Код для вказівників
    } else {
        // Код для звичайних значень
    }
}
```

У C++20 з'явилися **Концепти** (англ. *Concepts*) та обмеження `requires`. Механізм вибору між функціями з різними концептами отримав назву **Constraint Subsumption** (поглинання обмежень). Якщо одне перевантаження вимагає концепт `SortableContainer`, а інше — більш жорсткий концепт `ContiguousSortableContainer`, компілятор гарантовано обере друге без жодної спеціалізації та без ризику колізій Дімова-Абрагамса.

Історія довела, що відмова від часткової спеціалізації функціональних шаблонів у C++98 була стратегічно правильним рішенням: замість ускладнення правил виклику мова врешті-решт отримала елегантну систему предикатів компіляції та концептуальних обмежень.
