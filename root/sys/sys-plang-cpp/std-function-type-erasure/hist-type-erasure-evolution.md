# 📜 Історія та еволюція стирання типів у C++: від Boost.Function до C++26

Історичний розвиток універсальних обгорток функціональних об'єктів у мові C++ відображає тривалу боротьбу між виражальністю високого рівня, ефективністю виклику та метапрограмуванням шаблонів. До появи стандарту C++11 мова не мала вбудованого механізму для передачі та збереження довільних викликальних об'єктів (англ. *callables*) без використання жорсткого спадкування або сирих функціональних вказівників мови C.

## Витоки: Проблема callback-функцій та бібліотека Boost.Function (2001)

Наприкінці 1990-х років розробка графічних інтерфейсів (GUI), асинхронних мережевих систем та обробників подій у C++ зіткнулася з фундаментальним обмеженням сирих C-вказівників на функції `R(*)(Args...)`. Вказівники мови C не могли зберігати стан, що унеможливлювало використання функціональних об'єктів (функторів із перевизначеним `operator()`), методів класів та об'єктів із прив'язаними аргументами.

Альтернативний підхід — класична ООП-ієрархія з абстрактним базовим класом на кшталт `class ICommandHandler { virtual void execute() = 0; }` — вимагав від кожного користувацького класу успадковувати конкретний інтерфейс. Це унеможливлювало передачу сторонніх бібліотечних функцій або простих глобальних функцій без створення громіздких класів-адаптерів (англ. *wrappers*).

У 2001 році американський дослідник Даглас Ґреґор (Douglas Gregor) створив бібліотеку **Boost.Function** як частину колекції Boost (версія 1.23.0). Основною ідеєю Ґреґора стало поєднання двох протилежних світів:
1. **Шаблонний конструктор** (англ. *template constructor*), який приймає об'єкт довільного типу `F` за умови, що він задовольняє синтаксису виклику `f(args...)`.
2. **Нешаблонний зовнішній тип** `boost::function<R(Args...)>`, який приховує конкретний тип `F` за внутрішньою таблицею функціональних покажчиків або віртуальним інтерфейсом.

Ця техніка отримала назву **стирання типів** (англ. *type erasure*). Вона дозволила створювати гетерогенні контейнери, наприклад `std::vector<boost::function<void()>>`, і зберігати там глобальні функції, функтори та результати викликів `boost::bind`.

```cpp
#include <boost/function.hpp>
#include <boost/bind.hpp>
#include <iostream>

struct Calculator {
    void add(int a, int b) { std::cout << (a + b) << '\n'; }
};

void legacy_print(int result) {
    std::cout << "Result: " << result << '\n';
}

int main() {
    // Boost.Function зберігає як вказівники на функції, так і зв'язані методи
    boost::function<void(int, int)> func1 = &legacy_print; // Адаптація сигнатури
    
    Calculator calc;
    boost::function<void()> func2 = boost::bind(&Calculator::add, &calc, 10, 20);
    
    func2(); // Друкує 30
}
```

Головним викликом бібліотеки Boost.Function на компіляторах початку 2000-х років (на кшталт GCC 2.95 або MSVC 6.0) була відсутність варіативних шаблонів (англ. *variadic templates*). Щоб підтримати функції з різною кількістю аргументів (від 0 до 10), розробники Boost вимушені були використовувати макроси препроцесора та згенеровані файли заголовків видами `boost/function/function0.hpp`, `function1.hpp` аж до `function10.hpp`.

## Технічний звіт C++ TR1 (2005) та стандартизація в C++11

У 2005 році Комітет зі стандартизації C++ опублікував **Technical Report 1 (TR1)** (ISO/IEC TR 19768:2007), куди Boost.Function увійшов під ім'ям `std::tr1::function` у просторі імен `std::tr1`.

З прийняттям стандарту **C++11** відбувся якісний стрибок у розвитку Type Erasure:
1. **Варіативні шаблони (Variadic Templates)**: Дозволили визначити `std::function<R(Args...)>` через єдине шаблонне визначення з розпакуванням пакетів параметрів `Args...`, усунувши потребу в макросних згенерованих файлах.
2. **Семантика переміщення (Move Semantics)**: Конструктори та оператори присвоєння `std::function` отримали можливість переміщувати ресурси внутрішнього функтора за `O(1)`, якщо функтор знаходився у купі.
3. **Лямбда-вирази (Lambda Expressions)**: Поява анонімних лямбда-функцій у C++11 створила синергетичний ефект. `std::function` став природним контейнером для збереження лямбд із захватом контексту.
4. **Small Buffer Optimization (SBO)**: Стандарт C++11 рекомендував реалізаціям зберігати малі функтори безпосередньо всередині об'єкта `std::function` без виділення пам'яті у купі через `malloc` / `operator new`.

Проте реалізація `std::function` у C++11 зафіксувала фундаментальне обмеження: об'єкт, який стирається, **мусить бути копійованим** (англ. *CopyConstructible*). Це було зумовлено тим, що сам клас `std::function` підтримував копіювання, а отже, його таблиця методів повинна була містити вказівник на функцію копіювання внутрішнього об'єкта.

## Занепад C++11 дизайну та виклики сучасної семантики: move-only об'єкти

З появою в C++11 типів, що підтримують лише переміщення (англ. *move-only types*), таких як `std::unique_ptr`, `std::thread`, `std::future` або файлові дескриптори, обмеження `std::function` стало критичною перешкодою.

Якщо лямбда-вираз захоплював `std::unique_ptr`, спроба зберегти таку лямбду у `std::function` призводила до помилки компіляції:

```cpp
auto ptr = std::make_unique<int>(42);
auto lambda = [p = std::move(ptr)]() { return *p; };

// ПОМИЛКА КОМПІЛЯЦІЇ у C++11..C++20:
// std::function вимагає, щоб лямбда була CopyConstructible!
// std::function<int()> fn = std::move(lambda); 
```

Розробники системного коду тривалий час використовували власні кишенькові реалізації (наприклад, `folly::Function` від Meta або `absl::AnyInvocable` від Google).

## Еволюція у C++23: `std::move_only_function`

У стандарті **C++23** Комітет вирішив цю проблему, додавши новий тип `std::move_only_function` (пропозиція **P0288R9**).

Головні відмінності `std::move_only_function` від класичного `std::function`:
1. **Підтримка Move-Only типів**: Конструктор не вимагає `CopyConstructible`, що дозволяє зберігати лямбди із захватом `std::unique_ptr` чи `std::thread`.
2. **Відсутність оператора копіювання**: Клас не має `operator=(const move_only_function&)` та конструктора копіювання.
3. **Кваліфікатори виклику (Const/Ref/Noexcept)**: `std::move_only_function` дозволяє явно вказувати кваліфікатори для внутрішнього `operator()`:

```cpp
// Підтримує лише виклики на const-об'єктах та гарантує noexcept
std::move_only_function<void() const noexcept> safe_fn;

// Підтримує лише виклик на rvalue (&)
std::move_only_function<void() &&> one_shot_fn;
```

4. **Відсутність RTTI та `target()`**: Для зменшення розміру vtable та прискорення виклику з `std::move_only_function` видалено метод `target()` та інтроспекцію типів через `typeid`.

## Легковаговий погляд без володіння: `std::function_ref` (C++26)

У стандарті **C++26** (пропозиція **P0792R14**) було додано ще один довгоочікуваний тип — `std::function_ref`.

На відміну від `std::function` та `std::move_only_function`, клас `std::function_ref` є **безволодісним поглядом** (англ. *non-owning view*), аналогічно до `std::string_view` або `std::span`.

```cpp
// C++26: std::function_ref не виділяє пам'ять і не копіює функтор
void process_events(std::function_ref<void(int)> callback) {
    callback(100);
}

int main() {
    auto heavy_lambda = [buffer = std::vector<int>(1000)] (int val) {
        // ...
    };
    
    // Передача без жодної алокації та без копіювання векторного буфера!
    process_events(heavy_lambda);
}
```

`std::function_ref` складається лише з двох покажчиків (`sizeof = 16` байтів):
- `void* object_ptr` — адреса самого функтора чи контексту в пам'яті;
- `R (*thunk_ptr)(void*, Args...)` — статична функція-перехідник.

Це повністю усуває алокації у купі та забезпечує мінімальні накладні витрати виклику, роблячи `std::function_ref` ідеальним вибором для параметрів функцій.
