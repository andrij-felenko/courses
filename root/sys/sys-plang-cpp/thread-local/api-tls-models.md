## 1. Специфікатор thread_local: синтаксичні комбінації та правила зв'язування

Специфікатор `thread_local` (введений у C++11) оголошує об'єкт із **тривалістю зберігання потоку** (thread storage duration). Пам'ять під об'єкт виділяється окремо для кожного потоку виконання, і час життя змінної прив'язаний до життєвого циклу потоку, що її створив.

### Таблиця комбінацій специфікаторів

| Оголошення | Область видимості (Scope) | Зв'язування (Linkage) | Час життя (Lifetime) | Коментар та семантика |
| :--- | :--- | :--- | :--- | :--- |
| `thread_local T x;` (у просторі імен / глобально) | Global / Namespace | Зовнішнє (External) | Від старту потоку до його виходу | Доступна з інших одиниць трансляції через `extern thread_local T x;`. |
| `static thread_local T x;` (у просторі імен) | Translation Unit | Внутрішнє (Internal) | Від старту потоку до його виходу | Приватна копія для кожного потоку в межах поточного файлу `.cpp`. |
| `extern thread_local T x;` | Global / Namespace | Зовнішнє (External) | Від старту потоку до його виходу | Декларація символу, визначеного в іншій одиниці трансляції. |
| `thread_local T x;` (всередині функції / блоку) | Блочна (Block) | Відсутнє (No linkage) | Від першого проходу виконання до виходу потоку | Автоматично має статичну тривалість прив'язки (неявно є `static thread_local`). Ініціалізується ліниво. |
| `static thread_local T x;` (всередині класу) | Class Scope | Зовнішнє (External) | Від старту потоку до його виходу | Статичний член класу, окремий екземпляр для кожного потоку. Вимагає визначення поза класом. |
| `inline thread_local T x;` (C++17) | Global / Class | Зовнішнє (External) | Від старту потоку до його виходу | Дозволяє визначення в заголовковому файлі `.hpp` без порушення правила ODR (One Definition Rule). |
| `constinit thread_local T x;` (C++20) | Global / Static / Class | Відповідно до контексту | Від старту потоку до його виходу | Гарантує статичну константну ініціалізацію на етапі компіляції. Забороняє динамічні конструктори. |

### Неприпустимі комбінації (помилки компіляції)

1. **`thread_local auto x;` як локальна змінна без ініціалізатора**: Компілятор не може вивести тип.
2. **`thread_local` для параметрів функцій**: Параметри функцій завжди розміщуються на стеку виконання і мають автоматичну тривалість зберігання.
3. **`thread_local` для нестатичних членів класу/структури**: Поле класу не може бути `thread_local`, якщо сам екземпляр класу живе на купі чи на стеку. Дозволено лише для `static` членів.
4. **`constexpr thread_local T x;`**: Специфікатор `constexpr` неявно додає `const`, але вказує на константу часу компіляції процесу. Для вимоги константної ініціалізації локальних змінних потоку в C++20 використовується виключно `constinit thread_local`.

## 2. Правила ініціалізації та розгортання конструкторів

Стандарт C++ поділяє ініціалізацію `thread_local` об'єктів на дві фази: **статичну (константну)** та **динамічну**.

### Статична (константна) ініціалізація
Якщо змінна ініціалізується константним виразом (або має тривіальний конструктор за замовчуванням):
- Компілятор записує її значення безпосередньо у бінарну секцію `.tdata` (ініціалізовані дані) або резервує місце в секції `.tbss` (занулені дані).
- Під час системного виклику створення потоку пам'ять миттєво копіюється з шаблону.
- Доступ до такої змінної не потребує жодних перевірок guard-змінних і виконується за 1 інструкцію.

### Динамічна ініціалізація та приховані функції-обгортки
Якщо тип `T` має нетривіальний конструктор (наприклад, `std::string`, `std::vector` або користувацький клас):
- Компілятор не може заздалегідь заповнити секцію `.tdata`.
- Для кожної такої змінної генерується прихована статична булева змінна-прапорець `__tls_guard` та функція-обгортка `__tls_init()`.
- Кожне звернення до змінної у коді підміняється компілятором на виклик цієї обгортки.

```cpp
// Код користувача:
thread_local std::string per_thread_name = "worker-" + get_uuid();

// Псевдокод, який генерує компілятор (Clang/GCC Itanium ABI):
static thread_local bool __tls_guard_per_thread_name = false;
static thread_local char __tls_storage_per_thread_name[sizeof(std::string)];

std::string& __get_per_thread_name() {
    if (!__tls_guard_per_thread_name) {
        __tls_guard_per_thread_name = true;
        // 1. Виклик конструктора на сирій пам'яті (placement new)
        new (__tls_storage_per_thread_name) std::string("worker-" + get_uuid());
        // 2. Реєстрація деструктора в рантаймі потоку
        __cxa_thread_atexit(
            [](void* ptr) { reinterpret_cast<std::string*>(ptr)->~basic_string(); },
            __tls_storage_per_thread_name,
            &__dso_handle
        );
    }
    return *reinterpret_cast<std::string*>(__tls_storage_per_thread_name);
}
```

## 3. Чотири моделі адресації ELF TLS: механіка та релаксації компонувальника

Компілятори для систем Linux та POSIX (GCC, Clang) підтримують чотири моделі доступу до `thread_local` змінних. Вибір моделі визначає баланс між швидкістю доступу (кількістю інструкцій CPU) та гнучкістю розміщення змінної (у головному бінарнику чи у динамічно завантажуваній бібліотеці). Модель вказується явно прапорцем `-ftls-model=<model>`.

### 1. Local Exec (LE) — `-ftls-model=local-exec`
Модель призначена виключно для основного виконуваного файлу програми (main executable). Вона спирається на інваріант: розмір та зміщення статичного TLS-блоку програми відомі лінкеру ще на етапі статичного збирання. Змінна ніколи не експортується у спільні бібліотеки.

На архітектурі x86-64 сегментний регістр `%fs` вказує на початок структури TCB (Thread Control Block). Статичний сегмент TLS розташовується безпосередньо перед TCB у від'ємній області адрес. Компонувальник обчислює точне байтове зміщення символу (наприклад, `-16` або `-32`) і генерує пряму інструкцію читання без жодних релокацій під час завантаження:

```asm
movq %fs:-16, %rax    ; Пряме апаратне читання: 1 інструкція CPU, 1 такт
```

На архітектурі AArch64 (ARM 64-bit) покажчик потоку зберігається в системному регістрі `TPIDR_EL0`. Статичний TLS розташовується вище TCB (додатні зміщення), тому компілятор генерує інструкції:

```asm
mrs  x0, TPIDR_EL0    ; Читання покажчика потоку у регістр x0
ldr  x1, [x0, #16]    ; Завантаження значення за відомим зміщенням
```

### 2. Initial Exec (IE) — `-ftls-model=initial-exec`
Модель застосовується для змінних у спільних бібліотеках (`.so`), які гарантовано завантажуються під час старту процесу (наприклад, через секцію `DT_NEEDED`), або коли змінна з головного виконуваного файлу експортується назовні.

Оскільки бібліотека може бути завантажена у довільний адресний простір, статичне зміщення змінної відносно `%fs` невідоме на етапі компіляції. Динамічний лінкер (`ld.so`) під час ініціалізації процесу виділяє місце у статичному пулі TLS і записує підсумкове зміщення у глобальну таблицю зміщень (Global Offset Table — GOT).

Асемблерний код на x86-64 складається з двох послідовних інструкцій:

```asm
movq var@gottpoff(%rip), %rax   ; 1. Завантаження зміщення з GOT (релокація R_X86_64_GOTTPOFF)
movq %fs:(%rax), %rcx           ; 2. Читання пам'яті за адресою %fs + %rax
```

Накладні витрати становлять одне додаткове читання з пам'яті (таблиця GOT майже завжди знаходиться у гарячому кеші L1), без виклику будь-яких рантайм-процедур.

### 3. Local Dynamic (LD) — `-ftls-model=local-dynamic`
Модель оптимізує доступ до кількох `thread_local` змінних з внутрішнім зв'язуванням (`static` або з видимістю `hidden`), визначених у межах однієї спільної бібліотеки.

Замість того, щоб викликати важку функцію динамічного пошуку окремо для кожної змінної, компілятор виконує один виклик `__tls_get_addr()` для отримання базової адреси TLS-блоку всієї бібліотеки, після чого кожна конкретна змінна адресується через фіксоване зміщення від цієї бази:

```asm
leaq var@tlsld(%rip), %rdi      ; Передача дескриптора модуля в перший аргумент (R_X86_64_TLSLD)
call __tls_get_addr@PLT         ; Отримання базової адреси TLS-блоку поточного модуля
leaq var1@dtpoff(%rax), %rcx    ; Обчислення адреси змінної 1 (R_X86_64_DTPOFF32)
leaq var2@dtpoff(%rax), %rdx    ; Обчислення адреси змінної 2 без повторного виклику функції
```

### 4. General Dynamic (GD) — `-ftls-model=global-dynamic`
Універсальна і найбільш гнучка модель, яка використовується за замовчуванням при компіляції позиційно-незалежного коду (`-fPIC`). Вона дозволяє безпечно звертатися до експортованих TLS-символів, визначених у будь-яких бібліотеках, зокрема завантажених під час роботи програми через виклик `dlopen()`.

Компілятор не робить жодних припущень про розташування змінної і на кожне звернення генерує повний виклик диспетчера TLS:

```asm
leaq var@tlsgd(%rip), %rdi      ; Покажчик на структуру {module_id, offset} (R_X86_64_TLSGD)
call __tls_get_addr@PLT         ; Динамічний пошук через Dynamic Thread Vector (DTV)
movq (%rax), %rcx               ; Читання значення за повернутою адресою
```

### Релаксація релокацій компонувальником (Linker Relaxation)
Якщо код компілювався з моделлю General Dynamic (`-fPIC`), але під час фінального збирання статичний лінкер бачить, що символ компонується у виконуваний файл без експорту, він виконує автоматичну оптимізацію інструкцій на рівні байтів:
- **GD → LE Relaxation**: Виклик `call __tls_get_addr` та інструкція `leaq` замінюються компілятором на `movq %fs:offset, %rax` із додаванням NOP-байт для вирівнювання довжини коду.
- **IE → LE Relaxation**: Інструкція читання GOT `movq var@gottpoff(%rip), %rax` замінюється на безпосереднє зміщення `movq $offset, %rax`.

## 4. Проблема вичерпання статичного пулу TLS (Dynamic TLS Exhaustion)

Одна з найнебезпечніших системних помилок у багатопотокових серверах та плагінних архітектурах — це помилка завантаження бібліотеки під час роботи програми:

```text
dlopen: cannot load shared library: cannot allocate memory in static TLS block
```

### Причина виникнення
Коли операційна система створює процес, динамічний лінкер `glibc` виділяє фіксований резервний пул пам'яті для статичного TLS (Initial Exec). Цей пул має обмежений розмір (за замовчуванням у `glibc` це всього 2048–4096 байтів).

Якщо стороння бібліотека (наприклад, оптимізований аллокатор `jemalloc`, бібліотека паралелізму OpenMP `libgomp` або розширення для штучного інтелекту) була скомпільована з прапорцем `-ftls-model=initial-exec` заради максимальної швидкодії, вона вимагає розміщення своїх `thread_local` змінних виключно у цьому статичному пулі. 

Коли програма завантажує кілька таких бібліотек динамічно через `dlopen()`:
1. Статичний пул TLS повністю заповнюється.
2. Черговий виклик `dlopen()` зазнає невдачі, повертаючи нульовий покажчик, навіть якщо у системі є гігабайти вільної оперативної пам'яті.

### Способи вирішення та системні налаштування
1. **Зміна моделі компіляції бібліотеки**: Компілювати спільні бібліотеки з моделлю за замовчуванням (`global-dynamic`) або використовувати `-ftls-model=global-dynamic`.
2. **Попереднє завантаження через LD_PRELOAD**: Якщо бібліотека завантажується на етапі старту процесу (до фіксації розміру пулу TLS), лінкер автоматично враховує її розмір при розрахунку початкового TCB:
   ```bash
   LD_PRELOAD=/usr/lib/libgomp.so.1 ./my_server_application
   ```
3. **Налаштування параметрів glibc (Linux glibc 2.32+)**: Збільшення розміру статичного резерву через системну змінну оточення:
   ```bash
   GLIBC_TUNABLES=glibc.rtld.optional_static_tls=16384 ./my_server_application
   ```

## 5. Системні структури та рантайм-інтерфейси (Runtime ABI)

### Структура tls_index (ELF ABI)

Для динамічних моделей адресації (GD/LD) динамічний лінкер використовує структуру дескриптора, яка передається першим аргументом у функцію розв'язання адрес:

:::tabs
```c
/* Структура дескриптора TLS для виклику __tls_get_addr в ELF ABI */
typedef struct {
    unsigned long int ti_module; /* Ідентифікатор модуля (Module ID в DTV) */
    unsigned long int ti_offset; /* Зміщення змінної всередині TLS-блоку модуля */
} tls_index;
```
```cpp
// Типізоване представлення дескриптора TLS в C++
#include <cstddef>

struct alignas(alignof(std::size_t)) TlsIndex {
    std::size_t moduleId;  // Ідентифікатор спільного об'єкта в DTV
    std::size_t offset;    // Зміщення символу в локальному блоці модуля
};
```
:::

### Функція __tls_get_addr

:::tabs
```c
/* Сигнатура функції ядра динамічного лінкера (ld-linux.so / glibc) */
void* __tls_get_addr(tls_index* ti);
```
```cpp
// Оголошення функції динамічного лінкера в C++ (Itanium ABI)
extern "C" void* __tls_get_addr(TlsIndex* ti) noexcept;
```
:::

**Алгоритм роботи диспетчера `__tls_get_addr`**:
1. Зчитує покажчик на масив DTV (Dynamic Thread Vector) потоку з TCB (Thread Control Block) через зміщення `%fs:0x8` (або `0x10` залежно від архітектури).
2. Перевіряє покоління вектора DTV (`dtv[0].counter`). Якщо з моменту останнього звернення відбулося вивантаження або завантаження бібліотек (`dlopen`/`dlclose`), рантайм оновлює таблицю модулів через функцію `_dl_update_slotinfo()`.
3. Перевіряє запис `dtv[ti->ti_module]`:
   - Якщо блок пам'яті для зазначеного модуля вже виділено для поточного потоку, повертає адресу `dtv[ti->ti_module] + ti->ti_offset`.
   - Якщо блок пам'яті ще не існує (ліниве виділення), викликає внутрішню функцію аллокації, копіює шаблон ініціалізації `.tdata` відповідної бібліотеки, занулює діапазон `.tbss`, зберігає отриману адресу у DTV і повертає кінцевий покажчик.

### Реєстрація та виконання деструкторів: __cxa_thread_atexit

Для коректного знищення нетривіальних об'єктів C++ (об'єктів із користувацькими деструкторами) рантайм використовує функцію стандарту Itanium C++ ABI:

:::tabs
```c
/* Сигнатура реєстрації деструктора локального об'єкта потоку */
int __cxa_thread_atexit(void (*destructor)(void*), void* obj, void* dso_handle);
```
```cpp
// Сигнатура реєстрації деструктора в C++ Itanium ABI
extern "C" int __cxa_thread_atexit(
    void (*destructor)(void*) noexcept,
    void* obj,
    void* dso_handle
) noexcept;
```
:::

- **`destructor`**: Покажчик на функцію-деструктор екземпляра.
- **`obj`**: Покажчик на фізичну пам'ять екземпляра об'єкта у локальному сховищі потоку.
- **`dso_handle`**: Дескриптор динамічної бібліотеки (Dynamic Shared Object). Він необхідний для запобігання фатальним помилкам: якщо динамічну бібліотеку вивантажують через `dlclose()` до завершення роботи потоків, рантайм примусово викликає всі деструктори, зареєстровані з цим `dso_handle`, до вивантаження коду деструкторів із віртуальної пам'яті.

**Порядок виконання деструкторів під час виходу з потоку**:
1. Коли головна функція потоку повертає керування (або потік викликає `pthread_exit()`), C++ runtime починає обхід зареєстрованого зв'язаного списку деструкторів.
2. Деструктори викликаються у **строго зворотному порядку** відносно завершення виконання їхніх конструкторів.
3. Якщо всередині деструктора одного `thread_local` об'єкта створюється інший `thread_local` об'єкт, рантайм реєструє новий деструктор і повторює цикл очищення. Стандарт POSIX гарантує щонайменше `PTHREAD_DESTRUCTOR_ITERATIONS` (зазвичай 4 або 8) ітерацій очищення, після чого незнищені об'єкти відкидаються для запобігання нескінченним циклам.

## 6. Порівняння архітектурних реалізацій TLS

| Параметр | Linux / ELF (x86-64) | Linux / ELF (AArch64) | Windows (x64) |
| :--- | :--- | :--- | :--- |
| **Регістр покажчика потоку** | Сегментний регістр `%fs` (база MSR) | Системний регістр `TPIDR_EL0` | Сегментний регістр `%gs` |
| **Структура керування** | TCB (Thread Control Block) | TCB (Variant I / II) | TEB (Thread Environment Block) |
| **Зміщення статичного TLS** | Від'ємні зміщення від `%fs:0` (`%fs:-offset`) | Додатні зміщення від `TPIDR_EL0` | Масив `ThreadLocalStoragePointer` у TEB |

## 8. Сучасна оптимізація: TLS Descriptors (TLSDESC / -mtls-dialect=gnu2)

Традиційні моделі General Dynamic та Local Dynamic вимагають обов'язкового виклику функції `__tls_get_addr()` через таблицю процедурних зв'язків (PLT) на кожне звернення. У програмах із сотнями викликів це спричиняє відчутні втрати тактів CPU через збереження регістрів та переходи.

Для усунення цієї неефективності Александр Оліва (Alexandre Oliva) розробив оптимізацію **TLS Descriptors (TLSDESC)**, яка підтримується в GCC, Clang та сучасних версіях `glibc` (прапорець `-mtls-dialect=gnu2`).

### Принцип роботи TLSDESC
Замість передачі структури `tls_index` у загальну функцію `__tls_get_addr`, компілятор виділяє у таблиці GOT дві сусідні комірки — **TLS Descriptor**:
1. Перша комірка містить покажчик на спеціалізовану функцію-обробник (resolver function).
2. Друга комірка містить аргумент для цього обробника (модуль або статичне зміщення).

Коли потік звертається до змінної, він виконує непрямий виклик через покажчик із GOT:
- Якщо під час завантаження динамічний лінкер бачить, що змінна потрапила у статичний пул TLS (Static TLS), він підставляє у першу комірку GOT адресу швидкої функції-трампліна `_dl_tlsdesc_return`. Ця функція повертає обчислене зміщення безпосередньо у регістрі `RAX` без збереження контексту регістрів (за 1–2 такти).
- Лише якщо змінна потребує динамічного виділення пам'яті через DTV, у GOT записується покажчик на повний динамічний диспетчер `_dl_tlsdesc_dynamic`.

Завдяки TLSDESC швидкість доступу до динамічних TLS-змінних наближається до швидкості моделі Initial Exec, зберігаючи повну безпеку динамічного завантаження бібліотек.

## 9. Внутрішня архітектура TLS у Windows та MSVC CRT

Операційна система Windows реалізує механізм локальної пам'яті потоку через структури завантажувача PE (Portable Executable) та блоку оточення потоку (Thread Environment Block — TEB).

### Структура каталогу IMAGE_TLS_DIRECTORY
У заголовку PE-файлу виконуваного модуля компілятор MSVC формує дескриптор каталогу TLS (`IMAGE_DIRECTORY_ENTRY_TLS`):
- `StartAddressOfRawData` та `EndAddressOfRawData`: Межі діапазону пам'яті шаблону ініціалізації (аналог `.tdata`).
- `AddressOfIndex`: Адреса змінної `_tls_index`, куди завантажувач записує числовий індекс слота модуля у масиві потоку.
- `AddressOfCallBacks`: Масив покажчиків на функції зворотного виклику (TLS Callbacks).
- `SizeOfZeroFill`: Кількість байтів, які занулюються після копіювання шаблону (аналог `.tbss`).

### Таблиця колбеків .CRT$XL*
Для забезпечення виклику конструкторів і деструкторів під час створення та знищення потоків MSVC CRT використовує спеціальні злиті секції бінарного файлу:
- `.CRT$XLA` — покажчик на початок масиву зворотних викликів.
- `.CRT$XLB` — реєстрація користувацьких та системних TLS-колбеків.
- `.CRT$XLZ` — нульовий термінатор масиву.

Коли процес створює новий потік операційної системи (`CreateThread`), ядро Windows перед запуском стартової функції потоку автоматично сканує масив `AddressOfCallBacks` усіх завантажених DLL-модулів і викликає зареєстровані колбеки з кодом події `DLL_THREAD_ATTACH`. Під час завершення потоку колбеки викликаються з кодом `DLL_THREAD_DETACH` для виклику деструкторів.

## 10. Критичні крайові випадки та пастки часу життя

### 1. Передача посилання або покажчика на thread_local в інший потік
Специфікатор `thread_local` визначає виключно спосіб виділення та час життя пам'яті. Він **не забороняє** отримати адресу змінної `&x` та передати її через спільний покажчик у сусідній потік.

```cpp
thread_local int thread_private_value = 100;

void dangerous_sharing(int*& out_ptr) {
    out_ptr = &thread_private_value; // Збереження адреси локальної змінної
} // Якщо потік завершується, thread_private_value ЗНИЩУЄТЬСЯ!

// В іншому потоці:
// *out_ptr = 200; // КАТАСТРОФА! Use-After-Free! Пам'ять TLS потоку вже звільнена ОС!
```

Якщо потік-власник завершує своє виконання, операційна система повертає сторінки TLS ядра або занулює пам'ять. Будь-яке наступне читання або запис через збережений покажчик у сусідньому потоці викликає фатальну помилку використання пам'яті після звільнення (Use-After-Free) та сегфолт.

### 2. Поведінка thread_local при виклику std::exit(), std::quick_exit() та _Exit()
Стандарт C++ чітко розмежовує сценарії завершення роботи програми:
- **Штатний вихід потоку**: Викликаються всі деструктори `thread_local` об'єктів даного потоку у зворотному порядку створення.
- **Виклик `std::exit()`**: Викликаються деструктори `thread_local` об'єктів **лише того потоку, який викликав `std::exit()`**, після чого викликаються глобальні деструктори `static` об'єктів. Інші паралельні потоки миттєво перериваються без виклику жодних деструкторів їхніх `thread_local` змінних!
- **Виклик `std::quick_exit()`**: Викликаються виключно обробники `std::at_quick_exit()`. Жодні деструктори `thread_local` об'єктів у жодному потоці не викликаються.
- **Виклик `std::_Exit()` або `std::abort()`**: Процес миттєво вбивається операційною системою без виклику деструкторів.

## 11. Взаємодія з інструментами динамічного аналізу (ASan, TSan, Valgrind)

Локальна пам'ять потоків вимагає спеціальної підтримки з боку санітайзерів компілятора:

1. **AddressSanitizer (ASan / `-fsanitize=address`)**: ASan розміщує захисні червоні зони (redzones) навколо кожної змінної у статичних секціях `.tdata` та `.tbss`. Це дозволяє перехоплювати помилки виходу за межі буфера (buffer overflow) у локальних масивах потоку.
2. **ThreadSanitizer (TSan / `-fsanitize=thread`)**: TSan ігнорує звернення потоку до власних `thread_local` змінних, оскільки вони є ізольованими за означенням. Проте якщо адресу `&x` передано в інший потік і до неї звертаються без синхронізації м'ютексом чи атоміками, TSan миттєво фіксує та діагностує гонку даних (Data Race on TLS memory).
3. **Valgrind (Memcheck)**: Потребує сучасної версії glibc з підтримкою налагоджувальних символів TLS, інакше динамічні виділення пам'яті всередині `__tls_get_addr` для DTV можуть помилково фіксуватися як втрачені блоки (still reachable memory).
