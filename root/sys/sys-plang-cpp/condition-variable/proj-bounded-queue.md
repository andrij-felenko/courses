# ⚙️ Реалізація потокобезпечної обмеженої черги (Bounded Concurrent Queue)

Обмежена потокобезпечна черга (англ. *Bounded Concurrent Queue* або *Bounded Producer-Consumer Queue*) є фундаментальною структурою даних у сфері високозавантаженого паралельного програмування. Вона слугує сполучною ланкою між потоками-виробниками (англ. *producers*), які генерують завдання чи оброблювальні блоки даних, та потоками-споживачами (англ. *consumers*), які вилучають ці дані та виконують їх безпосередню обробку.

Головним призначенням обмеженої черги є регулювання швидкості обробки та запобігання неконтрольованому споживанню оперативної пам'яті. Якщо потоки-виробники починають генерувати елементи швидше, ніж потоки-споживачі встигають їх опрацьовувати, черга розростається до заданої верхньої межі (місткості). Після досягнення цієї межі будь-який подальший спроба додати елемент змушує потік-виробник призупинити виконання й заснути на умовній змінній `cv_not_full_`. Коли один зі споживачів вилучає елемент, він сповіщає виробників про появу вільного місця. Аналогічно, якщо черга стає порожньою, потоки-споживачі переходять у сон на умовній змінній `cv_not_empty_` до появі нових елементів.

## 1. Архітектурні вимоги, інваріанти та дизайн

Для побудови надійної промислової черги, придатної для використання у багаторазово потокових серверах та алгоритмах обробки даних, необхідно забезпечити дотримання чотирьох ключових архітектурних інваріантів:

1. **Строге обмеження місткості (Bounded Capacity):** Задання максимальної кількості елементів при ініціалізації структури. Це запобігає вичерпанню пам'яті (OOM) під час сплесків навантаження.
2. **Двоканальна синхронізація через умовні змінні:**
   * `cv_not_empty_` — умовна змінна, на якій чекають споживачі, коли черга порожня.
   * `cv_not_full_` — умовна змінна, на якій чекають виробники, коли черга заповнена.
3. **Корректне та безпечне завершення (Graceful Shutdown):** Підтримка спеціального прапорця зупинки `stopped_`. При виклику методу `shutdown()` черга розблоковує абсолютно всі заснулі потоки виробників та споживачів, дозволяючи їм коректно завершити виконання без вичного зависання чи витоку ресурсів.
4. **Сувора гарантія безпеки винятків (Strong Exception Guarantee):** Якщо під час копіювання чи переміщення об'єкта всередині черги виникає виняток, стан черги залишається валідним, а утримувані м'ютекси автоматично звільняються завдяки RAII-обгорткам.

## 2. Реалізація: Порівняння C++ та POSIX C

Нижче наведено дві повноцінні реалізації потокобезпечної обмеженої черги. 

Реалізація мовою C++ спирається на шаблони типів, RAII-замки `std::unique_lock`, примітиви `std::condition_variable`, автоматичне управління пам'яттю контейнера `std::queue` та семантику переміщення `std::move`. 

Реалізація мовою C показує низькорівневу побудову аналогічної структури над системними примітивами POSIX `pthread_mutex_t` та `pthread_cond_t` із кільцевим буфером (англ. *ring buffer*) на динамічному масиві покажчиків та явним управлінням пам'яттю.

```cpp
#include <iostream>
#include <queue>
#include <mutex>
#include <condition_variable>
#include <optional>
#include <thread>
#include <vector>
#include <chrono>

template <typename T>
class BoundedQueue {
public:
    explicit BoundedQueue(std::size_t capacity)
        : capacity_(capacity), stopped_(false) {}

    ~BoundedQueue() {
        shutdown();
    }

    // Забороняємо копіювання для запобігання гонкам замків
    BoundedQueue(const BoundedQueue&) = delete;
    BoundedQueue& operator=(const BoundedQueue&) = delete;

    // Вставка елемента (блокування виробника при переповненні)
    bool push(T item) {
        std::unique_lock<std::mutex> lock(mtx_);
        
        // Очікуємо появу вільного місця або сигнал зупинки
        cv_not_full_.wait(lock, [this]() {
            return queue_.size() < capacity_ || stopped_;
        });

        if (stopped_) {
            return false; // Черга закрита для запису
        }

        queue_.push(std::move(item));

        // Сповіщаємо один із потоків-споживачів про появу елемента
        cv_not_empty_.notify_one();
        return true;
    }

    // Вилучення елемента (блокування споживача при порожній черзі)
    std::optional<T> pop() {
        std::unique_lock<std::mutex> lock(mtx_);

        // Очікуємо наявність елементів або сигнал зупинки
        cv_not_empty_.wait(lock, [this]() {
            return !queue_.empty() || stopped_;
        });

        if (queue_.empty() && stopped_) {
            return std::nullopt; // Черга порожня й закрита
        }

        T item = std::move(queue_.front());
        queue_.pop();

        // Сповіщаємо один із потоків-виробників про наявність вільного місця
        cv_not_full_.notify_one();
        return item;
    }

    // Сигнал чистого завершення роботи
    void shutdown() {
        {
            std::lock_guard<std::mutex> lock(mtx_);
            if (stopped_) return;
            stopped_ = true;
        }
        // Розблоковуємо абсолютно всі потоки в чергах сну
        cv_not_empty_.notify_all();
        cv_not_full_.notify_all();
    }

    std::size_t size() const {
        std::lock_guard<std::mutex> lock(mtx_);
        return queue_.size();
    }

private:
    const std::size_t capacity_;
    std::queue<T> queue_;
    mutable std::mutex mtx_;
    std::condition_variable cv_not_empty_;
    std::condition_variable cv_not_full_;
    bool stopped_;
};
```
```c
#include <stdio.h>
#include <stdlib.h>
#include <stdbool.h>
#include <pthread.h>

typedef struct {
    void** buffer;
    size_t capacity;
    size_t head;
    size_t tail;
    size_t count;
    bool stopped;
    pthread_mutex_t mutex;
    pthread_cond_t cv_not_empty;
    pthread_cond_t cv_not_full;
} bounded_queue_t;

bounded_queue_t* queue_create(size_t capacity) {
    bounded_queue_t* q = (bounded_queue_t*)malloc(sizeof(bounded_queue_t));
    if (!q) return NULL;

    q->buffer = (void**)malloc(sizeof(void*) * capacity);
    if (!q->buffer) {
        free(q);
        return NULL;
    }

    q->capacity = capacity;
    q->head = 0;
    q->tail = 0;
    q->count = 0;
    q->stopped = false;

    pthread_mutex_init(&q->mutex, NULL);
    pthread_cond_init(&q->cv_not_empty, NULL);
    pthread_cond_init(&q->cv_not_full, NULL);

    return q;
}

bool queue_push(bounded_queue_t* q, void* data) {
    pthread_mutex_lock(&q->mutex);

    while (q->count == q->capacity && !q->stopped) {
        pthread_cond_wait(&q->cv_not_full, &q->mutex);
    }

    if (q->stopped) {
        pthread_mutex_unlock(&q->mutex);
        return false;
    }

    q->buffer[q->tail] = data;
    q->tail = (q->tail + 1) % q->capacity;
    q->count++;

    pthread_cond_signal(&q->cv_not_empty);
    pthread_mutex_unlock(&q->mutex);
    return true;
}

void* queue_pop(bounded_queue_t* q) {
    pthread_mutex_lock(&q->mutex);

    while (q->count == 0 && !q->stopped) {
        pthread_cond_wait(&q->cv_not_empty, &q->mutex);
    }

    if (q->count == 0 && q->stopped) {
        pthread_mutex_unlock(&q->mutex);
        return NULL;
    }

    void* data = q->buffer[q->head];
    q->head = (q->head + 1) % q->capacity;
    q->count--;

    pthread_cond_signal(&q->cv_not_full);
    pthread_mutex_unlock(&q->mutex);
    return data;
}

void queue_shutdown(bounded_queue_t* q) {
    pthread_mutex_lock(&q->mutex);
    if (q->stopped) {
        pthread_mutex_unlock(&q->mutex);
        return;
    }
    q->stopped = true;
    pthread_mutex_unlock(&q->mutex);

    pthread_cond_broadcast(&q->cv_not_empty);
    pthread_cond_broadcast(&q->cv_not_full);
}

void queue_destroy(bounded_queue_t* q) {
    if (!q) return;
    queue_shutdown(q);

    pthread_mutex_destroy(&q->mutex);
    pthread_cond_destroy(&q->cv_not_empty);
    pthread_cond_destroy(&q->cv_not_full);

    free(q->buffer);
    free(q);
}
```

## 3. Детальний аналіз реалізації та алгоритму

### Крок 1: Управління ресурсами та RAII у C++

У реалізації C++ використовується класична концепція RAII (англ. *Resource Acquisition Is Initialization*). М'ютекс `mtx_` обгортається в `std::unique_lock<std::mutex>` всередині методів `push()` та `pop()`. Це гарантує, що якщо під час виклику `queue_.push()` або `std::move()` виникне виняток (наприклад, виняток нехватки пам'яті `std::bad_alloc`), м'ютекс буде автоматично розблокований при розгортанні стека (англ. *stack unwinding*).

Використання `std::optional<T>` у коді C++ дозволяє елегантно обробити випадок закриття черги: коли метод `pop()` повертає `std::nullopt`, потік-споживач точно знає, що черга зупинена і нових даних більше не буде.

### Крок 2: Низькорівневий кільцевий буфер у C

У реалізації C замість готового STL-контейнера застосовується динамічний кільцевий буфер (англ. *ring buffer*). Стан буфера описується трьома індексами:
* `head` — індекс елемента, який буде вилучено наступним у виклику `pop()`.
* `tail` — індекс позиції, у яку буде записано наступний елемент у виклику `push()`.
* `count` — поточна кількість елементів у буфері.

Для обчислення наступних позицій використовується операція остачі від ділення: `(tail + 1) % capacity`. У критичних секціях функції `queue_push()` та `queue_pop()` перевірка стану виконується строго в циклах `while (count == capacity)` та `while (count == 0)` для захисту від фіктивних пробуджень POSIX `pthread_cond_wait()`.

### Крок 3: Стратегія розблокування при завершенні (Graceful Shutdown)

Ключовим моментом надійності структури даних є метод `shutdown()`. При завершенні роботи програми необхідно розбудити всі потоки, які заснули в очікуванні умовних змінних:
1. Прапорець `stopped` встановлюється у `true` під захистом м'ютекса.
2. Викликається `notify_all()` (або `pthread_cond_broadcast()`) для обох умовних змінних: `cv_not_empty_` та `cv_not_full_`.
3. Усі заснулі потоки прокидаються, перевіряють умову в циклі `while`, бачать `stopped == true` і безпечно повертають керування назовні без виклику винятків чи взаємного блокування.

## 4. Практичний демонстраційний тест (Producer-Consumer)

Нижче наведено повністю робочу програму на C++, яка демонструє роботу обмеженої черги при одночасному виконанні 2 потоків-виробників та 3 потоків-споживачів.

```cpp
int main() {
    // Створюємо чергу місткістю 5 елементів
    BoundedQueue<int> queue(5);

    std::vector<std::thread> producers;
    std::vector<std::thread> consumers;

    // Запуск 2 потоків-виробників
    for (int p = 0; p < 2; ++p) {
        producers.emplace_back([&queue, p]() {
            for (int i = 0; i < 10; ++i) {
                int item = p * 100 + i;
                if (queue.push(item)) {
                    std::cout << "[Producer " << p << "] Pushed: " << item << "\n";
                }
                std::this_thread::sleep_for(std::chrono::milliseconds(20));
            }
        });
    }

    // Запуск 3 потоків-споживачів
    for (int c = 0; c < 3; ++c) {
        consumers.emplace_back([&queue, c]() {
            while (true) {
                auto item = queue.pop();
                if (!item.has_value()) {
                    std::cout << "[Consumer " << c << "] Signal shutdown received. Exit.\n";
                    break;
                }
                std::cout << "[Consumer " << c << "] Popped: " << *item << "\n";
                std::this_thread::sleep_for(std::chrono::milliseconds(35));
            }
        });
    }

    // Очікуємо завершення роботи виробників
    for (auto& t : producers) {
        t.join();
    }

    // Ініціюємо чисте завершення черги
    queue.shutdown();

    // Очікуємо завершення роботи споживачів
    for (auto& t : consumers) {
        t.join();
    }

    std::cout << "Усі потоки успішно завершили роботу.\n";
    return 0;
}
```

## 5. Оптимізації продуктивності та крайові випадки

### 1. Поділ умовних змінних (cv_not_empty_ та cv_not_full_)

Ключовим архітектурним рішенням є використання двох окремих умовних змінних замість однієї спільної. Якщо б черга мала лише одну умовну змінну `cv_`, виклики `push()` та `pop()` були б змушені використовувати `notify_all()`. З єдиною умовною змінною виклик `notify_one()` міг би розбудити інший потік-виробник замість споживача, що призвело б до безневинного зависання всієї системи. Дві окремі змінні гарантують, що сигналізування направляється строго потрібній групі потоків.

### 2. Хибне розділення кеш-ліній (False Sharing)

У низькорівневих C-реалізаціях на багатоядерних процесорах індекси `head` та `tail` можуть потрапити на одну 64-байтну кеш-лінію (англ. *cache line*). Коли потік-виробник оновлює `tail`, а потік-споживач оновлює `head`, ядра процесора змушені постійно інвалідувати кеш-лінії один одного через протокол кеш-когерентності (MESI). Для усунення цього ефекту у високопродуктивних бібліотеках індекси вирівнюють за допомогою `alignas(64)` або додають пустий падінг (англ. *padding bytes*).

### 3. Продуктивність та масштабованість під навантаженням

Під час роботи з великою кількістю потоків (наприклад, 16 виробників та 16 споживачів) обмежена черга на основі м'ютекса стає вузьким місцем через затор м'ютекса (англ. *lock contention*). У таких випадках розробники переходять на lock-free черги на основі атомарних кільцевих буферів із CAS-інструкціями (`std::atomic::compare_exchange_weak`), проте для більшості прикладних задач реалізація на умовних змінних залишається еталоном за надійністю та простотою відлагодження.

## 6. Методний розбір та інваріанти безпеки винятків

### Аналіз методу push()

1. **Захоплення замка:** Потік ініціалізує `std::unique_lock<std::mutex> lock(mtx_)`. М'ютекс захоплюється блокуючим чином.
2. **Перевірка предиката:** Викликається `cv_not_full_.wait(lock, pred)`. Якщо `queue_.size() == capacity_` і `stopped_ == false`, потік атомарно відпускає `mtx_` і засинає.
3. **Обробка прапорця зупинки:** При пробудженні потік повторно захоплює `mtx_`. Якщо `stopped_ == true`, метод повертає `false`, не модифікуючи чергу.
4. **Вставка елемента:** Виконується `queue_.push(std::move(item))`. Якщо конструктор переміщення типу `T` викидає виняток, стан черги залишається валідним, а `lock` автоматично звільняє м'ютекс під час розгортання стека.
5. **Сигналізування:** Викликається `cv_not_empty_.notify_one()`, що розблоковує один із потоків-споживачів.

### Аналіз методу pop()

1. **Захоплення замка:** Потік ініціалізує `std::unique_lock<std::mutex> lock(mtx_)`.
2. **Перевірка предиката:** Викликається `cv_not_empty_.wait(lock, pred)`. Потік засинає, якщо черга порожня й не зупинена.
3. **Обробка порожнього стану при зупинці:** Якщо `queue_.empty() && stopped_`, повертається `std::nullopt`.
4. **Вилучення елемента:** Елемент переміщується з `queue_.front()`, після чого робиться `queue_.pop()`.
5. **Сигналізування:** Викликається `cv_not_full_.notify_one()`, пробуджуючи одного з заснулих виробників.

## 7. Детальний розбір C-реалізації кільцевого буфера

У реалізації мовою C низькорівнева структура `bounded_queue_t` повністю моделює поведінку об'єктно-орієнтованого класу C++:

* **Функція `queue_create(capacity)`:** Виділяє пам'ять під головну структуру через `malloc(sizeof(bounded_queue_t))` та під динамічний масив покажчиків `malloc(sizeof(void*) * capacity)`. У разі помилки виділення пам'яті коректно звільняє частково виділені ресурси та повертає `NULL`. Ініціалізує системні примітиви `pthread_mutex_init` та `pthread_cond_init`.
* **Функція `queue_push(q, data)`:** Захоплює м'ютекс `pthread_mutex_lock(&q->mutex)`. Очікує вивільнення місця у циклі `while (q->count == q->capacity && !q->stopped)` через `pthread_cond_wait(&q->cv_not_full, &q->mutex)`. Записує покажчик за індексом `q->tail`, оновлює індекс `q->tail = (q->tail + 1) % q->capacity` та збільшує лічильник `q->count++`. Сповіщає споживачів через `pthread_cond_signal(&q->cv_not_empty)` та звільняє м'ютекс.
* **Функція `queue_pop(q)`:** Захоплює м'ютекс, очікує появі елементів у циклі `while (q->count == 0 && !q->stopped)`. Якщо черга зупинена і порожня, повертає `NULL`. Зчитує покажчик `q->buffer[q->head]`, оновлює індекс `q->head = (q->head + 1) % q->capacity` та зменшує `q->count--`. Сповіщає виробників через `pthread_cond_signal(&q->cv_not_full)` та повертає дані.
* **Функція `queue_shutdown(q)`:** Встановлює `q->stopped = true` під захистом м'ютекса та розсилає масове сповіщення через `pthread_cond_broadcast()` для обох умовних змінних.
* **Функція `queue_destroy(q)`:** Забезпечує коректне зупинення та знищення системних примітивів `pthread_mutex_destroy` та `pthread_cond_destroy`, а також звільняє виділену динамічну пам'ять.

---

## 8. Динамічне тестування та відлагодження (Sanitizers & Valgrind)

Для забезпечення абсолютної надійності багаторазово потокового коду застосовують спеціалізовані інструменти автоматичного аналізу:

* **ThreadSanitizer (TSan):** Компіляція прапорцем `g++ -fsanitize=thread -g main.cpp` дозволяє виявити гонки даних (data races), недотримання порядків замків та некоректну роботу з атомарними прапорцями під час виконання тесту.
* **Valgrind / Helgrind:** Інструмент `valgrind --tool=helgrind ./my_app` виконує глибокий аналіз системних викликів pthreads, перевіряючи порядок захоплення м'ютексів та виявляючи потенційні взаємні блокування (deadlocks).
* **AddressSanitizer (ASan):** Прапорець `g++ -fsanitize=address -g` допомагає переконатися у відсутності витоків пам'яті (memory leaks) та виходів за межі буфера в C-реалізації кільцевого буфера.

---

## 9. Аналіз затримок та розподіл часу очікування (Latency Tail Analysis)

При оцінці продуктивності обмеженої черги у промислових серверах вимірюють не лише середню пропускну здатність, але й **хвостові затримки** (англ. *tail latency*: 99-й та 99.9-й перцентилі):

* **Середня затримка (p50):** У звичайному режимі перемикання контексту між потоком-виробником та потоком-споживачем за допомогою `futex` займає від 1.5 до 3 мікросекунд на сучасних процесорах Intel Xeon / AMD EPYC.
* **Хвостова затримка (p99.9):** При системному переповненні черги або високому навантаженні з боку операційної системи (наприклад, при зборі сміття в сусідніх процесах або оновленні кешів) затримка розблокування окремих заснулих потоків може зростати до 50–100 мікросекунд.
* **Регулювання місткості:** Збільшення місткості черги (наприклад, з 100 до 10000 елементів) поглинає короткочасні сплески трафіку, згладжуючи p99 затримку, але збільшує використання RAM і середній час перебування завдання в черзі.

---

## 10. Інтеграція у промислові асинхронні двигуни (Event Loop & Thread Pool)

У реальних мережевих серверах (наприклад, HTTP-серверах або серверах баз даних) обмежена черга використовується як міст між асинхронним циклами вводу-виводу (Event Loop на основі `epoll` / `io_uring`) та пулом обчислювальних потоків (Worker Thread Pool):

1. **Event Loop потік (Виробник):** Приймає нові мережеві з'єднання та пакети даних із сокетів, створює об'єкти завдань і викликає `queue.push(std::move(task))`. Якщо черга заповнена, потік вводу-виводу може скинути таймаут або повернути клієнту помилку `503 Service Unavailable` (backpressure mechanism).
2. **Worker потоки (Споживачі):** Циклічно виконують `queue.pop()`, отримують завдання та виконують ресурсоємні обчислення або звернення до СУБД.
3. **Graceful Shutdown:** При отриманні системного сигналу `SIGTERM` головний потік викликає `queue.shutdown()`. Усі робітники доопрацьовують поточні завдання і завершують роботу без втрати даних користувачів.

---

## 11. Математичні інваріанти структури BoundedQueue

Двостороння обмежена черга підпорядковується фундаментальним законм теорії масового обслуговування (Теорія черг, Закон Літтла):

1. **Базове обмеження довжини:** У будь-який момент часу `t` кількість елементів у черзі `N(t)` задовольняє інваріант `0 <= N(t) <= capacity`.
2. **Закон Літтла:** Середня кількість елементів у черзі `L` пов'язана з середньою інтенсивністю надходження запитів `lambda` та середнім часом очікування в черзі `W` співвідношенням `L = lambda * W`.
3. **Стабільність системи:** Якщо середня інтенсивність генерації виробників перевищує пропускну здатність споживачів (`lambda > mu`), черга швидко заповнюється до `capacity`, змушуючи виробників засинати на `cv_not_full_`. Це вирівнює ефективну швидкість генерації до швидкості споживання.

---

## 12. Гарантії безпеки винятків у конструкторах та операторах переміщення

При збереженні довільних складних типів користувацьких даних `T` черга забезпечує такі гарантії:

* **Помилка виділення пам'яті під час push():** Якщо контейнер `std::queue<T>` викидає виняток `std::bad_alloc` під час виклику `queue_.push()`, м'ютекс `mtx_` розблоковується деструктором `std::unique_lock`, а елемент `item` не втрачається.
* **Виняток у конструкторі переміщення `T(T&&)`:** Якщо конструктор переміщення типу `T` викидає виняток під час створення `item` у виклику `pop()`, елемент у голові черги `queue_.front()` залишається неушкодженим, а м'ютекс звільняється без порушення інваріантів черги.

---

## 13. Чек-лист готовності для промислової експлуатації

* [x] **Використання RAII-замків:** Усі критичні секції обгорнуті в `std::unique_lock<std::mutex>` або `std::lock_guard`.
* [x] **Предикатні цикли `while`:** Усі виклики `wait()` використовують лямбда-предикати або зовнішні цикли перевірки умови.
* [x] **Дві умовні змінні:** Черга використовує окремі `cv_not_empty_` та `cv_not_full_` для виключення плутанини сигналів.
* [x] **Підтримка Graceful Shutdown:** Реалізовано прапорець `stopped_` та масове сповіщення `notify_all()` при завершенні.
* [x] **Заборона копіювання:** Оператор присвоєння та конструктор копіювання видалені через `= delete`.

---

## 14. Порівняння з іншими парадигмами (Message Passing vs Work Stealing)

Окрім класичної обмеженої черги на основі спільної пам'яті та м'ютекса, у сучасних паралельних архітектурах використовуються інші підходи до передачі завдань:

1. **Модель акторів (Actor Model / CSP):** Потоки спілкуються виключно передачею повідомлень через асинхронні канали без спільного регульованого стану (Erlang, Go channels). Це виключає прямі замки м'ютексів, але вимагає внутрішньої побудови подібних черг на рівні рантайму мови.
2. **Крадіжка роботи (Work Stealing Queue):** Кожен потік-робітник має власну локальну двосторонню чергу (deque). Виробник додає завдання у власний дек, а безробітні потоки "крадуть" завдання з протилежного кінця деків інших потоків (Intel TBB, C++20 executors). Це знижує контенцію м'ютекса порівняно з єдиною спільною обмеженою чергою.

---

## 15. Практичний висновок та рекомендації щодо впровадження

Побудована в цьому практичному матеріалі обмежена потокобезпечна черга є стандартним високонадійним рішенням для організації зв'язку між потоками виробників та споживачів у промислових C++ проєктах. 

Вона поєднує повну гарантію відсутності втрат сигналів (lost wakeups), захист від фіктивних пробуджень (spurious wakeups), автоматичне звільнення замків при винятках через RAII та чистий механізм завершення (graceful shutdown). 

Завдяки розділенню на дві умовні змінні `cv_not_empty_` та `cv_not_full_` забезпечується точне сигналізування потрібних груп заснулих потоків без створення марного "шторму пробудження" (thundering herd problem). Для переважної більшості реальних асинхронних сервісів та обчислювальних систем таке рішення забезпечує ідеальний баланс між продуктивністю, безпекою пам'яті та читабельністю коду. Ретельно підібрана місткість черги та коректний виклик `shutdown()` забезпечують високу надійність роботи додатку навіть під час критичних системних збоїв чи раптових сплесків мережевого навантаження.
