# 📋 Інтерфейс та API: std::condition_variable та std::condition_variable_any

Модуль синхронізації мови C++ постачає засоби очікування подій у заголовку `<condition_variable>`. Центральними елементами цього заголовка є два класи: `std::condition_variable` та `std::condition_variable_any`, а також допоміжний перелічуваний тип `std::cv_status`. Ця довідка містить розгорнутий опис контракту методів, вимог до типів замків, гарантій безпеки винятків, умов невизначеної поведінки та конструкцій кооперативного скасування C++20.

## 1. Клас std::condition_variable

Клас `std::condition_variable` є спеціалізованим примітивом синхронізації, оптимізованим для використання виключно з м'ютексом типу `std::mutex` через обгортку `std::unique_lock<std::mutex>`. Об'єкти цього класу не є копійованими та не є переміщуваними.

### Конструктори, копіювання та деструктор

```cpp
condition_variable();                                           // (1) Основний конструктор
condition_variable(const condition_variable&) = delete;         // (2) Заборона копіювання
condition_variable& operator=(const condition_variable&) = delete; // (3) Заборона присвоєння
~condition_variable();                                          // (4) Деструктор
```

#### Детальний аналіз конструктора по замовчуванню (1)

* **Функціональне призначення:** Створює новий екземпляр умовної змінної та виділяє необхідні внутрішні ресурси операційної системи.
* **Обробка системних помилок:** Якщо операційній системі не вдається створити примітив синхронізації через брак внутрішніх ресурсів пам'яті чи перевищення ліміту дескрипторів, конструктор викидає виняток `std::system_error` із відповідним системним кодом помилки (`std::errc::resource_unavailable_try_again`).
* **Безпека потоків при ініціалізації:** Конструктор повинен завершити виконання до того, як будь-який інший потік звернеться до об'єкта умовної змінної.

#### Заборона семантики копіювання та присвоєння (2, 3)

* **Причина обмеження:** Семантика умовної змінної тісно прив'язана до її конкретного фізичного місця розташування у системній пам'яті, оскільки нативні системні виклики ядра (наприклад, `sys_futex` у Linux або `CONDITION_VARIABLE` у Windows API) працюють безпосередньо з її покажчиком. Копіювання об'єкта зламало б внутрішні черги очікування.

#### Деструктор та інваріанти знищення (4)

* **Функціональне призначення:** Знищує об'єкт умовної змінної та звільняє виділені ресурси операційної системи.
* **Строга предумова:** Жоден потік виконання не повинен перебувати в стані сну на цій умовній змінній у момент виклику її деструктора.
* **Наслідки порушення предумови:** Якщо деструктор викликається в момент, коли на умовній змінній чекає хоча б один потік, виникає незворотна невизначена поведінка (Undefined Behavior). Розробник зобов'язаний гарантувати, що всі потоки вже розблоковані й завершили виклики `wait()`.

### Нативний дескриптор: native_handle()

```cpp
using native_handle_type = /* platform-defined */;
native_handle_type native_handle();
```

* **Опис:** Повертає платформно-залежний покажчик або дескриптор на нативний об'єкт умовної змінної операційної системи.
* **Тип повертаваного значення:** На POSIX-системах (Linux, macOS, FreeBSD) повертає покажчик `pthread_cond_t*`. На Windows повертає `PCONDITION_VARIABLE` (покажчик на структуру Windows Condition Variable).
* **Сфера застосування:** Використовується при написанні низькорівневого системного коду для налаштування специфічних параметрів системного примітива (наприклад, задання годинника `CLOCK_MONOTONIC` через `pthread_condattr_setclock` у POSIX).
* **Застереження щодо переносності:** Виклики `native_handle()` роблять код непереносним між різними ОС і повинні обгортатися у відповідні директиви препроцесора `#ifdef`.

### Методи сповіщення: notify_one() та notify_all()

Методи сповіщення використовуються потоками-виробниками для розблокування потоків-споживачів, що перебувають у черзі очікування.

```cpp
void notify_one() noexcept;
void notify_all() noexcept;
```

#### Метод notify_one()

* **Функціональне призначення:** Розблоковує один із потоків, які наразі перебувають у черзі очікування на цій умовній змінній.
* **Алгоритм вибору потоку:** Якщо у черзі чекають декілька потоків, конкретний потік обирається диспетчером планувальника операційної системи. Жодних гарантій дотримання порядку FIFO (First-In, First-Out) стандарт C++ не дає.
* **Поведінка при порожній черзі:** Якщо жодного потоку немає в черзі очікування, виклик `notify_one()` не створює жодного побічного ефекту, а сигнал сповіщення безслідно втрачається.
* **Складність виконання:** `O(1)` відносно кількості потоків у черзі.
* **Специфікація винятків:** Позначено як `noexcept` — не викидає винятків за жодних умов.

#### Метод notify_all()

* **Функціональне призначення:** Одночасно розблоковує абсолютно всі потоки, які наразі перебувають у черзі очікування на цій умовній змінній.
* **Сфера застосування:** Використовується для масових сигналів (наприклад, сигнал зупинки всієї системи `shutdown` або досягнення барьєру синхронізації).
* **Складність виконання:** `O(N)`, де `N` — кількість потоків у черзі очікування.
* **Специфікація винятків:** `noexcept` — за жодних обставин не викидає винятків.

### Методи очікування: wait(), wait_for(), wait_until()

Усі методи очікування приймають посилання на захоплений `std::unique_lock<std::mutex>&`. Викликаючий потік повинен обов'язково володіти м'ютексом у момент виклику цих методів, інакше виникає невизначена поведінка (UB).

```cpp
// --- Базове неограничене очікування ---
void wait(std::unique_lock<std::mutex>& lock); // (1)

template<class Predicate>
void wait(std::unique_lock<std::mutex>& lock, Predicate pred); // (2)
```

#### Метод wait() без предиката (1)

* **Атомарність переходу:** Атомарно звільняє захоплений м'ютекс `lock` та переводить потік у сон. При пробудженні метод повторно захоплює `lock` перед поверненням керування.
* **Предумова:** `lock.owns_lock() == true`. Об'єкт `lock` повинен обов'язково утримувати замок м'ютекса.

#### Метод wait() з предикатом (2)

* **Функціональне призначення:** Приймає функціональний об'єкт або лямбда-вираз `pred`, який повертає `bool`. Еквівалентний виконанню циклу:
  ```cpp
  while (!pred()) {
      wait(lock);
  }
  ```
* **Захист від фиктивних пробуджень:** Гарантує, що потік відновить виконання лише тоді, коли предикат `pred()` стане істинним.

---

#### Очікування з відносним таймаутом: wait_for()

Метод `wait_for()` зупиняє виконання потоку на заданий відносний проміжок часу або до надходження сповіщення.

```cpp
template<class Rep, class Period>
std::cv_status wait_for(
    std::unique_lock<std::mutex>& lock,
    const std::chrono::duration<Rep, Period>& rel_time
); // (1)

template<class Rep, class Period, class Predicate>
bool wait_for(
    std::unique_lock<std::mutex>& lock,
    const std::chrono::duration<Rep, Period>& rel_time,
    Predicate pred
); // (2)
```

* **Деталі реалізації (1):** Внутрішньо конвертує відносний інтервал `rel_time` в абсолютну часову точку через `std::chrono::steady_clock::now() + rel_time` і викликає `wait_until()`.
* **Перелічуваний тип `std::cv_status`:**
  * `std::cv_status::no_timeout` — потік успішно розблоковано до закінчення тривалості внаслідок виклику `notify()`.
  * `std::cv_status::timeout` — заданий часовий інтервал вичерпано до отримання сповіщення.
* **Перевантаження з предикатом (2):** Повертає `true`, якщо предикат `pred()` став істинним до закінчення тривалості, і `false` при спливі таймауту.

---

#### Очікування до абсолютної часової точки: wait_until()

Метод `wait_until()` зупиняє виконання потоку до досягнення конкретної часової точки.

```cpp
template<class Clock, class Duration>
std::cv_status wait_until(
    std::unique_lock<std::mutex>& lock,
    const std::chrono::time_point<Clock, Duration>& abs_time
); // (1)

template<class Clock, class Duration, class Predicate>
bool wait_until(
    std::unique_lock<std::mutex>& lock,
    const std::chrono::time_point<Clock, Duration>& abs_time,
    Predicate pred
); // (2)
```

* **Робота з годинниками:** Застосування `std::chrono::steady_clock` гарантує стійкість до зміни системного часу.
* **Перевага над wait_for:** Рекомендовано застосовувати саме `wait_until()` у циклах повторної перевірки, оскільки цей метод не накопичує похибку часу при повторних фіктивних засинаннях.

## 2. Клас std::condition_variable_any

Клас `std::condition_variable_any` — це узагальнена версія умовної змінної, яка здатна працювати з довільними типами замків, що відповідають вимогам концепту `BasicLockable` (мають методи `.lock()` та `.unlock()`).

### Контракт концепту BasicLockable

Тип замка `Lock`, що передається у `std::condition_variable_any`, повинен надавати такі методи:
* `void lock()` — блокує замок.
* `void unlock()` — розблоковує замок.

Завдяки цьому `std::condition_variable_any` може використовуватися з `std::shared_lock<std::shared_mutex>`, користувацькими спінлоками або рекурсивними м'ютексами.

---

### Конструкції C++20 з кооперативним скасуванням (std::stop_token)

Починаючи зі стандарту C++20, клас `std::condition_variable_any` отримав розширені методи очікування з об'єктом `std::stop_token`.

```cpp
template<class Lock, class Predicate>
bool wait(
    Lock& lock,
    std::stop_token stoken,
    Predicate pred
); // (1) C++20

template<class Lock, class Rep, class Period, class Predicate>
bool wait_for(
    Lock& lock,
    std::stop_token stoken,
    const std::chrono::duration<Rep, Period>& rel_time,
    Predicate pred
); // (2) C++20

template<class Lock, class Clock, class Duration, class Predicate>
bool wait_until(
    Lock& lock,
    std::stop_token stoken,
    const std::chrono::time_point<Clock, Duration>& abs_time,
    Predicate pred
); // (3) C++20
```

#### Механізм роботи stop_token

1. **Реєстрація зворотного виклику:** Під час входу в `wait()` метод створює внутрішній об'єкт `std::stop_callback`, прив'язаний до `stoken`.
2. **Реакція на сигнал скасування:** Якщо інший потік викликає `request_stop()` на відповідному `std::stop_source`, функція зворотного виклику негайно розблоковує умовну змінну.
3. **Повертане значення:** Метод повертає поточне значення предиката `pred()`. Якщо очікування перервано скасуванням, а предикат хибний, повертається `false`.

## 3. Перелічуваний тип std::cv_status

Тип `std::cv_status` є строго типізованим переліченням (англ. *scoped enum*), яке описує результат виконання методів очікування з таймаутами.

```cpp
enum class cv_status {
    no_timeout, // Потік прокинувся через сигнал сповіщення (notify)
    timeout     // Часовий інтервал вичерпано до отримання сповіщення
};
```

### Значення елементів

1. `std::cv_status::no_timeout` — означає, що при set-up часовому інтервалі відбулося сповіщення від іншого потоку через `notify_one()` або `notify_all()`, або мало місце фіктивне пробудження.
2. `std::cv_status::timeout` — означає, що відведений час очікування повністю сплив, а сповіщення так і не надійшло.

## 5. Гарантії безпеки винятків та крайові випадки

### 1. Поведінка при винятках у предикаті

Якщо переданий функціональний об'єкт `pred()` викидає виняток усередині методу `wait()`, умовна змінна забезпечує **сувору гарантію безпеки винятків**:
* Замок `lock` гарантовано **повторно захоплюється** перед тим, як виняток вилетить за межі виклику `wait()`.
* Цілісність замка та м'ютекса не порушується, що запобігає витоку ресурсів.

### 2. Системні помилки

Якщо внутрішній системний виклик операційної системи (наприклад, `pthread_cond_wait` у Unix або `SleepConditionVariableCS` у Windows) повертає код помилки, умовна змінна викидає виняток `std::system_error` із відповідною деталізацією.

### 3. Автоматичне звільнення через RAII

Використання `std::unique_lock` у поєднанні з умовною змінною забезпечує повний захист від взаємних блокувань: якщо під час роботи критичної секції виникає виняток, деструктор `std::unique_lock` автоматично звільняє м'ютекс під час розгортання стека (англ. *stack unwinding*).

## 6. Детальний аналіз специфікації потокобезпеки (Thread Safety Matrix)

Для безпечного використання `std::condition_variable` у багаторазово потокових середовищах розробник повинен чітко розуміти гарантії потокобезпеки кожного методу:

* **Конкурентні виклики notify_one() / notify_all():** Є повністю потокобезпечними. Безліч потоків-виробників можуть одночасно викликати сповіщення на одному об'єкті умовної змінної без додаткової зовнішньої синхронізації.
* **Конкурентні виклики wait() / wait_for() / wait_until():** Є повністю потокобезпечними за умови, що всі потоки-споживачі використовують **один і той самий м'ютекс**. Використання різних м'ютексів з однією умовною змінною є невизначеною поведінкою.
* **Деструктор ~condition_variable():** Не є потокобезпечним відносно інших методів. Жоден потік не повинен викликати `wait()` або `notify()` під час виконання деструктора.

---

## 7. Детальний довідник кодових винятків std::system_error

Методи умовної змінної можуть викидати виняток `std::system_error` у разі виникнення збоїв системного рівня в операційній системі:

1. `std::errc::resource_unavailable_try_again` — операційна система не здатна виділити додаткові ресурси пам'яті чи системні об'єкти synchronization events.
2. `std::errc::operation_not_permitted` — виникає, якщо потік намагається виконати чекання без належного володіння замком м'ютекса (`lock.owns_lock() == false`).
3. `std::errc::device_or_resource_busy` — системний код помилки, який повертається при спробі знищення умовної змінної, яка наразі перебуває у заблокованому стані під очікуванням активних потоків.

---

## 8. Докладний довідник засобів кооперативного скасування C++20

Стандарт C++20 розширив можливості `std::condition_variable_any` через інтеграцію з токенами скасування:

* `std::stop_token` — передається в метод `wait(lock, stoken, pred)`. Дозволяє потокові реагувати на зовнішній сигнал `request_stop()`.
* `std::stop_callback` — внутрішній об'єкт, який автоматично створюється всередині `wait()`. При виклику `request_stop()` на джерелі скасування `std::stop_source` функція зворотного виклику будить умовну змінну.
* **Повертане значення в C++20:** Метод `wait(lock, stoken, pred)` повертає `bool`. Якщо очікування завершилося внаслідок скасування, а предикат `pred()` хибний, повертається `false`. Якщо предикат стає істинним, повертається `true`.

## 9. Матриця гарантій безпеки винятків для всіх методів

| Метод | Гарантія винятків | Умови виникнення винятку |
| :--- | :--- | :--- |
| `condition_variable()` | Basic guarantee | Брак ресурсів ОС (`std::system_error`) |
| `~condition_variable()` | `noexcept` | Ніколи (UB якщо є заснулі потоки) |
| `notify_one()` | `noexcept` | Ніколи не викидає винятків |
| `notify_all()` | `noexcept` | Ніколи не викидає винятків |
| `wait(lock)` | Basic guarantee | Системна помилка ОС |
| `wait(lock, pred)` | Strong guarantee | Якщо `pred()` викидає виняток, м'ютекс повторно захоплюється |
| `wait_for(lock, rel_time)` | Basic guarantee | Системна помилка або помилка таймера |
| `wait_until(lock, abs_time)` | Basic guarantee | Системна помилка або помилка таймера |

## 10. Детальний аналіз конструктивних вимог до вирівнювання у пам'яті

Об'єкти класу `std::condition_variable` вимагають строгого вирівнювання в пам'яті (англ. *alignment requirements*), що визначається системними вимогами процесора та ядерних примітивів:

* **Вирівнювання футекса у Linux:** Системний виклик `sys_futex` оперує 32-бітними цілочисельними атомарними адресами, вирівняними строго по 4-байтній межі в пам'яті (`alignof(int32_t)`). Спроба передати невирівняну адресу призводить до помилки ядра `EFAULT` або аварійного завершення програми через `SIGBUS`.
* **Розміщення у структурі даних:** При проектуванні системних структур даних об'єкти `std::condition_variable` рекомендується розміщувати на початку структури або застосовувати специфікатор `alignas(64)` для запобігання перетину межі кеш-лінії.
* **Заборона розміщення у напіввідкритих масивах:** Створення динамічних масивів умовних змінних без належного вирівнювання через `malloc()` або `realloc()` заборонено. Рекомендується використовувати стандартний контейнер `std::vector<std::condition_variable>` або `std::unique_ptr`.

## 11. Внутрішня метапрограмувальна реалізація std::condition_variable_any

Для роботи з довільними типами замків клас `std::condition_variable_any` створює допоміжну внутрішню обгортку:

1. **Типовидалення (Type Erasure):** Використовує внутрішній `std::shared_ptr<std::mutex>`, який гарантує синхронізацію між викликами `.lock()` та `.unlock()` користувацького замка та нативною умовною змінною.
2. **Атомарний перехід для користувацьких замків:** Під час входу у `wait()` створюється тимчасовий внутрішній м'ютекс. Внутрішній замок захоплюється до виклику `unlock()` користувацького замка, що гарантує відсутність гонки між вивільненням користувацького замка та реєстрацією потоку в черзі сну.
3. **Захист від винятків у користувацькому unlock():** Якщо виклик `lock.unlock()` користувацького замка викидає виняток, внутрішній м'ютекс автоматично звільняється, запобігаючи незворотному взаємному блокуванню.

## 12. Специфікація передумов та післяумов усіх методів

| Метод | Передумови (Preconditions) | Післяумови (Postconditions) |
| :--- | :--- | :--- |
| `wait(lock)` | `lock.owns_lock() == true` | `lock.owns_lock() == true` |
| `wait(lock, pred)` | `lock.owns_lock() == true` | `lock.owns_lock() == true && pred() == true` |
| `wait_for(lock, rel_time)` | `lock.owns_lock() == true` | `lock.owns_lock() == true` |
| `wait_until(lock, abs_time)`| `lock.owns_lock() == true` | `lock.owns_lock() == true` |
| `notify_one()` | Немає (може викликатися з будь-якого потоку) | Один потік розблокований (або нічого якщо черга порожня) |
| `notify_all()` | Немає (може викликатися з будь-якого потоку) | Усі заснулі потоки розблоковані |

## 13. Взаємодія з системними утилітами динамічного аналізу

Під час використання умовних змінних у промислових C++ проєктах застосовуються інструменти динамічного аналізу коду:

* **ThreadSanitizer (TSan):** Розпізнає атомарні операції `notify_one()` та `wait()` як точки синхронізації (англ. *synchronization points*). TSan перевіряє, що всі модифікації захищеного стану виконані перед викликом `notify()`, запобігаючи виникненню невидимих race conditions.
* **Valgrind DRD / Helgrind:** Інструмент DRD (Data Race Detector) контролює правильність передачі м'ютексів у `pthread_cond_wait()`. Якщо потік намагається передати м'ютекс, захоплений в іншому потоці, Helgrind миттєво генерує попередження про порушення контракту впорядкування.

## 14. Підсумкові правила проєктування інтерфейсів синхронізації

1. **Завжди перевіряй предикат у циклі:** Ніколи не викликай `wait()` без лямбди або циклу `while (!pred())`.
2. **Використовуй std::unique_lock:** Умовна змінна вимагає обгортки `std::unique_lock`, яка підтримує тимчасове розблокування.
3. **Обирай правильний клас:** Для стандартного м'ютекса використовуй `std::condition_variable`. Узагальнену версію `std::condition_variable_any` застосовуй лише при потребі роботи з `shared_lock` або `stop_token`.

Завдяки строго формалізованому інтерфейсу та суворим гарантіям безпеки винятків, примітиви `std::condition_variable` та `std::condition_variable_any` слугують надійним фундаментом для побудови складних асинхронних архітектур.
