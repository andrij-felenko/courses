# 📜 Від статті Александреску до P0052: історія охоронців області

Охоронці області видимості з'явилися як відповідь на кризу складності: написання винятково безпечного коду в C++ вимагало надмірної кількості дубльованих блоків очищення або заплутаних переходів, що спонукало розробників шукати спосіб перетворити деструктор на універсальний механізм відкату.

## Виняткові гарантії та глухий кут ручного відкату

Наприкінці 1990-х років комітет стандартизації C++ та спільнота розробників активно осмислювали концепцію винятків. Дейв Абрагамс (Dave Abrahams) сформулював три рівні виняткових гарантій (англ. *exception safety guarantees*), які згодом стали фундаментальним стандартом проектування надійних систем:

1. **Базова гарантія** (англ. *basic guarantee*): у разі виникнення винятку ресурси не витікають, а всі об'єкти програми залишаються у внутрішньо узгодженому (хоч і, можливо, зміненому) стані.
2. **Сильна гарантія** (англ. *strong guarantee*), або транзакційна поведінка: операція або виконується повністю й успішно, або, у разі будь-якої помилки, стан системи повертається точно до моменту перед початком виклику («все або нічого»).
3. **Гарантія відсутності винятків** (англ. *no-throw guarantee*): операція гарантовано завершується успішно й ніколи не викидає винятків назовні (зокрема, це критично для деструкторів і функцій вивільнення ресурсів).

Хоча ідіома RAII (англ. *Resource Acquisition Is Initialization*, «захоплення ресурсу є ініціалізація») ідеально вирішувала проблему витоку окремих ресурсів за базової гарантії (пам'ять звільняється через `std::auto_ptr` чи власні класи-обгортки), забезпечення **сильної гарантії** у багатоетапних операціях виявилося справжнім випробуванням.

Якщо операція складалася з кількох кроків — наприклад, резервування коштів на банківському рахунку, створення запису в журналі транзакцій та надсилання мережевого сповіщення, — збій на третьому кроці вимагав явного відкату перших двох. У чистому C++98 це призводило до громіздких конструкцій:

```cpp
void process_transaction(Account& acc, double amount, Logger& log, Network& net) {
    acc.reserve(amount);
    try {
        log.record_intent(acc.id(), amount);
        try {
            net.notify_peer(acc.id(), amount);
        } catch (...) {
            log.cancel_intent(acc.id(), amount);
            throw;
        }
    } catch (...) {
        acc.cancel_reservation(amount);
        throw;
    }
}
```

Кожен новий крок додавав новий рівень вкладеності блоків `try-catch`. Код ставав пірамідальним, логіка очищення розпорошувалася по різних гілках обробки, а випадковий пропуск одного з рівнів перехоплення призводив до тихого спотворення стану системи.

Альтернативний підхід у стилі мови C з єдиною точкою виходу та мітками `goto` не працював із винятками, оскільки неперехоплений виняток оминав явні переходи `goto error_step2`. Створення ж окремого RAII-класу для кожної можливої операції відкату (наприклад, `AccountReservationRollbackGuard`, `LogIntentCancelGuard`) спричиняло лавину одноразового допоміжного коду. Розробник був змушений писати десятки шаблонних класів із конструкторами, полями для збереження аргументів та викликами методів відкату у деструкторах, що розривало безперервність алгоритму.

## 2000 рік: стаття Александреску та Мерджиняна

У грудні 2000 року в авторитетному виданні *C/C++ Users Journal* Андрей Александреску (Andrei Alexandrescu) та Петру Мерджинян (Petru Marginean) опублікували статтю під назвою *«Generic<Programming>: Change the Way You Write Exception-Safe Code — Forever»* («Змініть спосіб написання винятково безпечного коду — назавжди»).

Автори запропонували революційну для свого часу ідею: створити єдиний, гранично узагальнений шаблонний клас `ScopeGuard`, здатний зв'язати виклик будь-якої функції, методу чи функціонального об'єкта з деструктором стекового об'єкта. Ключовим елементом концепції стала можливість скасування відкату через виклик методу `dismiss()` у разі успішного завершення операції.

Оскільки в C++98 ще не існувало лямбда-виразів, реалізація вимагала витонченого шаблонного метапрограмування. Автори побудували ієрархію класів:
- базовий нешаблонний інтерфейс `ScopeGuardImplBase`, що зберігав булевий прапорець `dismissed_` і надавав метод `dismiss()`;
- шаблонні похідні класи `ScopeGuardImpl0`, `ScopeGuardImpl1<F, P1>`, `ScopeGuardImpl2<F, P1, P2>`, які зберігали вказівник на функцію чи метод та значення переданих аргументів;
- перевантажені фабричні функції `MakeGuard` та `MakeObjGuard`, які виводили типи аргументів шаблону з параметрів виклику, позбавляючи розробника необхідності писати довгі параметризації вручну.

```cpp
// Концептуальний вигляд використання в бібліотеці Loki (2000–2001 рр.)
void process_transaction(Account& acc, double amount, Logger& log, Network& net) {
    acc.reserve(amount);
    ScopeGuard guard_acc = MakeObjGuard(acc, &Account::cancel_reservation, amount);

    log.record_intent(acc.id(), amount);
    ScopeGuard guard_log = MakeObjGuard(log, &Logger::cancel_intent, acc.id(), amount);

    net.notify_peer(acc.id(), amount);

    // Якщо дійшли сюди — все успішно, скасовуємо відкат:
    guard_log.dismiss();
    guard_acc.dismiss();
}
```

Щоб дозволити прив'язувати тимчасовий об'єкт `ScopeGuardImpl` до константного посилання `const ScopeGuard&` (що за правилами C++ подовжує час життя тимчасового об'єкта до кінця поточної області), Александреску застосував трюк із мутабельним прапорцем `mutable bool dismissed_`.

Для випадків, коли назва змінної охоронця не мала значення і дія мала виконуватися безумовно при будь-якому виході, автори створили макрос `ON_BLOCK_EXIT`, який генерував унікальне ім'я змінної за допомогою макросного склеювання та константи номера рядка `__LINE__`.

Це рішення з бібліотеки Loki стало сенсацією: код відкату тепер писався безпосередньо поруч із дією, яка вимагала компенсації, а виконання відкату гарантувалося деструктором автоматичного об'єкта під час розгортання стека.

## Мова D: охоронці як першокласні конструкції мови

Андрей Александреску, бувши одним із провідних архітекторів мови програмування D (разом із її творцем Волтером Брайтом, Walter Bright), переніс і розвинув цю концепцію в дизайні D 2.0 (близько 2006–2007 років).

Усвідомивши, наскільки часто розробники потребують різних режимів спрацювання охоронця, автори мови D відмовилися від бібліотечних обгорток та макросів на користь трьох повноцінних інструкцій рівня синтаксису:
- `scope(exit)` — виконати блок виразів завжди при виході з поточної області (як при нормальному поверненні, так і при розгортанні винятком);
- `scope(failure)` — виконати блок виразів лише тоді, коли область залишається через викинутий виняток;
- `scope(success)` — виконати блок виразів лише у разі нормального (безаварійного) виходу.

Синтаксис мови D вражав своєю чистотою:

```d
// Код на мові D
void processTransaction(ref Account acc, double amount) {
    acc.reserve(amount);
    scope(failure) acc.cancelReservation(amount); // виконається тільки при збої

    log.recordIntent(acc.id, amount);
    scope(failure) log.cancelIntent(acc.id, amount);

    net.notifyPeer(acc.id, amount);
}
```

Компілятор мови D самостійно транслював ці інструкції у внутрішнє синтаксичне дерево з блоками `try ... finally` або перевірками стану винятків. У мові D відпала необхідність вручну викликати `dismiss()` наприкінці блоку: компілятор сам аналізував спосіб виходу з області видимості. Цей підхід став еталоном ергономіки обробки винятків і сформував чітке бачення того, як має виглядати ідеальне керування життєвим циклом у C++.

## Епоха Boost: макросна метапрограма Boost.ScopeExit

У 2007 році Олександр Насонов створив бібліотеку `Boost.ScopeExit`, яка згодом увійшла до офіційного дистрибутива Boost (версія 1.38). Її метою було надати C++-розробникам синтаксис, максимально наближений до `scope(exit)` з мови D, не виходячи за межі тодішнього стандарту C++98/03.

Оскільки мова все ще не підтримувала лямбди та автоматичне виведення типів `auto`, бібліотека використовувала складну препроцесорну метапрограму на базі `Boost.Preprocessor` та механізмів виведення типу виразу `typeof` (`Boost.Typeof`):

```cpp
// Використання Boost.ScopeExit у C++03
void update_data(Database& db, Record& r) {
    db.begin_transaction();
    bool commit = false;

    BOOST_SCOPE_EXIT((&db)(&commit)) {
        if (!commit) {
            db.rollback();
        }
    } BOOST_SCOPE_EXIT_END

    db.modify(r);
    commit = true; // фіксуємо зміни
}
```

Макрос `BOOST_SCOPE_EXIT` оголошував локальний клас усередині функції, копіював або захоплював за посиланням вказані змінні за допомогою послідовностей препроцесора та інстанціював анонімний стековий екземпляр. Попри важкий синтаксис і помітне навантаження на компілятор під час розбору шаблонів, `Boost.ScopeExit` стала фактичним стандартом у великих промислових проектах, де вимагалася сувора виняткова безпека.

## Революція C++11: лямбди витісняють макроси

Прийняття стандарту C++11 докорінно змінило можливості мови. Завдяки впровадженню легких анонімних замикань (лямбда-виразів), синтаксису захоплення контексту `[&]` або `[=]`, а також семантики переміщення (`std::move`), створення універсального охоронця області перестало потребувати макросних генераторів.

Будь-який розробник міг створити компактний шаблонний клас:

```cpp
template <typename F>
class CustomScopeGuard {
    F fn_;
    bool active_{true};
public:
    explicit CustomScopeGuard(F fn) : fn_(std::move(fn)) {}
    ~CustomScopeGuard() { if (active_) fn_(); }
    void dismiss() noexcept { active_ = false; }
    CustomScopeGuard(CustomScopeGuard&& o) noexcept 
        : fn_(std::move(o.fn_)), active_(std::exchange(o.active_, false)) {}
};
```

У цей же період у провідних промислових бібліотеках виникли власні оптимізовані інструменти:
- `folly::makeGuard`, макроси `SCOPE_EXIT`, `SCOPE_FAIL`, `SCOPE_SUCCESS` у бібліотеці Folly від Meta;
- `absl::Cleanup` у відкритій бібліотеці Abseil від Google;
- `gsl::finally` у складі Guidelines Support Library (GSL), створеної Б'ярном Страуструпом та Гербом Саттером для супроводу C++ Core Guidelines.

## Довгий шлях до стандарту: пропозиція P0052

Попри повсюдне використання патерна, стандартній бібліотеці бракувало уніфікованих класів для охоронців області.

У 2014–2015 роках Петер Зоммерлад (Peter Sommerlad) та Ендрю Л. Сандовал (Andrew L. Sandoval) представили комітету ISO C++ пропозицію, яка згодом кристалізувалася в документ **P0052** (*Generic Scope Guard and RAII Wrapper for the Standard Library*).

Автори запропонували додати до стандарту три класи:
1. `std::scope_exit` — базовий безумовний охоронець.
2. `std::scope_fail` — охоронець, що спрацьовує виключно у разі аварійного виходу з області через виняток.
3. `std::scope_success` — охоронець, що виконує дію лише за умови успішного завершення блоку.

Ключовою технічною перешкодою для надійної роботи `scope_fail` та `scope_success` у ранніх стандартах була недосконалість функції `std::uncaught_exception()` (в однині), успадкованої ще з C++98. Ця функція повертала простий булевий прапорець: чи є взагалі хоч один активний виняток у поточному потоці.

Цей прапорець виявився концептуально хибним у разі вкладених винятків. Якщо деструктор якогось об'єкта виконувався під час розгортання стека й усередині викликав функцію, яка створювала власний внутрішній блок `try-catch`, то функція `std::uncaught_exception()` продовжувала повертати `true` навіть тоді, коли вкладена функція успішно завершувала свій внутрішній блок. Через це умовні охоронці помилково вважали успішні локальні операції аварійними й виконували некоректний відкат.

Прорив стався в C++17 із прийняттям пропозиції Герба Саттера N4152, яка замінила булевий прапорець цілочисельною функцією `std::uncaught_exceptions()` (у множині), що повертає точну кількість активних винятків у потоці. Це дозволило охоронцю зберігати лічильник винятків у момент свого конструювання й порівнювати його в деструкторі: якщо на виході кількість винятків строго більша за початкову, отже, область залишається через новий виняток.

Специфікація P0052 (з фінальною ревізією P0052R10) була успішно прийнята до технічної специфікації *C++ Extensions for Library Fundamentals, Version 3 (Library Fundamentals TS v3)*. Вона стала логічним завершенням двадцятирічної еволюції: від експериментальних макросів Александреску у 2000 році до стандартизованого, високоефективного інструменту сучасного C++.
