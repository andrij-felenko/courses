# 📋 Довідник правил виведення типів та неявних трансформацій

Цей довідник містить систематизовані таблиці, формальні алгоритми та повний опис правил виведення аргументів шаблонів функцій і класів (Template Argument Deduction, TAD) відповідно до стандарту ISO/IEC 14882 (C++11, C++14, C++17 та C++20). Довідник призначений для швидкого пошуку точних правил трансформації типів, згортання посилань, списку недедукованих контекстів та синтаксису користувацьких правил виведення (Deduction Guides).

## 1. Загальний алгоритм зіставлення форми P та аргументу A

Виведення аргументів шаблону базується на формальному зіставленні пари:
- `P` (Parameter Template) — тип формального параметра, що містить один або декілька параметрів шаблону;
- `A` (Argument Type) — точний тип фактичного аргументу, переданого в точці виклику або ініціалізації.

Алгоритм виконується незалежно для кожного аргументу виклику. Якщо шаблон має декілька параметрів, результати виведення для одного й того самого параметра-типу `T` повинні точно збігатися (після зняття посилань у відповідних контекстах), інакше компілятор фіксує помилку дедукції `conflicting deduced types for parameter T`.

```text
Виклик: f(arg1, arg2, ..., argN)
  ├─ Для кожної пари (P_i, A_i):
  │    ├─ Перевірити, чи P_i містить дедукований параметр шаблону
  │    ├─ Якщо P_i — недедукований контекст ⇒ пропустити виведення для цього аргументу
  │    ├─ Виконати трансформацію типу A_i (зняття посилань / decay відповідно до форми P_i)
  │    └─ Зіставити структуру P_i з A_i та отримати зв'язування T = DeductedType_i
  ├─ Об'єднати результати для всіх аргументів:
  │    └─ Якщо знайдено різні типи для одного T (наприклад, int та double) ⇒ ПОМИЛКА ДЕДУКЦІЇ
  └─ Підставити виведені типи в сигнатуру та перевірити обмеження (Concepts / SFINAE)
```

### Формальні етапи зіставлення згідно зі стандартом ISO C++

Процес виведення аргументів шаблону функції регулюється розділом §13.10.2 [temp.deduct] стандарту C++ і складається з трьох послідовних кроків:

1. **Нормалізація типів аргументів виклику (Argument Adjustment).** Якщо тип аргументу `A` є посиланням (наприклад, `const int&`), посилання відкидається перед початком порівняння. Якщо формальний параметр `P` оголошений не як посилання, масиви розпадаються у вказівники на перший елемент, а типи функцій — у вказівники на функції (Type Decay).
2. **Структурне вирівнювання (Structural Pattern Matching).** Компілятор рекурсивно порівнює вузли синтаксичного дерева типу `P` та типу `A`. Наприклад, якщо `P` має форму `std::vector<T*>`, а аргумент `A` має тип `std::vector<int*>`, компілятор спускається до аргументу шаблону `vector`, зіставляє `T*` із `int*` і виводить `T = int`.
3. **Перевірка сумісності та підстановка (Type Consistency & SFINAE).** Якщо один і той самий параметр `T` присутній у кількох формальних параметрах (наприклад, `f(T, T)`), виведені з кожного аргументу типи порівнюються на строгу ідентичність. Якщо типи різняться (наприклад, `int` та `double`), дедукція вважається невдалою, і перевантаження відхиляється без помилки збірки відповідно до правила SFINAE (Substitution Failure Is Not An Error).

## 2. Матриця базових контекстів передачі параметрів

Нижче наведено повну матрицю трансформацій типів під час виклику функцій залежно від форми параметра `P` та типу переданого виразу `A`:

| Форма параметра `P` | Тип аргументу `A` | Кваліфікатори `A` | Виведений тип `T` | Тип параметра у виклику | Особливості трансформації |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `T` (за значенням) | `int` | немає | `int` | `int` | Пряме копіювання |
| `T` (за значенням) | `const int` | top-level const | `int` | `int` | Відкидання top-level const |
| `T` (за значенням) | `const int&` | const + reference | `int` | `int` | Відкидання посилання та const |
| `T` (за значенням) | `int[10]` | C-масив | `int*` | `int*` | Array-to-pointer decay |
| `T` (за значенням) | `const char[6]` | рядковий літерал | `const char*` | `const char*` | Array decay зі збереженням const для елементів |
| `T` (за значенням) | `void(int)` | сигнатура функції | `void(*)(int)` | `void(*)(int)` | Function-to-pointer decay |
| `T&` (lvalue-посилання) | `int` | lvalue | `int` | `int&` | Зв'язування lvalue |
| `T&` (lvalue-посилання) | `const int` | const lvalue | `const int` | `const int&` | Константність переходить у `T` |
| `T&` (lvalue-посилання) | `const int&` | const ref lvalue | `const int` | `const int&` | Посилання ігнорується, const переходить у `T` |
| `T&` (lvalue-посилання) | `int[10]` | lvalue-масив | `int[10]` | `int(&)[10]` | Масив НЕ розпадається; зберігає розмір 10 |
| `const T&` (константне ref) | `int` | lvalue або rvalue | `int` | `const int&` | `const` є частиною `P`, тому `T = int` |
| `const T&` (константне ref) | `const int` | const lvalue | `int` | `const int&` | `T` виводиться без повторного `const` |
| `const T&` (константне ref) | `int[10]` | lvalue-масив | `int[10]` | `const int(&)[10]` | Зберігає тип і фіксований розмір масиву |
| `T&&` (передавальне ref) | `int` (lvalue `x`) | lvalue | `int&` | `int&` | Згортання: `int& && = int&` |
| `T&&` (передавальне ref) | `const int` (lvalue `cx`) | const lvalue | `const int&` | `const int&` | Згортання: `const int& && = const int&` |
| `T&&` (передавальне ref) | `int` (rvalue `42`) | prvalue | `int` | `int&&` | `T` виводиться без посилань |
| `T&&` (передавальне ref) | `std::move(x)` | xvalue | `int` | `int&&` | `T` виводиться як `int`, параметр стає `int&&` |
| `T*` (вказівник) | `int*` | покажчик | `int` | `int*` | Зіставлення за формою покажчика |
| `const T*` (вказівник на const) | `const int*` | покажчик на const | `int` | `const int*` | `const` належить формі `P`, `T = int` |
| `const T*` (вказівник на const) | `int*` | покажчик | `int` | `const int*` | Дозволено неявне додавання const до pointee |

### Детальні правила деградації типів (Type Decay)

Деградація типу (Array-to-pointer та Function-to-pointer decay) відбувається лише тоді, коли параметр `P` передається **за значенням** (`T` або `auto`).
- **Масиви:** Тип масиву `ElementType[Size]` перетворюється на вказівник `ElementType*`. Якщо масив був константним `const char[10]`, він перетворюється на вказівник на константу `const char*`. Багатовимірні масиви `int[3][4]` розпадаються у покажчик на масив `int(*)[4]`, де втрачається лише перша розмірність.
- **Функції:** Сигнатура функції `ReturnType(ArgTypes...)` розпадається у покажчик на функцію `ReturnType(*)(ArgTypes...)`.
- **Посилання як блокіратор деградації:** Якщо параметр оголошено за посиланням `T&` або `const T&`, деградація суворо заборонена стандартом. Тип масиву зберігається повністю, включаючи його фіксовану довжину, що дозволяє реалізовувати безпечні шаблонні функції перевірки розмірів буферів під час компіляції.

## 3. Матриця та алгебра згортання посилань (Reference Collapsing)

Правила згортання посилань застосовуються компілятором у випадках, коли посилання виникає на інше посилання (через підстановку параметрів шаблону `template<typename T>`, використання `decltype`, псевдонімів `using` або typedef).

У мові C++ подвійні посилання згортаються за комутативною логічною операцією:

```text
&  + &  ⇒ &   [lvalue + lvalue = lvalue]
&  + && ⇒ &   [lvalue + rvalue = lvalue]
&& + &  ⇒ &   [rvalue + lvalue = lvalue]
&& + && ⇒ &&  [rvalue + rvalue = rvalue]
```

### Таблиця комбінацій згортання у шаблонних підстановках

| Виведений тип `T` | Оголошений тип параметра `P` | Синтезоване проміжне посилання | Результуючий тип аргументу |
| :--- | :--- | :--- | :--- |
| `MyClass&` | `T&` | `MyClass& &` | `MyClass&` |
| `MyClass&` | `T&&` | `MyClass& &&` | `MyClass&` |
| `const MyClass&` | `T&&` | `const MyClass& &&` | `const MyClass&` |
| `MyClass&&` | `T&` | `MyClass&& &` | `MyClass&` |
| `MyClass&&` | `T&&` | `MyClass&& &&` | `MyClass&&` |
| `MyClass` | `T&&` | `MyClass&&` | `MyClass&&` |

### Інваріанти згортання посилань у системному коді

Головний закон згортання посилань можна сформулювати так: **lvalue-посилання завжди домінує**. Якщо хоча б одне з посилань у ланцюжку є посиланням на lvalue (`&`), результуючий тип завжди згортається у звичайне lvalue-посилання `&`.

Єдиний випадок, коли результуючий тип стає rvalue-посиланням (`&&`), це ситуація, коли обидва компоненти є виключно rvalue-посиланнями (`&& + && = &&`).

Саме цей фундаментальний інваріант робить можливою роботу утиліти `std::forward<T>` (ідеальна передача). Коли у функцію передається lvalue, `T` виводиться як `U&`, і виклик `std::forward<T>(arg)` перетворюється на `static_cast<U& &&>(arg) = static_cast<U&>(arg)`. Коли ж передається rvalue, `T` виводиться як `U`, і виклик стає `static_cast<U&&>(arg)`.

## 4. Повний перелік недедукованих контекстів (Non-deduced Contexts)

Відповідно до стандарту C++ (§13.10.2.5 [temp.deduct.type]), компілятор не виконує виведення типів для таких синтаксичних форм:

1. **Залежні імена з оператором розділення видимості `::`:**
   Форма `typename T::nested_type` або `Class<T>::member`.
   *Причина:* Компілятор не може знати всі можливі спеціалізації `Class<T>`, які могли б визначити `member` як конкретний тип.
   *Приклад:*
   ```cpp
   template<typename T>
   void func(typename std::vector<T>::iterator it); // Недедукований контекст для T!
   ```

2. **Нетипові параметри шаблону (NTTP) у складних виразах:**
   Вирази, що містять арифметичні операції або виклики функцій над параметром `N`.
   *Причина:* Компілятор не має універсального аналітичного інвертора для довільних математичних рівнянь над типами.
   *Приклад:*
   ```cpp
   template<int N>
   void process(std::array<int, N + 1> arr); // Недедукований контекст для N!
   ```

3. **Шаблонний аргумент, переданий у перевантажену функцію без однозначного типу:**
   Якщо як аргумент передається ім'я перевантаженої функції або шаблон функції без явних аргументів:
   ```cpp
   template<typename T> void execute(void (*fn)(T));
   void handler(int);
   void handler(double);
   // execute(handler); // ПОМИЛКА: неоднозначність недедукованого виклику
   ```

4. **Аргументи за замовчуванням у параметрах функцій:**
   Типи аргументів за замовчуванням ніколи не беруть участі у дедукції параметрів шаблону:
   ```cpp
   template<typename T>
   void reset(T* ptr, T default_val = T{});
   // reset(my_ptr); // T виводиться ТІЛЬКИ з my_ptr, default_val не впливає
   ```

5. **Використання `std::type_identity` або `std::type_identity_t` (C++20):**
   Стандартна метафункція для явного переведення параметра у недедукований контекст:
   ```cpp
   template<typename T>
   void set_range(T lower_bound, std::type_identity_t<T> upper_bound);
   // lower_bound визначає T, upper_bound неявно приводиться до T
   ```

## 5. Дозволені неявні перетворення під час виведення типів

Під час звичайного виклику перевантажених нешаблонних функцій компілятор може виконувати широкий спектр стандартних неявних перетворень: цілочислове розширення (`short -> int`), приведення з плаваючою крапкою (`float -> double`), перетворення користувача через конструктори та оператори приведення.

Проте під час виведення аргументів шаблонів функцій діє суворе обмеження: **компілятор не виконує загальних неявних перетворень типів для дедукції**. Єдиними дозволеними трансформаціями для зіставлення форми `P` з типом `A` є:

1. **Кваліфікаційні перетворення (Qualification Conversions):** Додавання `const` або `volatile` до вказівників (наприклад, зіставлення `const int*` із параметром `const T*` дедукує `T = int`).
2. **Перетворення до базового класу (Base-to-Derived Conversions):** Якщо параметр оголошено за формою `Base<T>*` або `Base<T>&`, аргумент похідного класу `Derived : Base<int>` дозволяє вивести `T = int`.
3. **Деградація масивів та функцій (Decay Conversions):** Перетворення `T[N] -> T*` та `Func -> Func*` лише за умови передачі за значенням.

Усі інші конверсії (наприклад, `int -> double` або `std::string_view -> std::string`) повністю заблоковані для дедукованих параметрів. Це математична гарантія однозначності виведення, що запобігає комбінаторному вибуху варіантів інстанціації шаблонів.

## 6. Виведення типів для шаблонів зі змінною кількістю аргументів (Variadic Packs)

Виведення пакетів параметрів шаблону `template<typename... Args>` підпорядковується спеціальним правилам розгортання та зіставлення послідовностей:

1. **Пакет у кінці списку параметрів (Trailing Pack):**
   Якщо шаблон має сигнатуру `template<typename T, typename... Args> void log(T head, Args... tail)`, перший аргумент зв'язується з `T`, а всі наступні фактичні аргументи формують пакет `Args...`:
   ```cpp
   log(1, 2.5, "test"); // T = int, Args = {double, const char*}
   ```
2. **Пакет на початку або в середині (Non-trailing Pack):**
   Якщо пакет параметрів стоїть перед звичайним параметром `template<typename... Args, typename Target> void send(Args... args, Target dst)`, компілятор не може визначити, де закінчується пакет і починається `Target`. У такому разі `Target` стає недедукованим контекстом і повинен бути явно вказаний у точці виклику:
   ```cpp
   // send(1, 2, 3); // ПОМИЛКА: Target не може бути виведений
   send<int, int, double>(1, 2, 3.14); // Успіх за явного вказання
   ```
3. **Паралельні пакети однакової довжини:**
   Якщо функція приймає два пакети однакової форми `template<typename... Ts> void zip(Pair<Ts, Ts>...)`, компілятор для кожної пари перевіряє рівність типів її компонентів.

## 7. Виведення аргументів під час взяття адреси шаблону функції

Відповідно до стандарту C++ (§13.10.2.2 [temp.deduct.funcaddr]), коли програміст бере адресу перевантаженого або шаблонного імені функції, цільовий тип вказівника використовується як тип аргументу `A` для виведення параметрів шаблону:

```cpp
template<typename T>
T compute_square(T x) { return x * x; }

// Цільовий тип вказівника на функцію:
int (*func_ptr)(int) = &compute_square;
// Компілятор зіставляє T(T) із int(int) і автоматично інстанціює compute_square<int>
```

Якщо контекст не надає точного очікуваного типу (наприклад, `auto ptr = &compute_square;`), компілятор зупиняє збірку з помилкою, оскільки адреса шаблону без аргументів не є конкретною адресою в пам'яті.

## 8. Виведення типів для шаблонів псевдонімів (Alias Templates)

Шаблони псевдонімів `template<typename T> using MyPtr = T*;` є прозорими синтаксичними скороченнями. Під час дедукції аргументів функцій компілятор розгортає псевдонім до його канонічної форми перед початком зіставлення типів:

```cpp
template<typename T> using VectorRef = const std::vector<T>&;

template<typename T>
void inspect(VectorRef<T> vec); // Розгортається компілятором у const std::vector<T>&
```

У C++17 виведення типів класів (CTAD) через alias templates було заборонено. У стандарті C++20 було ухвалено пропозицію P1814R0 (*«Class Template Argument Deduction for Alias Templates»*), яка дозволила автоматично генерувати deduction guides для alias templates шляхом дедукції та заміщення аргументів базового первинного шаблону.

## 9. Правила синтезу кандидатів CTAD (Class Template Argument Deduction)

Починаючи з C++17, під час ініціалізації екземпляра шаблонного класу `TemplateClass obj(arg1, arg2);` компілятор формує множину уявних функцій-кандидатів виведення (Deduction Candidates Set):

### 1. Неявні кандидати конструкторів (Implicit Constructor Candidates)

Для кожного конструктора `TemplateClass(P1, P2, ...)` у первинному шаблоні класу компілятор генерує еквівалентну уявну функцію:
```cpp
template<typename... TemplateParams, typename... ConstructorParams>
auto __synthesized_guide(P1, P2, ...) -> TemplateClass<TemplateParams...>;
```

### 2. Неявний кандидат копіювання (Implicit Copy Candidate)

Для будь-якого шаблонного класу автоматично синтезується спеціальний кандидат копіювання:
```cpp
template<typename... TemplateParams>
auto __synthesized_copy_guide(TemplateClass<TemplateParams...>) 
    -> TemplateClass<TemplateParams...>;
```
Цей кандидат гарантує, що запис `std::vector v2{v1}` завжди викликає копіювання вектора, а не створення вкладеного вектора векторів `std::vector<std::vector<T>>`.

### 3. Синтез кандидатів для агрегатів (C++20, P1816R0)

Якщо шаблон класу є агрегатом (структурою без конструкторів, приватних полів та базових класів), компілятор автоматично генерує кандидата, параметри якого відповідають типам відкритих полів класу:
```cpp
template<typename T1, typename T2>
struct Pair { T1 first; T2 second; };

// Синтезований кандидат C++20:
template<typename T1, typename T2>
auto __synthesized_aggregate_guide(T1, T2) -> Pair<T1, T2>;
```

### 4. Пріоритети розв'язання перевантаження у CTAD

Під час виконання Overload Resolution серед згенерованого набору кандидатів CTAD діють такі стандартизовані правила вибору найкращого кандидата:
1. **Користувацькі правила виведення (Deduction Guides) мають рівні права з неявними кандидатами конструкторів:** Якщо сигнатури явного guide та конструктора збігаються, вони розглядаються як звичайні перевантаження.
2. **Більш спеціалізований шаблон перемагає (Partial Ordering):** Якщо один кандидат є більш спеціалізованим за інший (наприклад, приймає `T*` замість `T`), вибирається більш спеціалізований варіант.
3. **Кандидати з `initializer_list` мають пріоритет при ініціалізації у фігурних дужках `{}`:** Якщо аргументи у фігурних дужках можуть бути приведені до типу елемента `std::initializer_list`, конструктор зі списком завжди перемагає звичайні конструктори з відповідною кількістю аргументів, окрім випадку ініціалізації одним елементом того самого типу.

## 10. Синтаксис та специфікатори Deduction Guides

Користувацькі правила виведення оголошуються в тій самій області видимості (просторі імен), що й сам шаблон класу.

### Граматика та синтаксична структура

```cpp
// Загальний синтаксис
[explicit] template <список_параметрів_шаблону>
Ім'яКласу (список_параметрів_правила) -> ТипСпеціалізаціїКласу;
```

### Ключові властивості Deduction Guides

1. **Не є функціями:** Deduction guides не мають тіла, не мають адреси в пам'яті, не експортуються як символи об'єктного файлу і не викликаються під час виконання програми. Вони існують виключно під час синтаксичного аналізу для алгоритму Overload Resolution.
2. **Специфікатор `explicit`:**
   - Deduction guide без `explicit` бере участь як у прямій ініціалізації (`Class obj(a, b);`, `Class obj{a, b};`), так і в ініціалізації копіюванням (`Class obj = {a, b};`, `Class obj = a;`).
   - Deduction guide з `explicit` бере участь **виключно** у прямій ініціалізації (`Class obj(a, b);` або `Class obj{a, b};`). Спроба виконати копіювальну ініціалізацію з `=` призводить до помилки компіляції.
3. **Область пошуку (Scope Lookup):**
   Керівне правило виведення має бути оголошене в тому самому просторі імен і після оголошення первинного шаблону класу, але до першого місця його використання з CTAD.

### Приклади стандартних правил виведення у бібліотеці C++

```cpp
// std::pair (C++17)
template<class T1, class T2>
pair(T1, T2) -> pair<T1, T2>;

// std::array (C++17)
template<class T, class... U>
array(T, U...) -> array<T, 1 + sizeof...(U)>;

// std::span (C++20)
template<class It, class EndOrSize>
span(It, EndOrSize) -> span<std::remove_reference_t<std::iter_reference_t<It>>>;

template<class T, std::size_t N>
span(T (&)[N]) -> span<T, N>;
```

## 11. Взаємодія правил виведення з ключовим словом auto

Ключове слово `auto` у мові C++ використовує точно ті самі математичні правила дедукції, що й параметри шаблонів функцій:

| Оголошення змінної | Еквівалентний шаблон функції | Застосовувані правила виведення |
| :--- | :--- | :--- |
| `auto x = expr;` | `template<typename T> void f(T x);` | За значенням: відкидання top-level const, розпад масивів |
| `const auto x = expr;` | `template<typename T> void f(const T x);` | За значенням із додаванням top-level const |
| `auto& x = expr;` | `template<typename T> void f(T& x);` | За lvalue-посиланням: збереження const та розмірів масивів |
| `const auto& x = expr;` | `template<typename T> void f(const T& x);` | За константним lvalue-посиланням: зв'язування з lvalue та rvalue |
| `auto&& x = expr;` | `template<typename T> void f(T&& x);` | Передавальне посилання: lvalue дає `auto&`, rvalue дає чистий тип |
| `decltype(auto) x = expr;` | *Немає аналога у TAD* | Виведення за правилами `decltype(expr)` без відкидання посилань |

### Скорочені шаблони функцій у C++20 (Abbreviated Function Templates)

Починаючи з C++20, використання `auto` або концептуальних плейсхолдерів у списку параметрів функцій є повністю еквівалентним оголошенню шаблонної функції:

```cpp
// Скорочений запис C++20:
void print_value(std::integral auto val, auto&& callback);

// Повний еквівалентний класичний запис:
template<std::integral T1, typename T2>
void print_value(T1 val, T2&& callback);
```

Виведення типів для таких скорочених функцій підпорядковується всім стандартним правилам Template Argument Deduction, включаючи відкидання константності для параметрів за значенням, згортання посилань для `auto&&` та перевірку обмежень концептів після завершення фази структурного вирівнювання типів.

## 12. Поведінка CTAD при різних формах ініціалізації об'єктів

Поведінка механізму CTAD суттєво залежить від синтаксичної форми ініціалізації об'єкта, оскільки різні форми активують різні набори кандидатів та правила конверсії:

| Синтаксис ініціалізації | Форма ініціалізації | Участь `explicit` deduction guides | Пріоритет конструктора списку (`initializer_list`) |
| :--- | :--- | :--- | :--- |
| `Container c(a, b);` | Direct-initialization | Дозволено (повний набір) | Низький (пріоритет звичайних конструкторів) |
| `Container c{a, b};` | Direct-list-initialization | Дозволено (повний набір) | Високий (якщо аргументи підходять під `initializer_list`) |
| `Container c = {a, b};` | Copy-list-initialization | Заборонено (лише не-explicit) | Високий (звужувальні перетворення заборонені) |
| `Container c = a;` | Copy-initialization | Заборонено (лише не-explicit) | Не застосовується (одиничний аргумент) |
| `auto c = Container(a);` | Direct-init у prvalue | Дозволено | Визначається формою дужок аргументу |

## 13. Таксономія повідомлень про помилки дедукції

У разі порушення правил дедукції сучасні компілятори C++ (Clang, GCC, MSVC) формують стандартизовані повідомлення про помилки:

1. **Конфлікт виведених типів (`conflicting deduced types`):** Виникає, коли один параметр `T` присутній у двох позиціях сигнатури, але фактичні аргументи вимагають несумісних типів (наприклад, `int` і `double` у `min(a, b)`). Розв'язання — явне зазначення `min<double>(a, b)` або використання `std::type_identity`.
2. **Неможливість виведення у недедукованому контексті (`could not deduce template argument`):** Виникає при спробі передати аргумент у форму `typename Container::iterator`. Розв'язання — параметризувати функцію типом самого ітератора.
3. **Неоднозначність кандидатів CTAD (`ambiguity in class template argument deduction`):** Виникає, коли два конструктори або deduction guides мають однакову вагу перевантаження. Розв'язання — обмежити правила за допомогою концептів `requires`.
4. **Порушення концептуальних обмежень (`constraints not satisfied`):** Виникає, коли тип виведено успішно, але він не задовольняє вимоги `requires`-секції.
5. **Невдача розкриття пакетів різної довжини (`pack expansion argument lengths differ`):** Виникає при спробі зіставити два паралельні пакети параметрів `template<typename... Ts> void f(Pair<Ts, Ts>...)`, якщо типи пар не узгоджуються між собою.
