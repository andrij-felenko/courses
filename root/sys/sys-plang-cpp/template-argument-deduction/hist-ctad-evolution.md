# 📜 Еволюція виведення аргументів шаблонів у C++: від C++98 до CTAD

Коли в середині 1990-х років Александр Степанов разом із Б'ярном Страуструпом інтегрували Standard Template Library (STL) до проєкту першого міжнародного стандарту ISO/IEC 14882:1998, головною метою було створення узагальнених алгоритмів із нульовими накладними витратами під час виконання. Алгоритми на зразок `std::sort` або `std::find` мали викликатися природно: програміст передавав ітератори `std::sort(vec.begin(), vec.end())`, а компілятор самостійно обчислював тип ітератора без потреби писати громіздку явну конструкцію `std::sort<std::vector<int>::iterator>(...)`.

Проте для шаблонів класів розробники мови залишили фундаментальну асиметрію, яка існувала майже два десятиліття. Створення екземпляра шаблонного класу вимагало обов'язкового явного зазначення параметрів у кутових дужках: вираз `std::pair<int, double> p(10, 3.14);` змушував дублювати типи, які компілятор уже міг прочитати з аргументів ініціалізації. Щоб обійти це обмеження, творці бібліотеки були змушені будувати паралельний шар вільних функцій-фабрик.

## Епоха C++98: фабричні помічники та комбінаторний глухий кут

У стандарті C++98 виведення аргументів шаблону (від лат. *deductio* — логічний висновок з очевидних передумов) працювало виключно для шаблонних функцій. Коли компілятор бачив виклик функції, він зіставляв типи переданих фактичних аргументів із типами формальних параметрів у сигнатурі. Для класів аналогічного механізму не передбачили: конструктор вважався внутрішньою функцією конкретної спеціалізації, а не окремим шаблоном. Перш ніж викликати конструктор, компілятор мусив уже знати повне ім'я класу з усіма типами-параметрами.

Ранні компілятори C++98 (зокрема GCC 2.95 та Microsoft Visual C++ 6.0) мали численні вади в реалізації алгоритму зіставлення шаблонів. Найбільші проблеми виникали із залежними типами: спроба передати ітератор `typename Container::iterator` у функціональний шаблон часто призводила до того, що компілятор потрапляв у недедукований контекст (Non-deduced Context) і вимагав явного зазначення параметрів.

Щоб зменшити синтаксичний шум у користувацькому коді, комітет запровадив ідіому допоміжних функцій-фабрик. Для базової структури `std::pair` було створено функцію `std::make_pair`:

```cpp
template<typename T1, typename T2>
std::pair<T1, T2> make_pair(T1 x, T2 y) {
    return std::pair<T1, T2>(x, y);
}
```

Оскільки `make_pair` є функцією, виклик `std::make_pair(10, 3.14)` запускав алгоритм виведення типів аргументів: `T1` дедукувався як `int`, `T2` як `double`, і функція конструювала потрібну пару. Згодом аналогічний підхід ліг в основу бібліотеки Boost.Tuple (`boost::make_tuple`), а також шаблонів виразів (Expression Templates) у бібліотеках Boost.Spirit та Boost.Phoenix, де довгі типи парсерів конструювалися виключно через ланцюжки викликів шаблонних функцій.

Однак фабричні функції C++98 мали фундаментальну ваду: передача за значенням `T1 x` змушувала виконувати зайве копіювання об'єктів, знімала кваліфікатори `const` і `volatile`, а також викликала розпад масивів та функцій у сирі вказівники. Якщо ж розробники намагалися оголосити параметри за константним посиланням `const T1&`, ставало неможливо передати неконстантні посилання для модифікації об'єктів на місці. Підтримка всіх можливих комбінацій `const` і не-`const` посилань для функцій із `N` параметрами спричиняла комбінаторний вибух: для фабрики з трьома параметрами потрібно було написати `2³ = 8` перевантажень, а для кортежу з десяти елементів — `2¹⁰ = 1024` окремі сигнатури.

## Революція C++11: rvalue-посилання та згортання посилань

Розв'язання комбінаторного глухого кута запропонував Говард Гіннант (Howard Hinnant) у співпраці з Б'ярном Страуструпом та Пітером Дімчевим (Peter Dimov) під час розробки семантики переміщення для стандарту C++11. Ключовим інструментом стало введення rvalue-посилань (позначуваних як `&&`) та суворих правил згортання посилань (Reference Collapsing).

Скотт Мейєрс назвав конструкцію `T&&` у шаблонному контексті «універсальним посиланням» (Universal Reference), тоді як комітет ISO зафіксував технічний термін **передавальне посилання** (Forwarding Reference). Якщо параметр функції оголошувався як `T&&`, де `T` є дедукованим типом-параметром цієї ж функції, компілятор застосовував спеціальне правило:
- якщо передано lvalue-вираз типу `U`, то `T` дедукується як lvalue-посилання `U&`;
- якщо передано rvalue-вираз типу `U`, то `T` дедукується як звичайний тип без посилання `U`.

Завдяки алгебрі згортання посилань (де `& + & = &`, `& + && = &`, `&& + & = &` і лише `&& + && = &&`), комбінація передавального посилання та допоміжної функції `std::forward<T>` дозволила створити єдине перевантаження фабричної функції, яке бездоганно зберігало категорію значення та константність:

```cpp
template<typename T1, typename T2>
std::pair<std::decay_t<T1>, std::decay_t<T2>> make_pair(T1&& x, T2&& y) {
    return std::pair<std::decay_t<T1>, std::decay_t<T2>>(
        std::forward<T1>(x),
        std::forward<T2>(y)
    );
}
```

Це нововведення дало змогу стандартизувати `std::make_tuple`, `std::make_shared`, а згодом у C++14 — `std::make_unique`. Проте потреба створювати власні `make_`-функції для кожного призначеного для користувача класу залишалася суттєвим тягарем для архітектури бібліотек.

## C++14: розширення auto та узагальнені лямбди

Паралельно з розвитком функціональних шаблонів комітет C++14 суттєво розширив використання ключового слова `auto`. Механізм виведення типів аргументів шаблону було покладено в основу дедукції типів локальних змінних, повертаних значень функцій (`auto` та `decltype(auto)`) і параметрів узагальнених лямбда-виразів (Generic Lambdas).

Коли програміст записував у C++14 лямбда-вираз:

```cpp
auto logger = [](auto&& message) {
    std::cout << "[LOG]: " << message << '\n';
};
```

компілятор генерував анонімний клас-функтор із шаблонним оператором виклику `template<typename T> auto operator()(T&& message) const`. Узагальнені лямбди довели спільноті та комітету ISO, що можливість опускати кутові дужки значно покращує читабельність коду, не зменшуючи при цьому строгість типізації. Проте виклик конструкторів шаблонних класів усе ще лишався заручником старого синтаксису.

## Пропозиція P0091 та народження CTAD у C++17

Незважаючи на гнучкість `auto`, створення об'єктів стандартних класів із конструкторами залишалося архаїчним. Найбільш показовим був приклад блокувальників м'ютексів: створення `std::lock_guard<std::mutex> lock(mtx);` змушувало програміста вказувати тип `std::mutex`, хоча компілятор чудово знав тип аргументу `mtx`. Аналогічно, обгортки на зразок `std::optional`, `std::variant` або користувацькі масиви вимагали дублювання коду.

У 2015 році Майк Спертус (Mike Spertus), Файзал Валі (Faisal Vali) та Річард Сміт (Richard Smith) представили пропозицію P0091 (*«Template argument deduction for class templates»*). Їхня ідея полягала в тому, щоб поширити виведення аргументів на конструктори класів без внесення глобальних змін у ядро мови.

Замість того щоб винаходити окремий механізм аналізу конструкторів, автори запропонували генерувати уявний набір перевантажень функцій (Fictitious Overload Candidate Set). Для кожного конструктора в первинному шаблоні класу компілятор автоматично синтезував еквівалентний шаблон функції, чиї параметри збігалися з параметрами конструктора, а повертаним типом була спеціалізація класу. Вибір типу зводився до запуску звичайного алгоритму Overload Resolution.

Під час обговорення в комітеті розгорнулася гостра дискусія щодо крайових випадків:
1. **Конфлікт ініціалізації вектором:** Що повинен виводити вираз `std::vector v{std::vector{1, 2}}` — вектор векторів `std::vector<std::vector<int>>` чи копіювати вихідний вектор `std::vector<int>`? Комітет вирішив, що якщо тип аргументу збігається з типом самого вектора, пріоритет має конструктор копіювання/переміщення, і лише при додаванні другого аргументу ініціалізація розглядається як вкладений список.
2. **Ітераторні конструктори:** Конструктор `std::vector(Iter first, Iter last)` приймає ітератори, але параметр класу `T` — це тип розіменованого елемента `*first`. Звичайної дедукції з конструктора було недостатньо.
3. **Керування явним викликом (explicit guides):** Як захистити бібліотеку від небажаних неявних перетворень типів під час дедукції? Для цього було стандартизовано специфікатор `explicit` у deduction guides, який дозволяє виведення лише під час прямої ініціалізації (Direct-initialization), блокуючи копіювальну ініціалізацію з присвоєнням.

Щоб розв'язати проблему ітераторів та інших нетривіальних трансформацій типів, автори P0091 додали синтаксис користувацьких правил виведення — **Deduction Guides**:

```cpp
template<typename Iterator>
Vector(Iterator, Iterator) -> Vector<typename std::iterator_traits<Iterator>::value_type>;
```

Ухвалення стандарту C++17 зробило Class Template Argument Deduction (CTAD) офіційною частиною мови. Зникла потреба у десятках застарілих фабрик `std::make_pair`, `std::make_tuple` та `std::make_lock_guard`.

## C++20: агрегати, неперервні представлення та концептуальні обмеження

Перша версія CTAD у C++17 мала одну помітну білу пляму: вона працювала виключно для класів із явно оголошеними конструкторами. Прості агрегатні структури (Aggregate Types) не мали конструкторів, тому вираз:

```cpp
template<typename T, typename U>
struct Pair {
    T first;
    U second;
};

// У C++17 це викликало помилку компіляції:
// Pair p{1, 2.5};
```

був заборонений. Програмісти мусили або писати явні конструктори, що позбавляло структуру статусу агрегату, або вручну писати довгі deduction guides.

У стандарті C++20 робоча група ухвалила пропозицію P1816R0 Тіма Шенга (Tim Shen) та Річарда Сміта, яка реалізувала синтез кандидатів виведення для агрегатів безпосередньо зі списку їхніх нестатичних полів. Це уможливило використання CTAD для легковагих структур без жодного рядка допоміжного шаблонного коду.

Ще одним важливим застосуванням CTAD у C++20 став тип `std::span`. Завдяки продуманим deduction guides `std::span` зміг автоматично виводити як тип елемента, так і статичний розмір масиву з сирих C-масивів `int arr[16]`, стандартних масивів `std::array` та контейнерів із неперервною пам'яттю `std::vector`, зв'язуючи статичну інформацію компіляції із безпекою доступу.

Крім того, стандарт C++20 гармонізував виведення аргументів шаблонів із системою концептів (Concepts). З'явилася можливість обмежувати типи безпосередньо у сигнатурах викликів через скорочені шаблони функцій (Abbreviated Function Templates): `void process(std::integral auto value)` та обмежувати правила виведення за допомогою `requires`-секцій.

Сьогодні виведення аргументів шаблонів у C++ пройшло шлях від простої евристики для ітераторів Степанова до математично замкненої, багаторівневої системи дедукції, що охоплює функції, змінні, лямбди, складні агрегати та концептуальні інтерфейси. Ця еволюція перетворила шаблони C++ із суто академічного експерименту на найпотужніший промисловий інструмент узагальненого програмування з нульовою вартістю абстракцій.
