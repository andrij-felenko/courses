# 📜 Від хаосу макросів компіляторів до SD-6 та заголовка <version>

Історія уніфікації тестування можливостей C++ розкриває, як спроба подолати несумісність між ранніми реалізаціями стандарту C++11 перетворила неформальну рекомендацію дослідницької групи на обов'язковий компонент міжнародного стандарту ISO.

У 2011 році, після прийняття революційного стандарту C++11, індустрія розробки програмного забезпечення зіткнулася з парадоксальною кризою. Стандарт приніс величезну кількість нововведень — від семантики переміщення та автоматичного виведення типів `auto` до лямбда-виразів, `constexpr` та моделі пам'яті для багатопоточності. Проте жоден компілятор того часу не міг імплементувати весь обсяг специфікації водночас. Команди розробників GCC, Clang, Microsoft Visual C++, Intel C++ Compiler та EDG (Edison Design Group) додавали нові синтаксичні конструкції та бібліотечні класи окремими фрагментами протягом багатьох років.

### Тупик макросу __cplusplus та комбінаторний вибух

Єдиним стандартизованим засобом перевірки версії мови в C++98 та C++11 був зумовлений препроцесорний макрос `__cplusplus`. Згідно зі специфікацією ISO/IEC 14882:2011, компілятор повинен був визначати цей макрос значенням `201103L` лише тоді, коли він повністю відповідав стандарту C++11. 

На практиці це створювало нерозв'язну дилему для виробників компіляторів:
- Якщо компілятор виставляв значення `__cplusplus = 201103L` за наявності 80% можливостей, вихідний код сторонніх бібліотек намагався викликати відсутні 20% і аварійно завершував компіляцію з синтаксичними помилками.
- Якщо ж компілятор тримав старе значення `199711L` до моменту реалізації останньої, найскладнішої фічі, розробники не мали змоги скористатися вже готовими 80% нововведень (наприклад, `nullptr` чи `static_assert`).

Бібліотеки загального призначення (зокрема Boost через підсистему `Boost.Config`) були змушені будувати гігантські евристичні матриці перевірок умовного препроцесора:

```cpp
#if defined(__clang__)
    #if __has_feature(cxx_rvalue_references)
        #define HAS_MOVE_SEMANTICS 1
    #endif
#elif defined(__GNUC__)
    #if (__GNUC__ > 4 || (__GNUC__ == 4 && __GNUC_MINOR__ >= 3)) && defined(__GXX_EXPERIMENTAL_CXX0X__)
        #define HAS_MOVE_SEMANTICS 1
    #endif
#elif defined(_MSC_VER)
    #if _MSC_VER >= 1600
        #define HAS_MOVE_SEMANTICS 1
    #endif
#endif
```

Ці матриці розросталися до десятків тисяч рядків макросів. Вони вимагали безперервного супроводу, ламалися з виходом кожного нового мінорного релізу компілятора та ставали повністю марними, коли на ринку з'являвся новий транслятор або коли Clang використовував бібліотеку заголовків від GCC чи MSVC.

### Народження дослідницької групи SG10

У 2012 році на засіданні робочої групи WG21 у місті Кона (Гаваї) Кларк Нельсон (Clark Nelson, представник Intel) та Майкл Вонг (Michael Wong, представник IBM) виступили з ініціативою створення окремої робочої групи для розв'язання кризи переносимості сирцевого коду. За підтримки Б'ярна Страуструпа (Bjarne Stroustrup) було сформовано дослідницьку групу **SG10 (Study Group 10: Feature Test Recommendations)**.

Перед групою SG10 стояло завдання розробити механізм, який задовольняв би чотири жорсткі вимоги:
1. **Гранулярність**: кожна окрема мовна або бібліотечна можливість повинна мати власний унікальний ідентифікатор препроцесора.
2. **Числова версійність**: оскільки можливості мови еволюціонують і доповнюються виправленнями (Defect Reports), макрос повинен бути числом, а не булевим прапорцем, щоб дозволити порівняння через `>=`.
3. **Нульова вартість**: зондування можливостей ядра не повинно вимагати підключення важких системних файлів або уповільнювати час трансляції.
4. **Уніфікована конвенція імен**: префікс `__cpp_` для ядра мови та `__cpp_lib_` для компонентів стандартної бібліотеки STL.

### Поява Постійного документа 6 (SD-6)

Замість того, щоб чекати наступного офіційного видання стандарту ISO (яке планувалося лише на C++14 чи C++17), комітет обрав гнучкий формат — **Постійний документ (англ. Standing Document, SD)**. Так народився документ **SD-6 (SG10 Feature Test Recommendations)**, перша редакція якого була опублікована у 2013 році під назвою папера N3745.

Формат Standing Document дозволяв публікувати оновлення рекомендацій двічі-тричі на рік, одразу після чергових пленарних засідань WG21. Коли комітет затверджував новий папір, автори SD-6 негайно призначали відповідний макрос та дату у форматі `YYYYMML`, яка точно відповідала місяцю голосування (наприклад, `201304L` для нововведень C++14, ухвалених у квітні 2013 року в Брістолі).

Виробники компіляторів зустріли ініціативу з великим ентузіазмом:
- Команда Clang швидко імплементувала підтримку макросів ядра та оператора `__has_include`.
- Розробники GCC інтегрували макроси у версію GCC 5.0.
- Microsoft почала поступово замінювати свої внутрішні макроси на макроси SD-6, починаючи з Visual Studio 2015 Update 2.

### Шлях до нормативного стандарту: папір P0941R2 та заголовок <version>

Хоча SD-6 здобув де-факто визнання індустрії, він юридично залишався лише неформальною порадою. Компілятор міг претендувати на 100% сумісність із ISO C++14 чи C++17, взагалі не визначаючи жодного макросу `__cpp_*`.

Переломний крок до стандартизації відбувся у 2018 році: після розгляду початкових редакцій на засіданні WG21 у Джексонвіллі (березень 2018 року) Вілле Воутілайнен (Ville Voutilainen) та Джонатан Вейклі (Jonathan Wakely) підготували папір **P0941R2 (Integrating feature-test macros into the C++ WD)**, який було остаточно затверджено комітетом на засіданні в Рапперсвілі (Rapperswil) у червні 2018 року. Папір запропонував перенести всі положення SD-6 безпосередньо в робочий проєкт нормативного тексту майбутнього стандарту C++20.

Нормативне закріплення принесло дві фундаментальні зміни:
1. **Обов'язковість операторів препроцесора**: `__has_include` та `__has_cpp_attribute` стали невіддільною частиною граматики фази препроцесингу ISO C++.
2. **Стандартизація легковагого заголовка `<version>`**: папір P0754R2 запровадив спеціальний заголовок стандартної бібліотеки, призначений виключно для постачання макросів `__cpp_lib_*`. Цей файл не оголошує жодних типів, не створює шаблонів, не виділяє пам'ять і гарантовано працює в автономних середовищах без операційної системи (Freestanding).

### Спадщина та значення стандартизації

З виходом стандарту ISO/IEC 14882:2020 епоха хаотичних перевірок версій компіляторів остаточно відійшла в минуле. Стандартизовані макроси дали змогу авторам бібліотек створювати тонкі адаптивні прошарки сумісності (поліфіли), які автоматично переходять на сучасні засоби мови в міру оновлення інструментів збірки, не вимагаючи переписування клієнтського коду.
