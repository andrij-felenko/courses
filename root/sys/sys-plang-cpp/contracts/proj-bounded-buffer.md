# ⚙️ Кільцевий буфер фіксованого розміру з повним контрактом

Цей проєкт демонструє практичну реалізацію високопродуктивного контейнера кільцевого буфера фіксованої місткості (`BoundedRingBuffer<T, Capacity>`) із вичерпною специфікацією контрактів мовою C++26. Проєкт детально розбирає, як за допомогою преумов, постумов, внутрішніх тверджень та інваріантів стану побудувати надійний контейнер нульової вартості для систем реального часу, вбудованих пристроїв, обробки аудіо/відео та мережевих конвеєрів.

## Інженерна задача та вимоги до контейнера

У високопродуктивних системах передавання повідомлень, низькорівневих драйверах периферійних пристроїв, обробці аудіо- та відеопотоків у реальному часі динамічне виділення пам'яті через системну купу (`heap allocation`) категорично неприйнятне. Виклики функцій `malloc` або оператора `new` мають недетермінований час виконання через необхідність пошуку вільних блоків пам'яті в пулі алокатора, можуть викликати блокування м'ютексів у багатопотокових середовищах та призводять до поступової фрагментації адресного простору.

У таких архітектурах базовою структурою збереження та передавання даних є черга з фіксованим розміром пам'яті (Bounded FIFO Queue). Традиційні підходи до розробки подібних контейнерів у попередніх стандартах C++ завжди були пов'язані з болючими компромісами між надійністю, швидкістю та чистотою інтерфейсу:

1. **Обробка помилок через винятки (`throw std::overflow_error`):** руйнує детермінізм часу виконання в критичних циклах реального часу. Генерація винятку вимагає виконання коду бібліотеки розкрутки стека (libunwind), пошуку обробників у таблицях LSDA та скидання кешів інструкцій процесора. Крім того, клієнтський код змушений ускладнювати власну структуру блоками `try/catch`.
2. **Мовчазне відкидання даних або циклічне перезаписування:** приховує логічні помилки на стороні викликача. Якщо черга заповнена, а клієнт продовжує запис, втрата даних відбувається тихо і непомітно, що згодом призводить до важковиправних багів розсинхронізації протоколів зв'язку.
3. **Використання повернення кодів помилок або типів `std::optional` / `std::expected`:** змушує клієнта на кожній ітерації виконувати розпакування результату та перевірку прапорця успіху. Це створює накладні витрати на передачу додаткових статусів через регістри процесора на критичних шляхах виконання (hot paths).
4. **Класичний макрос `assert()`:** повністю видаляється компілятором у релізних збірках із прапорцем `-DNDEBUG`. Це залишає будь-яке випадкове переповнення черги безконтрольним, перетворюючи логічний дефект на прямий вихід за межі масиву та небезпечне пошкодження пам'яті.

Контракти стандарту C++26 пропонують четвертий шлях: формальний опис вимог на рівні інтерфейсу, що забезпечує повний контроль за дотриманням протоколу взаємодії як під час компіляції, так і під час виконання без будь-яких прихованих накладних витрат у релізі.

## Архітектура пам'яті та математична модель кільцевого буфера

Контейнер `BoundedRingBuffer` резервує весь необхідний обсяг пам'яті статично безпосередньо всередині власного тіла. Щоб уникнути створення неініціалізованих або фіктивних об'єктів типу `T` під час конструювання буфера (що вимагало б наявності публічного конструктора за замовчуванням у типі `T` та створювало б зайву роботу для CPU), пам'ять виділяється у вигляді сирого масиву байтів.

Масив байтів обов'язково вирівнюється за вимогами типу `T` за допомогою специфікатора `alignas(alignof(T))`. Створення об'єктів у цій пам'яті здійснюється через розміщувальний оператор `new` (placement new), а знищення — через явний прямий виклик деструктора `ptr->~T()`.

Стан структури даних у будь-який момент часу однозначно визначається трьома невід'ємними цілими числами:
- `head_` — індекс комірки масиву, де зберігається найстаріший доданий елемент, який буде видалено наступним при виклику `pop()`;
- `tail_` — індекс комірки масиву, куди буде збережено наступний новий елемент при виклику `push()`;
- `size_` — поточна кількість активних живих об'єктів, збережених у буфері.

### Формальні інваріанти структури
Математична коректність стану буфера описується трьома строгими твердженнями, які повинні залишатися істинними до і після завершення будь-якої відкритої операції:

- **Інваріант місткості:** `size_ <= Capacity`. Кількість збережених об'єктів ніколи не може бути від'ємною або перевищувати статичний ліміт `Capacity`.
- **Інваріант валідності індексів:** `head_ < Capacity` та `tail_ < Capacity`. Обидва індекси завжди знаходяться в строгому діапазоні допустимих індексів внутрішнього масиву `[0, Capacity - 1]`.
- **Інваріант циклічної узгодженості:** `(head_ + size_) % Capacity == tail_`. Позиція комірки запису `tail_` є математичним наслідком зміщення від поточної позиції читання `head_` на величину `size_` за модулем місткості `Capacity`.

## Повний вихідний код контейнера `BoundedRingBuffer`

Нижче наведено повну реалізацію контейнера з усіма контрактними специфікаціями C++26:

```cpp
#include <contracts>
#include <cstddef>
#include <concepts>
#include <utility>
#include <new>
#include <type_traits>
#include <optional>

template <typename T, std::size_t Capacity>
    requires (Capacity > 0)
class BoundedRingBuffer {
private:
    // Сире сховище для розміщення об'єктів типу T без виклику конструкторів за замовчуванням
    alignas(alignof(T)) std::byte storage_[Capacity * sizeof(T)];
    std::size_t head_{0};
    std::size_t tail_{0};
    std::size_t size_{0};

    // Допоміжні методи прямого доступу до сирої пам'яті
    [[nodiscard]] T* ptr_at(std::size_t index) noexcept
        pre: index < Capacity
        post(ptr): ptr != nullptr
    {
        return reinterpret_cast<T*>(&storage_[index * sizeof(T)]);
    }

    [[nodiscard]] const T* ptr_at(std::size_t index) const noexcept
        pre: index < Capacity
        post(ptr): ptr != nullptr
    {
        return reinterpret_cast<const T*>(&storage_[index * sizeof(T)]);
    }

public:
    // Конструктор за замовчуванням: створює порожній буфер
    constexpr BoundedRingBuffer() noexcept
        post: empty() && size() == 0 && capacity() == Capacity
    {}

    // Деструктор: знищує всі живі елементи
    ~BoundedRingBuffer() noexcept {
        clear();
    }

    // Заборона копіювання для уникнення прихованих алокацій
    BoundedRingBuffer(const BoundedRingBuffer&) = delete;
    BoundedRingBuffer& operator=(const BoundedRingBuffer&) = delete;

    // Конструктор переміщення
    BoundedRingBuffer(BoundedRingBuffer&& other) noexcept
        post: other.empty() && other.size() == 0
    {
        while (!other.empty()) {
            push(std::move(other.front()));
            other.pop();
        }
    }

    // Інформаційні методи доступу до стану
    [[nodiscard]] constexpr std::size_t size() const noexcept
        post(res): res <= Capacity
    {
        return size_;
    }

    [[nodiscard]] constexpr std::size_t capacity() const noexcept
        post(res): res == Capacity
    {
        return Capacity;
    }

    [[nodiscard]] constexpr bool empty() const noexcept
        post(res): res == (size() == 0)
    {
        return size_ == 0;
    }

    [[nodiscard]] constexpr bool full() const noexcept
        post(res): res == (size() == Capacity)
    {
        return size_ == Capacity;
    }

    // Додавання нового елемента в кінець черги (копіюванням)
    void push(const T& value)
        pre [buffer_not_full]: !full()
        post: !empty() && (size() > 0)
    {
        contract_assert [valid_tail]: tail_ < Capacity;

        ::new (static_cast<void*>(ptr_at(tail_))) T(value);
        tail_ = (tail_ + 1) % Capacity;
        ++size_;

        contract_assert [math_invariant]: (head_ + size_) % Capacity == tail_;
    }

    // Додавання нового елемента в кінець черги (переміщенням)
    void push(T&& value)
        pre [buffer_not_full]: !full()
        post: !empty() && (size() > 0)
    {
        contract_assert [valid_tail]: tail_ < Capacity;

        ::new (static_cast<void*>(ptr_at(tail_))) T(std::move(value));
        tail_ = (tail_ + 1) % Capacity;
        ++size_;

        contract_assert [math_invariant]: (head_ + size_) % Capacity == tail_;
    }

    // Видалення найстарішого елемента черги
    void pop()
        pre [buffer_not_empty]: !empty()
        post: !full()
    {
        contract_assert [valid_head]: head_ < Capacity;

        ptr_at(head_)->~T();
        head_ = (head_ + 1) % Capacity;
        --size_;

        contract_assert [math_invariant]: (head_ + size_) % Capacity == tail_;
    }

    // Доступ до найстарішого елемента
    [[nodiscard]] T& front() noexcept
        pre [buffer_not_empty]: !empty()
    {
        return *ptr_at(head_);
    }

    [[nodiscard]] const T& front() const noexcept
        pre [buffer_not_empty]: !empty()
    {
        return *ptr_at(head_);
    }

    // Доступ до останнього доданого елемента
    [[nodiscard]] T& back() noexcept
        pre [buffer_not_empty]: !empty()
    {
        std::size_t last_idx = (tail_ == 0) ? (Capacity - 1) : (tail_ - 1);
        return *ptr_at(last_idx);
    }

    [[nodiscard]] const T& back() const noexcept
        pre [buffer_not_empty]: !empty()
    {
        std::size_t last_idx = (tail_ == 0) ? (Capacity - 1) : (tail_ - 1);
        return *ptr_at(last_idx);
    }

    // Повне очищення буфера зі знищенням елементів
    void clear() noexcept
        post: empty() && size() == 0
    {
        while (!empty()) {
            pop();
        }
        head_ = 0;
        tail_ = 0;
        size_ = 0;
    }
};
```

## Детальний аналіз конструкторів, методів та контрактних меж

Розглянемо покроково функціонування кожної окремої операції нашого контейнера та роль відповідних контрактів.

### 1. Конструктор за замовчуванням та семантика переміщення
Конструктор за замовчуванням ініціалізує всі індекси нулями, залишаючи сиру пам'ять `storage_` неторканою. Його постумова:
```cpp
post: empty() && size() == 0 && capacity() == Capacity
```
Ця постумова формально декларує, що новостворений об'єкт гарантовано є порожнім, а його місткість відповідає параметру шаблону `Capacity`.

Конструктор переміщення (`move constructor`) переносить усі живі елементи з іншого буфера `other` у поточний за допомогою семантики переміщення `std::move(other.front())`. Його постумова `post: other.empty() && other.size() == 0` гарантує так званий "стан спустошення" (moved-from state): після переміщення вихідний буфер залишається повністю валідним, але абсолютно порожнім. Це унеможливлює повторне помилкове читання переміщених даних.

### 2. Захист низькорівневого доступу до сирої пам'яті (`ptr_at`)
Методи `ptr_at` виконують низькорівневе приведення типів вказівників за допомогою `reinterpret_cast`. У традиційному коді будь-яка помилка в обчисленні індексу передається в цей метод і безпосередньо призводить до читання або запису пам'яті за межами масиву або некоректного вирівнювання адреси.

У нашій реалізації метод `ptr_at` забезпечений строгою преумовою:
```cpp
pre: index < Capacity
```
Ця перевірка гарантує, що арифметичне обчислення зміщення `index * sizeof(T)` гарантовано залишається в межах статично виділеного блоку `storage_`. Постумова `post(ptr): ptr != nullptr` запевняє викликача, що отримана адреса є ненульовою і готова для розміщення об'єкта. Оскільки методи `ptr_at` є закритими (`private`), їхні контракти виступають внутрішніми інваріантами реалізації класу, захищаючи розробника контейнера від власних внутрішніх помилок.

### 3. Розподіл відповідальності через преумови `push` та `pop`
Операції додавання елементів `push` використовують іменовані преумови:
```cpp
void push(const T& value)
    pre [buffer_not_full]: !full()
```
Ця преумова чітко розмежовує зони відповідальності:
- Викликач зобов'язаний самостійно перевірити стан черги через `!buffer.full()` або знати це з архітектурного контексту (наприклад, якщо перед цим було викликано `buffer.pop()`).
- Реалізація методу `push` позбавляється від необхідності писати внутрішні перевірки `if (size_ == Capacity) return;` або генерувати винятки.

Якщо клієнт все ж порушує контракт і викликає `push` для заповненого буфера, обробник порушень фіксує мітку `buffer_not_full`. Це негайно вказує автору коду, де саме сталася помилка логіки викликача.

Аналогічно, преумова `pre [buffer_not_empty]: !empty()` для методів `pop()`, `front()` та `back()` захищає від виклику деструктора або розіменування неініціалізованої пам'яті у порожньому буфері.

### 4. Внутрішні твердження (`contract_assert`) як варта інваріантів
Всередині методів `push` та `pop` виконується модифікація стану буфера:
- переміщення циклічного індексу через формулу `(tail_ + 1) % Capacity`;
- зміна лічильника збережених елементів `size_`.

У середині цих методів розміщено інструкцію:
```cpp
contract_assert [math_invariant]: (head_ + size_) % Capacity == tail_;
```
Ця перевірка верифікує збереження інваріанта циклічної адресації безпосередньо після виконання операції. Якщо майбутній розробник під час оптимізації або рефакторингу припуститься помилки (наприклад, забуде виконати операцію взяття за модулем `% Capacity` або помилиться з інкрементом лічильника), `contract_assert` виявить математичну неузгодженість миттєво в місці здійснення помилки, не дозволяючи пошкодженому стану поширитися далі по системі.

### 5. Постумови як математичний доказ результату
Постумови виконують роль формальної специфікації поведінки методу. Наприклад, для методу `push`:
```cpp
post: !empty() && (size() > 0)
```
Це означає, що після успішного виконання додавання елемента контейнер математично не може бути порожнім, а його розмір строго більший за нуль. Викликач може повністю спиратися на цю гарантію.

Метод `clear()` забезпечений постумовою `post: empty() && size() == 0`, яка гарантує клієнтові повне очищення черги та повернення структури до початкового стану.

## Гарантії безпеки винятків (Exception Safety)

Контейнери стандартної бібліотеки зобов'язані чітко декларувати свою поведінку у випадку, якщо користувацький конструктор типу `T` згенерує виняток. Розглянемо взаємодію контрактів із гарантіями безпеки винятків у нашому кільцевому буфері:

1. **Сильна гарантія (Strong Exception Guarantee) у методі `push`:**
   У методі `push` створення об'єкта через `::new (static_cast<void*>(ptr_at(tail_))) T(value)` відбувається **до** зміни індексу `tail_` та лічильника `size_`. Якщо конструктор копіювання `T` викине виняток під час створення об'єкта в сирій пам'яті, керування негайно покине метод `push`. Оскільки змінні `tail_` та `size_` ще не були модифіковані, стан буфера залишається абсолютно ідентичним тому, яким він був до початку виклику. Всі математичні інваріанти структури зберігаються.
2. **Гарантія відсутності винятків (`nothrow guarantee`) у методах навігації:**
   Методи `front()`, `back()`, `pop()`, `size()`, `empty()`, `full()` позначені специфікатором `noexcept`. Вони виконують лише арифметичні операції над цілими числами та виклики деструкторів, які за стандартом C++ зобов'язані бути `noexcept`.
3. **Роль контрактів у винятковій безпеці:**
   Контракти C++26 не замінюють обробку винятків бізнес-логіки типу `T`, проте вони повністю виключають ситуації, коли метод викликається для невалідного стану контейнера (наприклад, спроба `pop()` над порожнім буфером). Завдяки цьому з коду видаляються всі проміжні аварійні гілки, а гарантії безпеки винятків стають простими для математичного доведення.

## Математика модульної адресації та оптимізація степенем двійки

У загальному випадку операція переходу до наступного індексу в кільцевому буфері вимагає виконання цілочисельного ділення за модулем:
```
next_index = (current_index + 1) % Capacity
```
Операція взяття залишку від ділення (`%`) на сучасних процесорах виконується за допомогою машинної інструкції `div` або `idiv`. Ця інструкція є відносно повільною і може займати від 10 до 25 тактів процесора на архітектурах x86_64 та ARM64.

Якщо розмір буфера `Capacity` є степенем двійки (тобто `Capacity = 2ⁿ`, наприклад 16, 64, 256, 1024), модульне ділення можна оптимізувати до однієї надшвидкої побітової операції `AND` (яка виконується за 1 такт):
```
next_index = (current_index + 1) & (Capacity - 1)
```

Завдяки контрактам C++26 коректність такої оптимізації можна верифікувати прямо в коді за допомогою внутрішнього твердження:
```cpp
contract_assert [bitwise_eq_modulo]: ((tail_ + 1) & (Capacity - 1)) == ((tail_ + 1) % Capacity);
```
У режимі налагодження компілятор перевірить еквівалентність обох виразів, а в режимі `ignore` згенерує лише швидку побітову інструкцію `and`.

## Апаратне вирівнювання кеш-ліній та захист від хибного розділення (False Sharing)

У багатопотокових обчислювальних конвеєрах (конвеєри обробки мережевих пакетів 100 GbE, аудіо-рушії низької затримки) важливу роль відіграє топологія кеш-пам'яті процесора. Розмір стандартної кеш-лінії в процесорах архітектур x86-64 та ARM Cortex-A становить 64 байти.

Якщо змінні `head_` та `tail_` розташовані поруч в одному 64-байтовому блоці пам'яті, спроба одного ядра процесора модифікувати `tail_` призведе до інвалідації всієї кеш-лінії на ядрі, яке зчитує `head_`. Це явище відоме як хибне розділення (false sharing) і може знизити пропускну здатність передавання даних у 10–20 разів.

Для запобігання цьому явищу в багатопотокових модифікаціях черги поля `head_` та `tail_` розносять по різних кеш-лініях за допомогою специфікатора вирівнювання:
```cpp
alignas(64) std::size_t head_{0};
alignas(64) std::size_t tail_{0};
```
Контракти C++26 дозволяють формально зафіксувати ці апаратні вимоги на рівні тверджень:
```cpp
contract_assert [cache_line_aligned]: (reinterpret_cast<std::uintptr_t>(&head_) % 64) == 0;
```

## Багатопотокові конвеєри (SPSC) та межі застосування контрактів

Кільцеві буфери є фундаментом для реалізації неблокуючих черг між одним потоком-виробником та одним потоком-споживачем (Single Producer Single Consumer, SPSC lock-free queue). У таких чергах індекси `head_` та `tail_` стають атомарними змінними (`std::atomic<std::size_t>`).

Важливо чітко розуміти межу між контрактами мови та синхронізацією пам'яті:
- **Контракти C++26** перевіряють логічну валідність значень змінних у поточній точці виконання одного потоку. Вони відповідають на питання: "Чи коректний цей індекс?".
- **Атомарні операції та бар'єри пам'яті (`std::memory_order_acquire` / `std::memory_order_release`)** відповідають за видимість змін між різними ядрами процесора та узгодженість кешів (cache coherence).

Контракти не можуть замінити бар'єри пам'яті, проте вони дозволяють перевіряти локальні інваріанти кожного окремого потоку: наприклад, що виробник ніколи не пересуває `tail_` далі, ніж дозволяє кешоване значення `head_`.

## Порівняння підходів у мовах програмування: C++, Rust, Ada, Eiffel

Проблема забезпечення коректності стану контейнерів вирішується по-різному в провідних мовах програмування:
- **Eiffel:** Батьківщина концепції DbC. Контракти є динамічними за замовчуванням і перевіряються через рантайм-перехоплювачі, з повною підтримкою інваріантів класів на рівні синтаксису мови.
- **Ada (Ada 2012):** Аспекти `Pre`, `Post` та `Type_Invariant` вбудовані в сигнатури пакетів. Статичний верифікатор SPARK дозволяє математично доводити відсутність порушень контрактів ще до компіляції.
- **Rust:** Покладається на систему типів (Type State Pattern) та макроси `debug_assert!`. Замість преумов `!empty()` Rust часто змушує повертати `Option<T>`, що вимагає розпакування на рівні мови.
- **C++26:** Пропонує найбільш гнучкий компроміс: повноцінна контрактна мова на рівні сигнатур із можливістю гнучкого вибору семантики (`ignore` для максимальної продуктивності, `observe` для аудиту та `enforce` для критичної безпеки).

## Інтеграція користувацького обробника для аудиту та телеметрії

У реальних вбудованих та розподілених системах порушення контракту часто вимагає не просто аварійної зупинки процесу, а й запису повного діагностичного звіту у постійну пам'ять або системний журнал телеметрії.

Нижче наведено приклад інтеграції надійного глобального обробника порушень, який працює без динамічних алокацій пам'яті (щоб гарантувати безпеку в критичних збоях) і реєструє метадані збою:

```cpp
#include <contracts>
#include <cstdio>
#include <array>

// Структура для статичного збереження телеметрії збою без використання купи
struct CrashReport {
    const char* file{nullptr};
    std::uint32_t line{0};
    const char* function{nullptr};
    const char* comment{nullptr};
    const char* predicate{nullptr};
    const char* kind{nullptr};
};

inline std::array<CrashReport, 16> g_crash_log{};
inline std::size_t g_crash_count{0};

void handle_contract_violation(const std::contracts::contract_violation& v) noexcept {
    static thread_local bool in_violation_handler = false;
    if (in_violation_handler) {
        // Захист від нескінченної рекурсії у разі повторного збою
        return;
    }
    in_violation_handler = true;

    const char* kind_str = "ASSERTION";
    if (v.kind() == std::contracts::contract_kind::pre) {
        kind_str = "PRECONDITION";
    } else if (v.kind() == std::contracts::contract_kind::post) {
        kind_str = "POSTCONDITION";
    }

    if (g_crash_count < g_crash_log.size()) {
        g_crash_log[g_crash_count++] = CrashReport{
            .file = v.file_name(),
            .line = static_cast<std::uint32_t>(v.line_number()),
            .function = v.function_name(),
            .comment = v.comment(),
            .predicate = v.predicate(),
            .kind = kind_str
        };
    }

    std::fprintf(stderr,
        "==========================================================\n"
        "[SAFETY AUDIT] ПОРУШЕННЯ КОНТРАКТУ В СИСТЕМІ РЕАЛЬНОГО ЧАСУ\n"
        "  Категорія:  %s\n"
        "  Файл:       %s:%u\n"
        "  Функція:    %s\n"
        "  Мітка:      %s\n"
        "  Предикат:   %s\n"
        "==========================================================\n",
        kind_str,
        v.file_name(),
        static_cast<unsigned int>(v.line_number()),
        v.function_name(),
        v.comment()[0] != '\0' ? v.comment() : "<без мітки>",
        v.predicate()
    );

    in_violation_handler = false;
}
```

## Комплексний тестовий стенд

Створимо тестову програму для перевірки всіх режимів функціонування кільцевого буфера, включаючи підтримку типів, які підтримують лише семантику переміщення (move-only types), та симуляцію збоїв.

```cpp
#include <iostream>
#include <cassert>
#include <string>

// Некопійований тип даних для перевірки коректності семантики переміщення
struct SensorPayload {
    int sensor_id{0};
    std::string data;

    SensorPayload(int id, std::string d) : sensor_id(id), data(std::move(d)) {}
    SensorPayload(const SensorPayload&) = delete;
    SensorPayload& operator=(const SensorPayload&) = delete;
    SensorPayload(SensorPayload&&) noexcept = default;
    SensorPayload& operator=(SensorPayload&&) noexcept = default;
    ~SensorPayload() = default;
};

void run_basic_lifecycle_tests() {
    std::cout << "[ТЕСТ 1] Перевірка життєвого циклу цілочисельного буфера...\n";
    BoundedRingBuffer<int, 3> q;

    assert(q.empty());
    assert(q.size() == 0);
    assert(q.capacity() == 3);

    q.push(10);
    q.push(20);
    assert(q.size() == 2);
    assert(q.front() == 10);
    assert(q.back() == 20);

    q.push(30);
    assert(q.full());
    assert(q.size() == 3);

    q.pop(); // Видаляємо 10
    assert(!q.full());
    assert(q.size() == 2);
    assert(q.front() == 20);

    q.push(40); // Циклічний перехід хвоста через нульовий індекс
    assert(q.full());
    assert(q.back() == 40);

    q.clear();
    assert(q.empty());
    assert(q.size() == 0);
    std::cout << "  -> Життєвий цикл перевірено успішно.\n";
}

void run_move_semantics_tests() {
    std::cout << "[ТЕСТ 2] Перевірка роботи з move-only об'єктами...\n";
    BoundedRingBuffer<SensorPayload, 2> sensor_queue;

    sensor_queue.push(SensorPayload(101, "Telemetry_GPS_OK"));
    sensor_queue.push(SensorPayload(102, "Telemetry_IMU_OK"));

    assert(sensor_queue.full());
    assert(sensor_queue.front().sensor_id == 101);

    SensorPayload payload = std::move(sensor_queue.front());
    sensor_queue.pop();

    assert(payload.sensor_id == 101);
    assert(payload.data == "Telemetry_GPS_OK");
    assert(sensor_queue.size() == 1);
    std::cout << "  -> Семантику переміщення перевірено успішно.\n";
}

void run_simulated_contract_check() {
    std::cout << "[ТЕСТ 3] Симуляція контрактного контролю на межі місткості...\n";
    BoundedRingBuffer<int, 2> test_q;
    test_q.push(1);
    test_q.push(2);

    // У режимі збирання observe наступна операція викличе handle_contract_violation,
    // зафіксує запис у g_crash_log і дозволить програмі продовжити роботу.
    // У режимі збирання enforce виклик призведе до std::terminate().
    std::cout << "  Буфер заповнено. Спроба push(3) перевіряє pre [buffer_not_full].\n";
    // test_q.push(3); // Розкоментувати для активації збою
}

int main() {
    std::cout << "=====================================================\n";
    std::cout << "  Тестування BoundedRingBuffer з контрактами C++26   \n";
    std::cout << "=====================================================\n";

    run_basic_lifecycle_tests();
    run_move_semantics_tests();
    run_simulated_contract_check();

    std::cout << "Усі тести завершено успішно.\n";
    return 0;
}
```

## Інженерні висновки та порівняльний аналіз

Реалізація кільцевого буфера за допомогою контрактів C++26 демонструє кілька фундаментальних переваг перед класичними підходами:

1. **Самодокументований інтерфейс без розмивання коду:** Усі обмеження на аргументи зафіксовані прямо в деклараторі функцій. Компілятор, інструменти автоматичної генерації документації та статичні аналізатори бачать контракти без потреби в розборі текстових коментарів.
2. **Семантична чистота алгоритмів:** Тіла функцій звільняються від розгалужених захисних перевірок та обробки штучних статус-кодів. Код містить виключно цільову логіку переміщення вказівників та виклику деструкторів.
3. **Нульова вартість у релізі (`ignore`):** Завдяки відокремленню перевірок від коду бізнес-логіки компілятор може повністю вимкнути генерацію коду контрактів у релізній збірці, забезпечуючи максимальну продуктивність для систем реального часу.
4. **Гнучкість аудиту (`observe` проти `enforce`):** Можливість перемикання між реєстрацією в телеметричний журнал та миттєвою аварійною зупинкою дає змогу безпечно тестувати інтеграцію модулів на стендах без раптових падінь процесу.
5. **Машинна оптимізація коду:** Оскільки контракти не викидають винятків всередині бізнес-логіки, компілятор може вільно векторизувати цикли та застосовувати агресивний інлайнінг функцій.
