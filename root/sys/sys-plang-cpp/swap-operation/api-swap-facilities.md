# 📋 Засоби обміну зі стандартної бібліотеки: сигнатури, `noexcept`, складність

Довідник відповідає на одне питання про кожен засіб обміну: **що саме буде викликано, чого це коштує і за яких умов воно не кине**. Нижче точні сигнатури з обмеженнями, повні умови `noexcept`, складність, риси типів для перевірки свого типу й окремий розділ про контейнери — де обмін має власні застереження щодо алокаторів та ітераторів. Формулювання звірені з чинним робочим проєктом стандарту; біля кожного засобу вказано, з якої версії він доступний.

## Чим спитати обмін

| Запис | Заголовок | Серед чого обирає компілятор |
|---|---|---|
| `using std::swap; swap(a, b);` | `<utility>` | два шаблони `std::swap` **плюс** усе, що дає ADL за типами аргументів |
| `std::ranges::swap(a, b);` | `<concepts>` (C++20) | те саме, але пошук робить сам об'єкт-точка налаштування |
| `a.swap(b);` | заголовок самого типу | рівно член цього типу, жодного пошуку |
| `std::swap(a, b);` | `<utility>` | **лише** шаблон зі `std`, хай би що мав тип |

## `std::swap`: два шаблони з `<utility>`

```cpp
template<class T>
constexpr void swap(T& a, T& b)
    noexcept(is_nothrow_move_constructible_v<T> && is_nothrow_move_assignable_v<T>);
// Обмеження: is_move_constructible_v<T> && is_move_assignable_v<T>
// Дія: обмінює значення; складність — стала (три переміщення)

template<class T, size_t N>
constexpr void swap(T (&a)[N], T (&b)[N]) noexcept(is_nothrow_swappable_v<T>);
// Обмеження: is_swappable_v<T>
// Дія: як swap_ranges(a, a + N, b); складність — рівно N обмінів
```

Слово «обмеження» тут має точний зміст: коли умова хибна, шаблон **тихо випадає з набору кандидатів** замість давати помилку в глибині бібліотеки. Саме тому в узагальненому коді на `std::swap` можна спиратися як на запасний варіант: для типу, який не переміщується, він просто не заважає.

| Версія | Що змінилося в цих шаблонах |
|---|---|
| C++98 | обмін із трьох **копій**; ні `noexcept`, ні обмежень |
| C++11 | три **переміщення**; додано умовний `noexcept`; додано перевантаження для масивів |
| C++17 | додано обмеження (`Constraints`) — обидва шаблони стали дружніми до SFINAE |
| C++20 | обидва стали `constexpr` |

## `std::ranges::swap`: точка налаштування

Це не функція, а об'єкт із заголовка `<concepts>` (C++20), який виконує пошук усередині себе — тому виклик пишеться кваліфіковано й перехопити його стороннім перевантаженням не можна. Про [спільний механізм таких об'єктів](root:sys-plang-cpp/customization-points) — як CPO ховає пошук за одним викликом і чому це надійніше за два рядки в тілі алгоритму — розказано окремо.

Вираз `std::ranges::swap(E1, E2)` розкривається в перший придатний рядок:

| № | Умова | Що виконується | `noexcept`, якщо |
|---|---|---|---|
| 1 | `E1` або `E2` має тип класу чи перелічення, і виклик `swap(E1, E2)` дійсний | цей знайдений обмін | не кидає знайдений обмін |
| 2 | обидва — lvalue масивів однакового розміру | `ranges::swap_ranges(E1, E2)` | не кидає обмін елемента |
| 3 | обидва — lvalue того самого `T`, що моделює `move_constructible` й `assignable_from<T&, T>` | три переміщення | `is_nothrow_move_constructible_v<T> && is_nothrow_move_assignable_v<T>` |
| — | жодна з умов | вираз **некоректний** — помилка компіляції | — |

Крок 1 працює в контексті, куди спеціально вкинуто «отруйну пігулку»:

```cpp
template<class T> void swap(T&, T&) = delete;
```

Вона відсікає необмежені саморобні шаблони `swap`, які інакше підхопили б будь-яку пару аргументів: якщо перемогла пігулка, крок 1 не спрацював і розгляд іде далі. Тому власний обмін мусить бути або нешаблонним, або обмеженим під свій тип.

## Риси й концепти: як спитати наперед

| Засіб | Заголовок · версія | Питання |
|---|---|---|
| `std::is_swappable_v<T>` | `<type_traits>` · C++17 | чи обміняються два `T&` |
| `std::is_swappable_with_v<T, U>` | `<type_traits>` · C++17 | те саме для різних типів (аргументи беруться як є, не як посилання) |
| `std::is_nothrow_swappable_v<T>` | `<type_traits>` · C++17 | і чи обіцяє той обмін не кидати |
| `std::is_nothrow_swappable_with_v<T, U>` | `<type_traits>` · C++17 | те саме для різних типів |
| `std::swappable<T>` | `<concepts>` · C++20 | чи дійсний `ranges::swap(a, b)` |
| `std::swappable_with<T, U>` | `<concepts>` · C++20 | те саме в обидва боки плюс спільне посилання |

Головне про ці риси: вони перевіряють **некваліфікований** виклик у контексті, де видимі обидва шаблони `std::swap`, — тобто рівно той двокроковий запис, яким користується узагальнений код. Тому `is_nothrow_swappable_v<T>` — правильне питання, а `is_nothrow_move_constructible_v<T>` — ні: власний обмін типу може обіцяти більше, ніж його переміщення. Загальні правила таких перевірок — у [рисах типів](root:sys-plang-cpp/type-traits): це шаблони, що обчислюють відповідь про тип під час компіляції й дають її як `constexpr`-значення.

Застереження одне: риса дивиться лише на безпосередній контекст виразу. Якщо помилка чигає глибше — у тілі інстанціювання, — риса поверне `true`, а компіляція все одно впаде.

```cpp
#include <concepts>
#include <type_traits>

namespace geo {
struct Path;
void swap(Path&, Path&) noexcept;
}

static_assert(std::is_swappable_v<geo::Path>);          // обмін узагалі можливий
static_assert(std::is_nothrow_swappable_v<geo::Path>);  // і він не кидає
static_assert(std::swappable<geo::Path>);               // те саме через ranges::swap
```

## Обмін через ітератори

| Засіб | Версія | Повертає | Складність |
|---|---|---|---|
| `swap_ranges(first1, last1, first2)` | C++98 (`constexpr` з C++20) | ітератор за останнім обміняним у другому діапазоні | рівно `M` обмінів |
| `swap_ranges(policy, …)` | C++17 | те саме | те саме, дозволено паралельно |
| `ranges::swap_ranges(r1, r2)` | C++20 | `{first1 + M, first2 + M}` | рівно `M` обмінів, `M = min` довжин |
| `iter_swap(a, b)` | C++98 (`constexpr` з C++20) | `void` | один обмін |
| `ranges::iter_swap(a, b)` | C++20 | `void` | один обмін |

`std::iter_swap(a, b)` виконує `swap(*a, *b)` тим самим двокроковим пошуком, а `std::swap_ranges` — `M` таких обмінів поспіль; передумова обох діапазонів — **не перетинатися**.

Різниця варта уваги лише для ітераторів із проксі-посиланням: `*it` у `std::vector<bool>` повертає не `bool&`, а тимчасовий об'єкт-посередник, і звичайний обмін двох тимчасових об'єктів нічого б не змінив у контейнері. `std::ranges::iter_swap` уміє впоратися й тут — він будується на `ranges::iter_move` і присвоєннях, а не на посиланнях; сам же `vector<bool>` окремо постачає обмін для свого посередника (донедавна — статичним членом, у чинному проєкті — функціями-друзями), тож `swap(v[0], v[1])` робить те, що ви й хотіли.

## `std::exchange` — сусід, який робить не те саме

```cpp
template<class T, class U = T>
constexpr T exchange(T& obj, U&& new_val)
    noexcept(is_nothrow_move_constructible_v<T> && is_nothrow_assignable_v<T&, U>);
// Дія: забрати старе значення obj, покласти туди new_val, повернути старе
```

C++14; `constexpr` з C++20; умовний `noexcept` — з C++23 (папір P2401R0, ухвалений як виправлення дефекту, тож реалізації дають його й у старших режимах мови).

Обмін лишає джерелу колишнє значення адресата — це добре, коли обидва значення потрібні. `exchange` лишає джерелу значення, яке ви назвали самі, — це те, що потрібно в тілі переміщувального конструктора: `head_(std::exchange(other.head_, nullptr))` і забирає нутрощі, і одразу приводить джерело до відомого порожнього стану.

## Контейнери: складність, `noexcept`, алокатори

Умова `noexcept` у члена `swap` має три форми (у теперішньому вигляді — з C++17); вільна функція `swap(a, b)` для кожного контейнера означена як `a.swap(b)`, тож усе сказане стосується й її.

```cpp
// A — послідовні контейнери й рядок
noexcept(allocator_traits<Allocator>::propagate_on_container_swap::value ||
         allocator_traits<Allocator>::is_always_equal::value)

// B — впорядковані асоціативні
noexcept(allocator_traits<Allocator>::is_always_equal::value &&
         is_nothrow_swappable_v<Compare>)

// C — невпорядковані
noexcept(allocator_traits<Allocator>::is_always_equal::value &&
         is_nothrow_swappable_v<Hash> && is_nothrow_swappable_v<Pred>)
```

| Контейнер | Форма умови | Складність |
|---|---|---|
| `vector`, `deque`, `list`, `forward_list`, `vector<bool>`, `basic_string` | A | стала |
| `set`, `multiset`, `map`, `multimap` | B | стала |
| `unordered_set`, `unordered_map` і їхні `multi`-родичі | C | стала |
| `stack`, `queue` | `is_nothrow_swappable_v<Container>` | як в основи |
| `priority_queue` | `is_nothrow_swappable_v<Container> && is_nothrow_swappable_v<Compare>` | як в основи |
| `array` | `is_nothrow_swappable_v<T>` | **лінійна**: `N` обмінів |

Три правила, які випливають із цих сигнатур і які варто тримати в голові разом.

**Алокатори.** Коли `propagate_on_container_swap` хибне — а в `std::allocator` воно саме таке, — алокатори **не обмінюються**, і поведінка невизначена, якщо `a.get_allocator() != b.get_allocator()`. Зі стандартним алокатором питання не виникає: `is_always_equal` істинне, усі його примірники рівні. Виникає воно з [власним алокатором](root:sys-plang-cpp/custom-allocators) — типом, що постачає контейнерові пам'ять зі своєї арени: два контейнери з різними аренами обміняти не можна, бо кожен потім звільнятиме чужий блок своїм алокатором.

**Ітератори й посилання.** Жоден обмін контейнерів їх не псує: ітератор, що вказував на елемент, після обміну вказує на **той самий елемент — уже в другому контейнері**. Виняток — `end()`: він ні на що не вказує, тож чи стане `a.end()` після обміну значенням `b.end()`, не визначено. Решта випадків, коли ітератор втрачає силу, зібрана в [інвалідації ітераторів](root:sys-plang-cpp/iterator-invalidation) — там про перерозподіл буфера й видалення елементів.

**`array` — інший в усьому.** Стандарт прямо це зазначає: на відміну від обміну решти контейнерів, `array::swap` займає лінійний час, **може вийти через виняток** і **не переводить ітератори до другого контейнера**. Ітератор на `a[0]` після обміну вказує на `a[0]` — просто значення там уже інше.

## Типи, що вже мають свій обмін

Для них писати нічого не треба — досить некваліфікованого виклику або `a.swap(b)`.

| Тип | Умова `noexcept` члена `swap` |
|---|---|
| `unique_ptr`, `shared_ptr`, `weak_ptr` | безумовно `noexcept` |
| `function`, `move_only_function`, `any` | безумовно `noexcept` |
| `thread`, `jthread`, `unique_lock`, `shared_lock`, `promise`, `packaged_task` | безумовно `noexcept` |
| `filesystem::path` | безумовно `noexcept` |
| `pair<T1, T2>` | `is_nothrow_swappable_v<T1> && is_nothrow_swappable_v<T2>` |
| `tuple<Types…>` | кон'юнкція `is_nothrow_swappable_v<Ti>` |
| `optional<T>` | `is_nothrow_move_constructible_v<T> && is_nothrow_swappable_v<T>` |
| `variant<Types…>` | кон'юнкція `is_nothrow_move_constructible_v<Ti> && is_nothrow_swappable_v<Ti>` |

Закономірність тут читається одразу: безумовне `noexcept` мають ті, чиє представлення — самі лише вказівники й дескриптори; умовне — ті, що тримають чужі значення всередині себе й тому можуть лише переказати обіцянку далі.
