# ⚙️ Лабораторія пошуку імен: п'ять програм, які кажуть, кого викликали насправді

Про пошук імен важко сперечатися вголос, бо його наслідки невидимі: у тексті стоїть `swap(a, b)`, а який саме `swap` виконався — з тексту не видно. Цей файл робить наслідки видимими найпростішим способом: **кожен кандидат сам називає себе**, коли його викликали. Далі лишається дивитися на вивід і не гадати.

## Умова

П'ять запитань, на які лабораторія відповідає роздруком, а не міркуванням:

1. Чому `operator<<`, який ви точно написали, компілятор «не бачить» — і чому `using namespace` рятує тільки в одному місці з двох.
2. Коли функція з чужої бібліотеки, якої ви не згадували на ім'я, перемагає вашу власну — і чому додавання одного `const` в аргументі змінює переможця.
3. Скільки насправді коштує `std::swap(a, b)` замість двокроку `using std::swap; swap(a, b)` — у переміщеннях.
4. Чи справді прихованого друга не видно нікому, крім ADL, — і що це дає.
5. Чим ADL вимикають і що після цього викликається.

Складність тут одна, зате принципова: **більшість цих подій — це вибір, а не дія**. Компілятор ухвалює рішення й нічого про нього не повідомляє; успішна програма виглядає однаково незалежно від того, вгадали ви переможця чи ні.

## Ідея

Інструмент вимірювання складається з двох частин. Перша — **самопідпис**: кожна функція-кандидат друкує власне повне ім'я, а шаблон додає ще й те, у що звівся його параметр. Тому в протоколі стоїть не «щось спрацювало», а конкретний рядок вихідного коду.

Друга частина потрібна там, де кандидати друкувати не можуть, — усередині `std::swap`. Там міряємо не ім'я, а **слід**: лічильники переміщень і власних обмінів. Загальний алгоритм робить три переміщення, спеціалізований — жодного, тож числа розрізняють їх однозначно.

Третя обставина — не інструмент, а обмеження: три з цікавих випадків **не збираються**. Їх винесено під `#ifdef SHOW_ERRORS`, і результатом досліду є текст відмови компілятора.

## Каркас

```cpp
// adl-lab.cpp — лабораторія пошуку імен. C++20, жодних залежностей.
#include <concepts>
#include <iostream>
#include <string>
#include <string_view>
#include <type_traits>
#include <utility>
#include <vector>

void head(std::string_view t) { std::cout << "\n──  " << t << "  ──\n"; }
void ask (std::string_view t) { std::cout << "    " << t << "  →  "; }
void say (std::string_view t) { std::cout << t << '\n'; }

namespace lib {                       // чужа бібліотека, яку ми не редагуємо

struct Widget { int id = 0; };
struct Point  { int x = 0, y = 0; };

struct Pixel {
    int x = 0, y = 0;
    friend std::ostream& operator<<(std::ostream& os, const Pixel& p) {   // прихований друг
        return os << '[' << p.x << ", " << p.y << ']';
    }
};

// «зручність», покладена у ЗОВНІШНІЙ простір бібліотеки
template <class T>
void trace(T&& v) {
    (void)v;
    std::cout << "lib::trace<T&&> (загальний шаблон), T&& звівся до "
              << (std::is_const_v<std::remove_reference_t<T>> ? "const&" : "&") << '\n';
}

void onlyAdl(const Widget&) { say("lib::onlyAdl — інакше її не дістати"); }

}  // namespace lib

namespace app {                       // наш код

std::ostream& operator<<(std::ostream& os, const lib::Point& p) {   // ← оператор не в тому просторі
    return os << '(' << p.x << ", " << p.y << ')';
}

void trace(const lib::Widget&) { say("app::trace(const Widget&) — наш, спеціальний"); }

}  // namespace app

namespace util {                      // третій простір: узагальнений друкар
template <class T>
void dump(std::string_view label, const T& v) {
    std::cout << "    " << label << "  →  " << v << '\n';
}
}
```

## Дослід 1: оператор, покладений не в той простір

```cpp
void part_operator() {
    head("1. Оператор, покладений не в той простір");

    lib::Point p{1, 2};
    lib::Pixel q{3, 4};

    {
        using namespace app;                        // діє лише в цих дужках
        ask("std::cout << p");  std::cout << p << '\n';
    }
    ask("std::cout << q");  std::cout << q << '\n';

    util::dump("util::dump(q) — крізь шаблон", q);
    // util::dump("util::dump(p)", p);              // НЕ збирається, див. -DSHOW_ERRORS
}
```

```
──  1. Оператор, покладений не в той простір  ──
    std::cout << p  →  (1, 2)
    std::cout << q  →  [3, 4]
    util::dump(q) — крізь шаблон  →  [3, 4]
```

Три рядки, і в них увесь сюжет. `p` виводиться лише тому, що директива `using` втягнула `app` у видимість цього блоку — тобто спрацював **звичайний** пошук, а не ADL: типи `std::ostream` і `lib::Point` асоціюють простори `std` і `lib`, і в жодному з них потрібного оператора немає.

Дальший рядок пояснює, чому ця «латка» — не полагодження. У `util::dump` вираз `os << v` залежить від параметра шаблону, тому вдруге його розв'язують у точці інстанціювання, і на цьому кроці працює **тільки ADL** — жодних директив `using` із чужих функцій він не бачить, хоч би де вони стояли. Для `q` це не біда: `operator<<` оголошено другом усередині `Pixel`, отже, він лежить у самому асоційованому класі. Для `p` виклик не збирається взагалі. Механіка цього роздвоєння — у темі [двофазний пошук імен у шаблонах](root:sys-plang-cpp/two-phase-name-lookup).

Полагодити можна тільки одним способом — **перенести оператор туди, де живе тип**: у `lib` або, ще краще, у тіло `Point` як `friend`. Тоді працюють обидва місця й будь-який чужий шаблон на додачу.

## Дослід 2: ADL-кандидат перемагає локально видимого

```cpp
namespace app {
void part_overload() {
    head("2. ADL-кандидат перемагає локально видимого");

    lib::Widget       w{7};
    const lib::Widget frozen{8};

    ask("trace(w)       ");  trace(w);
    ask("trace(frozen)  ");  trace(frozen);
    ask("(trace)(w)     ");  (trace)(w);
    ask("app::trace(w)  ");  app::trace(w);
}
}
```

```
──  2. ADL-кандидат перемагає локально видимого  ──
    trace(w)         →  lib::trace<T&&> (загальний шаблон), T&& звівся до &
    trace(frozen)    →  app::trace(const Widget&) — наш, спеціальний
    (trace)(w)       →  app::trace(const Widget&) — наш, спеціальний
    app::trace(w)    →  app::trace(const Widget&) — наш, спеціальний
```

Перші два рядки — найдорожчий урок цієї лабораторії: **один і той самий виклик пішов у різні функції, і різницю зробив лише `const` на аргументі**.

Кандидатів щоразу двоє. Звичайний пошук зупиняється в `app` і дає `app::trace(const Widget&)`; ADL додає `lib::trace`, бо тип аргументу живе в `lib`. Для змінного `w` шаблон із [універсальним посиланням](root:sys-plang-cpp/perfect-forwarding) `T&&` зводиться до параметра `Widget&`, наша функція бере `const Widget&` — обидва зв'язування мають ранг точного збігу, і нічию розсуджує окреме правило: коли посилання дивляться на той самий тип і різняться лише верхнім `const`, кращим є **менш кваліфіковане** зв'язування. Виграє `lib::trace`. Для `frozen` параметри стають однаковими, нічия доходить до наступного правила — «не-шаблон кращий за спеціалізацію шаблону», — і виграє наша. Порядок цих правил розібрано в [розв'язанні перевантажень](root:sys-plang-cpp/overload-resolution).

Найгірше в цій пастці те, що збірка мовчить: обидві функції існують, обидві приймають `Widget`, програма просто робить не те. І писала її не одна людина — `lib::trace` міг з'явитися в бібліотеці на пів року пізніше за наш код.

Ліки з двох боків. Автор `lib` не має класти надто загальний шаблон у зовнішній простір: місце такої допоміжної функції — у вкладеному `detail`, куди ADL не дістає. Ми зі свого боку захищаємося кваліфікацією або дужками — два останні рядки протоколу показують, що обидва прийоми повертають виклик нашій функції.

## Дослід 3: двокрок проти кваліфікованого виклику

```cpp
namespace img {

inline int moveCount = 0;
inline int swapCount = 0;

class Buffer {
public:
    Buffer(std::string tag, std::size_t n)
        : tag_(std::move(tag)), data_(new int[n]), size_(n) {}
    ~Buffer() { delete[] data_; }

    Buffer(const Buffer&)            = delete;
    Buffer& operator=(const Buffer&) = delete;

    Buffer(Buffer&& o) noexcept
        : tag_(std::move(o.tag_)), data_(o.data_), size_(o.size_) {
        o.data_ = nullptr; o.size_ = 0; ++moveCount;
    }
    Buffer& operator=(Buffer&& o) noexcept {
        if (this == &o) return *this;
        delete[] data_;
        tag_ = std::move(o.tag_); data_ = o.data_; size_ = o.size_;
        o.data_ = nullptr; o.size_ = 0; ++moveCount;
        return *this;
    }

    friend void swap(Buffer& a, Buffer& b) noexcept {      // прихований друг
        std::swap(a.tag_,  b.tag_);
        std::swap(a.data_, b.data_);
        std::swap(a.size_, b.size_);
        ++swapCount;
    }

    const std::string& tag() const { return tag_; }

private:
    std::string tag_;
    int*        data_ = nullptr;
    std::size_t size_ = 0;
};

}  // namespace img

template <class T> void twoStep  (T& a, T& b) { using std::swap; swap(a, b); }
template <class T> void qualified(T& a, T& b) { std::swap(a, b); }
template <class T> void viaCpo   (T& a, T& b) { std::ranges::swap(a, b); }

void report(std::string_view what, int m0, int s0) {
    std::cout << "    " << what << "  →  переміщень Buffer: " << img::moveCount - m0
              << ",  власний swap: " << img::swapCount - s0 << '\n';
}

void part_swap() {
    head("3. Двокрок проти кваліфікованого виклику");

    img::Buffer a("кадр-A", 1024), b("кадр-B", 1024);
    int m, s;

    m = img::moveCount; s = img::swapCount;
    twoStep(a, b);    report("using std::swap; swap(a, b)", m, s);

    m = img::moveCount; s = img::swapCount;
    qualified(a, b);  report("std::swap(a, b)            ", m, s);

    m = img::moveCount; s = img::swapCount;
    viaCpo(a, b);     report("std::ranges::swap(a, b)    ", m, s);

    std::cout << "    у a лежить «" << a.tag() << "», у b — «" << b.tag() << "»\n";
}
```

```
──  3. Двокрок проти кваліфікованого виклику  ──
    using std::swap; swap(a, b)  →  переміщень Buffer: 0,  власний swap: 1
    std::swap(a, b)              →  переміщень Buffer: 3,  власний swap: 0
    std::ranges::swap(a, b)      →  переміщень Buffer: 0,  власний swap: 1
    у a лежить «кадр-B», у b — «кадр-A»
```

Три рядки роблять те саме, і всі три «працюють» — різниця лише в ціні. Двокрок дав нуль переміщень: оголошення `using std::swap` кладе загальний алгоритм у множину кандидатів запасним варіантом, ADL додає туди `img::swap`, і не-шаблон виграє в шаблону. Кваліфікований виклик вимкнув ADL, лишив одного кандидата — і той чесно зробив те, що вміє: тимчасовий об'єкт плюс два присвоєння, три переміщення на порожньому місці. Ціна цих переміщень зростає разом із типом; для буфера з [власним володінням пам'яттю](root:sys-plang-cpp/move-semantics) це три зайві оновлення трьох полів, для типу з дорожчим переміщенням — більше.

Третій рядок цікавий тим, що виглядає **як кваліфікований, а поводиться як двокрок**. Причина в тому, що `std::ranges::swap` — не функція, а об'єкт із `operator()`, і цей оператор усередині виконує двокрок за нас. Тобто те саме правило «звичайний пошук знайшов не функцію → ADL мовчить» тут не заважає, а працює: жоден сторонній `swap` не перехопить сам виклик, зате всередині об'єкт свідомо шукає ваш через ADL. Це загальний прийом стандартної бібліотеки — [точки налаштування й CPO](root:sys-plang-cpp/customization-points); докладніше про сам обмін — у темі [обміну значеннями](root:sys-plang-cpp/swap-operation).

## Дослід 4: прихованого друга не видно нікому, крім ADL

```cpp
void part_hidden() {
    head("4. Прихований друг і множина кандидатів");

    img::Buffer a("а", 8), b("б", 8);
    const int s = img::swapCount;
    swap(a, b);                       // жодного `swap` у видимості — і все одно працює
    std::cout << "    голий swap(a, b) у глобальній області  →  власний swap: "
              << img::swapCount - s << '\n';

    std::vector<lib::Widget> box(2);
    ask("trace(box) // box — std::vector<lib::Widget>");  trace(box);
}
```

```
──  4. Прихований друг і множина кандидатів  ──
    голий swap(a, b) у глобальній області  →  власний swap: 1
    trace(box) // box — std::vector<lib::Widget>  →  lib::trace<T&&> (загальний шаблон), T&& звівся до &
```

Перший рядок — доказ від протилежного. У глобальній області немає ані оголошення `swap`, ані директиви `using`; єдиний спосіб, яким компілятор міг знайти цю функцію, — асоціювати простір `img` через тип аргументу. Що ім'я справді не існує ніде більше, показують дві відмови нижче: ні `img::swap(a, b)`, ні `using img::swap;` не збираються.

Другий рядок показує зворотний бік. `lib::trace` лежить у просторі як звичайна функція — і тому потрапляє в множину кандидатів навіть тут, де про `lib` нема й згадки: `std::vector<lib::Widget>` асоціює і `std`, і `lib`, бо спеціалізація шаблону тягне за собою простори своїх типових аргументів. Був би `trace` прихованим другом `Widget`, цей виклик просто не зібрався б — і чесна відмова була б кращим результатом, ніж мовчазний виклик функції, написаної не для векторів.

> 🔧 **Навіщо це.** Різниця між двома рядками протоколу — це різниця між «функцію видно рівно тоді, коли її просять» і «функцію видно завжди, коли поблизу пробігав наш тип». Друге коштує не лише випадковими перехопленнями: кожен такий кандидат компілятор перевіряє на придатність у кожному виклику з відповідним іменем, а коли виклик не складається — вивалює весь перелік у повідомлення про помилку. Практичне правило одне: оператори й функції-точки налаштування — прихованими друзями, узагальнені помічники — у вкладений `detail`.

## Дослід 5: три вимикачі

```cpp
namespace guard {
inline constexpr struct TraceFn {
    void operator()(const lib::Widget&) const {
        std::cout << "guard::trace — це ОБ'ЄКТ, тому ADL не вмикається\n";
    }
} trace{};
}

void part_switches() {
    head("5. Три вимикачі ADL");

    lib::Widget w{7};

    ask("lib::onlyAdl(w) // кваліфіковано ");  lib::onlyAdl(w);
    ask("onlyAdl(w)      // голе ім'я     ");  onlyAdl(w);
    {
        using guard::trace;                    // ім'я в цій області — не функція
        ask("trace(w)        // trace — об'єкт");  trace(w);
    }
}
```

```
──  5. Три вимикачі ADL  ──
    lib::onlyAdl(w) // кваліфіковано   →  lib::onlyAdl — інакше її не дістати
    onlyAdl(w)      // голе ім'я       →  lib::onlyAdl — інакше її не дістати
    trace(w)        // trace — об'єкт  →  guard::trace — це ОБ'ЄКТ, тому ADL не вмикається
```

Другий рядок доводить, що `lib::onlyAdl` не видима звичайним пошуком узагалі: у глобальній області такого імені немає, і виклик тримається виключно на аргументі. Третій — найважливіший. Оголошення `using guard::trace;` вводить у блок **змінну**, звичайний пошук зупиняється на ній, і ADL не запускається взагалі: `lib::trace`, який у другому досліді перемагав, тут навіть не стає кандидатом. Саме на цьому стоїть весь `std::ranges`, і саме тому такі об'єкти оголошують `inline constexpr` — щоб у всіх одиницях трансляції це був [один і той самий об'єкт](root:sys-plang-cpp/odr-and-linkage).

## Що не збирається

```cpp
#ifdef SHOW_ERRORS
// Збірка з -DSHOW_ERRORS має провалитися. Цікаво саме те, ЯК вона провалюється.
inline void broken() {
    lib::Point p{1, 2};
    std::cout << p;                     // (1)
    util::dump("p", p);                 // (2)

    img::Buffer a("а", 8), b("б", 8);
    img::swap(a, b);                    // (3)

    lib::Widget w{7};
    (onlyAdl)(w);                       // (4)
}
using img::swap;                        // (5)
#endif

int main() {
    part_operator();
    app::part_overload();
    part_swap();
    part_hidden();
    part_switches();
}
```

Формулювання GCC (Clang каже те саме іншими словами):

| # | що написано | відмова | що це доводить |
|---|---|---|---|
| 1 | `std::cout << p` без `using` | `no match for 'operator<<' (operand types are 'std::ostream' and 'lib::Point')` | ADL шукає в `std` і `lib`, а оператор лежить у `app` |
| 2 | те саме крізь `util::dump` | та сама відмова + `in instantiation of 'void util::dump(...)'` | другий прохід шаблону має тільки ADL |
| 3 | `img::swap(a, b)` | `'swap' is not a member of 'img'` | прихованого друга не дістати кваліфіковано |
| 4 | `(onlyAdl)(w)` | `'onlyAdl' was not declared in this scope` | дужки вимкнули ADL, і кандидатів не лишилося |
| 5 | `using img::swap;` | `'swap' is not a member of 'img'` | його не можна навіть впустити до себе |

Збирати так:

```
g++ -std=c++20 -O2 -Wall -Wextra adl-lab.cpp -o adl-lab && ./adl-lab
g++ -std=c++20 -fsyntax-only -DSHOW_ERRORS adl-lab.cpp     # має провалитися п'ять разів
```

## Пастки

**Пастка з компілятором.** Дослід 1 відтворюється лише там, де двофазний пошук справді двофазний. У MSVC його вмикає режим `/permissive-` (прапорець `/Zc:twoPhase`); зі `/std:c++latest` він увімкнений сам, інакше його додають руками — без нього `util::dump(p)` може зібратися, і найцінніший рядок лабораторії зникне.

**Пастка з `-O2`.** Тут вона зворотна до звичної: оптимізація нічого не приховує, бо ми міряємо не швидкість, а лічильники й імена. А от `std::swap` на реальному типі під `-O2` може виявитися не дорожчим за власний обмін — три переміщення тривіальних полів компілятор зазвичай згортає. Число «3» у протоколі — це кількість викликів наших операторів, а не гарантована ціна в машинному коді; вона стає реальною там, де переміщення справді щось робить.

**Пастка з порядком оголошень.** Якби `using namespace app;` стояла у файлі **до** визначення `util::dump`, перший прохід шаблону побачив би оператор звичайним пошуком, і дослід 1 «полагодився» б сам собою — але тільки в цьому файлі й тільки для цього порядку включень. Саме такі випадкові полагодження й роблять помилку плаваючою: у сусідній одиниці трансляції той самий код не збереться.

**Чого лабораторія не міряє.** Вона нічого не каже про час збірки — головну ціну роздутої множини кандидатів. Щоб побачити її, потрібні інші інструменти (`-ftime-trace` у Clang, `/d1reportTime` у MSVC) і бібліотека з десятками операторів, а не п'ять функцій в одному файлі.
