# 📋 Повний довідник інтерфейсів C++26: std::meta, контракти, execution, linalg та simd

Стандарт ISO/IEC 14882:2026 (C++26) істотно трансформує архітектуру мови та стандартної бібліотеки STL. Реліз впроваджує нові фундаментальні простори імен, мовні оператори інспекції та генерації синтаксичного дерева, формалізовану контрактну модель верифікації функцій, уніфіковане асинхронне середовище та високоефективні математичні й векторні типи. Цей довідник надає вичерпний опис інтерфейсів, функціональних контрактів, вимог до пам'яті, гарантій винятків, макросів перевірки можливостей та семантики викликів для ключових підсистем: метапрограмування `<meta>`, контрактів `<contracts>`, асинхронності `<execution>`, лінійної алгебри `<linalg>`, векторних операцій `<simd>` та розширень пам'яті часу компіляції.

## 1. Статична рефлексія та компіляторна генерація коду: заголовок `<meta>`

Система статичної рефлексії (папір P2996) повністю витісняє застарілі шаблонні трюки на базі SFINAE прямою інспекцією синтаксичного дерева AST під час компіляції. Робота з метаінформацією базується на взаємодії двох нових операторів ядра мови (`^^` та `[: :]`) та функцій часу компіляції з простору імен `std::meta`.

### Оператори ядра мови та їхня семантика

Оператор отримання метаінформації `^^` (англ. *reflection operator*) приймає як операнд будь-яку іменовану сутність C++ — тип, шаблон, простір імен, змінну, поле структури, перелік або функцію. Результатом виразу є значення непрозорого скалярного типу `std::meta::info`. Отриманий дескриптор є значенням часу компіляції (prvalue), яке не створює нових типів у внутрішній таблиці символів компілятора і тому не збільшує споживання оперативної пам'яті компілятором під час аналізу коду. Завдяки цьому компілятор здатний обробляти рефлексію над десятками тисяч класів без помітного сповільнення фази семантичного аналізу.

Оператор зворотного підставляння або сплайсингу `[: expr :]` (англ. *splicer operator*) перетворює дескриптор `std::meta::info` назад у конструкцію мови C++. Залежно від граматичного контексту, сплайсер виконує різні форми матеріалізації:
- Якщо `expr` позначає поле структури чи локальну змінну, вираз `obj.[: expr :]` повертає безпосередній доступ до цього члена з урахуванням константності та категорії значення об'єкта.
- Якщо дескриптор позначає тип, синтаксис `typename [: expr :]` матеріалізує тип для оголошення змінних, повернених значень чи параметрів шаблонів.
- Якщо дескриптор позначає простір імен, конструкція `namespace [: expr :]` відкриває доступ до кваліфікованого пошуку символів.
- Якщо дескриптор позначає шаблон, вираз `template [: expr :]` дозволяє безпосередньо інстанціювати цільовий шаблон.

| Оператор | Синтаксис | Операнд | Результат виразу | Семантика матеріалізації |
| :--- | :--- | :--- | :--- | :--- |
| **Рефлексія** | `^^entity` | Тип, поле, метод, простір імен | `std::meta::info` | Створює легковажний дескриптор синтаксичного вузла AST |
| **Сплайсинг виразу** | `[: expr :]` | `std::meta::info` | Член або вираз | Відновлює доступ до ідентифікатора у виразі |
| **Сплайсинг типу** | `typename [: expr :]` | `std::meta::info` | Оголошення типу | Матеріалізує тип для створення змінних або шаблонів |
| **Сплайсинг простору** | `namespace [: expr :]` | `std::meta::info` | Простір імен | Дозволяє кваліфікований пошук символів |
| **Сплайсинг шаблону** | `template [: expr :]` | `std::meta::info` | Шаблон | Інстанціює шаблон за метадескриптором |

### Непрозорий дескриптор `std::meta::info`

Дескриптор `std::meta::info` реалізований як скалярний літеральний тип. Компілятор гарантує, що два дескриптори рівні за оператором `==` тоді й лише тоді, коли вони посилаються на одну й ту саму сутність AST (наприклад, однаковий тип або те саме поле класу).

```cpp
namespace std::meta {
    using info = /* компіляторний скалярний тип */;

    consteval bool operator==(info a, info b) noexcept;
    consteval auto operator<=>(info a, info b) noexcept;
}
```

Дескриптор можна вільно передавати як параметр у функції з кваліфікаторами `constexpr` та `consteval`, зберігати в константних масивах `std::array<std::meta::info, N>` або динамічних векторах `std::vector<std::meta::info>` під час компіляції, а також повертати як результат алгоритмів сортування, фільтрації чи структурної трансформації полів.

### Функції інспекції синтаксичного дерева AST

Усі функції простору імен `std::meta` оголошені як `consteval`, тобто виконуються суворо на етапі компіляції. Будь-яка спроба викликати їх у динамічному часі виконання (run-time) призводить до помилки компіляції.

Функція `name_of(r)` повертає базовий рядок ідентифікатора без префіксів просторів імен (наприклад, `"id"` для поля `User::id`). Функція `display_name_of(r)` формує повне людиночитне представлення сутності разом із типами та просторами імен (наприклад, `"int User::id"`). ## 2. Контракти ядра мови: заголовок `<contracts>`

Контрактна підсистема C++26 (папір P2900) надає формальний мовний механізм для зазначення умов коректності функцій та інваріантів алгоритмів. Вона повністю замінює використання макроса `assert()` та небезпечні коментарі в документації, інтегруючи контрактні перевірки у загальну систему типів та компіляторного аналізу.

### Синтаксис предикатів контракту та їхня взаємодія

Контракти інтегровані безпосередньо в граматику огорожі функцій через три ключові конструкції:
1. **Преумова (`pre`):** перевіряє коректність вхідних аргументів функції безпосередньо перед виконанням її тіла. Якщо функція має кілька преумов `pre`, вони обчислюються зліва направо у порядку їхнього оголошення. Порушення першої ж умови негайно зупиняє подальші перевірки.
2. **Постумова (`post`):** перевіряє стан поверненого значення та інваріанти об'єкта одразу після завершення тіла функції (перед знищенням локальних змінних стека). За допомогою синтаксису `post [r] (умова)` повернене значення стає доступним у виразі під локальним псевдонімом `r`.
3. **Локальне твердження (`contract_assert`):** фіксує проміжний інваріант у довільному місці алгоритму всередині тіла функції.

:::code api-cpp26-core-library/cpp/syntaksys-predykativ.hpp

У разі віртуального успадкування контракти підпорядковуються принципу підстановки Лісков (LSP): похідний клас не може посилювати преумови базового класу, але може розширювати постумови гарантій поверненого результату.

### Семантичні режими компіляції контрактів

Стандарт суворо розділяє написання контракту та спосіб його виконання. Режим перевірки задається прапорцями системи збірки для всього проєкту або окремих одиниць трансляції:

| Режим | Обчислення предикату | Поведінка при порушенні | Рекомендована сфера застосування |
| :--- | :--- | :--- | :--- |
| `ignore` | Предикат не обчислюється, машинний код перевірки не генерується | Порушення не фіксуються, накладні витрати дорівнюють нулю | Фінальні релізні білди з екстремальними вимогами до мікросекундної затримки |
| `observe` | Предикат обчислюється при кожному виклику | Викликається обробник порушень, після чого виконання продовжується | Продакшен-сервери для фонового моніторингу помилок без аварійного завершення |
| `enforce` | Предикат обчислюється при кожному виклику | Викликається обробник порушень, після чого викликається `std::terminate()` | Тестування, інтеграційні стенди та критичні за безпекою системи |

У режимі `ignore` оптимізатор компілятора має право трактувати контрактні предикати як аксіоматичні припущення (compiler assumptions), усуваючи зайві перевірки меж масивів чи нульових покажчиків у згенерованому коді.

### Обробка порушень та клас `std::contracts::contract_violation`

Якщо умова контракту виявляється хибною в режимах `observe` або `enforce`, система конструює діагностичний об'єкт класу `contract_violation` і передає його у зареєстрований обробник порушень:

:::code api-cpp26-core-library/cpp/obrobka-porushen-ta-klas.cpp

Метод `detection_mode()` сигналізує, чи умова повернула логічне значення `false` (`predicate_false`), чи під час обчислення предикату було згенеровано виняток (`evaluation_exception`). Користувацький обробник порушень має сигнатуру `void handle_contract_violation(const std::contracts::contract_violation& violation)` і може записувати інформацію у системний лог або формувати дамп пам'яті. Реєстрація глобального обробника відбувається на етапі запуску програми без виклику динамічних алокацій пам'яті.

## 3. Асинхронна архітектура: заголовок `<execution>`

Модель асинхронності P2300 (`std::execution`) стандартизує трифазний життєвий цикл операцій, повністю усуваючи необхідність у динамічних виділеннях пам'яті під стан задач і забезпечуючи детерміноване керування контекстами виконання.

### Базові концепти та канали зв'язку

Приймач результатів (`receiver`) підтримує три взаємовиключні канали сповіщення, один із яких обов'язково викликається точно один раз наприкінці асинхронної операції:
- `set_value(rcvr, args...)`: успішне завершення задачі з передачею довільного кортежу обчислених значень.
- `set_error(rcvr, err)`: аварійне завершення з передачею об'єкта помилки або винятку `std::exception_ptr`.
- `set_stopped(rcvr)`: дострокове скасування виконання за запитом токена зупинки `std::stop_token`.

:::code api-cpp26-core-library/cpp/bazovi-kontsepty-ta-kanaly.cpp

Модель гарантує структурований паралелізм: стан задачі `operation_state` створюється на стеку викликаючої функції під час виклику `connect(sender, receiver)`. Пам'ять під проміжні результати виділяється компілятором у складі єдиного монолітного об'єкта стану, що повністю виключає виклики `malloc` та `new`. Обробка винятків відбувається автоматично: якщо функція користувача у конвеєрі кидає виняток, середовище перехоплює його через `std::current_exception()` і спрямовує у канал `set_error`.

### Фабрики джерел задач (Sender Factories)

Фабрики створюють початкові легковажні сендери, які слугують вихідними вузлами в дереві обчислень:

### Адаптери конвеєрів (Sender Adaptors)

Адаптери приймають вхідний сендер і повертають новий сендер, що реалізує додаткову логіку перетворення результатів або маршрутизації потоків керування:

:::code api-cpp26-core-library/cpp/adaptery-konveieriv-sender.hpp

Конструкція `when_all` запускає всі передані сендери паралельно і очікує завершення кожного з них. Якщо хоча б один сендер завершується з помилкою через `set_error`, решта операцій у конвеєрі отримують сигнал скасування через механізм `std::stop_source`, а помилка прокидається далі по ланцюгу.

## 4. Стандартна лінійна алгебра: заголовок `<linalg>`

Бібліотека `<linalg>` (папір P1673) реалізує стандартизований інтерфейс BLAS (Basic Linear Algebra Subprograms) на базі неволодіючих багатовимірних буферів `std::mdspan`. Це дозволяє виконувати векторні та матричні обчислення над будь-якими неперервними, блочними чи розрідженими структурами пам'яті без копіювання даних.

### Векторні операції першого рівня (Level 1 BLAS)

Функції першого рівня призначені для поелементних векторних обчислень, знаходження норм, обертань Гівенса та скалярних добутків:

:::code api-cpp26-core-library/cpp/vektorni-operatsii.hpp

Усі векторні функції приймають об'єкти одновимірного `std::mdspan` з довільним макетом розміщення в пам'яті (наприклад, `std::layout_stride` для векторів із довільним кроком у пам'яті або `std::layout_right` для послідовних масивів C).

### Матрично-векторні операції другого рівня (Level 2 BLAS)

Функції другого рівня реалізують множення матриці на вектор та розв'язання трикутних систем рівнянь:

:::code api-cpp26-core-library/cpp/matrychno-vektorni.hpp

Тег `Triangle` може набувати значень `std::linalg::upper_triangle` або `std::linalg::lower_triangle`, що дозволяє оптимізувати обчислення для симетричних чи ермітових матриць, зберігаючи в пам'яті лише половину коефіцієнтів. Тег `Diagonal` визначає, чи є діагональні елементи одиничними (`std::linalg::unit_diagonal`) або довільними (`std::linalg::explicit_diagonal`).

### Матрично-матричні операції третього рівня (Level 3 BLAS)

Операції третього рівня охоплюють матричне множення GEMM та факторизацію:

```cpp
namespace std::linalg {
    // Загальне матричне множення: C = A * B
    template <typename InMatA, typename InMatB, typename OutMatC>
    void matrix_product(InMatA A, InMatB B, OutMatC C);

    // Факторизація Холецького для симетричних додатних матриць
    template <typename InOutMat, typename Triangle>
    void cholesky_factorization(InOutMat A, Triangle t);
}
```

Компілятор має право транслювати виклики функцій `<linalg>` у спеціалізовані процесорні інструкції FMA (Fused Multiply-Add) або пов'язувати їх із системними апаратно оптимізованими бібліотеками вендорів (такими як Intel MKL, AMD BLIS або Apple Accelerate).

## 5. Векторні типи з прямою апаратною адресацією: заголовок `<simd>`

Бібліотека `<simd>` (папір P1928) надає шаблонні класи `std::simd` та `std::simd_mask`, які безпосередньо відображаються на апаратні векторні регістри процесора (наприклад, 128-бітні SSE/NEON, 256-бітні AVX2 або 512-бітні AVX-512).

### Шаблон класу `std::simd`

## 6. Розширення підсистеми `constexpr` та динамічна пам'ять

Стандарт C++26 суттєво послаблює обмеження на операції часу компіляції, перетворюючи середовище `constexpr` на повноцінну платформу для виконання алгоритмів:
1. **Динамічне виділення пам'яті:** оператори `constexpr new` та `delete` тепер підтримують користувацькі поліморфні алокатори та віртуальні деструктори за умови, що вся виділена пам'ять звільняється до завершення фази константного обчислення. Будь-який витік пам'яті під час компіляції негайно генерує діагностичну помилку з точним зазначенням місця алокації.
2. **Константна робота зі `std::variant`:** шаблон `std::variant` отримав повноцінну підтримку `constexpr`-відвідування через `std::visit` для побудови кінцевих автоматів та компіляторних парсерів під час компіляції.
3. **Послаблення вимог до `placement new`:** папір P2741 дозволяє використовувати явне конструювання об'єктів у заздалегідь виділених буферах `constexpr` пам'яті типу `unsigned char[]` або `std::byte[]` без порушення правил ODR та часу життя об'єктів.

## 7. Синтаксичні інновації ядра мови: розширення мовних конструкцій

Окрім великих підсистем, C++26 впроваджує низку точкових синтаксичних розширень, спрямованих на зменшення надлишкового коду та покращення інженерної ергономіки:

1. **Змінні-плейсхолдери `_` (P2169):** змінна з іменем `_` тепер вважається анонімним плейсхолдером. У межах однієї області видимості дозволено створювати довільну кількість змінних з ім'ям `_` без колізій імен. Це усуває необхідність вигадувати штучні імена для ігнорованих полів структурованих зв'язувань `auto [id, _, status] = fetch_record()` або блокувань `std::lock_guard _(mtx)`. Компілятор не виділяє пам'ять під плейсхолдери, якщо вони не використовуються.
2. **Пакетне індексування Pack Indexing (P2662):** прямий доступ до елемента варіативного пакета за константним індексом через синтаксис `T...[I]` для типів та `args...[I]` для виразів. Це повністю усуває потребу у рекурсивних шаблонних структурах для отримання N-го аргументу функції або елемента кортежу. Час компіляції таких звернень становить O(1).
3. **Рядки пояснення для вилучених функцій (P2573):** синтаксис `void bad_function() = delete("користувацьке повідомлення")` дозволяє виводити зрозумілу причину вилучення методу безпосередньо у звіті компілятора при спробі його виклику.
4. **Розширення структурованих зв'язувань (P1061):** додано підтримку розгортання зв'язувань у варіативний пакет `auto [...args] = my_tuple`, що дозволяє передавати всі поля структури чи кортежу у функцію через механізм ідеального передавання `std::forward(args...)`.
5. **Форматування та системний вивід:** розширено бібліотеки `std::format` та `std::print` підтримкою автоматичного форматування діапазонів `std::ranges` із користувацькими розділювачами, форматування шляхів файлової системи `std::filesystem::path` та безпечного друку часових зон із бібліотеки `<chrono>` без попередньої конвертації у тимчасові рядки.
