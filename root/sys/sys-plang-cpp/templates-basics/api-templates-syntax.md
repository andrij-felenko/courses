# 📋 Довідник синтаксису, параметрів та інстанціювання шаблонів C++

Шаблони у C++ є формальними засобами генеративного метапрограмування, що дозволяють описувати параметризовані родини функцій, класів, змінних та типів-псевдонімів. Компілятор використовує визначення шаблону як синтаксичне лекало (креслення), за яким у точках використання автоматично або явно генерує конкретні екземпляри машинного коду та структур даних.

У цьому довіднику наведено вичерпний опис синтаксичних форм оголошення шаблонів, таксономії їхніх параметрів, правил взаємодії з системою типів, механізмів синтаксичного усунення неоднозначностей (`typename` та `template`), внутрішньої логіки лінивого інстанціювання, моделі зв'язування ODR, дружніх оголошень та керування одиницями трансляції через команди явного інстанціювання й модулі C++20.

## Форми оголошення та категорії шаблонів

Оголошення будь-якого шаблону починається з ключового заголовка `template <список_параметрів>`, за яким безпосередньо слідує сутність, що підлягає параметризації. Список параметрів не може бути порожнім, за винятком випадків повної явної спеціалізації.

| Вид шаблону | Стандарт | Базовий синтаксис | Типове призначення |
| :--- | :--- | :--- | :--- |
| **Шаблон функції** | C++98 | `template <typename T> T max(T a, T b);` | Узагальнені алгоритми, перевантаження, математичні операції |
| **Шаблон класу / структури** | C++98 | `template <typename T> class Vector { ... };` | Параметризовані контейнери, розумні вказівники, політики |
| **Шаблон об'єднання (union)** | C++98 | `template <typename T> union Storage { ... };` | Низькорівневі сирі буфери пам'яті під неініціалізовані типи |
| **Шаблон псевдоніма (Alias)** | C++11 | `template <typename T> using Ptr = T*;` | Скорочення складних типів, проекції type traits |
| **Шаблон змінної (Variable)** | C++14 | `template <typename T> constexpr T pi = ...;` | Математичні та конфігураційні константи, traits `_v` |
| **Скорочений шаблон (Terse)** | C++20 | `void sort(auto& container);` | Компактний запис шаблонів функцій із параметрами `auto` |

### 1. Шаблони функцій та механізм виведення аргументів

Шаблон функції визначає алгоритм, який компілятор може адаптувати під довільні типи. Головною особливістю шаблонів функцій є підтримка автоматичного виведення аргументів шаблону (англ. *Template Argument Deduction*): компілятор зіставляє типи фактичних аргументів виклику з параметрами функції та автоматично визначає типи `T`.

```cpp
template <typename T>
T clamp(T val, T min_val, T max_val) {
    if (val < min_val) return min_val;
    if (max_val < val) return max_val;
    return val;
}

// Виклики функції:
auto a = clamp(15, 0, 10);          // Неявне виведення: T = int
auto b = clamp<double>(15.5, 0, 10); // Явна типізація: T = double, аргументи 0 і 10 приводяться до double
```

Якщо типи аргументів конфліктують (наприклад, `clamp(15, 0.0, 10)`), компілятор не виконує неявних приведень типів для параметрів `T` і зупиняє трансляцію з помилкою неоднозначності виведення, вимагаючи або явної передачі типу `<double>`, або перевантаження функції.

### 2. Шаблони класів та зовнішні визначення методів

Шаблон класу описує тип даних, структура та внутрішні поля якого залежать від параметрів. Окремі методи шаблону класу самі по собі розглядаються компілятором як шаблони функцій, але вони нерозривно пов'язані з контекстом класу.

Якщо метод класу визначається за межами його тіла, розробник зобов'язаний повністю повторити заголовок `template <...>` перед кожним зовнішнім методом, а кваліфікатор імені класу повинен містити повний список формальних параметрів.

```cpp
template <typename T, typename Allocator = std::allocator<T>>
class DynamicArray {
public:
    DynamicArray();
    void push_back(const T& item);
    void push_back(T&& item);
    
    // Вкладений шаблон методу (Member Function Template)
    template <typename InputIterator>
    void assign(InputIterator first, InputIterator last);

private:
    T* buffer_{nullptr};
    std::size_t size_{0};
    std::size_t capacity_{0};
};

// Зовнішнє визначення звичайного конструктора:
template <typename T, typename Allocator>
DynamicArray<T, Allocator>::DynamicArray()
    : buffer_(nullptr), size_(0), capacity_(0) {}

// Зовнішнє визначення методу push_back:
template <typename T, typename Allocator>
void DynamicArray<T, Allocator>::push_back(const T& item) {
    // Тіло методу
}

// Зовнішнє визначення вкладеного методу-шаблону:
template <typename T, typename Allocator>
template <typename InputIterator>
void DynamicArray<T, Allocator>::assign(InputIterator first, InputIterator last) {
    // Вкладений метод має два рівні параметризації
}
```

### 3. Шаблони змінних (Variable Templates, C++14)

До стандарту C++14 для створення типізованих числових констант розробникам доводилося оголошувати фіктивні статичні структури-обгортки зі статичними константами всередині. Шаблони змінних дозволили оголошувати глобальні та просторові константи безпосередньо:

```cpp
// Параметризована константа
template <typename T>
constexpr T golden_ratio = T(1.61803398874989484820458683436563811772L);

// Використання:
float  phi_f = golden_ratio<float>;   // Точність single-precision
double phi_d = golden_ratio<double>;  // Точність double-precision

// Скорочення для стандартних рис типів (Type Traits)
template <typename T>
inline constexpr bool is_integral_v = std::is_integral<T>::value;

template <typename From, typename To>
inline constexpr bool is_convertible_v = std::is_convertible<From, To>::value;
```

Шаблони змінних можуть спеціалізуватися для конкретних типів, що дозволяє перевизначати значення констант для користувацьких структур або особливих типів матриць і векторів.

### 4. Шаблони псевдонімів (Alias Templates, C++11)

Шаблони псевдонімів створюються за допомогою директиви `using` і є повноцінною заміною застарілого `typedef`. Головна перевага полягає в тому, що `using` дозволяє залишати частину параметрів незаповненими, проектуючи нове узагальнене сімейство типів.

```cpp
// 1. Проекція з фіксацією частини параметрів
template <typename Value>
using StringMap = std::unordered_map<std::string, Value>;

// 2. Спрощення доступу до асоційованих типів трансформацій
template <typename T>
using decay_t = typename std::decay<T>::type;

template <bool B, typename T = void>
using enable_if_t = typename std::enable_if<B, T>::type;

// Використання у коді:
StringMap<int> registry; // Еквівалентно std::unordered_map<std::string, int>
```

## Таксономія параметрів шаблону

У заголовку шаблону дозволено комбінувати три принципово різні категорії параметрів: параметри-типи, нетипізовані параметри та параметри-шаблони.

### 1. Параметри-типи (Type Template Parameters)

Параметри-типи виступають ідентифікаторами типів, які підставляються під час інстанціювання. Вони позначаються ключовими словами `typename` або `class`.

```cpp
template <
    typename T,                             // Обов'язковий параметр типу
    class Allocator = std::allocator<T>     // Параметр типу зі значенням за замовчуванням
>
class List;
```

#### Правила значень за замовчуванням:
- **У шаблонах класів, псевдонімів та змінних:** Якщо для певного параметра вказано значення за замовчуванням, усі наступні параметри у списку також зобов'язані мати значення за замовчуванням.
- **У шаблонах функцій:** Параметр зі значенням за замовчуванням може стояти перед параметром без значення за замовчуванням, за умови, що наступні параметри можуть бути виведені з аргументів виклику функції (`template <typename T = int, typename U> void fn(U val);`).

---

### 2. Нетипізовані параметри (Non-Type Template Parameters — NTTP)

Нетипізований параметр приймає не тип, а константне значення часу компіляції. Значення NTTP стає невіддільною частиною типу екземпляра: класи `Array<int, 5>` та `Array<int, 10>` є абсолютно різними типами даних, мають різний бінарний розмір `sizeof` і не можуть неявно перетворюватися один в одного.

#### Еволюція дозволених типів для NTTP у стандартах:

| Категорія типів NTTP | C++98/03 | C++11 | C++17 | C++20 |
| :--- | :---: | :---: | :---: | :---: |
| **Цілочислові типи (`int`, `size_t`, `char`, `bool`)** | Так | Так | Так | Так |
| **Переліки (`enum`, `enum class`)** | Так | Так | Так | Так |
| **Вказівники / посилання на об'єкти з зовнішнім зв'язуванням** | Так | Так | Так | Так |
| **Вказівники на функції та статичні методи** | Так | Так | Так | Так |
| **Вказівники на члени класів (Pointers-to-members)** | Так | Так | Так | Так |
| **Нульовий вказівник (`std::nullptr_t`)** | Ні | Так | Так | Так |
| **Автоматичне виведення типу NTTP (`template <auto N>`)** | Ні | Ні | Так | Так |
| **Числа з рухомою комою (`float`, `double`, `long double`)** | Ні | Ні | Ні | Так |
| **Літеральні класи (Structural Types / Compile-time Strings)** | Ні | Ні | Ні | Так |

#### Механізм виведення типів NTTP (C++17)

Починаючи з C++17, ключове слово `auto` дозволяє параметризувати шаблон будь-якою константою без явного зазначення її типу в заголовку:

```cpp
template <auto Value>
struct ValueBox {
    static constexpr auto stored_value = Value;
    using value_type = decltype(Value);
};

ValueBox<42>      int_box;    // Value = 42, value_type = int
ValueBox<'Z'>     char_box;   // Value = 'Z', value_type = char
ValueBox<false>   bool_box;   // Value = false, value_type = bool
```

#### Структурні типи класів як NTTP (C++20)

У C++20 суттєво розширено межі метапрограмування: об'єкт класу може передаватися як NTTP, якщо його тип є **структурним типом** (англ. *Structural Type*). Щоб тип відповідав цьому критерію, він повинен задовольняти такі вимоги:
1. Усі нестатичні поля даних та прямі базові класи є відкритими (`public`) і також мають структурний тип.
2. Клас не містить віртуальних функцій та віртуальних базових класів (щоб гарантувати передбачувану розкладку пам'яті).
3. Клас підтримує константне порівняння на рівність: оператор `operator==` повинен бути оголошений як `constexpr` або згенерований компілятором за замовчуванням (`= default`).

Це нововведення уможливило передачу текстових рядків безпосередньо в параметри шаблонів:

```cpp
template <std::size_t N>
struct FixedString {
    char data[N]{};

    // Конструктор виконується під час компіляції
    constexpr FixedString(const char (&str)[N]) {
        for (std::size_t i = 0; i < N; ++i) {
            data[i] = str[i];
        }
    }

    constexpr bool operator==(const FixedString&) const = default;
};

// Шаблон, параметризований рядком
template <FixedString Identifier>
class LoggerChannel {
public:
    void log(const char* msg) {
        std::cout << "[" << Identifier.data << "] " << msg << "\n";
    }
};

// Використання:
LoggerChannel<"NETWORK_CORE"> net_log; // Кожен рядок породжує унікальний тип!
```

### 3. Параметри-шаблони (Template Template Parameters)

Параметр-шаблон дозволяє передавати в якості аргументу не повністю інстанційований тип даних (`std::vector<int>`), а саме відкрите сімейство типів — неінстанційований шаблон (`std::vector`). Це необхідно для побудови контейнерів-адаптерів та компонентів вищого порядку.

```cpp
// Оголошення параметра-шаблона Container, який сам приймає один параметр типу
template <typename T, template <typename> class Container>
class StackAdapter {
public:
    void push(const T& val) { storage_.push_back(val); }
    void pop() { storage_.pop_back(); }
private:
    Container<T> storage_;
};

// До C++17 у списку параметрів-шаблонів вимагалося винятково слово class.
// Починаючи з C++17, дозволено використовувати typename:
template <typename T, template <typename...> typename Container>
class ModernStackAdapter {
    Container<T> storage_;
};

// Використання:
StackAdapter<int, std::vector> int_stack;   // storage_ матиме тип std::vector<int>
StackAdapter<double, std::list> real_stack; // storage_ матиме тип std::list<double>
```

#### Історична проблема зіставлення параметрів-шаблонів:
У C++98/03 шаблон `std::vector` оголошено як `template <typename T, typename Alloc = std::allocator<T>> class vector;`. Він має два параметри. Якщо передати `std::vector` у шаблон `template <template <typename> class C>`, компілятори C++98 видавали жорстку помилку невідповідності кількості параметрів шаблону, ігноруючи аргумент за замовчуванням `Alloc`.

Стандарт C++17 виправив цю проблему: правила зіставлення були послаблені, дозволивши підставляти шаблони з дефолтними параметрами у вужчі параметри-шаблони, а універсальний синтаксис пакетів параметрів `template <typename...> class C` остаточно зняв будь-які конфлікти арності.

## Синтаксичні дисамбігуатори: typename та template

Розділення аналізу шаблонів на дві фази (Two-Phase Name Lookup) створює фундаментальну проблему для парсера під час першої фази (Definition Time). Компілятор повинен перевірити синтаксичну структуру шаблону, коли тип `T` ще невідомий.

За правилами стандарту C++, будь-яке залежне ім'я за замовчуванням вважається **значенням (змінною або функцією)**, а не типом і не шаблоном. Якщо залежне ім'я є типом або вкладеним шаблоном, програміст зобов'язаний явно вказати це за допомогою синтаксичних дисамбігуаторів.

### 1. Ключове слово typename для залежних типів

Розглянемо синтаксичний конфлікт у виразі:

```cpp
template <typename T>
void process_data() {
    T::Subtype* ptr;
}
```

Без дисамбігуатора парсер розглядає `T::Subtype` як статичне числове поле класу `T`, а символ `*` — як оператор множення на глобальну змінну `ptr`. Компілятор не створює локальну змінну-покажчик, а парсить вираз множення двох змінних. Якщо глобальної змінної `ptr` немає, виникає синтаксична помилка на Фазі 1.

Ключове слово `typename` вказує парсеру, що наступне кваліфіковане залежне ім'я слід трактувати як тип:

```cpp
template <typename T>
void process_data() {
    typename T::Subtype* ptr; // Створюється покажчик ptr на тип T::Subtype!
    
    // Оголошення псевдоніма залежного типу:
    using ItemType = typename T::value_type;
}
```

#### Послаблення правил typename у C++20:
Стандарт C++20 скасував обов'язковість слова `typename` у контекстах, де ім'я синтаксично не може бути нічим іншим, крім типу:
- У типах повернення функцій (`T::value_type get_val();`).
- У списках параметрів функцій та конструкторів.
- У списках базових класів (`class MyClass : public T::Base`).
- У виразах приведення типів (`static_cast<T::value_type>(x)`).
- У списку ініціалізації членів конструктора.

### 2. Ключове слово template для залежних методів і типів

Розглянемо синтаксичний конфлікт при виклику методу-шаблону:

```cpp
template <typename Storage>
void extract_and_run(Storage& s) {
    s.get<int>(0);
}
```

Коли парсер зустрічає вираз `s.get<int>`, він ще не знає, що `get` є шаблоном методу. Символ `<` розпізнається як оператор порівняння «менше ніж», символ `int` викликає синтаксичний збій, а символ `>` трактується як «більше ніж». Увесь вираз парситься як безглузде порівняння `((s.get < int) > (0))`.

Префікс `template` явно наказує компілятору відкрити список аргументів шаблону:

```cpp
template <typename Storage>
void extract_and_run(Storage& s) {
    // Явне позначення виклику методу-шаблону:
    auto val1 = s.template get<int>(0);
    
    // Виклик через покажчик:
    Storage* s_ptr = &s;
    auto val2 = s_ptr->template get<double>(1);
}

// Використання template для вкладених шаблонів типів (Rebind):
template <typename Allocator>
struct AllocatorWrapper {
    // Вкладений шаблон Rebind всередині залежного алокатора:
    using OtherAlloc = typename Allocator::template rebind<double>::other;
};
```

## Дружні оголошення всередині шаблонів класів

Оголошення дружніх функцій (англ. *Friend Declarations*) усередині шаблону класу має важливі особливості, залежно від того, чи є сама дружня функція шаблоном:

1. **Нешаблонна дружня функція, створена всередині шаблону (Hidden Friends):** Функція оголошується та визначається безпосередньо в тілі шаблону класу без власного заголовка `template <...>`. Вона генерується як звичайна глобальна функція для кожного інстанційованого типу і стає доступною винятково через пошук, залежний від аргументів (ADL). Це рекомендований ідіоматичний патерн для перевантаження операторів (`operator<<`, `operator+`).
2. **Дружній шаблон функції:** Якщо дружня функція оголошується з власним заголовком `template <typename U>`, вона надає доступ до приватних полів усім екземплярам зовнішнього шаблону.

```cpp
template <typename T>
class Matrix {
public:
    // Hidden Friend: створює дружній оператор для конкретного Matrix<T>
    friend std::ostream& operator<<(std::ostream& os, const Matrix<T>& m) {
        os << "[" << m.rows_ << "x" << m.cols_ << "]";
        return os;
    }

    // Дружній шаблон для міжтипових перетворень
    template <typename U>
    friend class Matrix;

private:
    std::size_t rows_{0};
    std::size_t cols_{0};
};
```

## Внутрішня механіка: ліниве інстанціювання (Lazy Instantiation)

Фундаментальною властивістю системи шаблонів C++ є **ліниве інстанціювання методів** (англ. *Lazy Member Instantiation*). Коли в програмі створюється екземпляр шаблону класу `std::vector<Widget>`, компілятор генерує лише:
1. Базову розкладку полів структури в пам'яті (розмір `sizeof`, вирівнювання).
2. Ті конструктори та деструктори, які безпосередньо викликаються в даному виразі.

Усі інші методи класу (наприклад, `push_back`, `resize`, `operator==`, `sort`) **не інстанціюються і не транслюються в машинний код взагалі**, доки у тексті програми не з'явиться прямий виклик конкретного методу для цього екземпляра.

```cpp
template <typename T>
class SmartContainer {
public:
    void basic_action() {
        // Працює для будь-якого типу
    }

    void print_payload() {
        // Вимагає наявності operator<< для типу T!
        std::cout << payload_ << "\n";
    }

private:
    T payload_{};
};

struct OpaqueType {}; // Не має operator<<

void test_lazy() {
    SmartContainer<OpaqueType> c;
    c.basic_action(); // Працює бездоганно!
    
    // c.print_payload(); // Якщо розкоментувати — виникне помилка компіляції на Фазі 2!
}
```

Завдяки лінивому інстанціюванню стандартні контейнери на кшталт `std::vector` можуть зберігати типи, які не мають конструктора за замовчуванням, оператора копіювання або оператора порівняння, за умови, що користувач не викликає методи, які безпосередньо спираються на ці операції.

## Правило одного визначення (ODR) та секції COMDAT

Шаблони кидають виклик класичному правилу одного визначення (**ODR** — *One Definition Rule*). Звичайна функція, визначена в кількох `.cpp` файлах без ключового слова `inline`, призводить до помилки компонування `duplicate symbol / multiple definition`.

Для шаблонів стандарт робить фундаментальний виняток:
1. Шаблон функції або метод шаблону класу може бути повністю визначений у заголовковому файлі (`.hpp`) і включений у сотні одиниць трансляції без порушення ODR.
2. Усі визначення шаблону в різних одиницях трансляції зобов'язані бути абсолютно ідентичними лексема за лексемою.

### Механізм секцій COMDAT у лінкері:
Коли компілятор транслює виклик `Vector<int>::push_back` у файлі `a.cpp` та у файлі `b.cpp`, він генерує ідентичний асемблерний код в обох об'єктних файлах `a.o` та `b.o`. Щоб уникнути колізій, компілятор поміщає машинний код інстанційованого методу у спеціальну секцію об'єктного файлу — **COMDAT** (в об'єктному форматі ELF / PE-COFF).

Під час фінального компонування лінкер виявляє однакові за іменами секції COMDAT, залишає рівно одну копію машинного коду у виконуваному файлі, а всі виклики з різних файлів перенаправляє на цю єдину фізичну адресу пам'яті. Решта дублікатів секції COMDAT просто відкидаються.

> ⚠️ **Пастка повної спеціалізації:** Повна спеціалізація шаблону функції чи методу (`template <> void sort<int>(...)`) перетворюється на звичайну функцію! Якщо помістити повну спеціалізацію в заголовок без ключового слова `inline`, лінкер видасть фатальну помилку множинного визначення символу.

## Керування інстанціюванням у проекті

Хоча секції COMDAT усувають дублювання машинного коду у фінальному бінарному файлі, неявне інстанціювання (Implicit Instantiation) створює колосальне навантаження на компілятор під час паралельної збірки великих проектів: кожна одиниця трансляції змушена парсити, аналізувати та генерувати AST для одних і тих самих типів.

Для оптимізації часу збірки стандарти C++ надають інструменти явного контролю генерації коду.

### 1. Явне визначення інстанціювання (Explicit Instantiation Definition)

Змушує компілятор повністю згенерувати машинний код для всіх методів класу або сигнатур функції в поточному об'єктному файлі:

```cpp
// Файл: Matrix_instantiations.cpp
#include "Matrix.hpp"

// Компілятор генерує машинний код для методів Matrix<float> та Matrix<double>:
template class Matrix<float>;
template class Matrix<double>;

// Явне визначення для конкретної функції:
template void quick_sort<int>(int* data, std::size_t size);
```

### 2. Явне оголошення інстанціювання (`extern template`, C++11)

Директива `extern template` повідомляє компілятору, що даний екземпляр шаблону гарантовано згенеровано в іншому об'єктному файлі. Компілятор припиняє локальну генерацію коду, залишаючи зовнішні посилання для лінкера:

```cpp
// Файл: Matrix.hpp
template <typename T>
class Matrix {
public:
    void invert();
    void multiply(const Matrix<T>& other);
};

// Заборона генерації коду Matrix<float> у всіх файлах, які включають цей заголовок:
extern template class Matrix<float>;
extern template class Matrix<double>;
```

#### Архітектурні наслідки extern template:
- **Скорочення часу компіляції:** Заощаджуються ресурси синтаксичного аналізатора та генератора коду в сотнях `.cpp` файлів.
- **Зменшення розміру проміжних `.obj` файлів:** Об'єктні файли не роздуваються дубльованими тілами методів.
- **Прискорення фінального лінкування:** Компоновщик не витрачає ресурси на дедуплікацію гігантських секцій COMDAT.

### 3. Модулі C++20 проти моделі включення

У традиційній моделі включення (*Inclusion Model*) увесь код реалізації шаблонів мусить знаходитися в заголовкових файлах `.hpp`, що призводить до багаторазового трансляційного оверхеду.

Модулі стандарту C++20 кардинально змінюють цей процес:
- Визначення шаблону всередині модуля експортується через ключове слово `export template`:
```cpp
// Модульний файл: math.ixx / math.cppm
export module math_core;

export template <typename T>
T compute_hypot(T a, T b) {
    return std::sqrt(a * a + b * b);
}
```
- Компілятор розбирає синтаксичне дерево модуля рівно один раз і зберігає його у бінарному форматі прекомпільованого інтерфейсу (BMI / IFC / PCM).
- Клієнтські файли, які виконують `import math_core;`, завантажують готове синтаксичне дерево миттєво, усуваючи необхідність текстового включення та прискорюючи компіляцію шаблонів у 5–10 разів.

## Зведена таблиця синтаксичних правил та діагностик

| Конструкція | Синтаксичний вигляд | Контекст застосування | Наслідок пропуску |
| :--- | :--- | :--- | :--- |
| `typename` | `typename T::NestedType` | Залежні вкладені типи даних | Помилка парсингу на Фазі 1 (трактується як змінна або множення) |
| `.template` | `obj.template method<U>()` | Виклик методів-шаблонів через об'єкт | Помилка парсингу на Фазі 1 (символ `<` трактується як оператор порівняння) |
| `->template` | `ptr->template method<U>()` | Виклик методів-шаблонів через покажчик | Помилка парсингу на Фазі 1 (символ `<` трактується як оператор порівняння) |
| `::template` | `T::template NestedTemplate<U>` | Звернення до вкладених шаблонів типів | Помилка парсингу на Фазі 1 (символ `<` трактується як оператор порівняння) |
| `template class` | `template class Vector<int>;` | Файл реалізації `.cpp` | Помилка лінкування `undefined reference`, якщо заголовок не містить тіл методів |
| `extern template` | `extern template class Vector<int>;` | Заголовковий файл `.hpp` | Дублювання генерації AST та сповільнення збірки |

Цей набір правил та синтаксичних конструкцій формує фундамент узагальненого програмування на C++, забезпечуючи поєднання статичної безпеки типів із максимальною продуктивністю цільової системи.
