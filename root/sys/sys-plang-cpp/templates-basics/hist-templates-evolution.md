# 📜 Еволюція шаблонів: від препроцесорних макросів до Тьюрінг-повної кодогенерації

Шаблони C++ (англ. *templates*) не виникли як абстрактна академічна концепція — вони народилися з гострої інженерної кризи середини 1980-х років. Під час створення перших версій мови C with Classes автор мови Б'ярн Страуструп (дан. *Bjarne Stroustrup*) зіткнувся з фундаментальним протиріччям між виразністю мови та її продуктивністю: програмістам були критично необхідні типобезпечні структури даних (списки, динамічні масиви, асоціативні таблиці), але наявний інструментарій змушував обирати між дірками в безпеці типів та неприпустимими втратами тактових циклів процесора.

## Препроцесорна криза та generic.h

У мові C для побудови узагальнених контейнерів історично існувало лише два шляхи, і обидва виявилися глухими кутами в промисловому проектуванні:

1. **Нетипізовані вказівники `void*`:** Контейнер зберігав універсальні адреси пам'яті. Щоб покласти в такий список скалярне значення (наприклад, `int` або `double`), його доводилося упаковувати в динамічну пам'ять на купі. Кожне зчитування вимагало ручного приведення типів `(int*)ptr`, яке компілятор не міг перевірити. Помилка програміста призводила до мовчазного спотворення пам'яті під час виконання. Додатково програма втрачала кеш-локальність через розкидані по пам'яті вузли.
2. **Багаторядкові препроцесорні макроси:** Щоб уникнути покажчиків, код структури загортали в гігантські макроси за допомогою оператора злиття лексем `##`.

Наприкінці 1980-х років Страуструп розробив стандартну бібліотеку `generic.h`, яка намагалася регламентувати макросну генерацію класів для C with Classes. Щоб створити стек цілих чисел, розробник мусив викликати спеціальні макроси:

```cpp
#include <generic.h>

#define Stack(type) name2(type,Stack)
#define Stackdeclare(type) \
struct Stack(type) {       \
    type* data;            \
    int top;               \
    void push(type val);   \
    type pop();            \
};
```

Цей механізм спричинив важку кризу підтримки коду у великих системах:

- **Відсутність ізоляції областей видимості:** Препроцесор працював до лексичного аналізу, тому макроси не підкорялися просторам імен або областям видимості класів, спричиняючи хаотичні колізії імен.
- **Неможливість зневадження:** Символьні таблиці зневаджувача бачили згенеровані типи на зразок `intStack` як окремі чужі структури, повністю втрачаючи зв'язок із вихідним алгоритмом.
- **Катастрофічна діагностика:** Якщо всередині макроса траплялася синтаксична або логічна помилка, компілятор вказував лише на рядок виклику макроса, приховуючи справжній контекст і тіло операції.

Страуструп дійшов висновку: генерація коду за параметризованим описом має стати невіддільною частиною самої мови, якою безпосередньо керує синтаксичний аналізатор і система перевірки типів компілятора.

## Концептуальне проектування: пошук синтаксису template

У фундаментальній монографії «Дизайн та еволюція C++» (*The Design and Evolution of C++*, 1994) Страуструп описує дискусії щодо форми узагальнень. Досліджувалися синтаксичні рішення з інших мов: модульні пакети мови Ada (`generic type T;`), параметризація у мові CLU та квадратні дужки `class Vector[T]`.

Квадратні дужки відкинули через непереборний конфлікт з індексацією масивів у парсері граматики C. Круглі дужки `Vector(T)` створювали синтаксичну неоднозначність із викликами функцій та конструкторів. Зрештою вибір зупинився на кутових дужках `<T>`, які в мові C використовувалися винятково як оператори порівняння.

Ключове слово `template` (буквально: «лекало», «трафарет» або «креслення») обрали свідомо, щоб підкреслити природу механізму: конструкція `template <class T> class Vector` не є типом даних і не створює жодного байта машинного коду під час визначення. Це креслення, за яким компілятор зобов'язаний виготовити новий повноцінний клас у той момент, коли в коді з'явиться конкретний тип-аргумент.

Початковий синтаксис `template <class T>` часто викликав плутанину в розробників, оскільки аргументом `T` міг бути як клас, так і вбудований скаляр (`int`, `char*`, `double`). Щоб усунути цей психологічний бар'єр, комітет ANSI/ISO стандартизував ключове слово `typename` як повноправний синонім `class` у списку параметрів типу.

## Внесок Степанова та народження STL

Паралельно з розвитком синтаксису шаблонів у лабораторіях Hewlett-Packard Александр Степанов (англ. *Alexander Stepanov*) разом із Девідом Массером розробляли філософію узагальненого програмування (*Generic Programming*). Степанов стверджував, що фундаментальні комп'ютерні алгоритми (пошук, сортування, трансформація) не залежать від конкретних структур даних, а вимагають лише певних алгебраїчних властивостей доступу до елементів.

Познайомившись зі Страуструпом у 1993 році, Степанов продемонстрував, що шаблони C++ дозволяють поєднати абстракцію ітераторів з абсолютною швидкодією: згенерований компілятором код для `std::sort` над масивом структур завдяки вбудовуванню (інлайнінгу) предикатів працював швидше за стандартну функцію `qsort` мови C, яка викликала покажчик на функцію через непрямий перехід на кожній ітерації.

У 1994 році комітет стандартизації C++ одноголосно проголосував за включення бібліотеки Степанова до стандарту під назвою STL (Standard Template Library), що назавжди закріпило шаблони в ролі головного архітектурного фундаменту мови.

## Відкриття 1994 року: несподівана Тьюрінг-повнота

Того ж 1994 року на засіданні комітету ANSI/ISO у Сан-Хосе (Каліфорнія) німецький інженер Ервін Унрух (нім. *Erwin Unruh*) продемонстрував колегам невелику програму. Файл взагалі не містив виконуваного коду всередині `main()`, але під час спроби компіляції змушував компілятор видавати каскад діагностичних помилок, у текстах яких містився повний список простих чисел до заданого ліміту.

```cpp
// Історична репродукція ідеї Ервіна Унруха (1994)
template <int i> struct is_prime;
template <int p, int d> struct is_prime_helper {
    static constexpr bool value = (p % d != 0) && is_prime_helper<p, d - 1>::value;
};
template <int p> struct is_prime_helper<p, 2> {
    static constexpr bool value = (p % 2 != 0);
};
template <int i> struct Prime_print {
    Prime_print<i - 1> a;
    enum { is_p = is_prime_helper<i, i - 1>::value };
    // Якщо число просте, створюється помилка типу, яка виводить 'i' в терміналі!
    void f() { struct Dummy { Dummy(int); } d = is_p ? i : 0; }
};
```

Це відкриття вразило спільноту: з'ясувалося, що механізм зіставлення шаблонів, рекурсивного інстанціювання та обчислення сталих виразів перетворює компілятор C++ на повноцінний інтерпретатор чистої функціональної мови програмування без побічних ефектів. Шаблони C++ виявилися **Тьюрінг-повною системою** (англ. *Turing-complete*), де значеннями виступають типи та числові константи, а функціями — спеціалізації шаблонів класів.

Це започаткувало дисципліну **метапрограмування на шаблонах** (англ. *Template Metaprogramming — TMP*), пізніше систематизовану Андрієм Александреску в книзі «Сучасне проектування на C++» (*Modern C++ Design*, 2001).

## Драматична епопея з export template

Однією з найдраматичніших сторінок в історії C++ стала спроба роздільної компіляції шаблонів через ключове слово `export`, зафіксоване в C++98. За задумом розробників, слово `export` мало дозволити поміщати оголошення шаблону в заголовок `.h`, а його визначення — в окремий файл реалізації `.cpp`, подібно до звичайних функцій.

На практиці це вимагало від компілятора зберігати розібране синтаксичне дерево (AST) або проміжне представлення в об'єктних файлах і виконувати повноцінну компіляцію під час зв'язування (лінкування). Протягом десятиліття лише одна компанія — Edison Design Group (EDG) — зуміла реалізувати `export template`, витративши на це роки праці провідних інженерів. Жоден масовий компілятор (ні GCC, ні Clang, ні MSVC) так і не підтримав цю функціональність через її гігантську складність.

У стандарті C++11 ключове слово `export` для шаблонів було офіційно скасоване (а пізніше у C++20 переосмислене для експорту модулів), закріпивши загальноприйняту модель включення (*Inclusion Model*), за якої визначення шаблонів розміщуються безпосередньо в заголовкових файлах.

## Еволюція через стандарти: від C++98 до C++20

З моменту стандартизації C++98 система шаблонів невпинно еволюціонувала від низькорівневих «трюків» до чистого, декларативного каркаса:

### C++98/03: Фундамент і SFINAE

Стандарт зафіксував двоетапний пошук імен (Two-Phase Name Lookup), повну й часткову спеціалізації, а також нетипізовані параметри (NTTP) базових цілих типів. Головним інструментом метапрограмування став принцип **SFINAE** (англ. *Substitution Failure Is Not An Error* — невдача підстановки не є помилкою), який дозволив вибірково активувати перевантаження функцій на основі характеристик типів-аргументів.

### C++11: Подолання історичних бар'єрів

Стандарт C++11 приніс найбільше оновлення шаблонів за всю історію:

- **Шаблони псевдонімів (Alias Templates):** Конструкція `template <typename T> using Vec = std::vector<T>;` замінила незручні вкладені `typedef` у допоміжних структурах.
- **Шаблони змінної арності (Variadic Templates):** Пакети параметрів `typename... Args` усунули потребу в генерації десятків препроцесорних перевантажень для функцій із довільною кількістю параметрів (`std::make_shared`, `std::tuple`).
- **Зовнішнє інстанціювання (`extern template`):** Надало контроль над дублюванням кодогенерації в різних одиницях трансляції.
- **Лексема `>>`:** Компілятори навчилися коректно закривати вкладені шаблони `std::vector<std::list<int>>` без обов'язкового пробілу між дужками.

### C++14: Шаблони змінних

У C++14 з'явилися **шаблони змінних** (англ. *Variable Templates*): `template <typename T> constexpr T pi = ...;`. Це спростило математичні обчислення та стандартизувало зручні скорочення для рис типів зі суфіксом `_v` (`std::is_same_v<T, U>` замість `std::is_same<T, U>::value`).

### C++17: Автоматизація та виведення типів

Стандарт C++17 ввів виведення аргументів шаблонів класів (**CTAD** — Class Template Argument Deduction), що дозволило створювати об'єкти без явної типізації (`std::pair p(10, "text")`), дозволив використання `auto` в нетипізованих параметрах шаблону (`template <auto N>`), запровадив конструкцію статичного розгалуження `if constexpr` та дозволив використовувати ключове слово `typename` замість `class` у параметрах-шаблонах.

### C++20: Ера концептів та структурних NTTP

Стандарт C++20 довів систему шаблонів до зрілості:

- **Концепти (Concepts):** Формальні обмеження на типи (`template <std::floating_point T>`) перетворили заплутані багатосторінкові звіти компілятора SFINAE на лаконічні та точні повідомлення про невідповідність інтерфейсу.
- **Розширені NTTP:** Шаблони отримали право приймати дійсні числа (`float`, `double`) та літеральні структурні класи, уможлививши передачу рядкових літералів у параметри шаблонів під час компіляції.

Еволюція шаблонів перетворила C++ на мову з унікальним балансом: нульова вартість абстракції під час виконання поєднується з безпрецедентною гнучкістю статичного моделювання програмних систем.
