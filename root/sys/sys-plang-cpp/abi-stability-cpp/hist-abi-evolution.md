# 📜 Еволюція ABI у C++: від «Дикого Заходу» до Празького розколу WG21

Історія двійкового інтерфейсу додатків (англ. Application Binary Interface, ABI) у мові C++ — це хроніка боротьби між двома фундаментальними цінностями інженерії програмного забезпечення: можливістю оптимізувати структури даних заради максимальної швидкодії апаратного забезпечення та необхідністю зберігати працездатність уже скомпільованих двійкових модулів без їхньої повної перезбірки з вихідного коду.

У перші два десятиліття розвитку мови C++ кожна компанія-розробник компіляторів формувала власні двійкові правила самостійно. Програми, скомпільовані компілятором GCC, не могли підключити динамічні бібліотеки, створені в Clang, MSVC, Borland C++ Builder або Intel C++ Compiler. Розуміння того, як мова перейшла від повної двійкової несумісності до стандартизованих платформних специфікацій та чому на початку 2020-х років комітет стандартизації ISO C++ опинився у глухому куті через неможливість оновити застарілі типи стандартної бібліотеки, розкриває справжні причини компромісів сучасного C++.

---

## 1. Епоха «Дикого Заходу» і перші компілятори (1985–1999)

Коли Б'ярн Страуструп (дан. *Bjarne Stroustrup*) створював мову «C з класами» (C with Classes), а згодом C++, першим транслятором був `cfront` (1985 рік). Він працював як попередній компілятор (транспілятор), перетворюючи вихідний код C++ у звичайний сирцевий код мови C, який потім збирався стандартним компілятором C відповідної операційної системи.

Оскільки мова C мала стабільні та прості угоди про виклики (англ. calling conventions) і плоскі імена функцій у символьній таблиці, `cfront` вирішував проблему перевантаження функцій та просторів імен шляхом прямого шифрування типів аргументів у кінець імені функції — механізмом, що отримав назву декорування або манглінгу імен (англ. name mangling, від лат. *mangulare* — спотворювати).

Проте з появою повноцінних нативних компіляторів C++ на початку 1990-х років виник фундаментальний розкол. Кожен виробник інструментів розробки створив власну несумісну двійкову модель:

1. **Компілятори Borland C++ та Watcom** на платформі x86 використовували специфічні правила розташування вказівника віртуальної таблиці (`vptr`), розміщуючи його після призначених для користувача полів або перед ними залежно від моделі пам'яті (Small, Medium, Large, Flat).
2. **Microsoft Visual C++** запровадив складну систему декорування імен, що починалася зі знака питання `?`, а також власну схему розміщення віртуальних базових класів через спеціальні зміщення у таблиці `vbtable` (Virtual Base Table), відокремленій від звичайної таблиці віртуальних функцій `vfptr`.
3. **GNU Compiler Collection (GCC 2.x)** застосовував власну схему декорування імен та особливий формат запису деструкторів, який не збігався з жодним комерційним компілятором Unix-систем (Sun CC, IBM XL C++, HP aCC).

У результаті в 1990-х роках жодна бібліотека C++ не поширювалася у двійковому форматі без жорсткої прив'язки до конкретної версії одного компілятора. Якщо розробник купував комерційну GUI-бібліотеку, скомпільовану в MSVC 4.2, він не міг використовувати її у проекті на MSVC 5.0 або Borland C++ 5.0. Єдиним надійним способом взаємодії між модулями залишався чистий двійковий інтерфейс мови C (`extern "C"`).

## 2. Ініціатива Itanium C++ ABI (2000–2005)

Наприкінці 1990-х років консорціум провідних IT-корпорацій (серед яких Intel, Hewlett-Packard, Silicon Graphics, IBM, Sun Microsystems, Red Hat та Cygnus Solutions) розпочав розробку 64-бітної мікропроцесорної архітектури Intel Itanium (IA-64).

Розробники усвідомили: якщо для нової 64-бітної платформи кожен вендор знову створить власний несумісний компілятор C++, екосистема операційних систем Unix та Linux зазнає нищівного удару. Було створено робочу групу з уніфікації, яка у 2001 році опублікувала **Специфікацію двійкового інтерфейсу C++ для Itanium (Itanium C++ ABI)**.

Специфікація Itanium C++ ABI вперше у світі детально і формально визначила:
- Уніфікований манглінг імен, де всі символи C++ починаються з префікса `_Z` (наприклад, `_ZN6Widget6renderEi`);
- Точне розташування полів у структурах і класах, включаючи вирівнювання (alignment), заповнення (padding) та оптимізацію порожнього базового класу (Empty Base Optimization, EBO);
- Точну структуру віртуальних таблиць (`vtable`), включаючи розміщення зміщення віртуальної бази (Virtual Base Offset), зміщення до повного об'єкта (Offset-to-Top), вказівника на метадані RTTI (`type_info`) та слотів віртуальних методів;
- Механізм розгортання стеку при винятках з нульовою ціною (Zero-Cost Exception Handling) на основі секцій DWARF `.eh_frame`;
- Семантику та імена внутрішніх допоміжних функцій середовища виконання (`__cxa_pure_virtual`, `__cxa_guard_acquire`, `__cxa_allocate_exception`).

Хоча сам процесор Itanium комерційно поступився архітектурі x86-64 від AMD, створений для нього двійковий стандарт виявився настільки технічно досконалим та вичерпним, що розробники GCC та Clang адаптували його для всіх сучасних архітектур: x86, x86-64, ARM (AArch32/AArch64), RISC-V, MIPS та PowerPC.

Сьогодні Itanium C++ ABI є загальноприйнятим де-факто стандартом для операційних систем Linux, macOS, iOS, Android, FreeBSD та вбудованих RTOS. Єдиним великим винятком залишається корпорація Microsoft, яка на платформі Windows зберегла власний MSVC ABI заради зворотної сумісності зі своїм багатим двійковим спадком (COM, WinRT, Windows SDK).

## 3. Криза C++11 і розкол std::string у GCC 5 (2011–2015)

З виходом стандарту C++11 мова отримала революційні можливості: семантику переміщення, лямбда-вирази, багатопотоковість і нові гарантії для контейнерів. Проте одна з цих вимог спричинила найбільшу двійкову кризу в історії GNU/Linux.

У стандарті C++98 реалізація `std::string` у бібліотеці GNU `libstdc++` (і багатьох інших) базувалася на оптимізації **копіювання при записі (Copy-on-Write, CoW)**. Об'єкт `std::string` містив лише один вказівник на виділений у купі буфер, перед яким зберігався лічильник посилань, довжина рядка та місткість. Копіювання рядка зводилося до простого копіювання вказівника та інкременту лічильника:

```cpp
// Концептуальна структура std::string у C++98 (libstdc++ CoW)
struct StringC++98 {
    char* data_; // Вказує на масив символів, перед яким лежить метазаголовок:
                 // [atomic<size_t> refcount][size_t length][size_t capacity][char data...]
};
```

Ця схема працювала блискавично в однопотокових програмах, але виявилася небезпечною та повільною у багатопотоковому середовищі через необхідність атомарного захисту лічильника при кожному читанні символу через `operator[]`. Крім того, стандарт C++11 висунув дві жорсткі вимоги:
1. Метод `std::string::size()` повинен виконуватися зі строгою часовою складністю `O(1)`;
2. Доступ за індексом `operator[]` або через ітератор не має права робити недійсними інші посилання чи копії рядка (що ламало CoW при спробі модифікації).

Це зробило модель CoW повністю незаконною. Бібліотекам довелося перейти на модель **оптимізації малих рядків (Small String Optimization, SSO)**, де об'єкт рядка займає 24 або 32 байти і містить вбудований статичний масив для коротких рядків:

```cpp
// Концептуальна структура std::string у C++11 (libstdc++ SSO)
struct StringC++11 {
    char* ptr_;
    size_t size_;
    union {
        size_t capacity_;
        char sso_buffer_[16];
    };
};
```

Ці дві структури мають абсолютно різний розмір (8 байтів проти 32 байтів) та несумісне розташування пам'яті. Якби розробники GCC просто оновили `std::string`, будь-яка клієнтська програма, скомпільована старим GCC 4.8, під час передачі `std::string` у нову бібліотеку GCC 5 зазнала б аварійного падіння через пошкодження пам'яті.

Щоб запобігти масовому краху всіх дистрибутивів Linux, у 2015 році в GCC 5 розробники пішли на безпрецедентний крок: вони запровадили **подвійний двійковий інтерфейс (Dual ABI)** за допомогою макроса `_GLIBCXX_USE_CXX11_ABI` та механізму `inline namespace`.

Новий рядок отримав манглене ім'я `std::__cxx11::basic_string`, тоді як старий рядок залишився під іменем `std::basic_string`. Дистрибутиви Linux витратили понад п'ять років на міграцію: розробникам доводилося перекомпілювати тисячі пакетів із прапорцем `-D_GLIBCXX_USE_CXX11_ABI=1`, а будь-яка спроба лінкувати сторонню пропрієтарну бібліотеку, зібрану для старої моделі CoW, завершувалася помилкою компонувальника `undefined reference to std::__cxx11::basic_string`.

Цей болючий досвід настільки налякав індустрію, що виробники операційних систем (зокрема Red Hat, Debian, SUSE) почали вимагати від комітету стандартизації ISO C++ категоричної відмови від будь-яких подальших змін ABI.

## 4. Празький саміт WG21 і великий розкол (лютий 2020)

До кінця 2010-х років накопичився великий список архітектурних недоліків стандартної бібліотеки C++, які неможливо було виправити без порушення двійкової сумісності:

1. **`std::regex`**: початкова реалізація в `libstdc++` вийшла надзвичайно повільною через неефективний стан внутрішніх автоматів. Виправити її без зміни розміру та розкладки полів класу `std::regex` неможливо. Як наслідок, спільнота змушена уникати стандартизованого `std::regex` на користь сторонніх рішень (Boost.Regex, PCRE2, RE2).
2. **`std::unique_ptr`**: згідно з правилами конвенції викликів Itanium ABI (розділ 3.1.4), якщо клас має призначений для користувача або нетривіальний деструктор, він класифікується як тип пам'яті (`MEMORY`) і передається через прихований вказівник на стеку, а не через швидкі регістри процесора (`%rdi`). Навіть якщо `sizeof(std::unique_ptr<int>) == 8`, функція, що приймає `unique_ptr` за значенням, працює у півтора-два рази повільніше за функцію з сирим вказівником `int*`. Зміна деструктора або введення спеціального атрибута передачі в регістрах ламає ABI викликів між старими та новими бібліотеками.
3. **`intmax_t`**: цей тип у стандарті C/C++ заморожено на рівні 64-бітного цілого числа на всіх x86_64 платформах, оскільки розширення його до 128-бітного цілого (`__int128`) зламає бінарний контракт функції `printf` та форматні специфікатори стандартної бібліотеки C (`libc`).

На засіданні комітету ISO C++ (WG21) у Празі в лютому 2020 року розгорнулася найзапекліша дискусія за всю історію мови. Розробники розділилися на два непримиренні табори:

- **Прихильники розриву ABI (Performance / Progress camp)**: представники високопродуктивних хмарних компаній (Google, Apple, Meta), які перезбирають усю свою монолітну кодову базу з вихідного коду (Live at Head). Їхня позиція: «C++ існує заради максимальної швидкодії (Zero Overhead). Якщо стандартна бібліотека втрачає швидкодію через двійкові рішення 15-річної давнини, розробники просто перестають користуватися STL і переходять на альтернативні мови (Rust, Zig) або власні фреймворки (Abseil, Folly)».
- **Прихильники стабільності ABI (Stability / Ecosystem camp)**: представники розробників операційних систем (Red Hat, Canonical), розробників ігрових рушіїв, фінансових систем і вбудованих платформ. Їхня позиція: «Тисячі компаній використовують комерційні пропрієтарні плагіни, драйвери та наукові бібліотеки без вихідного коду. Якщо C++23 зламає ABI, користувачі просто застрягнуть на C++17 чи C++20 назавжди, як це сталося під час переходу з Python 2 на Python 3».

У Празі було проведено серію показових сигнальних голосувань (straw polls). Комітет поставив питання: *«Чи готові ми розірвати ABI у версії C++23 заради продуктивності або покращення мови?»*. Результат голосування був категоричним: переважна більшість членів комітету проголосувала **проти** будь-якого порушення двійкової сумісності в C++23.

## 5. Сучасний стан і майбутнє

Рішення празького саміту 2020 року визначило вектор розвитку C++ на наступні десятиліття. Комітет офіційно визнав: **стабільність ABI є довгостроковим пріоритетом мови C++**.

Це рішення має далекосяжні інженерні наслідки:
- Старі типи стандартної бібліотеки з неефективним двійковим компонуванням (`std::regex`, `std::function`) залишаються замороженими; замість їхньої модернізації комітет вводить нові типи під іншими іменами (наприклад, `std::move_only_function` у C++23, `std::copyable_function` у C++26);
- Нові мовні засоби проєктуються з урахуванням того, що вони не повинні змінювати розкладку пам'яті вже наявних абстракцій;
- Розробка сучасних системних бібліотек вимагає від архітекторів обов'язкового впровадження внутрішніх механізмів двійкового захисту: версіонованих просторів імен (`inline namespace`), непрозорих вказівників (PImpl) та контролю експорту символів.

Стабільність ABI у C++ більше не є випадковим побічним ефектом роботи компілятора — це фундаментальна інженерна дисципліна, що гарантує збереження життєздатності світової інфраструктури програмного забезпечення.
