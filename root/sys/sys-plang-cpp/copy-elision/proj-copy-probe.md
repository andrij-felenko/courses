# ⚙️ Стенд: тип, що звітує про кожну свою копію

Це готова однофайлова програма на C++, яку можна зібрати чотирма способами й побачити власними очима, скільки об'єктів насправді народжується за кожним `return` — бо жодна словесна відповідь на питання «а чи спрацює тут RVO» не важить стільки, скільки один запуск на вашому компіляторі.

## Задача

Треба зробити видимою річ, яку мова навмисно ховає: **кількість об'єктів**. Компілятор має право не покликати конструктор копіювання, і саме тому лічильника «скільки разів мене скопіювали» в мові немає — його доводиться вбудовувати самому.

Стенд має відповісти на п'ять питань за один запуск:

1. Скільки об'єктів реально виникає, коли повертається безіменний вираз, а скільки — коли іменована локальна змінна.
2. Що змінює прапорець `-fno-elide-constructors`, який вимикає **необов'язкові** усунення.
3. Що з цього змінилося між C++14 і C++17 — і, головне, що **не** змінилося.
4. Чим `return p;` відрізняється від `return std::move(p);` у числах, а не в загальних словах.
5. Чи справді локальна змінна всередині функції та змінна на боці виклику лежать **за однією адресою**.

## Ідея

Піддослідний тип має три способи народитися — звичайний конструктор, конструктор копіювання, конструктор переміщення — і кожен друкує рядок. Кожен примірник отримує **номер**, а копія й переміщення друкують ще й номер джерела: так у виводі видно не лише «скільки», а й **хто з кого** постав. Деструктор друкує свій номер, тож наприкінці кожного сценарію кількість народжень має збігтися з кількістю смертей — це вбудована самоперевірка стенду.

Побічні дії в конструкторі копіювання — це рівно те, чого в бойовому коді робити не можна: саме через них мова була змушена окремо дозволити усунення копій. У вимірювальному стенді вони доречні: ми тут не пишемо програму, ми ловимо компілятор за руку.

Друкувати варто через `std::printf`, а не через `std::cout`: `printf` не тягне за собою статичної ініціалізації потоків, тож стенд лишається придатним і тоді, коли ви зробите піддослідний об'єкт глобальним.

## Код

Один файл, без залежностей, збирається і як C++14, і як C++17 — останній сценарій захищено перевіркою `__cplusplus`, бо в C++14 він просто не компілюється (це й є частина досліду).

```cpp
// copy_probe.cpp — стенд для спостереження за усуненням копій
#include <cstdio>
#include <utility>

struct Probe {
    static int next_id, ctors, copies, moves, dtors;
    int id;

    Probe() : id(++next_id) {
        ++ctors;
        std::printf("    [%d] конструктор\n", id);
    }
    Probe(const Probe& src) : id(++next_id) {
        ++copies;
        std::printf("    [%d] КОПІЯ з [%d]\n", id, src.id);
    }
    Probe(Probe&& src) noexcept : id(++next_id) {
        ++moves;
        std::printf("    [%d] переміщення з [%d]\n", id, src.id);
    }
    ~Probe() {
        ++dtors;
        std::printf("    [%d] деструктор\n", id);
    }
};

int Probe::next_id = 0;
int Probe::ctors = 0;
int Probe::copies = 0;
int Probe::moves = 0;
int Probe::dtors = 0;

// ── шість сценаріїв повернення ───────────────────────────────────────

Probe urvo()               { return Probe(); }
Probe nrvo()               { Probe p; return p; }
Probe two_branches(bool c) { Probe a, b; if (c) return a; return b; }
Probe with_move()          { Probe p; return std::move(p); }

struct Box { Probe member; };
Probe from_field()         { Box b; return b.member; }

Probe const_local()        { const Probe p; return p; }

// ── чи справді комірка одна ──────────────────────────────────────────

Probe report_own_address(void** where) { Probe p; *where = &p; return p; }

// ── фабрика типу, що не копіюється й не переміщується ────────────────

#if __cplusplus >= 201703L
struct Latch {
    Latch()  { std::printf("    [L] конструктор\n"); }
    ~Latch() { std::printf("    [L] деструктор\n"); }
    Latch(const Latch&) = delete;
    Latch(Latch&&)      = delete;
};
Latch make_latch() { return Latch(); }
#endif

// ── обслуга стенду ───────────────────────────────────────────────────

static void start(const char* title, const char* code) {
    Probe::next_id = Probe::ctors = Probe::copies = 0;
    Probe::moves = Probe::dtors = 0;
    std::printf("\n=== %s   |   %s\n", title, code);
}

static void finish() {
    std::printf("    ─ об'єктів %d (звичайних %d, копій %d, переміщень %d), знищень %d\n",
                Probe::ctors + Probe::copies + Probe::moves,
                Probe::ctors, Probe::copies, Probe::moves, Probe::dtors);
}

int main() {
    std::printf("__cplusplus = %ld\n", (long)__cplusplus);

    start("1. безіменне значення (URVO)", "return Probe();");
    { Probe q = urvo();            (void)q; }
    finish();

    start("2. іменована локальна (NRVO)", "Probe p; return p;");
    { Probe q = nrvo();            (void)q; }
    finish();

    start("3. дві змінні на двох гілках", "if (c) return a; return b;");
    { Probe q = two_branches(true); (void)q; }
    finish();

    start("4. зайвий std::move", "return std::move(p);");
    { Probe q = with_move();       (void)q; }
    finish();

    start("5. повернення поля", "Box b; return b.member;");
    { Probe q = from_field();      (void)q; }
    finish();

    start("6. const-локальна", "const Probe p; return p;");
    { Probe q = const_local();     (void)q; }
    finish();

    start("7. одна комірка чи дві", "адреса локальної vs адреса q");
    {
        void* inside = nullptr;
        Probe q = report_own_address(&inside);
        std::printf("    локальна: %p, q: %p — %s\n",
                    inside, (void*)&q,
                    inside == (void*)&q ? "ТА САМА комірка" : "різні комірки");
    }
    finish();

#if __cplusplus >= 201703L
    std::printf("\n=== 8. фабрика типу без копіювання й переміщення (лише C++17)\n");
    { Latch l = make_latch();  (void)l; }
#else
    std::printf("\n=== 8. фабрика типу без копіювання й переміщення: у C++14 не збереться\n");
#endif
}
```

## Чотири збірки

Прапорець `-fno-elide-constructors` вимикає ті усунення, які лишилися **необов'язковими**, і не чіпає гарантованих. Разом зі стандартом це дає чотири кути огляду:

```sh
for std in 14 17; do
  for flag in "" "-fno-elide-constructors"; do
    g++ -std=c++$std -O2 $flag copy_probe.cpp -o probe
    echo "──────── -std=c++$std $flag"
    ./probe
  done
done
```

Рівень оптимізації тут не важить. І GCC, і Clang ухвалюють рішення про усунення у **фронтенді**, ще до оптимізатора, тож `-O0` і `-O2` дають однакові числа; єдиний важіль — це саме `-fno-elide-constructors`. (У MSVC довго було інакше: до Visual Studio 2022 17.4 необов'язкове усунення робилося лише під `/O2`, а тепер керується окремим `/Zc:nrvo`, який умикається сам під `/O2`, `/permissive-` або `/std:c++20`.)

## Що друкує

Найцікавіший — другий сценарій, іменована локальна змінна. Ось три його виводи поспіль.

**`-std=c++14` і `-std=c++17` без прапорця — однаково:**

```
=== 2. іменована локальна (NRVO)   |   Probe p; return p;
    [1] конструктор
    [1] деструктор
    ─ об'єктів 1 (звичайних 1, копій 0, переміщень 0), знищень 1
```

**`-std=c++14 -fno-elide-constructors`:**

```
    [1] конструктор
    [2] переміщення з [1]
    [1] деструктор
    [3] переміщення з [2]
    [2] деструктор
    [3] деструктор
    ─ об'єктів 3 (звичайних 1, копій 0, переміщень 2), знищень 3
```

**`-std=c++17 -fno-elide-constructors`:**

```
    [1] конструктор
    [2] переміщення з [1]
    [1] деструктор
    [2] деструктор
    ─ об'єктів 2 (звичайних 1, копій 0, переміщень 1), знищень 2
```

Ось воно, у двох рядках різниці. Переміщень було два: одне з локальної `p` у значення, що повертається, і друге — з цього значення у змінну `q` того, хто викликав. C++17 прибрав **друге назавжди**: змінна `q` тепер і **є** тим об'єктом, який будує функція, тож переносити нікуди. А перше переміщення нікуди не поділося — воно й далі залежить від доброї волі компілятора, і прапорець цю волю відбирає.

## Зведення

Ось усі шість сценаріїв у форматі **об'єктів / копій / переміщень** — так це виглядає на g++ під Linux x86-64. Жирним — дві клітинки, заради яких стенд і зібрано: у них видно, де гарантія C++17 діє, а де закінчується.

| № | Сценарій | c++14 | c++14 `-fno-elide` | c++17 | c++17 `-fno-elide` |
|---|---|---|---|---|---|
| 1 | `return Probe();` | 1 / 0 / 0 | 3 / 0 / 2 | 1 / 0 / 0 | **1 / 0 / 0** |
| 2 | `Probe p; return p;` | 1 / 0 / 0 | 3 / 0 / 2 | 1 / 0 / 0 | **2 / 0 / 1** |
| 3 | дві змінні, дві гілки | 3 / 0 / 1 | 4 / 0 / 2 | 3 / 0 / 1 | 3 / 0 / 1 |
| 4 | `return std::move(p);` | 2 / 0 / 1 | 3 / 0 / 2 | 2 / 0 / 1 | 2 / 0 / 1 |
| 5 | `return b.member;` | 2 / 1 / 0 | 3 / 1 / 1 | 2 / 1 / 0 | 2 / 1 / 0 |
| 6 | `const Probe p; return p;` | 2 / 1 / 0 | 3 / 1 / 1 | 2 / 1 / 0 | 2 / 1 / 0 |

## Розбір рядків

**Рядок 1 — чиста дія нової моделі prvalue.** У C++14 прапорець повертає всю наївну картину: тимчасовий об'єкт, значення, що повертається, і змінна в того, хто викликав — три об'єкти, два переміщення. У C++17 той самий прапорець не дає **нічого**: `Probe()` — це [prvalue](topic:sys-plang-cpp/value-categories), а prvalue більше не позначає об'єкта, який можна було б створити зайвий раз. Вимикати нема чого. Документація GCC каже це прямо: у C++17 компілятор **зобов'язаний** обійтися без цих тимчасових об'єктів, і опція на них уже не впливає.

**Рядок 2 — межа гарантії.** Однакові одиниці в обох колонках без прапорця обманюють: здається, ніби C++17 гарантував і цей випадок. Права колонка розкриває правду — лишилося одне переміщення, і воно необов'язкове. Гарантія C++17 стосується **лише** ділянки між функцією та тим, хто її викликав; те, чи збігається адреса вашої локальної змінної з коміркою результату, як було доброю волею компілятора, так і лишилося.

**Рядок 3 — межа доброї волі.** Комірка під результат одна, а живих кандидаток на неї дві, тож усунути копію не можна в принципі: обидві змінні існують одночасно й мусять мати різні адреси. Тут навіть без прапорця є переміщення, і жоден стандарт цього не прибере. Показово, що Microsoft у документації до `/Zc:nrvo` записала цей випадок як явний виняток — «функція повертає кілька символів із перекривними часами життя»; у GCC і Clang правило те саме, просто не записане в довіднику опцій.

**Рядок 4 — ціна зайвого `std::move`.** Порівняйте з рядком 2 без прапорця: там об'єкт один, тут — два. `std::move(p)` перетворює ім'я на виклик функції, а умова усунення вимагає саме **імені**; написавши `std::move`, ви не прискорили повернення, а власноруч забрали найкращий варіант. Обидва компілятори вміють на це сваритися: зберіть із `-Wall` і побачите `-Wpessimizing-move` — «переміщення локального об'єкта в `return` заважає усуненню копії».

**Рядки 5 і 6 — де з'являється справжня копія.** Це єдині два рядки таблиці, де в колонці копій стоїть одиниця. `b.member` — не ім'я локальної змінної, а звернення до члена, тож [неявне переміщення](topic:sys-plang-cpp/move-semantics) до нього не застосовується — ні в C++17, ні в C++20, ні в C++23, хоча дві останні редакції це правило саме розширювали: усі вони вимагають, щоб операндом `return` було **ім'я змінної**, а не вираз доступу до поля. З `const`-локальною причина інша: усунення тут дозволене, але GCC його не робить, а перемістити з константи неможливо — лишається копія.

Саме рядок 6 варто перевірити на **своєму** компіляторі, бо тут GCC і Clang розходяться: за вимірюваннями на Compiler Explorer, Clang 20 застосовує NRVO до `const`-локальної й дає 1 / 0 / 0, тоді як GCC — від восьмої версії до п'ятнадцятої — не застосовує й дає повноцінну копію. Це не помилка жодного з них: обидва в межах дозволеного.

**Сценарій 7** підтверджує фізику однією парою чисел (у вас будуть інші адреси, важлива тільки їхня рівність):

```
    локальна: 0x7ffd4c1a2b30, q: 0x7ffd4c1a2b30 — ТА САМА комірка
```

Локальна `p` живе не в кадрі своєї функції, а прямо в тій ділянці, яку виділив під результат той, хто викликав. Це й означає «усунути копію»: не викинути виклик конструктора наприкінці, а від початку розмістити об'єкт там, де він має опинитися.

## Фабрика типу, що не копіюється й не переміщується

Восьмий сценарій — той, заради якого C++17 і робили. У стенді він схований за `#if`, тож перенесімо його в окремий файл — без захисту, щоб побачити саму помилку:

```cpp
struct Latch {
    Latch()  = default;
    ~Latch() = default;
    Latch(const Latch&) = delete;
    Latch(Latch&&)      = delete;
};

Latch make_latch() { return Latch(); }   // ← ось рядок, що вирішує все

int main() {
    Latch l = make_latch();
    (void)l;
}
```

`g++ -std=c++17` збирає це мовчки. `g++ -std=c++14` — ні:

```
error: use of deleted function 'Latch::Latch(Latch&&)'
```

Clang формулює те саме інакше — «call to deleted constructor of 'Latch'», — але суть одна. У C++14 дозвіл **не виконувати** копіювання не скасовував вимоги, щоб копіювання було **можливим**: компілятор мусив вибрати конструктор і пересвідчитися, що той доступний, і аж потім його не кликати. Видалений конструктор вибору не проходив — і функція, яка насправді не збиралася нічого копіювати, не компілювалася.

У C++17 вибирати нема чого, бо копіювання не відбувається за визначенням. Тому з фабрики можна повертати за значенням `std::mutex`, `std::atomic<int>`, будь-яку обгортку над ресурсом, прив'язану до власної адреси. Додайте `-fno-elide-constructors` до збірки C++17 — програма все одно збереться: гарантія прапорцем не вимикається.

## Підводні камені

**Числа стенду — не контракт, а знімок.** Уся ця таблиця описує ваш компілятор вашої версії, а не мову. Обіцяне стандартом видно лише в правій колонці: там прапорець уже забрав усе, що мав право забрати, тож лишилося те, чого забрати не можна. Решта клітинок — спостереження, і жодна з них не зобов'язана бути такою наступного року. Тому автоматичний тест, який стверджує «конструктор копіювання не викликається жодного разу», — це тест на компілятор, і він законно зламається після оновлення. Перевіряти треба спостережувану поведінку, а не кількість об'єктів.

**Windows потребує трьох окремих домовленостей.** Консоль треба перевести на UTF-8 (`chcp 65001`, а файл збирати з `/utf-8`), інакше кириличні написи в `printf` перетворяться на сміття. Макрос `__cplusplus` MSVC повідомляє чесно лише під `/Zc:__cplusplus` — без нього там завжди `199711L`, і восьмий сценарій мовчки випаде. Необов'язкове усунення вмикається окремим `/Zc:nrvo`; вимикається — `/Zc:nrvo-`, і це найближчий відповідник `-fno-elide-constructors`. Докладніше про такі розбіжності між реалізаціями — у [підтримці стандартів компіляторами](topic:sys-plang-cpp/compiler-support).

**Не ускладнюйте піддослідний тип.** Спокуса додати в `Probe` поле-`std::string`, щоб «було реалістичніше», псує дослід: у вивід домішуються конструктори рядка, і за головним стає важко стежити. Так само не варто друкувати через `std::cout`: якщо ви колись зробите `Probe` глобальним об'єктом, він може народитися раніше за потоки виводу, і стенд почне брехати саме там, де вимірює найтонше.

**Порядок деструкторів — теж дані.** У третьому сценарії локальні `a` і `b` гинуть у зворотному порядку до створення, і вже **після** того, як побудовано значення, що повертається. Якщо у вашому виводі деструктор локальної змінної стоїть **перед** переміщенням із неї — ви дивитеся не на той рядок; такого бути не може.

**Найдешевша перевірка — рівність народжень і смертей.** Останнє число в кожному рядку `finish()` має збігатися з першим. Якщо ні — десь у сценарії лишився живий об'єкт поза блоком, і всі решта чисел у цьому рядку рахують не те, що ви думаєте.
