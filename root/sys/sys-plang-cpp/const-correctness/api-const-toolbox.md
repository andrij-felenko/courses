# 📋 Довідник засобів константності

Усе, чим у C++ константність **додають**, **знімають**, **перевіряють** і **проштовхують углиб**, зібрано тут одним переліком: сигнатура, версія стандарту, заголовок і та пастка, на якій кожен засіб ловить найчастіше. Засоби розкидані по мові й чотирьох заголовках, і майже кожен має рівно один спосіб тихо зрадити — тому все далі влаштоване парами «що робить / де підводить».

Дві домовленості на весь текст. **Верхній рівень** `const` — той, що заморожує сам об'єкт (`const int n`, `char* const q`); **нижній** — той, що заморожує те, на що об'єкт дивиться (`const char* p`). Версія стандарту для рис типів указана двічі: сама риса прийшла в C++11, а зручний псевдонім `_t` або змінна `_v` — пізніше.

## Мовні засоби

| засіб | з версії | що робить | де підводить |
|---|---|---|---|
| `const T`, `const T*`, `T* const` | C++98 | кваліфікує тип на потрібному рівні | `const T*` і `T const*` — той самий тип, лише два стилі запису |
| `T f() const` | C++98 | `this` всередині методу стає `const C*` | не поєднується зі `static`; з C++11 несе ще й обіцянку потокобезпеки |
| `T f() const&`, `T f() const&&` | C++11 | добирає перевантаження ще й за категорією значення виразу-об'єкта | щойно ref-кваліфікатор з'явився в одного перевантаження, усі однойменні з тим самим списком параметрів мусять його мати |
| `mutable` на полі | C++98 | знімає з поля `const`, накинутий `const`-методом | не можна на `static`-полі, на `const`-полі й на полі-посиланні |
| `mutable` на лямбді | C++11 | робить `operator()` замикання неконстантним | без нього захоплені за значенням копії всередині тіла — сталі |
| `const_cast<T&>`, `const_cast<T*>` | C++98 (`T&&` — C++11) | знімає (чи додає) `const`/`volatile`, більше нічого | запис у справді `const`-об'єкт — [невизначена поведінка](root:sf-lang/undefined-behavior) |
| `auto&& f(this Self&& self)` | C++23 | [явний параметр об'єкта](root:sys-plang-cpp/deducing-this): одне тіло методу на обидві константності | нове; потребує сучасного компілятора |
| `constexpr` на змінній | C++11 | між іншим робить її `const` | зворотне неправда: `const` про час обчислення не каже нічого |
| `const` на змінній рівня простору імен | C++98 | дає їй внутрішнє зв'язування (у C — ні) | у кожній одиниці трансляції своя копія, тож адреси різні |

Три з цих рядків заслуговують на розгорнутий вигляд.

**Ref-кваліфікатори.** Вони добирають перевантаження не за константністю об'єкта, а за [категорією значення](root:sys-plang-cpp/value-categories) виразу, на якому метод викликано: `&` ловить іменований об'єкт, `&&` — тимчасовий. Комбінація з `const` дає чотири клітинки, і найдивніша з них, `const&&`, має цілком практичне застосування — заборонити виклик на тимчасовому:

```cpp
class Config {
    std::string path_;
public:
    const std::string& path() const&  { return path_; }
    const std::string& path() const&& = delete;   // на тимчасовому — не дамо
};

const std::string& p = load_config().path();      // ✗ помилка компіляції, а не висяче посилання
```

Без другого рядка виклик компілювався б і повертав посилання всередину об'єкта, який помирає в кінці цього самого виразу.

**`mutable` на лямбді** — те саме правило, тільки з іншого боку. `operator()` замикання за замовчуванням `const`, тому копії, захоплені за значенням, усередині тіла сталі:

```cpp
auto tick = [n = 0]() mutable { return ++n; };   // без mutable ++n не компілюється
```

**`const_cast`** приймає лише вказівник, посилання (з C++11 — і rvalue-посилання) чи вказівник на член, і міняє в них рівно `const` та `volatile` — на будь-яку іншу зміну типу він не здатний. Законність визначає не те, звідки взявся вираз, а те, яким **оголошено сам об'єкт**: якщо він мінливий, каст лише обходить обмеження шляху; якщо він `const`, запис — вихід за межі мови незалежно від того, що показав запуск.

## Бібліотека: додати й зняти const

```cpp
// <utility>, C++17
template <class T>
constexpr std::add_const_t<T>& as_const(T& t) noexcept;   // (1) віддає const T&
template <class T>
void as_const(const T&&) = delete;                        // (2) rvalue — заборонено
```

`std::as_const` не копіює й нічого не змінює: він лише повертає той самий об'єкт як `const`-посилання, щоб [добір перевантаження](root:sys-plang-cpp/overload-resolution) — механізм, яким компілятор із кількох однойменних функцій вибирає найточнішу під аргументи, — узяв `const`-версію. Перевантаження (2) вилучено навмисно: `std::as_const(make_thing())` дало б посилання на тимчасовий об'єкт, який зникає одразу після виразу, тож замість висячого посилання ти отримуєш помилку компіляції.

Дві пастки навколо нього. Перша: `auto x = std::as_const(v);` **копіює** й губить `const` — виведення `auto` відкидає посилання й верхній рівень кваліфікації, тож треба `auto&` або `decltype(auto)`. Друга: він робить `const` **вид**, а не `const` **об'єкт** — усі інші шляхи до цього об'єкта лишаються такими, як були.

Поруч живуть іще два бібліотечні способи вплинути на константність:

| засіб | версія · заголовок | що робить |
|---|---|---|
| `std::cref(t)` | C++11 · `<functional>` | загортає об'єкт у `std::reference_wrapper<const T>` — «посилання, яке можна класти в контейнер і копіювати»; rvalue-перевантаження теж вилучено |
| `std::const_pointer_cast<T>(sp)` | C++11 · `<memory>` | `shared_ptr<const T>` → `shared_ptr<T>`; з C++20 є ще й перевантаження для rvalue |
| `std::as_bytes(s)` / `std::as_writable_bytes(s)` | C++20 · `<span>` | `span<T>` → `span<const std::byte>` / `span<std::byte>` — сирий байтовий вид із збереженням чи зняттям права запису |

`std::const_pointer_cast` підпорядкований тому самому правилу, що й `const_cast`: він законний, лише якщо об'єкт у керованій пам'яті від початку створювався мінливим. Докладніше про те, як [`shared_ptr`](root:sys-plang-cpp/shared-weak-ptr) веде облік власників, — в окремій темі; тут важливо лише те, що каст міняє тип вказівника, а не природу об'єкта.

## Бібліотека: риси типів

Усі — з `<type_traits>`. Спільна їхня риса й спільна пастка одна: вони бачать **тільки верхній рівень**.

| риса | версія · псевдонім | що дає | де підводить |
|---|---|---|---|
| `std::is_const<T>::value` | C++11 · `is_const_v` (C++17) | чи `const`-кваліфікований сам `T` | посилання ніколи не `const`-кваліфіковане: `is_const_v<const int&>` → `false` |
| `std::add_const<T>::type` | C++11 · `add_const_t` (C++14) | `T` → `const T` | посилання, функції й уже-`const` лишає без змін: `add_const_t<int&>` = `int&` |
| `std::remove_const<T>::type` | C++11 · `remove_const_t` (C++14) | знімає `const` верхнього рівня | `remove_const_t<const int*>` = `const int*` — нижній рівень недоторканий |
| `std::remove_cv<T>::type` | C++11 · `remove_cv_t` (C++14) | знімає `const` і `volatile` верхнього рівня | на `const int&` не діє з тієї самої причини |
| `std::remove_cvref<T>::type` | C++20 · `remove_cvref_t` | знімає посилання, **потім** кваліфікатори | те, чого зазвичай і хочуть від `remove_const_t` |
| `std::decay<T>::type` | C++11 · `decay_t` (C++14) | як передавання за значенням: знімає посилання й кваліфікатори, масив і функцію зводить до вказівника | робить більше, ніж часто треба |

Правильний спосіб спитати «а чи не можна крізь цей тип писати» — спершу здерти посилання:

```cpp
template <class T>
constexpr bool read_only = std::is_const_v<std::remove_reference_t<T>>;

static_assert( read_only<const int&>);
static_assert(!read_only<int&>);
```

> 🔧 **Навіщо це.** Риси не «дивляться на тип очима» — вони роблять рівно одну текстову операцію над верхнім шаром. Тому в шаблонному коді помилка майже завжди та сама: параметр приїхав як `const T&`, риса відповіла `false`, гілка пішла в неконстантну — і зламалась аж на інстанціюванні, з вивертом діагностики на пів екрана. Правило просте: перш ніж питати про `const`, зведи тип до значення (`remove_reference_t` або `remove_cvref_t`). Решта [рис типів](root:sys-plang-cpp/type-traits) улаштовані так само поверхнево — це загальна властивість інструмента, а не вада конкретної риси.

## Бібліотека: константні ітератори

| засіб | версія · заголовок | що дає |
|---|---|---|
| `C::const_iterator` | C++98 · контейнер | тип ітератора, крізь який елемент лише читається |
| `c.cbegin()`, `c.cend()`, `c.crbegin()`, `c.crend()` | C++11 · члени контейнера | `const_iterator` на **неконстантному** контейнері |
| `std::cbegin(c)`, `std::cend(c)`, `std::crbegin(c)`, `std::crend(c)` | C++14 · `<iterator>` | те саме вільними функціями — працюють і на C-масиві |
| `std::ranges::cbegin(r)`, `std::ranges::cend(r)` | C++20 · `<ranges>` | те саме для діапазонів |
| `std::basic_const_iterator<It>`, `std::const_iterator<It>`, `std::make_const_iterator(it)` | C++23 · `<iterator>` | обгортка, що робить константним **будь-який** ітератор |
| `std::views::as_const(r)` | C++23 · `<ranges>` | вид «лише читати» над готовим діапазоном |

Дві історичні деталі пояснюють, чому цей ряд такий довгий.

Перша: до C++11 позицію в контейнер треба було передавати звичайним `iterator` — `vector::erase(iterator)`, `insert(iterator, …)`, — і `const_iterator` для цього не годився, хоч ніякого запису крізь нього й не робилося. Папір **N2350** («Container insert/erase and iterator constness») змінив ці підписи на `const_iterator`, і відтоді позицію можна отримувати через `cbegin()`, не втрачаючи права змінити контейнер.

Друга: `cbegin` на діапазоні спрацьовував не завжди. Прийом «узяти діапазон як `const` — і елементи стануть сталими» тримається на тому, що константність контейнера доходить до елементів; для [видів](root:sys-plang-cpp/ranges-pipelines), які всередині тримають посилання, вона туди не доходить, тож `ranges::cbegin` на такому діапазоні міг віддати цілком мінливий ітератор. Папір **P2278R4** («`cbegin` should always return a constant iterator») закрив діру в C++23: тепер результат за потреби загортається в `std::basic_const_iterator`, який гарантує константність незалежно від будови діапазону.

## Бібліотека: види й проштовхування вглиб

У невласницьких видів `const` доводиться писати двічі, і два записи означають протилежні речі:

| запис | сам вид | елементи |
|---|---|---|
| `std::span<T>` | можна переставити на інші дані | можна писати |
| `const std::span<T>` | не можна переставити | **можна писати** |
| `std::span<const T>` | можна переставити | не можна писати |
| `const std::span<const T>` | не можна переставити | не можна писати |

Потрібне майже завжди третє: «дивлюся й не чіпаю» — це `std::span<const T>` (C++20, `<span>`). Перетворення `span<T>` → `span<const T>` компілятор робить сам, тож звузити права по дорозі нічого не коштує. Те саме розрізнення закладене в [`span`](root:sys-plang-cpp/span-contiguous) і в `std::string_view`, який за будовою і є видом на сталі символи.

Коли ж константність треба **проштовхнути** крізь вказівник-поле, у мові інструмента немає — є бібліотечний, і той поза стандартом:

```cpp
// <experimental/propagate_const>, Library Fundamentals TS v2
template <class T> class propagate_const;
```

`std::experimental::propagate_const` загортає вказівник (звичайний або розумний) і показує його як вказівник на `const`, коли до нього дістаються крізь `const`-шлях. Класичне застосування — [PIMPL](root:sys-plang-cpp/pimpl), візерунок, де все нутро класу винесене в окремий тип за вказівником: без обгортки `const`-методи бачать поле як `Impl* const` і можуть кликати мінливі методи реалізації, з обгорткою — не можуть.

```cpp
class Widget {
    std::experimental::propagate_const<std::unique_ptr<Impl>> impl_;
public:
    void draw() const { impl_->paint(); }   // impl_ бачиться як const Impl* → paint() має бути const
    void resize()     { impl_->relayout(); }
};
```

Дві пастки: обгортка **не копіюється** — вона переміщувана, але не копійовна, тож клас із таким полем автоматичного копіювання не дістане; і вона й досі живе в `std::experimental` — до самого стандарту Library Fundamentals TS v2 її не довели, тож перед уживанням варто перевірити свою реалізацію бібліотеки.

## Коли const у підписі нічого не означає

`const` верхнього рівня на параметрі компілятор **відкидає**, коли визначає тип функції. Наслідки видно в трьох місцях одразу: у перевантаженні, у повторному оголошенні й у манґленому імені для лінкера.

| позиція `const` | входить у тип функції | видно тому, хто викликає |
|---|---|---|
| `void f(int n)` проти `void f(const int n)` | ні | ні — це **одна й та сама функція**, не перевантаження |
| `void f(int* const p)` | ні | ні — те саме |
| `void f(const int* p)` | так | так — окреме перевантаження |
| `void f(const int& r)` | так | так — окреме перевантаження |
| `int f() const` (метод) | так | так — добір за константністю об'єкта |
| `const int f()` (повернення скаляра) | так | ні — prvalue скалярного типу губить кваліфікацію |
| `const std::string f()` | так | так — і мовчки вимикає переміщення результату |

Практично з цієї таблиці випливають три звички. У **оголошенні** `const` верхнього рівня на параметрі — шум, його прибирають; в **означенні** він законний і корисний як обіцянка самому собі не крутити параметр усередині тіла. Повертати за значенням `const` не варто ніколи: для скаляра це порожній звук, для класу — тиха заборона перемістити результат. І остання: `const` **нижнього рівня** входить у манґлене ім'я, тому дописати його до параметра-посилання в уже опублікованій бібліотеці означає [зламати ABI](root:sys-plang-cpp/abi-stability-cpp) — старі об'єктні файли шукатимуть символ, якого більше немає.

Компілятори й аналізатори вміють стежити за цим самі:

```
-Wignored-qualifiers        (у складі -Wextra, GCC/Clang) — const на типі повернення, який ігнорується
clang-tidy readability-avoid-const-params-in-decls  — const верхнього рівня в оголошеннях
clang-tidy readability-const-return-type            — const на типі повернення
clang-tidy misc-const-correctness                   — локальні змінні, які могли б бути const
```

## Які конверсії константності компілятор робить сам

| з | у | можна | чому |
|---|---|---|---|
| `T*` | `const T*` | ✓ | звуження прав на одному рівні |
| `T&` | `const T&` | ✓ | те саме для посилань |
| `T[N]` | `const T*` | ✓ | розпад масиву плюс звуження |
| `const T*` | `T*` | ✗ | розширення прав — лише `const_cast` |
| `T**` | `T* const*` | ✓ | `const` став на рівні 1, нижче нічого не змінилось |
| `T**` | `const T**` | ✗ | крізь неї відкрився б шлях запису в `const`-об'єкт |
| `T**` | `const T* const*` | ✓ | `const` додано й на проміжному рівні |
| `std::span<T>` | `std::span<const T>` | ✓ | бібліотечна конверсія, не мовна |
| `std::shared_ptr<T>` | `std::shared_ptr<const T>` | ✓ | конверсійний конструктор; назад — `const_pointer_cast` |

Нижній: від char** три стрілки до char* const* (✓), до const char** (✗, червона), до const char* const* (✓); біля кожної короткий вислід. Унизу правило: додаєш const на глибині — постав його й на всіх проміжних рівнях](img/qual-conversions.svg)

*Конверсія кваліфікації дозволена, коли на кожному рівні права лише звужуються, а до того ж — коли `const` стоїть на всіх рівнях між верхнім і тим, куди його додали. Заборонений випадок посередині: без нього з'явився б законний шлях записати в сталий об'єкт крізь звичайний вказівник.*

## Що const-поле робить з операціями класу

Поле, оголошене `const`, виглядає як безкоштовна гарантія — і мовчки вимикає половину операцій типу.

| операція | з `const`-полем |
|---|---|
| конструктор за замовчуванням | вилучений, якщо поле не має ініціалізатора в класі й не є типом із власним конструктором за замовчуванням |
| копіювальний конструктор | працює |
| переміщувальний конструктор | оголошується, але поле однаково **копіюється** — із сталого джерела не забрати нутрощі |
| копіювальне присвоєння | **вилучене** |
| переміщувальне присвоєння | **вилучене** |
| деструктор | працює |

Поле-посилання (`T&`) поводиться так само: присвоєння вимкнене з тієї ж причини. А вилучене присвоєння відрізає тип від усього, що переставляє елементи:

```cpp
struct Config {
    const std::string name;   // виглядає «правильно»
    int retries;
};

std::vector<Config> v;
v.push_back({"a", 3});                        // ✓ конструюванням — можна
std::sort(v.begin(), v.end(), by_retries);    // ✗ sort присвоює елементи
v.erase(v.begin());                           // ✗ erase зсуває хвіст присвоєнням
std::swap(v[0], v[1]);                        // ✗ swap — це три присвоєння
```

Тому незмінність поля майже завжди краще виражати приватним полем без сетера: гарантія назовні та сама, а тип лишається повноцінним значенням із живими операціями (які саме операції треба тримати живими — у [правилі п'яти й правилі нуля](root:sys-plang-cpp/rule-of-five-zero)).

## Зразок, що збирає все докупи

Збирається як `-std=c++20`; статичні перевірки в ньому фіксують саме ті межі, на яких риси підводять.

```cpp
#include <iostream>
#include <span>
#include <type_traits>
#include <utility>
#include <vector>

static_assert( std::is_const_v<const int>);
static_assert(!std::is_const_v<const int&>);      // посилання ніколи не const-кваліфіковане
static_assert(!std::is_const_v<const int*>);      // const на мішені, не на стрілці
static_assert( std::is_const_v<int* const>);      // а тут — на стрілці
static_assert(std::is_same_v<std::add_const_t<int&>,          int&>);
static_assert(std::is_same_v<std::remove_const_t<const int*>, const int*>);
static_assert(std::is_same_v<std::remove_cvref_t<const int&>, int>);

class Table {
    std::vector<int> rows_{1, 2, 3};
    mutable std::size_t reads_ = 0;          // лічильник звернень — назовні невидимий

public:
    int&       at(std::size_t i)       { return rows_[i]; }
    const int& at(std::size_t i) const { ++reads_; return rows_[i]; }

    std::span<const int> view()  const { return rows_; }   // vector → span<const int>
    std::size_t          reads() const { return reads_; }
};

int main() {
    Table t;
    t.at(0) = 10;                            // об'єкт мінливий → неконстантне перевантаження
    int x = std::as_const(t).at(0);          // той самий t, але добір іде на const-версію

    std::span<const int> s = t.view();       // дивимось, не чіпаючи
    std::cout << x << ' ' << s.size() << ' ' << t.reads() << '\n';   // 10 3 1
}
```

Три речі, які тут варто побачити. `std::as_const(t)` не створює нової таблиці — `reads_` рахує звернення до **того самого** об'єкта, і саме тому наприкінці друкується `1`. Поле `reads_` позначене `mutable`, бо `const`-метод у нього пише, а назовні цей запис не видно: жодна відповідь класу від нього не змінюється. І `view()` віддає `span<const int>`, а не `const span<int>`, — інакше читач міг би переписати рядки крізь виданий йому вид.
