# ⚙️ Лінивий кеш усередині const-методу: п'ять версій одного класу

Клас `Document` тримає текст і вміє відповісти, скільки в ньому слів і який у нього геш. Відповісти — це пройти весь текст, тому природно порахувати один раз і запам'ятати, а метод лишити `const`, бо назовні він нічого не змінює. Далі — п'ять версій цього класу підряд, у робочому коді: перша не компілюється, друга компілюється й тихо ламається на двох потоках, третя правильна й повільна, четверта правильна й швидка, п'ята вміє ще й копіюватися. На кожному кроці — що саме ламається, як це побачити інструментом, а не на слово, і скільки коштує лагодження.

## Спільна частина: що ми рахуємо

Обидва значення дає один прохід по тексту, тому й тримати їх зручно разом.

```cpp
#include <cstddef>
#include <cstdint>
#include <string>

struct Summary {
    std::size_t words = 0;   // кількість слів
    std::string digest;      // геш тексту, шістнадцятковим рядком
};

// FNV-1a, 64 біти: одна з найпростіших пристойних некриптографічних геш-функцій
std::string to_hex(std::uint64_t v) {
    static const char* d = "0123456789abcdef";
    std::string out(16, '0');
    for (int i = 15; i >= 0; --i, v >>= 4) out[i] = d[v & 0xF];
    return out;
}

Summary compute_summary(const std::string& text) {
    std::uint64_t h = 0xcbf29ce484222325ull;      // FNV offset basis
    std::size_t words = 0;
    bool in_word = false;

    for (unsigned char c : text) {
        h = (h ^ c) * 0x100000001b3ull;           // FNV prime
        const bool space = (c == ' ' || c == '\n' || c == '\t' || c == '\r');
        if (space)            in_word = false;
        else if (!in_word)  { ++words; in_word = true; }
    }
    return Summary{words, to_hex(h)};
}
```

Функція чиста: той самий текст завжди дає той самий `Summary`. Саме ця чистота й робить кеш законним — вона гарантує, що запам'ятана відповідь ніколи не розійдеться з обчисленою наново. Якби `compute_summary` залежала ще від чогось (від часу, від глобальної таблиці, від локалі), кеш би вже брехав, і жоден замок цього не полагодив би. Запам'ятовувати взагалі можна лише результат [чистої функції](topic:sf-apps/pure-functions-side-effects) від того стану, який кеш стереже, — це передумова, яку не перевіряє ні компілятор, ні санітайзер.

Зверни увагу, що кеш — це **два** поля, а не одне: сам `Summary` і прапорець «уже пораховано». Так само влаштований `std::optional` усередині: значення плюс ознака зайнятості. Ми розписуємо їх руками навмисно — далі саме те, що записів два, і зробить гонку видимою очима.

## Версія 1: чесна спроба, яка не компілюється

```cpp
class Document {
    std::string text_;
    Summary     cache_;
    bool        ready_ = false;

public:
    explicit Document(std::string text) : text_(std::move(text)) {}

    std::size_t word_count() const {
        if (!ready_) {
            cache_ = compute_summary(text_);   // ✗
            ready_ = true;                     // ✗
        }
        return cache_.words;
    }
};
```

GCC відповідає рівно те, що відбувається:

```
error: assignment of member 'Document::cache_' in read-only object
error: assignment of member 'Document::ready_' in read-only object
```

Слова «read-only object» тут точні. Усередині `const`-методу `this` має тип `const Document*`, тому кожне поле бачиться зі своїм `const` верхнього рівня: `cache_` — це `const Summary`, `ready_` — це `const bool`. Компілятор не читає наших намірів і не знає, що ці два поля — не стан документа, а лише запам'ятана відповідь. Він бачить обіцянку в типі й тримає її.

Спокуса тут очевидна й майже завжди помилкова: зняти `const` з методу. Але `word_count()` — питання, а не команда, і зробити його неконстантним означає, що документ не можна буде питати крізь `const Document&`, тобто крізь звичайний спосіб передавати його у функції. Одне слово в підписі потягне за собою десятки правок угору по коду, і всі — у бік послаблення гарантій. Правильний хід протилежний: пояснити компіляторові, що саме ці два поля до контракту не належать.

## Версія 2: mutable — компілюється і тихо ламається

```cpp
class Document {
    std::string     text_;
    mutable Summary cache_;
    mutable bool    ready_ = false;

public:
    explicit Document(std::string text) : text_(std::move(text)) {}

    std::size_t word_count() const {
        if (!ready_) { cache_ = compute_summary(text_); ready_ = true; }
        return cache_.words;
    }
    std::string digest() const {
        if (!ready_) { cache_ = compute_summary(text_); ready_ = true; }
        return cache_.digest;
    }
};
```

Компілюється, працює, тести зелені. У однопотоковій програмі цей клас бездоганний: `word_count()` віддає те саме число скільки завгодно разів, просто вдруге швидше. Логічна константність дотримана.

А тепер два потоки питають той самий документ одночасно.

```cpp
#include <atomic>
#include <iostream>
#include <thread>

std::string make_text(int seed) {
    std::string s;
    for (int i = 0; i < 400; ++i) {            // рівно 400 слів
        s += "word";
        s += char('a' + (seed + i) % 26);
        s += ' ';
    }
    return s;
}

int main() {
    std::size_t bad = 0;

    for (int round = 0; round < 50000; ++round) {
        Document doc(make_text(round));        // свіжий об'єкт: кеш порожній
        std::atomic<int> gate{0};
        std::size_t a = 0, b = 0;

        auto worker = [&](std::size_t& out) {
            gate.fetch_add(1, std::memory_order_relaxed);
            while (gate.load(std::memory_order_relaxed) < 2)   // стартуємо разом
                std::this_thread::yield();
            out = doc.word_count();
        };

        std::thread t1(worker, std::ref(a));
        std::thread t2(worker, std::ref(b));
        t1.join();
        t2.join();

        if (a != 400 || b != 400) ++bad;
    }
    std::cout << "неправильних відповідей: " << bad << " із 100000\n";
}
```

Свіжий документ на кожному колі — обов'язковий, інакше кеш прогріється на першому ж виклику й гонитися буде нічому. Спільний лічильник `gate` вирівнює старт: без нього другий потік майже завжди приходить, коли перший уже все порахував, і вікно гонки не відкривається.

Запусти — і десь на першій-другій тисячі кіл програма впаде:

```
free(): double free detected in tcache 2
```

Ось що сталося. Обидва потоки бачать `ready_ == false`, обидва рахують, обидва присвоюють `cache_`. Присвоєння `Summary` — це присвоєння `std::string` усередині: звільнити свій старий буфер, виділити новий, скопіювати байти, записати вказівник і довжину. Два потоки роблять це над однією й тією самою парою полів. Один звільняє буфер, який другий у цю мить уже звільнив, — і алокатор ловить подвійне звільнення. Числа збіглися б (обидва порахували те саме), але рядок не переживає одночасного запису, бо запис рядка — це не одна дія, а чотири.

Тепер прибери з `Summary` поле `digest` і лиши тільки `words`. Програма перестане падати й надрукує `неправильних відповідей: 0`. І це найнебезпечніший момент усього прикладу: **нуль тут нічого не доводить**. Обидва потоки записали в `cache_.words` те саме число, тож збіг байтів приховав гонку. Це класичний [гейзенбаг](topic:sf-release/heisenbug) — помилка, яка ховається саме тоді, коли на неї дивишся.

Питати треба не програму, а інструмент, який перевіряє правило, а не наслідок:

```
$ g++ -std=c++20 -O1 -g -fsanitize=thread doc.cpp -o doc && ./doc
```

[ThreadSanitizer](topic:sf-release/thread-sanitizer) стежить не за значеннями, а за доступами: він бачить два незахищені звернення до однієї адреси з різних потоків, де хоч одне — запис, і повідомляє про це незалежно від того, чи зіпсувалися дані цього разу:

```
WARNING: ThreadSanitizer: data race (pid=4711)
  Write of size 8 at 0x7b0400000d20 by thread T2:
    #0 Document::word_count() const doc.cpp:23
  Previous write of size 8 at 0x7b0400000d20 by thread T1:
    #0 Document::word_count() const doc.cpp:23
SUMMARY: ThreadSanitizer: data race doc.cpp:23 in Document::word_count() const
```

Це [гонка даних](topic:sf-tasks/atomicity-races) за буквою стандарту, а гонка даних — [невизначена поведінка](topic:sf-lang/undefined-behavior). Слово «невизначена» означає, що зіпсовані числа — не найгірший сценарій, а найм'якший. Компілятор має право зробити з коду, у якому гонка неможлива за припущенням, що завгодно: продублювати читання `ready_` (перше побачило `false`, друге вже `true` — і повертається неініціалізований `cache_`), винести читання з циклу, переставити два записи місцями.

![Дві доріжки часу поруч. Ліва — потік A: бачить ready_ == false і рахує compute_summary(), потім запис 1 у cache_, потім запис 2 у ready_. Права — потік B: читає ready_ і бачить true, читає cache_ і бачить ще порожній, віддає сміття. Червона стрілка від запису прапорця в потоці A до читання прапорця в потоці B](img/lazy-cache-race.svg)

*Найтонший сценарій із можливих: потоки навіть не пишуть одночасно. Потік A записує кеш, потім прапорець — але це два звичайні незахищені записи, і ні компілятор, ні процесор не зобов'язані лишати їх у написаному порядку. Досить, щоб `ready_` ліг у пам'ять першим, і потік B побачить «готово» над ще незаповненим кешем.*

> 🔧 **Навіщо це.** Тут стає видно, чому C++11 підняв планку для `mutable`. До моделі пам'яті логічної константності справді вистачало: `word_count()` не змінює відповідей, отже `const` не бреше. Після — обіцянка `const` стала ширшою: об'єкт, розданий кільком потокам лише для читання, мусить це читання витримати. Клас із версії 2 цю обіцянку порушує тихо, у збірці без санітайзера й на однопотокових тестах він виглядає бездоганно. Саме тому [потокову безпеку](topic:sf-tasks/thread-safety) типу неможливо додати пізніше «за потреби»: до моменту, коли потреба виявиться, твій тип уже роздано в десяток місць як `const&`.

## Версія 3: mutable-м'ютекс — просто й правильно

```cpp
#include <mutex>

class Document {
    std::string        text_;
    mutable std::mutex m_;
    mutable Summary    cache_;
    mutable bool       ready_ = false;

    void ensure_locked() const {          // викликати ЛИШЕ під захопленим m_
        if (!ready_) { cache_ = compute_summary(text_); ready_ = true; }
    }

public:
    explicit Document(std::string text) : text_(std::move(text)) {}

    std::size_t word_count() const {
        std::lock_guard lock(m_);
        ensure_locked();
        return cache_.words;
    }
    std::string digest() const {
        std::lock_guard lock(m_);
        ensure_locked();
        return cache_.digest;             // копія під замком — назовні йде значення
    }
};
```

М'ютекс теж `mutable`, і це не косметика: захоплення замка змінює його стан, а робимо ми це з `const`-методу — без `mutable` версія 3 не скомпілюється так само, як версія 1. Тип `std::mutex` у полі — це нормально й правильно; докладніше про самі замки та їхні RAII-обгортки — у [м'ютексі й RAII-замках](topic:sys-plang-cpp/mutex-and-raii-locks).

Три речі тут зроблено навмисно, і кожна з них — окрема пастка, у яку легко впасти.

**`digest()` віддає копію, а не посилання.** Спокусливий підпис `const std::string& digest() const` заощадив би копіювання рядка — і повернув би посилання на дані, які захищає замок, уже після того, як `lock_guard` цей замок відпустив. Той, хто викликав, дістав би посилання на дані, яких у цю мить ніхто не стереже. Правило просте й безвиняткове: з-під замка назовні виходить **значення**, не посилання й не ітератор.

**`ensure_locked()` приватний і має в назві слово «locked».** Це найдешевша доступна документація інваріанта, який компілятор не перевіряє. Функція, безпечна лише під замком, і функція, яка сама бере замок, — різні речі, і плутанина між ними закінчується або дедлоком (подвійне захоплення нерекурсивного `std::mutex` — невизначена поведінка), або гонкою.

**Виняток обробляється сам собою.** Якщо `compute_summary` кине `std::bad_alloc`, `lock_guard` відпустить замок під час розкрутки стека, а `ready_` лишиться `false` — наступний виклик просто спробує ще раз. Порядок рядків тут важить: спершу присвоюємо `cache_`, і лише потім ставимо прапорець. Зроби навпаки — і об'єкт після винятку тверджуватиме, що кеш готовий, а він порожній. Це та сама [сильна гарантія безпеки винятків](topic:sys-plang-cpp/exception-safety-guarantees), тільки в одному рядку.

### Чому подвійна перевірка тут зайва

Перше, що хочеться дописати, побачивши замок на кожному виклику, — швидкий вихід перед ним:

```cpp
    std::size_t word_count() const {
        if (ready_) return cache_.words;      // ✗ і ось тут усе знову зламалося
        std::lock_guard lock(m_);
        ensure_locked();
        return cache_.words;
    }
```

Це рівно та сама гонка, від якої ми щойно втекли. М'ютекс упорядковує лише ті потоки, які **обидва** його беруть. Читання `ready_` і `cache_` поза замком не бере його зовсім, а інший потік у цю мить пише в ті самі поля під замком — санітайзер повідомить про гонку тими самими словами, що й для версії 2. Швидка перевірка над незахищеними полями — не оптимізація, а повернення помилки під новою назвою.

Полагодити це можна, але не одним рядком: прапорець мусить стати атомарним із правильним порядком пам'яті — і це вже інша конструкція, версія 4. Тому питання не «додати чи не додати перевірку», а «чи варте це того», і відповідь дає замір. Незайнятий `std::mutex` коштує пари атомарних операцій — десятки наносекунд; якщо `word_count()` викликають раз на дію користувача, цієї вартості просто не видно ні в чому. Історія тут повчальна: візерунок подвійної перевірки роками ходив по книжках як «швидкий безпечний ледачий Singleton», доки Скотт Меєрс і Андрей Александреску не показали у статті «C++ and the Perils of Double-Checked Locking» (Dr. Dobb's, липень–серпень 2004), що до появи моделі пам'яті записати його правильно в C++ було **неможливо** — жодною комбінацією `volatile`, бо мова просто не мала слів, якими можна було б заборонити перестановку двох записів. Модель пам'яті C++11 ці слова дала.

## Версія 4: атомарний прапорець — правильно і швидко

```cpp
#include <atomic>
#include <mutex>

class Document {
    std::string             text_;
    mutable std::mutex      m_;
    mutable Summary         cache_;
    mutable std::atomic<bool> ready_{false};

    void fill() const {
        std::lock_guard lock(m_);
        if (!ready_.load(std::memory_order_relaxed)) {   // під замком — досить relaxed
            cache_ = compute_summary(text_);
            ready_.store(true, std::memory_order_release);
        }
    }

public:
    explicit Document(std::string text) : text_(std::move(text)) {}

    std::size_t word_count() const {
        if (!ready_.load(std::memory_order_acquire)) fill();
        return cache_.words;
    }
    std::string digest() const {
        if (!ready_.load(std::memory_order_acquire)) fill();
        return cache_.digest;
    }
};
```

Уся правильність тримається на парі `release` — `acquire`, і варто розібрати, що саме ці два слова обіцяють. Запис `ready_.store(true, release)` каже: усе, що цей потік записав **до** цього рядка, стає видимим для будь-якого потоку, який прочитає з `ready_` значення `true` через `acquire`. Читання `ready_.load(acquire)`, побачивши `true`, каже симетричне: усе, що записав потік-публікатор, тепер видно й мені. Разом вони будують місток «раніше-ніж» між двома потоками — рівно те, чого не було у версії 2. Це загальна механіка [порядку пам'яті](topic:sf-tasks/memory-ordering-barriers), і `std::atomic` — місце, де вона в C++ записується словами; докладніше — в [std::atomic і порядку пам'яті](topic:sys-plang-cpp/std-atomic).

Заміни `release`/`acquire` на `relaxed` — і клас зламається знову, причому найпідступнішим чином: `relaxed` гарантує атомарність самого прапорця й **нічого** про сусідні записи, тож `ready_` знову може стати видимим раніше за `cache_`. Це саме та картинка, яку показував малюнок вище, і на слабких моделях пам'яті — ARM, POWER — вона реалізується не в теорії, а на живому залізі.

Внутрішнє читання під замком може бути `relaxed`, бо взаємне виключення й порядок тут уже дає сам м'ютекс: `ready_` записує тільки той, хто тримає `m_`.

Другу перевірку всередині `fill()` викидати не можна. Поки перший потік рахує, другий заходить у `fill()` і чекає на замку; коли він його отримає, кеш уже готовий — і без перевірки він порахував би все вдруге поверх уже записаного. Не гонка (обидва під замком), але подвійна робота й зайве присвоєння рядка.

**Скільки коштує швидкий шлях.** На x86-64 читання `bool` з порядком `acquire` компілюється в звичайну інструкцію читання — апаратна модель x86 і так не переставляє читання з читаннями, тому впорядкування безкоштовне:

```
; gcc -O2, word_count() на прогрітому кеші
movzx  eax, BYTE PTR [rdi+72]     ; ready_.load(acquire) — просто читання
test   al, al
je     .Lslow
mov    rax, QWORD PTR [rdi+40]    ; cache_.words
ret
```

На aarch64 замість звичайного читання стане `ldarb` — справжнє acquire-читання, на кілька тактів дорожче, але це все одно на порядок дешевше за захоплення замка.

### Варіант на once_flag

Те саме можна записати коротше, віддавши всю синхронізацію бібліотеці:

```cpp
#include <mutex>

class Document {
    std::string          text_;
    mutable std::once_flag once_;
    mutable Summary      cache_;

public:
    explicit Document(std::string text) : text_(std::move(text)) {}

    std::size_t word_count() const {
        std::call_once(once_, [this] { cache_ = compute_summary(text_); });
        return cache_.words;
    }
};
```

[`std::call_once`](topic:sys-plang-cpp/call-once-lazy-init) гарантує, що лямбда виконається рівно один раз, а її завершення буде «раніше-ніж» повернення з усіх інших викликів із тим самим прапорцем. Порядку пам'яті тут немає взагалі — його немає де переплутати, і це головна перевага варіанта. Три речі, які варто знати, перш ніж його брати.

**Виняток не зараховується.** Якщо лямбда кине, `call_once` пропустить виняток нагору, а прапорець лишиться неставленим — наступний виклик спробує ще раз. Поведінка правильна й саме та, що потрібна кешу, але історично небездоганна в реалізаціях: libstdc++ на POSIX будує `call_once` поверх `pthread_once`, і в glibc на ARM та ppc64le виняток із ініціалізатора підвішував `pthread_once` намертво (помилка GCC 66146; libstdc++ відтоді вважає `pthread_once` необізнаним із винятками скрізь, крім цілей, де протилежне доведено).

**Ціна виклику вища за атомарне читання.** Швидкий шлях `pthread_once` — теж атомарне читання й перехід, але дійти до нього треба через невбудовуваний виклик у бібліотеку. Тому за швидкодією `call_once` сідає між замком і атомарним прапорцем, ближче до першого. Якщо потрібне саме читання ціною в одну інструкцію, версія 4 із явним `atomic<bool>` лишається єдиним варіантом.

**Прапорець не можна ні скопіювати, ні переставити назад.** Це вилазить боком у наступному кроці — і це найдорожча властивість `once_flag`.

Спокуса, повз яку варто пройти свідомо: локальна статична змінна. З C++11 ініціалізація функційно-локальної статики потокобезпечна за стандартом — папір N2660 Лоуренса Кровла «Dynamic Initialization and Destruction with Concurrency» (2008) зробив так, що інший потік, який зайшов у те саме оголошення, чекає завершення ініціалізації. Компілятор ставить туди рівно ту саму подвійну перевірку, тільки безкоштовно для програміста. Але для нашої задачі це не працює взагалі: статика в методі одна на всю програму, а кеш нам потрібен **свій у кожного документа**. Механізм правильний — область дії не та.

![Таблиця з чотирьох рядків і чотирьох стовпців: варіант кеша, що на гарячому шляху, один потік, кілька потоків. Рядок mutable-поле без синхронізації — читання поля, ~2 нс, гонка = UB, виділений червоним. Рядок mutable mutex на кожному виклику — lock плюс unlock, ~20 нс, ~125 нс і росте. Рядок atomic-прапорець плюс mutex на повільному — acquire-читання, ~2 нс, ~2 нс не росте. Рядок once_flag плюс call_once — виклик у бібліотеку, між ними, між ними](img/lazy-cache-cost.svg)

*Наскільки різняться версії на прогрітому кеші. Найважливіший тут останній стовпець: замок не просто дорожчий, він **дорожчає з кожним читачем**, бо всі вони штовхаються за одну кеш-лінію. Атомарне читання рядка, у який ніхто не пише, обслуговується з власного L1 кожного ядра й не дорожчає зовсім.*

## Замір: як не збрехати самому собі

```cpp
#include <chrono>
#include <cstdio>

template <class Doc>
void bench(const char* name, const Doc& doc, int reps) {
    doc.word_count();                                   // прогріти кеш

    volatile std::size_t sink = 0;                      // щоб цикл не викинули
    const auto t0 = std::chrono::steady_clock::now();
    for (int i = 0; i < reps; ++i) sink += doc.word_count();
    const auto t1 = std::chrono::steady_clock::now();

    const double ns = std::chrono::duration<double, std::nano>(t1 - t0).count() / reps;
    std::printf("%-34s %7.2f нс/виклик\n", name, ns);
}
```

Три речі, без яких замір нічого не показує. `volatile sink` — інакше оптимізатор побачить, що результат нікуди не йде, і викине весь цикл; поміряний нуль ти приймеш за перемогу. Прогрів до старту годинника — інакше в перший виклик потрапить увесь `compute_summary`, і на тисячі повторів він розмажеться в рівний шум. І `steady_clock`, а не `system_clock`: перший монотонний, другий може стрибнути назад посеред заміру, бо його підправив NTP.

Головний вимір цієї задачі — не однопотоковий. Постав `bench` у чотири потоки на **одному й тому самому** документі — і побачиш те, заради чого все й затівалося:

```cpp
    std::vector<std::thread> ts;
    for (int i = 0; i < 4; ++i)
        ts.emplace_back([&] { bench("4 потоки", doc, 10'000'000); });
    for (auto& t : ts) t.join();
```

Порядки величини, до яких зводяться всі чотири версії, добре відомі й лягають на кілька чітких сходинок. Тревіс Даунз у розборі «A Concurrency Cost Hierarchy» заміряв їх на Skylake 2.6 ГГц і розклав по сходинках: звичайна інструкція без синхронізації — близько 2 нс; незайнята атомарна операція — близько 10 нс; те саме під суперництвом двох потоків — 100–125 нс, і `std::mutex` там лягає рівно на цю сходинку. Твоя машина дасть інші абсолютні числа, але відстані між сходинками лишаться.

Читати цю таблицю треба по останньому стовпцю. Однопотоково замок коштує вдесятеро більше за читання поля — прикро, але майже завжди байдуже. Багатопотоково він коштує вшістдесятеро більше **й погіршується з кожним новим читачем**: усі вони по черзі змінюють одну кеш-лінію, і вона ганяє між ядрами. Атомарне читання не дорожчає взагалі, бо в лінію, яку ніхто не пише, кожне ядро дивиться зі свого L1 у спільному стані. Ось справжній аргумент за подвійну перевірку — і він з'являється тільки тоді, коли читачів кілька, а виклик гарячий. Механіка цього — у [когерентності кешів](topic:hw-arch/cache-coherence).

Дві пастки, у які тут заходять із добрими намірами. Перша: взяти `std::shared_mutex`, «щоб читачі не блокували одне одного». Захоплення на читання теж збільшує спільний лічильник, тобто теж пише в одну лінію, а коштує дорожче за звичайний `std::mutex`; на критичній секції в кілька наносекунд [shared_mutex](topic:sys-plang-cpp/shared-mutex) програє однозначно. Друга: якщо документи лежать щільно в масиві, прапорці двох сусідніх об'єктів можуть потрапити в одну кеш-лінію — і перші виклики почнуть штовхатися між зовсім не пов'язаними об'єктами; це [хибне спільне використання](topic:hw-arch/false-sharing), і воно зникає, щойно кеші прогріваються.

## Версія 5: що робиться з кешем при копіюванні й переміщенні

Щойно в класі з'явився `mutable std::mutex`, `Document` перестав бути повноцінним значенням, і компілятор про це не попередить, доки не спробуєш:

```cpp
std::vector<Document> docs;
docs.push_back(Document("текст"));   // ✗ use of deleted function
```

`std::mutex` не копіюється й не переміщується, тому неявний копіювальний конструктор і копіювальне присвоєння оголошуються **вилученими**, а неявних переміщувальних не з'являється взагалі. Правило тут звичайне: клас із некопійовним полем некопійовний, і додати п'ять спеціальних функцій руками доведеться самому — це той випадок, коли [правило п'яти](topic:sys-plang-cpp/rule-of-five-zero) не порада, а вимога компілятора.

Спершу — рішення по суті, бо саме воно, а не синтаксис, тут головне.

**Копію кешу переносити треба.** Копія документа має той самий текст, а `compute_summary` — чиста функція від тексту, отже запам'ятана відповідь для копії правильна. Переносити її — не оптимізація, а збереження вже зробленої роботи. Але правило, за яким це вирішують, ширше й важливіше за цей висновок: **кеш копіюється разом зі станом тоді й лише тоді, коли він є функцією від скопійованого стану**. Якби в кеші лежав вказівник усередину самого об'єкта, ітератор у власний контейнер, реєстрація в глобальній таблиці за адресою або час обчислення з терміном придатності — усе це прив'язане до особи об'єкта, а не до його вмісту, і в копії такий кеш треба скидати.

**Переміщення мусить скинути кеш джерела.** Після переміщення `text_` джерело лишається [в дійсному, але невизначеному стані](topic:sys-plang-cpp/move-semantics) — його рядок майже напевно порожній, але стандарт цього не обіцяє. Якщо лишити прапорець готовності, джерело почне впевнено відповідати «400 слів» над порожнім текстом. Формально ним і не можна користуватися, крім присвоєння й знищення, — практично ж перший `assert(doc.word_count() == recount(doc.text()))` у зневаджувальній збірці спрацює саме тут, і шукати причину доведеться довго.

```cpp
class Document {
    std::string             text_;
    mutable std::mutex      m_;
    mutable Summary         cache_;
    mutable std::atomic<bool> ready_{false};

public:
    explicit Document(std::string text) : text_(std::move(text)) {}

    Document(const Document& other) {
        std::lock_guard lock(other.m_);          // джерело живе — його треба стерегти
        text_  = other.text_;
        cache_ = other.cache_;
        ready_.store(other.ready_.load(std::memory_order_relaxed),
                     std::memory_order_relaxed);
        // m_ — свіжий власний м'ютекс: новий об'єкт ще нікому не роздано
    }

    Document(Document&& other) noexcept
        : text_(std::move(other.text_)),
          cache_(std::move(other.cache_)),
          ready_(other.ready_.load(std::memory_order_relaxed)) {
        other.cache_ = Summary{};                          // джерело більше не має тексту —
        other.ready_.store(false, std::memory_order_relaxed);  // його кеш став брехнею
    }

    Document& operator=(const Document& other) {
        if (this == &other) return *this;        // обов'язково, і не заради швидкості
        std::scoped_lock lock(m_, other.m_);     // C++17: обидва разом, без дедлоку
        text_  = other.text_;
        cache_ = other.cache_;
        ready_.store(other.ready_.load(std::memory_order_relaxed),
                     std::memory_order_relaxed);
        return *this;
    }

    Document& operator=(Document&& other) noexcept {
        if (this == &other) return *this;
        text_  = std::move(other.text_);
        cache_ = std::move(other.cache_);
        ready_.store(other.ready_.load(std::memory_order_relaxed),
                     std::memory_order_relaxed);
        other.cache_ = Summary{};
        other.ready_.store(false, std::memory_order_relaxed);
        return *this;
    }

    ~Document() = default;

    // word_count(), digest() і fill() — без змін, як у версії 4
};
```

Розберімо, чому кожне з цих рішень саме таке.

**У копіювальному конструкторі захоплюємо замок джерела, а свій — ні.** Об'єкт, що будується, ще нікому не видано: ні з якого іншого потоку до нього не дістатися, стерегти нічого. А от джерело цілком може в цю мить прогрівати свій кеш з іншого потоку, і копіювати його поля без замка — та сама гонка, що у версії 2. Замок береться через `other.m_`, і працює це лише тому, що поле `mutable`: інакше `const Document&` не дав би його захопити.

**Копіювальне присвоєння бере обидва замки одним `std::scoped_lock`.** Два `lock_guard` підряд у сталому порядку «спершу свій, потім чужий» дають дедлок за секунду: потоки виконують `a = b` і `b = a` одночасно, кожен тримає свій замок і чекає на чужий. `std::scoped_lock` (C++17) захоплює обидва алгоритмом, що не дедлочиться, — це `std::lock` під капотом. До C++17 те саме писали трьома рядками: `std::lock(m_, other.m_)` і два `lock_guard` з `std::adopt_lock`.

**Перевірка на самоприсвоєння тут не про швидкодію.** `scoped_lock(m_, m_)` над одним і тим самим `std::mutex` — це рекурсивне захоплення нерекурсивного м'ютекса, тобто невизначена поведінка. У класі без замків самоприсвоєння — зазвичай просто зайва робота; тут його пропуск — помилка.

**`noexcept` на переміщеннях чесний лише тому, що ми не беремо замок.** І це найтонше місце всієї версії. `std::mutex::lock()` може кинути `std::system_error`, тож переміщувальний конструктор, який щось замикає, не має права називатися `noexcept`. А без `noexcept` `std::vector<Document>` під час зростання переходить на **копіювання** замість переміщення: `vector` користується `std::move_if_noexcept`, бо інакше не зміг би дати сильну гарантію на `push_back`. Тобто один захоплений замок усередині переміщення тихо перетворює всі перерозподіли вектора на копіювання рядків.

Вихід — не хитрощі, а розмежування права: **копіювати живий спільний об'єкт законно, переміщувати — ні**. Переміщення забирає нутрощі, тому воно вимагає одноосібного володіння джерелом; якщо на джерело в цю мить дивиться ще хтось із іншого потоку, програма зламана незалежно від замків. Тому замок у копіювальному конструкторі стереже реальний сценарій, а замок у переміщувальному стеріг би вже неможливий — і платив би за це втратою `noexcept`.

І останнє, що змикає цей крок із попереднім: версія на `std::once_flag` цієї свободи не має зовсім. `once_flag` не копіюється, не переміщується й не має способу сказати «вважай, що виклик уже відбувся». Копія такого документа завжди дістає свіжий прапорець, тобто **гарантовано перерахує кеш заново**, хоч текст і той самий. Для дорогого обчислення й коду, який часто копіює документи, це вирішальний аргумент проти найкоротшого варіанта.

## Що з цього обирати

Порядок рішень тут зворотний до порядку версій.

Перше питання — не «який замок», а **чи потрібна лінивість узагалі**. Порахувати `Summary` у конструкторі й зробити поля звичайними, не `mutable`, — це нуль синхронізації, нуль гонок, нуль спеціальних функцій, повністю копійовний і переміщуваний тип. [Ліниве обчислення](topic:sf-lang/lazy-evaluation) окупається лише тоді, коли обчислення справді дороге **і** справді часто не потрібне; якщо документ майже завжди питають хоча б раз, лінивість не заощаджує нічого, зате коштує всього, про що ця стаття.

Якщо лінивість потрібна — бери версію 3. `mutable std::mutex` плюс `lock_guard` — найкоротша конструкція, у якій нема чого переплутати, і десятки наносекунд на виклик у переважній більшості коду просто не помітні.

На версію 4 переходь **після заміру**, а не замість нього, і замір робити треба той, що з кількома потоками: різниця, заради якої вводять атомарний прапорець, живе саме в останньому стовпці таблиці. Ознаки, за якими варто піти й поміряти: виклик усередині гарячого циклу, кілька читачів на одному об'єкті, профіль, у якому [видно](topic:sf-release/profiling) чекання на замку.

Версію на `once_flag` бери, коли обчислення одне, копіювання об'єкта не трапляється й хочеться найменше коду, у якому можна помилитися.

І перевіряти все це треба інструментом, а не міркуванням: зелений тест на одному потоці не бачить жодної з описаних тут помилок, а `-fsanitize=thread` бачить їх усі — навіть у прогоні, де вони цього разу не проявилися.
