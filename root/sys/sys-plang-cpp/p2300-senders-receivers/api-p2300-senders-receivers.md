# 📋 Довідник API: Концепти, CPO та алгоритми std::execution

Цей довідник містить вичерпну технічну специфікацію інтерфейсів, концептів C++20/C++26, об'єктів точок кастомізації (Customization Point Objects, CPO), стандартних алгоритмів-адаптерів та запитів середовища бібліотеки `std::execution` (документ P2300). Довідник призначений для використання як структурований технічний орієнтир при написанні, налагодженні та інтеграції асинхронних компонентів стандарту C++26.

---

## 1. Фундаментальні концепти моделі виконання

Простір імен `std::execution` визначає набір концептів C++20, що фіксують контракти між описувачами асинхронних операцій, їхніми споживачами та контекстами виконання безпосередньо на етапі компіляції. Завдяки концептам будь-які помилки несумісності типів сигналів або відсутності методів виявляються статично, не призводячи до незрозумілих багаторівневих повідомлень компілятора.

### `std::execution::receiver<R>`
Концепт перевіряє, що тип `R` здатний виступати споживачем асинхронних результатів, підтримує семантику переміщення у пам'яті та надає доступ до об'єкта свого середовища виконання через точку кастомізації `get_env`. Приймач є кінцевою точкою доставки результатів асинхронної роботи і зобов'язаний реалізовувати протокол обробки сигналів.

```cpp
template <class R>
concept receiver =
    std::move_constructible<std::remove_cvref_t<R>> &&
    std::constructible_from<std::remove_cvref_t<R>, R> &&
    requires(const std::remove_cvref_t<R>& r) {
        { std::execution::get_env(r) } -> std::execution::queryable;
    };
```
- **Вимоги до типу**: тип `R` не повинен бути посиланням при перевірці базових властивостей; об'єкт середовища, повернутий викликом `get_env(r)`, зобов'язаний задовольняти концепт `queryable`, що дозволяє запитувати властивості контексту (токени скасування, планувальники, алокатори).
- **Семантичні інваріанти**: приймач гарантує, що жоден із його каналів завершення не викликається повторно після першого виклику будь-якого з каналів (`set_value`, `set_error` або `set_stopped`). Будь-який сигнал завершення є термінальним.

### `std::execution::receiver_of<R, CompletionSignatures>`
Уточнює концепт `receiver`, перевіряючи, що приймач `R` підтримує всі сигнатури завершення, перелічені у списку `CompletionSignatures`. Це забезпечує повну перевірку сумісності між результатами, які сендер здатний згенерувати, та сигнатурами, які приймач здатний обробити.

```cpp
template <class R, class Completions>
concept receiver_of =
    std::execution::receiver<R> &&
    /* R підтримує всі сигнатури з Completions через set_value/set_error/set_stopped */;
```
- **Призначення**: використовується алгоритмами зв'язування `connect` для запобігання ситуаціям, коли сендер намагається передати типи даних, які приймач не може прийняти через відсутність відповідного перевантаження методу `set_value` або `set_error`.

### `std::execution::sender<S>`
Оголошує тип `S` лінивим описувачем асинхронної операції. Сендер представляє обчислювальний вираз або граф задач, але не ініціює жодних обчислень і не виділяє ресурси до моменту явного зв'язування з приймачем та запуску.

```cpp
template <class S>
concept sender =
    std::move_constructible<std::remove_cvref_t<S>> &&
    !std::execution::is_sender_v<S> &&
    requires(S&& s, const std::execution::empty_env& env) {
        std::execution::get_completion_signatures(s, env);
    };
```
- **Вимоги**: сендер зобов'язаний оголошувати підтримувані канали через внутрішній тип `completion_signatures` або через спеціалізацію функціонального об'єкта `get_completion_signatures`.
- **Властивості**: створення, копіювання або переміщення сендера є дешевою операцією конструювання легкої структури-дескриптора на стеку і не повинно виконувати блокуючих дій чи важких системних викликів.

### `std::execution::sender_to<S, R>`
Перевіряє, що сендер `S` та приймач `R` сумісні за типами сигналів і можуть бути з'єднані за допомогою виклику точки кастомізації `std::execution::connect(s, r)`.

```cpp
template <class S, class R>
concept sender_to =
    std::execution::sender<S> &&
    std::execution::receiver<R> &&
    requires(S&& s, R&& r) {
        std::execution::connect(std::forward<S>(s), std::forward<R>(r));
    };
```
- **Призначення**: гарантує, що операція `connect` є валідною і повертає коректний об'єкт стану операції `operation_state`.

### `std::execution::operation_state<O>`
Концепт об'єкта стану операції. Стан операції інкапсулює всі ресурси, системні дескриптори, буфери проміжних даних та зворотні посилання, необхідні для фізичного виконання операції.

```cpp
template <class O>
concept operation_state =
    std::destructible<O> &&
    std::is_object_v<O> &&
    requires(O& o) {
        { std::execution::start(o) } noexcept;
    };
```
- **Заборона переміщення**: об'єкти, що реалізують `operation_state`, є строго нерухомими (`non-movable` і `non-copyable`). Конструктори та оператори копіювання/переміщення мають бути видалені (`= delete`). Це гарантує стабільність адреси об'єкта в пам'яті, що дозволяє безпечно реєструвати низькорівневі вказівники у системних викликах ОС або драйверах.
- **Вимога `noexcept`**: метод `start(o)` гарантовано не викидає винятків. Будь-які системні або логічні помилки запуску передаються виключно асинхронно через канал `set_error`.

### `std::execution::scheduler<Sch>`
Концепт легковажної ручки (handle) планувальника контекстів виконання. Планувальник представляє обчислювальний ресурс (пул потоків, графічний процесор, чергу ядра) і слугує фабрикою початкових сендерів.

```cpp
template <class Sch>
concept scheduler =
    std::equality_comparable<Sch> &&
    std::copy_constructible<Sch> &&
    requires(Sch&& sch) {
        { std::execution::schedule(std::forward<Sch>(sch)) } -> std::execution::sender;
    };
```
- **Вимоги**: об'єкти планувальника мають бути дешевими для копіювання за значенням, підтримувати перевірку на рівність `==` та повертати валідний Sender при виклику `schedule(sch)`.

## 2. Об'єкти точок кастомізації (CPO)

Точки кастомізації (Customization Point Objects, CPO) викликаються як глобальні константні функціональні об'єкти, що запобігають конфліктам просторів імен та ізолюють виклики через механізм ADL (Argument-Dependent Lookup). Кожен CPO інкапсулює правила пошуку користувацьких перевизначень (через методи класу або приховані дружні функції `friend`).

### Канали сповіщення приймача (Completion Channels)

| CPO | Сигнатура виклику | Призначення та семантика | Вимоги безпеки |
| :--- | :--- | :--- | :--- |
| `std::execution::set_value` | `set_value(rcvr, args...)` | Повідомляє про успішне завершення обчислення та передає $0..N$ результуючих значень у приймач. | Зобов'язаний бути `noexcept` |
| `std::execution::set_error` | `set_error(rcvr, err)` | Повідомляє про аварійне завершення операції та передає об'єкт помилки (`std::exception_ptr`, `std::error_code` або користувацьку структуру). | Зобов'язаний бути `noexcept` |
| `std::execution::set_stopped` | `set_stopped(rcvr)` | Повідомляє про штатне скасування операції через токен скасування `std::stop_token`. | Зобов'язаний бути `noexcept` |

### Протокол життєвого циклу операції

| CPO | Сигнатура виклику | Опис дії | Повернений тип |
| :--- | :--- | :--- | :--- |
| `std::execution::connect` | `connect(snd, rcvr)` | Зв'язує опис операції з її споживачем, створюючи об'єкт стану операції на стеку. | Тип, що задовольняє `operation_state` |
| `std::execution::start` | `start(op_state)` | Ініціює фізичне виконання асинхронної роботи у відповідному контексті. | `void` (гарантовано `noexcept`) |
| `std::execution::schedule` | `schedule(sch)` | Породжує базовий сендер, що переводить виконання на контекст вказаного планувальника. | Тип, що задовольняє `sender` |

## 3. Фабрики базових сендерів (Sender Factories)

Фабрики створюють початкові сендери з літералів, значень, помилок або контекстів планувальників без потреби у попередніх асинхронних операціях.

### `std::execution::just`
Створює сендер, який при запуску негайно передає передані значення у канал `set_value` приймача.

```cpp
template <class... Ts>
/* sender */ just(Ts&&... values);
```
- **Канал завершення**: викликає `set_value(rcvr, std::forward<Ts>(values)...)`.
- **Семантика пам'яті**: якщо передано rvalue-аргументи, вони зберігаються всередині сендера за значенням і переміщуються у приймач під час виконання операції.
- **Приклад використання**:
```cpp
auto snd = std::execution::just(42, std::string("payload"));
```

### `std::execution::just_error`
Створює сендер, який при запуску негайно передає збережений об'єкт помилки у канал `set_error`.

```cpp
template <class Error>
/* sender */ just_error(Error&& err);
```
- **Канал завершення**: викликає `set_error(rcvr, std::forward<Error>(err))`.
- **Приклад використання**:
```cpp
auto snd = std::execution::just_error(std::make_exception_ptr(std::runtime_error("network timeout")));
```

### `std::execution::just_stopped`
Створює сендер, який при запуску негайно надсилає сигнал скасування у канал `set_stopped`.

```cpp
/* sender */ just_stopped();
```
- **Канал завершення**: викликає `set_stopped(rcvr)`.
- **Призначення**: використовується для раннього переривання конвеєрів або умовного повернення з гілок, де операція не повинна продовжуватися.

### `std::execution::read_env`
Створює сендер, який зчитує параметр із середовища приймача за переданим тегом запиту і передає прочитане значення у канал `set_value`.

```cpp
template <class Tag>
/* sender */ read_env(Tag tag);
```
- **Приклад використання**:
```cpp
auto snd = std::execution::read_env(std::execution::get_stop_token);
```

## 4. Алгоритми-адаптери сендерів (Sender Adapters)

Адаптери приймають один або кілька сендерів як вхідні параметри та повертають новий складений сендер. Вони підтримують функціональний синтаксис конвеєра через перевантажений оператор `|`.

### `std::execution::then`
Синхронно трансформує значення успішного каналу (`set_value`), застосовуючи користувацьку функцію `f`.

```cpp
template <sender S, class F>
/* sender */ then(S&& snd, F&& f);
```
- **Правила трансформації**: якщо вхідний сендер `snd` передає аргументи `(a, b)`, адаптер викликає `f(a, b)` і надсилає отриманий результат у наступний `set_value`. Якщо `f` повертає `void`, наступний приймач отримує виклик `set_value()` без аргументів.
- **Безпека винятків**: якщо виклик `f` викидає виняток, адаптер автоматично перехоплює його та перетворює на асинхронний виклик `set_error(rcvr, std::current_exception())`.

### `std::execution::upon_error` та `std::execution::upon_stopped`
Синхронна обробка аварійних сигналів та скасувань.

```cpp
template <sender S, class F>
/* sender */ upon_error(S&& snd, F&& f);

template <sender S, class F>
/* sender */ upon_stopped(S&& snd, F&& f);
```
- **Семантика `upon_error`**: якщо вхідний сендер завершується викликом `set_error(err)`, адаптер викликає функцію відновлення `f(err)`, а її результат спрямовує у канал `set_value`. Це дозволяє безпечно відновити нормальне виконання після збою.
- **Семантика `upon_stopped`**: якщо операція була скасована, викликається функція `f()`, перетворюючи сигнал зупинки на звичайне значення у каналі `set_value`.

### `std::execution::let_value` (Монадичне зв'язування)
Приймає результат попереднього сендера та передає його у функцію `f`, яка **повертає новий сендер**. Це дозволяє динамічно будувати наступні кроки асинхронного конвеєра залежно від отриманих проміжних даних.

```cpp
template <sender S, class F>
/* sender */ let_value(S&& snd, F&& f);
```
- **Аналоги для інших каналів**: `let_error(snd, f)` — асинхронне відновлення після помилки із поверненням нового сендера; `let_stopped(snd, f)` — асинхронне виконання альтернативної операції при скасуванні.

### `std::execution::starts_on` та `std::execution::continues_on`
Декларативне керування контекстами виконання операцій.

```cpp
// Запускає виконання всього вхідного сендера snd на планувальнику sch
template <scheduler Sch, sender S>
/* sender */ starts_on(Sch&& sch, S&& snd);

// Переносить виконання наступних операцій ланцюжка на планувальник sch
template <sender S, scheduler Sch>
/* sender */ continues_on(S&& snd, Sch&& sch);
```
- **Різниця між адаптерами**: `starts_on` гарантує, що початкова точка входу сендера `snd` буде запланована на `sch`; `continues_on` перехоплює сигнал завершення `snd` і виконує перемикання контексту перед викликом наступного приймача.

### `std::execution::when_all`
Паралельне розгалуження та злиття (Fork-Join).

```cpp
template <sender... Senders>
/* sender */ when_all(Senders&&... snds);
```
- **Канал `set_value`**: збирає всі значення, повернуті переданими сендерами, у єдиний спільний кортеж аргументів `set_value(rcvr, val1..., val2..., ...)`.
- **Політика скасування**: якщо один із паралельних сендерів завершується через `set_error` або `set_stopped`, решта паралельних операцій негайно отримують запит на скасування через свій внутрішній токен скасування `std::stop_token`.

### `std::execution::split`
Перетворює одноразовий сендер (move-only rvalue sender) на багаторазовий (copyable lvalue sender). Стан операції зберігає результат у спільному буфері та роздає його всім підписникам.

```cpp
template <sender S>
/* sender */ split(S&& snd);
```

### `std::execution::into_variant`
Пакує множинні типи можливих успішних завершень сендера в єдиний екземпляр `std::variant`.

```cpp
template <sender S>
/* sender */ into_variant(S&& snd);
```

## 5. Споживачі та синхронізація (Consumers)

### `std::execution::sync_wait`
Синхронний блокуючий міст між асинхронним графом сендерів та звичайним синхронним кодом.

```cpp
template <sender S>
auto sync_wait(S&& snd) 
    -> std::optional<std::tuple<typename /* типи результатів */...>>;
```
- **Повернене значення**: повертає кортеж значень у `std::optional`.
- **Обробка скасування**: якщо операція завершилася викликом `set_stopped`, функція повертає `std::nullopt`.
- **Обробка винятків**: якщо операція завершилася викликом `set_error` з об'єктом `std::exception_ptr`, `sync_wait` відновлює та повторно викидає цей виняток через `std::rethrow_exception`.

### `std::execution::start_detached`
Запускає сендер у фоновому неблокуючому режимі (Fire-and-Forget).

```cpp
template <sender S>
void start_detached(S&& snd);
```
- **Пам'ять**: стан операції виділяється у динамічній пам'яті через стандартний алокатор та автоматично звільняється після отримання фінального сигналу в будь-який із трьох каналів.

## 6. Запити до середовища виконання (Environment Queries)

Приймачі надають доступ до середовища виконання для конфігурації поведінки сендерів:

| Запит середовища | Сигнатура виклику | Семантика та призначення |
| :--- | :--- | :--- |
| `get_env` | `get_env(rcvr)` | Отримує об'єкт середовища з приймача або сендера. |
| `get_scheduler` | `get_scheduler(env)` | Повертає планувальник за замовчуванням для поточного контексту. |
| `get_delegatee_scheduler` | `get_delegatee_scheduler(env)` | Повертає планувальник, якому можна делегувати фонову роботу. |
| `get_stop_token` | `get_stop_token(env)` | Повертає екземпляр `std::stop_token` для перевірки запитів на скасування. |
| `get_allocator` | `get_allocator(env)` | Повертає алокатор пам'яті для внутрішніх структур алгоритмів. |
| `get_forward_progress_guarantee` | `get_forward_progress_guarantee(sch)` | Повертає тип гарантії прогресу виконання планувальника. |

### Гарантії прогресу виконання (Forward Progress Guarantees)
Стандарт P2300 класифікує планувальники за трьома категоріями гарантій прогресу:
1. `std::execution::forward_progress_guarantee::concurrent`: потік виконання гарантовано робить прогрес незалежно від інших потоків (класичні потоки ОС).
2. `std::execution::forward_progress_guarantee::parallel`: потік робить прогрес, якщо періодично поступається ресурсами іншим потокам (пули задач із робочими чергами).
3. `std::execution::forward_progress_guarantee::weakly_parallel`: потік не гарантує прогресу без зовнішнього просування (потоки SIMD або варпи GPU).

## 7. Зведена таблиця перетворень адаптерів

У таблиці показано, як базові адаптери P2300 реагують на сигнали, що надходять у три канали завершення:

| Вхідний канал | Адаптер `then(f)` | Адаптер `upon_error(f)` | Адаптер `upon_stopped(f)` | Адаптер `let_value(f)` |
| :--- | :--- | :--- | :--- | :--- |
| **`set_value(v...)`** | Викликає `f(v...)` → надсилає результат у `set_value` | Пропускає сигнал без змін | Пропускає сигнал без змін | Викликає `f(v...)` → зв'язує та запускає новий сендер |
| **`set_error(e)`** | Пропускає сигнал без змін | Викликає `f(e)` → надсилає результат у `set_value` | Пропускає сигнал без змін | Пропускає сигнал без змін |
| **`set_stopped()`** | Пропускає сигнал без змін | Пропускає сигнал без змін | Викликає `f()` → надсилає результат у `set_value` | Пропускає сигнал без змін |
