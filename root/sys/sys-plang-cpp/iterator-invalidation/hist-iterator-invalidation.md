# 📜 Історія та еволюція правил інвалідації ітераторів у стандарту C++

Концепція ітератора виникла на початку 1990-х років у працях Олександра Степанова та Менга Лі під час створення бібліотеки HP STL (Hewlett-Packard Standard Template Library). Головною ідеєю була відокремленість алгоритмів від фізичної структури даних. Проте з перших днів застосування мови C++ постала серйозна проблема: коли алгоритм або користувацький код змінює структуру контейнера (додає, видаляє або переставляє елементи), існуючі вказівники та курсори можуть раптово стати недійсними, вказуючи на звільнену пам'ять або на інший елемент.

Еволюція мови C++ від стандарту C++98 до C++26 — це тривала історія формалізації гарантій стабільності ітераторів, усунення небезпечних прихованих оптимізацій та створення нових механізмів безбезпечної маніпуляції пам'яттю.

---

## 1. Ера C++98: Зародження гарантій та проблема Copy-On-Write у std::string

У першому офіційному стандарті ISO/IEC 14882:1998 регулювання інвалідації було сформульовано у вигляді базованих вимог до контейнерів. Контейнери поділили на два табори:
1. **Послідовні суцільні контейнери** (`std::vector`, `std::string`) — реалокація пам'яті руйнувала всі ітератори.
2. **Вузлові контейнери** (`std::list`, `std::set`, `std::map`) — гарантували, що вставка або видалення вузла не впливає на ітератори інших вузлів.

Проте стандарт C++98 містив приховану та дуже небезпечну невизначеність щодо типу `std::string`. На той час поширеною оптимізацією розробників компіляторів (зокрема у бібліотеках `libstdc++` від GCC та `libc++`) було використання механізму **Copy-On-Write (COW)**.

### Як працював Copy-On-Write та чому він ламав гарантії ітераторів

При копіюванні об'єкта `std::string s2 = s1;` виділення нового буфера у купі не відбувалося. Обидва об'єкти вказували на один і той самий динамічний буфер у пам'яті, де також зберігався лічильник посилань (англ. *reference count*).

Фізичний розділення буферів відкладалося до моменту, коли один із рядків намагався виконати модифікацію (наприклад, через оператор `s2[0] = 'X'`).

```cpp
// Поведінка у C++98 (з реалізацією Copy-On-Write)
std::string s1 = "Hello World";
std::string s2 = s1; // Обидва рядки ділять один буфер у купі!

const char* p1 = s1.data(); // Вказівник на символ 'H'

s2[0] = 'X'; // COW розділяє буфер: s2 виділяє новий буфер!
             // Буфер s1 залишається незмінним, але...
             // виклик non-const operator[] на s2 міг викликати unshare()!

// АЛЕ якщо викликати s1[0] = 'Y', буфер s1 реалокується, 
// і вказівник p1 несподівано стає недійсним (Undefined Behavior)!
```

Головна трагедія COW полягала у підриві константних гарантій та багатопотоковості:
- Виклик неконстантного оператора індексування `operator[]` або методу `begin()` змушений був перевіряти лічильник посилань і виконувати реалокацію розділення буфера (`unshare()`).
- У багатопотоковому середовищі два потоки, що читали `s1` та `s2`, могли зіткнутися з гонитвою даних (англ. *data race*) всередині лічильника посилань, що інвалідувало вказівники та ітератори під час звичайного читання.

## 2. Революція C++11: Заборона COW, семантика переміщення та суцільність пам'яті

Комітет зі стандартизації C++ під керівництвом Герба Саттера та Говарда Гіннанта визнав COW антипатерном для сучасних базісних рядків.

У стандарті **C++11** відбулося дві фундаментальні зміни:
1. **Заборона Copy-On-Write (Clause 21)**: Стандарт зобов'язав `std::basic_string` зберігати елементи у суцільному неперервному блоці пам'яті та заборонив спільне володіння буфером між різними екземплярами рядків.
2. **Гарантія SSO (Small String Optimization)**: Рядки малого розміру (зазвичай до 15 або 22 символів) зберігаються безпосередньо всередині самого об'єкта `std::string` на стеку, уникнувши викликів `malloc`.

### Поведінка ітераторів при переміщенні (Move Semantics)

C++11 ввів rvalue-посилання `&&` та семантику переміщення. Це створило нові суворі правила інвалідації при операціях `std::move`:

```cpp
std::vector<int> v1 = {1, 2, 3, 4, 5};
auto it = v1.begin() + 2; // Вказує на значення 3 (адреса в купі)

std::vector<int> v2 = std::move(v1); 
// v2 просто забирає вказівник на буфер v1 у купі за O(1).

// Згідно зі стандартом C++11:
// Ітератор `it` залишається ДІЙСНИМ, але тепер він вказує на елемент всередині v2!
// v1 переходить у "valid but unspecified state" (зазвичай порожній).
```

Гарантія C++11: Переміщувальне конструювання `Container v2(std::move(v1))` **не інвалідує** ітератори та посилання на елементи. Вони продовжують вказувати на ті самі об'єкти у купі, змінюється лише об'єкт-власник контейнера.

Однако при переміщувальному присвоєнні `v2 = std::move(v1)` ітератори `v2` інвалідуються (оскільки старий буфер `v2` знищується), а ітератори `v1` зберігають дійсність і переходять до `v2`, якщо алокатори контейнерів є рівними (`alloc1 == alloc2`).

## 3. C++17: Вузлові хендли (Node Handles) та безбезпечне переміщення

До C++17 переміщення елемента з одного асоціативного контейнера в інший (наприклад, з `std::map<int, string>` у інший `std::map<int, string>`) вимагало виділення пам'яті під новий вузол дерева та видалення старого вузла:

```cpp
// До C++17: Неефективно і з інвалідацією
std::map<int, std::string> src = {{1, "one"}, {2, "two"}};
std::map<int, std::string> dst;

// Вставка копіювала/переміщувала дані, створюючи новий вузол у купі
dst.insert(*src.find(1));
src.erase(1); // Інвалідувало ітератор на вузол 1
```

Стандарт **C++17** вирішив цю проблему, додавши метод `.extract()` та об'єкти **Node Handle** (`container::node_type`).

### Механізм вилучення вузла без інвалідації посилань

Метод `src.extract(key)` або `src.extract(iterator)` фізично від'єднує вузол червоно-чорного дерева від контейнера-джерела без виклику деструктора елемента та без вивільнення пам'яті `free()`.

```cpp
// У C++17: Використання node handle
std::map<int, std::string> src = {{1, "one"}, {2, "two"}};
std::map<int, std::string> dst;

auto node = src.extract(1); // Вузол вилучено! Ітератори src інвалідовано.
// АЛЕ: Покажчики &node.mapped() та посилання на дані всередині вузла 
// залишаються повністю ДІЙСНИМИ!

node.key() = 10; // C++17 дозволяє змінювати ключ вилученого вузла!
dst.insert(std::move(node)); // Вузол вбудовано у нове дерево без alloc/free!
```

Це стало величезним проривом: розробники отримали можливість переносити елементи між хеш-таблицями та деревами з високою продуктивністю `O(1)` або `O(log N)` із гарантованою збереженістю адрес об'єктів у RAM.

## 4. C++20 / C++23: Неволодіючі представлення (std::span) та flat-контейнери

У сучасних стандартах C++20 та C++23 з'явилися нові абстракції, що змінили підходи до обходу пам'яті:

### `std::span` та `std::string_view` (C++20)
Це легкі неволодіючі обгортки над суцільними масивами (парою `ptr + size`).
- Вони самі не володіють пам'яттю, тому не мають операцій реалокації.
- Проте їхні ітератори та самі об'єкти view **миттєво інвалідуються**, якщо контейнер-власник (`std::vector` або `std::string`), на який вони посилаються, виконує реалокацію або змінює розмір.

### Flat-контейнери C++23 (`std::flat_map`, `std::flat_set`)
Стандарт C++23 ввів адаптери `std::flat_map`, які зберігають ключі та значення у двох паралельних суцільних векторах `std::vector<Key>` та `std::vector<Value>` замість узлового дерева.

Це дає виняткову кеш-локальність при пошуку `O(log N)`, але змінює гарантії інвалідації з рівня `std::map` (абсолютна стабільність) на рівень `std::vector` (будь-яка вставка чи видалення зсуває масив й інвалідує всі ітератори після точки вставки).

## 5. Підсумкова хронологія гарантій

| Стандарт | Ключове нововведення | Вплив на стабільність ітераторів та посилань |
| :--- | :--- | :--- |
| **C++98** | Перша стандартизація STL | Запроваджено базову матрицю інвалідації; невизначеність через COW `std::string`. |
| **C++11** | Заборона COW, Move Semantics | `std::string` отримав суцільну пам'ять; `std::move` контейнера зберігає дійсність ітераторів. |
| **C++17** | Node Handles (`extract`/`merge`) | Можливість вилучення та переносу вузлів `set`/`map` без реалокації та втрати посилань. |
| **C++20** | Ranges, Sentinels, `std::span` | Формалізація `ContiguousIterator`; легкі перегляди успадковують ризики інвалідації джерела. |
| **C++23** | `std::flat_map`, `std::flat_set` | Компроміс між кеш-локальністю та інвалідацією: адаптери на базі векторів. |

Еволюція гарантій інвалідації C++ показує виразний вектор: мова поступово відмовляється від прихованих неявних реалокацій на користь точного контролю за ресурсами та прозорих математичних гарантій.
