# 📋 Матриця правил інвалідації та контракти гарантій контейнерів C++

Цей довідник містить повний нормативний специфікатор гарантій стабільності ітераторів, покажчиків та посилань для всіх контейнерів стандартної бібліотеки C++ (від стандарту C++98 до C++26), а також правила поведінки при спеціальних операціях, вимоги алокаторів пам'яті та прапорці компіляторів для виявлення порушень.

---

## 1. Повна нормативна матриця інвалідації для послідовних контейнерів

Послідовні контейнери визначають порядок зберігання елементів у пам'яті відповідно до послідовності їхнього додавання. Правила інвалідації для них прямо залежать від фізичного розміщення об'єктів у оперативній пам'яті (суцільне, посторінкове або вузлове).

### Суцільні послідовні контейнери (std::vector, std::string)
У суцільних контейнерах елементи розміщуються у єдиному неперервному блоці пам'яті. Згідно зі специфікацією стандарту ISO/IEC 14882 [vector.modifiers], будь-яка операція вставки, яка призводить до перевищення поточної місткості `capacity()`, викликає повне перерозподілення буфера у купі. Усі існуючі ітератори, посилання та сирі покажчики на будь-які елементи даного контейнера стають недійсними. 

Якщо реалокація не відбувається (`size() < capacity()`), вставка у кінець інвалідує лише ітератор `end()`, тоді як вставка або видалення у середину інвалідує всі ітератори та посилання починаючи з позиції модифікації і до кінця масиву через фізичний зсув елементів.

Позначення у таблиці:
- **Дійсні** — ітератори та посилання зберігають повну коректність та вказують на ті самі об'єкти.
- **Інвалідовані** — будь-яке звернення призводить до невизначеної поведінки (Undefined Behavior).
- **Зсув** — ітератори до позиції модифікації дійсні; у позиції модифікації та після неї — інвалідовані через фізичний зсув об'єктів.

| Контейнер | Операція модифікації | Стан ітераторів | Стан посилань (`T&`) та покажчиків (`T*`) |
| :--- | :--- | :--- | :--- |
| **`std::vector`** | `push_back` / `emplace_back` (без реалокації, `size < capacity`) | Ітератор `end()` інвалідується; інші дійсні | **Усі посилання та покажчики ДІЙСНИМИ** |
| | `push_back` / `emplace_back` (з реалокацією, `size == capacity`) | **Усі ітератори інвалідуються** | **Усі посилання та покажчики інвалідуються** |
| | `insert` / `emplace` у середину | Зсув: інвалідуються від `pos` до кінця | Зсув: інвалідуються від `pos` до кінця |
| | `erase(pos)` з середини | Зсув: інвалідуються від `pos` до кінця | Зсув: інвалідуються від `pos` до кінця |
| | `pop_back()` | `end()` та видалений елемент інвалідуються | Лише посилання на видалений елемент інвалідується |
| | `clear()` | **Усі ітератори інвалідуються** | **Усі посилання та покажчики інвалідуються** |
| | `resize(n)` (з реалокацією) | **Усі ітератори інвалідуються** | **Усі посилання та покажчики інвалідуються** |
| | `reserve(n)` (якщо `n > capacity`) | **Усі ітератори інвалідуються** | **Усі посилання та покажчики інвалідуються** |
| **`std::string`** | Будь-яка вставка з реалокацією | **Усі ітератори інвалідуються** | **Усі посилання інвалідуються** (включаючи `c_str()`) |
| | Зміна рядка в межах SSO (Small String Optimization) | Перехід із SSO у купу інвалідує все | Перехід із SSO у купу інвалідує все |
| **`std::deque`** | `push_front` / `push_back` / `emplace` по краях | **Усі ітератори інвалідуються** | **Усі посилання `T&` та покажчики `T*` ДІЙСНИМИ!** |
| | `insert` / `emplace` / `erase` у середині | **Усі ітератори інвалідуються** | **Усі посилання та покажчики інвалідуються** |
| | `pop_front()` / `pop_back()` по краях | Лише ітератор на видалений елемент | Лише посилання на видалений елемент |
| **`std::list`** | `push_front` / `push_back` / `insert` / `emplace` | **Жоден ітератор не інвалідується** | **Жодне посилання не інвалідується** |
| | `erase(pos)` / `pop_front()` / `pop_back()` | Лише видалений ітератор `pos` | Лише посилання на видалений елемент |
| | `splice()` (перенесення вузлів) | **Жоден ітератор не інвалідується** | **Жодне посилання не інвалідується** |
| **`std::forward_list`**| `insert_after` / `emplace_after` | **Жоден ітератор не інвалідується** | **Жодне посилання не інвалідується** |
| | `erase_after` | Лише ітератор на видалений елемент | Лише посилання на видалений елемент |

## 2. Нормативна матриця для асоціативних та геш-контейнерів

Асоціативні контейнери впорядковують дані за ключами або геш-кодами. Головною рисою вузлових асоціативних контейнерів є повна ізоляція пам'яті окремих вузлів, що регламентується специфікаціями [associative.reqmts] та [unord.req].

### Деревоподібні асоціативні контейнери
Контейнери на основі червоно-чорних дерев (`std::map`, `std::set`, `std::multimap`, `std::multiset`) гарантують стабільність адрес вузлів протягом усього часу існування об’єкта. Оскільки повороти дерев при балансуванні змінюють лише внутрішні вказівники зв’язків між вузлами, адреса самого вузла у купі залишається незмінною. Вставка нових елементів ніколи не інвалідує існуючі ітератори або посилання.

### Геш-таблиці з відокремленими ланцюжками
У геш-контейнерах (`std::unordered_map`, `std::unordered_set`) гарантії розділяються між ітераторами та посиланнями. Посилання та сирі покажчики на об’єкти залишаються дійсними навіть при операції повторного гешування `rehash()`, оскільки дані зберігаються у нерухомих вузлах. Проте сам масив кошиків реалокується, що повністю інвалідує ітератори послідовного обходу.

| Контейнер | Операція модифікації | Стан ітераторів | Стан посилань (`T&`) та покажчиків (`T*`) |
| :--- | :--- | :--- | :--- |
| **`std::map` / `set`** | `insert` / `emplace` / `operator[]` | **Жоден ітератор не інвалідується** | **Жодне посилання не інвалідується** |
| | `erase(pos)` | Лише видалений ітератор `pos` | Лише посилання на видалений елемент |
| | `extract(pos)` (C++17 node handle) | Ітератор `pos` інвалідується | **Покажчики `&node.mapped()` залишаються ДІЙСНИМИ** |
| | `merge(src)` (C++17) | Перенесені ітератори інвалідуються | **Усі посилання на дані залишаються ДІЙСНИМИ** |
| **`std::unordered_*`**| `insert` (без `rehash`, `load_factor <= max`) | Можуть змінювати порядок ітерації | **Усі посилання `T&` та покажчики `T*` ДІЙСНИМИ** |
| | `insert` (з `rehash`, `load_factor > max`) | **Усі ітератори інвалідуються** | **Усі посилання `T&` та покажчики `T*` ДІЙСНИМИ** |
| | `erase(pos)` | Лише видалений ітератор `pos` | Лише посилання на видалений елемент |
| | `rehash(n)` / `reserve(n)` | **Усі ітератори інвалідуються** | **Усі посилання `T&` та покажчики `T*` ДІЙСНИМИ** |
| **`std::flat_map`** | Будь-яка вставка чи видалення (C++23) | Повністю аналогічно `std::vector` | Повністю аналогічно `std::vector` |
| **`std::span`** | Зміна контейнера-власника | Інвалідуються разом із джерелом | Інвалідуються разом із джерелом |

## 3. Вплив алокаторів пам'яті та операцій swap / move

Поведінка ітераторів при взаємодії контейнерів регулюється нормами метафункцій `std::allocator_traits` стандарту ISO/IEC 14882.

### 1. Операція `c1.swap(c2)`
- **Стандартна гарантія**: Для всіх контейнерів STL операція `swap` виконує обмін внутрішніми вказівниками буферів за час `O(1)`.
- **Стабільність адрес**: Жоден ітератор, покажчик або посилання на елементи не інвалідується.
- **Зміна приналежності**: Ітератор `it1`, який до виклику `swap` посилався на елемент всередині `c1`, після обміну продовжує посилатися на той самий елемент у пам'яті, який тепер перебуває всередині `c2`.
- **Вимога рівності алокаторів**: Якщо прапорець `std::allocator_traits<Alloc>::propagate_on_container_swap::value` дорівнює `false`, а алокатори контейнерів не є рівними (`c1.get_allocator() != c2.get_allocator()`), стандарт оголошує виклик `swap` **невизначеною поведінкою (Undefined Behavior)**.

### 2. Переміщуюче конструювання `Container c2(std::move(c1))`
- При створенні нового контейнера через переміщення `c2` просто забирає вказівник на динамічний буфер джерела `c1`.
- Ітератори, що вказували на елементи `c1`, залишаються **повністю дійсними** та починають посилатися на елементи у складі `c2`.

### 3. Переміщуюче присвоєння `c2 = std::move(c1)`
- **Якщо алокатори рівні (`c1.get_allocator() == c2.get_allocator()`)**:
  - Усі ітератори та посилання на елементи `c2` інвалідуються (оскільки старий вміст `c2` знищується).
  - Усі ітератори та посилання на елементи `c1` **залишаються дійсними** і переходять у володіння `c2`.
- **Якщо алокатори не рівні**:
  - Метафункція `allocator_traits` не дозволяє просто забрати буфер джерела. Контейнер вимушений виконувати покомпонентне переміщення кожного елемента за лінійний час `O(N)`. **Усі ітератори обох контейнерів повністю інвалідуються**.

## 4. Гарантії виняткобезпеки (Exception Safety Guarantees)

Стандарт STL накладає суворі обмеження щодо збереження стабільності ітераторів у разі виникнення винятків під час виконання операцій:

1. **Сувора гарантія (Strong Exception Guarantee)**:
   Якщо під час вставки виникає виняток (наприклад, конструктор типу `T` кидає помилку при копіюванні чи переміщенні), стан контейнера повністю відкочується до початкового стану перед викликом методу.
   - `push_back()` у `std::vector` надає сувору гарантію, якщо `T` має `noexcept` конструктор переміщення (`std::is_nothrow_move_constructible<T>::value == true`). У цьому випадку існуючі ітератори зберігають дійсність, якщо реалокації не відбулося. Якщо ж конструктор переміщення може кинути виняток, а конструктор копіювання недоступний, сувора гарантія втрачається.
   - Усі вставки у `std::list`, `std::map`, `std::set` завжди надають сувору гарантію: якщо виділення вузла завершується винятком, створений вузол вивільняється, а наявні ітератори залишаються недоторканими.

2. **Базова гарантія (Basic Exception Guarantee)**:
   Якщо виникає виняток, контейнер залишається у валідному стані (відсутні витоки пам'яті, збережено інваріанти структури), але частина ітераторів може бути інвалідована (наприклад, при масовій вставці діапазону `insert(beg, end)` у вектор).

3. **Гарантія відсутності винятків (Nothrow Guarantee)**:
   Операції `pop_back()`, `pop_front()`, `clear()`, `swap()` та деструктор гарантовано не кидають винятків і надають гарантію **nothrow**.

## 5. Прапорці компіляторів для перевірки інвалідації

Сучасні середовища розробки надають спеціальні макроси для увімкнення перевірок поколінь ітераторів під час виконання (Runtime Iterator Debugging):

### GNU GCC (`libstdc++`)
```bash
g++ -D_GLIBCXX_DEBUG main.cpp -o main
```
- **Функціонал**: Обгортає ітератори вектора та списків у перевірочні структури. При реалокації або видаленні елементів будь-яке звернення до інвалідованого ітератора викликає виклик `__builtin_trap()` із друком опису помилки у `stderr`.

### LLVM Clang (`libc++`)
```bash
clang++ -D_LIBCPP_ENABLE_ASSERTIONS=1 -fsanitize=address main.cpp -o main
```
- **AddressSanitizer (ASan)**: Прапорець `-fsanitize=address` додає аналіз отруєної пам'яті (Memory Poisoning), миттєво виявляючи використання висячих покажчиків після реалокацій.

### Microsoft Visual C++ (MSVC)
```cpp
#define _ITERATOR_DEBUG_LEVEL 2
```
- **Значення**:
  - `0` — перевірки вимкнено (режим Release, висока продуктивність).
  - `1` — перевірки меж індексування та початкових діапазонів.
  - `2` — повний контроль інвалідації ітераторів та перевірка приналежності ітераторів до контейнерів (режим Debug за замовчуванням).
