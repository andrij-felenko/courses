# 📜 Від сторожових значень до std::optional: еволюція опціональних типів у C++

Спроба виразити відсутність результату в мовах C та ранньому C++ тривалий час спиралася на домовленості про сторожові значення (англ. *sentinel values*), які регулярно призводили до витоків пам'яті, логічних помилок та руйнування системної типізації. Програмісти змушені були резервувати особливі константи для сигналізації про помилку — такі як `-1` для системних викликів POSIX, `EOF` для стандартного введення-виведення, `nullptr` для вказівників чи `std::string::npos` для алгоритмів пошуку підрядка. Ця вставка розкриває історичний шлях від небезпечних C-паттернів через розробку бібліотеки Boost до включення `std::optional` у стандарт C++17 та його розширення монадичними операціями у C++23.

## Ера сторожових значень та її системні вади

У мові C відсутність результату традиційно позначалася двома шляхами: через повернення спеціального «недійсного» значення основного типу або через передачу вихідного параметра за допомогою вказівника. 

Перший підхід вимагав резервування однієї зі комбінацій бітів типу під прапорець помилки. Наприклад, функція `getchar()` повертає `int`, а не `char`, саме для того, щоб мати можливість віддати значення `-1` (значення константи `EOF`), яке не перетинається з діапазоном дійсно зчитаних байтів `0..255`. Проте для багатьох математичних та системних функцій таке резервування виявлялося неможливим. Якщо функція обчислює температуру процесора або шукає корені рівняння, будь-яке число з діапазону `int` чи `double` може бути цілком коректним результатом. Повернення `-1` або `0` у разі збою змушувало розробників запроваджувати глобальну змінну `errno`, що створювало проблеми у багатопотокових програмах та ускладнювало локальність коду.

Другий підхід полягав у поверненні статусного коду помилки, тоді як самий результат записувався за вказаною адресою через вихідний параметр:

:::tabs
```c
// C: повернення статусного коду та запис у вихідний параметр через вказівник
int read_sensor_data(sensor_t* dev, double* out_value) {
    if (!dev || !dev->is_ready) {
        return -1; // Код помилки
    }
    *out_value = dev->hardware_register;
    return 0; // Успіх
}
```
```cpp
// C++: повернення значення або std::nullopt без вихідних вказівників
std::optional<double> read_sensor_data(const Sensor& dev) noexcept {
    if (!dev.is_ready()) {
        return std::nullopt; // Пристрій не готовий або збій
    }
    return dev.read_hardware_register();
}
```
:::

Такий підхід позбавляв від проблеми резервування констант, але руйнував виразність коду: функції більше не могли використовуватися у виразах безпосередньо, а програміст змушений був створювати непотрібні змінні до виклику функції. Крім того, компілятор C не міг перевірити, чи перевірив викликач статус повернення до розгортання значення `out_value`.

З появою мови C++ розробники спробували вирішити цю проблему через повернення вказівників (`T*`) або розумних вказівників (`std::unique_ptr<T>`), де відсутність значення виражалася через `nullptr`. Проте цей підхід створив нову проблему — ціну динамічної пам'яті. Повернення об'єкта через `unique_ptr` змушувало викликати `operator new`, що вимагало сотень тактів процесора на алокацію у купі, створювало фрагментацію пам'яті та руйнувало локальність даних у кеші процесора через розіменування вказівника.

Інша альтернатива — використання `std::pair<bool, T>` — дозволяла уникнути динамічної пам'яті, зберігаючи прапорець успіху поруч із значенням. Але вона мала критичний недолік: конструктор `T` викликався **завжди**, навіть якщо прапорець `bool` дорівнював `false`. Якщо тип `T` не мав деструктора за замовчуванням або його створення вимагало виділення системних ресурсів (наприклад, відкриття файлового дескриптора чи виклику мережевого сокета), використання `std::pair` ставало неприпустимим.

## Революція Boost.Optional (2002–2003)

Усвідомлення необхідності створення типу, який би поєднував точну семантику наявності значення з нульовими витратами на динамічну пам'ять та лінивим конструюванням, привело аргентинського розробника Фернандо Каччіолу (Fernando Cacciola) до створення бібліотеки `Boost.Optional`.

У 2002 році Каччіола представив спільноті Boost концептуальний шаблон `boost::optional<T>`. Головна ідея полягала у створенні неіменованого союзу (union) або вирівняного буфера байтів `boost::aligned_storage`, розмір якого точно відповідав `sizeof(T)`, а вирівнювання — `alignas(T)`. 

Поруч із буфером розміщувався один байт прапорця `bool m_initialized`. При створенні порожнього `boost::optional<T>` конструктор `T` взагалі не викликався. Пам'ять залишалася неініціалізованою, а прапорець встановлювався у `false`. Коли програма присвоювала значення, виконувався розміщувальний виклик `placement new`:

```cpp
::new (static_cast<void*>(address)) T(args...);
```

Це дозволило вперше в історії C++ безпечно зберігати значення типу `T` безпосередньо у стековому фреймі, гарантуючи при цьому, що ресурси типу `T` створюються та знищуються лише тоді, коли об'єкт дійсно присутній.

Бібліотека `Boost.Optional` швидко стала стандартом де-факто для обробки необов'язкових даних у промисловому C++. Вона успішно застосовувалася у складних математичних обчисленнях, розборі конфігурацій та графічних рушіях.

## Шлях до стандартизації: від N3527 до C++17

З початком роботи над стандартом C++14 комітет зі стандартизації ISO C++ розпочав процес перенесення найважливіших компонентів Boost до стандартної бібліотеки. Пропозицію щодо включення `optional` очолили Беман Доус (Beman Dawes), Фернандо Каччіола та польський дослідник Анджей Кшеменьскі (Andrzej Krzemieński).

У серії робочих документів N3527 (2013), N3672 та N3793 автори сформулювали вимоги до стандартного `std::optional`:

1. **Строга семантика значень (Value Semantics)**: `std::optional<T>` має поводитися як звичайне значення, підтримуючи копіювання, переміщення та порівняння, якщо тип `T` підтримує ці операції.
2. **Тип-маркер порожнечі**: замість використання `nullptr` (який асоціюється з вказівниками) було введено спеціальний теговий тип `std::nullopt_t` та константу `std::nullopt`.
3. **Конструювання на місці**: введення тегу `std::in_place` дозволило передавати аргументи безпосередньо конструктору `T` усередині буфера без створення тимчасових об'єктів.

Проте процес стандартизації зіштовхнувся з тривалими дискусіями довкола двох концептуальних питань:

### Дискусія довкола посилань: std::optional<T&>

Найбільші суперечки викликала проблема підтримки посилальних типів у шаблоні `std::optional`. У мові C++ посилання `T&` після ініціалізації не може бути перезв'язане (rebound) на інший об'єкт. Якщо уявити код:

```cpp
int a = 10;
int b = 20;
std::optional<int&> opt_a = a;
std::optional<int&> opt_b = b;

opt_a = opt_b; // Що має відбутися?
```

Виникали дві принципово несумісні інтерпретації:
- **Перезв'язування (Rebinding)**: `opt_a` тепер посилається на змінну `b`.
- **Присвоєння значення (Value assignment)**: значення змінної `b` (тобто `20`) копіюється у змінну `a`, на яку посилається `opt_a`.

Оскільки спільнота комітету не дійшла згоди щодо єдиної семантики присвоєння для посилань, у C++17 вирішили повністю заборонити спеціалізацію `std::optional<T&>` за допомогою `static_assert`. Для роботи з посиланнями програмістам запропонували використовувати `std::optional<std::reference_wrapper<T>>` або звичайні вказівники. (Лише у C++26 після додаткових досліджень повернулися до обговорення підтримки посилань із семантикою перезв'язування).

### Дискусія довкола Undefined Behavior при розгортанні

Другим питанням була поведінка `operator*()` при зверненні до порожнього `optional`. Частина членів комітету наполягала на тому, щоб `operator*()` завжди кидав виняток. Проте прибічники високої продуктивності переконали комітет, що перевірка прапорця при кожному розгортанні знищить конкурентну перевагу C++ у системних та високочастотних алгоритмах. 

У результаті було прийнято компромісне рішення:
- `operator*()` та `operator->()` не виконують жодних перевірок і гарантують `noexcept`. Звернення до порожнього об'єкта є неокресленою поведінкою (Undefined Behavior).
- Метод `.value()` виконує явну перевірку і кидає виняток `std::bad_optional_access` у разі порожнього стану.

У 2014 році тип був опублікований у технічній специфікації Library Fundamentals TS, а у 2017 році офіційно увійшов до стандарту C++17 у заголовочному файлі `<optional>`.

## Розширення у C++23: Монадичні операції (P0798R8)

Після виходу C++17 з'ясувалося, що хоча `std::optional` чудово вирішив проблему збереження пам'яті, код для його обробки часто перетворювався на громіздкі деревоподібні структури з вкладених перевірок `if (opt.has_value())`:

```cpp
std::optional<User> user = find_user(id);
if (user) {
    std::optional<Config> config = load_config(*user);
    if (config) {
        std::optional<Server> server = connect_server(*config);
        if (server) {
            server->process();
        }
    }
}
```

У мовах функціонального програмування (Haskell, Scala) та сучасних системних мовах (Rust з його типом `Option`) подібні ланцюжки оброблялися через монадні оператори `map`, `flatMap` та `orElse`.

У 2021 році Вісент Ботет Ескріба (Vicente J. Botet Escribá) подав документ P0798R8 «Monadic operations for std::optional», який був прийнятий до стандарту C++23. Робота додала до `std::optional` три нові методи:

- `.and_then()`: связує функції, які самі повертають `std::optional` (аналог `flatMap`).
- `.transform()`: застосовує функцію до значення усередині `optional` та обгортає результат назад у `std::optional` (аналог `map`).
- `.or_else()`: виконує альтернативну дію, якщо `optional` виявився порожнім.

Завдяки цьому ланцюжок розбору в C++23 скоротився до єдиного виразного виразу без жодної вкладеної гілки `if`:

```cpp
find_user(id)
    .and_then(load_config)
    .and_then(connect_server)
    .transform([](auto server) { return server.process(); })
    .or_else([]() { log_error("Не вдалося запустити конвеєр"); return std::nullopt; });
```

Еволюція `std::optional` від небезпечних C-строк та сторожових значень до монадного конвеєра C++23 стала яскравим прикладом того, як мова C++ поетапно поєднує низькорівневий контроль над пам'яттю з високорівневими абстракціями функціонального програмування.
