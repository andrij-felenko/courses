# 📋 Довідник інтерфейсу std::expected та монадичних операторів

Цей довідник описує повний специфікований контракт шаблонів `std::expected<T, E>`, `std::expected<void, E>` та `std::unexpected<E>` у стандарті C++23, включаючи сигнатури методів, категорії посилань (`const`, `rvalue`), вимоги до типів, гарантії винятків та таблиці бінарного розміщення у пам'яті.

## 1. Шаблони класів та обгортки помилок

Заголовочний файл `<expected>` оголошує три основні сутності для організації детермінованого оброблення помилок без використання механізму винятків:

```cpp
namespace std {
    // 1. Основний шаблон для результату зі значенням T або помилкою E
    template <typename T, typename E>
    class expected;

    // 2. Спеціалізація для процедур без повернення значення (void)
    template <typename E>
    class expected<void, E>;

    // 3. Явна обгортка для маркування значення помилки
    template <typename E>
    class unexpected;

    // 4. Тип винятку при небезпечному доступі через .value()
    template <typename E>
    class bad_expected_access;
}
```

### Вимоги до типів T та E
Типи `T` та `E`, які передаються як параметри шаблону `std::expected<T, E>`, підпорядковуються чітко визначеним фундаментальним обмеженням стандарту C++23:
- Тип корисного навантаження `T` має бути варіантним типом, що задовольняє концепт `std::is_destructible_v<T>`. Тип `T` не може бути масивом, абстрактним класом, посиланням, спец-типом `std::unexpect_t` або екземпляром шаблону `std::unexpected`. Якщо розробникові потрібно повернути посилання на існуючий об'єкт, слід використовувати шаблон `std::reference_wrapper<T>` або звичайний сирий вказівник `T*`.
- Тип помилки `E` має бути об'єктним типом (`std::is_object_v<E>`), що не є масивом, абстрактним типом, посиланням або спец-типами `std::in_place_t` чи `std::unexpect_t`. Окрім цього, тип `E` обов'язково має бути здатним до конструювання при копіюванні чи переміщенні (`std::is_copy_constructible_v<E>` або `std::is_move_constructible_v<E>`).

При порушенні будь-якої з цих вимог компілятор видає помилку на етапі ініціалізації шаблону через інструкції `static_assert`, запобігаючи створенню некоректних типів даних у програмі. Окрім того, обидва типи підтримують правильну відпрацьованість метапрограмування через концепційні trait-адаптери стандартної бібліотеки.

## 2. Конструктори та маркування стану

Об'єкт `std::expected<T, E>` зберігає або значення `T`, або значення помилки `E` в єдиному внутрішньому буфері пам'яті (за аналогією з `std::variant`), дискримінованому внутрішнім прапорцем `bool`.

### Створення успішного значення
Конструювання об'єкта в успішному стані здійснюється декількома способами залежно від вимог до продуктивності та наявності конструкторів типів:
1. **Неявне або явне конструювання з `T`**:
   Якщо тип `T` підтримує неявне конструювання з переданого аргументу, об'єкт `expected` створюється природним присвоєнням або передачею значення у функцію:
   ```cpp
   std::expected<std::string, int> res = "Успішне виконання"; // Конструює T в буфері
   ```
2. **In-place конструювання (`std::in_place`)**:
   Для уникнення створення тимчасових об'єктів та додаткових викликів конструкторів переміщення використовується маркерний тег `std::in_place`. Це дозволяє передавати аргументи безпосередньо в конструктор `T` за місцем у внутрішньому буфері об'єкта:
   ```cpp
   std::expected<std::vector<int>, std::string> res(std::in_place, {10, 20, 30, 40});
   ```

Цей спосіб ідеально підходить для важких об'єктів, таких як контейнери або мережеві буфери, усуваючи будь-які оверхеди на копіювання чи переміщення. Окрім цього, використання `std::in_place_type_t<U>` дозволяє конструювати альтернативні типи `U`, що перетворюються на `T`. Конструктор за замовчуванням створює об'єкт зі значенням `T()`, якщо `T` підтримує default constructor.

### Створення помилки через std::unexpected та std::unexpect
Оскільки типи `T` та `E` можуть збігатися (наприклад, `std::expected<std::string, std::string>` або `std::expected<int, int>`), пряме передавання аргументу не дозволяє компілятору однозначно визначити, чи створюється успішне значення, чи помилка. Для вирішення цієї амбівалентності стандарт вводить обгортку `std::unexpected`:

```cpp
// 1. Створення помилки через обгортку std::unexpected
std::expected<int, int> err1 = std::unexpected(404);

// 2. In-place конструювання помилки за допомогою тегу std::unexpect
std::expected<std::string, ComplexError> err2(std::unexpect, "Помилка таймауту", 500);
```

Спроба передати помилку без `std::unexpected` у випадку збігу типів спричинить помилку компіляції на етапі розв'язання перевантаження конструкторів, захищаючи програму від семантичних помилок. Шаблон `std::unexpected<E>` виступає прозорою обгорткою, яка має атрибути `explicit` конструктора і підтримує семантику переміщення.

## 3. Методи інспекції та доступу до даних

### Перевірка стану (Observers)
Для швидкої перевірки того, який саме стан є активним у даний момент, клас надає нотифіковані методи зі збереженням гарантії `noexcept`:
- `constexpr bool has_value() const noexcept;` — повертає `true`, якщо об'єкт містить успішне значення `T`; повертає `false`, якщо об'єкт містить помилку `E`.
- `constexpr explicit operator bool() const noexcept;` — тотожний виклику `has_value()`, що дозволяє використовувати об'єкт безпосередньо в умовних інструкціях `if (res)`.

Ці методи виконуються за один такт процесора, перевіряючи значення прапорця `bool` у пам'яті.

### Незахищений доступ (Unchecked Access — O(1) noexcept)
Незахищений доступ забезпечує найвищу швидкість виконання без жодних перевірок у runtime. Метод надає повну групу перевантажень для всіх категорій посилань та const-кваліфікаторів:
- `constexpr T& operator*() & noexcept;`
- `constexpr const T& operator*() const & noexcept;`
- `constexpr T&& operator*() && noexcept;`
- `constexpr const T&& operator*() const && noexcept;`
- `constexpr T* operator->() noexcept;`
- `constexpr const T* operator->() const noexcept;`

*Критичне застереження*: виклик `operator*` або `operator->` на об'єкті, у якому `has_value() == false`, призводить до **невизначеної поведінки (Undefined Behavior)**. Компілятор не генерує жодних перевірок у release-збірках, очікуючи, що розробник перевірив стан через `has_value()`.

### Захищений доступ (Checked Access)
Захищений доступ гарантує безпеку цілісності даних ціною потенційного генератора винятку:
- `constexpr T& value() &;`
- `constexpr const T& value() const &;`
- `constexpr T&& value() &&;`
- `constexpr const T&& value() const &&;`

Якщо `has_value() == true`, метод повертає посилання відповідної категорії на значення `T`.
Якщо `has_value() == false`, метод перериває нормальне виконання та кидає виняток `std::bad_expected_access<E>(error())`.

### Доступ до помилки
Для отримання об'єкта помилки використовуються методи `.error()`:
- `constexpr E& error() & noexcept;`
- `constexpr const E& error() const & noexcept;`
- `constexpr E&& error() && noexcept;`
- `constexpr const E&& error() const && noexcept;`

*Застереження*: виклик `.error()` при `has_value() == true` є невизначеною поведінкою. Перевірка `!has_value()` є обов'язковою перед викликом цього методу.

### Значення за замовчуванням
Для безпечного вилучення значення з можливістю підстановки резервного варіанту використовується метод `value_or`:
- `template <typename U> constexpr T value_or(U&& default_value) const &;`
- `template <typename U> constexpr T value_or(U&& default_value) &&;`

Метод повертає копію або переміщене значення `T`, якщо `has_value() == true`. Якщо об'єкт містить помилку, повертається `static_cast<T>(std::forward<U>(default_value))`.

## 4. Монадичні оператори трансформації (Monadic Operations)

C++23 надає чотири монадичні методи, які дозволяють будувати безперервні конвеєри обробки даних без явного написання розлогих каскадів умовних операторів `if (!res.has_value())`.

### Таблиця семантики монадичних методів

| Метод | Сигнатура предикату `f` | Умова виклику `f` | Результат при `has_value() == true` | Результат при `has_value() == false` |
| :--- | :--- | :--- | :--- | :--- |
| **`and_then(f)`** | `T -> std::expected<U, E>` | Лише при `has_value() == true` | Повертає результат виклику `f(value())` | Повертає `std::unexpected(error())` без змін |
| **`transform(f)`** | `T -> U` | Лише при `has_value() == true` | Обгортає `f(value())` у `std::expected<U, E>` | Повертає `std::unexpected(error())` без змін |
| **`or_else(f)`** | `E -> std::expected<T, F>` | Лише при `has_value() == false` | Повертає початковий `expected<T, E>` | Повертає результат виклику `f(error())` |
| **`transform_error(f)`** | `E -> F` | Лише при `has_value() == false` | Повертає початковий `expected<T, E>` | Обгортає `f(error())` у `std::unexpected<F>` |

### Деталізація функціональної семантики монадичних методів

1. **`and_then(f)` (Monadic Bind)**:
   Застосовується для зв'язування послідовних операцій, кожна з яких сама може завершитися помилкою і повертає свій власний `std::expected<U, E>`. Якщо поточний стан — помилка, функція `f` не викликається зовсім, а помилка автоматично прокидається далі за конвеєром. Це дозволяє поєднувати незалежні функції з обробленням помилок у єдиний ланцюжок. Важливо, що тип помилки `E` мусить залишатися тотожним для всіх викликів у ланцюжку `and_then`.

2. **`transform(f)` (Monadic Map)**:
   Застосовується для чистих трансформацій корисного навантаження, які гарантовано не зазнають невдачі (наприклад, конвертація рядка у верхній регістр, масштабування числа або витягнення поля зі структури). Функція `f` приймає `T` і повертає `U`. Результат автоматично загортається у новий `std::expected<U, E>`. Якщо вхідний об'єкт містить помилку, функція `f` не обчислюється, а об'єкт помилки прокидається далі.

3. **`or_else(f)` (Monadic Recovery / Catch)**:
   Застосовується для перехоплення та відновлення після помилок. Функція `f` приймає об'єкт помилки `E` і повертає новий `std::expected<T, F>`. Це дозволяє спробувати альтернативне джерело даних, використати закешоване значення або перетворити помилку на успішне дефолтне значення. Якщо вхідний об'єкт містив значення `T`, функція відновлення відкидається.

4. **`transform_error(f)` (Monadic Error Mapping)**:
   Застосовується для адаптації або трансляції типів помилок при переході між архітектурними шарами системи (наприклад, трансформація низькорівневої помилки введення-виведення `IoError` у високорівневу бізнес-помилку `DomainError`). Функція `f` приймає `E` і повертає `F`. При наявності значення `T` функція `f` не викликається.

Кожен із цих методів підтримує перевантаження для rvalue-посилань (`&&`), що дозволяє ефективно переміщувати тимчасові об'єкти через конвеєр без зайвого виділення пам'яті чи копіювання рядків та векторів.

## 5. Спеціалізація std::expected<void, E>

Для системних процедур та процедур запису, які не повертають обчислених даних у разі успіху (повертають `void`), але можуть завершитися помилкою, стандарт надає спеціалізацію `std::expected<void, E>`.

### Особливості семантики `std::expected<void, E>`:
- **Відсутність корисного навантаження**: успішний стан не зберігає жодного об'єкта `T`. Фізичний розмір `sizeof` визначається виключно розміром типу помилки `E` та прапорця `bool`.
- **Конструювання за замовчуванням**: конструктор за замовчуванням створює об'єкт у стан успіху: `std::expected<void, ErrorCode> res;`.
- **Відсутність операторів разіменування**: методи `operator*` та `operator->` вилучено з інтерфейсу.
- **Метод `.value()`**: повертає `void`, якщо `has_value() == true`, або кидає виняток `std::bad_expected_access<E>`, якщо об'єкт містить помилку.
- **Монадичні адаптери**: для `std::expected<void, E>` методи `.and_then(f)` та `.transform(f)` приймають лямбда-функції без аргументів (`f()`), які викликаються лише при успішному стані.

Це робить спеціалізацію `std::expected<void, E>` ідеальною заміною для процедур, які раніше повертали прапорець `bool` або `int` код помилки у стиль C.

## 6. Гарантії винятків та безпека переміщення (Exception Safety)

Операції над `std::expected<T, E>` надають суворі гарантії безпеки винятків відповідно до стандартів C++23:
- **Гарантія конструктора переміщення**: якщо і `T`, і `E` забезпечують `noexcept` під час переміщення (`std::is_nothrow_move_constructible_v<T>` та `std::is_nothrow_move_constructible_v<E>`), конструктор переміщення `std::expected` також гарантовано отримує специфікатор `noexcept`.
- **Операції присвоєння та зміна стану**: під час присвоєння об'єкта нового стану (наприклад, перехід від наявного значення `T` до нової помилки `E`) відбувається знищення поточного об'єкта `T` через виклик його деструктора та створення об'єкта `E` за допомогою placement new. Якщо конструктор `E` кидає виняток під час створення, об'єкт `std::expected` залишається у стані, визначеному строгими гарантіями винятків (зазвичай зберігається попереднє значення або об'єкт переходить у стан валідного, але невизначеного вмісту).
- **Своп (Swap)**: функція `swap(std::expected& rhs)` має специфікатор `noexcept`, якщо конструктори переміщення та операції `swap` для обох типів `T` та `E` є `noexcept`. У випадку розбіжності станів (один об'єкт містить `T`, а інший `E`) виконання `swap` вимагає створення тимчасового об'єкта на стеку.

Окрім цього, стандарт гарантує, що при використанні тривіально копійованих типів `T` та `E` оператор присвоєння стає тривіальним викликом `memcpy`, що забезпечує нульовий оверхед на рівні машинних інструкцій.

## 7. Клас винятку std::bad_expected_access

Якщо розробник здійснює виклик методу `.value()` на об'єкті `std::expected<T, E>`, який перебуває в стані помилки (`has_value() == false`), стандарт гарантує виклик винятку типу `std::bad_expected_access<E>`.

```cpp
namespace std {
    template <typename E>
    class bad_expected_access : public bad_expected_access<void> {
    private:
        E val_; // Зберігає копію або переміщений об'єкт помилки
    public:
        explicit bad_expected_access(E e) : val_(std::move(e)) {}

        // Доступ до збереженого об'єкта помилки
        const E& error() const & noexcept { return val_; }
        E& error() & noexcept { return val_; }
        const E&& error() const && noexcept { return std::move(val_); }
        E&& error() && noexcept { return std::move(val_); }

        const char* what() const noexcept override {
            return "bad access to std::expected in error state";
        }
    };

    // Спеціалізація для void
    template <>
    class bad_expected_access<void> : public std::exception {
    public:
        const char* what() const noexcept override {
            return "bad access to std::expected<void>";
        }
    };
}
```

Цей тип винятку успадковується від `std::exception` і зберігає всередині себе копію об'єкта помилки `E`. Це дозволяє обробнику винятків витягнути оригінальний код помилки через метод `.error()` навіть тоді, коли код перейшов від монадичної моделі до традиційного блоку `try-catch`. Наявність повноцінної ієрархії винятків забезпечує зворотну сумісність із застарілими фреймворками.

## 8. Конвертувальні конструктори та приведення типів

Шаблон `std::expected<T, E>` підтримує прозоре приведення сумісних типів через конвертувальні конструктори:

```cpp
// Перетворення std::expected<U, G> у std::expected<T, E>
template <typename U, typename G>
constexpr explicit(!std::is_convertible_v<const U&, T> || !std::is_convertible_v<const G&, E>)
expected(const expected<U, G>& rhs);
```

Конструктор конвертації стає `explicit` (явним), якщо хоча б одне з перетворень `U -> T` або `G -> E` є явним. Якщо об'єкт `rhs` містив значення `U`, ініціалізується внутрішній `T`. Якщо `rhs` містив помилку `G`, ініціалізується внутрішній `E`. Цей механізм дозволяє прозоро повертати `std::expected<double, Error>` з функцій, які обчислюють `int` значення, без необхідності явного перетворення типів розробником.

## 9. Порівняльний аналіз з іншими типами бібліотеки

Для чіткого вибору інструменту в архітектурі системи корисно порівняти `std::expected` з суміжними контейнерами стандартної бібліотеки:

1. **`std::expected<T, E>` проти `std::optional<T>`**:
   - `std::optional` зберігає лише факт відсутності значення (`std::nullopt`). Він ідеально підходить для ситуацій, коли відсутність даних є нормою і не вимагає пояснення причини (наприклад, пошук елемента в хеш-таблиці або неіснуючий конфігураційний параметр).
   - `std::expected` зберігає повноцінний об'єкт помилки `E`. Він призначений для операцій, які можуть зазнати невдачі з різних причин (мережеві збої, відсутність прав, помилки парсингу) і вимагають логування чи специфічної реакції на конкретну причину.

2. **`std::expected<T, E>` проти `std::variant<T, E>`**:
   - `std::variant` є асиметрично-нейтральною сумою типів. Він не має вбудованого поняття "успіх" або "помилка", а доступ до типів вимагає використання `std::visit` або `std::get_if`.
   - `std::expected` має чітку семантичну орієнтацію: `T` є первинним "щасливим" значенням, а `E` — винятковим станом. Це дозволяє надати методи `.operator*()`, `.value()`, `.error()` та монадичні оператори `.and_then()` і `.transform()`, яких немає в `std::variant`.

3. **`std::expected<T, E>` проти винятків (`throw` / `catch`)**:
   - Винятки створюють неявний бічний канал передачі даних, розгортають стек і вимагають створення складних таблиць у бінарному файлі (`.eh_frame`). Вони ідеально підходять для справді рідкісних катастрофічних помилок (наприклад, вичерпання системної пам'яті або відсутність системного драйвера).
   - `std::expected` є повністю детермінованим контейнером на стеку. Він гарантує нульові накладні витрати на таблиці винятків та 100% передбачуваний час виконання, що робить його головним вибором для штатного оброблення помилок у високочастотних та embedded-системах.

## 10. Сумісність із constexpr та обчислення на етапі компіляції

Починаючи з C++23, усі конструктори, деструктори, оператори доступів та монадичні трансформації у `std::expected` позначені модифікатором `constexpr`. Це дозволяє виконувати повноцінну перевірку оброблення помилок ще на етапі компіляції програми.

```cpp
constexpr std::expected<int, const char*> parse_digit(char c) {
    if (c >= '0' && c <= '9') {
        return c - '0';
    }
    return std::unexpected("Не є цифрою");
}

// Перевірка обчислення в consteval контексті
static_assert(parse_digit('5').value() == 5);
static_assert(!parse_digit('a').has_value());
static_assert(parse_digit('a').error() == std::string_view("Не є цифрою"));
```

Можливість використання `std::expected` у `constexpr`-контекстах відкриває широкі можливості для побудови статично верифікованих парсерів конфігурацій, математичних обчислень та таблиць обробки даних без жодного виклику в runtime. Використання `consteval` функцій з `std::expected` гарантує, що некоректні дані перехоплюються ще під час збірки проекту компілятором.

## 11. Фізичний макет у пам'яті та бінарні розміри (Memory Layout)

Об'єкт `std::expected<T, E>` реалізовано як вирівняне теговане об'єднання (tagged union) без застосування динамічного виділення пам'яті в купі.

```cpp
// Концептуальна внутрішня структура реалізації у бібліотеці STL
template <typename T, typename E>
class expected {
private:
    union {
        T val_;
        E unex_;
    };
    bool has_value_;
};
```

### Формула обчислення загального розміру `sizeof`
Розмір об'єкта `std::expected<T, E>` розраховується за формулою з урахуванням вимог вирівнювання типів (`alignof`):

```
sizeof(std::expected<T, E>) 
= align_up(max(sizeof(T), sizeof(E)), alignof(bool)) + sizeof(bool) + padding
```

### Таблиця бінарних розмірів для поширених типів (x86_64, GCC/Clang):

| Тип `T` | Тип `E` | `sizeof(T)` | `sizeof(E)` | `sizeof(expected)` | Аналіз вирівнювання та заповнення (padding) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `int` | `int` | 4 | 4 | **8 байтів** | 4 байти max(T,E) + 1 байт bool + 3 байти padding до alignof(int)=4 |
| `double` | `int` | 8 | 4 | **16 байтів** | 8 байтів max(T,E) + 1 байт bool + 7 байтів padding до alignof(double)=8 |
| `std::string` | `std::error_code` | 32 | 16 | **40 байтів** | 32 байти max(T,E) + 16 байтів err + 1 байт bool + 7 байтів padding |
| `void` | `int` | 0 | 4 | **8 байтів** | 4 байти E + 1 байт bool + 3 байти padding |
| `void` | `std::error_code` | 0 | 16 | **24 байти** | 16 байтів E + 1 байт bool + 7 байтів padding до alignof(ptr)=8 |

Якщо і `T`, і `E` є тривіально копійованими типами (`std::is_trivially_copyable_v`), компілятор автоматично робить тривіально копійованим і сам `std::expected<T, E>`. Це дозволяє передавати об'єкти `std::expected` безпосередньо через регістри CPU (`RAX`, `RDX`), забезпечуючи максимальну продуктивність системних викликів на рівні сирих C-структур.

Окрім цього, сучасні компілятори (GCC та Clang) виконують оптимізацію передачі малого об'єкта `expected` у регістрі `RAX` (або `EAX` для 32-бітних архітектур), що повністю усуває необхідність проходження через стек при поверненні результату з функції.
