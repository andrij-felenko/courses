# 📋 Довідник сигнатур та реалізації CPO і tag_invoke

Цей довідник містить повну технічну специфікацію, сигнатури, архітектурні шаблони та контракти реалізації точок налаштування у C++. У ньому наведено детальний аналіз функціональних викликів, механізмів ізоляції просторів імен, концептуальних обмежень та готових паттернів для проектирования власних розширюваних бібліотек — від класичного ADL до об'єктів CPO стандарту C++20 та уніфікованого механізму `tag_invoke` у C++23/C++26.

## 1. Специфікація класичного ADL-патерну з фолбеком (C++11/C++14)

Класична точка налаштування C++11 покладається на поєднання неповнокваліфікованого виклику функції з попередньою декларацією `using`. Цей механізм вимагає суворого дотримання трьох конструктивних вимог: наявності базової функції у стандартному або бібліотечному просторі імен, використання двохкрокової ідіоми виклику та забезпечення коректного вибору між перевантаженнями за допомогою вагових маркерів типів.

### Механізм диспетчеризації через пріоритетні маркери

Для того щоб бібліотечна функція могла відрізнити користувацьку специфічну реалізацію від стандартної базової версії без виникнення рекурсії або неоднозначності перевантаження (ambiguous call), використовується ідіома з передачею цілочисельного маркера пріоритету (`int` проти `long`). Компілятор віддає перевагу точному збігу типу `int` над неявним приведенням до `long`, що дозволяє надавати пріоритет перевантаженню, знайденому через ADL, над базовим фолбеком.

У наведеному нижче шаблоні реалізовано двокрокову систему `serialize_impl`. Перша гілка відповідає за стандартний запасний варіант (fallback), яка активується тільки у тому випадку, коли користувацький тип не надає власного перевантаження. Друга гілка через SFINAE перевіряє наявність функції `serialize` у просторі імен аргументу:

```cpp
namespace my_lib {
    namespace detail {
        // Низькопріоритетний фолбек для будь-яких типів, що підтримують std::ostream
        template<typename T>
        auto serialize_impl(const T& obj, std::ostream& os, long)
            -> decltype(os << obj, void())
        {
            os << obj;
        }

        // Високопріоритетне перевантаження, що активується за наявності користувацької serialize
        template<typename T>
        auto serialize_impl(const T& obj, std::ostream& os, int)
            -> decltype(serialize(os, obj), void()) 
        {
            serialize(os, obj); // Виклик користувацької функції через ADL
        }
    }

    // Публічний фасад бібліотеки
    template<typename T>
    void serialize(const T& obj, std::ostream& os) {
        using my_lib::detail::serialize_impl;
        serialize_impl(obj, os, 0); // int(0) віддає перевагу високопріоритетній гілці
    }
}
```

### Контракт реалізації в користувацькому коді

Розробник користувацького типу має оголосити функцію `serialize` у тому ж просторі імен, де визначено сам тип. Найбільш надійним способом є використання дружньої вкладеної функції (`friend function`), яка оголошується всередині тіла структури чи класу. Це гарантує, що функція не засмічує зовнішній простір імен і доступна виключно через ADL при передачі об'єкта даного типу:

```cpp
namespace user_space {
    class DataPacket {
    private:
        std::string header_;
        std::vector<uint8_t> payload_;

    public:
        DataPacket(std::string h, std::vector<uint8_t> p)
            : header_(std::move(h)), payload_(std::move(p)) {}

        // Дружня точка налаштування, що знаходиться виключно через ADL
        friend void serialize(std::ostream& os, const DataPacket& packet) {
            os << "Packet[" << packet.header_ << "]: " << packet.payload_.size() << " bytes";
        }
    };
}
```

Головним обмеженням даної моделі є відсутність суворого контролю на рівні сигнатури виклику: якщо розробник припустився помилки у типах аргументів дружньої функції, компілятор мовчки відкине її й застосує фолбек, що призводить до важковловимих помилок під час виконання програмою.

## 2. Специфікація C++20 Customization Point Object (CPO)

Відповідно до вимог нормативного розділу стандарту C++20 `[custom.mana]`, об'єкт-CPO є глобальним константним екземпляром унікального класу-функтора. Такий об'єкт має жорстко визначені властивості щодо категорій значень, номінальної безпеки винятків та відсутності мутабельного стану.

### Нормативні вимоги стандарту C++20 до CPO

Для того щоб об'єкт повністю відповідав специфікації CPO C++20, він повинен задовольняти наступні чотири імперативні вимоги:
1. **Незмінність та константність.** Об'єкт повинен бути оголошений як `inline constexpr` і мати семантику безстанового (stateless) функтора. Оператори виклику `operator()` обов'язково маркуються як `const`.
2. **Заборона копіювання та копіювального присвоювання.** Тип функтора не дозволяє створення копій або переміщення екземплярів об'єкта, щоб унеможливити передачу CPO за значенням у шаблонні функції.
3. **Захист від викрадення адреси.** Взяття адреси об'єкта `&cpo` заборонено або повертає спеціальний захищений тип, що запобігає конвертації CPO у сирий покажчик на функцію.
4. **Гарантія точного відбору (Constrained Call Site).** Виклик `cpo(args...)` є цілісним концептуальним виразом. Якщо аргументи не відповідають жодній із гілок диспетчеризації, вираз `std::invocable<decltype(cpo), Args...>` повертає `false`, а спроба виклику призводить до помилки у місці виклику, а не всередині тіла функтора.

### Перелік основних CPO стандартної бібліотеки C++20

Стандарт C++20 містить цілу серію готових CPO у просторі імен `std::ranges`:

- **`std::ranges::begin`**: повертає ітератор на початок діапазону. Послідовно перевіряє метод `t.begin()`, потім ADL `begin(t)`, потім роботу з C-масивами.
- **`std::ranges::end`**: повертає маркер кінця (ітератор або sentinel). Перевіряє `t.end()`, потім ADL `end(t)`.
- **`std::ranges::swap`**: здійснює обмін двох значень. Перевіряє ADL `swap(a, b)`, потім метод-член, потім загальний переміщувальний обмін.
- **`std::ranges::size`**: повертає кількість елементів діапазону. Перевіряє `t.size()`, ADL `size(t)`, або обчислює різницю `end(t) - begin(t)`.
- **`std::ranges::data`**: повертає покажчик на сирий масив даних. Перевіряє `t.data()`, або `std::to_address(begin(t))`.
- **`std::ranges::empty`**: повертає булевий прапорець порожнечі. Перевіряє `t.empty()`, `size(t) == 0`, або порівняння `begin(t) == end(t)`.

### Детальний розбір механізму Poisoned Context (отруєного контексту)

Найважливішим елементом безпеки CPO є захист від нескінченної рекурсії під час пошуку через ADL. Коли об'єкт CPO `std::ranges::begin` намагається виконати виклик `begin(t)` через ADL, існує ризик того, що компілятор знов повернеться до виклику самого глобального об'єкта `std::ranges::begin`.

Щоб цього не сталося, виклик `begin(t)` виконується всередині приватного простору імен деталі (`namespace __detail`), де явно оголошено видалену функцію з тією ж назвою:

```cpp
namespace std::ranges::__detail {
    // Декларація видаленої функції відключає пошук об'єкта CPO в зовнішніх просторах
    void begin() = delete;
    void end() = delete;
}
```

Коли компілятор обчислює вираз `begin(t)` всередині `__detail`:
- Якщо у просторі імен аргументу `T` існує користувацька функція `begin(T&)`, ADL знаходить її у просторі імен аргументу. Оскільки користувацька функція є більш специфічною, ніж `void begin() = delete`, компілятор обирає користувацьку реалізацію.
- Якщо користувацької функції у просторі імен `T` немає, ADL знаходить лише видалену декларацію `void begin() = delete` у поточному просторі імен. Оскільки функція видалена, компілятор відкидає цю гілку диспетчеризації за правилом SFINAE і переходить до наступної гілки (наприклад, перевірки C-масивів).

Ця архітектура повністю виключає нескінченну рекурсію та робить відбір перевантажень абсолютно детермінованим.

### Простеження алгоритму диспетчеризації CPO під час компіляції

Коли компілятор зустрічає кваліфікований виклик `std::ranges::begin(expr)`, виконання виразу не викликає динамічної диспетчеризації через таблицю віртуальних функцій (vtable). Натомість компілятор обчислює шаблонний тип `T = decltype(expr)` і послідовно виконує вибір відповідного перевантаження `operator()` на етапі компіляції:

1. **Аналіз виразу на наявність методу-члена.** Компілятор перевіряє, чи вираз `expr.begin()` є синтаксично коректним і чи повертає об'єкт, який задовольняє концепт `std::input_or_output_iterator`. Якщо ця умова виконується, інстанціюється перша гілка `operator()`, яка виконує безпосередній виклик методу-члена.
2. **Перевірка відсутності методу та виконання ADL.** Якщо метод-член відсутній або повертає тип, який не є ітератором, компілятор обчислює предикат другої гілки. У цій гілці виконується неповнокваліфікований виклик `begin(expr)` у закритому просторі імен. Пошук ADL сканує всі асоційовані простори імен типу `T`. Якщо знайдено підходяще перевантаження, інстанціюється друга гілка.
3. **Обробка спеціальних типів та масивів.** Якщо аргументом `expr` є статичний C-масив `U[N]`, обирається спеціалізоване масивне перевантаження, що повертає покажчик `expr + 0`.
4. **SFINAE-відмова у разі відсутності кандидатів.** Якщо жодна з трьох гілок не справдилася, компілятор вилучає об'єкт CPO з множини кандидатів для виклику. При цьому вираз `requires { std::ranges::begin(expr); }` оцінюється як `false`, що дозволяє використовувати CPO у предикатах концептів без ризику зупинки компіляції.

### Анатомія класу CPO (`custom_cpo_fn`)

Нижче наведено вичерпну виробничу реалізацію CPO `my_lib::draw`. Архітектура розбита на чотири ізольовані шари: отруєний контекст для запобігання рекурсії, предикати концептів, клас-функтор та глобальний екземпляр.

```cpp
namespace my_lib {
    namespace __draw_detail {
        // Крок 1: Оголошення видаленої функції в отруєному контексті.
        // Це блокує нескінченну рекурсію, якщо ADL знову знайде назву draw
        void draw() = delete;

        // Крок 2: Опис концептів для послідовного вибору гілки диспетчеризації
        template<typename T>
        concept has_member_draw = requires(T&& t) {
            std::forward<T>(t).draw();
        };

        template<typename T>
        concept has_adl_draw = !has_member_draw<T> && requires(T&& t) {
            draw(std::forward<T>(t)); // ADL шукає у внутрішньому просторі __draw_detail
        };

        // Крок 3: Головний тип функтора
        struct __draw_fn {
            // Гілка 1: Виклик методу-члена класу t.draw()
            template<has_member_draw T>
            constexpr auto operator()(T&& t) const
                noexcept(noexcept(std::forward<T>(t).draw()))
            {
                return std::forward<T>(t).draw();
            }

            // Гілка 2: Виклик функції draw(t) через ADL у ізольованому контексті
            template<has_adl_draw T>
            constexpr auto operator()(T&& t) const
                noexcept(noexcept(draw(std::forward<T>(t))))
            {
                return draw(std::forward<T>(t));
            }

            // Заборона шкідливих операцій над CPO об'єктом
            __draw_fn() = default;
            __draw_fn(const __draw_fn&) = delete;
            __draw_fn(__draw_fn&&) = delete;
            __draw_fn& operator=(const __draw_fn&) = delete;
            __draw_fn& operator=(__draw_fn&&) = delete;
        };
    }

    // Крок 4: Глобальна inline constexpr константа CPO
    inline constexpr __draw_detail::__draw_fn draw{};
}
```

### Використання концептів для перевірки спроможності виклику

Завдяки такій структурі перевірка того, чи підтримує тип `T` точку налаштування `my_lib::draw`, стає тривіальною метапрограмістською операцією:

```cpp
template<typename T>
concept drawable = std::invocable<decltype(my_lib::draw), T>;

// Приклад використання в обмеженому шаблоні
template<drawable T>
void render_object(const T& obj) {
    my_lib::draw(obj); // Гарантовано безпечний виклик
}
```

## 3. Специфікація двигуна `tag_invoke` (C++20/C++23)

Патерн `tag_invoke` є архітектурним узагальненням CPO, розробленим для уникнення вибухового зростання кількості об'єктів-функторів у великих фреймворках (таких як `std::execution`). У цьому підході замість створення десятків унікальних імен функцій ADL шукає **лише одну функцію** під іменем `tag_invoke`, а сама точка налаштування передається першим аргументом як тип-тег.

### Переваги архітектури `tag_invoke` у масштабних фреймворках

Застосування `tag_invoke` вирішує три критичні архітектурні проблеми проектування складних C++ бібліотек:
- **Уніфікація ADL-пошуку.** Пошук імен обмежується дослідженням лише однієї назви `tag_invoke`. Це спрощує роботу оптимізаторів компілятора та прискорює створення індексів у середовищах розробки (IDE).
- **Спрощення створення користувацьких типів.** Розробник стороннього класу реалізує один шаблонний метод `friend auto tag_invoke(Tag, ...)` у якому за допомогою `if constexpr` або спеціалізацій тегів описує реакцію класу на будь-які точки налаштування фреймворку.
- **Гнучка передача контексту та атрибутів.** Тег точки налаштування може нести у своєму типі додаткові метадані (наприклад, типи повернюваних значень або вимоги до потокобезпечності), які стають доступними при аналізі сигнатури `tag_invoke`.

### Детальна механіка відбору перевантажень у `tag_invoke`

Коли виконується виклик `my_framework::tag_invoke(tag, args...)`, компілятор обробляє вираз у наступній послідовності:

1. **Ідентифікація типів аргументів.** Компілятор визначає тип тегу `Tag` та типи всіх переданих параметрів `Args...`.
2. **Сканування асоційованих просторів імен.** Виконується ADL для ім'я `tag_invoke`. Пошук охоплює простір імен самого тегу `Tag`, а також простори імен усіх типів з `Args...`.
3. **Сотування кандидатур за відповідністю.** Якщо розробник користувацького типу оголосив дружню функцію `friend auto tag_invoke(Tag_Type, Target_Type, ...)`, вона стає найкращим кандидатом завдяки точній відповідності першого аргументу (типу тегу).
4. **Оцінка концепту `tag_invocable`.** Якщо ADL не знаходить підходящої функції `tag_invoke`, концепт `tag_invocable<Tag, Args...>` оцінюється як `false`. Завдяки цьому виклик CPO відхиляється на рівні `requires`-блоки без генерації важких каскадних помилок компілятора.

### Повний виробничий шаблон двигуна `tag_invoke`

Двигун складається з базового функтора `__tag_invoke_fn`, концепту перевірки `tag_invocable` та єдиного глобального CPO `my_framework::tag_invoke`:

```cpp
namespace my_framework {
    namespace __tag_invoke_detail {
        // Оголошення незавершеної функції в отруєному контексті
        void tag_invoke();

        // Концепт перевірки спроможності виклику tag_invoke для даного тегу та аргументів
        template<typename Tag, typename... Args>
        concept tag_invocable = requires(Tag&& tag, Args&&... args) {
            tag_invoke(std::forward<Tag>(tag), std::forward<Args>(args)...);
        };

        // Функтор диспетчеризації
        struct __tag_invoke_fn {
            template<typename Tag, typename... Args>
                requires tag_invocable<Tag, Args...>
            constexpr decltype(auto) operator()(Tag&& tag, Args&&... args) const
                noexcept(noexcept(tag_invoke(std::forward<Tag>(tag), std::forward<Args>(args)...)))
            {
                return tag_invoke(std::forward<Tag>(tag), std::forward<Args>(args)...);
            }
        };
    }

    // Єдиний глобальний об'єкт диспетчеризації
    inline constexpr __tag_invoke_detail::__tag_invoke_fn tag_invoke{};

    // Допоміжний концепт для публічного користування
    template<typename Tag, typename... Args>
    concept tag_invocable = __tag_invoke_detail::tag_invocable<Tag, Args...>;
}
```

### Створення конкретної точки налаштування (Тегу)

Для створення нової точки налаштування у фреймворку не потрібно знову писати класи ізоляції ADL. Достатньо визначити порожній тип тегу з власним `operator()`:

```cpp
namespace my_framework {
    // Структура тегу точки налаштування "connect"
    struct connect_t {
        template<typename Sender, typename Receiver>
            requires tag_invocable<connect_t, Sender, Receiver>
        constexpr decltype(auto) operator()(Sender&& s, Receiver&& r) const
            noexcept(noexcept(tag_invoke(connect_t{}, std::forward<Sender>(s), std::forward<Receiver>(r))))
        {
            return tag_invoke(connect_t{}, std::forward<Sender>(s), std::forward<Receiver>(r));
        }
    };

    // Глобальний об'єкт точки налаштування connect
    inline constexpr connect_t connect{};
}
```

### Інтеграція користувацького типу з двигуном `tag_invoke`

Користувач описує будь-яку кількість точок налаштування фреймворку всередині свого класу через уніфікований інтерфейс `friend tag_invoke`:

```cpp
namespace user_space {
    struct MyOperationState {
        void start() noexcept {}
    };

    struct MySender {
        // Реалізація точки налаштування connect для MySender
        template<typename Receiver>
        friend auto tag_invoke(my_framework::connect_t, MySender&& self, Receiver&& r) noexcept {
            return MyOperationState{};
        }
    };
}
```

### Основні точки налаштування у `std::execution` (C++26 P2300)

Фреймворк асинхронного програмування `std::execution` будується на широкому застосуванні `tag_invoke` для управління обчислювальними графами (Sender/Receiver model):

- **`std::execution::connect`**: зв'язує джерело результату (Sender) із приймачем (Receiver), повертаючи об'єкт стану операції (Operation State).
- **`std::execution::start`**: запускає асинхронну операцію, збережену в Operation State.
- **`std::execution::set_value`**: передає успішний результат обчислення від Sender до Receiver.
- **`std::execution::set_error`**: передає інформацію про виняток чи помилку Receiver-у.
- **`std::execution::set_stopped`**: сповіщає Receiver про скасування виконання операції.
- **`std::execution::get_env`**: запитує контекст виконання або оточення (Environment) у Sender чи Receiver.

## 4. Специфікація C++23/C++26 Статичних CPO (`static operator()`)

З прийняттям стандарту C++23 мова дозволила оголошувати оператор виклику функтора як статичний метод (`static operator()`). Це дає вагому оптимізацію для об'єктів CPO: компілятору більше не потрібно передавати неактуальний покажчик `this` через регістри процесора під час виклику CPO.

### Шаблон CPO стандарту C++23/C++26

```cpp
namespace my_lib_cpp23 {
    struct __process_fn {
        // Статичний оператор виклику усуває оверхед передачі прихованого аргументу this
        template<typename T>
        static constexpr auto operator()(T&& t) noexcept(noexcept(std::forward<T>(t).process()))
            requires requires { std::forward<T>(t).process(); }
        {
            return std::forward<T>(t).process();
        }
    };

    inline constexpr __process_fn process{};
}
```

## 5. Порівняльна матриця характеристик підходів

Нижче наведено вичерпне порівняння чотирьох підходів до проектирования точок налаштування у C++ за ключовими технічними критеріями:

| Критерій порівняння | Класичний ADL (C++98/11) | Спеціалізація `std` (C++98) | CPO Ranges (C++20) | Двигун `tag_invoke` (C++23) |
| :--- | :--- | :--- | :--- | :--- |
| **Синтаксис виклику** | `using std::swap; swap(a, b);` | `std::hash<T>{}(val);` | `std::ranges::swap(a, b);` | `my_fw::connect(s, r);` |
| **Точність локалізації ADL** | ❌ Відкрита (ризик викрадення) | ✅ Відсутній ADL | ✅ Ізольований Poisoned Context | ✅ Ізольований єдиний вузол |
| **Вплив на час компіляції** | ⚡ Мінімальний | 🐢 Високий (шаблони класів) | 🐢 Помітне зростання типів | ⚡ Оптимальний (одне ім'я ADL) |
| **Діагностика помилок** | ❌ Каскадна у надрах шаблону | ⚠️ Часткова | ✅ Миттєва у точці виклику | ✅ Миттєва у точці виклику |
| **Обсяг метакоду (Boilerplate)**| ⚡ Практично відсутній | ⚠️ Помірний | 🐢 Великий для кожного CPO | ⚡ Мінімальний (один тег) |
| **Підтримка концептів C++20** | ❌ Вимагає складних SFINAE | ⚠️ Поліморфізм типів | ✅ Вроджена через `requires` | ✅ Вроджена через `requires` |
| **Сумісність зі стандартами** | C++98 / C++11 | C++98 / C++11 | C++20 | C++23 / C++26 |

## 6. Критичні підводні камені реалізації та як їх уникати

1. **Втрата специфікації `noexcept`.** Оператор виклику `operator()` у CPO або в обгортках `tag_invoke` повинен завжди точно транслювати умовний `noexcept(noexcept(...))` від виклику підстилаючої реалізації. Якщо специфікацію `noexcept` пропущено, компілятор вважатиме виклик CPO потенційно небезпечним, що відключить оптимізації переміщення у стандартних контейнерах.
2. **Відсутність блокування рекурсії в отруєному контексті.** Якщо всередині приватного простору імен деталі CPO не оголошено видалену функцію з тією ж назвою (`void draw() = delete;`), недоглянутий ADL-виклик за відсутності користувацького перевантаження спробує повторно викликати самий об'єкт CPO, спричиняючи нескінченну рекурсію та переповнення стеку під час компіляції чи виконання.
3. **Некоректна категорія значень при передачі аргументів.** Усі оператори виклику CPO та функції `tag_invoke` повинні приймати аргументи за прохідними посиланнями (`T&&... args`) і застосовувати `std::forward<Args>(args)...` при передачі в підстилаючі методи. Передача аргументів за значенням призводить до небажаних копіювань тимчасових об'єктів та руйнує семантику переміщення.
4. **Ненавмисне захоплення тимчасових об'єктів (Dangling References).** При поверненні посилань з CPO (наприклад, `std::ranges::begin`) необхідно переконуватися, що CPO не приймає rvalue тимчасовий контейнер за посиланням, адже повернений ітератор стане невалідним одразу після завершення виразу (dangling iterator).
5. **Проблема порядку статики (Static Initialization Order Fiasco).** Завдяки маркуванню CPO як `inline constexpr` об'єкти конструюються на етапі компіляції й не залежать від порядку ініціалізації глобальних змінних у різних модулях компіляції (translation units).
6. **Правильне використання у метапрограмуванні.** Для перевірки наявності CPO в типах слід використовувати `std::invocable<decltype(cpo), T>` замість власноруч написаних конструкцій SFINAE з `decltype`, що гарантує сумісність із концептами C++20.
7. **Оптимізація часу компіляції.** У великих проектах надмірне залучення CPO з багатьма гілками перевірок `requires` може сповільнювати збірку. Використання `tag_invoke` знижує кількість згенерованих компілятором типів функторів і скорочує час компіляції.
