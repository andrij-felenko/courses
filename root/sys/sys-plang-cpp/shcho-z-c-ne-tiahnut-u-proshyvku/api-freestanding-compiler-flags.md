# 📋 Прапорці компілятора та таблиці ABI для Freestanding C++

У розробці системного програмного забезпечення без операційної системи (Freestanding Environment) конфігурація компілятора та компонувальника безпосередньо визначає двійковий склад кінцевого образу прошивки. На відміну від прикладних програм для комп'ютерів із повноцінною операційною системою (Hosted Environment), де середовище виконання надає готові системні сервіси, завантажувач динамічних бібліотек, віртуальну пам'ять та диспетчер винятків, мікроконтролерні програми починають виконання з «голого заліза» одразу після сигналу апаратного скидання.

Якщо скомпілювати стандартний проєкт C++ для вбудованої системи без спеціальних прапорців, компілятор за замовчуванням припускає наявність середовища Hosted. У результаті компонувальник додає сотні кілобайтів службових таблиць часу виконання, підключає важкі функції ініціалізації середовища, створює приховані залежності від системних викликів `_sbrk` або `_exit` та перетворює передбачувані інструкції на непрямі переходи.

Нижче наведено структурований довідник прапорців компіляторів GCC та Clang (`arm-none-eabi-g++`, `riscv-none-elf-g++`), аналіз двійкових секцій лінкера та огляд офіційної матриці доступності заголовків стандартної бібліотеки C++ у середовищі Freestanding.

---

## 1. Системні прапорці компілятора для середовища Freestanding

Компілятори C++ надають набір спеціалізованих прапорців, які вимикають невідповідні механізми часу виконання та переводять кодогенератор у режим генерації строго автономного двійкового коду.

### Прапорець `-ffreestanding`
Цей прапорець фундаментально змінює модель цільової платформи в компіляторі. У стандартному режимі `-fhosted` компілятор вважає, що програма запускається через стандартну функцію `int main(int argc, char** argv)`, а перед цим виконується системний файл ініціалізації `crt0.o`. У режимі `-ffreestanding` компілятор позбавляється припущення про наявність операційної системи: функція `main` більше не зобов'язана приймати аргументи, вона може взагалі ніколи не повертати керування, а точкою входу може бути будь-який символ вектора переривань (наприклад, `Reset_Handler`). Водночас цей прапорець вимикає неявну підстановку системних функцій стандартної бібліотеки C, залишаючи лише базові вбудовані операції (`memcpy`, `memmove`, `memset`, `memcmp`).

### Прапорець `-fno-exceptions`
Цей прапорець повністю вимикає генерацію коду обробки винятків (`try`, `catch`, `throw`). У стандартному режимі для кожної функції компілятор зобов'язаний згенерувати метадані розгортання стеку (Stack Unwinding Tables) та секції зворотних викликів деструкторів (Landing Pads), які займають від 15% до 30% загального обсягу Flash-пам'яті. Прапорець `-fno-exceptions` запобігає створенню цих таблиць у секціях `.ARM.exidx` та `.ARM.extab` або `.eh_frame`. Якщо у вихідному коді або заголовках бібліотеки зустрічається ключове слово `throw`, компілятор замінює його на прямий виклик `std::terminate()` або генерує помилку компіляції.

### Прапорець `-fno-rtti`
Цей прапорець вимикає генерацію інформації про типи під час виконання (Run-Time Type Information). За замовчуванням для кожного класу з віртуальними функціями компілятор розміщує в секції констант `.rodata` спеціальну структуру `std::type_info`, яка містить манглену назву класу, покажчики на базові класи та зміщення для поліморфного приведення. Використання `-fno-rtti` повністю видаляє ці структури, економлячи від 5% до 15% простору Flash. При спробі використати оператори `dynamic_cast` або `typeid` компілятор зупиняє збирання з помилкою.

### Прапорець `-fno-threadsafe-statics`
Згідно зі стандартом C++11 (ініціалізація Меєрса), локальні статичні змінні всередині функцій повинні ініціалізуватися безпечно в багатопотоковому середовищі. Для цього компілятор генерує приховані виклики функцій `__cxa_guard_acquire` та `__cxa_guard_release`, які блокують виконання через системний м'ютекс. У середовищі мікроконтролера без операційної системи ці функції або викликають помилку компонування, або тягнуть за собою порожні системні заглушки. Прапорець `-fno-threadsafe-statics` прибирає ці виклики, перетворюючи ініціалізацію на перевірку простого бітового прапорця, що є безпечним для однопотокових систем або вимагає захисту критичної секції через заборону переривань.

### Прапорець `-fno-use-cxa-atexit`
У класичних настільних додатках під час завершення функції `main` або виклику `exit()` операційна система послідовно викликає деструктори всіх глобальних та статичних об'єктів у порядку, зворотному до їх створення. Для цього використовується функція реєстрації `__cxa_atexit`, яка виділяє блоки в динамічній пам'яті. Оскільки мікроконтролер виконує прошивку в нескінченному циклі й ніколи не завершує роботу штатно, реєстрація деструкторів у таблиці виходу є абсолютно безглуздою тратою оперативної та постійної пам'яті. Прапорець `-fno-use-cxa-atexit` забороняє реєстрацію таких обробників.

### Прапорці `-fno-unwind-tables` та `-fno-asynchronous-unwind-tables`
Ці прапорці забороняють кодогенератору додавати в об'єктні файли DWARF-таблиці розгортання стек-фреймів для зневадження та асинхронної обробки сигналів. Це значно скорочує розмір проміжних об'єктних файлів та запобігає випадковому потраплянню налагоджувальних метаданих у двійковий образ прошивки.

### Прапорці секціонування `-ffunction-sections` та `-fdata-sections`
За замовчуванням компілятор поміщає машинний код усіх функцій однієї одиниці трансляції в єдину секцію `.text`, а всі змінні — у секції `.data` та `.bss`. Якщо програма використовує лише одну функцію з великого вихідного файлу бібліотеки, лінкер буде змушений включити у прошивку весь об'єктний файл цілком. Прапорці секціонування змушують компілятор поміщати кожну функцію в окрему секцію `.text.function_name`, а кожну змінну — у `.data.variable_name`. Це дає компонувачу можливість видалити абсолютно весь мертвий код за допомогою прапорця лінкера `--gc-sections`.

## 2. Опції компонувальника та зв'язування з бібліотеками

Компонування прошивки вимагає узгодження адресного простору з картою апаратних регістрів та розміщення секцій пам'яті за допомогою скрипта лінкера (Linker Script).

```
┌─────────────────────────────────────────────────────────────┐
│                 Об'єктні файли програми (.o)                │
└──────────────────────────────┬──────────────────────────────┘
                               │ Компонування: -Wl,--gc-sections
                               ▼
┌─────────────────────────────────────────────────────────────┐
│              Видалення невикористаних секцій                │
│   • Видалення функцій, які не викликаються з entry point    │
│   • Видалення невикористовуваних константних таблиць        │
└──────────────────────────────┬──────────────────────────────┘
                               │ Бібліотеки: -specs=nano.specs
                               ▼
┌─────────────────────────────────────────────────────────────┐
│              Кінцевий бінарний образ (.elf / .bin)          │
└─────────────────────────────────────────────────────────────┘
```

### Прапорець `-Wl,--gc-sections`
Команда передає прапорець `--gc-sections` (Garbage Collection of Sections) безпосередньо компонувальнику. Лінкер будує граф викликів, починаючи від точки входу програми (`Reset_Handler`), та рекурсивно позначає всі досяжні секції коду й даних. Усі секції, які не мають активних посилань, безповоротно видаляються з двійкового образу. Це забезпечує мінімальний розмір фінального бінарного файлу.

### Специфікація `-specs=nano.specs`
Стандартна бібліотека C Newlib містить повні реалізації функцій форматованого виводу (`printf`, `sprintf`), які підтримують плаваючу кому, локалі та довгі формати, що додає від 30 до 60 КБ Flash. Підключення специфікації Newlib-nano підміняє ці функції їх мініатюрними версіями, спеціально оптимізованими для вбудованих систем із жорстким обмеженням пам'яті.

### Специфікація `-specs=nosys.specs`
Під час виклику деяких внутрішніх бібліотечних функцій стандартна бібліотека звертається до низькорівневих системних викликів операційної системи (таких як `_sbrk` для виділення купи, `_write` для виводу символів або `_exit`). У середовищі без операційної системи ці символи відсутні, що призводить до помилки лінкера. Специфікація `nosys.specs` підключає порожні заглушки для всіх системних викликів, дозволяючи проєкту успішно компонуватися без ручного написання десятків порожніх функцій.

## 3. Двійкові секції пам'яті та їх призначення у Flash і SRAM

Фізична пам'ять мікроконтролера розділена на енергонезалежну пам'ять програм (Flash/ROM) та швидку оперативну пам'ять із довільним доступом (SRAM). Робота прошивки опирається на чітке структурування секцій:

- **Секція коду `.text`**: Містить безпосередньо виконувані машинні інструкції функцій та вектор таблиці переривань. У мікроконтролерах ця секція розміщується у Flash і виконується на місці без копіювання в RAM (механізм XIP — Execute In Place).
- **Секція сталих `.rodata`**: Зберігає незмінні дані: числові константи, рядкові літерали, масиви перекодування та налагоджувальні рядки. Розміщується у Flash-пам'яті.
- **Секція ініціалізованих змінних `.data`**: Містить глобальні та статичні змінні з ненульовими початковими значеннями. Початкові байти зберігаються у Flash-пам'яті (LMA — Load Memory Address), а стартап-код мікроконтролера перед передачею керування функції `main` копіює їх у пам'ять SRAM за реальними адресами виконання (VMA — Virtual Memory Address).
- **Секція неініціалізованих змінних `.bss`**: Містить статичні змінні з нульовою або відсутньою явною ініціалізацією. Для економії місця у Flash самі нулі не зберігаються: у бінарнику фіксується лише розмір секції, а стартап-код заповнює цей діапазон у SRAM нулями під час запуску.
- **Таблиця конструкторів `.init_array`**: Спеціальна секція у Flash-пам'яті, що містить список адрес конструкторів усіх глобальних об'єктів C++. Стартап-код послідовно проходить цей масив і викликає кожен конструктор до запуску основної логіки.
- **Таблиці розгортання винятків `.ARM.exidx` та `.ARM.extab`**: Секції ARM Exception Handling ABI, які описують діапазони адрес та інструкції відновлення регістрів. При використанні прапорця `-fno-exceptions` ці секції стають порожніми та повністю видаляються компонувальником.

## 4. Доступність компонентів C++ у середовищі Freestanding

Стандарти C++20 та C++23 офіційно закріпили статус Freestanding як повноправного режиму виконання мови, розширивши перелік гарантовано доступних заголовків.

```
┌─────────────────────────────────────────────────────────────┐
│                 Freestanding C++ Заголовки                  │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ <cstddef> <cstdint> <type_traits> <limits> <utility>  │  │
│  │ <tuple> <span> <array> <optional> <expected>          │  │
│  │ <variant> <bit> <concepts> <numbers> <atomic>         │  │
│  └───────────────────────────────────────────────────────┘  │
│                                                             │
│              Hosted C++ Заголовки (Потребують ОС/купи)      │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ <vector> <string> <iostream> <thread> <filesystem>    │  │
│  │ <regex> <future> <memory_resource> <chrono>           │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

У середовищі Freestanding без операційної системи гарантовано працюють:
1. **Типові та числові примітиви**: `<cstddef>` (базові типи `size_t`, `std::byte`), `<cstdint>` (цілі типи фіксованої ширини `uint32_t`), `<limits>` (апаратні числові межі) та `<numbers>` (математичні константи `pi`, `e`).
2. **Метапрограмування та концепції**: `<type_traits>` (перевірка типів на етапі компіляції), `<concepts>` (обмеження шаблонних параметрів) та `<utility>` (операції переміщення `std::move`, пряме перенаправлення `std::forward`).
3. **Статичні контейнери та представлення пам'яті**: `<array>` (фіксовані буфери без динамічної пам'яті), `<span>` (типобезпечний неволодіючий зріз неперервної пам'яті).
4. **Типобезпечні обгортки значень та результатів**: `<optional>` (значення або порожній стан), `<variant>` (типобезпечне теговане об'єднання фіксованого розміру) та `<expected>` (повернення результату або коду помилки без генерації винятків).
5. **Бітові маніпуляції**: `<bit>` (підрахунок провідних нулів `std::countl_zero`, швидке реверсування бітів, безпечне перетворення представлення через `std::bit_cast`).
6. **Атомарні операції**: `<atomic>` (гарантовано працює для lock-free типів, що транслюються в прямі апаратні інструкції мікропроцесора `LDREX`/`STREX` або `LR`/`SC`).

Водночас заголовки динамічних контейнерів (`<vector>`, `<string>`, `<map>`), потоків введення-виведення (`<iostream>`), багатопотоковості (`<thread>`, `<mutex>`) та файлової системи (`<filesystem>`) належать виключно до режиму Hosted і не можуть використовуватися безпосередньо в середовищі мікроконтролера без надання власних реалізацій алокаторів та підсистем введення-виведення.

## 5. Еталонна конфігурація CMake для вбудованого проєкту

Нижче наведено фрагмент конфігураційного файлу `CMakeLists.txt`, який встановлює перелічені прапорці компілятора та лінкера для мікроконтролера ARM Cortex-M4:

```cmake
# Встановлення цільової архітектури та обмежень Freestanding
target_compile_options(firmware_target PRIVATE
    -mcpu=cortex-m4
    -mthumb
    -mfpu=fpv4-sp-d16
    -mfloat-abi=hard
    
    # Режим без операційної системи та вимкнення важких підсистем
    -ffreestanding
    -fno-exceptions
    -fno-rtti
    -fno-threadsafe-statics
    -fno-use-cxa-atexit
    -fno-unwind-tables
    -fno-asynchronous-unwind-tables
    
    # Оптимізація та секціонування для видалення мертвого коду
    -Os
    -ffunction-sections
    -fdata-sections
    -Wall
    -Wextra
    -Wpedantic
)

# Налаштування компонувальника
target_link_options(firmware_target PRIVATE
    -mcpu=cortex-m4
    -mthumb
    -mfpu=fpv4-sp-d16
    -mfloat-abi=hard
    -T${CMAKE_CURRENT_SOURCE_DIR}/linker_script.ld
    -Wl,--gc-sections
    -specs=nano.specs
    -specs=nosys.specs
    -Wl,-Map=${CMAKE_CURRENT_BINARY_DIR}/firmware.map
)
```
