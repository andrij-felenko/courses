# 📜 Еволюція C++ у вбудованих системах: від невдачі EC++ до нульових накладних витрат

Спроби пристосувати мову C++ до мікроконтролерів із жорстко обмеженими ресурсами пам'яті почалися майже одразу після її виходу за межі дослідницьких лабораторій Bell Labs. У 1990-х роках типовий мікроконтролер мав лише кілька кілобайтів постійної пам'яті (Flash/ROM) і кілька сотень байтів оперативної пам'яті (SRAM). У таких умовах стандартний компілятор C++ генерував двійковий код, який часто не поміщався на кристалі через таблиці розгортання винятків, метадані динамічної ідентифікації типів і бібліотечні залежності.

---

## 1. Створення консорціуму Embedded C++ (1996)

У 1995–1996 роках група провідних японських виробників напівпровідників та електроніки (серед яких були NEC, Hitachi, Fujitsu, Toshiba та Matsushita) за участі розробників компіляторів сформувала консорціум **Embedded C++ Technical Committee**. Метою групи було створення офіційного підмножинного діалекту мови C++, адаптованого для 8-, 16- та 32-бітних мікроконтролерів.

У 1996 році комітет опублікував специфікацію **Embedded C++ (EC++)**. З мови було механічно видалено всі можливості, які, на думку розробників специфікації, спричиняли роздування розміру двійкового файлу або недетермінований час виконання:

- **Механізм винятків (`try`, `catch`, `throw`)** — через накладні витрати на службові таблиці та бібліотеку часу виконання;
- **Динамічна ідентифікація типів (RTTI, `typeid`, `dynamic_cast`)** — через витрати Flash на дескриптори типів;
- **Множинне та віртуальне успадкування** — через складність розрахунку зміщень покажчиків і розростання таблиць `vtable`;
- **Шаблони (Templates)** — через побоювання дублювання коду при багаторазовому інстанціюванні;
- **Простори імен (`namespace`)** — аргументовано відсутністю потреби у великих модульних системах;
- **Нові оператори приведення типів (`static_cast`, `reinterpret_cast`, `const_cast`)** — повернуто класичний небезпечний C-style cast;
- **Стандартна бібліотека C++ (STL)** — замінена мініатюрною версією EC++ Library без потоків `iostream` і динамічних контейнерів.

```
┌─────────────────────────────────────────────────────────────┐
│                       Повний C++98                          │
│  ┌───────────────────────────────────────────────────────┐  │
│  │             Embedded C++ (EC++, 1996)                 │  │
│  │  • Класи, методи, інкапсуляція                        │  │
│  │  • Просте одиночне успадкування                       │  │
│  │  • Базовий віртуальний поліморфізм                    │  │
│  └───────────────────────────────────────────────────────┘  │
│  Вирізано: шаблони, винятки, RTTI, простори імен, STL,      │
│            множинне успадкування, нові cast-оператори       │
└─────────────────────────────────────────────────────────────┘
```

## 2. Чому EC++ зазнав нищівної поразки

Творці EC++ припустилися фундаментальної концептуальної помилки: видаливши з мови шаблони та простори імен разом із винятками, вони знищили саме ті інструменти, які забезпечували нульові накладні витрати абстракцій (Zero-Overhead Principle).

Творець мови C++ Б'ярн Страуструп (англ. *Bjarne Stroustrup*) виступив із різкою критикою EC++ у статті «Why Embedded C++ is not C++». Він вказав на кілька парадоксів цього діалекту:

1. **Втрата типобезпеки без шаблонів**. Без шаблонів розробники мікроконтролерних систем були змушені повертатися до покажчиків `void*` та макросів препроцесора `#define` для створення узагальнених структур даних (наприклад, кільцевих буферів або черг повідомлень). Це призводило до помилок часу виконання, які шаблони C++ виявляли на етапі компіляції.
2. **Шаблони як засіб економії пам'яті**. Узагальнене програмування дозволяє компілятору виконувати обчислення під час компіляції та інлайнити короткі функції (наприклад, бітові операції над регістрами периферії) у прямі машинні інструкції. Без шаблонів та інлайнінгу розробники EC++ отримували додаткові виклики функцій замість прямого доступу до портів введення-виведення.
3. **Фрагментація інструментів**. Розробка окремих компіляторів для діалекту EC++ коштувала дорого, а перенесення коду між звичайним C++ та EC++ вимагало постійного ручного переписування заголовків.

На початку 2000-х років розвиток технологій оптимізації в компіляторах GCC та Clang остаточно позбавив EC++ сенсу: компілятори навчилися видаляти невикористовуваний шаблонний код (`-ffunction-sections`, `-fdata-sections`, `--gc-sections`), а прапорці `-fno-exceptions` та `-fno-rtti` дозволили вимикати важкі динамічні механізми без спотворення синтаксису мови.

## 3. Стандарти безпеки: MISRA C++ та AUTOSAR

Замість створення урізаних діалектів індустрія вбудованих систем перейшла до створення стандартів дисципліни коду (англ. *coding guidelines*), які використовують повноцінну мову, але обмежують небезпечні або недетерміновані конструкції.

```
1996 ────────────► 2008 ────────────► 2014 ────────────► 2023
EC++               MISRA C++:2008     AUTOSAR C++14      MISRA C++:2023
(Урізаний діалект) (Правила C++03)    (Правила C++14)    (Спільний стандарт C++17)
```

### MISRA C++:2008
Організація **Motor Industry Software Reliability Association (MISRA)**, яка раніше створила надзвичайно успішний стандарт MISRA C для автомобільної електроніки, у 2008 році випустила **MISRA C++:2008**. 

Стандарт базувався на стандарті C++03 і встановлював суворі правила:
- Повна заборона динамічного виділення пам'яті (`malloc`, `free`, `new`, `delete`) після завершення фази ініціалізації системи;
- Суворі обмеження на використання винятків: заборона виходу винятків за межі потоків або обробників переривань;
- Вимога перевірки статичними аналізаторами коду всіх приведень типів та поліморфних ієрархій.

### AUTOSAR Adaptive Platform C++14
З появою систем автономного водіння, радарів і складних блоків керування двигуном консорціум **AUTOSAR (Automotive Open System Architecture)** розробив **Guidelines for the use of the C++14 language in critical and safety-related systems (AUTOSAR C++14)**. 

Цей стандарт зробив революційний крок: він легалізував сучасні можливості мови C++11 та C++14 у критичних системах:
- Семантику переміщення (`std::move`, rvalue references) для усунення копіювання даних без динамічної пам'яті;
- `constexpr` для перенесення важких розрахунків калібрувальних таблиць на етап компіляції;
- Розумні вказівники з фіксованими алокаторами;
- Прапорець `-fno-exceptions` для жорсткого реального часу, або використання локалізованих винятків із детермінованим часом обробки.

### MISRA C++:2023
У жовтні 2023 року організації MISRA та AUTOSAR об'єднали зусилля й опублікували спільний стандарт **MISRA C++:2023** (*Guidelines for the use of the C++17 language in critical and safety-related systems*) на базі стандарту ISO C++17 (ISO/IEC 14882:2017). Він замінив попередні настанови MISRA C++:2008 та інтегрував доробок AUTOSAR C++14. Стандарт адаптував для безпечно-критичних систем ключові можливості C++17: безпечні неволодіючі перегляди рядків (`std::string_view`), декомпозиційне зв'язування (*structured bindings*), вкладені простори імен (*nested namespaces*), вбудовані змінні (*inline variables*), вирази згортки (*fold expressions*) та інструкції `if constexpr` для спрощення узагальненого коду під час компіляції без накладних витрат у двійковому файлі, закріпивши статус сучасного C++ як основного інструменту високонадійних вбудованих систем.

## 4. Сучасний консенсус: мова на повну потужність із нульовими накладними витратами

Історія показала, що вбудовані системи потребують не «простішої мови», а суворішого контролю над згенерованим машинним кодом. 

Сучасні стандарти C++17, C++20 та C++23 остаточно реалізували бачення мови без накладних витрат для мікроконтролерів:

| Епоха | Підхід до вбудованого C++ | Результат |
|---|---|---|
| **1996 (EC++)** | Заборонити шаблони, RTTI, винятки на рівні синтаксису мови | Провал: втрата типобезпеки, повернення до небезпечних C-макросів |
| **2008 (MISRA C++:2008)** | Заборонити динамічну пам'ять, обмежити винятки через правила лінтерів | Стабільність ціною застарілих конструкцій C++03 |
| **2014–2020 (AUTOSAR / C++20)** | Використання `constexpr`, `concepts`, `std::span`, семантики переміщення | Повний контроль над двійковим кодом без витрат RAM і Flash |

Сучасний розробник прошивок не використовує спеціальний компілятор із підмножиною мови. Натомість використовується стандартний компілятор із прапорцями вимкнення важких підсистем часу виконання (`-fno-exceptions -fno-rtti`) та багатство статичних можливостей C++20/C++23 для створення надійного, швидкого та компактного двійкового коду.
