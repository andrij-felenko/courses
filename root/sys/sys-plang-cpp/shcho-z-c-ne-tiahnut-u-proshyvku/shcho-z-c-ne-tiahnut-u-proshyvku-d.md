Коли стандартна програма на C++ компілюється для звичайного комп'ютера з операційною системою, середовище виконання неявно надає їй гігабайти віртуальної пам'яті, підсистему динамічного завантаження бібліотек, захист сторінок пам'яті через апаратний диспетчер MMU та автоматичний диспетчер винятків. Проте у мікроконтролері (наприклад, кристалах ARM Cortex-M0/M3/M4, RISC-V чи ESP32) умови є принципово іншими: обсяг постійної пам'яті програм (Flash) обмежений кількома сотнями кілобайтів (від 16 до 512 КБ), оперативна пам'ять (SRAM) вимірюється десятками кілобайтів (від 2 до 128 КБ), операційна система відсутня, а кожна мікросекунда затримки в контурі керування електродвигуном або обробці переривання сенсора може призвести до фізичної аварії обладнання.

Якщо перенести в таку систему класичні ідіоми C++ без свідомого контролю за згенерованим двійковим кодом, прошивка миттєво втратить стабільність або взагалі не поміститься у кристалі. Поодинокий виклик ключового слова `throw` підтягне в образ десятки кілобайтів службових таблиць розгортання стек-фреймів та виділить пам'ять через прихований виклик системного алокатора; оператор `dynamic_cast` запустить пошук по дереву типів замість прямого звернення до регістрів; динамічна купа через кілька годин роботи фрагментує пам'ять до повної відмови виділити масив у 64 байти, а віртуальні таблиці збільшать витрати SRAM та сповільнять конвеєр команд процесора.

Через це у вбудованому програмуванні на C++ виробився суворий інженерний консенсус: чотири базові механізми мови або повністю вимикають на рівні прапорців компілятора, або замінюють детермінованими статичними альтернативами з нульовими накладними витратами.

## 1. Чотири апаратні бар'єри вбудованих систем

Розробка прошивок для середовища без операційної системи (Freestanding Environment) підпорядкована чотирьом фізичним та системним обмеженням, які докорінно відрізняють мікроконтролер від настільного процесора.

1. **Фіксований та обмежений обсяг Flash і SRAM**. У мікроконтролері немає файлу підкачки (Swap) чи можливості динамічно підвантажити відсутній модуль. Кожен байт службових метаданих у пам'яті програм (Flash) зменшує місце для алгоритмів керування, а кожен зайвий байт у пам'яті даних (SRAM) наближає переповнення стеку (Stack Overflow) до зіткнення з глобальними даними.
2. **Жорсткий реальний час (Hard Real-Time)**. Контури стабілізації безпілотних апаратів, цифрові фільтри сигналів та драйвери переривань вимагають гарантованого виконання коду за фіксовану кількість тактів тактового генератора. Властивість коду завжди виконуватися за передбачуваний, заздалегідь відомий час називається **детермінізмом** (від лат. *determinare* — обмежувати, визначати, окреслювати межі). Будь-яка непередбачувана затримка (джитер) через пошук у списках чи сканування таблиць порушує роботу контуру керування.
3. **Відсутність апаратного блоку керування пам'яттю (No MMU)**. У більшості мікроконтролерів немає віртуальної адресації: всі покажчики вказують на фізичні адреси пам'яті. Це унеможливлює дефрагментацію пам'яті на рівні сторінок операційної системи.
4. **Відсутність точки виходу з програми**. Прошивка запускається після сигналу апаратного скидання (Reset) і працює в нескінченному циклі до зняття напруги живлення. Тут не існує повернення з функції `main()`, а отже класичні механізми завершення процесу та виклику деструкторів глобальних об'єктів втрачають сенс.

```
┌─────────────────────────────────────────────────────────────┐
│                 Фізична карта мікроконтролера               │
├──────────────────────────────┬──────────────────────────────┤
│ Flash / ROM (16 КБ – 512 КБ) │ SRAM (2 КБ – 128 КБ)         │
│ • Вектор переривань          │ • Стек викликів (SP)         │
│ • Код програми (.text)       │ • Статичні змінні (.data)    │
│ • Константи (.rodata)        │ • Нульові змінні (.bss)      │
│ • Конструктори (.init_array) │ • Вільна пам'ять (Купа/Пул)  │
└──────────────────────────────┴──────────────────────────────┘
```

## 2. Механізм винятків (Exceptions) та прапорець `-fno-exceptions`

У стандартному C++ для обробки аварійних ситуацій використовується конструкція з трьох ключових слів: `try`, `catch` та `throw`. Сам термін **виняток** (англ. *exception*, від лат. *exceptio* — вилучення, виняток, що походить від дієслова *excipere* — виймати, виключати) позначає подію, яка порушує звичайний хід виконання алгоритму.

У настільних операційних системах домінує таблична модель обробки винятків із нульовою вартістю на звичайному шляху виконання (Zero-Cost Exceptions за специфікаціями Itanium C++ ABI та ARM Exception Handling ABI). Якщо виняток не генерується, процесор не витрачає додаткових тактів на його перевірку. Проте ціною такої нульової вартості в нормальному режимі стають значні накладні витрати на обсяг постійної пам'яті та повна втрата детермінізму при виникненні помилки.

```
┌─────────────────────────────────────────────────────────────┐
│                 Машинний код функції (.text)                │
└──────────────────────────────┬──────────────────────────────┘
                               │ Збій: виклик throw
                               ▼
┌─────────────────────────────────────────────────────────────┐
│         Таблиці розгортання стеку (.ARM.exidx / .ARM.extab) │
│   • Пошук адреси функції за поточним лічильником PC         │
│   • Читання інструкцій відновлення регістрів зі стеку       │
│   • Пошук вказівника на обробник Landing Pad                │
└──────────────────────────────┬──────────────────────────────┘
                               │ Робота Personality Routine
                               ▼
┌─────────────────────────────────────────────────────────────┐
│              Виклик деструкторів на кожному фреймі          │
│   • Відновлення стану стек-фрейма за фреймом (500-5000 такт)│
│   • Перехід у блок catch або виклик std::terminate()        │
└──────────────────────────────┬──────────────────────────────┘
```

### Як влаштоване табличне розгортання стеку під капотом
Коли компілятор транслює функцію з підтримкою винятків, він супроводжує кожну машинну інструкцію записом у спеціальних секціях пам'яті Flash — `.ARM.exidx` (індекс функцій) та `.ARM.extab` (таблиця інструкцій розгортання). Процес відновлення попереднього стану програми називається **розгортанням стеку** (англ. *stack unwinding*, від префікса *un-* — назад, скасування та давньоангл. *windan* — вити, скручувати, розплутувати).

Секція `.ARM.exidx` містить впорядковані пари 32-бітних слів:
- Перше слово кодує відносне зміщення адреси початку функції від поточної позиції у Flash;
- Друге слово містить або компактну 3-байтну інструкцію розгортання регістрів (Compact Model), або покажчик на розширений запис у секції `.ARM.extab`.

Під час виконання оператора `throw` процесор проходить складний багатоетапний ланцюжок:
1. **Виділення пам'яті під об'єкт винятку**. Викликається системна функція ABI `__cxa_allocate_exception()`. Якщо статичний резервний пул вичерпано, ця функція звертається безпосередньо до системного алокатора `malloc()`. У вбудованій системі з вичерпаною пам'яттю спроба згенерувати виняток про брак пам'яті (`std::bad_alloc`) сама призводить до фатального краху.
2. **Запуск функції аналізу стек-фреймів (Personality Routine)**. Викликається підпрограма `__gxx_personality_v0` (або `__aeabi_unwind_cpp_pr0` / `pr1` на архітектурі ARM). Вона зчитує поточне значення лічильника інструкцій процесора (`PC` — Program Counter) та виконує двійковий пошук у таблиці `.ARM.exidx` у Flash-пам'яті, щоб знайти межі поточної функції.
3. **Покрокове розгортання фреймів**. Знайшовши дескриптор функції, Personality Routine декодує байт-код розгортання, який вказує, які саме регістри процесора збережені на стеку (`r4-r11`) і як змістити покажчик стеку `SP`. Далі викликаються деструктори всіх локальних об'єктів, створених у цьому блоці до моменту викидання винятку (так звані *Landing Pads*).
4. **Пошук відповідного блоку `catch`**. Якщо поточна функція не містить відповідного обробника, алгоритм повторює процедуру для функції, яка її викликала, піднімаючись угору по стеку викликів аж до точки входу.

![Накладні витрати розгортання винятків](/root/sys/sys-plang-cpp/shcho-z-c-ne-tiahnut-u-proshyvku/img/exceptions-unwind-overhead.svg)
*Накладні витрати розгортання винятків через секції розгортання стеку та пошук обробника проти повернення значень результату.*

### Чому винятки заборонені в прошивках:
- **Роздування Flash на 15–30%**. Таблиці розгортання стек-фреймів та код Landing Pads дублюють логіку викликів для кожної скомпільованої функції. У проєкті на 100 КБ коду таблиці винятків можуть займати від 20 до 35 КБ Flash-пам'яті.
- **Повна втрата детермінізму часу**. Час розгортання стеку залежить від глибини вкладеності викликів, кількості локальних об'єктів та структури таблиць у Flash. Обробка помилки через `throw` займає від 500 до 5000 тактів процесора проти 2–4 тактів при поверненні коду через регістр. Якщо виняток виникає всередині швидкісного переривання (ISR), система гарантовано пропустить наступні апаратні події.
- **Приховане використання купи**. Розміщення об'єктів винятків через динамічну пам'ять суперечить вимогам надійності та безпеки.

### Інженерне рішення: прапорець `-fno-exceptions` та `std::expected`
Усі прошивки мікроконтролерів компілюються з прапорцем `-fno-exceptions`. Детальний опис впливу цього прапорця на таблиці лінкера наведено у [довіднику прапорців компілятора](root:sys-plang-cpp/shcho-z-c-ne-tiahnut-u-proshyvku/api-freestanding-compiler-flags.md).

Замість винятків у сучасній мові C++ використовується функціональний підхід на базі типів-значень. Починаючи зі стандарту C++23, у мову введено шаблонний тип `std::expected<T, E>`, який повертає або валідне значення типу `T`, або код помилки типу `E` без жодного виділення пам'яті на купі та без таблиць розгортання.

Крім прямої перевірки оператором `if`, `std::expected` підтримує функціональні монадичні операції (`.and_then()`, `.transform()`, `.or_else()`), що дозволяє організувати послідовну обробку апаратних пакетів у вигляді лінійного конвеєра без вкладених розгалужень та без винятків:

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>

/* Коди помилок операції */
typedef enum {
    ADC_SUCCESS = 0,
    ADC_ERR_TIMEOUT,
    ADC_ERR_OVERVOLTAGE
} AdcStatus;

/* Повернення результату через покажчик та код статусу */
AdcStatus adc_read_voltage(uint32_t channel, uint16_t* out_mv) {
    if (channel > 15) {
        return ADC_ERR_TIMEOUT;
    }
    /* Імітація зчитування апаратного регістра */
    *out_mv = 3300;
    return ADC_SUCCESS;
}
```
```cpp
#include <cstdint>
#include <expected>

/* Типобезпечні помилки АЦП */
enum class AdcError : uint8_t {
    InvalidChannel,
    Timeout,
    Overvoltage
};

/* Обробка помилки через значення без динамічної пам'яті та винятків */
[[nodiscard]] constexpr std::expected<uint16_t, AdcError> 
adc_read_voltage(uint32_t channel) noexcept {
    if (channel > 15) {
        return std::unexpected(AdcError::InvalidChannel);
    }
    /* Результат повертається безпосередньо через регістр процесора R0 */
    return static_cast<uint16_t>(3300);
}

/* Монадичний ланцюжок обробки без винятків */
[[nodiscard]] constexpr std::expected<float, AdcError>
get_calibrated_voltage(uint32_t channel) noexcept {
    return adc_read_voltage(channel)
        .transform([](uint16_t raw_mv) noexcept {
            return static_cast<float>(raw_mv) * 0.001f;
        });
}
```

## 3. Динамічна ідентифікація типів (RTTI) та прапорець `-fno-rtti`

У стандартному C++ для безпечного приведення типів вниз по ієрархії спадкування використовується оператор `dynamic_cast`, а для отримання імені типу під час виконання — оператор `typeid`. Сукупність цих механізмів називається **динамічною ідентифікацією типів** (англ. *Run-Time Type Information, RTTI*, де *інформація* походить від лат. *informatio* — виклад, роз'яснення, надання форми).

Для підтримки RTTI компілятор розміщує в секції констант Flash-пам'яті (`.rodata`) спеціальні дескриптори типу `std::type_info` для кожного поліморфного класу (класу, що має хоча б один віртуальний метод).

```
┌─────────────────────────────────────────────────────────────┐
│                 Flash-пам'ять (.rodata)                     │
│  ┌───────────────────────────────────────────────────────┐  │
│  │             Таблиця vtable класу Sensor               │  │
│  │  [-1]: typeinfo pointer ──────────┐                   │  │
│  │  [ 0]: &Sensor::read_sample       │                   │  │
│  └───────────────────────────────────┼───────────────────┘  │
│                                      ▼                      │
│  ┌───────────────────────────────────────────────────────┐  │
│  │            Дескриптор std::type_info                  │  │
│  │  • Манглений рядок: "6Sensor" (Flash .rodata)         │  │
│  │  • Покажчики на базові класи та зміщення для cast     │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

Залежно від складності ієрархії успадкування компілятор генерує один із трьох різновидів дескрипторів:
- `__fundamental_type_info` — для базових числових типів;
- `__si_class_type_info` — для класів з одиночним публічним невіртуальним успадкуванням;
- `__vmi_class_type_info` (Virtual/Multiple Inheritance) — для складних ієрархій із масивом прапорців та зміщень базових класів.

### Чому RTTI неприйнятний у прошивках:
1. **Витрати Flash на дескриптори та рядки назв типів**. Для кожного класу у Flash записується його повна манглена назва та граф успадкування. Якщо прошивка містить сотні класів датчиків, протоколів та пакетів даних, ці службові структури можуть займати від 5 до 15 КБ Flash, ніяк не впливаючи на корисну логіку роботи пристрою. Крім того, наявність посилань на назви типів заважає компонувальнику видаляти невикористовувані класи.
2. **Недетермінізм оператора `dynamic_cast`**. При спробі виконати `dynamic_cast<Target*>(base_ptr)` середовище виконання запускає рекурсивний обхід дерева типів, зчитуючи зміщення `offset_to_top` (розташоване у слоті `vtable[-2]`) та порівнюючи покажчики на дескриптори `type_info`. Час виконання такого приведення залежить від глибини ієрархії класів та розташування класу в дереві, що неприпустимо для коду реального часу.

### Інженерне рішення: прапорець `-fno-rtti` та статична диспетчеризація
Усі вбудовані проєкти збираються з прапорцем `-fno-rtti`. Якщо програма вимагає збереження одного з кількох типів даних без використання динамічного поліморфізму, застосовується типобезпечне теговане об'єднання `std::variant` у парі з функцією `std::visit` або шаблонні концепції (C++20 Concepts).

## 4. Динамічна купа (Dynamic Heap) та відмова від загальних алокаторів

У прикладних програмах пам'ять виділяється через оператор `new` або функцію `malloc()`. Сама область пам'яті, з якої виділяються блоки довільного розміру, традиційно називається **купою** (англ. *heap*, від прагерманського **haupaz* — купа, насип, нагромадження однакових предметів). 

У мікроконтролері з 32 КБ оперативної пам'яті використання універсального алокатора загального призначення (`dlmalloc` або стандартна купа `newlib` через системний виклик `_sbrk`) є найчастішою причиною відмов обладнання через прогресуюче руйнування цілісності адресного простору.

Процес розбиття неперервної області пам'яті на дрібні ізольовані проміжки називається **фрагментацією** (від лат. *fragmentum* — уламок, обрізок, що походить від дієслова *frangere* — ламати, розбивати на шматки).

```
Початковий стан SRAM:
┌─────────────────────────────────────────────────────────────┐
│ [   Вільний суцільний блок пам'яті: 1024 байти            ] │
└─────────────────────────────────────────────────────────────┘

Після десятків виділень та звільнень різних розмірів (Фрагментація):
┌──────┬─────┬──────┬──────┬──────┬─────┬──────┬──────────────┐
│Зайнято│Дірка│Зайнято│Дірка │Зайнято│Дірка│Зайнято│Дірка 64 Б    │
│128 Б │48 Б │256 Б │96 Б  │64 Б  │32 Б │128 Б │              │
└──────┴─────┴──────┴──────┴──────┴─────┴──────┴──────────────┘
Сумарно вільно: 240 байтів, але запит malloc(100 байтів) зазнає НЕВДАЧІ (NULL)!
```

![Фрагментація динамічної купи проти статичного блокового пулу](/root/sys/sys-plang-cpp/shcho-z-c-ne-tiahnut-u-proshyvku/img/heap-fragmentation-baremetal.svg)
*Прогресуюча фрагментація мікроконтролерної оперативної пам'яті при динамічному виділенні та детермінована робота блокового пулу.*

### Чому динамічна купа руйнує стабільність прошивки:
1. **Зовнішня фрагментація пам'яті**. Оскільки в мікроконтролері немає віртуальної пам'яті (MMU), алокатор не може перемістити зайняті блоки, щоб об'єднати вільні проміжки. У результаті пристрій, який успішно працював кілька діб, раптово падає через повернення `nullptr` з алокатора: у пам'яті є сумарно 8 КБ вільного місця, але жоден суцільний фрагмент не перевищує 64 байти.
2. **Недетермінований час виділення пам'яті**. Пошук вільного блоку потрібного розміру в двозв'язних списках вільних блоків (алгоритми First-Fit, Best-Fit) вимагає перебору пам'яті. Час виконання `malloc` коливається від десятків до тисяч тактів.
3. **Накладні витрати службових заголовків**. Кожен виділений блок пам'яті потребує службового заголовка (від 4 до 16 байтів) для збереження розміру блоку та прапорців зайнятості. Для пакета розміром 16 байтів оверхед пам'яті може складати 50–100%.

### Детерміновані альтернативи купі в прошивках

Замість загальної динамічної купи розробники прошивок використовують чотири повністю детерміновані моделі керування пам'яттю:

#### 1. Статичне виділення та фіксовані масиви
Об'єкти створюються як глобальні або статичні екземпляри, розміщуючись у секціях `.bss` (неініціалізовані дані) або `.data`. Усі буфери мають фіксовану довжину `std::array<T, N>` або `std::span<T>`, що дозволяє лінкеру розрахувати точне споживання SRAM ще під час компіляції.

#### 2. Фіксований блоковий пул (Fixed-Size Pool Allocator)
Пам'ять розділяється на однакові за розміром слоти (наприклад, по 128 байтів). Вільні слоти організовуються в інваріантний список (Intrusive Free-List), де покажчик на наступний вільний блок зберігається безпосередньо всередині самого вільного блоку пам'яті, що не вимагає жодного додаткового байта RAM. Виділення та звільнення слота виконуються за гарантований час `O(1)` (рівно 3–4 такти процесора: вилучення елемента з голови списку), а зовнішня фрагментація математично неможлива.

Нижче наведено порівняння реалізації блокового пулу мовами C та C++:

:::tabs
```c
#include <stdint.h>
#include <stddef.h>
#include <stdbool.h>

#define BLOCK_SIZE  64
#define BLOCK_COUNT 16

typedef struct BlockNode {
    struct BlockNode* next;
} BlockNode;

typedef struct {
    uint8_t storage[BLOCK_COUNT * BLOCK_SIZE];
    BlockNode* free_head;
} MemoryPoolC;

void pool_init_c(MemoryPoolC* pool) {
    pool->free_head = NULL;
    for (size_t i = 0; i < BLOCK_COUNT; ++i) {
        BlockNode* node = (BlockNode*)&pool->storage[i * BLOCK_SIZE];
        node->next = pool->free_head;
        pool->free_head = node;
    }
}

void* pool_allocate_c(MemoryPoolC* pool) {
    if (pool->free_head == NULL) return NULL;
    BlockNode* node = pool->free_head;
    pool->free_head = node->next;
    return (void*)node;
}

void pool_deallocate_c(MemoryPoolC* pool, void* ptr) {
    if (ptr == NULL) return;
    BlockNode* node = (BlockNode*)ptr;
    node->next = pool->free_head;
    pool->free_head = node;
}
```
```cpp
#include <cstdint>
#include <cstddef>
#include <array>
#include <new>

template <typename T, size_t Capacity>
class StaticObjectPool {
public:
    constexpr StaticObjectPool() noexcept {
        for (size_t i = 0; i < Capacity; ++i) {
            auto* node = reinterpret_cast<Node*>(&m_storage[i]);
            node->next = m_free_head;
            m_free_head = node;
        }
    }

    template <typename... Args>
    [[nodiscard]] T* create(Args&&... args) noexcept {
        if (m_free_head == nullptr) return nullptr;
        Node* node = m_free_head;
        m_free_head = node->next;
        return ::new (static_cast<void*>(node)) T(std::forward<Args>(args)...);
    }

    void destroy(T* obj) noexcept {
        if (obj == nullptr) return;
        obj->~T();
        auto* node = reinterpret_cast<Node*>(obj);
        node->next = m_free_head;
        m_free_head = node;
    }

private:
    union Node {
        Node* next;
        alignas(T) std::byte storage[sizeof(T)];
    };

    std::array<Node, Capacity> m_storage{};
    Node* m_free_head{nullptr};
};
```

#### 3. Монотонна арена (Linear / Bump Allocator)
Складається зі статичного масиву байтів та одного покажчика зсуву. Виділення пам'яті полягає у простому збільшенні покажчика на потрібну кількість байтів (`offset += size`). Пам'ять ніколи не звільняється по шматочках: вся арена повністю скидається в нуль (`offset = 0`) після завершення фази обробки пакету або транзакції.

#### 4. Розміщувальний оператор `new` (Placement New)
Дозволяє викликати конструктор C++ класу на заздалегідь виділеному статичному буфері пам'яті без звернення до алокатора:

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

/* Фіксований буфер пам'яті під структуру */
typedef struct {
    uint32_t sensor_id;
    float last_value;
} SensorDataC;

static uint8_t sensor_storage[sizeof(SensorDataC)];

/* Ініціалізація структури у статичній пам'яті */
SensorDataC* create_sensor_c(uint32_t id) {
    SensorDataC* s = (SensorDataC*)sensor_storage;
    s->sensor_id = id;
    s->last_value = 0.0f;
    return s;
}
```
```cpp
#include <cstdint>
#include <new> // Необхідний для розміщувального new

class SensorNode {
public:
    explicit constexpr SensorNode(uint32_t id) noexcept 
        : m_id(id), m_value(0.0f) {}

    [[nodiscard]] float read() const noexcept { return m_value; }

private:
    uint32_t m_id;
    float m_value;
};

/* Буфер потрібного розміру та вирівнювання у секції .bss */

/* Конструювання об'єкта через placement new без динамічної купи */
```

## 5. Віртуальні функції та vtable: прихована ціна динамічного поліморфізму

Класичний динамічний поліморфізм у C++ реалізується через віртуальні функції (`virtual`). Кожен клас, що містить віртуальні методи, отримує у Flash-пам'яті статичну **таблицю віртуальних методів** (англ. *virtual method table, vtable*, від лат. *virtualis* — можливий, дієвий, що походить від *virtus* — сила, спроможність). Кожен об'єкт цього класу неявно містить перший прихований член — покажчик на цю таблицю (`vptr`).

Звернення до методу через покажчик на базовий клас вимагає додаткового рівня адресації, що зветься **індирекцією** (англ. *indirection*, від лат. *indirectus* — непрямий, обхідний).

```
┌─────────────────────────────────────────────────────────────┐
│                 Об'єкт у пам'яті SRAM                       │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ offset 0: vptr ────────────────────────┐              │  │
│  │ offset 4: int sensor_id;               │              │  │
│  │ offset 8: float calibration_val;       │              │  │
│  └────────────────────────────────────────┼──────────────┘  │
└───────────────────────────────────────────┼─────────────────┘
                                            ▼
┌─────────────────────────────────────────────────────────────┐
│                 Таблиця vtable у Flash (.rodata)            │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ [0]: &UartDriver::send_byte                           │  │
│  │ [1]: &UartDriver::receive_byte                        │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

![Розкладка в пам'яті та механізм виклику](/root/sys/sys-plang-cpp/shcho-z-c-ne-tiahnut-u-proshyvku/img/vtable-vs-crtp-memory.svg)
*Структура об'єкта в оперативній пам'яті та спосіб адресації коду для віртуальних методів і CRTP.*

### Чому віртуальні виклики обмежують у прошивках:
1. **Витрати SRAM на покажчик `vptr` (+4 або +8 байтів)**. Кожен екземпляр класу збільшується на розмір адресного покажчика. Якщо у програмі створено 100 дрібних об'єктів (наприклад, дескрипторів пакетів черги CAN-шини розміром по 8 байтів), покажчики `vptr` додадуть 400 байтів зайвої пам'яті SRAM (+50% оверхеду).
2. **Непрямі переходи та скидання конвеєра**. На процесорах архітектури ARM Cortex-M виклик віртуального методу транслюється в інструкцію `BLX Rm` (Branch with Link and Exchange to Register). Процесор не може передбачити цільову адресу переходу до моменту зчитування регістра, що викликає затримку конвеєра інструкцій (Pipeline Stall) на 2–4 такти.
3. **Блокування інлайнінгу (Inlining Barrier)**. Це найважчий недолік: компілятор не може підставити тіло віртуальної функції в місце виклику, оскільки остаточна адреса методу визначається лише під час виконання. Втрачається можливість видалення мертвого коду, поширення констант (Constant Propagation) та оптимізації регістрів.

### Статичний поліморфізм через CRTP
Для збереження єдиного узагальненого інтерфейсу без втрати продуктивності у прошивках використовують **статичний поліморфізм** (від давньогрецького *polys* — численний та *morphe* — форма) за шаблоном CRTP (Curiously Recurring Template Pattern).

Детальний приклад реалізації повноцінного апаратного драйвера периферії на базі CRTP наведено у практичній вставці [драйвер периферії без купи й vtable](root:sys-plang-cpp/shcho-z-c-ne-tiahnut-u-proshyvku/proj-crtp-baremetal-driver.md).

```cpp
/* Базовий інтерфейс без віртуальних методів */
template <typename Derived>
class GpioDriver {
public:
    void set_high() noexcept {
        /* Приведення типів виконується на етапі компіляції */
        static_cast<Derived*>(this)->set_high_impl();
    }
};

/* Конкретна апаратна реалізація */
class Stm32GpioPin : public GpioDriver<Stm32GpioPin> {
public:
    explicit constexpr Stm32GpioPin(volatile uint32_t* bsrr, uint32_t pin_mask) noexcept
        : m_bsrr(bsrr), m_mask(pin_mask) {}

    /* Метод повністю інлайниться в пряму інструкцію STR */
    void set_high_impl() noexcept {
        *m_bsrr = m_mask;
    }

private:
    volatile uint32_t* m_bsrr;
    uint32_t m_mask;
};
```

При виклику `pin.set_high()` компілятор повністю ліквідує абстракцію та генерує одну пряму інструкцію запису в пам'ять `STR R1, [R0, #0]`. Розмір об'єкта в SRAM не містить жодного `vptr`, а час виконання скорочується до 1 такту.

### Динамічний поліморфізм без купи: `std::variant` та `std::visit`
Якщо програма вимагає збереження колекції різнорідних об'єктів (наприклад, масиву датчиків різного типу), закритий набір типів можна об'єднати за допомогою `std::variant`. У цьому випадку компілятор створює фіксовану таблицю переходів або простий оператор `switch` за цілочисельним дискримінатором, уникаючи покажчиків `vptr` та динамічної пам'яті:

```cpp
#include <variant>
#include <array>

struct TemperatureSensor {
    [[nodiscard]] float read() const noexcept { return 25.4f; }
};

struct PressureSensor {
    [[nodiscard]] float read() const noexcept { return 1013.25f; }
};

using SensorVariant = std::variant<TemperatureSensor, PressureSensor>;

float sample_sensor(const SensorVariant& s) noexcept {
    return std::visit([](const auto& sensor) noexcept {
        return sensor.read();
    }, s);
}
```

## 6. Приховані пастки Freestanding C++: статична ініціалізація та atexit

Окрім чотирьох основних тем, стандартна мова C++ містить кілька прихованих механізмів, які можуть несподівано порушити роботу мікроконтролера.

### Потокобезпечна ініціалізація локальних статичних змінних
Згідно зі стандартом C++11, якщо функція містить локальну статичну змінну:
```cpp
void process_sample() {
    static FilterInstance filter; // Потокобезпечна ініціалізація Меєрса
    filter.apply();
}
```
компілятор зобов'язаний гарантувати, що змінна буде ініціалізована рівно один раз, навіть якщо функцію одночасно викликають кілька потоків. Для цього компілятор вставляє виклики `__cxa_guard_acquire()` та `__cxa_guard_release()`. 

У системі без операційної системи ці виклики створюють невирішені символи лінкера. Щоб прибрати ці приховані блокування, проєкт обов'язково збирають із прапорцем `-fno-threadsafe-statics`.

### Реєстрація деструкторів `__cxa_atexit`
Коли у програмі створюється глобальний об'єкт із деструктором:
```cpp
GlobalTelemetryLogger g_logger; // Має нетривіальний деструктор ~GlobalTelemetryLogger()
```
компілятор генерує код, який під час старту програми викликає функцію `__cxa_atexit()` для реєстрації покажчика на деструктор у системній таблиці завершення. 

Оскільки мікроконтролер ніколи не виходить із робочого циклу, накопичення адрес деструкторів у таблиці є марною тратою пам'яті. Прапорець `-fno-use-cxa-atexit` повністю вимикає генерацію викликів реєстрації деструкторів.

### Порядок виклику глобальних конструкторів (.init_array)
Усі конструктори глобальних об'єктів C++ записуються компонувальником у спеціальну секцію Flash-пам'яті `.init_array`. Стартап-код мікроконтролера (файл `startup.cpp` або `startup.s`) перед переходом до функції `main()` зобов'язаний у циклі викликати кожну функцію з цієї таблиці.

```
Порядок запуску мікроконтролера після апаратного скидання:
1. Завантаження покажчика стеку SP з вектора переривань (адреса 0x00000000)
2. Перехід на Reset_Handler (адреса 0x00000004)
3. Копіювання секції .data з Flash (LMA) у SRAM (VMA)
4. Занулення секції .bss у SRAM
5. Послідовний виклик функцій із таблиці .init_array (глобальні конструктори)
6. Перехід до функції main()
```

```cpp
/* Фрагмент виклику глобальних конструкторів у стартап-коді */
extern void (*__init_array_start[])(void) __attribute__((weak));
extern void (*__init_array_end[])(void) __attribute__((weak));

void SystemInit_Cpp() {
    const size_t count = __init_array_end - __init_array_start;
    for (size_t i = 0; i < count; ++i) {
        __init_array_start[i](); // Виклик глобального конструктора
    }
}
```

Однак покладання на глобальні конструктори небезпечне через проблему **невизначеного порядку ініціалізації** (Static Initialization Order Fiasco): якщо об'єкт `UART` ініціалізується в одному файлі, а об'єкт `Logger`, який намагається відправити повідомлення в цей `UART`, — в іншому, порядок їх конструювання стандартом не гарантується. Тому у прошивках глобальні об'єкти зазвичай мають тривіальні конструктори або конструюються константно (`constexpr`), а запуск периферії здійснюється через явний метод `init()`.

## 7. Від штучних заборон до сучасної дисципліни нульових витрат

Історія розвитку мови C++ у вбудованих системах пройшла шлях від невдалих спроб заборонити ключові можливості мови до створення системи нульових накладних витрат.

У 1996 році консорціум виробників мікроконтролерів спробував створити спрощений діалект Embedded C++ (EC++), заборонивши не лише винятки та RTTI, а й шаблони та простори імен. Про те, чому ця спроба зазнала нищівної поразки і як індустрія перейшла до стандартів MISRA C++ та AUTOSAR C++, детально описано в історичній вставці [еволюція C++ у вбудованих системах](root:sys-plang-cpp/shcho-z-c-ne-tiahnut-u-proshyvku/hist-embedded-cpp-evolution.md).

Сучасні стандарти C++17, C++20 та C++23 довели, що для створення високонадійних, швидких та компактних прошивок не потрібно спотворювати мову. 

Поєднуючи прапорці вимкнення важких підсистем часу виконання (`-fno-exceptions -fno-rtti -fno-threadsafe-statics`) із багатим арсеналом сучасних можливостей — `constexpr` обчисленнями, концепціями, `std::span`, `std::expected` та статичним поліморфізмом CRTP — розробник отримує абсолютний контроль над кожним байтом пам'яті та кожною машинною інструкцією процесора, зберігаючи найвищий рівень архітектурної виразності.
