# 📋 Довідник API: std::async та std::packaged_task

Цей довідник містить повну специфікацію публічного інтерфейсу узагальненої функції `std::async`, шаблону класу `std::packaged_task`, пов'язаних типів політик запуску, переліків помилок, гарантій потокобезпеки, правил володіння пам'яттю та вимог до життєвого циклу об'єктів у стандартній бібліотеці C++ (стандарти C++11, C++14, C++17, C++20, C++23).

---

## 1. Функція `std::async`

Узагальнена функція `std::async` слугує високорівневим інтерфейсом для асинхронного виконання обчислень. Вона зв'язує переданий callable-об'єкт із внутрішнім спільним станом (Shared State) та негайно повертає об'єкт `std::future`, через який споживач згодом зчитує результат або перехоплює винятки.

### Сигнатури та налаштування (Header `<future>`)

Стандарт надає два основні перевантаження шаблону функції `std::async`:

```cpp
// (1) Запуск із системною політикою за замовчуванням (std::launch::async | std::launch::deferred)
template< class Function, class... Args >
[[nodiscard]] std::future<std::invoke_result_t<std::decay_t<Function>, std::decay_t<Args>...>>
async( Function&& f, Args&&... args );

// (2) Явне вказування політики виконання через бітову маску policy
template< class Function, class... Args >
[[nodiscard]] std::future<std::invoke_result_t<std::decay_t<Function>, std::decay_t<Args>...>>
async( std::launch policy, Function&& f, Args&&... args );
```

Починаючи зі стандарту C++20, функція маркується атрибутом `[[nodiscard]]`. Це зроблено для того, щоб запобігти випадковим помилкам розробників, коли повернений об'єкт `std::future` не присвоюється жодній змінній і нищиться у тій самій інструкції, викликаючи синхронне блокування викликаючого потоку у деструкторі rvalue-об'єкта.

### Деталізація параметрів виклику

Перший параметр `policy` задає політику запуску задачі. Він приймає значення зі спеціалізованого переліку-маски `std::launch`.

Другий параметр `f` є універсальним посиланням (forwarding reference) на callable-об'єкт. Ним може виступати звичайна функція, лямбда-вираз, функціональний об'єкт (функтор), результат виклику `std::bind` або вказівник на метод класу.

Параметри `args...` представляють варіативний пакет аргументів, які передаються у функцію `f`. Усі аргументи копіюються або переміщуються у внутрішнє сховище спільного стану при створенні задачі. Оскільки аргументи розгортаються за допомогою `std::decay_t`, масиви перетворюються на вказівники, а посилання знімаються. Якщо розробник бажає передати аргумент за посиланням у фоновий потік, слід використовувати обгортку `std::ref` або `std::cref`.

### Політики виконання `std::launch`

Тип `std::launch` є переліком типу бітової маски (bitmask type / scoped enum), оголошеним у просторі імен `std`:

```cpp
enum class launch : unsigned int {
    async = 1,          // Обов'язкове створення або використання фонового потоку
    deferred = 2        // Відкладене ліниве виконання у потоці викликача
};
```

- **`std::launch::async`**: Гарантує, що обчислення функції `f` буде запущено в окремому потоці виконання паралельно з викликаючим потоком. Операційна система або системне середовище виконання (runtime) створює новий потік чи виділяє його із системного пулу.
- **`std::launch::deferred`**: Абсолютно виключає створення нового потоку. Виконання функції `f` відкладається до моменту, коли на повернутому об'єкті `std::future` буде первинно викликано метод `.get()` або `.wait()`. Виконання відбувається повністю синхронно всередині того потоку, який викликав `.get()`. Якщо методи `.get()` чи `.wait()` не викликаються протягом усього життя програми, функція `f` не буде виконана ніколи.
- **`std::launch::async | std::launch::deferred`** (За замовчуванням): Залишає остаточний вибір політики за середовищем виконання. Рантайм оцінює поточне завантаження процесорних ядер, доступність пам'яті та ліміти потоків ОС. Якщо ресурси є — вибирається `async`, якщо система перевантажена — вибирається `deferred`.

### Винятки та гарантії помилок

Виклик `std::async` може кидати такі системні винятки:

- **`std::system_error`**: Кидається у випадку, коли вказано політику `std::launch::async` (або вибрано її за замовчуванням), але операційна система не може створити новий потік виконання через перевищення ліміту процесів або вичерпання системних ресурсів. Код помилки у цьому разі відповідає `std::errc::resource_unavailable_try_again`.
- **`std::bad_alloc`**: Кидається, якщо системному менеджеру пам'яті не вдалося виділити динамічний блок пам'яті під внутрішній спільний стан (Shared State).

## 2. Шаблон класу `std::packaged_task`

`std::packaged_task` є універсальною move-only обгорткою для callable-об'єктів, яка відокремлює конструювання та зв'язування задачі з `std::future` від безпосереднього моменту її виконання.

### Оголошення та спеціалізація шаблону

```cpp
template< class > class packaged_task; // Основний первинний шаблон (не визначений)

template< class R, class... Args >
class packaged_task<R(Args...)>;      // Часткова спеціалізація для сигнатури R(Args...)
```

Спеціалізація приймає сигнатуру функції, де `R` означає тип поверненого значення, а `Args...` — типи параметрів, які приймає обгортана функція.

### Конструктори та деструктор

```cpp
// 1. Конструктор за замовчуванням: створює об'єкт без спільного стану
packaged_task() noexcept;

// 2. Параметризований конструктор: приймає callable-об'єкт f
template< class F >
explicit packaged_task( F&& f );

// 3. Конструктор із підтримкою розподілювача пам'яті (вилучено в C++17)
template< class F, class Alloc >
packaged_task( std::allocator_arg_t, const Alloc& alloc, F&& f );

// 4. Конструктор переміщення: передає володіння спільним станом
packaged_task( packaged_task&& rhs ) noexcept;

// 5. Заборонений конструктор копіювання
packaged_task( const packaged_task& ) = delete;

// 6. Деструктор
~packaged_task();
```

При використанні конструктора (2) об'єкт виділяє пам'ять під спільний стан у купі, зберігає у ньому копію або переміщений об'єкт `f` та ініціалізує канали синхронізації. У C++17 конструктори з аргументом `std::allocator_arg_t` були вилучені зі стандарту через високу складність реалізації та відсутність підтримки у більшості компіляторів.

Якщо об'єкт `packaged_task` нищиться у деструкторі до того, як для нього було викликано `operator()`, але при цьому об'єкт `std::future` вже був вилучений через `.get_future()`, деструктор робить спільний стан готовим і записує туди код помилки `std::future_errc::broken_promise`. При спробі викликати `.get()` на стороні споживача буде згенеровано виняток `std::future_error`.

### Оператори присвоєння

```cpp
// Переміщувальне присвоєння: передає стан від rhs до поточного об'єкта
packaged_task& operator=( packaged_task&& rhs ) noexcept;

// Заборонене копіювальне присвоєння
packaged_task& operator=( const packaged_task& ) = delete;
```

### Гайди виведення типів шаблону (Deduction Guides) у C++17

Починаючи зі стандарту C++17, компілятор здатен автоматично виводити типи шаблону `std::packaged_task` з аргументів конструктора без явного вказування сигнатури `R(Args...)`:

```cpp
// Автоматично виводить std::packaged_task<int(double, char)>
template<class R, class... Args>
packaged_task(R(*)(Args...)) -> packaged_task<R(Args...)>;
```

Завдяки цьому розробник може конструювати обгортки над звичайними функціями простішим синтаксисом: `std::packaged_task task(my_func);`.

## 3. Методи класу `std::packaged_task`

### Метод `valid`

```cpp
bool valid() const noexcept;
```

Перевіряє, чи містить поточний об'єкт `packaged_task` дійсний ініціалізований спільний стан. Повертає `true`, якщо об'єкт сконструйований із функцією і ще не був переміщений (moved-from). Повертає `false` для об'єктів, створених конструктором за замовчуванням, або тих, з яких стан було переміщено в інший екземпляр. Будь-які спроби виконання операцій над об'єктом, для якого `valid() == false`, призводять до винятку `std::future_error`.

### Метод `get_future`

```cpp
std::future<R> get_future();
```

Створює та повертає об'єкт `std::future<R>`, під'єднаний до спільного стану даної задачі. Через цей об'єкт споживач може перевіряти готовність результату та отримувати значення `R`.

Метод `get_future()` дозволяється викликати **лише один раз** для кожного об'єкта `packaged_task`. Повторний виклик генерує виняток `std::future_error` із кодом `std::future_errc::future_already_retrieved`. Якщо розробникові потрібно роздати результат кільком потокам споживачам, повернутий `std::future` слід сконвертувати у `std::shared_future` за допомогою метода `fut.share()`.

Якщо об'єкт не має дійсного стану (`valid() == false`), кидається виняток із кодом `std::future_errc::no_state`.

### Метод `operator()`

```cpp
void operator()( Args... args );
```

Викликає збережений усередині обгортки callable-об'єкт із аргументами `args...`. Виконання відбувається синхронно у тому потоці, який викликав `operator()`.

- Якщо збережена функція успішно повертає результат `r` типу `R`, цей результат атомарно записується у спільний стан, а сам стан переводиться у режим «готовий» (ready).
- Якщо збережена функція під час виконання кидає виняток будь-якого типу, цей виняток перехоплюється блоком `try-catch`, упаковується в об'єкт `std::exception_ptr` за допомогою `std::current_exception()` та записується у спільний стан замість результату.
- Усі потоки, які у цей момент чекали на результат через `future.wait()` або `future.get()`, миттєво розблоковуються.
- **Винятки:** Якщо `operator()` викликається для задачі, яка вже була виконана раніше (і для неї не викликали метод `.reset()`), генерується виняток `std::future_error` із кодом `std::future_errc::promise_already_satisfied`.

### Метод `make_ready_at_thread_exit`

```cpp
void make_ready_at_thread_exit( Args... args );
```

Виконує збережений callable-об'єкт із аргументами `args...` та записує результат чи виняток у спільний стан, але **не активує** прапор готовності стану негайно. Спільний стан переводиться у готовий режим лише тоді, коли поточний потік виконання повністю завершується і в ньому викликаються деструктори всіх об'єктів із тривалістю життя `thread_local`.

Цей метод є необхідним у сценаріях, коли результати обчислення або повернуті посилання пов'язані з потоко-локальними даними. Якби стан став готовим негайно, споживач у іншому потоці міг би отримати результат і почати нищити залежні ресурси до того, як потік-виконавець завершить очищення своїх `thread_local` змінних, що викликало б стан гонитви.

### Метод `reset`

```cpp
void reset();
```

Скидає внутрішній стан `packaged_task`, виділяючи новий спільний стан та створюючи новий канал зв'язку для майбутніх обчислень. При цьому збережений callable-об'єкт (функція або лямбда) залишається незмінним.

Після виклику `.reset()` об'єкт знову стає придатним для нового виклику `.get_future()` та наступного виконання через `operator()`. Це дозволяє повторно використовувати один і той самий екземпляр задачі у циклічних обробниках або пулах задач без повторного виділення пам'яті під самого функтора.

- **Винятки:** Кидає `std::future_error` із кодом `std::future_errc::no_state`, якщо у об'єкта відсутня збережена функція.

### Метод `swap`

```cpp
void swap( packaged_task& other ) noexcept;
```

Атомарно обмінює вміст та спільні стани двох об'єктів `packaged_task`.

## 4. Система помилок та виняток `std::future_error`

Усі помилки, що виникають під час маніпуляцій зі спільним станом у `std::async` та `std::packaged_task`, виражаються через виняток `std::future_error`, який успадковано від `std::logic_error`.

### Інтерфейс `std::future_error`

```cpp
class future_error : public std::logic_error {
public:
    explicit future_error( std::error_code ec );
    const std::error_code& code() const noexcept;
    const char* what() const noexcept override;
};
```

Метод `code()` повертає об'єкт `std::error_code`, який можна порівнювати з переліком `std::future_errc`.

### Перелік кодів помилок `std::future_errc`

Стандарт C++ визначає чотири стандартні коди помилок для асинхронних примітивів:

```cpp
enum class future_errc {
    broken_promise = 1,           // Спільний стан втрачено до запису результату
    future_already_retrieved = 2, // Метод get_future() вже викликався раніше
    promise_already_satisfied = 3,// Спроба повторно записати результат у ready-стан
    no_state = 4                  // Спроба операції над об'єктом без спільного стану
};
```

#### Детальний аналіз причин виникнення кодів помилок:

1. **`broken_promise`**: Помилка виникає, коли об'єкт `std::packaged_task` (або `std::promise`) нищиться у деструкторі без виконання операції запису результату. Це сигнал споживачеві, що задача була анульована (наприклад, видалена з черги пулу потоків при аварійному зупиненні) і результат вже ніколи не буде обчислено.
2. **`future_already_retrieved`**: Виникає спробі повторно викликати метод `.get_future()` для одного й того самого об'єкта `packaged_task`. Спільний стан підтримує лише один асоційований `std::future`. Якщо розробникові потрібно роздати доступ багатьом потокам-споживачам, повернутий `std::future` слід сконвертувати у `std::shared_future` за допомогою метода `.share()`.
3. **`promise_already_satisfied`**: Виникає, коли `operator()` або `make_ready_at_thread_exit()` викликаються повторно для задач, які вже записали свій результат і перебувають у стані ready. Щоб дозволити повторне виконання, обов'язково треба викликати метод `.reset()`.
4. **`no_state`**: Помилка виникає при спробі звернутися до методів `.get_future()`, `.operator()`, `.reset()` або `.make_ready_at_thread_exit()` на порожньому об'єкті (наприклад, сконструйованому за замовчуванням або після того, як з нього було виконано `std::move`).

## 5. Проброс винятків через `std::exception_ptr`

Однією з найважливіших функцій `std::packaged_task` та `std::async` є автоматична трансляція виняткових ситуацій між потоками виконання без втрати типізації та контексту помилки.

Коли усередині обгортаної функції `f` кидається виняток (наприклад, `throw std::out_of_range("Index too large")`), перехоплення виконується за такою внутрішньою схемою:

1. `packaged_task::operator()` загортає виклик функції у блок `try-catch (...)`.
2. У гілці `catch` викликається системна функція `std::current_exception()`, яка створює об'єкт `std::exception_ptr`, що володіє копією винятку в купі з дотриманням атомарного лічильника посилань.
3. Об'єкт `std::exception_ptr` зберігається у внутрішній комірці спільного стану (Shared State) замість значення `R`.
4. Коли споживач у своєму потоці викликає `future.get()`, інтерфейс перевіряє вміст спільного стану. Якщо стан містить `std::exception_ptr`, метод виконує `std::rethrow_exception(stored_exception)`, повторно кидаючи точно такий самий виняток у потоці споживача.

Завдяки цьому споживач може використовувати стандартні блоки `try { auto res = fut.get(); } catch (const std::exception& e) { ... }`, не відрізняючи асинхронні помилки від локальних.

## 6. Сумісність із контейнерами та вимоги до стирання типів

Оскільки шаблонний клас `std::packaged_task<R(Args...)>` жорстко зафіксований за конкретною сигнатурою поверненого значення `R` та параметрів `Args...`, зберігання об'єктів із різними поверненими типами у єдиному гетерогенному контейнері (наприклад, `std::vector` чи `std::queue` у пулі потоків) вимагає стирання типів (type erasure).

Стандартна бібліотека C++ пропонує два основні підходи для згладжування типів:

- **Використання `std::packaged_task<R()>` у поєднанні з `std::shared_ptr`**: Задача без параметрів `R()` упаковується у купі за допомогою `std::make_shared<std::packaged_task<R()>>(std::bind(f, args...))`. Для збереження у стандартній черзі `std::queue<std::function<void()>>` створюється безпараметрична лямбда вида `[task] { (*task)(); }`.
- **Використання `std::move_only_function<void()>` у C++23**: Оскільки `std::function` вимагає від збереженого функтора здатності до копіювання (CopyConstructible), а `std::packaged_task` є строго move-only об'єктом, пряме розміщення `packaged_task` у `std::function` неможливе без `std::shared_ptr`. У C++23 впроваджено новий обгортковий тип `std::move_only_function<void()>`, який підтримує переміщувані об'єкти без додаткових шарів індирекції та лічильників посилань.

---

## 7. Низькорівнева реалізація спільного стану та накладні витрати

Для ефективного проектування систем важливо розуміти внутрішній макет та ціну створення об'єктів `std::packaged_task` та `std::async`.

Внутрішній спільний стан (Shared State) виділяється у динамічній пам'яті (купі) через виклик `operator new`. Цей блок пам'яті керується атомарним лічильником посилань (аналогічно до `std::shared_ptr`), оскільки на нього одночасно посилаються екземпляр `std::packaged_task` та екземпляр `std::future`.

Всередині спільного стану знаходяться такі примітиви:

- Атомарний прапор стану (State Enum: Empty, Stored, Exception, Read).
- Буфер вирівняної пам'яті `std::aligned_storage` під значення `R` або об'єкт `std::exception_ptr`.
- Примітив системної синхронізації: м'ютекс `std::mutex` та умовна змінна `std::condition_variable` (або виклик системного футекса `futex` у новіших реалізаціях Linux libstdc++), які реалізують зачекання у викликах `.wait()` та `.get()`.

Через це створення кожного нового об'єкта `std::packaged_task` чи `std::async` тягне за собою щонайменше одне динамічне виділення пам'яті в купі та ініціалізацію системних мутексів, що робить їх використання недоцільним для надто дрібних обчислень (наприклад, додавання двох чисел у циклі).

---

## 8. Гарантії потокобезпеки та інваріанти пам'яті

Для правильної побудови багатопотокових систем розробник мусить враховувати такі інваріанти потокобезпеки об'єктів `std::packaged_task` та `std::future`:

1. **Один викликач — Один виконавець**: Об'єкт `std::packaged_task` **не є потокобезпечним за внутрішнім станом**. Не дозволяється одночасно викликати методи `.operator()`, `.reset()` або `.get_future()` з двох різних потоків над одним і тим самим об'єктом `packaged_task` без зовнішньої синхронізації через `std::mutex`. Це призведе до стану гонитви (data race) та невизначеної поведінки.
2. **Безпека каналу зв'язку**: Сам *спільний стан* (Shared State), котрий знаходиться всередині купи і з'єднує `packaged_task` та `std::future`, є повністю потокобезпечним. Потік A може викликати `task(args...)`, а потік B у цей самий час чекати на `future.get()` — внутрішня синхронізація реалізації гарантує коректний атомарний запис і читання без дедлоків.
3. **Семантика переміщення**: Оскільки `std::packaged_task` не може бути скопійованим, його передача між потоками здійснюється виключно через `std::move`. Після переміщення початковий об'єкт втрачає стан (`valid() == false`), а новий об'єкт отримує повні права володіння функцією та спільним станом.

## 9. Взаємодія з `std::shared_future`

Коли результат обчислення `std::packaged_task` має бути переданий багатьом потокам-споживачам паралельно, стандартний `std::future` виявляється недостатньо гнучким, оскільки метод `future.get()` можна викликати лише один раз (він переміщує результат або виняток із спільного стану).

Для вирішення цієї проблеми C++ надає тип `std::shared_future<R>`, який конструюється шляхом переміщення зі звичайного `std::future`:

```cpp
std::packaged_task<int()> task([] { return 42; });
std::future<int> fut = task.get_future();
std::shared_future<int> shared_fut = fut.share(); // fut стає недійсним (valid() == false)
```

Об'єкт `std::shared_future` підтримує копіювання. Кілька потоків можуть мати власні копії `shared_fut` і одночасно викликати метод `.get()`. Усі вони отримають константне посилання на одне й те саме значення у спільному стані без стану гонитви.
