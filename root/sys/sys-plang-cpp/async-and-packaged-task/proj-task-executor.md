# ⚙️ Практична реалізація: Пул задач на основі std::packaged_task

Ця проєктна вставка містить повну, виробничу реалізацію базісного пулу робочих потоків (Thread Pool / Task Executor) мовою C++20. Приклад демонструє практичну цінність `std::packaged_task` для побудови асинхронних обчислювальних конвеєрів: як відокремити тип повернутого значення задачі `R` від типо-стертої черги виконання та забезпечити безпечне передавання результатів і винятків у покликуючі потоки через `std::future`.

---

## 1. Постановка архітектурної задачі та аналіз проблем паралелізму

При розробці високонавантажених серверів, графічних рушіїв чи систем обробки потокових даних виникає потреба регулярно виконувати сотні або тисячі дрібних обчислювальних задач. Створення нового потоку операційної системи (`std::thread`) на кожну окрему задачу супроводжується значними накладними витратами: виділенням стеку потоку (від 1 до 8 Мегабайтів), системними викликами до ядра ОС та частими переключеннями контексту (context switches).

Щоб вирішити цю проблему, застосовується паттерн **Пул Потоків (Thread Pool)**. Архітектура пулу складається з трьох ключових елементів:

1. Фіксована група робочих потоків (Worker Threads), які створюються один раз при старті пулу і живуть протягом усього часу роботи програми.
2. Потокобезпечна черга задач (Task Queue), у яку покликуючі потоки (клієнти) відправляють свої функції.
3. Канал зв'язку, через який кожен клієнт отримує результат саме своєї задачі (або перехоплює виняток), не блокуючи виконання інших задач у пулі.

Головна технічна складність полягає у тому, що клієнти надсилають задачі із **різними** сигнатурами, різними типами аргументів та різними повернутими типами `R`. Черга задач повинна мати єдиний уніфікований тип (наприклад, `std::queue<std::function<void()>>`), але клієнт має отримати строкотипізований `std::future<R>`.

Шаблон `std::packaged_task` є ідеальним мостом для вирішення цього завдання: він упаковує довільну функцію `R(Args...)` у безпараметричний функтор `R()`, зберігає винятки у спільному стані та надає клієнту чистий `std::future<R>`.

При проектуванні даного пулу необхідно враховувати чотири фундаментальні ризики розробки паралельних систем:

- **Суперечка за м'ютекс (Mutex Contention)**: Якщо десяток робочих потоків одночасно намагаються витягнути задачу з єдиної черги під блокуванням м'ютекса, продуктивність системи починає падати через простої процесорних ядер у черзі до синхронізатора. Щоб мінімізувати цей ефект, критична секція повинна обмежуватися виключно операцією витягування вказівника на задачу з черги, а саме обчислення задачі має виконуватися повністю поза м'ютексом.
- **Хибне розблокування (Spurious Wakeups)**: Умовні змінні ОС (`std::condition_variable`) за своєю природою можуть розблоковувати чекаючий потік навіть за відсутності сигналу `notify`. Для захисту від цього стан перевіряється у циклі через предикат готовності.
- **Помилки руйнування стеку (Stack Tearing & Dangling References)**: Якщо передати аргумент за посиланням на локальну змінну викликаючого потоку, а цей потік вийде з зони видимості до того, як потік пулу виконає задачу, стається руйнування пам'яті. Для вирішення цієї проблеми аргументи мають або копіюватися, або загортатися у `std::shared_ptr`.
- **Хибне розділення кєш-ліній (False Sharing)**: Коли кілька потоків часто модифікують суміжні змінні, що лежать на одній кєш-лінії процесора (64 байти), стається постійне скидання L1/L2 кєшів ядер (Cache Line Bouncing).

## 2. Повний сирцевий код пулу задач (C++20)

Нижче наведено самодостатній, готовий до компіляції модуль пулу задач `TaskExecutor`.

```cpp
#include <iostream>
#include <vector>
#include <queue>
#include <thread>
#include <mutex>
#include <condition_variable>
#include <future>
#include <functional>
#include <memory>
#include <stdexcept>
#include <chrono>
#include <numeric>

// Клас пулу задач на основі std::packaged_task
class TaskExecutor {
public:
    // Конструктор створює вказану кількість робочих потоків (за замовчуванням — кількість ядер ЦП)
    explicit TaskExecutor(size_t threads = std::thread::hardware_concurrency())
        : stop_(false) 
    {
        if (threads == 0) {
            threads = 1; // Гарантуємо наявність щонайменше одного потоку
        }

        workers_.reserve(threads);
        for (size_t i = 0; i < threads; ++i) {
            workers_.emplace_back([this] { worker_loop(); });
        }
    }

    // Забороняємо копіювання та переміщення пулу
    TaskExecutor(const TaskExecutor&) = delete;
    TaskExecutor& operator=(const TaskExecutor&) = delete;
    TaskExecutor(TaskExecutor&&) = delete;
    TaskExecutor& operator=(TaskExecutor&&) = delete;

    // Деструктор автоматично зупиняє пул і чекає завершення виконання усіх потоків
    ~TaskExecutor() {
        shutdown();
    }

    // Основний шаблонний метод постановки задачі в чергу
    template<typename F, typename... Args>
    auto enqueue(F&& f, Args&&... args) 
        -> std::future<std::invoke_result_t<F, Args...>> 
    {
        using return_type = std::invoke_result_t<F, Args...>;

        // 1. Упаковуємо функцію та її аргументи у безпараметричний функтор packaged_task
        auto task = std::make_shared<std::packaged_task<return_type()>>(
            std::bind_front(std::forward<F>(f), std::forward<Args>(args)...)
        );

        // 2. Отримуємо future, який буде повернено клієнту
        std::future<return_type> res = task->get_future();

        {
            std::unique_lock<std::mutex> lock(queue_mutex_);

            // Забороняємо додавати нові задачі у зупинений пул
            if (stop_) {
                throw std::runtime_error("Спроба додати задачу у зупинений TaskExecutor");
            }

            // 3. Стирання типу: загортаємо виклик task у безпараметричну лямбду void()
            tasks_.emplace([task]() { 
                (*task)(); 
            });
        }

        // 4. Сповіщаємо один із вільних робочих потоків
        cv_.notify_one();
        return res;
    }

    // Ручна зупинка пулу (якщо потрібно зупинити до виклику деструктора)
    void shutdown() {
        {
            std::unique_lock<std::mutex> lock(queue_mutex_);
            if (stop_) {
                return; // Вже зупинено
            }
            stop_ = true;
        }

        // Сповіщаємо усі потоки про необхідність виходу
        cv_.notify_all();

        // Очікуємо приєднання кожного потоку
        for (std::thread& worker : workers_) {
            if (worker.joinable()) {
                worker.join();
            }
        }
        workers_.clear();
    }

private:
    // Цикл виконання робочого потоку
    void worker_loop() {
        while (true) {
            std::function<void()> task;

            {
                std::unique_lock<std::mutex> lock(queue_mutex_);
                
                // Чекаємо появу задачі або прапора зупинки
                cv_.wait(lock, [this] {
                    return stop_ || !tasks_.empty();
                });

                // Якщо пул зупинено і черга порожня — виходимо з потоку
                if (stop_ && tasks_.empty()) {
                    return;
                }

                // Витягуємо задачу з черги
                task = std::move(tasks_.front());
                tasks_.pop();
            }

            // Виконуємо задачу поза блокуванням м'ютекса!
            task();
        }
    }

    std::vector<std::thread> workers_;          // Вектор робочих потоків
    std::queue<std::function<void()>> tasks_;  // Черга типо-стертих задач
    std::mutex queue_mutex_;                   // М'ютекс синхронізації черги
    std::condition_variable cv_;               // Умовна змінна сповіщення потоків
    bool stop_;                                // Прапор аварійної або планової зупинки
};
```

## 3. Детальний покроковий аналіз реалізації та інваріантів

Розглянемо детально кожну інженерну ланку реалізованого пулу задач `TaskExecutor`.

### 3.1. Ініціалізація та розрахунок ресурсів у конструкторі

Конструктор пулу приймає параметром кількість робочих потоків:
```cpp
explicit TaskExecutor(size_t threads = std::thread::hardware_concurrency())
```
Стандартний метод `std::thread::hardware_concurrency()` повертає кількість логічних процесорних ядер у системі. Проте у деяких середовищах (наприклад, у віртуальних контейнерах Docker або застарілих операційних системах) цей виклик може повертати `0`. Для захисту від створення пулу із нульовою кількістю потоків додано перевірку:
```cpp
if (threads == 0) threads = 1;
```
Викликом `workers_.reserve(threads)` ми заздалегідь виділяємо неперервний блок пам'яті у векторі для зберігання потоків. Це запобігає реалокації вектора під час додавання нових екземплярів `std::thread`. Оскільки `std::thread` є строго move-only об'єктом, його реалокація з копіюванням призвела б до помилки компіляції.

### 3.2. Виведення типу поверненого значення через `std::invoke_result_t`

У сигнатурі шаблону метода `enqueue`:
```cpp
template<typename F, typename... Args>
auto enqueue(F&& f, Args&&... args) 
    -> std::future<std::invoke_result_t<F, Args...>>
```
Застосовується метафункція C++17 `std::invoke_result_t<F, Args...>`. Вона розраховує під час компіляції точний тип `R`, який буде повернуто викликом `f(args...)`. Це дозволяє методу повертати строкотипізований об'єкт `std::future<R>`, зберігаючи повний контроль над типом для клієнтського коду.

Для зв'язування функції `f` та переданих аргументів `args...` застосовується нова функція стандарту C++20 `std::bind_front`:
```cpp
auto task = std::make_shared<std::packaged_task<return_type()>>(
    std::bind_front(std::forward<F>(f), std::forward<Args>(args)...)
);
```
На відміну від застарілого `std::bind`, функція `std::bind_front` не вимагає використання плейсхолдерів (`std::placeholders::_1`), є набагато простішою для оптимізації компілятором і краще зберігає категорії значень (lvalue/rvalue) переданих аргументів.

### 3.3. Принцип стирання типів через `std::shared_ptr` та `std::function`

Шаблонний клас `std::packaged_task` є move-only тип. Однак обгортка `std::function<void()>`, яка формує тип елементів нашої черги `tasks_`, за специфікацією стандарту C++ вимагає, щоб збережений у ній функтор був копіюваним (CopyConstructible).

Щоб розв'язати цю суперечність типів, ми створюємо об'єкт `std::packaged_task` у динамічній пам'яті через розумний вказівник:
```cpp
auto task = std::make_shared<std::packaged_task<return_type()>>(...);
```
Потім ми створюємо безпараметричну лямбду-функцію, яка захоплює цей `task` **за значенням** (тобто копіює сам вказівник `std::shared_ptr`):
```cpp
tasks_.emplace([task]() { 
    (*task)(); 
});
```
Оскільки копіювання `std::shared_ptr` є швидкою атомарною операцією інкременту лічильника посилань, утворена лямбда стає копіюваною і легко поміщається у `std::queue<std::function<void()>>`. У момент виконання потік-воркер викликає лямбду, яка робить розвказівування `(*task)()` і виконує розрахунок.

### 3.4. Оптимізація локальності та розблокування м'ютекса

У циклі виконання робочого потоку `worker_loop` витягування задачі з черги відбувається всередині критичної секції під захистом RAII-замка `std::unique_lock<std::mutex>`:
```cpp
{
    std::unique_lock<std::mutex> lock(queue_mutex_);
    cv_.wait(lock, [this] { return stop_ || !tasks_.empty(); });
    if (stop_ && tasks_.empty()) return;
    task = std::move(tasks_.front());
    tasks_.pop();
} // М'ютекс queue_mutex_ автоматично звільняється тут!

task(); // Безпосереднє виконання обчислень відбувається ПОЗА критичною секцією
```
Це найважливіше правило проектування паралельних обробників. Безпосередній виклик `task()` відбувається повністю **поза** м'ютексом. Якщо б ми викликали `task()` всередині критичної секції, інші робочі потоки не змогли б витягувати нові задачі з черги під час довгих обчислень, і весь пул перетворився б на повільний послідовний процес.

### 3.5. Корректне завершення роботи та профілактика дедлоків у `shutdown()`

Метод `shutdown()` забезпечує коректне зупинення пулу потоків з вичерпанням усіх залишкових задач у черзі:

1. Спочатку під блокуванням м'ютекса встановлюється прапор `stop_ = true`.
2. Викликом `cv_.notify_all()` розблоковуються усі робочі потоки, які перебували у стані очікування на умовній змінній `cv_.wait()`.
3. Кожен потік прокинувшись перевіряє предикат: бачить `stop_ == true` та чинить останню перевірку: якщо черга ще містить задачі, потік допрацьовує їх, а коли черга стає порожньою (`tasks_.empty() == true`), потік повертається з виклику `worker_loop()` і завершує своє існування.
4. У циклі `for (auto& worker : workers_) worker.join()` головний потік приєднує кожен робочий потік, гарантуючи відсутність висячих потоків та витоків системних хендлів.

## 4. Порівняння реалізації у C++20 проти C++23 (`std::move_only_function`)

Наведена вище реалізація пулу C++20 використовує `std::shared_ptr` для розміщення `packaged_task` у `std::function`. У C++23 стандарт отримав новий обгортковий тип **`std::move_only_function<void()>`**, який знімає обмеження на обов'язкове копіювання збереженого функтора.

Завдяки цьому у C++23 реалізація пулу задач стає ще ефективнішою:
```cpp
// Реалізація черги у C++23 без використання std::shared_ptr та без виділення пам'яті під лічильник посилань
std::queue<std::move_only_function<void()>> tasks_;

template<typename F, typename... Args>
auto enqueue(F&& f, Args&&... args) -> std::future<std::invoke_result_t<F, Args...>> {
    using return_type = std::invoke_result_t<F, Args...>;
    
    std::packaged_task<return_type()> task(
        std::bind_front(std::forward<F>(f), std::forward<Args>(args)...)
    );
    
    std::future<return_type> res = task.get_future();

    {
        std::unique_lock<std::mutex> lock(queue_mutex_);
        if (stop_) throw std::runtime_error("TaskExecutor is stopped");
        
        // Пряме переміщення packaged_task у move_only_function без std::shared_ptr!
        tasks_.emplace([task = std::move(task)]() mutable { 
            task(); 
        });
    }
    cv_.notify_one();
    return res;
}
```
Використання `std::move_only_function` у C++23 повністю усуває оверхед на створення `std::shared_ptr`, роблячи систему набагато швидшою та зменшуючи фрагментацію динамічної пам'яті.

## 5. Захист від вкладених дедлоків та вибір розміру пулу

При експлуатації пулу задач у складних системах виникають ситуації, коли самі задачі у пулі намагаються викликати `pool.enqueue(...)` для підзадач.

### 5.1. Пастка вкладених зачекань (Thread Starvation Deadlock)

Уявимо сценарій:
```cpp
pool.enqueue([&pool] {
    auto sub_fut = pool.enqueue(sub_task);
    return sub_fut.get(); // Блокування потоку пулу!
});
```
Якщо розмір пулу дорівнює `N`, і у пул одночасно надходить `N` таких базних задач, усі `N` робочих потоків візьмуть по одній задачі і викличуть `pool.enqueue(sub_task)`. Після цього всі `N` потоків заблокуються на `sub_fut.get()`, чекаючи виконання підзадач. Однак для виконання `sub_task` у пулі більше немає жодного вільного потоку! Виникає взаємне зачекання (дедлок виснаження потоків / Thread Starvation Deadlock).

Щоб уникнути цього, реальні асинхронні середовища впроваджують механізми **Work Stealing** або підтримують кооперативні виклики `yield`, коли потік, який чекає на `future.get()`, тимчасово витягує з черги інші задачі та виконує їх замість простою у блокуванні.

### 5.2. Поведінка при передчасному скиданні `std::future`

Що відбудеться, якщо покликуючий потік відправив задачу в пул через `enqueue`, отримав `std::future`, але згодом нищить цей `std::future` (або виходить із зони видимості), так і не викликавши `.get()`?

Оскільки `std::packaged_task` утримує власну копію посилання на спільний стан усередині `std::shared_ptr`, знищення `future` клієнтом не перериває виконання задачі. Робочий потік витягне задачу з черги, виконає її розрахунок і запише результат у спільний стан. Після завершення виконання `packaged_task` нищиться, лічильник посилань спільного стану стає рівним нулю, і пам'ять під спільний стан автоматично звільняється.

### 5.3. Порівняння одночергової архітектури з Work-Stealing (Intel TBB)

Наш `TaskExecutor` використовує єдину загальну чергу задач `tasks_`, захищену м'ютексом `queue_mutex_`. Такий підхід є простим і надійним для малих та середніх систем (до 16-32 потоків).

Однак у масивних обчислювальних кластерах (64 і більше ядер) єдина черга стає "пляшковим горлом" через суперечку за м'ютекс. Сучасні промислові бібліотеки (Intel OneTBB, Go Runtime, Rust Tokio) застосовують підхід **Work Stealing**:

- Кожен робочий потік має власну двосторонню чергу (deque).
- Нові задачі додаються у локальну чергу потоку в режимі LIFO (Last-In, First-Out) для кращої локальності кєшу.
- Якщо локальна черга потоку порожня, він намагається "вкрасти" задачу з дна черги (FIFO) іншого потоку.

Завдяки цьому `std::packaged_task` може легко переміщуватися між чергами різних потоків за допомогою `std::move`, мінімізуючи точки синхронізації.

### 5.4. Вибір кількості робочих потоків (CPU-bound vs I/O-bound)

Оптимальна кількість робочих потоків у конструкторі `TaskExecutor` залежить від специфіки обчислювальних задач:

- **Для обчислювальних задач (CPU-bound)**: Кількість потоків має дорівнювати кількості фізичних ядер процесора (`N_threads = N_cores`). Створення більшої кількості потоків не прискорить обчислення, а лише збільшить витрати часу ЦП на переключення контексту між стеками.
- **Для задач вводу-виводу (I/O-bound)**: Коли потоки чекають на відповіді від диска, мережевих сокетів або баз даних, більшу частину часу потік перебуває у стані сну (blocked state). Кількість потоків розраховується за формулою:

```
N_threads = N_cores · (1 + W / C)
```

де `W` — час очікування I/O, а `C` — час активного використання процесора.

## 6. Механізми трасування та діагностики асинхронних контекстів

При збоях у багатопотокових системах стандартного стек-трейса (stack trace) недостатньо, оскільки виняток виникає усередині робочого потоку воркера, де інформація про покликуючий потік втрачається.

Для вирішення цієї проблеми у промислових реалізаціях `TaskExecutor` до `std::packaged_task` додають обгортки телеметрії (Tracing Spans):

1. **Ідентифікатор кореляції (Trace ID)**: При постановці задачі в чергу у метод `enqueue` передається унікальний ідентифікатор транзакції.
2. **Обгортка контексту**: Перед викликом `task()` у `worker_loop` робочий потік встановлює `thread_local` змінну поточного Trace ID, а після завершення задачі очищує її.
3. **Логування та профілювання**: Усі повідомлення про винятки або затримки виконання автоматично прив'язуються до початкового викликача, що дозволяє легко відстежувати причинно-наслідкові зв'язки задач у великих розподілених системах.

## 7. Оцінка продуктивності та групування задач (Batching)

При роботі з дуже дрібними задачами (час виконання яких вимірюється наносекундами) оверхед на блокування м'ютекса та сповіщення через `condition_variable` може перевищувати корисну роботу самої функції.

Для досягнення максимальної пропускної здатності застосовують три техніки оптимізації:

- **Групування задач (Batching)**: Метод `enqueue_bulk` приймає масив задач і додає їх у чергу за один виклик під єдиним блокуванням м'ютекса, після чого викликає `cv_.notify_all()`. Це зменшує кількість системних блокувань м'ютекса у `K` разів, де `K` — розмір пачки.
- **Використання `notify_one` замість `notify_all`**: При постановці однієї задачі слід викликати `cv_.notify_one()`. Виклик `notify_all()` для однієї задачі розбудить усі чекаючі потоки (Thundering Herd Problem), змусивши їх змагатися за єдиний м'ютекс і марно витрачати процесорний час.
- **Підготовка пам'яті через custom allocators**: Для прискорення створення спільного стану в `std::packaged_task` можна застосовувати арени пам'яті (Memory Arenas / Bump Allocators) у сумісних C++14 середовищах.

### 7.1. Порівняння оверхеду системних виділень пам'яті

Виділення пам'яті у динамічній купі (`malloc` / `operator new`) супроводжується пошуком вільного блоку у таблицях аллокатора та потенційними системними викликами розширення сегмента даних `brk` / `mmap`. Коли сотні тисяч дрібних `std::packaged_task` створюються та нищаться кожної секунди, менеджер пам'яті стає джерелом фрагментації та виникають системні простої у `malloc_mutex`.

Застосування басейнів пам'яті (Memory Pools) або локальних середовищ `std::pmr::unsynchronized_pool_resource` повністю знімає цей оверхед, прискорюючи виконання асинхронного конвеєра у кілька разів. Спеціалізовані арени гарантують виділення пам'яті за константний час `O(1)` без блокування глобальних м'ютексів системного менеджера купи. Це принципово важливо для низькозатримкових додатків, таких як торгові термінали та графічні ігрові двигуни.

## 8. Демонстраційна програма та верифікація

Нижче наведено комплект тестів, який перевіряє паралельний розрахунок сум великих масивів, обробку винятків у фонових потоках та повторний запуск задач.

```cpp
// Допоміжна функція для імітації складного розрахунку
long long compute_sum(int id, const std::vector<int>& data) {
    std::cout << "[Потік " << std::this_thread::get_id() 
              << "] Початок обробки задачі #" << id << std::endl;
    
    // Імітуємо обчислювальне навантаження
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    
    long long sum = std::accumulate(data.begin(), data.end(), 0LL);
    
    std::cout << "[Потік " << std::this_thread::get_id() 
              << "] Завершення задачі #" << id << " -> Сума = " << sum << std::endl;
    return sum;
}

// Функція, яка кидає виняток під час виконання
double risky_division(double a, double b) {
    if (b == 0.0) {
        throw std::invalid_argument("Ділення на нуль у фоновому потоці!");
    }
    return a / b;
}

int main() {
    std::cout << "=== Старт демонстрації TaskExecutor ===" << std::endl;

    // Створюємо пул із 4 робочих потоків
    TaskExecutor pool(4);

    // 1. Надсилаємо групу обчислювальних задач
    std::vector<int> numbers(100000, 1); // Вектор з 100 000 одиниць
    std::vector<std::future<long long>> futures;

    for (int i = 1; i <= 8; ++i) {
        futures.push_back(pool.enqueue(compute_sum, i, std::cref(numbers)));
    }

    // 2. Надсилаємо задачу з потенційним винятком
    auto err_future = pool.enqueue(risky_division, 10.0, 0.0);

    // 3. Збираємо результати паралельних обчислень
    long long total_sum = 0;
    for (size_t i = 0; i < futures.size(); ++i) {
        // fut.get() чекає завершення конкретної задачі
        total_sum += futures[i].get();
    }

    std::cout << "\n[Головний потік] Усі обчислення завершено. Загальна сума = " 
              << total_sum << std::endl;

    // 4. Перевіряємо обробку винятку
    try {
        double res = err_future.get();
        std::cout << "Результат ділення: " << res << std::endl;
    } catch (const std::exception& e) {
        std::cout << "\n[Головний потік] Успішно перехоплено виняток з пулу: " 
                  << e.what() << std::endl;
    }

    std::cout << "=== Завершення демонстрації ===" << std::endl;
    return 0;
}
```

## 9. Результати виконання та оцінка продуктивності

При запуску на 4-ядерній системі програма демонструє такі ключові характеристики:

1. **Паралельне виконання**: 8 задач обробки масивів розподіляються між 4 робочими потоками. Чотири задачі виконуються паралельно у першій хвилі, а наступні чотири — у другій хвилі. Загальний час виконання становить близько 200 мс замість 800 мс при послідовному виконанні.
2. **Прозорий проброс винятків**: Виняток `std::invalid_argument`, згенерований усередині `risky_division` у фоновому потоці воркера, перехоплюється обгорткою `std::packaged_task`, зберігається у спільном стані через `std::exception_ptr` і безпечно перевикидається у головному потоці при виклику `err_future.get()`. Робочий потік при цьому **не падає** і залишається готовим до виконання наступних задач.
3. **Безпечне завершення (RAII)**: Деструктор `TaskExecutor` автоматично встановлює прапор `stop_`, викликом `cv_.notify_all()` розблоковує всі воркер-потоки і приєднує їх через `.join()`, виключаючи витоки ресурсів або зависання процесу.
