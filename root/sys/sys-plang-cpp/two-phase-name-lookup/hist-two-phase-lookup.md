# 📜 Історія двофазного пошуку й епопея з export

У цій історичній довідці відтворено хроніку виникнення та прийняття двофазного пошуку імен у стандарті C++98, драматичну епопею навколо роздільної компіляції шаблонів і ключового слова `export`, а також глибокі технічні причини, з яких розробники Microsoft Visual C++ понад двадцять років зберігали нестандартний однофазний парсер.

##Витоки проблеми: шаблони як текстові макроси з контролем синтаксису

Коли Б'ярн Страуструп розробляв перші версії шаблонів для мови C++ у період 1988–1990 років (що знайшло своє відображення у класичній книзі *The Annotated C++ Reference Manual*, ARM, 1990), узагальнене програмування сприймалося як суттєве еволюційне вдосконалення макросів препроцесора. Головна ідея полягала в тому, щоб дозволити програмісту описувати алгоритм один раз, залишаючи типи параметрів відкритими для подальшої підстановки.

На початковому етапі модель компіляції шаблонів була винятково простою та імпліцитною. Коли компілятор зустрічав визначення шаблону типу `template <typename T> void process(T x)`, він не намагався будувати повноцінне абстрактне синтаксичне дерево (AST) із зафіксованими зв'язками між символами. Замість цього транслятор просто зберігав послідовність синтаксичних лексем у пам'яті. Коли у коді з'являвся виклик виду `process(42)` або `process(my_widget)`, компілятор брав збережений текст шаблону, підставляв `int` або `Widget` замість формального параметра `T` і запускав повний процес компіляції з нуля для утвореної функції.

Цей ранній макросний підхід мав кілька фундаментальних недоліків, які ставали очевидними у міру зростання розмірів C++ проєктів:

1. **Запізніла діагностика помилок:** Якщо автор шаблону робив банальну синтаксичну помилку в тілі функції (наприклад, помилявся у назві стандартного типу або пропускав крапку з комою), компілятор мовчав під час трансляції заголовкового файлу. Помилка виявлялася лише тоді, коли користувач намагався інстанціювати шаблон у власному файлі. Якщо ж шаблон жодного разу не інстанціювався у даній одиниці трансляції, синтаксичний дефект міг роками залишатися непоміченим у бібліотеці.
2. **Нестабільність семантики та захоплення імен (Name Hijacking):** Оскільки аналіз коду відбувався повністю в точці виклику, усі некваліфіковані виклики функцій у тілі шаблону зв'язувалися з тими оголошеннями, які були видимими у файлі користувача перед викликом шаблону. Якщо користувач у власному файлі випадково оголошував функцію з таким самим іменем, як внутрішня допоміжна функція автора шаблону, компілятор мовчки обирав функцію користувача. Це призводило до важкодіагностованих помилок під час виконання.

Розробникам мови стало зрозуміло: шаблонам потрібна сувора теоретична модель, яка чітко розмежує контекст створення шаблону та контекст його використання.

## Пропозиція ISO C++98 та народження двофазного пошуку

Під час активної фази стандартизації C++ у середині 1990-х років комітет ISO WG21 (у якому провідну роль у питанні шаблонів відігравали Ервін Унру, Нейтан Майєрс, Дейв Ранд та члени компанії Edison Design Group) поставив за мету розробити систему пошуку імен, яка б гарантувала передбачуваність складання коду.

Фундаментальне рішення полягало в умовному розділенні життєвого циклу шаблону на два контексти:

- **Контекст визначення (Definition Context):** Простір імен, заголовки та області видимості, що знаходяться у місці, де автор написав код шаблону.
- **Контекст інстанціювання (Instantiation Context):** Область видимості у місці, де користувач передає конкретні типові аргументи `T`.

Щоб поєднати безпеку першого контексту з гнучкістю другого, комітет сформулював правила **двофазного пошуку імен** (англ. *Two-Phase Name Lookup*):

1. **Фаза 1 (на етапі визначення):** Компілятор негайно розбирає синтаксис шаблону та аналізує всі імена, які не залежать від параметрів `T` (незалежні імена). Вони зв'язуються з оголошеннями у контексті визначення і більше ніколи не змінюють своєї прив'язки.
2. **Фаза 2 (на етапі інстанціювання):** Пошук імен, які залежать від `T` (залежні імена), відкладається до моменту відомості `T`. У точці інстанціювання (POI) компілятор шукає відповідні перевантаження, комбінуючи контекст визначення з асоційованими просторами імен типів-аргументів через пошук за аргументами (ADL).

Ця модель увійшла до складу першого офіційного стандарту ISO/IEC 14882:1998 (C++98). Вона забезпечила математично строгу семантику, але висунула надзвичайно високі вимоги до архітектури компіляторів.

## Двофазний пошук і роздільна компіляція: епопея з ключовим словом export

Паралельно з двофазним пошуком у стандарт C++98 було включено механізм, який спричинив найбільшу дискусію в історії мови — роздільну компіляцію шаблонів за допомогою ключового слова `export`.

Ідея `export template` виглядала надзвичайно привабливо: дозволити розробникам розділяти шаблон на оголошення у заголовковому файлі (`.h`) та визначення у файлі реалізації (`.cpp`), як це віддавна робилося для звичайних функцій:

```cpp
// Header: my_container.h
template <typename T>
class MyContainer {
public:
    void process();
};

// Source: my_container.cpp
export template <typename T>
void MyContainer<T>::process() {
    // реалізація
}
```

Проте реалізація `export` разом із двофазним пошуком вимагала від компілятора зберігати не просто згенерований машинний код або об'єктні символи, а повне абстрактне синтаксичне дерево (AST) шаблону разом із точним станом усіх областей видимості Фази 1 всередині об'єктних файлів (`.o` / `.obj`). Під час компонування (link-time) компонувальник або спеціальний препроцесор повинен був підтягувати це AST, підставляти типи з інших одиниць трансляції та запускати Фазу 2.

Єдиною компанією, якій вдалося повністю реалізувати `export template`, була **Edison Design Group (EDG)** під керівництвом Джона Спайсера та Давіда Вандевоорде. На це пішло понад п'ять років напруженої інженерної праці, а результат вимагав складного проміжного інструменту компіляції. Жоден з інших провідних виробників компіляторів (включаючи GCC, Clang та Microsoft) так і не реалізував `export`.

У 2003 році Давід Вандевоорде та Микола Джоссутіс опублікували фундаментальну працю *C++ Templates: The Complete Guide*, у якій детально описали всю складність `export`. Стало зрозуміло, що затрати ресурсів компілятора не виправдовують отриманих переваг. Зрештою, у 2011 році комітет ISO C++ одностайно ухвалив рішення про вилучення `export template` з мови у стандарті C++11 (пропозиція N3065), звільнивши шлях для сучасної системи модулів (C++20).

## Аномалія MSVC: двадцять років однофазного аналізу

У той час як розробники GCC (починаючи з версій 3.x) та Clang (від самого початку його створення у 2007 році) будували свої фронтенди на принципах суворого двофазного пошуку відповідно до ISO C++98, компілятор Microsoft Visual C++ пішов повністю іншим шляхом.

Архітектура фронтенду MSVC (відома як C2), що розроблялася на початку 1990-х років для компіляції C і ранніх версій C++, виявилася неготовою до складностей Фази 1. Абіційна мета Microsoft забезпечити максимальну швидкість компіляції на тогочасному апаратному забезпеченні призвела до рішення зберегти однофазний аналіз.

У результаті MSVC працював за спрощеною схемою:
- Під час першого прочитання шаблону компілятор виконував лише поверховий грубий розбір лексем.
- Повноцінне синтаксичне дерево будувалося лише тоді, коли шаблон інстанціювався у коді.
- Усі імена (як залежні, так і незалежні) шукалися в точці інстанціювання.

Цей відступ від стандарту спричинив глибокий розколоти у спільноті C++ розробників:

- Код із відсутніми `this->` перед членами базових залежних класів компілювався в Visual Studio без жодних зауважень.
- Код із відсутніми ключовими словами `typename` перед залежними типами сприймався MSVC як коректний.
- Мільйони рядків коду, написані корпоративними розробниками під Windows, виявлялися повністю непрацездатними під час спроби зібрати їх під Linux за допомогою GCC або Clang.

Ситуація стала критичною з появою стандарту C++11 та поширенням складних метапрограмованих бібліотек (Boost, Eigen, Catch2). Нестандартна поведінка MSVC вимагала від авторів бібліотек писати величезну кількість розархітектурених `#ifdef _MSC_VER` хаків.

У 2017 році команда Visual C++ під керівництвом Ендрю Пардо розпочала масштабний проєкт переписання фронтенду MSVC. З випуском Visual Studio 2017 (версія 15.3) було представлено новий відповідний стандарту парсер, який активувався прапорцем `/permissive-` (а у Visual Studio 2019 з вибором `/std:c++20` став поведінкою за замовчуванням). Це стало остаточним завершенням 20-літнього періоду відхилень і повернуло суворий двофазний пошук імен як єдиний загальновизнаний стандарт для всіх платформ.
