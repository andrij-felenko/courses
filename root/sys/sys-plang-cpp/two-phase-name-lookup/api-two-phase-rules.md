# 📋 Довідник правил класифікації імен та дисамбігуаторів у шаблонах

У цій довідковій вставці систематизовано формальні правила класифікації залежних та незалежних імен, семантичну механіку визначення точок інстанціювання (Point of Instantiation — POI), синтаксичні правила застосування дисамбігуаторів `typename` та `template`, а також їхню еволюцію у стандартах від C++98 до C++20.

## 1. Матриця класифікації імен у тілі шаблону

Під час первинного парсингу синтаксичного дерева (Фаза 1) компілятор аналізує кожну лексему всередині шаблону і відносить її до однієї з двох фундаментальних категорій: **незалежне ім'я (non-dependent name)** або **залежне ім'я (dependent name)**. Категоризація визначає часовий момент та семантичні правила, за якими компілятор шукатиме відповідний символ у програмі.

| Категорія виразу | Приклад синтаксису у коді | Фаза аналізу | Механізм та правила пошуку імен |
| :--- | :--- | :--- | :--- |
| **Незалежний тип** | `int`, `std::size_t`, `std::string` | Фаза 1 | Звичайний пошук у місці визначення шаблону. Не залежить від `T`. |
| **Незалежна функція** | `global_func(42)`, `std::abs(-5)` | Фаза 1 | Фіксація перевантаження у контексті визначення. Пізні оголошення не бачить. |
| **Кваліфікований незалежний член** | `Base::display()`, `::helper()` | Фаза 1 | Звичайний кваліфікований пошук у зазначених областях видимості. |
| **Залежний параметр шаблону** | `T`, `typename Container::value_type` | Фаза 2 | Підстановка конкретного параметра при інстанціюванні. |
| **Залежний виклик функції** | `process(t)`, `serialize(obj, stream)` | Фаза 2 | Контекст визначення + ADL в асоційованих просторах типів у POI. |
| **Звернення через this** | `this->data`, `this->update()` | Фаза 2 | Вказівник `this` має залежний тип `Class<T>*`, тому вираз є залежним. |
| **Поле залежної бази** | `Base<T>::member` | Фаза 2 | Потрібна явна кваліфікація; пошук виконується у конкретизованій `Base<T>`. |
| **Залежний шаблонний метод** | `obj.template parse<int>()` | Фаза 2 | Потрібен явний дисамбігуатор `template` після `.`, `->` або `::`. |

### Детальний опис механізмів класифікації

Незалежні імена характеризуються тим, що їхня семантика повністю зафіксована у момент написання шаблону. Якщо компілятор зустрічає незалежне ім'я, він не чекає на створення об'єктів або виклики методів з конкретними типами `T`. Звичайний пошук відбувається негайно через перегляд поточного блоку, охопних класів, просторів імен та глобальної області видимості. Якщо незалежне ім'я не вдається зв'язати з жодним оголошенням, компілятор зупиняє трансляцію і видає повідомлення про помилку на Фазі 1.

Залежні імена, навпаки, є умовними конструкціями. Їхня точна семантика не може бути встановлена без знання конкретної структури типів-аргументів `T`. Оскільки `T` може бути як вбудованим типом (`int`), так і складним класом з іншої бібліотеки (`physics::Vector`), компілятор зберігає залежне ім'я у синтаксичному дереві у вигляді відкладеного вузла. Його розв'язання здійснюється лише на Фазі 2 у точці інстанціювання.

## 2. Класифікація виразів та типів на залежність

Залежність виразу від параметрів шаблону вимірюється не просто наявністю символу `T` у назві, а глибинною прив'язкою типу або обчислення до формальних параметрів шаблону. Мова C++ розрізняє дві основні форми залежності: залежність типів та залежність виразів.

### Залежні типи (Dependent Types)

Тип вважається залежним, якщо його повна структура або значення визначиться лише після підстановки аргументів шаблону. Відповідно до стандарту, тип є залежним, якщо він постає як:

1. **Безпосередній параметр шаблону:** Сам тип `T`, або параметр-не-тип `N` у списку шаблону `template <typename T, int N>`.
2. **Кваліфіковане ім'я з залежною лівою частиною:** Конструкції вигляду `T::nested_type`, `std::vector<T>::iterator` або `MyTraits<T>::type`.
3. **Составний тип, побудований на основі залежного:** Покажчик `T*`, посилання `T&` або `T&&`, масив залежного розміру або типу `T[N]`, константна модифікація `const T`, а також тип функції `T(*)(int, const T&)`.
4. **Спеціалізація шаблону класу із залежним аргументом:** Тип `std::map<std::string, T>` є залежним, тому що другий параметр залежить від `T`, хоча перший параметр `std::string` є незалежним типом.

### Залежні вирази (Dependent Expressions)

Вираз у коді шаблону вважається залежним від параметрів шаблону за наявності однієї з таких умов:

1. **Його тип є залежним типом:** Змінна `x`, оголошена як `T x`, або вираз `T()`.
2. **Вираз містить залежний оператор:** Операторний вираз `a + b`, якщо принаймні один із операндів належить до залежного типу (наприклад, `t + 5`).
3. **Вираз є некваліфікованим викликом функції з залежним аргументом:** Виклик `process(x)` вважається залежним виразом тоді і тільки тоді, коли принаймні один з переданих аргументів має залежний тип. Якщо всі аргументи мають незалежні типи (наприклад, `process(42)`), то виклик вважається незалежним, навіть якщо він знаходиться всередині шаблону!
4. **Звернення до члена через залежний об'єкт:** Вирази `object.field`, `pointer->method()` або `object.template method<T>()` є залежними, якщо тип `object` або `pointer` є залежним.

### Залежність значень та параметрів-не-типів (NTTP)

У разі використання параметрів шаблону, які є значеннями (non-type template parameters, наприклад `template <int N>`), вираз вважається залежним від значення (value-dependent), якщо його чисельний результат не може бути обчислений під час Фази 1.

До залежних від значення виразів належать:
- Сам параметр `N` або вирази з його участю (`N + 1`, `sizeof(T)`).
- Розмір масиву, параметризований залежною константою (`char buffer[N]`).
- Вирази `alignof(T)` або `noexcept(expr)`, де `expr` містить залежні операції.

## 3. Точки інстанціювання (Point of Instantiation — POI)

Точка інстанціювання (POI) — це фундаментальне поняття мови C++, яке визначає точну позицію в одиниці трансляції, де компілятор створює конкретну спеціалізацію шаблону і запускає Фазу 2 пошуку імен.

### Розміщення POI в одиниці трансляції

Формальні правила розміщення POI зафіксовані у розділі `[temp.point]` стандарту C++:

1. **Для шаблонів функцій:**
   Якщо інстанціювання виклику шаблону функції відбувається неявно, POI розміщується у глобальній області видимості **одразу після найближчого зовнішнього оголошення або визначення функції чи глобального блоку**, який містить виклик. Якщо у файлі є кілька викликів однієї й тієї самої спеціалізації, компілятор створює кілька POI, але в результаті використовується контекст першої з них.
2. **Для шаблонів класів:**
   POI для спеціалізації шаблону класу розміщується **безпосередньо перед оголошенням або визначенням**, у якому вперше знадобився повний тип цього класу (наприклад, при створенні об'єкта `Container<int> c;` або успадкуванні від нього).
3. **Для шаблонних змінних та псевдонімів:**
   POI для змінної-шаблону (C++14) створюється безпосередньо перед першим виразом, де ця змінна використовується як rvalue або lvalue.
4. **Механіка об'єднання контекстів у POI:**
   У точці POI для залежного виклику функції компілятор будує підсумкову множину кандидатів перевантаження, об'єднуючи два незалежні списки:
   - **Список 1:** Усі функції з відповідним ім'ям, які були оголошені у контексті визначення шаблону (Фаза 1).
   - **Список 2:** Усі функції, знайдені за допомогою пошуку за аргументами (ADL) у просторах імен, асоційованих із конкретними типами-аргументами, за умови, що ці функції оголошені **до точки POI включно**.

> ⚠️ **Критичний нюанс:** Звичайний некваліфікований пошук (Non-ADL Lookup) на Фазі 2 НЕ проглядає глобальний простір імен на предмет нових функцій, доданих між оголошенням шаблону та POI. Додаткові перевантаження на Фазі 2 знаходяться ВИКЛЮЧНО через ADL в асоційованих просторах типів-аргументів!

## 4. Правила синтаксичних дисамбігуаторів: `typename` та `template`

Оскільки на Фазі 1 компілятор аналізує текст шаблону без знання конкретної внутрішньої структури `T`, в синтаксисному аналізаторі виникає природна граматична двозначність. Залежні імена можуть позначати типи, значення або шаблони.

### Дисамбігуатор `typename`

Відповідно до стандарту C++, за замовчуванням будь-яке залежне кваліфіковане ім'я (ім'я вигляду `T::name` або `Class<T>::name`) вважається **значенням (змінною, константою або функцією)**. Якщо автор шаблону розраховує на те, що `T::name` є типом, він зобов'язаний поставити перед ним ключове слово `typename`.

```cpp
template <typename T>
struct ContainerWrapper {
    // ПОМИЛКА на Фазі 1 без typename: T::value_type сприймається як статичне поле!
    // T::value_type * ptr; // Парсер трактує це як множення: (T::value_type) * (ptr)

    // КОРЕКТНО:
    typename T::value_type* ptr;
};
```

#### Еволюція застосування `typename` у стандартах C++

У міру розвитку мови комітет C++ поступово спрощував правила, прибираючи вимогу написання `typename` у тих синтаксичних контекстах, де поява значення є граматично неможливою.

| Контекст у коді шаблону | Специфікація C++98 / C++11 | Специфікація C++17 | Специфікація C++20 |
| :--- | :--- | :--- | :--- |
| **Залежна змінна** (`T::type x;`) | Обов'язково `typename` | Обов'язково `typename` | Обов'язково `typename` |
| **Псевдонім типу** (`using A = T::type;`) | Обов'язково `typename` | Обов'язково `typename` | **Непотрібно** (контекст типу) |
| **Тип повернення** (`T::type func();`) | Обов'язково `typename` | Обов'язково `typename` | **Непотрібно** (контекст повернення) |
| **Базовий клас** (`struct D : T::base`) | **Заборонено** `typename` | **Заборонено** `typename` | **Заборонено** `typename` |
| **Оператор new** (`new T::type()`) | Обов'язково `typename` | Обов'язково `typename` | **Непотрібно** (контекст new) |
| **Параметр шаблону** (`template<T::type N>`) | Обов'язково `typename` | Обов'язково `typename` | **Непотрібно** (контекст параметра) |

### Дисамбігуатор `template`

Друга граматична двозначність пов'язана з використанням углових дужок `<` та `>`. За замовчуванням символ `<` після залежного імені об'єкта або покажчика сприймається парсером як бінарний оператор **"менше ніж"**.

Щоб підказати компіляторові на Фазі 1, що ім'я методу є шаблоном функції, перед ним додається ключове слово `template`:

```cpp
template <typename T>
void process_node(T& node) {
    // ПОМИЛКА на Фазі 1 без template:
    // node.get_data<int>(); // Трактується як (node.get_data < int) > ()

    // КОРЕКТНО:
    node.template get_data<int>();
}
```

Синтаксичні варіанти застосування `template`:
- Після крапки: `instance.template method<Args...>()`
- Після стрілка: `pointer->template method<Args...>()`
- Після розрізнення області видимості: `BaseClass<T>::template nested_template<Args...>`
- У шаблонних параметрах-шаблонах: `template <template <typename> class TT>`

## 5. Область видимості параметрів шаблону та перекриття (Shadowing)

Стандарт C++ суворо забороняє повторне оголошення імені параметра шаблону всередині його тіла або списку параметрів.

1. **Заборона перекриття в тілі шаблону:**
   Ім'я параметра шаблону `T` не може бути перекрите внутрішньою змінною чи типом:
   ```cpp
   template <typename T>
   void func() {
       // ПОМИЛКА: Перекриття параметра шаблону T заборонено стандартом!
       // int T = 10; 
   }
   ```
2. **Перекриття у вкладених шаблонах:**
   У разі оголошення вкладеного шаблону класу або методу ім'я внутрішнього параметра `T` мусить відрізнятися від зовнішнього `T`:
   ```cpp
   template <typename T>
   struct Outer {
       // ПОМИЛКА: Внутрішній параметр U не може називатися T
       template <typename U> 
       void inner_method(U val);
   };
   ```

## 6. Зведена таблиця поведінки компіляторів та прапорців

Різні компілятори C++ протягом тривалого часу відрізнялися за ступенем відповідності вимогам двофазного пошуку. Нижче наведено зведену таблицю режимів та прапорців компіляції:

| Назва компілятора | Стандартна поведінка | Суворий режим двофазного пошуку | Наслідки недотримання правил у коді |
| :--- | :--- | :--- | :--- |
| **GCC** (всі версії 3.x+) | Повна відповідність стандарту | Увімкнено завжди за замовчуванням | Помилки компіляції на Фазі 1 при пропущенні `this->` чи `typename`. |
| **Clang** (всі версії) | Повна відповідність стандарту | Увімкнено завжди за замовчуванням | Суворі й детальні повідомлення про пропущені дисамбігуатори. |
| **MSVC 2015 і старші** | Однофазний аналіз (C2) | Відсутній у старих версіях | Мовчки приймає некоректний код, що призводить до поломок на GCC. |
| **MSVC 2017+** | Стандартний двофазний пошук | Прапорець `/permissive-` | Повна діагностика Фази 1 відповідно до вимог ISO C++. |
