# 📋 Інтерфейс shared_ptr і weak_ptr за версіями стандарту

Це довідник до двох типів із `<memory>`: що саме можна викликати, з точними сигнатурами — і з якої версії стандарту кожне з цього існує. Друга половина важить не менше за першу. Те, що сьогодні здається природною частиною типу — масиви, `weak_from_this`, типобезпечний атомарний доступ, — приїхало пізніше за C++11, а дещо з C++11 із мови вже прибрано зовсім. Довідник без позначки версії обманює того, хто збирає проєкт під старіший прапорець.

Скрізь далі `T` — тип, яким параметризовано покажчик, а `element_type` — це `std::remove_extent_t<T>`: для `T = U[]` він дорівнює `U`, для решти — самому `T` (так з C++17).

## Склад заголовка

| сутність | версія | роль |
|---|---|---|
| `std::shared_ptr<T>` | C++11 | власник, зареєстрований у сильному лічильнику |
| `std::weak_ptr<T>` | C++11 | спостерігач; впливає лише на слабкий лічильник |
| `std::make_shared<T>` | C++11 (масиви — C++20) | створення об'єкта разом із блоком, одним виділенням |
| `std::allocate_shared<T>` | C++11 (масиви — C++20) | те саме через власний алокатор |
| `std::make_shared_for_overwrite<T>` | C++20 | без ініціалізації пам'яті |
| `std::allocate_shared_for_overwrite<T>` | C++20 | те саме через алокатор |
| `std::enable_shared_from_this<T>` | C++11 | база, що дає об'єктові доступ до власного блока |
| `std::bad_weak_ptr` | C++11 | виняток: блок є, об'єкта вже нема |
| `std::get_deleter<D>` | C++11 | дістати збережений видаляч, якщо його тип саме `D` |
| `std::owner_less<T>` | C++11 (`owner_less<void>` — C++17) | порівняння за блоком, а не за адресою |
| `std::owner_hash`, `std::owner_equal` | C++26 | те саме для невпорядкованих контейнерів |
| `std::atomic<shared_ptr<T>>`, `std::atomic<weak_ptr<T>>` | C++20 | атомарна змінна-покажчик |
| `std::atomic_load`, `std::atomic_store`, … | C++11 → застаріло C++20 → **прибрано C++26** | старий вільно-функційний атомарний доступ |

## Створення

| виклик | версія | що робить з пам'яттю під елементи |
|---|---|---|
| `make_shared<T>(args…)` | C++11 | один блок пам'яті; об'єкт ініціалізовано `T(args…)` |
| `make_shared<T[]>(n)` | C++20 | масив `n` елементів, кожен ініціалізовано значенням |
| `make_shared<T[]>(n, u)` | C++20 | масив `n` елементів, кожен — копія `u` |
| `make_shared<T[N]>()` / `make_shared<T[N]>(u)` | C++20 | масив сталої довжини |
| `make_shared_for_overwrite<T>()` | C++20 | пам'ять сира: ініціалізація усталена, для тривіальних типів — жодної |
| `allocate_shared<T>(a, args…)` | C++11 | те саме, але пам'ять бере алокатор `a`, і його копія лягає в блок |

```cpp
auto p  = std::make_shared<Session>(sock, timeout);   // Session(sock, timeout)
auto z  = std::make_shared<Stats>();                  // ініціалізовано значенням: нулі
auto raw = std::make_shared_for_overwrite<double[]>(1 << 20);  // 8 МіБ без обнулення
```

Алокатор із `allocate_shared` обслуговує **одну** ділянку — блок разом з об'єктом, — і копія алокатора зберігається в блоці, бо звільняти цю ділянку доведеться вже після смерті об'єкта. Про самі вимоги до такого типу — [власні алокатори](topic:sys-plang-cpp/custom-allocators): це не просто пара «виділити/звільнити», а інтерфейс із перевизначенням типів і копіюванням разом з контейнером.

Жодна з форм `make_shared` не приймає власного видаляча: об'єкт вона будує сама, тож і знищує сама. Потрібен інший спосіб знищення — залишається конструктор із сирого покажчика.

Із тієї ж причини `make_shared` не дістанеться до закритого конструктора: будує вона зсередини себе, а не зсередини класу. Коли клас хоче заборонити створення на стеку, але зберегти одне виділення, конструктор роблять відкритим для власника перепустки — типу, який може створити лише сам клас:

```cpp
class Session {
    struct Key { explicit Key() = default; };      // створити Key може лише Session
public:
    explicit Session(Key, int fd);                 // відкритий, але недосяжний ззовні
    static std::shared_ptr<Session> open(int fd) {
        return std::make_shared<Session>(Key{}, fd);
    }
};
```

## Конструктори shared_ptr

| сигнатура | версія | примітка |
|---|---|---|
| `constexpr shared_ptr() noexcept` | C++11 | порожній; `use_count() == 0` |
| `constexpr shared_ptr(std::nullptr_t) noexcept` | C++11 | те саме, явно |
| `template<class Y> explicit shared_ptr(Y* p)` | C++11 | вимагає коректного `delete p`; з C++17 для `T = U[]` бере `delete[]` |
| `template<class Y, class D> shared_ptr(Y* p, D d)` | C++11 | видаляч `d` — у блок |
| `template<class Y, class D, class A> shared_ptr(Y* p, D d, A a)` | C++11 | ще й алокатор для блока |
| `template<class D> shared_ptr(std::nullptr_t, D d)` | C++11 | порожній покажчик із видалячем |
| `shared_ptr(const shared_ptr& r) noexcept` | C++11 | +1 до сильного лічильника |
| `shared_ptr(shared_ptr&& r) noexcept` | C++11 | лічильника не чіпає; `r` стає порожнім |
| `template<class Y> shared_ptr(const shared_ptr<Y>& r, element_type* p) noexcept` | C++11 | **аліасний**: чужий блок, свій покажчик |
| `template<class Y> shared_ptr(shared_ptr<Y>&& r, element_type* p) noexcept` | C++20 | аліасний із переміщенням |
| `template<class Y> explicit shared_ptr(const weak_ptr<Y>& r)` | C++11 | кидає `std::bad_weak_ptr`, якщо об'єкт помер |
| `template<class Y, class D> shared_ptr(std::unique_ptr<Y, D>&& r)` | C++11 | забирає володіння разом із видалячем |
| `template<class Y> shared_ptr(std::auto_ptr<Y>&& r)` | C++11 … **прибрано C++17** | разом із самим `auto_ptr` |

Конструктор з `unique_ptr` — односторонні двері: [одноосібне володіння](topic:sys-plang-cpp/unique-ptr) можна віддати у спільне, назад — ні, бо решта власників уже могла з'явитися. Видаляч при цьому переїжджає з типу `unique_ptr` у блок і зникає з типу покажчика.

Скидання має дзеркальний набір: `reset()`, `reset(Y* p)`, `reset(Y* p, D d)`, `reset(Y* p, D d, A a)` — усі з C++11.

## Аліасний конструктор

Це єдиний спосіб зробити `shared_ptr`, чий `get()` не збігається з тим, що звільнятиме блок: покажчик показує на одне, а володіє програма іншим.

```cpp
struct Packet { Header hdr; std::vector<std::byte> body; };

auto pkt = std::make_shared<Packet>(/*…*/);
std::shared_ptr<Header> h(pkt, &pkt->hdr);   // володіє Packet, показує на Header
// h.use_count() == 2, h.get() != pkt.get()
```

Дістати `Header`, що не переживе свого пакета, тепер неможливо: доки живий `h`, живий увесь `Packet`. Порожній `r` теж дозволено — вийде покажчик із `use_count() == 0` і ненульовим `get()`, тобто такий, що не володіє нічим.

Форма з переміщенням (C++20) робить те саме без атомарного приросту, але ставить пастку: порядок обчислення аргументів функції не визначений, тож `&pkt->hdr` може бути обчислено **після** того, як `std::move(pkt)` спорожнить `pkt`. Адресу треба взяти окремим рядком:

```cpp
Header* raw = &pkt->hdr;
std::shared_ptr<Header> h(std::move(pkt), raw);   // жодної атомарної операції
```

## Видаляч

Вимоги до `D` короткі: вираз `d(p)` мусить бути коректним, сам `D` — копійовним, а його копіювання й знищення не мають кидати. Тип `D` у типі покажчика не з'являється — він стертий усередині блока ([стирання типу](topic:sf-lang/type-erasure): один інтерфейс замість переліку типів, ціною непрямого виклику).

```cpp
std::shared_ptr<FILE> log(std::fopen("app.log", "a"), &std::fclose);

if (auto* d = std::get_deleter<int(*)(FILE*)>(log))   // C++11
    (void)d;                                          // тип збігся — покажчик на видаляч
```

`get_deleter<D>` повертає `nullptr`, якщо збережений видаляч має інший тип, — звірка точна, без перетворень.

Одна гарантія тут неочевидна й дуже практична: якщо виділення пам'яті під блок не вдалося, конструктор викличе `d(p)` перед тим, як кинути далі. Відповідальність за сирий покажчик він бере в момент виклику, а не після успішного завершення, тож `shared_ptr<FILE>(std::fopen(…), &std::fclose)` не лишить відкритого файлу навіть за `std::bad_alloc`. Це рівно те, що називають гарантією без витоку ([гарантії безпеки винятків](topic:sys-plang-cpp/exception-safety-guarantees) розрізняють три рівні, і цей — найнижчий із придатних).

## Масиви

До C++17 масив доводилося вести вручну, бо усталений видаляч кликав `delete` замість `delete[]`, а індексуватися можна було лише через `get()`:

```cpp
std::shared_ptr<int> old(new int[n], std::default_delete<int[]>());  // C++11
old.get()[7] = 1;

std::shared_ptr<int[]> p(new int[n]);          // C++17: delete[] обрано само
p[7] = 1;                                       // operator[] — C++17
auto q = std::make_shared<int[]>(n);            // C++20
```

Розподіл операцій жорсткий: `operator*` і `operator->` є лише в немасивному `shared_ptr<T>`, `operator[]` — лише в масивному `shared_ptr<T[]>`. Меж масиву `operator[]` не перевіряє.

## Що можна спитати в покажчика

| член | версія | що повертає |
|---|---|---|
| `T* get() const noexcept` | C++11 | збережену адресу; володіння не передає |
| `long use_count() const noexcept` | C++11 | скільки є `shared_ptr`-власників; `0` — порожній |
| `explicit operator bool() const noexcept` | C++11 | чи `get() != nullptr` |
| `bool unique() const` | C++11 → застаріло C++17 → **прибрано C++20** | було `use_count() == 1` |
| `owner_before(const shared_ptr<U>&)` / `(const weak_ptr<U>&)` | C++11 | строгий порядок за **блоком** |
| `size_t owner_hash() const noexcept` | C++26 | геш блока, узгоджений з `owner_equal` |
| `bool owner_equal(…) const noexcept` | C++26 | чи це той самий блок |
| `weak_type` | C++17 | псевдонім `weak_ptr<T>` — щоб не писати тип руками в шаблоні |

`use_count()` у багатопотоковій програмі — знімок, застарілий уже на виході з функції: інший потік міг відпустити або взяти частку в ту саму мить. Саме тому прибрано `unique()`: питання «чи я один» має відповідь, з якої не можна нічого зробити, бо між відповіддю й дією все встигає змінитися. Придатне значення одне — `0`, бо з нуля лічильник не піднімається.

Порівняння `==` і `<=>` (останнє з C++20) дивляться на `get()`. Це не те саме, що тотожність володіння: аліасний конструктор дає два покажчики з одним блоком і різними адресами, а два незалежні блоки можуть зберігати однакову адресу. Питання «це той самий об'єкт обліку?» відповідає окремий набір — `owner_before` і його похідні.

> 🔧 **Навіщо це.** У `weak_ptr` немає ані `get()`, ані звичайних порівнянь — порівнювати нічого, бо об'єкт міг померти. Тому ключем у `std::map` слабке посилання стає лише через `std::owner_less<>` (C++17 — прозорий, змішує `shared_ptr` і `weak_ptr` різних `T`), а ключем у `std::unordered_map` — лише з C++26, коли з'явилися `owner_hash` і `owner_equal`. Практичний виграш C++26 у тому, що шукати в такій таблиці можна за `shared_ptr`, не будуючи з нього тимчасового `weak_ptr`.

## Приведення типів

| функція | версія | що робить |
|---|---|---|
| `static_pointer_cast<T>(sp)` | C++11 (rvalue-форма — C++20) | `static_cast` над збереженою адресою, блок спільний |
| `dynamic_pointer_cast<T>(sp)` | C++11 (rvalue — C++20) | `dynamic_cast`; не вдалося — порожній результат |
| `const_pointer_cast<T>(sp)` | C++11 (rvalue — C++20) | знімає чи додає `const` |
| `reinterpret_pointer_cast<T>(sp)` | C++17 (rvalue — C++20) | `reinterpret_cast` над адресою |

Усі чотири побудовані на аліасному конструкторі, тому результат володіє тим самим, чим і джерело. Перевантаження для rvalue (C++20) переносять частку володіння замість того, щоб додавати ще одну, — з єдиним винятком: невдалий `dynamic_pointer_cast` джерела не спорожнює. Що саме перевіряє `dynamic_cast` у час виконання — [RTTI і dynamic_cast](topic:sys-plang-cpp/rtti-and-dynamic-cast).

## weak_ptr

| член | версія | примітка |
|---|---|---|
| `constexpr weak_ptr() noexcept` | C++11 | порожній; ні на що не показує |
| `template<class Y> weak_ptr(const shared_ptr<Y>& r) noexcept` | C++11 | неявний; +1 до слабкого лічильника |
| `weak_ptr(const weak_ptr&)`, `weak_ptr(weak_ptr&&)` | C++11 | копія й переміщення |
| `shared_ptr<T> lock() const noexcept` | C++11 | атомарна спроба взяти частку; невдача — порожній `shared_ptr` |
| `bool expired() const noexcept` | C++11 | `use_count() == 0`; правдиве «так» остаточне, «ні» — ні |
| `long use_count() const noexcept` | C++11 | **сильних** власників, не слабких |
| `void reset() noexcept`, `void swap(weak_ptr&)` | C++11 | |
| `owner_before`, `owner_hash`, `owner_equal` | C++11 / C++26 | єдиний спосіб порівнювати слабкі посилання |

`operator*`, `operator->` і `get()` тут відсутні свідомо — між перевіркою й зверненням об'єкт міг би померти. Доступ дає або `lock()`, або конструктор `shared_ptr(w)`, і різняться вони лише поведінкою на мертвому об'єкті: перший повертає порожнечу, другий кидає `std::bad_weak_ptr`.

## enable_shared_from_this

| член | версія | примітка |
|---|---|---|
| `shared_ptr<T> shared_from_this()` | C++11 | і `const`-перевантаження, що дає `shared_ptr<const T>` |
| `weak_ptr<T> weak_from_this() noexcept` | C++17 | коли потрібне посилання без вимоги бути живим |

Успадковувати треба **відкрито**; конструктори бази захищені, тож окремо створити її не вийде. Виклик `shared_from_this()` на об'єкті, який ще не під наглядом `shared_ptr`, з C++17 кидає `std::bad_weak_ptr` — до того це була невизначена поведінка, і найчастіше вона мовчала.

## Атомарний доступ

Ідеться про випадок, коли кілька потоків пишуть в **одну змінну** `shared_ptr`. Копіювання власних копій цього не потребує — блок і так атомарний.

| C++11 (застаріло C++20, прибрано C++26) | C++20 |
|---|---|
| `std::atomic_load(&sp)` | `a.load()` |
| `std::atomic_store(&sp, v)` | `a.store(v)` |
| `std::atomic_exchange(&sp, v)` | `a.exchange(v)` |
| `std::atomic_compare_exchange_weak(&sp, &exp, v)` | `a.compare_exchange_weak(exp, v)` |
| `std::atomic_is_lock_free(&sp)` | `a.is_lock_free()` |
| — | `a.wait(old)`, `a.notify_one()`, `a.notify_all()` |

Старий набір прибрали не за красу: він брав звичайну змінну `shared_ptr` за адресою, тож ніщо не заважало комусь поряд звернутися до неї напряму — і атомарність зникала мовчки. `std::atomic<std::shared_ptr<T>>` (як і `std::atomic<std::weak_ptr<T>>`) робить неатомарний доступ неможливим уже в типі. Про сам сенс атомарної операції й порядок пам'яті — [std::atomic і порядок пам'яті](topic:sys-plang-cpp/std-atomic).

Одна цифра тут вирішує все: `is_always_lock_free` для цих спеціалізацій стандарт фіксує як `false`. Реалізації тримають усередині замок, бо атомарно змінити два слова (адресу й блок) і водночас поправити лічильник звичайна машина не вміє. Тому це інструмент для рідкісної заміни покажчика, а не для гарячого циклу.

## Що змінилося після C++11

| зміна | коли |
|---|---|
| масиви `T[]`, `operator[]`, `weak_type`, `reinterpret_pointer_cast`, `weak_from_this`, `owner_less<void>`, правила виведення типу | C++17 |
| конструктор із `auto_ptr` | прибрано C++17 |
| `unique()` | застаріло C++17, прибрано C++20 |
| `make_shared` для масивів, `*_for_overwrite`, аліасний конструктор із переміщенням, rvalue-приведення, `operator<=>`, `atomic<shared_ptr>` | C++20 |
| вільні `atomic_*` над `shared_ptr` | прибрано C++26 (P2869R4) |
| `owner_hash`, `owner_equal` | C++26 (P1901R2) |
| `constexpr` майже на всьому інтерфейсі, включно з `get_deleter` й атомарними спеціалізаціями | C++26 (P3037R6) |

Остання позиція міняє не сигнатуру, а місце застосування: з C++26 спільне володіння працює і в сталих обчисленнях, тобто структуру з `shared_ptr` можна побудувати під час компіляції. Це вимагало окремої роботи саме через стирання типу видаляча — тому папір і йшов до стандарту шість редакцій.
