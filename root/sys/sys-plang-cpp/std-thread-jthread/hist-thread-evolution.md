# 📜 Історія еволюції потоків у C++: від системних API до C++20 std::jthread

Історична еволюція систем багатопотоковості в мовах C та C++ відображає тридцятирічний шлях від низькорівневих платформно-залежних сирих викликів операційної системи до високорівневих RAII-абстракцій та безпечного асинхронного скасування.

---

## 1. Достандартна епоха: C++98 та проблема абстракції бібліотеки

До прийняття стандарту C++11 мова C++ взагалі не мала уявлення про багатопотоковість. Стандарт C++98 описував виконання програми як абстрактний послідовний автомат (single-threaded abstract machine). Операційна система та апаратне забезпечення вже широко використовували багатопотоковість, але з точки зору компілятора C++98 будь-яка модифікація пам'яті іншим потоком вважалася несумісною з оптимізаціями.

Програмістам доводилося використовувати системні API напряму:

- **POSIX Threads (pthreads)** на UNIX-подібних системах (`pthread_create`, `pthread_join`, `pthread_cancel`).
- **Win32 API** на платформах Windows (`CreateThread`, `WaitForSingleObject`, `TerminateThread`).

### Моделі потоків у ядрах операційних систем: M:N проти 1:1

У 1990-х роках точилася гостра архітектурна дискусія щодо відображення користувацьких потоків (user threads) на потоки ядра (kernel threads):

1. **Модель M:N (Green Threads / Fiber Model)**: Багато користувацьких потоків `M` керувалися бібліотекою у просторі користувача і планувалися на малу кількість потоків ядра `N`. Ця модель мала надзвичайно швидке переключення контексту, але створювала катастрофічні проблеми при системних викликах: якщо один зелений потік виконував блокуючий виклик `read()`, увесь потік ядра засинав, паралізуючи решту `M-1` користувацьких потоків.
2. **Модель 1:1 (Native Kernel Threads)**: Кожен об'єкт потоку у програмі відповідає одному дійсному потоку ядра операційної системи. У Linux ця модель остаточно перемогла з появою бібліотеки NPTL (Native POSIX Thread Library) у ядрі 2.6, замінивши застарілу реалізацію LinuxThreads.

У 2005 році Ганс-Й. Бем (Hans-J. Boehm) опублікував фундаментальну працю *"Threads Cannot be Implemented as a Library"*, у якій математично та практично довів: неможливо реалізувати безпечну багатопотоковість виключно у вигляді сторонньої бібліотеки без підтримки з боку мовної моделі пам'яті (Memory Model). Компілятори C++98 агресивно реорганізовували інструкції читання/запису пам'яті, вважаючи, що між ними немає стороннього впливу, що призводило до непередбачуваної поведінки при міжпотоковій взаємодії.

## 2. Стандарт C++11: поява std::thread та дискусії навколо деструктора

Комітет стандартизації C++11 вирішив цю фундаментальну проблему, заклавши формальну модель пам'яті (C++ Memory Model) та стандартний клас `std::thread`. Модель пам'яті чітко визначила поняття гонки даних (data race), атомарних операцій та порядків пам'яті (memory ordering).

Однак при розробці специфікації `std::thread` у комітеті точилися гарячі суперечки між Гербом Саттером (Herb Sutter), Ентоні Вільямсом (Anthony Williams) та Б'ярном Страуструпом (Bjarne Stroustrup) стосовно поведінки деструктора `std::thread::~thread()`.

Розглядалося три можливі варіанти поведінки деструктора при знищенні joinable потоку:

1. **Автоматичний detach()**: Деструктор робить потік фоновим. Цей варіант було відхилено, оскільки він створював катастрофічні витоки пам'яті та помилки Use-After-Free, коли потік звертався до знищених локальних змінних.
2. **Автоматичний join()**: Деструктор чекає завершення потоку. Цей варіант було відхилено, бо якщо деструктор викликався під час розгортання стеку через виняток, блокуючий `join()` міг спричинити вічний дедлок (deadlock), якщо потік чекав на ресурси, які вже були заблоковані батьківським потоком.
3. **Виклик std::terminate()**: Якщо потік залишався joinable, деструктор вважав це порушенням контракту управління ресурсами та аварійно завершував увесь процес.

Комітет C++11 обрав найжорсткіший варіант — виклик `std::terminate()`. Програміст був зобов'язаний явно викликати `.join()` або `.detach()`. 

Якщо між створенням потоку та викликом `.join()` виникав виняток, розгортання стеку знищувало об'єкт `std::thread`, що призводило до неминучого крашу всієї системи в продакшені. Для обходу цієї вади розробники роками створювали власні RAII-обгортки (`thread_guard` або `boost::scoped_thread`).

## 3. Революція C++20: пропозиція P0660 та народження std::jthread

У відповідь на накопичений десятилітній досвід помилок, Ніколай Йосуттіс (Nicolai Josuttis), Льюїс Бейкер (Lewis Baker), Герб Саттер (Herb Sutter) та Ентоні Вільямс подали до комітету ISO C++ пропозицію **P0660R10** (*"Stop Tokens and Joining Thread"*).

Пропозиція P0660 вирішила дві ключові проблеми `std::thread`:

1. **Автоматичне приєднання (Auto-joining):** Деструктор `std::jthread` більше не викликає `std::terminate()`. Замість цього він автоматично надсилає сигнал скасування та викликає `.join()`, блокуючи потік до безпечного завершення виконання.
2. **Стандартизоване кооперативне скасування:** Введення тріади `std::stop_source`, `std::stop_token` та `std::stop_callback` надало мові C++20 єдиний стандартизований механізм передачі сигналів переривання без небезпечного примусового вбивства потоків.

### Основні етапи еволюції конкаренсі в стандартизованому C++

- **C++98 / C++03**: Відсутність моделі пам'яті. Використання сторонніх бібліотек (`pthreads`, Win32 API).
- **C++11**: Офіційна модель пам'яті, `std::thread`, `std::async`, `std::atomic`, `std::mutex`. Створення базового фундаменту.
- **C++14 / C++17**: Введення `std::shared_timed_mutex` та паралельних алгоритмів STL (`std::execution::par`).
- **C++20**: Введення `std::jthread`, `std::stop_token`, арифметика атомарних float, атомарні смарт-поінтери (`std::atomic<std::shared_ptr>`), засуви та бар'єри (`std::latch`, `std::barrier`).
- **C++23**: Розширення монадного оброблення помилок та сумісності з корутинами.

Прийняття `std::jthread` у C++20 стало завершальним етапом трансформації потоків у C++: від небезпечного системного виклику до безпечного RAII-ресурсу з підтримкою кооперативного скасування.
