# 📜 Історія виникнення std::span: від array_view до стандарту C++20

Історія створення `std::span` у стандартній бібліотеці C++ відображає тривалу боротьбу комітету з стандартизації WG21 за поєднання двох фундаментальних, але часто протилежних цілей: забезпечення максимальної продуктивності при роботі з пам'яттю та запобігання фатальним помилкам виходу за межі бувера (англ. *buffer overflow*), які десятиліттями залишалися головним джерелом вразливостей у системному програмному забезпеченні.

## Проблема передачі масивів у C та ранньому C++

У мові C та ранніх версіях C++ (від C++98 до C++11) основним способом передачі послідовностей елементів у функції залишалися сирі вказівники C-стилю разом із окремим аргументом розміру:

```cpp
void process_data(const int* data, std::size_t count);
```

Цей підхід мав кілька критичних недоліків, які ускладнювали написання надійного коду:

1. **Втрата інформації про розмір при розпаді масиву** (англ. *array decay*): при передачі масиву `int arr[10]` у функцію тип масиву автоматично перетворювався на вказівник `int*`, і компілятор втрачав будь-яку можливість перевірити статичні межі.
2. **Розсинхронізація вказівника та довжини**: розробник міг помилково передати вказівник на один масив і розмір іншого, або змістити вказівник `data + 5`, забувши зменшити `count - 5`.
3. **Відсутність єдиного абстрактного інтерфейсу**: функції, що працювали з `std::vector<int>`, не могли безпосередньо приймати статичні масиви `std::array<int, N>` або сирі буфери `int[N]` без написання шаблонних обгорток або передачі пар ітераторів.

Використання пар ітераторів `(first, last)`, запозичене з архітектури STL, розв'язувало проблему для алгоритмів, але створювало надмірне громіздке синтаксичне навантаження при передачі простих буферів пам'яті в системні функції API.

## Зародження концепції в C++ Core Guidelines та бібліотеці GSL

Справжній перелом у підході до безволодісних зрізів пам'яті відбувся у 2015 році, коли Б'ярне Страуструп (англ. *Bjarne Stroustrup*) та Герб Саттер (англ. *Herb Sutter*) презентували на конференції CppCon ініціативу **C++ Core Guidelines**. Головною метою проекту було створення набору правил та низькорівневих типів, які дозволили б писати повністю безпечний щодо пам'яті код без втрати швидкодії.

У рамках цієї ініціативи Ніл Макінтош (англ. *Neil MacIntosh*) з компанії Microsoft розробив базову бібліотеку підтримки засад (англ. *Guideline Support Library*, GSL). Одним із ключових типів GSL став `gsl::span` — легковагова безволодісна обгортка, що об'єднувала вказівник на дані та їх довжину.

Початкова версія `gsl::span` була натхненна класом `array_view`, який використовувався у бібліотеці Microsoft C++ AMP (Accelerated Massive Parallelism) для обробки багатовимірних масивів на графічних процесорах (GPU). Розробники GPU-апаратного забезпечення потребували єдиного абстрактного типу для передачі геометричних сіток та буферів пікселів між центральним процесором (CPU) та відеокартою. Проте `gsl::span` було спрощено та адаптоване для загального системного програмування на CPU, зберігши зосередженість на одновимірних суцільних зрізах.

Варто відзначити, що ідея безволодісних зрізів пам'яті паралельно розвивалася і в інших сучасних мовах системного програмування. У мові Go зрізи (англ. *slices*) `[]T` були вбудовані у систему типів з моменту її створення у 2009 році. У мові Rust концепція `&[T]` (слайс-посилання) стала фундаментальним фундаментом безпеки пам'яті без сміттєзбірника. У платформі .NET компанія Microsoft запровадила `Span<T>` та `ReadOnlySpan<T>` для усунення зайвих алокацій при обробці рядків та мережевих потоків. Це свідчило про те, що екосистема системного програмування сформувала стійкий запит на уніфіковану концепцію безволодісного суцільного зрізу.

## Еволюція пропозицій WG21: від P0122 до C++20

У 2015 році Ніл Макінтош та Стефан Т. Лававей (англ. *Stephan T. Lavavej*) подали до комітету WG21 офіційну пропозицію **P0122R0** під назвою *"span: bounds-safe views for sequence containers"*. Документ пропонував стандартизувати безпечний безволодісний перегляд суцільних послідовностей.

Шлях пропозиції P0122 від першої чернетки до остаточного затвердження в C++20 тривав понад чотири роки і пройшов через вісім ревізій (від R0 до R7). Основні робочі групи комітету — LEWG (Library Evolution Working Group) та LWG (Library Working Group) — провели гарячі дискусії довкола кількох фундаментальних питань дизайну.

### 1. Великий спір про знаковий чи беззнаковий тип індексу

Найбільш запекла дискусія виникла навколо типу, який `std::span` мав використовувати для підрахунку елементів і індексації: `std::size_t` (беззнаковий) чи `std::ptrdiff_t` (знаковий).

Ніл Макінтош та група розробників GSL відстоювали використання знакового типу `std::ptrdiff_t`. Рекомендації C++ Core Guidelines стверджували, що використання беззнакових типів для кількісних величин часто призводить до багів переповнення при відніманні або порівнянні у циклах (наприклад, `for (auto i = s.size() - 1; i >= 0; --i)` викликає нескінченний цикл при `size_t` через переповнення в бік максимального значення).

Проте представники стандартної бібліотеки STL вказували на те, що всі існуючі контейнери C++ (`std::vector`, `std::string`, `std::array`) використовують `std::size_t` для `size()`, `capacity()` та оператора `operator[]`. Використання `ptrdiff_t` у `std::span` створювало б постійний конфлікт типів і вимагало б неявних або явних приведень зі знакових у беззнакові типи при взаємодії з STL.

На засіданні комітету в Празі у лютому 2020 року (останньому перед прийняттям стандарту C++20) було прийнято остаточний компроміс: `std::span` використовує `std::size_t` як `size_type`, зберігши єдність з рештою екосистеми STL.

### 2. Динамічний та статичний розмір (Dynamic vs Static Extent)

Іншим важливим етапом розвитку стандарту стало розділення `std::span` на два режими роботи за допомогою параметру шаблону `Extent`:

- `std::span<T, std::dynamic_extent>` — розмір масиву визначається під час виконання програми (об'єкт зберігає два поля: `ptr` та `size`).
- `std::span<T, N>` — розмір масиву `N` відомий під час компіляції (об'єкт зберігає лише `ptr`, а `size()` повертає константу `N`).

Це рішення дозволило оптимізувати розмір `std::span<T, N>` до розміру одного вказівника (8 байтів на 64-бітних архітектурах), що усунуло будь-які накладні витрати пам'яті порівняно зі звичайним сирим вказівником.

### 3. Роль робочої групи SG14 (High Performance and Games)

Величезний внесок у фінальне шліфування `std::span` зробила підгрупа комітету **SG14**, яка опікується розробкою C++ для ігрової індустрії, фінансових систем з низькою затримкою (HFT) та вбудованих систем. Розробники ігор наполягали на тому, щоб створення зрізів `subspan()`, `first()` та `last()` мало нульову вартість у такті процесора і не робило неявних перевірок у release-збірках, залишаючи перевірку меж для спеціальних режимів налагодження (англ. *debug mode*).

Також робоча група SG14 переконала комітет спростити синтаксис створення піддіапазонів. У ранніх пропозиціях замість `span.subspan(offset, count)` пропонувалася складніша алгебра зрізів з окремими класами-індексаторами. Спрощення до єдиного методу `subspan` з двома перевантаженнями (шаблонним та звичайним) зробило клас надзвичайно зручним для обробки мережевих пакетів та графових вершин у real-time рушіях.

## Прийняття у C++20 та подальша еволюція

У листопаді 2020 року стандарт C++20 офіційно включив заголовочний файл `<span>` із класом `std::span`. Це стало однією з головних системних новацій мови поруч із концептами (Concepts), діапазонами (Ranges) та корутинами (Coroutines).

У наступних стандартах (C++23 та C++26) розвиток суцільних зрізів продовжується:
- У C++23 конструктор `std::span` отримав підтримку ініціалізації з будь-яких діапазонів, що задовольняють концепт `std::ranges::contiguous_range`.
- Розроблено багатовимірний аналог `std::mdspan` для C++23, який поширює ідею безволодісного перегляду на двовимірні, тривимірні та N-вимірні матриці з довільним кроком (stride) та макетами впорядкування елементів у пам'яті (LayoutLeft, LayoutRight, LayoutStride).
- У рамках обговорення **C++ Safe Profiles** (ініціативи Б'ярне Страуструпа та комітету WG21 щодо гарантій безпеки пам'яті у майбутніх версіях C++) `std::span` розглядається як фундаментальний замінник сирих вказівників при роботі з масивами у сучасній ідіоматиці C++.
