# 📋 Довідник інтерфейсів та операцій std::string і std::string_view

Цей довідник систематизує методи, гарантії безпеки, тип-визначення та особливості взаємодії між типами `std::string` та `std::string_view` у стандартах від C++11 до C++23. Взаємодія між цими типами часто стає джерелом тонких помилок інвалідації ітераторів та виходу за межі буфера, тому знання чітких контрактів кожного методу є критичним для проектування C++ програм.

## Систематична порівняльна таблиця операцій

| Категорія | Операція / Метод | `std::string` | `std::string_view` |
| :--- | :--- | :--- | :--- |
| **Пам'ять** | Володіння ресурсом | Так (Heap або SSO) | Ні (вказівник на чужий буфер) |
| | Розмір об'єкта (`sizeof`) | 24–32 байти | 16 байтів (на 64-бітних CPU) |
| | Гарантія `\0` в кінці | **Так** (гарантовано `c_str()`) | **Ні** (лише масив `data()`) |
| **Модифікація** | Зміна довжини / буфера | Так (`append`, `resize`) | Ні (лише зсув вікна) |
| | Модифікація вмісту | Так (`operator[]`, `data()`) | Ні (тільки `const char*`) |
| | Зсув меж підрядка | Створює новий рядок `O(N)` | `remove_prefix`/`remove_suffix` `O(1)` |
| **Пошук** | Пошук підрядка (`find`) | Так (`O(N*M)`) | Так (`O(N*M)`) |
| | Перевірка префікса | C++20 `starts_with()` | C++20 `starts_with()` |
| | Перевірка суфікса | C++20 `ends_with()` | C++20 `ends_with()` |
| | Перевірка наявності | C++23 `contains()` | C++23 `contains()` |
| **Літерали** | Суфікс літерала | `"текст"s` (із `<string>`) | `"текст"sv` (із `<string_view>`) |

## Фундаментальні типи-вкладення (Member Types)

Обидва класи поставляють повний набір стандартних типів для забезпечення сумісності з концептами контейнерів та ітераторів.

Вкладені типи `std::string` визначають як константні, так і неконстантні варіанти:
- `value_type`: `char` (або відповідний тип символу для `basic_string`);
- `pointer` / `const_pointer`: `char*` / `const char*`;
- `reference` / `const_reference`: `char&` / `const char&`;
- `iterator` / `const_iterator`: Random Access / Contiguous Iterator;
- `size_type`: `std::size_t` (зазвичай `uint64_t`);
- `difference_type`: `std::ptrdiff_t` (зазвичай `int64_t`).

Вкладені типи `std::string_view` є **виключно константними**, оскільки погляд принципово забороняє модифікацію чужих байтів:
- `value_type`: `char`;
- `pointer` / `const_pointer`: `const char*` (обидва типи є константними вказівниками!);
- `reference` / `const_reference`: `const char&`;
- `iterator` / `const_iterator`: `const_iterator` (неконстантного ітератора для `string_view` не існує);
- `size_type`: `std::size_t`;
- `difference_type`: `std::ptrdiff_t`.

### Чому конверсія `string_view` -> `string` є explicit

Конструктор `std::string(std::string_view)` зроблено явним (`explicit`), щоб запобігти невидимим алокаціям у купі під час передачі аргументів у функції. Якби конверсія була неявною, виклик функції з параметром `const std::string&` приймав би `std::string_view`, створюючи тимчасовий рядок без відома розробника.

Розглянемо випадок C++23: додано конструктор `std::string_view` з будь-якого `std::ranges::contiguous_range`. Це дозволяє створювати погляди безпосередньо з `std::vector<char>` або `std::span<const char>` без проміжних приведених типів. Водночас конструктор `std::string_view(std::nullptr_t)` було оголошено видаленим (`= delete`), що гарантує помилку компіляції при спробі конструювання погляду з нульового покажчика.

Розглянемо детальніше алгоритм конструювання `std::string_view` з C-рядка `const char* str`. У конструкторі викликається функція `std::char_traits<char>::length(str)`, яка виконує побайтове сканування до символу `\0` (еквівалент `strlen`). Складність конструювання з `const char*` становить `O(N)`. Якщо ж конструювання здійснюється з об'єкта `std::string`, розмір вже відомий заздалегідь із поля `size()`, тому конструювання виконується за постійний час `O(1)`.

## Елементи доступу та безпека меж

Обидва типи надають ідентичний набір методів для доступу до символів: `operator[]`, `at()`, `front()`, `back()`, `data()`. Проте їхні контракти безпеки суттєво відрізняються.

Метод `operator[](size_type pos)` забезпечує прямий доступ за індексом за постійний час `O(1)`. Він не виконує жодних перевірок меж. Якщо індекс `pos >= size()`, виклик викликає невизначену поведінку (UB). Для `std::string` звернення до `s[s.size()]` у C++11 повертає константне посилання на нульовий термінатор `\0`. Для `std::string_view` звернення до `sv[sv.size()]` є прямою помилкою читання за межами масиву.

Метод `at(size_type pos)` виконує явну перевірку індексу. Якщо `pos >= size()`, метод кидає виняток `std::out_of_range`. У критичних до продуктивності циклах рекомендується використовувати `operator[]`, залишаючи `at()` для зовнішніх даних нестабільного походження.

Методи `front()` та `back()` повертають посилання на перший `[0]` та останній `[size() - 1]` символи відповідно. Викликати ці методи для порожнього контейнера (`empty() == true`) заборонено і є невизначеною поведінкою.

Розглянемо різницю у повернених типах методів `data()` між класами. У `std::string` метод `data()` повертає `const char*` у константній контексті та `char*` у неконстантній контексті починаючи з C++17. Це дозволяє використовувати `str.data()` для прямого запису символів у буфер рядка з зовнішніх C-функцій (наприклад, `fread(str.data(), 1, count, file)`). У `std::string_view` метод `data()` **завжди повертає `const char*`**, незалежно від константності об'єкта погляду.

## Методи обрізання та зсуву меж (Window Trimming)

Головною перевагою `std::string_view` над `std::string` є можливість модифікувати межі погляду без зміни самого вихідного тексту.

### Операції `remove_prefix` та `remove_suffix`

Ці методи змінюють внутрішній вказівник та розмір об'єкта `std::string_view` за час `O(1)`:

:::code api-string-view-ops/cpp/operatsii-remove-prefix-ta.cpp

Математичні інваріанти методів зсуву вікна:
- `sv.remove_prefix(n)` виконує: `ptr_ += n; size_ -= n;`
- `sv.remove_suffix(n)` виконує: `size_ -= n;`

⚠️ **Застереження щодо меж:** Виклики `remove_prefix(n)` та `remove_suffix(n)` **не перевіряють** чи `n <= size()`. Якщо `n` перевищує розмір погляду, це викликає undefined behavior (зіпсування вказівника чи негативний розмір).

Для безпечного зсуву меж рекомендується спочатку обчислювати мінімальне значення: `sv.remove_prefix(std::min(n, sv.size()))`. Це гарантує збереження інваріантів безпеки навіть при отриманні некоректної довжини від зовнішнього джерела.

## Оператори літералів `""s` та `""sv`

C++14 та C++17 ввели користувацькі літерали для створення рядків без явного виклику конструкторів.

:::code api-string-view-ops/cpp/operatory-literaliv-s-ta.cpp

Літерал `"text"sv` дозволяє підставляти погляди у `constexpr` вирази та функції розбору тексту на етапі компіляції.

Особливістю суфікса `""sv` є його можливість обробляти рядки з нульовими байтами всередині: `"Hello\0World"sv` створює `std::string_view` з довжиною 11 символів, оскільки довжина строкового літерала визначається розміром масиву на етапі компіляції. На противагу цьому, звичайний конструктор `std::string_view("Hello\0World")` зупиниться на першому `\0` і створить погляд довжиною лише 5 символів.

## Алгоритми пошуку та складність операцій

Обидва типи підтримують повне сімейство методів пошуку підрядків та символів:
- `find(sv, pos = 0)`: повертає індекс першого входження підрядка `sv` починаючи з позиції `pos`.
- `rfind(sv, pos = npos)`: повертає індекс останнього входження (зворотний пошук).
- `find_first_of(sv, pos = 0)`: шукає **будь-який** із символів, що входять до `sv`.
- `find_last_of(sv, pos = npos)`: зворотний пошук будь-якого з символів set.
- `find_first_not_of(sv, pos = 0)`: шукає перший символ, що **не входить** до множини `sv`.
- `find_last_not_of(sv, pos = npos)`: зворотний пошук першого символу поза множиною `sv`.

У разі невдалого пошуку всі методи повертають константу `std::string_view::npos` (яка дорівнює `static_cast<size_type>(-1)` або `std::numeric_limits<size_t>::max()`).

Найгірша алгоритмічна складність методу `find` у реалізаціях стандартної бібліотеки становить `O(N * M)`, де `N` — довжина рядка, а `M` — довжина шуканого підрядка. Проте для пошуку поодиноких символів (`char`) реалізації використовують SIMD-прискорені системні виклики (наприклад, інструкції `memchr` з використанням AVX2/AVX-512), що дає швидкість до десятків гігабайтів на секунду.

Розглянемо методи перевірки префіксів та суфіксів у C++20:
- `sv.starts_with(prefix)`: еквівалентно `sv.substr(0, prefix.size()) == prefix`. Має складність `O(K)`, де K — довжина префікса.
- `sv.ends_with(suffix)`: еквівалентно `sv.size() >= suffix.size() && sv.substr(sv.size() - suffix.size()) == suffix`.
- `sv.contains(sub)` у C++23: еквівалентно `sv.find(sub) != std::string_view::npos`.

## Правила інвалідації ітераторів та посилань

Взаємодія `std::string` та `std::string_view` вимагає розуміння того, коли вказівники всередині `string_view` стають недійсними.

### Події, що інвалідують `std::string_view`

Якщо `std::string_view` посилається на об'єкт `std::string`, погляд **інвалідується** (стає висячим вказівником) у таких випадках:

1. **Модифікація розміру рядка-джерела**: Виклики `push_back`, `append`, `insert`, `erase`, `replace`, `+=` або `resize` можуть спричинить реалокацію буфера в купі.
2. **Переміщення рядка-джерела**: Виклик `std::move(str)` залишає об'єкт `str` у валидному, але невизначеному стані. Буфер переходить до іншого об'єкта, а `string_view` продовжує вказувати на стару (значену) адресу.
3. **SSO Модифікація**: Якщо джерело є малим рядком (SSO) і над ним виконується переміщення `auto s2 = std::move(s1)`, малий буфер копіюється на новий стек. Будь-який `string_view`, що посилався на `s1`, стає висячим!
4. **Знищення об'єкта-джерела**: Вихід `std::string` з області видимості.

:::code api-string-view-ops/cpp/podii-shcho-invaliduiut.cpp

Розглянемо детальніше інвалідацію ітераторів самого `std::string`. При додаванні символів, якщо новий розмір перевищує `capacity()`, відбувається перевиділення буфера у купі. Усі ітератори, вказівники та посилання на елементи рядка інвалідуються. Якщо ж `size() + count <= capacity()`, інвалідуються лише ітератори від точки вставки до кінця рядка. Для `std::string_view` ітератори не інвалідуються ніколи самі по собі, оскільки `string_view` є immutable (незмінним) об'єктом. Інвалідація погляду відбувається лише через зміну або знищення вихідного контейнера-джерела.

### Зведені гарантії методів `data()` та `c_str()`

- `std::string::c_str()`: Повертає `const char*`. Гарантує наявність `\0` на позиції `[size()]`.
- `std::string::data()`: У C++11 і новіших повертає еквівалент `c_str()`. З C++17 повертає `char*` (неконстантний) для модифікації за місцем.
- `std::string_view::data()`: Повертає `const char*`. **НЕ гарантує** наявність `\0` після елемента `[size() - 1]`.

Ці відмінності визначають головне правило безпеки: **ніколи не передавайте `std::string_view::data()` безпосередньо у C-функції, які очікують нуль-термінований C-рядок.**
