# 📜 Еволюція Guidelines Support Library: від маніфесту CppCon 2015 до стандартів ISO

Проблема безпеки роботи з оперативною пам'яттю (англ. *memory safety*) та надійності програмного коду супроводжувала мову C++ із перших днів її створення. Будучи прямою спадкоємицею мови C, C++ зберегла фундаментальний принцип нульових накладних витрат (англ. *zero-overhead principle*): розробник не платить швидкодією чи обсягом пам'яті за абстракції, якими він безпосередньо не користується. Проте зворотним боком цієї безкомпромісної апаратної продуктивності стала надмірна семантична перевантаженість базових конструкцій мови.

У класичному C++ сирий вказівник `T*` одночасно виступав у чотирьох принципово різних ролях:
1. Посилання на один обов'язковий об'єкт у пам'яті (який ніколи не повинен дорівнювати `nullptr`).
2. Опціональний вказівник, відсутність значення в якому кодується нульовою адресою.
3. Початок неперервного масиву елементів довільної довжини, межі якого передаються окремою цілочисельною змінною або взагалі не контролюються.
4. Власницький дескриптор динамічно виділеної пам'яті, за вивільнення якої через `delete` або `free()` відповідає певна функція.

Оскільки компілятор C++ трактував усі ці чотири випадки однаково як тривіальну адресу в пам'яті, він не міг автоматично запобігти типовим катастрофічним збоям: розіменуванню нульового вказівника (англ. *null pointer dereference*), виходу за межі буфера (англ. *buffer overflow*) або витоку ресурсів (англ. *resource leak*).

## 1. Виклики нової епохи та конференція CppCon 2015

На початку 2010-х років тиск на індустрію системного програмування суттєво зріс. Звіти про кібербезпеку від Microsoft, Google Chromium та Apple демонстрували стійку статистику: близько 70% усіх критичних уразливостей у великих програмних продуктах були безпосередньо спричинені помилками керування пам'яттю в коді на C та C++. Поява мов нового покоління, зокрема Rust із її формальною моделлю власності (англ. *ownership model*) та borrow checker на етапі компіляції, змусила лідерів спільноти C++ запропонувати системну відповідь на ці виклики.

Поворотний момент настав у вересні 2015 року на щорічній конференції CppCon у місті Белв'ю (штат Вашингтон, США). Творець мови C++ Б'ярн Страуструп (англ. *Bjarne Stroustrup*) та голова комітету зі стандартизації ISO C++ Герб Саттер (англ. *Herb Sutter*) представили спільну програмну доповідь під назвою «Writing Good C++14».

У цій доповіді було проголошено амбітну мету: зробити сучасний C++ гарантовано типобезпечним (англ. *type-safe*) та ресурсобезпечним (англ. *resource-safe*) без втрати продуктивності та без руйнування сумісності з мільярдами рядків наявного промислового коду.

Для досягнення цієї мети було запропоновано триєдність взаємодоповнюючих компонентів:
1. **C++ Core Guidelines** — структурований відкритий звід практичних правил та інваріантів, розроблений під керівництвом Страуструпа та Саттера на майданчику GitHub.
2. **Статичний аналіз (Static Analysis Tooling)** — спеціалізовані модулі аналізу коду (MSVC C++ Core Check, Clang-Tidy), здатні верифікувати дотримання правил на рівні компілятора.
3. **Guidelines Support Library (GSL)** — компактна заголовна бібліотека, яка надає базові типи-маркери та допоміжні структури для явного вираження контрактів у системі типів.

## 2. Філософія Type-Rich Programming замість змін у синтаксисі

Ключовим стратегічним рішенням авторів ініціативи була відмова від негайного внесення нових ключових слів у синтаксис мови C++.

Внесення змін до мовного стандарту через робочу групу ISO WG21 — процес консервативний і тривалий, який зазвичай займає від трьох до шести років. Додавання нових ключових слів (наприклад, гіпотетичних `notnull` або `owner`) неминуче призвело б до конфліктів імен у величезній кількості існуючих кодових баз, де ці слова вже використовувалися як імена змінних або полів структур.

Натомість автори зробили ставку на парадигму *Type-Rich Programming* (насичене типами програмування):
- Замість неформальних коментарів на кшталт `/* non-null */` або макросів розробник використовує шаблонні типи `gsl::not_null<T*>`.
- Компілятор автоматично використовує механізми перевірки типів, дедукції шаблонів та перевантаження функцій для контролю інваріантів.
- Інструменти статичного аналізу отримують точні семантичні маркери безпосередньо з абстрактного синтаксичного дерева (AST), орієнтуючись на стандартизовані сутності простору імен `gsl::`.
- У фінальному машинному коді після оптимізацій більшість обгорток GSL повністю зникає, гарантуючи абсолютно нульові накладні витрати в runtime.

## 3. Розвиток реалізацій та дивергенція екосистеми

Першу еталонну реалізацію Guidelines Support Library було опубліковано корпорацією Microsoft у вересні 2015 року під ліцензією MIT на GitHub. Керівником проєкту та провідним розробником став інженер Microsoft Ніл Макінтош (англ. *Neil Macintosh*). 

Ця бібліотека була розроблена в тісному тандемі з командою компілятора MSVC і дебютувала у Visual Studio 2015 Update 1. Тоді ж розробники отримали перші попередження групи C++ Core Checkers, які в автоматичному режимі відстежували передачу сирих вказівників без перевірки на `nullptr` або небезпечну адресну арифметику.

У наступних версіях Visual Studio (2017, 2019 та 2022) інтеграція GSL була розширена до повноцінного профілювання безпеки: з'явилися окремі профілі перевірок Lifetime Profile, Bounds Profile та Type Profile. Це дало змогу виявляти складні міжпроцедурні помилки витоків пам'яті безпосередньо в середовищі IDE під час набору коду.

Паралельно виникли інші незалежні реалізації, покликані задовольнити потреби різних сегментів індустрії:

- **Microsoft GSL (ms-gsl)** — офіційна бібліотека від авторів ініціативи. Орієнтована на сучасні компілятори з підтримкою C++14, C++17 та C++20. Вона стала де-факто стандартом для корпоративної розробки під Windows, Linux та macOS.
- **gsl-lite** — надзвичайно гнучка та популярна кросплатформна реалізація, створена нідерландським дослідником Мартіном Муне (англ. *Martin Moene*). Особливістю `gsl-lite` стала підтримка застарілих діалектів аж до C++98/C++03, що дозволило впроваджувати сучасні практики безпеки в консервативних галузях: автомобільній електроніці (AUTOSAR), авіоніці та вбудованих системах реального часу.
- **cpp-gsl від Nick Craig-Wood** та спеціалізовані модулі перевірок у межах проєкту LLVM Clang. Спільнота Clang розробила набір діагностичних правил `cppcoreguidelines-*` для інструмента `clang-tidy`, забезпечивши повну інтеграцію GSL у відкритий тулчейн компіляції GCC та LLVM.

## 4. Дискусії у комітеті ISO WG21 та стандартизація компонентів

Бібліотека GSL замислювалася не лише як допоміжний інструмент, але й як відкритий полігон (англ. *testbed*) для апробації ідей перед їх стандартизацією в ISO C++. Протягом 2015–2020 років кілька ключових компонентів GSL пройшли шлях від експериментальних шаблонів до повноправних елементів стандарту C++.

```
       GSL (2015) ──────────────────────────► ISO C++ Стандарт
       ───────────────────────────────────────────────────────
       gsl::span<T>               ──►  std::span<T> (C++20, P0122R7)
       gsl::byte                  ──►  std::byte (C++17, P0298R3)
       gsl::string_span           ──►  std::string_view (C++17, P0254R2)
       Expects() / Ensures()      ──►  Contracts TS / C++26 (P2900)
       gsl::finally               ──►  std::scope_exit (C++26 / TS)
```

### Батл довкола знаковості: gsl::span проти std::span
Найбільш запекла дискусія в історії стандартизації розгорнулася довкола шаблона `gsl::span<T>`. У початковому варіанті GSL індекс та розмір зрізу пам'яті мали знаковий тип `std::ptrdiff_t` (або спеціальний псевдонім `gsl::index`). Б'ярн Страуструп наполягав, що використання знакових чисел запобігає класичним багам переповнення та нескінченних циклів при зворотній ітерації (`for (auto i = size - 1; i >= 0; --i)`), де беззнаковий `size_t` спричиняє небезпечне зациклення через перехід `0 - 1 = MAX_UINT`.

Однак комітет ISO WG21 прагнув зберегти повну сумісність зі стандартними контейнерами STL (`std::vector`, `std::string`), де тип розміру історично є беззнаковим (`std::size_t`). У результаті в C++20 увійшов `std::span` із типом `size_type = std::size_t`. Проте версія `gsl::span` зберегла строгий контроль меж за замовчуванням, демонструючи фокус GSL саме на захисті від уразливостей.

### Стандартизація std::byte (C++17)
До стандарту C++17 для представлення сирих байтів пам'яті використовували типи `char`, `signed char` або `unsigned char`. Це створювало фундаментальну двозначність: компілятор дозволяв виконувати над байтами масиву арифметичні операції додавання чи множення, сприймаючи їх як числа чи символи. Бібліотека GSL ввела `gsl::byte` як `enum class`, що забороняє математичну арифметику, але дозволяє побітові маски (`&`, `|`, `^`, `~`). У 2017 році цю концепцію було офіційно включено до C++17 у вигляді `std::byte` (пропозиція P0298R3).

### Еволюція контрактного програмування
Конструкції `Expects()` та `Ensures()` у GSL продемонстрували цінність декларативного вираження преумов і постумов функцій. Досвід експлуатації GSL показав, що розробникам потрібна гнучка реакція на порушення контракту: від швидкого аварійного завершення (`std::terminate`) у production-середовищі до кидання винятків у тестових фреймворках або мовчазного збору телеметрії. Ці напрацювання стали фундаментом сучасної робочої групи ISO C++ зі стандартизації мовних контрактів для стандарту C++26.

## 5. Підсумки та місце GSL у сучасному стеку технологій

Guidelines Support Library успішно виконала свою історичну місію і продовжує залишатися фундаментальним інструментом C++ розробника. Навіть сьогодні такі типи, як `gsl::not_null<T*>`, `gsl::owner<T>`, `gsl::narrow` та `gsl::finally`, не мають прямих аналогів у стандартній бібліотеці STL.

GSL довела світовій спільноті розробників, що мова C++ здатна забезпечувати математично строгу безпеку без компромісів щодо продуктивності та без відмови від накопиченого досвіду попередніх десятиліть промислового програмування.
