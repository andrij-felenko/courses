# 📜 Історія виникнення std::filesystem: від Boost до ISO C++17

Цей історичний огляд відстежує шлях еволюції абстракцій файлової системи в мові програмування C++ — від перших експериментальних бібліотечних модулів у складі проекту Boost до офіційного входження стандартного модуля файлової системи у міжнародний стандарт ISO C++17. Розуміння цієї багаторічної передісторії пояснює, чому архітектура сучасних кросплатформових шляхів розділена на синтаксичний та нативний рівні представлення і чому підсистема обробки помилок підтримує два паралельних інтерфейси взаємодії.

## Достандартна ера: хаос платформозалежних системних викликів та обмеження POSIX і Win32

Упродовж перших двох десятиліть існування мови C++ (від стандарту C++98 до виходу стандарту C++14) мова не мала жодного стандартного кросплатформового засобу для маніпуляцій об'єктами файлової системи. Модуль потокового файлового вводу-виводу надавав лише класи для відкриття окремого файлу за його текстовим іменем, але мова не містила жодних засобів для перевірки існування файлу, обходу вмісту каталогів, створення нових каталогів, опитування розміру на диску, читання атрибутів прав доступу чи маніпулювання символьними посиланнями.

У результаті розробники були змушені будувати власний шар ізоляції навколо низькорівневих системних викликів кожної цільової операційної системи. Це спричиняло глибоку фрагментацію кодової бази та створювало величезну кількість прихованих дефектів під час портування програм між Unix-подібними системами та Microsoft Windows.

У системному програмуванні для POSIX-сумісних операційних систем (таких як Linux, macOS, FreeBSD, OpenBSD та Solaris) маніпуляції з каталогами та атрибутами файлів виконувалися через класичні функціональні виклики системної C-бібліотеки. Робота з шляхами базувалася на використанні звичайних масивів символів у кодуванні UTF-8 або локальному системному кодуванні ASCII. У POSIX-моделі файлової системи розділювачем каталогів слугував єдиний символ прямого слешу, а метадані файлів описувалися через індексні дескриптори ядра операційної системи.

Натомість у розробці під операційні системи Microsoft Windows застосовувалася фундаментально інша модель представлення файлів та каталогів. Починаючи з версії Windows NT, операційна система внутрішньо перейшла на кодування двобайтових широких символів. Системні виклики маніпуляції файлами вимагали рядків широких символів та спеціалізованих функцій Win32 API.

Офіційним розділювачем каталогів у системі Windows слугував зворотний слеш, хоча низькорівневі підсистеми Win32 API частково сприймали і прямий слеш. Більше того, синтаксис шляху в Windows включав літери дискових накопичувачів, префікси мережевих ресурсів універсального іменування, а також спеціальні пристроєві префікси для обходу історичного системного обмеження максимальної довжини шляху в 260 символів.

:::tabs
```c
// POSIX C: Отримання розміру файлу та часу модифікації
#include <sys/stat.h>
#include <stdio.h>

long long get_posix_file_size(const char* path) {
    struct stat st;
    if (stat(path, &st) == 0) {
        return (long long)st.st_size;
    }
    return -1;
}
```
```cpp
// Win32 C++: Отримання розміру файлу та часу модифікації
#include <windows.h>
#include <iostream>

long long get_win32_file_size(const wchar_t* path) {
    WIN32_FILE_ATTRIBUTE_DATA data;
    if (GetFileAttributesExW(path, GetFileExInfoStandard, &data)) {
        LARGE_INTEGER size;
        size.HighPart = data.nFileSizeHigh;
        size.LowPart = data.nFileSizeLow;
        return size.QuadPart;
    }
    return -1;
}
```
:::

Така глибока архітектурна розбіжність призводила до того, що будь-який приклад коду для створення каталогу або перевірки існування файлу обростав нескінченними блоками умовної компіляції. Програми регулярно страждали від помилок при виклику відкриття файлу із шляхами, що містили юнікодні символи або некоректні розділювачі каталогів. Якщо програміст передавав у Windows-функцію рядок у кодуванні UTF-8, система інтерпретувала його у застарілому локальному системному кодуванні, що призводило до незворотного пошкодження імен файлів із кирилицею чи ієрогліфами.

Крім того, системний виклик обходу каталогів у POSIX повертав вказівник на буфер структури каталогу, який вимагав ручного порівняння імен файлів із спецсимволами поточного та батьківського каталогів. Виклик обходу у Windows вимагав обов'язкового закриття системного дескриптора, і найменша помилка в управління ресурсами призводила до витоків системних дескрипторів файлів.

## Бібліотека Boost.Filesystem та роль Бемана Доуса

У 2002 році американський інженер та один із найактивніших членів комітету стандартизації C++ Беман Доус (Beman Dawes, 1943–2021) заснував проект Boost.Filesystem. Його головною метою було створення єдиного, безпечного, об'єктно-орієнтованого та кросплатформового інтерфейсу для маніпуляції шляхами, каталогами та метаданими файлової системи.

Беман Доус висунув фундаментальну архітектурну ідею, яка лягла в основу всього сучасного модуля: шлях не є звичайним текстовим рядком символів, а є самостійним доменно-специфічним типом даних з власною граматикою, інваріантами, правилами нормалізації та операціями синтаксичної декомпозиції. Шлях повинен інкапсулювати розбіжності між кодуваннями однобайтових та широких рядків на рівні системної платформи та надавати розробнику безпечні об'єктні методи маніпуляції розширеннями файлів, базовими іменами, кореневими каталогами та батьківськими шляхами.

Перша офіційна версія Boost.Filesystem увійшла до складу релізу бібліотек Boost 1.30 у 2003 році. Бібліотека запропонувала уніфікований клас шляху, вільні операційні функції для роботи з файловою системою та ітератор обходу каталогів.

Протягом 2003–2012 років бібліотека Boost.Filesystem пройшла три великі етапи внутрішньої еволюції та вдосконалення:

1. Перша версія: Формування базової концепції класу шляху, введення фундаментальних операторів додування шляхів та створення перших ітераторів обходу каталогів. На цьому початковому етапі шляхи зберігалися переважно як звичайні текстові рядки.
2. Друга версія: Глибока інтеграція підтримки широких рядків для повноцінної роботи на платформі Windows. Запровадження концепцій кросплатформової конверсії кодувань та підтримка рекурсивного обходу дерев каталогів.
3. Третя версія: Повна переробка системи конверсій кодувань рядків, введення концепції кешованих елементів каталогу для мінімізації повторних системних викликів ядра, а також стабілізація двокамерного API (паралельне надання версій функцій, що кидають винятки, та версій без винятків, що приймають об'єкти кодів помилок).

Комітет стандартизації уважно спостерігав за експлуатацією Boost.Filesystem у промислових проектах розробки ігрових рушіїв, баз даних, геоінформаційних систем та серверного програмного забезпечення. Експеримент Бемана Доуса довів, що запропонована об'єктна модель шляхів та ітераторів є надзвичайно зручною, стійкою до помилок та витримує високі обчислювальні навантаження.

## Проблема портативності та розширення інваріантів шляху

Під час підготовки специфікації розробники зіткнулися з проблемою нелінійного розбору імен у різних файлових системах. У багатьох Unix-подібних системах один і той самий фізичний файл може мати декілька жорстких посилань у різних каталогах диска. Це означає, що порівняння двох текстових шляхів на рівні рядків не дозволяє відповісти на питання, чи вказують вони на один і той самий об'єкт файлової системи.

Для розв'язання цієї проблеми в архітектуру було закладено дві принципово різні категорії операцій над шляхами:

- Синтаксичні операції: виконуються виключно у оперативній пам'яті процесу над текстом шляху без жодного звернення до системних викликів ядра чи дискового накопичувача. До них належать методи виділення розширення, базового імені, батьківського каталогу, а також лексична нормалізація.
- Операції файлової системи: виконують реальні системні виклики ядра операційної системи для перевірки фактичного існування файлу на диску, опитування його розміру, прав доступу, а також створення чи видалення об'єктів.

Такий чіткий розподіл дозволив досягти високої продуктивності програмування. Розробник може виконувати сотні тисяч маніпуляцій над текстовими шляхами у пам'яті процесу абсолютно безкоштовно з точки зору дискових викликів.

Вимоги до продуктивності системного програмного забезпечення спонукали комітет впровадити спеціальні гарантії щодо мінімізації виділення оперативної пам'яті. Конкатенація двох шляхів або виділення розширення файлу оптимізовані таким чином, щоб уникнути зайвого дублювання рядків у динамічній купі.

Операції конкатенації шляхів було розроблено таким чином, щоб автоматично враховувати наявність або відсутність розділювачів на стику рядків. Якщо ліва частина шляху закінчується на розділювач або є кореневим каталогом, оператор додування не додає повторний слеш, що запобігає виникненню подвійних розділювачів у тексті. Якщо ж ліва частина є звичайним каталогом без розділювача на кінці, оператор автоматично вставляє нативний розділювач поточної операційної системи.

Крім того, велика увага приділялася питанню порівняння шляхів. Стандартна бібліотека надає як лексичне порівняння шляхів у пам'яті, так і операційну перевірку еквівалентності файлів на диску. Лексичне порівняння зіставляє текстові компоненти шляху за абеткою без звернення до диска, що є надзвичайно швидким. Операційне порівняння еквівалентності звертається до ядра операційної системи, порівнює індексні дескриптори файлів або унікальні системні ідентифікатори дискового тому, за рахунок чого коректно розпізнає жорсткі та символьні посилання, що вказують на один і той самий об'єкт.

## Еволюція обробки помилок від глобальних змінних до двокамерної моделі

У класичному програмуванні мовою C сигналізування про помилку під час роботи з файловою системою здійснювалося через глобальну змінну системної помилки. Цей підхід мав колосальні недоліки у багатопотокових програмах, де декілька потоків виконання могли одночасно перезаписувати значення помилки. Крім того, глобальний код помилки не містив інформації про те, який саме з кількох вхідних шляхів спричинив збій.

У бібліотеці Boost.Filesystem, а згодом і у стандарті C++17, було закладено двокамерний механізм обробки системних помилок:

- Версія з винятками: при виникненні будь-якої системної помилки функція викидає спеціалізований виняток файлової системи. Цей виняток успадковує базовий клас системної помилки та зберігає не лише код помилки операційної системи, але й обидва текстові шляхи, які брали участь у операції. Це дозволяє сформувати вичерпні повідомлення у системних логах.
- Версія з кодом помилки: приймає посилання на об'єкт коду помилки як вихідний параметр. Ця версія гарантує абсолютну відсутність винятків і повертає код системної помилки безпосередньо у передану змінну. Якщо операція завершилася успішно, код помилки автоматично скидається.

Цей двокамерний підхід дозволив застосовувати модуль файлової системи як у високонавантажених сервісах із суворими вимогами щодо заборони винятків, так і у прикладних програмах із класичною обробкою винятків.

Важливим досягненням стала уніфікація типів кодів помилок. Коди системних помилок операційної системи транспонуються у категорію помилок стандартної бібліотеки, що дозволяє виконувати кросплатформове порівняння кодів помилок із стандартними значеннями (наприклад, відсутність файлу або відмова у доступі).

Розробники серверних систем та вбудованого програмного забезпечення високо оцінили відсутність винятків у версіях функцій із кодом помилки. Передаючи змінну коду помилки у виклики перевірки існування чи створення каталогів, програма повністю уникає витрат часу процесора на алокацію об'єктів винятків та розмотування обчислювального стеку у разі очікуваних відмов.

## Технічний звіт C++ TS 18822 та процес стандартизації

Завдяки колосальному успіху у спільноті розробників, у 2012 році Комітет стандартизації ISO/IEC JTC1/SC22/WG21 прийняв рішення підготувати офіційний Технічний Звіт (Technical Specification) для переносу файлової системи до стандартної бібліотеки C++.

У робочих пропозиціях комітету розгорталися гострі дискусії щодо кількох критичних питань архітектури:
- Конверсія рядкових літералів: Як обробляти строкові літерали у кодуванні UTF-8 на системі Windows, де нативні API приймають лише UTF-16?
- Синтаксичні проти операційних методів: Чи повинен метод перевірки абсолютного шляху робити виклик до файлової системи для перевірки існування диска, чи працювати виключно як синтаксичний аналізатор рядка? Перемогла позиція чистого синтаксичного розбору.
- Обробка символьних посилань: Як захистити програміста від нескінченного зациклення при рекурсивному обході каталогів, що містять циклічні символьні посилання?
- Помилки доступу: Як поводитися ітератору обходу при зустрічі з каталогом, до якого у процесу немає прав читання?

У 2015 році було опубліковано офіційний специфікаційний документ ISO/IEC TS 18822:2015. У цей період модуль поставлявся розробникам у простір імен експериментальної файлової системи у складі відповідного заголовочного файлу. Провідні виробники компіляторів — GCC, Clang та Microsoft Visual C++ — включили підтримку специфікації у свої поставляємі бібліотеки, що дозволило зібрати багатий зворотний зв'язок від індустрії.

На підсумковому засіданні комітету ISO C++ у США восени 2016 року рішенням більшості голосів специфікацію файлової системи було офіційно включено до основного стандарту C++17. Модуль отримав свій остаточний заголовочний файл та простір імен стандартної файлової системи.

Головними архітектурними стовпами стандартизованого модуля файлової системи стали:

1. Строга сепарація синтаксису та операцій диска: Клас шляху виконує суто синтаксичний аналіз текстового рядка у оперативній пам'яті й ніколи не робить операцій дискового вводу-виводу або системних викликів ядра при створенні, модифікації чи декомпозиції.
2. Двокамерний API обробки помилок: Кожна вільна функція файлової системи має дві строго узгоджені перевантажені версії. Перша версія генерує виняток у разі виникнення системного збою. Друга версія приймає вихідний параметр коду помилки, гарантує відсутність винятків та повертає код системної помилки безпосередньо у змінну.
3. Ефективне кешування у елементах каталогу: Під час обходу дерев каталогів ітератором атрибути (розмір файлу, тип об'єкта, час останньої модифікації) зчитуються безпосередньо з системного буфера розбору структури каталогу. Це усунуло потребу у виконанні мільйонів повторних системних викликів під час обходу дискових масивів.

## Дискусії комітету WG21 щодо розділювачів та кодувань

Одною з найскладніших суперечок при розробці специфікації була проблема обробки розділювачів каталогів під час кросплатформової конкатенації шляхів. У системі Windows розділювачем за замовчуванням є зворотний слеш, однак операційна система також визнає прямий слеш у більшості системних викликів. Натомість у Unix-подібних системах символ зворотного слешу не є розділювачем, а вважається звичайним допустимим символом в імені файлу.

Комітет вирішив створити концепцію нативного розділювача. При виклику методу приведення до нативного формата об'єкт шляху замінює усі розділювачі на нативний формат поточної платформи. Крім того, оператор конкатенації гарантує додавання розділювача лише тоді, коли лівий операнд ще не закінчується розділювачем або не є порожнім.

Прийняття рішень у комітеті супроводжувалося вимірюванням продуктивності на реальних навантаженнях. Обхід дерева на сто тисяч файлів із прямим викликом отримання статусу для кожного об'єкта вимагав близько 1200 мілісекунд у системі Linux, тоді як обхід через кешований елемент каталогу завершувався всього за 180 мілісекунд. Це переконало розробників стандартних бібліотек зробити кешування атрибутів обов'язковою вимогою до ітераторів.

Значні зусилля були спрямовані на забезпечення сумісності з розпаралелюванням обчислень. Обхід дерев каталогів за допомогою рекурсивних ітераторів був спроектований таким чином, щоб декілька потоків виконання могли одночасно сканувати незалежні гілки файлової системи без виникнення взаємних блокувань або гонок за дані.

Окремим предметом полеміки була поведінка ітератора обходу при виявленні циклічних символьних посилань на каталоги. Без належної обробки рекурсивний ітератор заходив у нескінченний цикл, що викликало вичерпання глибини стеку викликів або переповнення системної таблиці відкритих файлових дескрипторів. У результаті комітет впровадив прапорці налаштування обходу, які за замовчуванням забороняють автоматичне слідування за символьними посиланнями на каталоги, вимагаючи явного підтвердження від розробника.

## Еволюція та покращення у C++20 та C++23

Після офіційного релізу C++17 стандартизація модуля файлової системи не зупинилася. Комітет продовжив удосконалювати сумісність файлової системи з новими можливостями мови:

- Явна підтримка кодування UTF-8 у C++20: Введення нового базового типу UTF-8 символу та відповідного рядка дозволило створити спеціальний метод перетворення та фабричну функцію. Це остаточно усунуло невизначеність щодо кодування рядків у системі Windows, зробивши обробку юнікодних шляхів абсолютно прозорою та типізованою.
- Інтеграція з хронометрією у C++20: Тип часу файлової системи було стандартизовано як точний псевдонім файлового годинника. З'явилися офіційні функції конверсії часу, що дозволило легко перетворювати час модифікації файлу у календарні дати системного годинника.
- Форматування рядків у C++23: Клас шляху отримав повну підтримку бібліотеки форматування рядків та функцій друку, що дозволяє друкувати об'єкти шляхів безпосередньо через стандартний виклик друку.

Завдяки 15 рокам інтенсивних польових випробувань у бібліотеці Boost та ретельній шліфовці в комітеті ISO C++, сучасний модуль файлової системи є одним із найзріліших, найбезпечніших та найефективніших модулів стандартної бібліотеки C++.
