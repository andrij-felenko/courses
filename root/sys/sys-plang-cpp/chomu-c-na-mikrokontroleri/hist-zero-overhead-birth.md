# 📜 Народження принципу нульових накладних витрат: ISO TR 18015 та суперечки довкола C++ в embedded

У 1990-х роках інженери вбудованих систем масово відмовлялися від переходу з мови C на C++, побоюючись непередбачуваного роздування машинного коду та втрати контролю над обмеженою пам'яттю мікроконтролерів. Щоб зрозуміти, чому сучасний C++ став стандартом для критичних вбудованих застосунків, необхідно простежити конфлікт між ініціативою спрощеного діалекту Embedded C++ та фундаментальною роботою комітету стандартизації ISO над технічним звітом щодо продуктивності.

## Контекст 1990-х: апаратні обмеження та страх перед компілятором

У середині 1990-х років типовий 8-бітний або 16-бітний мікроконтролер (такі як Motorola 68HC11, Intel 8051 або Hitachi H8) мав від кількох сотень байтів до пари кілобайтів оперативної пам'яті (RAM) та 16–64 КіБ постійної пам'яті програм (ROM/Flash). Кожен збережений байт і кожен зекономлений машинний такт визначали, чи поміститься прошивка в дешеву мікросхему масового виробництва.

Мова C повністю домінувала у цій галузі. Компілятори C генерували передбачуваний машинний код: кожна функція перетворювалася на фіксовану послідовність інструкцій, доступ до регістрів виконувався через пряме розіменування вказівників, а стек витрачався лише на збереження аргументів та локальних змінних.

Поява C++ у версіях початку 1990-х років (стандартизованого згодом як C++98) викликала серйозне занепокоєння серед розробників вбудованого програмного забезпечення. Ранні компілятори C++ часто грішили недосконалими механізмами оптимізації. Додавання у код одного віртуального методу несподівано підтягувало в прошивку дескриптори інформації про типи, обробка винятків вимагала масивних статичних таблиць розгортання стеку, а неакуратне створення копій тимчасових об'єктів переповнювало мініатюрну пам'ять мікроконтролера.

Серед розробників апаратури сформувався стійкий міф: «C++ надто важкий для систем реального часу та мікроконтролерів».

## Ініціатива Embedded C++ (EC++): спроба ампутації мови

У 1996 році консорціум провідних японських виробників напівпровідників — серед яких були Hitachi, NEC, Fujitsu та Toshiba — вирішив створити власний стандарт для вбудованих систем під назвою **Embedded C++** (скорочено EC++).

Метою консорціуму було усунення всіх конструкцій мови, які потенційно могли спричинити накладні витрати пам'яті або втрату детермінізму в часі виконання. Під скальпель розробників EC++ потрапили:

- **Винятки (`try`/`catch`/`throw`):** через великі таблиці розгортання стеку та недетермінований час передачі керування.
- **Інформація про типи часу виконання (RTTI, `typeid`, `dynamic_cast`):** через накладні витрати на структури опису типів у ROM.
- **Множинне та віртуальне успадкування:** через складні таблиці зсувів у вказівниках на таблиці віртуальних методів (`vtable`).
- **Простори імен (`namespace`):** консорціум вважав їх зайвим ускладненням для компілятора та таблиці символів.
- **Шаблони (`template`):** розробники EC++ побоювалися неконтрольованого дублювання коду (англ. *code bloat*) при інстанціюванні для різних типів.
- **Нові оператори приведення типів (`static_cast`, `reinterpret_cast` тощо):** як непотрібна синтаксична надлишковість.

Консорціум EC++ оголосив свій діалект ідеальним рішенням для мікроконтролерів. Виробники компіляторів (зокрема IAR Systems, Keil та Green Hills) почали постачати окремі режими збірки для EC++.

## Відповідь Б'ярна Страуструпа та провал EC++

Творець мови C++ Б'ярн Страуструп (Bjarne Stroustrup) виступив із різкою та послідовною критикою ініціативи Embedded C++. Він зазначив, що розробники EC++ зробили фундаментальну помилку: вони видалили з мови не просто високорівневі надбудови, а інструменти, які робили код надійним і водночас безкоштовним з точки зору швидкодії.

Видалення просторів імен змусило інженерів повертатися до небезпечних глобальних префіксів у стилі C. Але найбільшим ударом стала заборона шаблонів. За відсутності шаблонів розробники не могли створювати типізовані абстракції апаратних регістрів, типобезпечні кільцеві буфери чи математичні перетворення без ручного копіювання коду або повернення до нетипізованих макросів препроцесора (`#define`) та вказівників `void*`.

Страуструп довів, що відмова від шаблонів не зменшує розмір програми, а збільшує його: замість одного скомпільованого й оптимізованого шаблонного класу інженери писали громіздкі дублікати функцій під кожен тип даних.

До початку 2000-х років стало очевидно, що EC++ зайшов у глухий кут. Проект фактично помер: виробники перестали розвивати діалект, а провідні постачальники компіляторів повернулися до повного стандарту ISO C++.

## Технічний звіт ISO/IEC TR 18015: наукова фіксація нульових витрат

Щоб остаточно розвіяти міфи про некерованість C++ у вбудованих системах, робоча група стандартизації ISO WG21 сформувала спеціальну підгрупу для вивчення продуктивності. Результатом багаторічної роботи став фундаментальний документ — **ISO/IEC TR 18015: Technical Report on C++ Performance**, опублікований у 2004 році.

Звіт складався з докладних експериментальних вимірювань, аналізу згенерованого асемблерного коду та чіткої математичної моделі витрат кожної конструкції мови.

Ключові висновки звіту ISO TR 18015 закріпили принципи створення прошивок:

1. **Модель пам'яті класів:** структура або клас мови C++ без віртуальних методів має точно такий самий розмір, вирівнювання та схему розташування полів у пам'яті (англ. *memory layout*), як і еквівалентна структура мови C (`struct`).
2. **Виклики методів:** виклик невиртуального методу об'єкта транслюється в пряму інструкцію переходу процесора (`bl` або `call`), де адреса об'єкта передається через перший регістр (як неявний параметр `this`). Накладні витрати на виклик дорівнюють нулю порівняно з передачею вказівника на структуру у звичайну C-функцію.
3. **Вбудовування коду (inlining):** оптимізатори C++ здатні повністю ліквідувати виклики дрібних функцій доступу (гетерів, сетерів, операторів бітових масок), підставляючи машинний код безпосередньо в місце виклику. Це робить високорівневі абстракції над регістрами MMIO настільки ж швидкими, як і макроси C.
4. **Шаблони як генератори безкоштовного коду:** шаблони інстанціюються під час компіляції. Якщо шаблон параметризований константною апаратною адресою (наприклад, адресою базового регістра таймера), компілятор підставляє значення безпосередньо в машинну команду завантаження, повністю усуваючи необхідність зберігати вказівники у змінних RAM.
5. **Локалізація витрат винятків та RTTI:** звіт чітко розмежував конструкції з фіксованою ціною від конструкцій із динамічним рантаймом. Було показано, що при вимкненні винятків (`-fno-exceptions`) та RTTI (`-fno-rtti`) компілятор генерує чистий код, у якому немає жодного байта прихованих накладних витрат.

## Спадщина та сучасний консенсус

Робота над ISO TR 18015 заклала фундамент того, як мова C++ розвивалася у наступні двадцять років. Починаючи зі стандарту C++11 і далі в C++14, C++17, C++20 та C++23, мова послідовно розширювала засоби обчислень на етапі компіляції (`constexpr`, `consteval`, `constinit`), додавала типобезпечні варіативні шаблони, концепції (Concepts) та бібліотеки для роботи з пам'яттю без динамічної купи (`std::span`, `std::string_view`).

Принцип нульових накладних витрат перестав бути просто побажанням — він став головним інженерним критерієм: розробник на мікроконтролері платить ресурсами процесора та пам'яті лише за те, що він безпосередньо використовує.
