# 📜 Від шести операторів до тричленного порядку

Історія порівняння об'єктів у C++ — це двадцятирічна боротьба між виразністю мови та лавиноподібним розростанням однакового коду. До виходу стандарту C++20 створення навіть найпростішого типу, який можна покласти в асоціативний контейнер або перевірити на рівність, вимагало від програміста написання шести окремих функцій-операторів: `==`, `!=`, `<`, `<=`, `>`, `>=`. Якщо ж тип мав взаємодіяти з іншим типом (наприклад, власний клас рядка з літералом `const char*`), кількість необхідних перевантажень зростала до вісімнадцяти.

## Проблема комбінаторного вибуху та спадщина Степанова

Коли Александр Степанов (англ. *Alexander Stepanov*) на початку 1990-х років проектував Standard Template Library (STL), він заклав у її фундамент концепцію строгого слабкого порядку (англ. *Strict Weak Ordering*). Алгоритми впорядкування та асоціативні контейнери — такі як `std::sort`, `std::set` та `std::map` — вимагали для своєї роботи лише одну-єдину операцію: `operator<`.

З погляду математичної мінімалістичності це здавалося елегантним:
- Відношення рівності елементів `a` та `b` можна було виразити через еквівалентність: якщо `!(a < b)` та `!(b < a)`, то елементи вважаються рівними для цілей пошуку в бінарному дереві.
- Відношення більшості `a > b` виражалося як `b < a`.
- Нестрогі нерівності `<=` та `>=` отримувалися інверсією результату протилежного оператора.

Проте за межами внутрішніх алгоритмів STL користувачам бібліотек був потрібен повноцінний набір операцій. Програміст, який створив власний тип і реалізував для нього лише `operator<` та `operator==`, швидко стикався з тим, що вираз `a != b` або `a <= b` викликав помилку компіляції. Люди очікували природного синтаксису для всіх шести реляційних операторів.

Ситуація ставала критичною у випадках гетерогенних (мішаних) порівнянь. Уявімо клас рядка `MyString`, який повинен ефективно порівнюватися як із власними екземплярами, так і з сирими C-рядками `const char*` без виділення тимчасової динамічної пам'яті:

```cpp
// 1. Порівняння двох об'єктів MyString (6 операторів)
bool operator==(const MyString&, const MyString&);
bool operator!=(const MyString&, const MyString&);
bool operator< (const MyString&, const MyString&);
bool operator<=(const MyString&, const MyString&);
bool operator> (const MyString&, const MyString&);
bool operator>=(const MyString&, const MyString&);

// 2. Порівняння MyString з const char* (6 операторів)
bool operator==(const MyString&, const char*);
bool operator!=(const MyString&, const char*);
bool operator< (const MyString&, const char*);
bool operator<=(const MyString&, const char*);
bool operator> (const MyString&, const char*);
bool operator>=(const MyString&, const char*);

// 3. Зворотне порівняння const char* з MyString (ще 6 операторів!)
bool operator==(const char*, const MyString&);
bool operator!=(const char*, const MyString&);
bool operator< (const char*, const MyString&);
bool operator<=(const char*, const MyString&);
bool operator> (const char*, const MyString&);
bool operator>=(const char*, const MyString&);
```

Вісімнадцять окремих сигнатур на один клас. Якщо типи підтримували ще й третій сумісний формат (наприклад, числовий тип із різними розмірами розрядності `FixedPoint<16>` та `FixedPoint<32>`), кількість необхідних функцій зростала пропорційно `6 · N²`. На практиці це призводило до копіювання фрагментів коду, механічних помилок (де у тілі `operator>=` випадково забували знак рівності) та значного збільшення часу синтаксичного аналізу файлів заголовків.

## Пастка шаблонної допомоги C++98: крах std::rel_ops

У першому міжнародному стандарті ISO/IEC 14882:1998 комітет спробував вирішити проблему механічно за допомогою узагальнених шаблонів. У заголовок `<utility>` додали спеціальний допоміжний простір імен `std::rel_ops`. Він містив чотири шаблони операторів, які автоматично виражали відсутні операції через користувацькі `==` та `<`:

```cpp
namespace std::rel_ops {
    template <class T>
    bool operator!=(const T& x, const T& y) { return !(x == y); }

    template <class T>
    bool operator>(const T& x, const T& y) { return y < x; }

    template <class T>
    bool operator<=(const T& x, const T& y) { return !(y < x); }

    template <class T>
    bool operator>=(const T& x, const T& y) { return !(x < y); }
}
```

Задум авторів стандарту C++98 здавався простим: розробникові типу достатньо було надати дві базові операції, після чого в коді клієнта писалося `using namespace std::rel_ops;`, і всі шість операторів ставали доступними. Проте на практиці цей механізм породив більше проблем, ніж розв'язав, і швидко перетворився на антипатерн:

1. **Глобальне засмічення простору імен.** Щойно директива `using namespace std::rel_ops;` потрапляла в область видимості (або, що ще гірше, у файл заголовка сторонньої бібліотеки), ці жадібні невимушені шаблони починали підставлятися для абсолютно *всіх* типів програми, включно з тими, автори яких навмисно не бажали надавати операції порядку.
2. **Конфлікти з пошуком ADL (Argument-Dependent Lookup).** Якщо сторонній тип уже мав власний оптимізований `operator!=`, підключення `rel_ops` часто призводило до фатальної неоднозначності виклику (`ambiguous overload`). Компілятор бачив двох однакових кандидатів і відмовлявся продовжувати збірку.
3. **Повна відсутність гетерогенності.** Шаблони `rel_ops` були зафіксовані на однорідних парах `(const T&, const T&)`. Для мішаних операцій на кшталт `MyString == const char*` вони не давали жодного результату.
4. **Хибна семантика для часткових порядків.** Логічне правило `x <= y ≡ !(y < x)` є математично істинним лише для повних лінійних порядків. Для чисел із плаваючою комою існування нечислових значень (`NaN` — Not-a-Number) повністю руйнує цю еквівалентність. За стандартом IEEE 754 будь-яке порівняння з `NaN` повертає `false` (як `NaN < 5.0`, так і `5.0 < NaN`). Відповідно, шаблон `rel_ops::operator<=` обчислював `!(5.0 < NaN)`, що давало `true` — грубе порушення вимог апаратного стандарту обчислень.

Через ці фундаментальні вади використання `std::rel_ops` було заборонено в більшості корпоративних стандартів кодування, а в стандарті C++20 цей простір імен отримав офіційний статус застарілого (`deprecated`).

## Досвід інших мов і перші пропозиції в комітеті

Тим часом в інших мовах програмування концепція тричленного порівняння (англ. *three-way comparison*) існувала десятиліттями:
- У мові **Perl 5** ще у 1994 році Ларрі Волл (англ. *Larry Wall*) запровадив символьний оператор `<=>` для порівняння чисел та ключове слово `cmp` для рядків. Через характерний зовнішній вигляд конструкцію `<=>` у спільноті розробників прозвали «космічним кораблем» (англ. *spaceship operator*) за схожість із силуетом винищувача Tie Fighter із кіновсесвіту «Зоряних воєн».
- Мови **Ruby**, **Groovy** та **PHP** згодом запозичили цей самий символ для операцій, що повертають `-1`, `0` або `1`.
- Мова **Rust** пішла шляхом суворої типізації й замість чисел запропонувала перелічувані типи `Ordering::Less`, `Ordering::Equal`, `Ordering::Greater` та два трейти: `PartialOrd` і `Ord`.
- У мові **C** стандартна функція `strcmp` та компаратори для `qsort` завжди повертали знакове ціле число (`int`), де знак результату вказував на відношення між елементами. Проте ціле число втрачало семантичну інформацію: воно не розрізняло, чи нульовий результат означає повну тотожність об'єктів, чи лише їхню еквівалентність за певним ключем, чи взагалі неможливість порівняння.

У 2013 році Б'ярн Страуструп (дан. *Bjarne Stroustrup*) опублікував документ **N3628: Default comparisons**, де запропонував дозволити компілятору генерувати `operator==` та `operator<` автоматично через почленне порівняння (`= default`). Проте пропозиція викликала гострі суперечки в робочій групі Evolution Working Group (EWG):
- Як контролювати випадки, коли структури містять поля з плаваючою комою, де потрібен частковий порядок?
- Що робити з покажчиками на виділену динамічну пам'ять, де почленне порівняння порівнює числові адреси в пам'яті, а не сам корисний вміст?
- Чому програміст все ще має окремо оголошувати решту операторів?

Лоуренс Кроул (англ. *Lawrence Crowl*) у серії фундаментальних документів 2014–2015 років (**N4114**, **N4231**) формалізував математичні категорії порядків у застосуванні до типізації C++. Він переконливо довів, що мові потрібен багатий тип результату, який передає математичну природу відношення, а не простий `bool` чи примітивний `int`.

## Прорив: пропозиція P0515 Герба Саттера

У листопаді 2017 року на засіданні комітету стандартизації в Альбукерке Герб Саттер (англ. *Herb Sutter*), Єнс Маурер (нім. *Jens Maurer*) та Волтер Браун (англ. *Walter E. Brown*) представили документ **P0515R0: Consistent Comparisons**.

Автори запропонували цілісну архітектурну модель:
1. Запровадити в синтаксис C++ новий оператор тричленного порівняння `<=>` (Spaceship Operator).
2. Замість сирих цілих чисел повертати об'єкти спеціальних типів категорій із заголовка `<compare>`: `std::strong_ordering`, `std::weak_ordering`, `std::partial_ordering`.
3. Дозволити компілятору самостійно генерувати оператор через ключове слово `= default`, здійснюючи послідовне почленне порівняння базових класів та нестатичних полів у порядку їхнього оголошення.
4. Модифікувати правила розв'язання перевантажень (англ. *overload resolution*): замість генерації десятків фіктивних функцій компілятор під час аналізу виразу `a < b` синтезує так званих **переписаних кандидатів** (англ. *rewritten candidates*), перетворюючи вираз на `(a <=> b) < 0`. Для зворотних операцій на кшталт `b > a` синтезуються **перевернуті кандидати** (англ. *reversed candidates*), тобто `0 < (a <=> b)`.

Це рішення стало справжнім проривом. Одного рядка `auto operator<=>(const Point&) const = default;` виявилося достатньо, щоб клас отримав повний комплект із усіх 6 операцій порівняння з бездоганною математичною семантикою та симетричною підтримкою гетерогенних типів.

## Велика дискусія: поділ рівності та порядку (P1185)

У первісній редакції P0515 передбачалося, що оператор `==` також синтезуватиметься через оператор `<=>`: компілятор мав переписувати вираз `a == b` у виклик `(a <=> b) == 0`. Проте це рішення несло в собі приховану катастрофу швидкодії, яку швидко виявили розробники стандартних бібліотек та високонавантажених систем.

Для таких фундаментальних типів, як рядки (`std::string`), динамічні вектори (`std::vector`) або деревоподібні структури даних, алгоритм перевірки на рівність та алгоритм лексикографічного впорядкування мають принципово різну часову складність:
- **Перевірка рівності (`==`):** спершу виконується швидке порівняння розмірів `size()`. Якщо довжини двох рядків відрізняються, операція завершується за один такт процесора `O(1)`, не звертаючись до купи (heap) та не навантажуючи кеш-пам'ять ЦП.
- **Лексикографічний порядок (`<=>`):** оператор **не має права** робити ранній вихід за довжиною! Рядок `"z"` довжини 1 стоїть в алфавітному порядку пізніше за рядок `"aaaaa"` довжини 5. Тому оператор `<=>` змушений завжди виконувати побайтне сканування префікса через `memcmp` за лінійний час `O(N)`, і лише при збігу префіксів дивитися на різницю довжин як на тайбрейкер.

Якби перевірка `a == b` викликала `(a <=> b) == 0`, будь-яке порівняння двох рядків різної довжини сповільнилося б у сотні разів і призводило б до небажаного кеш-промаху під час читання далеких областей пам'яті.

У жовтні 2018 року на зустрічі в Сан-Дієго Герб Саттер і Баррі Ревзін (англ. *Barry Revzin*) подали виправний папір **P1185R2: A proposal to separate == and <=>**. Вони довели необхідність архітектурного розділення рівності та порядку:
- Операція `==` повинна обслуговуватися власним оператором `operator==`, а нерівність `!=` переписується як `!(a == b)`.
- Операції відносного порядку `<`, `<=`, `>`, `>=` обслуговуються оператором `operator<=>`.
- Синтаксична конструкція `operator<=> = default` зобов'язана автоматично генерувати окремий прихований `operator== = default`, який виконує пряме почленне тестування на рівність найшвидшим шляхом.

Цей поділ дозволив поєднати максимальну продуктивність детермінованих перевірок рівності з компактністю та виразністю тричленного порівняння.

## Фіналізація в C++20 і шліфування правил

Остаточне узгодження деталей відбулося в серії документів 2019–2020 років:
- **P1614R2: The Mothership has Landed** — оновлення всіх типів стандартної бібліотеки (ітераторів, кортежів `std::tuple`, контейнерів, розумних вказівників `std::unique_ptr` та `std::shared_ptr`) для підтримки `operator<=>`.
- **P1630R1: Spaceship cleanup** — усунення неоднозначностей під час розв'язання перевантажень для класів із неявними перетвореннями типів, а також захист від рекурсивного переписування викликів у коді, що мігрував із C++17.
- **P1946R0: Allow defaulting comparisons by value** — дозвіл оголошувати `= default` для параметрів, що передаються за значенням (для дрібних типів на кшталт `std::complex` або ітераторів покажчикового типу).

Тричленне порівняння стало одним із найуспішніших нововведень стандарту C++20. Воно скоротило обсяг шаблонного boilerplate-коду в призначених для користувача типах на 80%, повністю усунуло випадкові розбіжності в поведінці операторів `<` та `==` і заклало надійний фундамент для концептів бібліотеки діапазонів (`std::ranges`).
