# 📜 Еволюція варіативності в C++: від va_list до виразів згортки

У ранніх версіях мов C та C++ створення функцій із довільною кількістю аргументів спиралося виключно на механізм мови C — макроси заголовка `<cstdarg>` (`va_list`, `va_start`, `va_arg`, `va_end`). Ця архітектура була створена під низькорівневу модель передачі аргументів через стек процесора в архітектурах 1970-х років. Механізм вимагав наявності хоча б одного фіксованого аргументу (як-от форматний рядок у `printf`), за адресою якого макрос `va_start` визначав початкове зміщення на стеку або в масиві збережених регістрів.

Компілятор повністю стирав інформацію про типи наступних аргументів. Під час виконання функція сліпо довіряла форматному рядку: якщо у `printf` передавали специфікатор `%s`, а у стек поклали 64-бітне ціле число, функція трактувала це число як віртуальну адресу пам'яті й намагалася прочитати байти за адресою, що неминуче спричиняло аварійне завершення процесу через збій сегментації (Segmentation Fault).

Ба більше, двійковий інтерфейс викликів (ABI) сучасних процесорних архітектур суттєво ускладнив роботу `va_list`. В архітектурі x86-64 за стандартом System V ABI перші шість цілочисельних аргументів передаються через регістри загального призначення (`%rdi`, `%rsi`, `%rdx`, `%rcx`, `%r8`, `%r9`), а перші вісім аргументів із рухомою комою — через регістри `%xmm0`–`%xmm7`. Регістр `%rax` (або `%al`) сигналізує точну кількість використаних векторних регістрів.

Щоб макрос `va_arg` міг послідовно читати аргументи, компілятор був змушений генерувати спеціальний пролог функції, який зберігав усі регістри передачі аргументів у спеціальну область пам'яті на стеку (англ. *register save area*). Об'єкти C++ з нетривіальними конструкторами або деструкторами (як-от `std::string` чи `std::vector`) узагалі не дозволялося передавати у варіативні функції C: стандарт класифікував це як безумовну непередбачувану поведінку (Undefined Behavior), оскільки виклик за правилами мови C не викликав конструкторів копіювання при передачі й деструкторів при завершенні виклику.

## Списки типів Александреску та метапрограмування C++98

Коли у 1990-х роках мова C++ почала розвивати парадигму узагальненого програмування, з'явилася гостра потреба створювати безпечні гетерогенні контейнери (кортежі `tuple`), фабричні обгортки (`make_shared`, `make_unique`), диспетчери подій та функціональні об'єкти (`bind`, `function`). Проте система шаблонів C++98 дозволяла лише фіксовану кількість параметрів для кожного визначення: `template <typename T1, typename T2, typename T3>`. Будь-яка узагальнена структура опинялася перед жорстким синтаксичним бар'єром.

У 2001 році Андрей Александреску (Andrei Alexandrescu) у праці «Modern C++ Design» запропонував фундаментальну ідіому списків типів (англ. *typelists*). Список типів моделювався як рекурсивна структура з голови (`Head`) та хвоста (`Tail`), яка термінувалася спеціальним маркерним типом `NullType`:

```cpp
struct NullType {};

template <typename H, typename T>
struct TypeList {
    using Head = H;
    using Tail = T;
};

using MyTypes = TypeList<int, TypeList<double, TypeList<std::string, NullType>>>;
```

На базі списків типів Александреску розробив метаструктури генерації ієрархій класів — `GenScatterHierarchy` та `GenLinearHierarchy`. `GenScatterHierarchy` рекурсивно розгортала список типів у дерево множинного успадкування, де кожен базовий клас зберігав значення відповідного типу з контейнера:

```cpp
template <class TList, template <class> class Unit>
class GenScatterHierarchy;

template <class T1, class T2, template <class> class Unit>
class GenScatterHierarchy<TypeList<T1, T2>, Unit>
    : public GenScatterHierarchy<T1, Unit>,
      public GenScatterHierarchy<T2, Unit> {};

template <class AtomicType, template <class> class Unit>
class GenScatterHierarchy : public Unit<AtomicType> {};
```

Цей підхід вперше надав C++ розробникам можливість конструювати гетерогенні структури довільного складу без порушення типобезпеки. Проте плата за таку гнучкість була надзвичайно високою: кожна операція над списком типів (визначення довжини, індексація, пошук позиції типу) вимагала створення лінійного ланцюжка рекурсивних інстанціацій шаблонів. Отримані структури перевантажували внутрішні таблиці символів компіляторів і призводили до колосальних витрат пам'яті середовища розробки.

## Макросна генерація Boost.Preprocessor

Для промислових бібліотек бібліотека Boost пішла іншим шляхом: замість складної рекурсії списків типів інженери Яакко Ярві (Jaakko Järvi), Девід Абрагамс (David Abrahams) та Олексій Гуртовий (Aleksey Gurtovoy) застосували автоматичну генерацію повторюваного коду засобами препроцесора.

У бібліотеках Boost.Tuple, Boost.Function та Boost.MPL використовувалася бібліотека Boost.Preprocessor (`BOOST_PP_REPEAT`, `BOOST_PP_ENUM_PARAMS`). Препроцесор фізично генерував десятки майже однакових перевантажень для 1, 2, 3, ..., 10, а в окремих конфігураціях до 50 параметрів:

```cpp
#define BOOST_PP_ITERATION_PARAMS_1 (3, (1, 10, "boost/tuple.hpp"))
#include BOOST_PP_ITERATE()
```

У результаті обробки препроцесором один заголовочний файл міг розростатися до десятків тисяч рядків коду з визначеннями типу:

```cpp
template <typename T0, typename T1 = null_type, typename T2 = null_type,
          typename T3 = null_type, typename T4 = null_type,
          typename T5 = null_type, typename T6 = null_type,
          typename T7 = null_type, typename T8 = null_type,
          typename T9 = null_type>
class tuple;
```

Цей підхід мав три критичні дефекти:
1. **Штучні ліміти:** Якщо розробнику був потрібен кортеж на 11 елементів у бібліотеці з лімітом 10, код відмовлявся компілюватися доти, доки в системі збирання не оголошували спеціальний макрос (наприклад, `#define BOOST_MPL_LIMIT_METAFUNCTION_ARITY 20`), що подвоювало час компіляції всього проєкту.
2. **Катастрофічне уповільнення збирання:** Препроцесор витрачав гігабайти оперативної пам'яті на генерацію та синтаксичний розбір нескінченних списків фіктивних параметрів `null_type`.
3. **Нечитабельна діагностика:** Помилка в передачі типу в десятий аргумент породжувала повідомлення компілятора на кілька сотень рядків, заповнених зашифрованими макросними іменами.

## Стандартизація N2080: поява Variadic Templates у C++11

Розуміючи тупиковість макросного підходу, на початку 2000-х років дослідники з Університету Індіани (Indiana University) Дуглас Ґреґор (Douglas Gregor) та Яакко Ярві разом із творцем мови Б'ярном Страуструпом розпочали розробку фундаментального розширення системи шаблонів.

У серії документів (N1403 у 2002 році, N1603 у 2004 році, N1704 та фінальному N2080 у 2006 році) робоча група запропонувала концепцію варіативних шаблонів (*Variadic Templates*). Головною ідеєю було введення математичного поняття пакета параметрів (англ. *parameter pack*), який позначався символом трикрапки (`...`).

Пропозиція визначила три фундаментальні семантичні ролі для `...`:
1. Оголошення пакета шаблонних параметрів типів або значень: `template <typename... Args>`.
2. Оголошення пакета параметрів функції: `void invoke(Args... args)`.
3. Операція розпакування патерну: `expr(args)...`.

Комітет ISO стандартизував цю модель у стандарті C++11. Це дало змогу реалізувати `std::tuple`, `std::make_shared`, `std::bind` та `std::thread` у вигляді елегантних, типізованих та абсолютно чистих шаблонів, що не містили жодних препроцесорних повторень чи штучних обмежень на кількість параметрів.

## Проблема лінійного обходу в C++11 та трюк Swallow

Попри тріумф C++11, виявилося, що мова не містила простого механізму обходу елементів пакета. Щоб виконати дію над кожним елементом (наприклад, надрукувати аргументи або перевірити умову), розробник мусив застосовувати рекурсивну функціональну декомпозицію:

```cpp
// Базовий термінальний випадок
void print_all() {}

// Рекурсивний крок
template <typename Head, typename... Tail>
void print_all(const Head& head, const Tail&... tail) {
    std::cout << head << ' ';
    print_all(tail...);
}
```

Для виклику з 20 аргументами компілятор був зобов'язаний згенерувати 21 окрему спеціалізацію шаблону функції. Якщо оптимізатор не вбудовував (не інлайнив) ці виклики через перевищення бюджету оптимізації, утворювався реальний стек рекурсивних викликів функцій під час виконання програми.

Щоб уникнути цього навантаження на компілятор, інженери винайшли ідіому поглинання (англ. *swallow idiom*). Вона використовувала властивість списку ініціалізації масиву `int[]`, який гарантував обчислення елементів строго зліва направо у визначеному порядку:

```cpp
template <typename... Args>
void print_all(const Args&... args) {
    using swallow = int[];
    (void)swallow{0, (void(std::cout << args << ' '), 0)...};
}
```

Вираз `(void(std::cout << args << ' '), 0)` спирався на вбудований оператор коми: спочатку виконувалася дія виведення в потік `std::cout`, після чого вираз повертав ціле число `0` для наповнення безіменного масиву. Хоча трюк дозволяв уникнути генерації 20 функцій, він виглядав як синтаксична аномалія, лякав розробників і часто спричиняв попередження статичних аналізаторів.

## Революція C++17: вирази згортки (Fold Expressions)

У 2014 році дослідники Ендрю Саттон (Andrew Sutton) та Річард Сміт (Richard Smith) подали пропозиції N4191 та N4295 (*Folding Expressions*), які увійшли до стандарту C++17.

Під час розробки виразів згортки робоча група обговорювала можливість створення узагальненої форми згортки над довільними бінарними функціями чи функторами `fold(binary_func, args...)`. Проте такий підхід суттєво ускладнив би синтаксичний аналіз та неоднозначність парсингу виразів. У результаті комітет зупинився на строгому списку з 32 вбудованих бінарних операторів C++, що дозволило вбудувати згортку безпосередньо в граматичне ядро транслятора.

Замість рекурсивного розгортання в окремі функції компілятор C++17 перетворює вираз `(args + ...)` на єдиний вузол бінарного дерева виразів `(a1 + (a2 + (a3 + a4)))` безпосередньо у внутрішньому синтаксичному дереві (AST). Це скоротило час трансляції шаблонних бібліотек у кілька разів і зробило варіативний код природним та лаконічним.

## Вплив на стандартну бібліотеку: від std::tuple до std::format

Поява варіативних шаблонів та виразів згортки докорінно змінила архітектуру стандартної бібліотеки C++:
- **Реалізація std::tuple:** У стандартних бібліотеках GCC (libstdc++), LLVM (libc++) та Microsoft MSVC STL реалізація `std::tuple` перейшла від рекурсивного успадкування до прямого плаского розташування полів за допомогою спеціальних варіативних сховищ `_Tuple_impl<Index, Types...>`.
- **Бібліотека {fmt} та std::format (C++20):** Розробка Віктора Звєровича (Victor Zverovich) до довела, що поєднання варіативних шаблонів із розпакуванням масивів дескрипторів типів дозволяє побудувати форматування рядків, яке перевершує за швидкістю класичний `printf` у 2–3 рази, зберігаючи повну типобезпеку та захист від атак переповнення буфера на етапі компіляції.
- **Диспетчеризація std::variant:** Завдяки виразам згортки генерація таблиць переходів для `std::visit` над кількома варіативними союзами скоротилася з сотень рядків коду до компактних шаблонних розгортань.

## Сучасний стан: C++20 та C++26

Еволюція варіативності не зупинилася на виразах згортки:
- **C++20:** Запроваджено розпакування пакетів у захопленнях лямбд: `[...args = std::move(args)]() { ... }`, використання явних списків параметрів шаблонів у лямбда-виразах `<typename... Ts>(Ts... args)`, а також пряму інтеграцію з концептами через вирази згортки `requires (std::is_integral_v<Args> && ...)`.
- **C++26:** Прийнято пропозицію P2663 щодо прямої індексації пакетів (`Args...[I]` для типів та `args...[I]` для значень). Це усуває останню потребу в рекурсивних метафункціях або штучних викликах `std::get` для вилучення `N`-го елемента пакета, перетворюючи довільний доступ до типу чи аргументу на миттєву операцію складності `O(1)`.
