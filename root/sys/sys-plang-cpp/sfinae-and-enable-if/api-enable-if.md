# 📋 Довідник інтерфейсів: std::enable_if, void_t та правила підстановки

Цей довідник містить формальні специфікації, сигнатури, правила використання, діагностичні особливості та детальний аналіз поведінки стандартних метафункцій контролю перевантажень на базі SFINAE у стандартах C++11, C++14 та C++17.

## 1. Метафункція std::enable_if та псевдонім std::enable_if_t

Визначена у стандартному заголовочному файлі `<type_traits>`.

### Формальна специфікація та визначення

```cpp
namespace std {
    // 1. Первинний шаблон для хибної умови (C++11)
    template<bool B, class T = void>
    struct enable_if {};

    // 2. Часткова спеціалізація для істинної умови (C++11)
    template<class T>
    struct enable_if<true, T> {
        using type = T;
    };

    // 3. Шаблонний псевдонім (починаючи з C++14)
    template<bool B, class T = void>
    using enable_if_t = typename enable_if<B, T>::type;
}
```

### Параметри шаблону

| Параметр | Тип | Опис та семантика |
| :--- | :--- | :--- |
| `B` | `bool` | Логічний вираз етапу компіляції (`constexpr bool`), який визначає, чи буде згенеровано результуючий тип. |
| `T` | `typename` | Тип, який надається у вкладеному псевдонімі `using type = T` у разі виконання умови `B == true`. За замовчуванням дорівнює `void`. |

### Вкладені типи та стан розіменування

| Ім'я члена | Стан за умови `B == true` | Стан за умови `B == false` |
| :--- | :--- | :--- |
| `type` | Визначається як тип `T`. Доступний для розіменування через `::type`. | **Повністю відсутній**. Спроба отримати доступ до `typename std::enable_if<false, T>::type` негайно генерує помилку підстановки (Substitution Failure) у сигнатурі. |

### Порівняння std::enable_if та std::conditional

Розробники-початківці іноді намагаються використовувати `std::conditional` для умовного вимкнення функцій, що є фатальною помилкою:

```cpp
// НЕПРАВИЛЬНО: std::conditional не генерує помилку SFINAE
template<typename T>
using bad_filter = typename std::conditional<std::is_integral_v<T>, void, struct InvalidType>::type;
```

`std::conditional<B, T, F>` завжди визначає вкладений тип `type` (або `T`, або `F`). Тому вираз залишається валідним і функція залишається у списку кандидатів із типом `InvalidType`. На противагу цьому, `std::enable_if<false, T>` взагалі не містить члена `type`, створюючи необхідну для SFINAE синтаксичну відмову.

## 2. Шаблонний псевдонім std::void_t

Визначений у стандартному заголовку `<type_traits>` (включений у C++17; доступний для C++11/14 через користувацьку реалізацію).

### Формальна сигнатура

```cpp
namespace std {
    template<class...>
    using void_t = void;
}
```

### Механізм роботи та дефект CWG 1558

У первинній редакції стандарту C++14 компілятори мали право відкидати шаблонні параметри в аліасах, якщо вони не брали участі у результуючому типі. Це призводило до того, що `void_t<InvalidExpr>` негайно згортався у `void` без обчислення виразу, руйнуючи всю логіку виявлення властивостей.

Згідно з виправленням дефекту **CWG 1558**, усі стандартні бібліотеки реалізують `void_t` через проміжну структуру:

```cpp
template<typename... Ts>
struct __make_void { using type = void; };

template<typename... Ts>
using void_t = typename __make_void<Ts...>::type;
```

### Поведінка у метапрограмуванні
- Якщо кожен аргумент у пакеті `...` є валідним синтаксичним типом або виразом `decltype(...)`, `std::void_t<...>` успішно розгортається у тип `void`.
- Якщо хоча б один вираз є невалідним (наприклад, звернення до неіснуючого методу чи оператора), підстановка всього шаблону зазнає невдачі у безпосередньому контексті.

## 3. Допоміжна функція std::declval

Визначена у стандартному заголовку `<utility>` (починаючи з C++11).

### Формальна сигнатура

```cpp
namespace std {
    template<class T>
    typename std::add_rvalue_reference<T>::type declval() noexcept;
}
```

### Правила застосування та гарантії

1. **Виключно неоцінюваний контекст (Unevaluated Operand):** Функція `std::declval<T>()` призначена для використання виключно всередині операторів `decltype`, `sizeof`, `typeid` та `noexcept`.
2. **Відсутність визначення (ODR-use ban):** Функція не має скомпільованого тіла. Будь-яка спроба викликати її у коді, що виконується в runtime, призводить до помилки компонування (Undefined Reference).
3. **Категорія значень та згортання посилань (Reference Collapsing):**
   - Для скалярного типу `T`: повертає rvalue-посилання `T&&` (категорія xvalue).
   - Для lvalue-посилання `T&`: повертає `T&` за правилом `T& && -> T&`.
   - Для rvalue-посилання `T&&`: повертає `T&&`.
4. **Робота з неповними та абстрактними типами:** Дозволяє опитувати інтерфейси абстрактних класів та класів із захищеними чи відсутніми конструкторами за замовчуванням.

## 4. Логічні операції короткого замикання: std::conjunction, std::disjunction, std::negation

Починаючи зі стандарту C++17, бібліотека `<type_traits>` надає набір метафункцій для безпечного комбінування умов SFINAE без передчасної інстанціації небезпечних гілок:

```cpp
namespace std {
    template<class... B> struct conjunction;
    template<class... B> struct disjunction;
    template<class B>    struct negation;

    template<class... B> inline constexpr bool conjunction_v = conjunction<B...>::value;
    template<class... B> inline constexpr bool disjunction_v = disjunction<B...>::value;
    template<class B>    inline constexpr bool negation_v    = negation<B>::value;
}
```

### Чому звичайні оператори && та || небезпечні у SFINAE

Коли розробник записує умову `std::enable_if_t<std::is_class_v<T> && has_method_v<T>>`, компілятор C++ зобов'язаний повністю обчислити обидва аргументи шаблону до виконання логічного «І». Якщо `T = int`, а трейт `has_method_v<int>` всередині звертається до полів класу, інстанціація `has_method_v<int>` спричинить жорстку помилку компіляції (Hard Error) ще до того, як оператор `&&` відкине вираз за першим `false`.

Метафункція `std::conjunction` реалізує справжнє ліниве коротке замикання на рівні типів: вона наслідується від першого ж трейту, значення `value` якого дорівнює `false`, і принципово не інстанціює решту трейтів у списку.

## 5. Канонічні правила безпосереднього контексту (Immediate Context Rules)

Згідно зі стандартом ISO C++ (§13.10.2 [temp.deduct]), правило SFINAE діє виключно у **безпосередньому контексті** (Immediate Context) оголошення шаблону.

### Локації безпосереднього контексту (SFINAE працює — тихе вилучення):

1. **Тип повернення функції:** Тип результату функції, включно з пізнім уточненням типу (Trailing Return Type) `auto func() -> decltype(...)`.
2. **Типи формальних параметрів функції:** Будь-які типи у списку аргументів `void func(typename T::type x)`.
3. **Значення за замовчуванням для параметрів функції:** Вирази ініціалізації аргументів `void func(T x, std::enable_if_t<Cond>* = nullptr)`.
4. **Параметри самого шаблону:** Типи та значення за замовчуванням у списку `template<typename T, std::enable_if_t<Cond, int> = 0>`.
5. **Явні аргументи шаблону:** Типи, передані безпосередньо у кутових дужках у точці виклику `func<Type>()`.
6. **Специфікація винятків:** Вираз всередині `noexcept(expr)`.

### Локації поза безпосереднім контекстом (Hard Error — падіння збірки):

1. **Тіло функції:** Будь-який блок коду всередині `{ ... }`.
2. **Неявна інстанціація стороннього класу:** Якщо підстановка у сигнатуру вимагає інстанціації класу `Helper<T>`, і вже всередині `Helper` виникає синтаксична помилка.
3. **Ініціалізатори статичних членів класу:** Константи `static constexpr`, що обчислюються під час інстанціації класу.
4. **Визначення методів усередині тіла класу:** Тіла конструкторів та методів, що генеруються компілятором.

## 6. SFINAE-дружні метафункції (SFINAE-Friendly Traits)

У ранніх версіях C++11 деякі стандартні трейти призводили до аварійного завершення компіляції, якщо їм передавали несумісні типи. Наприклад, `std::common_type<T, U>` для типів без спільного предка або `std::result_of<F(Args...)>` для невідповідних аргументів викликали Hard Error всередині стандартної бібліотеки.

Починаючи з C++14 та C++17, стандарт вимагає, щоб усі трейти перевірки та виведення були **SFINAE-дружніми** (SFINAE-friendly). Це означає, що за неможливості обчислити результат метафункція не повинна падати: вона зобов'язана просто не визначати член `type`.

Прикладом такої безпечної заміни є метафункція `std::invoke_result` (C++17), яка замінила застарілий `std::result_of`:

```cpp
// Якщо f(args...) неможливо викликати, invoke_result<F, Args...>
// не містить вкладеного ::type, що дозволяє безпечно використовувати його в SFINAE
template<typename F, typename... Args>
auto call_if_possible(F&& f, Args&&... args) 
    -> typename std::invoke_result<F, Args...>::type 
{
    return std::forward<F>(f)(std::forward<Args>(args)...);
}
```

## 7. Допоміжний набір Library Fundamentals TS: is_detected

Для стандартизації ідіоми виявлення в інженерних бібліотеках було розроблено набір `std::experimental::is_detected` (Library Fundamentals TS v2):

```cpp
#include <experimental/type_traits>

// 1. Оголошення мета-виразу
template<typename T>
using serialize_op = decltype(std::declval<T>().serialize());

// 2. Предикат існування
template<typename T>
using has_serialize = std::experimental::is_detected<serialize_op, T>;

// 3. Отримання результуючого типу або заглушки
template<typename T>
using serialize_result_t = std::experimental::detected_or_t<void, serialize_op, T>;
```

### Зведена таблиця API родини is_detected

| Шаблонний інтерфейс | Повернене значення / тип | Семантичне призначення |
| :--- | :--- | :--- |
| `is_detected<Op, Args...>` | `std::true_type` або `std::false_type` | Перевіряє, чи вираз `Op<Args...>` є валідним типом. |
| `is_detected_v<Op, Args...>` | `constexpr bool` | Зручний константний булевий доступ до результату перевірки. |
| `detected_t<Op, Args...>` | Отриманий тип або `nonesuch` | Повертає реальний тип виразу або маркерний тип `std::experimental::nonesuch`. |
| `detected_or_t<Default, Op, Args...>` | Отриманий тип або `Default` | Безпечно повертає альтернативний тип за замовчуванням, якщо операція не підтримується. |
| `is_detected_exact<Expected, Op, Args...>` | `std::true_type` або `std::false_type` | Перевіряє, чи вираз `Op<Args...>` точно дорівнює типу `Expected`. |
| `is_detected_convertible<To, Op, Args...>` | `std::true_type` або `std::false_type` | Перевіряє, чи результат виразу `Op<Args...>` можна неявно перетворити на тип `To`. |

### Анатомія типу nonesuch

Тип `std::experimental::nonesuch` використовується як маркер відсутності результату. Він спроектований так, що його неможливо створити, скопіювати чи перетворити на будь-який інший тип:

```cpp
struct nonesuch {
    ~nonesuch() = delete;
    nonesuch(const nonesuch&) = delete;
    void operator=(const nonesuch&) = delete;
};
```
