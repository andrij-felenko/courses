# 📜 Історія появи шаблонів, проблеми розростання коду та боротьби з тривалою компіляцією

Наприкінці 1980-х років розробка великих системних програм мовою C++ зіштовхнулася з принциповим роздоріжжям. Узагальнений код вимагав або небезпечних препроцесорних макросів `#define`, які втрачали контроль типів та спричиняли масу побічних ефектів при повторному обчисленні аргументів, або ручного дублювання функцій та класів для кожного потрібного типу даних. Б'ярн Страуструп (Bjarne Stroustrup) разом із розробниками компілятора Cfront створили механізм шаблонів (`templates`), представлений у доповіді «Parameterized Types for C++» на конференції USENIX C++ у жовтні 1988 року (Денвер). У 1990 році шаблони були схвалені комітетом ANSI C++ X3J16. Однак обрана модель включення (`Inclusion Model`) породила нову системну проблему — вибухове зростання часу компіляції та розростання бінарного коду (`Code Bloat`), яке переслідує мову C++ протягом багатьох десятиліть.

## Моделі компіляції шаблонів у 1990-х: включення проти репозиторію

У перших реалізаціях мови C++ (компілятор Cfront 3.0) шаблони транслятором спочатку перетворювалися на звичайний код мови C. Для кожного нового типу генерувалися структури `struct` та глобальні функції мови C з унікальними декорованими іменами. 

З появою нативних компіляторів виникли дві конкуруючі філософії того, де саме і коли саме компілятор повинен будувати машинний код спеціалізацій шаблонів:

Модель включення (`Inclusion Model`), яку від початку підтримував Страуструп, вимагала наявності повного визначення (тіла) шаблону в кожному заголовочному файлі. Щоразу, коли одиниця компіляції (`.cpp` файл) використовувала `std::vector<int>`, компілятор повністю розгортав синтаксичне дерево (AST) і генерував машинний код для `std::vector<int>`. Якщо проект складався з 500 файлів `.cpp`, і кожен з них включав `<vector>`, компілятор генерував машинний код `vector<int>` 500 разів поспіль.

Щоб уникнути цього гігантського дублювання роботи, розробники компанії Edison Design Group (EDG) запропонували модель репозиторію (`Repository Model`). У цій моделі компілятор під час аналізу `.cpp` файлів не генерував машинний код шаблонів одразу, а лише записував вимоги до інстанціації в спеціальну базу даних — репозиторій (файл `.rpo`). На етапі компонування спеціальний компонувальник аналізував репозиторій, виявляв усі унікальні інстанціації, викликав компілятор для їх одноразової збірки й лише потім збирав остаточний виконуваний файл. Цей підхід використовувався у компіляторах SGI IRIX C++, Cfront та у вихідних версіях GCC (з прапорцем `-frepo`).

Паралельно компанія Borland у своєму компіляторі Borland C++ 4.0 застосувала підхід `Smart Templates` (з прапорами `-Jg` та `-Jgi`): компілятор генерував код шаблонів у кожному об'єктному файлі, але розміщував його в особливих сегментах пам'яті, які лінкер міг розпізнавати й видаляти за наявності дублікатів.

Також у C++98 було зафіксовано ключове слово `export template`, яке мало дозволити розділяти оголошення шаблону у заголовочному файлі та його реалізацію у файлі `.cpp`. Однак реалізація `export template` виявилася настільки складною для творців компіляторів, що її змогла повноцінно імплементувати лише компанія EDG (у компіляторах Comeau C++) через 10 років після прийняття стандарту. Жоден з масових компіляторів (GCC, MSVC) так і не реалізував `export template`, і в C++11 це слово було офіційно вилучено зі стандарту.

```
          Модель включення (Inclusion)          Модель репозиторію (EDG Repository)
     ┌───────────────────────────────────┐    ┌───────────────────────────────────┐
     │ main.cpp   →  gen vector<int>     │    │ main.cpp   →  запис у .rpo файл   │
     │ io.cpp     →  gen vector<int>     │    │ io.cpp     →  запис у .rpo файл   │
     │ net.cpp    →  gen vector<int>     │    │ net.cpp    →  запис у .rpo файл   │
     └─────────────────┬─────────────────┘    └─────────────────┬─────────────────┘
                       │                                        │
           Дублювання на етапі збірки               Одноразова компіляція на етапі
           Видалення дублів у лінкері               компонування через репозиторій
```

Війна моделей компіляції тривала до прийняття першого стандарту ISO C++98. Перемогла модель включення через її простоту для творців заголовочних бібліотек: користувачеві достатньо було написати `#include <vector>`, не налаштовуючи складні бази даних репозиторіїв та спеціалізовані компонувальники.

## Перемога COMDAT та народження проблеми Code Bloat

Із перемогою моделі включення всі провідні компілятори (GCC, MSVC, Clang) адаптували механізм секцій COMDAT (Comdat Fold / Weak Symbols). Компілятор згенеровував машинний код для кожної неявної інстанціації в об'єктному файлі `.o`, але позначав ці функції спеціальним прапорцем для компонувальника (у форматі ELF — `.gnu.linkonce`, у форматі PE/COFF — `IMAGE_COMDAT_SELECT_NODUPLICATES`). 

Під час остаточного компонування лінкер залишав лише одну копію машинного коду `std::vector<int>::push_back`, а решту 499 дубльованих секцій відкидав.

Хоча проблему розміру бінарного файлу на диску було частково розв'язано через COMDAT, виникла нова фундаментальна проблема: марна робота компілятора (`Compiler Wasted Work`). Компілятор витрачав 99% свого часу процесора на багаторазове синтаксичне розбирання, перевірку типів та генерацію інструкцій асемблера для одних і тих самих комбінацій шаблонів, аби лінкер наприкінці просто викинув 99% згенерованого коду в смітник.

Більше того, у реальних проектах початку 2000-х років розробники зіштовхнулися з явищем `Code Bloat` на рівні кешу процесора. Навіть якщо компонувальник згортав точні дублікати функцій, інстанціація `std::vector<int>`, `std::vector<long>`, `std::vector<unsigned int>`, `std::vector<void*>`, `std::vector<MyClass*>` створювала десятки практично ідентичних функцій у пам'яті. Усі ці функції виконували однакові операції над пам'яттю, але мали різні адреси та типи, вимиваючи кеш інструкцій (I-cache) центрального процесора під час виконання програми.

## Ера Boost.MPL та експоненційне зростання метапрограмування

На початку 2000-х років поява бібліотеки Boost.MPL (Metaprogramming Library) Олексія Гуревого (Aleksey Gurtovoy) довела метапрограмування на шаблонах до абсолютного максимуму. Бібліотеки почали використовувати типи C++ як змінні, а рекурсивну інстанціацію шаблонів — як цикли й розгалуження під час компіляції.

Паралельно виникли виразові шаблони (Expression Templates) у бібліотеках лінійної алгебри Blitz++ Тодда Вельдхейзена (Todd Veldhuizen) та Boost.Spirit для розбору граматик. Вони будували складні дерева типів на етапі компіляції для усунення тимчасових векторів під час векторних обчислень.

Однак ціна таких обчислень виявилася колосальною. Інстанціація глибоких структур типу `boost::mpl::vector` або виразових шаблонів у Blitz++ чи Spirit призводила до того, що компіляторам GCC 3.x та MSVC 7.1 бракувало оперативної пам'яті. Інстанціація дерева шаблонів глибиною в кілька сотень рівнів створювала мільйони вузлів AST у пам'яті компілятора, збільшуючи час збірки невеликого проекту з секунд до десятків хвилин.

## Стандартизація `extern template` у C++11

Прагнучи приборкати тривалість збірки у великих телекомунікаційних та ігрових рушіях, інженери звернули увагу на явні інстанціації (`Explicit Instantiation`). У стандарті C++98 вже існував синтаксис `template class std::vector<int>;`, який змушував компілятор згенерувати код спеціалізації в конкретному `.cpp` файлі. Проте бракувало зворотної інструкції — як наказати компілятору в усіх інших файлах *не* генерувати неявну інстанцію, бо вона вже існує в іншому місці.

У 2003 році Мет Маркус (Mat Marcus), Габріель Дос Рейс (Gabriel Dos Reis) та Джон Спайсер (John Spicer) подали пропозицію ISO C++ N1448 («Controlling Implicit Template Instantiation») до комітету C++ щодо введення розширення `extern template`. Воно дозволяло вказати компілятору: «Не інстанціюй цей шаблон у цьому файлі, сильні символи будуть надані іншим об'єктним модулем».

Після тривалих обговорень синтаксис `extern template` увійшов до стандарту C++11. Це стало першим офіційним інструментом мови, який дозволив розробникам бібліотек явно керувати вартістю компіляції та контролювати точки генерації машинного коду.

## Еволюція метапрограмування: від SFINAE до C++20 Concepts

Паралельно з розвитком моделей компіляції відбувалася еволюція самого метапрограмування. Відкриття Олександром Степановим (Alexander Stepanov) концепції узагальненого програмування у STL та подальше відкриття Ервіном Унру (Erwin Unruh) того факту, що шаблони C++ є Тюрінг-повною мовою обчислень під час компіляції, спричинили вибух використання метапрограмування.

У 2000-х роках основними інструментами вибору шаблонів були SFINAE (`Substitution Failure Is Not An Error`) та `std::enable_if`. Кожен виклик перевантаженої шаблоної функції змушував компілятор оцінювати десятки кандидатів, будувати гігантські вирази підстановки та генерувати сотні тимчасових типів. При помилках у типах компілятор видавав знамениті «простирадла помилок» (`template backtrace explosion`) обсягом у десятки кілобайт, а час компіляції зростав експоненційно від кількості параметрів.

Розв'язанням цієї кризи стало введення Концептів (Concepts) у C++20. Розробка концептів тривала понад 15 років (початкова версія C++0x concepts була відхилена у 2009 році через надмірну складність). Реалізація Концептів у C++20 дозволила перевіряти обмеження типів *до* підстановки у підпис функції та генерації синтаксичного дерева, скоротивши навантаження на компілятор під час вирішення перевантажень у рази.

Додатковим полегшенням стало введення `constexpr` у C++11 та `constexpr if` у C++17. Вони дозволили замінити рекурсивну інстанціацію шаблонів звичайними обчисленнями у стилі імперативного програмування, що зменшило кількість створюваних тимчасових типів на декілька порядків.

## Революція модулів у C++20

Найрадикальнішим кроком у боротьбі з вартістю шаблонів за всю історію мови C++ стало введення Модулів (`Modules`) у C++20. Модулі відмовляються від текстової моделі включення заголовочних файлів (`#include`), яка існувала з часів мови C 1970-х років.

При використанні модулів компілятор аналізує шаблонний інтерфейс один раз, будує його бінарне представлення (`BMI` — Binary Module Interface) і використовує це готове представлення в усіх інших модулях без повторного синтаксичного розбору текстових заголовочних файлів. Це знімає текстове навантаження препроцесора, хоча внутрішня вартість підстановки та інстанціації конкретних типів залишається фундаментальною властивістю строго типізованої мови C++.
