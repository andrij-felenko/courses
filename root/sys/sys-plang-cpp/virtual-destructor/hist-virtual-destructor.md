# 📜 Еволюція віртуальних деструкторів: від Cfront до сучасного C++

Історія віртуального деструктора в C++ є літописом одного з найважливіших компромісів в інженерії мов програмування: балансу між абсолютною продуктивністю низькорівневих абстракцій та безпекою високорівневого об'єктно-орієнтованого проектування. Цей компроміс сформував сучасний вигляд мови та визначив її ключові архітектурні принципи.

## Перші дні C with Classes та Cfront (1979–1985)

Коли Б'ярн Страуструп (Bjarne Stroustrup) у науково-дослідному центрі Bell Labs почав розробляти *C with Classes* (прямого попередника C++), його головною метою було поєднати виразні засоби мови Simula 67 з безкомпромісною швидкістю та прямим доступом до апаратного забезпечення мови C.

У мові Simula 67 кожна процедура та кожен об'єкт несли відчутні накладні витрати пам'яті через динамічне зв'язування та автоматичне керування пам'яттю. Працюючи над симуляцією розподілених обчислювальних систем на комп'ютерах з обмеженою оперативною пам'яттю, Страуструп зіткнувся з тим, що Simula була занадто повільною для реальних задач моделювання ядра операційної системи, тоді як C був швидким, але не мав засобів абстракції типів.

Саме тоді Страуструп сформулював фундаментальний принцип, який згодом ліг в основу стандарту ISO C++: **«Те, чим ви не користуєтеся, не повинно вам нічого коштувати»** (*Zero-overhead principle*).

```
«C++ implementations obey the zero-overhead principle:
What you don't use, you don't pay for.
What you do use, you couldn't hand code any better.»
— Bjarne Stroustrup
```

Коли у версії транслятора Cfront 1.0 (1985 рік) з'явилися класи з конструкторами та деструкторами, у дослідницькій групі Bell Labs постало принципове питання: чи повинен деструктор класу бути віртуальним автоматично за замовчуванням?

Якщо зробити деструктор автоматично віртуальним для кожного класу:
1. Кожна проста структура на зразок `struct Point { int x, y; };` автоматично отримає додатковий прихований покажчик на віртуальну таблицю `vptr` (4 байти на 32-бітних або 8 байтів на 64-бітних архітектурах).
2. Розмір елементарних структур даних зросте у два або три рази, що зробить неефективним зберігання масивів із мільйонів точок чи векторів у пам'яті.
3. Структури C++ втратять бінарну сумісність із мовою C (перестануть бути *Plain Old Data* / *Standard Layout*), що зруйнує можливість прямої взаємодії з системними викликами операційної системи Unix (`read`, `write`, `ioctl`).
4. Будь-який виклик деструктора перетвориться на непрямий перехід через таблицю, унеможливлюючи агресивне вбудовування коду (*inlining*) оптимізатором компілятора.

З огляду на ці аргументи Страуструп ухвалив безкомпромісне рішення: деструктори за замовчуванням є звичайними статично зв'язаними функціями. Клас платить за віртуальну таблицю `vtable` лише тоді, коли розробник явно додає ключове слово `virtual`. Зворотним боком цієї оптимізації стала поява класичної пастки для програмістів: випадкове видалення об'єкта похідного типу через вказівник на базовий клас без віртуального деструктора.

## Формалізація в ARM та стандарті C++98

Наприкінці 1980-х років, із появою Cfront 2.0 (1989 рік) та впровадженням множинного успадкування, проблема невіртуального видалення набула особливої гостроти. Якщо при одиничному успадкуванні без полів у нащадку виклик `free(p)` міг випадково спрацювати без падіння, то при множинному успадкуванні зміщення покажчика на другий базовий клас призводило до негайного руйнування структур пам'яті операційної системи.

У класичній книзі 1990 року *The Annotated C++ Reference Manual* (відомій як *ARM*) Маргарет Елліс (Margaret A. Ellis) та Б'ярна Страуструпа, яка стала базовим документом для першого офіційного комітету стандартизації ISO WG21, статус видалення через невіртуальну базу було остаточно формалізовано як **невизначену поведінку** (*Undefined Behavior*).

У першому офіційному міжнародному стандарті C++98 (ISO/IEC 14882:1998) розділ 5.3.5 [expr.delete] закріпив це правило:

> «Якщо статичний тип об'єкта, що видаляється, відрізняється від його динамічного типу, статичний тип повинен бути базовим класом динамічного типу об'єкта, і статичний тип повинен мати віртуальний деструктор, або поведінка є невизначеною.»

Цікаво порівняти цей підхід з іншими об'єктно-орієнтованими мовами того періоду. Мови Java (1995) та пізніше C# (2000) обрали діаметрально протилежний шлях: усі класи неявно успадковуються від єдиного кореневого типу `Object`, усі об'єкти виділяються виключно в динамічній пам'яті через збирач сміття (*Garbage Collector*), а кожен об'єкт несе обов'язковий заголовок (*object header*) розміром від 8 до 16 байтів. C++ відмовився від універсального кореневого класу, зберігши максимальну апаратну продуктивність для системних завдань.

## C++11: Семантика переміщення та криза Правила трьох

До прийняття стандарту C++11 у спільноті розробників неподільно панувало так зване **Правило трьох** (*Rule of Three*), сформульоване Маршаллом Клайном (Marshall Cline) у 1991 році: якщо клас керує ресурсом і оголошує користувацький деструктор, конструктор копіювання або оператор копіювального присвоєння, він майже напевно повинен явно оголосити всі три спеціальні методи.

Поява в C++11 семантики переміщення (*move semantics*), rvalue-посилань (`&&`) та оператора `std::move()` кардинально змінила баланс. Комітет стандартизації ISO WG21 (документ N3053) встановив нове суворе правило задля забезпечення безпеки коду: наявність користувацького деструктора (включно з конструкцією `virtual ~Base() = default;`) **повністю пригнічує автоматичну генерацію конструктора та оператора переміщення**.

Це призвело до хвилі неочевидних проблем у промислових кодових базах: розробники додавали віртуальний деструктор до інтерфейсних класів і виявляли, що передача таких об'єктів у стандартні контейнери `std::vector` починала мовчки виконувати важке поглибле копіювання замість швидкого переміщення вказівників.

Як відповідь на цей виклик було сформульовано сучасне **Правило п'яти** (*Rule of Five*), а для чистих поліморфних інтерфейсів затверджено патерн явного видалення операцій копіювання та переміщення (`= delete`) для запобігання зрізанню об'єктів.

## C++14: Sized Deallocation (N3778) та кінець «прихованих» помилок

Останнім вирішальним етапом в еволюції деструкторів стало прийняття пропозиції **N3778** (автор Лоуренс Кроул, Lawrence Crowl) у стандарті C++14 — **вивільнення пам'яті з фіксованим розміром** (*Sized Deallocation*).

До C++14 стандартний глобальний оператор деалокації мав єдину форму:

```cpp
void operator delete(void* ptr) noexcept;
```

Щоб повернути пам'ять системі, алокатор був змушений або зберігати метадані про розмір кожного виділеного блоку безпосередньо перед користувацькими даними, або здійснювати дорогий пошук заголовка блоку в глобальних таблицях сторінок пам'яті. У високопродуктивних багатопотокових серверах це створювало серйозні затримки синхронізації.

Стандарт C++14 запровадив перевантаження:

```cpp
void operator delete(void* ptr, std::size_t size) noexcept;
```

Компілятор, знаючи тип об'єкта, що видаляється, автоматично передає константу `sizeof(T)` другим аргументом. Сучасні алокатори нового покоління (наприклад, `tcmalloc` від Google та `jemalloc` від Facebook) змогли миттєво повертати вивільнений блок у відповідну розмірну корзину (*size bin*) за час `O(1)` без звернення до глобальних блокувань.

Проте саме ця оптимізація перетворила прихований дефект невіртуального деструктора на гарантований аварійний збій: якщо об'єкт `Derived` розміром 128 байтів видаляється через покажчик `Base*` розміром 8 байтів, компілятор викликає `operator delete(ptr, 8)`. Алокатор повертає 128-байтовий блок у пул дрібних об'єктів. Наступне виділення пам'яті призводить до накладання чужих даних і руйнування пам'яті.

Так за сорок років розвитку мови віртуальний деструктор перетворився з низькорівневої деталі оптимізації на наріжний камінь безпеки пам'яті та архітектурної надійності програмних систем на C++.
