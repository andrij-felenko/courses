# 📋 Специфікація деструкторів в ABI та діагностика компіляторів

Цей довідник містить вичерпну інженерну специфікацію реалізації віртуальних деструкторів у двійкових інтерфейсах додатків (Itanium C++ ABI та MSVC ABI), розбір структур таблиць vtable на рівні пам'яті, сигнатури системних операторів деалокації пам'яті, нормативні вимоги стандарту ISO C++ та матрицю прапорців діагностики компіляторів для запобігання дефектам поліморфного руйнування.

## Специфікація деструкторів в Itanium C++ ABI

Специфікація **Itanium C++ ABI** (розділ 5.1.5 *Destructor Variants*) є загальноприйнятим стандартом двійкової сумісності для компіляторів GCC, Clang, Intel ICX на платформах Linux, macOS, Android, iOS та BSD.

Головна вимога до деструктора в C++ полягає в тому, що він повинен підтримувати два принципово різні сценарії виконання:
1. **Звичайне завершення часу життя** (руйнування автоматичних змінних на стеку, статичних об'єктів або полів іншого класу), коли пам'ять самого екземпляра звільняти не потрібно;
2. **Динамічне вивільнення** (виклик оператора `delete ptr`), коли після руйнування полів об'єкта необхідно передати його початкову адресу системному алокатору пам'яті.

Щоб уникнути зайвих накладних витрат у кожному сценарії, транслятор генерує для кожного віртуального деструктора три спеціалізовані варіанти функцій із власними унікальними мангльованими іменами (*mangled symbols*):

| Варіант ABI | Суфікс манглювання | Назва сутності | Технічний опис та обов'язки функції |
| :--- | :--- | :--- | :--- |
| **D0** | `_ZN<Клас>D0Ev` | **Deleting Destructor** | Функція-обгортка для динамічного вивільнення. Вона спочатку викликає повний деструктор `D1`, а потім негайно викликає `operator delete(ptr, sizeof(Клас))`. У разі множинного або віртуального успадкування ця функція коригує покажчик `this` за допомогою таблиці зміщень (*offset-to-top*), щоб передати в алокатор адресу вихідного блоку пам'яті. |
| **D1** | `_ZN<Клас>D1Ev` | **Complete Object Destructor** | Виконує повне руйнування екземпляра. Знищує всі нестатичні члени поточного класу, викликає деструктори безпосередніх базових класів, а також деструктори всіх віртуальних базових класів. Ця функція **не здійснює вивільнення пам'яті** через `operator delete` і викликається при виході автоматичного об'єкта з області видимості. |
| **D2** | `_ZN<Клас>D2Ev` | **Base Object Destructor** | Виконує руйнування лише власної частини екземпляра та його невіртуальних баз. Руйнування віртуальних базових класів **ігнорується**, оскільки за специфікацією ABI за руйнування віртуальних баз відповідає лише найвищий повний деструктор `D1`. Використовується як внутрішній крок у ланцюгу множинного та віртуального успадкування. |

### Розташування та компонування у таблиці vtable

У структурі віртуальної таблиці класу під деструктор виділяються рівно два послідовні слоти:
- **Перший слот (індекс 0):** покажчик на повний деструктор `D1` (*Complete Object Destructor*);
- **Другий слот (індекс 1):** покажчик на деструктор видалення `D0` (*Deleting Destructor*).

Базовий деструктор `D2` не потребує окремого слота у vtable, оскільки він викликається лише статично зсередини тіл деструкторів похідних класів під час розгортання ланцюга руйнування.

```
Структура пам'яті vtable для класу Derived (Itanium ABI):
┌─────────────────────────────────────────────────────────────┐
│ [ -2 ]: offset-to-top (зсув від поточної бази до початку)    │
│ [ -1 ]: RTTI pointer (покажчик на std::type_info)           │
├─────────────────────────────────────────────────────────────┤ <-- vptr вказує сюди
│ [  0 ]: Derived::~Derived() [D1: Complete Object Dtor]      │
│ [  1 ]: Derived::~Derived() [D0: Deleting Destructor]       │
│ [  2 ]: Derived::virtual_method_1()                         │
│ [  3 ]: Derived::virtual_method_2()                         │
└─────────────────────────────────────────────────────────────┘
```

Коли програма виконує інструкцію `delete base_ptr;`:
1. Компілятор зчитує `vptr` з об'єкта `base_ptr`;
2. Зчитує адресу слота 1 (`D0 Deleting Destructor`) з таблиці `vtable`;
3. Виконує непрямий виклик `call *vtable[1]`;
4. Функція `D0` знищує об'єкт через `D1` і звільняє пам'ять викликом `operator delete`.

### Таблиці VTT (Virtual Table Table) при віртуальному успадкуванні

Коли ієрархія класів використовує віртуальне успадкування (`class Derived : virtual public Base`), виникає фундаментальна проблема: під час виконання проміжних деструкторів віртуальна таблиця повинна коректно відображати стан об'єкта, що перебуває в процесі часткового руйнування.

Для вирішення цієї задачі Itanium ABI впроваджує масив **VTT** (*Virtual Table Table*):
- VTT містить покажчики на вторинні таблиці vtable та конструкційні vtable (*construction vtables*);
- деструктори базових об'єктів `D2` приймають прихований додатковий аргумент `const void* const* vtt`;
- під час виконання ланцюга руйнування `D2` оновлює покажчики `vptr` у підоб'єктах значеннями з масиву VTT, гарантуючи, що віртуальні виклики з проміжних деструкторів направлятимуться у відповідні конструкційні таблиці, а не в таблицю вже частково знищеного класу `Derived`.

## Специфікація деструкторів у Microsoft Visual C++ (MSVC ABI)

Компілятор Microsoft Visual C++ для платформ Windows (x86, x64, ARM64) використовує інший підхід для оптимізації розміру таблиць віртуальних методів. Замість виділення двох окремих слотів під `D0` та `D1`, у vtable розміщується єдиний покажчик на комбіновану функцію-диспетчер.

### Скалярний деструктор видалення (Scalar Deleting Destructor)

Функція має мангльоване ім'я вида `??_G<Клас>@@UAEPAXI@Z` (для 32-бітних) або `??_G<Клас>@@UEAAPEAXI@Z` (для 64-бітних систем) і приймає прихований цілочисельний аргумент прапорців:

```cpp
void* Derived::__scalar_deleting_destructor(unsigned int flags);
```

Значення бітової маски `flags` визначає дію функції:
- `flags == 0x0`: виконати лише руйнування членів і баз (аналог `D1`), не викликати вивільнення пам'яті;
- `flags & 0x1`: виконати руйнування об'єкта та після цього викликати `operator delete(ptr)`;
- `flags & 0x2`: викликати **векторний деструктор видалення** (*Vector Deleting Destructor*, манглювання `??_E`), який ітерується по елементах динамічного масиву при виклику `delete[] ptr`.

Така схема дозволяє MSVC зменшити розмір кожної vtable на один покажчик (8 байтів на 64-бітних системах) ціною одного додаткового умовного переходу всередині деструктора.

## Сигнатури операторів вивільнення пам'яті (Sized Deallocation)

Починаючи зі стандарту C++14, мова підтримує оператори деалокації з точним розміром (*Sized Deallocation*), а починаючи з C++17 — оператори з явним вирівнюванням (*Aligned Deallocation*).

Повний перелік стандартних глобальних сигнатур оператора вивільнення:

```cpp
#include <new>
#include <cstddef>

// 1. Базові скалярні та масивні оператори (C++98)
void operator delete(void* ptr) noexcept;
void operator delete[](void* ptr) noexcept;

// 2. Оператори вивільнення з точним розміром (C++14 Sized Deallocation)
void operator delete(void* ptr, std::size_t size) noexcept;
void operator delete[](void* ptr, std::size_t size) noexcept;

// 3. Оператори з вирівнюванням (C++17 Aligned Deallocation)
void operator delete(void* ptr, std::align_val_t al) noexcept;
void operator delete[](void* ptr, std::align_val_t al) noexcept;

// 4. Комбіновані оператори з розміром та вирівнюванням (C++17)
void operator delete(void* ptr, std::size_t size, std::align_val_t al) noexcept;
void operator delete[](void* ptr, std::size_t size, std::align_val_t al) noexcept;
```

Якщо клас визначає власний класовий оператор деалокації:

```cpp
class CustomNode {
public:
    virtual ~CustomNode() = default;

    // Класовий оператор деалокації
    static void operator delete(void* ptr, std::size_t sz) noexcept {
        CustomMemoryPool::deallocate(ptr, sz);
    }
};
```

Коли деструктор базового класу оголошено віртуальним, слот `D0` генерує виклик `operator delete` з точним значенням `sizeof(Derived)`. Якщо ж деструктор не є віртуальним, компілятор статично передасть `sizeof(CustomNode)`, що призведе до помилкового вивільнення в пулі пам'яті.

## Стандартні норми ISO C++ (Standard Clauses)

Ключові нормативні вимоги закріплені в таких пунктах стандарту ISO/IEC 14882:

### 1. Розділ [expr.delete] (§7.6.2.8)

> «У виразі видалення першого типу (скалярне видалення `delete ptr`), якщо статичний тип об'єкта, що видаляється, відрізняється від його динамічного типу, статичний тип повинен бути базовим класом динамічного типу об'єкта, і статичний тип повинен мати віртуальний деструктор, інакше поведінка є невизначеною.
> 
> У виразі видалення другого типу (видалення масиву `delete[] ptr`), динамічний тип об'єкта повинен точно збігатися зі статичним типом, інакше поведінка є невизначеною.»

Цей пункт стандарту підкреслює важливу деталь: поліморфне видалення масивів (`delete[] base_array_ptr`) є **невизначеною поведінкою завжди**, навіть якщо базовий клас має віртуальний деструктор. Арифметика покажчиків у масиві спирається на `sizeof(Base)`, тоді як елементи в пам'яті розташовані з кроком `sizeof(Derived)`.

### 2. Розділ [class.dtor] (§11.4.7)

> «Деструктор може бути оголошений як `virtual` або `pure virtual`. Якщо базовий клас оголошує віртуальний деструктор, будь-який деструктор у похідному класі автоматично стає віртуальним (навіть якщо специфікатор `virtual` опущенене).
> 
> Якщо клас містить віртуальні функції, але не має віртуального деструктора, спроба поліморфного руйнування через покажчик на цей клас є помилкою часу виконання.»

### 3. Розділ [class.virtual] (§11.7.3)

> «Чисто віртуальний деструктор повинен мати визначення (тіло), оскільки всі деструктори базових класів неявно викликаються під час руйнування похідного класу.»

## Прапорці діагностики компіляторів та статичного аналізу

Сучасні компілятори надають потужний набір прапорців попереджень для виявлення дефектів невіртуального видалення ще на етапі збирання проекту.

### Прапорці компіляторів GCC та Clang

| Прапорець | Опис діагностики та приклад ситуації | Рекомендована дія |
| :--- | :--- | :--- |
| `-Wnon-virtual-dtor` | Генерує попередження, якщо клас містить хоча б одну віртуальну функцію, але має відкритий невіртуальний деструктор. Попереджає про потенційну небезпеку поліморфного видалення. | **Обов'язковий прапорець** для всіх C++ проектів. Рекомендується вмикати разом із `-Werror=non-virtual-dtor`. |
| `-Wdelete-non-abstract-non-virtual` | Попереджає про виклик `delete ptr;`, коли статичний тип покажчика вказує на неабстрактний клас без віртуального деструктора, від якого існують нащадки. | Увімкнено за замовчуванням у Clang. |
| `-Wdelete-abstract-non-virtual-dtor` | Попереджає про спробу видалення екземпляра абстрактного класу, деструктор якого не позначений як віртуальний. | Завжди свідчить про архітектурну помилку. |
| `-Wreorder` | Попереджає про те, що порядок членів у списку ініціалізації не збігається з порядком їхнього оголошення в класі (а отже, і з порядком руйнування). | Допомагає уникнути читання неініціалізованої пам'яті в деструкторі. |
| `-fsized-deallocation` | Примусово активує генерацію викликів `operator delete(ptr, size)` для діагностики невідповідності розмірів алокації. | Увімкнено за замовчуванням у стандартах C++14 і вище. |

### Прапорці компілятора MSVC

| Прапорець / Код | Опис діагностики |
| :--- | :--- |
| `/w14150` або `C4150` | Виклик `delete` для покажчика на неповний тип (*incomplete type* / *forward declaration*). Деструктор не викликається, пам'ять звільняється некоректно. |
| `C5205` | Видалення об'єкта класу з віртуальними функціями, але без віртуального деструктора, призводить до невизначеної поведінки. |
| `/Zc:sizedDealloc` | Примусова активація оптимізації вивільнення пам'яті з точним розміром. |

### Правила статичних аналізаторів (Clang-Tidy)

- **`cppcoreguidelines-virtual-class-destructor`** (Правило C.35 з C++ Core Guidelines): перевіряє, щоб будь-який базовий клас містив або відкритий віртуальний деструктор (`public virtual`), або захищений невіртуальний деструктор (`protected non-virtual`).
- **`cppcoreguidelines-owning-memory`**: перевіряє, щоб покажчики-власники коректно викликали повний цикл деструкторів.
- **`clang-analyzer-cplusplus.NewDeleteLeaks`**: знаходить витоки пам'яті, спричинені пропущеними викликами деструкторів нащадків.

## Зведена матриця ідіом проектування деструкторів

| Ідіома проектування | Синтаксис оголошення | Статус vptr | Доступність `delete ptr` | Типовий сценарій використання |
| :--- | :--- | :--- | :--- | :--- |
| **Публічний віртуальний** | `public: virtual ~Base() = default;` | Додає vptr (8 байтів) | Дозволено звідусіль | Динамічний поліморфізм (`std::unique_ptr<Base>`, фабрики об'єктів). |
| **Захищений невіртуальний** | `protected: ~Base() = default;` | **Відсутній (0 байтів)** | Заборонено (помилка компіляції) | Базові класи домішок (Mixins), статичний поліморфізм CRTP, класи стратегій. |
| **Чисто віртуальний** | `public: virtual ~Base() = 0;` *(+ обов'язкове тіло)* | Додає vptr (8 байтів) | Дозволено звідусіль | Суто абстрактні інтерфейси без інших природних pure-методів. |
| **Приватний деструктор** | `private: ~Base();` *(friend-фабрика)* | Залежить від віртуальності | Лише через метод-фабрику | Контрольоване руйнування, патерни Singleton, пули пам'яті з підрахунком посилань. |
| **Кінцевий клас значення** | `public: ~Leaf() = default;` *(final)* | Відсутній (0 байтів) | Дозволено для `Leaf*` | DTO, математичні вектори, структури даних без успадкування. |
