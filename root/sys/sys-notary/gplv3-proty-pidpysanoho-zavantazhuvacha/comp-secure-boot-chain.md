# 🔌 Ланцюг криптографічної довіри Secure Boot

Безпечне завантаження (англ. *Secure Boot*) — це ієрархічний криптографічний механізм валідації, покликаний гарантувати, що кожен виконуваний програмний компонент обчислювальної системи є автентичним, не зазнав несанкціонованих модифікацій та походить від довіреного джерела. Архітектура безпечного завантаження базується на концепції **ланцюга довіри** (англ. *Chain of Trust*): кожен рівень системи перед передачею керування наступному завантажувальному модулю обов'язково перевіряє його цілісність та цифровий підпис за допомогою асиметричної криптографії.

Якщо на будь-якому етапі обчислений геш не збігається з підписом або сертифікат відсутній у базі дозволених ключів, процес завантаження негайно переривається, а процесор переходить у стан аварійного зупинення (*panic*) або блокує шини вводу-виводу.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    ІЄРАРХІЯ ЛАНЦЮГА SECURE BOOT                         │
├─────────────────────────────────────────────────────────────────────────┤
│ [Кремній / eFuses]    Публічний кореневий ключ (RoT PK Hash)           │
│         │                                                               │
│         ▼                                                               │
│ [BootROM (Незмінний)] Обчислює геш SPL / BL2 ──► Перевіряє RSA/ECDSA    │
│         │                                                               │
│         ▼                                                               │
│ [SPL / FSBL / Shim]   Валідує таблиці та підпис SSBL (U-Boot / GRUB2)   │
│         │                                                               │
│         ▼                                                               │
│ [SSBL (Завантажувач)] Верифікує FIT-образ / PE-COFF образ ядра Linux    │
│         │                                                               │
│         ▼                                                               │
│ [Ядро Linux]          Перевіряє модуль ядра (`.ko`) + dm-verity rootfs  │
└─────────────────────────────────────────────────────────────────────────┘
```

## 1. Апаратний корінь довіри (Hardware Root of Trust)

Основою будь-якого ланцюга безпечного завантаження є **апаратний корінь довіри** (англ. *Root of Trust*, RoT). Це набір апаратних вузлів всередині мікропроцесора (кристала SoC), функціонування яких вважається безумовно надійним і не може бути змінене програмними засобами після виготовлення чи конфігурації плати:

- **Одноразово програмовані перемички (OTP eFuses):** матриця мікроскопічних електричних запобіжників на кристалі кремнію. Під час фабричного програмування (англ. *provisioning*) виробник записує туди криптографічний геш публічного кореневого ключа (Root Public Key Hash) та прапорці безпеки (наприклад, `SEC_CONFIG[1] = 1`, що безповоротно вмикає обов'язкову перевірку підписів). Після перепалювання запобіжників змінити геш або вимкнути захист апаратно неможливо.
- **Вбудована пам'ять BootROM:** блок маскової пам'яті (Mask ROM), виготовлений на етапі літографії кремнієвої пластини. BootROM містить первинний завантажувальний код, який процесор починає виконувати одразу після скидання сигналу ресету (Reset Vector). Цей код містить реалізацію криптографічних алгоритмів (SHA-256/384, RSA-2048/4096 або ECDSA P-256/384) та апаратного зв'язку з регістрами eFuses.
- **Апаратні лічильники версій (Monotonic Anti-Rollback Counters):** спеціальні регістри eFuses, що зберігають мінімально допустимий номер версії прошивки. Вони унеможливлюють так звану атаку відкочування (англ. *downgrade attack* або *rollback attack*), коли зловмисник намагається прошити старий, але коректно підписаний вендором образ, що містить відомі вразливості нульового дня.

## 2. Первинний завантажувач: SPL, ATF та Shim

Обсяг внутрішньої статичної пам'яті процесора (SRAM), доступної на етапі роботи BootROM, зазвичай обмежений десятками або сотнями кілобайтів. Цього недостатньо для завантаження повноцінного ядра ОС або складної графічної оболонки. Тому BootROM завантажує компактний проміжний модуль — **первинний завантажувач** (англ. *First Stage Bootloader*, FSBL або *Secondary Program Loader*, SPL):

1. BootROM зчитує заголовок SPL із зовнішньої пам'яті (eMMC, SPI NOR Flash, NAND).
2. Заголовок містить метадані: адресу завантаження, довжину бінарного блоку, публічний ключ розробника та цифровий підпис самого образу.
3. BootROM обчислює криптографічний геш наданого публічного ключа і порівнює його з еталонним гешем, зашитим у eFuses.
4. Якщо геші збігаються, BootROM верифікує цифровий підпис тіла SPL за допомогою цього ключа.
5. У разі успішної перевірки керування передається у точку входу SPL, а контролер DDR-пам'яті ініціалізується для подальшої роботи.

В архітектурі ARM64 цей процес стандартизовано у специфікації ARM Trusted Firmware (TF-A), де етапи завантаження розділені на фази: BL1 (BootROM), BL2 (Trusted Boot Firmware), BL31 (EL3 Runtime), BL32 (Secure OS / OP-TEE) та BL33 (Non-secure World Bootloader).

На платформі ПК під керуванням UEFI еквівалентом цього етапу виступає мінімалістичний завантажувач **Shim** (під ліцензією BSD-2-Clause). Shim підписаний глобальним ключем Microsoft 3rd Party UEFI CA, що дозволяє йому безперешкодно стартувати на будь-якому x86-комп'ютері, після чого він розгортає власну базу сертифікатів дистрибутива Linux (Canonical, Red Hat, SUSE, Debian) та підтримує базу ключів власника машини (англ. *Machine Owner Key*, MOK).

## 3. Вторинний завантажувач та верифікація ядра

Отримавши керування, вторинний завантажувач (англ. *Second Stage Bootloader*, SSBL) — U-Boot, Barebox або GRUB 2 — готує апаратне середовище для запуску операційної системи.

У вбудованих Linux-системах найпоширенішим форматом є **FIT-образ** (англ. *Flattened Image Tree*). Це деревоподібна структура даних у форматі Device Tree Blob (`.dtb`), що об'єднує під одним дахом бінарний файл ядра `vmlinux`/`Image`, початковий диск у пам'яті `initramfs` та конфігураційні файли дерева пристроїв.

В U-Boot реалізовано механізм `CONFIG_FIT_SIGNATURE`:
- Підпис створюється утилітою `mkimage` під час збирання системи за допомогою приватного ключа RSA.
- Публічний ключ вбудовується у контрольний блок самого завантажувача U-Boot (у структуру `control.dtb`).
- Під час завантаження U-Boot перевіряє вузол `configurations`: підписується комбінація гешів ядра, initramfs та dtb, що унеможливлює підміну навіть окремого рядка конфігурації заліза.

У середовищі UEFI використовується підпис файлів формату PE/COFF (специфікація Microsoft Authenticode). Завантажувач GRUB 2 або Shim верифікує цифровий підпис образу ядра `vmlinuz` за алгоритмом PKCS#7 / CMS перед виконанням системного виклику UEFI `StartImage()`.

## 4. Захист ядра під час виконання: Lockdown та простори довіри

Перевірка підпису ядра перед запуском захищає систему лише від підміни файлу на диску. Щойно ядро завантажується в оперативну пам'ять, виникає новий виклик: користувач із правами суперкористувача (`root`) має технічну можливість модифікувати машинний код працюючого ядра (через пристрої `/dev/mem`, інтерфейси відлагодження `ptrace`, відладчик ядра `kprobes`, механізм сплячого режиму ACPI Hibernate або довільне завантаження сторонніх модулів ядра `.ko`).

Щоб ланцюг довіри не руйнувався після завершення завантаження, ядро Linux реалізує спеціальний режим ізоляції — **Kernel Lockdown Mode** (`kernel_lockdown(7)`):

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    РІВНІ РЕЖИМУ KERNEL LOCKDOWN                         │
├───────────────────┬─────────────────────────────────────────────────────┤
│ Рівень            │ Обмеження та механізми захисту                      │
├───────────────────┼─────────────────────────────────────────────────────┤
│ `none`            │ Звичайний режим: root має повний контроль над RAM. │
├───────────────────┼─────────────────────────────────────────────────────┤
│ `integrity`       │ Блокуються механізми прямого запису в пам'ять ядра: │
│                   │ • Заборонено запис у `/dev/mem` та `/dev/kmem`;     │
│                   │ • Завантаження модулів ядра (`insmod`) лише з        │
│                   │   дійсним криптографічним підписом (X.509);         │
│                   │ • Заборонено модифікацію MSR-регістрів CPU;          │
│                   │ • Заборонено kexec на непідписані ядра.             │
├───────────────────┼─────────────────────────────────────────────────────┤
│ `confidentiality` │ Додатково блокується читання чутливих даних:       │
│                   │ • Заборонено зчитування пам'яті ядра через `/dev/mem`│
│                   │ • Заблоковано трасування апаратних портів I/O;      │
│                   │ • Заборонено налагодження ядра через BPF/kprobes.   │
└───────────────────┴─────────────────────────────────────────────────────┘
```

Якщо система стартує в режимі UEFI Secure Boot, ядро автоматично вмикає режим блокування `integrity`. Це гарантує, що навіть скомпрометований процес простору користувача з правами root не зможе обійти захист Secure Boot та встановити прихований руткіт на рівні ядра.

## 5. Фізичні та апаратні вектори атак на ланцюг

Жоден криптографічний ланцюг не є абсолютним, якщо порушено фізичну безпеку мікросхеми. На практиці інженери захищають систему від таких критичних апаратних атак:

- **Ін'єкція збоїв за живленням та тактовою частотою (Voltage / Clock Glitching):** зловмисник подає короткочасний імпульс падіння напруги на ніжку живлення процесора в момент, коли інструкція перевірки результату криптографічного порівняння (`CMP R0, #0; BNE boot_fail`) завантажується в конвеєр виконання. Збій живлення змушує ALU процесора пропустити умовний перехід, і BootROM продовжує завантаження непідписаного коду. Сучасні SoC протидіють цьому за допомогою внутрішніх детекторів перепадів напруги (Brown-out Detectors) та рандомізації затримок конвеєра.
- **Перехоплення шин пам'яті (Bus Sniffing):** якщо шина між зовнішньою пам'яттю flash/RAM та процесором не зашифрована, зловмисник може модифікувати біти даних «на льоту». Для захисту застосовують механізми inline-шифрування шини (наприклад, AES-XTS контролери пам'яті в архітектурах NXP i.MX та AMD SME).
- **Апаратні інтерфейси налагодження (JTAG / SWD):** якщо лінії JTAG залишаються активними, будь-який дослідник може підключити апаратний програматор, зупинити виконання BootROM і записати власний код безпосередньо в регістри CPU. У комерційних пристроях доступ до JTAG безповоротно випалюється відповідним бітом у eFuses на виробництві.
