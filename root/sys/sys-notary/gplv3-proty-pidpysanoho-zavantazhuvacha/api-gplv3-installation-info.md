# 📋 Стаття 6 GPLv3: вимоги до Installation Information та критерії User Product

Стаття 6 ліцензії GNU General Public License версії 3 (GPLv3) — «Передача у формі, відмінній від вихідного коду» (англ. *Conveying Non-Source Forms*) — містить ключові правові норми щодо антитайвоізації. Вона регламентує обов'язки дистриб'ютора скомпільованого двійкового коду перед кінцевим одержувачем та встановлює межі апаратного контролю над виконанням програм. Нижче наведено систематизований довідник юридичних понять, структури зобов'язань, класифікації пристроїв, інженерних винятків та практичних стратегій відповідності.

## 1. Юридичні дефініції та термінологічний апарат

Текст статті 6 вводить три фундаментальні правові конструкції, які визначають, коли саме дистриб'ютор двійкового образу зобов'язаний розкрити криптографічну інформацію.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    КРИТЕРІЇ АКТИВАЦІЇ СТАТТІ 6 GPLv3                    │
├─────────────────────────────────────────────────────────────────────────┤
│ 1. Дія:         Передача бінарного образу (Conveying Object Code)       │
│                            │                                            │
│                            ▼                                            │
│ 2. Об'єкт:      У складі або для використання в «Споживчому продукті»  │
│                 (User Product)                                          │
│                            │                                            │
│                            ▼                                            │
│ 3. Зобов'язання:Надати повну «Інформацію для встановлення»              │
│                 (Installation Information) разом із вихідним кодом      │
└─────────────────────────────────────────────────────────────────────────┘
```

### Споживчий продукт (User Product)

Ліцензія визначає **«Споживчий продукт»** як будь-який матеріальний виріб особистого користування, що належить до однієї з двох категорій:
1. **Споживчі товари (Consumer Goods):** будь-яке рухоме майно, яке зазвичай використовується для особистих, сімейних або домашніх потреб. Це формулювання запозичене з комерційного права США (зокрема, закону про захист споживачів Магнусона-Мосса) та Директив Європейського Союзу про права споживачів.
2. **Товари для житла:** будь-які вироби, спроєктовані або продані для інтеграції, монтажу чи встановлення в житлових приміщеннях (наприклад, розумні термостати, датчики диму, системи керування освітленням, роутери Wi-Fi, домофони).

**Правові правила тлумачення статусу продукту:**
- *Презумпція споживчого призначення:* у разі виникнення сумнівів щодо того, чи є конкретний виріб споживчим, юридичний аналіз тлумачить статус продукту на користь його включення до категорії *User Product*.
- *Стандарт звичайного використання:* категорія виробу визначається за тим, як цей клас продукції **зазвичай** використовується на ринку, незалежно від специфічного статусу конкретного покупця (наприклад, купівля смарт-телевізора комерційною компанією для переговорної кімнати або планшета для складу не позбавляє ці вироби статусу *User Product*).

### Інформація для встановлення (Installation Information)

Під **«Інформацією для встановлення»** розуміється будь-який набір методів, процедур, ключів авторизації або інших технічних даних, необхідних для інсталяції та повноцінного запуску модифікованої версії програми на базі її відповідного вихідного коду (*Corresponding Source*).

**Обов'язковий склад Інформації для встановлення:**
- **Криптографічні ключі та токени:** приватні ключі підпису, симетричні ключі шифрування прошивки, паролі доступу до сервісних меню та цифрові сертифікати авторизації завантажувача.
- **Протоколи та утиліти запису:** інструкції з переводу плати в режим прошивки (ROM DFU, Fastboot, recovery), опис інтерфейсів передачі образу та вихідний код утиліт для взаємодії з апаратними завантажувачами.
- **Вимоги до апаратної цілісності:** документація щодо розташування перемичок, розпіновки сервісних роз'ємів (UART/JTAG, якщо вони необхідні для відновлення працездатності) та вимог до форматування розділів пам'яті.

## 2. Структура зобов'язань та обмежень

Стаття 6 накладає прямі вимоги до функціональності модифікованого програмного забезпечення після його встановлення:

```
┌───────────────────┬─────────────────────────────────────────────────────┐
│ Категорія вимоги  │ Зміст юридичного обов'язку за статтею 6            │
├───────────────────┼─────────────────────────────────────────────────────┤
│ Безперешкодний    │ Інформація повинна бути достатньою для того, щоб    │
│ запуск            │ модифікований бінарний код гарантовано виконувався  │
│                   │ процесором пристрою без аварійного блокування.      │
├───────────────────┼─────────────────────────────────────────────────────┤
│ Повнота           │ Якщо виробник використовує захищені апаратні чипи   │
│ ключів            │ (TPM, CryptoAuth, HSM), він зобов'язаний надати     │
│                   │ ключі, необхідні для підпису модифікованого образу. │
├───────────────────┼─────────────────────────────────────────────────────┤
│ Заборона          │ Заборонено вимагати підписання додаткових угод NDA  │

│                   │ отримання ключів інсталяції.                        │
└───────────────────┴─────────────────────────────────────────────────────┘
```

## 3. Межі винятків та безпечні гавані (Safe Harbors)

Стаття 6 GPLv3 містить чітко окреслені межі, які захищають вендорів від надмірних вимог та запобігають компрометації мережевої безпеки:

### Виняток мережевих сервісів (Network Access Safe Harbor)
Вимога надання інформації для встановлення **не зобов'язує** виробника продовжувати надання послуг хостингу, доступу до хмарного бекенду або підтримки пристрою, на якому запущено модифікований код. Якщо модифікація прошивки порушує правила мережевої взаємодії або створює загрозу стабільності сервісу, оператор має повне юридичне право заблокувати доступ такого пристрою до своєї хмарної інфраструктури (наприклад, відкликати сертифікат доступу до платного потокового відео або корпоративного API).

### Виняток фізичної неможливості оновлення (ROM Exception)
Якщо пристрій виготовлено з використанням маскової пам'яті (Mask ROM) або мікросхем одноразового запису (OTP PROM) без жодної технічної можливості оновлення прошивки навіть самим виробником (в апараті відсутні завантажувачі, USB-порти, бездротові інтерфейси оновлення чи механізми перепрошивки флеш-пам'яті), вимога надання *Installation Information* не застосовується, оскільки інсталяція нового коду є фізично неможливою.

### Промислове та корпоративне обладнання
Обладнання, спроєктоване виключно для комерційного, індустріального чи спеціального застосування (промислові програмовані логічні контролери ПЛК, вузли стільникового зв'язку Base Station, сервери центрів обробки даних, що не продаються фізичним особам), виведено з-під дії визначення *User Product*. Виробники таких систем мають право використовувати заблоковані криптографічні завантажувачі без розкриття приватних ключів.

### Виняток рантайм-бібліотек компілятора (GCC Runtime Exception v3.1)
Коли інженер компілює пропрієтарну програму компілятором GCC версії 4.3+ під GPLv3, до складу виконуваного файлу автоматично лінкуються системні модулі `libgcc.a` та стандартна бібліотека `libstdc++.so`. Щоб це не змушувало розкривати вихідний код і ключі пропрієтарних додатків, FSF створив *GCC Runtime Library Exception*: якщо код згенеровано безпосередньо процесом компіляції GCC з оригінального тексту, вимоги GPLv3 щодо копілефту та статті 6 на такий двійковий файл не поширюються.

## 4. Конфігурація білд-систем: вилучення GPLv3 у Yocto та Buildroot

Для комерційних вбудованих виробів із закритим апаратним Secure Boot системні архітектори зазвичай налаштовують автоматичне блокування пакетів під ліцензією GPLv3 на рівні системи збирання:

- **У білд-системі Yocto Project (Poky):**
  У конфігураційному файлі `conf/local.conf` або конфігурації дистрибутива вказується директива:
  `INCOMPATIBLE_LICENSE = "GPL-3.0-only GPL-3.0-or-later LGPL-3.0-only LGPL-3.0-or-later"`
  Це змушує Yocto автоматично замінювати утиліти GNU на дозвільні або GPLv2-альтернативи (наприклад, використовувати `busybox` або `toybox` замість `coreutils`, `bash` замінювати на `dash` або `ash`, завантажувач `grub` на `u-boot`).
- **У білд-системі Buildroot:**
  Через інтерфейс `make menuconfig` у розділі системних пакетів вимикаються утиліти GNU та обираються альтернативні компіляторні й системні стеки без копілефту третьої версії.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    МАТРИЦЯ ОЦІНКИ РИЗИКУ GPLv3                          │
├──────────────────────────┬──────────────────────┬───────────────────────┤
│ Тип пристрою             │ Апаратний захист     │ Рішення для GPLv3     │
├──────────────────────────┼──────────────────────┼───────────────────────┤
│ Споживчий IoT / Smart-TV │ Заблокований BootROM │ ❌ Неприпустимо:      │
│                          │ без доступу до MOK   │ Порушення ст. 6       │
├──────────────────────────┼──────────────────────┼───────────────────────┤
│ Споживчий IoT / Smart-TV │ Підтримка MOK /      │ ✔ Дозволено:          │
│                          │ меню розблокування   │ Ст. 6 виконана        │
├──────────────────────────┼──────────────────────┼───────────────────────┤
│ Промисловий контролер    │ Заблокований BootROM │ ✔ Дозволено:          │
│ (B2B, non-consumer)      │ виробника            │ Не є User Product     │
├──────────────────────────┼──────────────────────┼───────────────────────┤
│ Персональний комп'ютер   │ UEFI Secure Boot     │ ✔ Дозволено:          │
│ (x86 Desktop / Ноутбук)  │ з вимкненням у BIOS  │ Повний контроль юзера │
└──────────────────────────┴──────────────────────┴───────────────────────┘
```
