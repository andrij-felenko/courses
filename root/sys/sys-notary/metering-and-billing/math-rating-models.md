# 🧮 Математика тарифікації: східчасті моделі, передоплата та округлення

Рушій тарифікації (rating engine) перетворює потік фізичних або логічних вимірів (кількість викликів API, секунди роботи процесора, гігабайт-години збережених файлів, вхідні й вихідні токени мовних моделей) на грошові суми. Хоча зовні ця операція здається звичайним множенням кількості на ціну, у реальних білінгових системах формули швидко перетворюються на кусково-неперервні функції багатьох змінних із нетривіальними крайовими умовами, обмеженнями монотонності та вимогами до повної відсутності похибок заокруглення.

Тут ми формалізуємо основні математичні моделі тарифікації, доведемо необхідність монотонності цінових кривих, виведемо формули інтегрування часових мультиплікаторів, алгоритм розподілу списання передплачених кредитів, математику 95-го процентиля для оцінки смуги пропускання, пропорційний розподіл спільних витрат кластера та розберемо точну арифметику фіксованої коми й банківського округлення.

## 1. Моделі ціноутворення: кусково-лінійні функції

Нехай `u` — невід'ємна величина спожитого ресурсу (`u ≥ 0`) за розрахунковий період, виміряна в базових одиницях (запити, байти, токени або секунди). Функція вартості `C(u)` ставить у відповідність обсягу `u` грошову суму в базовій валюті.

Розглянемо три фундаментальні форми функції `C(u)`.

### Лінійна тарифікація (Flat-rate / Linear)

Найпростіший випадок — пряма пропорційність із фіксованою ставкою `p` за одиницю:

```
C(u) = u · p
```

Властивості лінійної моделі:
- Гранична вартість одиниці ресурсу є сталою: `dC/du = p`.
- Функція строго монотонна та однорідна першого степеня: `C(k · u) = k · C(u)`.

Ця модель є прозорою, але не враховує ефекту масштабу (економії на гуртовому споживанні) та не дозволяє встановлювати мінімальні пороги окупності інфраструктури.

### Блокова тарифікація (Volume-based Tiering)

У блоковій моделі ціна за одиницю залежить від того, у який діапазон (блок) потрапив *весь підсумковий обсяг* `u`.

Задано `n` порогових меж:

```
0 = T₀ < T₁ < T₂ < ... < Tₙ = ∞
```

Кожному інтервалу `(T_{k-1}, T_k]` відповідає своя ставка за одиницю `p_k`, де зазвичай `p₁ > p₂ > ... > pₙ` (чим більший обсяг, тим менша ставка).

Формула вартості блокової моделі:

```
C_vol(u) = u · p_k,   якщо T_{k-1} < u ≤ T_k
```

**Математичний дефект блокової моделі (розрив першого роду):**

У кожній точці порогового переходу `T_k` функція зазнає стрибка вниз (від'ємний розрив). Розглянемо ліву та праву границі у точці `T_k`:

```
Границя зліва:   lim_{u → T_k⁻} C_vol(u) = T_k · p_k
Границя справа:  lim_{u → T_k⁺} C_vol(u) = T_k · p_{k+1}
```

Оскільки `p_{k+1} < p_k`, стрибок вартості становить:

```
ΔC = T_k · (p_{k+1} - p_k) < 0
```

Це означає порушення монотонності: існують такі значення `u_a < u_b`, для яких `C_vol(u_a) > C_vol(u_b)`.

**Приклад аномалії:**
Нехай поріг `T₁ = 10 000` запитів.
Ставка `p₁ = $0.010` за запит для обсягів до 10 000.
Ставка `p₂ = $0.007` за запит для обсягів понад 10 000.

Розрахуємо вартість для 9 999 та 10 001 запитів:

```
C_vol(9999)  = 9999 · 0.010 = $99.99
C_vol(10001) = 10001 · 0.007 = $70.007 ≈ $70.01
```

Користувач, який використав на два запити більше, сплачує майже на $30 менше. Утворюється зона шкідливих економічних стимулів (perverse incentive): споживачеві математично вигідно згенерувати фіктивний трафік наприкінці розрахункового місяця, щоб перетнути поріг і зменшити фінальний рахунок. Через цей дефект блокова тарифікація вважається антипатерном у сучасному веб-білінгу.

### Пошарова тарифікація (Graduated / Tiered Pricing)

Пошарова модель усуває розриви: знижена ставка застосовується *виключно до тієї частини обсягу, яка перевищила поріг*, тоді як попередні частини тарифікуються за своїми ставками.

Формула вартості для `u ∈ (T_{k-1}, T_k]`:

```
C_grad(u) = ∑_{i=1}^{k-1} (T_i - T_{i-1}) · p_i  +  (u - T_{k-1}) · p_k
```

**Доведення неперервності та монотонності:**

Перевіримо неперервність у довільній точці переходу `T_k`:

```
Значення в точці T_k (кінці k-го рівня):
C_grad(T_k) = ∑_{i=1}^{k-1} (T_i - T_{i-1}) · p_i + (T_k - T_{k-1}) · p_k
            = ∑_{i=1}^{k} (T_i - T_{i-1}) · p_i                             [об'єднання суми з останнім доданком]

Границя при переході у (k+1)-й рівень:
lim_{u → T_k⁺} C_grad(u) = ∑_{i=1}^{k} (T_i - T_{i-1}) · p_i + lim_{u → T_k⁺} (u - T_k) · p_{k+1}
                         = ∑_{i=1}^{k} (T_i - T_{i-1}) · p_i + 0     [граничний перехід: (u - T_k) → 0]
                         = C_grad(T_k)                               [збіг зі значенням у точці T_k]
```

Ліва та права границі збігаються зі значенням функції. Отже, функція `C_grad(u)` є **неперервною** на всій області визначення `[0, ∞)`.

Похідна (гранична вартість) `dC_grad/du` на інтервалі `(T_{k-1}, T_k)` дорівнює `p_k > 0`. Оскільки похідна всюди строго додатна, функція `C_grad(u)` є **строго монотонно зростаючою**:

```
∀ u₁, u₂: u₁ < u₂  ⇒  C_grad(u₁) < C_grad(u₂)
```

Жодне додаткове використання ресурсу не може зменшити підсумковий рахунок, що виключає маніпуляції з фіктивним споживанням.

## 2. Моделі з мінімальним зобов'язанням та овердрафтом (Commitment & Overage)

Поширеним у B2B-контрактах є поєднання фіксованої базової плати з пакетом включених одиниць та оплатою за перевищення (overage):

- `B` — фіксована абонентська плата за період (Base Fee).
- `U_inc` — обсяг ресурсу, включений у базову плату (Included Allowance).
- `p_over` — тариф за одиницю перевищення понад `U_inc`.

Функція вартості записується через оператор максимуму:

```
C_over(u) = B + max(0, u - U_inc) · p_over
```

Якщо перевищення тарифікується пошарово за сіткою ставок `p_{over, k}`, то формула набуває вигляду:

```
C_over(u) = B + C_grad(max(0, u - U_inc))
```

Ця функція є опуклою (convex) кусково-лінійною зі зламом у точці `u = U_inc`, де граничні витрати стрибкоподібно зростають від 0 до `p_over`.

## 3. Багатовимірна тарифікація та інтегрування часових вікон

Сучасні хмарні операції рідко вимірюються одним скаляром. Наприклад, виклик моделі штучного інтелекту або запуск аналітичного запиту характеризується вектором метрик:

```
v = (x_prompt, x_completion, x_cached_prompt, x_compute_ms, x_egress_bytes)
```

де кожен компонент має власну цінову сітку `p_j`, яка додатково залежить від модифікаторів середовища:
- ідентифікатора ресурсу або моделі `M`;
- географічного регіону виконання `R`;
- часу доби `t` (піковий чи нічний тариф).

### Інтегрування вартості у неперервному часі (Time-varying Rates)

Якщо ресурс споживається неперервно впродовж часового інтервалу `[t_start, t_end]` (наприклад, віртуальний сервер споживає потужність з інтенсивністю `r(t)` vCPU за секунду), а ставка за секунду змінюється в часі `p(t)` (динамічні спотові тарифи або пікові коефіцієнти), повна вартість є інтегралом:

```
Cost = ∫_{t_start}^{t_end} r(t) · p(t) dt
```

Оскільки в дискретному конвеєрі бекенду тарифи змінюються стрибками у фіксовані моменти часу `t₀ < t₁ < ... < t_m` (наприклад, початок нічного тарифу о 00:00:00 UTC), інтеграл зводиться до суми кінцевих зрізів:

```
Cost = ∑_{k=1}^{m} r_k · p_k · Δt_k
```

де `Δt_k = t_k - t_{k-1}` — тривалість перебування всередині k-го тарифного вікна.

### Мультивалютне узгодження та валютні буфери

Якщо споживання обліковується в одній базовій валюті (наприклад, USD для глобальних моделей AI), а інвойс виставляється у локальній валюті клієнта (наприклад, EUR або UAH), обчислюється зважений курс валют на момент здійснення кожної транзакції:

```
Cost_local = ∑_{i=1}^{N} Cost_USD(E_i) · FX_rate(t_i)
```

де `FX_rate(t_i)` — зафіксований курс конвертації на мітку часу події `t_i`. Фіксація курсу в момент події (а не єдиного курсу наприкінці місяця) усуває валютний ризик (FX volatility) як для клієнта, так і для провайдера.

## 4. Алгоритм списання пулів передоплачених кредитів (Credit Burn-down)

Багато платформ продають абстрактні «кредити» (Credits / Tokens), які клієнт купує наперед. Оскільки кредити можуть надходити з різних джерел із різними умовами (маркетингові гранти з обмеженим терміном дії, річні передплачені пакети, додатково придбані кошти), система веде баланс як впорядкований список кредитних кошиків (Buckets).

Нехай активний баланс клієнта складається з `m` кошиків:

```
B = [ b₁, b₂, ..., bₘ ]
```

Кожен кошик `b_i` задається трійкою:

```
b_i = ( R_i, E_i, T_i )
```
де:
- `R_i` — залишок кредитів у кошику (`R_i ≥ 0`);
- `E_i` — мітка часу закінчення терміну дії (Expiration Timestamp);
- `T_i` — тип кошика (`PROMOTIONAL`, `PREPAID`, `OVERDRAFT`).

Коли надходить списання на суму `S` кредитів, застосовується детермінований пріоритет виснаження:

1. **Сортування кошиків:**
   Кошики впорядковуються за правилом:
   - Спочатку кошики з типом `PROMOTIONAL` (бо вони "згорають" першими).
   - За однакового типу — за зростанням `E_i` (найближча дата згоряння — принцип FIFO за часом життя).
   - За однакової дати — за зростанням ідентифікатора кошика (детермінізм).

2. **Послідовне списання (Water-filling / Drain loop):**

```
Залишок до списання: Δ = S
Для кожного кошика b_i у впорядкованому списку B:
  Якщо Δ = 0: перервати цикл
  d_i = min(R_i, Δ)         [сума, що списується з кошика i]
  R_i = R_i - d_i           [оновлення залишку кошика]
  Δ   = Δ - d_i             [зменшення необхідної суми]

Якщо після проходу Δ > 0:
  Зафіксувати овердрафт (непокрите споживання) на суму Δ.
```

Цей алгоритм гарантує, що клієнт не втратить кошти через передчасне закінчення терміну дії короткоживучих бонусів, а кожне часткове списання є математично прозорим для аудиту.

## 5. Тарифікація пікового навантаження: математика 95-го процентиля

Для інфраструктурних ресурсів зі змінним трафіком (пропускна здатність мережі в Мбіт/с, розмір виділеного пулу з'єднань, активні воркери) підсумкова плата часто базується не на сумарному обсязі байтів, а на піковій потужності.

Найвідоміша модель — **тарифікація за 95-м процентилем (Burstable 95th Percentile Billing)**.

### Формалізація алгоритму 95-го процентиля

1. Розрахунковий період (наприклад, 30 календарних днів) розбивається на рівні дискретні інтервали дискретизації `Δt = 5` хвилин (300 секунд).
2. Загальна кількість точок вимірювання за місяць:
   
```
N = (30 днів · 24 години · 60 хвилин) / 5 хвилин = 8 640 зрізів
```

3. Для кожного інтервалу обчислюється середнє значення швидкості трафіку `x_k = Bytes_k / 300`. Утворюється вибірка `X = { x₁, x₂, ..., x_N }`.
4. Вибірка сортується за зростанням (формується варіаційний ряд):

```
x_{(1)} ≤ x_{(2)} ≤ x_{(3)} ≤ ... ≤ x_{(N)}
```

5. Визначається індекс відсікання 95-го процентиля:

```
k_95 = ⌈0.95 · N⌉ = ⌈0.95 · 8640⌉ = 8 208
```

6. Розрахункова тарифікована швидкість встановлюється рівною значенню елемента `x_{(8208)}`:

```
R_bill = x_{(8208)}
```

Верхні 5% вибірки (рівно `8640 - 8208 = 432` п'ятихвилинних інтервали, або сумарно `432 · 5 / 60 = 36` годин на місяць) повністю відкидаються.

### Математичний зміст моделі

Модель 95-го процентиля забезпечує стійкість до випадкових короткочасних сплесків (DDoS-атаки, разове викачування бекапів, маркетингові промо-кампанії тривалістю менше півтори доби на місяць). Якщо клієнт більшу частину місяця споживає 100 Мбіт/с, але протягом 24 годин мав сплеск до 10 Гбіт/с, його фінальний рахунок буде розрахований строго за ставкою 100 Мбіт/с, оскільки весь сплеск умістився у відсічені 5% екстремумів.

## 6. Розподіл спільних витрат інфраструктури (Fair Cost Allocation)

У мультитенантних системах виникає завдання: як розподілити спільні непрямі витрати кластера (Fixed Base Cost `F_base`, наприклад, $1000/місяць за виділену базу даних або контрольну площину Kubernetes) між `K` орендарями, кожен із яких згенерував змінний обсяг споживання `u_i`.

Застосовується модель пропорційного зважування (Proportional Overhead Sharing):

```
Повне навантаження системи: U_total = ∑_{j=1}^{K} u_j

Частка i-го орендаря:       w_i = u_i / U_total

Підсумкова вартість:        C_total(i) = u_i · p_variable + w_i · F_base
```

Властивості моделі:
- **Баланс бюджету (Budget Balance):** Сума виставлених рахунків строго дорівнює повній собівартості інфраструктури:

```
∑_{i=1}^{K} C_total(i)
= p_variable · ∑ u_i  +  F_base · ∑ (u_i / U_total)   [підстановка формули C_total(i)]
= p_variable · U_total + F_base · 1                 [сума часток ∑ w_i ≡ 1]
= Total_Cost                                        [означення повної собівартості інфраструктури]
```

- **Симетрія та нульовий внесок:** Якщо клієнт не виконав жодного запиту (`u_i = 0`), його частка спільних витрат дорівнює нулю (`w_i = 0`), що відповідає моделі оплати виключно за споживання. Орендарі з однаковим рівнем використання `u_a = u_b` несуть строго однакові фінансові зобов'язання.

## 7. Точна фінансова арифметика: фіксована кома та похибки заокруглення

Головна пастка під час реалізації білінгу — використання двійкових чисел із плаваючою комою стандарту IEEE 754 (`float32` або `float64`/`double`).

### Пастка двійкового дробу

У двійковій системі число `0.1` є нескінченним періодичним дробом:

```
0.1₁₀ = 0.00011001100110011...₂
```

Під час представлення у 64-бітному типі `double` (53 біти мантиси) число зберігається з неминучим усіканням:

```
0.1000000000000000055511151231257827021181583404541015625
```

Якщо помножити цей дріб або накопичити суму для 10 мільйонів транзакцій вартістю по $0.000015:

```
Теоретична точна сума:
10 000 000 · 0.000015 = $150.000000

Акумуляція через двійковий double у наївному циклі:
sum = 150.0000000009388...
```

У фінансовому балансі реєстру виникає розбіжність між сумою сирих проведень і підсумковим інвойсом, через що бухгалтерія не може звести дебет і кредит у нуль.

### Арифметика фіксованої коми (Fixed-Point Micros / Nanos)

Єдине коректне інженерне рішення — відмова від `float` на користь цілих чисел із масштабуванням (Scaled Integers).

Замість доларів або центів усі обчислення ведуться в мікроцентах (`10⁻⁶` цента) або нанодоларах (`10⁻⁹` долара):

```
1 USD = 100 Cent = 100 000 000 Microcents = 1 000 000 000 Nanos
```

Множення кількості одиниць `u` на ціну в нанодоларах `p_nano`:

```
Cost_nano = u · p_nano      [цілочисельне множення 64-бітних цілих]
```

Оскільки операція проводиться над `int64` (або `int128`), точність є абсолютною: `d(A + B) ≡ dA + dB`.

### Стратегії заокруглення та накопичувальне зміщення (Rounding Bias)

Під час фінального формування інвойсу сума в нанодоларах має бути переведена у валюту платежу (центи). Для цього дріб ділиться на `10⁷` і заокруглюється до найближчого цілого цента.

Розглянемо дві основні стратегії заокруглення дробу `x = k + 0.5` (рівновіддалена середина):

**1. Арифметичне заокруглення від нуля (Round Half-Up):**
Правило: якщо залишок `≥ 0.5`, завжди округлювати вгору (до плюс нескінченності).

Математичне зміщення (Bias):
Якщо дробові частини транзакцій розподілені рівномірно на інтервалі `[0, 1)`, то рівновіддалена точка `0.5` завжди зсувається в бік збільшення. 
Математичне сподівання похибки заокруглення однієї транзакції:

```
E[Error_half_up] = +0.5 · P(x = k + 0.5) > 0
```

На мільярді транзакцій це створює накопичувальне завищення підсумкової суми (платформа систематично списує з клієнтів зайві гроші).

**2. Банківське заокруглення (Banker's Rounding / Round Half to Even):**
Правило: якщо дріб знаходиться рівно посередині (`0.5`), число округлюється до *найближчого парного цілого*.

Приклади:
```
1.5  → округлюється до 2  (2 — парне)
2.5  → округлюється до 2  (2 — парне)
3.5  → округлюється до 4  (4 — парне)
4.5  → округлюється до 4  (4 — парне)
```

Математична перевага банківського заокруглення:
Оскільки половина цілих чисел є парними, а половина — непарними, половина граничних випадків округлюється вгору, а інша половина — вниз:

```
E[Error_bankers] = (+0.5) · 0.5 + (-0.5) · 0.5 = 0
```

Математичне сподівання накопиченої похибки на великому масиві незалежних мікротранзакцій дорівнює нулю. Саме банківське заокруглення є стандартом ISO/IEC/IEEE 754 та загальноприйнятим правилом фінансового обліку GAAP/IFRS.

### Алгоритм переносу залишку (Bresenham Fractional Carry-Over)

Якщо білінгова система обробляє потік мікроподій у реальному часі й повинна списувати дискретні цілі центи або токени без втрати часток, застосовується алгоритм накопичення невживаного залишку (аналог алгоритму Брезенгема для дискретизації ліній):

```
Клас FractionalAccumulator:
    стан: remainder_nano = 0

    метод Charge(units, rate_nano):
        total_nano = units · rate_nano + remainder_nano
        cents_to_charge = ⌊total_nano / 10^7⌋
        remainder_nano  = total_nano mod 10^7
        повернути cents_to_charge
```

Усі дробові частки, які не увійшли в поточне списання, не губляться й не зрізаються, а переходять у наступну транзакцію як початковий залишок `remainder_nano`. Сума списань у часі залишається строго еквівалентною теоретичному інтегралу споживання:

```
∑_{k=1}^{N} Charge_k(u_k) + remainder_{final} ≡ ∑_{k=1}^{N} (u_k · rate_nano)
```

Цей простий алгоритм повністю ліквідує будь-яке витікання грошей (revenue leakage) або переплату клієнта незалежно від частоти та розміру одиничних подій.
