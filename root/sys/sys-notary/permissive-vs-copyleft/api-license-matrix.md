# 📋 Довідник сумісності ліцензійних умов та правил компонування

Цей довідник містить нормативні правила юридичної сумісності ліцензій відкритого коду при компонуванні бінарних образів, правила алгебри виразів SPDX, аналіз механізмів патентного захисту та критерії вибору архітектурних меж для запобігання неконтрольованому ліцензійному зараженню комерційних продуктів.

## 1. Загальні правила алгебри ліцензійної сумісності

При поєднанні кількох програмних компонентів в одному бінарному модулі або системному образі результуючий вихідний артефакт підпорядковується правилу **найсуворішого правового обмеження** (*One-Way Upstream Compatibility*). 

Сутність цього правила полягає в тому, що умови дозвільних ліцензій не суперечать умовам копілефту, оскільки пермісивні ліцензії дозволяють будь-яку подальшу дистрибуцію за умови збереження повідомлення про копірайт. Натомість копілефт вимагає, щоб **увесь скомпільований твір загалом** поширювався на умовах цієї копілефтної ліцензії.

Якщо компонент під слабшою ліцензією (наприклад, MIT або BSD-3-Clause) статично збирається разом із кодом під суворішою ліцензією (наприклад, GPLv3), результуючий виконуваний файл може поширюватися **виключно на умовах суворішої ліцензії (GPLv3)**. При цьому початкові вихідні файли, взяті з проєкту MIT, не змінюють свого ліцензійного тексту і зберігають первинне авторське маркування, проте комбінований бінарний файл підпорядковується вимогам GPLv3.

```
                  ┌──────────────────────┐
                  │    Public Domain     │ (CC0, Unlicense)
                  └──────────┬───────────┘
                             │  Дозволяє перехід
                             ▼
                  ┌──────────────────────┐
                  │  Permissive (MIT/BSD)│ (MIT, BSD-2/3, ISC)
                  └──────────┬───────────┘
                             │  Дозволяє перехід
                             ▼
                  ┌──────────────────────┐
                  │     Apache 2.0       │ (Додає патентний грант)
                  └──────────┬───────────┘
                             │  Сумісна з GPLv3 (Несумісна з GPLv2!)
                             ▼
                  ┌──────────────────────┐
                  │  Weak Copyleft (MPL) │ (MPL 2.0, LGPL v2.1/v3)
                  └──────────┬───────────┘
                             │  Дозволяє реліцензування
                             ▼
                  ┌──────────────────────┐
                  │ Strong Copyleft (GPL)│ (GPLv2, GPLv3)
                  └──────────┬───────────┘
                             │  Поглинається мережевим копілефтом
                             ▼
                  ┌──────────────────────┐
                  │ Network Copyleft     │ (AGPLv3)
                  └──────────────────────┘
```

## 2. Нормативна матриця сумісності для єдиного адресного простору

Таблиця визначає можливість поєднання двох компонентів (Компонент A та Компонент B) в одному двійковому файлі (статичне компонування або завантаження в спільну пам'ять процесу через системні виклики завантажувача):

| Вхідна ліцензія A | Вхідна ліцензія B | Можливість поєднання | Результуюча ліцензія артефакту | Особливі юридичні умови |
| :--- | :--- | :--- | :--- | :--- |
| **MIT / BSD-2 / BSD-3** | **MIT / BSD / ISC** | Сумісно | **MIT / BSD** | Збереження авторських рядків копірайту у документації або бінарнику. |
| **MIT / BSD-2 / BSD-3** | **Apache 2.0** | Сумісно | **Apache 2.0** | Збереження копірайтів та файлу `NOTICE` згідно з §4(d) Apache 2.0. |
| **MIT / BSD-2 / BSD-3** | **LGPL-2.1-only** | Сумісно | **LGPL-2.1-only** | Код MIT може входити в бібліотеку LGPL; весь артефакт під LGPL. |
| **MIT / BSD-2 / BSD-3** | **GPL-2.0-only** | Сумісно | **GPL-2.0-only** | Результуючий бінарник вимагає повного розкриття сирців під GPLv2. |
| **MIT / BSD-2 / BSD-3** | **GPL-3.0-only** | Сумісно | **GPL-3.0-only** | Результуючий бінарник вимагає повного розкриття сирців під GPLv3. |
| **Apache 2.0** | **GPL-2.0-only** | **НЕСУМІСНО ✖** | *Неможливо поширювати* | **Патентна колізія:** §3 Apache 2.0 (припинення ліцензії при патентному позові) є «додатковим обмеженням» у розумінні §6 GPLv2. |
| **Apache 2.0** | **GPL-2.0-or-later**| Сумісно | **GPL-3.0-or-later** | Дозволено шляхом підвищення версії GPL до 3.0 (§7 GPLv3 сумісна з Apache). |
| **Apache 2.0** | **GPL-3.0-only** | Сумісно | **GPL-3.0-only** | Стаття 7(e) GPLv3 явно дозволяє умови захисту від патентних позовів. |
| **LGPL-2.1-only** | **GPL-2.0-only** | Сумісно | **GPL-2.0-only** | Стаття 3 LGPLv2.1 дозволяє пряме переліцензування бібліотеки на GPLv2. |
| **LGPL-2.1-only** | **GPL-3.0-only** | **НЕСУМІСНО ✖** | *Неможливо поширювати* | LGPL-2.1-only сумісна лише з GPLv2; для переходу на GPLv3 потрібна клауза `LGPL-2.1-or-later`. |
| **LGPL-3.0-only** | **GPL-3.0-only** | Сумісно | **GPL-3.0-only** | Пряма сумісність через спільну кодову базу GPLv3. |
| **GPL-2.0-only** | **GPL-3.0-only** | **НЕСУМІСНО ✖** | *Неможливо поширювати* | **Ідеологічна колізія:** антитайвоізаційні вимоги GPLv3 §6 заборонені клаузою §6 GPLv2 («no further restrictions»). |
| **GPL-3.0-only** | **AGPL-3.0-only** | Сумісно | **AGPL-3.0-only** | Стаття 13 обох ліцензій явно дозволяє компонування модулів під AGPLv3. |
| **GPL-2.0 / GPL-3.0** | **Пропрієтарний** | **НЕЗАКОННО ✖** | *Контрафакт* | Статичне або тісне динамічне компонування порушує авторські права авторів GPL. |

## 3. Детальний аналіз патентної колізії Apache 2.0 та GPLv2

Найбільш підступною пасткою при формуванні дистрибутивів вбудованих систем є спроба скомпонувати в єдиний виконуваний модуль бібліотеку під ліцензією Apache 2.0 (наприклад, Apache Thrift або AWS IoT SDK) з кодом під ліцензією GPLv2-only (наприклад, утилітами BusyBox або окремими компонентами ядра).

Юридична причина несумісності криється у взаємодії двох конкретних статей цих ліцензій:

1. **Стаття 3 ліцензії Apache 2.0 (Patent License & Retaliation):**
   Кожен контрибутор надає користувачеві безвідкличну патентну ліцензію на використання технологій, втілених у коді. Проте якщо ліцензіат ініціює патентний судовий процес проти автора коду, стверджуючи, що програмний пакет порушує його патент, дія патентної ліцензії Apache 2.0 негайно та автоматично припиняється. Цей механізм називається «захисним патентним застереженням» (*patent retaliation clause*).
2. **Стаття 6 ліцензії GPLv2 (No Further Restrictions):**
   Текст GPLv2 встановлює категоричну заборону: дистриб'ютор не має права накладати на одержувача програми жодних додаткових обмежень щодо реалізації прав, наданих цією ліцензією («*You may not impose any further restrictions on the recipients' exercise of the rights granted herein*»).

Фонд вільного програмного забезпечення (FSF) офіційно визнав, що автоматичне припинення дії патентної ліцензії в Apache 2.0 є додатковим юридичним обмеженням, яке прямо заборонене статтею 6 ліцензії GPLv2. Оскільки жодна зі сторін не може відмовитися від умов своєї ліцензії, одночасне виконання вимог Apache 2.0 та GPLv2 в одному бінарному творі є юридично неможливим. Поширення такого двійкового образу автоматично анулює права на обидва компоненти.

У версії **GPLv3** цю колізію було повністю вирішено: стаття 7(e) нової ліцензії явно дозволяє додавати умови, які вимагають припинення прав у разі подання патентних позовів. Тому поєднання **Apache 2.0 + GPLv3** є повністю легітимним, а результуючий продукт поширюється під GPLv3.

## 4. Регламент використання бібліотек LGPL у комерційному коді

Ліцензії **LGPL-2.1** та **LGPL-3.0** розроблені для системних бібліотек і дозволяють їх використання з пропрієтарним кодом за дотримання трьох обов'язкових інженерних та юридичних умов:

1. **Динамічне лінкування (Shared Library Linking):**
   - Пропрієтарний додаток компонується з бібліотекою через динамічний завантажувач (`.so` в Linux або `.dll` у Windows).
   - Користувач пристрою повинен мати технічну можливість замінити бібліотеку LGPL на власну модифіковану версію без порушення працездатності додатку.
2. **Вимога перелінкування при статичному компонуванні:**
   - Якщо бібліотека LGPL збирається статично (`.a` / `.lib`) в єдиний монолітний бінарник із закритим кодом, виробник **зобов'язаний надати покупцям проміжний об'єктний код (`.o`)** закритого додатку разом із лінкерними скриптами, щоб користувач міг самостійно перелінкувати бінарник з оновленою версією бібліотеки.
3. **Заборона антиреверсних застережень:**
   - Угода користувача (EULA) комерційного продукту не має права забороняти зворотну розробку (*reverse engineering*) та зневадження (*debugging*) для модифікації бібліотеки LGPL.

## 5. Механізм файлового копілефту Mozilla Public License (MPL 2.0)

Ліцензія **MPL 2.0** пропонує компромісну модель слабкого копілефту, межа якого проходить не по лінії динамічного лінкування бібліотек, а виключно **по межах окремих вихідних файлів**:

- Якщо інженер модифікує існуючий файл під ліцензією MPL 2.0, цей файл та всі внесені до нього зміни залишаються під MPL 2.0 і підлягають обов'язковому оприлюдненню.
- Якщо інженер створює нові файли з власним закритим кодом і компілює їх разом із файлами MPL у єдиний виконуваний бінарник (концепція «Більшого твору», *Larger Work*, стаття 3.3 MPL), закриті файли не інфікуються і можуть поширюватися під комерційною пропрієтарною ліцензією.
- MPL 2.0 містить вбудовану сумісність із вторинними ліцензіями (*Secondary Licenses*): якщо у файлі немає явного маркування «Incompatible With Secondary Licenses», його можна реліцензувати під GPLv2, GPLv3, LGPLv2.1 або AGPLv3 для включення у великі вільні проєкти.

## 6. Специфікація виразів ліцензійної сумісності SPDX 2.3 / 3.0

Для машиночитаного аудиту в CI/CD використовуються стандартизовані логічні оператори специфікації SPDX (Software Package Data Exchange):

- **Оператор `AND`:** позначає, що результуючий бінарник вимагає одночасного виконання умов обох ліцензій.
  - Приклад: `MIT AND Apache-2.0` (необхідно надати текст копірайту MIT і файл `NOTICE` Apache).
- **Оператор `OR` (Dual Licensing):** дистриб'ютор або користувач має право самостійно обрати один із двох режимів виконання.
  - Приклад: `GPL-2.0-only OR Apache-2.0` (дозволяє обрати Apache 2.0 для уникнення копілефту).
- **Оператор `WITH` (Виняток із ліцензії):** модифікує базову ліцензію спеціальним юридичним винятком.
  - `GPL-2.0-only WITH Linux-syscall-note` — ядро Linux: системні виклики з простору користувача не заражають прикладні програми.
  - `GPL-3.0-or-later WITH GCC-exception-3.1` — компілятор GCC: скомпільований бінарний код не стає GPL через включення рантайм-коду `libgcc`.
  - `LGPL-3.0-or-later WITH WxWindows-exception-3.1` — графічна бібліотека wxWidgets: дозволяє статичне лінкування без обов'язку надавати `.o` файли.
