# 📋 Статті LGPLv2.1 §6 та LGPLv3 §4: юридичний контракт перелінкування

Ліцензії родини LGPL (GNU Lesser General Public License) визначають чіткий правовий та інженерний контракт між розробником відкритої бібліотеки та творцем комерційного чи закритого продукту. Центральне місце в цьому контракті займають умови дистрибуції комбінованих робіт: **стаття 6 ліцензії LGPLv2.1** та **стаття 4 ліцензії LGPLv3**.

Цей нормативний довідник містить детальний структурний розбір положень обох версій ліцензії, вимог до надання об'єктного коду, обмежень на заборону зворотного інжинірингу, правил обробки C++ шаблонів і макросів, патентних зобов'язань та вимог щодо апаратного оновлення прошивок.

## Понятійний апарат ліцензії: межі та категорії коду

Перш ніж аналізувати обов'язки дистриб'ютора, ліцензія встановлює точне розмежування трьох категорій коду, від яких залежить обсяг авторських прав та обов'язків:

```
┌────────────────────────────────────────────────────────────────────────┐
│                   КАТЕГОРІЇ КОДУ В КОНТЕКСТІ LGPL                      │
├───────────────────┬──────────────────────────┬─────────────────────────┤
│ Категорія         │ Юридичне визначення      │ Ліцензійні наслідки     │
├───────────────────┼──────────────────────────┼─────────────────────────┤
│ Бібліотека        │ Сам вихідний або         │ Будь-які модифікації    │
│ (The Library)     │ скомпільований код під   │ зобов'язані залишатися  │
│                   │ ліцензією LGPL.          │ під LGPL (копілефт).    │
├───────────────────┼──────────────────────────┼─────────────────────────┤
│ Твір, що          │ Програма, створена для   │ Дозволено залишати під  │
│ використовує      │ компіляції та зв'язу-    │ будь-якою закритою чи   │
│ бібліотеку (Work  │ вання з бібліотекою      │ комерційною ліцензією   │
│ that uses the Lib)│ через її інтерфейс.      │ (до моменту збирання).  │
├───────────────────┼──────────────────────────┼─────────────────────────┤
│ Комбінований      │ Виконуваний бінарний     │ Підпадає під дію        │
│ твір (Combined    │ файл або прошивка, що    │ LGPLv2.1 §6 або LGPLv3  │
│ Work)             │ об'єднує обидві частини. │ §4 при дистрибуції.     │
└───────────────────┴──────────────────────────┴─────────────────────────┘
```

Головна правова тонкість полягає в моменті перетворення: поки вихідний код вашої програми лежить у репозиторії у вигляді незалежних файлів `.c` або `.cpp`, він є суверенним твором (*Work that uses the Library*). Проте в момент, коли компілятор і лінкер об'єднують ці файли з бібліотекою у єдиний виконуваний двійковий файл (наприклад, прошивку мікроконтролера `firmware.elf`), результуючий бінарник стає **комбінованим твором**. Поширення такого комбінованого твору дозволяється лише за суворого дотримання умов статті 6 (у версії 2.1) або статті 4 (у версії 3.0).

## LGPLv2.1: Стаття 6 — Дистрибуція скомпільованих творів

Стаття 6 LGPLv2.1 регулює комерційне використання відкритої бібліотеки. Вона дозволяє поєднувати закриту програму з бібліотекою в єдиний образ або поширювати їх разом за умови виконання двох обов'язкових юридичних передумов:

1. **Дозвіл на модифікацію:** Умови ліцензійної угоди кінцевого користувача (EULA) або договору купівлі-продажу обладнання повинні прямо дозволяти замовнику модифікувати відкриту бібліотеку для власних потреб.
2. **Дозвіл на зворотний інжиніринг:** Ліцензія кінцевого продукту повинна прямо дозволяти зворотний інжиніринг (англ. *reverse engineering*) виключно для налагодження та інтеграції таких модифікацій.

Будь-які пункти комерційних договорів, які встановлюють абсолютну заборону на реверс-інжиніринг («Замовник не має права дизасемблювати, декомпілювати або вивчати структуру двійкового коду»), прямо суперечать статті 6 LGPLv2.1. У разі судового спору такі обмеження або визнаються нікчемними, або спричиняють повне анулювання прав вендора на використання LGPL-бібліотеки.

### Механізми виконання обов'язку перелінкування (Пункти 6a–6e)

Щоб гарантувати користувачеві можливість замінити бібліотеку модифікованою версією, дистриб'ютор зобов'язаний надати один із п'яти передбачених ліцензією інженерних механізмів:

```
┌────────────────────────────────────────────────────────────────────────┐
│                 МЕХАНІЗМИ ВИКОНАННЯ LGPLv2.1 СТАТТІ 6                  │
├───────┬──────────────────────┬─────────────────────────────────────────┤
│ Пункт │ Механізм             │ Інженерні вимоги до дистриб'ютора       │
├───────┼──────────────────────┼─────────────────────────────────────────┤
│ 6a    │ Об'єктний код або    │ Надати повний вихідний код бібліотеки   │
│       │ повний вихідний код  │ ТА повний об'єктний код програми (.o),  │
│       │ додатку              │ щоб користувач міг перелінкувати образ. │
├───────┼──────────────────────┼─────────────────────────────────────────┤
│ 6b    │ Механізм спільної    │ Використати динамічний лінкер ОС.       │
│       │ бібліотеки (Shared   │ Бібліотека існує як окремий файл (.so), │
│       │ Library Mechanism)   │ а додаток зв'язується під час запуску.  │
├───────┼──────────────────────┼─────────────────────────────────────────┤
│ 6c    │ Письмова оферта      │ Додати письмову пропозицію надати       │
│       │ (Written Offer)      │ матеріали з пунктів 6a або 6b, дійсну   │
│       │                      │ щонайменше 3 роки.                      │
├───────┼──────────────────────┼─────────────────────────────────────────┤
│ 6d    │ Мережевий репозиторій│ Надати публічний мережевий доступ для   │
│       │ (Designated Place)   │ безкоштовного завантаження об'єктного   │
│       │                      │ коду та вихідників бібліотеки.          │
├───────┼──────────────────────┼─────────────────────────────────────────┤
│ 6e    │ Перевірка наявності  │ Переконатися, що бібліотека вже є в     │
│       │ бібліотеки в системі │ системі користувача (для системних утиліт)│
└───────┴──────────────────────┴─────────────────────────────────────────┘
```

Найважливішим для системної архітектури є пункт **6b (Shared Library Mechanism)**. Він встановлює два технічні критерії:
- Додаток повинен використовувати наявну в системі копію бібліотеки під час виконання, а не копіювати функції бібліотеки у свій двійковий образ під час компіляції.
- Додаток повинен коректно функціонувати з модифікованою версією бібліотеки, якщо модифікована версія зберігає інтерфейсну сумісність (ABI) з версією, для якої розроблявся додаток.

Якщо цільова платформа не має операційної системи або завантажувача з підтримкою пункту 6b, єдиним законним шляхом залишається пункт **6a** — постачання скомпільованих об'єктних файлів `.o`.

## Виняток для заголовкових файлів, макросів та inline-коду (LGPLv2.1 §5)

Коли пропрієтарний файл вихідного коду підключає заголовковий файл (`#include <library.h>`), препроцесор і компілятор переносять частину визначень безпосередньо у скомпільований об'єктний файл `.o`.

Стаття 5 LGPLv2.1 розв'язує потенційний конфлікт, визначаючи поріг «інтерфейсного мінімуму»:

```
Критерії винятку за статтею 5 LGPLv2.1:
1. Визначення числових параметрів, констант і типів даних.
2. Макети структур та об'єднань (struct/union layouts).
3. Невеликі макроси та вбудовані функції (inline functions)
   завдовжки НЕ БІЛЬШЕ 10 рядків коду.
→ Об'єктний файл залишається «твором, що використовує бібліотеку»,
  і НЕ перетворюється на похідний твір від бібліотеки.
```

Якщо заголовковий файл містить розлогі вбудовані функції, складні алгоритми у макросах або шаблони класів C++ (англ. *templates*), тіло яких перевищує 10 рядків, скомпільований об'єктний файл юридично вважається похідним твором. У такому разі дистриб'ютор втрачає право вважати свій об'єктний файл незалежним і зобов'язаний поширювати його за суворими правилами статті 6.

## LGPLv3: Стаття 4 — Комбіновані твори та антитайвоїзація

Ліцензія LGPLv3 (2007 рік) побудована як документ «додаткових дозволів» над базовим текстом суворої ліцензії GPLv3. Стаття 4 LGPLv3 замінює статтю 6 попередньої версії і вводить термін **«Комбінований твір»** (*Combined Work*).

```
┌────────────────────────────────────────────────────────────────────────┐
│                 ВИМОГИ СТАТТІ 4 ЛІЦЕНЗІЇ LGPLv3                        │
├───────────────────────────────────┬────────────────────────────────────┤
│ Обов'язок атрибуції               │ Зберегти всі повідомлення про      │
│                                   │ авторські права у вихідному коді   │
│                                   │ та на видному місці інтерфейсу.    │
├───────────────────────────────────┼────────────────────────────────────┤
│ Надання коду бібліотеки           │ Передати Відповідний вихідний код  │
│ (Corresponding Source)            │ бібліотеки у формі, передбаченій   │
│                                   │ статтями 4–6 ліцензії GPLv3.       │
├───────────────────────────────────┼────────────────────────────────────┤
│ Надання коду додатку              │ Надати Об'єктний код додатку       │
│ (Application Object Code)         │ (Application Structure / .o) або   │
│                                   │ забезпечити механізм спільної .so. │
├───────────────────────────────────┼────────────────────────────────────┤
│ Інформація про встановлення       │ Якщо пристрій є «споживчим» (User  │
│ (Installation Information, GPLv3§6)│ Product), надати всі ключі, серти- │
│                                   │ фікати та інструкції прошивання.   │
└───────────────────────────────────┴────────────────────────────────────┘
```

Головною відмінністю LGPLv3 є пряма інтеграція зі статтею 6 GPLv3 щодо **Інформації про встановлення** (*Installation Information*). Якщо комбінований твір поширюється у складі споживчого пристрою (побутова техніка, телевізори, роутери, автомобілі, мультимедійні блоки), виробник зобов'язаний надати замовнику:
- Усі криптографічні ключі, необхідні для підпису та верифікації модифікованого двійкового образу прошивки.
- Опис протоколів прошивання та сервісних утиліт завантажувача.
- Інструкції, що гарантують, що модифікована прошивка буде безперешкодно запущена апаратним забезпеченням.

Якщо виробник використовує апаратний криптографічний чип або захищений завантажувач Secure Boot, який відхиляє прошивки без цифрового підпису вендора, і відмовляється передати ключі користувачеві, це є прямим порушенням LGPLv3.

## Патентні застереження та судова практика

Ліцензія LGPLv3 містить пряме положення про взаємне надання патентних ліцензій (стаття 3 GPLv3, яка поширюється на LGPLv3). Кожен автор або розробник, який робить внесок у код бібліотеки, автоматично надає безстрокову безкоштовну ліцензію на всі свої патенти, втілені у цьому коді.

Якщо комерційна компанія лінкує бібліотеку під LGPLv3 і згодом подає судовий позов проти користувача чи іншого розробника за порушення патентів, пов'язаних із кодом бібліотеки, її власна ліцензія на LGPLv3 автоматично анулюється (*patent retaliation clause*).

У судовій практиці європейських країн (зокрема серії прецедентів за позовами Гаральда Вельте, *Welte v. D-Link*, *Welte v. Sitecom* у судах Німеччини) було встановлено:
- Відсутність повної інструкції та скриптів для повторного збирання бінарного образу прирівнюється до повної ненадачі вихідного коду.
- Посилання на «закритість архітектури апаратного забезпечення» не є виправданням для невиконання умов надання об'єктного коду для перелінкування.
- Суди беззастережно видають приписи про конфіскацію партій приладів та заборону їх імпорту до повного усунення ліцензійних порушень.

### Порівняльний аналіз: LGPLv2.1 проти LGPLv3

```
┌──────────────────────────────┬────────────────────────┬────────────────────────┐
│ Параметр                     │ LGPLv2.1 (1999)        │ LGPLv3.0 (2007)        │
├──────────────────────────────┼────────────────────────┼────────────────────────┤
│ Структура тексту             │ Автономний документ    │ Перелік винятків до    │
│                              │                        │ ліцензії GPLv3         │
│ Зворотний інжиніринг         │ Обов'язковий дозвіл    │ Обов'язковий дозвіл    │
│ для налагодження             │ (стаття 6)             │ (стаття 4)             │
│ Динамічне лінкування (.so)   │ Дозволене (пункт 6b)   │ Дозволене (стаття 4d0) │
│ Статичне лінкування (.o)     │ Вимагає надання .o     │ Вимагає надання .o     │
│ Патентна ліцензія            │ Неявна                 │ Явна патентна ліцензія │
│                              │                        │ та захист від патентів │
│ Антитайвоїзація              │ Відсутня (можна шити   │ Обов'язкова для        │
│ (Installation Info)          │ криптопідписом)        │ побутових пристроїв    │
└──────────────────────────────┴────────────────────────┴────────────────────────┘
```

Юридична суворість LGPLv3 робить її практично несумісною з комерційними монолітними вбудованими пристроями, в яких реалізовано апаратний корінь довіри (*Hardware Root of Trust*). У таких системах статичне компонування бібліотек під LGPLv3 створює непереборний конфлікт між вимогами інформаційної безпеки та ліцензійними зобов'язаннями перед правовласниками відкритого коду.
