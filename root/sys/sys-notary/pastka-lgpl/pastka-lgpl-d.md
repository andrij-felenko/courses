Коли інженерний відділ готує до серійного виробництва нову апаратну платформу — наприклад, контролер промислового приводу на базі мікроконтролера ARM Cortex-M4 з 512 кілобайтами оперативної пам'яті та двома мегабайтами флеш-пам'яті, — типовий процес розробки виглядає як збирання конструктора. Пропрієтарні алгоритми безсенсорного векторного керування двигуном, адаптивні ПІД-регулятори та цифрові фільтри пишуться всередині компанії, а для вирішення стандартних інженерних завдань залучаються готові сторонні модулі: алгоритми компресії діагностичних логів `liblzma`, криптографічні підсистеми або стеки промислових протоколів обміну даними.

Під час попереднього аудиту ліцензійної чистоти юридичний відділ зазвичай вимагає категорично уникати ліцензії GNU GPL. Причина очевидна: сильний копілефт (англ. *copyleft*, від англ. *left* — залишене, вільне, на противагу *right* — монопольне право) вимагає відкриття повного вихідного коду всього комбінованого твору. Побачивши у репозиторії сторонньої бібліотеки ліцензію GNU Lesser General Public License (LGPL версії 2.1 або 3.0), розробники та керівники проєктів зітхають із полегшенням: у масовій інженерній культурі закріпився стійкий міф про те, що «LGPL створена спеціально для бібліотек і дозволяє безперешкодно лінкувати закритий комерційний код із відкритим модулем».

Проте щойно готовий двійковий образ прошивки `firmware.bin` компілюється в монолітний масив, прошивається на заводському програматорі у внутрішню пам'ять контролера і партія приладів вирушає замовникам, компанія потрапляє в класичну юридичну пастку. Виявляється, що за умов відсутності операційної системи з динамічним завантажувачем (англ. *dynamic linker*) ліцензія LGPL накладає на виробника зобов'язання, які практично унеможливлюють збереження комерційної таємниці або вимагають докорінної зміни всієї системної архітектури пристрою.

## Юридична природа компромісу: чому LGPL вимагає перелінкування

Щоб зрозуміти причину виникнення цієї пастки, необхідно розглянути юридичний баланс інтересів, закладений творцями ліцензії LGPL (спочатку *GNU Library General Public License*, а згодом *GNU Lesser General Public License*).

На відміну від дозвільних (англ. *permissive*, від лат. *permissivus* — той, що дозволяє) ліцензій, таких як MIT, BSD або Apache 2.0, які дозволяють беззастережно приватизувати відкритий код та включати його у закриті комерційні продукти за умови збереження повідомлення про авторство, ліцензія LGPL залишається копілефтною. Її мета — не безкоштовне надання коду корпораціям, а гарантування кінцевому користувачеві програмного продукту непорушних прав на вивчення, модифікацію, виправлення помилок та заміну відкритого компонента у будь-якому оточенні, де цей компонент працює.

```
┌────────────────────────────────────────────────────────────────────────┐
│                   ФІЛОСОФСЬКИЙ КОНТРАКТ ЛІЦЕНЗІЇ LGPL                  │
├───────────────────────────────────┬────────────────────────────────────┤
│ Що ліцензія дозволяє автору       │ Що ліцензія вимагає надати         │
│ пропрієтарного додатку            │ кінцевому користувачеві            │
├───────────────────────────────────┼────────────────────────────────────┤
│ • Зберігати вихідний код власного │ • Право вільно модифікувати        │
│   додатку в таємниці.             │   код відкритої LGPL-бібліотеки.   │
│ • Поширювати комерційний бінарний │ • Реальний інженерний механізм     │
│   продукт на власних умовах.      │   запуску комерційного додатку     │
│ • Не надавати патентних ліцензій  │   з оновленою (модифікованою)      │
│   на свій пропрієтарний код.      │   версією цієї бібліотеки.         │
└───────────────────────────────────┴────────────────────────────────────┘
```

Цей принцип закріплено у **статті 6 ліцензії LGPLv2.1** та **статті 4 ліцензії LGPLv3**. Ліцензія проголошує непорушне правило: ви маєте право поширювати закриту програму, яка використовує бібліотеку під LGPL, лише за умови, що ви надаєте користувачеві доступний і практично здійсненний інженерний спосіб **перекомпонувати (перелінкувати)** або запустити модифіковану версію цієї бібліотеки разом із вашою програмою.

У праві інтелектуальної власності (зокрема за нормами Розділу 17 Кодексу США про авторське право та Директиви ЄС 2009/24/EC про правову охорону комп'ютерних програм) будь-яка компіляція двох модулів у єдиний виконуваний двійковий файл створює єдиний **похідний або складений твір** (англ. *derivative work* або *composite work*). За замовчуванням правовласник кожного компонента має абсолютне право заборонити поширення такого комбінованого бінарника.

Ліцензія LGPL створює виняток із монопольного права автора бібліотеки, але обумовлює цей виняток суворою вимогою взаємності: комерційний розробник отримує право не відкривати вихідний код своєї частини лише в обмін на надання кінцевому споживачеві реальної інженерної свободи заміни відкритої частини.

Детальний постатейний юридичний аналіз тексту обох версій ліцензії та нормативних винятків наведено в довіднику [Статті LGPLv2.1 §6 та LGPLv3 §4: юридичний контракт перелінкування](root:sys-notary/pastka-lgpl/api-lgpl-clauses.md).

## Десктопний світ: чому на Linux та Windows проблеми не існує

На персональних комп'ютерах, серверах та смартфонах під керуванням операційних систем із повноцінним ядром (Linux, FreeBSD, Windows, macOS) виконання вимог LGPL досягається природним шляхом завдяки **динамічному лінкуванню** (англ. *dynamic linking*, від грец. *dynamis* — сила, рух).

Коли пропрієтарна програма компілюється на операційній системі з динамічним завантажувачем, компілятор створює двійковий файл формату ELF або PE/Mach-O. Усі виклики функцій з LGPL-бібліотеки залишаються у вигляді незаповнених посилань у таблиці імпорту динамічних символів, а в секції динамічного заголовка записується тег `DT_NEEDED` із назвою файлу спільної бібліотеки (наприклад, `libcrypto.so.3` або `libavcodec.so.59`).

![Порівняння динамічного та статичного лінкування в контексті зобов'язань LGPL](/root/sys/sys-notary/pastka-lgpl/img/static-vs-dynamic-lgpl.svg)
*Порівняння правового статусу компонування: на операційних системах із динамічним завантажувачем зв'язування відбувається в пам'яті через окремі файли `.so`, тоді як у вбудованих монолітах статичне об'єднання `.o` та `.a` вимагає передачі закритих об'єктних файлів.*

У такій архітектурі юридичний договір виконується автоматично:
1. Бібліотека постачається як окремий файл спільного об'єкта `libcrypto.so`.
2. Пропрієтарний додаток постачається як окремий бінарник `my_proprietary_app`.
3. Якщо користувач знаходить вразливість у криптографічній бібліотеці, він завантажує її вихідний код, виправляє помилку, компілює власну версію `libcrypto.so.3` і замінює файл у каталозі `/usr/lib` або підміняє шлях через системну змінну `LD_LIBRARY_PATH`.
4. Під час наступного старту програми системний динамічний завантажувач (`ld.so`) зв'язує закритий двійковий файл із новою бібліотекою користувача прямо в оперативній пам'яті процесу.

Компанії-виробнику закритого софту для повної ліцензійної чистоти достатньо виконати дві базові дії: поширювати бібліотеку як спільний об'єкт (`.so` або `.dll`) та надати посилання на вихідний код цієї бібліотеки. Жоден рядок власного коду відкривати не потрібно, а об'єктні файли додатку залишаються всередині закритого контуру розробки.

## Вбудований світ: фізика статичного моноліту

У світі мікроконтролерів (bare-metal розробка на чистому залізі) та класичних операційних систем реального часу (RTOS — FreeRTOS, Zephyr у монолітній конфігурації, ThreadX, Keil RTX, embOS) архітектура виконання програм докорінно відрізняється від настільних систем.

```
┌────────────────────────────────────────────────────────────────────────┐
│            МОНОЛІТНА СТРУКТУРА ПАМ'ЯТІ МІКРОКОНТРОЛЕРА                 │
├────────────────────────────────────────────────────────────────────────┤
│ 0x08000000: Вектори переривань (ISR Vector Table)                      │
│ 0x08000100: Пропрієтарний код керування (секція .text)                 │
│ 0x08040000: Статично вшита LGPL-бібліотека (mbedtls/lzma)              │
│ 0x08080000: Таблиці констант та рядків (секція .rodata)                │
│                                                                        │
│ Усі відносні адреси переходів (BL/BLX у Thumb-2) обчислені на етапі    │
│ збирання прошивки лінкером 'ld' і жорстко зашиті у флеш-пам'ять.       │
└────────────────────────────────────────────────────────────────────────┘
```

У мікроконтролерах немає апаратного блоку керування віртуальною пам'яттю (MMU), немає файлової системи зі спільними бібліотеками та немає системного динамічного завантажувача. Розробка відбувається за схемою прямої статичної трансляції:
1. Компілятор перетворює кожен вихідний файл `.c` або `.cpp` на окремий релокабельний об'єктний файл `.o`.
2. Статичний компонувальник (лінкер `arm-none-eabi-ld` або `lld`) зчитує всі об'єктні файли додатку та статичні архіви бібліотек `.a` (які є простими архівами файлів `.o`).
3. Лінкер аналізує скрипт розміщення секцій `linker_script.ld`, вирішує всі символьні адреси, обчислює зміщення для інструкцій переходу (наприклад, інструкцій `BL` та `BLX` в архітектурі ARM Thumb-2) і генерує монолітний файл образу `firmware.elf`.
4. Під час зв'язування лінкер обробляє таблиці релокацій (наприклад, типи записів `R_ARM_THM_CALL` для викликів підпрограм або `R_ARM_ABS32` для абсолютних адрес глобальних змінних). Усі символьні посилання остаточно замінюються на конкретні фізичні адреси у флеш-пам'яті або SRAM.
5. Утиліта `objcopy` видаляє всі службові заголовки ELF і формує сирий плоский масив байтів `firmware.bin`, який байт за байтом записується у флеш-пам'ять за базовою адресою (наприклад, `0x08000000`).

Коли в такий монолітний образ статично лінкується бібліотека під ліцензією LGPL, вона фізично перестає існувати як окрема сутність. Її функції перемішуються з пропрієтарними функціями, змінні потрапляють у спільні секції оперативного завантаження `.data` та `.bss`, а виклики перетворюються на абсолютні та відносні зміщення адрес у кристалі пам'яті.

У цей момент набуває чинності пункт 6a статті 6 ліцензії LGPLv2.1 (або стаття 4d0 ліцензії LGPLv3): **якщо у системі не використовується механізм спільної динамічної бібліотеки, дистриб'ютор ЗОБОВ'ЯЗАНИЙ надати користувачеві повний вихідний код бібліотеки РАЗОМ із повним об'єктним кодом пропрієтарного додатку (`.o` файли) та скриптами лінкування, щоб користувач мав реальну можливість власноруч перелінкувати виконуваний образ із модифікованою бібліотекою**.

![Анатомія пастки LGPL у вбудованих пристроях](/root/sys/sys-notary/pastka-lgpl/img/embedded-relink-trap.svg)
*Анатомія юридичної пастки: виробник вбудованого виробу опиняється перед дилемою між судовим позовом за порушення копілефту та витоком комерційної таємниці через надання об'єктних модулів.*

## Чому надання `.o`-файлів є катастрофою для комерційного продукту

Багато розробників і керівників підприємств помилково припускають: «Якщо закон вимагає надати об'єктні файли `.o`, ми просто надамо скомпільовані бінарні модулі замість вихідного коду `.c`. Оскільки це бінарний машинний код, наша інтелектуальна власність залишиться надійно захищеною».

Це одне з найнебезпечніших інженерних і юридичних самообманів у вбудованій індустрії. На практиці обов'язок надання об'єктних файлів створює п'ять критичних загроз, здатних знищити комерційну цінність продукту.

### 1. Декомпіляція та прозорість внутрішньої архітектури

Об'єктний файл `.o` містить колосальний обсяг структурованої метаінформації, якої немає у фінальному монолітному образі `firmware.bin`.

Під час компіляції модуля компілятор зберігає в об'єктному файлі:
- **Чіткі межі функцій:** Кожна функція є ізольованою секцією коду зі своєю точкою входу, прологом та епілогом стека.
- **Таблиці релокацій (`.rel.text` або `.rela.text`):** Лінкерні записи точно вказують, до яких глобальних змінних, структур даних або зовнішніх драйверів звертається кожна конкретна інструкція.
- **Символьні таблиці (`.symtab` та `.strtab`):** Якщо символи не були агресивно локалізовані, файл містить точні імена функцій, обробників переривань та системних структур.
- **Розмітку структур даних:** Зсуви полів у структурах, розміри буферів та типи констант відновлюються майже автоматично.

Сучасні інструменти реверсивного інжинірингу — такі як IDA Pro, Ghidra від АНБ США або Binary Ninja — декомпілюють окремий об'єктний файл `.o` у читабельний, практично готовий до повторного використання C-код. Якщо у пристрої реалізовано пропрієтарний алгоритм цифрової обробки сигналів, унікальна модель компенсації температурного дрейфу сенсора чи алгоритм шифрування каналу зв'язку, надання файлу `proprietary_core.o` конкурентам рівнозначне публікації вихідного коду на відкритому сервері.

### 2. Пряма заборона на договірне обмеження зворотного інжинірингу

У класичних ліцензійних угодах кінцевого користувача (EULA), комерційних договорах поставки та сервісних контрактах завжди міститься обов'язкове положення про заборону дослідження програми: «Покупцеві категорично забороняється декомпілювати, дизасемблювати, вивчати структуру або здійснювати зворотний інжиніринг будь-якої частини програмного забезпечення».

Проте стаття 6 ліцензії LGPLv2.1 містить категоричну імперативну вимогу:

> *«Ви повинні дозволити зворотний інжиніринг виключно з метою налагодження модифікацій відкритої бібліотеки».*

Це означає, що якщо клієнт, отримавши прилад і файли `.o`, завантажить їх в інтерактивний декомпілятор для «налагодження сумісності оновленої версії бібліотеки», виробник позбавлений будь-якого юридичного захисту. Будь-який пункт комерційного договору, що забороняє реверс-інжиніринг, буде визнаний судом нікчемним на підставі пріоритету умов ліцензії LGPL. Якщо ж виробник спробує наполягати на забороні дослідження коду, він автоматично визнається порушником ліцензії LGPL, що призводить до негайного анулювання ліцензійних прав та позову за порушення авторських прав (*copyright infringement*).

### 3. Конфлікт із криптографічним захистом: Secure Boot та антитайвоїзація

В абсолютній більшості сучасних промислових контролерів, автомобільних блоків (ECU), медичних приладів та систем розумного будинку використовується апаратний корінь довіри (*Hardware Root of Trust*). Завантажувач пристрою (Secure Boot) перевіряє цифровий підпис прошивки перед її стартом за допомогою відкритого асиметричного ключа (RSA або ECDSA), вшитого в одноразово програмовані регістри чіпа (OTP/eFuse). Якщо образ модифіковано або підпис недійсний, контролер переходить у режим блокування.

Якщо у такій системі статично використовується бібліотека під ліцензією **LGPLv3**, вимога перелінкування перетворюється на технічну міну під системою безпеки. Стаття 4 LGPLv3 прямо інтегрує статтю 6 ліцензії GPLv3, яка встановлює обов'язок надання **«Інформації про встановлення»** (англ. *Installation Information*) для споживчих товарів (*User Products*).

Виробник зобов'язаний надати покупцеві пристрою:
- Усі криптографічні ключі або сертифікати, необхідні для підпису модифікованого двійкового образу, АБО
- Апаратний чи програмний механізм відключення верифікації цифрового підпису (наприклад, спеціальний інженерний режим розблокування завантажувача).

Якщо компанія відмовляється надати закриті ключі, мотивуючи це вимогами корпоративної кібербезпеки або захистом від несанкціонованого модифікування параметрів приладу, вона здійснює пряме порушення статті 4 LGPLv3. Пристрій втрачає ліцензійну чистоту, а продаж такої продукції на ринках США та Європейського Союзу стає об'єктом блокування через судові приписи (*preliminary injunctions*).

### 4. Руйнівний вплив міжпроцедурної оптимізації (LTO)

Сучасні вбудовані компілятори активно використовують технологію оптимізації на етапі лінкування (Link-Time Optimization, прапорець `-flto`).

Під час збирання з `-flto`:
1. Компілятор не генерує фінальний машинний код на етапі компіляції окремих файлів `.c`, а записує в об'єктні файли `.o` внутрішнє проміжне представлення компілятора (GIMPLE у GCC або LLVM Bitcode у Clang).
2. На етапі лінкування оптимізатор аналізує всю програму цілком, агресивно вбудовуючи тіла функцій бібліотеки LGPL прямо всередину пропрієтарних функцій додатку (англ. *function inlining*) та навпаки.

У результаті застосування LTO межа між пропрієтарним кодом і кодом під LGPL повністю стирається на фізичному рівні: байтові послідовності відкритої бібліотеки виявляються розсіяними всередині пропрієтарних функцій. Якщо вендор спробує згенерувати об'єктні файли для релінк-пакета з LTO, він буде змушений передати клієнту GIMPLE-байткод, який містить повні дерева абстрактного синтаксису (AST) всієї закритої програми, що робить декомпіляцію абсолютно тривіальною. Якщо ж відключити LTO лише для релінк-пакета, розмір коду та споживання пам'яті можуть різко зрости, що призведе до неможливості помістити прошивку у флеш-пам'ять мікроконтролера.

### 5. Довічні зобов'язання підтримки інструментарію (Toolchain Drift)

Юридична вимога щодо можливості перелінкування повинна бути реально здійсненною на практиці. Це накладає на виробника зобов'язання довгострокової підтримки:
- Вендор зобов'язаний зафіксувати точну версію компілятора, компонувальника, прапорців збирання та скриптів лінкера (наприклад, `arm-none-eabi-gcc 10.3-2021.10`).
- Якщо через 3–5 років після випуску пристрою клієнт звернеться з вимогою надати релінк-пакет, вендор зобов'язаний надати працездатний комплект, який успішно скомпілює та збере фінальний образ без помилок несумісності ABI.

Особливо гостро ця проблема постає у проєктах на мові C++. Якщо LGPL-бібліотека містить шаблонні класи (наприклад, лінійну алгебру чи математичні контейнери), інстанціювання шаблонів відбувається безпосередньо у пропрієтарних одиницях трансляції. При зміні версії стандартної бібліотеки або опцій оптимізації компілятора структура згенерованих vtable та символів розгортання стека змінюється, що робить перелінкування старого об'єктного файлу з новою бібліотекою неможливим без вихідних текстів додатку.

Історія того, як ідеологічні суперечки щодо статусу системних бібліотек у проєкті GNU сформували ці жорсткі правила, детально описана у нарисі [Від «Library» до «Lesser»: компроміс Столлмана та ідеологічна пастка LGPL](root:sys-notary/pastka-lgpl/hist-library-gpl-split.md).

## Архітектурні моделі уникнення пастки

Якщо у процесі аудиту виявлено, що у монолітну вбудовану прошивку інтегровано компонент під ліцензією LGPL, інженерна команда має застосувати одну з чотирьох перевірених архітектурних стратегій нейтралізації ризиків.

![Архітектурні патерни безпечного використання або заміни LGPL-компонентів](/root/sys/sys-notary/pastka-lgpl/img/isolation-architectures.svg)
*Три інженерні підходи до нейтралізації ризиків LGPL: ізоляція компонента через процеси та стандартизований IPC, використання модульного динамічного завантажувача у флеш-пам'яті або заміна на дозвільні аналоги.*

### Стратегія 1: Процесна та апаратна ізоляція (IPC Boundary)

Найбільш бездоганним з юридичної точки зору методом використання LGPL-коду є повне винесення його за межі монолітного адресного простору пропрієтарної програми.

З точки зору авторського права два програмні модулі не вважаються єдиним похідним або комбінованим твором, якщо вони:
1. Виконуються як повністю незалежні системні процеси з власними адресними просторами (наприклад, під керуванням Embedded Linux, QNX Neutrino, PikeOS, seL4 або VxWorks у режимі RTP).
2. Взаємодіють виключно через стандартизовані системні інтерфейси IPC: локальні сокети домену Unix (`AF_UNIX`), канали іменованих пайпів (`FIFO`), механізм спільної пам'яті (`POSIX shared memory`) або мережеві протоколи передачі повідомлень (gRPC, MQTT, CBOR поверх TCP/UDP).
3. Протокол обміну повідомленнями є відкритим, публічно задокументованим і не містить специфічних внутрішніх структур компілятора.

На мікроконтролерних системах без повноцінної операційної системи той самий принцип надійно реалізується за допомогою **двочіпової апаратної архітектури**:

```
┌──────────────────────────────┐              ┌──────────────────────────────┐
│  Головний MCU (STM32 / NXP)   │     UART     │ Допоміжний MCU (ESP32 / RP)  │
│  [Пропрієтарна прошивка]     │ ──────────── │ [LGPL-стек: WiFi / Кодеки]   │
│                              │   (Протокол  │                              │
│ • Закритий монолітний образ  │     COBS/    │ • Повний вихідний код        │
│ • Алгоритми керування        │   Protobuf)  │   відкрито та доступно       │
│ • Без надання .o файлів      │              │ • Прошивається через UART    │
└──────────────────────────────┘              └──────────────────────────────┘
```

У цій схемі допоміжний комунікаційний мікроконтролер (наприклад, дешевий ESP32), на якому крутиться відкритий LGPL-стек, є повністю відкритим. Користувач має змогу модифікувати його код і перепрошивати через сервісний порт UART. Основний же мікроконтролер керування залишається на 100% закритим, захищеним криптографічним завантажувачем Secure Boot, і не підпадає під дію копілефту, оскільки розглядає другий чип як звичайний зовнішній периферійний пристрій.

### Стратегія 2: Модульний динамічний завантажувач на мікроконтролері

Якщо розробка ведеться на одному мікроконтролері без зовнішніх чипів, але компанія категорично не бажає розкривати об'єктні файли `.o`, у флеш-пам'яті контролера реалізують внутрішню архітектуру модульного зв'язування.

Флеш-пам'ять контролера розбивається на два повністю незалежні сектори з урахуванням меж фізичного стирання флеш-сторінок (наприклад, сектори по 128 КБ у STM32F4/F7):
1. **Сектор пропрієтарного ядра (Application Flash Region):** містить скомпільовану закриту прошивку. Вона не містить коду LGPL-бібліотеки, а звертається до неї через непрямі виклики покажчиків на функції (таблицю переходів, *Jump Table* або *Dispatch Vector*).
2. **Сектор LGPL-модуля (Library Flash Region):** містить скомпільовану LGPL-бібліотеку, розміщену за фіксованою базовою адресою (наприклад, `0x08080000`). Бібліотека розміщує на самому початку свого сектора таблицю адрес своїх відкритих функцій.

:::tabs
```c
/* jump_table_interface.h — Інтерфейс виклику LGPL-модуля у Flash */
#pragma once
#include <stdint.h>
#include <stddef.h>

/* Фіксована адреса таблиці функцій у секторі LGPL */
#define LGPL_MODULE_BASE_ADDR 0x08080000

typedef struct {
    uint32_t magic_header;
    uint32_t api_version;
    int (*init)(void);
    int (*compress)(const uint8_t *in, size_t in_len, uint8_t *out, size_t *out_len);
    int (*decompress)(const uint8_t *in, size_t in_len, uint8_t *out, size_t *out_len);
} lgpl_driver_api_t;

/* Отримання покажчика на інтерфейс модуля */
static inline const lgpl_driver_api_t* get_lgpl_driver(void) {
    const lgpl_driver_api_t *driver = (const lgpl_driver_api_t *)LGPL_MODULE_BASE_ADDR;
    if (driver->magic_header != 0x4C47504C) { /* "LGPL" marker */
        return NULL;
    }
    return driver;
}
```

```cpp
// jump_table_interface.hpp — Інтерфейс виклику LGPL-модуля у Flash
#pragma once
#include <cstdint>
#include <cstddef>
#include <span>
#include <expected>

namespace embedded_modular {

inline constexpr uintptr_t LGPL_MODULE_BASE_ADDR = 0x08080000;
inline constexpr uint32_t LGPL_MAGIC = 0x4C47504C;

struct DriverVTable {
    uint32_t magic_header;
    uint32_t api_version;
    int (*init)() noexcept;
    int (*compress)(const uint8_t *in, size_t in_len, uint8_t *out, size_t *out_len) noexcept;
    int (*decompress)(const uint8_t *in, size_t in_len, uint8_t *out, size_t *out_len) noexcept;
};

enum class DriverError {
    ModuleNotFound,
    VersionMismatch,
    ExecutionFailed
};

class LgplModuleBridge {
public:
    static std::expected<LgplModuleBridge, DriverError> bind() noexcept {
        auto *vtable = reinterpret_cast<const DriverVTable*>(LGPL_MODULE_BASE_ADDR);
        if (!vtable || vtable->magic_header != LGPL_MAGIC) {
            return std::unexpected(DriverError::ModuleNotFound);
        }
        if (vtable->api_version != 1) {
            return std::unexpected(DriverError::VersionMismatch);
        }
        return LgplModuleBridge(vtable);
    }

    std::expected<size_t, DriverError> compress(std::span<const uint8_t> in, 
                                               std::span<uint8_t> out) const noexcept {
        size_t written = out.size();
        int rc = vtable_->compress(in.data(), in.size(), out.data(), &written);
        if (rc != 0) {
            return std::unexpected(DriverError::ExecutionFailed);
        }
        return written;
    }

private:
    explicit LgplModuleBridge(const DriverVTable *vtable) noexcept : vtable_(vtable) {}
    const DriverVTable *vtable_;
};

} // namespace embedded_modular
```
:::

У такій модульній системі вимоги статті 6 LGPLv2.1 виконуються без передачі пропрієтарного коду:
- Користувачеві надається повний вихідний код сектора `lgpl_module`, його персональний скрипт лінкера для прив'язки до адреси `0x08080000` та проста інструкція з прошивання цього конкретного сектора через SWD/JTAG або сервісний бутлоадер.
- Користувач може змінити внутрішню логіку модуля, скомпілювати новий файл `lgpl_module.bin` і прошити його у вказаний сектор пам'яті. Основне закрите ядро пристрою залишиться недоторканим і продовжить коректно функціонувати через таблицю адрес.

### Стратегія 3: Чиста заміна на дозвільні аналоги (Clean Replacement)

Найбільш надійним, інженерно зрілим та економічно доцільним рішенням для комерційного пристрою залишається повна відмова від використання бібліотек під LGPL на користь дозвільного програмного забезпечення (ліцензії Apache 2.0, MIT, BSD, ISC, zlib).

Сучасна екосистема відкритого коду для вбудованих систем пропонує високоякісні дозвільні альтернативи практично для кожної популярної LGPL-бібліотеки:

```
┌──────────────────────────────┬──────────────────────────────┬──────────────────────────┐
│ Функціональна підсистема     │ Бібліотека LGPL (Ризик)      │ Дозвільний аналог        │
│                              │                              │ (MIT / BSD / Apache 2.0) │
├──────────────────────────────┼──────────────────────────────┼──────────────────────────┤
│ Криптографія та TLS          │ GnuTLS, libgcrypt (LGPL)     │ mbedTLS (Apache 2.0),    │
│                              │                              │ BearSSL (MIT)            │
├──────────────────────────────┼──────────────────────────────┼──────────────────────────┤
│ Компресія даних (Deflate/LZ) │ liblzma, lzo (LGPL/GPL)      │ miniz (MIT),             │
```

### Стратегія 4: Комерційне ліцензування (Dual-Licensing)

Комерційні розробники багатьох популярних бібліотек (наприклад, фреймворку Qt від The Qt Company або криптографічного стека wolfSSL) свідомо використовують ліцензію LGPLv3 як інструмент конверсії бізнес-клієнтів.

Модель подвійного ліцензування працює за чіткими правилами:
1. Якщо ви створюєте некомерційний або повністю відкритий проєкт — ви використовуєте бібліотеку безкоштовно на умовах суворої LGPLv3 (із зобов'язанням передачі об'єктного коду та ключів підпису).
2. Якщо ви випускаєте закритий комерційний монолітний пристрій із заблокованим завантажувачем і не бажаєте передавати клієнтам жодного об'єктного файлу — ви купуєте **комерційну пропрієтарну ліцензію**.

Комерційна угода з правовласником юридично скасовує всі вимоги статті 6 LGPLv2.1 та статті 4 LGPLv3, надаючи компанії право монолітного статичного лінкування без жодних зустрічних зобов'язань перед користувачем.

### Стратегія 5: Інженерно коректний конвеєр перелінкування

Якщо заміна бібліотеки технічно неможлива, а бюджет не дозволяє придбати комерційну ліцензію, компанія змушена підготувати офіційний комплект перелінкування.

Щоб мінімізувати витік внутрішньої інформації під час формування такого комплекту:
- Застосовують прапорці приховування глобальних символів `-fvisibility=hidden`.
- Використовують утиліту `objcopy --localize-hidden` для видалення локальних імен функцій з таблиці символів.
- Очищають об'єктний файл від налагоджувальних секцій DWARF за допомогою `strip --strip-debug`.
- Створюють прості, зрозумілі клієнтські файли `Makefile` та скрипти лінкера.
- Ретельно документують залежності стандартного C-рантайму (`newlib` або `glibc`), щоб лінкування з модифікованою бібліотекою не ламалося через системні вбудовані функції (`__aeabi_memcpy`, `__aeabi_ldivmod` чи математичні емулятори софт-флоату).

Покрокову інженерну реалізацію конвеєра підготовки об'єктного комплекту та автоматизований тест верифікації наведено в практикумі [Практикум перелінкування: ізоляція об'єктних файлів та скрипт перезбирання прошивки](root:sys-notary/pastka-lgpl/proj-relink-pipeline.md).

## Інженерний протокол: аудит ліцензійної чистоти прошивки

Перед передачею будь-якої мікроконтролерної прошивки у виробництво інженерна команда зобов'язана провести перевірку за наступним алгоритмом:

```
┌────────────────────────────────────────────────────────────────────────┐
│             ЧЕКЛІСТ ЛІЦЕНЗІЙНОГО АУДИТУ МОНОЛІТНОЇ ПРОШИВКИ            │
├────────────────────────────────────────────────────────────────────────┤
│ [ ] 1. Генерація повного маніфесту залежностей (SBOM).                 │
│        Чи містить прошивка бодай один статичний архів під LGPLv2/v3?   │
│                                                                        │
│ [ ] 2. Перевірка архітектури виконання:                                │
│        • Є динамічний завантажувач (.so)? → Ризик відсутній.           │
│        • Монолітний образ (Flash)? → ПЕРЕХІД ДО ПУНКТУ 3.              │
│                                                                        │
│ [ ] 3. Оцінка допустимості передачі об'єктних файлів (.o):             │
│        • Чи містять .o файли критичну інтелектуальну власність?        │
│        • Чи захищений пристрій Secure Boot (криптопідписом)?           │
│        • Якщо так → LGPL ЗАБОРОНЕНА для статичного лінкування.         │
│                                                                        │
│ [ ] 4. Вибір інженерного рішення:                                      │
│        • Заміна на MIT/BSD аналог (mbedTLS, miniz, lwIP).              │
│        • Апаратна/процесна ізоляція через IPC / окремий чіп.           │
│        • Придбання комерційної ліцензії у правовласника.               │
└────────────────────────────────────────────────────────────────────────┘
```

У сучасних виробничих конвеєрах цей процес автоматизується за стандартами OpenChain (ISO/IEC 5230). Спеціалізовані сканери вихідних текстів та скомпільованих бінарних файлів (інструменти `fossology`, `ort` або `syft`) генерують машиночитні специфікації програмних компонентів (SPDX або CycloneDX). Якщо у статичному ланцюгу зв'язування виявляється бібліотека з тегом `LGPL-2.1-only` або `LGPL-3.0-or-later`, система збирання негайно блокує випуск релізного образу до ухвалення одного з описаних архітектурних рішень.

Глибоке розуміння зв'язку між юридичними вимогами копілефту та фізикою компіляції монолітних виконуваних файлів дозволяє закладати безпечну архітектуру вбудованого виробу на ранніх стадіях проєктування, усуваючи загрози для бізнесу ще до написання першого рядка коду.
