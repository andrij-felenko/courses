# 📜 Від «Library» до «Lesser»: компроміс Столлмана та ідеологічна пастка LGPL

Коли Річард Столлман (англ. *Richard Stallman*) у 1989–1991 роках формулював правові засади руху за вільне програмне забезпечення (англ. *Free Software Movement*), його головною зброєю була ліцензія GNU General Public License (GPL). Механізм копілефту (англ. *copyleft*) у GPL мав безкомпромісний характер: якщо розробник використовує бодай один рядок коду під GPL у своїй програмі, увесь результуючий твір зобов'язаний поширюватися на умовах GPL. Для компіляторів, текстових редакторів та утиліт командного рядка ця стратегія працювала бездоганно. Проте коли проєкт GNU підійшов до створення системних бібліотек — насамперед бібліотеки стандартних функцій мови C (GNU C Library, `glibc`) — ідеологія зіткнулася з жорсткою ринковою реальністю.

## Стратегічний глухий кут: проблема стандартної бібліотеки C

На початку 1990-х років панівне становище у світі Unix займали пропрієтарні системи: SunOS/Solaris від Sun Microsystems, AIX від IBM, HP-UX від Hewlett-Packard та Ultrix від DEC. Кожна з цих операційних систем постачалася з власною закритою стандартною бібліотекою `libc`.

Програмісти комерційних компаній писали прикладне програмне забезпечення для комерційних Unix-систем. Якби проєкт GNU випустив бібліотеку `glibc` під стандартною ліцензією GPL, жоден комерційний розробник не зміг би скомпілювати свою закриту програму на системі GNU. Лінкування з GPL-бібліотекою автоматично перетворювало б комерційну програму на похідний твір (англ. *derivative work*), змушуючи бізнес відкривати весь пропрієтарний код або відмовлятися від платформи GNU.

Результат був очевидним: розробники не переходили б на вільну систему GNU/Linux, а продовжували б купувати пропрієтарні робочі станції Unix. Вільна системна бібліотека, замість поширення свободи, перетворилася б на ізолятор, що відрізав би операційну систему GNU від ринку прикладного софту.

## Компроміс 1991 року: поява GNU Library General Public License

Щоб вирішити цю дилему, у червні 1991 року Фонд вільного програмного забезпечення (Free Software Foundation, FSF) опублікував GNU Library General Public License версії 2.0 (LGPLv2.0) паралельно з релізом класичної GPLv2.

Головним нововведенням ліцензії стало розмежування понять:
1. «Твір, що містить бібліотеку» (англ. *work based on the Library*) — модифікації самого коду бібліотеки, які залишаються під суворим копілефтом.
2. «Твір, що використовує бібліотеку» (англ. *work that uses the Library*) — прикладні програми, які лише викликають функції з інтерфейсу бібліотеки.

LGPLv2 дозволила розробникам комерційного та пропрієтарного ПЗ лінкувати свої програми з вільною бібліотекою без обов'язку відкривати вихідний код власної програми. Проте Столлман не хотів віддавати код задарма: натомість він заклав у статтю 6 ліцензії жорстку інженерну вимогу — користувач комерційної програми повинен мати реальну практичну можливість модифікувати відкриту бібліотеку та перелінковувати або запускати додаток із модифікованою версією цієї бібліотеки.

На рівні настільних робочих станцій під керуванням Unix та Linux, де стрімко розвивався механізм динамічного завантаження спільних бібліотек (англ. *shared libraries*, файли `.so`), це компромісне рішення стало тріумфом: бібліотека `glibc` постачалася як динамічний об'єкт, а комерційні програми зв'язувалися з нею під час запуску в пам'яті.

## 1999 рік: чому «Library» перейменували на «Lesser»

Початкова назва ліцензії — *Library GPL* — викликала серйозну плутанину в інженерній спільноті. Розробники відкритого коду масово вирішили, що якщо вони пишуть бібліотеку, то за правилами FSF її *слід* випускати під ліцензією LGPL, а якщо пишуть виконуваний файл — під GPL.

Річард Столлман побачив у цьому фатальну загрозу для стратегії копілефту. У лютому 1999 року FSF випустив версію ліцензії 2.1, офіційно змінивши назву на **GNU Lesser General Public License** (англ. *lesser* — менша, слабша, другорядна). Цією зміною Столлман хотів підкреслити: LGPL надає користувачам *менше свободи*, ніж повноцінна GPL, і є вимушеним компромісом, а не бажаним стандартом.

Одночасно з виходом LGPLv2.1 Столлман опублікував програмне есе «Чому ви не повинні використовувати Lesser GPL для вашої наступної бібліотеки» (*Why you shouldn't use the Lesser GPL for your next library*). У ньому він сформулював чітку стратегічну доктрину розділення бібліотек на дві категорії:

```
┌────────────────────────────────────────────────────────────────────────┐
│                   СТРАТЕГІЧНИЙ ВИБІР ЛІЦЕНЗІЇ ЗА FSF                   │
├───────────────────────────────────┬────────────────────────────────────┤
│ Коли обирати LGPL (Lesser GPL)    │ Коли обирати сувору GPL            │
├───────────────────────────────────┼────────────────────────────────────┤
│ • Існують якісні закриті аналоги  │ • Бібліотека реалізує унікальний   │
│   (наприклад, стандартна C libc). │   функціонал, якого немає в інших. │
│ • Відмова від LGPL лише виштовхне │ • Закритий софт не має альтернатив │
│   розробників до конкурентів.     │   і змушений відкривати свій код   │
│ • Мета: масове впровадження.      │   заради доступу до технології.    │
│   Приклад: GNU C Library (glibc). │   Приклад: GNU Readline.           │
└───────────────────────────────────┴────────────────────────────────────┘
```

Найвідомішим прикладом тріумфу суворої GPL для бібліотек стала бібліотека автодоповнення та редагування командного рядка `GNU Readline`. Коли компанії захотіли використати її зручний інтерфейс у своїх комерційних базах даних та інтерпретаторах, FSF навідріз відмовився ліцензувати її під LGPL. Як наслідок, багатьом проєктам довелося або відкривати вихідний код, або писати власні аналоги з нуля (як це зробив проєкт BSD, створивши `libedit`).

## Як настільний компроміс перетворився на вбудовану пастку

У 1991 та 1999 роках автори LGPL мислили категоріями комп'ютерів загального призначення: робочих станцій, серверів та персональних комп'ютерів із повноцінними операційними системами, віртуальною пам'яттю (MMU) та динамічними завантажувачами програм. У цьому середовищі механізм перелінкування або підміни спільних бібліотек (`.so` у Linux або `.dll` у Windows) працював непомітно і без додаткових інженерних витрат для виробника закритого коду.

Проте на початку 2000-х років розпочалася революція вбудованих систем (англ. *embedded systems*): мікроконтролери ARM Cortex-M, RISC-V, ESP32, автомобільні контролери (ECU) та промислові сенсори. У цих системах немає операційної системи з динамічним завантажувачем: вся прошивка компілюється в один монолітний бінарний образ (`firmware.bin`), що прошивається безпосередньо у флеш-пам'ять мікроконтролера.

Формулювання статті 6 LGPLv2.1, розраховані на роздільні файли в операційній системі, у світі статичного монолітного лінкування несподівано перетворилися на юридичну пастку:
1. За відсутності динамічного завантажувача єдиним способом виконати вимогу ліцензії про можливість «перелінкування» стало зобов'язання віддати замовнику всі пропрієтарні об'єктні файли (`.o`), скрипти лінкера та опис середовища компіляції.
2. Пропрієтарні компанії, які впевнено інтегрували LGPL-бібліотеки (кодеки звуку, криптографію, стеки протоколів), раптом опинилися перед вибором: або повністю розкривати архітектуру та структури даних закритих алгоритмів через надання об'єктних файлів, або ставати правопорушниками.

У 2007 році FSF випустив ліцензію LGPLv3.0. Замість окремого самостійного тексту LGPLv3 була оформлена як перелік додаткових дозволів (англ. *additional permissions*) над текстом суворої ліцензії GPLv3. Ця версія додала пряму заборону апаратного блокування модифікацій (антитайвоїзація, англ. *anti-tivoization*), остаточно закривши для виробників закритих вбудованих пристроїв можливість сховатися за криптографічним підписом завантажувача.
