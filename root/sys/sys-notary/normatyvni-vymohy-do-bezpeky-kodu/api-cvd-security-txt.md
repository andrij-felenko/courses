# 📋 Стандартизований інтерфейс розкриття вразливостей: security.txt (RFC 9116), CSAF та OpenVEX

Регламент Європейського Союзу про кіберстійкість (CRA, Додаток I, Частина II) та гармонізований стандарт ETSI EN 303 645 (Пункт 5.2) встановлюють категоричну вимогу: виробник зобов'язаний надати публічний, прозорий і машиночитний інтерфейс для отримання повідомлень про знайдені вразливості (*Coordinated Vulnerability Disclosure*, CVD). Дослідник з безпеки не повинен шукати особисті поштові скриньки інженерів у соціальних мережах або заповнювати форми загальної технічної підтримки; пристрій та сервісна інфраструктура виробника мусять надавати стандартизовані кінцеві точки (англ. *endpoints*).

Для цього в індустрії вбудованих систем і вебінтерфейсів застосовують три взаємодоповнюючі формати: текстовий маніфест `security.txt` (IETF RFC 9116) для первинного контакту людини, формат бюлетенів безпеки CSAF 2.0 (OASIS) для автоматизованого обміну повідомленнями про загрози та маніфест експлуатабельності OpenVEX.

## 1. Специфікація текстового контракту security.txt (RFC 9116)

Файл `security.txt` — це людино- та машиночитний текстовий документ у кодуванні UTF-8, що розміщується на вебсервері вбудованого пристрою або на офіційному порталі підтримки виробника за фіксованими URI-шляхами.

### Стандартні шляхи розміщення (URI Paths) та мережеві вимоги

За стандартом RFC 9116 клієнт або автоматизований сканер шукає файл у такому пріоритетному порядку:
1. `https://<host>/.well-known/security.txt` (основне канонічне розміщення згідно з реєстром IANA Well-Known URIs)
2. `https://<host>/security.txt` (сумісність із застарілими клієнтами та простими вбудованими вебсерверами)

Сервер зобов'язаний повертати цей файл із HTTP-заголовком `Content-Type: text/plain; charset=utf-8`. Будь-які відкриті запити за незахищеним протоколом HTTP (порт 80) повинні безумовно перенаправлятися статусами 301 (*Moved Permanently*) або 308 (*Permanent Redirect*) на захищений HTTPS-канал (порт 443) із чинним сертифікатом TLS. Застосування самопідписаних сертифікатів без попереднього встановлення кореневого сертифіката вважається порушенням вимоги безпечного зв'язку (EN 303 645 Cl. 5.5).

### Директиви та поля формату RFC 9116

Кожен непорожній рядок файлу містить назву директиви, двокрапку та значення. Регістр літер у назвах директив не має значення, але для сумісності застосовується стиль CamelCase. Рядки, що починаються з символу `#`, вважаються коментарями й ігноруються парсерами.

| Директива | Обов'язковість | Опис та семантика поля | Приклад синтаксису |
|---|---|---|---|
| `Contact` | **Обов'язкова** | URI для прямого зв'язку з командою безпеки (поштова скринька `mailto:`, захищена вебформа `https://` або міжнародний номер телефону `tel:`). Дозволяється кілька рядків | `Contact: mailto:psirt@example.com` |
| `Expires` | **Обов'язкова** | Дата й час завершення чинності маніфесту в форматі ISO 8601 (RFC 3339). Час не повинен перевищувати 1 рік від моменту публікації | `Expires: 2027-12-31T23:59:59.000Z` |
| `Encryption` | Рекомендована | Посилання на відкритий PGP-ключ команди безпеки для наскрізного шифрування звітів про 0-day вразливості | `Encryption: https://example.com/pgp-key.asc` |
| `Canonical` | Рекомендована | Канонічна схема та повна адреса розміщення файлу для захисту від атак через підроблені дзеркала та кеш | `Canonical: https://example.com/.well-known/security.txt` |
| `Policy` | Рекомендована | Посилання на опублікований регламент узгодженого розкриття вразливостей (SLA розгляду, захист дослідників Safe Harbor) | `Policy: https://example.com/security-policy` |
| `Acknowledgments`| Опціональна | Посилання на офіційну сторінку визнання заслуг дослідників («Зала слави» / Hall of Fame) | `Acknowledgments: https://example.com/hall-of-fame` |
| `Preferred-Languages`| Опціональна | Перелік підтримуваних мов спілкування згідно з кодами ISO 639-1, розділених комами | `Preferred-Languages: uk, en, de` |
| `CSAF` | Рекомендована | Посилання на каталог або метадані машиночитних бюлетенів безпеки CSAF провайдера | `CSAF: https://example.com/.well-known/csaf/provider-metadata.json` |

### Цифровий підпис маніфесту OpenPGP

Для запобігання підміні контактних даних зловмисниками (наприклад, під час компрометації DNS або кешуючих проксі-серверів) стандарт RFC 9116 рекомендує підписувати вміст файлу за допомогою цифрового підпису OpenPGP (RFC 4880 Clearsigned Message Framework). Автоматизовані валідатори регуляторів перевіряють цей підпис перед внесенням виробника до реєстру довірених каналів зв'язку.

```text
-----BEGIN PGP SIGNED MESSAGE-----
Hash: SHA256

# Офіційний маніфест розкриття вразливостей згідно з CRA та ETSI EN 303 645
Contact: mailto:psirt@iot-device.eu
Contact: https://iot-device.eu/security/report
Expires: 2027-08-31T00:00:00.000Z
Encryption: https://iot-device.eu/.well-known/pgp-key.asc
Canonical: https://iot-device.eu/.well-known/security.txt
Policy: https://iot-device.eu/security/coordinated-vulnerability-disclosure
Acknowledgments: https://iot-device.eu/security/hall-of-fame
Preferred-Languages: uk, en
CSAF: https://iot-device.eu/.well-known/csaf/provider-metadata.json
-----BEGIN PGP SIGNATURE-----

iQEzBAEBCAAdFiEE6W7... (криптографічний підпис відкритого ключа команди) ...
-----END PGP SIGNATURE-----
```

## 2. Машиночитний бюлетень безпеки CSAF 2.0 (OASIS Standard)

Стандарт **CSAF 2.0** (*Common Security Advisory Framework*, розроблений консорціумом OASIS) — це відкрита специфікація на основі формату JSON, призначена для публікації та автоматизованого оброблення сповіщень про вразливості, виправлення та оновлення мікропрограмного забезпечення.

За регламентом CRA європейське агентство з кібербезпеки ENISA та національні координаційні центри CSIRT агрегують бюлетені виробників у режимі реального часу. Ручне заповнення PDF-документів або публікація текстових блогів більше не відповідає вимогам законодавства: системи моніторингу вимагають суворо валідованої JSON-схеми.

### Структурні вузли документа CSAF JSON

Кожен документ CSAF містить чітку ієрархію об'єктів:
1. **`document` (Метадані повідомлення):**
   - `category`: тип документа (наприклад, `csaf_security_advisory` або `csaf_vex`).
   - `tracking`: унікальний ідентифікатор бюлетеня, історія ревізій, поточний статус (`draft`, `interim`, `final`) та дата першої публікації.
   - `publisher`: юридичні реквізити команди реагування на інциденти продуктової безпеки (*Product Security Incident Response Team*, PSIRT).
2. **`product_tree` (Ієрархія апаратних і програмних продуктів):**
   - Деревоподібний перелік ідентифікаторів `product_id`, що пов'язують ревізії апаратних плат і версії двійкових прошивок із уніфікованими ідентифікаторами пакетів Package URL (PURL, наприклад `pkg:generic/iot-gw4-firmware@2.1.0`) або Common Platform Enumeration (CPE 2.3).
3. **`vulnerabilities` (Масив зафіксованих вразливостей):**
   - Ідентифікатор CVE (*Common Vulnerabilities and Exposures*).
   - Вектор і бали оцінки небезпеки за шкалою CVSS v3.1 або CVSS v4.0.
   - Матриця стану продуктів `product_status` (`known_affected`, `fixed`, `known_not_affected`).
   - Рекомендації та посилання на завантаження оновлень у секції `remediations`.

```json
{
  "document": {
    "category": "csaf_security_advisory",
    "csaf_version": "2.0",
    "title": "Уразливість переповнення буфера в мережевому стеку роутера IoT-GW4",
    "tracking": {
      "id": "CVD-2026-0042",
      "current_release_date": "2026-08-15T10:00:00Z",
      "initial_release_date": "2026-08-15T10:00:00Z",
      "status": "final",
      "version": "1.0.0"
    },
    "publisher": {
      "category": "vendor",
      "name": "IoT Hardware Labs PSIRT",
      "namespace": "https://iot-device.eu"
    }
  },
  "product_tree": {
    "full_product_names": [
      {
        "product_id": "PROD-GW4-FW-2.1.0",
        "name": "Прошивка контролера IoT-GW4 версії 2.1.0"
      }
    ]
  },
  "vulnerabilities": [
    {
      "cve": "CVE-2026-38491",
      "title": "RCE через переповнення буфера парсера DHCP опції 119",
      "scores": [
        {
          "cvss_v3": {
            "version": "3.1",
            "vectorString": "CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H",
            "baseScore": 9.8,
            "baseSeverity": "CRITICAL"
          }
        }
      ],
      "product_status": {
        "known_affected": [
          "PROD-GW4-FW-2.1.0"
        ]
      },
      "remediations": [
        {
          "category": "vendor_fix",
          "details": "Оновіть прошивку до версії 2.2.0 або новішої через захищений канал OTA.",

            "PROD-GW4-FW-2.1.0"
          ],
          "url": "https://iot-device.eu/downloads/firmware/v2.2.0.bin"

      ]
    }
  ]
}
```

## 3. Маніфест експлуатабельності OpenVEX

Коли під час аудиту програмного ланцюга постачання інструменти сканування SBOM виявляють відкриті бібліотеки (наприклад, `libcurl`, `mbedtls` або `busybox`), автоматизовані системи безпеки сигналізують про наявність десятків вразливостей CVE. Проте у реальній прошивці вразливий код може бути фізично вирізаний оптимізатором компілятора під час лінкування (*dead code elimination*) або відповідна вразлива опція конфігурації може бути вимкнена макросом препроцесора (`#undef`).

Якщо виробник не надасть машиночитне пояснення, замовники та регулятори вважатимуть продукт небезпечним. Для розв'язання цієї проблеми в межах CRA застосовується формат **OpenVEX** (*Vulnerability Exploitability eXchange*), що є компактним відкритим стандартом на базі JSON-LD.

### Статуси та нормативні обґрунтування OpenVEX

Стандарт OpenVEX визначає чотири базові статуси впливу вразливості на конкретний бінарний артефакт:

| Статус (`status`) | Значення статусу | Допустимі нормативні обґрунтування (`justification`) |
|---|---|---|
| `not_affected` | Продукт не зазнає впливу CVE | `component_not_present` — вразливий модуль взагалі не включено в збірку.<br>`vulnerable_code_not_present` — код видалено лінкувальником під час збирання.<br>`vulnerable_code_cannot_be_controlled_by_adversary` — вхідні дані надходять лише з ізольованого джерела.<br>`vulnerable_code_not_in_execute_path` — функція ніколи не викликається в рантаймі.<br>`inline_mitigations_already_exist` — апаратний блок MPU або TrustZone блокує експлуатацію. |
| `affected` | Продукт дійсно вразливий | Обов'язкове поле `action_statement` з детальним описом заходів захисту та термінів випуску патчу. |
| `fixed` | Уразливість виправлено | Поле `impact_statement` із зазначенням версії прошивки, у якій застосовано виправлення. |
| `under_investigation` | Триває інженерний аналіз | Тимчасовий статус на період дослідження коду командою розробників. |

### Зразок документа OpenVEX JSON

```json
{
  "@context": "https://openvex.dev/ns/v0.2.0",
  "@id": "https://iot-device.eu/vex/2026/vex-gw4-001.json",
  "author": "IoT Hardware Labs Security Team",
  "timestamp": "2026-08-20T14:30:00Z",
  "version": 1,
  "statements": [
    {
      "vulnerability": {
        "name": "CVE-2023-38545"
      },
      "products": [
        "pkg:generic/iot-gw4-firmware@2.2.0"
      ],
      "status": "not_affected",
      "justification": "vulnerable_code_cannot_be_controlled_by_adversary",
      "impact_statement": "Функція SOCKS5-проксі вбудованої бібліотеки curl вимкнена макросом CURL_DISABLE_PROXY під час компіляції образу прошивки."
    }
  ]
}
```

## 4. Пастки реалізації та крайові випадки

Під час розгортання інтерфейсів узгодженого розкриття вразливостей інженери найчастіше припускаються чотирьох типових помилок, що призводять до штрафів під час аудиту:
1. **Прострочений термін дії (`Expires` у минулому):** Автоматизовані сканери європейських регуляторів перевіряють значення поля `Expires`. Якщо дата минула, файл юридично втрачає чинність, що фіксується як відсутність обов'язкового каналу зв'язку за стандартом EN 303 645. Виробник зобов'язаний автоматизувати щорічне оновлення дати в пайплайні CI/CD.
2. **Невідповідність канонічної адреси (`Canonical` mismatch):** Якщо файл завантажено з дзеркала `cdn.device.com`, а директива `Canonical` вказує на `primary.device.com`, клієнтський сканер зобов'язаний виконати повторний запит до первинного домену для верифікації автентичності.
3. **Відсутність PGP-ключа для конфіденційних звітів:** Якщо рядок `Encryption` відсутній або веде на бите посилання, дослідник змушений надсилати інформацію про невиправлену критичну вразливість відкритим текстом електронною поштою, що грубо порушує вимоги конфіденційності передачі даних.
4. **Блокування автоматичних сканерів через CAPTCHA або Cloudflare:** Розміщення файлу `security.txt` за інтерактивними формами перевірки браузера або антибот-системами унеможливлює автоматичну індексацію європейськими центрами безпеки та порушує вимоги стандарту RFC 9116.
