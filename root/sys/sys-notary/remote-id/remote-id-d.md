# Remote ID: апарат, що називає себе

<preknowlist>
- [Радіосертифікація: FCC, CE, SRRC](root:sys-notary/regulatory-radio-certification) — процедури сертифікації радіообладнання, обмеження потужності EIRP та правила неліцензованого випромінювання.
- [ISM-діапазони](root:sys-notary/ism-bands) — правила розподілу неліцензованих смуг 2.4 ГГц та 5.8 ГГц для цивільних радіосистем.
- [Час у ефірі (time on air)](root:sys-notary/time-on-air) — тривалість передачі радіопакетів та обмеження робочого циклу передавача.
- [Декларація відповідності й технічний файл](root:sys-notary/deklaratsiia-vidpovidnosti-i-tekhnichnyi-fail) — структура технічної документації та оцінка відповідності вимогам директив ЄС.
</preknowlist>

Патрульний екіпаж поблизу глісади міжнародного аеропорту фіксує квадрокоптер масою близько двох кілограмів, що завис на висоті 120 метрів безпосередньо в зоні заходу на посадку пасажирських літаків. Оптичні реєстраційні номери на фюзеляжі з землі неможливо розгледіти навіть у бінокль, а бортовий авіаційний радар не бачить пластиковий апарат із мізерною ефективною площею розсіювання. Проте портативний радіосканер на планшеті інспектора за 800 мілісекунд перехоплює безперервні пакети радіомовлення на частоті 2.4 ГГц. На екрані миттєво з'являються точні координати дрона, його висота за еліпсоїдом WGS84, вектор швидкості 14 м/с, серійний номер виробника за стандартом ANSI/CTA-2063-A та географічна точка розташування оператора з пультом на даху сусідньої будівлі.

Цей сценарій описує роботу прямої цифрової ідентифікації — **Remote ID** (англ. *Remote Identification*, дистанційна ідентифікація, від лат. *identitas* — тотожність). Це технологічний і нормативний механізм, який зобов'язує безпілотне повітряне судно (БПС) безперервно транслювати у відкритий радіоефір власні телеметричні та реєстраційні дані без встановлення двостороннього з'єднання з приймачем.

Історію формування міжнародних мандатів Remote ID — від транспортного колапсу в аеропорту Гатвік у 2018 році та суперечок між мережевою і прямою моделями до судового прецеденту *RaceDayQuads v. FAA* — викладено в [історичному нарисі появи мандатів Remote ID](root:sys-notary/remote-id/hist-remote-id-mandates.md).

### Регуляторний фундамент: FAA Part 89 та EASA 2019/945 / 2019/947

Правова вимога обов'язкової наявності цифрового «номерного знака» закріплена двома провідними авіаційними регуляторами світу: Федеральним управлінням цивільної авіації США (FAA) та Європейським агентством з авіаційної безпеки (EASA).

```
Регуляторні парадигми Remote ID:
+-------------------------------+-----------------------------------+-----------------------------------+
| Параметр                      | FAA Part 89 (США)                 | EASA 2019/945 / 2019/947 (ЄС)     |
+-------------------------------+-----------------------------------+-----------------------------------+
| Назва технології              | Broadcast Remote ID               | Direct Remote ID (DRI)            |
| Обов'язкові класи / категорії | Усі дрони > 250 г та комерційні   | Класи C1, C2, C3 (Open A1/A2/A3)  |
| Ідентифікатор борту           | Серійний номер ANSI/CTA-2063-A    | Серійний номер ANSI/CTA-2063-A    |
| Ідентифікатор пілота          | Не транслюється (лише координати) | Номер реєстрації оператора EASA   |
| Частота оновлення             | 1.0 Гц (1 пакет на секунду)       | 1.0 Гц (1 пакет на секунду)       |
| Фізичні носії                 | Bluetooth 4/5, Wi-Fi Beacon/NAN   | Bluetooth 4/5, Wi-Fi Beacon/NAN   |
| Механізм автономного модуля   | Remote ID Broadcast Module        | Direct Remote ID Add-on Module    |
| Процедура сертифікації        | Declaration of Compliance (DoC)   | Декларація CE (Module A)          |
+-------------------------------+-----------------------------------+-----------------------------------+
```

#### 1. Сполучені Штати Америки: 14 CFR Part 89
Норматив FAA Title 14 розділу 89 Зводу федеральних нормативних актів США розділяє експлуатацію цивільних безпілотників на три взаємовиключні категорії:
- **Standard Remote ID Drone:** Безпілотник із заводською інтеграцією системи ідентифікації. Контролер апарата апаратно блокує запуск двигунів (англ. *takeoff interlock*), якщо модуль Remote ID не пройшов самодіагностику або GNSS-приймач не отримав валідної навігаційної прив'язки. Система зобов'язана транслювати координати БПЛА, його висоту, швидкість, серійний номер, часову мітку та динамічні координати пульта керування або наземної станції (GCS). Якщо оператор переміщується (наприклад, керує дроном із рухомого автомобіля чи катера), передавач оновлює точку пульта в реальному часі.
- **Remote ID Broadcast Module:** Автономний зовнішній радіомаяк із власним супутниковим приймачем, живленням та антеною, який закріплюється на саморобних, аматорських або застарілих заводських дронах. Транслює координати апарата та фіксовану точку зльоту (англ. *Takeoff Location*), оскільки зв'язок із пультом оператора відсутній. Політ такого дрона обмежується межами прямої видимості (Visual Line of Sight, VLOS).
- **FAA-Recognized Identification Area (FRIA):** Спеціально сертифіковані географічні зони (зазвичай аеродроми авіамодельних клубів та навчальних закладів), у межах яких дозволено виконувати польоти без передавача Remote ID за умови збереження постійного візуального контакту (VLOS).

Для виходу на ринок США виробник зобов'язаний розробити засіб відповідності (Means of Compliance, MOC), верифікований за стандартом ASTM F3586, та зареєструвати офіційну Декларацію відповідності (Declaration of Compliance, DoC) у реєстрі FAA.

#### 2. Європейський Союз: Регламенти 2019/945 та 2019/947
Європейська модель базується на класному маркуванні апаратів відкритої категорії (Open Category):
- БПЛА класів **C1** (маса < 900 г або кінетична енергія при зіткненні < 80 Дж), **C2** (< 4 кг) та **C3** (< 25 кг) зобов'язані мати вбудовану систему Direct Remote ID (DRI);
- Для старих апаратів без класного маркування, що експлуатуються у відкритій або специфічній категорії (Specific Category), передбачено використання автономних модулів *Direct Remote ID Add-on Module*;
- Окрім навігаційних параметрів, європейський регламент вимагає обов'язкової трансляції унікального **номера реєстрації оператора (Operator Registration Number)** у системі EASA. Цей номер складається з 16 символів відкритої частини та 3 символів секретного перевірочного коду (PIN), який зберігається в закритій базі національної авіаційної влади і ніколи не передається у відкритий радіоефір.

#### 3. Стандарт серійних номерів ANSI/CTA-2063-A
Для унеможливлення дублювання ідентифікаторів міжнародний стандарт ANSI/CTA-2063-A визначає сувору 20-символьну структуру рядка серійного номера:
```
[ MFR (4 символи) ] [ Length Code (1 символ) ] [ Sequence Number (до 15 символів) ]
```
- **MFR (Manufacturer Code):** 4-значний шістнадцятковий код виробника, офіційно зареєстрований асоціацією Consumer Technology Association (CTA) або ICAO (наприклад, коди для провідних виробників електроніки);
- **Length Code:** 1 символ (від `1` до `F`), що визначає точну довжину серійної частини виробника (від 1 до 15 знаків);
- **Sequence Number:** Унікальний літерно-цифровий номер конкретного примірника плати або літального апарата.

### Архітектура двійкових кадрів ASTM F3411 та ASD-STAN prEN 4709-002

Фізичні носії неліцензованого радіомовлення (зокрема Bluetooth 4.2 Legacy) накладають жорсткі обмеження на розмір одного кадру. Комітет ASTM International спільно з європейським інститутом ASD-STAN розробив компактний бінарний формат **ASTM F3411**, у якому всі повідомлення квантовані до фіксованого розміру **25 байтів**.

![Структура двійкових повідомлень ASTM F3411 / Open Drone ID](/root/sys/sys-notary/remote-id/img/astm-f3411-frame-structure.svg)
*Структура двійкових повідомлень ASTM F3411 / Open Drone ID: бітові поля та формати базових повідомлень*

Кожен 25-байтний двійковий блок починається з однобайтового заголовка (байт 0):
- **Старші 4 біти (7..4):** Тип повідомлення (Message Type);
- **Молодші 4 біти (3..0):** Версія протоколу (`0x1` для стандарту F3411-22a).

Повний перелік бітових полів, структур даних та числових констант наведено в [довіднику специфікації ASTM F3411](root:sys-notary/remote-id/api-astm-f3411.md).

#### 1. Повідомлення 0x0: Basic ID (Ідентифікатор апарата)
Передає тип та унікальний номер борту:
- **Байт 1:** Старші 4 біти — тип ідентифікатора (`1` = ANSI/CTA-2063-A, `2` = CAA ID, `4` = Session ID); молодші 4 біти — тип повітряного судна (`1` = Літак, `2` = Гелікоптер, `15` = Мультиротор);
- **Байти 2..21:** 20 байтів рядка UAS ID;
- **Байти 22..24:** Зарезервовано (`0x00`).

Якщо повітряне судно має одночасно фізичний серійний номер виробника та офіційний реєстраційний номер цивільної авіації, передавач транслює два окремих повідомлення Basic ID з індексами `ID Type = 1` та `ID Type = 2`.

#### 2. Повідомлення 0x1: Location / Vector (Місцезнаходження та вектор руху)
Передає миттєвий навігаційний стан із кроком не рідше одного разу на секунду:
- **Статус польоту (Байт 1, біти 7..4):** `0` = Undeclared, `1` = Ground, `2` = Airborne, `3` = Emergency;
- **Курс руху (Байт 2):** Значення від `0` до `359` градусів відносно географічного півночі;
- **Горизонтальна швидкість (Байт 3):** Крок дискретизації `0.25 м/с` (діапазон 0–62.5 м/с) або `0.75 м/с` для швидкісних БПЛА;
- **Вертикальна швидкість (Байт 4):** Знаковий байт `int8_t` із кроком `0.5 м/с` (`+` підйом, `-` спуск);
- **Широта та довгота (Байти 5..12):** Два 32-бітних знакових цілих числа (`int32_t`), отриманих множенням кутових градусів на `10 000 000` (роздільна здатність ~1.1 см на екваторі);
- **Геодезична висота WGS84 (Байти 13..14):** 16-бітне ціле число з нульовою точкою зміщення -1000 метрів та кроком дискретизації `0.5 метра`:
```
Alt_encoded = round((Altitude_WGS84_m + 1000.0) / 0.5)
```
- **Барометрична висота (Байти 15..16):** Висота відносно стандартної ізобари 1013.25 гПа з аналогічним числовим кодуванням;
- **Точність GNSS (Байт 19):** Старший нібл — горизонтальна точність (NACp від `0` до `13`, де `11` відповідає похибці < 3 м); молодший нібл — вертикальна точність (GVA);
- **Часова мітка (Байти 21..22):** Десяті частки секунди в межах поточної години (діапазон від `0` до `35999`, що забезпечує дискретність 100 мс).

#### 3. Повідомлення 0x3: Self-ID (Текстовий опис місії)
Передає вільний текстовий коментар пілота довжиною до 23 символів ASCII (наприклад, `SURVEY-GRID-04`, `SEARCH-RESCUE` або контактний телефон екстреного зв'язку). Застосовується службами повітряного простору для швидкого з'ясування мети польоту без звернення до хмарного реєстру.

#### 4. Повідомлення 0x4: System Data (Дані оператора та зони польоту)
Передає контекст місії:
- **Тип локації оператора (Байт 1):** `0` = Точка зльоту (Takeoff Location), `1` = Динамічні координати пульта (Live GNSS GCS), `2` = Фіксована точка;
- **Широта й довгота оператора (Байти 2..9):** Формат `int32_t` (масштаб 1e-7 градуса);
- **Геодезична висота оператора WGS84 (Байти 18..19):** Формат `uint16_t` зі зміщенням -1000 м;
- **Параметри зони операції (Байти 10..16):** Кількість апаратів у рою (`Area Count`), радіус дозволеного циліндра польоту (`Area Radius` із кроком 10 м), верхня стеля (`Area Ceiling`) та нижня межа (`Area Floor`);
- **Категорія ризику (Байт 17):** Бітові прапорці класифікації EASA (Open Class C0..C6, Specific Category).

#### 5. Повідомлення 0xF: Message Pack (Агрегатор повідомлень)
Оскільки сучасні радіомодулі Bluetooth 5 та Wi-Fi здатні передавати сотні байтів корисного навантаження в одному кадрі, протокол передбачає контейнер `Message Pack`. Контейнер містить заголовок `0xF1`, фіксований розмір одного елемента `0x19` (25 байтів), кількість упакованих повідомлень `N` та послідовний масив із `N` окремих 25-байтних повідомлень (наприклад, Basic ID + Location + System Data = 78 байтів). Це гарантує атомарне приймання навігаційних даних дрона та оператора без часового розриву.

### Фізичні носії радіомовлення: Bluetooth та Wi-Fi

Стандарт ASTM F3411 специфікує чотири взаємодоповнюючі радіофізичні канали передачі даних у відкритих ISM-діапазонах 2.4 ГГц та 5.8 ГГц.

![Інкапсуляція Open Drone ID у кадри Bluetooth та Wi-Fi](/root/sys/sys-notary/remote-id/img/rf-transport-encapsulation.svg)
*Інкапсуляція Open Drone ID у кадри Bluetooth та Wi-Fi: формати PDU для Bluetooth Legacy, Long Range та Wi-Fi Beacon*

```
Порівняння фізичних радіоносіїв Remote ID:
+-----------------------+-----------------------+-----------------------+-----------------------+
| Фізичний носій        | Розмір корисного PDU  | Дальність зв'язку     | Сумісність зі смарт-  |
|                       |                       |                       | фонами                |
+-----------------------+-----------------------+-----------------------+-----------------------+
| Bluetooth 4.2 Legacy  | 25 байтів (1 повідом) | 100 .. 300 метрів     | 100% усіх пристроїв   |
| Bluetooth 5 Long Range| 254 байти (Msg Pack)  | 1000 .. 3000 метрів   | Нові моделі (BT5 Coded)|
| Wi-Fi Beacon (2.4 ГГц)| 254 байти (Msg Pack)  | 300 .. 800 метрів     | Повна (Promiscuous/P2P)|
| Wi-Fi NAN / Aware     | 254 байти (Msg Pack)  | 200 .. 500 метрів     | Часткова (Android 9+) |
```

#### 1. Bluetooth 4.2 Legacy Advertising (Повідомлення за замовчуванням)
Найпростіший і найбільш сумісний канал. Передавач використовує стандартні рекламні непід'єднувані канали 37, 38 та 39 (частоти 2402, 2426, 2480 МГц) з модуляцією 1M PHY:
- **Структура PDU:** Загальний ліміт PDU становить 37 байтів (6 байтів MAC-адреси + 31 байт корисних даних AD Structure);
- **Структура AD Data:**
  - 3 байти: Flags (`0x02, 0x01, 0x06`);
  - 28 байтів: Service Data 16-bit UUID (`Length = 0x1B`, `AD Type = 0x16`, `UUID = 0xFFFA` у форматі little-endian `0xFA, 0xFF`);
  - 25 байтів: Одне повідомлення Open Drone ID.
- **Циклічна ротація (Round-Robin):** Оскільки 31-байтний пакет вміщує рівно одне 25-байтне повідомлення, передавач зобов'язаний випромінювати повідомлення по черзі з інтервалом 200–250 мс: наприклад, `0.0 с: Basic ID`, `0.25 с: Location`, `0.5 с: System Data`, `0.75 с: Location`.

#### 2. Bluetooth 5 Extended Advertising (Coded PHY S=8)
Використовує розширені можливості специфікації Bluetooth 5.0 для забезпечення наддалекого зв'язку:
- **Механізм первинних і вторинних каналів:** На первинних каналах (37–39) передається лише короткий вказівник `ADV_EXT_IND`, який вказує на точний час і номер вторинного каналу даних (0–36);
- **Модуляція Coded PHY (S=8):** Кожен інформаційний біт кодується 8 канальними символами з прямою корекцією помилок (FEC). Це забезпечує виграш у чутливості приймача на рівні 8–10 дБ і збільшує дальність виявлення БПЛА до 2–3 кілометрів;
- **Передача Message Pack:** Великий розмір PDU (до 254 байтів) дозволяє передавати всі типи повідомлень (Basic ID, Location, System Data, Self-ID) одночасно в єдиному пакеті `0xF` щосекунди.

#### 3. Wi-Fi Beacon (IEEE 802.11 Vendor Specific IE)
Модуль транслює стандартні кадри управління точкою доступу (Beacon Frames) на фіксованому каналі 6 (2437 МГц) без створення відкритої мережі:
- **Ідентифікація через Information Element (IE):** У тіло маяка вбудовується інформаційний елемент постачальника (Element ID `221` / `0xDD`);
- **OUI Wi-Fi Alliance:** Поле OUI містить значення `0xFA-0B-BC`, а поле OUI Type — `0x0D` (Open Drone ID);
- **Корисне навантаження:** Всередині елемента розміщується блок `Message Pack` (78–103 байти). Смартфон у режимі пасивного сканування Wi-Fi перехоплює маяки без потреби автентифікації чи підключення до мережі.

#### 4. Wi-Fi NAN (Neighbor Awareness Networking / Wi-Fi Aware)
Високоефективний протокол прямої взаємодії пристроїв без використання точок доступу. Дрон випромінює сервісні кадри відкриття (Service Discovery Frames, SDF) на соціальних каналах 6 (2.4 ГГц) або 44/149 (5 ГГц) синхронно під час спеціальних 512-мікросекундних вікон Discovery Windows (DW). Сервіс публікується з хешем імені `org.wi-fi.wifiaware.opendroneid`.

### Криптографічна автентифікація та захист від підробки (Anti-Spoofing)

Фундаментальна особливість Remote ID полягає в тому, що **радіомовлення є повністю незашифрованим**. Будь-який громадянин або співробітник поліції має право вільно прочитати координати дрона за допомогою смартфона без отримання паролів чи авторизації на серверах.

Проте відкритість створює вразливість до атак активного радіоперешкоджання та підробки:
- **Атака фантомного рою (Ghost Drone Spoofing):** Зловмисник із портативним програмно-визначеним радіопередавачем (SDR, наприклад HackRF) може згенерувати тисячі фальшивих кадрів Open Drone ID, імітуючи атаку неіснуючих БПЛА на диспетчерські системи аеропорту;
- **Атака повторення (Replay Attack):** Запис легітимного ефіру з подальшим повторним випромінюванням для створення хибного алібі;
- **Підміна координат оператора:** Передавач транслює справжні координати дрона, але вказує фальшиву точку розташування пілота для уникнення затримання.

```
Ланцюг криптографічного захисту:
[ Координати + Час + Серійний № ] 
               |
               v
     [ Хеш SHA-256 (32 байти) ]
               |
               v
   [ Secure Element / HSM ] ---> [ Приватний ключ ECDSA P-256 (eFuse) ]
               |
               v
[ Електронний цифровий підпис R (32B) + S (32B) = 64 байти ]
               |
               v
[ Фрагментація на 4 сторінки Auth Message 0x2 (по 17-23 байти) ]
               |
               v
[ Радіоефір BLE / Wi-Fi ] ---> [ Перевірка публічним ключем регулятора ]
```

![Фрагментація та верифікація повідомлень автентифікації (Authentication Paging)](/root/sys/sys-notary/remote-id/img/auth-signature-paging.svg)
*Фрагментація та верифікація повідомлень автентифікації: розбиття цифрового підпису ECDSA на сторінки та конвеєр валідації*

#### 1. Механізм сторінкової автентифікації (Authentication Message Paging)
Для захисту цілісності стандарт ASTM F3411 передбачає повідомлення типу `0x2 (Authentication)`. Повний криптографічний підпис алгоритму **ECDSA NIST P-256** (або Ed25519) має розмір 64 байти (дві 32-байтні координати точки еліптичної кривої `r` та `s`), а разом із часовою міткою та ідентифікатором сертифіката сягає 72–80 байтів.

Оскільки одне повідомлення вміщує лише 25 байтів, цифровий підпис розбивається на сторінки (англ. *paging*):
- **Сторінка 0 (Page 0):** Містить заголовок `0x21`, тип підпису `Auth Type = 1 (ECDSA)`, індекс останньої сторінки `Last Page Index = 3`, 4-байтну часову мітку створення підпису та перші 17 байтів даних підпису;
- **Сторінки 1, 2, 3 (Pages 1..3):** Містять по 23 байти наступних фрагментів цифрового підпису.

Приймач накопичує всі 4 сторінки протягом 1–2 секунд, збирає єдиний криптографічний блок і здійснює верифікацію.

#### 2. Запобігання атакам повторення (Replay Protection)
Підпис накладається на об'єднаний хеш SHA-256 від поточних координат дрона (Location), серійного номера (Basic ID) та поточної мітки часу UTC. Наземний приймач відхиляє пакет, якщо часова мітка підпису відрізняється від поточного системного часу GNSS більш ніж на `±1.0 секунду`. Це унеможливлює повторне відтворення попередньо записаних радіосигналів.

#### 3. Апаратний корінь довіри (Hardware Root of Trust)
Вимоги FAA та EASA до захисту від несанкціонованого втручання (англ. *Tamper Resistance*) вимагають, щоб приватний криптографічний ключ підпису генерувався всередині апаратного криптографічного співпроцесора (Secure Element, наприклад ATECC608A або захищені eFuse-регістри SoC) під час заводського калібрування. Прошивка польотного контролера не має прямого доступу до приватного ключа і звертається до криптомодуля виключно через апаратну команду запиту підпису навігаційного блоку.

### Програмна архітектура та реалізація на мікроконтролері

Практична інтеграція генератора Open Drone ID у бортовий комп'ютер або автономний радіомаяк вимагає циклічного опитування супутникового модуля, масштабування координат та формування бінарних структур.

Нижче наведено базовий модуль пакування навігаційних даних на мовах C та C++:

:::tabs
```c
#include <stdint.h>
#include <string.h>
#include <math.h>

#pragma pack(push, 1)

typedef struct {
    uint8_t  header;             /* 0x11: Msg Type 0x1, Version 0x1 */
    uint8_t  status_flags;       /* Біти 7..4: статус польоту (2 = Airborne) */
    uint8_t  direction;          /* 0..359 град */
    uint8_t  speed_h;            /* крок 0.25 м/с */
    int8_t   speed_v;            /* крок 0.5 м/с зі знаком */
    int32_t  lat;                /* grad * 1e7 */
    int32_t  lon;                /* grad * 1e7 */
    uint16_t alt_geodetic;       /* (alt_m + 1000) / 0.5 */
    uint16_t alt_pressure;       /* (alt_m + 1000) / 0.5 */
    uint16_t height_agl;         /* AGL / 0.5 */
    uint8_t  accuracy_horiz_vert;/* HAcc (4b) | VAcc (4b) */
    uint8_t  accuracy_baro_speed;/* BaroAcc (4b) | SpeedAcc (4b) */
    uint16_t timestamp_tenths;   /* 0.1 с поточної години */
    uint8_t  time_adv_acc;
    uint8_t  reserved;
} odid_location_msg_t;

#pragma pack(pop)

void encode_location_frame(odid_location_msg_t *msg, double lat, double lon, 
                           double alt_wgs84, double spd_h, double spd_v, 
                           double hdg, uint32_t sec_in_hour, uint32_t ms) {
    memset(msg, 0, sizeof(odid_location_msg_t));
    msg->header = (0x1 << 4) | 0x01;
    msg->status_flags = (2 << 4); /* Airborne */
    
    int deg = (int)round(hdg);
    msg->direction = (uint8_t)((deg >= 0 ? deg : deg + 360) % 360);
    
    msg->speed_h = (uint8_t)fmin(spd_h / 0.25, 254.0);
    msg->speed_v = (int8_t)fmax(-127.0, fmin(spd_v / 0.5, 127.0));
    
    msg->lat = (int32_t)round(lat * 10000000.0);
    msg->lon = (int32_t)round(lon * 10000000.0);
    
    double enc_alt = (alt_wgs84 + 1000.0) / 0.5;
    msg->alt_geodetic = (uint16_t)(enc_alt < 0 ? 0 : (enc_alt > 65535 ? 65535 : enc_alt));
    msg->alt_pressure = msg->alt_geodetic;
    
    msg->accuracy_horiz_vert = (11 << 4) | (10 & 0x0F); /* HAcc < 3m, VAcc < 10m */
    msg->accuracy_baro_speed = (10 << 4) | (10 & 0x0F);
    
    msg->timestamp_tenths = (uint16_t)(((sec_in_hour % 3600) * 10 + (ms / 100)) % 36000);
}
```
```cpp
#include <cstdint>
#include <cstring>
#include <cmath>
#include <algorithm>
#include <span>

namespace remote_id {

#pragma pack(push, 1)

struct alignas(1) LocationMessage {
    uint8_t  header{0x11};
    uint8_t  status_flags{0x20}; /* Airborne */
    uint8_t  direction{0};
    uint8_t  speed_h{0};
    int8_t   speed_v{0};
    int32_t  lat{0};
    int32_t  lon{0};
    uint16_t alt_geodetic{0};
    uint16_t alt_pressure{0};
    uint16_t height_agl{0};
    uint8_t  accuracy_horiz_vert{0xBA}; /* HAcc=11, VAcc=10 */
    uint8_t  accuracy_baro_speed{0xAA};
    uint16_t timestamp_tenths{0};
    uint8_t  time_adv_acc{0x10};
    uint8_t  reserved{0};

    LocationMessage(double latitude, double longitude, double alt_wgs84,
                    double speed_horiz, double speed_vert, double heading,
                    uint32_t sec_in_hour, uint32_t ms_part) noexcept {
        int deg = static_cast<int>(std::round(heading));
        direction = static_cast<uint8_t>((deg >= 0 ? deg : deg + 360) % 360);

        speed_h = static_cast<uint8_t>(std::clamp(speed_horiz / 0.25, 0.0, 254.0));
        speed_v = static_cast<int8_t>(std::clamp(speed_vert / 0.5, -127.0, 127.0));

        lat = static_cast<int32_t>(std::round(latitude * 1e7));
        lon = static_cast<int32_t>(std::round(longitude * 1e7));

        double enc_alt = std::clamp((alt_wgs84 + 1000.0) / 0.5, 0.0, 65535.0);
        alt_geodetic = static_cast<uint16_t>(std::round(enc_alt));
        alt_pressure = alt_geodetic;

        timestamp_tenths = static_cast<uint16_t>(((sec_in_hour % 3600) * 10 + (ms_part / 100)) % 36000);
    }

    [[nodiscard]] std::span<const uint8_t> bytes() const noexcept {
        return {reinterpret_cast<const uint8_t*>(this), sizeof(LocationMessage)};
    }
};

#pragma pack(pop)

} // namespace remote_id
```

### Апаратні та радіоелектронні виклики інтеграції

Інтеграція передавача Remote ID у конструкцію БПЛА пов'язана з низкою інженерних обмежень:

1. **Електромагнітна інтерференція з каналами радіокерування:** Передавач Remote ID випромінює на частоті 2.4 ГГц у безпосередній близькості від бортових приймачів керування (наприклад, ExpressLRS, TBS Tracer або цифрових відеосистем DJI O3 / Walksnail). Якщо антена Remote ID розташована ближче ніж на 10–15 см від антени приймача керування, потужні імпульси передавача (+20 дБм) викликають динамічне блокування вхідного малошумлячого підсилювача (LNA desensitization) та деградацію телеметрії. Вирішенням є просторове рознесення антен та використання вузькосмугових керамічних фільтрів.
2. **Вплив вуглецевого композиту фюзеляжу:** Карбонові пластини рами є електропровідними і практично повністю екранують радіовипромінювання на частотах 2.4 ГГц. Антена модуля Direct Remote ID повинна бути винесена за межі карбонового каркаса на діелектричному кронштейні з круговою діаграмою спрямованості у нижню півсферу.
3. **Температурний дрейф кварцового генератора (TCXO):** Під час зимової експлуатації або нагрівання від силових регуляторів швидкості (ESC) звичайний кварцовий резонатор зазнає частотного дрейфу. Відхилення опорної частоти понад ±20 ppm порушує декодування розширених рекламних пакетів Bluetooth 5 Coded PHY на наземних приймачах, тому в сертифікованих модулях застосовуються термокомпенсовані генератори (TCXO).

> 🔧 **Навіщо це.**
> Пряма дистанційна ідентифікація Remote ID перетворює анонімний радіокерований апарат на юридично підзвітного учасника повітряного простору. Розуміння двійкових структур ASTM F3411 та правил радіоінкапсуляції дозволяє розробникам авіоніки створювати сертифіковані за стандартами FAA Part 89 та EASA 2019/945 комерційні безпілотні системи, інтегрувати бортові передавачі з польотними контролерами на рівні протоколів MAVLink (повідомлення `OPEN_DRONE_ID_*`) та проектувати наземні комплекси моніторингу повітряного простору.
