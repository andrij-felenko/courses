Коли компілятор завершує збирання вбудованого дистрибутива чи контейнерного образу, результуючий двійковий файл об'єднує в собі сотні компонентів: системні виклики ядра Linux, функції бібліотеки C-рантайму (glibc або musl), криптографічні примітиви mbedTLS, рушій бази даних SQLite та прикладні алгоритми керування пристроєм. За замовчуванням право авторської власності (англ. *copyright*, від лат. *copia* — копія, достаток + *ius* — право) встановлює абсолютну монополію творця: будь-яке копіювання, модифікація, компонування чи поширення комп'ютерної програми без прямої згоди автора є правопорушенням.

Щоб програмний код міг вільно використовуватись іншими інженерами, правовласник видає односторонній дозвільний документ — **ліцензію** (лат. *licentia* — свобода дій, дозвіл, від дієслова *licere* — бути дозволеним). Ліцензія відкритого коду трансформує правову монополію автора з інструменту заборони в інструмент надання прав. Проте умови, за яких надаються ці права, принципово різняться: від повної свободи використання без жодних зустрічних вимог до зобов'язання оприлюднити повний вихідний код усього кінцевого продукту.

## Юридична природа ліцензії: односторонній дозвіл проти договору

У праві інтелектуальної власності важливо розрізняти двосторонній договір (угоду кінцевого користувача, EULA або договір купівлі-продажу) та **односторонню безоплатну ліцензію на авторське право** (англ. *bare copyright license*).

Двосторонній комерційний договір вимагає прямого акцепту (підписання або натискання кнопки «Згоден») та наявності зустрічного задоволення (англ. *consideration* у загальному праві) — наприклад, сплати грошей. Натомість публічна ліцензія відкритого коду діє як односторонній дозвіл правовласника. Автор не вимагає від вас укладання договору для того, щоб ви просто читали або запускали програму на власному комп'ютері.

Проте щойно інженер починає здійснювати дії, на які закон про авторське право надає монополію виключно автору — компілювати код у складі іншого продукту, модифікувати його, вшивати у флеш-пам'ять пристрою та продавати партію обладнання замовникам — ліцензія стає єдиним юридичним щитом, що захищає інженера від суду.

Якщо компанія порушує умови цього дозволу (наприклад, поширює скомпільовану під GPLv2 прошивку без вихідного коду), ліцензія автоматично анулюється. У цей момент компанія стає не просто порушником умов угоди (*breach of contract*), а прямим **порушником авторських прав** (*copyright infringement*). У судовому прецеденті *Jacobsen v. Katzer* (Федеральний окружний суд США, 2008 рік) було остаточно встановлено: умови відкритих ліцензій є обов'язковими юридичними обмеженнями на обсяг наданих прав, а їхнє порушення дозволяє авторам негайно вимагати повної судової заборони на продаж комерційних виробів (*preliminary injunction*) та стягнення статутних збитків.

## Правовий спектр: дозвільні ліцензії проти копілефту

Усі ліцензії відкритого коду, схвалені організацією Open Source Initiative (OSI) та Фондом вільного програмного забезпечення (Free Software Foundation, FSF), поділяються на дві фундаментальні філософські й юридичні категорії: **дозвільні** (*permissive*) та **копілефтні** (*copyleft*).

![Правовий спектр ліцензій відкритого коду від дозвільних до мережевого копілефту](/root/sys/sys-notary/open-source-licenses/img/license-spectrum.svg)
*Спектр юридичних зобов'язань: ліворуч розташовані дозвільні ліцензії, що надають право закривати похідний код; праворуч — копілефтні ліцензії різного рівня суворості, які вимагають збереження відкритості та взаємності (reciprocity).*

### Дозвільні ліцензії (Permissive Licenses)

Дозвільна ліцензія (англ. *permissive license*, від лат. *permissivus* — той, що дозволяє або прощає) надає користувачеві максимальний обсяг прав при мінімальних юридичних обмеженнях. Вона дозволяє:
- Безкоштовно використовувати, змінювати та поширювати код у будь-яких цілях (зокрема комерційних).
- Компонувати вихідний або скомпільований код із закритим пропрієтарним програмним забезпеченням.
- Змінювати ліцензію для похідних творів та не розкривати вихідний код модифікацій.

Головною та фактично єдиною умовою дозвільних ліцензій є **обов'язок збереження атрибуції**: у всіх копіях програми або істотних її частинах необхідно зберігати початкове повідомлення про авторські права (*copyright notice*) та відмову автора від будь-яких гарантійних зобов'язань (*disclaimer of warranty*).

До цієї родини належать такі класичні ліцензії:
1. **MIT (Massachusetts Institute of Technology):** найкоротший і найпопулярніший текст у сучасній індустрії. Надає повну свободу дій за умови збереження повідомлення про копірайт.
2. **BSD 2-Clause / BSD 3-Clause (Berkeley Software Distribution):** ліцензії, створені для операційної системи BSD UNIX. Історична ліцензія BSD 4-Clause містила так зване «рекламне застереження» (*advertising clause*), яке вимагало згадувати Каліфорнійський університет у Берклі в усіх рекламних матеріалах. Коли дистрибутиви почали об'єднувати сотні пакетів, це призвело до абсурдної ситуації, коли рекламні буклети повинні були містити десятки сторінок подяк. У 1999 році цей пункт скасували, створивши чисту ліцензію BSD 3-Clause (з забороною використання імен авторів для реклами) та BSD 2-Clause (повністю еквівалентну MIT).
3. **ISC (Internet Systems Consortium):** функціональний аналог MIT та BSD-2-Clause, текст якого очищено від архаїчних юридичних формулювань відповідно до Бернської конвенції.
4. **Apache 2.0 (Apache Software Foundation):** сучасна дозвільна ліцензія, яка, крім базових прав копіювання, містить детальний апарат передачі патентних прав, правила щодо торгових марок та вимогу зберігати історію змін файлів.

### Копілефт (Copyleft) та принцип взаємності

Копілефт (англ. *copyleft*, від англ. *left* — залишене, вільне, на противагу *right* — право, монополія) — це юридична конструкція, яка використовує копірайт для гарантування постійної відкритості програми. Якщо дозвільні ліцензії дозволяють «приватизувати» відкритий код (включити його у пропрієтарний закритий продукт), то копілефт накладає на дистриб'ютора вимогу **взаємності** (англ. *reciprocity*, від лат. *reciprocus* — зворотний, взаємний).

Суть принципу взаємності полягає в тому, що право на поширення бінарних файлів програми надається лише за умови, що одержувач бінарника отримує:
1. Повний відповідний вихідний код (*Complete Corresponding Source Code*).
2. Право модифікувати цей вихідний код і компілювати власні версії.
3. Ліцензію на поширення своїх модифікацій на тих самих умовах, без додавання нових обмежень.

Історичні передумови появи цієї концепції та конфлікти навколо закритого коду в лабораторії MIT детально описані в історичному нарисі [Народження копілефту: від принтера Xerox до розколу GPLv3](root:sys-notary/open-source-licenses/hist-copyleft-origins.md).

## Рівні копілефту: слабкий, сильний та мережевий

Юридична сила копілефту визначається тим, де саме проходить межа «похідного твору» (англ. *derivative work*, від лат. *derivare* — виводити одне з іншого, відводити русло), на який поширюється обов'язок розкриття вихідних текстів. За цією глибиною поширення ліцензії поділяються на три рівні.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        РІВНІ КОПІЛЕФТУ ТА МЕЖІ                         │
├───────────────────┬──────────────────────────┬─────────────────────────┤
│ Слабкий копілефт  │ Сильний копілефт         │ Мережевий копілефт      │
│ (Weak Copyleft)   │ (Strong Copyleft)        │ (Network Copyleft)      │
├───────────────────┼──────────────────────────┼─────────────────────────┤
│ • LGPL v2.1/v3.0  │ • GPL v2.0               │ • AGPL v3.0             │
│ • MPL 2.0         │ • GPL v3.0               │ • SSPL (non-OSI)        │
│ • EPL 2.0 / CDDL  │                          │                         │
│                   │                          │                         │
│ Межа зараження:   │ Межа зараження:          │ Межа зараження:         │
│ Окремий файл або  │ Весь комбінований        │ Весь серверний бекенд   │
│ скомпільована     │ двійковий процес         │ при мережевому доступі  │
│ бібліотека        │ (статичний/динамічний)   │ користувачів (SaaS)     │
└───────────────────┴──────────────────────────┴─────────────────────────┘
```

### 1. Слабкий копілефт (Weak Copyleft)

Слабкий копілефт встановлює межу відкритості на рівні окремого файлу або окремої бібліотеки.

- **MPL 2.0 (Mozilla Public License):** файловий копілефт. Якщо інженер змінює код у файлі під ліцензією MPL, цей файл зобов'язаний залишитися відкритим. Проте нові файли у тому ж проєкті, які лише викликають функції з MPL-файлу, можуть залишатися повністю закритими і поширюватися під комерційною ліцензією.
- **LGPL v2.1 / LGPL v3.0 (GNU Lesser General Public License):** бібліотечний копілефт. Ліцензія розроблена спеціально для системних бібліотек. Вона дозволяє розробникам пропрієтарного ПЗ компонувати свої закриті програми з бібліотекою LGPL за умови дотримання суворих інженерних правил лінкування.

### 2. Сильний копілефт (Strong Copyleft)

Сильний копілефт встановлює межу відкритості на рівні **всього комбінованого твору** (бінарного файлу або взаємопов'язаного монолітного адресного простору).

- **GPL v2.0 (GNU General Public License версії 2, 1991):** якщо будь-яка частина програми містить або походить від коду під GPLv2, вся програма в цілому повинна поширюватися під GPLv2 при її публічній дистрибуції. Ця ліцензія використовується в ядрі Linux.
- **GPL v3.0 (2007):** оновлена версія ліцензії, яка зберігає вимоги сильного копілефту, але додає механізми захисту від апаратного блокування модифікованих прошивок (антитайвоізація) та взаємний обмін патентними правами (див. [GPLv3 проти підписаного завантажувача](root:sys-notary/gplv3-proty-pidpysanoho-zavantazhuvacha)).

### 3. Мережевий копілефт (Network / Service Copyleft)

Класичні ліцензії GPLv2 та GPLv3 активують вимогу розкриття коду лише в момент **дистрибуції** (англ. *distribution* або *conveying*) — тобто передачі фізичного носія або завантаження скомпільованого бінарного файлу кінцевому користувачеві. Якщо компанія запускає модифіковану версію програми на власному сервері й надає користувачам доступ до її функціоналу через інтернет (модель Software-as-a-Service, SaaS), факту передачі бінарного образу не відбувається. Цю юридичну лазівку називають «ASP-лазівкою» (*Application Service Provider loophole*).

- **AGPL v3.0 (GNU Affero General Public License):** стаття 13 цієї ліцензії встановлює, що надання доступу до програми через комп'ютерну мережу юридично прирівнюється до її фізичного поширення. Сервер зобов'язаний надати всім мережевим клієнтам можливість безперешкодно завантажити повний вихідний код модифікованої серверної програми через мережевий протокол (наприклад, через пряме посилання в інтерфейсі).

## Межі похідного твору: статичне, динамічне лінкування та IPC

Головне інженерне питання ліцензійної відповідності формулюється просто: в який саме момент підключення стороннього модуля робить ваш власний код «похідним твором» і змушує розкрити комерційну таємницю?

Юридичний статус залежить від архітектурного способу взаємодії компонентів у системі.

![Архітектурні межі програми та глибина поширення копілефту](/root/sys/sys-notary/open-source-licenses/img/linking-and-derivative-work.svg)
*Анатомія ізоляції: ліворуч показано тісні механізми компонування в єдиному адресному просторі, що створюють єдиний твір; праворуч — інтерфейси міжпроцесної ізоляції, які зберігають незалежність творів.*

### Статичне компонування (.a / .o)

Під час статичного лінкування [компонувальник](root:sys-unix/static-and-dynamic-linking) бере об'єктні файли вашої програми та бібліотеки й зшиває їх в один суцільний виконуваний образ ELF. Машинні інструкції обох частин переплітаються, таблиці адрес модифікуються, а символи остаточно зв'язуються.

З погляду права такий бінарний файл є нерозривним єдиним твором. Якщо до його складу увійшов хоча б один статичний модуль під ліцензією `GPL-2.0` або `GPL-3.0`, **весь виконуваний файл повинен бути ліцензований під GPL**. Закрити свій код у такій конфігурації юридично неможливо.

### Динамічне завантаження (.so / .dll) та пастка LGPL

Під час динамічного лінкування виконуваний файл містить лише запис `DT_NEEDED` у заголовках ELF, а фактичне завантаження бібліотеки в адресний простір і розв'язання символів виконує динамічний компонувальник операційної системи (`ld-linux.so`) під час старту процесу.

Юридичні наслідки динамічного зв'язування залежать від типу ліцензії:

1. **Динамічний лінк із GPL:** позиція Фонду вільного програмного забезпечення (FSF) є однозначною: якщо програма та бібліотека виконуються в єдиному адресному просторі, обмінюються складними внутрішніми структурами даних C/C++ та мають тісний зв'язок викликів, вони утворюють комбінований твір. Отже, динамічний лінк із GPL-бібліотекою інфікує основну програму.
2. **Динамічний лінк із LGPL:** стаття 4 LGPLv2.1 та стаття 4 LGPLv3 явно дозволяють підключати LGPL-бібліотеку до комерційного коду, якщо використовується **механізм спільного об'єкта** (*shared library mechanism*).
3. **Статичний лінк із LGPL:** якщо інженер змушений скомпонувати LGPL-бібліотеку статично (наприклад, у замкненій системі без підтримки динамічного завантаження), ліцензія вимагає передати кінцевому користувачеві не лише прошивку, а й **комплект нескомпонованих об'єктних файлів (`.o`) власної програми**. Це необхідно для того, щоб користувач міг модифікувати код LGPL-бібліотеки та власноруч перелінковати бінарник. Докладно про цей інженерний капкан читайте у статті [Пастка LGPL: статичне лінкування й вимога дати переліновку](root:sys-notary/pastka-lgpl).

### Чисті межі: міжпроцесна взаємодія (IPC)

Якщо два модулі виконуються в окремих адресних просторах як незалежні процеси операційної системи (мають різні ідентифікатори PID у ядрі) і взаємодіють через стандартні системні механізми:
- Текстові або бінарні канали зв'язку (UNIX Domain Sockets, Pipes, FIFOs).
- Мережеві протоколи (HTTP REST, gRPC, WebSocket).
- Виклик окремої бінарної утиліти через системні виклики `fork()` та `execve()` з передачею параметрів через `argv[]`.

У цьому разі програми визнаються **юридично незалежними творами** (*separate works*), які взаємодіють на відстані витягнутої руки (*arms-length relationship*). Використання ліцензованої під GPL утиліти (наприклад, `ffmpeg` або `busybox`) через системний виклик `execve` не змушує відкривати вихідний код керуючого бекенд-сервісу.

> 🔧 **Навіщо це в реальній розробці:**
> Якщо вашому комерційному рішенню конче потрібна функціональність важкої GPL-бібліотеки, винесіть роботу з нею в окремий мікросервіс-демон. Спілкування з основним процесом через локальний UNIX-сокет за допомогою серіалізованих JSON-повідомлень захищає вашу інтелектуальну власність від копілефтного зараження.

## Моделі подвійного ліцензування (Dual Licensing)

Оскільки автор початкового коду володіє повним обсягом авторських прав, він не обмежений власною ліцензією і може поширювати ту саму кодову базу одночасно під кількома взаємовиключними правовими режимами. Ця стратегія називається **подвійним або комерційним ліцензуванням** (*Dual / Multi-Licensing*).

Класичні бізнес-моделі подвійного ліцензування будуються за двома схемами:

1. **Модель «GPL + Commercial OEM» (на прикладі Qt, MySQL, Berkeley DB):**
   Базова версія продукту публікується під сильною ліцензією GPL або AGPL. Компанії, що створюють повністю відкриті безкоштовні проєкти, використовують її вільно. Проте якщо комерційний замовник бажає створити закритий пропрієтарний продукт і не хоче публікувати свій вихідний код, він купує в правовласника спеціальну комерційну ліцензію (*Commercial License*), яка звільняє його від усіх зобов'язань копілефту.
2. **Модель «Permissive + Reciprocal» (на прикладі mbedTLS або cJSON):**
   Код пропонується користувачеві під вибором: `Apache-2.0 OR GPL-2.0-or-later`. Розробник, який будує систему на базі GPLv2 (наприклад, модулі ядра Linux), обирає гілку GPL, тоді як розробник пропрієтарного ПЗ обирає гілку Apache 2.0.

## Судова практика та забезпечення виконання ліцензій

Реальність ліцензійних зобов'язань підтверджується десятиліттями міжнародної судової практики:

- **Діяльність gpl-violations.org у Німеччині:** німецький інженер Гаральд Вельте (Harald Welte) виграв десятки судових процесів проти великих виробників мережевого обладнання (D-Link, Sitecom, Netgear). Компанії використовували ядро Linux та пакет BusyBox у прошивках роутерів, але відмовлялися надавати вихідний код і скрипти складання. Суди Франкфурта та Мюнхена визнали повну юридичну силу GPLv2, наклали судові заборони на продаж партій обладнання та змусили виробників компенсувати судові витрати й відкрити вихідні коди.
- **Позови Software Freedom Conservancy (SFC) проти Vizio:** у 2021 році організація SFC подала позов проти виробника телевізорів Vizio. Унікальність процесу полягала в тому, що позов було подано не від імені автора коду, а від імені кінцевого споживача як третьої сторони-бенефіціара (*third-party beneficiary*) за ліцензією GPL, вимагаючи надати доступ до вихідного коду SmartCast OS.
- **Судовий процес Artifex Software v. Hancom:** американський суд визнав, що корейська компанія Hancom, використавши PDF-інтерпретатор Ghostscript під ліцензією GPL без придбання комерційної ліцензії та без розкриття власного коду, вчинила пряме порушення копірайту, що завершилося великою фінансовою мировою угодою.

## Матриця сумісності ліцензій та асиметричні конфлікти

Дві ліцензії `L_A` та `L_B` називаються **сумісними** (англ. *license compatibility*, від лат. *compatibilitas* — здатність співіснувати, від *compati* — співчувати, терпіти разом), якщо код під цими ліцензіями можна скомпонувати в єдиний виконуваний артефакт `C`, умови поширення якого не порушують жодної з вимог `L_A` чи `L_B`.

Сумісність ліцензій відкритого коду є **спрямованою та несиметричною**: код під дозвільною ліцензією майже завжди можна включити у проєкт під сильною копілефтною ліцензією, але зворотна операція категорично заборонена.

![Спрямовані потоки та сумісність поєднання ліцензійних сімейств](/root/sys/sys-notary/open-source-licenses/img/license-compatibility-matrix.svg)
*Спрямований граф ліцензійної сумісності: дозволені переходи та критичний конфлікт між ліцензіями Apache 2.0 та GPLv2.*

### Конфлікт століття: чому Apache 2.0 несумісна з GPLv2

Найвідомішим і найгострішим конфліктом сумісності в індустрії є поєднання коду під ліцензіями `Apache-2.0` та `GPL-2.0-only`.

Механізм цього конфлікту криється в зіткненні двох конкретних юридичних статей:
1. **Стаття 3 ліцензії Apache 2.0 (Патентна відсіч):** ліцензія містить застереження: якщо одержувач коду ініціює патентний судовий позов проти авторів або контриб'юторів Apache-проєкту, стверджуючи, що їхнє програмне забезпечення порушує його патент, усі патентні права, надані цьому позивачеві ліцензією Apache 2.0, **автоматично анулюються**.
2. **Стаття 6 ліцензії GPLv2 (Заборона додаткових обмежень):** ліцензія GPLv2 містить категоричну норму: дистриб'ютор не має права накладати на одержувача програми жодних додаткових обмежень (англ. *no further restrictions*) щодо здійснення наданих прав.

Юристи FSF дійшли висновку: умова автоматичного скасування прав у разі патентного позову за статтею 3 Apache 2.0 є «додатковим обмеженням», якого початковий текст GPLv2 не передбачав. Оскільки стаття 6 GPLv2 забороняє будь-які нові обмеження, скомпонувати код `Apache-2.0` та `GPL-2.0-only` в один бінарник **юридично неможливо** — виникає нерозв'язна правова суперечність.

Конфлікт було усунуто лише у 2007 році у версії `GPL-3.0`: стаття 13 нової ліцензії була спеціально спроєктована для гармонізації з патентними умовами Apache 2.0. Тому комбінація `Apache-2.0 + GPL-3.0` є повністю сумісною і поширюється під загальною ліцензією GPLv3.

### Матриця поєднання базових ліцензійних родин

При поєднанні двох компонентів у межах одного двійкового образу кінцева ліцензія артефакту визначається такою матрицею:

| Ліцензія компонента A | Ліцензія компонента B | Результуюча ліцензія бінарника | Юридичний статус збірки |
|:---|:---|:---|:---|
| `MIT / BSD-2/3` | `MIT / BSD-2/3` | `MIT / BSD` | **Сумісно** (збереження всіх копірайтів) |
| `MIT / BSD` | `Apache-2.0` | `Apache-2.0` | **Сумісно** (поглинання більш суворою) |
| `MIT / BSD / Apache-2.0` | `LGPL-2.1-or-later` | `LGPL-2.1` | **Сумісно** (при дотриманні правил лінку) |
| `MIT / BSD` | `GPL-2.0-only` | `GPL-2.0-only` | **Сумісно** (поглинання сильним копілефтом) |
| `Apache-2.0` | `GPL-2.0-only` | **Неможливо** | **НЕСУМІСНО ✖** (патентний конфлікт §6 GPLv2) |
| `Apache-2.0` | `GPL-3.0-only` | `GPL-3.0-only` | **Сумісно** (пряма сумісність §13 GPLv3) |
| `GPL-2.0-only` | `GPL-3.0-only` | **Неможливо** | **НЕСУМІСНО ✖** (різні версії без 'or-later') |
| `GPL-2.0-or-later` | `GPL-3.0-only` | `GPL-3.0-only` | **Сумісно** (підвищення версії дозволено) |
| `GPL-3.0` | `AGPL-3.0` | `AGPL-3.0` | **Сумісно** (через статтю 13 AGPL) |
| `GPL-2.0 / GPL-3.0` | `Proprietary (Закритий)`| **Неможливо** | **НЕСУМІСНО ✖** (порушення умов ліцензії) |

## Патентні положення та захист торгових марок

Право інтелектуальної власності розділяє авторське право на текст коду та патентне право на ідею чи алгоритм.

**Копірайт** захищає конкретну форму вираження — послідовність символів у файлі вихідного коду (як літературний твір). Якщо інший розробник напише ту саму логіку з нуля іншими словами, авторське право не порушується.

**Патент** (від лат. *patere* — бути відкритим, доступним; *litterae patentes* — відкриті грамоти монарха) захищає сам винахід — функціональний алгоритм, метод обробки інформації або структуру апаратно-програмного комплексу. Якщо компанія запатентувала структуру даних або алгоритм стиснення, використання навіть повністю самостійно написаного відкритого коду є порушенням патенту.

### Неявний проти явного патентного дозволу

Ранні дозвільні ліцензії (MIT, BSD) створювалися до епохи масових патентних війн. Вони містять лише право на «використання та копіювання коду», не згадуючи слово «патент». У суді це створює концепцію **неявного патентного дозволу** (*implied patent license*): припускається, що автор, викладаючи код, дозволив його використання, але межі цього дозволу юридично не визначені.

Сучасні ліцензії (Apache 2.0, GPL v3, MPL 2.0) містять **прямий патентний грант** (*express patent grant*):
1. Кожен контриб'ютор, який передає свій код у проєкт, автоматично надає кожному користувачеві безвідкличну, безоплатну та безстрокову патентну ліцензію на всі свої патенти, які реалізовані у цьому коді.
2. **Застереження про патентну відсіч (Patent Retaliation Clause):** якщо компанія-користувач подає позов про порушення патентів проти будь-якого учасника проєкту щодо цього ПЗ, її власна ліцензія негайно припиняє дію.

Додатковим індустріальним механізмом захисту є мережа Open Invention Network (OIN) — патентний пул взаємного ненападу, учасники якого зобов'язуються не пред'являти патентні претензії щодо компонентів ядра Linux та ключових бібліотек відкритого коду (докладно див. [Патенти на ПЗ і патентні пули](root:sys-notary/software-patents-and-pools)).

### Захист торгових марок

Ліцензія на код ніколи не є ліцензією на комерційний бренд. Стаття 6 ліцензії Apache 2.0 та політики Linux Foundation прямо наголошують: право на модифікацію коду не дає права використовувати торгові марки (*trademarks*), офіційні логотипи чи назви первинного проєкту для маркування власних комерційних виробів.

## Стандарти інженерного аудиту в CI/CD: SPDX та SBOM

Ручна перевірка ліцензій у сучасних проєктах із тисячами залежностей неможлива. Для автоматизації юридичного аудиту розроблено міжнародний стандарт **SPDX** (англ. *Software Package Data Exchange*, ISO/IEC 5962:2021).

### Ідентифікатори у заголовках файлів

Замість копіювання багатосторінкових юридичних текстів у кожен вихідний файл стандарт SPDX вводить стандартизовані однорядкові машинозчитувані мітки у коментарях:

```spdx
SPDX-License-Identifier: MIT
SPDX-License-Identifier: Apache-2.0 WITH LLVM-exception
SPDX-License-Identifier: GPL-2.0-or-later OR Apache-2.0
```

Синтаксис та формальна граматика логічних виразів (`AND`, `OR`, `WITH`), правила розв'язання винятків та повний перелік канонічних позначень специфіковані у довіднику [Специфікація виразів SPDX 2.3/3.0 та нормалізовані ідентифікатори](root:sys-notary/open-source-licenses/api-spdx-expressions.md).

### Генерація SBOM (Software Bill of Materials)

**SBOM** (англ. *Software Bill of Materials* — програмна відомість матеріалів, від англ. *bill* — рахунок, список + *materials* — компоненти, складники) — це структурований машинозчитний паспорт програмного продукту, що містить повний перелік усіх його компонентів, їхніх версій, хешів цілісності та ліцензійних ідентифікаторів.

![Автоматизований конвеєр аудиту ліцензійної чистоти та SBOM у CI/CD](/root/sys/sys-notary/open-source-licenses/img/spdx-sbom-pipeline.svg)
*Конвеєр забезпечення відповідності: від статичного аналізу коду й парсингу ELF-заголовків до перевірки ліцензійної матриці та випуску підписаного SBOM-паспорта.*

У промислових конвеєрах CI/CD інструменти аналізу (ScanCode, Fossology, Syft, Trivy) генерують SBOM у форматі SPDX JSON або CycloneDX. Спеціальний шлюз контролю якості (*Compliance Quality Gate*) зіставляє виявлені ліцензії з політикою безпеки підприємства:
- Якщо виявлено `GPL-3.0` у закритому модулі — збірка автоматично переривається з кодом помилки.
- Якщо виявлено `LGPL-2.1` — перевіряється наявність динамічного лінкування через таблицю ELF `DT_NEEDED`.
- На фінальному етапі формується юридичний звіт для технічного файлу виробу (див. [SBOM: перелік складників образу](root:sys-notary/sbom-perelik-skladnykiv-obrazu-i-navishcho-ioho)).

## Практичний розбір: аналізатор бінарних залежностей та ліцензійної сумісності

Розглянемо практичний алгоритм інженерної перевірки, який аналізує граф зв'язування компонентів, зіставляє типи ліцензій та видає вердикт щодо безпеки релізу.

:::tabs
```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdbool.h>

/* Бітові класифікатори ліцензій */
typedef enum {
    LIC_PERMISSIVE = 1 << 0,  /* MIT, BSD, ISC */
    LIC_APACHE2    = 1 << 1,  /* Apache 2.0 */
    LIC_LGPL       = 1 << 2,  /* LGPL v2.1/v3.0 */
    LIC_GPL2       = 1 << 3,  /* GPL-2.0-only */
    LIC_GPL3       = 1 << 4,  /* GPL-3.0-or-later */
    LIC_PROPRIETARY= 1 << 5   /* Комерційний закритий код */
} LicenseClass;

typedef enum {
    LINK_STATIC,
    LINK_DYNAMIC,
    LINK_IPC
} LinkType;

typedef struct {
    const char *module_name;
    const char *spdx;
    LicenseClass lic;
    LinkType link;
} ModuleDep;

/* Перевірка сумісності за матрицею ліцензійних правил */
static bool check_compatibility(LicenseClass target, LicenseClass dep, LinkType link) {
    /* Міжпроцесний бар'єр (IPC) повністю знімає ліцензійні вимоги */
    if (link == LINK_IPC) return true;

    /* Правила для закритого пропрієтарного продукту */
    if (target == LIC_PROPRIETARY) {
        if (dep == LIC_PERMISSIVE || dep == LIC_APACHE2) return true;
        if (dep == LIC_LGPL) return (link == LINK_DYNAMIC);
        return false; /* GPL/AGPL блокують реліз */
    }

    /* Правила для продукту під GPL-2.0-only */
    if (target == LIC_GPL2) {
        if (dep == LIC_PERMISSIVE || dep == LIC_GPL2) return true;
        if (dep == LIC_APACHE2) return false; /* Патентний конфлікт */
        if (dep == LIC_GPL3) return false;    /* Конфлікт версій */
        return true;
    }

    /* Правила для продукту під GPL-3.0 */
    if (target == LIC_GPL3) {
        if (dep == LIC_GPL2) return false;   /* GPL-2.0-only несумісна з v3 */
        return true;                          /* MIT, Apache-2.0, LGPL сумісні */
    }

    return false;
}

int main(void) {
    ModuleDep deps[] = {
        {"libjson-c",    "MIT",        LIC_PERMISSIVE, LINK_STATIC},
        {"libcrypto",    "Apache-2.0", LIC_APACHE2,    LINK_STATIC},
        {"libprotocols", "LGPL-2.1",   LIC_LGPL,       LINK_DYNAMIC},
        {"system-core",  "GPL-2.0",    LIC_GPL2,       LINK_IPC},
        {"libdsp_filter","GPL-2.0",    LIC_GPL2,       LINK_STATIC} /* Порушення! */
    };
    size_t count = sizeof(deps) / sizeof(deps[0]);

    printf("=== АУДИТ ЛІЦЕНЗІЙНОЇ ВІДПОВІДНОСТІ (PROPRIETARY) ===\n");
    int failed = 0;
    for (size_t i = 0; i < count; ++i) {
        bool ok = check_compatibility(LIC_PROPRIETARY, deps[i].lic, deps[i].link);
        const char *link_name = (deps[i].link == LINK_STATIC) ? "STATIC" :
                                (deps[i].link == LINK_DYNAMIC) ? "DYNAMIC" : "IPC";

        if (ok) {
            printf("[OK]   %-15s (%-10s) Link: %-8s\n", deps[i].module_name, deps[i].spdx, link_name);
        } else {
            printf("[FAIL] %-15s (%-10s) Link: %-8s <-- БЛОКУВАННЯ ЗБІРКИ!\n",
                   deps[i].module_name, deps[i].spdx, link_name);
            failed++;
        }
    }

    printf("----------------------------------------------------\n");
    if (failed > 0) {
        printf("РЕЗУЛЬТАТ: Виявлено %d порушень. Збірку зупинено.\n", failed);
        return 1;
    }
    printf("РЕЗУЛЬТАТ: Всі залежності юридично сумісні.\n");
    return 0;
}
```

```cpp
#include <iostream>
#include <string>
#include <string_view>
#include <vector>
#include <expected>
#include <format>
#include <span>

namespace audit {

enum class LicenseClass {
    Permissive,  // MIT, BSD, ISC
    Apache2,     // Apache 2.0
    Lgpl,        // LGPL v2.1/v3.0
    Gpl2,        // GPL-2.0-only
    Gpl3,        // GPL-3.0-or-later
    Proprietary  // Закритий комерційний код
};

enum class LinkType {
    Static,
    Dynamic,
    Ipc
};

struct ModuleDependency {
    std::string name;
    std::string spdx;
    LicenseClass license;
    LinkType linkage;
};

struct ComplianceViolation {
    std::string module_name;
    std::string spdx;
    std::string reason;
};

class LicenseEvaluator {
public:
    static constexpr bool is_compatible(LicenseClass target, LicenseClass dep, LinkType link) noexcept {
        if (link == LinkType::Ipc) {
            return true;
        }

        switch (target) {
        case LicenseClass::Proprietary:
            if (dep == LicenseClass::Permissive || dep == LicenseClass::Apache2) return true;
            if (dep == LicenseClass::Lgpl) return (link == LinkType::Dynamic);
            return false;

        case LicenseClass::Gpl2:
            if (dep == LicenseClass::Permissive || dep == LicenseClass::Gpl2) return true;
            if (dep == LicenseClass::Apache2 || dep == LicenseClass::Gpl3) return false;
            return true;

        case LicenseClass::Gpl3:
            if (dep == LicenseClass::Gpl2) return false;
            return true;

        default:
            return false;
        }
    }

    static std::expected<void, std::vector<ComplianceViolation>> verify_manifest(
        std::string_view target_name,
        LicenseClass target_lic,
        std::span<const ModuleDependency> dependencies)
    {
        std::vector<ComplianceViolation> errors;
        std::cout << std::format("=== АУДИТ ЛІЦЕНЗІЙНОЇ ВІДПОВІДНОСТІ: {} ===\n", target_name);

        for (const auto& dep : dependencies) {
            const bool valid = is_compatible(target_lic, dep.license, dep.linkage);
            const std::string_view link_str = (dep.linkage == LinkType::Static) ? "STATIC" :
                                              (dep.linkage == LinkType::Dynamic) ? "DYNAMIC" : "IPC";

            if (valid) {
                std::cout << std::format("[OK]   {:<15} ({:<10}) Link: {:<8}\n",
                                         dep.name, dep.spdx, link_str);
            } else {
                std::cout << std::format("[FAIL] {:<15} ({:<10}) Link: {:<8} <-- БЛОКУВАННЯ ЗБІРКИ!\n",
                                         dep.name, dep.spdx, link_str);
                errors.push_back({dep.name, dep.spdx, "Неприпустима комбінація ліцензії та лінкування"});
            }
        }

        std::cout << "----------------------------------------------------\n";
        if (!errors.empty()) {
            return std::unexpected(errors);
        }
        return {};
    }
};

} // namespace audit

int main() {
    using namespace audit;

    const std::vector<ModuleDependency> project_deps = {
        {"libjson-c",    "MIT",        LicenseClass::Permissive, LinkType::Static},
        {"libcrypto",    "Apache-2.0", LicenseClass::Apache2,    LinkType::Static},
        {"libprotocols", "LGPL-2.1",   LicenseClass::Lgpl,       LinkType::Dynamic},
        {"system-core",  "GPL-2.0",    LicenseClass::Gpl2,       LinkType::Ipc},
        {"libdsp_filter","GPL-2.0",    LicenseClass::Gpl2,       LinkType::Static} // Порушення!
    };

    auto result = LicenseEvaluator::verify_manifest("Firmware-App", LicenseClass::Proprietary, project_deps);

    if (!result) {
        std::cout << std::format("РЕЗУЛЬТАТ: Виявлено {} порушень. Збірку зупинено.\n", result.error().size());
        return 1;
    }

    std::cout << "РЕЗУЛЬТАТ: Всі залежності юридично сумісні.\n";
    return 0;
}
```

## Підсумкова інженерна настанова

Побудова безпечної архітектури на базі відкритого коду спирається на три непохитні правила:

1. **Ізоляція за способом лінкування:** ніколи не компонуйте код під сильним або слабким копілефтом статично у комерційний виконуваний файл, якщо ви не готові оприлюднити повний вихідний код або надати об'єктні файли (`.o`) для перелінкування.
2. **Увага до патентних умов:** уникайте комбінування сторонніх бібліотек під `Apache-2.0` з модулями під `GPL-2.0-only` в одному адресному просторі. Якщо ядро вашого продукту вимагає GPLv2, використовуйте дозвільні компоненти під `MIT` або `BSD-2/3-Clause`.
3. **Автоматизований контроль у CI/CD:** впроваджуйте генерацію SBOM та обов'язкову верифікацію ідентифікаторів SPDX на кожному етапі збирання. Ліцензійна помилка, виявлена на етапі компіляції, коштує кілька хвилин на заміну бібліотеки; та сама помилка, виявлена після відвантаження фізичної партії пристроїв замовникам, призводить до судових позовів, блокування продажів та примусового відкриття комерційної таємниці.
