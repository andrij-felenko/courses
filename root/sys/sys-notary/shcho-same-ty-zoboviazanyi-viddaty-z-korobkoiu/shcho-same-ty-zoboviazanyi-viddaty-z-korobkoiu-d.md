# Що саме ти зобов'язаний віддати з коробкою: атрибуція, тексти ліцензій, письмова пропозиція джерел

<preknowlist>
- [Ліцензії відкритого коду](root:sys-notary/open-source-licenses) — дозвільні та копілефтні моделі, юридична сила публічних ліцензій і принцип взаємності.
- [SBOM: перелік складників образу](root:sys-notary/sbom-perelik-skladnykiv-obrazu-i-navishcho-ioho) — облік сторонніх компонентів, ідентифікація пакетів та версій у двійкових прошивках.
- [Пастка LGPL](root:sys-notary/pastka-lgpl) — статичне та динамічне лінкування, вимога надання об'єктних файлів для повторного компонування.
- [GPLv3 проти підписаного завантажувача](root:sys-notary/gplv3-proty-pidpysanoho-zavantazhuvacha) — апаратні ключі підпису, захист від блокування оновлень та інформація про встановлення.
</preknowlist>

Коли виробнича лінія упаковує партію промислових телеметричних контролерів, IoT-шлюзів чи автопілотів для безпілотників у картонні коробки для відвантаження замовникам, у енергонезалежній флеш-пам'яті кожного пристрою вже записано бінарний образ операційної системи. Цей образ містить ядро Linux, завантажувач U-Boot, набір системних утиліт BusyBox, системні бібліотеки glibc або musl, криптографічні модулі mbedTLS та пропрієтарні керуючі алгоритми компанії. Якщо коробку запечатати й відправити клієнту без супровідного ліцензійного буклету, повних текстів ліцензій або юридично дійсної письмової оферти на надання вихідного коду, компанія-виробник у ту ж секунду вчиняє правопорушення у сфері авторського права. Правовласники відкритого коду або організації правового захисту мають законне право через окружний суд вимагати негайної судової заборони на продаж усієї лінійки пристроїв, арешту складських запасів на митниці та виплати штрафних збитків за кожен реалізований екземпляр.

Відвантаження фізичного обладнання з прошитим двійковим кодом докорінно змінює правовий статус інженерної розробки. Доки код компілюється та тестується всередині лабораторії, будь-які ліцензійні вимоги залишаються «сплячими». Проте момент передачі коробки третій особі активує юридичний механізм дистрибуції. Щоб комерційний продукт залишався легальним, інженерний та юридичний відділи зобов'язані сформувати й передати разом із фізичним пристроєм суворо визначений комплект юридичних та технічних артефактів.

## Юридична природа дистрибуції: чому виникає обов'язок

У праві інтелектуальної власності комп'ютерна програма захищається нормами авторського права (англ. *copyright*, від лат. *copia* — копія + *ius* — право) аналогічно до літературних творів. За замовчуванням закон закріплює за автором абсолютну монополію: ніхто не має права копіювати, змінювати, компонувати чи передавати твір іншим особам без прямого дозволу правовласника.

Публічні ліцензії відкритого коду — це односторонній дозвіл автора, який надає інженерам право вільно використовувати та модифікувати код. Проте цей дозвіл є **умовним** (англ. *conditional grant*). Автор дозволяє поширювати скомпільований двійковий файл виключно за умови виконання зустрічних зобов'язань: збереження імен авторів (атрибуції), надання повних текстів ліцензійних угод та розкриття модифікованого вихідного коду разом зі складальними скриптами.

```
┌────────────────────────────────────────────────────────────────────────┐
│             МЕХАНІЗМ ДІЇ ЛІЦЕНЗІЙНОГО ДОЗВОЛУ ПРИ ДИСТРИБУЦІЇ          │
├────────────────────────────────────────────────────────────────────────┤
│ 1. Внутрішня розробка (Internal Use):                                  │
│    Компіляція, тестування на стенді, закриті експерименти              │
│    → Ліцензійні зобов'язання СПЛЯТЬ (немає факту передачі).           │
├────────────────────────────────────────────────────────────────────────┤
│ 2. Фізичне відвантаження (Distribution / Conveying):                   │
│    Продаж коробки, передача OEM-партнеру, бета-тестування замовником   │
│    → АКТИВАЦІЯ ЗОБОВ'ЯЗАНЬ РОЗКРИТТЯ АРТЕФАКТІВ.                      │
├────────────────────────────────────────────────────────────────────────┤
│ 3. Відвантаження БЕЗ обов'язкових артефактів:                          │
│    Порушення умов ліцензії (GPLv2 §4 / GPLv3 §8)                      │
│    → АВТОМАТИЧНЕ АНУЛЮВАННЯ ЛІЦЕНЗІЙНОГО ДОЗВОЛУ                      │
│    → Компанія стає піратом (Copyright Infringement)                   │
│    → Судова заборона продажів (Injunction) та арешт товару.            │
└────────────────────────────────────────────────────────────────────────┘
```

Момент передачі права власності або фізичного володіння пристроєм сторонній особі (покупцю, дистриб'ютору, системному інтегратору чи учаснику закритого бета-тестування) у термінології GPLv2 називається **дистрибуцією** (англ. *distribution*, від лат. *distribuere* — розподіляти, поширювати), а в GPLv3 — **передачею** (англ. *conveying*, від лат. *convehere* — звозити, доставляти).

Якщо виробник відвантажує пристрій, але не виконує передбачених ліцензією умов дистрибуції, відбувається автоматичне скасування ліцензійного дозволу (GPLv2, стаття 4):

> *«Будь-яка спроба копіювання, модифікації, субліцензування або поширення Програми інакше, ніж прямо передбачено цією Ліцензією, є недійсною і автоматично припиняє ваші права за цією Ліцензією».*

У ту ж мить, коли ліцензія анулюється, виробник втрачає законне право записувати код ядра Linux чи BusyBox у флеш-пам'ять своїх плат. Кожен наступний проданий контролер або дрон стає контрафактним примірником.

## Анатомія ліцензійного комплекту пристрою

Щоб пристрій був юридично чистим і захищеним від судових претензій, постачання апаратного виробу має супроводжуватися чотирма обов'язковими юридично-технічними компонентами.

![Анатомія ліцензійного комплекту: що постачається з фізичним пристроєм](/root/sys/sys-notary/shcho-same-ty-zoboviazanyi-viddaty-z-korobkoiu/img/box-compliance-bundle.svg)
*Повний склад комплаєнс-пакета для апаратного виробу: фізичні матеріали в коробці (буклет атрибуції та письмова оферта) і повний вихідний код зі скриптами збирання, доступний за запитом або онлайн.*

Кожен із цих чотирьох блоків вирішує окрему юридичну задачу та вимагається різними класами ліцензій відкритого коду:

1. **Буклет відкритих повідомлень (Open Source Notices):** закриває вимоги дозвільних ліцензій (MIT, BSD, Apache, ISC) та вимоги атрибуції копілефту;
2. **Письмова пропозиція (Written Offer):** юридичний документ за пунктом 3(b) ліцензії GPLv2 або 6(b) ліцензії GPLv3, який гарантує право будь-якої особи отримати вихідний код;
3. **Повний відповідний вихідний код (Complete Corresponding Source Code):** модифіковані дерева сирцевих текстів усіх компонентів під копілефтом, які дозволяють зібрати прошивку;
4. **Скрипти збирання та керування інсталяцією (Scripts used to control compilation and installation):** Makefiles, рецепти Yocto/Buildroot, конфігураційні файли ядра `.config` та інструкції прошивання.

## Обов'язковий ліцензійний буклет (Open Source Notices)

Поширена інженерна помилка полягає у переконанні, що дозвільні (англ. *permissive*) ліцензії — такі як MIT, BSD-2-Clause, BSD-3-Clause чи Apache 2.0 — дозволяють брати чужий код і використовувати його без жодних зобов'язань. Це не так. Дозвільні ліцензії не є суспільним надбанням (англ. *public domain*). Вони висувають одну сувору та безумовну вимогу: **збереження повідомлення про авторські права та відмови від гарантій**.

Текст ліцензії MIT прямо встановлює:

> *«The above copyright notice and this permission notice shall be included in all copies or substantial portions of the Software».*
> *(«Наведене вище повідомлення про авторські права та це повідомлення про дозвіл повинні включатися до всіх копій або істотних частин Програмного забезпечення»).*

Коли бібліотека cJSON, mbedTLS або libcurl компілюється й потрапляє у двійковий образ прошивки, кінцевий користувач отримує копію програми у двійковій формі. Відповідно, виробник зобов'язаний доставити користувачеві текст копірайту та ліцензії.

```
┌────────────────────────────────────────────────────────────────────────┐
│             СПОСОБИ ДОСТАВКИ OPEN SOURCE NOTICES КОРИСТУВАЧЕВІ         │
├───────────────────┬──────────────────────────┬─────────────────────────┤
│ Бездисплейний     │ Пристрій із графічним    │ Мережевий пристрій      │
│ мікроконтролер    │ екраном (HMI / GUI)      │ (Web / CLI інтерфейс)   │
├───────────────────┼──────────────────────────┼─────────────────────────┤
│ • Друкований      │ • Розділ «Налаштування   │ • Веб-сторінка          │
│   вкладиш/буклет  │   → Про систему →        │   http://192.168.1.1/   │
│   у коробку       │   Юридична інформація»   │   legal/notices.html    │
│ • Розділ у друко- │ • Текстове вікно з прок- │ • Вивід термінальної    │
│   ваній інструкції│   ручуванням ліцензій    │   команди               │
│   користувача     │   та копірайтів          │   `show licenses`       │
└───────────────────┴──────────────────────────┴─────────────────────────┘
```

Якщо пристрій не має дисплея (наприклад, датчик із бездротовим каналом LoRaWAN або контролер двигуна), єдиним законним способом надання повідомлень є **фізичний друкований буклет у коробці** або виділений розділ у друкованій інструкції з експлуатації. Розміщення інформації виключно у PDF-файлі на сайті компанії визнається неналежним виконанням ліцензії, оскільки користувач може не мати доступу до інтернету на момент розпакування товару.

### Особливі вимоги ліцензії Apache 2.0: збереження файлу NOTICE

Ліцензія Apache 2.0 містить додаткову вимогу в Розділі 4(d): якщо оригінальний проєкт містить текстовий файл з назвою `NOTICE`, дистриб'ютор зобов'язаний включити читабельну копію повідомлень про авторство з цього файлу до складу документації або інтерфейсу виробу.

Ігнорування вмісту файлів `NOTICE` під час автоматизованого збирання ліцензійних буклетів є типовим дефектом комплаєнсу, який часто стає формальним приводом для претензійних листів.

Детальні стандартизовані шаблони ліцензійних блоків для кожного типу ліцензій та правила оформлення файлів `NOTICE` наведено в довіднику [Шаблони письмової пропозиції та структури ліцензійного буклету](root:sys-notary/shcho-same-ty-zoboviazanyi-viddaty-z-korobkoiu/api-written-offer-templates.md).

## Письмова пропозиція вихідного коду (Written Offer)

Якщо для дозвільних ліцензій достатньо надрукувати буклет із копірайтами, то для компонентів під сильним копілефтом (GPLv2, GPLv3, LGPLv2.1, LGPLv3) головним обов'язком є надання вихідного коду.

Стаття 3 ліцензії GPLv2 надає дистриб'ютору три взаємовиключні шляхи виконання зобов'язання:

```
┌────────────────────────────────────────────────────────────────────────┐
│              ТРИ ЮРИДИЧНІ ШЛЯХИ ДИСТРИБУЦІЇ ЗА GPLv2 СТАТТЯ 3          │
├───────────────────┬──────────────────────────┬─────────────────────────┤
│ Пункт 3(a)        │ Пункт 3(b)               │ Пункт 3(c)              │
│ Фізичний носій    │ Письмова оферта          │ Некомерційна передача   │
│ у кожній коробці  │ (Written Offer)          │ отриманої оферти        │
├───────────────────┼──────────────────────────┼─────────────────────────┤
│ До кожного прист- │ У коробку вкладається    │ Застосовується виключно │
│ рою додається     │ юридично зобов'язуючий   │ неприбутковими органі-  │
│ USB-флешка або    │ документ із пропозицією  │ заціями, які передають  │
│ оптичний диск із  │ надати вихідний код за   │ чужий софт без змін     │
│ повним вихідним   │ запитом протягом 3 років │ (не для комерційних     │
│ кодом прошивки.   │ будь-якій третій особі.  │ виробників заліза!).    │
└───────────────────┴──────────────────────────┴─────────────────────────┘
```

Вкладати фізичний накопичувач (USB Flash Drive) у кожну коробку промислового пристрою за пунктом 3(a) економічно невигідно: це збільшує собівартість одиниці продукції (BOM) на кілька доларів і вимагає постійного перезапису флешок під час оновлення ревізій прошивки на заводі.

Тому 99% виробників електроніки обирають шлях **пункту 3(b) — письмову пропозицію (Written Offer)**.

### Життєвий цикл та правові пастки письмової оферти

Письмова пропозиція є публічною юридичною офертою (лат. *offero* — пропонувати), умови якої жорстко регламентовані текстом GPLv2.

![Життєвий цикл письмової пропозиції вихідного коду](/root/sys/sys-notary/shcho-same-ty-zoboviazanyi-viddaty-z-korobkoiu/img/written-offer-lifecycle.svg)
*Хронологія дії письмової оферти: строк 3 років розраховується окремо для кожного відвантаженого екземпляра виробу від дати його реалізації.*

Практичне застосування пункту 3(b) має кілька критичних юридичних нюансів, на яких найчастіше зрізаються компанії:

1. **Термін дії — не менше 3 років для КОЖНОГО екземпляра:** якщо компанія виготовила й прошила плату в січні 2024 року, але пристрій пролежав на складі дистриб'ютора і був проданий кінцевому клієнту в грудні 2025 року, трирічний строк надання вихідного коду для цього конкретного екземпляра закінчується лише в грудні 2028 року. Виробник зобов'язаний зберігати точні вихідні коди та конфігурацію саме цієї ревізії протягом усього періоду.
2. **Адресат — будь-яка третя особа (Any Third Party):** ліцензія GPLv2 §3b прямо вимагає надати код *«будь-якій третій особі»* (англ. *to give any third party*). Це означає, що виробник не має права вимагати підтвердження факту купівлі пристрою, чека, серійного номера чи реєстрації акаунта. Запит може надіслати сторонній дослідник безпеки, конкурент або громадський активіст — і компанія зобов'язана надати повний архів.
3. **Обмеження на оплату (Nominal Cost):** компанія має право стягнути плату виключно за фізичний носій та поштову пересилку (наприклад, 10–15 доларів за запис USB-накопичувача та доставку). Заборонено вимагати гроші за «роботу інженера з пошуку коду», «ліцензійний збір» чи «оплату доступу до репозиторію».
4. **Хибність посилання на апстрім (Upstream Fallacy):** написати в оферті «Вихідний код ядра Linux доступний за адресою kernel.org» — це пряме порушення ліцензії. Апстрім не містить ваших змін, ваших конфігурацій, драйверів апаратури та Device Tree файлів. Зобов'язання надати код лежить персонально на дистриб'юторі.

Як судова практика та позови проти гігантів ритейлу остаточно закріпили обов'язок надання письмової оферти та ліквідували практику формальних посилань на апстрім, детально описано в історичному нарисі [Судові війни навколо BusyBox: як формувався судовий стандарт виконання GPL](root:sys-notary/shcho-same-ty-zoboviazanyi-viddaty-z-korobkoiu/hist-busybox-gpl-litigation.md).

## Що вважається «Повним відповідним вихідним кодом»

Найбільш суперечливим питанням при підготовці комплаєнс-пакета є обсяг вихідного коду, який компанія зобов'язана передати. Розробники часто прагнуть обмежитися передачею кількох `.c` файлів, які вони особисто змінили в дереві ядра.

Ліцензія GPLv2 у статті 3 дає вичерпне інженерне та юридичне визначення поняття **Complete Corresponding Source Code (CCS)**:

> *«Для виконуваного твору повний вихідний код означає весь вихідний код для всіх модулів, які він містить, плюс будь-які пов'язані файли визначення інтерфейсів, плюс скрипти, що використовуються для керування компіляцією та встановленням виконуваного файлу».*

Судовий та індустріальний стандарт повноти формулюється через **критерій незалежної відтворюваності**:

> ⚖️ **Критерій повноти вихідного коду (The Reproducibility Test):**
> Сторонній кваліфікований інженер, отримавши наданий архів вихідних кодів на чистій хост-системі, повинен мати можливість запустити надані скрипти збирання й без ручного внесення змін чи пошуку відсутніх файлів отримати робочий бінарний образ, ідентичний за функціоналом тому, що прошитий у заводському пристрої.

```
┌────────────────────────────────────────────────────────────────────────┐

### Межа ядра та простору користувача: виняток системних викликів

Одне з найважливіших питань архітектури вбудованих систем — як поєднати відкрите ядро Linux під ліцензією GPLv2 із закритими комерційними алгоритмами керування пристроєм.

Лінус Торвальдс разом із першими авторами ядра зафіксував у головному файлі `COPYING` спеціальне роз'яснення:

> *«This copyright does *not* cover user programs that use normal system calls to talk to the kernel; this is considered normal use of the kernel, does not fall under the heading of "derived work"».*

Це означає, що прикладний бінарний файл, який працює у просторі користувача (user-space) і викликає стандартні функції ядра через системні виклики (`read()`, `write()`, `ioctl()`, `socket()`), не стає похідним твором від ядра Linux і не підлягає обов'язковому розкриттю під GPLv2.

Проте якщо пропрієтарний код компілюється як **модуль ядра** (Loadable Kernel Module, `.ko`), він завантажується у спільний адресний простір ядра, використовує неекспортовані внутрішні структури даних (`struct task_struct`, `struct net_device`) або викликає функції, позначені макросом `EXPORT_SYMBOL_GPL()`. У такому випадку модуль юридично розглядається як єдиний похідний твір із ядром і зобов'язаний поширюватися під ліцензією GPLv2. Спроби створення проміжних двійкових обгорток (англ. *binary shims*) без розкриття вихідних текстів неодноразово визнавалися порушенням ліцензії в судах Німеччини та США.

### Виняток для системних бібліотек (System Library Exception) та вбудовані системи

У статті 3 GPLv2 міститься так званий виняток для системних бібліотек:

> *«Однак, як спеціальний виняток, вихідний код, що поширюється, не повинен включати нічого, що зазвичай поширюється (у вихідній або двійковій формі) з основними компонентами (компілятором, ядром тощо) операційної системи, на якій виконується виконуваний файл, якщо тільки цей компонент сам не супроводжує виконуваний файл».*

На звичайному ПК під керуванням Ubuntu чи Fedora цей виняток дозволяє розробникам прикладних програм не включати стандартну бібліотеку `glibc` до складу архіву сирців своєї програми, оскільки вона постачається самою операційною системою.

Проте для вбудованих пристроїв (Embedded Appliances) **цей виняток не діє**. Оскільки виробник продає пристрій як єдине ціле (апаратну частину разом із прошивкою, ядром та libc), операційна система «супроводжує виконуваний файл». Тому виробник зобов'язаний розкривати вихідні коди ядра Linux, glibc, BusyBox та всіх інших системних компонентів прошивки.

## Специфіка ліцензії LGPL: вимоги до перелінковки

Окрему небезпеку для виробників становить використання бібліотек під Меншою стандартною громадською ліцензією GNU (LGPLv2.1 або LGPLv3), таких як `glibc`, `libsystemd`, `ffmpeg` чи `libusb`.

Ліцензія LGPL дозволяє розробникам створювати закриті комерційні додатки, що використовують бібліотеку LGPL, але накладає сувору умову взаємності: **користувач повинен мати технічну та юридичну можливість замінити бібліотеку LGPL на власну модифіковану версію та повторно скомпонувати програму**.

```
┌────────────────────────────────────────────────────────────────────────┐
│             ВИМОГИ LGPL ДО ЛІНКУВАННЯ ЗАКРИТОГО КОДУ                   │
├───────────────────────────────────┬────────────────────────────────────┤
│ Динамічне лінкування (.so)        │ Статичне лінкування (.a)           │
├───────────────────────────────────┼────────────────────────────────────┤
│ • Закритий бінарник завантажує    │ • Бібліотека LGPL зшита в єдиний   │
│   бібліотеку під час запуску.     │   монолітний двійковий файл.       │
│ • Користувач може замінити файл   │ • ВИРОБНИК ЗОБОВ'ЯЗАНИЙ НАДАТИ:    │
│   `libcustom.so` на файловій      │   1. Вихідний код бібліотеки LGPL; │
│   системі пристрою.               │   2. РЕЛОКОВНІ ОБ'ЄКТНІ ФАЙЛИ (.o) │
│ • Вихідний код закритого бінарника│      свого закритого додатка;      │
│   розкривати НЕ ПОТРІБНО.         │   3. Складальні скрипти лінкування.│
└───────────────────────────────────┴────────────────────────────────────┘
```

Якщо компанія статично компонує закриту керуючу програму зі статичним архівом `liblgpl.a`, вона зобов'язана вкласти в комплаєнс-архів усі об'єктні файли `.o` свого закритого додатка разом зі складальним скриптом `Makefile`, щоб користувач міг викликати компонувальник `ld` і зшити модифіковану версію бібліотеки з фірмовим додатком. Якщо передача об'єктних файлів розкриває комерційну таємницю, єдиним законним архітектурним виходом є повний перехід на динамічне лінкування (`.so`).

Детальні інженерні сценарії статичного та динамічного компонування розібрано в статті [Пастка LGPL: статичне лінкування й вимога дати переліновку](root:sys-notary/pastka-lgpl).

## Скрипти збирання та інструкції зі встановлення

Вимога надати *«scripts used to control compilation and installation»* є невіддільною частиною статті 3 GPLv2. Надання «голого» дерева вихідних кодів без інструкцій і скриптів, які викликають компілятор із потрібними прапорцями оптимізації та компонування, визнається судами неповноцінним виконанням оферти.

Складальний комплект повинен містити:
- Головний скрипт збирання (наприклад, `build.sh` або `Makefile`), який запускає повний цикл компіляції;
- Вказівку на точну версію крос-компілятора (наприклад, `arm-linux-gnueabihf-gcc 11.3.0`) та цільові параметри архітектури (`-march=armv7-a -mfpu=neon`);
- Файли конфігурації підсистем (файли `.config` для Linux Kernel та BusyBox).

### Різниця між GPLv2 та GPLv3: Інформація про встановлення (Installation Information)

Ліцензія GPLv2 вимагає надати скрипти збирання, але не зобов'язує виробника надавати криптографічні ключі для підпису двійкових образів, якщо процесор пристрою вимагає перевірки цифрового підпису перед завантаженням (Secure Boot). Ця юридична особливість дозволила створити бізнес-модель «тайвоізації» (Tivoization).

На противагу цьому, ліцензія GPLv3 у Розділі 6 прямо вводить поняття **Інформації про встановлення (Installation Information)**. Якщо продукт є споживчим виробом (англ. *User Product*), виробник зобов'язаний надати покупцеві:
1. Усі необхідні інструкції з прошивання зібраного бінарного образу у пам'ять плати;
2. Неконфіденційні ключі, цифрові сертифікати чи методи розблокування завантажувача, необхідні для того, щоб модифікована користувачем версія програми могла виконуватися на апаратному пристрої.

Якщо компанія використовує у прошивці компоненти під GPLv3 і блокує можливість оновлення апаратними ключами, це є прямим порушенням ліцензії GPLv3. Детальні правові механізми захисту від апаратного блокування розглянуто в статті [GPLv3 проти підписаного завантажувача: антитайвоізація](root:sys-notary/gplv3-proty-pidpysanoho-zavantazhuvacha).

## Аудит ланцюга постачання: пастки ODM та чипсетних BSP

У сучасній розробці електроніки виробники рідко пишуть увесь низькорівневий софт з нуля. Типовий процес базується на інтеграції готового комп'ютера-на-модулі (System-on-Module, SoM) від стороннього ODM-постачальника (наприклад, Variscite, Toradex або китайських вендорів Rockchip / Allwinner) або використанні заводського пакета підтримки плати (Board Support Package, BSP).

У цьому криється серйозна юридична пастка: **дистриб'ютор кінцевого виробу несе повну правову відповідальність за всі ліцензійні дефекти, закладені його постачальниками**.

```
┌────────────────────────────────────────────────────────────────────────┐
│             ЛАНЦЮГ ВІДПОВІДАЛЬНОСТІ ПРИ ВИКОРИСТАННІ СТОРОННІХ BSP     │
├────────────────────────────────────────────────────────────────────────┤
│ 1. Виробник чипсета / ODM (Китай / Тайвань):                           │
│    • Модифікує ядро Linux, додаючи бінарні блоби для GPU чи VPU.       │
│    • Не надає Device Tree або «забуває» вихідний код драйверів Wi-Fi.  │
├────────────────────────────────────────────────────────────────────────┤
│ 2. Виробник кінцевого виробу (Ваша компанія):                          │
│    • Інтегрує SoM у власний корпус, наклеює торгову марку.             │
│    • Продає готовий виріб у ЄС, США чи Україні.                        │
├────────────────────────────────────────────────────────────────────────┤
│ 3. Юридичний наслідок:                                                 │
│    • Судовий позов пред'являється НЕ китайському вендору чипсета,      │

│    • Неможливість отримати код від постачальника НЕ ЗВІЛЬНЯЄ від       │
│      виплати збитків та судової заборони продажів.                     │

Перед взяттям стороннього SoM або чипсетного BSP у серійне виробництво інженерний відділ зобов'язаний провести вхідний аудит (англ. *Inbound Compliance Audit*):
- Переконатися, що вендор надав повне сирцеве дерево ядра з можливістю чинної збірки безпосередньо з вихідних текстів;
- Перевірити відсутність закритих бінарних обгорток усередині простору ядра (`.ko`);
- Отримати письмові гарантії ліцензійної чистоти від постачальника апаратного модуля.

## Стандарт OpenChain (ISO/IEC 5230) та корпоративні вимоги

У сучасній контрактній розробці та серійному виробництві електроніки дотримання ліцензійної чистоти перестало бути виключно внутрішньою справою компанії. Великі системні інтегратори, автоконцерни та аерокосмічні підприємства вимагають від постачальників апаратних вузлів обов'язкової відповідності міжнародному стандарту **ISO/IEC 5230:2020 (OpenChain Specification)**.

Стандарт OpenChain встановлює ключові вимоги до організаційних процесів компанії-виробника:

1. **Призначення відповідальних:** наявність у штаті офіцера з комплаєнсу (Open Source Compliance Officer) або юридичної робочої групи, що перевіряє кожен реліз;
2. **Ведення актуального SBOM:** обов'язкове формування машинозчитуваного паспорта компонентів прошивки за специфікацією SPDX або CycloneDX при кожній збірці образу;
3. **Аудит сторонніх BSP:** перевірка пакетів підтримки плат (Board Support Packages), отриманих від постачальників чипсетів (NXP, STMicroelectronics, Rockchip, MediaTek). Вендорські BSP часто містять приховані бінарні бібліотеки без ліцензій, які порушують правила GPL ядра Linux;
4. **Контроль EOL та сервісного обслуговування:** якщо сервісний центр замінює материнську плату в купленому пристрої на нову апаратну ревізію з оновленим ядром, факт видачі відремонтованого пристрою клієнту є новою дистрибуцією. Це вимагає надання оновленої оферти та збереження вихідних кодів нової ревізії протягом наступних 3 років.

## Відтворюване збирання (Reproducible Builds) як доказ повноти

У судових та аудиторських перевірках головним доказом того, що наданий архів Complete Corresponding Source дійсно містить усі необхідні компоненти, є досягнення **відтворюваного збирання (англ. *Reproducible Builds*)**.

Якщо незалежний аудитор компілює код із наданого архіву і результуючий бінарний файл ядра чи кореневої файлової системи має інші криптографічні хеші (SHA-256), це викликає підозру у приховуванні додаткових вихідних текстів або патчів.

Щоб гарантувати бінарну ідентичність, інженерний конвеєр налаштовує детерміністичні параметри компіляції:
- **Фіксація часових позначок (SOURCE_DATE_EPOCH):** усі часові мітки у згенерованих файлах замінюються на фіксовану дату останнього коміту в репозиторії;
- **Нормалізація шляхів компіляції:** використання прапорця GCC `-fdebug-prefix-map`, щоб абсолютні шляхи до файлів на складальній машині розробника не потрапляли в налагоджувальні секції DWARF двійкового образу;
- **Детерміністичний порядок файлів у файлових системах:** генерація образів SquashFS та ext4 із фіксованим сортуванням імен файлів та фіксованими UID/GID.

## Подвійне ліцензування криптографічних бібліотек

Окрему увагу інженери повинні звертати на компоненти з комерційною моделлю подвійного ліцензування (англ. *dual-licensing*). Такі бібліотеки, як WolfSSL, Qt або SQLite (із платними розширеннями), поширюються одночасно під жорстким копілефтом (GPLv2/GPLv3) та комерційною платною ліцензією.

Якщо розробник включає WolfSSL у прошивку комерційного пристрою і не купує комерційну ліцензію у правовласника, діє ліцензія GPLv3. Це автоматично вимагає розкрити повний вихідний код усього додатку керування, який лінкується з WolfSSL. Спроба закрити код без оплати комерційного ліцензійного збору є класичним випадком подвійного правопорушення — як порушення копілефту GPLv3, так і прямого порушення умов комерційного використання.

## Економіка та наслідки ліцензійних порушень

Ігнорування ліцензійних вимог при відвантаженні коробок із залізом створює для бізнесу серйозні фінансові та операційні ризики, які значно перевищують витрати на налаштування комплаєнс-конвеєра.

Юридичний процес у випадку виявлення порушення розгортається за типовим сценарієм:

1. **Претензійний лист (Abmahnung у Німеччині / Cease & Desist у США):** правовласник або юридична фірма надсилає офіційну вимогу негайно припинити порушення, підписати зобов'язання про утримання від порушень під загрозою штрафу (нім. *strafbewehrte Unterlassungserklärung*) та компенсувати витрати на юридичний аналіз прошивки (зазвичай від 5 000 до 30 000 євро на першому етапі).
2. **Попередня судова заборона (Preliminary Injunction):** якщо компанія ігнорує претензію або відмовляється надати повний вихідний код зі скриптами збирання, суд ухвалює рішення про накладення арешту на комерційні партії товару.
3. **Блокування митного оформлення:** судове рішення передається митним органам, які зупиняють імпорт будь-яких контейнерів із пристроями цієї торгової марки.
4. **Вилучення з ритейлу (Product Recall):** великі торговельні мережі та маркетплейси (Amazon, Best Buy) негайно видаляють сторінки товару та повертають залишки на склад виробника, щоб уникнути солідарної відповідальності.
5. **Примусовий аудит та публікація коду:** компанія змушена наймати зовнішніх аудиторів для повної перевірки кодової бази та оприлюднювати вихідні коди разом з усіма накопиченими вендорськими патчами.

## Інженерний регламент відвантаження коробки

Щоб повністю захистити апаратний продукт від юридичних претензій, перед запуском кожної нової ревізії у масове виробництво інженерний відділ виконує фінальний чекліст передачі:

```
┌────────────────────────────────────────────────────────────────────────┐
│           ФІНАЛЬНИЙ ЧЕКЛІСТ ГОТОВНОСТІ КОРОБКИ ДО ВІДВАНТАЖЕННЯ        │
├────────────────────────────────────────────────────────────────────────┤
│ [ ] 1. Друкований буклет Open Source Notices вкладено в коробку        │
│        (містить копірайти авторів та повні тексти ліцензій).           │
│ [ ] 2. Текст письмової оферти (Written Offer) надруковано в інструкції │
│        із зазначенням строку дії ≥ 3 років та контактної адреси.       │
│ [ ] 3. Архів Complete Corresponding Source сформовано автоматично      │
│        через `archiver.bbclass` або `make legal-info`.                 │
│ [ ] 4. Робочий файл конфігурації ядра (.config) та .dts файли присутні.│
│        Чиста хост-машина успішно збирає бінарний образ з архіву.       │
│ [ ] 5. Бінарний образ прошивки зафіксовано в системі контролю версій   │
│        разом із точним Git SHA та хеш-сумою (SHA-256).                 │
│ [ ] 6. Архів джерел завантажено на довгостроковий захищений сервер     │
│        оферти із гарантією збереження не менше 3 років.                │
└────────────────────────────────────────────────────────────────────────┘
```

Дотримання цього регламенту перетворює відкритий вихідний код із юридичної міни уповільненої дії на надійний фундамент апаратного бізнесу, гарантуючи безперешкодне проходження митниці, довіру інституційних замовників і стабільність комерційних продажів.
