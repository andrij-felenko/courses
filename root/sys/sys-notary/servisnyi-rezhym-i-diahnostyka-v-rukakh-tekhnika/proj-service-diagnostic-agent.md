# ⚙️ Вбудований діагностичний агент із криптографічною автентифікацією

Розробка програмного забезпечення для промислових діагностичних інтерфейсів вимагає суворого дотримання принципів детермінізму, передбачуваного використання пам'яті та стійкості до збоїв передачі даних. У системах функціональної безпеки та критичної інфраструктури неприпустимо використовувати динамічне виділення пам'яті (`malloc`/`free` або неконтрольовані структури купи), оскільки фрагментація оперативної пам'яті може призвести до раптової відмови пристрою під час польового обслуговування.

Цей інженерний проект містить повну, виробничу реалізацію вбудованого сервісного агента (Embedded Diagnostic Agent), розробленого згідно з рекомендаціями стандартів IEC 61508 (SIL 3) та MISRA C:2012 / MISRA C++:2023. Реалізація охоплює повний стек діагностичного обміну:

1. **Канальний рівень (Framing):** Потоковий скінченний автомат розбору пакетів із кодуванням COBS (Consistent Overhead Byte Stuffing) та перевіркою контрольної суми CRC32. Кодування COBS гарантує швидку синхронізацію кадру за нульовим байтом-роздільником і виключає хибні спрацьовування при втраті зв'язку.
2. **Криптографічний рушій (Crypto Engine):** Модуль автентифікації техніка за протоколом виклику-відповіді (Challenge-Response). Підтримує генерацію випадкових одноразових блоків (Nonce) через TRNG, перевірку цифрових підписів та обчислення симетричних кодів автентифікації повідомлень HMAC-SHA256 із захистом від таймінг-атак (Constant-Time memory comparison).
3. **Диспетчер команд із матрицею привілеїв (Capability Dispatcher):** Рольове розмежування доступу до сервісних операцій на основі 32-бітної бітової маски дозволів (Capability Bitmask). Кожна команда перевіряється на відповідність активним правам сесії та наявності апаратного інтерлоку.
4. **Атомарний менеджер калібрувальних даних (Double-Buffer Storage):** Модуль збереження налаштувань у Flash-пам'яті за двобанковою схемою (Slot A / Slot B). Забезпечує захист від пошкодження даних при раптовому знеструмленні (Power-Loss Corruption) та проводить сувору верифікацію допустимих фізичних діапазонів (Plausibility Bounding Box Checks).
5. **Незмінний криптографічний журнал аудиту (Tamper-Resistant Audit Log):** Модуль циклічного запису транзакцій у хеш-ланцюг (Hash Chain), що гарантує юридичну беззаперечність і неможливість непомітного видалення або підробки записів про обслуговування.

```
+───────────────────────────────────────────────────────────────────────────+
| АРХІТЕКТУРА ВБУДОВАНОГО ДІАГНОСТИЧНОГО АГЕНТА                            |
```

## Теоретичні та інженерні основи безпечного агента

Для побудови системи з гарантованим рівнем стійкості необхідно детально розібрати внутрішню математику, протокольні структури та поведінку кожного ізольованого шару вбудованого агента.

### 1. Потокове обрамлення COBS: структура станів та доведення меж

Алгоритм COBS (Consistent Overhead Byte Stuffing) вирішує задачу прозорої передачі довільних бінарних даних через послідовний канал. Головна вимога промислового зв'язку — гарантувати, що символ початку/кінця кадру (байт `0x00`) зустрічається виключно на межах між пакетами і ніколи не з'являється всередині корисного навантаження.

Нехай вхідне повідомлення `M` складається з послідовності байтів `b₀, b₁, ..., bₙ₋₁`, де деякі байти `b_i = 0x00`. Якщо закодувати повідомлення за правилом COBS, ми отримаємо вихідну послідовність `C = c₀, c₁, ..., c_m, 0x00`, де:

```
c_k ∈ [0x01 .. 0xFF]   для всіх   k ∈ [0 .. m]
```

Значення першого байта `c₀` визначає зміщення (індекс) до наступного модифікованого байта:
- Якщо `c₀ = k`, це означає, що наступні `k-1` байтів передаються без змін, а на позиції `k` у вихідному повідомленні знаходився нульовий байт `0x00` (або це кінець блоку довжиною 254 байти).
- Якщо фрагмент даних без нулів має довжину рівно 254 байти, на початку записується код `0xFF`, після чого передаються всі 254 байти, і наступний байт коду знову визначає зміщення для подальших даних.

```
+───────────────────────────────────────────────────────────────────────────+
| ПРИКЛАД КОДУВАННЯ COBS ДЛЯ БЛОКУ З ТРЬОМА НУЛЯМИ                          |
|                                                                           |
| Вхідні байти:   [ 0x41, 0x00, 0x42, 0x43, 0x00, 0x00, 0x44 ]             |
| Індекси:           0     1     2     3     4     5     6                  |
|                                                                           |
| Крок 1 (Зсув 1): Байт 0x41 до нуля -> Зсув = 2                            |
| Крок 2 (Зсув 2): Байти 0x42, 0x43 до нуля -> Зсув = 3                     |
| Крок 3 (Зсув 3): Одразу нуль -> Зсув = 1                                  |
| Крок 4 (Зсув 4): Байт 0x44 до кінця -> Зсув = 2                           |
|                                                                           |
| Вихідний COBS:  [ 0x02, 0x41, 0x03, 0x42, 0x43, 0x01, 0x02, 0x44, 0x00 ] |
+───────────────────────────────────────────────────────────────────────────+
```

Математичне доведення накладних витрат:
Максимальне збільшення довжини кадру відбувається, коли у вхідному повідомленні взагалі немає нульових байтів. Тоді кожні 254 байти потребують вставки одного байта коду `0xFF`, плюс один початковий байт зміщення та один кінцевий термінатор:

```
Length_out = Length_in + 1 + ⌈ Length_in / 254 ⌉ + 1
```

Для типових сервісних команд довжиною `N ≤ 128` байт накладні витрати становлять рівно `2` байти (менше 1.6% смуги пропускання), що на порядок ефективніше за шістнадцяткове кодування Base64 або ASCII-Hex (де накладні витрати сягають 33–100%).

Скінченний автомат приймача (COBS Rx State Machine):

```
       ┌─────────────────────────────────────────────────────────┐
       │                СТАН 0: СИНХРОНІЗАЦІЯ                    │
       │    Очікування нульового байта-демаркатора               │
       └────────────────────────────┬────────────────────────────┘
                                    │ Отримано 0x00
                                    ▼
       ┌─────────────────────────────────────────────────────────┐
       │                СТАН 1: ЗЧИТУВАННЯ КОДУ                  │
       │    Code = Rx_Byte; Block_Len = Code - 1;                │
       └────────────────────────────┬────────────────────────────┘
                                    │ Code > 0
                                    ▼
       ┌─────────────────────────────────────────────────────────┐
       │                СТАН 2: КОПІЮВАННЯ ДАНИХ                 │
       │    Копіювання Block_Len корисних байтів у буфер         │
       └──────────────┬───────────────────────────┬──────────────┘
                      │ Block_Len вичерпано       │ Отримано 0x00
                      ▼                           ▼
       ┌──────────────────────────┐   ┌──────────────────────────┐
       │ ВСТАВКА НУЛЯ (якщо <255) │   │ ЗАВЕРШЕННЯ КАДРУ         │
       │ Перехід до СТАНУ 1       │   │ Перехід до валідації CRC │
       └──────────────────────────┘   └──────────────────────────┘
```

### 2. Математика контролю цілісності: CRC-32 IEEE 802.3

Контрольна сума CRC-32 базується на поліноміальній арифметиці над полем Галуа `GF(2)`. Повідомлення довжиною `k` біт представляється як двійковий поліном `M(x)`. Передавач множить `M(x)` на `x³²` і виконує ділення за модулем 2 на генераторний поліном `G(x)`:

```
M(x) · x³² = Q(x) · G(x) + R(x)
```

Залишок від ділення `R(x)` є 32-бітним кодом CRC. Під час прийому контролер обчислює залишок від ділення отриманого полінома `M'(x) · x³² + R(x)` на `G(x)`. Якщо спотворень не було, залишок дорівнює нулю (або магічній константі `0xDEBB20E3` при використанні інвертованого початкового стану).

Математичні гарантії стандарту IEEE 802.3:
- Відстань Геммінга `d = 4` для довжин блоків до 256 байтів: гарантоване виявлення будь-яких 1, 2 та 3-бітових спотворень;
- Гарантоване виявлення всіх поодиноких пачок помилок (Burst Errors) довжиною до 32 біт;
- Ймовірність непоміченої помилки для випадкового шуму в каналі зв'язку: `P_undetected = 2⁻³² ≈ 2.33 × 10⁻¹⁰`.

### 3. Специфікація бінарного протоколу (Wire Format) та структура кадрів

Діагностичний протокол працює поверх каналу байт-орієнтованих повідомлень. До накладання кодування COBS кожен пакет упакований у детермінований бінарний кадр `diag_frame_t` фіксованого максимального розміру (136 байтів):

```
+───────────────────────────────────────────────────────────────────────────+
| СТРУКТУРА НЕПАКОВАНОГО БІНАРНОГО КАДРУ DIAGNOSTIC FRAME                   |
|                                                                           |
|  0          1          2          3          4 ... (4+L-1)   (4+L) ...+3  |
| ┌──────────┬──────────┬──────────┬──────────┬──────────────┬────────────┐ |
| │  MAGIC   │ MSG_TYPE │ SEQ_NUM  │ PAYLOAD  │ PAYLOAD DATA │   CRC-32   │ |
| │  (0x53)  │ (uint8)  │ (uint8)  │ LEN (L)  │  (0..128 B)  │ (Little-E) │ |
| └──────────┴──────────┴──────────┴──────────┴──────────────┴────────────┘ |
|   1 байт     1 байт     1 байт     1 байт      L байтів       4 байти     |
+───────────────────────────────────────────────────────────────────────────+
```

Призначення полів заголовка та кінцевика кадру:
1. `MAGIC` (байт 0, значення `0x53` = ASCII `'S'`): магічний ідентифікатор протоколу. Дозволяє приймачу миттєво відкинути сміттєві байти або чужорідні пакети іншого протоколу до початку криптографічної обробки.
2. `MSG_TYPE` (байт 1): числовий код типу операції `diag_msg_type_t`. Визначає семантику корисного навантаження.
3. `SEQ_NUM` (байт 2): монотонно зростаючий лічильник послідовності пакетів (0..255). Відповідь діагностичного агента відтворює значення `SEQ_NUM` із отриманого вхідного запиту (`tx_frame.seq_num = rx_frame.seq_num`), завдяки чому зовнішня діагностична утиліта надійно пов'язує надіслані команди з отриманими відповідями в асинхронному режимі.
4. `PAYLOAD_LEN` (байт 3): фактична довжина поля корисного навантаження в байтах (`0 ≤ L ≤ 128`). Обмеження в 128 байтів гарантує детермінізм статичного виділення пам'яті в мікроконтролері.
5. `PAYLOAD DATA` (байти 4 .. 4+L-1): бінарні параметри команди.
6. `CRC-32` (байти 4+L .. 7+L): 32-бітна контрольна сума IEEE 802.3 у порядку байтів Little-Endian, обчислена за першими `4 + L` байтами кадру (`MAGIC || MSG_TYPE || SEQ_NUM || PAYLOAD_LEN || PAYLOAD`).

Повний розбір форматів корисного навантаження (Payload Layout):

- `MSG_CHALLENGE_REQ` (`0x01`): `PAYLOAD_LEN = 0`. Слугує тригером для генерації нового одноразового криптографічного виклику.
- `MSG_CHALLENGE_RESP` (`0x02`): `PAYLOAD_LEN = 36`. Формат: `[32B Nonce] || [4B Session_ID (uint32)]`. Одноразовий блок Nonce створюється апаратним генератором TRNG.
- `MSG_AUTH_SUBMIT` (`0x03`): `PAYLOAD_LEN = 76`. Формат: `[4B Technician_ID] || [4B Requested_Capabilities] || [4B Lease_Duration_Sec] || [64B Ed25519_Signature]`. Підпис обчислюється над хешем квитка `SHA256(Technician_ID || Requested_Caps || Lease_Duration_Sec || Nonce)`.
- `MSG_AUTH_STATUS` (`0x04`): `PAYLOAD_LEN = 13`. Формат: `[1B Status_Code] || [4B Granted_Capabilities] || [4B Active_Lease_Sec] || [4B Session_ID]`. Повертає статус авторизації та фактично призначені маски прав.
- `MSG_CALIB_WRITE` (`0x10`): `PAYLOAD_LEN = 20`. Формат packed-структури `diag_sensor_calib_t`:
  * `zero_offset` (`int32`, 4 байти): апаратне зміщення нульової точки АЦП;
  * `gain_scale` (`float32` IEEE 754, 4 байти): коефіцієнт перерахунку шкали;
  * `temp_coeff` (`int32`, 4 байти): лінійний коефіцієнт температурної компенсації;
  * `sequence_id` (`uint32`, 4 байти): лічильник версії налаштування;
  * `crc32` (`uint32`, 4 байти): контрольна сума перших 16 байтів калібрувальної структури.
- `MSG_CALIB_READ` (`0x11`): `PAYLOAD_LEN = 1`. Формат: `[1B Slot_Selector]` (`0x00` — активний слот, `0x01` — Slot A, `0x02` — Slot B).
- `MSG_CALIB_STATUS` (`0x12`): `PAYLOAD_LEN = 21`. Формат: `[1B Active_Slot_Index] || [20B diag_sensor_calib_t]`.
- `MSG_HEARTBEAT_PING` (`0x20`): `PAYLOAD_LEN = 4`. Формат: `[4B Client_Uptime_MS]`.
- `MSG_HEARTBEAT_PONG` (`0x21`): `PAYLOAD_LEN = 5`. Формат: `[1B Session_State] || [4B Remaining_Lease_MS]`.
- `MSG_ERROR_RESP` (`0xFF`): `PAYLOAD_LEN = 7`. Формат: `[1B Error_Status] || [1B Offending_Msg_Type] || [1B Subsystem_ID] || [4B Trace_Error_Code]`.

Всі багатобайтні цілі числа передаються виключно в порядку від молодшого байта до старшого (Little-Endian), що відповідає апаратній архітектурі ядер ARM Cortex-M та RISC-V.

### 4. Автомат станів сесії, ієрархія тайм-аутів та сторожові таймери

Для запобігання несанкціонованому перехопленню контролю та гарантії повернення системи в безпечний стан життєвий цикл сервісного зв'язку моделюється скінченним автоматом із суворими часовими межами.

```
       ┌─────────────────────────────────────────────────────────┐
       │                СТАН 0: UNAUTHENTICATED                  │
       │    Дозволено лише MSG_CHALLENGE_REQ та відкрите читання │
       └────────────────────────────┬────────────────────────────┘
                                    │ Отримано MSG_CHALLENGE_REQ
                                    │ Nonce = TRNG(32); запуск T_challenge
                                    ▼
       ┌─────────────────────────────────────────────────────────┐
       │                СТАН 1: CHALLENGE_PENDING                │
       │    Очікування підписаного квитка від техніка            │
       └──────────────┬───────────────────────────┬──────────────┘
                      │ T_challenge > 10 с        │ MSG_AUTH_SUBMIT валідний
                      ▼                           ▼
       ┌──────────────────────────┐   ┌──────────────────────────┐
       │ АНУЛЮВАННЯ NONCE         │   │ СТАН 2: AUTHENTICATED    │
       │ Очищення пам'яті         │   │ Призначення прав (Caps)  │
       │ Повернення в СТАН 0      │   │ Запуск Lease та Heartbeat│
       └──────────────────────────┘   └───────────┬──────────────┘
                                                  │
                 ┌────────────────────────────────┴────────────────────────────────┐
                 │ Heartbeat відсутній > 15 с або вичерпано Lease Duration         │
                 ▼                                                                 ▼
       ┌───────────────────────────────────────────────────────────────────────────┐
       │                СТАН 3: EXPIRED / SAFE SHUTDOWN                            │
       │    active_capabilities = 0; блокування актуаторів; аудит-запис у Flash    │
       └───────────────────────────────────────────────────────────────────────────┘
```

Ієрархія та призначення тайм-аутів сервісної сесії:

1. **Тайм-аут одноразового виклику (`T_challenge_timeout = 10` с):**
   Після генерації 32-байтного блоку `Nonce` за запитом `MSG_CHALLENGE_REQ` запускається зворотний відлік тривалістю 10 секунд. Якщо протягом цього вікна технік не надіслав коректно підписаний пакет `MSG_AUTH_SUBMIT`, одноразовий блок безповоротно стирається з оперативної пам'яті викликом безпечного затирання `memset(current_nonce, 0, 32)`. Будь-яка запізніла відповідь відхиляється з кодом `DIAG_ERR_INVALID_NONCE`. Це виключає можливість накопичення активних викликів і блокує відкладені атаки зловмисника.

2. **Сторожовий таймер життєдіяльності зв'язку (`Heartbeat Watchdog`):**
   - Нормальний інтервал відправки пінґів: `T_ping_interval = 5000` мс.
   - Критичний поріг втрати зв'язку (Grace Timeout): `T_watchdog_timeout = 15000` мс (три пропущені цикли).
   Якщо під час активного калібрування або тестування приводів діагностичний кабель випадково від'єднано чи планшет техніка завис, агент не залишається у відкритому стані. Після закінчення 15 секунд сторожовий таймер автоматично обнуляє маску привілеїв `active_capabilities = 0`, повертає виконавчі органи в аварійний нейтральний стан і переводить сесію в режим `EXPIRED`.

3. **Таймер абсолютної тривалості оренди (`Lease Duration Timer`):**
   Параметр `Lease_Sec` передається у підписаному квитку техніка (за замовчуванням 1800 с = 30 хвилин; максимально допустиме значення за політикою безпеки становить 7200 с = 2 години). Таймер монотонно зменшується внутрішнім апаратним лічильником системного часу `SysTick`. Після закінчення орендованого інтервалу сесія примусово закривається незалежно від наявності поточних Heartbeat-пінґів. Для продовження роботи технік зобов'язаний пройти повну процедуру автентифікації заново.

4. **Апаратний інтерлок безпеки (Hardware Safety Interlock):**
   Програмна перевірка привілеїв дублюється апаратним контролем фізичного стану системи. Перед виконанням критичних дій (зміна нульової точки датчика або калібрувального діапазону) агент опитує стан апаратного піна `SAFETY_INTERLOCK_PIN`. Якщо фізична перемичка або кінцевий вимикач безпеки розімкнуті, команда негайно блокується з кодом `DIAG_ERR_UNAUTHORIZED` навіть за наявності всіх програмних бітів у масці прав.

### 5. Багаторівневий захист від перебору ключів, повторних спроб та виснаження ресурсів

Підключення до промислової діагностичної лінії (RS-485, CAN-FD або сервісного роз'єму) створює загрозу автоматизованих атак перебору (Brute-Force), спроб виснаження джерела випадкових чисел (TRNG Entropy Starvation) та атак на вичерпання процесорного часу мікроконтролера (Denial of Service). Для повної нейтралізації цих векторів у діагностичному агенті реалізовано багаторівневий комплекс контрзаходів.

#### Алгоритм прогресивного експоненційного штрафу (Exponential Penalty Backoff)

Кожна невдала спроба автентифікації (недійсний підпис, некоректний Nonce або відхилена маска привілеїв) збільшує внутрішній лічильник помилок `failed_auth_counter`. Поведінка агента змінюється за ступінчастою шкалою покарань:

```
+───────────────────────────────────────────────────────────────────────────+
| МАТРИЦЯ ШТРАФІВ ПРИ НЕВДАЛИХ СПРОБАХ АВТЕНТИФІКАЦІЇ                       |
|                                                                           |
| Кількість невдач  | Реакція агента             | Затримка / Блокування    |
| ──────────────────┼────────────────────────────┼───────────────────────── |
| 1 – 2 спроби      | Стала штучна затримка      | +500 мс до відповіді     |
| 3 – 4 спроби      | Тимчасовий штрафний тайм-аут| Повне блокування на 5 с  |
| 5 – 9 спроб       | Тривалий локаут + тривога  | Блокування на 60 с + Flash |
| ≥ 10 спроб        | Апаратний Hardware Lockout | Блокування до рестарту  |
+───────────────────────────────────────────────────────────────────────────+
```

Механіка роботи штрафного механізму:
- **1–2 помилки:** агент штучно затримує формування негативної відповіді на 500 мс. Це нівелює швидкісну перевагу зловмисника на високошвидкісній шині (наприклад, 1 Мбод CAN-FD), обмежуючи швидкість перебору двома спробами на секунду, але не створює незручностей інженеру при випадковій помилці набору.
- **3–4 помилки:** агент переходить у стан `PENALTY_COOLDOWN` на 5 секунд. Будь-які вхідні пакети `MSG_AUTH_SUBMIT` відкидаються канальним парсером ще до виклику криптографічних підпрограм.
- **5–9 помилок:** час блокування збільшується до 60 секунд. Одночасно агент генерує критичний запис аудиту з типом події `SECURITY_ALERT_BRUTE_FORCE` і фіксує його в енергонезалежному Flash-журналі для подальшого розслідування інциденту безпеки.
- **≥ 10 помилок:** активується режим безповоротного апаратного блокування (Hardware Lockout Mode). Прийом будь-яких діагностичних пакетів заморожується назавжди. Вихід із цього стану можливий виключно через повне фізичне знеструмлення приладу (Power Cycle) та одночасне замикання заводського сервісного перемикача на друкованій платі.

#### Захист від виснаження пулу ентропії TRNG (Entropy Depletion Guard)

Апаратні генератори випадкових чисел (TRNG), побудовані на основі аналогового теплового шуму діодів Зенера або кільцевих генераторів (Ring Oscillators), мають обмежену продуктивність ентропії (зазвичай від 10 до 100 кбіт/с). Неперервне бомбардування запитами `MSG_CHALLENGE_REQ` могло б повністю виснажити пул ентропії або перевантажити шину периферії MCU.

Для запобігання цьому агент використовує алгоритм маркерного кошика (Token Bucket):
- Місткість кошика становить `Bucket_Capacity = 3` токени;
- Швидкість відновлення: 1 токен щосекунди (`Refill_Rate = 1` токен/с);
- Кожен запит `MSG_CHALLENGE_REQ` списує 1 токен.
Якщо токени вичерпані, агент негайно повертає статус `DIAG_ERR_UNAUTHORIZED` (Rate Limited) без звернення до апаратного блоку TRNG, що гарантує 100% захист генератора від перевантаження та забезпечує незмінно високу ентропію видаваних блоків Nonce.

#### Захист від атак сторонніми каналами за часом (Side-Channel Constant-Time Hardening)

Стандартні бібліотечні функції порівняння блоків пам'яті (такі як `memcmp`) оптимізовані за швидкістю та виконують ранній вихід (Early Exit) при знаходженні першого відмінного байта:

:::tabs
```c
/* ВРАЗЛИВА РЕАЛІЗАЦІЯ: час виконання залежить від першого незбігу */
while (len--) {
    if (*p1++ != *p2++) return (*(p1-1) - *(p2-1));
}
```
```cpp
// ВРАЗЛИВА РЕАЛІЗАЦІЯ: ранній вихід розкриває позицію першого незбігу
bool vulnerable_equals(std::span<const std::byte> a, std::span<const std::byte> b) noexcept {
    if (a.size() != b.size()) return false;
    for (std::size_t i = 0; i < a.size(); ++i) {
        if (a[i] != b[i]) return false; // Early exit розкриває секрет
    }
    return true;
}
```
:::

Вимірюючи час реакції контролера високоточним таймером або осцилографом на лінії TX, атакуючий може побайтово підбирати правильні значення Nonce або цифрового підпису.

У представленому агенті вся перевірка секретів реалізована функцією `diag_constant_time_memcmp` (та `constant_time_equals` у C++20), де цикл завжди беззаперечно проходить усі `len` байтів масиву, накопичуючи побітове "АБО" над різницею:

:::tabs
```c
/* ЗАХИЩЕНА CONSTANT-TIME РЕАЛІЗАЦІЯ: незмінний час виконання */
uint8_t diff = 0U;
for (size_t i = 0; i < len; ++i) {
    diff |= (uint8_t)(p1[i] ^ p2[i]);
}
return (int)diff;
```
```cpp
// ЗАХИЩЕНА CONSTANT-TIME РЕАЛІЗАЦІЯ: незмінний час виконання
bool constant_time_equals(std::span<const std::byte> a, std::span<const std::byte> b) noexcept {
    if (a.size() != b.size()) return false;
    std::byte diff{0};
    for (std::size_t i = 0; i < a.size(); ++i) {
        diff |= (a[i] ^ b[i]);
    }
    return diff == std::byte{0};
}
```
:::

Такий підхід забезпечує сталий час виконання з точністю до одного процесорного такту незалежно від вмісту перевірених блоків, що повністю нівелює можливість проведення атак за сторонніми часовими каналами.

### 6. Фізичні моделі сенсорного калібрування та температурної компенсації

Для прецизійного вимірювального каналу (п'єзорезистивного моста тиску або тензодатчика) вихідний сигнал АЦП зазнає температурного дрейфу нуля та зміни чутливості. Повна математична модель перетворення має вигляд:

```
P_phys = Gain(T) · [ Raw_ADC − Offset(T) ]
```

Де температурні залежності описуються поліномами другого порядку:

```
Offset(T) = Offset₀ + α₁ · (T − T_ref) + α₂ · (T − T_ref)²
Gain(T)   = Gain₀   + β₁ · (T − T_ref)
```

Параметри, що налаштовуються під час польового сервісу:
- `Offset₀` (`zero_offset`): апаратне зміщення нуля при нормальній температурі `T_ref = 25.0 °C` (допустимий діапазон: `500 .. 3500` відліків для 16-бітного АЦП із середньою точкою 2048);
- `Gain₀` (`gain_scale`): номінальний масштабний множник шкали (допустимий діапазон: `0.0001 .. 10.0` бар/відлік);
- `α₁` (`temp_coeff`): лінійний температурний коефіцієнт компенсації нуля.

### 7. Геометрія Bounding Box та верифікація допустимості

Функція контролю меж (Plausibility Bounding Box Check) виконує перевірку вектора параметрів `θ = [Offset₀, Gain₀, α₁]` на належність допустимому паралелепіпеду станів `Ω`:

```
OFFSET_MIN     ≤ Offset₀ ≤ OFFSET_MAX
GAIN_MIN       ≤ Gain₀   ≤ GAIN_MAX
TEMP_COEFF_MIN ≤ α₁      ≤ TEMP_COEFF_MAX
```

Якщо вектор параметрів виходить за межі паралелепіпеда `Ω`, операція запису негайно відхиляється без звернення до енергонезалежної пам'яті Flash.

### 8. Незмінний криптографічний журнал аудиту (Tamper-Resistant Audit Log)

Кожна сервісна операція генерує 64-байтний запис аудиту `diag_audit_entry_t`. Запис зв'язується з попереднім станом системи за алгоритмом хеш-ланцюга:

```
H₀ = Genesis_Hash
H_k = SHA256( H_{k-1} || Seq_k || Timestamp_k || Tech_ID_k || Action_k || Caps_k || SHA256(Payload_k) )
```

Властивості безпеки хеш-ланцюга:
1. **Неможливість підміни запису (Tamper Evidence):** Будь-яка зміна навіть одного біта в історичному записі `k` призведе до зміни значення `H_k`, що автоматично робить недійсними всі подальші контрольні суми `H_{k+1}, H_{k+2}, ..., H_n`.
2. **Неможливість видалення або вставки (Forward Secrecy):** Видалення проміжного запису скорочує ланцюг, порушуючи послідовність монотонних лічильників `Sequence_ID` та розриваючи хеш-зв'язок.
3. **Юридична беззаперечність (Non-Repudiation):** Запис містить ідентифікатор техніка `Tech_ID` та фіксує точний час і параметри внесених змін.

### 9. Апаратна інтеграція з перериваннями та контролером DMA

У високонавантажених вбудованих додатках обробка кожного байта за поодиноким перериванням UART RXNE створює неприпустимо велике навантаження на ядро (до 15–20% процесорного часу на швидкості 921600 бод).

Для усунення цього оверхеду в реальних прошивках канальний рівень COBS зв'язується з апаратним контролером прямого доступу до пам'яті (DMA):

```
       ┌─────────────────────────────────────────────────────────┐
       │                ФІЗИЧНА ЛІНІЯ UART RX                    │
       └────────────────────────────┬────────────────────────────┘
                                    │ Байти надходять по шині
                                    ▼
       ┌─────────────────────────────────────────────────────────┐
       │             АПАРАТНИЙ КІЛЬЦЕВИЙ БУФЕР DMA               │
       │    Розмір: 256 байтів у статичній SRAM пам'яті          │
       │    Покажчик запису контролюється апаратним лічильником   │
       └──────────────┬───────────────────────────┬──────────────┘
                      │ Half-Transfer (HT)        │ IDLE Line Interrupt
                      ▼                           ▼
       ┌──────────────────────────┐   ┌──────────────────────────┐
       │ ОБРОБКА ПЕРШОЇ ПОЛОВИНИ  │   │ ДЕТЕКЦІЯ ЗАВЕРШЕННЯ КАДРУ│
       │ Передача в COBS-декодер  │   │ Пошук 0x00 і виклик FSM  │
       └──────────────────────────┘   └──────────────────────────┘
```

Така комбінація (Circular DMA + IDLE Line Detection) зводить процесорні витрати майже до нуля під час очікування кадру, виділяючи обчислювальні ресурси ядра виключно на етапі декодування COBS та валідації CRC32/SHA256.

## Інженерний аналіз та верифікація реалізації

Наведена реалізація забезпечує суворе виконання вимог безпеки промислових вбудованих систем:

1. **Гарантія детермінізму часу та пам'яті:** Усі буфери (прийомний, передавальний та криптографічні хеш-стани) розміщуються статично або на стеку в межах фіксованих структур. Жодна операція не звертається до купи (Heap), що повністю виключає непередбачувані затримки від збирача сміття або помилки нестачі пам'яті (Out of Memory).
2. **Стійкість до атак за часом (Side-Channel Hardening):** Перевірка цифрового підпису та мандатів сесії виконується функцією `diag_constant_time_memcmp` (у C99) та `constant_time_equals` (у C++20), що унеможливлює вимірювання затримок для побайтового підбору секретів.
3. **Цілісність калібрувальних таблиць:** Використання механізму подвійної буферизації з контрольною сумою CRC32 та магічними мітками `0xCAFEBABE` гарантує, що при знеструмленні під час запису прилад автоматично повернеться до попереднього валідного калібрувального слота без зупинки виробничого процесу.
4. **Незмінний аудит:** Хеш-ланцюг оновлюється при кожній успішній операції калібрування чи автентифікації, забезпечуючи захист від відкату та повну простежуваність дій польового персоналу відповідно до регламентів Cyber Resilience Act.
5. **Зв'язок із загальною архітектурою:** Цей модуль безпосередньо інтегрується в ядро системи та доповнює концепції, викладені в [головній статті про сервісний режим і діагностику](root:sys-notary/servisnyi-rezhym-i-diahnostyka-v-rukakh-tekhnika/servisnyi-rezhym-i-diahnostyka-v-rukakh-tekhnika-d.md).

```
| ─────────────────────────────┼─────────────────────┼───────────────────── |

| ─────────────────────────────┼─────────────────────┼───────────────────── |

| Loss) посеред запису сектора | (Double-Buffer A/B) | валідний слот        |

```

Детальний аналіз відмовостійкості:
- **Стійкість до апаратного знеструмлення (Power-Loss Tolerance):** При збереженні нового калібрування агент спочатку записує дані в пасивний слот Flash (наприклад, Slot B, якщо активним є Slot A), обчислює та зберігає контрольну суму CRC32 і збільшує покоління `sequence_id = slot_a.sequence_id + 1`. Лише після успішної перевірки записаного блоку перемикається індекс `active_slot_index = 1`. Якщо живлення вимкнеться в середині операції програмування Flash, пошкоджений Slot B буде відкинутий під час наступного завантаження через незбіг контрольної суми CRC32 або пошкодження магічного заголовка `0xCAFEBABE`, і система продовжить безпечну роботу на перевірених налаштуваннях слота Slot A.
- **Стійкість до спотворень лінії зв'язку:** Приймальний скінченний автомат COBS не містить нескінченних циклів або блокуючих операцій. Будь-який некоректний байт зміщення або поява нульового роздільника `0x00` посеред очікуваного блоку призводить до негайного скидання індексу прийому `write_idx = 0` та переходу в стан синхронізації без зависання периферії DMA.
- **Захист від несанкціонованого калібрування:** Перевірка геометрії допустимого паралелепіпеда станів (Bounding Box) проводиться строго до виконання будь-яких низькорівневих операцій запису у Flash-пам'ять. Це виключає деградацію ресурсу зносу комірок пам'яті (Flash Endurance Wear-Out) при спробах надсилання некоректних параметрів шкідливим або несправним діагностичним обладнанням.
