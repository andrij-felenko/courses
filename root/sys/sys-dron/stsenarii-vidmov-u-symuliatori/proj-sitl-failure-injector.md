# Інжектор аномалій та відмов для SITL/MAVLink: тестовий фреймворк і валідатор реакцій автопілота

Тестування реакції безпілотного апарата на критичні збої сенсорів, обрив каналів зв'язку та фізичну відмову силової установки вимагає наявності спеціалізованого проміжного програмного забезпечення. Звичайний запуск автопілота в симуляторі транслює ідеальний потік телеметрії, приховуючи граничні умови, за яких розширюваний фільтр Калмана EKF або автомат Failsafe можуть увійти в стан некерованої розбіжності. Для вирішення цього завдання створюється проксі-інжектор аномалій (MAVLink Fault Injector), який прозоро вбудовується в мережевий розрив між фізичним симулятором (Gazebo, AirSim, jMAVSim) та процесом автопілота (PX4 Autopilot або ArduPilot).

```
   ┌──────────────────────┐                     ┌──────────────────────┐
   │  ФІЗИЧНИЙ СИМУЛЯТОР  │                     │   ПОЛЬОТНИЙ СТЕК     │
   │  (Gazebo / AirSim)   │                     │    (SITL / HITL)     │
   │  UDP Порт: 14560     │                     │  UDP Порт: 14550     │
   └──────────┬───────────┘                     └──────────▲───────────┘
              │                                            │
              │  HIL_SENSOR / GPS_RAW_INT                  │
              ▼                                            │
   ┌───────────────────────────────────────────────────────┴───────────┐
   │            ПРОКСІ-ІНЖЕКТОР АНОМАЛІЙ (Fault Injector)              │
   │                                                                   │
   │   1. Розбір та парсинг фреймів MAVLink v2 (CRC16 + CRC Extra)     │
   │   2. Диспетчеризація сценаріїв за модельним часом `time_usec`     │
   │   3. Модулі мутації:                                              │
   │      • GPS Jamming / Spoofing (HDOP, Satellites, Fix Type)        │
   │      • Link Degradation (Delay Buffer, Jitter, Burst Drop)        │
   │      • IMU Drift & Sensor Noise (Allan Variance / Bias Step)      │
   │      • Motor Kill & Actuator Saturation (PWM / DShot Clamp)       │
   │   4. Перерахунок контрольних сум CRC16 та прозора ретрансляція    │
   │   5. Валідатор асертів (Assert Engine) та оцінка реакції Failsafe │
   └───────────────────────────────────────────────────────────────────┘
```

## 1. Мережева топологія та архітектура MAVLink-проксі

Проксі-інжектор функціонує як мережевий міст на базі неблокуючих сокетів UDP (POSIX Sockets API). Інжектор відкриває два незалежні мережеві кінцеві вузли:
- **Вузол симулятора (Simulator Endpoint)**: прив'язується до локального порту (наприклад, `14560`) і здійснює двосторонній обмін пакетами сенсорних вимірювань `HIL_SENSOR`, `GPS_RAW_INT` та відправку зворотних сигналів актуаторів `HIL_ACTUATOR_CONTROLS`.
- **Вузол автопілота (Autopilot Endpoint)**: зв'язується з портом польотного контролера (наприклад, `14550`), передаючи модифікований потік даних та приймаючи команди керування.

Головний цикл інжектора побудовано на системному виклику мультиплексування вводу-виводу `poll()` або `epoll()`, що забезпечує мікросекундний час реакції на надходження пакетів без споживання процесорного часу у порожніх циклах очікування.

Для уникнення блокування потоків передачі даних при високих навантаженнях (понад 500 Гц) сокети налаштовуються з опцією `SO_REUSEADDR` та збільшеними системними буферами прийому `SO_RCVBUF` і відправки `SO_SNDBUF` розміром не менше 512 КБ. Це гарантує відсутність втрат пакетів на рівні ядра операційної системи хоста під час тривалих перехідних процесів.

Внутрішня архітектура інжектора побудована навколо чотирьох функціональних блоків:
1. **Шар асинхронного введення-виведення (I/O Layer)**: забезпечує неблокуюче читання сирих байтових масивів із UDP-сокетів та їх передачу в конвеєр обробки.
2. **Синтаксичний аналізатор протоколу (Protocol Parser)**: розбирає потік байтів, виділяє заголовки MAVLink v2, верифікує контрольні суми, визначає ідентифікатор повідомлення `MSG_ID` та розпаковує структури корисного навантаження (Payload).
3. **Конвеєр параметричних мутаторів (Mutation Pipeline)**: послідовно застосовує активні правила спотворення інформації відповідно до поточного сценарію тестування.
4. **Диспетчер черги затримки (Delay Scheduler)**: реалізує впорядкований за часом кільцевий буфер для точного моделювання мережевої затримки (Latency) та фазового джитера (Jitter).

```

                 │
                 ▼

                 │
                 ▼
   ┌────────────────────────────┐
   │ MAVLink v2 Frame Parser    │
   └─────────────┬──────────────┘
                 │
                 ▼
   ┌────────────────────────────┐
   │ Mutation Pipeline:         │

### Синхронізація модельного часу та покроковий детермінізм

При тестуванні складних сценаріїв відмов критично важливо забезпечити детерміністичну прив'язку аномалій до модельного часу симулятора. У фізичних рушіях (Gazebo, JSBSim) час симуляції `time_usec` транслюється всередині кожного сенсорного повідомлення. Якщо інжектор спиратиметься на системний годинник комп'ютера `gettimeofday()`, будь-яке коливання продуктивності хоста спотворить момент інжекції збою.

Інжектор використовує власний віртуальний годинник, синхронізований із позначками `time_usec` у повідомленнях `HIL_SENSOR` та `GPS_RAW_INT`. При активації lockstep-режиму симуляції кожен крок фізики заморожується до моменту повної обробки попереднього пакету. Це дозволяє запускати матриці тестів у headless-режимі з прискоренням у 5–10 разів без будь-якої зміни фізичної динаміки збоїв.

Для забезпечення максимальної пропускної здатності черга пакетів побудована як односпрямований кільцевий буфер без блокувань (Single-Producer Single-Consumer Lock-Free Queue). Обмін вказівниками між мережевим потоком прийому та потоком мутації виконується за допомогою атомарних операцій з упорядкуванням пам'яті `std::memory_order_release` та `std::memory_order_acquire`. Це виключає використання системних м'ютексів і запобігає виникненню інверсії пріоритетів.

Для запобігання деградації кеш-пам'яті процесора через ефект хибного розділення ліній кешу (False Sharing) структури вказівників голівки (`head`) та хвоста (`tail`) черги вирівнюються за межею 64-байтової лінії кешу за допомогою специфікатора `alignas(64)`. Коли потік-виробник (Producer) інкрементує хвіст черги `tail.store(next_tail, std::memory_order_release)`, процесорне ядро оновлює лише свій локальний кеш L1D без інвалідації кеш-лінії потоку-споживача (Consumer), що читає показчик `head.load(std::memory_order_acquire)`. Завдяки цьому пропускна здатність внутрішньої черги інжектора досягає понад 12 мільйонів пакетів на секунду при затримці між потоками менше 40 наносекунд.

Шар мережевої маршрутизації підтримує роботу з множинними польотними контролерами та ройовими конфігураціями (Multi-Vehicle Simulation). Інжектор відстежує поле системного ідентифікатора `SYS_ID` у заголовку кожного пакета і направляє модифікований трафік на відповідні індивідуальні порти автопілотів (`14550 + (SYS_ID - 1) * 10`). Це дозволяє тестувати сценарії часткового придушення зв'язку в рою, коли глушиться лише частина безпілотників групи, тоді як решта апаратів перерозподіляє завдання ретрансляції даних.

Під час передачі пакетів через віртуальні інтерфейси операційної системи Linux критично контролювати затримку на перемикання контексту ядра. Використання сокетів UDP дозволяє реалізувати механізм Zero-Copy передачі даних: інжектор читає пакет безпосередньо в заздалегідь виділений буфер у кільцевій черзі, модифікує зміщення байтів «на місці» (in-place mutation) і передає вказівник у виклик `sendto()`. Завдяки цьому відсутні зайві операції виділення динамічної пам'яті (`malloc` / `new`) у реальному часі циклу обробки, а середня затримка проходження інжектора не перевищує 8 мікросекунд на пакет.

Для усунення фрагментації пам'яті при тривалому стрес-тестуванні (понад 24 години безперервної симуляції) інжектор використовує пул статично виділених сторінок пам'яті HugePages розміром 2 МБ (через прапорець `mmap(MAP_HUGETLB)`). Це зменшує навантаження на буфер асоціативної трансляції адрес процесора (TLB - Translation Lookaside Buffer) та повністю запобігає затримкам на обробку промахів TLB під час інтенсивного обміну сенсорними пакетами.

Крім того, на рівні мережевих сокетів інжектор налаштовує пороги низької ватерлінії (Low Watermark `SO_RCVLOWAT` та `SO_SNDLOWAT`). Встановлення значення ватерлінії рівним розміру мінімального валідного кадру MAVLink (12 байт) гарантує, що планувальник ядра Linux генерує подію готовності `POLLIN` у підсистемі `poll` / `epoll` у той самий момент, коли перший заголовок надходить до мережевої карти, запобігаючи накопиченню напівпорожніх буферів. Для захисту від випадкових сплесків системних затримок черга відправки використовує механізм циклічного перезапису найстаріших непривілейованих телеметричних кадрів, віддаючи абсолютний пріоритет критичним пакетам `HIL_SENSOR` та `HEARTBEAT`.

У сучасних ядрах Linux (версії 5.10 і новіших) для максимальної мінімізації накладних витрат операційної системи замість класичного виклику `poll()` застосовується підсистема асинхронного введення-виведення `io_uring`. Механізм `io_uring` базується на двох спільних кільцевих буферах ядра та простору користувача: черзі відправки SQ (Submission Queue) та черзі завершення CQ (Completion Queue). Інжектор надсилає системні запити на прийом (`IORING_OP_RECVMSG`) та відправку (`IORING_OP_SENDMSG`) без виконання блокуючих системних викликів `syscall`, що повністю усуває витрати процесора на зміну привілеїв ядра та перехід між кільцями захисту Ring 3 і Ring 0.

Для забезпечення передбачуваного часу реакції при роботі на високих частотах дискретизації (1000 Гц для симуляції фізики та 400 Гц для контуру оновлення EKF) інжектор налаштовує планувальник операційної системи реального часу. Потік обробки мережевих пакетів переводиться в клас реального часу `SCHED_FIFO` із системним пріоритетом 85 через виклик `pthread_setschedparam()`. Крім того, робочий потік жорстко прив'язується до виділеного ізольованого ядра центрального процесора (Core Pinning) за допомогою функції `pthread_setaffinity_np()`. Це унеможливлює витиснення інжектора фоновими процесами операційної системи хоста та ліквідує паразитичний джитер системних таймерів.

У високопродуктивних інженерних середовищах замість сокетів UDP може використовуватися міжпроцесна взаємодія на базі бібліотеки ZeroMQ (патерни `ZMQ_PAIR` або `ZMQ_ROUTER/DEALER`) через транспорт `ipc://` або спільну пам'ять `shm_open()`. Порівняльний аналіз показує, що передача фреймів через спільну пам'ять знижує середню дисперсію затримки доставки пакета від симулятора до автопілота з 12.4 мкс (для сокетів UDP) до 0.85 мкс (для Lock-Free SHM), що робить симуляцію повністю ідентичною роботі реальних апаратних шин SPI та CAN на борту фізичного дрона.

Для оптимізації мережевих черг Linux інжектор автоматично перевіряє системні буфери прийому і встановлює прапорець `IP_TOS` зі значенням `IPTOS_LOWDELAY` (0x10) для мінімізації черг маршрутизації в ядрі. Також відключається алгоритм Нейгла на рівні транспорту для усунення штучної буферизації дрібних телеметричних пакетів.

## 2. Структура бінарного кадру MAVLink v2 та перерахунок контрольних сум

Протокол MAVLink версії 2 оптимізований для надійної передачі двійкових структур по ненадійних каналах зв'язку з мінімальними накладними витратами.

```
+----+-----+-----+-----+-----+--------+---------+--------+---------+----------+-----------+
|STX | LEN | INC | CMP | SEQ | SYS_ID | COMP_ID | MSG_ID | PAYLOAD | CHECKSUM | SIGNATURE |
|1 B | 1 B | 1 B | 1 B | 1 B |  1 B   |   1 B   |  3 B   | 0..255B |   2 B    |   13 B    |
+----+-----+-----+-----+-----+--------+---------+--------+---------+----------+-----------+
```

### Призначення полів заголовка

1. `STX` (Magic Byte): обов'язковий початковий байт `0xFD`. Використовується приймачем для синхронізації та пошуку початку кадру в потоці байтів.
2. `LEN` (Payload Length): кількість байтів корисного навантаження в пакеті (від 0 до 255).
3. `INC` (Incompatibility Flags): прапорці несумісності. Біт 0 (`0x01`) вказує на наявність 13-байтового цифрового підпису пакета (Signature). Якщо приймач не підтримує встановлені прапорці, пакет відкидається.
4. `CMP` (Compatibility Flags): прапорці сумісності. Використовуються для розширення функціоналу без порушення роботи застарілих парсерів.
5. `SEQ` (Sequence Number): циклічний лічильник номерів пакетів (0..255). Дозволяє фіксувати пропуски та втрати пакетів у каналі зв'язку.
6. `SYS_ID` (System ID): ідентифікатор безпілотного апарата в мережі (1..255).
7. `COMP_ID` (Component ID): ідентифікатор конкретного бортового модуля (1 = Autopilot, 100 = Camera, 190 = Ground Station).
8. `MSG_ID` (Message ID): 24-бітне ціле число (3 байти, порядок байтів Little-Endian), яке однозначно визначає тип переданої структури.

### Математичний алгоритм CRC16-MCRF4XX та CRC_EXTRA

Контрольна сума MAVLink v2 забезпечує захист як від випадкових бітових спотворень у каналі зв'язку, так і від несумісності версій прошивок між передавачем та приймачем.

Розрахунок ведеться за стандартом CRC16-MCRF4XX з поліномом `0x1021` та початковим значенням регістру `0xFFFF`. Алгоритм побайтового накопичення контрольної суми формулюється наступним чином:

```
tmp = byte ^ (crc & 0xFF)
tmp ^= (tmp << 4)
crc = (crc >> 8) ^ (tmp << 8) ^ (tmp << 3) ^ (tmp >> 4)
```

Головною інженерною особливістю MAVLink є механізм `CRC_EXTRA`. Для кожного повідомлення на етапі генерації коду з XML-схеми обчислюється спеціальний магічний байт на основі імен та типів полів структури:

```
CRC_EXTRA = CRC8(message_name + field_types + field_names)
```

Під час фінального розрахунку контрольної суми байт `CRC_EXTRA` накопичується у регістр CRC16 останнім, але не передається фізично по лінії зв'язку:

```
uint16_t final_crc = crc_calculate(packet_bytes_without_stx);
crc_accumulate(CRC_EXTRA, &final_crc);
```

Якщо інжектор змінює будь-яке поле всередині корисного навантаження (наприклад, модифікує широту чи кількість супутників), він зобов'язаний заново перерахувати двобайтову контрольну суму з використанням точного `CRC_EXTRA` для відповідного `MSG_ID`. Якщо цього не зробити, низькорівневий драйвер автопілота порахує пакет битим і відкине його на рівні переривання UART або мережевого стека NuttX.

У таблиці наведено параметри та константи `CRC_EXTRA` для критичних повідомлень симуляції:

| Повідомлення | MSG_ID | Розмір Payload | CRC_EXTRA | Призначення в симуляторі |
|---|---|---|---|---|
| `HEARTBEAT` | 0 | 9 байт | 50 | Пульс системи, стан автопілота та режим польоту |
| `GPS_RAW_INT` | 24 | 30 байт | 24 | Сирі координати, HDOP, VDOP, кількість супутників |
| `ATTITUDE` | 30 | 28 байт | 39 | Просторова орієнтація (Roll, Pitch, Yaw, кутові швидкості) |
| `LOCAL_POSITION_NED` | 32 | 28 байт | 185 | Оцінені координати та швидкості в локальній системі NED |

### Детальна структура бінарних полів повідомлень

Для прецизійної модифікації інжектор повинен знати точне побайтове зміщення кожного поля всередині корисного навантаження (Little-Endian):

1. **`GPS_RAW_INT` (MSG_ID = 24)**:
   - Байти `0..7`: `time_usec` (`uint64_t`) — час у мікросекундах від запуску системи.
   - Байти `8..11`: `lat` (`int32_t`) — широта в градусах `* 1e7` (WGS-84).
   - Байти `12..15`: `lon` (`int32_t`) — довгота в градусах `* 1e7` (WGS-84).
   - Байти `16..19`: `alt` (`int32_t`) — висота над рівнем моря в міліметрах (MSL).
   - Байти `20..21`: `eph` (`uint16_t`) — горизонтальна дисперсія похибки у сантиметрах.
   - Байти `22..23`: `epv` (`uint16_t`) — вертикальна дисперсія похибки у сантиметрах.
   - Байти `24..25`: `vel` (`uint16_t`) — 2D шляхова швидкість у см/с.
   - Байти `26..27`: `cog` (`uint16_t`) — курс руху в сантиградусах (`0..35999`).
   - Байт `28`: `fix_type` (`uint8_t`) — тип навігаційного рішення (0-1 = No Fix, 2 = 2D, 3 = 3D, 4 = DGPS, 5 = RTK Float, 6 = RTK Fixed).
   - Байт `29`: `satellites_visible` (`uint8_t`) — кількість видимих супутників.

2. **`HIL_SENSOR` (MSG_ID = 107)**:
   - Байти `0..7`: `time_usec` (`uint64_t`) — мітка часу симуляції.
   - Байти `8..11`: `xacc` (`float`) — прискорення по осі X у зв'язаній системі `[m/s²]`.
   - Байти `12..15`: `yacc` (`float`) — прискорення по осі Y у зв'язаній системі `[m/s²]`.
   - Байти `16..19`: `zacc` (`float`) — прискорення по осі Z у зв'язаній системі `[m/s²]`.
   - Байти `20..23`: `xgyro` (`float`) — кутова швидкість крену (Roll Rate) `[rad/s]`.
   - Байти `24..27`: `ygyro` (`float`) — кутова швидкість тангажу (Pitch Rate) `[rad/s]`.
   - Байти `28..31`: `zgyro` (`float`) — кутова швидкість рискання (Yaw Rate) `[rad/s]`.
   - Байти `32..35`: `xmag` (`float`) — магнітне поле X `[Gauss]`.
   - Байти `36..39`: `ymag` (`float`) — магнітне поле Y `[Gauss]`.
   - Байти `40..43`: `zmag` (`float`) — магнітне поле Z `[Gauss]`.
   - Байти `44..47`: `abs_pressure` (`float`) — абсолютний барометричний тиск `[hPa]`.
   - Байти `48..51`: `diff_pressure` (`float`) — диференціальний тиск трубки Піто `[hPa]`.
   - Байти `52..55`: `pressure_alt` (`float`) — барометрична висота `[m]`.
   - Байти `56..59`: `temperature` (`float`) — температура навколишнього середовища `[°C]`.
   - Байти `60..63`: `fields_updated` (`uint32_t`) — бітова маска оновлених сенсорів.

3. **`HIL_ACTUATOR_CONTROLS` (MSG_ID = 115)**:
   - Байти `0..7`: `time_usec` (`uint64_t`) — мітка часу контролера.
   - Байти `8..23`: `controls[0..3]` (`float[4]`) — нормалізовані команди керування тягою моторів та відхиленням поверхонь `[0.0 .. 1.0]` або `[-1.0 .. +1.0]`.
   - Байти `24..39`: `controls[4..7]` (`float[4]`) — додаткові канали для багатороторних октокоптерів чи сервоприводів закрилків.
   - Байти `40..55`: `controls[8..11]` (`float[4]`) — службові канали корисного навантаження (сервопідвіс камери, замки скидання).
   - Байт `56`: `mode` (`uint8_t`) — режим роботи блоку мікшування.
   - Байти `57..64`: `flags` (`uint64_t`) — бітові прапорці стану актуаторів.

4. **`ESTIMATOR_STATUS` (MSG_ID = 230)**:
   - Байти `0..7`: `time_usec` (`uint64_t`) — час оцінювача.
   - Байти `8..9`: `vel_ratio` (`float16` або нормалізований `uint16`) — тестовий коефіцієнт інновацій швидкості.
   - Байти `10..11`: `pos_horiz_ratio` (`uint16`) — тестовий коефіцієнт горизонтальної позиції.
   - Байти `12..13`: `pos_vert_ratio` (`uint16`) — тестовий коефіцієнт вертикальної позиції.
   - Байти `14..15`: `mag_ratio` (`uint16`) — тестовий коефіцієнт магнітометра.
   - Байти `16..17`: `hagl_ratio` (`uint16`) — коефіцієнт висоти над рівнем землі (далекомір).
   - Байти `18..19`: `tas_ratio` (`uint16`) — коефіцієнт істинної повітряної швидкості.
   - Байти `20..21`: `pos_horiz_accuracy` (`float`) — оцінка точності 1-sigma в метрах.
   - Байти `22..23`: `pos_vert_accuracy` (`float`) — вертикальна точність в метрах.
   - Байти `24..27`: `flags` (`uint32_t`) — бітова маска попереджень EKF (інновації перевищено, збій сузір'я, відмова компаса).

### Криптографічний підпис MAVLink v2 та робота з захищеними каналами

При тестуванні систем із увімкненим підписом повідомлень (MAVLink 2 Signing) інжектор враховує додатковий 13-байтовий блок:
- Байт `0`: `link_id` (`uint8_t`) — ідентифікатор логічного каналу зв'язку.
- Байти `1..6`: `timestamp` (`uint48_t`) — 48-бітний монотонно зростаючий лічильник часу (з дискретністю 10 мкс) для захисту від атак повторного відтворення (Replay Attacks).
- Байти `7..12`: `signature` (`uint8_t[6]`) — перші 6 байтів гешу HMAC-SHA256, розрахованого від усього кадру з додаванням 32-байтового секретного ключа (Shared Secret Key).

У сучасному стандарті C++20 для безпечного перетворення байтових послідовностей у типи з плаваючою комою використовується функція `std::bit_cast` із заголовного файлу `<bit>`. На відміну від небезпечного приведення типів через `reinterpret_cast<float*>`, яке порушує правила суворого аліасингу (Strict Aliasing Rule) та призводить до оптимізаційних помилок компілятора при прапорцях `-O2` / `-O3`, `std::bit_cast` гарантує побітове копіювання значення на етапі компіляції або генерує оптимальний машинний код без порушення стандартів мови. Для роботи з неперервними фрагментами кадру використовується `std::span<uint8_t>`, що унеможливлює вихід за межі виділеного буфера (Buffer Overflow).

Кожна аномалія проходить через чітко регламентований автомат станів:

- `ACTIVE`: конвеєр мутатора модифікує пакети у реальному часі.
- `DECAY`: плавний перехідний процес повернення до нормальних вимірювань (наприклад, плавне відновлення сузір'я GNSS після виходу з зони дії РЕБ).
- `COMPLETED`: дія аномалії завершена, запускається перевірка фінальних асертів.

### Моделювання оптичного потоку та лазерного далекоміра

При тестуванні навігації в закритих приміщеннях (GPS-Denied Navigation) або під час посадки на непідготовлені майданчики інжектор симулює деградацію повідомлення `OPTICAL_FLOW` (Message ID: 100):
- **Падіння освітленості (Illumination Drop)**: якість візуального захоплення `quality` падає з 255 до менш ніж 30, що призводить до відкидання оптичного потоку фільтром швидкості.
- **Ефект апертури та просторовий шум**: додавання випадкового шуму до кутових швидкостей оптичного зсуву `flow_x, flow_y` при польоті над дзеркальними або однорідними текстурами (асфальт, пісок, вода).

Для далекоміра (LiDAR / Rangefinder) моделюється явище дзеркального відбиття від водної гладі за законом Френеля:
```
R_fresnel(θ) = 0.5 · ( ( (n_air·cos(θ) - n_water·cos(θ_t)) / (n_air·cos(θ) + n_water·cos(θ_t)) )² + 
                       ( (n_water·cos(θ) - n_air·cos(θ_t)) / (n_water·cos(θ) + n_air·cos(θ_t)) )² )
```
При кутах падіння променя `θ > 30°` відбитий сигнал не повертається у приймальну лінзу далекоміра, і інжектор переводить вимірювання висоти в статус `Out of Range`, змушуючи EKF опиратися виключно на інтегрування вертикального акселерометра та барометр.

### Моделювання зриву комутації безколекторного двигуна (ESC Phase Desync)

Зрив синхронізації електронного регулятора швидкості (ESC Desynchronization) виникає при надмірно швидкому наростанні команди газу, коли зворотна ЕРС (BEMF) не встигає зареєструватися компаратором мікроконтролера ESC у вікні переходу через нуль (Zero-Crossing Window).

Динаміка швидкості обертання ротора `Ω` при зриві комутації моделюється диференціальним рівнянням гальмування протидіючим електромагнітним моментом фазового короткого замикання:

```
J_motor · dΩ/dt = -M_bemf_drag(Ω) - M_aero_prop(Ω) - K_desync · Ω²
```

Інжектор модулює повідомлення `ACTUATOR_OUTPUT_STATUS`: при подачі команди `PWM = 1900 мкс` фактичні оберти мотора `RPM` за 50 мс падають з 12000 об/хв до 1200 об/хв із високою високочастотною вібрацією, що транслюється в IMU як сплеск шуму на частоті комутації `f_comm = (RPM · N_poles) / 120`.

## 4. Математичні моделі генерації аномалій та шуму

Для достовірного моделювання фізичних та інформаційних порушень інжектор використовує аналітичні та стохастичні генератори збоїв.

### Генерація гаусового білого шуму (Box-Muller Transform)

Для емуляції шуму датчиків МЕМС необхідно генерувати незалежні псевдовипадкові числа з нормальним (гаусовим) розподілом `N(0, σ²)`. Перетворення Бокса-Мюллера переводить два рівномірно розподілені на відрізку `(0, 1]` випадкові числа `u_1` та `u_2` у два незалежні нормальні відліки `z_0` та `z_1`:

```
z_0 = √( -2 · ln(u_1) ) · cos(2π · u_2)
z_1 = √( -2 · ln(u_1) ) · sin(2π · u_2)
```

Результуючий вимір сенсора із шумом та зсувом нуля розраховується за формулою:

```
value_noisy = value_true + bias_drift + z_0 · σ_noise
```

Для високочастотних генераторів (понад 1000 Гц) застосовується алгоритм Зіккурат (Ziggurat Algorithm), який розбиває функцію густини ймовірності нормального розподілу на горизонтальні прямокутні шари. Це дозволяє у 98% випадків уникати повільних трансцендентних операцій `sqrt()` та `log()`, зводячи генерацію випадкового числа до простої операції зсуву бітів та порівняння з таблицею констант.

### Моделювання випадкового блукання зсуву нуля (Wiener Process)

Зсув нуля (Bias Instability) реальних гіроскопів та акселерометрів є нестаціонарним процесом. У симуляторі він моделюється як інтеграл від білого шуму (вінерівський процес випадкового блукання):

```
b_{k+1} = b_k + w_b · √dt,    w_b ~ N(0, σ_bias_walk²)
```

Це дозволяє точно перевіряти здатність фільтра Калмана EKF2 оцінювати та компенсувати зміщення дельти кута та швидкості під час тривалого польоту.

```
             Зсув нуля b(t)
                ▲
                │                  /---\
                │    /\           /     \       /---\
  Випадкове     │   /  \  /\     /       \     /     \
  блукання      │  /    \/  \---/         \---/       \
  (Wiener)      │ /
                └─────────────────────────────────────────► Час t
```

### Геодезичний перерахунок координат при GNSS Spoofing

При когерентному спуфінгу інжектор генерує вектор фальшивої швидкості відносно землі `v_spoof = [v_north, v_east, v_down]ᵀ`. Для оновлення широти `φ` та довготи `λ` на еліпсоїді WGS-84 використовуються радіуси кривини меридіана `M(φ)` та першого вертикалу `N(φ)`:

```
M(φ) = a · (1 - e²) / (1 - e² · sin²(φ))^(3/2)
N(φ) = a / √(1 - e² · sin²(φ))

де:
a = 6378137.0 м           [велика піввісь еліпсоїда WGS-84]
e² = 0.00669437999014     [квадрат першого ексцентриситету]
```

Приріст географічних координат за інтервал часу `dt` обчислюється як:

```
Δφ = (v_north · dt) / (M(φ) + h)
Δλ = (v_east · dt) / ((N(φ) + h) · cos(φ))
Δh = -v_down · dt
```

Отримані значення перетворюються у цілочисельний формат MAVLink (`int32_t` градуси `· 1e7`) і записуються в тіло кадру `GPS_RAW_INT`.

### Моделювання відмови датчика швидкості (Pitot Tube)

Порушення роботи трубки Піто моделюється через розрахунок динамічного тиску `q`. При частковому засміченні вхідного отвору тиск описується апертурним коефіцієнтом прохідності `k_clog ∈ [0.0, 1.0]`:

```
q_measured = k_clog · 0.5 · ρ · V_true² + Δp_leak(t)
```

де `Δp_leak(t) = Δp_0 · exp(-t / τ_leak)` моделює повільний витік тиску через мікротріщину в силіконовій трубці з постійною часу `τ_leak ≈ 3–8` с.

### Моделювання магнітометричних та електромагнітних збурень

Магнітометричний мутатор застосовує тривимірне афінне перетворення для симуляції впливу металевих мас та струмових петель живлення силових двигунів:

```
B_measured = (I + S_soft) · R_misalign · B_earth + B_hard + K_esc · I_battery
```

де `S_soft` — матриця асиметрії м'якого заліза розміру `3 × 3`, `B_hard` — тривимірний вектор постійного зсуву твердого заліза, `K_esc` — коефіцієнт наведення магнітного поля від споживання струму силовою установкою, виміряного в амперах.

При прольоті над залізобетонними спорудами інжектор генерує просторовий градієнт магнітного поля у вигляді локального дипольного збурення, напруженість якого спадає обернено пропорційно кубу відстані до віртуальної магнітної маси:

```
B_dipole(r) = (μ_0 / (4π)) · ( (3 · r · (m_dipole · r)) / |r|⁵ - m_dipole / |r|³ )
```

Математична процедура калібрування магнітометра полягає у розв'язанні задачі апроксимації еліпсоїда методом найменших квадратів. Якщо вектор сирих вимірювань `z_raw = [x, y, z]ᵀ` належить деформованому еліпсоїду:

```
(z_raw - b_hard)ᵀ · M_softᵀ · M_soft · (z_raw - b_hard) = B_earth_norm²
```

Інжектор обчислює сингулярний розклад (Singular Value Decomposition, SVD) матриці коваріації вимірювань `U · Σ · Vᵀ = cov(z_raw)` і генерує ортогональне перетворення, що штучно деформує сферичну поверхню магнітного поля у витягнутий еліпсоїд із співвідношенням осей `1 : 1.8 : 2.4`. Це змушує фільтр оцінки орієнтації фіксувати розбіжність магнітного курсу зі швидкістю понад 15 градусів за секунду під час виконання розворотів.

### Статистична теорія перевірки гіпотез у брамі інновацій (NIS Hypothesis Testing)

Тест узгодженості вимірювань розширеного фільтра Калмана базується на статистичному критерії узгодженості Пірсона. Якщо модель динаміки та шуми процесу ідентифіковані абсолютно точно, нормалізований квадрат інновацій `NIS = yᵀ · S⁻¹ · y` строго підпорядковується центральному розподілу хі-квадрат `χ²(k)` із `k` ступенями вільності.

Ймовірність хибної тривоги (Type I Error, False Alarm Rate `α`) — коли коректний супутниковий вимір помилково відкидається брамою через рідкісний статистичний викид шуму — визначається інтегралом хвоста розподілу:

```
α = P( NIS > NIS_thresh | H_0 ) = 1 - F_χ²(k)(NIS_thresh) = ∫_{NIS_thresh}^{∞} ( 1 / (2^(k/2) · Γ(k/2)) ) · x^(k/2 - 1) · e^(-x/2) dx
```

Для 3D вимірювання позиції (`k = 3`) при виборі порогу `NIS_thresh = 11.34` теоретична ймовірність хибного відкидання становить строго `α = 0.01` (1%).

Ймовірність пропуску аномалії (Type II Error, Missed Detection Rate `β`) при інжекції когерентного спуфінгу зі зміщенням вектора позиції на `δ` підпорядковується нецентральному розподілу хі-квадрат `χ²(k, λ)` із параметром нецентральності `λ = δᵀ · S⁻¹ · δ`:

```
β = P( NIS ≤ NIS_thresh | H_1 ) = F_χ²(k, λ)(NIS_thresh)
```

Assert Engine розраховує фактичну статистику відкидань за 1000 кроків симуляції та підтверджує, що частота помилкових спрацьовувань брами при відсутності збоїв не перевищує 1.2%, а час фіксації спуфінгу при `λ > 25.0` не перевищує 3 такти фільтра (75 мс).

### Моделювання багатопроменевого поширення сигналів GNSS (Multipath)

У міських каньйонах або поблизу промислових споруд прямий радіосигнал супутника затінюється, а антена приймача фіксує відбиті від фасадів промені. Затримка відбитого променя `τ_multipath` створює додаткову фазову та кодову похибку псевдовідстані:

```
Δρ_multipath = c · τ_multipath = 2 · h_obstacle · sin(θ_elevation)
```

Результуючий прийнятий радіочастотний сигнал є суперпозицією прямої хвилі з амплітудою `A_0` та відбитих хвиль із амплітудами `α_i · A_0` та зсувами фаз `Δφ_i`:

```
s_rx(t) = A_0 · c(t - τ_0) · cos(ω_0 · t + φ_0) + ∑ α_i · A_0 · c(t - τ_0 - τ_i) · cos(ω_0 · t + φ_0 + Δφ_i)
```

Інжектор обчислює геометричну деградацію співвідношення сигнал/шум несучої `C/N_0`:

```
Δ(C/N_0) = 10 · log10( 1 + α² + 2 · α · cos(Δφ) )
```

Коли дрон знижується поміж віртуальних будівель, інжектор динамічно підмішує багатопроменеву похибку величиною 5–25 метрів до окремих каналів супутників із низькими кутами піднесення (`θ < 25°`), викликаючи раптову нелінійну розбіжність фільтра швидкості та позиції.

### Електрична модель просідання напруги батареї (Cell Voltage Sag)

Для тестування батарейного Failsafe інжектор модулює вимірювання напруги та струму в повідомленні `BATTERY_STATUS` (Message ID: 147). Напруга на клемах акумулятора моделюється за модифікованою формулою Шеперда:

```
V_batt(t) = E_0 - R_int · I(t) - K_polarization · ( Q_max / (Q_max - Q_used(t)) ) · I(t) + A_exp · exp(-B_exp · Q_used(t))
```

де `E_0` — напруга холостого ходу повністю зарядженого елемента, `R_int` — внутрішній омічний опір, `K_polarization` — коефіцієнт поляризаційного опору, `Q_max` — номінальна ємність у ампер-годинах, а `Q_used` — інтеграл спожитого струму.

При різкому збільшенні тяги (наприклад, під час екстреного гальмування) струм `I(t)` стрибає від 15 А до 80 А, породжуючи миттєве просідання напруги `ΔV = I · R_int`. Інжектор перевіряє, чи не призводить короткочасне просідання напруги тривалістю 200 мс до помилкового переходу в критичний Battery Failsafe, якщо середня напруга батареї залишається у безпечних межах.

### Моделювання поля вітру та атмосферної турбулентності (Dryden Wind Model)

Для перевірки стійкості контурів оцінки вітру та стабілізації швидкості інжектор симулює нелінійні просторові пориви вітру за моделлю Драйдена (Dryden Wind Turbulence Model). Вектор швидкості вітру у земній системі координат представляється сумою постійного середнього вітру `V_wind_mean` та стохастичної турбулентної складової `u_g, v_g, w_g`:

```
V_wind(t) = V_wind_mean + [ u_g(t), v_g(t), w_g(t) ]ᵀ
```

Дискретна реалізація формуючих фільтрів Драйдена виконується через перетворення Тастіна (білінійне z-перетворення) неперервних передатних функцій. Для поздовжньої компоненти поривів фільтр описується різницевим рівнянням другого порядку:

```
u_g[k] = a_1 · u_g[k-1] + a_2 · u_g[k-2] + b_0 · w_white[k] + b_1 · w_white[k-1]
```

де коефіцієнти розраховуються на основі середньоквадратичного відхилення швидкості вітру `σ_u`, просторового масштабу турбулентності `L_u` (за стандартом MIL-F-8785C `L_u = 1750` футів на великих висотах) та шляхової швидкості апарата `V_inf`.

Інжектор підмішує пориви вітру як у фізичні рівняння динаміки симулятора (через розрахунок відносної повітряної швидкості обтікання лопатей та крила `V_rel = V_body - R(q) · V_wind`), так і в сенсорні повідомлення трубки Піто `diff_pressure`, створюючи динамічні умови для стрес-тесту оцінювача вітру в EKF.

### Моделювання відмови шини CAN (DroneCAN / UAVCAN)

Сучасні цифрові вузли авіоніки (інтелектуальні ESC, цифрові сервоприводи, датчики RTK GNSS) об'єднуються шиною CAN. Інжектор симулює відмови канального рівня протоколу DroneCAN:
- **Вставка бітових помилок (Bit-Stuffing Error)**: спотворення контрольного біта в кадровому полі CRC кадру CAN, що викликає відкидання повідомлення апаратним контролером bxCAN мікроконтролера STM32.
- **Стан Bus-Off**: примусова генерація 255 помилкових фреймів поспіль, що переводить трансивер CAN польотного контролера в ізольований режим блокування (Bus-Off State).
- **Підміна ідентифікаторів вузлів (Node ID Collision)**: надсилання фальшивих повідомлень із тим самим `Node_ID`, що провокує арбітражний конфлікт на шині та перевіряє здатність автопілота виявляти колізії адрес.

## 5. Двигун верифікації та автоматизований валідатор реакцій (Assert Engine)

Інжектор не лише вносить несправності, але й виступає арбітром коректності поведінки автопілота. Для цього зворотний потік повідомлень від автопілота (`HEARTBEAT`, `ATTITUDE`, `LOCAL_POSITION_NED`, `VEHICLE_STATUS`) аналізується модулем перевірки тверджень (Assert Engine).

### Формальна верифікація на основі лінійної темпоральної логіки (LTL)

Вимоги безпеки до поведінки автопілота записуються у формі предикатів лінійної темпоральної логіки (Linear Temporal Logic, LTL):

1. **Інваріант реакції на критичний розряд батареї**:
   ```
   □ ( (BatteryLevel < 0.05) → ◇_[0, 1.5s] (NavState == EMERGENCY_LAND) )
   ```
   *«Завжди (□), якщо рівень заряду батареї падає нижче 5%, врешті-решт протягом не більше ніж 1.5 секунди (◇) стан навігації повинен перейти в аварійну посадку».*

2. **Інваріант обриву радіолінка керування RC**:
   ```
   □ ( (RCLinkLost) → ( □_[0, 2.0s] (NavState == HOLD_LOITER) ∧ ◇_[2.0s, 3.5s] (NavState == RETURN_TO_LAUNCH) ) )
   ```
   *«При втраті зв'язку дрон зобов'язаний утримувати поточну точку протягом 2 секунд дебаунсу, після чого перейти в режим повернення додому».*

3. **Інваріант збереження стійкості при відмові одного мотора квадрокоптера**:
   ```
   □ ( (MotorFailed) → □ ( (AttitudeError < 35°) ∨ (FlatSpinActive ∧ Vz_descent < 4.5) ) )
   ```
   *«При відмові двигуна апарат або зберігає крен менше 35 градусів, або активує керований плоский спуск зі швидкістю не більше 4.5 м/с».*

### Контроль 3D просторових коридорів (Spatial Boundary Assertion)

Модуль асертів у реальному часі відстежує відхилення дрона від планової траєкторії місії. Нехай плановий сегмент маршруту задається відрізком між точками `A` та `B`. Відстань бічного відхилення (Cross-Track Error `e_ct`) та висотного відхилення (`e_v`) розраховуються за формулами векторної геометрії:

```
e_ct = |(p_current - p_A) × (p_B - p_A)| / |p_B - p_A|
e_v  = |(p_current - p_A)_z - ( ( (p_current - p_A) · (p_B - p_A) ) / |p_B - p_A|² ) · (p_B - p_A)_z|
```

Якщо під час перехідного процесу Failsafe відхилення `e_ct` перевищує допустимий радіус віртуального циліндра безпеки `R_corridor = 15.0` метрів, валідатор фіксує порушення умов польоту `ASSERT_FAILED: Spatial corridor breached`.

Модуль асертів верифікує наступні метрики безпеки:

1. **Час спрацьовування Failsafe (Time-to-Failsafe)**:
   ```
   Δt_reaction = t_state_change - t_fault_injected
   ASSERT(Δt_reaction <= MAX_ALLOWED_LATENCY_S)
   ```
2. **Максимальне кутове відхилення (Attitude Excursion)**: перевіряє, що під час перехідного процесу (наприклад, при раптовій зупинці двигуна) кути крену `Roll` та тангажу `Pitch` не перевищують критичний поріг перекидання `70.0°`.
3. **Брама інновацій EKF (Innovation Gate Verification)**: перевіряє, що при інжекції похибки GNSS фільтр зафіксував зростання нормалізованого квадрата інновацій `NIS > 11.34` і перестав використовувати скомпрометовані координати для корекції стану.
4. **Кінетична енергія приземлення (Touchdown Kinetic Energy)**:
   ```
   E_k = 0.5 · m · (v_x² + v_y² + v_z²)
   ASSERT(v_z <= 2.2 м/с)
   ```

```
           [Інжекція відмови] (t = 15.0 c)
                   │

                   │

### Кодування польотних режимів у повідомленні HEARTBEAT

Повідомлення `HEARTBEAT` (Message ID: 0) транслює стан готовності системи кожні 1000 мс. Інжектор та Assert Engine аналізують два ключових поля для фіксації переходу у Failsafe:
- `base_mode`: бітова маска стандартних станів MAVLink:
  - Біт 7 (`128`, `MAV_MODE_FLAG_SAFETY_ARMED`): апарат озброєний (мотори обертаються).
  - Біт 3 (`8`, `MAV_MODE_FLAG_GUIDED_ENABLED`): керування за автономною програмою.
  - Біт 0 (`1`, `MAV_MODE_FLAG_CUSTOM_MODE_ENABLED`): активний специфічний режим прошивки.
- `custom_mode`: 32-бітне ціле число, формат якого різниться між польотними стеками:
  - **У стеку PX4 Autopilot**: `custom_mode` упаковується як складний бітовий запис `[Main Mode : 8 біт] [Sub Mode : 8 біт] [Flags : 16 біт]`. Режим RTL кодується як `Main Mode = 5` (Auto), `Sub Mode = 5` (RTL); режим Land — як `Main Mode = 5`, `Sub Mode = 6` (Land).
  - **У стеку ArduPilot (Copter)**: `custom_mode` є прямим переліком enum `Copter::Mode::Number`: `0 = Stabilize`, `3 = Auto`, `5 = Loiter`, `6 = RTL`, `9 = Land`, `11 = Drift`, `21 = Smart_RTL`.
- `system_status`: статус здоров'я автопілота: `3 = MAV_STATE_STANDBY`, `4 = MAV_STATE_ACTIVE`, `5 = MAV_STATE_CRITICAL` (Failsafe активний), `6 = MAV_STATE_EMERGENCY` (негайне вимкнення моторів).

## 7. Інтеграція в автоматизовані CI/CD конвеєри та аналіз логів

Фреймворк інжектора підключається до автоматизованого конвеєра тестування безпілотних комплексів у контейнерах Docker. Під час виконання кожного сценарію інжектор реєструє події у синхронізований JSON-файл логів та звіряє часові мітки спрацьовування захисних автоматів автопілота.

### Методологія регресійного тестування Монте-Карло

Для гарантії надійності прошивки одиночного прогону тесту недостатньо. Застосовується метод Монте-Карло з рандомізацією початкових умов:
1. **Параметричний свип вітру**: швидкість фонового вітру варіюється від 0 до 18 м/с із випадковим напрямком `[0..360°]`.
2. **Стохастичний шум сенсорів**: генератор псевдовипадкових чисел ініціалізується різними значеннями seed (`N = 100` прогонів).
3. **Випадковий час інжекції**: збій мотора активується у довільний момент виконання віражу, зльоту або гальмування.

Статистичний критерій успішності регресії вимагає, щоб коефіцієнт успішних посадок (Success Rate) становив `≥ 99.0%` при довірчій ймовірності 95%.

Повний цикл стрес-тестування в CI виконується наступним чином:
1. Запуск headless-симулятора Gazebo та бінарника SITL автопілота.
2. Старт проксі-інжектора з обраним конфігураційним сценарієм `scenario.json`.
3. Моніторинг статусу виконання місії через сокет телеметрії.
4. Автоматична зупинка процесів після завершення тесту та експорт звітів у форматі JUnit XML для візуалізації на дашборді CI/CD.

### Вирівнювання структур та запобігання невизначеній поведінці (Structure Packing)

При низькорівневій серіалізації та десеріалізації повідомлень MAVLink v2 у пам'яті комп'ютера виникає небезпека непередбачуваного зміщення полів через компіляторне вирівнювання (Structure Padding). Стандарт мови C за замовчуванням вирівнює 32-бітні цілі та числа з плаваючою комою за адресами, кратними 4 байтам, а 64-бітні цілі — за адресами, кратними 8 байтам.

Оскільки корисне навантаження кадру MAVLink v2 починається з 10-го байта (не кратно 4 чи 8), пряме приведення вказівника на непарну адресу `(float*)(payload + offset)` на архітектурах ARM (наприклад, Cortex-M4/M7 або Cortex-A53) провокує апаратне виключення вирівнювання (Alignment Fault / HardFault Exception) або виконує неатомарні повільні подвійні цикли читання з шини пам'яті.

Щоб гарантувати 100% сумісність та максимальну швидкодію без невизначеної поведінки (Undefined Behavior), інжектор використовує виключно безпечну функцію `memcpy()` для копіювання значень або атрибут пакування структур `__attribute__((packed))` у деклараціях структур протоколу. Сучасні оптимізуючі компілятори GCC та Clang розгортають виклики `memcpy()` фіксованого розміру (4 або 8 байт) в одну неблокуючу інструкцію асемблера `ldr` / `str` або `vldr` / `vstr`, забезпечуючи нульові накладні витрати часу виконання.

Систематичне виконання таких перевірок на етапі неперервної інтеграції повністю усуває людський фактор і гарантує, що жодна деградація алгоритмів оцінки чи безпеки не потрапить на реальний борт літального апарата. Комплексна автоматизація стрес-тестів скорочує цикл валідації критичних оновлень прошивки з тижнів польових випробувань до лічених хвилин у віртуальному хмарному кластері.
