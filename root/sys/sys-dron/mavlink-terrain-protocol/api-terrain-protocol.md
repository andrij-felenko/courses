# 📋 Довідник повідомлень та структур MAVLink Terrain Protocol

Протокол рельєфу MAVLink (*MAVLink Terrain Protocol*) стандартизований у загальносистемному діалекті `common.xml` і визначає програмний контракт для потокового обміну висотними сітками між польотним контролером (FCU, *Flight Control Unit*) та наземною станцією керування (GCS, *Ground Control Station*) або бортовим комп'ютером-компаньйоном (*Companion Computer*).

У безпілотній авіації польотний контролер функціонує в умовах суворо обмежених апаратних ресурсів: оперативна пам'ять SRAM вимірюється сотнями кілобайтів, доступ до постійної флеш-пам'яті має непередбачувані затримки, а швидкість радіотелеметрійного каналу рідко перевищує 57 600 біт/с. Протокол рельєфу вирішує ці обмеження за допомогою дискретної тяглової архітектури, у якій автопілот запитує лише компактні локальні блоки 4×4 вузли навколо поточної та прогнозованої позицій апарата.

## 1. Загальний огляд сімейства повідомлень рельєфу

Сімейство повідомлень рельєфу складається з чотирьох повідомлень, кожне з яких має унікальний числовий ідентифікатор (Message ID) та фіксовану бінарну розкладку:

```
Склад сімейства повідомлень MAVLink Terrain Protocol:
┌────────┬─────────────────┬───────────┬──────────────┬────────────────────────────────────────────────────────┐
│ ID     │ Назва           │ Напрямок  │ Довжина (B)  │ Призначення у протоколі                                │
├────────┼─────────────────┼───────────┼──────────────┼────────────────────────────────────────────────────────┤
│ #133   │ TERRAIN_REQUEST │ FCU → GCS │ 18           │ Запит списку відсутніх блоків у кластері 8×8           │
│ #134   │ TERRAIN_DATA    │ GCS → FCU │ 43           │ Передача матриці 4×4 висот окремого блоку              │
│ #135   │ TERRAIN_CHECK   │ GCS → FCU │ 8            │ Запит перевірки відомої автопілоту висоти в точці      │
│ #136   │ TERRAIN_REPORT  │ FCU → GCS │ 22           │ Періодичний звіт про висоту рельєфу, кліренс та кеш    │
└────────┴─────────────────┴───────────┴──────────────┴────────────────────────────────────────────────────────┘
```

Ці повідомлення інкапсулюються у стандартні кадри MAVLink v1 або MAVLink v2. Для контролю цілісності кожного типу повідомлення генератор коду MAVLink додає спеціальний байт CRC-EXTRA до насіння контрольної суми CRC-16-CCITT, що гарантує несумісність між несумісними версіями структур даних.

У протоколі MAVLink v2 кадри мають додаткові можливості порівняно з першою версією протоколу:
- Довжина службового заголовка становить 10 байтів проти 6 байтів у MAVLink v1;
- Підтримується 24-бітний простір ідентифікаторів повідомлень (Message ID), що дозволяє адресацію понад 16 мільйонів типів пакетів;
- Реалізовано алгоритм утискання нульових байтів (*Zero-Byte Suppression*): якщо хвостові байти корисного навантаження заповнені нулями, вони не передаються в радіоефір, а відновлюються приймачем автоматично на основі фіксованої довжини структури;
- Додано необов'язковий 13-байтовий блок криптографічного підпису (*Message Signing*), який захищає команди керування та дані рельєфу від підміни зловмисниками.

### Маршрутизація та адресація в мережі MAVLink

Усі повідомлення протоколу рельєфу підтримують стандартну схему маршрутизації MAVLink:
- **Широкомовний запит `TERRAIN_REQUEST`:** Автопілот відправляє запит у режимі мовлення (`broadcast`) або адресує його безпосередньо наземній станції (ідентифікатор системи `target_system = 255`, компонент `target_component = 0` або `MAV_COMP_ID_MISSIONPLANNER`). Якщо на борту присутній комп'ютер-компаньйон (наприклад, Raspberry Pi з компонентом `MAV_COMP_ID_ONBOARD_COMPUTER`), він може перехопити запит і відповісти локально з SSD-накопичувача, не займаючи радіоефір.
- **Цільова відповідь `TERRAIN_DATA`:** Наземна станція адресує пакети висот конкретному літальному апарату (наприклад, `target_system = 1`, `target_component = MAV_COMP_ID_AUTOPILOT1`), запобігаючи перевантаженню інших дронів у групових місіях (Swarm operations).

## 2. Специфікація повідомлення TERRAIN_REQUEST (#133)

Повідомлення `TERRAIN_REQUEST` генерується фоновим потоком підсистеми рельєфу польотного контролера, коли під час аналізу навігаційного маршруту або вектора випередження (lookahead) виявлено відсутність даних рельєфу в оперативному кеші RAM та на карті MicroSD.

- **Ідентифікатор повідомлення:** `133` (`0x85`)
- **Довжина корисного навантаження:** 18 байтів
- **Константа цілісності CRC-EXTRA:** `6`

```
Розкладка полів повідомлення TERRAIN_REQUEST (18 байтів):
┌────────┬──────────────┬──────────────┬───────────────┬────────────────────────────────────────────────────────┐
│ Зсув   │ Тип даних    │ Поле         │ Одиниці       │ Призначення та діапазон                                │
├────────┼──────────────┼──────────────┼───────────────┼────────────────────────────────────────────────────────┤
│ 0..7   │ uint64_t     │ mask         │ бітове поле   │ 64-бітна маска необхідних блоків у кластері 8×8        │
│ 8..11  │ int32_t      │ lat          │ град · 10⁷    │ Географічна широта центру кластера [-90° .. +90°]       │
│ 12..15 │ int32_t      │ lon          │ град · 10⁷    │ Географічна довгота центру кластера [-180° .. +180°]   │
│ 16..17 │ uint16_t     │ grid_spacing │ метри         │ Горизонтальний крок між вузлами сітки (типово 100 м)   │
└────────┴──────────────┴──────────────┴───────────────┴────────────────────────────────────────────────────────┘
```

### Семантика полів повідомлення TERRAIN_REQUEST

1. **`mask` (`uint64_t`, 8 байтів):** 64-бітне бітове поле, у якому кожен біт відповідає одному блоку в сітці 8×8 блоків навколо центру кластера.
   - Біт з індексом `k = row · 8 + col` (де `row, col ∈ [0..7]`) встановлюється в `1`, якщо блок відсутній у пам'яті автопілота і вимагає завантаження.
   - Біт скидається в `0`, якщо блок уже завантажений у RAM-кеш або успішно зчитаний з карти MicroSD.
   - Нульовий біт (`bit 0`) відповідає південно-західному (SW) блоку кластера, а 63-й біт (`bit 63`) — північно-східному (NE) блоку.
2. **`lat` (`int32_t`, 4 байти):** Географічна широта центральної точки кластера, виражена у градусах WGS84, помножених на коефіцієнт масштабування `10⁷` (дискретність приблизно 1.1 сантиметра).
3. **`lon` (`int32_t`, 4 байти):** Географічна довгота центральної точки кластера у системі WGS84 з масштабом `10⁷`.
4. **`grid_spacing` (`uint16_t`, 2 байти):** Горизонтальна відстань між сусідніми висотними вузлами у метрах. За замовчуванням становить 100 метрів. Це значення визначає геометричний розмір одного блоку (300×300 м) та всього кластера (2400×2400 м).

### Порядок полів та вирівнювання у бінарному кадрі

У стандарті MAVLink поля структури всередині бінарного кадру впорядковуються за спаданням розміру типу даних для запобігання нерегулярному вирівнюванню (unaligned memory access) на процесорах архітектури ARM Cortex-M:
- Спочатку розміщуються 8-байтові поля (`uint64_t mask`, зсув 0);
- Потім 4-байтові поля (`int32_t lat`, зсув 8; `int32_t lon`, зсув 12);
- Наприкінці 2-байтові поля (`uint16_t grid_spacing`, зсув 16).

Завдяки цьому структура займає рівно 18 байтів без жодного байта внутрішнього заповнення (padding), що мінімізує обсяг радіотрафіку в ефірі.

## 3. Специфікація повідомлення TERRAIN_DATA (#134)

Повідомлення `TERRAIN_DATA` надсилається наземною станцією керування (GCS) або бортовим комп'ютером у відповідь на отриманий запит `TERRAIN_REQUEST`. Кожен пакет містить завершену матрицю висот 4×4 вузли для одного конкретного блоку.

- **Ідентифікатор повідомлення:** `134` (`0x86`)
- **Довжина корисного навантаження:** 43 байти
- **Константа цілісності CRC-EXTRA:** `237`

```
Розкладка полів повідомлення TERRAIN_DATA (43 байти):
┌────────┬──────────────┬──────────────┬───────────────┬────────────────────────────────────────────────────────┐
│ Зсув   │ Тип даних    │ Поле         │ Одиниці       │ Призначення та діапазон                                │
├────────┼──────────────┼──────────────┼───────────────┼────────────────────────────────────────────────────────┤
│ 0..3   │ int32_t      │ lat          │ град · 10⁷    │ Широта південно-західного (SW) кута блоку              │
│ 4..7   │ int32_t      │ lon          │ град · 10⁷    │ Довгота південно-західного (SW) кута блоку             │
│ 8..9   │ uint16_t     │ grid_spacing │ метри         │ Горизонтальний крок між вузлами (має збігатися із запитом)│
│ 10     │ uint8_t      │ gridbit      │ індекс (0..63)│ Позиція блоку в 64-бітній масці кластера (row·8 + col) │
│ 11..42 │ int16_t[16]  │ data         │ метри (AMSL)  │ Матриця 4×4 висот рельєфу [-32768 .. +32767 м]         │
└────────┴──────────────┴──────────────┴───────────────┴────────────────────────────────────────────────────────┘
```

### Семантика полів повідомлення TERRAIN_DATA

1. **`lat` та `lon` (`int32_t`, по 4 байти):** Точні географічні координати південно-західного (SW) кутового вузла цього конкретного блоку 4×4 (відповідає точці `data[0]`).
2. **`grid_spacing` (`uint16_t`, 2 байти):** Крок між вузлами у метрах. Автопілот порівнює це поле зі своєю внутрішньою конфігурацією (`TERRAIN_SPACING`). Якщо крок не збігається, блок відкидається для запобігання геометричному спотворенню карти.
3. **`gridbit` (`uint8_t`, 1 байт):** Номер біта (від 0 до 63) у масці `TERRAIN_REQUEST`, відповіддю на який є цей пакет. Автопілот використовує це поле для швидкого скидання біта очікування у своїй черзі запитів.
4. **`data` (`int16_t[16]`, 32 байти):** Одновимірний масив із 16 цілих чисел зі знаком, що представляє матрицю 4×4 вузлів. Кожне значення задає абсолютну висоту рельєфу над рівнем моря (AMSL) у цілих метрах.

### Упорядкування елементів масиву `data[16]`

Вузли матриці передаються у пам'яті за рядками від півдня до півночі, а всередині кожного рядка — із заходу на схід:

```
Розкладка індексів масиву data[16] на фізичній сітці:
Північ (North) ↑
   Рядок 3 (lat_sw + 3·Δlat): data[12]   data[13]   data[14]   data[15] (NE кут)
   Рядок 2 (lat_sw + 2·Δlat): data[8]    data[9]    data[10]   data[11]
   Рядок 1 (lat_sw + 1·Δlat): data[4]    data[5]    data[6]    data[7]
   Рядок 0 (lat_sw + 0·Δlat): data[0]    data[1]    data[2]    data[3]  (SE кут)
                              (SW кут)
                              ----------------------------------------→ Схід (East)
                              Стовпець 0 Стовпець 1 Стовпець 2 Стовпець 3
                              (lon_sw)  (+1·Δlon)  (+2·Δlon)  (+3·Δlon)
```

Спеціальні значення висоти в масиві `data`:
- **`-32768` (`0x8000`):** Маркер відсутності топографічних даних (*void/no-data*). Якщо автопілот виявляє це значення в одній із чотирьох вершин активної комірки, інтерполяція вважається недійсною, і вмикається аварійний режим Terrain Failsafe.
- **`0` метрів:** Рівень геоїда EGM96 (середній рівень моря). Для відкритих морських та океанічних просторів бази SRTM повертають 0 м.

### Порядок байтів (Endianness) та перетворення форматів

У сирих файлах топографії SRTM (`.hgt`) висотні матриці зберігаються у порядку байтів **Big-Endian** (старший байт іде першим), що відповідає стандарту космічного апарату Shuttle Radar. 

Протокол MAVLink для всіх числових полів (`int16_t`, `int32_t`, `uint64_t`) використовує порядок байтів **Little-Endian** (молодший байт іде першим), оскільки процесори ARM Cortex-M та x86-64 є нативно Little-Endian архітектурами. 

Коли наземна станція керування (GCS) читає файл SRTM:
1. Вона зчитує 16-бітні слова у форматі Big-Endian;
2. Виконує перестановку байтів (`bswap16` / `htons`);
3. Упаковує значення у масив `data[16]` повідомлення `TERRAIN_DATA` у форматі Little-Endian.

Польотний контролер копіює масив `data[16]` безпосередньо у свою пам'ять за допомогою швидкої операції `memcpy()`, не витрачаючи такти процесора на побайтову конвертацію.

### Механізм темпування пачок (Burst Pacing)

Коли наземна станція отримує запит `TERRAIN_REQUEST` із 64 піднятими бітами, вона не повинна надсилати всі 64 пакети `TERRAIN_DATA` безперервним суцільним потоком. Швидкість UART-інтерфейсу радіомодему польотного контролера зазвичай становить 57 600 біт/с, а розмір апаратного буфера FIFO приймача UART — від 16 до 64 байтів.

Якщо GCS вистрілить 64 пакети сумарним обсягом понад 3.5 КБ без пауз, апаратні черги польотного контролера переповняться, що призведе до втрати пакетів та повторних циклів `TERRAIN_REQUEST`.

Стандарт рекомендує застосовувати алгоритм **темпування відправки (Pacing)**: GCS транслює блоки пачками по 2–4 пакети з міжпакетною затримкою в **10–25 мілісекунд**. Це дає процесору автопілота час обробити переривання UART, скопіювати байти в RAM та за потреби зберегти сектор на MicroSD без блокування навігаційного контуру EKF.

## 4. Специфікація повідомлення TERRAIN_CHECK (#135)

Повідомлення `TERRAIN_CHECK` використовується наземною станцією для діагностики або верифікації висот перед стартом місії. Наземна станція опитує автопілот про висоту рельєфу у довільних координатах маршруту.

- **Ідентифікатор повідомлення:** `135` (`0x87`)
- **Довжина корисного навантаження:** 8 байтів
- **Константа цілісності CRC-EXTRA:** `203`

```
Розкладка полів повідомлення TERRAIN_CHECK (8 байтів):
┌────────┬──────────────┬──────────────┬───────────────┬────────────────────────────────────────────────────────┐
│ Зсув   │ Тип даних    │ Поле         │ Одиниці       │ Призначення та діапазон                                │
├────────┼──────────────┼──────────────┼───────────────┼────────────────────────────────────────────────────────┤
│ 0..3   │ int32_t      │ lat          │ град · 10⁷    │ Географічна широта точки запиту [-90° .. +90°]         │
│ 4..7   │ int32_t      │ lon          │ град · 10⁷    │ Географічна довгота точки запиту [-180° .. +180°]     │
└────────┴──────────────┴──────────────┴───────────────┴────────────────────────────────────────────────────────┘
```

Отримавши `TERRAIN_CHECK`, автопілот виконує пошук відповідного блоку у своєму кеші, обчислює білінійну інтерполяцію висоти та негайно надсилає відповідь у вигляді повідомлення `TERRAIN_REPORT` із цими ж координатами.

## 5. Специфікація повідомлення TERRAIN_REPORT (#136)

Повідомлення `TERRAIN_REPORT` транслюється автопілотом у режимі регулярної телеметрії (типово з частотою 1 Гц) або генерується як пряма відповідь на запит `TERRAIN_CHECK`.

- **Ідентифікатор повідомлення:** `136` (`0x88`)
- **Довжина корисного навантаження:** 22 байти
- **Константа цілісності CRC-EXTRA:** `1`

```
Розкладка полів повідомлення TERRAIN_REPORT (22 байти):
┌────────┬──────────────┬──────────────┬───────────────┬────────────────────────────────────────────────────────┐
│ Зсув   │ Тип даних    │ Поле         │ Одиниці       │ Призначення та діапазон                                │
├────────┼──────────────┼──────────────┼───────────────┼────────────────────────────────────────────────────────┤
│ 0..3   │ int32_t      │ lat          │ град · 10⁷    │ Поточна широта безпілотника або точки перевірки        │
│ 4..7   │ int32_t      │ lon          │ град · 10⁷    │ Поточна довгота безпілотника або точки перевірки       │
│ 8..11  │ float        │ terrain_height│ метри (AMSL) │ Інтерпольована абсолютна висота поверхні землі         │
│ 12..15 │ float        │ current_height│ метри (AGL)  │ Істинний кліренс безпілотника над землею (H_amsl - H_terr)│
│ 16..17 │ uint16_t     │ spacing      │ метри         │ Поточний крок сітки дискретизації                      │
│ 18..19 │ uint16_t     │ pending      │ кількість     │ Кількість блоків, що очікують відповіді від GCS        │
│ 20..21 │ uint16_t     │ loaded       │ кількість     │ Загальна кількість валідних блоків у кеші автопілота   │
└────────┴──────────────┴──────────────┴───────────────┴────────────────────────────────────────────────────────┘
```

### Діагностичне значення полів TERRAIN_REPORT

- **`terrain_height` (`float`, 4 байти):** Обчислена методом білінійної інтерполяції абсолютна висота рельєфу над рівнем моря (AMSL) у метрах. Якщо дані відсутні, поле містить `NaN` або `0.0`.
- **`current_height` (`float`, 4 байти):** Поточний розрахунковий кліренс апарата над підстильною поверхнею (AGL): `current_height = H_vehicle_amsl - terrain_height`. Наземна станція відображає цю величину на панелі приладів для індикації небезпечного зближення із землею.
- **`pending` (`uint16_t`, 2 байти):** Кількість блоків у черзі запитів, для яких автопілот очікує отримання пакетів `TERRAIN_DATA`. Значення понад 10–20 свідчить про високі втрати пакетів у радіолінку або про повільну роботу сховища GCS.
- **`loaded` (`uint16_t`, 2 байти):** Загальна кількість дійсних блоків 4×4, які наразі утримуються в оперативній пам'яті та на MicroSD. Оператор використовує цей лічильник для візуалізації прогресу передпольотного завантаження карт.

Наземна станція керування може динамічно налаштовувати частоту передачі повідомлення `TERRAIN_REPORT` за допомогою стандартної команди `MAV_CMD_SET_MESSAGE_INTERVAL` (команда `#511`), вказуючи бажаний період у мікросекундах (наприклад, `1000000` мкс для частоти 1 Гц або `200000` мкс для частоти 5 Гц під час швидкісного польоту над складним рельєфом).

## 7. Словник параметрів підсистеми рельєфу в автопілотах

Конфігурація підсистеми рельєфу в автопілотах ArduPilot (`AP_Terrain`) здійснюється за допомогою набору параметрів:

```
Словник параметрів автопілота для роботи з рельєфом:
┌──────────────────┬───────────┬───────────────┬────────────────────────────────────────────────────────┐
│ Назва параметра  │ Замовчування│ Одиниці     │ Опис та призначення                                    │
├──────────────────┼───────────┼───────────────┼────────────────────────────────────────────────────────┤
│ TERRAIN_ENABLE   │ 1         │ прапорець     │ 0: Вимкнено; 1: Увімкнено підтримку рельєфу            │
│ TERRAIN_FOLLOW   │ 1         │ прапорець     │ 0: Тільки моніторинг; 1: Використовувати у польоті     │
│ TERRAIN_SPACING  │ 100       │ метри         │ Горизонтальний крок сітки дискретизації (30–500 м)     │
│ TERRAIN_LOOKAHEAD│ 20        │ секунди       │ Часовий горизонт завчасного завантаження (5–60 с)      │
│ TERRAIN_OPTIONS  │ 0         │ бітова маска  │ Біт 0: Сувора заборона зведення двигунів без даних;    │
│                  │           │               │ Біт 1: Використовувати рельєф для розрахунку RTL       │
└──────────────────┴───────────┴───────────────┴────────────────────────────────────────────────────────┘
```

Детальний опис впливу параметрів:
- **`TERRAIN_ENABLE`:** Головний перемикач модуля. Якщо встановлено в `0`, автопілот повністю зупиняє фоновий потік `AP_Terrain`, не виділяє RAM-буфери і не надсилає повідомлення `TERRAIN_REQUEST`.
- **`TERRAIN_FOLLOW`:** Визначає, чи дозволено навігаційному контролеру коригувати висоту польоту в режимах автономного слідування за маршрутом (AUTO, GUIDED, RTL). Якщо параметр вимкнено (`0`), автопілот накопичує дані рельєфу лише для відображення кліренсу в телеметрії `TERRAIN_REPORT`, але сам політ виконується на фіксованій висоті над точкою старту.
- **`TERRAIN_SPACING`:** Задає бажаний крок між вузлами сітки. Зменшення кроку зі 100 м до 30 м підвищує точність огинання вузьких ущелин, але збільшує обсяг пам'яті та трафіку телеметрії приблизно в 11 разів (`(100/30)² ≈ 11.1`).
- **`TERRAIN_LOOKAHEAD`:** Час у секундах, на який автопілот множить поточну шляхову швидкість `V_ground` для розрахунку випередження. Збільшення значення до 30–40 с необхідне для швидкісних літаків (понад 30 м/с), щоб компенсувати затримки радіолінку.
- **`TERRAIN_OPTIONS`:** Керує поведінкою передпольотного тесту безпеки (Pre-arm Check). Увімкнення біта `0` блокує запуск двигунів, якщо хоча б для одного навігаційного пункту місії відсутні завантажені блоки рельєфу.

## 8. Специфікація бінарного формату файлів на MicroSD (/TERRAIN/*.DAT)

Для автономної роботи без наземної станції автопілот ArduPilot підтримує зберігання тайлів на карті пам'яті MicroSD у спеціалізованому бінарному форматі. Каталог `/TERRAIN/` містить файли, розбиті за географічними квадратами розміром 1°×1°.

Ім'я файлу формується за шаблоном: `[N|S]YY[E|W]XXX.DAT`:
- `N48E024.DAT` — квадрат із південно-західним кутом на 48° пн. ш., 24° сх. д. (Карпати, Україна);
- `S13W072.DAT` — квадрат 13° пд. ш., 72° зх. д. (Анди, Перу).

### Структура бінарного файлу .DAT

Файл складається із фіксованого 16-байтового заголовка та послідовності бінарних записів блоків:

```
Формат 16-байтового заголовка файлу .DAT:
┌────────┬──────────────┬──────────────┬────────────────────────────────────────────────────────┐
│ Зсув   │ Тип даних    │ Поле         │ Значення та опис                                       │
├────────┼──────────────┼──────────────┼────────────────────────────────────────────────────────┤
│ 0..3   │ uint32_t     │ magic        │ Магічне число 0x54455252 (ASCII "TERR")                │
│ 4      │ uint8_t      │ version      │ Версія формату (1)                                     │
│ 5      │ uint8_t      │ grid_spacing │ Крок сітки в декаметрах (10 = 100 метрів)              │
│ 6..7   │ int16_t      │ lat_deg      │ Цілий градус широти SW кута квадрата (-90..+90)        │
│ 8..9   │ int16_t      │ lon_deg      │ Цілий градус довготи SW кута квадрата (-180..+180)    │
│ 10..11 │ uint16_t     │ block_count  │ Кількість валідних блоків у цьому файлі                │
│ 12..15 │ uint32_t     │ reserved     │ Зарезервовано для майбутніх розширень (заповнено 0)    │
└────────┴──────────────┴──────────────┴────────────────────────────────────────────────────────┘

Формат 36-байтового запису блоку:
┌────────┬──────────────┬──────────────┬────────────────────────────────────────────────────────┐
│ Зсув   │ Тип даних    │ Поле         │ Значення та опис                                       │
├────────┼──────────────┼──────────────┼────────────────────────────────────────────────────────┤
│ 0      │ uint8_t      │ block_idx_x  │ Індекс блоку по довготі всередині 1° квадрата          │
│ 1      │ uint8_t      │ block_idx_y  │ Індекс блоку по широті всередині 1° квадрата           │
│ 2..3   │ uint16_t     │ flags        │ Біт 0: валідність; Біт 1: наявність void-вузлів        │
│ 4..35  │ int16_t[16]  │ data         │ Матриця 4×4 висот AMSL у метрах (32 байти)             │
└────────┴──────────────┴──────────────┴────────────────────────────────────────────────────────┘
```

Така фіксована структура дозволяє автопілоту за координатами літака обчислювати точне бінарне зміщення (*file offset*) всередині файлу за формулою `offset = 16 + index · 36` і виконувати пряме читання секторів функцією `fseek()` за час `O(1)` без повного завантаження файлу в пам'ять.

### Архітектура взаємодії з файловою системою FAT32

При зверненні до MicroSD операційна система реального часу NuttX або ChibiOS використовує кешований драйвер блочного пристрою SDIO. Підсистема `AP_Terrain` відкриває файли `.DAT` у режимі тільки для читання (`O_RDONLY`), якщо блок уже записаний, або з прапорцем оновлення (`O_RDWR | O_CREAT`), коли новий блок надходить по радіолінку від GCS.

Для запобігання пошкодженню файлової системи FAT32 під час раптового знеструмлення апарата у польоті операція запису супроводжується скиданням буферів драйвера `fsync()` лише після накопичення пачки з 8–16 нових блоків, що суттєво зменшує зношування флеш-пам'яті картки.
