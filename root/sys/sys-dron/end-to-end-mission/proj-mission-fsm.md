# ⚙️ Автомат місії на C: таблиця переходів і стійке виявлення посадки

Автомат станів місії легко намалювати стрілочками на дошці й важко написати так, щоб він **не міг зламатися**. Наївна реалізація — купа прапорців `bool armed`, `bool flying`, `bool landing` і ліс `if`-ів навколо них — здається робочою рівно доти, доки хтось не виставить два прапорці одночасно й апарат не опиниться в стані «озброєний і роззброєний водночас». Задача цього проєкту — зібрати автомат так, щоб **нелегальний перехід був неможливий за побудовою** (а не «ми ж перевіряємо, що так не буває»), щоб крок місії **ніколи не блокував** контур стабілізації під ним, і — найтонше — щоб роззброєння наприкінці спрацьовувало на **стійку** ознаку посадки, а не на одиничний спалах, який здіймає удар об землю.

Розкладімо це на три шматки, кожен зі своєю пасткою, і зберімо їх у робочу прошивку.

## Ідея: стан — це дані, перехід — це таблиця

Перше рішення, від якого залежить усе решта: **стан має бути одним значенням, а не набором прапорців.** Якщо апарат описано трьома `bool`-ами, то простір станів — це 2³ = 8 комбінацій, і лише 6 із них осмислені; решта — «озброєний і роззброєний», «летить, але завантажується» — сміття, яке *технічно можна виставити*. Один `enum` прибирає це коріння зла: змінна `state` завжди дорівнює рівно одному зі станів, і немає жодного способу закодувати нею суперечність.

```c
typedef enum {
    ST_BOOT = 0,   // піднімається прошивка, йде самоперевірка
    ST_READY,      // готово, двигуни РОЗЗБРОЄНІ (disarmed)
    ST_ARMED,      // двигуни озброєні, апарат ще на землі
    ST_FLYING,     // у польоті, веде маршрут
    ST_LANDING,    // сідає, чекає стійкого торкання землі
    ST_DISARMED,   // сіло, двигуни дорізані, місію завершено
    ST_COUNT       // не стан — розмір для таблиць (завжди останній)
} mission_state_t;
```

Друге рішення випливає з першого. Якщо стан — це просто число (індекс), то **дозволені переходи — це таблиця**, а не розсипані по коду `if`-и. Запитання «чи можна з A перейти в B?» стає одним звертанням до двовимірного масиву `allowed[A][B]`. І щойно перехід описаний **даними**, з'являється точка, крізь яку **зобов'язаний** пройти кожен перехід, — а отже, місце, де нелегальний перехід можна відрубати раз і назавжди. Ти не «намагаєшся не робити» стрибок `ST_LANDING → ST_FLYING`; його просто **немає** в таблиці, тож функція переходу його не пропустить, хай хто її покличе.

> 🔧 **Навіщо це.** Різниця між «перевіряємо, що не буває» і «не може бути за побудовою» — це різниця між багом, який колись стрельне, і багом, якого не існує. Прапорці покладаються на дисципліну програміста: *не забудь* скинути `flying`, коли ставиш `landing`. Таблиця переходів не покладається ні на кого — забути нема чого, бо єдиний вхід у зміну стану сам звіряється з таблицею. Це і є «неможливо за побудовою»: помилку прибрано не пильністю, а формою коду.

## Таблиця переходів: зробити нелегальне неможливим

Опишемо, які переходи взагалі дозволені. Уперед ланцюг однобічний — кожен стан пускає рівно в наступний; але є ще й рухи **назад-у-безпечніше** (аварійні виходи), і їх теж треба дозволити явно, інакше автомат не зможе врятуватися. Наприклад, `ST_ARMED → ST_READY` (роззброїтися на землі) чи `ST_FLYING → ST_LANDING` (аварійно сісти) — легальні; а от `ST_DISARMED → ST_FLYING` (злетіти вже роззброєним) — ні.

```c
// allowed[from][to] == true  ⟺  перехід from→to дозволений.
// Усе, чого тут немає, — НЕЛЕГАЛЬНЕ й буде відкинуте функцією переходу.
static const bool allowed[ST_COUNT][ST_COUNT] = {
//              BOOT  READY ARMED FLY   LAND  DISARM
/* BOOT   */  { 0,    1,    0,    0,    0,    0 },  // самоперевірка → READY
/* READY  */  { 0,    0,    1,    0,    0,    0 },  // ARM → ARMED
/* ARMED  */  { 0,    1,    0,    1,    0,    0 },  // роззброїтись назад / зліт
/* FLYING */  { 0,    0,    0,    0,    1,    0 },  // місію виконано / RTL → LANDING
/* LANDING*/  { 0,    0,    0,    1,    0,    1 },  // сіло → DISARM; зірвати посадку → FLYING
/* DISARM */  { 0,    1,    0,    0,    0,    0 },  // після паузи можна знову READY
};
```

Прочитаймо кілька клітинок, бо в них — уся логіка безпеки. У рядку `ARMED` стоять дві одиниці: `→READY` (роззброїтися назад, це рух у безпечніший бік, тому дозволено) і `→FLYING` (зліт). У рядку `FLYING` — лише `→LANDING`: з польоту нема прямої дороги ні назад в `ARMED`, ні тим паче в `DISARMED` — знеструмити двигуни в повітрі означає впасти, тож єдиний легальний вихід із польоту веде через посадку. А клітинка `LANDING→FLYING = 1` — це навмисний **зрив посадки** (go-around): якщо під час зниження щось пішло не так, автомат може перервати посадку й піти на друге коло замість того, щоб дорізати двигуни в метрі над перешкодою.

Тепер — **єдині двері** в зміну стану. Жоден `case` автомата не чіпає `state` напряму; усі кличуть `mission_transition()`, а вона першою дією звіряється з таблицею:

```c
static mission_state_t state = ST_BOOT;

// ЄДИНА функція, що змінює state. Іншого шляху немає — отже, обійти
// таблицю неможливо. Повертає true, якщо перехід відбувся.
static bool mission_transition(mission_state_t to) {
    if (to >= ST_COUNT)        return false;   // за межі enum — брак
    if (!allowed[state][to]) {                 // НЕЛЕГАЛЬНИЙ перехід —
        log_illegal(state, to);                //   не мовчки: лишаємо слід у лозі,
        return false;                          //   бо це майже завжди баг у логіці
    }
    on_state_exit(state);      // прибрати за старим станом (напр. згасити таймери)
    state = to;
    on_state_enter(to);        // ЄДИНЕ місце, де стан ставить свою ЦІЛЬ контуру
    return true;
}
```

Три речі роблять цю функцію надійною. По-перше, перевірка `allowed[state][to]` стоїть **перед** будь-якою зміною — нелегальний перехід не встигає нічого зіпсувати. По-друге, він не тоне тихо: `log_illegal` лишає слід, бо спроба нелегального переходу — це не «нормально, буває», а сигнал, що десь у логіці помилка, і її треба побачити. По-третє, `on_state_enter(to)` викликається **рівно в одному місці** — тут, — а отже, входовий обробник стану (той, що ставить контуру нову ціль) не можна ні пропустити, ні задублювати. Порівняй із прапорцями, де ти виставляєш `state` в п'яти місцях і в кожному *маєш не забути* ще й оновити ціль.

Ось як входовий обробник ставить цілі — і, що важливо, **лише ставить**, а не «летить»:

```c
// Викликається З mission_transition при вході в новий стан.
// Кожен стан робить рівно одне: оголошує контуру свою ЦІЛЬ.
static void on_state_enter(mission_state_t s) {
    switch (s) {
    case ST_READY:    motors_disarm();                 break; // двигуни мертві
    case ST_ARMED:    motors_arm();  hold_position();  break; // тримати точку на землі
    case ST_FLYING:   set_target_alt(TAKEOFF_ALT_CM);  break; // ціль — набрати висоту
    case ST_LANDING:  set_descent_rate(LAND_SPEED_CM); break; // ціль — плавно вниз
    case ST_DISARMED: motors_disarm();                 break; // дорізати, зафіксувати
    default: break;
    }
}
```

Жоден рядок тут не крутить двигуни й не піднімає апарат руками. `set_target_alt` каже контуру стабілізації «твоя нова ціль — отака висота», і на цьому робота стану скінчена: далі окремий швидкий контур сам, такт за тактом, зводитиме апарат до цієї цілі. Механіку цього поділу — чому повільний автомат лише міняє цілі, а тримає їх [контур реального часу](topic:sys-dron/flight-controller) з гарантованим строком — тут не переказую; для автомата важливо тільки, що вхід у стан **не блокує** й **не чекає**.

## Неблокуючий tick: чому тут не можна спати

Тепер сам крок повільного годинника. Його викликають регулярно — скажімо, 50 разів на секунду, — але **не** всередині критичного контуру, а поряд із ним. Головна вимога до нього одна, і вона категорична: **`mission_tick` мусить повернути керування швидко, ніколи не блокуючи.** Причина пряма й безжальна. Контур стабілізації, що тримає апарат у повітрі, крутиться на тому ж процесорі. Кожна мілісекунда, яку `mission_tick` проведе в `delay()` чи в очікуванні `while (!condition) {}`, — це такт, який контур **не виконав**, а отже, мілісекунда, за яку апарат нахилився не туди й ніхто його не виправив. Блокування в логіці місії не «сповільнює місію» — воно **валить стабілізацію**.

Тому автомат ніде не «робить і чекає». Він **питає**: чи справдилася умова? Ні — вийшли, повернемося наступним тактом і спитаємо знову. Так виглядає весь автомат:

```c
// ПОВІЛЬНИЙ годинник: викликається зрідка (напр. 50 Гц), ПОРЯД із контуром,
// але НЕ в ньому. Ніде не блокує: лише читає події й, якщо брама відкрита,
// просить перехід. Тримання цілей — робота контуру, не ця.
void mission_tick(void) {
    switch (state) {

    case ST_BOOT:
        if (selftest_passed())                 // брама: самоперевірка пройдена
            mission_transition(ST_READY);
        break;

    case ST_READY:
        // Озброєння — лише за командою оператора І з пройденими arming-перевірками.
        if (cmd_arm() && arming_allowed())
            mission_transition(ST_ARMED);
        break;

    case ST_ARMED:
        if (failsafe_now())                     // аварія на землі → назад у безпечне
            mission_transition(ST_READY);       //   (роззброїти — на землі це безпечно)
        else if (cmd_takeoff())                 // брама: команда зльоту
            mission_transition(ST_FLYING);
        break;

    case ST_FLYING:
        run_mission_legs();                     // веде цілі по маршруту — НЕ блокуючи
        if (failsafe_now())                     // аварія в повітрі → КЕРОВАНО вниз,
            mission_transition(ST_LANDING);     //   а не «вимкнути двигуни»
        else if (mission_complete())
            mission_transition(ST_LANDING);
        break;

    case ST_LANDING:
        if (go_around_requested())              // зрив посадки → друге коло
            mission_transition(ST_FLYING);
        else if (land_detected())               // брама: СТІЙКЕ торкання землі
            mission_transition(ST_DISARMED);
        break;

    case ST_DISARMED:
        // Кінцевий стан-«тупик»: двигуни вже дорізано у on_state_enter,
        // лог закрито. Нічого не крутимо. Вихід — лише через окрему
        // команду reset у READY (рядок DISARM у таблиці це дозволяє).
        break;
    }
}
```

Придивися, що **в кожному** стані, де є ризик, стоїть свій аварійний вихід — і вони **різні**, бо різна ціна помилки. З `ST_ARMED` аварія веде в `ST_READY`: апарат на землі, найбезпечніше — роззброїти, знеструмити гвинти. З `ST_FLYING` та сама `failsafe_now()` веде **не** в роззброєння, а в `ST_LANDING` — бо в повітрі вимкнути двигуни означає впасти, і єдиний безпечний вихід — керовано опуститися. Одна й та сама подія «сталася біда» розв'язується протилежно залежно від стану — і саме тому автомат тримає стан явно: не знаючи, **де** апарат, неможливо вирішити, **куди** його рятувати. Загальна дисципліна таких запобіжників (при сумніві — у бік менших наслідків) — це тема [failsafe](topic:sys-dron/failsafe); тут вона проступає конкретикою таблиці.

І ще одне, що легко проґавити: у `ST_LANDING` **два** виходи — стійка посадка веде вниз, у `ST_DISARMED`, а `go_around_requested()` — угору, назад у `ST_FLYING`. Обидва легальні за таблицею. Стан, з якого є лише «вперед», — потенційна пастка: якщо єдина ознака «вперед» не настане (апарат завис і не сідає), автомат застрягне назавжди без способу вибратися. Наявність `go_around` — це і є той аварійний вихід зі стану посадки, без якого зависання над перешкодою не мало б розв'язку.

> 🔧 **Навіщо це.** «Неблокуюче мислення» звучить абстрактно, поки не побачиш ціну блокування в цифрах. Контур на 400 Гц має 2.5 мс на такт. Один `delay(20)` у `mission_tick` — це вкрадені **вісім** тактів стабілізації поспіль: апарат вісім разів мав виправити нахил і жодного не виправив. На стенді це «іноді смикається», у польоті — падіння. Правило без винятків: у логіці місії немає `delay`, немає `while (!x) {}`, немає жодного очікування «на місці» — лише «спитав, не готове — вийшов, спитаю наступним тактом».

## Стійке виявлення посадки: чому одного кадру мало

Дійшли до найтоншого шматка — `land_detected()`. Спокуса написати його наївно велика й підступна: «висота ≈ 0 → сіло → роззброїти». Ця версія майже працює й тому особливо небезпечна.

Розберімо, чому вона хибна, від фізики. По-перше, висота від барометра **дихає**: тиск гуляє від поривів вітру, від власного обдування гвинтами біля землі, і показ «нуль» стрибає туди-сюди на метри навіть коли апарат нерухомо висить. Роззброїтися на випадковому провалі показу до нуля — означає дорізати двигуни в повітрі. По-друге, і це головне: у **мить удару** об землю апарат часто **підскакує**. Шасі пружинить, гвинти ще дають тягу — і на частку секунди апарат знову в повітрі, злітає на кілька сантиметрів. Якщо автомат роззброївся на першому ж кадрі «схоже, сіло», він відрубає двигуни рівно в мить підскоку — і апарат падає рештою висоти вже мертвим, перекидається, ламає гвинти.

Висновок від зворотного: посадка — це **не подія одного кадру, а стан, що триматься**. Справжня посадка виглядає так: тяга давно на мінімумі (контур більше не тримає апарат — нема потреби), вертикальна швидкість близька до нуля (не піднімається й не падає), апарат нерухомий (акселерометр не бачить ні поштовхів, ні обдування). І — ключове — усі ці ознаки тримаються **разом і безперервно** якийсь час. Одиничний підскок їх усі одразу **рве**: у мить відскоку вертикальна швидкість стрибає, тяга можливо зростає, акселерометр ловить поштовх. Тому лік «скільки поспіль тактів усе тихо» відрізняє справжнє стояння від миттєвого стрибка.

Це називають **усуненням деренчання** (англ. *debounce* — прибрати брязкіт контакту): та сама ідея, що гасить брязкіт механічної кнопки, гасить і «брязкіт» посадки. Умову визнаємо істинною не тоді, коли вона *справдилась*, а тоді, коли вона *протрималась* N тактів підряд без жодного зриву.

Так це виглядає в коді. Реальний автопілот саме так і робить: ArduPilot вважає, що мультикоптер сів, коли тяга на нижній межі, вертикальна швидкість у вікні близько ±1 м/с і апарат не прискорюється — **і все це протягом приблизно однієї секунди** підряд; лічильник кадрів росте, поки всі умови разом істинні, і **скидається в нуль тієї ж миті**, щойно хоч одна відпала *(джерело — `ArduCopter/land_detector.cpp`; конкретні пороги й час залежать від апарата й версії, це усталена практика платформи, а не жорсткий стандарт)*.

```c
// Порогові значення — з фізики апарата (тут як приклад типових величин).
#define LAND_VZ_MAX_CMS      50      // |верт. швидкість| < 0.5 м/с — «нерухомо по вертикалі»
#define LAND_ACC_MAX_CMS2    100     // збурення прискорення < 1 м/с² — «не трясе»
#define LAND_HOLD_TICKS      50      // умови мусять протриматись 50 тактів поспіль
//                                      (при 50 Гц це рівно 1 секунда)

// true — ЛИШЕ якщо всі ознаки посадки протрималися LAND_HOLD_TICKS тактів підряд.
// Один зрив будь-якої ознаки скидає лік у нуль (пружний підскок нас не обдурить).
bool land_detected(void) {
    static uint16_t stable = 0;      // скільки тактів поспіль «схоже на землю»

    // Три незалежні ознаки того, що апарат СТОЇТЬ на землі:
    bool low_thrust  = throttle_out() <= throttle_min();      // контур уже не тримає
    bool no_vspeed   = abs_i(climb_rate_cms()) < LAND_VZ_MAX_CMS;   // не лізе й не падає
    bool still       = accel_disturb_cms2() < LAND_ACC_MAX_CMS2;    // не трясе / не обдуває

    if (low_thrust && no_vspeed && still) {
        if (stable < LAND_HOLD_TICKS)
            stable++;                // ще один тихий такт — присуваємось до впевненості
    } else {
        stable = 0;                  // ХОЧ ОДНА ознака зірвалась → лік з нуля
    }

    return stable >= LAND_HOLD_TICKS;   // впевнені лише коли витримали всі N тактів
}
```

Уся сила — в гілці `else`. Вона каже: **будь-який** зрив **будь-якої** ознаки скидає лічильник у нуль **негайно**, не зменшує на одиницю, а обнуляє. Тому 49 тихих тактів і один підскок дають не «майже готово», а **чистий нуль** — відлік починається спочатку. Саме це робить виявлення стійким до одиничного стрибка: щоб `land_detected()` повернув `true`, апарат мусить простояти тихо всі 50 тактів **без єдиної перерви**. Пружний відскок рве серію — і серія починається наново, поки апарат справді не заспокоїться на землі.

Зверни увагу й на те, чого тут **немає**: у переліку ознак немає висоти. Це навмисно. Висота — ненадійний свідок (барометр дихає), а надійні свідки — тяга, вертикальна швидкість і нерухомість, бо вони описують не «де апарат», а «що з ним відбувається». Апарат, що **стоїть**, віддає ці три ознаки незалежно від того, що бреше барометр. Висоту в кращому разі беруть як грубий запобіжник («не роззброюйся, поки барометр показує вище десяти метрів»), але **ніколи** — як єдину чи головну ознаку посадки.

> 🔧 **Навіщо це.** Це найдорожча пастка з усіх у прошивці апарата, бо наївна версія «висота ≈ 0 → роззброїти» проходить усі стендові перевірки — на столі апарат і справді біля нуля — і вбиває апарат саме в полі, на реальній твердій посадці з підскоком. Стійке (debounced) виявлення коштує п'ять рядків із лічильником і рятує апарат від роззброєння в мить відскоку. Правило: роззброюй за **стійкою ознакою стояння**, яка витримала N тактів, а не за миттєвим значенням висоти.

## Складність і пастки

Автомат вище компактний, але кожен його елемент з'явився, щоб закрити конкретну діру. Зберімо пастки разом — це чек-лист, за яким варто перечитати будь-який автомат місії, свій чи чужий.

**Блокуюча пауза в логіці місії.** Найпоширеніша й найпідступніша. Хтось пише в `mission_tick` щось на кшталт «дай зльоту команду, `delay(2000)`, тоді переходь у політ» — і краде в контуру стабілізації дві секунди тактів. Апарат смикає, у гіршому разі падає. Ознака в чужому коді проста: будь-який `delay()`, `sleep()`, `vTaskDelay()` чи `while (!x) {}` десь поряд із логікою місії — майже напевно баг. Лік часу в місії робиться **неблокуюче**: запам'ятав мітку часу, а на кожному такті **питаєш**, чи минуло; сплю — ніколи. Загальний апарат такого мислення (мітки замість пауз) — це [неблокуючий час](topic:sf-devices/nonblocking-time), а місце для повільного `mission_tick` поряд із швидким контуром дає [періодичне планування](topic:sf-devices/periodic-scheduling).

**Роззброєння за нульовою висотою замість стійкої ознаки.** Розібрано вище, але воно варте окремого рядка в чек-листі, бо ховається краще за інші: код виглядає розумно, працює на столі й гине в полі. Якщо в `land_detected()` фігурує висота як **головна** умова — це діра. Ознаки посадки — тяга, вертикальна швидкість, нерухомість, — і всі з дебаунсом на N тактів.

**Стан без аварійного виходу.** Пройдись поглядом по `switch` і в кожному `case` спитай: якщо саме тут станеться біда, куди автомат піде? Якщо у стані стоїть лише перехід «вперед» і жодного `failsafe`-виходу — це діра: настане збій саме в цій фазі, і апарат зробить щось довільне або зависне назавжди. У нашому автоматі `ST_ARMED` має вихід у `ST_READY`, `ST_FLYING` — у `ST_LANDING`, `ST_LANDING` — go-around назад у `ST_FLYING`. Стан-тупик допустимий лише один — кінцевий `ST_DISARMED`, і то навмисно (місія завершена, апарат безпечний).

**Прямий запис у `state` повз таблицю.** Досить одного місця в коді, де хтось написав `state = ST_FLYING;` напряму — і вся гарантія «нелегальне неможливе» розсипається, бо цей рядок таблицю не звіряє. Дисципліна проста й перевірна: `state` — `static` у своєму файлі, змінює його **лише** `mission_transition`, і це можна навіть механічно перевірити (жодного `state =` поза цією функцією). Тоді таблиця — справді єдина брама, а не одна з кількох.

**Мовчазний нелегальний перехід.** Протилежна крайність: `mission_transition` відкидає нелегальний перехід, але робить це **тихо**, просто `return false`. Тоді баг у логіці (хтось попросив неможливий перехід) не видно — автомат просто «нічого не зробив», а розробник години шукає, чому апарат «застряг». Тому в коді стоїть `log_illegal`: спроба нелегального переходу — це майже завжди помилка **в самій логіці**, і вона мусить лишати слід, а не глухо зникати.

**Плутанина двох годинників.** І, підсумовуючи, найглибша концептуальна пастка: змішати повільний автомат зі швидким контуром в один цикл. Тоді або логіка місії засмічує критичний контур (і той не встигає стабілізувати), або контур нав'язує місії свій жорсткий ритм (і та стає нечитабельною). Автомат місії й контур стабілізації — **різні годинники з різними вимогами**: перший рідко перемикає цілі й може дозволити собі складну логіку станів, другий щотакту тримає апарат і не сміє запізнитися. Наш `mission_tick` тому й лише **міняє цілі** й **ніколи не блокує** — це єдиний спосіб дати обом годинникам цокати поряд, не заважаючи один одному.
