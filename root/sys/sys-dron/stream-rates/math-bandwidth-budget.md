# 🧮 Математичний розрахунок бюджету смуги пропускання телеметрії

Цей документ містить строгий математичний аналіз накладних витрат протоколу MAVLink, формули розрахунку ємності фізичного інтерфейсу UART, рівняння утилізації радіоканалу та числові моделі розподілу частот телеметрії для різних типів каналів зв'язку.

---

### 1. Теоретична ємність каналу та межа Шеннона

Фундаментальним обмеженням будь-якої радіолінії зв'язку є теорема Шеннона — Гартлі. Вона визначає максимальну теоретичну швидкість передачі інформації `C` (біт/с) без помилок через неперервний аналоговий канал зі смугою пропускання `W` (Гц) за наявності адитивного білого гаусового шуму (AWGN):

```
C
= W · log₂(1 + SNR)             [теорема Шеннона — Гартлі: максимальна місткість каналу]
```

У типовому вузькосмуговому FSK-радіомодемі діапазону 433/915 МГц (наприклад, SiK Radio) ширина радіоканалу становить `W = 100` кГц. За сприятливого відношення сигнал/шум `SNR = 20` дБ (лінійне відношення потужностей `SNR = 100`):

```
C_shannon
= 100000 · log₂(1 + 100)        [підстановка параметрів у формулу Шеннона]
= 100000 · log₂(101)            [додавання одиниці до лінійного SNR]
= 100000 · 6.658                [обчислення двійкового логарифма]
= 665800 біт/с                  [теоретична фізична межа ефіру ~665 кбіт/с]
```

Однак реальні апаратні модулятори мікроконтролерів використовують прості схеми 2-GFSK або 4-GFSK модуляції без складних багатопозиційних QAM-сузір'їв. Через це «повітряна» швидкість радіотрансивера (*Air Data Rate*) фіксується на рівні 64 кбіт/с (8000 байт/с).

Далі вступає в дію напівдуплексний режим з часовим розділенням TDD (*Time Division Duplexing*). Ефір ділиться між передачею БПЛА та прийомом станції у співвідношенні приблизно 50/50. Додатково віднімаються міжкадрові захисні інтервали (*Guard Times*) та час перемикання синтезатора частоти під час стрибків FHSS (50 стрибків на секунду). Це зменшує доступний ефірний потік корисних байтів до величини:

```
C_air_effective
= 8000 · 0.50 · 0.85            [50% TDD напівдуплекс · 85% ефективність без пауз]
= 3400 Б/с                      [реальна межа пропускної здатності радіоефіру]
```

Саме тому фізична пропускна здатність радіоканалу майже завжди нижча, ніж швидкість дротового з'єднання UART польотного контролера.

### 2. Фізична ємність послідовного порту UART

Інтерфейс UART передає кожен байт даних у вигляді асинхронного кадру стандарту 8N1: 1 стартовий біт (логічний нуль), 8 бітів корисних даних, 0 бітів контролю парності та 1 стоповий біт (логічна одиниця). Таким чином, для передачі одного байта інформації на фізичному рівні витрачається рівно 10 бітових інтервалів.

Теоретична максимальна швидкість передачі байтів `C_uart` обчислюється через бодрейт `Baud`:

```
C_uart
= Baud ÷ 10                     [фізичний формат кадру 8N1: 10 біт на кожен переданий байт]
```

Розрахунок ємності для стандартних швидкостей телеметрійних радіомодемів:

```
C_uart(57600)
= 57600 ÷ 10                    [ділення бодрейту на 10 бітів кадру]
= 5760 Б/с                      [базовий режим SiK Radio / 3DR Telemetry]

C_uart(115200)
= 115200 ÷ 10                   [ділення бодрейту на 10 бітів кадру]
= 11520 Б/с                     [високошвидкісний режим радіомодема]

C_uart(921600)
= 921600 ÷ 10                   [ділення бодрейту на 10 бітів кадру]
= 92160 Б/с                     [пряме кабельне / супутнє з'єднання]
```

### 3. Накладні витрати кадрів MAVLink v1 та MAVLink v2

Повна довжина пакета `L_packet` на дроті складається з розміру корисного навантаження (Payload) `L_payload` та службового обрамлення заголовка і контрольної суми CRC.

#### Структура кадру MAVLink v1
Службовий заголовок містить 6 байтів:
1. Стартовий байт STX (`0xFE`) — 1 байт.
2. Довжина корисного навантаження Payload Length — 1 байт (0..255).
3. Лічильник послідовності Packet Sequence — 1 байт (0..255 для виявлення втрат).
4. Системний ID передавача System ID — 1 байт.
5. Компонентний ID передавача Component ID — 1 байт.
6. Ідентифікатор типу повідомлення Message ID — 1 байт (підтримує лише ID від 0 до 255).
7. Контрольна сума CRC-16/MCRF4XX — 2 байти.

```
L_packet_v1
= L_payload + 6 + 2             [6 байтів заголовок + 2 байти контрольної суми CRC]
= L_payload + 8                 [сумарне службове обрамлення MAVLink v1 становить 8 байтів]
```

#### Структура кадру MAVLink v2 (без криптографічного підпису)
Заголовок MAVLink v2 містить 10 байтів:
1. Стартовий байт STX (`0xFD`) — 1 байт.
2. Довжина корисного навантаження Payload Length — 1 байт.
3. Прапорці несумісності Incompatibility Flags — 1 байт (наприклад, біт 0x01 вказує на наявність підпису).
4. Прапорці сумісності Compatibility Flags — 1 байт.
5. Лічильник послідовності Packet Sequence — 1 байт.
6. Системний ID передавача System ID — 1 байт.
7. Компонентний ID передавача Component ID — 1 байт.
8. Розширений Message ID — 3 байти (підтримує 24-бітні ідентифікатори від 0 до 16 777 215).
9. Контрольна сума CRC-16/MCRF4XX — 2 байти.

```
L_packet_v2
= L_payload + 10 + 2            [10 байтів заголовок + 2 байти контрольної суми CRC]
= L_payload + 12                [сумарне службове обрамлення MAVLink v2 становить 12 байтів]
```

#### Механізм нульового обрізання (Zero-Truncation) у MAVLink v2
Протокол MAVLink v2 оптимізує передачу повідомлень шляхом видалення кінцевих байтів зі значенням `0x00` у полі Payload перед відправкою. На приймальній стороні буфер ініціалізується нулями, і непередані байти автоматично відновлюються. 

Наприклад, якщо у структурі `OPTICAL_FLOW` останні 10 байтів якості та інтегрованого зсуву дорівнюють нулю, довжина поля Payload зменшується з 44 байтів до 34 байтів. У розрахунках нижче ми використовуємо максимальну повну довжину повідомлень як найгірший гарантований сценарій (*worst-case sizing*).

#### Накладні витрати криптографічного підпису (Signing)
Якщо в каналі увімкнено автентифікацію повідомлень MAVLink v2, до кінця кадру додається 13-байтний блок підпису:
- Ідентифікатор ключа зв'язку `link_id` — 1 байт.
- 48-бітний монотонний мікросекундний штамп часу `timestamp` — 6 байтів (захист від атак повторного відтворення).
- Сигнатура HMAC-SHA256, усічена до 48 бітів — 6 байтів.

```
L_packet_v2_signed
= L_payload + 12 + 13           [базовий кадр v2 + 13 байтів криптографічного блоку підпису]
= L_payload + 25                [сумарне службове обрамлення з підписом становить 25 байтів]
```

### 4. Формули розрахунку потоку даних та утилізації каналу

Для кожного окремого типу повідомлення `i`, що транслюється з частотою `F_i` (Гц) і має повний розмір кадру `L_i` (байтів), миттєвий потік байтів `R_i` та бітрейт `B_i` визначаються як:

```
R_i
= F_i · L_i                     [миттєвий потік байтів на секунду для потоку i]

B_i
= R_i · 10                      [фізичний бітрейт на рівні порту UART 8N1]
```

Сумарний потік даних телеметрії `R_total` для набору з `N` повідомлень становить:

```
R_total
= ∑ (F_i · L_i)                 [сума добутків частоти на довжину по всіх N потоках]
```

Коефіцієнт утилізації каналу (Link Utilization) `U` виражається у відсотках відносно номінальної швидкості порту:

```
U
= (R_total ÷ C_uart) · 100%     [відношення сумарного потоку до максимальної ємності UART]
```

### 5. Повний розрахунковий баланс типового польотного профілю

Розглянемо стандартний польотний набір телеметрії для безпілотника літакового або мультироторного типу при використанні протоколу MAVLink v2 без підпису:

```
+----+---------------------+------------+-----------+-----------+----------+-----------+
| №  | Повідомлення        | Payload (B)| Кадр v2(B)| Частота(Гц| Потік(Б/с| Бітрейт   |
+----+---------------------+------------+-----------+-----------+----------+-----------+
| 1  | ATTITUDE (#30)      | 28         | 40        | 50        | 2000     | 20000 bps |
| 2  | GLOBAL_POSITION_INT | 28         | 40        | 10        | 400      | 4000 bps  |
| 3  | VFR_HUD (#74)       | 20         | 32        | 10        | 320      | 3200 bps  |
| 4  | ALTITUDE (#141)     | 32         | 44        | 5         | 220      | 2200 bps  |
| 5  | GPS_RAW_INT (#24)   | 30         | 42        | 5         | 210      | 2100 bps  |
| 6  | SYS_STATUS (#1)     | 31         | 43        | 2         | 86       | 860 bps   |
| 7  | BATTERY_STATUS (#147| 41         | 53        | 1         | 53       | 530 bps   |
| 8  | RADIO_STATUS (#109) | 9          | 21        | 2         | 42       | 420 bps   |
| 9  | HEARTBEAT (#0)      | 9          | 21        | 1         | 21       | 210 bps   |
+----+---------------------+------------+-----------+-----------+----------+-----------+
```

Покроковий розрахунок сумарного навантаження каналу:

```
R_total
= 2000 + 400 + 320 + 220 + 210 + 86 + 53 + 42 + 21  [сума потоків усіх 9 активних повідомлень]
= 3352 Б/с                      [сумарний потік нестисненої телеметрії]
```

Покроковий розрахунок коефіцієнта утилізації для каналу SiK Radio 57600 бод (`C_uart = 5760` Б/с):

```
U
= (3352 ÷ 5760) · 100%          [ділення сумарного потоку на ємність каналу 57600 бод]
= 0.5819 · 100%                 [обчислення частки завантаження порту]
= 58.19%                        [робоча зона: завантаження каналу строго менше 60%]
```

Обчислення залишкового резерву пропускної здатності:

```
R_reserve
= C_uart - R_total              [віднімання зайнятої смуги від повної місткості]
= 5760 - 3352                   [підстановка числових значень у байтах на секунду]
= 2408 Б/с                      [вільний резерв: 41.81% смуги під команди та завади]
```

### 6. Аналіз перевантаження при запиті параметрів (Param Burst)

Під час ініціалізації сесії зв'язку наземна станція виконує вичитування дерева параметрів за допомогою команди `PARAM_REQUEST_LIST` (#21). Польотний контролер відповідає лавиною повідомлень `PARAM_VALUE` (#22).

Кожне повідомлення `PARAM_VALUE` містить 25 байтів корисного навантаження:
- `param_value` (float) — 4 байти.
- `param_count` (uint16_t) — 2 байти.
- `param_index` (uint16_t) — 2 байти.
- `param_id` (char[16]) — 16 байтів рядкового імені.
- `param_type` (uint8_t) — 1 байт.

Повний розмір кадру MAVLink v2:

```
L_param
= 25 + 12                       [25 байтів payload + 12 байтів службового заголовка v2]
= 37 Байт                       [повний розмір одного кадру значення параметра]
```

Якщо польотний контролер містить `M = 800` параметрів і намагається передати їх із максимальною швидкістю за `t = 4` секунди (частота 200 пакетів/с):

```
R_param
= (800 · 37) ÷ 4                [множення кількості параметрів на розмір і ділення на час]
= 29600 ÷ 4                     [сумарний обсяг байтів усіх 800 параметрів]
= 7400 Б/с                      [потік самих лише параметрів без урахування телеметрії]

R_burst_total
= R_telemetry + R_param         [додавання фонового польотного потоку до потоку параметрів]
= 3352 + 7400                   [підстановка значень потоків]
= 10752 Б/с                     [сумарний піковий потік у серійному каналі]
```

Розрахунок коефіцієнта перевантаження для каналу 57600 бод:

```
U_burst
= (10752 ÷ 5760) · 100%         [ділення пікового потоку на ємність каналу 5760 Б/с]
= 1.8667 · 100%                 [обчислення кратності перевантаження]
= 186.67%                       [перевантаження каналу на 86.67% понад фізичну стелю!]
```

**Інженерний висновок:** Під час вичитування параметрів потік перевищує фізичну ємність порту майже вдвічі. Апаратний буфер модема переповнюється за 400 мілісекунд, що призводить до втрати пакетів `HEARTBEAT` та затримки доставки команд. Для запобігання колапсу планувальник MAVLink прошивки зобов'язаний обмежувати швидкість передачі параметрів константою (наприклад, не більше 20–30 пакетів `PARAM_VALUE` на секунду, що додає лише 740–1110 Б/с).

### 7. Математичні обмеження телеметрії в ExpressLRS (ELRS)

У протоколах ExpressLRS радіолінк спроєктовано для надшвидкої передачі команд керування з пульта пілота. Канал працює фіксованими пакетами з частотою `F_packet` (від 50 до 500 Гц). Зворотна телеметрія передається у виділених слотах за коефіцієнтом мультиплексування `Telemetry_Ratio = 1:N` (наприклад, 1:64 або 1:32).

Кількість доступних телеметрійних кадрів на секунду `F_telem_slots`:

```
F_telem_slots
= F_packet ÷ N                  [ділення базової частоти пакетів на коефіцієнт телеметрії]
```

Розрахунок доступних слотів для типових конфігурацій:

```
F_telem(250 Гц, 1:64)
= 250 ÷ 64                      [250 Гц пакетна частота при співвідношенні 1:64]
= 3.906 Гц                      [~3.9 телеметрійних радіокадрів на секунду]

F_telem(100 Гц, 1:32)
= 100 ÷ 32                      [100 Гц пакетна частота при співвідношенні 1:32]
= 3.125 Гц                      [~3.1 телеметрійних радіокадрів на секунду]

F_telem(50 Гц, 1:16)
= 50 ÷ 16                       [50 Гц пакетна частота при співвідношенні 1:16]
= 3.125 Гц                      [~3.1 телеметрійних радіокадрів на секунду]
```

У режимі ExpressLRS Airport (прозорий міст MAVLink) кожен телеметрійний кадр OTA вміщує до `S_payload = 64` байтів даних. Максимальна теоретична пропускна здатність телеметрійного каналу `C_elrs` становить:

```
C_elrs(250 Гц, 1:64)
= 3.906 · 64                    [множення кількості слотів на місткість кадру]
= 249.98 Б/с                    [абсолютна фізична стеля телеметрії ~250 Байт/с]
```

Порівняння з номінальним польотним профілем (3352 Б/с):

```
Дефіцит смуги
= 3352 ÷ 250                    [ділення стандартного потоку на місткість ELRS]
= 13.408                        [дефіцит пропускної здатності у 13.4 раза]
```

#### Розрахунок оптимізованого ультракомпактного профілю для ExpressLRS

Щоб передавати телеметрію через лінк ExpressLRS, польотний контролер повинен повністю вимкнути важкі повідомлення (штучний горизонт ATTITUDE на 50 Гц, приладову швидкість VFR_HUD та сирі дані сенсорів) і залишити лише критичний мінімум:

```
+----+---------------------+------------+-----------+-----------+----------+
| №  | Повідомлення        | Payload (B)| Кадр v2(B)| Частота(Гц| Потік(Б/с|
+----+---------------------+------------+-----------+-----------+----------+
| 1  | ATTITUDE (#30)      | 28         | 40        | 2         | 80       |
| 2  | GLOBAL_POSITION_INT | 28         | 40        | 1         | 40       |
| 3  | SYS_STATUS (#1)     | 31         | 43        | 0.5       | 21.5     |
| 4  | HEARTBEAT (#0)      | 9          | 21        | 1         | 21       |
+----+---------------------+------------+-----------+-----------+----------+
```

Покрокове обчислення оптимізованого навантаження:

```
R_elrs_opt
= 80 + 40 + 21.5 + 21           [сума 4 оптимізованих потоків телеметрії]
= 162.5 Б/с                     [сумарний потік стисненої телеметрії]

U_elrs
= (162.5 ÷ 250.0) · 100%        [ділення потоку на ємність телеметрії ELRS]
= 0.6500 · 100%                 [обчислення частки завантаження радіолінку]
= 65.0%                         [безпечна робоча утилізація радіолінку ELRS]
```

Такий баланс утримує навантаження на рівні 65% від ємності телеметрії ExpressLRS, гарантуючи стабільне оновлення координат на карті та контроль заряду батареї без втрати радіозв'язку на дистанціях понад 30 кілометрів.
