Важкий гексакоптер масою дванадцять кілограмів виконує автономну місію моніторингу промислової зони, рухаючись уздовж коридору високовольтних ліній передач зі швидкістю п'ятнадцять метрів на секунду. На шостій точці маршруту лідар фіксує невідому перешкоду (стрілу будівельного крана) за чотири метри по курсу, водночас напруга літій-полімерної батареї через сильний зустрічний вітер просідає нижче критичних 14.0 В, а основний канал радіокерування втрачає несучу частоту. Якщо логіка прийняття рішень на борту побудована на класичному скінченному автоматі (*Finite State Machine*, FSM, від латинського *finitus* — обмежений), системі необхідно виконати перехід між взаємовиключними станами: ухилення від зіткнення, аварійне повернення додому (*RTL*) чи екстрена автопосадка. Але стан «Ухилення» не має закладеного прямого переходу в «Посадку за низьким зарядом», а стан «RTL» не знає, як продовжити обхід перешкоди після відновлення зв'язку. Програма зависає в проміжному прапорці, дрон втрачає висоту і стикається з конструкцією. Ця системна нездатність класичних автоматів масштабуватися під комбінаторні виклики складної автономії спричинила перехід сучасної авіоніки та робототехніки до **дерев поведінки** (*Behavior Trees*, BT, від давньоанглійського *treow* — дерево, деревоподібна структура).

### Криза класичних автоматів (FSM) у бортовій автономії

Скінченний автомат описує поведінку системи через формальну математичну п'ятірку:

```
M = (S, Sigma, delta, s_0, F)   [формальне визначення скінченного автомата]
```

де:
- `S = {s_1, s_2, ..., s_N}` — скінченна множина дискретних станів;
- `Sigma` — вхідний алфавіт подій або тригерів (повідомлення сенсорів, таймери, команди оператора);
- `delta: S × Sigma → S` — функція переходів, яка кожній парі «стан-подія» зіставляє наступний стан;
- `s_0 ∈ S` — початковий стан системи;
- `F ⊆ S` — множина термінальних або фінальних станів.

Ця математична модель бездоганно працює в низькорівневих задачах із фіксованим, лінійним життєвим циклом: розкрутка безколекторних моторів через електронні регулятори швидкості (ESC), ініціалізація шини SPI, конфігурація регістрів барометра або парсинг бінарних пакетів телеметрії MAVLink. У цих сценаріях кількість станів зазвичай не перевищує 3–5, а граф переходів є практично односпрямованим і детермінованим.

Проте при переході до високорівневої автономії безпілотного апарата класичний FSM зазнає незворотного структурного колапсу через чотири фундаментальні обмеження.

```
       СКІНЧЕННИЙ АВТОМАТ (FSM)               ДЕРЕВО ПОВЕДІНКИ (BT)
   Комбінаторний вибух переходів:         Ієрархічна модульна композиція:

         ┌────────┐      ┌────────┐                  ┌─────────┐
    ┌───►│ Takeoff│◄────►│ Cruise │◄───┐             │Fallback?│
    │    └───┬────┘      └───┬────┘    │             └────┬────┘
    │        │ ╲            ╱ │        │        ┌─────────┴─────────┐
    │        │  ╲          ╱  │        │        ▼                   ▼
    │        ▼   ▼        ▼   ▼        │   ┌─────────┐         ┌─────────┐
    │    ┌────────┐      ┌────────┐    │   │Failsafe→│         │Mission →│
    └───►│ Avoid  │◄────►│  RTL   │◄───┘   └────┬────┘         └────┬────┘
         └───┬────┘      └───┬────┘           ┌─┴─┐               ┌─┴─┐
             │ ╲            ╱ │               ▼   ▼               ▼   ▼
             ▼  ▼          ▼  ▼              ( ) [ ]             [ ] [ ]
            ┌────────┐ ┌────────┐           Умови Дії           Зліт Політ
            │LandNow │ │ Payload│
            └────────┘ └────────┘
```

#### 1. Квадратичне зростання кількості переходів O(N²)
У системі з `N` дискретних польотних станів повний граф потенційних спрямованих переходів описується комбінаторною формулою:

```
T_max = N · (N - 1) = O(N²)   [максимальна кількість ребер у повнозв'язному графі FSM]
```

Якщо система містить 4 стани, кількість зв'язків дорівнює `4 · 3 = 12`. Але в реальному автономному дроні кількість станів швидко досягає 16–32 (передпольотна діагностика, калібрування сенсорів, очікування супутників GNSS, зліт, набір висоти, патрулювання за точками, обліт рельєфу, огинання перешкод, скидання корисного навантаження, пошук оптичного маркера, аварійне зависання, посадка, розброєння мотора, порушення геозони, реакція на відмову компаса, реакція на втрату радіоканалу).

Для 16 станів максимальна кількість переходів сягає:

```
16 · (16 - 1) = 240 переходів   [комбінаторне число зв'язків для N = 16]
```

Для 32 станів це число зростає до `32 · 31 = 992` переходів. Кожен новий стан вимагає перегляду та модифікації логіки **всіх** наявних станів. Якщо розробник додає новий аварійний режим «Екстрене розкриття рятувального парашута», йому необхідно вручну прописати умови переходу з кожного з попередніх станів. Пропуск хоча б одного ребра переходу (наприклад, стан «Скидання вантажу» або «Калібрування гіроскопа» не має обробника сигналу відмови двигуна) створює критичну «мертву зону» в логіці безпеки, яку складно виявити звичайним тестуванням.

#### 2. Жорстке зчеплення та відсутність модульного перевикористання
У класичному автоматі кожен стан явно вказує ім'я цільового стану, до якого він передає керування. Тіло стану `CruiseFlight` виглядає так:

:::tabs
```c
void state_cruise_update(flight_ctx_t *ctx) {
    if (ctx->battery_voltage < 14.0f) {
        fsm_transition_to(ctx, STATE_LAND_NOW);
    } else if (ctx->obstacle_detected) {
        fsm_transition_to(ctx, STATE_COLLISION_AVOIDANCE);
    } else if (ctx->rc_lost) {
        fsm_transition_to(ctx, STATE_RTL);
    } else {
        execute_path_following(ctx);
    }
}
```
```cpp
void CruiseFlightState::update(FlightContext& ctx) {
    if (ctx.battery_voltage < 14.0f) {
        ctx.fsm.transition_to(FlightState::LandNow);
    } else if (ctx.obstacle_detected) {
        ctx.fsm.transition_to(FlightState::CollisionAvoidance);
    } else if (ctx.rc_lost) {
        ctx.fsm.transition_to(FlightState::ReturnToLaunch);
    } else {
        execute_path_following(ctx);
    }
}
```
:::

Через це програмний модуль `CruiseFlightState` не є автономним. Він містить жорсткі залежності від конкретних переліків станів `LandNow`, `CollisionAvoidance` та `ReturnToLaunch`. Його неможливо повторно використати в іншій місії (наприклад, на розвідувальному літаку крилатого типу, де замість `LandNow` потрібен перехід у `GlideToSafeZone`) без редагування вихідного коду стану. Стан перестає бути ізольованим «чорним ящиком».

#### 3. Пастки та витік переходів в ієрархічних автоматах (HFSM)
Ієрархічні автомати станів (*Hierarchical Finite State Machines*, HFSM) намагаються подолати квадратичну складність групуванням станів у супер-стани (наприклад, супер-стан `IN_FLIGHT`, що об'єднує підстани `TAKEOFF`, `CRUISE`, `AVOIDANCE`). Перехід на рівні супер-стану (наприклад, подія `BATTERY_CRITICAL`) автоматично виводить систему з будь-якого вкладеного підстану.

Проте HFSM створюють іншу інженерну проблему — явище «витоку переходів» (*transition leakage*):
- **Порушення інкапсуляції:** Внутрішні підстани часто змушені знати про зовнішній контекст і ініціювати переходи, що пробивають кордони супер-станів;
- **Проблема глибокої історії (*Deep History State*):** Якщо виконання супер-стану `SURVEY_MISSION` було перерване аварійним режимом `RC_FAILSAFE`, після відновлення радіозв'язку системі невідомо, до якої саме підзадачі повертатися: починати галс заново, летіти до останньої точки чи зависати;
- **Складна семантика повернення:** Реалізація стеків повернення перетворює автомат на магазинний автомат (*pushdown automaton*), що експоненційно ускладнює формальну верифікацію та провокує стан гонитви (*race condition*) між паралельними подіями.

#### 4. Неможливість природного паралелізму
Реальний автопілот зобов'язаний виконувати кілька дій одночасно: утримувати стабілізацію за креном і тангажем, вести апарат уздовж просторової траєкторії, керувати триосьовим гіростабілізованим підвісом оптичної камери, опитувати лідар і передавати телеметрію по радіоканалу.

В автоматі станів паралелізм моделюється через так звані «ортогональні регіони» (*Orthogonal Regions*). Стан усієї системи стає декартовим добутком станів кожного регіону:

```
S_total = S_nav × S_gimbal × S_comms × S_safety   [декартів добуток множин станів]
```

Якщо підсистема навігації має 8 станів, підвіс — 4 стани, канал зв'язку — 3 стани, а контур безпеки — 5 станів, загальний фазовий простір системи становить:

```
8 · 4 · 3 · 5 = 480 комбінованих станів   [розмір простору станів]
```

Покриття такого графа модульними тестами стає математично нездійсненним, а поведінка системи в непередбачених комбінаціях станів (наприклад, «втрата зв'язку під час калібрування підвісу в режимі екстреного зниження») призводить до програмного блокування автопілота.

### Анатомія та формальна модель дерева поведінки (BT)

Дерево поведінки (*Behavior Tree*, BT) — це спрямований ациклічний граф з єдиним кореневим вузлом (*Root*), де обхід і прийняття рішень організовані зверху вниз і зліва направо за допомогою періодичних сигналів активації — **Тіків** (*Ticks*, від англійського *tick* — цокання, квант часу).

Формально дерево поведінки задається як трійка:

```
T = (V, E, root)   [формальне математичне визначення дерева поведінки]
```

де `V` — множина вузлів, `E ⊂ V × V` — множина орієнтованих ребер ієрархії, а `root ∈ V` — кореневий вузол. Кожен вузол `v ∈ V` реалізує функтор відображення стану системи `x_k ∈ X` у статус виконання `y_k ∈ {SUCCESS, FAILURE, RUNNING}` та оновлений стан системи `x_{k+1}`:

```
f_v: X → {SUCCESS, FAILURE, RUNNING} × X   [функтор виконання вузла]
```

Математична перевага дерева над автоматом полягає у **властивості композиційної монотонності**: при додаванні нового піддерева з `K` вузлів у граф із `M` вузлів кількість нових зв'язків завжди дорівнює точно одиниці (`+1` ребро до батьківського вузла), а складність системи зростає лінійно:

```
C_BT(M + K) = C_BT(M) + C_BT(K) = O(M + K)   [лінійна композиційна складність дерева]
```

тоді як для автомата додавання `K` станів збільшує складність зв'язків квадратично:

```
C_FSM(M + K) = (M + K) · (M + K - 1) = O(M² + 2MK + K²)   [квадратичний вибух зв'язків FSM]
```

![Ієрархічна структура дерева поведінки автономного дрона](/root/sys/sys-dron/derevo-povedinky/img/drone-behavior-tree-structure.svg)
*Ієрархічна структура дерева поведінки автономного дрона: корінь у вигляді реактивного селектора (Fallback) безперервно оцінює безпекові гілки (Failsafe та реактивне ухилення) перед передачею керування на гілку виконання штатної місії.*

Кожен вузол дерева поведінки є повністю ізольованим програмним блоком і реалізує строго уніфікований контракт. Вузол приймає виклик `Tick()` від свого батьківського вузла, виконує обчислення і повертає батькові один із трьох статусів виконання:

1. `SUCCESS` (Успіх): ціль вузла успішно досягнута (координати точки досягнуто, сенсор пройшов перевірку, замок скидання вантажу спрацював). Батьківський керівний вузол переходить до наступного кроку;
2. `FAILURE` (Невдача): виконання неможливе або предикат хибний (напруга нижче норми, виявлено перешкоду, двигун не запустився). Батьківський вузол активує альтернативну гілку;
3. `RUNNING` (Виконується): дія триває в часі та потребує додаткових польотних циклів (набір висоти, політ до точки маршруту зі швидкістю 15 м/с, виконання процедури розвороту). Дерево призупиняє обхід і повертає керування планувальнику до наступного періоду такту.

Усі вузли дерева діляться на три класи:

```
                       ┌────────────────────────┐
                       │  ВУЗЛИ ДЕРЕВА (NODES)  │
                       └───────────┬────────────┘
         ┌─────────────────────────┼─────────────────────────┐
         ▼                         ▼                         ▼
┌──────────────────┐      ┌──────────────────┐      ┌──────────────────┐
│ КЕРУВАННЯ        │      │ ВИКОНАННЯ        │      │ ДЕКОРАТОРИ       │
│ (Control Nodes)  │      │ (Execution Nodes)│      │ (Decorators)     │
├──────────────────┤      ├──────────────────┤      ├──────────────────┤
│ • Sequence (→)   │      │ • Action [ ]     │      │ • Inverter (NOT) │
│ • Fallback (?)   │      │ • Condition ( )  │      │ • Retry (N)      │
│ • Parallel (⇉)   │      │                  │      │ • Timeout (t)    │
│ • ReactiveSeq    │      │                  │      │ • RateLimiter    │
│ • ReactiveFallbk │      │                  │      │ • BlackboardCheck│
└──────────────────┘      └──────────────────┘      └──────────────────┘
```

#### 1. Вузли керування (Control Nodes)
Вузли керування мають двох або більше дочірніх нащадків і визначають маршрутизацію сигналу `Tick`:

- **Sequence (Послідовність, позначається `→` або `AND`, від латинського *sequentia* — слідування):**
  Моделює ланцюжок обов'язкових послідовних дій. Виконує дітей по черзі зліва направо. Якщо поточна дитина повертає `SUCCESS`, Sequence негайно викликає наступну дитину в тому ж такті. Якщо дитина повертає `RUNNING`, Sequence призупиняє обхід і повертає `RUNNING` своєму батькові. Якщо будь-яка дитина повертає `FAILURE`, весь ланцюжок переривається і негайно повертає `FAILURE`.
- **ReactiveSequence (Реактивна послідовність):**
  На відміну від звичайної послідовності з пам'яттю, реактивна послідовність на кожному такті перезапускає перевірку всіх попередніх умов і дій зліва направо. Якщо дія з індексом `k` повернула `RUNNING`, на наступному такті вузол знову тікає дітей від `0` до `k - 1`. Якщо якась раніше успішна передумова раптом повертає `FAILURE`, активна дія `k` примусово переривається через `Halt()`, а послідовність завершується невдачею.
- **Fallback / Selector (Селектор вибору, позначається `?` або `OR`, від латинського *selectio* — вибір):**
  Моделює систему пріоритетів і резервування. Тікає дітей зліва направо. Якщо дитина повертає `FAILURE`, Fallback негайно передає тік наступному нащадку. Якщо дитина повертає `SUCCESS` або `RUNNING`, Fallback негайно зупиняє перебір і транслює цей статус нагору, не викликаючи менш пріоритетних дітей.
- **ReactiveFallback (Реактивний селектор):**
  Головний інструмент побудови контурів безпеки. На кожному такті опитує дітей, починаючи з нульової (найбільш пріоритетної), навіть якщо на попередньому такті менш пріоритетна дія повертала `RUNNING`. Якщо високорівнева аварійна гілка раптом стає активною, тривала дія в поточній гілці негайно скидається.
- **Parallel (Паралельний вузол, позначається `⇉`):**
  Одночасно активує всіх своїх дітей на кожному такті. Завершується успіхом або невдачею відповідно до налаштованої числової політики:
  - `ThresholdPolicy (M-of-N)`: повертає `SUCCESS`, якщо щонайменше `M` з `N` дітей завершилися з `SUCCESS`, і повертає `FAILURE`, якщо кількість невдалих нащадків перевищила `N - M + 1`;
  - `SequenceParallel`: вимагає успіху **всіх** дітей (`M = N`), невдача хоча б одного негайно скидає решту через `Halt()`;
  - `SelectorParallel`: завершується успіхом при успіху **хоча б одного** нащадка (`M = 1`).

```
СЕМАНТИКА ВУЗЛІВ КЕРУВАННЯ ПРИ ТІКУ:

Sequence (AND):
  Child 1 -> SUCCESS ──► Child 2 -> SUCCESS ──► Child 3 -> RUNNING ──► Результат: RUNNING
  Child 1 -> SUCCESS ──► Child 2 -> FAILURE ─────────────────────────► Результат: FAILURE (зупинка)

Fallback (OR):
  Child 1 -> FAILURE ──► Child 2 -> SUCCESS ─────────────────────────► Результат: SUCCESS (зупинка)
  Child 1 -> FAILURE ──► Child 2 -> FAILURE ──► Child 3 -> RUNNING ──► Результат: RUNNING

Parallel (M-of-N, наприклад 2 з 3):
  Child 1 (RUNNING) + Child 2 (SUCCESS) + Child 3 (SUCCESS) ─────────► Результат: SUCCESS (поріг 2 досягнуто)
```

#### 2. Вузли виконання (Execution Nodes / Leaf Nodes)
Листкові вузли безпосередньо взаємодіють із фізичним або алгоритмічним світом автопілота:

- **Condition (Умова, позначається `( )`):**
  Чистий предикат без побічних ефектів. Зчитує стан бортових систем або сенсорів (наприклад, `battery_voltage > 14.2V`, `gnss_fix == 3D_FIX` чи `lidar_dist < 3.0m`). Виконується миттєво за нульовий час і повертає строго `SUCCESS` або `FAILURE`. Ніколи не повертає `RUNNING`.
- **Action (Дія, позначається `[ ]`):**
  Виконує фізичну чи обчислювальну задачу (генерація векторів тяги, увімкнення відеозапису, побудова траєкторії). Дії поділяються на:
  - **Синхронні (Instant Actions):** виконуються за один такт (наприклад, перемикання реле, встановлення прапорця режиму камери) і повертають `SUCCESS` або `FAILURE`;
  - **Асинхронні (Duration Actions):** тривають багато тактів, повертаючи `RUNNING`. Мають обов'язковий життєвий цикл із трьох фаз:
    - `on_start()` — одноразова ініціалізація ресурсів при першому переході зі стану спокою в роботу;
    - `on_tick()` — циклічний крок обчислення уставки на поточному такті;
    - `on_halt()` — детермінована зупинка та очищення уставок при аварійному або плановому витісненні іншою гілкою.

```
       ЖИТТЄВИЙ ЦИКЛ АСИНХРОННОЇ ДІЇ (ACTION NODE)
 
      ┌───────────────┐
      │  STATUS_IDLE  │◄─────────────────────────────┐
      └───────┬───────┘                              │
              │ Перший виклик Tick()                 │
              ▼                                      │
        [ on_start() ]                               │
              │                                      │
              ▼                                      │
      ┌───────────────┐                              │
 ┌───►│STATUS_RUNNING │                              │
 │    └───────┬───────┘                              │
 │            │                                      │
 │            ├────── Повернено SUCCESS / FAILURE ───┤
 │            │                                      │
 │      [ on_tick() ]                                │
 │            │                                      │
 └────────────┘                                      │
              │                                      │
              ▼ Витіснення пріоритетом               │
         [ on_halt() ] ──────────────────────────────┘
```

#### 3. Декоратори (Decorator Nodes, від латинського *decorare* — прикрашати)
Декоратор має рівно одного нащадка і модифікує його статус завершення або керує динамікою його викликів:

- **Inverter (Інвертор, NOT):** перетворює `SUCCESS` на `FAILURE`, а `FAILURE` на `SUCCESS`. Статус `RUNNING` транслюється без змін;
- **Retry (Повторювач, `N`):** при отриманні `FAILURE` від дитини повторює її виклик до `N` разів перед тим, як остаточно повернути `FAILURE` нагору;
- **Timeout (Таймаут, `t`):** якщо дочірня дія перебуває в стані `RUNNING` довше за заданий інтервал часу `T_max`, декоратор примусово викликає `halt()` для дитини і повертає `FAILURE`;
- **ForceSuccess / ForceFailure:** примусово транслює фіксований статус незалежно від того, як завершилася дитина (використовується для ігнорування некритичних помилок сенсорів);
- **RateLimiter (Обмежувач частоти):** блокує виклики важких обчислювальних дій (наприклад, глобального перепланувальника `A*` чи оптимізатора сплайнів), дозволяючи тікати нащадка не частіше заданої частоти (наприклад, 2 Гц замість 50 Гц основного дерева);
- **BlackboardCheck:** умовний охоронець, який перевіряє значення певної змінної на Дошці Оголошень перед передачею тіку нащадку.

### Механіка Тіку (Tick) та реактивність у контурі 10–50 Гц

У традиційних імперативних архітектурах тривала дія блокує потік виконання функцією на зразок `sleep()` або очікуванням у циклі. У деревах поведінки виконання є строго дискретизованим і неблокуючим. Планувальник автопілота генерує сигнал `Tick()` з фіксованою частотою польотного контуру (типово 20–50 Гц, тобто кожні 20–50 мілісекунд).

![Конвеєр Тіку та обмін даними через Дошку Оголошень](/root/sys/sys-dron/derevo-povedinky/img/bt-tick-and-blackboard.svg)
*Конвеєр обробки тіків та зв'язок із Дошкою Оголошень (Blackboard): на кожному такті планувальника корінь генерує імпульс Tick, опитує предикати безпеки, скидає застарілі дії через Halt і координує видачу уставок у контури автопілота.*

Фундаментальна відмінність між стандартними та реактивними вузлами керування полягає в наявності чи відсутності пам'яті про активного нащадка:

#### Вузли з пам'яттю (SequenceWithMemory, FallbackWithMemory)
Запам'ятовують індекс дитини, яка повернула `RUNNING` на попередньому такті. На наступному такті тік спрямовується безпосередньо цій дитині, минаючи раніше виконані вузли. Це економить мікросекунди процесорного часу, але повністю позбавляє дерево реактивності на раптові зміни навколишнього середовища: якщо під час руху до точки розрядиться батарея, умова перевірки батареї на початку послідовності не буде викликана.

#### Реактивні вузли (ReactiveSequence, ReactiveFallback)
На **кожному** такті обхід графа починається з нульового (найбільш лівого) нащадка, навіть якщо на попередньому такті нащадок з індексом `k > 0` повернув `RUNNING`.

Розглянемо часову шкалу подій, коли дрон летить за маршрутом (гілка 3, `Action: FlyToWaypoint` повертає `RUNNING`), але лідар на черговому такті фіксує перешкоду за два метри:

```
Такт T (Нормальний політ, t = 0.00 с):
  Root ReactiveFallback:
    ├── 1. Failsafe Sequence -> Condition(Bat < 20%): FAIL
    ├── 2. Avoidance Sequence -> Condition(Lidar < 3m): FAIL
    └── 3. Mission Sequence:
          └── Action(FlyToWaypoint): обчислення уставки -> RUNNING
  Результат Root: RUNNING (активна гілка: 3)

Такт T + 20 мс (Поява перешкоди, t = 0.02 с):
  Root ReactiveFallback:
    ├── 1. Failsafe Sequence -> Condition(Bat < 20%): FAIL
    └── 2. Avoidance Sequence:
          ├── Condition(Lidar < 3m): SUCCESS (перешкода виявлена!)
          └── Action(LocalAvoidance): ініціалізація on_start() -> RUNNING
  Спрацював механізм Preemption:
    - Root виявляє зміну активного індексу з 3 на 2;
    - Виклик FlyToWaypoint.halt() -> миттєве обнулення уставки швидкості;
    - Статус FlyToWaypoint скидається в IDLE.
  Результат Root: RUNNING (активна гілка: 2)
```

Цей механізм **реактивного витіснення** (*Reactive Preemption*, від латинського *praeemere* — випереджати) реалізується автоматично завдяки самій топології дерева. Розробнику не потрібно писати жодного рядка коду переходів або обробників переривань між польотом і ухиленням: пріоритети однозначно задаються позицією гілок у кореневому селекторі.

#### Часовий бюджет та аналіз найгіршого часу виконання (WCET)
Оскільки дерево поведінки виконується в контурі реального часу мікроконтролера разом із фільтром Калмана (EKF) та кутовими PID-регуляторами, сумарний час повного спуску по дереву не повинен перевищувати виділений квант часу — зазвичай 200–500 мікросекунд.

Найгірший час виконання (*Worst-Case Execution Time*, WCET) одного тіку обмежується сумою часів обробки вузлів найдовшої гілки обходу:

```
T_tick_wcet ≤ ∑_{i=1}^{D_max} T_node(v_i) + T_halt_max   [верхня межа часу такту]
```

На 32-бітному мікроконтролері ARM Cortex-M7 (тактова частота 480 МГц, STM32H7):
- Виклик `Condition` (читання змінної з кешу L1 + порівняння): `~20–50 нс`;
- Виклик `Action::on_tick` (генерація команди швидкості або запис у регістр): `~100–300 нс`;
- Виклик `Control Node` (ітерація по масиву індексів дітей): `~30–80 нс`.

Для типового дерева місії з глибиною `D_max = 6` та загальною кількістю вузлів `N = 24` повний час виконання такту на частоті 50 Гц становить від 2 до 15 мікросекунд, що займає менше 0.1% доступного бюджету процесорного ядра мікроконтролера.

Для забезпечення жорсткого детермінізму діють два правила:
1. **Заборона важких обчислень у тіку:** Вузли `Condition` повинні лише читати готові дані з пам'яті. Пошук шляху на 3D-сітці або розпізнавання образів із камери мають виконуватися в окремих низькопріоритетних потоках ОС, а дерево лише перевіряє статус готовності фонового обчислення;
2. **Обмеження глибини рекурсії:** Максимальна глибина дерева `D_max` жорстко лімітується на етапі проектування (типово `D_max ≤ 8`), що гарантує відсутність переповнення стека задачі RTOS.

### Архітектура Дошки Оголошень (Blackboard) та потокобезпека

Вузли дерева поведінки є повністю ізольованими: вони не зберігають прямих вказівників один на одного і не викликають методів сусідніх гілок. Для обміну інформацією між умовами, діями та зовнішніми драйверами автопілота застосовується централізоване сховище — **Дошка Оголошень** (*Blackboard*, від англійського *blackboard* — класна дошка).

```
   ┌─────────────────────────────────────────────────────────────┐
   │                ДОШКА ОГОЛОШЕНЬ (BLACKBOARD)                 │
   │  ┌────────────────────────┬─────────────┬────────────────┐  │
   │  │ Ключ (Key)             │ Тип даних   │ Значення       │  │
   │  ├────────────────────────┼─────────────┼────────────────┤  │
   │  │ drone/battery_voltage  │ float       │ 14.85 V        │  │
   │  │ sensor/lidar_min_dist  │ float       │ 1.82 m         │  │
   │  │ mission/current_wp_idx │ uint16_t    │ 4              │  │
   │  │ nav/target_pos_ned     │ Vector3f    │ [120, 45, -30] │  │
   │  │ cmd/velocity_setpoint  │ Vector3f    │ [8.0, 0.0, 0.0]│  │
   │  └────────────────────────┴─────────────┴────────────────┘  │
   └───────▲──────────────────────────▲─────────────────────┬────┘
           │ Запис телеметрії         │ Читання умов        │ Читання
           │ (200 Гц EKF)             │ (dist < 3.0m)       │ уставок
    ┌──────┴──────┐            ┌──────┴──────┐       ┌──────▼──────┐
    │ Сенсори/EKF │            │  Condition  │       │   Action    │
    └─────────────┘            └─────────────┘       └─────────────┘
```

#### Типізовані порти вводу-виводу (Input / Output / Bidirectional Ports)
Взаємодія вузлів із Дошкою Оголошень організована через строго типізовані порти:
- **InputPort<T>:** вхідний порт, з якого вузол читає значення параметра на початку свого тіку;
- **OutputPort<T>:** вихідний порт, у який вузол записує результат своїх обчислень після завершення;
- **BidirectionalPort<T>:** порт двостороннього доступу для модифікації наявного об'єкта.

При побудові місії виконується **перевизначення портів** (*Port Remapping*). Наприклад, універсальний вузол `Action: ComputeTrajectory` має вхідний порт `goal_position` та вихідний порт `computed_path`. При розміщенні в дереві його порт `goal_position` зіставляється з ключем Blackboard `mission/waypoint_coord`.

Це забезпечує повну модульність: один і той самий скомпільований бінарний вузол навігації можна використовувати в дереві для польоту до точки місії, для польоту в зону скидання вантажу чи для польоту на домашній майданчик, просто прив'язавши його вхідний порт до різних ключів Дошки Оголошень.

#### Потокобезпека та механізми обміну даними
У реальному автопілоті сенсорний потік EKF оновлює вектор стану на високій частоті (100–200 Гц), тоді як дерево рішень тікає на частоті 20–50 Гц, а планувальник траєкторій може працювати на частоті 2 Гц. Якщо кілька потоків одночасно читають і записують складені багатобайтові структури даних (наприклад, матрицю коваріацій або масив точок шляху), виникає загроза розірваного читання (*torn read*).

Для захисту даних застосовуються три підходи:

1. **М'ютекси та спінлоки (Mutexes / Spinlocks):** Класичне блокування. Проте на RTOS використання м'ютексів у високочастотному контурі загрожує інверсією пріоритетів (*Priority Inversion*), коли низькопріоритетний вузол логування блокує високопріоритетний контур стабілізації;
2. **Подвійна буферизація (Double-Buffering):** Сховище містить два буфери (Front і Back) та атомарний вказівник. Потік запису наповнює Back-буфер, після чого однією атомарною інструкцією `atomic_exchange` міняє буфери місцями. Читачі завжди працюють із консистентним Front-буфером без очікування;
3. **Read-Copy-Update (RCU):** Читачі звертаються до даних за вказівником без будь-яких блокувань. Потік запису створює копію структури, оновлює її та атомарно перемикає вказівник. Стара копія звільняється лише тоді, коли всі активні читачі завершили свій такт.

#### Ізоляція просторів імен (Scoped Blackboards)
При побудові складних дерев використовують вкладені піддерева (*Subtrees*). Якщо два різних піддерева патрулювання використовують однаковий внутрішній ключ `target_wp`, прямий запис призведе до взаємного псування даних.

Для усунення колізій застосовують ієрархічні простори імен:
- **Global Blackboard:** доступна всім вузлам дерева (глобальні системні змінні: напруга батареї, режим автопілота, координати бази);
- **Tree Blackboard:** область видимості конкретного дерева місії;
- **Scoped Blackboard:** локальна область видимості піддерева. Зовнішні ключі прокидаються всередину піддерева виключно через явне зіставлення портів (*Port Mapping*), подібно до передачі аргументів у функцію.

> 🔧 **Навіщо це в реальній розробці.**
> У великих проектах автономії (наприклад, автономна доставка вантажів або ройове картографування) різні команди розробляють окремі піддерева: одна команда пише алгоритми пошуку посадкового майданчика за камерою, інша — логіку ухилення від птахів і проводів. Завдяки типізованим портам та ізольованим просторам Blackboard ці піддерева можна збирати як незалежні модулі, тестувати на окремих стендах і зшивати в єдину систему без ризику конфлікту глобальних змінних.

### Наскрізний аналіз автономної місії: 5 польотних сценаріїв

Для практичного розуміння того, як топологія дерева поведінки виключає людські помилки при проектуванні, розглянемо повний цикл автономної місії дрона-кур'єра, оснащеного 3D-лідаром, оптичною камерою точної посадки та резервним парашутом.

```
                  ┌─────────────────────────────────────────┐
                  │    Root: ReactiveFallback (Селектор)    │
                  └────────────────────┬────────────────────┘
       ┌───────────────────────────────┼───────────────────────────────┐
       ▼                               ▼                               ▼
┌──────────────┐                ┌──────────────┐                ┌──────────────┐
│  Failsafe →  │                │  Avoidance → │                │  Mission →   │
│(Аварійний)   │                │ (Ухилення)   │                │ (Штатна)     │
└──────┬───────┘                └──────┬───────┘                └──────┬───────┘
  ┌────┴────┐                      ┌───┴───┐                  ┌────────┼────────┐
  ▼         ▼                      ▼       ▼                  ▼        ▼        ▼
(Bat<14V) [LandNow]            (Dist<3m) [AvoidPath]       [Takeoff] [Survey⇉] [LandMark]
                                                                       ┌───┴───┐
                                                                       ▼       ▼
                                                                  [FlyWp] [TrackGimbal]
```

#### Сценарій 1: Штатне виконання місії
1. Кореневий `ReactiveFallback` запускає тік;
2. Гілка 1 (`Failsafe`) тікає умову `Bat < 14V` — напруга 15.6 В, умова повертає `FAILURE`;
3. Гілка 2 (`Avoidance`) тікає умову `Dist < 3m` — дистанція 8.0 м, умова повертає `FAILURE`;
4. Гілка 3 (`Mission`) активується. Вузол `Takeoff` завершується з `SUCCESS` після набору висоти 30 метрів;
5. Запускається паралельний вузол `Survey`: дія `FlyWp` веде дрон за координатами зі швидкістю 12 м/с (`RUNNING`), а дія `TrackGimbal` паралельно орієнтує камеру на цільовий об'єкт (`RUNNING`);
6. Дерево стабільно повертає `RUNNING` на кожному такті 50 Гц.

#### Сценарій 2: Раптове виявлення перешкоди (будівельний кран)
1. Під час польоту між точками 4 і 5 лідар фіксує металоконструкцію на відстані 2.4 м;
2. На черговому такті планувальника (період 20 мс) кореневий `ReactiveFallback` опитує дітей зліва направо;
3. Гілка 1 (`Failsafe`): умова `Bat < 14V` повертає `FAILURE`;
4. Гілка 2 (`Avoidance`): умова `Dist < 3m` повертає `SUCCESS`!
5. Гілка 2 активує дію `AvoidPath` (обхід по траєкторії динамічного вікна DWA). Дія повертає `RUNNING`;
6. `ReactiveFallback` фіксує зміну активної гілки з 3 (`Mission`) на 2 (`Avoidance`) і автоматично викликає `halt()` для всієї підгілки `Mission`;
7. Дія `FlyWp.halt()` миттєво обнуляє вектор горизонтальної швидкості та переводить автопілот у режим гальмування;
8. Дрон огинає кран за новою локальною траєкторією. Коли перешкода залишається позаду (дистанція > 3.5 м з урахуванням гістерезису), умова `Dist < 3m` повертає `FAILURE`, і дерево безшовно повертається до гілки 3, продовжуючи політ до поточної точки маршруту.

#### Сценарій 3: Подвійна відмова (перешкода + критичний розряд батареї)
1. Під час маневру огинання перешкоди (активна гілка 2) зустрічний порив вітру спричиняє просідання напруги акумулятора до 13.7 В;
2. На наступному такті 50 Гц `ReactiveFallback` починає спуск із нульової дитини;
3. Гілка 1 (`Failsafe`): умова `Bat < 14V` повертає `SUCCESS`!
4. Гілка 1 активує дію `LandNow` (екстрена вертикальна посадка), яка повертає `RUNNING`;
5. `ReactiveFallback` виявляє, що активний індекс змінився з 2 на 1. Відбувається негайний виклик `AvoidPath.halt()`, маневр ухилення скасовується, і апарат негайно починає детерміноване вертикальне зниження.

#### Сценарій 4: Захист від брязкоту умов (Chattering)
Якщо дистанція до лісу коливається навколо порогу 3.0 м (наприклад, через шуми далекоміра: 2.98 м → 3.02 м → 2.99 м), наївний селектор перемикав би гілки на кожному такті, викликаючи безперервні виклики `halt()` та посмикування моторів.

У деревах поведінки це вирішується гістерезисними предикатами або фільтрацією на рівні Дошки Оголошень:
- Поріг спрацьовування умови тривоги: `dist < 2.8 м`;
- Поріг скидання умови тривоги: `dist > 3.6 м`.
Це гарантує стійкість системи прийняття рішень до шумів вимірювань.

#### Сценарій 5: Втрата супутників GNSS та радіоглушіння
1. При попаданні в зону дії засобів радіоелектронної боротьби EKF фіксує втрату супутникового фіксу (`gnss_fix == NO_FIX`);
2. Умова `IsGnssValid` повертає `FAILURE` у підгілці глобальної навігації;
3. Селектор навігації `Fallback` перемикає джерело позиції на резервне піддерево `VisualOdometryNavigation` (оптичний потік та візуально-інерціальна одометрія VIO);
4. Дрон продовжує політ без використання супутникових координат.

### Інтеграція з навігаційним стеком: ROS 2 Nav2 та BehaviorTree.CPP v4

У сучасних автономних робототехнічних комплексах стандартом де-факто є фреймворк **BehaviorTree.CPP v4**, інтегрований у навігаційний стек **ROS 2 Navigation2 (Nav2)**.

```
       XML-КОНФІГУРАЦІЯ ДЕРЕВА (mission_tree.xml)
                         │
                         ▼
           ╔═══════════════════════════╗
           ║    BehaviorTree.CPP v4    ║◄──── Groot 2 (ZeroMQ відладка)
           ║  (Рушій прийняття рішень) ║
           ╚═════════════╤═════════════╝
                         │ ROS 2 Action Clients
       ┌─────────────────┼─────────────────┐
       ▼                 ▼                 ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ Nav2 Planner │  │ Nav2 Control │  │ Autopilot    │
│ Server (A*)  │  │ Server (TEB) │  │ MAVLink/DDS  │
└──────────────┘  └──────────────┘  └──────────────┘
```

#### 1. Декларативний опис структури в XML
Дерево поведінки не компілюється монолітно в коді, а завантажується динамічно з XML-файлу під час старту системи:

```xml
<root BTCPP_format="4">
    <BehaviorTree ID="DroneAutonomousMission">
        <ReactiveFallback name="RootSafetySelector">
            <!-- Пріоритет 1: Аварійний контур -->
            <Sequence name="BatteryFailsafe">
                <Condition ID="IsBatteryLow" threshold="14.0"/>
                <Action ID="ExecuteEmergencyLand" descent_rate="0.8"/>
            </Sequence>

            <!-- Пріоритет 2: Реактивне ухилення -->
            <Sequence name="ObstacleAvoidance">
                <Condition ID="IsObstacleClose" min_distance="3.0"/>
                <Action ID="ComputeAvoidanceVector" output_vel="{avoid_vel}"/>
            </Sequence>

            <!-- Пріоритет 3: Штатний політ -->
            <Sequence name="StandardMission">
                <Action ID="Takeoff" altitude="30.0"/>
                <Action ID="NavigateThroughWaypoints" path="{global_path}"/>
            </Sequence>
        </ReactiveFallback>
    </BehaviorTree>
</root>
```

#### 2. Динамічні плагіни дій автопілота
Кожен тип вузла компілюється як динамічна бібліотека (`.so` або `.dll`) і реєструється на фабриці рушія `BehaviorTreeFactory`. Вузол дії транслює тік дерева в асинхронний виклик `ROS 2 Action Client`:
- При отриманні першого тіку вузол надсилає запит на дію `NavigateToPose.send_goal()`;
- Поки ціль обробляється навігаційним сервером, вузол перевіряє зворотний зв'язок `feedback` і повертає `NodeStatus::RUNNING`;
- Якщо гілка витісняється реактивним селектором, рушій викликає `halt()`, який негайно надсилає `NavigateToPose.cancel_goal()`, скидаючи низькорівневі регулятори автопілота.

#### 3. Візуальне налагодження в реальному часі через Groot 2
Фреймворк BehaviorTree.CPP підтримує сервер інтроспекції через ZeroMQ. Інженер підключає графічну утиліту **Groot 2** до працюючого на борту дрона процесу:
- На екрані в реальному часі відображається дерево, де активні вузли підсвічуються помаранчевим (`RUNNING`), успішні — зеленим (`SUCCESS`), а заблоковані — червоним (`FAILURE`);
- Можна в реальному часі переглядати значення будь-якого ключа Дошки Оголошень;
- Можна вручну інжектувати збої (наприклад, змінити прапорець `IsBatteryLow`) для перевірки реакції системи безпеки.

### Порівняльний інженерний аналіз: FSM, HFSM та Behavior Tree

| Критерій порівняння | Скінченний автомат (FSM) | Ієрархічний автомат (HFSM) | Дерево поведінки (BT) |
|---|---|---|---|
| **Масштабованість складності** | Критична (`O(N²)` переходів) | Середня (локалізація в супер-станах) | Висока (лінійна `O(N)` за кількістю вузлів) |
| **Зв'язність компонентів** | Жорстка (стан знає адресатів переходів) | Жорстка в межах рівня ієрархії | Нульова (вузли взаємодіють через Blackboard) |
| **Реактивне витіснення** | Складне (вимагає ручного опитування подій) | Складне (проблема відновлення підстанів) | Вбудоване (реактивний тік від кореня) |
| **Повторне використання** | Практично неможливе | Обмежене супер-станами | Повне (вузли як незалежні будівельні блоки) |
| **Паралельне виконання дій** | Вимагає окремого автомата синхронізації | Обмежене ортогональними регіонами | Рідне через вузли `Parallel` |
| **Візуальне налагодження** | Граф станів із перевантаженими зв'язками | Вкладені діаграми переходів | Ієрархічне дерево з колірною індикацією статусів |
| **Оверхед на пам'ять і стек** | Мінімальний (1 байт поточного стану) | Малий (стек супер-станів) | Середній (масив вузлів + порти Blackboard) |

```cpp
#include <cstdint>
#include <string_view>
#include <optional>
#include <span>
#include <array>

namespace autopilot::bt {

enum class NodeStatus : uint8_t {
    Success = 0,
    Failure,
    Running
};

struct DroneTelemetry {
    float battery_voltage{15.2f};
    float obstacle_distance{10.0f};
    bool geofence_breached{false};
};

class INode {
public:
    virtual ~INode() = default;
    [[nodiscard]] virtual NodeStatus tick(DroneTelemetry& telemetry) noexcept = 0;
    virtual void halt(DroneTelemetry& telemetry) noexcept = 0;
};

class LowBatteryCondition final : public INode {
public:
    [[nodiscard]] NodeStatus tick(DroneTelemetry& telemetry) noexcept override {
        return (telemetry.battery_voltage < 14.0f) ? NodeStatus::Success : NodeStatus::Failure;
    }

    void halt(DroneTelemetry&) noexcept override {}
};

class EmergencyLandAction final : public INode {
public:
    [[nodiscard]] NodeStatus tick(DroneTelemetry&) noexcept override {
        /* Формування команди аварійного зниження Vz = -0.5 м/с */
        return NodeStatus::Running;
    }

    void halt(DroneTelemetry&) noexcept override {
        /* Очищення прапорців аварійної посадки */
    }
};

class CruiseMissionAction final : public INode {
public:
    [[nodiscard]] NodeStatus tick(DroneTelemetry&) noexcept override {
        /* Проходження сегменту місії за вектором швидкості */
        return NodeStatus::Running;
    }

    void halt(DroneTelemetry&) noexcept override {
        /* Скидання уставки горизонтальної швидкості до зависання */
    }
};

template <size_t MaxChildren>
class ReactiveFallback final : public INode {
public:
    void add_child(INode* child) noexcept {
        if (count_ < MaxChildren && child != nullptr) {
            children_[count_++] = child;
        }
    }

    [[nodiscard]] NodeStatus tick(DroneTelemetry& telemetry) noexcept override {
        for (size_t i = 0; i < count_; ++i) {
            const auto status = children_[i]->tick(telemetry);

            if (status == NodeStatus::Running) {
                if (running_idx_.has_value() && *running_idx_ > i) {
                    children_[*running_idx_]->halt(telemetry);
                }
                running_idx_ = i;
                return NodeStatus::Running;
            }

            if (status == NodeStatus::Success) {
                if (running_idx_.has_value() && *running_idx_ != i) {
                    children_[*running_idx_]->halt(telemetry);
                }
                running_idx_.reset();
                return NodeStatus::Success;
            }
        }

        running_idx_.reset();
        return NodeStatus::Failure;
    }

    void halt(DroneTelemetry& telemetry) noexcept override {
        if (running_idx_.has_value()) {
            children_[*running_idx_]->halt(telemetry);
            running_idx_.reset();
        }
    }

private:
    std::array<INode*, MaxChildren> children_{};
    size_t count_{0};
    std::optional<size_t> running_idx_{std::nullopt};
};

} // namespace autopilot::bt
```

### Архітектурний висновок

Перехід від скінченних автоматів до дерев поведінки не був зміною стилю програмування — це була математична необхідність подолання комбінаторного глухого кута. Розділивши прийняття рішень на композиційні вузли керування, ізольовані листки дій і спільну дошку оголошень, Behavior Tree перетворило складну автономію дронів із заплутаного графу непередбачуваних переходів `O(N²)` на детерміновану, модульну та масштабовану ієрархію `O(N)`.
