# ⚙️ Контракт HAL у коді: чистий інтерфейс і змінний бекенд

## Задача

Стаття обіцяє багато: один політний код біжить на десятках плат і навіть у симуляторі, а будь-який шар можна замінити, не чіпаючи решти. Слова «контракт» та «інтерфейс» звучать гарно — але що це **в коді**? Що саме компілюється в прошивку, коли драйвер під STM32 і драйвер під Linux дають верхньому коду «однаковий» порт? І чому верхній код можна **скомпілювати один раз**, а підставляти різне залізо? Поки не побачиш сам механізм мовою C++, переносність лишається магією. Мета — на дрібному, але справжньому прикладі (послідовний порт `UARTDriver`) показати, з чого зроблений шар абстрагування заліза й де в ньому ховаються граблі.

## Ідея

Контракт у C++ — це **клас із суто віртуальними методами** (англ. *pure virtual*, метод без тіла, позначений `= 0`). Такий клас не вміє нічого сам; він лише оголошує, які виклики **зобов'язана** надати реалізація. Саме так влаштований `AP_HAL`: майже весь він — заголовки з порожніми інтерфейсами, без жодного рядка робочого коду. Весь верхній код залежить **тільки** від цих інтерфейсів.

Конкретний **бекенд** під плату успадковує інтерфейс і дає тілам методів реальний зміст: на STM32 `write()` штовхає байт у регістр периферії UART, на Linux — у файловий дескриптор `/dev/ttyS*`, у симуляторі — у мережеву трубу до моделі апарата. Верхній код тримає **вказівник на інтерфейс** (`AP_HAL::UARTDriver*`) і не знає, на який саме об'єкт той вказівник дивиться.

Розрулює це механізм C++ під назвою **таблиця віртуальних методів** (англ. *vtable*): у кожного об'єкта з віртуальними методами є прихований покажчик на таблицю адрес його реальних тіл. Виклик `port->write(b)` не «зашитий» на етапі компіляції — програма під час виконання дивиться в таблицю того об'єкта, що лежить за вказівником, і стрибає на потрібне тіло. Тому той самий машинний код виклику веде то в регістр STM32, то в сокет SITL — залежно лише від того, якого нащадка туди поклали. Звідси й переносність: тип вказівника однаковий, таблиця — різна; підміна заліза — це підстановка іншого нащадка за тим самим вказівником, без жодної правки у верхньому коді.

Той самий прийом дає й **резервування**: фронтенд (наприклад, `AP_GPS`) тримає масив вказівників на кілька бекендів-драйверів і перемикається між ними при відмові — бо для нього всі вони на вигляд однаковий інтерфейс. Три фізично різні приймачі GNSS виглядають для верху як три однакові `UARTDriver*`, тож вибір справного зводиться до зсуву індексу в масиві.

А ось **верхній код** — той, що пише MAVLink чи читає GNSS. Він знає **лише** інтерфейс і нічого — про плату. Той самий об'єктний файл лягає і в прошивку, і в симулятор:

```cpp
// Верхній шар: бачить тільки AP_HAL::UARTDriver*. Скомпільований один раз.
void send_heartbeat(AP_HAL::UARTDriver *port) {
    const uint8_t msg[] = { 0xFE, 0x09, /* …решта пакета MAVLink… */ };
    for (uint8_t i = 0; i < sizeof(msg); i++) {
        port->write(msg[i]);          // чиє тіло? вирішить таблиця віртуальних
    }                                 // методів — STM32, Linux чи SITL
}
```

Який саме бекенд опиниться за вказівником — вирішує **збірка під плату**: при старті HAL створює потрібного нащадка й роздає верхньому коду його адресу. Зміна цілі (`./waf configure --board CubeOrange` проти `--board sitl`) міняє лише цей вибір — верхній код перекомпілюється без жодної правки.

Резервування виходить тим самим прийомом — масив вказівників на інтерфейс і вибір основного:

```cpp
// Фронтенд тримає кілька бекендів за одним інтерфейсом і обирає справний.
AP_HAL::UARTDriver *sensors[3];       // три однотипні джерела
uint8_t primary = 0;
// при відмові основного — просто зсунути індекс; тип усюди однаковий
if (sensors[primary]->available() == 0 && health_bad(primary)) {
    primary = pick_healthy(sensors, 3);
}
```

## Пастки

- **Забутий `override`.** Якщо сигнатура методу в бекенді розійшлася з інтерфейсом (інший тип аргументу), без `override` компілятор мовчки заведе **новий** метод, а віртуальний лишиться чистим — об'єкт не можна буде створити або викликатиметься не те. `override` змушує компілятор перевірити, що метод справді перекриває контракт.
- **Невіртуальний деструктор.** Верхній код тримає `UARTDriver*`; якщо видаляти об'єкт через цей вказівник, а деструктор базового класу **не** віртуальний — тіло бекенда не відпрацює (витік ресурсу плати). Тому деструктор інтерфейсу завжди `virtual`.
- **Виклик до ініціалізації HAL.** Вказівник на бекенд існує лише після того, як HAL його створив на старті. Звернення до порту з конструктора глобального об'єкта (до запуску HAL) — звернення за нульовим вказівником і падіння. Тому весь доступ до заліза йде **після** ініціалізації HAL, не з конструкторів статичних об'єктів.
- **«Протікання» бекенда у верх.** Якщо у верхній код просочився тип `UARTDriver_ChibiOS` чи виклик, якого немає в інтерфейсі, переносність зламано: під SITL воно не збереться. Дисципліна проста — верх бачить **лише** `AP_HAL::`, ніколи конкретного нащадка.
- **Ціна віртуального виклику.** Кожен виклик через інтерфейс — це стрибок за таблицею віртуальних методів, трохи дорожчий за прямий. На гарячих шляхах (читання IMU щотакту) це враховують, але для портів і шин виграш переносності цю крихту перекриває.
