# 📋 Контракт опису виконавчих механізмів: ключі схеми, номери функцій, поля команд

Один JSON-файл виду `COMP_METADATA_TYPE_ACTUATORS` (5), дві команди MAVLink і наскрізна нумерація функцій — це весь контракт, за яким апарат розповідає станції, з чого він складається й куди що припаяно, а станція показує сторінку налаштування, нічого про цей апарат не знаючи наперед. Числа й імена ключів тут звірені зі схемою `component_metadata/actuators.schema.json` і прикладом `actuators.example.json` із репозиторію MAVLink, із `common.xml`, із генератора PX4 `Tools/module_config/generate_actuators_metadata.py` разом із `src/lib/mixer_module/output_functions.yaml` і `src/modules/control_allocator/module.yaml`, а також із коду QGroundControl у `src/Vehicle/Actuators/`. Ними можна користуватися як специфікацією: писати власний генератор описів, читати чужий опис або надсилати команди перевірки без застосунку.

Доставляє файл [підсистема відомостей про компонент](topic:sys-dron/component-information): апарат оголошує адресу опису в загальному покажчику, станція викачує його через MAVFTP або з мережі й розпаковує. Формат — звичайний [JSON](topic:sf-data/json-format); майже кожен ключ у ньому зрештою вказує на [параметр апарата](topic:sys-dron/parameter-manager), тож опис — це не дані, а схема доступу до даних, які й так лежать у параметрах.

## Верхній рівень

| Ключ | Тип | Обов'язковий за схемою | Що робить станція |
|---|---|---|---|
| `version` | ціле, за схемою **≥ 2** | **так** | **не читає взагалі** |
| `show-ui-if` | умова | ні | показувати чи ховати всю сторінку |
| `outputs_v1` | масив | **так** | групи виходів → таблиця розпаяння |
| `functions_v1` | об'єкт | **так** | словник функцій → переліки в списках і в перевірці |
| `mixer_v1` | об'єкт | **так** | геометрія, межі перевірки, правила |
| `translation` | об'єкт | ні | не читає (переклади їдуть окремим файлом) |

Перший рядок вартий уваги двічі. Схема вимагає `version` не менше двох, а генератор PX4 безумовно пише `"version": 1` — те саме число стоїть і в еталонному прикладі поруч зі схемою. Тобто **справжні описи не відповідають власній схемі за першим же ключем**. Наслідків немає рівно тому, що станція, отримавши файл, перевіряє його схемою лише заради журналу:

```cpp
// CompInfoActuators::setJson()
if (!JsonSchemaValidator::validate(jsonDoc, QStringLiteral(":/json/component_metadata/actuators.schema.json"), schemaError)) {
    qCWarning(CompInfoActuatorsLog) << "Metadata json schema validation failed: compid:" << compId << schemaError;
}
vehicle->setActuatorsMetadata(compId, metadataJsonFileName, jsonDoc);   // ← далі однаково
```

Невідповідність схемі не зупиняє нічого. Єдина справжня перевірка — наявність трьох ключів у розборі, і вона зроблена так:

```cpp
QJsonValue outputsJson = obj.value("outputs_v1");
...
if (outputsJson.isNull() || functionsJson.isNull() || mixerJson.isNull()) { ... return false; }
```

`QJsonObject::value()` для відсутнього ключа повертає значення типу *Undefined*, а `isNull()` істинний лише для типу *Null*. Тобто ця перевірка ловить **явний `"mixer_v1": null`**, а не пропущений ключ: файл без `mixer_v1` пройде далі й дасть порожню геометрію. Практичний висновок для того, хто генерує опис: обрізаний або недописаний файл дасть не чесну відмову, а половину сторінки.

## Умова: одна граматика на шість місць

Умова (`condition`) — це порівняння одного параметра з цілим числом, і саме нею опис вмикає й вимикає власні частини.

```
<ім'я параметра><операція><ціле зі знаком>
операції: >  >=  ==  !=  <  <=
приклади: SYS_CTRL_ALLOC==1     PWM_AUX_TIM0<-1     UAVCAN_ENABLE>=2
```

| Де стоїть | Ключ | Що вмикає |
|---|---|---|
| корінь файлу | `show-ui-if` | усю сторінку виконавчих механізмів |
| група виходів | `show-subgroups-if` | усі підгрупи групи |
| параметр каналу | `show-if` | одне поле в усіх каналах підгрупи |
| дія підгрупи | `supported-if` | доступність дії |
| функція | `note.condition` | показ примітки під функцією |
| варіант геометрії | `option` | вибір цього варіанта |

Поведінка станції на крайніх випадках несиметрична, і це варто знати наперед:

| Рядок умови | Результат |
|---|---|
| ключа немає або порожній рядок | **істина** |
| `true` / `false` | істина / хиба |
| порівняння, параметр існує й має тип `bool` або `int32` | власне порівняння |
| порівняння, параметр не існує | **хиба** |
| порівняння, параметр існує, але тип не `bool`/`int32` (наприклад, float) | **хиба** |
| рядок не розібрався регулярним виразом | **істина** |

Друкарська помилка в умові робить її **завжди істинною**, а посилання на неіснуючий чи речовинний параметр — **завжди хибним**. Обидва випадки мовчазні; видно їх лише з категорії журналу `Vehicle.Actuators.Common`.

Ще одна тонкість: схема дозволяє в імені параметра крапку й обмежує його шістнадцятьма символами, а розбирач станції (`^([0-9A-Za-z_-]+)([\!=<>]+)(-?\d+)$`) крапки не приймає й довжини не обмежує. Ім'я з крапкою пройде схему й стане «завжди істиною» в станції.

## `outputs_v1`: групи, підгрупи, канали

Група виходів — фізична колодка або шина; підгрупа — набір каналів, що поділяють спільне налаштування (для PWM це апаратний таймер, для CAN — окреме повідомлення); канал — один контакт.

**Група**

| Ключ | Тип | Обов'язковий | Зміст |
|---|---|---|---|
| `label` | рядок | **так** | підпис групи (`MAIN`, `AUX`, `UAVCAN`) |
| `subgroups` | масив | **так** | підгрупи |
| `parameters` | масив | ні | налаштування всієї групи (швидкість шини тощо) |
| `show-subgroups-if` | умова | ні | коли показувати канали групи |

Елемент `parameters` групи: `name` (обов'язковий, ≤16 символів), `label` (обов'язковий), `function` — тільки `enable`. Параметр із `function: "enable"` станція виймає з переліку й ставить окремо як вимикач групи.

**Підгрупа**

| Ключ | Тип | Обов'язковий | Зміст |
|---|---|---|---|
| `per-channel-parameters` | масив | **так** | шаблон рядка таблиці |
| `channels` | масив | **так** | самі канали |
| `label` | рядок | ні (потрібен, якщо підгруп кілька) | підпис (`AUX 1-4`) |
| `parameters` | масив | ні | налаштування підгрупи |
| `supported-actions` | об'єкт | ні | разові накази регулятору |

Елемент `parameters` підгрупи має `function` лише `primary`: такий параметр станція виносить у заголовок підгрупи замість підпису (для PWM це `PWM_MAIN_TIM0` — вибір протоколу таймера). Прибирає вона його з переліку безумовно, і **останній `primary` витісняє попередній**, а не додається поруч.

**Канал** — це рівно дві речі:

| Ключ | Тип | Обов'язковий | Зміст |
|---|---|---|---|
| `label` | рядок | **так** | підпис контакту (`MAIN 3`) |
| `param-index` | ціле | **так** | число, яке підставляється замість `${i}` |

**Параметр каналу** (спільна форма `per-item-parameters`, тут із власними обмеженнями)

| Ключ | Тип | Обов'язковий | Зміст |
|---|---|---|---|
| `label` | рядок | **так** | підпис стовпця |
| `name` | рядок | **так** | ім'я параметра, може містити `${i}` |
| `function` | рядок | ні | `function` · `disarmed` · `min` · `max` · `failsafe` |
| `index-offset` | ціле | ні (0) | додається до `param-index` перед підстановкою |
| `show-as` | рядок | ні | `bitset` · `true-if-positive` |
| `advanced` | булеве | ні | ховати, доки не ввімкнено «додаткові налаштування» |
| `show-if` | умова | ні | коли показувати стовпець |

Підстановка робиться так:

```
ім'я параметра = name, у якому "${i}" замінено на (param-index + index-offset)
```

**Умова: канал `MAIN 3` (`param-index` = 3), два стовпці однієї підгрупи.**

```
name = "PWM_MAIN_FUNC${i}", index-offset = 0   →  3 + 0  = 3   →  PWM_MAIN_FUNC3
name = "PWM_MAIN_REV",      index-offset = −1  →  3 − 1  = 2   →  PWM_MAIN_REV, біт 2
```

Другий рядок показує, навіщо тут `show-as: "bitset"`: одне ціле число зберігає прапорці всіх каналів, а `index-offset` перетворює номер каналу на номер біта. Прапорець у таблиці — це [окремий факт](topic:sys-dron/fact-system), що читає й пише свій біт у спільному параметрі.

Ключ `function` у параметрі каналу потрібен не для показу, а для роботи: за `function: "function"` станція знаходить параметр призначення — саме його вона перебирає, шукаючи повтори й непризначені функції, і саме він живить перелік дій.

**Стандартні параметри PWM-каналу PX4** (префікс `PWM_MAIN` або `PWM_AUX`; межі — з `src/drivers/pwm_out/module.yaml`)

| Параметр | `function` | Межі | Усталене |
|---|---|---|---|
| `PWM_MAIN_FUNC${i}` | `function` | перелік із `functions_v1` | — |
| `PWM_MAIN_DIS${i}` | `disarmed` | 800…2200 | 1000 |
| `PWM_MAIN_MIN${i}` | `min` | 800…1400 | 1000 |
| `PWM_MAIN_CENT${i}` | — | 800…2200 | — |
| `PWM_MAIN_MAX${i}` | `max` | 1600…2200 | 2000 |
| `PWM_MAIN_FAIL${i}` | `failsafe` | 800…2200 | — (`advanced`) |
| `PWM_MAIN_REV` | — | бітове поле, `index-offset` −1 | — |

Параметр підгрупи `PWM_MAIN_TIM<n>` (із `function: "primary"`) задає протокол усім каналам свого таймера:

```
−8 BDShot150   −7 BDShot300   −6 BDShot600
−5 DShot150    −4 DShot300    −3 DShot600
−1 OneShot
50 100 200 400  — PWM відповідної частоти (усталено 400); будь-яке число >0 — власна частота
```

**Дії підгрупи** — `supported-actions`. Ключі фіксовані схемою, значення описує, коли дія доступна:

| Ключ дії | `ACTUATOR_CONFIGURATION` | Що робить регулятор |
|---|---|---|
| `beep` | 1 `BEEP` | пікнути зараз |
| `3d-mode-on` | 2 `3D_MODE_ON` | увімкнути реверсивний режим **назавжди** |
| `3d-mode-off` | 3 `3D_MODE_OFF` | вимкнути реверсивний режим |
| `set-spin-direction1` | 4 `SPIN_DIRECTION1` | задати напрямок обертання 1 |
| `set-spin-direction2` | 5 `SPIN_DIRECTION2` | задати протилежний напрямок |

Кожне значення — об'єкт із двох необов'язкових полів: `supported-if` (умова) і `actuator-types` (перелік типів механізмів; порожній перелік означає «будь-який»). Станція показує дію, якщо канал має призначену функцію, умова істинна й тип цієї функції входить у перелік. Це не параметри: дії летять на борт [командою](topic:sys-dron/mavlink-commands) `MAV_CMD_CONFIGURE_ACTUATOR` і доходять до [регулятора](topic:hw-motion/esc) вже [цифровим протоколом DShot](topic:com-devices/dshot-protocol) — звідси й умова `PWM_AUX_TIM0<-1` у прикладах: значення таймера менші за −1 — це DShot, а на звичайному PWM таких наказів надіслати нікуди.

## `functions_v1`: словник функцій

Об'єкт, де **ключ — десятковий номер функції в лапках**, а значення описує, як її звати й що з нею можна.

| Ключ | Тип | Обов'язковий | Зміст |
|---|---|---|---|
| `label` | рядок | **так** | людський підпис (`Motor 1`) |
| `exclude-from-actuator-testing` | булеве | ні (хиба) | не пропонувати цю функцію до перевірки |
| `note` | об'єкт | ні | `condition` + `text`: примітка під функцією, коли умова істинна |

Ключ `"0"` особливий і завжди означає «вимкнено». Запис **без `label` станція мовчки викидає** — функція зникає і з випадного списку каналу, і з переліку перевірки.

Прапорець `exclude-from-actuator-testing` існує через функції, які фізично нічим не рухають: захоплення кадру камери чи вхід імпульсів часу займають контакт, але «покрутити» їх не можна. Такі функції призначаються на канал нарівні з рештою, а в перелік перевірки не потрапляють.

## Нумерація функцій PX4

Джерело — `output_functions.yaml`; підписи генератор творить із імені, замінюючи підкреслення пробілом і додаючи порядковий номер там, де є `count`.

| Номери | Роль | Підпис |
|---|---|---|
| 0 | вимкнено | `Disabled` |
| 1 · 2 | стала нижня / верхня межа | `Constant Min` · `Constant Max` |
| 101…112 | мотори (12) | `Motor 1`…`Motor 12` |
| 201…215 | серви (15) | `Servo 1`…`Servo 15` |
| 301…306 | периферія, керована ззовні (6) | `Peripheral via Actuator Set 1`… |
| 400 | шасі | `Landing Gear` |
| 401 | парашут | `Parachute` |
| 402…406 | пряме проведення RC: крен, тангаж, газ, рискання, закрилки | `RC Roll`…`RC Flaps` |
| 407…412 | пряме проведення RC, вільні канали (6) | `RC AUX 1`…`RC AUX 6` |
| 420 · 421 · 422 | підвіс: крен, тангаж, рискання | `Gimbal Roll/Pitch/Yaw` |
| 430 | захват | `Gripper` |
| 440 | кероване колесо шасі | `Landing Gear Wheel` |
| 450…453 | ДВЗ: запалювання, дросель, підсмоктувач, стартер | `IC Engine Ignition`… |
| 2000 | спуск затвора камери | `Camera Trigger 1` |
| 2032 | зворотний зв'язок камери | `Camera Capture 1` |
| 2064 | вхід секундного імпульсу | `PPS Input 1` |
| 2070 | вхід тахометра | `RPM Input 1` |

Чотири останні існують **лише на PWM-контактах польотного контролера**, усі мають `exclude-from-actuator-testing` і всі приходять із приміткою на кшталт «спершу ввімкніть це параметром `TRIG_MODE`». Нумерація стабільна за домовленістю: у самому файлі стоїть попередження не міняти індекси вже наявних функцій, бо номер лежить у параметрах зібраних апаратів.

## Дві нумерації в одному полі й зсув на тисячу

MAVLink має власний, значно бідніший перелік `ACTUATOR_OUTPUT_FUNCTION`:

| Номери | Ім'я | Скільки |
|---|---|---|
| 0 | `NONE` | — |
| 1…16 | `MOTOR1`…`MOTOR16` | 16 |
| 33…48 | `SERVO1`…`SERVO16` | 16 |
| ≥ 1000 | зарезервовано під нумерацію конкретного автопілота | — |

Останній рядок і є домовленістю. Станція **завжди** надсилає `1000 + <номер PX4>`, в обох командах:

```cpp
// ActuatorTesting.cc і ActuatorActions.cc — той самий аргумент
1000+function,                    // function
```

Прошивка розбирає поле так (`Commander::handleCommandActuatorTest`):

```cpp
if (actuator_test.function < 1000) {
    const int first_motor_function = 1;    // з MAVLink ACTUATOR_OUTPUT_FUNCTION
    const int first_servo_function = 33;

    if (function >= first_motor_function && function < first_motor_function + MAX_NUM_MOTORS) {        // 1…12
        function = function - first_motor_function + FUNCTION_MOTOR1;                                  // → 101…112
    } else if (function >= first_servo_function && function < first_servo_function + MAX_NUM_SERVOS) { // 33…47
        function = function - first_servo_function + FUNCTION_SERVO1;                                  // → 201…215
    } else {
        return VEHICLE_CMD_RESULT_UNSUPPORTED;
    }
} else {
    actuator_test.function -= 1000;
}
```

**Умова: канал несе `Motor 1`, тобто параметр функції дорівнює 101.**

```
номер функції PX4              = 101
станція надсилає param5        = 101 + 1000  = 1101
прошивка: 1101 ≥ 1000          → віднімає тисячу
функція для виконання          = 1101 − 1000 = 101
```

**Умова: стороння станція шле чистий MAVLink і просить `SERVO16`.**

```
стандартний номер SERVO16      = 48
прошивка: 48 < 1000            → гілка стандартної нумерації
серв у PX4                     = MAX_NUM_SERVOS = 15  →  приймаються 33…47
48 поза діапазоном             → MAV_RESULT_UNSUPPORTED
```

Тобто стандартна нумерація підтримана **частково**: `MOTOR1`…`MOTOR12` і `SERVO1`…`SERVO15` пройдуть, `MOTOR13`…`MOTOR16` і `SERVO16` дадуть відмову, а шасі, парашута чи захвата в стандартній нумерації немає взагалі.

Дві реалізації розбирають поле трохи по-різному, і це видно лише на межі: команда перевірки бере `< 1000` (тобто рівно 1000 стає функцією 0), а драйвер DShot для команди налаштування бере `> 1000` (тобто рівно 1000 не розпізнається й дає `UNSUPPORTED`). Функцію 0 надсилати нема сенсу, тож на практиці розбіжність не болить — але власний генератор чи клієнт краще на неї не спирати.

## `mixer_v1`: типи, геометрії, правила

**Типи механізмів** — `actuator-types`, об'єкт «ім'я → опис». Ім'я довільне, але `motor` і `servo` мають окреме значення: за ними станція розуміє, що малювати на схемі апарата.

| Ключ | Тип | Обов'язковий | Зміст |
|---|---|---|---|
| `values` | об'єкт | **так** | межі повзунка перевірки |
| `function-min` | ціле | **так** (крім `DEFAULT`) | перша функція цього типу |
| `function-max` | ціле | **так** (крім `DEFAULT`) | остання функція цього типу |
| `label-index-offset` | ціле | ні (0) | зсув між індексом і підписом |
| `per-item-parameters` | масив | ні | параметри, спільні для всіх механізмів типу |

Ключ `DEFAULT` обов'язковий і задає межі для всіх функцій, що не потрапили в жоден діапазон, — шасі, парашута, захвата.

**`values` — межі перевірки**

| Ключ | Тип | Обов'язковий | Зміст |
|---|---|---|---|
| `min` · `max` | число −1…1 | **так** | краї повзунка |
| `default` | число −1…1 | ні | усталене положення |
| `default-is-nan` | булеве | ні | усталене — NaN, тобто «відпустити керування» |
| `reversible` | булеве | ні | діапазон можна віддзеркалити в `[−max, −min]` |

Значення для PX4:

```
motor     min 0    max 1    default-is-nan: true     (спокій мотора — вимкнений мотор)
servo     min −1   max 1    default 0                (спокій серви — середина)
DEFAULT   min −1   max 1    default −1
```

Поле `reversible` станція читає й **нікуди не подає** — у переліку механізмів перевірки використані лише `min`, `max` і `default`. Опис реверсивного мотора з поверненим діапазоном на сьогодні нічого не змінює.

**Варіанти геометрії** — масив `config`. Схема допускає три законні форми: перелік із умовами (`option`), рівно один варіант без умови, і **порожній перелік** — це вимикає геометрію взагалі, лишаючи саму таблицю виходів.

| Ключ | Тип | Зміст |
|---|---|---|
| `option` | умова | коли цей варіант чинний (у PX4 — `CA_AIRFRAME==<номер>`) |
| `type` | рядок | тільки `multirotor`; підказка, який малюнок годиться |
| `title` · `help-url` | рядок | підпис і адреса довідки |
| `actuators` | масив | **обов'язковий**: групи механізмів варіанта |

Станція бере **перший** варіант, чия умова істинна, і решту не дивиться.

**Група механізмів варіанта**

| Ключ | Тип | Обов'язковий | Зміст |
|---|---|---|---|
| `group-label` | рядок | **так** | підпис групи (`Motors`) |
| `actuator-type` | рядок | **так** | ім'я з `actuator-types` |
| `count` | рядок або ціле | **так** | ім'я параметра-лічильника **або** стале число |
| `per-item-parameters` | масив | **так** | поля рядка |
| `required` | булеве | ні | без призначення цих функцій апарат не вважається налаштованим |
| `item-label-prefix` | рядок або масив | ні | уточнення підпису: `Left Aileron (Servo 1)` |
| `parameters` | масив | ні | параметри всієї групи |

`count` рядком — це саме те, завдяки чому квадрокоптер і гексакоптер не є різними варіантами: станція читає значення параметра й будує стільки рядків, скільки в ньому написано.

**Поля рядка геометрії** — та сама форма `per-item-parameters`, але з іншим переліком значень `function`:

| `function` | Зміст | Очікуваний тип параметра |
|---|---|---|
| `posx` · `posy` · `posz` | координати, метри від центра ваги | float |
| `axisx` · `axisy` · `axisz` | куди дивиться механізм | float |
| `spin-dir` | напрямок обертання (істина = проти годинникової) | float, `show-as: true-if-positive` |
| `type` | перелік підтипів (наприклад, тип аеродинамічної поверхні) | int32 |
| `reversible` | реверсивний мотор | bool/int32 |

Обов'язковий тут лише `label`; `show-if` схема в геометрії не дозволяє взагалі — умовна видимість поля робиться правилом, а не умовою. Замість `name` поле може мати `value` — масив сталих чисел завдовжки як `count` (або з одного числа на всіх). Так описують нередаговану геометрію: числа показуються, але вводяться в опис, а не в параметри. Довжина, що не збігається з фіксованим `count`, викидає таке поле цілком.

Підстановка `${i}` тут працює **не так, як у виходах**, і плутати їх дорого:

| Звідки поле | Індекс для `${i}` |
|---|---|
| `per-item-parameters` групи геометрії | номер механізму **всередині групи**, від 0, плюс `index-offset` |
| `per-item-parameters` типу механізму | наскрізний номер механізму **цього типу у варіанті**, від 0, плюс `index-offset` |

Різниця видно, коли варіант має дві групи одного типу: у другій групі номер усередині групи знову починається з нуля, а наскрізний номер типу продовжується. Функція механізму, до речі, теж рахується з наскрізного: `function-min + <наскрізний номер типу>`.

Приклад із PX4 (`module.yaml`, ще в підкресленнях):

```yaml
- actuator_type: 'motor'
  count: 'CA_ROTOR_COUNT'
  per_item_parameters:
      standard:
          position: [ 'CA_ROTOR${i}_PX', 'CA_ROTOR${i}_PY', 'CA_ROTOR${i}_PZ' ]
      extra:
        - name: 'CA_ROTOR${i}_KM'
          label: 'Direction CCW'
          function: 'spin-dir'
          show_as: 'true-if-positive'
```

**Правила** — `rules`, масив. Правило перекриває значення й видимість сусідніх полів залежно від вибору в одному полі-перемикачі.

| Ключ | Тип | Обов'язковий | Зміст |
|---|---|---|---|
| `select-identifier` | рядок | **так** | ідентифікатор керівного поля |
| `apply-identifiers` | масив рядків | **так** | ідентифікатори керованих полів, **порядок значущий** |
| `items` | об'єкт | **так** | «значення керівного → масив обмежень» |

Ідентифікатори — довільні рядки; поле геометрії підключається до правила ключем `identifier` у своєму описі. Керівне поле мусить бути цілим (`int32`), керовані — дробовими. **На групу дозволено щонайбільше одне правило**, і станція справді бере лише перше знайдене.

Елемент масиву обмежень (їх має бути рівно стільки, скільки `apply-identifiers`, інакше запис відкидається з попередженням):

| Ключ | Тип | Дія станції |
|---|---|---|
| `min` · `max` | число | підтягнути поточне значення в межі |
| `default` | число | підставити **при зміні** керівного значення |
| `hidden` | булеве | сховати поле |
| `disabled` | булеве | показати, але не дати редагувати |

Ключове в поведінці: `min`/`max` застосовуються завжди, а `default` — **лише коли керівне значення щойно змінилося**, і застосування пише значення в параметр. Тобто вибір у списку типу поверхні мовчки переписує сусідні параметри на борту.

## Джерело в PX4: `module.yaml` → `actuators.json`

Документація PX4 і файли модулів описують те саме іншим написанням, і це головна причина, чому ключі з інструкцій не знаходяться у справжньому файлі. Генератор `generate_actuators_metadata.py` збирає `actuators.json` під час збирання прошивки й дорогою перейменовує:

| У `module.yaml` (підкреслення) | У `actuators.json` (дефіси) |
|---|---|
| `actuator_testing_values` | `values` |
| `default_is_nan` | `default-is-nan` |
| `per_item_parameters` | `per-item-parameters` |
| `index_offset` | `index-offset` |
| `show_as` · `show_if` | `show-as` · `show-if` |
| `select_identifier` · `apply_identifiers` | `select-identifier` · `apply-identifiers` |
| `exclude_from_actuator_testing` | `exclude-from-actuator-testing` |
| `set_spin_direction1` | `set-spin-direction1` |
| `functions: 'Motor'` | `function-min: 101`, `function-max: 112` |

Останній рядок — не перейменування, а обчислення: генератор бере ім'я родини функцій, знаходить її в `output_functions.yaml` і розгортає в пару меж. `label-index-offset` він завжди ставить `1` для всіх типів, крім `DEFAULT`.

## `MAV_CMD_ACTUATOR_TEST` — 310

Наказ покрутити функцію, а не контакт. Специфікація прямо каже, що це наступник `MAV_CMD_DO_MOTOR_TEST`, який адресував вихід за номером.

| Поле | Підпис | Межі | Зміст |
|---|---|---|---|
| `param1` | Value | −1…1 | 1 — максимум у плюс; 0 — центр серви або мінімальна тяга (мотор крутиться); −1 — максимум у мінус (для нереверсивного мотора все, що менше 0, стає NaN); **NaN — відпустити, зупинити** |
| `param2` | Timeout | 0…3 с | термін, після якого вихід повертається до попереднього значення; **0 — повернути негайно** |
| `param3` · `param4` | — | 0 | зарезервовані |
| `param5` | Output Function | `ACTUATOR_OUTPUT_FUNCTION` | номер функції (з PX4 — зі зсувом `1000 +`) |
| `param6` · `param7` | — | 0 | зарезервовані |

Що робить прошивка PX4, отримавши наказ:

| Крок | Поведінка |
|---|---|
| апарат готовий до руху **або** є запобіжний перемикач і його не знято | `MAV_RESULT_DENIED`, наказ не виконується |
| `param2 · 1000` ≤ 0 | дія стає «відпустити керування» |
| термін > 3000 мс | обрізається до 3000 мс |
| функція не розпізналася | `MAV_RESULT_UNSUPPORTED` |
| інакше | `MAV_RESULT_ACCEPTED` і публікація наказу драйверам |

Тут ховається розбіжність зі специфікацією: MAVLink вимагає відповідати на цю команду `MAV_RESULT_TEMPORARILY_REJECTED`, доки апарат готовий до руху, а PX4 відповідає `MAV_RESULT_DENIED`. Клієнт, що розрізняє «зараз не можна» й «ніколи не можна» за кодом відповіді, на PX4 помилиться; станція про це знає й показує різні повідомлення на обидва коди.

**Як тримає наказ станція.** Ключова властивість — наказ не вмикається й вимикається, а щоразу продовжується:

```cpp
// у польоті щонайбільше одна команда; наступну шлють на підтвердження попередньої
sendMavlinkRequest(actuator->function(), _states[_currentState].value, 1.f);  // тримати 1 с
sendMavlinkRequest(actuator->function(), NAN,                          0.f);  // відпустити

// сторожовий таймер станції
_watchdogTimer.setInterval(100);
_watchdogTimer.setSingleShot(false);
// ... якщо значення каналу не оновлювали понад 100 мс — станція сама його зупиняє
```

Тобто контракт з боку клієнта: **оновлюй значення частіше, ніж раз на 100 мс, поки крутиш, і надішли NaN із нульовим терміном, коли закінчив**. Замовкнути — теж законний спосіб зупинитися: борт відпустить вихід сам, найпізніше через три секунди.

**Умова: клієнт просить утримання на 10 с і замовкає одразу після наказу.**

```
термін у param2                = 10 с → 10000 мс
обрізання прошивкою            = min(10000, 3000) = 3000 мс
залишковий рух після мовчання  = 3000 мс
```

**Найкоротший робочий виклик**

```cpp
// покрутити Motor 1 (функція PX4 = 101) на 30 % тяги протягом секунди
vehicle->sendMavCommand(MAV_COMP_ID_AUTOPILOT1, MAV_CMD_ACTUATOR_TEST,
                        true,          // showError
                        0.3f,          // param1: значення
                        1.0f,          // param2: термін, с
                        0, 0,
                        1000 + 101,    // param5: функція зі зсувом
                        0, 0);

// відпустити
vehicle->sendMavCommand(MAV_COMP_ID_AUTOPILOT1, MAV_CMD_ACTUATOR_TEST,
                        true, NAN, 0.0f, 0, 0, 1000 + 101, 0, 0);
```

## `MAV_CMD_CONFIGURE_ACTUATOR` — 311

| Поле | Підпис | Зміст |
|---|---|---|
| `param1` | Configuration | значення `ACTUATOR_CONFIGURATION`: 0 нічого · 1 пікнути · 2 реверсивний режим увімкнути · 3 вимкнути · 4 напрямок 1 · 5 напрямок 2 |
| `param2`…`param4` | — | зарезервовані |
| `param5` | Output Function | номер функції (зі зсувом `1000 +`) |
| `param6` · `param7` | — | зарезервовані |

Виконує наказ драйвер DShot, і його межі значно вужчі за перелік у схемі:

| Обмеження | Наслідок |
|---|---|
| функція мусить бути мотором у діапазоні DShot-каналів | будь-що інше → `MAV_RESULT_UNSUPPORTED` |
| канал мусить бути на виході з DShot-протоколом | на PWM-каналі накази нікуди надіслати |
| нерозпізнане значення `param1` | нічого не надсилається, відповідь `MAV_RESULT_UNSUPPORTED` |
| зміни режиму й напрямку йдуть із прапорцем збереження | записуються **в пам'ять регулятора назавжди** |
| «пікнути» не зберігається | разова дія |

Різниця між останніми двома рядками — це різниця між «спробувати» й «переналаштувати залізо»: чотири з п'яти дій змінюють стан регулятора, який переживе вимкнення живлення, а перевірити результат можна лише покрутивши мотор.

## Пастки контракту

- **`version` ніхто не читає, а схема його не пропускає.** Схема вимагає ≥ 2, генератор PX4 пише 1, станція число ігнорує. Валідація схемою — лише попередження в журналі.
- **Перевірка трьох ключів ловить `null`, а не відсутність.** Відсутній `mixer_v1` дасть порожню геометрію, а не відмову від файлу.
- **Помилка в умові робить її істинною, посилання на неіснуючий параметр — хибним.** Обидва випадки мовчазні, обидва легко переплутати з робочою умовою.
- **Ім'я параметра з крапкою пройде схему й не пройде розбирач станції.** Стане «завжди істиною».
- **`${i}` у виходах і в геометрії рахується від різних індексів.** Номер каналу з `param-index` проти номера механізму від нуля; `index-offset` додається до обох.
- **`default` у правилі пише в параметр.** Вибір у списку типу мовчки міняє сусідні значення й одразу надсилає їх на борт; кнопки «застосувати» немає.
- **Роль без `label` зникає безслідно.** Ні в списку каналу, ні в перевірці, ні в журналі-попередженні.
- **`values.reversible` мертвий.** Ключ читається й ніде не використовується.
- **Стандартна нумерація MAVLink підтримана частково.** `MOTOR13`…`MOTOR16` і `SERVO16` дають `UNSUPPORTED`; шасі, парашута й захвата в ній немає взагалі.
- **Відмова через готовність до руху приходить кодом `DENIED`, а не `TEMPORARILY_REJECTED`.** Специфікація вимагає другого.
- **Термін перевірки обрізає прошивка, а не станція.** Просити більше трьох секунд безглуздо; просити нуль означає «відпусти негайно».
- **Дії налаштування пишуть у пам'ять регулятора.** Реверсивний режим і напрямок обертання переживуть вимкнення живлення; «пікнути» — ні.
