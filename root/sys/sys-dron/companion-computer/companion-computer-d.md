Раптовий запуск згорткової нейромережі чи оптимізації глобального графа поз у задачі SLAM спричиняє стрибок споживання струму одноплатного комп'ютера з 0.8 А до 3.5–5.0 А за кілька десятків мікросекунд. Якщо бортовий комп'ютер (*companion computer*) під'єднаний до спільної шини живлення з політним контролером (*flight controller*, FC), індуктивність джгута та обмежена швидкість реакції імпульсного стабілізатора спричиняють просідання напруги (*brownout*) нижче критичного порога 4.5 В. Мікроконтролер контролера перезавантажується, і апарат миттєво втрачає керування. Одночасно, якщо архітектура зв'язку вимагає синхронного очікування відповідей від операційної системи Linux усередині контуру орієнтації, затримка планувальника задач на 40–80 мс через операції дискового вводу-виводу чи виділення сторінок пам'яті зриває фазу швидкісного контуру кутової швидкості (*Rate PID*), викликаючи розгойдування та звалювання в штопор.

Безпечна інтеграція високого рівня інтелекту на безпілотному апараті вимагає безкомпромісного фізичного, електричного та протокольного розділення двох світів: мікроконтролерного ядра жорсткого реального часу (*hard real-time*), що гарантує фізичне виживання, та багатоядерного Linux-хоста м'якого реального часу (*soft real-time*), що виконує важкі обчислення сприйняття, навігації й планування.

### Апаратне спряження MCU та SBC: архітектура двох плат

Типовий сучасний борт автономного безпілотника будується на тандемі двох обчислювачів:
1. **Політний контролер (FC):** спеціалізована плата на базі 32-бітного мікроконтролера ARM Cortex-M7 (STM32H743/H753, 480 МГц, 2 МБ Flash, 1 МБ SRAM з апаратним блоком операцій із рухомою комою подвійної точності DP-FPU) або Cortex-M4 (STM32F765), що працює під керуванням операційної системи реального часу (RTOS, наприклад NuttX у PX4 або ChibiOS в ArduPilot).
2. **Бортовий комп'ютер (Companion SBC / SOM):** одноплатний комп'ютер (*Single Board Computer*) або системний модуль (*System on Module*), такий як Raspberry Pi CM4 (4x Cortex-A72 @ 1.5 ГГц), NVIDIA Jetson Orin Nano (6x Cortex-A78AE, графічний процесор Ampere з 1024 ядрами CUDA та тензорними ядрами, 20–40 TOPS) або Rockchip RK3588, що працює під керуванням повнофункціональної ОС Linux (Ubuntu Server, Yocto Project із ядром PREEMPT_RT).

![Апаратна архітектура двопроцесорного борту: розподіл функціональних блоків та інтерфейсів](/root/sys/sys-dron/companion-computer/img/dual-board-architecture.svg)
*Апаратне спряження політного контролера (STM32H7) та бортового комп'ютера (Jetson/CM4): виділені домени живлення, шини зв'язку UART/Ethernet та апаратна лінія скидання.*

Фізичне поєднання двох систем потребує суворого дотримання трьох електрофізичних інваріантів:
* **Ізоляція доменів живлення та динаміка перехідних процесів:** FC та Companion живляться від абсолютно незалежних імпульсних перетворювачів напруги (DC-DC BEC). FC підключається до виділеного стабілізатора з ультранизьким рівнем пульсацій (LDO після імпульсного ступеня, рівень шуму менше 15 мВ у смузі 10 Гц – 100 кГц), оснащеного вбудованим датчиком струму та напруги (INA226 або резистивний дільник на АЦП). Companion живиться від потужного силового DC-DC перетворювача (5 В / 5 А або 12–19 В / 4 А для Jetson), розрахованого на пікові струми інференсу штучного інтелекту, з батареєю Low-ESR конденсаторів ємністю 1500–2200 мкФ на вході.
  
  Розрахуймо динамічне просідання напруги на лінії живлення при стрибку споживання GPU. Провід живлення перерізом AWG22 довжиною 15 см має опір \`R ≈ 0.015 Ом\` та власну паразитну індуктивність \`L ≈ 180 нГн\`. При старті інференсу швидкість наростання струму становить \`dI/dt = 3.5 А / 5 мкс = 7 · 10⁵ А/с\`. Індуктивне просідання напруги на джгуті:
  \`\`\`
  V_L = L · (dI/dt) = 180 · 10⁻⁹ Гн · 7 · 10⁵ А/с = 0.126 В
  \`\`\`
  Разом із резистивним падінням \`ΔV_R = 3.5 А · 0.015 Ом = 0.052 В\` сумарний імпульсний спад сягає майже 0.18 В без урахування внутрішньої затримки зворотного зв'язку DC-DC перетворювача (яка додає ще 0.3–0.5 В просідання на 20–50 мкс). Якщо FC живитиметься від цієї ж лінії, напруга 5.0 В просяде нижче порога спрацьовування супервізора живлення STM32 (\`V_BOR = 4.35 В\` для рівня BOR3), викликаючи скидання мікроконтролера. Окремий DC-DC з власним LC-фільтром повністю відсікає цей перехідний процес.
* **Зіркова топологія заземлення:** силові мінуси обох перетворювачів сходяться в єдиній точці силового розподільника живлення (PDB). Сигнальна лінія GND між FC та SBC не повинна бути паралельною силовим проводам живлення, інакше струми комутації ядер CPU/GPU створюватимуть паразитне падіння напруги `ΔV = I(t) · R_gnd` на сигнальній землі, спотворюючи цифрові рівні UART та аналогові покази сенсорів.
* **Захист від паразитного живлення (*phantom powering*):** якщо Companion знеструмлений (наприклад, перебуває у стані перезавантаження чи вимкнений за низького заряду батареї), а FC залишається під напругою, струм із вихідних пінів UART TX або I2C SCL (3.3 В) через внутрішні захисні ESD-діоди мікросхеми SoC починає живити шину живлення процесора комп'ютера. Це викликає перевантаження вихідних каскадів мікроконтролера (струм до 40–80 мА на пін), небезпечний нагрів кристала та зависання інтерфейсів. Для запобігання цьому явища на міжплатні лінії встановлюють послідовні резистори номіналом 220–470 Ом або двонапрямлені буфери-транслятори рівнів із високим імпедансом у вимкненому стані (наприклад, TI TXU0204 чи NXP 74LVC2T45).

### Розподіл обов'язків: жорсткий проти м'якого реального часу

Розподіл обчислювального навантаження визначається природою часового детермінізму (*determinism*, від латинського *determinare* — обмежувати, визначати). Жорсткий реальний час (*hard real-time*) означає, що запізнення обчислення хоча б на один такт є повною системною відмовою з фатальними наслідками. М'який реальний час (*soft real-time*) означає, що запізнення зменшує якість результату, але не руйнує систему, а середня пропускна здатність важливіша за фіксований час відгуку.

![Часовий детермінізм: часові шкали виконання контурів на FC та Companion Computer](/root/sys/sys-dron/companion-computer/img/realtime-vs-soft-domains.svg)
*Порівняння жорсткого та м'якого реального часу: мікросекундний детермінізм контурів стабілізації на контролері проти мілісекундних затримок планувальника та нейромереж на Linux-хості.*

На рівні внутрішньої архітектури обов'язки розподіляються за принципом критичності:

#### 1. Зона відповідальності політного контролера (Hard Real-Time):
* **Контури кутової швидкості та орієнтації (*Rate & Attitude PID*):** виконання на частотах 800 Гц – 8 кГц для контуру швидкостей і 400–800 Гц для контуру кутів. Час виконання одного кроку регулятора не перевищує 0.2–0.4 мс, а розкид затримки (*jitter*) становить менше 5 мкс.
* **Розширений фільтр Калмана (EKF3 / EKF2):** високочастотне злиття показів первинних інерційних датчиків (IMU ICM-42688-P або BMI088 по шині SPI на частоті 24 МГц), барометра (MS5611 по I2C/SPI), магнітометра та супутникового приймача GNSS із тактом 100–400 Гц.
* **Генерація вихідних керуючих сигналів на регулятори моторів (ESC):** передача цифрових пакетів DShot300/600 (пакет 16 біт із контрольною сумою CRC передається за 26.7 мкс для DShot600) через апаратні канали таймерів із прямим доступом до пам'яті (DMA), що унеможливлює тремтіння фази ШІМ.
* **Аварійна автоматика (Failsafe Engine):** автономний моніторинг рівня заряду батареї, якості радіозв'язку RC, геозон (*geofence*) та таймаутів вхідних уставок. Рішення про перехід в аварійний стан ухвалюється апаратно-програмним ядром контролера без жодної залежності від стану комп'ютера.

#### 2. Зона відповідальності бортового комп'ютера (Soft Real-Time):
* **Сенсорне бачення та одометрія (VIO / LiDAR SLAM):** обробка стереокамер, камер глибини (Intel RealSense D435i, OAK-D) або лазерних сканерів. Розрахунок візуально-інерційної одометрії (OpenVINS, ROVIO, Isaac ROS VIO) та побудова тривимірних карт зайнятості (*3D Occupancy Grid*, OctoMap / Voxblox) з частотою 15–30 Гц і затримкою 25–45 мс.
* **Нейромережеве виявлення та супровід цілей (AI Perception):** інференс моделей детекції об'єктів (YOLOv8n / YOLOv10 в оптимізованому середовищі TensorRT FP16) на вбудованому GPU/NPU з часом обробки кадру 15–35 мс.
* **Генерація та оптимізація траєкторій:** розрахунок траєкторій польоту у просторі перешкод за допомогою мінімізації ривка (*Minimum Snap Trajectory Generation*) або алгоритмів прогнозуючого керування моделлю (*Model Predictive Control*, MPC) з горизонтом 1–3 секунди й темпом оновлення 10–20 Гц.
* **Комунікаційний та сервісний стек:** виконання вузлів ROS 2 (Robot Operating System), MAVROS / micro-ROS агентів, запис високошвидкісних логів на NVMe SSD, стиснення та передача відеопотоків H.264/H.265 через GStreamer та RTSP-сервери по каналу цифрового радіозв'язку (Wi-Fi 6, 4G/5G, Silvus/COFDM).

Розрахуємо наслідки зриву дедлайну для обох систем:
```
Контур кутової швидкості (FC):
  f = 1000 Гц  →  T = 1.0 мс  (Дедлайн t_max = 1.0 мс)
  WCET (найгірший час обчислення) = 0.35 мс
  Запас часу = 0.65 мс
  Пропуск 1 такту (запізнення на 1 мс):  фазовий зсув контуру ~36°  →  помітний ривок
  Пропуск 20 тактів (пауза ОС 20 мс):   повна втрата фази  →  миттєве звалювання

Контур трекінгу цілі (Companion):
  f = 30 Гц  →  T = 33.3 мс  (Цільовий інтервал)
  Час обробки кадру в YOLOv8 = 28 мс
  Джиттер планувальника Linux = 15 мс
  Загальний час відгуку = 43 мс (пропуск кадру)
  Наслідок: FC екстраполює попередню швидкість, дрон продовжує плавний рух
```

> 🔧 **Навіщо це.** Чітке розмежування детермінізму позбавляє ілюзії, ніби «потужний процесор замінить мікроконтролер». Навіть процесор із частотою 2.5 ГГц під звичайним Linux будь-якої миті може перервати виконання на 15–30 мс через дисковий буфер, очищення кешу або обробку мережевого переривання. Відокремлений мікроконтролер гарантує виконання кожного такту з точністю до мікросекунди незалежно від того, наскільки перевантажений Linux-хост.

### Фізичні та протокольні інтерфейси зв'язку FC ↔ Companion

Зв'язок між двома бортовими машинами реалізується через один або кілька апаратних інтерфейсів, кожен із яких оптимізований під конкретний клас трафіку:

```
ШИНИ ЗВ'ЯЗКУ FC ↔ COMPANION:
  UART (Serial):   921.6k – 3.0M бод, RTT 1.5 – 3.5 мс  → MAVLink v2
  Ethernet (PHY):  100 Мбіт/с,        RTT 0.2 – 0.5 мс  → micro-XRCE-DDS / UDP
  USB-CDC:         12 – 480 Мбіт/с,   RTT 1.0 – 2.5 мс  → MAVLink (Лабораторія)
  CAN / DroneCAN:  1.0 Мбіт/с,        RTT 0.8 – 1.2 мс  → UAVCAN v0/v1
```

#### 1. Послідовний порт UART (MAVLink over Serial)
UART — найбільш перевірений і стійкий до апаратних збоїв канал. З'єднання потребує лише трьох ліній: `TX`, `RX` та `GND` (і за потреби ліній апаратного керування потоком `RTS`/`CTS`).

Для забезпечення стабільного обміну швидкість порту повинна бути правильно узгоджена з обсягом трафіку. Розрахуємо пропускну здатність та коефіцієнт завантаження каналу:

В асинхронному протоколі UART 8N1 кожен корисний байт передається у фреймі з 10 біт (1 старт-біт, 8 біт даних, 1 стоп-біт). Отже, теоретична пропускна здатність у байтах на секунду дорівнює бітрейту, поділеному на 10:
```
C_bytes = Baudrate / 10
При 115200 бод:  C = 115200 / 10 =  11 520 байт/с (11.25 кБайт/с)
При 921600 бод:  C = 921600 / 10 =  92 160 байт/с (90.00 кБайт/с)
При 1500000 бод: C = 1500000 / 10 = 150 000 байт/с (146.48 кБайт/с)
При 3000000 бод: C = 3000000 / 10 = 300 000 байт/с (292.96 кБайт/с)
```

Типовий потік телеметрії від FC до Companion містить:
* `HIGHRES_IMU` (id 105, 62 байти payload + 12 байтів MAVLink v2 header/checksum = 74 Б) @ 50 Гц = 3 700 Б/с
* `ATTITUDE` (id 30, 28 Б payload + 12 Б = 40 Б) @ 50 Гц = 2 000 Б/с
* `LOCAL_POSITION_NED` (id 32, 28 Б payload + 12 Б = 40 Б) @ 50 Гц = 2 000 Б/с
* `ODOMETRY` (id 331, 232 Б payload + 12 Б = 244 Б) @ 30 Гц = 7 320 Б/с
* `VFR_HUD` (id 74, 20 Б payload + 12 Б = 32 Б) @ 20 Гц = 640 Б/с
* `SYS_STATUS` та службові повідомлення @ 5 Гц ≈ 800 Б/с

Зворотний потік від Companion до FC (уставки та одометрія зору):
* `SET_POSITION_TARGET_LOCAL_NED` (id 84, 53 Б payload + 12 Б = 65 Б) @ 30 Гц = 1 950 Б/с
* `VISION_POSITION_ESTIMATE` (id 102, 114 Б payload + 12 Б = 126 Б) @ 30 Гц = 3 780 Б/с
* `HEARTBEAT` та команди керування ≈ 400 Б/с

Сумарний двонапрямлений потік: `Q ≈ 22 600 байт/с` (22.07 кБайт/с).

Аналіз завантаження каналу:
* На швидкості **115200 бод**: `Завантаження = (22600 / 11520) · 100% = 196.2%` — **перевантаження каналу!** Буфери UART переповнюються, втрачається понад 50% пакетів, затримка передачі зростає до 300–800 мс, робота автопілота в режимі Offboard неможлива.
* На швидкості **921600 бод**: `Завантаження = (22600 / 92160) · 100% = 24.5%` — **оптимальний режим**. Запас пропускної здатності 75% гарантує нульові черги в буферах FIFO та мінімальну латентність передачі (< 2 мс).
* На швидкості **1.5M / 3.0M бод**: завантаження становить менше 8–15%, що дозволяє передавати високочастотні дані інерціальних датчиків (200–400 Гц) для VIO-алгоритмів.

На стороні мікроконтролера STM32H7 обробка потоку 921600+ бод організується через контролер прямого доступу до пам'яті (DMA1/DMA2) у кільцевому режимі (*Circular DMA RX*). Використання звичайних переривань по кожному байту (`USART_IT_RXNE`) на швидкості 3 Мбод генерувало б 300 000 переривань на секунду, що паралізувало б ядро процесора. Замість цього потік спрямовується в DMA-буфер, а процесор прокидається лише у двох випадках:
* Подія половинного або повного заповнення кільцевого буфера (`HTIF` / `TCIF`).
* Апаратне переривання виявлення простою лінії (*IDLE Line Detection*, `USART_ISR_IDLE`). Коли передача пачки байтів завершується і лінія RX залишається у високому стані протягом тривалості одного фрейму (10 бітових інтервалів), генерується одне переривання, драйвер обчислює поточну кількість отриманих байтів за лічильником `NDTR` і миттєво відправляє пакет на розбір без штучних затримок.

#### 2. Мережевий інтерфейс Ethernet (micro-XRCE-DDS / IP)
На сучасних апаратах із контролерами високого класу (наприклад, Pixhawk 6X / 6C, Holybro Kakute H7 v2 з апаратним PHY LAN8720 або DP83848) зв'язок реалізується через повнодуплексний Ethernet 100BASE-TX.

Переваги над UART:
* **Гальванічна трансформаторна розв'язка:** вбудовані імпульсні трансформатори роз'єму (LAN Magnetics) забезпечують ізоляцію до 1500 В, унеможливлюючи утворення земляних петель та захищаючи чутливі інтерфейси від імпульсних наведень моторів.
* **Нативна інтеграція з ROS 2:** протокол micro-XRCE-DDS реалізує клієнт-серверну архітектуру DDS прямо на мікроконтролері. Внутрішні топіки автопілота PX4 (`uORB`) публікуються безпосередньо в простір імен топіків ROS 2 без потреби у проміжних важких трансляторах на кшталт MAVROS.
* **Висока швидкість:** смуга 100 Мбіт/с дозволяє передавати сирі масиви сенсорних даних, наприклад карти глибини та хмари точок LiDAR.

#### 3. Чому USB-CDC не застосовують на льотних зразках
Віртуальний COM-порт по шині USB (USB-CDC) часто використовують у лабораторіях для налагодження, але уникають у реальних польотах:
1. **Механічна ненадійність роз'ємів:** стандартні роз'єми Micro-USB та Type-C без гвинтового замка під дією вібрацій 100–500 Гц зазнають мікророзмикань контактів тривалістю десятки мікросекунд.
2. **Збій стану хост-драйвера Linux:** при мікророзриві або апаратному скиданні FC драйвер ядра Linux `cdc_acm` закриває дескриптор пристрою `/dev/ttyACM0`. Після повторної ініціалізації контролер монтується як новий пристрій `/dev/ttyACM1`. Програмні демони MAVROS або ROS-ноди, відкриті на старий дескриптор, втрачають зв'язок назавжди аж до повного перезапуску процесів.
3. **Високі накладні витрати MCU:** стек USB 2.0 Full Speed вимагає обробки тисяч переривань кінцевих точок (*endpoints*) на секунду, відбираючи до 8–12% обчислювального часу ядра ARM Cortex-M.

### Надійність, сторожові таймери та життєвий цикл

Головний принцип безпеки двопроцесорної архітектури: **політний контролер ніколи не розглядає бортовий комп'ютер як життєво необхідний компонент**. Бортовий комп'ютер має право зависнути, перегрітися чи перезавантажитися в будь-яку мить польоту без загрози падіння апарата.

#### 1. Сторожовий таймер уставок (*Setpoints Watchdog*)
У режимах автоматичного керування від зовнішнього комп'ютера (режим *Offboard* у PX4 або *Guided* в ArduPilot) контролер очікує безперервного потоку цільових уставок швидкості, прискорення чи положення з частотою не нижче 2 Гц:
* У прошивці PX4 параметр `COM_OF_LOSS_T` задає максимальний дозволений інтервал між уставками (типово 500 мс). Якщо потік повідомлень `SET_POSITION_TARGET_LOCAL_NED` чи `SET_ATTITUDE_TARGET` переривається на час, більший за `COM_OF_LOSS_T`, автопілот миттєво виходить із режиму Offboard і вмикає аварійну дію (`COM_OBL_ACT`): зависання в поточній точці (*Hold / Position Hold*), плавний спуск (*Land*) або повернення на домашню точку (*Return-to-Launch, RTL*).
* В ArduPilot за це відповідає таймаут `GUID_TIMEOUT`. Якщо протягом 3 секунд нових уставок немає, апарат зупиняє рух і переходить в утримання позиції за власними датчиками.

#### 2. Апаратний сторожовий перезапуск Companion (*Hard-Reset Watchdog*)
Якщо ядро Linux зависає через паніку ядра (*kernel panic*), вичерпання пам'яті (*OOM-killer*) або перегрів, програмний перезапуск неможливий. Для відновлення працездатності застосовують апаратну лінію скидання:
* Бортовий комп'ютер періодично шле контролеру повідомлення стану `ONBOARD_COMPUTER_STATUS` (id 390) або `HEARTBEAT` із прапорцем компонента `MAV_COMP_ID_COMPANION_COMPUTER`.
* Якщо контролер не отримує жодного сигналу життя протягом 15–30 секунд, виділений пін GPIO політного контролера формує сигнал низького рівня на лінію `SYS_RESET#` комп'ютера або короткочасно розмикає силове реле (P-канальний MOSFET-транзистор) у ланцюзі живлення SBC. Комп'ютер проходить холодний цикл перезавантаження (*Power Cycle*), завантажує операційну систему за 20–40 секунд і відновлює передачу даних, тоді як контролер увесь цей час утримує апарат у повітрі.

Нижче наведено робочий модуль асинхронного читання та відправки MAVLink-повідомлень між Linux-хостом та політним контролером через послідовний порт UART з обробкою таймаутів та контролем втрати зв'язку.

/* ============================================================================
 * Драйвер послідовного порту MAVLink для бортового комп'ютера (C99 / POSIX)
 * ============================================================================ */
#define _POSIX_C_SOURCE 200809L
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <stdbool.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>
#include <termios.h>
#include <errno.h>
#include <time.h>

/* Базові константи та типи протоколу MAVLink v2 */
#define MAVLINK_STX_V2          0xFD
#define MAVLINK_MAX_PACKET_LEN  280
#define BUFFER_SIZE             1024

typedef struct {
    int fd;
    char device[64];
    speed_t baudrate;
    uint8_t rx_buffer[BUFFER_SIZE];
    uint32_t rx_head;
    uint32_t rx_tail;
    uint64_t last_heartbeat_ms;
} serial_bridge_t;

/* Отримання поточного часу в мілісекундах */
static uint64_t get_time_ms(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (uint64_t)ts.tv_sec * 1000ULL + (uint64_t)ts.tv_nsec / 1000000ULL;
}

/* Ініціалізація та конфігурація POSIX UART у режимі RAW */
int serial_bridge_open(serial_bridge_t *b, const char *device, speed_t baud) {
    memset(b, 0, sizeof(*b));
    strncpy(b->device, device, sizeof(b->device) - 1);
    b->baudrate = baud;

    /* Відкриття порту: неблокуючий режим, без захоплення терміналу */
    b->fd = open(device, O_RDWR | O_NOCTTY | O_NONBLOCK);
    if (b->fd < 0) {
        perror("Помилка відкриття UART");
        return -1;
    }

    struct termios config;
    if (tcgetattr(b->fd, &config) < 0) {
        perror("Помилка отримання конфігурації termios");
        close(b->fd);
        return -1;
    }

    /* Налаштування сирого режиму (RAW mode) */
    cfmakeraw(&config);
    cfsetispeed(&config, baud);
    cfsetospeed(&config, baud);

    /* 8 біт даних, 1 стоп-біт, без парності, без апаратного контролю */
    config.c_cflag |= (CLOCAL | CREAD | CS8);
    config.c_cflag &= ~(PARENB | CSTOPB | CRTSCTS);

    /* Неблокуюче читання: негайне повернення, якщо буфер порожній */
    config.c_cc[VMIN] = 0;
    config.c_cc[VTIME] = 0;

    if (tcsetattr(b->fd, TCSANOW, &config) < 0) {
        perror("Помилка застосування termios");
        close(b->fd);
        return -1;
    }

    tcflush(b->fd, TCIOFLUSH);
    b->last_heartbeat_ms = get_time_ms();
    return 0;
}

/* Неблокуюче читання та базовий парсинг STX маркера MAVLink */
int serial_bridge_poll_rx(serial_bridge_t *b) {
    uint8_t temp_buf[256];
    ssize_t bytes_read = read(b->fd, temp_buf, sizeof(temp_buf));

    if (bytes_read > 0) {
        for (ssize_t i = 0; i < bytes_read; ++i) {
            uint8_t byte = temp_buf[i];
            /* Виявлення початку кадру MAVLink v2 */
            if (byte == MAVLINK_STX_V2) {
                b->last_heartbeat_ms = get_time_ms();
            }
        }
        return (int)bytes_read;
    }
    return 0;
}

/* Відправка бінарного пакета у порт */
ssize_t serial_bridge_send(serial_bridge_t *b, const uint8_t *data, size_t len) {
    if (b->fd < 0 || !data || len == 0) return -1;
    return write(b->fd, data, len);
}

/* Перевірка таймауту зв'язку з політним контролером */
bool serial_bridge_is_alive(const serial_bridge_t *b, uint32_t timeout_ms) {
    uint64_t now = get_time_ms();
    return (now - b->last_heartbeat_ms) < (uint64_t)timeout_ms;
}

void serial_bridge_close(serial_bridge_t *b) {
    if (b->fd >= 0) {
        close(b->fd);
        b->fd = -1;
    }
}

// ============================================================================
// Драйвер послідовного порту MAVLink для бортового комп'ютера (C++20)
// ============================================================================
#include <iostream>
#include <vector>
#include <span>
#include <chrono>
#include <optional>
#include <string>
#include <string_view>
#include <system_error>
#include <cstdint>
#include <cstring>
#include <unistd.h>
#include <fcntl.h>
#include <termios.h>

class MavlinkSerialBridge {
public:
    static constexpr uint8_t STX_V2 = 0xFD;

    explicit MavlinkSerialBridge(std::string_view port, speed_t baud = B921600)
        : port_name_(port), baudrate_(baud) {}

    ~MavlinkSerialBridge() noexcept {
        close_port();
    }

    // Заборона копіювання для захисту дескриптора (RAII)
    MavlinkSerialBridge(const MavlinkSerialBridge&) = delete;
    MavlinkSerialBridge& operator=(const MavlinkSerialBridge&) = delete;

    MavlinkSerialBridge(MavlinkSerialBridge&& other) noexcept
        : fd_(other.fd_), port_name_(std::move(other.port_name_)),
          baudrate_(other.baudrate_), last_heartbeat_(other.last_heartbeat_) {
        other.fd_ = -1;
    }

    bool open_port() {
        fd_ = ::open(port_name_.c_str(), O_RDWR | O_NOCTTY | O_NONBLOCK);
        if (fd_ < 0) {
            return false;
        }

        struct termios tty{};
        if (::tcgetattr(fd_, &tty) != 0) {
            close_port();
            return false;
        }

        ::cfmakeraw(&tty);
        ::cfsetispeed(&tty, baudrate_);
        ::cfsetospeed(&tty, baudrate_);

        tty.c_cflag |= (CLOCAL | CREAD | CS8);
        tty.c_cflag &= ~(PARENB | CSTOPB | CRTSCTS);
        tty.c_cc[VMIN] = 0;
        tty.c_cc[VTIME] = 0;

        if (::tcsetattr(fd_, TCSANOW, &tty) != 0) {
            close_port();
            return false;
        }

        ::tcflush(fd_, TCIOFLUSH);
        last_heartbeat_ = std::chrono::steady_clock::now();
        return true;
    }

    void close_port() noexcept {
        if (fd_ >= 0) {
            ::close(fd_);
            fd_ = -1;
        }
    }

    // Відправка буфера без зайвого копіювання через std::span
    [[nodiscard]] bool send_packet(std::span<const uint8_t> packet) const noexcept {
        if (fd_ < 0 || packet.empty()) return false;
        auto written = ::write(fd_, packet.data(), packet.size());
        return written == static_cast<ssize_t>(packet.size());
    }

    // Неблокуюче читання вхідних байтів
    std::size_t receive_bytes(std::span<uint8_t> out_buffer) {
        if (fd_ < 0 || out_buffer.empty()) return 0;
        auto bytes_read = ::read(fd_, out_buffer.data(), out_buffer.size());
        if (bytes_read > 0) {
            for (ssize_t i = 0; i < bytes_read; ++i) {
                if (out_buffer[i] == STX_V2) {
                    last_heartbeat_ = std::chrono::steady_clock::now();
                }
            }
            return static_cast<std::size_t>(bytes_read);
        }
        return 0;
    }

    // Перевірка активності каналу зв'язку
    [[nodiscard]] bool is_connected(std::chrono::milliseconds timeout = std::chrono::milliseconds(1000)) const noexcept {
        auto now = std::chrono::steady_clock::now();
        return (now - last_heartbeat_) < timeout;
    }

private:
    int fd_{-1};
    std::string port_name_;
    speed_t baudrate_;
    std::chrono::steady_clock::time_point last_heartbeat_{};
};

### Підсумкова інженерна архітектура

Інтеграція бортового комп'ютера розширює можливості безпілотного апарата від сліпого виконання заданих координат до повноцінного автономного сприйняття навколишнього середовища. Водночас надійність усієї системи визначається правильним дотриманням меж відповідальності:
1. **Політний контролер (STM32H7)** відповідає за фізичне виживання, тримає високочастотний контур стабілізації (1–8 кГц), детермінований фільтр Калмана (EKF3) та апаратний Failsafe.
2. **Бортовий комп'ютер (Jetson / RPi CM4)** відповідає за інтелект, виконує VIO, SLAM, детекцію об'єктів та планування траєкторій (15–30 Гц) у м'якому реальному часі.
3. **Шини зв'язку** (високошвидкісний UART 921600+ бод та ізольований Ethernet 100BASE-TX) забезпечують надійний обмін уставками та телеметрією з контрольованим рівнем завантаження менше 30%.
4. **Ізоляція живлення та сторожові таймери** гарантують, що будь-який програмний чи апаратний збій комп'ютера не призведе до падіння апарата, дозволяючи автопілоту стабілізувати дрон і безпечно повернутися на точку старту.
