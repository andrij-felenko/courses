# 📋 Контракт LinkManager: підписи, умови виклику, потоки

Менеджер каналів віддає назовні три різні набори входів, і плутати їх дорого: те, що екран налаштувань спокійно кличе з натискання кнопки, з потоку з'єднання зламає застосунок, а метод, який виглядає як «створи з'єднання», нічого не повертає й про невдачу мовчить. Тут зібрано всі три набори — методи для інтерфейсу, методи для коду підсистем, властивості та сигнали — з підписами, умовою виклику, поведінкою на невдачі й позначкою потокової безпеки; окремо — контракт `LinkConfiguration`, бо саме його властивості читає список каналів.

Підписи наведено за поточною гілкою QGroundControl, де класи лежать у `src/Comms/` (`LinkManager.h`, `LinkConfiguration.h`, `LinkInterface.h`). У гілці 4.x ті самі класи жили в `src/comm/`, і частина методів мала інші імена — для довідника питання «а в якій версії?» тут доречне завжди, тож звіряйтеся з заголовком своєї збірки.

## Як дістатися до об'єкта

Менеджер — один на застосунок, доступ через статичний метод:

```cpp
LinkManager *lm = LinkManager::instance();
```

Об'єкт створюється при піднятті застосунку, `init()` кличе сам застосунок один раз, і живе він у головному потоці. Наслідок, з якого випливає вся таблиця потоків нижче: усе, що створює або видаляє об'єкти Qt чи чіпає властивості, дозволено лише з головного потоку; з інших потоків можна кликати рівно ті методи, які беруть внутрішній м'ютекс списку. Про те, чому єдиний екземпляр тут доречний і де ця конструкція кусається, — у темі [сінглтон](root:sf-apps/singleton).

Позначки в колонці «потік» далі:

- 🔒 — метод бере м'ютекс списку з'єднань; можна кликати з будь-якого потоку;
- ⚠️ — лише головний потік;
- ⛔ — метод **блокує**, доки не виконається умова.

## Методи для інтерфейсу (`Q_INVOKABLE`)

Ці дванадцять методів позначені як доступні з декларативного шару — їх кличе екран налаштувань каналів. З коду C++ вони теж доступні, це звичайні публічні методи.

| Підпис | Коли кличуть | Невдача | Потік |
|---|---|---|---|
| `LinkConfiguration *createConfiguration(int type, const QString &name)` | користувач обрав тип у діалозі «додати канал» | тип поза переліком `LinkConfiguration::LinkType` — опису не буде | ⚠️ |
| `LinkConfiguration *startConfigurationEditing(LinkConfiguration *config)` | відкрито діалог правки наявного опису | — | ⚠️ |
| `void endConfigurationEditing(LinkConfiguration *config, LinkConfiguration *editedConfig)` | натиснуто «Гаразд» | — | ⚠️ |
| `void cancelConfigurationEditing(LinkConfiguration *config) const` | натиснуто «Скасувати» | — | ⚠️ |
| `void endCreateConfiguration(LinkConfiguration *config)` | «Гаразд» у діалозі **створення** | — | ⚠️ |
| `void removeConfiguration(LinkConfiguration *config)` | натиснуто «Видалити» | опис, якого нема в списках, просто ігнорується | ⚠️ |
| `void createConnectedLink(const LinkConfiguration *config)` | натиснуто «Під'єднати» | **мовчить**: результату не повертає | ⚠️ |
| `void disconnectLink(LinkInterface *link)` | натиснуто «Від'єднати» на живому з'єднанні | — | ⚠️ |
| `void disconnectLinkConfiguration(LinkConfiguration *config)` | те саме, але з рядка списку каналів | нема живого з'єднання — нічого не робить | ⚠️ |
| `void createMavlinkForwardingSupportLink()` | увімкнено пересилання трафіку назовні | — | ⚠️ |
| `void shutdown()` | застосунок закривається | — | ⛔ |
| `LogReplayLink *startLogReplay(const QString &logFile)` | обрано файл записаного польоту | повертає порожній вказівник | ⚠️ |

Три пояснення, без яких таблиця оманлива.

**`createConfiguration` віддає об'єкт, за який ніхто не відповідає.** Новий опис створюється **без батька** і в списки менеджера не потрапляє. Поки його не передали в `endCreateConfiguration`, він висить сам по собі: у коді C++ це витік, а з декларативного шару рушій за загальним правилом Qt бере на себе власність над об'єктом, поверненим із виклику методу, якщо в того нема батька, — тобто збирач сміття може прибрати опис просто посеред заповнення діалогу. Обидва результати кепські, тож між `createConfiguration` і `endCreateConfiguration` не повинно бути нічого, крім заповнення полів.

**`endCreateConfiguration` — саме та мить, коли власність переходить.** Усередині він кличе `addConfiguration()`, який загортає сирий вказівник у спільний і кладе його у два списки, а тоді записує список на диск. Що саме потрапляє у файл налаштувань і що станція перечитує на старті — у темі [збереження налаштувань](root:sys-dron/settings-persistence).

**`createConnectedLink` у цьому наборі повертає `void`.** Він знаходить у списку описів спільний вказівник, що відповідає переданому сирому, скидає лічильник невдач і позначає опис як «уже запускали в цьому сеансі», а тоді кличе повноцінний варіант, який повертає `bool`. Це `bool` нікуди не доходить. Тому єдиний зворотний зв'язок для інтерфейсу — властивість `linkActive` на описі, яка не стане правдивою, і сигнал `communicationError` від самого з'єднання, з якого станція малює повідомлення про помилку. Якщо переданого опису в списках нема, метод теж мовчки виходить.

## Три ланцюжки виклику

Порядок тут не довільний: кожен ланцюжок має мить, до якої опис іще нічий, і мить, після якої він належить менеджерові.

```cpp
// 1 · створення нового опису
LinkManager *lm = LinkManager::instance();
LinkConfiguration *cfg = lm->createConfiguration(LinkConfiguration::TypeUdp, "Симулятор");
// ... діалог заповнив адресу й порт просто в cfg ...
lm->endCreateConfiguration(cfg);          // з цієї миті опис у списках і на диску
```

```cpp
// 2 · правка наявного опису — через тимчасову копію
LinkConfiguration *edited = lm->startConfigurationEditing(orig);
// ... діалог править edited, а не orig ...
lm->endConfigurationEditing(orig, edited); // copyFrom(edited) → запис на диск → delete edited
// або, якщо натиснуто «Скасувати»:
lm->cancelConfigurationEditing(edited);    // delete edited; orig не змінився
```

```cpp
// 3 · під'єднання й розрив
lm->createConnectedLink(orig);             // void: про успіх дізнаємося з linkActive
// ...
lm->disconnectLinkConfiguration(orig);     // розрив + заборона автопідйому
```

Найлихіша пастка всього контракту сидить у другому ланцюжку. `cancelConfigurationEditing` у своєму тілі має буквально `delete config` — і аргумент цього методу **не оригінал, а копія**, яку раніше повернув `startConfigurationEditing`. Ім'я параметра однакове в обох методах, тип теж, компілятор мовчить. Передати туди оригінал — знищити робочий опис, залишивши в двох списках менеджера вказівники на звільнену пам'ять. Ознака помилки на екрані виглядатиме зовсім не як «скасування зіпсувало опис»: застосунок упаде згодом, коли список каналів наступного разу спробує прочитати ім'я.

Симетрична річ у `endConfigurationEditing`: він теж видаляє **другий** аргумент, а перший лише оновлює через `copyFrom()` і зберігає список. Тобто копію видаляє будь-який із двох завершальних викликів, а не викликати жоден із них — це витік.

І окремо: `removeConfiguration` сам об'єкт **не видаляє**. Він рве живе з'єднання, якщо воно є, знімає опис з обох списків і зберігає новий список. Об'єкт після цього нікому не належить.

## Методи для коду підсистем

Другий набір — те, що кличуть апарат, підсистема логів, автопідключення й код розширень. Тут якраз більшість позначено 🔒.

| Підпис | Що робить і коли кликати | Результат при невдачі | Потік |
|---|---|---|---|
| `static LinkManager *instance()` | доступ до єдиного екземпляра | — | 🔒 |
| `void init()` | одноразове піднімання підсистеми на старті | — | ⚠️ |
| `QList<SharedLinkInterfacePtr> links()` | **знімок** списку живих з'єднань | порожній список — нормальний стан | 🔒 |
| `SharedLinkInterfacePtr sharedLinkInterfacePointerForLink(const LinkInterface *link)` | єдиний правильний спосіб **зберегти** вказівник на з'єднання | порожній вказівник — штатна відповідь «уже нема» | 🔒 |
| `bool containsLink(const LinkInterface *link)` | миттєва перевірка «чи є ще в списку» | `false` | 🔒 |
| `SharedLinkConfigurationPtr addConfiguration(LinkConfiguration *config)` | передати менеджерові власність над описом | — | ⚠️ |
| `void startAutoConnectedLinks()` | один раз на старті: підняти всі описи з галочкою автопідключення | — | ⚠️ |
| `bool createConnectedLink(SharedLinkConfigurationPtr &config)` | повний варіант із чесним результатом | `false` — і все зроблене відкочено | ⚠️ |
| `void disconnectAll()` | розірвати всі канали | — | 🔒 |
| `SharedLinkInterfacePtr mavlinkForwardingLink()` | канал пересилання трафіку | порожній вказівник, якщо пересилання вимкнено | 🔒 |
| `SharedLinkInterfacePtr mavlinkForwardingSupportLink()` | окремий канал підтримки пересилання | те саме | 🔒 |
| `uint8_t allocateMavlinkChannel()` | видати номер каналу розбирача | `invalidMavlinkChannel()`, тобто 255 | ⚠️ |
| `void freeMavlinkChannel(uint8_t channel)` | повернути номер у маску | значення 255 ігнорується | ⚠️ |
| `static constexpr uint8_t invalidMavlinkChannel()` | значення-ознака «каналу нема» | завжди 255 | 🔒 |
| `void setConnectionsSuspended(const QString &reason)` | заборонити підйом каналів із причиною для повідомлення | — | ⚠️ |
| `void setConnectionsAllowed()` | зняти заборону | — | ⚠️ |
| `void loadLinkConfigurationList()` / `void saveLinkConfigurationList()` | перечитати чи записати список описів | — | ⚠️ |
| `static bool isLinkUSBDirect(const LinkInterface *link)` | чи це серійний канал прямо в USB (а не через радіо) | `false` для будь-якого несерійного | 🔒 |
| `static bool isBluetoothAvailable()` | чи зібрано підтримку Bluetooth і чи ввімкнено адаптер | `false` | 🔒 |

**`links()` повертає копію списку, а не посилання на нього.** Це не марнотратство, а суть контракту: копія робиться під м'ютексом, і спільні вказівники всередині неї тримають з'єднання живими весь час, поки ви цією копією ходите. Перебирати щось усередині менеджера ви не можете й не повинні. Механіка, на якій це стоїть, — звичайний [підрахунок посилань](root:sf-lang/reference-counting).

**`containsLink` дає відповідь про минуле.** Між `containsLink(link) == true` і наступним рядком коду з'єднання може зникнути зі списку — рішення про розрив приймають інші потоки. Тому перевірка годиться для діагностики й ніколи — як дозвіл слати: якщо ви збираєтеся щось робити зі з'єднанням, беріть `sharedLinkInterfacePointerForLink` і перевіряйте його на порожність. Різницю між «перевірити» і «втримати» докладно розібрано в темах про [потокову безпеку](root:sf-tasks/thread-safety) та [слабкі посилання](root:sf-lang/weak-references).

**`shutdown()` блокує.** Він забороняє нові з'єднання, рве наявні, а тоді крутить чергу подій доти, доки не зникне останній апарат. Кликати його з обробника, який сам чогось чекає, — надійний спосіб отримати застосунок, що не закривається.

## Видача каналів MAVLink

Ці три методи — облік скінченного ресурсу, і числа тут важать більше за підписи:

```
MAVLINK_COMM_NUM_BUFFERS = 16    // Linux, macOS, Windows
MAVLINK_COMM_NUM_BUFFERS = 4     // решта платформ
invalidMavlinkChannel()  = 255   // std::numeric_limits<uint8_t>::max()

маска стартує зі значенням 1 → біт 0 зайнято ще до першого з'єднання
доступних номерів = 15 (на настільних системах) або 3
```

Контракт `allocateMavlinkChannel()` ширший, ніж «віддати вільне число». Перед поверненням номера метод скидає стан розбору для цього каналу й виставляє на ньому прапорець вихідної першої версії протоколу — доки не з'ясується, якою версією говорить співрозмовник. Тобто видача номера — це ще й прибирання за попереднім власником. Номер прив'язує з'єднання до конкретного слота в статичних масивах бібліотеки, де лежить усе: де саме посеред [пакета](root:sys-dron/mavlink-packet) зупинився розбір, обрана версія, підпис і лічильники, з яких станція рахує втрати. Що з цим станом робиться далі — у темі [обробки MAVLink](root:sys-dron/mavlink-handling).

`freeMavlinkChannel()` перевіряє рівно одне: чи не передали йому 255. Подвійне звільнення дійсного номера тихо скине біт удруге — і якщо цей номер уже встигли видати іншому з'єднанню, два джерела осядуть в одному стані розбору. Симптом на екрані буде далекий від причини: стрибучий відсоток утрат і помилки контрольної суми на каналі, з яким усе гаразд.

> 🔧 **Навіщо це.** Правило користування цією трійкою одне: **не кличте `allocateMavlinkChannel()` самі**. Номер видає й повертає менеджер у межах народження й смерті з'єднання, і робить це рівно по одному разу. Код розширення, що відкриває свій сокет повз менеджер і бере номер власноруч, отримує рівно ті два симптоми, від яких найдовше шукають причину: канал без відповідного з'єднання в списку та номер, який ніхто не поверне.

## Заборона нових з'єднань

```cpp
void setConnectionsSuspended(const QString &reason);   // прапорець + текст причини
void setConnectionsAllowed();                          // зняти прапорець
```

Обидва методи визначені прямо в заголовку й лише переставляють прапорець. Важлива тут не механіка, а межа дії: прапорець перевіряє **секундний прохід автопідключення** — саме він не піднімає нових каналів, поки заборона стоїть, — і код, що показує людині причину. Явний виклик `createConnectedLink` цей прапорець не блокує. Тобто це заборона для станції, а не для користувача, і саме тому вона перша дія в `shutdown()`: інакше автопідключення підняло б назад канал, розірваний рядком нижче.

## Властивості та сигнали

Список каналів на екрані налаштувань підписаний на ці властивості менеджера:

| Властивість | Тип | Сповіщення | Що це |
|---|---|---|---|
| `linkConfigurations` | `QmlObjectListModel *` | сталий вказівник | модель списку описів; змінюється не вказівник, а вміст моделі |
| `linkTypeStrings` | `QStringList` | сталий | назви типів каналів у порядку переліку `LinkType` |
| `isBluetoothAvailable` | `bool` | `isBluetoothAvailableChanged` | чи є сенс показувати тип «Bluetooth» |
| `mavlinkSupportForwardingEnabled` | `bool` | `mavlinkSupportForwardingEnabledChanged` | чи ввімкнено канал підтримки пересилання |
| `serialPorts` | `QStringList` | `commPortsChanged` | системні шляхи портів (`/dev/ttyACM0`, `COM3`) |
| `serialPortStrings` | `QStringList` | `commPortStringsChanged` | ті самі порти в людському вигляді, для випадного списку |
| `serialBaudRates` | `QStringList` | сталий | підтримувані швидкості серійного порту |

Три серійні властивості існують лише в збірці **з** підтримкою серійного порту: під прапорцем `QGC_NO_SERIAL_LINK` вони з класу зникають разом із відповідними методами. Звертання до них із декларативного шару в такій збірці дасть невизначене значення, а не помилку компіляції, — тож у власній збірці без серійного порту цей шматок інтерфейсу треба ховати явно. Про самі різновиди каналів і їхні налаштування — у темі [типи каналів](root:sys-dron/link-types).

Сигналів у менеджера рівно чотири, і всі — про зміну властивостей:

```cpp
void isBluetoothAvailableChanged();
void mavlinkSupportForwardingEnabledChanged();
void commPortStringsChanged();
void commPortsChanged();
```

Важливіше те, чого в цьому переліку **нема**. Менеджер не має сигналів «канал з'єднався» чи «канал розірвався». Про з'єднання й розрив повідомляє саме з'єднання своїми `connected` / `disconnected`, а для інтерфейсу це видно як зміна `linkActive` на описі. Хто хоче знати про появу апарата, слухає не менеджер каналів, а [підсистему апаратів](root:sys-dron/multi-vehicle) — канал і апарат тут навмисно різні події.

## Контракт `LinkConfiguration`

Список каналів на екрані показує **описи**, тож саме ці властивості й читає кожен рядок.

| Властивість | Тип | Доступ | Сповіщення | Що означає |
|---|---|---|---|---|
| `name` | `QString` | читання й запис | `nameChanged` | ім'я в списку; його ж міняє завершення правки |
| `link` | `LinkInterface *` | читання | `linkChanged` | **сирий** вказівник на живе з'єднання або `nullptr` |
| `linkActive` | `bool` | читання | `linkActiveChanged` | «станція вважає цей канал своїм» — ширше, ніж «сокет відкрито» |
| `linkType` | `LinkType` | читання | сталий | тип, заданий при створенні; змінити не можна |
| `dynamic` | `bool` | читання й запис | `dynamicChanged` | опис вигадав застосунок сам — на диск не потрапить |
| `autoConnect` | `bool` | читання й запис | `autoConnectChanged` | станція піднімає цей канал сама |
| `highLatency` | `bool` | читання й запис | `highLatencyChanged` | канал із великою затримкою (супутник) — інший темп запитів |
| `settingsURL` | `QString` | читання | сталий | файл редактора налаштувань саме цього типу |
| `settingsTitle` | `QString` | читання | сталий | заголовок цього редактора |

Дві властивості тут поводяться не так, як здається з назви.

**`link` повертає сирий вказівник, і зберігати його не можна.** Усередині опис тримає з'єднання **слабко** і на кожен виклик питає, чи воно ще живе; поверненого сирого вказівника вистачає рівно на те, щоб щось із нього прочитати просто зараз. Якщо вказівник потрібен вам довше — беріть спільний через `sharedLinkInterfacePointerForLink()` і перевіряйте на порожність.

**`linkActive` — не «сокет відкрито».** Для опису з автопідключенням вона лишається правдивою і в проміжках між спробами підняти канал: істина тут «станція працює над цим каналом», а не «саме цієї мілісекунди байти йдуть». Інакше при поганому зв'язку кнопка блимала б щосекунди.

Крім властивостей, опис має набір методів, доступних лише з C++ — на них стоїть уся логіка перепідключення:

```cpp
bool isForwarding() const;             void setForwarding(bool forwarding = true);
bool suppressAutoReconnect() const;    void setSuppressAutoReconnect(bool suppress);
bool autoConnectStarted() const;       void setAutoConnectStarted(bool started);

bool reconnectReady() const;           // чи минула витримка після невдалої спроби
void noteReconnectAttempt();           // зафіксувати невдачу — витримка подвоїться
void resetReconnectBackoff();          // явне під'єднання скидає лічильник
void noteConnected();                  void noteDisconnected();

virtual void copyFrom(const LinkConfiguration *source);
virtual LinkType type() const = 0;
virtual void loadSettings(QSettings &settings, const QString &root) = 0;
virtual void saveSettings(QSettings &settings, const QString &root) const = 0;

static LinkConfiguration *createSettings(int type, const QString &name);
static LinkConfiguration *duplicateSettings(const LinkConfiguration *source);
```

Три булеві прапорці — `suppressAutoReconnect`, `autoConnectStarted` і `dynamic` — разом визначають, чи чіпатиме цей опис секундний прохід автопідключення. Перший означає «розрив був волею людини, не збоєм», другий — «цей опис уже запускали в цьому сеансі», третій — «опис вигадала станція, зберігати його не треба». Перелік `LinkType` — `TypeSerial`, `TypeUdp`, `TypeTcp`, `TypeBluetooth`, `TypeMock`, `TypeLogReplay`, `TypeLast` — задає і порядок рядків у `linkTypeStrings`, і те, який клас з'єднання народиться з опису.

## Що можна робити з `LinkInterface`

Половина методів менеджера бере або віддає `LinkInterface *`, тож мінімум із його контракту потрібен і тут.

| Підпис | Що робить | Потік |
|---|---|---|
| `virtual void disconnect() = 0` | розірвати; реалізації зобов'язані переживати повторний виклик | ⚠️ |
| `virtual bool isConnected() const = 0` | чи справді відкрито порт або сокет саме зараз | ⚠️ |
| `uint8_t mavlinkChannel() const` | номер каналу розбирача цього з'єднання | 🔒 |
| `bool mavlinkChannelIsSet() const` | чи номер уже видано — перевіряти **перед** використанням | 🔒 |
| `SharedLinkConfigurationPtr linkConfiguration()` | опис, за яким це з'єднання народилося (міцне посилання) | 🔒 |
| `void writeBytesThreadSafe(const char *bytes, int length)` | відправити сирі байти | 🔒 |
| `void sendMessageThreadSafe(mavlink_message_t &message)` | єдина точка відправки повідомлення | 🔒 |
| `void addVehicleReference()` / `void removeVehicleReference()` | облік апаратів на каналі: нуль — канал рветься сам | 🔒 |
| `virtual bool isLogReplay() const` | це відтворення записаного польоту, а не живий канал | 🔒 |
| `virtual bool isSecureConnection() const` | канал сам по собі захищений | 🔒 |

Конструктор `LinkInterface` захищений, а `LinkManager` оголошено дружнім класом — створити з'єднання повз менеджер не можна навіть навмисно. Сигнали з'єднання: `bytesReceived(LinkInterface*, QByteArray)`, `bytesSent(...)`, `connected()`, `disconnected()`, `communicationError(QString title, QString error)`.

Лічильник апаратів (`addVehicleReference` / `removeVehicleReference`) — не той самий лічильник, що в спільному вказівнику. Перший вирішує, **чи має сенс тримати канал відкритим**; другий — **чи можна звільнити пам'ять**. Об'єкт цілком може бути вже розірваним, поки на нього є посилання з черги подій, і навпаки. Куди при цьому потрапляє кожне повідомлення, коли апаратів на каналі кілька, — у темі про [маршрутизацію](root:sys-dron/message-routing).

## Мінімальний робочий виклик

Найчастіша операція коду підсистеми — пройтися по живих каналах і щось відправити. Ось вона цілком, із усіма перевірками, які контракт вимагає:

```cpp
void broadcastGcsHeartbeat(uint8_t sysid, uint8_t compid)
{
    // links() віддає КОПІЮ списку; спільні вказівники в ній тримають
    // з'єднання живими доти, доки жива сама копія
    for (const SharedLinkInterfacePtr &link : LinkManager::instance()->links()) {
        if (!link->isConnected() || !link->mavlinkChannelIsSet()) {
            continue;                  // ще не з'єдналося або номера каналу нема
        }

        mavlink_message_t msg;
        mavlink_msg_heartbeat_pack_chan(
            sysid, compid, link->mavlinkChannel(), &msg,
            MAV_TYPE_GCS, MAV_AUTOPILOT_INVALID,
            MAV_MODE_MANUAL_ARMED, 0, MAV_STATE_ACTIVE);

        link->sendMessageThreadSafe(msg);   // єдина точка відправки
    }
}
```

Три речі тут не прикраса. Перевірка `mavlinkChannelIsSet()` потрібна тому, що номер видається окремим кроком і між створенням об'єкта та видачею є вузьке вікно. Номер каналу йде в саму функцію пакування (`_pack_chan`), бо порядковий номер повідомлення веде **стан каналу**, а не відправник — послати той самий `msg` у два канали означає збити нумерацію обом. І цикл ходить копією списку: цього досить, щоб з'єднання не померло під ногами, навіть якщо інший потік саме цієї миті прибирає його з менеджера.

Зворотний бік цієї зручності — не тримайте `SharedLinkInterfacePtr` у полі довше, ніж треба. Поки ваше посилання живе, живе й об'єкт з'єднання, хоч сокет давно закрито; це не аварія, але пам'ять і підписки на сигнали тримаються без причини.

## Зведення пасток

- `cancelConfigurationEditing` бере **копію**, а не оригінал: усередині — `delete config`.
- `endConfigurationEditing` видаляє **другий** аргумент; не викликати ні його, ні `cancel` — витік.
- `removeConfiguration` знімає опис зі списків, але сам об'єкт не видаляє.
- Об'єкт із `createConfiguration` не має батька: між ним і `endCreateConfiguration` не має бути нічого зайвого.
- `createConnectedLink` у наборі для інтерфейсу повертає `void`; чесний `bool` дає лише варіант зі спільним вказівником на опис.
- `containsLink` — знімок минулого; для дії беріть `sharedLinkInterfacePointerForLink` і перевіряйте на порожність.
- `link` в описі — сирий вказівник, не зберігати.
- `allocateMavlinkChannel` повз менеджер не кликати; `freeMavlinkChannel` захищений лише від значення 255.
- `shutdown()` блокує, доки не зникне останній апарат.
