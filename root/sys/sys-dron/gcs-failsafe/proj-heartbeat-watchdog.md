# ⚙️ Програмний сторож пульсу та монітор якості каналу телеметрії

У розподілених системах безпілотного керування наземна станція (GCS) та бортовий польотний контролер (FC) функціонують асинхронно через ненадійний радіоканал. Щоб своєчасно розпізнати аварійний розрив зв'язку, сторожовий таймер (Watchdog) мусить безперервно відстежувати часові інтервали між пакетами пульсу (`HEARTBEAT`) та розраховувати відсоток втрат пакетів за ковзним вікном.

Простий таймер, що реагує лише на одноразове перевищення порогу тиші, є вразливим до короткочасних завмирань радіосигналу: поодинокий пропуск пакетів через інтерференцію не повинен призводити до негайної паніки оператора, проте стійка втрата понад встановлений ліміт зобов'язана беззастережно переводити систему в аварійний стан.

---

### Архітектура та розподіл потоків у наземній станції

У реальних додатках станцій керування (таких як QGroundControl або Mission Planner) обробка зв'язку розділена між декількома паралельними системними потоками. Такий поділ критично важливий для запобігання хибним спрацьовуванням аварійних таймерів.

```
+-------------------------------------------------------------------------------+
|                       НАЗЕМНА СТАНЦІЯ КЕРУВАННЯ (GCS)                         |
|                                                                               |
|  +--------------------+    MAVLink кадри    +------------------------------+  |
|  | Потік вводу/виводу | ------------------> | Потік диспетчеризації        |  |
|  | (I/O Thread)       |                     | та аналізу черги (Link Watch)|  |
|  +--------------------+                     +------------------------------+  |
|           ^                                                |                  |
|           | Читання сокета / COM-порту                     | Стан лінку       |
|           v                                                v                  |
|  +--------------------+                     +------------------------------+  |
|  | Апаратний модем    |                     | Графічний потік інтерфейсу   |  |
|  | (UART / UDP / LTE) |                     | (UI Event Loop / Рендеринг)  |  |
|  +--------------------+                     +------------------------------+  |
+-------------------------------------------------------------------------------+
```

Потік вводу/виводу (I/O Thread) безперервно очікує надходження сирих байтів з мережевого сокета або віртуального послідовного порту. Його єдине завдання — швидко вичитати дані з системного буфера, розпарсити заголовок кадру MAVLink, зафіксувати поточну мітку монотонного часу та передати розпізнаний пакет до диспетчера.

Потік диспетчеризації та аналізу черги містить екземпляр сторожового таймера `LinkWatchdog`. Він виконує математичний аналіз номерів послідовності, оновлює ковзне вікно втрат, розраховує час кругового обігу RTT і визначає стан каналу.

Графічний потік інтерфейсу (UI Event Loop) відповідає за візуалізацію 3D-мапи, штучного горизонту та віджетів телеметрії. Якщо інтерфейс зазнає короткочасного зависання через завантаження важких супутникових знімків, це не повинно впливати на точність сторожового таймера. Прив'язка таймера до графічного циклу призвела б до того, що під час будь-якого зависання інтерфейсу станція вважала б зв'язок із дроном втраченим.

### Математичні основи оцінки якості каналу

Якість каналу передачі даних у реальному часі визначається двома основними метриками: часовою затримкою доставки (Round-Trip Time, RTT) та коефіцієнтом втрати пакетів (Packet Loss Rate, PLR).

#### 1. Ковзне вікно втрат пакетів на основі бітової маски
Кожен пакет MAVLink містить у заголовку 8-бітне поле послідовності `seq` (від `0` до `255`). Послідовність інкрементується на одиницю з кожним відправленим кадром. Знаючи попередній номер `seq_{prev}` та щойно отриманий `seq_{curr}`, модуль фіксує пропуск:

```
втрачено = (seq_{curr} - seq_{prev} - 1) mod 256
```

Для ефективного збереження історії прийому останніх 64 пакетів без виділення динамічної пам'яті використовується 64-бітне беззнакове число (`uint64_t`). Кожен отриманий пакет зсуває маску ліворуч на кількість пропущених позицій і записує одиницю в молодший біт.

Кількість успішно доставлених пакетів у вікні розраховується через апаратну операцію підрахунку одиничних бітів (`popcount`):

```
PLR = (1 - popcount(mask) / 64) · 100 %
```

Якщо за останні 64 кадри доставлено 48 пакетів, коефіцієнт втрат становить:
```
PLR = (1 - 48 / 64) · 100 % = (1 - 0.75) · 100 % = 25 %
```

#### 2. Експоненційно зважене ковзне середнє для затримки (EWMA)
Для фільтрації випадкових стрибків затримки (джитеру) оцінка поточного часу кругового обігу `RTT_{est}` оновлюється за формулою експоненційного згладжування:

```
RTT_{est} = (1 - α) · RTT_{est} + α · RTT_{meas}
```

де коефіцієнт згладжування `α = 0.125` (1/8) забезпечує стійкість оцінки до поодиноких затримок у радіомодемі, одночасно швидко реагуючи на систематичну деградацію каналу.

Вибір коефіцієнта `1/8` є класичним для мережевих протоколів (зокрема алгоритму Якобсона в TCP): множення та ділення на степені двійки реалізуються швидкими операціями бітового зсуву без залучення арифметики з рухомою комою.

#### 3. Оцінка дисперсії затримки та динамічний адаптивний таймаут
У радіоканалах зі змінним завантаженням (наприклад, при паралельній передачі відеопотоку або в стільникових мережах LTE) фіксований таймаут у 3.5 секунди може бути або занадто грубим, або провокувати хибні тривоги.

Для адаптивного контролю обчислюється середнє абсолютне відхилення затримки `RTT_{var}`:

```
RTT_{var} = (1 - β) · RTT_{var} + β · |RTT_{meas} - RTT_{est}|
```

де коефіцієнт `β = 0.25` (1/4). Динамічний аварійний таймаут для окремих запитів розраховується як `T_{timeout} = RTT_{est} + 4 · RTT_{var}`. Якщо відповідь на критичну команду не надходить протягом цього часу, станція негайно повторює запит або інформує оператора про затримку виконання.

### Архітектура скінченного автомата стану лінку

Монітор лінку реалізує скінченний автомат із трьома основними станами:

```
+------------------+   Δt >= 1500 ms   +--------------------+   Δt >= 3500 ms   +------------------+
| LINK_CONNECTED   | ----------------> |   LINK_DEGRADED    | ----------------> |    LINK_LOST     |
| (Нормальний рух) | <---------------- | (Жовте застереження)|                  | (Аварійний стан) |
+------------------+   Отримано кадри  +--------------------+                  +------------------+
        ^                                                                               |
        |                      Отримано 3 валідні Heartbeat поспіль                     |
        +-------------------------------------------------------------------------------+
```

#### Стан 1: Штатне з'єднання (`LINK_STATE_CONNECTED`)
У цьому стані інтервал часу від моменту прийому останнього пакета пульсу не перевищує поріг застереження: `Δt < T_WARNING` (типово 1500 мс). Коефіцієнт втрат пакетів у ковзному вікні перебуває в допустимих межах: `PLR ≤ 40 %`.

Усі підсистеми наземної станції функціонують у штатному режимі. Оператор має повний доступ до надсилання будь-яких команд: зміни польотних режимів, корекції навігаційних точок місії, прямого пілотування через джойстик та калібрування сенсорів.

#### Стан 2: Деградація сигналу (`LINK_STATE_DEGRADED`)
Стан деградації активується за однієї з двох умов:
- Інтервал відсутності пульсу перевищив поріг застереження, але ще не досяг аварійного порогу: `1500 мс ≤ Δt < 3500 мс`.
- Коефіцієнт втрат пакетів за останні 64 кадри перевищив допустиму норму: `PLR > 40 %`, навіть якщо поодинокі кадри пульсу продовжують надходити.

У стані деградації інтерфейс GCS забарвлює віджет лінку в жовтий колір і видає текстове застереження. Щоб уникнути ризику спотворення даних, станція блокує надсилання критичних налаштувань (запис параметрів, оновлення польотного плану), проте дозволяє базовий моніторинг.

#### Стан 3: Аварійний розрив (`LINK_STATE_LOST`)
Цей стан фіксується, коли тривалість повної тиші в ефірі перевищує поріг Failsafe: `Δt ≥ T_TIMEOUT` (типово 3500–5000 мс).

Станція фіксує повну втрату контакту з безпілотним судном:
- Генерується звукова та візуальна тривога підвищеної гучності («Telemetry lost»).
- Інтерфейс блокує всі органи ручного пілотування, а віртуальні стики джойстика примусово скидаються в нейтральне положення.
- Очищається черга непідтверджених команд керування, щоб запобігти їх раптовому виконанню при відновленні зв'язку.
- Станція переходить у режим пасивного радіолокаційного очікування, припускаючи, що автопілот на борту перейшов до виконання власного аварійного алгоритму RTL або Land.

#### Механізм гістерезису при відновленні каналу
Коли апарат перебуває на межі зони впевненого прийому, радіосигнал часто з'являється уривками. Якби станція поверталася в стан `CONNECTED` відразу після отримання одного-єдиного кадру, це викликало б безперервне миготіння інтерфейсу та брязкіт аварійних тривог.

Для запобігання цьому явищу реалізовано обов'язковий лічильник відновлення `consecutive_valid_hb`. Перехід із `LINK_STATE_LOST` назад у `LINK_STATE_CONNECTED` дозволяється виключно після того, як станція отримає щонайменше 3 послідовні кадри `HEARTBEAT` без жодного пропуску.

### Адаптивне керування пропускною здатністю каналу

Коли сторожовий таймер фіксує перехід каналу в стан `DEGRADED`, наземна станція не повинна пасивно очікувати повного обриву зв'язку. У сучасних системах реалізовано алгоритм динамічного дроселювання потоків телеметрії (Dynamic Stream Rate Throttling).

Радіомодеми мають обмежену швидкість передачі (типово 57600 бод, що відповідає приблизно 4–5 КБ/с корисного навантаження). Якщо радіоефір засмічений, автопілот намагається надіслати більше даних, ніж модем здатен передати. Буфер передавача переповнюється (`RADIO_STATUS.txbuf > 80 %`), і пакети пульсу починають відкидатися.

При виявленні стану деградації станція автоматично надсилає на борт серію команд `MAV_CMD_SET_MESSAGE_INTERVAL`, знижуючи частоту другорядних повідомлень:
- Частота передачі стану батареї (`BATTERY_STATUS`) зменшується з 2 Гц до 0.5 Гц.
- Частота передачі сирих даних сенсорів (`RAW_IMU`, `SCALED_PRESSURE`) знижується з 10 Гц до 1 Гц.
- Пріоритет зберігається виключно за критичними навігаційними повідомленнями `GLOBAL_POSITION_INT` (5 Гц) та `ATTITUDE` (10 Гц).

Це дозволяє миттєво розвантажити вихідний буфер радіомодема, знизити джитер і повернути канал зв'язку в штатний стан `CONNECTED` без втручання оператора.

### Повна реалізація монітора каналу

Нижче наведено модульний вихідний код сторожового таймера та аналізатора якості каналу. Програмний модуль спроектовано для роботи в реальному часі без динамічного виділення пам'яті під час польоту.

```c
#include <stdint.h>
#include <stdbool.h>

#define LINK_WARNING_TIMEOUT_MS  1500u
#define LINK_FAILSAFE_TIMEOUT_MS 3500u
#define LINK_RECOVERY_PACKETS    3u
#define PACKET_WINDOW_SIZE       64u

typedef enum {
    LINK_STATE_LOST = 0,
    LINK_STATE_DEGRADED = 1,
    LINK_STATE_CONNECTED = 2
} link_state_t;

typedef struct {
    uint32_t last_heartbeat_ms;
    uint32_t last_any_packet_ms;
    uint32_t smoothed_rtt_ms;
    uint32_t rtt_variance_ms;
    uint8_t  last_sequence;
    uint64_t packet_history_mask; // 1 = отримано, 0 = втрачено
    uint32_t consecutive_valid_hb;
    link_state_t current_state;
    bool has_received_any;
} link_monitor_t;

// Підрахунок кількості одиничних бітів у 64-бітному числі (алгоритм Браяна Кернігана)
static inline uint32_t count_set_bits(uint64_t v) {
    uint32_t count = 0;
    while (v > 0) {
        v &= (v - 1);
        count++;
    }
    return count;
}

// Ініціалізація внутрішнього стану монітора
void link_monitor_init(link_monitor_t *mon) {
    mon->last_heartbeat_ms = 0;
    mon->last_any_packet_ms = 0;
    mon->smoothed_rtt_ms = 0;
    mon->rtt_variance_ms = 0;
    mon->last_sequence = 0;
    mon->packet_history_mask = 0;
    mon->consecutive_valid_hb = 0;
    mon->current_state = LINK_STATE_LOST;
    mon->has_received_any = false;
}

// Реєстрація надходження будь-якого кадру MAVLink для аналізу лічильника seq
void link_monitor_feed_packet(link_monitor_t *mon, uint8_t seq, uint32_t now_ms) {
    mon->last_any_packet_ms = now_ms;
    if (!mon->has_received_any) {
        mon->has_received_any = true;
        mon->last_sequence = seq;
        mon->packet_history_mask = 1ULL;
        return;
    }

    uint8_t diff = (uint8_t)(seq - mon->last_sequence);
    if (diff > 0 && diff < 128) {
        // Зсув маски на кількість пропущених пакетів
        if (diff >= PACKET_WINDOW_SIZE) {
            mon->packet_history_mask = 0;
        } else {
            mon->packet_history_mask <<= diff;
        }
        mon->packet_history_mask |= 1ULL; // Поточний пакет успішно отримано
        mon->last_sequence = seq;
    } else if (diff == 0) {
        // Дублікат кадру: стан послідовності не змінюється
    } else {
        // Запізнілий пакет або пакет з іншого каналу
    }
}

// Оновлення згладженої затримки RTT та її варіації за формулою EWMA
void link_monitor_feed_rtt(link_monitor_t *mon, uint32_t measured_rtt_ms) {
    if (mon->smoothed_rtt_ms == 0) {
        mon->smoothed_rtt_ms = measured_rtt_ms;
        mon->rtt_variance_ms = measured_rtt_ms / 2;
    } else {
        int32_t delta = (int32_t)measured_rtt_ms - (int32_t)mon->smoothed_rtt_ms;
        if (delta < 0) delta = -delta;
        
        // Варіація RTT: beta = 1/4 -> (3 * var + delta) / 4
        mon->rtt_variance_ms = (mon->rtt_variance_ms * 3u + (uint32_t)delta) >> 2;
        
        // Згладжене RTT: alpha = 1/8 -> (7 * smoothed + measured) / 8
        mon->smoothed_rtt_ms = (mon->smoothed_rtt_ms * 7u + measured_rtt_ms) >> 3;
    }
}

// Реєстрація надходження службового кадру пульсу (HEARTBEAT)
void link_monitor_feed_heartbeat(link_monitor_t *mon, uint8_t seq, uint32_t now_ms) {
    link_monitor_feed_packet(mon, seq, now_ms);
    mon->last_heartbeat_ms = now_ms;
    mon->consecutive_valid_hb++;

    if (mon->current_state == LINK_STATE_LOST) {
        if (mon->consecutive_valid_hb >= LINK_RECOVERY_PACKETS) {
            mon->current_state = LINK_STATE_CONNECTED;
        }
    }
}

// Обчислення відсотка втрачених пакетів у ковзному вікні (діапазон 0..100 %)
uint8_t link_monitor_get_loss_percent(const link_monitor_t *mon) {
    if (!mon->has_received_any) return 100;
    uint32_t received = count_set_bits(mon->packet_history_mask);
    return (uint8_t)(100u - (received * 100u / PACKET_WINDOW_SIZE));
}

// Розрахунок адаптивного порогу таймауту на основі RTT та варіації
uint32_t link_monitor_get_adaptive_timeout_ms(const link_monitor_t *mon) {
    if (mon->smoothed_rtt_ms == 0) {
        return LINK_FAILSAFE_TIMEOUT_MS;
    }
    uint32_t timeout = mon->smoothed_rtt_ms + (mon->rtt_variance_ms << 2);
    if (timeout < 1000u) timeout = 1000u;
    if (timeout > LINK_FAILSAFE_TIMEOUT_MS) timeout = LINK_FAILSAFE_TIMEOUT_MS;
    return timeout;
}

// Періодична функція оновлення автоматів станів (викликається в циклі таймера)
link_state_t link_monitor_update(link_monitor_t *mon, uint32_t now_ms) {
    if (!mon->has_received_any) {
        mon->current_state = LINK_STATE_LOST;
        return mon->current_state;
    }

    uint32_t dt = now_ms - mon->last_heartbeat_ms;
    uint8_t loss = link_monitor_get_loss_percent(mon);

    if (dt >= LINK_FAILSAFE_TIMEOUT_MS) {
        mon->current_state = LINK_STATE_LOST;
        mon->consecutive_valid_hb = 0;
    } else if (dt >= LINK_WARNING_TIMEOUT_MS || loss > 40) {
        if (mon->current_state != LINK_STATE_LOST) {
            mon->current_state = LINK_STATE_DEGRADED;
        }
    } else {
        if (mon->current_state == LINK_STATE_DEGRADED) {
            mon->current_state = LINK_STATE_CONNECTED;
        }
    }

    return mon->current_state;
}
```

```cpp
#include <cstdint>
#include <chrono>
#include <functional>
#include <bitset>
#include <algorithm>

enum class LinkState {
    Lost = 0,
    Degraded = 1,
    Connected = 2
};

class LinkWatchdog {
public:
    using Milliseconds = std::chrono::milliseconds;
    using TimePoint = std::chrono::steady_clock::time_point;

    struct Config {
        Milliseconds warningTimeout{1500};
        Milliseconds failsafeTimeout{3500};
        uint32_t recoveryHeartbeats{3};
        uint8_t lossThresholdPercent{40};
    };

    explicit LinkWatchdog(Config config = {})
        : config_(config), state_(LinkState::Lost) {}

    // Реєстрація зворотного виклику для оповіщення про зміну стану лінку
    void onStateChanged(std::function<void(LinkState oldState, LinkState newState)> callback) {
        stateCallback_ = std::move(callback);
    }

    // Реєстрація будь-якого отриманого MAVLink пакета для підрахунку втрат
    void feedPacket(uint8_t seq, TimePoint now = std::chrono::steady_clock::now()) {
        lastAnyPacketTime_ = now;
        if (!hasReceivedAny_) {
            hasReceivedAny_ = true;
            lastSequence_ = seq;
            packetWindow_.reset();
            packetWindow_.set(0, true);
            return;
        }

        uint8_t diff = static_cast<uint8_t>(seq - lastSequence_);
        if (diff > 0 && diff < 128) {
            if (diff >= packetWindow_.size()) {
                packetWindow_.reset();
            } else {
                packetWindow_ <<= diff;
            }
            packetWindow_.set(0, true);
            lastSequence_ = seq;
        }
    }

    // Оновлення розрахункової затримки RTT та варіації за алгоритмом EWMA
    void feedRtt(Milliseconds measuredRtt) noexcept {
        if (smoothedRtt_ == Milliseconds{0}) {
            smoothedRtt_ = measuredRtt;
            rttVariance_ = measuredRtt / 2;
        } else {
            auto delta = std::chrono::abs(measuredRtt - smoothedRtt_);
            rttVariance_ = (rttVariance_ * 3 + delta) / 4;
            smoothedRtt_ = (smoothedRtt_ * 7 + measuredRtt) / 8;
        }
    }

    // Реєстрація кадру пульсу HEARTBEAT
    void feedHeartbeat(uint8_t seq, TimePoint now = std::chrono::steady_clock::now()) {
        feedPacket(seq, now);
        lastHeartbeatTime_ = now;
        consecutiveHeartbeats_++;

        if (state_ == LinkState::Lost && consecutiveHeartbeats_ >= config_.recoveryHeartbeats) {
            transitionTo(LinkState::Connected);
        }
    }

    // Поточний коефіцієнт втрат пакетів у ковзному вікні (0..100 %)
    [[nodiscard]] uint8_t packetLossPercent() const noexcept {
        if (!hasReceivedAny_) return 100;
        size_t received = packetWindow_.count();
        return static_cast<uint8_t>(100 - (received * 100 / packetWindow_.size()));
    }

    // Поточна згладжена затримка передачі
    [[nodiscard]] Milliseconds smoothedRtt() const noexcept {
        return smoothedRtt_;
    }

    // Поточна варіація затримки (джитер)
    [[nodiscard]] Milliseconds rttVariance() const noexcept {
        return rttVariance_;
    }

    // Розрахунок адаптивного таймауту відповіді
    [[nodiscard]] Milliseconds adaptiveTimeout() const noexcept {
        if (smoothedRtt_ == Milliseconds{0}) {
            return config_.failsafeTimeout;
        }
        auto timeout = smoothedRtt_ + (rttVariance_ * 4);
        return std::clamp(timeout, Milliseconds{1000}, config_.failsafeTimeout);
    }

    // Періодичне оновлення внутрішніх таймерів
    LinkState update(TimePoint now = std::chrono::steady_clock::now()) {
        if (!hasReceivedAny_) {
            transitionTo(LinkState::Lost);
            return state_;
        }

        auto dt = std::chrono::duration_cast<Milliseconds>(now - lastHeartbeatTime_);
        uint8_t loss = packetLossPercent();

        if (dt >= config_.failsafeTimeout) {
            consecutiveHeartbeats_ = 0;
            transitionTo(LinkState::Lost);
        } else if (dt >= config_.warningTimeout || loss > config_.lossThresholdPercent) {
            if (state_ != LinkState::Lost) {
                transitionTo(LinkState::Degraded);
            }
        } else {
            if (state_ == LinkState::Degraded) {
                transitionTo(LinkState::Connected);
            }
        }

        return state_;
    }

    [[nodiscard]] LinkState state() const noexcept { return state_; }
    [[nodiscard]] bool isConnected() const noexcept { return state_ == LinkState::Connected; }

private:
    void transitionTo(LinkState newState) {
        if (state_ != newState) {
            LinkState oldState = state_;
            state_ = newState;
            if (stateCallback_) {
                stateCallback_(oldState, newState);
            }
        }
    }

    Config config_;
    LinkState state_;
    TimePoint lastHeartbeatTime_{};
    TimePoint lastAnyPacketTime_{};
    Milliseconds smoothedRtt_{0};
    Milliseconds rttVariance_{0};
    uint8_t lastSequence_{0};
    uint32_t consecutiveHeartbeats_{0};
    std::bitset<64> packetWindow_{};
    bool hasReceivedAny_{false};
    std::function<void(LinkState, LinkState)> stateCallback_;
};
```

### Інженерні пастки та крайові випадки реалізації

#### 1. Арифметика переповнення 8-бітного лічильника `seq`
Поле послідовності `seq` у протоколі MAVLink має розмір рівно 1 байт (значення від `0` до `255`). Після кадру `255` передавач транслює кадр `0`. При простому порівнянні `seq_curr > seq_prev` перехід `255 -> 0` помилково інтерпретувався б як надходження застарілого пакета з минулого.

Правильне обчислення різниці полягає у беззнаковому 8-бітному відніманні: `(uint8_t)(seq_curr - seq_prev)`. Завдяки властивостям доповняльного коду:
```
(uint8_t)(0 - 255) = 1    [перехід через нуль без втрат]
(uint8_t)(2 - 255) = 3    [перехід через нуль із втратою 2 пакетів]
```
Якщо отримана різниця перебуває в діапазоні `1..127`, пакет вважається новішим; якщо різниця перевищує `128`, пакет кваліфікується як запізнілий дублікат або результат реверсу черги.

#### 2. Захист від стрибків системного часу ОС
Використання функцій календарного часу (`gettimeofday`, `time()`, `std::chrono::system_clock`) є неприпустимим у сторожових таймерах. Під час польоту операційна система ноутбука станції може автоматично скоригувати час через службу NTP або підключений GPS-модуль. Стрибок годинника назад на 5 секунд призведе до замерзання таймера тиші, а стрибок уперед — до миттєвого хибного спрацьовування тривоги втрати зв'язку.

Єдиним надійним джерелом часу є монотонний лічильник процесора: `CLOCK_MONOTONIC_RAW` у стандарті POSIX або `std::chrono::steady_clock` у C++, які гарантовано не мають зворотного ходу та не піддаються зовнішнім стрибкам.

#### 3. Пастка буферизації у віртуальних COM-портах
Більшість радіомодемів SiK підключаються до станції через USB-to-UART мости (FTDI, CP2102, CH340). Драйвер операційної системи має внутрішній буфер прийому (FIFO). Якщо додаток GCS зависає на кілька секунд через рендеринг складної 3D-мапи, буфер драйвера наповнюється пакетами.

Після розблокування графічного потоку GCS миттєво зчитує сотні застарілих пакетів поспіль із нульовою дельтою часу. Необхідно, щоб сторожовий таймер прив'язував мітки часу не до моменту обробки пакета в UI, а безпосередньо до моменту його вичитування з сокета в окремому низькорівневому потоці вводу/виводу.

#### 4. Тестування поведінки методом ін'єкції збоїв (Fault Injection)
При розробці та верифікації модулів зв'язку обов'язковим етапом є стрес-тестування на програмному симуляторі (Software-in-the-Loop, SITL). Штучний емулятор каналу навмисно вносить випадкову затримку від 100 до 3000 мс і відкидає до 50 % пакетів MAVLink за законом розподілу Бернуллі або моделлю Гілберта-Елліота (пакетні сплески втрат).

Таке тестування дозволяє переконатися, що сторожовий таймер коректно фільтрує поодинокі провали радіосигналу, своєчасно сигналізує оператору про небезпечну деградацію каналу і надійно блокує надсилання застарілих команд у моменти відновлення зв'язку.

#### 5. Багатопотокова синхронізація та потокобезпечність (Thread Safety)
Оскільки метод `feedPacket()` викликається з високочастотного мережевого потоку вводу/виводу, а метод `update()` опитується системним таймером або диспетчером інтерфейсу, критичні структури даних мають бути потокобезпечними.

У C++ для досягнення максимальної швидкодії без блокування м'ютексами поля `lastHeartbeatTime_`, `lastSequence_` та лічильник `consecutiveHeartbeats_` можуть бути оформлені як атомарні типи `std::atomic<uint32_t>`. Це гарантує відсутність стану гонитви (Race Condition) при надходженні сотень телеметричних повідомлень на секунду без накладних витрат на перемикання контексту ядра операційної системи.

#### 6. Верифікація автомата за допомогою детермінованих юніт-тестів
Для перевірки коректності переходів скінченного автомата без тривалого очікування реального часу в юніт-тестах застосовується техніка штучного прокручування монотонного годинника (Mock Clock).

Тестовий набір перевіряє такі критичні інваріанти:
1. **Тест стабільного потоку:** Послідовне надходження 100 пакетів із дельтою 1000 мс повинно утримувати стан `Connected` з нульовим відсотком втрат.
2. **Тест деградації:** Пропуск 5 пакетів поспіль за збереження окремих повідомлень переводить систему в `Degraded` без виклику аварійного звукового сигналу.
3. **Тест аварійного таймауту:** Повна відсутність пакетів протягом 3501 мс гарантовано переводить автомат у `Lost` і обнуляє лічильник `consecutiveHeartbeats_`.
4. **Тест захисту від брязкоту:** Отримання двох пакетів після стану `Lost` залишає автомат у `Lost`; лише третій послідовний пакет переводить систему в `Connected`.

#### 7. Безпечне завершення з'єднання та очищення ресурсів (Teardown and Cleanup)
При вимкненні радіомодема або фізичному від'єднанні USB-кабелю мережевий потік генерує подію `LINK_DISCONNECTED`.

Процедура закриття зобов'язана повністю очистити чергу невідправлених пакетів, скинути стан монітора в початковий `LINK_STATE_LOST` та звільнити дескриптори сокетів. Якщо цього не зробити, повторне підключення кабелю почнеться з відправки старих буферизованих команд і спричинить хибну інтерпретацію застарілих лічильників послідовності `seq`.

#### 8. Апаратна індикація стану лінку на борту (LED та Buzzer)
На стороні польотного контролера перехід сторожового таймера між станами транслюється на фізичні індикатори платформи:
- У стані `Connected` зовнішній RGB-світлодіод апарата блимає зеленим кольором.
- При переході в стан `Degraded` або `Lost` драйвер освітлення перемикає колір на жовтий або пульсуючий синій, а бортовий п'єзодинамік (Buzzer) генерує звуковий патерн аварії втрати телеметрії. Це дозволяє наземному технічному персоналу візуально ідентифікувати втрату лінку безпосередньо перед зльотом або під час посадки.

#### 9. Верифікація на апаратно-програмних стендах (Hardware-in-the-Loop)
Фінальним етапом перевірки перед польотом є випробування на HIL-стенді: реальний польотний контролер з'єднується з фізичними радіомодемами, а радіосигнал пропускається через керований атенюатор (програмований послаблювач сигналу). Ступінчасте збільшення затухання від 0 до 90 дБ дозволяє експериментально перевірити, при яких саме рівнях RSSI та відсотках втрат пакетів спрацьовує перемикання станів FSM у реальному кремнії.

### Методи простеження та відлагодження у реальному часі (Tracing)

При виникненні аномалій зв'язку під час льотних випробувань інженери використовують інструменти низькорівневого трасування телеметрії:

1. **Аналізатор Wireshark з плагіном MAVLink Dissector:** Дозволяє захоплювати UDP/TCP пакети телеметрії на мережевому інтерфейсі станції. Плагін автоматично декодує поля `seq`, розраховує мікросекундну дельту між кадрами та підсвічує червоним кольором пропущені номери послідовностей або пошкоджені контрольні суми.
2. **Скрипти фільтрації MAVProxy:** Утиліта консольного моніторингу `mavproxy.py` підключається паралельно до потоку даних і виводить статистику в реальному часі: `status` демонструє поточний packet drop rate, завантаження буфера радіомодема та частоту надходження кадрів пульсу.
3. **Зіставлення бортового логу та наземного TLog:** Після завершення аварійного польоту часові графіки `RADIO_STATUS.rssi` з наземного логу станції синхронізуються за GPS-часом із бортовим записом `GPS.TimeUS` та кутами крену літака `ATTITUDE.Roll`. Це дозволяє точно довести, чи був обрив зв'язку викликаний затіненням антени фюзеляжем під час віражу, чи зовнішньою радіозавадою.
