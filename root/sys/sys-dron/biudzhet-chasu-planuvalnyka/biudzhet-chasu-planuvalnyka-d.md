Коли мультикоптер масою 3.5 кг мчить між деревами на швидкості 12 м/с (43.2 км/год), бортовий лідар або пара стереокамер розпізнає тонку гілку чи натягнутий трос на відстані 9 метрів. Щоб уникнути зіткнення, системі керування потрібен час на повний цикл реакції: зчитування та фільтрація сенсорних даних займає 30 мс, розрахунок просторової траєкторії в обхід перешкоди — 40 мс, передача пакетів команд через послідовну шину на автопілот — 5 мс, а поворот корпусу дрона для створення горизонтального гальмівного вектора тяги (динаміка регуляторів та моторів) — ще 15 мс. Сумарна затримка системи становить 90 мс. Протягом цих дев'яти сотих секунди безпілотник продовжує летіти за інерцією вперед і до початку фактичного уповільнення долає 1.08 метра «наосліп». Якщо максимальне допустиме уповільнення апарата становить `a_max = 6 м/с²`, суто фізичний гальмівний шлях складе `12² / (2 · 6) = 12.0 метрів`, що разом із дистанцією реакції дає повну зупинну дистанцію 13.08 метра — апарат гарантовано вріжеться в перешкоду за 4 метри до повної зупинки.

Зіткнення стається не тому, що алгоритм побудував неправильний шлях, а тому, що він не мав права думати так довго. В автономній робототехніці правильне рішення, ухвалене із запізненням навіть на кілька мілісекунд, еквівалентне катастрофічній відмові. Межа між керованим польотом і руйнацією тримається на суворому математичному розподілі часових ресурсів — **бюджеті часу планувальника** та дотриманні жорсткого часового дедлайну (англ. *deadline* — «граничний термін виконання», від англ. *dead* — «мертвий» та *line* — «лінія, межа»).

## Фізика запізнення: гальмівний шлях проти горизонту сенсорів

Кожен рух безпілотного апарата обмежений двома фундаментальними факторами: оптичним або радіолокаційним горизонтом виявлення перешкод сенсорами `d_sensor` та загальною затримкою ланцюга керування `t_latency`. Повний ланцюг затримки складається з чотирьох послідовних фаз:

```
t_latency = t_sensing + t_compute + t_comm + t_actuation
```

1. **Затримка сенсорного збору (`t_sensing`, 20–40 мс)**: час експозиції глобального затвора камери, час сканування променя лідара, передача «сирих» кадрів по шині MIPI-CSI або USB 3.0, перетворення хмари точок у локальну воксельну карту (Occupancy Grid) або поле відстаней ESDF (Euclidean Signed Distance Field).
2. **Затримка планувальника (`t_compute`, 20–50 мс)**: час пошуку геодезичного шляху у графі конфігураційного простору, генерації безпечного поліедрального коридору (Safe Flight Corridor, SFC) та чисельної оптимізації поліноміального сплайна.
3. **Затримка транспорту та серіалізації (`t_comm`, 2–5 мс)**: час упаковки структур сетпоінтів у протокольні повідомлення MAVLink або фрейми Micro-XRCE-DDS та передача через UART чи Ethernet до мікроконтролера автопілота.
4. **Затримка динаміки приводів (`t_actuation`, 10–25 мс)**: електромеханічна стала часу ESC-регуляторів і безколекторних моторів, а також час, необхідний контуру орієнтації для переорієнтації вектора тяги гвинтів (нахил за тангажем).

![Часовий ланцюг затримки планувальника та просторова шкала гальмування](/root/sys/sys-dron/biudzhet-chasu-planuvalnyka/img/planning-latency-braking.svg)
*Часовий ланцюг затримки планувальника та просторова шкала гальмування: повний ланцюг затримки реагування t_latency визначає дистанцію сліпого прольоту d_react перед початком активного гальмування d_brake.*

Протягом часу `t_latency` дрон рухається з початковою швидкістю `v₀`, пролітаючи дистанцію реакції:

```
d_react = v₀ · t_latency
```

Після створення максимального гальмівного прискорення `a_max` (яке обмежене тягооснащеністю апарата, кутом нахилу `θ_max` та силою тяжіння `g`) дрон переходить у фазу активного уповільнення. Гальмівна дистанція `d_brake` визначається інтегруванням другого закону Ньютона:

```
d_brake = v₀² / (2 · a_max)
```

Повна зупинна дистанція апарата `d_stop` складається з відстані реакції та гальмівного шляху:

```
d_stop = d_react + d_brake
       = v₀ · t_latency + v₀² / (2 · a_max)
```

Критична умова безпечного автономного польоту вимагає, щоб повна зупинна дистанція з урахуванням запасу безпеки `d_margin` (радіус корпусу дрона плюс захисний буфер) не перевищувала дальність надійного розпізнавання сенсора `d_sensor`:

```
d_stop + d_margin ≤ d_sensor
v₀ · t_latency + v₀² / (2 · a_max) + d_margin ≤ d_sensor
```

Ця нерівність визначає **максимально допустиму безпечну швидкість польоту** `v_max` для поточного сенсорного горизонту та обчислювальної затримки. Розв'язуючи квадратне рівняння відносно `v₀`, отримуємо граничну швидкість:

```
v_max = - a_max · t_latency + √( (a_max · t_latency)² + 2 · a_max · (d_sensor - d_margin) )
```

> 🔧 **Навіщо це.** Якщо бортовий лідар бачить на 12 метрів, `a_max = 5 м/с²`, `d_margin = 1.0 м`, а сумарна затримка `t_latency` збільшується з 50 мс до 150 мс через фонові процеси в операційній системі Linux, безпечна швидкість польоту дрона падає з 10.2 м/с (36.7 км/год) до 9.7 м/с. Проте якщо затримка через зависання планувальника сягне 500 мс, максимальна безпечна швидкість впаде до 8.2 м/с, а будь-яка спроба летіти швидше гарантовано призведе до катастрофи при появі раптової перешкоди.

### Вплив обмеження ривка на перехідний процес

У реальних польотних умовах прискорення не може зрости миттєво від `0` до `a_max`: безколекторний мотор має момент інерції ротора, а автопілот штучно обмежує швидкість зміни кутового прискорення (ривок, англ. *jerk* `j_max = da/dt`), щоб уникнути зриву струменя на пропелерах і перевантаження акумулятора.

Час виходу на максимальне уповільнення становить `t_jerk = a_max / j_max`. Протягом цього перехідного інтервалу прискорення зростає лінійно `a(t) = j_max · t`, що додає до зупинної дистанції додаткову похибку:

```
d_jerk = v₀ · t_jerk - (j_max · t_jerk³) / 6 = v₀ · (a_max / j_max) - a_max³ / (6 · j_max²)
```

Якщо для спортивного квадрокоптера `j_max` досягає `50–100 м/с³`, то для важкого БПЛА літакового типу або дрона-вантажопідйомника обмеження ривка `j_max ≈ 10..15 м/с³` додає до зупинного шляху ще 1.5–2.5 метра, що робить кожну мілісекунду обчислювального бюджету ще критичнішою.

## Багаторівневе планування за частотами (Multi-rate Planning Cascade)

Спроба розв'язати всю навігаційну задачу автономного польоту — від утримання кутів нахилу до прокладання глобального маршруту через гори — в рамках одного єдиного монолітного алгоритму є принципово нездійсненною. Цьому перешкоджає фундаментальна дилема реального часу:

- **Висока частота оновлення** (250–1000 Гц) вимагає простого, детермінованого алгоритму з фіксованим часом виконання менше 1 мілісекунди. Проте такий алгоритм не здатен враховувати складну геометрію тривимірних перешкод на кілометри вперед.
- **Глибока просторова оптимізація** (пошук у просторі станів високої розмірності) вимагає обробки мільйонів вокселів і розв'язання нелінійних оптимізаційних задач, що займає сотні мілісекунд. Проте оновлення керування з такою низькою частотою (1–2 Гц) призведе до миттєвого перекидання та падіння дрона під дією першого ж пориву вітру.

Єдиним архітектурним рішенням є **багаторівневий частотний каскад** (лат. *frequentia* — «частота», італ. *cascata* — «водоспад»), у якому система розбивається на чотири ізольовані шари керування, кожен зі своїм горизонтом передбачення, частотою дискретизації та допустимим рівнем джиттеру.

![Багаторівнева каскадна ієрархія планування за частотами](/root/sys/sys-dron/biudzhet-chasu-planuvalnyka/img/multirate-planning-hierarchy.svg)
*Багаторівнева каскадна ієрархія планування за частотами: від низькочастотного глобального графа (0.5–2 Гц) до надшвидкого внутрішнього PID-контуру кутових швидкостей (250–1000 Гц) з лінією сторожового перехоплення таймаутів.*

### Рівень 1 (250–1000 Гц): Контур швидкої стабілізації (Attitude Rate PID)
- **Де виконується**: Мікроконтролер польотного контролера (FCU, наприклад STM32H7 / Cortex-M7, 480 МГц) під керуванням RTOS твердого реального часу (NuttX, FreeRTOS).
- **Вхідні дані**: Сирі покази тривісного гіроскопа й акселерометра IMU, цільовий кватерніон просторової орієнтації `q_des` або бажані кутові швидкості `ω_des = [p, q, r]ᵀ` та нормована тяга `T_des`.
- **Вихідні дані**: Цифрові протокольні імпульси DShot300/DShot600 або ШІМ-сигнали на електронні регулятори швидкості (ESC) моторів.
- **Вимоги до часу**: Твердий реальний час (Hard Real-Time). Період квантування `Δt = 1.0..4.0 мс`, допустимий джиттер не більше 5–10 мікросекунд. Будь-яка затримка понад 5 мс викликає зрив фази в контурі зворотного зв'язку і миттєве неконтрольоване обертання апарата.

### Рівень 2 (50–100 Гц): Локальний траєкторний трекер (SE(3) Position Tracker)
- **Де виконується**: Високопріоритетний потік на мікроконтролері або бортовому комп'ютері з ядром Linux PREEMPT_RT.
- **Вхідні дані**: Високоточна оцінка стану від розширеного фільтра Калмана (EKF2) на частоті 100 Гц та миттєва точка цільової траєкторії: позиція `p_des(t)`, швидкість `v_des(t)`, прискорення прямого зв'язку (feedforward) `a_des(t)` та кут курсу `yaw_des(t)`.
- **Вихідні дані**: Цільовий кватерніон орієнтації `q_des` та повна проєкція сили тяги, розраховані на базі геометричного контролера на групі Лі `SE(3)`.
- **Вимоги до часу**: Твердий або жорсткий м'який реальний час (Soft Real-Time). Період `Δt = 10..20 мс`. Прямий зв'язок за прискоренням `a_des` дозволяє дрону завчасно нахиляти корпус при вході у віраж, не чекаючи накопичення просторової помилки позиції `e_p = p_des - p`.

### Рівень 3 (10–20 Гц): Локальний планувальник ухилення (Local Obstacle Avoidance)
- **Де виконується**: Багатоядерний процесор бортового комп'ютера (ARM Cortex-A76 / x86, наприклад Jetson Orin Nano, Raspberry Pi 5).
- **Вхідні дані**: Локальна карта щільності вокселів (OctoMap / Voxblox), хмара точок лідара, поточний кінематичний стан дрона та найближча опорна точка глобального маршруту.
- **Вихідні дані**: Неперервна безпечна траєкторія на найближчі 2–4 секунди вперед, представлена у вигляді набору поліноміальних сплайнів мінімального ривка (Minimum Jerk / Minimum Snap).
- **Вимоги до часу**: М'який реальний час із суворим дедлайном (Anytime Deadline). Бюджет кванту обчислень: `T_budget = 40..80 мс`. Якщо планувальник не встиг за 40 мс знайти глобальний оптимум, він зобов'язаний видати найкращий знайдений проміжний розв'язок.

### Рівень 4 (0.5–2 Гц): Глобальний оптимізатор місії (Global Route Planner)
- **Де виконується**: Фоновий потік низького пріоритету бортового комп'ютера або наземна станція керування (QGC).
- **Вхідні дані**: Глобальна карта висот рельєфу (DEM), векторні зони заборони польотів (Geofence), координати точок місії (Waypoints).
- **Вихідні дані**: Топологічний коридор або розріджений граф безпечних коридорів довжиною в сотні й тисячі метрів.
- **Вимоги до часу**: Не вимагає реального часу (Non-Real-Time). Час розрахунку може становити від 500 мс до 5 секунд. Під час розрахунку нового глобального маршруту дрон безпечно рухається за раніше згенерованим локальним коридором 3-го рівня.

### Безблокувальна взаємодія між частотними шарами

Оскільки контури працюють на різних частотах у різних потоках операційної системи (або на різних фізичних чипах), пряма синхронізація через блокуючі м'ютекси (Mutex Locks) заборонена: швидкий трекер (100 Гц) не має права чекати, поки важкий планувальник (20 Гц) закінчить запис нової поліноміальної кривої.

Обмін даними організовується через механізм **подвійної/потрійної буферизації з атомарними покажчиками** (Lock-free Double/Triple Buffering):

```
Планувальник (20 Гц)                     Трекер траєкторії (100 Гц)
┌──────────────────────┐                 ┌──────────────────────┐
│  Формування нової    │                 │  Зчитування активної │
│  траєкторії у        │                 │  траєкторії з        │
│  Buffer[Back]        │                 │  Buffer[Front]       │
└──────────┬───────────┘                 └──────────▲───────────┘
           │                                        │
           ▼                                        │
  Атомарний swap покажчиків: ───────────────────────┘
  atomic_store(&ActiveTrajectory, &Buffer[Back])
```

Трекер траєкторії щотакту (кожні 10 мс) зчитує поточний час `t_now`, обчислює відносний зсув `τ = t_now - t_traj_start` і викликає аналітичну функцію обчислення положення та прискорення сплайна `p_des(τ), a_des(τ)`. Якщо за 100 мс новий сплайн не надійшов, спрацьовує сторожовий таймер (Watchdog).

### Синхронізація часу та компенсація затримок передачі (Time Sync & Extrapolation)

При передачі сетпоінтів між бортовим комп'ютером (Linux) та польотним контролером (FCU) виникає затримка транспорту послідовної шини (UART Baudrate 921600 або Ethernet). Крім того, годинники двох процесорів мають взаємний дрейф.

Для коректного виконання траєкторії застосовується протокол синхронізації часу:
1. За протоколом MAVLink через повідомлення `TIMESYNC` компаньйон регулярно вимірює зміщення годинників (Offset) та повний час кругового обігу пакетів (Round Trip Time, RTT):
   ```
   offset = ((t2 - t1) + (t3 - t4)) / 2
   RTT    = (t4 - t1) - (t3 - t2)
   ```
   де `t1, t4` — часові мітки компаньйона, а `t2, t3` — часові мітки FCU.
2. При формуванні цільової точки для трекера 2-го рівня планувальник обчислює сетпоінт не для поточного моменту `t_now`, а з упередженням на затримку передачі та реакції:
   ```
   t_target = t_now + (RTT / 2) + t_actuation
   ```
   Екстраполяція за аналітичним поліномом `p_des(t_target)` дозволяє повністю нівелювати динамічне відставання контуру положення, зберігаючи точність проходження коридору на швидкостях понад 10 м/с.

## Стратегії обриву обчислень: парадигма Anytime Planning

Класичні алгоритми глобального пошуку на графах (як-от повний алгоритм Дейкстри) чи стандартні розв'язувачі задач квадратичного програмування (QP Solvers з методом активних обмежень) страждають на недетермінований час виконання: у відкритому полі алгоритм знаходить шлях за 2 мс, але у складному лабіринті між колонами час пошуку може стрибнути до 350 мс. Якщо планувальник заблокує видачу команд на 350 мс, дрон на швидкості вріжеться в першу ж перешкоду.

Для гарантування стабільності застосовується концепція **Anytime-алгоритмів** (англ. *anytime algorithm* — алгоритм будь-якого моменту, від англ. *any time* — «будь-який час»):
1. Алгоритм здатний миттєво (за перші 5–10% відведеного бюджету) згенерувати грубий, суб-оптимальний, але **гарантовано безпечний та кінематично допустимий розв'язок**.
2. Якщо час залишається, алгоритм продовжує ітеративно покращувати якість траєкторії (зменшувати інтегральний ривок, збільшувати кліренс до перешкод, згладжувати кутові швидкості).
3. При настанні дедлайну алгоритм **може бути обірваний у будь-який мікросекундний момент** і віддати найкращий розв'язок, досягнутий на поточну ітерацію.

```
Якість траєкторії (1 / Cost)
 ▲
 │                          Точка глобального оптимуму
 │                                      ┌───────────────────────
 │                       Ітерація 3     │
 │                     ┌────────────────┘
 │        Ітерація 2   │
 │      ┌──────────────┘
 │      │
 │──────┘ ◄── Ітерація 1: Перший допустимий розв'язок (Seed)
 │
 └──────┼──────────────┼────────────────┼───────────────────────►
       t=0            t=5 мс           t=40 мс (Дедлайн)      Час [мс]
```

### 1. Anytime Repairing A* (ARA*)
Алгоритм ARA* модифікує класичний евристичний пошук A*, вводячи коефіцієнт інфляції евристики `ε > 1`. Оцінка вартості вершини набуває вигляду:

```
f(s) = g(s) + ε · h(s)
```

- При великому `ε` (наприклад `ε = 3.0`) евристика стає агресивно жадібною: пошук перетворюється на спрямований промінь і знаходить перший субоптимальний шлях за 2–3 мс, обходячи лише мінімальну кількість вузлів.
- Після знаходження першого шляху алгоритм не скидає дерево пошуку, а знижує коефіцієнт `ε` (наприклад до `ε = 2.0`, потім `ε = 1.5`, і врешті `ε = 1.0`).
- Замість повторного сканування всього простору, ARA* підтримує множину неузгоджених вершин `INCONS` (вершини, чия вартість `g(s)` покращилася на попередньому кроці). Нова ітерація лише перевпорядковує чергу пріоритетів `OPEN` з множини `INCONS`, заощаджуючи до 90% обчислень.

### 2. Anytime RRT* (Швидкодосліджувані випадкові дерева)
У класичному RRT дерево росте доки не досягне цілі, після чого робота зупиняється. В Anytime RRT*:
- Перша гілка, що досягла цільової області, миттєво фіксується як поточна активна траєкторія.
- У решту часу до настання дедлайну алгоритм продовжує генерувати випадкові точки `x_rand`, оптимізуючи локальні зв'язки через процедуру перепідключення сусідніх вершин (Rewiring) у радіусі `r_RRT = γ · (log(N) / N)^(1/d)`.
- Довжина шляху та його гладкість монотонно наближаються до асимптотичного оптимуму доти, доки таймер не перерве цикл.

### 3. Safe Flight Corridor (SFC) та декомпозиція простору
Сучасні планувальники швидкісних безпілотників (наприклад, алгоритми класу EGO-Planner або Fast-Planner) використовують двокроковий підхід:
1. **Геометричний скелет**: швидкий пошук кінодинамічного шляху за алгоритмом A* або ARA* на воксельній сітці (3–5 мс).
2. **Опукла декомпозиція коридору (Safe Flight Corridor)**: навколо знайдених відрізків будуються просторові опуклі поліедри (Convex Polyhedra), вільні від перешкод. Опуклий поліедр задається системою лінійних нерівностей `A_k · p ≤ b_k`.
3. **Квадратична оптимізація сплайна (QP Spline Refinement)**: оскільки кожен сегмент кривої лежить всередині опуклого багатогранника, нелінійна задача ухилення від перешкод перетворюється на задачу опуклого квадратичного програмування:

```
Мінімізувати:   J = ∫ ||p⁽³⁾(t)||² dt          [Мінімізація ривка / Jerk]
За умов:        p(0) = p_start,  p(T) = p_goal  [Крайові умови стану]
                A_k · p(t) ≤ b_k, ∀ t ∈ [t_k, t_k+1] [Коридор безпеки]
                ||ṗ(t)|| ≤ v_max, ||p̈(t)|| ≤ a_max   [Динамічні межі]
```

Опукла задача QP має гарантовану збіжність до єдиного глобального мінімуму за поліноміальний час без ризику застрягання в локальних ямах, що дозволяє отримувати гладку аналітичну криву за 10–25 мс.

### Геометрична декомпозиція: вирощування еліпсоїдів та KKT-система

Побудова опуклого коридору SFC базується на методі послідовного роздування вписаних еліпсоїдів (Inscribed Ellipsoid Expansion):
1. На кожному відрізку опорного шляху `[w_k, w_k+1]` будується початковий витягнутий еліпсоїд `E = { p | (p - c)ᵀ · M · (p - c) ≤ 1 }`, де центр `c = (w_k + w_k+1) / 2`.
2. Еліпсоїд ітеративно масштабується у просторі доти, доки його поверхня не торкнеться найближчого зайнятого вокселя карти перешкод.
3. У точці дотику будується дотична гіперплощина, яка відсікає півпростір із перешкодою. Повторення процедури для всіх навколишніх перешкод формує замкнений опуклий поліедр (Safe Polyhedron), описаний матрицею півпросторів `A_k · p ≤ b_k`.

Для отримання коефіцієнтів поліномів у коридорі SFC задача QP зводиться до розв'язання розрідженої блочно-діагональної системи рівнянь Каруша — Куна — Таккера (KKT Matrix):

```
┌───────┬───────┐ ┌───┐   ┌───┐
│   Q   │  Aᵀ   │ │ c │   │ 0 │
├───────┼───────┤ ├───┤ = ├───┤
│   A   │   0   │ │ λ │   │ b │
└───────┴───────┘ └───┘   └───┘
```

де `Q` — симетрична додатно визначена матриця інтегрального ривка (Hessian matrix), `A` — матриця умов неперервності та крайових обмежень `C²`/`C³`, `c` — вектор коефіцієнтів сплайнів усіх сегментів, а `λ` — вектор множників Лагранжа. Оскільки матриця KKT має стрічкову структуру, факторизація Холецького `L · D · Lᵀ` виконується всього за 2–4 мс.

## Архітектура таймера та сторожового контролю кванту часу

Для надійного обмеження часу виконання на бортовому комп'ютері під керуванням Linux використовується прецизійний системний таймер `CLOCK_MONOTONIC_RAW`. На відміну від стандартного `CLOCK_REALTIME`, цей годинник є строго монотонним і не піддається стрибкам при коригуванні часу демонами NTP чи PTP.

Типовий бюджет кванту часу 50 мс (частота 20 Гц) розподіляється на наступні захищені часові слоти:

```
┌────────────────────────────────────────────────────────────────────────┐
│              Повний квант циклу планування: 50.0 мс                    │
├───────────────┬───────────────────────────────┬───────────┬────────────┤
│ 1. Збір даних │ 2. Ітеративна оптимізація     │ 3. Валі-  │ 4. Відправ-│
│ та ESDF карта │    Anytime (ARA* + SFC + QP)  │    дація  │    ка MAVL │
│    8.0 мс     │           36.0 мс             │   3.0 мс  │    3.0 мс  │
└───────────────┴───────────────────────────────┴───────────┴────────────┘
                                                ▲
                                                │
                                    Жорсткий дедлайн: t = 44.0 мс
```

Якщо оптимізаційний цикл досягає позначки `t = 44.0 мс`, він негайно обривається. Залишок у 6.0 мс гарантовано резервується на фінальну перевірку колізій (Safety Validation) та серіалізацію пакетів для шини зв'язку.

### Аварійний маневр при зриві бюджету часу (Failsafe Fallback)

Що робити, якщо через раптовий збій процесора або перевантаження пам'яті планувальник взагалі не зміг згенерувати жодного нового розв'язку за 50 мс?

Система реалізує трирівневий захисний каскад Failsafe:
1. **Рівень 1: Виконання хвоста попередньої траєкторії**. Оскільки кожен розрахований сплайн має горизонт 2–4 секунди, а оновлення відбувається кожні 50 мс, контролер має запас автономного руху на 1.95–3.95 секунди вперед. Пропуск одного або двох тактів планування (до 100 мс) є абсолютно прозорим для польоту.
2. **Рівень 2: Активація заздалегідь прорахованого примітива гальмування (Emergency Braking Primitive)**. На кожному успішному такті паралельно з основним планом генерується траєкторія екстреного вертикального набору висоти або повної зупинки в поточній точці. Якщо новий план не надійшов за 200 мс, трекер автоматично перемикається на виконання збереженого аварійного примітива.
3. **Рівень 3: Апаратне перехоплення автопілотом (FCU Watchdog)**. Якщо зв'язок із бортовим комп'ютером повністю зникає на час понад 500 мс (за таймаутом повідомлення `HEARTBEAT` або потоку сетпоінтів `SET_POSITION_TARGET_LOCAL_NED`), польотний контролер FCU самостійно скидає режим `OFFBOARD`, переходить у захисний режим `POSCTL` (Position Hold) або `AUTO_RTL` (Return to Land) і зависає на місці, спираючись виключно на власні сенсори EKF2.

Нижче наведено практичну реалізацію керуючого циклу Anytime-планувальника з детермінованим контролем часу дедлайну, ітеративним обривом оптимізації та аварійним фолбеком на C та C++.

```c
#define _POSIX_C_SOURCE 199309L
#include <stdio.h>
#include <stdbool.h>
#include <stdint.h>
#include <time.h>
#include <unistd.h>

#define PLANNING_BUDGET_US   40000ULL /* Бюджет кванту часу: 40 мс (40000 мкс) */
#define SAFETY_MARGIN_US      4000ULL /* Резерв на відправку та валідацію: 4 мс */

typedef struct {
    double x, y, z;
} Point3D;

typedef struct {
    Point3D waypoints[16];
    size_t count;
    double cost;
    uint32_t iteration;
    bool is_valid;
} TrajectoryPlan;

static inline uint64_t get_monotonic_us(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC_RAW, &ts);
    return (uint64_t)ts.tv_sec * 1000000ULL + (uint64_t)ts.tv_nsec / 1000ULL;
}

/* Імітація ітеративного покращення траєкторії */
bool optimize_trajectory_step(TrajectoryPlan* plan, uint32_t step, uint64_t deadline_us) {
    /* Симуляція обчислень: перевірка часу перед кожною важкою операцією */
    if (get_monotonic_us() >= deadline_us) {
        return false; /* Дедлайн вичерпано — припиняємо роботу */
    }
    
    /* Ітеративне покращення кривої */
    plan->iteration = step;
    plan->cost *= 0.85; /* Зниження ривка / покращення плавності */
    plan->is_valid = true;
    
    /* Симуляція навантаження 1.5 мс */
    usleep(1500);
    return true;
}

/* Головний цикл планування з жорстким часовим дедлайном */
TrajectoryPlan execute_planning_cycle(const TrajectoryPlan* fallback_plan) {
    uint64_t start_time_us = get_monotonic_us();
    uint64_t deadline_us = start_time_us + (PLANNING_BUDGET_US - SAFETY_MARGIN_US);
    
    TrajectoryPlan current_best;
    if (fallback_plan && fallback_plan->is_valid) {
        current_best = *fallback_plan; /* Ініціалізація гарантованим резервним планом */
    } else {
        current_best.count = 1;
        current_best.cost = 99999.0;
        current_best.iteration = 0;
        current_best.is_valid = false;
    }
    
    uint32_t step = 1;
    while (get_monotonic_us() < deadline_us) {
        TrajectoryPlan candidate = current_best;
        if (!optimize_trajectory_step(&candidate, step, deadline_us)) {
            break; /* Оптимізація була перервана таймером */
        }
        current_best = candidate;
        step++;
    }
    
    uint64_t total_elapsed_us = get_monotonic_us() - start_time_us;
    printf("[Anytime C] Цикл завершено за %llu мкс (Ітерацій: %u, Вартість: %.2f)\n",
           (unsigned long long)total_elapsed_us, current_best.iteration, current_best.cost);
    
    return current_best;
}
```

```cpp
#include <iostream>
#include <chrono>
#include <thread>
#include <vector>
#include <span>
#include <optional>

struct Point3D {
    double x{0.0}, y{0.0}, z{0.0};
};

struct TrajectoryPlan {
    std::vector<Point3D> waypoints;
    double cost{99999.0};
    uint32_t iteration{0};
    bool is_valid{false};
};

class RealTimePlanner {
public:
    static constexpr auto kPlanningBudget = std::chrono::microseconds(40000); // 40 мс
    static constexpr auto kSafetyMargin   = std::chrono::microseconds(4000);  // 4 мс

    [[nodiscard]] TrajectoryPlan execute_cycle(const std::optional<TrajectoryPlan>& fallback_plan) const {
        using Clock = std::chrono::steady_clock;
        const auto start_time = Clock::now();
        const auto deadline = start_time + (kPlanningBudget - kSafetyMargin);

        TrajectoryPlan best_plan = fallback_plan.value_or(TrajectoryPlan{
            .waypoints = {Point3D{0, 0, 0}},
            .cost = 99999.0,
            .iteration = 0,
            .is_valid = false
        });

        uint32_t step = 1;
        while (Clock::now() < deadline) {
            TrajectoryPlan candidate = best_plan;
            if (!optimize_step(candidate, step, deadline)) {
                break; // Дедлайн вичерпано
            }
            best_plan = candidate;
            step++;
        }

        const auto elapsed = std::chrono::duration_cast<std::chrono::microseconds>(Clock::now() - start_time);
        std::cout << "[Anytime C++] Цикл завершено за " << elapsed.count()
                  << " мкс (Ітерацій: " << best_plan.iteration
                  << ", Вартість: " << best_plan.cost << ")\n";

        return best_plan;
    }

private:
    [[nodiscard]] bool optimize_step(TrajectoryPlan& plan, uint32_t step,
                                     std::chrono::steady_clock::time_point deadline) const {
        using Clock = std::chrono::steady_clock;
        if (Clock::now() >= deadline) {
            return false;
        }

        plan.iteration = step;
        plan.cost *= 0.85;
        plan.is_valid = true;

        // Симуляція обчислювального навантаження
        std::this_thread::sleep_for(std::chrono::microseconds(1500));
        return true;
    }
};
```

## Пастки реального часу: джиттер пам'яті, тротлінг і затримки черг

Навіть ідеально оптимізований алгоритм C/C++ із теоретичною складністю `O(N)` може раптово зірвати дедлайн у реальному польоті через системні пастки операційної системи загального призначення Linux.

```
┌────────────────────────────────────────────────────────────────────────┐
│                   Джерела недетермінізму в Linux                       │
├──────────────────────────┬─────────────────────────┬───────────────────┤
│ Джиттер пам'яті (Heap)   │ Тепловий тротлінг (SoC) │ Черги драйверів   │
│ malloc / Page Fault      │ Зниження частоти CPU    │ Буфери V4L2/ROS2  │
│ Затримка: 1–10 мс        │ Затримка: зростає ×3    │ Затримка: 50–200мс│
└──────────────────────────┴─────────────────────────┴───────────────────┘
```

### 1. Динамічне виділення пам'яті (Heap Allocations & Page Faults)
Виклики `malloc()`, `free()`, `new`, а також неявні алокації у контейнерах `std::vector::push_back` або `std::string` категорично заборонені в гарячому циклі планування:
- **Блокування м'ютекса купи**: стандартний алокатор `glibc` захищений м'ютексом. Якщо інший потік (наприклад, потік запису логу на SSD чи передачі відеокадрів) у цей момент виділяє пам'ять, планувальник зависає в очікуванні м'ютекса на 0.5–3.0 мс.
- **Мажорні та мінорні збої сторінок (Page Faults)**: коли процес запитує нову сторінку пам'яті, ядро Linux повинно знайти вільний фізичний фрейм, обнулити його та оновити таблицю сторінок процесора (MMU). Це призводить до виходу з користувацького простору в ядро та неконтрольованої затримки.
- **Рішення**: архітектура з нульовим виділенням пам'яті (Zero-Allocation Architecture). Усі матриці, масиви вокселів та буфери сплайнів розміщуються у статичній пам'яті (`static` / `std::array`) або пре-алокованих аренах пам'яті, виділених під час ініціалізації системи з обов'язковим блокуванням адресного простору в оперативній пам'яті через `mlockall(MCL_CURRENT | MCL_FUTURE)`.

### 2. Тепловий тротлінг процесора (Thermal Throttling)
Під час автономного польоту бортовий комп'ютер одночасно виконує нейромережевий аналіз зображення з двох камер, будує тривимірну воксельну карту та транслює відеопотік. За високої температури навколишнього середовища (+35 °C) кристал SoC швидко нагрівається до критичних 85 °C.
- Автоматичний захист процесора (DVFS — Dynamic Voltage and Frequency Scaling) миттєво скидає тактову частоту ядер (наприклад, з 2.0 ГГц до 600 МГц) для запобігання перегріву.
- Як наслідок, час виконання тієї самої ітерації планувальника раптово зростає з 25 мс до 80 мс, ламаючи розрахований часовий бюджет.
- **Рішення**: активне радіаторне охолодження з вентилятором, налаштування фіксованого профілю продуктивності (`jetson_clocks` або регулятор `performance` у Linux) та моніторинг температури кристала через `sysfs` (`/sys/class/thermal/thermal_zone*/temp`) з автоматичним зниженням швидкості польоту дрона при зростанні температури.

### 3. Накопичення затримок у чергах повідомлень (Sensor Queue Lag)
Якщо сенсорний драйвер камери чи лідара генерує дані зі швидкістю 30 кадрів/с, а планувальник обробляє їх на частоті 20 Гц, у черзі повідомлень (ROS2 Subscription Queue або буфер V4L2) неминуче утворюється затор.
- Планувальник на кожному кроці зчитує з черги повідомлення типу FIFO (First In, First Out), вважаючи його свіжим. Проте через накопичений буфер затримка даних становить 150–200 мс — дрон будує траєкторію за картиною світу, якої вже не існує.
- **Рішення**: конфігурація черг за принципом «тільки останній кадр» (`queue_size = 1`, політика `KeepLast(1)` або `O_NONBLOCK` у файлових дескрипторах V4L2) з примусовим відкиданням застарілих кадрів, а також сувора перевірка часової мітки сенсорного кадру `t_sensor` відносно поточного монотонного часу `t_now`: якщо `t_now - t_sensor > 60 мс`, кадр вважається застарілим і відкидається.

### 4. Пріоритетизація потоків та ізоляція ядер (RT Scheduling & Core Pinning)
Операційна система Linux повинна бути налаштована на виділення ексклюзивних ресурсів під контур керування:
- Використання планувальника реального часу `SCHED_FIFO` або `SCHED_RR` з високим пріоритетом (90–98) через системний виклик `pthread_setschedparam()`.
- Ізоляція виділеного ядра процесора через параметр завантаження ядра Linux `isolcpus=3` та прив'язка потоку планувальника до цього ядра через `pthread_setaffinity_np()`. Це унеможливлює витіснення планувальника фоновими службами операційної системи або обробниками переривань Wi-Fi/Ethernet.

### 5. Вітрові збурення та деградація сенсорів
У польоті на відкритому просторі сильний зустрічний або бічний порив вітру швидкістю `v_wind = 8..12 м/с` створює постійну аеродинамічну силу опору. Для компенсації цієї сили дрон повинен нахиляти корпус на додатковий кут `θ_wind = arctan(F_drag / (m · g))`, що суттєво «з'їдає» динамічний діапазон доступного прискорення:

```
a_reserve = a_max - ||a_wind||
```

Якщо `a_reserve` падає з `6.0 м/с²` до `3.0 м/с²`, гальмівний шлях подвоюється. Планувальник, що адаптується до зовнішнього середовища, зобов'язаний оцінювати вітрове збурення через інтегратор EKF2 або розширений спостерігач стану (Extended State Observer, ESO) і динамічно перераховувати безпечну крейсерську швидкість `v_max` згідно з формулою гальмівної дистанції.

Аналогічно, при вильоті з затемненого ангара на яскраве сонце (оптичне засліплення камер VIO або переекспозиція сенсора) розсіяння хмари точок різко зростає. У цей момент оцінювач достовірності карти (Confidence Metric) фіксує деградацію сенсорних даних і автоматично збільшує просторовий буфер безпеки `d_margin` з 0.5 м до 2.0 м, змушуючи планувальник обирати консервативніші та просторіші траєкторії.
