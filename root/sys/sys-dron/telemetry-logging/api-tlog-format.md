# 📋 Формат `.tlog`: побайтова розкладка запису й контракт для читача

Файл телеметрії наземної станції — не контейнер із заголовком, а гола послідовність записів «мітка часу плюс кадр», у якій немає жодного байта метаданих про сам файл. Тут зібрано точну розкладку запису, межі його довжини, різні правила двох шляхів запису, іменування файлів — і окремим блоком повний перелік того, чого у форматі немає, з наслідками для кожного, хто береться цей файл читати.

Звірено з гілкою `master` репозиторію `mavlink/qgroundcontrol` 2 серпня 2026 року: `src/Comms/MAVLinkProtocol.cc`, `MAVLinkProtocol.h`, `LinkManager.cc`, `LinkInterface.cc`, `src/Settings/AppSettings.h`, `AppSettings.cc`. Формат кадру — за специфікацією серіалізації MAVLink (`mavlink.io/en/guide/serialization.html`); поведінка читача — за `mavutil.py` з гілки `master` репозиторію `ArduPilot/pymavlink`.

## Одиниця файлу — запис

```
Зсув   Розмір      Поле
0      8 Б         мітка часу: мікросекунди від початку епохи Unix,
                   беззнакове 64-бітове ціле, СТАРШИЙ БАЙТ ПЕРШИМ
8      8…280 Б     кадр MAVLink: від стартового байта до останнього байта
                   контрольної суми (а для підписаного — до кінця підпису)
────   ────────
       16…288 Б    запис
```

Файл — такі записи впритул один за одним, від нульового байта до кінця. Перед ними немає заголовка, між ними немає ні вирівнювання, ні роздільника, після останнього немає хвостовика. Це весь формат.

Мітка часу — єдине, що станція додає від себе, тож варто розписати її поле за полем.

| Властивість | Значення | Що з цього випливає для читача |
|---|---|---|
| ширина | 8 байтів, беззнакове ціле | фіксована; перші вісім байтів файлу — завжди мітка |
| порядок байтів | старший першим (`qToBigEndian` на боці станції, `struct.unpack('>Q', …)` на боці pymavlink) | побайтове порівняння двох міток дає той самий результат, що й числове |
| одиниця | мікросекунда | |
| фактична роздільність | мілісекунда: значення береться як `currentMSecsSinceEpoch() · 1000` | три молодші десяткові розряди завжди нулі; кадри однієї мілісекунди мають **однакову** мітку |
| початок відліку | 1970-01-01T00:00:00Z | мітка не залежить від часового поясу |
| джерело | настінний годинник операційної системи | значення може стрибнути назад, якщо годинник перевели |
| діапазон | до ≈ 584 542 років від епохи | переповнення поля неможливе |

```
мітка = currentMSecsSinceEpoch() · 1000

діапазон восьми байтів:
2⁶⁴ мкс = 18 446 744 073 709 551 616 мкс
        = 1.8446744·10¹³ с
        ÷ 31 556 952 с/рік ≈ 584 542 роки
```

Порядок «старший першим» — не данина мережевій традиції, а робоча властивість: у такому вигляді [байти мітки](root:sf-algorithms/bits-bytes-endianness) зростають у лексикографічному порядку разом із числом, тож читач може порівнювати мітки, не збираючи з них 64-бітових чисел. Ціною є те, що на настільній машині запис вимагає явного перевертання, а помилка в цьому місці не видна одразу — про це нижче, у розділі про пастки.

## Скільки байтів займає кадр

Довжину запису неможливо взяти з самого запису: у форматі немає поля довжини. Її знає лише кадр усередині — через свій стартовий байт, поле довжини навантаження й прапорці. Ось усі можливі межі. Будова полів — у [пакеті MAVLink](root:sys-dron/mavlink-packet).

| Версія кадру | Заголовок | Навантаження | Сума | Підпис | Кадр | Запис (кадр + 8 Б) |
|---|---|---|---|---|---|---|
| v1, магія `0xFE` | 6 Б | 0…255 Б | 2 Б | — | 8…263 Б | 16…271 Б |
| v2 без підпису, магія `0xFD` | 10 Б | 0…255 Б | 2 Б | — | 12…267 Б | **20…275 Б** |
| v2 з підписом, магія `0xFD` | 10 Б | 0…255 Б | 2 Б | 13 Б | 25…280 Б | 33…288 Б |

Число **275 Б** — це і є практична стеля запису для сучасної станції: v2 без підпису з повним навантаженням. Офіційна сторінка формату в посібнику розробника QGroundControl досі описує запис як «байти 1–8: мітка, байти 9–271: пакет, максимум 263 байти» — це межі **першої** версії MAVLink, і сторінка від тих часів не оновлювалася. Статус: числа 263/271 достовірні для v1 і застарілі для v2; межі v2 обчислено з чинної специфікації серіалізації.

Мінімум у 12 байтів для v2 випливає з правила обрізання: реалізація зобов'язана відкинути нульові байти в хвості навантаження, але перший байт навантаження не обрізається ніколи — тож 12 байтів дає лише повідомлення, у визначенні якого навантаження порожнє.

Звідси єдина правильна процедура «скільки читати далі»:

```c
/* Довжина запису, що починається на початку буфера buf довжиною avail байтів.
   Повертає 0, якщо байтів ще не вистачає або на місці магії щось інше. */
size_t tlog_record_len(const uint8_t *buf, size_t avail)
{
    if (avail < 10) return 0;                 /* 8 мітки + магія + довжина */

    const uint8_t magic = buf[8];
    const uint8_t len   = buf[9];             /* довжина навантаження */

    if (magic == 0xFE) {                      /* MAVLink 1 */
        return 8 + 6 + (size_t)len + 2;
    }
    if (magic != 0xFD) return 0;              /* це не початок кадру */

    if (avail < 11) return 0;                 /* потрібен ще байт прапорців */
    const uint8_t incompat = buf[10];
    const size_t  sig = (incompat & 0x01) ? 13 : 0;   /* MAVLINK_IFLAG_SIGNED */

    return 8 + 10 + (size_t)len + 2 + sig;
}
```

Функція навмисно не звіряє контрольної суми: її завдання — сказати, де закінчується поточний запис. Чи кадр цілий, вирішує вже [розбирач](root:com-protocol/stream-parser), і саме він потрібен, коли `tlog_record_len` натрапила на байт, що не є магією.

## Два шляхи запису — і різні правила на них

Записи у файлі народжуються в двох різних місцях коду, з різних приводів і за різними правилами. Плутати їх дорого, бо все, що зазвичай кажуть про формат («у лозі немає підписів», «`SETUP_SIGNING` відфільтровано»), справджується лише для одного з двох.

| | шлях прийому (`MAVLinkProtocol::receiveBytes`) | шлях відправлення (`MAVLinkProtocol::logSentBytes`) |
|---|---|---|
| що спричиняє запис | кожне повідомлення, яке розбирач визнав цілим | кожен блок байтів, відданий транспортові (сигнал `LinkInterface::bytesSent`) |
| що лягає у файл | повторна серіалізація розібраного кадру (`MAVLinkSigning::serializeUnsignedCopy`) | блок байтів як є |
| підпис | знято: тринадцять байтів прибрано, прапорець `MAVLINK_IFLAG_SIGNED` скинуто, суму перераховано | лишається, якщо канал підписаний |
| `SETUP_SIGNING` | у файл не потрапляє — окрема перевірка `msgid` | окремої перевірки немає |
| сміття, обірвані кадри, биті суми | не потрапляє: кран стоїть після розбору | не існує: станція пише лише власні кадри |
| скільки кадрів в одному записі | рівно один | стільки, скільки пішло в транспорт одним записом (на практиці один) |

Перерахунок суми на шляху прийому — не примха, а вимушений крок. Контрольна сума MAVLink 2 рахується від байта довжини й до останнього байта навантаження, з магії й підпису не рахується — а отже, **байт прапорців несумісности до неї входить**. Скинути в ньому біт підписаности й лишити стару суму означало б покласти у файл кадр, що не пройде перевірки в жодного читача. Механіку самого підпису розбирає [підпис у MAVLink 2](root:sys-dron/mavlink-v2-signing), алгоритм суми — [циклічний надлишковий код](root:com-modulation/crc).

> 🔧 **Навіщо це.** Асиметрія двох шляхів має практичний наслідок для того, хто пересилає логи. Фільтр `SETUP_SIGNING` — повідомлення, що несе секретний ключ підпису, — стоїть лише на шляху прийому. Ключ, який **станція надіслала апаратові**, проходить шляхом відправлення, де фільтра немає, і лягає у файл разом із рештою трафіку. Тому лог сеансу, у якому вмикали підпис, перед пересиланням варто переглянути: `mavlogdump.py --types SETUP_SIGNING` відповість за секунду. Загальні правила поводження з такими даними — у [керуванні секретами](root:sf-security/secrets-management).

## Файли: тимчасовий і збережений

| | тимчасовий | збережений |
|---|---|---|
| розширення | `.mavlink` | `.tlog` |
| ім'я | `FlightDataXXXXXX.mavlink`, де `XXXXXX` — шість символів, що їх підставляє система | `yyyy-MM-dd hh-mm-ss.tlog`, наприклад `2026-08-02 12-00-00.tlog` |
| тека | системна тека тимчасових файлів | `<Save path>/Telemetry/` |
| коли існує | від першого серцебиття до кінця сеансу | від кінця сеансу й далі |
| формат вмісту | **той самий** | **той самий** |

Різниця між двома розширеннями — не різниця форматів. `.mavlink` означає рівно одне: «цей файл ще не завершено або не збережено». Байт у байт це той самий формат, і будь-який інструмент, що читає `.tlog`, прочитає `.mavlink` без перейменування — pymavlink, наприклад, відкриває як лог **будь-який наявний файл**, не дивлячись на розширення.

Три особливості імені збереженого файлу, які регулярно спантеличують:

- **Час в імені — локальний, час у записах — від епохи.** Ім'я складається з `QDateTime::currentDateTime()`, тобто в поясі машини; мітки всередині рахуються від UTC. Різниця між ними дорівнює зсуву пояса, і це нормально, а не пошкодження.
- **Це час збереження, а не час початку сеансу.** Для нормального завершення різниця — тривалість польоту. Для файлу, врятованого після падіння застосунку, ім'я отримає час **наступного запуску**, який може настати через кілька днів. Судити про давність польоту з імені файлу не можна — тільки з першої мітки всередині.
- **Формат `yyyy-MM-dd hh-mm-ss` — не ISO 8601.** Замість `T` стоїть пропуск, замість двокрапок у часі — дефіси, бо двокрапка заборонена в іменах файлів Windows. Головна властивість [ISO 8601](root:sf-data/iso-8601) при цьому вціліла: у межах одного пояса лексикографічне сортування імен збігається з хронологічним. Година в цьому шаблоні двадцятичотиригодинна.

Якщо ім'я вже зайняте (два сеанси, збережені в ту саму секунду), перед розширенням вставляється лічильник: `2026-08-02 12-00-00.1.tlog`, `…2.tlog` і далі.

Тека телеметрії — це підтека `Telemetry` всередині шляху збереження, що його задає користувач; сам шлях живе разом із рештою [налаштувань застосунку](root:sys-dron/settings-persistence). Константу назви теки в коді позначено як придатну до перекладу, тож підпис у локалізованому інтерфейсі може не збігатися з ім'ям на диску.

## Контракт для читача

Усе, що вище, — це те, що у форматі **є**. Практична робота зі сторонніми інструментами впирається переважно в те, чого в ньому **немає**.

| Немає | Чим це заміняють | Ціна |
|---|---|---|
| магічного числа й версії формату | здогад за правдоподібністю перших байтів | файл неможливо впізнати надійно; помилковий здогад виявляється лише на середині |
| поля довжини запису | повний розбір кадру | послідовний доступ, ніякого пошуку за зсувом |
| позначки напрямку | ідентифікатор системи в кадрі | напрям — здогад за домовленістю, а не факт із файлу |
| позначки каналу | нічого | усі канали сеансу злиті в один файл без розрізнення |
| назви діалекту й версії словника | нічого | навантаження може розібратися неправильно й мовчки |
| оголошення порядку байтів мітки | правдоподібність числа | старі й чужі файли доводиться розпізнавати евристикою |
| індексу, змісту, хвостовика | нічого | тривалість запису відома лише після читання до кінця |

### Файл — ланцюг, а не масив

Без поля довжини дійти до наступного запису можна єдиним способом: розібрати поточний кадр. Сотий запис недосяжний, доки не пройдено дев'яносто дев'ять попередніх. З цього випливає все інше: перемотування коштує читання, тривалість логу відома лише після повного проходу, розпаралелити розбір без попереднього індексування не вийде, а пошкоджений байт у середині файлу збиває рахунок і вимагає повторної синхронізації — пошуку наступного стартового байта з перевіркою суми. Формати, що прив'язують до кожного запису його довжину, цієї ціни не платять; чому обрамлення взагалі буває різним, розбирає [обрамлення повідомлень у потоці](root:com-protocol/tcp-message-framing).

### Обидва напрямки лежать поруч і нічим не позначені

У файлі впереміш лежать кадри, що прийшли від апарата, і кадри, що станція надіслала. Позначки, який запис звідки, у форматі немає — обидва шляхи пишуть однаковий за будовою запис.

Розрізнити їх можна лише за ідентифікаторами системи й компонента всередині кадру: у станції свій номер системи (типово 255), у апарата — свій (типово 1). Але це **домовленість, а не поле формату**: номер станції — налаштування, номер апарата — теж, і обидва можна змінити.

> 🔧 **Навіщо це.** Будь-яка статистика по лозі, порахована без розділення напрямків, буде неправильною, і неправильною тихо. Частота повідомлень подвоїться там, де станція перепитує апарат тим самим типом повідомлення. Затримка «запит — відповідь» перетвориться на нуль, бо обидві події лежать поруч. Втрати за розривами в номерах послідовности порахуються по двох незалежних лічильниках, зліплених в один, — і покажуть десятки відсотків утрат на цілком здоровому каналі. Перший рядок будь-якого аналізатора логу має бути групуванням за парою «система, компонент».

### Усі канали сеансу — в одному файлі

Файл журналу один на застосунок, а не на канал: усі відкриті канали під'єднані до тих самих слотів запису. Якщо апарат чути одночасно через радіомодем і через мережу, кожен його кадр потрапляє у файл **двічі**, з двома різними мітками часу, і жодного поля, за яким їх розрізнити, у записі немає. Ідентифікатори системи й компонента в обох копіях однакові — це той самий апарат; збігаються й номери послідовности. Практичний спосіб виявити подвоєння — саме повторення номера послідовности з тим самим типом повідомлення в межах кількох мілісекунд. Чому канали множаться й хто ними керує — у [менеджері каналів](root:sys-dron/link-manager).

### Порядок байтів мітки не самоописовий

Це найгостріша пастка формату без заголовка. Файл не каже, як записано мітку, — а варіантів історично більше ніж один:

- **Старший байт першим** — чинна домовленість, яку реалізують і станція, і pymavlink.
- **Молодший байт першим** — так формат описував ранній опис у трекері QGroundControl (звідти пішла назва `LITTLE_ENDIAN_UINT64_USEC_TIMESTAMP`), і так писали давні збірки, що клали мітку в рідному порядку байтів платформи. Статус: описано в тодішньому тексті трекера, чинний код пише старшим-першим; на старі файли й на чужі інструменти покладатися не можна.
- **Двадцять символів тексту** — так званий планувальний формат Mission Planner, де замість восьми двійкових байтів стоїть текстове подання часу .NET: лічильник стонаносекундних тактів від 1 січня 1 року, що його читач переводить у епоху Unix множенням на 10⁻⁷ і відніманням 719163 діб. pymavlink читає такий файл лише за явним проханням: `mavlink_connection(шлях, planner_format=True)`, у командному рядку — прапорець `--planner`.

Три несумісні кодування того самого поля, і файл не містить жодного байта, який дозволив би обрати правильне. Єдина рятівна ознака — правдоподібність: справжня мітка сьогодні — це число близько 1.79·10¹⁵, а те саме число з переставленими байтами дає або мізерію, або дату за межами тисячоліть. Саме на цьому й тримається перевірка «no valid timestamps», якою pymavlink відмовляється читати файл. Друга ознака — байт `0xFD` (або `0xFE`) рівно на дев'ятому байті файлу.

### Діалект у файлі не записано

Кадр несе числовий ідентифікатор повідомлення, а не його опис. Що означає навантаження, вирішує словник — [діалект MAVLink](root:sys-dron/mavlink-dialect), — і його назви у файлі немає. Читач із іншим словником розбере знайомі повідомлення правильно, чужі позначить як невідомі, а найгірший випадок — коли ідентифікатор зайнято в обох словниках різними повідомленнями: тоді розбір мовчки дасть неправильні числа. Контрольна сума частково рятує: у неї домішано байт, похідний від опису повідомлення, тож розбіжність визначень зазвичай виявляється як неспівпадіння суми, а не як тихо неправильні дані. Зазвичай — але не завжди, і лог із власними повідомленнями проєкту без свого словника читати марно.

### Час може йти назад

Мітки беруться з настінного годинника, тож переведення часу чи підтягування мережевим синхронізатором посеред сеансу зсуває всі наступні мітки, зокрема й назад. Читач не має права припускати, що мітки монотонно зростають, а обчислення тривалости як «остання мінус перша» на такому файлі дасть нісенітницю. Різниця між двома видами годинника — у [настінному й монотонному часі](root:sf-apps/monotonic-vs-wall-time).

## Як цей файл читають наявні інструменти

| Інструмент | Виклик | Що варто знати |
|---|---|---|
| pymavlink, бібліотека | `mavutil.mavlink_connection(шлях)` | будь-який наявний файл відкривається як лог; мітка читається як `'>Q'`, кожне повідомлення отримує поле `_timestamp` у секундах |
| pymavlink, файл без міток | `mavlink_connection(шлях, notimestamps=True)`, у командному рядку `--no-timestamps` | для `.rlog` Mission Planner та іншого «сирого» потоку без восьмибайтових міток |
| pymavlink, планувальний формат | `mavlink_connection(шлях, planner_format=True)`, у командному рядку `--planner` | текстова мітка з часу .NET замість двійкової |
| `mavlogdump.py` | `mavlogdump.py --types HEARTBEAT лог.tlog` | той самий читач у командному рядку; уміє вивантажувати в CSV, JSON і MAT |
| `MAVExplorer.py` | `MAVExplorer.py лог.tlog` | графіки полів прямо з логу |
| Mission Planner | пише власні `.tlog` у цьому ж форматі та `.rlog` без міток | `.rlog` відтворити неможливо — лише перечитати з `notimestamps` |

Мінімальний робочий прохід файлом — вісім рядків:

```python
from pymavlink import mavutil

log = mavutil.mavlink_connection("2026-08-02 12-00-00.tlog")
while True:
    msg = log.recv_match(blocking=False)
    if msg is None:                      # кінець файлу
        break
    if msg.get_type() == "BAD_DATA":     # ресинхронізація після сміття
        continue
    print(f"{msg._timestamp:.3f}  {msg.get_srcSystem():3d}/{msg.get_srcComponent():<3d}  {msg.get_type()}")
```

Два рядки тут — це весь контракт у мініатюрі. `BAD_DATA` доводиться пропускати вручну, бо байти, що не склалися в кадр, читач віддає як окремий псевдотип, а не викидає. А `msg.get_srcSystem()` у виводі стоїть тому, що без нього неможливо сказати, у який бік летів кадр.

Те саме з командного рядка:

```bash
# перелік типів і скільки їх у файлі
mavlogdump.py --show-types "2026-08-02 12-00-00.tlog"

# позиція в CSV для зовнішнього аналізу
mavlogdump.py --format csv --types GLOBAL_POSITION_INT "2026-08-02 12-00-00.tlog" > pos.csv

# перевірка на випадковий витік ключа підпису
mavlogdump.py --types SETUP_SIGNING "2026-08-02 12-00-00.tlog"
```

Три прапорці того самого інструмента закривають рівно ті три діри формату, про які йшлося вище, і саме тому їх варто знати напам'ять. `--show-source` дописує до кожного рядка ідентифікатори системи й компонента — це єдиний спосіб побачити напрямок; `--source-system` і `--source-component` тим самим полем фільтрують, лишаючи один бік розмови. `--dialect` задає словник, якого у файлі немає, — без нього читач бере типовий і на чужих повідомленнях мовчить. `--show-seq` виводить номер у послідовності до кожного рядка — і повторення того самого номера підряд одразу видає подвоєння записів із двох каналів. Сусідній `--show-loss` рахує втрати за розривами цих номерів, але на файлі з подвоєнням чи з двома різними джерелами в одному потоці його число нічого не варте, поки джерела не розділено за парою «система, компонент».

## Перший запис під шістнадцятковим редактором

Найшвидший спосіб переконатися, що файл справді той, — глянути на його початок. Ось справжній перший запис: серцебиття квадрокоптера з автопілотом PX4, прийняте о 12:00:00 UTC 2 серпня 2026 року.

```
Зсув  Байти                                 Що це

0000  00 06 58 0F 29 3E D0 00               мітка = 1 785 672 000 000 000 мкс
                                            = 2026-08-02 12:00:00 UTC
0008  FD                                    магія MAVLink 2
0009  09                                    довжина навантаження = 9
000A  00 00                                 прапорці несумісности й сумісности
000C  2A                                    номер у послідовності = 42
000D  01 01                                 система 1, компонент 1
000F  00 00 00                              ідентифікатор повідомлення = 0 (HEARTBEAT)
0012  00 00 00 00                             custom_mode = 0
0016  02                                      type = 2 (квадрокоптер)
0017  0C                                      autopilot = 12 (PX4)
0018  51                                      base_mode = 0x51
0019  04                                      system_status = 4 (активний)
001A  03                                      mavlink_version = 3
001B  EF 7B                                 контрольна сума
────
      29 Б                                  увесь запис
```

Три речі тут варті перевірки очима. Мітка закінчується двома нульовими байтами — це та сама мілісекундна роздільність: рівна секунда дає нулі, будь-яка інша мить дасть у кінці числа три нулі в десятковому записі. Байт `0x51` — це `0x40 | 0x10 | 0x01`: дозволено ручне керування, увімкнено стабілізацію, режим власний для автопілота; біта зброєности `0x80` не піднято, тож апарат на землі. І контрольна сума `EF 7B` порахована не лише по показаних байтах: у неї домішано байт, похідний від визначення `HEARTBEAT` (для цього повідомлення — 50), тож відтворити її можна тільки маючи той самий словник.

Наступний запис починається одразу за сумою, на зсуві `001D`, — і знову з восьми байтів мітки.
