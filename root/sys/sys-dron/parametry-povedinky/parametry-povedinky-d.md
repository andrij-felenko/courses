# Параметри поведінки: що налаштовне, а що зашите

<preknowlist>
- [Протокол параметрів MAVLink](root:sys-dron/mavlink-param-protocol-model) — бінарне кодування, біт-кастинг у float32 та обмін PARAM_VALUE / PARAM_SET.
- [Менеджер параметрів GCS](root:sys-dron/parameter-manager) — архітектура синхронізації дерева параметрів та валідація на боці наземної станції.
- [Дерево поведінки](root:sys-dron/derevo-povedinky) — структура дій, селекторів та параметричних умов автономної навігації.
- [Передпольотні перевірки Arming Checks](root:sys-dron/arming-checks) — верифікація цілісності калібрувань та валідності параметрів перед стартом.
- [Захист від відмов Failsafe](root:sys-dron/failsafe) — критичні пороги напруги, втрати зв'язку та таймаутів переходу в аварійні режими.
- [Мікшер моторів](root:sys-dron/motor-mixer) — матриця розподілу зусиль та конфігурація геометрії приводів.
- [Автомат польотних режимів](root:sys-dron/mode-state-machine) — стани системи та правила блокування небезпечних змін конфігурації.
</preknowlist>

Коли розвідувальний дрон літакового типу виконує політ за маршрутом в умовах бокового вітру 14 м/с, радіус прийняття проміжної навігаційної точки (Waypoint Acceptance Radius) у `1.5 м` змушує навігатор нескінченно кружляти довкола цілі. На швидкості польоту 22 м/с мінімальний радіус розвороту літака з граничним креном 35° становить близько 60 метрів, тому борт фізично не здатний перетнути півтораметрове коло без зриву потоку. Якщо це значення зашите у вихідному коді прошивки як константа `const float ACCEPTANCE_RADIUS = 1.5f;`, польова команда опиняється в глухому куті. Щоб змінити півтора метра на сорок, інженерам довелося б розгортати середовище кроскомпіляції на польовому ноутбуці, перезбирати бінарний образ, підключати програматор до роз'єму SWD під розібраним корпусом, прошивати мікроконтролер та наново проходити повну процедуру калібрування сенсорів.

З іншого боку, якщо розробник вирішить усунути будь-які обмеження і винесе у відкриту таблицю конфігурації абсолютно все — від частоти дискретизації гіроскопа до максимального кута нахилу планера, — система втрачає захищеність від людського фактора. Оператор наземної станції керування, налаштовуючи в польових умовах швидкість баражування над районом розвідки, може помилитися полем або випадково ввести в десятковому дробі кому замість крапки, надіславши граничний кут крену `85°` замість `35°`. За одну транзакцію безпілотник перетворюється на некерований снаряд, який при першій же спробі скоригувати курс виходить на закритичні кути атаки та руйнується в повітрі.

Цей конфлікт між польовою адаптивністю та структурною надійністю розв'язується через багаторівневу архітектуру параметризації (грец. παράμεтроς — співрозмірний, допоміжний показник). Вона проводить суворі інженерні межі між трьома категоріями даних: що зафіксовано в коді як непорушний закон фізики конкретного планера, що налаштовується одноразово під час виробництва чи стендового калібрування, а що віддається операторові для тактичного керування місією в реальному часі.

## Трирівнева таксономія параметрів автопілота

Усі константи, коефіцієнти зворотного зв'язку, ліміти та пороги прийняття рішень автопілота поділяються на три ієрархічні рівні. Кожен рівень має власне фізичне місце збереження, правила доступу, темп модифікації та модель захисту від збоїв.

![Ієрархія рівнів параметризації](/root/sys/sys-dron/parametry-povedinky/img/parameter-hierarchy-levels.svg)
*Трирівнева піраміда параметризації польотного контролера: від жорстко зашитих апаратних і фізичних інваріантів безпеки до динамічних місійних параметрів поведінки.*

### Рівень 1: Жорстко зашиті інваріанти безпеки (Hard Safety Limits)

Інваріанти (лат. invariabilis — незмінний) першого рівня ніколи не з'являються в таблицях протоколів конфігурації, не транслюються на наземну станцію як змінювані поля і не записуються в енергонезалежну пам'ять. Вони існують виключно в сегменті коду або констант (`.rodata` / Flash ROM) бінарного образу прошивки. Їхня модифікація вимагає явної правки вихідного коду мовами C/C++ та проходження повного циклу збирання, статичного аналізу й стендового тестування.

До твердих інваріантів належать:

1. **Граничні фізичні межі сенсорів та інтерфейсів:**
   - Максимальний динамічний діапазон гіроскопа IMU (наприклад, `±2000 dps` для мікросхеми ICM-42688P). Будь-який алгоритм фільтрації зобов'язаний вважати вимірювання за межами цього діапазону апаратним насиченням (Saturation) і відкидати їх у розрахунках орієнтації.
   - Гранична тактова частота шини SPI або I2C для опитування первинних датчиків (наприклад, `24 МГц` для швидкісного читання FIFO акселерометра).
   - Часові параметри апаратних сигналів керування моторами: мінімальна тривалість імпульсу протоколу DShot (наприклад, бітовий квант 1.67 мкс для DShot600), вихід за межі якого спричиняє зрив синхронізації мікроконтролера інвертора ESC.

2. **Абсолютні інваріанти просторової стійкості:**
   - Граничний кут крену та тангажу в режимах автономної стабілізації:
     ```
     MAX_TILT_ANGLE = 60.0°
     ```
     Перевищення цього значення в мультироторних системах веде до катастрофічної втрати вертикальної проекції сумарного вектора тяги: при нахилі 60° вертикальна сила становить лише `cos(60°) = 0.5` від номіналу, що змушує мотори працювати на 200% потужності лише для утримання висоти. У літакових планерів крен понад 60° без різкого збільшення швидкості призводить до миттєвого зриву потоку з крила та переходу в штопор.
   - Максимально допустима кутова швидкість обертання за курсом, креном і тангажем:
     ```
     MAX_ANGULAR_RATE = 300.0°/s
     ```
     Цей поріг гарантує, що матриця інтегрування кінематичних рівнянь орієнтації на основі кватерніонів не накопичує критичну похибку дискретизації за один крок інтегрування.

3. **Критичні електрохімічні пороги живлення:**
   - Абсолютний поріг напруги літієвої комірки:
     ```
     CELL_HARD_MIN_VOLT = 3.00 V
     ```
     Падіння напруги під навантаженням нижче 3.0 В на комірку ініціює незворотну хімічну деградацію катода, виділення металевого літію на аноді та стрімке лавиноподібне зростання внутрішнього опору акумулятора. Як тільки напруга перетинає цей поріг, польотний контролер зобов'язаний переходити в режим негайної керованої аварійної посадки незалежно від будь-яких налаштувань місії чи команд оператора.

4. **Часові кванти детермінованого реального часу:**
   - Період виконання внутрішнього контуру стабілізації:
     ```
     ATTITUDE_LOOP_PERIOD_US = 1000 µs (частота 1 кГц)
     ```
     Усі коефіцієнти цифрових фільтрів Баттерворта, смугових режекторних фільтрів (Notch Filters) та дискретні інтегратори базуються на фіксованому часовому кроці `dt`. Зміна цього періоду зруйнувала б частотну характеристику контуру стабілізації.

5. **Математичний захист FPU від аномальних значень:**
   - Перевірка на нечислові значення (`NaN`) та нескінченність (`Inf`): будь-який проміжний результат обчислень матриці орієнтації або інтегратора PID, що перетворюється на `NaN`, негайно блокується, замінюючись на безпечний нейтральний сигнал (наприклад, утримання поточного положення), що запобігає аварійному блокуванню апаратного математичного співпроцесора Cortex-M4/M7 FPU.

Фіксація цих констант через ключові слова `constexpr` та перевірка на етапі компіляції за допомогою `static_assert` створює надійний апаратний бар'єр. Навіть якщо енергонезалежна пам'ять польотного контролера зазнає локального пошкодження внаслідок стрибка напруги чи радіаційного збою (Single-Event Upset), жорстко зашиті інваріанти в захищеній від запису пам'яті Flash залишаються неушкодженими.

### Рівень 2: Калібрувальні та апаратні параметри (Tuning & Calibration)

Параметри другого рівня кількісно описують фізичну індивідуальність конкретного зібраного екземпляра безпілотника. Два апарати, побудовані за одним кресленням, завжди відрізняються через технологічні допуски виготовлення датчиків, неідеальність монтажу друкованої плати, залишкову намагніченість елементів конструкції та нерівномірність тяги моторів.

Ця категорія включає:

- **Калібрувальні матриці та нульові зміщення сенсорного блоку:**
  - Зміщення нуля акселерометра за трьома осями (`ACC_OFF_X`, `ACC_OFF_Y`, `ACC_OFF_Z`) та масштабні коефіцієнти чутливості (`ACC_SCALE_X`, `ACC_SCALE_Y`, `ACC_SCALE_Z`).
  - Коефіцієнти корекції твердого (Hard-Iron) та м'якого (Soft-Iron) магнітного заліза для тривісного компаса:
    ```
    B_corrected = M_soft · (B_raw - V_hard)
    ```
    де `V_hard` — вектор тривимірного зміщення (Hard-Iron offset), а `M_soft` — симетрична матриця `3×3` деформації та взаємного перекосу осей магнітометра (Soft-Iron distortion matrix), що отримуються за алгоритмом еліпсоїдальної апроксимації найменших квадратів.
  - Нульовий рівень та температурний дрейф датчика статичного й динамічного тиску трубки Піто.
  - Частоти зрізу гіроскопічних фільтрів низьких частот (`GYRO_LPF_CUTOFF`) та смугових фільтрів придушення вібрацій пропелерів (`GYRO_NOTCH_FREQ`), які розраховуються відповідно до теореми Найквіста-Котельникова:
    ```
    f_cutoff ≤ 0.5 · f_sampling
    ```
- **Геометрія рами та динамічні характеристики планера:**
  - Матриця розподілу тяги та моментів ([мікшер моторів](root:sys-dron/motor-mixer)), що враховує відстані від центру мас до кожної силової установки та кути нахилу пропелерів.
  - Головні моменти інерції апарата `I_xx`, `I_yy`, `I_zz`, необхідні для модельного прогнозування динаміки кутового руху.
  - Вектор просторового виносу антени супутникової навігації відносно блоку IMU (Lever-Arm Offset), що запобігає появі хибних прискорень у розрахунках розширеного фільтра Калмана (EKF).
- **Коефіцієнти зворотного зв'язку стабілізаторів:**
  - Пропорційні, інтегральні, диференціальні коефіцієнти та вагові коефіцієнти прямого зв'язку регуляторів кутових швидкостей (`MC_ROLLRATE_P`, `MC_ROLLRATE_I`, `MC_ROLLRATE_D`, `MC_ROLLRATE_FF`).

Головне системне правило для параметрів другого рівня: **сувора заборона зміни в повітрі (`DISARMED_ONLY`)**.

Коли мотори зведені й апарат перебуває в польоті (`ARMED`), будь-яка спроба модифікації коефіцієнтів PID або офсетів сенсорів негайно блокується скінченним автоматом автопілота ([автомат польотних режимів](root:sys-dron/mode-state-machine)). Стрибкоподібна зміна коефіцієнта `MC_ROLLRATE_P` усього на 25% у повітрі здатна миттєво перевести замкнений контур регулювання в режим автоколивань на власній резонансній частоті рами (зазвичай 40–90 Гц). За 50–100 мілісекунд такий резонанс створює колосальні струмові перевантаження в силі обмоток моторів, руйнує кріплення пропелерів і випалює силові MOSFET-транзистори електронних регуляторів швидкості.

### Рівень 3: Поведінкові та місійні параметри (Behavior & Mission Parameters)

Параметри третього рівня керують тактичною поведінкою, правилами вибору цілей, плануванням просторових траєкторій та алгоритмами реакції на нештатні ситуації. Вони спеціально спроєктовані для того, щоб оператор або автономне [дерево поведінки](root:sys-dron/derevo-povedinky) могли оперативно адаптувати дрон до поточного бойового або виробничого завдання.

Типовий склад параметрів поведінки:

- **Просторові та швидкісні уставки навігатора:**
  - Радіус кола прийняття навігаційної точки (`NAV_ACC_RAD`): визначає, на якій відстані від цільових координат точка маршруту вважається досягнутою.
  - Радіус кола баражування (`NAV_LOITER_RAD`): задає радіус орбіти очікування в зоні розвідки.
  - Круїзна швидкість польоту (`NAV_CRUISE_SPD`) та швидкість пошуку (`NAV_SEARCH_SPD`).
  - Максимальна вертикальна швидкість набору висоти (`NAV_MAX_CLIMB_RATE`) та зниження (`NAV_MAX_DESC_RATE`).
  - Дистанція випередження навігаційного переслідування (Pure Pursuit Lookahead Distance):
    ```
    L_lookahead = k_v · V_ground + L_min
    ```
    що динамічно регулює агресивність повернення дрона на лінію шляху при боковому вітрі.
- **Конфігурація аварійних систем захисту ([Failsafe](root:sys-dron/failsafe)):**
  - Пороги раннього та критичного сповіщення про розрядження батареї (`BATT_LOW_VOLT`, `BATT_CRIT_VOLT`).
  - Таймаут втрати зв'язку з пультом дистанційного керування (`COM_RC_LOSS_T`) та наземною станцією (`COM_GCS_LOSS_T`).
  - Висота безпечного повернення додому (`RTL_ALT`) та поведінка при втраті сигналу GNSS (утримання курсу за компасом чи негайна посадка).
- **Пороги оптичних та дистанційних сенсорів:**
  - Дистанція екстреного гальмування перед перешкодою за даними далекоміра чи лідара (`OBS_STOP_DIST`).
  - Поріг впевненості детектора нейромережевого модуля виявлення об'єктів для автоматичного переходу в режим супроводу цілі.
  - Таймаути повторного захоплення оптичного трекера при тимчасовому затіненні об'єкта перешкодами рельєфу.

Поведінкові параметри можуть безпечно змінюватися оператором у реальному часі безпосередньо під час польоту через телеметричний радіоканал MAVLink. Оновлення значення набуває чинності на наступному кроці планувальника місії (наприклад, на частоті 50 Гц) без зупинки процесора та без перезавантаження операційної системи реального часу (RTOS).

## Фізичні сховища параметрів: Flash, FRAM та EEPROM

Збереження налаштувань автопілота на борту вбудованого контролера підпорядковується жорстким апаратним обмеженням мікроелектроніки. Польотний контролер оперує трьома основними типами енергонезалежної пам'яті, кожен з яких має кардинально відмінні часові та фізичні характеристики.

| Апаратна характеристика | Внутрішня Flash MCU (NOR) | Зовнішня SPI/I2C EEPROM | Зовнішня SPI FRAM (FeRAM) |
| :--- | :--- | :--- | :--- |
| **Принцип зберігання заряду** | Плаваючий затвор / пастка заряду | Плаваючий затвор | Поляризація сегнетоелектрика |
| **Мінімальна одиниця стирання** | Фізичний сектор (16–128 КБ) | Байт або сторінка (32–128 Б) | Відсутнє (побайтовий перезапис) |
| **Час запису одного байта** | ~20–40 мкс | ~5 мс (Write Cycle Time) | ~50–100 нс (швидкість шини SPI) |
| **Час стирання сектора** | 200–1500 мс (**блокуючий!**) | Не потребує стирання сектора | Не потребує стирання |
| **Ресурс циклів перезапису** | 10 000 – 100 000 | 1 000 000 (10⁶) | 100 000 000 000 000 (10¹⁴) |
| **Стійкість до знеструмлення** | Вразлива під час стирання | Вразлива під час запису сторінки | Абсолютна (запис за наносекунди) |

### Небезпека блокуючого стирання внутрішньої Flash-пам'яті

Найбільш підступна пастка при збереженні конфігурації у внутрішню Flash-пам'ять мікроконтролерів популярних серій (STM32F4, STM32F7, STM32H7) криється у фізиці напівпровідникового процесу стирання комірок NOR Flash.

Щоб перезаписати хоча б одне 32-бітне число з `0` назад в `1`, апаратний контролер пам'яті зобов'язаний попередньо стерти весь фізичний сектор. Для цього вбудований помповий помножувач напруги (Charge Pump) генерує потенціал близько 12–15 В і подає його на підкладку сектора, очищуючи плаваючі затвори транзисторів від електронів (тунелювання Фаулера-Нордгейма). Цей процес займає від 200 мс на малих секторах до 1.5–2.0 секунд на великих 128-кілобайтних секторах.

У цей час внутрішній контролер Flash повністю блокує доступ до шини пам'яті (Flash Memory Controller Stall). Якщо мікроконтролер виконує польотний код із тієї ж фізичної банки пам'яті, ядро процесора ARM Cortex-M негайно зупиняється на апаратному рівні:
1. Забороняється обробка будь-яких високопріоритетних переривань від таймерів генерації сигналів DShot/ШІМ для моторів.
2. Контур оцінки кутового положення (частотою 1000 Гц) пропускає сотні послідовних циклів дискретизації.
3. Електронні регулятори швидкості ESC, не отримавши керівного імпульсу протягом таймауту безпеки (зазвичай 50–100 мс), знеструмлюють мотори.
4. Дрон переходить у некероване падіння ще до того, як операція запису параметра завершиться.

Для подолання цієї загрози в професійних польотних стеках (PX4 Autopilot, ArduPilot) використовують три взаємодоповнюючі інженерні підходи:

1. **Застосування зовнішньої сегнетоелектричної пам'яті FRAM (FeRAM):**
   Мікросхеми FRAM (наприклад, FM25V02A або MB85RS64) використовують зміщення іонів цирконію або титану всередині кристалічної решітки титанату свинцю-цирконію (PZT) під дією електричного поля. Запис відбувається миттєво (за десятки наносекунд) на повній частоті шини SPI (до 40 МГц) побайтово без необхідності попереднього стирання. Ресурс у `10¹⁴` циклів повністю усуває проблему деградації комірок, а нульова затримка виключає просідання продуктивності процесора.

2. **Емуляція EEPROM у двобанковій архітектурі Dual-Bank Flash:**
   У мікроконтролерах із двома незалежними банками пам'яті (наприклад, STM32H743/753, де є Bank 1 та Bank 2 по 1 МБ кожна) виконуваний код програми жорстко лінкується в Bank 1, а сектори збереження параметрів розміщуються виключно в Bank 2. Контролер пам'яті дозволяє процесору безперервно зчитувати інструкції з першої банки під час тривалого апаратного стирання сектора у другій банці.

3. **Асинхронний фоновий сервіс скидання (Deferred Storage Thread):**
   При зміні параметра в польоті оновлюється лише оперативний кеш у SRAM, а відповідний елемент маркується прапорцем модифікації (`dirty`). Фізичний запис у Flash відкладається до моменту деактивації моторів (`DISARMED`) або передається низькопріоритетному фоновому потоку RTOS із жорстким обмеженням тривалості операцій, що гарантує збереження часового бюджету контурів керування.

## Двобуферна транзакційна архітектура сховища (Ping-Pong Storage)

Фізична енергонезалежна пам'ять не захищена від раптового знеструмлення борту. Якщо живлення зникає саме в той момент, коли контролер записує байти оновленого параметра у Flash або EEPROM (аварія батареї, спрацьовування апаратного захисту від короткого замикання, від'єднання силового роз'єму XT60), у комірках пам'яті утворюється напівзаписане сміття.

Щоб гарантувати непорушну транзакційність (лат. transactio — здійснення, завершена дія) і цілісність конфігурації, сховище організовується за схемою **подвійної буферизації з пінг-понг секторами**.

![Конвеєр обробки та збереження параметрів](/root/sys/sys-dron/parametry-povedinky/img/param-storage-validation-pipeline.svg)
*Архітектура сховища параметрів: валідація вхідного MAVLink-пакета, потокобезпечне оновлення кешу в ОЗП, двобуферний запис у Flash з контролем CRC32 та зворотне сповіщення контурів керування.*

Фізична пам'ять ділиться на два рівновеликі сектори: `Сектор 0` та `Сектор 1`. Кожен сектор має чітку двійкову структуру з фіксованим вирівнюванням полів за 4-байтовою межею:

```
+---------------+---------------+------------------+------------------+-----------------------+---------------+
| Magic (4B)    | Format (2B)   | Sequence No (4B) | Records Cnt (2B) | Payload Data [N] ...  | CRC32 (4B)    |
| 0x5041524D    | 0x0001        | 0x00000042       | 0x00A8           | [Hash][Type][Value]   | 0x9E2B41A7    |
+---------------+---------------+------------------+------------------+-----------------------+---------------+
```

### Покроковий алгоритм транзакційного збереження

Процес оновлення конфігурації на фізичному носії виконується за строгою послідовністю дій:

```
1. Визначення цільового сектора:
   TargetSector = (ActiveSector == 0) ? 1 : 0

2. Підготовка образу в швидкій оперативній пам'яті SRAM:
   Image.Magic       = 0x5041524D ("PARM")
   Image.Format      = 0x0001
   Image.SequenceNo  = ActiveSector.SequenceNo + 1
   Image.RecordsCnt  = TotalRegisteredParams
   Копіювання всіх поточних валідних значень з кешу ОЗП у масив Image.Payload

3. Розрахунок контрольної суми CRC32:
   CRC_Calculated = CRC32_IEEE802_3(&Image, OffsetOf(CRC32))
   Image.CRC32    = CRC_Calculated

4. Запис у фізичну пам'ять:
   Апаратне стирання TargetSector (якщо це Flash)
   Послідовний запис Image у TargetSector

5. Верифікація та фіксація перемикання:
   Зчитування TargetSector з фізичного носія
   CRC_Readback = CRC32_IEEE802_3(TargetSector.Data, OffsetOf(CRC32))
   ЯКЩО CRC_Readback == TargetSector.CRC32:
       ActiveSector = TargetSector       [Транзакцію зафіксовано успішно]
       Скидання прапорців dirty в кеші
   ІНАКШЕ:
       Генерація системної помилки сховища
       ActiveSector залишається незмінним [Відкат транзакції]
```

### Стійкість до аварійного знеструмлення (Brownout Recovery)

Розглянемо найгірший сценарій: живлення бортмережі просідає нижче робочої межі стабілізатора 3.3 В рівно посеред виконання кроку 4, коли контролер встиг записати лише 40% байтів у цільовий сектор.

Під час наступного ввімкнення живлення процедура ініціалізації сховища виконує перевірку:

```
Сектор 0: Magic OK, Seq=66, CRC32 валідний   -> Стан: ДІЙСНИЙ (VALID)
Сектор 1: Magic OK, Seq=67, CRC32 ПОШКОДЖЕНИЙ -> Стан: СМІТТЯ (CORRUPTED)
```

Система виявляє невідповідність контрольної суми в Секторі 1 і повністю ігнорує його вміст. Активним сектором обирається Сектор 0 із монотонним номером послідовності `Seq=66`. Усі налаштування дрона відновлюються до стабільного стану, що передував аварійній транзакції. Жоден параметр не пошкоджується, а польотний стек виводить у системний журнал попередження `PARAM_STORAGE_TRANSACTION_RECOVERED`.

Якщо ж унаслідок катастрофічної апаратної відмови пошкоджено обидва сектори, реєстр завантажує заводські константи за замовчуванням (`def_val`), блокує зведення моторів ([передпольотні перевірки Arming Checks](root:sys-dron/arming-checks)) і сигналізує наземній станції про необхідність повторного стендового калібрування.

## Багаторівневий конвеєр валідації параметрів

Коли нове значення параметра надходить через радіоканал телеметрії або генерується внутрішнім скриптом автопілота, воно ніколи не потрапляє безпосередньо у фізичні змінні контурів стабілізації. Значення проходить послідовну фільтрацію крізь три рубежі оборони.

### 1. Синтаксична валідація меж та квантування (Range & Step Checks)

Кожен дескриптор параметра в сегменті метаданих містить мінімальну допустиму межу (`min_val`), максимальну (`max_val`) та крок дискретизації (`step`).

- **Діапазонні перевірки дійсних чисел:**
  Якщо для параметра радіуса прийняття точки `NAV_ACC_RAD` визначено діапазон `[1.0, 100.0] м`, надходження значення `-5.0` або `250.0` негайно відхиляється валідатором із поверненням статусу помилки діапазону.
- **Перевірка бітових масок (Bitmask Sanity):**
  Для параметрів-масок (наприклад, маски ввімкнення окремих передпольотних перевірок `ARMING_CHECK_MASK`, де використовується лише перші 12 бітів 32-розрядного слова) валідатор виконує побітове множення з маскою дозволених бітів:
  ```
  if ((new_val_u32 & ~VALID_ARMING_BITS_MASK) != 0) {
      return REJECT_UNKNOWN_BITS;
  }
  ```
  Це унеможливлює активацію зарезервованих або недокументованих режимів.

### 2. Контекстні та станційні охоронці (State & Access Guards)

Окремі параметри мають жорсткі обмеження на право їхньої модифікації залежно від глобального стану системи:

- **`READ_ONLY`:** ідентифікатор типу планера, унікальний 96-бітний UID кремнієвого кристала процесора, дата заводської прошивки. Модифікація заблокована на рівні API.
- **`REBOOT_REQUIRED`:** конфігурація апаратних периферійних блоків мікроконтролера — вибір протоколу виходів приводів (PWM / DShot300 / DShot600), зміна швидкості порту телеметрії `TELEM1_BAUD` з 57600 на 921600 бод, перепризначення каналів шини CAN. Нове значення успішно зберігається в енергонезалежне сховище, але робоча змінна периферійного драйвера не оновлюється до повного апаратного перезавантаження мікроконтролера.
- **`DISARMED_ONLY`:** параметри геометрії рами, офсети сенсорів, коефіцієнти стабілізатора кутових швидкостей. Зміна в польоті заблокована.

### 3. Перехресні смислові перевірки (Cross-Parameter Sanity Checks)

Найбільш критичні інженерні дефекти виникають у ситуаціях, коли кожен параметр окремо лежить у межах свого синтаксичного діапазону, але їхня спільна комбінація породжує математично некоректну або фізично аварійну поведінку.

Польотний стек реалізує систему семантичних правил взаємної сумісності:

1. **Правило орбіти очікування:**
   Радіус кола прийняття точки навігації повинен бути строго меншим за радіус кругового баражування:
   ```
   NAV_ACC_RAD < 0.8 · NAV_LOITER_RAD
   ```
   Якщо `NAV_ACC_RAD ≥ NAV_LOITER_RAD`, алгоритм навігації фіксуватиме проходження точки ще до того, як планер вийде на стабільну кругову орбіту. Це породжує нескінченне высокочастотне перемикання станів скінченного автомата між фазою підльоту та фазою утримання точки, викликаючи хаотичні ривки кермових поверхонь.

2. **Ієрархія порогів напруги акумулятора:**
   Напруга аварійної посадки повинна бути строго нижчою за напругу попереджувального повернення додому, а та — нижчою за номінальну напругу:
   ```
   CELL_HARD_MIN_VOLT < BATT_CRIT_VOLT < BATT_LOW_VOLT < BATT_NOMINAL_VOLT
   ```
   Інверсія цих значень (наприклад, встановлення `BATT_CRIT_VOLT = 3.6 В`, а `BATT_LOW_VOLT = 3.4 В`) призведе до того, що дрон проігнорує фазу керованого повернення на базу ([повернення додому](root:sys-dron/povernennia-dodomu)) і миттєво ініціює аварійну посадку посеред лісу або над водою при першому незначному просіданні напруги.

3. **Співвідношення безпечних висот місії:**
   ```
   RTL_ALT ≥ MIS_TAKEOFF_ALT  та  RTL_ALT ≤ GEOFENCE_MAX_ALT
   ```
   Висота повернення на базу зобов'язана перевищувати висоту стандартного зльоту, щоб уникнути зіткнення з деревами та спорудами довкола стартового майданчика, але не перевищувати стелю дозволеної геозони польотів ([геозона](root:sys-dron/geofence)).

4. **Швидкісні діапазони літакових планерів:**
   ```
   NAV_MIN_AIRSPEED < NAV_CRUISE_AIRSPEED < NAV_MAX_AIRSPEED
   ```
   Мінімальна повітряна швидкість розраховується з коефіцієнта запасу над швидкістю звалювання (Stall Speed) `V_stall`:
   ```
   NAV_MIN_AIRSPEED ≥ 1.3 · V_stall
   ```
   Спроба встановити круїзну швидкість нижче цього порогу негайно відхиляється семантичним валідатором.

## Протокол обміну MAVLink PARAM та клієнтські гарантії

Взаємодія польотного контролера з наземними станціями керування (QGroundControl, Mission Planner) здійснюється за відкритим протоколом **MAVLink Parameter Protocol** (версії v1 та v2).

### Проблема типізації та механіка побітового копіювання (Bit-Casting)

Історична специфікація MAVLink v1 проектувалася з жорстким обмеженням на розмір телеметричного кадру. Для уніфікації структури пакетів `PARAM_VALUE` та `PARAM_SET` усі типи значень передаються через єдине 4-байтове поле `param_value` з типом `float`:

:::tabs
```c
// Заголовок структури повідомлення PARAM_VALUE (MAVLink v1/v2)
typedef struct __mavlink_param_value_t {
    float    param_value;       // 4 байти корисного навантаження (Bit-Cast!)
    uint16_t param_count;       // Загальна кількість зареєстрованих параметрів
    uint16_t param_index;       // Порядковий індекс поточного параметра (0..N-1)
    char     param_id[16];      // 16-символьний ASCII-ідентифікатор
    uint8_t  param_type;        // Код типу (MAV_PARAM_TYPE_INT32, REAL32 тощо)
} mavlink_param_value_t;
```
```cpp
// Ідіоматичне C++20 представлення телеметричного повідомлення параметрів
struct MavlinkParamValueMsg {
    float            param_value{0.0f};  // 4 байти корисного навантаження (std::bit_cast)
    uint16_t         param_count{0};     // Загальна кількість зареєстрованих параметрів
    uint16_t         param_index{0};     // Порядковий індекс поточного параметра
    std::string_view param_id{};         // ASCII-ідентифікатор (до 16 символів)
    uint8_t          param_type{0};      // Код типу з переліку MAV_PARAM_TYPE
};
```
:::

Для передачі цілих 32-розрядних чисел (`int32_t`, `uint32_t`, бітових масок) протокол вимагає **побітового відображення (Bit-Casting)**, а не математичного приведення типів `(float)val_i32`.

Стандарт IEEE 754 для 32-бітних чисел із рухомою комою виділяє 1 біт на знак, 8 бітів на експоненту та 23 біти на мантису. При явному математичному приведенні цілого числа, що перевищує `2²⁴ = 16 777 216` (наприклад, бітової маски сенсорів `0x01FFFFFF = 33 554 431`), молодші розряди цілого числа безповоротно спотворюються через обмежену розрядність мантиси:

```
Оригінальне uint32:    0x01FFFFFF (33 554 431)
Математичне (float):   33554432.0f -> бінарно в пам'яті: 0x4C000000
Зворотне приведення:   33 554 432 (втрачено молодший біт 0!)
----------------------------------------------------------------------
Побітовий memcpy:      0x01FFFFFF -> інтерпретується як float: ~4.70e-38
Зворотний memcpy:      0x01FFFFFF (абсолютна точність усіх 32 бітів)
```

У мові C для цього застосовують `memcpy` або `union`, а в сучасному стандарті C++20 — безпечну функцію `std::bit_cast<float>(val_i32)` з заголовного файлу `<bit>`.

Детальний аналіз специфікації кадру, бінарних кодів `MAV_PARAM_TYPE` та механізмів обробки втрачених пакетів наведено у статті [Протокол параметрів MAVLink](root:sys-dron/mavlink-param-protocol-model).

### Гарантії транзакцій та негативне підтвердження (NACK)

Оскільки радіоканал телеметрії є ненадійним середовищем із можливими втратами пакетів, операція зміни параметра побудована на принципі замкненого квитування (Handshake):

```
Наземна станція GCS                               Польотний контролер
        |                                                 |
        |--- 1. PARAM_SET(param_id, new_value) ---------->|
        |                                                 | [Синтаксична валідація меж]
        |                                                 | [Перевірка стану Disarmed]
        |                                                 | [Семантичний Sanity Check]
        |                                                 | [Запис у кеш SRAM + dirty]
        |                                                 | [Сповіщення навігатора]
        |<-- 2. PARAM_VALUE(param_id, confirmed_val) -----|
        |                                                 |
```

Якщо надіслане значення є некоректним (наприклад, оператор спробував змінити `MC_ROLLRATE_P` у стані `ARMED`), польотний контролер відхиляє транзакцію і відправляє у відповідь повідомлення `PARAM_VALUE`, яке містить **поточне старе (незмінене) значення**.

Отримавши назад старе значення замість відправленого, наземна станція QGroundControl фіксує відхилення, скидає поле вводу у графічному інтерфейсі до дійсного значення борту і виводить оператору текстове попередження про причину блокування команди.

## Організація високошвидкісного реєстру в реальному часі

У високочастотному контурі стабілізації кутової орієнтації (період 1000 мкс) неприпустимо виконувати текстовий пошук параметра за рядковим іменем через функцію `strcmp`. Пошук серед 1500 параметрів дрона створив би неприйнятну затримку в 15–30 мікросекунд на кожен виклик, що відібрало б значну частку процесорного часу ядра.

Тому реєстр параметрів розділяється на дві рівноцінні складові:

1. **Словник метаданих у пам'яті констант (`.rodata`):**
   Глобальна статична таблиця, що містить повні текстові ASCII-імена, типи даних, значення за замовчуванням, межі та бітові прапорці. До цієї таблиці звертаються виключно низькочастотні сервіси: потік телеметрії MAVLink та фоновий демон синхронізації з Flash.

2. **Масив числових дескрипторів (Param Handles) у швидкій SRAM:**
   Контури стабілізації, навігації та систем безпеки під час завантаження системи одноразово знаходять числовий індекс `param_handle_t` (від `0` до `N-1`) і зберігають його. Усі подальші звернення в реальному часі здійснюються за час `O(1)` шляхом прямого індексування масиву або атомарного читання комірки пам'яті.

Нижче наведено базову організацію потокобезпечного елемента реєстру мовами C та C++.

```c
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

typedef enum {
    PARAM_TYPE_INT32 = 0,
    PARAM_TYPE_FLOAT = 1
} param_type_t;

typedef enum {
    PARAM_FLAG_NONE          = 0,
    PARAM_FLAG_DISARMED_ONLY = 1 << 0,
    PARAM_FLAG_REBOOT_REQ    = 1 << 1,
    PARAM_FLAG_READ_ONLY     = 1 << 2
} param_flags_t;

typedef union {
    int32_t i32;
    float   f32;
    uint8_t raw[4];
} param_val_t;

// Незмінні метадані у Flash ROM (.rodata)
typedef struct {
    const char*   name;            // ASCII-ім'я (до 16 символів)
    param_type_t  type;            // Код типу даних
    param_val_t   min_val;         // Мінімальна синтаксична межа
    param_val_t   max_val;         // Максимальна синтаксична межа
    param_val_t   def_val;         // Значення за замовчуванням
    uint16_t      flags;           // Бітові прапорці доступу
} param_meta_t;

// Оперативний запис у швидкій SRAM
typedef struct {
    const param_meta_t* meta;      // Покажчик на константні метадані
    param_val_t         val;       // Поточне значення
    volatile bool       dirty;     // Ознака необхідності збереження у Flash
} param_entry_t;

// Потокобезпечна валідація та запис
bool param_set_value_safe(param_entry_t* entry, param_val_t new_val, bool is_armed) {
    if (!entry || !entry->meta) return false;

    // 1. Перевірка атрибута тільки для читання
    if (entry->meta->flags & PARAM_FLAG_READ_ONLY) {
        return false;
    }

    // 2. Перевірка блокування при зведених моторах
    if (is_armed && (entry->meta->flags & PARAM_FLAG_DISARMED_ONLY)) {
        return false;
    }

    // 3. Синтаксична перевірка діапазонів
    if (entry->meta->type == PARAM_TYPE_FLOAT) {
        if (new_val.f32 < entry->meta->min_val.f32 || new_val.f32 > entry->meta->max_val.f32) {
            return false;
        }
    } else {
        if (new_val.i32 < entry->meta->min_val.i32 || new_val.i32 > entry->meta->max_val.i32) {
            return false;
        }
    }

    // 4. Оновлення значення та встановлення прапорця dirty
    entry->val = new_val;
    entry->dirty = true;
    return true;
}
```

```cpp
#include <cstdint>
#include <string_view>
#include <variant>
#include <optional>
#include <atomic>
#include <bit>

enum class ParamType : uint8_t {
    Int32,
    Float
};

enum class ParamFlags : uint16_t {
    None           = 0,
    DisarmedOnly   = 1 << 0,
    RebootRequired = 1 << 1,
    ReadOnly       = 1 << 2
};

inline constexpr ParamFlags operator|(ParamFlags a, ParamFlags b) noexcept {
    return static_cast<ParamFlags>(static_cast<uint16_t>(a) | static_cast<uint16_t>(b));
}

inline constexpr bool has_flag(ParamFlags flags, ParamFlags check) noexcept {
    return (static_cast<uint16_t>(flags) & static_cast<uint16_t>(check)) != 0;
}

using ParamValue = std::variant<int32_t, float>;

// Опис метаданих для розміщення у .rodata
struct ParamMeta {
    std::string_view name;
    ParamType        type;
    ParamValue       min_val;
    ParamValue       max_val;
    ParamValue       def_val;
    ParamFlags       flags{ParamFlags::None};
};

class ParamEntry {
public:
    constexpr explicit ParamEntry(const ParamMeta& meta) noexcept
        : meta_(meta), val_(meta.def_val), dirty_(false) {}

    [[nodiscard]] ParamValue get() const noexcept {
        return val_;
    }

    [[nodiscard]] bool set(ParamValue new_val, bool is_armed) noexcept {
        if (has_flag(meta_.flags, ParamFlags::ReadOnly)) {
            return false;
        }

        if (has_flag(meta_.flags, ParamFlags::DisarmedOnly) && is_armed) {
            return false;
        }

        if (meta_.type == ParamType::Float) {
            const float v = std::get<float>(new_val);
            const float min_v = std::get<float>(meta_.min_val);
            const float max_v = std::get<float>(meta_.max_val);
            if (v < min_v || v > max_v) {
                return false;
            }
        } else {
            const int32_t v = std::get<int32_t>(new_val);
            const int32_t min_v = std::get<int32_t>(meta_.min_val);
            const int32_t max_v = std::get<int32_t>(meta_.max_val);
            if (v < min_v || v > max_v) {
                return false;
            }
        }

        val_ = new_val;
        dirty_.store(true, std::memory_order_release);
        return true;
    }

    [[nodiscard]] bool is_dirty() const noexcept {
        return dirty_.load(std::memory_order_acquire);
    }

    void clear_dirty() noexcept {
        dirty_.store(false, std::memory_order_release);
    }

    [[nodiscard]] const ParamMeta& meta() const noexcept {
        return meta_;
    }

private:
    const ParamMeta&   meta_;
    ParamValue         val_;
    std::atomic<bool>  dirty_;
};
```

> 🔧 **Навіщо це на практиці.**
> Чітке розмежування параметрів на тверді інваріанти, калібрування планера та тактичну поведінку рятує борт від типових польових аварій. Коли оператор під час нічної розвідувальної місії збільшує дистанцію виявлення перешкод `OBS_STOP_DIST` з 5 до 15 метрів через інтерфейс планшета, це оновлення не зачіпає критичні коефіцієнти PID-регуляторів моторів і не викликає блокуючого стирання Flash-пам'яті мікроконтролера в повітрі. Атомарний кеш оперативної пам'яті гарантує, що планувальник траєкторії миттєво застосує нову безпечну дистанцію на наступному кроці алгоритму без найменшого збою в роботі 1-кГц контуру стабілізації.
