# ⚙️ Борг злиття форку в числах: як виміряти площу дотику

Питання «наскільки ми відійшли від апстриму і скільки коштуватиме наступне підтягування» має точну відповідь у вигляді трьох чисел, і всі три дістаються з git за секунду — треба лише знати, від якої точки міряти й що саме рахувати. Нижче — команди, скрипт і те, чому найважливіше з цих трьох чисел не те, яке зазвичай називають.

## Чому «скільки рядків ми змінили» — не відповідь

Найпоширеніша спроба відповісти на питання про розходження — назвати обсяг: стільки-то тисяч рядків, стільки-то файлів. Ця цифра описує **вже зроблену** роботу. А питання було про **майбутню**: скільки людино-днів піде на те, щоб узяти свіжий апстрим і не зламатися.

Ці дві величини не пов'язані. Десять тисяч рядків у файлах, яких апстрим ніколи не відкриває, вливаються автоматично й коштують нуль. Двадцять рядків у файлі, який апстрим за пів року переписав, коштують вечора зосередженої роботи — і коштуватимуть його знову на наступному релізі. Обсяг міряє вашу працю, а рахунок виставляє **збіг**: скільки файлів правили обидві сторони одночасно.

Тому вимірювати треба не «скільки ми змінили», а «де ми змінили те саме, що й вони». Це різні множини, і git уміє показати обидві.

## Усе міряють від точки розгалуження

Перша спокуса — порівняти свою вершину з вершиною апстриму: `git diff upstream/master HEAD`. Так робити не можна, і причина логічна, а не технічна.

Такий diff показує різницю двох станів, у якій **змішано дві історії**. Рядок, що в ньому виглядає як «ваша зміна», може насправді бути чужою зміною, якої у вас просто ще немає. Розрізнити їх у самому diff нічим: він не знає, хто автор, він знає лише «тут одне, там інше». Питання ж стоїть про внески кожної сторони окремо.

Розділити їх можна тільки одним способом — знайти останній стан, у якому обидві сторони були згодні, і від нього побудувати **два незалежні** diff-и. Цей стан у git називається базою злиття (англ. *merge base*) — найпізніший спільний предок двох комітів. Саме його бере тришляхове злиття, коли вирішує, чия зміна де: [механіку цього рішення розібрано окремо](root:sf-release/version-control/math-three-way-merge.md), і вона пояснює, чому без бази задача взагалі не має розв'язку.

```bash
git remote add upstream https://github.com/mavlink/qgroundcontrol.git
git fetch upstream --tags
git merge-base upstream/master HEAD
# 9f3c1ad2b7e5...
```

Одна деталь про суміжну команду: `git merge-base --fork-point` шукає базу не в графі комітів, а в рефлозі віддаленої гілки — тобто спирається на локальний журнал того, де ця гілка стояла раніше. Рефлог живе обмежений час і вичищається складачем сміття; коли потрібний запис зник, режим `--fork-point` просто здається — так задумано, щоб не видати випадковий результат. Для довгоживучого форку це означає одне: у скриптах і в CI беріть звичайний `merge-base`, без `--fork-point`, бо він працює з графа й не залежить від того, що пам'ятає ваша копія.

![Угорі — лінія апстриму й лінія форку, що розходяться з однієї точки; підписано, що рахують «позаду» і «попереду». Унизу три смуги: файли, які змінив апстрим від точки розгалуження; файли, які змінив форк; їхній перетин, підписаний як рахунок за наступне злиття](img/divergence-measure.svg)

*Від точки розгалуження виходять два незалежні diff-и. Конфлікт може народитися лише там, де вони накладаються.*

## Три команди, три числа

**Календарна відстань.** Скільки комітів у кожної сторони від бази:

```bash
git rev-list --left-right --count upstream/master...HEAD
# 1487	63
```

Три крапки тут означають симетричну різницю: ліве число — коміти, що є в апстримі й нема у вас (ви позаду), праве — ваші власні (ви попереду). Це число добре відповідає на питання «як давно ми не синхронізувалися», і майже нічого не каже про ціну. Ще й бреше після роздавлених злиттів: якщо ваші правки йшли в апстрим через squash, у вас лишаються оригінальні коміти, яких там формально немає, і «попереду» роздувається.

**Обсяг.** Скільки файлів і рядків ви змінили від бази:

```bash
git diff --stat upstream/master...HEAD | tail -1
# 312 files changed, 18944 insertions(+), 2201 deletions(-)
```

Обережно з трьома крапками: у `git diff` вони означають **не** те, що в `git log` і `git rev-list`. Там це симетрична різниця, а тут — «від бази злиття до правого коміта», тобто рівно `merge-base(A,B)..B`. Одна й та сама нотація, два різні значення; плутанина тут коштує неправильних чисел у звіті.

**Розподіл по дереву.** Куди саме розповзлися правки:

```bash
git diff --dirstat=files,0,2 upstream/master...HEAD
#   4.8% CMakeLists.txt
#  31.2% src/FlightDisplay/
#  22.5% src/Vehicle/
#  38.9% custom/
```

`files` каже рахувати файли, а не рядки, перший нуль знімає поріг відсікання дрібних тек, двійка обмежує глибину. Цей рядок — перше, що варто подивитися: він одразу показує, чи ваша робота зібрана в кількох місцях, чи розмазана по всьому дереву.

## Число, яке справді є рахунком

Тепер головне. Візьмімо два списки файлів від однієї бази:

```
M — файли, які від бази змінили ВИ
U — файли, які від бази змінив АПСТРИМ
```

Файл, що лежить лише в `M`, апстрим не чіпав — злиття перенесе вашу версію без запитань. Файл, що лежить лише в `U`, не чіпали ви — прийде чужа версія, теж без запитань. **Ручна робота можлива тільки в перетині.** Це не емпіричне спостереження, а прямий наслідок того, як працює тришляхове злиття: коли одна зі сторін не змінювала файл відносно бази, вибір однозначний.

Звідси два робочі показники:

```
S = M \ (тека накладки)      площа дотику: спільні файли, які ви правили
C = S ∩ U                    зона зіткнення: рахунок за наступне злиття

частка зіткнення   c = |C| / |S|
```

Тека накладки віднімається не для краси. Своє в `custom/` апстрим не бачить у принципі — [окремої теки для власної збірки](root:sys-dron/custom-build) там просто немає, тож у `U` ці шляхи не потраплять ніколи. Двісті файлів накладки й п'ятдесят правок у спільному коді — це форк із боргом на п'ятдесят файлів, а не на двісті п'ятдесят.

Уточнення, без якого показник обманює в інший бік: `C` — це **верхня межа** конфліктів, а не їх кількість. Git зливає порядкові куски, тож у файлі, який обидві сторони чіпали в різних місцях, автоматика впорається сама. Але переглянути такий файл усе одно доведеться — «зібралося без конфлікту» не означає «поводиться як треба», особливо коли апстрим переписав функцію, яку ви обгорнули своєю. Тому `|C|` — це чесна оцінка обсягу **рецензування**, а число справжніх конфліктів усередині неї менше й наперед невідоме.

Груба модель ціни, з якої вже можна планувати:

```
ціна злиття ≈ Σ (t₀ + k·Lᵢ),   i ∈ C
t₀ — стала на файл: відкрити, згадати, чому там наша правка   (≈ 5–15 хв)
Lᵢ — скільки рядків апстрим змінив у цьому файлі від бази
k  — ваша власна швидкість розбору                            (≈ 0.2–1 хв/рядок)
```

Сталу `t₀` й коефіцієнт `k` беруть із власного досвіду — після першого ж злиття, зробленого з секундоміром, вони стають вашими числами, а не чужими.

> 🔧 **Навіщо це.** Ці цифри перетворюють суперечку на арифметику. Коли замовник просить функцію, яку не витягти точками розширення, ви більше не кажете «це дорого в супроводі» — ви кажете «це додасть вісім файлів до зони зіткнення, а вони в найгарячішій теці апстриму, тож кожен реліз коштуватиме на день більше». Порахувати це можна ще до того, як написано перший рядок: досить подивитися, скільки апстрим наміняв у тих файлах за минулий рік.

## Скрипт: площа дотику й зона зіткнення

Робота тут — запустити git, розібрати текст, перетнути множини й згрупувати за теками. Це класичний аналітичний скрипт на робочій машині й у CI, тому основна версія — Python: `subprocess`, множини й `Counter` уже в стандартній бібліотеці, збирати нічого не треба. Друга вкладка — TypeScript для команд, у яких CI й так на Node; логіка та сама, ідіоми свої.

Скрипт розділяє ваші зміни на три купи (накладка, нові файли у спільних теках, правки чужих файлів), перетинає третю з апстримними змінами й дозважує перетин обсягом апстримних правок у кожному файлі.

:::code proj-fork-divergence/ts/index.ts

Запуск на форку станції виглядає так — переклади й згенероване одразу відсікаємо, чому саме так, пояснено нижче:

```bash
python fork_debt.py \
  --upstream upstream/master \
  --overlay custom/ \
  --exclude 'translations/*.ts' \
  --exclude '*.qm' \
  --budget 60
```

## Як читати звіт

Числа в прикладі ілюстративні — вони показують форму відповіді, не чийсь конкретний форк:

```text
точка розгалуження        : 9f3c1ad2b7
комітів позаду / попереду : 1487 / 63

ваші зміни від точки розгалуження
  у теці накладки custom/          214
  нові файли у спільних теках      9
  ПРАВКИ спільних файлів          57   ← площа дотику

апстрим від тієї ж точки зачепив 3162 файли
зона зіткнення: 41 із 57 (72%) — тут буде ручна робота

  src/Vehicle                        14 файлів     2843 рядки апстриму
  src/FlightDisplay                   9 файлів      612 рядків апстриму
  src/Settings                        7 файлів      430 рядків апстриму
  src/AutoPilotPlugins                4 файли       905 рядків апстриму
  (корінь)                            3 файли       188 рядків апстриму
```

Читається це так. Дві сотні файлів у накладці — добра новина, а не погана: там сидить основна робота, і вона безкоштовна в супроводі. П'ятдесят сім правок у спільному коді — це і є весь борг. Сімдесят два відсотки зіткнення — сигнал тривоги: ви лізли саме в те, що апстрим активно розвиває, і кожен синхрон буде важким. Були б ті самі п'ятдесят сім файлів у сонному куті дерева, частка впала б до одиниць відсотків, а разом із нею й ціна.

Розбивка за теками каже, **куди дивитися**. Чотирнадцять файлів у `src/Vehicle` при майже трьох тисячах змінених там апстримом рядків — це найдорожча позиція звіту, і саме її варто пробувати переписати на точки розширення. Три файли в корені при ста вісімдесяти рядках — це майже напевно правки збірки, і їх дешевше не чіпати взагалі, а винести в свій `cmake`-файл усередині накладки.

Головне ж — цифру треба **міряти регулярно й тримати межу**. Прапорець `--budget` для цього й потрібен: поставте його в CI на кожен pull request у свою гілку, і будь-яка правка, що виводить зону зіткнення за домовлену межу, зупиняється до окремого рішення. Без такої межі площа дотику росте безшумно — кожна окрема правка «маленька», а через рік підтягування апстриму стає проєктом на місяць. Це рівно та сама механіка, що й у [технічного боргу](root:sf-apps/technical-debt): тіло боргу непомітне, дорого коштують відсотки, і платять їх щоразу.

## Скільки це коштує рахувати

Сам скрипт лінійний: він читає вивід git і кладе шляхи в множини, тобто `O(|M| + |U|)`. На дереві станції це кількадесят тисяч рядків тексту — мілісекунди.

Ціну задає git, і головна її частина — не обхід дерева, а **розпізнавання перейменувань**. Точний етап зіставляє однакові хеші вмісту й дешевий. Неточний етап шукає схожі файли серед доданих і вилучених, порівнюючи їх попарно, тобто працює за `O(A·D)`. Саме тому в git є стеля `diff.renameLimit`, а при її перевищенні з'являється попередження, що неточне розпізнавання пропущено. Для форку це не дрібниця: коли перейменування не розпізналося, ваш файл виглядає як пара «вилучено + додано», і він **випадає** із зони зіткнення саме тоді, коли насправді дорожчає найбільше. Тож або підніміть межу (`git config diff.renameLimit 0` знімає її зовсім, ціною часу), або звіряйте звіт із окремим списком апстримних перейменувань:

```bash
git log --diff-filter=R --find-renames --name-status --oneline \
        $(git merge-base upstream/master HEAD)..upstream/master
```

Практичний орієнтир: на дереві масштабу станції повний прогін звіту вкладається в кілька секунд, тобто його спокійно можна тримати кроком CI, а не ритуалом раз на квартал.

## Пастки

**Ребейз довгоживучої гілки.** Спокуса «просто відребейзити наш форк на свіжий апстрим, щоб історія була рівна» коштує дорого саме тому, що ребейз **переписує коміти**: у них нові хеші, а стара точка розгалуження перестає бути спільним предком узагалі. Наслідки йдуть ланцюжком. Усі, хто клонував форк, дістають гілку, що не зливається з їхньою. Історія «хто й навіщо це змінив» тепер вказує на дату ребейзу, а не на дату рішення. І найдошкульніше — записані розв'язання конфліктів (`git rerere`, вмикається `git config rerere.enabled true`) перестають збігатися, бо збіг там шукається за станом конфлікту, а стан змінився. Для форку-продукту правильний хід — злиття: воно лишає базу на місці, тож усі виміри вище лишаються можливими, а `rerere` знімає з вас повторне розв'язування того самого конфлікту на кожному релізі. Ребейз добрий рівно там, де він і задуманий, — на короткій гілці, яку зараз віддадуть в апстрим; [різницю між цими двома режимами роботи з історією](root:sys-ide/git-branching-and-history) варто розуміти до того, як ви оберете стратегію на роки.

**Перейменування в апстримі.** Крім описаної вище межі розпізнавання, є простіший випадок: апстрим переніс теку. Ваші правки лишилися прив'язані до старих шляхів, і злиття або принесе конфлікт «видалено в них, змінено в нас», або, ще гірше, тихо збереже ваш файл на старому місці — де його вже ніхто не збирає. Тому список апстримних перейменувань дивляться **перед** злиттям, а не після. У самому проєкті станції є навчальний випадок такої пастки: документація радить не перейменовувати теку-зразок `custom-example` у `custom`, а **скопіювати** її — бо перейменування, за словами документації, призводить до проблем зі злиттям, коли ви підтягуєте свіжий апстрим. Причина рівно та: `custom-example` — файли апстриму, а перейменована тека для git виглядає як перенесення саме їх.

**Підмодулі.** [Підмодуль](root:sys-ide/git-submodules) — це чужий репозиторій, вкладений у ваш: батьківське дерево зберігає не його файли, а один ідентифікатор коміта, на якому цей репозиторій зафіксовано. Тому підмодуль у diff — це один рядок. Ваш звіт побачить «один змінений файл», а за ним може стояти рік чужої роботи; злиття ж дасть конфлікт вигляду «дві різні версії покажчика», який автоматика не розв'яже ніколи, бо не знає, яка з версій вам потрібна. Гірше те, що склад підмодулів сам є рухомою частиною: у лінії 4.4 репозиторій станції ніс близько десятка підмодулів — від бібліотеки MAVLink у `libs/mavlink/include/mavlink/v2.0` і драйверів GPS у `src/GPS/Drivers` до `libs/eigen` і `libs/shapelib`, — а в гілці 5.0 лишився рівно один, `src/FirmwarePlugin/APM/ArduPilot-Parameter-Repository`, бо решту залежностей перевели на завантаження засобами CMake. Такий перехід одним махом перекроює вашу площу дотику: файли, які ви правили в підмодулі, більше не там, а ваші правки збірки — про механізм, якого вже немає. Дивіться на `git submodule status` окремо від головного звіту й тримайте зміни підмодулів у власних гілках цих підмодулів, а не в робочій копії.

**Згенероване й переклади.** Каталог перекладів станції — це файли `translations/qgc_*.ts`, які збирає й перезаписує інструмент розбору вихідників; збірка забирає їх звідти шаблоном. Досить будь-кому запустити оновлення перекладів, і в diff з'являються десятки тисяч змінених рядків, які нічого не означають. Те саме роблять будь-які згенеровані артефакти, що потрапили під версійний контроль. Для звіту вони — чистий шум, який роздуває і площу дотику, і зону зіткнення. Виключати їх треба **явно** (`:(exclude)` у скрипті), але з двома застереженнями: рахуйте раз із ними й раз без них, бо велика різниця сама по собі є діагнозом — у вас у репозиторії лежить те, чого там бути не мало; і не виключайте нічого «на око», бо під шум легко сховати справжню правку.

**Не та гілка апстриму й неповний клон.** Форк, зроблений від релізної гілки, треба міряти проти неї ж: база проти `master` буде значно старіша, а числа — паніка на порожньому місці. І окремо про CI: у неглибокому клоні (`git clone --depth 1`) спільної історії просто немає, тож `merge-base` не знайде нічого. Або клонуйте повністю, або дотягуйте історію (`git fetch --unshallow`) перед виміром — інакше звіт мовчки збреше на нуль.

Унизу: ребейз довгоживучої гілки — стара точка більше не спільна, старі коміти показані сірим як такі, що більше не існують](img/fork-history-strategy.svg)

*Злиття зберігає точку розгалуження — і разом із нею можливість щось виміряти. Ребейз її знищує.*

Останнє зауваження про сенс усієї вправи. Виміряна площа дотику — не вирок, а карта: вона показує, які саме правки варто спробувати перенести в накладку, а які — віддати назад у джерело, з якого форк зроблено, як нову точку розширення. Цей другий шлях працює лише тому, що між похідним репозиторієм і його [джерелом](root:sf-release/fork-and-upstream) зміни ходять в обидва боки, а не тільки згори вниз. Форк, який міряє свій борг щомісяця, зазвичай виявляє, що вісімдесят відсотків зони зіткнення дає п'ятірка файлів — і що з чотирьох із них можна вийти за тиждень роботи.
