Вантажний гексакоптер масою вісім кілограмів виконує повністю автономну доставку контейнера з медикаментами на автоматизовану прийомну станцію за дванадцять кілометрів від точки старту. На чотирнадцятій навігаційній точці маршруту апарат переходить у фазу фінального позиціонування: він повинен знизитися до висоти дванадцяти метрів, увімкнути курсову камеру, розпізнати візуальну мітку посадкового термінала (AprilTag) та надіслати цифровий запит на відкриття захисного люка по радіоканалу MAVLink, очікуючи квитування `COMMAND_ACK`.

Під час зависання над терміналом локальний порив вітру здіймає хмару піску, яка забруднює захисне скло камери, а електромагнітні завади від промислового приводу шлюзу блокують приймання пакетів відповіді. Навігаційний автомат переходить у стан `WAITING_FOR_DOCK_READY`. Команда на відкриття шлюзу не підтверджується, умова завершення етапу не настає, але для стандартної системи аварійного захисту (Failsafe) політ виглядає штатно: зв'язок із супутниками GNSS стабільний, розширений фільтр Калмана (EKF) видає високу точність позиції, а мотори бездоганно тримають горизонт. Шість безколекторних моторів споживають сумарний струм 42 А при потужності 950 Вт. За шість з половиною хвилин нерухомого очікування в повітрі акумуляторна батарея 6S ємністю 22 000 мА·год повністю вичерпує свій корисний заряд, напруга на силовій шині просідає нижче 18.0 В (3.0 В на банку), супервізор живлення польотного контролера ініціює апаратне відсікання живлення (under-voltage lockout), і апарат падає на бетонний майданчик поруч із терміналом.

Ця катастрофа розкриває фундаментальну проблему архітектури автономного польоту: **завислу поведінку** (*Hung Behavior*). Якщо кожна окрема підзадача місії не має детермінованого ліміту часу, не контролює фізичний рух до мети і не звіряє витрати енергії з вартістю маневру відступу, автопілот стає заручником очікування події, яка в реальному фізичному світі може ніколи не відбутися.

## Анатомія «вічного очікування» в автономних системах

В інженерії програмного забезпечення польотних стеків зависання поведінки суттєво відрізняється від класичного зависання операційної системи (deadlock, livelock або паніка ядра RTOS). У середовищах NuttX, FreeRTOS чи ChibiOS планувальник задач справно перемикає контексти, потік контуру стабілізації з частотою 400 Гц генерує PWM-сигнали для регуляторів швидкості (ESC), навігаційний потік на частоті 50 Гц зливає покази акселерометрів, гіроскопів та GNSS, а модуль зв'язку транслює телеметрію на наземну станцію.

Зависання відбувається на рівні **логіки поведінкового автомата** (*Behavior State Machine*): поточний стан очікує виконання певної булевої умови переходу, яка за поточних фізичних або програмних умов стала принципово недосяжною.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    ПРИРОДА ЗАВИСАННЯ АВТОНОМНОЇ ПОВЕДІНКИ                   │
├─────────────────────────────────────────────────────────────────────────────┤
│ 1. Аеродинамічне насичення: зустрічний вітер > максимальної швидкості       │
│    Дрон летить на 100% тяги вперед, але фізично зноситься назад             │
├─────────────────────────────────────────────────────────────────────────────┤
│ 2. Оптична та сенсорна сліпота: забруднення, засвічення, втрата контрасту   │
│    Нескінченне очікування захоплення візуального орієнтира або мітки        │
├─────────────────────────────────────────────────────────────────────────────┤
│ 3. Геометричні тупики: симетричні перешкоди та локальні мінімуми APF        │
│    Нульовий результуючий вектор сил відштовхування та притягання            │
├─────────────────────────────────────────────────────────────────────────────┤
│ 4. Зависання детектора контакту: шум лідара, екранний ефект у траві         │
│    Неможливість зафіксувати спадання ваги й нульову вертикальну швидкість   │
├─────────────────────────────────────────────────────────────────────────────┤
│ 5. Комунікаційний дедлок: втрата MAVLink COMMAND_ACK або CAN-пакета         │
│    Безтаймаутне блокування синхронного або асинхронного запиту              │
└─────────────────────────────────────────────────────────────────────────────┘
```

Розглянемо фізичні та програмні механізми, які перетворюють штатні польотні операції на нескінченні пастки.

### 1. Аеродинамічне насичення та боротьба із зустрічним вітром

При переміщенні до чергової точки маршруту навігаційний алгоритм очікує, що апарат увійде у сферу радіуса прийняття (*Acceptance Radius* `R_acc`, типово 1.5–3.0 м). Для переміщення вперед мультикоптер нахиляє вектор сумарної тяги пропелерів на кут тангажу `θ`.

Максимальний кут нахилу апарата `θ_max` жорстко обмежений параметрами автопілота (зазвичай 30–35°), щоб запобігти зриву потоку з гвинтів, перевантаженню силових транзисторів ESC та зберегти достатню вертикальну проекцію тяги для компенсації сили тяжіння.

Рівняння стаціонарного горизонтального польоту пов'язують вертикальну та горизонтальну проекції тяги гвинтомоторної групи:

```
T · cos(θ_max) = m · g                                      [компенсація сили тяжіння]
T · sin(θ_max) = 0.5 · C_d · ρ · A · v_air²                 [горизонтальна сила тяги]
tan(θ_max) = (0.5 · C_d · ρ · A · v_air²) ÷ (m · g)         [відношення сил]
v_air_max = √((2 · m · g · tan(θ_max)) ÷ (C_d · ρ · A))     [гранична повітряна швидкість]
```

де:
* `m` — злітна маса безпілотника (кг),
* `g` — прискорення вільного падіння (9.81 м/с²),
* `C_d` — коефіцієнт лобового аеродинамічного опору рами та корисного навантаження,
* `ρ` — густина повітря (типово 1.225 кг/м³ на рівні моря),
* `A` — площа міделевого перерізу апарата (м²),
* `v_air_max` — гранична швидкість руху відносно повітряної маси.

Якщо швидкість зустрічного вітру `v_wind` перевищує граничну повітряну швидкість `v_air_max`, результуюча колійна швидкість відносно землі (`v_ground`) стає від'ємною:

```
v_ground = v_air_max - v_wind < 0  [рух апарата у зворотному напрямку]
```

Автопілот утримує максимальний кут тангажу, інтегральна складова PID-регулятора швидкості насичується до максимального ліміту (integrator windup), струм моторів досягає пікових значень, але апарат фізично віддаляється від цілі. Якщо навігаційний менеджер не перевіряє знак та величину наближення, дрон буде спалювати батарею на повній потужності, поки не впаде через повний розряд.

### 2. Оптична сліпота та втрата візуальних орієнтирів

У місіях із застосуванням технічного зору (посадка на рухому платформу, інспекція будівельних конструкцій, точне позиціонування за алгоритмами оптичного потоку або Visual-Inertial Odometry, VIO) поведінковий стан очікує появи в кадрі специфічного патерну.

Сенсорний зрив стається через природні оптичні фактори:
* **Пряме сонячне засвічення (Sun Flare)**: потрапляння променів низького сонця безпосередньо в об'єктив викликає паразитні відблиски та засліплює CMOS-матрицю, знижуючи контрастність зображення до нуля.
* **Динамічне розмиття (Motion Blur)**: різкий порив вітру викликає кутове прискорення рами, через що алгоритми детекції кутів (FAST, Harris, ORB) втрачають опорні точки.
* **Однорідна підстильна поверхня**: політ над свіжим снігом, спокійною водою або свіжим асфальтом не дає градієнтів яскравості для обчислення оптичного потоку. При цьому ранг матриці градієнтів яскравості в алгоритмі Лукаса-Канаде падає, матриця автокореляції стає виродженою, і оцінка переміщення занулюється.

Якщо поведінка наведення спроєктована без обмеження часу на пошук орієнтира, алгоритм потрапляє в режим нескінченного нишпорення (searching spiral), утримуючи апарат у повітрі до вичерпання палива чи заряду.

### 3. Геометричні пастки та локальні мінімуми планувальника

Під час автономного обходу перешкод на базі бортових лідарів чи стереокамер широко застосовується метод штучних потенціальних полів (*Artificial Potential Fields*, APF) або локальні планувальники траєкторій (VFH+, TEB Local Planner).

У методі потенційних полів ціль створює притягальну силу `F_att`, а кожна виявлена перешкода — відштовхувальну силу `F_rep`:

```
F_total = F_att(p, p_target) + ∑ F_rep(p, p_obs_i)  [результуючий вектор сили]
```

Коли безпілотник підлітає до U-подібної будівлі, високого лісового масиву або групи опор ЛЕП, вектор відштовхування від стін може стати точно протилежним за напрямком і рівним за модулем вектору притягання до точки:

```
F_att + ∑ F_rep = 0  [стан локального мінімуму]
```

Результуюча розрахункова швидкість падає до нуля. Дрон зупиняється перед перешкодою, не маючи змоги рухатися вперед, але й не відступаючи назад. З точки зору місійного таймера дрон «летить до точки», хоча фактично він нерухомо завис у кінематичній пастці.

### 4. Зависання детектора контакту з землею (Touchdown Detector Lock)

Фінальна фаза автоматичної посадки — одна з найнебезпечніших ділянок польоту. Польотний контролер повинен надійно зняти блокування моторів (*Disarm*), коли шасі торкнулися ґрунту.

Стандартний кінцевий автомат детектора посадки вимагає одночасного виконання трьох фізичних умов протягом фіксованого вікна стабільності `T_touch` (1.0–2.0 с):
1. Тяга моторів перебуває на мінімальному рівні утримання (`T_cmd ≤ T_min_landing`, зазвичай 15–20% від номіналу).
2. Оцінка вертикальної швидкості за EKF перебуває в межах нуля (`|v_z| < 0.15–0.25 м/с`).
3. Висота за даними далекоміра не змінюється протягом заданого інтервалу.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    УМОВИ СПРАЦЮВАННЯ ДЕТЕКТОРА ПОСАДКИ                      │
├─────────────────────────────────────────────────────────────────────────────┤
│ (T_cmd < 0.20 · T_hover) ∧ (|v_z| < 0.15 м/с) ∧ (Δh_lidar < 0.05 м)        │
│                Тривалість виконання умов: t ≥ 1.5 с                         │
└─────────────────────────────────────────────────────────────────────────────┘
```

Якщо посадка виконується у густу траву, чагарник або на пухкий сніг, виникають дві аномалії:
* Лазерний промінь лідара проходить крізь стебла на різну глибину, викликаючи високочастотні шумові стрибки вимірюваної висоти.
* Аеродинамічний екранний ефект (*Ground Effect*) створює під пропелерами подушку підвищеного статичного тиску:
  
  ```
  Δp_ground = 0.5 · ρ · (v_downwash)²
  ```
  
  через що апарат продовжує підстрибувати на висоті 10–20 см, а барометричний висотомір фіксує помилкові коливання тиску.

У результаті вертикальна швидкість за EKF ніколи не опускається нижче 0.15 м/с. Детектор торкання зависає, автопілот не знімає тягу з моторів, пропелери чіпляють рослинність, що призводить до перегріву обмоток, згоряння ключів MOSFET у регуляторах швидкості або перекидання апарата.

### 5. Комунікаційні блокування (Handshake Deadlock)

Сучасні дрони містять розподілену обчислювальну мережу: польотний контролер жорсткого реального часу (Flight Controller, наприклад STM32H7 під керуванням PX4/ArduPilot), бортовий комп'ютер комп'ютерного зору (Companion Computer, наприклад NVIDIA Jetson Orin під Linux/ROS 2), смарт-батарею по шині SMBus, корисне навантаження (сервопривід скидання, гіростабілізований підвіс камери) по шині CAN/DroneCAN.

Якщо алгоритм переходу в наступний стан місії реалізовано за наївною синхронною моделлю запиту-відповіді:

```
[Стан: RELEASE_PAYLOAD] ───> Надіслати CAN-пакет 'ACTUATOR_OPEN'
                                   │
                                   ├───> Очікування переривання від кінцевика
                                   └───> Очікування відповіді 'PAYLOAD_RELEASED'
```

Будь-яка апаратна відмова — перебитий дріт зворотного зв'язку, механічне заклинювання сервоприводу, збій трансивера CAN або переповнення черги повідомлень UART — повністю паралізує навігаційний потік. Контролер залишається заблокованим у стані очікування квитування, спалюючи залишок енергії батареї на утримання позиції.

## Тривимірна архітектура моніторингу часу та прогресу

Щоб унеможливити потрапляння автопілота у стан вічного очікування, польотний стек повинен використовувати **тривимірну систему нагляду за поведінкою** (*Three-Dimensional Behavior Watchdog Architecture*). Жодна поведінка не може вважатися безпечною, якщо вона контролюється лише одним скалярним таймером.

Три виміри контролю діють абсолютно незалежно й паралельно:

```
                      ┌────────────────────────────────────────┐
                      │    ТРИВИМІРНИЙ ПРОСТІР ТАЙМАУТІВ       │
                      └───────────────────┬────────────────────┘
                                          │
            ┌─────────────────────────────┼────────────────────────────┐
            ▼                             ▼                            ▼
  ┌───────────────────┐         ┌───────────────────┐        ┌───────────────────┐
  │ ЖОРСТКИЙ ЧАСОВИЙ  │         │   ПРОСТОРОВИЙ     │        │   ЕНЕРГЕТИЧНИЙ    │
  │  (Hard Real-Time) │         │ (Kinematic Prog)  │        │  (Energy Budget)  │
  ├───────────────────┤         ├───────────────────┤        ├───────────────────┤
  │ Абсолютний ліміт  │         │ Проекція швидкості│        │ Динамічний ліміт  │
  │ за монотонним     │         │ на вектор мети,   │        │ повернення додому │
  │ таймером (мкс)    │         │ дисперсія EKF     │        │ з урахуванням вітру│
  └───────────────────┘         └───────────────────┘        └───────────────────┘
```

Розглянемо фізичну та математичну сутність кожного виміру.

### 1. Жорсткий абсолютний таймаут (Hard Real-Time Watchdog)

Жорсткий таймаут є останньою безумовною лінією захисту. Він визначає максимальний астрономічний інтервал часу, виділений на виконання операції за найгірших умов.

#### Вимоги до джерела часу в критичних системах
Використання функцій календарного часу (`gettimeofday()`, POSIX `CLOCK_REALTIME` або часу GNSS) у сторожових таймерах **категорично неприпустиме**. 

Причини відмови від астрономічного часу:
1. **Стрибки при отриманні навігаційного фіксу**: до моменту захоплення супутників системний годинник бортового комп'ютера стартує з епохи за замовчуванням (наприклад, 1 січня 1970 року або дата збірки ядра). При отриманні першого NMEA/UBX-повідомлення час миттєво стрибає вперед на десятиліття. Якщо таймаут обчислювався як `t_start + T`, різниця `t_now - t_start` миттєво викличе хибне аварійне спрацювання.
2. **Секунди координації (Leap Seconds) та корекція NTP/PTP**: ступенева корекція часу назад на одну секунду призводить до від'ємного інтервалу `Δt < 0`, що в беззнаковій арифметиці (`uint32_t`, `uint64_t`) викликає переповнення лічильника до `2⁶⁴ - 1` і повне заморожування таймауту на сотні тисяч років.

#### Монотонний апаратний лічильник
Відлік часу повинен базуватися виключно на монотонному таймері апаратного рівня (`CLOCK_MONOTONIC_RAW` в Linux або `hrt_absolute_time()` у мікроконтролерах STM32 під NuttX).

В операційній системі NuttX системний таймер високої роздільної здатності (*High Resolution Timer*, HRT) налаштовується на базі 32-бітного апаратного таймера (наприклад, TIM2 або TIM5 у мікроконтролерах STM32H7), тактованого з частотою 1 МГц (дискретність 1 мікросекунда). Переповнення 32-бітного регістра (кожні 71.5 хвилин) обробляється швидким перериванням ISR, яке інкрементує старші 32 біти в оперативній пам'яті, формуючи безперервний 64-бітний монотонний лічильник мікросекунд:

```
Δt_elapsed = hrt_absolute_time() - behavior_start_time_us
```

Якщо `Δt_elapsed ≥ T_hard_limit_us`, навігаційний диспетчер генерує безумовний сигнал переривання дії `STATUS_TIMEOUT_HARD`.

### 2. Моніторинг динамічного кінематичного прогресу (Progress-Based Watchdog)

Очікування спрацювання жорсткого таймауту часто є надто повільним: якщо на політ до точки виділено 90 секунд, а апарат застряг на перших метрах через шквал вітру, спалювати енергію решту 85 секунд неприпустимо. Необхідно відстежувати **динаміку просторового наближення**.

#### Векторна проекція швидкості на вісь мети
Нехай поточні координати апарата в локальній системі координат NED становлять `p(t) = [x, y, z]ᵀ`, а координати цільової точки — `p_target = [x_t, y_t, z_t]ᵀ`.

Вектор просторової нев'язки `Δp` та поточна евклідова відстань `d(t)` визначаються як:

```
Δp = p_target - p(t)                 [вектор напрямку до цілі]
d(t) = √(Δp_x² + Δp_y² + Δp_z²)      [евклідова відстань у 3D]
```

Для запобігання діленню на нуль при підльоті впритул до цілі запроваджується параметр регуляризації `ε = 10⁻⁴ м`:

```
u_target(t) = Δp ÷ max(d(t), ε)      [одиничний вектор напрямку]
```

Нехай вектор поточної колійної швидкості апарата за оцінкою EKF становить `v(t) = [v_x, v_y, v_z]ᵀ`. Миттєва швидкість фізичного наближення до точки визначається як скалярний добуток вектора швидкості на одиничний вектор мети:

```
v_proj(t) = v(t) · u_target(t) = v_x·u_x + v_y·u_y + v_z·u_z  [скалярна проекція швидкості]
```

Знак та амплітуда `v_proj` дають вичерпну картину руху:
* `v_proj > 0` — апарат фізично скорочує дистанцію до цілі.
* `v_proj = 0` — дрон завис на місці або рухається суворо перпендикулярно до лінії шляху.
* `v_proj < 0` — апарат зноситься у протилежний бік (віддаляється від точки).

#### Інтеграл наближення та фільтрація стагнації
Одиничне короткочасне падіння `v_proj` (наприклад, через турбулентність чи маневр обльоту птиці) не повинно скидати поведінку. Сторожовий таймер застосовує комбінований критерій:

1. **Монотонне оновлення рекорду мінімальної дистанції**:
   Змінна `d_min_recorded` ініціалізується початковою дистанцією `d(t_start)`. Якщо поточна дистанція зменшується більш ніж на величину просторового гістерезису `δ_hyst` (типово 0.25–0.50 м):
   
   ```
   d(t) < d_min_recorded - δ_hyst
   ```
   
   значення `d_min_recorded` оновлюється, а таймер останнього прогресу `t_last_progress` скидається на поточний монотонний час `t_now`.

2. **Перевірка вікна стагнації**:
   Якщо протягом ковзного часового вікна `T_stagnation_window` (типово 4.0–8.0 с) умова наближення не виконується:
   
   ```
   t_now - t_last_progress ≥ T_stagnation_window
   ```
   
   супервізор фіксує стан **стагнації руху** (*Stagnation Detected*) та ініціює дострокове переривання операції.

#### Моніторинг збіжності коваріаційної матриці EKF
Рух до точки має сенс лише тоді, коли автопілот довіряє власній оцінці координат. Якщо внаслідок глушіння сигналів GNSS або відмови інерціальних датчиків коваріаційна матриця стану розширюється, політ стає неконтрольованим.

Супервізор безперервно обчислює слід (*trace*) блоку позиційних дисперсій матриці коваріації EKF `P`:

```
σ_pos² = trace(P_pos) = P_xx + P_yy + P_zz  [сумарна просторова невизначеність]
```

Якщо `σ_pos² > σ_max_allowed²` (де `σ_max_allowed` становить 3.0–5.0 м для відкритого простору або 0.8 м для точної посадки), таймаут прогресу анулюється через деградацію оцінки стану (*EKF Divergence*), запобігаючи зіткненню з перешкодами наосліп.

### 3. Енергетичний сторожовий таймер (Dynamic RTL Energy Budget)

Енергетичний сторожовий таймер розраховує граничний час, протягом якого дрон може продовжувати поточну дію без ризику втратити можливість повернутися на базу або безпечний запасний майданчик.

#### Фізика розрахунку енергетичного бюджету повернення
Нехай поточна відстань до точки старту (Home) становить `d_home`. Потужність, необхідна для горизонтального польоту з крейсерською швидкістю `v_cruise`, становить `P_cruise` (Вт).

Швидкість зустрічного вітру вздовж вектора повернення визначається через проекцію вітрової оцінки EKF `w = [w_x, w_y, w_z]ᵀ`:

```
v_wind_head = w · (-u_home)  [зустрічна складова вітру на шляху додому]
```

Ефективна шляхова швидкість повернення:

```
v_return_ground = max(v_cruise - v_wind_head, 1.0)  [швидкість відносно землі, м/с]
```

Час, необхідний для подолання дистанції додому:

```
t_RTL_flight = d_home ÷ v_return_ground  [секунди]
```

Повний енергетичний бюджет повернення `E_RTL` (у Джоулях або Ват-годинах) складається з трьох компонентів:
1. Енергія на горизонтальний політ: `E_horiz = t_RTL_flight · P_cruise`.
2. Енергія на попередній набір безпечної висоти повернення `Δh_climb`:
   
   ```
   E_climb = Δh_climb · (m · g ÷ η_climb)
   ```
   де `η_climb` — електромеханічний коефіцієнт корисної дії гвинтомоторної групи при наборі висоти (типово 0.55–0.65).
3. Енергія на вертикальне зниження та посадку:
   
   ```
   E_land = (h_safe ÷ v_descend) · P_hover
   ```

Повна необхідна енергія повернення з урахуванням нормативного коефіцієнта безпеки `k_safety = 1.20` (20% гарантований резерв):

```
E_required = (E_horiz + E_climb + E_land) · k_safety
```

#### Розрахунок точки неповернення (Point of No Return)
Нехай поточний залишок енергії в батареї становить `E_battery_remaining` (обчислюється кулон-лічильником смарт-батареї як інтеграл струму `∫ U(t)·I(t) dt`).

Залишковий часовий бюджет, який можна виділити на виконання поточної дії зі споживаною потужністю `P_current`:

```
E_free = E_battery_remaining - E_required
T_energy_budget = max(E_free ÷ P_current, 0.0)  [секунди]
```

Якщо `E_free ≤ 0` (тобто `T_energy_budget == 0`), енергетичний сторожовий таймер миттєво обнуляє час очікування будь-якої місійної поведінки, перехоплює керування та ініціює повернення додому.

## Дерево та каскад ескалації помилок (Escalation Ladder)

Спрацювання таймауту не повинно призводити до миттєвого аварійного вимкнення моторів чи панічної посадки в першому ліпшому місці. В інженерії авіоніки діє принцип **пропорційної ескалації** (*Escalation Ladder*): система спершу намагається локально усунути збурення, потім переходить до тактичного відступу, і лише за вичерпання резервів активує стратегічні аварійні протоколи.

```
       ┌─────────────────────────────────────────────────────────────┐
       │             ІЄРАРХІЯ КАСКАДУ ЕСКАЛАЦІЇ ПОВЕДІНКИ            │
       ├─────────────────────────────────────────────────────────────┤
       │ Сходинка 1: Retry & Relaxation (Локальна адаптація)         │
       │   Збільшення радіуса прийняття, зміна ракурсу, підйом       │
       ├─────────────────────────────────────────────────────────────┤
       │ Сходинка 2: Safe Fallback (Тактичний маневр)                │
       │   Пропуск точки (Skip WP), Loiter на висоті, зміна LZ       │
       ├─────────────────────────────────────────────────────────────┤
       │ Сходинка 3А: Emergency RTL (Стратегічний відступ)           │
       │   Прямолінійне повернення на базу за наявності заряду       │
       ├─────────────────────────────────────────────────────────────┤
       │ Сходинка 3Б: Emergency Land (Вимушена керована посадка)     │
       │   Зниження на поточному місці при вичерпанні енергії        │
       ├─────────────────────────────────────────────────────────────┤
       │ Сходинка 4: Flight Termination / Parachute                  │
       │   Аварійне знеструмлення або викид парашута при падінні     │
       └─────────────────────────────────────────────────────────────┘
```

Розглянемо параметри та умови переходу між кожним рівнем каскаду.

### Сходинка 1: Retry з пом'якшенням критеріїв (Relaxation)

Якщо зрив таймауту або зупинка наближення спричинені тимчасовим зовнішнім фактором (порив вітру, відблиск сонця), автопілот виконує обмежену кількість повторних спроб (`N_retries ≤ 2`), тимчасово пом'якшуючи умови переходу:

* **Розширення радіуса прийняття точки**: якщо дрон не може увійти в коло радіусом 1.5 м через турбулентні завихрення біля споруди, поріг `R_acc` збільшується до 4.0 м. Точка вважається успішно пройденою, і місія триває.
* **Зміна висоти та ракурсу огляду камери**: якщо оптична мітка не захоплюється на висоті 6 м, дрон виконує підйом на 10 м (що розширює поле зору камери FOV на 66%) або здійснює поворот за курсом на 90°, виводячи сонце із прямої зони засвічення матриці.
* **Скидання інтегратора регулятора (I-term Reset)**: очищення накопиченої інтегральної помилки швидкості для усунення перерегулювання після сильного пориву вітру.

### Сходинка 2: Safe Fallback (Тактична заміна поведінки)

Якщо після вичерпання ліміту спроб (`retry_count >= max_retries`) мета залишається недосяжною, але апарат має повну керованість і достатній запас батареї, активується запасна дія:

* **Пропуск поточної точки (`Skip Waypoint`)**: якщо проміжна точка фотофіксації недосяжна через локальну перешкоду, навігатор виключає її з черги завдань і спрямовує апарат до наступної точки місії.
* **Зависання в зоні очікування (`Loiter / Hold`)**: безпілотник фіксує позицію на безпечній висоті ешелону (наприклад, 50 м) і транслює на наземний пункт керування аварійний статус MAVLink `STATUSTEXT: "WP 14 unreachable, holding position"`.
* **Перехід на альтернативний майданчик (`Alternate LZ / Rally Point`)**: якщо основне місце посадки заблоковане або не розпізнане, маршрут автоматично перебудовується на заздалегідь запрограмовану резервну точку посадки.

### Сходинка 3: Аварійний відступ або вимушена посадка (Emergency RTL / Land)

Якщо тактичні маневри не розв'язали проблему, або якщо спрацював енергетичний чи сенсорний сторожовий таймер, система приймає безповоротне стратегічне рішення:

* **Emergency RTL (Повернення додому)**: активується, якщо оцінка позиції EKF залишається валідною (`σ_pos² < σ_max²`), а залишок енергії перевищує розраховану вартість повернення `E_battery > E_required`. Дрон піднімається на безпечну висоту повернення, розгортається на базу та летить за найкоротшою прямою траєкторією, ігноруючи решту місійних завдань.
* **Emergency Land (Примусова вертикальна посадка)**: активується, якщо залишку батареї недостатньо для повернення додому (`E_free ≤ 0`) або якщо відмовила супутникова навігація і EKF втратив координати. Апарат стабілізує горизонтальні швидкості в нуль за даними оптичного потоку або інерціальних датчиків і виконує плавне вертикальне зниження зі швидкістю 1.0–1.5 м/с на поточному місці.

Графічну структуру дерева рішень ескалації наведено на схемі:

![Дерево ескалації дій](/root/sys/sys-dron/taimaut-na-kozhnu-povedinku/img/behavior-escalation-ladder.svg)
*Дерево та послідовність переходів у каскаді ескалації: від локального пом'якшення критеріїв до вимушеної аварійної посадки при дефіциті енергії.*

## Реалізація в польотних архітектурах промислового рівня

У сучасних відкритих і комерційних польотних стеках (PX4 Autopilot, ArduPilot, ROS 2 Navigation Stack / Nav2) контроль таймаутів розподіляється між навігаційним менеджером і модулем безпеки.

### Архітектура PX4 Autopilot
У польотному стеку PX4 кожна поведінка місії наслідується від базового класу `MissionBlock` усередині модуля `navigator`. Щокроку навігаційний потік викликає віртуальний метод перевірки умов досягнення мети `is_mission_item_reached()`:

```
[Потік Navigator (50 Гц)]
       │
       ▼
MissionBlock::is_mission_item_reached()
       │
       ├──> 1. hard_timeout_check()    ───> Перевірка hrt_absolute_time()
       ├──> 2. progress_rate_check()   ───> Скалярна проекція швидкості EKF
       └──> 3. energy_budget_check()   ───> Оцінка запасу LiPo через Battery status
```

Якщо перевірка фіксує відсутність прогресу або перевищення ліміту, `Navigator` публікує у шину uORB повідомлення про збій виконання місії, після чого модуль арбітражу `Commander` перемикає головний польотний режим у `NAVIGATION_STATE_AUTO_RTL` або `NAVIGATION_STATE_AUTO_LAND`.

### Архітектура Behavior Trees (BT.CPP / ROS 2 Nav2)
У високорівневих автономних стеках під керуванням ROS 2 навігаційні завдання моделюються деревами поведінки (*Behavior Trees*). Контроль таймаутів та ескалації реалізується через комбінацію спеціалізованих вузлів-декораторів та композитів:

```
                  ┌─────────────────────────────────┐
                  │       RecoveryNode (Каскад)     │
                  └────────────────┬────────────────┘
                                   │
               ┌───────────────────┴───────────────────┐
               ▼                                       ▼
     ┌───────────────────┐                   ┌───────────────────┐
     │ TimeoutDecorator  │                   │  RecoveryAction   │
     │   (T_limit = 30s) │                   │  (Spin / Climb)   │
     ├───────────────────┤                   └───────────────────┘
     │ NavigateToPose    │
     └───────────────────┘
```

* `TimeoutDecorator`: повертає статус `FAILURE`, якщо дочірній вузол `NavigateToPose` не повернув `SUCCESS` протягом заданого інтервалу.
* `RecoveryNode`: при отриманні `FAILURE` від першої гілки запускає відновлювальну дію (наприклад, очищення локальної карти вартості *Costmap Clear* або маневр розвороту), після чого повторює спробу.

### Конфігураційні параметри автопілотів

У польотних контролерах параметри поведінкових таймаутів калібруються інженерами перед вильотом відповідно до типу рами та умов місії:

```
┌──────────────────┬─────────────────┬────────────────────────────────────────┐
│ Параметр PX4     │ Параметр ArduP  │ Інженерний зміст                       │
├──────────────────┼─────────────────┼────────────────────────────────────────┤
│ NAV_ACC_RAD      │ WPNAV_RADIUS    │ Радіус прийняття точки за замовчуванням│
│ NAV_MAX_RAD_REL  │ WPNAV_ACCEL     │ Межа тимчасового розширення радіуса    │
│ MIS_TAKEOFF_ALT  │ TKOFF_ALT       │ Висота безпеки для відмови на зльоті   │
│ COM_POS_FS_DELAY │ FS_OPTIONS      │ Затримка детекції зриву EKF перед RTL  │
│ BAT_EMERGEN_THR  │ BATT_FS_CRT_ACT │ Критичний поріг відсікання батареї     │
│ MPC_LAND_SPEED   │ LAND_SPEED      │ Швидкість керованого зниження (м/с)    │
└──────────────────┴─────────────────┴────────────────────────────────────────┘
```

Емпіричне правило налаштування вікна стагнації `T_stagnation_window`: воно повинно бути не меншим за період максимального прогнозованого пориву вітру (зазвичай 4–6 секунд), але не перевищувати 10% від повного розрахункового часу польоту між сусідніми точками маршруту.

## Практична реалізація оцінки інваріантів поведінки

Нижче наведено робочу реалізацію модуля перевірки інваріантів часу, просторового прогресу та енергетичного бюджету для інтеграції в польотний цикл.

```c
#include <stdint.h>
#include <stdbool.h>
#include <math.h>

#define WATCHDOG_EPSILON 1e-4f

typedef enum {
    EVAL_RESULT_OK = 0,
    EVAL_RESULT_HARD_TIMEOUT,
    EVAL_RESULT_STAGNATION,
    EVAL_RESULT_EKF_DIVERGENCE,
    EVAL_RESULT_ENERGY_CRITICAL
} behavior_eval_result_t;

typedef struct {
    float x;
    float y;
    float z;
} vec3_t;

typedef struct {
    uint64_t hard_limit_us;       /* Жорсткий граничний дедлайн (мкс) */
    uint64_t stagnation_time_us;  /* Вікно фіксації відсутності наближення (мкс) */
    float min_speed_mps;          /* Поріг швидкості наближення (м/с) */
    float max_pos_variance_m2;    /* Гранична дисперсія координат EKF (м²) */
    float cruise_power_w;         /* Крейсерська потужність польоту (Вт) */
    float cruise_speed_mps;       /* Крейсерська швидкість руху (м/с) */
    float energy_margin_j;        /* Незнижуваний резерв енергії для RTL (Дж) */
} behavior_params_t;

typedef struct {
    uint64_t start_time_us;
    uint64_t last_progress_us;
    vec3_t target_pos;
    float min_distance_recorded_m;
    uint8_t retry_count;
    bool is_active;
} behavior_state_t;

static inline float vec3_dist(const vec3_t *a, const vec3_t *b) {
    float dx = a->x - b->x;
    float dy = a->y - b->y;
    float dz = a->z - b->z;
    return sqrtf(dx * dx + dy * dy + dz * dz);
}

/* Оцінка інваріантів поточної поведінки в реальному часі */
behavior_eval_result_t evaluate_behavior_safety(const behavior_params_t *params,
                                               behavior_state_t *state,
                                               uint64_t now_us,
                                               const vec3_t *curr_pos,
                                               const vec3_t *curr_vel,
                                               float ekf_variance_m2,
                                               float remaining_energy_j,
                                               const vec3_t *home_pos) {
    if (!state->is_active) {
        return EVAL_RESULT_OK;
    }

    /* 1. Перевірка жорсткого таймауту за монотонним лічильником */
    if ((now_us - state->start_time_us) >= params->hard_limit_us) {
        return EVAL_RESULT_HARD_TIMEOUT;
    }

    /* 2. Перевірка розбіжності та деградації оцінки фільтра EKF */
    if (ekf_variance_m2 > params->max_pos_variance_m2) {
        return EVAL_RESULT_EKF_DIVERGENCE;
    }

    /* 3. Оцінка енергетичного бюджету повернення додому */
    float dist_home = vec3_dist(curr_pos, home_pos);
    float time_to_home_s = dist_home / fmaxf(params->cruise_speed_mps, 1.0f);
    float energy_needed_for_rtl_j = time_to_home_s * params->cruise_power_w;

    if (remaining_energy_j <= (energy_needed_for_rtl_j + params->energy_margin_j)) {
        return EVAL_RESULT_ENERGY_CRITICAL;
    }

    /* 4. Оцінка просторового наближення до цільової точки */
    float current_dist = vec3_dist(curr_pos, &state->target_pos);

    if (current_dist < (state->min_distance_recorded_m - 0.25f)) {
        state->min_distance_recorded_m = current_dist;
        state->last_progress_us = now_us;
    } else if (current_dist > WATCHDOG_EPSILON) {
        /* Обчислення проекції швидкості на одиничний вектор напрямку */
        float ux = (state->target_pos.x - curr_pos->x) / current_dist;
        float uy = (state->target_pos.y - curr_pos->y) / current_dist;
        float uz = (state->target_pos.z - curr_pos->z) / current_dist;
        float v_proj = curr_vel->x * ux + curr_vel->y * uy + curr_vel->z * uz;

        if (v_proj >= params->min_speed_mps) {
            state->last_progress_us = now_us;
        }
    }

    /* Перевірка тривалості стагнації */
    if ((now_us - state->last_progress_us) >= params->stagnation_time_us) {
        return EVAL_RESULT_STAGNATION;
    }

    return EVAL_RESULT_OK;
}
```

```cpp
#include <chrono>
#include <cmath>
#include <algorithm>

namespace drone::safety {

enum class EvalResult : uint8_t {
    Ok = 0,
    HardTimeout,
    Stagnation,
    EkfDivergence,
    EnergyCritical
};

struct Vector3f {
    float x{0.0f};
    float y{0.0f};
    float z{0.0f};

    [[nodiscard]] constexpr float distance_to(const Vector3f& other) const noexcept {
        const float dx = x - other.x;
        const float dy = y - other.y;
        const float dz = z - other.z;
        return std::sqrt(dx * dx + dy * dy + dz * dz);
    }
};

struct BehaviorParams {
    std::chrono::microseconds hard_limit{std::chrono::seconds(60)};
    std::chrono::microseconds stagnation_time{std::chrono::seconds(6)};
    float min_speed_mps{0.35f};
    float max_pos_variance_m2{3.0f};
    float cruise_power_w{450.0f};
    float cruise_speed_mps{14.0f};
    float energy_margin_j{18000.0f};
};

struct BehaviorState {
    std::chrono::microseconds start_time{0};
    std::chrono::microseconds last_progress{0};
    Vector3f target_pos{};
    float min_distance_recorded_m{1e6f};
    uint8_t retry_count{0};
    bool is_active{false};
};

class BehaviorSafetyEvaluator {
public:
    explicit constexpr BehaviorSafetyEvaluator(const BehaviorParams& params) noexcept
        : params_(params) {}

    [[nodiscard]] EvalResult evaluate(BehaviorState& state,
                                      std::chrono::microseconds now,
                                      const Vector3f& curr_pos,
                                      const Vector3f& curr_vel,
                                      float ekf_variance_m2,
                                      float remaining_energy_j,
                                      const Vector3f& home_pos) const noexcept {
        if (!state.is_active) {
            return EvalResult::Ok;
        }

        // 1. Жорсткий дедлайн за монотонним таймером
        if ((now - state.start_time) >= params_.hard_limit) {
            return EvalResult::HardTimeout;
        }

        // 2. Дисперсія EKF
        if (ekf_variance_m2 > params_.max_pos_variance_m2) {
            return EvalResult::EkfDivergence;
        }

        // 3. Динамічний енергетичний бар'єр повернення
        const float dist_home = curr_pos.distance_to(home_pos);
        const float time_to_home_s = dist_home / std::max(params_.cruise_speed_mps, 1.0f);
        const float energy_needed_for_rtl_j = time_to_home_s * params_.cruise_power_w;

        if (remaining_energy_j <= (energy_needed_for_rtl_j + params_.energy_margin_j)) {
            return EvalResult::EnergyCritical;
        }

        // 4. Кінематичний прогрес наближення
        const float current_dist = curr_pos.distance_to(state.target_pos);

        if (current_dist < (state.min_distance_recorded_m - 0.25f)) {
            state.min_distance_recorded_m = current_dist;
            state.last_progress = now;
        } else if (current_dist > 1e-4f) {
            const float ux = (state.target_pos.x - curr_pos.x) / current_dist;
            const float uy = (state.target_pos.y - curr_pos.y) / current_dist;
            const float uz = (state.target_pos.z - curr_pos.z) / current_dist;
            const float v_proj = curr_vel.x * ux + curr_vel.y * uy + curr_vel.z * uz;

            if (v_proj >= params_.min_speed_mps) {
                state.last_progress = now;
            }
        }

        if ((now - state.last_progress) >= params_.stagnation_time) {
            return EvalResult::Stagnation;
        }

        return EvalResult::Ok;
    }

private:
    BehaviorParams params_;
};

} // namespace drone::safety
```
