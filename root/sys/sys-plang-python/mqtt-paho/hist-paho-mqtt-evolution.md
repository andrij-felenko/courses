# 📜 Еволюція Paho MQTT: від нафтопроводів SCADA до стандарту v2

Протокол MQTT (Message Queuing Telemetry Transport) створювався не для вебу і не для мікросервісних бекендів. Його історія почалася наприкінці 1990-х років у середовищі промислової автоматизації SCADA, де кожен байт каналу зв'язку мав пряму грошову вартість.

## 1. Народження протоколу: нафтопроводи та супутниковий зв'язок (1999)

У 1999 році інженери Енді Стенфорд-Кларк (Andy Stanford-Clark, представник дослідницького центру IBM Hursley) та Арлен Ніппер (Arlen Nipper, компанія Arcom Control Systems, згодом Eurotech) зіткнулися з інженерною проблемою для нафтової корпорації Phillips 66. Необхідно було збирати дані телеметрії з тисяч вимірювальних пунктів на нафтопроводах, розкиданих пустелями та важкодоступними регіонами.

Єдиним доступним каналом зв'язку був супутниковий зв'язок (VSAT) із тарифікацією за кожен переданий байт та високими затримками. Традиційні протоколи промислового опитування (такі як Modbus або опитування через TCP/IP) вимагали безперервного надсилання циклічних запитів «майстер — слейв» (Polling), що призводило до колосальних рахунків за супутниковий трафік і швидкого виснаження акумуляторів на необслуговуваних вузлах.

Стенфорд-Кларк і Ніппер розробили компактний бінарний протокол, що спирався на три фундаментальні ідеї:
1. **Патерн «Публікація — Підписка» (Publish/Subscribe):** усунення постійного опитування; пристрій передає дані лише тоді, коли значення датчика дійсно змінилося (Report by Exception).
2. **Мінімальний заголовок фіксованої довжини:** компактний базовий заголовок розміром усього 2 байти, що дозволяло пакувати телеметрію без надлишкових текстових заголовків (на відміну від протоколу HTTP).
3. **Рівні обслуговування (QoS) та заповіт (Last Will and Testament, LWT):** механізм гарантії доставки через нестабільні канали зв'язку та автоматичне сповіщення системи про раптовий обрив з'єднання з вузлом.

## 2. Відкриття стандарту та заснування Eclipse Paho (2010–2011)

Протягом першого десятиліття MQTT залишався пропрієтарною розробкою IBM і використовувався в корпоративному продукті IBM WebSphere MQ Integrator та компактному брокері RSMB (Really Small Message Broker). 

У 2010 році IBM опублікувала специфікацію MQTT версії 3.1 без роялті, що відкрило шлях до широкого міжнародного визнання. У 2011 році корпорація IBM спільно з Eurotech передали вихідні коди клієнтських бібліотек у фонд Eclipse Foundation, започаткувавши проєкт **Eclipse Paho**. 

Метою проєкту стало створення еталонних, відкритих та високопродуктивних клієнтських реалізацій MQTT для всіх популярних мов програмування: C/C++, Java, Python, JavaScript, Go та Rust. Клієнт для Python (`paho-mqtt`) швидко став де-факто стандартом для наукових експериментів, прототипування IoT на базі Raspberry Pi та побудови промислових шлюзів збору даних.

У 2014 році протокол MQTT версії 3.1.1 був офіційно ратифікований консорціумом OASIS та стандартизований ISO (ISO/IEC 20922:2016).

## 3. MQTT 5.0 та накопичення технічного боргу в Python-клієнті (2019–2023)

У 2019 році консорціум OASIS затвердив стандарт **MQTT 5.0**. Це було наймасштабніше оновлення в історії протоколу, яке перетворило MQTT з простого телеметричного транспорту на повноцінний промисловий стандарт корпоративного рівня.

MQTT 5.0 додав критично важливі можливості:
- **Користувацькі властивості (User Properties):** довільні пари ключ-значення в метаданих пакетів (аналог HTTP-заголовків) для трасування запитів і маршрутизації.
- **Розширені коди причин (Reason Codes):** брокер та клієнт отримали змогу повертати десятки стандартизованих кодів помилок (наприклад, перевищення квоти, відхилення авторизації, непідтримуваний рівень QoS) не лише при підключенні `CONNACK`, а й у відповідях `PUBACK`, `SUBACK`, `DISCONNECT`.
- **Шаблони «Запит — Відповідь» (Response Topic та Correlation Data):** вбудована підтримка двостороннього обміну повідомленнями.

Проте архітектура бібліотеки `paho-mqtt` для Python версії 1.x створювалася в епоху MQTT 3.1. Сигнатури її зворотних викликів були жорстко зафіксовані:

```python
# Застарілий інтерфейс paho-mqtt v1.x
def on_connect(client, userdata, flags, rc):
    # rc приймав лише ціле число від 0 до 5
    pass

def on_disconnect(client, userdata, rc):
    pass
```

Коли розробники спробували додати підтримку MQTT 5.0 у лінійку `paho-mqtt 1.x`, виник конфлікт: старі сигнатури не могли приймати нові об'єкти `Properties` та розширені `ReasonCodes` без порушення зворотної сумісності. Деякі методи отримали перевантажені аргументи, перевірки типів стали крихкими, а спроба відрізнити код повернення 3.1.1 від коду 5.0 вимагала небезпечних умовних розгалужень у клієнтському коді.

## 4. Революція версії 2.0: CallbackAPIVersion (2024)

У лютому 2024 року команда мейнтейнерів Eclipse Paho випустила мажорний реліз **`paho-mqtt 2.0.0`**, який провів рішуче очищення технічного боргу.

Ключовим архітектурним рішенням стало введення переліку `CallbackAPIVersion`. Тепер розробник зобов'язаний явно вказати версію інтерфейсу зворотних викликів під час створення екземпляра клієнта:

```python
from paho.mqtt.client import Client, CallbackAPIVersion

# Новий стандартизований виклик у v2.x
client = Client(CallbackAPIVersion.VERSION2)
```

У режимі `VERSION2`:
1. **Уніфіковано всі сигнатури:** усі колбеки (`on_connect`, `on_disconnect`, `on_publish`, `on_subscribe`, `on_unsubscribe`) отримали чіткий набір параметрів, що обов'язково включає типізований `reason_code` (`ReasonCode`) та `properties` (`Properties | None`).
2. **Типізація кодів помилок:** замість магічних чисел `rc == 0` з'явилися зрозумілі об'єкти статусів з методом `.is_failure` та зрозумілими рядковими назвами (`ReasonCodes.SUCCESS`, `ReasonCodes.NOT_AUTHORIZED`).
3. **Повна сумісність з екосистемою:** новий інтерфейс дозволив однаково надійно будувати як легкі клієнти для версії 3.1.1, так і високонавантажені асинхронні шлюзи стандарту MQTT 5.0.

Ця зміна спричинила тимчасове ламання багатьох старих скриптів, які ініціалізували клієнт без аргументів (`Client()`), проте вона заклала надійний фундамент для розвитку Python у сфері промислового Інтернету речей на наступне десятиліття.
