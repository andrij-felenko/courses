Коли системний адміністратор виконує команду `dnf upgrade`, `firewall-cmd --reload` або ініціалізує новий сервер у хмарі через `cloud-init`, операційна система не звертається до скомпільованих бінарних файлів мовою C. Вона завантажує системний інтерпретатор `/usr/bin/python3`, відкриває десятки модулів зі стандартного каталогу дистрибутива та виконує високорівневі інструкції керування вузлом. У сучасних дистрибутивах Linux (Debian, Ubuntu, Red Hat Enterprise Linux, Fedora, Arch Linux) та середовищі macOS інтерпретатор Python є не просто інструментом розробника, а невіддільним ядром простору користувача (Userland), на якому тримається конфігурація мережі, автентифікація, розгортання оновлень та керування апаратними драйверами.

Втручання в це середовище сторонніми інструментами керування пакунками (передусім командою `sudo pip install`) створює пряму загрозу життєздатності всієї операційної системи. Спроба оновити окрему бібліотеку заради користувацького скрипту здатна зруйнувати граф системних залежностей, затінити критичні модулі несумісними версіями та заблокувати роботу самого пакетного менеджера, позбавивши адміністратора можливості полагодити сервер штатними засобами.

## 1. Системний інтерпретатор як критична інфраструктура ОС

Вибір Python як базової мови системного адміністрування у дистрибутивах Linux був зумовлений потребою замінити розрізнені, складні в супроводі скрипти оболонки POSIX Shell та Perl структурованою мовою з потужною стандартною бібліотекою. Завдяки високій швидкості розробки та виразному синтаксису розробники дистрибутивів переписали ключові службові демони та інтерфейси керування на Python.

У дистрибутивах родини Red Hat (RHEL, Fedora, CentOS Stream, Rocky Linux, AlmaLinux) на Python побудовано фундаментальний інструментарій керування операційною системою:
- **`dnf` (Dandified YUM):** головний менеджер пакунків операційної системи. Він реалізований як набір високорівневих Python-модулів (`dnf`, `libdnf`), які взаємодіють із C-бібліотекою `libsolv` для розв'язання задач сумісності пакунків через алгоритми булевої задовольняваності (SAT-солвери).
- **`firewalld` (`firewall-cmd`):** динамічний демон керування міжмережевим екраном, що транслює високорівневі правила фільтрації пакетів у ядро через інтерфейси `nftables` або `iptables`.
- **`authselect`:** підсистема декларативної конфігурації профілів автентифікації PAM (Pluggable Authentication Modules) та NSS (Name Service Switch).
- **`subscription-manager` та `insights-client`:** клієнтські підсистеми управління корпоративними підписками, ліцензіями та моніторингу вразливостей.
- **`sosreport`:** системна утиліта збору діагностичних даних, конфігурацій та журналів для аналізу збоїв ядра та обладнання.
- **`anaconda`:** графічний та текстовий установник операційної системи, що виконує форматування дисків, конфігурацію LVM/LUKS та розгортання початкового образу системи.

У дистрибутивах сімейства Debian та Ubuntu Python безпосередньо забезпечує життєвий цикл сервера:
- **`cloud-init`:** загальноприйнятий стандарт ініціалізації віртуальних інстансів у хмарних середовищах (AWS, Google Cloud, Azure, OpenStack, Hetzner). Під час першого завантаження операційної системи `cloud-init` парсить метадані провайдера, налаштовує статичні IP-адреси або DHCP, розбиває диски на розділи, створює облікові записи та інжектує публічні ключі SSH. Збій інтерпретатора Python на цій стадії призводить до того, що новостворена віртуальна машина стає повністю недоступною через мережу.
- **`software-properties-common` (`add-apt-repository`):** утиліти верифікації криптографічних GPG-ключів та додавання сторонніх репозиторіїв до списків APT.
- **`ubuntu-drivers`:** автоматизований комплекс виявлення апаратних адаптерів та встановлення бінарних модулів ядра для графічних процесорів Nvidia та Wi-Fi чипсетів.
- **`netplan`:** декларативний рушій конфігурації мережі, чиї парсери структури YAML та генератори конфігурацій для `systemd-networkd` частково реалізовані на базі бібліотек Python.
- **`update-manager` та `apt-listchanges`:** інструменти перевірки оновлень безпеки та інформування системного адміністратора про критичні зміни в поведінці служб.

В операційній системі macOS системний інтерпретатор `/usr/bin/python3` постачається у складі Apple Command Line Developer Tools. Він використовується середовищем Xcode, утилітами автоматизації робочого столу, генераторами проектів та скриптами інсталяції системних плагінів.

```
/usr/bin/python3 (Системний виконуваний файл CPython)
  ├── Red Hat / Fedora : dnf, firewall-cmd, authselect, sosreport, anaconda
  ├── Debian / Ubuntu  : cloud-init, software-properties-common, ubuntu-drivers, netplan
  ├── Arch Linux       : pacman-contrib, mkinitcpio-хуки, reflector (дзеркала)
  └── macOS            : Command Line Developer Tools, автоматизація Xcode
```

Усі ці інструменти починаються зі стандартного рядка Shebang:

```python
#!/usr/bin/python3
```

Коли операційна система виконує файл, ядро через системний виклик `execve` жорстко завантажує саме бінарний файл за шляхом `/usr/bin/python3`. Будь-яка зміна або дестабілізація середовища цього конкретного інтерпретатора автоматично руйнує роботу всього переліченого системного стека.

![Архітектурна роль системного Python у стеку дистрибутива Linux](/root/sys/sys-plang-python/system-python/img/system-python-ecosystem.svg)
*Архітектурний зв'язок між системними службами ОС, інтерпретатором /usr/bin/python3 та базою даних пакетного менеджера.*

## 2. Анатомія каталогів імпорту та стандарт FHS

Стандарт ієрархії файлової системи (Filesystem Hierarchy Standard, FHS) визначає суворе призначення каталогів в операційній системі. Розуміння цих зон відповідальності пояснює, чому дистрибутиви організовують бібліотеки Python саме таким чином:

- **/usr :** містить дані та програми, якими розпоряджається виключно сам дистрибутив. Усі файли в каталозі `/usr` перебувають на обліку в базі даних системного пакетного менеджера (`dpkg`, `rpm`, `pacman`). Жодна стороння програма, скрипт чи інженер не мають права записувати або видаляти файли в `/usr` в обхід пакетного менеджера.
- **/usr/local :** зарезервований для програмного забезпечення, яке системний адміністратор встановлює локально на цьому конкретному вузлі (наприклад, збирає з вихідних кодів через `configure && make install`). Системний менеджер пакунків дистрибутива ніколи не додає, не змінює і не видаляє файли в каталозі `/usr/local`.

### Каталоги дистрибутивів Debian та Ubuntu

В операційних системах Debian та Ubuntu шляхи встановлення модулів CPython модифіковані спеціальним патчем, який розділяє каталог розширень на два рівні:

```
/usr/lib/python3.X/                        ← Стандартна бібліотека CPython (os, sys, math, ssl)
/usr/lib/python3/dist-packages/            ← Системні пакунки, встановлені через APT (dpkg)
/usr/local/lib/python3.X/dist-packages/    ← Локальні пакунки, встановлені адміністратором
```

Мейнтейнери Debian навмисно перейменували стандартний каталог `site-packages` на `dist-packages` для системного рівня. Ця зміна гарантує, що модулі, зібрані під конкретну версію Debian, не перетинаються автоматично зі стандартними каталогами сторонніх установників.

### Каталоги дистрибутивів Fedora, RHEL та Arch Linux

У дистрибутивах сімейства Red Hat та Arch Linux використовується традиційна структура назв, де 64-бітні бінарні бібліотеки та C-розширення відокремлені у каталог `lib64`:

```
/usr/lib64/python3.X/                      ← Стандартна бібліотека CPython та C-розширення
/usr/lib/python3.X/site-packages/          ← Системні пакунки дистрибутива (RPM/Pacman)
/usr/local/lib/python3.X/site-packages/    ← Пакунки локального встановлення адміністратора
```

### Механізм конструювання sys.path та затінення імен

Під час ініціалізації середовища CPython виконує модуль `site.py`, який формує в оперативній пам'яті список пошуку `sys.path`. Послідовність елементів у цьому списку суворо детермінована і задає порядок пошуку файлів під час виконання інструкції `import`:

```
sys.path = [
    '/usr/local/lib/python3.12/dist-packages',  # 1. Локальний каталог адміністратора
    '/usr/lib/python3/dist-packages',          # 2. Системні пакунки дистрибутива (APT/DPKG)
    '/usr/lib/python3.12',                     # 3. Стандартна бібліотека CPython
    '/usr/lib/python3.12/lib-dynload'          # 4. Бінарні скомпільовані модулі C
]
```

Головна небезпека криється в тому, що каталог `/usr/local` розташований **перед** каталогом `/usr/lib`. Якщо модуль з однаковим ім'ям (наприклад, `urllib3`) присутній в обох каталогах, інтерпретатор знайде і завантажить версію з `/usr/local`, повністю проігнорувавши системну версію в `/usr/lib`.

Цей ефект називається **затіненням імен** (Shadowing). Він був задуманий для того, щоб адміністратор міг за потреби замінити системну утиліту власною версією, проте у випадку складних графів залежностей Python затінення призводить до катастрофічних наслідків.

> 🔧 **Навіщо це.**
> Порядок обходу `sys.path` є фундаментальним механізмом CPython. Проте через пріоритет `/usr/local` над `/usr/lib` будь-яке встановлення стороннього пакунка через `sudo pip install` автоматично підміняє модулі для всіх системних служб операційної системи.

## 3. Анатомія руйнування: наслідки sudo pip install

Коли розробник або адміністратор стикається з помилкою `ModuleNotFoundError: No module named 'yaml'` під час виконання власного скрипту, найпростішим кроком здається виконання команди `sudo pip install pyyaml`. Оскільки звичайний користувач не має прав на запис у системні каталоги, використання `sudo` примушує операційну систему виконати інсталяцію від імені суперкористувача `root`.

Інструмент `pip` створювався для розгортання ізольованих застосунків в екосистемі Python Package Index (PyPI). Він не має доступу до баз даних операційної системи і не знає про існування `dpkg` чи `rpm`.

Запуск `sudo pip install` спричиняє комплексне руйнування системного простору:

### 1. Несумісність версій усередині системного графа залежностей

Системні утиліти дистрибутива ретельно тестуються на сумісність із зафіксованими версіями бібліотек. Системний пакетний менеджер (як `dnf` або `apt`) перевіряє цілісність графа через SAT-солвер, який гарантує глобальну несуперечливість усіх компонентів ОС. Натомість установник `pip` перевіряє лише власні залежності для одного конкретного пакету.

Розглянемо класичний приклад збою пакетного менеджера `dnf` або сервісу `cloud-init`:

Операційна система постачає:
- `python3-requests` версії 2.25.0 (знаходиться в `/usr/lib/.../site-packages`)
- `python3-urllib3` версії 1.26.0 (знаходиться в `/usr/lib/.../site-packages`)
- Менеджер `dnf` імпортує `requests`, який всередині викликає методи `urllib3`.

Користувач встановлює нову бібліотеку для роботи зі стороннім API, яка вимагає найсвіжішої версії `requests`:

```bash
sudo pip install requests==2.32.0
```

`pip` завантажує пакунок і записує його в `/usr/local/lib/python3.X/site-packages/requests`. Проте `pip` не оновлює системний `urllib3` або оновлює його частково. Коли після цього адміністратор запускає `dnf upgrade`, виникає такий ланцюг подій:

```
sys.path завантажує:
  /usr/local/.../requests (версія 2.32.0)  ← Завантажено з /usr/local (новіший API)
  /usr/lib/.../urllib3   (версія 1.26.0)  ← Завантажено з /usr/lib (старий API)
```

Новий `requests` очікує наявність внутрішніх класів та винятків, доданих у `urllib3` версії 2.0+, і викликає:

```python
from urllib3.exceptions import SSLError
```

Оскільки в системному каталозі `/usr/lib` встановлена стара версія `urllib3 1.26.0`, де такий символ відсутній або має іншу сигнатуру, інтерпретатор викидає фатальний виняток:

```
ImportError: cannot import name 'HTTPResponse' from 'urllib3.response'
```

Оскільки сам `dnf` є програмою на Python, він падає з трасуванням стека (Traceback). Система втрачає головний інструмент керування пакунками: адміністратор більше не може ані оновити систему, ані перевстановити зламаний пакет штатними засобами.

![Механізм затінення системних бібліотек через пріоритети sys.path](/root/sys/sys-plang-python/system-python/img/path-shadowing-conflict.svg)
*Схема виникнення збою: пріоритет каталогу /usr/local у sys.path перехоплює імпорт і ламає залежності системного пакетного менеджера.*

### 2. Порушення бази цілісності системного менеджера DPKG / RPM

Системний пакетний менеджер веде суворий облік кожного байта, встановленого в системі:
- У Debian/Ubuntu інформація про належність кожного файлу зберігається у файлах списків `/var/lib/dpkg/info/*.list`, а контрольні суми — у файлах `.md5sums`.
- У RHEL/Fedora повний граф зв'язків, версій, розмірів та криптографічних хешів зберігається в реляційній базі даних RPM `/var/lib/rpm/rpmdb.sqlite`.

Коли `pip` встановлює пакунки безпосередньо в `/usr/lib/python3/dist-packages` (як це відбувалося в старіших версіях систем або при використанні небезпечних прапорців), він перезаписує файли прямо поверх системних пакетів. Системний пакетний менеджер не отримує жодних сповіщень про цю модифікацію.

Наслідки:
1. Контрольні суми файлів на диску перестають відповідати записам у базі даних `dpkg`/`rpm`.
2. Під час наступного планового оновлення безпеки `apt upgrade` системний менеджер намагається розпакувати новий `.deb` пакет і виявляє сторонні файли, зупиняючись із фатальною помилкою: `dpkg: error processing archive ... trying to overwrite file, which is also in package...`.
3. Якщо адміністратор спробує видалити системний пакунок через `apt remove python3-requests`, `dpkg` видалить файли з диска, але `pip` вважатиме пакунок наявним через залишені метадані `.dist-info`, переводячи інтерпретатор у розірваний неконсистентний стан.

### 3. Конфлікти ABI бінарних C-розширень та динамічного лінкувальника

Значна частина бібліотек Python містить скомпільовані бінарні розширення мовами C, C++ або Rust (файли зі спільними об'єктами `.so`). Прикладами є `cryptography`, `psycopg2`, `numpy`, `pillow`, `grpcio`, `lxml`.

Системні пакунки дистрибутива компілюються централізовано єдиним тулчейном компілятора GCC/Clang з гарантією двійкової сумісності інтерфейсів (Application Binary Interface, ABI) із спільними бібліотеками системи: `libssl.so.3`, `libcrypto.so.3`, `libffi.so.8`, `glibc 2.38`.

Коли користувач встановлює пакунок через `pip`, інструмент завантажує універсальне попередньо скомпільоване колесо формату `manylinux` із дзеркала PyPI. Для забезпечення переносимості розробники коліс застосовують утиліту `auditwheel`, яка вшиває всередину колеса власні статичні копії або змінені версії бібліотек:

```
Конфлікт символів у віртуальній пам'яті процесу:
  /usr/bin/python3 (динамічно підключив системний /lib64/libssl.so.3)
      ↕  [Конфлікт несумісних структур OpenSSL та символів ABI]
  /usr/local/.../cryptography.so (містить вшиту версію OpenSSL)
      → SEGMENTATION FAULT (SIGSEGV, сигнал ядра 11)
```

Коли інтерпретатор завантажує системний модуль, що використовує системний `libssl.so`, а потім підвантажує стороннє C-розширення з іншою версією OpenSSL, у таблиці глобальних символів динамічного лінкувальника `ld.so` виникає колізія. Результатом є аварійне падіння процесу з сигналом порушення захисту пам'яті (`Segmentation fault`), яке неможливо перехопити жодною мовною конструкцією Python.

### 4. Проблема кешування байткоду та прав доступу (__pycache__)

Під час виконання `sudo pip install` CPython автоматично компілює вихідні файли `.py` у бінарний байткод `.pyc`, розміщуючи їх у каталогах `__pycache__`. Оскільки команда виконувалася з правами `root`, власником створених `.pyc` файлів стає користувач `root:root` з маскою прав доступу `0644`.

Якщо надалі системний демон або користувацька служба запускається від імені непривілейованого системного користувача (наприклад, `www-data`, `nginx` чи `systemd-network`), інтерпретатор не може оновити кешований байткод у разі модифікації файлів. Це призводить або до помилок `PermissionError`, або до несподіваного уповільнення холодного старту через постійну перекомпіляцію вихідного коду в оперативній пам'яті процесу без запису на диск.

### 5. Небезпека встановлення через pip install --user

Часто як «безпечну альтернативу» `sudo pip` пропонували команду `pip install --user`. Вона записує пакунки в домашній каталог користувача:

```
~/.local/lib/python3.X/site-packages/
```

Проте модуль `site.py` за замовчуванням автоматично додає цей каталог на початок списку `sys.path`. Якщо користувач встановлює несумісні версії бібліотек у свій домашній каталог, це ламає всі графічні утиліти робочого столу, які запускаються від імені цього користувача (наприклад, GNOME Shell Extensions, термінал GNOME, графічний центр програм та утиліти керування принтерами). Саме тому сучасні дистрибутиви поширюють дію блокування і на режим `--user`.

Повний історичний опис того, як багаторічні конфлікти між дистриб'юторами Linux та робочою групою PyPA призвели до створення стандарту блокування, викладено у вставці [Історія конфлікту між pip та дистрибутивами: як народився PEP 668](root:sys-plang-python/system-python/hist-pep668-origin.md).

## 4. Захисний бар'єр: стандарт PEP 668 та файл EXTERNALLY-MANAGED

Щоб захистити користувачів від випадкового знищення операційної системи, спільнота Python Packaging Authority (PyPA) спільно з інженерами Red Hat, Canonical та Debian розробила та стандартизувала [PEP 668](https://peps.python.org/pep-0668/) (*«Marking Python base environments as “externally managed”»*).

### Механіка стандарту PEP 668

Стандарт запровадив чітке правило взаємодії: дистрибутив має можливість повідомити стороннім установникам (`pip`, `installer`, `flit`, `hatch`), що базове середовище контролюється зовнішнім системним менеджером пакунків.

Для цього дистрибутив розміщує маркерний конфігураційний файл `EXTERNALLY-MANAGED` у каталозі стандартної бібліотеки інтерпретатора (шлях повертається викликом `sysconfig.get_path('stdlib')` або `platstdlib`):

```
/usr/lib/python3.12/EXTERNALLY-MANAGED
```

Коли користувач виконує команду `pip install` або `pip uninstall`, клієнт `pip` (починаючи з версії 23.0) виконує алгоритм перевірки:
1. Перевіряє, чи запущено процес усередині віртуального середовища (`sys.prefix != sys.base_prefix`). Якщо так — операція дозволена без обмежень.
2. Якщо середовище базове (системне) — перевіряє наявність файлу `EXTERNALLY-MANAGED`.
3. Якщо файл знайдено — `pip` миттєво припиняє виконання, не робить жодних мережевих запитів і повертає статус помилки `externally-managed-environment` з детальним поясненням від мейнтейнерів дистрибутива.

```
$ pip install requests
error: externally-managed-environment

× This environment is externally managed
╰─> To install Python packages on this system, use apt install
    python3-xyz, where xyz is the package you are trying to
    install.
    
    If you wish to install a non-Debian-packaged Python package,
    create a virtual environment using python3 -m venv path/to/venv.
    Then use path/to/venv/bin/python and path/to/venv/bin/pip.
```

![Алгоритм перевірки PEP 668 під час запуску pip install](/root/sys/sys-plang-python/system-python/img/pep668-decision-flow.svg)
*Логіка прийняття рішень інструментом pip під час виявлення маркера EXTERNALLY-MANAGED.*

Повний формат файлу `EXTERNALLY-MANAGED`, синтаксичні правила секцій INI та приклади конфігурацій для різних дистрибутивів описано у вставці [Специфікація EXTERNALLY-MANAGED: маркер зовнішнього керування оточенням](root:sys-plang-python/system-python/api-pep668-spec.md).

### Прапорець --break-system-packages та його межі

PEP 668 передбачає можливість примусового обходу захисту для автоматизованих сценаріїв (наприклад, збирання тимчасових Docker-образів, де в контейнері працює єдиний ізольований процес):

```bash
pip install --break-system-packages requests
```

Також захист можна вимкнути через змінну середовища:

```bash
export PIP_BREAK_SYSTEM_PACKAGES=1
```

> [!CAUTION]
> Використання прапорця `--break-system-packages` на робочих комп'ютерах або виробничих серверах повертає всі описані ризики руйнування системи. Його легітимне використання обмежене виключно одноразовими OCI-контейнерами (Docker/Podman).

## 5. Чотири лінії оборони: моделі безпечної ізоляції

Відмова від модифікації системного Python є обов'язковим стандартом інженерної культури. Для розробки та запуску застосунків застосовують чотири рівні ізоляції.

![Чотири архітектурні моделі ізоляції середовищ Python](/root/sys/sys-plang-python/system-python/img/isolation-architectures.svg)
*Порівняння чотирьох рівнів ізоляції програмного забезпечення на базі Python.*

### 1. Віртуальні середовища (модуль venv)

Стандартний модуль `venv` створює автономне дерево каталогів, що містить власні бінарні файли, налаштування та ізольований каталог `site-packages`:

```bash
# Створення ізольованого середовища проєкту
python3 -m venv .venv

# Активація в поточній сесії оболонки
source .venv/bin/activate

# Безпечне встановлення будь-яких бібліотек
pip install requests fastapi uvicorn
```

Внутрішня механіка `venv`:
- Каталог `.venv/bin/python3` є символічним посиланням на системний інтерпретатор `/usr/bin/python3`.
- У корені середовища створюється файл `pyvenv.cfg`, який містить рядок `home = /usr/bin`.
- Під час старту CPython перевіряє каталог запуску. Знайшовши `pyvenv.cfg`, інтерпретатор встановлює `sys.prefix = "/шлях/до/.venv"`, залишаючи `sys.base_prefix = "/usr"`.
- Список `sys.path` перенаправляється в каталог `.venv/lib/pythonX.Y/site-packages`. Системні пакунки дистрибутива стають невидимими, а маркер `EXTERNALLY-MANAGED` ігнорується.

### 2. [Ізоляція утиліт через pipx](root:sys-plang-python/pipx-cli-isolation)

Для запуску глобальних CLI-інструментів, написаних на Python (`ansible`, `black`, `flake8`, `poetry`, `yt-dlp`, `cookiecutter`, `httpie`), використовується менеджер `pipx` ([детальний розбір у статті про pipx](root:sys-plang-python/pipx-cli-isolation)):

```bash
# Встановлення ізольованої утиліти
pipx install ansible

# Виклик команди з будь-якого каталогу
ansible --version
```

`pipx` автоматизує керування середовищами:
1. Створює для кожної утиліти окреме віртуальне середовище в каталозі `~/.local/pipx/venvs/<tool-name>/`.
2. Встановлює в це середовище саму програму та всі її залежності.
3. Створює символічні посилання на виконувані файли програми в загальнодоступному каталозі `~/.local/bin/`.
4. Забезпечує повну ізоляцію: оновлення версії `ansible` або `black` не впливає на інші утиліти та операційну систему.

### 3. Автономні менеджери інтерпретаторів (uv / pyenv)

Коли проєкту потрібна інша версія Python, ніж та, що встановлена в дистрибутиві (наприклад, дистрибутив постачає Python 3.10, а розробнику потрібен Python 3.12 чи експериментальний 3.13), системний інтерпретатор залишають незмінним.

Сучасний високошвидкісний інструмент `uv` (написаний на Rust) або класичний `pyenv` завантажують та розгортають автономні бінарні збірки CPython у домашній каталог користувача:

```bash
# Створення venv з автоматичним завантаженням потрібної версії Python через uv
uv venv --python 3.12
source .venv/bin/activate
uv pip install pydantic
```

Усі файли інтерпретатора зберігаються в каталозі `~/.local/share/uv/python/` або `~/.pyenv/versions/`, не маючи жодного відношення до системного `/usr/bin/python3`.

### 4. Контейнеризація (Docker / Podman / Distrobox)

Для серверних сервісів та виробничих систем стандартом є запуск у середовищі OCI-контейнерів:

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "main.py"]
```

Для інтерактивної розробки на Linux робочих станціях популярність здобули інструменти `distrobox` та `toolbox`. Вони дозволяють створити всередині робочого столу повноцінний контейнер із будь-яким дистрибутивом Linux (наприклад, Arch Linux або Ubuntu), змонтувати домашній каталог користувача та вільно використовувати `sudo pip install` чи експериментальні компілятори всередині контейнера без жодного ризику для хостової операційної системи.

У сучасних незмінних операційних системах (Immutable OS, таких як Fedora Silverblue, CoreOS, openSUSE MicroOS) кореневий каталог `/usr` змонтовано в режимі лише для читання (`ro`). У такому середовищі прямий запуск `sudo pip install` фізично завершується помилкою ядра `EROFS: Read-only file system`, що робить контейнеризацію єдиним штатним шляхом виконання розробницьких завдань.

### Порівняльна характеристика моделей ізоляції

| Критерій | Системний Python (APT/DNF) | Віртуальне середовище (venv) | Менеджер утиліт (pipx) | Менеджер рантаймів (uv/pyenv) | OCI-контейнер (Docker) |
|---|---|---|---|---|---|
| **Призначення** | Служби операційної системи | Розробка конкретного проєкту | Запуск глобальних CLI-утиліт | Робота з різними версіями мови | Продакшн-доставка сервісів |
| **Місце розміщення** | `/usr/lib/...` | `./.venv/lib/...` | `~/.local/pipx/venvs/...` | `~/.local/share/uv/...` | Ізольований шар rootfs |
| **Ризик для ОС** | 🔴 Критичний при модифікації | 🟢 Нульовий | 🟢 Нульовий | 🟢 Нульовий | 🟢 Повна ізоляція хоста |
| **Витрати пам'яті** | 0 MB (спільна пам'ять) | ~15–50 MB на venv | ~20–60 MB на утиліту | ~100 MB на інтерпретатор | ~50–200 MB на контейнер |
| **Керування версією** | Жорстко зафіксована ОС | Версія базового Python | Версія за замовчуванням | Будь-яка версія за запитом | Будь-яка версія в образі |

## 6. Діагностика та аудит стану системного оточення

Для забезпечення стабільності серверної інфраструктури системні інженери застосовують регулярний аудит системного простору Python.

### Перевірка цілісності через debsums та RPM

У дистрибутивах Debian та Ubuntu цілісність усіх встановлених файлів Python перевіряється утилітою `debsums`:

```bash
# Перевірка контрольних сум усіх встановлених пакетів python3
sudo debsums -c $(dpkg -l 'python3*' | awk '/^ii/ {print $2}')
```

У дистрибутивах Red Hat та Fedora аудит здійснюється засобами RPM:

```bash
# Перевірка контрольних сум, розмірів та атрибутів системних пакунків
rpm -V $(rpm -qa | grep -E '^python3-')
```

Якщо утиліти повідомляють про змінені файли, це свідчить про сторонній перезапис системних модулів.

### Простеження імпорту через системні виклики

Якщо системна служба поводиться нестабільно, адміністратор може відстежити, звідки саме інтерпретатор завантажує модулі, за допомогою утиліти трасування системних викликів `strace`:

```bash
# Трасування системних викликів openat та stat під час запуску утиліти
strace -f -e trace=openat,newfstatat dnf check-update 2>&1 | grep -E '(site-packages|dist-packages)'
```

У виводі команди чітко видно кожну спробу відкриття файлів `.py` та `.so`. Якщо серед перших рядків з'являються шляхи з `/usr/local/`, це підтверджує факт перехоплення системних залежностей локальними файлами.

### Виявлення затінених модулів у /usr/local

Щоб виявити пакунки, які перехоплюють системні виклики через каталог вищого пріоритету, достатньо перевірити вміст каталогів локального встановлення:

```bash
ls -la /usr/local/lib/python3.*/dist-packages/
ls -la /usr/local/lib/python3.*/site-packages/
```

Якщо в цьому каталозі виявлено пакунки, які дублюють системні модулі (`requests`, `urllib3`, `yaml`, `six`, `certifi`), їх слід вилучити або перенести в ізольовані віртуальні середовища.

Повнофункціональний інструмент автоматизованої діагностики та пошуку конфліктів мовами Python, C та C++ наведено у вставці [Низькорівневий аудит системного Python та діагностика конфліктів середовища](root:sys-plang-python/system-python/proj-env-auditor.md).

## 7. Термінологічний підсумок та етимологія

Усі розглянуті механізми захисту спираються на фундаментальні поняття системного програмування:

- **Інтерпретатор** (від латинського *interpretator* — тлумач, посередник, роз'яснювач, від дієслова *interpretari*) — програма, яка безпосередньо виконує інструкції вихідного коду або проміжного байткоду без попередньої повної трансляції у машинний код процесора.
- **Дистрибутив** (від латинського *distributio* — поділ, розподіл, класифікація, від дієслова *distribuere*) — цілісний комплект операційної системи, що містить ядро, системні бібліотеки, базові утиліти простору користувача та пакетний менеджер.
- **Ізоляція** (від латинського *insula* — острів, через італійське *isolato* — відокремлений, острівний) — метод організації обчислювального процесу, за якого ресурси, файли та адресний простір однієї програми логічно або фізично відокремлені від інших компонентів системи.
- **Конфлікт** (від латинського *conflictus* — зіткнення, протиборство, сутичка, від дієслова *confligere*) — стан обчислювальної системи, за якого два або більше компонентів висувають взаємовиключні вимоги до версій спільних ресурсів, глобальних символів або динамічних бібліотек.
- **Оточення / Середовище** (від праслов'янського *середъ* — середина, простір довкола / латинського *ambiens* — те, що оточує) — сукупність системних змінних, каталогів пошуку файлів, спільних бібліотек та конфігурацій, у контексті яких виконується процес.
- **Пакет / Пакунок** (від французького *paquet* — клунок, зв'язка, згорток) — структурований архівний файл, який містить скомпільовані бінарні файли чи скрипти програми разом із метаданими про її версію, контрольні суми та перелік обов'язкових залежностей.
- **Затінення / Перекриття** (від англійського *shadowing* — кидання тіні) — ефект у підсистемах пошуку та розв'язання імен, за якого елемент із вищим пріоритетом у ланцюгу пошуку унеможливлює доступ до однойменного елемента з нижчим пріоритетом.
- **Символічне посилання** (від грецького *symbolon* — умовний знак, прикмета, ознака) — спеціальний тип файлу у файловій системі POSIX, який містить текстовий шлях до іншого цільового файлу або каталогу.
