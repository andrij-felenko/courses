# 📋 Специфікація EXTERNALLY-MANAGED: маркер зовнішнього керування оточенням

Специфікація [PEP 668](https://peps.python.org/pep-0668/) визначає стандартний протокол взаємодії між постачальниками операційних систем (або системних менеджерів пакунків) та інструментами встановлення пакунків Python (`pip`, `build`, `installer`, `flit`, `hatch`, `uv`, `poetry`, `pdm`). Вона дозволяє дистрибутиву безпечно заблокувати несанкціоновану модифікацію системного каталогу `site-packages` та спрямувати користувача до рекомендованих інструментів ізоляції.

## 1. Розташування та виявлення файлу маркера

Інструмент встановлення виконує перевірку наявності файлу `EXTERNALLY-MANAGED` під час кожної спроби інсталяції або видалення пакунків, якщо цільове середовище **не є** активним віртуальним середовищем (`venv` або `virtualenv`).

Алгоритм виявлення маркерного файлу складається з кількох послідовних кроків перевірки конфігурації платформи:

1. **Опитування шляхів стандартної бібліотеки:**
   Клієнт звертається до стандартного модуля `sysconfig` для отримання двох ключових шляхів файлової системи:
   - Каталог стандартної платформонезалежної бібліотеки: `sysconfig.get_path('stdlib')`.
   - Каталог платформозалежних скомпільованих C-розширень: `sysconfig.get_path('platstdlib')`.

2. **Формування кандидатів шляхів:**
   У кожному із знайдених каталогів формується шлях до файлу:
   - `os.path.join(stdlib, "EXTERNALLY-MANAGED")`
   - `os.path.join(platstdlib, "EXTERNALLY-MANAGED")`

3. **Перевірка фізичної наявності та розіменування посилань:**
   Якщо хоча б один із цих файлів існує на файловій системі (включно із символічними посиланнями, які розв'язуються системним викликом `stat`) та доступний для зчитування поточним процесом, інтерпретатор класифікується як **зовнішньо керований** (Externally Managed Environment).

4. **Обробка мережевих та контейнерних файлових систем:**
   Якщо файлова система змонтована в режимі лише для читання (Read-Only Rootfs) або використовує шар перекриття (OverlayFS), алгоритм перевірки не намагається створювати тимчасові файли для тесту запису. Наявності файлу на рівні читання достатньо для спрацьовування захисту.

### Типові фізичні шляхи в операційних системах

У різних дистрибутивах Linux та середовищах POSIX розташування стандартної бібліотеки відрізняється через архітектурні особливості компонування каталогів:

| Операційна система / Менеджер | Абсолютний шлях до файлу EXTERNALLY-MANAGED | Примітки архітектури |
|---|---|---|
| **Debian 12+ (Bookworm/Trixie)** | `/usr/lib/python3.11/EXTERNALLY-MANAGED` | Встановлюється пакетом `python3.11-minimal` |
| **Ubuntu 23.04+ / 24.04 LTS** | `/usr/lib/python3.12/EXTERNALLY-MANAGED` | Встановлюється пакетом `python3.12-minimal` |
| **Fedora 38+ / RHEL 10** | `/usr/lib64/python3.12/EXTERNALLY-MANAGED` | Розділення 64-бітних бібліотек у `/usr/lib64` |
| **Arch Linux** | `/usr/lib/python3.12/EXTERNALLY-MANAGED` | Постачається у складі основного пакунка `python` |
| **Alpine Linux 3.18+** | `/usr/lib/python3.12/EXTERNALLY-MANAGED` | Базується на `musl libc`, пакунок `python3` |
| **macOS (Homebrew Apple Silicon)** | `/opt/homebrew/lib/python3.12/EXTERNALLY-MANAGED` | Власна ієрархія Homebrew під `/opt/homebrew` |
| **macOS (Homebrew Intel x86_64)** | `/usr/local/lib/python3.12/EXTERNALLY-MANAGED` | Традиційна ієрархія під `/usr/local` |

## 2. Формат, синтаксис та граматика файлу

Файл `EXTERNALLY-MANAGED` відповідає базовому синтаксису конфігураційних файлів INI, який обробляється стандартним парсером `configparser.RawConfigParser`.

```ini
[externally-managed]
Error = Текст повідомлення про помилку, який буде показано користувачеві.
        Повідомлення може бути багаторядковим із відступами на початку
        наступних рядків за стандартом RFC 822.
```

### Специфікація секцій та параметрів

Згідно зі стандартом PEP 668, файл конфігурації повинен задовольняти такі правила:

- **Назва секції:** Обов'язкова секція `[externally-managed]`. Регістр символів назви секції є нечутливим у більшості реалізацій, але стандарт вимагає запису виключно в нижньому регістрі.
- **Параметр `Error` / `error`:** Опціональне текстове поле. Містить зрозумілу для людини інструкцію, складену мейнтейнерами дистрибутива, про те, як правильно встановити або розгорнути потрібне програмне забезпечення.
- **Коментарі:** Рядки, що починаються із символів `#` або `;`, трактуються як коментарі та ігноруються парсером.
- **Кодування:** Файл повинен бути збережений у кодуванні UTF-8 без мітки порядку байтів (BOM).

### Граматичні правила парсингу для клієнтських утиліт

Клієнтські інструменти встановлення реалізують сувору логіку інтерпретації вмісту:

1. **Файл існує, але порожній (0 байтів):** Якщо файл `EXTERNALLY-MANAGED` присутній на диску, але має нульовий розмір або містить лише коментарі, клієнт **зобов'язаний заблокувати** встановлення, використавши вбудований шаблон повідомлення про помилку за замовчуванням.
2. **Секція `[externally-managed]` відсутня:** Якщо файл містить інші секції, але не містить `[externally-managed]`, це вважається дійсним маркером блокування зі стандартним текстом помилки.
3. **Багаторядкові значення:** Якщо параметр `Error` займає кілька рядків, усі наступні рядки повинні мати відступ щонайменше в один пробіл або символ табуляції (стандарт продовження рядків RFC 822 / MIME).
4. **Обрізання пробілів:** Клієнтський інструмент зобов'язаний виконати операцію `strip()` для значення повідомлення, вилучивши початкові та кінцеві порожні рядки, проте зберігши внутрішню структуру абзаців та відступів.
5. **Захист від невалідного кодування:** Якщо файл містить некоректні байти UTF-8, клієнт не повинен аварійно падати з винятком `UnicodeDecodeError`. Натомість установник перемикається на вбудоване системне повідомлення про помилку, забезпечуючи блокування навіть у пошкодженому середовищі.

## 3. Матриця поведінки інструментів та прапорців CLI

Специфікація PEP 668 поширюється на всі операції, які здатні модифікувати дерево файлів стандартного інтерпретатора.

### Поведінка pip з різними режимами встановлення

| Команда або прапорець | Вплив маркера EXTERNALLY-MANAGED | Пояснення поведінки |
|---|---|---|
| `pip install <pkg>` | 🔴 **Блокується** | Спроба запису в системний `site-packages` заборонена. |
| `pip install --user <pkg>` | 🔴 **Блокується** | За замовчуванням блокується в більшості дистрибутивів, оскільки каталог користувача `~/.local/lib/pythonX.Y/site-packages` також затіняє системні пакунки в `sys.path`. |
| `pip install --target <dir> <pkg>` | 🟢 **Дозволено** | Запис відбувається в довільний користувацький каталог `<dir>`, який не впливає на системний інтерпретатор. |
| `pip install --prefix <dir> <pkg>` | 🟢 **Дозволено** | Пакунки розгортаються в окреме дерево каталогів за вказаним префіксом. |
| `pip install --break-system-packages <pkg>` | ⚠️ **Дозволено з ризиком** | Примусове ігнорування маркера та запис у системне середовище. |
| `pip uninstall <pkg>` | 🔴 **Блокується** | Заборона видалення файлів, які можуть належати системному пакетному менеджеру. |

### Поведінка під час створення віртуальних середовищ

Коли інструменти створення віртуальних середовищ (`python3 -m venv`, `virtualenv`, `uv venv`) розгортають новий префікс:
- Вони копіюють або лінкують системний бінарний файл `python3`.
- Вони **не копіюють** файл `EXTERNALLY-MANAGED` у каталог новоствореного середовища.
- Створюється файл `pyvenv.cfg`, який сигналізує інструментам `pip`, що нове оточення є автономним і в ньому дозволені будь-які операції встановлення пакунків.

### Змінні середовища та конфігураційні файли

Для автоматизованих конвеєрів неперервної інтеграції (CI/CD) та збирання контейнерів стандарт дозволяє відключати перевірку через змінні середовища:

```bash
# Тимчасове вимкнення блокування для поточної команди або сесії
export PIP_BREAK_SYSTEM_PACKAGES=1
pip install requests
```

У конфігураційних файлах `pip` (`/etc/pip.conf`, `/etc/xdg/pip/pip.conf` або `~/.config/pip/pip.conf`):

```ini
[global]
break-system-packages = true
```

## 4. Реальні тексти конфігурацій у провідних дистрибутивах

Дистрибутиви використовують поле `Error` для надання точних команд під свій пакетний менеджер:

### Debian 12 / Ubuntu 24.04 LTS

```ini
[externally-managed]
Error=To install Python packages on this system, use the system package manager:
    apt install python3-xyz

    where xyz is the package you are trying to install.

    If you wish to install a non-Debian-packaged Python application,
    it may be easiest to use pipx:
    apt install pipx
    pipx install xyz

    If you wish to install a non-Debian-packaged Python package,
    create a virtual environment using python3 -m venv path/to/venv.
    Then use path/to/venv/bin/python and path/to/venv/bin/pip. Make
    sure you have the python3-full package installed.

    For more information visit http://loca.host/pep-668
```

### Fedora Linux / Red Hat Enterprise Linux

```ini
[externally-managed]
Error=This system-provided Python interpreter is managed by the system package manager (dnf).

    To install Python packages system-wide, use:
    sudo dnf install python3-xyz

    To run standalone applications in isolated environments, consider using pipx:
    sudo dnf install pipx
    pipx install xyz

    To develop Python applications, create a virtual environment:
    python3 -m venv .venv
    source .venv/bin/activate
    pip install xyz
```

### Alpine Linux

```ini
[externally-managed]
Error=This environment is externally managed by apk.

    To install packages system-wide, use:
    apk add py3-xyz

    If the package is not available in the Alpine repositories,
    create a virtual environment:
    python3 -m venv .venv
    source .venv/bin/activate
    pip install xyz
```

### Рекомендації для мейнтейнерів власних дистрибутивів

Якщо організація збирає власний корпоративний дистрибутив Linux або образ базової операційної системи (наприклад, на базі Yocto Project або Buildroot):
1. Файл `EXTERNALLY-MANAGED` повинен входити до складу базового кореневого пакета CPython.
2. Повідомлення про помилку повинно чітко вказувати шлях до внутрішнього сховища пакунків або корпоративного порталу документації.
3. Не рекомендується видаляти маркерний файл з метою полегшення роботи розробників — правильною практикою є попереднє встановлення `pipx` та модуля `python3-venv`.

## 5. Статуси завершення процесу та коди помилок

Коли інструмент виявляє маркер `EXTERNALLY-MANAGED` і операція переривається:
- **Код завершення процесу (Exit Code):** завжди повертається значення `1`.
- **Потік виводу:** Повідомлення про помилку записується виключно в стандартний потік помилок `stderr`.
- **Ідентифікатор винятку:** У системних журналах та JSON-виводах діагностики фіксується помилка `externally-managed-environment`.

Це дозволяє скриптам автоматизації та інструментам моніторингу однозначно розрізняти помилку блокування системного середовища від мережевих помилок чи збоїв компіляції скомпільованих C-розширень.
