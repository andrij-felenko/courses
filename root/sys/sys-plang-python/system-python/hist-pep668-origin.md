# 📜 Історія конфлікту між pip та дистрибутивами: як народився PEP 668

Протягом майже п'ятнадцяти років у світі Unix-подібних операційних систем тривало протистояння між двома несумісними філософіями керування програмним забезпеченням. З одного боку стояли мейнтейнери дистрибутивів Linux (Debian, Red Hat, Ubuntu, Arch), які розглядали файлову систему `/usr` як цілісну базу даних, контрольовану виключно системним пакетним менеджером (`dpkg`, `rpm`, `pacman`). З іншого боку розвивалася екосистема Python Package Index (PyPI) та інструмент `pip`, розраховані на модель безперервної доставки, де розробник має право встановити найсвіжішу версію будь-якої бібліотеки однією командою.

Зіткнення цих підходів щодня генерувало сотні звітів про фатальні збої операційних систем, утворюючи хронічну точку напруги між спільнотою дистриб'юторів та робочою групою пакування Python (PyPA).

## 1. Спадщина distutils та винахід dist-packages

На початку 2000-х років стандартний модуль `distutils` встановлював усі сторонні пакунки в єдиний каталог `/usr/lib/pythonX.Y/site-packages`. Коли адміністратор сервера запускав команду `python setup.py install` або ранні версії `easy_install` з правами суперкористувача `root`, файли записувалися безпосередньо в системну ієрархію.

Мейнтейнери дистрибутива Debian першими усвідомили масштаб загрози. Системні пакунки Debian (як-от `python-support` чи пізніше `python3-apt`) встановлювалися в той самий каталог. Якщо користувач вручну ставив свіжішу версію бібліотеки, вона перезаписувала файли, за які відповідав `dpkg`. Коли згодом `apt-get upgrade` намагався оновити системний пакунок, виникав конфлікт контрольних сум або розірвані залежності.

У 2009 році розробники Debian (зокрема Маттіас Клозе) створили локальний патч для CPython, який розділив каталог встановлення на два рівні:
1. `/usr/lib/python3/dist-packages` — призначений **виключно** для пакунків, які постачаються через системні `.deb` архіви під контролем `dpkg`.
2. `/usr/local/lib/python3.X/dist-packages` — виділений для сторонніх модулів, які користувач встановлює самостійно.

CPython у Debian був модифікований так, що стандартний шлях `site-packages` вилучався із `sys.path`, а замість нього додавалися обидва каталоги `dist-packages`. Це створило тимчасову ілюзію безпеки, проте заклало ще глибшу проблему: затінення імен (Shadowing). Оскільки каталог `/usr/local` мав вищий пріоритет у списку пошуку `sys.path`, будь-який пакунок із `/usr/local` непомітно перехоплював виклики системних утиліт.

## 2. Ера pip та епідемія звітів про поламані системи

Поява інструмента `pip` (створеного Ієном Бікінгом у 2008 році як `pyinstall`) кардинально змінила культуру розробки. Завдяки інтуїтивному інтерфейсу та автоматичному розв'язанню залежностей `pip` став де-факто стандартом. Тисячі посібників і документацій до бібліотек рекомендували розпочинати роботу з інструкції:

```bash
sudo pip install <package-name>
```

Для користувача ця команда виглядала природно: якщо бракує прав на запис у системні каталоги, слід використати `sudo`. Проте `pip` не знав нічого про системні зв'язки операційної системи. Він завантажував колесо чи вихідний код і агресивно перезаписував або затіняв критичні бібліотеки: `urllib3`, `requests`, `cryptography`, `six`, `pyyaml`, `setuptools`.

Наслідки виявилися катастрофічними:
- У дистрибутивах Fedora та RHEL оновлення `requests` або `urllib3` ламало менеджер пакунків `dnf` та утиліту керування брандмауером `firewall-cmd`. Адміністратор більше не міг встановити жодного пакунка, щоб полагодити систему.
- В Ubuntu та Debian оновлення бібліотеки `cryptography` порушувало роботу служби ініціалізації хмарних інстансів `cloud-init` та інструмента `software-properties-common`. Сервери після перезавантаження втрачали мережу або доступ за SSH-ключами.
- У баг-трекері Debian з'явився відомий звіт [#820987](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=820987) («pip should not overwrite packages managed by dpkg»), який обговорювався роками без узгодженого технічного рішення.

Спроби дистриб'юторів блокувати `pip` локальними патчами призводили лише до обурення користувачів. Якщо дистрибутив відключав `pip` за замовчуванням або видаляв його із базового образу, користувачі завантажували скрипт `get-pip.py` і виконували його з `sudo`, обходячи всі системні запобіжники.

## 3. Дві правди: конфлікт інтересів та глухий кут

Конфлікт загострився через принципову різницю в цілях двох груп інженерів:

Мейнтейнери дистрибутивів аргументували свою позицію вимогами надійності:
- Операційна система — це монолітний механізм, де сотні системних скриптів залежать від конкретних, суворо протестованих версій бібліотек.
- Пакунки ОС збираються єдиним тулчейном із гарантією стабільності двійкового інтерфейсу (ABI) та спільними версіями C-бібліотек (`libssl`, `libxml2`, `glibc`).
- Пакетний менеджер повинен мати абсолютну монополію на файли в `/usr` та `/usr/local`, щоб гарантувати транзакційність оновлень і можливість аудиту системи.

Розробники PyPA та інструмента `pip` (зокрема Дональд Стаффт, Пол Мур, Прадюн Гедам) захищали інтереси розробників прикладного ПЗ:
- Python — це передусім мова програмування для створення застосунків, а не лише внутрішній скриптовий інструмент Linux.
- Розробники потребують нових функцій бібліотек негайно, а не чекають два роки на черговий стабільний реліз Debian чи RHEL.
- Якщо операційна система використовує Python для власних утиліт, вона повинна самостійно ізолювати свої скрипти (наприклад, у приватні префікси), а не забороняти розробнику використовувати мову.
- `pip` не повинен містити специфічної логіки для десятків різних менеджерів (`apt`, `rpm`, `pacman`, `zypper`, `apk`, `brew`), оскільки це зробить код непридатним для супроводу.

## 4. Консенсус: розробка та прийняття PEP 668

Глухий кут тривав до 2021 року, коли інженер Red Hat і член Python Security Response Team Баррі Ворсоу (Barry Warsaw), разом із Прадюном Гедамом (Pradyun Gedam) та Дональдом Стаффтом (Donald Stufft), запропонували формальний компроміс у вигляді [PEP 668](https://peps.python.org/pep-0668/) під назвою *«Marking Python base environments as “externally managed”»*.

Ідея стандарту полягала в мінімалізмі та чіткому розділенні обов'язків:
1. **Інструменти встановлення (`pip`, `installer`, `flit`, `hatch`) залишаються нейтральними.** Вони не перевіряють тип дистрибутива і не звертаються до баз даних `dpkg` чи `rpm`.
2. **Дистрибутив явно декларує статус оточення.** Якщо дистрибутив бажає захистити свій системний інтерпретатор, він кладе в каталог стандартної бібліотеки маркерний конфігураційний файл `EXTERNALLY-MANAGED`.
3. **Клієнт поважає маркер і зупиняє операцію.** Виявивши файл `EXTERNALLY-MANAGED`, `pip` відмовляється записувати пакунки в це оточення і виводить користувачеві текст помилки, складений авторами дистрибутива (із посиланням на правильні практики: `apt install`, `venv` або `pipx`).
4. **Аварійний клапан залишається за користувачем.** Якщо адміністратор повністю усвідомлює наслідки (наприклад, під час збирання одноразового Docker-образу), він може використати прапорець із промовистою назвою `--break-system-packages`.

## 5. Впровадження в екосистему

PEP 668 був офіційно прийнятий у червні 2022 року. Підтримка перевірки маркера з'явилася в `pip 23.0` (січень 2023 року).

Першим великим дистрибутивом, який увімкнув захист за замовчуванням, став **Debian 12 (Bookworm)**, випущений у червні 2023 року. Слідом за ним захисний файл `EXTERNALLY-MANAGED` додали **Ubuntu 23.04 / 24.04 LTS**, **Fedora 38+**, **Arch Linux**, **Alpine Linux 3.18+** та менеджер пакунків **Homebrew** для macOS.

Прийняття PEP 668 ознаменувало завершення п'ятнадцятирічної ери «дикого sudo pip install». Воно остаточно закріпило стандартну архітектурну модель: системний Python належить операційній системі, а вся розробка користувацьких проєктів та встановлення сторонніх утиліт повинні відбуватися в суворо ізольованих віртуальних середовищах.
