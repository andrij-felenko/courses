Коли користувач вводить у терміналі команду `python3 script.py`, оболонка командного рядка здійснює системний виклик `execve("/usr/bin/python3", argv, envp)`. Ядро операційної системи очищає попередній адресний простір процесу, монтує сторінки пам'яті виконуваного ELF-образу інтерпретатора, відображає динамічний компонувальник (`ld.so`), завантажує спільні бібліотеки `libc.so` та `libpython3.so` і передає керування на асемблерну точку входу `_start`. Звідти виклик переходить до функції `main()` у файлі `Programs/python.c`, яка негайно передає керування функції `Py_BytesMain(argc, argv)` у `Modules/main.c`. Між цим першим машинним тактом і виконанням першого байткод-опокоду користувацького скрипту лежить розгалужений ланцюг системних перевірок та ініціалізацій: конфігурація алокаторів пам'яті, зчитування змінних оточення, евристичний розрахунок системних шляхів, розгортання вбудованої підсистеми імпорту зі статичних C-структур та сканування каталогів сторонніх пакунків.

## 1. Системний виклик, точка входу та архітектура PEP 587

Після завершення системного виклику `execve` процес отримує стандартне сегментування віртуальної пам'яті: сегмент коду (`.text`), сегмент ініціалізованих констант (`.rodata`), сегмент даних (`.data`), неініціалізовані змінні (`.bss`), а також порожні області купи (`heap`) та стека викликів (`stack`).

У ранніх версіях CPython ініціалізація інтерпретатора спиралася на розрізнені глобальні змінні мови C (`Py_NoSiteFlag`, `Py_OptimizeFlag`, `Py_VerboseFlag`, `Py_IgnoreEnvironmentFlag`). Такий підхід мав критичні недоліки: глобальні прапорці унеможливлювали одночасне створення кількох незалежних інтерпретаторів у різних потоках одного C/C++ застосунку (Embedding), створювали стан гонитви при модифікації конфігурації під час виконання та призводили до помилок кодувань, якщо системна локаль змінювалася після часткового зчитування аргументів командного рядка.

Починаючи з Python 3.8, процес старту повністю стандартизовано в межах [PEP 587](https://peps.python.org/pep-587/) («Python Initialization Configuration»). Стандарт розділив ініціалізацію на дві взаємопов'язані фази:
1. **Перед-ініціалізація (`PyPreConfig`):** налаштування системних алокаторів пам'яті, системної локалі C та режиму обробки кодування UTF-8.
2. **Повна ініціалізація (`PyConfig`):** зчитування параметрів CLI, змінних оточення та атомарне розгортання структур середовища CPython.

Функція `Py_BytesMain()` організовує послідовне проходження цих фаз:

```
execve("/usr/bin/python3", argv, envp)
  → _start [glibc]
    → main() [Programs/python.c]
      → Py_BytesMain(argc, argv) [Modules/main.c]
        → Py_PreInitializeFromBytesArgs(&preconfig, argc, argv)
        → PyConfig_InitPythonConfig(&config)
        → PyConfig_SetBytesArgv(&config, argc, argv)
        → PyConfig_Read(&config)
        → Py_InitializeFromConfig(&config)
        → pymain_run_python(&config)
```

Перед-ініціалізація `Py_PreInitialize` виконує лише ті низькорівневі налаштування, без яких CPython не може навіть декодувати рядки аргументів `argv` у формат широких символів `wchar_t*`:
- Ініціалізує низькорівневі алокатори пам'яті `PyMem_RawMalloc` та `pymalloc`.
- Викликає функцію `setlocale(LC_CTYPE, "")`, щоб прив'язати процес до системного мовного середовища операційної системи.
- Визначає режим UTF-8 відповідно до [PEP 540](https://peps.python.org/pep-0540/): якщо системна локаль встановлена в `C` або `POSIX`, CPython примусово вмикає прозоре декодування UTF-8 для всіх шляхів і потоків вводу-виводу, уникаючи збоїв при обробці символів за межами ASCII.

Лише після завершення роботи `PyPreConfig` інтерпретатор переходить до конфігурації основної структури `PyConfig`. Повний опис полів структури, кодів повернення `PyStatus` та прикладів безпечного вбудовування інтерпретатора мовами C і C++ наведено у вставці [Інтерфейс конфігурації CPython: структура PyConfig](root:sys-plang-python/interpreter-startup/api-pyconfig.md).

```
+-------------------------------------------------------------------------+
|                        ФАЗИ СТАРТУ CPYTHON                              |
+------------------------------------+------------------------------------+
| 1. OS & C-Entry                    | 2. Pre-Initialization (PEP 587)    |
|    • execve("/usr/bin/python3")    |    • PyMem / pymalloc init         |
|    • ld.so: libc, libpython        |    • setlocale(LC_CTYPE, "")       |
|    • main() -> Py_BytesMain()      |    • UTF-8 mode detection (PEP 540)|
+------------------------------------+------------------------------------+
| 3. Configuration Parsing           | 4. Core Runtime Bootstrap          |
|    • CLI flags (-S, -O, -v, -P)    |    • PyInterpreterState / Thread   |
|    • Env: PYTHONHOME, PYTHONPATH   |    • Core Types: object, type, str |
|    • _PyPathConfig (Landmarks)     |    • builtins & sys module init    |
+------------------------------------+------------------------------------+
| 5. Import Bootstrap                | 6. Environment & Execution         |
|    • _frozen_importlib (C memory)  |    • site.py (.pth files scan)     |
|    • Deep-Frozen modules (3.11+)   |    • Module __main__ creation      |
|    • sys.meta_path setup           |    • PyFrameObject -> First Opcode |
+------------------------------------+------------------------------------+
```

## 2. Зчитування конфігурації та розрахунок шляхів (_PyPathConfig)

Під час виклику функції `PyConfig_Read(&config)` середовище CPython об'єднує конфігураційні дані з двох незалежних джерел: аргументів командного рядка та змінних середовища операційної системи.

Якщо прапорець повної ізоляції `config.isolated` не встановлено в `1`, інтерпретатор перевіряє системні змінні:
- `PYTHONHOME` — примусово перевизначає базовий каталог стандартної бібліотеки.
- `PYTHONPATH` — список каталогів, розділених двокрапкою (у Unix) або крапкою з комою (у Windows), які додаються на початок системного списку пошуку модулів `sys.path`.
- `PYTHONNOUSERSITE` (або прапорець командного рядка `-s`) — забороняє автоматичне додавання каталогу користувацьких пакунків до `sys.path`.
- `PYTHONSAFEPATH` (або прапорець `-P`) — блокує небезпечне додавання поточного робочого каталогу чи каталогу скрипту на початок `sys.path`, захищаючи процес від підміни системних модулів шкідливими локальними файлами.
- `PYTHONOPTIMIZE` (або прапорці `-O`, `-OO`) — задає рівень оптимізації байткоду (видалення інструкцій `assert` та рядків документації `__doc__`).
- `PYTHONDONTWRITEBYTECODE` (або прапорець `-B`) — забороняє запис скомпільованих файлів `.pyc` у каталоги `__pycache__`.
- `PYTHONDEVMODE` (або прапорець `-X dev`) — вмикає розширений режим розробника з детальними перевірками коректності роботи алокаторів пам'яті та лічильників посилань.

Після валідації змінних оточення CPython запускає алгоритм розрахунку шляхів `_PyPathConfig` (у версіях Python 3.11+ він реалізований як спеціальний модуль `Modules/getpath.py`). Основне завдання цього алгоритму — визначити фізичні каталоги встановлення інтерпретатора (`prefix`), скомпільованих C-розширень (`exec_prefix`) та побудувати базовий список каталогів `sys.path` без завантаження повноцінної бібліотеки.

CPython реалізує евристичний алгоритм пошуку орієнтирів (Landmark Search):
1. **Пошук віртуального середовища (`venv`):** починаючи від каталогу, де розташовано виконуваний файл `sys.executable` (з урахуванням розіменування символічних посилань через системний виклик `readlink`), інтерпретатор піднімається вгору по дереву каталогів і шукає маркерний конфігураційний файл `pyvenv.cfg`. Якщо файл знайдено, каталог оголошується домашнім каталогом префікса (`prefix`), а системні шляхи спрямовуються у віртуальне середовище.
2. **Пошук системної стандартної бібліотеки:** якщо файл `pyvenv.cfg` відсутній, інтерпретатор шукає каталог бібліотеки за наявністю характерного файлу-орієнтира (Landmark File) — як-от `os.py` або бінарного каталогу `lib-dynload`.
3. **Побудова базового списку `sys.path`:** на основі знайденого префікса інтерпретатор конструює початковий список каталогів пошуку:

```
/usr/lib/python312.zip
/usr/lib/python3.12
/usr/lib/python3.12/lib-dynload
```

*Послідовність фаз ініціалізації середовища виконання CPython від завантаження двійкового образу до запуску віртуальної машини.*

## 3. Ініціалізація ядра середовища: Py_InitializeFromConfig

Отримавши перевірену та заповнену структуру `PyConfig`, функція `Py_InitializeFromConfig(&config)` переходить до розгортання структур середовища CPython. На цьому етапі виділяється та налаштовується пам'ять під ключові підсистеми:

1. **Створення стану інтерпретатора (`PyInterpreterState`):**
   Виділяється головна структура, що представляє ізольований екземпляр віртуальної машини Python. Вона містить таблицю завантажених модулів `interp->modules` (майбутній `sys.modules`), словник вбудованих функцій `interp->builtins`, внутрішні лічильники та списки поколінь циклічного збирача сміття GC (`interp->gc`), таблицю інтернованих рядків і словник ідентифікаторів потоків.
2. **Створення стану головного потоку (`PyThreadState`):**
   Структура `PyThreadState` прив'язує потік операційної системи до віртуальної машини CPython, створює стек фреймів виконання, ініціалізує глобальне блокування інтерпретатора (GIL) та налаштовує вказівники на поточні винятки.
3. **Ініціалізація базової системи типів:**
   CPython налаштовує статичні структури `PyTypeObject` для всіх фундаментальних типів: `object`, `type`, `int`, `bool`, `float`, `str`, `bytes`, `tuple`, `list`, `dict`, `set`. Для кожного типу ініціалізуються слоти магічних методів `tp_as_number`, `tp_as_sequence`, `tp_as_mapping`, налаштовується порядок розв'язання методів (MRO) та розраховуються бітові прапорці `Py_TPFLAGS_READY`.
4. **Створення модулів `builtins` та `sys`:**
   Інтерпретатор викликає `_PyBuiltin_Init` та `_PySys_InitCore`, створюючи об'єкти модулів `builtins` (куди заносяться функції `print`, `len`, `range`, `isinstance`, типи винятків `Exception`, `ValueError`) та `sys` (із константами `sys.version`, `sys.platform`, `sys.maxsize` та початковим словником `sys.modules`).

Після завершення цих дій ядро CPython готове до роботи, але постає фундаментальна проблема: у системі ще немає модулів, а вся високорівнева логіка пошуку та завантаження файлів з диска (`importlib`) написана самою мовою Python.

## 4. Заморожені модулі та розв'язання проблеми бутстрапу

Щоб завантажити будь-який файл `.py` з диска, інтерпретатор мусить виконати код модуля `importlib._bootstrap`. Але щоб виконати `importlib._bootstrap`, його спершу треба імпортувати. Це парадокс замкненого кола (бутстрапінг).

CPython розв'язує цей парадокс за допомогою механізму **заморожених модулів** (Frozen Modules).

Під час компіляції самого двійкового файлу CPython на етапі збирання проєкту вихідні файли `Lib/importlib/_bootstrap.py` та `Lib/importlib/_bootstrap_external.py` транслюються у байткод і серіалізуються у масиви байтів мови C всередині файлу `Python/frozen.c`. Коли CPython стартує, функція `_PyImport_InitCore()` звертається безпосередньо до пам'яті процесу, зчитує ці бінарні масиви та створює об'єкти коду без жодного звернення до файлової системи чи викликів `stat()`/`open()`.

```
+-------------------------------------------------------------------------+
|                  МЕХАНІЗМ ЗАМОРОЖЕНИХ МОДУЛІВ (FROZEN)                 |
+-------------------------------------------------------------------------+
| Збирання CPython (Build time):                                          |
| _bootstrap.py ──[ Компілятор ]──> Байткод ──[ C-Array ]──> frozen.c     |
|                                                                         |
| Запуск CPython (Runtime startup):                                       |
| frozen.c (у RAM) ──[ PyMarshal_Read ]──> PyCodeObject ──> sys.modules   |
+-------------------------------------------------------------------------+
```

### Еволюція: від Frozen до Deep-Frozen (Python 3.11+)

У класичних заморожених модулях (Python 3.8–3.10) двійковий масив містив серіалізований маршалом потік байтів. Під час кожного запуску інтерпретатор викликав функцію `PyMarshal_ReadObjectFromString()`, яка парсила байти й динамічно виділяла у купі (`heap`) пам'ять під об'єкти `PyCodeObject`, кортежі імен та констант.

У межах ініціативи Faster CPython у Python 3.11 було впроваджено технологію **Deep-Freeze** (глибоке заморожування). Утиліта `Tools/build/deepfreeze.py` під час компіляції CPython генерує об'єкти коду `PyCodeObject` безпосередньо як статичні структури мови C зі специфікатором `const`.

Це дає три принципові переваги:
- **Нульовий час десеріалізації:** об'єкти коду готові до виконання процесором негайно, без викликів маршалу.
- **Розміщення у сегменті `.rodata`:** структури не потребують виділення динамічної пам'яті в купі під час старту.
- **Розділення пам'яті (Page Sharing):** сторінки пам'яті `.rodata` розділяються між усіма запущеними процесами Python через сторінковий механізм віртуальної пам'яті ядра ОС, зменшуючи фізичне споживання RAM.

Історичні передумови та технічні деталі еволюції бутстрапу від монолітного коду Python 1.x/2.x до сучасного Deep-Freeze розкрито у вставці [Еволюція бутстрапу CPython: від монолітної ініціалізації до Deep-Freeze](root:sys-plang-python/interpreter-startup/hist-cpython-bootstrap.md).

![Порівняння імпорту з диска проти Frozen та Deep-Frozen модулів: усунення I/O та десеріалізації](/root/sys/sys-plang-python/interpreter-startup/img/frozen-vs-disk-import.svg)
*Еволюція завантаження модулів ядра від дискових викликів через маршалізацію байткоду до статичних C-структур у пам'яті .rodata.*

Після завантаження `_frozen_importlib_external` CPython ініціалізує список шукачів `sys.meta_path`:
1. `BuiltinImporter` — відповідає за завантаження вбудованих у двійковий файл C-модулів (`sys`, `builtins`, `gc`, `_ast`).
2. `FrozenImporter` — відповідає за пошук заморожених модулів стандартної бібліотеки.
3. `PathFinder` — універсальний шукач файлів `.py`, `.pyc` та `.so` у каталогах зі списку `sys.path`.

## 5. Розгортання середовища: виконання site.py

Після успішного встановлення механізму імпорту інтерпретатор перевіряє прапорець `config.site_import`. Якщо під час виклику не було задано прапорець `-S`, CPython автоматично імпортує стандартний модуль `site.py`.

Модуль `site.py` відповідає за підготовку робочого середовища розробника:
1. **Обчислення каталогів `site-packages`:** визначає шляхи до сторонніх бібліотек на основі `prefix` та `exec_prefix` (наприклад, `/usr/local/lib/python3.12/dist-packages` та `/usr/lib/python3.12/site-packages`) і додає їх у кінець списку `sys.path`.
2. **Підключення користувацького каталогу (User Site Directory):** якщо не встановлено змінну `PYTHONNOUSERSITE` або прапорець `-s`, перевіряє наявність локального каталогу користувача (`~/.local/lib/python3.12/site-packages`) і додає його до `sys.path`.
3. **Сканування та обробка `.pth` файлів:** перевіряє всі каталоги `site-packages` на наявність файлів із розширенням `.pth` (Path Configuration). Для кожного такого файлу:
   - Звичайні текстові рядки інтерпретуються як додаткові шляхи до каталогів і додаються до `sys.path`.
   - Рядки, що починаються з префікса `import `, виконуються як довільний Python-код через `exec()`. Цей механізм активно використовується інструментами пакування (`setuptools`, `editable installs` у режимі розробки, хуки інструментів вимірювання покриття коду `coverage`).
4. **Реєстрація інтерактивних об'єктів:** додає до простору імен `builtins` допоміжні об'єкти `quit`, `exit`, `help`, `copyright` та `license`.
5. **Налаштування потоків введення-виведення:** встановлює кодування UTF-8 для стандартних потоків `sys.stdin`, `sys.stdout`, `sys.stderr`.

Обробка `site.py` є однією з найбільш витратних фаз холодного старту через необхідність багаторазового сканування файлової системи.

## 6. Структура часу старту (Startup Latency)

Повний час старту CPython — це сумарна латентність від моменту виконання системного виклику `execve` до моменту готовності віртуальної машини виконувати код користувача. Цей час можна описати як баланс окремих компонентів:

```
T_total
= T_os + T_c_init + T_site + T_imports + T_script
```

де:
- `T_os` — час роботи ядра операційної системи: виділення віртуальної пам'яті, завантаження сторінок ELF-образу та робота динамічного компонувальника `ld.so` (1.0–2.5 мс).
- `T_c_init` — виконання C-коду CPython: `Py_PreInitialize`, `PyConfig_Read`, розгортання вбудованих типів, виконання Deep-Frozen коду `importlib` (1.5–3.5 мс у Python 3.11+).
- `T_site` — виконання модуля `site.py`: пошук каталогів `site-packages`, сканування та виконання `.pth` файлів (10–30 мс).
- `T_imports` — транзитивне завантаження модулів, явно імпортованих у скрипті користувача (`import requests`, `import numpy`, `import pandas`) — від 20 мс до сотень мілісекунд.
- `T_script` — компіляція та виконання першого фрейму користувацького коду.

```
+-------------------------------------------------------------------------+
|                  СТРУКТУРА ЗАТРИМКИ СТАРТУ (LATENCY BUDGET)             |
+-------------------------------------------------------------------------+
| [T_os] 2ms   [T_c_init] 3ms   [T_site] 22ms       [T_imports] 58ms      |
| |====|       |======|         |==================| |==================| |
|  execve       PyConfig         site.py / .pth       import numpy / deps |
|                                                                         |
| Без оптимізацій (Звичайний старт): ~85-120 мс                           |
| З прапорцем -S (Без site.py):       ~25-35 мс                            |
| З -S та Lazy Imports:              ~5-7 мс                              |
+-------------------------------------------------------------------------+
```

### Вузькі місця: дисковий I/O та валідація байткоду

Головною причиною високої латентності старту є системні виклики до файлової системи (`stat`, `open`, `access`). Коли інтерпретатор обробляє інструкцію `import foo`, шукач `PathFinder` не знає заздалегідь, де розташовано файл, і послідовно перевіряє кожен запис списку `sys.path`:
1. Викликає `stat("/path/foo")`, перевіряючи, чи є об'єкт каталогом із файлом `__init__.py`.
2. Викликає `stat("/path/foo.py")` для пошуку вихідного коду.
3. Викликає `stat("/path/foo.cpython-312-x86_64-linux-gnu.so")` для пошуку C-розширення.

Якщо `sys.path` містить 15 каталогів, а модуль розташований в останньому, CPython здійснить до 45 системних викликів `stat()` лише для пошуку одного модуля.

Після знаходження файлу `.py` CPython перевіряє кеш байткоду `__pycache__/foo.cpython-312.pyc`:
- Файл `.pyc` містить 16-байтовий заголовок:
  - 4 байти магічного числа версії байткоду (Magic Number);
  - 4 байти бітових прапорців;
  - 8 байтів часової мітки модифікації вихідного файлу та його розміру (або 8 байтів SIPHASH-хешу вихідного файлу).
- Якщо кеш валідний, CPython викликає `marshal.loads()` і негайно отримує готовий `PyCodeObject` без парсингу.
- Якщо `.pyc` застарілий або відсутній, інтерпретатор запускає повний цикл компіляції: токенізацію, парсинг граматики PEG, побудову абстрактного синтаксичного дерева (AST), генерацію байткоду та запис оновленого `.pyc` на диск. Це збільшує час завантаження модуля в 5–15 разів.

![Бюджет часу старту CPython: розподіл латентності між ядром, site.py та імпортами залежностей](/root/sys/sys-plang-python/interpreter-startup/img/latency-breakdown.svg)
*Структура часу запуску: скорочення латентності зі стандартних 85 мс до 5.5 мс завдяки прапорцю -S та відкладеним імпортам.*

## 7. Техніки оптимізації та прискорення старту

Для короткоживучих процесів (утиліти командного рядка, бекенд-хуки, безсерверні обчислення AWS Lambda / Cloud Functions) скорочення часу старту є ключовим фактором продуктивності. Нижче наведено основні інженерні підходи до мінімізації латентності.

### 1. Пропуск обробки пакунків: прапорець -S

Якщо виконуваний скрипт є самодостатнім і не залежить від неявних шляхів `site-packages`, виконання `site.py` можна повністю відключити:

```bash
python3 -S script.py
```

Прапорець `-S` встановлює `config.site_import = 0`, виключаючи сканування каталогів `site-packages` та парсинг `.pth` файлів. Це зменшує чистий час ініціалізації CPython з ~25–30 мс до ~4–6 мс.

### 2. Профілювання часу імпорту: прапорець -X importtime

Для виявлення важких модулів, які спричиняють вибух часу старту (Import Explosion), застосовують вбудований профілювальник:

```bash
python3 -X importtime script.py
```

Профілювальник виводить ієрархічне дерево імпортованих модулів із двома часовими показниками (у мікросекундах):
- `self [us]` — час, витрачений безпосередньо на виконання верхньорівневого коду самого модуля.
- `cumulative [us]` — сумарний час завантаження модуля включно з усіма його транзитивними залежностями.

Приклад аналізу профілю:

```
import time: self [us] | cumulative [us] | imported module
import time:        120 |            120 |   _opcode
import time:        340 |            460 | opcode
import time:       1250 |           1710 | dis
import time:       8420 |          24500 | heavy_package
```

### 3. Відкладені імпорти (Lazy Imports)

У розгалужених застосунках більшість залежностей потрібні лише для специфічних підкоманд або рідкісних сценаріїв обробки помилок. Патерн відкладеного імпорту (Lazy Import) замінює синхронне завантаження легковажним проксі-об'єктом, який ініціює реальне зчитування з диска лише тоді, коли програма вперше звертається до атрибута чи функції модуля.

Повну архітектуру, реалізацію потокобезпечного проксі-модуля та бенчмарк виграшу в часі старту наведено у проєктній вставці [Реалізація механізму відкладеного завантаження модулів (Lazy Imports)](root:sys-plang-python/interpreter-startup/proj-lazy-import.md).

> 🔧 **Навіщо це.**
> Утиліта командного рядка з 20 підкомандами (`aws-cli`, `gcloud`, внутрішні сервісні утиліти) при жадібному імпорті всіх підмодулів на старті вимагає 400–800 мс лише на завантаження бібліотек. Використання відкладених імпортів зменшує час старту команд `tool --version` або `tool status` до 15–25 мс, роблячи відгук інтерфейсу миттєвим для користувача.

## 8. Запуск коду користувача та перший байткод-опокод

Коли всі підсистеми CPython ініціалізовано, функція `pymain_run_python()` у файлі `Modules/main.c` переходить до виконання цільового коду:

1. **Створення модуля `__main__`:**
   Інтерпретатор створює об'єкт модуля з іменем `"__main__"` і реєструє його в системному словнику `sys.modules["__main__"]`. Словник простору імен цього модуля (`__main__.__dict__`) стає глобальним простором імен для виконання скрипту.
2. **Встановлення службових атрибутів:**
   Встановлюються службові поля `__file__` (абсолютний шлях до файлу скрипту), `__name__ = "__main__"`, `__doc__ = None`, `__package__ = None`, `__annotations__ = {}`.
3. **Компіляція або отримання коду:**
   Функція `PyRun_SimpleFileExFlags()` відкриває вихідний файл. Якщо поруч існує валідний `.pyc`, інтерпретатор завантажує `PyCodeObject`; інакше CPython компілює вихідний код у новий об'єкт коду на льоту.
4. **Створення кореневого фрейму виконання (`PyFrameObject`):**
   Виділяється структура фрейму, що містить посилання на об'єкт коду, глобальний простір імен `__main__.__dict__`, локальний масив змінних і стек операндів.
5. **Вхід у головний цикл віртуальної машини:**
   Функція `_PyEval_EvalFrameDefault()` (або спеціалізований інтерпретатор у версіях Python 3.12+) починає виконання байткоду.

Перший байткод-опокод скрипту береться до виконання:
- У Python 3.10 і раніше першою інструкцією модуля зазвичай була `LOAD_CONST` або `LOAD_GLOBAL`.
- Починаючи з Python 3.11, кожен модуль і кожна функція обов'язково починаються з інструкції `RESUME 0`, яка виконує внутрішню перевірку системних сигналів ОС, оновлює стан відстеження трасування і передає керування наступним інструкціям програми.

У цей момент ініціалізація CPython завершується, і віртуальна машина переходить у режим безперервного виконання користувацького алгоритму.

## Терміни та етимологія

| Термін | Етимологія | Значення у контексті CPython |
|---|---|---|
| **Ініціалізація** | Від лат. *initialis* — початковий, від *initium* — початок. | Послідовний процес приведення середовища виконання CPython із неактивного стану в стан повної готовності до виконання байткоду. |
| **Бутстрапінг** | Від англ. *bootstrapping*, від *bootstrap* — вушко черевика для затягування; метафора витягування себе за шнурки. | Процес завантаження підсистеми імпорту CPython за допомогою заздалегідь скомпільованого байткоду самої мови Python. |
| **Заморожений модуль** (*Frozen Module*) | Від англ. *freeze* — заморожувати, фіксувати. | Модуль Python, байткод або C-структура якого скомпільовані безпосередньо у двійковий файл інтерпретатора на етапі збирання проєкту. |
| **Латентність старту** (*Startup Latency*) | Від лат. *latentia* — прихованість, затримка, від *latere* — ховатися. | Часовий інтервал від моменту виклику `execve()` до моменту виконання першої інструкції скрипту користувача. |
| **Транзитивний імпорт** | Від лат. *transitivus* — перехідний, від *transire* — переходити. | Каскадне завантаження модулів-залежностей, які викликаються всередині явно імпортованих бібліотек. |
