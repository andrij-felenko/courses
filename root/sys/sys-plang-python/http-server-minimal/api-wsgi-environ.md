# Специфікація WSGI environ та API BaseHTTPRequestHandler

Цей довідник містить повну нормативну структуру словника оточення `environ`, сигнатури функцій специфікації WSGI (PEP 3333), правила обробки двійкових даних і текстових кодувань, протокол валідації сумісності, а також опис внутрішнього API та життєвого циклу обробника `http.server.BaseHTTPRequestHandler` зі стандартної бібліотеки Python.

## 1. Словник оточення WSGI (`environ`)

Згідно зі специфікацією [PEP 3333](https://peps.python.org/pep-3333/), WSGI-сервер або шлюз передає вебзастосунку стандартний словник Python `environ`, що містить змінні оточення у стилі CGI (Common Gateway Interface), специфічні змінні WSGI-шлюзу та довільні додаткові параметри операційної системи.

Усі ключі в словнику є звичайними рядками (`str`). Для збереження сумісності з протоколом HTTP/1.1 у Python 3 рядкові значення заголовків та шляхів декодуються сервером із байтів мережевого потоку за стандартом Latin-1 (ISO-8859-1). Якщо застосунок очікує дані в кодуванні UTF-8 (наприклад, у значеннях заголовків або `PATH_INFO`), він повинен виконати повторне кодування рядка: `path_info.encode('latin-1').decode('utf-8')`.

### 1.1. Обов'язкові змінні стандарту CGI

Специфікація WSGI вимагає наявності такого мінімального набору змінних, успадкованих від стандарту RFC 3875 (CGI/1.1):

| Ключ | Тип | Нормативний опис та інваріанти стандарту | Приклад значення |
| :--- | :--- | :--- | :--- |
| `REQUEST_METHOD` | `str` | Метод HTTP-запиту у верхньому регістрі (`GET`, `POST`, `PUT`, `DELETE`, `HEAD`, `OPTIONS`, `PATCH`). Є строго обов'язковим для кожного виклику. | `"POST"` |
| `SCRIPT_NAME` | `str` | Початкова частина шляху URL, що відповідає префіксу монтування застосунку. Може бути порожнім рядком `""`, якщо застосунок обслуговує корінь сервера. Завжди починається зі скісної риски `/`, якщо не порожній. | `""` або `"/api/v1"` |
| `PATH_INFO` | `str` | Залишкова частина шляху запиту всередині застосунку. Завжди починається зі скісної риски `/`, якщо запит має непустий шлях. Може бути порожнім рядком, якщо запит спрямовано на `SCRIPT_NAME` без кінцевого слеша. | `"/telemetry/sensors"` |
| `QUERY_STRING` | `str` | Рядок параметрів запиту після символу `?`. Якщо рядок запиту відсутній у URL, значенням є порожній рядок `""`. Сервер не здійснює автоматичного синтаксичного розбору параметрів. | `"device_id=node-01&limit=50"` |
| `CONTENT_TYPE` | `str` | Значення заголовка `Content-Type` із клієнтського HTTP-запиту. Якщо клієнт не надав цей заголовок, ключ може бути відсутній або містити порожній рядок. | `"application/json; charset=utf-8"` |
| `CONTENT_LENGTH` | `str` | Значення заголовка `Content-Length` (десяткове число у вигляді рядка). Вказує розмір тіла запиту в байтах. Якщо тіло відсутнє, ключ може бути пропущений або дорівнювати `""`. | `"256"` |
| `SERVER_NAME` | `str` | Мережеве ім'я хоста сервера або IP-адреса, на якій сервер приймає з'єднання (визначається з заголовка `Host` або системної конфігурації). | `"127.0.0.1"` |
| `SERVER_PORT` | `str` | Десятковий номер порту TCP, на якому сервер очікує підключення. | `"8080"` |
| `SERVER_PROTOCOL` | `str` | Версія протоколу, за якою клієнт надіслав запит (наприклад, `"HTTP/1.0"` або `"HTTP/1.1"`). | `"HTTP/1.1"` |

### 1.2. Обов'язкові змінні специфікації WSGI (`wsgi.*`)

WSGI визначає окремий простір імен змінних із префіксом `wsgi.`, призначений для взаємодії із середовищем виконання сервера:

| Ключ | Тип | Опис та системний контракт |
| :--- | :--- | :--- |
| `wsgi.version` | `tuple[int, int]` | Кортеж версії стандарту WSGI. Для PEP 3333 значенням є строго `(1, 0)`. |
| `wsgi.url_scheme` | `str` | Схема протоколу, за якою було отримано мережевий запит: `"http"` або `"https"`. |
| `wsgi.input` | `BinaryIO` | Потік читання байтів (файлоподібний об'єкт), що надає доступ до сирого тіла клієнтського запиту. |
| `wsgi.errors` | `TextIO` | Текстовий потік виведення для запису діагностичних повідомлень, попереджень та помилок сервера (обгортка над `sys.stderr`). |
| `wsgi.multithread` | `bool` | Прапорець `True`, якщо один і той самий екземпляр застосунку може викликатися одночасно в різних потоках одного процесу. |
| `wsgi.multiprocess` | `bool` | Прапорець `True`, якщо застосунок виконується у кількох незалежних процесах ОС (наприклад, воркери Gunicorn або uWSGI). |
| `wsgi.run_once` | `bool` | Прапорець `True`, якщо процес сервера завершить виконання відразу після поточної відповіді (характерно для класичного CGI). |

### 1.3. Перетворення клієнтських заголовків HTTP (`HTTP_*`)

Усі довільні заголовки клієнтського HTTP-запиту, за винятком `Content-Type` та `Content-Length`, перетворюються WSGI-сервером у змінні `environ` за чітким алгоритмом:
1. Усі символи назви заголовка переводяться у верхній регістр (`UPPERCASE`).
2. Усі дефіси `-` замінюються на символи підкреслення `_`.
3. До назви додається префікс `HTTP_`.

Заголовки `Content-Type` та `Content-Length` зберігаються без префікса `HTTP_` як змінні `CONTENT_TYPE` та `CONTENT_LENGTH` відповідно, оскільки вони мають спеціальний статус у стандарті CGI.

Специфікація забороняє серверу передавати до застосунку «хоп-за-хопом» (Hop-by-hop) заголовки, які керують фізичним TCP-з'єднанням між безпосередніми вузлами: `Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `TE`, `Trailers`, `Transfer-Encoding`, `Upgrade`.

### 1.4. Контракт потоку `wsgi.input`

Об'єкт `wsgi.input` є двійковим потоком і повинен надавати такі базові методи читання:
- `read(size: int = -1) -> bytes`: зчитує до `size` байтів. Якщо параметр `size` опущено, потік зчитує всі дані до кінця файлу (EOF). Застосунок **не повинен** викликати `read()` без аргументу, якщо клієнт тримає постійне з'єднання HTTP Keep-Alive, оскільки сервер не надсилає EOF і виклик зависне назавжди;
- `readline(size: int = -1) -> bytes`: зчитує один рядок байтів до символу нового рядка `\n` або до досягнення ліміту `size`;
- `readlines(hint: int = -1) -> list[bytes]`: повертає список рядків байтів;
- `__iter__() -> Iterator[bytes]`: дозволяє ітерувати потік рядок за рядком.

## 2. Сигнатура та протокол `start_response`

Функція `start_response` передається сервером у застосунок під час кожного виклику:

```python
def start_response(
    status: str,
    response_headers: list[tuple[str, str]],
    exc_info: tuple | None = None
) -> Callable[[bytes], None]:
    ...
```

### 2.1. Нормативні вимоги до аргументів

1. **`status` (`str`):**
   Рядок статусу відповіді HTTP, що складається з тризначного числового коду та пояснювального тексту через один пробіл (наприклад, `"200 OK"`, `"201 Created"`, `"400 Bad Request"`, `"404 Not Found"`, `"500 Internal Server Error"`). Передача порожнього рядка, лише коду чи наявність керуючих символів `\r\n` заборонені.

2. **`response_headers` (`list[tuple[str, str]]`):**
   Список кортежів виду `(header_name, header_value)`. Заголовки повинні бути рядками `str` у кодуванні Latin-1. Застосунок не повинен додавати транспортні заголовки керування з'єднанням (`Connection`, `Date`, `Server`), оскільки за них відповідає безпосередньо серверний шлюз.

3. **`exc_info` (`tuple | None`):**
   Кортеж `sys.exc_info()`, що передається виключно під час обробки винятків у застосунку. Якщо застосунок уже викликав `start_response`, але заголовки ще не були фізично відправлені в сокет, виклик `start_response` з переданим `exc_info` дозволяє змінити статус відповіді на `"500 Internal Server Error"`. Якщо ж перші байти тіла вже надіслано в мережу, виклик `start_response` з `exc_info` зобов'язаний знову підняти цей виняток через `raise exc_info[1].with_traceback(exc_info[2])`.

### 2.2. Застарілий зворотний виклик `write`

Функція `start_response` повертає функцію `write(data: bytes) -> None`. Вона була введена в PEP 333 для підтримки застарілих фреймворків із прямим імперативним потоковим виведенням. Стандарт PEP 3333 категорично рекомендує не використовувати `write`, а повертати байти через ітерований об'єкт із самої точки входу застосунку (`return [payload]`).

## 3. Інтерфейс `http.server.BaseHTTPRequestHandler`

Клас `BaseHTTPRequestHandler` є базовим каркасом обробки HTTP-запитів у стандартній бібліотеці Python. Він поєднує низькорівневе читання сокета з динамічною диспетчеризацією методів.

### 3.1. Атрибути екземпляра обробника

Під час надходження кожного клієнтського з'єднання екземпляр обробника наповнюється такими полями:

| Атрибут | Тип | Опис та призначення |
| :--- | :--- | :--- |
| `self.command` | `str` | HTTP-метод запиту, вилучений зі стартового рядка (`"GET"`, `"POST"`, `"PUT"` тощо). |
| `self.path` | `str` | Повний шлях URL запиту разом із рядком запиту (наприклад, `"/metrics?format=json"`). |
| `self.request_version` | `str` | Версія протоколу клієнта зі стартового рядка (`"HTTP/1.0"` або `"HTTP/1.1"`). |
| `self.headers` | `http.client.HTTPMessage` | Об'єкт розібраних заголовків. Надає словниковий доступ без урахування регістру: `self.headers.get("Content-Length")`. |
| `self.rfile` | `io.BufferedReader` | Буферизований вхідний потік читання із сокета клієнта. |
| `self.wfile` | `io.BufferedWriter` | Буферизований вихідний потік запису в сокет клієнта. |
| `self.client_address` | `tuple[str, int]` | Кортеж `(ip_address, port)` віддаленого клієнтського сокета. |
| `self.server` | `socketserver.BaseServer` | Посилання на екземпляр сервера, що створив цей обробник. |
| `self.protocol_version` | `str` | Версія протоколу відповідей сервера (за замовчуванням `"HTTP/1.0"`, рекомендується встановлювати `"HTTP/1.1"`). |
| `self.close_connection` | `bool` | Прапорець розриву з'єднання. Якщо `True`, цикл обробника завершується і сокет закривається; якщо `False`, сокет залишається відкритим для очікування наступного HTTP-запиту (Keep-Alive). |

### 3.2. Методи життєвого циклу та формування відповіді

| Метод | Сигнатура | Опис внутрішньої поведінки |
| :--- | :--- | :--- |
| `handle_one_request` | `()` | Зчитує стартовий рядок і заголовки, визначає метод `do_<COMMAND>` і викликає його. |
| `send_response` | `(code: int, message: str | None = None)` | Записує статусний рядок `HTTP/1.1 <code> <message>\r\n`, а також автоматично додає службові заголовки `Server` та `Date`. |
| `send_response_only`| `(code: int, message: str | None = None)` | Записує лише статусний рядок без автоматичного генерування заголовків `Server` та `Date`. |
| `send_header` | `(keyword: str, value: str)` | Записує рядок заголовка у буфер `self.wfile` у форматі `<keyword>: <value>\r\n`. |
| `end_headers` | `()` | Записує кінцевий роздільник `\r\n` заголовків та скидає буфер у сокет через `self.wfile.flush()`. |
| `send_error` | `(code: int, message: str | None = None, explain: str | None = None)` | Відправляє клієнту згенеровану HTML-сторінку помилки та виставляє `self.close_connection = True`. |
| `log_message` | `(format: str, *args)` | Форматує та виводить рядок доступу в `sys.stderr`. Перевизначається для інтеграції з модулем `logging` або повного вимкнення виводу. |

## 4. Потокове передавання даних та звільнення ресурсів

Коли WSGI-застосунок генерує об'ємне корисне навантаження (великі файли, нескінченні потоки подій), він повертає не список із одним елементом, а генератор або користувацький ітератор, який генерує байти порціями (`yield chunk`).

Згідно зі специфікацією PEP 3333, якщо ітерований об'єкт відповіді містить метод `close()`, WSGI-сервер зобов'язаний гарантовано викликати його після завершення надсилання всіх байтів або в разі аварійного розриву клієнтського TCP-з'єднання. Це забезпечує звільнення відкритих файлових дескрипторів, курсорів баз даних та мережевих з'єднань через стандартну конструкцію `try ... finally`:

```python
def streaming_file_app(environ: dict, start_response):
    """Приклад генератора потокової відповіді з гарантованим закриттям ресурсу."""
    file_handle = open("telemetry_archive.log", "rb")

    def file_stream():
        try:
            while chunk := file_handle.read(65536):
                yield chunk
        finally:
            file_handle.close()

    status = "200 OK"
    headers = [
        ("Content-Type", "application/octet-stream"),
        ("Content-Disposition", "attachment; filename=archive.log"),
    ]
    start_response(status, headers)
    return file_stream()
```

## 5. Обробка мережевих винятків і помилок сокета

Під час роботи з мережевим потоком введення-виведення у класах `BaseHTTPRequestHandler` та WSGI-шлюзах виникають типові системні винятки, спричинені поведінкою віддаленого клієнта:

1. **`BrokenPipeError` (помилка `EPIPE`):**
   Виникає під час спроби запису у `self.wfile` або сокет, якщо клієнт несподівано закрив TCP-з'єднання до отримання всієї відповіді (наприклад, користувач натиснув Stop у браузері або скасував команду `curl`). Сервер повинен перехоплювати цей виняток, припиняти генерацію тіла відповіді та коректно закривати дескриптор без аварійної зупинки процесу.

2. **`ConnectionResetError` (помилка `ECONNRESET`):**
   Виникає, коли клієнт надіслав пакет TCP RST (скидання зв'язку) під час читання `self.rfile` або запису `self.wfile`.

3. **`TimeoutError` (помилка `ETIMEDOUT`):**
   Виникає, якщо сокет було сконфігуровано з таймаутом (`socket.settimeout()`), і клієнт не передав чергову порцію даних протягом відведеного інтервалу.

Коректна обробка цих винятків у виробничих серверах полягає у встановленні прапорця розриву з'єднання `self.close_connection = True` та звільненні буферів без викидання аварійного трасування стека в загальні логи системи.

## 6. Валідація за стандартом `wsgiref.validate`

Стандартна бібліотека містить еталонний валідатор `wsgiref.validate.validator`, що перевіряє повну відповідність застосунку правилам PEP 3333. Він виконує такі інваріантні перевірки:
1. Тип об'єкта `environ` — строго вбудований словник `dict`, а не підклас.
2. Усі обов'язкові CGI-ключі присутні та містять значення типу `str`.
3. Заголовки у `start_response` є списком кортежів із двох елементів типу `str` без заборонених керуючих символів.
4. Повертаний об'єкт є ітератором, кожен елемент якого є строго типом `bytes` (використання `str` викликає негайний виняток `AssertionError`).

Застосування валідатора в тестах гарантує сумісність із будь-яким виробничим вебсервером:

```python
from wsgiref.validate import validator
from wsgiref.simple_server import make_server


def my_app(environ, start_response):
    start_response("200 OK", [("Content-Type", "text/plain; charset=utf-8")])
    return [b"Valid WSGI response"]


# Обгортання додатку валідатором для перевірки сумісності
strict_app = validator(my_app)

if __name__ == "__main__":
    with make_server("127.0.0.1", 8080, strict_app) as httpd:
        httpd.serve_forever()
```
