# Історія веб-інтерфейсів у Python: від CGI до WSGI та ASGI

Розвиток протоколів зв'язку між вебсерверами та виконуваним кодом на Python пройшов тривалу еволюцію: від ізольованих запусків процесів через CGI та нестабільних вбудованих модулів Apache до формування універсального стандарту WSGI (PEP 333 / PEP 3333) і подальшої появи сучасного асинхронного інтерфейсу ASGI.

## 1. Епоха CGI та рання фрагментація (кінець 1990-х — 2003)

Наприкінці 1990-х років основним способом виконання серверного коду на Python був протокол **CGI (Common Gateway Interface)**. Робота вебсервера (типово NCSA HTTPd або Apache) виглядала так:
1. Клієнт надсилав HTTP-запит до вебсервера.
2. Вебсервер створював новий процес операційної системи (`fork()` + `execve()`) для виконання Python-скрипта.
3. Сервер передавав заголовки та параметри запиту через змінні оточення процесу (`REQUEST_METHOD`, `QUERY_STRING`, `PATH_INFO`), а тіло запиту спрямовував у стандартний потік введення `sys.stdin`.
4. Скрипт виводив HTTP-заголовки та HTML-тіло у стандартний потік виведення `sys.stdout` і завершував процес.

Такий підхід мав фатальний недолік: створення нового процесу ОС та повторна ініціалізація інтерпретатора CPython на кожен HTTP-запит створювали колосальні накладні витрати CPU та пам'яті. За навантаження у кілька десятків запитів на секунду сервер вичерпував ліміти дескрипторів та процесорний час на запуск середовища.

Для вирішення проблеми продуктивності спільнота створила кілька несумісних між собою технологій:
- **FastCGI та SCGI:** протоколи, що тримали пул довгоживучих процесів Python у фоні та передавали їм запити через сокети.
- **`mod_python` для Apache:** модуль, що вбудовував інтерпретатор CPython безпосередньо в адресний простір процесів вебсервера Apache HTTP Server.
- **Вбудовані сервери прикладних систем:** фреймворки Zope (сервер Medusa), Twisted та Quixote містили власні унікальні HTTP-сервери, жорстко прив'язані до їхньої внутрішньої архітектури.

Це призвело до «кризи сумісності»: вебзастосунок, написаний під `mod_python`, не міг працювати під FastCGI чи Twisted без повного переписування коду взаємодії із сервером. Кожен новий вебфреймворк був змушений писати власні драйвери для всіх існуючих вебсерверів.

## 2. Поява стандарту WSGI: PEP 333 (2003)

У 2003 році Філіп Ебі (Phillip J. Eby) за участі спільноти Python Web-SIG опублікував документ [PEP 333 — Python Web Server Gateway Interface v1.0](https://peps.python.org/pep-0333/). Метою специфікації було створення простого, універсального та мовно-нейтрального інтерфейсу між вебсервером і вебзастосунком за аналогією до Java Servlet API.

Ключові архітектурні принципи PEP 333:
1. **Мінімалізм:** застосунок визначається як звичайний Python-об'єкт, що підтримує виклик (функція, метод або екземпляр класу з `__call__`), який приймає два позиційні аргументи: `environ` (словник) та `start_response` (функція зворотного виклику).
2. **Поділ обов'язків:** вебсервер бере на себе низькорівневу роботу із сокетами, пулами потоків/процесів, парсингом HTTP та формуванням TCP-пакетів. Застосунок займається виключно маршрутизацією, бізнес-логікою та генерацією корисного навантаження.
3. **Концепція Middleware:** оскільки і сервер, і застосунок взаємодіють через єдиний інтерфейс, між ними можна вбудовувати проміжні ланцюжки обробників (Middleware). Проміжний шар одночасно виступає як застосунок для сервера і як сервер для кінцевого застосунку, дозволяючи прозоро реалізовувати автентифікацію, кешування, стиснення Gzip, маршрутизацію та обробку винятків.

Стандарт WSGI миттєво змінив екосистему Python:
- З'явилися універсальні виробничі WSGI-сервери: **Gunicorn** (Green Unicorn), **uWSGI**, **Waitress**, **mod_wsgi** (створений Грехемом Дамплтоном як заміна `mod_python`).
- Виникло нове покоління вебфреймворків, які спиралися виключно на WSGI: **Django**, **Flask**, **Bottle**, **Pyramid**, **Falcon**. Будь-який із цих фреймворків міг бути розгорнутий на будь-якому WSGI-сервері без зміни жодного рядка коду.
- До стандартної бібліотеки Python 2.5 увійшов модуль `wsgiref`, який надав референсну реалізацію WSGI-сервера (`wsgiref.simple_server`) та набір валідаторів для тестування.

## 3. Перехід на Python 3: PEP 3333 (2010)

Перехід мови на Python 3 виявив серйозну проблему в початковій специфікації PEP 333, зумовлену зміною моделі рядків.

У Python 2 тип `str` був послідовністю сирих байтів, а `unicode` — послідовністю символів. У Python 3 тип `str` став строго текстовим (Unicode), а для сирих байтів було введено тип `bytes`. Виникло питання: чим мають бути змінні в `environ` (заголовки, URL-шляхи) та тіло HTTP-відповіді?

У 2010 році було прийнято оновлений стандарт [PEP 3333 — Python Web Server Gateway Interface v1.0.1](https://peps.python.org/pep-3333/), який закріпив строгі правила типізації:
- **Тіло запиту та відповіді:** строго двійкові дані `bytes`. Потік `wsgi.input` повертає `bytes`, а ітерований об'єкт застосунку повертає `iterable[bytes]`.
- **Ключі та значення `environ`:** рядки типу `str`.
- **Правило кодування заголовків:** оскільки протокол HTTP/1.1 історично базувався на 8-бітних рядках, WSGI-сервер зобов'язаний декодувати сирі байти заголовків та `PATH_INFO` у рядки `str` за допомогою кодування **Latin-1 (ISO-8859-1)**, яке забезпечує взаємно-однозначне відображення байтів 0x00–0xFF у перші 256 код-пойнтів Unicode без помилок декодування. Застосунки, що очікують UTF-8 у тілі чи заголовках, мають самостійно виконати повторне кодування/декодування за потреби.

## 4. Обмеження WSGI та перехід до ASGI (2018 — сучасність)

Незважаючи на успіх, архітектурна модель WSGI була розрахована виключно на синхронну парадигму обробки: «один запит — одна блокувальна відповідь у виділеному потоці чи процесі».

З розвитком протоколів **WebSocket**, тривалих HTTP-підключень (Server-Sent Events, HTTP Long Polling) та появою нативної асинхронності в Python 3.5 (`async`/`await`, модуль `asyncio`) проявилися фундаментальні обмеження WSGI:
1. Потік сервера виявлявся заблокованим на весь час життя довгого WebSocket-з'єднання, утримуючи системні ресурси.
2. WSGI не підтримував одночасне отримання та надсилання повідомлень (повнодуплексний режим).
3. Відсутня інтеграція з асинхронним циклом подій `asyncio.get_event_loop()`.

Для вирішення цих викликів команда розробників Django на чолі з Ендрю Годвіном (Andrew Godwin) розробила специфікацію **ASGI (Asynchronous Server Gateway Interface)**. ASGI замінив синхронний виклик `app(environ, start_response)` на асинхронну корутину:

```python
async def application(scope, receive, send):
    ...
```

ASGI став стандартом де-факто для сучасного асинхронного вебу в Python, на базі якого працюють такі високопродуктивні сервери, як **Uvicorn** і **Hypercorn**, та фреймворки **FastAPI**, **Starlette** і **Litestar**, тоді як класичний WSGI залишається надійним фундаментом для синхронних корпоративних систем на Django та Flask.
