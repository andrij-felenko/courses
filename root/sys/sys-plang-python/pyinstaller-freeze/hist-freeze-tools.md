# 📜 Від freeze.py до PyInstaller, Nuitka та PyOxidizer

Ідея перетворення динамічного скрипта мовою Python на автономний виконуваний двійковий файл виникла майже одночасно з появою самої мови. У стандартному робочому процесі інтерпретатор CPython вимагає наявності встановленого системного середовища: виконуваного файлу `python`, файлів стандартної бібліотеки, розширень `.so` чи `.dll` та сторонніх бібліотек у каталозі `site-packages`. Для розробників, які постачали комерційні або настільні утиліти кінцевим користувачам без досвіду системного адміністрування, потреба змушувати клієнта власноруч встановлювати інтерпретатор і збирати залежності через термінал створювала нездоланний бар'єр.

Еволюція інструментів заморожування застосунків пройшла три чіткі етапи: від примітивної компіляції байткоду в масиви мови C до створення саморозпаковних контейнерів із завантажувачем, і зрештою — до безпосередньої трансляції в машинний код та завантаження образів із оперативної пам'яті.

## 1. Перша генерація: утиліта freeze.py та статичні масиви C (1995)

У 1995 році творець мови Гвідо ван Россум (Guido van Rossum) включив до складу сирцевого дерева CPython утиліту `Tools/freeze/freeze.py`. Її робота ґрунтувалася на простому, але жорсткому механізмі:

1. Утиліта аналізувала вхідний скрипт і будувала повний граф модулів, необхідних для його роботи.
2. Кожен знайдений `.py`-файл компілювався у стандартний байткод CPython.
3. Отриманий масив байтів серіалізувався у вихідний код мовою C як статичний масив `unsigned char` через внутрішню структуру CPython `struct _frozen`.
4. Генерувався допоміжний файл `frozenmain.c`, де оголошувалася таблиця `PyImport_FrozenModules` і викликалася функція `Py_FrozenMain()`.
5. Локальний компілятор C (наприклад, `gcc`) компілював згенеровані файли і компонував їх зі статичною бібліотекою інтерпретатора `libpython.a`.

```
[ Скрипт app.py ] ──> [ Байткод .pyc ] ──> [ Масив C: unsigned char M_app[] ]
                                                    │
                                                    ▼
[ Сирці CPython: libpython.a ] ───────────> [ Компілятор C / Лінкер ]
                                                    │
                                                    ▼
                                          [ Бінарний файл app ]
```

Підхід `freeze.py` створював справжній монолітний виконуваний файл, проте мав критичні недоліки. Він вимагав наявності компілятора мови C та статичної версії `libpython.a` на машині розробника. Будь-які C-розширення (наприклад, модулі для роботи з базами даних чи графікою) мали компілюватися статично, що було вкрай складно реалізувати на операційній системі Windows. Крім того, інструмент не мав механізму додавання довільних файлів даних (іконок, конфігурацій, сертифікатів).

## 2. Друга генерація: Gordon McMillan Installer та народження PyInstaller (1999–2005)

Наприкінці 1990-х років Гордон Макміллан (Gordon McMillan) запропонував принципово іншу архітектуру, створивши *McMillan Installer* (який згодом ліг в основу проєкту **PyInstaller**). Замість перекомпіляції інтерпретатора під кожен застосунок Макміллан запропонував розділити артефакт на два незалежних шари:

- **Універсальний скомпільований завантажувач (Bootloader):** невеликий двійковий файл на C, який уміє ініціалізувати вбудований інтерпретатор CPython, налаштовувати шляхи пошуку модулів `sys.path` та запускати точку входу.
- **Вбудований архів корисного навантаження (Archive):** стиснений контейнер `ZlibArchive` (PYZ), що містить байткод усіх модулів застосунку та стандартної бібліотеки, розміщений у кінці виконуваного файлу або у суміжній теці.

Ця архітектура позбавила розробника необхідності мати встановлений C-компілятор: розробники PyInstaller постачали попередньо скомпільовані бінарники завантажувача для всіх популярних платформ (Windows x86, Linux ELF, macOS Mach-O). Процес «заморожування» перетворився на чисте конструювання бінарного контейнера, де до готового завантажувача дописувався стиснений архів і таблиця змісту (TOC — Table of Contents).

Паралельно виникли спеціалізовані інструменти:
- **`py2exe`** (автор Марк Гаммонд, Mark Hammond): спеціалізований пакувальник для платформи Windows, що активно використовував специфіку PE-формату, вбудовував маніфести сумісності та підтримував створення служб Windows (Windows Services).
- **`py2app`** (автор Боб Іпполіто, Bob Ippolito): адаптація концепції для macOS зі створенням повноцінних бандлів `.app` з ресурсами, іконками `icns` та фреймворками.
- **`cx_Freeze`** (автор Ентоні Тунінга, Anthony Tuininga): кросплатформенний пакувальник, що зосередився на моделі One-Folder і прямому вбудовуванні динамічних бібліотек без розпакування у тимчасові каталоги.

У середині 2000-х років проєкт McMillan Installer був відроджений Джованні Баджо (Giovanni Bajo), Гартмутом Гебелем (Hartmut Goebel) та Браяном Джонсом (Bryan A. Jones) під сучасною назвою **PyInstaller**. Він став стандартом де-факто завдяки модульній системі «хуків» (Hooks) для автоматичного виявлення складних прихованих залежностей у великих екосистемах (PyQt, NumPy, SciPy, Cryptography).

## 3. Третя генерація: компіляція в нативний C++ (Nuitka) та завантаження з пам'яті (PyOxidizer)

Попри зручність PyInstaller, класичне заморожування у формат One-File мало два вроджених обмеження: високі накладні витрати часу на розпакування файлів у тимчасовий каталог `_MEIxxxxxx` під час кожного старту та повну відсутність захисту коду (байткод `.pyc` легко видобувається з архіву стандартними утилітами декомпіляції). Це спонукало до появи інструментів нового покоління:

### Nuitka (2010+)
Проєкт, створений Кеєм Гаєном (Kay Hayen), відмовився від пакування інтерпретатора з архівом байткоду. Nuitka є повноцінним транслятором:
- Код Python транслюється в оптимізований вихідний код мовою C++, де операції з об'єктами перетворюються на прямі виклики Python/C API.
- Отриманий C++ компілюється через GCC, Clang або MSVC у нативний двійковий модуль або автономний виконуваний файл.
- Застосунок позбувається потреби інтерпретувати інструкції віртуальної машини для власного коду, що збільшує швидкість виконання на 10–400% і суттєво ускладнює зворотну розробку (Reverse Engineering).

### PyOxidizer (2019+)
Розроблений Грегорі Шорцем (Gregory Szorc), PyOxidizer переосмислив завантаження інтерпретатора за допомогою мови Rust:
- Інтерпретатор CPython статично лінкується всередину двійкового файлу на Rust.
- Модулі Python, спільні бібліотеки та ресурси зберігаються у пам'яті двійкового файлу в спеціальному оптимізованому форматі.
- Використовуючи кастомний завантажувач модулів на базі C API (`PyImport_ExtendInittab` та прямий мапінг пам'яті через `mmap`), PyOxidizer імпортує модулі **безпосередньо з оперативної пам'яті** без розпакування жодного файлу на диск.
- Завдяки цьому досягається рекордна швидкість холодного запуску застосунку та усуваються проблеми з блокуванням файлів антивірусними сканерами у каталозі `%TEMP%`.

```
+------------------+-----------------------+------------------------+-----------------------+
| Критерій         | PyInstaller           | Nuitka                 | PyOxidizer            |
+------------------+-----------------------+------------------------+-----------------------+
| Мова завантажувача| C                     | C++                    | Rust                  |
| Формат коду      | Байткод CPython (.pyc)| Скомпільований C++     | Байткод або C-мапінг  |
| Потрібен C-компіл| Ні (готові бінарники) | Так (GCC/Clang/MSVC)   | Так (Rust Toolchain)  |
| Розпакування на ди| Так (у режимі onefile)| Опційно                | Ні (імпорт із пам'яті)|
| Захист коду      | Мінімальний (є .pyc)  | Високий (машинний код) | Середній (у пам'яті)  |
| Швидкість старту | Повільна (--onefile)  | Висока                 | Миттєва               |
+------------------+-----------------------+------------------------+-----------------------+
```

Розвиток інструментів пакування відображає постійний пошук компромісу між простотою збирання, швидкістю запуску та автономністю кінцевого бінарного артефакту в операційній системі.
