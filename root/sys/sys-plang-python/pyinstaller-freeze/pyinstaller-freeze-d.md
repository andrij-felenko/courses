Коли користувач запускає настільний застосунок або системну утиліту, написану мовою Python, операційна система не може виконати вихідні файли `.py` безпосередньо процесором. Звичайний сценарій виконання передбачає, що на цільовій машині вже встановлено сумісну версію інтерпретатора CPython, системні динамічні бібліотеки `libpython`, а в каталозі `site-packages` розгорнуто всі транзитивні сторонні пакети з відповідними скомпільованими C-розширеннями. Якщо цільова система не має встановленого Python або версії локальних пакетів конфліктують із вимогами програми, запуск завершується аварійною помилкою імпорту. Заморожування застосунку (англ. *freezing*) перетворює дерево вихідного коду, скомпільований байткод, інтерпретатор CPython, усі залежні динамічні бібліотеки та статичні ресурси на єдиний самодостатній двійковий файл, який запускається без будь-яких попередніх вимог до оточення хоста.

Такий автономний двійковий артефакт називається **замороженим застосунком** (*Frozen Application*, від лат. *applicatio* — «приєднання, застосування» та англ. *freeze* — «заморожувати», від давньоангл. *freosan*).

## 1. Спектр автономності: скрипт, заморожений бінарник, транспільований код

Щоб обрати правильний спосіб постачання програми, необхідно розуміти архітектурну різницю між чотирма основними моделями дистрибуції коду в екосистемі Python:

```
[ Сирцевий скрипт (.py) ]
       │  (Потребує хостовий Python, pip, venv, компілятор для розширень)
       ▼
[ Заморожений застосунок (PyInstaller, cx_Freeze) ]
       │  (Вбудований CPython + PYZ-архів байткоду + спільні бібліотеки .so/.dll)
       ▼
[ Транспільований машинний код (Nuitka) ]
       │  (Python AST -> C++ -> GCC/MSVC -> нативний двійковий файл)
       ▼
[ Монолітний образ у пам'яті (PyOxidizer) ]
          (CPython статично лінкується у двійковий файл на Rust, імпорт суто з RAM)
```

1. **Вихідний скрипт у віртуальному середовищі (`venv` + `pip`):** Традиційна модель для серверної розробки та дата-сайєнсу. Код постачається як текст або wheel-пакети. Вся відповідальність за конфігурацію середовища покладається на системного адміністратора чи сценарій Dockerfile.
2. **Заморожений двійковий бандл (PyInstaller, cx_Freeze):** Байткод усіх модулів пакується в стиснений архів, який об'єднується зі скомпільованим двійковим завантажувачем і динамічними бібліотеками CPython. Інтерпретатор виконує байткод у звичайному режимі, проте всі компоненти ізольовані всередині контейнера.
3. **Транспіляція в нативний код (Nuitka):** Вихідний код мовою Python транслюється у вихідний код мовою C++, оптимізується на рівні C API та компілюється системним компілятором у машинний код цільової архітектури. Це забезпечує захист інтелектуальної власності та приріст швидкодії.
4. **Вбудовування в монолітний рантайм на Rust (PyOxidizer):** Інтерпретатор CPython компілюється як статична бібліотека всередину двійкового файлу на Rust. Усі модулі Python та C-розширення упаковуються в оптимізований блок пам'яті і підвантажуються безпосередньо з RAM через системний виклик `mmap` без розпакування на диск.

Детальний аналіз історичного шляху від першої утиліти `freeze.py` 1995 року до сучасних систем викладено у вставці [Історія еволюції інструментів заморожування: від freeze.py до PyOxidizer](root:sys-plang-python/pyinstaller-freeze/hist-freeze-tools.md).

```
+---------------------------+-----------------------------------+-----------------------------------+
| Властивість               | Скрипт у середовищі (Script/Venv) | Заморожений двійковий файл (Freeze)|
+---------------------------+-----------------------------------+-----------------------------------+
| Вимоги до цільової ОС     | Встановлений Python, libc, headers| Лише сумісне ядро ОС та libc      |
| Час холодного запуску     | 50–200 мс                         | 300–2500 мс (залежно від onefile) |
| Розмір кінцевого артефакту| Кілька кілобайтів (без venv)      | 30–300 Мегабайтів                 |
| Зручність оновлення       | `git pull` або `pip install -U`   | Заміна всього бінарного файлу     |
| Читабельність коду        | Відкритий текст .py               | Байткод .pyc у zip-архіві         |
| Портативність між ОС      | Висока (якщо чистий Python)       | Нульова (бінарник під конкретну ОС|
+---------------------------+-----------------------------------+-----------------------------------+
```

## 2. Анатомія замороженого файлу: завантажувач, PYZ-архів і корисне навантаження

Щоб зрозуміти внутрішню організацію скомпільованого виконуваного файлу, розглянемо його двійкову топологію у режимі створення єдиного файлу (`--onefile` у PyInstaller).

![Анатомія замороженого двійкового файлу](/root/sys/sys-plang-python/pyinstaller-freeze/img/frozen-executable-anatomy.svg)
*Структурна організація двійкового виконуваного файлу: завантажувач на C, таблиця змісту, динамічні бібліотеки, стиснений архів байткоду PYZ та кінцева мітка зміщення.*

Двійковий файл формується шляхом зшивання п'яти послідовних блоків даних:

1. **Двійковий завантажувач (Bootloader):** Скомпільований виконуваний файл мовою C (у форматі ELF для Linux, PE/COFF для Windows або Mach-O для macOS). Він містить нативну точку входу процесу `main()` або `WinMain()`, логіку читання власного двійкового образу, розпакування компонентів та виклики функцій Python/C API (`Py_InitializeFromConfig`, `PyRun_SimpleString`).
2. **Таблиця змісту (Table of Contents / TOC):** Серіалізований список усіх вбудованих компонентів. Кожен запис TOC містить назву файлу, початкове зміщення (байт-офсет) відносно початку архіву, розмір у стисненому та розпакованому вигляді, тип ресурсу (спільна бібліотека, байткод, файл даних) та алгоритм стиснення.
3. **Спільні динамічні бібліотеки та C-розширення:** Скомпільовані бінарні модулі, необхідні для роботи інтерпретатора та сторонніх пакетів:
   - Бібліотека рантайму `libpython3.x.so` (Linux), `python3x.dll` (Windows) або `Python.framework` (macOS).
   - Скомпільовані модулі C-розширень стандартної бібліотеки (`_ssl`, `_socket`, `_sqlite3`, `_ctypes`, `math`).
   - Сторонні динамічні бібліотеки, від яких залежать модулі (наприклад, `libssl.so`, `libcrypto.so`, DLL-бібліотеки OpenCV чи системні драйвери баз даних).
4. **Архів байткоду (PYZ / ZlibArchive):** Спеціалізований стиснений контейнер, що містить виключно скомпільований **байткод** (англ. *bytecode*, від англ. *byte* — одиниця даних, та лат. *codex* — «звід законів, книга») усіх чисто пітонівських модулів стандартної бібліотеки та вихідного коду проєкту. Сирцеві тексти `.py` у фінальний архів не потрапляють — замість них зберігаються маршалізовані об'єкти коду (*code objects*) у форматі `.pyc`.
5. **Файли даних та ресурсів:** Конфігураційні файли (YAML, JSON), SSL-сертифікати (`cacert.pem`), шаблони Jinja2, графічні ресурси (PNG, SVG) та шрифти, явно оголошені розробником.
6. **Кінцева службова мітка (Cookie / Archive Trailer):** Останні байти файлу (зазвичай 64 або 96 байтів), які містять сигнатуру `MEI\014\013\012\013\016`, версію структури пакувальника та 64-бітне ціле число, що вказує на точне зміщення таблиці TOC від початку або кінця файлу.

### Механіка самоінспекції завантажувача

Коли ядро операційної системи створює процес, завантажувач повинен знайти власні зашиті ресурси. Для цього він визначає абсолютний шлях до власного виконуваного файлу на диску за допомогою системних інтерфейсів:

- **Linux:** Читання символьного посилання `/proc/self/exe` через системний виклик `readlink()`.
- **Windows:** Виклик функції Win32 API `GetModuleFileNameW(NULL, buffer, size)`.
- **macOS:** Виклик функції `_NSGetExecutablePath()`.

Після отримання дескриптора власного бінарного файлу завантажувач відкриває його у режимі бінарного читання (`fopen(self_path, "rb")`), переміщує файловий вказівник у самий кінець файлу за допомогою виклику `fseek()` і вичитує службову мітку (Trailer). Отримавши зміщення TOC, завантажувач зчитує зміст архіву в оперативну пам'ять і переходить до розгортання рантайму.

Повний робочий прототип автономного завантажувача на мовах C та C++ з використанням ізольованої конфігурації `PyConfig` наведено у вставці [Реалізація мінімального C/C++ завантажувача CPython](root:sys-plang-python/pyinstaller-freeze/proj-mini-bootloader.md).

## 3. Режими роботи: One-Folder проти One-File та їхня системна ціна

Пакувальник підтримує два принципово відмінні режими формування кінцевого артефакту: створення теки з файлами (`--onedir` або `-D`) та пакування в єдиний виконуваний файл (`--onefile` або `-F`).

![Порівняння життєвого циклу One-Folder та One-File](/root/sys/sys-plang-python/pyinstaller-freeze/img/onedir-vs-onefile-lifecycle.svg)
*Послідовність виконання застосунку: прямий запуск із каталогу (One-Folder) проти видобування у тимчасову теку _MEIxxxxxx (One-File).*

### Режим One-Folder (`--onedir`)

У режимі One-Folder результатом збирання є звичайний каталог файлової системи (наприклад, `dist/my_app/`), всередині якого розміщено:
- Головний виконуваний бінарник `my_app` (або `my_app.exe`).
- Системний підкаталог (у сучасних версіях PyInstaller це `_internal/`), куди винесено `libpython`, усі спільні об'єкти `.so`/`.pyd`/`.dll`, архів байткоду `base_library.zip` та ресурси даних.

Життєвий цикл One-Folder відзначається максимальною простотою:
1. ОС завантажує бінарник у пам'ять.
2. Завантажувач додає шлях до каталогу `_internal` у системні шляхи завантажувача динамічних бібліотек (`SetDllDirectoryW` у Windows або внутрішній `DT_RPATH`/`DT_RUNPATH` у заголовку ELF на Linux).
3. Завантажувач ініціалізує інтерпретатор і передає керування точці входу.

**Переваги:** Миттєвий старт без накладних витрат на дисковий ввід/вивід; легке налагодження (можна вручну замінити конфігураційний файл або оновити окрему динамічну бібліотеку); коректна робота антивірусного програмного забезпечення.
**Недоліки:** Необхідність постачати застосунок у вигляді ZIP-архіву чи інсталятора (Inno Setup, NSIS, MSI), оскільки переміщення окремого бінарника без сусіднього каталогу `_internal` ламає пошук бібліотек.

### Режим One-File (`--onefile`)

У режимі One-File весь вміст каталогу стискається і зашивається безпосередньо у тіло виконуваного файлу. Кожен запуск такого файлу ініціює повний цикл тимчасового розгортання:

1. **Створення унікального каталогу:** Завантажувач створює тимчасову теку з префіксом `_MEI` та випадковим суфіксом (наприклад, `/tmp/_MEIa8X12q` у Linux або `C:\Users\User\AppData\Local\Temp\_MEI149202` у Windows).
2. **Розпакування двійкових залежностей:** Завантажувач вичитує стиснені блоки з власного файлу, розпаковує через алгоритм `zlib` усі файли `.so`, `.dll`, `.pyd` та ресурси даних і записує їх на фізичний диск у щойно створену теку `_MEIxxxxxx`.
3. **Налаштування середовища:** Завантажувач встановлює змінну оточення `LD_LIBRARY_PATH` або викликає `SetDllDirectoryW`, встановлює атрибути `sys.frozen = True` та `sys._MEIPASS = "/path/to/_MEIxxxxxx"`.
4. **Виконання:** Завантажується `libpython`, монтується PYZ-архів байткоду, стартує головний скрипт.
5. **Очищення (Cleanup):** При виході з програми завантажувач перехоплює завершення процесу і рекурсивно видаляє каталог `_MEIxxxxxx` разом із усім його вмістом.

### Системна ціна та приховані проблеми режиму One-File

Хоча режим One-File є привабливим завдяки зручності передачі одного файлу клієнту, він створює серйозні експлуатаційні проблеми у виробничому середовищі:

#### 1. Деградація часу холодного старту (I/O Bottleneck)
Якщо застосунок містить важкі наукові пакети чи GUI-фреймворки (PyQt6, PySide6, Torch, TensorFlow, SciPy), розмір розпакованих бінарних файлів сягає 150–400 МБ. На звичайних жорстких дисках (HDD) або повільних мережевих дисках розпакування сотень двійкових файлів під час кожного кліку займає від 3 до 10 секунд процесорного часу.

#### 2. Засмічення накопичувача «зомбі-каталогами» (_MEI Leaks)
Завантажувач видаляє теку `_MEIxxxxxx` лише за умови **коректного штатного завершення процесу**. Якщо процес зазнає аварійної зупинки з фатальною системною помилкою (*Segmentation fault*), буде примусово завершений диспетчером завдань або сигналом `SIGKILL` (`kill -9`), або якщо користувач вимкне живлення комп'ютера, код очищення завантажувача взагалі не встигне виконатися. З часом у каталозі `%TEMP%` або `/tmp` накопичуються десятки гігабайтів покинутих каталогів `_MEI`, що призводить до вичерпання дискового простору чи дескрипторів інодів (*inodes*).

#### 3. Помилкові спрацьовування антивірусів (False Positives)
Поведінка, коли виконуваний файл під час старту створює прихований виконуваний двійковий файл у каталозі `%TEMP%` і намагається динамічно завантажити звідти спільні бібліотеки, збігається з класичним поведінковим патерном троянських дропперів (*Trojan Droppers*). Евристичні сканери антивірусів (Windows Defender, CrowdStrike, SentinelOne) нерідко блокують заморожені застосунки одразу після старту, видаючи сповіщення на кшталт `Heur.Bzc`.

## 4. Виявлення залежностей: статичний аналіз AST, хуки та динамічні імпорти

Найскладніше інженерне завдання пакувальника полягає у визначенні повного переліку модулів, які необхідно включити у фінальний бінарник.

![Конвеєр виявлення залежностей і компонування](/root/sys/sys-plang-python/pyinstaller-freeze/img/dependency-analysis-pipeline.svg)
*Етапи збирання: статичний розбір AST-дерева, обробка правил динамічних хуків, збір спільних бібліотек та генерація виконуваного файлу.*

### Статичний аналіз через модуль `modulegraph`

Пакувальник аналізує вхідні файли за допомогою статичного парсингу синтаксичного дерева (**AST** — від грец. *σύνταξις* (*syntaxis*) — «побудова, упорядкування»). Сканер рекурсивно шукає вузли `ast.Import` та `ast.ImportFrom`:

```python
import os                       # Виявлено: модуль 'os'
from urllib.parse import urlparse # Виявлено: модуль 'urllib.parse'
```

Сканер будує орієнтований граф залежностей: якщо модуль `A` імпортує `B`, а `B` імпортує `C`, усі три модулі потрапляють до списку включення в PYZ-архів.

### Пастка динамічних імпортів (Dynamic Import Trap)

Статичний аналізатор безсилий проти конструкцій, де ім'я модуля обчислюється динамічно під час виконання:

```python
# Статичний аналізатор AST не може знати значення змінної driver_name:
driver_name = config.get("database_driver") # Наприклад, "psycopg2"
db_module = importlib.import_module(driver_name)

# Реєстрація плагінів через рядкові імена:
plugin = __import__(f"plugins.{plugin_name}")
```

Якщо модуль `psycopg2` не згадується у відкритому вигляді через інструкцію `import psycopg2`, статичний аналізатор пропустить його. У результаті бінарник успішно збереться, але впаде у клієнта під час виконання з помилкою `ModuleNotFoundError: No module named 'psycopg2'`.

### Механізм хуків (Hooks Architecture)

Для вирішення проблеми динамічних імпортів PyInstaller використовує систему **хуків** (англ. *hook* — «гачок», від прагерм. *hokaz* — «вигин, перехоплювач»). Хук — це ізольований скрипт із назвою `hook-<package_name>.py`, який містить декларативні інструкції про те, які приховані модулі, C-бібліотеки та файли даних потрібно обов'язково додати в бандл при виявленні цього пакета.

```python
# Приклад хука: hook-sqlalchemy.py
from PyInstaller.utils.hooks import collect_submodules, collect_data_files

# 1. Примусово підтягнути всі можливі бекенди діалектів SQL
hiddenimports = collect_submodules('sqlalchemy.dialects')

# 2. Додати метадані та сертифікати
datas = collect_data_files('sqlalchemy')
```

Офіційний репозиторій PyInstaller містить сотні попередньо налаштованих хуків для популярних бібліотек (Matplotlib, Pandas, Cryptography, Boto3, Qt, OpenSSL). Розробник також може писати власні проєктні хуки і вказувати шлях до них у `.spec`-файлі або передавати приховані імпорти через прапорець командного рядка:

```bash
pyinstaller --onefile --hidden-import="sqlalchemy.dialects.sqlite" src/main.py
```

### Внутрішній ланцюг завантажувальних модулів (Bootstrap Modules)

Щоб інтерпретатор зміг працювати з архівом безпосередньо у пам'яті, PyInstaller вбудовує три системні модулі попередньої ініціалізації:
1. `pyimod01_os_path.pyc`: забезпечує базові маніпуляції зі шляхами до того, як стандартні модулі `os` та `posixpath` будуть завантажені з PYZ.
2. `pyimod02_importers.pyc`: встановлює в `sys.meta_path` кастомний шукач `PyZlibArchiveLoader`, який перехоплює виклики імпорту байткоду з вбудованого PYZ-архіву.
3. `pyimod03_ctypes.pyc`: перевизначає функцію завантаження бібліотек у `ctypes.CDLL`, автоматично додаючи шлях `sys._MEIPASS` до стандартних каталогів пошуку спільних об'єктів.

### Додавання бінарних бібліотек та статичних файлів

Якщо застосунок використовує сторонні бібліотеки, скомпільовані на C/C++ чи Rust (наприклад, `libcustom_driver.so` або `native_wrapper.dll`), або потребує статичних ресурсів (іконки, конфігурації, шрифти), їх необхідно явно передати через параметри `--add-binary` та `--add-data`:

```bash
# Синтаксис: "джерело:цільова_тека_всередині_бандла" (у Windows роздільник крапка з комою ';')
pyinstaller --onefile \
  --add-data "config/app_config.yaml:config" \
  --add-data "assets/logo.png:assets" \
  --add-binary "vendor/libengine.so:." \
  src/main.py
```

Детальний довідник класів конфігураційного файла `.spec` та публічного API бібліотеки утиліт хуків наведено у вставці [Специфікація .spec та API хуків PyInstaller](root:sys-plang-python/pyinstaller-freeze/api-pyinstaller-spec.md).

## 5. Рантайм-середовище замороженого процесу: sys.frozen, sys._MEIPASS та доступ до ресурсів

Після успішного старту завантажувача інтерпретатор CPython опиняється в модифікованому системному стані. Щоб застосунок міг коректно визначати своє місцезнаходження, завантажувач інжектує в простір імен модуля `sys` спеціальні атрибути:

- **`sys.frozen = True`:** Булевий прапорець, який сигналізує програмі, що вона виконується у замороженому стані, а не запускається інтерпретатором зі звичайного файлу `.py`.
- **`sys._MEIPASS`:** Рядок із абсолютним шляхом до каталогу, де розміщено розпаковані ресурси. У режимі One-File це шлях до тимчасової теки `_MEIxxxxxx`, а в режимі One-Folder — шлях до каталогу застосунку або його підкаталогу `_internal`.
- **`sys.executable`:** Абсолютний шлях до самого скомпільованого двійкового файлу `app` чи `app.exe` на диску (а не до системного `python3`).

### Пастка багатопроцесорності у Windows (`multiprocessing.freeze_support`)

На операційних системах сімейства Windows системний виклик `fork()` відсутній. Коли програма створює дочірній процес через стандартний модуль `multiprocessing.Process()`, Python запускає новий примірник виконуваного файлу `sys.executable`, передаючи йому спеціальні службові аргументи командного рядка (наприклад, `--multiprocessing-fork`).

У замороженому застосунку цим двійковим файлом є сам завантажувач `app.exe`. Якщо на початку головного скрипта відсутній виклик `multiprocessing.freeze_support()`, дочірній процес не розпізнає службові аргументи і почне заново виконувати головний скрипт програми з першого рядка. Це призводить до катастрофічної неконтрольованої ланцюгової реакції: кожен новий процес породжує сотні нових копій самого себе («форк-бомба»), повністю вичерпуючи пам'ять та ресурси процесора за лічені секунди.

```python
import multiprocessing
import sys

def worker_task(task_id: int):
    print(f"Обробка задачі {task_id} у дочірньому процесі")

if __name__ == "__main__":
    # КРИТИЧНО для заморожених застосунків на Windows/macOS:
    multiprocessing.freeze_support()

    # Подальша безпечна робота з пулом процесів:
    processes = [multiprocessing.Process(target=worker_task, args=(i,)) for i in range(4)]
    for p in processes: p.start()
    for p in processes: p.join()
```

### Пастка некоректного визначення шляхів через `__file__`

Класичний пітонівський патерн знаходження ресурсів через атрибут `__file__` у замороженому застосунку поводиться небезпечно:

```python
# НЕБЕЗПЕЧНО у замороженому застосунку:
base_dir = os.path.dirname(os.path.abspath(__file__))
config_path = os.path.join(base_dir, "config.yaml")
```

У замороженому коді модулі читаються з віртуального PYZ-архіву, тому значення `__file__` може містити внутрішній віртуальний шлях усередині архіву (наприклад, `my_module.pyc`), за яким операційна система не зможе відкрити реальний фізичний файл з конфігурацією.

### Надійний патерн безпечного доступу до ресурсів

Коректний підхід полягає у перевірці атрибута `sys.frozen` та використанні модуля `pathlib.Path`:

```python
import sys
from pathlib import Path

def get_bundle_dir() -> Path:
    """
    Повертає базовий каталог розпакованих або локальних ресурсів застосунку.
    Працює однаково надійно у сирцевому режимі (.py), у режимі --onedir та --onefile.
    """
    if getattr(sys, "frozen", False) and hasattr(sys, "_MEIPASS"):
        # Режим замороженого файлу (PyInstaller): повертаємо тимчасову теку _MEI
        return Path(sys._MEIPASS)
    
    # Звичайний режим виконання через python main.py
    return Path(__file__).resolve().parent

def resolve_asset_path(relative_asset_path: str) -> Path:
    """Знаходить вшитий файл ресурсів (зображення, сертифікат, шаблон)."""
    target = get_bundle_dir() / relative_asset_path
    if not target.exists():
        raise FileNotFoundError(f"Вбудований ресурс не знайдено: {target}")
    return target
```

### Заборона запису у каталог `sys._MEIPASS`

Критична помилка багатьох розробників — спроба зберігати змінювані файли (бази даних SQLite, лог-файли, налаштування користувача) за відносними шляхами всередині `sys._MEIPASS`. 

У режимі One-File будь-які зміни, записані в `_MEIxxxxxx`, **будуть безповоротно знищені** під час закриття програми разом із видаленням тимчасової теки. Наступний запуск створить абсолютно нову порожню теку `_MEIyyyyyy`, і всі збережені дані користувача буде втрачено.

Змінювані файли конфігурації та призначені для запису дані обов'язково повинні розміщуватися у стандартних системних каталогах профілю користувача:
- **Linux:** Каталог за специфікацією XDG Base Directory: `~/.config/my_app/` (налаштування) та `~/.local/share/my_app/` (дані).
- **Windows:** Каталог `%APPDATA%\my_app\` (`C:\Users\<User>\AppData\Roaming\my_app`).
- **macOS:** Каталог `~/Library/Application Support/my_app/`.

```python
import os
import sys
from pathlib import Path

def get_user_data_dir(app_name: str) -> Path:
    """Повертає постійний каталог для запису даних та конфігурацій користувача."""
    if sys.platform == "win32":
        base = Path(os.environ.get("APPDATA", Path.home() / "AppData" / "Roaming"))
    elif sys.platform == "darwin":
        base = Path.home() / "Library" / "Application Support"
    else:
        # Linux / POSIX стандарт XDG
        xdg_data = os.environ.get("XDG_DATA_HOME")
        base = Path(xdg_data) if xdg_data else Path.home() / ".local" / "share"
    
    app_dir = base / app_name
    app_dir.mkdir(parents=True, exist_ok=True)
    return app_dir
```

## 6. Виробничі підводні камені, захист інтелектуальної власності та сумісність ABI

Під час підготовки заморожених бінарників до промислової експлуатації виникає низка системних обмежень, які необхідно враховувати на етапі проєктування CI/CD-конвеєрів.

### Ілюзія захисту інтелектуальної власності

Поширена помилкова думка полягає в тому, що заморожування у двійковий `.exe` або ELF надійно захищає сирцевий код від копіювання чи декомпіляції. Це не так:
1. Двійковий завантажувач містить стандартний архів PYZ, який можна видобути з файлу за лічені секунди за допомогою відкритих утиліт (наприклад, `pyinstxtractor.py`).
2. Видобуті з PYZ файли байткоду `.pyc` містять повну структуру класів, імена функцій, сигнатури та інструкції віртуальної машини CPython.
3. Сучасні декомпілятори байткоду (як-от `pylingual`, `pycdc` або `uncompyle6`) відновлюють вихідний текст Python майже у первісному вигляді, включно зі структурою циклів та розгалужень.

Якщо бізнес-вимоги вимагають жорсткого захисту інтелектуальної власності, необхідно транспілювати критичні модулі бізнес-логіки в нативні бібліотеки C/C++ за допомогою **Cython** або **Nuitka**, перетворюючи код на справжні машинні інструкції до моменту пакування в PyInstaller.

### Стиснення UPX: компроміс між розміром та стабільністю

PyInstaller підтримує автоматичну інтеграцію з утилітою **UPX** (*Ultimate Packer for eXecutables*) — потужним пакувальником двійкових файлів. Застосування UPX зменшує розмір кінцевого бінарника на 30–60%. Проте використання UPX несе два суттєвих ризики:
- **Пошкодження C-розширення:** UPX іноді руйнує секції релокацій у складних динамічних бібліотеках (наприклад, у `vcruntime140.dll` під Windows або `.so`-файлах бібліотеки `cryptography`), внаслідок чого застосунок аварійно падає при спробі завантажити пошкоджену DLL. У файлі `.spec` такі бібліотеки обов'язково додають у винятки `upx_exclude=['vcruntime140.dll']`.
- **Посилення підозр антивірусів:** Стиснені через UPX бінарники сигнатурні сканери вважають ще більш підозрілими, оскільки пакувальник часто використовується авторами шкідливого ПЗ для приховування коду.

### Підписування коду та сертифікати безпеки (Code Signing & Notarization)

Сучасні операційні системи жорстко контролюють запуск невідомих бінарних файлів:
- **Windows SmartScreen:** Блокує запуск замороженого файлу з червоним попередженням «Windows захистила ваш комп'ютер», якщо двійковий файл не має цифрового підпису сертифікатом Authenticode (EV Code Signing).
- **macOS Gatekeeper та Нотаріація:** Операційна система macOS вимагає, щоб усі виконувані файли були підписані сертифікатом Apple Developer ID та пройшли перевірку на серверах Apple (Notarization). Для цього у файлі `.spec` налаштовуються параметри `codesign_identity` та `entitlements_file`, де обов'язково дозволяється виділення виконуваної пам'яті (`com.apple.security.cs.allow-unsigned-executable-memory`) для роботи вбудованого CPython.

### Сумісність glibc під час збирання під Linux

У середовищі Linux скомпільований бінарник завантажувача та динамічні бібліотеки `libpython` лінкуються з системною бібліотекою мови C — `glibc` ([Статичне й динамічне лінкування](root:sys-unix/static-and-dynamic-linking)). 

Стандартне правило динамічного завантажувача Linux: **двійковий файл, зібраний на новішій версії glibc, не може запуститися на старішій версії glibc**. Якщо ви збираєте PyInstaller-пакунок на сучасній робочій станції з Ubuntu 24.04 (де встановлено `glibc 2.39`), отриманий артефакт не запуститься на сервері з Ubuntu 20.04 або Debian 11 (де встановлено `glibc 2.31`), аварійно завершившись помилкою:

```
/lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.38' not found (required by ./my_app)
```

Щоб створити максимально портативний Linux-бінарник, процес збирання необхідно проводити всередині Docker-контейнера на базі старого сумісного дистрибутива (наприклад, AlmaLinux 8, Debian 10 або спеціалізованих образів `manylinux2014`). Скомпільований у такому середовищі завантажувач буде використовувати низьку версію символів glibc і гарантовано запуститься на будь-якому сучасному дистрибутиві Linux.

> 🔧 **Навіщо це.** Заморожування застосунку вирішує головну проблему дистрибуції — усуває необхідність узгодження системних залежностей на цільовому хості. Розуміння внутрішнього устрою завантажувача, механіки розпакування `_MEIPASS` та структури PYZ-архіву дозволяє створювати надійні настільні й серверні автономні інструменти, уникаючи пасток витоку пам'яті, аварійного очищення тимчасових каталогів та блокувань антивірусним захистом.
