# 📋 Специфікація збирання PyInstaller (.spec) та інтерфейс налаштування

Конфігураційний файл із розширенням `.spec` (англ. *specification* — «специфікація», від лат. *species* — «вид, зразок» та *facere* — «робити») є виконуваним сценарієм мовою Python, який визначає повний декларативний граф збирання автономного артефакту в PyInstaller. Коли користувач викликає утиліту `pyinstaller app.py`, збирач спершу автоматично генерує файл `app.spec` на основі переданих аргументів командного рядка, а потім виконує його через власний інтерпретатор для конструювання двійкового образу.

Пряме редагування `.spec`-файлу перетворює процес пакування з простого виклику консольної команди на керований інженерний конвеєр. Це дозволяє тонко керувати включенням динамічних бібліотек, додавати довільні дерева небінарних ресурсів, конфігурувати багатофайлові або багатомодульні збірки (наприклад, окремий клієнт і серверний фоновий демон в одному пакеті), виключати зайві системні пакети для оптимізації ваги та налаштувати права доступу чи сертифікати безпеки.

## 1. Архітектура та конвеєр класів конфігураційного графа

Специфікація PyInstaller будується як послідовний конвеєр трансформації артефактів за допомогою чотирьох фундаментальних класів: `Analysis`, `PYZ`, `EXE` та `COLLECT`. Кожен клас приймає результати роботи попереднього етапу, трансформує структури даних і передає їх далі за графом.

```python
# Приклад розширеного app.spec для комбінованого застосунку
# -*- mode: python ; coding: utf-8 -*-

from PyInstaller.utils.hooks import collect_data_files, collect_submodules, copy_metadata

block_cipher = None

# 1. ЕТАП: Статичний аналіз коду, парсинг AST та агрегація залежностей
a = Analysis(
    ['src/entrypoint.py'],
    pathex=['src'],
    binaries=[
        ('vendor/libcustom.so', '.')            # Кортеж: (вихідний шлях на хості, цільова тека в бандлі)
    ],
    datas=[
        ('config/*.yaml', 'config'),
        ('assets/logo.png', 'assets')
    ] + collect_data_files('certifi') + copy_metadata('cryptography'),
    hiddenimports=[
        'pkg_resources.py2_warn',
        'sqlalchemy.dialects.sqlite'
    ] + collect_submodules('my_plugins'),
    hookspath=['build_hooks'],
    hooksconfig={},
    runtime_hooks=['build_hooks/runtime_init.py'],
    excludes=['tkinter', 'unittest', 'pytest', 'matplotlib'],
    win_no_prefer_redirects=False,
    win_private_assemblies=False,
    cipher=block_cipher,
    noarchive=False
)

# 2. ЕТАП: Компіляція та компресія чистого Python-байткоду в PYZ-контейнер
pyz = PYZ(
    a.pure,
    a.zipped_data,
    cipher=block_cipher
)

# 3. ЕТАП: Компонування двійкового завантажувача з PYZ та прапорцями виконання
exe = EXE(
    pyz,
    a.scripts,
    [],
    exclude_binaries=True,                       # True для режиму onedir, False для режиму onefile
    name='my_application',
    debug=False,
    bootloader_ignore_signals=False,
    strip=False,                                # Видалення налагоджувальних символів через strip
    upx=True,                                   # Стиснення бінарників алгоритмом UPX
    upx_exclude=['vcruntime140.dll'],           # Виключення нестабільних DLL з UPX-компресії
    runtime_tmpdir=None,                        # Перевизначення базового каталогу для _MEIxxxxxx
    console=True,                               # Запуск у консолі (True) або прихований GUI-режим (False)
    disable_windowed_traceback=False,
    target_arch=None,
    codesign_identity=None,
    entitlements_file=None,
    icon='assets/app.ico'
)

# 4. ЕТАП: Формування кінцевого каталогу розгортання (використовується лише для --onedir)
coll = COLLECT(
    exe,
    a.binaries,
    a.zipfiles,
    a.datas,
    strip=False,
    upx=True,
    upx_exclude=[],
    name='my_application'
)
```

## 2. Довідник параметрів ключових класів збирання

### Клас `Analysis`
Клас `Analysis` виконує всю підготовчу аналітичну роботу. Він сканує вхідні сценарії, запускає синтаксичний парсер `modulegraph` для побудови повного дерева імпортів, виконує призначені хуки та формує списки файлів для пакування.

Він повертає об'єкт аналізу, що містить такі атрибути вихідних даних:
- `a.pure`: список чисто пітонівських модулів (файли `.py`), які будуть скомпільовані в байткод і запаковані в PYZ-архів.
- `a.binaries`: список динамічних спільних бібліотек (`.so`, `.dll`, `.dylib`, `.pyd`), які повинні фізично розміщуватися у файловій системі поряд із завантажувачем або розпаковуватися в `_MEIxxxxxx`.
- `a.datas`: список небінарних файлів (шаблони, сертифікати, конфігурації, іконки).
- `a.scripts`: головні виконувані сценарії запуску (*bootstrap scripts*).

| Параметр | Тип | Призначення та поведінка |
|---|---|---|
| `scripts` | `list[str]` | Список шляхів до вхідних файлів `.py`. Перший файл у списку визначає головну точку входу процесу. |
| `pathex` | `list[str]` | Список додаткових каталогів файлової системи, які додаються до шляху пошуку `sys.path` виключно на етапі аналізу залежностей. |
| `binaries` | `list[tuple[str, str]]` | Список кортежів `(source, dest_dir)`. Дозволяє явно підшити спільні бібліотеки та C-розширення, які не вдалося виявити автоматично. |
| `datas` | `list[tuple[str, str]]` | Список кортежів `(source, dest_dir)` для включення статичних файлів даних. Підтримує маски файлів на зразок `'config/*.json'`. |
| `hiddenimports` | `list[str]` | Список імен модулів, що імпортуються динамічно через виклики `importlib.import_module()` або `__import__()`. |
| `hookspath` | `list[str]` | Каталоги у файловій системі проєкту, де розміщено власні сценарії хуків `hook-<name>.py`. |
| `runtime_hooks` | `list[str]` | Скрипти, які виконуватимуться завантажувачем у рантаймі перед передачею керування головній точці входу (наприклад, для налаштування змінних оточення). |
| `excludes` | `list[str]` | Список модулів та пакетів, які примусово блокуються та виключаються з кінцевого артефакту заради оптимізації розміру (наприклад, тестові фреймворки `pytest`). |
| `noarchive` | `bool` | Якщо встановлено `True`, чисті модулі Python не упаковуються у PYZ-архів, а розкладаються окремими файлами у каталозі збірки. |

### Клас `PYZ`
Клас `PYZ` бере список чистих модулів `a.pure`, компілює їх у двійковий байткод (файли `.pyc`), застосовує компресію `zlib` та створює єдиний стиснений контейнер `ZlibArchive`. Завдяки цьому сотні дрібних файлів стандартної бібліотеки об'єднуються в один компактний блок, що мінімізує кількість операцій пошуку на файловій системі під час завантаження коду.

### Клас `EXE`
Клас `EXE` відповідає за створення фінального виконуваного файлу завантажувача. Він бере скомпільований бінарник завантажувача під цільову платформу, додає до нього іконку, ресурси версії Windows (VersionInfo), налаштовує параметри підсистеми ОС (консольний або графічний застосунок) та зшиває його з архівом PYZ.

| Параметр | Тип | Призначення та поведінка |
|---|---|---|
| `name` | `str` | Базове ім'я створюваного двійкового файлу (наприклад, `'my_tool'` або `'my_tool.exe'`). |
| `console` | `bool` | Якщо `True`, застосунок створюється для консольної підсистеми (відкриває термінал і передає потоки `stdin/stdout/stderr`). Якщо `False`, створюється віконний GUI-застосунок без консолі. |
| `icon` | `str` | Шлях до файлу іконки програми (`.ico` для Windows, `.icns` для macOS). |
| `strip` | `bool` | Якщо `True`, викликає системну утиліту `strip` для видалення налагоджувальних символів і таблиць імен із завантажувача та бібліотек на Linux. |
| `upx` | `bool` | Якщо `True`, застосовує бінарний компресор UPX для стиснення виконуваних секцій завантажувача та спільних бібліотек. |
| `upx_exclude` | `list[str]` | Список імен файлів та бібліотек, які заборонено стискати утилітою UPX через ризик пошкодження релокацій (наприклад, `vcruntime140.dll`). |
| `runtime_tmpdir` | `str \| None` | Вказує альтернативний шлях для розпакування тимчасової теки `_MEIxxxxxx` замість системного каталогу `/tmp` або `%TEMP%` у режимі One-File. |
| `bootloader_ignore_signals` | `bool` | Якщо `True`, завантажувач ігнорує системні сигнали переривання (наприклад, `SIGINT`), делегуючи їхню повну обробку інтерпретатору Python. |

### Клас `COLLECT`
Клас `COLLECT` використовується виключно в режимі формування теки (`--onedir`). Він збирає двійковий файл завантажувача, згенерований класом `EXE`, динамічні бібліотеки `a.binaries`, архів байткоду та файли даних `a.datas`, розкладаючи їх у деревоподібну структуру кінцевого каталогу розгортання `dist/<name>/`.

## 3. Публічний інтерфейс утиліт для створення хуків (`PyInstaller.utils.hooks`)

Створення надійних хуків для сторонніх бібліотек зі складною внутрішньою динамікою вимагає використання офіційного модульного API. Модуль `PyInstaller.utils.hooks` надає набір функцій-помічників:

### `collect_submodules(package_name: str, filter: Callable = None) -> list[str]`
Функція рекурсивно імпортує вказаний пакет у тимчасовому ізольованому процесі, обходить усе дерево його підкаталогів та повертає вичерпний перелік імен усіх виявлених підмодулів. Це головний інструмент для підтримки бібліотек із динамічною диспетчеризацією (наприклад, бекендів баз даних `sqlalchemy.dialects` чи драйверів `rasterio`).

### `collect_data_files(package_name: str, include_py_files: bool = False, subdir: str = None) -> list[tuple[str, str]]`
Знаходить усі несирцеві статичні ресурси всередині встановленого пакета (конфігураційні JSON-файли, кореневі сертифікати SSL, файли локалізації `.mo`, моделі машинного навчання, схеми валідації) і повертає їх у вигляді списку кортежів `(source_path, target_subfolder)`.

### `collect_dynamic_libs(package_name: str, dest: str = None) -> list[tuple[str, str]]`
Сканує каталог пакета на наявність скомпільованих бінарних модулів та динамічних бібліотек (`.so`, `.pyd`, `.dll`, `.dylib`) і повертає їх для включення у список `binaries`.

### `copy_metadata(package_name: str, recursive: bool = False) -> list[tuple[str, str]]`
Знаходить і копіює каталог системних метаданих встановленого дистрибутива (`<package>-<version>.dist-info`). Багато сучасних бібліотек (зокрема `importlib.metadata`, `pkg_resources`, `pydantic`, `transformers`) перевіряють власну версію та точки входу (*entry points*) через аналіз каталогу `.dist-info`. Без копіювання метаданих такі бібліотеки викидають виняток `PackageNotFoundError` під час запуску в замороженому стані.

### `is_module_satisfies(requirements: str) -> bool`
Перевіряє, чи встановлена в середовищі збирання версія модуля відповідає заданому діапазону вимог (наприклад, `'numpy >= 1.20.0'`). Дозволяє застосовувати різні правила пакування залежно від версії бібліотеки.

## 4. Відповідність між прапорцями CLI та декларативними полями .spec

Кожен аргумент командного рядка утиліти `pyinstaller` транслюється у відповідну конструкцію всередині згенерованого `.spec`-файлу:

| Прапорець командного рядка CLI | Еквівалентна конструкція у файлі .spec |
|---|---|
| `-F`, `--onefile` | `EXE(..., a.binaries, a.zipfiles, a.datas, exclude_binaries=False)` без виклику `COLLECT()` |
| `-D`, `--onedir` | `EXE(..., exclude_binaries=True)` із наступним викликом `COLLECT(...)` |
| `--add-data "src:dest"` | `Analysis(datas=[('src', 'dest'), ...])` |
| `--add-binary "src:dest"` | `Analysis(binaries=[('src', 'dest'), ...])` |
| `--hidden-import mod` | `Analysis(hiddenimports=['mod', ...])` |
| `-w`, `--windowed`, `--noconsole` | `EXE(console=False)` |
| `-c`, `--nowindowed`, `--console` | `EXE(console=True)` |
| `--exclude-module mod` | `Analysis(excludes=['mod', ...])` |
| `--runtime-tmpdir path` | `EXE(runtime_tmpdir='path')` |
| `--icon app.ico` | `EXE(icon='app.ico')` |
| `--runtime-hook hook.py` | `Analysis(runtime_hooks=['hook.py', ...])` |
| `--paths dir` | `Analysis(pathex=['dir', ...])` |

## 5. Диспетчеризація багатоцільових збірок (Multi-Target Spec Files)

Один файл `.spec` може описувати створення одразу кількох двійкових артефактів у межах одного прогону збирання. Типовий приклад у корпоративній розробці — одночасне створення графічного клієнта з віконним інтерфейсом (`client.exe`) та консольного серверного демона (`server.exe`), які використовують спільну бібліотеку бізнес-логіки та однаковий набір залежностей.

У такому сценарії створюється два об'єкти `Analysis`, два архіви `PYZ` та два виклики `EXE`, об'єднані в один каталог через `COLLECT`:

```python
# Багатоцільова збірка клієнта та демона в єдиному каталозі dist/my_suite/
a_client = Analysis(['src/client_main.py'], pathex=['src'], datas=[('assets/*', 'assets')])
pyz_client = PYZ(a_client.pure, a_client.zipped_data)
exe_client = EXE(pyz_client, a_client.scripts, exclude_binaries=True, name='client', console=False)

a_server = Analysis(['src/server_daemon.py'], pathex=['src'])
pyz_server = PYZ(a_server.pure, a_server.zipped_data)
exe_server = EXE(pyz_server, a_server.scripts, exclude_binaries=True, name='server', console=True)

coll = COLLECT(
    exe_client, a_client.binaries, a_client.zipfiles, a_client.datas,
    exe_server, a_server.binaries, a_server.zipfiles, a_server.datas,
    strip=False, upx=True, name='my_suite'
)
```

Такий підхід суттєво економить дисковий простір: динамічні бібліотеки `libpython`, DLL-файли та C-розширення розкладаються в спільний підкаталог `_internal`, і обидва двійкові завантажувачі повторно використовують спільні системні компоненти без дублювання.

## 6. Життєвий цикл Runtime Hooks (`runtime_hooks`)

Сценарії `runtime_hooks` виконуються двійковим завантажувачем у просторі інтерпретатора Python **до завантаження головної точки входу** застосунку. Вони є ключовим інструментом для виправлення поведінки сторонніх C-розширень, які покладаються на специфічні змінні оточення або системні шляхи.

Типові задачі, що вирішуються через runtime hooks:
- Встановлення змінної `os.environ["QT_PLUGIN_PATH"]` або `os.environ["PROJ_LIB"]` для вказування на розпаковані ресурси в каталозі `sys._MEIPASS`.
- Патчинг модуля `ssl` або `certifi` для спрямування пошуку кореневих CA-сертифікатів за адресою `os.path.join(sys._MEIPASS, "certifi", "cacert.pem")`.
- Реєстрація користувацьких перехоплювачів логування помилок або налаштування обробки сигналів переривання.

Використання файлу специфікації є обов'язковим для промислових проєктів, оскільки воно фіксує точні правила збирання в системі контролю версій Git і позбавляє розробників від потреби передавати десятки довгих параметрів у терміналі.
