Коли менеджер пакетів `pip` отримує команду встановити сторонню бібліотеку, наприклад `pip install cryptography`, перед клієнтською системою постає вибір між двома принципово відмінними форматами постачання коду: вихідним архівом або готовим двійковим пакунком. Якщо індекс пакунків повертає вихідний архів, процес інсталяції перетворюється на повний цикл компіляції: клієнтська машина мусить мати встановлений компілятор мови C або Rust, заголовні файли інтерпретатора `Python.h`, заголовні файли системних бібліотек на зразок `libssl-dev` та інструменти збирання. Якщо бодай один системний заголовок чи компілятор відсутній, встановлення негайно переривається аварійною помилкою компонування. Натомість двійковий пакунок містить уже скомпільовані спільні бібліотеки та байткод, розкладені за структурою кінцевого каталогу `site-packages`. Його встановлення не потребує запуску компілятора чи виконання коду на цільовій машині й зводиться до простого та безпечного розпакування архіву за лічені мілісекунди.

Ці два формати постачання звуться відповідно **sdist** (англ. *Source Distribution* — «розподіл вихідного коду», від лат. *distributio* — «розподіл, розміщення») та **wheel** (англ. *wheel* — «колесо», двійковий формат за стандартом PEP 427).

![Порівняння розгортання пакунка: вихідний архів (sdist) проти wheel (.whl)](/root/sys/sys-plang-python/wheels-and-sdist/img/sdist-vs-wheel.svg)
*Послідовність дій під час встановлення пакета: компіляція з вихідного архіву (sdist) проти прямого розпакування попередньо скомпільованого двійкового колеса (wheel).*

## 1. Два світи дистрибуції: вихідний код проти готового бінарного артефакту

Щоб зрозуміти механіку взаємодії менеджера пакетів із джерелом коду, необхідно простежити шлях файлів від моменту публікації автором до завантаження інтерпретатором у робочому середовищі.

Вихідний дистрибутив (`sdist`) є стисненим архівом — зазвичай із розширенням `.tar.gz` або `.zip` (від грец. *ἀρχεῖон* (*archeion*) — «державне сховище документів»). Він містить вихідні тексти модулів мовою Python, сирцевий код розширень мовами C, C++, Cython або Rust, маніфест проєкту `pyproject.toml` і допоміжні сценарії збирання. Головна властивість `sdist` — його **платформонезалежність на етапі зберігання**: один і той самий архів завантажується на сервер PyPI і може бути завантажений користувачем Linux на архітектурі x86_64, користувачем macOS на процесорі Apple Silicon (arm64) чи розробником під Windows.

Проте за універсальність вихідного архіву доводиться платити високу ціну на етапі розгортання:
1. **Наявність повного інструментарію збирання (Toolchain):** цільова операційна система повинна мати сумісні компілятори (`gcc`, `clang`, `msvc`, `rustc`), збирачі (`make`, `ninja`, `cmake`), а також системні бібліотеки розробки (Headers). На серверах виробничого середовища (Production) та у мінімалістичних контейнерах Docker встановлення компіляторів створює суттєві ризики безпеки та збільшує розмір базового образу на сотні мегабайтів.
2. **Витрати процесорного часу та пам'яті:** компіляція великих C/C++ бібліотек (як-от `numpy`, `scipy`, `cryptography` чи `grpcio`) на малопотужних пристроях інтернету речей (Raspberry Pi, ARM SBC) або в обмежених за ресурсами CI/CD раннерах може тривати від 15 хвилин до кількох годин.
3. **Недетермінованість оточення:** компілятор на машині користувача може мати іншу версію оптимізацій або підхопити несумісну версію локально встановленої бібліотеки, що призводить до прихованих помилок під час виконання.

Двійковий дистрибутив (`wheel`) усуває ці проблеми за рахунок перенесення етапу компіляції з машини кінцевого користувача на машину розробника або автоматизований сервер безперервної інтеграції (CI). Формат wheel фіксує артефакт у стані, готовому до негайного використання.

Детальний опис історичного шляху від застарілих інструментів `distutils` та небезпечного формату `.egg` до сучасних стандартів наведено у вставці [Історія еволюції форматів пакування в Python](root:sys-plang-python/wheels-and-sdist/hist-wheel-evolution.md).

```
+--------------------------+-----------------------------------+-----------------------------------+
| Властивість              | Source Distribution (sdist)       | Built Distribution (wheel)        |
+--------------------------+-----------------------------------+-----------------------------------+
| Розширення файлу         | .tar.gz, .zip                     | .whl                              |
| Вміст                    | Сирцевий код (.py, .c, .rs),      | Байткод, .py, скомпільовані       |
|                          | конфігурація pyproject.toml       | модулі .so/.pyd, каталог .dist-info|
| Вимоги до клієнта        | Python.h, gcc/clang/rustc,        | Лише сумісний інтерпретатор       |
|                          | системні бібліотеки-заголовки     | Python та libc                    |
| Час встановлення         | Від кількох секунд до годин       | Десятки мілісекунд                |
| Виконання коду при інстал| Так (виклик build-backend hooks)  | Ні (суто копіювання файлів)       |
| Платформозалежність      | Універсальний (один для всіх ОС)  | Жорстко прив'язаний до тегів ОС   |
+--------------------------+-----------------------------------+-----------------------------------+
```

## 2. Анатомія wheel-пакета: структура zip-контейнера та стандарт PEP 427

Фізично файл із розширенням `.whl` є стандартним ZIP-архівом без стиснення або зі стисненням Deflate. Стандарт [PEP 427](https://peps.python.org/pep-0427/) визначає жорстку внутрішню топологію каталогу, яку менеджер пакетів може розпакувати в один прохід.

![Анатомія wheel-пакета (ZIP-архів із розширенням .whl)](/root/sys/sys-plang-python/wheels-and-sdist/img/wheel-structure.svg)
*Внутрішня організація архіву .whl: корисне навантаження пакета (модулі Python, скомпільовані C-розширення) та службовий каталог метаданих .dist-info.*

Архів містить два обов'язкових компоненти:
1. **Корисне навантаження пакунка (Payload):** каталоги та окремі файли модулів, які після встановлення потрапляють безпосередньо в системний каталог `site-packages`. Для суто пітонівських пакетів це файли `.py`. Для бінарних розширень це динамічні спільні об'єкти з розширенням `.so` (в Linux), `.dylib` (в macOS) або `.pyd` (динамічна бібліотека формату PE/DLL у Windows).
2. **Каталог метаданих (`.dist-info`):** каталог із назвою `{distribution}-{version}.dist-info`, де зосереджена вся системна інформація про дистрибутив.

Каталог `.dist-info` містить чотири критично важливі файли:
- `METADATA`: текстовий маніфест за специфікацією Core Metadata Specification (PEP 566 / PEP 643 / PEP 685). Містить нормалізовану назву пакета (`Name`), версію (`Version`), короткий опис, мінімальну версію інтерпретатора (`Requires-Python`) та повний перелік залежностей (`Requires-Dist`) з маркерами оточення (Environment Markers).
- `WHEEL`: службовий файл формату PEP 427. Він оголошує версію стандарту колеса (`Wheel-Version: 1.0`), назву генератора (`Generator: hatchling 1.22.0`), прапорець розміщення (`Root-Is-Purelib: true/false`) та список тегів сумісності (`Tag`).
- `RECORD`: маніфест цілісності за стандартом PEP 376. Це CSV-файл, у якому кожен рядок містить шлях до кожного розпакованого файлу, його криптографічний хеш SHA-256 (закодований у URL-безпечний Base64 без кінцевих символів `=`) та фізичний розмір у байтах. Сам рядок для файлу `RECORD` залишається без хешу. Завдяки `RECORD` утиліта `pip` під час видалення (`pip uninstall`) точно знає, які саме файли належать цьому пакету, і не залишає сміття в системі.
- `entry_points.txt`: перелік точок входу, зокрема виконуваних консольних команд (`[console_scripts]`), для яких менеджер пакетів створює виконувані бінарні обгортки у каталозі `bin/` (або `Scripts/` у Windows).

Повні структури заголовків, специфікації полів та сценарій генерації маніфесту наведено у вставці [Специфікація метаданих wheel: WHEEL, METADATA та RECORD](root:sys-plang-python/wheels-and-sdist/api-wheel-metadata.md).

Розрізняють два типи коліс за прапорцем `Root-Is-Purelib`:
- **Pure Python Wheel (`Root-Is-Purelib: true`):** пакет складається виключно з коду мовою Python. Такий архів розпаковується в каталог `purelib` (загальний `site-packages`) і працює на будь-якій операційній системі та процесорній архітектурі.
- **Platform Wheel (`Root-Is-Purelib: false`):** пакет містить скомпільовані машинним кодом модулі розширення. Він розпаковується в каталог `platlib` і може виконуватися лише на тій платформі та версії інтерпретатора, для яких був скомпільований.

## 3. Теги сумісності: потрійний ключ PEP 425

Щоб менеджер пакетів міг автоматично визначити, чи підходить конкретне скомпільоване колесо для поточної операційної системи та інтерпретатора, стандарт [PEP 425](https://peps.python.org/pep-0425/) запровадив систему найменування файлів на основі **тегів сумісності** (англ. *compatibility tags*, від лат. *compatibilis* — «той, що співіснує»).

Назва будь-якого файлу wheel має суворо стандартизований вигляд із п'яти (або шести) сегментів, розділених дефісами:

```
{distribution}-{version}(-{build_tag})?-{python_tag}-{abi_tag}-{platform_tag}.whl
```

Складові частини трійки тегів визначають умови сумісності:

```
┌─────────────────┐   ┌─────────────┐   ┌────────────────────────────────┐
│   Python Tag    │ - │   ABI Tag   │ - │          Platform Tag          │
├─────────────────┤   ├─────────────┤   ├────────────────────────────────┤
│ cp312           │   │ cp312       │   │ manylinux_2_28_x86_64          │
│ py3             │   │ none        │   │ any                            │
│ cp39            │   │ abi3        │   │ macosx_11_0_arm64              │
└─────────────────┘   └─────────────┘   └────────────────────────────────┘
```

### Python Tag (Тег мови та реалізації)
Вказує, для якої реалізації та версії мови зібрано пакет:
- `py3` / `py2.py3`: універсальний код на чистому Python, сумісний з будь-яким інтерпретатором версії 3.x.
- `cp312`: спеціалізована версія для стандартного інтерпретатора CPython 3.12.
- `pp310`: версія для JIT-інтерпретатора PyPy версії 3.10.

### ABI Tag (Тег двійкового інтерфейсу прикладного рівня)
Визначає двійкові угоди викликів мови C, компонування структур у пам'яті та стан прапорців компіляції інтерпретатора:
- `none`: двійковий інтерфейс не використовується (для чистого Python коду).
- `cp312`: розширення скомпільовано під внутрішній двійковий інтерфейс CPython 3.12. Такий модуль не зможе завантажитися в CPython 3.11 або 3.13, оскільки внутрішні структури `PyObject` та зміщення полів у пам'яті змінюються між мінорними релізами.
- `cp312t`: нова мітка для збірок CPython 3.13+ із вимкненим глобальним блокуванням інтерпретатора (Free-threaded / no-GIL), де структури пам'яті мають інше вирівнювання через відмову від глобального м'ютекса.
- `abi3` (Stable ABI / Limited API за PEP 384): спеціальний режим бінарної сумісності. Якщо автор C-розширення обмежується використанням лише тих функцій C-API, які входять до стабільного підмножини Limited API, такий двійковий модуль, скомпільований для Python 3.9 (`cp39-abi3`), може завантажуватися будь-якою наступною версією CPython (3.10, 3.11, 3.12, 3.13, 3.14) без повторної компіляції.

### Platform Tag (Тег операційної системи та архітектури)
Фіксує ядро, формат виконуваних файлів, системні бібліотеки та архітектуру процесора:
- `any`: чистий Python, працює на будь-якій системі.
- `win_amd64` / `win_arm64`: 64-розрядні операційні системи Windows для архітектур x86-64 та ARM64 відповідно.
- `macosx_11_0_arm64` / `macosx_10_9_x86_64`: macOS із зазначенням мінімальної версії операційної системи та процесорної платформи.
- `manylinux_2_28_x86_64` / `musllinux_1_2_aarch64`: стандарти двійкової сумісності для дистрибутивів Linux.

Під час виконання команди `pip install` клієнтська бібліотека `packaging.tags` формує впорядкований пріоритетний список тегів, які підтримуються поточною машиною (`sys_tags()`). Наприклад, для CPython 3.12 на 64-розрядному процесорі Linux список сумісних тегів містить понад сотню комбінацій:

```
1. cp312-cp312-manylinux_2_35_x86_64   [Найвищий пріоритет: точна версія glibc]
2. cp312-cp312-manylinux_2_28_x86_64   [Базовий сумісний manylinux]
3. cp312-abi3-manylinux_2_28_x86_64    [Stable ABI для CPython 3.12]
4. cp39-abi3-manylinux_2_28_x86_64     [Stable ABI, зібраний на Python 3.9]
...
N. py3-none-any                        [Чистий Python: найнижчий пріоритет]
```

Менеджер `pip` опитує репозиторій PyPI, порівнює наявні колеса з цим списком і обирає файл із найвищим пріоритетом.

## 4. Проблема бінарної сумісності в Linux: стандарти manylinux та musllinux

У світі Windows та macOS питання постачання бінарних модулів вирішується просто: операційні системи мають стабільні системні динамічні бібліотеки (`Kernel32.dll`, `libSystem.B.dylib`) із зворотною сумісністю ABI протягом десятиліть. 

У світі Linux ситуація виявилася значно складнішою. Ядро Linux гарантує стабільність лише на рівні системних викликів (Syscalls), але не на рівні користувацького простору (User Space). Усі компільовані C/C++ програми взаємодіють з операційною системою через стандартну бібліотеку мови C — `libc` (переважно `glibc` або `musl`).

Головною перешкодою для універсального тегу `linux_x86_64` став механізм **версіонування символів у glibc** (Symbol Versioning). Коли компілятор та лінкер збирають динамічну бібліотеку `.so` на сучасному дистрибутиві (наприклад, Ubuntu 24.04 з `glibc 2.39`), лінкер записує в заголовки ELF точні версії функцій, з якими зв'язувався код, наприклад `memcpy@@GLIBC_2.14` або `posix_spawn@@GLIBC_2.34`. 

Якщо цей скомпільований файл спробувати завантажити на сервері зі старішим дистрибутивом (наприклад, Debian 11 з `glibc 2.31` або RHEL 8 з `glibc 2.28`), динамічний завантажувач ядра `ld.so` під час виклику `dlopen()` перевіряє таблицю символів і негайно аварійно завершує роботу процесу:

```
ImportError: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.34' not found (required by /site-packages/_fastmath.so)
```

Правило сумісності `glibc` діє лише в один бік: **код, зібраний на старій версії glibc, працює на всіх новіших системах, але зворотне неможливо**:

```
Бінарник зібрано на glibc 2.28  ──>  Працює на glibc 2.28, 2.31, 2.35, 2.39  [СУМІСНО]
Бінарник зібрано на glibc 2.39  ──>  Збій на glibc 2.28, 2.31, 2.35          [НЕСУМІСНО]
```

Щоб вирішити цю кризу, робоча група PyPA розробила серію стандартів **manylinux** (від англ. *many* — «багато» та *Linux*). Стандарти зафіксували мінімальний гарантований набір бібліотек і версій ядер, які розробник може вважати гарантовано наявними в системі:

1. **`manylinux1` ([PEP 513](https://peps.python.org/pep-0513/), 2016 рік):** базувався на застарілому дистрибутиві CentOS 5 (`glibc 2.5`). Дозволяв завантаження на 99% наявних на той час систем Linux.
2. **`manylinux2010` ([PEP 571](https://peps.python.org/pep-0571/)):** перехід на CentOS 6 (`glibc 2.12`), що дозволило використовувати компілятори з підтримкою стандарту C++11.
3. **`manylinux2014` ([PEP 599](https://peps.python.org/pep-0599/)):** перехід на CentOS 7 (`glibc 2.17`), додано офіційну підтримку архітектур `aarch64` (ARM64), `ppc64le` та `s390x`.
4. **Сучасний стандарт `manylinux_x_y` ([PEP 600](https://peps.python.org/pep-0600/)):** запровадив вічну (Perennial) схему іменування тегів без прив'язки до назв дистрибутивів. Тег прямо вказує мінімальну необхідну версію `glibc`. Наприклад:
   - `manylinux_2_28_x86_64`: вимагає `glibc >= 2.28` (базується на RHEL 8 / AlmaLinux 8 / Debian 10).
   - `manylinux_2_34_x86_64`: вимагає `glibc >= 2.34` (Ubuntu 22.04+).
5. **`musllinux_x_y` ([PEP 656](https://peps.python.org/pep-0656/)):** стандарт для дистрибутивів на базі легкої бібліотеки `musl libc`, зокрема популярного в контейнеризації дистрибутива Alpine Linux. Тег `musllinux_1_2_x86_64` гарантує роботу в середовищах із `musl >= 1.2`.

> 🔧 **Білий список системних бібліотек.** Стандарт manylinux чітко визначає вичерпний «білий список» спільних бібліотек, з якими розширення має право зв'язуватися динамічно через системні шляхи хоста (`/lib`, `/usr/lib`). До нього входять лише базові компоненти: `libc.so.6`, `libm.so.6`, `libdl.so.2`, `libpthread.so.0`, `librt.so.1`, `libutil.so.1`, `libresolv.so.2`, `libX11.so.6`, `libGL.so.1`. Будь-яка інша бібліотека (наприклад, `libpng`, `libgfortran`, `libopenblas`, `libssl`) вважається зовнішньою і **заборонена** для прямого динамічного зв'язування з хостом — вона повинна постачатися безпосередньо всередині колісного архіву.

## 5. Анатомія лінкування C-розширень: auditwheel, RPATH та ізоляція $ORIGIN

Якщо скомпільований модуль C-розширення `_core.so` залежить від зовнішніх бібліотек (наприклад, `libpng.so.16` чи `libz.so`), простий запис цього модуля у ZIP-архів призведе до аварії на машині клієнта: якщо в системі користувача не встановлено пакунок `libpng-dev`, динамічний завантажувач `ld.so` не зможе знайти файл бібліотеки за записом `DT_NEEDED` у заголовку ELF.

Для автоматичного вирішення цієї проблеми створено спеціалізований інструмент **auditwheel** (для Linux), а також його аналоги **delocate** (для macOS) та **delvewheel** (для Windows).

![Трансформація двійкового модуля інструментом auditwheel (manylinux)](/root/sys/sys-plang-python/wheels-and-sdist/img/manylinux-auditwheel.svg)
*Механізм аудиту та ізоляції залежностей утилітою auditwheel: перевірка символів glibc, копіювання внутрішніх динамічних бібліотек та модифікація заголовка DT_RUNPATH через макрос $ORIGIN.*

Процес перетворення сирого бінарного колеса на сумісне з manylinux складається з чотирьох кроків:

### Крок 1. Аудит символів (Symbol Audit)
`auditwheel repair` відкриває всі файли `.so` всередині незбілдженого колеса, зчитує секції динамічного зв'язування ELF та будує повний граф залежностей:
- Сканує таблицю `DT_NEEDED`, яка містить імена всіх спільних об'єктів, необхідних для завантаження модуля.
- Аналізує версії символів `GLIBC_X.Y` для кожної імпортованої функції. Якщо виявлено символ з версії `GLIBC_2.34`, колесо не може бути позначене тегом `manylinux2014` (`glibc 2.17`), і утиліта підвищує тег до `manylinux_2_34` або сигналізує про помилку.

### Крок 2. Копіювання залежностей (Vendoring)
Усі знайдені динамічні бібліотеки, яких немає в «білому списку» стандарту manylinux, утиліта копіює з хостової системи збирання у спеціальний внутрішній каталог всередині структури колеса — зазвичай `{package_name}.libs/` (наприклад, `numpy.libs/` або `cryptography.libs/`).

### Крок 3. Унікалізація імен (Soname Mangling)
Якщо кілька різних пакетів Python запакують у свої колеса власні версії популярної бібліотеки `libpng16.so.16`, під час одночасного завантаження обох пакетів в один процес інтерпретатора виникне конфлікт імен: динамічний завантажувач зв'яже обидва розширення з першою завантаженою копією в пам'яті, що може призвести до пошкодження пам'яті через несумісність версій структур.

Щоб запобігти конфліктам, `auditwheel` генерує для кожної запакованої бібліотеки унікальний хеш і змінює її внутрішнє ім'я `soname` та ім'я файлу на диску:

```
libpng16.so.16  ──>  libpng16-cb829391.so.16.37.0
```

Усі посилання на цю бібліотеку в залежних модулях `.so` також оновлюються на нове унікальне ім'я через модифікацію секції `DT_NEEDED`.

### Крок 4. Перезапис RPATH через макрос $ORIGIN
За замовчуванням завантажувач `ld.so` шукає бібліотеки у глобальних системних шляхах (`/lib`, `/usr/lib`) або за шляхами змінної `LD_LIBRARY_PATH`. Але скомпільований пакет встановлюється у довільний каталог віртуального середовища, абсолютний шлях до якого невідомий на етапі збирання (наприклад, `/home/user/project/.venv/lib/python3.12/site-packages/`).

Для розв'язання цієї проблеми використовується спеціальний запис заголовка ELF — **`DT_RUNPATH`** (або застарілий `DT_RPATH`), у який записується динамічний макрос завантажувача **`$ORIGIN`**:

```
DT_RUNPATH = $ORIGIN/../fastmath.libs
```

Символ `$ORIGIN` — це спеціальний системний токен динамічного завантажувача Linux. Під час виконання виклику `dlopen()` завантажувач `ld.so` замінює `$ORIGIN` на фізичний абсолютний шлях до каталогу, в якому розташований сам завантажуваний файл `.so`. 

Таким чином, розширення `_fastmath.so` шукає свої залежні бібліотеки не в глобальній системі, а у сусідньому внутрішньому каталозі `fastmath.libs/` поруч із собою. Це забезпечує абсолютну автономність та ізоляцію пакета.

Для інспекції та ручного редагування RPATH застосовується утиліта `patchelf`:

```bash
# Перевірка поточних залежностей та RUNPATH
readelf -d _fastmath.cpython-312-x86_64-linux-gnu.so | grep -E '(NEEDED|RUNPATH|RPATH)'

# Встановлення відносного RUNPATH через $ORIGIN
patchelf --set-rpath '$ORIGIN/fastmath.libs' _fastmath.cpython-312-x86_64-linux-gnu.so
```

Повний практичний практикум зі збирання двійкового розширення мовами C та C++, патчингу ELF-заголовків та створення колеса наведено у вставці [Збирання бінарного wheel із C-розширенням та налаштування RPATH](root:sys-plang-python/wheels-and-sdist/proj-c-wheel-builder.md).

## 6. Сучасні інтерфейси збирання: стандарти PEP 517, PEP 518, PEP 621 та сучасні бекенди

Історично збирання як вихідних архівів `sdist`, так і коліс `wheel` було жорстко монополізоване бібліотекою `setuptools`. Розробник був змушений описувати конфігурацію виключно у файлі `setup.py`, викликаючи команди `python setup.py sdist` або `python setup.py bdist_wheel`. Це створювало замкнене коло залежностей (Bootstrapping Problem): щоб встановити пакет, менеджерові потрібен був `setuptools`, але сам `setuptools` розповсюджувався як пакет і вимагав інструментів для встановлення.

Сучасна екосистема Python розділила процес пакування на два незалежних шари за чіткими інтерфейсними контрактами:

```
┌─────────────────────────────────────────────────────────────┐
│                    BUILD FRONTEND                           │
│                 (pip, python -m build)                      │
└──────────────────────────────┬──────────────────────────────┘
                               │  PEP 517 / PEP 518 Hooks
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                    BUILD BACKEND                            │
│  (hatchling, flit_core, maturin, scikit-build-core, ...)   │
└─────────────────────────────────────────────────────────────┘
```

1. **Декларація залежностей збирання ([PEP 518](https://peps.python.org/pep-0518/)):**
   Таблиця `[build-system]` у файлі `pyproject.toml` визначає, які саме пакети потрібні для запуску процесу збирання, ще до того, як розпочнеться аналіз самого проєкту:

   ```toml
   [build-system]
   requires = ["scikit-build-core>=0.9.0", "nanobind>=1.9.0"]
   build-backend = "scikit_build_core.build"
   ```

   Отримавши цю таблицю, утиліта-фронтенд (`pip` або `build`) створює ізольоване тимчасове віртуальне середовище, автоматично встановлює туди вказані інструменти з PyPI і лише після цього викликає бекенд.

2. **Стандартний протокол бекенду ([PEP 517](https://peps.python.org/pep-0517/)):**
   Бекенд збирання — це звичайний модуль Python, який обов'язково експортує фіксований набір функцій-хуків (Hooks):
   - `build_wheel(wheel_directory, config_settings=None, metadata_directory=None)`: збирає бінарний архів `.whl` і записує його у вказаний каталог.
   - `build_sdist(sdist_directory, config_settings=None)`: упаковує вихідний архів `.tar.gz`.
   - `get_requires_for_build_wheel(config_settings=None)`: повертає список додаткових динамічних залежностей, необхідних для збирання колеса (наприклад, перевіряє наявність компілятора в системі).
   - `prepare_metadata_for_build_wheel(metadata_directory, config_settings=None)`: генерує лише каталог `.dist-info` без повної компіляції колеса, що дозволяє `pip` блискавично розрахувати граф залежностей без витрат на збирання C-коду.

3. **Стандартизовані декларативні метадані ([PEP 621](https://peps.python.org/pep-0621/)):**
   Секція `[project]` у `pyproject.toml` містить єдиний стандартизований формат опису назви, версії, авторів, ліцензій та залежностей, спільний для всіх сучасних інструментів.

Завдяки відокремленню фронтенду від бекенду в екосистемі з'явилася плеяда вузькоспеціалізованих високоефективних інструментів збирання:

| Бекенд збирання | Призначення та особливості | Типовий стек |
|---|---|---|
| **`flit_core`** | Мінімалістичний швидкісний бекенд для чистих Python бібліотек. Не підтримує C-розширень, фокусується на простоті | Чистий Python |
| **`hatchling`** | Гнучкий модульний бекенд із багатою системою плагінів (динамічне обчислення версій з git-тегів, кастомні маніфести) | Загальні проєкти |
| **`maturin`** | Спеціалізований збирач для розширень мовою Rust (на базі PyO3 або uniffi). Автоматично створює manylinux-колеса | Rust + Python |
| **`scikit-build-core`** | Сучасна заміна застарілого setuptools для C/C++/Fortran розширень на базі CMake та Ninja. Підтримує nanobind та pybind11 | C/C++, CMake |
| **`meson-python`** | Бекенд на базі системи збирання Meson. Використовується в масштабних наукових пакетах (NumPy, SciPy) | C, C++, Fortran |

Для локального збирання артефактів з командного рядка використовується стандартний фронтенд `build` (PyPA):

```bash
# Встановлення стандартного фронтенду
pip install build

# Збирання вихідного архіву (sdist) та колеса (wheel) в каталог dist/
python -m build
```

## 7. Програмна інспекція тегів та діагностика сумісності

Менеджер `pip` використовує модуль `packaging.tags` для точного обчислення сумісності платформи. Розуміння того, які саме теги генерує середовище, дозволяє заздалегідь виявити причину, чому `pip` відмовляється завантажувати бінарне колесо і починає компіляцію з `sdist`.

Наведений нижче скрипт наочно демонструє, як інтерпретатор перевіряє сумісність конкретного файлу wheel із поточною операційною системою:

```py
import sys
from pathlib import Path
from packaging.tags import sys_tags
from packaging.utils import parse_wheel_filename


def inspect_wheel_compatibility(wheel_path_str: str) -> None:
    """Перевірити сумісність wheel-файлу з поточним середовищем Python."""
    wheel_path = Path(wheel_path_str)
    
    # 1. Розбір назви колеса на компоненти (PEP 425)
    name, version, build, tags = parse_wheel_filename(wheel_path.name)
    
    print(f"Пакет: {name} (версія {version})")
    print(f"Теги колеса: {[str(t) for t in tags]}")
    
    # 2. Отримання списку сумісних системних тегів
    current_system_tags = list(sys_tags())
    print(f"Системне середовище: {current_system_tags[0]}")
    
    # 3. Перевірка перетину множин тегів
    matching_tags = [t for t in tags if t in current_system_tags]
    
    if matching_tags:
        best_match = matching_tags[0]
        priority_index = current_system_tags.index(best_match)
        print(f"Статус: СУМІСНИЙ")
        print(f"Найкращий збіг: {best_match} (індекс пріоритету: {priority_index})")
    else:
        print("Статус: НЕСУМІСНИЙ")
        print("Причина: жоден із тегів колеса не знайдено серед підтримуваних тегів середовища.")
        print("pip спробує завантажити sdist або іншу версію wheel.")


if __name__ == "__main__":
    example_wheel = f"cryptography-42.0.5-cp39-abi3-manylinux_2_28_x86_64.whl"
    inspect_wheel_compatibility(example_wheel)
```

## 8. Експлуатаційна безпека, перевірка та розмір артефактів

Поширення скомпільованих бінарних коліс несе не лише вигоди у швидкості, але й специфічні експлуатаційні виклики, які інженер повинен контролювати в процесі постачання ПЗ.

### Розмір бінарних коліс (Fat Wheels)
Оскільки стандарт `manylinux` вимагає запаковувати всі несистемні динамічні бібліотеки всередину колеса, розмір бінарних архівів може сягати сотень мегабайтів. Наприклад, пакунки для машинного навчання (`torch`, `tensorflow`, `cupy`) містять усередині динамічні бібліотеки CUDA Toolkit, MKL та cuDNN. У результаті розмір одного wheel-файлу може перевищувати 800–1200 МБ. У розподілених хмарних системах розгортання таких коліс на сотнях вузлів створює колосальне навантаження на мережевий канал та збільшує час прогріву нових контейнерів.

### Цілісність та публікація через Trusted Publishing
Для захисту ланцюга постачання (Supply Chain Security) репозиторій PyPI відмовився від застарілих паролів розробників на користь стандарту **Trusted Publishing** (OpenID Connect / OIDC). Процес збирання бінарних коліс у GitHub Actions генерує криптографічні докази походження (SLSA Provenance Attestation), що гарантує: опублікований `.whl` був зібраний саме з перевіреного коміту у відкритому репозиторії з дотриманням автоматизованої процедури `cibuildwheel`.

Для валідації зібраного дистрибутива перед публікацією використовується утиліта `twine`:

```bash
# Перевірка коректності метаданих та синтаксису опису
twine check dist/*

# Інспекція внутрішніх бібліотек manylinux-колеса
auditwheel show dist/example_pkg-1.0.0-cp312-cp312-linux_x86_64.whl
```

Своєчасний аудит двійкових тегів, контроль залежностей через `auditwheel` та використання сучасних бекендів збирання забезпечують надійне, блискавичне та передбачуване розгортання Python-пакунків на будь-якій цільовій платформі.
