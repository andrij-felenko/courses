# 📜 Від setup.py та .egg до PEP 427: еволюція пакування в Python

Наприкінці 1990-х років розповсюдження програмного коду мовою Python не мало єдиного системного стандарту. Розробники поширювали програми або у вигляді вихідних текстів через архіви `.tar.gz`, або ручним копіюванням файлів `.py` безпосередньо в каталоги системного інтерпретатора. Якщо бібліотека містила скомпільовані розширення мовами C чи C++, автор самостійно створював `Makefile`, вручну прописував шляхи до заголовних файлів `Python.h` та бібліотек компілятора. Такий підхід унеможливлював автоматизоване керування залежностями: кожен користувач мусив власноруч розв'язувати конфлікти версій і налаштовувати прапорці компіляції.

## 1. Епоха distutils та імперативний сценарій setup.py

У 2000 році з релізом Python 1.6 та Python 2.0 Грег Ворд (Greg Ward) розробив стандартний модуль `distutils` (PEP 229). Модуль запропонував парадигму імперативного конфігурування: процес збирання та встановлення описувався виконуваним скриптом `setup.py`. Розробник оголошував функції збирання, перелік модулів і розширень всередині виклику `setup()`, а користувач інсталював бібліотеку стандартною системною командою:

```bash
python setup.py install
```

```
+───────────────────────────+
|      Розробник коду       |
|    (.py, .c, setup.py)    |
+─────────────┬─────────────+
              │
              ▼ [Виконання довільного Python-коду]
+───────────────────────────+
|   python setup.py install | ──> Виклик системного gcc/clang
+─────────────┬─────────────+
              │
              ▼ [Копіювання файлів без маніфесту]
+───────────────────────────+
| /usr/lib/python/site-pkgs | ──> Неможливо автоматично видалити!
+───────────────────────────+
```

Імперативна модель `setup.py` створила глибокі системні вади, які стримували розвиток екосистеми понад десятиліття:
1. **Виконання довільного неізольованого коду:** інсталяція вимагала запуску скрипту `setup.py` на машині користувача. Якщо пакет встановлювався у системні каталоги, скрипт виконувався з привілеями адміністратора (`root`), що створювало критичну вразливість безпеки.
2. **Проблема курки та яйця (Bootstrapping Problem):** якщо файл `setup.py` для свого виконання імпортував сторонній допоміжний модуль (наприклад, генератор коду чи `Cython`), встановлення було неможливим без попереднього ручного встановлення цих залежностей.
3. **Відсутність маніфесту та деінсталяції:** `distutils` просто копіював файли у каталог `site-packages`, не фіксуючи контрольних сум і списку створених об'єктів. Команди `uninstall` не існувало, і користувачі мусили вручну вишукувати розкидані файли модулів.

## 2. Поява setuptools та архітектурна криза формату .egg

У 2004 році Філіп Ібі (Phillip Eby) представив бібліотеку `setuptools` та утиліту `easy_install`. Головною інновацією став перший бінарний формат дистрибуції — `.egg` (англ. *egg* — «яйце»). Формат являв собою ZIP-архів або окремий каталог, що містив скомпільований байткод `.pyc`, динамічні бібліотеки C-розширень `.so` / `.pyd` та службовий каталог `EGG-INFO`.

```
.egg (2004, setuptools)                   .whl (2012, PEP 427)
├── my_package/                           ├── my_package/
│   ├── __init__.pyc                      │   ├── __init__.py
│   └── _native.so                        │   └── _native.so
└── EGG-INFO/                             └── my_package-1.0.dist-info/
    ├── PKG-INFO                              ├── METADATA
    ├── SOURCES.txt                           ├── WHEEL
    ├── requires.txt                          └── RECORD
    └── entry_points.txt
(Вимагає runtime pkg_resources)           (Чисте розпакування у site-packages)
```

Незважаючи на успіх у розв'язанні проблеми автоматичного викачування залежностей через протокол EasyInstall, архітектура `.egg` спричинила нові експлуатаційні проблеми:
- **Втручання у середовище виконання:** щоб інтерпретатор міг імпортувати файли з нерозпакованого архіву `.egg`, системний шлях `sys.path` перевантажувався за допомогою файлів `.pth`.
- **Затримки старту та кешування:** якщо архів `.egg` містив скомпільовані C-розширення, інтерпретатор не міг завантажити їх прямо з ZIP-файлу через системний виклик `dlopen()`. Бібліотека `pkg_resources` була змушена під час кожного старту процесу прозоро розпаковувати C-модулі у тимчасовий каталог користувача `~/.python-eggs/`. Це створювало блокування файлів у багатопотокових серверах, затримки ініціалізації та неконтрольоване засмічення дисків.
- **Відсутність стандартизації бінарної сумісності:** формат не підтримував точних міток ABI та версій системних бібліотек, через що бінарні яйця, зібрані на одній машині, аварійно падали на іншій.

## 3. Стандартизація сучасного пакування: PEP 376 та PEP 427

У 2009–2012 роках робоча група PyPA (Python Packaging Authority) під проводом Даніеля Голта (Daniel Holth) та Антуана Пітру (Antoine Pitrou) здійснила докорінну реформу підсистеми постачання.

Спершу стандарт [PEP 376](https://peps.python.org/pep-0376/) стандартизував структуру встановленого пакета: замість розрізнених форматів було впроваджено єдиний каталог метаданих `.dist-info` з обов'язковим криптографічним маніфестом `RECORD`. Це дозволило менеджеру пакетів `pip` здійснювати детерміноване видалення пакетів та перевіряти цілісність встановлених файлів.

У 2012 році було прийнято стандарт [PEP 427](https://peps.python.org/pep-0427/), який зафіксував специфікацію формату `wheel` (`.whl`). Філософія колеса докорінно відрізнялася від `.egg`:
1. `wheel` є суто транспортним інсталяційним контейнером, а не виконуваним середовищем. Він не додається до `sys.path` і не потребує бібліотек підтримки під час імпорту.
2. Встановлення колеса зводиться до безпечного розпакування архіву у цільовий каталог `site-packages`. На машині клієнта не виконується жодний код мовою Python чи C.
3. Стандарт [PEP 425](https://peps.python.org/pep-0425/) запровадив суворі правила тегів сумісності, що гарантувало однозначну відповідність між двійковим файлом і цільовою операційною системою.

## 4. Фінал моноліту: перехід до PEP 517 та PEP 518

Останнім бар'єром на шляху до повної стандартизації залишався монополізм `setuptools` як єдиного інструменту генерації пакетів. У 2015–2017 роках стандарти [PEP 518](https://peps.python.org/pep-0518/) (декларація залежностей збирання у файлі `pyproject.toml`) та [PEP 517](https://peps.python.org/pep-0517/) (стандартизований інтерфейс взаємодії між збирачем-фронтендом та бекендом) остаточно позбавили екосистему залежності від імперативного файлу `setup.py`.

Утиліти встановлення (`pip`, `build`) отримали відкритий протокол викликів, завдяки чому розробники отримали змогу вільно обирати швидкісні, безпечні та спеціалізовані бекенди нового покоління (`hatchling`, `flit_core`, `maturin`, `scikit-build-core`), побудовані на основі декларативних стандартів.
