Коли програмі на Python потрібно викликати скомпільовану функцію зі сторонньої динамічної бібліотеки (`.so` у Linux, `.dll` у Windows, `.dylib` у macOS), стандартний підхід вимагає створення модуля розширення мовою C. Розробник повинен написати код-обгортку за допомогою CPython C API, вручну розпакувати об'єкти `PyObject*` через `PyArg_ParseTuple()`, перевірити типи, викликати нативну функцію, упакувати результат назад у `PyObject*` через `Py_BuildValue()` і скомпільувати двійковий файл під кожну версію Python та операційну систему. Якщо версія CPython змінюється або на машині користувача відсутній компілятор C/C++, такий модуль перестає працювати.

Альтернативою є чужорідний інтерфейс функцій (*Foreign Function Interface*, FFI — від лат. *forasticus* — зовнішній, чужий та *inter-facio* — розділяю/з'єдную). FFI дозволяє динамічно завантажувати бібліотеку в адресний простір процесу за допомогою системних викликів `dlopen()` або `LoadLibrary()`, знаходити адресу потрібного символу через `dlsym()` або `GetProcAddress()` і конструювати машинний виклик безпосередньо під час виконання програми. У екосистемі Python цей підхід реалізовано двома основними інструментами: стандартним модулем `ctypes` та бібліотекою `cffi`.

## 1. Архітектура ctypes та динамічна генерація машинних викликів

Модуль `ctypes` входить до стандартної бібліотеки Python і надає механізм динамічного виклику C-функцій без компіляції проміжних файлів. Робота `ctypes` спирається на внутрішній модуль ядра `Modules/_ctypes/_ctypes.c` та низькорівневу системну бібліотеку `libffi`.

### Системне завантаження бібліотек і пошук символів

Під час створення екземпляра `ctypes.CDLL("libm.so")` інтерпретатор виконує системний виклик `dlopen()` (у POSIX-системах) або `LoadLibraryExW()` (у Windows). Динамічний компонувальник операційної системи (`ld.so` у Linux або завантажувач NTDLL у Windows) монтує сегменти коду (`.text`) та даних (`.rodata`, `.data`) бібліотеки у віртуальну пам'ять процесу.

Коли виконується звернення до атрибута об'єкта бібліотеки, наприклад `lib.cos`, модуль `ctypes` викликає функцію пошуку адреси символу `dlsym(handle, "cos")`. Отримана адреса є сирим 64-бітним або 32-бітним покажчиком на першу машинну інструкцію функції в сегменті пам'яті. Історія створення бібліотеки `libffi` та включення `ctypes` до складу ядра CPython детально описана у вставці [Еволюція Foreign Function Interface: від libffi до CFFI](root:sys-plang-python/ctypes-and-cffi/hist-libffi-evolution.md).

### Внутрішній устрій libffi: структура CIF і трампліни виклику

Процесор не оперує динамічними об'єктами Python: на апаратному рівні він працює з регістрами загального призначення (`RAX`, `RDI`, `RSI`, `RDX`, `RCX`, `R8`, `R9` на архітектурі x86-64) та регістрами векторних інструкцій (`XMM0`–`XMM7`). Інтерпретатор Python не може виконати прямий асемблерний стрибок `call [address]`, оскільки кількість, розмір та типи аргументів стають відомими лише під час виконання коду.

Бібліотека `libffi` вирішує цю проблему через двоетапний механізм:

1. **Інтерфейс виклику (Call Interface, CIF):** Структура `ffi_cif` містить опис типу значення, що повертається, кількості параметрів та масиву покажчиків на описи типів `ffi_type` (`ffi_type_sint32`, `ffi_type_double`, `ffi_type_pointer`). Функція `ffi_prep_cif()` аналізує ці описи, розраховує вимоги до вирівнювання стека та точні зміщення для цільової апаратної платформи.
2. **Асемблерний трамплін (Trampoline — від італ. *trampolino* — трамплін для стрибка):** Функція `ffi_call()` отримує підготовлену структуру `ffi_cif`, адресу цільової C-функції, буфер для повернення результату та масив покажчиків на значення аргументів. На основі цих даних `ffi_call` виконує асемблерний мікрокод: розкладає перші аргументи у відповідні регістри процесора згідно з правилами ABI операційної системи, записує решту аргументів у стек процесу, вирівнює покажчик стека `RSP` по межі 16 байтів і виконує машинну інструкцію `call`. Після повернення результат зчитується з регістрів `RAX` або `XMM0` і записується у вихідний буфер.

При профілюванні програми за допомогою системних утиліт `perf` або `gdb` виклик через `ctypes` завжди відображається у стеку викликів як проходження крізь функції `_PyCFuncPtr_Call()`, `ffi_call()` та внутрішній асемблерний трамплін `ffi_call_unix64`.

### Конвенції викликів: cdecl, stdcall та 64-бітний уніфікований ABI

Конвенція виклику (*calling convention*, від лат. *conventio* — угода, домовленість) регламентує, як саме параметри передаються у функцію (через регістри чи стек), у якому порядку вони записуються та хто очищає стек після повернення (викликач чи викликана функція).

1. **`cdecl` (C Declaration):** Історичний стандарт для мови C на 32-бітних платформах x86. Аргументи проштовхуються у стек справа наліво. Стек очищає функція, що викликає (*caller cleanup*). Це дозволяє функціям приймати змінну кількість аргументів (`printf(fmt, ...)`). У `ctypes` завантаження з цією конвенцією виконує клас `ctypes.CDLL`.
2. **`stdcall` (Standard Call):** Стандарт для Win32 API на 32-бітних системах Windows. Аргументи передаються через стек справа наліво, але стек очищає сама викликана функція перед інструкцією повернення `ret N` (*callee cleanup*). У `ctypes` для таких бібліотек використовується клас `ctypes.WinDLL`. Помилка у виборі між `CDLL` та `WinDLL` на 32-бітній системі призводить до невідповідності покажчика стека `ESP` та аварійного завершення процесу.
3. **64-бітні ABI (System V AMD64 проти Microsoft x64):** На 64-бітних архітектурах конвенції уніфіковано на рівні операційної системи. У Linux/macOS (System V AMD64 ABI) перші 6 цілочисельних аргументів або покажчиків передаються через регістри `RDI`, `RSI`, `RDX`, `RCX`, `R8`, `R9`, а перші 8 чисел з плаваючою комою — через `XMM0`–`XMM7`. У Windows x64 перші 4 аргументи передаються через `RCX`, `RDX`, `R8`, `R9` (або `XMM0`–`XMM3`), з обов'язковим резервуванням 32 байтів тіньового простору (*shadow space*) на стеку. Бібліотека `libffi` та модуль `ctypes` автоматично враховують ці відмінності під час виклику `ffi_call()`.

### Оголошення типів, маршалінг та накладні витрати

Маршалінг (*marshalling*, від давньоверхньонім. *marah* — кінь + *scalc* — слуга, через фр. *maréchal* та англ. *marshalling* — впорядкування, шикування) — це процес перетворення внутрішнього представлення об'єктів мови високого рівня у двійковий формат, придатний для обробки процесором або передачі нативному коду.

У `ctypes` маршалінг відбувається повністю динамічно під час кожного виклику. Розглянемо приклад налаштування сигнатури для C-функції додавання векторів:

:::tabs
```c
// math_ops.c
#include <stdint.h>

int32_t add_vectors(const int32_t *a, const int32_t *b, int32_t *out, size_t n) {
    if (!a || !b || !out) return -1;
    for (size_t i = 0; i < n; ++i) {
        out[i] = a[i] + b[i];
    }
    return 0;
}
```
```cpp
// math_ops.cpp
#include <cstdint>
#include <cstddef>
#include <span>

extern "C" int32_t add_vectors(const int32_t *a, const int32_t *b, int32_t *out, std::size_t n) noexcept {
    if (!a || !b || !out) return -1;
    std::span<const int32_t> span_a(a, n);
    std::span<const int32_t> span_b(b, n);
    std::span<int32_t>       span_out(out, n);
    for (std::size_t i = 0; i < n; ++i) {
        span_out[i] = span_a[i] + span_b[i];
    }
    return 0;
}
```
:::

Виклик цієї функції з Python через `ctypes` вимагає суворого опису типів аргументів та результату:

```python
import ctypes

lib = ctypes.CDLL("./libmath_ops.so")

# Обов'язкове налаштування сигнатури: restype та argtypes
lib.add_vectors.restype = ctypes.c_int32
lib.add_vectors.argtypes = [
    ctypes.POINTER(ctypes.c_int32),
    ctypes.POINTER(ctypes.c_int32),
    ctypes.POINTER(ctypes.c_int32),
    ctypes.c_size_t,
]

size = 4
arr_type = ctypes.c_int32 * size
vec_a = arr_type(1, 2, 3, 4)
vec_b = arr_type(10, 20, 30, 40)
vec_out = arr_type()

ret = lib.add_vectors(vec_a, vec_b, vec_out, size)
# vec_out містить результат [11, 22, 33, 44]
```

Якщо властивості `argtypes` або `restype` не задано явно, `ctypes` вважає всі цілочисельні аргументи C-типом `int` (4 байти), а результат — також `int`. На 64-бітних системах це є поширеним джерелом критичних помилок: якщо функція повертає покажчик `void*` (8 байтів), `ctypes` відсікає старші 32 біти адреси, що призводить до негайного падіння з помилкою сегментації пам'яті (*Segmentation Fault*).

Кожен виклик через `ctypes` супроводжується відчутними накладними витратами:
1. Інтерпретатор перевіряє відповідність переданих Python-об'єктів типам у списку `argtypes`.
2. Створюються тимчасові екземпляри C-типів або видобуваються сирі адреси пам'яті.
3. Формується масив покажчиків для `ffi_call`.
4. Здійснюється непрямий виклик через трамплін `libffi`.
5. Отримане з регістра значення загортається у новий об'єкт Python (`int`, `float` чи екземпляр `ctypes`).

### Покажчики, приведення типів (Cast) та перевірка на NULL у ctypes

У `ctypes` сирі адреси пам'яті представляються типом `ctypes.c_void_p`. Для приведення покажчика одного типу до іншого використовується функція `ctypes.cast(obj, type)`. Якщо створюється типізований покажчик `ptr = ctypes.POINTER(ctypes.c_int32)()`, його початкове значення дорівнює `NULL` (нульова адреса). Спроба прочитати значення через `ptr.contents` на відміну від нативного C не викликає краху сегментації: `ctypes` автоматично перевіряє адресу і викидає виняток `ValueError: NULL pointer access`.

### Функції зі змінною кількістю аргументів (Variadic Functions) у ctypes

Функції мови C зі змінною кількістю аргументів (наприклад, `printf`, `ioctl`, `fcntl`, `open` з прапорцем `O_CREAT`) підпорядковуються спеціальним правилам ABI. На архітектурі x86-64 перед викликом такої функції регістр `AL` (молодші 8 бітів регістра `RAX`) повинен містити точну кількість векторних регістрів `XMM`, задіяних для передачі чисел з плаваючою комою.

У `ctypes` не можна задати список `argtypes` з багатокрапкою `...`. Якщо функція викликається з різними наборами параметрів, розробник повинен динамічно змінювати атрибут `argtypes` перед кожним окремим викликом або створювати окремі екземпляри об'єкта функції:

```python
libc = ctypes.CDLL(None)

# Налаштовуємо виклик sprintf для трьох аргументів: буфер, формат, ціле число
libc.sprintf.argtypes = [ctypes.c_char_p, ctypes.c_char_p, ctypes.c_int]

buf = ctypes.create_string_buffer(64)
libc.sprintf(buf, b"Value: %d", 42)
```

### Автоматична обробка кодів повернення через errcheck

Для автоматизації обробки помилок C-функцій (наприклад, перевірки кодів завершення `-1` або `NULL`-покажчиків) модуль `ctypes` надає механізм хука `errcheck`. Атрибут `errcheck` приймає функцію Python із сигнатурою `errcheck(result, func, arguments)`:

```python
def check_negative_status(result, func, arguments):
    if result < 0:
        errno_val = ctypes.get_errno()
        raise OSError(errno_val, f"C-функція {func.__name__} повернула помилку {result}")
    return result

# Прив'язуємо хук до функції
lib.add_vectors.errcheck = check_negative_status
```

Якщо нативна функція повертає від'ємне значення, `ctypes` автоматично викликає перевірку, вилучає збережене системне значення `errno` та генерує стандартний виняток Python `OSError`.

### Рядкові типи та небезпека кодувань у ctypes

При передачі рядків через `ctypes` використовується тип `ctypes.c_char_p`. У Python 3 передача звичайного рядка `str` у `c_char_p` заборонена: розробник повинен явно передавати байти `bytes`, закодовані в UTF-8 або ASCII з нуль-термінатором `\0`.

Якщо функція C приймає широкий рядок `wchar_t*`, у `ctypes` використовується `ctypes.c_wchar_p`, який приймає стандартний Python `str` і прозоро конвертує його в системний формат `wchar_t` (2 байти у Windows UTF-16LE або 4 байти в Linux UTF-32). Для створення мутабельних буферів рядків використовуються допоміжні фабрики `ctypes.create_string_buffer(size)` та `ctypes.create_unicode_buffer(size)`.

### Метаклас Structure, дескриптори полів та порядок байтів

При створенні класів-структур `class Point(ctypes.Structure)` у CPython спрацьовує спеціальний метаклас `PyCStructType_Type`. Під час інтерпретації атрибута `_fields_` метаклас виконує такі низькорівневі дії:
- Обчислює розмір кожного поля та вимоги до вирівнювання за правилами цільового C-компілятора.
- Вставляє необхідний паддінг між полями та в кінці структури.
- Створює в словнику класу дескриптори полів (`CFieldObject`).
- При зверненні до поля `p.x` дескриптор безпосередньо зчитує байти з відповідного зміщення у внутрішньому буфері екземпляра без виклику проміжних Python-методів.

Для розбору бінарних пакетів мережевих протоколів або апаратних реєстрів модулів `ctypes` підтримує явний контроль порядку байтів через класи `ctypes.BigEndianStructure` (мережевий порядок байтів Big-Endian) та `ctypes.LittleEndianStructure` (Little-Endian).

Повна таблиця зіставлення базових типів `ctypes`, покажчиків, об'єднань та структур наведена у вставці [Зіставлення типів і сигнатур: контракт ctypes та cffi](root:sys-plang-python/ctypes-and-cffi/api-ffi-contracts.md).

## 2. Архітектура cffi та режим компіляції API

Бібліотека `cffi` (*C Foreign Function Interface*) була розроблена Арміном Ріґо та Мацеєм Фіялковським з метою подолання обмежень `ctypes`: усунення помилок ручного опису двійкових структур, прискорення маршалінгу та забезпечення повної інтеграції з JIT-компілятором PyPy.

На відміну від `ctypes`, де структури описуються через спеціальні класи Python, у `cffi` інтерфейс декларується безпосередньо стандартним синтаксисом мови C. Для розбору заголовків використовується вбудований синтаксичний аналізатор `pycparser`. Синтаксичний парсер також розпізнає константи препроцесора `#define MAX_BUFFER 4096` та перелічення `enum`, автоматично роблячи їх доступними як атрибути об'єкта `lib`.

### Чотири режими роботи cffi

Бібліотека `cffi` підтримує 4 режими взаємодії, які комбінують спосіб отримання адрес (ABI проти API) та час генерації коду (In-line проти Out-of-line).

![Матриця архітектурних режимів cffi](/root/sys/sys-plang-python/ctypes-and-cffi/img/cffi-modes-comparison.svg)
*Порівняння чотирьох режимів cffi: залежність від наявності C-компілятора під час запуску та накладні витрати на виконання.*

1. **ABI In-line:**
   Аналог `ctypes`, але з описом інтерфейсу мовою C. Під час запуску програми виконується `ffi.cdef(...)`, де `cffi` парсить декларації, а `ffi.dlopen("lib.so")` вантажить спільний об'єкт. Виклики здійснюються через `libffi`. Компілятор C не потрібен, однак зберігаються накладні витрати динамічного маршалінгу та ризик невідповідності вирівнювання полів.
2. **ABI Out-of-line:**
   Декларації `cdef` парсяться заздалегідь на етапі збірки пакета окремим скриптом, генеруючи Python-модуль. Під час виконання програма лише імпортує готовий модуль та викликає `ffi.dlopen()`. Режим корисний для систем, де немає C-компілятора, але потрібен швидкий запуск без витрат часу на синтаксичний аналіз рядків `cdef`.
3. **API In-line:**
   Розробник вказує C-заголовок та нативний вихідний код у `ffi.set_source()`. Під час першого імпорту `cffi` прозоро викликає встановлений у системі компілятор C (`gcc`, `clang`, `cl.exe`), компілює тимчасовий модуль розширення і завантажує його в пам'ять. Головний недолік — помітна затримка старту процесу при першому запуску.
4. **API Out-of-line (Промисловий стандарт):**
   Код розширення компілюється на етапі збірки проєкту (наприклад, під час формування пакетів `wheel` через `pip wheel` або `setuptools`). Згенерований C-файл містить статичні C-функції обгортки, які викликають цільову бібліотеку напряму. **У цьому режимі `libffi` взагалі не використовується.**

### Подолання ламкості структур у режимі API Out-of-line

Найбільша небезпека режиму ABI (як у `ctypes`, так і в `cffi ABI`) — це приховані розбіжності в розкладці структур (*struct layout*). Якщо в C-заголовку структура містить умовну компіляцію через `#ifdef` або оптимізаційне вирівнювання компілятора, ручна декларація у Python може помилитися на кілька байтів. Читання поля за неправильним зміщенням призводить до спотворення даних (*memory corruption*).

У режимі `cffi API` розробник використовує синтаксис `...;` у тілі структури:

```python
# build_sensor.py
from cffi import FFI

ffibuilder = FFI()

ffibuilder.cdef("""
    typedef struct {
        int sensor_id;
        double calibration_factor;
        ...; /* Невідомі або внутрішні поля та вирівнювання */
    } SensorData;

    int read_sensor(SensorData *dev);
""")

ffibuilder.set_source(
    "_sensor_backend",
    """
    #include <sensor_driver.h>
    """,
    libraries=["sensor_driver"],
)

if __name__ == "__main__":
    ffibuilder.compile(verbose=True)
```

Під час виконання `ffibuilder.compile()` `cffi` генерує C-файл, де для кожного поля структури компілятор обчислює точний зсув за допомогою стандартного макросу `offsetof(SensorData, calibration_factor)` та оператора `sizeof(SensorData)`. Якщо поле відсутнє або має інший тип, C-компілятор видасть помилку компіляції ще на етапі збірки пакета, запобігши фатальному збою під час роботи програми у продакшені.

### Генерація коду розширення та JIT-оптимізація у PyPy

Згенерований CFFI файл розширення (наприклад, `_sensor_backend.c`) містить статичну таблицю функцій та прямі C-виклики:

:::tabs
```c
/* Фрагмент C-коду, згенерованого CFFI у режимі API */
static PyObject *
_cffi_f_read_sensor(PyObject *self, PyObject *arg0)
{
    SensorData *x0;
    int result;

    /* Пряме отримання нативного покажчика з CData */
    if (_cffi_to_c((char *)&x0, _cffi_type(1), arg0) < 0)
        return NULL;

    Py_BEGIN_ALLOW_THREADS
    result = read_sensor(x0); /* Прямий C-виклик без libffi! */
    Py_END_ALLOW_THREADS

    return _cffi_from_c_int(result, int);
}
```
```cpp
// Еквівалентна пряма обгортка у C++ модулі розширення
#include <pybind11/pybind11.h>
#include "sensor_driver.hpp"

namespace py = pybind11;

int read_sensor_cpp(SensorData &dev) {
    py::gil_scoped_release release; // RAII-відпускання та захоплення GIL
    return read_sensor(&dev);       // Прямий виклик нативної функції
}
```
:::

У середовищі PyPy трасувальний JIT-компілятор розпізнає внутрішні операції CFFI і повністю розгортає їх (*inline expansion*), перетворюючи виклик C-функції на одну машинну інструкцію `call` без виділення проміжних об'єктів у купі.

### Вбудовування Python у C-застосунки (CFFI Embedding)

Бібліотека `cffi` підтримує режим зворотної інтеграції (*embedding*): компіляцію логіки Python у стандартну нативну динамічну бібліотеку (`.so` або `.dll`), яка експортує звичайні C-функції. Сторонній застосунок на мові C, C++, Rust або Go завантажує цю бібліотеку через `dlopen()` і викликає функції без знання про те, що всередині працює інтерпретатор Python:

```python
# embedding_build.py
from cffi import FFI

ffibuilder = FFI()

ffibuilder.embedding_api("""
    int calculate_checksum(const char *data, int len);
""")

ffibuilder.embedding_init_code("""
    from _embedded_lib import ffi

    @ffi.def_extern()
    def calculate_checksum(data, length):
        raw_bytes = ffi.buffer(data, length)[:]
        return sum(raw_bytes) % 256
""")

ffibuilder.set_source("_embedded_lib", "")
ffibuilder.compile(target="libchecksum.so", verbose=True)
```

При першому зверненні до функції `calculate_checksum` нативний C-трамплін автоматично ініціалізує середовище виконання CPython (`Py_Initialize()`), завантажує вбудований байткод і передає аргументи у Python.

### Інтеграція зі збіркою pyproject.toml та setuptools

Для автоматичної компіляції CFFI-модуля при встановленні пакета використовується декларація модуля збірки:

```toml
# pyproject.toml
[build-system]
requires = ["setuptools>=61.0", "wheel", "cffi>=1.15.0"]
build-backend = "setuptools.build_meta"

[project]
name = "fastsensor"
version = "0.1.0"
dependencies = [
    "cffi>=1.15.0",
]
```

У файлі `setup.py` або конфігурації збірки вказується посилання на скрипт генератора:

```python

    cffi_modules=["build_sensor.py:ffibuilder"],
)
```

## 3. Керування пам'яттю, життєвий цикл та протокол буфера

При взаємодії з нативним кодом пам'ять розділяється на два принципово різні світи:
1. **Керована купа Python (Python Managed Heap):** об'єкти створюються алокатором `pymalloc` або `PyMem_Malloc()`, їхній життєвий цикл контролюється лічильником посилань (`ob_refcnt`) та збирачем циклічного сміття (Cycle GC).
2. **Сира нативна пам'ять (Raw Native Memory):** байти виділяються через системний алокатор `malloc()` або `posix_memalign()` і повинні бути явно вивільнені через `free()`.

![Керування пам'яттю та життєвий цикл GIL](/root/sys/sys-plang-python/ctypes-and-cffi/img/memory-and-gil-flow.svg)
*Взаємодія між керованою пам'яттю Python та нативними буферами: автоматичне звільнення пам'яті за допомогою ffi.gc(), робота протоколу буфера та поведінка GIL під час FFI-викликів.*

### Запобігання витокам пам'яті та Use-After-Free через ffi.gc()

Класична помилка при роботі з `ctypes` полягає у втраті зв'язку між об'єктом-володарем і сирим покажчиком. Якщо Python-об'єкт, що містить буфер пам'яті, знищується збирачем сміття, нативний C-код отримує «висячий покажчик» (*dangling pointer*), звернення до якого призводить до помилки використання після вивільнення (*Use-After-Free*, UAF).

Модуль `cffi` вирішує цю проблему за допомогою функції `ffi.gc(cdata, destructor)`:

```python
from _sensor_backend import ffi, lib

def create_managed_context():
    # Нативна функція C виділяє пам'ять через malloc()
    raw_ctx = lib.sensor_context_create()
    if raw_ctx == ffi.NULL:
        raise MemoryError("Не вдалося ініціалізувати нативний контекст")

    # Прив'язуємо C-деструктор до об'єкта cdata
    # Коли gc_ctx збирається GC Python, автоматично викликається sensor_context_destroy(raw_ctx)
    gc_ctx = ffi.gc(raw_ctx, lib.sensor_context_destroy)
    return gc_ctx
```

Об'єкт `gc_ctx` можна вільно передавати між функціями або зберігати в структурах Python. Коли кількість посилань на `gc_ctx` падає до нуля, CPython викликає фіналізатор об'єкта, який гарантовано передає сирий покажчик функції `sensor_context_destroy()`.

### Протокол буфера (Buffer Protocol) і передача даних без копіювання

Копіювання великих масивів даних (зокрема зображень, аудіопотоків, тензорів нейромереж або великих бінарних файлів) між структурами Python та C-функціями створює критичне навантаження на підсистему пам'яті. Для вирішення цього завдання використовується протокол буфера CPython (*Buffer Protocol*, структура `Py_buffer`).

Об'єкти Python, такі як `bytearray`, `memoryview`, стандартний `array.array` або масиви `numpy.ndarray`, експортують пряму адресу свого внутрішнього суцільного блоку пам'яті через структуру `Py_buffer`, що містить покажчик `buf`, загальну довжину `len`, розмір елемента `itemsize` та масиви розмірностей `shape` і кроків `strides`.

#### Передача без копіювання в ctypes

У `ctypes` доступ до пам'яті буферних об'єктів здійснюється через метод `from_buffer()`:

```python
import ctypes

# Створюємо мутабельний байтовий буфер розміром 1 МБ
buffer_data = bytearray(1024 * 1024)

# Отримуємо обгортку ctypes над тим самим блоком пам'яті (без копіювання!)
c_buffer = (ctypes.c_uint8 * len(buffer_data)).from_buffer(buffer_data)

# Передаємо покажчик нативній C-функції
lib.process_raw_bytes(c_buffer, len(buffer_data))
```

#### Передача без копіювання в cffi

У `cffi` аналогічну операцію виконує метод `ffi.from_buffer()`:

```python
# Пряме отримання cdata покажчика на пам'ять bytearray/memoryview
c_ptr = ffi.from_buffer("uint8_t[]", buffer_data)

lib.process_raw_bytes(c_ptr, len(buffer_data))
```

Функція `ffi.from_buffer()` створює легко вагомий об'єкт `cdata`, який утримує блокування буфера Python (запобігаючи зміні розміру або релокації масиву в пам'яті) і надає прямий покажчик на машинну пам'ять із нульовими витратами процесорного часу на копіювання.

### Зрізи пам'яті та багатовимірні масиви

Якщо C-функції потрібно передати лише піддіапазон великого буфера, створення звичайного зрізу `buffer_data[100:500]` створило б новий об'єкт `bytearray` з повним копіюванням байтів. Використання `memoryview` усуває це копіювання:

```python
# Створюємо нуль-копійний зріз віртуального вікна пам'яті
sub_view = memoryview(buffer_data)[100:500]

# cffi миттєво отримує зміщену адресу buf + 100
sub_ptr = ffi.from_buffer("uint8_t[]", sub_view)
lib.process_raw_bytes(sub_ptr, len(sub_view))
```

Для багатовимірних масивів критично контролювати неперервність розташування рядків у пам'яті: C-функції за замовчуванням очікують суцільне розташування рядків (*C-contiguous*), тоді як транспоновані або фортранівські масиви (*F-contiguous*) мають ненульові кроки зміщень `strides` і вимагають явного вирівнювання перед передачею в нативний код.

## 4. Багатопотоковість, поведінка GIL та C-зворотні виклики

Однією з найважливіших переваг використання C-бібліотек у Python є можливість обходу глобального блокування інтерпретатора (*Global Interpreter Lock*, GIL).

### Відпускання GIL під час виконання нативного коду

Коли C-код виконує складні математичні розрахунки, криптографічні операції чи блокувальний ввід-вивід, утримувати GIL недоцільно: блокування заважає іншим потокам Python виконувати байткод на сусідніх ядрах процесора.

1. **Поведінка `ctypes`:**
   У модулі `ctypes` будь-який виклик функції через екземпляр `CDLL` або `WinDLL` **автоматично відпускає GIL** перед викликом `ffi_call()` за допомогою макросу `Py_BEGIN_ALLOW_THREADS` (виклик C-функції `PyEval_SaveThread()`). Після завершення роботи функції потік повертає блокування через `Py_END_ALLOW_THREADS` (`PyEval_RestoreThread()`).
2. **Поведінка `cffi`:**
   У режимі `cffi API` за замовчуванням усі виклики функцій також автоматично відпускають і захоплюють GIL. Якщо функція є короткою і викликається мільйони разів у циклі, накладні витрати на синхронізацію GIL (атомарні операції та робота з чергою м'ютекса інтерпретатора) можуть перевищувати час виконання самої функції. У такому разі в `cdef` можна додати специфікатор `no_gil`:

```python
ffibuilder.cdef("""
    /* Функція виконується без відпускання GIL (економія ~30-50 нс на виклик) */
    int fast_inline_math(int x) no_gil;
""")
```

### Free-Threaded Python 3.13 (PEP 703) та FFI

У збірках CPython без GIL (*Free-Threaded CPython*) нативні виклики через FFI отримують додаткову перевагу: одночасні виклики C-функцій з різних потоків більше не конкурують за глобальний м'ютекс інтерпретатора. Однак це накладає суворі вимоги на потокобезпечність самої C-бібліотеки:
- Функції бібліотеки C повинні бути реентерабельними (*reentrant*).
- Спільні нативні ресурси повинні захищатися внутрішніми м'ютексами (`pthread_mutex_t` або `std::mutex`).
- Використання статичних змінних всередині C-функцій без блокувань стає джерелом стану гонитви (*race conditions*).

### Обробка сигналів POSIX під час виконання C-коду

Коли потік операційної системи виконує C-код з відпущеним GIL, обробники сигналів Python (наприклад, сигнал переривання `SIGINT` при натисканні Ctrl+C) не можуть виконатися негайно. Ядро ОС встановлює прапорець сигналу в C-структурі процесу, проте відповідний Python-виняток `KeyboardInterrupt` буде згенеровано лише в той момент, коли C-функція поверне керування, потік захопить GIL і інтерпретатор перевірить чергу сигналів (`PyErr_CheckSignals()`). Якщо C-функція зависає у нескінченному циклі без системних викликів, зупинити процес можна лише аварійним сигналом `SIGKILL`.

### Зворотні виклики (Callbacks): виклик Python із мови C

Багато C-бібліотек вимагають передачі покажчиків на функції зворотного виклику (*callback* — від англ. *call* — виклик + *back* — назад), наприклад, для кастомного сортування масивів, фільтрації пакетів або обробки подій графічного вікна.

#### Механізм зворотних викликів у ctypes

У `ctypes` тип функції-колбека створюється фабрикою `ctypes.CFUNCTYPE(restype, *argtypes)`:

```python
import ctypes

# 1. Визначаємо прототип функції: (повертає int, приймає два int)
CMP_FUNC_TYPE = ctypes.CFUNCTYPE(ctypes.c_int, ctypes.c_int, ctypes.c_int)

# 2. Пишемо звичайну функцію Python
def my_comparator(a, b):
    return (a > b) - (a < b)

# 3. Створюємо C-покажчик на функцію (C-callable object)
c_callback = CMP_FUNC_TYPE(my_comparator)

# 4. Передаємо в C-бібліотеку
lib.quick_sort(array_ptr, size, c_callback)
```

> [!CAUTION]
> **Небезпека передчасного збирання сміття (GC Garbage Collection):**
> Об'єкт `c_callback` повинен обов'язково утримуватися активним посиланням у пам'яті Python протягом усього часу, поки C-бібліотека може його викликати. Якщо посилання зникне, збирач сміття видалить об'єкт-трамплін, і наступний виклик із C спробує виконати пам'ять за недійсною адресою, викликавши миттєвий крах процесу.

#### Механізм зворотних викликів у cffi (@ffi.def_extern)

У `cffi` зворотні виклики реалізовані безпечніше за допомогою механізму `@ffi.def_extern()`:

```python
# build_events.py
ffibuilder.cdef("""
    typedef void (*event_handler_t)(int event_id, const char *msg);
    void register_handler(event_handler_t handler);

    /* Оголошуємо зовнішню функцію Python */
    extern "Python" void python_event_receiver(int event_id, const char *msg);
""")
```

У коді програми:

```python
from _events import ffi, lib

@ffi.def_extern()
def python_event_receiver(event_id, msg):
    message_str = ffi.string(msg).decode('utf-8')
    print(f"Отримано подію {event_id}: {message_str}")

# Передаємо згенерований C-символ
lib.register_handler(lib.python_event_receiver)
```

Коли C-код викликає `lib.python_event_receiver`, керування потрапляє на згенерований під час компіляції C-трамплін. Цей трамплін виконує такі кроки:
1. Викликає функцію `PyGILState_Ensure()`: якщо виклик надійшов із нативного фонового потоку операційної системи, який ніколи не бачив Python, CPython автоматично створює для нього локальний стан потоку (`PyThreadState`) та захоплює GIL.
2. Конвертує нативні аргументи у формат `cdata`.
3. Викликає Python-функцію `python_event_receiver`.
4. Якщо у Python-коді виникає необроблений виняток (*Exception*), CFFI перехоплює його, друкує трасування стека у `sys.stderr` і повертає з C-функції значення за замовчуванням, не дозволяючи винятку Python зруйнувати C-стек.
5. Викликає `PyGILState_Release()`, відновлюючи стан блокування потоку.

## 5. Порівняльний аналіз швидкодії та критерії вибору

Вибір між `ctypes`, `cffi ABI`, `cffi API` або повноцінними C-розширеннями базується на балансі між швидкістю виконання, простотою розгортання та вимогами до компілятора.

### Структура накладних витрат на один виклик

Розрахуємо теоретичні витрати часу на виклик простої скалярної C-функції (наприклад, додавання двох цілих чисел `int add(int a, int b)`):

```
Накладні витрати виклику = T_unpack + T_cif + T_call + T_gil + T_pack

Де:
T_unpack : вилучення C-значення з об'єктів PyObject (цілочисельний розпаковщик)
T_cif    : підготовка структури аргументів libffi (відсутня в API режимі)
T_call   : асемблерний перехід (регістри процесора або стек)
T_gil    : збереження та відновлення стану GIL потоку
T_pack   : створення результуючого об'єкта PyObject
```

У числових показниках на сучасному процесорі x86-64:
- **`ctypes`:** ~100–130 нс на виклик (динамічний пошук типів, динамічна розкладка `libffi`, перемикання GIL).
- **`cffi ABI`:** ~70–90 нс на виклик (оптимізований парсинг C-типів, але збереження `libffi`).
- **`cffi API (Out-of-line)`:** **~8–15 нс на виклик** (прямий виклик скомпільованої C-функції, відсутність посередників).
- **Пряме C-розширення (Python/C API):** ~5–10 нс на виклик.

Детальний benchmark-проект з вимірюванням пропускної здатності векторних обчислень та роботи з пам'яттю наведено у вставці [Профілювання та оптимізація FFI-межі: бенчмарк ctypes, cffi та C-розширень](root:sys-plang-python/ctypes-and-cffi/proj-ffi-benchmarking.md).

### Критерії вибору інструменту

| Критерій | `ctypes` | `cffi` (ABI Mode) | `cffi` (API Out-of-line) | C-розширення / Cython / PyBind11 |
| :--- | :--- | :--- | :--- | :--- |
| **Наявність у стандартній бібліотеці** | Так (з коробки) | Потрібен `pip install` | Потрібен `pip install` | Потрібні сторонні інструменти |
| **Потреба у C-компіляторі** | **Ні** | **Ні** | **Так** (на етапі збірки) | **Так** (на етапі збірки) |
| **Швидкодія одиночних викликів** | Низька (~120 нс) | Середня (~80 нс) | **Висока (~10 нс)** | **Максимальна (~5 нс)** |
| **Сумісність з PyPy (JIT)** | Погана (руйнує JIT) | Посередня | **Ідеальна (інлайнінг)** | Обмежена (через емуляцію cpyext) |
| **Стійкість до зміни C-структур** | Низька (ручний розрахунок) | Низька | **Абсолютна (компілятор C)**| **Абсолютна (компілятор C)** |
| **Безпека зворотних викликів (Callbacks)**| Ризик падіння GC | Ризик падіння GC | **Вбудований захист GILState**| Потребує ручного керування GIL |

### Архітектурний вибір у сучасній екосистемі Python

Практика великих проектів демонструє чіткий поділ сфер застосування FFI:
- Пакет **`cryptography`** повністю відмовився від класичного Python/C API на користь `cffi API Out-of-line` для зв'язування з OpenSSL. Це дозволило позбутися сотень рядків ручного маршалінгу пам'яті, гарантувати відповідність структур версіям OpenSSL на етапі збірки та забезпечити однакову високу швидкість роботи як на CPython, так і на PyPy.
- Бібліотека **`pynacl`** використовує `cffi` для прив'язки до бібліотеки `libsodium`, отримуючи автоматичний захист від витоків чутливих ключів завдяки детермінованому деструктору `ffi.gc()`.
- Стандартний модуль **`uuid`** використовує `ctypes` для прямого виклику системних функцій генерації UUID (`uuid_generate_time` з `libuuid.so` у Linux або `UuidCreate` з `Rpcrt4.dll` у Windows), оскільки стандартна бібліотека не може мати зовнішніх залежностей на етапі встановлення.
- Якщо необхідно створити прив'язку до складного об'єктно-орієнтованого фреймворку C++ (з поліморфізмом, шаблонами, класами та винятками C++), інструменти на кшталт **PyBind11** або **Cython** є зручнішими за CFFI, оскільки вони здатні автоматично генерувати C++ транслятори для `std::vector`, `std::string` та ловити винятки `std::exception`. Проте для чистих C-бібліотек та криптографії `cffi API` залишається найнадійнішим стандартом індустрії.

> 🔧 **Навіщо це в реальній розробці:**
> - Якщо ви пишете швидкий системний скрипт для Linux/Windows, утиліту адміністрування або невеликий GUI-застосунок, де критично **не мати жодних зовнішніх залежностей** і збирачів — обирайте стандартний `ctypes`.
> - Якщо ви розробляєте промислову бібліотеку для роботи з криптографією, мережевими драйверами, аудіо/відео кодеками або базами даних, яка поширюється у вигляді `wheel`-пакетів на PyPI — стандартом індустрії є **`cffi` у режимі API Out-of-line**. Він гарантує надійність двійкових структур, максимальну швидкість виконання на CPython та бездоганну оптимізацію під JIT-компілятор PyPy.
