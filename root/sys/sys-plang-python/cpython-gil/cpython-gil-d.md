Запуск чотирьох системних потоків `threading.Thread` на чотириядерному процесорі для паралельного виконання математичних розрахунків на чистому Python демонструє несподіваний результат: замість очікуваного чотирикратного прискорення загальний час обчислень збільшується на 20–30% порівняно з простим однопотоковим циклом. Системний монітор `top` при цьому фіксує 400% навантаження CPU. Чотири процесорні ядра працюють на повній потужності, але корисна робота не виконується — ресурси апаратури поглинаються внутрішньою боротьбою потоків за право виконувати байткод інтерпретатора.

Причиною такої поведінки є Global Interpreter Lock (GIL, від англ. *global* — всеохопний, *interpreter* — тлумач, перекладач, *lock* — замок) — системний м'ютекс (*mutex*, від англ. *mutual exclusion* — взаємне виключення), що захищає структури даних інтерпретатора CPython від одночасного доступу з боку кількох потоків виконання (*thread*, від англ. *thread* — нитка, потік).

## 1. Фізична природа GIL та проблема паралелізму в CPython

Еталонна реалізація Python — CPython — є стек-орієнтованою віртуальною машиною, написаною мовою C. Кожен об'єкт у динамічній пам'яті (число, рядок, список, словник, функція, модуль) представлений у купі структурою `PyObject`. Заголовок цієї структури містить 64-бітне цілочисельне поле `ob_refcnt` — лічильник активних посилань на об'єкт у програмі.

Керування пам'яттю в CPython побудоване на детермінованому підрахунку посилань. Будь-яка базова операція над об'єктом вимагає негайного оновлення цього лічильника:
- Прив'язка об'єкта до нової змінної викликає макрос `Py_INCREF()`, що інкрементує `ob_refcnt`.
- Передача об'єкта як аргументу у функцію або додавання до списку також викликає `Py_INCREF()`.
- Вихід змінної з локальної області видимості або видалення елемента зі словника викликає макрос `Py_DECREF()`.
- Коли значення `ob_refcnt` стає рівним нулю, інтерпретатор негайно викликає деструктор `tp_dealloc` і повертає виділену пам'ять у внутрішній пул алокатора (*allocator*, від лат. *allocare* — розміщувати).

```
[Об'єкт PyObject у купі пам'яті]
+------------------------------------+
| ob_refcnt : uint64_t (лічильник)   |  <--- Будь-яке читання чи запис змінює це поле
+------------------------------------+
| ob_type   : struct _typeobject*    |  <--- Покажчик на тип об'єкта (int, str, list)
+------------------------------------+
| Дані об'єкта (значення, поля)      |
+------------------------------------+
```

### Стан гонитви на лічильниках посилань

Потоки модуля `threading` у Python не є псевдопотоками чи зеленими нитками: це реальні системні потоки ядра операційної системи (`pthread_t` у Linux/macOS або Win32 Threads у Windows), кожен з яких має власний стек викликів і планується безпосередньо планувальником ядра ОС.

Якби інтерпретатор дозволив двом потокам на різних процесорних ядрах одночасно виконувати байткод без глобальної синхронізації, виникали б неминучі стани гонитви (*race conditions*). Операція `ob_refcnt++` на рівні машинних інструкцій процесора x86-64 не є атомарною і складається з трьох окремих мікроінструкцій:

```
mov rax, [rdi + 0]    ; 1. Зчитування ob_refcnt з ОЗП або кешу в регістр CPU
add rax, 1            ; 2. Збільшення значення в регістрі на 1
mov [rdi + 0], rax    ; 3. Запис оновленого значення назад у пам'ять
```

Якщо Потік 1 на Ядрі 0 і Потік 2 на Ядрі 1 одночасно зчитують початкове значення `ob_refcnt = 1`, обидва інкрементують його до `2` у своїх реєстрах і записують результат назад, підсумкове значення стане рівним `2` замість правильного `3`. 

Коли надалі обидва потоки завершать використання об'єкта і викличуть `Py_DECREF()`, лічильник двічі зменшиться і стане рівним `0`, хоча в пам'яті все ще залишається третє активне посилання. Інтерпретатор вивільнить пам'ять живого об'єкта, що призведе до критичного збою пошкодження купи (*heap corruption*) або аварійного завершення *use-after-free* при наступному зверненні.

### Чому не дрібногранулярні замки

Альтернативою глобальному замку могло б стати встановлення окремого м'ютекса всередині кожного об'єкта `PyObject` або заміна лічильників на атомарні змінні процесора з префіксом `LOCK` (`atomic_fetch_add`).

Проте кожна атомарна інструкція на рівні процесорної шини блокує лінію L1/L2 кешу для забезпечення протоколу когерентності (*cache coherency*, протокол MESI). Навіть на однопотокових задачах постійні атомарні операції під час кожного присвоєння змінної чи читання словника уповільнюють виконання програми на 30–50%. Крім того, наявність м'ютекса в кожному об'єкті збільшила б розмір базових типів у пам'яті щонайменше вдвічі.

Тому творець Python Ґвідо ван Россум обрав простіше й ефективніше для однопотокових задач рішення: один спільний глобальний м'ютекс для всього процесу. Потік має право читати й модифікувати будь-які об'єкти Python, стек та глобальні словники лише тоді, коли він захопив цей єдиний замок. Детальний аналіз історії виникнення GIL, патча Ґреґа Стайна та наступних спроб реформування наведено у вставці [Еволюція та спроби видалення GIL у CPython](root:sys-plang-python/cpython-gil/hist-gil-origins-and-attempts.md).

## 2. Внутрішня архітектура GIL у ядрі CPython

У вихідному коді CPython (файли `Include/internal/pycore_ceval.h` та `Python/ceval_gil.h`) механізм блокування інтерпретатора інкапсульовано в структурі `struct _gil_runtime_state`:

:::tabs
```c
// pycore_ceval.h
struct _gil_runtime_state {
    /* Атомарний інтервал перемикання потоків у мікросекундах */
    unsigned long interval;
    
    /* Прапорець стану: 1 - замок зайнятий, 0 - вільний */
    _Py_atomic_int locked;
    
    /* Системний м'ютекс ОС для захисту самого стану GIL */
    PyMUTEX_T mutex;
    
    /* Умовна змінна ОС для сповіщення потоків, що чекають */
    PyCOND_T cond;
    
    /* Умовна змінна для підтвердження передачі керування */
    PyCOND_T switch_cond;
    
    /* Покажчик на стан потоку (PyThreadState), що останнім утримував GIL */
    _Py_atomic_address last_holder;
};
```
```cpp
// pycore_ceval.hpp (еквівалентне представлення структури стану GIL)
struct alignas(64) GILRuntimeState {
    unsigned long interval{5000};
    std::atomic<int> locked{0};
    PyMUTEX_T mutex{};
    PyCOND_T cond{};
    PyCOND_T switch_cond{};
    std::atomic<PyThreadState*> last_holder{nullptr};
};
```
:::

Головний цикл виконання байткоду інтерпретатора зосереджений у C-функції `_PyEval_EvalFrameDefault()`. Ця функція в нескінченному циклі `for (;;)` вибирає чергову інструкцію (опкод) скомпільованого кадру і переходить до відповідного обробника через гігантський перемикач `switch-case`.

![Архітектура GIL та цикл виконання байткоду в CPython](/root/sys/sys-plang-python/cpython-gil/img/gil-mutex-architecture.svg)
*Схема внутрішнього устрою GIL у CPython: взаємодія системних потоків ОС, м'ютекса ядра та циклу інтерпретації байткоду.*

### Життєвий цикл потоку в CPython

Коли програма створює та запускає потік `threading.Thread(target=worker).start()`, послідовність низькорівневих операцій розгортається наступним чином:

1. **Створення стану потоку:** Інтерпретатор виділяє в купі структуру `PyThreadState`, яка містить покажчик на стек кадрів виконання (`PyFrameObject`), локальні словники та статус винятків.
2. **Системний виклик ОС:** CPython викликає `pthread_create()` (або `_beginthreadex()` у Windows), передаючи адресу внутрішньої функції-обгортки `t_bootstrap`.
3. **Очікування GIL:** Новостворений системний потік починає виконання, але перш ніж прочитати хоча б один байткодовий опкод цільової функції `worker`, він зобов'язаний викликати функцію `take_gil(tstate)`.
4. **Блокування:** Якщо головний потік уже утримує GIL, новий потік переходить у стан очікування, блокуючись на умовній змінній `PyCOND_WAIT(&gil->cond, &gil->mutex)`. Планувальник ядра ОС виводить цей потік з черги виконання на процесорі й переводить його в стан сну (`TASK_INTERRUPTIBLE` у Linux).
5. **Виконання:** Щойно головний потік відпускає замок, потік, що очікував, пробуджується, виставляє `locked = 1`, записує свій `tstate` у поле `last_holder` і починає виконання циклу `_PyEval_EvalFrameDefault()`.

Повний довідник макросів та C API функцій для низькорівневого контролю стану потоку представлено у вставці [Довідник API керування GIL: C-макроси, стан інтерпретатора та системні параметри](root:sys-plang-python/cpython-gil/api-gil-management.md).

## 3. Механізм перемикання потоків та явище GIL Thrashing

Якщо програма запускає кілька обчислювальних потоків, які не виконують операцій вводу-виводу, інтерпретатор повинен примусово перемикати керування між ними, щоб жоден потік не монополізував процесор.

### Інтервал перемикання: sys.getswitchinterval()

Починаючи з Python 3.2, квантування часу в інтерпретаторі спирається на фіксований часовий інтервал `switch_interval`, значення якого за замовчуванням становить `0.005` секунди (5 мілісекунд). Перевірити або змінити це значення можна за допомогою функцій `sys.getswitchinterval()` та `sys.setswitchinterval()`.

Перемикання відбувається за чітким протоколом кооперативного витіснення:

1. Потік 1 утримує GIL і виконує обчислювальний цикл байткоду на Ядрі 0.
2. Потік 2 намагається захопити GIL і блокується на системній умовній змінній `PyCOND_TIMEDWAIT(&gil->cond, &gil->mutex, 5000)`.
3. Якщо за 5 мс Потік 1 добровільно не відпустив GIL, таймер `PyCOND_TIMEDWAIT` спрацьовує. Потік 2 прокидається і встановлює атомарний сигнальний прапорець `gil_drop_request = 1` (у сучасних версіях — сигнальне поле `eval_breaker` у заголовку структури інтерпретатора).
4. Потік 1 після завершення поточної інструкції байткоду перевіряє `eval_breaker`. Побачивши запит на вивільнення, Потік 1 призупиняє виконання, викликає `drop_gil(tstate)`, виставляє `locked = 0` і викликає `PyCOND_SIGNAL(&gil->cond)`, сповіщаючи інші потоки.
5. Щоб Потік 1 негайно знову не захопив замок, він викликає `PyCOND_WAIT(&gil->switch_cond, &gil->mutex)` і чекає, поки Потік 2 підтвердить, що він успішно захопив GIL.

![Конкуренція за GIL та явище GIL Thrashing на багатоядерному процесорі](/root/sys/sys-plang-python/cpython-gil/img/gil-thrashing-multicore.svg)
*Часова діаграма виникнення GIL Thrashing: конфлікт ядер при перехопленні м'ютекса та марні витрати квантів планувальника ОС.*

### Чому виникає GIL Thrashing на багатоядерних системах

На одноядерному процесорі ця схема працює майже бездоганно: коли Потік 1 засинає, планувальник ОС перемикає єдине ядро на Потік 2.

Проте на багатоядерних системах виникає деструктивне явище, відоме як **GIL Thrashing** (від англ. *thrashing* — биття, метання) або ефект конвою (*convoy effect*):

1. Потік 1 працює на Ядрі 0, а Потік 2 спить на Ядрі 1.
2. Після 5 мс Потік 2 виставляє запит `gil_drop_request = 1` і чекає.
3. Потік 1 на Ядрі 0 скидає GIL і надсилає сигнал пробудження через системний виклик ядра ОС `futex_wake()` (у Linux).
4. Системний виклик `futex_wake()` вимагає взаємодії між ядрами процесора (*Inter-Processor Interrupt*, IPI) та планувальником ОС. Час реакції планувальника на пробудження сплячого потоку становить від `20` до `80` мікросекунд.
5. Тим часом Потік 1 на Ядрі 0 завершує системний виклик скидання і, якщо в коді є наступні інструкції, миттєво знову намагається захопити GIL. Оскільки структура м'ютекса `gil_mutex` уже гаряча в L1/L2 кеші Ядра 0, Потік 1 захоплює її за 10–20 наносекунд — задовго до того, як Ядро 1 встигне фізично запустити Потік 2!
6. Коли Потік 2 на Ядрі 1 нарешті прокидається, він виявляє, що GIL уже знову зайнятий Потоком 1. Потік 2 марно витрачає процесорний час і знову ініціює системний виклик `futex_wait()`, повертаючись у стан сну.

У результаті виникає стан безперервної конфронтації: мільйони системних викликів ядра ОС, постійна інвалідація кеш-ліній між ядрами процесора через протокол MESI та гігантські накладні витрати часу. Замість корисної роботи процесор витрачає такти на марні перемикання контексту.

## 4. Розподіл задач: чому I/O-bound прискорюється, а CPU-bound сповільнюється

Вплив GIL на швидкодію програми залежить від природи обчислювального навантаження. Усі задачі поділяються на два принципово різні класи: I/O-bound (обмежені вводом-виводом) та CPU-bound (обмежені обчислювальною потужністю процесора).

```
Характер задачі
├── I/O-Bound (мережа, файли, сокети, запити до БД)
│   └── Потоки threading ДАЮТЬ прискорення (GIL добровільно відпускається)
│
└── CPU-Bound (матричні розрахунки, парсинг JSON, обробка зображень на Python)
    └── Потоки threading ДЕГРАДУЮТЬ (GIL Thrashing і черга за один замок)
```

### Механіка прискорення I/O-bound задач

Коли потік у Python виконує операцію вводу-виводу (наприклад, читання з мережевого сокета `sock.recv(4096)`, запис у файл на диску `f.write(data)` або очікування відповіді від бази даних), низькорівнева реалізація функції в C-коді CPython огортає блокувальний системний виклик спеціальними макросами:

:::tabs
```c
// socket_wrapper.c
#include <Python.h>
#include <sys/socket.h>

ssize_t custom_socket_receive(int socket_fd, void *buffer, size_t size) {
    ssize_t bytes_read;
    
    Py_BEGIN_ALLOW_THREADS
    /* GIL вивільнено! Поточний потік не виконує байткод Python.
       Інтерпретатор вільний для виконання інших потоків. */
    bytes_read = recv(socket_fd, buffer, size, 0);
    Py_END_ALLOW_THREADS
    /* Після отримання даних потік знову захоплює GIL для створення об'єкта bytes */
    
    return bytes_read;
}
```
```cpp
// socket_wrapper.cpp
#include <Python.h>
#include <sys/socket.h>
#include <span>
#include <cstddef>

ssize_t custom_socket_receive_cpp(int socket_fd, std::span<char> buffer) noexcept {
    ssize_t bytes_read = 0;
    
    Py_BEGIN_ALLOW_THREADS
    bytes_read = recv(socket_fd, buffer.data(), buffer.size(), 0);
    Py_END_ALLOW_THREADS
    
    return bytes_read;
}
```
:::

У момент виклику `Py_BEGIN_ALLOW_THREADS` потік добровільно віддає GIL. Поки операційна система очікує прибуття мережевих пакетів від віддаленого сервера, інші 10, 50 чи 100 потоків Python можуть безперешкодно виконувати свій код. 

Математична модель часу виконання для `N` паралельних I/O-запитів показує суттєвий виграш:

```
T_serial = ∑(T_cpu_i + T_io_i)                    [послідовне виконання: сума всіх затримок]
T_threaded = ∑(T_cpu_i) + max(T_io_1, ..., T_io_N) [багатопотокове: затримки I/O перекриваються]
```

Оскільки час очікування мережі `T_io` зазвичай на кілька порядків перевищує час обробки в інтерпретаторі `T_cpu` (мілісекунди проти мікросекунд), багатопотоковість у задачах веб-скрейпінгу, мережевих серверів та мікросервісів дає практично лінійне прискорення відгуку.

### Механіка деградації CPU-bound задач

У чисто обчислювальних задачах (наприклад, розрахунок контрольних сум, обробка векторів на чистому Python, чисельне інтегрування) код безперервно маніпулює об'єктами Python:

```python
def compute_heavy(n):
    total = 0
    for i in range(n):
        total += (i * i) % 1234567
    return total
```

У цьому циклі немає жодного виклику функцій ОС або I/O-операцій, які б відпускали GIL. Кожна операція додавання чисел створює новий проміжний об'єкт `int` або змінює лічильники посилань. Потоки не можуть виконуватися паралельно: вони шикуються в чергу і виконуються строго по черзі через кожні 5 мс, додаючи накладні витрати на перемикання контексту:

```
T_total(N) = T_work + N · T_context_switch + T_contention_overhead
```

Оскільки `T_work` не зменшується (лише одне ядро CPU виконує код у кожен момент часу), а доданки `T_context_switch` та `T_contention_overhead` невпинно зростають зі збільшенням кількості потоків `N`, багатопотокова версія гарантовано працює повільніше за однопотокову.

## 5. Способи обходу GIL та масштабування обчислень

Для досягнення реального паралелізму на багатоядерних процесорах в екосистемі Python застосовують чотири фундаментальні архітектурні підходи.

### 1. Багатопроцесорність: модуль multiprocessing

Найпростіший спосіб обійти GIL на рівні стандартної бібліотеки — замінити потоки на процеси операційної системи за допомогою модуля `multiprocessing` або `concurrent.futures.ProcessPoolExecutor`.

Кожен процес ОС має власний повністю ізольований адресний простір, власний екземпляр віртуальної машини CPython і свій власний незалежний GIL. Чотири процеси виконуються на чотирьох фізичних ядрах абсолютно паралельно без жодної взаємної конкуренції за блокування.

```
Процес 1 [CPython VM + GIL 1] ---> Ядро CPU 0 (100% завантаження)
Процес 2 [CPython VM + GIL 2] ---> Ядро CPU 1 (100% завантаження)
Процес 3 [CPython VM + GIL 3] ---> Ядро CPU 2 (100% завантаження)
Процес 4 [CPython VM + GIL 4] ---> Ядро CPU 3 (100% завантаження)
```

Головним обмеженням стандартного `multiprocessing` є необхідність міжпроцесорного обміну даними (IPC, *Inter-Process Communication*). Коли головний процес передає аргументи дочірньому процесу через `multiprocessing.Queue` або системні канали (*pipes*), дані проходять через трирівневий конвеєр:
1. **Серіалізація (Pickling):** Об'єкт Python у пам'яті головного процесу перетворюється в лінійну послідовність байтів модулем `pickle`.
2. **Системна передача:** Байти копіюються з пам'яті процесу в буфер каналу ядра ОС, а звідти — в адресний простір дочірнього процесу.
3. **Десеріалізація (Unpickling):** Дочірній процес зчитує потік байтів і конструює точну копію об'єктів у власній купі пам'яті.

Для великих масивів даних (наприклад, 100 МБ масив NumPy або зображення 4K) час серіалізації `pickle` повністю нівелює весь виграш від паралельного розрахунку.

### 2. Спільна пам'ять (Shared Memory) та нульове копіювання

Щоб усунути накладні витрати на серіалізацію, починаючи з Python 3.8, стандартна бібліотека містить модуль `multiprocessing.shared_memory`.

Замість передачі байтів через сокети чи пайпи, модуль створює спільний анонімний або іменований сегмент пам'яті на рівні операційної системи (виклик `shm_open()` у Linux або `CreateFileMapping()` у Windows). Сторінки фізичної оперативної пам'яті відображаються безпосередньо в таблиці віртуальних сторінок (*page tables*) кожного процесу.

![Порівняння передачі даних через IPC Queue проти Shared Memory](/root/sys/sys-plang-python/cpython-gil/img/multiprocessing-shared-memory.svg)
*Порівняння моделей міжпроцесорного обміну: триразове копіювання з pickle-серіалізацією проти прямого доступу до ОЗП через SharedMemory.*

Процеси монтують масиви `numpy.ndarray` безпосередньо поверх сегмента спільної пам'яті через об'єкт `memoryview`. Час передачі навіть гігабайтних масивів стає нульовим (*zero-copy*), оскільки дані фізично не переміщуються в пам'яті.

### 3. Відпускання GIL у скомпільованих C/C++/Rust розширеннях

Наукові та високопродуктивні бібліотеки (NumPy, SciPy, OpenCV, PyTorch, Polars, TensorFlow) реалізують важкі алгоритми на скомпільованих мовах низького рівня (C, C++, Rust, Fortran).

Усередині C/C++ розширення розробник явно відпускає GIL на час виконання чисельного циклу:

:::tabs
```c
// matrix_simd.c
#include <Python.h>

void fast_matrix_multiply(const float *a, const float *b, float *c, int n) {
    // Відпускаємо GIL: цикл виконуватиметься паралельно з іншими потоками
    Py_BEGIN_ALLOW_THREADS

    #pragma omp parallel for
    for (int i = 0; i < n; ++i) {
        for (int j = 0; j < n; ++j) {
            float sum = 0.0f;
            for (int k = 0; k < n; ++k) {
                sum += a[i * n + k] * b[k * n + j];
            }
            c[i * n + j] = sum;
        }
    }

    // Відновлюємо GIL перед поверненням у простір інтерпретатора
    Py_END_ALLOW_THREADS
}
```
```cpp
// matrix_simd.cpp
#include <Python.h>
#include <vector>
#include <span>
#include <omp.h>

namespace linalg {

void fast_matrix_multiply(std::span<const float> a, std::span<const float> b, 
                          std::span<float> c, int n) noexcept {
    // Звільняємо GIL на час обчислень
    Py_BEGIN_ALLOW_THREADS

    #pragma omp parallel for collapse(2)
    for (int i = 0; i < n; ++i) {
        for (int j = 0; j < n; ++j) {
            float sum = 0.0f;
            for (int k = 0; k < n; ++k) {
                sum += a[i * n + k] * b[k * n + j];
            }
            c[i * n + j] = sum;
        }
    }

    Py_END_ALLOW_THREADS
}

} // namespace linalg
```
:::

Усередині блоку `Py_BEGIN_ALLOW_THREADS` C-код може використовувати технологію OpenMP, заводити власні системні потоки `std::thread` або використовувати векторні інструкції SIMD/AVX2. Інтерпретатор Python у цей час залишається вільним для виконання коду в інших потоках.

Практичну реалізацію стенду обробки потоку телеметрії з детальними вимірюваннями продуктивності для всіх підходів наведено у вставці [Практичне бенчмаркування обробки телеметрії: Threading, Multiprocessing та C-розширення](root:sys-plang-python/cpython-gil/proj-telemetry-benchmarking.md).

### 4. Збірка Free-threaded Python (PEP 703 / Python 3.13+)

Починаючи з версії Python 3.13, у CPython з'явилася офіційна підтримка режиму без глобального замка (*free-threaded build*, бінарний файл `python3.13t`).

У цій збірці GIL повністю видалено з ядра завдяки чотирьом інноваціям керування пам'яттю:
1. **Потокоізольований алокатор mimalloc:** Кожен системний потік виділяє об'єкти з власного локального сегмента пам'яті без глобальних блокувань.
2. **Безсмертні об'єкти (Immortal Objects):** Статичні константи інтерпретатора (`None`, `True`, малі цілі числа, вбудовані методи) мають фіксований прапорець безсмертності — операції `Py_INCREF` та `Py_DECREF` їх не чіпають, усуваючи конфлікти на рівні процесорного кешу.
3. **Зсунутий підрахунок посилань (Biased Reference Counting):** Потік, який створив об'єкт, змінює його лічильник локальними дешевими інструкціями; інші потоки використовують атомарні змінні лише при міжпотоковому зверненні.
4. **Відкладений підрахунок посилань (Deferred Reference Counting):** Для функцій та модулів лічильники посилань не оновлюються під час виклику, а прибирання сміття делеговано циклічному збирачу GC.

У збірці `python3.13t` звичайні потоки `threading.Thread` на чистому Python отримують справжній апаратний паралелізм і лінійно масштабуються на всі ядра процесора без необхідності використання процесів чи C-розширень.

## 6. Порівняльний аналіз та критерії архітектурного вибору

Вибір моделі одночасності в Python залежить від типу навантаження, обсягу даних та вимог до пам'яті:

| Критерій | Потоки (`threading`) | Процеси (`multiprocessing`) | Спільна пам'ять (`SharedMemory`) | C/C++ розширення | Free-threaded (Python 3.13t) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Цільове навантаження** | I/O-bound (мережа, файли, БД) | CPU-bound (ізольовані задачі) | CPU-bound (великі масиви даних) | Важкі чисельні розрахунки, SIMD | Будь-який CPU-bound код на Python |
| **Вплив GIL** | Блокує паралельний CPU-код | Окремий GIL у кожному процесі | Окремий GIL у кожному процесі | GIL явно відпускається | GIL відсутній |
| **Витрати оперативної пам'яті** | Мінімальні (спільна купа) | Високі (дублювання пам'яті) | Помірні (нульове копіювання даних) | Мінімальні | Мінімальні |
| **Накладні витрати IPC** | Відсутні (спільна пам'ять) | Високі (серіалізація `pickle`) | Мінімальні (лише синхронізація) | Відсутні | Відсутні |
| **Складність синхронізації** | Низька (захист спільних змінних) | Низька (ізоляція процесів) | Середня (м'ютекси для спільного буфера) | Висока (нативний код C/C++) | Середня (потрібні замки для спільних структур) |

> 🔧 **Навіщо це.**
>
> 1. Якщо ваша програма чекає на відповіді мережевих сокетів, HTTP-запитів чи запитів до бази даних — сміливо використовуйте `threading` або `asyncio`: GIL не буде перешкодою, оскільки мережевий драйвер відпускає замок перед очікуванням пакетів.
> 2. Якщо потрібно паралельно обробити чисельний масив, матрицю чи кадр відео на всіх ядрах процесора — ніколи не використовуйте стандартні потоки `threading` на чистому Python: замість прискорення ви отримаєте сповільнення через GIL Thrashing. Використовуйте `numpy` (де важкі матричні операції вже відпускають GIL) або пул процесів `multiprocessing` із сегментами `SharedMemory`.
> 3. Якщо проект переходить на Python 3.13+ і всі залежності скомпільовані з підтримкою ABI free-threaded — використовуйте збірку `python3.13t`, яка перетворює стандартний модуль `threading` на повноцінний інструмент паралельних обчислень.
