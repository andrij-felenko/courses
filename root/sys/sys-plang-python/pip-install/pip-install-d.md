## 1. Анатомія запиту та протокол Simple Repository API

Робота менеджера пакетів починається з інтерпретації вимоги (Requirement Specification), заданої користувачем у командному рядку або файлі `requirements.txt` згідно зі стандартом PEP 508. Специфікатор на зразок `requests[security,socks]>=2.28.0,<3.0.0; python_version >= "3.10"` містить базове ім'я проекту, перелік додаткових наборів залежностей (Extras), допустимий діапазон семантичних версій та опціональні маркери оточення (Environment Markers).

Отримавши ім'я цільового проекту, `pip` виконує процедуру нормалізації назви (PEP 503). В екосистемі Python назви з дефісами, крапками чи підкресленнями вважаються еквівалентними, тому рядок зводиться до нижнього регістру, а всі послідовності роздільників `[-_.]+` замінюються на один дефіс `-`. Після цього клієнт конструює URL-адресу ендпоінта проекту відносно базового індексу (за замовчуванням `https://pypi.org/simple/`):

```
https://pypi.org/simple/requests/
```

Клієнт надсилає HTTP GET-запит із заголовком узгодження вмісту `Accept: application/vnd.pypi.simple.v1+json, application/vnd.pypi.simple.v1+html;q=0.2, text/html;q=0.01`. Для підтримки високої швидкодії `pip` використовує пул повторно використовуваних TCP-з'єднань із підтримкою HTTP Keep-Alive та автоматичним експоненційним повторенням запитів (Exponential Backoff) при виникненні тимчасових мережевих помилок або отриманні HTTP-статусу `429 Too Many Requests`.

Якщо сервер підтримує сучасний стандарт PEP 691, він повертає легкий структурований JSON-документ; інакше повертається традиційний HTML-документ стандарту PEP 503.

```
+-----------------------------------------------------------------------------------+
|                        ПРОТОКОЛ ВЗАЄМОДІЇ З РЕПОЗИТОРІЄМ                          |
+-----------------------------------------------------------------------------------+
| 1. Клієнт pip            --> GET /simple/requests/ (Accept: PEP 691 JSON / HTML)  |
| 2. Сервер PyPI / Nexus   <-- 200 OK: Список посилань, файлів, хешів та маркерів   |
| 3. Клієнт pip            --> Оцінка data-requires-python та вибір кандидатів      |
| 4. Клієнт pip            --> GET /packages/.../requests-2.31.0.whl.metadata       |
| 5. Сервер PyPI           <-- 200 OK: Текст METADATA (PEP 658, 4 КБ замість 60 КБ) |
+-----------------------------------------------------------------------------------+
```

У тілі відповіді міститься повний список гіперпосилань на всі опубліковані дистрибутиви проекту. Кожне посилання супроводжується спеціальними метаданими:
- `href` — відносна або абсолютна адреса файлу колеса (`.whl`) або вихідного архіву (`.tar.gz`). Адреса зазвичай містить фрагмент `#sha256=<hex>`, що надає контрольну суму для валідації без надсилання додаткових запитів.
- `data-requires-python` — специфікатор сумісності з версіями інтерпретатора. `pip` перевіряє це поле до завантаження файлу: якщо поточний інтерпретатор не задовольняє умові, артефакт відкидається негайно.
- `data-dist-info-metadata` (або `data-core-metadata` за PEP 658) — вказує, що сервер здатний віддати файл метаданих `METADATA` окремо за адресою `<wheel-url>.metadata`. Це радикально скорочує мережевий трафік, оскільки резолверу більше не потрібно завантажувати повні багатомегабайтні архіви заради читання списку залежностей `Requires-Dist`.
- `data-yanked` (PEP 592) — ознака відкликання релізу автором через виявлені критичні помилки або вразливості безпеки. Відкликані релізи ігноруються, якщо версія не закріплена у запиті користувача абсолютно точно.

### Оцінка маркерів оточення PEP 508

Маркери середовища дозволяють декларативно прив'язувати залежності до властивостей цільової платформи. Під час аналізу метаданих `pip` обчислює предикати відносно системних змінних:
- `os_name` — назва операційної системи (`posix`, `nt`).
- `sys_platform` — платформа (`linux`, `darwin`, `win32`).
- `platform_machine` — архітектура CPU (`x86_64`, `arm64`, `aarch64`, `i386`).
- `python_version` та `python_full_version` — версія мови (`3.11`, `3.12.1`).
- `implementation_name` — реалізація інтерпретатора (`cpython`, `pypy`, `graalpy`).
- `extra` — активний додатковий набір залежностей, запитаний користувачем (наприклад, `requests[socks]`).

Якщо маркер обчислюється як хибний (наприклад, `sys_platform == 'win32'` під час запуску в Linux), відповідна залежність повністю вилучається з графу аналізу ще до звернення до мережі.

### Фільтрація та вибір сумісних коліс (Wheel Tags)

Для кожного знайденого файлу колеса `pip` розбирає його стандартизоване ім'я згідно з PEP 425:

```
{distribution}-{version}(-{build tag})?-{python tag}-{abi tag}-{platform tag}.whl
```

Клієнт формує впорядкований список усіх підтримуваних комбінацій тегів для поточного інтерпретатора CPython за допомогою бібліотеки `packaging.tags` і порівнює їх із властивостями знайдених коліс:
1. **Python Tag:** версія мови (`py3`, `py2.py3`, `cp312`).
2. **ABI Tag:** бінарний інтерфейс додатків (`cp312`, `cp312t` для Free-threaded CPython без блокування GIL, `abi3` для стабільного C API або `none` для чистого Python).
3. **Platform Tag:** операційна система та архітектура процесора (`manylinux_2_28_x86_64`, `musllinux_1_2_aarch64`, `win_amd64`, `macosx_11_0_arm64`, `any`).

Для платформи Linux стандарт сумісності `manylinux` (PEP 513, PEP 571, PEP 599, PEP 600) визначає мінімальну підтримувану версію системної бібліотеки `glibc`. Клієнт зчитує системну версію C-бібліотеки через системний виклик `gnu_get_libc_version()`: якщо колесо скомпільовано під новішу `glibc`, ніж наявна в операційній системі, `pip` відхиляє цей бінарний файл, захищаючи систему від помилок динамічного зв'язування `ELF` під час виконання.

Детальний опис форматів відповідей, полів JSON-схеми та правил узгодження вмісту наведено у вставці [Специфікація Simple Repository API: PEP 503 та PEP 691](root:sys-plang-python/pip-install/api-pep-503.md). Історію переходу від архаїчного `easy_install` та `.egg` до сучасного протоколу Simple API розкрито у вставці [Еволюція менеджерів пакунків: від distutils до pip](root:sys-plang-python/pip-install/hist-pip-evolution.md).

## 2. Алгоритм розв'язання залежностей: resolvelib та Backtracking

Після отримання списку доступних дистрибутивів `pip` переходить до побудови узгодженого графу залежностей. Ця задача належить до класу NP-повних проблем задоволення обмежень (Constraint Satisfaction Problem, CSP), яка математично еквівалентна задачі здійсненності булевих формул (Boolean Satisfiability, SAT).

До версії `pip 20.3` менеджер застосовував спрощений жадібний (greedy) алгоритм: якщо перший пакет у списку вимагав `urllib3<1.27`, а десятий пакет у ланцюгу транзитивних залежностей вимагав `urllib3>=2.0`, `pip` встановлював останню версію, не перевіряючи попередніх обмежень, що призводило до «тихого псування» середовища (Silent Downgrades та зламані ромбоподібні залежності Diamond Dependencies).

Сучасний `pip` використовує ядро на базі бібліотеки `resolvelib`. Алгоритм працює через цикл зворотного пошуку (Backtracking Search) і взаємодіє з трьома абстрактними компонентами:
1. **`Provider`:** постачальник кандидатів. Він відповідає на запитання «які версії пакета `X` доступні?» та «які вимоги висуває кандидат `X==1.2.0`?». Постачальник враховує маркери PEP 508 (наприклад, `sys_platform == "linux"` або `implementation_name == "cpython"`), відсікаючи невідповідні гілки ще до початку аналізу.
2. **`Reporter`:** спостерігач за ходом пошуку, що збирає статистику та діагностує тупикові стани.
3. **`Resolver`:** ядро алгоритму, що веде стан графу, стек рішень та перевіряє сумісність обмежень.

```
+-----------------------------------------------------------------------------------+
|                      АЛГОРИТМ ПОШУКУ З ПОВЕРНЕННЯМ (RESOLVELIB)                   |
+-----------------------------------------------------------------------------------+
| [Вхідні вимоги: requests >= 2.0, urllib3 < 2.0]                                   |
|   │                                                                               |
|   ├── Крок 1: Вибір кандидата requests == 2.31.0                                  |
|   │     └── Вимоги кандидата: [urllib3 >= 1.21.1, < 3, charset_normalizer, ...]   |
|   │                                                                               |
|   ├── Крок 2: Перетин обмежень для urllib3:                                       |
|   │     └── Обмеження 1: < 2.0 (від користувача)                                  |
|   │     └── Обмеження 2: >= 1.21.1, < 3 (від requests)                           |
|   │     └── Підсумковий діапазон: >= 1.21.1, < 2.0                               |
|   │                                                                               |
|   ├── Крок 3: Вибір кандидата urllib3 == 1.26.18 (найновіший у діапазоні)          |
|   │     └── Усі обмеження задоволено!                                             |
|   │                                                                               |
|   └── Якщо виникає конфлікт:                                                      |
|         └── Відкат (Backtrack) до попереднього вузла -> вибір іншого кандидата   |
+-----------------------------------------------------------------------------------+
```

Розмір комбінаторного простору станів `S`, який досліджує резолвер для списку прямих та непрямих залежностей `P = {p₁, p₂, ..., pₙ}`, визначається добутком кількостей сумісних релізів для кожного пакета:

```
S = |C(p₁)| · |C(p₂)| · ... · |C(pₙ)|
  = ∏ |C(pᵢ)|      [комбінаторний простір: добуток множин версій усіх пакетів]
```

де `C(pᵢ)` — множина кандидатів-релізів для пакета `pᵢ`, що відповідають базовим критеріям платформи.

### Евристики сортування кандидатів та розв'язання циклів

Щоб не перебирати весь експоненційний простір станів наосліп, `resolvelib` застосовує спеціальні евристики пріоритету:
1. **Пріоритет стабільних релізів:** Релізи без суфіксів альфа/бета (`alpha`, `beta`, `rc`, `dev`) розглядаються першими, якщо користувач явно не вказав вимогу пре-релізів (`--pre`).
2. **Перевага бінарних коліс:** Кандидати з готовими `.whl` мають вищий пріоритет над `sdist`, оскільки не потребують виділення ресурсів на компіляцію.
3. **Евристика найвужчих обмежень (Most Constrained Variable First):** Резолвер першими обробляє ті пакети, для яких множина допустимих кандидатів є найменшою. Це дозволяє виявити нездійсненні гілки на ранніх кроках дерева пошуку, мінімізуючи глибину відкатів.
4. **Обробка циклічних залежностей:** Якщо пакет `A` вимагає `B`, а пакет `B` вимагає `A` (поширена практика для розділення плагінів), резолвер відстежує вже додані у поточну гілку вузли графу. Якщо обмеження обох пакетів узгоджені, цикл вважається допустимим і не призводить до нескінченного зациклення.

Якщо на певному кроці комбінація версій призводить до порожнього перетину множин допустимих версій (`C(p_k) = ∅`), алгоритм виконує відкат (Backtrack): повертається на попередній рівень стека рішень, відкидає останнього обраного кандидата, фіксує конфлікт і вибирає наступну доступну версію з вищим пріоритетом.

> 🔧 **Навіщо це.**
> Повноцінний backtracking-резолвер гарантує, що після завершення роботи `pip install` у середовищі не опиниться двох взаємовиключних версій однієї бібліотеки. Якщо узгодженого набору версій не існує фізично, `pip` перериває процес до зміни будь-яких файлів на диску і виводить чітке дерево конфлікту (Resolution Impossible).

## 3. Джерела пакетів, конфігурація та загроза Dependency Confusion

Менеджер `pip` підтримує гнучку систему підключення джерел дистрибутивів: загальнодоступного індексу PyPI, корпоративних приватних сховищ (Nexus, JFrog Artifactory, GitLab Package Registry, devpi, AWS CodeArtifact), локальних каталогів файлової системи та окремих архівів.

Конфігураційні параметри зчитуються за суворою ієрархією:
1. Системний рівень (`/etc/pip.conf` у Linux, `C:\ProgramData\pip\pip.ini` у Windows).
2. Користувацький рівень (`~/.config/pip/pip.conf` або `%APPDATA%\pip\pip.ini`).
3. Рівень віртуального середовища (`$VIRTUAL_ENV/pip.conf`).
4. Змінні оточення процесу з префіксом `PIP_` (наприклад, `PIP_INDEX_URL`).
5. Аргументи командного рядка CLI (найвищий пріоритет).

### Автентифікація в приватних репозиторіях

Для доступу до закритих корпоративних сховищ `pip` підтримує кілька методів передачі облікових даних:
- **Вбудовані облікові дані в URL:** `https://user:token@nexus.corp.internal/repository/pypi/simple`. Цей метод не рекомендується для файлів конфігурації, що потрапляють під контроль версій.
- **Файл облікових даних `.netrc`:** розміщений у домашньому каталозі користувача `~/.netrc` (або `_netrc` у Windows), де вказуються реквізити доступу для кожного окремого хоста:
  ```netrc
  machine nexus.corp.internal
  login deploy-agent
  password secret-token
  ```
- **Плагіни постачальників автентифікації (Keyring / Keyring CLI):** починаючи з `pip 22.0`, клієнт підтримує інтеграцію з системним сховищем ключів операційної системи (Keychain у macOS, Secret Service у Linux, Credential Manager у Windows) через бібліотеку `keyring`.

### Прапорці `--index-url` проти `--extra-index-url`

Для роботи з приватними репозиторіями `pip` надає дві різні опції:
- `--index-url <URL>`: встановлює **єдине базове джерело** пакетів, повністю замінюючи стандартний `https://pypi.org/simple`. Усі запити спрямовуються виключно за цією адресою.
- `--extra-index-url <URL>`: додає **додаткове джерело** пакетів до базового індексу.

```ini
# Приклад небезпечної конфігурації у ~/.config/pip/pip.conf
[global]
index-url = https://pypi.org/simple
extra-index-url = https://artifactory.corp.internal/artifactory/api/pypi/pypi-local/simple
```

*Механізм атаки Dependency Confusion через спільний пошук у приватному та публічному індексах за допомогою прапорця --extra-index-url.*

### Механізм атаки Dependency Confusion (Заміна залежностей)

Використання директиви `--extra-index-url` створює критичну вразливість у ланцюгу постачання (Supply Chain Vulnerability). Причина криється у внутрішній логіці `pip`: менеджер надсилає паралельні HTTP-запити до **всіх** зареєстрованих індексів одночасно. На відміну від менеджерів пакунків інших екосистем (як-от npm з просторами імен `@scope/pkg`), `pip` не має концепції пріоритету джерел чи прив'язки префіксів пакетів до конкретних серверів.

Якщо компанія використовує внутрішній приватний пакет з назвою `corp-auth` версії `1.2.0`, розміщений на внутрішньому сервері Artifactory:
1. Зловмисник реєструє в публічному PyPI пакет із такою самою назвою `corp-auth`.
2. Зловмисник публікує реліз із навмисно завищеною семантичною версією, наприклад `99.0.0`, що містить шкідливий код у файлі `setup.py` або `__init__.py`.
3. Під час чергового запуску збірки або розгортання `pip install corp-auth --extra-index-url <private-repo>` опитує обидва репозиторії.
4. Порівнюючи кандидатів `1.2.0` (з Artifactory) та `99.0.0` (з PyPI), `pip` обирає найвищу версію `99.0.0` з публічного джерела.
5. Шкідливий артефакт завантажується та виконується на цільовому сервері розробки або у виробничому кластері.

Ця вразливість, досліджена спеціалістом з безпеки Алексом Бірсаном (Alex Birsan) у 2021 році, дозволила скомпрометувати внутрішні контури десятків світових технологічних корпорацій (включно з Apple, Microsoft, PayPal, Shopify) через автоматичне виконання коду під час інсталяції.

### Стратегії захисту

1. **Єдиний віртуальний проксі-індекс:** Замість `--extra-index-url` налаштовується єдиний параметр `--index-url`, що вказує на внутрішній репозиторій-агрегатор (Nexus / Artifactory). Сервер конфігурується так, щоб внутрішні простори імен (`corp-*`) ніколи не перенаправлялися до зовнішнього PyPI.
2. **Превентивне резервування імен:** Реєстрація порожніх пакетів-заглушок у публічному PyPI для всіх внутрішніх проектів компанії.
3. **Локальні джерела з прапорцем `--no-index`:** Повне відключення мережевих індексів та робота через попередньо завантажені колеса:
   ```bash
   pip install --no-index --find-links=/opt/wheels corp-auth
   ```
4. **Хеш-піннінг (`--require-hashes`):** Фіксація криптографічних контрольних сум унеможливлює підміну файлу незалежно від версії.

Повний довідник параметрів конфігурації та безпекових налаштувань наведено у вставці [Конфігурація джерел pip та безпека ланцюга постачання](root:sys-plang-python/pip-install/api-pip-config.md).

## 4. Завантаження, кешування та криптографічна верифікація хешів

Коли список дистрибутивів узгоджено, `pip` переходить до фази отримання бінарних файлів або вихідних кодів.

### Дворівнева підсистема кешування

Кеш `pip` розташовано в каталозі `~/.cache/pip` (у Linux) або `%LOCALAPPDATA%\pip\Cache` (у Windows). Він складається з двох ізольованих сховищ:
1. **HTTP-кеш відповідей (`http-v2/`):** реалізує повноцінну специфікацію RFC 7234 на базі адаптованого модуля `cachecontrol`. Кожна збережена відповідь розбивається на метадані (заголовки, статус, мітка часу) та сирий потік тіла. Ключем файлу є SHA-256 хеш від канонічного URL запиту. Якщо відповідь містить заголовок `Cache-Control: max-age=3600`, `pip` повертає кешовані дані без звернення до мережі протягом однієї години. Якщо термін дії вичерпано, клієнт надсилає умовний запит із заголовком `If-None-Match: <ETag>`, отримуючи легку відповідь `304 Not Modified` замість повного повторного завантаження сторінки.
2. **Кеш бінарних коліс (`wheels/`):** якщо пакет завантажується як вихідний дистрибутив (`sdist`), після його локального збирання отриманий `.whl` файл зберігається в цьому каталозі. Ключ інвалідації формується на основі хешу вихідного дерева коду, версії CPython та прапорців компілятора. Під час наступної інсталяції `pip` використовує готове скомпільоване колесо без повторної компіляції C/Rust-коду.

```
+-----------------------------------------------------------------------------------+
|                        ПЕРЕВІРКА ХЕШІВ У РЕЖИМІ --require-hashes                  |
+-----------------------------------------------------------------------------------+
| requirements.txt:                                                                 |
|   cryptography==41.0.3 \                                                          |
|     --hash=sha256:7b68832a87a2d9c... (Linux x86_64 wheel)                        |
|     --hash=sha256:4a3891c938f21e0... (macOS arm64 wheel)                          |
|                                                                                   |
| Потокове зчитування файлу:                                                        |
|   [Вхідний потік] ──> Блок 64 КБ ──> SHA256_Update(&ctx, chunk, len)             |
|                        ├── Запис у тимчасовий файл .whl                           |
|                        └── Наступний блок...                                      |
|                                                                                   |
| Обчислення дайджесту:                                                             |
|   SHA256_Final(digest, &ctx)                                                      |
|   hex_digest = "7b68832a87a2d9c..."                                               |
|                                                                                   |
| Порівняння:                                                                       |
|   hex_digest ∈ {allowed_hashes}  ──[ ТАК ]──> Запуск інсталяції                   |
|                                  ──[ НІ  ]──> HashMismatchError (Abort)           |
+-----------------------------------------------------------------------------------+
```

### Режим суворої перевірки хешів (Hash-checking Mode)

Прапорець `--require-hashes` активує режим захисту від атак типу Man-in-the-Middle (MITM), підміни DNS та компрометації дзеркал репозиторіїв. У цьому режимі `pip` накладає суворі інваріанти:
- Кожен пакет у `requirements.txt` зобов'язаний мати щонайменше одну директиву `--hash=sha256:<hex>`. Оскільки один пакет для різних операційних систем має різні бінарні файли коліс, у файлі вимог фіксується набір усіх допустимих хешів для всіх цільових архітектур.
- Автоматичне неявне розв'язання залежностей блокується. Усі прямі й транзитивні залежності мусять бути виписані й захешовані явно (Locked Graph).
- Інсталяція з довільних URL або вихідних VCS-репозиторіїв (`git+https://...`) забороняється, оскільки вони не гарантують незмінності бінарного вмісту.

Обчислення хешу `H(A)` артефакту `A`, що складається з послідовності блоків `Chunk₁, Chunk₂, ..., Chunkₙ` розміром 64 КБ:

```
H(A) = SHA256(Chunk₁ || Chunk₂ || ... || Chunkₙ)
H(A) = H_expected    [перевірка цілісності: збіг із зафіксованим дайджестом]
```

Якщо обчислений дайджест не збігається з жодним із дозволених хешів, `pip` негайно видаляє завантажений тимчасовий файл, генерує виняток `HashMismatchError` і припиняє виконання без модифікації файлової системи цільового середовища.

Повний працюючий приклад клієнта Simple API з потоковою верифікацією SHA-256 мовами Python, C та C++ наведено у вставці [Реалізація клієнта PEP 503 та верифікація SHA-256 хешів](root:sys-plang-python/pip-install/proj-repo-client.md).

## 5. Процес інсталяції: розпакування Wheel проти збирання Sdist

Отриманий артефакт потрапляє в один із двох принципово різних конвеєрів інсталяції залежно від його формату.

![Порівняння шляхів інсталяції: Wheel проти Sdist](/root/sys/sys-plang-python/pip-install/img/wheel-unpack-vs-sdist-build.svg)
*Порівняння шляхів інсталяції: пряме розпакування бінарного колеса (Wheel) та багатоетапне складання вихідного дистрибутива (Sdist) в ізольованому середовищі.*

### Шлях 1: Готове бінарне колесо (`.whl`)

Файл `.whl` (PEP 427) — це стандартний ZIP-архів. Його встановлення не потребує запуску інтерпретатора чи компілятора:
1. `pip` відкриває ZIP-архів через модуль `zipfile`.
2. Файли модулів та пакетів переміщуються безпосередньо у каталог `site-packages`.
3. Каталог `*.dist-info` копіюється у `site-packages`.
4. Спеціальний каталог `*.data/` розпаковується за призначенням згідно з `sysconfig.get_paths()`:
   - `*.data/purelib/` та `*.data/platlib/` — переміщуються у `site-packages`.
   - `*.data/scripts/` — виконувані файли переносяться у системний `bin/` (або `Scripts` у Windows).
   - `*.data/headers/` — заголовкові файли C переносяться у каталог `include/`.
   - `*.data/data/` — додаткові спільні файли даних переносяться у корінь префікса `sys.prefix`.
5. Генеруються скомпільовані файли байткоду `.pyc` у підкаталогах `__pycache__` за допомогою модуля `compileall` для прискорення першого імпорту.

Цей процес є суто операцією введення-виведення на файловій системі і триває лічені мілісекунди.

### Шлях 2: Вихідний дистрибутив (`.tar.gz` sdist) та ізоляція збирання (PEP 517 / 518)

Якщо доступний лише вихідний код, `pip` виконує збирання колеса в тимчасовому ізольованому просторі (Build Isolation):
1. **Зчитування `pyproject.toml` (PEP 518):** `pip` розпаковує архів у тимчасовий каталог і парсить секцію `[build-system]`:
   ```toml
   [build-system]
   requires = ["hatchling>=1.18.0", "hatch-vcs"]
   build-backend = "hatchling.build"
   ```
2. **Створення ізольованого оточення:** `pip` створює тимчасове віртуальне середовище (у каталозі `/tmp/pip-build-env-...`) і завантажує туди інструменти, зазначені у списку `requires`. Це гарантує, що конфлікти між системними пакетами та інструментами збирання не зламають процес компіляції.
3. **Виклик хуків збирання (PEP 517):** через стандартний протокол міжпроцесної взаємодії `pip` викликає Python-хуки бекенду:
   - `get_requires_for_build_wheel` — повертає динамічні системні залежності.
   - `prepare_metadata_for_build_wheel` — генерує каталог метаданих `.dist-info` без повної компіляції двійкових файлів.
   - `build_wheel(wheel_directory, config_settings)` — бекенд компілює розширення C/C++/Rust, збирає модулі та генерує валідний `.whl` файл.
4. **Інсталяція згенерованого колеса:** отриманий файл колеса встановлюється за стандартним Шляхом 1, а тимчасове середовище збирання повністю знищується.

У сценаріях збирання пакетів для системних дистрибутивів Linux (Debian, Fedora, Alpine) доступ до мережі під час збірки суворо заборонено. У таких випадках застосовується прапорець `--no-build-isolation`: `pip` не створює тимчасового середовища, а виконує хуки бекенду безпосередньо у поточному оточенні, де всі інструменти збирання вже встановлені системним менеджером пакунків.

### Режим редагованого встановлення (Editable Installs, PEP 660)

Під час локальної розробки бібліотек застосовується команда `pip install -e .` (або `pip install --editable .`). Раніше для цього використовувалися нестандартизовані механізми `setuptools develop` та файли `.egg-link`.

Стандарт [PEP 660](https://peps.python.org/pep-0660/) перевів цей режим на офіційний бекенд-інтерфейс через хук `build_editable`. Замість копіювання вихідних файлів у `site-packages`, бекенд збирання створює спеціальне колесо-заглушку. Воно монтує файл пошуку шляхів `.pth` (або легковий завантажувач модуля на базі `importlib`), який динамічно додає робочий каталог розробника до `sys.path`. Будь-які зміни у коді відбиваються негайно без повторного запуску `pip install`.

## 6. Структура метаданих dist-info та облік встановлених файлів

Після розміщення модулів у `site-packages` `pip` формує обов'язковий службовий каталог метаданих `{distribution}-{version}.dist-info/` (PEP 376). Цей каталог містить критичні файли, що забезпечують працездатність інструментів діагностики (`pip list`, `importlib.metadata`) та чистого видалення (`pip uninstall`).

```
site-packages/
├── requests/
│   ├── __init__.py
│   ├── api.py
│   └── sessions.py
└── requests-2.31.0.dist-info/
    ├── METADATA
    ├── RECORD
    ├── INSTALLER
    ├── WHEEL
    ├── entry_points.txt
    └── direct_url.json
```

```
+-----------------------------------------------------------------------------------+
|                         ФАЙЛ METADATA (CORE METADATA 2.3)                         |
+-----------------------------------------------------------------------------------+
| Metadata-Version: 2.3                                                             |
| Name: requests                                                                    |
| Version: 2.31.0                                                                   |
| Summary: Python HTTP for Humans.                                                  |
| Requires-Python: >=3.7                                                            |
| Requires-Dist: charset-normalizer <4,>=2                                          |
| Requires-Dist: idna <4,>=2.5                                                      |
| Requires-Dist: urllib3 <3,>=1.21.1                                                |
| Requires-Dist: certifi >=2017.4.17                                                |
| Requires-Dist: PySocks !=1.5.7,>=1.5.6 ; extra == 'socks'                         |
+-----------------------------------------------------------------------------------+
```

### Файл RECORD та механіка `pip uninstall`

Файл `RECORD` — це CSV-таблиця, що містить повний перелік усіх файлів, записаних під час інсталяції. Кожен рядок має три колонки:
1. Відносний шлях до файлу відносно каталогу `site-packages`.
2. Хеш вмісту у форматі `sha256=<base64url>` (для текстових або двійкових файлів). Хеш обчислюється шляхом кодування двійкового SHA-256 дайджесту у безпечний для URL алфавіт Base64 з відсіканням кінцевих символів вирівнювання `=`.
3. Розмір файлу в байтах.

```csv
requests/__init__.py,sha256=a89f9b...34,4520
requests/api.py,sha256=1bc23e...89,6102
requests-2.31.0.dist-info/METADATA,sha256=7f881a...11,4096
requests-2.31.0.dist-info/RECORD,,
```

Сам файл `RECORD` вноситься останнім рядком без зазначення хешу та розміру. Під час інсталяції `pip` перевіряє `RECORD` інших встановлених пакетів: якщо новий пакет намагається записати файл, який уже належить іншому дистрибутиву, `pip` генерує попередження або помилку колізії (File Overwrite Conflict).

Коли користувач викликає команду `pip uninstall requests`:
1. `pip` знаходить каталог `requests-2.31.0.dist-info`.
2. Зчитує список файлів із `RECORD`.
3. Перевіряє наявність кожного файлу на диску та видаляє його.
4. Видаляє скомпільовані `.pyc` файли з каталогів `__pycache__`, навіть якщо вони не були зафіксовані в `RECORD`.
5. Видаляє сам каталог `.dist-info`. Завдяки цьому видалення відбувається повністю без залишення слідів.

### Інші файли метаданих

- **`INSTALLER`:** містить єдиний текстовий рядок, що ідентифікує утиліту встановлення (для `pip` вміст файлу — рядок `pip\n`, для `conda` — `conda\n`, для `uv` — `uv\n`).
- **`WHEEL`:** містить параметри сумісності згенерованого колеса (`Wheel-Version: 1.0`, `Tag: py3-none-any`).
- **`entry_points.txt`:** описує виконувані точки входу (Console Scripts). На основі цього файлу `pip` створює виконувані скрипти-обгортки у каталозі `bin/` (у Linux/macOS) або `.exe`-лаунчери (у Windows):
  ```ini
  [console_scripts]
  black = black:patched_main
  ```
  В операційній системі Windows створення простих текстових скриптів не дозволяє запускати команду напряму без зазначення інтерпретатора. Тому `pip` використовує модуль `distlib` для генерації двійкових файлів-обгорток (`black.exe`), які містять скомпільований C-код завантажувача, що автоматично знаходить `python.exe` поточного оточення та передає йому керування на вказану функцію точки входу.
- **`direct_url.json` (PEP 610):** записується лише у випадку, якщо пакет було встановлено не з індексу, а за прямим посиланням (наприклад, `pip install git+https://github.com/psf/black.git@main` або `pip install ./my-package`). Він фіксує точний VCS-хеш коміту або локальний шлях для аудиту походження коду.

### Захист системного Python (PEP 668)

У сучасних дистрибутивах Linux (Debian 12+, Ubuntu 23.04+, Fedora 38+) спроба виконати `pip install` у системному каталозі `/usr/lib/python3.X` блокується повідомленням про помилку `externally-managed-environment`. Це реалізовано за стандартом [PEP 668](https://peps.python.org/pep-0668/) через наявність маркерного файлу `/usr/lib/python3.X/EXTERNALLY-MANAGED`. Маркер захищає системні інструменти операційної системи (`apt`, `dnf`, `systemd-python`) від неконтрольованого перезапису бібліотек користувацькими версіями, скеровуючи розробника до обов'язкового використання віртуальних середовищ `venv`.

## 7. Етимологія та понятійний апарат

- **Репозиторій** — походить від латинського *repositorium* («сховище», «комора», «шафа»), утвореного від дієслова *reponere* (*re-* — «назад», «знову» + *ponere* — «класти», «розміщувати»). Означає централізоване сховище структурованих цифрових даних та артефактів.
- **Резолвер (розв'язувач)** — походить від латинського *resolvere* (*re-* — префікс зворотної дії + *solvere* — «розв'язувати», «розплутувати», «звільняти»). Означає обчислювальний алгоритм, який розплутує складні комбінаторні зв'язки та знаходить несуперечливий стан множини залежностей.
- **Хеш (дайджест)** — слово *hash* походить від старофранцузького *hache* («сокира») та дієслова *hacher* («рубати», «дрібно кришити»). Термін *дайджест* походить від латинського *digestus*, дієприкметника від *digerere* (*dis-* — «в різні боки» + *gerere* — «нести», «розподіляти», «впорядковувати»). В інформатиці означає незворотне стиснення довільного масиву даних у фіксований числовий вектор.
- **Колесо (Wheel)** — походить від давньоанглійського *hweol*, що сходить до прагерманського *\*hwehwlaz* та праіндоєвропейського *\*kʷekʷlo-* («обертатися», «коло»). У метафоричному контексті Python packaging є відсилкою до фразеологізму *«re-inventing the wheel»* (не винаходити колесо наново), вказуючи на готовий скомпільований артефакт, який не потребує повторного збирання.
- **Дистрибутив** — походить від латинського *distributio* («розподіл», «розподілення»), утвореного від дієслова *distribuere* (*dis-* — «окремо» + *tribuere* — «ділити», «надавати»). Означає скомплектований та готовий до постачання користувачам пакет програмного забезпечення.
- **Метадані** — гібридний термін, утворений від грецького *meta* (*μετά* — «поза», «про», «після») та латинського *data* («дані», множина від *datum* — «дане», від *dare* — «давати»). Означає інформацію, що описує властивості, зв'язки та структуру інших даних.
- **Артефакт** — походить від латинського виразу *arte factum* (*ars* / *artis* — «ремесло», «майстерність», «мистецтво» + *facere* — «робити»). Означає штучно створений об'єкт, зокрема двійковий файл, сформований процесом компіляції чи збирання.
- **Кеш** — походить від французького дієслова *cacher* («ховати», «приховувати»), що сходить до вульгарно-латинського *\*coactare* («стискати», «збирати разом»). Означає високошвидкісну проміжну область пам'яті для тимчасового зберігання даних із метою уникнення повторних повільних операцій.
- **Ізоляція** — походить від італійського *isolato* («відокремлений», «самотній»), утвореного від іменника *isola* («острів»), що сходить до латинського *insula* («острів»). Означає повне відокремлення обчислювального середовища або процесу від зовнішніх побічних впливів.
- **Бекенд** — походить від англійських слів *back* («задня частина», «тил», що сходить до прагерманського *\*baką*) та *end* («кінець», «край», що сходить до праіндоєвропейського *\*antí* — «навпроти»). В архітектурі збирання означає внутрішній рушій компіляції та пакування, відокремлений від користувацького фронтенд-інтерфейсу.
