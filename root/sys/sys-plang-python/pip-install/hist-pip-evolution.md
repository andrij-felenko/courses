# 📜 Еволюція менеджерів пакунків: від distutils до pip

Історія появи та розвитку інструментів інсталяції пакунків у екосистемі Python розкриває, чому сучасний менеджер `pip` отримав саме таку архітектуру і чому відмова від ранніх підходів на кшталт `easy_install` та формату `.egg` виявилася неминучою для стабільності програмних систем.

## Зародження дистрибуції: distutils та setuptools

Наприкінці 1990-х років розгортання бібліотек для Python зводилося до ручного копіювання `.py` файлів у каталог стандартної бібліотеки або запуску саморобних скриптів інсталяції. У 1998 році Грег Ворд (Greg Ward) представив модуль `distutils`, який увійшов до стандартної бібліотеки Python 1.6 та Python 2.0. Він увів єдиний інтерфейс збирання через файл `setup.py` та команду `python setup.py install`.

Однак `distutils` мав принципове обмеження: він не мав механізму автоматичного завантаження залежностей через мережу. Розробник мусив власноруч знайти, завантажити, розпакувати й скомпілювати кожен допоміжний пакет.

У 2004 році Філіп Ебі (Phillip J. Eby) у межах проекту PEAK (Python Enterprise Application Kit) створив надбудову `setuptools` та перший мережевий менеджер пакунків `easy_install`. Ця утиліта вперше інтегрувалася з офіційним індексом PyPI (Python Package Index, створеним у 2003 році за PEP 301 Річардом Джонсом), автоматично витягувала вихідні архіви або скомпільовані бінарні файли власного формату `.egg` (ZIP-архіви зі спеціальною структурою каталогу `EGG-INFO`) та монтувала їх у системний каталог `site-packages` шляхом маніпуляції файлом `.pth` (файлом шляхів пошуку модулів інтерпретатора).

```
+-------------------------------------------------------------------+
|               ХРОНОЛОГІЯ ЕВОЛЮЦІЇ МЕНЕДЖЕРІВ ПАКЕТІВ              |
+-------------------------------------------------------------------+
| 1998 | distutils (Greg Ward) — ручний запуск setup.py install      |
| 2003 | PyPI (PEP 301, Richard Jones) — централізований реєстр      |
| 2004 | setuptools / easy_install (Phillip J. Eby) — формат .egg    |
| 2008 | pyinstall -> pip (Ian Bicking) — безпечне видалення та flat |
| 2012 | PEP 427 Wheel (Daniel Holth) — стандартизація замість .egg  |
| 2015 | PEP 503 Simple Repository API — нормалізація індексів       |
| 2017 | PEP 517 / 518 (Thomas Kluyver et al.) — build isolation    |
| 2020 | pip 20.3 (Pradyun Gedam et al.) — resolvelib backtracking   |
+-------------------------------------------------------------------+
```

## Криза формату .egg та утиліти easy_install

Незважаючи на прорив у зручності, підхід `easy_install` спричинив серйозні технічні проблеми:

1. **Неможливість безпечного видалення:** `easy_install` не фіксував список установлених файлів. Команди `easy_install --uninstall` не існувало в принципі. Видалення пакета перетворювалося на ручний пошук файлів на диску, що неминуче залишало «сміття» та ламало пов'язані залежності.
2. **Динамічний імпорт та навантаження на запуск:** Пакети `.egg` могли залишатися запакованими ZIP-архівами, до яких інтерпретатор звертався через внутрішні імпортери `zipimport`. Метадані шукалися під час кожного імпорту через бібліотеку `pkg_resources`, яка динамічно сканувала всі доступні яйця в пошуку точок входу (`entry points`). На великих серверах час старту Python-процесу деградував на секунди лише через парсинг каталогів `.egg`.
3. **Непрозорість збирання:** Виконання довільного Python-коду всередині `setup.py` безпосередньо під час розпакування заважало кешуванню та створювало суттєві вразливості в ланцюгу постачання.

## Поява pyinstall та народження pip

У 2008 році відомий розробник інфраструктури Python Ієн Бікінг (Ian Bicking) опублікував утиліту `pyinstall`, яку незабаром перейменував на `pip` — рекурсивний акронім від *«Pip Installs Packages»* (або *«Pip Installs Python»*).

Головні архітектурні принципи Бікінга сформували основу сучасного менеджменту пакетів:
- **Плоска розпаковка (Flat unpack):** Пакет розпаковується безпосередньо у стандартні каталоги `site-packages`, без збереження ZIP-структури та без потреби у складних хуках імпорту `pkg_resources`.
- **Повноцінний облік інсталяції (`pip uninstall`):** Запис файлу метаданих `installed-files.txt` (який згодом перетворився на стандартизований `RECORD` у `.dist-info`), що дозволив видаляти пакети чисто й атомарно.
- **Підтримка файлів вимог (`requirements.txt`):** Можливість декларативного фіксування списку залежностей для відтворюваних середовищ.
- **Повна сумісність із віртуальними середовищами `virtualenv`:** Бікінг також був автором `virtualenv`, тому `pip` із перших версій розроблявся як штатний інструмент ізоляції оточення.

## Стандартизація формату Wheel (PEP 427)

Формат `.egg` лишався пропрієтарним винаходом проекту `setuptools`. У 2012 році Деніел Голт (Daniel Holth) запропонував [PEP 427](https://peps.python.org/pep-0427/), який ввів стандартний бінарний формат дистрибуції — `wheel` (`.whl`). 

На відміну від `egg`, `wheel` являє собою звичайний ZIP-архів із суворо стандартизованою схемою найменування файлу (`{distribution}-{version}(-{build tag})?-{python tag}-{abi tag}-{platform tag}.whl`) та спеціальним каталогом `{distribution}-{version}.dist-info/`. Встановлення `.whl` не вимагає запуску жодного рядка виконуваного коду: менеджер пакетів `pip` просто розпаковує файли на диск, що прискорило інсталяцію бібліотек у десятки разів і усунуло загрози виконання зловмисного коду на етапі розпакування.

## Епоха ізоляції збирання (PEP 517 / PEP 518)

До 2016 року для збирання будь-якого вихідного коду `pip` неявно припускав наявність `setuptools` у системі й викликав команду `setup.py egg_info` або `setup.py bdist_wheel`. Це призводило до «проблеми курки і яйця»: якщо для запуску `setup.py` був потрібен `cython` або `cffi`, встановити їх до виконання `setup.py` було неможливо.

У 2017 році Томас Клюйвер (Thomas Kluyver), Натаніель Сміт (Nathaniel J. Smith) та Дональд Стаффт (Donald Stufft) створили стандарти PEP 518 (декларація залежностей збирання у `pyproject.toml` у секції `[build-system]`) та PEP 517 (абстрактний API для інструментів збирання: `build_wheel`, `build_sdist`). Це дозволило позбутися монополії `setuptools` і породило нову генерацію швидких та безпечних інструментів складання: `flit`, `hatch`, `poetry` та `maturin` (для розширень мовою Rust).

## Новий резолвер pip 20.3 на базі resolvelib

Історично `pip` використовував примітивний «жадібний» (greedy) резолвер: він обробляв пакети послідовно у порядку їхньої появи в списку аргументів. Якщо перший пакет вимагав `library < 2.0`, а десятий — `library >= 2.0`, `pip` без попередження перезаписував уже встановлену версію, залишаючи середовище у зламаному та неконсистентному стані (Silent Downgrades).

У 2020 році в межах проекту модернізації (фінансованого фондами MOSS та Chan Zuckerberg Initiative) команда інженерів під керівництвом Прадьюна Гедама (Pradyun Gedam) повністю переписала ядро вирішення залежностей у релізі `pip 20.3`. Новий алгоритм на основі бібліотеки `resolvelib` реалізував повноцінний пошук із поверненням (Backtracking), що перетворило `pip` на надійний інструмент з математично доведеною гарантією несуперечливості зібраного графу залежностей.
