# 📜 Еволюція підсистеми імпорту: від ihooks до PEP 302 та PEP 451

У перших версіях Python підсистема імпорту була жорстко монолітною процедурою мовою C. Якщо розробнику було потрібно імпортувати код із нестандартного джерела — зашифрованого архіву, бази даних чи віддаленого сервера, — єдиним шляхом було або низькорівневе втручання в C-код інтерпретатора, або підміна вбудованої функції `__import__` за допомогою експериментального модуля `ihooks`. Розуміння того, як Python перейшов від монолітного `import.c` до сучасної модульної архітектури `importlib` на основі `ModuleSpec`, пояснює фундаментальні причини сучасного дизайну: поділ імпорту на фази пошуку, створення та виконання.

## 1. Монолітний C-код і спроби перехоплення (Python 1.x – 2.2)

На початку існування CPython вся логіка пошуку файлів на диску, їхнього відкриття, читання та компіляції містилася у файлі `Python/import.c`. Логіка була жорстко прив'язана до файлової системи: інтерпретатор послідовно перебирав каталоги зі списку `sys.path`, перевіряв наявність файлів із розширеннями `.py`, `.pyc` або бінарних бібліотек динамічного завантаження (`.so`/`.pyd`) і виконував знайдений байткод.

У такій схемі не існувало офіційного API для розширення. Єдиним механізмом модифікації поведінки був модуль `ihooks`, запропонований у Python 1.3. Він дозволяв замінити системну функцію `__import__` власним екземпляром класу `Hooks`. Проте цей підхід мав серйозні недоліки:

1. **Глобальний стан та конфлікти:** кілька сторонніх бібліотек, намагаючись встановити власні хуки через `ihooks`, затирали роботу одна одної, оскільки не існувало ланцюжка обробки (Chain of Responsibility).
2. **Дублювання C-логіки:** будь-який користувацький завантажувач мусив вручну відтворювати складні правила обробки відносних імпортів, ієрархій пакунків та кешування в `sys.modules`.
3. **Проблеми швидкодії:** інтерпретація чистого Python-коду під час кожного імпорту без системного кешування значно сповільнювала старт програм.

## 2. Стандартизація хуків імпорту: PEP 302 (Python 2.3)

У 2002 році було прийнято стандарт [PEP 302](https://peps.python.org/pep-0302/) («New Import Hooks»), авторами якого стали Юст ван Россум (Just van Rossum) та Пол Мур (Paul Moore). Метою стандарту було створити розширювану та передбачувану архітектуру, яка дозволила б завантажувати модулі з zip-архівів (`zipimport`), динамічно згенерованого коду або мережі без зламу базового інтерпретатора.

PEP 302 увів до ядра дві ключові концепції:

- **Знахідник (Finder):** об'єкт, який визначає місцезнаходження модуля і реалізує метод `find_module(fullname, path=None)`.
- **Завантажувач (Loader):** об'єкт, який трансформує модуль у пам'ять і реалізує метод `load_module(fullname)`.

Також було запроваджено два системні списки у модулі `sys`:
- `sys.meta_path` — список знахідників найвищого пріоритету, які викликаються до будь-якого сканування `sys.path`.
- `sys.path_hooks` — список фабрик, які створюють знахідники для конкретних записів у `sys.path` (наприклад, для шляхів усередині `.zip` архівів).

```
Запит import foo
  → Обхід sys.meta_path:
      finder = sys.meta_path[i]
      loader = finder.find_module("foo", path)
  → Якщо знайдено:
      module = loader.load_module("foo")
```

Реалізація PEP 302 стала великим кроком уперед, уможлививши стандартне постачання zip-пакунків та створення ізольованих середовищ. Проте згодом виявилися глибокі архітектурні вади дизайну `load_module()`.

## 3. Криза методу load_module() та проблеми кругових залежностей

Головна слабкість протоколу PEP 302 полягала в тому, що метод `load_module(fullname)` покладав на завантажувач забагато обов'язків одночасно:

1. Створення екземпляра `types.ModuleType`.
2. Заповнення службових атрибутів (`__name__`, `__file__`, `__path__`, `__loader__`, `__package__`).
3. Реєстрацію створеного модуля у глобальному словнику `sys.modules`.
4. Компіляцію та виконання коду всередині простору імен модуля.
5. Обробку помилок і очищення `sys.modules` у разі збою під час виконання коду.

Оскільки кожен сторонній завантажувач мав самостійно реалізовувати ці п'ять кроків, виникали масові помилки узгодженості:

- **Порушення циклічних імпортів:** розробники часто забували додати модуль у `sys.modules` *до* виклику `exec()`, через що циклічний імпорт усередині завантажуваного файлу призводив до нескінченної рекурсії.
- **Забруднення кешу:** якщо виконання модуля завершувалося винятком, некоректні завантажувачі залишали напівініціалізований модуль у `sys.modules`, ламаючи подальші спроби імпорту.
- **Повторне створення модуля:** при повторному виклику `load_module` для вже існуючого модуля деякі завантажувачі створювали новий об'єкт замість перевикористання вже зареєстрованого в `sys.modules`, що розривало посилання у клієнтському коді.

## 4. Просторові пакунки без \_\_init\_\_.py: PEP 420 (Python 3.3)

Зі зростанням великих монорепозиторіїв та модульних фреймворків виникла потреба розділяти один логічний пакунок між різними фізичними каталогами або дистрибутивами. Раніше для цього використовувалися складні маніпуляції з атрибутом `__path__` або пакунки `pkg_resources` / `pkgutil.extend_path()`.

Стандарт [PEP 420](https://peps.python.org/pep-0420/) («Implicit Namespace Packages») усунув вимогу обов'язкової наявності файлу `__init__.py` для пакунків. Якщо знахідник зустрічає каталог без `__init__.py`, він не відкидає його, а створює просторовий пакунок (*Namespace Package*), чий атрибут `__path__` динамічно об'єднує всі однойменні каталоги по всьому списку `sys.path`.

Це вимагало фундаментального перегляду того, як знахідники повертають інформацію про знайдені компоненти, оскільки `find_module()` міг повернути лише завантажувач, але просторові пакунки не мають файлу ініціалізації й, відповідно, не мають звичайного файлового завантажувача.

## 5. Розділення фаз і архітектура ModuleSpec: PEP 451 (Python 3.4+)

Щоб остаточно ліквідувати недоліки PEP 302 та гармонізувати механізм із просторовими пакунками PEP 420, Ерік Сноу (Eric Snow) розробив [PEP 451](https://peps.python.org/pep-0451/) («A ModuleSpec Type for the Import System»).

PEP 451 запровадив структуру метаданих `ModuleSpec` та чітко розмежував відповідальність:

```
[Пошук: Finder] ──find_spec()──> [ModuleSpec]
                                      │
 ┌────────────────────────────────────┴────────────────────────────────────┐
 │                                                                         │
 ▼                                                                         ▼
[Створення: Loader.create_module()]                       [Виконання: Loader.exec_module()]
   • ядро CPython алокує ModuleType                          • завантажувач лише виконує код
   • ядро виставляє службові поля (__name__, __spec__...)    • ядро контролює транзакційність
   • ядро атомарно реєструє в sys.modules                    • відкат при винятку робить ядро
```

Завдяки PEP 451:
1. **Знахідник (Finder)** більше не створює завантажувачі наосліп. Він повертає `ModuleSpec`, що описує модуль (назва, походження, шляхи пошуку підмодулів, завантажувач).
2. **Завантажувач (Loader)** позбувся монопольного методу `load_module()`. Його замінили два атомарні методи: `create_module(spec)` (який за замовчуванням делегується системному конструктору CPython) та `exec_module(module)` (який лише виконує скомпільований код у просторі імен модуля).
3. **CPython повністю контролює життєвий цикл:** керування словником `sys.modules`, підтримка циклічних посилань, валідація кешу та коректне очищення пам'яті при помилках стали обов'язком самого середовища виконання, а не розробників сторонніх завантажувачів.

Уся підсистема імпорту була переписана мовою Python у складі бібліотеки `importlib` (`_frozen_importlib` та `_frozen_importlib_external`), що скомпільована у заморожений байткод і вбудована безпосередньо у бінарний виконуваний файл інтерпретатора.
