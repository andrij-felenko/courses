Коли інтерпретатор CPython зустрічає в коді інструкцію `import foo` або виклик `__import__("foo")`, віртуальна машина виконує опкод `IMPORT_NAME`. За цим простим виразом стоїть розгалужена багатофазна інженерна система: середовище повинно перетворити абстрактний текстовий рядок назви модуля на живий об'єкт у пам'яті, запобігти повторному читанню з диска при багаторазових викликах, захистити стан від гонитви потоків, коректно розв'язати циклічні залежності між взаємопов'язаними файлами, побудувати ієрархію пакунків, знайти або скомпільувати бінарний байткод та зв'язати отриманий простір імен із поточним кадром виконання.

## 1. Архітектура конвеєра імпорту: від байткоду до словника кешу

Виконання інструкції `IMPORT_NAME` у віртуальній машині CPython транслюється у низькорівневий C-виклик функції `PyImport_ImportModuleLevelObject()`. Процес завантаження модуля розбито на чотири строго послідовні фази:

1. **Фаза кешування (`sys.modules`):** перевірка, чи не було цей модуль уже імпортовано раніше.
2. **Фаза пошуку (Finders / `sys.meta_path`):** виявлення фізичного чи віртуального джерела коду та побудова опису модуля (`ModuleSpec`).
3. **Фаза створення екземпляра (Module Allocation):** виділення об'єкта типу `types.ModuleType`, заповнення службових атрибутів та попередня реєстрація в кеші.
4. **Фаза виконання (Module Execution):** трансляція байткоду в просторі імен створеного модуля через завантажувач (`Loader`).

![Конвеєр імпорту CPython: від виклику до кешування](/root/sys/sys-plang-python/import-machinery/img/fig-import-pipeline.svg)
*Чотири фази виконання інструкції import: перевірка глобального кешу sys.modules, опитування знахідників sys.meta_path, виділення пам'яті під types.ModuleType та виконання коду завантажувачем*

Ключовим компонентом першої фази є глобальний словник `sys.modules`. Це системний кеш усіх модулів, які коли-небудь завантажувалися в межах поточного процесу інтерпретатора. Коли виконується запит на імпорт модуля `math`, CPython спершу виконує пошук за ключем `"math"` у `sys.modules`:

- Якщо ключ знайдено, і модуль повністю ініціалізовано, CPython негайно повертає посилання на існуючий об'єкт, уникаючи будь-яких звернень до файлової системи чи повторного виконання байткоду.
- Якщо ключа немає, інтерпретатор переходить до опитування зареєстрованих знахідників у списку `sys.meta_path`.
- Якщо модуль міститься в кеші, але перебуває в процесі ініціалізації (наприклад, при циклічному імпорті), CPython повертає посилання на частково заповнений модуль.

Для забезпечення потокобезпеки операції імпорту CPython використовує механізм блокувань імпорту. В історичних версіях використовувався глобальний лок (*Global Import Lock*), який зупиняв паралельні імпорти в інших потоках. У сучасному CPython блокування реалізовано на рівні окремих модулів: потік, що ініціює завантаження конкретного модуля, захоплює м'ютекс саме цього модуля, дозволяючи іншим потокам операційної системи паралельно імпортувати незалежні модулі.

Детальний аналіз історичного розвитку підсистеми імпорту від ранніх монолітних хуків до сучасної архітектури наведено у вставці [Еволюція підсистеми імпорту: від ihooks до PEP 302 та PEP 451](root:sys-plang-python/import-machinery/hist-pep302-pep451.md).

Під капотом ядро CPython ділить реалізацію імпорту між двома рівнями: ядром мовою C (`Python/import.c`) та базовою бібліотекою мовою Python (`Lib/importlib/_bootstrap.py` і `Lib/importlib/_bootstrap_external.py`). Щоб уникнути циклічної проблеми курки та яйця (коли для завантаження коду імпорту на Python потрібен сам імпорт), ці два файли компілюються під час складання CPython у статичні C-масиви байткоду `_frozen_importlib` та `_frozen_importlib_external`, які вшиваються безпосередньо у бінарний файл `python`.

## 2. Інструкції віртуальної машини: IMPORT_NAME та IMPORT_FROM

У циклі диспетчеризації інструкцій віртуальної машини CPython виконання конструкцій `import` та `from ... import` спирається на взаємодію двох опкодів:

- `IMPORT_NAME`: приймає ім'я модуля з таблиці констант `co_names` та вилучає зі стека об'єкти `level` (число крапок для відносного імпорту) і `fromlist` (кортеж імен, що імпортуються).
- `IMPORT_FROM`: видобуває конкретне ім'я зі словника модуля, що лежить на вершині стека, і кладе знайдений об'єкт на стек для наступного збереження інструкцією `STORE_FAST` або `STORE_NAME`.

Розглянемо різницю в роботі стекового кадру на прикладі двох виразів:

```python
# Варіант 1: прямий імпорт модуля
import math

# Байткод CPython:
# 0 LOAD_CONST     0 (0)         [level = 0: абсолютний імпорт]
# 2 LOAD_CONST     1 (None)      [fromlist = None]
# 4 IMPORT_NAME    0 (math)      [виклик конвеєра імпорту]
# 6 STORE_NAME     0 (math)      [збереження модуля у локальну змінну math]
```

```python
# Варіант 2: вибірковий імпорт атрибута
from math import sqrt

# Байткод CPython:
# 0 LOAD_CONST     0 (0)         [level = 0]
# 2 LOAD_CONST     1 (('sqrt',)) [fromlist = ('sqrt',)]
# 4 IMPORT_NAME    0 (math)      [завантажує модуль math на вершину стека]
# 6 IMPORT_FROM    1 (sqrt)      [видобуває функцію sqrt на стек]
# 8 STORE_NAME     1 (sqrt)      [зберігає sqrt у локальний простір]
# 10 POP_TOP                     [скидає об'єкт модуля math зі стека]
```

Цей механізм пояснює важливу технічну деталь: навіть при вибірковому імпорті `from math import sqrt` інтерпретатор завжди завантажує весь модуль `math` цілком і розміщує його у глобальному кеші `sys.modules`. Конструкція `from math import sqrt` не економить оперативну пам'ять інтерпретатора — вона лише визначає, яке саме ім'я буде зв'язане у поточному просторі імен.

## 3. Знахідники (Finders), протокол PEP 451 та об'єкт ModuleSpec

У ранніх версіях Python знахідники повертали безпосередньо об'єкт завантажувача. Стандарт PEP 451 уніфікував цей механізм, ввівши проміжний об'єкт специфікації — `importlib.machinery.ModuleSpec`.

Об'єкт `ModuleSpec` інкапсулює всі метадані, необхідні інтерпретатору для подальшого керування модулем:

```
ModuleSpec
  ├── name: "pkg.submodule"                    [Повна кваліфікована назва]
  ├── loader: <SourceFileLoader ...>           [Об'єкт завантажувача коду]
  ├── origin: "/usr/lib/python3.12/pkg/sub.py"  [Фізичне джерело файлу]
  ├── submodule_search_locations: None         [Список шляхів для пакунків]
  ├── loader_state: None                       [Додатковий контекст завантажувача]
  ├── cached: ".../__pycache__/sub.cpython.pyc" [Шлях до кешованого байткоду]
  └── has_location: True                       [Ознака наявності у файловій системі]
```

Пошук специфікації здійснюється послідовним опитуванням списку `sys.meta_path`. Кожен елемент цього списку є екземпляром класу, що реалізує протокол `importlib.abc.MetaPathFinder` з обов'язковим методом:

```python
finder.find_spec(fullname, path=None, target=None)
```

Параметр `fullname` містить повне ім'я модуля (наприклад, `email.mime.text`). Параметр `path` дорівнює `None` для модулів верхнього рівня або містить список шляхів `parent.__path__`, якщо імпортується підмодуль усередині пакунка.

![Диспетчеризація знахідників у sys.meta_path](/root/sys/sys-plang-python/import-machinery/img/fig-meta-path-traversal.svg)
*Послідовність опитування знахідників у sys.meta_path та делегування пошуку файлів через sys.path_hooks і FileFinder*

За замовчуванням список `sys.meta_path` містить три системні знахідники:

1. **`BuiltinImporter`:** знаходить C-модулі, скомпільовані статично всередину двійкового файлу `python` (наприклад, `sys`, `builtins`, `_ast`, `_thread`). Для таких модулів `origin` встановлюється в `"built-in"`, а `submodule_search_locations` дорівнює `None`.
2. **`FrozenImporter`:** виявляє модулі, чий байткод «заморожено» безпосередньо у виконуваному образі інтерпретатора (зокрема, сам модуль `_frozen_importlib`). Для них `origin = "frozen"`.
3. **`PathFinder`:** універсальний знахідник для файлової системи. Він сканує каталоги зі списку `sys.path` (або `path` батьківського пакунка).

`PathFinder` не виконує операції читання файлів самостійно. Він делегує роботу механізму `sys.path_hooks` (де, зокрема, реєструється шукач для [імпорту із ZIP-архівів](root:sys-plang-python/zipimport-module)). Для кожного рядка каталогу в `sys.path` інтерпретатор знаходить відповідний об'єкт `PathEntryFinder` (за замовчуванням — `importlib.machinery.FileFinder`), який кешується у системному словнику `sys.path_importer_cache`. Це позбавляє CPython необхідності повторно виконувати дорогі системні виклики сканування каталогів `opendir()` / `readdir()`.

Об'єкт `FileFinder` зберігає таблицю відповідностей суфіксів файлів до відповідних завантажувачів:
- `.py` пов'язується з `SourceFileLoader`.
- `.pyc` пов'язується з `SourcelessFileLoader`.
- `.so` (у Linux), `.dylib` (у macOS) або `.pyd` (у Windows) пов'язуються з `ExtensionFileLoader`.

Повний довідник протоколів `MetaPathFinder`, `PathEntryFinder` та сигнатур C-API винесено у вставку [Протоколи імпорту importlib та C-API](root:sys-plang-python/import-machinery/api-import-protocols.md).

## 4. Завантажувачі (Loaders): створення, реєстрація та виконання модуля

Отримавши об'єкт `ModuleSpec`, CPython переходить до фази завантаження. Стандарт PEP 451 розділив завантаження на два незалежні кроки: алокацію об'єкта модуля (`create_module`) та виконання коду (`exec_module`).

Завантажувач реалізує абстрактний інтерфейс `importlib.abc.Loader`:

```python
class Loader(abc.ABC):
    def create_module(self, spec: ModuleSpec) -> types.ModuleType | None:
        """Створює об'єкт модуля або повертає None для стандартної алокації."""
        return None

    @abc.abstractmethod
    def exec_module(self, module: types.ModuleType) -> None:
        """Виконує скомпільований код у просторі імен module.__dict__."""
        pass
```

Конвейєр завантаження виконується за строго визначеним інваріантом:

```
[1] module = spec.loader.create_module(spec)
    (якщо повернуто None → module = types.ModuleType(spec.name))
 │
[2] Заповнення службових атрибутів ядра:
    module.__name__ = spec.name
    module.__spec__ = spec
    module.__loader__ = spec.loader
    module.__file__ = spec.origin
    module.__cached__ = spec.cached
    module.__package__ = spec.parent
    якщо spec.submodule_search_locations не None:
        module.__path__ = spec.submodule_search_locations
 │
[3] АТОМАРНИЙ ЗАПИС У КЕШ:
    sys.modules[spec.name] = module  <── КРИТИЧНО: ДО виклику exec_module!
 │
[4] ВИКОНАННЯ КОДУ:
    try:
        spec.loader.exec_module(module)
    except BaseException:
        try:
            del sys.modules[spec.name]   <── ВІДКАТ при винятку
        except KeyError:
            pass
        raise
```

Запис модуля у `sys.modules` на кроці [3] *до* виконання першого рядка коду на кроці [4] є найважливішим архітектурним рішенням у CPython. Саме завдяки цьому розв'язуються циклічні імпорти:

Якщо модуль `A` імпортує модуль `B`, а модуль `B` всередині імпортує модуль `A`, процес відбувається без зациклення:
1. `A` створюється і записується в `sys.modules["A"]`.
2. Починається виконання `A`. Натрапивши на `import B`, інтерпретатор призупиняє виконання `A` і запускає завантаження `B`.
3. `B` створюється і записується в `sys.modules["B"]`.
4. Виконуючись, `B` викликає `import A`.
5. Інтерпретатор перевіряє `sys.modules`: ключ `"A"` вже існує. CPython негайно повертає об'єкт `A` (навіть якщо той ще не завершив своє виконання).
6. `B` завершує виконання свого коду.
7. Керування повертається до `A`, який також завершує виконання.

Цей механізм має зворотний бік: якщо модуль `B` під час завантаження намагається звернутися до атрибута `A.foo`, який ще не встиг створитися через незавершене виконання файлу `A.py`, виникає помилка `AttributeError: partially initialized module 'A' has no attribute 'foo' (most likely due to a circular import)`.

Якщо під час виклику `exec_module()` виникає будь-який виняток (синтаксична помилка, збій ініціалізації бази даних чи `ImportError`), CPython негайно видаляє модуль із `sys.modules`. Це гарантує, що зламаний модуль не залишиться у системному кеші та не спотворить наступні імпорти.

## 5. Модулі проти пакунків: регулярні каталоги та Namespace Packages (PEP 420)

У системі типів CPython немає окремого класу «пакунок». І звичайний файл, і пакунок представляються одним і тим самим типом `types.ModuleType`. Єдиною формальною системною відмінністю пакунка від листового модуля є наявність атрибута `__path__`.

![Порівняння структури модулів і пакунків у CPython](/root/sys/sys-plang-python/import-machinery/img/fig-module-vs-package.svg)
*Анатомія листового модуля, регулярного пакунка з файлом \_\_init\_\_.py та просторового пакунка PEP 420*

### Регулярні пакунки (*Regular Packages*)

Регулярний пакунок — це каталог на диску, який обов'язково містить файл `__init__.py` (або `__init__.pyc`).

Коли виконується `import pkg`, знахідник `PathFinder` виявляє файл `pkg/__init__.py`. Створюється `ModuleSpec`, у якому:
- `origin` встановлюється на повний шлях до `pkg/__init__.py`.
- `submodule_search_locations` ініціалізується списком із одного елемента: `[os.path.dirname(spec.origin)]`.
- При створенні модуля атрибут `pkg.__path__` отримує цей список.

Коли надалі запитується підмодуль `import pkg.sub`, CPython передає список `pkg.__path__` як аргумент `path` у метод `find_spec("pkg.sub", path=pkg.__path__)`. Завдяки цьому пошук підмодуля ведеться виключно всередині каталогу `pkg/`.

### Просторові пакунки (*Namespace Packages*, PEP 420)

До стандарту PEP 420 пакунок без `__init__.py` вважався некоректним і ігнорувався. PEP 420 запровадив поняття неявних просторових пакунків (*Implicit Namespace Packages*). Вони дозволяють розділити частини одного логічного простору імен між різними незалежними каталогами чи встановленими дистрибутивами.

Якщо на диску існують шляхи:
- `/opt/company/plugins/auth/`
- `/usr/local/lib/python3.12/site-packages/company/plugins/billing/`

І в каталогах `company/` та `plugins/` немає файлу `__init__.py`, інтерпретатор об'єднує їх:

1. `PathFinder` проходить по всьому списку `sys.path` і збирає всі каталоги з назвою `company/plugins`.
2. Створюється `ModuleSpec` зі спеціальним фіктивним завантажувачем `_NamespaceLoader`:
   - `spec.origin = None` (немає фізичного файлу ініціалізації).
   - `spec.submodule_search_locations` містить динамічний список `_NamespacePath`, який включає обидва каталоги.
3. Модуль створюється без виконання коду (оскільки `__init__.py` відсутній), але має атрибут `__path__`, що вказує на обидва фізичні каталоги.

Це дозволяє імпортувати як `company.plugins.auth`, так і `company.plugins.billing` у межах одного спільного кореневого простору.

## 6. Відносні імпорти та роздільна здатність пакетних імен

Синтаксис відносного імпорту (`from . import sibling` або `from ..parent import utils`) використовується всередині пакунків, щоб уникнути жорсткої прив'язки до кореневої назви бібліотеки.

Коли CPython виконує відносний імпорт, опкод `IMPORT_NAME` отримує цілочисельний параметр `level`:
- `level = 0`: абсолютний імпорт (пошук починається від кореня `sys.path`).
- `level = 1`: імпорт із поточного каталогу пакунка (`.` — один рівень).
- `level = 2`: імпорт із батьківського каталогу пакунка (`..` — два рівні).

Алгоритм обчислення повного імені спирається на атрибут `__spec__.parent` або глобальну змінну `__package__` викликаючого модуля:

```
Розрахунок повного імені для відносного імпорту:
1. Отримуємо base = __spec__.parent (або __package__)
2. Якщо base is None або base == "":
   → Викидаємо ImportError: attempted relative import with no known parent package
3. Розбиваємо base на сегменти: parts = base.split(".")
4. Якщо level > len(parts):
   → Викидаємо ValueError: attempted relative import beyond top-level package
5. Обчислюємо префікс: prefix = ".".join(parts[:len(parts) - level + 1])
6. Формуємо повну назву: fullname = f"{prefix}.{name}"
```

Саме тому відносні імпорти завжди зазнають невдачі, якщо файл запускається як головна точка входу процесу через команду `python script.py`. При такому запуску CPython призначає модулю ім'я `__main__`, а атрибути `__spec__.parent` та `__package__` залишаються порожніми (`None`), позбавляючи інтерпретатор інформації про ієрархію пакунка.

## 7. Завантаження бінарних C-розширень (Dynamic Loading)

Коли `PathFinder` виявляє файл із розширенням `.so` (в Linux/macOS) або `.pyd` (у Windows), створення модуля делегується завантажувачу `ExtensionFileLoader`.

Під капотом завантаження динамічних бібліотек спирається на функціонал операційної системи:
1. CPython викликає системний API динамічного зв'язування `dlopen()` (у POSIX) або `LoadLibraryExW()` (у Windows).
2. За замовчуванням бібліотека завантажується з прапорцями `RTLD_NOW | RTLD_LOCAL`, що ізолює внутрішні C-символи розширення від глобального простору імен процесу.
3. Інтерпретатор формує ім'я точки входу: для модуля з назвою `fast_calc` шукається експортована функція `PyInit_fast_calc`.
4. Завантажувач викликає `PyInit_fast_calc()`, яка виконує ініціалізацію розширення.

Сучасний CPython підтримує дві моделі ініціалізації C-розширень:

- **Однофазна ініціалізація (Legacy Single-Phase):** функція `PyInit_` викликає `PyModule_Create()` і повертає готовий об'єкт `PyObject*`. Недоліком є неможливість повної ізоляції глобального стану C при створенні кількох інтерпретаторів у межах одного процесу (*Sub-interpreters*).
- **Багатофазна ініціалізація (Multi-Phase Initialization, PEP 489):** функція `PyInit_` повертає опис модуля `PyModuleDef*`. Алокація та ініціалізація розділяються на етапи `Py_mod_create` та `Py_mod_exec`, що повністю відповідає філософії PEP 451 і гарантує коректну роботу в ізольованих субінтерпретаторах.

## 8. Механізм zipimport та розширення sys.path_hooks

Стандартна підсистема імпорту CPython здатна прозоро завантажувати модулі безпосередньо з архівів ZIP та пакетів Wheel без їхнього попереднього розпакування на диск. За цю функціональність відповідає вбудований C-модуль `zipimport`.

Під час ініціалізації інтерпретатора клас `zipimport.zipimporter` додається до системного списку фабрик `sys.path_hooks`. Коли `PathFinder` перевіряє запис у `sys.path`:

1. `PathFinder` послідовно викликає фабрики з `sys.path_hooks` для вказаного шляху.
2. Якщо шлях вказує на файл архіву (наприклад, `/app/libs/bundle.zip`), `zipimporter(path)` перевіряє сигнатуру центрального каталогу ZIP (*Central Directory*) у кінці файлу.
3. Якщо архів валідний, `zipimporter` зчитує зміст архіву в оперативну пам'ять та кешує екземпляр у `sys.path_importer_cache`. Якщо шлях не є zip-архівом, фабрика викидає виняток `ZipImportError`, і керування переходить до наступного хука (`FileFinder`).
4. При запиті модуля `zipimporter` знаходить відповідний запис у стиснутому дереві, декомпресує байти `.py` або скомпільованого `.pyc` безпосередньо в буфер пам'яті та передає його функції `marshal.loads()` або вбудованому компілятору.

## 9. Багатопоточність, блокування та Free-Threaded CPython (PEP 703)

У багатопотокових застосунках кілька потоків можуть одночасно виконувати інструкції імпорту однакових або взаємопов'язаних модулів. Щоб запобігти стану гонитви та виникненню взаємних блокувань (*Deadlocks*), CPython використовує багаторівневу схему синхронізації.

Кожен модуль під час завантаження асоціюється з окремим об'єктом блокування (*Module Lock*). Коли потік `T1` починає завантажувати модуль `A`:

1. `T1` захоплює м'ютекс модуля `A` через `_PyImport_AcquireLock("A")`.
2. Якщо інший потік `T2` одночасно запитує `import A`, `T2` блокується на цьому м'ютексі доти, доки `T1` не завершить виконання методу `exec_module()`.
3. Якщо `T1` під час завантаження `A` викликає `import A` (самоімпорт або рекурсивний виклик), CPython виявляє, що поточний потік уже володіє блокуванням модуля `A`, і дозволяє реентрантний прохід без блокування.

У випадку перехресних залежностей між потоками (потік 1 завантажує `A`, який імпортує `B`, а потік 2 завантажує `B`, який імпортує `A`), CPython реалізує алгоритм виявлення дедлоків: якщо потік виявляє зациклення очікування блокувань, він тимчасово звільняє власне блокування, дозволяючи іншому потоку завершити ініціалізацію.

У версіях Python 3.13+ з експериментальною підтримкою вимкнення глобального блокування інтерпретатора (Free-Threaded CPython за стандартом PEP 703) синхронізація словника `sys.modules` була суттєво перероблена: читання зі словника кешу є вільним від блокувань (*Lock-Free Read*) завдяки використанню захищених атомарних вказівників, а модифікації структури модуля захищаються дрібногранулярними версійними блокуваннями словників.

## 10. Перезавантаження модулів: importlib.reload()

Функція `importlib.reload(module)` дозволяє перечитати та повторно виконати код модуля під час роботи програми без перезапуску інтерпретатора. Це незамінно в інтерактивних середовищах розробки та системах гарячого оновлення коду (*Hot Reloading*).

Механіка перезавантаження має принципові відмінності від первинного імпорту:

1. `reload()` вимагає передачі вже існуючого екземпляра модуля `types.ModuleType`, що міститься у `sys.modules`.
2. Інтерпретатор знаходить специфікацію `module.__spec__` або генерує нову за допомогою `find_spec(module.__name__)`.
3. Замість створення нового об'єкта `types.ModuleType` завантажувач викликає метод `exec_module(module)` над *тим самим* існуючим об'єктом.
4. Усі функції, класи та глобальні змінні у словнику `module.__dict__` перезаписуються новими об'єктами.

Зворотним наслідком цього механізму є проблема старих посилань: якщо сторонній модуль раніше імпортував функцію через `from mod import helper`, його локальна змінна `helper` продовжить посилатися на стару функцію в пам'яті. Перезавантаження модуля `mod` оновить лише словник `mod.__dict__`, але не оновить локальні змінні інших модулів, які вже встигли зберегти прямі посилання на старі об'єкти.

Також бінарні C-розширення з однофазною ініціалізацією не підтримують коректне перезавантаження: системний виклик `dlopen()` повертає той самий завантажений образ бібліотеки, а повторний виклик `PyInit_` може призвести до пошкодження пам'яті C-алокаторів.

## 11. Кешування байткоду: бінарний формат і валідація файлів .pyc

Парсинг тексту мови Python, побудова лексичних токенів, генерація абстрактного синтаксичного дерева (AST) та трансляція в інструкції віртуальної машини вимагають значних обчислювальних витрат процесора. Щоб прискорити час старту, завантажувач `SourceFileLoader` компілює вихідний код у байткод і зберігає його в каталозі `__pycache__` у вигляді файлу з розширенням `.pyc` (наприклад, `module.cpython-312.pyc`).

Починаючи з Python 3.7, заголовок файлу `.pyc` стандартизовано у 16 байтів (4 слова по 32 біти):

![Бінарна структура файлу байткоду .pyc](/root/sys/sys-plang-python/import-machinery/img/fig-pyc-format.svg)
*Структура заголовка .pyc: магічне число версії, прапорці валідації PEP 552, часова мітка/хеш та маршалізований PyCodeObject*

### Розбір полів заголовка .pyc

1. **Магічне число (Байти 0..3):**
   - 2 байти: унікальний номер версії байткоду CPython (змінюється щоразу, коли змінюються опкоди або внутрішня структура `PyCodeObject`).
   - 2 байти: константа `\r\n` (`0x0D 0x0A`), що слугує індикатором пошкодження файлу при некоректній передачі через FTP у текстовому режимі.
2. **Бітове поле прапорців (Байти 4..7):**
   - Стандарт PEP 552 запровадив підтримку хеш-валідації.
   - Біт 0: `0` — валідація за часовою міткою (*Timestamp-based*), `1` — валідація за хешем (*Hash-based*).
   - Біт 1: `0` — хеш обов'язково перевіряється (*Checked hash*), `1` — хеш не перевіряється (*Unchecked hash*, використовується для прискорення завантаження контейнерів і системних пакетів).
3. **Метадані валідації (Байти 8..15):**
   - Для *Timestamp-based*: 4 байти часу модифікації (`mtime` вихідного `.py` у форматі Unix Timestamp) + 4 байти розміру файлу (`size` у байтах).
   - Для *Hash-based*: 8 байтів контрольної суми SIPHASH-24 від вмісту вихідного тексту `.py`.
4. **Тіло файлу (Байти 16..кінець):**
   - Серіалізований об'єкт `PyCodeObject`, записаний за допомогою вбудованого C-модуля `marshal` (`marshal.dump(code, f)`).

### Алгоритм валідації та інвалідації кешу

Коли `SourceFileLoader` перевіряє валідність `.pyc`, інтерпретатор зіставляє метадані заголовка з реальними параметрами файлу на диску:

```
Перевірка валідності .pyc:
1. magic_pyc == importlib.util.MAGIC_NUMBER
   [якщо ні → байткод застарів або скомпільований іншою версією Python]
2. Якщо flags == 0 (Timestamp-based):
   mtime_pyc == stat(source_file).st_mtime
   AND size_pyc == stat(source_file).st_size
   [якщо рівні → завантажуємо marshal.load(); якщо ні → перекомпіляція]
3. Якщо flags == 1 (Hash-based):
   siphash24(source_file) == hash_pyc
   [якщо хеші збігаються → кеш валідний; якщо ні → перекомпіляція]
```

Якщо перевірка не проходить або файл `.pyc` відсутній, CPython компілює вихідний текст у новий `PyCodeObject`, виконує його та атомарно (через тимчасовий файл і системний виклик `rename`) перезаписує `.pyc` у каталозі `__pycache__`.

Запис `.pyc` можна вимкнути за допомогою прапорця командного рядка `-B` або змінної оточення `PYTHONDONTWRITEBYTECODE=1`. Це корисно у середовищах із файловими системами, доступними лише для читання, або у Docker-контейнерах під час розгортання образів.

## 12. Створення власних знахідників та завантажувачів

CPython дозволяє повністю перевизначити або доповнити стандартний механізм пошуку файлів. Власні імпортери застосовуються для завантаження коду з оперативної пам'яті, zip-архівів, шифрованих сховищ, баз даних або віддалених HTTP-серверів.

Для створення повноцінного імпортера необхідно реалізувати два класи: знахідник (`MetaPathFinder`) та завантажувач (`Loader`).

```python
import sys
import types
from importlib.abc import Loader, MetaPathFinder
from importlib.machinery import ModuleSpec


class VirtualCodeLoader(Loader):
    """Завантажувач коду з віртуального сховища пам'яті."""

    def __init__(self, source_code: str):
        self.source_code = source_code

    def create_module(self, spec: ModuleSpec) -> types.ModuleType | None:
        # Повертаємо None: CPython самостійно створить об'єкт types.ModuleType
        return None

    def exec_module(self, module: types.ModuleType) -> None:
        # Компілюємо вихідний текст у просторі імен модуля
        origin = module.__spec__.origin or "<virtual>"
        code_obj = compile(self.source_code, origin, "exec")
        exec(code_obj, module.__dict__)


class VirtualPathFinder(MetaPathFinder):
    """Знахідник мета-шляху для віртуальних модулів."""

    def __init__(self, code_registry: dict[str, str]):
        self.code_registry = code_registry

    def find_spec(
        self,
        fullname: str,
        path: list[str] | None = None,
        target: types.ModuleType | None = None,
    ) -> ModuleSpec | None:
        if fullname in self.code_registry:
            source = self.code_registry[fullname]
            loader = VirtualCodeLoader(source)
            return ModuleSpec(
                name=fullname,
                loader=loader,
                origin=f"<virtual://{fullname}>",
                is_package=False,
            )
        return None


# Реєстрація власного знахідника на початку системного списку
storage = {
    "telemetry_client": "def send_ping(): return {'status': 'ok', 'code': 200}"
}

sys.meta_path.insert(0, VirtualPathFinder(storage))

# Звичайний імпорт віртуального модуля
import telemetry_client
response = telemetry_client.send_ping()
print("Результат віртуального виклику:", response)
```

## 13. Взаємодія з C-API та низькорівневі виклики

При розробці системних C/C++ розширень або вбудовуванні інтерпретатора CPython у сторонні застосунки розробники взаємодіють із підсистемою імпорту через набір функцій C-API.

Основними функціями є:
- `PyImport_ImportModule(name)`: високорівневий імпорт модуля за його ім'ям.
- `PyImport_ImportModuleLevelObject(name, globals, locals, fromlist, level)`: повний системний виклик, що виконує інструкцію `IMPORT_NAME`.
- `PyImport_GetModuleDict()`: повертає словник `sys.modules` у вигляді `PyObject*`.

Нижче наведено порівняння імпорту модуля та виклику функції мовами C та C++20:

```c
#define PY_SSIZE_T_CLEAN
#include <Python.h>
#include <stdio.h>

/**
 * Імпортує модуль math та викликає функцію sqrt засобами чистого C C-API.
 */
int calculate_square_root_c(double value, double *result) {
    // 1. Імпортуємо системний модуль (повертає New reference)
    PyObject *math_mod = PyImport_ImportModule("math");
    if (!math_mod) {
        PyErr_Print();
        return -1;
    }

    // 2. Отримуємо функцію sqrt зі словника модуля
    PyObject *sqrt_func = PyObject_GetAttrString(math_mod, "sqrt");
    Py_DECREF(math_mod); // Модуль більше не потрібен напряму

    if (!sqrt_func || !PyCallable_Check(sqrt_func)) {
        Py_XDECREF(sqrt_func);
        PyErr_Print();
        return -1;
    }

    // 3. Викликаємо функцію з числовим аргументом
    PyObject *args = PyTuple_Pack(1, PyFloat_FromDouble(value));
    PyObject *py_res = PyObject_CallObject(sqrt_func, args);
    Py_DECREF(sqrt_func);
    Py_DECREF(args);

    if (!py_res) {
        PyErr_Print();
        return -1;
    }

    *result = PyFloat_AsDouble(py_res);
    Py_DECREF(py_res);
    return 0;
}
```

```cpp
#define PY_SSIZE_T_CLEAN
#include <Python.h>
#include <iostream>
#include <memory>
#include <stdexcept>
#include <string_view>

// RAII-обгортка над PyObject* для безпечного автоматичного зменшення посилань
struct PyDeleter {
    void operator()(PyObject* ptr) const noexcept {
        if (ptr) {
            Py_DECREF(ptr);
        }
    }
};

using ScopedPyObject = std::unique_ptr<PyObject, PyDeleter>;

/**
 * Ідіоматичний C++20 клас для імпорту та взаємодії з модулями CPython.
 */
class PythonImporter {
public:
    static double calculate_sqrt(double value) {
        // 1. Імпорт модуля через RAII
        ScopedPyObject math_mod(PyImport_ImportModule("math"));
        if (!math_mod) {
            throw std::runtime_error("Не вдалося імпортувати модуль math");
        }

        // 2. Отримання атрибута функції
        ScopedPyObject sqrt_func(PyObject_GetAttrString(math_mod.get(), "sqrt"));
        if (!sqrt_func || !PyCallable_Check(sqrt_func.get())) {
            throw std::runtime_error("Функція sqrt відсутня або не є викликаємою");
        }

        // 3. Підготовка аргументів та виклик
        ScopedPyObject arg(PyFloat_FromDouble(value));
        ScopedPyObject args_tuple(PyTuple_Pack(1, arg.get()));
        ScopedPyObject py_result(PyObject_CallObject(sqrt_func.get(), args_tuple.get()));

        if (!py_result) {
            throw std::runtime_error("Помилка виконання функції math.sqrt");
        }

        return PyFloat_AsDouble(py_result.get());
    }
};
```

## 14. Терміни та етимологія

- **Знахідник (Finder)** — компонент підсистеми імпорту, що визначає наявність модуля та генерує його специфікацію (англ. *find* — знаходити, виявляти; від давньоанглійського *findan* — натрапляти, відкривати).
- **Завантажувач (Loader)** — компонент, що виконує виділення пам'яті та трансляцію коду модуля в його словник простору імен (англ. *load* — вантажити, наповнювати; від давньоанглійського *lād* — шлях, тягар).
- **Специфікація (Specification / ModuleSpec)** — структурований опис метаданих модуля, необхідних для його завантаження (лат. *species* — вид, вигляд, форма + *facere* — робити, створювати; буквально — надання конкретного вигляду).
- **Кеш (Cache / sys.modules)** — проміжний буфер швидкого доступу для зберігання вже ініціалізованих модулів і запобігання повторним операціям вводу-виводу (фр. *cacher* — ховати, приховувати; від латинського *coactare* — змушувати, стискати).
- **Простір імен (Namespace)** — абстрактний контекст або словник, що забезпечує унікальність ідентифікаторів змінних, функцій і класів (лат. *spatium* — проміжок, вільне місце + *nomen* — ім'я, назва).
- **Байткод (Bytecode)** — проміжне машинно-незалежне представлення програми у вигляді послідовності компактних числових інструкцій віртуальної машини (англ. *byte* — одиниця цифрових даних, скорочення від *by eight* + *code* — від лат. *codex* — книга законів, збірка правил).
- **Маршалізація (Marshal / Serialization)** — процес трансформації внутрішніх структур даних CPython у лінійний потік байтів для збереження на диск або передачі мережею (англ. *marshal* — вишиковувати, впорядковувати; від старофранцузького *mareschal* — розпорядник, наглядач).
