# 📜 Еволюція асинхронності в Python: від генераторів до TaskGroup

Асинхронна модель у мові Python формувалася понад два десятиліття. Її розвиток визначався фундаментальним протиріччям між блокувальною природою системних викликів введення-виведення та наявністю глобального блокування інтерпретатора (Global Interpreter Lock, GIL), яке обмежує виконання байткоду CPython одним системним потоком на ядро процесу.

## 1. Генератори як основа кооперативної багатозадачності (Python 2.2 – 2.5)

Початком асинхронної моделі стала поява простих генераторів у Python 2.2 через специфікацію PEP 255 (*Simple Generators*). Інструкція `yield` дозволила функції зберігати свій локальний стек виклику, змінні та положення лічильника інструкцій, перетворюючись на ітератор, який повертає значення вызывачеві без знищення власного контексту.

Однак генератори першого покоління були односпрямованими: вони лише віддавали дані назовні. Справжній прорив у бік співпрограм (корутин) відбувся у Python 2.5 із прийняттям PEP 342 (*Coroutines via Enhanced Generators*). Специфікація перетворила генератори на повноцінні двобічні канали зв'язку, додавши три методи:
- `generator.send(value)`: передача значення всередину призупиненого генератора, де воно стає результатом обчислення виразу `yield`;
- `generator.throw(type, value, traceback)`: генерація винятку всередині фрейму генератора в точці поточної зупинки;
- `generator.close()`: ініціалізація винятку `GeneratorExit` для детермінованого звільнення ресурсів.

Завдяки цим методам з'явилася можливість будувати примітивні планувальники задач (*trampoline loops*), які по черзі передавали керування генераторам через виклики `.send(None)`.

## 2. Епоха сторонніх фреймворків: Twisted та Tornado

Паралельно з розвитком ядра Python спільнота розробляла власні механізми неблокувального введення-виведення на базі мультиплексування дескрипторів (`select`, `poll`, `epoll`).

1. **Twisted (2002):** Архітектура Twisted будувалася на концепції зворотних викликів (*callbacks*) та об'єктів `Deferred`. Кожна асинхронна операція повертала відкладений результат, до якого розробник ланцюжком прив'язував обробники успіху (`addCallback`) та помилок (`addErrback`). Головним недоліком цього підходу було «пекло колбеків» (*Callback Hell*) — втрата лінійної структури коду та фрагментація стека викликів.
2. **Tornado (2009):** Створений Бретом Тейлором для FriendFeed, фреймворк Tornado запропонував декоратор `@gen.coroutine`. Він використовував розширені генератори PEP 342 для написання асинхронного коду, який візуально нагадував синхронний: `response = yield http_client.fetch(url)`. Планувальник `IOLoop` отримував від генератора об'єкт `Future`, підписувався на його завершення і відновлював виконання через `send()`.

## 3. Делегування підгенераторам: PEP 380 та yield from (Python 3.3)

Складання багаторівневих асинхронних викликів у генераторній моделі вимагало громіздких циклів ручної ретрансляції значень `send()` та винятків `throw()` крізь усі проміжні функції.

У Python 3.3 специфікація PEP 380 запровадила синтаксичну конструкцію `yield from`. Вона автоматизувала прозоре двоспрямоване прокидання даних та помилок між викликачем і найглибшим вкладеним підгенератором, а також повернула значення фінального виразу `return` через виняток `StopIteration.value`. Це заклало фундамент для стандартної бібліотеки асинхронності.

## 4. Народження asyncio та проєкт Tulip (Python 3.4)

У 2012–2013 роках Гвідо ван Россум ініціював проєкт під кодовою назвою *Tulip*, який ліг в основу PEP 3156 (*Asynchronous IO Support Rebooted*) і увійшов до стандартної бібліотеки Python 3.4 як модуль `asyncio`.

Архітектура `asyncio` першого покоління спиралася на:
- Декоратор `@asyncio.coroutine` для позначення функцій-генераторів як корутин;
- Синтаксис `yield from future` для очікування результатів;
- Абстракцію `AbstractEventLoop` над низькорівневими системними селекторами `epoll`, `kqueue` та Windows `IOCP`;
- Модель `Transport` і `Protocol` для мережевої взаємодії, запозичену з Twisted.

## 5. Нативні корутини: async та await (Python 3.5 – 3.7)

Співіснування генераторів для обходу колекцій та генераторів для асинхронного керування створювало плутанину: випадковий виклик функції без `yield from` не викликав помилки компіляції, а повертав не запущений генераторний об'єкт.

У Python 3.5 Юрій Селіванов запропонував PEP 492 (*Coroutines with async and await syntax*). Специфікація розділила ці концепції на рівні синтаксису мови:
- Ключове слово `async def` створило новий тип об'єкта — нативну корутину `coroutine` (`PyCoroObject` у C-ядрі);
- Ключове слово `await` замінило `yield from` і стало приймати лише об'єкти, які реалізують протокол `__await__()` (екземпляри `asyncio.Future`, `asyncio.Task` або інші корутини);
- Було введено асинхронні ітератори (`async for`, `__aiter__`, `__anext__`) та асинхронні контекстні менеджери (`async with`, `__aenter__`, `__aexit__`).

У Python 3.7 модуль `asyncio` отримав високошвидкісну C-реалізацію об'єктів `Task` та `Future` (`_asyncio.c`), а також PEP 567 (*Context Variables*), що дозволило коректно передавати контекст (ідентифікатори транзакцій, автентифікаційні токени, трасування) крізь асинхронні перемикання завдань.

## 6. Структурована асинхронність та TaskGroup (Python 3.11+)

Традиційні підходи до конкурентності через `asyncio.gather()` або неконтрольоване створення завдань `asyncio.create_task()` страждали від фундаментальної вади: якщо одне завдання падало з помилкою, інші продовжували працювати у фоні без прив'язки до батьківського контексту. Такі «висячі» задачі (*orphaned tasks*) споживали пам'ять, блокували дескриптори сокетів і ускладнювали налагодження.

Під впливом досліджень Мартіна Сустріка (проєкт Trio та концепція *Structured Concurrency*) і робіт Натаніеля Сміта, у Python 3.11 було прийнято комплексні покращення:
1. **PEP 654 (Exception Groups and except\*):** З'явився клас винятків `ExceptionGroup`, здатний упаковувати кілька одночасних помилок з різних гілок виконання, та конструкція `except*` для їхньої паралельної фільтрації.
2. **`asyncio.TaskGroup`:** Новий стандарт керування паралелізмом. Контекстний менеджер `async with asyncio.TaskGroup() as tg:` гарантує детерміноване деревоподібне життя завдань: вихід із блоку можливий лише після завершення всіх дочірніх задач. Якщо будь-яка задача викидає виняток, усі інші задачі групи негайно скасовуються, а всі виниклі помилки збираються в єдиний `ExceptionGroup`.

Еволюція пройшла шлях від низькорівневих маніпуляцій станом генераторного стека через інструкції `yield` до суворої структурованої асинхронності, де життєвий цикл кожного паралельного обчислення обмежений межами лексичного блоку коду.
