# 📋 Контракти ядра asyncio: Event Loop, Future та Transport/Protocol

Архітектура `asyncio` будується на суворому математичному та системному розділенні обов'язків між диспетчером подій, примітивами відкладеного результату та дворівневою моделлю введення-виведення. Кожен шар системи взаємодіє з іншими через чітко визначені протоколи, що дозволяє замінювати внутрішні реалізації (наприклад, стандартний `asyncio` на `uvloop`) без модифікації коду прикладного рівня.

Нижче наведено детальний опис контрактів, станів, винятків та системних гарантій компонентів ядра CPython `asyncio`.

---

## 1. Контракт циклу подій (asyncio.AbstractEventLoop)

Клас `AbstractEventLoop` визначає інтерфейс низькорівневого диспетчера. Екземпляр циклу подій керує трьома системними структурами: чергою готових обробників `_ready`, бінарною мін-купою таймерів `_scheduled` та системним селектором сокетів.

### Планування обробників і міжпотокова взаємодія

Планування функцій зворотного виклику здійснюється за допомогою методів групи `call_*`:

- **`call_soon(callback, *args, context=None) -> Handle`:**
  Додає об'єкт виклику в кінець черги `_ready` поточного циклу. Виклик гарантовано виконується на поточній або найближчій ітерації `_run_once()`. Метод не є потокобезпечним: його дозволено викликати виключно з того системного потоку ОС, у якому виконується цикл подій. Якщо передано необов'язковий параметр `context`, функція виконується у відповідному контексті `contextvars.Context`.
- **`call_soon_threadsafe(callback, *args, context=None) -> Handle`:**
  Потокобезпечний варіант планування. Додає дію до внутрішнього списку черги з використанням м'ютекса операційної системи та записує один сигнальний байт у системний сокетний канал (*self-pipe* або сокетну пару `socketpair()`). Це перериває блокувальний виклик `select()` або `epoll_wait()` у потоці циклу подій, змушуючи його негайно опрацювати нову дію.
- **`call_later(delay, callback, *args, context=None) -> TimerHandle`:**
  Планує виконання обробника через відносний проміжок часу `delay` (у секундах). Обчислює абсолютний час запуску як `loop.time() + delay` і розміщує об'єкт `TimerHandle` у бінарній мін-купі `_scheduled`.
- **`call_at(when, callback, *args, context=None) -> TimerHandle`:**
  Планує виклик на абсолютний монотонний момент часу `when`. Час повинен бути узгоджений зі значенням годинника `loop.time()`. Від'ємні або минулі значення `when` призводять до виконання обробника на найближчій ітерації.
- **`time() -> float`:**
  Повертає поточний час за внутрішнім монотонним годинником циклу, який використовує системний виклик `clock_gettime(CLOCK_MONOTONIC)` або `time.monotonic()`. Значення не зазнає впливу коригувань системного часу (NTP).

### Мультиплексування сокетів та дескрипторів

Керування подіями готовності дескрипторів сокетів у системному селекторі:

- **`add_reader(fd, callback, *args) -> None`:**
  Реєструє дескриптор файлу або сокета `fd` у селекторі ОС для відстеження події готовності до читання (`selectors.EVENT_READ`). Коли в буфер сокета надходять нові байти або сокет готовий прийняти вхідне з'єднання через `accept()`, цикл подій ставить `callback(*args)` у чергу `_ready`. Якщо дескриптор уже відстежується, попередня дія замінюється новою.
- **`remove_reader(fd) -> bool`:**
  Видаляє дескриптор зі списку спостереження за читанням. Повертає `True`, якщо дескриптор був успішно зареєстрований і видалений, або `False`, якщо він був відсутній у селекторі.
- **`add_writer(fd, callback, *args) -> None`:**
  Реєструє дескриптор у селекторі для відстеження події готовності до запису (`selectors.EVENT_WRITE`), що сигналізує про наявність вільного місця у вихідному системному буфері `SO_SNDBUF`.
- **`remove_writer(fd) -> bool`:**
  Видаляє дескриптор зі списку спостереження за подіями запису.

### Керування життєвим циклом та станом циклу

- **`run_forever() -> None`:**
  Переводить цикл подій у нескінченний режим виконання ітерацій `_run_once()`. Метод блокує викликаючий потік ОС доти, доки не буде викликано метод `stop()`. Якщо цикл уже виконується, генерується `RuntimeError`.
- **`run_until_complete(future) -> Any`:**
  Приймає об'єкт `Future` або корутину (яка автоматично загортається в `Task`). Запускає виконання циклу подій і повертає значення `future.result()` після завершення. Якщо корутина завершується винятком, цей виняток повторно піднімається з `run_until_complete`.
- **`stop() -> None`:**
  Сигналізує циклу подій про необхідність зупинки після завершення поточної ітерації `_run_once()`. Усі готові дії, що залишилися в `_ready`, не знищуються і залишаються доступними для виконання під час наступного запуску.
- **`is_running() -> bool`:**
  Повертає логічне `True`, якщо цикл подій наразі активно обробляє черги та селектори.
- **`is_closed() -> bool`:**
  Повертає `True`, якщо цикл подій було остаточно закрито через `close()`.
- **`close() -> None`:**
  Звільняє всі системні ресурси, закриває селектори ОС і wake-up сокети. Виклик `close()` на активному циклі, що виконується, викликає критичний виняток `RuntimeError`.

## 2. Об'єкти низькорівневих обробників: Handle та TimerHandle

Кожна дія, запланована в циклі подій, упаковується в легкоатлетичний об'єкт `Handle`:

- **Властивості `asyncio.Handle`:**
  - `handle.cancelled() -> bool`: Повертає `True`, якщо обробник було скасовано до його запуску.
  - `handle.cancel() -> None`: Позначає обробник як скасований (`_cancelled = True`). При вилученні з черги `_ready` такий обробник не викликається, а його посилання на функцію та аргументи обнуляються для запобігання витокам пам'яті.
- **Особливості `asyncio.TimerHandle`:**
  - Успадковує `Handle` і містить додаткове поле абсолютного часу `_when`.
  - Метод `timer_handle.when() -> float` повертає точний час активації.
  - Реалізує магічні методи порівняння (`__lt__`, `__le__`, `__gt__`, `__ge__`), що дозволяє об'єктам автоматично впорядковуватися всередині бінарної мін-купи ядра CPython.

## 3. Контракти примітивів синхронізації: Future та Task

### Стан і переходи asyncio.Future

Об'єкт `Future` інкапсулює кінцевий автомат результату асинхронної дії:

```
[ PENDING ] ─── set_result() ────► [ FINISHED ]
     │
     ├─── set_exception() ───────► [ FINISHED (with error) ]
     │
     └─── cancel() ──────────────► [ CANCELLED ]
```

1. **`done() -> bool`:** Повертає `True`, якщо стан об'єкта відмінний від `PENDING` (тобто операція завершилася успіхом, помилкою або скасуванням).
2. **`cancelled() -> bool`:** Повертає `True`, якщо стан об'єкта перейшов у `CANCELLED`.
3. **`result() -> Any`:**
   - Якщо стан `FINISHED` і результат було встановлено через `set_result(val)` — повертає `val`.
   - Якщо стан `FINISHED`, але було зафіксовано помилку через `set_exception(exc)` — викидає виняток `exc`.
   - Якщо стан `CANCELLED` — викидає `asyncio.CancelledError`.
   - Якщо стан `PENDING` — викидає `asyncio.InvalidStateError`.
4. **`exception() -> BaseException | None`:** Повертає об'єкт винятку, якщо встановлено помилку, `None` при успішному результаті, або піднімає `InvalidStateError` / `CancelledError`.
5. **`add_done_callback(fn, *, context=None) -> None`:**
   Реєструє функцію зворотного виклику `fn(future)`. Якщо на момент реєстрації `Future` уже завершено (`done() == True`), виклик `fn` негайно планується в `_ready` через `loop.call_soon()`. Якщо ні — додається до внутрішнього масиву `_callbacks`.
6. **`set_result(result) -> None`:** Переводить стан у `FINISHED`, зберігає значення та планує запуск усіх зареєстрованих обробників зворотного виклику. Повторний виклик викликає `InvalidStateError`.
7. **`set_exception(exception) -> None`:** Переводить стан у `FINISHED` зі збереженням об'єкта винятку. Передача екземпляра `StopIteration` заборонена і викликає `TypeError`.

### Керування виконанням у класі asyncio.Task

Клас `Task` успадковує `Future` і бере на себе обов'язки драйвера корутини:

- **`get_coro() -> Coroutine`:** Повертає об'єкт обгорнутої нативної корутини.
- **`get_name() -> str` / `set_name(name: str) -> None`:** Читання та встановлення людського імені завдання для діагностики й трасування.
- **`get_stack(*, limit=None) -> list[FrameType]`:** Повертає стек викликів корутини, якщо вона призупинена, або порожній список, якщо завдання завершено.
- **`cancel(msg=None) -> bool`:** Планує викидання винятку `CancelledError` всередині корутини під час наступного кроку `_step()`. Повертає `True`, якщо запит на скасування успішно виставлено.
- **`cancelling() -> int` (Python 3.11+):** Повертає кількість активних запитів на скасування.
- **`uncancel() -> int` (Python 3.11+):** Зменшує внутрішній лічильник скасувань на одиницю. Використовується в механізмах структурованої асинхронності для локалізації `CancelledError`.

## 4. Контракти Transport та Protocol (Низькорівневий I/O)

Дворівнева архітектура розділяє фізичний сокет (Transport) та логіку розбору протоколу (Protocol).

### Життєвий цикл asyncio.Protocol

1. **`connection_made(transport: BaseTransport) -> None`:**
   Викликається селектором у момент успішного встановлення мережевого з'єднання. Отриманий об'єкт транспорту зберігається в атрибутах протоколу для виконання операцій запису.
2. **`data_received(data: bytes) -> None`:**
   Викликається щоразу, коли системний виклик `recv()` вичитує порцію байтів із вхідного сокета. Дані передаються у вигляді незмінного об'єкта `bytes`.
3. **`eof_received() -> bool | None`:**
   Викликається при отриманні TCP FIN сегмента від віддаленого вузла. Якщо метод повертає `True` або `None`, транспорт закривається автоматично; якщо `False` — з'єднання залишається відкритим для запису.
4. **`pause_writing() -> None` та `resume_writing() -> None`:**
   Методи керування зворотним тиском. `pause_writing()` викликається транспортом, коли обсяг невідправлених даних у вихідному буфері перевищує межу `high_water`. `resume_writing()` викликається, коли буфер спорожнюється нижче `low_water`.
5. **`connection_lost(exc: Exception | None) -> None`:**
   Фінальний метод життєвого циклу. Викликається при повному закритті сокета. Якщо закриття відбулося штатно за ініціативою клієнта або сервера, аргумент `exc` дорівнює `None`. Якщо з'єднання розірвано внаслідок збою мережі або таймауту, `exc` містить об'єкт винятку (`ConnectionResetError`, `BrokenPipeError`).

### Контракт керування буфером WriteTransport

- **`write(data: bytes) -> None`:** Асинхронно записує байти у внутрішній буфер пам'яті транспорту. Метод ніколи не блокує виконання коду.
- **`set_write_buffer_limits(high=None, low=None) -> None`:** Встановлює водяні мітки для керування зворотним тиском (за замовчуванням `high_water = 64 КБ`, `low_water = 16 КБ`).
- **`get_write_buffer_size() -> int`:** Повертає точну кількість байтів, що очікують відправки у мережевий сокет.

## 5. Контракти StreamReader та StreamWriter (Високорівневі потоки)

Шар потоків надає зручні корутини для послідовного читання та запису даних без створення класів-протоколів.

### Буферизоване читання: asyncio.StreamReader

- **`read(n=-1) -> bytes`:** Зчитує до `n` байтів. Якщо `n=-1`, очікує і повертає всі доступні байти до моменту закриття потоку (EOF).
- **`readline() -> bytes`:** Зчитує байти до символу нового рядка `\n`. Якщо досягнуто кінця файлу без роздільника, повертає накопичений залишок.
- **`readexactly(n: int) -> bytes`:** Зчитує рівно `n` байтів. Якщо потік закривається раніше, ніж прочитано `n` байтів, генерується виняток `asyncio.IncompleteReadError`.
- **`readuntil(separator=b'\n') -> bytes`:** Зчитує дані до вказаного байтового роздільника. Якщо розмір прочитаного буфера перевищує внутрішній ліміт `limit` до знаходження роздільника, викидається `asyncio.LimitOverrunError`.

### Буферизований запис і зворотний тиск: asyncio.StreamWriter

- **`write(data: bytes) -> None`:** Поміщає дані у вихідний буфер транспорту.
- **`drain() -> None`:** Асинхронний метод синхронізації зворотного тиску. Якщо вихідний буфер транспорту перевищив поріг `high_water`, виклик `await writer.drain()` створює об'єкт `Future` і призупиняє поточну корутину. Щойно буфер опускається нижче `low_water`, корутина прокидається і продовжує виконання.
- **`close() -> None`:** Ініціює закриття підлеглого транспорту та сокета.
- **`wait_closed() -> None`:** Корутина, що очікує повного завершення процедури закриття з'єднання на системному рівні.
