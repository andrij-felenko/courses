Коли мережевий сервер на Python обслуговує тисячі клієнтських з'єднань одночасно, класична багатопотокова модель виділяє окремий системний потік операційної системи на кожен активний сокет. Системний потік вимагає від 1 до 8 мегабайтів виділеного адресного простору під стек, а витісняльне перемикання контексту ядра (*preemptive context switch*) навантажує планувальник ОС та скидає кеші процесора (L1/L2). Крім того, глобальне блокування інтерпретатора (GIL) у CPython обмежує виконання байткоду одним ядром: потоки конкурують за замок м'ютекса, утворюючи чергу очікування навіть у тих випадках, коли переважна більшість часу витрачається на очікування надходження байтів із мережевої карти.

Асинхронна парадигма розв'язує цю проблему через мультиплексування введення-виведення в одному системному потоці. Замість блокування потоку на виклику `recv()` сокети переводяться в неблокувальний режим (`O_NONBLOCK`), а ядро операційної системи повідомляє інтерпретатор про появу даних через спеціалізовані механізми сповіщення (`epoll`, `kqueue` або `IOCP`). Керування цим процесом у Python бере на себе стандартна підсистема `asyncio`.

## 1. Внутрішня механіка циклу подій (Event Loop) та системні селектори

Цикл подій (*Event Loop*, від лат. *eventus* — випадок, наслідок та англ. *loop* — петля, замкнений контур) — це центральний планувальник та диспетчер завдань, що працює як нескінченний цикл опитування та маршрутизації подій.

```
+─────────────────────────────────────────────────────────────+
|               Базовий цикл диспетчеризації                 |
|                                                             |
|   1. Обчислити таймаут для селектора (до найближчого таймера) |
|   2. Опитати ОС: events = selector.select(timeout)          |
|   3. Додати сокетні колбеки та дозрілі таймери в _ready     |
|   4. Виконати пачку завдань: for h in ready: h._run()       |
+─────────────────────────────────────────────────────────────+
```

### Підсистема селекторів: epoll, kqueue та IOCP

В основі `asyncio` лежить стандартний модуль `selectors`, який надає платформонезалежну обгортку над механізмами мультиплексування дескрипторів конкретної операційної системи:
- **`epoll` у Linux (`selectors.EpollSelector`):** Створює системний контекст через `epoll_create1()`. На відміну від застарілих `select()` та `poll()`, складність яких масштабується лінійно `O(N)` від загальної кількості відкритих сокетів, `epoll` працює за `O(1)` від кількості активних подій, повертаючи готовий список дескрипторів із простору ядра.
- **`kqueue` у macOS та FreeBSD (`selectors.KqueueSelector`):** Використовує універсальну чергу подій ядра (*kernel queue*), що відстежує стан сокетів, файлів, процесів та сигналів без накладних витрат на сканування таблиці дескрипторів.
- **`IOCP` у Windows (`asyncio.ProactorEventLoop`):** Порти завершення введення-виведення (*I/O Completion Ports*). На відміну від POSIX-систем, де застосовується реакторна модель (*Reactor pattern* — ядро повідомляє про *готовність* дескриптора до операції), Windows застосовує проакторну модель (*Proactor pattern* — застосунок ініціює асинхронне читання `ReadFileEx()` або запис `WSASend()`, а ядро сигналізує про *фактичне завершення* перенесення байтів у виділений буфер).

На низькому системному рівні очікування готовності сокетів реалізується через реєстрацію дескрипторів у ядрі ОС:

:::tabs
```c
// epoll_reactor.c: Низькорівневе очікування подій сокета
#include <sys/epoll.h>
#include <unistd.h>

int wait_for_socket_event(int epoll_fd, int socket_fd, int timeout_ms) {
    struct epoll_event event;
    event.events = EPOLLIN | EPOLLET; // Edge-Triggered читання
    event.data.fd = socket_fd;
    
    if (epoll_ctl(epoll_fd, EPOLL_CTL_ADD, socket_fd, &event) < 0) {
        return -1;
    }
    
    struct epoll_event active_events[1];
    int n = epoll_wait(epoll_fd, active_events, 1, timeout_ms);
    return n; // Кількість активних подій
}
```
```cpp
// epoll_reactor.cpp: Ідіоматична обгортка над системним селектором
#include <sys/epoll.h>
#include <unistd.h>
#include <span>
#include <system_error>

int wait_for_socket_event(int epoll_fd, int socket_fd, int timeout_ms) {
    epoll_event ev{};
    ev.events = EPOLLIN | EPOLLET;
    ev.data.fd = socket_fd;

    if (epoll_ctl(epoll_fd, EPOLL_CTL_ADD, socket_fd, &ev) < 0) {
        throw std::system_error(errno, std::generic_category(), "epoll_ctl error");
    }

    epoll_event active_events[1];
    int n = epoll_wait(epoll_fd, active_events, 1, timeout_ms);
    if (n < 0) {
        throw std::system_error(errno, std::generic_category(), "epoll_wait error");
    }
    return n;
}
```

### Структури даних циклу: _ready та _scheduled

У CPython базовий клас циклу подій `BaseEventLoop` містить дві ключові структури черг:
1. **Черга готових завдань (`_ready`):** Двобічна черга `collections.deque`, яка містить екземпляри `asyncio.Handle`. Усі функції, додані через `loop.call_soon()`, зворотні виклики завершених завдань або кроки корутин потрапляють сюди. Елементи черги готові до негайного послідовного виконання за правилом FIFO (First-In, First-Out).
2. **Черга таймерів (`_scheduled`):** Бінарна мін-купа (масив Python, керований модулем `heapq`), де елементи `asyncio.TimerHandle` впорядковані за монотонною часовою міткою `when`. На вершині купи (`_scheduled[0]`) завжди розташовується об'єкт із найближчим дедлайном спрацьовування.

### Анатомія кроку диспетчеризації: метод _run_once()

Кожна ітерація циклу подій реалізована внутрішнім методом `_run_once()`. Робота методу розбита на чотири послідовні фази:

1. **Розрахунок таймауту селектора:**
   Планувальник оцінює стан черг. Якщо в черзі `_ready` уже є готові обробники, цикл не має права засинати: таймаут виставляється в `0` (`timeout = 0`). Якщо черга `_ready` порожня, перевіряється черга таймерів `_scheduled`. Час очікування розраховується як різниця між вершиною купи та поточним моментом: `timeout = max(0, _scheduled[0].when - loop.time())`. Якщо таймерів немає, таймаут дорівнює `None` (блокування селектора до появи першої події сокета).
2. **Опитування селектора:**
   Виконується виклик `event_list = self._selector.select(timeout)`. Потік звільняє процесорне ядро і переходить у стан очікування на рівні системного виклику ОС. Після пробудження селектор повертає список зареєстрованих файлових дескрипторів, у яких відбулися події `EVENT_READ` або `EVENT_WRITE`. Обробники, прив'язані до цих сокетів, упаковуються в `Handle` і переносяться в кінець черги `_ready`.
3. **Перенесення дозрілих таймерів:**
   Цикл перевіряє мін-купу `_scheduled`. Усі об'єкти `TimerHandle`, час спрацьовування яких менший або дорівнює поточному часу `now = loop.time()`, вилучаються з купи через `heapq.heappop()` і переміщуються у чергу `_ready`. Якщо таймер було скасовано (`handle.cancelled() == True`), він просто відкидається.
4. **Виконання пачки дій:**
   Фіксується поточна довжина черги: `ntasks = len(self._ready)`. Цикл вилучає рівно `ntasks` елементів через `self._ready.popleft()` і викликає метод `handle._run()`. Якщо під час виконання обробника створюються нові завдання через `call_soon()`, вони потрапляють у хвіст `_ready` і будуть оброблені лише на наступній ітерації `_run_once()`. Це гарантує захист від нескінченного зависання на одному кроці.

### Механіка таймерів та асинхронної паузи (asyncio.sleep)

Функція `asyncio.sleep(delay, result=None)` демонструє елегантне поєднання таймерної черги та примітива `Future`:
1. `sleep()` отримує поточний активний цикл подій через `loop = asyncio.get_running_loop()`.
2. Якщо `delay <= 0`, функція викликає `await asyncio.sleep(0)`, що всередині транслюється у `loop.call_soon()` — це передає квант часу іншим готовим корутинам без зупинки селектора.
3. Якщо `delay > 0`, створюється новий об'єкт `future = loop.create_future()`.
4. Цикл реєструє дію через `h = loop.call_later(delay, future.set_result, result)`.
5. `sleep` очікує завершення: `return await future`.
6. Якщо під час очікування завдання скасовується, обробник перехоплює `CancelledError` і викликає `h.cancel()`, видаляючи таймер із бінарної купи та усуваючи марні виклики.

> 🔧 **Навіщо це.**
> Розуміння послідовності `_run_once()` пояснює, чому будь-який синхронний блокувальний виклик (наприклад, `time.sleep(5)`, довге математичне обчислення або синхронне звернення до диска `open().read()`) заморожує весь застосунок. Оскільки виконання коду відбувається синхронно у фазі 4, цикл не може перейти до фази 2 (опитування селектора). Усі інші клієнтські сокети перестають приймати пакети, а таймери перестають спрацьовувати до моменту, поки блокувальна функція не поверне керування.
> 
> Для делегування блокувальних дій у фоновий пул потоків використовується `asyncio.to_thread(func, *args)` (або низькорівневий `loop.run_in_executor(None, func)`). Функція запускає дію в системному потоці `ThreadPoolExecutor`, відпускає GIL під час виконання важкого коду, а після завершення повертає результат у головний потік циклу подій через потокобезпечний метод `loop.call_soon_threadsafe()`.

Детальний опис еволюції асинхронної моделі від генераторів Python 2.2 до сучасної архітектури наведено у вставці [Еволюція асинхронності в Python: від генераторів до TaskGroup](root:sys-plang-python/asyncio-event-loop/hist-async-evolution.md).

## 2. Корутини, інструкція await, різниця між Task та Future

### Внутрішній устрій корутини (PyCoroObject)

Оголошення функції через ключове слово `async def` створює функцію-корутину. Виклик такої функції не виконує її тіло негайно, а повертає спеціальний об'єкт корутини — екземпляр C-структури `PyCoroObject`:

```
+───────────────────────────────────────────────────────────+
|               Структура PyCoroObject у CPython            |
|                                                           |
|  • cr_code: посилання на скомпільований PyCodeObject      |
|  • cr_frame: кадр виконання з локальними змінними         |
|  • cr_await: посилання на поточний очікуваний об'єкт      |
|  • cr_state: CORO_CREATED / RUNNING / SUSPENDED / CLOSED  |
+───────────────────────────────────────────────────────────+
```

Корутина є кінцевим автоматом:
- **`CORO_CREATED`:** Об'єкт створено, виконання ще не розпочато;
- **`CORO_RUNNING`:** Байткод виконується інтерпретатором у даний момент;
- **`CORO_SUSPENDED`:** Виконання призупинено в точці інструкції `await`;
- **`CORO_CLOSED`:** Виконання завершено через повернення значення або виняток.

Просування корутини вперед здійснюється за допомогою низькорівневого методу `.send(value)`. Перший запуск виконується викликом `coro.send(None)`, що запускає виконання байткоду до першого виразу `await`. Якщо під час очікування виникає необхідність ініціювати виняток (наприклад, скасування), викликається метод `coro.throw(exc)`.

### Протокол __await__() та механіка зупинки

Коли інтерпретатор зустрічає інструкцію `await expr`, він викликає у цільового об'єкта магічний метод `expr.__await__()`. Цей метод зобов'язаний повернути стандартний ітератор.

Усередині циклу виконання інтерпретатор переходить до байткод-інструкцій `SEND` та `YIELD_VALUE`. Корутина призупиняє свій стековий кадр, зберігає стан усіх локальних змінних у купі CPython й віддає значення очікуваного об'єкта (зазвичай екземпляра `Future`) викликачеві.

### Примітив відкладеного результату: asyncio.Future

`asyncio.Future` — це низькорівневий об'єкт збереження стану операції, яка ще не завершилася. Він не містить коду виконання чи посилань на корутини, а виконує роль контейнера для трьох полів:
- **`_state`:** Поточний стан — `PENDING` (в очікуванні), `FINISHED` (завершено) або `CANCELLED` (скасовано);
- **`_result` / `_exception`:** Збережене значення успішного результату або об'єкт винятку;
- **`_callbacks`:** Список функцій зворотного виклику, які повинні бути виконані після переходу в стан `FINISHED`.

Метод `future.set_result(val)` переводить об'єкт у стан `FINISHED` і автоматично ставить усі зареєстровані в `_callbacks` функції у чергу `_ready` циклу подій через `loop.call_soon()`.

### Керівний рушій: asyncio.Task

`asyncio.Task` є прямим нащадком `asyncio.Future`. Завдання загортає об'єкт корутини та керує її життєвим циклом, пов'язуючи призупинення на `await` з диспетчеризацією циклу подій.

```
       coro.send(None)
Task ─────────────────► Coroutine
  ▲                         │
  │     yields Future       │ await future
  └─────────────────────────┘
  │
  ├─► future.add_done_callback(Task._wakeup)
  │
  ▼  (Подія I/O завершилася ──► future.set_result())
Task._wakeup()
  │
  └─► loop.call_soon(Task._step) ──► coro.send(result)
```

Алгоритм роботи методу `Task._step()`:
1. Завдання викликає `result = self._coro.send(val)`.
2. Якщо корутина повертає фінальне значення (завершується винятком `StopIteration`), `Task` перехоплює виняток і викликає `self.set_result(StopIteration.value)`.
3. Якщо корутина виконує `await future`, оператор `yield` повертає очікуваний об'єкт `Future`. `Task` підписується на завершення цього об'єкта через `future.add_done_callback(self._wakeup)`.
4. Коли низькорівнева операція I/O добігає кінця (селектор фіксує надходження даних), системний обробник викликає `future.set_result(data)`.
5. Спрацьовує колбек `Task._wakeup()`, який ставить черговий крок `Task._step` у чергу `_ready`.
6. На наступній ітерації циклу `_step` відновлює корутину, передаючи отримані дані: `self._coro.send(future.result())`.

### Механіка скасування задач та asyncio.shield

Коли викликається метод `task.cancel(msg="timeout")`, завдання не зупиняється миттєво. Планувальник виконує такі кроки:
1. Об'єкту `Task` виставляється прапорець запиту на скасування, а внутрішній лічильник `cancelling()` збільшується.
2. Якщо задача перебуває в стані очікування на внутрішньому `Future`, цей `Future` також скасовується.
3. Під час наступного виклику `Task._step()` замість `coro.send(val)` викликається `coro.throw(asyncio.CancelledError)`.
4. Корутина отримує можливість перехопити виняток `try...except asyncio.CancelledError` для виконання фінального прибирання ресурсів (закриття файлів, відправки прощальних повідомлень у мережу).
5. Якщо корутина не придушує виняток, він спливає назовні, і `Task` остаточно переходить у стан `CANCELLED`.

Для захисту критичних операцій від зовнішнього скасування використовується обгортка `asyncio.shield(coro_or_future)`:

```python
async def handle_transaction():
    # Навіть якщо клієнт обірвав з'єднання і handle_transaction скасовується,
    # операція commit_to_database продовжить виконуватися до кінця
    await asyncio.shield(commit_to_database())
```

Метод `shield()` створює зовнішній проміжний `Future`, який транслює результат внутрішньої задачі, але поглинає зовнішні запити на скасування, не передаючи їх внутрішній операції.

Повний довідник інтерфейсів циклу подій, сигнатур та методів `Transport`/`Protocol` наведено у вставці [Контракти ядра asyncio: Event Loop, Future та Transport/Protocol](root:sys-plang-python/asyncio-event-loop/api-event-loop-core.md).

## 3. Керування паралелізмом: gather, структурована асинхронність та TaskGroup

### asyncio.gather та проблема некерованих завдань

Історично першим способом конкурентного запуску кількох корутин була функція `asyncio.gather(*aws, return_exceptions=False)`:

```python
results = await asyncio.gather(
    fetch_user_profile(user_id),
    fetch_user_orders(user_id),
    fetch_user_notifications(user_id),
)
```

Функція `gather()` загортає всі передані корутини в об'єкти `Task`, реєструє їх у циклі подій і очікує завершення кожного з них. Якщо параметр `return_exceptions=False` (за замовчуванням), перший же збій в одній із задач призводить до негайного підняття цього винятку в точці виклику `await gather()`.

Однак решта запущених задач **не скасовуються автоматично**. Вони продовжують виконуватися у фоновому режимі як «завдання-сироти» (*orphaned tasks*). Якщо ці задачі звертаються до вже закритих сокетів або модифікують стан пам'яті, це призводить до прихованих витоків ресурсів та стану гонитви.

Якщо ж передати `return_exceptions=True`, функція `gather()` не викидає винятки, а повертає їх як елементи вихідного списку разом із успішними результатами `[data1, DatabaseError(), data3]`. Це вимагає ручної перевірки кожного елемента через `isinstance(res, Exception)`.

### Структурована асинхронність у Python 3.11+: asyncio.TaskGroup

Структурована асинхронність (*Structured Concurrency*) постулює фундаментальне правило: **час життя дочірніх паралельних обчислень має бути суворо обмежений межами лексичного блоку коду батьківського контексту**.

У Python 3.11 для цього введено асинхронний контекстний менеджер `asyncio.TaskGroup`:

```python
async def load_dashboard_data(user_id: int) -> dict:
    async with asyncio.TaskGroup() as tg:
        task_profile = tg.create_task(fetch_user_profile(user_id))
        task_orders = tg.create_task(fetch_user_orders(user_id))
        task_metrics = tg.create_task(fetch_analytics_metrics(user_id))

    # Вихід із блоку 'async with' гарантує, що ВСІ задачі успішно завершилися
    return {
        "profile": task_profile.result(),
        "orders": task_orders.result(),
        "metrics": task_metrics.result(),
    }
```

### Механіка обробки помилок та ExceptionGroup (PEP 654)

Якщо одна із задач усередині `TaskGroup` зазнає невдачі (наприклад, `task_orders` викидає `DatabaseTimeoutError`), контекстний менеджер `TaskGroup` гарантує виконання наступного детермінованого протоколу:
1. Приймання нових задач через `tg.create_task()` блокується.
2. Усі інші незавершені задачі групи (`task_profile`, `task_metrics`) негайно отримують команду скасування `task.cancel()`.
3. Контекстний менеджер очікує завершення виконання процедур очищення (блоків `finally`) у кожній скасованій задачі.
4. Усі виниклі помилки (як первинний виняток, так і винятки, що могли виникнути під час скасування інших задач) збираються в єдиний ієрархічний об'єкт `ExceptionGroup`.
5. `ExceptionGroup` піднімається назовні блоку `async with`.

Для обробки окремих типів помилок із `ExceptionGroup` використовується синтаксис `except*`:

```python
try:
    await load_dashboard_data(user_id=42)
except* DatabaseTimeoutError as eg:
    logger.error(f"Помилка бази даних: {eg.exceptions}")
except* NetworkError as eg:
    logger.error(f"Мережевий збій: {eg.exceptions}")
```

### Обмеження конкурентності: asyncio.Semaphore

Коли сервер виконує тисячі асинхронних запитів до зовнішніх API або бази даних, надмірний паралелізм може вичерпати системні ліміти дескрипторів або перевантажити віддалений сервіс (*Thundering Herd Problem*).

Для обмеження кількості одночасних операцій використовується `asyncio.Semaphore(value)`:

```python
class ResourcePool:
    def __init__(self, max_concurrent: int = 50) -> None:
        self._semaphore = asyncio.Semaphore(max_concurrent)

    async def fetch_resource(self, client: aiohttp.ClientSession, url: str) -> bytes:
        async with self._semaphore:
            # Не більше 50 корутин можуть перебувати в цьому блоці одночасно
            async with client.get(url) as response:
                return await response.read()
```

Усередині `asyncio.Semaphore` підтримує цілочисельний лічильник доступних дозволів `_value` та чергу очікувачів `_waiters` (двобічну чергу об'єктів `Future`). Коли лічильник досягає `0`, виклик `await semaphore.acquire()` створює новий `Future`, додає його в чергу і призупиняє корутину. При виході з блоку `semaphore.release()` вилучає перший `Future` із черги й переводить його в завершений стан через `set_result(True)`, пробуджуючи наступну корутину за правилом абсолютної справедливості (FIFO).

### Асинхронні черги (asyncio.Queue) проти багатопотокових

Для обміну даними між корутинами-виробниками (*Producers*) та корутинами-споживачами (*Consumers*) використовується клас `asyncio.Queue`:
- На відміну від `queue.Queue` із модуля `threading`, який використовує важкі блокування ОС (`threading.Lock` та `threading.Condition`), `asyncio.Queue` працює повністю без м'ютекса.
- Якщо черга порожня, виклик `await queue.get()` створює об'єкт `Future`, поміщає його у внутрішню чергу `_getters` і призупиняє корутину.
- Щойно виробник викликає `await queue.put(item)`, черга бере перший `Future` із `_getters` і негайно передає йому елемент через `set_result(item)`.
- Якщо черга має обмежений розмір (`maxsize > 0`) і заповнена, корутини-виробники блокуються у черзі `_putters` доти, доки споживачі не викличуть `get()`.

## 4. Асинхронний мережевий I/O та зворотний тиск (Backpressure)

Мережева підсистема `asyncio` розділена на два рівні абстракції:
1. **Низькорівневий шар Transports і Protocols:** Пряма обробка сокетних подій через об'єкти зворотних викликів.
2. **Високорівневий шар Streams (StreamReader та StreamWriter):** Корутинний інтерфейс, що дозволяє працювати з мережевими сокетами так само просто, як зі звичайними файлами.

### Архітектура потоків: StreamReader та StreamWriter

Створення клієнтського з'єднання або запуск сервера за допомогою `asyncio.open_connection()` та `asyncio.start_server()` повертає пару пов'язаних об'єктів:
- **`StreamReader`:** Буферизований приймач байтів. Надає асинхронні методи читання: `read(n)` (до `n` байтів), `readline()` (читання до перенесення рядка `\n`), `readexactly(n)` (рівно `n` байтів або виняток `IncompleteReadError`).
- **`StreamWriter`:** Обгортка над вихідним буфером транспорту. Метод `writer.write(data)` є **синхронним і неблокувальним**: він не виконує системний виклик `send()` негайно, а лише розміщує байти у внутрішньому буфері пам'яті CPython.

### Механізм зворотного тиску: High Watermark та Low Watermark

Якщо сервер генерує дані зі швидкістю 100 МБ/с (наприклад, передає великий файл), а клієнт підключений через повільний мобільний канал зі швидкістю 1 МБ/с, відсутність контролю швидкості призведе до того, що `writer.write()` накопичуватиме невідправлені гігабайти у вихідному буфері оперативної пам'яті процесу.

Для запобігання цьому явищу застосовується механізм зворотного тиску (*Backpressure*):

```
                       write(chunk)
Корутина ─────────────────────────────────────────► Вихідний буфер
   ▲                                                      │
   │  await drain()                                       │ > high_water (64 КБ)
   │  (зупиняє корутину)                                  ▼
   └────────────────────────────────────────────── pause_reading()
                                                          │
                                                          │ (Ядро вивантажує
                                                          │  байти в мережу)
                                                          ▼
Корутина ◄──────────────────────────────────────── < low_water (16 КБ)
                   resume_reading() /
                 waiter.set_result(None)
```

1. Транспорт має дві межі буферизації: `high_water` (за замовчуванням 64 КБ) та `low_water` (за замовчуванням 16 КБ).
2. Коли обсяг невідправлених байтів у буфері перевищує `high_water`, транспорт переходить у стан блокування і викликає метод протоколу `pause_writing()`.
3. Коли розробник викликає `await writer.drain()`, метод перевіряє стан транспорту. Якщо буфер переповнено, `drain()` створює об'єкт `Future` (`_drain_waiter`) і призупиняє поточну корутину.
4. Операційна система поступово передає пакети з буфера сокета в фізичну мережу.
5. Щойно розмір черги опускається нижче порогу `low_water`, транспорт викликає `resume_writing()`, який встановлює результат для `_drain_waiter`.
6. Корутина прокидається з `await writer.drain()` і отримує дозвіл на відправку наступної порції даних.

*Механізм зворотного тиску в asyncio.StreamWriter: контроль водяних міток high_water/low_water, робота методу drain() та координація з сокетним буфером ядра ОС.*

## 5. Профілювання, налагодження та оптимізація продуктивності

### Режим налагодження циклу подій (Debug Mode)

Під час розробки та діагностики неочевидних зависань застосунку рекомендується вмикати режим налагодження через змінну середовища `PYTHONASYNCIODEBUG=1` або програмно:

```python
loop = asyncio.get_running_loop()
loop.set_debug(True)
loop.slow_callback_duration = 0.05  # Поріг фіксації повільних колбеків (50 мс)
```

У режимі налагодження `asyncio` активує глибоку інтроспекцію:
1. **Фіксація повільних дій (*Slow Callbacks*):** Якщо будь-який обробник або крок корутини у фазі 4 методу `_run_once()` виконується довше за `slow_callback_duration`, у лог записується попередження із точним часом затримки та місцем у вихідному коді.
2. **Перевірка незапущених корутин (*Unawaited Coroutines*):** Якщо функція `async def` була викликана без `await` чи передачі в `create_task()`, деструктор об'єкта при збиранні сміття виводить детальне попередження `RuntimeWarning: coroutine was never awaited` разом зі стеком виклику місця створення.
3. **Відстеження витоків дескрипторів:** Цикл перевіряє коректність закриття сокетів та підпорядкованих транспортів.

### Високопродуктивна заміна ядра: бібліотека uvloop

Стандартний цикл подій CPython реалізований частково мовою Python, а частково мовою C (`_asyncio.c`). Для екстремальних навантажень (від десятків до сотень тисяч запитів на секунду) стандартом індустрії є використання бібліотеки `uvloop`.

`uvloop` — це повноцінна низькорівнева заміна стандартного `asyncio.EventLoop`, написана мовою Cython поверх системної C-бібліотеки `libuv` (того самого рушія, що забезпечує асинхронність у Node.js). Підключення `uvloop` здійснюється одним рядком перед запуском програми:

```python
import asyncio
import uvloop

uvloop.install()  # Підміняє фабрику циклів подій за замовчуванням
asyncio.run(main())
```

Завдяки прямим C-структурам та агресивній оптимізації системних викликів `uvloop` скорочує накладні витрати на перемикання завдань у 2–4 рази, наближаючи продуктивність мережевого стека Python до рішень на мовах Go та Rust.

## 6. Архітектура високонавантаженого сервера телеметрії

Об'єднаємо розглянуті компоненти — селектори циклу, структуровані задачі `TaskGroup`, примітиви `Semaphore`, потокові сокети з контролем `drain()` та прямі датаграмні протоколи `DatagramProtocol` — у єдину промислову систему збирання телеметрії.

```
                  +──────────────────────────────+
                  |    Мережевий вхідний пул     |
                  +──────────────┬───────────────+
                                 │
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
       +───────────────────+           +───────────────────+
       |   TCP Слухач      |           |   UDP Ендпоінт    |
       |  StreamReader/    |           |  DatagramProtocol |
       |  StreamWriter     |           |  (Zero-alloc)     |
       +─────────┬─────────+           +─────────┬─────────+
                 │                               │
                 │   await writer.drain()        │   put_nowait()
                 │   (Backpressure)              │   (Load Shedding)
                 ▼                               ▼
       +───────────────────────────────────────────────────+
       |      Обмежена черга: asyncio.Queue(maxsize)       |
       +─────────────────────────┬─────────────────────────+
                                 │
                 ┌───────────────┼───────────────┐
                 ▼               ▼               ▼
           +───────────+   +───────────+   +───────────+
           | Воркер 1  |   | Воркер 2  |   | Воркер N  |
           |   (Task)  |   |   (Task)  |   |   (Task)  |
           +─────┬─────+   +─────┬─────+   +─────┬─────+
                 │               │               │
                 └───────────────┼───────────────┘
                                 ▼
                     +───────────────────────+
                     |  ClickHouse / Timescale|
                     |  (Пакетний запис)     |
                     +───────────────────────+
```

### Ключові інженерні принципи реалізації

1. **Гібридне приймання даних:**
   - Для UDP-пакетів застосовується низькорівневий клас `asyncio.DatagramProtocol`. Замість виділення важких об'єктів `Task` на кожну датаграму, метод `datagram_received()` виконує розбір сирих байтів через `struct.unpack()` і безпосередньо передає запис у чергу через `put_nowait()`. Це усуває накладні витрати на виділення пам'яті й дозволяє утилізувати всю смугу мережевого інтерфейсу.
   - Для TCP-з'єднань створюється повноцінна корутина-обробник на базі `asyncio.start_server()`. Обробник читає бінарні кадри через `reader.readexactly(24)`, валідує XOR-контрольну суму та надсилає підтвердження (ACK) із обов'язковим викликом `await writer.drain()`.
2. **Захист пам'яті через обмежені черги (Bounded Queues):**
   Мережеві обробники взаємодіють із воркерами запису через `asyncio.Queue(maxsize=10000)`. Якщо база даних тимчасово сповільнює обробку, черга запобігає вичерпанню пам'яті процесу: у UDP-каналі надлишкові пакети безпечно скидаються, а в TCP-каналі спрацьовує природний зворотний тиск на клієнтів.
3. **Структурований життєвий цикл та Graceful Shutdown:**
   Пул фонових воркерів та слухаючих серверів управляється через `asyncio.TaskGroup()`. При надходженні сигналів операційної системи `SIGINT` або `SIGTERM` цикл подій зупиняє прийом нових з'єднань, очікує повного вивантаження накопиченої черги через `await queue.join()` і лише після цього закриває активні завдання без втрати метрик.

Повна робоча реалізація сервера телеметрії з конфігурацією сокетів `TCP_NODELAY`, бінарним парсером та структурованим пулом задач наведена у практичній вставці [Високонавантажений сервер телеметрії на TCP та UDP](root:sys-plang-python/asyncio-event-loop/proj-telemetry-server.md).

## 7. Зведена матриця компонентів підсистеми asyncio

Для вибору оптимальних інструментів під час проєктування асинхронних систем на Python використовується порівняльна матриця компонентів ядра:

| Компонент | Рівень абстракції | Внутрішній механізм CPython | Основне призначення | Типові системні ризики |
|---|---|---|---|---|
| **`BaseEventLoop`** | Системне ядро | `selectors` (`epoll`/`kqueue`), `heapq`, `deque` | Маршрутизація подій I/O, виконання черг | Заморожування циклу синхронними блокувальними викликами |
| **`coroutine`** | Мова (`async def`) | `PyCoroObject`, стек-фрейм, `__await__` | Опис покрокової асинхронної бізнес-логіки | Створення без запуску (`coroutine was never awaited`) |
| **`asyncio.Future`** | Примітив синхронізації | Кінцевий автомат станів, масив `_callbacks` | Контейнер для збереження результату I/O операції | Зависання в стані `PENDING` при втраті сигналу завершення |
| **`asyncio.Task`** | Планувальник задач | Нащадок `Future`, метод `_step()`, `_coro` | Конкурентне виконання корутини в циклі подій | Некеровані фонові задачі (*orphaned tasks*) |
| **`TaskGroup`** | Структурованість | Контекстний менеджер, дерево задач, `ExceptionGroup` | Детерміноване керування групою конкурентних задач | Ігнорування обробки винятків `except*` |
| **`asyncio.Semaphore`** | Контроль ресурсів | Лічильник дозволів `_value`, черга `_waiters` | Захист пулів підключень, обмеження паралелізму | Взаємне блокування (*Deadlock*) при некоректній вкладеності |
| **`StreamReader/Writer`** | Потоковий I/O | Протокол буфера, водяні мітки `high/low_water` | Високорівнева робота з TCP-сокетами | Витік пам'яті через відсутність виклику `await writer.drain()` |
| **`DatagramProtocol`** | Низькорівневий I/O | Прямі системні виклики `recvfrom()`/`sendto()` | Швидкісне оброблення UDP без виділення об'єктів | Переповнення сокетного буфера ядра `SO_RCVBUF` |
