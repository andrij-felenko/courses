# Еволюція багатозадачності в Python: від asyncore до asyncio.to_thread

Кооперативна багатозадачність в інтерпретаторі Python виникла задовго до появи сучасного синтаксису `async`/`await`, пройшовши шлях від низькорівневих обгорток над системним викликом `select()` до повноцінних гібридних середовищ виконання, здатних прозоро делегувати блокувальні задачі пулам системних потоків. Розуміння цієї еволюції пояснює, чому блокувальний виклик залишається фатальним для циклу подій і як архітектура мови прийшла до сучасного розділення I/O-bound та CPU-bound навантажень.

## 1. Народження неблокувального I/O: Medusa та asyncore (1998)

Наприкінці 1990-х років більшість мережевих серверів працювали за моделлю «один клієнт — один потік» або «один клієнт — один процес». Для мови Python, де кожен потік операційної системи потребував виділення окремого стека пам'яті (зазвичай від 2 до 8 мегабайтів) та створював значні накладні витрати на перемикання контексту ядра, така модель різко обмежувала масштабованість кількома сотнями одночасних з'єднань.

У 1998 році Сем Рашинг (*Sam Rushing*) розробив високопродуктивний вебсервер Medusa та створив модулі `asyncore` і `asynchat`, які згодом увійшли до стандартної бібліотеки Python 1.5.2. Архітектура `asyncore` базувалася на єдиному нескінченному циклі `asyncore.loop()`, який опитував зареєстровані сокети через системний виклик `select()`.

Головним обмеженням `asyncore` була повна відсутність ізоляції блокувального коду. Якщо обробник мережевої події виконував тривале читання з диска, звертався до DNS через блокувальний `socket.gethostbyname()` або проводив математичні обчислення, весь сервер Medusa зупиняв обробку пакетів для всіх клієнтів. `asyncore` не мав вбудованих механізмів винесення блокувальних дій у фонові потоки, покладаючи всю відповідальність за неблокувальний стан на розробника.

## 2. Епоха фреймворків: Twisted та поява deferToThread (2001–2008)

У 2001 році Гліф Лефковіц (*Glyph Lefkowitz*) разом із командою започаткував проект Twisted. Twisted став першим промисловим асинхронним каркасом для Python, який запровадив концепцію реактора (*Reactor Pattern* — від лат. *re-* — проти, назад + *agere* — діяти) та об'єктів відкладеного результату `Deferred`.

Twisted вперше системно розв'язав проблему блокувального коду в асинхронному середовищі, створивши утиліту `twisted.internet.threads.deferToThread()`. Цей механізм дозволяв розробнику передати блокувальну функцію (наприклад, звернення до реляційної бази даних чи виклик синхронної бібліотеки) у внутрішній пул потоків реактора. Функція повертала об'єкт `Deferred`, на який можна було навісити колбеки `addCallback()` і `addErrback()`. Коли робочий потік завершував виконання коду, реактор за допомогою спеціального каналу міжпотокового сповіщення повертав результат у головний потік виконання.

Паралельно, у 2009 році, Брет Тейлор (*Bret Taylor*) та команда FriendFeed (згодом придбаного Facebook) представили фреймворк Tornado. Він оптимізував диспетчеризацію під Linux-механізм `epoll` та використав генератори Python (`yield`) для написання асинхронного коду без громіздких ланцюжків колбеків. У Tornado винесення блокувальних функцій здійснювалося через інтеграцію з пулами потоків та генераторний декоратор `@tornado.gen.coroutine`.

## 3. Стандартизація: PEP 3156, Tulip та народження asyncio (2012–2014)

Фрагментація екосистеми між Twisted, Tornado, Gevent та Eventlet спонукала автора Python Гвідо ван Россума (*Guido van Rossum*) створити єдиний стандарт асинхронного програмування. У 2012 році з'явилася чернетка PEP 3156 під кодовою назвою Tulip, яка лягла в основу модуля `asyncio` у складі Python 3.4.

PEP 3156 чітко зафіксував архітектурне правило: цикл подій `BaseEventLoop` повинен працювати в одному системному потоці, використовуючи кооперативну багатозадачність. Для взаємодії з блокувальним кодом модуль отримав фундаментальний метод:

```python
loop.run_in_executor(executor, func, *args)
```

Цей інтерфейс став уніфікованим мостом між світом асинхронних корутин та абстракцією пулів `concurrent.futures.Executor`, що з'явилася в Python 3.2 (PEP 3148). Якщо параметр `executor` дорівнював `None`, цикл подій створював і повторно використовував власний екземпляр `ThreadPoolExecutor`.

## 4. Нативний синтаксис та контекстні змінні: Python 3.5–3.9

Подальша еволюція мови була спрямована на спрощення роботи з асинхронними конструкціями та усунення прихованих пасток багатопоточності:

1. **Python 3.5 (PEP 492, 2015):** Запроваджено ключові слова `async def` та `await`. Корутини отримали статус повноцінного типу даних інтерпретатора, відокремившись від звичайних генераторів `yield from`.
2. **Python 3.7 (PEP 567, 2018):** Впроваджено модуль `contextvars` для збереження контексту (локальних змінних задач, ідентифікаторів трейсингу, сесій автентифікації) під час перемикання корутин. Виникла нова проблема: при виклику `loop.run_in_executor()` контекстні змінні не копіювалися у робочий потік автоматично.
3. **Python 3.9 (2020):** Додано високорівневу функцію `asyncio.to_thread()`. Вона автоматично викликає `contextvars.copy_context().run()`, передаючи поточний зріз контекстних змінних у потік виконання, та ізолює розробника від ручного управління об'єктом циклу `loop`.

Сьогодні екосистема Python розглядає `asyncio` не як заміну потоків або процесів, а як координаційний центр, що поєднує реактивний неблокувальний увід-вивід із фоновими пулами виконання.
