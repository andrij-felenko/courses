# 🔌 Моделі ізоляції оточень: venv, virtualenv, conda та PEP 582

Ізоляція середовищ розробки та виконання у світі Python реалізується кількома принципово різними архітектурними підходами. Вибір між легковажним перенаправленням системних префіксів, незалежним дистрибутивом із власним набором C-бібліотек або локальною структурою каталогів визначає швидкість старту, споживання дискового простору, переносність артефактів та глибину контролю над двійковими залежностями операційної системи.

## 1. Порівняльна матриця архітектурних рішень

У таблиці нижче зіставлено п'ять ключових моделей організації середовищ:

| Критерій | `venv` (PEP 405) | `virtualenv` (v20+) | `conda` (Anaconda/Miniconda) | PEP 582 `__pypackages__` | Контейнеризація (OCI/Docker) |
|---|---|---|---|---|---|
| **Механізм ізоляції** | `pyvenv.cfg` + підміна `sys.prefix` | `pyvenv.cfg` + кешовані колеса | Власний ізольований sysroot + бінарні пакунки | Пошук локального каталогу у `sys.path` | Простори назв ядра Linux (cgroups/namespaces) |
| **Рівень ізоляції** | Лише Python-пакунки (`site-packages`) | Лише Python-пакунки | Python + C-бібліотеки + системний рантайм | Лише Python-пакунки | Повна файлова система ОС та процеси |
| **Потреба у власному інтерпретаторі** | Ні (симлінк на хостовий Python) | Ні (симлінк або трамплін) | Так (повна копія двійкового інтерпретатора) | Ні (використовує будь-який викликаний Python) | Так (інтерпретатор всередині образу) |
| **Керування системними C-залежностями** | Ні (залежить від системних `glibc`, `libssl`) | Ні (залежить від системних бібліотек) | Так (постачає власні збірки `OpenSSL`, `CUDA`, `HDF5`) | Ні (залежить від системних бібліотек) | Так (повний контроль над пакетами дистрибутива) |
| **Швидкість створення** | 100–500 мс (симлінки) | 10–50 мс (кешовані колеса) | 5–30 с (розв'язання SAT-солвера + розпаковка) | Миттєво (створення папки) | 1–60 с (збірка шарів образу) |
| **Розмір на диску** | 10–50 КБ (без встановлених пакунків) | 10–50 КБ | 100–500 МБ (базовий рантайм) | 0 КБ | 50–500 МБ |
| **Статус стандарту** | Офіційний стандарт CPython (Python 3.3+) | Сторонній інструмент (PyPA) | Незалежна бінарна екосистема (NumFOCUS) | Відхилено (PEP 582 Rejected у 2023 році) | Стандарт інфраструктури (Open Container Initiative) |

## 2. venv: легковажний стандарт середовища

Модуль `venv` спирається на стандарт PEP 405 і є невіддільною частиною стандартної бібліотеки CPython. Його головна перевага — нульова ціна підтримки та гарантована наявність у будь-якому дистрибутиві Python (за винятком деяких пакунків Debian/Ubuntu, де його винесено в окремий пакет `python3-venv`).

`venv` не дублює файли стандартної бібліотеки та двійкові образи, обмежуючись створенням символічних посилань на системний інтерпретатор. Це робить створення нового середовища практично миттєвим. 

Проте `venv` обмежений поточною версією інтерпретатора: ви не можете створити оточення Python 3.11, викликавши модуль `venv` з-під Python 3.12. Крім того, `venv` повністю залежить від системних динамічних бібліотек: якщо скомпільоване C-розширення вимагає `libssl.so.1.1`, а в операційній системі встановлено `libssl.so.3`, модуль не зможе завантажитися.

## 3. virtualenv: швидкість та гнучкість поверх стандарту

Сучасний `virtualenv` версії 20.0+ побудований поверх тих самих принципів PEP 405, що й `venv`, проте оптимізований для автоматизації та інструментів тестування (наприклад, `tox` або `nox`).

Ключові відмінності від `venv`:
- **Пошук версій (Python Discovery):** утиліта сканує систему та вміє знаходити різні встановлені версії CPython та PyPy за аргументом `--python=3.10`.
- **Кешування коліс (Wheel Seeding):** замість повільної розпаковки `ensurepip`, `virtualenv` зберігає попередньо зібрані колеса `pip` та `wheel` у каталозі користувача, створюючи готове до роботи середовище в 5–10 разів швидше за стандартний `venv`.
- **Бінарні трампліни на Windows:** вирішує проблеми відсутності прав на створення символічних посилань без необхідності повного дублювання виконуваних файлів.

## 4. Conda: мультимовна ізоляція системного рівня

Conda (менеджер середовищ від Anaconda) підходить до ізоляції з протилежного боку. Це не просто менеджер пакунків Python, а повноцінний кросплатформний менеджер двійкових пакунків, призначений для scientific computing та data science.

Кожне середовище Conda є незалежним ізольованим кореневим каталогом (`sysroot`):
- Усередині середовища встановлюється власна версія двійкового файлу `python`, власний набір системних бібліотек (`OpenSSL`, `zlib`, `bzip2`), власний C/C++ компілятор та оптимізовані математичні бібліотеки (Intel MKL, OpenBLAS, CUDA Toolkit).
- Conda повністю ігнорує системні бібліотеки хостової ОС, уникаючи конфліктів ABI між пакетами Linux чи Windows.

Ціною такої ізоляції є значне споживання дискового простору (сотні мегабайтів на кожне середовище), складніший процес розв'язання залежностей через SAT-солвер та несумісність деяких системних викликів.

## 5. PEP 582 (__pypackages__): невдала спроба безвіртуальної ізоляції

У 2018–2023 роках активну дискусію викликав проєкт [PEP 582](https://peps.python.org/pep-0582/) («Python local packages directory»). Пропозиція намагалася перенести у світ Python модель, схожу на `node_modules` у JavaScript (Node.js):
- Замість створення віртуального середовища та маніпуляцій з `$PATH` інтерпретатор при запуску скрипта автоматично шукав каталог `__pypackages__/3.12/lib/` у поточному або батьківському каталозі та додавав його до `sys.path`.

У березні 2023 року керівна рада Python (Steering Council) **офіційно відхилила PEP 582** з кількох фундаментальних причин:
1. **Проблема вкладених підпроцесів:** якщо скрипт всередині проєкту викликає іншу утиліту з іншого каталогу, неявне підключення `__pypackages__` призводило до непередбачуваних збоїв імпорту або витоку несумісних залежностей.
2. **Консольні точки входу (Console Scripts):** скрипти на кшталт `pytest` чи `flake8` потребують точного шебангу для запуску. Без каталогу `bin/` операційна система не має стандартизованого механізму пошуку бінарників локальних утиліт.
3. **Фрагментація екосистеми:** поява двох паралельних стандартів (віртуальні середовища та локальні пакунки) розколола б інструменти аналізу коду, лінтери, IDE та засоби розгортання.

## 6. Контейнеризація та роль venv у виробничому середовищі

Поширена хибна думка стверджує, що всередині Docker-контейнера віртуальне середовище непотрібне, оскільки сам контейнер уже є ізольованим. На практиці створення `venv` всередині контейнера залишається найкращою інженерною практикою:

1. **Захист системного Python дистрибутива:** сучасні образи (наприклад, Debian 12 Bookworm або Ubuntu 24.04) вмикають обмеження [PEP 668](https://peps.python.org/pep-0668/) (`EXTERNALLY-MANAGED`), яке блокує прямий виклик `pip install` у системний каталог, щоб запобігти руйнуванню системного менеджера `apt`.
2. **Багатоетапні збірки (Multi-stage Builds):** у першому етапі Dockerfile у віртуальне середовище встановлюються пакунки, компілюються C-розширення з потрібними заголовними файлами `gcc` та `musl-dev`, а у фінальний мінімальний образ копіюється лише каталог `.venv` без важких інструментів компіляції:

```dockerfile
# Етап 1: Збірка залежностей
FROM python:3.12-slim AS builder
WORKDIR /app
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Етап 2: Фінальний образ
FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /opt/venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY . .
CMD ["python", "main.py"]
```

Такий підхід забезпечує мінімальний розмір результуючого образу, швидке розгортання та повну ізоляцію артефактів.
