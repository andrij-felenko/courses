# 📋 Специфікація pyvenv.cfg та API модуля venv

Формат файлу `pyvenv.cfg` та програмний інтерфейс стандартного модуля `venv` утворюють офіційний контракт ізоляції середовищ виконання CPython. Цей документ містить вичерпний опис конфігураційних ключів, низькорівневих інваріантів синтаксичного аналізатора CPython, сигнатур методів класу `venv.EnvBuilder` та механізмів створення спеціалізованих генераторів середовищ для інженерних пайплайнів.

## 1. Специфікація формату pyvenv.cfg

Конфігураційний файл `pyvenv.cfg` є фундаментальним маркером стандарту PEP 405. Це текстовий документ у кодуванні UTF-8, що складається з пар `ключ = значення`. На відміну від файлів конфігурації формату INI, файл `pyvenv.cfg` не містить заголовків секцій (квадратних дужок на кшталт `[general]`) і читається інтерпретатором лінійно зверху вниз.

Низькорівневий парсер CPython, реалізований у модулі `Modules/getpath.py` (а в C-коді до версії 3.11 — у `Modules/getpath.c`), має такі особливості обробки:
- **Пробільні символи:** пробіли та знаки табуляції ліворуч і праворуч від символу рівності `=` повністю ігноруються.
- **Коментарі:** рядки, що починаються з символу `#`, вважаються коментарями та пропускаються. Коментарі в кінці рядка після значення не підтримуються і зчитуються як частина значення.
- **Регістр ключів:** імена ключів обробляються у нижньому регістрі.

### Ключі конфігурації та їхній вплив на середовище виконання

Розглянемо кожен із параметрів, які інтерпретатор CPython або діагностичні утиліти вичитують із файлу:

1. **`home` (обов'язковий рядок шляху):**
   Визначає абсолютний або відносний шлях до каталогу, де розташовано оригінальний виконуваний бінарний файл базового інтерпретатора. Саме на основі цього параметра CPython обчислює `sys.base_prefix` та `sys.base_exec_prefix`. Якщо у `pyvenv.cfg` вказано `home = /usr/bin`, інтерпретатор автоматично визначає, що стандартна бібліотека розташована в `/usr/lib/python3.X`. Якщо цей параметр відсутній або вказує на неіснуючий каталог, CPython відхиляє файл як пошкоджений і переходить до системного пошуку орієнтирів.

2. **`include-system-site-packages` (необов'язковий булевий прапорець):**
   Керує тим, чи матиме ізольоване середовище доступ до глобальних пакетів операційної системи. Якщо значення дорівнює `true` (або `1`, `yes`), модуль `site.py` додає системний каталог `/usr/lib/python3/dist-packages` (чи аналогічний каталог базової інсталяції) до списку `sys.path` після локального каталогу середовища. За замовчуванням значення встановлюється в `false`, що гарантує повну ізоляцію від сторонніх системних пакетів.

3. **`version` (необов'язковий рядок версії):**
   Зберігає точну версію інтерпретатора, яка використовувалася під час генерації середовища (наприклад, `3.12.3`). Цей параметр не впливає на внутрішній розрахунок шляхів самого CPython, проте активно використовується менеджерами пакунків `pip`, `poetry` та інструментами аудиту для завчасного виявлення несумісності, коли середовище намагаються запустити іншим інтерпретатором.

4. **`executable` (необов'язковий абсолютний шлях):**
   Вказує прямий шлях до фізичного двійкового файлу CPython, використаного для створення віртуального оточення. Параметр дозволяє утилітам відрізнити базовий інтерпретатор від проміжних символічних посилань або системних обгорток (`pyenv`, `asdf`).

5. **`command` (необов'язковий рядок виклику CLI):**
   Містить точну команду командного рядка, за допомогою якої було ініціалізовано середовище (наприклад, `/usr/bin/python3 -m venv --without-pip .venv`). Використовується для аудиту, відтворюваності та регенерації оточення.

6. **`appdata_model` (специфічний параметр для Windows):**
   Використовується у спеціальних збірках Python, що постачаються через Microsoft Store. Прапорець визначає, чи повинен інтерпретатор ізолювати каталог налаштувань користувача `AppData/Local/Packages` для запобігання міжпроєктним колізіям.

### Інваріанти розташування pyvenv.cfg у файловій системі

Алгоритм пошуку конфігураційного файлу є суворо детермінованим. Під час старту процес інтерпретатора перевіряє рівно дві локації відносно каталогу бінарного образу `sys.executable`:
- **Локація 1 (каталог бінарника):** `dirname(sys.executable)/pyvenv.cfg`. Цей варіант характерний для компактних інсталяцій або специфічних розгорток у вбудованих системах.
- **Локація 2 (батьківський каталог префікса):** `dirname(dirname(sys.executable))/pyvenv.cfg`. Це стандартна структура віртуального середовища, де бінарник розташовано в `.venv/bin/python`, а конфігураційний файл — у корені `.venv/pyvenv.cfg`.

Якщо файл відсутній в обох локаціях, інтерпретатор вважає, що працює у стандартному глобальному режимі без ізоляції.

## 2. Високорівнева функція venv.create

Модуль `venv` надає функцію швидкого створення середовища для типових скриптів автоматизації:

```py
import venv

venv.create(
    env_dir,
    system_site_packages=False,
    clear=False,
    symlinks=False,
    with_pip=False,
    prompt=None,
    upgrade_deps=False,
    scm_ignore_files=frozenset(),
)
```

Функція приймає такі параметри:
- `env_dir`: шлях до каталогу цільового середовища (рядок або об'єкт `pathlib.Path`). Якщо каталог не існує, він створюється разом з усіма проміжними батьківськими каталогами.
- `system_site_packages`: логічний прапорець, що керує записом значення `include-system-site-packages` у згенерований `pyvenv.cfg`.
- `clear`: якщо встановлено у `True`, функція повністю очищає вміст каталогу `env_dir`, якщо він уже існував, запобігаючи накопиченню застарілих бібліотек.
- `symlinks`: на POSIX-системах за замовчуванням намагається створити символічні посилання на бінарний файл `python3`. Якщо значення `False` (або на Windows), бінарний інтерпретатор або копіюється, або замінюється трампліном.
- `with_pip`: якщо прапорець увімкнено, після генерації структури каталогів автоматично викликається внутрішній модуль `ensurepip`, який розгортає пакети `pip` та `setuptools` безпосередньо в ізольований каталог `site-packages`.
- `prompt`: текстовий префікс для запрошення термінала під час активації (наприклад, `(my-project)`). Якщо не вказано, використовується назва каталогу середовища.
- `upgrade_deps`: автоматично запускає оновлення встановленого `pip` до найновішої версії з індексу PyPI одразу після ініціалізації.
- `scm_ignore_files`: множина систем контролю версій (наприклад, `frozenset(["git"])`), для яких у корені середовища генеруються файли ігнорування (`.gitignore` із вмістом `*`).

## 3. Об'єктний каркас EnvBuilder та життєвий цикл генерації

Клас `venv.EnvBuilder` є базовим об'єктно-орієнтованим каркасом, який розбиває створення віртуального оточення на окремі дискретні фази. Це дозволяє розробникам системних утиліт перевизначати окремі етапи життєвого циклу або вбудовувати власну логіку ініціалізації.

### Послідовність викликів життєвого циклу

Метод `EnvBuilder.create(env_dir)` виконує сувору послідовність кроків:

1. **`clear_directory(env_dir)`:** видаляє наявний вміст цільового каталогу, якщо було передано прапорець `clear=True`.
2. **`ensure_directories(env_dir)`:** створює дерево каталогів (`bin`/`Scripts`, `include`, `lib/pythonX.Y/site-packages`) і повертає об'єкт контексту `context` (екземпляр `types.SimpleNamespace`), який містить усі обчислені шляхи.
3. **`create_configuration(context)`:** генерує та записує файл `pyvenv.cfg` на основі налаштувань білдера.
4. **`setup_python(context)`:** створює символічні посилання на інтерпретатор Python (або копіює виконувані файли) всередині каталогу `bin/` середовища.
5. **`setup_scripts(context)`:** копіює скрипти активації для різних командних оболонок (`activate`, `activate.csh`, `activate.fish`, `activate.ps1`, `activate.bat`) у каталог `bin/` або `Scripts/`, підставляючи розраховані значення назви середовища та шляхів.
6. **`post_setup(context)`:** спеціальний метод-хук, призначений для користувацької логіки розширення. У базовому класі цей метод викликає `ensurepip` (якщо `with_pip=True`).
7. **`upgrade_dependencies(context)`:** виконує підпроцес `python -m pip install --upgrade pip setuptools`, якщо активовано прапорець `upgrade_deps`.

### Структура об'єкта контексту (context)

Об'єкт `context`, який передається у всі методи життєвого циклу, містить вичерпний набір атрибутів:

- `context.env_dir` — абсолютний шлях до кореня створюваного віртуального середовища.
- `context.env_name` — ім'я середовища (за замовчуванням ім'я останнього сегмента шляху).
- `context.prompt` — відформатований рядок префікса командного рядка.
- `context.executable` — шлях до бінарного інтерпретатора всередині створеного середовища (`.venv/bin/python`).
- `context.env_exe` — базове ім'я виконуваного файлу (`python3` або `python.exe`).
- `context.bin_dir` — шлях до каталогу виконання (`.venv/bin` у POSIX або `.venv\Scripts` у Windows).
- `context.include_dir` — шлях до каталогу заголовних файлів (`.venv/include`).
- `context.lib_dir` — шлях до каталогу бібліотек (`.venv/lib/python3.X` у POSIX або `.venv\Lib` у Windows).
- `context.site_packages` — шлях до каталогу встановлення ізольованих пакунків.
- `context.bin_name` — ім'я каталогу бінарних файлів (`"bin"` або `"Scripts"`).

## 4. Створення кастомного будівельника середовищ

Завдяки архітектурі хуків розробник може створити спеціалізований клас білдера, який не лише генерує оточення, але й автоматично створює конфігураційні файли проєкту, встановлює внутрішні сертифікати безпеки та розгортає обов'язкові інструменти розробки:

```py
import os
import subprocess
import venv
from pathlib import Path

class CorporateEnvBuilder(venv.EnvBuilder):
    """Спеціалізований конструктор venv для корпоративної інфраструктури."""
    
    def __init__(self, dev_tools=None, extra_index_url=None, **kwargs):
        super().__init__(**kwargs)
        self.dev_tools = dev_tools or ["pytest", "ruff", "mypy"]
        self.extra_index_url = extra_index_url

    def post_setup(self, context):
        """Хук розширення, що виконується після базового створення середовища."""
        # 1. Автоматична генерація файлу .gitignore
        gitignore = Path(context.env_dir) / ".gitignore"
        if not gitignore.exists():
            gitignore.write_text("*\n", encoding="utf-8")

        # 2. Налаштування корпоративного індексу пакетів pip.conf всередині venv
        if self.extra_index_url:
            pip_conf_dir = Path(context.env_dir)
            pip_conf = pip_conf_dir / "pip.conf"
            pip_conf.write_text(
                f"[global]\nextra-index-url = {self.extra_index_url}\n",
                encoding="utf-8"
            )

        # 3. Автоматичне встановлення базових інструментів тестування
        if self.with_pip and self.dev_tools:
            cmd = [context.executable, "-m", "pip", "install", "--quiet"] + self.dev_tools
            subprocess.run(cmd, check=True)
            print(f"Успішно встановлено корпоративний набір утиліт: {', '.join(self.dev_tools)}")

if __name__ == "__main__":
    builder = CorporateEnvBuilder(
        with_pip=True,
        prompt="corp-backend",
        extra_index_url="https://pypi.internal.corp/simple",
        dev_tools=["fastapi", "pytest", "ruff"]
    )
    builder.create("./.backend_env")
```

Такий підхід забезпечує повну відтворюваність робочих оточень серед усіх членів команди розробки, гарантує єдині версії лінтерів та автоматизує інтеграцію з локальними репозиторіями артефактів.
