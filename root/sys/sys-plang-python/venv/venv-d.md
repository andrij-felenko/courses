Коли операційна система запускає інтерпретатор CPython за замовчуванням, процес зчитує бібліотеки з глобальних системних каталогів (`/usr/lib/python3.X/` та `/usr/lib/python3/dist-packages/` у Linux або `C:\Program Files\Python312\Lib\site-packages\` у Windows). Якщо адміністративний менеджер пакунків дистрибутива (наприклад, `apt`, `dnf` або `pacman`) використовує утиліти на Python, прив'язані до конкретної версії бібліотеки `urllib3 1.26.18`, а розроблюваний вебзастосунок вимагає `urllib3 >= 2.0.0`, встановлення нового пакунка в загальну систему призводить до взаємного руйнування залежностей. Спроба розгорнути на одному сервері два незалежні мережеві сервіси з різними версіями фреймворку `FastAPI` чи бібліотеки `pydantic` викликає прямий конфлікт файлів у спільному каталозі `site-packages`.

Стандарт [PEP 405](https://peps.python.org/pep-0405/) вирішує цю проблему без віртуалізації на рівні операційної системи та без фізичного дублювання сотень мегабайтів коду стандартної бібліотеки. Замість копіювання бінарних файлів інтерпретатора, динамічних бібліотек `libc`/`libpython` та модулів стандартної бібліотеки механізм віртуального середовища (`venv`) реалізує легковажне перенаправлення системних шляхів через маркерний файл `pyvenv.cfg`. Інтерпретатор виявляє цей файл під час низькорівневої ініціалізації, підміняє базовий префікс пошуку сторонніх пакунків (`sys.prefix`), проте продовжує прозоро використовувати модулі базової стандартної бібліотеки з незмінного системного каталогу (`sys.base_prefix`).

## 1. Анатомія каталогу venv та роль pyvenv.cfg

Фізично віртуальне середовище являє собою звичайне дерево каталогів у файловій системі користувача, створене за чітко визначеною структурою.

У POSIX-сумісних операційних системах (Linux, macOS, FreeBSD) каталог середовища містить три ключові підкаталоги та один конфігураційний файл:

```
.venv/
├── bin/
│   ├── activate
│   ├── activate.csh
│   ├── activate.fish
│   ├── pip
│   ├── python -> /usr/bin/python3.12 (символічне посилання)
│   └── python3 -> python (символічне посилання)
├── include/
├── lib/
│   └── python3.12/
│       └── site-packages/
│           ├── pip/
│           └── requests/
└── pyvenv.cfg
```

У середовищі Microsoft Windows структура адаптована під конвенції операційної системи:

```
.venv\
├── Include\
├── Lib\
│   └── site-packages\
├── Scripts\
│   ├── activate.bat
│   ├── Activate.ps1
│   ├── pip.exe
│   ├── python.exe (симлінк або бінарний трамплін)
│   └── pythonw.exe
└── pyvenv.cfg
```

![Анатомія каталогу віртуального середовища PEP 405 та зв'язок із системним інтерпретатором](/root/sys/sys-plang-python/venv/img/venv-directory-structure.svg)
*Структура каталогів віртуального середовища PEP 405: перенаправлення префікса через pyvenv.cfg та відображення стандартної бібліотеки з базової інсталяції.*

Кожен компонент цього дерева виконує строго визначену функцію:

1. **Каталог виконання (`bin/` або `Scripts/`):**
   Містить символічні посилання на бінарний файл базового інтерпретатора Python (`sys.executable`), скрипти активації сесії термінала для різних командних оболонок, а також виконувані консольні точки входу (Console Scripts) для встановлених сторонніх утиліт (наприклад, `pip`, `pytest`, `uvicorn`, `flake8`).

2. **Каталог заголовних файлів (`include/`):**
   Порожній або заповнений символічними посиланнями каталог для C/C++ заголовних файлів (`Python.h`). Коли менеджер пакунків компілює бінарне C-розширення з вихідного коду (`sdist`), компілятор шукає заголовки саме за шляхом `$VIRTUAL_ENV/include/`.

3. **Каталог ізольованих бібліотек (`lib/pythonX.Y/site-packages/` або `Lib\site-packages\`):**
   Єдине місце, куди встановлюються файли всіх сторонніх коліс (`wheel`) та бібліотек під час виконання команд `pip install` або `poetry add`. Модуль `site.py` під час запуску середовища автоматично реєструє цей каталог у системному списку імпорту `sys.path`.

4. **Файл конфігурації `pyvenv.cfg`:**
   Текстовий файл у кодуванні UTF-8, який містить декларативні параметри прив'язки середовища до базової системи:

```ini
home = /usr/bin
include-system-site-packages = false
version = 3.12.3
executable = /usr/bin/python3.12
command = /usr/bin/python3 -m venv /home/user/project/.venv
```

Ключ `home` є обов'язковим інваріантом: він вказує низькорівневому завантажувачу CPython каталог, у якому лежить справжній бінарний образ інтерпретатора та поруч із яким розташована стандартна бібліотека. Ключ `include-system-site-packages` визначає, чи будуть глобальні бібліотеки операційної системи видимі всередині віртуального середовища.

Повний довідник конфігураційних ключів `pyvenv.cfg`, параметрів класу `venv.EnvBuilder` та механізмів програмної генерації середовищ наведено у вставці [Специфікація pyvenv.cfg та API модуля venv](root:sys-plang-python/venv/api-pyvenv-cfg.md). Детальний аналіз передумов появи цього стандарту та відмови від ранніх інструментів підміни файлів стандартної бібліотеки винесено у вставку [Історія ізоляції середовищ у Python: від virtual-python до PEP 405](root:sys-plang-python/venv/hist-pep-405.md).

## 2. Виявлення venv під час старту інтерпретатора: розрахунок sys.prefix та sys.base_prefix

Ініціалізація віртуального середовища відбувається не у високорівневому коді Python, а на найбільш ранньому етапі завантаження CPython під час обчислення конфігурації шляхів (`_PyPathConfig_Calculate` у C-коді ядра або `Modules/getpath.py`, починаючи з Python 3.11).

Коли користувач або скрипт викликає двійковий файл `.venv/bin/python3`, операційна система здійснює системний виклик `execve` і передає керування точці входу інтерпретатора. До завантаження будь-якого байткоду CPython виконує детермінований алгоритм пошуку орієнтирів (Landmark Search):

```
execve(".venv/bin/python3")
  │
  ├── 1. Обчислення абсолютного шляху до бінарника: sys.executable
  │
  ├── 2. Пошук pyvenv.cfg:
  │      • Перевірка dirname(sys.executable)       → .venv/bin/pyvenv.cfg
  │      • Перевірка dirname(dirname(sys.executable)) → .venv/pyvenv.cfg
  │
  ├── 3. Якщо pyvenv.cfg ЗНАЙДЕНО:
  │      • Зчитування ключа "home" (наприклад, /usr/bin)
  │      • sys.prefix = .venv (каталог середовища)
  │      • sys.exec_prefix = .venv
  │      • sys.base_prefix = /usr (батьківський каталог для home)
  │      • sys.base_exec_prefix = /usr
  │      • Стандартна бібліотека os.py завантажується з sys.base_prefix/lib/python3.X
  │
  └── 4. Якщо pyvenv.cfg ВІДСУТНІЙ:
         • sys.prefix = /usr
         • sys.base_prefix = /usr
```

![Покроковий алгоритм виявлення pyvenv.cfg та формування системних префіксів під час старту CPython](/root/sys/sys-plang-python/venv/img/startup-prefix-resolution.svg)
*Послідовність перевірок орієнтирів та підміни префіксів під час низькорівневої ініціалізації CPython.*

У коді Python різниця між префіксами стає доступною через модуль `sys`:

- `sys.prefix` — кореневий каталог поточного активного середовища виконання, відносно якого шукаються сторонні модулі та локальні бібліотеки `site-packages`.
- `sys.exec_prefix` — каталог для платформозалежних файлів та скомпільованих динамічних бібліотек (`.so`/`.pyd`).
- `sys.base_prefix` — вихідний каталог первинної інсталяції Python, з якого імпортується стандартна бібліотека (`json`, `http`, `sqlite3`, `ctypes`).
- `sys.base_exec_prefix` — базовий каталог системних C-розширень стандартної бібліотеки (`lib-dynload`).

Якщо інтерпретатор запущено без віртуального середовища (глобально), змінні `sys.prefix` та `sys.base_prefix` мають однакове значення:

```
sys.prefix == sys.base_prefix == "/usr"
```

Якщо ж інтерпретатор запущено всередині `venv`, рівність порушується:

```
sys.prefix      == "/home/user/project/.venv"
sys.base_prefix == "/usr"
```

Ця проста перевірка є стандартним і найнадійнішим способом програмного визначення того, чи виконується код у віртуальному середовищі:

```py
import sys

def in_virtualenv() -> bool:
    """Перевіряє, чи виконується процес у віртуальному середовищі PEP 405."""
    return sys.prefix != getattr(sys, "base_prefix", sys.prefix)
```

## 3. Робота модуля site.py, include-system-site-packages та обробка .pth файлів

Після завершення низькорівневого розрахунку префіксів ядро CPython ініціалізує середовище виконання та автоматично імпортує системний модуль `site.py` (якщо під час запуску не було передано прапорець повної ізоляції `-S`).

Функція `site.main()` відповідає за наповнення списку каталогів пошуку `sys.path`. Її робота у віртуальному середовищі підпорядковується таким правилам:

1. **Додавання локального каталогу середовища:**
   Модуль `site` бере значення `sys.prefix` (`/home/user/project/.venv`) і генерує шлях до локального каталогу сторонніх пакунків:
   `/home/user/project/.venv/lib/python3.12/site-packages`.
   Цей шлях додається на початок списку `sys.path` (після каталогу поточного скрипту).

2. **Обробка прапорця `include-system-site-packages`:**
   Модуль зчитує значення параметра з файлу `pyvenv.cfg`:
   - Якщо параметр дорівнює `false` (значення за замовчуванням), системні каталоги `/usr/lib/python3/dist-packages` або `/usr/local/lib/python3.12/site-packages` взагалі **не додаються** до `sys.path`. Сторонні бібліотеки, встановлені на рівні ОС, стають повністю невидимими для проєкту.
   - Якщо параметр дорівнює `true`, системні каталоги додаються в кінець списку `sys.path`. Інтерпретатор спершу шукає модуль у локальному `.venv`, і лише якщо його там немає, звертається до системного пакетного сховища.

3. **Сканування файлів конфігурації шляхів (`.pth`):**
   Усередині каталогу `site-packages` віртуального середовища модуль `site` сканує всі файли з розширенням `.pth`. Кожен рядок такого файлу або інтерпретується як додатковий каталог, що додається до `sys.path`, або виконується як код Python, якщо рядок починається з ключового слова `import `.

Простежимо реальний стан `sys.path` усередині активованого віртуального середовища:

```py
import sys
import site

print(f"sys.prefix:      {sys.prefix}")
print(f"sys.base_prefix: {sys.base_prefix}")
print("\nКаталоги пошуку sys.path:")
for idx, path in enumerate(sys.path):
    print(f"  [{idx}] {path}")

print("\nЗареєстровані каталоги site-packages:")
for sp in site.getsitepackages():
    print(f"  • {sp}")
```

Результат виклику у Linux-середовищі:

```
sys.prefix:      /home/user/project/.venv
sys.base_prefix: /usr

Каталоги пошуку sys.path:
  [0] /home/user/project
  [1] /usr/lib/python312.zip
  [2] /usr/lib/python3.12
  [3] /usr/lib/python3.12/lib-dynload
  [4] /home/user/project/.venv/lib/python3.12/site-packages

Зареєстровані каталоги site-packages:
  • /home/user/project/.venv/lib/python3.12/site-packages
```

Елементи `[1]`, `[2]` та `[3]` беруться з базового префікса `sys.base_prefix` (`/usr`), забезпечуючи доступ до стандартних модулів `os`, `sys`, `math` та скомпільованих бінарників `lib-dynload/_ssl.so`. Елемент `[4]` вказує на ізольований каталог проєкту. Жоден системний пакунок із `/usr/lib/python3/dist-packages` до списку не потрапив.

## 4. Механіка скриптів активації: змінна PATH, шебанг і прямий виклик

Найбільш поширеною хибною думкою щодо віртуальних середовищ є переконання, що середовище необхідно обов'язково «активувати» командою `source .venv/bin/activate` перед будь-яким запуском. З точки зору ядра CPython активація не має жодного відношення до ізоляції імпортів.

### Що насправді робить скрипт `activate`

Скрипт `activate` — це простий текстовий сценарій для командної оболонки (Shell), який виконує рівно чотири дії в поточному процесі сесії термінала:

1. **Модифікує змінну середовища `$PATH`:**
   Додає абсолютний шлях до каталогу `.venv/bin` на самий початок системного списку пошуку виконуваних файлів:
   `PATH="/home/user/project/.venv/bin:$PATH"`.
   Завдяки цьому введення короткої команди `python` або `pip` змушує командну оболонку викликати саме `.venv/bin/python`, а не глобальний `/usr/bin/python`.
2. **Встановлює змінну `$VIRTUAL_ENV`:**
   Експортує змінну середовища `VIRTUAL_ENV="/home/user/project/.venv"`, яку використовують зовнішні інструменти (лінтери в IDE, генератори документації, утиліти розгортання) для ідентифікації поточного активного оточення.
3. **Змінює рядок запрошення термінала (`$PS1`):**
   Додає префікс середовища до командного рядка користувача, наприклад `(.venv) user@host:~$ `.
4. **Створює функцію `deactivate`:**
   Оголошує в пам'яті поточної оболонки функцію для відновлення початкового значення змінних `$PATH` та `$PS1`.

![Механіка виклику інтерпретатора: порівняння прямого запуску та модифікації змінної оточення PATH через activate](/root/sys/sys-plang-python/venv/img/activation-path-flow.svg)
*Порівняння шляхів виклику: прямий виклик інтерпретатора середовища проти модифікації змінної оточення PATH через скрипт активації.*

### Чому прямий виклик надійніший за активацію

Оскільки пошук `pyvenv.cfg` здійснюється інтерпретатором відносно шляху власного виконуваного файлу (`sys.executable`), прямий виклик двійкового файлу за абсолютним або відносним шляхом працює зі 100% збереженням повної ізоляції:

```bash
$ /home/user/project/.venv/bin/python main.py
```

Під час такого виклику CPython знаходить `pyvenv.cfg` у батьківському каталозі, налаштовує `sys.prefix` і завантажує пакети з `.venv/lib/site-packages`, навіть якщо в терміналі не виконувалася команда `source activate`, а змінна `$PATH` вказує на системні каталоги.

Прямий запуск є стандартом де-факто для автоматизації:
- **У планувальниках задач (Cron, Systemd таймери):**
  Запис `/home/user/app/.venv/bin/python /home/user/app/worker.py` гарантує запуск потрібного середовища без залежності від оточення оболонки.
- **У юнітах служб Systemd:**
  Директива `ExecStart=/opt/myapp/.venv/bin/uvicorn app.main:app --port 8000` надійно стартує вебсервер з ізольованими залежностями.
- **У CI/CD пайплайнах (GitHub Actions, GitLab CI):**
  Виклик `.venv/bin/pytest tests/` запускає тести без попередніх маніпуляцій з оболонкою.

### Роль шебангу в консольних утилітах

Коли `pip` встановлює бібліотеку, що містить консольні команди (наприклад, `pytest`, `black`, `uvicorn`), він автоматично генерує виконуваний скрипт у каталозі `.venv/bin/`. Перший рядок цього скрипту (шебанг, Shebang) містить прямий абсолютний шлях до інтерпретатора цього ж віртуального середовища:

```python
#!/home/user/project/.venv/bin/python3
# -*- coding: utf-8 -*-
import re
import sys
from pytest import console_main
if __name__ == "__main__":
    sys.argv[0] = re.sub(r"(-script\.pyw|\.exe)?$", "", sys.argv[0])
    sys.exit(console_main())
```

Коли ядро операційної системи виконує файл `.venv/bin/pytest`, воно читає шебанг і автоматично запускає саме `.venv/bin/python3`, що гарантує виконання утиліти в ізольованому середовищі без попередньої активації.

Практичний покроковий приклад створення власного повноцінного віртуального середовища за стандартом PEP 405 із генерацією скриптів активації та валідацією шебангів на чистому Python наведено у вставці [Створення віртуального середовища без модуля venv](root:sys-plang-python/venv/proj-minimal-venv.md).

## 5. C/C++ API: низькорівнева перевірка ізоляції та робота з PyConfig

Під час вбудовування CPython у сторонні застосунки на C або C++ (наприклад, у рушії баз даних, ігрові рушії або системні демони) коректне налаштування віртуального середовища вимагає прямої взаємодії з C API інтерпретатора.

Починаючи з Python 3.8, конфігурація середовища здійснюється через стандартизовану структуру `PyConfig` ([PEP 587](https://peps.python.org/pep-0587/)).

Нижче наведено приклади ініціалізації інтерпретатора CPython мовами C та C++ з явним заданням шляху до віртуального середовища та наступною перевіркою коректності розрахунку `sys.prefix` і `sys.base_prefix`.

:::tabs
```c
#define PY_SSIZE_T_CLEAN
#include <Python.h>
#include <stdio.h>
#include <stdlib.h>

/* Ініціалізація CPython з явним підключенням venv через PyConfig */
int run_embedded_venv(const wchar_t *venv_path) {
    PyStatus status;
    PyConfig config;
    PyConfig_InitPythonConfig(&config);

    /* Задаємо ізольований префікс середовища */
    status = PyConfig_SetString(&config, &config.prefix, venv_path);
    if (PyStatus_Exception(status)) {
        PyConfig_Clear(&config);
        return 1;
    }

    /* Дозволяємо виконання site.py для сканування site-packages */
    config.site_import = 1;

    /* Ініціалізуємо середовище CPython */
    status = Py_InitializeFromConfig(&config);
    PyConfig_Clear(&config);
    if (PyStatus_Exception(status)) {
        return 2;
    }

    /* Інтроспекція сформованих шляхів через модуль sys */
    PyObject *sys_mod = PyImport_ImportModule("sys");
    if (!sys_mod) {
        PyErr_Print();
        Py_FinalizeEx();
        return 3;
    }

    PyObject *prefix = PyObject_GetAttrString(sys_mod, "prefix");
    PyObject *base_prefix = PyObject_GetAttrString(sys_mod, "base_prefix");

    if (prefix && base_prefix) {
        PyObject *p_str = PyObject_Str(prefix);
        PyObject *bp_str = PyObject_Str(base_prefix);
        printf("C Runtime: sys.prefix      = %s\n", PyUnicode_AsUTF8(p_str));
        printf("C Runtime: sys.base_prefix = %s\n", PyUnicode_AsUTF8(bp_str));
        Py_XDECREF(p_str);
        Py_XDECREF(bp_str);
    }

    Py_XDECREF(prefix);
    Py_XDECREF(base_prefix);
    Py_DECREF(sys_mod);

    Py_FinalizeEx();
    return 0;
}

int main(void) {
    const wchar_t *env = L"/home/user/project/.venv";
    return run_embedded_venv(env);
}
```

```cpp
#define PY_SSIZE_T_CLEAN
#include <Python.h>
#include <iostream>
#include <string_view>
#include <memory>
#include <stdexcept>

/* RAII-обгортка над життєвим циклом вбудованого інтерпретатора CPython */
class PythonRuntime {
public:
    explicit PythonRuntime(std::wstring_view venv_path) {
        PyConfig config;
        PyConfig_InitPythonConfig(&config);

        PyStatus status = PyConfig_SetString(&config, &config.prefix, venv_path.data());
        if (PyStatus_Exception(status)) {
            PyConfig_Clear(&config);
            throw std::runtime_error("Не вдалося встановити prefix для PyConfig");
        }

        config.site_import = 1;

        status = Py_InitializeFromConfig(&config);
        PyConfig_Clear(&config);
        if (PyStatus_Exception(status)) {
            throw std::runtime_error("Помилка ініціалізації CPython із PyConfig");
        }
    }

    ~PythonRuntime() {
        if (Py_IsInitialized()) {
            Py_FinalizeEx();
        }
    }

    PythonRuntime(const PythonRuntime&) = delete;
    PythonRuntime& operator=(const PythonRuntime&) = delete;

    void inspect_prefixes() const {
        PyObject* sys_mod = PyImport_ImportModule("sys");
        if (!sys_mod) {
            PyErr_Print();
            throw std::runtime_error("Не вдалося імпортувати модуль sys");
        }

        auto py_decref = [](PyObject* obj) { Py_XDECREF(obj); };
        std::unique_ptr<PyObject, decltype(py_decref)> sys_guard(sys_mod, py_decref);

        PyObject* prefix = PyObject_GetAttrString(sys_mod, "prefix");
        PyObject* base_prefix = PyObject_GetAttrString(sys_mod, "base_prefix");
        std::unique_ptr<PyObject, decltype(py_decref)> pref_guard(prefix, py_decref);
        std::unique_ptr<PyObject, decltype(py_decref)> base_guard(base_prefix, py_decref);

        if (prefix && base_prefix) {
            std::cout << "C++ Runtime: sys.prefix      = " << PyUnicode_AsUTF8(prefix) << "\n";
            std::cout << "C++ Runtime: sys.base_prefix = " << PyUnicode_AsUTF8(base_prefix) << "\n";
        }
    }
};

int main() {
    try {
        PythonRuntime runtime(L"/home/user/project/.venv");
        runtime.inspect_prefixes();
    } catch (const std::exception& ex) {
        std::cerr << "Помилка виконання: " << ex.what() << "\n";
        return 1;
    }
    return 0;
}
```

## 6. Порівняння архітектурних моделей ізоляції

Екосистема Python використовує кілька альтернативних підходів до ізоляції середовищ. Кожен підхід вирішує ізоляцію на різній глибині системного стека:

1. **`venv` (PEP 405):**
   Вбудоване рішення стандартної бібліотеки CPython. Забезпечує легковажну ізоляцію сторонніх модулів на рівні перенаправлення системних префіксів `sys.prefix` через символічні посилання. Повністю залежить від версії CPython, з якої було створене, та системних динамічних C-бібліотек хостової ОС.

2. **`virtualenv`:**
   Сторонній інструмент, який розвивається у межах PyPA (Python Packaging Authority). Сучасні версії `virtualenv` (20.0+) використовують той самий механізм `pyvenv.cfg`, але додають глобальний кеш розпакованих коліс `pip`/`setuptools` (Wheel Seeding), підтримують автоматичний пошук різних встановлених версій Python (Discovery) та створюють бінарні трампліни на платформах без повноцінних символічних посилань.

3. **`Conda` (Anaconda / Miniconda):**
   Кросплатформний бінарний менеджер пакунків та середовищ. На відміну від `venv`, Conda ізолює не лише Python-пакунки, але й двійковий образ інтерпретатора, компілятори, C/C++ бібліотеки (CUDA, OpenBLAS, OpenSSL, HDF5) та системний рантайм. Кожне середовище Conda є повноцінним ізольованим каталогом `sysroot`.

4. **PEP 582 (`__pypackages__`):**
   Пропозиція щодо автоматичного підключення локального каталогу `__pypackages__` у `sys.path` без створення окремих віртуальних середовищ (за аналогією з `node_modules` у Node.js). Проєкт було **офіційно відхилено керівною радою Python у 2023 році** через невирішені проблеми з шебангами консольних утиліт та витоками контексту у вкладених підпроцесах.

Детальний порівняльний аналіз, таблицю характеристик споживання пам'яті, швидкості створення та правила використання `venv` всередині контейнерів Docker наведено у вставці [Моделі ізоляції оточень: venv, virtualenv, conda та PEP 582](root:sys-plang-python/venv/comp-isolation-models.md).

## 7. Підводні камені: витік змінних середовища та вкладені підпроцеси

Незважаючи на простоту архітектури PEP 405, під час експлуатації віртуальних середовищ виникає низка типових інженерних проблем:

### 1. Витік змінних PYTHONPATH та PYTHONHOME

Віртуальне середовище ізолює шляхи `sys.prefix`, проте інтерпретатор CPython за замовчуванням продовжує зчитувати системні змінні оточення:

- Якщо в сесії термінала або системному профілі встановлено змінну `PYTHONPATH`, інтерпретатор всередині `.venv` додасть зазначені в ній каталоги на початок `sys.path`. Це призводить до імпорту несумісних модулів з іншого проєкту або глобальної системи.
- Якщо встановлено змінну `PYTHONHOME`, CPython спробує використати її замість параметра `home` із `pyvenv.cfg`, що повністю ламає розрахунок префіксів і викликає аварійну зупинку `Fatal Python error: init_fs_encoding: failed to get the Python codec of the filesystem encoding`.

Для гарантованого захисту від витоку змінних оточення у виробничих скриптах інтерпретатор запускають з прапорцем повної ізоляції параметрів середовища `-E` (ігнорувати змінні `PYTHON*`) або `-I` (режим повної ізоляції):

```bash
$ /home/user/project/.venv/bin/python -E script.py
```

### 2. Запуск дочірніх підпроцесів (Subprocesses)

Поширеною помилкою у скриптах автоматизації є виклик підпроцесів за загальним іменем команди:

```py
# НЕПРАВИЛЬНО: викликає той python, який першим знайдено в системному $PATH
import subprocess
subprocess.run(["python", "worker.py"])
```

Якщо скрипт запущено прямим викликом `.venv/bin/python` без попереднього `source activate`, змінна `$PATH` містить системні шляхи, і виклик `subprocess.run(["python", ...])` запустить системний `/usr/bin/python` замість середовища проєкту.

Правильний підхід полягає у явному посиланні на поточний активний інтерпретатор через `sys.executable`:

```py
# ПРАВИЛЬНО: гарантовано викликає той самий інтерпретатор venv
import sys
import subprocess
subprocess.run([sys.executable, "worker.py"])
```

### 3. Руйнування символічних посилань під час оновлення ОС

Оскільки `.venv/bin/python3` є символічним посиланням на конкретний бінарний файл базової системи (наприклад, `/usr/bin/python3.12`), оновлення операційної системи може змінити версію базового інтерпретатора на Python 3.13 або перемістити файли. У такому разі символічне посилання стає «висячим» (Dangling Symlink), а спроба запуску повертає системну помилку `No such file or directory`. 

Віртуальні середовища є одноразовими розхідними артефактами (Ephemeral Artifacts). Замість спроб вручну полагодити зламані посилання середовище видаляють і миттєво регенерують зі списку зафіксованих залежностей (`requirements.txt` або `poetry.lock`).

### 4. Непереносність між машинами та шляхами

Каталог віртуального середовища категорично заборонено переміщувати у файловій системі, копіювати на інший комп'ютер або додавати до репозиторію Git:
1. Файл `pyvenv.cfg` містить жорсткий шлях до базового каталогу `home`.
2. Усі консольні скрипти у каталозі `bin/` містять абсолютний шлях до інтерпретатора у своєму шебангу.
3. Скомпільовані бінарні колеса C-розширень жорстко лінкуються з версіями системних бібліотек (`glibc.so`, `libssl.so`) конкретного хоста.

Каталог `.venv` має обов'язково бути внесений до файлу `.gitignore`.

## 8. Термінологія

Нижче наведено етимологію ключових понять, що визначають архітектуру ізоляції середовищ:

- **Віртуальне середовище** (*Virtual environment*) — від лат. *virtualis* (потенційний, дієвий, уявний; від *virtus* — сила, здатність) та лат. *ambiens* (те, що охоплює навколо; від *ambire* — обходити кругом). Вказує на логічно відокремлений простір каталогів, який імітує самостійну інсталяцію системи без фізичного дублювання її компонентів.
- **Префікс** (*Prefix*) — від лат. *praefixus* (закріплений попереду; від *prae-* — попереду + *figere* — прикріплювати). Базовий кореневий каталог у файловій системі Unix-подібних систем, від якого відраховуються стандартні шляхи розміщення програмних ресурсів (`/bin`, `/lib`, `/include`).
- **Символічне посилання** (*Symlink / Symbolic link*) — від грец. *σύμβολον* (знак, прикмета, умовний сигнал) та давньоангл. *hlince* (ланка ланцюга, з'єднання). Спеціальний тип файлу файлової системи, що містить текстовий шлях до іншого цільового файлу або каталогу.
- **Орієнтир** (*Landmark*) — від фр. *orienter* (орієнтувати, визначати положення; від лат. *oriens* — схід сонця) та давньоангл. *landmearc* (межовий камінь, знак на землі). Характерний маркерний файл або каталог, за наявністю якого завантажувач автоматично визначає тип середовища та конфігурацію шляхів.
- **Шебанг** (*Shebang / Hashbang*) — від амер. сленг. комбінації символів *sharp* (`#`) та *bang* (`!`). Перший рядок текстового скрипту в POSIX-системах, що вказує завантажувачу ядра операційної системи точний шлях до програми-інтерпретатора.
- **Трамплін** (*Trampoline*) — від італ. *trampolo* (ходулі, опора) та нім. *trampeln* (тупотіти, переступати). Компактний двійковий виконуваний файл-посередник, єдиним завданням якого є миттєве перенаправлення виклику та аргументів на цільовий бінарний образ.

> 🔧 **Навіщо це.**
>
> Віртуальні середовища PEP 405 усувають проблему «пекла залежностей» (Dependency Hell), розділяючи глобальні системні утиліти операційної системи та прикладні бібліотеки проєктів.
> 
> У виробничій інженерії `venv` дозволяє створювати легковажні ізольовані контейнери, розгортати мікросервіси з взаємно несумісними версіями бібліотек на одному хості та забезпечувати строгу детермінованість збірок. Завдяки розумінню того, що ізоляція тримається на підміні `sys.prefix` через `pyvenv.cfg`, інженер може надійно налаштовувати CI/CD конвеєри, утиліти моніторингу та сервіси Systemd через прямий виклик `/path/to/venv/bin/python`, повністю позбавляючись крихких маніпуляцій зі змінними командної оболонки.
