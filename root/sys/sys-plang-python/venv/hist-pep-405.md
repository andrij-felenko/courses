# 📜 Історія ізоляції середовищ у Python: від virtual-python до PEP 405

Ізоляція середовищ виконання в екосистемі Python пройшла шлях від кустарних скриптів копіювання бінарних файлів на початку 2000-х років до стандартизованого протоколу рівня ядра інтерпретатора. Розуміння цієї еволюції пояснює, чому сучасний механізм `venv` спирається на мінімальний файл `pyvenv.cfg`, чому ранні інструменти ламалися під час кожного оновлення операційної системи та чому утиліта `virtualenv` продовжує існувати поруч зі стандартним модулем інтерпретатора.

## 1. Епоха системного хаосу та поява virtual-python

На початку 2000-х років стандартний спосіб поширення бібліотек у Python базувався на модулі `distutils` та команді `python setup.py install`. Ця команда копіювала файли безпосередньо у системний каталог `site-packages` інтерпретатора (зазвичай `/usr/lib/python2.X/site-packages` у Unix-подібних системах або `/usr/local/lib/`).

Такий підхід породжував три критичні проблеми:
1. **Потреба у правах суперкористувача (`root`):** звичайний розробник без адміністративного доступу не міг встановити жодної сторонньої бібліотеки на спільних серверах або університетських кластерах.
2. **Конфлікт версій:** якщо застосунок `A` потребував бібліотеки `docutils 0.3`, а застосунок `B` вимагав `docutils 0.4`, їхнє одночасне розгортання на одній машині ставало неможливим, оскільки в системному каталозі міг існувати лише один модуль із назвою `docutils.py` чи однойменний каталог.
3. **Руйнування системних утиліт:** встановлення оновленої версії базової бібліотеки (наприклад, `pycurl` чи `rpm-python`) ламало системні менеджери пакунків операційної системи (`yum`, `apt`), які залежали від конкретного ABI системного Python.

Першу спробу вирішити цю проблему здійснив Джеймс Ґарднер (James Gardner) у 2006 році, створивши скрипт `virtual-python.py`. Ідея Ґарднера полягала у створенні користувацького дерева каталогів, куди за допомогою символічних посилань копіювався системний виконуваний файл `python`, а також створювався локальний каталог `lib/python2.X/site-packages/`.

Скрипт перенаправляв пошук модулів шляхом модифікації бінарного образу інтерпретатора або використання змінної середовища `PYTHONPATH`. Проте таке рішення було надзвичайно крихким: воно не забезпечувало повної ізоляції, ламалося при роботі з C-розширеннями та вимагало ручного налаштування змінних оточення перед кожним викликом.

## 2. Революція virtualenv та модифікація site.py

У 2007 році Ієн Бікінґ (Ian Bicking), відомий автор фреймворків Paste та SQLObject, представив інструмент `virtualenv`. Замість ненадійних маніпуляцій зі змінними середовища Бікінґ застосував глибокий хак механізму ініціалізації CPython.

Під час старту стандартний інтерпретатор CPython завжди імпортує модуль `site.py` для налаштування шляхів пошуку модулів `sys.path`. `virtualenv` використовував цю особливість:
- У цільовому каталозі середовища створювалася копія (або символічне посилання) бінарного файлу `python`.
- Поруч із бінарником розгорталася власна версія файлу `site.py`, яка заміщала системний модуль стандартної бібліотеки.
- Цей модифікований `site.py` під час імпорту видаляв системні каталоги `site-packages` зі списку `sys.path` і додавав замість них локальний каталог середовища.

Цей трюк забезпечив справжню локальну ізоляцію. Розробники отримали змогу створювати незалежні середовища під кожен проєкт командою `virtualenv myenv`, встановлювати туди пакунки через `easy_install` (а згодом `pip`) і фіксувати списки залежностей.

Проте підміна `site.py` мала серйозні технічні вади:
- **Крихкість при оновленні версії Python:** якщо системний CPython оновлювався (наприклад, з 2.7.2 до 2.7.3), модифікований `site.py` всередині старого середовища міг містити застарілий код ініціалізації, що призводило до раптових аварійних зупинок (Segmentation Fault) або відмов імпорту.
- **Проблеми з бінарними C-розширеннями:** спільні бібліотеки (`.so` та `.dll`) часто не знаходили потрібних символів, оскільки інтерпретатор плутав системні та локальні шляхи заголовних файлів.
- **Складність підтримки Windows:** у Windows символічні посилання тривалий час були недоступні без адміністративних привілеїв, тому `virtualenv` був змушений фізично копіювати двійкові файли `python.exe` та допоміжні DLL-бібліотеки, що займало зайве місце на диску й порушувало цифрові підписи бінарників.

## 3. Карл Меєр і народження PEP 405

До початку 2010-х років віртуальні середовища стали фактичним стандартом розробки на Python, проте залишалися стороннім стороннім хаком над інтерпретатором. У 2011 році розробник Карл Меєр (Carl Meyer) запропонував кардинальне архітектурне рішення: перенести логіку виявлення віртуального оточення безпосередньо в низькорівневе ядро CPython.

У жовтні 2011 року було опубліковано [PEP 405](https://peps.python.org/pep-0405/) («Python Virtual Environments»). Головна ідея Меєра полягала у відмові від підміни `site.py` на користь протоколу конфігураційних маркерів:
1. Замість копіювання інтерпретатора створюється легковажне символічне посилання на системний бінарник `python3`.
2. Поруч із бінарником або в його батьківському каталозі розміщується маркерний файл `pyvenv.cfg`.
3. Під час запуску інтерпретатора алгоритм розрахунку шляхів (`getpath.c` у CPython) до завантаження будь-яких модулів Python шукає файл `pyvenv.cfg`.
4. Якщо файл знайдено, ядро CPython автоматично спрямовує `sys.prefix` на каталог середовища, а базову стандартну бібліотеку продовжує завантажувати з системного каталогу, вказаного у параметрі `home`.

PEP 405 було прийнято й реалізовано у релізі **Python 3.3** у вересні 2012 року у вигляді стандартного модуля `venv` та консольної утиліти `pyvenv` (пізніше заміненої на стандартний виклик `python3 -m venv`).

## 4. Чому virtualenv не зник після появи venv

Незважаючи на включення модуля `venv` до стандартної бібліотеки, утиліта `virtualenv` продовжує активно розвиватися і залишається популярною в індустрії. У 2020 році Бернат Ґабор (Bernát Gábor) повністю переписав кодову базу `virtualenv` (версія 20.0+), перевівши її на механізми PEP 405, але додавши низку критичних оптимізацій:

- **Підтримка багатьох версій Python (Discovery):** `virtualenv` вміє самостійно знаходити встановлені в системі різні версії CPython, PyPy та альтернативні реалізації, тоді як модуль `venv` може створити оточення лише для тієї поточної версії, якою його викликано.
- **Вбудоване кешування коліс (Seeder Wheels):** стандартний `venv` з прапорцем `--with-pip` змушений розпаковувати колеса `pip` та `setuptools` із вбудованого модуля `ensurepip`, що вимагає часу. `virtualenv` використовує оптимізований механізм попередньо закешованих коліс (Wheel Cache), створюючи оточення за мілісекунди.
- **Символічні копії та жорсткі посилання:** на платформах, де симлінки обмежені або небажані, сучасний `virtualenv` створює оптимізовані двійкові трампліни (Binary Trampolines), запобігаючи дублюванню важких файлів.
- **Підтримка старих версій:** тривалий час `virtualenv` залишався єдиним способом створити ізольоване середовище для проєктів на Python 2.7, де модуля `venv` не існувало.

Сьогодні стандартний модуль `venv` є фундаментальним низькорівневим фундаментом середовища Python, на який опираються всі сучасні менеджери пакунків та інструменти автоматизації — від `pipenv` і `poetry` до надшвидкого менеджера `uv`.
