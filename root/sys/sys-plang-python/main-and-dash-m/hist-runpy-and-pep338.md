# 📜 Історія PEP 338, PEP 366 та еволюція прапорця -m

Прапорець командного рядка `-m` та внутрішній модуль `runpy` з'явилися для розв'язання фундаментальної суперечності архітектури CPython: виконуваний скрипт і бібліотечний модуль вимагали діаметрально протилежних умов ініціалізації простору імен. До появи цих стандартів запуск файлу, схованого всередині ієрархії пакунків, або ламав пошук сусідніх модулів через спотворення `sys.path`, або вимагав написання зовнішніх скриптів-обгорток для кожного окремого інструмента.

## 1. Проблема запуску модулів у ранньому Python (1990-ті — 2004)

У перших версіях Python єдиним способом запустити код із командного рядка була пряма передача шляху до файлу в системний виклик операційної системи: `python path/to/script.py`. Інтерпретатор витягував каталог переданого файлу (`path/to/`) і розміщував його на нульовій позиції системного списку пошуку `sys.path[0]`.

Така поведінка була простою, але виявлялася безпорадною в трьох поширених системних сценаріях:
1. **Запуск утиліт зі стандартної бібліотеки:** щоб запустити вбудований профайлер `profile` або модуль тестування `unittest`, розробник мусив знати точний абсолютний шлях до каталогу встановлення стандартної бібліотеки в операційній системі (наприклад, `/usr/lib/python2.3/profile.py`), що руйнувало переносимість команд між платформами.
2. **Пакети як інструменти:** якщо модуль лежав усередині простору імен пакунка `mypackage.tools.cleanup`, прямий виклик `python mypackage/tools/cleanup.py` додавав у `sys.path[0]` каталог `mypackage/tools/`. У результаті інструкція `import mypackage` усередині скрипту завершувалася фатальною помилкою `ImportError`, оскільки кореневий каталог проєкту випадав зі шляхів пошуку.
3. **Виконання модулів із ZIP-архівів:** з появою підтримки імпорту з архівів (PEP 273 та PEP 302 у Python 2.3) файли всередині `.zip` взагалі не мали прямого відображення у файловій системі операційної системи, тому ядро ОС не могло передати їхній шлях інтерпретатору.

У відповідь на численні запити спільноти розробників Ґвідо ван Россум (Guido van Rossum) у Python 2.4 реалізував базову підтримку прапорця `-m` (скорочення від англ. *module*). Проте початкова реалізація в CPython була вкрай обмеженою: інтерпретатор просто викликав функцію мови C `PyImport_ImportModule(modname)` і потім шукав атрибут `__file__`, щоб виконати знайдений файл як звичайний скрипт.

Такий наївний підхід мав критичний дефект: модуль завантажувався двічі. Спершу підсистема імпорту виконувала файл під його справжнім ім'ям і кешувала в `sys.modules`, а потім інтерпретатор перезапускав той самий файл у просторі імен `__main__`. Це призводило до подвійного виконання глобального коду, дублювання реєстрації об'єктів та стану гонитви в багатопотокових програмах.

## 2. PEP 338 та народження модуля runpy (Python 2.5)

У 2004–2006 роках розробник ядра CPython Нік Коґлан (Nick Coghlan) запропонував радикальний перегляд механізму виконання модулів у стандарті [PEP 338](https://peps.python.org/pep-0338/) («Executing Modules as Scripts»).

Коґлан сформулював ключовий архітектурний принцип: модуль, запущений як скрипт, повинен проходити стандартну процедуру пошуку завантажувача через `sys.meta_path`, але виконуватися лише один раз — безпосередньо в просторі імен `__main__`.

Для реалізації цього принципу стандарт запровадив спеціалізований модуль стандартної бібліотеки `runpy` та його головну функцію `run_module()`:

```
[CLI: python -m pkg.server]
          │
          ▼
[Modules/main.c: Py_RunMain]
          │  виклик runpy._run_module_as_main("pkg.server")
          ▼
[runpy.py: run_module]
    1. Пошук завантажувача через імпортні гачки (sys.meta_path)
    2. Отримання об'єкта коду (PyCodeObject) без виконання модуля
    3. Очищення або створення простору імен sys.modules['__main__']
    4. Запис метаданих: __file__, __loader__, __name__ = '__main__'
    5. Виконання байткоду в __main__.__dict__
```

Модуль `runpy` усунув подвійне виконання і дозволив інтерпретатору знаходити модулі за їхнім кваліфікованим ім'ям у будь-якому місці, доступному через `sys.path`, включно з ZIP-архівами та віртуальними сховищами.

Більше того, PEP 338 додав підтримку запуску цілих пакунків. Якщо користувач передавав ім'я пакета `python -m pkg`, `runpy` перевіряв наявність усередині каталогу пакета файлу `__main__.py` і виконував його, перетворюючи звичайні бібліотечні каталоги на повноцінні виконувані застосунки.

## 3. Криза відносних імпортів та PEP 366 (Python 2.7 / 3.1)

Хоча PEP 338 розв'язав проблему пошуку модулів, виникла нова серйозна криза, пов'язана з прийняттям стандарту [PEP 328](https://peps.python.org/pep-0328/) («Imports: Multi-Line and Absolute/Relative»).

PEP 328 ввів у Python синтаксис явних відносних імпортів:
```python
from .database import get_connection
from ..core.config import Settings
```

Механіка відносного імпорту спиралася на значення атрибута `__name__` поточного модуля. Наприклад, якщо модуль мав `__name__ = 'mypackage.services.worker'`, завантажувач відкидав останній сегмент (`.worker`) і розумів, що крапка `.` позначає пакет `mypackage.services`.

Однак при запуску через `python -m mypackage.services.worker` інтерпретатор перезаписував `__name__` на рядок `'__main__'`. Зв'язок з ієрархією пакунка миттєво втрачався:
- Байткод зустрічав інструкцію `from .database import get_connection`.
- Підсистема імпорту дивилася на `__name__`, бачила `'__main__'` і не могла визначити батьківський вузол.
- Інтерпретатор викидав виняток: `SystemError: Parent module '' not loaded, cannot perform relative import` (пізніше `ImportError: attempted relative import with no known parent package`).

Це змушувало розробників уникати відносних імпортів у файлах, які потенційно могли запускатися як точки входу CLI.

У 2007 році Нік Коґлан створив [PEP 366](https://peps.python.org/pep-0366/) («Explicit Relative Imports From a Main Module»), який запропонував елегантне рішення: відокремити ім'я точки входу від інформації про батьківський пакет.

PEP 366 запровадив новий спеціальний атрибут модуля — `__package__`:
- Для звичайних імпортованих модулів `__package__` автоматично дорівнював імені пакета (або порожньому рядку для модулів верхнього рівня).
- Коли `runpy` запускав модуль як `__main__`, він встановлював `__name__ = '__main__'`, але водночас явно записував у `__package__` ім'я батьківського вузла (наприклад, `__package__ = 'mypackage.services'`).
- Підсистема імпорту отримала правило: при резолюції відносних імпортів першочергово перевіряти атрибут `__package__`, і лише якщо він відсутній — звертатися до `__name__`.

Завдяки PEP 366 розробники отримали змогу безперешкодно поєднувати відносні імпорти всередині кодової бази зі зручним прямим запуском окремих компонентів через `python -m`.

## 4. Уніфікація специфікацій у PEP 451 (Python 3.4+)

Останнім великим кроком у еволюції точок входу став [PEP 451](https://peps.python.org/pep-0451/) («A ModuleSpec Type for the Import System»), розроблений Еріком Сноу (Eric Snow) у 2013 році.

До Python 3.4 метадані модуля були розкидані по кількох окремих атрибутах: `__file__`, `__loader__`, `__package__`, `__path__`, `__cached__`. Це призводило до розсинхронізації стану, якщо один із атрибутів модифікувався стороннім кодом.

PEP 451 запровадив уніфікований об'єкт специфікації — `ModuleSpec` (клас `importlib.machinery.ModuleSpec`), який зберігає всю інформацію про походження модуля:
- `spec.name` — оригінальне повне ім'я модуля (наприклад, `'mypackage.services.worker'`).
- `spec.loader` — екземпляр завантажувача, відповідального за створення байткоду.
- `spec.origin` — фізичне джерело файлу або архіву.
- `spec.parent` — батьківський пакет модуля.

У сучасному CPython модуль `runpy` більше не маніпулює атрибутами модуля вручну. Він створює або отримує `ModuleSpec`, встановлює `__spec__ = spec`, а значення `__package__` обчислюється автоматично з `spec.parent`. Якщо запущено кореневий файл `__main__.py` всередині каталогу чи zipapp, `spec.name` отримує значення `'__main__'`, а `spec.parent` зберігає ім'я простору імен.

Ця багаторічна еволюція перетворила прапорець `-m` із простої синтаксичної зручності на надійний механізм системного компонування та ізоляції точок входу в екосистемі Python.
