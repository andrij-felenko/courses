Коли інтерпретатор CPython отримує команду виконати сирцевий файл, переданий через аргументи командного рядка, стандартний потік вводу чи строковий вираз `-c`, він не виконує інструкції в анонімному вакуумі. На найпершому кроці ініціалізації середовище створює в глобальній таблиці завантажених модулів `sys.modules` повноцінний екземпляр об'єкта модуля під зарезервованим службовим ключем `'__main__'` і призначає його внутрішньому атрибуту `__name__` текстове значення `'__main__'`. Якщо ж той самий файл зчитується іншим скриптом за допомогою інструкції `import my_module`, підсистема імпорту реєструє його в `sys.modules` під його канонічним ім'ям `'my_module'` і встановлює атрибут `__name__ = 'my_module'`. Ця фундаментальна асиметрія простору імен лежить в основі класичної ідіоми `if __name__ == '__main__':`, яка дозволяє одному й тому самому файлу виступати або автономною виконуваною програмою, або пасивною бібліотекою функцій і класів.

## 1. Анатомія модуля `__main__` та атрибута `__name__`

На рівні вихідного коду віртуальної машини CPython модуль `__main__` створюється викликом низькорівневої функції мови C `PyImport_AddModule("__main__")`. Якщо модуль із таким ім'ям ще не зареєстровано в словнику `interp->modules`, ядро алокує нову структуру `PyModuleObject`, ініціалізує її внутрішній словник атрибутів `md_dict` і вносить запис у глобальний кеш `sys.modules`.

Простір імен модуля `__main__` отримує стандартний набір службових змінних, які визначають контекст виконання програми:
- `__name__`: завжди містить рядок `'__main__'`, незалежно від того, як файл називається на диску чи в архівах.
- `__doc__`: рядок документації модуля (дорівнює `None`, якщо перший вираз у файлі не є строковим літералом).
- `__package__`: рядок з ім'ям батьківського пакета або порожній рядок чи `None` при автономному запуску окремого файлу.
- `__loader__`: екземпляр завантажувача, що надав скомпільований байткод (наприклад, `_frozen_importlib_external.SourceFileLoader`).
- `__spec__`: об'єкт специфікації модуля `ModuleSpec` (при прямому запуску через ім'я файлу встановлюється в `None`, а при запуску через `-m` містить повні метадані).
- `__builtins__`: посилання на модуль `builtins` або його словник `__dict__`, що відкриває коду прямий доступ до базових типів `int`, `str`, `list` та вбудованих функцій `len()`, `range()`, `print()`.
- `__file__`: абсолютний або відносний шлях до файлу, який було передано інтерпретатору.
- `__cached__`: шлях до скомпільованого файлу байткоду `.pyc` у каталозі `__pycache__` (якщо код завантажується завантажувачем файлової системи).
- `__annotations__`: словник анотацій типів змінних рівня модуля (створюється за потреби).

Коли компілятор Python транслює блок умови перевірки точки входу:

```python
if __name__ == "__main__":
    main()
```

він не створює спеціальних директив препроцесора чи магічних структур. У генераторі байткоду формується звичайна послідовність низькорівневих інструкцій стекової машини віртуального процесора:

```
0   LOAD_NAME        0 (__name__)
2   LOAD_CONST       0 ('__main__')
4   COMPARE_OP       0 (==)
8   POP_JUMP_IF_FALSE 16
10  LOAD_NAME        1 (main)
12  CALL_FUNCTION    0
14  POP_TOP
16  ...
```

Стекова машина завантажує значення глобальної змінної `__name__` з поточного словника `globals()`, кладе на стек константу `'__main__'`, здійснює операцію порівняння рядків і у разі невідповідності здійснює перехід за межі умовного блоку.

### Небезпека подвійного імпорту (Dual-Import Problem)

Критична архітектурна пастка виникає тоді, коли файл, запущений безпосередньо як головна точка входу (`python server.py`), одночасно імпортується іншими модулями проєкту або навіть самим собою за допомогою інструкції `import server`.

Підсистема імпорту шукає модуль `server` у таблиці `sys.modules`. Оскільки запущений скрипт був зареєстрований виключно під псевдонімом `'__main__'`, запис `sys.modules['server']` відсутній. CPython відкриває файл `server.py` вдруге, компілює його байткод і створює абсолютно новий екземпляр `PyModuleObject` під іменем `'server'`.

У результаті в пам'яті одного процесу виникають два ізольовані модулі:
1. `sys.modules['__main__']` — контекст, у якому виконується точка входу.
2. `sys.modules['server']` — контекст, який використовують усі імпортовані підмодулі.

Таке роздвоєння простору імен призводить до трьох категорій дефектів:
- **Руйнування глобальних синглтонів:** змінні рівня модуля (як-от пули з'єднань з базою даних, системні кеші чи конфігураційні об'єкти) ініціалізуються двічі та не синхронізуються між собою.
- **Збій перевірки типів `isinstance()`:** клас `User`, визначений у `__main__`, і клас `User`, імпортований через `from server import User`, є різними об'єктами в купі CPython, тому перевірка `isinstance(user_obj, User)` повертає `False`.
- **Подвійна реєстрація обробників:** якщо модуль реєструє сигнали операційної системи, веб-роути або хуки логування на глобальному рівні, ці дії виконуються двічі, спричиняючи дублювання подій.

Щоб уникнути роздвоєння простору імен, код точки входу повинен бути максимально легким: він має лише зчитувати параметри командного рядка та делегувати виконання функції всередині бібліотечного пакета.

## 2. Прапорець `-m` та внутрішня механіка `runpy`

Прямий запуск скрипту через передачу шляху до файлу (`python app/services/worker.py`) створює фатальну проблему для організації великих проєктів: він ламає відносні імпорти.

Коли CPython запускає файл за шляхом, він виконує наступні дії:
1. Отримує каталог переданого файлу: `os.path.dirname(os.path.abspath("app/services/worker.py"))` -> `/project/app/services/`.
2. Записує цей каталог на нульову позицію списку шляхів пошуку: `sys.path[0] = "/project/app/services/"`.
3. Встановлює атрибут `__package__ = ""` (або `None`), оскільки CPython розглядає запущений файл як ізольований скрипт верхнього рівня.

Якщо всередині `worker.py` міститься інструкція відносного імпорту:

```python
from .database import get_pool
from ..core.config import settings
```

інтерпретатор завершує роботу винятком:
```
ImportError: attempted relative import with no known parent package
```

Підсистема імпорту не може обчислити відносний шлях, оскільки атрибут `__package__` не встановлено, а батьківський каталог проєкту `/project` взагалі відсутній у `sys.path`.

### Як прапорець `-m` змінює правила завантаження

Прапорець `-m` (англ. *module*) докорінно змінює логіку ініціалізації середовища. Замість виконання файлу за фізичним шляхом інтерпретатор запускає модуль за його логічним кваліфікованим ім'ям:

```bash
python -m app.services.worker
```

У цьому режимі CPython не намагається відкрити файл самостійно, а передає керування внутрішньому модулю стандартної бібліотеки `runpy` (функція `runpy._run_module_as_main()`).

![Ініціалізація та стан простору імен: порівняння трьох режимів запуску](/root/sys/sys-plang-python/main-and-dash-m/img/main-module-lifecycle.svg)
*Порівняння конфігурації sys.path[0], атрибутів __name__, __package__ та __spec__ для прямого запуску скрипту, виклику через -m та бібліотечного імпорту.*

Ланцюг виконання `runpy.run_module()` складається з п'яти обов'язкових кроків:

1. **Конфігурація `sys.path[0]`:** на нульову позицію списку шляхів записується поточний робочий каталог процесу (`os.getcwd()`), а не вкладений підкаталог файлу. Завдяки цьому кореневий пакет `app` залишається доступним для імпорту.
2. **Пошук специфікації (`find_spec`):** `runpy` звертається до стандартної підсистеми `importlib.util.find_spec("app.services.worker")`. Завантажувачі сканують `sys.meta_path` і повертають повноцінний екземпляр `ModuleSpec`, що містить посилання на завантажувач та інформацію про батьківський пакет (`spec.parent = "app.services"`).
3. **Обробка пакунків:** якщо цільовий модуль виявляється пакетом (каталогом з `__init__.py`), `runpy` автоматично модифікує ім'я пошуку на `app.services.worker.__main__` і повторює процедуру пошуку.
4. **Формування метаданих точки входу:** `runpy` створює або очищає модуль `__main__` і встановлює коректні системні атрибути:
   - `__name__ = '__main__'`
   - `__spec__ = spec` (де `spec.name == "app.services.worker"`)
   - `__package__ = spec.parent` (тобто `'app.services'`)
   - `__file__ = spec.origin`
5. **Виконання об'єкта коду:** завантажувач компілює вихідний код у `PyCodeObject` без виконання і передає його функції `exec()`, яка виконує байткод безпосередньо у просторі імен `sys.modules['__main__'].__dict__`.

### Механізм резолюції відносних імпортів через `__spec__.parent`

Коли підсистема імпорту (`importlib._bootstrap`) зустрічає інструкцію `from ..core.config import settings`, вона запускає внутрішню функцію `_resolve_name(name, package, level)`:

- Параметр `level` вказує на кількість крапок на початку імпорту (`level = 2` для двох крапок `..`).
- Функція зчитує атрибут `__package__` поточного модуля. Якщо він не встановлений, береться `__spec__.parent`.
- У нашому випадку `package = "app.services"`.
- Функція розбиває рядок за крапками на список сегментів: `["app", "services"]`.
- З кінця списку відкидається `level - 1` сегментів (для двох крапок відкидається один сегмент `services`), залишаючи базовий пакет `["app"]`.
- До отриманого префікса додається цільовий шлях імпорту: `"app" + "." + "core.config"` -> `"app.core.config"`.
- Інтерпретатор виконує стандартний абсолютний імпорт модуля `app.core.config`.

Якби модуль запускався прямо через `python app/services/worker.py`, значення `package` було б порожнім або `None`, і функція `_resolve_name` викинула б `ImportError` на кроці розрахунку базового префікса.

Історію виникнення прапорця `-m`, мотиви його розробників та подолання кризи відносних імпортів описано у вставці [Історія PEP 338, PEP 366 та еволюція прапорця -m](root:sys-plang-python/main-and-dash-m/hist-runpy-and-pep338.md). Повний опис функцій та параметрів модуля `runpy` наведено у вставці [Програмний інтерфейс модуля runpy та функції запуску C API](root:sys-plang-python/main-and-dash-m/api-runpy.md).

## 3. Пакети та каталоги як виконувані сутності: `__main__.py` та `zipapp`

Python підтримує пряме виконання не лише окремих файлів, але й цілих каталогів та архівів. Якщо передати інтерпретатору ім'я каталогу або ZIP-архіву:

```bash
python /path/to/my_application/
python /path/to/my_application.zip
```

CPython перевіряє наявність файлу `__main__.py` у корені зазначеного каталогу чи архіву.

### Механізм запуску каталогу через `__main__.py`

Коли інтерпретатор отримує каталог `/path/to/my_application/`:
1. Шлях `/path/to/my_application/` додається на початок списку `sys.path[0]`.
2. Інтерпретатор перевіряє існування файлу `/path/to/my_application/__main__.py`.
3. Якщо файл існує, CPython компілює його та виконує в контексті модуля `__main__`.
4. Якщо файл `__main__.py` відсутній, інтерпретатор завершує роботу з фатальною помилкою: `can't find '__main__' module in '/path/to/my_application/'`.

Цей механізм дозволяє проєктувати пакунки, які одночасно є бібліотеками та виконуваними утилітами. При імпорті `import my_application` виконується файл `__init__.py`, а файл `__main__.py` повністю ігнорується. При запуску через командний рядок `python -m my_application` інтерпретатор спершу виконує `__init__.py` (ініціалізуючи пакет), а потім виконує `__main__.py` як точку входу.

### Автономні [виконувані архіви zipapp](root:sys-plang-python/zipapp-executables) (PEP 441)

Стандарт [PEP 441](https://peps.python.org/pep-0441/) стандартизував механізм пакування комплексних застосунків Python у єдиний виконуваний файл формату `.pyz` (або `.zipapp`). Докладний аналіз цієї підсистеми розкрито у статті про [виконувані архіви zipapp](root:sys-plang-python/zipapp-executables).

В основі технології `zipapp` лежить особливість специфікації формату ZIP та стандарту завантаження файлів POSIX:

![Анатомія виконуваного файлу zipapp: подвійне парсування заголовків](/root/sys/sys-plang-python/main-and-dash-m/img/zipapp-shebang-structure.svg)
*Фізична структура автономного виконуваного файлу zipapp та механіка його обробки ядром ОС і модулем zipimport.*

1. **Формат ZIP зчитується з кінця файлу:** специфікація ZIP-архіву не вимагає, щоб перший байт файлу містив магічні сигнатури. Бібліотека розпакування знаходить запис `End of Central Directory Record` (EOCD), зчитуючи останні 22 байти файлу, і звідти обчислює зміщення таблиці каталогів.
2. **Ядро ОС зчитує файл із початку:** системний виклик `execve()` операційної системи Linux/macOS аналізує перші два байти файлу в пошуках магічних символів `#!` (шебанг).

Завдяки цьому файл `zipapp` конструюється шляхом конкатенації двох частин:
- **Префікс:** текстовий рядок шебангу (наприклад, `#!/usr/bin/env python3\n`).
- **Тіло:** стандартний бінарний потік даних ZIP-архіву, що містить файл `__main__.py` у корені та скомпільовані модулі пакунка.

Коли користувач запускає файл у терміналі як `./sysmon.pyz`:
1. Ядро операційної системи виявляє шебанг, парсить шлях до бінарного файлу `/usr/bin/env python3` і запускає інтерпретатор Python, передаючи шлях до `./sysmon.pyz` як аргумент `argv[1]`.
2. CPython додає `./sysmon.pyz` у `sys.path[0]`. Вбудований завантажувач `zipimport` перехоплює звернення до архіву, знаходить у ньому `__main__.py` і виконує байткод безпосередньо з пам'яті процесу, без розпакування файлів на диск.

Повну реалізацію генератора zipapp-архівів та системного C/C++ завантажувача продемонстровано у практичній вставці [Автономний виконуваний пакунок zipapp та C/C++ завантажувач](root:sys-plang-python/main-and-dash-m/proj-zipapp-runtime.md).

## 4. Точки входу консольних скриптів (`console_scripts`) та `pyproject.toml`

Для кінцевих користувачів виклик застосунків через `python -m myapp` або `./myapp.pyz` часто є незручним. Стандартним способом дистрибуції консольних утиліт в екосистемі Python є механізм точок входу консольних скриптів (Console Scripts Entry Points).

### Декларація точки входу за стандартом PEP 621

У сучасному стандарті конфігурації проєктів точка входу оголошується в маніфесті [Метадані проєкту в pyproject.toml](root:sys-plang-python/pyproject-toml) у секції `[project.scripts]`:

```toml
[project]
name = "hyperflux"
version = "2.4.0"
dependencies = [
    "click>=8.1.0",
    "rich>=13.0.0",
]

[project.scripts]
hyperflux-cli = "hyperflux.cli.entry:main"
```

Синтаксис `"hyperflux.cli.entry:main"` складається з двох частин, розділених двокрапкою:
- `hyperflux.cli.entry` — повне кваліфіковане ім'я модуля, де розташована функція запуску.
- `main` — ім'я викликаного об'єкта (функції або екземпляра класу, що реалізує метод `__call__`).

Під час збирання розподільчого пакунка [sdist, wheel і бінарні колеса](root:sys-plang-python/wheels-and-sdist) інструмент збирання (наприклад, `flit`, `hatchling` або `setuptools`) генерує службовий файл `entry_points.txt` всередині каталогу `.dist-info`:

```ini
[console_scripts]
hyperflux-cli = hyperflux.cli.entry:main
```

### Генерація виконуваних обгорток установника (`pip`)

Коли інсталятор `pip` встановлює пакунок у віртуальне середовище або системний каталог, він зчитує метадані `console_scripts` і автоматично створює виконуваний файл у системному каталозі бінарних файлів (`<venv>/bin/` у POSIX-системах або `<venv>\Scripts\` у Windows).

У середовищах POSIX (Linux, macOS) `pip` генерує компактний скрипт Python:

```python
#!/path/to/virtualenv/bin/python3
# -*- coding: utf-8 -*-
import re
import sys
from hyperflux.cli.entry import main

if __name__ == '__main__':
    sys.argv[0] = re.sub(r'(-script\.pyw|\.exe)?$', '', sys.argv[0])
    sys.exit(main())
```

Ключові властивості згенерованої обгортки:
1. **Жорстка прив'язка інтерпретатора:** перший рядок містить абсолютний шлях до інтерпретатора конкретного віртуального середовища (`#!/path/to/virtualenv/bin/python3`), а не загальний `#!/usr/bin/env python`. Це гарантує, що скрипт завжди запускається з правильним набором залежностей і коректним `sys.executable`.
2. **Ізоляція імпорту:** функція `main()` імпортується як звичайний бібліотечний модуль, тому всі відносні імпорти всередині пакунка функціонують у штатному режимі.
3. **Обробка коду завершення:** результат виклику `main()` передається безпосередньо у функцію `sys.exit()`, гарантуючи коректне повернення системного статусу (`0` при успіху або відмінне від нуля число при збої) батьківському процесу операційної системи.

У середовищі Windows, де ядро операційної системи не підтримує нативну інтерпретацію POSIX-шебангів у текстових файлах, `pip` використовує скомпільовані C-лаунчери (`pip.exe` / бібліотека `distlib`). Інсталятор записує у каталог `Scripts/` файл `hyperflux-cli.exe`, який містить скомпільований бінарний завантажувач з вбудованим Python-скриптом у ресурсах, що самостійно знаходить суміжний `python.exe` і передає йому керування.

## 5. Вбудовування та запуск точок входу через C API

Під час інтеграції CPython у нативні системні застосунки на C та C++ розробники керують створенням та виконанням точки входу безпосередньо через функції C API.

Нижче наведено приклад хост-програми, яка конфігурує інтерпретатор через стандартизовану структуру `PyConfig` (PEP 587), передає аргументи командного рядка та запускає цільовий модуль або скрипт.

:::tabs
```c
/* main_host.c — Запуск модуля Python через C API */
#define PY_SSIZE_T_CLEAN
#include <Python.h>
#include <stdio.h>

int run_embedded_module(const char *module_name, int argc, char *argv[]) {
    PyStatus status;
    PyConfig config;

    /* Ініціалізуємо конфігурацію Python за замовчуванням */
    PyConfig_InitPythonConfig(&config);
    config.parse_argv = 1;

    /* Встановлюємо модуль, який буде запущено як точка входу (аналог python -m) */
    status = PyConfig_SetBytesString(&config, &config.run_module, module_name);
    if (PyStatus_Exception(status)) {
        PyConfig_Clear(&config);
        fprintf(stderr, "Помилка встановлення імені модуля в PyConfig\n");
        return 1;
    }

    /* Передаємо список аргументів командного рядка */
    status = PyConfig_SetBytesArgv(&config, argc, argv);
    if (PyStatus_Exception(status)) {
        PyConfig_Clear(&config);
        fprintf(stderr, "Помилка встановлення аргументів argv\n");
        return 1;
    }

    /* Розгортаємо структури ядра інтерпретатора */
    status = Py_InitializeFromConfig(&config);
    if (PyStatus_Exception(status)) {
        PyConfig_Clear(&config);
        fprintf(stderr, "Фатальна помилка ініціалізації середовища CPython\n");
        return 1;
    }
    PyConfig_Clear(&config);

    /* Запускаємо модуль у контексті __main__ */
    int exit_code = Py_RunMain();
    return exit_code;
}

int main(int argc, char *argv[]) {
    const char *target = (argc > 1) ? argv[1] : "http.server";
    printf("[Host C] Запуск цільового модуля Python: %s\n", target);
    return run_embedded_module(target, argc, argv);
}
```
```cpp
// main_host.cpp — Ідіоматичний C++20 завантажувач модуля з RAII
#define PY_SSIZE_T_CLEAN
#include <Python.h>
#include <iostream>
#include <memory>
#include <stdexcept>
#include <string_view>
#include <span>

class EmbeddedPythonHost {
public:
    explicit EmbeddedPythonHost(std::string_view module_name, std::span<char*> args) {
        PyConfig config;
        PyConfig_InitPythonConfig(&config);
        config.parse_argv = 1;

        PyStatus status = PyConfig_SetBytesString(&config, &config.run_module, module_name.data());
        if (PyStatus_Exception(status)) {
            PyConfig_Clear(&config);
            throw std::runtime_error("Не вдалося сконфігурувати цільовий модуль run_module");
        }

        status = PyConfig_SetBytesArgv(&config, static_cast<int>(args.size()), args.data());
        if (PyStatus_Exception(status)) {
            PyConfig_Clear(&config);
            throw std::runtime_error("Не вдалося ініціалізувати масив аргументів CLI");
        }

        status = Py_InitializeFromConfig(&config);
        PyConfig_Clear(&config);

        if (PyStatus_Exception(status)) {
            throw std::runtime_error("Помилка розгортання структур середовища CPython");
        }
    }

    ~EmbeddedPythonHost() {
        if (Py_IsInitialized()) {
            Py_Finalize();
        }
    }

    EmbeddedPythonHost(const EmbeddedPythonHost&) = delete;
    EmbeddedPythonHost& operator=(const EmbeddedPythonHost&) = delete;

    [[nodiscard]] int execute() noexcept {
        return Py_RunMain();
    }
};

int main(int argc, char* argv[]) {
    try {
        std::string_view target_module = (argc > 1) ? argv[1] : "http.server";
        std::span<char*> args(argv, static_cast<size_t>(argc));

        std::cout << "[Host C++] Ініціалізація CPython для модуля: " << target_module << std::endl;
        EmbeddedPythonHost host(target_module, args);
        int exit_code = host.execute();
        std::cout << "[Host C++] Виконання модуля завершено з кодом: " << exit_code << std::endl;
        return exit_code;
    } catch (const std::exception& err) {
        std::cerr << "[Host C++ Error] " << err.what() << std::endl;
        return 1;
    }
}
```

## 6. Діагностика, типові пастки та інженерні практики

Практична робота з точками входу в Python пов'язана з низкою типових системних помилок. Нижче наведено розбір чотирьох найпоширеніших пасток та інженерні методи їх нейтралізації.

### Пастка 1: Виклик інструментів через глобальний виконуваний файл замість `python -m`

Коли розробник викликає інструмент розробки безпосередньо за його системним ім'ям:

```bash
pip install requests
pytest tests/
mypy src/
```

оболонка командного рядка операційної системи шукає перший-ліпший бінарний файл з відповідним ім'ям у системній змінній `PATH`. Якщо в системі встановлено кілька версій Python або активне віртуальне середовище було переміщене, викликаний бінарний файл `pip` може належати зовсім іншому інтерпретатору. У результаті пакунки встановлюються не в те середовище, в якому запускається проєкт.

**Інженерне правило:** завжди викликати системні утиліти через явний інтерпретатор:

```bash
python3 -m pip install requests
python3 -m pytest tests/
python3 -m mypy src/
```

Такий виклик математично гарантує, що інструмент буде виконано саме тим екземпляром інтерпретатора, який викликав команду, і встановить залежності в його локальний каталог `site-packages`.

### Пастка 2: Мутація `sys.path[0]` та конфлікти локальних імен

При прямому запуску `python script.py` каталог скрипту стає `sys.path[0]`. Якщо в цьому каталозі випадково створено файл з іменем, що збігається з модулем стандартної бібліотеки (наприклад, `random.py`, `email.py`, `queue.py` або `math.py`), будь-який бібліотечний імпорт `import random` усередині сторонніх пакунків імпортує ваш локальний файл замість стандартної бібліотеки, викликаючи незрозумілі винятки `AttributeError`.

**Метод захисту:** використання прапорця безпечних шляхів `-P` (або змінної середовища `PYTHONSAFEPATH=1`, починаючи з Python 3.11). Прапорець блокує додавання поточного робочого каталогу на початок `sys.path`, захищаючи процес від випадкового або шкідливого перехоплення імен системних модулів.

### Пастка 3: Виконання коду під час імпорту (Import-Time Side Effects)

Якщо логіка запуску (відкриття сокетів, парсинг аргументів `sys.argv`, запис у базу даних) розміщена на глобальному рівні модуля без огортання в функцію та блок `if __name__ == '__main__':`, вона безумовно виконується при кожній спробі імпортувати модуль сторонніми скриптами чи тестовими фреймворками:

```python
# АНТИПАТЕРН: важкі побічні ефекти на глобальному рівні модуля
import sys
import argparse

parser = argparse.ArgumentParser()
parser.add_argument("--port", type=int, default=8080)
args = parser.parse_args()  # Ламає тестові фреймворки при спробі 'import my_module'

server = start_server(args.port)  # Негайно відкриває мережевий сокет
```

**Канонічний шаблон побудови точки входу:**

```python
# ПРАВИЛЬНО: повна ізоляція логіки виконання
import sys
import argparse


def parse_arguments(argv: list[str] | None = None) -> argparse.Namespace:
    """Парсить параметри командного рядка."""
    parser = argparse.ArgumentParser(description="Мережевий мікросервіс")
    parser.add_argument("--port", type=int, default=8080, help="Порт сервера")
    return parser.parse_args(argv)


def main(argv: list[str] | None = None) -> int:
    """Головна точка входу: повертає числовий код завершення."""
    args = parse_arguments(argv)
    try:
        server = start_server(args.port)
        server.serve_forever()
        return 0
    except KeyboardInterrupt:
        return 130
    except Exception as err:
        sys.stderr.write(f"Фатальна помилка: {err}\n")
        return 1


if __name__ == "__main__":
    sys.exit(main())
```

Переваги канонічного шаблону:
1. Функція `main()` приймає опціональний аргумент `argv`, що дозволяє легко тестувати точку входу в модульних тестах `unittest`/`pytest` без маніпуляцій з глобальним `sys.argv`.
2. Функція явно повертає цілочисельний код завершення процесу, який передається у `sys.exit()`.
3. Модуль можна імпортувати в будь-якому місці програми для повторного використання окремих функцій без ризику запуску сервера чи блокування потоку.

### Пастка 4: Робота налагоджувачів і профайлерів з прапорцем `-m`

При профілюванні чи налагодженні застосунків розробники часто передають модуль профайлера перед цільовим скриптом:

```bash
python -m cProfile app/server.py
```

У такій конфігурації модуль `cProfile` сам стає модулем `__main__`, а файл `app/server.py` виконується через низькорівневий компілятор байткоду в просторі імен профайлера. Якщо ж цільовий модуль сам є пакетом і вимагає запуску через `-m`, виклик набуває форми:

```bash
python -m cProfile -m app.server
```

Модуль `cProfile` стандартної бібліотеки самостійно викликає функцію `runpy.run_module("app.server", run_name="__main__")`. Розуміння ролі `runpy` як універсального двигуна виконання модулів дозволяє розробникам створювати власні системні обгортки (інструменти моніторингу пам'яті, трейсери, інжектори залежностей), які прозоро перехоплюють виконання точок входу без модифікації коду цільових застосунків.

## 7. Терміни, етимологія та підсумок

Для закріплення матеріалу зведемо ключові поняття теми та їхнє походження:

- **Точка входу** (англ. *entry point*, лат. *punctum* — укол, крапка) — початкова адреса інструкції в пам'яті або викликана функція, з якої починається послідовне виконання байткоду процесу після завантаження операційною системою.
- **Модуль** (лат. *modulus* — міра, зразок, невеликий блок) — автономна структурна одиниця коду, що інкапсулює власний простір імен `__dict__` у вигляді екземпляра `PyModuleObject`.
- **Пакет** (фр. *paquet*, нід. *pak* — вузол, пакунок) — ієрархічний простір імен, що об'єднує групу пов'язаних модулів навколо спільного каталогу з атрибутом `__path__`.
- **Шебанг** (англ. *shebang*, утворено від сленгового скорочення символів решітки *hash* `#!` та знака оклику *bang*) — магічна двобайтова послідовність символів `0x23 0x21` на початку файлу, за якою завантажувач ядра POSIX визначає шлях до інтерпретатора.
- **Архівація zipapp** (англ. *zip application*) — технологія пакування повного середовища виконання програми та її точок входу в єдиний виконуваний ZIP-файл.

Архітектура точок входу в Python спирається на гармонійне поєднання низькорівневих метаданих об'єкта модуля (`__name__`, `__package__`, `__spec__`), службового модуля `runpy` та стандартизованих форматів пакування (`zipapp`, `console_scripts`). Розуміння різниці між прямим виконанням скрипту за шляхом і запуском через прапорець `-m` усуває дефекти імпорту, запобігає роздвоєнню глобального простору імен і забезпечує бездоганну надійність розгортання програмних систем.
