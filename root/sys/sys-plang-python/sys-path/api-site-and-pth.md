# 📋 Контракт модуля site, специфікація .pth та змінні оточення sys.path

Під час ініціалізації CPython формування остаточного списку каталогів `sys.path` делегується модулю стандартної бібліотеки `site.py`. Цей модуль виконує виявлення каталогів встановлення сторонніх пакунків (`site-packages`), парсинг і виконання конфігураційних файлів `.pth`, підключення ізольованих користувацьких каталогів та виконання системних хуків налаштування середовища `sitecustomize` і `usercustomize`.

Нижче наведено формальну специфікацію інтерфейсів модуля `site`, граматику файлів `.pth`, протокол обробників `sys.path_hooks`, механізми роботи сучасних розробницьких встановлень за стандартом PEP 660 та зведену таблицю конфігураційних змінних оточення і прапорців командного рядка.

## 1. Програмний інтерфейс модуля site

Модуль `site` імпортується автоматично на фінальній фазі завантаження інтерпретатора (якщо не передано прапорець `-S`). Усі функції працюють з глобальним списком `sys.path` або повертають розраховані системні шляхи.

| Елемент API | Сигнатура / Тип | Опис та семантика виконання |
|---|---|---|
| `site.main()` | `() -> None` | Головна точка входу. Викликає послідовно `abs__file__()`, `known_paths = set()`, `addsitepackages(known_paths)`, `addusersitepackages(known_paths)`, `execsitecustomize()`, `execusercustomize()`. |
| `site.addsitedir()` | `(sitedir: str \| Path, known_paths: set[str] \| None = None) -> set[str]` | Додає каталог `sitedir` до `sys.path`, сканує його на наявність файлів `*.pth`, обробляє їхній вміст і рекурсивно додає всі знайдені шляхи до списку пошуку. Повертає оновлену множину нормалізованих шляхів. |
| `site.addsitepackages()` | `(known_paths: set[str], prefixes: list[str] \| None = None) -> set[str]` | Визначає шляхи `site-packages` для всіх префіксів із `site.PREFIXES` (або переданого списку `prefixes`), перевіряє їхню наявність на диску та реєструє через `addsitedir()`. |
| `site.addusersitepackages()` | `(known_paths: set[str]) -> set[str] \| None` | Перевіряє константу `ENABLE_USER_SITE`. Якщо прапорець істинний, визначає шлях до каталогу користувача через `getusersitepackages()` і викликає `addsitedir()`. |
| `site.getsitepackages()` | `(prefixes: list[str] \| None = None) -> list[str]` | Повертає список стандартних каталогів `site-packages` для поточної платформи без їхньої фактичної реєстрації в `sys.path`. |
| `site.getusersitepackages()` | `() -> str` | Повертає платформозалежний шлях до каталогу користувацьких пакунків (`~/.local/lib/pythonX.Y/site-packages` у POSIX або `%APPDATA%\Python\PythonXY\site-packages` у Windows). |
| `site.getuserbase()` | `() -> str` | Повертає базовий шлях користувацького середовища (`~/.local` у POSIX або `%APPDATA%\Python` у Windows). |
| `site.ENABLE_USER_SITE` | `bool \| None` | Прапорець дозволу використання користувацьких каталогів. Встановлюється в `False` при передачі прапорця `-s`, `-I` або встановленні змінної `PYTHONNOUSERSITE=1`. |
| `site.PREFIXES` | `list[str]` | Список префіксів встановлення інтерпретатора. За замовчуванням містить `[sys.prefix, sys.exec_prefix]`. |

```python
import site
import sys
from pathlib import Path

# Програмне підключення зовнішнього каталогу пакунків з обробкою його .pth файлів
known_paths = set(sys.path)
plugin_dir = Path("/opt/custom_plugins")

if plugin_dir.is_dir():
    site.addsitedir(str(plugin_dir), known_paths=known_paths)

print("Загальні каталоги site-packages:", site.getsitepackages())
print("Користувацький site-packages:", site.getusersitepackages())
print("Статус активації User Site:", site.ENABLE_USER_SITE)
```

## 2. Специфікація конфігураційних файлів .pth

Файли з розширенням `.pth` (Path Configuration Files) розташовуються безпосередньо всередині каталогів `site-packages`. Вони дозволяють пакетам і менеджерам залежностей динамічно розширювати список `sys.path` або виконувати код бутстрапу без необхідності модифікувати глобальні файли інтерпретатора.

### Правила парсингу та граматика

Функція `site.addsitedir()` знаходить усі файли з розширенням `.pth` у переданому каталозі, сортує їх в алфавітному порядку (`sorted(os.listdir(sitedir))`) і построково інтерпретує кожен файл відповідно до таких правил:

1. **Ігнорування порожніх рядків:** Рядки, що містять лише пробільні символи або символи переведення рядка `\r\n`, пропускаються без генерації помилок.
2. **Коментарі:** Рядки, першим непробільним символом яких є знак решітки `#`, ігноруються. Коментарі не можуть бути інлайн-хвостами після шляхів.
3. **Рядки шляхів файлової системи:** Будь-який рядок, що не починається з інструкції `import `, вважається шляхом до каталогу.
   - Якщо шлях абсолютний (`/opt/libs/mylib`), він нормалізується функцією `os.path.abspath()` і перевіряється на існування на диску через системний виклик `stat()`.
   - Якщо шлях відносний (`src` або `../subpkg`), він розраховується відносно каталогу, у якому розташовано сам `.pth` файл.
   - Знайдений і валідований каталог додається в кінець `sys.path` (якщо він ще не присутній у множині `known_paths`).
   - Якщо доданий каталог сам містить файли `*.pth`, вони не скануються повторно автоматично, якщо не викликано вкладений `addsitedir`.
4. **Рядки динамічного виконання (Executive lines):** Якщо рядок починається з ключового слова `import ` або `import\t`, увесь залишок рядка передається у вбудовану функцію `exec()`.

```ini
# Приклад структури файлу editable_package.pth
# 1. Додавання абсолютного шляху до розробницького каталогу
/home/developer/projects/core_engine/src

# 2. Додавання відносного шляху відносно каталогу site-packages
../custom_toolchain/lib

# 3. Виконання довільного Python-коду під час ініціалізації
import sys, os; sys.path.insert(0, os.path.expanduser('~/fast_overrides'))
```

> [!WARNING]
> Рядки з `import` у файлах `.pth` виконуються під час кожного старту інтерпретатора з правами поточного користувача. Якщо зловмисник отримує права на запис у каталог `site-packages` або створює шкідливий `.pth` файл у користувацькому каталозі `~/.local/lib/pythonX.Y/site-packages`, це призводить до виконання довільного коду (Arbitrary Code Execution) ще до початку роботи основного скрипту застосунку.

## 3. Режими розробницького встановлення (PEP 660 та .pth файли)

При виконанні команди `pip install -e .` (Editable Installs) інструменти збирання (`setuptools`, `flit`, `hatchling`, `meson-python`) повинні зробити код проєкту доступним для імпорту без фізичного копіювання файлів у `site-packages`. Сучасні бекенди використовують два принципово різні підходи до створення файлів `.pth`:

### Підхід 1: Простий шлях (Path-based .pth)

Традиційний підхід, що використовується для простих пакетів без компільованих C-розширень. Менеджер пакетів створює файл `myproject.pth` у каталозі `site-packages`, який містить один рядок — абсолютний шлях до каталогу `src`:

```
/home/developer/workspace/project/src
```

Перевага цього підходу — нульові накладні витрати на швидкодію імпорту, оскільки шлях просто додається до списку `sys.path`.

### Підхід 2: Завантажувач імпорту (Loader-based .pth за PEP 660)

Якщо проєкт містить динамічно згенеровані модулі, C-розширення або складне відображення пакетів, просте додавання шляху до `sys.path` може призвести до затінення файлів або некоректної роботи просторів імен. Бекенд збирання (наприклад, `setuptools >= 64`) генерує файл `__editable__.myproject-0.1.0.pth`, що містить виконавчий рядок:

```python
import _editable_setuptools_myproject_finder; _editable_setuptools_myproject_finder.install()
```

Поруч у каталозі `site-packages` створюється модуль `_editable_setuptools_myproject_finder.py`, який реєструє спеціальний об'єкт `MetaPathFinder` у списку `sys.meta_path`. Цей шукач перехоплює імпорти конкретного пакета та динамічно транслює їх у файли робочого каталогу, залишаючи решту простору імен ізольованою.

## 4. Протокол перехоплювачів sys.path_hooks та кеш імпортерів

Список `sys.path` працює у тісному зв'язку з двома системними структурами ядра CPython: `sys.path_hooks` та `sys.path_importer_cache`. Вони забезпечують поліморфний пошук модулів як у звичайних каталогах файлової системи, так і всередині спеціальних контейнерів (zip-архіви, об'єктні сховища, розподілена пам'ять).

```
Вхідний шлях із sys.path: "/app/packages.zip"
                     │
                     ▼
          sys.path_importer_cache?
          ┌──────────┴──────────┐
       [Присутній]          [Відсутній]
          │                     │
          ▼                     ▼
   Повертає об'єкт        Ітерація по sys.path_hooks:
   Finder з кешу          1. zipimport.zipimporter("/app/packages.zip")
                          ├─ Підходить → Створює zipimporter
                          └─ Не підходить → Кидає ImportError
                                │
                                ▼
                          Запис у sys.path_importer_cache
```

### Специфікація обробників та інтерфейс пошуку:

- `sys.path_hooks`: Список викликаних об'єктів (Callables: класи або функції), які приймають один рядковий аргумент — шлях із `sys.path`.
  - Якщо обробник здатний обслуговувати цей шлях (наприклад, `zipimport.zipimporter` для валідного zip-файлу або кастомний `NetworkFinder`), він повертає об'єкт шукача (Finder), що реалізує інтерфейс `find_spec(fullname, target=None)`.
  - Якщо шлях не підтримується цим обробником, він зобов'язаний згенерувати виняток `ImportError`.
  - Якщо жоден обробник із `sys.path_hooks` не повернув шукача, стандартний механізм `PathFinder` створює екземпляр `_frozen_importlib_external.FileFinder` для звичайної файлової системи.
- `sys.path_importer_cache`: Словник, що відображає рядки шляхів на екземпляри шукачів. Якщо каталог не існує або для нього не знайдено жодного імпортера, у словник записується значення `None` (або `NullFinder`), щоб уникнути повторних дорогих перевірок системними викликами `stat()`.

```python
import sys
from importlib.machinery import FileFinder, SourceFileLoader

# Приклад реєстрації власного хука для пошуку модулів у зашифрованих контейнерах
def custom_archive_hook(path: str):
    if path.endswith(".secure_pkg"):
        # Повертаємо спеціалізований Finder для захищеного архіву
        return CustomSecureFinder(path)
    raise ImportError(f"Шлях {path} не є захищеним пакетом")

# Додавання хука на початок списку перехоплювачів
sys.path_hooks.insert(0, custom_archive_hook)

# Очищення кешу імпортерів для форсування повторного опитування
sys.path_importer_cache.clear()
```

## 5. Конфігураційні прапорці CLI та змінні оточення

Поведінка розрахунку `sys.path` та виконання модуля `site` контролюється через аргументи командного рядка інтерпретатора та змінні середовища процесу.

| Прапорець CLI | Змінна оточення | Вплив на формування sys.path |
|---|---|---|
| `-P` | `PYTHONSAFEPATH=1` | **Безпечний шлях:** забороняє додавання потенційно небезпечного поточного каталогу або каталогу скрипту в `sys.path[0]`. Значення `sys.path[0]` взагалі не створюється або очищається. |
| `-S` | *(немає)* | **Вимкнення site.py:** інтерпретатор не завантажує `site.py`. У `sys.path` залишаються лише початкові шляхи standard library, без `site-packages`, без `.pth` та без `user-site`. |
| `-s` | `PYTHONNOUSERSITE=1` | **Вимкнення User Site:** блокує додавання користувацького каталогу `~/.local/lib/pythonX.Y/site-packages` до `sys.path`. Встановлює `site.ENABLE_USER_SITE = False`. |
| `-E` | `PYTHONIGNOREENVIRONMENT=1` | **Ігнорування середовища:** змушує CPython повністю ігнорувати всі змінні оточення `PYTHON*` (включно з `PYTHONPATH`, `PYTHONHOME`, `PYTHONSAFEPATH`). |
| `-I` | *(немає)* | **Ізольований режим (Isolated Mode):** вмикає одночасно комбінацію `-E`, `-s` та блокує неявне додавання поточного каталогу в `sys.path[0]`. Рекомендовано для системних демонів і скриптів адміністрування. |
| *(немає)* | `PYTHONPATH` | **Користувацькі шляхи:** рядок шляхів, розділених `os.pathsep` (`:` у POSIX, `;` у Windows). Вставляються в `sys.path` безпосередньо після `sys.path[0]`, але перед стандартною бібліотекою. |
| *(немає)* | `PYTHONHOME` | **Перевизначення префікса:** задає альтернативне розташування стандартної бібліотеки Python. Може містити один каталог `prefix` або пару `prefix:exec_prefix`. |
| `-v` | `PYTHONVERBOSE=1` | **Трасування імпорту:** виводить у потік `stderr` кожен крок сканування `sys.path`, ініціалізації `site.py`, виконання файлів `.pth` та пошуку модулів у файловій системі. |

## 6. Системні хуки sitecustomize та usercustomize

Модуль `site` підтримує два офіційні механізми глобальної ін'єкції коду в усі процеси Python, що запускаються в системі:

1. `sitecustomize.py`: Модуль, який шукається у всіх зареєстрованих каталогах `site-packages`. Якщо файл знайдено, `site.py` імпортує його. Застосовується системними адміністраторами для встановлення глобальних налаштувань (наприклад, реєстрації системної телеметрії, конфігурації глобальних кодувань або додавання загальнокорпоративних шляхів до `sys.path`).
2. `usercustomize.py`: Модуль, який імпортується з каталогу користувача (`getusersitepackages()`). Дозволяє окремому розробнику автоматично завантажувати персональні налагоджувальні утиліти, профайлери або перевизначати поведінку середовища без зміни системних файлів і без згоди адміністратора хоста.

Обидва модулі завантажуються у захищеному блоці `try...except ImportError`, тому їхня відсутність у файловій системі є штатним станом і не призводить до збоїв запуску інтерпретатора.
