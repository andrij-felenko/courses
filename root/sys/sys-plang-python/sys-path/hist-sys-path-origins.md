# 📜 Еволюція пошуку шляхів у CPython: від жорстких констант до getpath.py

Пошук модулів у ранніх версіях Python (0.9.1–1.4) спирався на жорстко зашиті шляхи компіляції мови C та примітивне зчитування змінної оточення `PYTHONPATH`. Коли інтерпретатор запускався на робочій станції Unix, двійковий файл `python` містив статичні C-рядки на зразок `/usr/local/lib/python1.4`. Перенесення бінарного файлу в інший каталог або розгортання кількох незалежних версій мови на одній машині вимагало або повної перекомпіляції інтерпретатора з новими префіксами `make prefix=/opt/python`, або примусового експорту довгого ланцюжка шляхів у системному шелі.

З появою портів для платформ із принципово відмінною файловою структурою — Windows NT, OS/2, MS-DOS та класичної Mac OS — концепція статичних шляхів остаточно зайшла у глухий кут. Кожна операційна система вимагала власної логіки визначення кореневих каталогів: Windows спиралася на реєстр системних ключів `HKEY_LOCAL_MACHINE\Software\Python`, Mac OS використовувала ресурси Finder, а Unix орієнтувався на структуру каталогів відносно розташування виконуваного файлу `argv[0]`.

## 1. Поява site.py та файлів конфігурації .pth (Python 1.5)

У 1997–1998 роках під час підготовки релізу Python 1.5 Гвідо ван Россум (Guido van Rossum) та Марк-Андре Лембург (Marc-André Lemburg) реалізували концептуальний поділ: ядро інтерпретатора мало відповідати лише за базову стандартну бібліотеку, тоді як реєстрація сторонніх модулів повинна була виконуватися динамічно на рівні мови Python.

Так з'явився системний модуль `site.py`. Інтерпретатор автоматично завантажував цей модуль під час старту, якщо користувач явно не вимикав його прапорцем `-S`. Модуль `site.py` визначав каталог `site-packages` на основі `sys.prefix` і сканував його на наявність спеціальних файлів із розширенням `.pth` (Path Configuration Files).

```
/usr/local/lib/python1.5/
├── os.py
├── site.py                 [Автоматичний запуск під час старту]
└── site-packages/          [Каталог сторонніх пакунків]
    └── numeric.pth         [Вміст: /opt/numeric-1.0]
```

Файли `.pth` розв'язали критичну проблему ранньої екосистеми: великі розширення (наприклад, `Numeric` — попередник `NumPy`) могли встановлюватися у власні ізольовані дерева каталогів, а в системний `site-packages` додавався лише текстовий маркерний файл розміром у кілька байтів. Це усунуло потребу ручного редагування системних змінних середовища чи скриптів запуску.

## 2. Імпорт із zip-архівів та протокол перехоплювачів (Python 2.3)

На початку 2000-х років розвиток корпоративних систем та вбудованих пристроїв висунув нову вимогу: можливість постачання застосунків разом з усіма залежностями у вигляді єдиного zip-архіву без розпакування на диск. Стандартна функція ядра CPython `import` працювала виключно з реальними системними викликами POSIX `stat()` та `open()`, що унеможливлювало пошук модулів усередині архівів.

У релізі Python 2.3 було прийнято два фундаментальні стандарти:
1. [PEP 273](https://peps.python.org/pep-0273/) («Import Modules from Zip Archives») — реалізація вбудованого C-модуля `zipimport`.
2. [PEP 302](https://peps.python.org/pep-0302/) («New Import Hooks») — розширення протоколу імпорту через списки `sys.meta_path` та `sys.path_hooks`.

Завдяки PEP 302 список `sys.path` перестав бути просто списком каталогів файлової системи. Елементом `sys.path` тепер міг бути шлях до довільного zip-файлу (`/opt/app/bundle.zip/lib`). При проходженні по `sys.path` підсистема імпорту опитувала зареєстровані обробники в `sys.path_hooks` (зокрема `zipimporter`), а результати кешувала у словнику `sys.path_importer_cache`. Це заклало фундамент для сучасних пакувальників виконуваних файлів та віртуальних файлових систем.

```
sys.path = ['/app/bundle.zip/lib', '/usr/lib/python2.3']
   ↓
sys.path_hooks = [zipimporter, ...]
   ↓
sys.path_importer_cache['/app/bundle.zip/lib'] = <zipimporter object>
```

## 3. Ізоляція середовищ без дублювання бінарників (Python 3.3)

До версії Python 3.3 створення ізольованих середовищ спиралося на сторонню утиліту `virtualenv`. Її механізм полягав у фізичному копіюванні або створенні символічних посилань на двійковий файл інтерпретатора `python` та базову бібліотеку в локальний каталог проєкту. Це створювало численні збої при оновленні системного інтерпретатора або зміні прав доступу.

13 червня 2011 року Карл Меєр (Carl Meyer) запропонував [PEP 405](https://peps.python.org/pep-0405/) («Python Virtual Environments»), який став частиною ядра Python 3.3 під назвою `venv`. Стандарт змінив сам алгоритм розрахунку `sys.prefix`:

```
sys.executable (/home/user/project/.venv/bin/python)
   ↓ (пошук вгору по дереву каталогів)
Знайдено маркерний файл /home/user/project/.venv/pyvenv.cfg
   ↓
sys.prefix = "/home/user/project/.venv"
sys.base_prefix = "/usr" (зчитується з параметра home у pyvenv.cfg)
```

Замість копіювання мегабайтів коду стандартної бібліотеки інтерпретатор перемикав свій `sys.prefix` на каталог віртуального середовища, одночасно зберігаючи доступ до системних C-розширень через `sys.base_prefix`. Усі наступні кроки — формування базового `sys.path`, запуск `site.py` та пошук `site-packages` — автоматично спрямовувалися в ізольований каталог віртуального середовища `.venv`.

## 4. Стандартизація структури конфігурації PEP 587 (Python 3.8)

Попри всі покращення, до версії 3.8 початковий розрахунок шляхів у мові C залишався вразливим. Глобальні C-змінні `Py_SetPythonHome()`, `Py_SetPath()`, `Py_NoSiteFlag` та `Py_IgnoreEnvironmentFlag` ініціалізувалися хаотично. Якщо C/C++ застосунок вбудовував інтерпретатор Python (Embedding) і модифікував ці змінні з різних потоків, виникали стани гонитви, пошкодження пам'яті та спотворення кодувань шляхів Unicode при перемиканні системної локалі `LC_CTYPE`.

Віктор Стіннер (Victor Stinner) розробив [PEP 587](https://peps.python.org/pep-587/) («Python Initialization Configuration»), який повністю перебудував запуск CPython. Усі глобальні змінні було зібрано в атомарні структури `PyPreConfig` та `PyConfig`. Розрахунок шляхів пошуку отримав чітку ізольовану структуру `_PyPathConfig` та детермінований інтерфейс валідації. Завдяки цьому вбудовані інтерпретатори отримали змогу явно задавати `config.module_search_paths` у пам'яті C, повністю блокуючи непередбачуване зчитування системних каталогів та змінних середовища хостової системи.

## 5. Великий рефакторинг: від getpath.c до getpath.py (Python 3.11)

Найрадикальніша зміна у формуванні `sys.path` відбулася в релізі Python 3.11 (2022 рік). Протягом понад 25 років розрахунок початкових шляхів виконувався низькорівневим файлом `Modules/getpath.c` (та його платформозалежними двійниками `PC/getpathp.c` для Windows). Цей код був перевантажений складними макросами `#ifdef`, ручним керуванням пам'яттю `malloc`/`free` для масивів `wchar_t*` та численними системними викликами `readlink()`, `GetModuleFileNameW()` та `stat()`. Підтримка цього коду стала однією з найважчих інженерних задач у репозиторії CPython.

У межах масштабного рефакторингу логіку пошуку шляхів переписали на чистій мові Python у файлі `Modules/getpath.py`. Під час збирання CPython цей скрипт компілюється в байткод і вбудовується безпосередньо в бінарний образ інтерпретатора як заморожений модуль (`frozen module`).

```
Збирання CPython (Build time):
  Modules/getpath.py → Байткод → C-масив у Python/frozen_modules/getpath.h

Старт інтерпретатора (Runtime):
  PyConfig_Read()
    → _PyConfig_InitPathConfig()
      → Виконання замороженого байткоду getpath.py у мінімальному середовищі
        → Повернення структури шляхів у C-структуру PyConfig
```

Заморожений модуль `getpath.py` виконується на найбільш ранньому етапі старту віртуальної машини, коли ще не доступні ні файлова система, ні повноцінний механізм імпорту. Він отримує інформацію про середовище процесу через словник системних змінних і конструює точний список шляхів стандартної бібліотеки, гарантуючи абсолютно ідентичну поведінку алгоритму на всіх підтримуваних операційних системах.
