Коли інтерпретатор CPython виконує інструкцію `import math` або байткод-опокод `IMPORT_NAME`, підсистема імпорту звертається до ланцюжка об'єктів у списку `sys.meta_path`. Головний файловий шукач середовища (`PathFinder`) не сканує всю файлову систему операційної системи; натомість він послідовно ітерується по впорядкованому списку рядкових шляхів, збережених у системному списку `sys.path`. Якщо каталог із файлом `math.py` або скомпільованим двійковим розширенням опиняється у цьому списку раніше за каталог стандартної бібліотеки, інтерпретатор завантажує знайдений файл і зв'язує його з глобальним простором імен модуля. Вміст і точний порядок елементів у `sys.path` не є статичною константою, зашитою в бінарний образ: вони динамічно конструюються під час запуску процесу через послідовний шестиетапний алгоритм, що об'єднує аргументи командного рядка, системні змінні середовища, евристичний пошук файлів-орієнтирів на диску та виконання системного модуля `site.py`.

## 1. Анатомія sys.path у пам'яті CPython

На рівні двійкового інтерфейсу ядра CPython список `sys.path` є стандартним мутабельним об'єктом мови Python типу `PyListObject`. Під час ініціалізації інтерпретатора структура `PyInterpreterState` створює словник системного модуля `sys` (`interp->sysdict`), куди додається посилання на цей список під ключем `"path"`.

```
PyInterpreterState
  └── interp->sysdict ("sys" module dictionary)
        └── "path" ──→ PyListObject (sys.path)
                         ├── [0] = "/home/user/project"
                         ├── [1] = "/usr/lib/python312.zip"
                         ├── [2] = "/usr/lib/python3.12"
                         ├── [3] = "/usr/lib/python3.12/lib-dynload"
                         └── [4] = "/usr/lib/python3.12/site-packages"
```

Оскільки `sys.path` реалізовано як звичайний динамічний масив покажчиків мови C (`PyObject**`), програма на Python може модифікувати його безпосередньо під час виконання: викликати методи `append()`, `insert()`, `extend()`, видаляти елементи через `pop()` або повністю перепризначати зрізи списку.

Однак `sys.path` не функціонує в ізоляції. Для оптимізації дискового введення-виведення інтерпретатор пов'язує його з двома додатковими підсистемами:

1. **`sys.path_hooks`:** Список об'єктів-фабрик (Callables), які перетворюють рядковий шлях на екземпляр шукача (Finder). За замовчуванням список містить обробник `zipimport.zipimporter`.
2. **`sys.path_importer_cache`:** Системний словник, що кешує створені екземпляри імпортерів для кожного унікального рядка шляху. Якщо для певного каталогу на диску вже створено об'єкт `FileFinder`, наступні інструкції імпорту не здійснюють повторних перевірок файлової системи за допомогою системного виклику `stat()`, а використовують кешований об'єкт шукача.

Коли прикладний код змінює вміст `sys.path` під час виконання, словник `sys.path_importer_cache` автоматично не очищається для видалених чи замінених каталогів, що може спричиняти розсинхронізацію між реальним станом дисків та внутрішнім кешем інтерпретатора.

Історичний шлях розвитку механізмів виявлення шляхів — від простих жорстко скомпільованих рядків у CPython 1.0 до сучасного модульного бутстрапу — докладно описано у вставці [Еволюція пошуку шляхів у CPython: від жорстких констант до getpath.py](root:sys-plang-python/sys-path/hist-sys-path-origins.md).

## 2. Шість етапів розрахунку шляхів під час старту

Побудова списку `sys.path` відбувається під час фази ініціалізації ядра за стандартом PEP 587 через виконання функції `PyConfig_Read()`. Алгоритм об'єднує шість незалежних джерел конфігурації у суворо визначеному порядку пріоритету.

![Шість послідовних етапів розрахунку та наповнення sys.path](/root/sys/sys-plang-python/sys-path/img/sys-path-resolution-pipeline.svg)
*Шість етапів формування списку каталогів sys.path від аргументів командного рядка до користувацьких пакетів.*

### Етап 1: Визначення точки входу (sys.path[0])

Перший елемент списку `sys.path[0]` визначає найвищий пріоритет під час пошуку імпортованих файлів. Його значення встановлюється залежно від режиму виклику двійкового файлу `python`:

1. **Режим прямого виконання скрипту (`python /path/to/app/main.py`):**
   Інтерпретатор витягує шлях до цільового файлу з аргументу `argv[1]`, розкриває можливі символічні посилання та вираховує його абсолютний батьківський каталог за допомогою системного виклику `realpath()`. Елемент `sys.path[0]` отримує значення `"/path/to/app"`. При цьому поточний робочий каталог термінала (`cwd`), з якого було викликано команду, повністю ігнорується.
2. **Режим запуску модуля через ключ `-m` (`python -m app.main`):**
   Інтерпретатор ініціалізує `sys.path[0]` значенням поточного робочого каталогу процесу (`os.getcwd()`). Це гарантує, що кореневий пакет `app` буде знайдено як модуль верхнього рівня безпосередньо у робочому каталозі.
3. **Режим інтерактивного REPL, передачі коду через `-c` або читання зі `stdin`:**
   Елемент `sys.path[0]` ініціалізується порожнім рядком `""`. У термінах файлового пошуку CPython порожній рядок інтерпретується як динамічний поточний каталог процесу в момент кожного окремого виклику `import`. Якщо процес у процесі роботи змінює робочий каталог через `os.chdir()`, пошук модулів автоматично перемикається на новий каталог.
4. **Режим безпечного шляху (`python -P` або `PYTHONSAFEPATH=1`):**
   Інтерпретатор примусово блокує додавання потенційно небезпечного каталогу скрипту чи робочого каталогу на початок списку. Список `sys.path` починається безпосередньо зі стандартної бібліотеки або шляхів `PYTHONPATH`.

### Етап 2: Змінна середовища PYTHONPATH

Якщо інтерпретатор не запущено в ізольованому режимі (без прапорців `-E` або `-I`), CPython зчитує системну змінну оточення `PYTHONPATH`.

Змінна містить перелік шляхів, розділених платформозалежним роздільником `os.pathsep` (`:` у Unix/Linux/macOS та `;` у Windows):

```
export PYTHONPATH="/opt/company_lib:/opt/shared_utils"
```

CPython розбиває рядок за роздільником, перетворює кожен шлях на абсолютний формат і вставляє їх у список `sys.path` одразу після елемента `sys.path[0]`, але **до** каталогів стандартної бібліотеки. Завдяки цій позиції записи з `PYTHONPATH` мають вищий пріоритет над вбудованими системними модулями мови Python, що дозволяє підміняти компоненти стандартної бібліотеки за потреби.

### Етап 3: Визначення префіксів та стандартна бібліотека (Landmarks)

На третьому етапі алгоритм пошуку шляхів `_PyPathConfig` (у версіях Python 3.11+ реалізований як заморожений байткод-модуль `Modules/getpath.py`) визначає фізичне розташування стандартної бібліотеки.

Алгоритм використовує метод пошуку орієнтирів (Landmark Search):
1. Починаючи від каталогу виконуваного двійкового файлу `sys.executable`, алгоритм піднімається вгору по дереву файлової системи і перевіряє наявність конфігураційного маркерного файлу `pyvenv.cfg`.
2. Якщо файл `pyvenv.cfg` знайдено, каталог оголошується префіксом віртуального середовища (`sys.prefix`), а базовий системний каталог `sys.base_prefix` зчитується з поля `home`.
3. Якщо файл `pyvenv.cfg` відсутній, інтерпретатор шукає каталог стандартної бібліотеки за наявністю характерного орієнтира — файлу `os.py` або скомпільованого бінарного каталогу `lib-dynload`.

Після визначення префіксів до `sys.path` послідовно додаються три системні компоненти:

```
[1] prefix/lib/pythonXY.zip              (якщо zip-архів існує на диску)
[2] prefix/lib/pythonX.Y                 (каталог чистої стандартної бібліотеки)
[3] exec_prefix/lib/pythonX.Y/lib-dynload (каталог скомпільованих C-розширень .so/.pyd)
```

### Етап 4: Запуск модуля site.py та каталоги site-packages

Якщо під час запуску не було передано прапорець `-S`, CPython автоматично виконує інструкцію `import site`. Головна функція `site.main()` обчислює розташування глобальних каталогів сторонніх пакунків (`site-packages`) для поточного префікса:

- У POSIX/Linux: `/usr/local/lib/pythonX.Y/site-packages` та `/usr/lib/pythonX.Y/site-packages`.
- У Debian/Ubuntu (системний Python): `/usr/local/lib/pythonX.Y/dist-packages` та `/usr/lib/pythonX.Y/dist-packages`.
- У Windows: `C:\PythonXY\Lib\site-packages`.
- У віртуальному середовищі `venv`: `/path/to/.venv/lib/pythonX.Y/site-packages`.

Для кожного знайденого каталогу викликається функція `site.addsitedir()`. Вона перевіряє наявність каталогу на диску, нормалізує його шлях, додає в кінець списку `sys.path` та ініціює сканування конфігураційних файлів `.pth`.

### Етап 5: Обробка конфігураційних файлів .pth

Під час виконання `site.addsitedir()` модуль `site` виконує пошук усіх файлів із розширенням `.pth` всередині каталогу `site-packages`. Файли сортуються в алфавітному порядку і зчитуються построково:

1. **Рядки каталогів:** Якщо рядок містить абсолютний або відносний шлях до каталогу (і цей каталог існує), він додається до `sys.path`. Відносні шляхи розраховуються відносно розташування самого `.pth` файлу.
2. **Рядки виконання:** Якщо рядок починається зі слова `import ` або `import\t`, увесь залишок рядка передається у функцію `exec()`. Це дозволяє пакетам динамічно налаштовувати середовище, встановлювати хуки або реєструвати шукачі імпорту. Оскільки і те, і інше відбувається мовчки й до першого рядка застосунку, варто вміти [покроково простежити, який саме файл `.pth` що додав до `sys.path` і який рядок виконав](root:sys-plang-python/sys-path/proj-pth-trace-and-hook.md).

Повну граматику файлів `.pth`, специфікацію функцій модуля `site` та роботу розробницьких встановлень за стандартом PEP 660 наведено у вставці [Контракт модуля site, специфікація .pth та змінні оточення sys.path](root:sys-plang-python/sys-path/api-site-and-pth.md).

### Етап 6: Користувацькі каталоги (User Site) та системні хуки

Якщо константа `site.ENABLE_USER_SITE` є істинною (не передано прапорець `-s` чи `-I` і відсутня змінна `PYTHONNOUSERSITE=1`), модуль `site` викликає `site.addusersitepackages()`.

Функція розраховує шлях до ізольованого каталогу поточного користувача:
- Linux/macOS: `~/.local/lib/pythonX.Y/site-packages`
- Windows: `%APPDATA%\Python\PythonXY\site-packages`

Каталог користувача додається до `sys.path` після системних каталогів `site-packages`. Завдяки цьому звичайний користувач без прав адміністратора `root` може встановлювати пакунки за допомогою команди `pip install --user package_name`.

Наприкінці ініціалізації `site.py` послідовно намагається імпортувати два файли конфігурації:
1. `sitecustomize.py` — глобальний системний конфігураційний модуль для всіх користувачів хоста.
2. `usercustomize.py` — персональний модуль користувача, розташований у його `user-site` каталозі.

Після завершення роботи `site.py` список `sys.path` набуває свого остаточного стартового вигляду.

## 3. Точки входу: python script.py проти python -m module

Одним із найпоширеніших джерел помилок імпорту в реальних проєктах є плутанина між запуском файлу як прямого скрипту та запуском у режимі модуля через прапорець `-m`.

Розглянемо типову структуру проєкту:

```
/home/user/project/
├── app/
│   ├── __init__.py
│   ├── main.py
│   └── database.py
└── tests/
    └── test_db.py
```

Усередині файлу `app/main.py` розробник використовує абсолютний імпорт `import app.database` або відносний імпорт `from . import database`.

![Порівняння станів середовища та sys.path[0] у режимах script та module](/root/sys/sys-plang-python/sys-path/img/script-vs-module-mode.svg)
*Різниця ініціалізації sys.path[0] та простору імен при прямому запуску файлу та запуску через ключ -m.*

### Сценарій 1: Прямий запуск файлу (python app/main.py)

Користувач перебуває в каталозі `/home/user/project` і запускає команду:

```bash
python app/main.py
```

Під час старту інтерпретатор встановлює параметри:
- `sys.path[0]` = `"/home/user/project/app"` (каталог самого скрипту).
- `__name__` = `"__main__"`.
- `__package__` = `""` або `None` (інтерпретатор не знає, що файл належить до пакета `app`).

**Наслідки для підсистеми імпорту:**
1. Інструкція `from . import database` завершується фатальною помилкою:
   `ImportError: attempted relative import with no known parent package`.
   Оскільки `__package__` не встановлено, CPython не має контексту батьківського пакета для виконання відносного імпорту.
2. Інструкція `import app.database` завершується помилкою:
   `ModuleNotFoundError: No module named 'app'`.
   Шукач `PathFinder` шукає папку `app` у каталогах `sys.path`. Оскільки в `sys.path[0]` записано каталог `/home/user/project/app`, інтерпретатор шукає шлях `/home/user/project/app/app/`, якого не існує. Каталог `/home/user/project` взагалі відсутній у `sys.path`.
3. Працюватиме лише прямий імпорт `import database`, який зв'язує модуль як модуль верхнього рівня, руйнуючи модульну структуру кодової бази при подальшому масштабуванні.

### Сценарій 2: Запуск модуля через ключ -m (python -m app.main)

Користувач запускає ту саму програму як модуль:

```bash
python -m app.main
```

Інтерпретатор налаштовує середовище принципово інакше:
- `sys.path[0]` = `"/home/user/project"` (поточний робочий каталог `cwd`).
- `__name__` = `"__main__"`.
- `__package__` = `"app"` (інтерпретатор явно знає, що модуль виконується всередині пакета `app`).

**Наслідки для підсистеми імпорту:**
1. Інструкція `from . import database` виконується успішно: CPython бачить `__package__ == "app"` і коректно резолвить модуль як `app.database`.
2. Інструкція `import app.database` виконується успішно: шукач бере `sys.path[0]` (`/home/user/project`), знаходить у ньому папку `app`, перевіряє наявність `__init__.py` і завантажує вкладений файл.

Зведена таблиця станів середовища для обох режимів:

| Властивість середовища | Режим скрипту: `python path/to/script.py` | Режим модуля: `python -m pkg.script` |
|---|---|---|
| Значення `sys.path[0]` | Абсолютний каталог скрипту (`/proj/path/to`) | Поточний робочий каталог виклику (`/proj`) |
| Значення `__name__` | `"__main__"` | `"__main__"` |
| Значення `__package__` | `None` або `""` | `"pkg"` (повне ім'я батьківського пакета) |
| Значення `__file__` | Абсолютний або відносний шлях до файлу | Повний абсолютний шлях до файлу |
| Відносні імпорти (`from . import x`) | Заборонені (`ImportError`) | Дозволені та коректно резолвляться |
| Абсолютні імпорти кореня (`import pkg.x`) | Падають (`ModuleNotFoundError`) | Працюють через кореневий `sys.path[0]` |

## 4. Колізії імен та затінення модулів (Module Shadowing)

Затінення модулів (Module Shadowing) — це критичний стан підсистеми імпорту, коли локальний файл або сторонній пакет перехоплює ім'я іншого модуля через вищий пріоритет власного каталогу в списку `sys.path`.

![Схема колізії імен та перехоплення імпорту локальним файлом](/root/sys/sys-plang-python/sys-path/img/module-shadowing-conflict.svg)
*Механізм виникнення колізії імен та аварійного завершення внутрішніх імпортів стандартної бібліотеки через пріоритет sys.path[0].*

### Анатомія колізії зі стандартною бібліотекою

Найнебезпечніший випадок затінення виникає, коли розробник створює тестовий або навчальний файл, ім'я якого збігається з модулем стандартної бібліотеки.

Розглянемо випадок створення файлу `math.py` у робочому каталозі проєкту:

```
/home/user/workspace/
├── math.py
└── main.py
```

Вміст файлу `main.py`:

```python
import random

print(random.randint(1, 100))
```

Розробник запускає програму: `python main.py`. У коді `main.py` немає жодної згадки файлу `math.py`. Проте виконання завершується аварією:

```
Traceback (most recent call last):
  File "/home/user/workspace/main.py", line 1, in <module>
    import random
  File "/usr/lib/python3.12/random.py", line 47, in <module>
    import math as _math
AttributeError: partially initialized module 'math' has no attribute 'sqrt' (most likely due to a circular import)
```

**Механізм збою:**
1. Оскільки `main.py` запущено як скрипт, `sys.path[0]` стає `/home/user/workspace`.
2. Інструкція `import random` ініціює завантаження системного модуля `/usr/lib/python3.12/random.py`.
3. Усередині свого вихідного коду модуль `random.py` виконує інструкцію `import math as _math`, щоб використовувати математичні функції `sqrt` та `log`.
4. Шукач `PathFinder` починає пошук модуля `math` зі списку `sys.path`.
5. Першим у списку стоїть каталог `sys.path[0]`, у якому лежить локальний файл `math.py`.
6. Інтерпретатор завантажує локальний порожній файл `math.py` замість системного C-розширення `math.cpython-312-x86_64-linux-gnu.so` з каталогу `lib-dynload`.
7. Коли `random.py` намагається звернутися до функції `_math.sqrt()`, виникає `AttributeError`, оскільки в локальному файлі ця функція відсутня.

Подібні приховані збої викликають імена файлів, що перекривають критичні системні модулі:
- `test.py` — ламає стандартну бібліотеку тестування `unittest` та внутрішні модулі CPython.
- `json.py` — ламає роботу HTTP-клієнтів (`requests`, `urllib`), парсерів та логерів.
- `string.py` / `types.py` / `io.py` — ламають сам бутстрап більшості сторонніх бібліотек під час їхнього імпорту.
- `email.py` — ламає розбір MIME-заголовків у вебсерверах та бібліотеці `urllib`.

### Затінення сторонніх пакетів (Third-Party Shadowing)

Аналогічна проблема виникає, коли локальна папка в корені проєкту має назву, ідентичну сторонньому пакету з `site-packages`. Якщо в проєкті створено каталог `requests/` для власних обробників запитів, інструкція `import requests` завантажить локальний каталог замість встановленої через `pip` однойменної бібліотеки.

Для автоматичного пошуку та аудиту колізій простору імен розроблено діагностичний інструмент, наведений у вставці [Аудит sys.path та автоматичне виявлення затінення модулів](root:sys-plang-python/sys-path/proj-shadow-detector.md).

## 5. Механіка розв'язання шляхів у PathFinder та пакети просторів імен

Коли `sys.meta_path` передає запит шукачу `PathFinder`, останній виконує структурований алгоритм пошуку специфікації модуля (`ModuleSpec`).

### Алгоритм ітерації PathFinder

Нехай шукається модуль із повним іменем `pkg.submod`. Якщо модуль верхнього рівня `pkg` уже імпортовано, пошук `submod` обмежується списком `pkg.__path__`. Якщо ж шукається модуль верхнього рівня `foo`, шукач використовує глобальний список `sys.path`.

Послідовність перевірок для кожного каталогу `entry` зі списку `sys.path`:

```
1. Отримання Finder з sys.path_importer_cache[entry]
   ├─ Немає в кеші → Ітерація по sys.path_hooks
   └─ Повертає FileFinder(entry)

2. FileFinder послідовно перевіряє наявність на диску:
   ├─ entry / "foo.cpython-312-x86_64-linux-gnu.so" (C-розширення)
   ├─ entry / "foo.py"                             (Вихідний файл Python)
   ├─ entry / "foo.pyc"                            (Байткод-кеш)
   ├─ entry / "foo" / "__init__.py"                (Звичайний пакет)
   └─ entry / "foo" (каталог без __init__.py)      (Кандидат у Namespace Package)
```

Якщо `FileFinder` знаходить C-розширення, файл `.py` або каталог із `__init__.py`, ітерація негайно зупиняється, а знайдений файл повертається як остаточна специфікація модуля.

### Пакети просторів імен (PEP 420 Namespace Packages)

Якщо каталог `foo` існує, але не містить файлу `__init__.py`, `PathFinder` не зупиняє роботу. Відповідно до стандарту PEP 420 («Implicit Namespace Packages»), один логічний пакет може бути розподілений між кількома незалежними каталогами на диску (наприклад, плагіни, встановлені в різні підкаталоги `site-packages`).

У цьому випадку шукач продовжує сканування решти елементів `sys.path`. Усі знайдені фізичні каталоги `entry_i / "foo"` об'єднуються у спеціальний ітерований об'єкт `_NamespacePath`. Коли імпортується вкладений модуль `foo.bar`, пошук виконуватиметься по черзі в усіх зібраних частинах простору імен.

## 6. Безпека: вразливості sys.path[0] та прапорець -P (PEP 686)

Наявність поточного каталогу в `sys.path[0]` становить суттєвий безпековий ризик у багатокористувацьких системах, серверах автоматизації та середовищах із підвищеними привілеями.

### Вектор атаки: підміна модуля через CWD (Current Working Directory Injection)

Розглянемо випадок системного адміністратора, який запускає утиліту обслуговування з правами суперкористувача:

```bash
cd /tmp/shared_uploads
sudo python3 /usr/local/bin/cleanup_tool.py
```

Якщо скрипт `cleanup_tool.py` виконує інструкцію `import shutil`, а зловмисник попередньо створив у каталозі `/tmp/shared_uploads` шкідливий файл `shutil.py`, поведінка процесу залежить від способу виклику:
- Якщо скрипт запущено через `python /usr/local/bin/cleanup_tool.py`, `sys.path[0]` стає `/usr/local/bin`. Якщо права на цей каталог захищені, атака зазнає невдачі.
- Якщо ж скрипт викликається через обгортку, яка використовує `python -m`, або виконується в інтерактивному режимі чи через середовище планувальника з `sys.path[0] = ""`, інтерпретатор завантажить `/tmp/shared_uploads/shutil.py` з правами `root`, що призводить до повної компрометації операційної системи.

### Захист через прапорець -P та PYTHONSAFEPATH

Для усунення цього класу вразливостей у версії Python 3.11 було запроваджено прапорець командного рядка `-P` та відповідну змінну середовища `PYTHONSAFEPATH=1`:

```bash
python3 -P /usr/local/bin/cleanup_tool.py
```

При активації цього режиму CPython повністю вилучає небезпечний `sys.path[0]` з початкової конфігурації. У списку пошуку залишаються виключно довірені системні префікси стандартної бібліотеки та глобальні каталоги `site-packages`.

## 7. Розрахунок орієнтирів у getpath.py (Python 3.11+)

Починаючи з версії Python 3.11, уся низькорівнева логіка визначення системних шляхів виконується всередині спеціального замороженого байткод-модуля `Modules/getpath.py`.

Цей модуль запускається у мінімальному середовищі бутстрапу, де ще недоступні модуль `os`, функції введення-виведення та повноцінний інтерпретатор. Для роботи `getpath.py` ядро CPython надає словник вихідних констант процесу та набір базових C-примітивів:

```
Вхідні параметри (config_dict):
  • "executable"       → "/home/user/project/.venv/bin/python3"
  • "prefix"           → NULL (потребує розрахунку)
  • "exec_prefix"      → NULL
  • "base_prefix"      → NULL
  • "pythonpath"       → Значення змінної PYTHONPATH або NULL
  • "home"             → Значення змінної PYTHONHOME або NULL
```

### Алгоритм дослідження орієнтирів (Landmark Probing)

Модуль `getpath.py` виконує три послідовні кроки евристичного аналізу:

```
Крок 1: Пошук pyvenv.cfg
  Перевірка каталогів від dirname(executable) вгору:
  ├── /home/user/project/.venv/bin/pyvenv.cfg  → Ні
  └── /home/user/project/.venv/pyvenv.cfg      → ЗНАЙДЕНО!
      ├── Читання параметра "home = /usr/bin"
      ├── prefix = "/home/user/project/.venv"
      └── base_prefix = "/usr"

Крок 2: Пошук Landmark стандартної бібліотеки (якщо pyvenv.cfg немає)
  Перевірка відносних шляхів для кожного кандидата префікса:
  ├── <prefix>/lib/pythonX.Y/os.py            → Перевірка через _isfile()
  └── <prefix>/lib/pythonX.Y/lib-dynload      → Перевірка через _isdir()

Крок 3: Конструювання списку module_search_paths
  1. Додавання zip-архіву: <prefix>/lib/pythonXY.zip
  2. Додавання PYTHONPATH (якщо use_environment == 1)
  3. Додавання stdlib: <prefix>/lib/pythonX.Y
  4. Додавання розширень: <exec_prefix>/lib/pythonX.Y/lib-dynload
```

Результат роботи `getpath.py` повертається назад у C-структуру `PyConfig`, яка передає розрахований список у фінальну функцію ініціалізації ядра.

## 8. Керування шляхами: антипатерни та інженерні практики

Пряма мутація `sys.path` у вихідному коді застосунків є поширеною, але вкрай небезпечною практикою, що порушує детермінізм середовища виконання.

### Чому sys.path.append() та sys.path.insert(0, ...) — антипатерни

У кодових базах часто зустрічається фрагмент:

```python
import sys
import os
# Додавання батьківського каталогу для доступу до сусідніх модулів
sys.path.insert(0, os.path.abspath(os.path.join(os.path.dirname(__file__), "..")))
```

Цей підхід має низку системних дефектів:

1. **Мутація глобального стану процесу:** Зміна `sys.path` впливає на всі наступні інструкції `import` у межах усього процесу CPython, включно з сторонніми бібліотеками, сторонніми потоками та асинхронними завданнями.
2. **Залежність від порядку виконання:** Якщо модуль `A` викликає `sys.path.insert(0, ...)`, а модуль `B` імпортується після модуля `A`, модуль `B` отримує змінені правила пошуку залежностей. Якщо змінити порядок імпортів на початку файлу, поведінка застосунку непередбачувано зміниться.
3. **Руйнування статичного аналізу (IDE, Linters, Type Checkers):** Інструменти статичної типізації (`mypy`, `pyright`) та середовища розробки (VS Code, PyCharm) аналізують код без його фізичного виконання. Вони не виконують виклики `sys.path.insert()`, тому маркують валідні імпорти як помилкові (`Unresolved import`).
4. **Неконтрольоване затінення:** Виклик `sys.path.insert(0, ...)` поміщає довільний каталог на першу позицію перед стандартною бібліотекою, що створює ризик раптового перехоплення системних модулів.

### Правильні підходи до керування шляхами

Замість ручної модифікації `sys.path` сучасна інженерна практика спирається на стандартизовані інструменти організації проєктів:

#### 1. Використання структури src-layout

Розташування вихідного коду всередині каталогу `src/` захищає розробника від випадкового затінення:

```
my_project/
├── pyproject.toml
├── src/
│   └── my_package/
│       ├── __init__.py
│       └── core.py
└── tests/
    └── test_core.py
```

Коли розробник запускає тести чи скрипти з кореневого каталогу `/home/user/my_project`, поточний каталог `sys.path[0]` містить лише `pyproject.toml` та каталог `src/`. Оскільки всередині немає модуля `my_package.py`, небезпека прямого затінення відсутня.

#### 2. Розробницьке встановлення (Editable Installs за PEP 660)

Щоб зробити пакет доступним для всієї системи без постійної ручної зміни шляхів, використовують віртуальне середовище `venv` та команду розробницького встановлення:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e .
```

Менеджер `pip` реєструє файл `.pth` у каталозі `.venv/lib/pythonX.Y/site-packages/`. Інтерпретатор автоматично додає шлях до `src/` у кінець `sys.path` під час кожного старту процесу через штатний механізм `site.py`.

#### 3. Контроль через PYTHONPATH у тестах та контейнерах

Якщо виникає потреба підключити спільні бібліотеки без їх інсталяції в середовище (наприклад, під час запуску тестів у CI/CD або всередині Docker-контейнера), конфігурацію виконують на рівні процесу до старту інтерпретатора:

```bash
export PYTHONPATH="/workspace/src"
pytest tests/
```

## 9. Трасування та діагностика пошуку шляхів

Коли виникає складна помилка імпорту або підозра на затінення модулів, CPython надає вбудовані засоби трасування розрахунку шляхів та файлових звернень.

### 1. Трасування через прапорець -v (Verbose Mode)

Запуск інтерпретатора з ключем `-v` (або подвійним `-vv` / змінною `PYTHONVERBOSE=1`) змушує підсистему імпорту виводити в `stderr` детальне повідомлення про кожен перевірений каталог, спробу завантаження файлу `.pyc` та виконання файлів `.pth`:

```bash
python3 -v -c "import math" 2>&1 | grep "math"
```

Вивід показує точне джерело файлу, з якого було завантажено модуль:

```
# /usr/lib/python3.12/lib-dynload/math.cpython-312-x86_64-linux-gnu.so matches /usr/lib/python3.12/lib-dynload/math.cpython-312-x86_64-linux-gnu.so
# code object from /usr/lib/python3.12/lib-dynload/math.cpython-312-x86_64-linux-gnu.so
import 'math' # <_frozen_importlib_external.ExtensionFileLoader object at 0x7f8b9c>
```

### 2. Програмна інспекція походження завантажених модулів

Під час виконання програми точне фізичне розташування кожного завантаженого модуля можна визначити через його атрибут `__file__` або властивість специфікації `__spec__.origin`:

```python
import sys
import math
import random

def inspect_module_origins():
    print(f"sys.path[0]: {sys.path[0]}")
    for name in ["math", "random", "os", "sys"]:
        if name in sys.modules:
            mod = sys.modules[name]
            origin = getattr(mod, "__file__", None) or getattr(getattr(mod, "__spec__", None), "origin", "built-in")
            print(f"Модуль '{name}': origin = {origin}")

inspect_module_origins()
```

## 10. Внутрішня реалізація CPython: структура PyConfig

У низькорівневому C API запуск інтерпретатора та розрахунок списку шляхів повністю інкапсульовано у структурі `PyConfig`.

Структура містить спеціальні поля для керування шляхами пошуку модулів:

```text
typedef struct {
    int isolated;                   /* Режим повної ізоляції */
    int use_environment;            /* Зчитування змінних PYTHONPATH/PYTHONHOME */
    int safe_path;                  /* Прапорець -P (заборона CWD у sys.path[0]) */
    int site_import;                /* Прапорець -S (дозвіл завантаження site.py) */
    
    wchar_t *home;                  /* Каталог PYTHONHOME */
    wchar_t *program_name;          /* Ім'я програми argv[0] */
    
    int module_search_paths_set;    /* Ознака явного завдання шляхів */
    PyWideStringList module_search_paths; /* Фізичний список шляхів для sys.path */
} PyConfig;
```

Якщо поле `module_search_paths_set` встановлено в значення `1`, функція `Py_InitializeFromConfig()` пропускає складний евристичний алгоритм пошуку орієнтирів (Landmark Search) і безпосередньо копіює рядки з масиву `config.module_search_paths` у створюваний список `sys.path`.

Нижче наведено приклад коду на C та ідіоматичному C++, що демонструє витягування розрахованих шляхів пошуку модулів під час ініціалізації середовища CPython:

:::tabs
```c
#define PY_SSIZE_T_CLEAN
#include <Python.h>
#include <stdio.h>
#include <wchar.h>

/* Витягування та друк розрахованого списку sys.path через структуру PyConfig */
int inspect_cpython_path_configuration(void) {
    PyStatus status;
    PyConfig config;
    PyConfig_InitPythonConfig(&config);

    /* Зчитування системної конфігурації з урахуванням оточення процесу */
    status = PyConfig_Read(&config);
    if (PyStatus_Exception(status)) {
        PyConfig_Clear(&config);
        return -1;
    }

    wprintf(L"Кількість розрахованих шляхів пошуку: %zu\n", config.module_search_paths.length);
    for (size_t i = 0; i < config.module_search_paths.length; i++) {

    }

    /* Звільнення виділених C-структур без запуску повного runtime */
    PyConfig_Clear(&config);
    return 0;
}
```

## 11. Терміни та етимологія

- **Шлях пошуку** (*search path*, англ. *path*, від давньоангл. *pæþ*, що походить від прагерманського *\*patha-* — стежка, протоптаний шлях, колія). У системному програмуванні — впорядкована послідовність каталогів файлової системи, які підсистема перевіряє для виявлення запитаного ресурсу.
- **Затінення** (*shadowing*, від англ. *shadow*, давньоангл. *sceadu*, прагерм. *\*skadwaz* — тінь, стан затемнення чи перекриття світла). Стан простору імен, коли об'єкт із вищим пріоритетом робить однойменний об'єкт із нижчим пріоритетом недосяжним.
- **Префікс** (*prefix*, від лат. *praefixus*, утвореного від *prae-* — попереду + *figere* — прикріплювати, встановлювати). Базовий каталог у файловій ієрархії, відносно якого розгортаються системні компоненти, виконувані файли та бібліотеки.
- **Орієнтир** (*landmark*, від давньоангл. *landmearc*, утвореного з *land* — земля + *mearc* — межа, мітка, знак кордону). Спеціальний характерний файл або каталог, наявність якого однозначно свідчить про тип та версію кореневої структури встановлення.
- **Колізія простору імен** (*namespace collision*, від лат. *collisio*, утвореного від дієслова *collidere*: *com-* — разом + *laedere* — ударяти, пошкоджувати). Ситуація, коли два незалежні програмні компоненти претендують на один і той самий ідентифікатор у межах одного контексту виконання.
