- [Конфлікти версій залежностей](root:sys-plang-python/dependency-conflicts) — виникнення несумісностей версій та проблема діамантової залежності (Diamond Dependency).
- [Метадані проєкту в pyproject.toml](root:sys-plang-python/pyproject-toml) — декларація прямих залежностей проєкту згідно з PEP 517, PEP 518 та PEP 621.
</preknowlist>

Коли інженер описує залежності програмного проєкту у маніфесті `pyproject.toml`, він фіксує абстрактний намір: «для виконання бізнес-логіки потрібні веб-фреймворк `fastapi >= 0.110.0` та бібліотека валідації `pydantic >= 2.0, < 3.0`». Якщо передати цей опис на іншу робочу станцію або запустити збірку через місяць на сервері безперервної інтеграції, стандартний інсталятор `pip` здійснить новий пошуковий запит до публічного репозиторію PyPI і завантажить найновіші доступні релізи. Проте за цей проміжок часу бібліотека `pydantic` могла випустити реліз `2.7.0`, який підтягує оновлений бінарний модуль `pydantic-core 2.18.1` зі зміненою семантикою обробки винятків або непередбаченою регресією у C-розширенні. Якщо транзитивна залежність другого чи третього рівня змінює свою внутрішню поведінку, програмний комплекс, який успішно проходив тестування вчора, зазнає аварійної зупинки під час промислового розгортання. Цей фундаментальний розрив між абстрактною декларацією вимог та детермінованим станом кінцевого середовища усувають файли-замки (Lock Files) — статичні, математично вивірені та криптографічно верифіковані зрізи повного графа залежностей.

## 1. Проблема відтворюваності та транзитивний дрейф

Головною перешкодою для досягнення абсолютної відтворюваності збірок (Reproducible Builds) у динамічних екосистемах є багаторівнева топологія зв'язків між сторонніми модулями.

Будь-який сучасний програмний проєкт складається з трьох структурних шарів залежностей:
1. **Прямі залежності (Direct Dependencies):** бібліотеки, до яких звертаються інструкції `import` безпосередньо у коді застосунку (наприклад, `fastapi`, `sqlalchemy` або `numpy`).
2. **Транзитивні залежності (Transitive Dependencies):** пакети, які потрібні прямим бібліотекам для їхньої внутрішньої реалізації. Наприклад, фреймворк `fastapi` залежить від ASGI-сервера `starlette`, який спирається на асинхронний рушій `anyio`, а той зі свого боку вимагає модулі `idna` та `sniffio`.
3. **Платформні розширення (Platform-Specific Extensions):** скомпільовані бінарні модулі мовами C/Rust або умовні пакети, які активуються виключно під певною операційною системою чи версією CPython (наприклад, `uvloop` на POSIX-сумісних системах Linux/macOS або `colorama` на платформі Windows).

```
[Код застосунку] ──> fastapi (>=0.110.0) [Пряма залежність]
                        │
                        ├──> starlette (>=0.37.0, <0.38.0) [Транзитивна 1-го рівня]
                        │        │
                        │        └──> anyio (>=3.6.2, <5.0.0) [Транзитивна 2-го рівня]
                        │                 │
                        │                 ├──> idna (>=2.8) [Транзитивна 3-го рівня]
                        │                 └──> sniffio (>=1.1) [Транзитивна 3-го рівня]
                        │
                        └──> pydantic (>=2.0.0, <3.0.0) [Пряма залежність]
                                 │
                                 └──> pydantic-core (==2.16.3) [Транзитивна 1-го рівня]
```

Якщо у системі контролю версій зафіксовано лише діапазони прямих вимог, кожен новий запуск інсталятора виконує динамічний перерахунок усього графа. Це породжує явище **транзитивного дрейфу** (Transitive Drift): неконтрольованої зміни кінцевого набору коду внаслідок публікації нових мінорних або патч-релізів підлеглими бібліотеками.

Масштаб проблеми визначається відношенням кількості транзитивних пакетів до прямих:

```
T_drift = N_total - N_direct
```

де `N_total` — загальна кількість пакетів у каталозі `site-packages`, а `N_direct` — кількість явно оголошених розробником бібліотек.

У середньому сервісі на 10–15 прямих бібліотек припадає від 70 до 150 транзитивних пакунків. Навіть якщо всі автори бібліотек намагаються дотримуватися правил семантичного версіонування (Semantic Versioning, SemVer), на практиці версіонування у світі Python базується на ширшому стандарті PEP 440 (який допускає пост-релізи `.post1`, релізи розробки `.dev` та епохи версій). Людський фактор, неявні зміни внутрішніх структур даних або випадкові регресії продуктивності призводять до того, що мінорний патч на четвертому рівні вкладеності ламає виробничий контур.

Другим критичним ризиком є компрометація ланцюга постачання (Supply Chain Vulnerability). Якщо завантажуваний пакет не верифікується за суворим криптографічним хешем, зловмисник, який зламав обліковий запис мейнтейнера популярного транзитивного пакета або скомпрометував локальне мережеве дзеркало PyPI, може підмінити файл дистрибутива на версію зі шкідливим кодом.

![Розрив відтворюваності між абстрактною декларацією вимог та детермінованим lock-файлом](/root/sys/sys-plang-python/lock-files/img/reproducibility-gap.svg)
*Розрив відтворюваності: неконтрольований транзитивний дрейф версій у традиційній схемі проти повної детермінації дерева та хешів у файлі-замку.*

## 2. Анатомія файлу-замка: три стовпи детермінізму

Файл-замок (Lock File) — це машинно-генерований статичний маніфест, який перетворює динамічний простір пошуку на детермінований стан повної математичної рівноваги. Справжній файл-замок базується на трьох обов'язкових інженерних компонентах:

### 1. Точна фіксація версій (Absolute Version Pinning)

Усі вузли транзитивного дерева фіксуються оператором точної рівності (`==`):

```text
fastapi == 0.110.0
starlette == 0.37.2
anyio == 4.3.0
idna == 3.6
sniffio == 1.3.1
pydantic == 2.6.4
pydantic-core == 2.16.3
```

Жоден компонент середовища не має права самостійно оновитися без явної дії інженера, навіть якщо у репозиторії з'явився новий безпековий реліз.

### 2. Замикання повного транзитивного графа (Full Transitive Closure)

Файл-замок зберігає не просто плаский перелік назв, а повну топологічну структуру зв'язків. Для кожного вузла зафіксовано, які саме пакети є його прямими предками і нащадками. Це дає змогу інсталятору миттєво перевірити валідність і внутрішню несуперечливість середовища без звернення до віддалених серверів.

### 3. Криптографічна фіксація цілісності артефактів (Cryptographic Hashes)

Для кожного пакета записується таблиця хешів за алгоритмом SHA-256 (або BLAKE3) для всіх офіційних дистрибутивів:
- Вихідного архіву (`sdist` — `.tar.gz` або `.zip`).
- Попередньо скомпільованих бінарних коліс (`wheel` — `.whl`) для кожної підтримуваної цільової платформи, архітектури та версії ABI (наприклад, CPython 3.12 `manylinux_2_17_x86_64`, CPython 3.12 `musllinux_1_2_aarch64`, CPython 3.11 `macosx_arm64` та `win_amd64`).

Під час завантаження колеса інсталятор паралельно пропускає потік байтів крізь криптографічний дайджест:

```text
H_calc = SHA256(Archive_Bytes)
assert H_calc == H_locked, "Security Violation: Artifact hash mismatch!"
```

Якщо хеш хоча б на один біт відрізняється від еталонного значення, зафіксованого у файлі-замку, процес інсталяції негайно переривається з аварійним кодом помилки.

## 3. Еволюція підходів: від pip freeze до нативних менеджерів

Шлях мови Python від простих скриптів встановлення до сучасних універсальних менеджерів зайняв понад 15 років. Детальний розбір історичного розвитку, появи утиліти `easy_install`, стандартів PEP 518, 517, 621 та суперечок навколо стандартів PEP 665 і PEP 751 наведено у вставці [Еволюція менеджерів і файлів блокування у Python](root:sys-plang-python/lock-files/hist-lockfile-evolution.md).

```
+-------------------------------------------------------------------------+
|                    ЧОТИРИ ПОКОЛІННЯ МЕНЕДЖМЕНТУ ЗАЛЕЖНОСТЕЙ             |
+--------------------+----------------------------------------------------+
| 1. Плоский дамп    | pip freeze > requirements.txt                      |
|    (2008–2012)     | Захоплення поточного site-packages. Немає різниці  |
|                    | між прямими й транзитивними dep. Засмічення платф. |
+--------------------+----------------------------------------------------+
| 2. Двоетапні маніф.| pip-tools (pip-compile requirements.in)            |
|    (2012–2017)     | Розділення абстрактних намірів і точних хешів.     |
|                    | Жорстка прив'язка до поточної платформи розробника.|
+--------------------+----------------------------------------------------+
| 3. Перші локери    | Pipenv (Pipfile.lock) / Poetry (poetry.lock)       |
|    (2017–2023)     | Впровадження TOML/JSON замків, PubGrub на Python.  |
|                    | Повільний парсинг метаданих віддалених коліс.      |
+--------------------+----------------------------------------------------+
| 4. Нативні універс.| PDM (pdm.lock) / Astral uv (uv.lock)               |
|    (2024–тепер)    | Крос-платформний граф, Rust-рушій, HTTP Range req, |
|                    | синхронізація venv за 10–50 мілісекунд.            |
+--------------------+----------------------------------------------------+
```

### 1. Перше покоління: pip freeze

У ранню добу єдиним способом фіксації була команда `pip freeze > requirements.txt`. Вона вивантажувала повний перелік усіх пакунків, знайдених у поточному каталозі `site-packages`. 

Недоліки цього підходу:
- **Змішування рівнів:** у плоскому списку стиралася межа між бізнес-залежностями та допоміжними бібліотеками.
- **Платформне забруднення:** якщо інженер запускав команду на macOS, до списку потрапляли специфічні системні біндінги Darwin, які призводили до збою під час розгортання в середовищі Linux.
- **Неможливість безпечного видалення:** якщо розробник прибирав бібліотеку з коду, її транзитивні підпакети залишалися у `requirements.txt` назавжди.

### 2. Друге покоління: pip-compile (pip-tools)

Утиліта `pip-tools` запровадила двоетапний робочий процес: прямі абстрактні вимоги записувалися у файл `requirements.in`, а команда `pip-compile --generate-hashes` формувала підсумковий `requirements.txt` із фіксацією хешів та коментарями щодо походження кожного транзитивного пакета (`# via fastapi`).

Проте `pip-tools` залишався одноплатформним інструментом: сформований файл відображав дерево рішень лише для тієї комбінації ОС та версії Python, на якій запускалася компіляція.

### 3. Третє покоління: Pipenv та Poetry

Менеджери `Pipenv` та `Poetry` здійснили перехід до структурованих маніфестів і виділених файлів блокування (`Pipfile.lock` у форматі JSON та `poetry.lock` у форматі TOML). `Poetry` вперше інтегрував у світ Python сучасний алгоритм розв'язання конфліктів `PubGrub`.

Головним обмеженням третього покоління була продуктивність: оскільки інструменти були написані мовою Python, операції десеріалізації, зчитування заголовків ZIP-архівів через мережу та обчислення графа займали від 30 секунд до кількох хвилин.

### 4. Четверте покоління: uv та універсальне блокування

Менеджер нового покоління `uv`, створений компанією Astral мовою Rust, переосмислив архітектуру роботи з залежностями:
- **Нативна швидкодія:** алгоритм PubGrub мовою Rust у поєднанні з оптимізованими бітовими масками здійснює розв'язання складних графів за 5–20 мілісекунд.
- **Діапазонні HTTP-запити (PEP 658):** `uv` зчитує лише блок метаданих `METADATA` із середини архіву `.whl` за допомогою HTTP-заголовків `Range: bytes=...`, уникаючи завантаження сотень мегабайтів непотрібного бінарного коду під час резолвінгу.
- **Єдиний універсальний замок `uv.lock`:** один файл містить математично точне дерево рішень для всіх платформ одночасно.

### Динамічний видобуток метаданих: PEP 658 проти повного завантаження

У класичній моделі інсталятора (ранній `pip` та `Pipenv`) для отримання списку транзитивних залежностей віддаленого пакета інструмент мусив повністю завантажити бінарний файл колеса `.whl` або вихідний архів `.tar.gz` з PyPI. Якщо бібліотека машинного навчання (наприклад, `torch` або `tensorflow`) важить від 800 МБ до 2 ГБ, простий розрахунок сумісності версій вимагав гігабайтів мережевого трафіку та десятків секунд очікування лише для того, щоб прочитати кілька кілобайтів текстового опису вимог.

Стандарт [PEP 658](https://peps.python.org/pep-0658/) («Serve Distribution Metadata in the Simple Repository API») дозволив репозиторіям пакетів надавати метадані окремим легковажним файлом або через діапазонні запити HTTP (`Range: bytes=start-end`):
1. Клієнт надсилає HTTP-запит `HEAD` або запитує перші й останні 4 КБ ZIP-архіву `.whl`.
2. Завдяки структурі формату ZIP центральний каталог файлів (Central Directory Record) розташований наприкінці архіву. Клієнт зчитує зміщення внутрішнього файлу `*.dist-info/METADATA`.
3. Другим точковим HTTP-запитом клієнт завантажує виключно байти файлу `METADATA` (зазвичай 2–15 КБ).
4. Резолвер отримує повний перелік залежностей та маркерів середовища без передачі жодного байта скомпільованого машинного коду.

Це зменшує обсяг мережевого трафіку на етапі резолвінгу на 98–99%, дозволяючи будувати файл-замок для проєкту зі 100 бібліотеками практично в режимі реального часу.

### Ізоляція збирання за PEP 517/518 проти довільного коду setup.py

У ранніх версіях екосистеми визначення залежностей для вихідних дистрибутивів (`sdist`) вимагало виконання коду `python setup.py egg_info`. Це створювало критичну вразливість безпеки та архітектурне замкнене коло:
- Для того щоб дізнатися, які залежності потрібні пакету, треба було **виконати довільний Python-код** із завантаженого архіву на машині розробника.
- Якщо сам скрипт `setup.py` імпортував допоміжний інструмент збирання (наприклад, `Cython`, `setuptools_scm` або `wheel`), інсталятор падав із помилкою `ModuleNotFoundError`, оскільки середовище збирання ще не було ініціалізовано.

Впровадження стандартів PEP 518 (декларація збиральних інструментів у таблиці `[build-system.requires]`) та PEP 517 (стандартизований інтерфейс хуків збирання `prepare_metadata_for_build_wheel`) усунуло цю проблему. Сучасні менеджери ізолюють процес збирання у тимчасових пісочницях і вимагають статичної декларації метаданих за стандартом PEP 621, унеможливлюючи виконання стороннього коду під час побудови lock-файлу.

## 4. Алгоритми резолвінгу: від наївного бектрекінгу до SAT/PubGrub

Задача визначення сумісності версій залежностей є NP-повною задачею задоволення булевих формул (Boolean Satisfiability, SAT).

Типовим викликом для резолвера є проблема діамантової залежності (Diamond Dependency Problem), коли два прямі пакети вимагають одну й ту саму спільну бібліотеку, але з різними обмеженнями версій:

```
       [Root Project]
        /          \
       v            v
  [Pkg A v2.1]  [Pkg B v1.4]
       \            /
        v          v
       [Pkg C: ?]
  (A: C >= 1.2, < 2.0)
  (B: C >= 1.5, < 3.0)
  --------------------
  Перетин: C ∈ [1.5, 2.0)
```

Математично резолвер розраховує перетин допустимих множин версій:

```
V_valid(C)
= V_req(A, C) ∩ V_req(B, C)   [перетин множин вимог від прямих залежностей A та B]
= [1.2, 2.0) ∩ [1.5, 3.0)     [підстановка допустимих інтервалів версій]
= [1.5, 2.0)                  [знаходження спільного інтервалу сумісності]
```

Якщо результуючий інтервал непорожній (`≠ ∅`), система обирає найвищий доступний стабільний реліз (наприклад, `C == 1.8.0`). Якщо ж пакет `B` вимагає `C >= 2.0`, перетин стає порожнім, що сигналізує про нерозв'язний конфлікт.

![Транзитивний граф залежностей та розв'язання конфліктів через перетин обмежень версій](/root/sys/sys-plang-python/lock-files/img/transitive-resolution-graph.svg)
*Побудова транзитивного графа залежностей: розв'язання діамантової проблеми через перетин діапазонів або навчання на конфліктах (CDCL).*

### Чому наївний бектрекінг зациклюється

Ранні версії `pip` використовували наївний пошук із поверненням (Backtracking). Якщо на глибині 10-го рівня виникав конфлікт, інсталятор відкочувався лише на один крок назад і починав послідовно перебирати сотні проміжних патч-релізів сусіднього пакета, який жодним чином не впливав на джерело конфлікту. Час роботи алгоритму зростав експоненційно як `O(V^N)`, де `V` — кількість доступних версій кожного пакета, а `N` — глибина графа.

### Принцип роботи алгоритму PubGrub (CDCL)

Сучасні менеджери спираються на парадигму Conflict-Driven Clause Learning (CDCL):
1. **Прийняття рішень (Decision):** резолвер обирає пакет із найвужчим діапазоном версій і призначає йому найвищий реліз.
2. **Поширення обмежень (Unit Propagation):** система аналізує вимоги обраного пакета та додає нові обмеження до поточної системи булевих рівнянь.
3. **Виявлення конфлікту та навчання (Clause Learning):** якщо виникає суперечність, алгоритм знаходить її першопричину і формує нове логічне правило несумісності (Incompatibility Clause). Наприклад: «Версія `A 2.1.0` несумісна з `B 1.4.0` через несумісність за пакетом `C`».
4. **Стрибок назад (Backjumping):** замість покрокового перебору резолвер миттєво повертається по стеку рішень до того рівня, де було обрано корінь конфлікту, відсікаючи все тупикове піддерево пошуку за один крок.
5. **Генерація зрозумілих повідомлень про помилки:** PubGrub зберігає історію виведення несумісностей, завдяки чому при нерозв'язному конфлікті видає людиночитаний звіт: «Пакет X не може бути встановлений, тому що версія Y вимагає Z, яка конфліктує з W».

Повну реалізацію власного CDCL-резолвера мовами Python, C та C++ з експортом у lock-формат наведено у вставці [Реалізація резолвера залежностей на базі SAT/CDCL з експортом у lock-формат](root:sys-plang-python/lock-files/proj-sat-resolver.md).

## 5. Концепція універсального lock-файлу (Universal Lock File)

У великих командах розробка ведеться на гетерогенних обчислювальних платформах:
- Розробник №1 пише код на Apple Silicon (macOS, архітектура `arm64`).
- Розробник №2 працює на робочій станції під керуванням Windows 11 (`x86_64`).
- Сервер тестового оточення CI/CD працює на Ubuntu Linux (`x86_64`).
- Продакшен-контейнери розгортаються на базі Alpine Linux (дистрибутив з `musl libc`, архітектура `aarch64`).

Спроба підтримувати окремий файл блокування під кожну систему (`requirements-linux.txt`, `requirements-macos.txt`) призводить до розсинхронізації, дублювання зусиль та випадкових помилок розгортання.

Універсальний lock-файл (Universal Lock File) розв'язує цю проблему, зберігаючи **повне дерево рішень для всіх платформ, архітектур та версій інтерпретатора в одному файлі `uv.lock`**.

```
[Універсальний uv.lock]
      │
      ├──> Linux (x86_64) ──> uvloop-0.19.0-cp312-manylinux.whl (SHA-256: 8f7e...)
      │
      ├──> macOS (ARM64)  ──> uvloop-0.19.0-cp312-macosx_arm64.whl (SHA-256: 9b8a...)
      │
      └──> Windows (x64)  ──> pywin32-306-cp312-win_amd64.whl (SHA-256: 4c2d...)
                              (uvloop автоматично ігнорується)
```

![Архітектура універсального крос-платформного lock-файлу з підтримкою Environment Markers](/root/sys/sys-plang-python/lock-files/img/universal-lock-matrix.svg)
*Універсальний замок: єдиний документ містить детерміноване дерево артефактів для будь-якої комбінації ОС, CPU та версії інтерпретатора.*

Коли розробник запускає команду встановлення, інструмент не виконує повторний розрахунок графа і не надсилає запитів до PyPI. Він локально зчитує файл `uv.lock` і фільтрує зафіксовані вузли за маркерами середовища (Environment Markers згідно з PEP 508):

```text
sys_platform == 'linux' and platform_machine == 'x86_64' and python_version >= '3.12'
```

Ця операція має лінійну складність `O(N)` від кількості пакетів і виконується в оперативній пам'яті за частки мілісекунди.

### Монорепозиторії, робочі простори (Workspaces) та PEP 735

У складних архітектурах один репозиторій Git часто містить кілька взаємопов'язаних сервісів і внутрішніх бібліотек (наприклад, `backend-api`, `worker`, `shared-models`, `auth-lib`). Раніше для кожного мікросервісу доводилося створювати окремий віртуальний простір та окремий файл блокування, що ускладнювало локальну розробку та оновлення спільних пакетів.

Сучасні менеджери (зокрема `uv` та `PDM`) підтримують концепцію **робочих просторів** (Workspaces):
1. **Єдиний кореневий `uv.lock`:** один файл блокування охоплює всі пакети монорепозиторію.
2. **Локальні редаговані лінки (Editable Links):** залежності між пакетами робочого простору монтуються напряму через механізм `site-packages/shared_models.pth` без проміжної компіляції коліс.
3. **Стандартизація груп залежностей (PEP 735):** залежності для тестування (`test`), лінтингу (`lint`) та документації (`docs`) групуються у таблиці `[dependency-groups]`. Резолвер генерує спільний замок, що гарантує сумісність тестових утиліт (`pytest`, `mypy`) із основними бібліотеками рантайму.

Формальну специфікацію схеми універсального lock-файлу, дескрипторів коліс та CLI-команд наведено у вставці [Специфікація універсального lock-файлу та інтерфейс синхронізації](root:sys-plang-python/lock-files/api-universal-lock.md).

## 6. Детермінізм і безпека у CI/CD

Впровадження детермінованих замків кардинально змінює інженерну надійність конвеєрів CI/CD.

### 1. Захист ланцюга постачання (Supply Chain Security)

При роботі з незафіксованими залежностями відкриваються вектори атак:
- **Typosquatting:** створення шкідливого пакета зі схожою назвою (`reqeusts` замість `requests`).
- **Dependency Confusion:** підміна внутрішнього приватного пакета компанії публічним пакетом з PyPI з вищим номером версії.
- **Підміна байтів на проміжних дзеркалах:** зловмисна модифікація коліс на публічних дзеркалах або кешуючих проксі.

Наявність у lock-файлі хешів SHA-256 для кожного артефакту повністю блокує ці загрози: якщо хеш завантаженого файлу не збігається із зафіксованим у репозиторії Git, розгортання негайно переривається.

### 2. Синхронізація замість сліпого встановлення

Традиційна команда `pip install -r requirements.txt` має суттєву ваду: вона встановлює відсутні пакети, але **ніколи не видаляє застарілі**. Якщо інженер прибрав бібліотеку з проєкту, на CI-сервері вона залишається у каталозі `site-packages`, маскуючи помилки імпорту відсутніх модулів.

Сучасні менеджери реалізують концепцію **атомарної синхронізації**:

```bash
# Синхронізація середовища в uv
uv sync --frozen

# Синхронізація середовища в Poetry
poetry install --sync --no-root
```

Команда синхронізації виконує три послідовні дії:
1. Завантажує та валідує за хешами всі необхідні колеса.
2. Приводить версії встановлених пакетів у строгу відповідність із замком.
3. **Атомарно видаляє (prune)** із каталогу `site-packages` усі файли та бібліотеки, які не описані у файлі-замку.

Прапорець `--frozen` гарантує, що менеджер не буде оновлювати lock-файл на сервері: якщо розробник змінив маніфест `pyproject.toml`, але забув оновити замок локально, CI впаде з явною помилкою, унеможливлюючи появу неперевіреного коду на продакшені.

### 3. Технології екстремального прискорення: CAS, Hardlinks та Reflinks

Класичний `pip` розпаковує кожен ZIP-архів окремо, виконуючи тисячі дискових операцій запису. При 100 залежностях це займає 30–90 секунд на кожен запуск тестів.

Менеджер `uv` використовує архітектуру контентно-адресованого сховища (Content-Addressable Storage, CAS):
1. Усі колеса розпаковуються в єдиний глобальний системний кеш `~/.cache/uv/archive/`.
2. При створенні віртуального середовища `uv sync` не копіює байти фізично, а створює жорсткі посилання (**Hardlinks**) або файлові посилання з копіюванням при записі (**Reflinks / Copy-on-Write** на файлових системах APFS у macOS, Btrfs та XFS у Linux).
3. Розгортання ізольованого середовища з сотні складних бібліотек триває від 10 до 50 мілісекунд, що на два-три порядки швидше за традиційні інструменти.

### 4. Оптимізація шарів у багатоетапних Dockerfile (Multi-stage Builds)

Завдяки відокремленню lock-файлу та прапорцю `--no-install-project` досягається ідеальне кешування Docker-шарів:

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.12-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/uv

WORKDIR /app
# 1. Копіюємо виключно файли маніфесту та замка
COPY pyproject.toml uv.lock ./

# 2. Встановлюємо лише сторонні залежності у .venv
RUN uv sync --frozen --no-install-project --no-dev

# 3. Копіюємо вихідний код застосунку
COPY src/ ./src/
RUN uv sync --frozen --no-dev

# Фінальний легковий рантайм-образ
FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
ENV PATH="/app/.venv/bin:$PATH"
CMD ["python", "-m", "src.main"]
```

Оскільки вихідний код копіюється після кроку інсталяції залежностей, Docker повторно використовує закешований шар зі встановленими бібліотеками. Збирання контейнера при зміні бізнес-логіки триває менше 1 секунди замість повторного завантаження коліс із мережі.

![Порівняння традиційного конвеєра pip проти детермінованого та надшвидкого uv sync у CI/CD](/root/sys/sys-plang-python/lock-files/img/cicd-sync-pipeline.svg)
*Конвеєр CI/CD: усунення мережевої латентності та ризиків ланцюга постачання завдяки кешу коліс і атомарній синхронізації.*

> 🔧 **Навіщо це.**
> У великих мікросервісних бекендах (десятки контейнерів у Kubernetes) скорочення часу підготовки оточення з 45 секунд до 50 мілісекунд кардинально прискорює цикл автоматичного масштабування (Horizontal Pod Autoscaling). Новий под починає обробляти трафік практично миттєво після отримання сигналу від балансувальника навантаження.

## Терміни та етимологія

| Термін | Етимологія | Значення у контексті керування залежностями |
|---|---|---|
| **Відтворюваність** (*Reproducibility*) | Від лат. *re-* — знову, повторно + *producere* — створювати, виводити вперед. | Властивість інженерного процесу збирання гарантувати ідентичний до біта результат виконання на будь-якій обчислювальній машині в будь-який момент часу. |
| **Файл-замок** (*Lock File*) | Від давньоангл. *loc* — засув, замкнутий простір, фіксація стану. | Машиночитаний статичний документ, що жорстко закріплює точні версії, топологію повного транзитивного графа та хеші цілісності всіх компонентів середовища. |
| **Транзитивність** (*Transitivity*) | Від лат. *transitivus* — перехідний, від *transire* — переходити, перетинати. | Каскадне відношення підпорядкування, за якого пряма залежність першого рівня передає свої власні підлеглі залежності кореневому проєкту. |
| **Резолвер** (*Resolver*) | Від лат. *resolvere* — розв'язувати, розплутувати, відпускати. | Спеціалізований алгоритмічний рушій (переважно на базі SAT/CDCL), який обчислює несуперечливий набір версій пакунків, що задовольняє всі обмеження системи. |
| **Маркер середовища** (*Environment Marker*) | Від лат. *marcare* — помічати, та англ. *environment* — оточення, середовище. | Стандартизований булевий вираз (PEP 508), який визначає умови активації конкретної гілки залежності залежно від операційної системи, версії інтерпретатора або архітектури процесора. |
| **Детермінізм** (*Determinism*) | Від лат. *determinare* — обмежувати, окреслювати, визначати. | Властивість обчислювальної системи видавати однозначно передбачуваний однаковий вихідний стан за однакових вхідних параметрів. |
