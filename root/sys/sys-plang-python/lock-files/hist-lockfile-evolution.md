Історія керування залежностями у мові Python є тривалим переходом від неструктурованих скриптів встановлення до формально верифікованих графів на базі SAT-солверів. Протягом двох десятиліть спільнота розв'язувала фундаментальний конфлікт між простотою додавання бібліотеки та гарантією незмінності кінцевого продуктового оточення.

```

                         │
                         ▼
2012: pip-tools (pip-compile) ──> 2016: PEP 518 (pyproject.toml)

2017: Pipenv (Pipfile.lock) ──> 2018: Poetry (poetry.lock) ──> 2024: uv (uv.lock)
```

## 1. Доба ручних архівів і поява setuptools (1998–2007)

У ранніх версіях Python (1.5–2.0) єдиним способом поширення стороннього коду було ручне завантаження архівів `.tar.gz` або `.zip`. Розробник розпаковував архів і запускав команду:

```bash
python setup.py install
```

Створений у 1998 році стандартний модуль `distutils` копіював файли безпосередньо в системний каталог `site-packages`. У цій моделі були відсутні концепції видалення пакунків, автоматичного завантаження залежностей та перевірки несумісності версій. Якщо бібліотека `foo` вимагала бібліотеку `bar`, користувач мусив самостійно знайти, завантажити та скомпілювати `bar`.

У 2004 році Філіп Ебі (Phillip J. Eby) представив бібліотеку `setuptools` та утиліту `easy_install`. Вона вперше запропонувала централізований репозиторій пакунків PyPI (Python Package Index, спочатку відомий як «Cheeseshop») і бінарний формат дистрибуції `.egg` (ZIP-архів із метаданими). `easy_install` автоматично завантажував залежності за посиланнями, проте мав критичні недоліки:
- Не підтримував деінсталяцію (`easy_install --uninstall` не існувало).
- Використовував небезпечний механізм динамічного підвантаження через файл `easy-install.pth`, що суттєво уповільнювало старт інтерпретатора.
- Завантажував першу-ліпшу версію без аналізу конфліктів у транзитивному дереві.

## 2. Народження pip і текстові вимоги (2008–2015)

У 2008 році Ієн Бікінґ (Ian Bicking) створив інструмент `pyinstall`, невдовзі перейменований на `pip` (рекурсивний акронім «Pip Installs Packages»). Головною метою `pip` було виправлення вад `easy_install`: запровадження безпечного видалення (`pip uninstall`), відмова від формату `.egg` на користь плоского розпакування у `site-packages` та підтримка плоских файлів вимог:

```bash
pip freeze > requirements.txt
```

Команда `pip freeze` зчитувала всі встановлені в поточному середовищі пакунки й виводила їх у форматі `name==version`. Цей підхід став стандартом на багато років, проте містив концептуальну пастку:
1. **Змішування рівнів:** у файлі `requirements.txt` стиралася межа між прямими залежностями бізнес-логіки (наприклад, `fastapi`) та їхніми внутрішніми транзитивними підпакетами (`starlette`, `anyio`, `idna`, `sniffio`).
2. **Забруднення платформними колісами:** якщо розробник запускав `freeze` на macOS, туди потрапляли специфічні для Darwin бібліотеки (як-от C-біндінги операційної системи), що робило збірку неробочою на серверах під керуванням Linux.
3. **Неможливість оновлення:** якщо треба було оновити одну верхньорівневу бібліотеку, не було надійного способу дізнатися, які саме транзитивні рядки у `requirements.txt` належали їй, а які — іншим модулям.

## 3. Двоетапна фіксація: pip-tools (2012)

У 2012 році Вінсент Дріссен (Vincent Driessen) розробив утиліту `pip-tools`, яка розділила абстрактні вимоги та конкретну фіксацію. Розробник оголошував прямі залежності у файлі `requirements.in`:

```text
# requirements.in
requests >= 2.25.0
pydantic < 3.0
```

Команда `pip-compile` зверталася до PyPI, вираховувала сумісні транзитивні версії та генерувала фінальний `requirements.txt` із коментарями про походження кожного транзитивного пакунка:

```text
# requirements.txt, згенеровано pip-compile
requests==2.31.0
    # via -r requirements.in
urllib3==2.2.1
    # via requests
certifi==2024.2.2
    # via requests
```

Згодом `pip-tools` отримав підтримку прапорця `--generate-hashes`, який додавав SHA-256 хеші файлів, заклавши основу для детермінованих перевірок цілісності в CI/CD. Проте `pip-tools` не розв'язував проблеми крос-платформності: сформований файл залишався жорстко прив'язаним до версії Python та операційної системи, на якій запускалася компіляція.

## 4. Спроба створення уніфікованих середовищ: Pipenv (2017)

У 2017 році Кеннет Райтц (Kenneth Reitz) презентував проєкт `Pipenv`, офіційно підтриманий Python Packaging Authority (PyPA). `Pipenv` спробував об'єднати в один інструмент віртуальні середовища (`virtualenv`), плоскі залежності (`pip`) та формат замка, натхненний Bundler (Ruby) та Cargo (Rust).

`Pipenv` ввів два файли:
- `Pipfile` — декларація залежностей у форматі TOML із поділом на секції `packages` та `dev-packages`.
- `Pipfile.lock` — JSON-документ із точними версіями, маркерами середовища та SHA-256 хешами для кожного дистрибутива.

Попри популярність, `Pipenv` зіткнувся з критикою через низьку швидкість резолвінгу. Інструмент завантажував вихідні архіви `.tar.gz` з PyPI, щоб розпарсити `setup.py` і дізнатися залежності, через що блокування проєкту середнього розміру могло тривати кілька хвилин.

## 5. Доба стандартизації та Poetry (2018–2023)

Паралельно спільнота стандартизувала інфраструктуру пакування:
- **PEP 518 (2016):** впровадив єдиний маніфест `pyproject.toml` і секцію `[build-system]`, поклавши край домінуванню ненадійних імпортів `setuptools` усередині `setup.py`.
- **PEP 517 (2017):** стандартизував інтерфейс взаємодії між збиральними бекендами (`flit`, `hatchling`, `poetry-core`) та інсталяторами.
- **PEP 621 (2020):** уніфікував декларацію метаданих проєкту (`[project.dependencies]`) у файлі `pyproject.toml`.

У 2018 році Себастьєн Юстас (Sébastien Eustace) створив `Poetry`. Poetry відмовився від застарілих алгоритмів жадібного бектрекінгу і вперше у світі Python реалізував сучасний алгоритм розв'язання конфліктів `PubGrub` (розроблений для екосистеми Dart/Flutter). 

Poetry генерував `poetry.lock` у форматі TOML і підтримував універсальне блокування для різних версій інтерпретатора. У 2020 році з'явився `PDM` (автор — Frost Ming), який першим повністю реалізував підтримку стандартного синтаксису PEP 621 у поєднанні з алгоритмом розв'язання `Resolvelib`.

## 6. Революція нативних менеджерів: uv (2024–тепер)

Незважаючи на зрілість алгоритмів, менеджери, написані на чистому Python, залишалися повільними через операції вводу-виводу при парсингу метаданих тисяч коліс.

У 2024 році компанія Astral (засновник — Чарлі Марш, автор лінтера Ruff) представила `uv` — менеджер пакунків, написаний мовою Rust. `uv` переосмислив роботу з залежностями:
- Власна реалізація PubGrub на Rust оптимізувала розв'язання складних графів залежностей до одиниць мілісекунд.
- Метадані коліс зчитуються через паралельні діапазонні HTTP-запити (HTTP Range Requests за стандартом PEP 658), що дозволяє отримати список транзитивних вимог колеса без повного завантаження самого архіву.
- Створено крос-платформний файл `uv.lock`, здатний в одному документі детерміновано зафіксувати матрицю сумісності для будь-якої комбінації Linux, macOS, Windows, архітектур x86_64, aarch64 та версій CPython 3.8–3.13.

## 7. Невдачі та прогрес стандартизації PEP для Lock-файлів

Екосистема Python тривалий час страждала від відсутності єдиного стандарту на файл-замок: Poetry мав `poetry.lock`, Pipenv — `Pipfile.lock`, PDM — `pdm.lock`, uv — `uv.lock`.

У 2021 році було запропоновано **PEP 665** («A file format to list Python dependencies for installation of an application»). Специфікація вимагала фіксації виключно бінарних коліс (wheels) і повністю забороняла підтримку вихідних дистрибутивів (`sdist`). Спільнота відхилила стандарт через те, що на багатьох платформах (BSD, специфічні архітектури ARM, системи без попередньо скомпільованих коліс) проєкти неможливо було розгорнути без локального збирання з вихідних текстів.

У 2024 році Брет Кеннон (Brett Cannon) представив проєкт **PEP 751** («A file format for recording resolved dependencies for installation»). PEP 751 узагальнює досвід PDM, Poetry та uv, пропонуючи відкритий стандарт універсального lock-файлу з підтримкою як коліс, так і вихідних збірок (`sdist`), а також повною верифікацією маркерів середовища.

Історія показала, що файл-замок перетворився зі звичайного дампу пам'яті середовища на математично строгий, криптографічно захищений документ, що гарантує надійність ланцюга постачання програмного забезпечення.
