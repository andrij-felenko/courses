# 📜 Від CGI та WSGI до ASGI: еволюція веб-інтерфейсів Python

Еволюція інтерфейсів взаємодії між веб-серверами та мовою Python відображає фундаментальну зміну мережевої парадигми: перехід від короткоживучих синхронних запитів раннього веб-простору до тривалих асинхронних з'єднань реального часу для інтернету речей та мікросервісів.

## Епоха CGI та фрагментація 1990-х

У ранні роки розвитку Всесвітнього павутиння стандартною моделлю виконання динамічних веб-додатків був інтерфейс CGI (англ. *Common Gateway Interface*). Сервер (найчастіше NCSA HTTPd або Apache) при отриманні кожного нового HTTP-запиту виконував системний виклик `fork()` та `execve()`, породжуючи окремий процес операційної системи. Вхідні параметри, заголовки HTTP та змінні оточення передавалися новому процесу через системні змінні оточення `os.environ`, а тіло запиту надходило у стандартний потік вводу `stdin`. Результат обробки скрипт записував у `stdout`.

Для мови Python такий підхід створював критичні накладні витрати:
1. Час ініціалізації середовища виконання CPython (парсинг бінарних заголовків, завантаження базових бібліотек, створення простору імен `builtins`) повторювався для кожного окремого HTTP-запиту і складав від 20 до 80 мілісекунд.
2. Оперативна пам'ять не перевикористовувалася між запитами; з'єднання з реляційними базами даних відкривалося заново під час кожного виклику.
3. Пропускна здатність CGI-сервера на обладнанні кінця 1990-х років рідко перевищувала кілька десятків запитів на секунду.

Спроби оптимізувати виконання породили специфічні серверні модулі: `mod_python` для сервера Apache, інтегровані веб-сервери всередині середовища Zope, кастомні адаптери для FastCGI та SCGI. Кожен із цих серверних рушіїв вимагав власного API. Фреймворк, написаний для `mod_python`, не міг працювати під FastCGI або Twisted без повного переписування коду адаптера. Виникла глибока фрагментація екосистеми: розробники бібліотек створювали окремі коннектори під кожну серверну платформу.

## PEP 333 та тріумф WSGI (2003)

У грудні 2003 року розробник Філіп Ебі (Phillip J. Eby) запропонував пропозицію щодо вдосконалення мови PEP 333 (англ. *Python Web Server Gateway Interface v1.0*). Метою специфікації було створення універсального, простого та суворо синхронного контракту, який відділяв веб-сервери від веб-фреймворків.

Архітектура WSGI будувалася на концепції викликального об'єкта (англ. *callable* — функція або клас із методом `__call__`), що приймає два позиційні аргументи:

```py
def simple_app(environ, start_response):
    status = "200 OK"
    response_headers = [("Content-Type", "text/plain; charset=utf-8")]
    start_response(status, response_headers)
    return [b"Telemetry received\n"]
```

WSGI розділив веб-стек на три ізольовані рівні:
* **Серверна сторона (Server / Gateway)**: багатопроцесні або багатопотокові сервери (Gunicorn, uWSGI, Apache mod_wsgi), які приймають TCP-з'єднання від клієнтів, парсять байти протоколу HTTP, формують словник `environ` і викликають додаток.
* **Проміжне програмне забезпечення (Middleware)**: компоненти, які реалізують інтерфейс сервера для верхнього рівня і інтерфейс додатку для нижнього (логіка аутентифікації, стиснення Gzip, маршрутизація URL, керування сесіями).
* **Додаток (Application / Framework)**: високорівневі бібліотеки (Django, Flask, Bottle, Pyramid), які надають розробнику зручну систему шаблонів, маршрутизацію та обробку бізнес-логіки.

У 2010 році специфікацію було формалізовано для Python 3 у PEP 3333. Завдяки WSGI розробники отримали можливість писати код один раз і вільно розгортати його на будь-якому сервері промислового рівня (Gunicorn, uWSGI, Waitress).

## Поява Flask (2010) та синхронний розквіт

У 2010 році Армін Ронахер (Armin Ronacher) представив мікрофреймворк Flask як першоквітневий жарт («Denkwerkzeug»), об'єднавши дві існуючі бібліотеки: маршрутизатор і WSGI-утиліти Werkzeug та шаблонізатор Jinja2.

Flask закріпив синхронну парадигму WSGI в елегантному мінімалістичному API:
* Маршрутизація через декоратори `@app.route('/path')`.
* Глобальні контекстні змінні `request` та `g`, реалізовані через механізм локального сховища потоків (англ. *Thread-Local Storage*, а згодом `ContextVar`).
* Гнучка система розширень (Flask-SQLAlchemy, Flask-Login, Flask-Migrate).

Протягом майже десятиліття комбінація Flask + Gunicorn + SQLAlchemy була де-факто промисловим стандартом створення REST API та веб-сервісів на Python.

## Криза C10k, веб-сокети та обмеження блокувальної моделі

На початку 2010-х років структура мережевого трафіку зазнала докорінних змін. Поширення мобільних додатків, односторінкових застосунків (SPA) та екосистеми інтернету речей (IoT) висунуло нові вимоги до бекендів:
* Необхідність утримувати постійні двонаправлені TCP-з'єднання через WebSockets (RFC 6455) для миттєвої передачі телеметрії та команд керування.
* Технології тривалого опитування (англ. *Long Polling*) та потокової передачі Server-Sent Events (SSE).
* Обробка десятків тисяч одночасних підключень (проблема C10k/C100k) на одному вузлі.

Специфікація WSGI виявилася принципово нездатною ефективно вирішувати ці завдання через три фундаментальні архітектурні обмеження:

1. **Синхронний життєвий цикл запиту-відповіді**: WSGI проектувався під послідовну модель: запит надійшов → обробився в поточному потоці → відповідь відправлена → з'єднання закрито або повернуто в пул keep-alive.
2. **Блокування системного потоку**: якщо датчик підключається через WebSocket і утримує канал відкритим протягом кількох годин, виділений потік або процес сервера Gunicorn залишається заблокованим протягом усього цього часу, не маючи змоги обробляти запити інших клієнтів.
3. **Ресурсний бар'єр**: створення 10 000 системних потоків ОС вимагає гігабайтів оперативної пам'яті лише на виділення стеків викликів (`pthread_create`), а накладні витрати на перемикання контексту ядра (англ. *context switching*) призводять до деградації процесора.

Спроби вирішити проблему за допомогою бібліотек неблокувального вводу-виводу першого покоління (Tornado, Twisted) або «мавпячого патчингу» (англ. *monkey-patching* сокетів у Gevent та Eventlet) створювали серйозні проблеми стабільності: сторонні C-розширення (наприклад, драйвери баз даних, криптографічні модулі) не піддавалися патчингу і викликали непередбачувані взаємні блокування (англ. *deadlocks*).

## Асинхронна революція: asyncio та народження ASGI (2015–2018)

Вихід Python 3.4 (PEP 3156, модуль `asyncio`) та Python 3.5 (синтаксичні конструкції `async` / `await`, PEP 492) надав мові рідну підтримку асинхронного програмування на рівні байткоду та циклу подій.

Проте стандарт WSGI не мав механізмів для виклику асинхронних корутин. У 2015 році Ендрю Ґодвін (Andrew Godwin), провідний розробник Django, розпочав роботу над проектом Django Channels для підтримки WebSockets і фонових задач. Для цього знадобився новий протокол взаємодії між веб-сервером і додатком, який отримав назву ASGI (англ. *Asynchronous Server Gateway Interface*).

Еволюція ASGI пройшла три етапи:
* **ASGI 1.0 / 2.0**: побудований навколо системи повідомлень та канальних шарів (Channel Layers) на базі черг Redis. Сервер і обробник спілкувалися через асинхронні повідомлення.
* **ASGI 3.0 (2019)**: відмова від складного канального прошарку на користь прямого інтерфейсу єдиної корутини. Нова специфікація визначила інтерфейс як виклик `async def application(scope, receive, send)`.

```py
async def simple_asgi_app(scope, receive, send):
    if scope["type"] == "http":
        await send({
            "type": "http.response.start",
            "status": 200,
            "headers": [[b"content-type", b"text/plain"]],
        })
        await send({
            "type": "http.response.body",
            "body": b"Async telemetry accepted\n",
        })
```

## Поява Starlette, Uvicorn та FastAPI (2018)

Формалізація ASGI 3.0 спричинила вибуховий розвиток асинхронних інструментів:
1. **Uvicorn**: розроблений Томом Крісті (Tom Christie) блискавичний ASGI-сервер на базі бібліотеки `uvloop` (C-обгортка над високопродуктивним системним мультиплексором `libuv`, що використовується в Node.js) та парсера `httptools` (C-порт HTTP-парсера Nginx).
2. **Starlette**: легковагий асинхронний веб-інструментарій від Тома Крісті, що реалізував маршрутизацію, обробку WebSockets, middleware та управління життєвим циклом (lifespan).
3. **FastAPI**: наприкінці 2018 року Себастьян Рамірес (Sebastián Ramírez) опублікував першу версію FastAPI. Фреймворк поєднав продуктивність Starlette/ASGI, строгу статичну типізацію Python 3.6+ та валідацію схем Pydantic.

FastAPI вирішив дві ключові проблеми, які гальмували розробку API на класичних синхронних фреймворках: повну автоматизацію валідації вхідних структур даних із генерацією інтерактивної документації OpenAPI/Swagger та нативну асинхронну обробку десятків тисяч одночасних підключень без блокування потоків ОС.
