# 📜 Еволюція включення коду: від tarball у дереві до Git-механізмів

У 1990-х роках інженерія вільного програмного забезпечення зіткнулася з проблемою, якої не знали закриті мейнфрейми: як розробляти операційну систему чи мережевий стек, коли окремі підсистеми (наприклад, драйвери контролерів, реалізації криптографічних алгоритмів DES/AES або бібліотеки стиснення `zlib`) пишуться незалежними авторами й поширюються у вигляді окремих архівів вихідного коду (англ. *tarball*). 

Централізовані системи контролю версій того часу — CVS, а пізніше Subversion (SVN) — не мали понять розподілених репозиторіїв чи ізольованих просторів імен. Коли Лінус Торвальдс або розробники BSD інтегрували драйвер мережевої карти чи модуль стиснення в дерево вихідних текстів ядра, єдиним доступним інженерним рішенням було фізичне розпакування чужого архіву безпосередньо в підкаталог `drivers/` або `lib/`. Увесь чужий код фіксувався звичайним комітом від імені інтегратора проєкту. Цей підхід отримав назву «копіювання вихідного коду» (англ. *in-tree vendoring*).

Головна перевага прямого включення була очевидною: розробник або користувач, який отримував дерево ядра, міг викликати `make` на машині без мережевого з'єднання і гарантовано отримати робочий бінарний образ. Проте ціною такої автономності став важкий тягар супроводу. Коли автори сторонньої бібліотеки випускали виправлення вразливостей, інтегратор мусив вручну завантажувати новий tarball, виконувати команду `diff -uNr` між двома версіями бібліотеки, відсікати власні локальні виправлення, накладати патч на репозиторій і вручну розв'язувати конфлікти рядків. Усі метадані історії — хто написав конкретний рядок, які коміти передували зміні, яке обговорення велося в списку розсилки — безповоротно втрачалися.

### Поява Git 1.5 і концепція підмодулів (2007)

У 2005 році Лінус Торвальдс створив Git, а вже у 2007 році, з випуском версії Git 1.5.3 під керівництвом Джуна Хамано (Jun Hamano), у системі з'явився механізм **Git Submodules**.

Ідея сабмодулів виникла як спроба розв'язати протиріччя між автономністю компонентів та чистотою історії. Замість того щоб змішувати історію ста розробників сторонньої бібліотеки з комітами основного додатку, Git запропонував зберігати в дереві лише 20-байтний криптографічний хеш коміту (SHA-1) зовнішнього репозиторію. Уся історія, теги та гілки бібліотеки лишалися в її власному сховищі. Батьківський репозиторій фіксував лише зв'язку: «у каталозі `libs/foo` має перебувати ревізія `abc1234` зі сховища `https://...`».

Підмодулі швидко стали стандартом для великих розподілених проєктів, таких як Android Open Source Project (AOSP), рушій WebKit та фреймворк Qt. Проте практична експлуатація сабмодулів виявила низку гострих ергономічних проблем. Розробники постійно потрапляли в пастку стану *detached HEAD* (відокремленої верхівки), коли правки вносилися без створення локальної гілки й безслідно зникали під час чергового `git submodule update`. Ще більшим лихом став людський фактор: розробник робив коміт у підмодулі, фіксував новий SHA у головному проєкті, відправляв головний репозиторій на сервер, але забував виконати `git push` усередині підмодуля. У результаті колеги та сервери автоматичного тестування CI/CD стикалися з фатальною помилкою відсутності дерева коміту.

### Винахід Git Subtree Ейвері Пеннаруном (2009)

У 2009 році канадський інженер Ейвері Пеннарун (Avery Pennarun) представив альтернативний інструмент — **`git-subtree`**.

Пеннарун відштовхнувся від спостереження: 95% розробників у повсякденній роботі взагалі не хочуть знати про існування вкладених репозиторіїв. Їм потрібен звичайний `git clone`, після якого всі файли одразу лежать на диску, редагуються у звичному редакторі та індексуються без додаткових ключів на зразок `--recurse-submodules`.

Механіка `git subtree` повернулася до ідеї зберігання фізичних файлів у головному репозиторії, але додала до неї математичну строгість спрямованого ациклічного графа (DAG) Git. За допомогою спеціальних команд синтезу злиття (`git subtree add`, `git subtree pull`) інструмент створював коміти злиття, що пов'язували дерево підкаталогу з графом віддаленого репозиторію. Це дозволило імпортувати сторонній код або разом з повною історією, або у вигляді одного згорнутого коміту (`--squash`), а також витягувати локальні виправлення назад в окрему гілку (`git subtree split`) для відправки апстрім-авторам. У версії Git 1.7.11 (2012 рік) модуль `git-subtree` було офіційно включено до стандартного дистрибутива Git.

### Революція vendor-каталогів у Go та сучасний ренесанс монорепозиторіїв

У 2015 році, з випуском Go 1.5, команда розробників мови під керівництвом Расса Кокса (Russ Cox) запровадила експериментальну підтримку каталогу `vendor/`, яка стала стандартною у Go 1.6. Цей крок закріпив термін **vendoring** у сучасному лексиконі програмістів.

Логіка авторів Go базувалася на захисті ланцюга постачання (англ. *supply chain security*) та відтворюваності збірок:
1. Залежності повинні бути зафіксовані не просто абстрактним номером версії у конфігураційному файлі, а точним байтовим станом у репозиторії.
2. Проєкт має гарантовано збиратися через 10 років, навіть якщо початковий репозиторій на GitHub буде видалено, обліковий запис автора заблоковано, а центральний реєстр зазнає DDoS-атаки.
3. Збірка в закритих промислових або оборонних контурах (air-gapped) не повинна залежати від наявності доступу до зовнішньої мережі Інтернет.

Сьогодні інженерна практика розділилася: відкриті бібліотеки та мікросервісні архітектури часто використовують декларативні менеджери пакунків, тоді як великі промислові монорепозиторії (Google, Meta) та вбудовані системи критичної інфраструктури спираються на прямий вендоринг або Git-піддерева як на найнадійніший захист від нестабільності зовнішнього мережевого середовища.
