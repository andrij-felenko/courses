# 📋 Довідник команд і конфігурації: Git Submodules та Git Subtree

Цей довідник містить повну специфікацію параметрів конфігураційного файлу `.gitmodules`, команд інтерфейсу командного рядка `git submodule` та `git subtree`, а також опис низькорівневих структур об'єктів Git для роботи з вкладеними деревами вихідного коду.

---

## 1. Специфікація конфігураційного файлу .gitmodules

Файл `.gitmodules` розміщується у корені робочого дерева батьківського репозиторію, версіонується разом із кодом проєкту та визначає декларативне зіставлення між локальними каталогами монтування й адресами віддалених сховищ. Файл використовує синтаксис конфігураційних файлів Git (подібний до формату INI) і складається з іменованих секцій виду `[submodule "<name>"]`.

```ini
[submodule "third_party/fmt"]
    path = third_party/fmt
    url = https://github.com/fmtlib/fmt.git
    branch = master
    update = checkout
    shallow = true
    ignore = untracked
```

### Таблиця параметрів секції `[submodule "<name>"]`

| Параметр | Тип | Обов'язковий | Призначення, допустимі значення та поведінка |
| :--- | :--- | :--- | :--- |
| `path` | Шлях | **Так** | Відносний шлях від кореня робочого дерева батьківського репозиторію до підкаталогу, куди монтується робоче дерево підмодуля. |
| `url` | URL / Шлях | **Так** | Адреса віддаленого або локального сховища. Підтримує протоколи `https://`, `git://`, `ssh://` (`git@...`), а також відносні шляхи (`../other-repo.git`). |
| `branch` | Рядок | Ні | Назва віддаленої гілки для відстеження оновлень за допомогою команди `git submodule update --remote`. За замовчуванням: `HEAD` віддаленого репозиторію. |
| `update` | Перелік | Ні | Визначає процедуру оновлення робочого дерева під час виклику `git submodule update`: <br>• `checkout` (типово) — перемикання робочого дерева на зафіксований SHA у стані detached HEAD;<br>• `rebase` — автоматичне перебазування поточної локальної гілки підмодуля на зафіксований SHA;<br>• `merge` — злиття зафіксованого коміту в поточну локальну гілку;<br>• `!command` — виконання довільної оболонкової команди shell;<br>• `none` — повне ігнорування оновлення для цієї цілі. |
| `shallow` | Булевий | Ні | Якщо встановлено у `true`, первинне клонування підмодуля виконується з глибиною 1 (`--depth 1`), що завантажує виключно цільовий коміт без історії попередніх ревізій, заощаджуючи мережевий трафік та дисковий простір. |
| `ignore` | Перелік | Ні | Визначає рівень фільтрації змін у підмодулі для команди `git status` та `git diff`: <br>• `all` — повністю ігнорувати всі зміни (нові коміти, незакомічені правки, нові файли);<br>• `dirty` — ігнорувати робочі модифікації у файлах підмодуля, фіксувати виключно зміну зафіксованого commit SHA;<br>• `untracked` — ігнорувати лише невідстежувані нові файли всередині підмодуля;<br>• `none` (типово) — фіксувати будь-які локальні відхилення. |
| `fetchRecurseSubmodules` | Булевий / Перелік | Ні | Керує поведінкою команди `git fetch` у батьківському проєкті (`true`, `false`, `on-demand`). У режимі `on-demand` Git скачує нові коміти підмодуля лише тоді, коли батьківський коміт посилається на новий commit SHA. |

### Пріоритет налаштувань: .gitmodules проти .git/config

Важливо пам'ятати про ієрархію конфігурацій Git:
1. Файл `.gitmodules` задає публічні дефолтні налаштування для всіх розробників проєкту і фіксується у репозиторії.
2. Під час виконання команди `git submodule init` значення з `.gitmodules` копіюються у локальний конфігураційний файл `.git/config`.
3. Після ініціалізації Git зчитує URL-адресу та параметри оновлення виключно з `.git/config`. Будь-яке ручне редагування `.gitmodules` не матиме ефекту, поки не буде виконано команду `git submodule sync`.

## 2. Команди інтерфейсу `git submodule`

Утиліта `git submodule` є стандартним інструментом командного рядка для керування життєвим циклом вкладених репозиторіїв.

```bash
git submodule [--quiet] [--cached]
git submodule add [-b <branch>] [-f|--force] [--name <name>] [--reference <repo>] [--depth <depth>] [--] <repository> [<path>]
git submodule init [--] [<path>...]
git submodule deinit [-f|--force] (--all|[--] <path>...)
git submodule update [--init] [--remote] [-N|--no-fetch] [--merge|--rebase] [--recursive] [--depth <depth>] [--] [<path>...]
git submodule set-branch (-b <branch>|-d|--default) [--] <path>
git submodule set-url [--] <path> <newurl>
git submodule sync [--recursive] [--] [<path>...]
git submodule status [--cached] [--recursive] [--] [<path>...]
git submodule foreach [--recursive] <command>
git submodule absorbgitdirs [--] [<path>...]
```

### Детальний розбір підкоманд

#### `git submodule add`
Реєструє новий сторонній репозиторій у складі поточного проєкту:
1. Записує блок `[submodule "<path>"]` із параметрами `path` та `url` у файл `.gitmodules`.
2. Клонує базу об'єктів зовнішнього репозиторію у службовий каталог `.git/modules/<path>/`.
3. Створює робочий підкаталог `<path>` і розміщує всередині нього текстовий покажчик `.git` із рядком `gitdir: ../../.git/modules/<path>`.
4. Створює запис типу `160000 commit <SHA>` в індексі Git батьківського проєкту.

```bash
# Додавання бібліотеки з обмеженням глибини історії та прив'язкою до релізної гілки
git submodule add -b release-v2 --depth 1 https://github.com/gabime/spdlog.git third_party/spdlog
```

#### `git submodule init`
Копіює конфігураційні налаштування (шляхи монтування та URL-адреси) із файлу `.gitmodules` до локального файлу конфігурації репозиторію `.git/config`. Ця команда не виконує мережевих запитів і не завантажує файли на диск, вона лише активує підмодулі для подальшого оновлення.

#### `git submodule update`
Приводить стан робочих каталогів підмодулів у точну відповідність до значень commit SHA, які зафіксовані в поточному коміті батьківського репозиторію.
* `--init` — автоматично виконує `git submodule init` для всіх підмодулів, які ще не були зареєстровані у локальному `.git/config`.
* `--recursive` — рекурсивно обходить усі вкладені сабмодулі другого, третього та наступних рівнів вкладеності.
* `--remote` — замість зафіксованого в індексі коміту завантажує найсвіжіший стан із віддаленої гілки, зазначеної у параметрі `branch` файлу `.gitmodules`.
* `--rebase` або `--merge` — інтегрує завантажений коміт у поточну робочу гілку підмодуля замість переведення робочого дерева у стан detached HEAD.

```bash
# Канонічна команда синхронізації всього дерева підмодулів після перемикання гілок
git submodule update --init --recursive
```

#### `git submodule status`
Виводить поточний стан кожного зареєстрованого підмодуля. Вивід містить спеціальний префіксний символ статусу перед commit SHA:
* ` ` (пробіл) — стан робочого дерева підмодуля повністю збігається із SHA, зафіксованим у батьківському коміті.
* `-` (мінус) — підмодуль ще не ініціалізовано на диску (робочий каталог порожній).
* `+` (плюс) — робоче дерево підмодуля переключено на інший commit SHA (наявні незафіксовані коміти або виконано перехід).
* `U` — підмодуль містить конфлікти злиття (merge conflicts), які потребують ручного вирішення.

```bash
$ git submodule status --recursive
 e69e60473215270258167f2b963a758d9a244463 third_party/fmt (v10.2.1)
+a89f30129bc41235123908129381203981203981 third_party/spdlog (v1.12.0-12-g8a9)
```

#### `git submodule deinit`
Виконує деактивацію підмодуля: видаляє відповідну секцію з локального файлу `.git/config` та видаляє всі файли з робочого підкаталогу на диску. При цьому база об'єктів у `.git/modules/<path>/` залишається недоторканою, що дозволяє швидко повторно активувати підмодуль без повторного скачування з Інтернету.

```bash
# Повне вимкнення та очищення підкаталогів усіх підмодулів
git submodule deinit -f --all
```

#### `git submodule sync`
Оновлює збережені адреси віддалених репозиторіїв у `.git/config` та `.git/modules/<path>/config` відповідно до актуальних значень, зазначених у файлі `.gitmodules`. Застосовується після того, як адреса віддаленого сховища бібліотеки змінилася або була перенесена на новий домен.

#### `git submodule foreach`
Запускає довільну команду або оболонковий скрипт по черзі всередині робочого каталогу кожного активного підмодуля. Команді доступні спеціальні змінні оточення:
* `$name` — ім'я підмодуля згідно з `.gitmodules`.
* `$sm_path` — шлях до підкаталогу підмодуля відносно кореня батьківського проєкту.
* `$displaypath` — шлях підмодуля від поточного робочого каталогу.
* `$sha1` — зафіксований 40-символьний хеш коміту підмодуля.
* `$toplevel` — абсолютний шлях до кореня головного репозиторію.

```bash
# Масове створення однакової робочої гілки в усіх підмодулях проєкту
git submodule foreach --recursive 'git checkout -b feature-upgrade'
```

#### `git submodule absorbgitdirs`
Шукає всі застарілі каталоги `.git`, які фізично знаходяться всередині підкаталогів підмодулів (типово для старих версій Git), переносить їх у структуру `.git/modules/<path>/` батьківського сховища та створює коректні файли-покажчики `gitdir: ...`.

## 3. Процедура повного видалення підмодуля

Утиліта Git не має окремої команди `git submodule remove`. Коректне та повне видалення підмодуля з репозиторію вимагає виконання суворої 5-крокової послідовності:

```bash
# Крок 1. Деініціалізація підмодуля (очищення .git/config та робочих файлів)
git submodule deinit -f third_party/fmt

# Крок 2. Видалення запису з індексу Git та файлу .gitmodules
git rm -f third_party/fmt

# Крок 3. Видалення фізичного сховища об'єктів підмодуля (запобігає засміченню .git)
rm -rf .git/modules/third_party/fmt

# Крок 4. Фіксація змін у батьківському репозиторії
git commit -m "Remove fmt submodule from third_party"

# Крок 5. Перевірка відсутності залишкових записів
git status
```

## 4. Внутрішня будова об'єктів Git (gitlink)

На рівні низькорівневої об'єктної моделі Git підмодуль не є каталогом і не є файлом. Він записується в об'єкт дерева репозиторію як спеціальний елемент — **gitlink**.

### Розбір виводу команди `git ls-tree`

```text
$ git ls-tree HEAD third_party/fmt
160000 commit e69e60473215270258167f2b963a758d9a244463	third_party/fmt
```

### Структура елементів запису дерева:
1. **`160000`** — спеціальний вісімковий бітовий режим доступу файлової системи (POSIX mode). Значення `160000` (двійкова константа `S_IFGITLINK`) повідомляє системі Git, що цей запис є символічним посиланням на коміт в іншому репозиторії, а не звичайним файлом (`100644`), виконуваним бінарником (`100755`) чи каталогом (`040000`).
2. **`commit`** — тип цільового об'єкта Git. Покажчик адресує виключно об'єкт коміту.
3. **`e69e6047321527025816...`** — 40-символьний SHA-1 (або 64-символьний SHA-256) геш-ідентифікатор коміту у базі стороннього сховища.
4. **`third_party/fmt`** — шлях монтування всередині дерева батьківського проєкту.

### Ручне маніпулювання покажчиками gitlink через низькорівневі команди (Plumbing)

Для скриптів автоматизації та інструментів CI зміну версії підмодуля можна здійснити безпосередньо через команди низького рівня без клонування вмісту на диск:

```bash
# Низькорівневе оновлення gitlink безпосередньо в індексі Git
git update-index --add --cacheinfo 160000 e69e60473215270258167f2b963a758d9a244463 third_party/fmt

# Фіксація нового стану дерева
git commit -m "Bump fmt submodule commit SHA via plumbing"
```

## 5. Команди інтерфейсу `git subtree`

Модуль `git subtree` дозволяє інтегрувати сторонній репозиторій у підкаталог головного проєкту без створення спеціальних режимів `160000` і без файлу `.gitmodules`.

```bash
git subtree add   --prefix=<prefix> <repository> <ref> [--squash]
git subtree pull  --prefix=<prefix> <repository> <ref> [--squash]
git subtree push  --prefix=<prefix> <repository> <ref>
git subtree split --prefix=<prefix> [<commit>] [-b <new-branch>] [--rejoin]
git subtree merge --prefix=<prefix> <commit> [--squash]
```

### Таблиця параметрів команди `git subtree`

| Параметр | Призначення та особливості роботи |
| :--- | :--- |
| `--prefix=<каталог>` (або `-P`) | **Обов'язковий параметр**. Задає відносний шлях до каталогу всередині головного проєкту, де розміщується дерево підпроєкту. |
| `--squash` | Згортає всю історію комітів стороннього репозиторію в один єдиний синтетичний коміт. Запобігає засміченню журналу головного репозиторію тисячами проміжних правок сторонніх розробників. |
| `-m <текст>` (або `--message`) | Задає користувацьке повідомлення для згенерованого коміту злиття (merge commit). |
| `-b <назва-гілки>` (для `split`) | Створює локальну синтетичну гілку, яка містить виключно історію комітів, що зачіпали файли всередині каталогу `--prefix`. |
| `--rejoin` (для `split`) | Синтезує додатковий merge-коміт після створення гілки, що значно прискорює наступні виклики `split` на великих проєктах. |
| `--annotate=<префікс>` | Додає вказаний текстовий префікс до повідомлень усіх імпортованих комітів під час роботи без ключа `--squash`. |

### Практичні сценарії роботи з `git subtree`

#### 1. Додавання нової бібліотеки з об'єднанням історії
```bash
git subtree add --prefix=third_party/json https://github.com/nlohmann/json.git v3.11.3 --squash -m "Vendor nlohmann_json v3.11.3"
```

#### 2. Оновлення коду до нового релізу
```bash
git subtree pull --prefix=third_party/json https://github.com/nlohmann/json.git v3.11.4 --squash -m "Update nlohmann_json to v3.11.4"
```

#### 3. Експорт локальних доробок для апстріму
```bash
# Крок 1: Виділяємо локальні зміни каталогу third_party/json в окрему гілку
git subtree split --prefix=third_party/json -b patch-json-upstream

# Крок 2: Відправляємо згенеровану гілку у власний форк бібліотеки на GitHub
git push git@github.com:myuser/json.git patch-json-upstream:feature-fix
```

### Внутрішня механіка команди `git subtree split`

Команда `git subtree split` виконує реконструкцію спрямованого ациклічного графа комітів:
1. Вона ітерує по всій історії батьківської гілки від початкового коміту до поточної верхівки `HEAD`.
2. Для кожного коміту перевіряється, чи містив він зміни у файлах каталогу, заданого аргументом `--prefix`.
3. Якщо коміт змінював цільовий каталог, Git створює новий синтетичний коміт, у якому вміст підкаталогу переноситься у корінь нового дерева.
4. Повідомлення коміту, авторство та часові мітки зберігаються, а батьківські зв'язки перенаправляються на попередньо створені синтетичні коміти.
5. Наприкінці новостворена гілка отримує покажчик на верхівку згенерованого ізольованого графа.

## 6. Діагностика типових збоїв та повідомлень про помилки у CI/CD

| Текст повідомлення про помилку | Технічна першопричина | Інженерний алгоритм усунення |
| :--- | :--- | :--- |
| `fatal: reference is not a tree: <SHA>` | Батьківський репозиторій зафіксував новий SHA підмодуля, але автор не виконав `git push` усередині підмодуля на віддалений сервер. | Розробник повинен зайти в підкаталог підмодуля й виконати `git push origin <branch>`. |
| `fatal: No url found for submodule path '...' in .gitmodules` | Запис у дереві Git (`160000`) існує, але відповідну секцію в `.gitmodules` було видалено або перейменовано. | Відновити секцію в `.gitmodules` або видалити gitlink командою `git rm --cached <path>`. |
| `Host key verification failed / Permission denied (publickey)` | У `.gitmodules` прописано абсолютний SSH URL (`git@github.com:...`), а агент CI не має відповідного приватного SSH-ключа. | Використовувати відносні шляхи в `.gitmodules` (`../other-repo.git`) або налаштовувати перенаправлення `git config --global url."https://token@...".insteadOf "git@..."`. |
| `You are in 'detached HEAD' state` | `git submodule update` перемикає робоче дерево на зафіксований SHA без прив'язки до локальної гілки. | Перед внесенням правок виконати `git checkout -b my-feature-branch` усередині підкаталогу підмодуля. |
| `Submodule path '...' not initialized` | Проєкт клоновано звичайним `git clone` без прапорця `--recurse-submodules`. | Виконати команду `git submodule update --init --recursive` у корені репозиторію. |
| `fatal: refusing to merge unrelated histories` під час `git subtree pull` | Історія гілки головного проєкту та історія зовнішнього репозиторію не мають спільного предка (типово при повторних злиттях без `--squash`). | Додати прапорець `--squash` або використати `git merge --allow-unrelated-histories`. |
