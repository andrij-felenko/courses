Коли компілятор на робочій станції з процесором x86_64 отримує завдання зібрати виконуваний файл для 64-бітного ARM-контролера промислового контролера або плати Raspberry Pi, стандартний виклик системного компілятора аварійно завершується або створює бінарний файл, нездатний виконатися на цільовому процесорі. Причина полягає в тому, що нативний компілятор за замовчуванням генерує машинний код для архітектури поточного комп'ютера (хоста) та використовує хостові системні заголовки `/usr/include` разом із системними бібліотеками `/usr/lib`. Навіть якщо встановити крос-компілятор, здатний транслювати код в інструкції цільової архітектури, йому необхідні дві принципові сутності: однозначна специфікація цільової платформи — набір інструкцій, операційна система, двійковий інтерфейс викликів та тип системної бібліотеки, — а також ізольоване дерево системних файлів цільової системи, де розміщені заголовки та попередньо скомпільовані залежності.

Ці два завдання розв'язуються за допомогою цільового кортежу (Target Triple) та системного кореня (Sysroot). Кортеж задає правила кодогенерації, конвенції виклику функцій та формат двійкового артефакту, тоді як sysroot виступає віртуальним коренем цільової файлової системи, що гарантує детермінованість пошуку заголовків і бібліотек без випадкового затягування хостових файлів.

## Анатомія цільового кортежу (Target Triple)

Цільовий кортеж (Target Triple) — це канонічний текстовий рядок, розділений дефісами, який однозначно ідентифікує платформу виконання для компіляторів, компонувальників, асемблерів та систем збірки. Історично концепція тріплета виникла в екосистемі GNU Autotools (зокрема в утилітах `config.guess` та `config.sub`) на початку 1990-х років, де конфігурація задавалася трьома компонентами: архітектура процесора, постачальник платформи та операційна система (`arch-vendor-os`). З розвитком двійкових стандартів викликів і появою різноманітних реалізацій стандартних бібліотек C класичних трьох полів виявилося недостатньо, тому кортеж розширився до чотирьох сегментів (`arch-vendor-os-abi`), проте назва «тріплет» закріпилася як загальноприйнятий термін в індустрії.

Канонічна структура сучасного цільового кортежу має такий вигляд:

```
[arch]-[vendor]-[os]-[abi/libc]
```

![Анатомія та декомпозиція цільового кортежу (Target Triple)](/root/sys/sys-bsystem/target-triple-sysroot/img/target-triple-anatomy.svg)
*Анатомія цільового кортежу (Target Triple): склад полів архітектури, постачальника, операційної системи та двійкового інтерфейсу з прикладами реальних систем.*

Кожен сегмент кортежу відповідає за строго визначений рівень абстракції апаратного та програмного забезпечення.

### 1. Архітектура процесора (`arch`)

Поле архітектури визначає систему команд (ISA — Instruction Set Architecture), розрядність регістрів загального призначення, порядок слідування байтів у пам'яті (endianness) та підтримуваний набір векторних чи скалярних інструкцій. Це поле безпосередньо керує бекендом компілятора (наприклад, LLVM Target Architecture або GCC machine description), визначаючи, які асемблерні мнемоніки та машинне кодування будуть згенеровані.

Типові позначення архітектур:
- `x86_64` (або `amd64`): 64-бітна архітектура x86 із порядком байтів Little-Endian;
- `i686` / `i386`: 32-бітна архітектура x86;
- `aarch64`: 64-бітна архітектура ARMv8-A / ARMv9-A (Little-Endian);
- `aarch64_be`: 64-бітна архітектура ARMv8-A у режимі Big-Endian;
- `armv7-a` / `armv7l`: 32-бітна архітектура ARMv7 для прикладних процесорів (Cortex-A);
- `thumbv7em`: 32-бітна архітектура ARMv7E-M із набором інструкцій Thumb-2 та розширеннями DSP/FPU (мікроконтролери Cortex-M4 / Cortex-M7);
- `riscv64`: 64-бітна архітектура RISC-V (зазвичай із базовим набором `rv64gc` — General purpose + Compressed);
- `mips64el`: 64-бітна архітектура MIPS у режимі Little-Endian.

### 2. Виробник / постачальник (`vendor`)

Поле постачальника вказує на організацію або середовище, що створило чи налаштувало дистрибутив платформи. У більшості сучасних систем загального призначення це поле не впливає на кодогенерацію процесорних інструкцій і встановлюється в значення `unknown`, `none` або `pc` (для персональних комп'ютерів на базі x86). Проте в спеціалізованих тулчейнах або операційних системах поле вендора несе функціональне навантаження:

- `apple`: платформи macOS, iOS, watchOS, tvOS (наприклад, `arm64-apple-darwin23.0.0` або `arm64-apple-ios`);
- `w64`: тулчейн MinGW-w64 для збірки бінарних файлів Windows (`x86_64-w64-mingw32`);
- `poky`: дистрибутив і тулчейн, згенерований мета-системою Yocto Project / OpenEmbedded;
- `alpine`: дистрибутив Linux на базі musl libc (`x86_64-alpine-linux-musl`);
- `none`: автономні системи без прив'язки до виробника чи операційної системи (наприклад, `arm-none-eabi`).

### 3. Операційна система (`os`)

Поле операційної системи визначає ядро та тип середовища, яке забезпечує системні виклики (syscalls), обробку сигналів, керування віртуальною пам'яттю та завантаження виконуваних файлів:

- `linux`: операційні системи на базі ядра Linux (системні виклики здійснюються через інструкції `syscall` на x86_64 або `svc #0` на ARM);
- `windows`: операційна система Microsoft Windows;
- `darwin`: ядро XNU та середовище Apple (macOS, iOS);
- `freebsd` / `openbsd` / `netbsd`: операційні системи сімейства BSD;
- `none`: відсутність операційної системи (Bare-metal прошивки для мікроконтролерів, код завантажувача bootloader або ядро ОС на етапі ініціалізації).

### 4. Двійковий інтерфейс та системна бібліотека (`abi/libc`)

Останнє поле кортежу визначає ABI (Application Binary Interface) — правила взаємодії бінарних модулів між собою та з ядром операційної системи. Сюди входять конвенція передачі параметрів у функції (через які регістри передаються цілочисельні аргументи та числа з плаваючою комою), вирівнювання структур у пам'яті (data alignment), формат винятків (exception handling format), а також використовувана системна бібліотека C (libc):

- `gnu`: двійковий інтерфейс GNU/Linux зі стандартною бібліотекою GNU C Library (glibc);
- `musl`: двійковий інтерфейс Linux із полегшеною стандартною бібліотекою musl libc (широко застосовується в Alpine Linux та контейнерах завдяки простоті статичного лінкування);
- `eabi`: Embedded ABI для архітектури ARM. Означає використання стандартних правил розміщення даних і викликів для вбудованих систем, зазвичай у поєднанні зі стандартною бібліотекою Newlib або Picolibc;
- `gnueabi` / `gnueabihf`: розширення для 32-бітного ARM Linux:
  - `gnueabi` (Soft-Float): аргументи функцій із плаваючою комою передаються через цілочисельні регістри загального призначення (`r0-r3`);
  - `gnueabihf` (Hard-Float): аргументи з плаваючою комою передаються безпосередньо через спеціалізовані апаратні регістри FPU/NEON (`s0-s15`, `d0-d7`). Бінарні об'єкти `gnueabi` та `gnueabihf` є несумісними між собою і не можуть лінкуватися в одну програму;
- `android` / `androideabi`: середовище операційної системи Android з бібліотекою Bionic libc;
- `msvc`: двійковий інтерфейс Microsoft Visual C++ для Windows (використовує Universal CRT / MSVCRT та конвенцію Microsoft x64 calling convention);
- `mingw32`: середовище MinGW для Windows із сумісністю з GCC.

### Реалізація тріплета в компіляторних ланцюгах

В екосистемі GNU (GCC та Binutils) для кожного цільового тріплета збирається окремий набір виконуваних файлів компіляторного ланцюга. Ім'я кожної утиліти починається з префікса цільового тріплета:

```bash
aarch64-linux-gnu-gcc -O2 main.c -o main.o
aarch64-linux-gnu-g++ -O2 app.cpp -o app.o
aarch64-linux-gnu-ld main.o app.o -o firmware.elf
aarch64-linux-gnu-objdump -d firmware.elf
```

В екосистемі Clang / LLVM підхід принципово відрізняється: виконуваний файл компілятора `clang` є універсальним і підтримує всі архітектури одночасно. Цільовий тріплет передається компілятору через командний рядок за допомогою прапорця `--target`:

```bash
clang --target=aarch64-linux-gnu -O2 main.c -c -o main.o
clang --target=arm-none-eabi -mcpu=cortex-m4 -mthumb -O2 main.c -c -o main.o
```

## Концепція Sysroot: ізоляція системного оточення

Цільовий тріплет дає компілятору розуміння того, як перетворювати вихідний код на машинний код цільового процесора. Проте код рідко існує у вакуумі: він підключає заголовні файли стандартної бібліотеки (`<stdio.h>`, `<pthread.h>`, `<sys/socket.h>`), звертається до сторонніх бібліотек (`<openssl/ssl.h>`, `<zlib.h>`) та лінкується з бінарними модулями (`libc.so`, `libcrypto.so`).

На нативній системі компілятор автоматично переглядає каталоги `/usr/include`, `/usr/local/include`, а лінкер — `/usr/lib`, `/lib`, `/usr/lib/x86_64-linux-gnu`. У разі крос-компіляції пряме використання цих каталогів є неприпустимим: вони містять заголовки та бібліотеки *хостової* системи збірки.

**Sysroot (System Root)** — це ізольований каталог у файловій системі комп'ютера збірки, структура підкаталогів якого повністю відтворює кореневу файлову систему цільової операційної системи. Sysroot містить усі системні заголовки, системні та сторонні бібліотеки, скомпільовані виключно під цільову платформу.

![Концепція Sysroot: ізоляція цільових заголовків та бібліотек від хоста](/root/sys/sys-bsystem/target-triple-sysroot/img/sysroot-directory-structure.svg)
*Концепція Sysroot: перенаправлення системних шляхів пошуку заголовків і бібліотек на ізольовану файлову структуру цільової платформи.*

Типова внутрішня структура каталогу sysroot має такий вигляд:

```
/opt/sysroots/aarch64-linux-gnu/
├── lib/
│   ├── ld-linux-aarch64.so.1
│   ├── libc.so.6
│   └── libm.so.6
├── usr/
│   ├── include/
│   │   ├── aarch64-linux-gnu/
│   │   │   ├── asm/
│   │   │   └── bits/
│   │   ├── openssl/
│   │   ├── pthread.h
│   │   ├── stdio.h
│   │   └── zlib.h
│   ├── lib/
│   │   ├── aarch64-linux-gnu/
│   │   │   ├── libc.so
│   │   │   ├── libcrypto.so -> libcrypto.so.3
│   │   │   ├── libcrypto.so.3
│   │   │   └── pkgconfig/
│   │   └── libz.so
│   └── share/
│       └── pkgconfig/
└── etc/
```

### Небезпека «отруєння» хостовими файлами (Host Contamination)

Якщо компілятор або лінкер під час крос-збірки випадково підхопить хостовий файл, виникає одна з двох критичних проблем:

1. **Отруєння заголовками (Header Contamination / ABI Mismatch):**
   Системні заголовні файли на різних архітектурах та версіях ядер містять різні визначення констант, розмірів базових типів та розкладок структур. Наприклад, структура інформації про файл `struct stat` у системному заголовку `<sys/stat.h>` на 64-бітному x86_64 хості містить інші зсуви полів (field offsets), ніж на 32-бітному ARM цільовому пристрої. Якщо крос-компілятор для 32-бітного ARM підхопить заголовок із хостового `/usr/include`, він згенерує бінарний код, що очікує 64-бітні поля та хостове вирівнювання. На цільовому пристрої під час системного виклику `stat()` ядро Linux запише в пам'ять дані за 32-бітною структурою ARM, що призведе до тихого спотворення пам'яті (memory corruption), некоректних даних або аварійної зупинки процесу (Segmentation Fault) під час виконання.

2. **Отруєння бібліотеками (Link Pollution):**
   Якщо системний компонувальник спробує підтягнути динамічну бібліотеку з хостового каталогу `/usr/lib/x86_64-linux-gnu/libssl.so`, лінкер виявить несумісність архітектур ELF і викине помилку `skipping incompatible /usr/lib/... when searching for -lssl`.
   
   Проте найнебезпечніший сценарій виникає, коли архітектури процесорів хоста й цілі збігаються (наприклад, обидва є `x86_64`), але вони працюють на різних версіях дистрибутивів або з різними C-рантаймами (наприклад, хост на Ubuntu 24.04 з glibc 2.39, а цільовий промисловий комп'ютер на Debian 11 з glibc 2.31). Якщо лінкер зв'яже програму з хостовою бібліотекою glibc, виконуваний файл скомпілюється без жодних помилок, але під час запуску на цільовому пристрої динамічний завантажувач відмовиться запускати процес із фатальною помилкою версіонування символів:
   ```
   ./application: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.38' not found (required by ./application)
   ```

### Пастка абсолютних символічних посилань (Absolute Symlink Trap)

Один із найпоширеніших дефектів при формуванні та експорті sysroot — це наявність абсолютних символічних посилань (symlinks) усередині цільової файлової системи.

У класичній установці Linux файл спільної бібліотеки `/usr/lib/aarch64-linux-gnu/libz.so` часто є символічним посиланням на реальний файл `/lib/aarch64-linux-gnu/libz.so.1`. Якщо скопіювати файлову систему цільового пристрою в каталог на хості `/opt/sysroots/aarch64`, посилання збереже свій абсолютний шлях:

```
/opt/sysroots/aarch64/usr/lib/libz.so -> /lib/aarch64-linux-gnu/libz.so.1
```

Коли крос-компонувальник на хості намагається відкрити цей файл, операційна система хоста розв'язує абсолютне посилання від *свого власного кореня* `/` і намагається прочитати файл `/lib/aarch64-linux-gnu/libz.so.1`. Оскільки на хості x86_64 такого файлу немає (або там лежить несумісний x86_64 бінарник), компонувальник завершує роботу з помилкою `cannot find -lz`.

Для усунення цієї проблеми всі абсолютні символічні посилання всередині sysroot підлягають обов'язковій конвертації у відносні шляхи (наприклад, `/opt/sysroots/aarch64/usr/lib/libz.so -> ../../lib/aarch64-linux-gnu/libz.so.1`), або лінкер має запускатися з підтримкою внутрішнього резолвінгу шляхів через параметр `--sysroot`.

## Прапорці компілятора та лінкера для роботи з Sysroot

Компілятори GCC, Clang та компонувальники GNU ld, LLVM lld підтримують спеціалізований набір прапорців командного рядка для керування системним коренем та перенаправлення шляхів пошуку.

### Прапорець `--sysroot=<каталог>`

Прапорець `--sysroot` задає логічний корінь для пошуку стандартних заголовків та бібліотек. Коли компілятору передано `--sysroot=/opt/sysroots/arm64`, він автоматично модифікує свої вбудовані системні шляхи:

- Стандартний шлях пошуку заголовків `/usr/include` перетворюється на `/opt/sysroots/arm64/usr/include`;
- Стандартні шляхи пошуку бібліотек `/lib` та `/usr/lib` перетворюються на `/opt/sysroots/arm64/lib` та `/opt/sysroots/arm64/usr/lib`.

```bash
# Компіляція та лінкування з GCC
aarch64-linux-gnu-gcc --sysroot=/opt/sysroots/aarch64-linux-gnu \
    -O2 main.c -lz -o app

# Компіляція та лінкування з Clang
clang --target=aarch64-linux-gnu --sysroot=/opt/sysroots/aarch64-linux-gnu \
    -O2 main.c -lz -o app
```

### Префікс `=` у шляхах пошуку заголовків та бібліотек

Якщо розробник передає власні шляхи пошуку через прапорці `-I` або `-L`, він може використовувати спеціальний символ `=` (або змінну `$SYSROOT`) на початку шляху. Компілятор GCC та Clang автоматично замінює провідний знак `=` на поточний шлях до sysroot:

```bash
# Знак = замінюється на /opt/sysroots/aarch64-linux-gnu
aarch64-linux-gnu-gcc --sysroot=/opt/sysroots/aarch64-linux-gnu \
    -I=/opt/custom/include \
    -L=/opt/custom/lib \
    -lcustom main.c -o app
```

Якщо прапорець `--sysroot` не встановлено, префікс `=` просто ігнорується, і шлях розглядається як абсолютний.

### Прапорець системних заголовків `-isystem <каталог>`

Прапорець `-isystem` додає вказаний каталог до списку системних заголовків. На відміну від звичайного `-I`:
1. Шляхи з `-isystem` переглядаються після користувацьких шляхів `-I`, але перед стандартними системними шляхами sysroot;
2. Компілятор автоматично пригнічує всі попередження (warnings) для коду, розміщеного у файлах із каталогу `-isystem`. Це критично важливо під час підключення складних системних заголовків, які можуть генерувати попередження компілятора при суворих прапорцях `-Wall -Wextra -Werror`.

### Прапорці компонувальника: `-rpath-link` та `--with-sysroot`

Під час динамічного лінкування виконуваного файлу лінкер повинен розв'язати не лише прямі залежності (наприклад, `libA.so`, передану через `-lA`), але й транзитивні залежності другого рівня (наприклад, `libA.so` залежить від `libB.so`, що зафіксовано в секції `DT_NEEDED` бібліотеки `libA.so`).

На нативній системі компонувальник шукає транзитивні бібліотеки у стандартних каталогах `/lib` та `/usr/lib`. У режимі крос-компіляції лінкер не має права звертатися до хостових каталогів. Для цього компонувальнику GNU `ld` передається прапорець `-rpath-link`:

```bash
aarch64-linux-gnu-gcc --sysroot=/opt/sysroots/aarch64-linux-gnu \
    -Wl,-rpath-link=/opt/sysroots/aarch64-linux-gnu/usr/lib/aarch64-linux-gnu \
    -Wl,-rpath-link=/opt/sysroots/aarch64-linux-gnu/lib/aarch64-linux-gnu \
    main.o -lA -o app
```

Прапорець `-rpath-link` підказує лінкеру каталоги для пошуку транзитивних бібліотек *виключно під час компонування на машині збірки*, не записуючи ці хостові шляхи в результуючий бінарний файл ELF (на відміну від прапорця `-rpath`, який зберігає шлях у тезі `DT_RUNPATH` бінарника і призначений для виконання на цільовому пристрої).

## Налаштування CMake Toolchain для цільових платформ

Система збірки CMake підтримує повноцінну інтеграцію з крос-тулчейнами та sysroot через механізм файлу тулчейна (Toolchain File). Файл тулчейна передається команді CMake під час початкової конфігурації за допомогою змінної `-DCMAKE_TOOLCHAIN_FILE=path/to/toolchain.cmake` або декларується в `CMakePresets.json`.

![Політики маршрутизації пошуку в CMake: CMAKE_FIND_ROOT_PATH_MODE_*](/root/sys/sys-bsystem/target-triple-sysroot/img/cmake-find-root-path-matrix.svg)
*Політики маршрутизації пошуку в CMake: перенаправлення find_program на хостову систему та find_package/find_library на ізольований sysroot.*

### Ключові змінні конфігурації крос-збірки

Коректний файл тулчейна CMake встановлює такий набір обов'язкових змінних:

1. **`CMAKE_SYSTEM_NAME`:**
   Встановлює ім'я цільової операційної системи (`Linux`, `Generic` для bare-metal систем без ОС, `Windows`, `Darwin`, `Android`).
   > ⚠️ Встановлення змінної `CMAKE_SYSTEM_NAME` є ключовим сигналом для CMake, який автоматично переводить генератор у режим крос-компіляції та встановлює внутрішню змінну `CMAKE_CROSSCOMPILING = TRUE`.

2. **`CMAKE_SYSTEM_PROCESSOR`:**
   Вказує архітектуру цільового процесора (`aarch64`, `arm`, `x86_64`, `riscv64`). Ця змінна використовується модулями CMake для умовної генерації коду та прапорців.

3. **`CMAKE_SYSROOT`:**
   Задає абсолютний шлях до каталогу цільового sysroot. CMake автоматично додає відповідний прапорець `--sysroot=<path>` до викликів компіляторів C, C++ та компонувальника.

4. **`CMAKE_C_COMPILER` / `CMAKE_CXX_COMPILER`:**
   Вказує шляхи до виконуваних файлів компіляторів цільового ланцюга.

5. **`CMAKE_FIND_ROOT_PATH`:**
   Список кореневих каталогів, що використовуються пошуковими командами CMake (`find_program`, `find_library`, `find_path`, `find_file`, `find_package`). За замовчуванням ця змінна містить значення `CMAKE_SYSROOT`.

### Керування політиками пошуку `CMAKE_FIND_ROOT_PATH_MODE_*`

Найбільш критичною частиною налаштування CMake для крос-компіляції є розділення пошуку інструментів, які виконуються на хості, від заголовків та бібліотек, які лінуються під цільову систему. Для цього CMake використовує чотири змінні режимів:

- **`CMAKE_FIND_ROOT_PATH_MODE_PROGRAM`:**
  Керує поведінкою команди `find_program()`. Для цієї змінної встановлюється режим **`NEVER`**.
  *Обґрунтування:* Утиліти збірки, такі як кодогенератори `protoc` (Protocol Buffers), генератори лексерів/парсерів `flex`/`bison`, транслятори `wayland-scanner` або інтерпретатор `python3`, мусять запускатися безпосередньо на хостовому процесорі під час збірки. Якщо дозволити пошук у sysroot, CMake спробує викликати цільовий AArch64 бінарник на хості x86_64, що призведе до помилки `Exec format error`.

- **`CMAKE_FIND_ROOT_PATH_MODE_INCLUDE`:**
  Керує поведінкою команд `find_path()` та `find_file()`. Встановлюється режим **`ONLY`**.
  *Обґрунтування:* Пошук заголовків обмежується виключно каталогами всередині sysroot (`${CMAKE_SYSROOT}/usr/include`), блокуючи хостові системні шляхи.

- **`CMAKE_FIND_ROOT_PATH_MODE_LIBRARY`:**
  Керує поведінкою команди `find_library()`. Встановлюється режим **`ONLY`**.
  *Обґрунтування:* Пошук бінарних бібліотек для лінкування здійснюється лише в межах sysroot.

- **`CMAKE_FIND_ROOT_PATH_MODE_PACKAGE`:**
  Керує поведінкою команди `find_package()`. Встановлюється режим **`ONLY`**.
  *Обґрунтування:* Забезпечує, що файли конфігурацій `Config.cmake` та скрипти модулів шукатимуться лише в дереві цільової системи.

### Режими маршрутизації: `ONLY`, `NEVER` та `BOTH`

- `ONLY`: Пошук виконується *тільки* з додаванням префіксів із `CMAKE_FIND_ROOT_PATH`. Стандартні системні шляхи хоста повністю ігноруються.
- `NEVER`: Пошук виконується *тільки* за стандартними системними шляхами без додавання префіксів `CMAKE_FIND_ROOT_PATH`.
- `BOTH`: Спочатку перевіряються шляхи всередині `CMAKE_FIND_ROOT_PATH`, а якщо артефакт не знайдено — пошук повторюється на хостовій системі.
  > ⚠️ Використання режиму `BOTH` для бібліотек та заголовків є антипатерном і джерелом прихованих помилок. Якщо потрібна цільова бібліотека відсутня в sysroot, режим `BOTH` змусить CMake підхопити хостову версію бібліотеки, що спричинить аварію на стадії лінкування або збій у рантаймі.

### Еталонний файл Toolchain для Linux AArch64

Нижче наведено виробничий файл тулчейна для крос-компіляції під 64-бітний ARM Linux (AArch64) із використанням крос-GCC та ізольованого sysroot:

```cmake
# toolchain-aarch64-linux-gnu.cmake
# Цільова операційна система та архітектура
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)

# Визначення цільового тріплета
set(TARGET_TRIPLE aarch64-linux-gnu)

# Шлях до кореневої файлової системи цільової платформи
set(TARGET_SYSROOT "/opt/sysroots/aarch64-linux-gnu")
set(CMAKE_SYSROOT "${TARGET_SYSROOT}")

# Встановлення крос-компіляторів
set(CMAKE_C_COMPILER   "${TARGET_TRIPLE}-gcc")
set(CMAKE_CXX_COMPILER "${TARGET_TRIPLE}-g++")
set(CMAKE_ASM_COMPILER "${TARGET_TRIPLE}-gcc")

# Додаткові шляхи пошуку префіксів (наприклад, сторонні залежності)
list(APPEND CMAKE_PREFIX_PATH "${TARGET_SYSROOT}/usr/local")

# Налаштування політик пошуку
set(CMAKE_FIND_ROOT_PATH "${TARGET_SYSROOT}")
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)

# Додаткові прапорці лінкера для безпечного пошуку транзитивних бібліотек
set(CMAKE_EXE_LINKER_FLAGS_INIT "-Wl,-rpath-link,${TARGET_SYSROOT}/usr/lib/${TARGET_TRIPLE} -Wl,-rpath-link,${TARGET_SYSROOT}/lib/${TARGET_TRIPLE}")
set(CMAKE_SHARED_LINKER_FLAGS_INIT "-Wl,-rpath-link,${TARGET_SYSROOT}/usr/lib/${TARGET_TRIPLE} -Wl,-rpath-link,${TARGET_SYSROOT}/lib/${TARGET_TRIPLE}")
```

Запуск конфігурації проекту з цим файлом:

```bash
cmake -B build-arm64 -S . \
    -DCMAKE_TOOLCHAIN_FILE=cmake/toolchain-aarch64-linux-gnu.cmake \
    -DCMAKE_BUILD_TYPE=Release
cmake --build build-arm64 --parallel
```

## Формування, підготовка та супровід Sysroot

Створення надійного та узгодженого sysroot є ключовою передумовою стабільної крос-збірки. Залежно від вимог проекту та цільової платформи застосовують один із чотирьох практичних методів створення sysroot.

### 1. Генерація за допомогою `debootstrap` та QEMU (Debian / Ubuntu)

Для платформ, які працюють під керуванням дистрибутивів Debian або Ubuntu, чистий sysroot збирається безпосередньо з офіційних дзеркал пакетів без наявності фізичного пристрою. Оскільки пакети призначені для чужої архітектури, процес розбивається на дві стадії:

```bash
# 1. Завантаження базових deb-пакетів для AArch64 (перша стадія)
sudo debootstrap --arch=arm64 --foreign bookworm /opt/sysroots/debian-arm64 http://deb.debian.org/debian

# 2. Копіювання статичного емулятора QEMU user mode всередину sysroot
sudo cp /usr/bin/qemu-aarch64-static /opt/sysroots/debian-arm64/usr/bin/

# 3. Виконання другої стадії розгортання всередині емульованого chroot
sudo chroot /opt/sysroots/debian-arm64 /debootstrap/debootstrap --second-stage

# 4. Установка необхідних -dev пакетів заголовків та бібліотек
sudo chroot /opt/sysroots/debian-arm64 apt-get update
sudo chroot /opt/sysroots/debian-arm64 apt-get install -y \
    build-essential libssl-dev zlib1g-dev libsqlite3-dev

# 5. Видалення емулятора після завершення підготовки
sudo rm /opt/sysroots/debian-arm64/usr/bin/qemu-aarch64-static
```

### 2. Вивантаження з реального цільового пристрою (Target Extraction)

Якщо проект розробляється під готовий образ плати з пропрієтарними драйверами (наприклад, плати з SoC Allwinner, Rockchip або NVIDIA Jetson), найпростішим способом є пряма синхронізація кореневої файлової системи з працюючого пристрою через мережу за допомогою утиліти `rsync`:

```bash
# Синхронізація файлової системи плати з локальним каталогом sysroot
mkdir -p /opt/sysroots/target-board
rsync -avz --delete \
    --exclude='/proc/*' \
    --exclude='/sys/*' \
    --exclude='/dev/*' \
    --exclude='/run/*' \
    --exclude='/tmp/*' \
    --exclude='/mnt/*' \
    --exclude='/media/*' \
    --exclude='/home/*' \
    root@192.168.1.100:/ /opt/sysroots/target-board/
```

### 3. Автоматизована санація символічних посилань

Після вивантаження файлової системи з пристрою всі абсолютні символічні посилання в каталогах `/usr/lib` та `/lib` вказують на хостовий корінь. Для їх перетворення у відносні посилання використовується утиліта `symlinks`:

```bash
# Встановлення утиліти керування symlink
sudo apt-get install symlinks

# Конвертація всіх абсолютних посилань у відносні (прапорець -c) рекурсивно (-r)
symlinks -cr /opt/sysroots/target-board
```

Альтернативою є скрипт нормалізації symlinks на мові Python, який обходить дерево каталогів, перевіряє ціль кожного символічного посилання і, якщо воно є абсолютним, обчислює відносний шлях від каталогу розміщення посилання до файлу всередині sysroot:

```python
#!/usr/bin/env python3
import os, sys

def sanitize_sysroot_links(sysroot_dir):
    sysroot_dir = os.path.abspath(sysroot_dir)
    fixed_count = 0
    
    for root, dirs, files in os.walk(sysroot_dir):
        for name in files + dirs:
            full_path = os.path.join(root, name)
            if os.path.islink(full_path):
                target = os.readlink(full_path)
                # Якщо посилання починається з '/', воно абсолютне
                if target.startswith('/'):
                    # Обчислюємо новий абсолютний шлях усередині sysroot
                    new_target_abs = os.path.join(sysroot_dir, target.lstrip('/'))
                    # Обчислюємо відносний шлях від поточного каталогу
                    rel_target = os.path.relpath(new_target_abs, start=root)
                    os.unlink(full_path)
                    os.symlink(rel_target, full_path)
                    fixed_count += 1
                    
    print(f"Санація завершена: виправлено {fixed_count} абсолютних symlink.")

if __name__ == '__main__':
    if len(sys.argv) < 2:
        print("Використання: python3 sanitize_sysroot.py <каталог_sysroot>")
        sys.exit(1)
    sanitize_sysroot_links(sys.argv[1])
```

### 4. Генерація SDK у Buildroot та Yocto Project

У професійній розробці вбудованих систем (Embedded Linux) sysroot створюється автоматично системами генерації дистрибутивів:

- **Buildroot:** Під час збірки створює каталог `output/staging/`, який містить повноцінний sysroot з усіма скомпільованими бібліотеками та заголовками. Buildroot автоматично генерує скрипт `output/host/bin/aarch64-linux-gcc`, що викликає компілятор із попередньо налаштованим параметром `--sysroot=output/staging`.
- **Yocto Project:** Команда `bitbake <image-name> -c populate_sdk` генерує автономний саморозпаковуваний архів (SDK), що містить тулчейн, sysroot цільової платформи, а також файл налаштування оточення `environment-setup-<arch>-poky-linux`. Запуск `source environment-setup-...` експортує готові змінні `CC`, `CXX`, `CFLAGS`, `LDFLAGS` та `PKG_CONFIG_SYSROOT_DIR`.

## Інтеграція з pkg-config у крос-середовищі

Утиліта `pkg-config` є стандартним механізмом отримання прапорців компіляції (`--cflags`) та лінкування (`--libs`) для сторонніх бібліотек на основі текстових метаданих `.pc` (наприклад, `openssl.pc`, `libpng.pc`).

За замовчуванням системний `pkg-config` на хості звертається до хостового каталогу `/usr/lib/pkgconfig`. У режимі крос-компіляції такий виклик поверне хостові шляхи `-I/usr/include` та хостові прапорці лінкування, що спричинить отруєння збірки.

Для коректної роботи `pkg-config` у крос-середовищі використовуються три спеціальні змінні оточення:

1. **`PKG_CONFIG_SYSROOT_DIR`:**
   Задає базовий каталог sysroot. `pkg-config` автоматично додає значення цієї змінної до всіх шляхів `-I` та `-L`, які містяться у вихідних `.pc` файлах.
2. **`PKG_CONFIG_LIBDIR`:**
   Повністю перекриває стандартні системні каталоги пошуку `.pc` файлів. Необхідно вказати шляхи до каталогів `pkgconfig` усередині цільового sysroot.
3. **`PKG_CONFIG_PATH`:**
   Додаткові користувацькі каталоги для пошуку `.pc` файлів.

### Налаштування крос-обгортки pkg-config

Класичним рішенням є створення скрипта-обгортки з префіксом цільового тріплета, наприклад `/usr/local/bin/aarch64-linux-gnu-pkg-config`:

```bash
#!/bin/sh
SYSROOT="/opt/sysroots/aarch64-linux-gnu"
export PKG_CONFIG_SYSROOT_DIR="${SYSROOT}"
export PKG_CONFIG_LIBDIR="${SYSROOT}/usr/lib/aarch64-linux-gnu/pkgconfig:${SYSROOT}/usr/lib/pkgconfig:${SYSROOT}/usr/share/pkgconfig"
export PKG_CONFIG_PATH=""

exec pkg-config "$@"
```

У файлі тулчейна CMake інтеграція виконується шляхом встановлення змінної `PKG_CONFIG_EXECUTABLE`:

```cmake
# Перенаправлення FindPkgConfig на цільовий sysroot
set(PKG_CONFIG_EXECUTABLE "${TARGET_TRIPLE}-pkg-config" CACHE FILEPATH "Крос-обгортка pkg-config")
```

## Діагностика архітектурних розбіжностей у коді

Для перевірки коректності застосованого тріплета та системного кореня розробники використовують тестові утиліти діагностики, що зчитують вбудовані компіляторні макроси та визначають розміри фундаментальних типів даних цільової платформи.

Нижче наведено приклад діагностичної програми, яка перевіряє конфігурацію архітектури та параметри системних типів у режимі компіляції та виконання:

:::tabs
```c
/* diagnostic.c - перевірка цільової архітектури та розмірів типів */
#include <stdio.h>
#include <stdint.h>
#include <sys/types.h>

int main(void) {
    printf("=== ДІАГНОСТИКА ЦІЛЬОВОЇ ПЛАТФОРМИ ===\n");

#if defined(__x86_64__) || defined(_M_X64)
    printf("Архітектура CPU: x86_64 (64-bit AMD/Intel)\n");
#elif defined(__aarch64__)
    printf("Архітектура CPU: AArch64 (64-bit ARMv8-A)\n");
#elif defined(__arm__)
    printf("Архітектура CPU: ARM (32-bit)\n");
#elif defined(__riscv)
    printf("Архітектура CPU: RISC-V (%d-bit)\n", __riscv_xlen);
#else
    printf("Архітектура CPU: Невідома цільова архітектура\n");
#endif

#if defined(__BYTE_ORDER__) && __BYTE_ORDER__ == __ORDER_LITTLE_ENDIAN__
    printf("Порядок байтів: Little-Endian\n");
#elif defined(__BYTE_ORDER__) && __BYTE_ORDER__ == __ORDER_BIG_ENDIAN__
    printf("Порядок байтів: Big-Endian\n");
#endif

    printf("Розмір void*:   %zu байтів\n", sizeof(void*));
    printf("Розмір long:    %zu байтів\n", sizeof(long));
    printf("Розмір time_t:  %zu байтів\n", sizeof(time_t));
    printf("Розмір off_t:   %zu байтів\n", sizeof(off_t));

    return 0;
```

## Типові помилки та практичний чекліст діагностики

Під час налаштування та супроводу крос-збірок інженери регулярно стикаються з типовими діагностичними симптомами:

1. **Симптом: `cannot find /lib/libc.so.6 inside /opt/sysroot`**
   *Причина:* Абсолютне символічне посилання в sysroot не було перетворено у відносне, або системний скрипт лінкера `libc.so` містить абсолютні шляхи `GROUP ( /lib/libc.so.6 /usr/lib/libc_nonshared.a )`.
   *Вирішення:* Провести санацію символічних посилань утилітою `symlinks -cr` та переконатися, що компонувальнику передано прапорець `--sysroot`.

2. **Симптом: `skipping incompatible /usr/lib/... when searching for -lfoo`**
   *Причина:* CMake або система збірки переглянула хостовий каталог через некоректно встановлений режим `CMAKE_FIND_ROOT_PATH_MODE_LIBRARY BOTH`.
   *Вирішення:* Змінити режим пошуку на `ONLY` та переконатися, що бібліотека `libfoo.so` присутня у підкаталогах sysroot.

3. **Симптом: Помилка CMake `The C compiler is not able to compile a simple test program` під час крос-збірки Bare-metal**
   *Причина:* За замовчуванням внутрішня команда CMake `try_compile()` намагається зібрати повноцінний виконуваний ELF-файл. Для систем без операційної системи (`arm-none-eabi`) лінкер не може створити виконуваний файл без скрипта компонувача (Linker Script) та коду стартапу, які налаштовуються пізніше в цілях проекту.
   *Вирішення:* Додати у файл тулчейна рядок:
   ```cmake
   set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)
   ```
   Це змушує CMake тестувати працездатність компілятора через створення статичної бібліотеки архіватором (`ar`), не викликаючи лінкер.

4. **Симптом: Витік хостових шляхів через згенеровані конфігураційні файли (Hardcoded Host Paths)**
   *Причина:* Залежності, скомпільовані на машині збірки, зберегли абсолютні шляхи комп'ютера збірки (наприклад, `/home/user/workspace/...`) у файлах `MyLibTargets.cmake` або `.pc`.
   *Вирішення:* Використовувати імпортовані цілі CMake (`IMPORTED_TARGETS`) та відносні шляхи до префіксів (`${_IMPORT_PREFIX}`).

> 🔧 **Навіщо це.**
> Цільовий тріплет і sysroot є фундаментальним базисом інженерії крос-платформної розробки. Тріплет формалізує параметри мікроархітектури, бінарного інтерфейсу викликів та операційного середовища для бекенда компілятора. Sysroot створює герметичний простір системних контрактів, унеможливлюючи отруєння збірки несумісними хостовими заголовками чи бібліотеками. У поєднанні з прецизійно налаштованим файлом тулчейна CMake це перетворює збірку під чужі платформи — від мікроконтролерів без ОС до складних 64-бітних серверів — на надійний, передбачуваний та повністю детермінований процес.
