Команда `make install` або `cmake --install`, виконана з правами суперкористувача на робочій машині розробника, безповоротно змінює стан операційної системи. Якщо проект сконфігуровано без явного зазначення цільових шляхів, скомпільований бінарний файл потрапляє в `/usr/local/bin`, спільні бібліотеки опиняються в `/usr/local/lib`, а конфігураційні файли записуються в `/usr/local/etc`. Проте спроба зібрати з того самого вихідного коду дистрибутивний пакет для Debian (`.deb`) або Red Hat (`.rpm`) миттєво стикається з фундаментальним протиріччям: пакувальник повинен скомпілювати програму так, щоб вона знала про своє майбутнє розміщення в системному каталозі `/usr`, але під час складання пакета жоден файл не має права потрапити у реальний каталог `/usr` хост-машини.

Прямий запис артефактів у системні каталоги під час складання пакета не лише вимагає небезпечних прав `root` на сервері безперервної інтеграції (CI), але й змішує файли нової програми з файлами поточної операційної системи, унеможливлюючи точний облік розміщених файлів. Розв'язання цієї проблеми спирається на суворе математичне та архітектурне розмежування двох сутностей: цільового префікса встановлення (**PREFIX**) та тимчасового каталогу проміжного монтування (**DESTDIR**).

## Ієрархія файлової системи: де пролягають межі власності

Операційні системи сімейства Unix та Linux організовують зберігання файлів згідно зі стандартом **Filesystem Hierarchy Standard (FHS)**. Стандарт визначає не просто набір назв папок, а суворі зони відповідальності: хто має право записувати файли в конкретний каталог і як довго ці файли зберігають свою актуальність.

![Ієрархія просторів FHS у системі Linux](/root/sys/sys-bsystem/install-prefix-and-destdir/img/fig-fhs-hierarchy.svg)

*Ієрархія просторів FHS: чітке розмежування каталогів дистрибутива, локального адміністратора, окремих застосунків та домашнього каталогу користувача.*

У сучасній системі виділяються чотири ключові рівні розміщення програмного забезпечення:

### 1. Каталог /usr: простір операційної системи та дистрибутивних пакетів

Каталог `/usr` містить усі програми, бібліотеки, заголовки та ресурси, якими керує системний менеджер пакетів операційної системи (`apt`, `dnf`, `pacman`, `apk`). 

- `/usr/bin` — виконувані файли програм загального призначення.
- `/usr/lib` (або `/usr/lib64`, `/usr/lib/x86_64-linux-gnu`) — динамічні спільні бібліотеки (`.so`), модулі ядра та плагіни.
- `/usr/include` — публічні заголовкові файли мов C та C++ (`.h`, `.hpp`), які використовуються системним компілятором за замовчуванням.
- `/usr/share` — архітектурно-незалежні статичні дані: локалізовані повідомлення (`share/locale`), сторінки довідки (`share/man`), іконки, теми інтерфейсу та схеми баз даних.

Головне правило системної інженерії: **користувачам і ручним збіркам заборонено писати у `/usr`**. Якщо розробник виконає ручний виклик `cmake -B build -DCMAKE_INSTALL_PREFIX=/usr && cmake --install build` із правами `sudo`, система скопіює файли просто поверх системних бібліотек. Наступне оновлення системи через системний пакетний менеджер або мовчки перезапише ці файли своєю версією, або впаде з фатальною помилкою конфлікту контрольних сум.

Історично існував ще й кореневий поділ між `/bin` та `/usr/bin`, що виник через апаратні обмеження дисків PDP-11 у 1971 році. Про те, як брак дискового простору породив сорокарічний поділ файлових систем і чому сучасний Linux ліквідував його через реформу UsrMerge, детально викладено у довідці: [історія розділення / та /usr](root:sys-bsystem/install-prefix-and-destdir/hist-slash-usr-split.md).

### 2. Каталог /usr/local: простір системного адміністратора

Каталог `/usr/local` за структурою повністю повторює `/usr` (`/usr/local/bin`, `/usr/local/lib`, `/usr/local/include`, `/usr/local/share`), але має принципово іншого власника. Сюди встановлюються програми, які системний адміністратор збирає з вихідного коду вручну, або інструменти, встановлені поза межами офіційних сховищ дистрибутива.

- Системні пакетні менеджери (`dpkg`, `rpm`) **ніколи** не записують файли в `/usr/local`. Оновлення операційної системи гарантовано не зачіпає вміст цього каталогу.
- За замовчуванням більшість систем збірки (зокрема GNU Autotools та CMake) використовують саме `/usr/local` як значення префікса за замовчуванням.
- Змінна середовища `$PATH` у більшості дистрибутивів налаштована так, що `/usr/local/bin` передує `/usr/bin`. Це дозволяє адміністратору встановити новішу версію утиліти (наприклад `git` чи `cmake`), яка автоматично перекриває застарілу версію, надану дистрибутивом.

### 3. Каталог /opt: автономні сторонні пакети

Каталог `/opt` призначений для встановлення великих, самодостатніх програмних комплексів від сторонніх виробників (наприклад Google Chrome, CLion, MATLAB, NVIDIA CUDA). 

На відміну від `/usr` та `/usr/local`, де файли одного пакета розкидаються по спільних каталогах `bin/`, `lib/` та `share/`, усередині `/opt` кожен програмний продукт отримує власний ізольований підкаталог: `/opt/google/chrome` або `/opt/cuda`. Увесь бінарний код, внутрішні приватні бібліотеки, скрипти запуску та ресурси зберігаються виключно в цій ізольованій гілці. Для інтеграції з системою такий пакет зазвичай створює лише одне символьне посилання у `/usr/local/bin` або додає `.desktop`-файл у `/usr/share/applications`.

### 4. Каталог ~/.local: користувацька ієрархія XDG

Для встановлення програм без прав суперкористувача `root` використовується підкаталог `~/.local` у домашньому каталозі поточного користувача. Ця структура стандартизована специфікацією **XDG Base Directory Specification**:

- `~/.local/bin` — виконувані файли (сюди потрапляють утиліти, встановлені через `pip install --user`, `cargo install` або локальну збірку).
- `~/.local/lib` — бібліотеки користувача.
- `~/.local/share` — дані додатків (`$XDG_DATA_HOME`).

Встановлення в `~/.local` досягається передачею прапорця `-DCMAKE_INSTALL_PREFIX=$HOME/.local` під час конфігурації CMake і не вимагає жодних привілеїв адміністратора.

## Префікс встановлення (PREFIX): чому шляхи зашиваються під час компіляції

Префікс встановлення (**PREFIX**, у CMake змінна `CMAKE_INSTALL_PREFIX`) — це корінь логічного дерева файлової системи, відносно якого програма очікує знайти всі свої компоненти під час запуску та виконання.

Поширена помилка розробників-початківців полягає в уявленні, ніби скомпільований двійковий файл є абсолютно незалежним від свого положення на диску, а операція встановлення зводиться до банального переміщення файлів. У мовах C та C++ це не так: значна частина шляхів фіксується у машинному коді та заголовках ELF-бінарника ще на стадії компіляції та лінкування.

### 1. Вшиті шляхи до ресурсів, локалей та конфігурацій

Виконуваному файлу під час роботи потрібен доступ до допоміжних файлів: шаблонів інтерфейсу, іконок, сертифікатів безпеки або бінарних каталогів перекладу `gettext` (`.mo`). 

У коді програми ці шляхи зазвичай формуються за допомогою макросів компілятора, які система збірки передає через прапорці `-D`:

:::tabs
@tab C
```c
#include <stdio.h>
#include <libintl.h>
#include <locale.h>

#ifndef APP_DATADIR
#define APP_DATADIR "/usr/local/share/myapp"
#endif

#ifndef APP_LOCALEDIR
#define APP_LOCALEDIR "/usr/local/share/locale"
#endif

void init_resources(void) {
    setlocale(LC_ALL, "");
    bindtextdomain("myapp", APP_LOCALEDIR);
    textdomain("myapp");

    char config_path[512];
    snprintf(config_path, sizeof(config_path), "%s/config.default.json", APP_DATADIR);
    
    FILE* f = fopen(config_path, "r");
    if (!f) {
        perror("Не вдалося відкрити базову конфігурацію");
    } else {
        fclose(f);
    }
}
```
@tab C++
```cpp
#include <iostream>
#include <filesystem>
#include <fstream>
#include <libintl.h>
#include <locale.h>

#ifndef APP_DATADIR
#define APP_DATADIR "/usr/local/share/myapp"
#endif

#ifndef APP_LOCALEDIR
#define APP_LOCALEDIR "/usr/local/share/locale"
#endif

void init_resources() {
    namespace fs = std::filesystem;

    std::setlocale(LC_ALL, "");
    bindtextdomain("myapp", APP_LOCALEDIR);
    textdomain("myapp");

    const fs::path config_path = fs::path(APP_DATADIR) / "config.default.json";
    
    std::ifstream file(config_path);
    if (!file.is_open()) {
        std::cerr << "Не вдалося відкрити базову конфігурацію за шляхом: " 
                  << config_path << '\n';
    }
}
```
:::

Якщо під час конфігурації було встановлено префікс `/usr/local`, макрос `APP_DATADIR` перетвориться на жорсткий рядковий літерал `"/usr/local/share/myapp"`, розміщений у секції констант `.rodata` виконуваного файлу. Якщо згодом цей файл просто перемістити в каталог `/opt/myapp/bin`, програма продовжить шукати свої ресурси за старою адресою в `/usr/local/share/myapp` і завершиться аварійно через відсутність файлів.

### 2. Рядок Shebang в інтерпретованих сценаріях

Якщо проєкт встановлює допоміжні скрипти на мовах Python, Perl або Bash (наприклад утиліту керування базою даних або діагностичний агент), система збірки під час інсталяції підставляє точний шлях до інтерпретатора в перший рядок файлу:

```python
#!/usr/bin/python3
# Цей шлях генерується системою збірки відносно цільового префікса середовища
```

Якщо скрипт збирається для специфічного віртуального оточення або замкненого префікса, жорсткий шлях у `shebang` прив'язує сценарій до конкретної версії середовища виконання.

### 3. Шляхи пошуку динамічних бібліотек: RPATH та RUNPATH

Коли виконуваний файл лінкується з нестандартною спільною бібліотекою (яка не лежить у системних шляхах динамічного завантажувача на кшталт `/lib` чи `/usr/lib`), лінкер записує в ELF-заголовок секцію `DT_RPATH` або `DT_RUNPATH`. 

Якщо система збірки встановлює бібліотеку в `/opt/company/lib`, а бінарник — у `/opt/company/bin`, лінкер записує в бінарник абсолютний шлях `/opt/company/lib`. Під час старту програми динамічний завантажувач ядра `ld.so` зчитує цей заголовок і шукає спільні об'єкти саме за цим абсолютним шляхом.

### 4. Метадані для споживачів: файли pkg-config (.pc)

Бібліотечні пакети під час інсталяції генерують описові файли для утиліти `pkg-config` (наприклад `libfoo.pc`). У цих файлах префікс фіксується у вигляді базової змінної:

```ini
prefix=/usr
exec_prefix=${prefix}
libdir=${exec_prefix}/lib
includedir=${prefix}/include

Name: libfoo
Description: Приклад бібліотеки C++
Version: 1.0.0
Libs: -L${libdir} -lfoo
Cflags: -I${includedir}
```

Зовнішні компілятори викликають `pkg-config --cflags libfoo` і отримують точний шлях до заголовків `-I/usr/include`. Якщо префікс у `.pc`-файлі не відповідає реальному розміщенню бібліотеки, зовнішні проєкти не зможуть скомпілюватися.

## Механіка DESTDIR: ізольоване встановлення для пакувальників

Коли розробник дистрибутива створює пакет Debian (`.deb`), Red Hat (`.rpm`), Arch Linux (`PKGBUILD`) чи Alpine (`apk`), виникає завдання пакування.

Розглянемо, що має відбутися:
1. Бінарні файли повинні містити всередині себе префікс `PREFIX=/usr` (щоб утиліти шукали файли в `/usr/share`, а `pkg-config` вказував на `/usr/lib`).
2. Проте на стадії збірки пакета файли **не можна** копіювати в `/usr` хост-системи.
3. Файли мають бути розміщені у спеціальному тимчасовому каталозі пісочниці (**Staging Root** / **Fake Root**), наприклад `/tmp/build-pkg-12345/`.
4. Усередині цього тимчасового каталогу має бути відтворена повна структура цільових каталогів:
   ```
   /tmp/build-pkg-12345/
   └── usr/
       ├── bin/
       │    └── myapp
       ├── lib/
       │    └── libmycore.so
       └── share/
            └── myapp/
                 └── data.json
   ```
5. Пакетний менеджер архівує вміст папки `/tmp/build-pkg-12345/`, відкидаючи тимчасовий шлях `/tmp/build-pkg-12345`, і створює двійковий пакет `.deb` чи `.rpm`.
6. Коли кінцевий користувач встановлює готовий пакет через `apt install` або `dnf install`, файли розпаковуються з кореня файлової системи просто в реальний `/usr`.

Інструментом, який робить це можливим, є змінна **DESTDIR** (Destination Directory).

![Рівняння DESTDIR + PREFIX: розведення шляхів копіювання та виконання](/root/sys/sys-bsystem/install-prefix-and-destdir/img/fig-destdir-equation.svg)

*Рівняння DESTDIR + PREFIX: фізичне копіювання файлів використовує комбінований шлях, тоді як бінарні артефакти отримують лише цільовий PREFIX.*

## Рівняння DESTDIR + PREFIX: шлях копіювання проти шляху виконання

Математика встановлення артефактів в операційну систему виражається єдиним співвідношенням формування фізичного шляху файлу під час інсталяції:

```text
Шлях запису на диск = DESTDIR + PREFIX + Каталог компонента
```

Якщо змінна `DESTDIR` порожня (як це буває під час звичайної локальної збірки користувачем), співвідношення спрощується до стандартного шляху:

```text
Шлях запису на диск = PREFIX + Каталог компонента
```

### Порівняльна таблиця трансформації шляхів

| Компонент системи | Значення під час компіляції (`PREFIX=/usr`) | Шлях копіювання під час встановлення (`DESTDIR=/tmp/stage`) | Шлях пошуку під час виконання програми на цільовій машині |
| :--- | :--- | :--- | :--- |
| **Виконуваний файл** | `/usr/bin/calc` | `/tmp/stage/usr/bin/calc` | `/usr/bin/calc` |
| **Динамічна бібліотека** | `/usr/lib/libcalc.so` | `/tmp/stage/usr/lib/libcalc.so` | `/usr/lib/libcalc.so` |
| **Файл ресурсів** | `/usr/share/calc/data.json` | `/tmp/stage/usr/share/calc/data.json` | `/usr/share/calc/data.json` |
| **Системна конфігурація** | `/etc/calc.conf` | `/tmp/stage/etc/calc.conf` | `/etc/calc.conf` |
| **Внутрішній RPATH** | `/usr/lib` | — (у бінарник записується `/usr/lib`) | `/usr/lib` |

### Золоте правило DESTDIR

**Змінна DESTDIR ніколи, за жодних обставин, не повинна потрапляти всередину двійкових файлів, скомпільованих макросів, ELF-заголовків або файлів конфігурації.**

`DESTDIR` — це виключно параметр файлової операції копіювання на етапі `make install` або `cmake --install`. 

Якщо автор системи збірки припуститься грубої помилки й передасть `DESTDIR` у прапорці компілятора:
```cmake
# АНТИПАТЕРН: Помилкове зашивання DESTDIR у код бінарника!
target_compile_definitions(myapp PRIVATE
    CONFIG_PATH="${DESTDIR}${CMAKE_INSTALL_FULL_SYSCONFDIR}/myapp.conf"
)
```
станеться катастрофа: під час збірки пакета на сервері компілятор зашиє в бінарник шлях `"/tmp/stage/etc/myapp.conf"`. Коли користувач встановить готовий `.deb`-пакет на свій сервер, програма спробує звернутися до `/tmp/stage/etc/myapp.conf`, отримає системну помилку `ENOENT (No such file or directory)` і завершить роботу аварійно, оскільки каталогу `/tmp/stage` на цільовому комп'ютері немає.

Повний покроковий практикум складання пакета, перевірки бінарників утилітами `readelf` та `strings` і формування ізольованого архіву викладено окремо: [практикум ізольованого пакування з DESTDIR](root:sys-bsystem/install-prefix-and-destdir/proj-destdir-staging.md).

## Реалізація інсталяції в CMake

Система збірки CMake має вбудовану повноцінну підтримку механізму `DESTDIR`, стандартних шляхів GNU та гнучкого налаштування префіксів.

### 1. Модуль GNUInstallDirs

Для того щоб проєкт автоматично відповідав стандартам системного пакування всіх дистрибутивів Linux, у кореневому `CMakeLists.txt` обов'язково підключають модуль `GNUInstallDirs`:

```cmake
include(GNUInstallDirs)
```

Цей модуль визначає набір змінних, які враховують особливості конкретної операційної системи. Наприклад, на 64-бітних дистрибутивах Fedora/RHEL змінна `CMAKE_INSTALL_LIBDIR` автоматично дорівнюватиме `lib64`, на Debian/Ubuntu — `lib/x86_64-linux-gnu`, а на macOS чи Windows — `lib`.

Детальний перелік усіх стандартних змінних модуля, їхні типові значення та зіставлення зі стандартами GNU Autotools і Meson наведено в довіднику: [довідник змінних розміщення GNU та CMake](root:sys-bsystem/install-prefix-and-destdir/api-gnu-install-dirs.md).

### 2. Встановлення цілей та файлів через відносні шляхи

Під час оголошення правил `install()` слід завжди використовувати **відносні** змінні `GNUInstallDirs`:

```cmake
# Встановлення двійкових цілей
install(TARGETS myapp mylib
    RUNTIME DESTINATION ${CMAKE_INSTALL_BINDIR}
    LIBRARY DESTINATION ${CMAKE_INSTALL_LIBDIR}
    ARCHIVE DESTINATION ${CMAKE_INSTALL_LIBDIR}
    INCLUDES DESTINATION ${CMAKE_INSTALL_INCLUDEDIR}
)

# Встановлення публічних заголовків
install(DIRECTORY include/
    DESTINATION ${CMAKE_INSTALL_INCLUDEDIR}
)

# Встановлення статичних ресурсів
install(DIRECTORY assets/
    DESTINATION ${CMAKE_INSTALL_DATADIR}/myapp
)
```

Чому важливо вказувати саме відносні шляхи (`${CMAKE_INSTALL_BINDIR}`, тобто `bin`), а не абсолютні (`/usr/local/bin`)?
Коли в `DESTINATION` передано відносний шлях, CMake автоматично приєднує його до префікса `CMAKE_INSTALL_PREFIX`. Це дозволяє користувачеві під час конфігурації або інсталяції вільно змінювати префікс без модифікації коду `CMakeLists.txt`. Якщо ж у `DESTINATION` передано абсолютний шлях, проєкт втрачає гнучкість і прив'язується до єдиного фіксованого місця у файловій системі.

### 3. Командний рядок: керування встановленням у CMake 3.15+

Сучасний CMake дозволяє виконувати фазу інсталяції безпосередньо через уніфікований інтерфейс командного рядка:

```bash
# 1. Звичайна інсталяція в сконфігурований CMAKE_INSTALL_PREFIX (за замовчуванням /usr/local)
cmake --install build

# 2. Інсталяція з тимчасовою зміною префікса без перекомпіляції
cmake --install build --prefix /opt/myapp

# 3. Інсталяція з очищенням налагоджувальних символів (strip)
cmake --install build --prefix /usr --strip

# 4. Інсталяція в ізольований каталог пакувальника через змінну DESTDIR
DESTDIR=/tmp/staging-pkg cmake --install build
```

CMake перевіряє наявність змінної середовища `DESTDIR` під час виконання згенерованого сценарію `cmake_install.cmake`. Якщо змінна встановлена, CMake додає її значення перед кожним шляхом запису файлу.

## Проблема RPATH при інсталяції та релокабельні пакети

Коли виконуваний файл залежить від спільної бібліотеки, яка встановлюється разом із ним у нестандартний каталог (наприклад в `/opt/mycompany/lib` або `~/.local/lib`), стандартний системний завантажувач `ld.so` не зможе знайти цю бібліотеку без спеціальних вказівок.

### Розділення Build RPATH та Install RPATH у CMake

Під час розробки виникає технічна дилема:
- **У дереві збірки (Build Tree):** виконуваний файл повинен запускатися для проходження тестів (наприклад `ctest`). Для цього він має шукати щойно скомпільовану бібліотеку у внутрішній папці збірки `build/lib/`.
- **У дереві інсталяції (Install Tree):** після виконання команди встановлення бінарник повинен шукати бібліотеку в кінцевому каталозі розміщення (наприклад `/usr/local/lib` або поруч із собою).

За замовчуванням CMake вирішує цю проблему автоматично:
1. Під час збірки проєкту CMake лінкує виконуваний файл із тимчасовим RPATH, що вказує на внутрішні каталоги папки `build/`.
2. Під час виконання команди `cmake --install` CMake виконує швидке бінарне редагування заголовків ELF (або Mach-O на macOS) і замінює внутрішній RPATH на фінальний `CMAKE_INSTALL_RPATH`, або повністю видаляє його, якщо бібліотека потрапляє в стандартний системний каталог `/usr/lib`.

```cmake
# Налаштування Install RPATH у CMake
set(CMAKE_INSTALL_RPATH_USE_LINK_PATH TRUE)
set(CMAKE_INSTALL_RPATH "${CMAKE_INSTALL_FULL_LIBDIR}")
```

### Справжня релокабельність: магія $ORIGIN у Linux

Якщо програмний продукт поширюється у вигляді автономного архіву (`.tar.gz` або AppImage), користувач може розпакувати його в будь-яку папку: `/home/user/apps/myapp`, `/opt/myapp` або навіть запустити з підключеного USB-накопичувача.

Жорстко зашитий абсолютний RPATH (наприклад `/opt/myapp/lib`) у такому разі зламає запуск: якщо перемістити теку з програмою, динамічний лінкер продовжуватиме шукати бібліотеки за старою адресою і завершить процес помилкою `cannot open shared object file`.

![Релокабельність бібліотек через відносний $ORIGIN у RPATH](/root/sys/sys-bsystem/install-prefix-and-destdir/img/fig-rpath-origin-relocation.svg)

*Релокабельність через $ORIGIN: динамічний завантажувач обчислює шлях до бібліотеки відносно положення виконуваного файлу.*

Для створення повністю переміщуваних (англ. *relocatable*) двійкових файлів стандарт ELF надає спеціальну динамічну змінну **`$ORIGIN`**.

Під час завантаження бінарника динамічний лінкер Linux (`ld.so`) розгортає ключове слово `$ORIGIN` у реальний абсолютний шлях до каталогу, в якому лежить сам виконуваний файл.

Якщо бінарник лежить у `<prefix>/bin`, а бібліотека — у `<prefix>/lib`, відносний шлях між ними завжди дорівнює `$ORIGIN/../lib`.

У CMake це налаштовується таким чином:

```cmake
# Встановлюємо відносний RPATH для релокабельних пакетів
# Екрануємо символ $, щоб CMake не сприймав ORIGIN як власну змінну
set(CMAKE_INSTALL_RPATH "$ORIGIN/../${CMAKE_INSTALL_LIBDIR}")

# Зберігаємо відносний RPATH навіть під час перекомпіляції
set(CMAKE_BUILD_WITH_INSTALL_RPATH FALSE)
set(CMAKE_INSTALL_RPATH_USE_LINK_PATH FALSE)
```

Аналогами `$ORIGIN` на інших платформах є:
- **macOS (Mach-O):** `@executable_path` (шлях до виконуваного файлу процесу) або `@loader_path` (шлях до конкретного модуля/бібліотеки, що ініціювала завантаження).
- **Windows (PE/COFF):** Операційна система за замовчуванням завжди шукає динамічні бібліотеки `.dll` у тому самому каталозі, де розташовано виконуваний файл `.exe`, тому потреба в RPATH на Windows відсутня.

### Безпека та обмеження SUID-бінарників при роботі з $ORIGIN

Використання відносних шляхів `$ORIGIN` має суворе обмеження безпеки в ядрі Linux та бібліотеці `glibc`. Якщо виконуваний файл має встановлені біти привілеїв SUID або SGID (наприклад `chmod u+s /usr/bin/sudo` чи утиліти монтування дисків), динамічний лінкер `ld.so` переходить у безпечний захищений режим (*secure execution mode*).

У захищеному режимі `ld.so`:
- Повністю ігнорує змінні середовища `LD_LIBRARY_PATH` та `LD_PRELOAD`, щоб запобігти підміні бібліотек непривілейованим користувачем.
- Ігнорує секцію `$ORIGIN` у заголовках `DT_RPATH` / `DT_RUNPATH`, якщо каталог не належить довіреним системним шляхам. Якби завантажувач обробляв `$ORIGIN` для SUID-файлів без обмежень, зловмисник міг би створити жорстке посилання на SUID-бінарник у каталозі `/tmp`, підкласти поруч шкідливу бібліотеку `libcore.so` і отримати повні привілеї суперкористувача `root`.

Тому системні утиліти з правами SUID завжди компілюються або без RPATH взагалі (покладаючись лише на глобальний системний кеш `/etc/ld.so.cache`), або виключно з абсолютними шляхами до системних каталогів дистрибутива.

### Інструменти діагностики та модифікації RPATH

Перевірити та відредагувати зашитий RPATH у вже скомпільованому ELF-файлі можна за допомогою системних утиліт:

```bash
# 1. Перегляд динамічної секції ELF через readelf
readelf -d /path/to/myapp | grep -E '(RPATH|RUNPATH)'

# 2. Перегляд за допомогою утиліти objdump
objdump -p /path/to/myapp | grep -E '(RPATH|RUNPATH)'

# 3. Швидка заміна RPATH без перекомпільовування за допомогою patchelf
patchelf --set-rpath '$ORIGIN/../lib' /path/to/myapp

# 4. Повне очищення RPATH перед публікацією в системний репозиторій
patchelf --remove-rpath /path/to/myapp
```

## Динамічний пошук ресурсів без жорстких шляхів часу компіляції

Повна релокабельність вимагає не лише відносного пошуку спільних бібліотек через `$ORIGIN`, а й відмови від жорсткого зашивання абсолютного шляху до статичних даних `APP_DATADIR` у код програми.

Сучасні автономні програми (наприклад текстові редактори, графічні пакети, ігри) визначають власне положення у файловій системі динамічно під час старту процесу.

### Кросплатформне визначення шляху до власного бінарника

Для визначення каталогу виконання програми використовуються системні виклики операційної системи:
- **Linux:** зчитування символьного посилання `/proc/self/exe` через `readlink()`.
- **FreeBSD / OpenBSD:** системний виклик `sysctl` із параметром `KERN_PROC_PATHNAME`.
- **macOS:** виклик функції `_NSGetExecutablePath()`.
- **Windows:** системний виклик Win32 API `GetModuleFileNameW()`.

Після отримання шляху до двійкового файлу програма піднімається на один рівень угору (`../share/myapp`) для доступу до ресурсів:

:::tabs
@tab C
```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <libgen.h>

int get_app_datadir(char* buffer, size_t max_len) {
    char exe_path[1024];
    ssize_t len = readlink("/proc/self/exe", exe_path, sizeof(exe_path) - 1);
    if (len == -1) {
        /* Fallback до скомпільованого префікса за замовчуванням */
        snprintf(buffer, max_len, "/usr/local/share/myapp");
        return 0;
    }
    exe_path[len] = '\0';

    /* Отримуємо каталог бінарника (наприклад /opt/myapp/bin) */
    char* dir = dirname(exe_path);
    /* Формуємо відносний шлях до ресурсів /opt/myapp/share/myapp */
    snprintf(buffer, max_len, "%s/../share/myapp", dir);
    return 1;
}
```
@tab C++
```cpp
#include <iostream>
#include <filesystem>
#include <string>
#include <unistd.h>

namespace fs = std::filesystem;

fs::path get_app_datadir() {
    char exe_path[1024];
    ssize_t len = readlink("/proc/self/exe", exe_path, sizeof(exe_path) - 1);
    if (len == -1) {
        // Fallback до зашитого префікса за замовчуванням
        return fs::path("/usr/local/share/myapp");
    }
    exe_path[len] = '\0';

    // Отримуємо каталог виконуваного файлу і будуємо шлях до share/
    fs::path bin_dir = fs::path(exe_path).parent_path();
    return bin_dir.parent_path() / "share" / "myapp";
}
```
:::

Такий комбінований підхід забезпечує найвищий рівень гнучкості: якщо програма встановлена стандартно через системний пакетний менеджер, вона знаходить ресурси за скомпільованим FHS-шляхом; якщо ж користувач запустив розпакований архів у довільному каталозі, динамічне обчислення шляху запобігає падінню.

## Крос-компіляція: координатна сітка PREFIX, SYSROOT та STAGING

Під час збірки під іншу архітектуру (наприклад компіляція прошивки для ARM-мікрокомп'ютера на сервері x86_64) виникає тривимірна координатна сітка шляхів, плутанина в якій ламає розгортання:

```
                      ┌──────────────────────────────────────────────┐
                      │    Три простори під час крос-компіляції      │
                      └──────────────────────┬───────────────────────┘
                                             │
      ┌──────────────────────────────────────┼──────────────────────────────────────┐
      │                                      │                                      │
      ▼                                      ▼                                      ▼
┌───────────────────────────┐  ┌───────────────────────────┐  ┌───────────────────────────┐
│     CMAKE_SYSROOT         │  │   CMAKE_INSTALL_PREFIX    │  │          DESTDIR          │
│   (Простір компілятора)   │  │   (Простір цільової ОС)   │  │     (Простір пакування)   │
│                           │  │                           │  │                           │
│ Шлях до заголовків і      │  │ Логічний шлях програми на │  │ Тимчасова тека на хості   │
│ бібліотек цільової плати  │  │ реальному пристрої:       │  │ для збирання файлів:      │
│ на хост-машині:           │  │                           │  │                           │
│ /opt/toolchain/sysroot    │  │ /usr або /opt/firmware    │  │ /tmp/stage_arm_pkg        │
└───────────────────────────┘  └───────────────────────────┘  └───────────────────────────┘
```

1. **`CMAKE_SYSROOT`:** вказує компілятору хоста, де шукати системні заголовки та бібліотеки цільової системи.
2. **`CMAKE_INSTALL_PREFIX`:** вказує програмі, де вона житиме після прошивання образу на реальну плату (наприклад `/usr`).
3. **`DESTDIR` (або `CMAKE_STAGING_PREFIX`):** вказує системі збірки, куди фізично записати скомпільовані файли на комп'ютері розробника для наступного пакування в образ кореневої файлової системи (rootfs).

## Функціональні моделі пакування: Nix, Guix та ізольовані контейнери

Класична ієрархія FHS зі спільними каталогами `/usr/bin` та `/usr/lib` базується на припущенні, що в системі одночасно встановлена рівно одна версія кожної бібліотеки. Якщо дві програми вимагають несумісних версій `libssl.so` або `libprotobuf.so`, виникає криза системних залежностей (**Dependency Hell**).

Сучасні системи вирішують цю проблему принципово іншими підходами до префіксів:

### 1. Функціональні пакетні менеджери: Nix та GNU Guix

У системах **Nix** та **GNU Guix** концепція єдиного глобального каталогу `/usr` повністю скасована:
- Кожен пакет встановлюється у власний ізольований префікс усередині сховища:
  `/nix/store/7x8z9...-openssl-3.1.0/` та `/nix/store/4k2m1...-openssl-1.1.1u/`.
- Префікс встановлення обчислюється як криптографічний хеш від усіх вхідних залежностей, прапорців компілятора та версій вихідного коду.
- Виконувані файли містять точні, незмінні шляхи `DT_RUNPATH` до конкретних хешованих бібліотек у `/nix/store`. Завдяки цьому поняття `DESTDIR` стає непотрібним: пакувальник одразу збирає програму в її унікальний префікс у сховищі, виключаючи будь-які конфлікти імен.

### 2. Пісочниці та пакети застосунків: Flatpak, AppImage, Snap

- **Flatpak:** ізолює застосунок у просторі імен монтування (*mount namespace*). Для кожного застосунку створюється віртуальне середовище, де системне оточення змонтовано в режим *read-only* у `/usr`, а сам застосунок завжди встановлюється з префіксом `CMAKE_INSTALL_PREFIX=/app`.
- **AppImage:** запаковує програму разом з усіма залежностями у стиснений образ файлової системи SquashFS. Під час запуску спеціальний завантажувач монтує цей образ у тимчасовий каталог `/tmp/.mount_appXXXXXX` і передає шлях через змінну середовища `$APPDIR`, а внутрішній RPATH бінарників налаштовується через `$ORIGIN/../lib`.
- **Snap:** монтує пакети у версіоновані підкаталоги `/snap/<app-name>/<revision>`, ізолюючи їх за допомогою профілів безпеки AppArmor та просторів імен ядра.

## Підсумковий синтез: анатомія конвеєра розгортання

Розгортання двійкового артефакту в операційній системі — це узгоджена взаємодія чотирьох рівнів інженерної абстракції:

1. **FHS (Filesystem Hierarchy Standard):** визначає юридичні зони відповідальності каталогів (`/usr` — системний дистрибутив, `/usr/local` — локальний адміністратор, `/opt` — вендори, `~/.local` — користувач).
2. **PREFIX:** фіксує логічне розміщення програми на етапі компіляції, формує константи в коді, шляхи до статичних даних, рядки `shebang` та конфігурації `pkg-config`.
3. **DESTDIR:** надає системним пакувальникам прозору пісочницю для безпечного фізичного збирання файлового дерева без привілеїв суперкористувача та без витоку тимчасових шляхів у кінцевий двійковий код.
4. **RPATH та $ORIGIN:** забезпечують надійне завантаження динамічних бібліотек у середовищі виконання, гарантуючи автономність та переміщуваність двійкових пакетів у сучасних гетерогенних системах.
