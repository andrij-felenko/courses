Коли розробка прошивки для мікроконтролера виходить за межі простого перемикання світлодіода на голому залізі й вимагає повноцінного мережевого стека, захищеного з'єднання TLS, підтримки оновлень по повітрю (OTA) та багатозадачної операційної системи реального часу, класичний монолітний Makefile миттєво стає некерованим. У сучасній системі-на-кристалі (*SoC*, англ. *System on Chip*) на кшталт ESP32 прошивка складається не з одного вихідного файлу, а з десятків взаємопов'язаних бібліотек: ядра операційної системи FreeRTOS, мережевого стека LwIP, криптографічного рушія mbedTLS, файлових систем SPIFFS або LittleFS, драйверів апаратної периферії та закритих бінарних блобів калібрування радіотракту Wi-Fi та Bluetooth. Якщо зміна розміру мережевого буфера або перемикання тактової частоти шини вимагає ручного редагування десятка заголовних файлів у різних підкаталогах, проєкт неминуче стикається з розсинхронізацією налаштувань, прихованими циклічними залежностями та зламаними збірками в автоматизованих пайплайнах CI/CD.

Для подолання цієї складності компанія Espressif побудувала фреймворк **ESP-IDF** (*Espressif IoT Development Framework*) навколо компонентної моделі на базі сучасного таргет-орієнтованого CMake та декларативної системи конфігурації Kconfig. Замість написання низькорівневих правил компіляції розробник оперує ізольованими модулями — **компонентами** (*components*), кожен з яких сам декларує свої вихідні файли, публічні інтерфейси, приватні залежності та власні пункти меню налаштувань.

*Конвеєр системи збірки ESP-IDF: утиліта idf.py оркеструє парсинг Kconfig через confgen.py, раннє розгортання CMake, створення таргетів бібліотек та формування бінарних образів прошивки.*

## Анатомія дерева проєкту та точка входу CMake

Типовий проєкт під керуванням ESP-IDF має чітку стандартизовану структуру каталогів. Ця структура є контрактом між розробником і скриптами автоматичного пошуку компонентів фреймворку:

```text
my_iot_project/
├── CMakeLists.txt              # Кореневий файл збірки проєкту
├── sdkconfig.defaults          # Версіоновані базові налаштування проєкту
├── partitions.csv              # (Опційно) Користувацька таблиця розділів Flash
├── main/                       # Головний компонент застосунку за замовчуванням
│   ├── CMakeLists.txt          # Реєстрація компонента main
│   ├── Kconfig.projbuild       # Глобальні налаштування проєкту для menuconfig
│   └── app_main.c              # Точка входу в програму (або main.cpp)
├── components/                 # Каталог власних та сторонніх модулів проєкту
│   └── sensor_hub/
│       ├── CMakeLists.txt
│       ├── Kconfig
│       ├── include/
│       │   └── sensor_hub.h
│       └── sensor_hub.c
└── build/                      # Каталог артефактів збірки (створюється автоматично)
```

Кореневий файл `CMakeLists.txt` у корені репозиторію має строго визначену послідовність викликів, яку не можна порушувати:

```cmake
# Мінімально необхідна версія CMake для генерації правил збірки
cmake_minimum_required(VERSION 3.16)

# Підключення інфраструктури ESP-IDF (перехоплює тулчейн і конфігурацію)
include($ENV{IDF_PATH}/tools/cmake/project.cmake)

# Декларація проєкту (лише ПІСЛЯ підключення project.cmake)
project(my_iot_project)
```

У звичайних проєктах на CMake виклик `project()` стоїть першим рядком одразу після `cmake_minimum_required()`. Проте в ESP-IDF включення `$ENV{IDF_PATH}/tools/cmake/project.cmake` **зобов'язане передувати** `project()`. Причина полягає в тому, що `project.cmake` налаштовує змінну `CMAKE_TOOLCHAIN_FILE`, яка вказує CMake на внутрішній файл тулчейну (`${IDF_PATH}/tools/cmake/toolchain-${IDF_TARGET}.cmake`). 

Коли CMake обробляє команду `project()`, він опитує встановлений тулчейн, визначає цільовий тріплет (наприклад, `xtensa-esp32-elf` для базового ESP32 чи `riscv32-esp-elf` для сучасних чипів ESP32-C3/C6), фіксує шляхи до крос-компіляторів GCC/G++, системні прапорці ABI та забороняє перевірку працездатності компілятора запуском бінарників на хост-машині. Якби `project()` викликався раніше, CMake спробував би використати хостовий компілятор операційної системи (MSVC або системний GCC хоста) і згенерував би непридатне для мікроконтролера середовище збірки.

> 🔧 **Навіщо це.** Рядок `include($ENV{IDF_PATH}/tools/cmake/project.cmake)` перед `project()` — це міст, який перетворює універсальний хостовий CMake на спеціалізований генератор прошивок під мікроконтролери з повною підтримкою архітектур Xtensa та RISC-V.

## Модель компонентів та макрос idf_component_register

У термінології ESP-IDF кожна структурна одиниця коду є **компонентом** (*component*). Сам фреймворк ESP-IDF — це просто колекція системних компонентів, розташованих у каталозі `$IDF_PATH/components/` (серед них `freertos`, `driver`, `esp_wifi`, `lwip`, `nvs_flash`, `vfs`, `mbedtls`, `esp_hw_support`). Власний код проєкту в каталозі `main/` або в підкаталогах `components/` обробляється точно за тими ж правилами, що й вбудовані системні драйвери.

Компонент заявляє про себе системі через власний локальний файл `CMakeLists.txt`, викликаючи макрос `idf_component_register`:

```cmake
# components/sensor_hub/CMakeLists.txt
idf_component_register(
    SRCS 
        "sensor_hub.c"
        "sensor_filter.c"
    INCLUDE_DIRS 
        "include"
    PRIV_INCLUDE_DIRS 
        "private_headers"
    REQUIRES 
        esp_timer
    PRIV_REQUIRES 
        driver
        nvs_flash
)
```

Система збірки ESP-IDF працює у дві чітко розмежовані фази розгортання CMake:

1. **Фаза раннього розширення (Early expansion phase):**  
   Система обходить каталог фреймворку `$IDF_PATH/components`, локальний каталог проєкту `components/`, каталог `main/` та будь-які додаткові шляхи, передані через змінну `EXTRA_COMPONENT_DIRS`. На цьому етапі вихідні файли ще не компілюються: система лише зчитує `CMakeLists.txt` компонентів, збирає списки залежностей і будує орієнтований граф компонентів, відсікаючи невикористані модулі для прискорення конфігурації. Також тут працює механізм перевизначення: якщо у локальному каталозі `components/` створити папку з ім'ям системного компонента (наприклад, `freertos`), ESP-IDF підставить вашу реалізацію замість стандартної.

2. **Фаза реєстрації та побудови таргетів (Target registration phase):**  
   Для кожного включеного в граф компонента макрос `idf_component_register` автоматично створює статичну бібліотеку CMake з ім'ям `__idf_<component_name>`. Параметри макроса безпосередньо транслюються в стандартні властивості таргету CMake:
   - `INCLUDE_DIRS` перетворюється на `target_include_directories(... INTERFACE)`. Каталоги, зазначені тут, стають видимими як для самого компонента, так і для будь-якого іншого модуля, що підключає його.
   - `PRIV_INCLUDE_DIRS` перетворюється на `target_include_directories(... PRIVATE)`. Ці заголовки доступні лише вихідним файлам самого компонента.
   - `REQUIRES` перетворюється на `target_link_libraries(... PUBLIC)`. Це публічна інтерфейсна залежність: якщо модуль `A` вимагає `B`, то публічні заголовки `B` стають частиною публічного інтерфейсу `A`.
   - `PRIV_REQUIRES` перетворюється на `target_link_libraries(... PRIVATE)`. Це залежність реалізації: заголовки потрібні лише для внутрішньої збірки `sensor_hub.c`, але споживачі `sensor_hub` їх не побачать.

![Поширення залежностей між компонентами: публічні та приватні інтерфейси](/root/sys/sys-bsystem/esp-idf-struktura-proiektu-komponenty-menuconfig/img/component-dependency-flow.svg)

*Розмежування залежностей: компонент main підключає sensor_hub через REQUIRES і бачить лише публічний інтерфейс sensor.h; низькорівневий драйвер i2c_driver ізольований у PRIV_REQUIRES.*

Повний перелік параметрів реєстрації, включаючи вбудовування бінарних ресурсів `EMBED_FILES` та керування скриптами лінкера, наведено у вставці 📋 [Довідник API: макрос idf_component_register та функції збірки ESP-IDF](root:sys-bsystem/esp-idf-struktura-proiektu-komponenty-menuconfig/api-component-register.md).

### Спеціальний статус компонента `main`

Компонент `main/` займає особливе місце в ієрархії. За замовчуванням система збірки вважає, що `main` є кінцевим споживачем усіх інших компонентів у дереві проєкту. Тому, якщо в `main/CMakeLists.txt` не вказано секцію `REQUIRES`, ESP-IDF автоматично додає до його списку залежностей **усі зареєстровані компоненти проєкту**.

```cmake
# main/CMakeLists.txt (мінімальний варіант)
idf_component_register(
    SRCS "app_main.c"
    INCLUDE_DIRS "."
)
```

Хоча для простих застосунків це зручно, у великих системах рекомендується явно вказувати `PRIV_REQUIRES` навіть для `main`. Це суттєво звужує простір пошуку заголовків компілятором і запобігає випадковому використанню внутрішніх функцій чужих модулів.

## Система конфігурації Kconfig та кодогенерація sdkconfig.h

Вбудовані системи вимагають тонкої адаптації коду під конкретне апаратне оточення: від вибору номерів виводів GPIO для інтерфейсу SPI до виділення розміру черг планувальника FreeRTOS. Якщо задавати ці параметри через прапорці компілятора `-D` у CMake, список аргументів розростається до сотень незрозумілих рядків.

ESP-IDF запозичив механізм конфігурації **Kconfig** із ядра Linux (*Linux Kernel Configuration*). Це декларативна мова опису деревоподібних меню параметрів із підтримкою типів (булеві прапорці, цілі числа, рядки, шістнадцяткові значення), діапазонів значень (`range`), взаємовиключних списків (`choice`) та правил залежностей (`depends on`, `select`).

### Kconfig проти Kconfig.projbuild

У структурі проєкту підтримуються два типи файлів конфігурації:

1. **`Kconfig` (локальний для компонента):**  
   Файл розташовується безпосередньо в каталозі компонента (`components/my_sensor/Kconfig`). Усі оголошені в ньому опції автоматично потрапляють у вкладене меню `menuconfig` за шляхом:  
   `Component config → [Назва компонента]`.

2. **`Kconfig.projbuild` (глобальний для проєкту):**  
   Файл розташовується в каталозі компонента або в `main/`. Опції з цього файлу виносяться безпосередньо у **головне кореневе меню** `menuconfig`. Це використовується для наскрізних параметрів виробу, таких як SSID домашньої мережі Wi-Fi, URL-адреса сервера телеметрії або режим роботи приладу.

Синтаксис файлу конфігурації є строго типізованим:

```kconfig
menu "Конфігурація модуля зв'язку"

    config APP_WIFI_SSID
        string "Назва точки доступу Wi-Fi (SSID)"
        default "ESP32_Device"
        help
            SSID бездротової мережі, до якої підключається пристрій під час старту.

    config APP_TELEMETRY_PORT
        int "TCP порт сервера телеметрії"
        range 1024 65535
        default 8883
        help
            Номер мережевого порту для надсилання пакетів даних.

    config APP_ENABLE_POWER_SAVE
        bool "Увімкнути режим глибокого сну пристрою"
        default y
        help
            Дозволяє процесору переходити в режим Low Power між вимірами.

endmenu
```

*Потік даних Kconfig: правила та дефолти перетворюються утилітою confgen.py на макроси sdkconfig.h для компілятора C/C++ та змінні sdkconfig.cmake для логіки збірки.*

### Конвеєр генерації: від текстового файлу до бінарника

Процес обробки конфігурації складається з чотирьох послідовних кроків:

1. **Редагування:** Розробник викликає `idf.py menuconfig`, відкриваючи псевдографічний термінальний інтерфейс на базі бібліотеки `kconfiglib`.
2. **Збереження стану:** Після збереження параметрів утиліта створює у корені проєкту простий текстовий файл `sdkconfig`. Цей файл містить плоский список пар ключ-значення:
   ```text
   CONFIG_APP_WIFI_SSID="ESP32_Device"
   CONFIG_APP_TELEMETRY_PORT=8883
   CONFIG_APP_ENABLE_POWER_SAVE=y
   ```
3. **Парсинг та валідація:** Спеціальний Python-скрипт фреймворку `confgen.py` зчитує всі знайдені файли `Kconfig`, звіряє їх із `sdkconfig`, перевіряє виконання умов `depends on` та обчислює значення за замовчуванням для неналаштованих полів.
4. **Кодогенерація артефактів:** `confgen.py` генерує два системні файли у каталозі збірки:
   - `build/config/sdkconfig.h`: Заголовний файл C/C++, у якому кожна увімкнена опція перетворюється на макрос препроцесора з префіксом `CONFIG_`:
     ```text
     #define CONFIG_APP_WIFI_SSID "ESP32_Device"
     #define CONFIG_APP_TELEMETRY_PORT 8883
     #define CONFIG_APP_ENABLE_POWER_SAVE 1
     ```
   - `build/config/sdkconfig.cmake`: Скрипт для CMake, у якому кожна опція стає змінною:
     ```cmake
     set(CONFIG_APP_WIFI_SSID "ESP32_Device")
     set(CONFIG_APP_TELEMETRY_PORT 8883)
     set(CONFIG_APP_ENABLE_POWER_SAVE 1)
     ```

Завдяки цьому подвійному генератору розробник може використовувати ті самі налаштування як у вихідному коді програми на C/C++ (через перевірки `#if CONFIG_APP_ENABLE_POWER_SAVE`), так і в правилах CMakeLists (наприклад, `if(CONFIG_APP_ENABLE_POWER_SAVE) list(APPEND SRCS "power_save.c") endif()`).

Практичний покроковий приклад створення драйвера датчика з власним меню Kconfig розібрано в ⚙️ [Практика: створення компонента датчика з Kconfig та підтримкою C/C++](root:sys-bsystem/esp-idf-struktura-proiektu-komponenty-menuconfig/proj-kconfig-workflow.md).

### Дисципліна керування конфігураціями: `sdkconfig.defaults`

Файл `sdkconfig` містить сотні згенерованих системних параметрів за замовчуванням і залежить від локального середовища, тому його **не додають до репозиторію Git** (його заносять у `.gitignore`). 

Для фіксації архітектурних змін проєкту у системі контролю версій використовується файл `sdkconfig.defaults`. У ньому записують **лише ті рядки, які відрізняються від стандартних заводських значень**:

```text
# sdkconfig.defaults
CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ_240=y
CONFIG_FREERTOS_HZ=1000
CONFIG_LOG_DEFAULT_LEVEL_DEBUG=y
CONFIG_APP_WIFI_SSID="Production_Gateway"
```

Коли новий розробник клонує репозиторій або система CI/CD запускає збірку на чистому сервері, команда `idf.py build` автоматично бере стандартні значення фреймворку, накладає зверху правила з `sdkconfig.defaults` і генерує коректний робочий `sdkconfig` без жодного ручного втручання. Більше того, ESP-IDF підтримує цільові конфігурації за допомогою суфіксів, наприклад, `sdkconfig.defaults.esp32s3` або `sdkconfig.defaults.ci`.

## Використання конфігурацій у коді C та C++

Усередині вихідних файлів доступ до налаштувань відкривається підключенням заголовка `#include "sdkconfig.h"`. Кожен компонент автоматично має шлях до каталогу генерації `build/config/`.

Нижче наведено ідіоматичні приклади ініціалізації системного модуля на мовах C та C++ з використанням згенерованих макросів конфігурації:

:::tabs
```c
/* main/app_main.c (C) */
#include <stdio.h>
#include <stdbool.h>
#include "esp_log.h"
```

## Розкладка Flash-пам'яті, Flash MMU та етапи завантаження

Мікроконтролери сімейства ESP32 здебільшого не мають вбудованої великої пам'яті програм Flash на самому кристалі кремнію. Замість цього поруч із кристалом монтується зовнішня мікросхема енергонезалежної пам'яті NOR Flash (підключена по високошвидкісній шині SPI, Quad-SPI або Octal-SPI обсягом від 4 до 32 МБ). Процесор виконує машинний код безпосередньо з Flash завдяки апаратному контролеру кешування та сторінкової трансляції адрес — **Flash MMU** (механізм *Execute In Place*, XIP).

### Апаратний механізм Flash MMU та кеш інструкцій

Фізично пам'ять Flash розбита на сторінки розміром 64 КБ. Апаратний блок Flash MMU містить таблицю дескрипторів, яка прозоро для процесора транслює віртуальні адреси адресного простору процесора (`0x400D0000` для інструкцій коду `.flash.text` та `0x3F400000` для констант `.flash.rodata`) у фізичні зміщення зовнішньої мікросхеми SPI Flash. 

Коли процесор запитує інструкцію за адресою Flash, контролер кешу перевіряє, чи є відповідний блок у внутрішньому швидкому SRAM-кеші. Якщо виникає промах кешу (*cache miss*), апаратний контролер шини SPI автоматично вичитує рядок кешу з зовнішньої мікросхеми Flash, зупиняючи конвеєр ядра на кілька десятків тактів.

Це створює найважливіше інженерне обмеження: **під час виконання операцій запису або стирання Flash-пам'яті контролер кешу апаратно блокується**. Якщо в цей момент спрацює переривання, чий код або константи знаходяться у Flash, виникне фатальна помилка процесора — `Cache disabled but cached memory region accessed`. Щоб цього уникнути, критичні обробники переривань та функції керування живленням позначають атрибутом `IRAM_ATTR`, змушуючи лінкер завантажувати їх безпосередньо у внутрішню оперативну пам'ять **IRAM** (*Instruction RAM*).

![Фізична розкладка SPI Flash у ESP32 та послідовність завантаження](/root/sys/sys-bsystem/esp-idf-struktura-proiektu-komponenty-menuconfig/img/flash-memory-layout.svg)

*Карта пам'яті SPI Flash: послідовний ланцюг виконання від апаратного ROM завантажувача до 2nd stage bootloader, парсинг таблиці розділів та старт застосунку.*

### Три ступені завантаження прошивки

Старт мікроконтролера після скидання живлення відбувається за чітким сценарієм:

1. **Перший ступінь — ROM Bootloader (1st stage):**  
   Незмінна програма, записана в кремній процесора під час виготовлення на фабриці. Після скидання вона зчитує стан виводів конфігурації (*strapping pins*). Якщо активовано режим завантаження з Flash, ROM-завантажувач ініціалізує базовий контролер SPI Flash на низькій безпечній частоті, зчитує завантажувач другого ступеня за фіксованою адресою **`0x1000`** (на класичному ESP32) або **`0x0000`** (на ESP32-S3 / ESP32-C3) та завантажує його у внутрішню швидку пам'ять IRAM.

2. **Другий ступінь — 2nd Stage Bootloader (`bootloader.bin`):**  
   Невеликий завантажувач, який компілюється разом із вашим проєктом із компонента `$IDF_PATH/components/bootloader`. Він виконується повністю з оперативної пам'яті IRAM. Його завдання:
   - Переналаштувати шину SPI Flash на максимальну робочу частоту (40/80/120 МГц) і увімкнути режим QIO (Quad I/O) чи OPI (Octal).
   - Зчитати бінарну таблицю розділів за фіксованою адресою **`0x8000`**.
   - Перевірити наявність оновлень у розділі даних вибору прошивки (`otadata`).
   - Перевірити цифрові підписи та контрольні суми образу (Secure Boot / SHA256).
   - Налаштувати дескриптори Flash MMU на початок розділу вибраного застосунку та передати керування на точку входу образу.

3. **Образ застосунку — Application Image (`app.bin`):**  
   Головний бінарний файл програми, розташований за зміщенням **`0x10000`** (розділ `factory` за замовчуванням) або в розділах `ota_0` / `ota_1`. Він містить заголовок `esp_image_header_t`, секції коду для Flash MMU, секції IRAM для критичних переривань та дані ініціалізації DRAM. Програма ініціалізує планувальник FreeRTOS і викликає функцію `app_main()`.

### Таблиця розділів: partitions.csv

Розподіл простору Flash-пам'яті описується у файлі формату CSV. Якщо проєкт не надає власного файлу, ESP-IDF використовує стандартну однопрошивкову схему.

Розглянемо типову конфігурацію промислового проєкту з підтримкою двох чергових банків оновлення по повітрю (OTA) та файлової системи:

```csv
# Name,   Type, SubType, Offset,   Size,     Flags
nvs,      data, nvs,     0x9000,   0x4000,
otadata,  data, ota,     0xd000,   0x2000,
phy_init, data, phy,     0xf000,   0x1000,
ota_0,    app,  ota_0,   0x10000,  0x180000,
ota_1,    app,  ota_1,   0x190000, 0x180000,
storage,  data, spiffs,  0x310000, 0xef000,
```

Поля таблиці розділів мають суворі правила:
- **`Name`**: Текстовий ідентифікатор розділу (до 16 символів), який використовується у викликах API (наприклад, `esp_partition_find_first(ESP_PARTITION_TYPE_DATA, ...)`).
- **`Type`**: Основний тип розділу — `app` (виконуваний код) або `data` (налаштування, файлові системи).
- **`SubType`**: Призначення розділу:
  - Для `app`: `factory` (базовий заводський застосунок), `ota_0` ... `ota_15` (слоти OTA оновлення), `test`.
  - Для `data`: `nvs` (енергонезалежне сховище ключ-значення для Wi-Fi паролів та калібрувань), `ota` (службовий стан OTA), `phy` (параметри радіочастотного тракту), `spiffs` / `fat` / `littlefs` (файлові сховища).
- **`Offset`**: Фізичне зміщення в байтах від початку Flash. Усі розділи **зобов'язані бути вирівняні за межею сектора 4 КБ (`0x1000`)**, а розділи типу `app` вимагають вирівнювання за межею 64 КБ (`0x10000`) для коректної прив'язки сторінок Flash MMU. Якщо зміщення залишити порожнім, компілятор таблиці (`gen_esp32part.py`) розрахує його автоматично.
- **`Size`**: Розмір розділу (також кратний 4 КБ).
- **`Flags`**: Додаткові атрибути (наприклад, `encrypted` для апаратного шифрування розділу за допомогою AES Flash Encryption).

### Механізм безпечного відкату прошивки (OTA Rollback)

Розділ `otadata` розміром 8 КБ (два сектори по 4 КБ для стійкості до раптового вимкнення живлення під час запису) зберігає лічильник послідовності та поточний стан прошивки:
- `ESP_OTA_IMG_NEW`: Новий образ успішно завантажений, призначений на наступне завантаження.
- `ESP_OTA_IMG_PENDING_VERIFY`: Завантажувач 2-го ступеня запустив новий образ вперше. Стартує апаратний сторожовий таймер (RTC WDT).
- `ESP_OTA_IMG_VALID`: Застосунок підтвердив свою працездатність викликом `esp_ota_mark_app_valid_cancel_rollback()`.
- `ESP_OTA_IMG_INVALID`: Прошивка впала у паніку під час старту. Завантажувач автоматично перемикається на попередній робочий банк.

Якщо новий образ містить критичну помилку (наприклад, не може підключитися до мережі або викликає Kernel Panic), сторожовий таймер перезавантажує чип, а завантажувач 2-го ступеня, бачачи стан `PENDING_VERIFY`, маркує цей слот як битий і прозоро повертає пристрій на попередню стабільну версію.

## Інтерфейс утиліти idf.py та автоматизація в CI/CD

Утиліта `idf.py` — це кросплатформний інтерфейс командного рядка (CLI-обгортка на мові Python), який об'єднує під єдиним інтерфейсом виклики CMake, генератора Ninja, компілятора Kconfig, утиліти прошивання `esptool.py` та монітора послідовного порту.

### Основні команди життєвого циклу розробки

| Команда | Що виконує під капотом |
|---|---|
| `idf.py set-target <chip>` | Очищує попередній кеш CMake, виставляє змінну `IDF_TARGET` (наприклад, `esp32s3`) та створює конфігурацію під нове процесорне ядро. |
| `idf.py menuconfig` | Запускає інтерактивний конфігуратор ncurses і генерує оновлений `sdkconfig`. |
| `idf.py build` | Запускає `cmake` та `ninja`, збираючи завантажувач `bootloader.bin`, таблицю розділів `partition-table.bin` та застосунок `my_project.bin`. |
| `idf.py flash` | Знаходить підключений COM/tty-порт і через `esptool.py` прошиває бінарники за відповідними зміщеннями Flash. |
| `idf.py monitor` | Відкриває термінал читання UART-порту з автоматичним декодуванням стеків викликів помилок (*Backtrace decoding* через GDB/addr2line). |
| `idf.py flash monitor` | Об'єднана дія: компіляція (за потреби), прошивання та негайний перехід у режим моніторингу виводу. |
| `idf.py size` | Аналізує згенерований ELF-файл і виводить підсумкове використання IRAM, DRAM та Flash пам'яті. |
| `idf.py size-components` | Деталізує витрати пам'яті за окремими статичними бібліотеками (`__idf_*`). |
| `idf.py fullclean` | Повністю видаляє каталог `build/` та згенеровані конфігураційні кеші. |

### Прошивання за зміщеннями проти єдиного фабричного образу

Під час виклику команди `idf.py flash` утиліта формує точний виклик `esptool.py`, передаючи список файлів та їхніх адрес:

```bash
esptool.py -p /dev/ttyUSB0 -b 460800 --chip esp32 write_flash \
    0x1000  build/bootloader/bootloader.bin \
    0x8000  build/partition_table/partition-table.bin \
    0x10000 build/my_iot_project.bin
```

Такий підхід є ідеальним для розробки, оскільки під час зміни лише прикладного коду `app_main.c` немає потреби перетирати завантажувач чи збережені в розділі NVS налаштування. 

Однак на промисловому конвеєрі під час серійного виробництва прошивати пристрій трьома окремими записами неефективно. ESP-IDF надає команду генерації єдиного суцільного бінарного образу:

```bash
idf.py merge-bin -o build/factory_firmware.bin
```

Команда створює монолітний файл `factory_firmware.bin`, у якому всі порожнечі між зміщеннями заповнені байтами `0xFF`. Такий файл записується на заводському програматорі за нульовою адресою `0x0000` за одну операцію.

## Автоматизація збірки в CI/CD без інтерактивного вводу

У системах неперервної інтеграції (GitHub Actions, GitLab CI, Jenkins) використання діалогового `menuconfig` неможливе. Збірка повинна бути повністю детермінованою, відтворюваною та автоматизованою.

Для цього використовується комбінація змінних оточення та заздалегідь підготовлених файлів `sdkconfig.defaults`.

Приклад конфігурації кроку збірки у headless-середовищі:

```bash
# 1. Завантаження системного оточення тулчейну ESP-IDF
. $IDF_PATH/export.sh

# 2. Встановлення цільового чипа без відкриття діалогів
idf.py set-target esp32s3

# 3. Збірка прошивки з перевіркою попереджень як помилок
idf.py -B build_ci \
       -DSDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.ci" \
       build
```

Ключові принципи надійної CI/CD автоматизації для ESP-IDF:
1. **Видалення локального `sdkconfig` перед стартом:** Це гарантує, що конфігурація збирається виключно з версіонованих у Git файлів `sdkconfig.defaults`.
2. **Передача додаткових профілів через `SDKCONFIG_DEFAULTS`:** Дозволяє накладати специфічні для тестового оточення опції (наприклад, увімкнення емуляції або активацію додаткових асертів) без зміни базового файлу конфігурації.
3. **Парсинг використання пам'яті:** Команда `idf.py size --json` видає структуру споживання пам'яті в машинно-читаному форматі JSON, що дозволяє в автоматичному режимі блокувати Pull Request, якщо розмір бінарника перевищив ліміт розділу `ota_0`.

## Інженерні пастки та діагностика помилок

Практична робота з системою збірки ESP-IDF пов'язана з кількома типовими помилками, причини яких криються в неочевидній взаємодії CMake, Kconfig та лінкера.

### 1. Помилка «Header file not found» при наявному компоненті

*Симптом:* У файлі `my_component.c` підключено заголовок `#include "esp_wifi.h"`, компонент `esp_wifi` гарантовано існує в ESP-IDF, але компілятор видає фатальну помилку відсутності файлу.  
*Причина:* У файлі `components/my_component/CMakeLists.txt` пропущено декларацію залежності. Компілятор ESP-IDF не додає шляхи до заголовків інших компонентів глобально.  
*Вирішення:* Додати `PRIV_REQUIRES esp_wifi` (або `REQUIRES esp_wifi`, якщо заголовок згадується у публічному `.h` файлі компонента) у виклик `idf_component_register`.

### 2. Плутанина між `#if` та `#ifdef` для булевих опцій Kconfig

*Симптом:* Функція виконується навіть тоді, коли відповідну опцію Kconfig вимкнено в `menuconfig`.  
*Причина:* Коли опція `config MY_FEATURE` вимкнена, утиліта `confgen.py` взагалі не генерує `#define CONFIG_MY_FEATURE` у файлі `sdkconfig.h` (або коментує її як `/* #undef CONFIG_MY_FEATURE */`). Якщо розробник пише `#if CONFIG_MY_FEATURE`, стандарти C і C++ замінюють невизначений макрос на `0`, і умова працює коректно. Проте якщо написати `#ifdef CONFIG_MY_FEATURE` або `#if defined(CONFIG_MY_FEATURE)`, умова перевіряє лише сам факт наявності макроса. Якщо ж опція була визначена як рядок або число `0`, `#ifdef` поверне `true`.  
*Правило:* Для перевірки булевих параметрів Kconfig завжди використовуйте прямий `#if CONFIG_NAME` або `#if !CONFIG_NAME`.

### 3. Переповнення розділу застосунку (Partition Overflow)

*Симптом:* Компіляція всіх `.c` файлів пройшла успішно, але на фінальній стадії створення бінарного образу процес завершується помилкою:  
`Error: app partition is too small for binary (size 0x184200, limit 0x180000)`.  
*Причина:* Стандартний компонувальник `ld` успішно зв'язав ELF-файл, оскільки віртуальний адресний простір Flash MMU є великим. Проте утиліта валідації образу виявила, що бінарний образ перевищує фізичний розмір розділу `ota_0`, виділений у `partitions.csv`.  
*Вирішення:* Оптимізувати розмір коду (увімкнути рівень оптимізації `-Os` у `menuconfig`, вимкнути непотрібні налагоджувальні логи), або відредагувати `partitions.csv`, збільшивши розмір розділів застосунків за рахунок зменшення файлової системи чи використання мікросхеми Flash більшого обсягу.

### 4. Втрата цільового чипа при зміні гілок у Git

*Симптом:* Після перемикання між гілками проєкту компілятор намагається зібрати код під старий чип або видає помилки про несумісні прапорці інструкцій.  
*Причина:* Файл `build/CMakeCache.txt` зберігає кешовану інформацію про попередньо вибраний `IDF_TARGET`.  
*Вирішення:* Виконати `idf.py fullclean` або видалити каталог `build/`, після чого заново запустити `idf.py set-target <chip>`.

## Підсумок

Архітектура системи збірки ESP-IDF поєднує строгість таргет-орієнтованого CMake з гнучкістю декларативної конфігурації Kconfig. Поділ коду на ізольовані компоненти через `idf_component_register` чітко розмежовує публічні та приватні інтерфейси, запобігаючи неконтрольованому заплутуванню залежностей. Конвеєр `confgen.py` автоматично транслює обрані в `menuconfig` або зафіксовані в `sdkconfig.defaults` параметри в код C/C++ та інструкції збірки CMake. Нарешті, зв'язка таблиці розділів `partitions.csv` та триступеневого завантажувача забезпечує надійне виконання та безпечне оновлення прошивки у фізичній пам'яті SPI Flash.
