Ви відкриваєте у текстовому редакторі сирцевий файл `sensor_node.cpp` на п'ятсот рядків коду. Редактор миттєво підкреслює перший десяток директив `#include` червоною хвилястою лінією з повідомленням про відсутність заголовків, оголошує половину типів невідомими й позначає виклики методів стандартної бібліотеки як синтаксичні помилки. Ви перемикаєтесь у термінал, вводите команду збірки — і компілятор без жодного зауваження за дві секунди збирає робочий бінарний файл. 

Код той самий, але для редактора він не має змісту, тоді як для компілятора — бездоганний. Причина цього розриву закладена в самій природі мов C та C++: вихідний текст файлу не є самодостатньою програмою. Він є лише сировиною, семантика якої повністю визначається контекстом виклику компілятора — каталогами пошуку заголовків, макросами препроцесора, версією стандарту мови, цільовою архітектурою та системними бібліотеками.

Щоб будь-який зовнішній інструмент — інтегроване середовище розробки (IDE), мовний сервер автодоповнення чи статичний аналізатор — зміг розібрати код точно так само, як це робить компілятор, йому потрібен стандартизований міст між системою збірки та світом інструментів аналізу. Таким універсальним мостом стала база даних компіляції — файл `compile_commands.json`.

## Одиниця трансляції не існує у вакуумі

У мовах на кшталт Java чи Go кожен пакет або модуль несе значну частину інформації про власні залежності безпосередньо в коді чи суворо регламентованій файловій структурі. У C та C++ ситуація принципово інша: сирцевий файл `.cpp` разом з усіма заголовками, які він рекурсивно підключає через директиви `#include`, утворює одиницю трансляції (англ. *translation unit*).

Сама по собі одиниця трансляції позбавлена однозначного значення без повного набору прапорців компілятора. Розглянемо простий фрагмент:

```cpp
#include <hal/uart.h>

void send_telemetry(const TelemetryPacket& packet) {
#if defined(ENABLE_CALIBRATION) && ENABLE_CALIBRATION == 1
    packet.apply_offsets();
#endif
    uart_write(TELEMETRY_PORT, packet.raw_data(), packet.size());
}
```

Щоб семантично розібрати ці вісім рядків, парсер мусить знати відповіді на п'ять незалежних питань:
1. **Де лежить `hal/uart.h`?** У системному каталозі `/usr/include`, у каталозі підмодуля `third_party/drivers/include` чи у згенерованій теці збірки `build/generated/include`? Без прапорця `-I` або `-isystem` парсер зупиниться на першому рядку.
2. **Яку гілку препроцесора обрати?** Чи передано прапорець `-DENABLE_CALIBRATION=1`, чи макрос не оголошено зовсім? Від цього залежить, чи існує виклик `packet.apply_offsets()`, і чи потрібно перевіряти наявність такого методу в класі `TelemetryPacket`.
3. **Який діалект мови використовується?** Якщо `TelemetryPacket` використовує `std::span`, компілятор з вимогою за замовчуванням `-std=c++11` вважатиме це помилкою, тоді як із прапорцем `-std=c++20` код скомпілюється коректно.
4. **Яка цільова архітектура?** Розмір покажчиків, вирівнювання структур у пам'яті та наявність апаратних інструкцій залежать від прапорців `--target=arm-none-eabi` чи `-march=armv7e-m`.
5. **Яке значення має `TELEMETRY_PORT`?** Це числовий макрос, переданий через командний рядок `-DTELEMETRY_PORT=2`, чи константа із заголовка?

Історично кожне інтегроване середовище розробки намагалося розв'язати цю проблему створенням власного закритого формату опису проєктів — `.vcxproj` у Visual Studio, `.cbp` у Code::Blocks, `.cproject` в Eclipse CDT. Це призводило до хронічного подвійного ведення конфігурації: інженер описував реальні правила збірки в `Makefile` чи `CMakeLists.txt`, а для роботи редактора змушений був паралельно заповнювати діалогові вікна IDE шляхами до заголовків та списками макросів.

![Традиційний розсинхронізований підхід проти єдиного джерела правди через compile_commands.json](/root/sys/sys-bsystem/compilation-database/img/compile-database-role.svg)
*При подвійному описі інструменти аналізу неминуче розходяться з реальним компілятором; база даних компіляції усуває розсинхронізацію, перетворюючи систему збірки на єдине джерело правди.*

Щойно розробник додавав новий каталог пошуку або змінював прапорець у системі збірки, редактор починав продукувати хибні помилки (англ. *false positives*), втрачав навігацію до визначень функцій і не міг коректно доповнювати імена типів. Система збірки — єдиний компонент, який володіє вичерпним і точним знанням про те, як саме має транслюватися кожен файл.

Виходом із цього глухого кута стало відокремлення механізму збірки від інструментів аналізу через стандартизований формат експорту — базу даних компіляції JSON (англ. *JSON Compilation Database*), спочатку специфіковану проєктом Clang/LLVM.

## Анатомія та схема compile_commands.json

База даних компіляції — це звичайний текстовий файл у форматі JSON, який містить кореневий масив об'єктів. Кожен об'єкт масиву описує команду компіляції рівно однієї одиниці трансляції.

Специфікація стандарту Clang визначає чотири ключові поля для кожного запису:

```json
[
  {
    "directory": "/home/developer/projects/embedded-node/build",
    "file": "../src/sensor_node.cpp",
    "arguments": [
      "/usr/bin/clang++",
      "-c",
      "-std=c++20",
      "-DENABLE_CALIBRATION=1",
      "-DTELEMETRY_PORT=2",
      "-I../include",
      "-I/opt/sdk/include",
      "-Wall",
      "-Wextra",
      "-o",
      "CMakeFiles/node.dir/src/sensor_node.cpp.o",
      "../src/sensor_node.cpp"
    ],
    "output": "CMakeFiles/node.dir/src/sensor_node.cpp.o"
  }
]
```

![Анатомія структури запису CompileCommand у JSON-масиві](/root/sys/sys-bsystem/compilation-database/img/entry-anatomy.svg)
*Кожен запис бази фіксує контекст виконання: абсолютний робочий каталог, файл джерела, аргументи виклику компілятора та цільовий вихідний об'єкт.*

Розберемо призначення та механіку роботи кожного поля:

### 1. Поле `directory`
Рядок, що містить робочий каталог, у якому виконується команда компілятора. За стандартом це має бути абсолютний шлях. 

Це поле є критично важливим якорем для всієї подальшої резолюції шляхів. Усі відносні шляхи в аргументах компілятора — наприклад, каталоги включення `-I../include` або сам шлях до вихідного файлу `../src/sensor_node.cpp` — обчислюються відносно значення `directory`, а не відносно місця розташування самого файлу `compile_commands.json` чи кореня проєкту. Якщо зовнішній інструмент проігнорує `directory` і спробує розгорнути `-I../include` відносно каталогу, де відкритий редактор, пошук заголовків зазнає краху.

### 2. Поле `file`
Головний вихідний файл одиниці трансляції (наприклад, `.c`, `.cpp`, `.cc`, `.m`). Шлях може бути як абсолютним, так і відносним до каталогу `directory`.

Зверніть увагу: заголовочні файли (`.h`, `.hpp`, `.hxx`) **не є** окремими одиницями трансляції, вони не передаються компілятору як самостійний аргумент компіляції в об'єктний файл, а отже, за замовчуванням взагалі **відсутні** в базі даних компіляції. Як інструменти обходять це фундаментальне обмеження, ми детально розберемо в розділі про роботу мовних серверів.

### 3. Поля `arguments` та `command`
Запис мусить містити або масив рядків `arguments`, або єдиний рядок `command`.
* `arguments` — рекомендований сучасний формат. Це структурований масив токенів командного рядка `argv`, який передається безпосередньо системному виклику сімейства `execve` без участі командної оболонки (англ. *shell*).
* `command` — спадковий формат, де вся команда записана одним суцільним рядком:
  ```json
  "command": "/usr/bin/clang++ -c -std=c++20 -DFOO=\\\"bar baz\\\" ../src/sensor_node.cpp"
  ```

Використання `command` породжує небезпечну неоднозначність: щоб розбити рядок на окремі аргументи, сторонній парсер має реалізувати логіку екранування символів командної оболонки. При цьому правила розбору лапок, зворотних слешів та пробілів у рядках на платформі POSIX (`/bin/sh`) принципово відрізняються від правил командного рядка Windows (`cmd.exe` та `CommandLineToArgvW`). Якщо макрос містить пробіли, наприклад `-DAPP_NAME="Smart Sensor"`, перетворення туди й назад через рядок `command` регулярно ламає екранування. Формат `arguments` повністю позбавлений цієї вади, оскільки кожен токен уже ізольований у власному рядку JSON.

### 4. Поле `output` (опційне)
Шлях до вихідного файлу артефакту (зазвичай об'єктного файлу `.o` або `.obj`). Поле дозволяє інструментам зіставити запис бази компіляції з конкретною вершиною графа залежностей системи збірки.

## Джерела походження: декларативний експорт проти динамічного перехоплення

База даних компіляції не створюється розробником вручну — підтримувати тисячі викликів компілятора з десятками прапорців у текстовому файлі неможливо. Існує два принципово різних підходи до її автоматичного отримання: **декларативна генерація** на основі моделі системи збірки та **динамічне перехоплення** реальних викликів операційної системи.

![Два шляхи генерації бази даних компіляції: декларативний експорт проти динамічного перехоплення викликів](/root/sys/sys-bsystem/compilation-database/img/generator-vs-interceptor.svg)
*Декларативний підхід вивантажує граф правил миттєво на етапі генерації; перехоплення спостерігає за системними викликами під час виконання збірки.*

### Декларативний експорт із генераторів збірки

Сучасні метасистеми збірки (CMake, Meson) під час конфігурації проєкту вже будують повний граф цілей, володіють інформацією про всі прапорці та каталоги включення. Тому вони здатні згенерувати `compile_commands.json` безпосередньо, без виконання самої компіляції.

У CMake експорт бази активується стандартною змінною:

```bash
cmake -B build -S . -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
```

Або декларативно всередині кореневого `CMakeLists.txt`:

```cmake
set(CMAKE_EXPORT_COMPILE_COMMANDS ON CACHE BOOL "Export compile_commands.json" FORCE)
```

На етапі генерації CMake створює файл `build/compile_commands.json`. 

Однак тут є суттєве обмеження архітектури CMake: прапорець `CMAKE_EXPORT_COMPILE_COMMANDS` підтримується **лише** генераторами на основі файлів правил: `Makefile` (Unix Makefiles) та `Ninja`. Генератори під багатоконфігураційні IDE (Visual Studio, Xcode) історично не підтримували цей прапорець, оскільки в них конфігурації Debug та Release співіснують в одному проєкті, а структура прапорців компіляції вирішується не генератором CMake, а внутрішнім рушієм MSBuild чи Xcode під час збірки.

Якщо проєкт збирається за допомогою Ninja, отримати базу компіляції можна безпосередньо з файлу `build.ninja` вбудованим інструментом:

```bash
ninja -t compdb > compile_commands.json
```

Ця команда зчитує всі правила компіляції, зареєстровані в `build.ninja`, підставляє змінні й видає валідний JSON у стандартний вивід.

### Динамічне перехоплення процесів (Bear, intercept-build)

Що робити, якщо проєкт використовує спадкову систему збірки — заплутаний монолітний `Makefile`, написаний тридцять років тому, набір скриптів на Bash чи складну систему на основі GNU Autotools, де виклики компілятора генеруються динамічно під час роботи?

У цьому випадку структуру викликів неможливо витягти декларативно. Єдиний спосіб — запустити реальну збірку проєкту й зафіксувати кожен процес компілятора, який операційна система намагається породити.

Саме так працює утиліта **Bear** (англ. *Build EAR* — «вухо збірки»). Використання Bear виглядає максимально прозоро для користувача:

```bash
bear -- make -j8
```

Під капотом Bear використовує один із двох системних механізмів перехоплення:

#### 1. Механізм `LD_PRELOAD` (динамічна підміна бібліотек)
На POSIX-системах (Linux, BSD) Bear запускає процес збірки зі встановленою змінною середовища `LD_PRELOAD`, яка вказує на спеціальну динамічну бібліотеку-перехоплювач (`libear.so`).

Ця бібліотека підміняє стандартні функції запуску процесів із бібліотеки C (`libc`):
* `execve`
* `execv`, `execvp`, `execvpe`
* `posix_spawn`, `posix_spawnp`

Коли `make` викликає, наприклад, `execve("/usr/bin/g++", argv, envp)`, керування спочатку потрапляє в обгортку Bear. Перехоплювач виконує такий алгоритм:
1. Зчитує поточний робочий каталог через системний виклик `getcwd()`.
2. Аналізує ім'я виконуваного файлу та аргументи `argv`. Якщо процес не є компілятором (наприклад, це `mkdir`, `cp`, `sed`, `git`), перехоплювач ігнорує його.
3. Якщо процес розпізнано як компілятор C/C++ (за маскою імен `gcc`, `g++`, `clang`, `c++`, `cc`, `arm-none-eabi-gcc` тощо) і в аргументах присутній прапорець компіляції (`-c`), Bear передає знімок виклику (`directory`, `file`, `argv`) головному процесу-демону через сокет UNIX або канал IPC.
4. Викликає справжню системну функцію `execve`, дозволяючи процесу компіляції продовжитися у звичайному режимі.

#### 2. Механізм `ptrace` (системне трасування)
На операційних системах із підвищеними вимогами до безпеки (наприклад, macOS із увімкненим механізмом SIP — System Integrity Protection) механізм `LD_PRELOAD` блокується ядром для системних бінарних файлів (зокрема `/bin/sh`). У таких середовищах Bear використовує системний виклик трасування процесів `ptrace`, перехоплюючи кожну точку входу в ядро при виконанні системного виклику створення образу процесу `sys_execve`.

Головна вимога при використанні перехоплювачів: **збірка обов'язково має бути чистою**. Якщо проєкт уже зібраний, інкрементальна збірка не викликатиме компілятор для незмінених файлів, і результуючий `compile_commands.json` виявиться порожнім або неповним:

```bash
# Правильний порядок для Bear:
make clean
bear -- make -j$(nproc)
```

## Споживачі бази: від LSP і clangd до статичного аналізу

Після того як `compile_commands.json` згенеровано, він стає спільним знаменником для цілої екосистеми інструментів розробки.

![Ланцюжок обробки бази компіляції в мовному сервері clangd](/root/sys/sys-bsystem/compilation-database/img/clangd-indexer-flow.svg)
*Мовний сервер використовує параметри з бази даних компіляції для побудови точного абстрактного синтаксичного дерева (AST).*

### Мовні сервери та протокол LSP (clangd, ccls)

Сучасні редактори (VS Code, Neovim, CLion, Emacs, Helix) спілкуються з мовними рушіями через стандартизований протокол LSP (англ. *Language Server Protocol*). Основним сервером мови для C++ у середовищі LLVM є **clangd**.

Коли ви відкриваєте файл проєкту, `clangd` виконує таку послідовність дій:
1. **Пошук бази даних:** Сервер сканує каталог відкритого файлу, піднімається вгору по дереву батьківських каталогів, а також перевіряє типові підкаталоги `build/`, `out/`, `build/Debug/`.
2. **Зіставлення файлу:** Знайшовши `compile_commands.json`, `clangd` шукає запис, поле `file` якого збігається з відкритим у редакторі файлом.
3. **Ініціалізація LibTooling:** `clangd` створює віртуальний екземпляр фронтенду компілятора (`clang::CompilerInstance`), передаючи йому робочий каталог `directory` та точний список прапорців `arguments`.
4. **Побудова AST та індексу:** Компілятор розгортає всі макроси, резолвить шаблони та будує повне абстрактне синтаксичне дерево (AST).

Завдяки цьому автодоповнення, перевірка типів і підказки аргументів працюють із стовідсотковою відповідністю реальній збірці.

### Евристика заголовків (The Header File Dilemma)

Як ми з'ясували, заголовки (`.h`, `.hpp`) не компілюються окремо, тому записів для них у `compile_commands.json` немає. Що відбувається, коли ви відкриваєте у редакторі `include/utils.hpp`?

`clangd` використовує складний алгоритм евристичної резолюції (англ. *header heuristics*):
1. **Пряме включення:** Сервер перевіряє глобальний індекс проєкту й шукає, чи є в базі файл джерела `.cpp`, який явно містить рядок `#include "utils.hpp"`. Якщо такий файл знайдено (наприклад, `src/utils.cpp`), `clangd` бере прапорці компіляції цього `.cpp` файлу.
2. **Файл-близнюк (Sister file):** Якщо прямих включень ще не проіндексовано, сервер шукає сирцевий файл з ідентичною базовою назвою в сусідніх каталогах (наприклад, `src/utils.cpp` або `lib/utils.cc`).
3. **Сусід по каталогу (Interpolation):** Якщо відповідника немає, `clangd` бере середньостатистичний запис компіляції для файлів із найближчого каталогу, видаляє прапорець вхідного файлу та замінює його на поточний заголовок.

Цей механізм дозволяє редактору бездоганно розбирати навіть ізольовані заголовочні файли.

### Статичний аналіз коду (clang-tidy)

Утиліта статичного аналізу `clang-tidy` перевіряє код на наявність логічних помилок, витоків ресурсів, порушень стандартів безпеки (CERT, MISRA) та застарілих ідіом мови.

Для роботи `clang-tidy` життєво необхідна база компіляції. Без інформації про макроси та шляхи пошуку заголовків статичний аналізатор просто не зможе побудувати AST і перетвориться на звичайний неефективний текстовий сканер регулярних виразів.

Запуск аналізу з використанням бази компіляції здійснюється прапорцем `-p`:

```bash
# -p вказує каталог, що містить compile_commands.json
clang-tidy -p build/ src/sensor_node.cpp
```

Аналізатор зчитує точні параметри трансляції, ініціалізує AST-матчери та знаходить реальні помилки, не відволікаючи розробника хибними повідомленнями про неіснуючі синтаксичні дефекти.

### Оптимізація дерева включень (Include-What-You-Use)

Інструмент **Include-What-You-Use (IWYU)** базується на бібліотеках Clang і використовує `compile_commands.json` для глибокого аналізу символів. Він з'ясовує, які саме типи з підключених заголовків насправді використовуються в кожній одиниці трансляції.

IWYU пропонує видалити зайві транзитивні директиви `#include` та замінити повні визначення класів на випереджальні оголошення (англ. *forward declarations*), що кардинально прискорює час збірки великих проєктів:

```bash
iwyu_tool -p build/ src/sensor_node.cpp
```

## Як інструменти нормалізують і фільтрують прапорці

База даних компіляції містить дослівний знімок виклику компілятора. Проте інструменти аналізу (такі як `clangd`, `clang-tidy` або `iwyu`) не є кодогенераторами — їхнє завдання полягає виключно в побудові семантичної моделі коду (AST), а не у створенні виконуваного бінарного коду.

Тому внутрішній рушій LLVM LibTooling застосовує до отриманого списку `arguments` правила автоматичної нормалізації та фільтрації:

### 1. Видалення прапорців виводу та контролю збірки
Прапорці, що керують створенням об'єктних файлів, не мають сенсу для аналізатора і видаляються з віртуального виклику:
* `-o <file>` — шлях збереження вихідного артефакту відкидається.
* `-c` або `-S` — інструкції генерації коду/асемблера.
* `-Werror` — заборона розглядати попередження як фатальні помилки, оскільки аналізатор мусить побудувати дерево навіть за наявності локальних попереджень.

### 2. Прапорці оптимізації та налагодження
Прапорці рівня оптимізації (`-O3`, `-O2`, `-Os`, `-flto`, `-g`, `-gline-tables-only`) та інструментування санітайзерами (`-fsanitize=address`) з точки зору чистки коду здебільшого ігноруються, оскільки вони стосуються бекенду компілятора. 

Проте прапорці оптимізації можуть неявно встановлювати макроси препроцесора (наприклад, `-O2` у GCC автоматично визначає `__OPTIMIZE__=1` та активує перевірки `_FORTIFY_SOURCE`). LibTooling враховує цей зв'язок, підтримуючи відповідні макроси активними у препроцесорі.

### 3. Фільтрація прапорців інших компіляторів (MSVC та GCC)
Якщо база компіляції була згенерована для збірки компілятором GCC або Microsoft Visual C++ (`cl.exe`), вона містить прапорці, синтаксис яких не є рідним для Clang (наприклад, `/EHsc`, `/std:c++latest`, `-fconserve-stack`).

Парсер аргументів Clang перемикається у відповідний режим сумісності драйвера (`clang-cl` для MSVC) або автоматично відкидає невідомі прапорці за допомогою правила `clang-diagnostic-unknown-argument`.

## Пастки, крос-компіляція та реальність інструментів

У реальних виробничих проєктах взаємодія інструментів із `compile_commands.json` стикається з низкою неочевидних крайових випадків.

### 1. Файли відповідей (Response Files `@file.rsp`)
На операційних системах із жорстким лімітом довжини командного рядка (зокрема у Windows API функція `CreateProcess` обмежує командний рядок 32767 символами) передача сотень каталогів включення у відкритому вигляді призводить до помилки переповнення буфера (англ. *command line too long*).

Системи збірки (CMake та Ninja) розв'язують цю проблему автоматично: вони записують усі прапорці в тимчасовий текстовий файл `flags.rsp`, а компілятору передають короткий рядок:

```bash
clang++ @CMakeFiles/node.dir/includes_CXX.rsp -c src/sensor_node.cpp
```

Якщо система збірки експортує такий запис у `compile_commands.json` у нерозгорнутому вигляді, простий сторонній парсер, який не вміє розгортати директиви `@file`, не побачить жодного каталогу пошуку заголовків. Сучасні бібліотеки (LLVM LibTooling) автоматично відкривають і парсять файли відповідей, але при самостійному аналізі бази це слід враховувати.

### 2. Обгортки компіляторів (ccache, distcc)
Якщо у проєкті увімкнено кешування компіляції через `ccache`, у виклику команди першим виконуваним файлом може стати сам `ccache`:

```json
"arguments": [
  "/usr/bin/ccache",
  "/usr/bin/g++",
  "-c",
  "src/sensor_node.cpp"
]
```

Інструменти аналізу повинні вміти розпізнавати префікси-обгортки та витягувати реальний драйвер компілятора (`/usr/bin/g++`), інакше спроба передати прапорці компілятора в `ccache` як у фронтенд завершиться помилкою розбору аргументів.

### 3. Крос-компіляція та прапорець `--query-driver`
Це одна з найглибших і найчастіших пасток у вбудованих системах (англ. *embedded development*).

Уявіть проєкт під мікроконтролер STM32 на базі ядра ARM Cortex-M4. Збірка виконується крос-компілятором:

```bash
arm-none-eabi-g++ -mcpu=cortex-m4 -mthumb -c main.cpp
```

Запис у `compile_commands.json` містить саме цей виклик. Однак мовний сервер `clangd`, запущений на комп'ютері розробника (архітектура x86_64), використовує внутрішній парсер Clang. Clang за замовчуванням звертається до системних заголовків стандартної бібліотеки хостової машини (`/usr/include/c++/...` для x86_64). У результаті типи на кшталт `uint32_t` або заголовки апаратних регістрів виявляються несумісними, і редактор заповнюється помилками.

Крос-компілятор `arm-none-eabi-g++` має власні вбудовані каталоги системних заголовків (sysroot), які він **не пише** у командному рядку, оскільки знає їх за замовчуванням.

Щоб повідомити `clangd` про ці приховані шляхи, використовується прапорець `--query-driver`:

```bash
clangd --query-driver=/usr/bin/arm-none-eabi*
```

Отримавши цей параметр, `clangd` під час завантаження бази знаходить виклик `arm-none-eabi-g++`, у фоновому режимі виконує команду:

```bash
arm-none-eabi-g++ -E -v -x c++ /dev/null
```

Ця команда змушує GCC вивести повний перелік його внутрішніх системних каталогів пошуку (sysroot, lib/gcc/arm-none-eabi/include тощо). `clangd` перехоплює цей вивід, витягує шляхи та прозоро додає їх до віртуального виклику свого парсера. У результаті інструмент аналізу бачить заголовки цільової вбудованої платформи з повною точністю.

### 4. Мультиконфігураційні збірки (Multi-Config Generators)

Коли проєкт збирається за допомогою генераторів типу `Ninja Multi-Config` або IDE-генераторів, дерево збірки містить одночасно кілька конфігурацій (Debug, Release, RelWithDebInfo).

Один і той самий файл `engine.cpp` у режимі Debug компілюється з прапорцями `-O0 -g -DDEBUG`, а в режимі Release — з `-O3 -DNDEBUG`. Базовий прапорець CMake `CMAKE_EXPORT_COMPILE_COMMANDS` за замовчуванням експортує лише першу або останню сконфігуровану збірку.

Щоб точно керувати конфігурацією в таких проєктах, застосовують роздільні каталоги збірки:

```bash
cmake -B build-debug -S . -DCMAKE_BUILD_TYPE=Debug -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake -B build-release -S . -DCMAKE_BUILD_TYPE=Release -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
```

Після цього мовний сервер або редактор налаштовується на роботу з відповідним підкаталогом збірки.

### 5. Згенеровані файли та послідовність першого запуску
База даних компіляції містить статичний опис того, **як** компілювати файли, але вона не містить вмісту згенерованих файлів.

Якщо ваш проєкт використовує генерацію коду — файли заголовків від Google Protocol Buffers (`message.pb.h`), конфігураційні заголовки CMake `config.h`, парсери Flex/Bison або метаоб'єктний компілятор Qt `moc` — ці файли фізично не існують на диску доти, доки не буде запущено збірку.

Навіть за наявності ідеального `compile_commands.json` мовний сервер виділятиме виклики `#include "message.pb.h"` як помилки, доки система збірки хоча б раз не виконає етап генерації цілей:

```bash
# Генерація обов'язкових заголовочних файлів перед початком редагування:
cmake --build build --target generate_headers
```

## Практичні маніпуляції з базою даних: jq, compdb та .clangd

У великих монорепозиторіях або проєктах із багатьма підсистемами часто виникає потреба об'єднати, трансформувати або доповнити базу даних компіляції.

### Об'єднання баз даних кількох підпроєктів через `jq`

Якщо репозиторій містить кілька незалежних компонентів зі своїми власними каталогами збірки (`backend/build` та `firmware/build`), їхні бази компіляції можна об'єднати в єдиний кореневий файл за допомогою утиліти `jq`:

```bash
jq -s 'add' backend/build/compile_commands.json firmware/build/compile_commands.json > compile_commands.json
```

Ця операція зливає два масиви в один, дозволяючи редактору працювати з усім деревом монорепозиторію з єдиної точки входу.

### Генерація синтетичних записів для заголовків через `compdb`

Утиліта `compdb` дозволяє модифікувати `compile_commands.json`, автоматично додаючи до нього явні записи для кожного знайденого заголовочного файлу `.h`/`.hpp`:

```bash
# Встановлення та запуск compdb
pip install compdb
compdb -p build/ list > build/compile_commands_with_headers.json
```

Для кожного заголовка `compdb` знаходить найбільш відповідний `.cpp` файл, дублює його рядок компіляції та замінює ім'я файлу джерела на ім'я заголовка. Це значно спрощує роботу старих інструментів аналізу, які не мають вбудованих евристик заголовків.

### Локальне коригування через файл `.clangd`

Якщо ви не можете змінити систему збірки, але мовний сервер потребує специфічних налаштувань, у корені проєкту створюється конфігураційний файл `.clangd`. Він дозволяє динамічно модифікувати прапорці під час завантаження бази:

```yaml
CompileFlags:
  # Додати прапорці до кожного запису
  Add: [-Wno-unknown-warning-option, -I/opt/custom_sdk/include]
  # Видалити конфліктні прапорці GCC/MSVC
  Remove: [-fconserve-stack, -mabi=*]
  # Вказати компілятор для драйвера
  Compiler: clang++
```

Цей механізм ізолює налаштування редактора від виробничих скриптів збірки.

## Програмна робота з базою даних через LibTooling

Для автоматизації аналізу та рефакторингу коду проєкт Clang надає офіційний інтерфейс C++ — бібліотеку **LibTooling**. Вона містить високорівневий клас `clang::tooling::CompilationDatabase`, призначений для завантаження, навігації та виконання дій над одиницями трансляції, описаними в `compile_commands.json`.

Наступний практичний приклад демонструє, як програмно завантажити базу компіляції з каталогу збірки, знайти прапорці для конкретного файлу джерела та вивести повний перелік команд компіляції:

:::tabs
```c
/* Приклад використання C API / системного інтерфейсу читання бази компіляції */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

/* Структура для збереження однієї команди одиниці трансляції */
typedef struct {
    char directory[1024];
    char file[1024];
    char command[4096];
} CompileEntry;

/* Простий лінійний парсер записів бази компіляції */
int parse_simple_compdb(const char* filepath, CompileEntry* entries, int max_entries) {
    FILE* fp = fopen(filepath, "r");
    if (!fp) {
        perror("Не вдалося відкрити compile_commands.json");
        return -1;
    }

    char line[1024];
    int count = 0;
    CompileEntry current;
    memset(&current, 0, sizeof(current));

    while (fgets(line, sizeof(line), fp) && count < max_entries) {
        char* dir_pos = strstr(line, "\"directory\":");
        char* file_pos = strstr(line, "\"file\":");
        char* cmd_pos = strstr(line, "\"command\":");

        if (dir_pos) {
            sscanf(dir_pos, "\"directory\": \"%1023[^\"]\"", current.directory);
        } else if (file_pos) {
            sscanf(file_pos, "\"file\": \"%1023[^\"]\"", current.file);
        } else if (cmd_pos) {
            sscanf(cmd_pos, "\"command\": \"%4095[^\"]\"", current.command);
            /* Завершення опису поточного об'єкта */
            entries[count++] = current;
            memset(&current, 0, sizeof(current));
        }
    }

    fclose(fp);
    return count;
}

int main(int argc, char** argv) {
    const char* db_path = (argc > 1) ? argv[1] : "build/compile_commands.json";
    CompileEntry entries[64];

    int total = parse_simple_compdb(db_path, entries, 64);
    if (total <= 0) {
        fprintf(stderr, "Записів компіляції не знайдено або сталася помилка.\n");
        return 1;
    }

    printf("Успішно завантажено записів: %d\n", total);
    for (int i = 0; i < total; ++i) {
        printf("[%d] Файл: %s\n    Каталог: %s\n", i + 1, entries[i].file, entries[i].directory);
    }

    return 0;
}

// Ідіоматична робота з базою компіляції через офіційний C++ API Clang LibTooling
#include <iostream>
#include <memory>
#include <string>
#include <string_view>
#include <vector>

#include <clang/Tooling/CompilationDatabase.h>
#include <clang/Tooling/Tooling.h>
#include <llvm/Support/raw_ostream.h>

void inspect_compilation_database(std::string_view build_directory) {
    std::string error_message;
    
    // Завантаження бази компіляції з каталогу збірки (RAII та безпечне керування пам'яттю)
    std::unique_ptr<clang::tooling::CompilationDatabase> compdb =
        clang::tooling::CompilationDatabase::loadFromDirectory(
            std::string(build_directory), error_message);

    if (!compdb) {
        llvm::errs() << "Помилка завантаження бази даних: " << error_message << "\n";
        return;
    }

    // Отримання списку всіх файлів, зареєстрованих у базі
    std::vector<std::string> all_files = compdb->getAllFiles();
    std::cout << "Знайдено одиниць трансляції в базі: " << all_files.size() << "\n\n";

    for (const auto& file_path : all_files) {
        std::cout << "Файл: " << file_path << "\n";

        // Отримання точних команд компіляції для конкретного файлу
        std::vector<clang::tooling::CompileCommand> commands =
            compdb->getCompileCommands(file_path);

        for (const auto& cmd : commands) {
            std::cout << "  Робочий каталог: " << cmd.Directory << "\n";
            std::cout << "  Вихідний артефакт: " << cmd.Output << "\n";
            std::cout << "  Аргументи виклику (" << cmd.CommandLine.size() << " токенів):\n";
            
            for (const auto& arg : cmd.CommandLine) {
                std::cout << "    " << arg << "\n";
            }
        }
        std::cout << "----------------------------------------\n";
    }
}

int main(int argc, char** argv) {
    std::string build_dir = (argc > 1) ? argv[1] : "build";
    inspect_compilation_database(build_dir);
    return 0;
}
```

## Синтез: міст через тридцятирічний розрив

Поява `compile_commands.json` стала поворотним моментом в інженерії програмного забезпечення на C та C++. Вона зруйнувала монополію закритих системних середовищ розробки й вирішила тридцятирічну проблему несумісності між системами збірки та інструментами аналізу.

Суть цього стандарту полягає в простому розподілі обов'язків:
1. **Система збірки** залишається єдиним господарем конфігурації: вона визначає макроси, залежності та прапорці оптимізації.
2. **База даних компіляції** слугує відкритим протоколом експорту цього знання у вигляді точного знімка викликів компілятора.
3. **Інструменти розробки** (LSP-сервери `clangd`, аналізатори `clang-tidy`, засоби аналізу безпеки CodeQL та утиліти рефакторингу) споживають цей знімок, гарантуючи стовідсоткову семантичну точність аналізу вихідного коду.

Розуміння структури `compile_commands.json`, механізмів його генерації через CMake чи Bear та методів розв'язання крайових випадків крос-компіляції є базовою навичкою сучасного системного розробника, яка перетворює налаштування робочого оточення з непередбачуваної боротьби з редактором на точний і керований інженерний процес.
