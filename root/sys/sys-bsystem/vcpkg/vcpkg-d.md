Кросплатформний промисловий шлюз збирає мережевий стек на базі Boost.Asio, бібліотеку серіалізації nlohmann_json та криптографічний рушій OpenSSL. Якщо цей проєкт компілювати для Windows за допомогою Visual Studio 2022 (компілятор MSVC, архітектура x64), розробник має гарантувати, що кожна стороння бібліотека скомпільована з однаковим варіантом рантайму C Runtime (CRT) — наприклад, динамічним `/MD` для релізної конфігурації та `/MDd` для налагоджувальної. Якщо ж хоча б одна статична бібліотека випадково зібрана зі статичним рантаймом `/MT`, компонувальник згенерує фатальні конфлікти символів `_malloc` та `_free`, а спроба виділити пам'ять в одному модулі та звільнити в іншому призведе до падіння процесу через пошкодження купи.

Коли той самий проєкт переносять на плату керування під Linux ARM64 (крос-компілятор `aarch64-linux-gnu-g++`) або збирають під macOS (Apple Clang), виникає новий набір несумісностей: відмінності в ABI стандартної бібліотеки C++ (`libstdc++` проти `libc++`), різні системні корені (sysroots) та необхідність компілювати інструменти генерації коду (такі як компілятор протобуферів `protoc`) під архітектуру хоста, а самі бібліотеки — під цільову архітектуру процесора.

Спроба завантажувати готові двійкові пакети з централізованого репозиторію розбивається об неможливість заздалегідь згенерувати бінарні файли під усі комбінації компіляторів, стандартів C++17/20/23, прапорців оптимізації та цільових платформ. Пакетний менеджер [vcpkg](root:sys-bsystem/vcpkg/hist-vcpkg-evolution.md) вирішує цю фундаментальну проблему за допомогою моделі повної збірки з вихідного коду (source-first): залежності описуються скриптами на самій мові CMake (**порти**), конфігурація цільової платформи фіксується в декларативних файлах (**тріплети**), а відтворюваність і швидкість гарантуються ізольованим **маніфестним режимом** та криптографічним **бінарним кешуванням**.

## Філософія та внутрішня структура каталогів vcpkg

На відміну від менеджерів пакетів, які використовують власні високорівневі мови опису конфігурацій (як-от Python у Conan чи власні DSL у системних пакувальниках), vcpkg побудований безпосередньо навколо мови CMake. Це зменшує когнітивне навантаження на інженерів C++: правила збірки портів, перевірка прапорців компілятора та експорт імпортованих цілей записуються стандартизованими викликами CMake.

Менеджер функціонує як оркестратор над нативними системами збірки сторонніх проєктів. Якщо бібліотека використовує CMake, vcpkg запускає генератор Ninja з потрібними прапорцями; якщо бібліотека збирається через Autotools, Meson або Make, vcpkg ініціалізує відповідне середовище (зокрема MSYS2 на Windows) і керує нативним процесом компіляції.

Для забезпечення чистоти та ізоляції збірки кореневий каталог vcpkg структурований на функціональні простори:

1. `ports/` — репозиторій рецептів збірки. Кожен підкаталог містить файл декларації метаданих `vcpkg.json`, скрипт збірки `portfile.cmake` та опціональні файли латок (`.patch`), що виправляють кросплатформні помилки або інтеграцію з CMake.
2. `triplets/` (та `triplets/community/`) — файли опису цільових систем (`.cmake`), які задають цільову архітектуру процесора, операційну систему, модель компонування бібліотек (статична чи динамічна) та модель зв'язування рантайму C/C++.
3. `downloads/` — централізований кеш вихідних кодів та зовнішніх утиліт. Усі завантажені архіви перевіряються за строгим криптографічним хешем SHA-512. Підкаталог `downloads/tools/` містить локальні портативні версії інструментів (CMake, Ninja, PowerShell, 7-Zip), що гарантує незалежність vcpkg від версій утиліт, встановлених у системі розробника.
4. `buildtrees/` — ізольовані тимчасові каталоги збірки. Для кожного порту тут створюються окремі дерева розпакованого вихідного коду (`src/`), конфігураційні простори та журнали компіляції окремо для конфігурацій Release (`*-rel/`) та Debug (`*-dbg/`). У разі збою компіляції точна причина міститься у відповідних файлах `config-*.log` та `build-*.log`.
5. `packages/` — проміжний каталог упакованих портів. Після успішного завершення `portfile.cmake` результат встановлення розміщується у підкаталозі `<port>_<triplet>/` (наприклад, `fmt_x64-windows/`), що містить строго стандартизовану структуру каталогів (`include/`, `lib/`, `bin/`, `share/`, `debug/lib/`, `debug/bin/`).
6. `installed/` (або `vcpkg_installed/` у маніфестному режимі) — фінальне дерево інсталяції. Саме цей каталог підключається до споживчого проєкту через механізм `CMAKE_TOOLCHAIN_FILE` і стає джерелом заголовків, бібліотек та конфігураційних файлів CMake.

Цей поділ гарантує, що жодна бібліотека не встановлюється в спільні системні каталоги операційної системи (`/usr/local` чи `Program Files`), усуваючи конфлікти версій та взаємне перезаписування заголовкових файлів.

## Анатомія порту: vcpkg.json, portfile.cmake та нормалізація

Порт vcpkg складається з двох ключових компонентів: декларативного маніфесту `vcpkg.json`, що визначає зовнішні метадані та граф залежностей, та процедурного скрипта `portfile.cmake`, що виконує етапи отримання та компіляції коду.

### Декларація маніфесту порту (vcpkg.json)

Маніфест порту є документом у форматі JSON, що описує ідентифікаційні дані пакета, ліцензійні обмеження, список залежностей та конфігураційні компоненти (features):

```json
{
  "name": "fast-telemetry",
  "version-semver": "2.1.0",
  "port-version": 2,
  "description": "Асинхронний рушій збору телеметрії",
  "homepage": "https://github.com/example/fast-telemetry",
  "license": "Apache-2.0",
  "dependencies": [
    "fmt",
    {
      "name": "openssl",
      "platform": "!windows | !arm"
    }
  ],
  "features": {
    "zstd": {
      "description": "Підтримка стиснення через zstd",
      "dependencies": [
        "zstd"
      ]
    }
  }
}
```

Поле `port-version` інкрементується тоді, коли автор порту вносить зміни в інструкції збірки, оновлює патчі або виправляє помилки експорту цілей CMake без зміни версії вихідного коду оригінальної бібліотеки. Поле `platform` дозволяє задавати булеві вирази для умовного підключення залежностей залежно від операційної системи та архітектури.

![Анатомія та послідовність фаз portfile.cmake](/root/sys/sys-bsystem/vcpkg/img/vcpkg-portfile-phases.svg)
*Анатомія та послідовність фаз portfile.cmake: конвеєр отримання сирців із перевіркою хешу, застосування латок, конфігурації, паралельної інсталяції та нормалізації експортованих цілей.*

### Життєвий цикл portfile.cmake

Скрипт `portfile.cmake` виконується рушієм vcpkg в ізольованому контексті інтерпретатора CMake. Його завдання — трансформувати вихідний код у стандартизовану структуру каталогу `packages/<port>_<triplet>/`.

Життєвий цикл порту складається з шести послідовних етапів:

1. **Отримання вихідного коду та перевірка цілісності:**
   Завантаження архіву виконується через спеціалізовані помічники, такі як `vcpkg_from_github()`, `vcpkg_from_git()` або `vcpkg_download_distfile()`. Обов'язковим параметром є `SHA512`: якщо завантажений файл не збігається з еталонним хешем, виконання миттєво переривається. Це унеможливлює підміну джерел коду та захищає конвеєр від атак на ланцюг постачання.

2. **Застосування латок (патчування):**
   Оригінальні репозиторії часто містять жорстко закодовані прапорці компілятора (наприклад, безумовний `/MT` у MSVC або `-fPIC` без перевірки типу бібліотеки), застарілі модулі пошуку залежностей або помилки експорту символів під Windows чи ARM. Список `.patch` файлів передається в секцію `PATCHES` функції завантаження, і vcpkg накладає їх на чисте дерево вихідного коду перед початком конфігурації.

3. **Конфігурація системи збірки:**
   Функція `vcpkg_cmake_configure()` ініціалізує генератор CMake (за замовчуванням Ninja) з прапорцями, визначеними поточним тріплетом. Функція автоматично транслює налаштування цільової архітектури, шляхи до залежностей через `CMAKE_PREFIX_PATH` та передає специфічні опції проєкту.

4. **Паралельна компіляція та встановлення:**
   Виклик `vcpkg_cmake_install()` компілює проєкт і встановлює артефакти в тимчасовий каталог `${CURRENT_PACKAGES_DIR}`. vcpkg автоматично виконує подвійну інсталяцію: спочатку конфігурацію Release (у корінь каталогу пакета), а потім конфігурацію Debug (у підкаталог `${CURRENT_PACKAGES_DIR}/debug/`).

5. **Нормалізація конфігураційних файлів (Fixup):**
   Сторонні системи збірки встановлюють конфігураційні файли CMake (`*Config.cmake`) у довільні місця: `lib/cmake/<port>/`, `share/cmake/<port>/` або `cmake/`. Хелпер `vcpkg_cmake_config_fixup()` переносить усі конфігураційні описи в уніфікований каталог `share/<port>/`, одночасно виправляючи відносні шляхи до бінарних бібліотек `lib/` та `debug/lib/`. Завдяки цьому споживчий проєкт завжди знаходить бібліотеку через `find_package(<port> CONFIG REQUIRED)`.

6. **Очищення та валідація лінтером:**
   Перед запаковуванням vcpkg запускає вбудовані перевірки:
   - Видаляє каталоги `debug/include` та `debug/share`, оскільки заголовкові файли та документація мають бути ідентичними для Release і Debug (наявність відмінностей вважається дефектом архітектури порту).
   - За допомогою `vcpkg_fixup_pkgconfig()` виправляє шляхи у файлах `*.pc`.
   - За допомогою `vcpkg_copy_pdbs()` копіює налагоджувальні символи Visual Studio у відповідні каталоги `bin/` та `debug/bin/`.
   - За допомогою `vcpkg_install_copyright()` копіює файл ліцензії в `share/<port>/copyright` (відсутність ліцензійного файлу блокує збірку).

Повний перелік усіх доступних функцій конфігурації та лінтування зібрано у [довіднику допоміжних функцій portfile](root:sys-bsystem/vcpkg/api-vcpkg-portfile-helpers.md).

## Тріплети: керування цільовою платформою та крос-компіляція

У термінології vcpkg **тріплет (triplet)** — це повний опис середовища компіляції та моделі двійкового компонування. Назва походить від традиційного поняття цільового тріплета компілятора (`arch-vendor-os`), проте у vcpkg тріплет є повноцінним конфігураційним файлом на мові CMake, що містить правила формування ABI.

![Анатомія тріплета та поділ на Target і Host](/root/sys/sys-bsystem/vcpkg/img/vcpkg-triplet-matrix.svg)
*Анатомія тріплета та поділ на Target і Host: налаштування архітектури, моделей зв'язування CRT і бібліотек, а також розмежування компіляції інструментів генерації коду та цільових бібліотек.*

### Ключові змінні тріплета

Файл тріплета (наприклад, `triplets/x64-windows.cmake` або користувацький оверлей-тріплет) оперує наступними системними змінними:

| Змінна | Значення | Призначення |
| :--- | :--- | :--- |
| `VCPKG_TARGET_ARCHITECTURE` | `x64`, `x86`, `arm`, `arm64`, `wasm32` | Цільова архітектура процесора. |
| `VCPKG_CRT_LINKAGE` | `dynamic`, `static` | Модель лінкування рантайму C (MSVC `/MD` vs `/MT`). |
| `VCPKG_LIBRARY_LINKAGE` | `dynamic`, `static` | Тип збірки створюваних бібліотек (`.so`/`.dll` vs `.a`/`.lib`). |
| `VCPKG_CMAKE_SYSTEM_NAME` | `WindowsStore`, `Linux`, `Darwin`, `Android`, `iOS` | Цільова операційна система (порожнє для Desktop Windows). |
| `VCPKG_CHAINLOAD_TOOLCHAIN_FILE` | Шлях до файлу | Шлях до зовнішнього тулчейна (наприклад, Android NDK або крос-GCC). |
| `VCPKG_C_FLAGS` / `VCPKG_CXX_FLAGS` | Рядок прапорців | Глобальні прапорці компіляції C/C++, що додаються до кожного порту. |

### Динамічне проти статичного лінкування на Windows

На платформі Windows комбінація змінних `VCPKG_LIBRARY_LINKAGE` та `VCPKG_CRT_LINKAGE` утворює чотири принципово різні моделі збірки:

1. `x64-windows` (за замовчуванням):
   `VCPKG_LIBRARY_LINKAGE = dynamic`, `VCPKG_CRT_LINKAGE = dynamic`. Порти збираються як `.dll`, використовуючи динамічний CRT (`/MD` у Release, `/MDd` у Debug).
2. `x64-windows-static`:
   `VCPKG_LIBRARY_LINKAGE = static`, `VCPKG_CRT_LINKAGE = static`. Порти збираються як статичні бібліотеки `.lib` зі статичним включенням рантайму (`/MT`, `/MTd`). Отримані виконувані файли є повністю автономними і не потребують встановлення розповсюджуваних пакетів Visual C++ Redistributable.
3. `x64-windows-static-md`:
   `VCPKG_LIBRARY_LINKAGE = static`, `VCPKG_CRT_LINKAGE = dynamic`. Бібліотеки є статичними архівами `.lib`, проте використовують динамічний рантайм (`/MD`). Це стандартна корпоративна практика для запобігання дублюванню глобального стану пам'яті всередині процесу.

### Розділення Target Triplet та Host Triplet

Під час крос-компіляції (наприклад, збірка на робочій станції x86_64 під керуванням Linux для цільової плати ARM64 Linux або Android) виникає класична проблема залежностей інструментарію:

- Проєкт використовує бібліотеку `protobuf`. Для роботи програми потрібна цільова бібліотека `libprotobuf.a`, скомпільована для ARM64.
- Проте під час самої збірки система має згенерувати C++-код із файлів `.proto`. Для цього необхідний виконуваний файл `protoc`, який повинен виконуватися на машині збірки (x86_64 Host).

vcpkg вирішує цю суперечність через явний поділ на **Target Triplet** (`--triplet=arm64-linux`) та **Host Triplet** (`--host-triplet=x64-linux`). У маніфесті залежність від компілятора протоколів оголошується з атрибутом `"host": true`:

```json
{
  "dependencies": [
    {
      "name": "protobuf",
      "host": true
    },
    {
      "name": "protobuf"
    }
  ]
}
```

vcpkg виконує збірку пакета `protobuf` двічі: спочатку для хостового тріплета, експортуючи бінарний файл `protoc` у каталог `buildtrees/`, а потім для цільового тріплета, лінкуючи вихідну цільову бібліотеку.

Для нестандартних вбудованих середовищ розробник може створювати власні тріплети без модифікації системного дерева vcpkg за допомогою механізму [оверлей-портів та оверлей-тріплетів](root:sys-bsystem/vcpkg/proj-custom-port-overlay.md).

## Класичний режим проти Маніфестного режиму

Історично vcpkg починався як імперативний системний інструмент (**Classic Mode**), проте для забезпечення сучасної інженерної культури безперервної інтеграції був переведений на декларативну модель (**Manifest Mode**).

### Класичний режим (Classic Mode) та його обмеження

У класичному режимі розробник керує пакетами через термінал:

```bash
vcpkg install fmt:x64-linux zlib:x64-linux sqlite3:x64-linux
```

Усі скомпільовані пакети встановлюються в єдиний глобальний каталог `vcpkg/installed/`. 

Цей режим має три системні вади:
1. **Відсутність ізоляції:** якщо Проєкт 1 вимагає `boost` версії 1.78, а Проєкт 2 потребує нововведень `boost` 1.83, вони не можуть співіснувати на одній машині розробника.
2. **Невизначеність залежностей у Git:** репозиторій проєкту не містить інформації про те, які пакети та яких версій потрібні для його збірки.
3. **Руйнування відтворюваності в CI:** зміна стану глобального репозиторію vcpkg ламає автоматичні збірки без зміни вихідного коду самого проєкту.

### Маніфестний режим (Manifest Mode)

У маніфестному режимі залежності стають частиною вихідного коду проєкту. У корені репозиторію поруч із `CMakeLists.txt` розміщується файл `vcpkg.json`.

Коли розробник запускає генерацію проєкту через CMake із зазначенням файлу тулчейна:

```bash
cmake -B build -S . -DCMAKE_TOOLCHAIN_FILE="$VCPKG_ROOT/scripts/buildsystems/vcpkg.cmake"
```

Тулчейн автоматично виконує наступну послідовність дій:
1. Виявляє `vcpkg.json` у дереві вихідного коду.
2. Створює ізольоване дерево інсталяції `build/vcpkg_installed/<triplet>/` безпосередньо всередині каталогу збірки.
3. Перевіряє наявність скомпільованих бінарних пакетів у локальному або віддаленому кеші.
4. Якщо бінарні пакети відсутні, завантажує сирці, компілює всі прямі та транзитивні залежності й встановлює їх в `build/vcpkg_installed/`.
5. Експортує шляхи до встановлених бібліотек у `CMAKE_PREFIX_PATH`, роблячи їх прозоро доступними для стандартних команд `find_package()`.

Керування конфігурацією маніфестного режиму здійснюється через супутній файл `vcpkg-configuration.json`, де визначаються реєстри пакетів, базові ревізії (baselines) та шляхи до локальних оверлеїв.

## Модель контролю версій: Baselines, MVS та Overrides

Однією з найскладніших проблем у керуванні залежностями C++ є вирішення конфліктів версій (Version Resolution). Класичні пакетні менеджери часто використовують SAT-солвери, які намагаються знайти максимально свіжу версію кожної бібліотеки, що відповідає діапазонам обмежень (наприклад, `^1.2.0` чи `>=2.0.0 <3.0.0`). У C++ такий підхід призводить до невідтворюваних збірок: сьогодні проєкт збирався успішно, а завтра випуск мінорного оновлення транзитивної залежності ламає компіляцію через непередбачені зміни у внутрішніх шаблонах.

vcpkg використовує детерміновану модель **Minimal Version Selection (MVS)**, запозичену з екосистеми мови Go, яка базується на трьох опорах: `builtin-baseline`, `version>=` та `overrides`.

![Модель версіонування та алгоритм Minimal Version Selection](/root/sys/sys-bsystem/vcpkg/img/vcpkg-version-resolution.svg)
*Модель версіонування та алгоритм Minimal Version Selection: детермінований вибір версій через початковий зріз baseline, фільтрацію High-Water Mark та абсолютний пріоритет секції overrides.*

### 1. Базовий зріз (builtin-baseline)

Поле `builtin-baseline` містить 40-символьний Git-хеш комміту офіційного репозиторію `microsoft/vcpkg`. Цей комміт задає точний «зріз у часі» для всієї екосистеми: кожному імені пакета зіставляється конкретна базова версія.

```json
{
  "name": "telemetry-gateway",
  "version-semver": "1.0.0",
  "builtin-baseline": "d3509a2d326f59fa05f4e1f7a1f59265f24ec4d9",
  "dependencies": [
    "fmt",
    "spdlog"
  ]
}
```

Якщо маніфест містить лише перелік імен бібліотек, vcpkg встановить рівно ті версії, які були зафіксовані у зазначеному комміті baseline (наприклад, `fmt` 9.1.0 та `spdlog` 1.11.0). Збірка залишатиметься побітово повторюваною через роки, навіть якщо в основній гілці vcpkg з'являться сотні нових випусків.

### 2. Схеми оголошення версій

vcpkg підтримує чотири формати запису версій:
- `version` — вільний семантичний формат (числа, розділені крапками).
- `version-semver` — строгий SemVer 2.0.0 (`MAJOR.MINOR.PATCH`).
- `version-date` — календарні версії (`YYYY-MM-DD`).
- `version-string` — текстовий рядок для проєктів із довільним найменуванням версій.

### 3. Обмеження версій та правило High-Water Mark

Якщо проєкт або одна з його бібліотек вимагає новішої функціональності, у маніфесті вказується мінімальне обмеження через `version>=`:

```json
{
  "dependencies": [
    {
      "name": "fmt",
      "version>=": "10.1.0"
    }
  ]
}
```

Рушій MVS обчислює фінальну версію за правилом **High-Water Mark**:
1. Початковою точкою є версія порту з `builtin-baseline`.
2. Якщо жодна пряма чи транзитивна залежність не вимагає вищої версії, обирається версія з baseline.
3. Якщо одна або кілька залежностей заявляють вимогу `version>=`, vcpkg обирає найвищу з усіх мінімально заявлених версій.
4. Менеджер ніколи самостійно не завантажує версію, новішу за максимальну з явно запитаних, що виключає випадковий дрейф версій.

### 4. Примусове перекриття (Overrides)

Якщо дві різні сторонні бібліотеки вимагають несумісних версій або розробнику необхідно терміново зафіксувати виправлену версію через виявлену вразливість, використовується блок `overrides`. Секція `overrides` має абсолютний пріоритет над baseline та всіма транзитивними обмеженнями `version>=`:

```json
{
  "overrides": [
    {
      "name": "fmt",
      "version": "10.1.1"
    },
    {
      "name": "openssl",
      "version": "3.1.4",
      "port-version": 1
    }
  ]
}
```

## Інтеграція з CMake: Toolchain, імпортовані цілі та розгортання DLL

Зв'язування vcpkg зі споживчим проєктом реалізовано через файл тулчейна CMake, розташований за шляхом `scripts/buildsystems/vcpkg.cmake`.

### Механіка роботи vcpkg.cmake

Під час конфігурації проєкту (`cmake -B build -DCMAKE_TOOLCHAIN_FILE=.../vcpkg.cmake`) файл тулчейна виконує три операції:

1. **Інжекція CMAKE_PREFIX_PATH:** Тулчейн додає каталоги `build/vcpkg_installed/<triplet>/` та `build/vcpkg_installed/<triplet>/debug/` до списку системного пошуку CMake.
2. **Перехоплення виклику find_package:** Тулчейн модифікує поведінку команд `find_package()`, надаючи пріоритет конфігураційним описам `*Config.cmake`, згенерованим та нормалізованим vcpkg.
3. **Chainloading сторонніх тулчейнів:** Якщо цільовий тріплет визначає змінну `VCPKG_CHAINLOAD_TOOLCHAIN_FILE`, vcpkg спочатку налаштовує власні внутрішні механізми маніфестів, а потім автоматично підключає вказаний файл тулчейна (наприклад, крос-компілятор для embedded Linux або тулчейн Clang/LLVM).

### Використання імпортованих цілей

Сучасний CMake оперує концепцією імпортованих цілей із просторами імен (`Namespace::Target`). vcpkg вимагає використання конфігураційного режиму пошуку (`CONFIG`):

```cmake
cmake_minimum_required(VERSION 3.24)
project(NetworkService CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# Пошук пакетів у дереві vcpkg_installed
find_package(fmt CONFIG REQUIRED)
find_package(nlohmann_json CONFIG REQUIRED)
find_package(OpenSSL REQUIRED)

add_executable(server src/main.cpp)

# Транзитивне зв'язування прапорців та каталогів заголовків
target_link_libraries(server PRIVATE
    fmt::fmt
    nlohmann_json::nlohmann_json
    OpenSSL::SSL
    OpenSSL::Crypto
)
```

Кожна імпортована ціль (`fmt::fmt`, `nlohmann_json::nlohmann_json`) автоматично містить усі публічні вимоги використання (`INTERFACE_INCLUDE_DIRECTORIES`, `INTERFACE_COMPILE_DEFINITIONS`, `INTERFACE_LINK_LIBRARIES`), позбавляючи розробника потреби вручну налаштовувати `include_directories()` чи `${OPENSSL_LIBRARIES}`.

### Автоматичне розгортання DLL під Windows (AppLocal)

На платформі Windows динамічні бібліотеки (`.dll`) завантажуються операційною системою за фіксованим алгоритмом пошуку: спочатку каталог, де розташований сам виконуваний файл `.exe`, потім системні каталоги `System32` та шляхи зі змінної оточення `PATH`. На відміну від Linux та macOS, виконувані файли Windows PE/COFF не підтримують механізм `RPATH`/`RUNPATH`.

Якщо проєкт зібрано з динамічним тріплетом `x64-windows`, усі скомпільовані `.dll` бібліотек розташовані в каталозі `build/vcpkg_installed/x64-windows/bin/`. Під час запуску скомпільованого `server.exe` операційна система видасть помилку про відсутність бібліотек `fmt.dll` чи `libssl-3-x64.dll`.

Для вирішення цієї проблеми vcpkg інтегрує скрипт `applocal.ps1` (або `applocal.py` на кросплатформних хостах). Під час фінального етапу збірки цілі в Visual Studio або Ninja тулчейн автоматично знаходить усі динамічні бібліотеки, від яких залежить виконуваний файл, і копіює їх безпосередньо в каталог виводу поруч із `.exe`. Керування цією поведінкою здійснюється змінною CMake:

```cmake
set(VCPKG_APPLOCAL_DEPS ON) # Увімкнено за замовчуванням для Windows
```

## Бінарне кешування та Asset Caching

Повна компіляція важких C++-бібліотек (таких як Boost, Qt, LLVM чи OpenCV) із вихідного коду може тривати годинами. Якщо кожен агент безперервної інтеграції (CI/CD) змушений повторювати збірку залежностей з нуля для кожного пул-реквесту, час зворотного зв'язку стає неприйнятним.

vcpkg усуває цю проблему за допомогою механізму **бінарного кешування (Binary Caching)**.

### Обчислення Package ABI Hash

Перед тим як почати збірку порту, vcpkg обчислює унікальний криптографічний хеш двійкової сумісності — **Package ABI Hash**. Цей хеш є детермінованою функцією від наступних параметрів:

1. Повний вміст файлів `vcpkg.json` та `portfile.cmake` порту.
2. Вміст усіх застосованих латок (`.patch`).
3. Повний вміст файлу тріплета (`x64-linux.cmake`) та налаштування тулчейна.
4. Ідентифікатор, точна версія та хеш двійкового файлу компілятора C/C++.
5. ABI-хеші всіх транзитивних залежностей порту.
6. Прапорці оптимізації та макроозначення препроцесора.

Зміна хоча б одного байта в будь-якому з цих компонентів (наприклад, зміна версії компілятора GCC з 13.1 на 13.2 або додавання оптимізаційного прапорця `-O3` у тріплет) змінює Package ABI Hash.

### Бекенди збереження бінарного кешу

Якщо пакет із поточним ABI Hash уже був одного разу скомпільований, vcpkg завантажує готовий упакований zip-архів із кешу і розпаковує його в `packages/<port>_<triplet>/` за кілька мілісекунд, минаючи етапи конфігурації та компіляції.

Конфігурація джерел кешу передається через змінну оточення `VCPKG_BINARY_SOURCES`:

```bash
# 1. Локальний файловий кеш на спільному мережевому диску
export VCPKG_BINARY_SOURCES="clear;files,/mnt/shared/vcpkg-cache,readwrite"

# 2. Кеш GitHub Actions у хмарі
export VCPKG_BINARY_SOURCES="clear;gha,readwrite"

# 3. Віддалений HTTP/REST сервер або корпоративний Nexus/Artifactory
export VCPKG_BINARY_SOURCES="clear;http,https://artifacts.company.internal/vcpkg/{name}/{version}/{sha}.zip,readwrite"

# 4. Репозиторій пакетів NuGet
export VCPKG_BINARY_SOURCES="clear;nuget,https://pkgs.dev.azure.com/org/_packaging/feed/nuget/v3/index.json,readwrite"
```

### Кешування вихідних ресурсів (Asset Caching)

Крім бінарних артефактів, vcpkg підтримує **Asset Caching** (кешування сирцевих архівів). Якщо зовнішній репозиторій бібліотеки на GitHub чи SourceForge тимчасово недоступний або проєкт збирається в повністю ізольованій корпоративній мережі без доступу до Інтернету (air-gapped environment), vcpkg завантажує оригінальні тарболи з внутрішнього корпоративного дзеркала:

```bash
export X_VCPKG_ASSET_SOURCES="clear;x-azurl,https://storage.company.internal/vcpkg-assets/,<sas-token>,readwrite"
```

## Зіставлення архітектурних рішень та діагностика

При впровадженні vcpkg у промислові проєкти важливо уникати поширених пасток конфігурації:

1. **Змішування рантаймів на Windows:** Завжди використовуйте узгоджені тріплети. Якщо проєкт збирається з прапорцем `/MD`, неприпустимо вручну підключати бібліотеки з тріплета `x64-windows-static` без ретельного контролю меж виділення пам'яті.
2. **Пропущений режим CONFIG у find_package:** Виклик `find_package(fmt REQUIRED)` замість `find_package(fmt CONFIG REQUIRED)` може призвести до випадкового підключення застарілого модуля `Findfmt.cmake` із системного каталогу CMake замість нативних конфігурацій vcpkg.
3. **Ігнорування блоку overrides при конфліктах транзитивних версій:** Якщо дві бібліотеки вимагають різних мажорних версій однієї залежності, рушій MVS вибере новішу, що може зламати компіляцію старішого коду. У таких випадках слід явно зафіксувати сумісну версію через `overrides` або адаптувати залежні модулі.

Завдяки поєднанню строгої декларативності маніфестів, гнучкості тріплетів та швидкості бінарного кешування vcpkg створює надійний фундамент для сучасної кросплатформної розробки мовами C та C++.
