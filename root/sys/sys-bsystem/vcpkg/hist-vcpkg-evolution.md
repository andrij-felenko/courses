# 📜 Еволюція vcpkg: від скриптів збірки під Windows до відтворюваних маніфестів

У вересні 2016 року на конференції CppCon інженери Microsoft презентували експериментальний інструмент з відкритим вихідним кодом під назвою vcpkg. На той момент екосистема C++ під Windows перебувала у стані глибокої кризи керування залежностями: у той час як світ .NET успішно використовував NuGet, спроби застосувати подібну модель бінарних пакетів до C++ зазнали невдачі. 

Головною перешкодою був комбінаторний вибух двійкового інтерфейсу (ABI). Бібліотека, скомпільована у Visual Studio 2015 під архітектуру x86 зі статичним зв'язуванням середовища виконання C Runtime (`/MT`), виявлялася абсолютно несумісною з проєктом під x64, зібраним у Visual Studio 2017 з динамічним рантаймом (`/MD`) у налагоджувальній конфігурації (`/MDd`). Спроба запакувати в один NuGet-пакет усі можливі комбінації прапорців призводила до гігабайтних архівів для найпростіших бібліотек, а поява нового оновлення компілятора робила весь репозиторій застарілим.

## Епоха єдиного комміту та модель портів

Команда розробників vcpkg під керівництвом Роберта Шумахера (Robert Schumacher) запропонувала принципово інший підхід, запозичений із традиційних систем портів операційних систем сімейства BSD (FreeBSD Ports, MacPorts) та Arch Linux AUR:
1. Замість поширення заздалегідь скомпільованих бінарних файлів інструмент постачає **інструкції збірки** (порти) мовою CMake.
2. Процес компіляції бібліотеки відбувається безпосередньо на машині розробника під керуванням його локального компілятора та з прапорцями, що відповідають його цільовій системі.
3. Усі порти зберігаються в єдиному монорепозиторії на GitHub.

У перші роки свого існування vcpkg працював за моделлю *rolling release* з єдиним станом (single-commit model). Користувач клонував репозиторій `microsoft/vcpkg`, запускав скрипт початкового завантаження (`bootstrap-vcpkg.bat` або `bootstrap-vcpkg.sh`) і виконував імперативну команду в терміналі:

```bash
vcpkg install boost-asio:x64-windows sqlite3:x64-windows
```

Усі скомпільовані заголовки, статичні бібліотеки `.lib` та динамічні бібліотеки `.dll` складалися в єдиний глобальний каталог `installed/x64-windows/`. За допомогою команди `vcpkg integrate install` менеджер прописував шляхи до цього каталогу в системні конфігураційні файли MSBuild, завдяки чому будь-який новостворений проєкт у Visual Studio міг автоматично бачити `#include <boost/asio.hpp>` без ручного налаштування властивостей проєкту.

Цей підхід забезпечив вибухове зростання популярності інструменту серед розробників під Windows, проте дуже швидко виявив суттєві архітектурні обмеження при масштабуванні на великі команди та кросплатформні системи.

## Криза глобального стану та відсутності версіонування

У міру того, як каталог vcpkg зріс від кількох десятків до кількох тисяч портів, модель єдиного комміту створила три критичні проблеми:

1. **Відсутність ізоляції між проєктами:** якщо Проєкт A потребував бібліотеки `fmt` версії 7.x, а Проєкт B на тій самій машині вимагав нововведень `fmt` 8.x, класичний режим vcpkg не дозволяв встановити дві версії одночасно в спільне дерево `installed/`. Оновлення порту ламало попередні проєкти.
2. **Неможливість зафіксувати версії в системі контролю коду:** вихідний код проєкту не містив жодних метаданих про те, які саме бібліотеки та яких версій йому потрібні. Інструкція зі збірки зводилася до текстового опису: «встановіть vcpkg станом на травень 2019 року та виконайте команду install».
3. **Руйнування відтворюваності в CI/CD:** якщо агент безперервної інтеграції виконував `git pull` у каталозі vcpkg перед запуском збірки, транзитивне оновлення будь-якої другорядної залежності могло несподівано зламати нічну збірку продакшн-коду через несумісні зміни в API.

Стало очевидно, що імперативний менеджер пакетів системного рівня непридатний для промислового життєвого циклу розробки програмного забезпечення.

## Перехід до маніфестів, реєстрів та бінарного кешу

У 2020–2021 роках команда Microsoft здійснила фундаментальну перебудову архітектури vcpkg, перетворивши його на повноцінний декларативний менеджер залежностей корпоративного рівня.

Основними етапами цієї трансформації стали:

1. **Маніфестний режим (Manifest Mode):** з'явився файл `vcpkg.json`, який розміщується безпосередньо в корені репозиторію проєкту поряд із `CMakeLists.txt`. Залежності стали декларативною частиною сирцевого коду, а їхнє відновлення та збірка автоматично відбуваються в ізольований каталог `vcpkg_installed/` всередині теки конфігурації CMake.
2. **Декларативне версіонування та схема Minimal Version Selection (MVS):** замість ненадійного підходу з пошуком найсвіжіших версій vcpkg впровадив детерміновану модель фіксації версій через `builtin-baseline` (конкретний Git-хеш каталогу портів), обмеження `version>=` та механізм точкового перекриття `overrides`.
3. **Кастомні та приватні реєстри (Custom Registries):** підтримка файлу `vcpkg-configuration.json` дозволила підприємствам підключати власні закриті Git-репозиторії з портами, ізолюючи внутрішні пропрієтарні бібліотеки від публічного каталогу.
4. **Бінарне кешування (Binary Caching):** щоб усунути головний недолік збірки з вихідного коду — тривалий час компіляції важких бібліотек у CI/CD, — vcpkg отримав систему криптографічного обчислення ABI-хешів та бекенди для збереження зібраних двійкових артефактів у локальних каталогах, сховищах NuGet, хмарах Azure Blob Storage, AWS S3 та кеші GitHub Actions.
5. **Кросплатформні оверлей-тріплети (Overlay Triplets):** архітектура тріплетів була розширена з орієнтації на Windows та MSVC до повної підтримки Linux (GCC, Clang), macOS (Apple Clang), Android NDK, iOS та WebAssembly/Emscripten, дозволяючи тонко налаштовувати крос-компіляційні тулчейни через `VCPKG_CHAINLOAD_TOOLCHAIN_FILE`.

У результаті цієї еволюції vcpkg трансформувався з локальної утиліти для розробників Visual Studio у кросплатформний інструмент керування залежностями, що поєднує гнучкість збірки з сирців із продуктивністю бінарних репозиторіїв.
