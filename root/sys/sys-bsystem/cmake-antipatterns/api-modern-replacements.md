# 📋 Таблиця заміни антипатернів: застарілі директиви проти цільових властивостей

Ця довідка містить структурований аналіз команд, глобальних змінних та конструкцій CMake 2.8 style у прямому зіставленні з цільовими властивостями, командами та інженерними механізмами Modern CMake (CMake 3.0+). Для кожного елемента наведено внутрішній механізм роботи в рушії CMake, пов'язані системні властивості цілей і каталогів, а також вплив на граф залежностей та інкрементальну збірку.

## 1. Заголовкові шляхи: каталожні директиви проти цільових вимог

У застарілому CMake шляхи пошуку заголовних файлів налаштовувалися як властивість каталогу:

```cmake
# Застарілий підхід (каталожний рівень)
include_directories(/path/to/headers)
```

Команда `include_directories()` записує значення у властивість поточного каталогу `INCLUDE_DIRECTORIES`. Під час виклику `add_subdirectory()` ця властивість копіюється в дочірній каталог. Будь-яка ціль, створена в цьому каталозі або його нащадках, отримує прапорці `-I/path/to/headers` (або `/I` для MSVC) у командний рядок компіляції. При цьому неможливо відокремити внутрішні заголовки від тих, що потрібні споживачам.

Сучасний підхід інкапсулює шляхи всередині цілі:

```cmake
# Цільовий підхід (Modern CMake)
target_include_directories(tgt [SYSTEM] [PRIVATE|PUBLIC|INTERFACE] dir...)
```

Команда записує шляхи у дві різні внутрішні структури даних цілі:
- Специфікатор `PRIVATE` додає шляхи до властивості `INCLUDE_DIRECTORIES` самої цілі.
- Специфікатор `INTERFACE` додає шляхи до властивості `INTERFACE_INCLUDE_DIRECTORIES`.
- Специфікатор `PUBLIC` записує шляхи одночасно в обидва списки.

Додатковий прапорець `SYSTEM` наказує компілятору трактувати каталог як системний (наприклад, прапорцем `-isystem` у GCC/Clang або `/external:I` в MSVC), що автоматично пригнічує попередження компілятора у сторонніх файлах.

Для цілей, що експортуються для зовнішнього вжитку, використовують генераторні вирази розмежування середовища збірки та інсталяції:
- `$<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>` — активується, коли проєкт збирається всередині власного дерева джерел;
- `$<INSTALL_INTERFACE:include>` — активується після виконання команди `cmake --install` для споживачів зібраного пакета.

## 2. Бібліотеки, каталоги лінкування та граф залежностей

У парадигмі Make-файлів лінкування зводилося до додавання шляхів пошуку бінарних бібліотек та імен самих файлів:

```cmake
# Застарілий підхід: маніпулювання пошуком лінкера
link_directories(/opt/local/lib)
link_libraries(crypto ssl)
```

Команда `link_directories()` додає прапорець `-L/opt/local/lib` усім цілям поточного каталогу. Це вкрай небезпечно, оскільки системний лінкер шукає будь-яку збіжну назву бібліотеки за цим шляхом раніше, ніж у стандартних системних каталогах. Якщо у вказаній папці лежить застаріла версія системної бібліотеки з тим самим ім'ям, проєкт слінкується з нею, що спричинить невиправні збої виконання (ABI mismatch).

Команда `link_libraries()` сліпо додає прапорці `-lcrypto -lssl` кожному виконуваному файлу, навіть тим, які не мають жодного стосунку до криптографії (наприклад, утилітам тестування або генераторам коду).

Сучасна модель базується на явному орієнтованому графі залежностей (DAG):

```cmake
# Цільовий підхід (Modern CMake)
target_link_libraries(consumer_tgt [PRIVATE|PUBLIC|INTERFACE] dependency_tgt...)
```

Команда формує ребра графу зв'язків:
- Якщо залежність `dependency_tgt` є створеною ціллю або імпортованою ціллю (`IMPORTED`), CMake зчитує точний абсолютний шлях до файлу бібліотеки з її властивості `IMPORTED_LOCATION`. Жодні прапорці `-L` не генеруються.
- Через механізм транзитивності споживач `consumer_tgt` автоматично отримує всі властивості `INTERFACE_*` залежності: каталоги заголовків, макроси препроцесора, стандарт мови та прапорці компіляції.
- Приватні залежності (`PRIVATE`) не протікають на наступні рівні споживачів, що мінімізує зв'язність модулів та прискорює лінкування.

## 3. Прапорці компіляції, макроси препроцесора та стандарти мови

Раніше будь-яка зміна конфігурації компілятора відбувалася через конкатенацію рядкових змінних:

```cmake
# Застарілий підхід: глобальні рядки та макроси
add_definitions(-DDEBUG_MODE=1 -D_GNU_SOURCE)
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -std=c++17 -Wall -Wextra")
```

Директива `add_definitions()` спочатку створювалася виключно для прапорців `-D`, але через відсутність перевірок розробники часто передавали туди довільні прапорці компілятора (`-Wall`, `-O2`). Це призводило до засмічення командних рядків, неможливості скасування прапорця для окремого файлу чи цілі та фатальних помилок при перенесенні проєкту на компілятори іншого сімейства.

Сучасний підхід розділяє препроцесор, стандарт мови та компіляційні прапорці на три незалежні механізми:

### Препроцесорні дефініції
```cmake
target_compile_definitions(tgt [PRIVATE|PUBLIC|INTERFACE] DEF_NAME=value...)
```
Записує дефініції без префікса `-D` у властивості `COMPILE_DEFINITIONS` та `INTERFACE_COMPILE_DEFINITIONS`. Компіляторний префікс додається генератором автоматично відповідно до використовуваного компілятора.

### Стандарти мови C/C++
```cmake
target_compile_features(tgt [PRIVATE|PUBLIC|INTERFACE] cxx_std_17)
set_target_properties(tgt PROPERTIES
    CXX_STANDARD 17
    CXX_STANDARD_REQUIRED ON
    CXX_EXTENSIONS OFF
)
```
CMake самостійно транслює вимогу стандарту `cxx_std_17` у правильний прапорець для конкретного компілятора: `-std=c++17` для GCC/Clang або `/std:c++17` для MSVC. Властивість `CXX_EXTENSIONS OFF` вимикає нестандартні діалекти виробників (наприклад, `gnu++17`).

### Специфічні прапорці оптимізації та попереджень
```cmake
target_compile_options(tgt [PRIVATE|PUBLIC|INTERFACE]
    $<$<CXX_COMPILER_ID:GNU,Clang,AppleClang>:-Wall -Wextra -Wpedantic>
    $<$<CXX_COMPILER_ID:MSVC>:/W4 /permissive->
)
```
Прапорці призначаються виключно через генераторні вирази, що усуває конфлікти при зміні компілятора або платформи.

## 4. Збір вихідних файлів та набори файлів (File Sets)

Замість нестабільного динамічного сканування каталогів:

```cmake
# Застарілий підхід: динамічний glob
file(GLOB SOURCES "src/*.cpp")
add_library(mylib ${SOURCES})
```

Modern CMake спирається на явний опис складу модуля через `add_library()` / `add_executable()` або цільову команду `target_sources()`:

```cmake
# Цільовий підхід: явні вихідні файли
add_library(mylib STATIC)
target_sources(mylib
    PRIVATE
        src/core.cpp
        src/detail/impl.cpp
)
```

Починаючи з версії CMake 3.23, з'явився канонічний механізм **наборів файлів** (`FILE_SET`):

```cmake
# Сучасний механізм наборів файлів (CMake 3.23+)
target_sources(mylib
    PUBLIC
        FILE_SET HEADERS
        BASE_DIRS include
        FILES
            include/mylib/core.h
            include/mylib/version.h
)
```

Механізм `FILE_SET HEADERS` автоматично розв'язує три завдання:
1. Додає каталог `include` до `INTERFACE_INCLUDE_DIRECTORIES` цілі;
2. Повідомляє IDE (Visual Studio, CLion, Xcode) про необхідність відображення заголовків у дереві проєкту;
3. Автоматично встановлює заголовки зі збереженням ієрархії під час виклику `install(TARGETS mylib FILE_SET HEADERS)`.

## 5. Змінні кешу та підпрограми: ізоляція областей

### Змінні кешу
- **Застарілий антипатерн:** `set(VAR_NAME "value" CACHE TYPE "doc" FORCE)` — безумовно затирає значення користувача під час кожного запуску конфігурації.
- **Сучасний еквівалент:** `option(VAR_NAME "doc" DEFAULT_VALUE)` або `set(VAR_NAME "value" CACHE TYPE "doc")` без `FORCE`. Змінна ініціалізується дефолтним значенням лише у випадку, якщо вона відсутня у кеші `CMakeCache.txt`.

### Підпрограми: функції проти макросів
- **Застарілий антипатерн:** `macro(my_routine arg)` — виконує текстову заміну аргументів без створення ізольованого контексту. Будь-які зміни змінних усередині макросу мутують змінні батьківського файлу, спричиняючи неявні побічні ефекти.
- **Сучасний еквівалент:** `function(my_routine arg)` створює новий стек викликів. Змінні залишаються локальними, а повернення результатів виконується через явний виклик `set(RESULT_VAR "val" PARENT_SCOPE)`. Для обробки складних іменованих параметрів використовується модуль `cmake_parse_arguments`.

## 6. Зведена таблиця відповідності директив і властивостей

| Застаріла директива (CMake 2.8) | Цільовий еквівалент (Modern CMake) | Властивість цілі (Target Property) | Властивість каталогу (Directory Property) |
| :--- | :--- | :--- | :--- |
| `include_directories(dir)` | `target_include_directories(tgt ...)` | `INCLUDE_DIRECTORIES`, `INTERFACE_INCLUDE_DIRECTORIES` | `INCLUDE_DIRECTORIES` |
| `link_libraries(lib)` | `target_link_libraries(tgt ...)` | `LINK_LIBRARIES`, `INTERFACE_LINK_LIBRARIES` | `LINK_LIBRARIES` |
| `link_directories(dir)` | Імпортовані цілі `find_package()` | `IMPORTED_LOCATION` | `LINK_DIRECTORIES` |
| `add_definitions(-DFOO)` | `target_compile_definitions(tgt ...)` | `COMPILE_DEFINITIONS`, `INTERFACE_COMPILE_DEFINITIONS` | `COMPILE_DEFINITIONS` |
| `set(CMAKE_CXX_FLAGS "...")` | `target_compile_features()`, `target_compile_options()` | `CXX_STANDARD`, `COMPILE_OPTIONS` | `COMPILE_OPTIONS` |
| `file(GLOB SRC "...")` | Явний список у `target_sources()` | `SOURCES`, `INTERFACE_SOURCES` | Не застосовується |
| `set(V v CACHE ... FORCE)` | `option(V ...)` або `set(V v CACHE ...)` | Запис у кеш | Не застосовується |
| `macro(...)` | `function(...)` із `PARENT_SCOPE` | Локальний стек викликів | Не застосовується |

## 7. Політики сумісності CMake (Policies), пов'язані з антипатернами

Політики гарантують плавну еволюцію рушія без порушення працездатності старого коду:

- **`CMP0021` (CMake 3.0):** Відносні шляхи в `INCLUDE_DIRECTORIES` цілі заборонені. У режимі `NEW` усі відносні шляхи викликають помилку, змушуючи розробника явно використовувати `${CMAKE_CURRENT_SOURCE_DIR}` або генераторні вирази.
- **`CMP0022` (CMake 3.0):** Інтерфейсні бібліотеки лінкування визначаються суворо властивістю `INTERFACE_LINK_LIBRARIES`, а не застарілою `LINK_INTERFACE_LIBRARIES`.
- **`CMP0023` (CMake 3.0):** Забороняє змішувати сигнатури `target_link_libraries()` без специфікаторів доступу та зі специфікаторами `PUBLIC`/`PRIVATE`/`INTERFACE` для однієї і тієї ж цілі.
- **`CMP0077` (CMake 3.13):** Команда `option()` не перезаписує наявну звичайну змінну з тим самим ім'ям. Це дозволяє батьківським проєктам надійно керувати параметрами залежностей без примусового переписування кешу.
- **`CMP0079` (CMake 3.13):** Дозволяє цілі викликати `target_link_libraries()` на іншій цілі, створеній в іншому каталозі (за межами поточного `add_subdirectory`).
- **`CMP0082` (CMake 3.14):** Правила інсталяції `install()` виконуються суворо у порядку їхнього оголошення в дереві проєктів, а не групуються штучно за каталогами.
- **`CMP0115` (CMake 3.20):** Вимагає явної вказівки розширень файлів вихідного коду (наприклад, `.cpp`), блокуючи повільний автоматичний перебір розширень на диску.
