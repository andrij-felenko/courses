# 📜 Від генератора Makefile до цільової моделі: народження Modern CMake

У 1999 році консорціум NLM (National Library of Medicine) у США фінансував розробку масштабної бібліотеки комп'ютерного зору та аналізу медичних зображень ITK (Insight Segmentation and Registration Toolkit). Проєкт мав збиратися на десятках комерційних Unix-систем (Solaris, IRIX, AIX, HP-UX), на Linux та у середовищі Microsoft Windows з Visual C++. Наявні на той момент інструменти збірки з тріском провалювали це завдання: Autotools вимагали емуляції POSIX-середовища на кшталт Cygwin під Windows і не вміли генерувати нативні проєкти для Visual Studio, а ручне підтримування окремих Makefile та `.dsp`/`.dsw` файлів для кожної платформи призводило до постійного розсинхрону.

Інженери компанії Kitware — Кен Мартін (Ken Martin), Білл Гоффман (Bill Hoffman) та їхні колеги — створили CMake як мета-систему збірки: легковаговий інструмент, який читає єдиний опис проєкту (`CMakeLists.txt`) і транслює його у нативні файли конкретної системи збірки (Makefiles для Unix, проєкти MSVC для Windows).

## Спадщина Make: каталог як одиниця мислення

Перші тринадцять років свого існування (епоха версій 1.x та 2.x) CMake розвивався під прямим впливом архітектури Make. У класичному Makefile усі змінні компіляції мають пласку, глобальну структуру для поточного каталогу: прапорці `-I`, `-D`, `-L` та `-l` додаються до спільних змінних `CFLAGS` чи `LDFLAGS`.

Команди CMake 2.x були прямою калькою з цих прапорців:
- `include_directories()` буквально означала «додай шлях до прапорця `-I` для всіх наступних цілей цього каталогу»;
- `add_definitions()` додавала `-D` макроси до командного рядка компілятора;
- `link_libraries()` додавала бібліотеки `-l` до команд лінкування всіх виконуваних файлів нижче за текстом.

Така модель чудово працювала для невеликих монолітних програм початку 2000-х років, де один розробник писав усе дерево сирців. Проте зі зростанням складності C++ проєктів каталожна модель стала джерелом системних збоїв. 

Коли у 2006 році великий проєкт KDE вирішив перейти з Autotools на CMake, кодова база налічувала сотні модулів. Головною проблемою виявився витік областей видимості: якщо один підкаталог викликав `include_directories(/usr/include/glib-2.0)`, цей шлях неминуче протікав у всі дочірні папки, викликаючи непередбачувані колізії заголовків. Водночас інформація про залежності не поширювалася «вгору» чи «вбік»: якщо бібліотека `A` вимагала лінкування з `B`, будь-яка виконувана програма `C`, яка використовувала `A`, мусила вручну повторити всі шляхи та прапорці для `B`.

## Таргетна революція: CMake 3.0 та рух «Modern CMake»

До 2012 року стало очевидно, що модель каталогів і глобальних змінних вичерпала себе. C++ перейшов у фазу швидкої еволюції (C++11, C++14), модульності та широкого вжитку сторонніх бібліотек із власними вимогами до компіляції.

Справжню революцію в архітектурі CMake здійснив Стефан Келлі (Stephen Kelly) за підтримки Бреда Кінга (Brad King) та команди Kitware у серії релізів 2.8.11–2.8.12, які стали фундаментом для епохального релізу **CMake 3.0** у червні 2014 року.

Суть реформи полягала в переході від **каталогоцентричної** моделі до **цілецентричної (target-based)** моделі, запозиченої з об'єктно-орієнтованого програмування:
1. **Ціль як самодостатній об'єкт.** Бібліотека чи виконуваний файл стали об'єктами з чітким набором внутрішніх властивостей (properties).
2. **Вимоги вжитку (Usage Requirements).** З'явилися ключові слова `PRIVATE`, `INTERFACE` та `PUBLIC`. Розробник бібліотеки отримав змогу точно вказати, які заголовки потрібні лише для її власної компіляції (`PRIVATE`), а які мають бути автоматично додані кожному, хто з нею лінкується (`INTERFACE`/`PUBLIC`).
3. **Транзитивність залежностей.** Команда `target_link_libraries()` перетворилася з простого виклику лінкера на потужний механізм передачі властивостей графом залежностей. Якщо додаток `App` лінкує `LibA`, а `LibA` публічно лінкує `LibB`, `App` автоматично отримує всі потрібні шляхи заголовків, макроси та стандарт мови від `LibB` без жодного рядка ручного коду.
4. **Імпортовані та псевдонімні цілі з просторами імен.** З'явився синтаксис `Namespace::Target` (наприклад, `OpenCV::opencv_core` чи `fmt::fmt`), який унеможливив випадкові помилки друку в іменах бібліотек на етапі генерації.

Цей комплекс архітектурних рішень отримав у спільноті розробників назву **Modern CMake**.

## Чому старий стиль не здався: політики сумісності та інерція

Попри очевидну інженерну перевагу Modern CMake, застарілий стиль CMake 2.8 продовжував масово використовуватися впродовж наступного десятиліття. Причини цієї живучості лежать у поєднанні інженерних рішень Kitware та соціології розробки програмного забезпечення.

### Безкомпромісна зворотна сумісність і механізм політик
Kitware сповідувала залізний принцип: оновлення версії CMake не повинно ламати складання наявних проєктів користувачів. Щоб забезпечити це, у CMake було впроваджено систему **політик** (`cmake_policy`). Замість видалення небезпечних команд на кшталт `include_directories()` чи `link_libraries()`, розробники залишили їх робочими, прив'язавши нову поведінку до версії у `cmake_minimum_required()`. Проєкти, написані у 2005 році, продовжували безпомилково компілюватися на CMake 3.25, не стимулюючи авторів переписувати старий код.

### Інерція навчальних матеріалів та алгоритмів пошуку
У 2008–2014 роках, під час масового переходу C++ індустрії на CMake, на платформі StackOverflow та у блогах було створено сотні тисяч відповідей на типові запитання розробників: «як додати бібліотеку», «як увімкнути C++11», «як підключити папку з заголовками». Завдяки високому авторитету доменів ці відповіді назавжди закріпилися на перших позиціях пошукових систем. Новачок, що зіткнувся з проблемою компіляції у 2024 році, скопіював із першого рядка пошуку `set(CMAKE_CXX_FLAGS "-std=c++11")` та `include_directories(include)`, закріплюючи застарілий антипатерн.

### Галюцинації великих мовних моделей
Сучасні генеративні нейромережі навчалися на терабайтах публічних репозиторіїв GitHub, де застарілий код CMake 2.8 кількісно переважав чистий Modern CMake. У результаті моделі машинного навчання роками генерували для користувачів код із глобальними директивами та конкатенацією прапорців, створюючи нове коло відтворення застарілих практик.

Розуміння цієї історичної траєкторії дає чіткий інженерний орієнтир: застарілі конструкції CMake не є альтернативною думкою чи «спрощеним стилем» — це рудименти перехідного періоду систем збірки, від яких сучасний інженерний процес вимагає повної відмови на користь інкапсульованих цілей.
