# 📜 Від AC_CONFIG_HEADERS до #cmakedefine: історія config.h

Поява автоматично згенерованого заголовка конфігурації стала відповіддю на кризу переносимості коду в епоху так званих «війн Unix» (англ. *Unix wars*) кінця 1980-х та початку 1990-х років. Коли програму на C потрібно було зібрати на десятках різних варіантів Unix — від BSD і System V до AIX, IRIX, Solaris та HP-UX — кожна система мала власний набір системних викликів, відмінні типи аргументів у стандартних заголовках та власні реалізації функцій на кшталт `strdup()` чи `mmap()`.

## Криза гігантських командних рядків

До появи систем автоматичної конфігурації розробники передавали всі виявлені особливості цільової платформи безпосередньо через прапорці компілятора в `Makefile`:

```sh
# Типовий виклик компілятора на початку 1990-х
cc -DHAVE_UNISTD_H -DHAVE_SYS_TIME_H -DHAVE_STRDUP -DHAVE_MMAP -DSIZEOF_INT=4 \
   -DSIZEOF_LONG=8 -DRETSIGTYPE=void -DWORDS_BIGENDIAN=1 -c main.c
```

Такий підхід швидко зайшов у глухий кут із трьох фундаментальних причин:

1. **Обмеження довжини командного рядка.** На багатьох тогочасних оболонках і ядрах довжина буфера виклику `execve()` обмежувалася кількома кілобайтами. Коли кількість прапорців наближалася до сотні, компілятор просто відмовлявся запускатися.
2. **Нестерпна складність супроводу Make-файлів.** Додавання нової платформи вимагало ручного редагування десятків рядків компіляції в кожному окремому `Makefile`.
3. **Руйнування кешу компілятора та відсутність модульності.** Будь-яка зміна єдиного макроса вимагала зміни тексту команди збірки для всіх файлів проєкту.

## Рішення GNU Autotools: autoheader та AC_CONFIG_HEADERS

У 1991 році Девід Маккензі (англ. *David MacKenzie*) розпочав розробку GNU Autoconf. Ідея полягала в тому, щоб скрипт `configure` на машині користувача автоматично виконував пробні мікрокомпіляції, з'ясовував можливості операційної системи та записував результат у єдиний конфігураційний заголовок — `config.h`.

Утиліта `autoheader` сканувала скрипт `configure.ac` (де викликалися макроси `AC_CHECK_HEADERS`, `AC_CHECK_FUNCS`) і генерувала шаблон `config.h.in`, у якому всі можливі параметри записувалися у вигляді закоментованих директив:

```text
/* config.h.in — шаблон Autotools */
#undef HAVE_UNISTD_H
#undef HAVE_MMAP
#undef VERSION
```

Під час запуску `./configure` скрипт на базі M4 та Sed читав цей шаблон і замінював `#undef` на `#define` для тих функцій, які вдалося знайти в системі. Програма на C тепер потребувала лише одного рядка `#include <config.h>`, а командний рядок компілятора залишався чистим.

## Проблеми монолітного підходу Autotools

Попри свій тріумф у світі відкритого ПЗ 1990-х років, модель `config.h` від Autotools страждала від кількох серйозних вад, які стали особливо болючими з розквітом C++:

- **Глобальне забруднення простору імен.** Autotools заохочували визначати в `config.h` загальні імена на зразок `PACKAGE_NAME`, `VERSION`, `PACKAGE_STRING` або `inline`. Коли великий проєкт C++ складався з багатьох підбібліотек і кожна підключала власний монолітний `config.h`, ці макроси неминуче конфліктували між собою та ламали код стандартних бібліотек.
- **Лавинні перекомпіляції.** У ранніх версіях Autotools будь-який повторний запуск `./configure` перезаписував `config.h` на диску, оновлюючи його мітку часу модифікації (`mtime`). Оскільки `config.h` підключався майже в кожен файл вихідного коду, утиліта `make` була змушена перекомпільовувати абсолютно весь проєкт з нуля, навіть якщо жоден прапорець не змінився.
- **Помилки непідключених заголовків.** Оскільки `autoheader` генерував `#define HAVE_FEATURE 1` або залишав `/* #undef HAVE_FEATURE */`, перевірка в коді зазвичай робилася через `#ifdef HAVE_FEATURE`. Якщо розробник у новому `.c`-файлі забував додати `#include "config.h"`, компілятор не видавав жодної помилки: він просто вважав, що функціональність вимкнена, що призводило до важковловлюваних помилок під час виконання.

## Як CMake переосмислив генерацію заголовків

Створюючи CMake на початку 2000-х років для медичного проєкту ITK (Insight Segmentation and Registration Toolkit), Білл Гофман (англ. *Bill Hoffman*) та команда Kitware поставили собі за мету замінити громіздкий ланцюжок Autotools (`autoconf` + `automake` + `autoheader` + `libtool`) єдиною платформонезалежною системою.

CMake запропонував команду `configure_file`, яка принципово змінила правила гри:

1. **Директива `#cmakedefine` замість неявного Sed.** Замість магічного сканування рядків `#undef`, CMake запровадив явний синтаксис `#cmakedefine VAR`, який чітко декларує намір розробника в шаблоні.
2. **Директива `#cmakedefine01` для надійного коду.** Для усунення помилок `#ifdef` CMake додав директиву `#cmakedefine01 VAR`, яка завжди генерує `#define VAR 1` або `#define VAR 0`. Це дозволило коду C/C++ безпечно використовувати арифметичну перевірку `#if VAR`, яка у поєднанні з прапорцем компілятора `-Wundef` миттєво ловить відсутність підключеного заголовка.
3. **Вбудоване відсікання за часом (Early Cutoff).** CMake із самого початку реалізував побайтове порівняння згенерованого вмісту з наявним файлом на диску. Якщо вміст ідентичний, `mtime` не змінюється, що зберегло мільйони годин розробникам під час інкрементальної збірки.
4. **Модульні заголовки цілей замість одного глобального файлу.** Сучасний CMake зробив крок від єдиного `config.h` у корені проєкту до ізольованих заголовків конфігурації для кожної конкретної бібліотеки (наприклад, `<my_module/config.h>`), захищених вимогами вжитку цілей (`target_include_directories`).
