# 📋 Повний синтаксис та поведінка configure_file

Команда `configure_file` виконує синтаксичний розбір і шаблонізацію вхідного текстового файлу на етапі конфігурації проєкту (англ. *configure time*). Вона трансформує змінні системи збірки CMake, кеш-параметри та перемикачі функцій у вихідний код мов C і C++, скрипти командної оболонки чи файли налаштування сервісів, зберігаючи результат у каталозі збірки.

## Формальна сигнатура команди

```cmake
configure_file(<input> <output>
               [@ONLY]
               [ESCAPE_QUOTES]
               [COPYONLY]
               [NO_SOURCE_PERMISSIONS | FILE_PERMISSIONS <permissions>...]
               [NEWLINE_STYLE [UNIX|DOS|WIN32|LF|CRLF]])
```

## Параметри та прапорці керування

### Шляхи введення та виведення

- `<input>`: Шлях до вхідного файлу-шаблона. Якщо вказано відносний шлях, CMake обчислює його відносно поточного каталогу вихідних текстів (`CMAKE_CURRENT_SOURCE_DIR`). Вхідний файл обов'язково повинен існувати на момент виконання команди; спроба вказати неіснуючий файл спричиняє фатальну помилку конфігурації. Шаблон розглядається виключно як текстовий файл у кодуванні UTF-8 або ASCII.
- `<output>`: Шлях до результуючого згенерованого файлу або цільового каталогу. Якщо вказано відносний шлях, він обчислюється відносно поточного каталогу збірки (`CMAKE_CURRENT_BINARY_DIR`). Якщо шлях вказує на наявний каталог, CMake автоматично створює всередині нього файл із таким самим базовим іменем, як у `<input>`. Будь-які відсутні проміжні каталоги у шляху виведення CMake створює автоматично перед записом.

### Режими підстановки та захисту

- `@ONLY`: Обмежує синтаксичний аналізатор CMake заміною виключно конструкцій вигляду `@VAR@`. Усі входження синтаксису `${VAR}` ігноруються й залишаються у згенерованому файлі без змін. Використання цього прапорця є обов'язковим стандартом безпеки для будь-яких файлів C, C++, Rust, Python та shell-скриптів, де послідовність `${...}` має власне семантичне значення в цільовій мові.
- `ESCAPE_QUOTES`: Інструктує CMake екранувати будь-які символи подвійних лапок `"` у підставлених значеннях змінних зворотним слешем (`\"`). Це запобігає синтаксичному розриву рядкових літералів C/C++, якщо змінна CMake містить внутрішні лапки (наприклад, рядок опису або складний прапорець).
- `COPYONLY`: Здійснює пряме побайтове копіювання файлу з `<input>` у `<output>` без виконання будь-якої шаблонізації, сканування директив чи заміни змінних. Цей прапорець є взаємовиключним із `@ONLY`, `ESCAPE_QUOTES` та `NEWLINE_STYLE`. У сучасному CMake (починаючи з версії 3.21) для копіювання файлів без шаблонізації рекомендовано використовувати спеціалізовану команду `file(COPY_FILE)`.

### Керування правами доступу (POSIX Permissions)

- За замовчуванням згенерований файл успадковує біти прав доступу від файлу-шаблона `<input>`, скориговані поточною маскою створення файлів процесу (`umask`).
- `NO_SOURCE_PERMISSIONS`: Вимикає автоматичне копіювання прав доступу з вхідного файлу. Результуючий файл отримує стандартні права для новостворених файлів у системі (зазвичай `0644`).
- `FILE_PERMISSIONS <permissions>...`: Дозволяє явно задати точний набір прав доступу для вихідного файлу. Можливі значення: `OWNER_READ`, `OWNER_WRITE`, `OWNER_EXECUTE`, `GROUP_READ`, `GROUP_WRITE`, `GROUP_EXECUTE`, `WORLD_READ`, `WORLD_WRITE`, `WORLD_EXECUTE`, `SETUID`, `SETGID`. Це дозволяє створювати готові до запуску виконувані скрипти без необхідності окремого виклику утиліти `chmod`.

### Форматування перенесень рядків

- `NEWLINE_STYLE <стиль>`: Примусово встановлює символи кінця рядка для вихідного текстового файлу, незалежно від формату вхідного файлу та операційної системи хоста.
  - `LF` або `UNIX`: Усі перенесення рядків конвертуються в одиничний байт `0x0A` (`\n`).
  - `CRLF`, `DOS` або `WIN32`: Усі перенесення конвертуються у двобайтову послідовність `0x0D 0x0A` (`\r\n`).
  - Використання цієї опції запобігає паразитним дифам у системах контролю версій Git під час кросплатформової збірки між Windows та Linux.

## Логіка перетворення директив препроцесора

CMake сканує вхідний файл порядково. Якщо рядок починається з ключових директив конфігурації, він замінюється згідно з правилами обчислення логічної істинності змінних у CMake.

### Таблиця істинності значень у CMake

Змінна вважається **істинною (truthy)**, якщо вона визначена і її значення дорівнює:
- `1`, `ON`, `YES`, `TRUE`, `Y`;
- Будь-якому ненульовому цілому чи дійсному числу;
- Будь-якому непустому рядку, який не входить до списку хибних значень.

Змінна вважається **хибною (falsy)**, якщо:
- Вона не була оголошена або видалена через `unset()`;
- Її значення є порожнім рядком `""`;
- Її значення дорівнює `0`, `OFF`, `NO`, `FALSE`, `N`, `IGNORE`, `NOTFOUND`;
- Її значення закінчується суфіксом `-NOTFOUND` (стандартний маркер невдалого пошуку пакетів і бібліотек).

### 1. Правила трансформації директиви #cmakedefine

Директива призначена для сумісності з традиційними перевірками препроцесора C/C++ на базі `#ifdef` та `#if defined()`.

| Початковий рядок у шаблоні | Стан змінної у CMake | Згенерований результат у коді |
| :--- | :--- | :--- |
| `#cmakedefine FEATURE_ENABLED` | `FEATURE_ENABLED = ON` | `#define FEATURE_ENABLED` |
| `#cmakedefine FEATURE_ENABLED` | `FEATURE_ENABLED = OFF` | `/* #undef FEATURE_ENABLED */` |
| `#cmakedefine FEATURE_ENABLED` | Змінна не визначена | `/* #undef FEATURE_ENABLED */` |
| `#cmakedefine BUFFER_LEN @BUFFER_LEN@` | `BUFFER_LEN = 8192` | `#define BUFFER_LEN 8192` |
| `#cmakedefine BUFFER_LEN @BUFFER_LEN@` | `BUFFER_LEN = ""` або `0` | `/* #undef BUFFER_LEN */` |
| `#cmakedefine DB_DRIVER "pgsql"` | `DB_DRIVER = "pgsql"` | `#define DB_DRIVER "pgsql"` |
| `#cmakedefine DB_DRIVER "pgsql"` | `DB_DRIVER = OFF` | `/* #undef DB_DRIVER */` |

> ⚠️ **Особливість обробки аргументів:** Якщо після імені змінної у директиві `#cmakedefine VAR ...` вказано додатковий текст (наприклад, константне значення чи маркер `@VAR@`), цей текст зберігається у вихідному рядку `#define VAR ...` лише тоді, коли змінна `VAR` є істинною. Якщо `VAR` є хибною, увесь рядок цілком замінюється на `/* #undef VAR */`.

### 2. Правила трансформації директиви #cmakedefine01

Директива `#cmakedefine01` створена для усунення помилок компіляції та забезпечення безпечних числових перевірок препроцесора через `#if` та мовних конструкцій C++ `if constexpr`.

| Початковий рядок у шаблоні | Стан змінної у CMake | Згенерований результат у коді |
| :--- | :--- | :--- |
| `#cmakedefine01 ENABLE_SSL` | `ENABLE_SSL = ON` | `#define ENABLE_SSL 1` |
| `#cmakedefine01 ENABLE_SSL` | `ENABLE_SSL = TRUE` | `#define ENABLE_SSL 1` |
| `#cmakedefine01 ENABLE_SSL` | `ENABLE_SSL = OFF` | `#define ENABLE_SSL 0` |
| `#cmakedefine01 ENABLE_SSL` | `ENABLE_SSL = 0` | `#define ENABLE_SSL 0` |
| `#cmakedefine01 ENABLE_SSL` | `ENABLE_SSL` не існує | `#define ENABLE_SSL 0` |

> ⚠️ На відміну від `#cmakedefine`, директива `#cmakedefine01` **ніколи не генерує коментар `/* #undef */`**. Вона завжди оголошує макрос, гарантуючи наявність явного числового значення `1` або `0`.

## Правила пошуку та розкриття змінних

1. **Область видимості (Scope):** Пошук значень змінних відбувається за стандартними правилами мови CMake:
   - Спочатку перевіряються локальні змінні поточної функції або поточного файлу `CMakeLists.txt`.
   - Далі перевіряються змінні батьківської області видимості (якщо виклик відбувається всередині вкладеного каталогу чи функції).
   - Якщо локальної змінної не знайдено, перевіряється значення у глобальному кеші CMake (`CMakeCache.txt`).
   - Якщо змінна відсутня у всіх областях, її підстановка дає порожній рядок (без генерації попередження чи помилки).
2. **Змінні середовища:** Синтаксис `@$ENV{VAR}@` або `@ENV{VAR}@` не підтримується синтаксичним аналізатором `configure_file`. Щоб підставити значення змінної середовища, її необхідно попередньо скопіювати у звичайну змінну CMake перед викликом генератора:
   ```cmake
   set(BUILD_USER "$ENV{USER}")
   configure_file(user_info.h.in user_info.h @ONLY)
   ```
3. **Обробка списків CMake:** Оскільки списки в CMake зберігаються як рядки з роздільником «крапка з комою» (наприклад, `val1;val2;val3`), підстановка змінної списку підставить рядок разом із крапками з комою. Якщо потрібен інший роздільник (наприклад, пробіли або коми для коду C/C++), список слід попередньо трансформувати через `string(JOIN " " ...)` або `list(JOIN ...)`.

## Порівняння механізмів генерації файлів у CMake

| Характеристика | `configure_file()` | `file(GENERATE)` | `add_custom_command()` |
| :--- | :--- | :--- | :--- |
| **Етап життєвого циклу** | Фаза конфігурації (*Configure Time*) | Фаза генерації (*Generate Time*) | Фаза збірки (*Build Time*) |
| **Генераторні вирази (`$<...>`)** | ❌ Не розкриваються | ✔️ Повна підтримка | ✔️ Повна підтримка в аргументах |
| **Підтримка `#cmakedefine`** | ✔️ Так | ❌ Ні | ❌ Ні (вимагає зовнішніх утиліт) |
| **Мультиконфігураційні білди** | Один файл для всіх конфігурацій | Окремий файл для кожного `$<CONFIG>` | Залежить від команди білд-графа |
| **Збереження мітки часу (`mtime`)** | ✔️ Автоматично (раннє відсікання) | ✔️ Автоматично | ❌ Потребує ручного контролю |
| **Основне призначення** | Заголовки конфігурації C/C++, скрипти, метадані версій | Файли відповідей компілятора, налаштування тестів під конфігурацію | Компіляція protobuf, генерація коду зовнішніми скриптами Python |
