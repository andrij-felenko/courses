# 📜 Від скриптового хаосу та пропрієтарних IDE-конфігів до єдиного стандарту

Два десятиліття з моменту появи CMake у 2000 році розробники на C та C++ жили в парадоксальній ситуації: сама збірка була кросплатформною, але запуск конфігуратора залишався глибоко прив'язаним до конкретної операційної системи й конкретного редактора коду. Щоб передати проєкту необхідний набір параметрів — шлях до компілятора, набір прапорців оптимізації, генератор, конфігурацію кешу та шлях до тулчейна сторонніх бібліотек, — команда була змушена писати імперативні сценарії оболонки. На Linux та macOS це був `build.sh` або `configure`, на Windows — `build.bat` чи `build.ps1`, а в середовищі безперервної інтеграції — довгі багаторядкові інструкції у конфігураційних файлах CI.

Кожен такий сценарій дублював ті самі виклики `cmake -B ... -S ... -D...`, але робив це з власними синтаксичними особливостями конкретного командного інтерпретатора. Спроба додати нову опцію конфігурації вимагала ручного редагування кількох скриптів на різних мовах, що неминуче призводило до розсинхронізації та важковловимих помилок між робочими машинами розробників і серверами тестування.

## Ранні спроби стандартизації: GUI та користувацькі файли

Першими спробами подолати складність командного рядка були графічні утиліти `cmake-gui` та термінальний інтерфейс `ccmake`. Вони дозволяли розробникові інтерактивно переглядати та змінювати змінні кешу у файлі `CMakeCache.txt`. Проте цей підхід не розв'язував головної проблеми командної розробки — відтворюваності. Інтерактивно налаштований кеш залишався локальним артефактом у каталозі збірки. Передати точну копію цих налаштувань колезі або перенести їх на сервер автоматичної збірки було неможливо без повторення ручних дій або написання чергового скрипта.

Виробники інтегрованих середовищ розробки намагалися зберегти вибір користувача у спеціальних файлах налаштувань. Наприклад, середовище Qt Creator створювало поруч із проєктом XML-файл `CMakeLists.txt.user`. Цей файл містив повні абсолютні шляхи до компіляторів, змінні середовища та параметри запуску CMake на конкретному комп'ютері. Через наявність локальних шляхів його не можна було фіксувати у системі контролю версій Git. Як наслідок, кожен новий член команди, схилонувавши репозиторій, мав вручну налаштовувати середовище з нуля, спираючись на довгі текстові інструкції у файлі `README.md`.

## Епоха пропрієтарних конфігурацій IDE

У середині 2010-х років розвиток сучасних редакторів коду лише поглибив фрагментацію. Середовища більше не задовольнялися згенерованими файлами проєктів на зразок `.sln` чи `Makefile` — вони прагнули відкривати вихідне дерево з файлом `CMakeLists.txt` напряму та самостійно керувати фазою конфігурації. Оскільки єдиного загальноприйнятого стандарту не існувало, кожен виробник інструментів створив власну несумісну схему.

Компанія Microsoft для середовища Visual Studio 2017 розробила формат `CMakeSettings.json`. Він описував назви конфігурацій, робочі каталоги, змінні середовища та параметри генератора, але був тісно прив'язаний до внутрішніх механізмів Visual Studio і не підтримувався іншими інструментами. Для редактора VS Code розширення CMake Tools запровадило власну схему через файл `cmake-kits.json` та конфігураційний блок у `.vscode/settings.json`. Середовище CLion від компанії JetBrains зберігало налаштування профілів CMake у власних XML-файлах всередині службового каталогу `.idea`.

```
                  ┌─────────────────────────────────────────┐
                  │          Дерево сирців CMake            │
                  └────────────────────┬────────────────────┘
          ┌────────────────────────────┼────────────────────────────┐
          ▼                            ▼                            ▼
┌──────────────────┐         ┌──────────────────┐         ┌──────────────────┐
│ Visual Studio    │         │     VS Code      │         │   CLion / IDE    │
│ CMakeSettings    │         │  cmake-kits.json │         │ workspace profiles│
│      .json       │         │  settings.json   │         │     (XML)        │
└─────────┬────────┘         └─────────┬────────┘         └─────────┬────────┘
          │                            │                            │
          └────────────────────────────┼────────────────────────────┘
                                       ▼
                  ┌─────────────────────────────────────────┐
                  │    Сценарії CI (bash / PowerShell)      │
                  │   Несумісні з жодним із файлів IDE     │
                  └─────────────────────────────────────────┘
```

У результаті типовий комерційний проєкт мусив паралельно підтримувати три або чотири різні описи того, як саме його слід збирати у режимах Debug чи Release. Коли розробник запускав компіляцію через термінал, вона нерідко завершувалася невдачею, хоча всередині Visual Studio все працювало бездоганно. Причина полягала в тому, що кожне середовище передавало власний, прихований від інших набір змінних кешу.

## Спільна ініціатива Kitware та Microsoft

Переломний момент настав наприкінці 2019 року. Інженери Kitware та команди розробки інструментів C++ корпорації Microsoft розпочали відкрите обговорення нового стандарту. Стало очевидним, що опис конфігурацій збірки має належати не графічній оболонці редактора, а безпосередньо самому рушію CMake.

Під час проєктування формату розгорнулися жваві дискусії щодо ключових архітектурних рішень:

1. **Вибір формату даних (JSON проти YAML):** чимало розробників пропонували використати YAML через його лаконічність. Проте комітет віддав перевагу строгому JSON. Головними аргументами стали простота парсера, детермінованість і відсутність неоднозначностей типізації, якими відомий YAML (наприклад, автоматичне перетворення рядка `NO` на булеве значення `false` через так звану проблему Норвегії). Крім того, наявність стандарту JSON Schema дозволила реалізувати миттєву валідацію та автодоповнення у всіх редакторах без написання спеціальних плагінів.
2. **Розділення на два файли:** однією з головних вимог було запобігти потраплянню приватних налаштувань у репозиторій. Рішенням стало створення пари файлів: `CMakePresets.json` фіксує канонічні командні конфігурації та зберігається в системі контролю версій Git, тоді як `CMakeUserPresets.json` призначений для локальних правок окремого розробника і додається до списку виключень `.gitignore`.
3. **Відокремлення конфігурації від збірки:** фундаментальною проблемою екосистеми була різниця між одноконфігураційними генераторами (Ninja, Unix Makefiles), де тип збірки `CMAKE_BUILD_TYPE` обирається під час фази конфігурації, та багатоконфігураційними генераторами (Visual Studio, Xcode, Ninja Multi-Config), де один каталог містить файли для всіх типів, а вибір Debug чи Release відбувається прапорцем `--config` уже на фазі збірки. Через це розробники вирішили розділити опис на незалежні сутності: `configurePresets` та `buildPresets`.
4. **Модель успадкування:** реальні проєкти вимагали гнучкого комбінування параметрів (наприклад, базовий компілятор плюс вибір типу збірки). Було розроблено механізм `inherits`, що підтримує як одиничне, так і множинне успадкування з чіткими правилами злиття словників та заміни скалярних значень.

У листопаді 2020 року разом із випуском CMake 3.19 було офіційно представлено механізм `CMakePresets.json` із першою версією схеми (`"version": 1`).

## Еволюція версій схеми від 1 до 8

Розвиток пресетів відбувався планомірно й охопив усі фази життєвого циклу проєкту:

- **Схема 1 (CMake 3.19, осінь 2020):** базовий фундамент стандарту. Реалізовано `configurePresets` (генератор, каталог збірки `binaryDir`, змінні кешу `cacheVariables`, змінні оточення `environment`, файл тулчейна `toolchainFile`) та `buildPresets` (вибір цільових артефактів, паралелізм `jobs`, прапорці рідного інструмента `nativeToolOptions`). Запроваджено перші макроси динамічної підстановки шляхів (`${sourceDir}`, `${presetName}`).
- **Схема 2 (CMake 3.20, весна 2021):** додано `testPresets` для безшовної інтеграції з тестовим рушієм CTest. Параметри фільтрації тестів, налаштування таймаутів і повторного запуску після помилки стали декларативними. З'явилося поле `vendor` для збереження специфічних метаданих інтегрованих середовищ без порушення валідації схеми.
- **Схема 3 (CMake 3.21, літо 2021):** додано `packagePresets` для генерації дистрибутивів за допомогою утиліти CPack, а також поле `installDir` для керування каталогом встановлення готових бінарних файлів.
- **Схема 4 (CMake 3.23, весна 2022):** впроваджено директиву `include`. Великі монорепозиторії та модульні системи отримали можливість розділяти монолітні файли конфігурацій на менші логічні модулі й імпортувати спільні базові налаштування.
- **Схема 5 (CMake 3.24, літо 2022):** додано розширені можливості діагностики та профілювання: пресети навчилися керувати режимами трасування `trace` та генерувати графи залежностей у форматі Graphviz.
- **Схема 6 (CMake 3.25, осінь 2022):** запроваджено `workflowPresets`. Це дозволило об'єднувати послідовні фази (конфігурація -> збірка -> тестування -> пакування) в єдиний атомарний робочий процес, що запускається однією командою `cmake --workflow --preset <назва>`.
- **Схема 7 (CMake 3.27, літо 2023):** розширено підтримку інтерактивних режимів і додано тонкий контроль над створенням каталогів збірки.
- **Схема 8 (CMake 3.28, осінь 2023):** додано повноцінний механізм умовних виразів `condition` (перевірки рівності, входження до списку, перевірки хостової операційної системи), що дозволило створювати компактні кросплатформні пресети без дублювання записів.

## Реакція менеджерів пакетів та екосистеми

Успіх пресетів швидко підхопили провідні менеджери пакетів для C++. Менеджер `vcpkg` від Microsoft отримав режим маніфесту та почав генерувати пресети, що автоматично підставляли шлях до його тулчейна. Менеджер `Conan 2.0` зробив генерацію `CMakeUserPresets.json` штатним механізмом: після встановлення залежностей Conan автоматично створює користувацький пресет із прописаними шляхами до зібраних бібліотек, звільняючи розробника від ручного передавання `-DCMAKE_TOOLCHAIN_FILE=...` чи `-DCMAKE_PREFIX_PATH=...`.

Такі популярні середовища розробки, як Visual Studio, Visual Studio Code, CLion, Qt Creator та Neovim, реалізували повну підтримку стандарту й оголосили застарілими власні пропрієтарні механізми.

## Зміна культури розробки та онбордингу

Головним наслідком стандартизації стала докорінна зміна процесу входження нових інженерів у проєкт. Якщо раніше онбординг у великий C++-проєкт займав від кількох годин до кількох днів через необхідність вичитувати інструкції, встановлювати специфічні змінні оточення та вручну вводити довгі команди в терміналі, то сьогодні цей процес звівся до двох стандартних дій: клонування репозиторію та вибору потрібного пресета у випадному списку середовища розробки.

Для інженерів безперервної інтеграції пресети прибрали тисячі рядків тендітного імперативного коду з файлів конфігурації GitHub Actions, GitLab CI та Azure Pipelines. Конвеєр CI тепер зводиться до виклику стандартної команди `cmake --workflow --preset ci-linux-release`. Якщо на сервері стається збій, розробник може стовідсотково відтворити його локально, виконавши в терміналі точно таку саму команду пресета.
