Коли до проєкту прошивки мікроконтролера додають кілька рядків логування або новий клас обробки датчика, компілятор успішно транслює кожен окремий сирцевий файл у машинний код без жодних попереджень. Проте фінальний крок збірки раптово переривається аварійною помилкою компонувальника:

```text
arm-none-eabi/bin/ld: firmware.elf section '.text' will not fit in region 'FLASH'
arm-none-eabi/bin/ld: region 'FLASH' overflowed by 24188 bytes
collect2: error: ld returned 1 exit status
```

Компілятор бачить лише одну одиницю трансляції (*translation unit*) за раз і нічого не знає про загальний обсяг апаратної пам'яті цільового чипа. Лише компонувальник (*linker*, від англ. *link* — «з'єднувати, зв'язувати») збирає докупи всі об'єктні файли, додає до них системні статичні бібліотеки (`libc.a`, `libgcc.a`, `libstdc++.a`) і розкладає отримані секції за фізичними адресами відповідно до правил скрипта компонування (*linker script*). Коли сумарний розмір секцій перевищує апаратні межі чипа, компонувальник констатує факт переповнення, але стандартне повідомлення про помилку не відповідає на головне інженерне запитання: яка саме функція, глобальний масив чи бібліотечна залежність проковтнула десятки кілобайтів пам'яті.

Єдиним документом, який фіксує повну топологію розміщення кожного байта коду та даних, є **Map-файл** (від лат. *mappa* — «полотно, креслення, карта»). Це текстовий звіт компонувальника, що реєструє походження кожного символу, розкладку секцій за адресами, обсяг вирівнювального падінгу та граф перехресних викликів.

![Анатомія Map-файлу компонувальника GNU ld та взаємозв'язок його розділів під час аналізу](/root/sys/sys-bsystem/map-fail/img/map-file-anatomy.svg)

*Структура звіту компонування: від конфігурації апаратних регіонів до виявлення мертвого коду й розв'язання перехресних залежностей.*

## Генерація Map-файлу компонувальником GNU ld

Компонувальник не створює текстову карту розподілу пам'яті за замовчуванням, оскільки це збільшує час лінкування та створює об'ємні текстові артефакти на диску. Щоб отримати звіт під час збірки через драйвер компілятора GCC або Clang, компонувальнику передають спеціальні інструкції через префікс `-Wl,`:

```text
-Wl,-Map=build/firmware.map,--cref,--print-memory-usage
```

Кожен елемент цієї комбінації виконує чітку роль:
- `-Wl,<опції>` наказує компілятору передати перелічені через кому параметри безпосередньо утиліті `ld`.
- `-Map=build/firmware.map` вказує ім'я вихідного файлу карти розподілу пам'яті. Якщо компонування завершується помилкою переповнення регіону, компонувальник GNU ld все одно встигає повністю сформувати цей файл до моменту зупинки, що дозволяє дослідити причину аварії.
- `--cref` активує генерацію таблиці перехресних посилань (*Cross Reference Table*). Без цього прапорця файл міститиме лише список адрес і розмірів, але не покаже, який саме вихідний файл чи функція спровокували підтягування важкого бібліотечного модуля.
- `--print-memory-usage` виводить у термінал коротке зведення заповнення пам'яті у відсотках одразу після завершення компонування.

У проєктах на базі CMake або Make ці прапорці задають у секції прапорців компонування цільового виконуваного файлу:

:::tabs
```cmake
# CMakeLists.txt (C та C++)
add_executable(firmware.elf
    src/main.c
    src/sensors.c
    src/startup_stm32f401xe.s
)

target_link_options(firmware.elf PRIVATE
    -T${CMAKE_CURRENT_SOURCE_DIR}/linker/STM32F401RETx_FLASH.ld
    -Wl,-Map=${CMAKE_CURRENT_BINARY_DIR}/firmware.map
    -Wl,--cref
    -Wl,--gc-sections
    -Wl,--print-memory-usage
)
```
```makefile
# Makefile
CC      := arm-none-eabi-gcc
CXX     := arm-none-eabi-g++
LDSCRIPT := linker/STM32F401RETx_FLASH.ld

LDFLAGS := -mcpu=cortex-m4 -mthumb -mfloat-abi=hard -mfpu=fpv4-sp-d16
LDFLAGS += -T$(LDSCRIPT)
LDFLAGS += -Wl,-Map=$(BUILD_DIR)/firmware.map,--cref
LDFLAGS += -Wl,--gc-sections
LDFLAGS += -Wl,--print-memory-usage

$(BUILD_DIR)/firmware.elf: $(OBJS)
	$(CC) $(OBJS) $(LDFLAGS) -o $@
```
:::

Прапорець `--print-memory-usage` виводить у консоль зручну таблицю, яка сигналізує про вичерпання ресурсів ще до аварійного збою:

```text
Memory region         Used Size  Region Size  %age Used
           FLASH:       61240 B        64 KB     93.45%
             RAM:        7840 B        20 KB     38.28%
          CCMRAM:           0 B        64 KB      0.00%
```

> 🔧 **Навіщо це.** Прапорці `-Wl,-Map=output.map,--cref` мають бути увімкнені в конфігураціях збірки постійно, а не лише тоді, коли пам'ять закінчилася. Постійна наявність актуального `.map` файлу дозволяє відстежувати динаміку зростання прошивки від коміту до коміту та виявляти небезпечні стрибки розміру на ранніх стадіях розробки.

## Розподіл секцій між Flash та SRAM: фізична основа розрахунку

Щоб коректно інтерпретувати зміст Map-файлу, необхідно зіставити символи та секції двійкового формату ELF (*Executable and Linkable Format*) з апаратною архітектурою мікроконтролера. Пам'ять типового МК розділена на два фундаментальні типи: енергонезалежну Flash-пам'ять програм (ROM) та енергозалежну оперативну пам'ять (SRAM).

![Розподіл секцій прошивки між фізичною пам'яттю Flash та SRAM і подвійне навантаження секції .data](/root/sys/sys-bsystem/map-fail/img/memory-regions-footprint.svg)

*Секції .text та .rodata займають лише Flash; .bss споживає виключно оперативну пам'ять; .data вимагає подвійного обсягу — LMA у Flash для зберігання та VMA в SRAM для виконання.*

Кожна секція програми має чітке призначення та правила завантаження:

1. **Секція `.text` (машинний код)**:
   Містить виконувані інструкції процесора: функції прикладного коду, драйвери периферії, векторну таблицю переривань та код ініціалізації середовища (*startup code*). Ця секція розташовується у Flash і має атрибути доступу лише для читання та виконання (`rx`). Її розмір напряму залежить від складності алгоритмів, рівня агресивності інлайнінгу функцій та підключених бібліотек.

2. **Секція `.rodata` (*read-only data*)**:
   Містить константні значення, строкові літерали (наприклад, текстові повідомлення `"Sensor timeout"`), константні структури конфігурацій, таблиці синусів/швидкого перетворення Фур'є, таблиці віртуальних методів C++ (`vtable`) та дескриптори типів RTTI. Ця секція також живе виключно у Flash (`r`).

3. **Секція `.data` (ініціалізовані глобальні та статичні змінні)**:
   Містить змінні, які мають початкове значення, відмінне від нуля на момент старту програми (наприклад, `uint32_t baud_rate = 115200;`).
   Ця секція має дві різні адреси:
   - **LMA** (*Load Memory Address*) — адреса завантаження у Flash-пам'яті, де двійковий образ початкових значень зберігається під час вимкненого живлення.
   - **VMA** (*Virtual / Virtual Memory Address*) — адреса розміщення в оперативній пам'яті SRAM, де змінні фізично модифікуються процесором під час роботи.

   До виклику функції `main()` стартап-код процесора (обробник `Reset_Handler`) виконує побайтове копіювання блоку `.data` з Flash у SRAM.
   
   **Подвійна ціна `.data`:** кожен байт секції `.data` одночасно зменшує доступний простір Flash і доступний простір SRAM. Якщо розробник оголошує конфігураційну таблицю на 4096 байтів без ключового слова `const`, він миттєво втрачає 4 КБ Flash і 4 КБ дорогоцінної оперативної пам'яті.

4. **Секція `.bss` (*block started by symbol*, неініціалізовані змінні)**:
   Містить глобальні та статичні змінні, які або не мають явної ініціалізації, або ініціалізовані нулем (наприклад, `uint8_t rx_buffer[1024];`).
   У двійковому образі Flash-пам'яті секція `.bss` займає **0 байтів**: у файлі прошивки зберігається лише одне число — сумарна довжина блоку. Під час старту МК `Reset_Handler` заповнює цей діапазон адрес у SRAM нулями. Переповнення `.bss` призводить до нестачі виключно оперативної пам'яті (`region 'RAM' overflowed`).

5. **Спеціальні секції (`.noinit`, `.ccmram`, DMA)**:
   - `.noinit` — область SRAM, яку стартап-код навмисно не очищує нулями під час перезавантаження (використовується для збереження crash-логів після спрацьовування Watchdog).
   - `.ccmram` (*Core Coupled Memory*) або TCM (*Tightly Coupled Memory*) — окремі швидкісні блоки SRAM, підключені напряму до шини ядра процесора. Вони мають власний діапазон адрес і потребують окремого опису в скрипті компонування.

6. **Купа (*Heap*) та Стек (*Stack*)**:
   Оперативна пам'ять, що залишилася після розміщення `.data` та `.bss`, ділиться між стеком викликів (росте від верхньої межі SRAM вниз) і купою динамічної пам'яті (росте від кінця `.bss` вгору). Якщо сума розмірів статичних секцій занадто велика, стек зустрінеться з купою під час виконання, що спричинить непередбачуване руйнування пам'яті (*Stack Overflow* або HardFault).

## Анатомія Map-файлу: читання та дешифрування розділів

Розглянемо структуру типового Map-файлу, згенерованого GNU ld під час збірки проекту для ARM Cortex-M. Файл складається з п'яти послідовних логічних блоків.

### 1. Розділ підключених об'єктів з архівів (Archive member included)

Цей розділ стоїть на самому початку файлу і фіксує, які саме об'єктні файли зі статичних архівів (`.a`) були затягнуті в збірку, і яка функція чи змінна стала причиною цього підтягування:

```text
Archive member included to satisfy reference by file (symbol)

/toolchain/arm-none-eabi/lib/libc_nano.a(lib_a-vfprintf.o)
                              build/sensors/telemetry.o (sprintf)
/toolchain/arm-none-eabi/lib/libc_nano.a(lib_a-dtoa.o)
                              /toolchain/arm-none-eabi/lib/libc_nano.a(lib_a-vfprintf.o) (_dtoa_r)
/toolchain/arm-none-eabi/lib/libgcc.a(_udivmoddi4.o)
                              build/drivers/timer.o (__aeabi_uldivmod)
```

Лінкер працює з архівами за принципом гранулярності об'єктного файлу: якщо з усього архіву `libc_nano.a` проєкту потрібна лише одна функція `sprintf`, лінкер втягує об'єктний модуль `lib_a-vfprintf.o` **повністю**. Разом із ним підтягуються всі внутрішні функції та глобальні змінні, оголошені всередині цього модуля, а також ланцюжок їхніх залежностей (наприклад, алгоритм конвертації чисел із рухомою комою `_dtoa_r`).

### 2. Розділ конфігурації пам'яті (Memory Configuration)

Тут наведено апаратні межі регіонів, визначені в скрипті компонування директивою `MEMORY`:

```text
Memory Configuration

Name             Origin             Length             Attributes
FLASH            0x08000000         0x00010000         xr
RAM              0x20000000         0x00005000         xrw
*default*        0x00000000         0xffffffff
```

- `FLASH`: початкова адреса `0x08000000`, довжина `0x00010000` (65536 байтів = 64 КБ), атрибути `xr` (*executable, read-only*).
- `RAM`: початкова адреса `0x20000000`, довжина `0x00005000` (20480 байтів = 20 КБ), атрибути `xrw` (*read, write, execute*).

Якщо компонувальник фіксує переповнення, він порівнює поточний лічильник адреси `.` саме з цими значеннями `Length`.

### 3. Розділ відкинутих вхідних секцій (Discarded input sections)

Цей блок показує результат роботи механізму усунення мертвого коду (*Dead Code Elimination*), що активується парою прапорців `-ffunction-sections -fdata-sections` на етапі компіляції та `-Wl,--gc-sections` на етапі лінкування:

```text
Discarded input sections

 .text.unused_calibration_calc
                0x00000000       0x7c build/sensors/calib.o
 .text.legacy_uart_send_byte
                0x00000000       0x34 build/drivers/uart.o
 .rodata.old_sin_lookup_table
                0x00000000      0x400 build/dsp/filters.o
```

Якщо функцію `unused_calibration_calc` або таблицю `old_sin_lookup_table` ніхто в проекті явно не викликає і не бере її адресу, компонувальник маркує відповідні секції як недосяжні вершини графа викликів і викидає їх з фінального бінарника.

**Діагностичне правило:** якщо розділ `Discarded input sections` порожній або містить лише системні секції компілятора (`.group`, `.comment`), це свідчить про те, що прапорці `-ffunction-sections -fdata-sections` або `-Wl,--gc-sections` не були активовані. У такому разі кожна невикористана функція в кожному `.c`/`.cpp` файлі проєкту безцільно спалює пам'ять Flash.

### 4. Розділ скрипта компонування та мапи пам'яті (Linker script and memory map)

Це головний і найдетальніший розділ Map-файлу. Він описує кожен об'єднаний блок вихідного ELF-образу, крок за кроком відображаючи вхідні секції об'єктних файлів, їхні адреси, розміри та внутрішні символи:

```text
Linker script and memory map

.text           0x08000000    0x0000ec48
 *(.isr_vector)
 .isr_vector    0x08000000        0x01ac build/core/startup_stm32f401xe.o
                0x08000000                g_pfnVectors
 *(.text*)
 .text.Reset_Handler
                0x080001ac        0x004c build/core/startup_stm32f401xe.o
                0x080001ac                Reset_Handler
 .text.main     0x080001f8        0x0094 build/main.o
                0x080001f8                main
 .text.vfprintf
                0x0800028c        0x00001b40 /toolchain/lib/libc_nano.a(lib_a-vfprintf.o)
                0x0800028c                vfprintf
                0x0800028c                _vfprintf_r
 *fill*         0x08001dcc        0x00000004 
 .text._dtoa_r  0x08001dd0        0x00002140 /toolchain/lib/libc_nano.a(lib_a-dtoa.o)
                0x08001dd0                _dtoa_r
```

Як правильно читати цей лістинг:
1. **Рядок вихідної секції**: `.text 0x08000000 0x0000ec48` — секція `.text` починається за адресою `0x08000000` і має сумарний розмір `0xEC48` (60488 байтів у десятковій системі).
2. **Вхідна секція**: `.text.vfprintf 0x0800028c 0x00001b40 ...` — функція `vfprintf` розташована за адресою `0x0800028c`, займає `0x1B40` (6976 байтів) і походить із файлу `lib_a-vfprintf.o` у складі бібліотеки `libc_nano.a`.
3. **Глобальні символи**: зміщення від лівого краю без крапки (`Reset_Handler`, `main`, `_dtoa_r`) позначають експортовані символи функцій та їхні абсолютні адреси в пам'яті.
4. **Вирівнювальний падінг (`*fill*`)**: рядок `*fill* 0x08001dcc 0x00000004` показує, що лінкер вставив 4 порожні байти для вирівнювання наступної функції за адресою, кратною 4 або 8 байтам (вимога апаратної шини процесора).

### 5. Розділ таблиці перехресних посилань (Cross Reference Table)

Коли в розділі карти пам'яті виявлено важку функцію (наприклад, `_dtoa_r` на 8.5 КБ), постає питання: який саме модуль проекту спричинив її завантаження? Відповідь дає таблиця `--cref`:

```text
Cross Reference Table

Symbol                         File
_dtoa_r                        /toolchain/lib/libc_nano.a(lib_a-dtoa.o)
                               /toolchain/lib/libc_nano.a(lib_a-vfprintf.o)
vfprintf                       /toolchain/lib/libc_nano.a(lib_a-vfprintf.o)
                               /toolchain/lib/libc_nano.a(lib_a-sprintf.o)
sprintf                        /toolchain/lib/libc_nano.a(lib_a-sprintf.o)
                               build/sensors/telemetry.o
g_sensor_data                  build/sensors/telemetry.o
                               build/main.o
                               build/display/gui.o
```

*Послідовність розслідування: від фіксації переповнення через аналіз найбільших секцій та таблицю перехресних посилань до конкретного рядка коду та вибору інженерного рішення.*

Читання таблиці перехресних посилань виконується знизу вгору або за ланцюжком символів:
1. Символ `_dtoa_r` визначено в `lib_a-dtoa.o`, але на нього посилається `lib_a-vfprintf.o`.
2. Функцію `vfprintf` визначено в `lib_a-vfprintf.o`, але її викликає `lib_a-sprintf.o`.
3. Функцію `sprintf` визначено в `lib_a-sprintf.o`, а викликає її файл `build/sensors/telemetry.o`.

Висновки розслідування: достатньо відкрити файл `sensors/telemetry.c` і прибрати прямий виклик `sprintf`, щоб лінкер викинув весь ланцюжок `sprintf -> vfprintf -> _dtoa_r` і миттєво звільнив понад 15–25 кілобайтів Flash.

## Типові винуватці раптового роздування Flash та RAM

На практиці 90% випадків несподіваного переповнення пам'яті у вбудованих системах спричинені чотирма типовими інженерними пастками.

### Пастка 1: Використання стандартного printf / sprintf з підтримкою float

Стандартна бібліотека мови C Newlib (`libc.a`), що постачається разом із GCC, спочатку створювалася для систем загального призначення. Реалізація функції `printf`/`sprintf` у ній підтримує всі модифікатори стандарту C99: позиційні аргументи, локалі, багатобайтові символи, буферизоване введення-виведення через дескриптори `FILE` та перетворення чисел із рухомою комою подвійної точності (`%f`, `%e`, `%g`).

Один виклик `sprintf(buffer, "Temp: %.2f", temperature);` призводить до підтягування:
- Парсера форматної стрічки `vfprintf` (~7 КБ Flash).
- Алгоритмів перетворення рухомої коми `_dtoa_r` та `_mprec` (арифметика довільної точності для коректного округлення останнього біта дробової частини) (~8–14 КБ Flash).
- Системних структур реентерабельності `struct _reent` у секції `.data` та `.bss` (~1 КБ RAM).
- Функцій динамічного виділення пам'яті `malloc` та `free`, які `vfprintf` використовує як внутрішній резервний буфер для складних форматів.

**Лікування:**
1. **Підключення newlib-nano:**
   Передача прапорця `-specs=nano.specs` у параметри компілятора та лінкера активує оптимізовану версію бібліотеки Newlib-Nano. У ній `printf` спрощено, видалено підтримку локалей та динамічних буферів, що зменшує розмір коду приблизно на 15–20 КБ.
2. **Керування форматуванням float:**
   У `newlib-nano` підтримку чисел із рухомою комою винесено в окремий модуль, вимкнений за замовчуванням. Форматування цілих чисел працює компактно. Якщо спробувати вивести `%f`, у вихідному рядку з'явиться порожнє місце. Якщо підтримка float дійсно потрібна, лінкеру передають прапорець `-u _printf_float` (це додасть ~10 КБ Flash).
3. **Заміна на спеціалізовані форматтери:**
   Для більшості завдань телеметрії доцільно замінити важкий `sprintf` на власні функції перетворення цілих чисел або чисел із фіксованою комою (*fixed-point arithmetic*).

Нижче наведено порівняння легкого форматування телеметрії без використання `printf` та динамічної пам'яті:

:::tabs
```c
// C99: Компактне форматування числа з фіксованою комою
#include <stdint.h>
#include <stddef.h>

// Форматує число виду 12345 (значення 123.45) у рядок без використання float і printf
// Займає всього ~120 байтів Flash замість 20+ КБ
size_t format_fixed_point(char *out, size_t max_len, int32_t val, uint8_t decimals) {
    char temp[16];
    size_t idx = 0;
    int is_neg = 0;

    if (val < 0) {
        is_neg = 1;
        val = -val;
    }

    // Запис дробової та цілої частин у зворотному порядку
    uint8_t dec_count = 0;
    do {
        if (decimals > 0 && dec_count == decimals) {
            temp[idx++] = '.';
        }
        temp[idx++] = (char)('0' + (val % 10));
        val /= 10;
        dec_count++;
    } while (val > 0 || dec_count <= decimals);

    if (is_neg) {
        temp[idx++] = '-';
    }

    if (idx >= max_len) {
        return 0; // Переповнення буфера
    }

    // Реверс рядка у вихідний буфер
    for (size_t i = 0; i < idx; ++i) {
        out[i] = temp[idx - 1 - i];
    }
    out[idx] = '\0';
    return idx;
}
```
```cpp
// C++20: Типобезпечне форматування без динамічної пам'яті та RTTI
#include <cstdint>
#include <cstddef>
#include <string_view>
#include <span>
#include <charconv>

// Компактний буфер фіксованого розміру (розміщується на стеку)
template <std::size_t N>
class FixedStringBuffer {
public:
    constexpr FixedStringBuffer() = default;

    bool append(std::string_view sv) noexcept {
        if (len_ + sv.size() >= N) return false;
        for (char c : sv) data_[len_++] = c;
        data_[len_] = '\0';
        return true;
    }

    bool append_int(std::integral auto val) noexcept {
        auto [ptr, ec] = std::to_chars(data_ + len_, data_ + N - 1, val);
        if (ec != std::errc()) return false;
        len_ = static_cast<std::size_t>(ptr - data_);
        data_[len_] = '\0';
        return true;
    }

    [[nodiscard]] std::string_view view() const noexcept {
        return std::string_view(data_, len_);
    }

private:
    char data_[N]{};
    std::size_t len_{0};
};
```

### Пастка 2: C++ RTTI, обробка винятків та віртуальні таблиці

Мова C++ надає потужні засоби абстракції, проте деякі стандартні механізми мови створюють приховані накладні витрати у прошивці:

1. **Механізм обробки винятків (`throw` / `catch`)**:
   Для забезпечення розгортання стеку (*stack unwinding*) компілятор генерує спеціальні секції `.ARM.extab` (*exception index table*) та `.ARM.exidx` (*exception handling table*) для кожної скомпільованої функції. Навіть якщо в проекті немає жодного виклику `throw`, але прапорець винятків не вимкнено, стандартні бібліотеки C++ тягнуть за собою рантайм `libsupc++` та функції аварійної зупинки. Це збільшує Flash на 30–80 КБ.
   
   *Рішення:* компіляція з прапорцем `-fno-exceptions`.

2. **Інформація про типи під час виконання (RTTI)**:
   Оператори `dynamic_cast` та `typeid` потребують збереження структур `std::type_info` і повних рядкових назв усіх поліморфних класів у секції `.rodata`.
   
   *Рішення:* компіляція з прапорцем `-fno-rtti`.

3. **Віртуальні таблиці методів (`vtable`) і блокування `--gc-sections`**:
   Якщо клас містить хоча б один віртуальний метод (наприклад, віртуальний деструктор), компілятор формує для нього статичну таблицю покажчиків на функції `vtable`. Якщо в програмі створюється хоча б один екземпляр цього класу, вся таблиця `vtable` позначається як використовувана. Відповідно, компонувальник зобов'язаний зберегти **всі** віртуальні методи, на які посилається таблиця, навіть якщо жоден із них ніколи не викликається в коді. Це унеможливлює видалення мертвого коду через `--gc-sections`.

   *Рішення:* використання статичного поліморфізму (шаблони, CRTP) замість віртуальних методів, увімкнення оптимізації девіртуалізації `-fdevirtualize` та оптимізації часу лінкування LTO (*Link-Time Optimization*, `-flto`).

### Пастка 3: Забутий const та роздування секції .data

Розглянемо поширену помилку під час оголошення конфігураційних таблиць або масивів шрифтів для графічних дисплеїв:

:::tabs
```c
// C99: Без const масив потрапляє в .data (LMA у Flash + VMA у RAM)
uint8_t font_table[8192] = { 0xAA, 0x55 /* ... */ };

// Із const масив потрапляє в .rodata (живе виключно у Flash)
const uint8_t font_table_rodata[8192] = { 0xAA, 0x55 /* ... */ };
```
```cpp
// C++20: constexpr std::array гарантовано розміщується компілятором у .rodata
#include <array>
#include <cstdint>

// constexpr масив не створює копії в оперативній пам'яті SRAM
constexpr std::array<uint8_t, 8192> font_table = { 0xAA, 0x55 /* ... */ };

// constinit вимагає статичної ініціалізації без динамічного конструктора
constinit const std::array<uint8_t, 8192> font_table_constinit = { 0xAA, 0x55 /* ... */ };
```
:::

У першому випадку розробник не вказав кваліфікатор `const`. Для компілятора це означає, що програма може змінювати байти шрифту під час виконання. В результаті:
1. Образ масиву на 8192 байти записується у Flash (LMA).
2. Під час старту МК виділяє 8192 байти в оперативній пам'яті SRAM (VMA) і копіює туди таблицю.
3. Якщо мікроконтролер має лише 20 КБ RAM, цей єдиний масив з'їдає майже половину всієї оперативної пам'яті чипа.

Додавання одного слова `const` переміщує масив у секцію `.rodata`. Він залишається у Flash-пам'яті, звідки читається напряму процесором через шину інструкцій/даних (XIP, *eXecute-In-Place*), звільняючи 8 КБ SRAM.

### Пастка 4: Невидима 64-бітна арифметика та подвійна точність на Cortex-M0/M3

Мікроконтролери сімейства ARM Cortex-M0/M0+/M3 є чисто 32-бітними ядрами і не мають апаратних інструкцій для ділення 64-розрядних чисел (`uint64_t`).

Якщо в коді обчислення тайм-аутів написати:
:::tabs
```c
// C99: 64-бітне ділення підтягує важку функцію __aeabi_uldivmod з libgcc.a
uint64_t current_time_us = get_system_ticks_64();
uint64_t time_ms = current_time_us / 1000ULL; // Непомітне 64-бітне ділення (+1.5 КБ коду)

// Оптимізація: 32-бітне ділення використовує апаратну інструкцію UDIV процесора
uint32_t current_time_ms = get_system_ticks_32();
uint32_t time_sec = current_time_ms / 1000U;  // Апаратна інструкція sdiv/udiv (1 такт)
```
```cpp
// C++20: Типобезпечні інтервали часу з std::chrono без важкої емуляції
#include <cstdint>
#include <chrono>

using namespace std::chrono_literals;

// 32-бітний інтервал часу без 64-бітної емуляції
using mcu_ticks_t = std::chrono::duration<uint32_t, std::milli>;

void process_timer(mcu_ticks_t now) noexcept {
    // std::chrono::duration_cast оптимізується компілятором в одну машинну команду
    auto seconds = std::chrono::duration_cast<std::chrono::seconds>(now);
    (void)seconds;
}
```
:::

Компілятор не може виконати цю операцію однією апаратною командою і генерує виклик допоміжної функції з бібліотеки `libgcc.a`: `__aeabi_uldivmod` або `__udivmoddi4`. Ця підпрограма разом із залежностями додає до секції `.text` від 1.5 до 3 КБ коду. Якщо тайм-аут можна вирахувати в межах 32 біт (`uint32_t`), заміна типу миттєво прибирає важку бібліотечну функцію.

Аналогічна проблема виникає з операціями над числами з рухомою комою. Ядро Cortex-M4F має апаратний блок FPU лише для одинарної точності (*single precision*, `float`). Якщо в коді випадково використати константу без суфікса `f` (наприклад, `x = y * 0.5;` замість `x = y * 0.5f;`), компілятор відповідно до стандарту C підвищує тип виразу до `double` і підтягує софтверну емуляцію подвійної точності `__aeabi_dmul` з `libgcc.a`, що коштує ще 3–5 КБ Flash.

## Автоматизація аналізу: утиліти та інструменти візуалізації

Читання сирого Map-файлу розміром у десятки мегабайтів вручну — повільний процес. Для швидкого аудиту та контролю регресій у щоденній розробці застосовують консольні утиліти GNU Binutils та спеціалізовані візуалізатори.

### 1. Швидкий аналіз символів через nm та size

Утиліта `size` з набору `arm-none-eabi-size` надає миттєвий підсумок розмірів основних секцій у форматі Berkeley або System V:

```bash
# Формат Berkeley: швидкий перегляд text, data, bss
arm-none-eabi-size -B build/firmware.elf

# Вивід:
#    text    data     bss     dec     hex filename
#   61240     320    7520   69080   10dd8 build/firmware.elf
```

Щоб знайти 15 найбільших функцій або глобальних змінних без відкриття Map-файлу, використовують утиліту `nm` із сортуванням за розміром:

```bash
# Сортування символів за розміром у десятковому форматі
arm-none-eabi-nm --print-size --size-sort --radix=d build/firmware.elf | tail -n 15
```

Команда виведе список символів, де перше число — адреса, друге — точний розмір у байтах, третє — тип секції (`T`/`t` — код у `.text`, `R`/`r` — константи в `.rodata`, `D`/`d` — змінні в `.data`, `B`/`b` — неініціалізовані дані в `.bss`), четверте — ім'я символу:

```text
08003a10 00000412 T SystemInit
08001200 00000840 T main
08004100 00001420 R calibration_lookup_table
0800028c 00006976 T vfprintf
08001dd0 00008512 T _dtoa_r
```

### 2. Диференційний аналіз за допомогою Bloaty McBloatface

**Bloaty McBloatface** (`bloaty`) — інструмент профілювання бінарних файлів від Google. Його головна перевага — вміння виконувати диференційний аналіз (diff) між двома двійковими файлами ELF, показуючи, які саме функції зросли після останніх правок у коді:

```bash
# Порівняння нової збірки firmware.elf зі старою firmware_old.elf
bloaty build/firmware.elf -- build/firmware_old.elf -d compileunits,symbols
```

Вивід Bloaty чітко показує дельту за одиницями трансляції та окремими символами:

```text
     VM SIZE                         FILE SIZE
 --------------                   --------------
  +24.1Ki  +12.4%   TOTAL          +24.1Ki  +12.4%
  +15.4Ki   +100%   libc_nano.a    +15.4Ki   +100%
    +8.3Ki  [NEW]     _dtoa_r        +8.3Ki  [NEW]
    +6.8Ki  [NEW]     vfprintf       +6.8Ki  [NEW]
   +8.7Ki   +85.2%  sensors/       +8.7Ki   +85.2%
    +8.5Ki  +120%     telemetry.c    +8.5Ki  +120%
```

За кілька секунд інженер бачить, що додавання функції логування у файлі `telemetry.c` спровокувало стрибок розміру на 24.1 КБ за рахунок бібліотеки `libc_nano.a`.

### 3. Графічна візуалізація через puncover та інтеграція в CI

Для наочного представлення ієрархії пам'яті використовують утиліту **puncover**. Вона аналізує одночасно Map-файл та налагоджувальну DWARF-інформацію з ELF-файлу, формуючи інтерактивний веб-звіт із деревом модулів, аналізом статичного розміру стеку функцій та графом викликів (*Call Graph*).

У виробничих процесах ручний аналіз замінюють автоматичними перевірками в CI. Для цього Map-файл парситься автоматизованими скриптами, які блокують злиття гілок (Pull Requests), якщо прошивка перевищує встановлений бюджет Flash/RAM або в бінарнику виявлено заборонені символи (`malloc`, `free`, `_dtoa_r`, таблиці RTTI).

Повну реалізацію виробничого Python-парсера та приклад налаштування пайплайну в GitHub Actions розібрано в окремій практичній вставці: ⚙️ [Автоматизований аудит Map-файлу в CI](root:sys-bsystem/map-fail/proj-map-audit.md).

## Інженерний чеклист діагностики та оптимізації пам'яті

Зведемо діагностичні ознаки та кроки усунення переповнення пам'яті в єдиний практичний чеклист:

```

overflowed              або vtable for __cxxabiv1         -fno-exceptions -fno-rtti

overflowed              масиви у файлах драйверів         таблиць, перенести у .rodata

overflowed              __udivmoddi4 у топі коду          на 32-бітний uint32_t для ділення
```
