Коли розробник створює в каталозі файл із назвою `clean` або запускає збірку з рядком `CFLAGS = $(CFLAGS) -O2`, інструмент раптово поводиться всупереч інтуїції імперативного програмування. У першому випадку команда `make clean` заявляє, що «ціль актуальна», і відмовляється видаляти скомпільовані файли. У другому — `make` аварійно завершується з повідомленням про нескінченну рекурсію змінної. Обидві ситуації виникають з однієї причини: `Makefile` — це не командний скрипт, який виконується послідовно зверху вниз, а декларативний опис графа залежностей зі строго розмежованими фазами обчислення.

Розуміння внутрішньої механіки GNU Make дає змогу бачити, як саме текстовий файл перетворюється на обчислюваний граф, чому змінні розгортаються не так, як у мовах програмування, і як побудувати надійну систему збірки, стійку до збоїв компілятора та паралельних запусків на десятках ядер.

## Анатомія правила: що, з чого і чим

Основою будь-якого Makefile є **правило** (*rule*). Воно описує локальний зв'язок у системі: який файл має бути створений, від яких файлів залежить його актуальність і які команди операційної системи потрібно запустити для його отримання.

Синтаксис правила складається з трьох ключових елементів:

```make
targets : prerequisites
	recipe
```

```
цілі : залежності
	рецепт (команди, кожна починається з символу табуляції)
```

Розберімо кожну частину правила за її системною роллю:

1. **Ціль (*target*)** — це ім'я файлу, який генерується правилом (наприклад, `main.o` або `bin/app`), або абстрактна дія (псевдоціль, як-от `clean` чи `test`). Одне правило може містити кілька цілей через пробіл — це означає, що для кожної з них діють однакові пререквізити та рецепт.
2. **Пререквізити або залежності (*prerequisites*)** — це список імен файлів, які мають існувати та бути актуальними **до** того, як почнеться виконання рецепта цієї цілі. Якщо хоча б одного пререквізиту немає на диску, `make` рекурсивно шукає інше правило для його створення.
3. **Рецепт (*recipe*)** — один або кілька рядків команд, які передаються командній оболонці операційної системи. Кожен рядок рецепта **зобов'язаний** починатися з символу табуляції (`\t`).

Символ табуляції — історична спадщина створення утиліти в Bell Labs у 1976 році. Перший парсер використовував найпростіший шаблон лексера: перехід рядка, за яким іде символ `\t`. За кілька тижнів перші користувачі вже написали власні файли, і автор інструменту відмовився змінювати синтаксис заради зворотної сумісності. Детальніше про цей вибір і передумови виникнення утиліти розповідає [історичний нарис про народження make](root:sys-bsystem/build-system-role/hist-make-birth.md).

### Ізоляція рядків рецепта

Найпоширеніша помилка під час написання рецептів — припущення, що кілька рядків рецепта виконуються в єдиному середовищі оболонки. Розгляньмо приклад:

```make
bad_rule:
	cd src
	gcc -c main.c
```

У цій ситуації `make` запустив команду `cd src` у першому підпроцесі `sh -c "cd src"`. Цей процес змінив свій робочий каталог і завершився. Другий рядок `gcc -c main.c` запускається у **новому**, незалежному процесі оболонки, чий робочий каталог знову є кореневим каталогом проекту. В результаті компілятор не знайде `main.c` і збірка впаде.

Правильний підхід вимагає або об'єднання команд в один рядок оболонки через логічне `&&` чи крапку з комою, або використання спеціальної директиви `.ONESHELL`:

```make
# Варіант 1: об'єднання в один рядок оболонки через \
good_rule:
	cd src && gcc -c main.c

# Варіант 2: багаторядкова конструкція в одній оболонці
script_rule:
	for f in *.c; do \
		echo "Compiling $$f"; \
		gcc -c "$$f"; \
	done
```

Зверніть увагу на подвійний знак долара `$$f`: одинарний `$f` утиліта `make` спробує розгорнути як власну внутрішню змінну ще до запуску оболонки. Подвійний `$$` екранує символ і передає командній оболонці справжній `$f`.

## Префікси рядків рецепта: модифікатори виконання

Кожен окремий рядок командного блоку може мати спеціальні односимвольні префікси, які модифікують взаємодію Make з операційною системою:

```make
deploy:
	@echo "Початок розгортання артефактів..."
	-rm -rf /tmp/old_build
	+$(MAKE) -C modules/engine
```

Розберімо дію цих трьох символів:

- **Префікс `@` (придушення відлуння):** За замовчуванням Make друкує в `stdout` кожен рядок команди перед тим, як передати його оболонці. Префікс `@` вимикає цей друк для конкретного рядка. Його ставлять перед командами `echo` або утилітами створення каталогів (`@mkdir -p $(@D)`), щоб лог збірки не засмічувався службовим шумом.
- **Префікс `-` (ігнорування помилок):** Зазвичай, якщо команда повертає ненульовий код завершення (*exit code*), Make негайно перериває збірку всієї гілки графа. Префікс `-` наказує Make проігнорувати аварійний код і продовжити виконання наступних рядків рецепта. Це корисно для очищення тимчасових файлів (`-rm -f core`), відсутність яких не є фатальною помилкою.
- **Префікс `+` (примусове виконання):** Якщо Make запущено в сухому режимі `make -n` (*dry-run*), команди не виконуються, а лише друкуються. Проте підпорядковані виклики `$(MAKE)` мають виконуватися навіть у сухому режимі, щоб Make міг розібрати вкладені графі залежностей. Префікс `+` змушує запустити вказаний рядок навіть під час дії прапорця `-n`.

## Двофазна модель: чому Makefile не виконується зверху вниз

Будь-яка плутанина з умовами, змінними та викликами функцій у Make зникає, щойно стає зрозумілою **двофазна модель обчислень** (*two-phase execution*).

Коли ви викликаєте `make`, утиліта не починає компілювати код із першого рядка. Вона ділить свою роботу на два чітко розмежовані етапи.

![Двофазна модель виконання GNU Make: фаза зчитування будує граф, фаза виконання обходить його за mtime](/root/sys/sys-bsystem/make/img/read-phase-vs-execute-phase.svg)
*Двофазна модель GNU Make. У першій фазі Make повністю читає Makefile, будує граф залежностей у пам'яті й розгортає негайні змінні. Лише у другій фазі відбувається обхід графа, порівняння часових позначок mtime і запуск команд рецептів.*

### Фаза 1: Зчитування та розбір (Read Phase)

На цій стадії `make` зчитує головний `Makefile`, усі файли, підключені через `include`, а також завантажує внутрішні вбудовані правила:

1. Текст розбирається на змінні, директиви та правила.
2. Виконуються умовні конструкції (`ifeq`, `ifdef`, `else`, `endif`).
3. Виконуються директиви підключення файлів `include`.
4. Розгортаються вирази, які мають **негайне розгортання** (оператори `:=`, директиви `ifeq`, виклики `$(shell ...)` у тілі таких змінних).
5. Будується орієнтований ациклічний граф залежностей (DAG) у пам'яті процесу.
6. Встановлюється ціль за замовчуванням (*default goal*) — нею стає перша явна ціль у файлі, яка не починається з крапки.

На цьому етапі **жодна команда компіляції не виконується**, а рядки рецептів зберігаються в пам'яті як сирий нерозгорнутий текст.

### Фаза 2: Виконання та оновлення цілей (Execute Phase)

Друга фаза розпочинається після того, як увесь граф повністю збудовано в оперативній пам'яті:

1. `make` обирає ціль для збірки (ціль за замовчуванням або цілі, явно передані в аргументах командного рядка, наприклад `make bin/app`).
2. Застосовується пошук у глибину (DFS) для топологічного обходу дерева залежностей від обраної цілі до листя графа (вихідних файлів).
3. Для кожного вузла перевіряються системні часові позначки `mtime` (час останньої модифікації) цілі та її пререквізитів.
4. Якщо ціль відсутня або хоча б один пререквізит новіший за ціль (`mtime(prereq) > mtime(target)`), ціль позначається як застаріла.
5. Для застарілої цілі розгортаються рядки її рецепта: обчислюються автоматичні змінні (`$@`, `$<`, `$^`), розгортаються відкладені змінні (`=`), і кожен рядок по черзі передається новому процесу `/bin/sh`.

Якщо рецепт завершується успішно (код повернення 0), `make` оновлює статус цілі й переходить до наступного залежного вузла графа.

## Змінні та розгортання: відкладене проти негайного

У GNU Make існує два принципово різних типи (*flavors*) змінних, які визначають момент їхнього розгортання.

![Таблиця різновидів присвоєння змінних у GNU Make: негайне, відкладене, умовне та командне](/root/sys/sys-bsystem/make/img/make-variable-expansion.svg)
*Присвоєння змінних у GNU Make. Оператор `:=` фіксує значення в момент зчитування рядка, унеможливлюючи нескінченну рекурсію, тоді як `=` зберігає сирий вираз і обчислює його щоразу заново під час кожного звернення.*

### 1. Відкладене / рекурсивно розгортане присвоєння (`=`)

Оператор `=` створює змінну, значення якої зберігається дослівно. Усі змінні та виклики функцій всередині правої частини **не розгортаються** у момент визначення. Вони обчислюються щоразу, коли до змінної звертаються:

```make
# Значення CXX розгортатиметься щоразу заново
CXX = g++
FLAGS = $(OPT) -Wall
OPT = -O2
```

Якщо викликати `$(FLAGS)`, Make підставить `$(OPT) -Wall`, побачить `$(OPT)`, підставить `-O2` і отримає `-O2 -Wall`. Змінна `OPT` була визначена **пізніше** за `FLAGS`, але це працює, бо розгортання відкладене.

Проте оператор `=` має небезпечну пастку — самопосилання:

```make
# ПОМИЛКА: нескінченна рекурсія!
CFLAGS = $(CFLAGS) -O2
```

Коли Make спробує обчислити `CFLAGS`, він підставить `$(CFLAGS) -O2`. Усередині знову стоїть `$(CFLAGS)`, що викликає повторне розгортання самого себе до переповнення стека. Make виявить це і завершиться з помилкою:

```text
Makefile:2: *** Recursive variable 'CFLAGS' references itself (eventually). Stop.
```

### 2. Негайне / просто розгортане присвоєння (`:=` або `::=`)

Оператор `:=` (або стандартний за POSIX 2024 `::=`) розгортає праву частину **один раз** прямо під час читання цього рядка у фазі 1:

```make
SRCS := $(wildcard src/*.c)
OBJS := $(SRCS:src/%.c=build/%.o)

# Дописування прапорців без рекурсії:
CFLAGS := -Wall
CFLAGS := $(CFLAGS) -O2   # Працює ідеально: CFLAGS отримує рядок "-Wall -O2"
```

> 🔧 **Інженерне правило:** За замовчуванням завжди використовуйте `:=` замість `=`. Це захищає від прихованої рекурсії та запобігає повторному виконанню важких функцій, як-от `$(shell ...)` чи `$(wildcard ...)`, під час кожної підстановки змінної в рецептах сотень файлів.

### 3. Умовне присвоєння (`?=`) та дописування (`+=`)

- `VAR ?= value` — присвоює значення тільки в тому разі, якщо змінна `VAR` ще не була визначена раніше (ні в Makefile, ні через змінну оточення, ні в аргументах командного рядка).
- `VAR += value` — дописує значення через пробіл. Якщо змінна була негайною (`:=`), вона розгортається негайно; якщо відкладеною (`=`), дописування зберігає відкладену поведінку.

### 4. Присвоєння через команду оболонки (`!=`)

Оператор `VAR != command` запускає команду оболонки у фазі 1, зчитує її стандартний вивід, замінює символи нового рядка на пробіли та негайно записує результат у змінну (аналог `VAR := $(shell command)`):

```make
GIT_HASH != git rev-parse --short HEAD 2>/dev/null || echo "unknown"
```

## Автоматичні змінні: динамічний контекст правила

Під час виконання рецепта у фазі 2 утиліта Make автоматично встановлює локальні змінні, що описують поточну ціль та її оточення. Вони починаються зі знака долара `$`, за яким іде один символ пунктуації або літера.

![Механіка зіставлення шаблонного правила та автоматичні змінні](/root/sys/sys-bsystem/make/img/pattern-rule-chain.svg)
*Зіставлення шаблонного правила та значення автоматичних змінних. Стебло `%` виділяється з імені цілі й підставляється у пререквізити, після чого змінні `$@`, `$<`, `$^`, `$*` стають доступними всередині команд рецепта.*

Розгляньмо ключові автоматичні змінні, які використовуються у повсякденній розробці:

| Змінна | Значення | Типове застосування |
|---|---|---|
| `$@` | Ім'я цілі, яку зараз будує правило | Ім'я вихідного файлу в прапорці `-o $@` |
| `$<` | Ім'я **першого** пререквізиту | Вхідний вихідний файл у компіляторі: `-c $<` |
| `$^` | Імена **всіх** пререквізитів через пробіл (дублікати видаляються) | Список усіх об'єктних файлів при лінкуванні |
| `$+` | Імена **всіх** пререквізитів зі збереженням повторів | Лінкування бібліотек із циклічними залежностями |
| `$?` | Імена лише тих пререквізитів, що новіші за ціль | Оновлення архівів або пакування інкрементів |
| `$*` | Основа (*stem*) шаблонного правила — текст, що збігся з `%` | Формування похідних імен файлів |
| `$(@D)` | Каталог цілі без завершального слеша | Автоматичне створення каталогу: `mkdir -p $(@D)` |
| `$(<D)` | Каталог першого пререквізиту | Пошук заголовків або локальних ресурсів |

Повний перелік автоматичних змінних, їхніх модифікаторів для каталогів та імен файлів, а також усіх вбудованих функцій тексту наведено в окремому [довіднику змінних і функцій GNU Make](root:sys-bsystem/make/api-make-variables.md).

## Явні, шаблонні та суфіксні правила

Make підтримує три способи опису правил перетворення файлів.

### 1. Явні правила (Explicit Rules)

Явне правило жорстко прив'язане до конкретних імен файлів на диску:

```make
bin/server: build/server.o build/net.o build/http.o
	$(CC) $(LDFLAGS) $^ $(LDLIBS) -o $@
```

Тут немає узагальнення: правило знає точні шляхи до всіх компонентів.

### 2. Шаблонні правила (Pattern Rules)

Шаблонні правила — це сучасний і гнучкий механізм GNU Make. У них символ відсотка `%` позначає довільний непорожній підрядок (*stem* — стебло):

```make
# Будь-який файл build/X.o робиться з src/X.c та include/X.h
build/%.o: src/%.c include/%.h
	@mkdir -p $(@D)
	$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@
```

Коли Make шукає спосіб побудувати ціль `build/math/matrix.o`:
1. Він зіставляє шаблон `build/%.o` з ціллю `build/math/matrix.o`.
2. Виділяє стебло `%` = `math/matrix`.
3. Підставляє це стебло у пререквізити: `src/math/matrix.c` та `include/math/matrix.h`.
4. Якщо пререквізити існують на диску (або для них є власні правила генерації), Make обирає це правило.

Шаблонні правила мають унікальну властивість: вони підтримують **багатоцільові шаблони** (*multiple targets in pattern rules*):

```make
# Одне виконання бізона створює ОДРАЗУ обидва файли
src/%.tab.c src/%.tab.h: src/%.y
	bison -d $< -o src/$*.tab.c
```

У шаблонному правилі з кількома цілями Make знає, що **один** запуск рецепта створює всі перелічені файли одночасно. Це принципово відрізняється від явного правила `file.c file.h: file.y`, яке Make трактує як два окремих незалежних правила з дубльованим виконанням команд.

### 3. Застарілі суфіксні правила (Suffix Rules)

Історичний спосіб опису неявних правил із ранніх версій POSIX:

```make
.SUFFIXES: .c .o
.c.o:
	$(CC) $(CFLAGS) -c $< -o $@
```

Суфіксні правила мають критичні обмеження: вони не вміють працювати з підкаталогами (не можна вказати `build/%.o`), не підтримують додаткових пререквізитів (як-от заголовкових файлів) і обмежені лише двома розширеннями. У сучасному коді їх замінюють на шаблонні правила з `%`.

## Подвійні двокрапки: незалежні правила для однієї цілі

Зазвичай для однієї цілі в Makefile можна визначити лише один командний рецепт. Якщо написати рецепт для `app` двічі через звичайну двокрапку, Make видасть попередження і проігнорує перший варіант.

Проте конструкція **подвійної двокрапки (`::`)** дозволяє розділити одну ціль на кілька абсолютно незалежних правил:

```make
# Перше правило: компіляція та генерація бінарника
target :: module1.o module2.o
	$(CC) $^ -o target

# Друге правило: збір та пакування ресурсів у той самий файл
target :: assets.zip
	zip -u target assets.zip
```

Коли Make обробляє правило з `::`, він перевіряє кожну групу пререквізитів окремо. Якщо `module1.o` новіший за `target`, виконається **лише перший** рецепт. Якщо ж оновився лише `assets.zip`, виконається **лише другий** рецепт. Це використовується рідко (наприклад, у скриптах ротації логів або оновлення складних саморозпаковуваних архівів), проте демонструє багатство внутрішньої граматики Make.

## Пошук вихідних файлів: механізми VPATH та vpath

У складних проектах вихідні файли часто розподілені між багатьма підкаталогами (`src/core/`, `src/net/`, `src/crypto/`), тоді як розробник бажає писати короткі уніфіковані правила без жорсткого дублювання структури папок.

Для цього GNU Make підтримує пошук джерел за шляхами:

1. **Глобальний `VPATH`:** Змінна, що містить список каталогів, розділених двокрапками або пробілами:
   ```make
   VPATH = src/core:src/net:src/crypto
   ```
2. **Шаблонний `vpath`:** Директива, яка прив'язує пошук конкретних розширень файлів до певних каталогів:
   ```make
   vpath %.c src/core src/net src/crypto
   vpath %.h include
   ```

### Пастка непрямого пошуку VPATH

Коли утиліта Make знаходить пререквізит через `vpath`, вона автоматично підставляє повний знайдений шлях у змінну `$<`. 

Розгляньмо приклад:

```make
vpath %.c src/net

# Якщо main.c лежить у src/net/main.c:
main.o: main.c
	$(CC) -c $< -o $@   # Спрацює: $< розгорнеться у src/net/main.c
```

Якщо ж розробник замість автоматичної змінної `$<` напише команду жорстко: `$(CC) -c main.c -o $@`, збірка зазнає краху, оскільки компілятор `gcc` не знає про внутрішній `vpath` утиліти Make і шукатиме `main.c` виключно в поточному каталозі.

## Псевдоцілі та спеціальні керуючі цілі

За замовчуванням Make вважає будь-яку ціль **файлом на диску**. Це призводить до класичного збою з цілями-командами.

### Проблема цілі `clean` та вирішення через `.PHONY`

Припустімо, у файлі написано правило:

```make
clean:
	rm -rf build bin
```

Якщо в кореневому каталозі хтось створить підкаталог із назвою `clean`, або з'явиться файл `clean`, наступний виклик команди поламається:

```console
$ make clean
make: 'clean' is up to date.
```

Make побачив, що файл `clean` існує на диску, у нього немає пререквізитів, отже, його не потрібно оновлювати, і команда `rm` не запускається.

Щоб виправити це, використовують спеціальну ціль `.PHONY`:

```make
.PHONY: all clean test install

clean:
	rm -rf build bin
```

Директива `.PHONY` повідомляє Make: зазначені цілі є абстрактними діями, а не файлами. Make ніколи не перевіряє файлову систему для цілей з `.PHONY` і завжди безумовно запускає їхній рецепт.

### Надійність збірки з `.DELETE_ON_ERROR`

Якщо під час компіляції сталася помилка синтаксису або користувач перервав збірку комбінацією `Ctrl+C`, компілятор міг уже створити порожній або неповний об'єктний файл `broken.o`. Без спеціальних налаштувань цей напівготовий файл лишиться на диску з актуальною часовою позначкою. Під час наступного запуску `make` вважатиме `broken.o` свіжим, перейде до лінкування й видасть незрозумілу помилку пошкодженого бінарного коду.

Спеціальна ціль `.DELETE_ON_ERROR:` виправляє цю небезпеку:

```make
.DELETE_ON_ERROR:
```

Якщо будь-яка команда рецепта завершується аварійно або з ненульовим кодом повернення, Make **автоматично видаляє ціль**, яка будувалася в цей момент.

## Часові позначки й особливості порядку обходу

Make вирішує, чи потрібно виконувати правило, на основі порівняння системних часових позначок `mtime` ([часових позначок файлів](root:sf-os/file-timestamps)).

Розгляньмо ланцюг обчислень:

```make
app: main.o util.o
	$(CC) $^ -o $@

main.o: main.c util.h
	$(CC) -c main.c -o $@
```

Алгоритм оновлення вузла `app`:
1. Make рекурсивно оновлює пререквізити `main.o` та `util.o`.
2. Для `main.o`: якщо `mtime(main.c) > mtime(main.o)` або `mtime(util.h) > mtime(main.o)`, запускається компіляція `main.o`. Файлова система оновлює `mtime(main.o)` поточним часом.
3. Make повертається до правила `app` і зчитує оновлений `mtime(main.o)`.
4. Тепер `mtime(main.o) > mtime(app)`. Отже, `app` застарів, і Make запускає команду лінкування.

### Залежності порядку (Order-Only Prerequisites)

Звичайні пререквізити мають подвійну роль: вони задають **порядок** збірки і слугують **критерієм застарілості**. Проте іноді потрібен лише порядок без перевірки дати зміни.

Класичний приклад — каталог збірки:

```make
# Розділювач | відокремлює звичайні пререквізити від order-only
build/%.o: src/%.c | build
	$(CC) $(CFLAGS) -c $< -o $@

build:
	mkdir -p build
```

У файлових системах POSIX запис нового файлу в каталог оновлює `mtime` самого каталогу. Якби `build` був звичайним пререквізитом, створення `build/main.o` оновило б дату каталогу `build`, що зробило б каталог новішим за всі раніше скомпільовані файли, і `make` щоразу перезбирав би весь проект заново.

Символ вертикальної риски `|` оголошує `build` як **order-only prerequisite**: Make гарантує, що каталог `build` буде створено до компіляції будь-якого `.o`, але зміна дати каталогу **не спричиняє** перекомпільовування об'єктних файлів.

## Рекурсивний Make та його архітектурні вади

У великих проектах часто використовують структуру з підкаталогами (`src/`, `lib/`, `plugins/`), викликаючи в кожному з них окремий екземпляр Make:

```make
# Рекурсивний підхід: виклик Make у підкаталогах
SUBDIRS = lib src

subdirs:
	for dir in $(SUBDIRS); do \
		$(MAKE) -C $$dir || exit 1; \
	done
```

Цей шаблон набув популярності в 1980-х роках, проте в 1997 році Пітер Міллер опублікував класичну працю «Recursive Make Considered Harmful» (*Рекурсивний Make вважається шкідливим*), у якій показав, чому такий підхід ламає базові гарантії системи збірки.

![Рекурсивний Make проти нерекурсивного: розрив графа залежностей проти єдиного зв'язного DAG](/root/sys/sys-bsystem/make/img/recursive-make-dag.svg)
*Порівняння рекурсивного та нерекурсивного підходів до організації Make. Рекурсивний виклик розділяє збірку на ізольовані підпроцеси, які не бачать змін у сусідніх каталогах. Нерекурсивний Make об'єднує всі модулі в єдиний цілісний граф, забезпечуючи точну мінімальну збірку та повне завантаження процесорних ядер.*

### Чому рекурсивний Make шкодить збірці:

1. **Втрата глобального графа залежностей:** Кожен дочірній процес `make -C lib` бачить тільки власний локальний Makefile. Якщо файл `src/main.c` включає заголовок `lib/engine.h`, головний Make не знає про цей зв'язок. Якщо ви зміните `lib/engine.h` і викличете `make src`, файл `main.c` **не буде перекомпільовано**, бо процес у теці `src/` не знає про зміни в `lib/`.
2. **Штучна фіксація порядку:** Каталоги збираються у жорсткій послідовності списку `SUBDIRS`, навіть якщо файли всередині `src/` могли б збиратися паралельно з `lib/`.
3. **Деградація паралелізму (`-j`):** Якщо головний Make не координує процеси через спеціальний системний протокол передачі токенів (*GNU Make Jobserver*), рекурсивні виклики можуть запустити неконтрольовану кількість процесів компіляції, перевантажуючи оперативну пам'ять і процесор.
4. **Зайві холості перевірки:** Щоб переконатися, що проект зібрано, головний Make змушений щоразу запускати окремий підпроцес для кожного підкаталогу, що на великих деревах додає секунди марного очікування.

### Механізм протоколу GNU Make Jobserver

Коли розробник викликає `make -j8`, утиліта Make має гарантувати, що в будь-який момент часу працює не більше ніж 8 паралельних процесів компіляції, навіть якщо вони породжені з різних рівнів рекурсивних викликів або процесом LTO-компілятора (GCC Link Time Optimization).

Ця координація реалізована через елегантний механізм **Jobserver**:
1. Головний батьківський процес `make` створює анонімний UNIX-канал (*pipe*) або POSIX-семафор.
2. У цей канал записується `N - 1` байтів (токенів авторизації). Перший слот займає сам батьківський процес.
3. Коли Make породжує дочірній процес (наприклад, підлеглий `$(MAKE)` або виклик `gcc`), він передає номери дескрипторів читання та запису каналу через аргумент командного рядка або змінну оточення `--jobserver-auth=R,W`.
4. Перед тим як запустити новий рядок рецепта, будь-який екземпляр Make зобов'язаний зчитати один байт із дескриптора `R`. Якщо канал порожній, процес блокується системним викликом `read()`.
5. Після завершення команди процес повертає токен, записуючи байт назад у дескриптор `W`.

Цей протокол дає змогу всій ієрархії процесів спільно ділити пул ядер без складних міжпроцесних замків.

### Альтернатива: нерекурсивний Make (Non-recursive Make)

Замість запуску нових процесів `make`, проект використовує **один кореневий Makefile**, який включає фрагменти правил із підкаталогів за допомогою директиви `include`:

```make
# Головний Makefile
all: bin/app

# Включення фрагментів описів модулів
include lib/module.mk
include src/module.mk

# Лінкування єдиного кінцевого бінарника
bin/app: $(LIB_OBJS) $(SRC_OBJS)
	@mkdir -p $(@D)
	$(CC) $(LDFLAGS) $^ $(LDLIBS) -o $@
```

У файлі `lib/module.mk` правила описуються відносно кореневого каталогу:

```make
# lib/module.mk
LIB_SRCS := lib/util.c lib/net.c
LIB_OBJS := $(LIB_SRCS:lib/%.c=build/lib/%.o)

build/lib/%.o: lib/%.c
	@mkdir -p $(@D)
	$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@
```

У такій структурі Make будує **один спільний DAG**. Зміна будь-якого файлу в будь-якому підкаталозі миттєво викликає перезбирання строго необхідного мінімуму компонентів, а паралельний запуск `make -j$(nproc)` ідеально утилізує всі наявні ядра процесора.

## Повноцінний сучасний Makefile для C та C++ проектів

Об'єднаймо всі розібрані концепції в готовий, надійний та ідіоматичний Makefile для проекту, що містить вихідний код, автоматичне відстеження змін у заголовкових файлах через генерацію dep-файлів компілятора (`-MMD -MP`) та правильну ізоляцію артефактів.

### Шаблон сучасного виробничого Makefile

```make
# ==============================================================================
# Сучасний ідіоматичний Makefile для C/C++ проекту з автоматичними dep-файлами
# ==============================================================================

# 1. Налаштування оболонки та керуючих параметрів Make
SHELL := /bin/sh
.ONESHELL:
.DELETE_ON_ERROR:
export LC_ALL := C

# 2. Визначення тулчейну та стандартних прапорців
CC       ?= gcc
CXX      ?= g++
CPPFLAGS := -Iinclude -MMD -MP
CFLAGS   := -std=c11 -O2 -Wall -Wextra -pedantic -g
CXXFLAGS := -std=c++20 -O2 -Wall -Wextra -g
LDFLAGS  := 
LDLIBS   := -lm

# 3. Структура каталогів проекту
SRC_DIR   := src
INC_DIR   := include
BUILD_DIR := build
BIN_DIR   := bin
TARGET    := $(BIN_DIR)/app

# 4. Пошук джерел та генерація списків об'єктів
C_SRCS    := $(wildcard $(SRC_DIR)/*.c)
CPP_SRCS  := $(wildcard $(SRC_DIR)/*.cpp)

C_OBJS    := $(patsubst $(SRC_DIR)/%.c,$(BUILD_DIR)/%.o,$(C_SRCS))
CPP_OBJS  := $(patsubst $(SRC_DIR)/%.cpp,$(BUILD_DIR)/%.o,$(CPP_SRCS))
ALL_OBJS  := $(C_OBJS) $(CPP_OBJS)

# Список файлів залежностей (.d), які компілятор згенерує поруч із .o
DEPS      := $(ALL_OBJS:.o=.d)

# 5. Головні цілі
.PHONY: all clean test info

all: $(TARGET)

# Лінкування фінального виконуваного бінарного файлу
$(TARGET): $(ALL_OBJS) | $(BIN_DIR)
	$(if $(CPP_SRCS),$(CXX),$(CC)) $(LDFLAGS) $^ $(LDLIBS) -o $@
	@echo "✓ Проект успішно зібрано: $@"

# Шаблонне правило для вихідних файлів на C
$(BUILD_DIR)/%.o: $(SRC_DIR)/%.c | $(BUILD_DIR)
	$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@

# Шаблонне правило для вихідних файлів на C++
$(BUILD_DIR)/%.o: $(SRC_DIR)/%.cpp | $(BUILD_DIR)
	$(CXX) $(CPPFLAGS) $(CXXFLAGS) -c $< -o $@

# Створення вихідних каталогів як order-only пререквізитів
$(BUILD_DIR) $(BIN_DIR):
	@mkdir -p $@

# 6. Очищення скомпільованих файлів
clean:
	@rm -rf $(BUILD_DIR) $(BIN_DIR)
	@echo "✓ Каталоги збірки очищено."

# 7. Діагностична інформація
info:
	@echo "Вихідні файли C:   $(C_SRCS)"
	@echo "Вихідні файли C++: $(CPP_SRCS)"
	@echo "Об'єктні файли:    $(ALL_OBJS)"
	@echo "Файли залежностей: $(DEPS)"

# 8. Підключення згенерованих компілятором файлів залежностей .d
# Префікс '-' ігнорує відсутність файлів під час першої збірки
-include $(DEPS)
```

### Як працює автоматичне відстеження заголовків через `-MMD -MP`

Найбільша слабкість ручних Makefile полягає в тому, що розробники забувають прописувати пререквізити заголовкових файлів (`main.o: include/config.h`). Якщо змінити константу в `config.h`, Make не перекомпільовує `main.c`, що призводить до прихованих багів у бінарному файлі.

Прапорець компілятора `-MMD -MP` повністю вирішує цю проблему:
- `-MMD` наказує компілятору під час компіляції файлу `src/main.c` згенерувати поруч файл `build/main.d`, який містить точне правило з усіма підключеними `#include`:
  ```make
  build/main.o: src/main.c include/config.h include/util.h
  ```
- `-MP` додає для кожного заголовка фіктивне порожнє правило (`include/config.h:`). Це рятує збірку від падіння, якщо якийсь заголовок було перейменовано або видалено з диска.
- Директива `-include $(DEPS)` наприкінці Makefile зчитує всі ці `.d` файли під час наступного запуску Make, вбудовуючи реальні залежності заголовків у граф.

### Приклад коду модуля, що збирається цим Makefile

Погляньмо на реалізацію обчислювального модуля та точки входу, для яких призначено наведений вище Makefile:

:::tabs

/* src/calc.c — обчислювальний модуль мовою C */
#include <stdio.h>

    if (n <= 1) return 1;
    long long result = 1;

    return result;
}

## Підсумок: правила надійної збірки на GNU Make

1. **Пам'ятайте про дві фази:** Усі змінні `:=`, умовні блоки `ifeq` та виклики `$(shell ...)` обчислюються під час зчитування Makefile, тоді як рядки рецептів і автоматичні змінні `$@`, `$<` — лише під час оновлення цілей у фазі виконання.
2. **Використовуйте `:=` за замовчуванням:** Відкладене `=` потрібне лише тоді, коли значення змінної свідомо залежить від визначень, що з'являться нижче у файлі, або коли вона формує динамічний шаблон команди.
3. **Завжди вмикайте `.DELETE_ON_ERROR:`** — це запобігає появі пошкоджених артефактів на диску після помилок компілятора або переривання процесу збірки.
4. **Оголошуйте псевдоцілі через `.PHONY:`** — це гарантує, що `make clean` та `make all` працюватимуть незалежно від випадково створених однойменних файлів чи підкаталогів.
5. **Ізолюйте каталоги через Order-Only пререквізити (`|`):** Створення вихідних папок `build` та `bin` не повинно інвалідувати часові позначки скомпільованих файлів.
6. **Генеруйте dep-файли компілятором (`-MMD -MP`):** Не пишіть залежності від заголовкових файлів вручну — компілятор формує точні правила автоматично під час кожної трансляції.
7. **Уникайте рекурсивного Make:** Замість ланцюжка `make -C` будуйте єдиний цілісний граф залежностей за допомогою `include module.mk`, забезпечуючи максимальний паралелізм та ідеальну інкрементальність збірки.
