# 📋 Довідник конфігурації platformio.ini

Маніфест `platformio.ini` визначає повну специфікацію збірки вбудованого проєкту: від вибору цільового чипа та фреймворку до прапорців крос-компілятора, правил пошуку бібліотек і параметрів апаратного завантажувача. Цей довідник містить структурований опис усіх секцій, директив, вбудованих змінних та механізмів інтерполяції, необхідних для точного налаштування конвеєра збірки без ручного редагування скриптів SCons.

## Структура файлу, типи секцій та правила парсингу

Конфігураційний файл `platformio.ini` використовує розширений синтаксис INI-формату. Рядки, що починаються із символу крапки з комою `;` або решітки `#`, вважаються коментарями та ігноруються синтаксичним аналізатором. Будь-яке значення директиви може бути багаторядковим: для цього кожен наступний рядок списку повинен мати обов'язковий початковий відступ у два або чотири пробіли.

Парсер PlatformIO обробляє конфігурацію у два послідовні проходи. На першому проході зчитуються всі статичні секції, будується дерево успадкування `extends` та розгортаються текстові підстановки. На другому проході виконуються динамічні команди ін'єкції через префікс `!` та розкриваються змінні середовища операційної системи `${sysenv.NAME}`.

```ini
; Глобальні налаштування структури репозиторію
[platformio]
default_envs = esp32_prod, stm32_prod
src_dir = src
include_dir = include

; Базове середовище для спільної конфігурації
[env]
framework = arduino
monitor_speed = 115200
build_flags =
    -Wall
    -Wextra
    -D PROJECT_VERSION=\"2.4.0\"

; Конкретне цільове оточення для ESP32
[env:esp32_prod]
platform = espressif32 @ 6.5.0
board = esp32dev
build_flags =
    ${env.build_flags}
    -D TARGET_ESP32=1
    -D CORE_DEBUG_LEVEL=0

; Конкретне цільове оточення для STM32
[env:stm32_prod]
platform = ststm32 @ 17.3.0
board = nucleo_f401re
build_flags =
    ${env.build_flags}
    -D TARGET_STM32=1
    -O2
```

## Секція [platformio]: глобальне керування структурою

Секція `[platformio]` конфігурує поведінку утиліти верхнього рівня та змінює стандартне розташування каталогів проєкту. Це дозволяє адаптувати PlatformIO до нестандартних структур репозиторіїв або монорепозиторіїв із спільним вихідним кодом.

| Директива | Тип | Опис | Значення за замовчуванням |
|---|---|---|---|
| `default_envs` | список | Перелік ідентифікаторів середовищ `[env:NAME]`, які збираються командою `pio run` без явного ключа `-e` | Усі оголошені середовища |
| `src_dir` | шлях | Каталог із вихідними файлами проєкту (`.c`, `.cpp`, `.S`) | `src` |
| `include_dir` | шлях | Каталог глобальних заголовкових файлів (`.h`, `.hpp`), що додається до пошуку через `-I` | `include` |
| `lib_dir` | шлях | Каталог локальних приватних бібліотек проєкту | `lib` |
| `libdeps_dir` | шлях | Каталог кешування завантажених зовнішніх бібліотек | `.pio/libdeps` |
| `build_dir` | шлях | Каталог проміжних об'єктних файлів та скомпільованих бінарників | `.pio/build` |
| `packages_dir` | шлях | Каталог завантажених тулчейнів і пакетів SDK | `~/.platformio/packages` |
| `data_dir` | шлях | Каталог файлів для генерації образів SPIFFS/LittleFS/FatFS | `data` |
| `test_dir` | шлях | Каталог модульних та інтеграційних тестів Unity | `test` |
| `extra_configs` | список | Шаблони шляхів (glob) до додаткових конфігураційних файлів INI | Немає |

Коли у директиві `extra_configs` вказано зовнішні файли (наприклад, `extra_configs = secret_credentials.ini`), їхній вміст зливається з головним конфігураційним деревом, що забезпечує безпечне відокремлення паролів та ключів шифрування від системи контролю версій.

## Директиви цільових середовищ [env] та [env:NAME]

Секція `[env]` містить глобальні налаштування, які автоматично підставляються в кожне цільове середовище `[env:NAME]`. Якщо однойменний параметр оголошено і в `[env]`, і в `[env:NAME]`, версія з конкретного цільового середовища або повністю перезаписує глобальну, або комбінується з нею через явну підстановку `${env.PARAMETER}`.

### Основні параметри платформи та апаратного забезпечення

Ці параметри визначають цільову мікросхему, системні константи та базовий набір драйверів периферії:

- **`platform`**: назва та версія платформи з офіційного реєстру PlatformIO. Дозволяє вказувати точну версію через оператор `@` (наприклад, `platform = espressif32 @ 6.5.0`), діапазон сумісності через семантичне версіонування (`platform = ststm32 @ ~17.3.0`), пряме посилання на Git-репозиторій платформи (`platform = https://github.com/platformio/platform-espressif32.git#v6.5.0`) або шлях до локального каталогу на диску.
- **`board`**: ідентифікатор плати з бази даних PlatformIO (`board = esp32dev`, `board = nucleo_f401re`, `board = bluepill_f103c8`). Цей параметр автоматично підтягує відповідну конфігурацію пінів, базові прапорці крос-компілятора, тип завантажувача та розмір пам'яті.
- **`board_build.mcu`**: примусове перевизначення маркування мікроконтролера для генерації прапорців архітектури (`-mcpu=` або `-march=`).
- **`board_build.f_cpu`**: тактова частота ядра мікроконтролера в герцах (наприклад, `160000000L` або `84000000L`). Значення автоматично експортується у вихідний код у формі макроса `F_CPU`.
- **`board_build.f_flash`**: частота тактування шини SPI для взаємодії із зовнішньою Flash-пам'яттю програм (наприклад, `80000000L` або `40000000L`).
- **`board_build.flash_mode`**: режим адресації та читання зовнішньої пам'яті Flash: Quad SPI (`qio`, `qout`) або Dual SPI (`dio`, `dout`).
- **`board_build.ldscript`**: шлях до власного файлу скрипта компонувальника (`.ld`). Використовується замість стандартного скрипта з SDK для створення нестандартних областей оперативної пам'яті, буферів DMA або секцій коду у швидкій RAM (ITCM).
- **`board_build.partitions`**: шлях до таблиці розділів Flash-пам'яті у форматі CSV (специфічно для мікроконтролерів ESP32 під фреймворком ESP-IDF або Arduino).
- **`framework`**: програмна основа прошивки. Допустимі значення залежать від платформи: `arduino`, `espidf`, `stm32cube`, `zephyr`, `cmsis`, `mbed`, `libopencm3`. PlatformIO дозволяє комбінувати сумісні фреймворки через кому (наприклад, `framework = arduino, espidf`).

## Керування прапорцями збірки: build_flags та build_unflags

Директиви прапорців збірки дають повний контроль над транслятором і компонувальником. Вони маршрутизуються у відповідні змінні середовища SCons: `CPPDEFINES` (макроси препроцесора), `CPPPATH` (каталоги пошуку заголовків), `CCFLAGS` (опції компілятора C), `CXXFLAGS` (опції компілятора C++) та `LINKFLAGS` (опції компонувальника).

### Синтаксис та правила екранування

```ini
[env:custom_flags]
platform = ststm32
board = nucleo_f401re
framework = stm32cube

build_flags =
    ; Оптимізація та налагодження
    -Os
    -g3
    -Wall
    -Wextra
    -Werror
    
    ; Шляхи пошуку заголовків
    -I include/drivers
    -I include/generated
    
    ; Макроси препроцесора
    -D USE_HAL_DRIVER
    -D STM32F401xE
    -D LOG_LEVEL=3
    -D DEVICE_NAME=\"SensorNode\"
    
    ; Прапорці лінкера: генерація map-файлу та оптимізація розміру секцій
    -Wl,-Map=.pio/build/nucleo_f401re/output.map
    -Wl,--gc-sections
    -Wl,--print-memory-usage

build_unflags =
    ; Видалення прапорців за замовчуванням, які автоматично підставив SDK
    -O2
    -Wno-unused-variable
```

Під час передачі рядкових констант у макроси через `-D` лапки необхідно обов'язково екранувати зворотним слешем: `-D VERSION=\"1.0.0\"`. Якщо пропустити екранування, препроцесор сприйме рядок як невідомий ідентифікатор у коді й аварійно зупинить компіляцію.

### Динамічне обчислення прапорців через зовнішні команди

PlatformIO дозволяє виконувати довільні консольні утиліти хост-системи для динамічної ін'єкції прапорців за допомогою префікса знаку оклику `!`:

```ini
[env:dynamic_meta]
platform = espressif32
board = esp32dev
framework = arduino
build_flags =
    -D BUILD_TIMESTAMP=!date '+%%s'
    -D GIT_REVISION=!git rev-parse --short HEAD
    -D BUILD_MACHINE=!hostname
```

Символ відсотка `%` всередині рядка команди необхідно дублювати `%%`, оскільки одиночний відсоток зарезервовано синтаксисом INI для інтерполяції змінних.

## Library Dependency Finder (LDF): конфігурація аналізатора

Підсистема LDF сканує вихідний код проєкту та підключає лише ті бібліотеки, заголовки яких дійсно фігурують у викликах `#include`. Це запобігає роздуванню бінарного файлу та виключає конфлікти компіляції.

### Детальний розбір режимів lib_ldf_mode

| Режим | Алгоритм роботи | Переваги | Недоліки / Ризики |
|---|---|---|---|
| `off` | Сканування відключено. Компілюються лише файли, додані вручну або через явні параметри. | Мінімальний оверхед на старті збірки. | Не знаходить транзитивні залежності автоматично. |
| `chain` | Лінійне сканування без виклику C-препроцесора (за замовчуванням). Перевіряє лише прямі `#include` у коді проєкту. | Висока швидкість аналізу. | Ігнорує директиви всередині неактивних гілок `#ifdef`/`#ifndef`. |
| `deep` | Рекурсивне сканування дерева `#include` без виклику C-препроцесора. Шукає залежності в бібліотеках, які включені іншими бібліотеками. | Знаходить глибоко вкладені модулі. | Може підтягнути непотрібні важкі бібліотеки через збіг назв `.h`. |
| `chain+` | Лінійне сканування з попереднім прогоном файлів через C-препроцесор (`gcc -E`). | Точно враховує макроси та конфігурацію з `build_flags`. | Додаткові витрати часу на препроцесинг кожного файлу. |
| `deep+` | Рекурсивне сканування з повним препроцесингом усіх вихідних файлів проєкту та бібліотек. | Найвища точність побудови графа залежностей. | Найдовший час первинного парсингу проєкту. |

У типових проєктах рекомендовано залишати режим `chain`. Перехід на `deep+` необхідний тоді, коли бібліотеки містять розгалужену логіку умовного підключення модулів (наприклад, драйвери дисплеїв, які підтягують шрифти лише за наявності відповідного макроса в конфігурації проєкту).

### Режими сумісності lib_compat_mode

- **`strict` (режим за замовчуванням)**: бібліотека вважається сумісною і підключається до збірки лише тоді, коли платформа і фреймворк поточного цільового середовища явно перелічені у файлі маніфесту `library.json`. Це захищає від спроб компіляції бібліотек, оптимізованих під конкретний процесор (наприклад, архітектурно-специфічні асемблерні оптимізації ESP32 у проєкті під STM32).
- **`soft`**: бібліотека підключається, якщо збігається використовуваний фреймворк (наприклад, `arduino`), навіть якщо виробник бібліотеки не додав поточну плату до офіційного списку протестованих пристроїв.

### Джерела залежностей у lib_deps

Директива `lib_deps` приймає перелік бібліотек із підтримкою різних джерел:

```ini
lib_deps =
    ; Семантичне версіонування з офіційного реєстру PlatformIO
    bblanchon/ArduinoJson @ ^7.0.4
    knolleary/PubSubClient @ ~2.8.0

    ; Точна фіксація версії пакета
    adafruit/Adafruit BME280 Library @ 2.2.4

    ; Git-репозиторій за тегом, гілкою або повним хешем коміту
    https://github.com/me-no-dev/ESPAsyncWebServer.git # v1.2.3
    https://github.com/username/custom-driver.git # 8a3f91c6b5

    ; Локальний каталог зі спільною бібліотекою
    file://../shared_components/crypto_engine
```

## Завантаження, налагодження та послідовний монітор

PlatformIO абстрагує протоколи прошивання та налагодження через уніфіковані параметри конфігурації:

### Налаштування завантажувача (Upload)

- **`upload_protocol`**: інтерфейс прошивання. Для ESP32 це зазвичай `esptool` або `espota` (прошивання по повітрю); для STM32 — `stlink`, `jlink`, `cmsis-dap`, `dfu`, `serial`.
- **`upload_port`**: послідовний порт (`/dev/ttyUSB0`, `COM3`) або мережева IP-адреса для бездротового OTA-завантаження.
- **`upload_speed`**: швидкість передачі даних по UART (наприклад, `921600` або `115200`).
- **`upload_flags`**: додаткові ключі командного рядка для утиліти прошивання.

### Налаштування монітора (Serial Monitor) та фільтри обробки

Директива `monitor_filters` застосовує конвеєр обробки текстового потоку з послідовного порту:

```ini
[env:monitor_cfg]
monitor_port = /dev/ttyUSB0
monitor_speed = 115200
monitor_filters =
    default
    time ; Додавання префікса точного системного часу до кожного рядка логу
    log2file ; Автоматичне дублювання всього термінального виводу у файл
    colorize ; Підсвічування ANSI-кольорів та рівнів логування (Error/Warn/Info)
    esp32_exception_decoder ; Автоматичний аналіз адрес стека помилок за допомогою addr2line
```

Фільтр `esp32_exception_decoder` є критично важливим для розробки під ESP32: при виникненні паніки ядра (Guru Meditation Error) він автоматично перехоплює шістнадцятковий дамп регістрів стека викликів і транслює адреси безпосередньо у назви функцій та номери рядків вихідного коду за допомогою утиліти `xtensa-esp32-elf-addr2line`.

## Механізм інтерполяції змінних та повторне використання блоків

PlatformIO підтримує потужну систему інтерполяції значень для виключення дублювання конфігурації:

1. **Підстановка із секцій INI**: синтаксис `${section.parameter}` дозволяє отримувати значення з будь-якої іншої секції конфігураційного файлу (наприклад, `${env.build_flags}` або `${platformio.src_dir}`).
2. **Підстановка змінних оточення операційної системи**: синтаксис `${sysenv.VARIABLE_NAME}` читає значення із середовища хоста під час збірки (наприклад, `${sysenv.CI_BUILD_ID}` чи `${sysenv.WIFI_PASSWORD}`).
3. **Наслідування секцій**: директива `extends = env:parent_name` копіює всі поля батьківського середовища до дочірнього, дозволяючи перевизначити лише необхідні параметри.
4. **Користувацькі блоки конфігурації**: створення власних секцій (наприклад, `[custom_settings]`) для збереження повторюваних прапорців або шляхів.

```ini
[custom_settings]
common_flags = -Wall -Wextra -std=gnu++17
release_opt = -O3 -DNDEBUG
wifi_ssid = ${sysenv.WIFI_SSID}

[env:device_base]
framework = arduino
build_flags =
    ${custom_settings.common_flags}
    -D WIFI_SSID=\"${custom_settings.wifi_ssid}\"

[env:production_firmware]
extends = env:device_base
platform = espressif32
board = esp32dev
build_flags =
    ${env:device_base.build_flags}
    ${custom_settings.release_opt}
```
