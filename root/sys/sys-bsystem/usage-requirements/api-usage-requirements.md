# 📋 Довідка команд вимог вжитку CMake

У цій довідці зібрано повний опис інтерфейсних команд CMake, що керують вимогами вжитку цілей: точні сигнатури, правила передачі властивостей через ключові слова `PUBLIC`, `PRIVATE`, `INTERFACE`, таблиці відповідності внутрішніх і транзитивних властивостей, а також спеціальні генераторні вирази простору збірки та інструменти діагностики графа.

Усі відомості узгоджено зі стандартами **CMake 3.28–3.31** та сучасною моделлю цільово-орієнтованої збірки (Target-Centric CMake).

## Архітектурний принцип команд налаштування цілей

У системі CMake кожна ціль (виконуваний файл, бібліотека чи спеціальний інтерфейсний модуль) є об'єктом, що містить внутрішній словник іменованих властивостей. Коли розробник викликає команди сімейства `target_*`, він не виконує безпосередніх дій компілятора, а наповнює цей словник рядковими списками конфігурації.

Ключові слова `PRIVATE`, `INTERFACE` та `PUBLIC` діють як внутрішній маршрутизатор:
* `PRIVATE` записує значення у власну властивість збірки, яка зчитується генератором під час формування командного рядка компіляції файлів поточної цілі.
* `INTERFACE` записує значення у властивість із префіксом `INTERFACE_`, яка повністю ігнорується під час збірки самої цілі, але автоматично приєднується до параметрів будь-якого зовнішнього модуля, що підключає цю ціль через `target_link_libraries`.
* `PUBLIC` здійснює дублюючий запис: значення одночасно потрапляє і до власної властивості цілі, і до її дзеркальної експортної властивості `INTERFACE_`.

Якщо команду викликано для інтерфейсної бібліотеки (`add_library(... INTERFACE)`), дозволяється використовувати виключно ключове слово `INTERFACE`. Спроба використати `PRIVATE` або `PUBLIC` призведе до фатальної помилки конфігурації, оскільки інтерфейсна ціль не має власних скомпільованих джерел і не володіє внутрішніми властивостями збірки.

Особливим випадком є псевдоніми цілей (`add_library(foo::foo ALIAS foo)`): для них команди сімейства `target_*` суворо заборонені. Псевдонім є виключно незмінним представленням цілі (read-only view), тому будь-які налаштування вимог вжитку слід застосовувати до оригінальної базової цілі.

## Імпортовані цілі (IMPORTED) та транзитивні вимоги

Імпортовані цілі описують зовнішні залежності, які були зібрані за межами поточного проєкту (наприклад, системні бібліотеки чи пакети, знайдені командою `find_package`).

```cmake
add_library(OpenSSL::Crypto UNKNOWN IMPORTED)
set_target_properties(OpenSSL::Crypto PROPERTIES
    IMPORTED_LOCATION "/usr/lib/libcrypto.so"
    INTERFACE_INCLUDE_DIRECTORIES "/usr/include"
    INTERFACE_COMPILE_DEFINITIONS "OPENSSL_API_COMPAT=0x10100000L"
)
```

Для імпортованих цілей діють такі фундаментальні правила:
1. Оскільки вихідні файли такої бібліотеки не компілюються, вона не має властивостей `INCLUDE_DIRECTORIES` чи `COMPILE_DEFINITIONS`.
2. Усі параметри використання налаштовуються виключно через властивості з префіксом `INTERFACE_`.
3. Коли проєкт викликає `target_link_libraries(my_app PRIVATE OpenSSL::Crypto)`, генератор CMake автоматично витягує шлях до бінарного файлу з `IMPORTED_LOCATION` та транзитивно передає вимоги з `INTERFACE_INCLUDE_DIRECTORIES` і `INTERFACE_COMPILE_DEFINITIONS` до командного рядка компілятора `my_app`.

## Зведена таблиця команд і пар властивостей

Кожна команда налаштування цілі є синтаксичним фасадом над парою властивостей у внутрішній моделі CMake: одна властивість призначена для компіляції файлів самої цілі, а друга (з префіксом `INTERFACE_`) — для транзитивного експорту споживачам.

| Команда | Внутрішня властивість (`PRIVATE`) | Експортна властивість (`INTERFACE`) | Дія ключового слова `PUBLIC` | Версія CMake |
|---|---|---|---|---|
| `target_include_directories()` | `INCLUDE_DIRECTORIES` | `INTERFACE_INCLUDE_DIRECTORIES` | Записує в обидва списки | 2.8.11 |
| `target_compile_definitions()` | `COMPILE_DEFINITIONS` | `INTERFACE_COMPILE_DEFINITIONS` | Записує в обидва списки | 2.8.11 |
| `target_compile_options()` | `COMPILE_OPTIONS` | `INTERFACE_COMPILE_OPTIONS` | Записує в обидва списки | 2.8.11 |
| `target_compile_features()` | `COMPILE_FEATURES` | `INTERFACE_COMPILE_FEATURES` | Записує в обидва списки | 3.1 |
| `target_sources()` | `SOURCES` | `INTERFACE_SOURCES` | Записує в обидва списки | 3.1 |
| `target_link_libraries()` | `LINK_LIBRARIES` | `INTERFACE_LINK_LIBRARIES` | Записує в обидва списки | 2.8.11 |
| `target_link_options()` | `LINK_OPTIONS` | `INTERFACE_LINK_OPTIONS` | Записує в обидва списки | 3.13 |
| `target_link_directories()` | `LINK_DIRECTORIES` | `INTERFACE_LINK_DIRECTORIES` | Записує в обидва списки | 3.13 |
| `target_precompile_headers()`| `PRECOMPILE_HEADERS` | `INTERFACE_PRECOMPILE_HEADERS` | Записує в обидва списки | 3.16 |

## Сигнатури команд налаштування цілей

### 1. `target_include_directories()`

Додає каталоги пошуку заголовних файлів до командного рядка компілятора (відповідає прапорцю `-I` у GCC/Clang або `/I` у MSVC).

```cmake
target_include_directories(<ціль> [SYSTEM] [BEFORE]
    <INTERFACE|PUBLIC|PRIVATE> [шлях1...]
    [<INTERFACE|PUBLIC|PRIVATE> [шлях2...] ...]
)
```

#### Параметри та модифікатори

* **`<ціль>`** — ім'я цілі, створеної через `add_executable()` або `add_library()`.
* **`SYSTEM`** — вказує, що перелічені каталоги містять системні або сторонні заголовки. Для споживачів запис додається у властивість `INTERFACE_SYSTEM_INCLUDE_DIRECTORIES`. Під час генерації команд збірки CMake підставляє прапорець `-isystem` (для GCC/Clang) або `/external:I` (для MSVC), що вимикає генерацію будь-яких компіляторних попереджень для коду всередині цих каталогів.
* **`BEFORE`** — вставляє вказані каталоги на початок списку замість усталеного додавання в кінець. Це критично, коли потрібно перекрити системні або сторонні заголовки локальними оновленими версіями.
* **Шляхи** — можуть бути абсолютними або відносними. Відносні шляхи всередині блоків `PRIVATE` інтерпретуються відносно `${CMAKE_CURRENT_SOURCE_DIR}`. Для блоків `PUBLIC` та `INTERFACE`, призначених для подальшого експорту через команду `install(EXPORT)`, обов'язковим є використання генераторних виразів `$<BUILD_INTERFACE>` та `$<INSTALL_INTERFACE>`.

Шляхи в CMake завжди нормалізуються з прямими скісними рисками (`/`), навіть на операційній системі Windows. Генератор автоматично перетворює їх на формат поточної платформи під час формування кінцевого командного рядка компілятора.

```cmake
target_include_directories(graphics_engine
    PUBLIC
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
        $<INSTALL_INTERFACE:include>
    PRIVATE
        ${CMAKE_CURRENT_SOURCE_DIR}/src/internal
    SYSTEM PRIVATE
        ${CMAKE_CURRENT_SOURCE_DIR}/third_party/stb
)
```

### 2. `target_compile_definitions()`

Додає макровизначення препроцесора до процесу компіляції (відповідає прапорцю `-D` у GCC/Clang та MSVC).

```cmake
target_compile_definitions(<ціль> [BEFORE]
    <INTERFACE|PUBLIC|PRIVATE> [макрос1...]
    [<INTERFACE|PUBLIC|PRIVATE> [макрос2...] ...]
)
```

#### Правила синтаксису макросів

* Визначення без значення записуються як `FOO` (автоматично розгортається компілятором у `-DFOO` або `FOO=1`).
* Визначення зі значенням записуються через знак рівності: `LOG_LEVEL=2` або `API_VERSION="1.0"`.
* Провідний префікс `-D` (наприклад, `-DDEBUG=1`) є зайвим: починаючи з CMake 3.26, він автоматично видаляється системою конфігурації.
* Ідентичні макровизначення автоматично фільтруються й дедуплікуються генератором CMake, щоб уникнути дублювання однакових параметрів у виклику компілятора.
* Якщо макровизначення містить спеціальні символи, лапки або пробіли, CMake автоматично виконує екранування відповідно до правил цільового низового інструменту (Ninja, GNU Make чи MSBuild).

```cmake
target_compile_definitions(audio_dsp
    PUBLIC
        AUDIO_SAMPLE_RATE=48000
        USE_DOUBLE_PRECISION=1
    PRIVATE
        DSP_INTERNAL_BUFFER_SIZE=4096
        $<$<CONFIG:Debug>:ENABLE_ASSERTIONS>
)
```

### 3. `target_compile_options()`

Додає специфічні прапорці компілятора безпосередньо до виклику транслятора вихідних файлів.

```cmake
target_compile_options(<ціль> [BEFORE]
    <INTERFACE|PUBLIC|PRIVATE> [прапорець1...]
    [<INTERFACE|PUBLIC|PRIVATE> [прапорець2...] ...]
)
```

#### Тонкощі використання прапорців

* Прапорці додаються безпосередньо у рядок виклику компілятора.
* Якщо прапорець починається з `-W` або `/W`, CMake застосовує евристичну дедуплікацію, запобігаючи повторенню однакових параметрів попереджень.
* **Префікс `SHELL:`** — якщо прапорець вимагає збереження пробілів або складається з кількох нерозривних слів (наприклад, `-framework Metal` на macOS чи `/clang:-O3` у MSVC), його слід загортати у вираз `SHELL:...`, інакше CMake розділить елементи на окремі екрановані аргументи.
* Команда призначена для прапорців трансляції файлів. Для налаштування стандарту мови слід використовувати `target_compile_features`, а для позиційно-незалежного коду — властивість `POSITION_INDEPENDENT_CODE`, оскільки ручне додавання прапорців на зразок `-std=c++20` чи `-fPIC` через `target_compile_options` порушує кросплатформну сумісність.

```cmake
target_compile_options(neural_network
    PRIVATE
        $<$<CXX_COMPILER_ID:GNU,Clang>:
            -Wall
            -Wextra
            -Wpedantic
            -march=native
        >
        $<$<CXX_COMPILER_ID:MSVC>:
            /W4
            /permissive-
        >
)
```

### 4. `target_compile_features()`

Встановлює вимоги до можливостей і стандарту мови програмування (C або C++). Це найбільш надійний та ідіоматичний спосіб вибору стандарту мови, який повністю абстрагує специфічні прапорці компіляторів.

```cmake
target_compile_features(<ціль>
    <INTERFACE|PUBLIC|PRIVATE> [вимога1...]
    [<INTERFACE|PUBLIC|PRIVATE> [вимога2...] ...]
)
```

#### Повний перелік мета-вимог стандарту C++

| Вимога | Стандарт мови | Мінімальна версія CMake |
|---|---|---|
| `cxx_std_98` | C++98 / C++03 | 3.1 |
| `cxx_std_11` | C++11 | 3.1 |
| `cxx_std_14` | C++14 | 3.1 |
| `cxx_std_17` | C++17 | 3.8 |
| `cxx_std_20` | C++20 | 3.12 |
| `cxx_std_23` | C++23 | 3.20 |
| `cxx_std_26` | C++26 | 3.25 |

#### Мета-вимоги стандарту C

| Вимога | Стандарт мови C | Мінімальна версія CMake |
|---|---|---|
| `c_std_90` | C90 | 3.1 |
| `c_std_99` | C99 | 3.1 |
| `c_std_11` | C11 | 3.1 |
| `c_std_17` | C17 | 3.21 |
| `c_std_23` | C23 | 3.27 |

Під час генерації проєкту CMake обчислює максимальний стандарт серед усіх цілей, з'єднаних у графі залежностей, і автоматично підставляє правильний прапорець (`-std=c++20`, `/std:c++20` тощо) для поточного компілятора. Якщо компілятор не підтримує потрібний стандарт, а властивість `CXX_STANDARD_REQUIRED` встановлена в `ON`, конфігурація зупиниться з точною помилкою непідтримуваної версії мови.

```cmake
# Вимагаємо C++20 у відкритих заголовках
target_compile_features(modern_containers INTERFACE cxx_std_20)
```

### 5. `target_sources()`

Додає файли вихідного коду до цілі або реєструє структуровані набори заголовків і модулів (`FILE_SET`).

```cmake
# Класичний синтаксис (додавання вихідних файлів)
target_sources(<ціль>
    <INTERFACE|PUBLIC|PRIVATE> [файл1...]
    [<INTERFACE|PUBLIC|PRIVATE> [файл2...] ...]
)

# Сучасний синтаксис структурованих наборів файлів (CMake 3.23+)
target_sources(<ціль>
    <INTERFACE|PUBLIC|PRIVATE>
    [FILE_SET <ім'я_набору> [TYPE <HEADERS|CXX_MODULES>]
     [BASE_DIRS <каталог_бази1...>]
     [FILES <файл1...>]]
)
```

#### Переваги використання FILE_SET HEADERS

* Автоматично наповнює властивість `INTERFACE_INCLUDE_DIRECTORIES` шляхами, вказаними в `BASE_DIRS`.
* Забезпечує коректну інсталяцію заголовків під час виклику команди `install(TARGETS ... FILE_SET HEADERS)`, усуваючи потребу в ручному копіюванні каталогів.
* Надає середовищам розробки (IDE) повну інформацію про ієрархію заголовних файлів бібліотеки.
* Дозволяє надійно підтримувати компіляцію інтерфейсів модулів C++20 (`TYPE CXX_MODULES`).

```cmake
target_sources(geometry_lib
    PUBLIC
        FILE_SET HEADERS
        BASE_DIRS include
        FILES
            include/geometry/point.hpp
            include/geometry/vector.hpp
    PRIVATE
        src/point.cpp
        src/vector.cpp
)
```

### 6. `target_link_libraries()`

Встановлює спрямовані ребра в графі залежностей між цілями та визначає правила розповсюдження вимог вжитку.

```cmake
target_link_libraries(<ціль>
    <INTERFACE|PUBLIC|PRIVATE> [залежність1...]
    [<INTERFACE|PUBLIC|PRIVATE> [залежність2...] ...]
)
```

#### Семантика категорій залежностей

* **`PRIVATE`** — залежність потрібна виключно для компіляції вихідних файлів самої цілі. До властивості `INTERFACE_LINK_LIBRARIES` запис не потрапляє, і споживачі цілі не бачать заголовків чи макросів цієї залежності. Для статичних бібліотек бінарний архів залежності автоматично просувається до фінального лінкера виконуваного файлу для розв'язання символів.
* **`PUBLIC`** — залежність використовується у вихідних файлах цілі та фігурує у її відкритих заголовках. Залежність одночасно потрапляє у `LINK_LIBRARIES` та `INTERFACE_LINK_LIBRARIES`.
* **`INTERFACE`** — залежність не потрібна для збірки самої цілі (наприклад, для header-only бібліотеки), але є обов'язковою для будь-якого споживача.

> ⚠️ **Політика CMP0023:** в одному проєкті заборонено змішувати виклики `target_link_libraries` із ключовими словами (`PUBLIC`/`PRIVATE`/`INTERFACE`) та застарілі виклики без ключових слів для однієї і тієї ж цілі.

### 7. `target_link_options()`

Додає прапорці безпосередньо до виклику редактора зв'язків (лінкера / компонувальника) під час створення виконуваного файла або спільної бібліотеки.

```cmake
target_link_options(<ціль> [BEFORE]
    <INTERFACE|PUBLIC|PRIVATE> [опція1...]
    [<INTERFACE|PUBLIC|PRIVATE> [опція2...] ...]
)
```

#### Префікс LINKER: для уніфікації прапорців

Починаючи з версії CMake 3.18, префікс `LINKER:` дозволяє описувати прапорці компонувальника без прив'язки до синтаксису драйвера компілятора. Вираз `LINKER:-z,now` автоматично перетворюється на `-Wl,-z,now` під час збірки через GCC/Clang або напряму передається утиліті `lld` чи `link.exe`.

```cmake
target_link_options(network_service
    PRIVATE
        "LINKER:-z,relro"
        "LINKER:-z,now"
        $<$<CXX_COMPILER_ID:AppleClang>:-dead_strip>
)
```

### 8. `target_link_directories()`

Додає шляхи пошуку бібліотек до командного рядка лінкера (відповідає прапорцю `-L` у GCC/Clang або `/LIBPATH` у MSVC).

```cmake
target_link_directories(<ціль> [BEFORE]
    <INTERFACE|PUBLIC|PRIVATE> [каталог1...]
    [<INTERFACE|PUBLIC|PRIVATE> [каталог2...] ...]
)
```

> ⚠️ **Архітектурне застереження:** у сучасному CMake використання `target_link_directories()` вважається небажаною практикою, оскільки пошук за відносним іменем (`-lfoo`) може випадково підтягнути системну бібліотеку з іншою версією. Натомість слід використовувати повні шляхи до імпортованих цілей (`add_library(foo UNKNOWN IMPORTED)` та `IMPORTED_LOCATION`).

### 9. `target_precompile_headers()`

Керує попередньою компіляцією заголовних файлів (PCH) для суттєвого прискорення часу компіляції великих кодових баз на C та C++.

```cmake
target_precompile_headers(<ціль>
    <INTERFACE|PUBLIC|PRIVATE>
    [<заголовок1> | "заголовок2.h" ...]
    [REUSE_FROM <інша_ціль>]
)
```

#### Правила синтаксису PCH

* Кутові дужки `<vector>` позначають включення системних або стандартних заголовків.
* Подвійні лапки `"project_pch.h"` позначають файли всередині дерева проєкту.
* Модифікатор **`REUSE_FROM`** дозволяє кільком цілям використовувати один і той самий скомпільований бінарний образ PCH від іншої цілі, якщо вони збираються з однаковими прапорцями компілятора, суттєво економлячи дисковий простір та пам'ять збіркового сервера.

```cmake
target_precompile_headers(core_lib
    PUBLIC
        <vector>
        <string>
        <memory>
    PRIVATE
        "src/internal_utils.h"
)
```

## Генераторні вирази у вимогах вжитку

Генераторні вирази оцінюються на етапі генерації збіркових файлів. Вони мають вигляд `$<ІМ'Я_ВИРАЗУ:...>` і дозволяють налаштовувати вимоги вжитку динамічно, залежно від типу компілятора, платформи чи активної конфігурації.

### 1. Розділення середовищ збірки та інсталяції

* **`$<BUILD_INTERFACE:...>`** — розгортається у вказане значення лише під час збірки цілей всередині поточного дерева проєкту. Під час створення експортного опису інсталяції перетворюється на порожній рядок.
* **`$<INSTALL_INTERFACE:...>`** — активується лише в експортованих цілях, згенерованих командою `install(EXPORT)`. Під час локальної розробки в дереві коду цей вираз ігнорується.

```cmake
target_include_directories(math_sdk
    PUBLIC
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
        $<INSTALL_INTERFACE:include>
)
```

### 2. Умовні вирази середовища та компілятора

* **`$<CXX_COMPILER_ID:ids...>`** — перевіряє ідентифікатор активного компілятора (`GNU`, `Clang`, `AppleClang`, `MSVC`, `IntelLLVM`).
* **`$<CONFIG:configs...>`** — повертає `1`, якщо поточна конфігурація збірки відповідає вказаній (`Debug`, `Release`, `RelWithDebInfo`, `MinSizeRel`).
* **`$<COMPILE_LANGUAGE:langs...>`** — перевіряє мову поточного трансльованого файла (`C`, `CXX`, `CUDA`, `ASM`).
* **`$<COMPILE_LANG_AND_ID:lang,ids...>`** — перевіряє комбінацію мови та ідентифікатора компілятора одночасно.
* **`$<PLATFORM_ID:platforms...>`** — перевіряє цільову операційну систему (`Linux`, `Windows`, `Darwin`, `Android`).

```cmake
target_compile_definitions(platform_adapter
    PUBLIC
        $<$<PLATFORM_ID:Windows>:WIN32_LEAN_AND_MEAN>
        $<$<PLATFORM_ID:Linux>:_GNU_SOURCE>
)
```

### 3. Динамічне читання властивостей споживача

* **`$<TARGET_PROPERTY:prop>`** — читає значення властивості безпосереднього споживача, до якого приєднано вимогу вжитку.
* **`$<TARGET_PROPERTY:tgt,prop>`** — читає значення вказаної властивості конкретної цілі `tgt`.

## Механізм сумісності інтерфейсів: COMPATIBLE_INTERFACE

Для складних бібліотечних екосистем CMake надає інструмент валідації сумісності вимог між незалежними вузлами графа залежностей. Це запобігає ситуаціям, коли дві підключені бібліотеки вимагають суперечливих глобальних налаштувань.

### Керуючі властивості сумісності

1. **`COMPATIBLE_INTERFACE_BOOL`** — список назв властивостей, які повинні мати однакове логічне значення (`1`/`0`, `ON`/`OFF`, `TRUE`/`FALSE`) у всіх цілей уздовж усього шляху транзитивності.
2. **`COMPATIBLE_INTERFACE_STRING`** — список назв властивостей, які повинні мати однакове рядкове значення серед усіх об'єднаних залежностей.
3. **`COMPATIBLE_INTERFACE_NUMBER_MAX`** — автоматично знаходить і застосовує максимальне числове значення властивості серед усіх учасників графа.
4. **`COMPATIBLE_INTERFACE_NUMBER_MIN`** — автоматично знаходить і застосовує мінімальне числове значення властивості.

```cmake
# Визначення сумісності конфігурації апаратного буфера
add_library(hal_driver STATIC hal.cpp)
set_target_properties(hal_driver PROPERTIES
    INTERFACE_DMA_ALIGNMENT "64"
    COMPATIBLE_INTERFACE_NUMBER_MAX DMA_ALIGNMENT
)
```

Якщо інша підключена бібліотека вимагає `DMA_ALIGNMENT` зі значенням `128`, CMake автоматично підніме значення для фінального споживача до `128`. Якщо ж буде виявлено суперечність у властивості, зареєстрованій у `COMPATIBLE_INTERFACE_BOOL`, генератор зупинить роботу з детальним повідомленням про конфлікт модулів.

## Політики CMake навколо вимог вжитку

Стабільність моделі вимог вжитку гарантується набором вбудованих політик сумісності (CMake Policies):

* **`CMP0021`** (CMake 2.8.12): забороняє використання відносних шляхів безпосередньо у властивості `INCLUDE_DIRECTORIES`. Усі шляхи мають бути або абсолютними, або загорнутими у генераторні вирази `$<BUILD_INTERFACE>` чи `$<INSTALL_INTERFACE>`.
* **`CMP0022`** (CMake 2.8.12): визначає, що транзитивні залежності лінкування для інтерфейсу беруться виключно з властивості `INTERFACE_LINK_LIBRARIES`, усуваючи застаріле неконтрольоване дублювання вмісту `LINK_LIBRARIES`.
* **`CMP0023`** (CMake 2.8.12): запроваджує сувору заборону змішування викликів `target_link_libraries` із ключовими словами (`PUBLIC`, `PRIVATE`, `INTERFACE`) та застарілих викликів без ключових слів у межах визначення однієї цілі.
* **`CMP0041`** (CMake 3.0): вимагає, щоб будь-яке звернення до невідомої цілі у властивості `INTERFACE_LINK_LIBRARIES` призводило до помилки під час генерації проєкту, захищаючи від непомічених одруківок.
* **`CMP0079`** (CMake 3.13): дозволяє викликати команду `target_link_libraries` над цілями, які були оголошені в інших підкаталогах дерева збірки, уможливлюючи гнучке налаштування залежностей без підняття змінних у глобальну область.

## Діагностика та інспектування властивостей

### Програмне інспектування в CMakeLists.txt

Для читання параметрів цілей під час конфігурації застосовується команда `get_target_property`:

```cmake
# Отримання списку внутрішніх каталогів включення
get_target_property(local_dirs my_target INCLUDE_DIRECTORIES)
message(STATUS "Власні каталоги: ${local_dirs}")

# Отримання списку експортних вимог включення
get_target_property(iface_dirs my_target INTERFACE_INCLUDE_DIRECTORIES)
message(STATUS "Експортні каталоги: ${iface_dirs}")

# Отримання списку прямих залежностей
get_target_property(link_list my_target LINK_LIBRARIES)
message(STATUS "Залежності лінкування: ${link_list}")
```

Якщо властивість не була задана на цілі, команда повертає спеціальне значення `<змінна>-NOTFOUND`, яке в умовних виразах `if()` оцінюється як хиба (`FALSE`).

### Трасування властивостей змінною CMAKE_DEBUG_TARGET_PROPERTIES

Для детального відстеження того, чому конкретна властивість отримала своє значення і які залежності вплинули на неї, CMake підтримує змінну `CMAKE_DEBUG_TARGET_PROPERTIES`:

```cmake
set(CMAKE_DEBUG_TARGET_PROPERTIES
    INCLUDE_DIRECTORIES
    COMPILE_DEFINITIONS
    POSITION_INDEPENDENT_CODE
)
```

Під час генерації CMake виведе в консоль покроковий журнал: яка бібліотека і яке значення додала до зазначених властивостей кожної цілі проєкту.

### Генерація та налаштування графа Graphviz

CMake дозволяє керувати виглядом згенерованого графа залежностей за допомогою спеціального файлу конфігурації `CMakeGraphVizOptions.cmake`, розташованого в корені проєкту:

```cmake
# CMakeGraphVizOptions.cmake
set(GRAPHVIZ_GRAPH_NAME "ArchitectureDependencies")
set(GRAPHVIZ_GRAPH_HEADER "node [fontsize=10, fontname=\"Arial\"];")
set(GRAPHVIZ_GENERATE_PER_TARGET ON)
set(GRAPHVIZ_IGNORE_TARGETS ".*_test;.*_benchmark")
set(GRAPHVIZ_STATIC_LIBS ON)
set(GRAPHVIZ_SHARED_LIBS ON)
set(GRAPHVIZ_INTERFACE_LIBS ON)
```

Запуск генерації здійснюється стандартною командою:
```bash
cmake --graphviz=build/project_graph.dot -B build
dot -Tsvg build/project_graph.dot -o build/project_graph.svg
```

Ці параметри дозволяють фільтрувати допоміжні тестові цілі та зосереджуватися виключно на аналізі архітектурних зв'язків між виробничими бібліотеками системи.
