Один і той самий вихідний файл на C++20 без жодних зауважень транслюється компілятором GCC на Linux, але при збірці через Clang оптимізатор мовчки викидає перевірку покажчика на нуль через виведення невизначеної поведінки, а при спробі зібрати його через MSVC під Windows компілятор зупиняється з синтаксичною помилкою у варіативному макросі, бо порожній список аргументів не поглинув попередню кому. Якщо ж розробник подолає етап компіляції і спробує передати екземпляр класу з віртуальним успадкуванням із динамічної бібліотеки, зібраної MinGW, у програму, скомпільовану MSVC, процес аварійно завершиться з помилкою захисту пам'яті (Access Violation) на першому ж виклику віртуального методу.

Причина таких розбіжностей криється у природі стандартів C та C++. Міжнародний комітет ISO стандартизує лише синтаксис і семантику абстрактної машини (мови вихідного коду), проте свідомо залишає за межами стандарту синтаксис командного рядка, мову вбудованого асемблера, модель оптимізації, структуру двійкового інтерфейсу (Application Binary Interface, ABI) та розташування об'єктів у пам'яті. Усі ці рішення приймаються авторами конкретних компіляторів. На практиці сучасний світ C та C++ утримують три головні родини компіляторних рушіїв: **GCC** (GNU Compiler Collection), **Clang/LLVM** та **MSVC** (Microsoft Visual C++). Знання їхніх внутрішніх відмінностей — це межа, що відділяє наївний код від надійних міжплатформних систем збірки.

## Архітектура трьох рушіїв: моноліт проти модульних бібліотек

Хоча всі три системи розв'язують однакову задачу — перетворити текст програми на машинний код цільового процесора, їхня внутрішня архітектура відображає принципово різні епохи та інженерні філософії.

![Порівняння архітектурних конвеєрів GCC, Clang/LLVM та MSVC](/root/sys/sys-bsystem/compiler-families/img/pipeline-comparison.svg)

*Архітектурні моделі трьох компіляторів: монолітний конвеєр GCC з GIMPLE та RTL, модульна бібліотечна структура Clang з універсальним LLVM IR, та двофазна схема MSVC з роздільними c1/c1xx та C2/UTC бекендом.*

### GCC: класичний монолітний конвеєр

GCC створювався у середині 1980-х років як основа вільної операційної системи GNU. Його головний архітектурний принцип — глибока інтеграція етапів аналізу та оптимізації.

Коли користувач викликає драйвер `gcc` або `g++`, цей процес не компілює код сам, а послідовно запускає внутрішні програми:
1. **Фронтенд (`cc1` для C, `cc1plus` для C++):** виконує лексичний аналіз, парсинг і семантичну перевірку, перетворюючи сирцевий текст на первинне абстрактне синтаксичне дерево (AST), яке одразу спрощується до представлення **GENERIC**.
2. **GIMPLE (Tree-SSA):** GENERIC перетворюється на GIMPLE — проміжне представлення у формі триадресного коду, де складні вирази розбиваються на елементарні операції з тимчасовими змінними. На цьому рівні GCC будує граф потоку керування (Control Flow Graph, CFG) і застосовує високорівневі машинно-незалежні оптимізації у статичній формі єдиного присвоєння (Static Single Assignment, SSA): усунення мертвих гілок, поширення констант, векторизацію циклів.
3. **RTL (Register Transfer Language):** оптимізований GIMPLE транслюється в низькорівневе квазі-асемблерне представлення RTL. На рівні RTL GCC моделює віртуальний процесор із нескінченною кількістю псевдорегістрів, виконує планування інструкцій, підбір машинних інструкцій цільового процесора та виділення фізичних регістрів (Register Allocation).
4. **Асемблер і лінкер:** GCC не генерує об'єктні двійкові файли самостійно. Він записує текстовий файл асемблера (`.s`) на диск або у пайп і викликає зовнішній системний асемблер `as` (з пакету GNU Binutils), після чого для формування фінального файлу запускає компонувальник `ld` (або сучасні `gold`, `mold`, `lld`).

Через історичне небажання авторів GNU створювати закриті форки компілятора, внутрішні структури GCC довгий час навмисно не мали стабільного API для вбудовування у сторонні середовища розробки (IDE) чи аналізатори.

### Clang та LLVM: компілятор як набір C++ бібліотек

Проєкт Clang створювався на початку 2000-х років у компанії Apple (під керівництвом Кріса Латтнера) з метою подолати обмеження монолітної структури GCC. Його ключова ідея: компілятор — це не монолітна утиліта, а **набір незалежних C++ бібліотек**.

Конвеєр Clang/LLVM побудований навколо суворого розділення фронтенду та бекенду:
1. **Фронтенд Clang (`libclang`):** виконує синтаксичний та семантичний аналіз і будує багате, точне AST (Clang AST), яке повністю зберігає інформацію про вихідний текст (включно з позиціями кожного токена, коментарями та макросами). Завдяки цьому Clang є не лише компілятором, а й основою для інструментів рефакторингу (`clang-tidy`, `clang-format`) та мовних серверів (`clangd`).
2. **LLVM IR (Intermediate Representation):** фронтенд перетворює AST на універсальне, строго типізоване проміжне представлення **LLVM IR**. Воно існує у трьох ізоморфних формах: текстовій (`.ll`), двійковій у пам'яті (C++ структури класів `llvm::Instruction`) та двійковому біткоді на диску (`.bc`).
3. **Оптимізатор (`opt`):** десятки незалежних проходів оптимізації (Passes) аналізують і трансформують виключно LLVM IR. Оптимізатор нічого не знає про вихідну мову C++ — для нього існують лише базові блоки, типи, SSA-значення та інструкції завантаження/збереження пам'яті.
4. **Бекенд кодогенерації (`LLVM Target` / `MC Layer`):** модуль генерації коду бере оптимізований LLVM IR і перетворює його на інструкції цільової архітектури (x86-64, ARM, RISC-V, WebAssembly). Завдяки вбудованому підрівню машинного коду (Machine Code, MC) Clang має **інтегрований асемблер** і безпосередньо створює об'єктні файли ELF, Mach-O або PE/COFF без виклику зовнішнього `as`.

Clang може виступати у двох ролях: як звичайний компілятор `clang`/`clang++` (з інтерфейсом прапорців командного рядка, ідентичним GCC) або як `clang-cl` — спеціальний драйвер для Windows, що повністю мімікрує під поведінку та прапорці MSVC.

### MSVC: пропрієтарний двофазний конвеєр Windows

Компілятор Microsoft Visual C++ (`cl.exe`) розвивався протягом трьох десятиліть як основа операційної системи Windows та середовища Visual Studio. Його архітектура розділена на дві чітко розмежовані компоненти:
1. **Фронтенд (`c1.dll` для C, `c1xx.dll` для C++):** розбирає вихідні файли, розгортає макроси, перевіряє типи та будує власне внутрішнє дерево. Фронтенд транслює код у внутрішнє проміжне представлення Microsoft Intermediate Language (CIL/IL).
2. **Бекенд UTC / C2 (`c2.dll`):** універсальний оптимізатор і генератор коду (Universal Target Compiler / C2). Цей самий бекенд історично використовувався не лише для C/C++, а й для кодогенерації з Fortran та ранніх версій .NET Native. Бекенд виконує глобальну оптимізацію, розміщення регістрів і напряму генерує об'єктні файли у форматі Microsoft COFF (`.obj`).
3. **Компонувальник (`link.exe`):** системний лінкер Windows збирає об'єктні файли COFF у виконувані файли PE (`.exe`) або динамічні бібліотеки (`.dll`), формуючи також файл налагоджувальних символів PDB (Program Database).

## Синтаксис командного рядка та модель конфігурації

Найбільш помітна для систем збірки відмінність — це несумісність інтерфейсу командного рядка (Command Line Interface, CLI). POSIX-тулчейни (GCC та Clang) використовують префікс тире (`-`), тоді як MSVC історично спирається на синтаксис MS-DOS з прямим слешем (`/`), хоча для більшості простих ключів приймає і тире.

### Рівні оптимізації

У GCC та Clang шкала оптимізації є лінійною і керується ключами `-O`:
- `-O0`: оптимізації вимкнено (режим налагодження);
- `-O1`: базові оптимізації без суттєвого уповільнення збірки;
- `-O2`: стандартна виробнича оптимізація. Вмикає інлайнінг, усунення спільних підвиразів, векторизацію;
- `-O3`: агресивна оптимізація. Додатково вмикає агресивне розгортання циклів, автовекторизацію з перевпорядкуванням пам'яті та міжпроцедурний аналіз;
- `-Os`: оптимізація за розміром (вимикає роздування коду);
- `-Oz` (лише в Clang): екстремальна оптимізація за розміром, де швидкість повністю приноситься в жертву компактності машинних інструкцій;
- `-Og`: оптимізація для комфортного налагодження (зберігає відповідність змінних та номерів рядків у GDB/LLDB).

У MSVC логіка інша:
- `/Od`: вимикає оптимізацію (Debug);
- `/O1`: оптимізація за мінімальним розміром (еквівалент `/Og /Os /Oy /Ob2 /Gs /GF /Gy`);
- `/O2`: оптимізація за максимальною швидкістю (еквівалент `/Og /Oi /Ot /Oy /Ob2 /Gs /GF /Gy`);
- `/Ox`: застарілий прапорець «максимальної оптимізації» (у сучасних версіях тотожний `/O2`).

Прапорця, еквівалентного `-O3`, в MSVC **немає взагалі**. Якщо система збірки без адаптації передасть `/O3` у `cl.exe`, компілятор завершить роботу з фатальною помилкою `D8021: invalid numeric argument '/O3'`.

Повна порівняльна таблиця прапорців для всіх рівнів оптимізації, генерації коду та режимів сумісності винесена в окрему довідкову вставку [Зведена таблиця прапорців, макросів та інтринсиків](root:sys-bsystem/compiler-families/api-flags-and-intrinsics.md).

### Рівні діагностики та суворості попереджень

Діагностичні шкали мають суттєву асиметрію, через яку наївне перенесення прапорців ламає збірку.

У GCC та Clang:
- `-Wall`: вмикає базовий, перевірений набір попереджень щодо поширених помилок;
- `-Wextra`: додає додаткові суворі перевірки (невживані параметри, порівняння знакових і беззнакових чисел);
- `-Wpedantic`: вимагає суворої відповідності стандарту ISO, відхиляючи нестандартні розширення;
- `-Werror`: перетворює всі попередження на фатальні помилки збірки.

У MSVC:
- `/W1` ... `/W4`: шкала суворості. Виробничим стандартом для надійного коду під Windows є `/W4`;
- `/Wall`: вмикає **абсолютно всі** попередження компілятора, включно з інформаційними (наприклад, попередження про те, що компілятор успішно вбудував функцію за допомогою inline). Системні заголовки Windows SDK не можуть скомпілюватися з `/Wall` без сотень попереджень, тому використання `/Wall` у реальних проєктах вимагає складного приглушення діагностики;
- `/WX`: еквівалент `-Werror` (попередження як помилки).

### Керування стандартом мови та прапорець `/Zc`

Вибір стандарту C++ у GCC та Clang виконується прапорцями `-std=c++17`, `-std=c++20`, `-std=c++23` (або `-std=gnu++XX`, якщо потрібні розширення).

У MSVC стандарт задається як `/std:c++17`, `/std:c++20` або `/std:c++latest`. Проте тут криється підступна пастка: навіть якщо передано `/std:c++20`, MSVC за замовчуванням визначає службовий макрос `__cplusplus` як `199711L` (значення C++98!). Це було зроблено для сумісності з мільйонами рядків старого коду, де логіка заголовків покладалася на конкретне старе число. Щоб MSVC повертав стандартне значення (наприклад, `202002L` для C++20), розробник зобов'язаний явно передати прапорець конформансу:

```
cl.exe /std:c++20 /Zc:__cplusplus /permissive- main.cpp
```

Прапорець `/permissive-` вимикає застарілі послаблення мови Microsoft (вмикає справжній двоетапний пошук імен у шаблонах), а префікс `/Zc:` (Conformance) керує десятками дрібних стандартних поведінок: `/Zc:inline`, `/Zc:strictStrings`, `/Zc:throwingNew`.

### Файли відповідей (Response Files)

Коли довжина рядка виклику лінкера чи компілятора перевищує ліміт операційної системи (наприклад, ліміт Windows `CreateProcess` у 32767 символів), системи збірки записують список об'єктних файлів і ключів у текстовий файл відповідей:

```
gcc @objects.rsp -o app
cl.exe @objects.rsp /Fe:app.exe
```

Розбіжність полягає в інтерпретації вмісту:
- GCC та Clang розглядають переноси рядків і пробіли як розділювачі аргументів, а зворотний слеш `\` сприймають як екранування (escape-символ). Шлях до файлу `C:\tools\lib.a` у файлі відповідей GCC буде прочитаний з помилкою як `C:toolslib.a`, якщо слеші не подвоєно (`C:\\tools\\lib.a`) або не замінено на прямі (`C:/tools/lib.a`).
- MSVC у файлах відповідей інтерпретує зворотний слеш `\` як звичайний розділювач шляхів Windows і вимагає взяття шляхів із пробілами у подвійні лапки.

## Препроцесорні розбіжності та пастки макросів

Препроцесор часто вважають найпростішим етапом збірки, проте саме тут криються підступні розбіжності між компіляторами.

### Традиційний препроцесор MSVC проти стандарту

Історичний препроцесор MSVC (розроблений ще для C89) не відповідав алгоритмам розгортання макросів, зафіксованим у стандарті ISO C99 / C++11. Він обчислював аргументи макросів «жадібно» (eager evaluation) до передачі їх усередину іншого макросу та некоректно поводився при склеюванні токенів (`##`) і заміні рядків (`#`). Через це бібліотеки метапрограмування на зразок `Boost.Preprocessor` містили окремі гілки коду з обхідними шляхами спеціально під MSVC.

У сучасних версіях Visual Studio (починаючи з VS 2019 v16.6) додано новий, повністю стандартний препроцесор, який активується прапорцем `/Zc:preprocessor`.

### Варіативні макроси та порожній хвіст аргументів

Класична проблема препроцесора — створення макросу логування з довільною кількістю параметрів:

```
#define LOG_PRINT(fmt, ...) printf(fmt, __VA_ARGS__)
```

Якщо викликати цей макрос без додаткових аргументів: `LOG_PRINT("Error occurred\n")`, він розгорнеться у неприпустиму конструкцію з висячою комою: `printf("Error occurred\n", )`.

Кожен компілятор історично вирішував цю проблему по-своєму:
1. **GCC та Clang** ввели нестандартне розширення `, ##__VA_ARGS__`: оператор склеювання `##`, поставлений між комою та `__VA_ARGS__`, примусово видаляє кому, якщо список варіативних аргументів порожній.
2. **Традиційний MSVC** автоматично ковтав кому перед `__VA_ARGS__` без жодних додаткових символів, що порушувало стандарт, але маскувало проблему.
3. **Стандарт C++20** нарешті уніфікував рішення через спеціальний функціональний макрос `__VA_OPT__(,)`:

:::tabs
```c
#include <stdio.h>

// Сумісний C-макрос із розширенням GNU/Clang
#if defined(__GNUC__) || defined(__clang__)
#define LOG_MSG(fmt, ...) printf("[LOG] " fmt "\n", ##__VA_ARGS__)
#elif defined(_MSC_VER)
#define LOG_MSG(fmt, ...) printf("[LOG] " fmt "\n", __VA_ARGS__)
#endif

void run_c_demo(void) {
    LOG_MSG("System initialized");
    LOG_MSG("Values: %d, %d", 10, 20);
}
```
```cpp
#include <iostream>
#include <format>
#include <string_view>

// Стандартний C++20 підхід з використанням __VA_OPT__ та std::format
#define LOG_MSG_CPP(fmt_str, ...) \
    std::cout << std::format("[LOG] " fmt_str "\n" __VA_OPT__(,) __VA_ARGS__)
```

### Визначення унікальності файлу в `#pragma once`

Директива `#pragma once` підтримується всіма трьома компіляторами як швидша альтернатива традиційним загороджувачам (`#ifndef / #define / #endif`), оскільки запобігає повторному читанню та парсингу файлу з диска. Проте спосіб ідентифікації того, що два шляхи вказують на **один і той самий файл**, кардинально різниться:

- **GCC та Clang (на POSIX-системах):** компілятор виконує системний виклик `stat()` над файлом і використовує кортеж `(st_dev, st_ino)` — номер пристрою та номер inode файлової системи. Навіть якщо заголовок включено через відносний шлях, абсолютний шлях чи символьне посилання, він має той самий inode, тому компілятор миттєво розпізнає дублікат.
- **MSVC (та Clang-cl на Windows):** у файлових системах Windows концепція inode відсутня або не гарантує стабільності для швидких запитів, тому препроцесор виконує нормалізацію текстового шляху (path normalization / canonicalization). Якщо один і той самий файл доступний через різні шляхи монтування (наприклад, мережевий диск Samba `\\server\share\header.h` та підключений диск `Z:\header.h`), або якщо в проєкті використовуються жорсткі посилання (hard links), MSVC вважатиме їх двома **різними** файлами і включить заголовок двічі, що призведе до помилок повторного оголошення типів (`redefinition of 'struct'`).

## Мовні розширення, атрибути та вбудований асемблер

Керування низькорівневою поведінкою кодогенератора — ще одна зона глибокого розколу.

### Синтаксис атрибутів

Історично кожна родина створила власний синтаксис атрибутів:
- **GNU (GCC / Clang):** `__attribute__((і'мя_атрибута))`
- **MSVC:** `__declspec(ім'я_специфікатора)`
- **Стандарт C++11:** уніфікований синтаксис квадратних дужок `[[ім'я_атрибута]]` з підтримкою префіксів просторів імен (`[[gnu::...]]`, `[[msvc::...]]`).

### Експорт символів та модель видимості

У форматі **ELF** (Linux) за замовчуванням діє відкрита модель: кожен глобальний символ (функція, змінна чи клас), оголошений у коді, потрапляє у динамічну таблицю символів `.dynsym` і є доступним для зв'язування ззовні. Щоб захистити внутрішні функції бібліотеки від експорту та прискорити час завантаження через оптимізацію таблиці переміщень (GOT/PLT), у GCC/Clang застосовують прапорець `-fvisibility=hidden` та явно відкривають потрібні функції атрибутом `__attribute__((visibility("default")))`.

У форматі **PE/COFF** (Windows) діє діаметрально протилежна закрита модель: за замовчуванням кожен символ усередині DLL є прихованим. Щоб зробити функцію видимою для зовнішніх програм, її обов'язково треба позначити як `__declspec(dllexport)`. При цьому у коді споживача цієї DLL та сама функція у заголовку має бути позначена як `__declspec(dllimport)` — це дозволяє компілятору генерувати прямі інструкції виклику через таблицю адрес імпорту (IAT) замість створення проміжних функцій-заглушок.

### Вбудований асемблер (Inline Assembly)

Розбіжність у підтримці асемблерного коду безпосередньо в тілі функцій C/C++ є однією з найглибших:

1. **GCC та Clang (GNU Extended Assembly):** використовують розширений синтаксис з описом вхідних/вихідних регістрів та списку зіпсованих регістрів (clobbers):
   ```
   asm volatile ("mov %1, %0" : "=r"(dst) : "r"(src) : "memory");
   ```
   За замовчуванням очікується синтаксис AT&T (де джерело стоїть перед приймачем), хоча прапорець `-masm=intel` дозволяє синтаксис Intel. Оптимізатор GCC повністю розуміє зв'язки між асемблерним рядком і C-змінними.

2. **MSVC на x86 (32 біти):** підтримує простий блок `__asm { ... }` з синтаксисом Intel.

3. **MSVC на x86-64 та ARM64 (64 біти):** **повністю видалив підтримку `__asm`**. В інженерів Microsoft оптимізатор бекенда C2 спирається на побудову глобального графа потоку даних SSA; непрозорі асемблерні вставки у 64-розрядному режимі руйнували оптимізацію регістрів і планування інструкцій. Тому для 64-бітних платформ під MSVC розробники зобов'язані використовувати або готові компіляторні інтринсики (Intrinsics), або виносити асемблерний код в окремі `.asm` файли та транслювати їх зовнішнім асемблером `ml64.exe` (MASM).

## Двійковий розкол: Itanium C++ ABI проти Microsoft Visual C++ ABI

Найважливіша фундаментальна розбіжність між світами — це несумісність двійкових інтерфейсів (C++ ABI). ABI визначає, як саме високорівневі сутності мови C++ кодуються у машинних байтах об'єктного файлу: як спотворюються (mangle) імена функцій, де в пам'яті розташовуються віртуальні таблиці та як працює розмотка стеку при викиданні винятків.

У сучасному комп'ютерному світі існують два головні стандарти ABI для C++:
1. **Itanium C++ ABI:** спочатку розроблений для 64-бітної архітектури Intel Itanium, цей ABI згодом став загальноприйнятим де-факто стандартом для всіх Unix-подібних систем (Linux, macOS, FreeBSD, Android, iOS), використовується GCC та Clang на будь-яких процесорах, а також портом MinGW на Windows.
2. **Microsoft Visual C++ ABI:** пропрієтарний стандарт, розроблений Microsoft для компілятора `cl.exe`, використовується у Windows і підтримується драйвером `clang-cl`.

### Декорація імен (Name Mangling)

Щоб підтримувати перевантаження функцій (overloading), простори імен (namespaces) та шаблони, компілятор зобов'язаний згенерувати унікальне ім'я символу для лінкера.

Розглянемо функцію:
```cpp
namespace engine {
    int calculate(double speed, int count);
}
```

- **Itanium ABI:** генерує ім'я `_ZN6engine9calculateEdi`. Воно починається з префікса `_ZN` (вкладене ім'я), далі йдуть пари «довжина_рядка + назва» (`6engine`, `9calculate`), літера `E` (завершення просторів імен) та однолітерні коди типів аргументів (`d` для double, `i` для int).
- **Microsoft C++ ABI:** генерує ім'я `?calculate@engine@@YAHNNAH@Z`. Воно починається зі знаку `?`, після чого йде назва функції, розділювачі просторів імен `@`, коди угоди про виклики та типи повернення й параметрів у складній системі алфавітних індексів.

Оскільки схеми декорування імен кардинально різні, об'єктний файл `.o`, скомпільований GCC, принципово неможливо напряму злінкувати з кодом MSVC: лінкер просто не знайде відповідних символів і завершиться помилкою `unresolved external symbol`.

### Розташування об'єктів у пам'яті та віртуальні таблиці (Vtables)

Коли клас має віртуальні методи, компілятор додає до об'єкта прихований покажчик на таблицю віртуальних функцій (`vptr`). Проте внутрішня структура цієї таблиці в обох ABI радикально різниться, особливо при множинному та віртуальному успадкуванні.

![Розташування об'єкта та таблиць віртуальних функцій в Itanium C++ ABI та Microsoft C++ ABI](/root/sys/sys-bsystem/compiler-families/img/vtable-layout-abi.svg)

*Двійковий розкол: в Itanium C++ ABI зсуви віртуальних баз зберігаються у спільній vtable за від'ємними індексами, тоді як у Microsoft C++ ABI для віртуального успадкування генерується окрема таблиця vbtbl та окремий покажчик vbptr.*

1. **Одиничне та множинне успадкування:**
   - В **Itanium ABI** об'єкт похідного класу містить основний `vptr` на початку. Якщо клас успадковує кілька базових класів з віртуальними функціями, створюються вторинні віртуальні таблиці для кожної бази. Якщо метод викликається через покажчик на другу базу, адреса покажчика `this` повинна зміститися. Для цього Itanium генерує спеціальні мікро-функції перехідники — **Thunks**, які віднімають необхідний зсув від регістра `rdi`/`rcx` перед стрибком на цільовий метод.
   - У **Microsoft C++ ABI** таблиця віртуальних функцій зветься `vftbl` (*virtual function table*), а покажчик у тілі об'єкта — `vftptr`. Для зміни адреси `this` MSVC генерує записи thunk безпосередньо у коді виклику або секції перехідників.

2. **Віртуальне успадкування (Virtual Inheritance):**
   - В **Itanium ABI** вся інформація про зміщення віртуальних базових класів (virtual base offset) зберігається **в тій самій таблиці vtable**, але за **від'ємними індексами** перед точкою, на яку вказує `vptr`. Також там зберігається зміщення до вершини об'єкта (`offset-to-top`) та покажчик на структуру RTTI `type_info`. Об'єкт залишається компактним і містить лише один `vptr` для первинної ієрархії.
   - У **Microsoft C++ ABI** віртуальні функції та віртуальні бази повністю розділені! Для знаходження віртуальної бази компілятор додає в об'єкт **другий прихований покажчик** — `vbptr` (*virtual base pointer*), який вказує на окрему таблицю **`vbtbl`** (*virtual base table*). Через це один і той самий об'єкт у MSVC має більший розмір у пам'яті (додаткові 8 байтів на x64 для кожного `vbptr`), ніж в Itanium ABI.

### Покажчики на методи класів (Pointer-to-Member)

Розмір і представлення покажчика на метод класу (`void (MyClass::*ptr)()`) — одна з найбільш вражаючих розбіжностей у дизайні:

- **В Itanium ABI** покажчик на метод завжди має **фіксований розмір** — рівно 16 байтів (на 64-бітній системі). Він складається зі структури двох полів: безпосередньої адреси функції (або індексу у vtable, якщо молодший біт встановлено в 1) та числового зсуву покажчика `this` (`adj`). Ця структура універсальна для будь-якого класу — простого, з множинним чи віртуальним успадкуванням.

- **У Microsoft C++ ABI** розмір покажчика на метод є **динамічним і залежить від ієрархії класу**:
  - Для простого класу (без множинного успадкування): **8 байтів** (простий покажчик на код функції);
  - Для класу з множинним успадкуванням: **16 байтів** (адреса функції + зсув `this`);
  - Для класу з віртуальним успадкуванням: **24 байти** (адреса функції + зсув `this` + зсув у `vbtbl`);
  - Для класу з невідомим на момент оголошення успадкуванням (forward declaration): **32 байти** (прапорці `/vmg`, `/vms`, `/vmm`, `/vmv`).

Якщо ви оголосите покажчик на метод неповного типу (`class Widget; void (Widget::*fn)();`), а потім спробуєте присвоїти йому метод скомпільованого класу, розміри структур не зійдуться, що призведе до розвалу пам'яті стеку, якщо не керувати прапорцями представлення моделей спадкування в MSVC.

### Моделі обробки винятків (Exception Handling)

Коли у програмі виконується оператор `throw`, рантайм компілятора повинен знайти найближчий відповідний блок `catch`, розмотати кадри стеку та викликати деструктори всіх локальних об'єктів, створених на пройдених ділянках стеку.

![Схеми пошуку обробників та розмотки стеку при винятку в Itanium ABI та Windows SEH](/root/sys/sys-bsystem/compiler-families/img/exception-unwinding.svg)

*Таблична обробка винятків: двофазний пошук та розмотка стеку в Itanium ABI через .eh_frame / DWARF CFI проти 64-розрядної моделі Windows SEH через секцію .pdata та обробник __CxxFrameHandler.*

1. **Itanium C++ ABI (Таблична модель DWARF / Zero-Cost):**
   - У нормальному режимі виконання (коли винятки не викидаються) накладні витрати на блоки `try/catch` дорівнюють нулю (Zero-Cost Exceptions): процесор не виконує жодних додаткових інструкцій реєстрації обробників.
   - Компілятор розміщує у двійковому файлі статичні метадані у секції `.eh_frame` (інформація про кадри виклику у форматі DWARF Call Frame Information, CFI) та секції `.gcc_except_table` (Language-Specific Data Area, LSDA).
   - При виклику `throw` запускається системна бібліотека розмотування `libunwind` і викликає функцію `_Unwind_RaiseException`.
   - Розмотка виконується у дві фази:
     - **Фаза 1 (Search):** бібліотека розмотування піднімається вгору стеком, читаючи `.eh_frame`, та для кожного кадру викликає функцію-особистість (`personality routine`, у GCC/Clang це `__gxx_personality_v0`). Особистість звіряє тип винятку з таблицею LSDA і визначає, чи є відповідний `catch`.
     - **Фаза 2 (Cleanup):** знаючи цільовий кадр, розмотувач повторно проходить стек угору, викликає деструктори локальних об'єктів (Cleanups) для кожного проміжного кадру і передає керування в блок `catch`.

2. **Microsoft C++ ABI (Windows Structured Exception Handling / SEH):**
   - На 32-розрядній системі x86 MSVC будував зв'язаний список обробників винятків безпосередньо на стеку під час входу в кожну функцію (що не було zero-cost).
   - На 64-розрядній системі x86-64 Windows реалізує zero-cost табличну модель SEH на рівні ядра операційної системи (`ntdll.dll`). Компілятор генерує секцію **`.pdata`** (масив структур `RUNTIME_FUNCTION`, що зіставляє діапазони адрес інструкцій зі зміщеннями на кадри) та секцію **`.xdata`** (детальні структури `UNWIND_INFO`).
   - Коли виникає C++ виняток, рантайм C++ викликає системну функцію `RaiseException`, передаючи магічний код помилки `0xE06D7363` (що в ASCII розшифровується як `msc`).
   - Ядро операційної системи бере на себе керування і викликає внутрішню функцію особистості компілятора — **`__CxxFrameHandler3`** або сучасний **`__CxxFrameHandler4`**. Цей обробник аналізує таблицю внутрішніх станів функції (State Index), де кожному локальному об'єкту присвоєно номер стану, викликає необхідні деструктори через системний виклик `RtlUnwindEx` і передає керування в блок `catch`.

Через несумісність рантаймів розмотування виняток C++, викинутий із коду MinGW/GCC на Windows, не може бути перехоплений блоком `catch` у коді MSVC і призведе до негайного виклику `std::terminate`.

## Гібридні світи та сумісність: Clang-cl, MinGW-w64 та стандартні бібліотеки

На практиці інженерам часто доводиться змішувати компіляторні технології. Розгляньмо, як ці світи взаємодіють між собою.

### Clang-cl: роздвоєння особистості Clang

Команда розробників Clang створила драйвер `clang-cl.exe`, щоб дати розробникам під Windows швидкість оптимізації LLVM та потужну діагностику Clang без необхідності переписувати файли проєктів Visual Studio:

- Зовні `clang-cl` поводиться як повний клон `cl.exe`: він приймає прапорці `/O2`, `/std:c++20`, `/MD`, `/W4`, `/showIncludes` та розуміє синтаксис файлів відповідей.
- Усередині `clang-cl` використовує фронтенд Clang та бекенд LLVM. Найважливіше: він перемикає внутрішню кодогенерацію на **Microsoft C++ ABI**!
- `clang-cl` генерує спотворені імена у форматі MSVC (`?name@@...`), будує віртуальні таблиці `vftbl`/`vbtbl`, підтримує SEH та компілює код для роботи з Microsoft C++ Runtime (`msvcp140.dll`) та STL від Microsoft.

Завдяки цьому об'єктні файли `.obj`, скомпільовані `clang-cl`, є **на 100% бінарно сумісними** з об'єктними файлами від MSVC `cl.exe`. Їх можна безперешкодно об'єднувати в одній програмі лінкером `link.exe` або `lld-link`.

### MinGW-w64: світ GNU на платформі Windows

MinGW-w64 (Minimalist GNU for Windows) — це порт тулчейна GCC (або Clang) під Windows. MinGW використовує звичний командний рядок GNU (`-O2`, `-std=c++20`, `-Wall`), але генерує виконувані файли формату Windows PE/COFF і компонує їх із системною бібліотекою C (`msvcrt.dll` або сучасним `ucrtbase.dll`).

Головне обмеження MinGW — це його C++ ABI:
- MinGW використовує **Itanium C++ ABI**.
- Це означає, що C++ бібліотека (`.dll` або `.a`), зібрана MinGW, **бінарно несумісна** з C++ кодом від MSVC. Спроба зв'язати C++ класи, викликати перевантажені функції чи передати `std::string` між MinGW та MSVC неминуче завершиться аварією.
- Єдиний надійний спосіб взаємодії між MinGW та MSVC — це створення **чистого C-інтерфейсу** (`extern "C"`) на межі динамічної бібліотеки, де всі типи даних зведені до простих структур і покажчиків, а функції повертають числові коди помилок замість винятків C++.

### Три незалежні стандартні бібліотеки (STL)

Навіть якщо компілятор підтримує однаковий стандарт C++20, реалізація стандартної бібліотеки шаблонів є окремою незалежною кодовою базою:
1. **`libstdc++` (GNU):** стандартна бібліотека проєкту GCC. Використовується за замовчуванням у GCC на Linux та MinGW.
2. **`libc++` (LLVM):** модульна, високоефективна бібліотека проєкту LLVM. Є системною бібліотекою за замовчуванням на macOS, iOS, Android NDK та FreeBSD.
3. **`MSVC STL` (Microsoft):** повністю відкрита (Open Source) бібліотека від Microsoft, що оптимізована для Windows та інтегрована з середовищем Visual Studio.

Кожна з цих бібліотек має різне внутрішнє розташування полів у класах `std::string`, `std::vector`, `std::unique_ptr` та `std::function`. Передача екземпляра `std::string` крізь межу модулів, скомпільованих із різними STL, призводить до порушення правила єдиного визначення (One Definition Rule, ODR) та неминучого пошкодження пам'яті через різний розмір внутрішніх буферів коротких рядків (Short String Optimization, SSO).

## Практика систем збірки: як абстрагувати компіляторні розбіжності

Сучасні метасистеми збірки (насамперед CMake та Meson) беруть на себе складну роботу з нівелювання компіляторних розбіжностей.

### Визначення компілятора в CMake

CMake визначає родину компілятора під час фази конфігурації та записує її ідентифікатор у змінну `CMAKE_CXX_COMPILER_ID`:
- `"GNU"`: для компіляторів GCC;
- `"Clang"`: для Clang (націленого на Unix/ELF або MinGW);
- `"AppleClang"`: для специфічної версії Clang, що постачається Apple у складі Xcode;
- `"MSVC"`: для компілятора MSVC `cl.exe` **або** для `clang-cl` у режимі сумісності з MSVC.

Щоб відрізнити справжній `cl.exe` від `clang-cl`, CMake надає змінну `CMAKE_CXX_COMPILER_FRONTEND_VARIANT`, яка для `clang-cl` містить значення `"MSVC"`, тоді як `CMAKE_CXX_COMPILER_ID` дорівнює `"Clang"`.

### Цільові властивості проти хардкоду прапорців

Найгірша практика в системах збірки — це пряме додавання прапорців до глобальних рядків:
```cmake
# АНТИПАТЕРН: зламається на першому ж іншому компіляторі
set(CMAKE_CXX_FLAGS "-O3 -Wall -std=c++20")
```

Сучасний CMake (Modern CMake) пропонує уніфіковані цільові властивості (Target Properties), які автоматично транслюються у правильні ключі конкретного тулчейна:

```cmake
add_library(core_engine STATIC src/engine.cpp)

# 1. Керування стандартом (додасть -std=c++20 або /std:c++20)
target_compile_features(core_engine PUBLIC cxx_std_20)
set_target_properties(core_engine PROPERTIES
    CXX_EXTENSIONS OFF  # вимкне gnu++ розширення на користь чистого ISO C++
)

# 2. Керування видимістю (додасть -fvisibility=hidden на GCC/Clang)
set_target_properties(core_engine PROPERTIES
    CXX_VISIBILITY_PRESET hidden
    VISIBILITY_INLINES_HIDDEN ON
)

# 3. Попередження як помилки (додасть -Werror або /WX)
set_target_properties(core_engine PROPERTIES
    COMPILE_WARNING_AS_ERROR ON
)
```

### Генераторні вирази для тонкого налаштування

Коли необхідно передати специфічний прапорець, якого немає у стандартних властивостях CMake, використовують генераторні вирази `$<COMPILE_LANG_AND_ID:...>`:

```cmake
target_compile_options(core_engine PRIVATE
    # Набір попереджень для GCC та Clang
    $<$<CXX_COMPILER_ID:GNU,Clang,AppleClang>:
        -Wall
        -Wextra
        -Wpedantic
        -Wconversion
    >
    # Набір попереджень для MSVC та clang-cl
    $<$<CXX_COMPILER_ID:MSVC>:
        /W4
        /permissive-
        /Zc:__cplusplus
        /Zc:preprocessor
    >
)
```

Розуміння архітектурних розбіжностей між GCC, Clang та MSVC дозволяє створювати архітектуру проєкту, яка не залежить від примх конкретного компілятора, забезпечує безшовну збірку на будь-якій операційній системі та захищає бінарні модулі від прихованих пасток несумісності двійкових інтерфейсів.
