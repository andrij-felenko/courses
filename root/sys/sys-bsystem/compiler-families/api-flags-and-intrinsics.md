# Зведена таблиця прапорців, макросів та інтринсиків

Коли системний чи прикладний проєкт переноситься між компіляторами GCC, Clang та MSVC, інженер щодня стикається з тим, що одна й та сама дія (увімкнення стандарту мови, генерація оптимізованого коду, керування експортом функцій чи використання низькорівневих бітових операцій процесора) записується принципово різними ключами командного рядка, системними атрибутами та внутрішніми функціями компілятора. Ця довідкова таблиця зіставляє еквіваленти для трьох провідних родин тулчейнів, фіксує семантичні відмінності між зовні схожими прапорцями та надає готові переносні обгортки.

## Керування стандартами мови та діалектами

Компілятори суттєво різняться за замовчуваним режимом трансляції вихідного коду. GCC та Clang історично активують власні розширення мови GNU (діалекти `gnu++XX`), що дозволяють вбудований асемблер, специфічні типи даних (як-от `__int128`) та адресні мітки у виразах. На противагу їм, MSVC довгі роки підтримував застарілу модель компіляції, в якій двоетапний пошук імен (two-phase name lookup) у шаблонах був вимкнений заради сумісності зі старим кодом Windows SDK.

Окремою пасткою залишається значення службового макросу `__cplusplus`. За стандартом ISO C++, цей макрос повинен розгортатися у числове значення року та місяця затвердження стандарту (наприклад, `202002L` для C++20). Однак MSVC за замовчуванням завжди повертає `199711L` (C++98), незалежно від переданого прапорця `/std:c++17` чи `/std:c++20`. Корпорація Microsoft пішла на це через те, що величезна кількість старого пропрієтарного коду перевіряла `#if __cplusplus == 199711L` і ламалася при зміні числа. Щоб змусити MSVC повідомляти чесну версію стандарту, розробник зобов'язаний явно передавати прапорець `/Zc:__cplusplus`.

| Призначення | GCC | Clang / Clang-cl | MSVC (`cl.exe`) | Примітки та пастки |
| :--- | :--- | :--- | :--- | :--- |
| **Стандарт C++17** | `-std=c++17` | `-std=c++17` або `/std:c++17` | `/std:c++17` | GCC/Clang за замовчуванням мають `-std=gnu++17` (з розширеннями typeof, asm). |
| **Стандарт C++20** | `-std=c++20` | `-std=c++20` або `/std:c++20` | `/std:c++20` | MSVC автоматично активує суворий режим відповідності стандартам. |
| **Сувора відповідність ISO** | `-pedantic-errors` | `-pedantic-errors` | `/permissive-` | `/permissive-` вимикає специфічні розширення Microsoft C++ (двоетапний пошук імен). |
| **Коректний макрос `__cplusplus`** | Завжди коректний | Завжди коректний | `/Zc:__cplusplus` | Без цього прапорця MSVC визначає `__cplusplus` як `199711L` заради сумісності зі старим кодом. |
| **Стандартний препроцесор** | За замовчуванням | За замовчуванням | `/Zc:preprocessor` | Вмикає препроцесор, що відповідає стандарту C99/C++11/C++20 (правильне розгортання `__VA_ARGS__`). |
| **Стандарт C11 / C17** | `-std=c11` / `-std=c17` | `-std=c11` / `-std=c17` | `/std:c11` / `/std:c17` | Підтримка C11/C17 у MSVC з'явилася починаючи з Visual Studio 2019 v16.8. |

## Рівні оптимізації та кодогенерація

Модель оптимізації POSIX-компіляторів базується на ієрархії рівнів від `-O0` до `-O3`, тоді як MSVC використовує комбінації прапорців `/O1`, `/O2` та застарілий `/Ox`. Семантика цих рівнів не є побайтово тотожною. 

Рівень `-O2` у GCC та Clang вмикає всі базові оптимізації потоку керування, інлайнінг невеликих функцій, усунення спільних підвиразів та базову векторизацію (в останніх версіях GCC). Рівень `-O3` додає агресивне розгортання циклів (loop unrolling), глибоку автовекторизацію з перевпорядкуванням інструкцій SIMD та агресивне клонування функцій для спеціалізації за константними аргументами. У MSVC прапорець `/O2` є складним макросом, що включає прапорці `/Og` (глобальна оптимізація), `/Oi` (генерація інтринсиків замість викликів функцій CRT), `/Ot` (перевага швидкості над розміром), `/Oy` (пропуск покажчика кадру стеку), `/Ob2` (агресивний інлайнінг) та `/GF` (об'єднання однакових рядкових літералів). Аналога екстремального прапорця `-O3` в MSVC немає.

Для мінімізації розміру бінарного образу Clang пропонує унікальний рівень `-Oz`, який іде далі звичайного `-Os` і забороняє будь-які трансформації коду, що збільшують розмір інструкцій бодай на один байт, навіть якщо це погіршує швидкість виконання на кілька тактів процесора.

| Мета оптимізації | GCC | Clang | MSVC (`cl.exe`) | Механічні розбіжності |
| :--- | :--- | :--- | :--- | :--- |
| **Вимкнено (Debug)** | `-O0` | `-O0` | `/Od` | Швидка компіляція, збереження кадру стеку для точного налагодження. |
| **Базова (налагоджувальна)** | `-Og` | `-Og` | Відсутній (зазвичай `/Od` або `/O1`) | `-Og` вмикає безпечні оптимізації, що не спотворюють налагодження через GDB/LLDB. |
| **Оптимізація за швидкістю** | `-O2` | `-O2` | `/O2` | В MSVC `/O2` еквівалентний `/Og /Oi /Ot /Oy /Ob2 /Gs /GF /Gy`. |
| **Агресивна оптимізація** | `-O3` | `-O3` | `/O2` (або застарілий `/Ox`) | `-O3` в GCC/Clang агресивно розгортає цикли й векторизує код; в MSVC аналога `-O3` немає. |
| **Мінімізація розміру** | `-Os` | `-Os` | `/O1` або `/Os` | Оптимізація без розгортання коду вшир; пригнічує інлайнінг великих функцій. |
| **Екстремальний розмір** | Відсутній | `-Oz` | `/Os` | Clang `-Oz` агресивно жертвує тактами процесора заради кожного байта інструкцій. |
| **Fast Math (небезпечно)** | `-ffast-math` / `-Ofast` | `-ffast-math` / `-Ofast` | `/fp:fast` | Порушує IEEE-754: вважає, що NaN та Inf неможливі, дозволяє асоціативне перегрупування. |
| **Міжмодульна оптимізація (LTO)** | `-flto` | `-flto` або `-flto=thin` | `/GL` (компілятор) + `/LTCG` (лінкер) | Clang ThinLTO дозволяє паралельну міжмодульну оптимізацію без споживання гігабайтів RAM. |

## Діагностика, попередження та обробка помилок

Шкала суворості діагностики в компіляторах має суттєву асиметрію. Прапорець `-Wall` у GCC та Clang насправді вмикає не «всі» попередження, а лише базовий набір конструкцій, які з високою ймовірністю містять логічні помилки. Для справді якісного аналізу розробники обов'язково додають `-Wextra` та `-Wpedantic`.

На противагу цьому, прапорець `/Wall` у MSVC вмикає буквально кожне попередження, включно з інформаційними повідомленнями компілятора про те, що функція була вбудована за допомогою inline. Оскільки системні заголовки Windows SDK не проходять збірку з чистим `/Wall`, стандартом де-факто для суворої розробки під Windows є прапорець `/W4`.

Щоб ізолювати попередження у зовнішніх бібліотеках від власного коду проєкту, POSIX-компілятори використовують прапорець `-isystem`, який позначає каталоги як системні та приглушує в них будь-які зауваження. У MSVC аналогічний функціонал з'явився відносно нещодавно через пару прапорців `/external:I <шлях>` та `/external:W0`.

| Призначення | GCC | Clang | MSVC (`cl.exe`) | Застереження |
| :--- | :--- | :--- | :--- | :--- |
| **Базові попередження** | `-Wall` | `-Wall` | `/W3` | `-Wall` у GCC/Clang — це розумний базовий набір, а не «всі» попередження. |
| **Розширені попередження** | `-Wextra` | `-Wextra` | `/W4` | `/W4` у MSVC є рекомендованим виробничим стандартом суворості. |
| **Абсолютно всі попередження** | `-Weverything` (нема в GCC) | `-Weverything` | `/Wall` | `/Wall` в MSVC та `-Weverything` в Clang активують попередження навіть у системних заголовках. |
| **Попередження як помилки** | `-Werror` | `-Werror` | `/WX` | Перетворює будь-яке діагностичне попередження на помилку збірки. |
| **Приглушення сторонніх заголовків** | `-isystem <path>` | `-isystem <path>` | `/external:I <path>` + `/external:W0` | Дозволяє ігнорувати застарілий чи неідеальний код у зовнішніх бібліотеках. |

## Експорт символів, видимість та зв'язування рантайму

Формати двійкових файлів ELF (Linux) та PE/COFF (Windows) мають фундаментально протилежні моделі експорту функцій та класів динамічних бібліотек.

У форматі ELF за замовчуванням кожен скомпільований символ є глобально видимим (`global`), що призводить до роздування динамічної таблиці символів (`.dynsym`), сповільнення завантаження програми через необхідність обробки релокацій у PLT/GOT та неможливості глибокого інлайнінгу всередині бібліотеки. Щоб наблизити поведінку Linux до ефективної моделі Windows, проєкти збирають із прапорцем `-fvisibility=hidden`, явно позначаючи експортовані точки входу атрибутом `__attribute__((visibility("default")))`.

У середовищі Windows (формат PE/COFF) кожен символ за замовчуванням є внутрішнім. Щоб функція чи клас потрапили до таблиці експорту DLL (Export Address Table, EAT), їх необхідно явно позначити як `__declspec(dllexport)`. При компіляції клієнтського коду, який використовує цю бібліотеку, заголовок повинен оголошувати ту саму функцію через `__declspec(dllimport)` — це дозволяє компілятору згенерувати прямий виклик через покажчик таблиці імпорту (Import Address Table, IAT), оминаючи проміжний код-перехідник (trampoline).

| Механізм | GCC / Clang (ELF / Linux) | Clang (Mach-O / macOS) | MSVC / Clang-cl (PE / Windows) |
| :--- | :--- | :--- | :--- |
| **Експорт символу з бібліотеки** | `__attribute__((visibility("default")))` | `__attribute__((visibility("default")))` | `__declspec(dllexport)` |
| **Імпорт символу з бібліотеки** | `__attribute__((visibility("default")))` | `__attribute__((visibility("default")))` | `__declspec(dllimport)` |
| **Приховування символу** | `__attribute__((visibility("hidden")))` | `__attribute__((visibility("hidden")))` | Без специфікатора (за замовчуванням приховано) |
| **За замовчуванням ховати символи** | `-fvisibility=hidden` | `-fvisibility=hidden` | Увімкнено архітектурно в PE/COFF |
| **Позиційно-незалежний код (shared lib)** | `-fPIC` | За замовчуванням увімкнено | Не застосовується (Windows DLL використовують релокації / ASLR) |
| **Динамічний рантайм C/C++** | За замовчуванням (динамічна glibc/libstdc++) | За замовчуванням (libc++) | `/MD` (Release) або `/MDd` (Debug) |
| **Статичний рантайм C/C++** | `-static` або `-static-libstdc++` | Зазвичай не підтримується | `/MT` (Release) або `/MTd` (Debug) |

## Мовні атрибути та розширення

Стандарт C++11 ввів уніфікований синтаксис квадратних дужок `[[...]]`, проте розширення від виробників тулчейнів продовжують використовувати власні ключові слова.

Атрибути дозволяють передавати компілятору специфічні вказівки, які неможливо виразити конструкціями мови: примусове вбудовування функції навіть при перевищенні порогу розміру, заборона інлайнінгу для збереження точного стеку викликів при профілюванні, або вказівка на те, що функція є математично чистою (не має побічних ефектів і не читає глобальну пам'ять), що дозволяє оптимізатору повністю усунути її повторні виклики з однаковими аргументами.

| Семантична дія | Стандартний C++11/20 | Розширення GNU (GCC / Clang) | Розширення MSVC (`cl.exe`) |
| :--- | :--- | :--- | :--- |
| **Примусове вбудовування (inline)** | `[[gnu::always_inline]]` / `[[msvc::forceinline]]` | `__attribute__((always_inline))` | `__forceinline` |
| **Заборона вбудовування (noinline)** | `[[gnu::noinline]]` / `[[msvc::noinline]]` | `__attribute__((noinline))` | `__declspec(noinline)` |
| **Невживаний результат (nodiscard)** | `[[nodiscard]]` (C++17) | `__attribute__((warn_unused_result))` | `_Check_return_` (через SAL) |
| **Недосяжний блок (unreachable)** | `[[assume(expr)]]` (C++23) | `__builtin_unreachable()` | `__assume(0)` |
| **Вирівнювання пам'яті (align)** | `alignas(N)` | `__attribute__((aligned(N)))` | `__declspec(align(N))` |
| **Щільне пакування структур (pack)** | Відсутній у стандарті | `__attribute__((packed))` | `#pragma pack(push, 1)` |
| **Позначення чистих функцій** | Відсутній у стандарті | `__attribute__((pure))` / `__attribute__((const))` | Відсутній аналог |

## Апаратні інтринсики (Intrinsics) та бітові операції

Для низькорівневих обчислень компілятори надають вбудовані функції, які транслюються безпосередньо в окремі інструкції процесора (наприклад, `bsr`, `lzcnt`, `popcnt` для архітектури x86-64).

Головна небезпека функцій підрахунку нулів у GCC та Clang полягає в тому, що `__builtin_clz(0)` та `__builtin_ctz(0)` призводять до невизначеної поведінки (undefined behavior). Це пов'язано з тим, що інструкції x86 `bsr` (Bit Scan Reverse) та `bsf` (Bit Scan Forward) не змінюють цільовий регістр, якщо вхідне число дорівнює нулю. На противагу їм, інтринсики MSVC `_BitScanReverse` та `_BitScanForward` повертають логічний результат (знайдено біт чи ні), записуючи індекс через покажчик, що захищає розробника від непередбачуваних помилок. Починаючи зі стандарту C++20, стандартний заголовок `<bit>` повністю усуває цю проблему, надаючи безпечні та повністю оптимізовані функції для всіх компіляторів.

:::tabs
```c
#include <stdint.h>

#if defined(_MSC_VER) && !defined(__clang__)
#include <intrin.h>

static inline uint32_t count_leading_zeros32(uint32_t x) {
    if (x == 0) return 32;
    unsigned long index;
    _BitScanReverse(&index, x);
    return 31 - index;
}

static inline uint32_t popcount32(uint32_t x) {
    return __popcnt(x);
}

#else

static inline uint32_t count_leading_zeros32(uint32_t x) {
    if (x == 0) return 32;
    return (uint32_t)__builtin_clz(x);
}

static inline uint32_t popcount32(uint32_t x) {
    return (uint32_t)__builtin_popcount(x);
}

#endif
```
```cpp
#include <cstdint>
#include <bit>

// Починаючи з C++20 стандартна бібліотека <bit> повністю
// абстрагує апаратні інтринсики процесора для всіх компіляторів.
constexpr std::uint32_t count_leading_zeros32(std::uint32_t x) noexcept {
    return static_cast<std::uint32_t>(std::countl_zero(x));
}

constexpr std::uint32_t popcount32(std::uint32_t x) noexcept {
    return static_cast<std::uint32_t>(std::popcount(x));
}
```

## Атомарні операції та бар'єри пам'яті

До стандарту C++11 кожен компілятор реалізовував власні інтринсики для міжпотокової синхронізації та атомарного оновлення змінних без блокувань.

Компілятори родини GNU надають родину вбудованих функцій `__atomic_*`, які приймають аргументом модель послідовності пам'яті (memory order): `__ATOMIC_RELAXED`, `__ATOMIC_ACQUIRE`, `__ATOMIC_RELEASE` та `__ATOMIC_SEQ_CST`. Це дозволяє генерувати мінімально необхідні бар'єри пам'яті на слабо-впорядкованих архітектурах, таких як ARM чи RISC-V.

На відміну від GNU, інтринсики MSVC `_Interlocked*` історично проєктувалися під апаратну модель x86/x64, де будь-яка інструкція з префіксом `LOCK` виконує повну послідовну синхронізацію (Sequentially Consistent). На сучасних ARM64-платформах Windows надає модифікації цих інтринсиків із суфіксами `_acq`, `_rel` та `_nf` (no fence). У сучасному коді всі ці платформо-залежні виклики повністю замінені стандартним заголовком `<atomic>`.

| Дія | GCC / Clang Built-in | MSVC Intrinsic (`<intrin.h>`) | C++11 / C++20 `<atomic>` |
| :--- | :--- | :--- | :--- |
| **Атомарне додавання (Fetch Add)** | `__atomic_fetch_add(ptr, val, mo)` | `_InterlockedExchangeAdd(ptr, val)` | `std::atomic<T>::fetch_add` |
| **Порівняння з обміном (CAS)** | `__atomic_compare_exchange_n(...)` | `_InterlockedCompareExchange(ptr, new, old)` | `std::atomic<T>::compare_exchange_strong` |
| **Атомарний запис (Store)** | `__atomic_store_n(ptr, val, mo)` | `_InterlockedExchange(ptr, val)` | `std::atomic<T>::store` |
| **Повний бар'єр пам'яті (Memory fence)** | `__atomic_thread_fence(__ATOMIC_SEQ_CST)` | `_ReadWriteBarrier()` / `MemoryBarrier()` | `std::atomic_thread_fence` |
