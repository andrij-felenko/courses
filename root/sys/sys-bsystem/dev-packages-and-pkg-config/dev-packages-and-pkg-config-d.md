Розробник налаштовує збірку мережевого сервісу на свіжовстановленому сервері під керуванням Ubuntu або Debian. Програма використовує базу даних SQLite та бібліотеку стиснення zlib. Утиліта командного рядка `sqlite3` вже встановлена в системі й успішно виконує SQL-запити, а системні демони використовують бібліотеку `/usr/lib/x86_64-linux-gnu/libsqlite3.so.0.8.6`. Проте перша ж спроба скомпілювати вихідний код програми командою `gcc main.c -lsqlite3 -lz` миттєво аварійно завершується:

```text
fatal error: sqlite3.h: No such file or directory
 #include <sqlite3.h>
          ^~~~~~~~~~~
compilation terminated.
```

Спроба виконати `apt install sqlite3` повідомляє, що пакет найновішої версії вже встановлено, але помилка компіляції нікуди не зникає: системний бінарник `/usr/bin/sqlite3` є, а заголовкових файлів у каталозі `/usr/include` немає. Лише встановлення спеціального пакета `apt install libsqlite3-dev` (або `dnf install sqlite3-devel` у дистрибутивах родини Red Hat) додає потрібні файли C API на диск, і збірка нарешті проходить.

Ця поведінка є прямим наслідком фундаментального принципу організації пакетних менеджерів Unix: **чіткого розділення артефактів на середовище виконання (Runtime) та середовище розробки (Development)**. Щоб ефективно керувати сторонніми залежностями, розробник повинен точно розуміти, як влаштований цей розкол, де саме компілятор шукає заголовки, як лінкер виявляє бінарні бібліотеки, і чому метадані у форматі `pkg-config` стали універсальним стандартом опису зовнішнього API.

## Анатомія розколу пакетів: Runtime проти Development

У дистрибутивах Linux вихідний код будь-якої бібліотеки (наприклад `libpng` чи `OpenSSL`) після компіляції розфасовується супроводжувачами (англ. *maintainers*) у щонайменше два різних бінарних пакунки.

![Анатомія розколу пакунків: Runtime проти Development](/root/sys/sys-bsystem/dev-packages-and-pkg-config/img/dev-vs-runtime-split.svg)

*Розподіл артефактів між пакетом виконання libfoo1 та пакетом розробки libfoo-dev: заголовки, статичні архіви та метадані існують лише у dev-пакеті.*

### Вміст пакета середовища виконання (Runtime Package)

Пакет середовища виконання (в Debian/Ubuntu він зазвичай має назву виду `libfoo1` або `libsqlite3-0`, у Fedora/RHEL — просто `libfoo` чи `sqlite-libs`) призначений виключно для запуску вже скомпільованих програм. До його складу входять лише три речі:

1. **Реальний скомпільований бінарний файл бібліотеки:** спільний об'єкт формату ELF із повною версією реалізації, наприклад `/usr/lib/x86_64-linux-gnu/libsqlite3.so.0.8.6`.
2. **Символічне посилання SONAME:** посилання виду `libsqlite3.so.0 -> libsqlite3.so.0.8.6`. Саме це ім'я жорстко зашите в заголовок `DT_NEEDED` кожного скомпільованого бінарника. Динамічний завантажувач ядра `ld-linux.so` під час старту програми шукає саме `libsqlite3.so.0`.
3. **Мінімальні ресурси часу виконання:** файли конфігурацій, локалізації чи системні сервіси (якщо вони критично необхідні для функціонування бібліотеки).

У runtime-пакеті принципово **відсутні** заголовкові файли (`.h`), статичні бібліотеки (`.a`), файли конфігурацій систем збірки (`.pc`, `.cmake`) та символічні посилання без версійних суфіксів (`libfoo.so`).

### Вміст пакета розробки (Development Package)

Пакет розробки (має суфікс `-dev` у Debian/Ubuntu або `-devel` у Red Hat, Fedora, Arch та SUSE, наприклад `libsqlite3-dev` чи `sqlite-devel`) містить усе, що потрібно компілятору та лінкеру для створення нових програм:

1. **Файли заголовків C/C++ API:** файли з деклараціями структур, типів, функцій і констант (`/usr/include/sqlite3.h`, `/usr/include/sqlite3ext.h`). Без них препроцесор компілятора GCC або Clang не може розгорнути директиви `#include`.
2. **Лінкувальний симлінк без версії:** символічне посилання `/usr/lib/x86_64-linux-gnu/libsqlite3.so -> libsqlite3.so.0.8.6`. Коли ви передаєте лінкеру прапорець `-lsqlite3`, компонувальник `ld` шукає файл із точним ім'ям `libsqlite3.so` або `libsqlite3.a`. Якщо в системі встановлено лише runtime-пакет із файлом `libsqlite3.so.0`, лінкер видасть помилку `cannot find -lsqlite3`, оскільки він не займається вгадуванням суфіксів версій.
3. **Статичні архіви:** файл `/usr/lib/x86_64-linux-gnu/libsqlite3.a` для забезпечення статичного компонування за допомогою прапорця `-static`.
4. **Файли метаданих для систем збірки:** файли опису `pkg-config` (`/usr/lib/x86_64-linux-gnu/pkgconfig/sqlite3.pc`) та конфігураційні файли CMake (`/usr/lib/cmake/SQLite3/SQLite3Config.cmake`).

### Чому цей розкол життєво необхідний

Поділ на runtime та development вирішує чотири системні завдання:

- **Мінімізація дискового простору та образів контейнерів:** на бойових веб-серверах, у хмарних контейнерах Docker або на мікроконтролерах із вбудованим Linux непотрібно зберігати десятки тисяч заголовкових файлів і масивні статичні архіви. Runtime-пакет займає у 5–20 разів менше місця, ніж повний комплект розробника.
- **Безпека та незалежне оновлення:** коли в бібліотеці OpenSSL виявляють уразливість, системний адміністратор оновлює лише бінарний runtime-пакет `libssl3`. Усі запущені сервіси після перезапуску негайно отримують виправлення без необхідності перекомпільовувати код і без оновлення інструментів розробки.
- **Одночасне співіснування різних ABI (Coexistence):** операційна система може одночасно містити старі програми, зібрані з `libpng12.so.0` (SONAME версії 12), та сучасні програми, що вимагають `libpng16.so.16` (SONAME версії 16). Обидва runtime-пакети встановлюються поруч без жодних конфліктів. Але пакет розробки `libpng-dev` у системі може бути лише один, оскільки файл `/usr/include/png.h` та лінкувальний симлінк `/usr/lib/libpng.so` мають унікальні фіксовані імена.
- **Чистота та герметичність збірки:** відсутність dev-пакетів на сервері гарантує, що випадковий скрипт не почне компілювати код із неперевіреними системними заголовками.

> 🔧 **Навіщо потрібен симлінк без номера `libfoo.so`.** Компонувальник GNU `ld` розрахований на роботу з абстрактними іменами бібліотек. Коли ви пишете `gcc main.o -lpng -o app`, лінкер розгортає `-lpng` у пошук файла `libpng.so`. Знайшовши цей файл (який насправді є симлінком на `libpng16.so.16.37.0`), лінкер зчитує з його заголовка ELF поле `SONAME` (там записано `libpng16.so.16`) і саме цей версійний рядок записує у вихідний бінарник `app` як залежність `DT_NEEDED`. Симлінк `libpng.so` потрібен лише на етапі створення виконуваного файла і ніколи не використовується під час його виконання.

## Де лежать файли: системні каталоги пошуку та Multiarch

Коли компілятор обробляє рядок `#include <foo.h>`, а компонувальник зустрічає аргумент `-lfoo`, вони звертаються до суворо визначеної ієрархії каталогів файлової системи Linux.

![Драбина пошуку компілятора, лінкера та pkg-config](/root/sys/sys-bsystem/dev-packages-and-pkg-config/img/search-paths-and-sysroot.svg)

*Драбина перевірки шляхів пошуку заголовків компілятором, метаданих pkg-config та бінарних бібліотек лінкером.*

### Драбина пошуку заголовків компілятора

Препроцесор компілятора розрізняє подвійні лапки `#include "foo.h"` та кутові дужки `#include <foo.h>`. У випадку лапок пошук починається з каталогу поточного вихідного файла. Для кутових дужок компілятор перевіряє каталоги в такому порядку:

1. **Каталоги, передані через прапорці `-I`:** перевіряються зліва направо у порядку їхнього зазначення в командному рядку (`-I/opt/custom/include`).
2. **Каталоги системних заголовків `-isystem`:** перевіряються після всіх `-I`. Заголовки з цих каталогів вважаються системними: компілятор автоматично пригнічує для них попередження попереджувальних прапорців (наприклад `-Wall -Wextra`).
3. **Локальний префікс користувача:** `/usr/local/include` (каталог для бібліотек, зібраних вручну з вихідного коду).
4. **Архітектурно-залежні каталоги Multiarch:** `/usr/include/x86_64-linux-gnu` (в Ubuntu/Debian) або `/usr/include/arm-linux-gnueabihf`.
5. **Загальносистемний стандартний каталог:** `/usr/include`.

Дізнатися точний вбудований список шляхів пошуку вашого компілятора можна за допомогою прямого запиту:

```bash
$ echo | gcc -E -Wp,-v -xc -
#include <...> search starts here:
 /usr/lib/gcc/x86_64-linux-gnu/13/include
 /usr/local/include
 /usr/include/x86_64-linux-gnu
 /usr/include
End of search list.
```

### Драбина пошуку бібліотек лінкером під час збірки

Компонувальник `ld` під час обробки аргументу `-lfoo` сканує дисковий простір у такому пріоритеті:

1. **Каталоги з прапорців `-L`:** зазначені явно в командному рядку (`-L/opt/custom/lib`).
2. **Локальні префікси системи:** `/usr/local/lib` або `/usr/local/lib64`.
3. **Архітектурні каталоги Multiarch:** `/usr/lib/x86_64-linux-gnu` та `/lib/x86_64-linux-gnu`.
4. **Стандартні системні каталоги:** `/usr/lib`, `/lib` або `/usr/lib64`.

### Драбина пошуку бібліотек завантажувачем під час запуску (Runtime Loader)

Коли створений бінарник запускається користувачем, ядро викликає динамічний завантажувач `/lib64/ld-linux-x86-64.so.2`. Завантажувач сканує заголовки `DT_NEEDED` і шукає відповідні файли `.so` за таким алгоритмом:

1. **ELF заголовок `DT_RPATH`:** жорстко зашиті шляхи всередині бінарника (якщо не встановлено `DT_RUNPATH`).
2. **Змінна оточення `LD_LIBRARY_PATH`:** список каталогів, заданий користувачем у поточному терміналі.
3. **ELF заголовок `DT_RUNPATH`:** сучасний стандарт зашивання шляхів пошуку, який перевіряється після `LD_LIBRARY_PATH`.
4. **Кеш динамічного лінкера `/etc/ld.so.cache`:** двійковий кеш, що генерується системною утилітою `ldconfig` на основі файлів конфігурації `/etc/ld.so.conf` та `/etc/ld.so.conf.d/*.conf`.
5. **Системні каталоги за замовчуванням:** `/lib/x86_64-linux-gnu`, `/usr/lib/x86_64-linux-gnu`, `/lib64`, `/usr/lib64`, `/lib`, `/usr/lib`.

### Multiarch (Debian/Ubuntu) проти Multilib (Fedora/RHEL)

В епоху 32-розрядних систем усі бібліотеки зберігалися в одному каталозі `/usr/lib`. Із появою 64-розрядних процесорів виникла потреба одночасно тримати в системі як 64-розрядні, так і 32-розрядні версії бібліотек (наприклад, для запуску 32-бітних ігор через Wine або збірки прошивок). Дистрибутиви розв'язали цю задачу двома різними шляхами:

- **Підхід Multilib (Fedora, RHEL, Arch, openSUSE):** 32-розрядні бібліотеки кладуться в `/usr/lib`, а 64-розрядні — у суміжний каталог `/usr/lib64`. Цей підхід підтримує лише дві фіксовані розрядності хост-архітектури.
- **Підхід Multiarch (Debian, Ubuntu):** бібліотеки кожної цільової архітектури розміщуються в каталозі з ім'ям відповідного тріплета GNU: `/usr/lib/x86_64-linux-gnu`, `/usr/lib/i386-linux-gnu`, `/usr/lib/aarch64-linux-gnu`, `/usr/lib/arm-linux-gnueabihf`. Це дозволяє паралельно встановлювати бібліотеки під будь-яку кількість цільових процесорів, що критично важливо для крос-компіляції.

Детальний аналіз реалізації розкладки Multiarch на рівні ядра та системних завантажувачів розкрито в темі [багатоархітектурна розкладка multilib та multiarch](root:sys-unix/multilib-multiarch).

## Проблема ручного підбору прапорців і народження pkg-config

Коли проєкт використовує одну бібліотеку на зразок `zlib`, передати компілятору `-lz` не становить труднощів. Але коли програма спирається на складні бібліотеки (наприклад GTK, FFmpeg, GStreamer чи Qt), ручне зазначення прапорців перетворюється на інженерний кошмар.

Розглянемо графічну бібліотеку `libpng`. Щоб скомпілювати файл `main.c`, який викликає функції `libpng`, розробнику потрібно:
1. Знати, що заголовки лежать не просто в `/usr/include`, а в окремому підкаталозі `/usr/include/libpng16`. Отже, компілятору треба обов'язково передати `-I/usr/include/libpng16`.
2. Знати, що бібліотека називається не `libpng.so`, а `libpng16.so`, тому лінкеру слід передати `-lpng16`.
3. Якщо бібліотека встановлена в нестандартний каталог (наприклад `/opt/libpng` або шлях менеджера пакетів Homebrew у macOS), додати відповідні прапорці `-I/opt/libpng/include` та `-L/opt/libpng/lib`.

Наприкінці 1990-х років кожна бібліотека намагалася вирішити це створенням власного виконуваного shell-скрипта (`gtk-config`, `sdl-config`, `xml2-config`). Це призвело до вибухового дублювання прапорців, повної неможливості крос-компіляції та повільної роботи.

Історію цієї кризи та перехід до декларативних метаданих детально викладено в окремому історичному нарисі: [від хаосу *-config скриптів до декларативного pkg-config](root:sys-bsystem/dev-packages-and-pkg-config/hist-pkg-config-birth.md).

Розв'язанням проблеми стало створення формату метаданих **`pkg-config`** (файли `.pc`) та однойменної утиліти (а в сучасному світі — її швидкої реалізації **`pkgconf`**).

## Анатомія .pc файлу: змінні, секції та вимоги

Файл опису пакета `.pc` — це текстовий файл, який автор бібліотеки встановлює в каталог `/usr/lib/x86_64-linux-gnu/pkgconfig/` (для архітектурно-залежних бібліотек) або `/usr/share/pkgconfig/` (для бібліотек із самих заголовків).

Погляньмо на реальний приклад файла `libpng16.pc`:

```ini
prefix=/usr
exec_prefix=${prefix}
libdir=${prefix}/lib/x86_64-linux-gnu
includedir=${prefix}/include/libpng16

Name: libpng
Description: Loads and writes PNG files
Version: 1.6.43
Requires.private: zlib
Libs: -L${libdir} -lpng16
Libs.private: -lm -lz
Cflags: -I${includedir}
```

### Структурні складові .pc файлу

Файл складається з трьох ключових блоків:

1. **Змінні префіксів і шляхів (Variables):**
   - `prefix=/usr`: кореневий каталог встановлення.
   - `exec_prefix=${prefix}`: префікс виконуваних і бінарних файлів.
   - `libdir=${prefix}/lib/x86_64-linux-gnu`: каталог розміщення бібліотек.
   - `includedir=${prefix}/include/libpng16`: каталог розташування заголовкових файлів.
   Змінні можуть посилатися одна на одну через синтаксис `${змінна}`. Це дозволяє зробити файл переміщуваним (relocatable), замінивши значення `prefix` під час конфігурації.

2. **Інформаційні метадані (Informational Metadata):**
   - `Name`: коротка назва пакета.
   - `Description`: опис бібліотеки.
   - `Version`: версія пакета. Дозволяє системам збірки перевіряти діапазони сумісності (наприклад `libpng >= 1.6.0`).
   - `URL`: домашня сторінка проєкту.

3. **Прапорці компілятора та лінкера (Flags & Dependencies):**
   - `Cflags`: прапорці, необхідні препроцесору та компілятору (`-I${includedir}`).
   - `Libs`: прапорці компонувальника для динамічного лінкування (`-L${libdir} -lpng16`).
   - `Requires`: список інших `.pc` пакетів, від яких ця бібліотека залежить публічно (їхні типи згадуються в публічних заголовках).
   - `Requires.private`: список пакетів, від яких бібліотека залежить лише внутрішньо у своїй реалізації.
   - `Libs.private`: додаткові прапорці компонувальника, потрібні **виключно для статичного лінкування** (наприклад системні модулі `-lm`, `-lpthread`, `-ldl`).

Повний нормативний перелік усіх полів і змінних зібрано у довіднику: [специфікація формату .pc та довідник CLI pkg-config](root:sys-bsystem/dev-packages-and-pkg-config/api-pc-file-spec.md).

## Як працює утиліта pkg-config / pkgconf

Утиліта `pkg-config` (або `pkgconf`) є синтаксичним аналізатором і генератором командного рядка для компілятора. Замість того, щоб вручну прописувати шляхи до каталогів, розробник звертається до утиліти з конкретними запитами.

### Базові команди CLI

Отримання прапорців компілятора (шляхів до заголовків):
```bash
$ pkg-config --cflags libpng
-I/usr/include/libpng16
```

Отримання прапорців лінкера для динамічного лінкування:
```bash
$ pkg-config --libs libpng
-lpng16
```
*(Зверніть увагу: прапорець `-L/usr/lib/x86_64-linux-gnu` утиліта автоматично відкинула, оскільки це стандартний системний каталог лінкера, і передавати його зайвий раз непотрібно).*

Отримання версії пакета:
```bash
$ pkg-config --modversion libpng
1.6.43
```

Перевірка мінімально необхідної версії в автоматизованих сценаріях (повертає код повернення 0 у разі успіху або 1, якщо версія не підходить):
```bash
$ pkg-config --exists 'libpng >= 1.6.0' && echo "Сумісна версія знайдена"
Сумісна версія знайдена
```

Отримання нестандартних змінних, закладених автором пакета:
```bash
$ pkg-config --variable=includedir libpng
/usr/include/libpng16
```

### Алгоритм топологічного сортування та дедуплікації

Коли утиліту запитують про кілька пакетів одночасно (наприклад `pkg-config --cflags --libs gtk+-3.0 libsoup-2.4`), вона виконує такий алгоритм:

1. Знаходить і парсить зазначені `.pc` файли.
2. Рекурсивно розгортає всі залежності через поля `Requires` (та `Requires.private` у разі статичного лінкування).
3. Будує спрямований ациклічний граф (DAG).
4. Виконує топологічне сортування: залежності вищого рівня розміщуються ліворуч, а базові низькорівневі бібліотеки — праворуч.
5. Усуває дублікати: для прапорців `-I` зберігається перше (найбільш специфічне) входження, а для прапорців лінкера `-l` зберігається порядок, який гарантує, що бібліотека-викликувач стоїть перед бібліотекою, чиї символи вона викликає.

### Змінні оточення: PKG_CONFIG_PATH, PKG_CONFIG_LIBDIR та PKG_CONFIG_SYSROOT_DIR

Поведінкою `pkg-config` можна гнучко керувати за допомогою трьох ключових змінних операційної системи:

#### 1. `PKG_CONFIG_PATH`
Список каталогів (розділених двокрапкою `:`), у яких `pkg-config` шукає `.pc` файли **перед тим, як перевіряти стандартні системні каталоги**.

Якщо ви зібрали власну версію бібліотеки й встановили її в домашній каталог `/home/user/my_libs`, достатньо експортувати:
```bash
export PKG_CONFIG_PATH=/home/user/my_libs/lib/pkgconfig:$PKG_CONFIG_PATH
```
`pkg-config` знайде вашу локальну бібліотеку раніше за системну.

#### 2. `PKG_CONFIG_LIBDIR`
Ця змінна **повністю замінює** стандартні системні шляхи пошуку.

Це головний інструмент ізоляції під час **крос-компіляції**. Якщо ви збираєте програму для ARM на комп'ютері x86_64, ви не маєте права підтягувати `.pc` файли хост-системи. Ви задаєте:
```bash
export PKG_CONFIG_LIBDIR=/opt/arm-sysroot/usr/lib/pkgconfig:/opt/arm-sysroot/usr/share/pkgconfig
```
У результаті утиліта бачитиме виключно метадані цільової платформи.

#### 3. `PKG_CONFIG_SYSROOT_DIR`
Вказує префікс цільової файлової системи (sysroot). Коли ця змінна встановлена, `pkg-config` автоматично дописує цей префікс до всіх абсолютних шляхів, що починаються з `/` у прапорцях `-I` та `-L`.

Якщо у файлі `libpng.pc` всередині sysroot записано `includedir=/usr/include/libpng16`, виклик із `PKG_CONFIG_SYSROOT_DIR=/opt/arm-sysroot` поверне:
```bash
-I/opt/arm-sysroot/usr/include/libpng16
```
Це унеможливлює випадкове включення хостових заголовків у крос-компілятор.

## Підводні камені: приватні залежності та випробування статичним лінкуванням

Найбільше прихованих помилок у системах збірки виникає на стику між динамічним і статичним компонуванням бібліотек. Поведінка `pkg-config` у цих двох режимах кардинально різниться.

![Розгортання залежностей pkg-config: Shared проти Static](/root/sys/sys-bsystem/dev-packages-and-pkg-config/img/pc-dependency-graph.svg)

*Розгортання дерева залежностей pkg-config: при динамічному лінкуванні повертається лише top-level прапорець, при статичному — рекурсивно розгортаються Requires.private та Libs.private.*

### Чому динамічному лінкеру байдуже до приватних залежностей

Уявімо бібліотеку `libfoo`, яка всередині використовує алгоритми шифрування з `libcrypto` (OpenSSL) та математичні функції `sin()` з `libm`.

Коли `libfoo` збирається як динамічна бібліотека `libfoo.so`, лінкер записує залежність від `libcrypto.so` безпосередньо у заголовок ELF створеного файла (поле `DT_NEEDED = libcrypto.so.3`).

Коли розробник пише програму `app`, яка використовує лише API самої `libfoo` (і не викликає функції OpenSSL напряму), компілятору потрібні лише заголовки `foo.h` та прапорець лінкера `-lfoo`:
```bash
gcc main.o -lfoo -o app
```
Компонувальнику `ld` не потрібно знати про `libcrypto`, оскільки під час старту програми динамічний завантажувач ядра `ld-linux.so` сам прочитає `DT_NEEDED` всередині `libfoo.so` і автоматично підвантажить `libcrypto.so` у пам'ять процесу.

Тому команда `pkg-config --libs foo` повертає лише:
```bash
-lfoo
```

### Чому статичне лінкування вимагає всього дерева символів

Тепер спробуємо зібрати ту саму програму статично, використовуючи статичний архів `libfoo.a`.

Статичний архів `.a` — це не скомпільований бінарний образ, а звичайний контейнер (архів `ar`), що містить набір об'єктних файлів `.o`. У ньому **немає заголовків ELF `DT_NEEDED`** і немає жодної інформації про залежності. Об'єктний файл `foo.o` просто містить невирішені (undefined) символи: виклики функцій `EVP_EncryptInit` (з OpenSSL) та `sin` (з libm).

Якщо ви спробуєте злінкувати статичну програму наївно:
```bash
gcc -static main.o -lfoo -o app
```
Лінкер негайно зупиниться з фатальними помилками:
```text
/usr/lib/libfoo.a(foo.o): in function `foo_process':
foo.c:(.text+0x42): undefined reference to `EVP_EncryptInit'
foo.c:(.text+0x78): undefined reference to `sin'
collect2: error: ld returned 1 exit status
```

Лінкер не знає, де шукати реалізацію цих функцій. Розробник змушений вручну передати лінкеру абсолютно всі транзитивні статичні архіви в строго правильному порядку:
```bash
gcc -static main.o -lfoo -lcrypto -lz -lm -lpthread -ldl -o app
```

### Як Requires.private та Libs.private рятують статичну збірку

Формат `.pc` розв'язує цю проблему за допомогою розділення публічних і приватних вимог:
- `Requires.private: libcrypto, zlib`
- `Libs.private: -lm -lpthread -ldl`

Коли ви додаєте аргумент `--static`, `pkg-config` змінює свою поведінку: він рекурсивно обходить усі пакети, вказані в `Requires.private`, витягує їхні прапорці `Libs` та додає прапорці з рядка `Libs.private`:

```bash
$ pkg-config --static --libs foo
-lfoo -lcrypto -lz -lm -lpthread -ldl
```

### Пастка порядку лінкування статичних бібліотек (Link Order)

Компонувальник GNU `ld` обробляє статичні бібліотеки строго в один прохід зліва направо:
1. Коли лінкер зустрічає `main.o`, він формує список невирішених символів (наприклад `foo_init`).
2. Коли він бачить `-lfoo`, він витягує з `libfoo.a` ті об'єктні файли, які містять `foo_init`. Але ці файли додають у список нові невирішені символи — `EVP_EncryptInit`.
3. Коли лінкер бачить наступний аргумент `-lcrypto`, він закриває символ `EVP_EncryptInit` об'єктними файлами з `libcrypto.a`.

Якщо порушити порядок і написати `-lcrypto -lfoo`:
1. Лінкер бачить `libcrypto.a`, але на цей момент список невирішених символів ще не містить `EVP_EncryptInit` (бо `libfoo.a` ще не відкривався). Лінкер просто ігнорує весь архів `libcrypto.a`.
2. Потім лінкер бачить `libfoo.a`, витягує `foo_init` і отримує невирішений символ `EVP_EncryptInit`.
3. Аргументи закінчилися — збірка падає з помилкою `undefined reference`.

Утиліта `pkg-config` автоматично розміщує прапорці у правильному зворотно-транзитивному порядку, гарантуючи успішне статичне компонування.

Повний покроковий процес створення власного `.pc` файла та перевірки лінкування продемонстровано у практичному проєкті: [створення та встановлення власних .pc пакетів](root:sys-bsystem/dev-packages-and-pkg-config/proj-pc-authoring.md).

## Інтеграція в системи збірки: CMake, Meson та GNU Make

У реальних проєктах розробники рідко викликають `pkg-config` вручну через термінал. Замість цього утиліта інтегрується в системи автоматизації збірки.

### 1. Інтеграція в CMake через модуль FindPkgConfig

CMake має власний вбудований механізм пошуку [find_package](root:sys-bsystem/find-package), але для взаємодії з дистрибутивними пакетами, які не постачають файлів `*Config.cmake`, CMake надає штатний модуль `FindPkgConfig`.

Сучасний стандарт роботи з `FindPkgConfig` вимагає використання прапорця `IMPORTED_TARGET`:

```cmake
# CMakeLists.txt
cmake_minimum_required(VERSION 3.16)
project(ImageProcessor LANGUAGES C CXX)

set(CMAKE_C_STANDARD 11)
set(CMAKE_CXX_STANDARD 20)

# Завантаження модуля пошуку pkg-config
find_package(PkgConfig REQUIRED)

# Пошук бібліотеки libpng версії не менше 1.6
# Прапорець IMPORTED_TARGET створює повноцінну імпортовану ціль PkgConfig::PNG
pkg_check_modules(PNG REQUIRED IMPORTED_TARGET libpng>=1.6)

# Створення виконуваного файлу
add_executable(img_proc src/main.c)

# Прив'язка залежності через імпортовану ціль
target_link_libraries(img_proc PRIVATE PkgConfig::PNG)
```

Використання імпортованої цілі `PkgConfig::PNG` дає принципові переваги:
- Вона інкапсулює шляхи до заголовків у властивості `INTERFACE_INCLUDE_DIRECTORIES`.
- Передає прапорці лінкера через `INTERFACE_LINK_LIBRARIES`.
- Не засмічує глобальні змінні проєкту, ізолюючи прапорці виключно для цілі `img_proc`.

Якщо проєкт збирається у статичному режимі (наприклад `set(BUILD_SHARED_LIBS OFF)`), виклик змінюють на:
```cmake
pkg_check_modules(PNG REQUIRED IMPORTED_TARGET STATIC libpng>=1.6)
```
Це змушує CMake викликати `pkg-config` із ключем `--static` і підтягнути всі приватні залежності.

### 2. Інтеграція в Meson: нативна підтримка першого класу

У системі збірки Meson утиліта `pkg-config` є основним, пріоритетним механізмом виявлення залежностей за замовчуванням:

```meson
# meson.build
project('image_processor', ['c', 'cpp'],
  version : '1.0.0',
  default_options : ['c_std=c11', 'cpp_std=c++20']
)

# Meson автоматично викликає pkg-config для пошуку libpng
png_dep = dependency('libpng', version : '>=1.6', required : true, static : false)

executable('img_proc',
  sources : ['src/main.cpp'],
  dependencies : [png_dep]
)
```

Meson самостійно перевіряє `PKG_CONFIG_PATH`, коректно обробляє sysroot при крос-компіляції та забезпечує кешування результатів безпосередньо через внутрішню бібліотеку `libpkgconf`.

### 3. Інтеграція в класичний GNU Make

У традиційних сценаріях `Makefile` прапорці підставляються через функцію виклику оболонки `$(shell ...)`:

```makefile
# Makefile
CC ?= gcc
CFLAGS ?= -Wall -Wextra -O2
PKG_CONFIG ?= pkg-config

# Отримуємо прапорці від pkg-config
PNG_CFLAGS := $(shell $(PKG_CONFIG) --cflags libpng)
PNG_LIBS := $(shell $(PKG_CONFIG) --libs libpng)

CFLAGS += $(PNG_CFLAGS)
LDLIBS += $(PNG_LIBS)

img_proc: src/main.o
	$(CC) $(LDFLAGS) $^ $(LDLIBS) -o $@

src/main.o: src/main.c
	$(CC) $(CFLAGS) -c $< -o $@

clean:
	rm -f src/*.o img_proc
```

#include <png.h>
#include <iostream>
#include <memory>
#include <string_view>
#include <expected>

// RAII обгортка для автоматичного контролю життєвого циклу ресурсів libpng
struct PngContext {
    png_structp png_ptr{nullptr};
    png_infop info_ptr{nullptr};

    PngContext() {
        png_ptr = png_create_read_struct(PNG_LIBPNG_VER_STRING, nullptr, nullptr, nullptr);
        if (png_ptr) {
            info_ptr = png_create_info_struct(png_ptr);
        }
    }

    ~PngContext() {
        if (png_ptr) {
            png_destroy_read_struct(&png_ptr, info_ptr ? &info_ptr : nullptr, nullptr);
        }
    }

    // Забороняємо копіювання ресурсу
    PngContext(const PngContext&) = delete;
    PngContext& operator=(const PngContext&) = delete;

    [[nodiscard]] bool is_valid() const noexcept {
        return png_ptr != nullptr && info_ptr != nullptr;
    }
};

        std::cerr << "Помилка: не вдалося ініціалізувати контекст libpng через RAII\n";
        return 1;
    }

    std::cout << "Структури libpng успішно ініціалізовано та захищено через RAII.\n";
    return 0;
}

## Типові помилки діагностики та способи їх усунення

Працюючи із системними пакетами та `pkg-config`, інженери регулярно стикаються з типовими збоями. Розуміння їхніх причин дозволяє локалізувати проблему за лічені секунди.

### 1. Пакет не знайдено: «Package foo was not found in the pkg-config search path»
- **Причина:** у системі або взагалі не встановлено пакет розробки (`-dev` / `-devel`), або `.pc` файл лежить у нестандартному каталозі.
- **Діагностика:**
  - В Ubuntu/Debian перевірити наявність пакета: `dpkg -S foo.pc` або `apt-file search foo.pc`.
  - У Fedora/RHEL знайти постачальника: `dnf provides 'pkgconfig(foo)'`.
- **Виправлення:** встановити dev-пакет (`apt install libfoo-dev`) або додати шлях до змінної:
  ```bash
  export PKG_CONFIG_PATH=/opt/custom/lib/pkgconfig:$PKG_CONFIG_PATH
  ```

### 2. Витік хостових шляхів під час крос-компіляції
- **Симптом:** компілятор ARM скаржиться на несумісний формат бібліотек або намагається відкрити `/usr/include/foo.h` хост-системи.
- **Причина:** `pkg-config` звернувся до системних каталогів хост-машини замість цільового sysroot.
- **Виправлення:** заблокувати системні шляхи та налаштувати sysroot:
  ```bash
  export PKG_CONFIG_LIBDIR=$SYSROOT/usr/lib/pkgconfig:$SYSROOT/usr/share/pkgconfig
  export PKG_CONFIG_SYSROOT_DIR=$SYSROOT
  ```

### 3. Помилки невирішених символів (undefined reference) при статичному лінкуванні
- **Симптом:** динамічна збірка працює, а зі прапорцем `-static` лінкер повідомляє про відсутність математичних чи криптографічних функцій.
- **Причина:** автор пакета забув вказати залежності в `Requires.private` або `Libs.private`, або збірка викликала `pkg-config` без ключа `--static`.
- **Виправлення:** перевірити вивід `pkg-config --static --libs foo` та переконатися, що всі підлеглі бібліотеки передаються лінкеру.

Розподіл пакетів на середовище виконання та середовище розробки разом із декларативними метаданими `pkg-config` створює надійний, передбачуваний фундамент керування залежностями в екосистемі Unix, гарантуючи стабільність системного оточення та гнучкість процесу компіляції.
