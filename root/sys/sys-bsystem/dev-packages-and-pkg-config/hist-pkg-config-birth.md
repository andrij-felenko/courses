# 📜 Від хаосу *-config скриптів до декларативного pkg-config

Наприкінці 1990-х років розробка прикладного програмного забезпечення для Unix та графічного середовища X11 зіткнулася з кризою масштабування системних залежностей. Програми перетворювалися з монолітних кодових баз на модульні конструкції, що спиралися на десятки сторонніх бібліотек: графічний інтерфейс GTK+, бібліотеку базових структур GLib, рендерер шрифтів FreeType, парсер XML `libxml2` та мультимедійну підсистему SDL.

Для кожної такої бібліотеки виникало те саме завдання: як сценарій конфігурації залежного проєкту (`./configure` на базі GNU Autotools) має дізнатися, де саме у файловій системі встановлено файли заголовків, у якому каталозі лежать скомпільовані бінарні файли та які саме прапорці потрібно передати компілятору й лінкеру?

## Епоха індивідуальних сценаріїв *-config

Першим рішенням, яке масово заполонило екосистему Unix, стало створення кожною бібліотекою власного виконуваного сценарію командної оболонки. Якщо проєкт називався `libfoo`, його автори створювали й установлювали в системний каталог `/usr/bin` або `/usr/local/bin` виконуваний файл `foo-config` (наприклад `gtk-config`, `glib-config`, `sdl-config`, `xml2-config`, `freetype-config`, `curl-config`).

Цей сценарій підтримував стандартний набір аргументів командного рядка:
- `foo-config --cflags` виводив препроцесорні шляхи включення на зразок `-I/usr/include/foo -D_REENTRANT`;
- `foo-config --libs` друкував прапорці лінкування, наприклад `-L/usr/lib -lfoo`;
- `foo-config --version` повертав рядок поточної версії.

Сценарій `configure.ac` прикладного проєкту викликав ці утиліти всередині підпроцесів shell через зворотні лапки або конструкцію `$(...)`:

```bash
# Типовий фрагмент configure.ac кінця 1990-х
GTK_CFLAGS=$(gtk-config --cflags)
GTK_LIBS=$(gtk-config --libs)
AC_SUBST(GTK_CFLAGS)
AC_SUBST(GTK_LIBS)
```

## Чому модель *-config зазнала колапсу

На практиці підхід із генерацією десятків окремих виконуваних сценаріїв містив чотири фундаментальні архітектурні вади, які зробили його непридатним для великих програмних систем.

### 1. Катастрофічне падіння швидкості конфігурації
Кожен виклик `*-config` породжував новий процес командної оболонки `/bin/sh`. Середній проєкт середовища GNOME використовував 15–25 сторонніх бібліотек. На етапі конфігурації сценарій перевіряв наявність бібліотек, їхні версії, прапорці компіляції та прапорці лінкування, виконуючи сотні послідовних викликів зовнішніх сценаріїв. На операційних системах із повільним створенням процесів (зокрема Windows через емуляцію Cygwin) фаза `./configure` могла тривати понад пів години.

### 2. Лавиноподібне розмноження дублікатів прапорців
Сценарії `*-config` були ізольованими програмами й нічого не знали один про одного. Розглянемо класичну проблему «діамантової залежності» (англ. *diamond dependency*):
- Графічна бібліотека `libgtk` використовує бібліотеку роботи із зображеннями `gdk-pixbuf` та рендерер тексту `pango`.
- І `gdk-pixbuf`, і `pango` всередині викликають базову бібліотеку `glib`.
- Усі три бібліотеки звертаються до системної бібліотеки потоків `pthread`.

Коли додаток збирав прапорці, викликаючи `gtk-config --cflags --libs`, `pango-config --cflags --libs` та `gdk-pixbuf-config --cflags --libs`, підсумковий командний рядок компілятора GCC роздувався до десятків кілобайт:
```bash
gcc main.c -I/usr/include/glib-1.2 -I/usr/lib/glib/include -I/usr/include/glib-1.2 -I/usr/lib/glib/include -I/usr/include/pango-1.0 -I/usr/include/glib-1.2 -L/usr/lib -lgtk -L/usr/lib -lgdk -L/usr/lib -lpango -L/usr/lib -lglib -lpthread -L/usr/lib -lglib -lpthread ...
```
Сценарії не мали централізованого механізму усунення дублікатів і топологічного сортування. У результаті лінкер багаторазово відкривав ті самі каталоги на диску, а порядок передачі прапорців `-l` часто порушувався, що спричиняло помилки відсутності символів під час статичного лінкування.

### 3. Повна непридатність до крос-компіляції
Сценарії `*-config` встановлювалися як системні виконувані бінарники хост-машини. Коли розробник на робочій станції з архітектурою x86_64 намагався зібрати прошивку для цільової плати з процесором ARM, виклик команди `gtk-config --libs` повертав шляхи до бібліотек операційної системи хоста (`/usr/lib`), а не каталогу цільової платформи (sysroot). Передача хостових бінарних шляхів у крос-компілятор ламала весь процес збірки. Перевизначити шляхи всередині жорстко закодованого shell-скрипта без модифікації його вихідного коду було практично неможливо.

### 4. Непереносимість між операційними системами
Сценарії вимагали наявності повноцінного інтерпретатора командної оболонки POSIX (`/bin/sh`). На платформі Microsoft Windows розробники не могли скористатися цими інструментами в нативному середовищі Visual Studio або MSVC без встановлення важких прошарків емуляції.

## Поява pkg-config у 2000 році: декларативна революція

У 2000 році інженер Ред Гет (Red Hat) та один із ключових розробників проєкту GNOME Гевок Пеннінґтон (англ. *Havoc Pennington*) запропонував кардинальну зміну парадигми: **метадані бібліотек мають бути суворо декларативними даними, а не виконуваним програмним кодом**.

Замість написання сотень індивідуальних сценаріїв авторам бібліотек було запропоновано поширювати простий текстовий файл із розширенням `.pc` (наприклад `gtk+-2.0.pc`), який містить звичайні текстові змінні та ключові поля:
- яку назву та версію має пакет;
- від яких інших `.pc` пакетів він залежить публічно чи приватно;
- які каталоги включення та прапорці лінкера потрібні саме цій бібліотеці.

Для обробки цих метаданих Пеннінґтон написав єдину високопродуктивну утиліту мовою C — **`pkg-config`**.

```
[Стара модель *-config]
Сценарій збірки ───> fork(/bin/sh gtk-config) ───> виведення прапорців (жорсткі шляхи хоста)
                 ───> fork(/bin/sh glib-config) ───> дублювання прапорців
                 ───> fork(/bin/sh pango-config)───> ламання порядку лінкування

[Нова модель pkg-config]
                     ┌──> зчитує gtk+-2.0.pc
Сценарій збірки ───> │──> зчитує pango.pc     ───> будує граф залежностей (DAG)
 (pkg-config)        └──> зчитує glib-2.0.pc  ───> видаляє дублікати, вирівнює порядок
                                              ───> видає єдиний очищений рядок прапорців
```

Утиліта `pkg-config` брала на себе всю складну логіку:
1. Завантажувала `.pc` файли всіх запитаних бібліотек.
2. Рекурсивно розгортала дерево залежностей через поля `Requires` та `Requires.private`.
3. Будувала спрямований ациклічний граф (DAG) і виконувала його топологічне сортування, гарантуючи, що високорівневі бібліотеки передаються лінкеру раніше за низькорівневі базові модулі.
4. Автоматично усувала повторювані прапорці `-I` та `-L`.
5. Підтримувала змінні середовища `PKG_CONFIG_PATH` та `PKG_CONFIG_SYSROOT_DIR`, вирішивши проблему крос-компіляції раз і назавжди.

## Перехід до pkgconf

Оригінальна реалізація `pkg-config` від Freedesktop.org спиралася на внутрішній примірник бібліотеки GLib для роботи з рядками, хеш-таблицями та графами. Це створювало парадоксальну циклічну залежність: щоб зібрати GLib, потрібен був `pkg-config`, а щоб зібрати `pkg-config`, потрібні були базові алгоритми GLib.

У 2011 році розробниця Аріадна Конілл (англ. *Ariadne Conill*, дистрибутив Alpine Linux) започаткувала проєкт **`pkgconf`**. Це була повна заміна `pkg-config`, написана чистою мовою C99 без жодних зовнішніх залежностей під ліберальною ліцензією ISC.

`pkgconf` запропонував фундаментальні вдосконалення:
- Повністю позбувся важких сторонніх бібліотек, що дозволило збирати його на ранніх етапах побудови мінімальних Linux-дистрибутивів (bootstrap).
- Надав бібліотеку `libpkgconf`, дозволивши системам збірки (наприклад Meson) та інтегрованим середовищам розробки вбудовувати пошук пакетів прямо у свій бінарний код без виклику зовнішніх процесів.
- Додав коректну підтримку прапорців `Cflags.private` та поліпшену нормалізацію префіксів `sysroot`.

Сьогодні практично всі провідні дистрибутиви Linux (Alpine, Fedora, Arch Linux, Debian, Ubuntu) та операційні системи сімейства BSD використовують `pkgconf` як штатну реалізацію команди `pkg-config`, зберігаючи повну зворотну сумісність із форматом файлів `.pc`, закладеним на початку 2000-х років.
