# 📜 Еволюція герметичних систем збірки: від Google Blaze до Buck2

Коли обсяг кодової бази компанії перетинає межу в десятки мільйонів рядків, а над єдиним репозиторієм одночасно працюють тисячі інженерів, традиційні утиліти збірки стикаються з нездоланною кризою масштабування. Історія герметичних систем збірки — це історія поступової відмови від неявного стану операційної системи на користь суворої математичної моделі чистих функцій.

## Криза Make у монорепозиторії Google та народження Blaze (2006)

На початку 2000-х років компанія Google прийняла фундаментальне архітектурне рішення: зберігати майже весь сирцевий код компанії (сервіси пошуку, реклами, карти, внутрішню інфраструктуру) в одному гігантському монорепозиторії. Збірка проєктів спочатку спиралася на складний лабіринт із файлів `Makefile` та скриптів генерації на Perl і Python.

Цей підхід зазнав краху з трьох причин:
1. **Недетерміністичні побічні ефекти**. Кожен розробник мав власну версію дистрибутиву Linux (glibc, libstdc++, системні бібліотеки в `/usr/lib`), через що успішно скомпільований на одній робочій станції бінарний файл падав із помилкою сегментації на серверах або машинах колег.
2. **Неможливість надійного кешування**. Make перевіряє лише позначки часу модифікації файлів (`mtime`). У розподіленій системі контролю версій операції `git checkout` або оновлення репозиторію змінюють `mtime` тисяч файлів без зміни їхнього фактичного змісту, провокуючи каскадну перекомпіляцію всього проєкту з нуля.
3. **Лінійні вузькі місця**. Відсутність точного графа дій унеможливлювала безпечний паралельний запуск компіляторів на сотнях віддалених серверів.

У 2006 році інженери Google створили систему **Blaze**. Замість імперативних скриптів, які могли виконувати довільні команди операційної системи, Blaze запропонувала декларативну модель. Розробники описували лише високорівневі цілі (бібліотеки, тести, бінарники), а рушій будував ациклічний граф елементарних дій (Action Graph).

Головною інновацією Blaze стала **герметичність**: компілятори Clang і GCC, системні бібліотеки sysroot та всі інструменти збірки були запаковані як незмінні бінарні артефакти всередині самого репозиторію. Компіляція відбувалася виключно в ізольованих пісочницях, що усунуло залежність від хостової операційної системи.

## Відкриття Bazel та мультимовний стандарт (2015)

Blaze був глибоко інтегрований у внутрішню інфраструктуру Google (протоколи Borg, Bigtable, внутрішні розподілені файлові системи), тому сторонні розробники не могли його запустити. У березні 2015 року Google випустила відкриту версію системи під назвою **Bazel** (анаграма слова Blaze).

Bazel стандартизувала мову конфігурації **Starlark** (раніше відому як Skylark) — детермінований діалект Python без доступу до системного годинника, мережі та файлової системи. Це гарантувало, що фаза обчислення графа залежностей завжди продукує абсолютно однаковий набір дій незалежно від машини, на якій запускається збірка.

Одночасно Bazel ввела індустріальний стандарт протоколу **Remote Execution API (REAPI)**. Це дозволило відокремити локальний клієнт збірки від обчислювального кластера: локальний ноутбук інженера лише генерує граф дій, а сотні паралельних компіляцій виконуються на пулі віддалених контейнерів із розподіленим кешуванням.

## Buck у Facebook: оптимізація для мобільної розробки (2013)

Паралельно з Google подібні виклики постали перед інженерами Facebook. Розробка мобільних додатків для Android та iOS вимагала збірки гігантських проєктів із десятками тисяч модулів на Java, C++, Objective-C та Swift.

У 2013 році Facebook випустила власну відкриту систему герметичної збірки — **Buck**. Перше покоління Buck фокусувалося на оптимізації правил для мобільних платформ:
- Введення кешування на основі ABI (якщо інтерфейс класу не змінився, залежні модулі не перекомпілюються, навіть якщо тіло методу зазнало правок).
- Архітектура на базі JVM, що забезпечувала високу швидкість обробки Java-байткоду.

Однак перше покоління Buck страждало від високого споживання пам'яті через JVM-рантайм, складності динамічного розширення правил користувачами та труднощів підтримки нових мов (Rust, Go).

## Поява Pants та альтернативних рішень

У цей самий період компанії Twitter, Foursquare та Square розробили систему **Pants**. Як і Blaze та Buck, Pants орієнтувалася на підтримку монорепозиторіїв, спершу зосередившись на екосистемі JVM (Scala, Java) та Python.

У версії Pants v2 архітектуру було повністю переписано на мові Rust з асинхронним рушієм обчислень на базі моделі акторів, що довело життєздатність концепції графа дій за межами Java-екосистеми.

## Переосмислення парадигми: Buck2 на Rust (2023)

У 2023 році компанія Meta представила **Buck2** — систему збірки нового покоління, створену з нуля на мові Rust після десятиліття експлуатації першого Buck.

Buck2 втілила кілька фундаментальних архітектурних рішень, що розв'язали давні проблеми Bazel та першого Buck:

| Характеристика | Bazel | Buck v1 | Buck2 |
|---|---|---|---|
| **Мова ядра** | Java / C++ | Java | Rust |
| **Рушій інкрементальності** | Skyframe | Спеціалізований DAG | DICE (асинхронні обчислення) |
| **Мова правил** | Вбудований Starlark (Java) | Python / Java | starlark-rust (чистий Starlark) |
| **Архітектура правил** | Вбудовані в ядро (C++/Java) + bzl | Вбудовані в ядро (Java) | 100% правил винесено в Starlark |
| **Remote Execution** | REAPI v2 (через gRPC) | Власний протокол | Рідна інтеграція REAPI v2 |
| **Споживання пам'яті** | Високе (JVM heap + GC паузи) | Високе (JVM heap) | Низьке (контрольоване Rust RAII) |

Головною інновацією Buck2 став рушій **DICE** (*Distributed Incremental Computation Engine*). DICE розглядає весь процес збірки як гігантське динамічне дерево обчислень. Якщо у процесі збірки генерується новий файл або змінюється значення конфігурації, DICE автоматично реінвалідує лише ті вузли графа, які безпосередньо залежать від змінених даних, без необхідності повторного проходження фази глобального аналізу.

Крім того, у Buck2 саме ядро системи не містить жодного рядка коду, специфічного для C++, Rust чи Java: усі правила збірки від найпростіших бібліотек до складних пакунків реалізовані як зовнішні плагіни на мові Starlark.

Еволюція герметичних систем перетворила процес збірки програмного забезпечення з ненадійного набору скриптів на строгу інженерну дисципліну з криптографічними гарантіями цілісності та необмеженим потенціалом горизонтального масштабування.
