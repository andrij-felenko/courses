У п'ятницю ввечері інженер відправляє останні зміни в репозиторій: усі автоматизовані тести проходять успішно, збірка на сервері неперервної інтеграції сяє зеленим статусом, а скомпільований бінарний файл бездоганно розгортається на тестовому стенді. У понеділок вранці, без жодного нового коміту у власному репозиторії проєкту, черговий запуск збірки несподівано завершується аварійною відмовою компілятора через синтаксичну помилку в сторонньому заголовку або, що значно гірше, бінарник успішно збирається, але падає із помилкою сегментації пам'яті `SIGSEGV` на першому ж клієнтському запиті.

Ця катастрофа трапляється через те, що у вихідному коді проєкту залежності було оголошено через відкриті, «плаваючі» діапазони версій або незакріплені гілки репозиторіїв. За вихідні автори однієї з транзитивних бібліотек випустили нову версію, яка формально заявлялася як «сумісне виправлення помилок», але на практиці змінила внутрішню поведінку, додала невидиме поле у структуру чи зламала двійковий інтерфейс (ABI). Менеджер пакетів під час чергового запуску звернувся до публічного реєстру, побачив новий реліз і автоматично підтягнув його у збірку.

Керування залежностями вимагає непохитного детермінізму: однаковий вихідний код, скомпільований сьогодні, через місяць чи через п'ять років, зобов'язаний збиратися з абсолютно ідентичних двійкових компонентів. Головним інструментом досягнення цієї стабільності є закріплення версій (англ. *version pinning*, від англ. *pin* — шпилька, пришпилювати) та використання замкових файлів (англ. *lockfiles*, від англ. *lock* — замок та *file* — файл).

## 1. Проблема «вчора збиралося, сьогодні ні»: природа неявного дрейфу

Класичні системи опису залежностей (такі як `conanfile.txt`, `Cargo.toml` чи `package.json`) створювалися для того, щоб розробник міг декларувати гнучкі наміри: «моєму проєкту потрібна будь-яка версія бібліотеки OpenSSL від 3.0.0 до 4.0.0» або «підійде сумісний реліз Boost 1.83.x». Проте між декларацією наміру та реальною фізичною компіляцією лежить прірва, яку заповнює алгоритм розв'язання залежностей (англ. *dependency resolution algorithm*).

![Плаваючі версії проти детермінізму замкового файлу](/root/sys/sys-bsystem/version-pinning/img/version-resolution-vs-lockfile.svg)
*Плаваючі діапазони версій призводять до неконтрольованого дрейфу коду з часом, тоді як замковий файл фіксує точний знімок графа.*

Коли збірка спирається на динамічні обмеження, виникають чотири фундаментальні джерела деградації:

### 1. Неконтрольований транзитивний дрейф (Transitive Drift)
Навіть якщо розробник жорстко зафіксував версії своїх прямих залежностей у маніфесті (наприклад, `libpng = "1.6.40"`), сама бібліотека `libpng` у власному маніфесті може вимагати компресор `zlib >= 1.2.11`. Якщо розробники `zlib` випускають версію `1.3.0`, менеджер пакетів автоматично підвищує транзитивну версію. Зміна одного непрямого вузла на п'ятому рівні вкладеності графа здатна змінити поведінку всієї програми.

### 2. Залежність від зовнішнього часу розв'язання
Результат роботи команди інсталяції пакетів залежить не від стану вашого Git-репозиторію, а від поточного фізичного часу виконання команди та вмісту віддаленого реєстру. Збірка стає недетермінованою функцією: `build(commit, time_t)`. Запуск збірки на машині розробника о 10:00 дає один граф залежностей, а запуск на білд-сервері о 10:05 — уже інший, якщо в цей п'ятихвилинний інтервал відбувся реліз стороннього пакета.

### 3. Комбінаторна нестабільність SAT-солвера
Сучасні менеджери пакетів використовують алгоритми задоволення булевих формул (SAT-солвери, PubGrub, CDCL) для пошуку несуперечливого набору версій у багатовимірному просторі обмежень. Додавання одного нового стороннього релізу в центральний реєстру може призвести до того, що солвер обере принципово іншу гілку всього дерева залежностей, перемкнувши десятки взаємопов'язаних бібліотек на альтернативні версії.

### 4. Ілюзія стабільності гілок та тегів Git
Використання прямих посилань на Git-гілки (наприклад, `branch = "main"` або `branch = "v1.x"`) є прямою відмовою від контролю версій. Гілка є рухомим покажчиком, який мутує з кожним комітом автора бібліотеки. Навіть використання тегів Git (наприклад, `tag = "v1.2.0"`) без криптографічного контролю хешів є небезпечним, оскільки власник репозиторію може видалити тег і створити його наново на іншому коміті (`git tag -f`).

Історичну хроніку того, як індустрія усвідомила критичність цієї проблеми після масштабних збоїв на кшталт Left-pad та впровадила інститут замкових файлів, детально викладено у довідці: [історію еволюції замкових файлів та атак на ланцюг постачання](root:sys-bsystem/version-pinning/hist-lockfiles-and-supply-chain.md).

## 2. Семантичне версіонування (SemVer) та його пастки в нативному коді

Щоб упорядкувати хаос сумісності, у 2011 році Том Престон-Вернер (Tom Preston-Werner, співзасновник GitHub) сформулював специфікацію **Семантичного версіонування** (SemVer — англ. *Semantic Versioning*, від лат. *semantikos* — значущий та *versio* — видозміна).

Згідно зі стандартом SemVer, номер версії складається з трьох числових компонентів:

```
MAJOR . MINOR . PATCH
  │       │       │
  │       │       └── зворотньо сумісні виправлення дефектів (Bug fixes)
  │       └────────── зворотньо сумісна нова функціональність (Features)
  └────────────────── несумісні зміни прикладного інтерфейсу (Breaking API changes)
```

Правила здаються кришталево прозорими:
* Зміна `PATCH` (`1.4.1` → `1.4.2`) зобов'язана виправляти внутрішні помилки без зміни інтерфейсу;
* Зміна `MINOR` (`1.4.0` → `1.5.0`) додає нові функції, зберігаючи працездатність старого коду;
* Зміна `MAJOR` (`1.0.0` → `2.0.0`) сигналізує про видалення чи модифікацію існуючого контракту.

Менеджери залежностей використовують ці правила для автоматичного оновлення: оператор `^1.4.0` дозволяє оновлюватися до будь-якої версії `< 2.0.0`, очікуючи, що `MINOR` та `PATCH` ніколи не зламають збірку.

Проте у світі системного програмування на C та C++ ця концепція регулярно зазнає краху.

![Ілюзія безпеки SemVer у C++ та поломка ABI](/root/sys/sys-bsystem/version-pinning/img/semver-vs-abi-breakage.svg)
*Семантичне версіонування у C/C++: зміна внутрішнього розміру структури в патч-релізі ламає двійковий інтерфейс ABI й спричиняє пошкодження стека.*

### Пастка 1: Розрив між API та ABI
SemVer було створено насамперед для мов із динамічною типізацією (Ruby, JavaScript, Python), де сумісність визначається виключно наявністю функцій із відповідними іменами. У компільованих мовах C та C++ існують два ортогональні рівні сумісності:
1. **API (Application Programming Interface):** сумісність на рівні вихідного коду. Якщо старий код компілюється без помилок синтаксису — API збережено;
2. **ABI (Application Binary Interface):** сумісність на рівні машинних інструкцій та двійкового представлення пам'яті.

Розглянемо класичний приклад патч-оновлення бібліотеки автентифікації:

:::tabs
```c
/* Версія v1.0.0: auth_session.h */
struct UserSession {
    uint32_t user_id;
    char token[32];
};

void init_session(struct UserSession* s);
int validate_session(const struct UserSession* s);
```
```cpp
// Версія v1.0.0: auth_session.hpp
#include <cstdint>
#include <string_view>
#include <array>

struct UserSession {
    uint32_t user_id;
    std::array<char, 32> token;
};

void init_session(UserSession* s);
[[nodiscard]] bool validate_session(const UserSession* s);
```
:::

У версії `v1.0.1` розробник бібліотеки вирішив виправити помилку обліку прав і додав логічний прапорець:

:::tabs
```c
/* Версія v1.0.1 (PATCH!): auth_session.h */
struct UserSession {
    uint32_t user_id;
    char token[32];
    uint8_t is_admin; /* Додано нове поле для багфіксу */
};

void init_session(struct UserSession* s);
int validate_session(const struct UserSession* s);
```
```cpp
// Версія v1.0.1 (PATCH!): auth_session.hpp
#include <cstdint>
#include <array>

struct UserSession {
    uint32_t user_id;
    std::array<char, 32> token;
    bool is_admin; /* Додано нове поле для багфіксу */
};

void init_session(UserSession* s);
[[nodiscard]] bool validate_session(const UserSession* s);
```
:::

З точки зору вихідного коду (API) зміна є бездоганною: сигнатури функцій `init_session` та `validate_session` не змінилися. Автор публікує реліз як сумісний `PATCH` `1.0.1`.

Проте на рівні двійкового інтерфейсу (ABI) сталася катастрофа:
* Розмір структури `sizeof(UserSession)` збільшився з 36 до 40 байтів (із урахуванням компіляторного вирівнювання пам'яті);
* Головна програма, скомпільована проти заголовків `v1.0.0`, виділяє на стеку рівно 36 байтів;
* Оновлена динамічна бібліотека `v1.0.1` під час виклику `init_session` записує 40 байтів, перезаписуючи сусідні змінні стека або адресу повернення з функції.

Результатом «сумісного патч-оновлення» стає приховане пошкодження пам'яті (Memory Corruption) або фатальне аварійне завершення процесу під час виконання.

### Пастка 2: Шаблони, вбудовані функції та ODR
У мові C++ значна частина коду живе безпосередньо в заголовочних файлах у вигляді шаблонів (`template<typename T>`) та вбудованих функцій (`inline`). Тіла цих функцій транслюються компілятором у машинний код безпосередньо всередині кожного файлу `.cpp` проєкту-споживача.

Якщо бібліотека в патч-релізі змінює алгоритм усередині `inline`-функції, а проєкт через складне дерево транзитивних залежностей збирає частину модулів зі старою версією заголовків, а частину — з новою, порушується **Правило одного визначення** (One Definition Rule, ODR). Компонувальник бере довільну з двох несумісних реалізацій функції, що призводить до непередбачуваної поведінки скомпільованого бінарника.

### Пастка 3: Закон Хайрума (Hyrum's Law)
Сформульований інженером Google Хайрумом Райтом (Hyrum Wright), закон стверджує:
> *«За достатньої кількості користувачів API не має значення, що саме ви обіцяєте в контракті: усі спостережувані особливості поведінки вашої системи стануть для когось критичною залежністю».*

Виправлення неочевидного дефекту в бібліотеці (наприклад, зміна порядку ітерації по геш-таблиці, зміна коду повернення на невалідний вхідний аргумент або виправлення граничних умов таймера) розглядається автором як безпечний `PATCH`. Але якщо код вашого проєкту неявно покладався на цю стару «помилкову» поведінку, патч-оновлення гарантовано зламає працездатність системи.

## 3. Діапазони версій проти точного закріплення: дилема бібліотек та застосунків

Для опису вимог до версій менеджери пакетів підтримують набір операторів діапазонів (англ. *version ranges*):

| Оператор | Синтаксис | Дозволений діапазон оновлень | Призначення |
| :--- | :--- | :--- | :--- |
| **Точне закріплення (Exact)** | `=1.2.3` або `1.2.3` | Тільки версія `1.2.3` (байт-у-байт) | Фіксація для кінцевих продуктів |
| **Тільда (Tilde Range)** | `~1.2.3` | `>= 1.2.3` та `< 1.3.0` | Дозволяє тільки `PATCH` оновлення |
| **Карет (Caret Range)** | `^1.2.3` | `>= 1.2.3` та `< 2.0.0` | Дозволяє `MINOR` та `PATCH` |
| **Карет для 0.x (SemVer Zero)**| `^0.2.3` | `>= 0.2.3` та `< 0.3.0` | У версіях `0.x` мінорний номер вважається ламаючим |
| **Реляційні оператори** | `>=1.2.0, <2.0` | Інтервал між двома межами | Гнучкий опис вимог бібліотек |
| **Підстановочний символ** | `1.2.*` або `*` | Будь-який реліз у межах гілки | Найбільш небезпечний плаваючий режим |

Вибір між гнучкими діапазонами та точним закріпленням породжує класичну інженерну дилему, розв'язання якої залежить від природи артефакту, що розробляється:

```
                  АРТЕФАКТ РОЗРОБКИ
                         │
        ┌────────────────┴────────────────┐
        ▼                                 ▼
   БІБЛІОТЕКА                        ЗАСТОСУНОК
(Re-distributable Lib)           (Deployable Target)
        │                                 │
Вимога: ГНУЧКІ ДІАПАЗОНИ          Вимога: ТОЧНЕ ЗАКРІПЛЕННЯ
(^1.2, >=2.0)                     (Exact Pinning + Lockfile)
        │                                 │
Мета: уникати конфліктів          Мета: 100% детермінізм
у споживачів                      та захист від поломок
```

### 1. Правило для бібліотек (Libraries / Packages)
Якщо ви розробляєте бібліотеку, призначену для використання іншими розробниками, у маніфесті (`conanfile.py`, `vcpkg.json`, `Cargo.toml`) слід вказувати **гнучкі діапазони версій** (`^` або `>=`). 

Якщо бібліотека `A` жорстко вимагатиме `=1.2.3` для `zlib`, а сусідня бібліотека `B` жорстко вимагатиме `=1.2.4`, розробник кінцевої програми не зможе скомпілювати свій проєкт: менеджер залежностей повідомить про нерозв'язний ромбоподібний конфлікт (Diamond Conflict). Гнучкі діапазони дозволяють солверу знайти спільну версію, яка задовольняє всіх споживачів у графі.

### 2. Правило для кінцевих застосунків (Applications / Services / Firmware)
Якщо ви розробляєте кінцевий продукт (вебсервіс, десктопний застосунок, вбудовану прошивку для мікроконтролера), уся збірка **зобов'язана бути жорстко заблокована**. На рівні виконуваного файлу гнучкість є джерелом хаосу. На машині розробника та у репозиторії обов'язково повинен бути зафіксований замковий файл.

### 3. Закріплення вихідного коду в CMake через FetchContent
Якщо сторонній модуль підключається засобами CMake через модуль `FetchContent`, класичною помилкою є вказування тегу або гілки:

```cmake
# НЕБЕЗПЕЧНО: Тег може бути переміщений або видалений, а гілка мутує щодня
FetchContent_Declare(
    fmt
    GIT_REPOSITORY https://github.com/fmtlib/fmt.git
    GIT_TAG        10.1.1 # Рухомий показчик без контролю хешу!
)
```

Детерміноване закріплення вимагає вказування точного 40-символьного SHA-1 коміту Git:

```cmake
# ДЕТЕРМІНОВАНО: Повний коміт гарантує незмінність байтів
FetchContent_Declare(
    fmt
    GIT_REPOSITORY https://github.com/fmtlib/fmt.git
    GIT_TAG        e69e5f977d4bfbf5d83d63c57d9f79b360b0e7b9
    GIT_SHALLOW    TRUE
)
```

## 4. Анатомія та механіка Lockfiles

Замковий файл (англ. *lockfile*) — це структурований документ, який містить вичерпний, статичний знімок (англ. *snapshot*) усього розв'язаного графа залежностей. Він генерується автоматично під час першого розв'язання маніфесту та зберігається поруч із вихідним кодом у системі Git.

![Анатомія вузла в замковому файлі](/root/sys/sys-bsystem/version-pinning/img/lockfile-integrity-hash-tree.svg)
*Структура заблокованого вузла: криптографічні хеші вихідних кодів, ревізії рецептів та конфігураційні ідентифікатори бінарників.*

Повний замковий файл містить п'ять критичних вимірів фіксації для кожного вузла графа:

1. **Точний ідентифікатор та версія:** повне ім'я пакета та номер релізу без будь-яких символів діапазонів (`zlib = "1.3.1"`);
2. **Криптографічний хеш вихідного коду (Source Digest / SRI):** контрольна сума SHA-256 або SHA-512 вихідного архіву чи точний 40-символьний хеш Git-коміту. Це унеможливлює атаку підміни вмісту на стороні сервера;
3. **Ревізія рецепта збірки (Recipe Revision, RREV):** хеш файлу інструкцій збірки (наприклад, `conanfile.py` або `portfile.cmake`). Якщо автор бібліотеки не змінював версію `1.3.1`, але змінив прапорці компіляції в рецепті, замок зафіксує цю зміну;
4. **Ідентифікатор двійкової конфігурації (Package ID / PREV):** хеш середовища компіляції (компілятор GCC 13, C++20, Release, CRT `/MD`, підтримка AVX2). Це гарантує точну двійкову сумісність (ABI);
5. **Фіксований список дочірніх ребер:** явний перелік заблокованих транзитивних залежностей, що унеможливлює підтягування сторонніх вузлів у граф.

### Реалізації Lockfile у нативних менеджерах пакетів

Формати та механізми блокування відрізняються між екосистемами, пропонуючи різні рівні гранулярності контролю:

#### 1. Conan 2.0 (`conan.lock`)
У Conan 2.0 замковий файл зберігається у форматі JSON. Він повністю кодує орієнтований ациклічний граф (DAG), розділяючи залежності цільової платформи (`host context`) та інструментів компіляції (`build context`, наприклад, CMake чи кодогенератори):

```bash
# Створення або оновлення замкового файлу з маніфесту
conan lock create conanfile.py --version=1.0.0 --lockfile-out=conan.lock

# Збирання проєкту в суворому режимі замка
conan install . --lockfile=conan.lock --build=missing
```

#### 2. Rust Cargo (`Cargo.lock`)
Cargo автоматично створює `Cargo.lock` у форматі TOML. Для кожного крейта записується рядок `checksum`, що містить SHA-256 хеш архіву `.crate` з реєстру `crates.io`:

```bash
# Збирання із суворою перевіркою замка (заборона будь-яких змін файлу)
cargo build --locked
```

#### 3. Microsoft vcpkg (Baselines та Overrides)
Менеджер `vcpkg` використовує дещо іншу архітектуру: замість окремого lock-файлу він спирається на маніфест `vcpkg.json` та конфігурацію `vcpkg-configuration.json`. Фіксація всього всесвіту пакетів реалізується через механізм **базового коміту (Baseline)** — хешу коміту Git в офіційному репозиторії `microsoft/vcpkg`:

```json
{
  "default-registry": {
    "kind": "git",
    "repository": "https://github.com/microsoft/vcpkg.git",
    "baseline": "a42af01b72c28c8117d3cf524ec946770f9e6870"
  }
}
```

Якщо конкретному проєкту потрібна відмінна від базової версія, вона жорстко закріплюється у блоці `overrides` маніфесту `vcpkg.json`.

Детальні структури даних, специфікації JSON-схем та таблиці атрибутів для всіх форматів наведено у довіднику: [специфікації форматів замкових файлів](root:sys-bsystem/version-pinning/api-lockfile-specifications.md).

## 5. Оновлення замків, аудит безпеки та атаки на ланцюг постачання

Замковий файл робить систему статичною. Проте програмне забезпечення не може залишатися незмінним вічно: у сторонніх бібліотеках виявляються критичні вразливості (CVE), виправляються помилки оптимізації та з'являється підтримка нових стандартів.

Головний принцип роботи з замками: **Оновлення залежностей має бути свідомим, ізольованим інженерним процесом, а не побічним наслідком випадкової збірки.**

```
                                  ЦИКЛ ОНОВЛЕННЯ ЗАМКА
                                           │
  ┌────────────────────────────────────────┴────────────────────────────────────────┐
  ▼                                        ▼                                        ▼
1. АУДИТ БЕЗПЕКИ                  2. ТОЧКОВЕ ОНОВЛЕННЯ                    3. АВТОМАТИЗОВАНЕ
(CVE / OSV Scanning)              (Targeted Lockfile Update)              РЕГРЕСІЙНЕ ТЕСТУВАННЯ
  │                                        │                                        │
Виявлення вразливих                cargo update -p zlib                   Повний прогін тестів
пакетів у замку                    conan lock create --update             усіх платформ у CI
```

### Безпечний життєвий цикл оновлення (Lockfile Lifecycle)

1. **Сканування вразливостей (CVE Scanning):**
   Замковий файл є ідеальним джерелом даних для аудиту безпеки, оскільки він містить точний перелік усіх скомпільованих версій та їхніх криптографічних хешів. Спеціалізовані сканери (наприклад, `cargo audit`, `osv-scanner`, `trivy`) зіставляють вміст замкового файлу з базами даних відомих вразливостей (National Vulnerability Database, GitHub Security Advisories).
2. **Точкове кероване оновлення:**
   Замість сліпого оновлення всього графа інженер виконує точкову актуалізацію конкретної бібліотеки:
   * `cargo update -p openssl` — оновлює в `Cargo.lock` виключно OpenSSL та його внутрішні підзалежності, залишаючи решту графа недоторканою;
   * `conan lock create --update` — перераховує новий стан для зазначених вузлів.
3. **Регресійне тестування та аудит дифу (Diff Review):**
   Змінений `lockfile` формує окремий Git Pull Request. Інженер зобов'язаний уважно переглянути текстовий diff замка, переконавшись, що оновлення не підтягнуло підозрілих сторонніх пакетів, після чого повний набір тестів у CI підтверджує працездатність системи.

### Захист від векторів атак на ланцюг постачання (Supply Chain Attacks)

Замковий файл є головним бар'єром захисту від сучасних кібератак:

#### 1. Атака заміщення залежностей (Dependency Confusion)
Зловмисник публікує у відкритому публічному реєстрі (наприклад, npm чи crates.io) шкідливий пакет із назвою вашого внутрішнього закритого корпоративного модуля (наприклад, `internal-crypto-auth`), встановлюючи версію `999.0.0`. Якщо у збірці відсутній замковий файл, менеджер завантажить «новішу» шкідливу версію з публічного інтернету. 

Замковий файл повністю нівелює цю загрозу: він жорстко фіксує точний URL джерела завантаження та SHA-256 хеш внутрішнього релізу, ігноруючи сторонні публікації.

#### 2. Тайпсквотинг та захоплення облікових записів (Typosquatting & Account Hijack)
Якщо зловмисник зламав акаунт розробника сторонньої бібліотеки й випустив шкідливий патч `1.2.4`, розробники з плаваючими діапазонами (`^1.2.0`) автоматично підтягнуть бекдор під час наступної збірки. Проєкти з незмінним замковим файлом залишаться на перевіреній версії `1.2.3` і будуть захищені, доки спільнота безпеки не відкличе скомпрометований реліз.

#### 3. Модифікація релізних архівів (Tarball Tampering)
Якщо хакери скомпрометували сервер дистрибуції стороннього коду й замінили архів із вихідними текстами без зміни номеру версії (як це відбувалося під час інциденту з бекдором у `xz-utils` CVE-2024-3094), менеджер пакетів під час завантаження обчислить SHA-256 архіву, зафіксує невідповідність еталонному хешу в `lockfile` та аварійно зупинить інсталяцію.

Практичну реалізацію автоматизованого скрипта контролю цілісності замків наведено у розробці: [практичний валідатор замкових файлів для CI/CD](root:sys-bsystem/version-pinning/proj-lockfile-ci-checker.md).

## 6. Інтеграція в CI/CD: режим строгого замка (--locked)

Найбільш критичною ланкою системи є конвеєр неперервної інтеграції (CI/CD). На білд-серверах діє залізне правило:

> **Білд-агент не має права думати, розв'язувати обмеження чи змінювати замковий файл. Він зобов'язаний виключно збирати те, що зафіксовано в Git.**

![Конвеєр CI/CD та захист ланцюга постачання](/root/sys/sys-bsystem/version-pinning/img/ci-supply-chain-pipeline.svg)
*Захист ланцюга постачання у CI/CD: прапорець --locked, аудит вразливостей та герметичне завантаження зафіксованих хешів.*

Якщо розробник змінив маніфест (додав нову бібліотеку), але забув згенерувати й заґомітити оновлений `lockfile`, звичайна команда менеджера пакетів тихо створить новий замок локально на сервері CI. Це створює ілюзію успішної збірки, але ламає відтворюваність у решти команди.

Щоб запобігти цьому, усі сучасні менеджери підтримують спеціальні режими суворої валідації (Frozen / Locked Modes):

### Команди суворої валідації для CI/CD

```bash
# 1. Rust Cargo
# Перериває роботу з кодом помилки, якщо Cargo.lock відсутній або вимагає оновлення
cargo build --locked

# 2. Node.js / npm
# Видаляє node_modules, встановлює суворо за package-lock.json і падає, якщо замок розходиться з package.json
npm ci

# 3. pnpm / yarn
pnpm install --frozen-lockfile
yarn install --immutable

# 4. Conan 2.0
# Забороняє додавати нові вузли чи змінювати ревізії у conan.lock
conan install . --lockfile=conan.lock --lockfile-partial=False
```

### Еталонний конфігураційний сценарій для GitHub Actions

Нижче наведено приклад суворого детермінованого конвеєра збірки на базі CMake та менеджера пакетів:

```yaml
name: Enterprise Strict Deterministic Build

on:
  push:
    branches: [ main, release/* ]
  pull_request:
    branches: [ main ]

jobs:
  verify-and-build:
    runs-on: ubuntu-24.04
    steps:
      - name: Checkout Source Code
        uses: actions/checkout@v4
        with:
          # Забороняємо неявні модифікації історії
          persist-credentials: false

      - name: Verify Lockfile Presence
        run: |
          if [ ! -f conan.lock ] && [ ! -f Cargo.lock ]; then
            echo "::error::CRITICAL: Замковий файл відсутній у репозиторії! Збірку відхилено."
            exit 1
          fi

      - name: Security Vulnerability Scan (CVE Audit)
        run: |
          # Сканування зафіксованих хешів на наявність відомих вразливостей
          conan audit --lockfile=conan.lock || true

      - name: Fetch Dependencies in Strict Locked Mode
        run: |
          # Встановлення в режимі повної ізоляції
          conan install . \
            --lockfile=conan.lock \
            --lockfile-out=conan.lock.check \
            --build=missing

      - name: Enforce Lockfile Immutability (Zero Mutation Gate)
        run: |
          # Порівнюємо початковий замок із тим, що згенерував агент
          if ! cmp -s conan.lock conan.lock.check; then
            echo "::error::FATAL: Маніфест було змінено без оновлення conan.lock розробником!"
            diff -u conan.lock conan.lock.check
            exit 1
          fi

      - name: Hermetic Compilation
        run: |
          # Збирання проєкту з увімкненими прапорцями детермінізму
          cmake --preset release -DCMAKE_BUILD_TYPE=Release
          cmake --build --preset release --parallel $(nproc)

      - name: Execute Test Suite
        run: |
          ctest --preset release --output-on-failure
```

## 7. Кросплатформні матричні замки (Matrix Lockfiles)

У промисловій розробці програмні комплекси компілюються під широкий спектр цільових операційних систем та архітектур: Linux x86_64, Windows MSVC, macOS AArch64 (Apple Silicon), а також вбудовані платформи на мікроконтролерах ARM Cortex-M.

Кожна з цих цільових систем вимагає специфічного набору двійкових опцій, системних заголовків та комбінацій прапорців оптимізації. Спроба використовувати єдиний плоский замковий файл, згенерований на робочій станції Linux, призведе до збою компілятора на платформі Windows через несумісність конфігурацій CRT (`/MD` проти `glibc`) або відсутність специфічних платформних залежностей.

### Стратегія побудови уніфікованого матричного замка

Для подолання цієї складності сучасні менеджери підтримують двоетапну процедуру фіксації:

1. **Генерація базових платформних знімків:**
   На кожній цільовій платформі (або у відповідних контейнерах крос-компіляції) виконується захоплення локального графа:
   ```bash
   # На сервері Linux:
   conan lock create conanfile.py -pr:h=profiles/linux_x86_64 --lockfile-out=conan_linux.lock

   # На сервері Windows:
   conan lock create conanfile.py -pr:h=profiles/windows_msvc --lockfile-out=conan_windows.lock

   # На сервері macOS:
   conan lock create conanfile.py -pr:h=profiles/macos_arm64 --lockfile-out=conan_macos.lock
   ```

2. **Злиття в єдиний монолітний замок:**
   Утиліта злиття об'єднує незалежні графи у спільний `conan.lock`:
   ```bash
   conan lock merge --lockfile=conan_linux.lock --lockfile=conan_windows.lock --lockfile=conan_macos.lock --lockfile-out=conan.lock
   ```

Отриманий замковий файл містить повну комбінаторну матрицю вузлів. Коли білд-агент на Windows зчитує цей файл, він вибирає гілку графа, яка відповідає його `package_id`, гарантуючи, що всі платформи збираються з узгоджених ревізій вихідного коду.

> Замковий файл перетворює розробку з ненадійного процесу, залежного від зовнішніх факторів та настрою сторонніх мейнтейнерів, на строгу математичну систему. Він гарантує, що вихідний код проєкту є єдиним джерелом правди. Фіксація версій та криптографічний контроль хешів усувають цілий клас проблем «у мене все працювало», блокують спроби атак на ланцюг постачання та дозволяють команді інженерів гарантувати відтворюваність релізів через роки після випуску.
