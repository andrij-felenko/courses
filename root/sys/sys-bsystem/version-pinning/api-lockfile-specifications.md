# 📋 Специфікації та схеми форматів замкових файлів

Цей технічний довідник описує структури даних, обов'язкові поля, семантику розв'язання залежностей та криптографічні контракти популярних форматів замкових файлів (Conan 2.0, Rust Cargo, Microsoft vcpkg, Node.js npm), які застосовуються в інженерній практиці для гарантування детермінізму збірки програмного забезпечення.

---

## 1. Специфікація графа Conan 2.0: conan.lock

У менеджері пакетів Conan версії 2.0 замковий файл зберігається у форматі JSON і описує повний стан графа залежностей. На відміну від мов високого рівня, де замок фіксує лише назви пакетів і номери версій, у C++ замковий файл зобов'язаний фіксувати простір бінарних конфігурацій (ABI) та ревізії інструкцій збірки.

```json
{
  "version": "0.5",
  "requires": [
    "zlib/1.3.1#d82e415902be34e0a0b1298f01834a91",
    "openssl/3.1.4#8c1b3f7491024e0b5d92a11b6d081298"
  ],
  "build_requires": [
    "cmake/3.28.1#9a7fa265902be34e0a0b1298f01834a9"
  ],
  "python_requires": [],
  "graph_lock": {
    "nodes": {
      "0": {
        "ref": "my_app/1.0.0#local_build",
        "options": "shared=False",
        "requires": [
          "1",
          "2"
        ],
        "context": "host"
      },
      "1": {
        "ref": "zlib/1.3.1#d82e415902be34e0a0b1298f01834a91",
        "package_id": "8c1b3f7491024e0b5d92a11b6d08129841f3918a",
        "prev": "f01834a91b29a8f40192837482910482018349a1",
        "options": "shared=False\nfPIC=True",
        "context": "host"
      },
      "2": {
        "ref": "openssl/3.1.4#8c1b3f7491024e0b5d92a11b6d081298",
        "package_id": "da39a3ee5e6b4b0d3255bfef95601890afd80709",
        "prev": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4",
        "requires": [
          "1"
        ],
        "options": "no_asm=False\nshared=False",
        "context": "host"
      }
    }
  }
}
```

### Детальний опис полів та семантики Conan 2.0

Формат `conan.lock` забезпечує багаторівневий контроль детермінізму завдяки таким полям:

1. **`version` (Рядок):** позначає версію схеми замкового файлу (поточна стабільна схема — `0.5`). Дозволяє утиліті Conan визначати правила зворотньої сумісності під час міграції інструментів.
2. **`ref` (Повне посилання на пакет):** рядок вигляду `pkg_name/version@user/channel#rrev`. Ключовим елементом тут є **Recipe Revision (`rrev`)** — криптографічний хеш SHA-1 або SHA-256 файлу рецепта `conanfile.py` та всіх асоційованих із ним патчів у каталозі експорту. Якщо мейнтейнер бібліотеки виправив прапорець компіляції в рецепті без зміни номеру версії `1.3.1`, значення `rrev` змінюється, сигналізуючи про модифікацію інструкцій побудови.
3. **`package_id` (Ідентифікатор бінарної конфігурації):** 160-бітний хеш, отриманий з нормалізованого списку налаштувань цільової платформи. Включає назву та версію компілятора (наприклад, GCC 13.2), діалект мови (`c++20`), тип стандартної бібліотеки (`libstdc++11`), режим оптимізації (`Release`), тип компонування (`shared=False`) та призначені для користувача опції (`fPIC=True`). Зміна будь-якого з цих параметрів породжує інший `package_id`, запобігаючи лінкуванню несумісних двійкових об'єктів.
4. **`prev` (Package Revision):** хеш конкретного скомпільованого двійкового архіву в репозиторії. Якщо рецепт перекомпільовано на новішій версії базової операційної системи, `package_id` залишається незмінним, але `prev` фіксує конкретний фізичний бінарний артефакт.
5. **`context` (Контекст виконання):** суворо розділяє граф на дві категорії:
   * `host` — бібліотеки, які компілюються під цільову платформу й компонуються у фінальний бінарник (наприклад, OpenSSL, zlib, Boost);
   * `build` — допоміжні інструменти, які повинні запускатися на самій машині збірки під час компіляції (наприклад, кодогенератор protobuf, асемблер NASM, система збірки CMake, компілятор bison).
6. **`requires` (Масив ідентифікаторів вузлів):** задає явні зв'язки в орієнтованому ациклічному графі (DAG). Кожен вузол посилається на точні числові індекси своїх дочірніх компонентів, що унеможливлює неявне підтягування сторонніх пакетів.

### Режими роботи із замковим файлом у Conan 2.0

* **Суворий режим (Strict Lockfile):** команда `conan install . --lockfile=conan.lock --lockfile-partial=False` забороняє будь-які відхилення. Якщо в графі з'явилася нова пряма залежність або змінився `package_id`, процес негайно переривається з помилкою;
* **Частковий замок (Partial Lockfile):** прапорець `--lockfile-partial` дозволяє блокувати лише частину відомих вузлів, дозволяючи динамічно розв'язувати нові модулі під час поетапної розробки;
* **Злиття замків (Lockfile Merge):** у мультиплатформних проєктах створюються окремі замки під Linux, Windows та macOS. Команда `conan lock merge` об'єднує їх у єдиний уніфікований `conan.lock`, який містить матрицю конфігурацій для всіх цільових архітектур.

## 2. Специфікація Rust Cargo: Cargo.lock (Формат V3/V4)

У системі збірки Cargo мови Rust замковий файл зберігається у форматі TOML. Він фіксує дерево залежностей (crates) разом із криптографічними контрольними сумами архівів вихідного коду, які завантажуються з центрального реєстру `crates.io` або зовнішніх репозиторіїв Git.

```toml
# This file is automatically @generated by Cargo.
# It is not intended for manual editing.
version = 3

[[package]]
name = "my_service"
version = "0.1.0"
dependencies = [
 "serde",
 "tokio",
]

[[package]]
name = "serde"
version = "1.0.197"
source = "registry+https://github.com/rust-lang/crates.io-index"
checksum = "3fb1c873e1b9b056a4dc4c0c198b24c3efa05924387205252850d9a57280564f"
dependencies = [
 "serde_derive",
]

[[package]]
name = "serde_derive"
version = "1.0.197"
source = "registry+https://github.com/rust-lang/crates.io-index"
checksum = "7eb0b34b42edc17f6b7cac84a52a1c5f0e1bb2227e997ca9011ea3dd34e8610b"
dependencies = [
 "proc-macro2",
 "quote",
 "syn",
]
```

### Структурні компоненти та гарантії безпеки Cargo.lock

1. **`version` (Ціле число):** версія внутрішньої структури файлу:
   * Версія `1` та `2` — застарілі формати з плоским списком метаданих;
   * Версія `3` — сучасний стандарт, що підтримує явний масив `dependencies` всередині кожної секції `[[package]]`, що дозволяє точно реконструювати дерево викликів;
   * Версія `4` — розширений формат, оптимізований для розріджених індексів (Sparse Registries) за протоколом HTTP.
2. **`name` та `version` (Рядки):** однозначний ідентифікатор крейта та його точна версія за SemVer. У `Cargo.lock` заборонено використання будь-яких префіксів діапазонів (`^`, `~`, `>=`).
3. **`source` (URI джерела):** рядок, що вказує на походження пакета:
   * `registry+https://github.com/rust-lang/crates.io-index` — офіційний публічний реєстр;
   * `git+https://github.com/org/repo.git?branch=main#commit_hash` — репозиторій Git із обов'язковою фіксацією точного 40-символьного SHA-1 коміту;
   * Порожнє значення — локальний пакет поточної робочої області (Workspace member).
4. **`checksum` (SHA-256 рядок):** 64-символьний шістнадцятковий хеш оригінального стисненого архіву `.crate`. Під час збирання Cargo завантажує архів, обчислює його контрольну суму SHA-256 і звіряє із замком. Якщо власник реєстру або зловмисник спробує підмінити вміст архіву на сервері без зміни версії, процес збірки буде аварійно зупинено.
5. **`dependencies` (Масив рядків):** список прямих підзалежностей вузла. Дозволяє розрізняти ситуації, коли в системі одночасно використовуються дві різні версії однієї бібліотеки для різних незалежних гілок дерева.

## 3. Специфікація Microsoft vcpkg: Базові лінії та перевизначення

Менеджер `vcpkg` відмовився від концепції монолітного замкового файлу на користь інтеграції з системою контролю версій Git. У маніфестному режимі (Manifest Mode) відтворюваність забезпечується комбінацією файлів `vcpkg-configuration.json` та `vcpkg.json`.

### Схема vcpkg-configuration.json: Визначення реєстрів та базових ліній

```json
{
  "$schema": "https://raw.githubusercontent.com/microsoft/vcpkg-tool/main/docs/vcpkg-configuration.schema.json",
  "default-registry": {
    "kind": "git",
    "repository": "https://github.com/microsoft/vcpkg.git",
    "baseline": "a42af01b72c28c8117d3cf524ec946770f9e6870"
  },
  "registries": [
    {
      "kind": "git",
      "repository": "https://github.com/my-org/custom-vcpkg-ports.git",
      "baseline": "7c9b8a6f34e021a8f9023412567890abcdef1234",
      "packages": [
        "custom-auth",
        "internal-telemetry"
      ]
    }
  ]
}
```

### Схема vcpkg.json: Декларація залежностей та масив Overrides

```json
{
  "$schema": "https://raw.githubusercontent.com/microsoft/vcpkg-tool/main/docs/vcpkg.schema.json",
  "name": "enterprise-app",
  "version": "2.4.0",
  "dependencies": [
    "boost-asio",
    "fmt",
    "nlohmann-json"
  ],
  "overrides": [
    {
      "name": "fmt",
      "version": "10.1.1",
      "port-version": 0
    },
    {
      "name": "boost-asio",
      "version": "1.83.0",
      "port-version": 1
    }
  ]
}
```

### Механізми контролю версій у vcpkg

1. **`baseline` (Базова лінія Git):** 40-символьний SHA-1 хеш коміту в офіційному репозиторії портів `microsoft/vcpkg`. Цей коміт однозначно фіксує дерево файлів `portfile.cmake` та версії всіх доступних бібліотек на конкретну дату. Базова лінія гарантує, що всі члени команди та сервери CI отримують абсолютно ідентичні вихідні тексти рецептів;
2. **`overrides` (Примусові перевизначення):** масив правил, які мають найвищий пріоритет у системі розв'язання залежностей. Якщо транзитивна бібліотека вимагає новішої версії, наявність запису в `overrides` змушує компілятор збирати саме вказану версію;
3. **`port-version` (Ревізія рецепта порту):** невід'ємне ціле число, яке збільшується щоразу, коли розробники vcpkg змінюють скрипт компіляції `portfile.cmake` або накладають патч сумісності без зміни версії самої вихідної бібліотеки.

## 4. Специфікація Node.js / npm: package-lock.json (Версія 3)

Формат `package-lock.json` версії 3 використовує плоску структуру `packages`, де кожен вузол адресується шляхом у файловій системі `node_modules`.

```json
{
  "name": "secure-gateway",
  "version": "1.0.0",
  "lockfileVersion": 3,
  "requires": true,
  "packages": {
    "": {
      "name": "secure-gateway",
      "version": "1.0.0",
      "dependencies": {
        "express": "4.18.2"
      }
    },
    "node_modules/express": {
      "version": "4.18.2",
      "resolved": "https://registry.npmjs.org/express/-/express-4.18.2.tgz",
      "integrity": "sha512-5/PsL6iVEkiGu9P0Y637VLNRwTXvVh/cP/SKzo07E12qNIdMDBko056z04ET230e72aeHBRw56939KR56Q2a==",
      "license": "MIT",
      "dependencies": {
        "accepts": "~1.3.8",
        "array-flatten": "1.1.1",
        "body-parser": "1.20.1"
      }
    }
  }
}
```

### Механізм контролю цілісності SRI (Subresource Integrity)

Поле `integrity` у файлах `package-lock.json` реалізує стандарт W3C Subresource Integrity:
* Формат значення: `<алгоритм>-<base64-хеш>`, наприклад `sha512-5/PsL6iVEki...`;
* Під час інсталяції клієнт завантажує двійковий архів `.tgz` за адресою з поля `resolved`;
* Обчислюється криптографічний хеш SHA-512 завантаженого файлу;
* Якщо розрахований хеш не збігається з рядком `integrity`, процес негайно переривається з помилкою `EINTEGRITY`, запобігаючи атакам типу Man-in-the-Middle або компрометації дзеркал реєстру.

## 5. Порівняльний аналіз архітектур замкових файлів

| Характеристика | Conan 2.0 (`conan.lock`) | Cargo (`Cargo.lock`) | vcpkg (`baseline + json`) | npm (`package-lock.json v3`) |
| :--- | :--- | :--- | :--- | :--- |
| **Формат представлення** | JSON (Орієнтований граф) | TOML (Список пакетів) | JSON (Маніфест + База) | JSON (Дерево каталогів) |
| **Фіксація вихідного тексту** | Recipe Revision (`rrev`) | Хеш архіву (`SHA-256`) | Git Commit Baseline SHA | SRI Хеш (`SHA-512 Base64`) |
| **Фіксація двійкового ABI** | `package_id` + `prev` | Відсутня (збірка з коду) | Тріплети компіляції | Не застосовується (JS) |
| **Розділення контекстів** | Так (`host` проти `build`) | Частково (proc-macro) | Так (host/target triplets) | Так (dependencies/devDeps) |
| **Прапорець суворого CI** | `--lockfile-out` + перевірка | `--locked` / `--frozen` | `--strict-mode` | `npm ci` / `--frozen-lockfile` |
| **Стійкість до підміни** | Повна (Хеші рецептів і бінарників) | Повна (Криптографічний SHA) | Повна (Дерево об'єктів Git) | Повна (Криптографічний SRI) |

Кожна з розглянутих систем реалізує принцип незмінності: на етапі виробничої збірки будь-яке автоматичне розв'язання залежностей вимикається, а система компілює виключно ті артефакти, чиї цифрові відбитки збігаються із записами в замковому файлі.
