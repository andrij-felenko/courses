# 📜 Еволюція фіксації залежностей та атаки на ланцюг постачання

Цей історичний огляд розкриває, як індустрія розробки програмного забезпечення пройшла шлях від відкритого хаосу динамічних версій до суворих криптографічних замкових файлів, і як катастрофічні інциденти в ланцюгах постачання змусили змінити архітектуру менеджерів пакетів.

---

## 1. Епоха «живого коду»: CPAN, незакріплені Make-файли та системні каталоги

На світанку модульного програмування у 1990-х роках концепції відтворюваних замкових файлів (англ. *lockfiles*) не існувало. Першим масовим централізованим репозиторієм сторонніх модулів став CPAN (Comprehensive Perl Archive Network), запущений у 1995 році. Утиліти встановлення того часу завантажували останню доступну версію модуля безпосередньо в глобальний каталог системи.

У світі мов C та C++ керування стороннім кодом обмежувалося двома підходами:
1. **Ручне копіювання вихідних текстів (Vendoring):** сторонні файли `.c` та `.h` фізично додавалися в репозиторій або архів проєкту. Це гарантувало стабільність, але унеможливлювало швидке оновлення виправлень безпеки.
2. **Збирання проти системних бібліотек:** файли `Makefile` або скрипти `configure` проєкту містили виклики компілятора з прапорцями `-lpng` чи `-lssl`. Передбачалося, що системний адміністратор самостійно встановив відповідні бібліотеки в `/usr/lib` або `/usr/local/lib`.

Головною проблемою цієї епохи був феномен «на моїй машині збирається, а на сервері ні» (англ. *works on my machine*). Якщо розробник локально компілював проєкт із встановленою версією бібліотеки `libxyz 1.2`, а сервер неперервної інтеграції під час виконання команди інсталяції підтягував свіжий реліз `libxyz 1.3`, збірка непередбачувано ламалася через зміни в сигнатурах функцій або поведінці внутрішніх структур.

## 2. Поява Bundler та винайдення Gemfile.lock (2010)

Справжній архітектурний перелом відбувся у 2008–2010 роках в екосистемі мови Ruby. Розробники стикалися з нескінченними конфліктами залежностей під час розгортання вебдодатків на базі фреймворку Ruby on Rails: кожен запуск команди інсталяції підбирав нові транзитивні пакунки, що приводило до непрацездатності виробничих серверів.

У 2010 році інженери Єгуда Кац (Yehuda Katz), Карл Лерхе (Carl Lerche) та Андре Арко (André Arko) представили менеджер залежностей **Bundler 1.0**. Bundler увів фундаментальний розподіл між двома типами конфігураційних файлів:
* `Gemfile` — маніфест вимог розробника, де вказуються бажані версії у вигляді гнучких діапазонів (наприклад, `gem 'nokogiri', '~> 1.4'`);
* `Gemfile.lock` — автоматично згенерований знімок (англ. *snapshot*) повністю розв'язаного графа, де кожна пряма й транзитивна залежність зафіксована до точного номеру версії.

Ідея Bundler полягала в тому, що ресурсомісткий процес розв'язання обмежень (англ. *constraint resolution*) виконується **один раз** на машині інженера, після чого згенерований `Gemfile.lock` обов'язково комітиться в систему контролю версій Git. Сервери розгортання та інші члени команди більше не запускають алгоритм пошуку сумісних версій: вони читають замок і встановлюють ідентичний набір пакетів.

Ця модель виявилася настільки успішною, що була миттєво запозичена новими мовами та інструментами:
* У 2012 році з'явився Composer для PHP (`composer.lock`);
* У 2014 році Єгуда Кац переніс цю архітектуру в мову Rust, створивши менеджер `cargo` та формат `Cargo.lock`;
* У 2016 році Facebook представив менеджер `yarn` із файлом `yarn.lock` як відповідь на нестабільність ранніх версій npm;
* У 2017 році менеджер npm випустив версію 5.0 із вбудованою підтримкою `package-lock.json`;
* У світі C++ менеджер Conan запровадив `conan.lock`, а vcpkg реалізував механізм `builtin-baseline` та `overrides`.

## 3. Катастрофа Left-pad (2016): руйнація міфу про стабільність відкритого коду

22 березня 2016 року сталася подія, яка наочно продемонструвала глобальну вразливість незакріплених транзитивних залежностей. Програміст Азер Кочулу (Azer Koçulu) через патентну суперечку з компанією Kik вирішив видалити з публічного реєстру npm усі свої 273 пакети.

Серед видалених модулів виявилася мікробібліотека `left-pad`, яка складалася з 11 рядків коду для доповнення рядка пробілами зліва:

```javascript
// Оригінальний вміст left-pad 0.0.3
function leftpad (str, len, ch) {
  str = String(str);
  var i = -1;
  if (!ch && ch !== 0) ch = ' ';
  len = len - str.length;
  while (++i < len) {
    str = ch + str;
  }
  return str;
}
```

Незважаючи на примітивність, пакет `left-pad` був непрямою транзитивною залежністю тисяч критичних проєктів, включаючи React, Babel та системи збірки сотень міжнародних корпорацій. Оскільки маніфести не закріплювали версії транзитивних вузлів через замкові файли, команди встановлення намагалися завантажити відсутній пакет із реєстру. Тисячі CI/CD конвеєрів по всьому світу миттєво зупинилися з фатальною помилкою `HTTP 404 Not Found`.

Інцидент із `left-pad` змусив індустрію усвідомити:
1. Будь-який відкритий реєстр без локального кешування та фіксації хешів є точкою відмови;
2. Транзитивне дерево є живим організмом, здатним зламатися будь-якої миті, якщо воно не зафіксоване замком;
3. Реєстри пакунків запровадили політику заборони видалення опублікованих релізів (англ. *unpublish restriction*).

## 4. Еволюція атак на ланцюг постачання (Supply Chain Attacks)

У період із 2018 по 2024 рік фокус кіберзагроз змістився від прямого зламу серверів до атак на ланцюг постачання програмного забезпечення (англ. *Software Supply Chain*). Зловмисники зрозуміли: замість того щоб атакувати захищену інфраструктуру цільової компанії, достатньо скомпрометувати одну дрібну бібліотеку, яку ця компанія використовує у своїй збірці.

### Інцидент Event-Stream (2018): соціальна інженерія та захоплення акаунтів

У листопаді 2018 року з'ясувалося, що популярний npm-пакет `event-stream` (понад 1,5 мільйона завантажень на тиждень) містить шкідливий код, призначений для викрадення криптовалюти з гаманців розробників додатку Copay.

Зловмисник під псевдонімом `right9ctrl` запропонував первинному автору бібліотеки допомогу у підтримці занедбаного проєкту. Отримавши права публікації в реєстрі, він випустив мінорне оновлення `event-stream 3.3.6`, яке додало залежність від шкідливого модуля `flatmap-stream`. Завдяки плаваючим діапазонам версій (`^3.3.4`) у маніфестах користувачів, оновлений шкідливий пакет автоматично потрапив у збірки без відома команд розробки.

### Атака Dependency Confusion (2021): отруєння публічних просторів імен

У лютому 2021 року дослідник безпеки Алекс Бірсан (Alex Birsan) продемонстрував фундаментальну вразливість у логіці пошуку пакетів популярних менеджерів (pip, npm, NuGet).

Більшість корпорацій використовують як внутрішні приватні бібліотеки (наприклад, `@company/auth`), так і відкриті публічні залежності. Якщо системний конфігуратор звертався до кількох реєстрів без замкового файлу з точними джерелами, менеджер пакетів порівнював номери версій. Бірсан створив у публічному реєстрі npm пакети з такими самими назвами, як у внутрішніх корпоративних модулів Apple, Microsoft, Tesla та Uber, але встановив штучно завищений номер версії `999.0.0`. Автоматизовані білд-сервери компаній під час збирання автоматично обирали «новішу» версію з публічного інтернету замість внутрішньої безпечної, виконуючи код дослідника всередині корпоративного периметра.

### Атака на XZ Utils (2024, CVE-2024-3094): найскладніший бекдор в історії

На початку 2024 року світ сколихнула найбільш витончена атака в історії відкритого коду. Зловмисник під ім'ям «Цзя Тань» (Jia Tan) протягом трьох років втиралася в довіру до єдиного виснаженого мейнтейнера бібліотеки стиснення `xz` (проєкт `XZ Utils` та бібліотека `liblzma`).

Отримавши статус співавтора, зловмисник запровадив прихований бекдор у випуски версій `5.6.0` та `5.6.1`. Механізм атаки був безпрецедентним:
* У репозиторії Git шкідливий код був відсутній і маскувався під невинні тестові двійкові файли для тестування алгоритмів розпакування;
* Під час генерації релізного архіву `xz-5.6.0.tar.gz` скрипт випуску вбудовував у фінальний файл `configure` складний M4-макрос, який модифікував процес компіляції;
* Під час збирання пакета в дистрибутивах Linux компілятор підміняв функцію перевірки автентифікації в системному демоні `sshd` через зв'язку з `systemd` та `liblzma`, дозволяючи зловмисникам отримувати несанкціонований доступ рівня root через SSH.

Бекдор було випадково виявлено інженером компанії Microsoft Андресом Фройндом (Andres Freund) під час аналізу аномального споживання процесора процесом `sshd` (затримка у 500 мілісекунд).

## 5. Сучасний стандарт: SLSA, криптографічні хеші та режим повної герметичності

Уроки історичних атак сформували сучасний підхід до безпеки ланцюга постачання:

```
2010 (Bundler): Фіксація версій у Gemfile.lock (порятунок від дрейфу версій)
     │
2016 (Left-pad): Заборона unpublish у реєстрах + локальні дзеркала
     │
2018 (Event-stream): Поява команд аудиту вразливостей (cargo audit, npm audit)
     │
2021 (Dependency Confusion): Прив'язка просторів імен до криптографічних джерел
     │
2024 (XZ Backdoor): Повна відмова від довіри до tarball, перехід на збірки за Git-хешами, SLSA та Sigstore
```

Сьогодні просте закріплення номерів версій (`1.2.3`) вважається недостатнім. Сучасні замкові файли (`Cargo.lock`, `conan.lock`, `package-lock.json`) обов'язково зберігають криптографічні контрольні суми вихідних кодів (SHA-256 / SHA-512) та бінарних артефактів. У системах неперервної інтеграції впроваджено обов'язковий прапорець заборони мутацій (`--frozen-lockfile` / `--locked`), що гарантує: жоден рядок коду не потрапить у бінарний дистрибутив без явного аудиту та коміту змін замкового файлу командою розробників.
