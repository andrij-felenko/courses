# 📜 Від /usr/local до єдиних маніфестів: історія пакування C та C++

У перші десятиліття існування мов C та C++ концепції окремого «менеджера пакетів для мови» (англ. *package manager*, від давньофр. *paquet* — згорток) взагалі не існувало. Програмні бібліотеки поширювалися як архіви вихідного коду (англ. *tarball*), які розробник завантажував вручну, розпаковував і збирав безпосередньо в операційній системі за допомогою утиліт `make` та системних компіляторів. Стандартом де-факто для Unix-подібних систем було копіювання заголовочних файлів у системний каталог `/usr/local/include`, а скомпільованих статичних чи динамічних бібліотек — у `/usr/local/lib` через команду `sudo make install`.

Ця парадигма спиралася на припущення, що операційна система має єдиний глобальний набір бібліотек, спільний для всіх програм. Поки проєкти залишалися відносно невеликими, а стандарт мови C еволюціонував повільно, такий підхід працював. Проте з бурхливим розвитком C++ у 1990-х роках глобальне розміщення залежностей почало призводити до систематичних колізій: різні програми вимагали несумісних версій однієї бібліотеки, а ручне видалення старих файлів із системних каталогів перетворювалося на складний квест із ризиком зламати працездатність самої операційної системи.

## Пастка системних пакетних менеджерів: APT, RPM та Pacman

У середині 1990-х років дистрибутиви Linux запропонували системні менеджери пакунків — Debian створив `dpkg`/`apt`, Red Hat розробив `rpm`, а пізніше з'явилися `pacman` та порти FreeBSD. Системні менеджери блискуче розв'язали проблему встановлення готового програмного забезпечення для кінцевих користувачів та системних адміністраторів, забезпечивши автоматичне відстеження залежностей і цілісність системи.

Проте для розробників прикладного C++ системні менеджери стали джерелом нездоланних обмежень:

1. **Жорстка прив'язка до релізу ОС.** Дистрибутив Linux фіксує єдину версію бібліотеки (наприклад, `libboost 1.74`) на весь життєвий цикл випуску операційної системи (часто на 3–5 років). Розробник, якому потрібні нові можливості C++20 із `Boost 1.82`, не мав легального способу встановити її через системний `apt`, не ризикуючи зламати системні утиліти самого дистрибутива.
2. **Єдина конфігурація збірки.** Системні пакунки компілюються виключно в оптимізованому режимі (`Release`), із динамічним компонуванням (`Shared`) та системним компілятором за замовчуванням. Розробнику ж постійно потрібні налагоджувальні версії (`Debug`) із символами та увімкненими санітайзерами (ASan, TSan), а також статичні версії (`Static`) для створення автономних бінарників.
3. **Відсутність кросплатформності.** Менеджери `apt` чи `rpm` не існують на Windows або macOS і не підтримують крос-компіляцію для вбудованих мікроконтролерів (ARM Cortex-M, RISC-V). Інженерна команда, що розробляє кросплатформний рушій або бібліотеку, не могла спиратися на Linux-специфічні пакети.

## Епоха вендорингу та «пекло сабмодулів» (2000–2014)

Неможливість використання системних менеджерів призвела до десятиліття «кустарного вендорингу» (англ. *vendoring*, від лат. *vendere* — продавати, постачати). Інженерні команди копіювали вихідний код сторонніх бібліотек безпосередньо у власний репозиторій (у каталог `third_party/` або `vendor/`).

З появою Git у 2005 році індустрія масово перейшла на технологію `git submodule` (та пізніше `git subtree`). Це створювало ілюзію керованості, проте породжувало нові катастрофічні проблеми:
* **Каскадний вибух часу збірки:** якщо 10 внутрішніх бібліотек компанії використовували Boost або OpenCV, кожен проєкт компілював сотні мегабайтів стороннього вихідного коду наново під час кожного чищення кешу.
* **Несумісність систем збірки:** одна підключена бібліотека використовувала Autotools, друга — власні Makefile, третя — CMake, а четверта збиралася лише через Visual Studio solution. Головний проєкт був змушений підтримувати громіздкі скрипти-обгортки на Python чи Bash, які намагалися узгодити ці різнорідні інструменти.
* **Відсутність дедуплікації:** у великому дереві сабмодулів одна й та сама бібліотека могла затягуватися на різній глибині дерева у трьох різних версіях, неминуче призводячи до помилок лінкування під час фінальної збірки.

## Ранні спроби мовних менеджерів: Biicode

Коли в інших мовах з'явилися й набули шаленої популярності централізовані менеджери залежностей (CPAN для Perl, RubyGems, npm для JavaScript у 2010 році, Cargo для Rust у 2014 році), спільнота C++ усвідомила критичну потребу у власному інструменті.

Першою помітною спробою став проєкт **Biicode** (2012–2015), заснований іспанськими інженерами. Biicode запропонував сміливу ідею: аналізувати директиви `#include` у вихідному коді C++ і автоматично витягувати потрібні файли з централізованої хмари на рівні окремих файлів або невеликих блоків (англ. *blocks*).

Проте концепція Biicode зазнала краху через специфіку мови C++:
* Гранулярність на рівні окремих файлів руйнувала цілісність складних бібліотек із конфігураційними заголовками, згенерованими на стадії збірки (наприклад, `config.h`).
* Модель не враховувала параметри компілятора та несумісність двійкового інтерфейсу (ABI).
* Спроба замінити систему збірки власним механізмом натрапила на шалений спротив індустрії, яка на той час уже стандартизувалася навколо CMake.

У 2015 році компанія Biicode закрилася, проте її уроки стали фундаментальним фундаментом для створення інструментів наступного покоління.

## Народження сучасного дуополізму: Conan та vcpkg (2015–дотепер)

У 2015 році Дієго Родрігес-Лосада (Diego Rodriguez-Losada) та Луїс Мартінес де Бартоломе (Luis Martínez de Bartolomé) заснували проєкт **Conan**. Вони врахували помилки Biicode і заклали в архітектуру три революційні принципи:
1. **Менеджер не замінює систему збірки:** Conan оркеструє наявні системи (CMake, Meson, Autotools, MSBuild), передаючи їм керування.
2. **Багатовимірна модель Package ID:** бінарні пакунки кешуються та ідентифікуються криптографічним хешем, розрахованим з повної матриці параметрів компіляції (ОС, архітектура, компілятор, версія стандарту C++, тип рантайму).
3. **Рецепти на мові Python:** повна гнучкість у конфігурації складних кроків складання та інсталяції.

У 2016 році корпорація Microsoft представила власний відкритий менеджер пакетів C++ — **vcpkg**. Microsoft обрала модель переважної збірки з вихідного коду (англ. *source-based*) з акцентом на простоту, декларативні файли опису портів (`portfile.cmake`) та безшовну інтеграцію з Visual Studio та CMake за допомогою механізму триплетів (англ. *triplets*).

Паралельно з розвитком Conan та vcpkg еволюціонував і сам **CMake**: версії 3.0+ запровадили модель імпортованих цілей (`IMPORTED TARGETS`), що дозволило менеджерам пакунків експортувати знайдені бібліотеки у вигляді стандартних конфігураційних файлів `find_package(Foo CONFIG)`. Завдяки цьому сучасний C++-код більше не залежить від того, яким саме інструментом було встановлено бібліотеку — збірка використовує єдиний стандартизований інтерфейс цілей.
