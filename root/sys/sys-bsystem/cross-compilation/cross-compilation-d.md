Розробник на робочій станції з процесором x86_64 збирає застосунок для промислового шлюзу на базі ARM Cortex-A53 або прошивку для мікроконтролера STM32 на ядрі ARM Cortex-M4. Якщо після успішного лінкування він спробує запустити отриманий двійковий файл безпосередньо у своєму терміналі, операційна система Linux негайно завершить процес аварійною помилкою ядра `Exec format error (ENOEXEC)` або сигналом `Illegal Instruction (SIGILL)`. Хостовий процесор x86_64 фізично не здатний декодувати й виконати бінарні опкоди чужого набору інструкцій ARM.

Природна спроба уникнути цього конфлікту — запустити компілятор безпосередньо на цільовому пристрої — розбивається об жорсткі апаратні обмеження вбудованих платформ. Типовий мікроконтролер має лише сотні кілобайтів Flash-пам'яті та оперативної пам'яті, а недорогі одноплатні комп'ютери мають від 64 мегабайтів до 1 гігабайта RAM і повільні флешнакопичувачі. Сучасний оптимізувальний компілятор рівня GCC або Clang разом із компонувальником LLD під час збірки проєкту на кілька сотень тисяч рядків вимагає гігабайти оперативної пам'яті та гігафлопси обчислювальної потужності; на слабкому процесорі нативна збірка тривала б годинами або завершувалася збоєм через нестачу пам'яті (Out-of-Memory Killer).

Виникає фундаментальна потреба **крос-компіляції** (англ. *cross-compilation*): процесу, за якого весь набір інструментів збірки виконується на потужній робочій станції або сервері CI/CD, але формує машинний код, системні структури та таблиці переміщень для абсолютно іншої апаратної та програмної платформи. Подолання цієї прірви вимагає суворого узгодження термінології ролей систем, глибокого розуміння розбіжностей двійкових інтерфейсів (розрядність, порядок байтів, ABI, вирівнювання структур) та вирішення проблеми виконання допоміжних генераторів коду під час самої збірки.

## Канонічна тріада GNU: Build, Host, Target

Щоб однозначно керувати складанням програмного забезпечення для чужих платформ, проєкт GNU на початку 1990-х років формалізував поняття трьох системних сутностей. Ця класифікація закріпилася в утилітах `autoconf`, `automake`, а згодом була успадкована системами CMake, Meson та інструментами збірки LLVM і Rust.

Будь-який процес компіляції оперує трьома незалежними координатами:
- **Build (Складальник)** — апаратна платформа та операційна система, на якій фізично запускається процес компіляції (де виконуються бінарники `gcc`, `clang`, `cmake`, `ninja`).
- **Host (Виконавець / Господар)** — платформа та операційна система, на якій виконуватиметься скомпільована програма чи бібліотека після завершення збірки.
- **Target (Ціль коду)** — апаратна архітектура та операційне середовище, для якого генеруватиме машинний код створений компілятор.

> [!IMPORTANT]
> Для звичайних прикладних програм та бібліотек координата `Target` не має практичного сенсу, оскільки кінцева програма не компілює чужий код. Для них існують лише дві системи: де компілюють (`Build`) та де запускають (`Host`). Поняття `Target` стає критично важливим лише тоді, коли ви збираєте сам компілятор, асемблер, лінкер чи зневаджувач (інструменти тулчейна).

*Канонічна тріада GNU: ролі систем Build, Host і Target та чотири базові конфігурації збірки.*

### Чотири конфігурації складання

Співвідношення між цими трьома параметрами формує чотири принципово різні інженерні сценарії:

| Конфігурація | Співвідношення систем | Приклад Build -> Host -> Target | Практичне застосування |
|---|---|---|---|
| **Нативна збірка** *(Native)* | `Build == Host == Target` | `x86_64-linux` -> `x86_64-linux` -> `x86_64-linux` | Звичайна розробка на робочій станції: бінарники створюються для тієї ж машини, де працює програміст. |
| **Крос-компілятор** *(Cross)* | `Build == Host != Target` | `x86_64-linux` -> `x86_64-linux` -> `aarch64-linux` | Стандартний крос-тулчейн: компілятор працює на x86_64 Linux і створює бінарники для ARM64 шлюзу. |
| **Крос-нативна збірка** *(Cross-native)* | `Build != Host == Target` | `x86_64-linux` -> `aarch64-linux` -> `aarch64-linux` | Складання нативного компілятора для одноплатника (Raspberry Pi) на швидкому сервері x86_64 для подальшої роботи на платі. |
| **Канадська збірка** *(Canadian Cross)* | `Build != Host != Target` | `x86_64-linux` -> `x86_64-w64-mingw32` -> `arm-none-eabi` | Складання на Linux-сервері тулчейна для розробників під Windows, який компілюватиме код під ARM Cortex-M. |

### Механіка канадської збірки (Canadian Cross)

Сценарій, коли всі три системи відрізняються одна від одної (`Build != Host != Target`), отримав назву **Canadian Cross** на честь трипартійної політичної системи Канади кінця 1980-х років. Детально про те, як інженери компанії Cygnus Support винайшли цей механізм для подолання апаратних обмежень комп'ютерів клієнтів, читайте в історичному нарисі: [як з'явилася канадська збірка](root:sys-bsystem/cross-compilation/hist-canadian-cross.md).

Збірка тулчейна в режимі Canadian Cross не може бути виконана за один прохід, оскільки на машині `Build` (наприклад, Linux x86_64) спочатку немає компілятора, здатного збирати бінарники під `Host` (Windows x86_64). Тому застосовується триетапний конвеєр:

```text
Етап 1: [Build: x86_64-linux] ──(нативний GCC)──> Створює: Крос-компілятор 1 (Build -> Host)
                                                  [Працює на Linux, генерує код Windows]

Етап 2: [Build: x86_64-linux] ──(нативний GCC)──> Створює: Крос-компілятор 2 (Build -> Target)
                                                  [Працює на Linux, генерує код ARM Cortex-M]
                                                  та збирає цільову C-бібліотеку Newlib

Етап 3: [Build: x86_64-linux] ──(Крос-компілятор 1)──> Створює: Кінцевий тулчейн (Host -> Target)
                                                       [Бінарник .exe для Windows, що генерує код ARM]
```

Отримана на виході збірка компілятора GCC або Clang є виконуваним файлом для Windows, який ніколи не зможе запуститися на складальному сервері Linux, але містить оптимізатор та генератор машинних інструкцій під мікроконтролери ARM.

## Анатомія архітектурних розбіжностей: залізо, біти та пам'ять

Перехід від нативної збірки до крос-компіляції ламає базові припущення мов C та C++ про еквівалентність представлення даних у пам'яті між середовищем розробки та цільовим пристроєм. Помилки такого класу є найнебезпечнішими в системному програмуванні, оскільки вони успішно проходять етап компіляції та компонування, але призводять до мовчазного спотворення даних або збоїв пам'яті під час виконання на цільовому процесорі.

![Порядок байтів та моделі даних розрядності](/root/sys/sys-bsystem/cross-compilation/img/endianness-and-data-models.svg)

*Порядок байтів (Endianness) у пам'яті та таблиця розмірів базових типів для моделей ILP32, LP64 і LLP64.*

### 1. Розрядність та моделі представлення даних

У мовах C і C++ стандарт не фіксує точний розмір базових типів `int`, `long` та `pointer` у байтах, визначаючи лише мінімальні співвідношення (`sizeof(short) <= sizeof(int) <= sizeof(long) <= sizeof(long long)`). Операційні системи та процесорні архітектури використовують різні **моделі даних** (англ. *Data Models*):

| Модель даних | `short` | `int` | `long` | `long long` | `void*` (вказівник) | Типові платформи |
|---|---|---|---|---|---|---|
| **ILP32** | 2 | 4 | 4 | 8 | 4 | 32-бітні Linux, Windows, ARM Cortex-M, RISC-V 32 |
| **LP64** | 2 | 4 | **8** | 8 | 8 | 64-бітні Linux, macOS, BSD, AArch64, x86_64 |
| **LLP64** | 2 | 4 | **4** | 8 | 8 | 64-бітні Microsoft Windows (x86_64, ARM64) |
| **ILP64** | 2 | 8 | 8 | 8 | 8 | Рідкісні історичні суперкомп'ютери (Cray) |

Головна небезпека крос-компіляції між 64-бітним хостом і 32-бітною ціллю полягає в типі `long`:
- На хості Linux x86_64 вираз `sizeof(long)` дорівнює 8 байтам.
- На цільовому мікроконтролері ARM Cortex-M вираз `sizeof(long)` дорівнює 4 байтам.

Якщо розробник використовує тип `long` для збереження міток часу в мілісекундах чи зміщень файлів, код на хості успішно оперує 64-бітними величинами. Проте після крос-компіляції під 32-бітну ціль тип `long` перетворюється на 32-бітне число, що призводить до несподіваного арифметичного переповнення (Integer Overflow) значень через 24–49 діб безперервної роботи пристрою.

Ще одна класична пастка — збереження вказівника в цілочисельний тип. Кастування `(uint32_t)ptr` на 64-бітному хості призводить до зрізання старших 32 бітів адреси (Pointer Truncation), тоді як на 32-бітній цілі цей код працює коректно. Єдиним правильним і переносним рішенням є використання типів фіксованої ширини `<cstdint>` (`int32_t`, `int64_t`, `uintptr_t`, `size_t`).

### 2. Порядок розташування байтів (Endianness)

Порядок байтів визначає послідовність, у якій байти багатобайтового числа (наприклад, 32-бітного цілого `0x12345678`) розташовуються в комірках оперативної пам'яті за зростанням адрес:

- **Прямий порядок (Little-Endian / LE)**: молодший значущий байт (LSB, `0x78`) зберігається за найменшою адресою пам'яті, а старший (MSB, `0x12`) — за найбільшою. Цей порядок є домінуючим у сучасних процесорах: x86_64, ARM Cortex-A/M (у типовому режимі), RISC-V.
- **Зворотний порядок (Big-Endian / BE)**: старший значущий байт (MSB, `0x12`) зберігається за найменшою адресою пам'яті. Цей порядок використовується в мережевих протоколах (IP/TCP), а також у процесорах IBM s390x, SPARC, класичних Motorola 68k/PowerPC та деяких промислових контролерах MIPS.

Пряме приведення вказівників (Pointer Punning) для вилучення окремих байтів є грубою помилкою перенесення коду між різними архітектурами:

:::tabs
@tab C
```c
#include <stdio.h>
#include <stdint.h>

void process_packet_header(const uint8_t *buffer) {
    // Помилка: припущення про Little-Endian у пам'яті
    uint32_t raw_id = *(const uint32_t *)buffer;

    // Надійна перевірка та конвертація з Big-Endian (Network Byte Order)
    #if defined(__GNUC__) || defined(__clang__)
    uint32_t id_le = __builtin_bswap32(raw_id);
    #else
    uint32_t id_le = ((raw_id >> 24) & 0xFF) |
                     ((raw_id >> 8)  & 0xFF00) |
                     ((raw_id << 8)  & 0xFF0000) |
                     ((raw_id << 24) & 0xFF000000);
    #endif

    (void)id_le;
}
```
@tab C++
```cpp
#include <iostream>
#include <bit>
#include <cstdint>
#include <span>
#include <concepts>

namespace net {

[[nodiscard]] constexpr uint32_t decode_be32(std::span<const uint8_t, 4> bytes) noexcept {
    if constexpr (std::endian::native == std::endian::little) {
        uint32_t val = (static_cast<uint32_t>(bytes[0]) << 24) |
                       (static_cast<uint32_t>(bytes[1]) << 16) |
                       (static_cast<uint32_t>(bytes[2]) << 8)  |
                       (static_cast<uint32_t>(bytes[3]));
        return val;
    } else {
        uint32_t val = (static_cast<uint32_t>(bytes[3]) << 24) |
                       (static_cast<uint32_t>(bytes[2]) << 16) |
                       (static_cast<uint32_t>(bytes[1]) << 8)  |
                       (static_cast<uint32_t>(bytes[0]));
        return val;
    }
}

} // namespace net
```
:::

У сучасному стандарті C++20 механізм `std::endian::native` дозволяє компілятору виконувати оптимізацію порядку байтів ще на етапі компіляції (`constexpr`), повністю усуваючи накладні витрати часу виконання.

### 3. Двійковий інтерфейс прикладних програм (ABI) та конвенції викликів

ABI (Application Binary Interface) — це сукупність низькорівневих правил, що визначають взаємодію скомпільованих модулів на рівні машинного коду:
- Які регістри процесора використовуються для передачі аргументів функцій, а які — для повернення результату.
- Які регістри функція зобов'язана зберегти на стеку перед модифікацією (Callee-saved / Preserved), а які може перезаписувати без узгодження (Caller-saved / Scratch).
- Правила вирівнювання стекового кадру (наприклад, вимога вирівнювання покажчика стека `SP` за межею 16 байтів перед викликом інструкцій SIMD/NEON).
- Механізм обробки апаратних чисел із плаваючою крапкою.

Розглянемо фундаментальну різницю в конвенціях виклику функції `int compute(int a, int b, int c, int d, int e, int f, int g)`:

- **System V AMD64 ABI (Linux x86_64)**: перші 6 цілочисельних аргументів передаються через регістри `RDI`, `RSI`, `RDX`, `RCX`, `R8`, `R9`. Сьомий аргумент `g` кладеться на стек.
- **ARM AAPCS (32-bit ARM Cortex-A/M)**: аргументи передаються лише через 4 регістри `r0`, `r1`, `r2`, `r3`. Решта аргументів `e`, `f`, `g` передаються через стек.
- **ARM64 AAPCS64 (AArch64)**: перші 8 аргументів передаються через 64-бітні регістри `x0`..`x7`.
- **RISC-V ABI (RV32/RV64)**: перші 8 цілочисельних аргументів передаються через регістри `a0`..`a7`.

#### Конфлікт Floating-Point ABI: hard-float проти soft-float

Одним із найпоширеніших джерел збоїв при крос-компіляції під 32-бітний ARM є несумісність бібліотек через вибір апаратного чи програмного режиму роботи з числами з плаваючою комою:

- **Soft-float (`armel` / `-mfloat-abi=soft`)**: компілятор генерує виклики програмних бібліотечних функцій емуляції чисел із плаваючою комою (`__adddf3`, `__mulsf3`). Аргументи типу `double` передаються парою цілочисельних регістрів `r0:r1`.
- **Hard-float (`armhf` / `-mfloat-abi=hard`)**: компілятор генерує прямі апаратні інструкції блоку VFP/NEON (`vadd.f32`, `vmul.f64`). Аргументи з плаваючою комою передаються безпосередньо у виділені регістри FPU `s0`..`s15` або `d0`..`d7`.
- **SoftFP (`-mfloat-abi=softfp`)**: компілятор генерує апаратні інструкції VFP, але конвенція виклику вимагає передавати параметри через цілочисельні регістри `r0`..`r3`.

Якщо застосунок скомпільовано з прапорцем `-mfloat-abi=hard`, а сторонню скомпільовану бібліотеку зібрано з `-mfloat-abi=softfp`, спроба викликати функцію з аргументом `double` призведе до того, що функція шукатиме число в регістрах `r0:r1`, тоді як викликач поклав його в регістр `d0`. Функція прочитає сміття з цілочисельних регістрів без жодного повідомлення про помилку з боку лінкера.

## Вирівнювання та пакування структур даних у пам'яті

Процесори зчитують дані з пам'яті блоками слів (по 4 або 8 байтів). Спроба прочитати 64-бітне число `uint64_t` за непарною адресою, не кратною 8, на одних процесорах спричиняє апаратний виняток пам'яті (Alignment Fault Trap на старіших ядрах ARM або MIPS), а на інших (x86_64) вимагає подвійного циклу звернення до шини пам'яті, що сповільнює роботу в кілька разів.

Щоб запобігти цьому, компілятор автоматично додає між полями структури порожні байти заповнення — **паддінг** (англ. *padding*), вирівнюючи кожне поле за межею, кратною його власному розміру (`alignof(T)`).

![Розбіжності вирівнювання структур даних ABI](/root/sys/sys-bsystem/cross-compilation/img/struct-alignment-padding.svg)

*Розбіжності вирівнювання (ABI Alignment) та байтового заповнення (Padding) для однакової структури C на x86-32 та ARM.*

### Демонстрація розбіжності розкладки структури

Розглянемо визначення структури мережевого пакета:

:::tabs
@tab C
```c
#include <stdint.h>

struct NetworkPacket {
    uint32_t header;  // 4 байти
    uint64_t payload; // 8 байтів
    uint16_t footer;  // 2 байти
};
```
@tab C++
```cpp
#include <cstdint>

struct NetworkPacket {
    uint32_t header;  // 4 байти
    uint64_t payload; // 8 байтів
    uint16_t footer;  // 2 байти
};
```
:::

Розподіл полів у пам'яті кардинально різниться залежно від цільового ABI:

1. **На x86-32 (Linux System V ABI)**:
   - Максимальне вирівнювання типу `uint64_t` на 32-бітній архітектурі x86 становить лише **4 байти**.
   - Поле `header` займає байти `0..3`.
   - Поле `payload` починається одразу з байта `4` (зміщення 4) і займає байти `4..11`.
   - Поле `footer` займає байти `12..13`.
   - Компілятор додає 2 байти паддінгу наприкінці (`14..15`), щоб розмір структури був кратним 4.
   - Підсумковий розмір: `sizeof(struct NetworkPacket) == 16 байтів`.

2. **На ARM (32-bit AAPCS та 64-bit AArch64)**:
   - Стандарт ARM AAPCS строго вимагає вирівнювання типу `uint64_t` за **8-байтовою межею**.
   - Поле `header` займає байти `0..3`.
   - Компілятор **змушений вставити 4 байти паддінгу** (`4..7`), щоб перенести `payload` на адресу, кратну 8!
   - Поле `payload` починається зі зміщення `8` і займає байти `8..15`.
   - Поле `footer` займає байти `16..17`.
   - Компілятор додає 6 байтів кінцевого паддінгу (`18..23`), щоб загальний розмір структури був кратним 8.
   - Підсумковий розмір: `sizeof(struct NetworkPacket) == 24 байти`!

Якщо програма на x86-32 запише цю структуру прямо в мережевий сокет або у файл, а пристрій на базі ARM спробує прочитати її через кастування буфера `(struct NetworkPacket*)buf`, поле `payload` на ARM прочитає 4 байти паддінгу та перші 4 байти справжнього корисного навантаження, перетворивши дані на сміття.

:::tabs
@tab C
```c
#include <stdio.h>
#include <stddef.h>
#include <stdint.h>

struct NetworkPacket {
    uint32_t header;
    uint64_t payload;
    uint16_t footer;
};

// Захист на етапі компіляції від неочікуваного вирівнювання
_Static_assert(sizeof(struct NetworkPacket) == 24, "Розмір структури не відповідає стандарту ARM AAPCS!");
_Static_assert(offsetof(struct NetworkPacket, payload) == 8, "Зміщення поля payload порушено!");
```
@tab C++
```cpp
#include <iostream>
#include <cstddef>
#include <cstdint>
#include <type_traits>

struct alignas(8) NetworkPacket {
    uint32_t header;
    uint64_t payload;
    uint16_t footer;
};

static_assert(std::is_standard_layout_v<NetworkPacket>, "Структура повинна мати Standard Layout!");
static_assert(sizeof(NetworkPacket) == 24, "Розмір NetworkPacket має бути рівно 24 байти!");
static_assert(offsetof(NetworkPacket, payload) == 8, "Зміщення payload повинно дорівнювати 8!");
static_assert(alignof(NetworkPacket) == 8, "Вирівнювання NetworkPacket має дорівнювати 8!");
```
:::

Використання атрибута `__attribute__((packed))` ліквідує всі проміжні байти паддінгу, стискаючи розмір структури до `4 + 8 + 2 = 14 байтів`. Проте на архітектурах без апаратної підтримки непарного доступу до пам'яті (деякі версії ARM Cortex-M0/M1) звернення до полів такої упакованої структури змушує компілятор генерувати побайтове зчитування за допомогою логічних зсувів і масок, що суттєво роздуває розмір бінарника та знижує швидкість доступу.

## Ізоляція системного дерева: Sysroot, Multilib та пошукові шляхи

Під час нативної збірки компілятор та компонувальник автоматично підтягують стандартні системні заголовні файли з каталогу `/usr/include` та скомпільовані динамічні бібліотеки з `/usr/lib` чи `/lib/x86_64-linux-gnu`.

Під час крос-компіляції підхід до пошуку залежностей повністю змінюється:
- Хостові каталоги `/usr/include` містять заголовки з конфігурацією макросів хоста (`<gnu/stubs-64.h>`), які оголошують типи під архітектуру x86_64.
- Хостові бібліотеки `/usr/lib/libssl.so` зібрані у форматі x86_64 ELF і не можуть бути приєднані компонувальником `aarch64-linux-gnu-ld`.

### Концепція Sysroot

Для запобігання конфліктам крос-компілятору передається каталог **Sysroot** (System Root) — повна копія кореневої файлової системи цільового пристрою, яка містить виключно цільові версії бібліотек C/C++ (`libc.so`, `libm.so`, `libstdc++.so`) та відповідні заголовні файли.

Шлях до цього дерева передається прапорцем `--sysroot=/path/to/target/sysroot` у викликах компілятора та лінкера. Компілятор підміняє всі абсолютні шляхи пошуку системних заголовків: замість `/usr/include/math.h` він відкриває `/path/to/target/sysroot/usr/include/math.h`.

### Механізм Multilib

Один і той самий крос-компілятор для мікроконтролерів (наприклад, `arm-none-eabi-gcc`) повинен уміти збирати прошивки для різних ядер родини ARM: від ARM Cortex-M0 (набір інструкцій ARMv6-M, без FPU) до ARM Cortex-M7 (ARMv7E-M, з подвійним FPU).

Компілятор вирішує цю проблему за допомогою механізму **Multilib**: тулчейн містить десятки попередньо скомпільованих версій стандартної бібліотеки C (Newlib) та `libgcc.a`, розкладених по окремих підкаталогах:

```text
/usr/lib/gcc/arm-none-eabi/13.2.1/
├── thumb/v6-m/nofp/libgcc.a      # Для Cortex-M0/M0+/M1
├── thumb/v7-m/nofp/libgcc.a      # Для Cortex-M3
├── thumb/v7e-m/nofp/libgcc.a     # Для Cortex-M4 без FPU
├── thumb/v7e-m/hard/libgcc.a     # Для Cortex-M4 з одинарною точністю FPU (FPv4-SP)
└── thumb/v7e-m/fp.dp/hard/libgcc.a # Для Cortex-M7 з подвійною точністю FPU (FPv5-DP)
```

Коли розробник передає прапорці `-mcpu=cortex-m4 -mfpu=fpv4-sp-d16 -mfloat-abi=hard`, драйвер компілятора автоматично вибирає відповідний каталог Multilib і лінкує саме ту версію стандартної бібліотеки, яка апаратно оптимізована під це ядро. Переглянути всі доступні комбінації в тулчейні можна командою `arm-none-eabi-gcc --print-multi-lib`.

### Скрипти компонувальника (Linker Scripts) проти динамічних завантажувачів

У крос-компіляції для операційних систем (Linux/Android) компонувальник генерує стандартний заголовок ELF із секцією `.interp`, куди записується шлях до динамічного компонувальника (наприклад, `/lib/ld-linux-aarch64.so.1`). Під час запуску ядро Linux завантажує цей інтерпретатор, який відображає спільні бібліотеки у віртуальну пам'ять процесу.

Навпаки, у крос-компіляції під «голе залізо» (Bare-metal MCU, `arm-none-eabi`) операційної системи немає, а адреси фізичної пам'яті зафіксовані апаратно на кристалі мікроконтролера. Компонувальник не може самостійно вирішити, куди розмістити код програми та змінні. Розробник зобов'язаний передати компонувальнику **скрипт лінкера** (`.ld`), який задає точну карту пам'яті:

```text
MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

SECTIONS
{
    .isr_vector : { KEEP(*(.isr_vector)) } > FLASH
    .text       : { *(.text*) *(.rodata*) }  > FLASH
    .data       : { *(.data*) } > RAM AT > FLASH
    .bss        : { *(.bss*) *(COMMON) }     > RAM
}
```

Без скрипта лінкера та мінімального стартового коду ініціалізації (`crt0.o` / `Reset_Handler`, який копіює секцію `.data` з Flash у RAM та обнуляє секцію `.bss`) компонувальник видасть фатальну помилку про відсутність пам'яті або точки входу. Прапорець `-T linkerscript.ld` та прапорці `--specs=nosys.specs` чи `--specs=nano.specs` є обов'язковими для кожного bare-metal крос-тулчейна.

### Пастка pkg-config при крос-компіляції

Утиліта `pkg-config` широко використовується в індустрії для отримання прапорців компіляції та лінкування сторонніх бібліотек (`pkg-config --cflags --libs libpng`).

Якщо викликати стандартний хостовий `pkg-config` під час крос-збірки, він прочитає конфігураційні `.pc` файли з хостового каталогу `/usr/lib/pkgconfig`. У результаті він поверне шляхи до хостових бібліотек x86_64.

Щоб ізолювати `pkg-config`, крос-тулчейни створюють спеціальну обгортку-скрипт (`aarch64-linux-gnu-pkg-config`), яка налаштовує службові змінні оточення:

```bash
#!/bin/sh
# Ізольована обгортка pkg-config для крос-компіляції під AArch64
export PKG_CONFIG_SYSROOT_DIR="/opt/sysroots/aarch64"
export PKG_CONFIG_LIBDIR="/opt/sysroots/aarch64/usr/lib/pkgconfig:/opt/sysroots/aarch64/usr/share/pkgconfig"
export PKG_CONFIG_PATH=""
exec /usr/bin/pkg-config "$@"
```

- `PKG_CONFIG_LIBDIR`: повністю замінює стандартні хостові шляхи пошуку каталогами всередині sysroot.
- `PKG_CONFIG_SYSROOT_DIR`: автоматично додає шлях до sysroot на початок кожного шляху `-I` та `-L`, знайденого в `.pc` файлах.

### Транзитивні залежності та прапорець -rpath-link

Під час крос-компонування динамічних бібліотек під Linux (AArch64) компонувальник часто стикається з транзитивними залежностями: бібліотека `libA.so` потребує `libB.so`. На хості цільові бібліотеки лежать не у звичних системних шляхах `/usr/lib`, а всередині sysroot.

Якщо передати прапорець `-rpath`, компонувальник запише шлях хостового каталогу в заголовок `DT_RPATH` цільового ELF-файлу, що зламає запуск програми на цільовому пристрої. Правильним інструментом для крос-компонувальника є прапорець `-Wl,-rpath-link,/opt/sysroots/aarch64/usr/lib`: він підказує компонувальнику, де шукати залежності **під час складання на хості**, не додаючи сміттєвих шляхів у кінцевий бінарник.

## Пастка кодогенерації під час збірки: Host tools проти Target binaries

Найпоширеніша інженерна криза при організації крос-збірки середніх і великих проєктів виникає, коли в дереві коду присутні допоміжні утиліти, які повинні бути скомпільовані й запущені **в процесі самої збірки** для генерації вихідних кодів, констант або синтаксичних аналізаторів (наприклад, `flex`, `bison`, компілятор protobuf `protoc`, генератори таблиць хешів чи конвертери шрифтів).

![Конвеєр подвійного тулчейну та кодогенерація](/root/sys/sys-bsystem/cross-compilation/img/dual-toolchain-pipeline.svg)

*Конвеєр подвійного тулчейну: генерація коду нативним інструментом хоста та компіляція цілі крос-компілятором.*

### Механіка помилки

Розглянемо типовий наївний фрагмент `CMakeLists.txt`:

```cmake
# Помилковий наївний підхід при крос-компіляції
cmake_minimum_required(VERSION 3.20)
project(MyEmbeddedDevice C CXX)

# Допоміжна утиліта для генерації хеш-таблиці
add_executable(generate_lookup_tables tools/table_generator.c)

# Генерація файлу під час компіляції
add_custom_command(
    OUTPUT "${CMAKE_CURRENT_BINARY_DIR}/lookup_table.c"
    COMMAND generate_lookup_tables -o "${CMAKE_CURRENT_BINARY_DIR}/lookup_table.c"
    DEPENDS generate_lookup_tables
)

# Цільова прошивка
add_executable(firmware main.c "${CMAKE_CURRENT_BINARY_DIR}/lookup_table.c")
```

Якщо цей проєкт конфігурується з файлом тулчейна для ARM64 (`-DCMAKE_TOOLCHAIN_FILE=arm64.cmake`), змінна `CMAKE_CROSSCOMPILING` встановлюється в `TRUE`. Команда `add_executable(generate_lookup_tables ...)` використовує цільовий крос-компілятор `aarch64-linux-gnu-gcc`.

У результаті файл `generate_lookup_tables` успішно збирається як двійковий файл для процесора AArch64. На наступному кроці система збірки (Ninja або Make) намагається виконати директиву `add_custom_command()`, запускаючи `generate_lookup_tables` на хості розробника (x86_64). Операційна система хоста повертає помилку:

```text
ninja: error: '/home/user/build/bin/generate_lookup_tables': cannot execute binary file: Exec format error
[12/45] Generating lookup_table.c FAILED
```

### Рішення подвійного тулчейну (Dual Toolchain)

Система збірки повинна чітко розрізняти інструменти хоста (Host Tools) та бінарники цільової платформи (Target Artifacts). Існують три стандартні інженерні стратегії:

1. **Розділення на два проєкти (Superbuild / ExternalProject)**:
   Створюється кореневий сценарій, який спочатку конфігурує та збирає підпроєкт `HostTools` за допомогою стандартного нативного компілятора хоста (`/usr/bin/gcc`), інсталює скомпільовані бінарники у тимчасовий каталог хоста, а потім запускає основну крос-збірку цільового проєкту, передаючи шлях до готових хостових генераторів через змінні.

2. **Експорт імпортованих цілей (`Export & Import Targets`)**:
   Хостова утиліта збирається окремо на хості, а її ціль експортується у файл `HostToolsConfig.cmake`. Основний крос-проєкт використовує стандартну команду `find_program()` або `find_package(HostTools REQUIRED)` з налаштуванням пошуку виключно на хості:

```cmake
# Пошук генератора protoc на хості під час крос-збірки
find_program(PROTOC_EXECUTABLE protoc
    NO_CMAKE_FIND_ROOT_PATH # Забороняє шукати всередині цільового sysroot
    REQUIRED
)
```

Повний наскрізний проєкт із конфігурацією подвійного тулчейну, утилітою розрахунку CRC-32 на C та C++ і захистом від помилок виконання розібрано у практичній вставці: [практикум подвійного тулчейну в CMake](root:sys-bsystem/cross-compilation/proj-dual-toolchain-codegen.md).

## Емуляція цільової архітектури: QEMU User Mode та binfmt_misc

Однією з найбільших перешкод у розробці під чужі платформи є тестування: як запустити модульні тести (Unit Tests) у системі неперервної інтеграції (CI/CD) на кожному коміті, якщо фізична апаратна плата (Hardware-in-the-Loop) недоступна або її підключення до сервера є занадто дорогим?

Найпотужнішим інструментом вирішення цієї проблеми в середовищі Linux є режим емуляції простору користувача **QEMU User Mode** (`qemu-user-static`) у поєднанні з модулем ядра **`binfmt_misc`**.

![Емуляція QEMU User Mode та binfmt_misc](/root/sys/sys-bsystem/cross-compilation/img/qemu-user-emulation.svg)

*Прозора емуляція цільових бінарників: перехоплення заголовка ELF модулем binfmt_misc та трансляція інструкцій у qemu-user-static.*

### Механізм прозорого перехоплення binfmt_misc

Ядро Linux містить підсистему `binfmt_misc` (Miscellaneous Binary Format), яка дозволяє реєструвати довільні інтерпретатори для двійкових файлів за їхньою сигнатурою (магічними байтами заголовка файлу).

Коли користувач або тестовий фреймворк викликає системний виклик `execve()` для двійкового файлу ARM64:
1. Ядро Linux на хості x86_64 зчитує заголовок ELF файлу.
2. Поле `e_machine` містить значення `0xB7` (`EM_AARCH64`), що не збігається з архітектурою хоста `0x3E` (`EM_X86_64`).
3. Модуль `binfmt_misc` перевіряє таблицю відповідностей і виявляє зареєстроване правило для архітектури AArch64.
4. Ядро прозоро підміняє виклик, запускаючи статично скомпільований емулятор `/usr/bin/qemu-aarch64-static` та передаючи йому цільовий бінарник як аргумент.

```bash
# Перевірка реєстрації емулятора в системі binfmt_misc
cat /proc/sys/fs/binfmt_misc/qemu-aarch64
# Вивід:
# enabled
# interpreter /usr/bin/qemu-aarch64-static
# flags: POCF
# offset 0
# magic 7f454c460201010000000000000000000200b700
# mask  ffffffffff010100fffffffffffffffffeffff00
```

### Динамічна двійкова трансляція TCG

Утиліта `qemu-aarch64-static` не емулює всю материнську плату, таймери чи периферію (як це робить QEMU System Mode). Вона працює виключно як транслятор простору користувача:
- **Tiny Code Generator (TCG)**: розбирає блоки інструкцій ARM64, перетворює їх на платформонезалежні мікрооперації, а потім генерує еквівалентний машинний код x86_64 на льоту, кешуючи трансльовані блоки у пам'яті.
- **Трансляція системних викликів (Syscall Translation)**: коли гостьова програма викликає системний виклик (наприклад, `write()` або `mmap()`), QEMU перехоплює номер виклику, транскодує структури даних із формату цілі у формат хоста (враховуючи різницю розмірів полів і порядок байтів) і передає виклик нативному ядру Linux x86_64.

### Інтеграція з CMake та CTest

CMake підтримує стандартний механізм запуску тестів через емулятор за допомогою властивості `CROSSCOMPILING_EMULATOR`:

```cmake
# У файлі тулчейна або CMakeLists.txt
if(CMAKE_CROSSCOMPILING)
    find_program(QEMU_ARM_EMULATOR NAMES qemu-aarch64-static qemu-aarch64)
    if(QEMU_ARM_EMULATOR)
        # Вказуємо шлях до цільового sysroot для пошуку динамічних бібліотек .so
        set(CMAKE_CROSSCOMPILING_EMULATOR
            "${QEMU_ARM_EMULATOR}"
            "-L" "${CMAKE_SYSROOT}"
        )
    endif()
endif()

# Оголошення тесту в CMake
enable_testing()
add_executable(unit_tests tests/test_main.cpp)
add_test(NAME CoreAlgorithmTests COMMAND unit_tests)
```

Тепер команда `ctest` на хості x86_64 автоматично запустить кожен цільовий ARM бінарник через QEMU, збере вивід та коди повернення так, ніби тести виконувалися нативно.

### Межі та сліпі зони емуляції QEMU User Mode

Попри зручність, QEMU User Mode не є повноцінною заміною реального апаратного тестування:

1. **Розбіжності моделі пам'яті (Memory Ordering Consistency)**:
   Процесори x86_64 реалізують строгу модель пам'яті TSO (Total Store Order), де операції запису гарантовано не обганяють інші записи. Навпаки, процесори ARM і RISC-V мають слабку модель пам'яті (Weak Memory Ordering). Багатопотоковий код із гонкою даних (Data Race) або відсутніми бар'єрами пам'яті (`std::memory_order_relaxed` замість `acquire`/`release`) може ідеально й стабільно працювати під QEMU на x86_64, але фатально зависати чи руйнувати пам'ять на фізичному кристалі ARM.
2. **Нестандартні `ioctl()` та прямий доступ до апаратури**:
   QEMU емулює стандартний набір викликів POSIX, але не вміє транслювати специфічні структури нестандартних драйверів пристроїв, GPIO, апаратних прискорювачів або контролерів переривань NVIC.
3. **Таймінги та системи реального часу**:
   Емуляція спотворює реальні часові характеристики виконання інструкцій; перевірити жорсткі дедлайни задач реального часу (RTOS) через QEMU неможливо.

## Інженерний чеклист надійної крос-компіляції

Стійкий і повторюваний конвеєр крос-компіляції базується на чотирьох залізних правилах:

1. **Абсолютна ізоляція цільового дерева (Sysroot)**:
   Крос-компілятор ніколи не повинен шукати заголовні файли чи бібліотеки в системних каталогах хоста (`/usr/include`, `/usr/lib`). Усі шляхи пошуку мають перенаправлятися в цільовий sysroot за допомогою прапорців `--sysroot` та змінних CMake `CMAKE_FIND_ROOT_PATH_MODE_*`.
2. **Явне керування розрядністю та порядком байтів**:
   Усі міжплатформні структури даних, файлові формати та мережеві протоколи повинні використовувати типи фіксованої довжини (`uint32_t`, `int64_t`) та явну конвертацію порядку байтів (`std::endian`). Пряме кастування сирих структур мови C заборонено.
3. **Детерміноване розділення інструментів хоста та коду цілі**:
   Усі допоміжні утиліти кодогенерації повинні збиратися нативним компілятором хоста в окремій області складання або імпортуватися як готові артефакти хоста.
4. **Багаторівнева верифікація**:
   Базові логічні тести мають запускатися автоматично в середовищі CI через QEMU User Mode та CTest, а багатопотокова синхронізація, драйвери периферії та часові обмеження повинні проходити обов'язкову верифікацію на реальному цільовому стенді.
