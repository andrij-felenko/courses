# 📜 Як з'явилася канадська збірка: витоки тристоронньої крос-компіляції

У практиці системного програмування канадською збіркою називають конфігурацію створення компілятора, за якої система збірки (Build), система виконання скомпільованого компілятора (Host) та цільова архітектура генерованого ним коду (Target) є трьома абсолютно різними апаратними чи програмними платформами.

Цей термін виник на зламі 1980-х і 1990-х років у надрах компанії Cygnus Support — першого у світі комерційного підприємства, збудованого навколо підтримки вільного програмного забезпечення. Засновник компанії Джон Гілмор (John Gilmore) разом із колегами Майклом Тіманном (Michael Tiemann) та Девідом Генкель-Воллесом (David Henkel-Wallace) зіткнулися з інженерним викликом, який диктувався економікою та апаратними обмеженнями тогочасної обчислювальної техніки.

---

## Апаратна криза розробки для вбудованих систем

На початку 1990-х років промислові замовники масово переходили на мікроконтролери та вбудовані процесори архітектур Motorola 68k, Hitachi H8/300, AMD 29k та MIPS. Розробники вбудованого коду працювали переважно за персональними комп'ютерами під керуванням MS-DOS або ранніх версій Windows NT. Вони потребували повноцінного оптимізувального тулчейна: компілятора GCC, компонувальника GNU ld та зневаджувача GDB, здатних працювати на їхніх офісних PC і генерувати прошивки для цільових плат.

Проте тогочасні персональні комп'ютери класу Intel 80386 або 80486 мали від 4 до 8 мегабайтів оперативної пам'яті й жорсткі диски на сотню мегабайтів. Сам компілятор GNU C (GCC) був велетенським багатопрохідним програмним комплексом. Спроба скомпілювати GCC нативним компілятором безпосередньо всередині DOS або раннього середовища Cygwin на машині 486/33 МГц вимагала понад 10–15 годин безперервної роботи, спричиняла переповнення дискового простору віртуальної пам'яті й нерідко завершувалася аварійним збоєм через вичерпання ресурсів.

Водночас інженери компанії Cygnus Support володіли потужними робочими станціями Sun Microsystems (процесори SPARC під керуванням операційної системи SunOS/Solaris) та HP 9000 (PA-RISC). Ці Unix-сервери мали швидкі RISC-процесори, десятки мегабайтів RAM та високопродуктивні дискові підсистеми SCSI. Збірка всього тулчейна на станції Sun займала лічені хвилини.

Виникла потреба використати потужні робочі станції Sun для складання бінарників GCC, які запускатимуться на комп'ютерах клієнтів під Windows, але створюватимуть машинний код для вбудованих мікроконтролерів Hitachi або Motorola.

## Чому саме «канадська»

Коли Джон Гілмор формалізував цю схему для системи конфігурації `configure` (попередника GNU Autotools), постало питання термінології. Звичайна крос-компіляція вже була відома індустрії: машина A збирає бінарник, що працює на машині B (дві сторони: Build=A, Host=B, Target=B).

У конфігурації Cygnus систем було три:
- **Build**: `sparc-sun-solaris2` (робоча станція, де крутиться процес збірки);
- **Host**: `i386-pc-cygwin32` або `i386-pc-mingw32` (робоче місце клієнта);
- **Target**: `h8300-hitachi-coff` або `m68k-unknown-elf` (цільовий мікроконтролер).

На той час у політичній системі Канади тривало гостре протистояння між трьома основними національними партіями: Прогресивно-консервативною (Progressive Conservatives), Ліберальною (Liberals) та Новою демократичною партією (New Democratic Party, NDP). Ситуація, коли жодна з двох традиційних партій не мала абсолютної більшості й утворювався стійкий тристоронній баланс сил, була відома в політичному жаргоні як трипартійна система Канади.

Оскільки в процесі компіляції брали участь саме три незалежні платформи (Build != Host != Target), Джон Гілмор жартома охрестив цей сценарій терміном **Canadian Cross** («Канадський хрест» або «Канадська збірка»). Термін настільки точно описав проблему взаємного схрещування архітектур, що миттєво закріпився в інженерній документації проєкту GNU і згодом увійшов до стандартів усіх промислових систем складання.

## Триетапний конвеєр побудови: подолання замкненого кола

Неможливо зібрати компілятор для платформи B на платформі A в один крок, якщо на платформі A немає компілятора, здатного створювати бінарники для B. Щоб подолати це замкнене коло, інженери Cygnus розробили суворий триетапний конвеєр:

1. **Етап 1 (Проміжний крос-компілятор Build -> Host)**:
   На системі Build (Solaris) нативним компілятором збирається крос-компілятор, який працює на Solaris, але генерує двійкові файли для Windows (`build=sparc-sun-solaris2`, `host=sparc-sun-solaris2`, `target=i386-pc-mingw32`).

2. **Етап 2 (Цільовий крос-компілятор Build -> Target)**:
   На системі Build тим самим нативним компілятором збирається другий крос-компілятор, який працює на Solaris і створює код для мікроконтролера (`build=sparc-sun-solaris2`, `host=sparc-sun-solaris2`, `target=m68k-elf`). Цей компілятор негайно використовується для складання стандартної бібліотеки C (Newlib) та системних бібліотек середовища виконання під процесор Motorola 68k.

3. **Етап 3 (Фінальна канадська збірка Host -> Target)**:
   На системі Build запускається компілятор першого етапу (`build -> host`), який компілює вихідні тексти GCC. Отримані бінарні файли вміють працювати лише у Windows (`host=i386-pc-mingw32`), але як кодогенератор у них зашито логіку створення інструкцій Motorola 68k (`target=m68k-elf`). До отриманого пакета додаються заздалегідь скомпільовані на другому етапі бібліотеки цілі (`target sysroot`).

У результаті клієнт отримував готовий інсталяційний пакет для Windows, скомпільований за лічені хвилини на потужному сервері Solaris, повністю готовий до прошивки вбудованого контролера без потреби мати потужне залізо на робочому місці.

Сьогодні канадська збірка є щоденною практикою великих дистрибутивів: саме так на високопродуктивних серверах x86_64 Linux у середовищі CI/CD створюються готові офіційні релізи тулчейнів LLVM та GCC для Windows (MinGW-w64) та macOS, що транслюють код для ARM Cortex-M, RISC-V або WebAssembly.
