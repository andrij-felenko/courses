Кросплатформенна бібліотека на C++, яка бездоганно збирається й проходить тести на Linux під GCC та на macOS під Clang, під час перенесення на Windows раптово зазнає фатального краху в процесі виконання: щойно виділений у динамічній бібліотеці (`.dll`) рядок `std::string` або динамічний масив знищується в коді головної програми (`.exe`), операційна система аварійно зупиняє процес із системним кодом винятку `STATUS_HEAP_CORRUPTION` (`0xC0000374`), хоча покажчик був валідним і пам'ять не звільнялася двічі. Одночасно система збірки CMake не може зібрати залежні виконувані файли через помилки нерозв'язаних символів `LNK2019`, бо компілятор не згенерував необхідний файл бібліотеки імпорту `.lib`, скрипт розгортання завершується з помилкою `ERROR_PATH_NOT_FOUND` через перевищення шляхом довжини у 261 символ, а повідомлення про помилки в консолі перетворюються на нечитабельні «кракозябри».

Причина криється в тому, що Windows фундаментально не є POSIX-сумісною операційною системою. Її двійковий формат виконуваних файлів Portable Executable (PE/COFF), механізм динамічного зв'язування бібліотек, структура стандартного рантайму C Runtime (CRT), правила адресації файлової системи та модель кодових сторінок тексту створювалися на основі інженерних рішень DEC VMS, MS-DOS та ранніх версій Windows NT. Розуміння цих низькорівневих механізмів є обов'язковим для побудови надійних міжплатформних систем збірки під Windows.

## Екосистема компіляторів на Windows: MSVC, MinGW-w64 та Clang-CL

На платформі Windows розробка на C та C++ спирається на три різні родини інструментів, кожна з яких має власний двійковий інтерфейс (ABI), формат діагностики та рівень інтеграції з операційною системою.

### MSVC (Microsoft Visual C++)

Рідний тулчейн Microsoft є стандартом де-факто для розробки під Windows. До його складу входять драйвер компілятора `cl.exe`, компонувальник `link.exe` та бібліотекар `lib.exe`.

На відміну від Unix-компіляторів, які за замовчуванням доступні через глобальний системний `PATH`, MSVC вимагає суворого налаштування змінних середовища для кожного сеансу збірки. Для цього розробник або система збірки запускає командний файл `vcvarsall.bat` (або `VsDevCmd.bat`), передаючи йому цільову архітектуру (`x64`, `x86`, `arm64` або варіанти крос-компіляції `x64_arm64`). Цей скрипт ініціалізує змінні:
- `INCLUDE`: абсолютні шляхи до системних заголовків Windows SDK та стандартної бібліотеки MSVC STL;
- `LIB`: каталоги пошуку імпортних та статичних бібліотек;
- `PATH`: каталоги з бінарними файлами компілятора відповідної архітектури (наприклад, `Hostx64\x64`).

Компілятор `cl.exe` використовує синтаксис прапорців MS-DOS із прямим слешем (`/`), підтримує структуровану обробку винятків Windows (Structured Exception Handling, SEH, конструкції `__try`/`__except`) та вимагає явного ввімкнення C++ винятків прапорцем `/EHsc`. Двійковий інтерфейс MSVC (Microsoft C++ ABI) регламентує власну схему спотворення імен (Name Mangling), унікальне розташування таблиць віртуальних методів (`vftable`, `vbtable`) та структури інформації про типи часу виконання (RTTI).

### MinGW-w64 (GCC та GNU Binutils)

Проєкт MinGW-w64 (Minimalist GNU for Windows) — це порт компілятора GCC та утиліт GNU Binutils (`as`, `ld`, `dlltool`) для генерації двійкового коду під Windows. Він надає власні чисті заголовкові файли та бібліотеки імпорту для системного Win32 API, дозволяючи використовувати традиційний синтаксис прапорців GCC (`-O2`, `-Wall`, `-I`, `-L`, `-l`).

Головна архітектурна пастка MinGW-w64 полягає в тому, що він використовує **Itanium C++ ABI** поверх двійкового формату Windows PE/COFF. Це означає, що правила спотворення імен функцій (`_Z...` у MinGW проти `?...` у MSVC), структура розміщення об'єктів у пам'яті та механізми розгортання стеку винятків (DWARF/SEH проти таблиць `__CxxFrameHandler3`) є повністю несумісними між MinGW та MSVC.

> ⚠️ **Передавання C++ об'єктів між MSVC та MinGW.** Спроба передати екземпляр C++ класу з віртуальними методами або стандартного контейнера (`std::vector`, `std::string`) через межу DLL, одна з яких зібрана MSVC, а інша — MinGW, є грубим порушенням ABI. Програма зазнає аварійного краху (Access Violation) на першому ж зверненні до пам'яті через несумісне розташування покажчиків `vptr`. Єдиний безпечний міст між цими тулчейнами — це чистий C ABI (`extern "C"` з примітивними типами або непрозорими покажчиками).

Історично MinGW лінкувався з застарілим системним файлом `msvcrt.dll`, що створювало проблеми з підтримкою стандартів C99/C11 (наприклад, форматними специфікаторами `%zu` та `%llx` у функціях `printf`). Сучасні версії MinGW-w64 дозволяють обирати Universal CRT (`ucrt`) як цільовий рантайм.

### Clang-CL (LLVM з сумісністю з MSVC)

Інструмент `clang-cl.exe` — це спеціальний драйвер компілятора Clang/LLVM, створений для повної мімікрії під поведінку `cl.exe`. Він приймає всі стандартні прапорці MSVC (`/O2`, `/MD`, `/std:c++20`, `/I`, `/Fo`), генерує повністю сумісний Microsoft C++ ABI, використовує офіційні заголовки Microsoft STL і Universal CRT.

У поєднанні з компонувальником `lld-link.exe` (режим LLD для Windows PE/COFF), Clang-CL забезпечує швидкість компонування у 3–5 разів вищу порівняно з `link.exe`, зберігаючи повну двійкову сумісність з об'єктними файлами та статичними бібліотеками, зібраними оригінальним MSVC.

## Лабіринт C Runtime (CRT) та катастрофа змішування рантаймів

У середовищі Windows кожна програма на C або C++ спирається на бібліотеку часу виконання (C Runtime Library, CRT). Ця бібліотека відповідає за ініціалізацію процесу перед викликом `main()`, керування динамічною пам'яттю (`malloc`, `free`, `new`, `delete`), операції введення-виведення (`FILE*`, файлові дескриптори) та підтримку локалі.

### Моделі зв'язування CRT: `/MT`, `/MTd`, `/MD`, `/MDd`

Компілятор MSVC пропонує чотири взаємовиключні режими підключення CRT, які задаються відповідними прапорцями:

1. `/MD` (Multi-threaded DLL, Release): код компонується з динамічним рантаймом. Під час збірки лінкер використовує бібліотеку імпорту `msvcrt.lib` (або сучасну пару `vcruntime.lib` + `ucrt.lib`), а під час запуску програми завантажуються динамічні бібліотеки `vcruntime140.dll` та `ucrtbase.dll`.
2. `/MDd` (Multi-threaded Debug DLL): налагоджувальна версія динамічного рантайму. Використовує бібліотеки `vcruntimed.lib` і `ucrtd.lib`, завантажуючи `vcruntime140d.dll` та `ucrtbased.dll`. Вмикає перевірки меж масивів, захисні байти пам'яті та налагоджувальні ітератори STL (`_ITERATOR_DEBUG_LEVEL = 2`).
3. `/MT` (Multi-threaded Static, Release): статичне вшивання рантайму. Код стандартної бібліотеки з файлів `libcmt.lib`, `libvcruntime.lib` та `libucrt.lib` копіюється безпосередньо у фінальний бінарний образ (`.exe` або `.dll`). Програма не потребує зовнішніх DLL рантайму на цільовій машині, проте її розмір зростає.
4. `/MTd` (Multi-threaded Debug Static): статичний налагоджувальний рантайм із бібліотек `libcmtd.lib`, `libvcruntimed.lib` та `libucrtd.lib`.

### Еволюція рантаймів: від `msvcrt.dll` до Universal CRT (UCRT)

Історично кожна версія Visual Studio постачалася з власною версією CRT: Visual Studio 2010 використовувала `msvcr100.dll`, Visual Studio 2012 — `msvcr110.dll`, а Visual Studio 2013 — `msvcr120.dll`. Якщо програма використовувала три різні сторонні бібліотеки, скомпільовані різними версіями студії, в адресний простір одного процесу одночасно завантажувалися три різні копії рантайму.

Починаючи з Visual Studio 2015, корпорація Microsoft реорганізувала архітектуру CRT, розділивши її на дві незалежні частини:
- **Universal CRT (UCRT):** низькорівнева реалізація стандартної бібліотеки C (`ucrtbase.dll`). UCRT стала системним компонентом Windows (починаючи з Windows 10 вона постачається та оновлюється разом з ОС). Вона є бінарно стабільною і не залежить від версії компілятора.
- **VC++ Runtime (VCRuntime):** компіляторно-залежний шар (`vcruntime140.dll` та `msvcp140.dll`), що містить реалізацію обробки винятків, ініціалізацію RTTI та стандартну бібліотеку C++ (STL). Microsoft гарантує двійкову сумісність цього шару для всіх версій починаючи з VS 2015 (v140) і до найновіших VS 2022 (v143).

Окремо в системному каталозі `System32` існує файл `msvcrt.dll`. Цей файл призначений виключно для внутрішніх потреб операційної системи Windows. Використання його у прикладних програмах сучасними компіляторами заборонене, оскільки він зафіксований на рівні стандарту C89 і не підтримує сучасні механізми захисту пам'яті.

### Механізм краху при невідповідності рантаймів (Heap Corruption)

Найнебезпечніша помилка під час збірки під Windows — це невідповідність рантаймів (Runtime Mismatch) між виконуваним файлом та підключеними DLL, або між різними DLL у межах одного процесу.

![Конфлікт рантаймів CRT та руйнування купи при виділенні та звільненні пам'яті](/root/sys/sys-bsystem/windows-toolchain-nuances/img/crt-heap-mismatch.svg)

*Процес Windows із двома різними екземплярами CRT: спроба звільнити блок пам'яті через `free()` у чужому рантаймі призводить до фатального винятку STATUS_HEAP_CORRUPTION.*

В основі цієї проблеми лежить механізм керування пам'яттю в ядрі Windows NT:

1. **Ізольовані дескриптори купи:** Під час завантаження кожного модуля зі статичним рантаймом (`/MT`) або окремого динамічного екземпляра CRT функція ініціалізації рантайму `_heap_init` викликає системну функцію Win32 API `HeapCreate(0, 0, 0)`. Ядро повертає приватний дескриптор купи (`HANDLE _crtheap`).
2. **Виділення пам'яті:** Коли код усередині DLL викликає `malloc(size)` або оператор `new`, рантайм транслює цей виклик у `HeapAlloc(_crtheap_B, 0, size)`. Менеджер купи виділяє сегмент пам'яті та записує безпосередньо перед адресою поверненого блоку службові метадані, прив'язані до дескриптора купи B.
3. **Звільнення чужої пам'яті:** Якщо покажчик на виділений блок передається у головний виконуваний файл, зібраний з динамічним рантаймом (`/MD`), і там викликається `free(ptr)` або оператор `delete`, рантайм застосунку викликає `HeapFree(_crtheap_A, 0, ptr)`.
4. **Крах процесу:** Менеджер купи операційної системи перевіряє метадані заголовка блоку `ptr` на відповідність дескриптору `_crtheap_A`. Оскільки блок належить іншій купі (дескриптору `_crtheap_B`), менеджер виявляє порушення цілісності структур даних і негайно генерує фатальний виняток `STATUS_HEAP_CORRUPTION (0xC0000374)`. Процес миттєво завершується без виконання деструкторів та збереження даних.

### Змішування Debug (`/MDd`) та Release (`/MD`)

Навіть якщо обидва модулі зібрані з динамічним рантаймом, але один у режимі Debug (`/MDd`), а інший у Release (`/MD`), програма зазнає руйнування пам'яті:
- У Debug-версії функція `malloc` насправді викликає `_malloc_dbg`. Вона виділяє додаткові байти для заголовка `_CrtMemBlockHeader` (32 байти), що зберігає ім'я вихідного файлу, номер рядка та лічильник виділень, а також додає 4 захисні байти `0xFD` (NoMansLand) перед і після корисного блоку.
- Коли Release-версія намагається звільнити цей блок через стандартний `free`, вона вважає, що заголовок `_CrtMemBlockHeader` відсутній, зчитує зміщення за іншою формулою і пошкоджує службові структури менеджера пам'яті.

### Файлові дескриптори та об'єкти C++ STL

Проблема не обмежується динамічною пам'яттю:
- **Таблиця файлових дескрипторів C:** Кожен екземпляр CRT підтримує власний внутрішній масив `_ioinfo` для відображення низькорівневих дескрипторів POSIX (`0, 1, 2...`) на системні дескриптори `HANDLE` Windows. Файл, відкритий через `_open()` або `fopen()` у модулі A, має дескриптор `3` у таблиці модуля A. Якщо передати цей числовий дескриптор у модуль B і викликати `_read(3, ...)`, модуль B звернеться до власної неініціалізованої таблиці, що призведе до помилки `EBADF` або читання сміття.
- **Об'єкти `std::string` та `std::vector`:** Реалізація `std::string` у Microsoft STL використовує оптимізацію малих рядків (Small String Optimization, SSO). У режимі Debug об'єкт містить додаткові поля перевірки ітераторів (`_ITERATOR_DEBUG_LEVEL`), тому розмір структури `std::string` у Debug складає 40 байтів, а в Release — 32 байти. Передавання такого об'єкта через границю функцій між модулями з різними налаштуваннями призводить до зсуву полів у пам'яті та руйнування стеку.

## Архітектура динамічних бібліотек Windows DLL та експорт символів

Модель динамічних бібліотек (Dynamic Link Library, DLL) у Windows суттєво відрізняється від моделі спільних бібліотек Shared Object (`.so`) у світі Linux/ELF.

### Явний експорт проти дефолтної видимості ELF

У форматі ELF за замовчуванням усі глобальні функції та змінні автоматично експортуються у динамічну таблицю символів `.dynsym`. У форматі PE/COFF діє протилежне правило: **за замовчуванням жоден символ з DLL не експортується назовні**.

Щоб зробити функцію або клас доступними для інших модулів, розробник зобов'язаний явно вказати це компілятору за допомогою спеціального атрибута декларації:

:::tabs
```c
__declspec(dllexport) int calculate_hash(const char* data, size_t length);
```
```cpp
__declspec(dllexport) int calculate_hash(std::span<const char> data);
```
:::

Коли компілятор `cl.exe` бачить `__declspec(dllexport)`, він генерує у скомпільованому об'єктному файлі (`.obj`) спеціальну директиву в секції `.drectve` (наприклад, `-export:calculate_hash`). 

Під час фінального компонування `link.exe /DLL`:
1. Формує виконуваний двійковий файл `.dll`, записуючи в нього таблицю адрес експорту (Export Address Table, EAT), таблицю імен та таблицю порядкових номерів (Ordinal Table).
2. Одночасно генерує допоміжний файл **бібліотеки імпорту (`.lib`)**.

![Архітектура експорту та імпорту символів через бібліотеку імпорту .lib](/root/sys/sys-bsystem/windows-toolchain-nuances/img/dll-import-export-flow.svg)

*Повний конвеєр створення DLL: компілятор створює директиви експорту, лінкер генерує образ DLL та файл імпорту .lib, а споживач використовує .lib для заповнення таблиці IAT.*

### Роль бібліотеки імпорту (.lib) та таблиця IAT

Початківці часто плутають бібліотеку імпорту (`mylib.lib`) зі статичною бібліотекою (`static_mylib.lib`). Бібліотека імпорту для DLL **не містить виконуваного коду функцій**. Вона являє собою невеликий COFF-архів, що містить короткі об'єктні заглушки (Import Thunks) та описи елементів, які вказують лінкеру споживача:
- З якого саме файлу DLL завантажувати функцію (`mylib.dll`);
- Яке ім'я має символ у таблиці адрес імпорту (Import Address Table, IAT), наприклад, `__imp_calculate_hash`.

Коли споживач компілює власний код, він оголошує функцію з атрибутом `__declspec(dllimport)`:

:::tabs
```c
__declspec(dllimport) int calculate_hash(const char* data, size_t length);
```
```cpp
__declspec(dllimport) int calculate_hash(std::span<const char> data);
```
:::

Атрибут `__declspec(dllimport)` оптимізує машинний код. Замість генерації звичайного виклику `call calculate_hash` (який вимагав би проміжного переходу через трамплін-заглушку `jmp [__imp_calculate_hash]`), компілятор генерує пряму інструкцію непрямого виклику:

```asm
call qword ptr [__imp_calculate_hash]
```

Під час запуску програми системний завантажувач Windows (NT Loader) відкриває `mylib.dll`, знаходить реальну адресу функції в пам'яті та записує її безпосередньо у відповідну комірку IAT виконуваного файлу.

> ⚠️ **Експорт глобальних змінних та статичних полів.** Якщо для функцій пропуск `__declspec(dllimport)` у коді споживача призводить лише до незначної втрати швидкості через зайвий перехід `jmp`, то для глобальних змінних та статичних полів класу відсутність `dllimport` є фатальною. Без `dllimport` компілятор згенерує інструкцію, що працює з адресою самої комірки IAT, замість розіменування адреси реальної змінної в DLL, що призведе до помилки лінкування `LNK2001` або читання невірної адреси.

### Автоматичний експорт у CMake: `CMAKE_WINDOWS_EXPORT_ALL_SYMBOLS`

Перенесення великих проєктів із Linux під Windows ускладнюється тим, що розробники рідко розставляють макроси експорту перед кожним класом. Для розв'язання цієї проблеми CMake надає механізм `CMAKE_WINDOWS_EXPORT_ALL_SYMBOLS`.

Під час увімкнення цієї властивості CMake виконує спеціальний конвеєр:
1. Компілює всі сирцеві файли цілі в об'єктні файли `.obj`.
2. Запускає допоміжну утиліту `bindexplib.exe`, яка парсить таблиці символів COFF у всіх `.obj` файлах цілі.
3. Фільтрує службові символи компілятора (RTTI, `DllMain`, внутрішні вектори винятків) та записує всі глобальні символи у текстовий файл визначення модуля `.def`.
4. Передає згенерований файл лінкеру через прапорець `/DEF:exports.def`.

### Проблема ліміту 65 535 символів (LNK1189)

Формат PE/COFF містить жорстке апаратне обмеження: поле порядкового номера символу в таблиці експорту (Ordinal Table) є 16-бітним беззнаковим цілим числом (`uint16_t`). Це означає, що жодна динамічна бібліотека Windows **не може експортувати більше ніж 65 535 символів**.

У великих C++ проєктах із глибоким використанням шаблонів (OpenCV, PyTorch, LLVM, Chromium) увімкнення `CMAKE_WINDOWS_EXPORT_ALL_SYMBOLS` миттєво генерує понад 100 000 експортованих спеціалізацій функцій, в результаті чого компонувальник `link.exe` падає з фатальною помилкою:

```text
fatal error LNK1189: library limit of 65535 objects exceeded
```

Єдиним надійним рішенням для великих бібліотек є відмова від автоматичного експорту на користь явних макросів API (таких як `MYLIB_API`), що відкривають назовні лише публічний інтерфейс системи.

Повні шаблони макросів експорту, конфігурацію CMake та зведення помилок компонування наведено в окремому довіднику [Довідкова матриця рантаймів, експорту та маніфестів Windows](root:sys-bsystem/windows-toolchain-nuances/api-windows-toolchain-matrix.md).

## Проблеми файлової системи: обмеження `MAX_PATH`, префікс `\\?\` та слеші

Операції з файлами та каталогами в середовищі Windows містять низку історичних пасток, здатних зламати виконання кросплатформенних скриптів збірки.

![Конвеєр обробки шляхів файлової системи та кодування тексту](/root/sys/sys-bsystem/windows-toolchain-nuances/img/path-encoding-pipeline.svg)

*Конвеєр обробки шляхів у Windows: зіставлення обмеження MAX_PATH з розширеним префіксом та робота з кодовими сторінками.*

### Обмеження `MAX_PATH` (260 символів)

У системному заголовку `minwindef.h` історично зафіксовано ліміт довжини шляху:

:::tabs
```c
/* Витяг із системного заголовка minwindef.h Windows SDK */
#define MAX_PATH 260
```
```cpp
// Типізована константа в сучасному коді C++
inline constexpr std::size_t kMaxPathLimit = 260;
```
:::

Це число складається з літери диска та двокрапки (`C:` — 2 символи), кореневого зворотного слеша (`\` — 1 символ), максимальної довжини шляху всередині диска (256 символів) та кінцевого нульового байта (`\0` — 1 символ):

```
2 + 1 + 256 + 1 = 260
```

Усі стандартні функції Win32 API для роботи з 8-бітними рядками (`CreateFileA`, `GetFullPathNameA`, `FindFirstFileA`), а також стандартні функції CRT (`fopen`, `stat`) історично виділяють фіксований стек-буфер довжиною `char szPath[MAX_PATH]`. 

Якщо дерево каталогу збірки (наприклад, у проєктах з глибокою ієрархією FetchContent, Conan або `node_modules`) має довжину 261 символ або більше:
- Системні виклики повертають помилку `ERROR_PATH_NOT_FOUND` (код 3) або `ERROR_FILENAME_EXCED_RANGE` (код 206);
- Компілятор `cl.exe` не може знайти заголовкові файли, що лежать за довгим шляхом;
- Інструменти архівування (наприклад, `cpack` чи `tar`) зазнають аварійної зупинки.

### Розширений префікс `\\?\` та режим Long Paths

Ядро операційної системи Windows NT на низькому рівні не має обмеження у 260 символів. Системні структури ядра `UNICODE_STRING` та системний виклик `NtCreateFile` підтримують шляхи довжиною до **32 767 символів**.

Щоб скористатися цим функціоналом через Win32 API, шлях повинен задовольняти двом умовам:
1. Передаватися у функцію з підтримкою широких символів Unicode (`CreateFileW`);
2. Мати спеціальний префікс розширеної довжини `\\?\` для локальних дисків (наприклад, `\\?\C:\Path\To\Deep\File.txt`) або `\\?\UNC\server\share\file.txt` для мережевих ресурсів.

Префікс `\\?\` повідомляє підсистемі Win32, що шлях є повністю абсолютним і канонічним: підсистема вимикає нормалізацію (перетворення `/` на `\`, обробку відносних переходів `.` та `..`) і передає рядок безпосередньо диспетчеру об'єктів ядра NT (`\??\C:\...`).

Починаючи з Windows 10 (версія 1607), обмеження можна зняти глобально:
- У системному реєстрі встановлюється ключ `LongPathsEnabled = 1` за шляхом `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem`;
- У маніфест програми додається тег `<longPathAware>true</longPathAware>`.

### Прямі (`/`) та зворотні (`\`) слеші

Поширена помилкова думка стверджує, що операційна система Windows підтримує виключно зворотні слеші (`\`). Насправді всі системні функції Win32 API (`CreateFile`, `LoadLibrary`, `SetCurrentDirectory`) та ядро NT чудово приймають прямі слеші (`/`) і автоматично нормалізують їх.

Конфлікт виникає виключно на рівні утиліт командного рядка:
- Командний інтерпретатор `cmd.exe` та багато класичних утиліт Windows (`copy`, `del`, `xcopy`) історично використовують прямий слеш `/` як символ введення прапорця команди (наприклад, `del /F /Q file.txt`). Якщо передати такій утиліті шлях `C:/build/file.txt`, вона сприйме `/build` як невідомий параметр команди.
- Компілятор `cl.exe` також використовує слеш для прапорців (`/O2`, `/I`). Якщо прапорець `/I` передається без пробілу перед шляхом (наприклад, `/IC:/headers`), компілятор може не розпізнати аргумент.

Системи збірки (CMake та Ninja) всередині графа залежностей нормалізують усі шляхи до прямого слеша (`/`), проте під час генерації команд для командного інтерпретатора або виклику генераторів коду розробник повинен конвертувати шляхи у рідний формат платформи за допомогою `cmake_path(NATIVE_PATH ...)` або `file(TO_NATIVE_PATH ...)`.

Нижче наведено практичну реалізацію функції безпечного відкриття файлів за довгими шляхами мовами C та C++.

:::tabs
```c
/* win32_longpath.c — безпечне відкриття файлу за довгим шляхом у C */
#include <windows.h>
#include <stdio.h>
#include <wchar.h>

HANDLE open_file_extended(const wchar_t* path, DWORD access_mode) {
    wchar_t extended_buffer[32768];
    const wchar_t* final_path = path;

    /* Якщо шлях довгий (> 240) і ще не має префікса \\?\ — додаємо його */
    if (wcslen(path) > 240 && wcsncmp(path, L"\\\\?\\", 4) != 0) {
        /* Обробка мережевих UNC шляхів: \\server\share -> \\?\UNC\server\share */
        if (wcsncmp(path, L"\\\\", 2) == 0) {
            swprintf(extended_buffer, 32768, L"\\\\?\\UNC\\%ls", path + 2);
        } else {
            swprintf(extended_buffer, 32768, L"\\\\?\\%ls", path);
        }
        final_path = extended_buffer;
    }

    return CreateFileW(
        final_path,
        access_mode,
        FILE_SHARE_READ,
        NULL,
        OPEN_EXISTING,
        FILE_ATTRIBUTE_NORMAL,
        NULL
    );
}
```
```cpp
// win32_longpath.cpp — безпечне відкриття файлу в C++ з std::filesystem
#include <windows.h>
#include <filesystem>
#include <iostream>
#include <string>

class UniqueHandle {
public:
    explicit UniqueHandle(HANDLE h = INVALID_HANDLE_VALUE) noexcept : handle_(h) {}
    ~UniqueHandle() noexcept {
        if (handle_ != INVALID_HANDLE_VALUE && handle_ != nullptr) {
            CloseHandle(handle_);
        }
    }

    UniqueHandle(const UniqueHandle&) = delete;
    UniqueHandle& operator=(const UniqueHandle&) = delete;

    UniqueHandle(UniqueHandle&& other) noexcept : handle_(other.handle_) {
        other.handle_ = INVALID_HANDLE_VALUE;
    }

    UniqueHandle& operator=(UniqueHandle&& other) noexcept {
        if (this != &other) {
            if (handle_ != INVALID_HANDLE_VALUE && handle_ != nullptr) {
                CloseHandle(handle_);
            }
            handle_ = other.handle_;
            other.handle_ = INVALID_HANDLE_VALUE;
        }
        return *this;
    }

    [[nodiscard]] HANDLE get() const noexcept { return handle_; }
    [[nodiscard]] bool is_valid() const noexcept { return handle_ != INVALID_HANDLE_VALUE; }

private:
    HANDLE handle_;
};

UniqueHandle open_file_modern(const std::filesystem::path& file_path, DWORD access_mode) {
    // std::filesystem під MSVC самостійно нормалізує та додає префікс \\?\ 
    // для абсолютних шляхів, якщо це необхідно
    const std::wstring native_path = file_path.wstring();

    HANDLE h = CreateFileW(
        native_path.c_str(),
        access_mode,
        FILE_SHARE_READ,
        nullptr,
        OPEN_EXISTING,
        FILE_ATTRIBUTE_NORMAL,
        nullptr
    );

    return UniqueHandle(h);
}
```

## Кодування символів та вивід у консоль: прапорець `/utf-8`

У той час як світ POSIX стандартизував представлення текстових рядків у форматі UTF-8 (де тип `char*` завжди містить байти UTF-8), в архітектурі Windows історично співіснують три несумісні моделі кодування тексту:

1. **Традиційні кодові сторінки ANSI (ACP):** 8-бітні кодування для однобайтових символів (Windows-1251 для кирилиці, Windows-1252 для Західної Європи). Усі функції Win32 з суфіксом `*A` (`CreateFileA`, `MessageBoxA`) очікують байти в поточній системній кодовій сторінці ANSI. Якщо файл має в імені літери з іншої мовної групи, функція `*A` не може його відкрити і замінює символи знаками питання (`?`).
2. **UTF-16LE (Широкі символи, Wide API):** Рідне внутрішнє кодування Windows NT, де кожен символ представляється типом `wchar_t` (16 бітів). Усі функції Win32 з суфіксом `*W` (`CreateFileW`) приймають рядки UTF-16LE і підтримують увесь простір символів Unicode.
3. **Кодові сторінки OEM (OCP):** Спеціальні застарілі кодування для консолі MS-DOS (CP866 для кирилиці, CP437 для США), через які стандартний вивід у консоль спотворює текст.

### Проблема інтерпретації сирцевих файлів та прапорець `/utf-8`

Коли компілятор MSVC зчитує вихідний файл (`.c` чи `.cpp`), збережений у кодуванні UTF-8 **без мітки порядку байтів (BOM)**, він за замовчуванням припускає, що файл закодовано в системній кодовій сторінці ANSI операційної системи розробника (наприклад, CP1251).

Якщо у файлі міститься рядковий літерал:

:::tabs
```c
const char* msg = "Привіт, світе!";
```
```cpp
constexpr std::string_view msg = "Привіт, світе!";
```
:::

Компілятор бере валідні байти UTF-8, помилково інтерпретує кожні два байти кирилиці як два окремих символи кодової сторінки Windows-1251, повторно перекодовує їх і записує у бінарну секцію констант `.rdata` пошкоджену послідовність байтів. Під час виконання програми на екран виводиться спотворений текст.

Для вирішення цієї проблеми MSVC надає прапорець `/utf-8`, який є комбінацією двох внутрішніх ключів:
- `/source-charset:utf-8`: наказує компілятору парсити текст вихідного файлу як UTF-8 (незалежно від наявності BOM);
- `/execution-charset:utf-8`: гарантує, що всі 8-бітні рядкові літерали (`const char*`) зберігаються у фінальному бінарному файлі у форматі UTF-8.

У CMake увімкнення цього прапорця для компілятора MSVC є критично важливим для будь-якого проєкту:

```cmake
if(MSVC)
    add_compile_options("/utf-8")
endif()
```

### Активна кодова сторінка UTF-8 у маніфесті процесу

Починаючи з Windows 10 (версія 1903), корпорація Microsoft додала можливість перевести підсистему Win32 у режим сумісності з UTF-8 без переписування кодової бази на `wchar_t`. 

Якщо у маніфест застосунку (`app.manifest`) додано налаштування `<activeCodePage>UTF-8</activeCodePage>`, операційна система змінює активну кодову сторінку процесу (Process ANSI Code Page) на `CP_UTF8` (65001). У результаті:
- Усі системні виклики з суфіксом `*A` (`CreateFileA`, `GetEnvironmentVariableA`, `LoadLibraryA`) починають сприймати 8-бітні рядки як повноцінний UTF-8;
- Стандартні функції C та C++ (`fopen`, `std::ifstream`, `std::filesystem::path`) можуть безпосередньо відкривати файли з будь-якими символами Unicode без використання проміжних конвертацій у `wchar_t`.

### Вивід у консоль та `SetConsoleOutputCP`

Навіть якщо застосунок скомпільовано з прапорцем `/utf-8`, а рядки сформовано коректно, вивід у стандартний потік термінала `stdout` через `printf` або `std::cout` за замовчуванням призведе до появи «кракозябр». Причина полягає в тому, що буфер виводу консолі Windows (`conhost.exe`) очікує дані у кодовій сторінці OEM.

Щоб налаштувати консоль на вивід Unicode, програма на початку виконання повинна викликати системні функції конфігурації сторінок:

:::tabs
```c
SetConsoleOutputCP(CP_UTF8);
SetConsoleCP(CP_UTF8);
```
```cpp
// Налаштування сторінки виводу через системний API в C++
SetConsoleOutputCP(CP_UTF8);
SetConsoleCP(CP_UTF8);
```
:::

Нижче наведено демонстраційний приклад коректної ініціалізації та виводу повідомлень різними мовами під Windows.

:::tabs
```c
/* utf8_demo.c — коректний вивід UTF-8 у консоль Windows мовою C */
#include <windows.h>
#include <stdio.h>

int main(void) {
    UINT old_cp = GetConsoleOutputCP();

    /* Встановлюємо активну сторінку виводу консолі в UTF-8 (65001) */
    SetConsoleOutputCP(CP_UTF8);

    /* Рядок скомпільовано з прапорцем /utf-8 */
    printf("Український текст: Вітання зі світу системної збірки!\n");
    printf("Спеціальні символи Unicode: ⚡ 🚀 🔧 [OK]\n");

    /* Відновлюємо початкову сторінку перед завершенням */
    SetConsoleOutputCP(old_cp);
    return 0;
}
```
```cpp
// utf8_demo.cpp — коректний вивід UTF-8 у консоль Windows мовою C++
#include <windows.h>
#include <iostream>
#include <string_view>

class ScopedConsoleEncoding {
public:
    explicit ScopedConsoleEncoding(UINT target_cp = CP_UTF8) noexcept
        : previous_cp_(GetConsoleOutputCP()) {
        SetConsoleOutputCP(target_cp);
    }

    ~ScopedConsoleEncoding() noexcept {
        SetConsoleOutputCP(previous_cp_);
    }

    ScopedConsoleEncoding(const ScopedConsoleEncoding&) = delete;
    ScopedConsoleEncoding& operator=(const ScopedConsoleEncoding&) = delete;

private:
    UINT previous_cp_;
};

int main() {
    const ScopedConsoleEncoding encoding_guard;

    constexpr std::string_view message = "Український текст: Вітання зі світу системної збірки!";
    constexpr std::string_view symbols = "Спеціальні символи Unicode: ⚡ 🚀 🔧 [OK]";

    std::cout << message << "\n" << symbols << std::endl;
    return 0;
}
```

## Зведення стратегій побудови міжплатформенної збірки

Надійна інженерна конфігурація збірки під Windows вимагає систематичного застосування таких правил:

1. **Єдиний рантайм для всього графа залежностей:** Усі статичні бібліотеки, динамічні модулі та виконувані файли повинні збиратися з однаковою моделлю рантайму (стандартно — динамічний `MultiThreaded$<$<CONFIG:Debug>:Debug>DLL`). Керування здійснюється через властивість CMake `CMAKE_MSVC_RUNTIME_LIBRARY`.
2. **Ізоляція меж динамічної пам'яті:** Будь-який ресурс (пам'ять, файловий дескриптор, сокет), виділений усередині DLL, має звільнятися функцією тієї самої DLL (наприклад, парні виклики `create_context()` / `destroy_context()`), або передаватися виключно через системні алокатори Win32 (`CoTaskMemAlloc` / `CoTaskMemFree`).
3. **Дисциплінований експорт символів:** Застосування явних макросів `MYLIB_API` з атрибутами `__declspec(dllexport)` та `__declspec(dllimport)` замість безконтрольного використання `CMAKE_WINDOWS_EXPORT_ALL_SYMBOLS`, що запобігає переповненню таблиці EAT понад 65 535 символів.
4. **Уніфікація кодування:** Обов'язкове встановлення прапорця `/utf-8` у налаштуваннях компілятора MSVC та підключення маніфесту застосунку з `<activeCodePage>UTF-8</activeCodePage>` та `<longPathAware>true</longPathAware>`.
