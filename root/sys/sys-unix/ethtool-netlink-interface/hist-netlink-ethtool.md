# 📜 Історія та еволюція інтерфейсів налаштування мережі в Linux

Перехід від перших мережевих карток 10BASE-T 1990-х років до сучасних оптичних трансиверів 400 GbE та 800 GbE виявив фундаментальні обмеження класичного системного виклику `ioctl(SIOCETHTOOL)`. Фіксована двійкова структура C-пакетів та синхронна блокуюча модель `ioctl` виявилися неспроможними масштабуватися під сотні нових режимів швидкостей, динамічні бітові маски та синхронне сповіщення багатьох процесів, що зрештою змусило ядро Linux перейти на гнучкий розширюваний протокол на базі Generic Netlink.

## 1. Епоха 1990-х: Системні виклики `ioctl` та хаос `SIOCDEVPRIVATE`

У початковий період розвитку ядра Linux (версії 1.x та 2.0, 1991–1996 роки) не існувало уніфікованого стандарту для керування апільними параметрами мережевих карт — такими як швидкість зв'язку, режим дуплексу, автоузгодження (Autonegotiation) чи перемикання між фізичними роз'ємами BNC (коаксіал), AUI та RJ-45 (кручена пара).

Кожен розробник драйвера мережевої карти створював власні приватні команди системного виклику `ioctl` (Input/Output Control), використовуючи виділений діапазон констант `SIOCDEVPRIVATE` (від `SIOCDEVPRIVATE` до `SIOCDEVPRIVATE + 15`).

Це призвело до ситуації, коли для кожної серії мережевих карт потрібна була власна спеціалізована утиліта налаштування з простору користувача. Утиліта для популярних карт 3Com 3c59x (`vortex-diag`) не мала жодної сумісності з картами Realtek RTL8139 (`rtl8139-diag`), Intel e100 чи DEC Tulip (`tulip-diag`). Системні адміністратори того часу були змушені тримати в операційній системі десяток розрізнених бінарних утиліт з різними ключами командного рядка.

У 1998–1999 роках провідні розробники мережевої підсистеми ядра Linux — Девід Міллер (David Miller), Олексій Кузнецов (Alexey Kuznetsov) та Джефф Гарзік (Jeff Garzik) — запропонували виробити єдиний уніфікований стандарт для системного адміністрування мережевого обладнання. 

Результатом їхньої співпраці стала поява консольної утиліти `ethtool` та відповідного системного виклику ядра `ioctl(fd, SIOCETHTOOL, &ifr)`.

Для передачі даних було створено єдину універсальну структуру `struct ethtool_cmd`. Код утиліти з простору користувача відкривав довільний мережевий сокет (наприклад, `AF_INET` або `AF_UNIX`), заповнював ім'я інтерфейсу у структурі `ifreq` та передавав вказівник `ifr_data` на структуру `ethtool_cmd`. Ядро Linux перехоплювало команду `SIOCETHTOOL` у функції `dev_ioctl()`, перевіряло привілеї процесів (`CAP_NET_ADMIN`) і викликало відповідний метод із зареєстрованого драйвером реєстру `ethtool_ops`.

## 2. Криза 40G/100G Ethernet та крах `struct ethtool_cmd`

Інтерфейс `ioctl(SIOCETHTOOL)` успішно задовольняв потреби операційної системи майже два десятиліття. Проте в його основі лежало фундаментальне інженерне обмеження C-структур із фіксованим двійковим розміром (Binary Layout ABI).

У початковій структурі `struct ethtool_cmd` підтримувані режими швидкості та дуплексу описувалися 32-бітовими масками прапорців `supported` та `advertising`:

```text
struct ethtool_cmd {
    __u32   cmd;
    __u32   supported;   /* Бітова маска supported modes */
    __u32   advertising; /* Бітова маска advertised modes */
    __u16   speed;       /* Низькі 16 біт швидкості */
    __u8    duplex;
    __u8    port;
    /* ... */
};
```

Кожен новий фізичний режим зв'язку (10BASE-T Half, 10BASE-T Full, 100BASE-TX Half, 1000BASE-T Full, 10GBASE-T) займав один біт у цій 32-бітній масці. На початку 2010-х років, із появою стандартів IEEE 802.3ba (40 GbE та 100 GbE), а згодом 25 GbE, 50 GbE, 200 GbE та 400 GbE із різними типами фізичних кодувань (KR4, CR4, SR4, LR4, ER4, DR4, FR4), кількість потрібних прапорців перевищила 32 біти.

Розробники спробували застосувати тимчасовий "кишеньковий" хак: у структурі знайшли резервні старші поля і додали `speed_hi` (старші 16 бітів для розширення діапазону швидкості до 4 Гбіт/с), але маски бітів `supported` та `advertising` розширити всередині фіксованої структури без зламу двійкової сумісності ABI було неможливо.

У 2016 році в ядрі Linux 4.6 розробники ввели нові структури `ethtool_link_settings` та `ethtool_ksettings`, де бітові маски стали динамічними масивами 32-бітних слів `__u32 link_mode_masks[]`. Проте передача таких масивів змінного розміру через `ioctl` вимагала складного двокрокового виклику:
1. Перший виклик `ioctl` із від'ємним розміром масиву, щоб дізнатися від ядра необхідний розмір буфера.
2. Виділення пам'яті в просторі користувача.
3. Другий виклик `ioctl` для безпосереднього зчитування даних.

Це суттєво ускладнило код утиліти `ethtool` та драйверів і не вирішувало інших критичних системних проблем `ioctl`.

## 3. Чому `sysfs` не стала альтернативою

На початку 2000-х років у ядрі Linux з'явилася псевдофайлова система `sysfs` (`/sys/class/net/<iface>/`), яка мала стати універсальним інтерфейсом для експорту параметрів обладнання у вигляді текстових файлів. Для багатьох підсистем (наприклад, блокових пристроїв чи систем охолодження) `sysfs` виявилася зручним рішенням.

Однак спроба перенести керування мережевими адаптерами в `sysfs` зазнала невдачі з кількох причин:

1. **Відсутність атомарності**: Налаштування мережевого лінку часто вимагає одночасного встановлення кількох взаємопов'язаних параметрів (наприклад, швидкості 100 Gbps, режиму автоузгодження `autoneg off` та конкретного типу FEC `rs`). У `sysfs` кожен параметр записується окремим системним викликом `write()` у свій файл. Ядро бачить це як серію ізольованих дій, що спричиняє проміжні нестабільні стани пристрою.
2. **Накладні витрати конвертації**: Перетворення двійкових бітових карт та чисел у текстовий формат ASCII й зворотний парсинг у ядрі на кожну дію створювало суттєві накладні витрати ресурсів CPU на системах із тисячами віртуальних інтерфейсів (VLAN, macvlan, VXLAN).
3. **Неможливість асинхронних сповіщень**: Файли `sysfs` не підтримують зручну підписку на події для багатьох процесів. Хоча механізм `poll()`/`epoll()` над атрибутами `sysfs` існує через `sysfs_notify()`, він не передає структуру змін (подія лише повідомляє, що файл змінився, змушуючи перечитати його повністю).

## 4. Поява Generic Netlink ethtool (Linux 5.6)

У 2018 році розробник ядра Міхал Кубечек (Michal Kubecek) із компанії SUSE запропонував фундаментальну реформацію ethtool API. Замість чергової спроби адаптувати `ioctl` або `sysfs`, було прийнято рішення створити повноцінне сімейство протоколу **Generic Netlink**.

Протокол Netlink до того часу вже довів свою ефективність у підсистемах `rtnetlink` (керування IP-адресами, маршрутами та інтерфейсами через `iproute2`), `nl80211` (конфігурація Wi-Fi) та `nfnetlink` (Netfilter/nftables).

Новий ethtool Netlink API було офіційно прийнято до основного дерева ядра Linux у версії 5.6 у березні 2020 року. Він впровадив:

* **Кодування NLA (Netlink Attributes)**: Кожен параметр передається у форматі TLV (Type-Length-Value). Це гарантує абсолютну зворотну й пряму сумісність: ядро й утиліти з простору користувача можуть додавати нові поля, не ламаючи старих бінарних файлів.
* **Багатоадресні групи (Multicast Notifications)**: Будь-який процес у просторі користувача може відкрити сокет Netlink, підписатися на групу `ETHTOOL_MCGRP_MONITOR` і миттєво отримувати сповіщення про зміну стану лінку, відключення кабелю чи апаратні помилки без журналювання polling.
* **Механізм Extack (Extended Acknowledgement)**: Ядро отримало можливість повертати текстові рядки пояснення помилки (наприклад, `"Requested speed 100000 is not supported by attached SFP module"`), звільняючи розробників від безнадійних EINVAL без контексту.

Перехід на Generic Netlink завершив тридцятирічний еволюційний шлях від розрізнених макросів `SIOCDEVPRIVATE` до стандартизованого, подійно-орієнтованого та гнучкого мережевого API сучасного ядра Linux.
