# 📋 Режим файлу: константи, підписи, коди помилок

Довідка за клавіатурою: як розкладено `st_mode` і як звуться всі його біти, за якою граматикою їх пише `chmod(1)` і читає `ls -l`, які системні виклики їх міняють — і котрий `errno` за яких саме обставин.

## `st_mode`: тип і дозволи в одному числі

Усе оголошено в `<sys/stat.h>`.

```c
#include <sys/stat.h>

struct stat st;
stat("/etc/passwd", &st);

st.st_mode & S_IFMT     /* поле типу — порівнювати, а не тестувати по біту */
st.st_mode & 07777      /* дванадцять бітів дозволів                       */
st.st_mode & 0777       /* лише дев'ятка класів, без спеціальних           */
```

Поле типу — не бітова маска: значення в ньому перекриваються бітами (`S_IFREG` — `0100000`, `S_IFBLK` — `0060000`), тому перевіряють рівність цілого поля, а не окремий біт. Для цього й існують макроси.

| стала | вісімково | об'єкт | макрос | літера `ls` |
|---|---|---|---|---|
| `S_IFMT` | `0170000` | маска самого поля типу | — | — |
| `S_IFSOCK` | `0140000` | сокет | `S_ISSOCK(m)` | `s` |
| `S_IFLNK` | `0120000` | символьне посилання | `S_ISLNK(m)` | `l` |
| `S_IFREG` | `0100000` | звичайний файл | `S_ISREG(m)` | `-` |
| `S_IFBLK` | `0060000` | блоковий пристрій | `S_ISBLK(m)` | `b` |
| `S_IFDIR` | `0040000` | каталог | `S_ISDIR(m)` | `d` |
| `S_IFCHR` | `0020000` | символьний пристрій | `S_ISCHR(m)` | `c` |
| `S_IFIFO` | `0010000` | канал FIFO | `S_ISFIFO(m)` | `p` |

Тип ставиться при створенні й жодним викликом не міняється. Той самий набір констант і макросів чинний і для поля `stx_mode` у [`statx`](topic:sys-unix/statx-mask-and-unknown-values).

## Дванадцять бітів дозволів

| стала | вісімково | що означає |
|---|---|---|
| `S_ISUID` | `04000` | set-user-ID: `exec` бере дійсний UID із власника файлу |
| `S_ISGID` | `02000` | на програмі — set-group-ID; на каталозі — нові записи всередині успадковують групу теки; на файлі **без** `S_IXGRP` — ознака обов'язкового [блокування](topic:sys-unix/file-locking) |
| `S_ISVTX` | `01000` | sticky: у каталозі прибрати чи перейменувати запис може лише його власник, власник теки або `CAP_FOWNER` |
| `S_IRWXU` | `00700` | уся трійка власника |
| `S_IRUSR` | `00400` | читання власником |
| `S_IWUSR` | `00200` | запис власником |
| `S_IXUSR` | `00100` | виконання (для каталогу — пошук) власником |
| `S_IRWXG` | `00070` | уся трійка групи |
| `S_IRGRP` | `00040` | читання групою |
| `S_IWGRP` | `00020` | запис групою |
| `S_IXGRP` | `00010` | виконання групою |
| `S_IRWXO` | `00007` | уся трійка решти |
| `S_IROTH` | `00004` | читання рештою |
| `S_IWOTH` | `00002` | запис рештою |
| `S_IXOTH` | `00001` | виконання рештою |

Три сукупності `S_IRWX*` не додають нічого нового — це побітове АБО своєї трійки, і тримають їх лише щоб не писати `S_IRUSR|S_IWUSR|S_IXUSR` руками.

## Граматика `chmod(1)`

```
chmod  <вісімкове число>            повністю задає всі 12 бітів
chmod  [ugoa…][-+=][perms…][,…]     правка окремих бітів

  u власник · g група · o решта · a усі три класи
  + додати · − зняти · = зробити рівно таким
  perms:  r w x · X · s · t · АБО рівно одна літера з u g o
```

Дві пастки заховані саме в граматиці. Перша: **числовий запис задає всі дванадцять бітів**, і пропущений старший розряд означає нуль, тож `chmod 755` мовчки гасить `setuid`, `setgid` і `sticky`. Друга: якщо не написати жодної з `ugoa`, діє `a`, **але біти, зведені в `umask`, не чіпаються** — через це `chmod +x` і `chmod a+x` дають різний результат на тій самій машині.

| команда | було | стало | що саме робить |
|---|---|---|---|
| `chmod 640 f` | `0644` | `0640` | задати числом усі дванадцять бітів одразу |
| `chmod u=rw,g=r,o= f` | `0644` | `0640` | те саме символьно, класами |
| `chmod a+x f` | `0644` | `0755` | додати `x` усім трьом класам |
| `chmod +x f` | `0644` | `0755` при `umask 022`, `0744` при `umask 077` | те саме, але біти, зведені в маску, не чіпаються |
| `chmod g=u f` | `0644` | `0664` | скопіювати трійку власника в трійку групи |
| `chmod u+s prog` | `0755` | `04755` | поставити set-user-ID, решти не торкаючись |
| `chmod g+s dir` | `0755` | `02755` | нові записи в теці успадковуватимуть її групу |
| `chmod +t /tmp/shared` | `0777` | `01777` | sticky на спільну теку |
| `chmod -R a+rX dir` | різне | різне | `X` дає `x` лише каталогам і тому, у кого `x` уже десь стоїть |

`X` — це те, заради чого рекурсивний обхід узагалі можна робити однією командою: `a+x` на дереві зробить виконуваним кожен текстовий файл, а `a+X` — лише каталоги та вже виконувані файли.

Оператор `=` змітає всі неназвані біти в межах названих класів — з одним винятком: на **каталозі** він лишає `set-user-ID` і `set-group-ID`, якщо їх не назвали явно. Числовий запис такої поблажки не має.

`chmod` завжди йде за символьним посиланням і міняє режим того, на що воно вказує; режиму самого [посилання](topic:sys-unix/hard-and-symbolic-links) у Linux не існує як чогось значущого.

## Розшифрування рядка `ls -l`

Десять знаків читаються позиційно: перший — тип із таблиці вище, далі три трійки `rwx` у порядку власник → група → решта.

| позиція | знак | що означає |
|---|---|---|
| 1 | `- d l c b p s` | тип об'єкта |
| 2, 5, 8 | `r` / `-` | читання є / немає |
| 3, 6, 9 | `w` / `-` | запис є / немає |
| 4 | `x` `s` `S` `-` | `x` — виконання · `s` — `setuid` **і** `x` · `S` — `setuid` **без** `x` · `-` — нічого |
| 7 | `x` `s` `S` `-` | те саме для `setgid` |
| 10 | `x` `t` `T` `-` | `t` — `sticky` **і** `x` · `T` — `sticky` **без** `x` |
| 11-й, коли є | `+` або `.` | `+` — на файлі є [ACL](topic:sys-unix/acl-and-xattr) · `.` — є мітка [SELinux](topic:sys-unix/mac-selinux-apparmor) |

Правило одне на всі три спеціальні біти: **велика літера означає, що спеціальний біт стоїть, а `x` під ним немає**. Тому `chmod 4644 prog` покаже `-rwSr--r--` — `setuid` проставлено, але запустити файл не може ніхто, отже, біт не спрацює ніколи. Це не помилка `ls`, а точний друк того, що лежить в inode.

## Змінити режим

```c
#include <sys/stat.h>
int chmod(const char *path, mode_t mode);
int fchmod(int fd, mode_t mode);

#include <fcntl.h>          /* AT_* */
#include <sys/stat.h>
int fchmodat(int dirfd, const char *path, mode_t mode, int flags);

#include <sys/syscall.h>    /* обгортки в glibc немає — лише через syscall() */
int syscall(SYS_fchmodat2, int dirfd, const char *path,
            mode_t mode, unsigned int flags);
```

`fchmodat` — з базового пакету [родини `*at`](topic:sys-unix/at-family-syscalls) (Linux 2.6.16, glibc 2.4). Аргумент `flags` у нього стоїть за POSIX, але **старий системний виклик його не мав узагалі**: обгортка glibc мусила або відмовляти на `AT_SYMLINK_NOFOLLOW`, або обходити його через `/proc`. Виклик `fchmodat2` (Linux 6.6) додав справжнє поле прапорців; від glibc 2.39 звичайний `fchmodat()` кличе саме його, коли ядро вміє.

Прапорців два. `AT_EMPTY_PATH` дозволяє передати порожній рядок і працювати з тим, що тримає сам `dirfd`. `AT_SYMLINK_NOFOLLOW` на справжньому символьному посиланні повертає `EOPNOTSUPP` — і в цьому вся його користь: цінність не в тому, щоб змінити режим посилання (це безглуздо), а в тому, щоб **відмовитися**, якщо на місці очікуваного файлу раптом опинилося посилання.

Ще одна тиха деталь: непривілейований процес (без `CAP_FSETID`), змінюючи режим файлу, чия група не входить до його груп, втрачає біт `S_ISGID` — той гасне мовчки, помилки не буде.

## Змінити власника

```c
#include <unistd.h>
int chown(const char *path, uid_t owner, gid_t group);
int fchown(int fd, uid_t owner, gid_t group);
int lchown(const char *path, uid_t owner, gid_t group);   /* не йде за посиланням */

#include <fcntl.h>
#include <unistd.h>
int fchownat(int dirfd, const char *path, uid_t owner, gid_t group, int flags);
```

`-1` на місці `owner` чи `group` означає «це поле не міняти». Власника може змінити лише процес із `CAP_CHOWN`; групу власник міняє сам, але тільки на ту, до якої [входить](topic:sys-unix/uid-gid-identity-model).

Коли непривілейований процес міняє власника або групу **виконуваного** файлу, ядро гасить `S_ISUID` і `S_ISGID` — інакше зміна власника мовчки перенаправила б усі майбутні [підвищення прав](topic:sys-unix/setuid-and-privilege). Виняток рівно один: якщо `S_IXGRP` не стоїть, `S_ISGID` там означає не set-group-ID, а обов'язкове блокування, і `chown` його не чіпає.

`fchownat` бере `AT_SYMLINK_NOFOLLOW` (поводитися як `lchown`) та `AT_EMPTY_PATH` (Linux 2.6.39).

## Спитати, чи можна

```c
#include <unistd.h>
int access(const char *path, int mode);          /* РЕАЛЬНІ UID/GID */

#include <fcntl.h>
#include <unistd.h>
int faccessat(int dirfd, const char *path, int mode, int flags);

#include <sys/syscall.h>
int syscall(SYS_faccessat2, int dirfd, const char *path, int mode, int flags);
```

`mode` — це `F_OK` (лише існування) або побітове АБО з `R_OK`, `W_OK`, `X_OK`. Прапорці: `AT_EACCESS` — перевіряти **дійсними** ідентифікаторами замість реальних; `AT_SYMLINK_NOFOLLOW` — питати про саме посилання.

Історія тут така сама, як у `fchmodat`: до glibc 2.32 обгортка `faccessat()` вдавала прапорці, комбінуючи виклик зі `fstatat()`, і та підробка не бачила ACL — тобто на файлових системах зі списками доступу відповідала неправду. Справжній `faccessat2` з полем прапорців з'явився в Linux 5.8, і від glibc 2.33 обгортка кличе його.

Відповідь усіх трьох застаріває тієї ж миті, коли повертається: між нею і дією файл встигає стати іншим ([гонка перевірки й використання](topic:sf-security/toctou-race)).

## Маска новоствореного

```c
#include <sys/stat.h>
mode_t umask(mode_t mask);      /* не може зазнати невдачі */
```

Виклик ставить нову маску, повертає стару й бере з аргументу лише `mask & 0777`. Прочитати поточне значення, не зачепивши його, окремим викликом не можна — доводиться ставити двічі (`mode_t m = umask(0); umask(m);`) або читати рядок `Umask` у `/proc/self/status`.

```
режим_створеного = режим_із_виклику & ~umask

0666 & ~0022 = 0644     звичайний файл: більшість програм просять 0666
0777 & ~0022 = 0755     каталог: mkdir просить 0777
0666 & ~0077 = 0600     та сама програма при umask 077
```

Якщо в батьківському каталозі є типовий ACL, маска не діє взагалі: біти беруться з успадкованого списку. Звідки процес дістає початкове значення маски — окрема тема: [`umask` і типові права новоствореного](topic:sys-unix/umask-and-defaults).

## Коли який `errno`

| код | обставина |
|---|---|
| `EACCES` | немає права пошуку (`x`) на якомусь складнику шляху; для `access`/`faccessat` — ще й коли не дозволено саме запитану дію |
| `EPERM` | режим міняє не власник і без `CAP_FOWNER`; власника — без `CAP_CHOWN`; або на inode стоїть [`immutable` чи `append-only`](topic:sys-unix/inode-flags-chattr) |
| `EROFS` | об'єкт лежить на файловій системі, змонтованій лише для читання |
| `ELOOP` | при розборі шляху трапилося забагато символьних посилань |
| `ENOTDIR` | складник шляху не каталог; для `*at` — шлях відносний, а `dirfd` указує не на каталог |
| `ENAMETOOLONG` | шлях довший за межу ядра |
| `ENOENT` | складника шляху немає або посилання висить у порожнечу |
| `EBADF` | `fd` чи `dirfd` не є відкритим дескриптором (для `*at` — і не `AT_FDCWD`) |
| `EINVAL` | недопустимий біт у `flags`; для `access` — безглузде `mode` |
| `EOPNOTSUPP` | `AT_SYMLINK_NOFOLLOW` на справжньому символьному посиланні |
| `ETXTBSY` | `access(…, W_OK)` на файлі, який зараз виконують |
| `EFAULT` · `EIO` · `ENOMEM` | вказівник поза адресним простором · збій носія · ядру бракує пам'яті |

Два коди відмови розділені не випадково. `EACCES` — це вирок дев'ятки бітів: вас не пустили пройти чи прочитати. `EPERM` — вирок власності та привілею: ви дійшли до об'єкта, але не маєте права саме на цю дію саме над ним.

> 🔧 **Навіщо це.** Розрізнення `EACCES` і `EPERM` економить найбільше часу при розборі відмови. `EPERM` від `chmod` одразу закриває половину гіпотез: біти на шляху цілі, і питання в тому, хто власник, чи є [`CAP_FOWNER`](topic:sys-unix/capabilities) і чи не позначено inode як незмінний. `EACCES` — навпаки: дивитися треба не на сам файл, а на кожен каталог у шляху, бо повідомлення `Permission denied` однакове й тоді, коли бракує права на файл, і тоді, коли `x` забрали з теки посередині.
