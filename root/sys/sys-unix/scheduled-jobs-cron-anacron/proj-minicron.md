# ⚙️ Реалізація власного планувальника: синхронізація хвилини, бітові маски та керування процесами

Розробка системного планувальника завдань вимагає розв'язання комплексу низькорівневих задач системного програмування в Unix: точної прив'язки до астрономічного часу без накопичення фазового зсуву, ефективної перевірки розкладів за константний час `O(1)`, безпечної ізоляції процесів-нащадків, контролю конкурентності під високим навантаженням та асинхронного збору статусів завершення без блокування головного потоку.

Класичний наївний підхід — нескінченний цикл із фіксованим викликом `sleep(60)` — у виробничих умовах швидко призводить до деградації: накладні витрати системних викликів [fork](root:sys-unix/fork-semantics) та перевірки умов зсувають момент пробудження відносно початку хвилини, через що періодично пропускаються запуски завдань. Крім того, прямий синтаксичний аналіз текстових рядків формату crontab щохвилини створював би невиправдані накладні витрати на парсинг та динамічне виділення пам'яті.

Нижче наведено повну реалізацію мінімального планувальника `minicron` мовами C та C++, що вирішує ці задачі за допомогою бітових масок, прецизійної синхронізації часу, коректної семантики POSIX для днів місяця й тижня та надійного конвеєра створення дочірніх процесів.

## 1. Архітектура та синтаксичний аналіз: представлення розкладів через бітові маски

Усі п'ять часових полів класичного розкладу crontab мають невеликі дискретні діапазони:
- **Хвилини:** від 0 до 59 (60 дискретних значень);
- **Години:** від 0 до 23 (24 дискретних значення);
- **День місяця (DOM, Day of Month):** від 1 до 31 (31 значення);
- **Місяць:** від 1 до 12 (12 значень);
- **День тижня (DOW, Day of Week):** від 0 до 7, де 0 і 7 позначають неділю (8 значень).

Замість збереження текстових конфігураційних рядків та їхнього повторного розбору на кожній ітерації таймера, `minicron` виконує синтаксичний аналіз один раз під час реєстрації завдання й транслює допустимі значення кожного поля у бітову маску (англ. *bitmask*).

```
Поле хвилин (0..59) -> 64-бітне ціле число (unsigned long long)
Біт k = 1  <=>  хвилина k дозволена розкладом
Біт k = 0  <=>  хвилина k заборонена розкладом

Приклад для розкладу "*/15" (хвилини 0, 15, 30, 45):
Біти: ... 001000000000000010000000000000010000000000000001₂
          └─ хв 45        └─ хв 30        └─ хв 15        └─ хв 0
```

Оскільки 64-бітне беззнакове ціле число вміщує до 64 незалежних прапорців, одного числа `unsigned long long` у C або спеціалізованого класу `std::bitset<N>` у C++ достатньо для представлення будь-якого поля розкладу.

### Структури даних та компонування пам'яті

У реалізації мовою C структура завдання `cron_job_t` скомпонована так, щоб мінімізувати накладні витрати пам'яті та забезпечити локальність даних у кеші процесора:

:::tabs
@tab C
```c
typedef struct {
    unsigned long long minute_mask;   /* 0-59 (8 байтів, 64 біти) */
    unsigned int hour_mask;           /* 0-23 (4 байти, 32 біти)  */
    unsigned int dom_mask;            /* 1-31 (4 байти, біти 1..31) */
    unsigned int month_mask;          /* 1-12 (4 байти, біти 1..12) */
    unsigned int dow_mask;            /* 0-7  (4 байти, біти 0..7)  */
    int dom_is_wildcard;              /* прапорець зірочки DOM (4 байти) */
    int dow_is_wildcard;              /* прапорець зірочки DOW (4 байти) */
    char command[MAX_CMD_LEN];        /* вбудований фіксований буфер команди (256 байтів) */
} cron_job_t;
```
@tab C++
```cpp
struct CronJob {
    std::bitset<60> minute_mask;   // 0..59 (60 бітів)
    std::bitset<24> hour_mask;     // 0..23 (24 біти)
    std::bitset<32> dom_mask;      // 1..31 (32 біти)
    std::bitset<13> month_mask;    // 1..12 (13 бітів)
    std::bitset<8>  dow_mask;      // 0..7 (8 бітів)
    bool dom_is_wildcard{false};
    bool dow_is_wildcard{false};
    std::string command;
};
```
:::

Статичний масив `static cron_job_t g_jobs[MAX_JOBS]` виділяється у сегменті BSS під час завантаження програми. Це усуває потребу у динамічних алокаціях (`malloc`/`free`) у гарячому циклі планувальника та запобігає фрагментації купи.

У реалізації C++ структура `CronJob` використовує точні розміри бітових масок через `std::bitset<N>`:
- `std::bitset<60> minute_mask` — рівно 60 бітів;
- `std::bitset<24> hour_mask` — 24 біти;
- `std::bitset<32> dom_mask` — 32 біти (нульовий біт не використовується, індексація 1..31);
- `std::bitset<13> month_mask` — 13 бітів (індексація 1..12);
- `std::bitset<8> dow_mask` — 8 бітів (індексація 0..7).

Динамічний вектор `std::vector<CronJob>` у класі `Scheduler` інкапсулює керування колекцією, а рядки команд зберігаються у стандартних контейнерах `std::string`.

### Алгоритм роботи парсера полів

Функція `parse_field` приймає текстовий фрагмент поля, допустимий числовий діапазон `[min_val, max_val]` та повертає згенеровану бітову маску. Парсер послідовно розпізнає чотири синтаксичні конструкції:

1. **Зірочка (`*`):** встановлює прапорець `is_wildcard = 1` та виставляє всі біти від `min_val` до `max_val` включно:
:::tabs
@tab C
```c
for (int i = min_val; i <= max_val; ++i) {
    *mask_out |= (1ULL << i);
}
```
@tab C++
```cpp
for (int i = min_val; i <= max_val; ++i) {
    mask.set(i);
}
```
:::

2. **Кроки зірочки (`*/step`):** зчитує цілочисельний крок після символу `/`, перевіряє умову `step > 0` та ітерує діапазон із заданим приростом `i += step`, виставляючи відповідні біти. Від'ємний або нульовий крок вважається синтаксичною помилкою.

3. **Діапазони чисел (`start-end`):** знаходить роздільник `-`, валідує умову `min_val <= start <= end <= max_val` та виставляє неперервний діапазон бітів від `start` до `end`. Якщо `start > end`, парсер відхиляє розклад як помилковий.

4. **Списки дискретних значень (`val1,val2,...`):** розділяє рядок за комою за допомогою токенайзера (`strtok` у C або `std::stringstream` у C++), перевіряє межі кожного числа та встановлює відповідний біт `(1ULL << val)`.

> 🔧 **Навіщо це.**
> Валідація числових меж безпосередньо під час розбору конфігурації унеможливлює виконання небезпечних побітових зсувів на від'ємну або надвелику кількість бітів (`1ULL << 65`), що є невизначеною поведінкою (undefined behavior) у мовах C та C++.

### Нормалізація неділі в стандарті POSIX

Стандарт POSIX допускає позначення неділі як цифрою `0`, так і цифрою `7`. Щоб усунути неоднозначність під час перевірки, функція додавання завдання `add_job` здійснює взаємну синхронізацію нульового та сьомого бітів у масці дня тижня:
:::tabs
@tab C
```c
if (dow_m & (1ULL << 7)) dow_m |= (1ULL << 0);
if (dow_m & (1ULL << 0)) dow_m |= (1ULL << 7);
```
@tab C++
```cpp
if (job.dow_mask.test(7)) job.dow_mask.set(0);
if (job.dow_mask.test(0)) job.dow_mask.set(7);
```
:::

Завдяки цьому перевірка поточного дня тижня через поле `tm_wday` структури `struct tm` (яке повертає значення від 0 до 6) коректно спрацьовує як для записів з цифрою `0`, так і для записів з цифрою `7`.

### Кон'юнкція та диз'юнкція полів часу (правило DOM || DOW)

Перевірка збігу поточного часу із завданням виконується за `O(1)` бітовими операціями перевірки біта:
:::tabs
@tab C
```c
int minute_match = (j->minute_mask & (1ULL << t->tm_min)) ? 1 : 0;
```
@tab C++
```cpp
bool minute_match = job.minute_mask.test(t.tm_min);
```
:::

Хвилини, години та місяці завжди об'єднуються логічним «І» (кон'юнкція, від лат. *conjunctio* — зв'язок). Проте для дня місяця (DOM) та дня тижня (DOW) діє особливе історичне правило POSIX:
- Якщо **обидва поля обмежені** (жодне з них не було задано зірочкою `*`), вони об'єднуються через логічне «АБО» (диз'юнкція, від лат. *disjunctio* — розділення). Наприклад, вираз `0 12 13 * 5` виконується як щоп'ятниці, так і 13-го числа місяця.
- Якщо **хоча б одне з полів містить зірочку**, діє стандартна кон'юнкція («І»).

```
                ┌──────────────────────────────────────┐
                │ Обидва поля DOM та DOW обмежені?     │
                │ (!dom_is_wildcard && !dow_is_wildcard)│
                └──────────────────┬───────────────────┘
                                   │
                   ┌───────────────┴───────────────┐
                   │                               │
                  ТАК                              НІ
                   │                               │
                   ▼                               ▼
       ┌───────────────────────┐       ┌───────────────────────┐
       │   Логічне «АБО» (OR)  │       │    Логічне «І» (AND)  │
       │  dom_match || dow_match │     │  dom_match && dow_match │
       └───────────────────────┘       └───────────────────────┘
```

У функції `job_matches` ця логіка реалізована компактним виразом:

:::tabs
@tab C
```c
if (!j->dom_is_wildcard && !j->dow_is_wildcard) {
    return dom_match || dow_match;
}
return dom_match && dow_match;
```
@tab C++
```cpp
if (!job.dom_is_wildcard && !job.dow_is_wildcard) {
    return dom_match || dow_match;
}
return dom_match && dow_match;
```
:::

## 2. Головний цикл планувальника: синхронізація часу та розрахунок найближчої події

### Проблема накопичення фазового дрейфу

Якщо демон використовує фіксовану паузу `sleep(60)`, виникає дрейф фази опитування. Створення процесів через `fork()`, ітерація масивом завдань і робота з файловою системою вимагають часу процесора (від часток мілісекунди до кількох секунд під високим навантаженням).

```
Ітерація 0: старт 00:00.000 -> робота 0.010 с -> sleep(60) -> пробудження 01:00.010
Ітерація 1: старт 01:00.010 -> робота 0.015 с -> sleep(60) -> пробудження 02:00.025
...
Ітерація N: накопичений зсув перевищує 60 с -> повний пропуск астрономічної хвилини!
```

Щоб запобігти зсуву, `minicron` перед кожним засинанням зчитує системний час функцією `localtime_r`, визначає поточну секунду `tm_sec` і засинає на динамічно обчислений залишок хвилини:
:::tabs
@tab C
```c
int seconds_to_next_minute = 60 - tm_now.tm_sec;
if (seconds_to_next_minute > 0) {
    sleep((unsigned int)seconds_to_next_minute);
}
```
@tab C++
```cpp
int sleep_sec = 60 - tm_now.tm_sec;
if (sleep_sec > 0) {
    std::this_thread::sleep_for(std::chrono::seconds(sleep_sec));
}
```
:::

Такий розрахунок щохвилини прив'язує момент пробудження до астрономічної нульової секунди. Навіть якщо обробка попередньої ітерації затрималася на 5 секунд, демон засне на `60 - 5 = 55` секунд і прокинеться точно на початку наступної хвилини.

### Розрахунок часу наступного запуску (Next Trigger Calculation)

Похвилинне пробудження є простим у реалізації, проте на малопотужних серверах та вбудованих пристроях регулярні пробудження процесора кожні 60 секунд заважають переходу ядер у стани глибокого енергозбереження (C-states).

Промисловий планувальник може розраховувати абсолютний момент часу наступного запуску як мінімальний час серед усіх зареєстрованих завдань. Для кожного завдання алгоритм знаходить найближчу комбінацію `(min, hour, dom, mon, dow)`, для якої всі бітові маски повертають істину, виконуючи каскадний перенос одиниць від хвилин до років.

```
Алгоритм розрахунку найближчого спрацьовування:
1. Поточний час T = (Y, M, D, H, Min)
2. Для кожного завдання J у таблиці розкладів:
     Для кожного місяця від M до 12 (і далі наступного року):
       Якщо біт місяця встановлено у month_mask:
         Для кожного дня місяця D_cur у цьому місяці:
           Якщо D_cur відповідає правилу (DOM || DOW):
             Для кожної години H_cur від H до 23:
               Якщо біт години встановлено в hour_mask:
                 Для кожної хвилини Min_cur від Min до 59:
                   Якщо біт хвилини встановлено в minute_mask:
                     Фіксуємо знайдений час T_cand
                     Next_Trigger = min(Next_Trigger, T_cand)
3. Планувальник переходить у стан сну на інтервал (Next_Trigger - Now)
```

Після визначення мінімального часу планувальник переходить у стан сну рівно до настання цієї позначки за допомогою системного таймера ядра.

### Таймери ядра: nanosleep та timerfd_create

Для високоточного позиціонування без накопичення помилок в ОС Linux використовують системні виклики сімейства [таймерів високої роздільної здатності](root:sys-unix/high-resolution-timers):

1. **`clock_nanosleep()` з прапорцем `TIMER_ABSTIME`:** на відміну від відносного сну, абсолютний таймер прив'язується до конкретної точки на шкалі `CLOCK_REALTIME` або `CLOCK_MONOTONIC`. Якщо виклик переривається сигналом, повторний виклик з тією самою абсолютною міткою часу не накопичує похибки.
2. **`timerfd_create()` та `timerfd_settime()`:** інтегрують таймер ядра безпосередньо у таблицю файлових дескрипторів процесу. Це дозволяє поєднувати очікування розкладу з моніторингом мережевих сокетів, сигналів та файлів конфігурації в єдиному циклі мультиплексування вводу-виводу (`epoll` або `poll`).

:::tabs
@tab C
```c
int tfd = timerfd_create(CLOCK_REALTIME, TFD_NONBLOCK | TFD_CLOEXEC);
struct itimerspec its;
memset(&its, 0, sizeof(its));
its.it_value.tv_sec = next_trigger_timestamp;
its.it_value.tv_nsec = 0;
timerfd_settime(tfd, TFD_TIMER_ABSTIME | TFD_TIMER_CANCEL_ON_SET, &its, NULL);
```
@tab C++
```cpp
int tfd = timerfd_create(CLOCK_REALTIME, TFD_NONBLOCK | TFD_CLOEXEC);
struct itimerspec its{};
its.it_value.tv_sec = next_trigger_timestamp;
its.it_value.tv_nsec = 0;
timerfd_settime(tfd, TFD_TIMER_ABSTIME | TFD_TIMER_CANCEL_ON_SET, &its, nullptr);
```
:::

### Гаряче перезавантаження конфігурацій: stat() проти inotify()

Системний планувальник повинен реагувати на зміну користувацьких або системних розкладів без перезапуску процесу демона:

1. **Опитування через `stat()`:** перед кожною перевіркою черги демон перевіряє час останньої модифікації `st_mtime` файлів конфігурації або каталогу спулу `/var/spool/cron/crontabs`. Якщо значення `st_mtime` новіше за час попереднього зчитування, база завдань перечитується.
2. **Асинхронний моніторинг через `inotify`:** демон реєструє спостереження за каталогами через системний виклик `inotify_add_watch(ifd, path, IN_CLOSE_WRITE | IN_MOVED_TO | IN_DELETE)`. Файловий дескриптор `inotify` додається до екземпляра `epoll`, завдяки чому перечитування конфігурації ініціюється подією ядра безпосередньо в момент збереження файлу редактором.

### Обробка стрибків часу та зміна часових поясів

Системний годинник реального часу `CLOCK_REALTIME` не є монотонним: системний адміністратор або служба синхронізації [NTP](root:sys-unix/wall-clock-and-timezones) можуть коригувати час стрибком через `settimeofday()` чи `clock_settime()`, а двічі на рік відбувається переведення годинників (Daylight Saving Time, DST).

У разі використання дескрипторів `timerfd` встановлюють прапорець `TFD_TIMER_CANCEL_ON_SET`. Якщо час годинника стрибкоподібно змінюється, ядро скидає таймер і переводить файловий дескриптор у стан готовності до читання. Виклик `read()` на дескрипторі повертає помилку з кодом `errno == ECANCELED`. Отримавши цей код, планувальник не виконує завдань помилково, а миттєво перераховує розклад на новій часовій шкалі.

## 3. Безпечний запуск завдань та конвеєр ізоляції середовища

Виконання корисного навантаження у фоновому планувальнику відбувається через розгалуження процесів. Головний демон не повинен блокуватися на час роботи призначеного скрипту, а сам скрипт має запускатися у суворо ізольованому середовищі.

```
                          ┌────────────────────────┐
                          │   Головний цикл cron   │
                          └───────────┬────────────┘
                                      │ fork()
                     ┌────────────────┴────────────────┐
                     ▼                                 ▼
         ┌───────────────────────┐         ┌───────────────────────┐
         │  Батьківський процес  │         │   Дочірній процес     │
         │  (продовжує таймер)   │         │ (підготовка оточення) │
         └───────────────────────┘         └───────────┬───────────┘
                                                       │
                                   ┌───────────────────┴───────────────────┐
                                   │ 1. setpgid(0, 0) -> власна група PGID │
                                   │ 2. setgid() / initgroups() / setuid() │
                                   │ 3. clearenv() / експорт PATH, HOME    │
                                   │ 4. dup2(/dev/null -> stdin)           │
                                   │ 5. dup2(pipe -> stdout/stderr)        │
                                   │ 6. close_range(3, ~0U, 0)             │
                                   │ 7. chdir(HOME)                        │
                                   │ 8. execve("/bin/sh", ...)             │
                                   └───────────────────────────────────────┘
```

### Поділ та безпечне зниження привілеїв

Якщо системний демон запущено від імені суперкористувача `root`, користувацькі розклади обов'язково повинні виконуватися зі зниженням повноважень ([поділу привілеїв](root:sys-unix/privilege-separation)).

Порядок системних викликів є критичним для безпеки:
1. `initgroups(username, user_gid)` або `setgroups()` — завантажує таблицю додаткових груп користувача з бази [NSS](root:sys-unix/user-database-nss).
2. `setgid(user_gid)` — встановлює реальний, ефективний та збережений ідентифікатор групи GID.
3. `setuid(user_uid)` — остаточно знижує ідентифікатор користувача UID.

> [!WARNING]
> Якщо викликати `setuid()` до викликів `setgid()` або `initgroups()`, процес втратить привілеї `CAP_SETGID` та права `root`. Наступні виклики зміни груп завершаться системною помилкою `EPERM`, і програма користувача залишиться виконуватися з правами груп суперкористувача.

### Очищення та санітизація змінних середовища

Успадкування оточення батьківського процесу несе суттєві ризики для безпеки: наявність змінних `LD_PRELOAD`, `LD_LIBRARY_PATH` або специфічних конфігурацій `IFS` може призвести до виконання довільного коду під час запуску команд.

Перед викликом [exec](root:sys-unix/exec-semantics) демон очищає успадкований масив [змінних оточення](root:sys-unix/argv-and-environment) та формує мінімальний детермінований набір:
- `PATH=/usr/bin:/bin` — суворо обмежений пошуковий шлях до системних бінарників;
- `SHELL=/bin/sh` — стандартний командний інтерпретатор POSIX;
- `USER` та `LOGNAME` — ім'я облікового запису власника завдання;
- `HOME` — домашній каталог користувача.

Після налаштування оточення процес викликає `chdir(HOME)`, щоб звільнити кореневий або монтований каталог демона.

### Ізоляція потоків вводу-виводу

У `minicron` реалізовано базову ізоляцію дескрипторів:
1. **Стандартний ввід (`stdin`, дескриптор 0):** перенаправляється на псевдопристрій `/dev/null`. Якщо запущена утиліта спробує прочитати дані з консолі, виклик `read()` негайно поверне ознаку кінця файлу (`EOF`, 0 байтів), запобігаючи вічному зависанню неінтерактивного процесу:
:::tabs
@tab C
```c
int devnull = open("/dev/null", O_RDWR);
if (devnull >= 0) {
    dup2(devnull, STDIN_FILENO);
    close(devnull);
}
```
@tab C++
```cpp
int devnull = open("/dev/null", O_RDWR);
if (devnull >= 0) {
    dup2(devnull, STDIN_FILENO);
    close(devnull);
}
```
:::
2. **Стандартний вивід (`stdout`) та вивід помилок (`stderr`):** у повнофункціональних демонах спрямовуються у неіменовані [програмні канали pipe](root:sys-unix/pipe-and-fifo) для запису в системний журнал або надсилання поштового сповіщення через `sendmail`.
3. **Закриття сторонніх дескрипторів:** усі внутрішні дескриптори демона (файли конфігурації, таймери, сокети) відкриваються з прапорцем [FD_CLOEXEC](root:sys-unix/close-on-exec) або примусово закриваються перед `exec` через `close_range(3, ~0U, 0)`.

### Створення окремої групи процесів (Process Group)

Команда в crontab часто запускає цілий конвеєр утиліт (`cat file | grep pattern | awk '{print $1}' > out`). Якщо залишити ці процеси в групі батьківського демона, плани знешкодження завислих завдань чи передачі сигналів порушаться.

Щоб ізолювати нащадків, дочірній процес перед викликом `exec` викликає `setpgid(0, 0)` ([сесії та групи процесів](root:sys-unix/sessions-and-process-groups)), призначаючи власний PID ідентифікатором нової групи процесів (PGID). Будь-які процеси, породжені оболонкою `/bin/sh`, автоматично потрапляють до цієї групи. Батьківський демон надалі може надіслати сигнал усій групі процесів однією операцією `kill(-pgid, signal)`, не ризикуючи залишити осиротілі процеси конвеєра.

### Запуск через командний інтерпретатор

Команда crontab виконується через запуск оболонки `/bin/sh -c cmd`:
:::tabs
@tab C
```c
execl("/bin/sh", "sh", "-c", cmd, (char *)NULL);
_exit(127);
```
@tab C++
```cpp
execl("/bin/sh", "sh", "-c", cmd.c_str(), nullptr);
_exit(127);
```
:::
Використання оболонки є обов'язковою вимогою стандарту: користувацькі команди часто містять конвеєри (`|`), логічні оператори (`&&`, `||`), екранування лапками та перенаправлення потоків (`>> /tmp/log`). Якщо виклик `execl()` зазнає невдачі, викликається `_exit(127)` замість `exit()`, щоб уникнути виклику обробників `atexit` батьківського адресного простору.

## 4. Асинхронний збір процесів-нащадків та обробка сигналів

Коли дочірній процес завершує роботу, операційна система звільняє зайняту ним пам'ять, проте зберігає запис у системній таблиці процесів із кодом завершення та статистикою використання ресурсів. Процес переходить у стан зомбі ([exit-wait-zombies](root:sys-unix/exit-wait-zombies)).

Якщо батьківський процес не викликає системні виклики родини `wait()`, зомбі-процеси накопичуються, що призводить до вичерпання таблиці дескрипторів процесів ядра (`/proc/sys/kernel/pid_max`) та неможливості створення нових процесів у системі.

```
+-------------------------------------------------------------------------+
|                  СИГНАЛ SIGCHLD ТА ЦИКЛ WNOHANG                         |
|                                                                         |
|  Завершення процесу N1 ─┐                                               |
|  Завершення процесу N2 ─┼─> [Один сигнал SIGCHLD] ──> sigchld_handler() |
|  Завершення процесу N3 ─┘                                    │          |
|                                                              │          |
|        ┌─────────────────────────────────────────────────────┘          |
|        ▼                                                                |
|   while (waitpid(-1, NULL, WNOHANG) > 0)                                |
|     ├── Ітерація 1: вичищено N1                                         |
|     ├── Ітерація 2: вичищено N2                                         |
|     ├── Ітерація 3: вичищено N3                                         |
|     └── Ітерація 4: повертає 0 (більше завершених немає)                |
+-------------------------------------------------------------------------+
```

### Обробник сигналу SIGCHLD

Блокуючий виклик `waitpid()` у головному циклі неприпустимий, оскільки тривале виконання завдання заблокує секундний таймер. Тому `minicron` реєструє асинхронний обробник сигналу `SIGCHLD`:

:::tabs
@tab C
```c
static void sigchld_handler(int sig) {
    (void)sig;
    int saved_errno = errno;
    while (waitpid(-1, NULL, WNOHANG) > 0) {
        /* Очищаємо всіх нащадків, що завершили роботу */
    }
    errno = saved_errno;
}
```
@tab C++
```cpp
static void setup_signal_handler() {
    struct sigaction sa{};
    sa.sa_handler = [](int) {
        int saved_errno = errno;
        while (waitpid(-1, nullptr, WNOHANG) > 0) {
            // Збір зомбі-процесів
        }
        errno = saved_errno;
    };
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART | SA_NOCLDSTOP;
    sigaction(SIGCHLD, &sa, nullptr);
}
```
:::

### Ключові інженерні вимоги до обробника

1. **Неблокуючий цикл `while (waitpid(-1, ... WNOHANG) > 0)`:** Стандартні сигнали Unix не ставляться в чергу ядра ([модель сигналів](root:sys-unix/signal-model)). Якщо три дочірні процеси завершаться одночасно під час блокування сигналів, ядро доставить батьківському процесу лише **один** екземпляр сигналу `SIGCHLD`. Одиночний виклик `waitpid()` забрав би лише один процес, залишивши решту у стані зомбі. Цикл `while` гарантує вичистку всіх готових процесів за одне спрацьовування обробника.
2. **Збереження та відновлення `errno`:** Системний виклик `waitpid()` у разі відсутності нащадків змінює глобальну змінну `errno` на `ECHILD`. Якщо сигнал перервав основний потік під час виконання іншого системного виклику, незбережений `errno` призведе до хибної діагностики помилок в основному циклі.
3. **Прапорці `SA_RESTART` та `SA_NOCLDSTOP`:** Прапорець `SA_RESTART` автоматично відновлює перервані системні виклики (наприклад, повільне читання з файлу), а `SA_NOCLDSTOP` забороняє генерацію сигналу `SIGCHLD`, якщо дочірній процес був просто призупинений (`SIGSTOP`/`SIGTSTP`), а не завершений.
4. **Асинхронна безпека за сигналами ([async-signal-safety](root:sys-unix/async-signal-safety)):** Всередині обробника сигналу суворо заборонено викликати функції, що використовують глобальні м'ютекси або виділяють динамічну пам'ять (`printf`, `malloc`, `free`, `std::cout`). Системний виклик `waitpid()` входить до стандартизованого переліку безпечних функцій POSIX.

## 5. Керування конкурентністю: ліміти процесів, Backpressure та захист від перевантаження

Запуск завдань без обмеження кількості паралельних процесів створює пряму загрозу відмови системи (Denial of Service). Якщо заплановане завдання (наприклад, резервне копіювання бази даних або перерахунок аналітичної вітрини) виконується довше за інтервал свого запуску (наприклад, 12 хвилин замість 5), кожна наступна ітерація розкладу породжуватиме новий важкий процес.

```
Хвилина 00:00 -> Старт копіювання Backup_1 (триває 15 хв) -> Активних процесів: 1
Хвилина 05:00 -> Старт копіювання Backup_2 (триває 15 хв) -> Активних процесів: 2 (CPU/IO росте)
Хвилина 10:00 -> Старт копіювання Backup_3 (триває 15 хв) -> Активних процесів: 3 (IO деградує)
Хвилина 15:00 -> Лавина процесів -> Вичерпання RAM -> Спрацьовує OOM Killer!
```

Накопичення конкуруючих процесів призводить до вичерпання дескрипторів у таблиці процесів ядра (`EAGAIN`), фрагментації дискового вводу-виводу, браку оперативної пам'яті та аварійного знищення процесів системним механізмом Out-of-Memory (OOM) Killer.

### Глобальний ліміт одночасних завдань (Max Concurrent Jobs)

Для запобігання перевантаженню планувальник встановлює жорстку верхню межу пулу активних процесів `MAX_CONCURRENT_JOBS` (наприклад, 8 або 16).

Демон веде облік активних дочірніх процесів через внутрішній реєстр PID:

:::tabs
@tab C
```c
#define MAX_CONCURRENT_JOBS 8

typedef struct {
    pid_t pid;
    size_t job_index;
    time_t start_time;
} active_job_t;

static active_job_t g_active_pool[MAX_CONCURRENT_JOBS];
static size_t g_active_count = 0;

static int can_spawn_job(void) {
    return g_active_count < MAX_CONCURRENT_JOBS;
}
```
@tab C++
```cpp
struct ActiveJob {
    pid_t pid;
    size_t job_index;
    std::chrono::steady_clock::time_point start_time;
};

class ConcurrencyController {
public:
    static constexpr size_t kMaxConcurrentJobs = 8;

    bool can_spawn() const {
        return active_jobs_.size() < kMaxConcurrentJobs;
    }

    void register_child(pid_t pid, size_t job_index) {
        active_jobs_[pid] = ActiveJob{pid, job_index, std::chrono::steady_clock::now()};
    }

    void unregister_child(pid_t pid) {
        active_jobs_.erase(pid);
    }

    size_t active_count() const { return active_jobs_.size(); }

private:
    std::unordered_map<pid_t, ActiveJob> active_jobs_;
};
```
:::

Коли функція `spawn_job` отримує валідний розклад, вона попередньо перевіряє доступність слота в пулі. Якщо ліміт вичерпано, створення процесу блокується або відкладається з фіксацією події у системному журналі.

### Захист від накладання екземплярів одного завдання (Per-Job Overlap Prevention)

Окрім загальносистемного ліміту, необхідно запобігати запуску кількох копій **того самого** завдання:
1. **Внутрішній прапорець виконання:** Структура розкладу містить прапорець `is_running` та ідентифікатор активного процесу `running_pid`. Прапорець виставляється в `1` під час виклику `fork()` і скидається в `0`, коли обробник `SIGCHLD` підтверджує завершення відповідного PID.
2. **Файлові блокування (File Locking / `flock`):** Для ізоляції між різними екземплярами демонів або захисту від ручного запуску скриптів користувачем утиліта може створювати ексклюзивне блокування файлу через `flock(fd, LOCK_EX | LOCK_NB)` у каталозі `/run/lock/minicron/job_<id>.lock`. Якщо системний виклик повертає `EWOULDBLOCK`, завдання пропускається як таке, що вже виконується.

### Стратегії зворотного тиску (Backpressure)

Якщо настає час запуску завдання, але система не має доступних ресурсів для його виконання (переповнений пул або попередній екземпляр не завершився), планувальник застосовує одну з трьох політик зворотного тиску (англ. *backpressure*):

1. **Пропуск виконання зі сповіщенням (Drop / Skip with Warning):** Найпростіша та найбезпечніша стратегія для ідемпотентних періодичних задач (моніторинг стану, збір метрик, очищення кешу). Завдання просто не стартує на поточній хвилині, а в журнал відправляється попередження рівня `LOG_WARNING`. Наступна спроба відбудеться за стандартним розкладом.
2. **Буферизація у чергу відкладених завдань (Bounded FIFO Queue):** Якщо завдання є критичним (наприклад, проведення банківської проводки або формування обов'язкового звіту), запит поміщається у чергу очікування. Щойно один із працюючих процесів завершується і звільняє слот, диспетчер витягує найстаріше завдання з черги. Черга обов'язково має обмежену ємність (англ. *bounded queue*): при перевищенні ліміту найстаріші або нові записи відкидаються із фіксацією помилки переповнення.
3. **Адаптивне дроселювання за завантаженням системи (Load Average Throttling):** Перед розгалуженням процесу демон зчитує системні метрики навантаження ([load-and-pressure](root:sys-unix/load-and-pressure)) через системний виклик `getloadavg()`:
:::tabs
@tab C
```c
double loadavg[1];
if (getloadavg(loadavg, 1) == 1) {
    /* Якщо 1-хвилинне середнє навантаження перевищує 4.0, відкладаємо запуск */
    if (loadavg[0] > 4.0) {
        /* Логування та затримка запуску */
    }
}
```
@tab C++
```cpp
double loadavg[1];
if (getloadavg(loadavg, 1) == 1) {
    if (loadavg[0] > 4.0) {
        // Логування перевантаження та перенесення завдання
    }
}
```
:::
Цей механізм аналогічний поведінці утиліти `batch` та демона `atd -l`, які автоматично призупиняють виконання фонових черг, доки середнє завантаження процесора не опуститься нижче заданого порогу.

## 6. Журналювання та спостережуваність: інтеграція із syslog та systemd-journald

Фоновий демон Unix не має керуючого термінала. Спроба виводити діагностичні повідомлення безпосередньо у `printf()` або `std::cout` є неприпустимою: стандартні потоки виводу перенаправлені у `/dev/null` або закриті. Будь-яка системна помилка (відмова виділення процесу, недійсний шлях до бінарника, відхилення прав доступу) залишиться непоміченою адміністратором без централізованого журналу подій.

### Традиційне логування через POSIX syslog

Класичним стандартом реєстрації подій у службі cron є протокол [syslog-protocol](root:sys-unix/syslog-protocol). Демон відкриває дескриптор системного логера на старті та адресує повідомлення у спеціалізовану категорію (facility) `LOG_CRON`.

:::tabs
@tab C
```c
#include <syslog.h>

void init_logging(void) {
    /* Відкриття журналу: LOG_PID додає ідентифікатор демона до кожного рядка */
    openlog("minicron", LOG_PID | LOG_NDELAY, LOG_CRON);
}

void log_job_start(pid_t pid, const char *cmd) {
    syslog(LOG_INFO, "JOB_START: pid=%d cmd=\"%s\"", pid, cmd);
}

void log_job_finish(pid_t pid, int exit_code, double duration_sec) {
    if (exit_code == 0) {
        syslog(LOG_INFO, "JOB_END: pid=%d exit=0 duration=%.2fs", pid, duration_sec);
    } else {
        syslog(LOG_ERR, "JOB_FAIL: pid=%d exit=%d duration=%.2fs", pid, exit_code, duration_sec);
    }
}

void cleanup_logging(void) {
    closelog();
}
```

### Градація рівнів пріоритетів (Syslog Severities)

Для чіткої фільтрації подій планувальник використовує відповідні рівні важливості:
- **`LOG_INFO`:** Штатні операційні події — успішний запуск завдання, нормальне завершення процесу з нульовим кодом повернення, фіксація тривалості виконання.
- **`LOG_NOTICE`:** Значущі системні зміни, які не є збоями — старт і коректна зупинка планувальника, перезавантаження таблиці розкладів після оновлення конфігурації, коригування таймерів у зв'язку зі стрибком часу NTP чи переведенням годинників (DST).
- **`LOG_WARNING`:** Нештатні, але контрольовані ситуації — пропуск завдання через спрацювання ліміту конкурентності (`MAX_CONCURRENT_JOBS`), відхилення повторного запуску через незавершений попередній процес, виявлення високого Load Average.
- **`LOG_ERR`:** Аварійні події конкретних завдань — збій виклику `fork()` через нестачу пам'яті ядра (`ENOMEM`), завершення дочірнього процесу з ненульовим кодом повернення, примусове вбивство нащадка сигналом (`SIGSEGV`, `SIGKILL`), помилка зниження прав доступу `setuid()`.
- **`LOG_CRIT` / `LOG_ALERT`:** Фатальні помилки самого демона — пошкодження файлу спулу завдань, неможливість створити таймер `timerfd`, отримання критичного сигналу аварійної зупинки.

### Сучасна нативна інтеграція із systemd-journald

Під час запуску планувальника як сервісу [systemd-model](root:sys-unix/systemd-model) стандартні потоки виводу `stdout` та `stderr` служби перехоплюються менеджером системи і передаються безпосередньо в [journald-structured-entry-model](root:sys-unix/journald-structured-entry-model).

1. **Потокові префікси пріоритетів (Stream Priority Prefixes):** Демон може передавати рівень повідомлення без виклику `syslog()`, додаючи спеціальний префікс `<p>` на початку кожного рядка:
   - `<6>minicron: JOB_START [backup.sh] PID 4512` — пріоритет `LOG_INFO` (6);
   - `<4>minicron: Job concurrency throttled, 8 jobs active` — пріоритет `LOG_WARNING` (4);
   - `<3>minicron: Fork failed: Cannot allocate memory` — пріоритет `LOG_ERR` (3).
   `systemd-journald` автоматично розпізнає цей префікс, відокремлює його від тіла повідомлення та виставляє відповідне поле `PRIORITY` у двійковому журналі.
2. **Структуровані поля журналу:** При використанні бібліотечного API `sd_journal_send()` або запису у сокет `/run/systemd/journal/socket` демон додає структуровані метадані:
   ```
   MESSAGE=Job execution completed with error
   PRIORITY=3
   SYSLOG_FACILITY=9
   CRON_JOB_NAME=nightly_backup
   CRON_JOB_PID=5124
   CRON_EXIT_STATUS=2
   CRON_DURATION_SEC=142.5
   ```
   Це дозволяє системним адміністраторам виконувати миттєву фільтрацію інструментом `journalctl`:
   ```bash
   journalctl -u minicron.service CRON_JOB_NAME=nightly_backup PRIORITY=3
   ```

## 7. Коректне завершення роботи (Graceful Shutdown) за сигналами SIGTERM та SIGINT

Раптова зупинка планувальника командою `kill -9` або необдумане завершення процесу через виклик `exit(0)` залишає систему в нестабільному стані. Дочірні завдання, які виконують тривалі операції (створення дампу бази даних, запис архіву на диск, зміна системних таблиць), перетворюються на «сироти» ([orphan-reparenting](root:sys-unix/orphan-reparenting)). Вони втрачають координацію з планувальником, можуть пошкодити тимчасові файли або безконтрольно споживати ресурси сервера.

Для запобігання цьому промисловий планувальник реалізує багатофазний протокол безпечного вимкнення ([orderly-shutdown](root:sys-unix/orderly-shutdown)) при отриманні сигналів `SIGTERM` (стандартний сигнал зупинки служби від systemd чи `kill`) та `SIGINT` (`Ctrl+C` під час ручного налагодження).

### Атомарні прапорці завершення

Обробник сигналів завершення не виконує складних операцій, а лише змінює стан атомарного прапорця:

:::tabs
@tab C
```c
static volatile sig_atomic_t g_shutdown_requested = 0;

static void sigterm_handler(int sig) {
    (void)sig;
    g_shutdown_requested = 1;
}

static void setup_shutdown_signals(void) {
    struct sigaction sa;
    memset(&sa, 0, sizeof(sa));
    sa.sa_handler = sigterm_handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0; /* Не ставимо SA_RESTART, щоб перервати системні виклики сну */
    sigaction(SIGTERM, &sa, NULL);
    sigaction(SIGINT, &sa, NULL);
}
```
@tab C++
```cpp
#include <atomic>
#include <csignal>

class SignalManager {
public:
    static inline std::atomic<bool> shutdown_requested{false};

    static void setup_handlers() {
        struct sigaction sa{};
        sa.sa_handler = [](int) {
            shutdown_requested.store(true, std::memory_order_relaxed);
        };
        sigemptyset(&sa.sa_mask);
        sa.sa_flags = 0;
        sigaction(SIGTERM, &sa, nullptr);
        sigaction(SIGINT, &sa, nullptr);
    }
};
```

### Багатофазний протокол безпечного вимкнення

1. **Фаза 1: Припинення нових запусків.** Під час чергової перевірки або після переривання виклику `sleep()` / `clock_nanosleep()` демон перевіряє значення прапорця. Якщо прапорець виставлено, планувальник негайно виходить із головного циклу таймера і забороняє будь-які нові виклики `fork()`.
2. **Фаза 2: Каскадне сповіщення нащадків.** Демон ітерує таблицею активних завдань і надсилає сигнал `SIGTERM` усім зареєстрованим процесам або їхнім групам через `kill(-pgid, SIGTERM)`. Це дає змогу запущеним користувацьким скриптам перехопити сигнал за допомогою обробників `trap` ([trap-and-cleanup](root:sys-unix/trap-and-cleanup)), коректно закрити відкриті з'єднання, скинути транзакції на диск та видалити тимчасові файли.
3. **Фаза 3: Очікування завершення із таймаутом (Grace Period).** Планувальник запускає таймер очікування (наприклад, 15 або 30 секунд). У циклі з короткими інтервалами сну (`nanosleep` на 100 мс) демон опитує статус процесів через `waitpid(-1, &status, WNOHANG)`. Якщо всі дочірні процеси успішно завершилися до вичерпання ліміту часу, демон одразу переходить до фінальної зачистки.
4. **Фаза 4: Примусова ескалація до SIGKILL.** Якщо строк очікування сплив, а деякі процеси все ще перебувають у системній таблиці (наприклад, процес заблокувався на безкінечному циклі чи проігнорував `SIGTERM`), планувальник здійснює ескалацію і надсилає безумовний сигнал знищення `kill(-pgid, SIGKILL)`. Сигнал `SIGKILL` не може бути перехоплений або проігнорований процесом. Після цього демон викликає блокуючий `waitpid()` для гарантованого видалення зомбі-записів.
5. **Фаза 5: Очищення системних ресурсів.** Після ліквідації всіх нащадків планувальник видаляє свій файл блокування блокування екземпляра (`/run/minicron.pid`), скидає стан відкритих дескрипторів, надсилає фінальне повідомлення в журнал викликом `closelog()` та завершує роботу процесу з кодом `0`.

:::tabs
@tab C
```c
void execute_graceful_shutdown(int timeout_sec) {
    syslog(LOG_NOTICE, "Initiating graceful shutdown (timeout %ds)...", timeout_sec);

    /* 1. Надсилаємо SIGTERM усім зареєстрованим групам нащадків */
    for (size_t i = 0; i < g_active_count; ++i) {
        if (g_active_pool[i].pid > 0) {
            kill(-g_active_pool[i].pid, SIGTERM);
        }
    }

    /* 2. Очікуємо завершення нащадків із таймаутом */
    time_t deadline = time(NULL) + timeout_sec;
    while (g_active_count > 0 && time(NULL) < deadline) {
        int status;
        pid_t p;
        while ((p = waitpid(-1, &status, WNOHANG)) > 0) {
            /* Видаляємо завершений PID з пулу активних */
            for (size_t i = 0; i < g_active_count; ++i) {
                if (g_active_pool[i].pid == p) {
                    g_active_pool[i] = g_active_pool[--g_active_count];
                    break;
                }
            }
        }
        struct timespec req = {0, 100000000L}; /* 100 мс */
        nanosleep(&req, NULL);
    }

    /* 3. Ескалація до SIGKILL для завислих процесів */
    if (g_active_count > 0) {
        syslog(LOG_WARNING, "Timeout expired: killing %zu stubborn processes", g_active_count);
        for (size_t i = 0; i < g_active_count; ++i) {
            if (g_active_pool[i].pid > 0) {
                kill(-g_active_pool[i].pid, SIGKILL);
                waitpid(g_active_pool[i].pid, NULL, 0);
            }
        }
        g_active_count = 0;
    }

    syslog(LOG_NOTICE, "Shutdown complete. Exiting.");
    closelog();
}
```
@tab C++
```cpp
void execute_graceful_shutdown(std::chrono::seconds timeout) {
    syslog(LOG_NOTICE, "Initiating graceful shutdown...");

    // 1. Сповіщення нащадків
    for (const auto& [pid, info] : active_jobs_) {
        kill(-pid, SIGTERM);
    }

    // 2. Очікування з таймаутом
    auto deadline = std::chrono::steady_clock::now() + timeout;
    while (!active_jobs_.empty() && std::chrono::steady_clock::now() < deadline) {
        int status = 0;
        pid_t p = 0;
        while ((p = waitpid(-1, &status, WNOHANG)) > 0) {
            active_jobs_.erase(p);
        }
        std::this_thread::sleep_for(std::chrono::milliseconds(100));
    }

    // 3. Примусове знищення
    if (!active_jobs_.empty()) {
        syslog(LOG_WARNING, "Killing %zu stubborn processes with SIGKILL", active_jobs_.size());
        for (const auto& [pid, info] : active_jobs_) {
            kill(-pid, SIGKILL);
            waitpid(pid, nullptr, 0);
        }
        active_jobs_.clear();
    }

    syslog(LOG_NOTICE, "Shutdown complete. Exiting.");
    closelog();
}
```

## 8. Обробка пропущених запусків та стан персистентності

Класичний `cron` проектувався для цілодобових серверів (24/7). Якщо комп'ютер було вимкнено під час запланованого нічного запуску (наприклад, створення резервної копії о 03:00), завдання взагалі не виконається: демон прокинеться вранці й очікуватиме наступної ночі.

Для систем із періодичним живленням (персональні комп'ютери, ноутбуки, спотові віртуальні машини в хмарі) використовується архітектурна модель утиліти `anacron`.

```
                    ┌───────────────────────────────┐
                    │      Старт демона / системи   │
                    └───────────────┬───────────────┘
                                    │
                                    ▼
                    ┌───────────────────────────────┐
                    │ Зчитування мітки часу з файлу │
                    │   /var/spool/anacron/<job>    │
                    └───────────────┬───────────────┘
                                    │
                    ┌───────────────┴───────────────┐
                    │                               │
            (now - last_run) >= період      (now - last_run) < період
                    │                               │
                    ▼                               ▼
      ┌───────────────────────────┐   ┌───────────────────────────┐
      │ Запуск із випадковою      │   │ Пропуск: завдання вже     │
      │ затримкою (RANDOM_DELAY)  │   │ виконувалося в цей період │
      └─────────────┬─────────────┘   └───────────────────────────┘
                    │
                    ▼
      ┌───────────────────────────┐
      │ Атомарне оновлення файлу  │
      │ мітки часу (rename tmp)   │
      └───────────────────────────┘
```

### Механізм файлів міток часу (Spool Timestamp Files)

Для кожного періодичного завдання виділяється файл стану у каталозі спулу (наприклад, `/var/spool/anacron/daily_backup`):
- У файлі зберігається дата останнього успішного старту завдання у форматі `YYYYMMDD` або числове значення секунд UNIX epoch (`time_t`).
- Під час завантаження планувальник зчитує мітку часу `last_run` для кожного зареєстрованого завдання й обчислює інтервал `days_passed = (now - last_run) / 86400`.
- Якщо `days_passed >= period_in_days`, завдання позначається як пропущене і ставиться в чергу на негайне виконання.

### Атомарний запис міток часу

Оновлення часової мітки після завершення завдання повинно бути стійким до раптового зникнення живлення. Запис безпосередньо в основний файл може залишити пошкоджений файл нульового розміру, якщо машина вимкнеться посеред операції `write()`.

Надійне оновлення здійснюється за схемою транзакційного перейменування:
1. Запис поточної дати у тимчасовий файл у тому самому каталозі: `/var/spool/anacron/daily_backup.tmp`.
2. Синхронізація буферів на диск викликом `fsync()`.
3. Атомарна заміна основного файлу системним викликом `rename("/var/spool/anacron/daily_backup.tmp", "/var/spool/anacron/daily_backup")`.

### Рандомізація затримок (Thundering Herd Protection)

Якщо комп'ютер був вимкнений протягом тижня, під час першого завантаження всі пропущені щоденні, щотижневі та щомісячні скрипти виявляться простроченими одночасно.

Одночасний запуск кількох важких сценаріїв (ротація журналів, оновлення пошукових індексів `updatedb`, антивірусне сканування) спричиняє шторм дискового вводу-виводу та перевантаження процесора. Для захисту від цього планувальник додає два типи затримок:
- **Базова затримка (`delay_in_minutes`):** фіксований час очікування після старту системи (наприклад, 5 хвилин для daily, 15 хвилин для weekly);
- **Випадкова затримка (`RANDOM_DELAY`):** випадкове число хвилин, що додається до базової затримки для розмивання пікового навантаження в часі.

## 9. Порівняльний інженерний аналіз реалізацій C та C++

Реалізації на C та C++ демонструють два різні підходи до розробки системних утиліт:

| Характеристика | Реалізація C (`main.c`) | Реалізація C++ (`main.cpp`) |
| :--- | :--- | :--- |
| **Керування пам'яттю** | Статичний масив фіксованого розміру (`g_jobs[32]`), нуль динамічних алокацій у рантаймі | Динамічний вектор `std::vector<CronJob>` із безпечним автоматичним керуванням пам'яттю |
| **Робота з рядками** | Токенізація через `strtok` із ручною модифікацією буфера на стеку | `std::string_view` без копіювання пам'яті та `std::stringstream` для розбору списків |
| **Представлення масок** | Побітові операції над цілими числами `unsigned long long` | Шаблонний клас `std::bitset<N>` із контролем меж і читабельними методами `.test()` / `.set()` |
| **Обробка сигналів** | Класична функція зворотного виклику із ручним збереженням `errno` | Лямбда-функція у статичному методі класу `Scheduler` |
| **Обробка помилок** | Числові коди повернення `-1` та перевірка викликів | Винятки `std::invalid_argument` та `std::out_of_range` із централізованим перехопленням у `main()` |
| **Керування ресурсами** | Ручний виклик `closelog()`, `close()`, явні цикли очищення | Патерн RAII: деструктори автоматично закривають дескриптори та звільняють ресурси |

### Практичне спостереження та налагодження

Для перевірки коректності функціонування зібраного бінарника `minicron` використовують стандартний інструментарій системного налагодження Linux:

1. **Трасування системних викликів розгалуження та сигналів:**
```bash
strace -f -e trace=clone,fork,execve,wait4,sigaction,nanosleep,kill ./minicron
```
У виводі `strace` чітко простежуються виклики створення процесу `clone`/`fork`, заміна образу на `/bin/sh` через `execve`, засинання батьківського процесу на точну кількість секунд, моментальний збір через `wait4` під час доставки `SIGCHLD` та надсилання сигналів зупинки `kill` під час graceful shutdown.

2. **Перевірка відсутності зомбі-процесів та активних груп:**
```bash
ps -eo pid,ppid,pgid,stat,comm | grep -E "minicron|defunct"
```
Таблиця процесів підтверджує, що дочірні завдання створюють власні групи `pgid`, а після завершення негайно вичищаються, не залишаючи записів зі статусом `Z` (`<defunct>`).

3. **Інспекція відкритих файлових дескрипторів:**
```bash
ls -l /proc/$(pgrep minicron)/fd
```
Команда дозволяє переконатися, що дескриптори `0`, `1`, `2` процесу коректно перенаправлені, а дескриптори таймерів `timerfd` та системного логера не витікають у дочірні процеси завдяки прапорцю `FD_CLOEXEC`.

4. **Перевірка масок сигналів та потоків процесу:**
```bash
cat /proc/$(pgrep minicron)/status | grep -E "Threads|SigCgt|SigIgn|FDSize"
```
Поле `SigCgt` (англ. *Signals Caught*) містить шістнадцяткову бітову маску перехоплених сигналів. Наявність встановлених бітів для `SIGCHLD` (сигнал 17), `SIGTERM` (сигнал 15) та `SIGINT` (сигнал 2) підтверджує коректну реєстрацію обробників через `sigaction`.

5. **Моніторинг системного журналу подій:**
```bash
journalctl -t minicron -f -o verbose
```
Команда виводить деталізований потік логів у реальному часі із відображенням міток старту, завершення, кодів виходу та часу роботи кожного запланованого завдання.
