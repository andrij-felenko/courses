# 📋 Формати конфігурації crontab, anacrontab та директиви systemd timers

Довідник синтаксису, конфігураційних файлів, змінних середовища та командних інтерфейсів для підсистем фонового планування в Unix та Linux: `cron`, `anacron` та `systemd.timer`.

## 1. Синтаксис розкладів crontab

Розклад періодичного запуску завдань у форматі `crontab` описується п'ятьма обов'язковими часовими полями, розділеними пробілами або символами табуляції. Кожне поле відповідає за свій вимір астрономічного часу та перевіряється демоном `crond` під час хвилинного пробудження:

```text
# ┌───────────── хвилини (0 - 59)
# │ ┌────────────── години (0 - 23)
# │ │ ┌─────────────── день місяця (1 - 31)
# │ │ │ ┌──────────────── місяць (1 - 12 або JAN-DEC)
# │ │ │ │ ┌───────────────── день тижня (0 - 7, де 0 і 7 = неділя, або SUN-SAT)
# │ │ │ │ │
# * * * * *  [користувач]  команда для виконання
```

### Правила інтерпретації часових полів
Кожне з п'яти часових полів приймає або точне числове значення, або спеціальні синтаксичні конструкції, що формують множину допустимих моментів часу:
- **Хвилини (0–59):** точна хвилина години, на якій має відбутися запуск. Значення `0` відповідає початку години.
- **Години (0–23):** година доби у 24-годинному форматі, де `0` позначає північ, а `23` — 23:00.
- **День місяця (1–31):** календарне число місяця. Якщо у поточному місяці менше днів, ніж зазначено (наприклад, 31 лютого), запуск у цей день просто не відбудеться.
- **Місяць (1–12 або JAN–DEC):** порядковий номер місяця або його трибуквена англомовна абревіатура без урахування регістру.
- **День тижня (0–7 або SUN–SAT):** день тижня. Стандарт POSIX визначає `0` як неділю, проте більшість сучасних реалізацій для зручності підтримують і `7` як неділю (`1` — понеділок, `6` — субота).

### Допустимі оператори у часових полях
| Оператор | Назва | Призначення | Приклад | Значення |
| :--- | :--- | :--- | :--- | :--- |
| `*` | Зірочка (wildcard) | Позначає будь-яке допустиме значення у повному діапазоні цього поля | `* * * * *` | Щомиті на початку кожної хвилини |
| `,` | Кома (список) | Задає перелік дискретних числових значень | `0,15,30,45 * * * *` | Щойно настає 0-ва, 15-та, 30-та або 45-та хвилина |
| `-` | Дефіс (діапазон) | Визначає неперервний інклюзивний інтервал значень від початкового до кінцевого | `0 9-17 * * *` | Щороку о 00 хвилин кожної години в інтервалі з 9:00 до 17:00 |
| `/` | Скісна риска (крок) | Вказує крок приросту через діапазон або повне поле зірочки | `*/10 * * * *` | Кожні 10 хвилин (значення 0, 10, 20, 30, 40, 50) |
| `L` | Last (специфічне розширення) | Останній можливий день місяця або дня тижня | `0 0 L * *` | Опівночі останнього дня поточного календарного місяця |

### Вбудовані мнемонічні макроси розкладу
Для спрощення конфігурації замість п'яти часових полів на початку рядка можна вказати одне зі спеціальних зарезервованих ключових слів. Демон `cron` автоматично розгортає їх у відповідні бітові маски:

| Макрос | Еквівалентний вираз | Опис часу виконання |
| :--- | :--- | :--- |
| `@reboot` | — | Одноразовий запуск відразу під час старту демона `cron` після завантаження операційної системи |
| `@yearly` / `@annually` | `0 0 1 1 *` | Запуск о 00:00 1 січня кожного календарного року |
| `@monthly` | `0 0 1 * *` | Запуск о 00:00 1 числа кожного календарного місяця |
| `@weekly` | `0 0 * * 0` | Запуск о 00:00 щонеділі |
| `@daily` / `@midnight` | `0 0 * * *` | Запуск о 00:00 щоночі |
| `@hourly` | `0 * * * *` | Запуск на початку кожної години на нульовій хвилині |

## 2. Типи файлів crontab та їхня внутрішня структура

У системі співіснують дві принципово різні категорії таблиць розкладів: ізольовані користувацькі файли та системні конфігураційні файли.

### Користувацькі файли розкладу (`crontab -e`)
Користувацькі розклади створюються, редагуються та видаляються виключно через однойменну утиліту `crontab`. Пряме редагування цих файлів у текстовому редакторі суворо не рекомендується, оскільки утиліта автоматично перевіряє синтаксичну коректність перед записом на диск та оновлює час модифікації каталогу спулу для сповіщення демона.
- **Шлях збереження:** `/var/spool/cron/crontabs/<username>` у дистрибутивах Debian/Ubuntu або `/var/spool/cron/<username>` у дистрибутивах родини Red Hat / SUSE.
- **Права доступу:** Файл належить користувачу `<username>`, має права доступу `0600` або `0400` та захищений спеціальною групою `crontab`.
- **Формат рядка:** `хвилини  години  день_місяця  місяць  день_тижня  команда` (поле користувача відсутнє, оскільки обліковий запис однозначно ідентифікується за назвою самого файлу).

### Системний файл `/etc/crontab` та каталоги `/etc/cron.d/`
Системні розклади призначені для адміністративних завдань та інтеграції пакетів програмного забезпечення (наприклад, ротації логів `logrotate` чи оновлення сертифікатів `certbot`).
- **Формат рядка:** `хвилини  години  день_місяця  місяць  день_тижня  КОРИСТУВАЧ  команда`.
- **Особливість:** Шосте поле є обов'язковим і явно визначає обліковий запис користувача, під чиїм UID та GID демон повинен запустити дочірній процес через системні виклики [setuid](root:sys-unix/permission-bits) та `setgid`.

### Змінні середовища у файлах crontab
У заголовку будь-якого crontab-файлу дозволено оголошувати власні змінні оточення у простому форматі `NAME="value"`. Це дозволяє уникнути проблем із жорстко обмеженим середовищем за замовчуванням:

| Змінна | Значення за замовчуванням | Інженерне призначення |
| :--- | :--- | :--- |
| `SHELL` | `/bin/sh` | Командна оболонка, яку `cron` викликає з прапорцем `-c` для інтерпретації рядка команди |
| `PATH` | `/usr/bin:/bin` | Список каталогів для пошуку бінарних файлів. Рекомендується явно вказувати повний список: `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` |
| `MAILTO` | Власник файлу (або `root`) | Адреса електронної пошти, на яку демон надсилає перехоплений вивід `stdout` та `stderr`. Якщо вказати `MAILTO=""`, надсилання пошти повністю вимикається |
| `HOME` | Домашній каталог з `/etc/passwd` | Робочий каталог, у який демон переходить системним викликом `chdir()` перед виконанням команди |
| `CRON_TZ` / `TZ` | Системний час ядра | Вказує локальний часовий пояс для інтерпретації полів розкладу цього конкретного файлу |
| `CONTENT_TYPE` | `text/plain; charset=UTF-8` | Заголовок MIME-типу, що формується поштовим агентом під час надсилання звіту про виконання |

## 3. Керування доступом до підсистеми crontab

Право звичайних користувачів на запуск утиліти `crontab` та створення власних розкладів регламентується політикою доступу на базі двох файлів:

```text
               Чи існує /etc/cron.allow?
                     /          \
                   ТАК          НІ
                   /              \
    Чи є користувач у ньому?    Чи існує /etc/cron.deny?
          /          \               /          \
        ТАК          НІ            ТАК          НІ
        /              \           /              \
     ДОЗВОЛЕНО      ЗАБОРОНЕНО   Чи є в ньому?   ДОЗВОЛЕНО
                                 /          \   (дефолт системи)
                               ТАК          НІ
                               /              \
                          ЗАБОРОНЕНО       ДОЗВОЛЕНО
```

- Якщо файл `/etc/cron.allow` існує, право на використання `crontab` мають виключно ті користувачі, чиї логіни явно перелічені в цьому файлі (по одному на рядок). Вміст `/etc/cron.deny` при цьому повністю ігнорується.
- Якщо `/etc/cron.allow` відсутній, демон перевіряє `/etc/cron.deny`: доступ дозволено всім користувачам, окрім тих, хто внесений до чорного списку.
- Якщо обидва файли відсутні, поведінка залежить від конфігурації дистрибутива: у більшості систем доступ дозволено лише суперкористувачу `root`, тоді як в інших — усім користувачам системи.

## 4. Конфігурація anacron (`/etc/anacrontab`)

Утиліта `anacron` призначена для запуску періодичних регламентних завдань на комп'ютерах, які вимикаються на ніч або переходять у сплячий режим (робочі станції, персональні ноутбуки). Файл `/etc/anacrontab` описує розклад в інтервалах днів:

```text
# період_у_днях   затримка_у_хвилинах   ідентифікатор_завдання   команда
1                 5                     cron.daily               run-parts /etc/cron.daily
7                 10                    cron.weekly              run-parts /etc/cron.weekly
@monthly          15                    cron.monthly             run-parts /etc/cron.monthly
```

### Поля структури запису anacrontab
1. **Період у днях (period):** числова кількість днів між обов'язковими запусками завдання (наприклад, `1` для щоденних, `7` для щотижневих, `30` або `@monthly` для щомісячних).
2. **Затримка у хвилинах (delay):** час очікування після запуску утиліти або ввімкнення машини перед початком виконання цього конкретного рядка. Затримки для різних завдань роблять різними, щоб уникнути одночасного пікового навантаження на диск і процесор під час завантаження системи.
3. **Ідентифікатор завдання (job-identifier):** унікальне ім'я, яке використовується як назва текстового файлу в каталозі `/var/spool/anacron/`. У цей файл `anacron` записує дату останнього успішного запуску у форматі `YYYYMMDD`.
4. **Команда (command):** виконуваний скрипт або утиліта. Найчастіше тут викликається допоміжний сценарій `run-parts`, який по черзі запускає всі скрипти з відповідного каталогу (`/etc/cron.daily`, `/etc/cron.weekly` тощо).

### Глобальні параметри середовища anacron
- `START_HOURS_RANGE=3-22` — вікно годин доби, у межах якого дозволено запускати завдання. Якщо систему ввімкнули о 23:30, `anacron` відкладе виконання до настання дозволеного діапазону.
- `RANDOM_DELAY=45` — додаткова випадкова затримка у хвилинах, що генерується індивідуально для кожної машини, запобігаючи одночасному навантаженню на мережеві сховища та сервери резервного копіювання у великих комп'ютерних кластерах.

## 5. Директиви таймерів systemd (`.timer`)

У сучасних Linux-системах на базі [systemd](root:sys-unix/systemd-model) розклад описується у файлі таймер-юніта з розширенням `.timer`. Таймер керує активацією однойменного або явно вказаного сервіс-юніта (`.service`), де зосереджено опис виконуваної команди та параметри ізоляції процесів.

### Директиви секції `[Timer]`
| Директива | Клас таймера | Опис та приклад конфігурації |
| :--- | :--- | :--- |
| `OnCalendar=` | Календарний (realtime) | Задає запуск за астрономічним календарем: `OnCalendar=*-*-* 04:00:00` або `OnCalendar=Mon..Fri 09:00:00` |
| `OnBootSec=` | Монотонний | Запуск через фіксований час після завантаження ядра операційної системи: `OnBootSec=15min` |
| `OnStartupSec=` | Монотонний | Запуск через вказаний інтервал після старту самого процесу менеджера systemd: `OnStartupSec=5min` |
| `OnUnitActiveSec=` | Монотонний | Запуск через інтервал від моменту попередньої успішної активації цільового сервісу: `OnUnitActiveSec=1h` |
| `OnUnitInactiveSec=` | Монотонний | Запуск через інтервал від моменту повного завершення попереднього циклу роботи сервісу: `OnUnitInactiveSec=30min` |
| `Persistent=` | Логічний (`true`/`false`) | Якщо увімкнено (`true`), менеджер фіксує мітку часу виконання на диску (`/var/lib/systemd/timers/stamp-*`). Якщо момент розкладу було пропущено під час вимкненого живлення, сервіс запуститься негайно після наступного завантаження |
| `AccuracySec=` | Часовий інтервал | Вікно точності об'єднання таймерів ядра для енергозбереження процесора: `AccuracySec=1s` (за замовчуванням `1min`) |
| `RandomizedDelaySec=`| Часовий інтервал | Максимальний випадковий зсув запуску для запобігання сплескам навантаження у хмарних кластерах: `RandomizedDelaySec=15m` |
| `Unit=` | Назва юніта | Явне ім'я сервісу, що активується (за замовчуванням активується однойменний `<ім'я_таймера>.service`): `Unit=backup-database.service` |
| `RemainAfterElapse=` | Логічний (`true`/`false`) | Чи залишати таймер у стані `active` після завершення розкладу (актуально для одноразових подій) |

### Формат календарних виразів `OnCalendar=`
Календарний синтаксис systemd будується за єдиним шаблоном: `ДеньТижня РРРР-ММ-ДД ГГ:ХХ:СС`

- `*-*-* 02:00:00` — виконувати щоночі рівно о 02:00:00.
- `Mon..Fri *-*-* 08:30:00` — виконувати щопонеділка, щовівторка, щосереди, щочетверга та щоп'ятниці о 08:30:00.
- `*-*-01 00:00:00` — виконувати першого числа кожного календарного місяця опівночі.
- `hourly` — готовий аліас для запуску на початку кожної години (`*-*-* *:00:00`).
- `daily` — аліас для щоденного запуску опівночі (`*-*-* 00:00:00`).
- `weekly` — аліас для запуску щопонеділка опівночі (`Mon *-*-* 00:00:00`).

Для перевірки правильності розбору календарних рядків та отримання інформації про майбутні моменти спрацьовування використовується службова утиліта:
```bash
systemd-analyze calendar "Mon..Fri *-*-* 09:00:00"
```

### Командний інтерфейс адміністрування таймерів systemd
- `systemctl list-timers --all` — виводить повну таблицю всіх активних та неактивних таймерів системи, включно з точним часом останнього спрацьовування, часом наступного запуску, залишком часу очікування та назвою пов'язаного сервісу.
- `systemctl enable --now <name>.timer` — додає таймер до автозавантаження та негайно активує його відлік.
- `journalctl -u <name>.service` — надає доступ до централізованого структурованого журналу виконання конкретного фонового завдання безпосередньо з підсистеми `journald`.
