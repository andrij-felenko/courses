# 📋 Формати конфігурації crontab, anacrontab, директиви systemd timers та утиліти at/batch

Технічний довідник синтаксису, структур файлів розкладу, змінних середовища, правил інтерпретації, обробки часових поясів та командних інтерфейсів для підсистем періодичного й разового планування в Unix та Linux: стандарти POSIX/Vixie `cron`, `anacron` 2.3, специфікація `systemd.timer` (із граматикою `systemd.time(7)`), а також підсистема черг відкладеного виконання `at`, `batch` та демона `atd`.

## 1. Синтаксис розкладів crontab

Розклад періодичного запуску завдань у форматі `crontab` визначається п'ятьма часовими полями для користувацьких таблиць та шістьма полями (із обов'язковим ім'ям користувача) для системних конфігурацій. Кожне поле перевіряється демоном `crond` під час хвилинного пробудження на нульовій секунді (`tm_sec == 0`).

```text
# ┌───────────── хвилини (0 - 59)
# │ ┌────────────── години (0 - 23)
# │ │ ┌─────────────── день місяця (1 - 31)
# │ │ │ ┌──────────────── місяць (1 - 12 або назва JAN - DEC)
# │ │ │ │ ┌───────────────── день тижня (0 - 7, де 0 і 7 = неділя, або SUN - SAT)
# │ │ │ │ │
# * * * * *  [користувач]  команда для виконання
```

### Специфікація часових полів

| Поле | Допустимий діапазон | Символьні назви | Опис та семантика |
| :--- | :--- | :--- | :--- |
| **Хвилини** (`minute`) | `0–59` | — | Дискретна хвилина години. `0` — початок години |
| **Години** (`hour`) | `0–23` | — | Година доби у 24-годинному форматі. `0` — північ, `12` — полудень, `23` — 23:00 |
| **День місяця** (`day of month`, DOM) | `1–31` | — | Календарне число місяця. Якщо у місяці менше днів (наприклад, 31 лютого чи 31 квітня), запуск у цей день не відбувається |
| **Місяць** (`month`) | `1–12` | `JAN`, `FEB`, `MAR`, `APR`, `MAY`, `JUN`, `JUL`, `AUG`, `SEP`, `OCT`, `NOV`, `DEC` | Номер або нечутлива до регістру назва місяця англійською мовою (підтримуються діапазони `JAN-MAR` та списки `SEP,OCT`) |
| **День тижня** (`day of week`, DOW) | `0–7` (0 і 7 = неділя) | `SUN`, `MON`, `TUE`, `WED`, `THU`, `FRI`, `SAT` | День тижня за стандартом POSIX (0 = неділя, 1 = понеділок, ..., 6 = субота). Значення `7` також позначає неділю для сумісності з ранніми BSD-системами |

### Правила розпізнавання текстових назв місяців та днів тижня

1. **Нечутливість до регістру:** Символьні назви розпізнаються без урахування регістру символів (`jan`, `Jan`, `JAN`, `mon`, `Mon`, `MON` є абсолютно еквівалентними).
2. **Спискові вирази та інтервали:** Назви дозволено використовувати у списках через кому (`JAN,APR,JUL,OCT` або `MON,WED,FRI`) та у неперервних інтервалах через дефіс (`MON-FRI` або `JUN-AUG`).
3. **Заборона змішування форматів у межах одного діапазону:** У стандартному парсері Vixie cron заборонено змішувати числові індекси та текстові назви в одному інтервалі (вирази виду `3-AUG` чи `MON-5` спричиняють синтаксичну помилку розбору рядка `bad minute/hour/day/month`).
4. **Обмеження на крок зі строковими назвами:** За стандартом POSIX та у класичному Vixie cron оператор кроку `/` не застосовується безпосередньо до назв (запис `JAN-DEC/2` є нестандартним розширенням і в деяких реалізаціях відхиляється, тоді як еквівалентний числовий запис `1-12/2` гарантовано підтримується всіма сумісними реалізаціями).

### Допустимі оператори у часових полях

| Оператор | Назва | Призначення та синтаксис | Приклад | Інтерпретація |
| :--- | :--- | :--- | :--- | :--- |
| `*` | Зірочка (*wildcard*) | Позначає будь-яке допустиме значення у повному діапазоні поля | `* * * * *` | Щомиті на початку кожної хвилини |
| `,` | Кома (*enumeration*) | Задає перелік дискретних числових або символьних значень | `0,15,30,45 * * * *` | На 0-й, 15-й, 30-й та 45-й хвилинах щогодини |
| `-` | Дефіс (*range*) | Визначає замкнений неперервний інтервал від початкового до кінцевого значення включно | `0 9-17 * * *` | О 00 хвилин щогодини з 9:00 до 17:00 (9, 10, ..., 17) |
| `/` | Скісна риска (*step*) | Задає крок ітерації по діапазону або повному діапазону зірочки: `<діапазон>/<крок>` | `*/10 * * * *`<br>`1-30/5 * * * *` | Кожні 10 хвилин (`0,10,20,30,40,50`)<br>Хвилини `1,6,11,16,21,26` |
| `~` | Тильда (*randomized offset*) | Випадковий зсув у межах інтервалу (розширення `cronie` та `dcron` для розмивання навантаження) | `0 0~4 * * *` | Щодня опівночі з випадковою затримкою до 4 годин |
| `L` | Last (*розширення*) | Останній день місяця або останній конкретний день тижня місяця (`5L` — остання п'ятниця) | `0 0 L * *` | Опівночі останнього дня календарного місяця (28/29/30/31) |
| `W` | Weekday (*розширення*) | Найближчий робочий день (понеділок–п'ятниця) до вказаного числа місяця | `0 0 15W * *` | Опівночі найближчого робочого дня до 15 числа |
| `#` | N-й день тижня (*розширення*) | Задає n-й день тижня у місяці у форматі `<день>#<номер>` (де 1–5 — номер входження) | `0 0 * * 5#3` | Опівночі третьої п'ятниці кожного місяця |

### Правило логічної взаємодії DOM та DOW (кон'юнкція проти диз'юнкції)

Стандарт POSIX.1 (IEEE Std 1003.1) та еталонний Vixie cron визначають спеціальний комбінований алгоритм перевірки полів **Дня Місяця (DOM)** та **Дня Тижня (DOW)**:

1. **Кон'юнкція (логічне «І»):** Якщо **хоча б одне** з полів DOM або DOW починається з символу зірочки (`*`), умова запуску вимагає одночасного виконання обох обмежень.
2. **Диз'юнкція (логічне «АБО»):** Якщо **обидва** поля (DOM і DOW) мають явно визначені обмеження (жодне з них не є `*`), завдання запускається, коли збігається умова дня місяця **АБО** умова дня тижня.

#### Таблиця істинності обчислення збігу дня (DOM проти DOW)

| Вираз поля DOM | Вираз поля DOW | Результуюча логіка зіставлення | Приклад виразу crontab | Умова фактичного спрацьовування |
| :--- | :--- | :--- | :--- | :--- |
| `*` (будь-який) | `*` (будь-який) | Кожен день | `0 3 * * *` | Щодня о 03:00 |
| `15` (явне значення) | `*` (будь-який) | Тільки обмеження DOM | `0 3 15 * *` | 15 числа кожного місяця о 03:00 |
| `*` (будь-який) | `5` (явне значення) | Тільки обмеження DOW | `0 3 * * 5` | Щоп'ятниці о 03:00 |
| `15` (явне значення) | `5` (явне значення) | **DOM АБО DOW (диз'юнкція)** | `0 3 15 * 5` | Кожного 15 числа місяця **АБО** щоп'ятниці о 03:00 |

```text
Приклад розкладу: 0 2 13 * 5 /usr/local/bin/backup.sh
DOM = 13 (явне число), DOW = 5 (п'ятниця, явне число).
Результат: запуск відбувається:
  1. Кожного 13-го числа місяця о 02:00 (незалежно від дня тижня);
  2. Щоп'ятниці о 02:00 (незалежно від календарного числа).
```

Внутрішній алгоритм перевірки у вихідному коді Vixie cron:
:::tabs
@tab C
```c
if ((entry->flags & DOM_STAR) || (entry->flags & DOW_STAR)) {
    day_match = dom_matches && dow_matches; /* Кон'юнкція: логічне І */
} else {
    day_match = dom_matches || dow_matches; /* Диз'юнкція: логічне АБО */
}
```
@tab C++
```cpp
if ((entry->flags & DOM_STAR) || (entry->flags & DOW_STAR)) {
    day_match = dom_matches && dow_matches; // Кон'юнкція: логічне І
} else {
    day_match = dom_matches || dow_matches; // Диз'юнкція: логічне АБО
}
```
:::

Якщо адміністратору потрібен запуск строго у «п'ятницю 13-го» (сувора кон'юнкція), поле DOW встановлюють у зірочку `*`, а перевірку дня тижня делегують командній оболонці через умовний вираз:
```crontab
0 2 13 * * [ "$(date +\%u)" -eq 5 ] && /usr/local/bin/backup.sh
```

### Вбудовані мнемонічні макроси розкладу

Замість п'яти часових полів на початку рядка дозволено використовувати одне з зарезервованих ключових слів. Демон `cron` автоматично замінює макрос на відповідну бітову маску під час розбору таблиці:

| Макрос | Еквівалентний вираз crontab | Точний момент виконання |
| :--- | :--- | :--- |
| `@reboot` | — | Одноразовий запуск відразу під час ініціалізації демона `cron` після завантаження операційної системи |
| `@yearly` / `@annually` | `0 0 1 1 *` | О 00:00 1 січня кожного календарного року |
| `@monthly` | `0 0 1 * *` | О 00:00 1 числа кожного календарного місяця |
| `@weekly` | `0 0 * * 0` | О 00:00 щонеділі |
| `@daily` / `@midnight` | `0 0 * * *` | О 00:00 щоночі |
| `@hourly` | `0 * * * *` | На початку кожної години на нульовій хвилині |

#### Особливості роботи макроса `@reboot`

- Демон `cron` реєструє факт запуску завдань `@reboot` під час своєї початкової ініціалізації.
- Якщо файл `crontab` оновлюється під час роботи системи за допомогою утиліти `crontab -e`, завдання з міткою `@reboot` **не виконуються повторно**, оскільки демон зберігає внутрішній прапорець пройденої фази завантаження.
- У разі ручного перезапуску самого сервісу `crond` через `systemctl restart crond` або отримання сигналу `SIGHUP`, поведінка залежить від реалізації: класичний Vixie cron не перезапускає `@reboot`, якщо демон виявляє наявність активного файлу стану або незмінний час завантаження системи `btime` у `/proc/stat`.

### Спеціальна обробка символу відсотка (`%`) та багаторядковий ввід

1. **Трансформація символу відсотка (`%`):** Усі не захищені зворотним слешем (`\`) символи `%` у полі команди замінюються планувальником на символи переходу на новий рядок (`\n`). Перший незахищений `%` розділяє командний рядок та потік стандартного вводу: усе, що стоїть після першого `%`, передається дочірньому процесу у потік `stdin`.
2. **Екранування зворотним слешем (`\%`):** Щоб передати символ `%` безпосередньо оболонці або аргументам команди (наприклад, утиліті `date`), його необхідно захищати як `\%`.
   - *Типова аварія конфігурації:* `0 1 * * * /usr/local/bin/backup.sh $(date +%Y-%m-%d)` — демон обірве команду на символі `%Y`, передавши залишок `Y-%m-%d)` на `stdin` запущеному скрипту.
   - *Коректний синтаксис:* `0 1 * * * /usr/local/bin/backup.sh $(date +\%Y-\%m-\%d)`.
3. **Багаторядковий ввід через `%`:**
   ```crontab
   0 8 * * 1 mail -s "Звіт за тиждень" admin@example.com%Вітаю!%Ось поточний статус системи.%-- Робот cron
   ```
   Команда `mail` отримає на потік `stdin` три окремі рядки тексту.
4. **Обов'язковий завершальний символ нового рядка (Trailing Newline):** За стандартом POSIX кожен коректний запис у файлі crontab зобов'язаний закінчуватися символом `\n`. Якщо останній рядок файлу не має завершального переводу рядка, класичний Vixie cron **ігнорує цей рядок без виведення попереджень чи повідомлень про помилку**.

### Переходи на літній/зимовий час (Daylight Saving Time, DST)

Під час сезонної зміни зміщення цивільного часу відносно UTC у часових поясах із літнім/зимовим часом (Daylight Saving Time, DST) системний астрономічний годинник `CLOCK_REALTIME` зазнає штучного стрибка. Це створює два граничні сценарії планування: пропуск цілої години в календарі (Spring Forward) та її подвійне проживання (Fall Back).

#### 1. Весняний перехід: пропуск годин (Spring Forward)

Під час переходу на літній час (наприклад, останньої неділі березня в поясі `Europe/Kyiv`) стрілки годинника о `01:59:59` переводяться на `03:00:00`. Годинний інтервал між `02:00:00` та `02:59:59` у локальному цивільному часі **фізично не настає**.

- **Механіка у демоні `cron` (Vixie cron та `cronie`):**
  1. Демон зберігає мітку часу попередньої хвилинної перевірки `time_t last_time`.
  2. Після чергового пробудження демон зчитує `time_t now = time(NULL)` та перетворює його у локальний час через `localtime_r()`.
  3. Якщо демон виявляє стрибок часу вперед (`now - last_time > 60` секунд або зміну прапорця `tm_isdst` з розривом у значеннях `tm_hour`), активується процедура компенсації пропущеного вікна.
  4. Планувальник генерує синтетичний послідовний ряд часових міток для кожної пропущеної хвилини в інтервалі `(last_time, now]` та зіставляє їх із зареєстрованими таблицями crontab.
  5. Усі завдання, призначені на пропущений проміжок (наприклад, щоденне резервне копіювання з розкладом `30 2 * * *`), запускаються **негайно в момент виявлення стрибка — о 03:00:00**. Це запобігає зриву регламентних системних завдань, проте може викликати короткочасний сплеск навантаження (Thundering Herd) через одночасний запуск усіх завдань, що потрапили у пропущену годину.
- **Механіка у підсистемі `systemd.timer` (`OnCalendar=`):**
  1. Календарний рушій systemd (функція `calendar_spec_next_usec()`) обчислює абсолютний час наступної активації в мікросекундах шкали `CLOCK_REALTIME` (UTC), використовуючи системну базу даних часових поясів IANA (`tzdata`) та виклики `mktime(3)` / `timegm(3)`.
  2. Якщо вираз задає запуск у пропущеному інтервалі (наприклад, `OnCalendar="*-*-* 02:30:00 Europe/Kyiv"`), бібліотека glibc під час виклику `mktime(&tm)` із недійсним локальним часом виявляє розрив сітки і автоматично нормалізує структуру `struct tm` до першого дійсного моменту цивільного часу після стрибка (до `03:00:00` або `03:30:00` залежно від конкретних правил зсуву зони).
  3. Утиліта діагностики `systemd-analyze calendar "*-*-* 02:30:00 Europe/Kyiv"` демонструє нормалізований момент спрацьовування у UTC, і дескриптор `timerfd` ядра Linux налаштовується саме на цю абсолютну точку часу.

#### 2. Осінній перехід: подвійне проходження годин (Fall Back)

Під час переходу на зимовий час (наприклад, останньої неділі жовтня) стрілки годинника о `02:59:59` переміщуються назад на `02:00:00`. Годинний інтервал між `02:00:00` та `02:59:59` повторюється двічі: спершу в режимі літнього часу (зміщення UTC+3, `tm_isdst == 1`), а потім у режимі стандартного зимового часу (зміщення UTC+2, `tm_isdst == 0`).

- **Механіка у демоні `cron` (захист від повторного виконання):**
  1. Демон фіксує зворотний стрибок годинника (`now < last_time`).
  2. Головна небезпека осіннього переходу — подвійний запуск завдань (наприклад, повторне списання коштів або перезапис архіву резервної копії).
  3. Для усунення дублювання класичний Vixie cron та `cronie` фіксують календарний номер доби та бітову маску або мітку часу останнього виконаного слоту.
  4. Якщо завдання з розкладом `30 2 * * *` уже було успішно запущено під час першого проходження години о 02:30 (літній час), демон блокує його повторну активацію під час другого проходження тієї самої години о 02:30 (зимовий час). Завдання не запускається вдруге, доки системний годинник остаточно не перетне позначку `03:00:00`.
- **Механіка у підсистемі `systemd.timer` (дизамбігуація часових поясів):**
  1. Менеджер systemd оперує внутрішніми таймерами за монотонною шкалою UTC, де кожна секунда є унікальною та неперервною (стрибків назад у шкалі UTC не існує).
  2. Неоднозначність локального часу (параметр `fold` у стандартах ISO 8601 та PEP 495) у системних таймерах розв'язується детерміновано: під час розрахунку майбутнього розкладу таймер призначається на перше хронологічне входження у часовий проміжок (fold 0, літній час).
  3. Після спрацьовування таймера сервіс переходить у стан `active`, а наступна календарна подія обчислюється рушієм `sd-event` строго від поточного моменту в майбутнє за віссю UTC. Оскільки наступна точка збігу з виразом `02:30:00` настане лише через добу (вже за стандартним часом), подвійний запуск у повторювану годину повністю виключається архітектурою менеджера.

#### 3. Виробнича рекомендація щодо часових поясів на серверах

Для усунення будь-яких ризиків, пов'язаних із переходами на літній/зимовий час, стандартом проектування виробничої інфраструктури (Production Infrastructure) є:
1. Встановлення системного годинника сервера виключно у незмінний часовий пояс [UTC](root:sys-unix/wall-clock-and-timezones):
   ```bash
   timedatectl set-timezone UTC
   ```
2. Явне задання `CRON_TZ=UTC` у заголовках користувацьких і системних таблиць crontab.
3. Використання явного суфікса `UTC` у календарних виразах systemd-таймерів:
   ```ini
   OnCalendar=*-*-* 02:30:00 UTC
   ```

## 2. Типи файлів crontab, файлова ієрархія та права доступу

Система розрізняє дві категорії розкладів: ізольовані користувацькі таблиці спулу та системні таблиці пакетів і адміністратора.

```text
/etc/
├── crontab                 # Головний системний розклад (формат із полем користувача)
├── cron.d/                 # Модульні системні розклади пакетів (формат із полем користувача)
├── cron.hourly/            # Каталог виконуваних скриптів (запуск щогодини через run-parts)
├── cron.daily/             # Каталог виконуваних скриптів (запуск щодня через run-parts)
├── cron.weekly/            # Каталог виконуваних скриптів (запуск щотижня через run-parts)
├── cron.monthly/           # Каталог виконуваних скриптів (запуск щомісяця через run-parts)
├── cron.allow              # Білий список користувачів для crontab(1)
└── cron.deny               # Чорний список користувачів для crontab(1)

/var/spool/cron/
├── crontabs/<username>     # Таблиці користувачів у Debian/Ubuntu (права 0600, root:crontab)
└── <username>              # Таблиці користувачів у RHEL/CentOS/Arch (права 0600, root:root)
```

### Порівняльна специфікація системних та користувацьких файлів

| Параметр | Користувацькі файли (`crontab -e`) | Системні файли (`/etc/crontab`, `/etc/cron.d/*`) |
| :--- | :--- | :--- |
| **Шлях у системі** | `/var/spool/cron/crontabs/<user>` (Debian)<br>`/var/spool/cron/<user>` (RHEL) | `/etc/crontab`<br>`/etc/cron.d/<ім'я_файлу>` |
| **Структура полів** | `хв год DOM mon DOW команда` (5 часових полів) | `хв год DOM mon DOW КОРИСТУВАЧ команда` (6 полів) |
| **Поле користувача** | Відсутнє (визначається іменем файлу в спулі) | Обов'язкове 6-те поле (UID/логін з `/etc/passwd`) |
| **Права доступу на файл** | `0600` або `0400`, власник — `<user>` | `0644`, власник — `root:root` |
| **Вимоги безпеки доступу** | Каталог спулу має права `01730` або `0700` | Файл **не повинен бути доступний на запис групі чи іншим** (`group/world-writable`). Демон відмовляється завантажувати небезпечні файли |
| **Механізм модифікації** | Виключно через утиліту `crontab(1)` | Пряме редагування адміністратором чи пакетами |
| **Перевірка змін демоном** | `stat()` на каталог спулу або `inotify` | `stat()` на `/etc/crontab` та `/etc/cron.d/` |

### Правила валідації імен файлів у `/etc/cron.d/` та утиліти `run-parts`

Файли, розміщені в `/etc/cron.d/`, а також виконувані сценарії у періодичних каталогах (`/etc/cron.daily/` тощо), обробляються утилітою `run-parts` або внутрішнім сканером демона згідно з суворими регулярними виразами:
- **Специфікація Debian/Ubuntu (`run-parts --lsbsysinit`):** Дозволено лише латинські літери обох регістрів, цифри, дефіси та символи підкреслення: `^[a-zA-Z0-9_-]+$`.
- **Заборонені символи:** Наявність крапки (`.`), тильди (`~`), коми чи спецсимволів призводить до **мовчазного ігнорування файлу**. Файли `backup.sh`, `cleanup.bak`, `service.dpkg-dist` чи `package.rpmsave` ніколи не будуть виконані.
- **Вимоги до скриптів у `/etc/cron.{hourly,daily,weekly,monthly}/`:**
  1. Наявність біта виконання (`chmod +x <файл>`);
  2. Наявність коректного шебанга у першому рядку (`#!/bin/sh` або `#!/bin/bash`);
  3. Відсутність розширень (`.sh`, `.py`, `.pl`).

## 3. Змінні середовища та конфігураційні директиви crontab

У заголовку будь-якого файлу crontab дозволено оголошувати змінні оточення у форматі `NAME=value`, `NAME="value"` або `NAME='value'`. Пробіли довкола знака `=` ігноруються. Значення змінних не піддаються розгортанню змінних оболонки (запис `PATH=$PATH:/opt/bin` збереже рядок `$PATH` буквально).

Оголошення змінних застосовуються зверху вниз: кожен рядок розкладу успадковує ті значення змінних, які були визначені вище за текстом таблиці. Це дозволяє перевизначати змінні для різних завдань у межах одного файлу.

| Змінна | Значення за замовчуванням | Призначення та поведінка системи |
| :--- | :--- | :--- |
| `SHELL` | `/bin/sh` | Командна оболонка, яку `cron` викликає для виконання рядка завдання (`$SHELL -c "команда"`). Запускається у неінтерактивному та не-login режимі (`~/.bashrc` не завантажується). Рекомендується `SHELL=/bin/bash` |
| `PATH` | `/usr/bin:/bin` | Список каталогів для пошуку бінарних файлів. Каталоги `/usr/local/bin`, `/sbin`, `/usr/sbin` та домашні папки за замовчуванням відсутні. Рекомендується явне задання: `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` |
| `MAILTO` | Власник файлу (або `root`) | Адреса електронної пошти для надсилання захоплених потоків `stdout` та `stderr` через системний MTA (`sendmail`). Якщо `MAILTO=""`, надсилання пошти повністю вимикається, вивід процесу скидається у `/dev/null` |
| `MAILFROM` | Власник процесу cron | Адреса відправника у заголовку `From:`, що формується поштовим агентом (підтримується у `cronie`) |
| `HOME` | Домашній каталог з `/etc/passwd` | Робочий каталог за замовчуванням. Демон викликає [chdir](root:sys-unix/process-model) у `$HOME` перед запуском команди |
| `LOGNAME` / `USER` | Власник таблиці | Встановлюється демоном автоматично з бази облікових записів [NSS](root:sys-unix/user-database-nss), перезапис користувачем ігнорується |
| `CRON_TZ` | Системний часовий пояс | Вказує локальний часовий пояс для інтерпретації п'яти часових полів розкладу цього конкретного файлу (наприклад, `CRON_TZ=UTC` або `CRON_TZ=Europe/Kyiv`). Автоматично виставляє змінну `TZ` для процесу-нащадка, якщо `TZ` не визначена явно |
| `TZ` | Системний часовий пояс | Встановлює часовий пояс для середовища виконання самої команди після того, як розклад уже обчислено |
| `CONTENT_TYPE` | `text/plain; charset=UTF-8` | Заголовок `Content-Type` MIME-повідомлення поштового звіту (наприклад, `text/html; charset=UTF-8`) |
| `CONTENT_TRANSFER_ENCODING` | `8bit` | Заголовок `Content-Transfer-Encoding` MIME-повідомлення (`8bit`, `quoted-printable`, `base64`) |
| `RANDOM_DELAY` | `0` | Максимальна випадкова затримка у хвилинах, що додається до часу запуску завдань (підтримується в `cronie`) |

## 4. Керування доступом, інтеграція з PAM, архітектура безпеки SELinux та AppArmor

Безпека підсистеми періодичного планування базується на багаторівневому комплексі механізмів авторизації, ізоляції файлових дескрипторів, контролю сесійних лімітів та мандатного розмежування доступу (Mandatory Access Control, MAC).

### Політика авторизації користувачів: cron.allow та cron.deny

Право звичайних користувачів на запуск утиліти `crontab(1)` та створення власних розкладів регламентується суворим алгоритмом перевірки конфігураційних списків доступу:

```text
               Чи існує файл /etc/cron.allow?
                     /               \
                   ТАК               НІ
                   /                   \
   Чи є користувач у списку?     Чи існує файл /etc/cron.deny?
         /          \                  /               \
       ТАК          НІ               ТАК               НІ
       /              \              /                   \
    ДОЗВОЛЕНО      ЗАБОРОНЕНО    Чи є в списку?      ДОЗВОЛЕНО
                                 /          \     (дефолт у більшості ОС;
                               ТАК          НІ     або ТІЛЬКИ root)
                               /              \
                          ЗАБОРОНЕНО       ДОЗВОЛЕНО
```

1. **Файли авторизації:** `/etc/cron.allow` та `/etc/cron.deny` містять рівно по одному імені користувача (логіну) на рядок. Порожні рядки, коментарі та пробіли не допускаються.
2. **Абсолютний пріоритет білого списку:** Наявність файлу `/etc/cron.allow` повністю вимикає дію `/etc/cron.deny`. Якщо `cron.allow` існує на файловій системі, але є порожнім, користуватися `crontab` заборонено всім обліковим записам, крім суперкористувача `root`.
3. **Поведінка за замовчуванням:** Якщо обидва файли відсутні, поведінка залежить від збірки дистрибутива: у більшості Linux-систем доступ надається всім користувачам, тоді як у захищених Unix-системах (наприклад, Solaris або загартованих BSD-профілях) доступ блокується для всіх звичайних користувачів.

### Моделі прав доступу та ізоляції каталогів спулу

Для запобігання підміні конфігурацій, витоку конфіденційних даних та атакам типу «гонка перевірки та використання» (Time-of-Check to Time-of-Use, TOCTOU) каталоги спулу користувацьких таблиць реалізують дві відмінні моделі ізоляції:

| Параметр | Модель Debian / Ubuntu | Модель RHEL / CentOS / Fedora / Arch |
| :--- | :--- | :--- |
| **Каталог спулу** | `/var/spool/cron/crontabs/` | `/var/spool/cron/` |
| **Права доступу на каталог** | `01730` (`drwx-wx-t`) | `0700` (`drwx------`) |
| **Власник каталогу** | `root:crontab` | `root:root` |
| **Бінарний файл `crontab`** | `/usr/bin/crontab` із бітом [SetGID](root:sys-unix/permission-bits) (`02755`, `root:crontab`) | `/usr/bin/crontab` із бітом [SetUID](root:sys-unix/permission-bits) (`04755`, `root:root`) |
| **Права на файл таблиці** | `0600` (`-rw-------`), власник `<user>:crontab` | `0600` (`-rw-------`), власник `<user>:<user>` |
| **Механізм захисту** | Sticky bit (`01000`) блокує видалення/перейменування чужих файлів користувачами групи | Повна відсутність доступу на читання/запис для будь-кого, крім `root` |

У моделі Debian біт прилипання (Sticky Bit, `01000` / `S_ISVTX`) на каталозі `/var/spool/cron/crontabs/` відіграє фундаментальну роль безпеки: попри те, що група `crontab` має право запису (`-wx`) для створення нових таблиць утилітою `crontab(1)`, ядро Linux дозволяє операції `unlink()` та `rename()` виключно власнику конкретного файлу або суперкористувачу `root`. Це унеможливлює видалення чи пошкодження чужих розкладів через скомпрометований процес із груповими правами `crontab`.

### Життєвий цикл сесій PAM (Pluggable Authentication Modules)

Перед виконанням кожного регулярного завдання демон `crond` ініціалізує повноцінний стек аутентифікації та обліку через інтерфейс PAM (`/etc/pam.d/crond` або `/etc/pam.d/cron`):

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                       СТЕК PAM У ДЕМОНІ CROND                               │
│                                                                             │
│   1. pam_start("crond", username, &conv, &pamh)                            │
│   2. pam_acct_mgmt(pamh, PAM_SILENT)  ──► перевірка блокування в shadow    │
│   3. pam_setcred(pamh, PAM_ESTABLISH_CRED)                                 │
│   4. pam_open_session(pamh, PAM_SILENT)                                     │
│      ├─► pam_limits.so   ──► застосування limits.conf (nofile, nproc, mem)   │
│      ├─► pam_env.so      ──► завантаження /etc/security/pam_env.conf        │
│      └─► pam_selinux.so  ──► обчислення та встановлення контексту безпеки   │
│   5. [Виконання корисного навантаження через fork/exec]                     │
│   6. pam_close_session(pamh, PAM_SILENT) ──► закриття аудиту сесії         │
│   7. pam_setcred(pamh, PAM_DELETE_CRED)                                    │
│   8. pam_end(pamh, status)                                                  │
└─────────────────────────────────────────────────────────────────────────────┘
```

1. **Перевірка стану облікового запису (`pam_acct_mgmt`):** Демон верифікує валідність облікового запису в системній базі `/etc/shadow`. Якщо термін дії пароля вичерпано (`password expired`), обліковий запис заблоковано символом `!` у полі хешу пароля, або користувачу призначено оболонку `/sbin/nologin` чи `/bin/false`, функція повертає код помилки `PAM_ACCT_EXPIRED` або `PAM_AUTH_ERR`. Демон негайно скасовує запуск завдання та генерує запис у системний журнал `syslog`.
2. **Контроль системних лімітів ресурсів (`pam_limits.so`):** Модуль зчитує директиви з `/etc/security/limits.conf` та каталогу `/etc/security/limits.d/`. Перед викликом `execve` дочірній процес встановлює м'які та жорсткі обмеження ядра через системний виклик `setrlimit()`: максимальний обсяг віртуальної пам'яті (`RLIMIT_AS`), ліміт відкритих файлових дескрипторів (`RLIMIT_NOFILE`), максимальну кількість процесів користувача (`RLIMIT_NPROC`) та пріоритет планувальника процесора (`RLIMIT_NICE`).
3. **Фіксація сесійного аудиту:** Модуль `pam_audit.so` реєструє подію відкриття та закриття сесії в підсистемі аудиту ядра Linux (Linux Audit Daemon, `auditd`), фіксуючи `auid` (Audit UID), `pid` та контекст безпеки.

### Архітектура мандатного доступу SELinux у підсистемі cron

У дистрибутивах із підтримкою SELinux (RHEL, Fedora, Rocky Linux, Debian із увімкненою політикою) безпека cron реалізується на рівні Type Enforcement (TE), переходів доменів (Domain Transitions) та багатокатегорійного розмежування (Multi-Category Security, MCS).

```text
┌───────────────────────────┐         execve(/usr/bin/crontab)        ┌───────────────────────────┐
│     user_t / unconfined_t │────────────────────────────────────────►│         crontab_t         │
│  (сеанс користувача)      │                                         │ (модифікація cron_spool_t)│
└───────────────────────────┘                                         └───────────────────────────┘
                                                                                    │
                                                                                    ▼ st_mtime / inotify
┌───────────────────────────┐         domain transition (execle)      ┌───────────────────────────┐
│       system_cronjob_t    │◄────────────────────────────────────────┤          crond_t          │
│   (завдання /etc/cron.*)  │                                         │   (фоновий демон crond)   │
└───────────────────────────┘                                         └─────────────┬─────────────┘
                                                                                    │
                                                                                    ▼ domain transition (pam_selinux)
                                                                      ┌───────────────────────────┐
                                                                      │      user_cronjob_t       │
                                                                      │ (ізольований контекст user│
                                                                      │   рівень s0:c10,c20)      │
                                                                      └───────────────────────────┘
```

#### 1. Типи безпеки та переходи доменів (Domain Transitions)

- **Контекст демона (`crond_t`):** Головний процес демона запускається в захищеному системному домені `system_u:system_r:crond_t:s0-s0:c0.c1023`. Цей домен має права на сканування каталогів спулу, зміну UID/GID, взаємодію з PAM та виконання системних перевірок.
- **Контекст утиліти редагування (`crontab_t`):** Бінарний файл `/usr/bin/crontab` має контекст `system_u:object_r:crontab_exec_t:s0`. Коли користувач у домені `user_t` або `unconfined_t` викликає `crontab`, політика SELinux виконує автоматичний перехід домену в `crontab_t`. Домен `crontab_t` має суворо обмежені дозволи: запис дозволено виключно у файли спулу з типом `cron_spool_t` (`/var/spool/cron/`), прямий доступ до довільних системних файлів повністю заблоковано.
- **Контексти виконання завдань:**
  - Системні завдання з `/etc/crontab` та `/etc/cron.d/` переходять у домен `system_u:system_r:system_cronjob_t:s0`.
  - Користувацькі завдання переходять у цільовий домен користувача: `user_u:user_r:user_cronjob_t:s0` (для звичайних обмежених облікових записів) або `unconfined_u:unconfined_r:unconfined_cronjob_t:s0`.

#### 2. Встановлення контексту виконання через libselinux

Перед заміщенням образу процесу оболонкою через `execle()` демон `crond` або модуль `pam_selinux.so` виконує процедуру визначення та фіксації контексту безпеки:
1. Запитує зіставлення користувача Linux із користувачем SELinux через функцію `getseuserbyname(username, &seuser, &level)`.
2. Отримує список допустимих контекстів через `get_default_context_with_level(seuser, level, NULL, &scon)`.
3. Викликає системну функцію `setexeccon(scon)`, яка записує рядок цільового контексту безпеки у спеціальний файл дескриптора процесу `/proc/thread-self/attr/exec` (або `/proc/self/attr/exec`).
4. Наступний системний виклик `execve()` атомарно переводить процес у новий домен SELinux.

#### 3. Багатокатегорійна ізоляція (Multi-Category Security, MCS)

У багатокористувацьких та контейнеризованих середовищах SELinux використовує категорії MCS (`c0.c1023`). Кожному користувачу призначається унікальна комбінація категорій (наприклад, `s0:c42,c105`). Навіть якщо завдання двох різних користувачів виконуються в межах одного домену `user_cronjob_t`, ядро Linux блокує будь-яку спробу читання файлів, надсилання сигналів або використання каналів IPC між процесами з неперетинними категоріями MCS.

#### 4. Обмеження ядерних привілеїв (Linux Capabilities)

Під час запуску демон `crond` володіє розширеним набором привілеїв ядра: `CAP_SETUID` (зміна UID), `CAP_SETGID` (зміна GID та груп), `CAP_DAC_OVERRIDE` (доступ до файлів спулу), `CAP_AUDIT_WRITE` (запис логів аудиту), `CAP_SYS_RESOURCE` (застосування лімітів пам'яті та дескрипторів) та `CAP_FOWNER`.

Перед виконанням користувацького коду демон повністю скидає всі активні та дозволені привілеї (`Effective` та `Permitted` capabilities). Крім того, сучасні версії `cronie` скидають маску обмеження ядерних привілеїв процесу (Capability Bounding Set) через системний виклик `prctl(PR_CAPBSET_DROP, cap)`, що унеможливлює отримання додаткових прав через setuid-бінарники всередині запланованого завдання.

### Архітектура ізоляції AppArmor

У дистрибутивах, що використовують систему AppArmor (Ubuntu, Debian, openSUSE), захист демона базується на шляховому мандатному профілі `/etc/apparmor.d/usr.sbin.cron`.

1. **Режими роботи профілю:** Профіль може перебувати у стані примусового блокування (`enforce`) або аудиту порушень (`complain`).
2. **Правила доступу до файлової ієрархії:**
   ```text
   /usr/sbin/cron {
     # Ядерні привілеї
     capability setuid,
     capability setgid,
     capability dac_override,
     capability audit_write,
     capability sys_resource,

     # Доступ до конфігурацій та спулу
     /etc/cron*/** r,
     /etc/crontab r,
     /var/spool/cron/crontabs/* r,
     /var/spool/cron/atjobs/* r,

     # Службові файли та логування
     /var/run/crond.pid rw,
     /var/log/cron.log w,

     # Переходи виконання (Execution Transitions)
     /bin/sh Px,
     /bin/bash Px,
     /usr/bin/crontab cx,
   }
   ```
3. **Прапорці переходу профілів (Transition Modes):**
   - `Px` (*Discrete Profile Execution with Scrubbed Environment*) — виконання командної оболонки з переходом у спеціалізований ізольований профіль та обов'язковим очищенням небезпечних змінних оточення (`LD_PRELOAD`, `LD_LIBRARY_PATH`).
   - `cx` (*Child Profile Transition*) — перехід у вкладений підпрофіль (наприклад, окремий профіль для утиліти `crontab`).
   - `Ux` (*Unconfined Execution*) — виконання без обмежень профілю (застосовується виключно для довірених системних бінарників).
4. **Перевірка стану ізоляції:** Поточний активний профіль AppArmor для будь-якого процесу інспектується через віртуальний файл `/proc/<pid>/attr/current`.

### Специфікація обмеження ресурсів та взаємодія з cgroups v2 через pam_systemd

У сучасних Linux-дистрибутивах із підтримкою уніфікованої ієрархії контрольних груп [cgroups v2](root:sys-unix/process-model) підсистема періодичного планування інтегрується з механізмами обліку та обмеження системних ресурсів ядра (пам'ять, процесорні квоти, операції введення-виведення та ліміти процесів). Це усуває критичну вразливість класичного `cron`, за якої неконтрольований витік пам'яті або зациклення у фоновому скрипті призводили до вичерпання ресурсів усієї операційної системи (Denial of Service).

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                    ІЄРАРХІЯ CGROUPS V2 ТА ІНТЕГРАЦІЯ PAM                    │
│                                                                             │
│   /sys/fs/cgroup/                                                           │
│   ├── system.slice/                                                         │
│   │   └── cron.service/ ──────────► Системні завдання (/etc/crontab,        │
│   │       ├── memory.max            /etc/cron.d/*) за замовчуванням         │
│   │       ├── cpu.max                                                       │
│   │       └── io.weight                                                     │
│   │                                                                         │
│   └── user.slice/                                                           │
│       └── user-1000.slice/ ───────► Користувацькі завдання (crontab -e)     │
│           ├── user@1000.service/    делегуються через pam_systemd.so        │
│           │   └── session-c2.scope/                                         │
│           │       ├── memory.max                                            │
│           │       ├── cpu.max                                               │
│           │       └── pids.max                                              │
│           └── custom-cron.slice/ ─► Ізольовані зрізи (systemd-run --slice) │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 1. Архітектура делегування сесій через pam_systemd

Коли демон `crond` ініціалізує стек PAM перед запуском завдання користувача, модуль `pam_systemd.so` виконує процедуру реєстрації нової сесії в системному менеджері:
1. **D-Bus виклик до systemd-logind:** Модуль надсилає повідомлення `CreateSession()` до системної служби `systemd-logind` через системну шину D-Bus.
2. **Розміщення у дереві зрізів (Slice Units):**
   - **Системні завдання (`/etc/crontab`, `/etc/cron.d/`):** Виконуються як прямі нащадки процесу `crond`. Якщо демон запущено як системний юніт `cron.service` (або `crond.service`), усі системні завдання за замовчуванням успадковують контрольну групу `/sys/fs/cgroup/system.slice/cron.service/`. Сумарні ресурси всіх паралельно виконуваних системних завдань обмежуються лімітами цього юніта.
   - **Користувацькі завдання (`crontab -e`):** За наявності `pam_systemd.so` демон створює транзієнтний сесійний скоуп-юніт (`session-<ID>.scope`) усередині призначеного для користувача зрізу `/sys/fs/cgroup/user.slice/user-<UID>.slice/`. Це гарантує повну ізоляцію завдань користувачів від системних служб.
3. **Увімкнення контролерів у cgroups v2:** Для керування дочірніми групами кореневий або проміжний зріз зобов'язаний мати активовані контролери у файлі `cgroup.subtree_control`:
   ```bash
   echo "+memory +cpu +io +pids" > /sys/fs/cgroup/user.slice/cgroup.subtree_control
   ```

#### 2. Специфікація контролерів cgroups v2 та інтерфейсних файлів ядра

| Контролер ядра | Файл інтерфейсу cgroups v2 | Директива systemd | Тип даних / Діапазон | Системна дія та семантика ядра |
| :--- | :--- | :--- | :--- | :--- |
| **Пам'ять (`memory`)** | `memory.max` | `MemoryMax=` | Байти (або `K`, `M`, `G`) / `max` | **Жорсткий ліміт пам'яті.** При досягненні ліміту ядро виконує витіснення сторінкового кешу (reclaim). Якщо пам'ять не звільнено, активується cgroup OOM Killer, який завершує процес завдання сигналом `SIGKILL` |
| **Пам'ять (`memory`)** | `memory.high` | `MemoryHigh=` | Байти (або `K`, `M`, `G`) / `max` | **М'який регуляторний ліміт.** При перевищенні ліміту процес не вбивається, але ядро сповільнює виділення пам'яті (throttling) і змушує процес виконувати пряме очищення сторінок (direct reclaim) |
| **Пам'ять (`memory`)** | `memory.swap.max` | `MemorySwapMax=` | Байти (або `K`, `M`, `G`) / `max` | **Ліміт простору підкачки.** Обмежує максимальний обсяг swap, який дозволено використати контрольній групі, запобігаючи вичерпанню загальносистемного swap |
| **Пам'ять (`memory`)** | `memory.current` | — | Байти (тільки читання) | Поточний обсяг використаної оперативної пам'яті (RSS + Page Cache + Kernel Memory) |
| **Пам'ять (`memory`)** | `memory.events` | — | Ключ-значення (тільки читання) | Лічильники аварійних подій ядра: `low`, `high`, `max`, `oom`, `oom_kill` |
| **Процесор (`cpu`)** | `cpu.max` | `CPUQuota=` | `$MAX $PERIOD` (мкс) | **Абсолютна квота планувальника CFS.** Задає максимальний час CPU за період `$PERIOD` (дефолтний період — `100000` мкс = 100 мс). `50000 100000` відповідає `CPUQuota=50%` (0.5 ядра), `200000 100000` відповідає `CPUQuota=200%` (2 повноцінних ядра) |
| **Процесор (`cpu`)** | `cpu.weight` | `CPUWeight=` | `1–10000` (дефолт `100`) | **Пропорційна вага розподілу CPU.** Визначає пріоритет розподілу процесорних квантів між змагальними групами під час 100% завантаження ядер |
| **Процесор (`cpu`)** | `cpu.stat` | — | Ключ-значення (тільки читання) | Метрики тротлінгу: `usage_usec`, `user_usec`, `system_usec`, `nr_periods`, `nr_throttled`, `throttled_usec` (час примусового простою процесу) |
| **Ввід-вивід (`io`)** | `io.weight` | `IOWeight=` | `1–10000` (дефолт `100`) | **Пропорційна вага дискового I/O.** Задає пріоритет черги введення-виведення для планувальника BFQ |
| **Ввід-вивід (`io`)** | `io.max` | `IOReadBandwidthMax=`<br>`IOWriteBandwidthMax=`<br>`IOReadIOPSMax=`<br>`IOWriteIOPSMax=` | `$MAJ:$MIN rbps=$N wbps=$M riops=$X wiops=$Y` | **Абсолютні ліміти швидкості та операцій I/O** для конкретного блокового пристрою (`$MAJ:$MIN`). Наприклад, `8:0 wbps=10485760` обмежує швидкість запису на `/dev/sda` до 10 МБ/с |
| **Ввід-вивід (`io`)** | `io.stat` | — | Ключ-значення (тільки читання) | Повна статистика операцій: `rbytes`, `wbytes`, `rios`, `wios`, `dbytes`, `dios` |
| **Процеси (`pids`)** | `pids.max` | `TasksMax=` | Ціле число / `max` | **Максимальна кількість процесів та потоків.** Захищає систему від розмноження fork-бомб у регулярних сценаріях |
| **Процеси (`pids`)** | `pids.current` | — | Ціле число (тільки читання) | Поточна активна кількість потоків (tasks) у групі |

#### 3. Порівняльний аналіз механізмів обмеження: cgroups v2 проти pam_limits.so

| Характеристика | Класичний `pam_limits.so` (`setrlimit`) | Контрольні групи `cgroups v2` |
| :--- | :--- | :--- |
| **Об'єкт застосування** | Окремий індивідуальний процес | **Усе ієрархічне дерево процесів** (батько + усі нащадки) |
| **Контроль пам'яті** | `RLIMIT_AS` обмежує віртуальний адресний простір, `RLIMIT_RSS` ігнорується сучасними ядрами Linux | `memory.max` контролює **реальні фізичні сторінки (RSS + сторінковий кеш + ядра пам'ять)** |
| **Сумісність із сучасними мовами** | **Ламає рантайми:** Go, Rust, Java, Node.js виділяють великі віртуальні адресні простори через `mmap(MAP_NORESERVE)` і миттєво падають при низькому `RLIMIT_AS` | **Повна сумісність:** обмежується виключно фактично виділена фізична пам'ять |
| **Поведінка при перевищенні пам'яті** | `malloc()` / `mmap()` повертає `ENOMEM`, що викликає аварійний крах програми | Ядро спершу виконує витіснення сторінкового кешу; при дефіциті активує cgroup OOM Killer тільки для цієї групи |
| **Керування процесором (CPU)** | Тільки зміна пріоритету `nice` (`RLIMIT_NICE`), відсутність квот | **Точне регулювання квот (CFS Bandwidth Control):** гарантує обмеження споживання процесора (наприклад, строго 1.5 ядра) через тротлінг |
| **Керування дисковим I/O** | **Повністю відсутнє** | Зважений поділ пропускної здатності (`io.weight`) та ліміти швидкості/IOPS (`io.max`) |
| **Контроль кількості процесів** | `RLIMIT_NPROC` враховує процеси користувача **глобально по всій ОС**, блокуючи запуск завдань при активності інших сесій | `pids.max` ізолює ліміт потоків **виключно в межах поточної групи/завдання** |

#### 4. Практичні методи обмеження ресурсів для cron-завдань

##### Метод A. Глобальне обмеження системної служби cron через drop-in конфігурацію systemd

Для запобігання перевантаженню сервера системними завданнями з `/etc/crontab` створюється файл конфігурації `/etc/systemd/system/cron.service.d/10-resource-limits.conf`:

```ini
[Service]
# Обмеження сумарної пам'яті для всіх системних cron-завдань до 4 ГБ
MemoryAccounting=yes
MemoryHigh=3.5G
MemoryMax=4G

# Обмеження сумарного використання процесора до 2 повноцінних ядер
CPUAccounting=yes
CPUQuota=200%
CPUWeight=50

# Обмеження дискового вводу-виводу
IOAccounting=yes
IOWeight=50

# Захист від fork-бомб: максимум 500 одночасних процесів
TasksAccounting=yes
TasksMax=500
```

Після збереження конфігурація застосовується командами:
```bash
systemctl daemon-reload
systemctl restart cron.service
```

##### Метод B. Динамічне обгортання важких завдань через `systemd-run` у таблиці crontab

Для ізоляції ресурсомістких завдань (наприклад, нічного бекапу бази даних або перерахунку пошукових індексів) без зміни глобальних налаштувань використовується запуск у транзієнтному зрізі через `systemd-run --scope`:

```crontab
# Щоночі о 02:00: запуск бекапу з жорстким лімітом 2 ГБ RAM, 80% одного ядра CPU та лімітом запису 25 МБ/с на /dev/sdb
0 2 * * * root systemd-run --scope --slice=cron-backup.slice -p MemoryMax=2G -p MemoryHigh=1.8G -p CPUQuota=80% -p IOWriteBandwidthMax="/dev/sdb 26214400" /usr/local/bin/backup-database.sh
```

##### Метод C. Моніторинг та діагностика вичерпання лімітів cgroups v2

Утиліти ядра дозволяють аналізувати фактичне навантаження та випадки спрацьовування обмежень:

```bash
# 1. Перевірка поточного споживання пам'яті та кількості OOM-подій
cat /sys/fs/cgroup/system.slice/cron.service/memory.current
cat /sys/fs/cgroup/system.slice/cron.service/memory.events
# Приклад виводу memory.events:
# low 0
# high 142
# max 12
# oom 2
# oom_kill 2

# 2. Перевірка процесорного тротлінгу (час затримки виконання у мікросекундах)
cat /sys/fs/cgroup/system.slice/cron.service/cpu.stat
# Приклад виводу cpu.stat:
# usage_usec 481290334
# user_usec 391200112
# system_usec 90090222
# nr_periods 12050
# nr_throttled 840
# throttled_usec 24501200

# 3. Інспекція дерева процесів та їхніх зрізів у реальному часі
systemd-cgls /system.slice/cron.service

# 4. Моніторинг споживання ресурсів у термінальному інтерфейсі
systemd-cgtop
```

## 5. Довідник командного інтерфейсу утиліти crontab(1)

Утиліта `crontab(1)` встановлюється з бітом [setgid/setuid](root:sys-unix/permission-bits) (`crontab` або `root`) для безпечного запису в захищений каталог спулу.

### Опції командного рядка

| Опція | Аргумент | Опис операції |
| :--- | :--- | :--- |
| `-e` | — | Відкриває таблицю розкладу поточного користувача у текстовому редакторі (визначається змінними `$VISUAL` або `$EDITOR`, за замовчуванням `/usr/bin/editor`). Перед збереженням утиліта перевіряє синтаксичну коректність |
| `-l` | — | Виводить поточний вміст таблиці розкладу користувача на стандартний вивід (`stdout`) |
| `-r` | — | Повністю видаляє таблицю розкладу поточного користувача зі спулу |
| `-i` | — | Інтерактивний режим: запитує підтвердження `y/n` перед видаленням таблиці (використовується разом із `-r`) |
| `-u` | `<username>` | Вказує цільового користувача, чию таблицю слід редагувати, переглянути чи видалити. Доступно лише суперкористувачу `root` |
| `-s` | — | Додає контекст безпеки SELinux до файлу таблиці під час збереження (у дистрибутивах із підтримкою SELinux) |
| `<шлях_до_файлу>` | Файл на диску або `-` | Встановлює розклад безпосередньо з вказаного текстового файлу або зі стандартного вводу `stdin` |

### Механізм безпечного атомарного оновлення

Під час виклику `crontab -e` утиліта реалізує такий ланцюжок дій:
1. Створює захищений тимчасовий файл у каталозі `/tmp/` (наприклад, `/tmp/crontab.XXXXXX`) із правами `0600`.
2. Копіює поточний вміст таблиці користувача зі спулу в тимчасовий файл.
3. Запускає редактор через системні виклики `fork()`/`exec()`.
4. Після закриття редактора зчитує файл, виконує парсинг полів та перевірку синтаксису.
5. Якщо знайдено синтаксичні помилки, утиліта виводить повідомлення із номером рядка і пропонує повторно відредагувати файл (`y/n`).
6. У разі успішної валідації файл атомарно переміщується у спул через системний виклик `rename()`, після чого оновлюється `st_mtime` каталогу для оповіщення демона через `stat()` або `inotify`.

### Коди завершення (Exit Codes) crontab(1)

| Код | Символьна назва | Причина повернення |
| :--- | :--- | :--- |
| `0` | `EXIT_SUCCESS` | Успішне виконання операції (встановлення, виведення, видалення таблиці) |
| `1` | `EXIT_FAILURE` | Помилка синтаксису розкладу, відсутність прав доступу, користувач заблокований у `cron.deny` або відсутній у `cron.allow` |

## 6. Внутрішній контракт та архітектура демона crond

Демон `crond` функціонує як фонова системна служба без керуючого термінала, відповідальна за постійний моніторинг конфігураційних файлів, розрахунок інтервалів пробудження, безпечну ініціалізацію контексту виконання дочірніх процесів та доставку діагностичного виводу.

### Внутрішній цикл синхронізації та виявлення оновлень (sleep проти inotify)

Головний цикл демона квантується інтервалом в **одну астрономічну хвилину**. Для забезпечення високої точності запуску та виключення фазового дрейфу розкладу планувальник реалізує спеціальний алгоритм розрахунку сну:

1. **Компенсація фазового дрейфу:** Замість фіксованої паузи `sleep(60)`, яка неминуче накопичувала б затримку через накладні витрати CPU та операцій введення-виведення на кожній ітерації, демон зчитує системний годинник `time(NULL)`, перетворює його у структуру `struct tm` через `localtime_r()` і розраховує точну кількість секунд до наступної нульової секунди хвилини: `sleep_seconds = 60 - tm_now.tm_sec`.
2. **Періодичне опитування (stat polling) у класичному Vixie cron:** Під час кожного хвилинного пробудження демон викликає системний виклик `stat()` для каталогів спулу `/var/spool/cron/crontabs/`, системного каталогу `/etc/cron.d/` та файлу `/etc/crontab`. Якщо час останньої модифікації `st_mtime` змінився, демон перечитує конфігурацію та інвалідує відповідні структури в пам'яті.
3. **Реактивний моніторинг (Linux inotify) у modern-реалізаціях (`cronie`):** Для мінімізації дискового I/O демон ініціалізує дескриптор `inotify_init1(IN_CLOEXEC | IN_NONBLOCK)` та реєструє точки спостереження через `inotify_add_watch()` на каталоги спулу та системні каталоги для маски подій `IN_MODIFY | IN_CREATE | IN_DELETE | IN_ATTRIB | IN_MOVED_TO | IN_MOVED_FROM | IN_CLOSE_WRITE`. У цьому режимі перечитування конфігурацій відбувається миттєво після збереження файлу без очікування настання чергової хвилини.
4. **Бітові маски бази завдань (`cron_db`):** Для виключення повільного рядкового парсингу щохвилини розібрані розклади зберігаються в оперативній пам'яті у вигляді бітових масок (хвилини: 60 біт, години: 24 біти, дні місяця: 32 біти, місяці: 12 біт, дні тижня: 8 біт). Зіставлення поточного часу з розкладом завдання зводиться до швидкої побітової перевірки.

```c
    if (!((entry->minute_mask >> t->tm_min) & 1)) return false;
    if (!((entry->hour_mask >> t->tm_hour) & 1)) return false;
```

### Порівняльний аналіз архітектур планування: дискретне опитування (Polling) проти hrtimer та timerfd

Фундаментальна архітектурна відмінність між класичним планувальником `cron` та сучасною підсистемою `systemd.timer` полягає у підході до квантування часу, взаємодії з апаратними таймерами ядра та керуванні станами енергозбереження центрального процесора.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                    ПОРІВНЯННЯ АРХІТЕКТУРНИХ МОДЕЛЕЙ ЧАСУ                    │
│                                                                             │
│   1. МОДЕЛЬ ОПИТУВАННЯ CRON (POLLING):                                      │
│      CPU C6/C7 ──► [Пробудження щохвилини] ──► stat() ──► Пошук у базі      │
│      (Примусовий вихід з глибокого сну кожні 60 с навіть при порожній черзі) │
│                                                                             │
│   2. МОДЕЛЬ СИСТЕМНИХ ТАЙМЕРІВ SYSTEMD (HRTIMER + TIMERFD):                 │
│      CPU C6/C7 ──► [Безперервний глибокий сон] ────────────────────────────┐│
│                    (Tickless ядро, APIC TSC-Deadline не програмується      ││
│                     до точного моменту настання або батчу)                 ││
│                                                                            ▼│
│      Подія timerfd ──► epoll_wait(sd-event) ──► Активація .service-юніта   │
│      (Наносекундна точність + CPU Wakeup Coalescing через AccuracySec=)     │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 1. Модель опитування cron: дискретність 1 хвилина та вплив на C-states CPU

Класичний демон `cron` використовує модель дискретного періодичного опитування (*polling*):
- **Фіксований хвилинний крок:** Демон примусово засинає на інтервал `sleep(60 - tm_sec)`. Дискретність планування обмежена `60` секундами (60 000 000 000 нс). Будь-які суб-хвилинні інтервали (секунди, мілісекунди) у цій моделі неможливі без кардинальної перебудови архітектури.
- **Вплив на процесорні стани енергозбереження (C-States):**
  - Сучасні мікропроцесори архітектур x86_64 та ARM64 підтримують ієрархію станів спокою ядер: від активного стану C0 до глибоких енергозберігаючих станів C1 (Halt), C3 (Sleep), C6 (Power Gated, з вимиканням живлення ядра та скиданням кешів L1/L2) та C7/C8.
  - Щомилинний цикл `cron` генерує регулярні переривання таймера ядра, змушуючи процесорні ядра примусово повертатися зі стану C6/C7 у стан C0.
  - Навіть якщо у розкладі немає жодного запланованого завдання, процес `crond` прокидається, виконує системні виклики `stat()`, перевіряє бітові маски і знову засинає. Це викликає додаткові витрати на перемикання контексту ядра (Context Switch Overhead), забруднення процесорних кешів (Cache Thrashing) та підвищене енергоспоживання (CPU Wakeup Storms), що особливо критично для хмарних гіпервізорів із сотнями віртуальних машин на хост або вбудованих автономних пристроїв.
- **Прив'язка до CLOCK_REALTIME:** Класичний `cron` оперує виключно астрономічним годинником `CLOCK_REALTIME`, через що будь-яка стрибкоподібна корекція часу (через NTP, команду `date` або перехід на літній/зимовий час) вимагає спеціальної евристичної обробки пропущених або повторюваних хвилин.

#### 2. Модель systemd-timers: hrtimer, timerfd та наносекундна дискретність

Підсистема `systemd.timer` повністю відмовляється від опитування і базується на підсистемі **High-Resolution Timers (`hrtimer`)** ядра Linux:
- **Червоно-чорні дерева hrtimer:** У ядрі Linux для кожного процесора створюються черги `struct hrtimer_clock_base`, організовані у вигляді самобалансованих червоно-чорних дерев (Red-Black Trees). Таймери впорядковані за наносекундним часом спрацьовування (`expires`).
- **Апаратне програмування таймерів:** Ядро розраховує час найближчої події у дереві та одноразово програмує апаратний таймер процесора (Local APIC Timer у режимі TSC-Deadline на x86_64 або ARM Generic Timer на ARM64).
- **Підтримка Tickless Kernel (`CONFIG_NO_HZ_IDLE` / `CONFIG_NO_HZ_FULL`):** Якщо у системі немає активних таймерів на найближчий час, періодичний системний тік ядра вимикається. Процесорні ядра залишаються у стані глибокого сну C6/C7 годинами без жодного паразитного пробудження (0% Idle CPU Overhead).
- **Реактивне мультиплексування через timerfd:** Диспетчер подій `sd-event` у складі `systemd` проектує стан таймера на файловий дескриптор `timerfd` і реєструє його в системному виклику `epoll_wait()`. Системний менеджер не витрачає процесорний час на цикл сну, реагуючи виключно на появу події готовності `EPOLLIN`.

#### 3. Оптимізація пробудження процесора: коалесценція таймерів (CPU Wakeup Coalescing)

Для запобігання надмірній фрагментації пробуджень CPU через тисячі незалежних системних таймерів `systemd` використовує механізм **коалесценції таймерів (CPU Wakeup Coalescing)** через директиву `AccuracySec=` (за замовчуванням `1min`):

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                 КОАЛЕСЦЕНЦІЯ ПРОБУДЖЕННЯ ПРОЦЕСОРА (COALESCING)             │
│                                                                             │
│   Без коалесценції (точні таймери):                                         │
│   Таймер A ──► Пробудження CPU (C6 -> C0)                                   │
│   Таймер B ────────► Пробудження CPU (C6 -> C0)                             │
│   Таймер C ─────────────► Пробудження CPU (C6 -> C0)                        │
│   [3 окремих апаратних переривання, 3 виходи зі стану сну]                  │
│                                                                             │
│   З коалесценцією (AccuracySec=1min, Range Timers):                         │
│   Таймер A ──┐                                                              │
│   Таймер B ──┼──► ОДНЕ СПІЛЬНЕ ПРОБУДЖЕННЯ CPU (C6 -> C0) ──► Пакетний запуск│
│   Таймер C ──┘                                                              │
│   [1 спільне апаратне переривання, максимальне збереження енергії ядра]     │
└─────────────────────────────────────────────────────────────────────────────┘
```

- **Діапазонні таймери ядра (Range Timers):** Кожен об'єкт `struct hrtimer` у ядрі містить два поля: `_softexpires` (найраніший допустимий момент запуску) та `node.expires` (найпізніший жорсткий дедлайн).
- **Злиття точок пробудження:** Коли `systemd` задає вікно неточності `AccuracySec=1min` (через розрахунок вікна або налаштування слаку `prctl(PR_SET_TIMERSLACK)`), ядро Linux не генерує окреме переривання для кожного таймера. Замість цього ядро відкладає спрацьовування таймера до найближчого вже запланованого пробудження процесора іншою задачею в межах вікна `[_softexpires, hard_expires]`.
- **Результат:** Дюжина фонових завдань (ротація логів, оновлення бази мандатів, синхронізація сертифікатів) виконуються пакетно під час **одного спільного виходу процесора зі стану сну C6/C7**, забезпечуючи максимальну енергоефективність серверів і робочих станцій.

#### 4. Порівняльна матриця характеристик механізмів планування

| Архітектурний вимір | Модель опитування `cron` (Polling) | Модель `systemd.timer` (`hrtimer` / `timerfd`) |
| :--- | :--- | :--- |
| **Базовий механізм ядра** | Цикл `sleep(60 - tm_sec)` у просторі користувача | Червоно-чорне дерево `struct hrtimer`, апаратне програмування APIC TSC-Deadline |
| **Мінімальна дискретність часу** | 1 хвилина (`60 с` = 60 000 000 000 нс) | **1 наносекунда (`1 нс`)** на рівні ядра, 1 мікросекунда у конфігураціях systemd |
| **Споживання CPU у стані очікування (Idle)** | Періодичні перемикання контексту ядра щохвилини для виконання `stat()` та перевірки масок | **0% CPU Overhead:** процес спить у виклику `epoll_wait()` без витрат тактової частоти |
| **Взаємодія зі станами сну CPU (C-States)** | Примусовий вихід із C6/C7 у C0 щохвилини для кожного екземпляра демона | Повна сумісність із Tickless (`NO_HZ`), процесор залишається в C6/C7 максимально довго |
| **Коалесценція пробуджень (Coalescing)** | **Відсутня:** жорстка фіксація на 00-й секунді кожної хвилини (сплески навантаження) | **Вбудована:** регулювання вікна релаксації `AccuracySec=`, об'єднання пробуджень у пакети |
| **Підтримка типів годинників** | Тільки цивільний час `CLOCK_REALTIME` | `CLOCK_REALTIME`, `CLOCK_MONOTONIC`, `CLOCK_BOOTTIME`, `CLOCK_REALTIME_ALARM` |
| **Стійкість до часових стрибків (NTP / DST)** | Потребує програмної емуляції пропущених хвилин та захисту від дублювання в коді демона | Нативна монотонність (`CLOCK_MONOTONIC`), прапорець `TFD_TIMER_CANCEL_ON_SET` |
| **Мультиплексування з подіями I/O** | Неможливо: блокуючий сон або розділення на окремі потоки/процеси | Нативне мультиплексування дескрипторів таймера разом із сокетами та IPC в `epoll(7)` |

### Конвеєр створення нащадка та зниження привілеїв (fork/exec pipeline)

Коли умова розкладу виконується, демон запускає суворо регламентований ланцюжок створення безпечного процесного оточення:

1. **Двохетапне розгалуження (Two-Stage Fork):** Батьківський демон `crond` викликає [fork](root:sys-unix/fork-semantics) для створення проміжного процесу-обробника (*job runner*). Це гарантує, що тривалі операції налаштування безпеки PAM, взаємодії з диском або зниження привілеїв не заблокують головний хвилинний цикл планувальника.
2. **Ізоляція сесії:** Проміжний процес викликає `setsid()` для від'єднання від поточної групи процесів та виключення можливості отримання сигналів від керуючого термінала.
3. **Аутентифікація та сесії PAM:**
   - Демон ініціалізує контекст PAM через `pam_start("crond", username, &conv, &pamh)`.
   - Викликає `pam_acct_mgmt(pamh, 0)` для перевірки статусу облікового запису (блокування в `/etc/shadow`, валідність терміну дії пароля).
   - Встановлює облікові дані через `pam_setcred(pamh, PAM_ESTABLISH_CRED)`.
   - Відкриває сесію через `pam_open_session(pamh, 0)`. Модуль `pam_limits.so` застосовує системні ліміти ресурсів (`setrlimit()`), визначені у `/etc/security/limits.conf`.
4. **Незворотне зниження привілеїв (Privilege Dropping Sequence):**
   - Демон завантажує список додаткових груп цільового користувача з бази [NSS](root:sys-unix/user-database-nss) через `initgroups(pwd->pw_name, pwd->pw_gid)`.
   - Змінює основний ідентифікатор групи процесу через `setgid(pwd->pw_gid)`.
   - Знижує реальний, ефективний та збережений UID через системний виклик `setuid(pwd->pw_uid)`. Ядро Linux безповоротно очищає прапорець `saved UID`, унеможливлюючи повернення привілеїв `root` кодом користувача.
5. **Стерилізація середовища виконання:**
   - Глобальний масив `environ` повністю очищається (виклик `clearenv()`).
   - Формується мінімальне безпечне оточення: `HOME=pwd->pw_dir`, `SHELL=/bin/sh`, `PATH=/usr/bin:/bin`, `LOGNAME=username`, `USER=username`.
   - Застосовуються змінні, явно оголошені у відповідному файлі `crontab`.
   - Робочий каталог змінюється через `chdir(pwd->pw_dir)`. Якщо домашній каталог недоступний, демон переходить у `/` або аварійно завершує підготовку із записом у `syslog`.
6. **Виклик [exec](root:sys-unix/exec-semantics):** Дочірній процес заміщує свій адресний простір командною оболонкою:
   ```text
   execle("/bin/sh", "sh", "-c", command_string, (char *)NULL, child_envp);
   ```

### Захоплення дескрипторів вводу-виводу (I/O Pipes)

Для ізоляції термінального оточення та отримання виводу виконуваної команди демон перед фінальним викликом `execle` налаштовує дескриптори вводу-виводу:

```text
┌─────────────────┐       pipe()       ┌──────────────────────┐
│ Дочірній процес ├───────────────────►│  Процес-монітор cron │
│ (user command)  │   stdout, stderr   │  (читання буфера)    │
└────────┬────────┘                    └──────────┬───────────┘
         │                                        │
         │ stdin                                  ▼ (якщо bytes_read > 0)
         ▼                               ┌───────────────────┐
    /dev/null                            │  sendmail MTA     │
                                         └───────────────────┘
```

1. **Ізоляція вводу (`stdin`):** Дескриптор `STDIN_FILENO` (0) підключається до спеціального пристрою `/dev/null` через системні виклики `open("/dev/null", O_RDWR)` та `dup2(null_fd, STDIN_FILENO)`. Будь-яка спроба команди зчитати дані негайно повертає нуль байтів (`EOF`).
2. **Створення односпрямованого каналу (`pipe`):** Проміжний процес створює канал `pipe(mail_pipe)`, де `mail_pipe[0]` — дескриптор для читання, а `mail_pipe[1]` — дескриптор для запису.
3. **Перенаправлення виводу (`stdout` та `stderr`):** У дочірньому процесі виконання команди викликом `dup2(mail_pipe[1], STDOUT_FILENO)` та `dup2(mail_pipe[1], STDERR_FILENO)` стандартний вивід та вивід помилок об'єднуються і спрямовуються у записуючий кінець каналу. Непотрібні кінці каналу закриваються (`close()`).
4. **Моніторинг виводу:** Процес-монітор читає дані з `mail_pipe[0]` у динамічний буфер до повного закриття каналу дочірнім процесом після завершення його роботи.

### Протокол доставки поштових сповіщень через MTA (sendmail contract)

Після завершення виконання команди процес-монітор приймає рішення щодо формування та відправки системного поштового звіту:

1. **Критерії запуску MTA:** Поштовий агент запускається **виключно за одночасного виконання двох умов**:
   - Змінна `MAILTO` визначена та містить непорожній рядок адреси або логіна отримувача (якщо `MAILTO=""`, вивід повністю скидається, надсилання блокується);
   - Процес команди згенерував **хоча б один байт** виводу у `stdout` або `stderr` (`bytes_read > 0`). Якщо команда завершилася мовчки (0 байтів виводу), MTA не викликається незалежно від коду повернення процесу.
2. **Командний контракт виклику MTA:** Демон запускає системний поштовий інтерфейс (зазвичай `/usr/sbin/sendmail` або `/usr/lib/sendmail`) із фіксованим набором аргументів:
   ```bash
   /usr/sbin/sendmail -FCronDaemon -odi -oem -oi -t
   ```
   - `-FCronDaemon` — встановлює повне ім'я відправника у заголовку (`Cron Daemon`);
   - `-odi` — доставка у фоновому неблокуючому режимі (*Option Delivery Interactive / Immediate*);
   - `-oem` — надсилання повідомлень про помилки доставки автору розкладу (*Option Errors Mail*);
   - `-oi` — заборона завершення вводу символом крапки на окремому рядку (`.` не закриває сесію);
   - `-t` — зчитування адреси одержувачів із заголовків `To:`, `Cc:`, `Bcc:` у тілі переданого повідомлення.
3. **Структура генерованого повідомлення (RFC 5322):**
   ```text
   From: root (Cron Daemon)
   To: developer@example.com
   Subject: Cron <developer@server01> /usr/local/bin/check-status.sh
   MIME-Version: 1.0
   Content-Type: text/plain; charset=UTF-8
   Content-Transfer-Encoding: 8bit
   Auto-Submitted: auto-generated
   X-Cron-Env: <SHELL=/bin/bash>
   X-Cron-Env: <PATH=/usr/local/bin:/usr/bin:/bin>
   X-Cron-Env: <HOME=/home/developer>

   [2026-08-29 03:00:01] Service health check: OK
   ```

## 7. Формат конфігурації anacron (`/etc/anacrontab`)

Утиліта `anacron(8)` призначена для гарантованого виконання періодичних завдань на серверах та робочих станціях із періодичним вимкненням живлення або переходом у режим сну.

### Структура запису конфігураційного рядка

Файл `/etc/anacrontab` містить записи, розділені пробілами або символами табуляції на чотири обов'язкові поля:

```text
# період_у_днях   затримка_у_хвилинах   ідентифікатор_завдання   команда
1                 5                     cron.daily               nice run-parts /etc/cron.daily
7                 10                    cron.weekly              nice run-parts /etc/cron.weekly
@monthly          15                    cron.monthly             nice run-parts /etc/cron.monthly
```

### Специфікація полів anacrontab

| Поле | Допустимі значення | Опис та механізм обробки |
| :--- | :--- | :--- |
| **Період у днях** (`period_in_days`) | Ціле число `> 0`, або макроси `@daily` (1), `@weekly` (7), `@monthly` (30 чи 1 міс) | Періодичність виконання у днях. Завдання виконується, якщо з моменту попереднього запуску минуло `>= N` днів |
| **Затримка у хвилинах** (`delay_in_minutes`) | Ціле число `>= 0` | Кількість хвилин, яку `anacron` очікує після свого старту (або після завершення попереднього завдання при послідовному запуску) перед початком виконання |
| **Ідентифікатор** (`job_identifier`) | Рядок `^[a-zA-Z0-9_-]+$` (без пробілів та слешів) | Унікальне системне ім'я завдання. Використовується як ім'я файлу часової позначки в каталозі `/var/spool/anacron/` |
| **Команда** (`command`) | Рядок шелл-команди | Команда, що передається на виконання оболонці `/bin/sh -c` |

### Глобальні змінні середовища anacron

| Змінна | Формат / Приклад | Призначення та поведінка |
| :--- | :--- | :--- |
| `START_HOURS_RANGE` | `HH-HH` (напр. `3-22` або `06-18`) | Часове вікно доби, у межах якого дозволено запуск завдань. Якщо `anacron` запущено поза цим інтервалом, виконання завдань блокується до настання вказаного часу або утиліта завершує роботу |
| `RANDOM_DELAY` | Ціле число хвилин (напр. `30`) | Верхня межа випадкової паузи (від 0 до `RANDOM_DELAY` хвилин), що додається до `delay_in_minutes` для розмивання пікового навантаження дискового I/O та процесора |
| `SHELL` | Шлях (напр. `/bin/sh`) | Командна оболонка для запуску завдань |
| `PATH` | Список каталогів | Список каталогів пошуку бінарних файлів |
| `MAILTO` | Email або логін (напр. `root`) | Отримувач звітів `stdout`/`stderr`. Якщо порожній (`MAILTO=""`), надсилання звітів не виконується |
| `HOME` | Шлях до каталогу | Робочий каталог виконання команди |

### Файли-мітки каталогу `/var/spool/anacron/`

Для кожного `job_identifier` у каталозі `/var/spool/anacron/` створюється файл, що містить єдиний рядок із датою останнього успішного запуску у форматі `YYYYMMDD` (наприклад, `20260829`).

#### Алгоритм рішення про запуск
```text
днів_минуло = поточна_дата_в_днях - дата_з_файлу_в_днях
якщо (днів_минуло >= period_in_days) або (файл_мітки_відсутній):
    запустити_із_затримкою(delay_in_minutes + random(0, RANDOM_DELAY))
    після_успішного_завершення: записати_в_файл(поточна_дата)
```

- **Обробка часових стрибків (Clock Skew):** Якщо дата у файлі-мітці знаходиться у майбутньому (наприклад, через скидання системного годинника чи некоректну синхронізацію NTP), `anacron` вважає запис невалідним і перезаписує його поточною датою після виконання завдання.

### Довідник опцій утиліти anacron(8)

| Опція | Опис та системна поведінка |
| :--- | :--- |
| `-s` | Послідовний (*serialized*) режим: виконує завдання строго по черзі, очікуючи повного завершення попереднього перед початком відліку затримки наступного |
| `-f` | Примусовий (*force*) запуск: ігнорує дати у файлах-мітках `/var/spool/anacron/` та запускає всі завдання незалежно від дати попереднього виконання |
| `-n` | Негайний запуск (*now*): ігнорує всі затримки `delay_in_minutes` та `RANDOM_DELAY` |
| `-d` | Налагоджувальний режим (*debug*): працює у фоновому режимі термінала (`foreground`), виводить повідомлення в `stderr` замість `syslog` |
| `-q` | Безшумний режим (*quiet*): пригнічує службові інформаційні повідомлення в `syslog` |
| `-u` | Оновлення міток (*update*): записує поточну дату у файли спулу `/var/spool/anacron/` без фактичного виконання команд |
| `-t <файл>` | Використовує альтернативний файл конфігурації замість `/etc/anacrontab` |
| `-T` | Перевірка синтаксису (*test*): тестує валідність конфігураційного файлу та повертає статус без виконання |
| `-V` | Виводить інформацію про версію |
| `-h` | Виводить довідку з використання |

## 8. Специфікація директив таймерів systemd (`.timer`)

У [моделі systemd](root:sys-unix/systemd-model) розклад описується у юніті з суфіксом `.timer`, що активує однойменний (або явно визначений) юніт служби `.service`.

### Повна структура секції `[Timer]` у файлі `.timer`

```ini
[Unit]
Description=Регулярне резервне копіювання бази даних
Documentation=man:backup-tool(8)

[Timer]
# Календарний розклад
OnCalendar=Mon..Fri *-*-* 03:00:00 UTC

# Монотонні тригери
OnBootSec=15min
OnUnitActiveSec=1d

# Обробка простоїв та точність
Persistent=true
AccuracySec=1s
RandomizedDelaySec=10min
FixedRandomDelay=false

# Активація цільового юніта
Unit=database-backup.service
RemainAfterElapse=true
WakeSystem=false

[Install]
WantedBy=timers.target
```

### Директиви секції `[Timer]`

| Директива | Тип значення | За замовчуванням | Системне призначення та семантика |
| :--- | :--- | :--- | :--- |
| `OnCalendar=` | Календарний вираз `systemd.time` | — | Задає запуск за абсолютним астрономічним часом. Дозволено вказувати кілька директив `OnCalendar=` у межах одного юніта (спрацьовує найближча подія) |
| `OnBootSec=` | Часовий інтервал | — | Монотонний таймер відносно точки завершення завантаження ядра Linux (`CLOCK_BOOTTIME`) |
| `OnStartupSec=` | Часовий інтервал | — | Монотонний таймер відносно моменту запуску системного менеджера systemd (PID 1) |
| `OnActiveSec=` | Часовий інтервал | — | Монотонний таймер відносно моменту активації самого таймер-юніта |
| `OnUnitActiveSec=` | Часовий інтервал | — | Монотонний таймер відносно часу останнього **успішного переходу в активний стан** цільового сервіс-юніта |
| `OnUnitInactiveSec=` | Часовий інтервал | — | Монотонний таймер відносно часу останнього **повного завершення (деактивації)** цільового сервіс-юніта |
| `Persistent=` | `true` / `false` | `false` | Зберігає часову мітку останнього виконання на диску. Якщо момент розкладу пропущено через вимкнене живлення, сервіс запускається негайно після завантаження системи |
| `AccuracySec=` | Часовий інтервал | `1min` | Вікно коалесценції (об'єднання) таймерів ядра через системний виклик `timerfd_settime()` для зменшення пробуджень процесора та енергозбереження |
| `RandomizedDelaySec=` | Часовий інтервал | `0` | Максимальний випадковий зсув запуску для запобігання ефекту «громового стада» (*Thundering Herd*) |
| `FixedRandomDelay=` | `true` / `false` | `false` | Якщо `true`, випадковий зсув з `RandomizedDelaySec=` обчислюється детерміновано від Machine ID (`/etc/machine-id`) та залишається однаковим між перезавантаженнями |
| `Unit=` | Назва юніта | `<timer_name>.service` | Явне ім'я юніта, що активується (за замовчуванням — однойменний `.service`) |
| `OnClockChange=` | `true` / `false` | `false` | Чи повторювати перерахунок календарних подій під час системної зміни годинника `CLOCK_REALTIME` |
| `OnTimezoneChange=` | `true` / `false` | `false` | Чи повторювати перерахунок таймерів під час зміни системного часового поясу |
| `RemainAfterElapse=` | `true` / `false` | `true` | Чи залишається юніт у стані `active`, якщо всі заплановані моменти спрацьовування минули (для монотонних разових таймерів) |
| `WakeSystem=` | `true` / `false` | `false` | Чи надсилати апаратний сигнал ACPI пробудження (*Resume RTC*) через `/dev/rtc0` для виведення системи зі стану Suspend/Hibernate |

### Граф транзитивних залежностей та порядок запуску (Dependencies & Ordering Graph)

Архітектура systemd розділяє облік часу та виконання корисного навантаження на два самостійні юніти: `.timer` (таймер-тригер) та `.service` (служба-виконавець). Граф залежностей між ними та системними цілями (Targets) підпорядковується суворим правилам:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                          ГРАФ ЗАЛЕЖНОСТЕЙ ТАЙМЕРА                           │
│                                                                             │
│   timers.target                                                             │
│         ▲                                                                   │
│   Wants │ (автозавантаження через WantedBy= у [Install])                    │
│         │                                                                   │
│   backup.timer ───[ After=time-sync.target ]──► синхронізація часу NTP      │
│         │                                                                   │
│         │ Активація за розкладом (Unit=backup.service)                      │
│         ▼                                                                   │
│   backup.service                                                            │
│         ├─► Requires=network-online.target ──► жорстка залежність мережі    │
│         ├─► After=network-online.target    ──► порядок запуску після мережі │
│         └─► OnFailure=alert-email@%n.service ──► обробка аварійного стану   │
└─────────────────────────────────────────────────────────────────────────────┘
```

1. **Розмежування залежностей таймера та сервісу:**
   - **Залежності юніта `.timer`:** Директиви `Requires=`, `Wants=`, `After=` у секції `[Unit]` файлу `.timer` регламентують **виключно момент запуску самого таймера**. Наприклад, директива `After=time-sync.target` гарантує, що розрахунок календарних подій `OnCalendar=` почнеться лише після корекції системного годинника через NTP. Встановлення `After=network-online.target` на `.timer` є поширеною помилкою: це лише затримає активацію таймера під час завантаження ОС, але не гарантує наявність мережі в момент спрацьовування розкладу через тиждень.
   - **Залежності юніта `.service`:** Усі системні передумови виконання корисного навантаження (доступність мережевих інтерфейсів `network-online.target`, змонтовані сховища `local-fs.target` або активні СУБД) повинні оголошуватися **виключно у файлі `.service`**.
2. **Директиви прив'язки життєвого циклу:**
   - `PartOf=<parent>.target` / `PartOf=<parent>.service` — якщо батьківський юніт зупиняється або перезапускається (наприклад, зупинка сервісу додатка), таймер автоматично зупиняється або перезапускається разом із ним.
   - `BindsTo=<unit>` — жорстка бінарна прив'язка: якщо вказаний юніт переходить у неактивний стан або раптово зникає (наприклад, відключення USB-накопичувача чи віртуального інтерфейсу), таймер негайно деактивується.
   - `Conflicts=<unit>` — взаємне виключення: таймер не може бути активований, якщо активний конфліктний юніт (і навпаки).
3. **Цільова група `timers.target`:** Стандартний механізм автозавантаження всіх системних і користувацьких таймерів. Секція `[Install]` містить `WantedBy=timers.target`, що створює символічне посилання у каталозі `/etc/systemd/system/timers.target.wants/` під час виконання команди `systemctl enable <name>.timer`.

### Обробка збоїв, перезапуски та взаємодія станів (Lifecycle & Error Handling)

Розділена природа юнітів `.timer` та `.service` створює унікальну семантику обробки системних відмов:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                       АВТОМАТ СТАНІВ ПРИ ЗБОЇ СЕРВІСУ                       │
│                                                                             │
│   backup.timer [active (waiting)]                                           │
│         │                                                                   │
│         │ 1. Настання моменту розкладу -> черга JobType=start               │
│         ▼                                                                   │
│   backup.service [activating -> active (running)]                           │
│         │                                                                   │
│         │ 2. Аварійний вихід (ExitCode != 0 або SIGSEGV)                    │
│         ▼                                                                   │
│   backup.service [active -> failed]                                         │
│         ├─► 3. backup.timer ЗАЛИШАЄТЬСЯ [active (waiting)]                  │
│         │      (таймер НЕ падає і чекає наступної точки розкладу)           │
│         │                                                                   │
│         ├─► 4. Активація тригера OnFailure=alert-handler@%n.service         │
│         │                                                                   │
│         └─► 5. Спроба Restart=on-failure (якщо дозволено лімітом Burst)     │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 1. Декупльований автомат станів

Коли таймер спрацьовує, системний менеджер systemd ставить задачу активації цільового сервісу (`JobType=start`). Якщо виконувана програма завершується з ненульовим кодом повернення (`exit code != 0`), завершується сигналом (`SIGKILL`, `SIGSEGV`) або перевищує ліміт пам'яті cgroups (OOM), сервіс-юніт переходить у стан `failed` (`ActiveState=failed`, `SubState=failed`).

**Фундаментальний інваріант:** Юніт `.timer` **не переходить у стан помилки** разом із сервісом. Він залишається у стані `active (waiting)`, продовжує монотонний або календарний відлік і здійснить спробу запуску сервісу в наступний запланований момент розкладу.

#### 2. Декларативні тригери аварій та сповіщень: OnFailure= та OnSuccess=

Для надійної обробки збоїв у секції `[Unit]` цільового `.service` оголошуються тригери відмов:

```ini
[Unit]
Description=Щоденне резервне копіювання PostgreSQL
After=network-online.target postgresql.service
Requires=postgresql.service
OnFailure=status-email@%n.service pagerduty-trigger@%n.service
OnSuccess=backup-metrics-exporter.service

[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup-pg.sh --database=production
TimeoutSec=1800
```

- `OnFailure=` — визначає перелік юнітів, які systemd безумовно активує в момент переходу поточного сервісу в стан `failed`.
- **Специфікатор `%n`:** Передає повне ім'я збійного юніта у параметризований сервіс (наприклад, `status-email@backup-database.service.service`), що дозволяє створити єдиний універсальний сервіс відправки сповіщень.
- **Специфікатор `%N`:** Неекрановане повне ім'я юніта.
- **Специфікатор `%i`:** Значення екземпляра для шаблонів (наприклад, `production` для `backup@production.service`).
- `OnSuccess=` — визначає перелік юнітів, що активуються виключно за успішного завершення (`EXIT_SUCCESS` або чистий вихід `ExitCode == 0`).

#### 3. Політика перезапусків та обмеження циклів (Restart Rate Limiting)

Для періодичних служб `Type=oneshot` директива `Restart=` за замовчуванням вимкнена (`Restart=no`). Якщо завдання має статус критичного і потребує автоматичного повтору при тимчасових мережевих збоях, застосовується конфігурація:

```ini
[Service]
Type=exec
ExecStart=/usr/local/bin/sync-s3.sh
Restart=on-failure
RestartSec=30s

# Захист від нескінченних петель перезапусків
[Unit]
StartLimitIntervalSec=10min
StartLimitBurst=3
```

- `Restart=on-failure` — ініціює перезапуск процесу лише у разі аварійного коду завершення, перевищення таймауту або вбивства сигналом ядра.
- `RestartSec=30s` — пауза перед повторною спробою виконання.
- `StartLimitIntervalSec=` та `StartLimitBurst=` — механізм захисту від шторму перезапусків: якщо сервіс зазнає краху понад `StartLimitBurst` разів (у прикладі: 3 рази) за інтервал `StartLimitIntervalSec` (10 хвилин), подальші спроби перезапуску блокуються, сервіс остаточно переходить у стан `failed` та активує `OnFailure=`.

#### 4. Колізії станів та накладання виконань (Overlapping & Coalescing)

- **Накладання тригерів під час активного виконання:** Якщо черговий момент спрацьовування таймера настав, а попередньо запущений екземпляр `.service` все ще виконується (`ActiveState=active` або `activating`), systemd **не запускає паралельний екземпляр тієї самої служби**. Менеджер фіксує колізію, записує інформаційне повідомлення в журнал і пропускає активацію (coalescing). На відміну від `cron`, systemd вбудовано захищає систему від паралельного накладання однакових завдань без необхідності ручного виклику `flock(1)`.
- **Пастка директиви `RemainAfterExit=true`:** Для служб `Type=oneshot` директива `RemainAfterExit=true` залишає юніт у стані `active (exited)` після завершення виконання команди. Якщо такий сервіс підключений до таймера, повторні спрацьовування таймера будуть бачити сервіс як уже активний і **не виконуватимуть команду `ExecStart=` повторно**. Для періодичних завдань обов'язковим є значення `RemainAfterExit=false` (налаштування за замовчуванням для `oneshot`).

## 9. Граматика та синтаксис специфікації `systemd.time(7)`

Календарні вирази `OnCalendar=` використовують розширену граматику нормалізованих часових подій:

```text
[ДеньТижня] [РРРР-ММ-ДД] [ГГ:ХХ:СС] [ЧасовийПояс]
```

### Формати часових інтервалів (Time Spans)

Використовуються у директивах `OnBootSec=`, `AccuracySec=`, `RandomizedDelaySec=` тощо. Складаються з числа та суфікса одиниці виміру:

| Суфікс одиниці | Повні назви | Значення |
| :--- | :--- | :--- |
| `us`, `µs` | `usec`, `us` | Мікросекунди |
| `ms` | `msec`, `ms` | Мілісекунди |
| `s` | `sec`, `second`, `seconds` | Секунди |
| `m`, `min` | `minute`, `minutes` | Хвилини |
| `h`, `hr` | `hour`, `hours` | Години |
| `d` | `day`, `days` | Доба (24 години) |
| `w` | `week`, `weeks` | Тиждень (7 діб) |
| `M` | `month`, `months` | Календарний місяць (30.44 доби) |
| `y` | `year`, `years` | Календарний рік (365.25 доби) |

*Приклади інтервалів:* `1h 30min`, `2d 12h`, `500ms`, `15s`.

### Компоненти календарних виразів `OnCalendar=`

1. **День тижня (`DayOfWeek`):**
   - Назви: `Mon`, `Tue`, `Wed`, `Thu`, `Fri`, `Sat`, `Sun`.
   - Діапазони: `Mon..Fri` (понеділок–п'ятниця), `Sat..Sun` (вихідні).
   - Списки: `Mon,Wed,Fri`.
2. **Дата (`Year-Month-Day`):**
   - Точна дата: `2026-08-29`.
   - Будь-який рік: `*-08-29` (щороку 29 серпня).
   - Будь-який місяць: `*-*-01` (перше число щомісяця).
   - Зсув від кінця місяця (тильда `~`): `*-02~03` (за 3 дні до кінця лютого), `*-*~01` (останній день кожного місяця).
   - Діапазони та списки дат: `*-01,06,12-01..05` (з 1 по 5 число у січні, червні та грудні).
3. **Час доби (`Hour:Minute:Second`):**
   - Точний час: `04:00:00`.
   - Без секунд: `04:00` (розгортається у `04:00:00`).
   - Будь-яка година: `*:00:00` (на початку кожної години).
   - Крок ітерації: `*:0/15:00` (кожні 15 хвилин), `00/2:00:00` (кожні дві години, починаючи з півночі).
4. **Часовий пояс (`Timezone`):**
   - Назва із бази IANA або аліас: `UTC`, `Europe/Kyiv`, `America/New_York`.

### Вбудовані мнемонічні аліаси OnCalendar

| Аліас | Нормалізований вираз `systemd.time` | Момент запуску |
| :--- | :--- | :--- |
| `minutely` | `*-*-* *:*:00` | Щомиті на нульовій секунді |
| `hourly` | `*-*-* *:00:00` | Щогодини на нульовій хвилині |
| `daily` | `*-*-* 00:00:00` | Щоночі опівночі |
| `weekly` | `Mon *-*-* 00:00:00` | Щопонеділка опівночі |
| `monthly` | `*-*-01 00:00:00` | Першого числа щомісяця опівночі |
| `quarterly` | `*-01,04,07,10-01 00:00:00` | Першого дня кожного кварталу |
| `semiannually` / `semi-annually` | `*-01,07-01 00:00:00` | Кожні пів року (1 січня та 1 липня) |
| `yearly` / `annually` | `*-01-01 00:00:00` | Щороку 1 січня опівночі |

### Службові файли часових позначок (Stamp Files)

Коли увімкнено `Persistent=true`, менеджер systemd зберігає стан виконання:
- **Системні таймери:** `/var/lib/systemd/timers/stamp-<unit_name>.timer`.
- **Користувацькі таймери (`--user`):** `~/.local/share/systemd/timers/stamp-<unit_name>.timer` (або за шляхом `$XDG_DATA_HOME/systemd/timers/`).
- Файл не містить текстових даних: systemd фіксує мітку часу через час останньої модифікації (`st_mtime`) самого файлу через системні виклики ядра `utimensat()`.

## 10. Командні інтерфейси перевірки та адміністрування таймерів systemd

### Діагностика календарних виразів через `systemd-analyze`

Утиліта `systemd-analyze calendar` здійснює валідацію рядка, виводить його нормалізовану форму та розраховує майбутні моменти спрацьовування:

```bash
systemd-analyze calendar "Mon..Fri *-*-* 09:00:00 Europe/Kyiv"
```

Приклад виводу утиліти:
```text
  Normalized form: Mon..Fri *-*-* 09:00:00 Europe/Kyiv
    Next elapse: Mon 2026-08-31 09:00:00 EEST
       (in UTC): Mon 2026-08-31 06:00:00 UTC
       From now: 1 day 17h left
```

Розрахунок наступних `N` моментів спрацьовування:
```bash
systemd-analyze calendar --iterations=5 "*-*-01 00:00:00"
```

### Моніторинг черги таймерів через `systemctl list-timers`

Команда `systemctl list-timers --all` відображає зведену таблицю таймерів:

```text
NEXT                         LEFT          LAST                         PASSED       UNIT                         ACTIVATES
Tue 2026-09-01 00:00:00 EEST 2d 7h left   Sat 2026-08-01 00:00:02 EEST 28 days ago  logrotate.timer              logrotate.service
Wed 2026-09-02 03:00:00 EEST 3d 10h left  Wed 2026-08-26 03:00:01 EEST 3 days ago   backup.timer                 backup.service
n/a                          n/a           Mon 2026-08-24 12:00:00 EEST 5 days ago   oneshot.timer                oneshot.service
```

- `NEXT` — абсолютний астрономічний час наступного запланованого спрацьовування.
- `LEFT` — інтервал зворотного відліку до наступного запуску.
- `LAST` — точний час попереднього спрацьовування.
- `PASSED` — скільки часу минуло з моменту останнього виконання.
- `UNIT` — назва активного юніта таймера (`.timer`).
- `ACTIVATES` — назва цільового юніта служби (`.service`), яку активує таймер.

### Керування станом таймер-юнітів

```bash
# Запуск таймера в поточній сесії
systemctl start backup.timer

# Зупинка відліку таймера
systemctl stop backup.timer

# Додавання таймера в автозавантаження (створення симлінка у timers.target.wants/)
systemctl enable backup.timer

# Перевірка поточного стану таймера
systemctl status backup.timer

# Перевірка користувацьких таймерів
systemctl --user list-timers
```

### Динамічні тимчасові таймери через `systemd-run`

Утиліта `systemd-run` створює разові або періодичні таймери прямо з командного рядка без створення постійних файлів на диску:

```bash
# Разовий запуск через 45 хвилин після поточного моменту
systemd-run --on-active="45min" --unit="quick-dump" /usr/local/bin/dump-state.sh

# Запуск через 10 хвилин після кожного завантаження ОС
systemd-run --on-boot="10min" /usr/local/bin/warmup-cache.sh

# Створення календарного розкладу з персистентністю
systemd-run --on-calendar="daily" --timer-property="Persistent=true" /usr/local/bin/sync-s3.sh
```

### Інтеграція з systemd-journald: структуровані метадані та фільтрація логів

На відміну від `cron`, де вивід команд захоплюється у поштовий конвеєр або неструктуровані текстові файли, `systemd` автоматично перехоплює всі потоки виводу (`stdout`/`stderr`), системні виклики логування та події життєвого циклу процесів у бінарний журнал `systemd-journald`.

```text
┌───────────────────────────┐         systemd PID 1           ┌───────────────────────────┐
│       backup.timer        │────────────────────────────────►│       backup.service      │
│  (генерація події розкладу│                                 │ (ExecStart=/bin/backup.sh)│
└─────────────┬─────────────┘                                 └─────────────┬─────────────┘
              │                                                             │
              │ Події таймера                                               │ Потоки stdout/stderr
              ▼                                                             ▼
┌─────────────────────────────────────────────────────────────────────────────────────────┐
│                                   systemd-journald                                      │
│                                                                                         │
│   • _SYSTEMD_UNIT=backup.timer           • _SYSTEMD_UNIT=backup.service                 │
│   • MESSAGE=Timer elapsed                • _SYSTEMD_INVOCATION_ID=d5e8...               │
│                                          • INVOCATION_ID=d5e8...                        │
│                                          • _TRANSPORT=stdout                            │
│                                          • EXIT_CODE=exited, EXIT_STATUS=0              │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. Структуровані поля журналу для періодичних завдань

Кожен запис журналу містить індексовані метадані ядра та системного менеджера:

| Поле журналу | Тип даних | Опис та системне призначення |
| :--- | :--- | :--- |
| `_SYSTEMD_UNIT` | Рядок | Ім'я юніта, що згенерував запис (`backup.service` для корисного навантаження або `backup.timer` для подій планувальника) |
| `UNIT` | Рядок | Аліас системного юніта в просторі користувача |
| `_SYSTEMD_INVOCATION_ID` | 128-бітний UUID | Унікальний ідентифікатор конкретного запуску екземпляра служби. Генерується наново під час кожного спрацьовування таймера |
| `INVOCATION_ID` | 128-бітний UUID | Змінна середовища, автоматично передана в процес виконання завдання. Дозволяє додатку маркувати власні логи тим самим UUID |
| `_TRANSPORT` | Рядок | Джерело походження запису: `stdout` (захоплення дескрипторів), `journal` (прямий виклик `sd_journal_print`), `syslog` |
| `_PID` | Ціле число | PID процесу, що виконав вивід |
| `_UID` / `_GID` | Ціле число | Реальні ідентифікатори користувача та групи процесу |
| `_COMM` | Рядок | Назва бінарного файлу або команди процесу |
| `EXIT_CODE` | Рядок | Причина завершення процесу (`exited`, `killed`, `dumped`) |
| `EXIT_STATUS` | Ціле число | Числовий код повернення процесу (0–255) або номер фатального сигналу ядра |

#### 2. Рецепти діагностики та фільтрації логів через `journalctl`

```bash
# 1. Повний перегляд логів виконання цільового сервісу
journalctl -u backup.service

# 2. Перегляд подій планування самого таймера (перерахунок розкладу, моменти спрацьовування)
journalctl -u backup.timer

# 3. Ізоляція логів виключно останнього запуску сервісу за його InvocationID
INVOCATION_ID=$(systemctl show -p InvocationID --value backup.service)
journalctl _SYSTEMD_INVOCATION_ID="$INVOCATION_ID"

# 4. Фільтрація логів за поточний сеанс завантаження ОС (Boot)
journalctl -u backup.service -b

# 5. Фільтрація повідомлень про помилки та критичні збої (пріоритети err, crit, alert, emerg)
journalctl -u backup.service -p err..emerg

# 6. Фільтрація логів за точним часовим інтервалом
journalctl -u backup.service --since "2026-08-29 02:00:00" --until "2026-08-29 04:00:00"

# 7. Моніторинг виводу виконання у реальному часі (з точністю до мікросекунд)
journalctl -u backup.service -f -o short-precise

# 8. Експорт структурованих записів у форматі JSON для централізованих систем моніторингу (Loki, Elasticsearch)
journalctl -u backup.service -n 50 -o json-pretty
```

#### 3. Діагностика збійних таймерів та сервісів

Якщо регулярне завдання зазнало краху, статус помилки фіксується у глобальному реєстрі менеджера systemd:

```bash
# Перегляд списку всіх сервісів у стані відмови (failed)
systemctl --failed --type=service

# Детальний діагностичний статус юніта з останніми рядками журналу
systemctl status backup.service

# Очищення стану помилки після усунення проблеми
systemctl reset-failed backup.service
```

## 11. Специфікація підсистеми разових завдань at, batch та демона atd

Підсистема `at` призначена для одноразового запуску сценаріїв у точно визначений момент часу в майбутньому, а утиліта `batch` — для виконання завдань тоді, коли системне навантаження знижується нижче встановленого порогу.

### Командний інтерфейс утиліт `at`, `batch`, `atq`, `atrm`

| Утиліта / Команда | Опції / Аргументи | Призначення та семантика виклику |
| :--- | :--- | :--- |
| `at` | `[-q черга] [-f файл] [-m] [-v] ЧАС` | Реєструє нове разове завдання на вказаний час. Тіло завдання зчитується зі стандартного вводу `stdin` або з файлу `-f` |
| `at -c <job_id>` | `<job_id>` | Виводить повний згенерований шелл-сценарій завдання (включно зі збереженим оточенням) на `stdout` |
| `atq` або `at -l` | `[-q черга] [користувач]` | Виводить список очікуваних завдань у черзі поточного користувача (або всіх завдань для `root`) |
| `atrm` або `at -d` | `<job_id> [job_id...]` | Видаляє одне або декілька завдань із черги спулу за їхніми ідентифікаторами |
| `batch` | `[-q черга] [-f файл] [-m] [ЧАС]` | Ставить завдання в чергу пакетної обробки для запуску при падінні Load Average нижче ліміту |

### Граматика специфікації часу утиліти `at(1)`

Утиліта `at` використовує гнучкий синтаксичний парсер часових виразів (специфікація POSIX.2):

```text
at [-q черга] [-f файл] ЧАС [ДАТА] [+ ПРИРІСТ]
```

1. **Часові формати доби:**
   - 24-годинний формат: `14:30`, `08:00`, `23:59`.
   - 12-годинний формат із суфіксами `am`/`pm`: `2:30pm`, `8am`, `11:45pm`.
   - Зарезервовані мнемоніки:
     - `noon` — 12:00 (полудень).
     - `midnight` — 00:00 (північ).
     - `teatime` — 16:00 (традиційний час чаю).
     - `now` — поточний момент часу (використовується разом із відносними приростами).
2. **Формати календарних дат:**
   - Назва місяця та день: `Jan 15`, `December 25 2026`, `Aug 29`.
   - Числові дати: `MMDDYY` (`082926`), `MM/DD/YY` (`08/29/26`), `DD.MM.YY` (`29.08.26`), `YYYY-MM-DD` (`2026-08-29`).
   - Відносні дні: `today` (сьогодні), `tomorrow` (завтра), `next week`, `next month`, `next Mon`, `next Fri`.
3. **Відносні прирости (`+ інтервал`):**
   - Синтаксис: `+ <число> <одиниця>`.
   - Одиниці: `minutes`, `hours`, `days`, `weeks`, `months`, `years`.
   - *Приклади комбінацій:*
     - `at now + 15 minutes` — через 15 хвилин від поточного моменту.
     - `at 4:00pm tomorrow` — о 16:00 наступного дня.
     - `at teatime + 3 days` — о 16:00 через 3 дні.
     - `at 02:00 2026-12-31` — о 02:00 31 грудня 2026 року.

### Механізм захоплення знімка середовища (Environment Snapshot)

На відміну від `cron`, який запускає команди у стерильному мінімальному оточенні, утиліта `at` у момент створення завдання робить **повний зліпок термінальної сесії користувача**:

1. **Збереження робочого каталогу:** Зчитує поточний каталог через `getcwd()` і генерує інструкцію `cd /шлях/до/каталогу || exit 1`.
2. **Збереження маски прав (`umask`):** Фіксує поточну маску створення файлів і генерує команду `umask 0022`.
3. **Експорт змінних оточення:** Ітерує по масиву `environ` і серіалізує всі активні змінні (`PATH`, `LANG`, `LD_LIBRARY_PATH`, власні змінні користувача) через блок команд `export VAR="значення"`.
4. **Виключення термінальних дескрипторів:** Змінні сесії, прив'язані до керуючого термінала (`TERM`, `DISPLAY`, `SSH_TTY`), можуть очищуватися або замінюватися.

Приклад структури згенерованого файлу завдання у спулі (`/var/spool/at/` або `/var/spool/cron/atjobs/`):

```bash
#!/bin/sh
# atrun GID: 1000 UID: 1000
umask 22
HOSTNAME=server01; export HOSTNAME
PWD=/home/developer/projects; export PWD
USER=developer; export USER
LANG=uk_UA.UTF-8; export LANG
PATH=/usr/local/bin:/usr/bin:/bin:/home/developer/bin; export PATH
cd /home/developer/projects || exit 1
${SHELL:-/bin/sh} << 'marcinDELIMITER5a2b3c4d'
/usr/local/bin/deploy-release.sh --version 2.4.0
marcinDELIMITER5a2b3c4d
```

### Черги та пріоритети завдань

Підсистема `at` підтримує множинні черги, що позначаються символами латинського алфавіту:
- **Черги `a–z` (нижній регістр):** Черга `a` є чергою за замовчуванням для завдань `at`. Черга `b` є чергою за замовчуванням для `batch`. Літери від `a` до `z` визначають спадний пріоритет планування (вищий пріоритет процесора `nice` для перших літер).
- **Черги `A–Z` (верхній регістр):** Завдання у чергах верхнього регістру не підлягають поштовому сповіщенню (`no mail`).
- **Спеціальна черга `=`:** Позначає завдання, які виконуються прямо в поточний момент.

### Демон `atd(8)` та семантика утиліти `batch`

Фоновий демон `atd` прокидається щохвилини, сканує каталог спулу на наявність завдань, чий час запуску настав, і виконує їх:

| Прапорець `atd` | Аргумент | Системна дія |
| :--- | :--- | :--- |
| `-l` | `<load_avg>` | Встановлює граничний рівень середнього навантаження системи (*Load Average* за 1 хвилину) для запуску завдань із черги `batch`. За замовчуванням — `0.8` (або `1.5` залежно від дистрибутива). Якщо поточний `load_avg >= ліміт`, завдання черги `b` відкладаються до наступної перевірки |
| `-b` | `<секунди>` | Мінімальний інтервал у секундах між послідовними запусками двох завдань черги `batch` (за замовчуванням — `60`) |
| `-d` | — | Робота у налагоджувальному режимі на передньому плані термінала (*foreground*) |
| `-s` | — | Одноразова обробка черги (*single run*) |

### Керування доступом: `/etc/at.allow` та `/etc/at.deny`

Авторизація користувачів підсистеми `at` працює за тими самими правилами, що й `cron`:
1. Якщо існує `/etc/at.allow`, створювати разові завдання дозволено **виключно** користувачам, вказаним у цьому файлі.
2. Якщо `/etc/at.allow` відсутній, демон перевіряє `/etc/at.deny`: доступ надається всім, крім перелічених облікових записів.
3. Якщо обидва файли відсутні, поведінка залежить від політики безпеки ОС: у більшості захищених систем доступ дозволено лише користувачу `root`.

## 12. Найкращі практики оркестрації та спостережуваності у production

Виробнича експлуатація фонових завдань вимагає гарантій відсутності гонок ресурсів, передбачуваної обробки зависань та інтеграції в централізовані системи моніторингу метрик.

### Запобігання паралельному запуску: flock проти lockf/fcntl

Класичний `cron` не відстежує стан попередньо запущених екземплярів одного й того самого завдання. Якщо виконання регулярної задачі (наприклад, бекапу бази даних) перевищує інтервал її планування, планувальник паралельно ініціалізує новий процес, що спричиняє деградацію I/O та взаємне блокування транзакцій.

#### Небезпека наївних PID-файлів у скриптах

Спроби запобігти паралельному виконанню через створення файлу ідентифікатора процесу (`/var/run/job.pid`) породжують критичні системні відмови:
1. **Гонка перевірки та запису (TOCTOU):** Між перевіркою `if [ ! -f "$PIDFILE" ]` та безпосереднім створенням `echo $$ > "$PIDFILE"` кілька процесів встигають перевірити умову одночасно й обидва переходять до виконання корисного навантаження.
2. **Завислі замки (Stale Locks):** Якщо процес завершується аварійно (сигнал `SIGKILL`, вичерпання пам'яті через OOM Killer або раптовий перезапуск сервера), PID-файл залишається на файловій системі. Подальші регулярні запуски хибно вважатимуть процес активним і блокуватимуться на невизначений час.
3. **Перевикористання PID (PID Recycling):** Простір ідентифікаторів процесів ядра Linux є скінченним (`/proc/sys/kernel/pid_max`). Перевірка `kill -0 $OLD_PID` може вказати на активність зовсім іншого, новоствореного системного процесу, який випадково отримав той самий PID.

#### Механізм ядерних замків відкритого файлового дескриптора (`flock`)

Утиліта `flock(1)` та системний виклик `flock(2)` створюють ексклюзивне блокування на рівні структури відкритого файлу в ядрі (`struct file`):
- **Атомарність:** Ядро гарантує, що лише один процес у системі може отримати ексклюзивний замок `LOCK_EX`.
- **Автоматичне очищення:** Замок безпосередньо прив'язаний до дескриптора. Коли процес завершується (нормально, аварійно, за `SIGKILL` або `SIGSEGV`), ядро автоматично викликає `filp_close()` і звільняє замок. Завислі замки (Stale Locks) неможливі фізично.

:::tabs
@tab C
```c
#include <sys/file.h>
#include <unistd.h>
#include <fcntl.h>
#include <stdio.h>
#include <errno.h>

int acquire_nonblocking_lock(const char *lock_file_path) {
    int fd = open(lock_file_path, O_RDWR | O_CREAT | O_CLOEXEC, 0600);
    if (fd < 0) {
        return -1;
    }
    /* Спроба ексклюзивного неблокуючого блокування */
    if (flock(fd, LOCK_EX | LOCK_NB) != 0) {
        close(fd);
        if (errno == EWOULDBLOCK) {
            return 0; /* Замок вже утримується іншим процесом */
        }
        return -1;    /* Системна помилка блокування */
    }
    return fd;        /* Замок успішно отримано, дескриптор утримується до завершення */
}
```
@tab C++
```cpp
#include <sys/file.h>
#include <unistd.h>
#include <fcntl.h>
#include <iostream>
#include <system_error>

[[nodiscard]] int acquire_nonblocking_lock(const char* lock_file_path) noexcept {
    int fd = ::open(lock_file_path, O_RDWR | O_CREAT | O_CLOEXEC, 0600);
    if (fd < 0) {
        return -1;
    }
    // Спроба ексклюзивного неблокуючого блокування
    if (::flock(fd, LOCK_EX | LOCK_NB) != 0) {
        ::close(fd);
        if (errno == EWOULDBLOCK) {
            return 0; // Замок вже утримується іншим процесом
        }
        return -1;    // Системна помилка блокування
    }
    return fd;        // Замок успішно отримано, дескриптор утримується до завершення
}
```
:::

#### Системний виклик `flock(2)` проти POSIX `fcntl(2)` / `lockf(3)`

| Параметр | `flock(2)` (BSD Locks) | `fcntl(2)` / `lockf(3)` (POSIX Record Locks) |
| :--- | :--- | :--- |
| **Об'єкт прив'язки в ядрі** | Структура відкритого файлу (`struct file`) | Пара `(PID процесу, inode)` |
| **Успадкування через `fork()`** | Успадковується нащадком (спільний опис файлу) | **НЕ успадковується** нащадком |
| **Збереження при `execve()`** | Зберігається (якщо не встановлено `FD_CLOEXEC`) | Зберігається (якщо не встановлено `FD_CLOEXEC`) |
| **Семантика закриття файлу** | Звільняється тільки після закриття **останнього** дескриптора | **Звільняється при закритті БУДЬ-ЯКОГО дескриптора** цього файлу у процесі |
| **Підтримка мережевих FS (NFS)** | Емулюється ядром через NLM або вимагає монтування `nolock` | Повноцінно підтримується протоколами NLM та NFSv4 |

#### Ідіома блокування у Shell через дескриптор

```bash
LOCKFILE="/var/lock/myjob.lock"
exec 200>"$LOCKFILE"
flock -n 200 || {
    echo "[$(date -Iseconds)] [ERROR] Інший екземпляр завдання вже активний. Завершення." >&2
    exit 1
}
```

### Контроль тривалості виконання та обробка сигналів завершення

Для захисту від нескінченних підвисань (наприклад, блокування на мережевих сокетах або deadlock у базі даних) виконання команди обмежується утилітою `timeout(1)`:

```bash
timeout --kill-after=30s --signal=TERM 1800s /usr/local/bin/backup-job.sh
```

- **Двоетапне завершення:**
  1. Після закінчення встановленого ліміту (`1800s` = 30 хвилин) утиліта надсилає процесу м'який сигнал `SIGTERM`. Скрипт отримує можливість коректно перехопити сигнал, закрити відкриті з'єднання, скинути буфери на диск та прибрати тимчасові файли.
  2. Якщо процес не завершився протягом грейс-періоду `30s` після отримання `SIGTERM`, утиліта надсилає безумовний сигнал `SIGKILL` (сигнал 9), гарантовано звільняючи системні ресурси ядра.

### Спостережуваність та експорт метрик у Prometheus (node_exporter Textfile Collector)

Для моніторингу статусу, тривалості та регулярності періодичних завдань у промислових середовищах використовується модуль **Textfile Collector** експортера Prometheus (`node_exporter`).

#### Архітектура збору метрик через Textfile Collector

`node_exporter` періодично зчитує всі текстові файли з розширенням `.prom` із каталогу `/var/lib/node_exporter/textfile_collector/` і додає їхній вміст до загального HTTP-ендпоінту `/metrics`.

```text
┌───────────────────────────┐
│     cron-wrapper.sh       │
│  (виконання розкладу)     │
└─────────────┬─────────────┘
              │ 1. Замір часу, коду повернення
              │ 2. Запис у тимчасовий /var/lib/.../job.prom.$$
              │ 3. Атомарний rename(2) -> job.prom
              ▼
┌───────────────────────────┐         HTTP GET /metrics         ┌───────────────────────────┐
│ /var/lib/node_exporter/   ├──────────────────────────────────►│    Сервер Prometheus      │
│ textfile_collector/*.prom │       (скрапінг метрик)           │  (алертинг, Grafana)      │
└───────────────────────────┘                                   └───────────────────────────┘
```

#### Специфікація метрик періодичного завдання

```text
# HELP node_cron_job_last_run_timestamp_seconds Unix timestamp останнього виконання завдання
# TYPE node_cron_job_last_run_timestamp_seconds gauge
node_cron_job_last_run_timestamp_seconds{job="postgres_backup"} 1788004800

# HELP node_cron_job_duration_seconds Тривалість виконання завдання у секундах
# TYPE node_cron_job_duration_seconds gauge
node_cron_job_duration_seconds{job="postgres_backup"} 42.150

# HELP node_cron_job_success Бінарний статус успішності (1 = успіх, 0 = помилка)
# TYPE node_cron_job_success gauge
node_cron_job_success{job="postgres_backup"} 1

# HELP node_cron_job_exit_code Числовий код повернення процесу
# TYPE node_cron_job_exit_code gauge
node_cron_job_exit_code{job="postgres_backup"} 0
```

#### Атомарний запис метрик

Скрапер `node_exporter` може прочитати файл прямо в процесі його запису скриптом, що призведе до синтаксичної помилки розбору неповної метрики. Щоб гарантувати цілісність, метрики записуються у тимчасовий файл у тому самому каталозі, після чого переміщуються атомарним викликом ядра `rename(2)`:


### Промисловий патерн універсальної шелл-обгортки періодичних завдань

Нижче наведено еталонний скрипт `cron-job-wrapper.sh`, який об'єднує блокування дескриптора через `flock`, замір часу виконання, протоколювання потоків виводу та атомарний експорт метрик у Prometheus:

```bash
#!/usr/bin/env bash
set -u

JOB_NAME="${1:-}"
TIMEOUT_SEC="${2:-3600}"
shift 2 || { echo "Використання: $0 <job_name> <timeout_sec> <команда> [аргументи...]" >&2; exit 2; }

if [ -z "$JOB_NAME" ]; then
    echo "Помилка: не вказано ім'я завдання" >&2
    exit 2
fi

LOCK_DIR="/var/lock/cron"
METRICS_DIR="/var/lib/node_exporter/textfile_collector"
LOG_DIR="/var/log/cron"

mkdir -p "$LOCK_DIR" "$METRICS_DIR" "$LOG_DIR"

LOCK_FILE="${LOCK_DIR}/${JOB_NAME}.lock"
PROM_FILE="${METRICS_DIR}/cron_${JOB_NAME}.prom"
LOG_FILE="${LOG_DIR}/${JOB_NAME}.log"

# Відкриття дескриптора 200 на lock-файл
exec 200>"$LOCK_FILE"

# Неблокуюча спроба отримати ексклюзивний замок
if ! flock -n 200; then
    echo "[$(date -Iseconds)] [WARN] Завдання '${JOB_NAME}' вже виконується іншим процесом. Запуск пропущено." >> "$LOG_FILE"
    exit 0
fi

START_TS=$(date +%s)
START_HIRES=$(date +%s.%N)
EXIT_CODE=0

echo "[$(date -Iseconds)] [INFO] Старт завдання '${JOB_NAME}': $*" >> "$LOG_FILE"

# Виконання команди з таймаутом та перенаправленням виводу в лог
timeout --kill-after=30s --signal=TERM "${TIMEOUT_SEC}" "$@" >> "$LOG_FILE" 2>&1
EXIT_CODE=$?

END_HIRES=$(date +%s.%N)
DURATION=$(awk "BEGIN {print $END_HIRES - $START_HIRES}")

SUCCESS=1
if [ "$EXIT_CODE" -ne 0 ]; then
    SUCCESS=0
    echo "[$(date -Iseconds)] [ERROR] Завдання '${JOB_NAME}' завершилося аварійно з кодом ${EXIT_CODE}" >> "$LOG_FILE"
else
    echo "[$(date -Iseconds)] [INFO] Завдання '${JOB_NAME}' успішно завершено за ${DURATION} с" >> "$LOG_FILE"
fi

# Атомарний експорт метрик у Textfile Collector
TMP_PROM="${PROM_FILE}.$$"
cat << EOF > "$TMP_PROM"
# HELP node_cron_job_last_run_timestamp_seconds Unix timestamp останнього запуску завдання
# TYPE node_cron_job_last_run_timestamp_seconds gauge
node_cron_job_last_run_timestamp_seconds{job="${JOB_NAME}"} ${START_TS}
# HELP node_cron_job_duration_seconds Тривалість виконання завдання у секундах
# TYPE node_cron_job_duration_seconds gauge
node_cron_job_duration_seconds{job="${JOB_NAME}"} ${DURATION}
# HELP node_cron_job_success Статус виконання завдання (1 = успіх, 0 = помилка)
# TYPE node_cron_job_success gauge
node_cron_job_success{job="${JOB_NAME}"} ${SUCCESS}
# HELP node_cron_job_exit_code Код повернення процесу
# TYPE node_cron_job_exit_code gauge
node_cron_job_exit_code{job="${JOB_NAME}"} ${EXIT_CODE}
EOF

mv -f "$TMP_PROM" "$PROM_FILE"

exit "$EXIT_CODE"
```

Приклад використання у файлі `/etc/cron.d/production-backup`:
```crontab

MAILTO=""

# Щоночі о 02:00 запуск резервного копіювання з таймаутом 45 хвилин
0 2 * * * root /usr/local/bin/cron-job-wrapper.sh postgres_backup 2700 /usr/local/bin/backup-pg.sh --all
```

## 14. Специфікація низькорівневих системних викликів таймерів Linux (`timerfd`, `epoll`, `prctl`)

Сучасні планувальники подій у Linux (зокрема диспетчер подій `sd-event` у складі `systemd`) відмовилися від класичних асинхронних сигналів таймера (`SIGALRM`, `setitimer(2)`, `timer_create(2)`). Асинхронні обробники сигналів створюють фатальні ризики порушення ревходу (*reentrancy*), взаємних блокувань у пам'яті (*deadlocks*) та обмежують доступний набір системних викликів функціями з переліку async-signal-safe.

Для усунення цих обмежень ядро Linux починаючи з версії 2.6.25 надає підсистему **`timerfd`**, яка проектує стан таймера на стандартний файловий дескриптор. Це дозволяє мультиплексувати таймери разом із мережевими сокетами та каналами IPC в єдиному неблокуючому циклі опитування `epoll(7)` або `io_uring`.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                          АРХІТЕКТУРА ПІДСИСТЕМИ TIMERFD                     │
│                                                                             │
│   Ядро Linux (hrtimer / timekeeping)                                        │
│         │                                                                   │
│         │ Апаратні переривання APIC / HPET / ARM Generic Timer              │
│         ▼                                                                   │
│   struct timerfd_ctx (kernel object)                                        │
│         │                                                                   │
│         ├─► ticks / expirations counter (uint64_t)                          │
│         ├─► struct itimerspec (it_value, it_interval)                       │
│         └─► wait_queue_head_t (оповіщення epoll)                            │
│                                                                             │
│   Простір користувача (systemd / sd-event / event loops)                    │
│         │                                                                   │
│         ├─► timerfd_create()  ──► створення анонімного inode дескриптора    │
│         ├─► timerfd_settime() ──► зведення таймера (абсолютний/відносний)  │
│         ├─► epoll_wait()      ──► реактивне пробудження за подією EPOLLIN   │
│         └─► read(tfd, &cnt, 8)──► вичитування кількості спрацьовувань       │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Системний виклик `timerfd_create(2)`

Створює новий екземпляр таймера ядра та повертає файловий дескриптор, що посилається на нього:

:::tabs
@tab C
```c
#include <sys/timerfd.h>

int timerfd_create(int clockid, int flags);
```
@tab C++
```cpp
#include <sys/timerfd.h>

int ::timerfd_create(int clockid, int flags);
```
:::

#### 1. Типи підтримуваних годинників (`clockid`)

| Ідентифікатор годинника | Поведінка та семантика відліку часу |
| :--- | :--- |
| `CLOCK_MONOTONIC` | Монотонний годинник, що не зазнає стрибків назад. Відлічує час від невизначеної точки в минулому (зазвичай від старту системи). **Не враховує час, коли система перебувала у стані сну (Suspend/Hibernate)** |
| `CLOCK_REALTIME` | Астрономічний системний час цивільного календаря (секунди від Epoch). Може стрибкоподібно змінюватися внаслідок адміністративного налаштування часу або корекції NTP |
| `CLOCK_BOOTTIME` *(Linux 3.15+)* | Монотонний незмінний годинник, який **включає час перебування системи у стані сну (Suspend/Deep Sleep)**. Ідеальний для періодичних фонових демонів на мобільних і серверних платформах |
| `CLOCK_REALTIME_ALARM` *(Linux 3.11+)* | Астрономічний годинник, здатний генерувати апаратне переривання через RTC і **будити систему зі стану глибокого сну (Suspend-to-RAM / S3)**. Вимагає ядерного привілею `CAP_WAKE_ALARM` |
| `CLOCK_BOOTTIME_ALARM` *(Linux 3.11+)* | Монотонний годинник часу завантаження, здатний будити систему зі стану сну. Вимагає ядерного привілею `CAP_WAKE_ALARM` |

#### 2. Прапорці ініціалізації (`flags`)

- `TFD_NONBLOCK` — встановлює прапорець неблокуючого вводу-виводу `O_NONBLOCK` на відкритий дескриптор. Наступні системні виклики `read(2)` повертатимуть `-1` з `errno = EAGAIN` замість блокування потоку, якщо таймер ще не спрацював.
- `TFD_CLOEXEC` — встановлює прапорець закриття при заміні образу процесу `FD_CLOEXEC` на дескриптор. Запобігає витоку відкритого таймера у процеси-нащадки під час викликів `execve(2)`.

#### 3. Коди помилок `timerfd_create`

- `EINVAL` — невідомий `clockid` або некоректні біти у масці `flags`.
- `EMFILE` — досягнуто ліміт відкритих дескрипторів для поточного процесу (`RLIMIT_NOFILE`).
- `ENFILE` — досягнуто загальносистемний ліміт відкритих файлів ядра (`/proc/sys/fs/file-max`).
- `ENODEV` — апаратний годинник не підтримує режим будильника (`_ALARM`).
- `EPERM` — процес не володіє `CAP_WAKE_ALARM` під час спроби створити `CLOCK_REALTIME_ALARM`.

### Системні виклики `timerfd_settime(2)` та `timerfd_gettime(2)`

Керують інтервалами та моментом спрацьовування таймера:

:::tabs
@tab C
```c
#include <sys/timerfd.h>

int timerfd_settime(int fd, int flags,
                    const struct itimerspec *new_value,
                    struct itimerspec *old_value);

int timerfd_gettime(int fd, struct itimerspec *curr_value);
```
@tab C++
```cpp
#include <sys/timerfd.h>

int ::timerfd_settime(int fd, int flags,
                      const struct itimerspec* new_value,
                      struct itimerspec* old_value);

int ::timerfd_gettime(int fd, struct itimerspec* curr_value);
```
:::

#### Структури представлення часу `struct itimerspec`

:::tabs
@tab C
```c
struct timespec {
    time_t tv_sec;  /* Секунди */
    long   tv_nsec; /* Наносекунди: діапазон [0 .. 999 999 999] */
};

struct itimerspec {
    struct timespec it_interval; /* Період повторення (0 = разовий таймер) */
    struct timespec it_value;    /* Час першого спрацьовування (0 = вимкнення таймера) */
};
```
@tab C++
```cpp
#include <ctime>

struct timespec {
    std::time_t tv_sec;  // Секунди
    long        tv_nsec; // Наносекунди: діапазон [0 .. 999 999 999]
};

struct itimerspec {
    struct timespec it_interval; // Період повторення (0 = разовий таймер)
    struct timespec it_value;    // Час першого спрацьовування (0 = вимкнення таймера)
};
```
:::

1. **Правила інтерпретації `it_value`:**
   - Якщо `it_value.tv_sec == 0` і `it_value.tv_nsec == 0`, таймер повністю **деактивується (disarmed)**.
   - Якщо хоча б одне з полів `it_value` ненульове, таймер зводиться на вказаний момент часу.
2. **Правила інтерпретації `it_interval`:**
   - Якщо `it_interval` дорівнює нулю (`0.0`), таймер є **разовим (one-shot)**: після першого спрацьовування він автоматично переходить у стан неактивності.
   - Якщо `it_interval` ненульовий, таймер є **періодичним**: після кожного спрацьовування ядро автоматично додає інтервал до часу наступного пробудження.

#### Прапорці налаштування (`flags`) у `timerfd_settime`

| Прапорець | Числове значення | Семантика інтерпретації часу |
| :--- | :--- | :--- |
| `0` (за замовчуванням) | `0` | **Відносний час (Relative Offset):** `it_value` задає часовий проміжок відносно поточного моменту годинника |
| `TFD_TIMER_ABSTIME` | `1 << 0` | **Абсолютний час (Absolute Time):** `it_value` інтерпретується як абсолютна точка часу на відповідному годиннику |
| `TFD_TIMER_CANCEL_ON_SET` | `1 << 1` | Працює разом із `TFD_TIMER_ABSTIME` на `CLOCK_REALTIME`. Якщо системний годинник зазнає дискретного стрибка (`settimeofday`, `clock_settime`), таймер скасовується, а виклик `read(2)` повертає помилку `ECANCELED` |

### Механіка читання (`read`) та інтеграція з `epoll(7)`

1. **Готовність дескриптора до читання (`EPOLLIN`):** Коли настає момент спрацьовування таймера, ядро інкрементує внутрішній 64-бітний лічильник тиків таймера `expirations` і переводить файловий дескриптор у стан готовності до читання. Диспетчер `epoll_wait()` миттєво повертає подію `EPOLLIN`.
2. **Вимоги до системного виклику `read(2)`:**
   - Додаток зобов'язаний передати у `read()` буфер розміром **щонайменше 8 байтів** (`sizeof(uint64_t)`).
   - Якщо розмір буфера менший за 8 байтів, системний виклик повертає `-1` з `errno = EINVAL`.
   - `read()` повертає `8` (кількість прочитаних байтів), а передана змінна типу `uint64_t` заповнюється числом — кількістю спрацьовувань, які відбулися з моменту попереднього читання або налаштування таймера.
   - Читання скидає внутрішній лічильник ядра назад у `0`.
   - Якщо після виклику `read()` таймер ще не спрацьовував знову:
     - у неблокуючому режимі (`TFD_NONBLOCK`) виклик `read()` повертає `-1` з `errno = EAGAIN` або `EWOULDBLOCK`;
     - у блокуючому режимі потік засинає до наступного спрацьовування.

### Коалесценція таймерів (Timer Coalescing) та затримка тайм-слаку (`prctl`)

На сучасних енергоефективних процесорах кожне апаратне переривання таймера змушує ядра виходити з глибоких енергозберігаючих станів сну (C-states: C6/C7) в активний стан C0, що різко підвищує енергоспоживання та тепловиділення сервера.

Для запобігання надмірній фрагментації переривань ядро Linux починаючи з версії 2.6.28 використовує механізм **Timer Coalescing (коалесценція таймерів)** на основі підсистеми **Range Timers**:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                    ВНУТРІШНЯ СТРУКТУРА HRTIMER В ЯДРІ LINUX                 │
│                                                                             │
│   struct hrtimer {                                                          │
│       struct timerqueue_node node;                                          │
│       │   └── ktime_t        expires;      ──► Жорсткий дедлайн (hard)     │
│       ktime_t                _softexpires; ──► М'який дедлайн (soft)       │
│       enum hrtimer_restart   (*function)(struct hrtimer *);                │
│       struct hrtimer_clock_base *base;                                     │
│       u8                     state;                                         │
│       u8                     is_rel;                                        │
│   };                                                                        │
│                                                                             │
│   Діапазон релаксації: [_softexpires .. node.expires]                        │
│   Довжина вікна = timerslack_ns (або обчислене значення AccuracySec=)       │
└─────────────────────────────────────────────────────────────────────────────┘
```

1. **М'який та жорсткий дедлайни (`_softexpires` проти `expires`):**
   - Функція ядра `hrtimer_set_expires_range_ns(struct hrtimer *timer, ktime_t time, u64 delta)` записує базовий момент часу у поле `_softexpires`, а кінцевий момент `time + delta` — у поле `node.expires`.
   - Якщо під час вставки таймера у червоно-чорне дерево черги `hrtimer_clock_base` ядро виявляє, що інший апаратний таймер уже запланований до спрацьовування в інтервалі `[_softexpires, expires]`, ядро **не перепрограмовує апаратний APIC-таймер**. Таймер спрацює одночасно з раніше запланованою подією.
   - Якщо в зазначеному вікні немає інших подій, апаратний переривач налаштовується строго на жорсткий дедлайн `node.expires`.
2. **Тайм-слак процесу (Timer Slack):** Кожен потік виконання має параметр допустимого відхилення часу спрацьовування таймера `timerslack_ns` (за замовчуванням у просторі користувача — `50 000 нс` = 50 мкс).
3. **Системний виклик налаштування слаку (`prctl`):**
:::tabs
@tab C
```c
#include <sys/prctl.h>

/* Встановлення допустимого вікна коалесценції у 100 мілісекунд (100 000 000 нс) */
prctl(PR_SET_TIMERSLACK, 100000000UL);
```
@tab C++
```cpp
#include <sys/prctl.h>
#include <chrono>

using namespace std::chrono_literals;
// Встановлення допустимого вікна коалесценції у 100 мілісекунд (100 000 000 нс)
constexpr unsigned long kTimerSlackNs = 100'000'000UL;
::prctl(PR_SET_TIMERSLACK, kTimerSlackNs);
```
:::
4. **Відображення у `/proc`:** Поточний активний слак потоку доступний для аудиту через `/proc/<pid>/timerslack_ns`.
5. **Зв'язок із `AccuracySec=` у systemd:**
   - Коли у файлі `.timer` задано `AccuracySec=1min`, менеджер `systemd` під час налаштування дескриптора `timerfd` через виклик `timerfd_settime()` використовує розширене вікно дедлайну або викликає `prctl(PR_SET_TIMERSLACK)`.
   - Ядро Linux об'єднує пробудження десятків системних таймерів (ротація журналів, оновлення баз сертифікатів, очищення тимчасових каталогів) в один спільний апаратний тік, мінімізуючи частоту пробудження ядер CPU зі стану C6/C7 та знижуючи середнє енергоспоживання серверної ферми.

### Промисловий приклад багатотаймерного диспетчера подій на C та C++

Нижче наведено еталонну реалізацію неблокуючого мультиплексора таймерів на основі `timerfd` та `epoll(7)`:

:::tabs
@tab C
```c
#include <sys/timerfd.h>
#include <sys/epoll.h>
#include <unistd.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <errno.h>

#define MAX_EVENTS 8

static int create_timer(int clockid, time_t init_sec, long init_nsec, time_t interval_sec, long interval_nsec) {
    int tfd = timerfd_create(clockid, TFD_NONBLOCK | TFD_CLOEXEC);
    if (tfd < 0) {
        perror("timerfd_create");
        return -1;
    }

    struct itimerspec its;
    its.it_value.tv_sec = init_sec;
    its.it_value.tv_nsec = init_nsec;
    its.it_interval.tv_sec = interval_sec;
    its.it_interval.tv_nsec = interval_nsec;

    if (timerfd_settime(tfd, 0, &its, NULL) < 0) {
        perror("timerfd_settime");
        close(tfd);
        return -1;
    }
    return tfd;
}

int main(void) {
    int epfd = epoll_create1(EPOLL_CLOEXEC);
    if (epfd < 0) {
        perror("epoll_create1");
        return EXIT_FAILURE;
    }

    /* Періодичний таймер: старт через 1 с, повтор щосекунди */
    int tfd_periodic = create_timer(CLOCK_MONOTONIC, 1, 0, 1, 0);
    /* Разовий таймер: старт через 5 с */
    int tfd_oneshot = create_timer(CLOCK_BOOTTIME, 5, 0, 0, 0);

    if (tfd_periodic < 0 || tfd_oneshot < 0) {
        return EXIT_FAILURE;
    }

    struct epoll_event ev;
    ev.events = EPOLLIN;
    ev.data.fd = tfd_periodic;
    epoll_ctl(epfd, EPOLL_CTL_ADD, tfd_periodic, &ev);

    ev.events = EPOLLIN;
    ev.data.fd = tfd_oneshot;
    epoll_ctl(epfd, EPOLL_CTL_ADD, tfd_oneshot, &ev);

    struct epoll_event events[MAX_EVENTS];
    int running = 1;

    while (running) {
        int nfds = epoll_wait(epfd, events, MAX_EVENTS, -1);
        if (nfds < 0) {
            if (errno == EINTR) continue;
            perror("epoll_wait");
            break;
        }

        for (int i = 0; i < nfds; ++i) {
            uint64_t expirations = 0;
            ssize_t s = read(events[i].data.fd, &expirations, sizeof(expirations));

            if (s == sizeof(uint64_t)) {
                if (events[i].data.fd == tfd_periodic) {
                    printf("[CLOCK_MONOTONIC] Періодичний тік. Спрацьовувань: %llu\n",
                           (unsigned long long)expirations);
                } else if (events[i].data.fd == tfd_oneshot) {
                    printf("[CLOCK_BOOTTIME] Разовий таймер спрацював. Завершення циклу.\n");
                    running = 0;
                }
            } else if (s < 0 && errno != EAGAIN) {
                perror("read timerfd");
            }
        }
    }

    close(tfd_periodic);
    close(tfd_oneshot);
    close(epfd);
    return EXIT_SUCCESS;
}
```
@tab C++
```cpp
#include <sys/timerfd.h>
#include <sys/epoll.h>
#include <unistd.h>
#include <cstdint>
#include <iostream>
#include <system_error>
#include <chrono>
#include <vector>

class TimerDescriptor {
public:
    TimerDescriptor(int clockid, std::chrono::nanoseconds initial, std::chrono::nanoseconds interval = std::chrono::nanoseconds{0}) {
        fd_ = ::timerfd_create(clockid, TFD_NONBLOCK | TFD_CLOEXEC);
        if (fd_ < 0) {
            throw std::system_error(errno, std::generic_category(), "timerfd_create failed");
        }

        struct itimerspec its{};
        const auto init_sec = std::chrono::duration_cast<std::chrono::seconds>(initial);
        const auto init_nsec = initial - init_sec;
        its.it_value.tv_sec = init_sec.count();
        its.it_value.tv_nsec = init_nsec.count();

        const auto int_sec = std::chrono::duration_cast<std::chrono::seconds>(interval);
        const auto int_nsec = interval - int_sec;
        its.it_interval.tv_sec = int_sec.count();
        its.it_interval.tv_nsec = int_nsec.count();

        if (::timerfd_settime(fd_, 0, &its, nullptr) < 0) {
            ::close(fd_);
            throw std::system_error(errno, std::generic_category(), "timerfd_settime failed");
        }
    }

    ~TimerDescriptor() noexcept {
        if (fd_ >= 0) {
            ::close(fd_);
        }
    }

    TimerDescriptor(const TimerDescriptor&) = delete;
    TimerDescriptor& operator=(const TimerDescriptor&) = delete;

    TimerDescriptor(TimerDescriptor&& other) noexcept : fd_{other.fd_} {
        other.fd_ = -1;
    }

    TimerDescriptor& operator=(TimerDescriptor&& other) noexcept {
        if (this != &other) {
            if (fd_ >= 0) ::close(fd_);
            fd_ = other.fd_;
            other.fd_ = -1;
        }
        return *this;
    }

    [[nodiscard]] int fd() const noexcept { return fd_; }

    [[nodiscard]] uint64_t read_expirations() const {
        uint64_t expirations{0};
        const ssize_t bytes_read = ::read(fd_, &expirations, sizeof(expirations));
        if (bytes_read == sizeof(uint64_t)) {
            return expirations;
        }
        if (bytes_read < 0 && (errno == EAGAIN || errno == EWOULDBLOCK)) {
            return 0;
        }
        throw std::system_error(errno, std::generic_category(), "timerfd read error");
    }

private:
    int fd_{-1};
};

int main() {
    try {
        const int epfd = ::epoll_create1(EPOLL_CLOEXEC);
        if (epfd < 0) {
            throw std::system_error(errno, std::generic_category(), "epoll_create1 failed");
        }

        using namespace std::chrono_literals;
        TimerDescriptor periodic_timer(CLOCK_MONOTONIC, 1s, 1s);
        TimerDescriptor oneshot_timer(CLOCK_BOOTTIME, 5s);

        epoll_event ev{};
        ev.events = EPOLLIN;
        ev.data.fd = periodic_timer.fd();
        ::epoll_ctl(epfd, EPOLL_CTL_ADD, periodic_timer.fd(), &ev);

        ev.data.fd = oneshot_timer.fd();
        ::epoll_ctl(epfd, EPOLL_CTL_ADD, oneshot_timer.fd(), &ev);

        std::vector<epoll_event> events(8);
        bool running = true;

        while (running) {
            const int nfds = ::epoll_wait(epfd, events.data(), static_cast<int>(events.size()), -1);
            if (nfds < 0) {
                if (errno == EINTR) continue;
                throw std::system_error(errno, std::generic_category(), "epoll_wait failed");
            }

            for (int i = 0; i < nfds; ++i) {
                if (events[i].data.fd == periodic_timer.fd()) {
                    const uint64_t exp = periodic_timer.read_expirations();
                    std::cout << "[CLOCK_MONOTONIC] Періодичний тік. Спрацьовувань: " << exp << '\n';
                } else if (events[i].data.fd == oneshot_timer.fd()) {
                    const uint64_t exp = oneshot_timer.read_expirations();
                    std::cout << "[CLOCK_BOOTTIME] Разовий таймер спрацював (" << exp << "). Завершення.\n";
                    running = false;
                }
            }
        }

        ::close(epfd);
    } catch (const std::exception& ex) {
        std::cerr << "Помилка: " << ex.what() << '\n';
        return EXIT_FAILURE;
    }
    return EXIT_SUCCESS;
}
```
