Автоматизація регулярного обслуговування системи — створення резервних копій, ротація журналів подій, оновлення сертифікатів безпеки та синхронізація баз даних — вимагає надійного механізму відкладеного виконання програм без участі людини. У багатозадачних операційних системах Unix спроба покласти це завдання на інтерактивні термінальні сесії користувачів неминуче призводить до аварій: закриття сеансу вбиває запущені процеси сигналом `SIGHUP`, а ручний запуск сценаріїв унеможливлює дотримання регламентних інтервалів.

Історично найпростішим рішенням здавалося створення індивідуальних нескінченних циклів у фонових сценаріях оболонки, які містять команду `sleep 86400`. Проте такий підхід породжує фатальні системні проблеми: накопичення сотень сплячих процесів у пам'яті ядра, непередбачуваний дрейф астрономічного часу через накладні витрати на виконання корисного навантаження, дублювання запущених копій у разі збоїв та повну втрату розкладу після перезавантаження сервера.

Для розв'язання цих проблем у системі Unix було створено спеціалізовану фонову службу планування — демона `cron`, систему керування розкладами `crontab`, утиліту компенсації простоїв `anacron` та сучасну підсистему таймерів `systemd`. Цей матеріал містить вичерпний інженерний аналіз внутрішньої архітектури планувальників, синтаксису виразів, пасток ізоляції середовища виконання та еволюції до сучасних декларативних таймерів.

## 1. Архітектура та життєвий цикл класичного демона cron

У класичній моделі Unix планувальник завдань реалізовано у вигляді єдиного системного демона (`crond` або `cron`), який запускається під час завантаження ядра з правами суперкористувача `root` і працює як неперервна фонова служба без власного керуючого термінала (детальніше про походження та еволюцію служби читайте у вставці [Еволюція планувальників: від хвилинного опитування V7 до Vixie cron та таймерів systemd](root:sys-unix/scheduled-jobs-cron-anacron/hist-vixie-cron.md)).

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                            ДЖЕРЕЛА РОЗКЛАДІВ                                │
│  • /etc/crontab (системний)       • /etc/cron.d/* (пакети)                  │
│  • /var/spool/cron/crontabs/* (користувацькі таблиці crontab -e)            │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                             ДЕМОН crond / cron                              │
│                                                                             │
│   1. Синхронізація: sleep(60 - now.tm_sec) до секунди 00                    │
│   2. Перевірка змін у каталогах через stat() st_mtime або inotify           │
│   3. Зіставлення полів часу: (хв, год, день, місяць, день_тижня)            │
│   4. Асинхронний збір завершених процесів у циклі waitpid(WNOHANG)          │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │
                                       ▼ (при збігу часу)
┌─────────────────────────────────────────────────────────────────────────────┐
│                       ВИКОНАННЯ ЗАВДАННЯ (НАЩАДОК)                          │
│                                                                             │
│   1. fork() -> створення нового дочірнього процесу                          │
│   2. setgid(), initgroups(), setuid(user) -> зниження привілеїв            │
│   3. chdir($HOME), скидання оточення (PATH=/usr/bin:/bin)                   │
│   4. stdin -> /dev/null, перехоплення stdout/stderr через pipe              │
│   5. execve("/bin/sh", ["sh", "-c", command], envp)                         │
│   6. Відправка виводу через sendmail (якщо задано MAILTO)                   │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Хвилинний цикл синхронізації
Головною одиницею дискретизації часу в класичному демоні `cron` є **одна астрономічна хвилина**. Демон не підтримує інтервали у секунди чи мілісекунди.

Його робочий цикл побудовано таким чином, щоб уникнути накопичення фазового дрейфу:
1. **Обчислення інтервалу сну:** Замість фіксованого виклику `sleep(60)`, який зміщував би початок ітерації через накладні витрати на парсинг і системні виклики, демон зчитує поточний системний час через `time(NULL)`, перетворює його на календарну структуру `struct tm` функцією `localtime()` та обчислює кількість секунд, що залишилися до настання наступної нульової секунди:
:::tabs
@tab C
```c
int seconds_to_sleep = 60 - tm_now.tm_sec;
sleep(seconds_to_sleep);
```
@tab C++
```cpp
int seconds_to_sleep = 60 - tm_now.tm_sec;
std::this_thread::sleep_for(std::chrono::seconds(seconds_to_sleep));
```
:::
2. **Пробудження на секунді 00:** Щойно системний годинник досягає нульової секунди хвилини, демон прокидається і фіксує поточний час.
3. **Перевірка оновлення конфігурацій:** Демон виконує системний виклик `stat()` для каталогів `/etc/cron.d/`, `/var/spool/cron/crontabs/` та файлу `/etc/crontab`. Якщо час останньої модифікації `st_mtime` змінився (або надійшла подія ядра через підсистему `inotify`), демон перечитує змінені файли в оперативну пам'ять, перебудовуючи внутрішній зв'язаний список завдань без необхідності перезапуску служби.
4. **Оцінка черги завдань:** Демон послідовно ітерує по всіх зареєстрованих записах і зіставляє поточні значення хвилини, години, дня місяця, місяця та дня тижня з правилами кожного завдання.
5. **Запуск завдань через fork/exec:** Для кожного рядка, що відповідає поточному моменту часу, створюється окремий процес-нащадок.

Повну робочу модель такого планувальника із зіставленням бітових масок реалізовано у проекті [Реалізація власного планувальника: синхронізація хвилини, бітові маски та керування процесами](root:sys-unix/scheduled-jobs-cron-anacron/proj-minicron.md).

![Архітектура та конвеєр виконання завдань демоном cron](/root/sys/sys-unix/scheduled-jobs-cron-anacron/img/cron-architecture-loop.svg)
*Архітектура та конвеєр виконання завдань демоном cron*

### Конвеєр ізоляції та запуску процесу-нащадка
Коли умова часу виконується, демон запускає ланцюжок підготовки безпечного середовища для нащадка:
1. **Виклик [fork](root:sys-unix/fork-semantics):** Батьківський процес `cron` продовжує свій хвилинний цикл, а виконання корисного навантаження делегується нащадку.
2. **Зниження привілеїв:** Якщо завдання належить звичайному користувачу, дочірній процес (який спочатку успадковує привілеї `root`) викликає `setgid()` для переходу в основну групу користувача, `initgroups()` для завантаження списку додаткових груп із бази [NSS](root:sys-unix/user-database-nss), і фінально `setuid()` для переходу під цільовий UID. Зворотне підвищення привілеїв після цього стає неможливим на рівні ядра.
3. **Зміна робочого каталогу:** Процес викликає `chdir()` у домашній каталог користувача `$HOME`. Якщо домашній каталог недоступний (наприклад, мережева файлова система NFS тимчасово відключена), демон переходить у кореневий каталог `/` або генерує помилку.
4. **Ізоляція дескрипторів:**
   - Стандартний ввід (`stdin`, дескриптор 0) перенаправляється на `/dev/null`. Будь-яка спроба команди прочитати дані з термінала негайно повертає кінець файлу (`EOF`).
   - Стандартний вивід (`stdout`, дескриптор 1) та стандартний вивід помилок (`stderr`, дескриптор 2) спрямовуються у неіменований програмний канал (`pipe`), інший кінець якого зчитується окремим потоком моніторингу демона.
5. **Запуск оболонки через [exec](root:sys-unix/exec-semantics):** Дочірній процес заміщує свій образ викликом:
:::tabs
@tab C
```c
execl("/bin/sh", "sh", "-c", user_command, (char *)NULL);
```
@tab C++
```cpp
execl("/bin/sh", "sh", "-c", user_command.c_str(), nullptr);
```
:::
   Використання оболонки `/bin/sh` є обов'язковим за стандартом POSIX, оскільки рядок команди може містити перенаправлення потоків (`>`, `|`), конкатенацію (`&&`, `;`) та підстановку змінних.
6. **Збір зомбі-процесів:** Щоб уникнути переповнення системної таблиці дескрипторів зомбі-процесами (`<defunct>`), батьківський процес `cron` реєструє обробник сигналу `SIGCHLD`, у якому в неблокуючому режимі викликає `waitpid(-1, &status, WNOHANG)`.

## 2. Анатомія синтаксису crontab та логіка перевірки розкладів

Розклад виконання завдань описується спеціалізованою граматикою. Стандартний рядок таблиці розкладу складається з п'яти часових полів і виконуваної команди.

![Анатомія синтаксису crontab та логіка перевірки умов](/root/sys/sys-unix/scheduled-jobs-cron-anacron/img/crontab-fields-and-matching.svg)
*Анатомія синтаксису crontab та логіка перевірки умов*

### П'ять часових полів
Кожне поле визначає допустиму множину значень для відповідного календарного виміру:
1. **Хвилини (0–59):** Дискретна хвилина запуску.
2. **Години (0–23):** Година доби (0 відповідає півночі).
3. **День місяця (1–31):** Календарне число.
4. **Місяць (1–12 або JAN–DEC):** Порядковий номер або назва місяця.
5. **День тижня (0–7 або SUN–SAT):** День тижня. Значення 0 та 7 відповідають неділі, 1 — понеділку.

Детальний довідник усіх директив, макросів та спеціальних символів наведено у вставці [Формати конфігурації crontab, anacrontab та директиви systemd timers](root:sys-unix/scheduled-jobs-cron-anacron/api-crontab-and-anacrontab.md).

### Спеціальні символи та оператори
- **Зірочка (`*`):** Означає «будь-яке можливе значення» в межах діапазону поля. Наприклад, `*` у полі місяця означає виконання щомісяця.
- **Кома (`,`):** Визначає дискретний список допустимих значень. Запис `1,15,30` у полі хвилин означає запуск на 1-й, 15-й та 30-й хвилинах.
- **Дефіс (`-`):** Задає замкнений діапазон значень. Запис `9-17` у полі годин активує запуск щогодини з 9:00 до 17:00 включно.
- **Скісна риска (`/`):** Визначає крок ітерації по діапазону або по полю зірочки. Запис `*/15` у полі хвилин еквівалентний списку `0,15,30,45`, а запис `1-30/10` позначає хвилини `1,11,21`.

### Критична підводна камінь: правило диз'юнкції (DOM || DOW)
Більшість часових полів об'єднуються між собою за правилом логічного **«І» (кон'юнкція)**: хвилина ПОВИННА збігатися, година ПОВИННА збігатися, і місяць ПОВИНЕН збігатися.

Проте стандарт POSIX.1 та еталонний Vixie cron містять критичний виняток щодо взаємодії між **Днем Місяця (Day of Month, DOM)** та **Днем Тижня (Day of Week, DOW)**:
- Якщо ОДНЕ з цих полів містить зірочку (`*`), а інше обмежене явним числом або списком, діє звичайна кон'юнкція.
- Якщо **ОБИДВА** поля (і DOM, і DOW) містять явні обмеження (тобто жодне з них не є символом `*`), вони об'єднуються через логічне **«АБО» (диз'юнкція)**.

```
                  ┌─────────────────────────────────────┐
                  │ Поля DOM та DOW обидва обмежені?   │
                  │ (жодне з них не є символом '*')     │
                  └──────────────────┬──────────────────┘
                                     │
                    ┌────────────────┴────────────────┐
                    │                                 │
                   ТАК                                НІ
                    │                                 │
                    ▼                                 ▼
       ┌─────────────────────────┐       ┌─────────────────────────┐
       │   Логічне «АБО» (OR)    │       │    Логічне «І» (AND)    │
       │ Спрацьовує, якщо збігся │       │ Спрацьовує лише у разі  │
       │ DOM АБО якщо збігся DOW │       │ одночасного збігу полів │
       └─────────────────────────┘       └─────────────────────────┘
```

Розглянемо практичний приклад, який є класичним джерелом помилок системного адміністрування:
```crontab
0 2 13 * 5 /usr/local/bin/backup.sh
```
Інтуїтивне очікування недосвідченого адміністратора — запуск резервного копіювання лише тоді, коли настає «п'ятниця 13-го». Проте через правило диз'юнкції планувальник виконає цей скрипт:
1. Щомісяця 13-го числа о 02:00 (незалежно від того, який це день тижня);
2. Щоп'ятниці о 02:00 (незалежно від календарного числа місяця).

Якщо необхідно реалізувати запуск виключно у «п'ятницю 13-го», перевірку другої умови виносять у тіло самої команди:
```crontab
0 2 13 * * [ "$(date +\%u)" -eq 5 ] && /usr/local/bin/backup.sh
```

### Системні проти користувацьких розкладів
У структурі каталогів операційної системи розрізняють два формати файлів:

| Критерій | Користувацькі файли (`crontab -e`) | Системні файли (`/etc/crontab`, `/etc/cron.d/*`) |
| :--- | :--- | :--- |
| **Місцезнаходження** | `/var/spool/cron/crontabs/<user>` | `/etc/crontab`, каталог `/etc/cron.d/` |
| **Кількість полів** | 5 полів часу + команда | 5 полів часу + **КОРИСТУВАЧ** + команда |
| **Спосіб зміни** | Тільки через утиліту `crontab` | Пряме редагування адміністратором чи пакетним менеджером |
| **Ідентифікація прав** | За іменем файлу спулу | Шосте поле явно вказує UID/користувача |
| **Права на файл** | `0600` або `0400`, власник — користувач | `0644`, власник — `root:root` |

### Періодичні каталоги та специфіка утиліти run-parts
Окрім файлів зі строгим синтаксисом crontab, у системі існують каталоги `/etc/cron.hourly/`, `/etc/cron.daily/`, `/etc/cron.weekly/` та `/etc/cron.monthly/`. Будь-який виконуваний файл, розміщений у цих каталогах, автоматично виконується з відповідною періодичністю.

Запуск скриптів із цих каталогів здійснюється через системну утиліту `run-parts`, яка має жорсткі правила фільтрації імен файлів:
- **Правило імен у Debian/Ubuntu:** За замовчуванням `run-parts` запускає лише ті файли, назви яких складаються виключно з латинських літер, цифр, символів підкреслення та дефісів (`^[a-zA-Z0-9_-]+$`).
- **Пастка розширення `.sh`:** Якщо адміністратор покладе у `/etc/cron.daily/` скрипт із назвою `backup.sh` або `cleanup.bak`, утиліта `run-parts` **мовчки проігнорує** цей файл через наявність крапки в імені! Це поширена причина, чому додані скрипти ніколи не запускаються.
- **Права на виконання:** Файл зобов'язаний мати біт виконання (`chmod +x`) та коректний [шебанг](root:sys-unix/exec-semantics) у першому рядку (`#!/bin/sh` або `#!/bin/bash`).

### Керування доступом через списки авторизації
Можливість використання утиліти `crontab` звичайними користувачами контролюється файлами `/etc/cron.allow` та `/etc/cron.deny`:
1. Якщо файл `/etc/cron.allow` існує, право редагувати розклади отримують **тільки** ті користувачі, чиї імена явно записані в цьому файлі. Файл `cron.deny` при цьому повністю ігнорується.
2. Якщо `/etc/cron.allow` відсутній, демон звертається до `/etc/cron.deny`: доступ надається всім користувачам, окрім перелічених у чорному списку.
3. Якщо обидва файли відсутні, у більшості сучасних дистрибутивів Linux створення розкладів дозволено лише суперкористувачу `root`.

### Інтеграція зі стеком PAM та обмеженнями ресурсів
Сучасні реалізації демона (зокрема `cronie`) інтегровані зі стеком модулів автентифікації [PAM](root:sys-unix/pam-stack) через конфігураційний файл `/etc/pam.d/crond` (або `/etc/pam.d/cron`).
- Перед запуском кожного завдання нащадок викликає `pam_acct_mgmt()`, перевіряючи, чи не заблоковано обліковий запис у `/etc/shadow` та чи не закінчився термін дії пароля.
- Модуль `pam_limits.so` завантажує системні обмеження з `/etc/security/limits.conf` (максимальний обсяг пам'яті, ліміт відкритих дескрипторів `nofile`, пріоритет процесора `nice`), ізолюючи завдання від надмірного споживання системних ресурсів.

## 3. Пастки та підводні камені середовища виконання cron

Переважна більшість помилок, коли сценарій успішно виконується адміністратором у терміналі вручну, але завершується аварією під час запуску через `cron`, зумовлена специфікою ізоляції фонового середовища.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    ТИПОВІ ПАСТКИ СЕРЕДОВИЩА ВИКОНАННЯ                       │
├────────────────────────────────┬────────────────────────────────────────────┤
│ Пастка                         │ Механізм відмови та рішення                │
├────────────────────────────────┼────────────────────────────────────────────┤
│ 1. Урізаний $PATH              │ PATH=/usr/bin:/bin. Бінарники з /usr/local │
│                                │ дають 127. Рішення: повні абсолютні шляхи. │
│ 2. Відсутність TTY             │ stdin -> /dev/null. Інтерактивні sudo/ssh  │
│                                │ зависають. Рішення: прапорці -n, batch.    │
│ 3. Символ відсотка «%»         │ Розгортається в \n. date +%Y-%m-%d ламає   │
│                                │ команду. Рішення: екранування \%.          │
│ 4. Неперехоплений stdout       │ cron шле пошту через MTA на кожен байт.    │
│                                │ Рішення: перенаправлення в лог, MAILTO="". │
│ 5. Накладання довгих завдань   │ Черговий запуск стартує паралельно з живим.│
│                                │ Рішення: блокування через flock(1).        │
│ 6. Переведення годинників(DST) │ Весняний стрибок пропускає годину, осінній │
│                                │ подвоює. Рішення: UTC або systemd timers.  │
└────────────────────────────────┴────────────────────────────────────────────┘
```

### 1. Урізана змінна середовища `$PATH`
Під час входу користувача в систему через SSH або локальну консоль командна оболонка виконує файли ініціалізації (`/etc/profile`, `~/.bash_profile`, `~/.bashrc`), налаштовуючи розширений `$PATH` (наприклад, додаючи `/usr/local/bin`, `/opt/bin` або `~/.local/bin`).

Демон `cron` запускає команду через невизначену оболонку без завантаження профілів користувача. Значення змінної `$PATH` за замовчуванням жорстко обмежене мінімальним списком:
```bash
PATH=/usr/bin:/bin
```
Якщо скрипт викликає сторонню утиліту `node`, `docker` або `aws` без зазначення повного шляху, оболонка повертає помилку `127: command not found`.

**Інженерні рішення:**
- Явно вказувати повний абсолютний шлях до всіх бінарних файлів (`/usr/local/bin/backup-tool`);
- Оголошувати розширену змінну `PATH` у першому рядку crontab-файлу:
  ```crontab
  PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
  SHELL=/bin/bash
  ```

### 2. Відсутність керуючого термінала (TTY) та ввід даних
Оскільки процес відірваний від сеансу та дескриптор `stdin` перенаправлено на `/dev/null`, будь-яка команда, що очікує інтерактивного введення від користувача, аварійно завершується або зависає:
- `sudo command` намагається зчитати пароль із термінала і завершується помилкою `sudo: a terminal is required to read the password` (якщо не налаштовано директиву `NOPASSWD` у `/etc/sudoers`);
- `ssh user@host` намагається запитати підтвердження автентичності хоста (`StrictHostKeyChecking`) або кодову фразу SSH-ключа;
- `apt-get upgrade` намагається запитати підтвердження `[Y/n]`.

Усі фонові сценарії зобов'язані запускатися у повністю неінтерактивному пакетному режимі (наприклад, `apt-get -y`, `ssh -o BatchMode=yes`).

### 3. Спеціальне значення символу відсотка (`%`)
У специфікації синтаксису crontab символ відсотка `%` має спеціальне призначення:
1. Перший символ `%` у рядку команди, не захищений зворотним слешем (`\`), інтерпретується парсером як кінець командного рядка.
2. Сам символ `%` та всі наступні символи до кінця рядка перетворюються на символи нового рядка (`\n`) і передаються команді на її стандартний ввід (`stdin`).

Спроба виконати форматування дати у звичному вигляді:
```crontab
# ПОМИЛКА: команда розірветься на символі % і завершиться збоєм синтаксису
0 1 * * * tar -czf /backup/data-$(date +%Y-%m-%d).tar.gz /var/data
```
Для коректної передачі символу `%` у командний рядок його необхідно обов'язково екранувати:
```crontab
# ПРАВИЛЬНО: символ відсотка захищено зворотним слешем
0 1 * * * tar -czf /backup/data-$(date +\%Y-\%m-\%d).tar.gz /var/data
```

### 4. Перехоплення виводу, локальна пошта та переповнення дисків
Демон `cron` уважно стежить за дескрипторами `stdout` та `stderr` процесу-нащадка. Якщо виконувана команда згенерувала хоча б один байт виводу, демон намагається надіслати цей текст локальним поштовим агентом (`/usr/sbin/sendmail`) на адресу, вказану у змінній `MAILTO` (за замовчуванням — власнику завдання).

На сучасних серверах, де локальний поштовий сервер (Postfix/Exim) часто не встановлено або не налаштовано:
- Виклики `sendmail` завершуються помилками, які починають циклічно засмічувати системний журнал `syslog`;
- Якщо поштовий сервер активний, папка `/var/mail/root` розростається до десятків гігабайтів через щохвилинний вивід інформаційних повідомлень, що врешті-решт призводить до вичерпання простору або дескрипторів `inode` на кореневому розділі.

**Правила обробки потоків у crontab:**
- Явно перенаправляти інформаційний вивід та помилки у файл системного журналу з ротацією:
  ```crontab
  0 3 * * * /usr/local/bin/nightly-sync.sh >> /var/log/nightly-sync.log 2>&1
  ```
- Якщо вивід не становить інтересу, глушити його:
  ```crontab
  */10 * * * * /usr/local/bin/health-check.sh > /dev/null 2>&1
  ```
- Вимикати поштові сповіщення на рівні конфігураційного файлу:
  ```crontab
  MAILTO=""
  ```

### 5. Гонки та накладання довгих завдань (Job Overlapping)
`cron` запускає завдання строго за годинником, абсолютно не контролюючи, чи завершилася попередня копія цього ж завдання.

Якщо створення резервної копії бази даних призначено щогодини (`0 * * * *`), але через збільшення обсягу даних процес бекапу затримався на 80 хвилин, рівно через 60 хвилин `cron` запустить другий паралельний екземпляр того самого скрипту. Дві копії почнуть одночасно читати та писати в одну базу даних або сховище, викликаючи взаємне блокування транзакцій, перевантаження дискової підсистеми I/O та пошкодження цілісності файлів.

**Запобігання накладанню через блокування файлів ([flock](root:sys-unix/file-locking)):**
Для гарантії єдиного екземпляра завдання використовують утиліту `flock(1)`, яка створює ексклюзивне блокування файлового дескриптора на рівні ядра:
```crontab
0 * * * * flock -n /var/run/db_backup.lock -c "/usr/local/bin/backup-database.sh"
```
Прапорець `-n` (*non-blocking*) вказує утиліті негайно завершити роботу з нульовим або ненульовим статусом без очікування, якщо замок уже утримується попереднім живим процесом.

### 6. Перехід на літній/зимовий час (DST) та часові пояси
У регіонах зі зміною сезонного часу (Daylight Saving Time) виникають дві аномалії:
- **Весняний стрибок уперед (02:00 -> 03:00):** Завдання, призначені на проміжок між 02:00 та 02:59, ризикують бути повністю пропущеними, оскільки ці хвилини не наступають у локальному календарі.
- **Осінній стрибок назад (03:00 -> 02:00):** Завдання в інтервалі повторюваної години можуть запуститися двічі.

Сучасні версії `cronie` містять евристики компенсації стрибків часу, проте найнадійнішим системним рішенням на серверах є налаштування системного годинника у незмінний часовий пояс [UTC](root:sys-unix/wall-clock-and-timezones) (`timedatectl set-timezone UTC`) або використання директиви `CRON_TZ=UTC` всередині таблиці розкладу.

## 4. Періодичні завдання на машинах з перервами в роботі: утиліта anacron

Класичний `cron` проектувався в епоху серверів архітектури мейнфреймів, які функціонували цілодобово. Проте персональні робочі станції, комп'ютери розробників та ноутбуки регулярно вимикаються ввечері або переводяться у сплячий режим (*sleep/suspend*).

Якщо регулярне завдання ротації логів або оновлення кешу призначено на 03:30 ночі, а користувач вимкнув ноутбук о 19:00 і ввімкнув о 09:00 наступного ранку, `cron` просто не зафіксує настання 03:30. У демона немає механізму збереження історії або виявлення пропущених подій: завдання не буде запущено взагалі. На машинах, які ніколи не працюють уночі, такі завдання не виконуватимуться роками.

Для усунення цієї вади було створено утиліту **anacron** (*Anachronistic Cron*).

![Порівняння парадигм виконання: демон cron проти anacron](/root/sys/sys-unix/scheduled-jobs-cron-anacron/img/anacron-vs-cron-model.svg)
*Порівняння парадигм виконання: демон cron проти anacron*

### Принцип роботи та відмінності від cron
`anacron` кардинально відрізняється від класичного демона за своєю філософією:
1. **Дискретизація в днях:** `anacron` не знає понять «хвилини» чи «години доби». Його мінімальний інтервал планування — **1 день**.
2. **Не є постійним фоновим демоном:** Зазвичай `anacron` викликається як короткоживуча утиліта під час старту операційної системи, під час виходу зі сплячого режиму або періодично щогодини через системний `cron`.
3. **Облік пропущеного часу через файли-мітки:** У каталозі `/var/spool/anacron/` для кожного зареєстрованого завдання зберігається однойменний текстовий файл, що містить єдиний рядок — дату останнього успішного запуску у форматі `YYYYMMDD`.

### Структура файлу `/etc/anacrontab`
Формат рядка конфігурації `anacron` складається з чотирьох обов'язкових полів:
```text
# період_у_днях   затримка_у_хвилинах   ідентифікатор   команда
1                 5                     cron.daily      nice run-parts /etc/cron.daily
7                 10                    cron.weekly     nice run-parts /etc/cron.weekly
@monthly          15                    cron.monthly    nice run-parts /etc/cron.monthly
```

**Алгоритм виконання anacron:**
1. Під час старту утиліта читає поточну календарну дату системи.
2. Для кожного рядка зчитується файл `/var/spool/anacron/<ідентифікатор>`.
3. Обчислюється різниця в днях: `різниця = поточна_дата - дата_файлу`.
4. Якщо `різниця >= період_у_днях`, завдання вважається простроченим.
5. Утиліта очікує вказану кількість хвилин (`затримка_у_хвилинах`), після чого запускає команду.
6. Після успішного завершення команди дата в `/var/spool/anacron/<ідентифікатор>` перезаписується на поточну.

### Захист від лавиноподібного навантаження (Thundering Herd)
Якби всі пропущені за ніч завдання (дефрагментація бази, ротація логів, оновлення індексів man) запустилися одночасно в першу секунду після ввімкнення комп'ютера, система зазнала б катастрофічного падіння продуктивності: жорсткий диск був би на 100% зайнятий операціями введення-виведення, заважаючи входу користувача.

Для запобігання цьому в `anacron` впроваджено два механізми:
- **Індивідуальна затримка (delay):** Кожне завдання має фіксовану паузу (наприклад, daily чекає 5 хвилин після ввімкнення, weekly — 10 хвилин, monthly — 15 хвилин).
- **Випадкова затримка (`RANDOM_DELAY`):** Глобальний параметр у `/etc/anacrontab` (наприклад, `RANDOM_DELAY=30`) генерує додаткову псевдовипадкову паузу від 0 до 30 хвилин для кожного запуску, розмиваючи навантаження на сховища та мережу.

## 5. Еволюція до systemd timers: сучасна архітектура та переваги

З переходом більшості сучасних дистрибутивів Linux на системний менеджер [systemd](root:sys-unix/systemd-model) класичний тандем `cron` + `anacron` дедалі частіше замінюється нативним механізмом **таймер-юнітів (`.timer`)**.

У моделі systemd планування реалізовано через розділення обов'язків між парою файлів:
1. **Юніт сервісу (`<name>.service`):** Описує, **ЩО** саме потрібно виконати (команду, робочий каталог, обмеження пам'яті, права доступу);
2. **Юніт таймера (`<name>.timer`):** Описує, **КОЛИ** та з якими умовами потрібно активувати однойменний сервіс.

![Архітектура та інтеграція таймерів у підсистему systemd](/root/sys/sys-unix/scheduled-jobs-cron-anacron/img/systemd-timer-architecture.svg)
*Архітектура та інтеграція таймерів у підсистему systemd*

### Типи розкладів у systemd timers

#### 1. Монотонні таймери (Monotonic Timers)
Запускають подію відносно певного системного стану або події ядра, не залежачи від астрономічного годинника та змін часових поясів:
- `OnBootSec=15min` — через 15 хвилин після завантаження ядра;
- `OnStartupSec=5min` — через 5 хвилин після старту процесу менеджера `systemd` (PID 1);
- `OnUnitActiveSec=1h` — через 1 годину після моменту останньої успішної активації цього сервісу;
- `OnUnitInactiveSec=30min` — через 30 хвилин після повного завершення попереднього циклу роботи сервісу (гарантує фіксовану паузу між ітераціями, повністю усуваючи ризик накладання копій).

#### 2. Календарні таймери (Realtime / Calendar Timers)
Працюють з астрономічним часом за допомогою декларативного синтаксису `OnCalendar=`:
```ini
[Timer]
# Запуск щопонеділка о 04:00 ранку
OnCalendar=Mon *-*-* 04:00:00
# Наздогнати пропущене під час простою (заміна anacron)
Persistent=true
```

### Ключові архітектурні переваги systemd timers

#### 1. Вбудована персистентність (`Persistent=true`)
Директива `Persistent=true` повністю усуває необхідність утиліти `anacron`. Якщо система була вимкнена в момент настання розкладу, `systemd` зберігає мітку часу останнього спрацьовування у файлі `/var/lib/systemd/timers/stamp-<name>.timer`. Під час наступного завантаження менеджер виявляє пропущений інтервал і негайно запускає сервіс.

#### 2. Централізоване структуроване журналювання
Усі потоки виводу (`stdout` та `stderr`) автоматично перехоплюються підсистемою `systemd-journald`. Більше немає потреби в локальному поштовому сервері `sendmail` чи ненадійному перенаправленні в текстові файли логів.

Будь-який запуск інспектується штатними засобами з повною фільтрацією за часом та PID:
```bash
journalctl -u backup-database.service --since "today"
```

#### 3. Контроль ресурсів та ізоляція через cgroups v2
Оскільки завдання є повноцінним сервісом, до нього можна застосувати всі механізми пісочниці та лімітів ядра:
```ini
[Service]
Type=oneshot
ExecStart=/usr/local/bin/heavy-report.sh
# Обмеження ресурсів через cgroups
MemoryMax=2G
CPUQuota=50%
# Безпека та ізоляція
DynamicUser=true
ProtectSystem=strict
ProtectHome=read-only
PrivateTmp=true
```

#### 4. Керування системними залежностями
Сервіс може явно декларувати вимоги до стану інфраструктури:
```ini
[Unit]
Description=Синхронізація віддаленого сховища
After=network-online.target
Wants=network-online.target
```
Таймер не почне виконання завдання, доки мережевий стек не підтвердить наявність підключення до Інтернету.

#### 5. Прозорий моніторинг та діагностика
Утиліта `systemctl list-timers` надає наочну таблицю всіх активних розкладів у системі:
```text
NEXT                         LEFT          LAST                         PASSED       UNIT                         ACTIVATES
Tue 2026-08-25 21:00:00 EEST 1h 2min left  Tue 2026-08-25 20:00:02 EEST 57min ago    sysstat-collect.timer        sysstat-collect.service
Wed 2026-08-26 00:00:00 EEST 4h 2min left  Tue 2026-08-25 00:00:02 EEST 19h ago      logrotate.timer              logrotate.service
Wed 2026-08-26 03:15:00 EEST 7h left       Tue 2026-08-25 03:15:01 EEST 16h ago      backup.timer                 backup.service
```

#### 6. Тимчасові (Transient) таймери через systemd-run
Для разового або динамічного планування завдань у командному рядку без створення постійних файлів юнітів утиліта `systemd-run` повністю витіснила застарілу команду `at`:
```bash
# Запуск разового бекапу через 30 хвилин
systemd-run --on-active="30m" --unit="quick-backup" /usr/local/bin/backup.sh

# Створення динамічного календарного таймера
systemd-run --on-calendar="2026-08-26 04:00:00" /usr/local/bin/db-upgrade.sh
```
Менеджер systemd динамічно генерує тимчасовий юніт в оперативній пам'яті (`/run/systemd/transient/`), виконує його в ізольованому контексті та автоматично очищає після завершення.

#### 7. Користувацькі таймери без привілеїв суперкористувача
Звичайні користувачі можуть керувати власними таймерами без залучення `sudo` через користувацький екземпляр менеджера:
```bash
# Перегляд таймерів поточного користувача
systemctl --user list-timers

# Активація власного таймера у ~/.config/systemd/user/
systemctl --user enable --now user-sync.timer
```
Для того, щоб користувацькі таймери продовжували працювати після закриття SSH-сесії, адміністратор вмикає постійний сеанс через утиліту `loginctl`:
```bash
loginctl enable-linger <username>
```

## 6. Зведена порівняльна таблиця підсистем планування

| Критерій | Класичний cron | anacron | systemd timers |
| :--- | :--- | :--- | :--- |
| **Мінімальна гранулярність** | 1 хвилина | 1 день | 1 мікросекунда |
| **Підтримка монотонного часу** | Відсутня (тільки календар) | Відсутня | Повна (`OnBootSec`, `OnUnitActiveSec`) |
| **Поведінка після вимкнення** | Завдання втрачається | Виконує пропущене за мітками дат | Виконує пропущене (`Persistent=true`) |
| **Журналювання виводу** | Локальна пошта `MAILTO` / pipe | Локальна пошта `MAILTO` | Централізоване у `journald` |
| **Рівень привілеїв** | `root` та окремі користувачі | Тільки `root` | Системні юніти та користувацькі (`--user`) |
| **Обмеження ресурсів** | Немає (лише `nice` / `ulimit`) | Немає (лише `nice`) | Повний контроль cgroups v2 (`MemoryMax`, `CPUQuota`) |
| **Ізоляція файлової системи** | Відсутня | Відсутня | Простори імен (`ProtectSystem`, `PrivateTmp`) |
| **Контроль накладання копій** | Потрібен сторонній `flock` | Послідовний запуск | Нативний (сервіс не стартує двічі) |
| **Інспекція майбутніх запусків** | Ручний парсинг `crontab -l` | Відсутня | Таблиця `systemctl list-timers` |

Вибір інструменту планування в сучасній системі визначається архітектурним контекстом: для простих користувацьких скриптів класичний `crontab` залишається зручним завдяки лаконічності одного рядка; для критичних системних сервісів, резервного копіювання та регламентних процедур стандартом є `systemd.timer`, що гарантує детерміноване журналювання, надійну ізоляцію та відновлення після простоїв.
