# 📋 Довідник системних викликів та псевдофайлів kexec/kdump

Цей довідник описує точний двійковий та файловий інтерфейс підсистем `kexec` і `kdump` у ядрі Linux, включаючи системні виклики `kexec_load` та `kexec_file_load`, відповідні прапорці, структури даних, псевдофайли у `sysfs` та специфікацію заголовка `/proc/vmcore`.

---

## 1. Системні виклики та їхня внутрішня механіка

Ядро Linux експортує два системні виклики для управління гарячим завантаженням коду: класичний `kexec_load` та сучасний `kexec_file_load`. Вибір між ними визначається вимогами щодо політики безпеки операційної системи, використанням механізму UEFI Secure Boot та наявністю розпаковщика точного виконуваного формату всередині ядра.

### 1.1. Системний виклик `kexec_load`

Системний виклик `kexec_load()` приймає від користувацького простору вже підготовлений масив сегментів пам'яті. Утиліта користувача (`kexec-tools`) самостійно читає з диска образ ядра, розпаковує його, розбирає ELF-заголовки або заголовки bzImage і формує список фізичних адрес, за якими ці сегменти мають опинитися.

```c
#include <linux/kexec.h>
#include <sys/syscall.h>

long syscall(SYS_kexec_load, unsigned long entry, unsigned long nr_segments,
             struct kexec_segment *segments, unsigned long flags);
```

#### Параметри системного виклику:
- `entry`: Фізична адреса точки входу нового ядра (наприклад, адреса ассемблерної мітки `startup_64` у 64-бітному режимі на архітектурі x86_64).
- `nr_segments`: Кількість елементів у масиві `segments`. Ядро обмежує цю кількість константою `KEXEC_SEGMENT_MAX` (зазвичай 16 сегментів на завантаження).
- `segments`: Вказівник у користувацькому просторі на масив структур `struct kexec_segment`.
- `flags`: Бітова маска прапорців управління завантаженням та вибором режиму target.

#### Покроковий механізм виконання всередині ядра:
1. **Перевірка прав доступу**: Ядро перевіряє наявність привілею `CAP_SYS_BOOT` у процесу, що викликав системний виклик. За відсутності привілею виклик негайно завершується з помилкою `EPERM`.
2. **Аллокація описувача `struct kimage`**: Функція `kimage_alloc_init()` створює керуючу структуру ядра для відстеження сторінок пам'яті.
3. **Копіювання сегментів**: За допомогою `kimage_load_segment()` ядро копіює буфери користувацького простору у тимчасові сторінки пам'яті (сторінки-джерела), які виділяються за допомогою подвійного зв'язаного списку сторінок-індирекцій.
4. **Призначення сторінок релокації**: Оскільки цільова фізична адреса завантаження нового ядра може бути зайнята поточним працюючим ядром, ядро виділяє тимчасові контрольні сторінки (`control_pages`).
5. **Фіксація образу**: Завантажений образ зберігається в глобальному вказівникові `kexec_image` (для звичайного `kexec`) або `kexec_crash_image` (якщо встановлено прапор `KEXEC_ON_CRASH`).

### 1.2. Системний виклик `kexec_file_load`

Системний виклик `kexec_file_load()` розроблений для підтримки механізму UEFI Secure Boot та централізованого контролю цілісності коду. На відміну від `kexec_load`, який приймає сирі сегменти без можливості перевірки їхнього походження, `kexec_file_load` передає в ядро лише відкриті файлові дескриптори. Ядро Linux самостійно розбирає внутрішню структуру образу `vmlinuz` (формат PE/COFF чи bzImage), витягує цифровий підпис із сертифікатної таблиці та валідує його за допомогою вбудованих ключів ядра (`.builtin_trusted_keys` або `.secondary_trusted_keys`).

```c
#include <linux/kexec.h>
#include <sys/syscall.h>

long syscall(SYS_kexec_file_load, int kernel_fd, int initrd_fd,
             unsigned long cmdline_len, const char *cmdline,
             unsigned long flags);
```

#### Параметри системного виклику:
- `kernel_fd`: Відкритий файловий дескриптор підписаного образу ядра (`vmlinuz` / `bzImage`) у режимі читання (`O_RDONLY`).
- `initrd_fd`: Відкритий файловий дескриптор початкового образу `initramfs` (передається значення `-1`, якщо initramfs не використовується).
- `cmdline_len`: Загальна довжина рядка командного рядка у байтах (включаючи завершальний нульовий символ `\0`).
- `cmdline`: Вказівник на рядок із текстовими параметрами завантаження ядра (наприклад, `"root=UUID=... console=ttyS0"`).
- `flags`: Бітова маска прапорців управління завантаженням.

#### Механізм верифікації підпису та парсингу:
- При виклику ядра парсер `kexec_file_load` звертається до вбудованого обробника форматів ядер (наприклад, `kexec_bzImage64_ops` для x86_64 або `kexec_elf_ops` для ARM64).
- Якщо увімкнено параметр ядра `CONFIG_KEXEC_SIG`, ядро перевіряє цифровий підпис PKCS#7 / X.509, прикріплений до файлу ядра.
- Якщо Secure Boot активовано у firmware і підпис недійсний або підписаний невідомим ключем, виклик повертає помилку `EKEYREJECTED` чи `EPERM`.
- Якщо валідація пройшла успішно, ядро самостійно розбирає образи `vmlinuz` та `initramfs`, виділяє відповідні сегменти й будує внутрішній об'єкт `struct kimage`.

### 1.3. Порівняльний аналіз `kexec_load` та `kexec_file_load`

| Критерій | `kexec_load` | `kexec_file_load` |
| :--- | :--- | :--- |
| **Точка парсингу образу** | У користувацькому просторі (`kexec-tools`) | Всередині ядра Linux |
| **Сумісність із UEFI Secure Boot** | Ні (блокується при включеному lockdown/SecureBoot) | Так (валідує цифровий підпис PKCS#7/X.509) |
| **Передача командного рядка** | Через окремий сегмент пам'яті (`setup_header` / boot parameters) | Прямим параметром `cmdline` у системному виклику |
| **Підтримувані формати** | Будь-які бинарні образи, підготовлені користувачем | Формати, підтримувані внутрішніми ядрами (bzImage, ELF, Image) |
| **Необхідні права** | `CAP_SYS_BOOT` | `CAP_SYS_BOOT` |
| **Вимоги до пам'яті** | Може виділяти буфери у довільних адресах утиліти | Оптимізує виділення сторінок безпосередньо у ядерному просторі |

---

### 1.4. Коди помилок системних викликів

Обидва системні виклики можуть повертати від'ємні значення зі встановленням змінної `errno`:

- **`EPERM`**: Процес не має привілею `CAP_SYS_BOOT`, або ввімкнено режим блокування ядра (`kernel lockdown`), що забороняє неофіційні завантаження.
- **`EINVAL`**: Недійсні прапорці, кількість сегментів перевищує `KEXEC_SEGMENT_MAX`, або адреси `mem` / розміри `memsz` не вирівняні за межею сторінки (`PAGE_SIZE`).
- **`ENOMEM`**: Недостатньо вільної фізичної пам'яті для виділення контрольних сторінок або аварійного буфера crashkernel.
- **`EBUSY`**: Спроба завантажити новий аварійний образ, коли попередній аварійний образ уже виконується або заблокований.
- **`ENOEXEC`**: Переданий файл ядра має невідомий або пошкоджений бінарний формат (для `kexec_file_load`).
- **`EKEYREJECTED`**: Цифровий підпис ядра не збігається із довіреними ключами в базі `.builtin_trusted_keys`.

## 2. Прапорці системних викликів (`flags`)

Бітові прапорці визначають режим використання завантаженого образу та поведінку системного виклику:

| Константа прапорця | Значення | Докладний опис поведінки та застосування |
| :--- | :--- | :--- |
| `KEXEC_ON_CRASH` | `0x00000001` | Завантажити ядро як аварійне (Crash Kernel для kdump). Пам'ять для сегментів виділяється виключно в межах області `crashkernel=`, зарезервованій під час старту первинного ядра. |
| `KEXEC_PRESERVE_CONTEXT` | `0x00000002` | Зберегти контекст поточного ядра при переході. Використовується в гібридних схемах відновлення після сну (suspend/hibernation). |
| `KEXEC_FILE_UNLOAD` | `0x00000001` | Вивантажити раніше завантажений образ ядра з пам'яті для виклику `kexec_file_load`. |
| `KEXEC_FILE_ON_CRASH` | `0x00000002` | Визначити, що завантажуване через `kexec_file_load` ядро призначене для використання під час Kernel Panic (аналог `KEXEC_ON_CRASH`). |
| `KEXEC_FILE_NO_INITRAMFS` | `0x00000004` | Вказати ядру не шукати образ `initramfs` при виконанні `kexec_file_load`. |

## 3. Структури даних ядра та сегментація пам'яті

Підсистема kexec оперує чітко визначеними структурованими описувачами сегментів пам'яті для ізоляції стартового коду від поточного виконання.

### 3.1. Структура `kexec_segment`

Структура `kexec_segment` визначає відображення між буфером у користувацькій пам'яті утиліти та його фінальним місцем у фізичній оперативній пам'яті:

```c
struct kexec_segment {
    const void *buf;   // Вказівник на буфер з даними у користувацькому просторі
    size_t bufsz;      // Розмір даних у користувацькому буфері у байтах
    const void *mem;   // Цільова фізична адреса розміщення в оперативній пам'яті
    size_t memsz;      // Загальний розмір виділеного сегмента у фізичній пам'яті
};
```

Вимога ядра полягає в тому, щоб `memsz` був більшим або дорівнював `bufsz`. Якщо `memsz > bufsz`, ядро автоматично заповнює решту байтів (від `bufsz` до `memsz`) нулями. Це використовується для сегментів `.bss` ядра та неініціалізованих областей даних. Крім того, адреса `mem` та розмір `memsz` мають бути суворо вирівняні за межею сторінки пам'яті `PAGE_SIZE` (4096 байтів на архітектурі x86_64).

---

### 3.2. Внутрішня структура `struct kimage` та індирекційні сторінки

Усі сегменти завантаженого ядра організуються ядром у внутрішню структуру `struct kimage`:

```c
struct kimage {
    kimage_entry_t *head;
    kimage_entry_t *entry;
    struct kexec_segment segment[KEXEC_SEGMENT_MAX];
    unsigned long nr_segments;
    unsigned long start; // Точка входу (entry address)
    struct page *control_code_page;
    unsigned int type; // KEXEC_TYPE_DEFAULT або KEXEC_TYPE_CRASH
};
```

#### Механізм індирекційних сторінок (Indirection Pages):
Оскільки під час гарячого перезавантаження нове ядро має бути розміщене за конкретними фізичними адресами (наприклад, початкові мегабайти RAM), які на момент роботи поточного ядра зайняті кодом і даними, ядро створює **список індирекційних сторінок**.

Кожен елемент списку `kimage_entry_t` являє собою unsigned long слово, де перші біти містять фізичну адресу сторінки, а молодші біти визначають прапор дії:

```c
#define IND_DESTINATION  0x1
#define IND_INDIRECTION  0x2
#define IND_DONE         0x4
#define IND_SOURCE       0x8
```

- **`IND_DESTINATION`**: Вказує фінальну фізичну адресу, куди має бути скопійована наступна сторінка даних.
- **`IND_SOURCE`**: Вказує тимчасову фізичну адресу сторінки, де зараз знаходяться завантажені дані.
- **`IND_INDIRECTION`**: Посилається на наступну сторінку списку покажчиків релокації.
- **`IND_DONE`**: Сигналізує про кінець списку релокації та готовність до передачі керування.

### 3.3. Проміжний виконуваний модуль Purgatory

**Purgatory** — це невеликий ізольований мікрозавантажувач (написаний мовою C та ассемблером), що розміщується між двома ядрами. Purgatory виконує наступні критичні завдання:

1. **Обчислення та перевірка контрольних сум**: Обчислює контрольні суми SHA-256 всіх завантажених сегментів пам'яті і порівнює їх із заздалегідь збереженим хешем. Якщо пам'ять була пошкоджена апаратно або через збій ядра, Purgatory зупиняє execution (викликає `hlt` або нескінченний цикл) для запобігання запуску зіпсованої системи.
2. **Налаштування регістрів CPU**: Переводить CPU у визначений архітектурний стан (наприклад, 64-бітний Flat Protected Mode з вимкненою пагінацією або з базовим Page Table на x86_64).
3. **Передача передавальних параметрів**: Передає вказівник на структуру `boot_params` (zero page) або Device Tree Blob (DTB) у відповідні процесорні регістри (наприклад, `rsi` для x86_64 чи `x0` для ARM64).

---

### 3.4. Архітектурно-специфічні особливості підготовки сегментів

- **x86_64**:
  - Обов'язкова наявність сегмента `zero_page` (`struct boot_params`), який містить інформацію про карту пам'яті E820/EFI, графічний режим, командний рядок та налаштування `initrd`.
  - Точка входу в ядро — ассемблерна мітка `startup_64`.
- **ARM64 (AArch64)**:
  - Образ ядра підключається у форматі `Image` (uncompressed) або `Image.gz`.
  - Обов'язковий сегмент Device Tree Blob (`.dtb`), адреса якого передається у регістрі `x0`. Регистри `x1`, `x2`, `x3` мають дорівнювати 0.
- **S390x / IBM Z**:
  - Сегменти розміщуються з урахуванням специфічних партицій LPAR та префіксних сторінок (Prefix Register).

## 4. Інтерфейси у псевдофайлових системах `/sys` та `/proc`

Підсистема kexec надає простору користувача прозорий стан завантажених ядер та зарезервованих областей пам'яті через псевдофайли у `sysfs` та `procfs`.

### 4.1. Керування та моніторинг через `/sys/kernel/`

| Шлях до псевдофайлу | Права | Опис, формат даних та механізм використання |
| :--- | :--- | :--- |
| `/sys/kernel/kexec_loaded` | `r--r--r--` | Повертає `1`, якщо у пам'яті підготовлено звичайне ядро для kexec; повертає `0`, якщо ядро не завантажено. |
| `/sys/kernel/kexec_crash_loaded` | `r--r--r--` | Повертає `1`, якщо в аварійній зоні завантажено Crash Kernel для kdump; повертає `0`, якщо kdump не активовано. |
| `/sys/kernel/kexec_crash_size` | `rw-r--r--` | Відображає поточний розмір зарезервованої пам'яті `crashkernel` у байтах. Дозволяє власнику root динамічно зменшити або звільнити пам'ять шляхом запису нового значення (наприклад, `echo 0 > /sys/kernel/kexec_crash_size`). |
| `/sys/kernel/notes` | `r--r--r--` | Експортує бінарні структури ELF Notes із записами останнього стану процесорів (регістрів) для поточного ядра. |
| `/sys/kernel/crash_notes` | `r--r--r--` | Вказує фізичну адресу нотаток паніки аварійного ядра для кожного процесора. |

#### Динамічна зміна розміру crashkernel через `sysfs`
Псевдофайл `/sys/kernel/kexec_crash_size` підтримує не лише читання, а й запис нових значень. Це дає змогу адмінським скриптам динамічно регулювати розмір зарезервованого Crash Kernel у працюючій системі:
- Запис `0` у файл (`echo 0 > /sys/kernel/kexec_crash_size`) повністю звільняє зарезервовану пам'ять `crashkernel`, повертаючи її у загальний розпорядник сторінок пам'яті ядра (Buddy Allocator).
- Запис меншого значення зменшує розмір зарезервованого блоку. Збільшення розміру після старту системи заборонено, оскільки ядро не може гарантувати наявність суцільного фізичного блоку RAM необхідного обсягу.

---

### 4.2. Аналіз фізичного розподілу через `/proc/iomem`

Псевдофайл `/proc/iomem` містить повну карту відображення фізичних адрес вхідної/вихідної пам'яті та системної RAM. Утиліти `kexec` та `makedumpfile` використовують його для виявлення зарезервованого аварійного регіону:

```text
00000000-00000fff : Reserved
00001000-0009fbff : System RAM
00100000-6f7fffff : System RAM
  2a000000-39ffffff : Crash kernel
70000000-7fffffff : ACPI Non-volatile Storage
```

Запис `Crash kernel` показує точні фізичні границі (наприклад, від `0x2a000000` до `0x39ffffff`), у межах яких системний виклик `kexec_load` із прапорцем `KEXEC_ON_CRASH` розміщує аварійне ядро та його initramfs.

---

### 4.3. Командний рядок аварійного ядра у `/proc/cmdline`

Командний рядок завантаження аварійного ядра має відрізнятися від командного рядка основи. Типові параметри включають:

- **`nr_cpus=1` або `maxcpus=1`**: Обмежує аварійне ядро використанням лише одного ядра CPU. Це суттєво прискорює ініціалізацію та виключає гонки переривань.
- **`reset_devices`**: Заставляє драйвери периферійних пристроїв (PCIe, NVMe, Ethernet) виконувати повне апаратне скидання (hard reset) перед ініціалізацією, оскільки контролери можуть знаходитися у невизначеному стані після Kernel Panic.
- **`cgroup_disable=memory`**: Вимикає підсистему cgroups пам'яті для заощадження RAM у середовищі kdump.
- **`elfcorehdr=0x...`**: Вказує аварійному ядру фізичну адресу заголовка `elfcorehdr`, підготовленого первинним ядром при виникненні паніки.

---

## 5. Специфікація псевдофайлу `/proc/vmcore`

Під час роботи аварійного ядра (Crash Kernel) підсистема kdump створює у псевдофайловій системі `procfs` об'єкт `/proc/vmcore`. Цей файл описує всю фізичну оперативну пам'ять померлого ядра у стандартному форматі ELF Core Dump 64-біт (`Elf64_Ehdr`).

### 5.1. Формат ELF64 Core Dump: `Elf64_Ehdr` та програмні заголовки

Файл розпочинається зі стандартного заголовка `Elf64_Ehdr`:
1. `e_ident`: Магічні байти ELF (`\x7fELF`), клас `ELFCLASS64`, кодування даних `ELFDATA2LSB`.
2. `e_type`: Тип ELF-файлу встановлюється в `ET_CORE` (значення `4`).
3. `e_machine`: Архітектура процесора (наприклад, `EM_X86_64` або `EM_AARCH64`).
4. `e_phnum`: Кількість програмних заголовків (`Elf64_Phdr`), які слідують одразу за основним заголовком.

#### Заголовки програмних сегментів (`Elf64_Phdr`):

- **Сегменти `PT_NOTE`**: Описують спецсегменти нотаток пам'яті. Кожен запис `PT_NOTE` посилається на бінарний блок нотатки, який містить:
  - `crash_notes`: Записи регістрів CPU на момент аварії (структура `elf_prstatus`).
  - `VMCOREINFO`: Текстовий блок метаданих розкладки ядра.
- **Сегменти `PT_LOAD`**: Відповідають суцільним діапазонам фізичної пам'яті померлого ядра. Поле `p_paddr` описує фізичну адресу RAM, `p_memsz` — розмір діапазону, а `p_offset` — зміщення всередині файлу `/proc/vmcore`.

---

### 5.2. Деталізація структури `elf_prstatus`

Кожен CPU у первинній системі перед панічним переходом зберігає свій стан у структуру `struct elf_prstatus` у нотатці `PT_NOTE`:

```c
struct elf_prstatus {
    struct elf_siginfo pr_info;    // Інформація про сигнал аварії
    short pr_cursig;               // Поточний сигнал
    unsigned long pr_sigpend;      // Зависші сигнали
    unsigned long pr_sighold;      // Заблоковані сигнали
    pid_t pr_pid;                  // PID процесу, що виконувався на цьому CPU
    pid_t pr_ppid;                 // PPID батьківського процесу
    pid_t pr_pgrp;                 // Група процесів
    pid_t pr_sid;                  // Сесія
    struct user_regs_struct pr_reg;// Збережені апаратні регістри CPU (RAX, RBX, RIP, RSP, RFLAGS)
};
```

---

### 5.3. Деталізація полів метаданих `VMCOREINFO`

Блок `VMCOREINFO` оформлюється як ELF-нотатка з ім'ям `"VMCOREINFO"`. Текст всередині складається з рядків формату `KEY=VALUE`, які критично необхідні інструментам `makedumpfile` та `crash`:

```text
OSRELEASE=6.8.0-40-generic
PAGESIZE=4096
SYMBOL(init_uts_ns)=ffffffff82c14480
SYMBOL(node_online_map)=ffffffff82c40c60
SYMBOL(contig_page_data)=ffffffff82d5a100
SIZE(task_struct)=11264
OFFSET(task_struct.tasks)=928
OFFSET(task_struct.pid)=1248
OFFSET(page.flags)=0
OFFSET(page._refcount)=28
NUMBER(KERNEL_IMAGE_SIZE)=1073741824
KERNELOFFSET=1f000000
CRASHTIME=1723620000
```

#### Значення основних параметрів `VMCOREINFO`:
- `PAGESIZE`: Розмір сторінки віртуальної пам'яті в байтах. Дозволяє відлагоджувачу правильно крокувати по таблицях сторінок.
- `KERNELOFFSET`: Величина зміщення KASLR. Оскільки нові версії ядра завантажуються за випадковими віртуальними адресами у верхньому просторі, `KERNELOFFSET` вказує точну різницю між адресами в файлі `vmlinux` та реальними адресами у пам'яті.
- `OFFSET(task_struct.pid)`: Зміщення поля ідентифікатора процесу всередині структури `task_struct`. Дозволяє утиліті `crash` відновлювати дерево процесів навіть при зміні версій ядра.
- `SYMBOL(contig_page_data)`: Адреса головного структурного вузла пам'яті для архітектур UMA або NUMA.

---

### 5.4. Внутрішні механізми доступу ядра до старої пам'яті

Під час читання `/proc/vmcore` аварійне ядро виконує звернення до фізичної оперативної пам'яті первинного ядра, яка не підключена до поточних таблиць сторінок аварійного ядра. Для цього ядро використовує функціонал `copy_oldmem_page()` або `read_from_oldmem()`:

- **`ioremap_cache()` / `kmap_atomic()`**: Аварійне ядро тимчасово відображає фізичні сторінки старого ядра у свій віртуальний простір адресації.
- **Оптимізація `vmcore_mmap`**: Замість послідовного виклику `read()` утиліти типу `makedumpfile` можуть мапувати `/proc/vmcore` безпосередньо в свій простір користувача через `mmap()`, що значно прискорює збереження дампу пам'яті обсягом у сотні гігабайтів.

---

### 5.5. Механізм формування `VMCOREINFO` у ядрі

Макроси `VMCOREINFO_SYMBOL()`, `VMCOREINFO_SIZE()`, `VMCOREINFO_OFFSET()` та `VMCOREINFO_NUMBER()` використовуються у вихідному коді ядра для автоматичної реєстрації фізичних характеристик структур.

Під час компіляції ядра та в процесі його старту функція `crash_save_vmcoreinfo()` записує сформовані текстові рядки метаданих у зарезервований буфер ELF-нотаток. Це гарантує, що при виникненні Kernel Panic утиліти обробки дампу пам'яті (`makedumpfile` та `crash`) мають вичерпну інформацію про геометрію структур даних без необхідності завантаження громіздкого налагоджувального образу `vmlinux` на аварійній системі.

### 6.2. Програмний виклик `kexec_file_load`

:::tabs
@tab C
```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/syscall.h>
#include <errno.h>

#ifndef SYS_kexec_file_load
#define SYS_kexec_file_load 320
#endif

int load_kernel_image(const char *kernel_path, const char *initrd_path, const char *cmdline) {
    int kfd = open(kernel_path, O_RDONLY);
    if (kfd < 0) {
        perror("Помилка відкриття файлу ядра");
        return -1;
    }

    int ifd = -1;
    if (initrd_path != NULL) {
        ifd = open(initrd_path, O_RDONLY);
        if (ifd < 0) {
            perror("Помилка відкриття файлу initrd");
            close(kfd);
            return -1;
        }
    }

    unsigned long cmdline_len = cmdline ? strlen(cmdline) + 1 : 0;
    long res = syscall(SYS_kexec_file_load, kfd, ifd, cmdline_len, cmdline, 0);

    if (ifd >= 0) close(ifd);
    close(kfd);

    if (res < 0) {
        perror("Помилка виконання kexec_file_load");
        return -1;
    }

    printf("Ядро успішно завантажено в пам'ять через kexec_file_load\n");
    return 0;
}
```

@tab C++
```cpp
#include <iostream>
#include <string>
#include <string_view>
#include <system_error>
#include <fcntl.h>
#include <unistd.h>
#include <sys/syscall.h>

#ifndef SYS_kexec_file_load
#define SYS_kexec_file_load 320
#endif

class ScopedFd {
    int fd_{-1};
public:
    explicit ScopedFd(int fd) : fd_(fd) {}
    ~ScopedFd() { if (fd_ >= 0) ::close(fd_); }
    ScopedFd(const ScopedFd&) = delete;
    ScopedFd& operator=(const ScopedFd&) = delete;
    ScopedFd(ScopedFd&& o) noexcept : fd_(o.fd_) { o.fd_ = -1; }
    ScopedFd& operator=(ScopedFd&& o) noexcept {
        if (this != &o) {
            if (fd_ >= 0) ::close(fd_);
            fd_ = o.fd_;
            o.fd_ = -1;
        }
        return *this;
    }
    [[nodiscard]] int get() const noexcept { return fd_; }
    [[nodiscard]] bool valid() const noexcept { return fd_ >= 0; }
};

void load_kernel(std::string_view kernel_path, std::string_view initrd_path, std::string_view cmdline) {
    ScopedFd kfd(::open(kernel_path.data(), O_RDONLY));
    if (!kfd.valid()) {
        throw std::system_error(errno, std::generic_category(), "Не вдалося відкрити ядро");
    }

    ScopedFd ifd(-1);
    if (!initrd_path.empty()) {
        ifd = ScopedFd(::open(initrd_path.data(), O_RDONLY));
        if (!ifd.valid()) {
            throw std::system_error(errno, std::generic_category(), "Не вдалося відкрити initrd");
        }
    }

    const unsigned long cmdlen = cmdline.empty() ? 0 : cmdline.size() + 1;
    const long ret = ::syscall(SYS_kexec_file_load, kfd.get(), ifd.get(), cmdlen, cmdline.data(), 0);

    if (ret < 0) {
        throw std::system_error(errno, std::generic_category(), "kexec_file_load завершився помилкою");
    }

    std::cout << "Ядро успішно завантажено у пам'ять через kexec_file_load\n";
}
```
