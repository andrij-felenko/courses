# ⚙️ Практикум діагностики: ізоляція збоїв та трасування suspend/resume

Збої під час переходу в системний сон та виходу з нього — одна з найскладніших проблем системного адміністрування та розробки драйверів ядра. Проблема полягає в тому, що коли машина зависає на півдорозі до стану S3 чи під час раннього пробудження, стандартні механізми логування (такі як `syslog` чи `systemd-journald`) уже вимкнені або ще не ініціалізовані. Типові симптоми варіюються від «чорного екрана» із завислими на повних обертах кулерами охолодження до раптового миттєвого самопробудження або зависання під час скидання живлення контролера NVMe чи відеокарти.

Нижче наведено покроковий алгоритм локалізації несправностей за допомогою напівкроків `pm_test`, аналізу ранніх повідомлень ядра, трасування затримок через `ftrace` та усунення перегонів під час виклику з простору користувача.

## Крок 1. Покрокова ізоляція фаз через `pm_test`

Перш ніж намагатися діагностувати зависання на рівні апаратного сну, необхідно точно локалізувати, яка саме підсистема ядра дає збій. Замість ризикованого повного знеструмлення платформи використовують налагодовий механізм `/sys/power/pm_test`, який виконує окремі фази призупинення, витримує паузу в 5 секунд і негайно запускає зворотне відновлення.

Тестування проводять суворо послідовно від найвищого логічного рівня до найнижчого:

```bash
# 1. Перевірка підсистеми заморожування процесів (Freezer)
sudo sh -c "echo freezer > /sys/power/pm_test"
sudo sh -c "echo mem > /sys/power/state"

# 2. Перевірка зворотних викликів драйверів пристроїв (DPM)
sudo sh -c "echo devices > /sys/power/pm_test"
sudo sh -c "echo mem > /sys/power/state"

# 3. Перевірка платформних викликів ACPI / Device Tree
sudo sh -c "echo platform > /sys/power/pm_test"
sudo sh -c "echo mem > /sys/power/state"

# 4. Перевірка відключення вторинних ядер процесора (CPU Hotplug)
sudo sh -c "echo processors > /sys/power/pm_test"
sudo sh -c "echo mem > /sys/power/state"

# 5. Перевірка зупинки системних переривань (syscore)
sudo sh -c "echo core > /sys/power/pm_test"
sudo sh -c "echo mem > /sys/power/state"

# Повернення до нормального режиму після завершення тестів
sudo sh -c "echo none > /sys/power/pm_test"
```

Кожен рівень тесту дає чітку відповідь про місце поломки:
- Якщо система зависає вже на етапі `freezer`, винуватцем є користувацький процес або ядерний потік у стані неперервного очікування (`TASK_UNINTERRUPTIBLE`), який заблокував дискову чергу введення-виведення або завис на сокеті мережевої файлової системи (NFS, SMB, FUSE).
- Якщо зависання стається на етапі `devices`, помилка виникає в конкретному драйвері периферії, чий зворотний виклик `suspend` або `resume` входить у нескінченний цикл очікування апаратного регістра.
- Якщо зависання проявляється на кроці `processors`, проблему спричиняє механізм відключення процесорних ядер `disable_nonboot_cpus()` — наприклад, коли таймери процесора не вдається мігрувати на нульове ядро.

## Крок 2. Збір налагодових логів через параметри ядра

За замовчуванням ядро вимикає консоль (`tty`) на ранніх фазах призупинення, щоб уникнути конфліктів із драйвером відеокарти під час зміни відеорежимів. Якщо драйвер падає після вимкнення консолі, повідомлення про паніку ядра (`kernel panic`) не потрапляє на екран і не зберігається на диск.

Щоб зберегти вивід діагностики, у параметри завантаження ядра (через конфігурацію завантажувача GRUB у файлі `/etc/default/grub` або під час вибору пункту меню) додають спеціальний набір прапорців:

```text
no_console_suspend initcall_debug ignore_loglevel pm_debug_messages
```

Призначення кожного з цих параметрів:
- `no_console_suspend` — забороняє ядру присипляти графічну або послідовну консоль, дозволяючи бачити аварійні повідомлення драйверів аж до моменту повної апаратної зупинки процесора.
- `initcall_debug` — змушує підсистему живлення друкувати в кільцевий буфер ядра точний час початку та завершення кожного зворотного виклику `dev_pm_ops` із зазначенням мілісекунд та коду повернення.
- `ignore_loglevel` — гарантує негайний вивід усіх рівнів повідомлень включно з `KERN_DEBUG` прямо на екран.
- `pm_debug_messages` — вмикає детальні трасування черги `dpm_list` та взаємозв'язків між пристроями.

Після успішного пробудження або під час перегляду збереженого журналу виявляють найповільніші пристрої, які затримують перехід у сон:

```bash
# Фільтрація журналу ядра за тривалістю виконання зворотних викликів DPM
sudo dmesg | grep -E "call.*returned" | sort -k8 -n -r | head -n 15
```

## Крок 3. Візуальне профілювання через SleepGraph (Ftrace)

Утиліта `sleepgraph` (з офіційного набору інструментів `pm-graph`) автоматично налаштовує підсистему `ftrace`, програмує апаратний будильник RTC на пробудження через заданий інтервал часу та формує інтерактивний графік часової шкали у форматі HTML.

```bash
# Запуск автоматичного тесту сну з пробудженням через 10 секунд
sudo sleepgraph -m mem -rtcwake 10 -f -dev
```

Згенерований звіт `suspend-resume.html` відображає детальний часовий розріз:
1. Повну часову шкалу виконання кожного виклику `suspend`, `suspend_late`, `suspend_noirq` та їхніх парних викликів `resume` для кожного пристрою на шинах PCI, USB, I²C та платформи.
2. Точну тривалість фази виведення з ладу вторинних процесорних ядер (`cpu_down` / CPU Hotplug).
3. Тривалість роботи низькорівневої прошивки BIOS/UEFI між знеструмленням платформи та передачею керування вектору ядра Linux (параметр *Firmware execution time*).

## Крок 4. Пошук збоїв раннього пробудження через RTC Hash (`pm_trace`)

Якщо машина зависає наглухо під час виходу з S3 до того, як ядро встигає підняти дисплей, ініціалізувати послідовний порт або зберегти дані в пам'ять, застосовують апаратний трекер `CONFIG_PM_TRACE_RTC`.

Перед кожним критичним викликом `dev_pm_ops` ядро обчислює хеш із назви поточного драйвера і номера рядка у вихідному коді та записує цей хеш у комірку енергонезалежної пам'яті CMOS годинника реального часу RTC (де в звичайному режимі зберігаються секунди дати).

```bash
# 1. Увімкнення апаратного збереження хешу в RTC
sudo sh -c "echo 1 > /sys/power/pm_trace"

# 2. Спроба переходу в сон
sudo sh -c "echo mem > /sys/power/state"

# 3. Якщо система зависла — виконуємо апаратний скид (кнопкою живлення / Reset),
# після завантаження читаємо винуватця збігу збереженого хешу:
sudo dmesg | grep "Magic number"
cat /sys/power/pm_trace_dev_match
```

Після завантаження ядро зчитує збережене магічне число з пам'яті RTC і зіставляє його з внутрішньою хеш-таблицею зареєстрованих драйверів, виводячи в консоль назву конкретного пристрою, на чиєму виклику система зазнала фатального збою.

## Крок 5. Діагностика самовільного пробудження (*Spurious Wakeup*)

Частою проблемою є ситуація, коли комп'ютер засинає і через 1–2 секунди самостійно прокидається. Причиною зазвичай є пристрої, які хибно генерують сигнал системного пробудження (наприклад, оптична миша на вібруючому столі, мережева карта з увімкненим Wake-on-LAN або таймер материнської плати).

Для аналізу джерел пробудження використовують інтерфейс ядра `debugfs`:

```bash
# Перевірка статистики подій усіх зареєстрованих джерел пробудження
sudo cat /sys/kernel/debug/wakeup_sources
```

У стовпцях виводу звертають увагу на `event_count` (кількість згенерованих сигналів) та `active_since` (чи блокує пристрій сон прямо зараз). Щоб заборонити проблемному пристрою (наприклад, USB-миші на порту `usb1`) будити систему, достатньо записати заборону у відповідний атрибут `sysfs`:

```bash
sudo sh -c "echo disabled > /sys/bus/usb/devices/usb1/power/wakeup"
```

## Крок 6. Безпечна ініціація сну з простору користувача

Просте виконання `echo mem > /sys/power/state` містить критичне вікно перегонів: якщо користувач натисне клавішу або прийде мережевий пакет за частку секунди до запису, подія буде зафіксована контролером, але не оброблена застосунком, і ноутбук засне всупереч бажанню користувача.

Правильний алгоритм використовує механізм атомарної верифікації через `/sys/power/wakeup_count`.

:::tabs
```c
/* userspace_suspend.c: безпечний перехід у сон без втрати подій */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>

int trigger_safe_suspend(void)
{
    char count_buf[64];
    int count_fd, state_fd;
    ssize_t bytes_read, bytes_written;

    /* Крок 1. Читаємо поточну кількість подій пробудження */
    count_fd = open("/sys/power/wakeup_count", O_RDWR);
    if (count_fd < 0) {
        perror("Не вдалося відкрити /sys/power/wakeup_count");
        return -errno;
    }

    bytes_read = read(count_fd, count_buf, sizeof(count_buf) - 1);
    if (bytes_read <= 0) {
        perror("Помилка читання лічильника подій");
        close(count_fd);
        return -EIO;
    }
    count_buf[bytes_read] = '\0';

    /* Крок 2. Атомарно записуємо зчитане значення назад у файл */
    lseek(count_fd, 0, SEEK_SET);
    bytes_written = write(count_fd, count_buf, strlen(count_buf));
    if (bytes_written < 0) {
        if (errno == EINVAL) {
            fprintf(stderr, "Подію пробудження зафіксовано перед сном! Призупинення скасовано.\n");
        } else {
            perror("Помилка запису в wakeup_count");
        }
        close(count_fd);
        return -errno;
    }
    close(count_fd);

    /* Крок 3. Ініціюємо перехід у сон */
    state_fd = open("/sys/power/state", O_WRONLY);
    if (state_fd < 0) {
        perror("Не вдалося відкрити /sys/power/state");
        return -errno;
    }

    printf("Перевірка успішна. Перехід у стан сну mem...\n");
    if (write(state_fd, "mem\n", 4) < 0) {
        perror("Помилка під час переходу в сон");
        close(state_fd);
        return -errno;
    }

    close(state_fd);
    printf("Система успішно прокинулася зі стану сну.\n");
    return 0;
}

int main(void)
{
    return trigger_safe_suspend() == 0 ? EXIT_SUCCESS : EXIT_FAILURE;
}
```
```cpp
// userspace_suspend.cpp: ідіоматична обгортка RAII для безпечного сну
#include <iostream>
#include <fstream>
#include <string>
#include <system_error>
#include <expected>

class PowerManager {
public:
    static std::expected<void, std::error_code> trigger_safe_suspend() {
        std::string wakeup_count_str;

        // Крок 1. Читаємо актуальне значення лічильника
        {
            std::ifstream count_in("/sys/power/wakeup_count");
            if (!count_in.is_open()) {
                return std::unexpected(std::make_error_code(std::errc::no_such_file_or_directory));
            }
            if (!(count_in >> wakeup_count_str)) {
                return std::unexpected(std::make_error_code(std::errc::io_error));
            }
        }

        // Крок 2. Атомарно верифікуємо лічильник записом назад
        {
            std::ofstream count_out("/sys/power/wakeup_count");
            if (!count_out.is_open()) {
                return std::unexpected(std::make_error_code(std::errc::permission_denied));
            }
            count_out << wakeup_count_str;
            count_out.flush();
            if (count_out.fail()) {
                std::cerr << "Подію пробудження зафіксовано перед сном! Призупинення скасовано.\n";
                return std::unexpected(std::make_error_code(std::errc::invalid_argument));
            }
        }

        // Крок 3. Ініціюємо перехід у сон
        {
            std::ofstream state_out("/sys/power/state");
            if (!state_out.is_open()) {
                return std::unexpected(std::make_error_code(std::errc::permission_denied));
            }
            std::cout << "Перевірка успішна. Перехід у стан сну mem...\n";
            state_out << "mem\n";
            state_out.flush();
            if (state_out.fail()) {
                return std::unexpected(std::make_error_code(std::errc::io_error));
            }
        }

        std::cout << "Система успішно прокинулася зі стану сну.\n";
        return {};
    }
};

int main() {
    auto result = PowerManager::trigger_safe_suspend();
    if (!result) {
        std::cerr << "Помилка призупинення: " << result.error().message() << '\n';
        return 1;
    }
    return 0;
}
```

Програма спочатку зчитує лічильник подій пробудження і записує його назад. Якщо між цими двома викликами клавіатура або мережева карта зафіксувала активність, ядро відхилить запис помилкою `EINVAL`, і процес не стане записувати `mem` у `/sys/power/state`, врятувавши користувача від втрати важливої дії.
