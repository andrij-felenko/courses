Коли фоновий чи дочірній процес у терміналі завершує роботу через системний виклик `exit_group()`, ядро Linux надсилає сигнал `SIGCHLD` батьківському процесу командної оболонки. Оболонка зчитує статус завершення через `waitpid()`, відновлює контроль над керівним терміналом викликом `tcsetpgrp()`, перемикає дисципліну лінії у неканонічний режим і виводить у стандартний потік помилок або виводу текстовий рядок запрошення. Цей рядок є не просто декоративним елементом інтерфейсу: він слугує візуальним контрактом синхронізації між людиною та операційною системою, повідомляючи, хто саме виконує команди, у якому каталозі перебуває процес, які привілеї доступні та чи успішно завершилася попередня дія.

Історично командні інтерпретатори пройшли шлях від жорстко зашитого в бінарний код символу `%` на паперових телетайпах до гнучких багатошарових систем динамічного рендерингу. Детальний опис цього шляху наведено в [Історії еволюції командного запрошення в Unix](root:sys-unix/shell-prompt/hist-prompt-evolution.md). У сучасних оболонках GNU Bash, Zsh та Korn Shell керування запрошенням розподілено між чотирма спеціальними змінними, вбудованими керівними послідовностями та подієвими хуками.

## 1. Ієрархія змінних запрошення: PS1, PS2, PS3 та PS4

В операційних системах сімейства Unix процес введення та інтерпретації команд розділений на кілька чітко розмежованих станів. За кожен із цих станів відповідає окрема змінна з префіксом `PS` (Prompt String).

![Ієрархія змінних запрошення оболонки](/root/sys/sys-unix/shell-prompt/img/prompt-hierarchy.svg)

### Первинне запрошення: PS1
Змінна `PS1` (Prompt String 1) визначає вигляд основного рядка запрошення, який користувач бачить у стані очікування нової команди. Оболонка виводить `PS1` лише тоді, коли вона працює в інтерактивному режимі (`$-` містить прапорець `i`), стандартний потік вводу підключено до термінала (`isatty(STDIN_FILENO) == 1`), а синтаксичний парсер перебуває в нейтральному початковому стані (всі попередні синтаксичні конструкції повністю завершені).

За замовчуванням у GNU Bash значення `PS1` встановлено як `\s-\v\$ ` (що розгортається, наприклад, у `bash-5.2$ `), проте дистрибутиви Linux зазвичай перевизначають його у системних конфігураціях `/etc/bash.bashrc` на інформативніші шаблони на кшталт `\u@\h:\w\$ `.

Перш ніж `PS1` потрапить на екран, оболонка виконує три послідовні фази обробки:
1. **Виконання передвиконавчих хуків:** запуск інструкцій або масиву функцій, зареєстрованих у змінній `PROMPT_COMMAND`;
2. **Розгортання керівних послідовностей:** підстановка бекслеш-символів (`\u`, `\h`, `\w`, `\$`);
3. **Параметричне розгортання та підстановка команд:** обчислення виразів `${VAR}` та `$(...)`, якщо рядок `PS1` було визначено в одинарних лапках.

### Вторинне запрошення продовження: PS2
Змінна `PS2` активується тоді, коли користувач натиснув клавішу `Enter`, але синтаксичний аналізатор оболонки виявив, що граматична конструкція є неповною і вимагає додаткових рядків для побудови валідного абстрактного синтаксичного дерева (AST).

Оболонка виводить `PS2` (за замовчуванням `> `) у таких ситуаціях:
1. **Непарні лапки:** відкрито одинарну (`'`) або подвійну (`"`) лапку, яка не була закрита перед символом переходу на новий рядок:
   ```bash
   $ echo "рядок 1
   > рядок 2"
   ```
2. **Багаторядкові керівні блоки:** введено початок складеної команди (`if`, `while`, `for`, `case`, `until`, `select`), тіло якої ще не завершено відповідним ключовим словом (`fi`, `done`, `esac`):
   ```bash
   $ for f in *.txt; do
   >   gzip "$f"
   > done
   ```
3. **Незавершені конвеєри та логічні оператори:** рядок завершується символом конвеєра `|`, логічним `&&` або `||`, що передбачає обов'язкову наявність правої частини виразу:
   ```bash
   $ cat large_file.log |
   > grep "ERROR" |
   > wc -l
   ```
4. **Екранований символ нового рядка:** рядок закінчується зворотним слешем `\`, який скасовує спеціальне значення байта `0x0A` (LF) і склеює введення з наступним рядком:
   ```bash
   $ gcc -Wall -Wextra -O3 \
   > -o program main.c
   ```
5. **Вбудовані документи (Here-Documents):** очікується введення тіла блоку `<<EOF` до зустрічі термінального маркерного рядка.

Під час виведення `PS2` оболонка не викликає функцій із `PROMPT_COMMAND` і не оновлює статус `$?`, оскільки логічна транзакція поточної команди все ще триває.

### Меню інтерактивного вибору: PS3
Змінна `PS3` використовується виключно вбудованою в оболонку конструкцією `select ... in ...; do ... done`, яка автоматично генерує нумероване текстове меню:

```bash
PS3="Оберіть середовище для розгортання: "
select env in "staging" "production" "local"; do
    echo "Обрано: $env"
    break
done
```

Оболонка виводить нумерований список варіантів, після чого друкує рядок `PS3` (за замовчуванням `#? `) і очікує введення числового індексу від користувача. Якщо користувач вводить некоректний номер або порожній рядок, оболонка повторно перемальовує меню та знову виводить `PS3`. На відміну від `PS1`, змінна `PS3` не проходить автоматичного розгортання бекслеш-послідовностей у старих версіях стандарту, тому туди зазвичай записують простий текст.

### Префікс трасування сценаріїв: PS4
Змінна `PS4` відіграє критичну роль в інженерному налагодженні оболоночних сценаріїв. Вона визначає префікс, який оболонка друкує перед кожною інструкцією, якщо увімкнено режим трасування виконання `set -x` (`set -o xtrace`).

За замовчуванням `PS4` дорівнює `+ `. Проте інтерпретатор Bash має унікальний механізм: перший символ рядка `PS4` автоматично дублюється стільки разів, якою є поточна глибина вкладеності підоболонок або вкладених сценаріїв (рівень `$SHLVL` та глибина виклику функцій).

Якщо налаштувати `PS4` із використанням системних змінних налагодження, трасування перетворюється на повноцінний лог виконання із зазначенням файлів, рядків і функцій:
```bash
export PS4='+ [${BASH_SOURCE[0]##*/}:${LINENO}] ${FUNCNAME[0]:+${FUNCNAME[0]}(): }'
```

Крім того, починаючи з версії Bash 4.1, існує спеціальна змінна `BASH_XTRACEFD`. Якщо спрямувати трасування у виділений файловий дескриптор:
```bash
exec 19> /tmp/script_trace.log
export BASH_XTRACEFD=19
set -x
```
Весь діагностичний вивід `PS4` піде у файл `/tmp/script_trace.log`, не засмічуючи стандартний потік помилок `stderr` (`fd 2`), що дозволяє чисто налагоджувати складні конвеєри без спотворення виводу робочих програм.

Повний перелік усіх підтримуваних параметрів та системних прапорців наведено в [Довіднику змінних запрошення та керуючих послідовностей оболонки](root:sys-unix/shell-prompt/api-prompt-escapes-and-vars.md).

## 2. Спеціальні керівні послідовності: розгортання шаблону без створення процесів

Рядок `PS1` у Bash підтримує спеціальні керуючі коди, що починаються із символу `\`. Їхня перевага полягає в тому, що оболонка розгортає їх внутрішнім C-кодом без виклику системних функцій `fork()` та `execve()`, використовуючи прямі звернення до кешованих даних процесу або швидкі системні виклики ядра.

### Ідентифікація користувача та вузла (\u, \h, \H)
Послідовність `\u` підставляє ім'я поточного користувача. Оболонка отримує його шляхом виклику функції C-бібліотеки `getpwuid(geteuid())`. Якщо змінну середовища `$USER` було підроблено або змінено у просторі користувача, `\u` все одно покаже реальне системне ім'я, прив'язане до ефективного ідентифікатора користувача (EUID) у дескрипторі процесу ядра.

Послідовності `\h` та `\H` повертають відповідно коротке ім'я хоста (до першої крапки) та повне доменне ім'я (FQDN). Вони базуються на єдиному системному виклику ядра `gethostname()`, результати якого оболонка кешує під час запуску сесії.

### Дискримінація привілеїв: послідовність \$
Керівна послідовність `\$` перевіряє ефективний ідентифікатор користувача процесу оболонки. Якщо `geteuid() == 0` (суперкористувач `root`), послідовність розгортається в символ гратки `#`. Для будь-якого іншого значення UID вона розгортається в знак долара `$`.

Жорстке прописування символу `$` у конфігураційних файлах `PS1` є грубою помилкою безпеки. Коли адміністратор перемикається на привілейований сеанс через `su` або `sudo -s`, статичний символ `$` маскує найвищий рівень доступу. Символ `#` слугує універсальним попередженням Unix про те, що будь-яка команда виконується з абсолютними правами над системними ресурсами.

### Робота з каталогами: \w, \W та PROMPT_DIRTRIM
Послідовність `\w` виводить повний шлях до поточного робочого каталогу. При цьому оболонка автоматично замінює домашній каталог користувача (`$HOME` або шлях із бази `/etc/passwd`) на тільду `~`. Послідовність `\W` повертає лише останній компонент шляху (basename).

Оболонка отримує поточний шлях або з внутрішньої змінної `$PWD` (яку вона синхронізує під час кожного виклику вбудованої команди `cd`), або звертаючись до ядра через системний виклик `getcwd()`.

Якщо інженер працює в глибоко вкладених деревах проєктів (наприклад, `/home/alex/workspace/company/services/auth-service/src/internal/transport/http`), довжина рядка шляху може перевищити ширину екрана термінала. Для автоматичного розв'язання цієї проблеми в Bash передбачено змінну `PROMPT_DIRTRIM`:

```bash
PROMPT_DIRTRIM=2
PS1='\u@\h:\w\$ '
```

При встановленні `PROMPT_DIRTRIM=2` довгий шлях автоматично скорочується до вигляду `~/.../transport/http$ `, залишаючи видимими рівно два останні каталоги та позначаючи відсічений префікс символом трикрапки `...`. Цей механізм реалізовано у внутрішній функції Bash `trim_pathname()`, яка працює безпосередньо в оперативній пам'яті без залучення зовнішніх утиліт.

### Історія, черги та часові позначки
- `\!` розгортається у номер поточної команди у глобальній історії Bash (`~/.bash_history`). Це полегшує швидкий повтор викликів через конструкцію `!<номер>`.
- `\#` повертає порядковий номер команди у межах виключно *поточного інтерактивного сеансу*.
- `\j` відображає кількість фонових завдань, керованих оболонкою в даний момент (кількість елементів у таблиці завдань, доступній через команду `jobs`). Це допомагає інженеру пам'ятати про запущені фонові процеси або компіляції перед виходом із сесії.
- `\t`, `\T`, `\@`, `\d`, `\D{format}` інтегрують поточний системний час. Конструкція `\D{%Y-%m-%d %H:%M:%S}` дозволяє використовувати будь-які директиви стандартної C-функції `strftime(3)`.

## 3. Проблема сітки термінала та Readline: колірні коди та маркери `\[` і `\]`

### Як працює екранна сітка термінала
Емулятор термінала розглядає робочий простір як двовимірну матрицю фіксованих знакомісць розміром C колонок на R рядків (наприклад, 80 на 24 або 120 на 40). Позиція курсора фізично визначається парою координат (X, Y).

Коли програма відправляє на термінал звичайні символи (літери, цифри, пробіли), термінал записує гліфи у поточні комірки матриці та зсуває координату курсора X праворуч на одиницю. Коли X досягає значення ширини термінала C, емулятор автоматично переносить курсор на наступний рядок (Y = Y + 1, X = 0).

Ширина символів на сітці регламентується системною функцією `wcwidth(wchar_t ucs)`:
- Звичайні ASCII-символи (латиниця, цифри) займають рівно 1 знакомісце;
- Східноазійські ієрогліфи (CJK) та частина символів Emoji займають 2 знакомісця (Wide Characters);
- Недруковані керівні символи (ANSI escape-послідовності) займають 0 знакомісць.

Коли програма надсилає керівну послідовність кольору ANSI, наприклад `\033[32m` (зелений колір тексту) або `\033[0m` (скидання стилів), термінал:
1. Перехоплює байт `0x1B` (ESC) та наступний символ `[` (CSI);
2. Змінює внутрішній графічний стан рендерера (активний колір пера);
3. **Не друкує жодного символу на екрані й не переміщує курсор** (видима ширина послідовності дорівнює нулю знакомісць).

### Де виникає збій у бібліотеці Readline
Бібліотека GNU Readline, яка відповідає за інтерактивне редагування командного рядка у Bash, не малює пікселі безпосередньо. Вона веде свій власний математичний облік того, де саме на екрані перебуває курсор.

Щоб знати, скільки вільного місця залишилося в поточному рядку до автоматичного перенесення, Readline повинна точно знати видиму довжину рядка запрошення `prompt_visible_length`.

Розглянемо, що відбувається, якщо записати колір без спеціального захисту:
```bash
# НЕПРАВИЛЬНО: байти escape-послідовностей не захищені
PS1="\e[32m\u@\h:\w\$ \e[0m"
```

Рядок `\e[32m` містить 5 байтів, а `\e[0m` — 4 байти. Разом це 9 керівних байтів. Для термінала рядок `user@host:~$ ` займає, припустимо, 13 видимих знакомісць. Але функція `strlen()` всередині Readline підраховує загальну кількість байтів у рядку:
```
13 (текст) + 9 (ANSI) = 22 байти
```

Readline вважає, що курсор уже стоїть у 22-й колонці екрана, тоді як на фізичній матриці термінала курсор стоїть у 13-й колонці.

### Системні симптоми розсинхронізації:
- **Передчасний перенос рядка:** коли користувач вводить довгу команду, вона раптово перескакує на новий рядок задовго до досягнення правого краю вікна термінала.
- **Накладання тексту під час гортання історії:** при натисканні клавіш `Стрілка вгору` або `Ctrl+R` попередні команди з історії не замінюють рядок повністю, а «впаюються» у промпт, залишаючи сміттєві хвости символів.
- **Злам клавіші Backspace:** курсор зупиняється, відмовляючись прати символи до реального початку введення, або перестрибує на середину попереднього рядка і затирає сам промпт.

### Рішення: маркери `\[` та `\]`
Для усунення цієї розбіжності розробники GNU Readline ввели протокол ігнорування недрукованих байтів. У коді Bash цей протокол реалізовано через пару символів `\[` та `\]`.

Під час обробки рядка `PS1` інтерпретатор Bash виконує таку трансляцію:
- Кожен символ `\[` перетворюється на недрукований байт `0x01` (ASCII SOH, константа `RL_PROMPT_START_IGNORE`);
- Кожен символ `\]` перетворюється на недрукований байт `0x02` (ASCII STX, константа `RL_PROMPT_END_IGNORE`).

Коли функція Readline `rl_expand_prompt()` обчислює геометрію рядка, вона повністю виключає з підрахунку ширини всі байти, що лежать між `0x01` та `0x02`. Проте під час фінального виведення рядка у дескриптор термінала ці керуючі байти передаються повністю без змін, що забезпечує коректне забарвлення тексту.

```bash
# ПРАВИЛЬНО: кожен ANSI-код обгорнутий у \[ та \]
PS1="\[\e[32m\]\u@\h:\w\$\[\e[0m\] "
```

У командній оболонці Zsh використовується інший синтаксис із тим самим призначенням: недруковані послідовності огортаються у `%{...%}` або записуються через нативні колірні директиви `%F{green}...%f`.

### Семантична інтеграція терміналів (OSC 133)
Сучасні емулятори терміналів (Alacritty, Kitty, WezTerm, iTerm2, Windows Terminal) підтримують протокол розмітки семантичних зон OSC 133 (FinalTerm Protocol). Вставка спеціальних кодів у промпт дозволяє терміналу розуміти межі команд:
- `\[\e]133;A\a\]` — маркер початку промпту;
- `\[\e]133;B\a\]` — маркер початку користувацького введення;
- `\[\e]133;C\a\]` — маркер запуску команди (початок виводу програми);
- `\[\e]133;D;0\a\]` — маркер завершення команди з передачею коду виходу.

Оскільки всі ці послідовності є керуючими командами термінала з нульовою шириною на сітці, їхнє обов'язкове огортання в `\[` та `\]` є критичною умовою збереження стабільності Readline.

## 4. Динамічний контекст і точки розширення: PROMPT_COMMAND проти $(...)

Сучасні робочі процеси вимагають відображення в терміналі контексту поточної задачі: активної гілки Git, статусу індексу (`clean`/`dirty`), коду помилки попередньої команди, назви контейнера чи віртуального оточення Python.

Для впровадження динамічної логіки в оболонці існує два фундаментальні механізми: вбудована підстановка команд `$(...)` безпосередньо в змінну `PS1` та спеціальний хук `PROMPT_COMMAND`.

![Життєвий цикл формування промпту](/root/sys/sys-unix/shell-prompt/img/prompt-lifecycle.svg)
*Життєвий цикл формування промпту: від фіксації коду виходу до виведення в термінал.*

### Різниця між одинарними та подвійними лапками в PS1
При визначенні динамічного `PS1` критично важливим є тип лапок:

```bash
# ПОМИЛКА: подвійні лапки виконують підстановку ОДИН РАЗ під час ініціалізації
PS1="$(date +%T) \$ "

# ПРАВИЛЬНО: одинарні лапки зберігають вираз для виконання ПЕРЕД КОЖНИМ ВИВОДОМ
PS1='$(date +%T) \$ '
```

Якщо використати подвійні лапки, підстановка `$(date +%T)` виконається рівно один раз — у момент завантаження файлу `.bashrc`. Після цього рядок `PS1` стане статичним текстом (наприклад, `14:00:00 $ `), і час більше ніколи не оновиться. Одинарні лапки запобігають передчасному розкриттю, змушуючи Bash виконувати вкладену команду щоразу, коли термінал готується відобразити новий промпт.

### Змінна PROMPT_COMMAND
`PROMPT_COMMAND` — це спеціальна змінна Bash, у якій міститься команда або ім'я функції, що виконується інтерпретатором безпосередньо перед кожним формуванням і виведенням рядка `PS1`.

Починаючи з версії Bash 5.1, `PROMPT_COMMAND` підтримує роботу у вигляді індексованого масиву, що дозволяє підключати кілька незалежних обробників (наприклад, збереження історії, оновлення заголовка вікна X11 та генерацію промпту) без ризику перезаписати конфігурацію інших плагінів:

```bash
# Сучасний синтаксис Bash 5.1+
PROMPT_COMMAND+=('history -a')
PROMPT_COMMAND+=('update_prompt_state')
```

### Пастка втрати коду повернення ($? та $PIPESTATUS)
Головний інженерний підводний камінь динамічних функцій у `PROMPT_COMMAND` — це легкість, з якою можна ненавмисно затерти статус виходу попередньої команди.

Змінна `$?` зберігає код завершення останньої виконаної програми. Якщо інженер бажає відобразити статус (наприклад, вивести червоний хрестик `✗` у разі ненульового виходу), операцію збереження `$?` необхідно виконати **абсолютно першим рядком** функції:

```bash
# АНТИПАТЕРН: статус $? перезаписується першою ж дією
set_prompt() {
    local venv="$VIRTUAL_ENV"  # Команда local завершується з кодом 0!
    local last_exit=$?         # Тут $last_exit ЗАВЖДИ дорівнюватиме 0!
    ...
}

# ПРАВИЛЬНИЙ ШАБЛОН: миттєве збереження
set_prompt() {
    local last_exit=$?
    local pipestatus=("${PIPESTATUS[@]}")
    # Далі безпечно виконуємо будь-яку логіку
}
PROMPT_COMMAND=set_prompt
```

Масив `${PIPESTATUS[@]}` зберігає коди повернення кожного окремого процесу у конвеєрі (наприклад, для `cmd1 | cmd2 | cmd3`). Якщо проігнорувати його і зчитувати лише `$?`, буде зафіксовано статус виключно останньої команди `cmd3`, що приховає аварії на ранніх етапах обробки даних.

### Індикація віртуальних середовищ та контейнерів
Сучасний інженерний промпт повинен ізолювати контекст виконання. Стандартні змінні для перевірки:
- `VIRTUAL_ENV` — шлях до активного середовища Python `venv` (назва середовища витягується через `${VIRTUAL_ENV##*/}`);
- `CONDA_DEFAULT_ENV` — активне середовище Anaconda/Miniconda;
- `CONTAINER_ID` або наявність файлу `/.dockerenv` чи `run/systemd/container` — індикація роботи всередині контейнера Docker/Podman/LXC;
- `KUBECONFIG` або контекст `kubectl` — поточний кластер та простір імен (namespace) Kubernetes.

Повну реалізацію швидкого модульного рушія, що враховує всі зазначені нюанси, наведено в проєкті [Створення високопродуктивного рушія командного запрошення](root:sys-unix/shell-prompt/proj-custom-prompt-engine.md).

## 5. Продуктивність, бюджет затримок та архітектура сучасних генераторів

Час відгуку інтерфейсу безпосередньо впливає на когнітивну швидкість роботи інженера. Дослідження ергономіки взаємодії людини з комп'ютером (HCI) встановлюють такі межі затримок для систем командного рядка:
- **менше 10 мс:** сприймається людиною як абсолютно миттєва реакція;
- **10–50 мс:** відчувається як швидка, плавна робота без затримок;
- **50–100 мс:** з'являється ледь помітна в'язкість введення;
- **понад 100 мс:** відчутна, дратівлива затримка на кожному натисканні клавіші `Enter`, яка суттєво уповільнює роботу.

### Ціна системних викликів fork() та execve()
У наївних конфігураціях для витягування інформації запускають зовнішні утиліти:
```bash
# Приклад катастрофічно повільного промпту:
PS1='$(whoami)@$(hostname):$(pwd) [$(git rev-parse --abbrev-ref HEAD 2>/dev/null)] \$ '
```

Для обчислення цього рядка оболонка повинна:
1. Викликати системний виклик `clone()` або `fork()` для створення чотирьох окремих дочірніх процесів простору користувача;
2. У кожному процесі виконати `execve()`, що змушує ядро перевірити права доступу, знайти бінарний файл у шляхах `$PATH`, розібрати заголовок ELF і завантажити динамічний лінкер `/lib64/ld-linux-x86-64.so.2`;
3. Лінкер завантажує стандартну бібліотеку `libc.so`, налаштовує глобальну таблицю зміщень (GOT) та процедурну таблицю зв'язування (PLT);
4. Процеси виконують роботу, записують байти у канали передачі даних (`pipe`) і завершуються, змушуючи оболонку обробляти події планувальника та перемикання контексту.

Сумарно на цей ланцюжок витрачається від 15 до 50 мілісекунд процесорного часу. Якщо робота ведеться у віртуальній машині або середовищі WSL2 (Windows Subsystem for Linux), накладні витрати можуть сягати 150–300 мс.

### Проблема Git у великих монорепозиторіях
Команда `git status` або `git describe` за замовчуванням сканує робоче дерево файлової системи, перевіряючи системні атрибути файлів `stat()` для виявлення модифікацій. У монорепозиторіях із сотнями тисяч файлів (наприклад, кодова база Chromium або ядра Linux) або на мережевих файлових системах (NFS, Ceph, SSHFS) виконання `git status` триває від 0.5 до 5 секунд.

Якщо цей виклик вбудовано у синхронний `PROMPT_COMMAND`, оболонка намертво блокується після введення будь-якої команди, доки диск не завершить обхід метаданих файлової системи.

### Оптимізація: Pure Shell Built-ins
Швидкий промпт повинен використовувати виключно вбудовані можливості оболонки, які виконуються всередині адресного простору поточного процесу:
- Замість виклику зовнішньої утиліти `whoami` слід використовувати бекслеш `\u` або внутрішню змінну `$USER`;
- Замість `hostname -s` слід використовувати `\h`;
- Замість виклику `sed` або `awk` для скорочення шляху слід використовувати вбудоване параметричне розкриття Bash: `${PWD/#$HOME/\~}`;
- Замість запуску `git rev-parse` слід безпосередньо зчитувати текстовий файл `.git/HEAD` за допомогою вбудованої команди `read -r`.

### Архітектура сучасних бінарних генераторів (Starship, Powerlevel10k)
Щоб вирішити конфлікт між багатством інформації та швидкістю відгуку, сучасна індустрія перейшла на дві архітектурні моделі:

1. **Скомпільовані мультиплатформні бінарні рушії (Starship):**
   Генератор написано мовою системного програмування (Rust). Він компілюється в один монолітний виконуваний файл без зовнішніх залежностей. Starship виконує паралельне асинхронне сканування системних файлів у пулі потоків (thread pool), кешує результати звернень до дисків і формує повний ANSI-розфарбований промпт із підтримкою десятків мов програмування менш ніж за 5–10 мілісекунд.

2. **Асинхронний рендеринг із фоновими демонами (Powerlevel10k у Zsh):**
   Оболонка ніколи не блокує користувацьке введення. При переході в каталог Zsh миттєво відмальовує базове запрошення з кешу і негайно віддає контроль людині. Одночасно у фоні запускається неблокуючий процес, який опитує важкі підсистеми (Git, Kubernetes, хмарні провайдери AWS/GCP). Як тільки фоновий воркер отримує свіжі дані, він надсилає сигнал головній оболонці, і рушій рядкового редактора ZLE безшовно перемальовує промпт без переривання набору тексту користувачем.
