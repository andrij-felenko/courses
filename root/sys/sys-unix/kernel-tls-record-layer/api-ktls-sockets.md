# 📋 Довідник сокетних опцій, C-структур та контрольних повідомлень kTLS

Програмний інтерфейс підсистеми Kernel TLS у ядрі Linux оперує спеціалізованим рівнем сокетних опцій `SOL_TLS`, двійковими C-структурами передачі криптографічних ключів сесії та допоміжними повідомленнями `cmsghdr` для маркування типів TLS-записів. Нижче наведено вичерпні специфікації заголовочних файлів, системних констант, бітових полів та кодів помилок.

## 1. Заголовні файли, системні константи та рівні сокетних опцій

Для роботи з підсистемою Kernel TLS у програмах мовами C або C++ необхідно включити три основних системних заголовних файли. Заголовок `<sys/socket.h>` надає базові оголошення системних викликів `setsockopt()`, `sendmsg()` та `recvmsg()`, а також макроси побудови допоміжних буферів `cmsghdr`. Заголовок `<netinet/tcp.h>` містить константи мережевого протоколу TCP, зокрема рівень `IPPROTO_TCP` та сокетну опцію `TCP_ULP`. Заголовок `<linux/tls.h>` надає описи спеціалізованих структур даних ядра, ідентифікаторів шифрів та констант рівня `SOL_TLS`.

При викликах системних функцій використовуються наступні ключові константи та рівні:

* `IPPROTO_TCP` — стандартний рівень сокетних опцій протоколу TCP (числове значення `6`). Використовується виключно на етапі активації модуля ULP для зв'язування сокета з підсистемою kTLS.
* `SOL_TLS` — спеціалізований рівень сокетних опцій для підсистеми Kernel TLS (у ядрі Linux визначений числом `282`). Усі подальші маніпуляції з налаштуванням криптографічних ключів, оновленням параметрів шифрування чи витягуванням статусу здійснюються виключно через цей рівень.
* `TLS_TX` — сокетна опція рівня `SOL_TLS` (значення `1`), призначена для конфігурації передавача даних (напрямок вихідного трафіку від додатка в мережу).
* `TLS_RX` — сокетна опція рівня `SOL_TLS` (значення `2`), призначена для конфігурації приймача даних (напрямок вхідного трафіку з мережі до додатка).
* `TLS_1_2_VERSION` — числова константа версії протоколу TLS 1.2 (значення `0x0303` у шістнадцятковому форматі), що занотовується у поле `version` структури криптографічної інформації.
* `TLS_1_3_VERSION` — числова константа версії протоколу TLS 1.3 (значення `0x0304` у шістнадцятковому форматі).

## 2. Покрокова активація ULP через TCP_ULP

Активація підсистеми kTLS на звичайному TCP-сокеті відбувається шляхом використання інфраструктури ULP (Upper Layer Protocol). Модуль ULP дозволяє динамично змінювати внутрішню таблицю методів сокета у ядрі.

Процедура активації вимагає передачі точного рядкового ідентифікатора модуля `"tls"` у системний виклик `setsockopt()`:

```c
const char *ulp = "tls";
int err = setsockopt(fd, IPPROTO_TCP, TCP_ULP, ulp, strlen(ulp));
```

При виконанні цього виклику ядро Linux здійснює наступну послідовність дій:
1. Пошук зареєстрованого модуля з ім'ям `"tls"` у внутрішній таблиці протоколів верхнього рівня ядра. Якщо модуль `tls.ko` не було завантажено раніше, ядро автоматично намагається виконати внутрішній `modprobe tls`.
2. Перевірка поточного стану TCP-з'єднання. Активація ULP припустима лише для сокетів у стані `TCP_ESTABLISHED`. Спроба активувати kTLS на сокеті, який перебуває у стані прослуховування (`TCP_LISTEN`) або у процесі встановлення з'єднання, повертає помилку.
3. Створення контексту `struct tls_context` та прикріплення його до внутрішнього поля сокета `sk->sk_user_data`.
4. Підміна таблиці операцій `sk->sk_prot` з початкового `tcp_prot` на промежуточний обробник kTLS.

Важливо враховувати, що одразу після виконання виклику `setsockopt(TCP_ULP)` сокет переходить у підвішений стан: передача звичайних незашифрованих даних через `send()` або `write()` на цьому етапі блокується або повертає помилку, оскільки ядро ще не отримало симетричних ключів шифрування.

## 3. Двійкові C-структури ключів та криптографічних параметрів (`<linux/tls.h>`)

Передача криптографічних ключів із простору користувача у ядро здійснюється шляхом заповнення спеціалізованих двійкових C-структур. Усі ці структури починаються зі спільної базової заголовної структури `struct tls_crypto_info`.

### 3.1. Загальна базова структура `struct tls_crypto_info`

Базова структура описує загальні ідентифікаційні параметри узгодженого криптографічного протоколу:

```c
struct tls_crypto_info {
    __u16 version;     /* Версія протоколу: TLS_1_2_VERSION (0x0303) або TLS_1_3_VERSION (0x0304) */
    __u16 cipher_type; /* Тип алгоритму шифрування (наприклад, TLS_CIPHER_AES_GCM_128) */
};
```

Поле `version` визначає формат формування заголовків записів TLS, які ядро буде додавати до кожного пакету. Поле `cipher_type` вказує ядру, який саме криптографічний алгоритм з Kernel Crypto API потрібно ініціалізувати і який конкретний розмір розширеної структури даних очікується у виклику `setsockopt()`.

### 3.2. Структура для алгоритму AES-128-GCM (`struct tls12_crypto_info_aes_gcm_128`)

Алгоритм AES-128-GCM є найбільш поширеним стандартом для TLS 1.2 та TLS 1.3. Для передачі його параметрів використовується структура наступного двійкового вигляду:

```c
struct tls12_crypto_info_aes_gcm_128 {
    struct tls_crypto_info info;
    unsigned char iv[TLS_CIPHER_AES_GCM_128_IV_SIZE];       /* 8 байт: явний вектор ініціалізації (Explicit IV) */
    unsigned char key[TLS_CIPHER_AES_GCM_128_KEY_SIZE];     /* 16 байт: симетричний секретний ключ AES-128 */
    unsigned char salt[TLS_CIPHER_AES_GCM_128_SALT_SIZE];   /* 4 байти: неявна сіль (Implicit Salt / Fixed IV) */
    unsigned char rec_seq[TLS_CIPHER_AES_GCM_128_REC_SEQ_SIZE]; /* 8 байт: поточний послідовний номер запису */
};
```

Детальний аналіз полів структури:
* `info.version`: встановлюється у `TLS_1_2_VERSION` або `TLS_1_3_VERSION`.
* `info.cipher_type`: встановлюється у значення `TLS_CIPHER_AES_GCM_128` (числове значення `51`).
* `iv`: масив розміром 8 байт (`TLS_CIPHER_AES_GCM_128_IV_SIZE`). У TLS 1.2 це явна частина вектора ініціалізації, яка змінюється або інкрементується для кожного нового запису.
* `key`: 16-байтовий (128-бітний) симетричний ключ, узгоджений під час фази TLS Handshake у просторі користувача.
* `salt`: 4-байтова неявна сіль. Загальний 12-байтовий вектор nonce для алгоритму Galois/Counter Mode (GCM) конкатенується з 4 байт `salt` та 8 байт `iv`.
* `rec_seq`: 8-байтовий послідовний номер запису (Sequence Number) у порядку big-endian. Якщо kTLS вмикається одразу після завершення Handshake, це поле заповнюється нулями. Якщо ж до моменту передачі ключів у ядро через сокет вже було відправлено декілька записів у user-space, додаток зобов'язаний вказати поточний інкрементований номер.

### 3.3. Структура для алгоритму AES-256-GCM (`struct tls12_crypto_info_aes_gcm_256`)

Для забезпечення вищого рівня криптографічної стійкості використовується 256-бітний варіант алгоритму AES-GCM:

```c
struct tls12_crypto_info_aes_gcm_256 {
    struct tls_crypto_info info;
    unsigned char iv[TLS_CIPHER_AES_GCM_256_IV_SIZE];       /* 8 байт: вектор ініціалізації */
    unsigned char key[TLS_CIPHER_AES_GCM_256_KEY_SIZE];     /* 32 байти: симетричний ключ AES-256 */
    unsigned char salt[TLS_CIPHER_AES_GCM_256_SALT_SIZE];   /* 4 байти: неявна сіль */
    unsigned char rec_seq[TLS_CIPHER_AES_GCM_256_REC_SEQ_SIZE]; /* 8 байт: послідовний номер запису */
};
```

Головна відмінність цієї структури полягає у збільшеному розмірі поля `key` до 32 байт (256 біт). Усі інші поля та принципи конкатенації вектора nonce аналогічні 128-бітному варіанту. Поле `info.cipher_type` для цієї структури має дорівнювати `TLS_CIPHER_AES_GCM_256` (числове значення `52`).

### 3.4. Структура для алгоритму ChaCha20-Poly1305 (`struct tls12_crypto_info_chacha20_poly1305`)

Для систем без апаратної підтримки інструкцій AES-NI (наприклад, деяких ARM-процесорів або легковажних IoT-пристроїв) ефективним є шифр ChaCha20-Poly1305. У ядрі Linux структура його налаштування має наступний вигляд:

```c
struct tls12_crypto_info_chacha20_poly1305 {
    struct tls_crypto_info info;
    unsigned char iv[TLS_CIPHER_CHACHA20_POLY1305_IV_SIZE];       /* 12 байт: повний вектор IV */
    unsigned char key[TLS_CIPHER_CHACHA20_POLY1305_KEY_SIZE];     /* 32 байти: ключ ChaCha20 */
    unsigned char rec_seq[TLS_CIPHER_CHACHA20_POLY1305_REC_SEQ_SIZE]; /* 8 байт: послідовний номер */
};
```

Особливості ChaCha20-Poly1305 у kTLS:
* Поле `info.cipher_type` дорівнює `TLS_CIPHER_CHACHA20_POLY1305` (значення `54`).
* Відсутнє окреме поле `salt`: вектор ініціалізації `iv` займає одразу всі 12 байт, необхідні для генерації одноразового блоку ChaCha20.
* Розмір симетричного ключа `key` становить 32 байти.

## 4. Контрольні повідомлення `cmsghdr` (Ancillary Data) та керування типом записів

Оскільки додаток передає через один і той самий сокет як звичайні дані (`Application Data`), так і службові керівні команди (наприклад, TLS Alert про розрив з'єднання чи повідомлення Handshake при ренегоціації), підсистема kTLS використовує механізм допоміжних даних (Ancillary Data) системних викликів `sendmsg()` та `recvmsg()`.

### 4.1. Відправка керівних записів через `TLS_SET_RECORD_TYPE`

За замовчуванням, коли додаток викликає `send()`, `write()` або `sendfile()`, ядро автоматично формує TLS-записи з типом корисного навантаження `23` (`0x17`, Application Data).

Якщо додатку необхідно надіслати службовий запис (наприклад, TLS Alert), він зобов'язаний використовувати виклик `sendmsg()`, додавши до структури `msghdr` буфер допоміжних даних `cmsghdr` з наступними параметрами:
* `cmsg_level`: встановити рівним `SOL_TLS`.
* `cmsg_type`: встановити рівним `TLS_SET_RECORD_TYPE`.
* `cmsg_len`: обчислити макросом `CMSG_LEN(sizeof(uint8_t))`.
* Значення даних: 1 байт беззнакового цілого числа (`uint8_t`), що вказує потрібний тип TLS-запису.

Стандартні числові значення типів TLS-записів згідно зі специфікацією RFC 8446:
- `20` (`0x14`) — `ChangeCipherSpec`: сигнальний запис зміни ключів шифрування.
- `21` (`0x15`) — `Alert`: повідомлення про помилку чи завершення сесії (наприклад, Close Notify).
- `22` (`0x16`) — `Handshake`: служебне повідомлення повторного узгодження ключів або KeyUpdate.
- `23` (`0x17`) — `Application Data`: звичайні дані додатка.

### 4.2. Отримання керівних записів через `TLS_GET_RECORD_TYPE`

При виклику `recvmsg()` на сокеті з активованим kTLS RX ядро розшифровує вхідний TLS-запис. Якщо отриманий запис є звичайними даними (`Application Data`), ядро просто копіює їх у буфер додатка.

Якщо ж із мережі прийшов службовий запис (наприклад, Alert від сервера), ядро повертає додатку допоміжне повідомлення в `cmsghdr`:
* `cmsg_level`: дорівнює `SOL_TLS`.
* `cmsg_type`: дорівнює `TLS_GET_RECORD_TYPE`.
* Дані `cmsg`: 1 байт `uint8_t` з типом отриманого запису.

Програма повинна проаналізувати отримане допоміжне повідомлення і, якщо тип запису відрізняється від `23`, передати прочитаний байтовий буфер у криптографічну бібліотеку для обробки TLS-події.

## 5. Таблиця кодів помилок, причини їх виникнення та методи усунення

У разі виникнення збоїв під час активації ULP чи налаштування ключів системні виклики повертають значення `-1`, а глобальна змінна `errno` встановлюється у відповідний код помилки. Нижче зведено вичерпну таблицю помилок підсистеми kTLS:

| Код помилки | Константа | Причинно-наслідковий механізм у ядрі | Спосіб усунення у коді додатка |
| :--- | :--- | :--- | :--- |
| `22` | `EINVAL` | Передано некоректний розмір структури у `setsockopt()`, вказано невідому версію `version` чи непідтримуваний `cipher_type`. | Перевірити відповідність розміру структури (`sizeof`) та коректність заповнення полів `info.version` і `info.cipher_type`. |
| `16` | `EBUSY` | Спроба повторно встановити ключі `TLS_TX` або `TLS_RX` для сокета, де ключі для цього напрямку вже були ініціалізовані раніше. | Пересвідчитися, що ключі `TLS_TX`/`TLS_RX` встановлюються рівно один раз після Handshake. Для оновлення ключів використовувати режим `TLS_1_3_VERSION`. |
| `92` | `ENOPROTOOPT` | Виклик `setsockopt(SOL_TLS)` виконано до того, як на сокеті було успішно активовано ULP модуль `"tls"` через `TCP_ULP`. | Дотримуватися суворого порядку: спочатку `setsockopt(IPPROTO_TCP, TCP_ULP, "tls")`, і лише потім `setsockopt(SOL_TLS, ...)`. |
| `17` | `EEXIST` | Модуль ULP `"tls"` вже був активований на даному TCP-сокеті раніше. | Уникати повторних викликів `setsockopt(TCP_ULP)` на одному й тому самому сокетному дескрипторі. |
| `95` | `EOPNOTSUPP` | Мережевий адаптер не підтримує запитаний режим апаратного розвантаження (NIC Offload) або шифр не підтримується системою. | Завантажити криптографічні модулі ядра (`modprobe aes_gcm`) або переключити сокет у програмний режим SW kTLS. |
| `71` | `EPROTO` | Апаратний або програмний двигун kTLS RX виявив незбіг авторизаційного тегу GCM при розшифруванні вхідного запису. | Дані в мережі було пошкоджено або рассинхронізовано вектор IV. З'єднання вважається компрометованим і має бути закрите. |
| `74` | `EBADMSG` | Отриманий з мережі TLS-запис має заголовок із некоректною версією або довжиною, що перевищує `TLS_MAX_PAYLOAD_SIZE`. | Закрити TCP-сокет, оскільки віддалена сторона порушила специфікацію протоколу TLS Record Layer. |
| `90` | `EMSGSIZE` | Спроба надсилання через `sendmsg()` із `cmsg` запису, розмір якого перевищує максимально припустимий ліміт TLS запису. | Розбивати великі службові повідомлення у просторі користувача на фрагменти розміром не більше 16384 байтів. |

Знання цих системних кодів дозволяє створювати надійні мережеві сервіси з вичерпною діагностикою помилок на рівні сокетного інтерфейсу Linux.
