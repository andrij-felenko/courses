# ⚙️ Бінарний пошук ключів btrfs_key у листі B-дерева

Усі заголовки елементів `struct btrfs_item` у будь-якому листі Btrfs розміщені в пам'яті підряд від початку листка (відразу за заголовком вузла `struct btrfs_header`) і суворо впорядковані за зростанням триплету ключа `(objectid, type, offset)`.

Така організація дозволяє ядру Linux відмовитися від повільного лінійного сканування листків на користь бінарного пошуку з часовою складністю `O(log₂ N)`, де `N` — кількість елементів у листі (зазвичай від 100 до 500 записів на один 16-кілобайтний листок).

Коли ядро Linux шукає метадані файлу (наприклад, розширені атрибути або екстент вмісту за конкретним зсувом), воно викликає ядерну функцію `btrfs_search_slot()`. Вона починає рух від кореневого вузла дерева і на кожному проміжному рівні використовує бінарний пошук для вибору дочірнього вузла, аж поки не досягне листка (рівень `level == 0`). Усередині листка ядро повторно запускає бінарний пошук `btrfs_bin_search()` для знаходження конкретного слота.

Нижче наведено практичну реалізацію алгоритму лексикографічного порівняння триплетних ключів та бінарного пошуку в масиві `btrfs_item`, яка моделює внутрішню роботу ядерних підсистем файлової системи Btrfs мовами C та C++.

## Алгоритм лексикографічного порівняння та бінарного пошуку

Порядок сортування елементів у листі Btrfs суворо визначений триплетом `key = (objectid, type, offset)`:

1. **Первинне групування за `objectid`:** Першим критерієм є 64-бітний ідентифікатор об'єкта. Усі метадані одного файлу або директорії (інода, ім'я, розширені атрибути, екстенти) мають однаковий `objectid` (номер іноди), тому вони розміщуються в листі суцільною групою.
2. **Вторинне сортування за `type`:** Усередині групи з однаковим `objectid` записи сортуються за числовим кодом типу. Спочатку йде основний запис іноди `INODE_ITEM` (`1`), потім зворотне посилання `INODE_REF` (`12`), розширені атрибути `XATTR_ITEM` (`24`), елементи директорії `DIR_ITEM` (`84`), і нарешті екстенти даних `EXTENT_DATA` (`108`).
3. **Третинне сортування за `offset`:** Якщо `objectid` та `type` збігаються, вирішальним є 64-бітне значення `offset`. Для екстентів даних це байтовий зсув усередині файлу (`0`, `4096`, `8192`...), що забезпечує сортування блоків файлу за порядком їхнього розташування.

## Аналіз складності, локальності кешу та інтерпретація результатів

Використання впорядкованого масиву `btrfs_item` гарантує найвищу продуктивність пошуку метаданих на процесорах сучасної архітектури:

1. **Часова складність `O(log₂ N)`:** Для типового листка з 300 елементами бінарний пошук робить не більше 9 ітерацій порівняння ключів `btrfs_comp_keys()`.
2. **Просторова локальність L1/L2 кешу (Cache Locality):** Оскільки заголовки елементів `btrfs_item` лежать у пам'яті суцільним масивом (кожен елемент займає 25 байтів), 300 елементів займають лише 7500 байтів. Оскільки весь листок (16 КБ) зчитується з диска в оперативну пам'ять як єдиний безперервний блок, масив заголовків за розміром уміщається в L1-кеш даних процесора (типово 32–48 КБ). Бінарний пошук чіпає лише кілька кеш-ліній цього масиву: перші звернення все одно дають промахи, зате далі порівняння йдуть уже з кешу, без походів у пам'ять.
3. **Обробка відсутності ключа (Slot for Insertion):** Якщо бінарний пошук не знаходить точного збігу шуканого ключа (наприклад, при спробі зчитати дані зсуву `2048` у файлі, де існують лише екстенти зі зсувами `0` та `4096`), функція повертає значення `1` і записує в індикатор `slot` індекс `low`. 

## Механіка просування шляхом пошуку `struct btrfs_path`

При реальній роботі в ядрі Linux бінарний пошук `btrfs_bin_search()` не існує сам по собі. Він є нижньою ланкою системної процедури обходу B-дерева `btrfs_search_slot()`.

Процес пошуку — це спуск за рівнями від кореневого вузла (`level = K`) через проміжні індексні вузли до цільового листка (`level = 0`); кроків рівно стільки, яка висота дерева. На кожному рівні ядро виконує бінарний пошук і фіксує стан проходження в системній структурі `struct btrfs_path`:

```c
struct btrfs_path {
    struct extent_buffer *nodes[BTRFS_MAX_LEVEL]; // Вказівники на буфери вузлів кожного рівня
    int slots[BTRFS_MAX_LEVEL];                  // Обраний індекс слота на кожному рівні
    u8 locks[BTRFS_MAX_LEVEL];                    // Типи утримуваних блокувань (read/write)
    unsigned int reada;                           // Прапорці упереджувального читання
};
```

Процес обходу відбувається наступним чином:
1. **Рівень `level = K` (внутрішній вузол):** Ядро завантажує буфер вузла і запускає `btrfs_bin_search()` над масивом `struct btrfs_key_ptr`. Результат пошуку повертає індекс `slot`. Якщо точного збігу немає, вибраний `slot` відповідає дочірньому вузлу, чий мінімальний ключ є найбільшим із тих, що не перевищують шуканий ключ.
2. **Перехід до `level = K - 1`:** Ядро отримує логічну дискову адресу дочірнього вузла `blockptr` зі структури `btrfs_key_ptr` і зчитує цей вузол з диска (або знаходить його в кеші `page cache`). Індекс `slot` зберігається у масиві `path->slots[K]`.
3. **Досягнення `level = 0` (листок):** Ядро виконує останній `btrfs_bin_search()` над масивом `btrfs_item`. Збережений `path->slots[0]` безпосередньо вказує на заголовок елемента, звідки ядро обчислює зсув `offset` до тіла даних в області даних листка.

Завдяки збереженню всього шляху у `struct btrfs_path`, ядро може миттєво переходити до наступного елемента в порядку сортування (наприклад, під час послідовного читання директорії) викликом `btrfs_next_item()`. Якщо `path->slots[0]` виходить за межі `nritems`, ядро піднімається по `path->nodes` на рівень вище і бере наступний слот у батьківському вузлі, уникаючи повторного пошуку від кореня.

## Обробка меж та послідовне ітерування (`btrfs_next_item`)

Коли програма виконує послідовне зчитування елементів (наприклад, сканування всіх екстентів великого файлу або перелічення елементів великої директорії), запуск нового пошуку `btrfs_search_slot()` від самого кореня для кожного ключа створював би зайву складність `O(H · log₂ N)`, де `H` — висота дерева.

Для вирішення цієї задачі підсистема Btrfs реалізує оптимальну функцію ітерування `btrfs_next_item(struct btrfs_root *root, struct btrfs_path *path)`:

1. Спочатку ядро просто нарощує індекс слота в листку: `path->slots[0]++`.
2. Якщо новий індекс `path->slots[0]` менший за загальну кількість елементів `nritems` поточного листка, функція повертає `0` за час `O(1)`. Елемент доступний негайно.
3. Якщо ж `path->slots[0] == nritems`, це означає, що поточний листок вичерпано. Ядро піднімається на рівень `level = 1` і перевіряє `path->slots[1] + 1`. Якщо у батьківському вузлі є наступний дочірній листок, ядро завантажує його, вивільняє блокування зі старого листка, встановлює `path->slots[0] = 0` і продовжує ітерацію.

Така дворівнева архітектура (бінарний пошук усередині листка + ітеративне просування утримуваним шляхом `btrfs_path`) дозволяє Btrfs поєднувати логарифмічний пошук точних елементів із лінійною швидкістю ітерації великих файлових масивів.

## Взаємодія з механізмом Copy-on-Write під час вставки (`btrfs_cow_block`)

Коли бінарний пошук викликається для операції модифікації або додавання нового запису (`btrfs_insert_empty_item`), підсистема обходу дерева перед модифікацією будь-якого вузла обов'язково викликає процедуру `btrfs_cow_block()`.

Ця процедура перевіряє номер транзакції `generation` у заголовку вузла:
- Якщо `generation` вузла збігається з номером поточної активної транзакції ядра, вузол уже був продубльований у цьому циклі запису, і модифікація виконується безпосередньо у його буфері.
- Якщо ж `generation` вузла належить минулій транзакції, ядро негайно алокує новий блок `extent_buffer`, копіює туди вміст вузла, оновлює батьківський вказівник у `path->nodes[level + 1]` і лише після цього передає новий вузол функції бінарного пошуку для виконання розсунення елементів та вставки нового `struct btrfs_item`.

Така інтеграція бінарного пошуку з механізмом CoW-дублювання забезпечує повну ізоляцію транзакцій та гарантує, що жодна операція пошуку або модифікації не пошкодить цілісність снапшотів чи фонових процесів читання.

## Механіка розсунення елементів та розщеплення листків (`btrfs_split_leaf`)

Після того, як бінарний пошук повернув індекс слота `slot` для вставки нового ключа, підсистема метаданих перевіряє наявність достатнього вільного простору у центрі 16-кілобайтного листка:

1. **Перевірка вільного місця:** Вільний простір — це відстань між кінцем масиву заголовків і початком тіл даних: `free_space = data_offset - nritems * sizeof(struct btrfs_item)`, де `data_offset`, як і всі зсуви елементів, відлічується від початку області даних, тобто одразу за `struct btrfs_header`.
2. **Вставка в існуючий листок:** Якщо `free_space >= sizeof(struct btrfs_item) + data_size`:
   - Ядро зсуває масив заголовків `btrfs_item` від позиції `slot` до `nritems - 1` на 25 байтів праворуч з допомогою виклику `memmove()`.
   - Тіла даних від зсуву `data_offset` до розрахованого місця зсуваються вліво для звільнення корисного вікна `data_size`.
   - Записується новий заголовок `btrfs_item` за індексом `slot`, і лічильник `nritems` збільшується на 1.
3. **Розщеплення листка (`btrfs_split_leaf`):** Якщо вільного місця недостатньо, ядро викликає процедуру розщеплення. Вона виділяє новий листок `right_leaf`, копіює туди приблизно половину записів з поточного листка, після чого вставляє новий ключ у відповідну з двох половин. Перший ключ нового листка `right_leaf->items[0].key` передається у батьківський вузол вищого рівня для реєстрації нової гілки B-дерева.

## Синхронізація та рівні блокування вузлів у `btrfs_path`

При паралельному доступі багатьох потоків ядра до дерев Btrfs, бінарний пошук мусить захищати прочитані вузли від одночасної модифікації іншими процесорами. Для цього в `struct btrfs_path` зберігається стан блокування кожного пройденого рівня:

1. **Читацьке блокування (`BTRFS_READ_LOCK`):** Кілька потоків ядра можуть одночасно виконувати бінарний пошук усередині одного вузла або листка. Вузли блокуються з допомогою ядерного механізму `rwsem` (Read/Write Semaphore).
2. **Записувальне блокування (`BTRFS_WRITE_LOCK`):** Потік, який збирається модифікувати листок (додати ім'я файлу або оновити розмір іноди), блокує вузол монопольно. Усі паралельні пошуки чекають на завершення CoW-модифікації.
3. **Історичний режим `BTRFS_WRITE_LOCK_BLOCKING`:** до ядра 5.6 Btrfs мала власні блокування з двома станами — спін-режимом і блокуючим, у який вузол переводили перед операцією з дисковим введенням-виведенням. Від 5.7 блокування вузлів — це звичайний `rw_semaphore`, який сам засинає за потреби, і окремого «блокуючого» стану вже немає.

Під час виконання `btrfs_search_slot()`, ядро вивільняє блокування «рука за руку» (hand-over-hand locking): щойно пошук опустився на рівень `level = K - 1`, блокування з батьківського вузла `level = K` вивільняється, якщо не вимагається розщеплення вузлів. Це запобігає виникненню вузьких місць продуктивності (lock contention) на верхніх рівнях B-дерев.

## Затримані модифікації в RAM (`btrfs_delayed_node`)

Для максимального скорочення кількості викликів бінарного пошуку в дискових буферах при частих дрібних оновленнях метаданих (наприклад, постійної зміни часу `mtime` або права доступу файлу), ядро Linux використовує підсистему затриманих інод (`btrfs_delayed_node`).

Коли програма викликає `write()` або `chown()`, ядро створює елемент `btrfs_delayed_item` в оперативній пам'яті (у червоно-чорному дереві `rb_tree` конкретної іноди). Замість негайного виконання пошуку `btrfs_search_slot()` та CoW-дублювання листка в B-дереві, ядро накопичує серію оновлень у пам'яті.

Під час планової фіксації транзакції (або при виклику `fsync()`), спеціалізована ядерна підсистема `btrfs_run_delayed_items()` виконує один єдиний `btrfs_search_slot()` у B-дереві і вносить усі накопичені оновлення метаданих пакетом (batch update) в один листок. Це суттєво зменшує дискову фрагментацію та скорочує використання ресурсів CPU при інтенсивному файловому вводі-виводі.

## Простеження виконання пошуку через kernel tracepoints

Аналітику та вимірювання затримок виконання бінарного пошуку в ядрі Linux можна здійснювати за допомогою підсистеми tracepoints. Основні точки простеження:

- **`btrfs:btrfs_search_slot`:** Фіксує кожен виклик обходу дерев. Виводить `root_objectid`, шуканий триплет ключа `(objectid, type, offset)` та результат пошуку.
- **`btrfs:btrfs_cow_block`:** Спрацьовує при виконанні CoW-дублювання вузла під час обходу B-дерева.
- **`btrfs:btrfs_space_reservation`:** Відстежує резервування метаданих перед початком вставки ключів.

Запуск команди `trace-cmd record -e btrfs:btrfs_search_slot` на працюючому сервері дозволяє системним інженерам отримати детальний профіль звернень до B-дерев та виявити найбільш завантажені субтоми та іноди в реальному часі.

## Реорганізація дерев при балансуванні (`btrfs balance`)

Під час виконання команди балансування тома `btrfs balance`, ядро переміщує дискові екстенти та реорганізує B-дерева для вивільнення незаповнених чанків:

1. **Сканування дерев:** Підсистема балансування викликає `btrfs_search_slot()` для систематичного проходження записів у `EXTENT_TREE` та `FS_TREE`.
2. **Переупаковка листків:** Дрібні екстенти метаданих з кількох напівпорожніх листків об'єднуються в суцільні компактні блоки, вивільняючи застарілі дискові чанки для повернення в загальний пул алокатора.
3. **Оновлення зворотних посилань:** Усі зміни дискових адрес оновлюються в `EXTENT_TREE` за допомогою точкових викликів бінарного пошуку для збереження цілісності таблиць CoW-посилань.

Окрім балансування, процедура оптимізації дерев регулярно викликається фоновим демоном ядра для автоматичної дефрагментації листків, які містять велику кількість видалених елементів («дірок» у просторі даних). Завдяки цьому Btrfs гарантує стабільний логарифмічний час доступу до метаданих протягом усього експлуатаційного циклу файлової системи Linux на високозавантажених серверах зберігання.

## Порівняльний аналіз real-world проти стандартного `std::lower_bound`

Реалізація бінарного пошуку в ядрі Linux має декілька специфічних відмінностей порівняно зі стандартними функціями бібліотек користувацького рівня (такими як C++ `std::lower_bound`):

1. **Відсутність віртуальних викликів та шаблонів:** У ядрі Linux `btrfs_bin_search()` є жорстко оптимізованою функцією мови C, яка порівнює інлайн-структури `struct btrfs_key` без використання вказівників на функції або віртуальних таблиць (vtables).
2. **Врахування специфіки Little-Endian:** у ядрі поля ключа лежать на диску в Little-Endian, тому перед порівнянням їх зчитують макросами на кшталт `le64_to_cpu()`. Наведена вище C++-модель працює вже з розпакованими значеннями в порядку байтів хоста, тож трибічний оператор `<=>` порівнює їх напряму — переведення порядку байтів у ній немає взагалі.
3. **Обробка колізій типів та зсувів:** Якщо ядро шукає розширені атрибути файлу, але точного атрибута з даним хешем `offset` не існує, повернутий слот вказує на точне місце, де цей атрибут має бути створений без порушення сортування масиву `btrfs_item`.

Завдяки цьому Btrfs досягає максимально можливої продуктивності метаданих, роблячи операції відкриття, пошуку та модифікації файлів швидкими та передбачуваними за часом виконання у критичних навантаженнях серверних систем Linux. Інтеграція алгоритму з CoW-механізмом робить Btrfs надійною базою для новітніх дискових масивів.
