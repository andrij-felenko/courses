# 📋 Інтерфейси прибивання пам'яті: виклики, прапорці, відмови, лічильники

П'ять системних викликів, чотири коди відмови, вісім місць у файловій системі процесів і шість способів виставити стелю — це весь інтерфейс прибивання. Нижче зібрано підписи, повний перелік прапорців із версіями ядра, точне значення кожної відмови (зокрема двох, що приходять не через `errno`) і поля, за якими видно результат.

## Виклики

```c
#include <sys/mman.h>

int mlock(const void *addr, size_t len);
int mlock2(const void *addr, size_t len, unsigned int flags);  /* Linux 4.4, glibc 2.27 */
int munlock(const void *addr, size_t len);

int mlockall(int flags);
int munlockall(void);
```

Усі повертають `0` при успіху й `-1` з виставленим `errno` при відмові.

| виклик | діапазон | приводить сторінки в пам'ять | лишає позначку на ділянці |
|---|---|---|---|
| `mlock` | заданий | так, до повернення керування | так |
| `mlock2` з `flags = 0` | заданий | так | так — тотожний `mlock` |
| `mlock2` з `MLOCK_ONFAULT` | заданий | ні — прибиває лише ті, що вже в пам'яті | так |
| `mlockall` | весь адресний простір | залежно від прапорців | так, на всі ділянки |
| `munlock` | заданий | — | знімає |
| `munlockall` | весь адресний простір | — | знімає, і `MCL_FUTURE` теж |

Прибивається завжди ціла сторінка: адресу ядро округляє **вниз** до межі сторінки, довжину — **вгору**. Тож `mlock(p, 1)` прибиває всю сторінку, у якій лежить `p`, а діапазон на 4097 байтів займе дві сторінки й дві сторінки з'їсть із межі.

Обгортка `mlock2` з'явилася в glibc аж 2.27 (лютий 2018), на два роки пізніше за сам виклик; на старіших системах його викликають напряму — `syscall(SYS_mlock2, addr, len, flags)`.

Знімання не парне до накладання: прибивання **не накопичується**, тож один `munlock` скасовує скільки завгодно попередніх `mlock` на той самий діапазон. Окремого `munlock2` немає — `munlock` знімає й звичайне прибиття, і `MLOCK_ONFAULT`.

## Прапорці

**`mlock2`** приймає рівно один прапорець; будь-який інший біт — це `EINVAL` (перевірка в ядрі буквально `flags & ~MLOCK_ONFAULT`).

| прапорець | значення | з ядра |
|---|---|---|
| `0` | поводиться точно як `mlock` | 4.4 |
| `MLOCK_ONFAULT` | прибити ті сторінки діапазону, що вже в пам'яті, і позначити ділянку так, щоб кожна решта прибивалася при своєму першому збої | 4.4 |

**`mlockall`** приймає три прапорці через `|`. Перші два стандартні (POSIX.1-2001) і є в Linux здавна, третій додано разом із `mlock2`.

| прапорець | що охоплює | з ядра |
|---|---|---|
| `MCL_CURRENT` | усе, що вже відображено на момент виклику | здавна |
| `MCL_FUTURE` | усе, що буде відображено після виклику | здавна |
| `MCL_ONFAULT` | **лише модифікатор** до одного з двох попередніх: позначені ділянки прибивають сторінки при збої, а не наперед | 4.4 |

Правило «лише модифікатор» — не домовленість, а перевірка в ядрі: `MCL_ONFAULT` наодинці й порожній набір прапорців обидва дають `EINVAL`.

```c
if (!flags || (flags & ~(MCL_CURRENT | MCL_FUTURE | MCL_ONFAULT)) ||
    flags == MCL_ONFAULT)
        return -EINVAL;
```

Звідси шість дозволених наборів:

| набір | наявні ділянки | майбутні ділянки |
|---|---|---|
| `MCL_CURRENT` | привести в пам'ять і прибити | не чіпати |
| `MCL_FUTURE` | не чіпати | приводити в пам'ять і прибивати |
| `MCL_CURRENT \| MCL_FUTURE` | привести в пам'ять і прибити | приводити в пам'ять і прибивати |
| `MCL_CURRENT \| MCL_ONFAULT` | прибити наявні сторінки, решту — при збої | не чіпати |
| `MCL_FUTURE \| MCL_ONFAULT` | не чіпати | прибивати сторінки при їхньому першому збої |
| `MCL_CURRENT \| MCL_FUTURE \| MCL_ONFAULT` | те саме, і так само для всього нового | так само |

Позначку `MCL_FUTURE` (з `MCL_ONFAULT` чи без) нащадок після `fork` не успадковує, а `execve` стирає її разом з усім образом.

## Відмови

| `errno` | де | що саме сталося |
|---|---|---|
| `EPERM` | усі, крім `munlock` | м'яка межа `RLIMIT_MEMLOCK` дорівнює **нулю** і в процесу немає `CAP_IPC_LOCK` |
| `ENOMEM` | `mlock`, `mlock2`, `mlockall` | прибиття вивело б суму прибитих байтів за м'яку межу |
| `ENOMEM` | `mlock`, `mlock2`, `munlock` | частина діапазону не відповідає жодному відображенню |
| `ENOMEM` | `mlock`, `mlock2` | перетнуто стелю числа ділянок (`vm.max_map_count`): прибиття частини ділянки розрізає її натроє |
| `EAGAIN` | `mlock`, `mlock2` | сторінки не вдалося привести в пам'ять — вільних кадрів забракло |
| `EINVAL` | `mlock`, `mlock2`, `munlock` | `addr + len` переповнилося, тобто сума менша за `addr` |
| `EINVAL` | `mlock2` | подано невідомий прапорець |
| `EINVAL` | `mlockall` | подано невідомий прапорець, порожній набір або самий `MCL_ONFAULT` |

Різниця між `EPERM` і `ENOMEM` — не про розмір прохання, а про те, чи процесові взагалі дозволено прибивати. Ядро ставить це питання першим (`can_do_mlock()`: межа ненульова **або** є можливість), і лише потім міряє, чи вміщається прохання.

> 🔧 **Навіщо це.** Служба в контейнері з `LimitMEMLOCK=0` отримає `EPERM` навіть на прибиття однієї сторінки — і в журналі це виглядатиме як брак прав, хоч жодних прав їй не бракує. Достатньо поставити ненульову межу, і той самий код піде. Навпаки, `ENOMEM` від `mlock` майже ніколи не означає, що в машині скінчилася пам'ять: у дев'яти випадках з десяти це вичерпана стеля.

Ще одна пара варта уваги: `EAGAIN` замість `ENOMEM`. Усередині обидві помилки народжуються на етапі заповнення сторінок, і ядро розводить їх навмисно — «діапазону не існує» стає `ENOMEM`, а «кадрів немає зараз» стає `EAGAIN`, бо друге має шанс минутися.

Дві найнеприємніші відмови приходять взагалі не через `errno` прибивання. Обидві — наслідок `MCL_FUTURE`, який робить межу умовою кожного майбутнього відображення:

| що робить програма | як це виглядає |
|---|---|
| `mmap`, `brk`, `malloc` за межу | звичайна відмова виділення: `MAP_FAILED` або `NULL` |
| стек росте за межу | ядро відмовляється розширювати ділянку й доставляє **`SIGSEGV`** |

Другий випадок падає в довільному місці — там, де глибина викликів дійшла до нової сторінки стека, — і до причини не має жодного видимого стосунку.

## Де видно результат

| місце | поле | одиниця | що рахує |
|---|---|---|---|
| `/proc/PID/status` | `VmLck` | КіБ | прибите цим процесом через `mlock`, `mlock2`, `mlockall` і `mmap(MAP_LOCKED)` |
| `/proc/PID/smaps` | `Locked` | КіБ | те саме, але окремо по кожній ділянці |
| `/proc/PID/smaps` | `VmFlags: lo` | — | ділянка прибита звичайним способом |
| `/proc/PID/smaps` | `VmFlags: lf` | — | ділянка прибивається при збої (`ONFAULT`) |
| `/proc/meminfo` | `Mlocked` | КіБ | по всій системі — те, що прибито родиною `mlock` |
| `/proc/meminfo` | `Unevictable` | КіБ | **увесь** список невитіснюваних сторінок |
| `/proc/vmstat` | `nr_mlock`, `nr_unevictable` | сторінки | ті самі два числа, але в сторінках |
| `/proc/vmstat` | `unevictable_pgs_*` | подій | скільки сторінок пройшло через кожен перехід |

Два загальносистемні числа розділені навмисно, і `Unevictable` завжди не менший за `Mlocked`. Різниця — це сторінки, нерухомі не через чиєсь прибивання: вміст `ramfs`, сегменти, замкнені через `shmctl`, ділянки `memfd_secret`. Великі сторінки `hugetlbfs` сюди не входять узагалі: вони не лежать у списках збирача й мають власний облік. Коли `Unevictable` росте, а `Mlocked` стоїть, шукати треба не програму з `mlock`.

Лічильники `unevictable_pgs_*` — це події, а не стан; набір трохи різниться між версіями ядра, але постійні чотири: `mlocked` (сторінка потрапила в список при збої у прибитій ділянці), `munlocked` (вийшла з нього при зніманні), `culled` (збирач наштовхнувся на неї під час обходу й відправив у список) і `rescued` (повернулася до звичайних списків, коли причина зникла).

Дивитися на це найзручніше поряд зі звичайними мірками пам'яті — [VSZ, RSS і PSS](root:sys-unix/memory-accounting) відповідають на питання «скільки процес зайняв», `VmLck` — на питання «скільки з того він не віддасть». Самі файли живуть у [файловій системі процесів](root:sys-unix/pseudo-filesystems), яка не має жодного байта на диску: кожне читання — це виклик функції ядра.

```sh
$ grep -E 'VmLck|VmRSS' /proc/self/status
VmRSS:      3968 kB
VmLck:         0 kB
$ grep -E 'Mlocked|Unevictable' /proc/meminfo
Unevictable:   84732 kB
Mlocked:       12288 kB
```

## Як виставити межу

Стеля прибитої пам'яті — це `RLIMIT_MEMLOCK`, звичайна [межа ресурсу](root:sys-unix/resource-limits) з парою значень: м'яку процес піднімає сам до жорсткої, жорстку — тільки з `CAP_SYS_RESOURCE`. Значення округляється вниз до цілої сторінки.

| спосіб | одиниця | приклад |
|---|---|---|
| `setrlimit(RLIMIT_MEMLOCK, …)` | байти | у власному коді, до першого `mlock` |
| `prlimit(pid, RLIMIT_MEMLOCK, …)` | байти | правка межі **живого чужого** процесу |
| `ulimit -l N` | **КіБ** | `ulimit -l 65536` — це 64 МіБ, не 64 КіБ |
| `prlimit(1)` | байти | `prlimit --memlock=8388608 --pid 1234` |
| `memlock` у `/etc/security/limits.conf` | **КіБ** або `unlimited` | `@rt hard memlock 262144` |
| `LimitMEMLOCK=` у юніті | байти з суфіксами | `LimitMEMLOCK=1G`, `LimitMEMLOCK=8M:64M` |

Розбіжність одиниць — найчастіше джерело помилок: `ulimit -l` і `limits.conf` рахують кілобайти (це успадковано ще від блоків по 1024 байти), а системні виклики й [юніти systemd](root:sys-unix/systemd-model) — байти. Рядок `limits.conf` спрацьовує лише там, де в стеку автентифікації є модуль `pam_limits` — тобто при вході в сеанс, а не при запуску служби; [стек PAM](root:sys-unix/pam-stack) і вирішує, чи його спитають узагалі. Службам межу задають директивою в юніті, а спільне значення для всіх — `DefaultLimitMEMLOCK=` у налаштуваннях менеджера.

Типове значення межі колись стояло на 64 КіБ і трималося так тринадцять років; у ядрі 5.16 його підняли до 8 МіБ. Це буквально одна константа:

```c
/* v5.15 і раніше */
#define MLOCK_LIMIT     ((PAGE_SIZE > 64*1024) ? PAGE_SIZE : 64*1024)

/* v5.16 і далі */
#define MLOCK_LIMIT     ((PAGE_SIZE > 8*1024*1024) ? PAGE_SIZE : 8*1024*1024)
```

Межа не належить самому `mlock`: у той самий рахунок ідуть замкнені сегменти спільної пам'яті, зареєстровані буфери [io_uring](root:sys-unix/io-uring-rings-model) і [довгі закріплення сторінок для пристроїв](root:sys-unix/page-pinning-gup) — саме потреби io_uring і зрушили константу.

Обійти межу цілком дає [можливість](root:sys-unix/capabilities) `CAP_IPC_LOCK`: із нею жодна з перевірок вище не спрацьовує, і прибивати можна скільки завгодно.

## Суміжні інтерфейси

| виклик або ключ | що робить | тонкість |
|---|---|---|
| `shmctl(id, SHM_LOCK, NULL)` | замикає сегмент спільної пам'яті System V | сторінки **не** приводить у пам'ять — це справа програми; від ядра 2.6.10 доступний без привілеїв, якщо ефективний UID процесу збігається з власником або творцем сегмента, а розмір уміщається в `RLIMIT_MEMLOCK` |
| `shmctl(id, SHM_UNLOCK, NULL)` | знімає замикання | після нього сторінки повертаються у звичайні списки — це видно як приріст `unevictable_pgs_rescued` |
| `mmap(…, MAP_LOCKED, …)` | прибити ділянку відразу при [відображенні](root:sys-unix/mmap-model) | гарантія **слабша** за `mlock`: якщо заповнити сторінки не вдалося, `mmap` усе одно повертає успіх, і збій станеться потім |
| `mmap(…, MAP_POPULATE, …)` | лише привести сторінки в пам'ять, без прибивання | перша половина роботи `mlock` окремо |
| `madvise(addr, len, MADV_DONTDUMP)` | виключити ділянку з [аварійного дампу](root:sys-unix/core-dump) | єдиний спосіб не пустити прибитий ключ у файл дампу — прибивання від цього не рятує |
| `vm.compact_unevictable_allowed` | чи вільно ущільненню рухати прибиті сторінки | типово `1`; на ядрах `PREEMPT_RT` типово `0`, щоб не породжувати збій там, де його не чекають — [гілка реального часу](root:sys-unix/preempt-rt-kernel-transformation) міняє значення саме з цієї причини |

Значення `sysctl` вимикається як завжди — записом у файл; [параметри ядра, які крутять на ходу](root:sys-unix/sysctl-tunables) описують, чому таке значення переживе перезавантаження лише з `/etc/sysctl.d/`.

```sh
$ sysctl -w vm.compact_unevictable_allowed=0
vm.compact_unevictable_allowed = 0
```

## Найменший робочий виклик

Прибити мегабайт анонімної пам'яті й переконатися, що це видно ззовні:

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/resource.h>

int main(void)
{
        size_t len = 1024 * 1024;
        void *p = mmap(NULL, len, PROT_READ | PROT_WRITE,
                       MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
        if (p == MAP_FAILED) { perror("mmap"); return 1; }

        struct rlimit rl;
        getrlimit(RLIMIT_MEMLOCK, &rl);
        printf("м'яка межа: %llu Б\n", (unsigned long long) rl.rlim_cur);

        if (mlock(p, len) != 0) { perror("mlock"); return 1; }
        memset(p, 0, len);      /* сторінки вже в пам'яті — жодного збою */

        char line[256];
        FILE *f = fopen("/proc/self/status", "r");
        while (fgets(line, sizeof line, f))
                if (strncmp(line, "VmLck:", 6) == 0)
                        fputs(line, stdout);
        fclose(f);

        munlock(p, len);
        munmap(p, len);
        return 0;
}
```

```
м'яка межа: 8388608 Б
VmLck:	    1024 kB
```

Якщо друга стрічка не з'явилася, а `mlock` повернув `EPERM` — межа дорівнює нулю; якщо `ENOMEM` — межа менша за мегабайт. Перевіряти обидва випадки варто саме так, читанням `rlim_cur` перед викликом: одне число пояснює відмову швидше за будь-який журнал.
