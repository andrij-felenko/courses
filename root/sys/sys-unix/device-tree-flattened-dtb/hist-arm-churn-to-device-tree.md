# 📜 Історія від хаосу board-файлів ARM до стандарту Device Tree

Стандарт Device Tree пройшов еволюцію від архітектури Open Firmware на комп'ютерах PowerPC і SPARC до вирішення кризи розростання C-коду в архітектурі ARM у ядрі Linux та революційного переходу на бінарні структури Flattened Device Tree у 2011–2013 роках.

## 1. Спадщина Open Firmware та IEEE 1275

Наприкінці 1980-х та у 1990-х роках компанії Sun Microsystems, Apple та IBM зіткнулися з потребою створення гнучкого механізму самоопису апаратури для своїх робочих станцій та серверів на базі процесорів SPARC і PowerPC. Традиційні на той час системні плати IBM PC спиралися на жорстко зафіксовані адреси системного контролера, переривань ISA та конфігурації BIOS. Натомість робочі станції високого рівня вимагали модульності, коли розширювальні плати шини SBus або PCI могли додавати до системи довільну периферію.

Для розв'язання цієї задачі розробили стандарт **Open Firmware** (затверджений як IEEE 1275 у 1994 році). Ідея Open Firmware полягала у створенні деревної структури об'єктів у енергонезалежній пам'яті (PROM або NVRAM) материнської плати. Кожен апаратний вузол мав свої властивості (адреси, переривання, тип пристрою) та містив байт-код мовою **Fcode** (діалект мови Forth). Під час увімкнення живлення прошивка виконувала байт-код Fcode для ініціалізації кожного пристрою, будувала дерево пристроїв у пам'яті та передавала його операційній системі (OpenBSD, Solaris або Linux).

Ядро Linux для архітектури PowerPC ще з кінця 1990-х років активно використовувало API Open Firmware для динамічного виявлення відеокарт, мережевих контролерів та системних шин. Однак для дешевих вбудованих систем (embedded systems) повноцінна реалізація Open Firmware із транслятором Forth була занадто громіздкою: вона вимагала сотень кілобайт додаткової прошивки та значного часу на виконання під час старт-апу.

## 2. Епоха вбудованих систем: ARM і катастрофа board-файлів

На початку 2000-х років у світі вбудованих систем почався бум архітектури ARM. Компанії Texas Instruments, Samsung, Marvell, Freescale (NXP), Qualcomm та Atmel розробляли власні системи на кристалі (SoC), такі як OMAP, S3C2410, i.MX та PXA. Кожен SoC мав унікальну комбінацію периферичних блоків (UART, SPI, I2C, таймери, контролери виводів GPIO), а кожна компанія-виробник кінцевих пристроїв (наприклад, Nokia, HTC, HP) комбінувала ці SoC із різними дисплеями, сенсорними екранами та флеш-пам'яттю.

На відміну від серверів x86 із шинами PCI або ACPI, у світі вбудованих ARM-процесорів не існувало стандартної шини самовиявлення. Усі периферійні пристрої були відображені безпосередньо у фізичний адресний простір CPU (MMIO).

Щоб ядро Linux могло працювати на конкретній платі, розробники створювали у вихідному коді ядра спеціальні файл-описи — **board-файли** (наприклад, `arch/arm/mach-omap2/board-rx51.c` для смартфона Nokia N900 або `arch/arm/mach-s3c24xx/board-smdk2410.c`). Ці файли описували апаратуру «в лоб» через статичні масиви C-структур `struct platform_device`:

```c
/* Типовий C-код з епохи board-файлів ядра Linux 2.6 (до 2011 року) */
static struct resource i2c_resources[] = {
    [0] = {
        .start = 0x48070000,
        .end   = 0x48070000 + 0x75,
        .flags = IORESOURCE_MEM,
    },
    [1] = {
        .start = 56, /* IRQ number */
        .end   = 56,
        .flags = IORESOURCE_IRQ,
    },
};

static struct platform_device omap_i2c_device1 = {
    .name          = "omap_i2c",
    .id            = 1,
    .num_resources = ARRAY_SIZE(i2c_resources),
    .resource      = i2c_resources,
};
```

Кожна зміна ревізії друкованої плати, заміна номера виводу GPIO для світлодіода або підключення нового датчика температури на шину I2C вимагали внесення змін безпосередньо у C-файл усередині дерева вихідного коду ядра Linux та перекомпіляції бінарного образу ядра `zImage`.

До 2011 року кількість board-файлів у каталозі `arch/arm/` перевищила кількасот одиниць. Обсяг коду в `arch/arm/mach-*` та `arch/arm/plat-*` сягнув понад 80 000 рядків суто конфігураційних C-структур. Розробники різних vendor-гілок ядра постійно дублювали однаковий код для ініціалізації контролерів переривань, таймерів та шин.

## 3. Криза березня 2011 року та ультиматум Лінуса Торвальдса

Критична точка настала в березні 2011 року під час підготовки випуску ядра Linux 2.6.38 / 2.6.39. Мейнтейнер архітектури ARM подав черговий патч-сет, який містив тисячі нових рядків коду для підтримки чергових китайських та американських вбудованих платформ.

Творець ядра Linux **Лінус Торвальдс (Linus Torvalds)** різко відреагував у розсилці Linux Kernel Mailing List (LKML):

> *"Gaah. Guys, this whole ARM thing is a fucking pain in the ass. […] Why is every single ARM SoC doing its own custom infrastructure for basic hardware setup? This needs to be cleaned up, or I will stop accepting ARM pull requests."*

Торвальдс вказав на те, що інфраструктура ARM перетворилася на хаотичне звалище дубльованого коду, яке ламає загальні абстракції ядра. Він поставив вимогу: спільнота ARM повинна знайти єдиний уніфікований спосіб опису апаратури поза C-кодом ядра, аналогічно до того, як це зроблено для PowerPC та x86.

## 4. Народження Flattened Device Tree (FDT) та компілятора DTC

Група ключових розробників ядра — Грант Лайклі (Grant Likely), Роб Геррінг (Rob Herring), Арнд Бергманн (Arnd Bergmann) та Томас Петаццоні (Thomas Petazzoni) — взяла за основу концепцію дерева пристроїв із стандарту IEEE 1275 (Open Firmware), але кардинально її спростила:

1. **Відмова від байт-коду Forth:** замість виконання складних скриптів Fcode прошивка або компілятор генерує статичну бінарну структуру даних у RAM.
2. **Формат Flattened Device Tree (FDT):** ієрархія вузлів та властивостей «сплющується» (flattened) у компактний бінарний файл (Device Tree Blob, `.dtb`), який містить заголовок, блок зарезервованої пам'яті, блок структур із тегами та блок рядків.
3. **Текстовий синтаксис DTS:** розробники описують плату в текстових файлах `.dts` (Device Tree Source), які компілюються у `.dtb` за допомогою утиліти **dtc (Device Tree Compiler)**.

Це дозволило повністю відокремити бінарний код ядра Linux від опису топології плати.

```
       [ Текстові синтаксичні файли ]
      soc.dtsi  +  my-board.dts
                     │
                     ▼
          ( Device Tree Compiler )
                     │  dtc -I dts -O dtb
                     ▼
         [ Бінарний блок .dtb ]
                     │
                     ▼
      ( Передача завантажувачу U-Boot )
                     │
                     ▼
  [ Єдине уніфіковане ядро vmlinuz/Image ]
```

## 5. Перемога уніфікованого ядра та сучасний стан

Перехід ядра Linux на Device Tree тривав із 2011 по 2015 рік (в епоху ядер 3.x та 4.x). У результаті цієї реформи:

- З каталогу `arch/arm/` було вилучено сотні тисяч рядків застарілих board-файлів.
- З'явилася підтримка конфігурації `CONFIG_ARCH_MULTIPLATFORM`. Завдяки цьому один бінарний файл ядра (`zImage` або `Image`) може завантажуватися на сотнях різних SoC та платформ (від Raspberry Pi до потужних серверів Marvell чи Ampere). Завантажувач U-Boot або UEFI просто зчитує з флеш-пам'яті відповідний `.dtb` файл для даної плати та передає його адресу у регістрі CPU при старті ядра.
- Стандарт Device Tree став обов'язковим для нових архітектур ядра, зокрема **ARM64 (AArch64)** та **RISC-V**. У специфікації RISC-V Supervisor Binary Interface (SBI) передача FDT у регістрі `a1` визначена як стандартний ABI-контракт між прошивкою (OpenSBI) та операційною системою.

Сьогодні Device Tree — це основний формат опису ненаукованої (non-discoverable) апаратури у світах ARM, RISC-V, MIPS та OpenPOWER, який забезпечує гнучкість, портованість та просту підтримку нових платформ без потреби перекомпіляції самого ядра Linux.
