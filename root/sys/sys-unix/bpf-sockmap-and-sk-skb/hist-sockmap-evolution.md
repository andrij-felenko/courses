# 📜 Історія еволюції BPF sockmap, sk_skb та sk_msg

Ця вставка детально описує хронологію, інженерні виклики та суперечки довкола створення технологій `SOCKMAP`, `sk_skb` та `sk_msg` у ядрі Linux, які дозволили коротко замкнути мережевий стек для сокетів на одному хості.

## Передумови: Проблема накладних витрат у Service Mesh (2015–2017)

Зі стрімким поширенням контейнеризації (Docker, Kubernetes) та мікросервісних архітектур у середині 2010-х років виник новий клас системних накладних витрат. У класичних монолітних додатках взаємодія між компонентами здійснювалася через оперативну пам'ять як звичайний виклик функції мови програмування чи передача вказівника. У мікросервісах ці ж самі виклики перетворилися на мережеві REST API, gRPC або Thrift запити, що передаються через протокол TCP.

Ситуація додатково загострилася з появою патерну Service Mesh (креаторами якого виступили проекти Envoy від Lyft, Linkerd та Istio від Google та IBM). У концепції Service Mesh поруч із кожним прикладним контейнером (Pod у Kubernetes) розгортається додатковий побічний контейнер-проксі (Sidecar Proxy). Усі вхідні та вихідні мережеві з'єднання додатку насильно перехоплюються через правила `iptables` (REDIRECT / TPROXY) і спрямовуються у локальний проксі-сервер для виконання функцій шифрування mTLS, збору метрик, балансування навантаження та аутентифікації.

У результаті кожен мережевий запит між двома мікросервісами A та B, розміщеними на одній і тій самій фізичній ноді, почав проходити колосальний ланцюжок повторних обробок:

1. **Application A** виконує виклик `write()` у локальний TCP-сокет, адресований до Sidecar A.
2. Пакет проходить через повний стек Linux TCP/IP, віртуальну пара-мережевих інтерфейсів `veth` та правило `iptables PREROUTING`.
3. **Sidecar A** виконує `read()`, розшифровує/обробляє запит, визначає маршрут і викликає `write()` у бік Sidecar B.
4. Пакет знову проходить через локальний TCP/IP стек ноди та віртуальний інтерфейс `loopback` (`lo`).
5. **Sidecar B** отримує пакет через `read()`, перевіряє права доступу та передає його через третю петлю TCP/IP до Application B.
6. **Application B** остаточно отримує дані через `read()`.

Аналіз продуктивності, проведений інженерами Google та Cilium у 2017 році, показав катастрофічні цифри: для відправки одного запиту потік даних проходив через стек TCP/IP ядра Linux до **чотирьох разів поспіль**. Це спричиняло від 8 до 12 перемикань контексту між простором користувача та ядром, від 4 до 6 повних копіювань пам'яті через системну шину та безперервне виділення й видалення об'єктів `sk_buff` у ядрі.

У високонавантажених серверних кластерах із десятками тисяч запитів на секунду до 25–30% ресурсів центрального процесора (CPU) витрачалося виключно на обробку заголовків TCP/IP та переміщення байтів у межах тієї самої оперативної пам'яті, де фізичного мережевого дроту взагалі не існувало.

```
Традиційний шлях у Service Mesh (до 4 проходів TCP/IP):
[App A] -> (TCP/IP) -> [Sidecar A] -> (TCP/IP / lo) -> [Sidecar B] -> (TCP/IP) -> [App B]
```

## Linux 4.14: Джон Фастабенд та поява BPF_MAP_TYPE_SOCKMAP (2017)

У 2017 році інженер Джон Фастабенд (John Fastabend), один із провідних архітекторів мережевого підрозділу eBPF у Linux та засновник проекту Cilium (на той час у складі Covalent), запропонував фундаментально новий підхід. Його теза була сформульована просто: якщо сокети відправника та отримувача перебувають на одному хості в межах операційної системи, ядро не повинно вдавати, ніби вони розділені фізичною мережею з можливими втратами пакетів, заторами та маршрутизаторами.

У серпні 2017 року до підсистеми `net-next` ядра Linux (яке згодом вийшло як реліз Linux 4.14) було включено патч-серію Фастабенда, яка заклала підвалини нової архітектури:

* **`BPF_MAP_TYPE_SOCKMAP`**: Спеціалізована структура даних у ядрі, призначена для зберігання посилань на відкриті сокети (`struct sock *`).
* **`BPF_PROG_TYPE_SK_SKB`**: Новий тип програм eBPF, які прикріплюються до сокетних карт і виконуються при надходженні даних у сокет.

Ключовим інженерним проривом стала підміна таблиці операцій протоколу TCP (`struct proto`). Коли файловий дескриптор сокета додавався до `SOCKMAP`, ядро непомітно замінювало стандартну функцію `tcp_sendmsg()` на BPF-обгортку `tcp_bpf_sendmsg()`. Коли додаток викликав `write()` або `send()`, ця обгортка перехоплювала буфер сокета (`sk_buff`) і замість запуску обчислень TCP (Window Size, Sequence Numbers, Congestion Control, Retransmission Timers) передавала його BPF-програмі **STREAM_VERDICT**.

BPF-програма виконувала аналіз і викликала функцію `bpf_sk_redirect_map()`. Бачачи цей вердикт, ядро витягувало буфер `sk_buff` і безпосередньо поміщало його у чергу прийому (`sk_receive_queue`) сокета-отримувача. Це було перше в історії Linux "коротке замикання" (short-circuiting) локального TCP-трафіку на рівні сокетів.

```
Шлях з BPF SOCKMAP (прямий байпас у ядрі):
[App A] -> send() -> [tcp_bpf_sendmsg] --(BPF Redirect)--> [sk_receive_queue Sock B] -> recv() -> [App B]
```

## Linux 4.17: Перехід до BPF_PROG_TYPE_SK_MSG та scatterlist (2018)

Попри вражаючий результат у тестах продуктивності (затримка знизилася у 2 рази), первинна реалізація мала приховане вузьке місце: вона працювала на рівні сформованих об'єктів `sk_buff`.

Для створення `sk_buff` ядро все одно мусило виділити пам'ять із системних слабів `kmem_cache`, ініціалізувати заголовок пакета та скопіювати байти з простору користувача в сторінки ядра ще **до** того, як BPF-програма `SK_SKB` отримувала керування і приймала рішення про перенаправлення.

У версії Linux 4.17 (червень 2018 року) Джон Фастабенд разом із розробниками ядра з Facebook та Isovalent представили концепцію `BPF_PROG_TYPE_SK_MSG` та структури `struct sk_msg`.

Замість очікування формування пакета `sk_buff`, хук `SK_MSG` спрацьовує на самому початку системного виклику `sendmsg()`, коли байти додатка ще знаходяться у векторі сторінок користувача (`struct scatterlist`). Програма eBPF приймає рішення про перенаправлення на рівні структури `sk_msg_md`. Допоміжна функція `bpf_msg_redirect_hash()` дозволяє спрямувати ці сторінки пам'яті безпосередньо у сокет отримувача без створення `sk_buff` на етапі відправки.

Ця оптимізація усунула останній бар'єр allocations у ядрі, забезпечивши передачу даних за характеристиками, близькими до чистих UNIX Domain Sockets, але з збереженням стандартного Socket API.

## Linux 5.0+: Інтеграція з kTLS, SOCKHASH та еволюція до eBPF Host Routing

У наступні роки розробка підсистеми сокетних карт BPF розвивалася у трьох ключових напрямках:

1. **Хеш-індексація сокетів `BPF_MAP_TYPE_SOCKHASH` (Linux 4.18)**: Використання хеш-таблиць замість простих масивів дозволило індексувати сокети за гнучкими 5-tuple ключами (IP відправника, IP отримувача, порти, мережевий простір назв). Це зняло потребу у веденні складних масивів індексів у проксі-контролерах.
2. **Апаратне та ядерне шифрування kTLS (Linux 5.2+)**: Раніше, якщо трафік між сервісами був зашифрований TLS, перенаправлення зашифрованих байтів у ядрі було некорисним без розшифрування в user-space. Інтеграція kTLS (Kernel TLS) з BPF SOCKMAP дозволила ядру виконувати симетричне шифрування/розшифрування AES-GCM безпосередньо під час BPF-перенаправлення, зберігаючи прозорість для додатків.
3. **Cilium eBPF Host Routing та Ambient Mesh (2020–2024)**: У сучасних архітектурах Kubernetes плагін Cilium застосовує SOCKMAP та SK_MSG для реалізації режиму "Host Routing" та "Ambient Mesh". Це дозволяє взагалі відмовитися від розгортання Sidecar-контейнерів у кожному поді, виконуючи прискорення, фільтрацію та балансування локального трафіку повністю на рівні ядра Linux.

Сьогодні технологія BPF SOCKMAP вважається золотим стандартом високопродуктивного IPC у хмарних операційних системах, заощаджуючи мільйони кіловат-годин електроенергії у світових дата-центрах.
