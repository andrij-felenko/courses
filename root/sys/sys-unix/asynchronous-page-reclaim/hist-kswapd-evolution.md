# 📜 Еволюція kswapd: від секундного таймера Linux 2.0 до MGLRU у ядрі 6.1

Асинхронне витіснення сторінок у ядрі Linux пройшло еволюцію та фундаментальні трансформації від простого таймерного демона 1990-х років до багатогенераційного алгоритму MGLRU. Архітектура kswapd перетворилася з глобального однопоточного процесу на розподілену систему per-node демонів у результаті послідовного розв'язання фундаментальних проблем дефіциту пам'яті та апаратних обмежень на кожному етапі розвитку ядра.

## Початок: bdflush, kswapd та глобальні пороги (Linux 1.x — 2.0)

На початку існування ядра Linux (версії 0.99, 1.2 та ранній цикл 2.0) підсистема управління пам'яттю була влаштована монолітно й розрахована на однопроцесорні комп'ютери з кількома мегабайтами оперативної пам'яті. Уся робота зі звільнення RAM спиралася на двох системних демонів: `bdflush` (відповідальний за скидання брудних буферів файлової системи на диск) та `kswapd` (первинний фоновий потік вивантаження сторінок).

У Linux 2.0 демон `kswapd` прокидався за замовчуванням кожну секунду за таймером або при безпосередньому виклику з підсистеми аллокатора сторінок. Його прийняття рішень спиралося на три глобальні змінні ядра: `freepages.min`, `freepages.low` та `freepages.high`.

```
freepages.min  [критична межа, пряме витіснення]
     ▲
     │   freepages.low  [поріг пробудження kswapd]
     │        ▲
     │        │   freepages.high  [засинання kswapd]
```

Ця схема чудово працювала на персональних комп'ютерах з 16–64 МБ оперативної пам'яті, але містила два кардинальних системних дефекти:
1. **Глобальний стан та відсутність зон:** Змінні `freepages` були єдиними на весь фізичний простір адресації. При появі апаратних обмежень (наприклад, 16-мегабайтної межі ISA DMA на архітектурі x86) ядро не знало, в якій саме ділянці фізичної RAM виник дефіцит.
2. **Сканування без урахування гарячих сторінок:** Витіснення відбувалося за лінійним обходом масиву `mem_map[]`, що призводило до вимивання з оперативної пам'яті часто використовуваних сторінок системних процесів та коду шелу.

## Драматичний цикл 2.4: Зони пам'яті та протистояння VM-алгоритмів

Під час розробки ядра Linux 2.4 (2000–2001 роки) підсистема віртуальної пам'яті пережила одну з найдраматичніших реформ в історії Linux. Розробники Рік ван Рієль (Rik van Riel) та Андреа Арканжелі (Andrea Arcangeli) повністю переписали витіснення сторінок. Пам'ять була розділена на **зони** (`ZONE_DMA`, `ZONE_NORMAL`, `ZONE_HIGHMEM`), а пізніше — на вузли NUMA (Non-Uniform Memory Access).

Замість глобальних `freepages` кожна зона отримала власний набір порогів — **watermarks** (у коді 2.4 це поля `zone->pages_min`, `pages_low`, `pages_high`; сучасні імена `WMARK_*` з'явилися вже в серії 2.6):
- `WMARK_MIN`: критичний рівень зони.
- `WMARK_LOW`: поріг пробудження `kswapd`.
- `WMARK_HIGH`: поріг зупинки `kswapd`.

Сам демон при цьому лишався один на всю систему. Окремий потік `kswapd` на кожен вузол NUMA (`kswapd0`, `kswapd1` тощо) з'явився вже в серії 2.6, коли ядро дістало повноцінну підтримку вузлів. Саме цей поділ зняв зайвий трафік міжпроцесорною шиною: кожен демон вивільняє пам'ять локальних модулів DRAM свого вузла.

Однак витіснення у ранніх випусках Linux 2.4 працювало нестабільно. Алгоритм Ріка ван Рієля часто впадав у так звані "thrashing loops", коли ядро безперервно скидало анонімну пам'ять у swap, повністю вимиваючи файловий кеш. Це спричиняло знамениті зависання серверів під навантаженням. 

Ситуація стала настільки критичною, що у версії Linux 2.4.10 Лінус Торвальдс пішов на безпрецедентний крок: він повністю замінив підсистему VM Ріка ван Рієля новим альтернативним алгоритмом Андреа Арканжелі прямо посеред стабільної серії ядер. Новий VM впровадив більш стабільний розрахунок водяних знаків та збалансоване витіснення.

## Двоярусні списки LRU та параметр Swappiness (Linux 2.6)

У циклі розробки Linux 2.6 (2003–2004 роки) Ендрю Мортон (Andrew Morton) та Нік Піггін (Nick Piggin) провели нову глибинну реформу reclaim-механізму. Головним нововведенням став **роздільний двоярусний список LRU (Split Active/Inactive LRU)**.

Спершу, у 2.6.0, єдиний список сторінок розділили надвоє — на активний та неактивний; окремий поділ на файлові й анонімні списки додав Рік ван Рієль у 2.6.28 (2008), і саме відтоді вузол утримує чотири списки:
1. `Active File` (гарячий файловий кеш)
2. `Inactive File` (холодний файловий кеш)
3. `Active Anon` (гаряча пам'ять процесів)
4. `Inactive Anon` (холодна пам'ять процесів)

```
[ Active Anon ]  ──demote──►  [ Inactive Anon ]  ──swapout──►  [ Swap Disk ]
[ Active File ]  ──demote──►  [ Inactive File ]  ──writeback─► [ Storage ]
```

Для керування вибором між анонімною пам'яттю та файловим кешем було введено параметр `vm.swappiness` та алгоритм **Two-Touch**, який вимагав двох послідовних звернень до сторінки під час її перебування у неактивному списку, перш ніж перевести її в активний стан. Це усунуло проблему вимивання кешу при одноразовому зчитуванні великих файлів.

## Захист від фрагментації: Watermark Boosting (Linux 5.0)

З появою великих прозорих сторінок (Transparent Huge Pages, THP) та мережевих стеків із 100-гігабітними адаптерами виникла нова проблема: **зовнішня фрагментація пам'яті**. Навіть якщо загальний обсяг вільної пам'яті в зоні перевищував `WMARK_HIGH`, у ній могло не бути жодного неперервного блоку розміром 2 МБ (high-order allocation).

У такій ситуації процеси користувача, роблячи запит `alloc_pages(order=9)`, провалювалися у важкий синхронний процес ущільнення пам'яті (`direct compaction`) та пряме витіснення (`direct reclaim`), викликаючи спалахи затримок.

У ядрі Linux 5.0 (2019 рік) Мел Горман (Mel Gorman) впровадив механізм **Watermark Boosting**. Коли аллокатор змушений забрати pageblock чужого типу міграції — тобто змішати в межах одного блоку сторінки різної мобільності, — ядро тимчасово збільшує значення `WMARK_LOW` та `WMARK_HIGH` для цієї зони на величину `watermark_boost`.

```
Нормальний стан:  WMARK_MIN  ───  WMARK_LOW  ───  WMARK_HIGH
Під час бусту:   WMARK_MIN  ───  (WMARK_LOW + Boost)  ───  (WMARK_HIGH + Boost)
```

Це змушує `kswapd` прокинутися завчасно й агресивно вивільнити більше сторінок, розчищаючи простір для ущільнення до того, як процес користувача заблокується в затримці.

## Революція MGLRU: Multi-Generational LRU (Linux 6.1+)

Попри всі удосконалення, двоярусна система Active/Inactive LRU мала фундаментальне обмеження: сканування сторінок за допомогою прапорців `PG_referenced` у структурі `page` вимагало постійного обходу таблиць сторінок (page tables) процесів. На сучасних серверах із терабайтами RAM цей обхід став помітною статтею витрат процесорного часу: `kswapd` палив такти на перегляд таблиць сторінок замість того, щоб вивільняти сторінки.

У грудні 2022 року в ядро Linux 6.1 було прийнято підсистему **MGLRU (Multi-Generational LRU)**, розроблену Ю Чжао (Yu Zhao) в компанії Google.

MGLRU замінив два жорстких списки (Active/Inactive) на **систему поколінь (generations)**, схожу на generational garbage collectors у мовах програмування:

```
Покоління N (найновіше, гаряче)  ◄── Звернення процесів
Покоління N-1
Покоління N-2
Покоління N-3 (найстаріше, витіснення) ──► reclaim by kswapd
```

Замість важкого сканування таблиць сторінок MGLRU використовує кільцевий буфер поколінь та апаратні біти доступу (PTE Young bit) з мінімальним блокуванням. Результати масового тестування Google на мільйонах пристроїв Android та ChromeOS, а також у дата-центрах Meta показали:
- Помітно менші витрати процесорного часу на сам `kswapd`.
- Менше падінь у direct reclaim, а отже й затримок (`allocstall`) у додатках.
- Суттєве покращення чутливості та виживання систем під дефіцитом пам'яті — зокрема менше OOM-убивств на ChromeOS та Android.

Еволюція `kswapd` демонструє головний вектор розвитку ядра Linux: перехід від простих таймерних опитувань до складних асинхронних зворотних зв'язків, які адаптують витіснення під реальні патерни доступу до пам'яті.
