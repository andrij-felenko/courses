# 🎛 Ручки PTI: символи збірки, параметри завантаження, звіти ядра й біти CR3

Це перелік усіх місць, де вирішується доля ізоляції таблиць сторінок на конкретній машині, і всіх місць, де ядро саме про неї звітує: точні назви символів конфігурації, параметри командного рядка з допустимими значеннями, файли `/sys` і `/proc` з розшифровкою кожного рядка, характерні записи в журналі та розкладка бітів у значенні `CR3`, якою ядро перемикає копії кореневої таблиці. Назви й числа звірено з чинним деревом ядра — `arch/x86/mm/pti.c`, `arch/x86/entry/calling.h`, `arch/x86/mm/tlb.c`, `arch/x86/include/asm/processor-flags.h`, `arch/x86/kernel/cpu/common.c`, `arch/x86/kernel/cpu/bugs.c`, `arch/arm64/kernel/cpufeature.c`, `Documentation/arch/x86/pti.rst`.

## Три рівні рішення — і жоден не діє на ходу

Перш ніж читати таблиці, варто знати межу можливого: **ізоляцію не можна ввімкнути чи вимкнути на живій системі.** Немає ні сисктла, ні файлу в `/sys`, ні параметра модуля. Причина проста й неусувна: механізм змінює розкладку кореневих таблиць кожного процесу й той код входу, який ядро переписало під себе ще при завантаженні. Усе, що доступне на ходу, — читання.

| Рівень | Де живе | Що може | Коли читається |
|---|---|---|---|
| збірка ядра | символи `CONFIG_*` | чи є в ядрі відповідний код узагалі | під час компіляції |
| командний рядок | параметри завантажника | примусово ввімкнути, примусово вимкнути, лишити на розсуд ядра | у ранній ініціалізації, до вмикання PTI |
| апаратура | модель процесора, біт у службовому регістрі | чи вважає ядро цей процесор враженим | одразу після визначення можливостей процесора |

Пріоритет саме такий, згори вниз. Немає символа збірки — інші два рівні не мають на що впливати. Є символ і є прямий наказ у командному рядку — апаратуру не питають. Немає наказу — рішення ухвалює ядро за апаратурою.

## Символи конфігурації

| Символ | Архітектура | Типово | Залежності |
|---|---|---|---|
| `CONFIG_MITIGATION_PAGE_TABLE_ISOLATION` | x86 | `y` | `X86_64` або `X86_PAE` |
| `CONFIG_PAGE_TABLE_ISOLATION` | x86, ядра до 6.8 включно | `y` | те саме |
| `CONFIG_UNMAP_KERNEL_AT_EL0` | arm64 | `y` | запит показують лише в режимі `EXPERT` |
| `CONFIG_RANDOMIZE_BASE` | arm64 | `y` | не вмикає ізоляцію, але **змушує** її ввімкнути (нижче) |
| `CONFIG_DEBUG_ENTRY` | x86 | `n` | додаткові перевірки коду входу; для тестування |

Перші два рядки — той самий символ під двома іменами. У версії 6.9 усі перемикачі пом'якшень апаратних вад у Linux дістали спільний префікс `MITIGATION_`, і ця латка не була винятком; в усьому, що старше, шукайте назву без префікса. Текст запису в `arch/x86/Kconfig` при перейменуванні не змінився ані на слово:

```
config MITIGATION_PAGE_TABLE_ISOLATION
	bool "Remove the kernel mapping in user mode"
	default y
	depends on (X86_64 || X86_PAE)
```

Назва arm64-символа не абревіатура, а опис: `UNMAP_KERNEL_AT_EL0` — «не відображати ядро на рівні EL0», тобто на рівні виконання програм. Запит на нього показують лише в режимі `EXPERT` — щоб вимкнути його випадково було важче.

Дізнатися, з чим зібране те ядро, що зараз працює, можна трьома способами, залежно від того, що дистрибутив зволив лишити:

```sh
$ zgrep PAGE_TABLE_ISOLATION /proc/config.gz          # якщо є CONFIG_IKCONFIG_PROC
$ grep PAGE_TABLE_ISOLATION "/boot/config-$(uname -r)"
$ grep UNMAP_KERNEL_AT_EL0 "/boot/config-$(uname -r)"  # arm64
```

Те, що набір можливостей ядра застигає в момент компіляції й далі лише читається, стосується не лише цієї латки — [конфігурація ядра як механізм](topic:sys-unix/kernel-config-and-build) пояснює, звідки беруться символи `CONFIG_*`, як вони залежать один від одного і чому дистрибутивне ядро не можна «донастроїти» без перезбирання.

## Параметри завантаження

Рядок параметрів складає завантажник і передає ядру, а ядро розбирає його на самому початку — [як саме командний рядок доходить до ядра](topic:sys-unix/bootloader-and-cmdline) варте окремого погляду; чинний рядок видно в `/proc/cmdline`.

| Параметр | Архітектура | Дія |
|---|---|---|
| `pti=on` | x86 | увімкнути незалежно від того, чи ядро вважає процесор враженим |
| `pti=off` | x86 | вимкнути незалежно від апаратури |
| `pti=auto` | x86 | рішення за ядром; це й є типова поведінка |
| `nopti` | x86 | давній синонім `pti=off`; лишений заради сумісності |
| `nopcid` | x86 | **не** вимикає ізоляцію — вимикає мітки адресних просторів |
| `kpti=on` / `kpti=off` | arm64 | те саме, що `pti=` на x86; значення розбирає `kstrtobool`, тож `1`/`0`, `y`/`n`, `yes`/`no` теж приймаються |
| `mitigations=…` | усі | загальний перемикач пом'якшень апаратних вад (нижче) |

Будь-яке інше значення `pti=` — помилка розбору, а не мовчазне «як завгодно»: розбирач повертає `EINVAL`.

`nopcid` заслуговує на окремий рядок, бо його регулярно плутають із вимикачем ізоляції. Він знімає з процесора можливість `PCID`, тобто [мітки адресних просторів у кеші перекладів](topic:hw-arch/tlb): без міток кожен запис у `CR3` скидає весь TLB, і саме тому ізоляція на такому ядрі коштує на порядок дорожче. Тобто `nopcid` ізоляцію не вимикає, а робить її найдорожчою з можливих — це важіль для вимірювань, а не для швидкодії.

Значення загального перемикача:

| Значення | Дія |
|---|---|
| `mitigations=auto` | усі пом'якшення ввімкнено; типова поведінка |
| `mitigations=auto,nosmt` | те саме плюс вимкнення багатопотоковості там, де вона заважає захисту |
| `mitigations=off` | вимкнути всі пом'якшення апаратних вад, зокрема й ізоляцію таблиць |
| `mitigations=no_user_kernel` | вимкнути лише пом'якшення напряму «програма проти ядра» — а це саме та група, до якої належить ізоляція |

Останній рядок — з нового набору керування за напрямом атаки (`Documentation/admin-guide/hw-vuln/attack_vector_controls.rst`): замість «усе або нічого» тепер можна відмовитися від захисту одного напряму. У коді це видно прямо: перш ніж вмикатися, ізоляція питає, чи взагалі пом'якшують напрям «користувач → ядро». Поруч є `no_user_user`, `no_guest_host`, `no_guest_guest`, `no_cross_thread` — до ізоляції таблиць вони стосунку не мають. *Статус: наявне в свіжих ядрах; на старіших залишається лише `mitigations=off`.*

Окрема пастка: якщо ядро зібране **без** символа ізоляції, файл `pti.c` не компілюється, а разом з ним і розбирачі `pti=`/`nopti`. Параметр стає нічиїм — ядро мовчки згадає його серед невпізнаних і передасть у простір користувача. Ніякої помилки, ніякого попередження про те, що наказ не виконано.

## Що система каже про себе

### Файл у sysfs

Ядро звітує про кожну відому апаратну ваду окремим файлом у [дереві пристроїв і підсистем](topic:sys-unix/sysfs-device-model), де кожен файл — це виклик функції ядра, а не збережений на диску текст:

```sh
$ cat /sys/devices/system/cpu/vulnerabilities/meltdown
Mitigation: PTI
```

| Рядок | Що означає |
|---|---|
| `Not affected` | процесор не має вади; ізоляція не потрібна й не ввімкнена |
| `Mitigation: PTI` | процесор вражений, ізоляція працює |
| `Vulnerable` | процесор вражений, ізоляції немає — вимкнено або не зібрано |
| `Unknown (XEN PV detected, hypervisor mitigation required)` | паравіртуалізований гість Xen: усередині гостя механізм безсилий, лікувати мусить гіпервізор |

Три перші форми — спільна мова всієї теки: `Not affected`, `Vulnerable`, `Mitigation: $M`, де `$M` — назва вжитого засобу. Сусідні файли (`spectre_v1`, `spectre_v2`, `l1tf`, `mds`, `retbleed`, `srbds`, `itlb_multihit`, `mmio_stale_data`, `spec_store_bypass`, `tsx_async_abort`, `gather_data_sampling`, `reg_file_data_sampling`, `old_microcode` та інші) читаються так само, але про ізоляцію таблиць не говорять нічого — вона закриває рівно одні двері.

Найважливіше в цій таблиці — **різниця між `Not affected` і `Vulnerable`**. Перше означає «нема чого лікувати», друге — «є що, і не лікуємо». Вимкнули ізоляцію на враженій машині — побачите саме `Vulnerable`, а не `Not affected`: ядро не забуває про ваду через те, що йому наказали її ігнорувати.

Сама тека з'явилася в ядрі 4.15, у січні 2018 року, разом із першою хвилею пом'якшень. На старіших ядрах її просто немає, і відсутність файлу нічого не говорить про стан машини.

### Прапорець у /proc/cpuinfo

```sh
$ grep -ow pti /proc/cpuinfo | head -1
pti
```

Прапорець `pti` у переліку можливостей процесора ядро підставляє тоді й лише тоді, коли ізоляція справді ввімкнена. Тут криється тонкість, варта уваги: рядок `flags` у [файлі відомостей про процесор](topic:sys-unix/proc-reading-process-and-kernel-state) змішує два різні типи записів — біти, які процесор справді повідомляє про себе інструкцією `CPUID`, і **штучні прапорці, які вигадало саме ядро**, щоб позначити стан своїх механізмів. `pti` — з других: у процесора немає й не може бути біта «на мені ввімкнено ізоляцію Linux». У джерелі це видно з номера — `X86_FEATURE_PTI ( 7*32+11)`, тобто сьоме слово, відведене під власні позначки ядра.

Поруч корисно глянути на справжні апаратні прапорці, від яких залежить ціна механізму:

| Прапорець | Природа | Значення для ізоляції |
|---|---|---|
| `pti` | штучний, від ядра | ізоляція ввімкнена |
| `pcid` | апаратний | є мітки адресних просторів — перемикання не скидає TLB |
| `invpcid` | апаратний | є точкове знецінення записів за міткою |
| `invpcid_single` | штучний, від ядра | ядро вважає, що точкове знецінення на цій машині можна вживати |

### Рядки в журналі ядра

Усі повідомлення механізму на x86 несуть спільний початок — його задано одним рядком у `arch/x86/mm/pti.c`:

```c
#define pr_fmt(fmt)     "Kernel/User page tables isolation: " fmt
```

| Повний рядок | Коли з'являється |
|---|---|
| `Kernel/User page tables isolation: enabled` | ізоляцію ввімкнено — єдине повідомлення про успіх |
| `Kernel/User page tables isolation: disabled on command line.` | вимкнено наказом **і** процесор при цьому вражений |
| `Kernel/User page tables isolation: force enabled on command line.` | увімкнено наказом **і** процесор при цьому не вражений |
| `Kernel/User page tables isolation: disabled on XEN PV.` | гість Xen PV; механізм вимкнено примусово |

Два середні рядки мають властивість, яку легко проґавити, а вона дуже зручна: **вони друкуються не завжди.** У джерелі за них відповідають дві різні функції — одна друкує, лише якщо процесор вражений вадою, друга — лише якщо не вражений. Логіка за цим така: попереджати варто про той наказ, який змінює становище на гірше або на дивне. Вимкнули ізоляцію на процесорі, якому вона й так не потрібна, — ядро змовчить, бо нічого не сталося. Тому **мовчання журналу після `pti=off` означає, що процесор і без того не вражений**, а не що наказ не почули.

На arm64 рядки інші й побудовані інакше — там ядро завжди називає причину рішення:

| Рядок | Коли |
|---|---|
| `kernel page table isolation disabled by kernel configuration` | ядро зібране без `CONFIG_UNMAP_KERNEL_AT_EL0` |
| `kernel page table isolation forced ON by kpti command line option` | наказ `kpti=on` |
| `kernel page table isolation forced OFF by kpti command line option` | наказ `kpti=off` |
| `kernel page table isolation forced ON by KASLR` | ізоляцію ввімкнено не проти витоку даних, а щоб не розсипалася [рандомізація розкладки ядра](topic:sys-unix/address-space-randomization) |
| `kernel page table isolation forced OFF by mitigations=off` | загальна відмова від пом'якшень |
| `kernel page table isolation forced OFF by ARM64_WORKAROUND_CAVIUM_27456` | обхід апаратної вади Cavium ThunderX несумісний із механізмом |

Рядки видно в `dmesg` одразу після завантаження й у `journalctl -k` пізніше — з тією поправкою, що [кільцевий буфер ядра має скінченний розмір](topic:sys-unix/journald-structured-entry-model) і ранні повідомлення з нього витісняються; якщо служба журналу їх не зберегла, шукати вже нема де.

### Зведення: що з чим збігається

| sysfs | прапорець `pti` | Вердикт |
|---|---|---|
| `Mitigation: PTI` | є | ізоляція працює |
| `Not affected` | немає | процесор не вражений; усе гаразд |
| `Vulnerable` | немає | вражений і не захищений — шукайте `pti=off`, `nopti` чи `mitigations=` у `/proc/cmdline`, а якщо їх нема, дивіться символ збірки |
| `Not affected` | є | суперечність, якої не буває: прапорець ставлять лише разом із механізмом, а механізм на невраженому процесорі вмикають хіба що наказом `pti=on` — тоді в журналі буде рядок про примусове ввімкнення |

## Розкладка бітів у значенні CR3

Тепер найточніша частина довідки — регістр, у якому все й відбувається. `CR3` містить фізичний номер кадру кореневої таблиці, а коли ввімкнено `CR4.PCIDE` — ще й мітку адресного простору в молодших дванадцяти бітах:

```
 63      62 … 52        51 … 12                  11    10 … 0
┌────────┬───────────┬──────────────────────────┬─────┬─────────┐
│ NOFLUSH│  нуль     │ номер кадру кореня       │ PTI │  мітка  │
└────────┴───────────┴──────────────────────────┴─────┴─────────┘
                        ▲                         ▲
                   біт 12 — молодший біт номера   │
                   кадру; він і розрізняє копії   │
                                    старший біт поля мітки
```

Ізоляція не додає до регістра жодного нового поля. Вона **захоплює по одному вже наявному біту з кожного кінця**: молодший біт номера кадру відрізняє дві копії кореня, старший біт поля мітки відрізняє дві мітки.

| Константа в ядрі | Значення | Що робить |
|---|---|---|
| `PTI_USER_PGTABLE_BIT` | `PAGE_SHIFT`, тобто `12` | 0 — ядерна копія кореня, 1 — користувацька |
| `PTI_USER_PGTABLE_MASK` | `0x1000` | той самий біт як маска |
| `X86_CR3_PTI_PCID_USER_BIT` | `11` | 0 — ядерна мітка, 1 — користувацька |
| `PTI_USER_PCID_MASK` | `0x800` | той самий біт як маска |
| `PTI_USER_PGTABLE_AND_PCID_MASK` | `0x1800` | обидва разом — щоб перемикати одною операцією |
| `X86_CR3_PCID_NOFLUSH_BIT` | `63` | «перемкни, але записів у TLB не викидай» |
| `X86_CR3_PCID_BITS` | `12` | ширина поля мітки в архітектурі |

Біт 12 обраний не довільно: обидва корені виділяють однією ділянкою на 8 КіБ, вирівняною по 8 КіБ, тож їхні фізичні адреси різняться рівно на розмір сторінки — а це й є біт номер `PAGE_SHIFT`. Тому перехід між копіями не потребує ані пошуку, ані розіменування.

Мітки ядро роздає за простою формулою. Внутрішній номер простору (ASID) — маленьке число; ядерна мітка дорівнює `ASID + 1`, користувацька — тій самій із піднятим одинадцятим бітом:

```c
static inline u16 kern_pcid(u16 asid)
{
	return asid + 1;
}

static inline u16 user_pcid(u16 asid)
{
	u16 ret = kern_pcid(asid);
#ifdef CONFIG_MITIGATION_PAGE_TABLE_ISOLATION
	ret |= 1 << X86_CR3_PTI_PCID_USER_BIT;
#endif
	return ret;
}
```

Одиниця в `kern_pcid` не забаганка: мітка нуль лишається за кодом, який про мітки нічого не знає, — так помилка «зберегли `CR3`, завантажили щось із нульовою міткою, відновили `CR3`» не псує чужих записів у TLB. Одинадцятий біт мусить лишатися вільним, тому динамічних номерів ядро тримає всього шість (`TLB_NR_DYN_ASIDS`), а сама ізоляція **звужує поле мітки з дванадцяти бітів до одинадцяти** — один біт вона забирає собі назавжди.

**Процес із ядерним коренем за фізичною адресою `0x1a2b2000` і внутрішнім номером простору 3:**

```
ядерна мітка         = 3 + 1                 = 4      = 0x004
користувацька мітка  = 4 | (1 << 11)         = 2052   = 0x804

ядерне значення CR3        = 0x1a2b2000 | 0x004
                           = 0x1a2b2004
користувацьке значення CR3 = 0x1a2b2000 | 0x1000 | 0x804
                           = 0x1a2b3804

вихід у простір програми, не скидаючи TLB:
  0x1a2b3804 | (1 << 63)   = 0x80000000_1a2b3804

вхід у ядро — одна маска на обидва біти:
  0x1a2b3804 AND NOT 0x1800 = 0x1a2b2004
```

Саме це й роблять два макроси коду входу, дослівно:

```asm
.macro ADJUST_KERNEL_CR3 reg:req
	ALTERNATIVE "", "SET_NOFLUSH_BIT \reg", X86_FEATURE_PCID
	andq    $(~PTI_USER_PGTABLE_AND_PCID_MASK), \reg
.endm

.macro SWITCH_TO_KERNEL_CR3 scratch_reg:req
	ALTERNATIVE "jmp .Lend_\@", "", X86_FEATURE_PTI
	mov	%cr3, \scratch_reg
	ADJUST_KERNEL_CR3 \scratch_reg
	mov	\scratch_reg, %cr3
.Lend_\@:
.endm
```

Дві директиви `ALTERNATIVE` тут — не оздоба, а спосіб не платити за перевірки на найгарячішому шляху системи. Кожна з них означає «постав перший варіант коду, а якщо в процесора є названа можливість — перепиши це місце другим». Переписування відбувається один раз, при завантаженні. Тому на машині без ізоляції на місці всього макроса стоїть безумовний стрибок через нього, а на машині з ізоляцією й мітками — три інструкції без жодного розгалуження.

Зворотний макрос трохи довший, бо мусить вирішити, чи можна не скидати мітку:

```asm
.macro SWITCH_TO_USER_CR3 scratch_reg:req scratch_reg2:req
	mov	%cr3, \scratch_reg
	ALTERNATIVE "jmp .Lwrcr3_\@", "", X86_FEATURE_PCID
	movq	\scratch_reg, \scratch_reg2
	andq	$(0x7FF), \scratch_reg
	bt	\scratch_reg, THIS_CPU_user_pcid_flush_mask
	jnc	.Lnoflush_\@
	btr	\scratch_reg, THIS_CPU_user_pcid_flush_mask
	movq	\scratch_reg2, \scratch_reg
	jmp	.Lwrcr3_pcid_\@
.Lnoflush_\@:
	movq	\scratch_reg2, \scratch_reg
	SET_NOFLUSH_BIT \scratch_reg
.Lwrcr3_pcid_\@:
	orq	$(PTI_USER_PCID_MASK), \scratch_reg
.Lwrcr3_\@:
	orq     $(PTI_USER_PGTABLE_MASK), \scratch_reg
	mov	\scratch_reg, %cr3
.endm
```

Маска `0x7FF` тут — це рівно одинадцять бітів мітки без дванадцятого: із чинного значення дістають **ядерну** мітку й за нею шукають біт у побітовій мапі `user_pcid_flush_mask`. Мапа веде облік того, для яких користувацьких міток на цьому процесорному ядрі накопичилися застарілі переклади. Біт стоїть — переклади треба викинути, тож у `CR3` пишуть без ознаки `NOFLUSH`, а біт гасять. Біта немає — ставлять `NOFLUSH` і не платять нічого.

> 🔧 **Навіщо це.** Із цієї механіки випливає прикладний висновок про заміри. Якщо міряти ціну перетину межі на машині, завантаженій із `nopcid`, отримані числа не описують нічого, крім найгіршого можливого випадку: обидва `ALTERNATIVE` розгортаються у варіант без міток, ознака `NOFLUSH` не ставиться ніде, і кожен вхід та вихід повністю знецінює TLB. Різниця між цим і звичайним режимом — не відсотки, а рази. Тому перше, що варто перевірити перед будь-яким виміром ціни ізоляції, — це наявність `pcid` у `/proc/cpuinfo`, а не версія ядра.

## Чому ізоляція може бути вимкнена без чийогось наказу

| Умова | Механізм | Як перевірити |
|---|---|---|
| процесор AMD або Hygon | внесені до переліку невражених у ядрі цілим виробником | `grep vendor_id /proc/cpuinfo` |
| старі ядра Intel Atom, Xeon Phi та інші з переліку | той самий перелік, за моделлю | `cat /sys/devices/system/cpu/vulnerabilities/meltdown` |
| ваду виправлено в кремнії | біт `RDCL_NO` у службовому регістрі `IA32_ARCH_CAPABILITIES` | `rdmsr 0x10a` |
| гість Xen PV | ізоляцію вимикають примусово: усередині гостя вона безсила | рядок про XEN PV у sysfs і в журналі |

Перші дві умови — це той самий перелік невражених процесорів у джерелі ядра (`cpu_vuln_whitelist`), просто в одних рядках стоїть виробник цілком, а в інших конкретні моделі. Він змінюється з версіями, тому єдиною надійною відповіддю лишається не список у голові, а вміст файлу sysfs на цій машині.

Третя умова цікавіша, бо це домовленість між процесором і ядром на майбутнє. `IA32_ARCH_CAPABILITIES` — [службовий регістр, специфічний для моделі](topic:hw-arch/msr), із номером `0x10A`; його нульовий біт зветься `RDCL_NO` і означає рівно «цей процесор не піддається зухвалому читанню з кешу даних» (англ. *rogue data cache load* — так Intel називає механізм Meltdown). Побачивши одиницю, ядро ізоляцію не вмикає — і саме так нові процесори позбуваються плати за неї, не потребуючи жодних змін у ядрі. Прочитати біт самому можна так:

```sh
$ sudo modprobe msr
$ sudo rdmsr -f 0:0 0x10a     # з пакета msr-tools; 1 означає RDCL_NO
1
```

Сам регістр існує не в кожного процесора: спершу перевірте наявність прапорця `arch_capabilities` у `/proc/cpuinfo`, інакше `rdmsr` поверне помилку вводу-виводу, а не нуль.

## Один захід: перевірка всього стану

Найкоротший спосіб зібрати всі чотири джерела в одну відповідь:

```sh
#!/bin/sh
# Стан ізоляції таблиць сторінок ядра на цій машині.

vuln=/sys/devices/system/cpu/vulnerabilities/meltdown

if [ -r "$vuln" ]; then
    printf 'sysfs   : %s\n' "$(cat "$vuln")"
else
    printf 'sysfs   : файлу немає — ядро старше за 4.15\n'
fi

if grep -qw pti /proc/cpuinfo; then
    printf 'cpuinfo : прапорець pti є\n'
else
    printf 'cpuinfo : прапорця pti немає\n'
fi
grep -qw pcid /proc/cpuinfo && printf 'cpuinfo : pcid є — перемикання дешеве\n'

printf 'збірка  : %s\n' "$(zgrep -h -E '^CONFIG_(MITIGATION_)?PAGE_TABLE_ISOLATION=|^CONFIG_UNMAP_KERNEL_AT_EL0=' \
        /proc/config.gz "/boot/config-$(uname -r)" 2>/dev/null | head -1)"
printf 'cmdline : %s\n' "$(cat /proc/cmdline)"

printf 'журнал  :\n'
{ dmesg 2>/dev/null || journalctl -k -o cat 2>/dev/null; } |
    grep -i -e 'page tables isolation' -e 'page table isolation'
```

Читати вивід треба в тому самому порядку пріоритетів, з якого починалася ця довідка: якщо рядка `CONFIG_…=y` немає, решта нічого не важить; якщо він є, дивіться на командний рядок; і лише коли там нічого про це не сказано — на вердикт sysfs, у якому відбилася апаратура.
