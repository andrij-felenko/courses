# 📋 Довідник API dlfcn та інтерфейсу налагодження rtld

Цей довідник описує програмний інтерфейс POSIX `dlfcn` (`dlopen`, `dlsym`, `dlclose`, `dlerror`, `dladdr`, `dlinfo`), прапори зв'язування спільних бібліотек, змінні середовища завантажувача `ld-linux.so` та внутрішній ABI налагодження `link_map` / `r_debug`.

## 1. Програмний інтерфейс POSIX dlfcn

Інтерфейс `dlfcn` є частиною стандарту POSIX.1-2001 і надає програмам можливість динамічно завантажувати об'єктні файли у власному просторі пам'яті безпосередньо під час виконання (Run-time Dynamic Loading). Для використання цього API у вихідному коді необхідно підключити заголовочний файл `<dlfcn.h>`. У класичних дистрибутивах Linux виклики даного API вимагали лінкування із прапорцем `-ldl` (бібліотека `libdl.so`), однак у сучасних версіях GNU C Library (починаючи з glibc 2.34) функціональність `libdl` повністю інтегровано до основного складу стандартної бібліотеки `libc.so`.

### Функція `dlopen`

:::tabs
```c
void *dlopen(const char *filename, int flags);
```
```cpp
// C++ оголошення <dlfcn.h>
void* dlopen(const char* filename, int flags);
```
:::

Функція `dlopen()` відкриває динамічну бібліотеку або ELF-модуль, вказаний у параметрі `filename`, та відображає його сегменти у віртуальний адресний простір викликаючого процесу.

- **Аргумент `filename`:** 
  Якщо цей параметр є вказівником на рядок, що містить хоча б один символ похилої риски `/` (наприклад, `./libcustom.so` або `/opt/lib/libdata.so`), завантажувач тлумачить ім'я як точний абсолютний або відносний шлях у файловій системі та відмовляється від пошуку у стандартних каталогах. 
  
  Якщо ж параметр `filename` містить лише ім'я файлу (наприклад, `libcrypto.so.3`), динамічний завантажувач розпочинає каскадний пошук у такій послідовності: каталоги `DT_RPATH` виконуваного файлу (якщо відсутній `DT_RUNPATH`), зміна середовища `LD_LIBRARY_PATH`, каталоги `DT_RUNPATH`, системний бінарний кеш `/etc/ld.so.cache` та стандартні системні каталоги (`/lib64`, `/usr/lib64`).
  
  Якщо параметр `filename` передано як `NULL`, функція `dlopen()` повертає непрозорий хендл для **головного виконуваного файлу** самого процесу. Це дає змогу за допомогою наступних викликів `dlsym()` шукати символи у власному коді програми або в бібліотеках, які були завантажені на етапі її старту.

- **Аргумент `flags`:** 
  Бітова маска прапорців, яка контролює миттєвість розв'язання символів та рівень видимості згенерованого модуля. Має містити один із двох базових режимів зв'язування (`RTLD_LAZY` або `RTLD_NOW`), комбінований через бітове «АБО» (`|`) із додатковими прапорцями видимості та поведінки (`RTLD_GLOBAL`, `RTLD_LOCAL`, `RTLD_NODELETE`, `RTLD_NOLOAD`, `RTLD_DEEPBIND`).

- **Значення повернення:**
  При успішному виконанні повертається непрозорий вказівник (хендл), який усередині завантажувача є адресою структури `struct link_map`. При виникненні помилки (файл не знайдено, відсутні права читання, нерозв'язані символи в режимі `RTLD_NOW`) функція повертає `NULL`, а детальний опис проблеми зберігається для наступного виклику `dlerror()`.

### Функція `dlsym`

:::tabs
```c
void *dlsym(void *handle, const char *symbol);
```
```cpp
// C++ оголошення <dlfcn.h>
void* dlsym(void* handle, const char* symbol);
```
:::

Функція `dlsym()` приймає хендл завантаженої бібліотеки `handle`, отриманий від `dlopen()`, та нуль-терміноване ім'я символу `symbol`, після чого повертає фактичну віртуальну адресу цієї функції або змінної в пам'яті.

- **Особливості пошуку та псевдо-хендли:**
  Окрім звичайних хендлів бібліотек, функція `dlsym()` підтримує два спеціальних псевдо-хендли, визначених у заголовку `<dlfcn.h>`:

  1. `RTLD_DEFAULT`: Інструктує завантажувач шукати символ `symbol`, обходячи всі завантажені бібліотеки у стандартному глобальному порядку (Global Scope), починаючи з головної програми.
  2. `RTLD_NEXT`: Використовується для перехоплення функцій (Function Interposition). Завантажувач шукає **наступний** екземпляр символу `symbol` у списку завантажених бібліотек, який розташований *після* того об'єкта, з якого здійснюється поточний виклик `dlsym()`. Це дає змогу користувацьким обгорткам у `LD_PRELOAD` викликати оригінальні функції стандартної бібліотеки після виконання власних перевірок.

- **Перевірка помилок при нульових адресах:**
  Оскільки значення символу в пам'яті теоретично може дорівнювати `NULL` (або дорівнювати 0 у випадку слабких символів), повернення `NULL` від `dlsym()` не завжди свідчить про помилку. Правильний алгоритм перевірки вимагає попереднього виклику `dlerror()` для очищення стану, після чого викликається `dlsym()`, і якщо результат дорівнює `NULL`, виконується повторний виклик `dlerror()`. Якщо повернений рядок не дорівнює `NULL`, це підтверджує наявність реальної помилки.

### Функція `dlclose`

:::tabs
```c
int dlclose(void *handle);
```
```cpp
// C++ оголошення <dlfcn.h>
int dlclose(void* handle);
```
:::

Функція `dlclose()` декрементує лічильник посилань на завантажений модуль, асоційований із хендлом `handle`. Якщо лічильник посилань падає до нуля, завантажувач викликає конструктори-фіналізатори модуля (функції із `.fini_array` або `__attribute__((destructor))`), після чого вивантажує сегменти бібліотеки з віртуальної пам'яті за допомогою системного виклику `munmap()`.

Якщо бібліотека була завантажена з прапорцем `RTLD_NODELETE`, або якщо від її коду все ще залежать інші відкриті бібліотеки, сегменти залишаються у пам'яті, незважаючи на обнулення конкретного хендла.

### Функція `dlerror`

:::tabs
```c
char *dlerror(void);
```
```cpp
// C++ оголошення <dlfcn.h>
char* dlerror();
```
:::

Функція `dlerror()` повертає людсько-читабельний рядок із описом останньої помилки, яка сталася під час виконання будь-якої з функцій підсистеми `dlfcn` (`dlopen`, `dlsym`, `dlclose`).

Важливою властивістю `dlerror()` є її **деструктивне зчитування**: перший виклик повертає рядок помилки та негайно скидає внутрішній стан помилки у `NULL`. Наступні послідовні виклики `dlerror()` повертатимуть `NULL` доти, доки у підсистемі не станеться нова помилка.

### Функція `dladdr` (GNU розширення)

:::tabs
```c
int dladdr(const void *addr, Dl_info *info);
```
```cpp
// C++ оголошення <dlfcn.h>
int dladdr(const void* addr, Dl_info* info);
```
:::

Функція `dladdr()` здійснює зворотне відображення адреси пам'яті (Address Resolution): вона приймає довільний вказівник `addr` і намагається визначити, якому саме завантаженому ELF-модулю та якому найближчому символу належить ця адреса.

Результат записується у структуру `Dl_info`:

:::tabs
```c
typedef struct {
    const char *dli_fname;  /* Абсолютний шлях до файлу спільної бібліотеки */
    void       *dli_fbase;  /* Базова адреса завантаження модуля у віртуальній пам'яті */
    const char *dli_sname;  /* Ім'я найближчого символу (функції), що передує адресі */
    void       *dli_saddr;  /* Точна віртуальна адреса знайденого символу */
} Dl_info;
```
```cpp
// C++ структуру Dl_info з <dlfcn.h>
struct Dl_info {
    const char *dli_fname;
    void       *dli_fbase;
    const char *dli_sname;
    void       *dli_saddr;
};
```
:::

Якщо адресу вдалося розв'язати у межах відомого об'єкта, функція повертає ненульове значення. Якщо адреса вказує на анонімну пам'яті або стек, повертається `0`.

## 2. Детальний довідник прапорців `dlopen()`

| Прапор | Числове значення | Семантика та практична роль у завантажувачі |
| :--- | :--- | :--- |
| `RTLD_LAZY` | `0x00001` | **Запізніле зв'язування (Lazy binding).** Завантажувач виконує релокацію лише для глобальних змінних (`.got`). Релокація функціональних викликів у `.got.plt` відкладається до першого фактичного виконання функції. Це прискорює відкриття великих бібліотек. |
| `RTLD_NOW` | `0x00002` | **Негативне зв'язування (Immediate binding).** Завантажувач примусово розв'язує адреси абсолютно всіх функцій під час виклику `dlopen()`. Якщо хоча б один символ не вдалося знайти, `dlopen()` завершується помилкою та не завантажує бібліотеку. |
| `RTLD_GLOBAL` | `0x00100` | **Глобальна видимість символів.** Символи, експортовані цією бібліотекою, робляться доступними для розв'язання релокацій у наступних бібліотеках, що відкриватимуться пізніше. |
| `RTLD_LOCAL` | `0x00000` | **Локальна ізоляція (За замовчуванням).** Символи даної бібліотеки є приватними і не використовуються для розв'язання залежностей у сторонніх модулях. |
| `RTLD_NODELETE` | `0x01000` | **Заборона вивантаження.** Інструктує rtld не вивантажувати бібліотеку з пам'яті під час виклику `dlclose()`. Змінні стани та код залишаються доступними до завершення процесу. |
| `RTLD_NOLOAD` | `0x00004` | **Перевірка наявності.** Завантажувач не виконує читання файлу з диска. Повертає valid хендл лише у тому разі, якщо бібліотека вже була завантажена у процес раніше; інакше повертає `NULL`. |
| `RTLD_DEEPBIND` | `0x00008` | **Пріоритет власних символів.** Змінює порядок пошуку символів: внутрішні виклики з цієї бібліотеки спочатку шукають символи у ній самій, і лише потім у глобальному середовищі програми. Це захищає бібліотеку від перехоплення її внутрішніх функцій зовнішнім `LD_PRELOAD`. |

## 3. Змінні середовища динамічного завантажувача `ld-linux.so`

Поведінка динамічного завантажувача може коригуватися без перекомпіляції бінарників за допомогою спеціальних змінних середовища.

### `LD_PRELOAD`
Приймає список шляхів до додаткових спільних бібліотек. Завантажувач відкриває ці бібліотеки **найпершими**, ще до завантаження основних залежностей програми. Оскільки пошук символів виконується у порядку їх появи у списку `link_map`, будь-яка функція, визначена у `LD_PRELOAD`, заміщує собою однойменну функцію у стандартних бібліотеках (`libc.so`, `libm.so`).

- **Захист:** Якщо процес заповнено із підвищенням привілеїв (прапорець `AT_SECURE == 1` у допоміжному векторі, наприклад для SUID/SGID програм), завантажувач **ігнорує** змінну `LD_PRELOAD` із міркувань безпеки.

### `LD_LIBRARY_PATH`
Список каталогів у файловій системі (розділених двокрапкою), в яких завантажувач шукає спільні бібліотеки перед тим, як переходити до системного кешу та стандартних шляхв `/lib64` / `/usr/lib64`. Так само ігнорується при встановленому `AT_SECURE`.

### `LD_BIND_NOW`
Якщо ця змінна містить ненульове значення, завантажувач ігнорує режим запізнілого зв'язування і виконує примусову релокацію усіх PLT-слотів під час старту процесу (аналогічно комбіляційній опції `-z now`).

### `LD_DEBUG`
Вмикає розширене налагоджувальне логування роботи завантажувача у текстовий потік `stderr`. 

Основні значення:
- `LD_DEBUG=libs`: Відображає процес пошуку, відкриття та відображення `.so` файлів.
- `LD_DEBUG=reloc`: Виводить кожну релокацію, що обробляється завантажувачем, із зазначенням адрес та типів.
- `LD_DEBUG=symbols`: Логує кожну спробу розв'язання символу через хеш-таблиці.
- `LD_DEBUG=bindings`: Показує підсумкові зв'язки між викликами функцій та їх реальними адресами у пам'яті.
- `LD_DEBUG=all`: Вмикає всі можливі категорії логування.

### `LD_SHOW_AUXV`
При значенні `1` змушує завантажувач вирукувати вміст допоміжного вектора (Auxiliary Vector), отриманого від ядра Linux при старті процесу, показуючи адреси `AT_PHDR`, `AT_ENTRY`, `AT_BASE` та інші параметри.

### `LD_AUDIT`
Вказує список бібліотек розширеного аудиту (rtld-audit API). Бібліотека аудиту може перехоплювати події завантаження модулів (`la_objopen`), розв'язання символів (`la_symbind`) та замінювати аргументи викликів.

## 4. Внутрішній ABI налагодження: `link_map` та `r_debug`

Для забезпечення взаємодії з налагоджувачами (GDB, LLDB) динамічний завантажувач експортує відкриті структури даних у пам'яті, які описано в системному заголовку `<link.h>`.

### Структура `r_debug`

Структура `r_debug` є головним вхідним вузлом для зовнішніх інструментів аналізу. Вона містить поточний стан завантажувача та вказівник на список усіх завантажених об'єктів.

:::tabs
```c
struct r_debug {
    int r_version;              /* Версія структури ABI (поточна версія — 1) */
    struct link_map *r_map;     /* Вказівник на перший елемент однозв'язного списку завантажених модулів */
    ElfW(Addr) r_brk;           /* Віртуальна адреса функції-пастки _dl_debug_state */
    enum {
        RT_CONSISTENT,          /* Карта завантажених бібліотек стабільна і готова до зчитування */
        RT_ADD,                 /* Завантажувач у процесі додавання нового ELF-модуля */
        RT_DELETE               /* Завантажувач у процесі вилучення ELF-модуля з пам'яті */
    } r_state;
    ElfW(Addr) r_ldbase;        /* Базова адреса завантаження самого динамічного завантажувача ld.so */
};
```
```cpp
// C++ версія r_debug з <link.h>
struct r_debug {
    int r_version;
    struct link_map *r_map;
    ElfW(Addr) r_brk;
    enum {
        RT_CONSISTENT,
        RT_ADD,
        RT_DELETE
    } r_state;
    ElfW(Addr) r_ldbase;
};
```
:::

### Структура `link_map`

Завантажувач підтримує однозв'язний (і внутрішньо двозв'язний) список усіх відображених ELF-об'єктів процесу у вигляді списку структур `struct link_map`:

:::tabs
```c
struct link_map {
    ElfW(Addr) l_addr;          /* Різниця між адресою в ELF-заголовку та реальною адресою завантаження у RAM */
    char *l_name;               /* Абсолютний шлях до файлу бібліотеки на диску (або порожній рядок для головної програми) */
    ElfW(Dyn) *l_ld;            /* Вказівник на секцію .dynamic даного ELF-модуля */
    struct link_map *l_next;    /* Вказівник на наступну бібліотеку у списку завантаження */
    struct link_map *l_prev;    /* Вказівник на попередню бібліотеку у списку завантаження */
};
```
```cpp
// C++ версія link_map з <link.h>
struct link_map {
    ElfW(Addr) l_addr;
    char *l_name;
    ElfW(Dyn) *l_ld;
    struct link_map *l_next;
    struct link_map *l_prev;
};
```
:::

### Механізм точки зупину `_dl_debug_state`

Налагоджувач GDB не може постійно опитувати пам'ять процесу для виявлення нових бібліотек. Замість цього використовується подійний механізм пастки (Breakpoint Hook):

1. При запуск під налагодженням GDB зчитує адресу `r_debug.r_brk`, яка вказує на внутрішню порожню функцію `_dl_debug_state()` у завантажувачі.
2. GDB встановлює програмну точку зупину (інструкцію `INT3` на x86_64) за цією адресою.
3. Коли програма викликає `dlopen()`, динамічний завантажувач змінює стан `r_debug.r_state = RT_ADD`, оновлює список `link_map` і викликає `_dl_debug_state()`.
4. Викликова інструкція перехоплюється налагоджувачем. GDB вичитує оновлений список `link_map`, зчитує відносні таблиці символів нових `.so` файлів і поновлює виконання програми.
5. Після завершення відображення завантажувач встановлює `r_debug.r_state = RT_CONSISTENT` і повторно викликає `_dl_debug_state()`.

```c
/* dlfcn_demo.c — Приклад динамічного завантаження плагіна мовою C */
#include <stdio.h>
#include <stdlib.h>
#include <dlfcn.h>

typedef double (*math_func_t)(double);

int main(void) {
    /* Відкриваємо математичну бібліотеку */
    void *handle = dlopen("libm.so.6", RTLD_LAZY);
    if (!handle) {
        fprintf(stderr, "dlopen error: %s\n", dlerror());
        return 1;
    }

    /* Очищаємо існуючі помилки */
    dlerror();

    /* Шукаємо функцію cos */
    math_func_t cos_fn = (math_func_t)dlsym(handle, "cos");
    const char *dlsym_err = dlerror();
    if (dlsym_err != NULL) {
        fprintf(stderr, "dlsym error: %s\n", dlsym_err);
        dlclose(handle);
        return 1;
    }

    /* Отримуємо інформацію про символ через dladdr */
    Dl_info info;
    if (dladdr((void*)cos_fn, &info)) {
        printf("Symbol 'cos' found in file: %s at base address: %p\n",
               info.dli_fname, info.dli_fbase);
    }

    /* Викликаємо знайдену функцію */
    double result = cos_fn(3.141592653589793 / 3.0);
    printf("cos(pi/3) = %f\n", result);

    /* Закриваємо хендл */
    dlclose(handle);
    return 0;
}
```

```cpp
// dlfcn_demo.cpp — Ідіоматичний C++20 RAII wrapper для dlfcn
#include <iostream>
#include <memory>
#include <expected>
#include <string_view>
#include <cmath>
#include <dlfcn.h>

namespace sys {

struct DlHandleDeleter {
    void operator()(void* handle) const noexcept {
        if (handle) {
            ::dlclose(handle);
        }
    }
};

using UniqueDlHandle = std::unique_ptr<void, DlHandleDeleter>;

class DynamicLibrary {
    UniqueDlHandle m_handle;
public:
    static std::expected<DynamicLibrary, std::string> load(std::string_view filename, int flags = RTLD_LAZY) {
        ::dlerror(); // Clear previous errors
        void* handle = ::dlopen(filename.data(), flags);
        if (!handle) {
            const char* err = ::dlerror();
            return std::unexpected(err ? err : "Unknown dlopen error");
        }
        return DynamicLibrary(UniqueDlHandle(handle));
    }

    explicit DynamicLibrary(UniqueDlHandle handle) : m_handle(std::move(handle)) {}

    template <typename FuncPtr>
    std::expected<FuncPtr, std::string> get_symbol(std::string_view symbol_name) const {
        ::dlerror(); // Clear errors
        void* sym = ::dlsym(m_handle.get(), symbol_name.data());
        const char* err = ::dlerror();
        if (err != nullptr) {
            return std::unexpected(std::string(err));
        }
        return reinterpret_cast<FuncPtr>(sym);
    }
};

} // namespace sys

int main() {
    auto lib_result = sys::DynamicLibrary::load("libm.so.6");
    if (!lib_result) {
        std::cerr << "Failed to load library: " << lib_result.error() << '\n';
        return 1;
    }

    auto cos_symbol = lib_result->get_symbol<double(*)(double)>("cos");
    if (!cos_symbol) {
        std::cerr << "Failed to resolve symbol: " << cos_symbol.error() << '\n';
        return 1;
    }

    auto cos_fn = *cos_symbol;
    std::cout << "cos(pi/3) = " << cos_fn(M_PI / 3.0) << '\n';

    return 0;
}
```
