Високонавантажена база даних PostgreSQL генерує тисячі випадкових читань та синхронних викликів `fsync()` щосекунди. Стандартний сторінковий кеш Linux керується алгоритмом LRU (Least Recently Used), який не відрізняє одноразового суцільного сканування диска від гарячого індексу B-tree, що призводить до вимивання важливих сторінок і просідання продуктивності IOPS у десятки разів. Для розв'язання цієї проблеми ZFS обходить сторінковий кеш ядра для власних читань і впроваджує самонастроюваний кеш ARC в оперативній пам'яті разом із журналом синхронних записів ZIL на енергонезалежному накопичувачі.

Така подвійна архітектура розділяє виклики читання та запису на два незалежні шляхи обробки. Запити на зчитування даних оптимізуються самонастроюваним алгоритмом у пам'яті, тоді як затримка синхронного запису скорочується до часток мілісекунди завдяки послідовному логуванню на швидкий накопичувач.

## 1. Недоліки LRU та двовимірне кешування ARC

Традиційні кеші ядра Linux будуються довкола одновимірних черг LRU. Головна слабкість класичного LRU полягає у відсутності пам'яті про частоту звернень. Якщо додаток виконує послідовне зчитування файлу розміром 50 ГБ, цей потік даних заповнює всі сторінки кешу, витісняючи структури даних, які використовувалися протягом місяців. Після завершення сканування система опиняється в стані «холодного кешу», а продуктивність основних процесів падає.

Алгоритм ARC (Adaptive Replacement Cache) розв'язує цю дилему, розбиваючи кеш оперативної пам'яті на два рівноправні списки блоків:
- **MRU (Most Recently Used)**: зберігає блоки, до яких зверталися принаймні один раз. Цей список захищає дані, потрібні для поточних короткочасних операцій.
- **MFU (Most Frequently Used)**: зберігає блоки, до яких зверталися принаймні двічі. Сюди потрапляють гарячі індекси, часті записи баз даних та метадані, які мають високу повторну цінність.

Сумарна ємність блоків у MRU та MFU дорівнює цільовому розміру кешу `c`. Проте фундаментальною новацією ARC є введення двох додаткових списків метаданих — списків «привидів» (ghost lists):
1. `mru_ghost` (B₁): містить покажчики та контрольні суми блоків, які були витіснені зі списку MRU через брак пам'яті.
2. `mfu_ghost` (B₂): містить покажчики блоків, витіснених зі списку MFU.

Списки привидів не займають значного обсягу пам'яті, оскільки утримують лише метадані без самого вмісту сторінок. Якщо додаток робить запит до блоку, якого немає в RAM, але його покажчик виявляється в списку `mru_ghost`, ZFS реєструє «влучання в привида» (ghost hit). Це сигнал для алгоритму, що список Recency зазнає надмірного тиску. ZFS миттєво реагує, збільшуючи адаптивний параметр `p` — цільову частку пам'яті під список MRU.

Коригування параметра `p` відбувається за формулою динамічного зворотного зв'язку. При влучанні в B₁ параметр `p` зростає:
```
p = min(c, p + max(1, |B2| / |B1|))      [збільшення ваги MRU]
```

І навпаки, якщо запит влучає в список B₂ (`mfu_ghost`), алгоритм розуміє, що системі бракує пам'яті під часто запитувані блоки, і зменшує параметр `p`:
```
p = max(0, p - max(1, |B1| / |B2|))      [збільшення ваги MFU]
```

Завдяки цьому співвідношенню ARC самостійно знаходить оптимальну точку рівноваги для будь-якого змішаного навантаження, забезпечуючи складність `O(1)` для кожної операції пошуку та витіснення. Докладний розбір винайдення цього алгоритму та його патентної історії наведено в матеріалі [Історія винайдення ARC та патентний конфлікт IBM і Sun](topic:sys-unix/zfs-on-linux-arc/hist-arc-algorithm.md).

## 2. Реалізація ZFS on Linux: керування пам'яттю ядра та L2ARC

У підсистемі ZFS on Linux (ZoL) реалізація ARC суттєво відрізняється від традиційного сторінкового кешу підсистеми VFS. Оскільки ZFS портовано із Solaris через шар абстракції SPL (Solaris Porting Layer), вона не тримає своїх блоків у сторінковому кеші VFS, а розподіляє оперативну пам'ять через власну систему слаб-алокаторів `spl_kmem_cache`.

Це створює специфічну взаємодію з підсистемою керування віртуальною пам'яттю (Linux Memory Management). З точки зору ядра Linux, уся пам'ять, виділена під ARC, вважається зайнятою ядром і його модулями (slab/kernel allocation), а не сторінковим кешем диска. Щоб запобігти передчасному виклику OOM Killer (Out Of Memory) при дефіциті RAM, ZFS реєструє спеціальний зворотний виклик у підсистемі ядра — `register_shrinker()`.

Коли Linux відчуває брак пам'яті під процеси користувача, механізм `shrinker` надсилає сигнал підсистемі ZFS. ARC негайно запускає процедуру витіснення сторінок (ARC Eviction), зменшуючи цільовий розмір `c` і повертаючи сторінки оперативної пам'яті ядру.

![Архітектура ZFS ARC, L2ARC та ZIL](img/arc-zil-arch.svg)
*Архітектура взаємодії оперативної пам'яті (ARC з MRU/MFU), розширення кешу читання L2ARC та прискорювача синхронного запису ZIL/SLOG.*

Для керування обсягом RAM ZFS надає серію параметрів модуля ядра:
- `zfs_arc_max`: верхній поріг ємності ARC (за замовчуванням дорівнює 50% фізичної RAM у Linux).
- `zfs_arc_min`: нижня межа, за яку `shrinker` не може стиснути ARC.
- `zfs_compressed_arc_enabled`: режим збереження стиснутих блоків у пам'яті. Якщо на датасеті активовано стискання LZ4 або ZSTD, ARC зберігає блоки в стиснутому вигляді, і ефективна ємність кешу зростає рівно настільки, наскільки стискаються самі дані: на текстах і сторінках баз даних з LZ4 це приблизно півтора-два рази, на вже стиснутих файлах — ніскільки.

Крім того, ZFS розділяє пам'ять під блоки даних та метадані (dnodes, dentries, ієрархічні покажчики). До OpenZFS 2.2 частку ARC під метадані обмежував окремий параметр `arc_meta_limit`. Від 2.2 цієї межі немає: адаптацію ARC переписано, баланс даних і метаданих він виводить сам із влучань у списки привидів, а єдиним важелем лишився `zfs_arc_meta_balance`.

Якщо обсягу оперативної пам'яті недостатньо для всього гарячого набору даних, ZFS дозволяє підключити швидкі SSD або NVMe накопичувачі як розширення кешу читання — **L2ARC (Level 2 ARC)**. Наповнює його фоновий потік `l2arc_feed_thread`: він періодично проглядає хвости списків MRU та MFU — тобто блоки, найближчі до витіснення, — і завчасно копіює їх на SSD. Саме витіснення з RAM після цього просто відкидає тіло блоку, бо копія вже лежить у L2ARC.

При цьому L2ARC залишається виключно кешем читання:
1. Запис у L2ARC відбувається асинхронно кільцевими буферами з обмеженням швидкості (`l2arc_write_boost` та `l2arc_write_max`), щоб не зношувати ресурс накопичувача SSD.
2. Для кожного блоку в L2ARC в основній оперативній пам'яті ARC утримується коротка структура метаданих — порядку сотні-двох байтів. Порахуймо: 1 ТБ L2ARC при типовому записі 128 КБ — це близько восьми мільйонів блоків, тобто одиниці гігабайтів RAM лише під заголовки. Та сама ємність під ZVOL із блоком 8 КБ дає вже понад сто мільйонів блоків — десятки гігабайтів, більше, ніж є на багатьох серверах.
3. Вміст L2ARC зберігається між перезавантаженнями завдяки постійним заголовкам (Persistent L2ARC, з OpenZFS 2.0), що звільняє від прогрівання кешу з нуля після планового обслуговування сервера.

Докладний опис усіх параметрів модуля ядра та метрик експорту наведено у статті [Інтерфейс kstat та параметри ядра для налаштування ARC і ZIL](topic:sys-unix/zfs-on-linux-arc/api-arc-kstat.md).

## 3. Внутрішня структура буферів `arc_buf_t` та керування життєвим циклом

Кожен блок даних у підсистемі ARC описується двома основними заголовочними структурами ядра: `arc_buf_hdr_t` (заголовок блоку ARC) та `arc_buf_t` (буфер доступу споживача). Розділення заголовка та самого буферного масиву дозволяє ZFS підтримувати кілька незалежних споживачів для одного фізичного блоку в пам'яті без дублювання тіла даних.

Структура `arc_buf_hdr_t` утримує ключові метадані:
- `b_dva`: трикомпонентний адресний вектор виділення на дисках (Data Virtual Address), який вказує на точне розміщення блоку в пулі VDEV.
- `b_birth`: номер транзакційної групи (TXG), в якій цей блок було створено або модифіковано.
- `b_flags`: набір прапорів стану (стиснутий блок, зашифрований блок, метадані, заголовок-привид без тіла даних).
- `b_l1hdr` / `b_l2hdr`: посилання на вузли двобічних зв'язаних списків MRU, MFU або L2ARC.

Життєвий цикл блоку в ARC проходить через стан зчитування, підтвердження цілісності та витіснення. Коли підсистема SPA (Storage Pool Allocator) зчитує блок із диска, виконується перевірка контрольної суми (Fletcher4 за замовчуванням, SHA-256 чи Skein — коли ввімкнено дедуплікацію або посилений режим), записаної у батьківському покажчику `blkptr_t`. Лише після збігу контрольної суми заголовок `arc_buf_hdr_t` отримує стан перевіреного блоку та зв'язується зі списком MRU.

Якщо пам'ять ARC зазнає тиску, алгоритм витіснення викликає функцію `arc_evict_state()`. Блоки зі списку MRU або MFU переходять у відповідні списки привидів B₁ або B₂, а їхній фактичний payload пам'яті повертається у слаб-алокатор `spl_kmem_cache`.

Така реалізація забезпечує чітке розділення між рівнями обробки: шар DMU (Data Management Unit) оперує абстракцією dnode та файловими об'єктами, шар ARC контролює виділення та витіснення оперативної пам'яті, а шар SPA займається кодуванням блоків у дискові масиви VDEV.

Крім того, на рівні DMU функціонує додатковий шар кешування метаданих — кеш буферів даних **DBuf (Data Buffer Cache)**. Структура `dmu_buf_impl_t` тримає окремий блок об'єкта (dnode, шматок файлу, indirect-блок) уже розпакованим — саме з нею працюють системні виклики `read()` та `write()`, не чіпаючи стиснутого вмісту ARC. Поріг пам'яті під цей кеш задає параметр ядра `dbuf_cache_max_bytes`. Коли поріг перевищено, фоновий потік викидає найдавніші dbuf-и; сам блок при цьому нікуди не зникає — він лишається в ARC, лише знову в стиснутому вигляді.

## 4. Журнал синхронного запису ZIL та SLOG

Забезпечення цілісності даних при записі у ZFS спирається на транзакційну модель Copy-on-Write (CoW). Усі операції зміни даних групуються в атомарні Transaction Groups (TXG). За замовчуванням ZFS збирає записи у пам'яті протягом 5 секунд (параметр `zfs_txg_timeout`), після чого фоновий процес впорядковує блоки, розраховує контрольні суми, формує нове дерево Merkle та скидає його на фізичні диски пулу.

Транзакційна група під час свого життєвого циклу проходить через чотири послідовні стани:
1. `TXG_STATE_OPEN`: поточна відкрита транзакція, в яку збираються всі операції запису процесів користувача у пам'яті RAM.
2. `TXG_STATE_QUIESCED`: групу закрито для нових записів, а ті, що вже розпочалися, доведено до кінця; нові операції йдуть у наступну відкриту групу.
3. `TXG_STATE_WAIT_FOR_SYNC`: очікування черги на скидання на диски.
4. `TXG_STATE_SYNCED`: потік синхронізації записав сформоване дерево блоків на накопичувачі VDEV і оновив uberblock.

Цей механізм ідеально працює для асинхронного запису (стандартний виклик `write()`), але створює критичну проблему для синхронних операцій. Коли додаток (наприклад, СУБД або сервер віртуалізації) викликає `fsync()`, `fdatasync()` або відкриває файл із прапорцем `O_SYNC`, POSIX-стандарт вимагає, щоб системний виклик не повертав керування доти, доки дані не будуть фізично закріплені на енергонезалежному носії. Чекати до 5 секунд на формування та повний запис усієї транзакційної групи TXG означало б падіння швидкості синхронного запису до одиниць IOPS.

Для розв'язання цієї проблеми в ZFS розроблено підсистему **ZIL (ZFS Intent Log)**.

![Дерево транзакцій ZFS та Merkle Tree](img/merkle-tree.svg)
*Ієрархічна структура дерев блоків ZFS, де Uberblock посилається на метадані та блоки даних із контролем цілісності.*

ZIL — це послідовний журнал намірів запису. Коли додаток ініціює синхронний запис, ZFS виконує дві паралельні дії:
1. Копіює блок даних у пам'ять ARC для включення у наступну планову транзакційну групу TXG.
2. Негайно формує компактну структуру запису журналу ZIL (`lwb_t` — Log Write Block) і копіює її на диск ZIL.

Запис у ZIL складається з заголовка `zil_header_t` та послідовності транзакційних блоків `lr_t` (Log Record). Кожна структура `lr_write_t` містить ідентифікатор об'єкта (dnode number), зміщення у файлі, довжину запису та безпосередній корисний вантаж даних.

При цьому підсистема ZIL має розумне розмежування за розміром блоку (параметр `zfs_immediate_write_sz`):
- Для малих записів (до 32 КБ за замовчуванням) тіло даних копіюється безпосередньо у блок ZIL для забезпечення найменшої затримки.
- Для великих записів (понад 32 КБ) ZIL виділяє блок безпосередньо у дисковому пулі VDEV, а в журнал SLOG записується лише короткий покажчик на цей блок, запобігаючи подвійному запису великих обсягів I/O.

Як тільки запис у ZIL завершено і накопичувач підтвердив збереження даних на магнітній пластині (або у флеш-пам'яті з захистом від збою живлення PLP), виклик `fsync()` миттєво повертає додаткам успішний статус.

Послідовність дій під час синхронного запису:

```
[Додаток: write() + fsync()]
         │
         ├───► 1. Збереження блоку в RAM (ARC) ───► Чекає скидання TXG (до 5 с)
         │                                               │
         └───► 2. Формування ZIL Record                  │
                     │                                   │
                     ▼                                   ▼
         3. Синхронний запис у SLOG/ZIL         5. Фоновий скид TXG на vdev
                     │                                   │
                     ▼                                   ▼
         4. Повернення успіху fsync()           6. Звільнення записів ZIL
```

Зверніть увагу: за нормальної роботи системи ZIL **ніколи не читається**. Він працює виключно в режимі запису. Блоки даних для подальшого зчитування додатками беруться з кешу ARC або з основних дисків пулу після скидання TXG. 

Зчитування ZIL відбувається лише в один момент — під час імпорту пулу після аварійного вимкнення живлення або паніки ядра (процедура **ZIL Replay Log**). Під час монтування ZFS знаходить останній валідний Uberblock, відкриває журнал ZIL і відтворює всі синхронні транзакції, які були підтверджені додатками, але ще не встигли увійти в останню збережену TXG на дисках.

За замовчуванням ZIL виділяє блоки для журналювання безпосередньо на основних дисках пулу (data vdevs). Якщо пул зібрано з повільних жорстких дисків HDD у масив RAID-Z, синхронний запис викликає сильну фрагментацію та затримки, оскільки голівкам диска доводиться постійно стрибати між зоною ZIL та зоною даних.

Для усунення цього вузького місця ZFS дозволяє винести журнал на окремий виділений пристрій — **SLOG (Separate Intent Log)**. SLOG створюється шляхом додавання швидких NVMe або SAS SSD накопичувачів із малим часом відгуку (Latency) та обов'язковим конденсаторним захистом від втрати живлення (Power Loss Protection, PLP) командою `zpool add pool log <device>`. 

Використання виділеного SLOG не змінює загальну семантику ZIL, але переносить навантаження з послідовного синхронного запису на надшвидкий SSD, залишаючи основними HDD-дискам лише роботу з фоновими послідовними транзакційними групами TXG.

Семантикою ZIL можна керувати на рівні окремих датасетів за допомогою властивості `sync`:
- `sync=standard` (режим за замовчуванням): синхронні записи йдуть через ZIL/SLOG, асинхронні — буферизуються в RAM.
- `sync=always`: примусово перетворює абсолютно всі операції запису (включно зі звичайними викликами `write()`) на синхронні через ZIL. Це гарантує максимальний рівень захисту від втрат, але суттєво підвищує навантаження на накопичувач.
- `sync=disabled`: повністю вимикає ZIL. Виклики `fsync()` повертають керування негайно, ніби дані вже на диску, хоча вони залишаються лише в оперативній пам'яті. **Увага:** цей режим забезпечує найвищу швидкість, але при збої живлення система втрачає останні 5 секунд усіх записів, що може призвести до руйнування внутрішніх структур СУБД.

## 5. Профілювання, інструментування та трасування ZFS on Linux

Для спостереження за станом ARC та ZIL ZFS експортує повну телеметрію через системний інтерфейс `/proc/spl/kstat/zfs/arcstats`. Текстовий файл містить лічильники зчитувань, влучань, промахів, а також розбиття обсягів оперативної пам'яті.

Ключовим показником ефективності підсистеми є коефіцієнт влучань **Hit Ratio**:
```
hit_ratio = (hits * 100.0) / (hits + misses)      [відсоток влучань ARC]
```

Якщо значення `hit_ratio` падає нижче 80–85% на серверах баз даних, це свідчить про те, що розмір гарячої бази перевищує виділену пам'ять `zfs_arc_max`, і система постійно звертається до дискових накопичувачів. Для глибшого аналізу розглядають частки влучань у списки MRU та MFU:
- Високий відсоток `mru_hits` вказує на навантаження з переважанням нових унікальних даних (наприклад, потік логів або завантаження медіафайлів).
- Переважання `mfu_hits` показує, що кеш успішно утримує повторювані структури (індекси, таблиці значень).

Моніторинг лічильників `mru_ghost_hits` та `mfu_ghost_hits` дає змогу оцінити напрямок адаптації кешу. Якщо лічильник `mru_ghost_hits` зростає з високою швидкістю, а параметр `p` уже вперся у верхню межу `c`, кешу немає куди рости — лишається додавати оперативну пам'ять. (На OpenZFS від 2.2 лічильника `p` в `arcstats` немає, і той самий висновок дає сама пара `mru_ghost_hits`/`mfu_ghost_hits`.)

Для глибинного налагодження розробники та системні інженери використовують шар трасування ядра Linux через утиліти `bpftrace` або `ftrace`. Модуль ZFS надає власну систему логування налагоджувальних повідомлень у `/proc/spl/kstat/zfs/dbgmsg`. Запис у цей буфер здійснюється внутрішньою функцією ядра `zfs_dbgmsg()`. Під час імпорту пулів або складних процедур відновлення ZIL Replay адміністратор може простежити хід операцій командою `cat /proc/spl/kstat/zfs/dbgmsg`.

Крім того, затримку запису в ZIL можна міряти в реальному часі, повісивши bpftrace на вхід і вихід ядрової функції `zil_commit()`:
```
# bpftrace -e 'kprobe:zil_commit { @start[tid] = nsecs; }
               kretprobe:zil_commit /@start[tid]/ {
                   @us = hist((nsecs - @start[tid]) / 1000); delete(@start[tid]); }'
```
Цей скрипт будує гістограму затримок викликів `zil_commit()`, дозволяючи виявити випадки, коли накопичувач SLOG зазнає сплесків затримок I/O через знос флеш-пам'яті або невиконаний TRIM.

Практичну реалізацію утиліти збору статистики на мовах C та C++ наведено в матеріалі [Моніторинг та аналіз ефективності ARC кешу мовами C та C++](topic:sys-unix/zfs-on-linux-arc/proj-arc-monitoring.md).

> 🔧 **Навіщо це.** На виділеному сервері баз даних під управлінням Linux та ZFS стандартні утиліти `free` та `top` показують, що майже вся оперативна пам'ять зайнята під `used`, а сторінковий кеш `buff/cache` залишається практично порожнім (близько кількох сотень мегабайт). Це нормальна поведінка ZFS: ARC зберігає свої сторінки у структурі `kmem_cache` ядра, яку Linux не зараховує до звичайного Buffer Cache. Для коректного визначення вільної пам'яті системний адміністратор повинен аналізувати показник `size` у `/proc/spl/kstat/zfs/arcstats` та обмежувати `zfs_arc_max`, щоб залишати достатній запас RAM під буфери сортування СУБД. При використанні синхронного запису додавання дзеркального NVMe SLOG із захистом PLP дозволяє підняти продуктивність викликів `fsync()` у СУБД PostgreSQL або MySQL із сотень операцій за секунду (стеля одиничного HDD) до десятків тисяч — без ризику втрати транзакцій.
