# 📋 Родина викликів exec: сигнатури, літери, помилки

Тут зібрано всі форми запуску програми — від системного виклику до бібліотечних обгорток: точні підписи, значення кожного аргументу, правила пошуку в `PATH`, повний перелік `errno` і версії, з яких воно доступне. Довідка потрібна в момент, коли код уже пишеться і треба вибрати одну з дев'яти форм, сім із яких відрізняються самими лише двома буквами в назві.

## Ім'я як код

Назви цієї родини не довільні: кожна літера після `exec` — це вмикач однієї властивості, і читати їх треба зліва направо.

| літера | що вмикає |
|---|---|
| **`l`** (*list*) | аргументи передають **окремими параметрами** через змінний список, кінець позначають нульовим покажчиком |
| **`v`** (*vector*) | аргументи передають **одним масивом** `char *const argv[]`, останній елемент — `NULL` |
| **`e`** (*environment*) | оточення задають **явним** масивом `envp`; без цієї літери воно береться з глобальної змінної `environ` |
| **`p`** (*path*) | якщо в імені немає скісної риски, файл **шукають у `PATH`**; без літери шлях виконують як є |

Літери `l` і `v` — взаємовиключні, `e` і `p` — незалежні. Виходить сітка з восьми клітинок, і сім із них мають імена:

| | шлях виконують як є | шукають у `PATH` |
|---|---|---|
| **список; оточення успадковане** | `execl` | `execlp` |
| **список; оточення задане** | `execle` | *немає* |
| **масив; оточення успадковане** | `execv` | `execvp` |
| **масив; оточення задане** | `execve` | `execvpe` |

Порожня клітинка — не помилка верстки: функції `execlpe` немає. POSIX стандартизував шість імен (`execl`, `execle`, `execlp`, `execv`, `execve`, `execvp`), сьоме — `execvpe` — додала glibc як власне розширення, а восьме не додав ніхто. Потрібна саме ця комбінація — складають масив і кличуть `execvpe`.

## Підписи

```c
#include <unistd.h>

int execl (const char *pathname, const char *arg, ... /*, (char *) NULL */);
int execlp(const char *file,     const char *arg, ... /*, (char *) NULL */);
int execle(const char *pathname, const char *arg, ...
                                 /*, (char *) NULL, char *const envp[] */);

int execv (const char *pathname, char *const argv[]);
int execvp(const char *file,     char *const argv[]);
int execve(const char *pathname, char *const argv[], char *const envp[]);
```

```c
#define _GNU_SOURCE
#include <unistd.h>

int execvpe(const char *file, char *const argv[], char *const envp[]);
int fexecve(int fd,           char *const argv[], char *const envp[]);
```

```c
#define _GNU_SOURCE
#include <linux/fcntl.h>   /* сталі AT_* */
#include <unistd.h>

int execveat(int dirfd, const char *pathname,
             char *const argv[], char *const envp[], int flags);
```

| форма | де живе | доступність | безпечна після `fork` у багатопотоковій програмі |
|---|---|---|---|
| `execve` | системний виклик | завжди | так |
| `execveat` | системний виклик | ядро 3.19; обгортка glibc — з 2.34, раніше `syscall(SYS_execveat, …)` | так |
| `execl`, `execle`, `execv` | бібліотека С | POSIX, завжди | так |
| `fexecve` | бібліотека С | glibc 2.3.2 | так |
| `execlp`, `execvp` | бібліотека С | POSIX, завжди | **ні** |
| `execvpe` | бібліотека С, розширення GNU | glibc 2.11 | **ні** |

Останній стовпчик — не дрібниця. Між розгалуженням і заміною образу дозволено кликати лише асинхронно-сигнально безпечні функції ([асинхронно-сигнальна безпека](root:sys-unix/async-signal-safety) — властивість функції не залежати від замків і глобального стану, які могли лишитися захопленими). Варіанти з `p` виконують пошук у просторі користувача й не мають гарантії обійтися без розподільника пам'яті — тому POSIX їх до безпечних не зараховує, а `execve`, `execv`, `execl`, `execle` й `fexecve` перелічує явно. Практичний висновок простий: у коді дитини після `fork` беруть форму без `p`, а пошук у `PATH`, якщо він потрібен, роблять **до** розгалуження. Одна історична поправка до таблиці: до glibc 2.24 `execl` і `execle` збирали масив аргументів через `realloc` і тому безпечними теж не були; виправлено у 2.24.

## Форми зі списком: змінний список і пастка з NULL

```c
execl("/bin/ls", "ls", "-l", "/tmp", (char *)NULL);
```

Тут `"/bin/ls"` — що виконати, а `"ls"` — те, чим програма себе побачить. Це різні речі, і саме тому вони стоять окремими аргументами.

Кінець списку **обов'язково** позначають нульовим покажчиком, і його **обов'язково** приводять до типу: `(char *)NULL`. Голий `NULL` тут — не стилістична вільність, а помилка. Змінна частина списку не має прототипу, тож компілятор нічого не перетворює: якщо `NULL` розкривається в цілий нуль, на стек ляже число розміром `int`, а функція зчитуватиме звідти покажчик — на 64-бітових платформах це різні розміри, і `execl` побачить сміття замість кінця списку. Правильна форма — `(char *)NULL`; `(char *)0` теж годиться.

Тієї самої природи друга властивість форм зі списком: кількість аргументів мусить бути відома під час компіляції. Список, довжина якого з'ясовується під час роботи, змінним списком не передати — для цього й існують форми з `v`.

У `execle` оточення стоїть **після** позначки кінця:

```c
char *env[] = { "LANG=C", "TZ=UTC", NULL };
execle("/usr/bin/date", "date", "+%H:%M", (char *)NULL, env);
```

## Форми з масивом

```c
char *argv[] = { "gzip", "-9", "data.bin", NULL };
execv("/usr/bin/gzip", argv);
```

Масив мусить закінчуватися `NULL` — саме він, а не якась окрема довжина, каже, де список скінчився. Тип `char *const argv[]` читається як «масив незмінних покажчиків на змінні символи»: перепризначати елементи не можна, а самі рядки формально не сталі. У С це нікому не заважає, бо рядковий літерал там має тип `char[]`; у C++ літерал уже `const char[]`, і той самий масив без приведення не збереться — звідси `const_cast` у коді, який доводиться писати обома мовами. Коли масив потрібен лише на один виклик, його зручно писати складеним літералом просто на місці:

```c
execv("/usr/bin/gzip", (char *[]){ "gzip", "-9", "data.bin", NULL });
```

`argv[0]` — домовленість, а не дані для ядра: система кладе рядок на стек нової програми й на цьому все. Тому в нього вкладають зміст. Оболонка, запущена як стартова для сеансу, дістає `argv[0]` з дефісом попереду — `-bash`, — і читає цю позначку як «я стартова оболонка, читай `profile`» ([оточення сеансу](root:sys-unix/session-environment) — які файли оболонка читає при вході й що з них дістає). Ані ядро, ані бібліотека цієї угоди не тлумачать.

## Оточення: `environ` чи `envp`

Форми без літери `e` беруть оточення з глобальної змінної:

```c
#include <unistd.h>
extern char **environ;         /* масив рядків "КЛЮЧ=значення", кінець — NULL */
```

Це та сама змінна, яку правлять `setenv`, `putenv` й `unsetenv`, тож `execv` після `setenv` передасть уже зміну. Форми з `e` на `environ` не дивляться взагалі — новий образ дістане рівно те, що ви склали ([аргументи й оточення програми](root:sys-unix/argv-and-environment) — як ці два масиви лягають на стек і як програма їх читає).

Хочете віддати порожнє оточення — передайте масив із одного `NULL`, а не сам `NULL`:

```c
execle("/bin/sh", "sh", "-c", "env", (char *)NULL, (char *[]){ NULL });
```

## Варіанти з `p`: пошук у `PATH` крок за кроком

Пошук робить бібліотека, тому його алгоритм можна описати точно.

1. Якщо в `file` є хоч одна скісна риска — це вже шлях, ніякого пошуку немає, одразу `execve`.
2. Інакше беруть `PATH` з оточення. Якщо змінної немає, підставляють типовий список від `confstr(_CS_PATH)` — зазвичай `/bin:/usr/bin`; поточного каталогу там немає.
3. Список ріжуть двокрапками й до кожного каталогу дописують `file`, після чого пробують `execve`.
4. **`EACCES`** не спиняє пошук: бібліотека запам'ятовує цю помилку й іде далі; якщо жодна інша спроба не вдалася, саме `EACCES` і повернеться наприкінці. Порожній елемент списку (`PATH=/usr/bin::/bin`) означає поточний каталог — стара звичка, через яку в `PATH` намагаються не лишати порожніх місць.
5. **`ENOEXEC`** — окремий випадок: файл існує, права є, але формат ядру невідомий. Тоді бібліотека запускає `/bin/sh`, передавши їй шлях до цього файлу першим аргументом. Це вимога POSIX і спадок часів, коли позначки інтерпретатора на початку файлу ще не існувало. Якщо й ця спроба провалилася, пошук припиняється.

Окрема тонкість `execvpe`, яка коштувала багатьом годину налагодження: **`PATH` береться з `environ` того, хто кличе, а не з переданого `envp`**. Тобто новий `PATH` у `envp` вплине на дочірню програму, але не на те, де шукали її саму. Треба шукати за іншим `PATH` — його виставляють собі через `setenv` перед викликом (або, у переносному коді, складають шлях самотужки).

> 🔧 **Навіщо це.** Звідси береться правило безпеки для програм із підвищеними правами: у них форми з `p` не вживають узагалі. `PATH` цілком контролює той, хто запустив програму, і `execvp("helper", …)` у привілейованому коді означає «виконай той `helper`, який мені підсунуть». Привілейований код кличе `execve` з абсолютним шляхом або `fexecve` на вже перевіреному дескрипторі ([setuid і підвищення прав](root:sys-unix/setuid-and-privilege) — за яких умов новий образ дістає чужу ідентичність).

## Два виклики ядра

`execve` приймає шлях. `execveat` приймає **пару** «дескриптор каталогу + шлях», як і решта викликів із суфіксом `at` ([розв'язання шляху](root:sys-unix/path-resolution) — як ім'я перетворюється на inode й чому проміжок між перевіркою і дією небезпечний).

| аргумент `execveat` | значення |
|---|---|
| `dirfd` | каталог, від якого відлічують відносний `pathname`; `AT_FDCWD` — від поточного каталогу; при абсолютному `pathname` ігнорується |
| `pathname` | шлях; порожній рядок дозволено лише з `AT_EMPTY_PATH` |
| `flags` | `0`, `AT_EMPTY_PATH`, `AT_SYMLINK_NOFOLLOW` або їх поєднання |

| прапорець | дія |
|---|---|
| `AT_EMPTY_PATH` | `pathname` порожній — виконати сам файл, на який указує `dirfd` (зокрема відкритий з `O_PATH`) |
| `AT_SYMLINK_NOFOLLOW` | якщо ціль виявилася символьним посиланням, виклик відмовляє з `ELOOP` замість переходу за ним |

`fexecve` — це та сама дія, лише коротшим підписом: виконати те, на що вже вказує дескриптор ([файловий дескриптор](root:sys-unix/file-descriptor) — число, за яким процес звертається до відкритого об'єкта). Сенс у ній один і серйозний: між перевіркою файлу й запуском немає імені, отже, немає й вікна, у яке ім'я можна перепризначити на інший файл. Відкрив, порахував відбиток, звірив, виконав **той самий** дескриптор.

Реалізація в glibc змінювалася: до версії 2.27 `fexecve` робив `execve("/proc/self/fd/N", …)` і без змонтованого `/proc` відмовляв із `ENOSYS`; з 2.27 він кличе `execveat` із `AT_EMPTY_PATH`, і `/proc` більше не потрібен.

Дві поведінки цієї пари, яких не видно з підпису:

- **Дескриптор із `FD_CLOEXEC` + сценарій = `ENOENT`.** Ядро запускає не сценарій, а інтерпретатора, і тому передає йому сам сценарій аргументом виду `/dev/fd/N`. Але дескриптор `N` закривається саме в момент заміни образу — інтерпретатор приходить до вже закритих дверей. Для сценаріїв прапорець доводиться знімати, і тоді дескриптор витікає в нову програму.
- **`argv[0]` сценарію — це `/dev/fd/N`, а не ім'я файлу.** Сценарій, який виводить своє ім'я чи шукає щось поруч із собою, побачить не те, що очікує.

## Повний перелік помилок

Усі форми повертають `-1` і виставляють `errno`; успішного повернення не буває. Помилки бібліотечних обгорток — це помилки `execve`, тож перелік один на всіх.

| `errno` | коли |
|---|---|
| `E2BIG` | сумарний розмір `argv` і `envp` перевищив стелю, або один рядок довший за 32 сторінки, або задовгий сам шлях |
| `EACCES` | немає права пошуку в каталозі шляху; немає біта виконання; файл не звичайний; файлову систему змонтовано з `noexec` |
| `EAGAIN` | зміна реального UID вивела б процес за `RLIMIT_NPROC` (з ядра 3.1) |
| `EBADF` | `execveat` із відносним шляхом і недійсним `dirfd` |
| `EFAULT` | шлях або покажчики всередині `argv`/`envp` дивляться поза доступну пам'ять |
| `EINVAL` | в ELF-файлі більш ніж один сегмент `PT_INTERP`; для `execveat` — недійсний `flags` |
| `EIO` | помилка вводу-виводу під час читання файлу |
| `EISDIR` | інтерпретатор ELF виявився каталогом |
| `ELIBBAD` | інтерпретатор ELF невідомого формату |
| `ELOOP` | забагато символьних посилань у шляху; перевищено межу вкладеності сценаріїв (чотири); для `execveat` — `AT_SYMLINK_NOFOLLOW` на посиланні |
| `EMFILE` | вичерпано ліміт відкритих дескрипторів процесу |
| `ENAMETOOLONG` | шлях задовгий |
| `ENFILE` | вичерпано системний ліміт відкритих файлів |
| `ENOENT` | немає файлу — **або** немає названого в ньому інтерпретатора; для `fexecve` — сценарій на дескрипторі з `FD_CLOEXEC` |
| `ENOEXEC` | формат не розпізнано: чужа архітектура, зіпсований заголовок, невідома прикмета |
| `ENOMEM` | бракує пам'яті ядра |
| `ENOSYS` | `fexecve` до glibc 2.27 без змонтованого `/proc` |
| `ENOTDIR` | елемент шляху не є каталогом |
| `EPERM` | біти підвищення прав на файлі з файлової системи `nosuid`; процес під трасуванням; програма «не розуміє можливостей» |
| `ETXTBSY` | файл відкрито кимось на запис |

Три рядки з цієї таблиці збивають з пантелику найчастіше. `ENOENT` при цілком наявному файлі майже завжди означає відсутнього інтерпретатора, а не відсутню програму. `EACCES` від форм із `p` — це підсумок усього пошуку, а не вирок конкретному каталогові. А `ENOEXEC` від форм із `p` ви не побачите ніколи: бібліотека перехоплює його й тихо підставляє `/bin/sh`.

## Порожній `argv` — окремий випадок

`execve` дозволяє передати `argv`, у якому немає жодного елемента (і навіть `NULL` замість масиву — нестандартне розширення Linux, на яке спиратися не варто). Нова програма при цьому стартує з `argc == 0`: `argv[0]` дорівнює `NULL`, а за ним у пам'яті одразу починається оточення, бо ядро кладе обидва масиви на стек упритул один до одного. Отже, `argv[1]` — це насправді `envp[0]`.

Саме на цьому побудували напад на `pkexec` (CVE-2021-4034, оприлюднено 25 січня 2022 року фірмою Qualys): привілейована програма читала `argv[1]`, не перевіривши `argc`, і тим самим давала змінній оточення потрапити туди, де код чекав на аргумент, — а далі підсунути собі чужу бібліотеку. Виправлення пішло у двох напрямках. Сама програма стала перевіряти `argc`; ядро ж від зміни `exec: Force single empty string when argv is empty` **саме додає порожній рядок**, роблячи `argc == 1`, і пише в журнал попередження `launched … with NULL argv: empty string added`. Обговорення почала Аріадна Коніл наприкінці січня 2022 року пропозицією просто відмовляти з `EINVAL`; у мейнлайн (5.18, березень 2022, з бекпортами в стабільні гілки 5.4–5.17) лягла м'якша редакція Кіса Кука, бо жорстка відмова ламала б наявні програми. OpenBSD й FreeBSD обрали саме суворий шлях і такий виклик відхиляють.

Для того, хто пише код: `argv[0]` завжди передавайте явно, а в програмі, що має підвищені права, першою дією перевіряйте `argc >= 1`.

## Мінімальний робочий виклик

Заміна образу відбувається вже в дитині, тож батько бачить лише код виходу `127` і не знає, чому саме не запустилося ([код виходу як інтерфейс програми](root:sys-unix/exit-status) — одне число, яким процес звітує про долю). Канонічний спосіб донести справжній `errno` — труба, помічена на закриття при заміні: якщо заміна вдалася, ядро закриє її саме, і батько прочитає нуль байтів; якщо ні — дитина встигне записати туди число ([канали](root:sys-unix/pipe-and-fifo) — однобічний потік байтів між спорідненими процесами).

```c
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

/* Повертає 0 і номер дитини в *out, або errno невдалого запуску. */
static int spawn(char *const argv[], pid_t *out)
{
    int pfd[2];
    if (pipe2(pfd, O_CLOEXEC) == -1)      /* обидва кінці закриються при exec */
        return errno;

    pid_t pid = fork();
    if (pid == -1) {
        int e = errno;
        close(pfd[0]);
        close(pfd[1]);
        return e;
    }

    if (pid == 0) {                       /* дитина */
        close(pfd[0]);
        execvp(argv[0], argv);            /* далі — лише гілка відмови */
        int e = errno;
        write(pfd[1], &e, sizeof e);      /* труба ще жива: заміни не сталося */
        _exit(127);
    }

    close(pfd[1]);                        /* кінець на запис лишається в дитини */

    int e = 0;
    ssize_t n = read(pfd[0], &e, sizeof e);
    close(pfd[0]);

    if (n == (ssize_t)sizeof e) {         /* дитина встигла поскаржитися */
        waitpid(pid, NULL, 0);
        return e;
    }
    *out = pid;                           /* n == 0: труба закрилася на exec */
    return 0;
}

int main(void)
{
    pid_t pid;
    int err = spawn((char *[]){ "gzip", "-9", "data.bin", NULL }, &pid);
    if (err != 0) {
        fprintf(stderr, "запуск не вдався: %s\n", strerror(err));
        return 1;
    }

    int status;
    waitpid(pid, &status, 0);
    printf("pid=%d exit=%d\n", pid, WIFEXITED(status) ? WEXITSTATUS(status) : -1);
    return 0;
}
```

Два місця тут неочевидні. `pipe2` з `O_CLOEXEC` стоїть замість пари `pipe` + `fcntl` не з любові до коротших рядків: між створенням труби й виставленням прапорця інший потік міг би зробити свою заміну образу й успадкувати кінець на запис — і тоді батько не дочекався б нуля байтів ніколи, бо труба лишалася б відкритою в сторонній програмі. А `execvp` тут ужито свідомо: у прикладі один потік, тож обмеження щодо форм із `p` не діє; у багатопотоковій програмі на цьому місці має стояти `execv` з уже знайденим шляхом.

## Сусіди, які не належать до родини

| що | підпис | коли доречно |
|---|---|---|
| `posix_spawn` | `int posix_spawn(pid_t *, const char *, const posix_spawn_file_actions_t *, const posix_spawnattr_t *, char *const [], char *const [])` | коли розгалуження надто дороге або заборонене; усе, що зазвичай роблять між `fork` і `exec`, задають структурою дій ([альтернативи розгалуженню](root:sys-unix/spawn-alternatives) — `posix_spawn`, `vfork` і `clone` та ціна кожного) |
| `system` | `int system(const char *command)` | рядок віддають оболонці; це не запуск програми, а виконання команди з усіма підстановками — джерело впровадження команд, якщо в рядку є чужі дані |
| `popen` | `FILE *popen(const char *command, const char *type)` | те саме плюс труба на потік; ті самі застереження |
| `execvP` (BSD) | `int execvP(const char *file, const char *search_path, char *const argv[])` | пошук у **заданому** списку каталогів замість `PATH`; є у FreeBSD й macOS, у Linux немає |

Перші три живуть у бібліотеці С і врешті кличуть той самий `execve` ([libc як шлюз](root:sys-unix/libc-as-gateway) — межа між тим, що вміє ядро, і тим, що добудовує бібліотека). Різниця між ними — не в можливостях, а в тому, скільки чужого коду стоїть між вашим рядком і виконаною програмою: у `execve` — нуль, у `execvp` — пошук у `PATH`, у `system` — ціла оболонка з підстановками, розбиттям на слова й розкриттям шаблонів ([розкриття й лапки](root:sys-unix/expansion-and-quoting) — що саме оболонка робить із рядком, перш ніж запустити хоч щось).
