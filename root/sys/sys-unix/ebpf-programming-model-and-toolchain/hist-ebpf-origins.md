# 📜 Історія виникнення eBPF: від фільтра BSD до JIT у ядрі

Еволюційне трансформаційне сходження механізму фільтрації пакетів від вузькоспеціалізованого інструмента сокетів BSD 1990-х років до повноцінної, безпечної віртуальної машини відкрило можливість виконувати довільний перевірений код безпосередньо в контексті ядра Linux.

---

## 1. Проблема перехоплення мережевих пакетів у 1980-х роках

На світанку розвитку комп'ютерних мереж та операційних систем Unix аналіз мережевого трафіку здійснювався шляхом копіювання кожного сирого пакета з мережевого адаптера безпосередньо у простір користувача. У операційній системі SunOS це забезпечував механізм Network Interface Tap (NIT), а в інших Unix-системах — механізм raw sockets.

Схема працювала вкрай неефективно:

```
┌─────────────────────────────────────────────────────────────┐
│                    Простір користувача                      │
│ ┌─────────────────────────────────────────────────────────┐ │
│ │ Програма аналізу трафіку (наприклад, tcpdump)           │ │
│ └───────────────────────────▲─────────────────────────────┘ │
└─────────────────────────────┼───────────────────────────────┘
                              │ Копіювання ВСІХ пакетів
                              │ (системний виклик read/recv)
┌─────────────────────────────┼───────────────────────────────┐
│ ┌───────────────────────────┴─────────────────────────────┐ │
│ │ Мережевий драйвер ядра (Network Interface Tap / NIT)     │ │
│ └───────────────────────────▲─────────────────────────────┘ │
│                             │                               │
│                     Мережевий адаптер                       │
└─────────────────────────────────────────────────────────────┘
```

Коли аналітична утиліта на кшталт `tcpdump` намагалася відфільтрувати лише пакети підтвердження DNS (UDP-порт 53), ядро операційної системи мусило передавати крізь кордон режимів привілеїв CPU (з привілейованого ring 0 у користувацький ring 3) абсолютно всі пакети, що надходили на мережеву карту. Це охоплювало гігабайти супутнього потокового HTTP-, FTP- чи SSH-трафіку. Утиліта у просторі користувача зчитувала пакет через системний виклик, перевіряла його заголовки у C-коді й у 99% випадків миттєво відкидала його як непотрібний.

Така архітектура спричиняла три фатальні категорії накладних витрат:
1. **Нерелевантні контекстні перемикання**: Тисячі переривань процесора на секунду для переходу у простір користувача ради пакетів, які не цікавили аналітичну програму.
2. **Марне копіювання пам'яті**: Заповнення L1 та L2 кешів процесора буферами пакетів, які одразу витіснялися з пам'яті без будь-якої корисної обробки.
3. **Вичерпання пропускної здатності**: При високих швидкостях мережевого каналу процесор витрачав 100% свого часу лише на копіювання пакетів у простір користувача, приносячи у жертву основні робочі процеси системи.

Потрібен був механізм, який дозволяв би відфільтровувати непотрібні пакети безпосередньо у контексті переривання ядра, ще до копіювання даних у буфери користувацького процесу.

## 2. Народження BSD Packet Filter (cBPF, 1992)

У 1992 році дослідники Стівен Маккейн (Steven McCanne) та Ван Якобсон (Van Jacobson) з Національної лабораторії імені Лоуренса в Берклі (Lawrence Berkeley Laboratory) опублікували фундаментальну працю *"The BSD Packet Filter: A New Architecture for User-level Packet Capture"*.

Вони запропонували впровадити всередину ядра Unix компактну, регістрову віртуальну машину (нова концепція отримала назву BPF — Berkeley Packet Filter).

```
┌─────────────────────────────────────────────────────────────┐
│ ┌─────────────────────────────────────────────────────────┐ │
│ │ Програма користувача (tcpdump)                          │ │
│ └───────────────────────────▲─────────────────────────────┘ │
└─────────────────────────────┼───────────────────────────────┘
                              │ Копіювання ЛИШЕ відфільтрованих
                              │ пакетів (DNS порт 53)
┌─────────────────────────────┼───────────────────────────────┐
│ ┌───────────────────────────┴─────────────────────────────┐ │
│ │ BPF Virtual Machine (In-Kernel Filter)                   │ │
│ └───────────────────────────▲─────────────────────────────┘ │
│                             │                               │
│ ┌───────────────────────────┴─────────────────────────────┐ │
│ │ Драйвер мережевого адаптера                             │ │
│ └─────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

### Архітектура та інструкції класичного BPF (cBPF)

Віртуальна машина cBPF була розроблена з розрахунком на просту інтерпретацію та максимальну швидкість обробки на 32-бітних архітектурах RISC того часу (MIPS, SPARC):

- **Акумулятор (`A`)**: 32-бітний основний регістр для виконання арифметичних і логічних операцій та збереження результатів читання з пакета.
- **Індексний регістр (`X`)**: 32-бітний додатковий регістр для збереження зміщень при адресації байтів у пакеті.
- **Пам'ять Scratch Memory**: Масив із 16 цілочисельних 32-бітних комірок пам'яті для тимчасового збереження станів між інструкціями.
- **Фіксований розмір інструкції**: Кожна інструкція складалася з 64 бітів: 16-бітного коду операції `code`, 8-бітних зміщень умовних переходів `jt` (jump true) та `jf` (jump false), і 32-бітного поля даних `k`.

Приклад інструкції cBPF для перевірки IP-протоколу:

```
[0] ld  h, [12]           ; Завантажити EtherType (байти 12-13) в регістр A
[1] jeq #0x800, 2, 0      ; Якщо EtherType == IPv4 (0x0800), перейти до [2], інакше [0] (drop)
[2] ld  b, [23]           ; Завантажити Protocol (байт 23) в регістр A
[3] jeq #0x11, 4, 0       ; Якщо Protocol == UDP (17), перейти до [4], інакше drop
[4] ret #65535            ; Прийняти весь пакет (повернути 64 КБ)
```

Користувацька програма `tcpdump` компілювала високорівневий вираз `udp port 53` у масив псевдоінструкцій cBPF і віддавала його ядру через системний виклик `setsockopt(fd, SOL_SOCKET, SO_ATTACH_FILTER, ...)` або через `ioctl`. Обробник сокета у ядрі інтерпретував цей байт-код для кожного пакета. Якщо фільтр повертав `0`, пакет миттєво відкидався без копіювання у простір користувача.

## 3. Перенесення в Linux та обмеження cBPF

У 1997 році розробник Джей Шуліст (Jay Schulist) переніс підсистему BPF у ядро Linux 2.1.75 під назвою Linux Socket Filter (LSF). Згодом Ерік Дюмазе (Eric Dumazet) у ядрі Linux 3.0 (2011 рік) створив перший JIT-компілятор для cBPF, який перекладав інструкції cBPF безпосередньо у машинний код x86.

Проте до 2013 року класичний BPF розбився об жорсткі архітектурні обмеження:

1. **Хронічна нестача регістрів**: Для складних аналітичних обчислень двох регістрів `A` та `X` бракувало. Це змушувало програмістів постійно скидати проміжні значення у розрахунковий стек (scratch memory), втрачаючи такти процесора на операції читання/запису.
2. **Невідповідність 64-бітним CPU**: cBPF розроблявся у 1990-х роках під 32-бітні процесори. На сучасних 64-бітних процесорах x86_64 та ARM64 виконання 32-бітних арифметичних операцій вимагало додаткових інструкцій розширення знаку (sign extension).
3. **Вузькоспеціалізованість під сокети**: cBPF міг обробляти виключно мережеві пакети у сокетах. Він не мав доступу до функцій ядра, не міг зчитувати трасувальні точки чи структури процесів.
4. **Відсутність глобального стану**: Програма cBPF виконувалася ізольовано для кожного пакета і не мала змоги зберігати дані між викликами (наприклад, рахувати кількість пакетів за хвилину або накопичувати статистику за IP-адресами).

## 4. Революція Alexei Starovoitov: розширений eBPF у Linux 3.18 (2014)

У 2013–2014 роках інженер Олексій Старовойтов (Alexei Starovoitov), працюючи разом із Деніелом Боркманном (Daniel Borkmann), висунув радикальну ідею: повністю переписати віртуальну машину BPF, перетворивши її з вузькоспеціалізованого мережевого фільтра на універсальну віртуальну машину ядра загального призначення.

На конференції Linux Plumbers Conference у 2013 році був презентований новий дизайн, а у грудні 2014 року у ядрі **Linux 3.18** офіційно з'явився **Extended BPF (eBPF)** (старий BPF з того моменту стали називати cBPF, Classic BPF).

Оновлена віртуальна машина eBPF мала такі кардинальні зміни:

- **11 64-бітних регістрів (`R0`–`R10`)**: Кількість і функціональне призначення регістрів були точно підгнані під конвенцію викликів (Calling Convention) апаратної архітектури x86_64 та ARM64. Це дозволило JIT-компілятору робити 1-в-1 відображення (mapping) регістрів eBPF на фізичні регістри процесора без накладних витрат.
- **Поява BPF Maps**: Ядро отримало вбудовані структури даних типу "ключ-значення" (`BPF_MAP_TYPE_HASH`, `BPF_MAP_TYPE_ARRAY`), що дозволило зберігати стан між викликами eBPF-програм і передавати дані у простір користувача.
- **Впровадження In-kernel Verifier**: Спеціальний верифікатор почав статично аналізувати байт-код перед завантаженням, гарантуючи відсутність нескінченних циклів та безпеку доступу до пам'яті ядра.
- **Розширення точок прикріплення (Hooks)**: eBPF-програми отримали можливість приєднуватися не лише до мережевих сокетів, але й до динамічних зондів `kprobes`/`uprobes`, статичних трасувальних точок `tracepoints` та швидкісного мережевого драйвера `XDP`.

Трансформація cBPF у eBPF зробила з eBPF новий "шар програмності" (programmability layer) для ядра Linux.

## 5. Заснування eBPF Foundation та сучасна екосистема

З появою бібліотеки `libbpf`, BTF (BPF Type Format) та концепції CO-RE (Compile Once – Run Everywhere) у 2019–2020 роках розробка eBPF-інструментів вийшла на масовий індустріальний рівень.

У серпні 2021 року провідні технологічні компанії — Meta, Google, Isovalent, Microsoft та Red Hat — заснували **eBPF Foundation** під парасолькою Linux Foundation. Метою фонду стала координація розвитку технології, створення стандарту BPF ISA (Instruction Set Architecture) у рамках робочої групи IETF, а також розширення застосування eBPF поза межами Linux (зокрема, створення проєкту eBPF for Windows від Microsoft).

Сьогодні eBPF став фундаментом для трьох ключових напрямків IT-інфраструктури:

1. **Мережева інфраструктура та CNI**: Проєкт Cilium повністю замінив застарілі підсистеми `iptables` та `ipvs` у Kubernetes-кластерах на eBPF, забезпечуючи нативну швидкість маршрутизації, балансування навантаження та L7-фільтрацію трафіку.
2. **Безпека та аудит у реальному часі**: Інструменти Falco та Tetragon аналізують системні виклики та поведінку ядра у режимі реального часу, миттєво блокуючи спроби підвищення привілеїв чи впровадження шкідливого коду у контейнерах.
3. **Спостережуваність (Observability) та Continuous Profiling**: Платформи Parca, Pyroscope та Pixie використовують eBPF для безперервного профілювання продуктивності процесів без зміни вихідного коду та без модифікації бінарних файлів.

Скромний фільтр пакетів BSD 1992 року еволюціонував у повноцінну інфраструктурну платформу, яка змінила спосіб взаємодії програмного забезпечення з ядром операційної системи.
