# ⚙️ Одна ехо-служба, два цикли: `epoll` і io_uring поруч

Один і той самий сервер, написаний двічі — щоб побачити рядок у рядок, що саме змінюється при переході від готовності до завершення. Виявиться, що логіка протоколу не змінюється взагалі: та сама функція розбору кадру працює в обох варіантах байт у байт. Змінюється власність на пам'ять — хто виділив буфер, коли його можна віддати й хто має право закрити дескриптор.

## Протокол і чому саме такий

Служба відповідає тим самим кадром, який отримала. Кадр — чотири байти довжини тіла в мережевому порядку, далі тіло. Заголовок тут не прикраса: без нього ехо було б «прочитав скільки дали — віддав скільки прочитав», і жодного стану в з'єднанні не існувало б. Заголовок робить часткові передачі не крайнім випадком, а буденністю — чотири байти довжини цілком можуть приїхати двома сегментами, і з'єднання мусить пам'ятати, що вже зібрало ([кадрування повідомлень у потоці TCP](topic:com-protocol/tcp-message-framing) — TCP не зберігає меж записів, тож межі кадрів доводиться нести в самих даних; довжинний заголовок — найпростіший спосіб).

Стан з'єднання виходить крихітний і однаковий для обох варіантів:

```c
#define HDR      4
#define MAXBODY  (1u << 20)     /* довжина з дроту — вхідні дані, не істина */
#define OUTMAX   (4u << 20)     /* клієнт не читає — не ростемо нескінченно */

struct conn {
    int       fd;
    uint8_t   hdr[HDR];
    unsigned  hdr_n;            /* скільки байтів заголовка вже зібрано */
    uint32_t  need;             /* скільки байтів тіла ще бракує; 0 = чекаємо заголовок */
    uint8_t  *out;              /* відповідь, що збирається й відсилається */
    size_t    out_cap, out_len, out_sent;
};
```

Розбір теж спільний. Він приймає шматок щойно прочитаних байтів — байдуже, звідки взявся той шматок, — і дописує готове до вихідного буфера. Оскільки відповідь дослівно дорівнює запиту, кадр можна вивалювати в `out` просто в міру надходження: навіть половина кадру на дроті є коректним початком відповіді.

```c
static int feed(struct conn *c, const uint8_t *p, size_t n) {
    while (n) {
        if (c->need == 0) {                              /* збираємо заголовок */
            size_t take = HDR - c->hdr_n;
            if (take > n) take = n;
            memcpy(c->hdr + c->hdr_n, p, take);
            c->hdr_n += take; p += take; n -= take;
            if (c->hdr_n < HDR) return 0;                /* заголовок ще неповний */
            uint32_t len = (uint32_t)c->hdr[0] << 24 | (uint32_t)c->hdr[1] << 16
                         | (uint32_t)c->hdr[2] <<  8 | (uint32_t)c->hdr[3];
            if (len == 0 || len > MAXBODY) return -1;    /* перевірка ДО виділення пам'яті */
            if (out_append(c, c->hdr, HDR) < 0) return -1;
            c->need = len; c->hdr_n = 0;
        }
        size_t take = c->need < n ? c->need : n;         /* тіло */
        if (out_append(c, p, take) < 0) return -1;
        c->need -= take; p += take; n -= take;
    }
    return 0;
}
```

Далі йдуть два цикли навколо цієї функції.

## Варіант перший: готовність, `epoll`

Дескриптори неблокуючі, стеження — за фронтом (`EPOLLET`), тож на кожну подію треба вичерпувати сокет до `EAGAIN`: інакше про залишок ніхто вдруге не нагадає ([неблокуючий режим](topic:sys-unix/blocking-and-nonblocking) — виклик не засинає, а відповідає `EAGAIN`, коли брати нічого; [`epoll`](topic:sys-unix/select-poll-epoll) — набір дескрипторів живе в ядрі, а `epoll_wait` повертає лише ті, на яких щось сталося).

Читання йде в **один буфер на потік**. Не на з'єднання — на потік:

```c
static _Thread_local uint8_t scratch[64 * 1024];   /* спільний для ВСІХ з'єднань цього потоку */

static void on_readable(int ep, struct conn *c) {
    for (;;) {
        ssize_t n = recv(c->fd, scratch, sizeof scratch, 0);
        if (n == 0) { drop(ep, c); return; }              /* другий бік закрив запис */
        if (n < 0) {
            if (errno == EINTR)  continue;
            if (errno == EAGAIN) break;                   /* буфер ядра вичерпано */
            drop(ep, c); return;
        }
        if (feed(c, scratch, (size_t)n) < 0) { drop(ep, c); return; }
        /* scratch вільний уже тут: усе потрібне переписане у стан з'єднання */
    }
    if (flush(ep, c) < 0) drop(ep, c);
}
```

Записом опікується `flush`. Він пхає в сокет, доки той бере, а коли ядро відмовляє — вмикає стеження за `EPOLLOUT` і йде; решту допише обробник готовності до запису.

```c
static int flush(int ep, struct conn *c) {
    while (c->out_sent < c->out_len) {
        ssize_t n = send(c->fd, c->out + c->out_sent,
                         c->out_len - c->out_sent, MSG_NOSIGNAL);
        if (n > 0) { c->out_sent += (size_t)n; continue; } /* часткова передача — норма */
        if (errno == EINTR)  continue;
        if (errno == EAGAIN) return want_write(ep, c, 1);  /* ядро більше не бере */
        return -1;
    }
    c->out_len = c->out_sent = 0;
    return want_write(ep, c, 0);
}
```

Пам'ять тут така. Транспортний буфер — спільний, 64 КіБ на потік, і його ніхто не звільняє, бо ніхто й не виділяв. Динамічний лише `out`, і живе він рівно стільки, скільки триває незакінчена відповідь: клієнт, який справно читає, залишає з'єднанню нуль байтів купи. Обіцянка «пам'ять пропорційна до активності, а не до кількості клієнтів» справджується не тому, що модель ощадлива, а тому, що ядро торкається нашої пам'яті лише зсередини `recv` і `send` — поки керування в нас, чіпати її нікому.

Помилка приходить звично: −1 і `errno`. Дескриптор закривається одним рядком у `drop()` — жодного «а раптом він ще комусь потрібен», бо розпочатої роботи не існує.

## Варіант другий: завершення, io_uring

Тут кожна дія — це замовлення в кільці подань, а відповідь на нього приїде колись у кільці завершень ([io_uring](topic:sys-unix/io-uring-rings-model) — два кільця у спільній із ядром пам'яті: подання й завершення). Замовлення треба чимось позначити, щоб упізнати його подію. Поле для цього одне — 64-бітний `user_data`, і туди кладуть покажчик на з'єднання. Тип операції ховаємо в молодших бітах: `malloc` вирівнює принаймні на вісім, тож два нижні біти покажчика завжди нульові й вільні.

```c
enum { OP_RECV = 0, OP_SEND = 1, OP_CANCEL = 2, OP_TMO = 3 };
#define TAG(c, op)  ((__u64)(uintptr_t)(c) | (op))
#define PTR(ud)     ((struct uconn *)((uintptr_t)(ud) & ~3ull))
#define OPC(ud)     ((unsigned)((ud) & 3))
```

Тепер головне правило, на якому тримається все інше. **Кожне подане замовлення бере посилання на з'єднання, кожна подія завершення його віддає; звільняти щось можна лише на нулі.** Не наприкінці обробника, не після `close`, а на нулі.

```c
struct uconn {
    struct conn  c;
    uint8_t      in[16 * 1024];   /* буфер ЦЬОГО з'єднання під подане читання */
    unsigned     refs;            /* операцій у польоті */
    int          closing;
    struct __kernel_timespec ts;  /* мусить пережити свою операцію */
};

static void arm_recv(struct io_uring *r, struct uconn *u) {
    if (u->closing) return;
    struct io_uring_sqe *sqe = io_uring_get_sqe(r);
    io_uring_prep_recv(sqe, u->c.fd, u->in, sizeof u->in, 0);
    io_uring_sqe_set_data64(sqe, TAG(u, OP_RECV));
    u->refs++;                    /* з цієї миті u->in і u->c.fd належать ядру */
}

static void arm_send(struct io_uring *r, struct uconn *u) {
    struct io_uring_sqe *sqe = io_uring_get_sqe(r);
    io_uring_prep_send(sqe, u->c.fd, u->c.out + u->c.out_sent,
                       u->c.out_len - u->c.out_sent, MSG_NOSIGNAL);
    io_uring_sqe_set_data64(sqe, TAG(u, OP_SEND));
    u->refs++;
}
```

Цикл забирає події просто з пам'яті — жодного виклику на кожну подію не потрібно:

```c
for (;;) {
    io_uring_submit_and_wait(&ring, 1);
    unsigned head, count = 0;
    struct io_uring_cqe *cqe;

    io_uring_for_each_cqe(&ring, head, cqe) {
        count++;
        struct uconn *u = PTR(cqe->user_data);
        switch (OPC(cqe->user_data)) {

        case OP_RECV:
            u->refs--;
            if (cqe->res <= 0) {                       /* 0 — закриття, <0 — це −errno */
                begin_close(&ring, u);                 /* ECONNRESET приїде як −104 */
                break;
            }
            if (feed(&u->c, u->in, (size_t)cqe->res) < 0) { begin_close(&ring, u); break; }
            if (u->c.out_len > u->c.out_sent) arm_send(&ring, u);
            else                              arm_recv(&ring, u);
            break;

        case OP_SEND:
            u->refs--;
            if (cqe->res < 0) { begin_close(&ring, u); break; }
            u->c.out_sent += (size_t)cqe->res;         /* часткова передача */
            if (u->c.out_sent < u->c.out_len) { arm_send(&ring, u); break; } /* ЗАЛИШОК */
            u->c.out_len = u->c.out_sent = 0;
            arm_recv(&ring, u);
            break;

        case OP_CANCEL: case OP_TMO:
            u->refs--;               /* −ENOENT тут нормальне: скасовувати не було чого */
            break;
        }
        if (u->refs == 0 && u->closing) reap(u);       /* єдине місце, де є free() */
    }
    io_uring_cq_advance(&ring, count);
}
```

Три зміни впадають в око одразу. Помилки більше не в `errno`, а від'ємним числом у `cqe->res`: подія народилася не в тому потоці, що її забирає, і глобальна змінна тут не мала б сенсу. Часткова передача не дочитується наступною подією, а **подається наново** — з новим зсувом і новим залишком. І буфер `in` став полем з'єднання: назвати його треба при поданні, тобто ще до того, як стане відомо, чи прийдуть дані взагалі.

Ще одна дрібниця, яку легко не помітити: `feed` викликається лише з події читання, а читання й запис у цій службі чергуються строго по черзі — жодного `send` у польоті в цю мить немає. Саме тому `out_append` вільно робить `realloc` буфера. Дозвольте собі читати й писати одночасно — і той самий `realloc` пересуне пам'ять з-під поданого запису.

## Кільце наданих буферів

Буфер на з'єднання — шістнадцять кілобайтів на кожного, хто просто підключився й мовчить. Сто тисяч тихих клієнтів обертаються півтора гігабайтами порожнечі. Лікується це тим, що буфер перестають називати при поданні: програма віддає ядру цілий пул, а ядро само бере з нього тоді, коли дані вже є.

```c
#define NBUF   2048
#define BUFSZ  (16 * 1024)
#define BGID   7

static struct io_uring_buf_ring *br;
static uint8_t *pool;
static int      br_mask;

static int setup_bufs(struct io_uring *r) {
    int err;
    br = io_uring_setup_buf_ring(r, NBUF, BGID, 0, &err);   /* NBUF — степінь двійки */
    if (!br) { errno = -err; return -1; }
    br_mask = io_uring_buf_ring_mask(NBUF);
    pool = malloc((size_t)NBUF * BUFSZ);
    for (int i = 0; i < NBUF; i++)
        io_uring_buf_ring_add(br, pool + (size_t)i * BUFSZ, BUFSZ, i, br_mask, i);
    io_uring_buf_ring_advance(br, NBUF);                    /* тепер їх бачить ядро */
    return 0;
}

static void arm_recv(struct io_uring *r, struct uconn *u) {
    if (u->closing) return;
    struct io_uring_sqe *sqe = io_uring_get_sqe(r);
    io_uring_prep_recv(sqe, u->c.fd, NULL, 0, 0);           /* адреси немає — обере ядро */
    sqe->flags     |= IOSQE_BUFFER_SELECT;
    sqe->buf_group  = BGID;
    io_uring_sqe_set_data64(sqe, TAG(u, OP_RECV));
    u->refs++;
}
```

У події з'являється третє поле, яке доводиться читати, — номер узятого буфера, у старших бітах `cqe->flags`:

```c
case OP_RECV:
    u->refs--;
    if (cqe->res == -ENOBUFS) { stall(u); break; }   /* пул порожній: тиснемо назад */
    if (cqe->res <= 0)        { begin_close(&ring, u); break; }

    int bid = cqe->flags >> IORING_CQE_BUFFER_SHIFT;
    uint8_t *data = pool + (size_t)bid * BUFSZ;
    int rc = feed(&u->c, data, (size_t)cqe->res);

    io_uring_buf_ring_add(br, data, BUFSZ, bid, br_mask, 0);  /* ПОВЕРНУТИ — завжди, */
    io_uring_buf_ring_advance(br, 1);                         /* і на шляху помилки теж */

    if (rc < 0) { begin_close(&ring, u); break; }
    ...
```

Пул на 2048 буферів — 32 МіБ незалежно від того, тисяча клієнтів чи сто тисяч, бо буфер зайнятий лише тоді, коли в ньому справді лежать дані. Ціна — новий стан відмови: коли пул вичерпано, читання завершується з `-ENOBUFS`. Це не помилка з'єднання й не привід його закривати, а сигнал, що служба не встигає споживати; правильна реакція — не подавати читання наново одразу, а зачекати на звільнення буферів.

## Скасування й таймаут

У першому варіанті таймаут на читання — це аргумент `epoll_wait` і запис у купі таймерів; скасувати очікування означає нічого не робити. У другому операція вже виконується в ядрі, тож і те, і те стає окремим замовленням.

Найдешевший таймаут — зв'язаний: читання позначається `IOSQE_IO_LINK`, а наступним подається таймер саме на нього.

```c
static void arm_recv_timed(struct io_uring *r, struct uconn *u, time_t sec) {
    struct io_uring_sqe *sqe = io_uring_get_sqe(r);
    io_uring_prep_recv(sqe, u->c.fd, u->in, sizeof u->in, 0);
    io_uring_sqe_set_data64(sqe, TAG(u, OP_RECV));
    sqe->flags |= IOSQE_IO_LINK;              /* наступний SQE — таймер ЦЬОГО читання */
    u->refs++;

    u->ts = (struct __kernel_timespec){ .tv_sec = sec };   /* поле з'єднання, не стек! */
    sqe = io_uring_get_sqe(r);
    io_uring_prep_link_timeout(sqe, &u->ts, 0);
    io_uring_sqe_set_data64(sqe, TAG(u, OP_TMO));
    u->refs++;
}
```

Подій буде дві. Спрацював таймер — він завершується з `-ETIME`, а читання слідом приходить із `-ECANCELED`. Дані встигли — читання завершується нормально, а таймер приходить із `-ECANCELED`. Обидві треба забрати й обидві зменшують лічильник посилань. Структура `ts` мусить дожити до події — це та сама вимога, що й до буфера, просто про іншу пам'ять.

Скасування без таймера — окрема операція за міткою:

```c
static void begin_close(struct io_uring *r, struct uconn *u) {
    if (u->closing) return;
    u->closing = 1;
    struct io_uring_sqe *sqe = io_uring_get_sqe(r);
    io_uring_prep_cancel64(sqe, TAG(u, OP_RECV), 0);   /* у польоті або воно, або запис: */
    io_uring_sqe_set_data64(sqe, TAG(u, OP_CANCEL));   /* запис доживе сам і теж віддасть */
    u->refs++;                       /* сама відмова теж тримає з'єднання живим */
}

static void reap(struct uconn *u) {  /* викликається ЛИШЕ при refs == 0 */
    close(u->c.fd);
    free(u->c.out);
    free(u);
}
```

## Чотири пастки, на яких ламаються переходи

**Два читання в польоті на одному дескрипторі.** Порядок завершення операцій ядро не гарантує, а другий `recv` не чекає першого. Подали двічі — і байти зберуться перемішаними, причому не завжди: під навантаженням, раз на мільйон кадрів, у місці, де протокол виглядає бездоганно. У коді вище цього не станеться за побудовою — наступне читання подається тільки з події попереднього. Хочете читати й писати одночасно — тримайте одне читання й один запис, і жодного разу по два.

**Буфер звільнено до події.** `free(u)` наприкінці обробника помилки виглядає природно й ламає все: подане читання досі живе в ядрі, і воно запише байти в пам'ять, яку вже роздав `malloc` комусь іншому. Ця ж пастка ховається в непомітнішому вигляді — `realloc` вихідного буфера під час поданого запису, автоматична змінна `struct __kernel_timespec` на стеку, локальний `iovec` для `writev`. Правило одне на всі випадки: пам'ять, названа при поданні, належить ядру до події.

**Дескриптор закрито в польоті.** Сама операція від цього не постраждає — io_uring тримає посилання на відкритий файл, а не на число. Постраждає бухгалтерія: номер звільняється негайно, `accept` видає його наступному клієнтові, і тепер два з'єднання мають один ключ. `close` у `reap()` стоїть після нуля посилань саме тому.

**Забуте повернення буфера.** Найтихіша з чотирьох. Служба працює, тримає навантаження, а через кілька годин перестає приймати дані: пул виїли шляхи помилок, на яких `io_uring_buf_ring_add` не викликали. Ознака в `strace` — рівний потік завершень з `-ENOBUFS` при живих з'єднаннях. Тому повернення буфера пишеться відразу після `feed`, до всякого розгалуження.

Ціна порядку, який цих пасток уникає, — сувора черговість: поки з'єднання відповідає, воно не читає. Знімається вона трьома окремими механізмами: багаторазове читання (`io_uring_prep_recv_multishot`, з ядра 6.0) подає одне замовлення, а події з нього приходять доти, доки в них стоїть `IORING_CQE_F_MORE`, і кожна приносить свій буфер із пулу; вихідний буфер розбивається на незмінні шматки, щоб поданий запис ніколи не бачив `realloc`; черговість там, де вона потрібна, просять явно через `IOSQE_IO_LINK`. Кожен із трьох додає стану — і кожен існує тому, що ядро тепер тримає в руках нашу пам'ять довше, ніж триває наш обробник.
