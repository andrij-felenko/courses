# 📋 Контракт вводу-виводу за сигналом: команди `fcntl`, поля `siginfo_t`, помилки

Механізм зібрано з трьох незалежних перемикачів — кому слати, чим слати, чи слати взагалі, — і кожен має власну команду `fcntl` із власним набором аргументів і помилок. Тут зібрано точні підписи, значення аргументів, склад доставленої структури й перелік того, чим ядро відповідає на неправильний виклик. Заглядати сюди доводиться тому, що промах у будь-якому з трьох перемикачів дає однакову видиму картину: усі виклики повернули нуль, а сигналів немає.

## Символи, заголовки, походження

| символ | заголовок | видно за | походження |
|---|---|---|---|
| `O_ASYNC` | `<fcntl.h>` | `_GNU_SOURCE` | 4.2BSD (там `FASYNC`), поза POSIX |
| `F_SETOWN`, `F_GETOWN` | `<fcntl.h>` | завжди | POSIX.1 |
| `F_SETOWN_EX`, `F_GETOWN_EX`, `struct f_owner_ex` | `<fcntl.h>` | `_GNU_SOURCE` | Linux, з ядра 2.6.32 |
| `F_SETSIG`, `F_GETSIG` | `<fcntl.h>` | `_GNU_SOURCE` | лише Linux |
| `POLL_IN` … `POLL_HUP` | `<signal.h>` | завжди | POSIX, коди `si_code` для `SIGPOLL` |

`_GNU_SOURCE` оголошують **до** першого `#include`: заголовок, уже розібраний без цього макроса, потрібних означень не додасть, і збірка впаде на невідомому `F_SETSIG`.

## Мінімальний повний виклик

```c
#define _GNU_SOURCE
#include <fcntl.h>
#include <signal.h>
#include <unistd.h>

#define SIG_READY  (SIGRTMIN + 1)

/* 0 — успіх, -1 з errno — ні */
int arm_fd(int fd)
{
    struct f_owner_ex own = { .type = F_OWNER_TID, .pid = gettid() };

    if (fcntl(fd, F_SETOWN_EX, &own) < 0)    return -1;   /* кому */
    if (fcntl(fd, F_SETSIG, SIG_READY) < 0)  return -1;   /* чим  */

    int fl = fcntl(fd, F_GETFL, 0);
    if (fl < 0) return -1;
    return fcntl(fd, F_SETFL, fl | O_ASYNC | O_NONBLOCK); /* чи слати */
}
```

Порядок не переставляється: `O_ASYNC` — останнім. Між двома викликами `fcntl` дані встигають прийти, і подія, що застала власника нулем, зникає безслідно.

## O_ASYNC: єдиний спосіб увімкнути

| питання | відповідь |
|---|---|
| де зберігається | у прапорцях статусу [опису відкритого файлу](root:sys-unix/open-file-description) — спільних для всіх копій дескриптора після `dup` і `fork` |
| як ставиться | тільки `fcntl(fd, F_SETFL, …)` |
| чи можна при `open` | ні: `open` приймає цей біт і мовчки його не застосовує |
| що ще змінює `F_SETFL` | лише `O_APPEND`, `O_ASYNC`, `O_DIRECT`, `O_NOATIME`, `O_NONBLOCK`; решту біт проігноровано |

`F_SETFL` записує весь набір прапорців разом, а не окремий біт. Тому значення беруть із `F_GETFL` і домальовують потрібне; інакше та сама операція знімає `O_NONBLOCK`, і дочитування до `EAGAIN` перетвориться на блокування.

## Власник події: F_SETOWN / F_GETOWN

```c
int fcntl(int fd, F_SETOWN, int arg);   /* → 0 або -1 */
int fcntl(int fd, F_GETOWN);            /* → pid, -pgid, 0 або -1 */
```

| `arg` | кого призначено |
|---|---|
| більше нуля | процес із таким pid; усередині нього сигнал дістанеться довільному потоку, який його не заблокував |
| менше нуля | групу процесів `-arg` — сигнал отримає кожен її учасник окремо |
| нуль | власника знято, події більше не породжують сигналів |
| `INT_MIN` | `EINVAL`: заперечення цього числа не має представлення в `int` |

`F_GETOWN` повертає нуль у двох різних випадках — власника не призначали або призначений процес уже завершився. Розрізнити їх цією командою неможливо; для цього є `F_GETOWN_EX`.

Один запис власника обслуговує два різні сигнали. `SIGIO` про готовність — лише за ввімкненого `O_ASYNC`; `SIGURG` про [термінові дані](root:sys-unix/out-of-band-data) на сокеті — незалежно від нього, самого `F_SETOWN` досить.

## Точне націлювання: F_SETOWN_EX / F_GETOWN_EX

```c
struct f_owner_ex {
    int   type;    /* F_OWNER_TID | F_OWNER_PID | F_OWNER_PGRP */
    pid_t pid;     /* ДОДАТНЕ число в усіх трьох випадках */
};
```

| `type` | що означає `pid` | звідки взяти число |
|---|---|---|
| `F_OWNER_TID` | окремий потік — [задача в термінах ядра](root:sys-unix/threads-as-tasks) | `gettid()` |
| `F_OWNER_PID` | процес у цілому | `getpid()` |
| `F_OWNER_PGRP` | групу процесів | `getpgrp()`, без мінуса |

Відмінність від `F_SETOWN` одна, зате принципова: знак числа більше нічого не кодує, вид власника названо явно. `F_GETOWN_EX` заповнює ту саму структуру, а для дескриптора без призначеного власника віддає `type = F_OWNER_TID` і `pid = 0`.

## Який сигнал: F_SETSIG / F_GETSIG

| `arg` для `F_SETSIG` | наслідок |
|---|---|
| нуль | типова поведінка: звичайний `SIGIO` без жодних подробиць |
| дозволений номер сигналу | цей сигнал замість `SIGIO` **і** передача заповненого `siginfo_t` |
| недозволений номер | `EINVAL` |

Сенс має лише [реальночасовий сигнал](root:sys-unix/realtime-signals) — від `SIGRTMIN` до `SIGRTMAX`. Тільки такі чергуються поштучно; звичайний сигнал зливає будь-яку кількість очікувань в одну доставку, і подробиці в ньому нема куди покласти. `F_GETSIG` повертає поточне значення, де нуль знову означає `SIGIO`.

## Що приходить у siginfo_t

Обробник, оголошений із `SA_SIGINFO` ([диспозиція сигналу](root:sys-unix/signal-disposition)), або синхронний прийом через `sigwaitinfo` дістає заповненими:

| поле | тип | вміст |
|---|---|---|
| `si_signo` | `int` | номер, заданий `F_SETSIG` |
| `si_errno` | `int` | завжди нуль |
| `si_code` | `int` | вид події: одне зі значень `POLL_*` |
| `si_fd` | `int` | дескриптор, на якому сталася подія |
| `si_band` | `long` | ті самі біти, які [`poll`](root:sys-unix/select-poll-epoll) кладе в `revents` |

`si_band` ядро складає з `si_code` за незмінною таблицею, тож нової інформації воно не несе — лише зручнішу форму для коду, який уже вміє розбирати `revents`. Перелічені біти в кожному рядку об'єднано побітовим АБО.

| `si_code` | привід | біти в `si_band` |
|---|---|---|
| `POLL_IN` | є що читати | `POLLIN`, `POLLRDNORM` |
| `POLL_OUT` | звільнилося місце для запису | `POLLOUT`, `POLLWRNORM`, `POLLWRBAND` |
| `POLL_MSG` | надійшло повідомлення | `POLLIN`, `POLLRDNORM`, `POLLMSG` |
| `POLL_ERR` | помилка на дескрипторі | `POLLERR` |
| `POLL_PRI` | термінові дані | `POLLPRI`, `POLLRDBAND` |
| `POLL_HUP` | другий бік від'єднався | `POLLHUP`, `POLLERR` |

## Кому ядро погодиться доставити

Дозвіл перевіряють так само, як для `kill`, але з важливим зсувом у часі: роль відправника грають [облікові дані](root:sys-unix/uid-gid-identity-model), запам'ятовані в мить виклику `F_SETOWN`, а не поточні.

```
доставка дозволена ⟺
       saved.euid == 0
    ∨  saved.euid == target.uid    ∨  saved.euid == target.suid
    ∨  saved.uid  == target.uid    ∨  saved.uid  == target.suid

saved  — uid і euid процесу, що викликав F_SETOWN, у мить того виклику
target — адресат доставки: процес, потік або учасник групи
```

Наслідки практичні й несиметричні. Демон, що виставив власника з-під root, а потім скинув привілеї, доставку зберігає: запам'ятовано `saved.euid == 0`. Зворотний порядок — спершу скинути привілеї, потім `F_SETOWN` — тихо лишає дескриптор без сигналів, бо відмова в правах не повертає помилки нікуди: подія просто не перетворюється на сигнал.

## Де воно взагалі працює

| тип файлу | підтримка |
|---|---|
| термінал, псевдотермінал | так — це первісний ужиток, з 4.2BSD |
| сокет | так |
| канал, іменований канал (FIFO) | так, з ядра 2.6 |
| звичайний файл, каталог | ні |

Звичайний файл не має стану «ще не готовий»: читання з нього чекає не на дані, а на диск. Сповіщати нема про що.

## Помилки

| errno | команда | причина |
|---|---|---|
| `EBADF` | будь-яка | `fd` не є відкритим дескриптором |
| `EINVAL` | `F_SETSIG` | число не є дозволеним номером сигналу |
| `EINVAL` | `F_SETOWN_EX` | `type` не є жодним із трьох дозволених значень |
| `EINVAL` | `F_SETOWN` | `arg` дорівнює `INT_MIN` |
| `ESRCH` | `F_SETOWN`, `F_SETOWN_EX` | ненульовий `pid` не відповідає наявному процесу, потоку чи групі |
| `EFAULT` | `F_SETOWN_EX`, `F_GETOWN_EX` | структура лежить поза доступним простором пам'яті |
| `ENOMEM` | `F_SETOWN*`, `F_SETSIG` | ядру забракло пам'яті на запис власника при дескрипторі |
| `EPERM` | `F_SETFL` | спроба зняти `O_APPEND` з файлу з ознакою append-only |

`ESRCH` тут відносно свіжий: перевірку аргументу додали в ядро 2017 року (латка Їржі Слабого, Jiří Slabý), а доти хибний pid мовчки скидав власника в нуль і `fcntl` рапортував успіх. На старших ядрах це найкоротший шлях до служби, яка «нічого не отримує» без жодного сліду в журналі.

## Пастки, яких не видно в підписах

**Групи в діапазоні −1…−4095.** Домовленість про системні виклики на кількох архітектурах (передусім i386) не дає відрізнити таке від'ємне повернення від коду помилки, і `F_GETOWN` для групи з такими номерами хибно виглядав як невдача. Починаючи з glibc 2.11 бібліотека реалізує `F_GETOWN` через `F_GETOWN_EX` і ваду ховає — але код, що звертається до ядра безпосередньо, її зустріне.

**Ядра 2.6.0–2.6.11.** У багатопотоковій програмі ненульовий `F_SETSIG` мовчки змінював зміст `F_SETOWN`: додатне число починало означати ідентифікатор потоку замість процесу. Цю поведінку прибрали у 2.6.12 й не повернули, лишивши натомість явний `F_SETOWN_EX`.

**`si_fd` після `dup` і `close`.** Поле несе номер, а не сам опис відкритого файлу. Якщо дескриптор продублювали, а вихідний номер закрили, у доставленому `siginfo_t` цілком може лежати вже закритий номер.

**Сигнал із власним простором `si_code`.** Для `SIGCHLD`, `SIGSEGV`, `SIGBUS`, `SIGILL`, `SIGFPE`, `SIGTRAP` і `SIGSYS` значення `si_code` вже мають інший, свій сенс, тому ядро підставляє `SI_SIGIO` і жодного `POLL_*` програма не побачить. Ще один доказ, що вибирати треба з реальночасового діапазону.

**Переповнення черги.** Кількість реальночасових сигналів в очікуванні обмежує [`RLIMIT_SIGPENDING`](root:sys-unix/resource-limits). Коли ліміт вичерпано, ядро надсилає натомість звичайний `SIGIO` — і той проходить як привілейований, повз ліміт черги, зате без `si_fd` і без `si_band`. Адреси події в ньому немає, тож єдина коректна відповідь — обійти всі дескриптори наново.
