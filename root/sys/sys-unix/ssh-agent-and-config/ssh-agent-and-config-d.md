## Нестерпна плата за надійні парольні фрази

Адміністратор підтримує пів сотні серверів: кластери баз даних у закритому периметрі, балансувальники навантаження, середовища безперервної інтеграції та тестові стенди. Кожен закритий ключ стандарту Ed25519 на локальній робочій станції зашифровано стійкою парольною фразою на 24 символи з використанням функції формування ключа bcrypt (KDF). Коли сценарій автоматизації або утиліта керування конфігураціями виконує опитування вузлів кожні п'ять хвилин, система вимагає ручного введення парольної фрази тридцять разів на годину.

У такій ситуації виникає психологічна втома від постійної автентифікації. Найпростіший шлях позбутися незручності — зняти парольну фразу за допомогою команди `ssh-keygen -p` і залишити закритий ключ у відкритому вигляді прямо у файлі `~/.ssh/id_ed25519`.

Цей крок ліквідує запити введення, але створює критичну загрозу безпеці. Закритий ключ у незашифрованому вигляді стає доступним будь-якому процесу з тим самим UID користувача. Випадкове створення резервної копії, потрапляння файлу до публічного сховища, помилка в скрипті резервування або локальна вразливість у браузері миттєво віддають незахищений криптографічний секрет зловмиснику. Щоб зберегти закритий ключ зашифрованим на диску й водночас не вводити пароль перед кожним системним викликом, розробники OpenSSH розділили процедуру зберігання секрету та операцію накладання цифрового підпису, винісши останню в окремий системний процес — `ssh-agent`.

## Чому розшифрування виноситься в окремий процес-демон

Якщо клієнт `ssh` сам зчитуватиме зашифрований файл ключа з диска, запитуватиме парольну фразу й триматиме розшифрований бінарний секрет у своїй пам'яті, цей секрет знищиться разом із завершенням процесу після закриття сеансу. Наступний виклик `ssh` чи `scp` буде новим процесом з окремим адресним простором, якому знову знадобиться читання з диска та інтерактивне опитування користувача.

Зберегти стан розшифрованого ключа між окремими запусками клієнтів можна лише в довгоживучому фоновому процесі. Цим процесом є демон `ssh-agent`.

```
        +-------------------------------------------------------------+
        |                 Робоча станція користувача                  |
        |                                                             |
        |  [Диск] ~/.ssh/id_ed25519 (Зашифровано парольною фразою)    |
        |                         |                                   |
        |                  (ssh-add запитує пароль 1 раз)             |
        |                         v                                   |
        |   +-----------------------------------------------------+   |
        |   | Демон ssh-agent (Окремий адресний простір)          |   |
        |   |  - Розшифрований закритий ключ у RAM                |   |
        |   |  - Системний захист: mlock() та MADV_DONTDUMP       |   |
        |   |  - Автоматичне вивантаження за таймером (-t 1h)     |   |
        |   +-----------------------------------------------------+   |
        |                         ^                                   |
        |           UNIX Socket   | (Запит підпису: challenge)        |
        |         $SSH_AUTH_SOCK  | (Відповідь: готовий signature)   |
        |                         v                                   |
        |     [Клієнт 1: ssh]          [Клієнт 2: git]                |
        |     (Не знає ключа)          (Не знає ключа)                |
        +-------------------------------------------------------------+
```

Демон `ssh-agent` завантажує закритий ключ в оперативну пам'ять один раз, розшифровує його за допомогою введеної людиною парольної фрази й утримує в оперативній пам'яті. Жоден клієнтський процес — ані `ssh`, ані `git`, ані `rsync` — більше ніколи не торкається файлу закритого ключа на диску й не знає парольної фрази.

### Захист пам'яті агента на рівні ядра Linux

Утримання розшифрованих приватних ключів у відкритому вигляді в пам'яті створює додаткові вектори атак. Якщо операційна система вичерпує фізичну пам'ять RAM, сторінки пам'яті процесу `ssh-agent` можуть бути вивантажені ядром у swap-розділ або swap-файл на накопичувачі NVMe чи SSD. У такому разі розшифрований ключ знову опиняється на фізичному носії у відкритому вигляді. Крім того, у разі аварійного падіння демона ядро може сформувати дамп пам'яті (core dump) у файловій системі.

Для запобігання цим загрозам `ssh-agent` застосовує низку системних викликів ядра Linux:
1. **Блокування сторінок через `mlock()`:** Демон фіксує виділені буфери з ключами у фізичній пам'яті, забороняючи підсистемі керування віртуальною пам'яттю переміщати їх у простір підкачки (swap).
2. **Заборона дампів через `madvise(..., MADV_DONTDUMP)`:** Сторінки оперативної пам'яті, що містять ключові структури, позначаються прапорцем виключення з будь-яких файлів core dump у разі отримання сигналів `SIGSEGV` чи `SIGABRT`.
3. **Занулення буферів (Zeroization):** Після завершення використання пам'яті або після закінчення таймауту демон перезаписує ділянки нулями за допомогою функцій типу `explicit_bzero()`, що гарантує відсутність оптимізацій компілятора, які могли б проігнорувати очищення незчитуваної пам'яті.

## Анатомія взаємодії через локальний сокет $SSH_AUTH_SOCK

Комунікація між клієнтом `ssh` і фоновим демоном `ssh-agent` здійснюється через локальний потоковий сокет домену UNIX (`AF_UNIX`, `SOCK_STREAM`). На відміну від мережевих сокетів TCP, сокет домену UNIX не виходить за межі ядра поточної машини й використовує стандартну модель прав доступу файлової системи POSIX.

### Запуск і змінні оточення

Під час ручного запуску через оболонку виконується команда:

```bash
eval $(ssh-agent -s)
```

Команда `ssh-agent -s` генерує на стандартний вивід команди експорту для поточної оболонки:

```bash
SSH_AUTH_SOCK=/tmp/ssh-XXXXXXaBcDeF/agent.14205; export SSH_AUTH_SOCK;
SSH_AGENT_PID=14206; export SSH_AGENT_PID;
echo Agent pid 14206;
```

Змінна середовища оточення `SSH_AUTH_SOCK` містить абсолютний шлях до файлової точки входу сокета. Каталог у `/tmp/` створюється з правами `0700` (`drwx------`) і належить виключно поточному UID користувача. Будь-який інший непривілейований локальний користувач, що спробує отримати доступ до сокета, отримає відмову `EACCES` на рівні системного виклику `connect()` ще до передачі першого байта.

У сучасних дистрибутивах Linux з ініціалізацією `systemd` демон агента часто запускається як системний користувацький юніт (`systemd --user`), а сокет розміщується у виділеному просторі `XDG_RUNTIME_DIR`:

```bash
/run/user/1000/openssh_agent
```

### Протокол взаємодії (Challenge-Response Workflow)

Клієнт SSH ніколи не запитує сам закритий ключ у демона, а демон ніколи не надсилає приватні байти клієнту. Спілкування побудоване за схемою запиту цифрового підпису:

![Взаємодія клієнта SSH та ssh-agent через локальний UNIX-сокет](/root/sys/sys-unix/ssh-agent-and-config/img/ssh-agent-protocol.svg)
*Клієнт SSH не зчитує закритий ключ: віддалений сервер надсилає виклик, клієнт ретранслює його через сокет до $SSH_AUTH_SOCK, а демон ssh-agent накладає цифровий підпис усередині захищеної оперативної пам'яті.*

Послідовність кроків автентифікації виглядає так:

1. **Запит списку ключів:** Клієнт надсилає в сокет `$SSH_AUTH_SOCK` повідомлення `SSH_AGENTC_REQUEST_IDENTITIES` (числовий код `11`).
2. **Відповідь агента:** Агент повертає `SSH_AGENT_IDENTITIES_ANSWER` (код `12`), де перераховано масив блобів відкритих ключів (наприклад, відкритий ключ Ed25519 довжиною 32 байти) разом із текстовими коментарями.
3. **Пропозиція сервера:** Клієнт передає віддаленому серверу `sshd` відкритий ключ: *«Я маю ключ із цим відбитком, чи дозволено мені вхід?»*.
4. **Виклик сервера (Challenge):** Сервер перевіряє свій файл `~/.ssh/authorized_keys`. Якщо відкритий ключ знайдено, сервер генерує випадковий криптографічний виклик (Challenge), що включає ідентифікатор поточного сеансу SSH (Session ID), і відправляє його клієнту.
5. **Делегування підпису агенту:** Клієнт пакує отриманий виклик і відкритий ключ у бінарне повідомлення `SSH_AGENTC_SIGN_REQUEST` (код `13`) і надсилає його в сокет `$SSH_AUTH_SOCK`.
6. **Обчислення підпису:** Демон `ssh-agent` знаходить у своїй захищеній оперативній пам'яті закритий ключ, що відповідає наданому публічному блобу, накладає цифровий підпис на дані виклику й повертає клієнту відповідь `SSH_AGENT_SIGN_RESPONSE` (код `14`), що містить готовий підпис.
7. **Фінал автентифікації:** Клієнт надсилає отриманий підпис віддаленому `sshd`. Сервер перевіряє підпис відкритим ключем і відкриває сеанс.

Детальний двійковий формат полів, коди команд та структури кадру протоколу викладено в [довідці команд та протоколу агента](root:sys-unix/ssh-agent-and-config/api-ssh-config-and-agent.md), а робочу низькорівневу реалізацію клієнта сокета розібрано в [практичному проекті клієнта агента](root:sys-unix/ssh-agent-and-config/proj-ssh-agent-signer.md).

## Керування життєвим циклом ключів і фатальні ризики ForwardAgent

За замовчуванням ключ, завантажений в агент командою `ssh-add`, залишається в пам'яті доти, доки працює процес демона або машина не буде вимкнена. Це створює вікно вразливості: якщо користувач залишає робочу станцію розблокованою, будь-який локальний скрипт або фізичний зловмисник може виконувати підписи через доступний сокет.

### Обмеження часу життя ключа (`-t`)

Для мінімізації часу перебування секрету в пам'яті `ssh-add` підтримує прапорець таймауту життя `-t`:

```bash
# Ключ автоматично вивантажиться з пам'яті через 1 годину (3600 секунд)
ssh-add -t 1h ~/.ssh/id_ed25519

# Завантаження ключа на робочий день (8 годин)
ssh-add -t 8h ~/.ssh/id_ed25519
```

Після закінчення таймера демон `ssh-agent` занулює структури пам'яті з приватними даними й вивільняє їх. Наступні спроби підпису повертатимуть помилку `SSH_AGENT_FAILURE`, змушуючи користувача повторно ввести парольну фразу.

### Ручне підтвердження кожного підпису (`-c`)

Найвищий рівень локальної безпеки забезпечує прапорець `-c` (confirmation):

```bash
ssh-add -c ~/.ssh/id_ed25519
```

Коли ключ позначено цим обмеженням, агент не виконує жодної операції підпису без явної згоди людини. У мить, коли клієнт звертається до агента з викликом `SSH_AGENTC_SIGN_REQUEST`, демон призупиняє обробку сокета, викликає зовнішню допоміжну утиліту `SSH_ASKPASS` (наприклад, графічне вікно `ssh-askpass` чи діалог оточення GNOME/KDE) і виводить запит: *«Allow use of key ~/.ssh/id_ed25519?»*.

Якщо користувач не натисне кнопку підтвердження особисто, агент відхиляє запит. Це робить неможливою приховану автентифікацію у фоні зловмисним програмним забезпеченням.

### Анатомія атаки через пересилання агента (`ForwardAgent yes`)

Опція `ForwardAgent yes` (або прапорець `ssh -A`) історично використовувалася для розв'язання проблеми доступу до сторонніх репозиторіїв чи наступних серверів із проміжної машини.

```bash
# Небезпечний виклик
ssh -A devops@bastion.example.com
```

Коли активовано пересилання агента, віддалений сервер `sshd` створює на своєму боці проксі-сокет домену UNIX (наприклад, `/tmp/ssh-a1b2c3/agent.54321`) і прописує шлях до нього у змінну оточення `$SSH_AUTH_SOCK` віддаленого сеансу. Будь-який запит на підпис, що надходить у цей віддалений сокет, демон `sshd` шифрує, пересилає через існуючий SSH-канал назад на локальну машину користувача й передає локальному `ssh-agent`.

```
[Локальна машина]                             [Скомпрометований сервер]
Локальний ssh-agent                            Віддалений сокет /tmp/ssh-XX/agent.PID
       ^                                                    ^
       |                                                    |
       +===== Шифрований тунель SSH (ForwardAgent yes) =====+
                                                            |
                                        [Зловмисник із правами root]
                                        Підключається до /tmp/ssh-XX/agent.PID
                                        і підписує запити до ДОВІЛЬНИХ інших серверів!
```

Небезпека полягає в тому, що на віддаленій машині користувач `root` (або процес зловмисника, що отримав права суперкористувача через локальну вразливість ядра) має необмежений доступ до файлової системи, включно з каталогом `/tmp/ssh-*`.

Зловмисник на віддаленому сервері просто зчитує змінну `$SSH_AUTH_SOCK` процесу користувача:

```bash
# Атакуючий підключається до чужого прокинутого сокета
export SSH_AUTH_SOCK=/tmp/ssh-a1b2c3/agent.54321
ssh admin@production-database.internal
```

Доки користувач тримає відкритим SSH-сеанс із бастіоном чи сервером розробки, зловмисник може виконувати автентифікацію на будь-якому іншому сервері інфраструктури, до якого має доступ жертва. Закритий ключ при цьому не викрадається, але зловмиснику це й не потрібно: він отримує повноцінний криптографічний оракул підпису.

Саме тому `ForwardAgent` суворо заборонено вмикати глобально в конфігурації `Host *`. Для переходу через проміжні вузли стандарт вимагає використання наскрізного тунелювання `ProxyJump`.

## Декларативна конфігурація клієнта: структура ~/.ssh/config

Ручне введення параметрів у командному рядку (`ssh -i ~/.ssh/id_ed25519_custom -p 2222 user@10.0.1.50`) не масштабується. Конфігураційний файл `~/.ssh/config` дозволяє декларативно описати параметри доступу для сотень машин, використовуючи псевдоніми та шаблони зіставлення.

### Семантика першого збігу та побудова блоків

Парсер OpenSSH оцінює файл згори вниз. Якщо значення для певної директиви вже встановлено попереднім блоком `Host`, наступні блоки не можуть його перезаписати.

```
# 1. Точковий хост із нестандартним портом та окремим користувачем
Host db-primary
    HostName db01.prod.internal
    User postgres
    Port 54322
    IdentityFile ~/.ssh/id_ed25519_postgres

# 2. Груповий шаблон для всіх серверів продакшену
Host *.prod.internal prod-*
    User devops
    IdentityFile ~/.ssh/id_ed25519_prod
    IdentitiesOnly yes

# 3. Базові налаштування для ВСІХ хостів — обов'язково в самому кінці
Host *
    AddKeysToAgent yes
    IdentitiesOnly yes
    ServerAliveInterval 30
    ServerAliveCountMax 3
```

Якщо виконати `ssh db-primary`:
1. Перший блок `Host db-primary` зіставляється першим: фіксуються `HostName = db01.prod.internal`, `User = postgres`, `Port = 54322`, `IdentityFile = ~/.ssh/id_ed25519_postgres`.
2. Другий блок `Host *.prod.internal` також зіставляється (оскільки `HostName` дорівнює `db01.prod.internal`), але директива `User` ігнорується, бо значення `postgres` уже закріплене. Директива `IdentityFile` додається до списку дозволених ключів, а `IdentitiesOnly` фіксується як `yes`.
3. Фінальний блок `Host *` заповнює невизначені директиви: `AddKeysToAgent`, `ServerAliveInterval` та `ServerAliveCountMax`.

### Проблема вичерпання спроб: «Too many authentication failures»

Типова поведінка OpenSSH-клієнта за замовчуванням: звернутися до `ssh-agent` і запропонувати серверу **всі** наявні в пам'яті відкриті ключі по черзі.

Якщо розробник має в агенті 6 ключів (особистий GitHub, корпоративний GitLab, ключ тестового кластера, ключ продакшену, ключ VPN, ключ бекап-сервера), а віддалений сервер `sshd` має в конфігурації директиву `MaxAuthTries 3` (або стандартне значення `6`), відбувається збій. Клієнт пропонує перші три невідповідні ключі, вичерпує ліміт спроб і сервер розриває з'єднання з фатальною помилкою:

```
Received disconnect from 192.168.1.50 port 22:2: Too many authentication failures
Disconnected from 192.168.1.50 port 22
```

Потрібний ключ так і не був спробуваний.

Розв'язанням цієї проблеми є обов'язкове використання пари директив:

```
Host prod-node
    HostName 10.0.2.10
    IdentityFile ~/.ssh/id_ed25519_specific
    IdentitiesOnly yes
```

Директива `IdentitiesOnly yes` наказує клієнту: *«Використовувати з агента ТІЛЬКИ той ключ, публічна частина якого явно збігається з файлом `~/.ssh/id_ed25519_specific`, ігноруючи решту завантажених ключів»*.

### Автоматичне ліниве завантаження: `AddKeysToAgent yes`

Замість ручного виклику `ssh-add` після кожного перезавантаження робочої станції, директива `AddKeysToAgent yes` активує автоматичне додавання:

```
Host *
    AddKeysToAgent yes
    IdentityFile ~/.ssh/id_ed25519
```

Під час першого виклику `ssh` клієнт бачить, що ключа ще немає в агенті, запитує парольну фразу один раз, виконує автентифікацію та самостійно надсилає розшифрований ключ у сокет `$SSH_AUTH_SOCK`. Усі наступні підключення беруть готовий підпис з агента без жодних запитів.

## Проходження через бастіони: механіка ProxyJump проти застарілого ProxyCommand

У сучасній архітектурі безпеки сервери баз даних та внутрішні мікросервіси не мають публічних IP-адрес. Вони розташовані в ізольованій підмережі (наприклад, `10.0.1.0/24`) і доступні виключно через проміжний вузол — сервер-бастіон (Jump Host), що має один зовнішній мережевий інтерфейс і один внутрішній.

### Застарілий підхід: `ProxyCommand` і зовнішні процеси

До появи OpenSSH 7.3 стандартним способом переходу через проміжну машину було використання директиви `ProxyCommand` у поєднанні з утилітою `netcat` (`nc`) або вкладеним викликом `ssh -W`:

```
# Застарілий конфіг через netcat
Host target-old
    HostName 10.0.1.50
    ProxyCommand ssh devops@bastion.example.com nc %h %p

# Застарілий конфіг через вкладений клієнт ssh -W
Host target-old-w
    HostName 10.0.1.50
    ProxyCommand ssh -W %h:%p devops@bastion.example.com
```

Механіка роботи `ProxyCommand`:
1. Головний клієнт `ssh` викликає системний виклик `fork()` і породжує дочірній процес командної оболонки.
2. Оболонка запускає окрему бінарну програму `ssh` або `nc`.
3. Дочірня програма встановлює з'єднання з бастіоном і перенаправляє весь свій стандартний ввід і вивід (`stdin`/`stdout`) через анонімні канали `pipe()` головному процесу `ssh`.
4. Головний клієнт трактує дескриптор каналу як віртуальний мережевий сокет.

Цей підхід створює надмірні системні накладні витрати: створення зайвих процесів на кожен виклик, передача кожного байта через буфери двох конвеєрів `pipe` ядра Linux, ускладнена обробка сигналів переривання (`SIGINT`) та зависання зомбі-процесів у разі розриву з'єднання.

### Сучасний стандарт: `ProxyJump` та канал `direct-tcpip`

Директива `ProxyJump` (або командний ключ `ssh -J`) реалізована всередині одного процесу клієнта OpenSSH за допомогою стандартного механізму мультиплексування каналів протоколу SSH:

```
Host bastion
    HostName bastion.corp.net
    User devops
    IdentityFile ~/.ssh/id_ed25519_bastion

Host internal-db
    HostName 10.0.1.50
    User postgres
    ProxyJump bastion
    IdentityFile ~/.ssh/id_ed25519_db
```

Команда запуску:

```bash
ssh internal-db
# Еквівалентно в CLI:
ssh -J devops@bastion.corp.net:22 postgres@10.0.1.50
```

![Наскрізний тунель ProxyJump через бастіон](/root/sys/sys-unix/ssh-agent-and-config/img/proxyjump-tunnel.svg)
*Архітектура ProxyJump: бастіон відкриває TCP-з'єднання через внутрішній канал direct-tcpip і прозоро передає байти, тоді як наскрізне шифрування та автентифікація виконуються безпосередньо між клієнтом і кінцевим сервером.*

### Низькорівнева послідовність встановлення тунелю ProxyJump

1. **Зовнішній сеанс до бастіону:** Клієнт відкриває стандартне TCP-з'єднання на `bastion.corp.net:22`, проходить перевірку відбитка хоста в `known_hosts`, автентифікується ключем `id_ed25519_bastion` і піднімає зашифрований транспортний сеанс.
2. **Запит каналу `direct-tcpip`:** Замість запиту командної оболонки (Shell або PTY) клієнт надсилає в шифрований сеанс бастіону канальний запит `SSH_MSG_CHANNEL_OPEN` типу `direct-tcpip`. У тілі запиту клієнт передає цільову IP-адресу `10.0.1.50` та порт `22`.
3. **З'єднання на боці бастіону:** Демон `sshd` на бастіоні викликає стандартний системний виклик `connect()` до сокета `10.0.1.50:22`. Якщо з'єднання успішне, бастіон повертає клієнту повідомлення `SSH_MSG_CHANNEL_OPEN_CONFIRMATION`.
4. **Прозоре мостування:** Бастіон стає простим побайтовим ретранслятором: усе, що надходить у виділений канал SSH від клієнта, записується в TCP-сокет до цільового сервера, і навпаки. Бастіон **не бере участі** в розшифруванні наступного рівня.
5. **Внутрішній наскрізний сеанс (End-to-End Encryption):** Клієнт розпочинає друге, повністю незалежне рукостискання SSH безпосередньо крізь відкритий потік байтів:
   - Виконується новий обмін ключами Diffie-Hellman із сервером `10.0.1.50`.
   - Звіряється відбиток цільового сервера `10.0.1.50` у локальному файлі `~/.ssh/known_hosts` клієнта.
   - Виконується автентифікація ключем `id_ed25519_db`.
   - Генеруються окремі симетричні ключі шифрування (ChaCha20-Poly1305 або AES-GCM).

### Чому ProxyJump забезпечує абсолютну ізоляцію

Навіть якщо сервер-бастіон повністю скомпрометовано зловмисником із привілеями `root`, безпека внутрішнього цільового сервера не порушується:
- Бастіон бачить виключно зашифрований шифротекст внутрішнього сеансу SSH.
- Бастіон не має доступу до приватного ключа `id_ed25519_db`.
- Бастіон не може модифікувати трафік або виконати атаку Man-in-the-Middle, оскільки не може підробити цифровий підпис цільового сервера під час обміну ключами Diffie-Hellman.
- Ключі автентифікації передаються з клієнтської машини, тому на самому бастіоні взагалі не зберігаються жодні приватні сертифікати чи ключі до внутрішньої інфраструктури.

### Каскадні стрибки через кілька бастіонів

Якщо цільовий контур вимагає проходження зовнішнього периметра, а потім внутрішнього шлюзу безпеки, `ProxyJump` підтримує послідовні ланцюжки переходів через кому:

```
Host secure-node
    HostName 172.16.0.42
    ProxyJump bastion-dmz,bastion-core
```

Клієнт спочатку встановить сеанс із `bastion-dmz`, крізь нього відкриє `direct-tcpip` до `bastion-core`, підніме в ньому другий сеанс SSH, запитає з нього другий канал `direct-tcpip` до `172.16.0.42` і встановити наскрізне з'єднання.

## Мультиплексування з'єднань OpenSSH (ControlMaster)

Встановлення нового з'єднання SSH є ресурсомісткою процедурою:
1. Трьохетапне рукостискання TCP (SYN, SYN-ACK, ACK) — 1 RTT.
2. Узгодження версій протоколу та обмін списками підтримуваних алгоритмів (`SSH2_MSG_KEXINIT`) — 1 RTT.
3. Обмін ключами на еліптичних кривих (Diffie-Hellman Key Exchange) та верифікація хоста — 1–2 RTT.
4. Процедура автентифікації користувача (перевірка підпису відкритого ключа) — 1–2 RTT.
5. Відкриття сеансового каналу (`session`) та виділення PTY — 1 RTT.

Якщо мережева затримка до віддаленого сервера становить 50 мс (RTT), кожен новий запуск команди `ssh` витрачає від 250 до 400 мілісекунд суто на встановлення зв'язку ще до передачі першого байта корисних даних. Під час виконання автоматизацій Ansible (яка відкриває сотні з'єднань для виконання дрібних модулів) або частих операцій `git fetch` цей час становить понад 80% загальної тривалості роботи.

### Механізм ControlMaster і ControlPath

Мультиплексування OpenSSH дозволяє відкрити повноцінне з'єднання один раз, а всі наступні сеанси запускати як паралельні логічні канали всередині вже існуючого зашифрованого TCP-тунелю.

```
Host *
    ControlMaster auto
    ControlPath ~/.ssh/sockets/%r@%h:%p
    ControlPersist 10m
```

![Мультиплексування з'єднань через ControlMaster і локальний сокет керування](/root/sys/sys-unix/ssh-agent-and-config/img/connection-multiplexing.svg)
*ControlMaster використовує спільне TCP-підключення: первинний процес утримує зашифрований тунель, а наступні утиліти миттєво підключаються через локальний сокет без повторного проходження фази рукостискання й автентифікації.*

### Як працює механіка Master/Slave

1. **Перший запуск (`Master`):**
   - Користувач запускає `ssh devops@server.internal`.
   - Завдяки `ControlMaster auto` клієнт перевіряє, чи існує сокет керування за шляхом `~/.ssh/sockets/devops@server.internal:22`.
   - Сокета немає: поточний процес стає **Майстром** (Master). Він виконує повне рукостискання TCP/SSH, автентифікується, створює каталог `~/.ssh/sockets/` і прив'язує локальний UNIX-сокет домену `ControlPath`.
2. **Паралельні виклики (`Slave`):**
   - У сусідній вкладці термінала виконується `git push` або `ssh devops@server.internal uptime`.
   - Клієнт бачить наявний файл сокета `ControlPath`, викликає `connect()` до локального сокета й надсилає запит на відкриття нового SSH-каналу.
   - Процес Master отримує запит, відкриває новий мультиплексований канал всередині вже встановленого TCP-з'єднання й передає файлові дескриптори вводу-виводу slave-клієнту.
   - Час підключення скорочується з 300 мс до **2–4 мс** (час локального міжпроцесного виклику).
3. **Фонове утримання (`ControlPersist 10m`):**
   - Користувач закриває первинний інтерактивний термінал командою `exit`.
   - Замість розриву TCP-з'єднання з сервером процес Master відв'язується від керуючого термінала (TTY), переходить у фоновий режим демона й утримує відкритий сокет ще протягом 10 хвилин.
   - Якщо протягом 10 хвилин запускається нова команда, таймер скидається. Якщо активність відсутня — Master коректно закриває з'єднання з сервером і видаляє файл сокета.

### Обмеження довжини шляху UNIX-сокета та токен `%C`

У ядрі Linux структура адреси сокета домену UNIX `sockaddr_un` має фіксований розмір буфера шляху `sun_path`, що за стандартом POSIX становить лише **108 байтів**:

```text
struct sockaddr_un {
    sa_family_t sun_family; /* AF_UNIX */
    char sun_path[108];      /* Шлях до файлу сокета */
};
```

Якщо шлях користувача містить довгі імена (`/home/verylongusername/.ssh/sockets/user@very-long-domain-name-production-database.internal:2222`), довжина рядка перевищує 108 байтів, і системний виклик `bind()` завершується помилкою `ENAMETOOLONG`.

Для запобігання цьому OpenSSH пропонує спеціальний токен хешування `%C`:

```
Host *
    ControlPath ~/.ssh/S-%C
```

Токен `%C` генерує детермінований 40-символьний хеш SHA1 від конкатенації рядків хоста, порту, користувача та локальної машини (`%l%h%p%r`), гарантуючи, що довжина шляху ніколи не вийде за межі ліміту операційної системи.

### Керування активним Master-процесом

Для перевірки стану, примусового перезапуску або закриття мультиплексованого з'єднання використовується прапорець `-O`:

```bash
# Перевірити, чи активний Master процес для вказаного хоста
ssh -O check devops@server.internal
# Відповідь: Master running (pid=45120)

# Заборонити прийом нових slave-сесій, але дозволити активним завершити роботу
ssh -O stop devops@server.internal

# Негайно розірвати всі активні канали та закрити TCP-з'єднання
ssh -O exit devops@server.internal
```

## Діагностика, налагодження та простеження з'єднань

Коли автентифікація або тунелювання поводиться неочікувано, найшвидший спосіб знайти причину — підвищити рівень деталізації журналу клієнта прапорцями `-v`, `-vv` або `-vvv`.

### Аналіз журналу автентифікації через агента

Команда `ssh -vvv target-server` виводить повний протокол узгодження:

```
debug1: Authentications that can continue: publickey,password
debug1: Next authentication method: publickey
debug1: Offering public key: /home/user/.ssh/id_ed25519 ED25519 SHA256:abc... explicit
debug3: send packet: type 50
debug2: we sent a publickey packet, wait for reply
debug3: receive packet: type 60
debug1: Server accepts key: /home/user/.ssh/id_ed25519 ED25519 SHA256:abc... explicit
debug3: sign_and_send_pubkey: using agent-provided signature
debug3: send packet: type 50
debug3: receive packet: type 52
debug1: Authentication succeeded (publickey).
```

У наведеному фрагменті:
- Пакет `type 50` (`SSH2_MSG_USERAUTH_REQUEST`) надсилає серверу відкритий ключ для попередньої перевірки.
- Пакет `type 60` (`SSH2_MSG_USERAUTH_PK_OK`) підтверджує, що ключ є у файлі `authorized_keys`.
- Рядок `sign_and_send_pubkey: using agent-provided signature` свідчить про те, що клієнт звернувся до сокета `$SSH_AUTH_SOCK`, отримав підпис від агента й відправив його серверу.
- Пакет `type 52` (`SSH2_MSG_USERAUTH_SUCCESS`) сигналізує про успішний вхід.

### Діагностика збоїв ProxyJump та завислих сокетів ControlMaster

Якщо цільовий сервер за бастіоном недоступний, налагоджувальний журнал показує точну ланку відмови:

```
debug1: Setting up multiplexed connection to 10.0.1.50:22 via bastion.corp.net:22
debug1: channel 0: new [direct-tcpip]
debug1: channel 0: open confirm rwindow 2097152 rmax 32768
```

Якщо в журналі з'являється `channel 0: open failed: connect failed: Connection refused`, це означає, що зв'язок із бастіоном успішний, але сам бастіон не може підключитися до внутрішнього порту 22 цільового сервера (наприклад, служба `sshd` зупинена або фаєрвол блокує підмережу).

У разі раптового збою живлення робочої станції або аварійного закриття термінала файл сокета `ControlPath` може залишитися на диску, хоча процес Master уже не існує. Під час наступного запуску OpenSSH помічає, що системний виклик `connect()` до сокета повертає помилку `ECONNREFUSED` («Connection refused»), автоматично видаляє мертвий файл сокета й безшовно створює новий процес Master, не вимагаючи ручного втручання від користувача.

## Зведена еталонна конфігурація та правила безпеки

Нижче наведено зразок файлу `~/.ssh/config`, у якому об'єднано розібрані практики ізоляції, швидкого доступу через бастіони та мультиплексування:

```
# ==============================================================================
# 1. СПЕЦИФІЧНІ ХОСТИ ТА ПЕРЕЛІК ПСЕВДОНІМІВ
# ==============================================================================

# Зовнішній бастіон інфраструктури
Host bastion
    HostName bastion.corp.example.com
    User gatekeeper
    Port 22022
    IdentityFile ~/.ssh/id_ed25519_bastion
    IdentitiesOnly yes

# Внутрішня база даних (доступ лише через бастіон)
Host prod-db
    HostName 10.0.4.100
    User postgres
    ProxyJump bastion
    IdentityFile ~/.ssh/id_ed25519_db
    IdentitiesOnly yes

# Кластер внутрішніх мікросервісів
Host k8s-*
    ProxyJump bastion
    User clusteradmin
    IdentityFile ~/.ssh/id_ed25519_k8s
    IdentitiesOnly yes

# ==============================================================================
# 2. ГЛОБАЛЬНІ ПРАВИЛА БЕЗПЕКИ ТА ШВИДКОДІЇ ДЛЯ ВСІХ ХОСТІВ
# ==============================================================================
Host *
    # Безпека: ніколи не пересилати агент за замовчуванням
    ForwardAgent no

    # Автоматичне завантаження розшифрованих ключів в ssh-agent при першому вході
    AddKeysToAgent yes

    # Запобігання "Too many authentication failures"
    IdentitiesOnly yes

    # Мультиплексування з'єднань: миттєвий вхід без повторних рукостискань
    ControlMaster auto
    ControlPath ~/.ssh/S-%C
    ControlPersist 15m

    # Підтримка зв'язку через фаєрволи та NAT (надсилання ping кожні 30 секунд)
    ServerAliveInterval 30
    ServerAliveCountMax 3

    # Суворе збереження нових ключів хостів без блокування
    StrictHostKeyChecking accept-new
```

### Підсумкові правила гігієни SSH

1. **Ніколи не знімайте парольну фразу з ключів на диску:** Використовуйте `ssh-agent` з директивою `AddKeysToAgent yes` замість незахищених приватних ключів.
2. **Обмежуйте час життя ключів у пам'яті:** Для чутливих ключів продакшену завантажуйте їх із таймаутом `ssh-add -t 1h` або вимогою підтвердження `ssh-add -c`.
3. **Забудьте про `ForwardAgent yes`:** Для переходу через проміжні сервери використовуйте виключно `ProxyJump`, що зберігає наскрізне шифрування й не відкриває локальний сокет віддаленим адміністраторам.
4. **Використовуйте `IdentitiesOnly yes`:** Це запобігає відмові в доступі через перебір ключів та блокує витік інформації про те, які саме ключі завантажені у вашому агенті.
5. **Вмикайте `ControlMaster` для частих підключень:** Мультиплексування усуває накладні витрати на повторне встановлення з'єднань, скорочуючи затримку запуску утиліт до лічених мілісекунд.
