# 📋 Довідник директив ~/.ssh/config, опцій ssh-add та протоколу агента

Цей довідник містить повну нормативну специфікацію директив конфігураційного файлу клієнта OpenSSH (`~/.ssh/config` та `/etc/ssh/ssh_config`), критеріїв умовного зіставлення `Match`, синтаксису токенів підстановки, параметрів утиліти `ssh-add`, змінних оточення та бінарного формату повідомлень протоколу `ssh-agent`.

---

## 1. Синтаксис та правила обчислення ~/.ssh/config

Клієнт OpenSSH зчитує конфігурацію з трьох джерел у строгому порядку пріоритету:
1. **Параметри командного рядка** (`-o Option=Value`, `-i key`, `-p port`, `-l user`).
2. **Користувацький конфігураційний файл** `~/.ssh/config` (або шлях, переданий через `ssh -F <файл>`).
3. **Загальносистемний конфігураційний файл** `/etc/ssh/ssh_config`.

### Базові правила оформлення та лексика

1. **Формат запису:** Кожен параметр задається окремим рядком у вигляді `Директива Значення` або `Директива = Значення`. Роздільником виступає довільна кількість пробілів або символів табуляції.
2. **Чутливість до регістру:** Назви директив нечутливі до регістру (`HostName`, `hostname`, `HOSTNAME` еквівалентні). Значення параметрів є **чутливими до регістру** (імена користувачів, шляхи до файлів, назви хостів, змінні середовища).
3. **Пробіли та екранування:** Якщо значення параметра містить пробіли (наприклад, складні команди `ProxyCommand`, шляхи або коментарі), воно береться у подвійні лапки: `IdentityFile "~/Keys/Work Key/id_ed25519"`.
4. **Коментарі та порожні рядки:** Порожні рядки та рядки, що починаються з `#` (після можливих пробілів), ігноруються. Внутрішньорядкові коментарі після значення не підтримуються.
5. **Вимоги до прав доступу файлової системи:** Файл `~/.ssh/config` повинен належати поточному користувачеві (UID) і мати права доступу `0600` (`-rw-------`) або `0644` (`-rw-r--r--`). Якщо файл має права запису для групи або сторонніх користувачів (`0664`, `0666`, `0777`), клієнт `ssh` перериває роботу з фатальною помилкою безпеки `Bad owner or permissions on ~/.ssh/config`.

### Директива Include

Директива `Include` дозволяє підключати зовнішні конфігураційні файли:

```sshconfig
Include ~/.ssh/config.d/*.conf
Include /etc/ssh/ssh_config.d/*.conf
```

- **Синтаксис:** `Include <шлях_або_маска>`
- **Розгортання:** Шляхи, що починаються з `~/`, розгортаються у домашній каталог користувача. Відносні шляхи обчислюються відносно `~/.ssh/` (для користувацького конфігу) або `/etc/ssh/` (для системного).
- **Маски пошуку (Globbing):** Підтримуються символи `*`, `?`, `[...]`. Якщо маска не знайшла жодного файлу, директива мовчки ігнорується без виклику помилки.
- **Вкладеність:** Директиви `Include` можуть бути вкладеними; глибина рекурсивного включення обмежена 16 рівнями для запобігання зацикленню.
- **Порядок обробки:** Вміст підключеного файлу вставляється безпосередньо в точку оголошення `Include` і підпорядковується правилу першого збігу.

### Порядок першого збігу (First Match Wins)

Клієнт OpenSSH читає конфігураційні файли послідовно згори вниз. Для кожної окремої директиви фіксується **перше знайдене значення**. Будь-які наступні входження тієї самої директиви для хоста, що збігся, мовчки ігноруються.

```sshconfig
# 1. Специфічний хост із точковими перевизначеннями
Host prod-db-01
    HostName 10.0.4.15
    User postgres
    Port 2222
    IdentityFile ~/.ssh/id_ed25519_db

# 2. Груповий шаблон для всіх серверів продакшену
Host prod-*
    User devops
    IdentityFile ~/.ssh/id_ed25519_prod

# 3. Глобальні параметри за замовчуванням — ЗАВЖДИ В КІНЦІ ФАЙЛУ
Host *
    IdentitiesOnly yes
    ServerAliveInterval 60
    ServerAliveCountMax 3
```

Під час виконання команди `ssh prod-db-01`:
- `HostName` отримає значення `10.0.4.15` (із першого блоку).
- `User` отримає значення `postgres` (значення `devops` із блоку `prod-*` ігнорується, бо директива `User` уже встановлена).
- `Port` отримає значення `2222`.
- `IdentityFile` накопичує значення: спочатку `~/.ssh/id_ed25519_db`, потім `~/.ssh/id_ed25519_prod` (директива `IdentityFile` є винятком спискового типу і додає ключі до списку спроб).
- `IdentitiesOnly`, `ServerAliveInterval` та `ServerAliveCountMax` беруться з фінального блоку `Host *`.

## 2. Специфікація блоків зіставлення Host та Match

### Шаблони блоків Host

Блок `Host` обмежує область дії директив за іменем хоста, переданим у командному рядку.

| Шаблон | Опис поведінки | Приклад |
|---|---|---|
| `*` | Збігається з нулем або більше будь-яких символів | `Host *.prod.internal` |
| `?` | Збігається рівно з одним довільним символом | `Host node-0?` |
| `!` | Заперечення умови (виключає конкретний збіг) | `Host *.internal !bastion.internal` |
| `пробіл` | Логічне «АБО» (роздільник списку псевдонімів) | `Host app1 app2 app3 staging-*` |

**Правило заперечення:** Шаблони із запереченням (`!`) повинні стояти поруч із загальними шаблонами. Якщо ім'я хоста збігається з шаблоном, перед яким стоїть `!`, весь блок `Host` вважається таким, що не збігся для цього хоста.

### Директива умовного зіставлення Match

Директива `Match` виконує динамічну оцінку умов під час встановлення з'єднання. На відміну від статичного `Host`, блок `Match` перевіряє атрибути сеансу, стан середовища та результат виконання зовнішніх утиліт.

```sshconfig
# Зіставлення за хостом та результатом виконання зовнішньої команди
Match host *.corp exec "nmcli connection show --active | grep -q VPN-Corp"
    ProxyJump none
    IdentityFile ~/.ssh/id_ed25519_direct

Match host *.corp
    ProxyJump bastion.corp.com
    IdentityFile ~/.ssh/id_ed25519_bastion
```

#### Критерії директиви Match

Усі критерії в межах одного рядка `Match` об'єднуються логічним «І» (AND). Усередині значень окремих критеріїв можна використовувати коми як логічне «АБО» (OR) та знак `!` для заперечення.

| Критерій | Синтаксис | Опис |
|---|---|---|
| `all` | `Match all` | Беззастережний збіг (використовується для скидання контексту або загальних правил). |
| `canonical` | `Match canonical` | Спрацьовує лише під час проходу після канонізації імені хоста через `CanonicalizeHostname`. |
| `final` | `Match final` | Спрацьовує на фінальному проході конфігурації після завершення всіх перетворень хоста та проксі. |
| `exec` | `Match exec "<команда>"` | Виконує команду оболонки (`/bin/sh -c`). Збіг успішний, якщо код повернення команди дорівнює `0`. Токени (`%h`, `%u`, `%p`, `%r`, `%L`) розгортаються перед запуском. |
| `host` | `Match host <шаблон>` | Зіставляє цільове ім'я хоста (після можливого розгортання `HostName` або канонізації). |
| `originalhost` | `Match originalhost <шаблон>` | Зіставляє вихідний рядок хоста, введений користувачем у CLI до будь-яких підстановок. |
| `user` | `Match user <шаблон>` | Зіставляє ім'я віддаленого користувача на сервері. |
| `localuser` | `Match localuser <шаблон>` | Зіставляє ім'я або UID локального користувача, що запустив клієнт `ssh`. |
| `localnetwork` | `Match localnetwork <CIDR/інтерфейс>` | Зіставляє локальну IP-підмережу або інтерфейс клієнта (підтримується в сучасних версіях OpenSSH). |
| `tagged` | `Match tagged <рядок>` | Зіставляє мітку, попередньо встановлену директивою `Tag`. |

#### Багатопрохідна модель обчислення конфігурації

Коли у конфігурації ввімкнено канонізацію (`CanonicalizeHostname yes` або `always`) чи присутні умовні блоки `Match canonical` та `Match final`, клієнт OpenSSH виконує обчислення конфігураційних файлів (`~/.ssh/config`, `/etc/ssh/ssh_config`) у кілька послідовних проходів (Multi-Pass Configuration Evaluation).

```
Вхідний рядок CLI: "ssh srv01"
              │
              ▼
    ┌───────────────────┐
    │     ПРОХІД 1      │ ──► Читання Host / Match (крім canonical і final)
    │  (Первинний збір) │     Визначення CanonicalizeHostname, User, Port, ProxyJump
    └─────────┬─────────┘
              │ CanonicalizeHostname == yes / always
              ▼
    ┌───────────────────┐
    │  ФАЗА РЕЗОЛВІНГУ  │ ──► Ітеративний DNS-пошук: srv01 + CanonicalDomains
    │   КАНОНІЗАЦІЇ     │     Перевірка правил CNAME (CanonicalizePermittedCNAMEs)
    └─────────┬─────────┘     Результат: "srv01.prod.internal.corp"
              │
              ▼
    ┌───────────────────┐
    │     ПРОХІД 2      │ ──► Повторне читання конфігурації
    │ (Match canonical) │     Зіставлення з новим FQDN (Host *.prod.internal.corp)
    └─────────┬─────────┘
              │
              ▼
    ┌───────────────────┐
    │     ПРОХІД 3      │ ──► Фіналізація параметрів підключення
    │   (Match final)   │     Закріплення ProxyCommand, IdentityFile, CertificateFile
    └─────────┬─────────┘
              │
              ▼
       Встановлення TCP-з'єднання та SSH KEX Handshake
```

##### Фази життєвого циклу обчислення

1. **Прохід 1 (Первинний збір та виявлення директив канонізації):**
   - Клієнт зчитує конфігурацію згори вниз, зіставляючи вихідне ім'я хоста з CLI (токен `%n` або директива `originalhost`).
   - На цьому етапі обробляються стандартні блоки `Host` та блоки `Match`, що **не містять** атрибутів `canonical` чи `final`.
   - Фіксуються первинні параметри: чинний `HostName`, цільовий `User`, `Port`, а також директиви керування DNS-канонізацією: `CanonicalizeHostname`, `CanonicalDomains`, `CanonicalizeMaxDots`, `CanonicalizeFallbackLocal` та `CanonicalizePermittedCNAMEs`.

2. **Фаза системного DNS-резолвінгу (Canonicalization Resolution Phase):**
   - Якщо `CanonicalizeHostname` встановлено у значення `yes` (або `always`), клієнт ініціює процедуру розширення короткого імені у FQDN (Fully Qualified Domain Name).
   - Якщо вхідне ім'я містить кількість крапок, меншу або рівну `CanonicalizeMaxDots` (за замовчуванням `1`), клієнт послідовно конкатенує ім'я хоста з кожним доменним суфіксом із переліку `CanonicalDomains` та виконує системний виклик `getaddrinfo()`.
   - Якщо домен повертає CNAME-запис, клієнт валідує відповідність цільового імені білому списку правил `CanonicalizePermittedCNAMEs`.
   - У разі успішного резолвінгу цільове ім'я хоста оновлюється до повного канонізованого FQDN.

3. **Прохід 2 (Канонічний прохід — `Match canonical`):**
   - Конфігураційні файли парсяться повторно з самого початку.
   - На цьому проході активуються блоки `Match canonical` та повторно оцінюються звичайні шаблони `Host <шаблон>` вже на основі повного FQDN.
   - Це дозволяє ізолювати середовища: наприклад, призначити приватний Bastion Host або внутрішній CA лише для хостів, які гарантовано зарезолвилися у домен `*.prod.datacenter.internal`.

4. **Прохід 3 (Фінальний прохід — `Match final`):**
   - Здійснюється завершальний прохід конфігурації.
   - Оцінюються блоки `Match final`, де вже відомі абсолютно всі атрибути сеансу (остаточна IP-адреса хоста, канонізоване ім'я, розгорнуті проксі-параметри).
   - Використовується для накладання безумовних політик безпеки (наприклад, примусове ввімкнення `IdentitiesOnly yes` або налаштування специфічних алгоритмів шифрування `Ciphers` для фінальних адрес).

## 3. Повний довідник директив ~/.ssh/config

### Маршрутизація, тунелювання та проксі

| Директива | Дозволені значення | Дефолт | Призначення та поведінка |
|---|---|---|---|
| `ProxyJump` | `[user@]host[:port][,...]`, `none` | `none` | Організовує наскрізний зашифрований тунель через один або ланцюжок проміжних бастіонів (Jump Hosts) за допомогою внутрішнього каналу `direct-tcpip`. Виключає створення проміжних шел-процесів. |
| `ProxyCommand` | шел-команда, `none` | `none` | Вказує зовнішню команду для підключення до сервера через канали `stdin`/`stdout`. Підтримує токени `%h`, `%p`, `%r`, `%n`. Значення `none` вимикає попередньо встановлені команди. |
| `LocalForward` | `[bind_addr:]port host:hostport` або `[bind_addr:]port /path/sock` | — | Відкриває локальний сокет на клієнтській машині та прокидає всі підключення на віддалений цільовий хост/порт через зашифрований SSH-сеанс. |
| `RemoteForward` | `[bind_addr:]port host:hostport` або `[bind_addr:]port /path/sock` | — | Відкриває сокет на віддаленому сервері та ретранслює вхідний трафік на вказаний локальний порт/сокет клієнта. Вимагає відповідних прав у `GatewayPorts` на стороні `sshd`. |
| `DynamicForward` | `[bind_addr:]port` | — | Піднімає локальний динамічний проксі-сервер прикладного рівня за протоколами SOCKS4 / SOCKS5. Розв'язання доменних імен (DNS) виконується на стороні віддаленого SSH-сервера. |
| `GatewayPorts` | `yes`, `no`, `clientspecified` | `no` | Дозволяє підключення сторонніх вузлів до локально прокинутих портів (`LocalForward`). При `no` сокет прив'язується виключно до loopback (`127.0.0.1` / `::1`). При `yes` сокет слухає `0.0.0.0`. |
| `ExitOnForwardFailure` | `yes`, `no` | `no` | Якщо встановлено `yes`, клієнт негайно перериває з'єднання та завершує процес із кодом помилки `255`, якщо хоча б одне з правил `LocalForward`, `RemoteForward` чи `DynamicForward` не змогло відкрити сокет (наприклад, порт зайнятий). |
| `ClearAllForwardings` | `yes`, `no` | `no` | Очищає всі правила `LocalForward`, `RemoteForward` та `DynamicForward`, оголошені у раніше зчитаних конфігураційних файлах або батьківських блоках. |
| `ForkAfterAuthentication` | `yes`, `no` | `no` | Переводить процес `ssh` у фоновий режим після успішного проходження автентифікації (еквівалент прапорця `-f`). Використовується для утримання портів фоновими тунелями. |
| `SessionType` | `default`, `none`, `subsystem` | `default` | Визначає тип віддаленого сеансу. Значення `none` блокує виділення PTY та запуск командної оболонки (еквівалент прапорця `-N`), що оптимізує ресурси під час роботи суто в режимі тунелювання портів. |

#### Архітектура транзиту та модель безпеки: ForwardAgent, ProxyJump і ProxyCommand

Для доступу до серверів у ізольованих мережевих сегментах через проміжні вузли (Jump Hosts / Bastions) застосовуються три принципово різні механізми. Вони мають суттєві відмінності у моделі довіри, криптографічних межах сеансу та векторах вразливостей.

| Параметр порівняння | ForwardAgent (`ssh -A`) | ProxyJump (`ssh -J`) | ProxyCommand (`nc` / `ssh -W`) |
|---|---|---|---|
| **Криптографічна межа** | Розривається на проміжному вузлі: окремий SSH-сеанс до бастіону, окремий — від бастіону до цілі. | Наскрізна (End-to-End): зовнішній SSH-сеанс інкапсулює внутрішній тунель `direct-tcpip`, усередині якого встановлюється незалежний SSH-сеанс до цілі. | Наскрізна (End-to-End): локальний процес `ssh` спілкується з цільовим сервером через канали `stdin`/`stdout` зовнішньої команди. |
| **Точка автентифікації** | Клієнт автентифікується на бастіоні; бастіон автентифікується на цільовому сервері, використовуючи прокинутий сокет агента. | Клієнт автентифікується окремо на бастіоні та окремо на цільовому сервері. Бастіон не бере участі в автентифікації до цілі. | Клієнт автентифікується безпосередньо на цільовому сервері. |
| **Наявність сокета агента на бастіоні** | **Так:** створюється сокет домену UNIX `/tmp/ssh-XXXXXX/agent.<ppid>`, змінна `$SSH_AUTH_SOCK`. | **Ні:** сокет агента на бастіоні не відкривається, змінна оточення не встановлюється. | **Ні:** сокет агента на проміжному вузлі відсутній. |
| **Вектор атаки при зломі бастіону** | **Критичний (Agent Hijacking):** процес із правами `root` або тим самим UID може підключитися до сокета та використовувати локальний `ssh-agent` як оракул підпису для доступу до довільних хостів. | **Мінімальний:** скомпрометований бастіон може лише скинути TCP-з'єднання або спробувати атаку MITM, яка блокується перевіркою ключа хоста в `known_hosts`. | **Мінімальний:** аналогічно `ProxyJump`. |
| **Вимоги до прав на бастіоні** | Потрібен інтерактивний шел (`shell access`) та увімкнена опція `AllowAgentForwarding yes` у серверному `sshd_config`. | Достатньо дозволу на прокидання TCP (`AllowTcpForwarding yes` або `AllowTcpForwarding local`). Виділення шелу чи PTY не потрібне. | Потрібна наявність утиліти перенаправлення трафіку (`nc`, `socat`) або підтримка прапорця `ssh -W`. |
| **Накладні витрати** | Один процес клієнта на локальній машині, один клієнтський процес `ssh` на бастіоні. | Один процес клієнта на локальній машині, що підтримує два вкладених криптографічних контексти. | Локальний клієнт породжує додатковий дочірній процес через системний виклик `fork()` / `exec()`. |

##### Механіка каналу auth-agent@openssh.com та ризики викрадення сокета

Коли у конфігурації увімкнено `ForwardAgent yes`, клієнт під час встановлення сеансу надсилає канальний запит типу `"auth-agent-req@openssh.com"` (RFC 4254). Віддалений демон `sshd` виконує такі системні кроки:
1. Створює тимчасовий каталог `/tmp/ssh-XXXXXXXXXX/` з правами `0700`, власником якого стає поточний користувач.
2. Створює та відкриває для прослуховування потоковий сокет домену UNIX (`AF_UNIX`, `SOCK_STREAM`) з назвою `agent.<ppid>`.
3. Експортує змінну оточення `SSH_AUTH_SOCK=/tmp/ssh-XXXXXXXXXX/agent.<ppid>` у командну оболонку сеансу.

Коли будь-який процес на віддаленій машині підключається до цього сокета через виклик `connect()`, демон `sshd` відкриває новий мультиплексований логічний канал SSH типу `"auth-agent@openssh.com"` у зворотному напрямку до клієнта. Клієнт, отримавши повідомлення каналу, підключається до свого справжнього локального сокета `$SSH_AUTH_SOCK` і прозоро ретранслює бінарні пакети між віддаленим сокетом і локальним демоном `ssh-agent`.

⚠️ **Механізм атаки Side-Channel Socket Hijacking:**
Протокол сокета домену UNIX є анонімним потоком байтів: демон `ssh-agent` не має технічної можливості дізнатися, яка саме віддалена програма надіслала пакет. Якщо бастіон або проміжний сервер скомпрометовано (зловмисник отримав права `root`, використав вразливість локального підвищення привілеїв ядра або має доступ до того самого UID), зловмисник може зчитати шлях із `/proc/<pid>/environ` та безпосередньо підключитися до відкритого сокета `/tmp/ssh-XXXXXX/agent.<ppid>`. Надіславши стандартні повідомлення `SSH2_AGENTC_REQUEST_IDENTITIES` та `SSH2_AGENTC_SIGN_REQUEST`, атакуючий може підписати довільні челенджі для автентифікації на внутрішніх базах даних, репозиторіях коду або серверах управління, доки користувач утримує з'єднання відкритим.

##### Заходи захисту та обмеження агента

1. **Інтерактивне підтвердження (`ForwardAgent confirm` та `ssh-add -c`):**
   При додаванні ключа з прапорцем `SSH_AGENT_CONSTRAIN_CONFIRM` (`0x02`) локальний демон `ssh-agent` призупиняє обробку кожного виклику `SIGN_REQUEST` і звертається до зовнішньої програми `SSH_ASKPASS`, вимагаючи фізичного підтвердження операції людиною. Якщо зловмисник намагається використати прокинутий сокет у фоні, на екрані користувача з'являється несподіваний діалог підтвердження.
2. **Обмеження призначення (Destination Constraints / `restrict-destination-v00@openssh.com`):**
   Починаючи з OpenSSH 8.9, утиліта `ssh-add -h <хост>` дозволяє прив'язати ключ до конкретних хостів призначення та дозволених проміжних вузлів. Якщо скомпрометований бастіон намагається використати ключ для з'єднання з вузлом, не зазначеним у бінарній структурі обмеження, `ssh-agent` відхиляє операцію кодом `SSH_AGENT_FAILURE`.
3. **Повна міграція на ProxyJump:**
   Використання директиви `ProxyJump` або прапорця `ssh -J` усуває загрозу на рівні архітектури: оскільки сокет `auth-agent@openssh.com` взагалі не створюється на бастіоні, проміжний вузол є повністю ізольованим від криптографічних ключів клієнта.

#### Архітектура апаратних модулів PKCS#11 та безпечних токенів (Cryptoki API)

Для сценаріїв із підвищеними вимогами до безпеки закриті ключі автентифікації зберігаються всередині апаратних криптографічних пристроїв: смарт-карток, апаратних ключів (YubiKey, Nitrokey, Feitian) або модулів апаратної безпеки (HSM / Hardware Security Module). Інтеграція клієнта OpenSSH та `ssh-agent` із такими пристроями спирається на галузевий стандарт **ANSI/OASIS PKCS#11 (Cryptoki API v2.40)**.

##### Принцип апаратної ізоляції та атрибути об'єктів

Всередині токена закритий ключ створюється або імпортується з жорстко зафіксованими системними атрибутами:
- `CKA_EXTRACTABLE = CK_FALSE`: апаратна мікропрограма чипа фізично блокує будь-яке читання сирих байтів закритого ключа назовні;
- `CKA_SENSITIVE = CK_TRUE`: ключ вважається конфіденційним і не може бути експортований навіть у зашифрованому вигляді без майстер-ключа токена;
- `CKA_PRIVATE = CK_TRUE`: доступ до операцій з об'єктом можливий виключно після успішної автентифікації користувача (введення PIN).

Клієнт OpenSSH ніколи не отримує байти приватного ключа в пам'ять хоста: він передає відкритий хеш виклику (challenge) у токен, а вбудований криптопроцесор повертає готовий цифровий підпис.

```
       Клієнт OpenSSH / ssh-agent                 Апаратний токен (YubiKey / PIV Smartcard)
┌───────────────────────────────────────┐       ┌───────────────────────────────────────────┐
│ dlopen("opensc-pkcs11.so")            │       │                                           │
│ C_Initialize()                        │       │                                           │
│ C_GetSlotList() ──────────────────────┼───────┼──► Виявлення підключеного зчитувача       │
│ C_OpenSession(slot_id)                │       │                                           │
│ C_Login(CKU_USER, PIN) ───────────────┼───────┼──► Верифікація PIN (апаратний лічильник)  │
│ C_FindObjects(CKO_CERTIFICATE / KEY)  │       │                                           │
│ C_GetAttributeValue() ◄───────────────┼───────┼─── Експорт відкритого ключа / X.509 cert  │
│                                       │       │                                           │
│ [Фаза автентифікації SSH]             │       │                                           │
│ C_SignInit(CKM_ECDSA / CKM_RSA_PKCS)  │       │                                           │
│ C_Sign(challenge_hash) ───────────────┼───────┼──► [Криптопроцесор: накладання підпису]   │
│                        ◄──────────────┼───────┼─── [Готовий бінарний підпис signature]    │
└───────────────────────────────────────┘       └───────────────────────────────────────────┘
```

##### Життєвий цикл роботи з динамічною бібліотекою постачальника

Коли в `~/.ssh/config` вказано директиву `PKCS11Provider <шлях>`, або клієнт запущено з прапорцем `ssh -I <шлях>`, або ключ додається через `ssh-add -s <шлях>`, OpenSSH виконує послідовність системних викликів:

1. **Динамічне завантаження (`dlopen`):**
   Процес завантажує спільну бібліотеку викликом `dlopen(provider_path, RTLD_NOW)`. Бібліотека експортує точку входу `C_GetFunctionList`, яка повертає структуру покажчиків на функції Cryptoki API.
2. **Ініціалізація підсистеми (`C_Initialize`):**
   Викликається `C_Initialize(NULL_PTR)`. Драйвер ініціалізує внутрішні черги та зв'язок зі службою керування смарт-картками (`pcscd`).
3. **Сканування слотів (`C_GetSlotList`):**
   Клієнт викликає `C_GetSlotList(CK_TRUE, NULL_PTR, &count)` для отримання кількості слотів з присутніми токенами (`CKF_TOKEN_PRESENT`), після чого виділяє масив і повторним викликом отримує їхні ідентифікатори `slot_id`.
4. **Опитування стану токена (`C_GetTokenInfo`):**
   Перевіряються атрибути `CK_TOKEN_INFO`: мітка токена (`label`), виробник (`manufacturerID`), модель, а також прапорці стану (`CKF_LOGIN_REQUIRED`, `CKF_USER_PIN_COUNT_LOW`, `CKF_USER_PIN_FINAL_TRY`, `CKF_USER_PIN_LOCKED`).
5. **Відкриття сесії (`C_OpenSession`):**
   Створюється паралельна сесія взаємодії викликом `C_OpenSession(slot_id, CKF_SERIAL_SESSION, NULL_PTR, NULL_PTR, &session)`.
6. **Автентифікація користувача (`C_Login`):**
   Якщо встановлено прапорець `CKF_LOGIN_REQUIRED`, клієнт запитує PIN-код та викликає `C_Login(session, CKU_USER, (CK_UTF8CHAR_PTR)pin, pin_len)`.
7. **Пошук ключів та сертифікатів (`C_FindObjectsInit` / `C_FindObjects`):**
   Клієнт шукає об'єкти класів `CKO_PRIVATE_KEY` та відповідні їм `CKO_CERTIFICATE` / `CKO_PUBLIC_KEY`. Через функцію `C_GetAttributeValue` зчитуються відкриті експоненти та модулі RSA, координати точок еліптичних кривих ECDSA (ANSI X9.62) або бінарні сертифікати X.509 у кодуванні DER, з яких конструюється стандартний відкритий блоб OpenSSH.
8. **Операція цифрового підпису (`C_SignInit` та `C_Sign`):**
   Під час проходження автентифікації SSH клієнт ініціює операцію викликом `C_SignInit(session, &mechanism, privkey_handle)` (де механізм — `CKM_RSA_PKCS`, `CKM_SHA256_RSA_PKCS`, `CKM_ECDSA` тощо) і передає хеш повідомлення у виклик `C_Sign(session, data, data_len, sig, &sig_len)`.
9. **Завершення сесії (`C_CloseSession`, `C_Finalize`, `dlclose`):**
   Після завершення автентифікації або при вивантаженні ключа клієнт закриває сесію, деініціалізує драйвер та вивантажує бібліотеку з пам'яті.

В операційних системах Linux, BSD та macOS застосовуються дві основні бібліотеки-провайдери:

| Характеристика | OpenSC (`opensc-pkcs11.so`) | Yubico PKCS#11 (`libykcs11.so`) |
|---|---|---|
| **Тип модуля** | Універсальний модульний шар абстракції для сотень моделей карт. | Вузькоспеціалізована бібліотека для апаратних ключів YubiKey 4 / 5 Series. |
| **Системні залежності** | Вимагає наявності системного демона `pcscd` та бібліотеки `libpcsclite.so`. | Спирається на прямий зв'язок через USB CCID / `libusb` або системний PC/SC. |
| **Підтримувані аплети** | PIV (FIPS 201), CAC, OpenPGP Card, eID (електронні паспорти), Feitian, Nitrokey. | Аплет PIV (NIST SP 800-73-4 Personal Identity Verification). |
| **Розподіл слотів** | Динамічний: кожен контейнер ключа або сертифікат на карті монтується як віртуальний слот. | Фіксована модель чотирьох стандартних PIV-слотів (`9a`, `9c`, `9d`, `9e`). |

##### Розподіл PIV-слотів та політики безпеки YubiKey

Аплет PIV на ключах YubiKey організований у вигляді чотирьох апаратних слотів із фіксованим призначенням:
1. **Слот `9a` (Authentication):** Призначений для входу в ОС та автентифікації SSH. PIN-код запитується один раз за сесію підключення до токена.
2. **Слот `9c` (Digital Signature):** Призначений для юридично значимих цифрових підписів (підпис Git-комітів, документів, релізів). За стандартом PIV вимагає введення PIN-коду **перед кожною окремою операцією підпису**.
3. **Слот `9d` (Key Management):** Призначений для операцій дешифрування сесійних ключів та відновлення доступу.
4. **Слот `9e` (Card Authentication):** Дозволяє автентифікацію пристрою без введення PIN-коду (використовується для систем фізичного контролю доступу).

Кожен ключ, згенерований у слоті YubiKey, захищений двома апаратними політиками:
- **`PIN Policy`:**
  - `never`: введення PIN не вимагається (лише слот `9e`);
  - `once`: PIN вводиться один раз після підключення токена до USB;
  - `always`: PIN вимагається перед кожним системним викликом `C_Sign`.
- **`Touch Policy` (Фізична присутність):**
  - `never`: підпис накладається автоматично програмним викликом;
  - `always`: перед накладанням кожного підпису світлодіод токена починає блимати, і криптопроцесор чекає фізичного дотику пальця людини до ємнісного контакту токена (таймаут 15 секунд). Програмні атаки з боку зловмисника, що має root-доступ на клієнті, блокуються на рівні заліза;
  - `cached`: фізичний дотик кешується апаратно на 15 секунд після першого дотику.

##### Обробка PIN-кодів через SSH_ASKPASS та захист від блокування (Lockout)

Під час звернення до PKCS#11 провайдера клієнт OpenSSH або утиліта `ssh-add` запитує PIN-код користувача за такими правилами:

1. **Термінальне введення (TTY):** За наявності керівного термінала PIN запитується через `/dev/tty` за допомогою функції `readpassphrase()`, яка вимикає ехо-відображення символів термінала (`ECHO` прапорець `termios`).
2. **Графічне введення через `SSH_ASKPASS`:** Якщо керівний TTY відсутній (графічний запуск, скрипти CI/CD) або встановлено `SSH_ASKPASS_REQUIRE=force`, процес викликає зовнішню програму:
   - Клієнт створює односпрямований канал `pipe()`;
   - Виконує системний виклик `fork()`;
   - У дочірньому процесі перенаправляє `stdout` у дескриптор запису каналу через `dup2()`, а `stdin` перенаправляє на `/dev/null`;
   - Викликає `execv(askpass_path, argv)`, передаючи у `argv[1]` текст запрошення: наприклад, `"Enter PIN for 'YubiKey PIV #12345678': "`;
   - Батьківський процес зчитує введений рядок, закриває дескриптори та негайно очищає буфер пам'яті за допомогою `explicit_bzero()` після передачі у виклик `C_Login()`.

⚠️ **Апаратний захист від перебору PIN (Retry Counter & Lockout):**
Апаратні токени містять енергонезалежний апаратний лічильник помилок введення PIN (за замовчуванням **3 спроби**). Якщо користувач або автоматизований процес передає невірний PIN-код, токен повертає код помилки `CKR_PIN_INCORRECT`, а лічильник спроб зменшується на одиницю. Якщо лічильник досягає нуля, токен переходить у заблокований стан `CKR_PIN_LOCKED`. Розблокування можливе виключно за допомогою коду адміністратора PUK (PIN Unblocking Key) командою `yubico-piv-tool -a unblock-pin` або шляхом повного апаратного скидання (Factory Reset), яке безповоротно знищує всі закриті ключі на чипі.

##### Порівняння: PKCS#11 проти сучасного стандарту FIDO2 / Security Keys (`-sk`)

Починаючи з OpenSSH 8.2, поруч із класичним стандартом PKCS#11 підтримується нативна робота з апаратними токенами через стандарт FIDO2 / CTAP2 (ключі типу `ecdsa-sk` та `ed25519-sk`):

| Критерій порівняння | PKCS#11 (PIV / CAC / Smartcards) | FIDO2 / Security Keys (`-sk` OpenSSH 8.2+) |
|---|---|---|
| **Драйверний стек** | Складний: вимагає бібліотек постачальника (`opensc-pkcs11.so`, `libykcs11.so`), системного демона `pcscd` та драйверів CCID. | Простий: пряма робота через USB HID (протокол CTAP2 / бібліотека `libfido2.so`), не потребує демона `pcscd`. |
| **Формат зберігання ключів** | Закритий ключ зберігається виключно всередині слота картки. На диск експортується відкритий сертифікат. | Підтримує два режими: 1) Файл дескриптора (Key Handle) на диску; 2) Резидентні ключі (Discoverable Credentials) на токені (`ssh-add -K`). |
| **Перевірка присутності (User Presence)** | Залежить від вендорних реалізацій PKCS#11 (touch policy YubiKey). Стандарт Cryptoki не має уніфікованого прапорця дотику. | Вбудована в протокол: обов'язковий фізичний дотик до токена (User Presence) та опційний біометричний PIN (User Verification). |
| **Криптографічні алгоритми** | Широкий вибір: RSA 2048/4096, ECDSA NIST P-256 / P-384, Ed25519 (залежно від моделі токена). | Жорстко стандартизовані: `sk-ecdsa-sha2-nistp256@openssh.com` та `sk-ssh-ed25519@openssh.com`. |
| **Апаратне блокування сокетів** | Токен може блокуватися, якщо два процеси намагаються одночасно відкрити монопольний доступ через PC/SC. | USB HID інтерфейс підтримує неблокуючий паралельний доступ для кількох застосунків. |

### Мультиплексування з'єднань (ControlMaster)

| Директива | Дозволені значення | Дефолт | Призначення та поведінка |
|---|---|---|---|
| `ControlMaster` | `yes`, `no`, `ask`, `auto`, `autoask` | `no` | Дозволяє спільне використання одного мережевого TCP/SSH з'єднання для кількох паралельних сесій. Значення `auto` створює Master-процес за відсутності сокета або підключається як Slave до існуючого сокета через дескриптор `SCM_RIGHTS`. |
| `ControlPath` | шлях до сокета | `none` | Шлях створення керівного UNIX-сокета мультиплексування. Підтримує токени підстановки (зокрема `%C`, `%r`, `%h`, `%p`, `%u`, `%l`, `%i`). |
| `ControlPersist` | `yes`, `no`, час (`10m`, `1h`, `4h`) | `no` | Залишає Master-процес у фоні після закриття первинного термінала на вказаний інтервал бездіяльності, підтримуючи відкритий тунель для наступних slave-підключень. |

#### Команди керування мультиплексуванням (ssh -O)

Керування активним сокетом Master-процесу здійснюється через опцію `-O`:
- `ssh -O check <хост>`: Перевіряє працездатність керівного сокета (повертає PID master-процесу).
- `ssh -O forward -L 8080:localhost:80 <хост>`: Динамічно додає новий тунель пересилання портів до працюючого master-з'єднання.
- `ssh -O cancel -L 8080:localhost:80 <хост>`: Скасовує активне правило пересилання port forwarding.
- `ssh -O stop <хост>`: Забороняє прийом нових slave-підключень і коректно завершує master-процес після закриття всіх поточних клієнтів.
- `ssh -O exit <хост>`: Примусово та негайно розриває всі активні slave-сесії та завершує процес master.

#### Внутрішній устрій ControlMaster: IPC через сокет UNIX та передача дескрипторів SCM_RIGHTS

Механізм `ControlMaster` дозволяє уникнути повторного проходження фаз встановлення TCP-з'єднання (TCP 3-Way Handshake), узгодження алгоритмів обміну ключами (Diffie-Hellman / ECDH KEX), перевірки хоста та криптографічної автентифікації користувача для кожного наступного виклику `ssh`, `scp`, `sftp` чи `rsync`.

##### Модель Master-Slave та життєвий цикл сокета

1. **Ініціалізація Master-процесу:**
   Перший процес `ssh`, запущений з опцією `ControlMaster auto` або `yes`, виявляє відсутність сокета за шляхом `ControlPath`. Він відкриває стандартне мережеве TCP-з'єднання з віддаленим сервером `sshd`, проходить автентифікацію, створює локальний потоковий сокет домену UNIX (`AF_UNIX`, `SOCK_STREAM`), прив'язує його викликом `bind()` до шляху `ControlPath`, переводить у режим очікування викликом `listen()` і входить у неблокуючий цикл мультиплексування подій (`poll()` / `epoll()` / `kqueue()`).
2. **Підключення Slave-клієнтів:**
   Наступний виклик `ssh` до того самого хоста намагається виконати системний виклик `connect()` до наявного файлу сокета `ControlPath`.
   - Якщо підключення успішне (`connect() == 0`), процес переходить у режим Slave і взаємодіє з Master-процесом через локальний протокол мультиплексування (OpenSSH Mux Protocol).
   - Якщо сокет відсутній (`ENOENT`) або попередній Master-процес аварійно завершився без видалення файлу (`ECONNREFUSED`), Slave-процес видаляє застарілий файл сокета викликом `unlink()` і сам стає новим Master-процесом.
3. **Завершення роботи та ControlPersist:**
   Коли первинний термінальний сеанс Master-процесу завершується, за наявності опції `ControlPersist <час>` Master переходить у фоновий режим демона, від'єднується від керівного TTY (`daemon()` / `setsid()`) і продовжує утримувати мережевий тунель протягом зазначеного інтервалу бездіяльності. Якщо за цей час підключається новий Slave-клієнт, таймер бездіяльності скидається.

##### Передача файлових дескрипторів через допоміжні дані (SCM_RIGHTS)

Для виконання інтерактивних сесій або команд клієнт Slave не читає і не пише дані у віддалений TCP-сокет самостійно: він передає власні відкриті файлові дескриптори безпосередньо процесу Master через механізм допоміжних керівних повідомлень (Ancillary Data / Control Messages) ядра операційної системи.

Під час передачі повідомлення `MUX_C_NEW_SESSION` Slave-процес формує системний виклик `sendmsg()`, передаючи структуру `struct msghdr`, яка містить буфер допоміжних даних `msg_control`:

```text
struct msghdr {
    void         *msg_name;       /* NULL для з'єднаного потокового сокета */
    socklen_t    msg_namelen;
    struct iovec *msg_iov;        /* Вказівник на бінарне тіло повідомлення MUX */
    size_t       msg_iovlen;
    void         *msg_control;    /* Буфер для керівних повідомлень cmsghdr */
    size_t       msg_controllen;  /* Розмір буфера допоміжних даних */
    int          msg_flags;
};
```

Усередині буфера `msg_control` розміщується заголовок керівного повідомлення `struct cmsghdr`:
- `cmsg_level = SOL_SOCKET` (рівень сокетного API ядра);
- `cmsg_type = SCM_RIGHTS` (Socket Control Message: передача прав доступу до дескрипторів);
- `cmsg_len = CMSG_LEN(sizeof(int) * 3)` (розмір заголовка плюс масив числових значень дескрипторів).

Тіло `CMSG_DATA()` містить масив дескрипторів Slave-процесу:
1. `fd[0]` — стандартний потік вводу `stdin` (або дескриптор підлеглого термінала slave PTY);
2. `fd[1]` — стандартний потік виводу `stdout`;
3. `fd[2]` — стандартний потік помилок `stderr`.

Ядро операційної системи, обробляючи виклик `sendmsg()`, знаходить відповідні записи в таблиці файлових дескрипторів Slave-процесу, збільшує лічильник посилань на системні структури відкритого файлу `struct file *` у пам'яті VFS ядра та виділяє нові дескриптори в таблиці Master-процесу під час виклику `recvmsg()`. Відтепер Master-процес може безпосередньо читати `stdin` термінала Slave-клієнта й записувати вивід сервера у `stdout`/`stderr` Slave-клієнта через стандартні виклики `read()` та `write()`.

##### Специфікація бінарного протоколу OpenSSH Mux Protocol

Взаємодія через керівний сокет `ControlPath` підпорядковується двійковому протоколу Mux. Кожен пакет складається з 4-байтового префікса довжини `uint32` (мережевий порядок байтів Big-Endian) та 4-байтового коду повідомлення `uint32`:

```
+------------------------------------+------------------------------------+------------------------------------+
|  Довжина корисного навантаження L  |          Код повідомлення          |       Параметри операції MUX       |
|       (uint32, 4 байти)            |         (uint32, 4 байти)          |        (L - 4 байтів)              |
+------------------------------------+------------------------------------+------------------------------------+
```

| Константа протоколу | Числовий код | Напрямок | Опис операції та структура корисного навантаження |
|---|---|---|---|
| `MUX_MSG_HELLO` | `0x00000001` | Двосторонній | Початкове привітання: `uint32 version` (поточна версія `4`), `uint32 pid` (PID процесу). |
| `MUX_C_NEW_SESSION` | `0x10000002` | Slave → Master | Запит відкриття сеансу: `uint32 session_id`, `boolean want_tty`, `boolean want_x11`, `boolean want_agent`, `boolean subsystem`, `string term`, `string cmd`, `array of env_vars`. Супроводжується дескрипторами `SCM_RIGHTS`. |
| `MUX_C_ALIVE_CHECK` | `0x10000004` | Slave → Master | Перевірка працездатності: не містить додаткових параметрів. |
| `MUX_C_TERMINATE` | `0x10000005` | Slave → Master | Запит примусового завершення Master-процесу. |
| `MUX_C_OPEN_FWD` | `0x10000006` | Slave → Master | Динамічне відкриття port forwarding: `uint32 req_id`, `uint32 fwd_type` (`1` — Local, `2` — Remote, `3` — Dynamic), `string listen_host`, `uint32 listen_port`, `string connect_host`, `uint32 connect_port`. |
| `MUX_C_CLOSE_FWD` | `0x10000007` | Slave → Master | Скасування активного тунелю port forwarding: `uint32 req_id`, `uint32 fwd_type`, `string listen_host`, `uint32 listen_port`, `string connect_host`, `uint32 connect_port`. |
| `MUX_C_PROXY` | `0x1000000f` | Slave → Master | Запит проксі-каналу для передачі `stdin`/`stdout` через сокет керування без `SCM_RIGHTS`. |
| `MUX_S_OK` | `0x80000001` | Master → Slave | Підтвердження успішного виконання команди (`uint32 req_id`). |
| `MUX_S_PERMISSION_DENIED` | `0x80000002` | Master → Slave | Відмова у виконанні операції через обмеження прав доступу (`uint32 req_id`, `string reason`). |
| `MUX_S_FAILURE` | `0x80000003` | Master → Slave | Помилка обробки команди (`uint32 req_id`, `string reason`). |
| `MUX_S_SESSION_OPENED` | `0x80000004` | Master → Slave | Сеанс успішно створено на віддаленому сервері (`uint32 session_id`). |
| `MUX_S_ALIVE` | `0x80000005` | Master → Slave | Відповідь на `ALIVE_CHECK` (`uint32 pid` Master-процесу). |
| `MUX_S_REMOTE_PORT` | `0x80000008` | Master → Slave | Повертає фактично виділений динамічний віддалений TCP-порт (`uint32 req_id`, `uint32 alloc_port`). |
| `MUX_S_TTY_ALLOC_FAIL` | `0x8000000a` | Master → Slave | Помилка виділення віддаленого псевдотермінала (`uint32 session_id`). |

#### Протокол мультиплексування каналів SSH (RFC 4254)

Після отримання запиту `MUX_C_NEW_SESSION` від Slave-клієнта, Master-процес створює новий логічний канал усередині існуючого захищеного TCP-з'єднання з сервером за протоколом SSH Connection Protocol (RFC 4254).

##### Реєстр повідомлень канального рівня SSH (RFC 4254)

| Код повідомлення | Тип (Dec) | Тип (Hex) | Напрямок | Структура кадру та опис полів |
|---|---|---|---|---|
| `SSH_MSG_CHANNEL_OPEN` | `90` | `0x5a` | Клієнт ↔ Сервер | `string channel_type` (`"session"`, `"direct-tcpip"`, `"forwarded-tcpip"`, `"x11"`, `"auth-agent@openssh.com"`), `uint32 sender_channel`, `uint32 initial_window_size`, `uint32 maximum_packet_size` + специфічні параметри типу. |
| `SSH_MSG_CHANNEL_OPEN_CONFIRMATION` | `91` | `0x5b` | Клієнт ↔ Сервер | `uint32 recipient_channel`, `uint32 sender_channel`, `uint32 initial_window_size`, `uint32 maximum_packet_size`. |
| `SSH_MSG_CHANNEL_OPEN_FAILURE` | `92` | `0x5c` | Клієнт ↔ Сервер | `uint32 recipient_channel`, `uint32 reason_code`, `string description`, `string lang_tag`. |
| `SSH_MSG_CHANNEL_WINDOW_ADJUST` | `93` | `0x5d` | Клієнт ↔ Сервер | `uint32 recipient_channel`, `uint32 bytes_to_add` (збільшення буфера прийому ковзного вікна). |
| `SSH_MSG_CHANNEL_DATA` | `94` | `0x5e` | Клієнт ↔ Сервер | `uint32 recipient_channel`, `string data` (корисні байти вводу/виводу). |
| `SSH_MSG_CHANNEL_EXTENDED_DATA` | `95` | `0x5f` | Клієнт ↔ Сервер | `uint32 recipient_channel`, `uint32 data_type_code` (`1` = `SSH_EXTENDED_DATA_STDERR`), `string data`. |
| `SSH_MSG_CHANNEL_EOF` | `96` | `0x60` | Клієнт ↔ Сервер | `uint32 recipient_channel` (одностороннє закриття потоку передачі даних). |
| `SSH_MSG_CHANNEL_CLOSE` | `97` | `0x61` | Клієнт ↔ Сервер | `uint32 recipient_channel` (повне закриття каналу та звільнення його ID). |
| `SSH_MSG_CHANNEL_REQUEST` | `98` | `0x62` | Клієнт ↔ Сервер | `uint32 recipient_channel`, `string request_type` (`"pty-req"`, `"shell"`, `"exec"`, `"env"`, `"window-change"`, `"signal"`), `boolean want_reply` + специфічні дані запиту. |
| `SSH_MSG_CHANNEL_SUCCESS` | `99` | `0x63` | Клієнт ↔ Сервер | `uint32 recipient_channel` (підтвердження успішного виконання канального запиту). |
| `SSH_MSG_CHANNEL_FAILURE` | `100` | `0x64` | Клієнт ↔ Сервер | `uint32 recipient_channel` (відхилення канального запиту). |

##### Коди відхилення відкриття каналу (`reason_code`)
- `1` (`SSH_OPEN_ADMINISTRATIVELY_PROHIBITED`): Адміністративна заборона (наприклад, `AllowTcpForwarding no` або відхилення відкриття PTY в політиці безпеки).
- `2` (`SSH_OPEN_CONNECT_FAILED`): Неможливо встановити підключення до цільового хоста при прокиданні портів (наприклад, цільовий сервіс недоступний або збій DNS).
- `3` (`SSH_OPEN_UNKNOWN_CHANNEL_TYPE`): Невідомий тип каналу, непідтримуваний протилежною стороною.
- `4` (`SSH_OPEN_RESOURCE_SHORTAGE`): Вичерпання системних ресурсів або ліміту максимальної кількості одночасних каналів (`MaxSessions`).

##### Механізм ковзного вікна керування потоком (Flow Control Sliding Window)

Кожен канал має незалежну систему контролю швидкості потоку даних, що запобігає переповненню буферів пам'яті:
1. Під час надсилання `SSH_MSG_CHANNEL_OPEN` кожна сторона повідомляє розмір свого первинного вікна прийому `initial_window_size` (наприклад, `2097152` байти = 2 МБ) та максимальний розмір одиничного пакета `maximum_packet_size` (зазвичай `32768` байтів = 32 КБ).
2. Відправник не має права надсилати більше корисних даних у повідомленнях `SSH_MSG_CHANNEL_DATA`, ніж поточний залишок вікна одержувача.
3. Коли одержувач зчитує дані зі свого буфера та передає їх застосунку або на термінал, він надсилає повідомлення `SSH_MSG_CHANNEL_WINDOW_ADJUST`, додаючи кількість звільнених байтів `bytes_to_add` до вікна відправника.
4. Якщо один із каналів (наприклад, повільний SFTP-трансфер через перевантажений дисковий накопичувач) призупиняє споживання даних, його вікно зменшується до нуля, і відправка даних для цього каналу блокується без зупинки інших каналів (інтерактивних терміналів SSH), які продовжують працювати у тому самому TCP-з'єднанні без затримок.

### Канонізація та резолвінг імен

| Директива | Дозволені значення | Дефолт | Призначення та поведінка |
|---|---|---|---|
| `CanonicalizeHostname` | `yes`, `no`, `always` | `no` | Вмикає внутрішню канонізацію коротких імен хостів у FQDN через DNS перед зіставленням блоків `Match canonical`. Значення `always` примусово виконує канонізацію навіть за наявності `ProxyJump` або `ProxyCommand`. |
| `CanonicalDomains` | список доменів через пробіл | — | Перелік доменних суфіксів пошуку, які послідовно додаються до неповного імені хоста під час канонізації. |
| `CanonicalizeMaxDots` | ціле число | `1` | Максимальна кількість крапок у імені хоста, за якої ще застосовується канонізація через суфікси `CanonicalDomains`. Якщо кількість крапок перевищує ліміт, ім'я вважається абсолютним. |
| `CanonicalizeFallbackLocal` | `yes`, `no` | `yes` | Чи виконувати повернення до вихідного нерозв'язаного імені хоста, якщо всі спроби канонізації через DNS завершилися невдачею. Запобігає фатальній помилці резолвінгу. |
| `CanonicalizePermittedCNAMEs` | перелік правил через кому | `none` | Білий список дозволених перенаправлень CNAME у форматі `джерело:ціль` (наприклад, `*.corp.example.com:*.dmz.example.com`). Блокує підміну хостів через зловмисні CNAME-записи DNS. |
| `AddressFamily` | `any`, `inet`, `inet6` | `any` | Обмежує вибір протоколу мережевого рівня: `inet` (виключно IPv4), `inet6` (виключно IPv6) або `any` (автовибір за DNS згідно з RFC 8305). |

#### Архітектура та протокол канонізації хостів (Host Canonicalization)

У розподілених корпоративних мережах із кількома датацентрами та хмарними регіонами системні адміністратори зазвичай підключаються до серверів за короткими псевдонімами (`ssh node-01`, `ssh pg-master`). Традиційний резолвінг через системний файл `/etc/resolv.conf` (параметр `search`) перетворює коротке ім'я в IP-адресу на рівні системної бібліотеки `glibc` (`getaddrinfo`), але файл `~/.ssh/config` до моменту підключення нічого не знає про кінцевий домен. Через це неможливо призначити специфічні ключі автентифікації, бастіони чи параметри безпеки для конкретних зон (наприклад, `*.eu-central.corp` проти `*.us-east.corp`).

Механізм канонізації OpenSSH переносить процедуру розгортання доменів безпосередньо у внутрішній рушій конфігурації клієнта.

##### Алгоритм ітеративного пошуку суфіксів

Коли увімкнено `CanonicalizeHostname yes`, клієнт виконує такі перевірки:

1. **Перевірка ліміту крапок (`CanonicalizeMaxDots`):**
   Клієнт підраховує кількість крапок у введеному користувачем рядку. Якщо введено `srv01` (0 крапок) або `srv01.db` (1 крапка при дефолтному `CanonicalizeMaxDots 1`), ім'я підлягає канонізації. Якщо введено `srv01.prod.internal.corp` (3 крапки), ім'я визнається повним FQDN і одразу перевіряється в DNS без додавання суфіксів.
2. **Ітеративне конструювання кандидатів:**
   Клієнт послідовно перебирає список доменів із директиви `CanonicalDomains`:
   - Спроба 1: `srv01` + `.prod.datacenter.internal` → виклик `getaddrinfo("srv01.prod.datacenter.internal")`.
   - Спроба 2: `srv01` + `.staging.datacenter.internal` → у разі невдачі першої.
   - Спроба 3: `srv01` + `.corp.net`.
3. **Обробка та валідація CNAME-записів (`CanonicalizePermittedCNAMEs`):**
   Якщо DNS-сервер повертає канонічний псевдонім (CNAME), зловмисник, що контролює локальний DNS, може перенаправити клієнта на підконтрольний хост для викрадення публічного ключа хоста або експлуатації вразливостей. Директива `CanonicalizePermittedCNAMEs` задає жорсткі межі довіри:
   ```sshconfig
   CanonicalizePermittedCNAMEs *.corp.example.com:*.dmz.example.com,*.internal.net:none
   ```
   Правило дозволяє CNAME-перенаправлення лише у випадку, якщо вихідне ім'я відповідає лівій частині правила (`*.corp.example.com`), а цільовий FQDN — правій частині (`*.dmz.example.com`). Значення `none` повністю забороняє використання CNAME для вказаного домену.
4. **Повернення до початкового стану (`CanonicalizeFallbackLocal`):**
   Якщо жоден із доменів не дав валідного запису `A` чи `AAAA`, при `CanonicalizeFallbackLocal yes` клієнт повертає початковий рядок `srv01`, дозволяючи системному резолверу ОС або статичним записам `/etc/hosts` спробувати обробити запит.

##### Продакшен-конфігурація багаторівневої канонізації

```sshconfig
# 1. Глобальні параметри канонізації
Host *
    CanonicalizeHostname yes
    CanonicalDomains prod.eu.corp.internal staging.eu.corp.internal mgmt.corp.internal
    CanonicalizeMaxDots 1
    CanonicalizeFallbackLocal yes
    CanonicalizePermittedCNAMEs *.corp.internal:*.dmz.corp.internal

# 2. Правила для робочих серверів після канонізації (Прохід 2)
Match canonical host *.prod.eu.corp.internal
    User ops-admin
    ProxyJump bastion-eu.corp.com:2222
    IdentityFile ~/.ssh/id_ed25519_prod_eu
    CheckHostIP yes

Match canonical host *.staging.eu.corp.internal
    User dev-user
    ProxyJump bastion-dev.corp.com:22
    IdentityFile ~/.ssh/id_ed25519_staging

# 3. Фінальні політики ізоляції (Прохід 3)
Match final host *.prod.eu.corp.internal
    IdentitiesOnly yes
    ServerAliveInterval 15
    ServerAliveCountMax 3
```

### Надійність транспорту, таймінги та довіра до хостів

| Директива | Дозволені значення | Дефолт | Призначення та поведінка |
|---|---|---|---|
| `ServerAliveInterval` | ціле число (секунди) | `0` | Інтервал надсилання контрольних пакетів через шифрований канал SSH (`SSH_MSG_GLOBAL_REQUEST`) для підтримки активності таблиць трансляції NAT та виявлення мертвого сервера. Значення `0` вимикає опитування. |
| `ServerAliveCountMax` | ціле число | `3` | Гранична кількість поспіль непідтверджених запитів `ServerAliveInterval`, після якої клієнт вважає з'єднання розірваним та аварійно завершує процес із кодом помилки `255`. |
| `TCPKeepAlive` | `yes`, `no` | `yes` | Надсилання keepalive зондів на рівні протоколу TCP операційної системи (`SO_KEEPALIVE`). |
| `ConnectTimeout` | ціле число (секунди) | `0` (системний) | Граничний таймаут встановлення TCP-з'єднання та первинного обміну SSH-банерами (застосовується окремо до кожної IP-адреси з DNS-відповіді). |
| `ConnectionAttempts` | ціле число | `1` | Кількість спроб перебору всього пулу IP-адрес хоста перед поверненням фатальної помилки. |
| `StrictHostKeyChecking` | `yes`, `no`, `ask`, `accept-new`, `off` | `ask` | Політика реакції на нові або змінені відбитки серверів у `known_hosts`. `accept-new` автоматично записує нові ключі, але блокує з'єднання при зміні існуючих. `yes` вимагає суворої попередньої наявності ключа. |
| `UserKnownHostsFile` | список шляхів | `~/.ssh/known_hosts` | Файл(и) бази відбитків довірених хостів користувача. Значення `/dev/null` вимикає збереження. |
| `GlobalKnownHostsFile` | список шляхів | `/etc/ssh/ssh_known_hosts` | Загальносистемна база довірених хостів. |
| `CheckHostIP` | `yes`, `no` | `no` | Додатково перевіряє IP-адресу сервера у файлі `known_hosts` для захисту від підміни DNS. |
| `HashKnownHosts` | `yes`, `no` | `no` | Хешує імена хостів та IP-адреси під час запису до `known_hosts` для захисту від зчитування інфраструктури зловмисником. |
| `UpdateHostKeys` | `yes`, `no`, `ask` | `no` | Автоматично оновлює локальний файл `known_hosts`, якщо сервер повідомляє про ротацію своїх відкритих ключів за протоколом Hostkey Update (RFC 8332). |
| `LogLevel` | `QUIET`, `FATAL`, `ERROR`, `INFO`, `VERBOSE`, `DEBUG1`, `DEBUG2`, `DEBUG3` | `INFO` | Рівень деталізації діагностичних службових повідомлень клієнта. |
| `Ciphers` | перелік алгоритмів | див. опис | Дозволений перелік симетричних шифрів сеансу (`chacha20-poly1305@openssh.com`, `aes256-gcm@openssh.com`, `aes128-gcm@openssh.com`). |
| `KexAlgorithms` | перелік алгоритмів | див. опис | Дозволені алгоритми обміну сеансовими ключами (наприклад, `curve25519-sha256`, `diffie-hellman-group16-sha512`). |
| `HostkeyAlgorithms` | перелік алгоритмів | див. опис | Дозволені алгоритми перевірки автентичності хоста (наприклад, `ssh-ed25519`, `rsa-sha2-512`). |

#### Конфігурації високої надійності транспорту: Keepalive, таймаути та стійкість з'єднань

Мережеві з'єднання SSH піддаються впливу трьох критичних факторів нестабільності: скидання трансляцій маршрутизаторами NAT / Stateful Firewall, зависання віддалених процесів демона та тривалі таймаути підключення при відмові окремих мережевих вузлів.

##### Механіка прикладного Keepalive (ServerAliveInterval + ServerAliveCountMax)

Прикладний механізм контролю активності реалізовано всередині протоколу SSH Connection Protocol (RFC 4254). Клієнт веде внутрішній лічильник `server_alive_count` та таймер бездіяльності:

1. **Формування запиту:** Після закінчення `ServerAliveInterval` секунд без надходження будь-яких пакетів від сервера клієнт формує та надсилає всередині шифрованого тунелю повідомлення `SSH_MSG_GLOBAL_REQUEST` (числовий код `80`):
   ```text
   byte    80                           # SSH_MSG_GLOBAL_REQUEST
   string  "keepalive@openssh.com"      # Ідентифікатор запиту
   boolean 1                            # want_reply = true (вимагати підтвердження)
   ```
2. **Обробка відповіді:**
   Серверний демон `sshd`, отримавши цей пакет, зобов'язаний повернути відповідь:
   - `SSH_MSG_REQUEST_SUCCESS` (код `81`) або `SSH_MSG_REQUEST_FAILURE` (код `82`).
   
   Обидва коди є юридично валідними: для клієнта важливий сам факт отримання криптографічно підтвердженого пакета з протилежного боку, що засвідчує життєздатність процесу сервера. При отриманні будь-якої відповіді клієнт скидає лічильник `server_alive_count = 0`.
3. **Діагностика обриву (Dead Peer Detection):**
   Якщо відповідь не надходить, лічильник `server_alive_count` збільшується на `1`. Щойно лічильник досягає значення `ServerAliveCountMax` (за замовчуванням `3`), клієнт OpenSSH констатує безповоротний обрив каналу, негайно перериває TCP-сеанс, очищає виділені ресурси та завершує роботу процесу з кодом `255`:
   `Timeout, server not responding.`

##### Порівняння механізмів: ServerAlive проти TCPKeepAlive

| Критерій порівняння | Прикладний `ServerAliveInterval` | Системний `TCPKeepAlive` |
|---|---|---|
| **Рівень моделі OSI** | Рівень застосунків (Application Layer L7) усередині шифрованого SSH-сеансу. | Транспортний рівень (Transport Layer L4) у стеку ядра операційної системи. |
| **Системний виклик** | Внутрішній таймер OpenSSH у циклі мультиплексування подій (`poll()` / `select()`). | Сокетна опція `setsockopt(fd, SOL_SOCKET, SO_KEEPALIVE, &1, sizeof(int))`. |
| **Реакція на зависання процесу sshd** | **Виявляє:** якщо серверний процес `sshd` заблокований у deadlock або завис на дисковому I/O, він не може надіслати `SSH_MSG_REQUEST_*`, і клієнт закриває сесію. | **Не виявляє (хибний статус «живий»):** ядро віддаленого сервера продовжує самостійно відповідати на TCP ACK-зонди навіть у випадку повної смерті процесу `sshd`. |
| **Робота через Stateful NAT / Firewalls** | **Ефективна:** пакети надсилаються з налаштованим інтервалом (наприклад, кожні 15–30 с), постійно освіжаючи таймери в таблицях conntrack міжмережевих екранів. | **Неефективна за замовчуванням:** системний параметр Linux `tcp_keepalive_time` зазвичай становить `7200` секунд (2 години). NAT скидає стан через 300–600 секунд. |
| **Підтримка шифрування** | Пакет зашифровано сесійним симетричним ключем сеансу (неможливо сфальсифікувати зловмиснику в мережі). | Відкриті службові TCP ACK сегменти без корисного навантаження. |

##### Таймаути встановлення з'єднання (ConnectTimeout та ConnectionAttempts)

Під час ініціалізації сеансу клієнт `ssh` переводить сокет у неблокуючий режим (`O_NONBLOCK`) та ініціює виклик `connect()`:

- **Механіка `ConnectTimeout`:**
  Клієнт очікує завершення фази TCP 3-Way Handshake за допомогою виклику `poll()` або `select()` із таймаутом `ConnectTimeout * 1000` мілісекунд. Крім того, цей самий таймаут обмежує фазу первинного обміну банерами версій (SSH Version Exchange / рядок `SSH-2.0-...`).
- **Багатоадресний перебір (Multi-Homed DNS & Happy Eyeballs):**
  Якщо DNS-запит повертає кілька IP-адрес (наприклад, два IPv6 та два IPv4 записи), OpenSSH застосовує `ConnectTimeout` **до кожної окремої IP-адреси послідовно**. Якщо встановлено `ConnectTimeout 10`, а хост має 4 недоступні IP-адреси, загальний час очікування до повернення помилки становитиме `40` секунд.
- **Директива `ConnectionAttempts M`:**
  Задає кількість повних циклів спроб перебору всього пулу IP-адрес. Використовується в автоматизованих сценаріях, коли цільовий сервер може перебувати в процесі планового перезавантаження.

##### Інженерні шаблони конфігурації під типові сценарії

```sshconfig
# Шаблон 1: CI/CD автоматизація та неінтерактивні скрипти (Fail-Fast)
Host ci-runner-*
    ConnectTimeout 10
    ConnectionAttempts 2
    ServerAliveInterval 10
    ServerAliveCountMax 2
    TCPKeepAlive yes
    StrictHostKeyChecking accept-new
    BatchMode yes

# Шаблон 2: Довгоживучі віддалені тунелі та фонові сесії ControlMaster
Host persistent-tunnel-*
    ServerAliveInterval 20
    ServerAliveCountMax 3
    TCPKeepAlive yes
    ControlMaster auto
    ControlPersist 8h
    ExitOnForwardFailure yes

# Шаблон 3: Нестабільні канали зв'язку з високим jitter (Starlink / 4G / Wi-Fi)
Host mobile-station-*
    ConnectTimeout 15
    ConnectionAttempts 5
    ServerAliveInterval 30
    ServerAliveCountMax 6
    IPQoS throughput
```

## 4. Специфікація токенів підстановки (Specifier Tokens)

У значеннях директив `ControlPath`, `IdentityFile`, `ProxyCommand`, `LocalCommand`, `RemoteCommand`, `CertificateFile` та аргументах `Match exec` OpenSSH розгортає спеціальні токени підстановки:

| Токен | Значення підстановки | Приклад розгортання | Контексти застосування |
|---|---|---|---|
| `%h` | Цільовий хост (значення директиви `HostName`) | `10.0.1.50` або `db.prod.internal` | `ProxyCommand`, `ControlPath`, `LocalCommand` |
| `%p` | Цільовий TCP-порт з'єднання на сервері | `22` або `2222` | `ProxyCommand`, `ControlPath`, `LocalCommand` |
| `%r` | Віддалене ім'я користувача на сервері | `ubuntu` або `devops` | `ProxyCommand`, `ControlPath`, `IdentityFile` |
| `%n` | Вихідне ім'я хоста, введене в командному рядку CLI | `db-staging` | `ProxyCommand`, `ControlPath`, `LocalCommand` |
| `%u` | Локальне ім'я користувача на клієнті | `andrij` | `ControlPath`, `IdentityFile`, `LocalCommand` |
| `%d` | Шлях до домашнього каталогу локального користувача | `/home/andrij` | `IdentityFile`, `CertificateFile`, `ControlPath` |
| `%i` | Числовий локальний ідентифікатор користувача (UID) | `1000` | `ControlPath`, `LocalCommand` |
| `%l` | Повне локальне доменне ім'я машини клієнта (FQDN) | `workstation.corp.net` | `ProxyCommand`, `ControlPath` |
| `%L` | Перший сегмент локального імені машини (до першої крапки) | `workstation` | `ProxyCommand`, `ControlPath` |
| `%k` | Використовуваний ключ хоста сервера або його псевдонім | `ssh-ed25519` | `LocalCommand` |
| `%K` | Серіалізований base64 публічний ключ хоста сервера | `AAAAC3NzaC1lZDI1NTE5...` | `LocalCommand` |
| `%f` | Відбиток (fingerprint) ключа хоста сервера | `SHA256:7uX9z...` | `LocalCommand` |
| `%C` | Хеш SHA1 від конкатенації рядка `%l%h%p%r` (довжина 40 символів) | `a4b7c8d9e0f1...` | `ControlPath` |
| `%T` | Назва локального tun/tap мережевого інтерфейсу | `tun0` | `LocalCommand` |
| `%%` | Символ відсотка `%` | `%` | Усі директиви |

### Токен %C та обмеження довжини шляху UNIX-сокета

Стандарт POSIX для структури `sockaddr_un` обмежує довжину масиву шляху сокета `sun_path` величиною у **108 байтів** у Linux (та 104 байти в деяких BSD-системах):

```text
struct sockaddr_un {
    sa_family_t sun_family; /* AF_UNIX */
    char sun_path[108];      /* Максимальний розмір шляху сокета */
};
```

Якщо шлях користувача містить довгі імена каталогів та повні FQDN адреси хостів:
`~/.ssh/sockets/devops-service-account@database-cluster-primary-datacenter-east.corp.internal:2222`
Загальна довжина перевищує 108 байтів, через що системний виклик ядра `bind()` завершується збоєм `ENAMETOOLONG`.

Використання токена `%C` розв'язує цю проблему:
```sshconfig
Host *
    ControlPath ~/.ssh/S-%C
```
Токен `%C` стискає довільну комбінацію параметрів у фіксований 40-символьний рядок, гарантуючи, що довжина шляху сокета завжди перебуває в межах лімітів ядра.

## 5. Довідник утиліти керування ключами ssh-add

Утиліта `ssh-add` забезпечує інтерфейс командного рядка для завантаження, перегляду, вивантаження та блокування ключів у пам'яті працюючого демона `ssh-agent`. Вона взаємодіє з сокетом, вказаним у змінній `$SSH_AUTH_SOCK`.

### Таблиця параметрів утиліти ssh-add

| Прапорець | Аргумент | Опис операції та системна поведінка |
|---|---|---|
| *(без прапорців)* | `[шлях_до_ключа]` | Завантажує стандартні ключі за замовчуванням (`~/.ssh/id_rsa`, `~/.ssh/id_ed25519` тощо) або вказаний файл закритого ключа до пам'яті агента, запитуючи парольну фразу. |
| `-l` | — | Виводить список завантажених у даний момент ключів: бітовий розмір, хеш відбитка (fingerprint), текстовий коментар та тип алгоритму. Код повернення: `0` — є ключі, `1` — агент порожній, `2` — зв'язок із агентом відсутній. |
| `-L` | — | Експортує публічні частини всіх завантажених ключів у текстовому форматі `authorized_keys`. |
| `-d` | `[шлях_до_файлу]` | Видаляє конкретний ключ із пам'яті демона. Можна передавати шлях як до закритого, так і до відкритого (`.pub`) файлу ключа. |
| `-D` | — | Повністю очищає пам'ять демона `ssh-agent`, видаляючи абсолютно всі завантажені ключі та сертифікати із зануленням пам'яті (`explicit_bzero`). |
| `-t` | `час` (`s`, `m`, `h`, `d`, `w`) | Встановлює обмеження часу життя ключа в пам'яті (`SSH_AGENT_CONSTRAIN_LIFETIME`). Приклади: `-t 1800` (1800 секунд), `-t 30m` (30 хвилин), `-t 8h` (8 годин), `-t 1d` (1 день). Після завершення часу ключ вивантажується автоматично. |

| `-s` | `шлях_до_бібліотеки` | Завантажує апаратні ключі через динамічну бібліотеку PKCS#11 або Security Key провайдер (наприклад, `ssh-add -s /usr/lib/x86_64-linux-gnu/opensc-pkcs11.so`). |
| `-e` | `шлях_до_бібліотеки` | Вивантажує всі апаратні ключі, надані вказаним PKCS#11 модулем. |
| `-K` | — | Завантажує всі резидентні ключі FIDO2 (discoverable credentials) з підключеного апаратного токена безпеки в пам'ять агента. |
| `-k` | — | Завантажує стандартні ключі з диска, пропускаючи обробку резидентних ключів смарт-карток. |
| `-T` | `шлях_до_pubkey` | Тестує, чи завантажений у даний момент закритий ключ, що відповідає вказаному файлу відкритого ключа, та чи готовий він до підпису. |
| `-h` | `хости_обмеження` | Встановлює обмеження призначення (OpenSSH 8.9+ destination constraint). Ключ дозволено використовувати лише для з'єднань через зазначені вузли. |
| `-E` | `md5` / `sha256` | Задає алгоритм хешування для відображення відбитків ключів у виводі команди `-l`. |
| `-q` | — | Тихий режим (пригнічує стандартні інформаційні повідомлення). |
| `-v` | — | Детальний діагностичний режим (виводить налагоджувальні повідомлення про взаємодію з сокетом агента). |

### Коди повернення утиліти ssh-add (Exit Codes)

Для використання у скриптах автоматизації та CI/CD пайплайнах `ssh-add` повертає такі числові коди:
- **`0` (Успіх):** Операцію виконано успішно (ключі завантажено/видалено, або команда `ssh-add -l` виявила хоча б один завантажений ключ).
- **`1` (Помилка / Порожньо):** Команда `ssh-add -l` не виявила жодного ключа в пам'яті (агент активний, але порожній), або сталася помилка валідації/додавання ключа.
- **`2` (Немає зв'язку):** Зв'язок із демоном `ssh-agent` відсутній (змінна `$SSH_AUTH_SOCK` не встановлена, вказаний сокет не існує або системний виклик `connect()` повернув помилку доступу `EACCES`/`ENOENT`).

#### Робота з апаратними модулями PKCS#11 через ssh-add

Команда `ssh-add -s <шлях_до_бібліотеки>` ініціює завантаження ключів апаратного токена безпосередньо у пам'ять `ssh-agent`:

1. Утиліта `ssh-add` перевіряє наявність термінала або викликає `SSH_ASKPASS` для зчитування PIN-коду смарт-картки.
2. Відправляє в UNIX-сокет `$SSH_AUTH_SOCK` двійковий пакет `SSH2_AGENTC_ADD_SMARTCARD_KEY` (код `20`) або `SSH2_AGENTC_ADD_SMARTCARD_KEY_CONSTRAINED` (код `26` за наявності прапорців `-t` чи `-c`).
3. Демон `ssh-agent` відкриває спільну бібліотеку викликом `dlopen()`, виконує вхід `C_Login()` із введеним PIN-кодом, зчитує всі відкриті сертифікати й відкриті ключі та додає їх до активної таблиці ключів.
4. Після успішного завантаження команда `ssh-add -l` відображає відкриті ключі токена, де замість шляху до файлу вказується шлях до PKCS#11 провайдера:
   ```text
   3072 SHA256:7uX9z... /usr/lib/x86_64-linux-gnu/opensc-pkcs11.so (RSA)
   256 SHA256:9vK1w... /usr/lib/x86_64-linux-gnu/libykcs11.so (ECDSA)
   ```
5. Для вивантаження всіх ключів конкретного PKCS#11 модуля виконується команда `ssh-add -e <шлях_до_бібліотеки>`, яка надсилає в сокет повідомлення `SSH2_AGENTC_REMOVE_SMARTCARD_KEY` (код `21`), змушуючи агент закрити сесію `C_CloseSession` та виконати `dlclose()`.

## 6. Змінні середовища оточення клієнта та агента

| Змінна оточення | Опис призначення та системний вплив |
|---|---|
| `SSH_AUTH_SOCK` | Містить абсолютний шлях до сокета домену UNIX (`AF_UNIX`), через який клієнти зв'язуються з процесом `ssh-agent`. Якщо змінна відсутня або порожня, клієнт вважає, що агент не запущено. |
| `SSH_AGENT_PID` | Зберігає числовий ідентифікатор процесу (PID) фонового демона `ssh-agent`. Використовується командою `ssh-agent -k` для відправки сигналу `SIGTERM` процесу демона під час завершення сеансу. |
| `SSH_ASKPASS` | Вказує абсолютний шлях до зовнішньої графічної або термінальної програми введення секретів (наприклад, `/usr/bin/ssh-askpass`, `/usr/bin/ksshaskpass`, `zenity`). Викликається, коли у клієнта відсутній керівний TTY, або при використанні прапорця підтвердження `ssh-add -c`. |
| `SSH_ASKPASS_REQUIRE` | Керує політикою примусового виклику `SSH_ASKPASS`: `never` (ніколи не викликати, завершуватися з помилкою без TTY), `prefer` (надавати перевагу askpass перед терміналом), `force` (викликати askpass завжди, навіть якщо присутній активний керівний термінал TTY). |
| `SSH_CONNECTION` | Автоматично експортується `sshd` у віддаленому сеансі: містить чотири розділені пробілами поля `<client_ip> <client_port> <server_ip> <server_port>`. |
| `SSH_CLIENT` | Застарілий формат змінної сеансу: містить три поля `<client_ip> <client_port> <server_port>`. |
| `SSH_TTY` | Вказує шлях до пристрою псевдотермінала (`/dev/pts/N`), виділеного поточному віддаленому сеансу. Якщо сеанс запущено без PTY (наприклад, через `ssh -N` або `ssh target command`), змінна не встановлюється. |
| `SSH_ORIGINAL_COMMAND` | Встановлюється демоном `sshd`, якщо в `authorized_keys` або блоці `Match` налаштовано директиву `ForceCommand`. Містить первинний рядок команди, яку намагався виконати клієнт. |
| `SSH_USER_AUTH` | Фіксує метод автентифікації, успішно пройдений користувачем під час підключення до сервера. |

### Протокол взаємодії та системний життєвий цикл SSH_ASKPASS

Змінні `SSH_ASKPASS` та `SSH_ASKPASS_REQUIRE` керують неінтерактивним та графічним введенням секретів: паролів облікових записів, парольних фраз закритих ключів, PIN-кодів PKCS#11 токенів та інтерактивних підтверджень операцій цифрового підпису (`ssh-add -c`).

#### Алгоритм вибору джерела введення

Під час потреби запиту секрету клієнт `ssh` або демон `ssh-agent` оцінює системне оточення:

1. Якщо змінна `SSH_ASKPASS_REQUIRE` встановлена у значення `force` (або `prefer` за відсутності TTY) і змінна `SSH_ASKPASS` містить валідний виконуваний файл, процес безумовно викликає зовнішню програму askpass.
2. Якщо `SSH_ASKPASS_REQUIRE` має значення `never`, запит виконується виключно через системний TTY. Якщо керівний термінал відсутній (наприклад, у фоновому скрипті cron чи демоні), операція негайно переривається з фатальною помилкою без відкриття діалогових вікон.
3. Якщо `SSH_ASKPASS_REQUIRE` не задано (стандартна поведінка):
   - Якщо процес має активний керівний термінал (`isatty(STDIN_FILENO)` або вдалося відкрити пристрій `/dev/tty`), секрет запитується через термінал;
   - Якщо відкрити `/dev/tty` неможливо (запуск із GUI-лаунчера, сервіс systemd), перевіряється наявність змінної `SSH_ASKPASS` та активного графічного дисплея (`DISPLAY` для X11 або `WAYLAND_DISPLAY`).

#### Системний життєвий цикл процесу askpass

```
   Процес OpenSSH (ssh / ssh-agent)                 Процес SSH_ASKPASS (ksshaskpass / zenity)
┌───────────────────────────────────────┐          ┌──────────────────────────────────────────┐
│ 1. pipe(pipefd)                       │          │                                          │
│ 2. fork() ────────────────────────────┼──────────┼──► [Новий дочірній процес]               │
│                                       │          │ 3. dup2(pipefd[1], STDOUT_FILENO)        │
│                                       │          │ 4. close(STDIN_FILENO) -> /dev/null      │
│                                       │          │ 5. execv(askpass, [prompt_str])          │
│                                       │          │ 6. Графічне вікно: введення PIN / пароля │
│ 7. read(pipefd[0], secret_buf) ◄──────┼──────────┼─── 8. write(STDOUT, secret) + exit(0)    │
│ 9. explicit_bzero(secret_buf)         │          └──────────────────────────────────────────┘
│ 10. waitpid(pid)                      │
└───────────────────────────────────────┘
```

1. **Ізоляція каналів вводу/виводу:** Батьківський процес створює односпрямований UNIX-пайп `pipe(pipefd)`.
2. **Форкінг:** Викликається `fork()`. У дочірньому процесі дескриптор запису пайпа дублюється на `STDOUT_FILENO` через `dup2()`, а стандартний ввід від'єднується від термінала й перенаправляється на `/dev/null` для запобігання взаємному блокуванню введення.
3. **Виклик виконуваного файлу:** Дочірній процес викликає `execv()`, передаючи рядок запрошення як перший аргумент командного рядка (`argv[1]`): наприклад, `"Enter PIN for 'YubiKey PIV #12345678': "`. Якщо задано `SSH_ASKPASS_REQUIRE=force`, додатково передається прапорець контексту.
4. **Зчитування та очищення пам'яті:** Батьківський процес зчитує секрет із `pipefd[0]`, закриває дескриптори, відсікає завершальний символ нового рядка `\n` і після передачі секрету криптопровайдеру негайно перезаписує буфер нулями за допомогою функції `explicit_bzero()`.

## 7. Бінарний протокол зв'язку OpenSSH Agent

Комунікація між клієнтом (`ssh`, `ssh-add`) та агентом (`ssh-agent`) здійснюється локально через потоковий сокет домену UNIX (`AF_UNIX`, `SOCK_STREAM`), шлях до якого зберігається в `$SSH_AUTH_SOCK`.

### Формат обрамлення кадру (Length-Prefixed Framing)

Оскільки сокет `SOCK_STREAM` передає потік байтів без збереження меж повідомлень, протокол використовує явний 4-байтовий префікс довжини. Усі багатобайтові числа передаються у мережевому порядку байтів (Big-Endian / Most Significant Byte First):

```
+------------------------------------+------------------+------------------------------------+
|  Довжина корисного навантаження L  |  Код типу кадру  |       Тіло повідомлення            |
|       (uint32, 4 байти)            | (uint8, 1 байт)  |     (L - 1 байтів згідно з кодом)  |
+------------------------------------+------------------+------------------------------------+
```

- **`packet_length` (uint32):** Число `L` визначає кількість байтів, що слідують після поля довжини (1 байт коду типу + корисні дані).
- **`message_type` (uint8):** Однобайтний код операції або відповіді.
- **`payload` (L - 1 байтів):** Серіалізовані структури даних.

### Базові типи серіалізації SSH Wire Protocol

- `byte` (1 байт): 8-бітне беззнакове число.
- `uint32` (4 байти): 32-бітне беззнакове ціле число в порядку Big-Endian.
- `string` (4 + N байтів): префікс довжини `uint32` (значення N), за яким слідують рівно N сирих байтів даних (рядок UTF-8, бінарний блоб відкритого ключа, підпис чи challenge). Рядки **не містять** завершального нульового байта `\0`.
- `mpint` (4 + N байтів): ціле число довільної точності зі знаком у доповняльному коді (використовується в параметрах RSA).

### Реєстр кодів повідомлень протоколу

| Константа протоколу | Код (Dec) | Код (Hex) | Напрямок | Опис операції |
|---|---|---|---|---|
| `SSH_AGENT_FAILURE` | `5` | `0x05` | Агент → Клієнт | Операцію відхилено, помилка або операція заборонена |
| `SSH_AGENT_SUCCESS` | `6` | `0x06` | Агент → Клієнт | Запит на додавання/видалення/блокування виконано успішно |
| `SSH_AGENTC_REQUEST_IDENTITIES` | `11` | `0x0b` | Клієнт → Агент | Запит списку всіх завантажених відкритих ключів |
| `SSH_AGENT_IDENTITIES_ANSWER` | `12` | `0x0c` | Агент → Клієнт | Відповідь з масивом публічних ключів та коментарів |
| `SSH_AGENTC_SIGN_REQUEST` | `13` | `0x0d` | Клієнт → Агент | Запит на цифровий підпис блоку даних конкретним ключем |
| `SSH_AGENT_SIGN_RESPONSE` | `14` | `0x0e` | Агент → Клієнт | Відповідь, що містить сформований контейнер цифрового підпису |
| `SSH_AGENTC_ADD_IDENTITY` | `17` | `0x11` | Клієнт → Агент | Завантаження закритого ключа без додаткових обмежень |
| `SSH_AGENTC_REMOVE_IDENTITY` | `18` | `0x12` | Клієнт → Агент | Видалення одного закритого ключа за його публічним блобом |
| `SSH_AGENTC_REMOVE_ALL_IDENTITIES`| `19` | `0x13` | Клієнт → Агент | Повне вивантаження та занулення всіх ключів у пам'яті |
| `SSH_AGENTC_ADD_SMARTCARD_KEY` | `20` | `0x14` | Клієнт → Агент | Додавання ключів через бібліотеку смарт-картки PKCS#11 |
| `SSH_AGENTC_REMOVE_SMARTCARD_KEY` | `21` | `0x15` | Клієнт → Агент | Вивантаження ключів смарт-картки за шляхом до бібліотеки |
| `SSH_AGENTC_LOCK` | `22` | `0x16` | Клієнт → Агент | Блокування пам'яті агента парольною фразою |
| `SSH_AGENTC_UNLOCK` | `23` | `0x17` | Клієнт → Агент | Розблокування пам'яті агента введеною парольною фразою |
| `SSH_AGENTC_ADD_ID_CONSTRAINED` | `25` | `0x19` | Клієнт → Агент | Додавання ключа з обмеженнями (lifetime, confirmation) |
| `SSH_AGENTC_ADD_SMARTCARD_KEY_CONSTRAINED` | `26` | `0x1a` | Клієнт → Агент | Додавання смарт-картки з обмеженнями lifetime/confirm |
| `SSH_AGENTC_EXTENSION` | `27` | `0x1b` | Клієнт → Агент | Виклик вендорного розширення OpenSSH (session-bind тощо) |
| `SSH_AGENT_EXTENSION_FAILURE` | `28` | `0x1c` | Агент → Клієнт | Невідоме або непідтримуване розширення протоколу |

### Детальна структура кадру основних операцій

#### 1. Отримання списку ключів (`REQUEST_IDENTITIES` → `IDENTITIES_ANSWER`)

Запит клієнта `SSH2_AGENTC_REQUEST_IDENTITIES` (код `11`) не містить корисного навантаження (загальна довжина кадру 1 байт):
`[00 00 00 01] [0b]`

Відповідь агента `SSH2_AGENT_IDENTITIES_ANSWER` (код `12`):
```text
uint32  nkeys         # Кількість завантажених ключів у пам'яті агента
# Далі nkeys разів послідовно повторюється структура:
  string  key_blob    # Бінарний серіалізований відкритий ключ (uint32 len + raw bytes)
  string  comment     # Текстовий коментар ключа в кодуванні UTF-8 (uint32 len + bytes)
```

Внутрішня структура відкритого блоба `key_blob`:
- **Для Ed25519 (`ssh-ed25519`):**
  - `string "ssh-ed25519"` (11 байтів ASCII);
  - `string pubkey_bytes` (32 байти відкритої точки кривої Curve25519).
  - Загальний розмір стандартного публічного блоба Ed25519 становить рівно 51 байт.
- **Для RSA (`ssh-rsa`):**
  - `string "ssh-rsa"` (7 байтів ASCII);
  - `mpint e` (відкрита експонента, зазвичай 3 байти `0x010001` для 65537);
  - `mpint n` (модуль RSA: 256 байтів для 2048 біт або 512 байтів для 4096 біт).
- **Для ECDSA (`ecdsa-sha2-nistp256`):**
  - `string "ecdsa-sha2-nistp256"`;
  - `string "nistp256"` (назва кривої);
  - `string Q` (відкрита точка кривої у форматі ANSI X9.62, 65 байтів).
- **Для Security Key FIDO2 (`sk-ssh-ed25519@openssh.com`):**
  - `string "sk-ssh-ed25519@openssh.com"`;
  - `string pubkey_bytes` (32 байти);
  - `string application` (ідентифікатор застосунку RP ID, наприклад `"ssh:"`).

#### 2. Запит та отримання цифрового підпису (`SIGN_REQUEST` → `SIGN_RESPONSE`)

Запит клієнта `SSH2_AGENTC_SIGN_REQUEST` (код `13`):
```text
string  key_blob      # Відкритий ключ, закрита пара якого має накласти підпис
string  data          # Дані виклику (challenge від sshd, що включає Session ID)
uint32  flags         # Бітові прапорці модифікації алгоритму підпису
```

##### Бітові прапорці підпису (`flags`)
- `0x00000000`: Стандартний підпис за замовчуванням (для RSA використовує застарілий SHA-1 підпис `ssh-rsa`).
- `0x00000002` (`SSH_AGENT_RSA_SHA2_256`): Вимагає накласти підпис RSA за схемою PKCS#1 v1.5 з гешуванням SHA-256 (ідентифікатор формату `rsa-sha2-256`).
- `0x00000004` (`SSH_AGENT_RSA_SHA2_512`): Вимагає накласти підпис RSA з гешуванням SHA-512 (ідентифікатор формату `rsa-sha2-512`).

*(Для ключів Ed25519 поле `flags` завжди передається як `0`, оскільки стандарт RFC 8032 жорстко закріплює внутрішнє гешування SHA-512).*

Відповідь агента `SSH2_AGENT_SIGN_RESPONSE` (код `14`):
```text
string  signature_blob   # Серіалізований контейнер підпису
```

Структура всередині `signature_blob`:
1. `string format`: Назва алгоритму підпису (наприклад, `"ssh-ed25519"`, `"rsa-sha2-256"`, `"rsa-sha2-512"`).
2. `string raw_sig`: Сирі байти підпису (для Ed25519 це 64 байти: конкатенація точки R та скаляра S).

#### 3. Додавання закритого ключа (`ADD_IDENTITY` / `ADD_ID_CONSTRAINED`)

Запит `SSH2_AGENTC_ADD_IDENTITY` (код `17`) передає закритий ключ у незашифрованому вигляді для завантаження в пам'ять агента:

- **Формат тіла ключа Ed25519:**
  ```text
  string  "ssh-ed25519"
  string  pubkey_bytes   # 32 байти відкритого ключа
  string  privkey_bytes  # 64 байти (32 байти seed/private + 32 байти public)
  string  comment        # Текстовий коментар ключа в UTF-8
  ```

- **Формат тіла ключа RSA:**
  ```text
  string  "ssh-rsa"
  mpint   n              # Модуль RSA
  mpint   e              # Відкрита експонента
  mpint   d              # Закрита експонента
  mpint   iqmp           # Коефіцієнт CRT (мультиплікативна інверсія q mod p)
  mpint   p              # Перший простий дільник модуля
  mpint   q              # Другий простий дільник модуля
  string  comment        # Текстовий коментар ключа
  ```

- **Формат тіла ключа ECDSA:**
  ```text
  string  "ecdsa-sha2-nistp256"
  string  "nistp256"
  string  Q              # Публічна точка еліптичної кривої
  mpint   d              # Закритий скалярний ключ
  string  comment        # Текстовий коментар ключа
  ```

- **Формат тіла ключа FIDO2/U2F (`sk-ssh-ed25519@openssh.com`):**
  ```text
  string  "sk-ssh-ed25519@openssh.com"
  string  pubkey_bytes   # 32 байти відкритого ключа
  string  application    # Ідентифікатор RP (наприклад, "ssh:")
  byte    flags          # Прапорці FIDO (User Presence, Verification)
  string  key_handle     # Дескриптор ключа токена
  string  reserved       # Порожній бінарний рядок
  string  comment        # Текстовий коментар ключа
  ```

При успіху агент повертає `SSH_AGENT_SUCCESS` (код `6`), при збої — `SSH_AGENT_FAILURE` (код `5`).

#### 4. Видалення ключів (`REMOVE_IDENTITY` та `REMOVE_ALL_IDENTITIES`)

- **`SSH2_AGENTC_REMOVE_IDENTITY` (код `18`):**
  ```text
  string  key_blob       # Серіалізований відкритий блоб ключа, що підлягає вивантаженню
  ```
  Агент знаходить закритий ключ за його публічним блобом, занулює пам'ять закритого ключа (`explicit_bzero`) та повертає `SSH_AGENT_SUCCESS`. Якщо відповідний ключ відсутній у пам'яті, агент повертає `SSH_AGENT_FAILURE`.

- **`SSH2_AGENTC_REMOVE_ALL_IDENTITIES` (код `19`):**
  Не містить корисного навантаження. Демон `ssh-agent` негайно занулює пам'ять усіх збережених ключів та сертифікатів і повертає `SSH_AGENT_SUCCESS`.

#### 5. Керування смарт-картками PKCS#11 (`ADD_SMARTCARD_KEY` / `REMOVE_SMARTCARD_KEY`)

Взаємодія з апаратними токенами через протокол агента дозволяє клієнтам використовувати апаратні ключі без прямого завантаження PKCS#11 бібліотек у власний адресний простір.

##### Кадр додавання модуля PKCS#11 (`SSH2_AGENTC_ADD_SMARTCARD_KEY` / `SSH2_AGENTC_ADD_SMARTCARD_KEY_CONSTRAINED`)

- **`SSH2_AGENTC_ADD_SMARTCARD_KEY` (код `20`):**
  ```text
  string  provider_path  # Абсолютний шлях до PKCS#11 бібліотеки на диску
  string  pin            # PIN-код доступу до токена/смарт-картки в кодуванні UTF-8
  ```

- **`SSH2_AGENTC_ADD_SMARTCARD_KEY_CONSTRAINED` (код `26`):**
  ```text
  string  provider_path  # Абсолютний шлях до PKCS#11 бібліотеки
  string  pin            # PIN-код доступу до смарт-картки
  # Далі слідує один або кілька блоків обмежень:
    byte    constraint_type   # 0x01 = LIFETIME, 0x02 = CONFIRM, 0xff = EXTENSION
    [байти параметрів обмеження згідно з таблицею п. 7]
  ```

##### Внутрішня модель стану демона ssh-agent для PKCS#11

Коли демон `ssh-agent` отримує повідомлення `ADD_SMARTCARD_KEY`:
1. **Завантаження драйвера:** Демон викликає `dlopen(provider_path, RTLD_NOW)` та ініціалізує Cryptoki через `C_Initialize()`.
2. **Сканування слотів та сесій:** Демон знаходить усі активні слоти `slot_id` через `C_GetSlotList()`, відкриває сесії `C_OpenSession()` та авторизується викликом `C_Login(session, CKU_USER, pin, pin_len)`.
3. **Експорт відкритих ключів:** Демон виконує пошук об'єктів `CKO_PRIVATE_KEY` та відповідних сертифікатів `CKO_CERTIFICATE` / `CKO_PUBLIC_KEY`. Для кожного знайденого ключа конструюється публічний блоб OpenSSH (RSA, ECDSA або Ed25519), який додається до внутрішньої таблиці ідентичностей агента. Текстовий коментар ключа встановлюється рівним шляху до бібліотеки `provider_path` (або мітці токена).
4. **Обробка виклику SIGN_REQUEST:** Коли клієнт `ssh` надсилає запит підпису `SSH2_AGENTC_SIGN_REQUEST` для відкритого ключа, зареєстрованого як PKCS#11, демон:
   - Знаходить відповідний дескриптор відкритої сесії Cryptoki та дескриптор об'єкта `CKO_PRIVATE_KEY`;
   - Перевіряє наявність токена у зчитувачі (якщо карту було вилучено, `C_SignInit` повертає `CKR_DEVICE_REMOVED`, і агент відповідає клієнту кодом `SSH_AGENT_FAILURE`);
   - Викликає `C_SignInit()` та `C_Sign()`, отримуючи бінарний підпис безпосередньо з апаратного чипа;
   - Формує та повертає клієнту пакет `SSH2_AGENT_SIGN_RESPONSE`.
5. **Безпека PIN-коду в пам'яті:** Буфер, переданий клієнтом у полі `pin`, занулюється за допомогою `explicit_bzero()` одразу після виклику `C_Login()`. Якщо провайдер вимагає повторного логіну при наступних операціях, PIN кешується у заблокованій через `mlock()` пам'яті демона та знищується при отриманні `SSH2_AGENTC_REMOVE_SMARTCARD_KEY` чи вивантаженні за таймаутом.

##### Кадр вивантаження модуля PKCS#11 (`SSH2_AGENTC_REMOVE_SMARTCARD_KEY`)

- **`SSH2_AGENTC_REMOVE_SMARTCARD_KEY` (код `21`):**
  ```text
  string  provider_path  # Абсолютний шлях до модуля PKCS#11
  string  pin            # PIN-код (зазвичай передається порожнім рядком len=0)
  ```
  Демон `ssh-agent` знаходить усі зареєстровані ключі, пов'язані з `provider_path`, закриває активні сесії `C_CloseSession()`, викликає `C_Finalize()`, звільняє ресурси бібліотеки викликом `dlclose()` та повертає `SSH_AGENT_SUCCESS`. Якщо відповідний провайдер не був зареєстрований, повертається `SSH_AGENT_FAILURE`.

#### 6. Парольне блокування та розблокування агента (`LOCK` / `UNLOCK`)

- **`SSH2_AGENTC_LOCK` (код `22`):**
  ```text
  string  passphrase     # Парольна фраза блокування
  ```
  Агент переходить у заблокований стан. У заблокованому стані всі виклики `REQUEST_IDENTITIES` повертають порожній список (`nkeys = 0`), а будь-які операції підпису `SIGN_REQUEST` відхиляються кодом `SSH_AGENT_FAILURE`. Повертає `SSH_AGENT_SUCCESS` або `SSH_AGENT_FAILURE` (якщо агент уже заблоковано).

- **`SSH2_AGENTC_UNLOCK` (код `23`):**
  ```text
  string  passphrase     # Парольна фраза розблокування
  ```
  Якщо передана парольна фраза збігається з паролем блокування, демон відновлює штатний режим роботи та повертає `SSH_AGENT_SUCCESS`. У разі невірного пароля повертається `SSH_AGENT_FAILURE`.

#### 7. Обмеження під час додавання ключів (Key Constraints)

Під час надсилання повідомлення `SSH2_AGENTC_ADD_ID_CONSTRAINED` (код `25`) або `SSH2_AGENTC_ADD_SMARTCARD_KEY_CONSTRAINED` (код `26`) після тіла закритого ключа та коментаря слідує один або кілька байтів обмежень:

| Байт типу обмеження | Назва константи | Подальші параметри в пакеті |
|---|---|---|
| `1` (`0x01`) | `SSH_AGENT_CONSTRAIN_LIFETIME` | `uint32 seconds` — час у секундах, після закінчення якого ключ буде занулено та автоматично вивантажено з пам'яті. |
| `2` (`0x02`) | `SSH_AGENT_CONSTRAIN_CONFIRM` | Не має додаткових полів. Зобов'язує демон запитувати явне підтвердження людини через `SSH_ASKPASS` перед кожною операцією підпису цим ключем. |
| `3` (`0x03`) | `SSH_AGENT_CONSTRAIN_MAXSIGN` | `uint32 count` — максимальна кількість дозволених операцій підпису, після вичерпання якої ключ видаляється. |
| `255` (`0xff`) | `SSH_AGENT_CONSTRAIN_EXTENSION` | `string ext_name`, `string ext_data` — розширення обмежень (зокрема прив'язка до хостів призначення `restrict-destination-v00@openssh.com`). |

#### 8. Розширення протоколу (Protocol Extensions)

Запит `SSH2_AGENTC_EXTENSION` (код `27`) забезпечує стандартний механізм розширення функціональності OpenSSH Agent без порушення зворотної сумісності:

```text
string  extension_type   # Назва розширення (наприклад, "session-bind@openssh.com")
string  extension_data   # Бінарні параметри конкретного розширення
```

Якщо агент не підтримує запитане розширення, він відповідає повідомленням `SSH2_AGENT_EXTENSION_FAILURE` (код `28`). Якщо розширення підтримується, агент повертає або `SSH_AGENT_SUCCESS` (код `6`), або специфічну відповідь із результатами обробки.

##### Специфікація розширення session-bind@openssh.com

Розширення `session-bind@openssh.com` використовується для прив'язки ключа до конкретного ідентифікатора сеансу SSH (Session ID), що запобігає використанню ключа поза межами узгодженого з'єднання:

```text
string  "session-bind@openssh.com"
string  key_blob         # Відкритий блоб ключа, що зв'язується з сеансом
string  session_id       # Хеш обміну ключами H (Session ID сеансу SSH-транспорту)
string  host_key         # Публічний ключ цільового сервера
byte    is_forwarding    # 1 — якщо сеанс пересилається через агент, 0 — прямий сеанс
```

Коли клієнт реєструє сеансову прив'язку, демон `ssh-agent` фіксує відповідність пари `(key_blob, session_id)`. Під час наступних запитів `SSH2_AGENTC_SIGN_REQUEST` агент перевіряє, чи підписуваний блок виклику містить саме цей зареєстрований `session_id`. У разі невідповідності агент відхиляє операцію, запобігаючи використанню ключа на сторонніх з'єднаннях.

##### Специфікація обмеження restrict-destination-v00@openssh.com

Обмеження призначень передається всередині запиту `SSH2_AGENTC_ADD_ID_CONSTRAINED` (код `25`) з типом обмеження `SSH_AGENT_CONSTRAIN_EXTENSION` (`0xff`):

```text
byte    0xff                                   # Константа SSH_AGENT_CONSTRAIN_EXTENSION
string  "restrict-destination-v00@openssh.com" # Ідентифікатор розширення
string  ext_data                               # Серіалізований масив правил обмеження
```

Структура даних `ext_data`:
```text
uint32  constraint_count                       # Кількість ланцюжків правил призначення
# Далі constraint_count разів повторюється блок:
  string  from_host_keys                       # Масив блобів ключів хостів, з яких дозволено перехід
  string  to_host_keys                         # Масив блобів ключів цільових серверів призначення
  uint32  flags                                # Бітові прапорці (наприклад, 0x01 = обов'язкова наявність сеансу)
  string  reserved                             # Зарезервоване поле (порожній рядок)
```

Коли утиліта `ssh-add -h <key>` додає ключ із цим обмеженням, клієнт `ssh` перед кожним підписом надсилає підтвердження маршруту транзиту. Якщо проміжний або цільовий вузол не збігається з переліком `from_host_keys` / `to_host_keys`, `ssh-agent` відхиляє підпис з кодом `SSH_AGENT_FAILURE`.

## 8. Взаємодія із системними сервісами брелоків (Keyrings) та сторонніми агентами

Протокол OpenSSH Agent є стандартом de facto для керування криптографічними ключами в операційних системах сімейства UNIX та Windows. Сторонні менеджери паролів, графічні сервіси ключів та криптографічні підсистеми реалізують інтерфейс сервера протоколу агента, слухаючи сокет домену UNIX (`$SSH_AUTH_SOCK`) або системний іменований канал (Windows Named Pipe).

### 1. Демон GnuPG (gpg-agent) у режимі емуляції SSH-агента

Утиліта `gpg-agent` забезпечує керування секретними ключами OpenPGP та може виступати повноцінною заміною `ssh-agent`.

#### Конфігурація та змінні оточення
Для активації підтримки SSH у конфігураційний файл `~/.gnupg/gpg-agent.conf` додаються параметри:

```ini
# Увімкнення емуляції OpenSSH agent протоколу
enable-ssh-support

# Час життя розшифрованого ключа в кеші за замовчуванням (у секундах)
default-cache-ttl-ssh 1800

# Максимальний час життя ключа в кеші від моменту останнього введення PIN (у секундах)
max-cache-ttl-ssh 7200
```

#### Розміщення сокетів та експорт
За стандартом XDG демон `gpg-agent` створює виділений сокет для SSH-протоколу:
- У каталозі користувача `systemd`: `/run/user/<UID>/gnupg/S.gpg-agent.ssh`
- Або в домашньому каталозі: `~/.gnupg/S.gpg-agent.ssh`

Для підключення клієнта `ssh` до агента GnuPG у файлі `~/.bashrc` чи `~/.zshrc` виконується експорт:
```bash
unset SSH_AGENT_PID
if [ "${gnupg_SSH_AUTH_SOCK_by:-0}" -ne $$ ]; then
    export SSH_AUTH_SOCK="$(gpgconf --list-dirs agent-ssh-socket)"
fi
```

#### Керування дозволеними ключами через sshcontrol
Демон `gpg-agent` не зберігає SSH-ключі у стандартному форматі OpenSSH. Замість цього він конвертує ключі у внутрішній формат GnuPG (S-Expressions) і зберігає їх у каталозі `~/.gnupg/private-keys-v1.d/<KEYGRIP>.key`.

Перелік дозволених для SSH ключів фіксується у файлі `~/.gnupg/sshcontrol`. Кожен запис містить:
```text
# <Keygrip хеш SHA1 (40 hex символів)> [TTL] [Прапорці]
3A4B5C6D7E8F0123456789ABCDEF0123456789AB 0 !
```
- **Keygrip (40 символів):** Унікальний криптографічний відбиток закритого ключа, незалежний від протоколу (отримується командою `gpg --with-keygrip -k`).
- **TTL (число секунд):** Індивідуальний таймаут життя розшифрованого ключа в пам'яті (`0` — використовувати значення `default-cache-ttl-ssh`).
- **Прапорець `!` (Confirm):** Зобов'язує демон `gpg-agent` викликати графічний діалог `pinentry` для ручного підтвердження кожної операції підпису цим ключем.

### 2. Служба ключів GNOME Keyring (gnome-keyring-daemon)

У середовищах стільниці GNOME та сумісних XDG-оточеннях демон `gnome-keyring-daemon` перехоплює функцію SSH-агента для забезпечення безшовної інтеграції з графічною сесією.

- **Запуск компонента:** Демон запускається з прапорцем `--components=secrets,ssh,pkcs11`.
- **Шлях до сокета:** Сокет монтується за адресою `/run/user/<UID>/keyring/ssh` або `/tmp/keyring-XXXXXX/ssh`.
- **Інтеграція з PAM (Pluggable Authentication Modules):** Модуль `pam_gnome_keyring.so`, прописаний у `/etc/pam.d/login` та `/etc/pam.d/gdm-password`, отримує пароль користувача під час первинного входу в систему та автоматично розблоковує зв'язку ключів `login.keyring`.
- **Збереження парольних фраз:** Коли користувач уперше вводить парольну фразу для `id_ed25519` у графічному вікні `gcr-prompter`, вона зберігається у зашифрованій системній зв'язці ключів GNOME. Під час наступних сеансів SSH пароль підставляється автоматично без повторного запиту.

### 3. Менеджер паролів KeePassXC (SSH Agent Integration)

KeePassXC надає захищене сховище закритих ключів усередині локальної бази паролів `.kdbx`, зашифрованої алгоритмами AES-256 або ChaCha20-Poly1305 з розтягуванням ключа через KDF Argon2id.

#### Режими функціонування
1. **Інтеграція з наявним системним агентом:** KeePassXC підключається до сокета `$SSH_AUTH_SOCK` (OpenSSH agent, `gpg-agent` або `gnome-keyring`). Під час відкриття бази даних KDBX програма надсилає в сокет запит `SSH2_AGENTC_ADD_ID_CONSTRAINED` (код `25`), передаючи розшифровані ключі з налаштованими обмеженнями. При блокуванні або закритті бази надсилається повідомлення `SSH2_AGENTC_REMOVE_IDENTITY` (код `18`) або `SSH2_AGENTC_REMOVE_ALL_IDENTITIES` (код `19`).
2. **Вбудований автономний сервер агента:** KeePassXC відкриває власний сокет `AF_UNIX` і безпосередньо обробляє клієнтські запити `SSH2_AGENTC_REQUEST_IDENTITIES` та `SSH2_AGENTC_SIGN_REQUEST`, утримуючи ключі в пам'яті виключно доки база KDBX відкрита.

#### Політики безпеки на рівні запису ключа
Для кожного запису ключа в KeePassXC налаштовуються індивідуальні атрибути:
- *Автоматичне завантаження ключа при відкритті бази;*
- *Автоматичне вивантаження ключа після закінчення N секунд;*
- *Вимога явного підтвердження операції підпису (прапорець `SSH_AGENT_CONSTRAIN_CONFIRM`);*
- *Блокування доступу до ключа при блокуванні сеансу ОС (Lock Screen).*

### 4. Агент автентифікації 1Password SSH Agent

Менеджер паролів 1Password реалізує повноцінний сервер протоколу OpenSSH Agent, інтегрований із біометричними підсистемами операційних систем.

- **Шляхи до сокетів IPC:**
  - Linux / macOS: `~/.1password/agent.sock`
  - Windows: системний іменований канал `\\.\pipe\openssh-ssh-agent`
- **Біометрична авторизація виклику (Zero-Knowledge & User Presence):**
  Закриті ключі зберігаються у сховищах 1Password у зашифрованому вигляді. Під час надходження клієнтського запиту `SSH2_AGENTC_SIGN_REQUEST` агент 1Password перехоплює виконання операції та ініціює перевірку присутності користувача:
  - macOS: апаратний Touch ID або Apple Watch;
  - Windows: Windows Hello (сканер відбитків, розпізнавання обличчя чи PIN TPM);
  - Linux: інтеграція з демоном `polkit` та PAM (сканер відбитків пальців `fprintd` або системний пароль).
- **Контекстний аудит підпису:** У вікні біометричного підтвердження відображається цільовий хост, відбиток відкритого ключа, а також ім'я та PID клієнтського процесу (наприклад, `git`, `ssh`, `docker`), що запобігає фоновому несанкціонованому використанню ключа іншими застосунками.

### 5. Міжплатформні відмінності IPC: сокети UNIX, Named Pipes та Pageant

Механізми міжпроцесної комунікації для протоколу SSH-агента суттєво відрізняються залежно від цільової операційної системи.

| Платформа | Механізм IPC | Ідентифікатор кінцевої точки | Модель безпеки та контроль доступу |
|---|---|---|---|
| **Linux / BSD / macOS** | Потоковий сокет домену UNIX (`AF_UNIX`, `SOCK_STREAM`) | Шлях файлової системи у змінній `$SSH_AUTH_SOCK` (наприклад, `/run/user/1000/ssh-agent.sock`) | Права доступу файлової системи POSIX (`0700` для каталогу, `0600` для сокета, перевірка UID через системні структури ядра). |
| **Windows (Win32-OpenSSH)** | Системний іменований канал (Windows Named Pipe) | Рядок `\\.\pipe\openssh-ssh-agent` | Дескриптори безпеки Windows (Security Descriptors / ACLs), перевірка Security Identifier (SID) клієнтського процесу. |
| **Windows (PuTTY / Pageant legacy)** | Обмін віконними повідомленнями Win32 `WM_COPYDATA` | Приховане вікно з класом `Pageant` (`FindWindow("Pageant", "Pageant")`) | Ізоляція сесій Windows Desktop. Відсутні гранулярні списки ACL: будь-який процес із тим самим Integrity Level у сеансі користувача може надіслати повідомлення. |
| **WSL2 (Linux під Windows)** | Трансляція сокета через міст-ретранслятор | Локальний UNIX-сокет всередині WSL2, підключений до Windows Named Pipe через утиліту-міст | Перевірка прав POSIX усередині WSL2 плюс перевірка прав Windows ACL під час звернення до Named Pipe. |

#### Організація мостів для взаємодії WSL2 та Windows Agents

Оскільки ядро WSL2 працює у виділеній легковаговій віртуальній машині Hyper-V, клієнт `ssh` усередині Linux не може безпосередньо відкрити Windows Named Pipe `\\.\pipe\openssh-ssh-agent`.

Для наскрізного підключення застосовується зв'язка утиліт `socat` (усередині WSL2) та допоміжного виконуваного файлу Windows `npiperelay.exe`:

```bash
# Налаштування проксі-сокета в ~/.bashrc всередині WSL2
export SSH_AUTH_SOCK="$HOME/.ssh/agent.sock"
if ! ss -a | grep -q "$SSH_AUTH_SOCK"; then
    rm -f "$SSH_AUTH_SOCK"
    (setsid socat UNIX-LISTEN:"$SSH_AUTH_SOCK",fork \
        EXEC:"npiperelay.exe -ei -s //./pipe/openssh-ssh-agent",nofork &) >/dev/null 2>&1
fi
```

Коли клієнт `ssh` усередині Linux-дистрибутива WSL2 надсилає бінарний запит у `$HOME/.ssh/agent.sock`, утиліта `socat` перенаправляє потік байтів процесу `npiperelay.exe`, який виконує системні виклики Windows API `CreateFile` / `ReadFile` / `WriteFile` для обміну даними з іменованим каналом хост-системи (де може працювати 1Password, KeePassXC або служба `ssh-agent` Windows).
