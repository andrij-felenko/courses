# 📋 Довідник директив ~/.ssh/config, опцій ssh-add та протоколу агента

Цей довідник містить повну специфікацію директив конфігураційного файлу клієнта OpenSSH (`~/.ssh/config`), синтаксис токенів підстановки, параметри керування демоном через утиліту `ssh-add` та бінарний формат повідомлень внутрішнього протоколу `ssh-agent`.

---

## 1. Синтаксис та правила обчислення ~/.ssh/config

Конфігураційний файл клієнта за замовчуванням розташований у `~/.ssh/config` (користувацький рівень) та `/etc/ssh/ssh_config` (системний рівень). Клієнтська програма об'єднує ці конфігурації, причому користувацький файл має вищий пріоритет.

### Базові правила оформлення

1. **Рядки та коментарі:** Порожні рядки ігноруються. Символ `#` на початку рядка або після пробілу позначає коментар, який відкидається лексичним аналізатором.
2. **Формат запису:** Кожен параметр записується у форматі `Директива Значення` або `Директива = Значення`. Регістр назв директив не має значення (`HostName` еквівалентно `hostname` чи `HOSTNAME`), але значення параметрів чутливі до регістру (імена користувачів, шляхи до файлів, назви хостів).
3. **Пробіли та лапки:** Якщо значення параметра містить пробіли (наприклад, складні шляхи до ключів або команди `ProxyCommand`), воно береться у подвійні лапки: `IdentityFile "~/My Secure Keys/id_ed25519"`.
4. **Спадкування прав доступу:** Файл `~/.ssh/config` повинен мати права доступу `0600` або `0644` та належати поточному користувачеві; наявність прав запису для інших користувачів призводить до відмови в зчитуванні та ігнорування файлу клієнтом із міркувань безпеки.

### Порядок першого збігу (First Match Wins)

Клієнт OpenSSH читає конфігураційний файл послідовно згори вниз. Для кожної конкретної директиви фіксується **перше знайдене значення**. Наступні входження тієї самої директиви для хоста, що збігся, мовчки ігноруються.

```
# Специфічний хост стоїть першим
Host prod-db-01
    HostName 10.0.4.15
    User postgres
    Port 2222
    IdentityFile ~/.ssh/id_ed25519_db

# Груповий шаблон для всіх серверів продакшену
Host prod-*
    User devops
    IdentityFile ~/.ssh/id_ed25519_prod

# Глобальний блок за замовчуванням — ЗАВЖДИ В КІНЦІ ФАЙЛУ
Host *
    IdentitiesOnly yes
    ServerAliveInterval 60
    ServerAliveCountMax 3
```

У наведеному прикладі під час виконання команди `ssh prod-db-01`:
- `HostName` отримає значення `10.0.4.15` (із першого блоку).
- `User` отримає значення `postgres` (із першого блоку; значення `devops` із блоку `prod-*` буде проігноровано, оскільки директива `User` уже має значення).
- `Port` отримає значення `2222`.
- `IdentityFile` збереже значення `~/.ssh/id_ed25519_db`.
- `IdentitiesOnly`, `ServerAliveInterval` та `ServerAliveCountMax` будуть взяті з фінального блоку `Host *`, оскільки вони не були визначені вище.

### Маски зіставлення шаблонів Host

Шаблони зіставлення `Host` дозволяють групувати однотипні машини та застосовувати до них спільні правила маршрутизації й безпеки:

| Шаблон | Опис поведінки | Приклад |
|---|---|---|
| `*` | Збігається з нулем або більше будь-яких символів у назві хоста | `Host *.prod.internal` |
| `?` | Збігається рівно з одним довільним символом у назві | `Host node-0?` |
| `!` | Заперечення умови (виключає конкретний збіг із загальної групи) | `Host *.internal !bastion.internal` |
| `пробіл` | Логічне «АБО» для списку псевдонімів хостів | `Host app1 app2 app3 staging-*` |

### Директива Match

Директива `Match` надає можливість динамічного умовного застосування налаштувань на основі виконання зовнішніх команд або атрибутів сеансу. На відміну від статичного `Host`, вираз `Match` може обчислювати поточний мережевий стан або локальне середовище:

```
# Застосувати окремий ключ, якщо виклик іде з локальної підмережі офісу
Match host *.internal exec "ip route get 10.0.0.1 | grep -q wlan0"
    IdentityFile ~/.ssh/id_ed25519_local_wifi
```

Критерії директиви `Match`:
- `canonical`: перевірка після канонізації імені хоста через DNS або директиву `CanonicalizeHostname`.
- `final`: фінальний прохід оцінки конфігурації після визначення всіх псевдонімів.
- `host <шаблон>`: зіставлення імені цільового хоста.
- `originalhost <рядок>`: первинне ім'я, передане в командному рядку до будь-яких перетворень.
- `user <користувач>`: віддалене ім'я користувача на сервері.
- `localuser <користувач>`: локальний UID або логін на клієнтській машині.
- `exec "<команда>"`: перевірка коду повернення шел-команди (код `0` означає успішний збіг критерію).

## 2. Довідкова таблиця директив ~/.ssh/config

### Адресація та автентифікація

Директиви цієї групи відповідають за мережеву локалізацію сервера, вибір облікового запису та криптографічних матеріалів автентифікації. Вони визначають, який мережевий порт слухає віддалена служба, під яким логіном здійснюється вхід та де зберігаються відповідні файли сертифікатів:

| Директива | Тип значення | Приклад | Призначення |
|---|---|---|---|
| `HostName` | рядок (IP / FQDN) | `HostName 192.168.1.100` | Справжня мережева адреса або доменне ім'я цільового сервера. |
| `User` | рядок | `User ubuntu` | Ім'я облікового запису на віддаленому сервері за замовчуванням. |
| `Port` | ціле число (1..65535) | `Port 22022` | Номер TCP-порту демона `sshd` на віддаленому сервері. |
| `IdentityFile` | шлях до файлу | `IdentityFile ~/.ssh/id_ed25519` | Шлях до файлу закритого ключа для автентифікації. Може вказуватися багаторазово. |
| `IdentitiesOnly` | `yes` / `no` | `IdentitiesOnly yes` | Використовувати виключно ключі, зазначені через `IdentityFile` або `-i`. Блокує неконтрольований перебір усіх ключів `ssh-agent`. |
| `AddKeysToAgent` | `yes` / `no` / `ask` / `confirm` | `AddKeysToAgent yes` | Автоматично додавати розшифрований ключ до `ssh-agent` під час першого успішного використання. |
| `CertificateFile` | шлях до файлу | `CertificateFile ~/.ssh/id-cert.pub` | Шлях до відкритого сертифіката OpenSSH Certificate Authority. |
| `PubkeyAuthentication` | `yes` / `no` | `PubkeyAuthentication yes` | Дозволити або заборонити спробу автентифікації за відкритими ключами. |
| `PasswordAuthentication`| `yes` / `no` | `PasswordAuthentication no` | Дозволити або заборонити інтерактивний ввід пароля. |

### Маршрутизація, тунелі та проксі

Ці параметри визначають спосіб проходження мережевих периметрів, організацію проміжних стрибків та прокидання портів. Завдяки їм клієнт може будувати тунелі до ізольованих контурів інфраструктури без розкриття проміжних облікових даних:

| Директива | Тип значення | Приклад | Призначення |
|---|---|---|---|
| `ProxyJump` | список хостів | `ProxyJump jump1.net,jump2.net` | Наскрізний тунель через один або кілька проміжних бастіонів (використовує канал `direct-tcpip`). |
| `ProxyCommand` | шел-команда | `ProxyCommand ssh -W %h:%p b1` | Застарілий спосіб тунелювання через запуск зовнішнього процесу зв'язку з stdin/stdout. |
| `ForwardAgent` | `yes` / `no` | `ForwardAgent no` | Пересилати з'єднання з локальним `ssh-agent` на віддалений сервер. Небезпечно при підключенні до ненадійних вузлів. |
| `LocalForward` | `[bind_addr:]port host:hostport` | `LocalForward 8080 127.0.0.1:80` | Прокидання локального TCP-порту клієнта на порт віддаленої мережі. |
| `RemoteForward` | `[bind_addr:]port host:hostport` | `RemoteForward 9000 127.0.0.1:9000` | Прокидання віддаленого TCP-порту сервера на локальний порт клієнта. |
| `DynamicForward`| `[bind_addr:]port` | `DynamicForward 1080` | Відкриття локального SOCKS4/SOCKS5 динамічного проксі-сервера. |

### Мультиплексування з'єднань (ControlMaster)

Параметри керування пулом активних каналів зв'язку дозволяють усунути накладні витрати на повторні фази встановлення з'єднань. Головний майстер-процес утримує єдиний відкритий TCP-тунель, а всі дочірні підключення стартують за лічені мілісекунди:

| Директива | Тип значення | Приклад | Призначення |
|---|---|---|---|
| `ControlMaster` | `yes` / `no` / `auto` / `autoask` | `ControlMaster auto` | Дозволяє спільне використання одного мережевого TCP/SSH з'єднання для кількох паралельних клієнтських сесій. |
| `ControlPath` | шлях до сокета | `ControlPath ~/.ssh/S.%r@%h:%p` | Шлях створення локального UNIX-сокета керування мультиплексованим з'єднанням. |
| `ControlPersist` | `yes` / `no` / час (`10m`, `1h`) | `ControlPersist 10m` | Залишати майстер-процес у фоновому режимі після закриття первинного термінала на вказаний інтервал неактивності. |

### Параметри стабільності, криптографії та налагодження

Ці директиви керують алгоритмами шифрування, періодичністю перевірки доступності каналу через файрволи та поведінкою клієнта у разі виявлення змінених ключів хостів:

| Директива | Тип значення | Приклад | Призначення |
|---|---|---|---|
| `ServerAliveInterval` | секунди | `ServerAliveInterval 30` | Інтервал надсилання порожніх пакетів перевірки активності сервера через шифрований канал. |
| `ServerAliveCountMax` | ціле число | `ServerAliveCountMax 3` | Кількість невідповідей на `ServerAliveInterval` перед примусовим розривом з'єднання клієнтом. |
| `TCPKeepAlive` | `yes` / `no` | `TCPKeepAlive yes` | Надсилання TCP Keepalive зондів на рівні транспортного протоколу ядра Linux. |
| `ConnectTimeout` | секунди | `ConnectTimeout 10` | Таймаут встановлення первинного TCP-з'єднання з сервером. |
| `StrictHostKeyChecking`| `yes` / `no` / `ask` / `accept-new` | `StrictHostKeyChecking accept-new` | Політика реакції на невідомі або змінені ключі сервера у файлі `known_hosts`. |
| `UserKnownHostsFile` | шлях до файлу | `UserKnownHostsFile ~/.ssh/known_hosts` | Шлях до бази відбитків довірених серверів. |
| `LogLevel` | рівень деталізації | `LogLevel DEBUG3` | Рівень виводу службових повідомлень (`QUIET`, `FATAL`, `ERROR`, `INFO`, `VERBOSE`, `DEBUG1`, `DEBUG2`, `DEBUG3`). |
| `Ciphers` | список шифрів | `Ciphers chacha20-poly1305@openssh.com` | Дозволений перелік симетричних алгоритмів шифрування сеансу. |
| `KexAlgorithms` | список алгоритмів | `KexAlgorithms curve25519-sha256` | Дозволені алгоритми обміну сеансовими ключами (Key Exchange). |
| `HostkeyAlgorithms` | список алгоритмів | `HostkeyAlgorithms ssh-ed25519` | Дозволені алгоритми перевірки відбитків хоста сервера. |
| `SetEnv` | змінні оточення | `SetEnv DEBIAN_FRONTEND=noninteractive` | Передача змінних середовища клієнта на віддалений сервер. |

## 3. Токени підстановки (Tokens / Specifiers)

У значеннях директив `ControlPath`, `IdentityFile`, `ProxyCommand`, `LocalForward` OpenSSH підтримує динамічні токени, які розгортаються парсером під час формування параметрів з'єднання. Це забезпечує можливість побудови універсальних шаблонів для довільних списків вузлів:

| Токен | Значення підстановки | Приклад розгортання |
|---|---|---|
| `%h` | Цільовий хост (значення `HostName`) | `192.168.1.50` |
| `%p` | Цільовий порт з'єднання | `22` |
| `%r` | Віддалений користувач на сервері | `devops` |
| `%n` | Первинне ім'я хоста, вказане в CLI | `db-staging` |
| `%u` | Локальне ім'я користувача на клієнті | `andrij` |
| `%l` | Локальне FQDN ім'я клієнтського комп'ютера | `laptop.corp.internal` |
| `%L` | Перший сегмент локального імені машини | `laptop` |
| `%k` | Використовуваний ключ хоста сервера | `ssh-ed25519-AAAAC3...` |
| `%C` | Хеш SHA1 від рядка `%l%h%p%r` (довжина 40 байтів) | `a8b3c4d5e6...` (ідеально для короткого `ControlPath`) |
| `%%` | Символ відсотка `%` | `%` |

Токен `%C` має особливе значення при налаштуванні `ControlPath`. Оскільки стандарт POSIX обмежує розмір шляху сокета `AF_UNIX` (поле `sun_path`) величиною в 108 байтів, довгі доменні імена в комбінації з користувачами призводять до помилки `ENAMETOOLONG`. Токен `%C` згортає всі змінні в детермінований 40-символьний хеш фіксованої довжини.

## 4. Керування ключами агента: утиліта ssh-add

Утиліта `ssh-add` забезпечує інтерфейс командного рядка для завантаження, перегляду та вивантаження ключів із пам'яті працюючого демона `ssh-agent`. Вона взаємодіє з сокетом `$SSH_AUTH_SOCK` від імені поточного користувача.

### Таблиця прапорців утиліти ssh-add

| Прапорець | Аргумент | Призначення |
|---|---|---|
| *(без прапорців)* | `[шлях]` | Додати стандартні ключі (`~/.ssh/id_rsa`, `~/.ssh/id_ed25519`) або вказаний файл ключа до агента. |
| `-t` | `час` (`1h`, `30m`, `8h`) | Встановити максимальний час життя ключа в пам'яті агента. Після закінчення таймера ключ видаляється. |
| `-c` | — | Вимагати явного ручного підтвердження від користувача перед кожним використанням ключа для підпису. |
| `-l` | — | Вивести список завантажених у даний момент ключів (розмір, SHA256 відбиток, коментар, тип). |
| `-L` | — | Експортувати публічні частини всіх завантажених ключів у форматі `authorized_keys`. |
| `-d` | `[шлях]` | Видалити конкретний ключ із пам'яті агента за вказаним файлом закритого або відкритого ключа. |
| `-D` | — | Повністю очистити пам'ять агента (видалити абсолютно всі завантажені ключі). |
| `-x` | — | Заблокувати агент паролем (усі операції підпису призупиняються до введення пароля розблокування). |
| `-X` | — | Розблокувати попередньо заблокований демон `ssh-agent`. |
| `-s` | `шлях_до_PKCS11` | Додати апаратний ключ смарт-картки через динамічну бібліотеку модуля PKCS#11. |
| `-e` | `шлях_до_PKCS11` | Вивантажити ключі модуля PKCS#11 з агента. |
| `-q` | — | Тихий режим роботи (придушення інформаційних повідомлень). |

Під час завантаження апаратних токенів PKCS#11 (прапорець `-s`) демон `ssh-agent` завантажує динамічну бібліотеку драйвера смарт-картки (наприклад, `/usr/lib/x86_64-linux-gnu/opensc-pkcs11.so`) у свій адресний простір. Агент спілкується з фізичним криптографічним чипом токена, і закритий ключ ніколи не потрапляє навіть в оперативну пам'ять демона, оскільки всі криптографічні підписи накладаються безпосередньо апаратним модулем смарт-картки.

## 5. Специфікація бінарного протоколу OpenSSH Agent

Комунікація між клієнтом (`ssh`, `ssh-add`) та сервером ключів (`ssh-agent`) здійснюється локально через потоковий сокет домену UNIX (`AF_UNIX`, `SOCK_STREAM`), адреса якого зберігається у змінній середовища оточення `$SSH_AUTH_SOCK`.

### Загальний формат кадру повідомлення

Усі цілочисельні поля довжини та прапорців кодуються у беззнаковому 32-бітному форматі в мережевому порядку байтів (Big-Endian / Most Significant Byte First):

```
+-----------------------------+-------------------+------------------------------------+
|  Довжина корисного блоку    |  Тип повідомлення |       Тіло повідомлення            |
|       (uint32, 4 байти)     | (uint8, 1 байт)   |   (N-1 байтів згідно зі специфікацією)  |
+-----------------------------+-------------------+------------------------------------+
```

### Коди типів повідомлень протоколу

Повний перелік повідомлень агентського протоколу OpenSSH:

| Назва константи | Числовий код | Напрямок | Опис операції |
|---|---|---|---|
| `SSH_AGENT_FAILURE` | `5` | Агент → Клієнт | Операцію відхилено або виникла помилка. |
| `SSH_AGENT_SUCCESS` | `6` | Агент → Клієнт | Запит на додавання/видалення/блокування виконано успішно. |
| `SSH_AGENTC_REQUEST_IDENTITIES` | `11` | Клієнт → Агент | Запит переліку публічних ключів, доступних в агенті. |
| `SSH_AGENT_IDENTITIES_ANSWER` | `12` | Агент → Клієнт | Відповідь із масивом відкритих ключів та коментарів. |
| `SSH_AGENTC_SIGN_REQUEST` | `13` | Клієнт → Агент | Запит на цифровий підпис блоку даних конкретним ключем. |
| `SSH_AGENT_SIGN_RESPONSE` | `14` | Агент → Клієнт | Відповідь, що містить сформований криптографічний підпис. |
| `SSH_AGENTC_ADD_IDENTITY` | `17` | Клієнт → Агент | Завантаження закритого ключа в пам'ять агента. |
| `SSH_AGENTC_REMOVE_IDENTITY` | `18` | Клієнт → Агент | Видалення одного ключа за його публічним блобом. |
| `SSH_AGENTC_REMOVE_ALL_IDENTITIES` | `19` | Клієнт → Агент | Повне очищення списку ключів агента. |
| `SSH_AGENTC_ADD_ID_CONSTRAINED` | `25` | Клієнт → Агент | Додавання закритого ключа з обмеженнями (lifetime/confirm). |
| `SSH_AGENTC_LOCK` | `22` | Клієнт → Агент | Запит на блокування агента рядком пароля. |
| `SSH_AGENTC_UNLOCK` | `23` | Клієнт → Агент | Запит на зняття блокування паролем. |

### Структури даних ключових операцій

#### 1. Запит та відповідь переліку ключів

Запит `SSH_AGENTC_REQUEST_IDENTITIES` (байт `11`) не містить корисного навантаження (довжина пакета 1 байт):
`[00 00 00 01][0B]`

Відповідь `SSH_AGENT_IDENTITIES_ANSWER` (байт `12`):
```
uint32  nkeys         # Кількість завантажених ключів у пам'яті
# Далі nkeys разів повторюється структура:
  string  key_blob    # Бінарний серіалізований відкритий ключ (uint32 len + raw bytes)
  string  comment     # Текстовий коментар ключа (uint32 len + UTF-8 string)
```

#### 2. Запит та відповідь цифрового підпису

Запит `SSH_AGENTC_SIGN_REQUEST` (байт `13`):
```
string  key_blob      # Відкритий ключ, закрита пара якого має виконати підпис
string  data          # Блок виклику (challenge), згенерований віддаленим sshd
uint32  flags         # Прапорці алгоритму підпису (наприклад для RSA)
```

Прапорці підпису (`flags`):
- `0x00`: стандартний підпис за замовчуванням (для RSA — застарілий SHA1 `ssh-rsa`).
- `0x02`: `SSH_AGENT_RSA_SHA2_256` (використання гешування SHA-256 для RSA підписів `rsa-sha2-256`).
- `0x04`: `SSH_AGENT_RSA_SHA2_512` (використання гешування SHA-512 для RSA підписів `rsa-sha2-512`).

Відповідь `SSH_AGENT_SIGN_RESPONSE` (байт `14`):
```
string  signature     # Серіалізований контейнер підпису (uint32 len + формат_підпису + raw_sig)
```

#### 3. Обмеження при додаванні ключа (Key Constraints)

Під час надсилання `SSH_AGENTC_ADD_ID_CONSTRAINED` (байт `25`) після стандартного опису закритого ключа передається послідовність байтів обмежень:
- `SSH_AGENT_CONSTRAIN_LIFETIME` (`1`): далі йде `uint32 seconds` — час автоматичного вивантаження.
- `SSH_AGENT_CONSTRAIN_CONFIRM` (`2`): без додаткових параметрів — вимагати виклику `SSH_ASKPASS` перед кожним підписом.
- `SSH_AGENT_CONSTRAIN_EXTENSION` (`255`): розширення обмежень OpenSSH (наприклад прив'язка до хоста призначення).

## 6. Змінні оточення клієнта та агента OpenSSH

Системні змінні середовища визначають параметри міжпроцесної взаємодії та маршрутизації:

| Змінна оточення | Призначення та вплив на поведінку |
|---|---|
| `SSH_AUTH_SOCK` | Вказує шлях до сокета домену UNIX, через який здійснюється зв'язок із `ssh-agent`. |
| `SSH_AGENT_PID` | Зберігає PID фонового процесу агента; використовується `ssh-agent -k` для завершення процесу. |
| `SSH_ASKPASS` | Шлях до зовнішньої графічної або консольної утиліти введення пароля (застосовується при відсутності TTY або при `ssh-add -c`). |
| `SSH_ASKPASS_REQUIRE` | Керує викликом `SSH_ASKPASS` (`never`, `prefer`, `force`). |
| `SSH_CONNECTION` | Встановлюється на віддаленому сервері: містить чотири значення `client_ip client_port server_ip server_port`. |
| `SSH_TTY` | Вказує шлях до псевдотермінала (`/dev/pts/N`), виділеного поточному віддаленому сеансу. |
