# 📋 Інтерфейс сокетів kTLS: ULP, socket options та структури ядра

Підсистема Kernel TLS (kTLS) надає програмний інтерфейс рівня ядра Linux для делегування симетричного шифрування та дешифрування записів протоколу TLS. Цей довідник містить повний опис сигнатур системних викликів, бінарних структур пам'яті, опцій сокетів, типів керуючих повідомлень `cmsg`, метрик `/proc/net/tls_stat` та системних кодів помилок.

---

## 1. Системні заголовки та умови збірки ядра

Для використання інтерфейсу kTLS у системному програмуванні C та C++ необхідно підключити відповідні заголовні файли ядра Linux та мережевого стеку. Підсистема вимагає ядра Linux версії 4.13 або новішої для вихідного трафіку (TX) та версії 4.17+ для вхідного трафіку (RX). У конфігурації ядра повинен бути увімкнений модуль `CONFIG_TLS=m` або `CONFIG_TLS=y`, а для апаратного розвантаження — прапор `CONFIG_TLS_DEVICE=y`.

:::tabs
```c
#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/tcp.h>
#include <linux/tls.h>
```
```cpp
#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/tcp.h>
#include <linux/tls.h>
```
:::

Файл `<linux/tls.h>` надає визначення основних констант криптографічних шифрів, версій TLS, типів керуючих повідомлень та специфічних структур даних пам'яті.

---

## 2. Активація протоколу верхнього рівня ULP (Upper Layer Protocol)

Перед тим як сокет зможе приймати криптографічні опції `SOL_TLS`, його необхідно перевести з режиму звичайного TCP під управління підсистеми ULP `"tls"`. Це здійснюється за допомогою виклику `setsockopt()` на рівні протоколу `SOL_TCP`.

### Сигнатура та параметри реєстрації ULP

Операція прив'язки підсистеми ULP вимагає, щоб TCP-сокет перебував виключно у стані встановленого з'єднання `TCP_ESTABLISHED`. Спроба викликати налаштування на непідключеному сокеті або на сокеті у стані слухання `LISTEN` призведе до відмови ядра.

:::tabs
```c
int val = setsockopt(sock_fd, SOL_TCP, TCP_ULP, "tls", sizeof("tls"));
```
```cpp
int val = ::setsockopt(sock_fd, SOL_TCP, TCP_ULP, "tls", sizeof("tls"));
```
:::

- **Дескриптор `sock_fd`:** Відкритий та успішно підключений файловий дескриптор сокета типу `SOCK_STREAM`.
- **Рівень `level`:** Системна константа `SOL_TCP` (числове значення `6`).
- **Опція `optname`:** Системна константа `TCP_ULP` (числове значення `31`).
- **Вказівник `optval`:** Рядковий літерал `"tls"`, що ідентифікує модуль ядра `net/tls`.
- **Розмір `optlen`:** Довжина рядка у байтах, включаючи кінцевий нульовий символ (`sizeof("tls")` дорівнює `4` байтам).

### Механіка роботи ядра при реєстрації ULP

Під час виконання цього виклику ядро Linux здійснює перевірку наявності завантаженого модуля `tls.ko`. Якщо модуль відсутній у оперативній пам'яті, підсистема `kmod` намагається автоматично завантажити його з диска. Після цього ядро замінює таблицю вказівників на сокетні операції `sk_prot` у внутрішній структурі `struct sock`. Звичайні методи обробки TCP замінюються на спеціалізовані адаптери kTLS:
- Метод запису в сокет `sk_prot->sendmsg` перенаправляється на функцію ядра `tls_sw_sendmsg()`.
- Метод відправки сторінок `sk_prot->sendpage` перенаправляється на `tls_sw_sendpage()`.
- Метод читання із сокета `sk_prot->recvmsg` перенаправляється на `tls_sw_recvmsg()`.

Якщо процедура заміни операцій пройшла успішно, виклик повертає `0`. У разі виникнення помилки повертається `-1`, а системна змінна `errno` встановлюється у відповідний код відмови.

## 3. Криптографічний рівень опцій `SOL_TLS`

Після того, як сокет пройшов процедуру ініціалізації ULP, ядро відкриває для нього спеціалізований рівень сокетних опцій `SOL_TLS` (числове значення `282`). Цей рівень використовується для передачі криптографічного стану (ключів, векторів ініціалізації, солі та послідовних номерів) окремо для кожного напрямку передачі даних.

### Список доступних опцій `SOL_TLS`

- **`TLS_TX` (числове значення `1`):** Налаштування симетричного шифрування для вихідного потоку даних. Викликається перед першою операцією відправки даних `write()` або `sendfile()`.
- **`TLS_RX` (числове значення `2`):** Налаштування симетричного дешифрування для вхідного потоку даних. Викликається перед першою операцією читання `read()` або `recv()`.
- **`TLS_TX_ZEROCOPY_RO` (числове значення `3`):** Прапорець оптимізації read-only сторінок у пам'яті ядра для режимів Zero-Copy.
- **`TLS_RX_EXPECT_NO_PAD` (числове значення `4`):** Інструкція ядру очікувати відсутність вирівнювальних байтів padding у вхідних TLS-записах для прискорення перевірки Auth Tag.

## 4. Структури даних криптографічних параметрів

Усі криптографічні конфігурації kTLS починаються із загального заголовочного блоку `struct tls_crypto_info`, після якого розміщуються поля конкретного алгоритму шифрування. Обсяг переданих даних у виклику `setsockopt()` повинен точно відповідати розміру специфічної структури обраного шифру.

### Базовий заголовок `struct tls_crypto_info`

:::tabs
```c
struct tls_crypto_info {
    __u16 version;     /* Версія протоколу TLS */
    __u16 cipher_type; /* Ідентифікатор симетричного алгоритму шифрування */
};
```
```cpp
struct tls_crypto_info {
    uint16_t version;     // Версія протоколу TLS
    uint16_t cipher_type; // Ідентифікатор симетричного алгоритму шифрування
};
```
:::

Поле `version` визначає версію протоколу TLS, для якої згенеровано ключі:
- `TLS_1_2_VERSION` (шестнадцяткове значення `0x0303`) — протокол TLS версії 1.2.
- `TLS_1_3_VERSION` (шестнадцяткове значення `0x0304`) — протокол TLS версії 1.3.

Поле `cipher_type` вказує ядру, який саме алгоритм AEAD повинен бути ініціалізований у підсистемі Kernel Crypto API:
- `TLS_CIPHER_AES_GCM_128` (значення `51`) — шифр AES у режимі Galois/Counter Mode із 128-бітним ключем.
- `TLS_CIPHER_AES_GCM_256` (значення `52`) — шифр AES-GCM із 256-бітним ключем.
- `TLS_CIPHER_AES_CCM_128` (значення `53`) — шифр AES у режимі Counter with CBC-MAC із 128-бітним ключем.
- `TLS_CIPHER_CHACHA20_POLY1305` (значення `54`) — потоковий шифр ChaCha20 з аутентифікатором Poly1305.

### Структура `struct tls12_crypto_info_aes_gcm_128`

Використовується для налаштування шифрування AES-GCM-128 як у протоколі TLS 1.2, так і у TLS 1.3.

:::tabs
```c
struct tls12_crypto_info_aes_gcm_128 {
    struct tls_crypto_info info;
    unsigned char iv[TLS_CIPHER_AES_GCM_128_IV_SIZE];       /* 8 байт: ініціалізаційний вектор nonce */
    unsigned char key[TLS_CIPHER_AES_GCM_128_KEY_SIZE];     /* 16 байт: симетричний ключ AES */
    unsigned char salt[TLS_CIPHER_AES_GCM_128_SALT_SIZE];   /* 4 байти: соляний префікс implicit IV */
    unsigned char rec_seq[TLS_CIPHER_AES_GCM_128_REC_SEQ_SIZE]; /* 8 байт: поточний порядковий номер запису */
};
```
```cpp
struct tls12_crypto_info_aes_gcm_128 {
    struct tls_crypto_info info;
    uint8_t iv[TLS_CIPHER_AES_GCM_128_IV_SIZE];       // 8 байт: ініціалізаційний вектор nonce
    uint8_t key[TLS_CIPHER_AES_GCM_128_KEY_SIZE];     // 16 байт: симетричний ключ AES
    uint8_t salt[TLS_CIPHER_AES_GCM_128_SALT_SIZE];   // 4 байти: соляний префікс implicit IV
    uint8_t rec_seq[TLS_CIPHER_AES_GCM_128_REC_SEQ_SIZE]; // 8 байт: поточний порядковий номер запису
};
```
:::

Детальний опис полів структури:
- **`info`:** Заголовок з указанням `version = TLS_1_2_VERSION` або `TLS_1_3_VERSION` та `cipher_type = TLS_CIPHER_AES_GCM_128`.
- **`iv`:** 8-байтний масив, який становить явну (explicit) або змінну частину вектора ініціалізації. Для кожного нового запису TLS цей лічильник інкрементується на `1`.
- **`key`:** 16-байтний (128 біт) секретний симетричний ключ, виведений бібліотекою користувацького простору під час фази Handshake.
- **`salt`:** 4-байтний незмінний префікс (implicit IV), який об'єднується з масивом `iv` для формування повного 12-байтного nonce алгоритму AES-GCM.
- **`rec_seq`:** 8-байтний (64 біти) порядковий номер TLS-запису (Record Sequence Number), з якого ядро повинно розпочати шифрування або дешифрування. Для TLS 1.2 і TLS 1.3 значення передається у форматі Big-Endian.

### Структура `struct tls12_crypto_info_aes_gcm_256`

Використовується для налаштування шифрування AES-GCM з розширеним 256-бітним ключем підвищеної стійкості.

:::tabs
```c
struct tls12_crypto_info_aes_gcm_256 {
    struct tls_crypto_info info;
    unsigned char iv[TLS_CIPHER_AES_GCM_256_IV_SIZE];       /* 8 байт */
    unsigned char key[TLS_CIPHER_AES_GCM_256_KEY_SIZE];     /* 32 байти */
    unsigned char salt[TLS_CIPHER_AES_GCM_256_SALT_SIZE];   /* 4 байти */
    unsigned char rec_seq[TLS_CIPHER_AES_GCM_256_REC_SEQ_SIZE]; /* 8 байт */
};
```
```cpp
struct tls12_crypto_info_aes_gcm_256 {
    struct tls_crypto_info info;
    uint8_t iv[TLS_CIPHER_AES_GCM_256_IV_SIZE];       // 8 байт
    uint8_t key[TLS_CIPHER_AES_GCM_256_KEY_SIZE];     // 32 байти
    uint8_t salt[TLS_CIPHER_AES_GCM_256_SALT_SIZE];   // 4 байти
    uint8_t rec_seq[TLS_CIPHER_AES_GCM_256_REC_SEQ_SIZE]; // 8 байт
};
```
:::

Поле `key` розширено до `32` байтів. Усі інші поля виконують аналогічні функції та мають такі ж розміри, як і в 128-бітній версії.

### Структура `struct tls12_crypto_info_chacha20_poly1305`

Використовується для високоефективного шифрування на мобільних пристроях та процесорах без апаратного модуля AES-NI.

:::tabs
```c
struct tls12_crypto_info_chacha20_poly1305 {
    struct tls_crypto_info info;
    unsigned char iv[TLS_CIPHER_CHACHA20_POLY1305_IV_SIZE];       /* 12 байт */
    unsigned char key[TLS_CIPHER_CHACHA20_POLY1305_KEY_SIZE];     /* 32 байти */
    unsigned char rec_seq[TLS_CIPHER_CHACHA20_POLY1305_REC_SEQ_SIZE]; /* 8 байт */
};
```
```cpp
struct tls12_crypto_info_chacha20_poly1305 {
    struct tls_crypto_info info;
    uint8_t iv[TLS_CIPHER_CHACHA20_POLY1305_IV_SIZE];       // 12 байт
    uint8_t key[TLS_CIPHER_CHACHA20_POLY1305_KEY_SIZE];     // 32 байти
    uint8_t rec_seq[TLS_CIPHER_CHACHA20_POLY1305_REC_SEQ_SIZE]; // 8 байт
};
```
:::

Особливості ChaCha20-Poly1305 у kTLS:
- Відсутнє окреме поле `salt`: повний 12-байтний ініціалізаційний вектор задається безпосередньо у масиві `iv`.
- Розмір симетричного ключа `key` становить `32` байти (256 біт).

## 5. Інтерфейс допоміжних даних `cmsg` для керуючих повідомлень

Стандартні системні виклики `write()`, `send()`, `sendfile()` та `splice()` при роботі з kTLS сокетом завжди упаковують передані байти у TLS-записи типу **`Application Data` (код `23`)**.

Проте протокол TLS вимагає періодичного обміну іншими типами записів:
- **`Alert` (код `21`):** Повідомлення про закриття з'єднання (`close_notify`) або критичні помилки криптографії.
- **`Handshake` (код `22`):** Повідомлення про оновлення ключів сесії (`KeyUpdate` у TLS 1.3) або переузгодження параметрів.
- **`ChangeCipherSpec` (код `20`):** Сигнальне повідомлення зміни шифру у TLS 1.2.

Для надсилання та прийому таких нееталонних записів використовується механізм **Control Messages (`cmsg`)** у системних викликах `sendmsg()` та `recvmsg()`.

### Конфігурація заголовка `struct cmsghdr` для надсилання запису

При формуванні виклику `sendmsg()` додаток додає до структури `struct msghdr` контрольний буфер із заголовком `struct cmsghdr`:

:::tabs
```c
/* Приклад встановлення cmsg для TLS Alert */
struct cmsghdr *cmsg;
char cmsgbuf[CMSG_SPACE(sizeof(unsigned char))];

msg.msg_control = cmsgbuf;
msg.msg_controllen = sizeof(cmsgbuf);

cmsg = CMSG_FIRSTHDR(&msg);
cmsg->cmsg_level = SOL_TLS;
cmsg->cmsg_type = TLS_SET_RECORD_TYPE;
cmsg->cmsg_len = CMSG_LEN(sizeof(unsigned char));

/* Вказуємо тип запису у корисній частині cmsg */
*((unsigned char *)CMSG_DATA(cmsg)) = TLS_RECORD_TYPE_ALERT;
```
```cpp
// C++20 аналог встановлення cmsg для TLS Alert
alignas(struct cmsghdr) std::array<char, CMSG_SPACE(sizeof(uint8_t))> cmsgbuf{};
msg.msg_control = cmsgbuf.data();
msg.msg_controllen = cmsgbuf.size();

struct cmsghdr *cmsg = CMSG_FIRSTHDR(&msg);
cmsg->cmsg_level = SOL_TLS;
cmsg->cmsg_type = TLS_SET_RECORD_TYPE;
cmsg->cmsg_len = CMSG_LEN(sizeof(uint8_t));

*reinterpret_cast<uint8_t*>(CMSG_DATA(cmsg)) = TLS_RECORD_TYPE_ALERT;
```
:::

Значення полів `cmsghdr`:
- **`cmsg_level`:** Повинно бути встановлено у `SOL_TLS` (`282`).
- **`cmsg_type`:** Константа `TLS_SET_RECORD_TYPE` (значення `1`) для вихідного трафіку.
- **`cmsg_len`:** Макрос `CMSG_LEN(sizeof(unsigned char))` для вирівнювання розміру байта типу.
- **`CMSG_DATA(cmsg)`:** Указатель на 1-байтне значення типу TLS-запису.

### Специфікація типів TLS-записів

- `TLS_RECORD_TYPE_CHANGE_CIPHER_SPEC` (значення `20`) — повідомлення зміни шифру.
- `TLS_RECORD_TYPE_ALERT` (значення `21`) — сигнальні та запереджувальні повідомлення.
- `TLS_RECORD_TYPE_HANDSHAKE` (значення `22`) — службові кадри рукостискання.
- `TLS_RECORD_TYPE_DATA` (значення `23`) — корисні дані додатка.

## 6. Моніторинг, метрики `/proc/net/tls_stat` та трасування

Ядро Linux збирає повну статистику щодо функціонування підсистеми kTLS та виводить її через псевдофайлову систему `/proc`.

### Метрики псевдофайлу `/proc/net/tls_stat`

Поточні системні значення можна зчитати звичайними утилітами моніторингу або відкривши файл у програмі:

```bash
cat /proc/net/tls_stat
```

Повний опис метрик ядра:
- **`TlsTxSw`:** Загальна кількість сокетів, які у даний момент використовують програмне шифрування ядра `TLS_SW` для вихідного трафіку.
- **`TlsRxSw`:** Загальна кількість сокетів, які використовують програмне дешифрування `TLS_SW` для вхідного трафіку.
- **`TlsTxDevice`:** Кількість активних сокетів, розвантажених на апаратне шифрування SmartNIC (`TLS_HW` / Inline TX).
- **`TlsRxDevice`:** Кількість сокетів з апаратним дешифруванням вхідного трафіку (`TLS_HW` / Inline RX).
- **`TlsTxSwFallback`:** Кількість вихідних пакетів, які були перенаправлені з апаратури у програмний модуль `TLS_SW` через тимчасову відсутність ресурсів у SmartNIC.
- **`TlsRxSwFallback`:** Кількість вхідних пакетів, дешифрованих програмно через втрату послідовності у мережевій карті.
- **`TlsAborted`:** Кількість сесій, аварійно розірваних ядром через недійсний Auth Tag або десинхронізацію порядкових номерів.
- **`TlsRxNumResyncReqReceived`:** Кількість запитів повторної апаратної синхронізації (Hardware Resync Requests), надісланих мережевою картою до ядра.

## 7. Коди помилок та інструкції з налагодження

У разі передачі некоректних параметрів або виникнення збоїв системні виклики `setsockopt()`, `sendfile()` та `read()` повертають значення `-1` та встановлюють змінну `errno`.

### Таблиця кодів помилок kTLS

| Числовий код `errno` | Символьна константа | Причина виникнення помилки | Спосіб вирішення та діагностика |
| :--- | :--- | :--- | :--- |
| `22` | `EINVAL` | Передано некоректний розмір структури `optlen`, непідтримувану версію TLS (`version`) або невідомий `cipher_type`. | Перевірити відповідність розміру структури `sizeof(struct tls12_crypto_info_aes_gcm_128)`. |
| `98` / `114` | `EADDRINUSE` / `EALREADY` | Спроба вдруге виконати `setsockopt(TLS_TX)` або `setsockopt(TLS_RX)` на сокеті, де контекст уже налаштовано. | Контекст kTLS є одноразовим. Для оновлення ключів викликом `setsockopt()` слід закрити сокет або використовувати `cmsg`. |
| `95` | `EOPNOTSUPP` | Ядро зкомпільовано без модуля `CONFIG_TLS` або обраний шифр не підтримується поточним драйвером SmartNIC. | Перевірити наявність модуля `modprobe tls` та вивід `ethtool -k`. |
| `74` | `EBADMSG` | Помилка перевірки аутентифікаційного теґу (Auth Tag Failure) при читанні даних `recvmsg()`. | Свідчить про пошкодження даних у мережі або розсинхронізацію `rec_seq`. |
