Зростання швидкостей у сучасних мережах та обов'язковий перехід на шифрування HTTPS створили серйозне випробування для високопродуктивних вебсерверів та мереж доставки контенту (CDN). Традиційна модель обробки протоколу Transport Layer Security (TLS) у користувацькому просторі (userspace) змушує ядро копіювати дані з дискового кешу у програму для шифрування, а потім копіювати зашифрований результат назад у ядро для передачі в мережу. Це повністю руйнує концепцію Zero-Copy і витрачає процесорний час на постійні системні виклики та переміщення байтів між регіонами пам'яті.

Для усунення цього фундаментального вузького місця інженерними командами було розроблено технологію **Kernel TLS (kTLS)**. Вона вирішує проблему шляхом розділення протоколу TLS на дві автономні фази: **Control Plane** (фаза рукостискання) залишається у користувацькому просторі у складі криптографічних бібліотек (OpenSSL, GnuTLS), а **Data Plane** (симетричне шифрування масиву даних) передається безпосередньо в мережевий стек ядра Linux.

---

## Головний механізм kTLS

Після успішного завершення асиметричного рукостискання у програмі користувача, отримані симетричні ключі (наприклад, AES-GCM 128 біт) передаються ядру за допомогою сокетних опцій `setsockopt(SOL_TLS)`. Після цього сокет у ядрі стає "TLS-обізнаним" за допомогою спеціалізованого модуля ULP (Upper Layer Protocol) `"tls"`.

```
Шлях даних при kTLS:

[ Дисковий кеш Page Cache ]
            │
            ▼ (Zero-Copy / In-Kernel Crypto)
[ Мережевий стек kTLS ULP ]
            │
            ▼ (DMA)
[ Мережева карта SmartNIC ] ──> Зашифрований трафік TLS у мережу
```

Завдяки цьому вебсервер відновлює можливість використовувати високоефективний системний виклик `sendfile()` для зашифрованих з'єднань. Ядро зчитує сторінки безпосередньо з дискового кешу (Page Cache), прозоро шифрує їх у мережевому стеку і передає у мережу без жодного виходу у простір користувача та без копіювання пам'яті.

## Режими розвантаження: TLS_SW та TLS_HW

Підсистема kTLS може працювати у двох основних режимах залежно від апаратних можливостей сервера:

1. **TLS_SW (Software Acceleration):** Симетричне шифрування виконується центральним процесором (CPU), але всередині ядра ОС через підсистему Kernel Crypto API. Це повністю усуває копіювання пам'яті між ядром і userspace, виключає перемикання контекстів та повертає можливість використання виклику `sendfile()`.
2. **TLS_HW (Hardware Offload):** Якщо у сервері встановлено мережеву карту класу SmartNIC (наприклад, Mellanox ConnectX-6), ядро передає симетричний ключ безпосередньо у драйвер адаптера. Мережева карта здійснює шифрування «на льоту» (inline) під час DMA-читання оперативної пам'яті. Це дає **повний Zero-Copy та нульове навантаження на CPU**, дозволяючи видавати понад 200 Гбіт/с зашифрованого трафіку з одного сервера.

## Керуючі повідомлення cmsg та обробка сповіщень

За замовчуванням будь-який виклик `write()` або `sendfile()` створює TLS-записи типу `Application Data` (код `23`). Для відправки сигнальних повідомлень протоколу (наприклад, TLS Alert `close_notify`, код `21`, або повідомлення переузгодження `Handshake`, код `22`) додаток використовує системний виклик `sendmsg()` із допоміжним блоком `cmsg` (Control Message) та прапорцем `TLS_SET_RECORD_TYPE`. Аналогічно при зчитуванні вхідного трафіку `recvmsg()` ядро повідомляє програму про надходження службових записів через структуру `cmsghdr`.

## Базовий приклад виклику у програмах C та C++

Активація kTLS вимагає реєстрації ULP `"tls"` та передачі криптоконтексту перед першою операцією відправки даних:

:::tabs
```c
/* Реєстрація ULP 'tls' на підключеному TCP-сокеті */
setsockopt(sock_fd, SOL_TCP, TCP_ULP, "tls", sizeof("tls"));

/* Передача симетричного ключа AES-GCM 128 біт у рівень SOL_TLS */
struct tls12_crypto_info_aes_gcm_128 crypto_info;
/* ... заповнення ключів, IV, солі та seq_num ... */
setsockopt(sock_fd, SOL_TLS, TLS_TX, &crypto_info, sizeof(crypto_info));

/* Відправка зашифрованого файлу без копіювання у пам'ять користувача */
sendfile(sock_fd, file_fd, &offset, file_size);
```
```cpp
// Ідіоматичний C++20 варіант активації kTLS
::setsockopt(sock_fd, SOL_TCP, TCP_ULP, "tls", sizeof("tls"));

struct tls12_crypto_info_aes_gcm_128 crypto_info{};
// ... заповнення ключів, IV, солі та seq_num ...
::setsockopt(sock_fd, SOL_TLS, TLS_TX, &crypto_info, sizeof(crypto_info));

::sendfile(sock_fd, file_fd, &offset, file_size);
```
:::

## Інтеграція у високорівневі вебсервери та бібліотеки

У сучасній системній розробці програмістам не потрібно писати виклики `setsockopt()` вручну. Починаючи з версії OpenSSL 3.0, підтримка kTLS додана у виклик `SSL_OP_ENABLE_KTLS`. Вебсервери NGINX та HAProxy використовують цю функцію для автоматичного ввімкнення Zero-Copy `sendfile()` при віддачі статичних файлів через HTTPS. При цьому вся асиметрична математика та перевірка сертифікатів безпеки залишається у простіру користувача, а лінійне шифрування трафіку виконує підсистема ядра Linux.

## Моніторинг, обмеження та перспективи розвитку

Перевірити роботу підсистеми kTLS у системі Linux можна за допомогою системних метрик ядра у псевдофайлі `/proc/net/tls_stat`, який відображає кількість активних програмних (`TlsTxSw`) та апаратних (`TlsTxDevice`) сокетів. Підтримка апаратного розвантаження мережевою картою перевіряється утилітою `ethtool -k eth0`. Додатковий моніторинг стану відкритих сокетів здійснюється через утиліту `ss -tneoi`.

Оскільки kTLS прив'язаний до підсистеми TCP ULP, він призначений для фундаментальних протоколів TLS 1.2 та TLS 1.3. Для новітніх протоколів на базі UDP (наприклад, QUIC та HTTP/3) розробники спільноти Linux будують аналогічні механізи розвантаження на базі підсистем eBPF та XDP, що дозволить розвантажувати UDP-пакети безпосередньо на рівні мережевих драйверів мережевої карти без додаткового копіювання пам'яті.

---

## Висновки

Технологія kTLS повертає вебсерверам продуктивність `sendfile()` у світі обов'язкового HTTPS-шифрування. Розділення складного рукостискання у userspace та симетричної обробки записів у ядрі дозволяє досягати максимальної пропускної здатності мережі з мінімальним споживанням ресурсів центрального процесора.
