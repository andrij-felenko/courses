# 📋 Інтерфейс та API детектора Kmemleak

<preknowlist>
- [Алокатори пам'яті ядра](topic:sys-unix/kernel-memory-slab) — механізми kmalloc та slab-кешів ядра Linux.
- [Псевдо-ФС: procfs, sysfs, debugfs](topic:sys-unix/debugfs-kernel-debug-vfs) — монтаж та взаємодія з віртуальними файловими системами.
</preknowlist>

Детектор витоків пам'яті ядра Kmemleak надає двоперевірковий інтерфейс: внутрішній програмний C API для розробників драйверів та підсистем ядра (оголошений у заголовочному файлі `<linux/kmemleak.h>`), а також зовнішній інтерфейс керування у віртуальній файловій системі `debugfs` за шляхом `/sys/kernel/debug/kmemleak`.

Цей довідник містить повне систематизоване зведення всіх функцій C API, прапорців, внутрішніх структур даних метаданих, правил синхронізації та текстуальних команд управління через `debugfs`, необхідних для анотування складного коду ядра та створення автоматизованих скриптів тестування.

---

## 1. Заголовочний файл та інтеграційні макроси

Програмний API Kmemleak стає доступним у коді ядра або системного модуля після підключення відповідного заголовочного файла:

```c
#include <linux/kmemleak.h>
```

Головною архітектурною особливістю реалізації `<linux/kmemleak.h>` є повна нейтральність до конфігурації збірки ядра. Якщо ядро скомпільовано без активного параметра `CONFIG_DEBUG_KMEMLEAK=y`, заголовочний файл замінює всі оголошення функцій на порожні статичні inline-заглушки (no-op stubs):

```c
#ifndef CONFIG_DEBUG_KMEMLEAK
static inline void kmemleak_alloc(const void *ptr, size_t size, int min_count, gfp_t gfp) {}
static inline void kmemleak_free(const void *ptr) {}
static inline void kmemleak_not_leak(const void *ptr) {}
static inline void kmemleak_ignore(const void *ptr) {}
static inline void kmemleak_no_scan(const void *ptr) {}
#endif
```

Завдяки цьому розробник драйвера може вільно додавати анотації Kmemleak у сирцевий код модуля. У відлагоджувальних збірках ядра з увімкненим `CONFIG_DEBUG_KMEMLEAK=y` ці анотації виконують повний аналіз досяжності, а у підготовлених для експлуатації (production) ядрах компілятор повністю вилучає їх з підсумкового двійкового коду без жодних накладних витрат продуктивності.

## 2. Анатомія структури метаданих (`struct kmemleak_object`)

Для кожного виділеного у ядрі блоку пам'яті Kmemleak внутрішньо виділяє об'єкт метаданих `struct kmemleak_object`. Ця структура є центральною ланкою алгоритму Mark-and-Sweep.

| Поле структури | Тип даних | Опис, призначення та специфіка використання |
| :--- | :--- | :--- |
| `pointer` | `unsigned long` | Віртуальна початкова адреса відстежуваного блоку пам'яті у просторі ядра. |
| `size` | `size_t` | Точний розмір виділеної області у байтах. |
| `min_count` | `int` | Мінімальна кількість знайдених вказівників, необхідна для визначення об'єкта як досяжного. За замовчуванням дорівнює `1`. Якщо встановити `min_count = 0`, об'єкт позначається як "завжди досяжний" і ніколи не генерує звіт про витік. Якщо встановити `min_count = -1`, об'єкт перевіряється на наявність посилань, але його власний вміст не сканується. |
| `count` | `int` | Лічильник вхідних посилань, знайдених під час поточного проходу сканування. Припускає від'ємні значення для системних прапорців. |
| `flags` | `unsigned int` | Бітова маска внутрішніх прапорців стану об'єкта (`KMEMLEAK_GREY`, `KMEMLEAK_NO_SCAN`, `KMEMLEAK_ALLOCATED`, `KMEMLEAK_PERSISTENT`). |
| `trace` | `unsigned long[MAX_TRACE]` | Масив адрес повернення стеку викликів (stack backtrace) на момент створення алокації. Глибина стеку визначається макросом `MAX_TRACE` (за замовчуванням 16 кадрів). |
| `rb_node` | `struct rb_node` | Вузол для включення об'єкта до глобального червоно-чорного дерева пошуку `object_tree`. Ключем пошуку є діапазон `[pointer, pointer + size]`. |
| `area_list` | `struct hlist_head` | Список спеціалізованих підрегіонів сканування, доданих через `kmemleak_scan_area()`. |
| `lock` | `raw_spinlock_t` | Низькорівневий спин-блокувальник для захисту полів структури від стану перегонів при паралельному скануванні з декількох ядер CPU. |

## 3. Повний C API ядра (`<linux/kmemleak.h>`)

### 3.1. Функції реєстрації користувацьких алокацій

Ця група функцій використовується під час створення власних підсистем виділення пам'яті (кастомних слабів, пулів сторінок або драйверів блокових пристроїв), які працюють безпосередньо з фізичною пам'яттю або виконують нетипову розмітку адресного простору.

#### `kmemleak_alloc`
Реєструє новий виділений блок пам'яті у системі відстеження Kmemleak.

```c
void kmemleak_alloc(const void *ptr, size_t size, int min_count, gfp_t gfp);
```

- **`ptr`**: Початкова віртуальна адреса виділеної області пам'яті. Якщо `ptr` дорівнює `NULL`, функція нічого не робить.
- **`size`**: Розмір області у байтах.
- **`min_count`**: Поріг посилань (зазвичай `1`).
- **`gfp`**: Прапорці алокатора пам'яті (`GFP_KERNEL`, `GFP_ATOMIC`, `GFP_NOWAIT`), які Kmemleak використовує для внутрішнього виділення структури `kmemleak_object`. У контексті переривань або спин-блокувань необхідно передавати `GFP_ATOMIC`.

#### `kmemleak_free`
Повідомляє Kmemleak про звільнення раніше зареєстрованого блоку пам'яті.

```c
void kmemleak_free(const void *ptr);
```

- **`ptr`**: Віртуальна адреса блоку пам'яті, що звільняється. Викликається безпосередньо перед або одразу після повернення пам'яті у систему. Якщо `ptr` є `NULL`, функція безпечно ігнорує виклик.

#### `kmemleak_free_part`
Видаляє з відстеження лише частину раніше зареєстрованого блоку пам'яті.

```c
void kmemleak_free_part(const void *ptr, size_t size);
```

- **`ptr`**: Початкова адреса підділянки, яка вилучається з відстеження.
- **`size`**: Розмір вилученої ділянки у байтах. Використовується при частковому звільненні буферів (наприклад, при вилученні заголовків пакетів).

#### `kmemleak_alloc_percpu` та `kmemleak_free_percpu`
Реєстрація та видалення пам'яті, виділеної окремо для кожного процесора (Per-CPU allocations).

```c
void kmemleak_alloc_percpu(const void __percpu *ptr, size_t size, gfp_t gfp);
void kmemleak_free_percpu(const void __percpu *ptr);
```

### 3.2. Функції маскування та усунення хибних спрацювань

Ці функції дозволяють розробникам ядра явно корегувати поведінку Mark-and-Sweep для запобігання появі помилкових звітів про витоки (False Positives).

#### `kmemleak_not_leak`
Повідомляє Kmemleak, що на вказаний об'єкт гарантовано немає витоку, навіть якщо під час сканування на нього не знайдено жодного вказівника з коренів.

```c
void kmemleak_not_leak(const void *ptr);
```

- **Механізм дії**: Внутрішньо встановлює `min_count = 0`. Об'єкт вважається **завжди досяжним**. Проте його власне тіло **продовжує скануватися**, тому всі вказівники, що зберігаються всередині цього блоку, будуть успішно знайдені та прослідковані Kmemleak.

#### `kmemleak_ignore`
Повністю виключає об'єкт та його вміст з поля зору Kmemleak.

```c
void kmemleak_ignore(const void *ptr);
```

- **Механізм дії**: Об'єкт повністю вилучається з червоно-чорного дерева `object_tree`. Він не вважається витоком, і його вміст **ніколи не сканується**. Використовується для великих буферів сирих даних (наприклад, файлових кешів чи відеокадрів), які гарантовано не містять вказівників мови C, що дозволяє суттєво прискорити фазу сканування.

#### `kmemleak_no_scan`
Забороняє сканування вмісту об'єкта, залишаючи сам об'єкт під наглядом детектора.

```c
void kmemleak_no_scan(const void *ptr);
```

- **Механізм дії**: Встановлює прапорець `KMEMLEAK_NO_SCAN`. Якщо вказівник на цей об'єкт буде втрачено, Kmemleak повідомить про витік. Проте внутрішній вміст блоку не аналізується на наявність вкладених посилань.

#### `kmemleak_scan_area`
Додає додаткову область сканування всередині зареєстрованого об'єкта.

```c
void kmemleak_scan_area(const void *ptr, size_t offset, size_t length, gfp_t gfp);
```

- **`ptr`**: Базова адреса об'єкта.
- **`offset`**: Зміщення у байтах від початку об'єкта.
- **`length`**: Довжина області для сканування.
- **Призначення**: Застосовується при роботі зі складними структурами, де вказівник зберігається у запакованому (packed) вигляді або зі зміщенням, яке виходить за межі стандартного вирівнювання слів.

#### `kmemleak_stop` та `kmemleak_disable`
Аварійне або програмоване вимкнення детектора у ядрі.

```c
void kmemleak_stop(void);
void kmemleak_disable(void);
```

## 4. Керівний інтерфейс Debugfs (`/sys/kernel/debug/kmemleak`)

Взаємодія системних адміністраторів та інструментів автоматизованого тестування з Kmemleak здійснюється через віртуальний файл `/sys/kernel/debug/kmemleak`.

### 4.1. Специфікація текстових команд запису

Для виконання керуючої дії у файл надсилається текстова команда за допомогою системного виклику `write()` (наприклад, через `echo <команда> > /sys/kernel/debug/kmemleak`):

| Команда | Тип виконання | Повний опис та механізм дії |
| :--- | :--- | :--- |
| `scan` | Синхронна | Негайно запускає повний цикл сканування пам'яті (Mark-and-Sweep). Запис у файл блокує викликаючий процес у просторі користувача до повного завершення обходу графу об'єктів. |
| `scan=on` | Асинхронна | Вмикає фоновий потік автоматичного сканування ядра (`kmemleak-scan`). |
| `scan=off` | Асинхронна | Зупиняє фоновий потік автоматичного сканування. При цьому ручний виклик `echo scan` залишається повністю робочим. |
| `scan=<N>` | Асинхронна | Встановлює інтервал між автоматичними проходами фонового сканування у `N` секунд (наприклад, `echo scan=120 > /sys/kernel/debug/kmemleak`). |
| `clear` | Синхронна | Очищає поточний список знайдених витоків. Усі виявлені на даний момент недосяжні об'єкти позначаються прапорцем "повідомлено" і при наступному читанні файлу приховуються, що дозволяє скинути базлайн перед тестом. |
| `off` | Незворотна | Повністю вимикає Kmemleak у працюючому ядрі та вивільняє всі внутрішні структури метаданих `kmemleak_object`. Дія є незворотною до повного перезавантаження ОС. |
| `stack=on` | Асинхронна | Вмикає збереження трасування стеку (stack trace) для кожного нового виклику алокації пам'яті. |
| `stack=off` | Асинхронна | Вимикає збереження трасування стеку при алокаціях, що зменшує накладні витрати пам'яті, але унеможливлює знаходження джерела витоку. |
| `dump=<addr>` | Синхронна | Примусово виводить у системний лог `dmesg` детальний дамп об'єкта за вказаною віртуальною адресою у шістнадцятковому форматі (наприклад, `dump=0xffff8881023b6000`). |
| `dump=all` | Синхронна | Примусово виводить у `dmesg` інформацію про всі відстежувані Kmemleak об'єкти у ядрі. |

### 4.2. Читання звітів та розшифровка результатів

При виконанні системного виклику `read()` з `/sys/kernel/debug/kmemleak` (наприклад, через команду `cat /sys/kernel/debug/kmemleak`) ядро послідовно форматує записи про всі об'єкти, які після останньої фази сканування залишилися у стані **"білий"** (недосяжний).

#### Структура текстового блоку звіту:

```text
unreferenced object 0xffff8881045a8000 (size 512):
  comm "kworker/u16:2", pid 184, jiffies 4294938210 (age 84.120s)
  hex dump (first 32 bytes):
    01 02 03 04 00 00 00 00 a0 80 5a 04 81 88 ff ff  ..........Z.....
    00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  ................
  backtrace:
    [<00000000a1b2c3d4>] kmem_cache_alloc_trace+0x140/0x2c0
    [<00000000e5f6a7b8>] my_driver_alloc_struct+0x28/0x80 [my_driver]
    [<00000000c1d2e3f4>] my_driver_probe+0x54/0x120 [my_driver]
    [<0000000087a6b5c4>] platform_probe+0x45/0x90
```

#### Детальна інтерпретація полів:

1. **`unreferenced object 0xffff8881045a8000`**: Віртуальна адреса початку виділеного блоку пам'яті в адресній просторі ядра. За цією адресою розробник може оглянути стан пам'яті через відлагоджувачі `gdb` або `crash`.
2. **`(size 512)`**: Точний розмір виділеного блоку у байтах.
3. **`comm "kworker/u16:2"`**: Назва процесу або потоку ядра, контекст якого виконував алокацію пам'яті.
4. **`pid 184`**: Ідентифікатор процесу (PID) на момент алокації.
5. **`jiffies` / `age 84.120s`**: Значення системного таймера ядра у jiffies та точний час у секундах, що минув з моменту створення алокації.
6. **`hex dump (first 32 bytes)`**: Шістнадцятковий вміст та ASCII-представлення перших 32 байтів виділеного блоку. Дозволяє ідентифікувати заголовок структури, магічні числа (magic numbers) або збережені текстові рядки.
7. **`backtrace`**: Послідовний стек адрес повернення ядерних функцій на момент алокації. Зміщення у байтах (наприклад, `my_driver_alloc_struct+0x28/0x80`) дозволяє відновити точний рядок сирцевого коду за допомогою утиліт `addr2line` або `decode_stacktrace.sh`.
