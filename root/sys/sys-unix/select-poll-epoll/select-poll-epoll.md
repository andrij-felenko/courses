- [Сокет як дескриптор](root:sys-unix/socket-as-descriptor) — з'єднання виглядає як звичайний дескриптор із буферами прийому й передачі в ядрі.

Уявіть мережевий сервер, до якого підключено десять тисяч клієнтів. У більшості з'єднань панує тиша: користувач згорнув застосунок, відкрив іншу вкладку чи чекає відповіді від бази даних. Дані в будь-яку мить надходять заледве на двохстах сокетах. Головна задача сервера — дізнатися, на яких саме дескрипторах є робота, не витрачаючи процесорний час на марне чекання.

Якщо перевіряти кожне з'єднання по черзі у неблокуючому режимі, процес зробить десять тисяч системних викликів на кожному обході й дістане дев'ять тисяч вісімсот відповідей «нічого немає». Таке постійне опитування марнує ціле ядро процесора. Якщо ж викликати звичайне блокуюче читання `read` на першому сокеті, потік засне до появи даних, але не зможе обслуговувати решту дев'ять тисяч дев'ятсот дев'яносто дев'ять клієнтів.

Розв'язок полягає у **мультиплексуванні вводу-виводу**: програма передає ядру операційної системи список усіх відкритих дескрипторів і засинає в одному системному виклику. Мережевий стек ядра самостійно стежить за буферами сокетів, будить потік у мить появи даних і повертає список лише тих дескрипторів, де справді є що читати чи писати.

## select і poll: опитування за списком від користувача

Історично першим механізмом мультиплексування Unix у 1983 році став системний виклик `select`. Його інтерфейс побудований на бітових масках `fd_set`. Програма встановлює біти для дескрипторів, за якими стежить, і передає маски ядру. 

Ця конструкція має три суттєві обмеження:
- **Жорстка стеля бітової маски.** Розмір `fd_set` обмежений константою `FD_SETSIZE` (типово 1024). Сокет із номером 1024 або вище просто не вміщується в мапу, а спроба його додати псує чужу пам'ять.
- **Перезапис маски на кожному кроці.** `select` модифікує передані маски на місці, залишаючи лише готові дескриптори. Тому перед кожним наступним викликом програма змушена будувати маску заново.
- **Лінійний обхід у ядрі.** Ядро сканує біти від нуля до найбільшого номера `maxfd`. Складність виклику становить O(N), де N — найбільший дескриптор у масці.

У 1987 році у System V Release 3 з'явився системний виклик `poll`. Замість бітових масок він використовує масив структур `struct pollfd`. Це зняло обмеження `FD_SETSIZE` та розділило запит (`events`) і відповідь ядра (`revents`), що позбавило потреби перебудовувати масив перед кожним викликом.

Проте `poll` не змінив головного: ядро все одно змушене перебирати кожен елемент масиву при кожному виклику, додавати задачу до черг очікування всіх сокетів, а після пробудження знову проходити весь масив для формування `revents`. Складність очікування залишилася лінійною — O(N). На десяти тисячах з'єднань постійне копіювання й обхід масиву створюють високу затримку й з'їдають процесорний час, навіть якщо активний лише один сокет.

## epoll: набір у ядрі та подійні сповіщення

Для подолання проблеми O(N) у Linux 2.5.44 розробили механізм `epoll`. Він змінює концепцію очікування у двох фундаментальних місцях:

1. **Список спостереження живе в ядрі.** Програма більше не пересилає масив дескрипторів при кожному виклику. Виклик `epoll_create1` створює в ядрі окремий об'єкт (який сам є файловим дескриптором). Набір змінюють викликом `epoll_ctl` — це коштує логарифм, O(log N), бо всередині червоно-чорне дерево.
2. **Асинхронний список готових подій.** Під час додавання сокета через `epoll_ctl` ядро реєструє зворотний виклик (callback) у черзі очікування сокета. Коли мережева карта приймає пакет, мережевий стек викликає цей callback, і той миттєво додає дескриптор до **списку готових** (`rdlist`).

Коли програма викликає `epoll_wait`, ядро не сканує всі дескриптори. Воно лише копіює накопичений список готових елементів у буфер користувача. Складність `epoll_wait` становить O(k), де k — кількість готових подій, і взагалі не залежить від загальної кількості відкритих сокетів N.

== C (системний виклик POSIX)
```c
int ep = epoll_create1(EPOLL_CLOEXEC);

struct epoll_event ev;
ev.events = EPOLLIN;
ev.data.fd = conn_fd;
epoll_ctl(ep, EPOLL_CTL_ADD, conn_fd, &ev);

struct epoll_event events[64];
for (;;) {
    int n = epoll_wait(ep, events, 64, -1);
    for (int i = 0; i < n; i++) {
        handle_data(events[i].data.fd);
    }
}
```
== C++ (обгортка та масив std::array)
```cpp
class Epoll {
    int epfd_;
public:
    Epoll() : epfd_(epoll_create1(EPOLL_CLOEXEC)) {
        if (epfd_ < 0) throw std::system_error(errno, std::generic_category(), "epoll_create1");
    }
    ~Epoll() { if (epfd_ >= 0) ::close(epfd_); }

    void add(int fd, uint32_t events) {
        struct epoll_event ev{};
        ev.events = events;
        ev.data.fd = fd;
        if (epoll_ctl(epfd_, EPOLL_CTL_ADD, fd, &ev) < 0) {
            throw std::system_error(errno, std::generic_category(), "epoll_ctl");
        }
    }

    int wait(std::span<struct epoll_event> events, int timeout_ms) {
        int n = epoll_wait(epfd_, events.data(), static_cast<int>(events.size()), timeout_ms);
        if (n < 0 && errno != EINTR) {
            throw std::system_error(errno, std::generic_category(), "epoll_wait");
        }
        return n;
    }
};

Epoll ep;
ep.add(conn_fd, EPOLLIN);

std::array<struct epoll_event, 64> events;
for (;;) {
    int n = ep.wait(events, -1);
    for (int i = 0; i < n; i++) {
        handle_data(events[i].data.fd);
    }
}
```
== Python (стандартний модуль select)
```python
import select

ep = select.epoll()
ep.register(conn_fd, select.EPOLLIN)

while True:
    events = ep.poll(-1)
    for fd, event in events:
        handle_data(fd)
```

## Режими сповіщення: рівень і фронт

`epoll` підтримує два режими інформування про готовність:

- **За рівнем (Level-Triggered, LT).** Типовий режим, аналогічний до `select` і `poll`. `epoll_wait` повертатиме дескриптор на кожному виклику доти, доки у буфері сокета залишаються непрочитані байти. Якщо прочитати лише частину даних, наступний `epoll_wait` знову сповістить про залишок.
- **За фронтом (Edge-Triggered, ET, `EPOLLET`).** Сповіщення надходить лише у мить **зміни стану** — коли прийшли нові дані. Якщо програма вичитає не всі байти з буфера, `epoll_wait` більше не нагадає про залишок, поки не надійде наступний пакет.

Для роботи в режимі ET дескриптор **обов'язково роблять неблокуючим** (`O_NONBLOCK`), а читання чи запис виконують у циклі до отримання помилки `EAGAIN` або `EWOULDBLOCK`. Це гарантує, що буфер вичитано повністю і система готова до очікування наступного фронту події.

## Практичні пастки та діагностика

У роботі з `epoll` найчастіше трапляються дві помилки:
1. **Зависання з'єднання в режимі ET.** Виникає, коли програма прочитала лише частину даних і не дійшла до `EAGAIN`. Наступні сповіщення не приходять, і сокет зависає.
2. **Стовідсоткове завантаження процесора при `EPOLLOUT`.** Прапорець готовності до запису `EPOLLOUT` спрацьовує завжди, коли у буфері передачі є вільне місце. Якщо не вимкнути `EPOLLOUT` після того, як надсилати вже нічого, `epoll_wait` повертатиметься миттєво й цикл крутитиметься вхолосту.

У багатопотокових серверах з пулом робочих потоків застосовують додаткові прапорці керування: `EPOLLONESHOT` гарантує, що подія віддасться лише одному потоку й дескриптор замовкне до виклику `epoll_ctl` з операцією `EPOLL_CTL_MOD`. Прапорець `EPOLLEXCLUSIVE` послаблює «громовий табун» при обробці нових з'єднань на спільному сокеті, що слухає: ядро будить не всіх, хто чекає, а одного-кількох (саме «не всіх», а не «рівно одного» — сильнішої гарантії воно не дає).

Перевірити стан наборів `epoll` у живій системі можна через файлову систему `/proc`: файл `/proc/<pid>/fdinfo/<epoll_fd>` містить список усіх зареєстрованих дескрипторів, їхні прапорці подій та внутрішні маски ядра.
