# 📋 Специфікація core_pattern, coredump_filter та suid_dumpable

Ця довідкова вставка містить вичерпну специфікацію та системний розбір параметрів ядра Linux, що відповідають за формування імен аварійних дампів, фільтрацію класів віртуальної пам'яті, керування привілеями при збереженні файлів `core` та конфігурацію системного демона `systemd-coredump`.

## 1. Специфікація шаблону `/proc/sys/kernel/core_pattern`

Параметр ядра `/proc/sys/kernel/core_pattern` являє собою текстовий рядок конфігурації, який визначає, яким чином ядро операційної системи Linux оброблятиме аварійний дамп процесу у разі фатального завершення. Максимальна допустима довжина рядка шаблону становить 128 байтів для класичного запису у файл або до 4096 байтів при використанні конвеєрного режиму обробки (pipe mode).

### Режим запису у файл (File Mode)

Якщо рядок конфігурації не починається з символу вертикальної риски `|`, ядро розглядає вказане значення як шлях до файлу на файловій системі. Якщо шлях є відносним (не починається з `/`), файл створюється у поточному робочому каталозі процесу, який зазнав краху. 

Для формування унікальних ідентифікуючих імен файлів ядро підтримує розширений набір специфікаторів форматування (форматних макросів), які починаються з символу `%`:

- **`%p` — PID процесу**: Ідентифікатор процесу (Process ID) у поточному просторі імен PID, що зазнав аварійного завершення. Це найпопулярніший специфікатор, який запобігає перезапису дампів при повторних падіннях однієї програми.
- **`%P` — PID головного потоку (PID лідера групи)**: Ідентифікатор головного процесу (`tgid` — Thread Group ID). У багатопотокових програмах `POSIX threads` кожен потік має власний TID, але спільний `tgid`. Специфікатор `%P` гарантує використання PID головного потоку.
- **`%i` — TID потоку**: Ідентифікатор конкретного потоку (Thread ID), у якому виникло апаратне переривання чи виняток, що викликав сигнал `Core`.
- **`%u` — Дійсний UID**: Дійсний ідентифікатор користувача (Real User ID), якому належав процес на момент аварії.
- **`%g` — Дійсний GID**: Дійсний ідентифікатор групи (Real Group ID) власника процесу.
- **`%s` — Номер сигналу**: Числовий номер POSIX-сигналу, що викликав генерацію дампа (наприклад `11` для `SIGSEGV`, `6` для `SIGABRT`, `8` для `SIGFPE`).
- **`%t` — UNIX Timestamp**: Час виникнення аварійної ситуації у секундах, розрахований від початку епохи (00:00:00 UTC, 1 січня 1970 року). Використовується для часового впорядкування дампів.
- **`%h` — Hostname**: Мережеве ім'я вузла (системне ім'я хоста), отримане через простір імен UTS. Корисно при використанні спільних мережевих файлових систем (NFS / Ceph).
- **`%e` — Коротке ім'я програми**: Назва виконуваного бінарного файлу (значення `comm` процесу), скорочена ядром до 16 байтів.
- **`%E` — Повний шлях до бінарника**: Повний абсолютний шлях до виконуваного файлу на файловій системі, у якому всі символи похилої риски `/` автоматично замінені на знаки оклику `!`. Це запобігає помилкам створення дочірніх каталогів (наприклад, шлях `/usr/bin/app` перетворюється на `!usr!bin!app`).
- **`%c` — Soft Limit RLIMIT_CORE**: М'який ліміт розміру аварійного дампа у байтах, встановлений для процесу на момент аварії.
- **`%d` — Режим dumpable**: Значення внутрішнього прапора ядра `dumpable` для процесу (`1` для звичайних процесів).

Повний список специфікаторів та приклади їх розгортання наведено в підсумковій таблиці нижче:

| Специфікатор | Назва параметра | Опис та семантика ядра | Приклад розгортання |
| :--- | :--- | :--- | :--- |
| `%p` | Process PID | PID процесу, що впав | `14230` |
| `%P` | Thread Group PID | PID лідера групи потоків (`tgid`) | `14200` |
| `%i` | Thread TID | TID конкретного потоку збою | `14235` |
| `%u` | Real UID | Numeric UID власника | `1000` |
| `%g` | Real GID | Numeric GID власника | `1000` |
| `%s` | Signal Number | Номер фатального сигналу | `11` (`SIGSEGV`) |
| `%t` | Timestamp | UNIX Epoch Time у секундах | `1735689600` |
| `%h` | Hostname | UTS Hostname вузла | `node-01.cluster` |
| `%e` | Executable Comm | Скорочена назва (до 16B) | `worker_node` |
| `%E` | Path Escaped | Абсолютний шлях з заміною `/` -> `!` | `!usr!local!bin!worker` |
| `%c` | RLIMIT_CORE Soft | М'який ліміт розміру | `2147483648` |
| `%d` | Dumpable Flag | Прапор dumpable процесу | `1` |

### Режим конвеєра (Pipe Mode)

Якщо рядок `/proc/sys/kernel/core_pattern` починається з символу `|`, ядро змінює стандартну поведінку. Замість безпосереднього відкриття файлу на диску ядро створює анонімний канальний буфер (pipe), запускає вказану утиліту у просторі користувача з правами суперкористувача (`root`) та підключає читальний кінець pipe до її стандартного введення (`stdin`).

Приклад реального рядка конвеєра для `systemd-coredump`:
```text
|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h
```

При роботі конвеєрного режиму ядро дотримується суворих системних правил:
1. **Простір імен (Namespaces)**: Утиліта обробки запускається в початкових (кореневих) просторах імен системного PID та Mount namespace. Якщо крах стався всередині ізольованого Docker-контейнера чи systemd-nspawn, обробник запускається на хост-системі, отримуючи доступ до віртуального адресного простору через `/proc/$PID/mem`.
2. **Буферизація та пропускні спроможності**: Якщо швидкість передачі даних через pipe перевищує розмір буфера ядра (за замовчуванням 64 КБ), ядро блокує процес запису до зчитування даних обробником. Якщо обробник не встигає зчитувати дані або зависає, запис переривається.
3. **Обмеження привілеїв**: Обробник виконується з максимальними системними привілеями (`CAP_SYS_ADMIN`), що вимагає ретельної перевірки вхідних параметрів для запобігання атакам підвищення привілеїв (Privilege Escalation).

## 2. Бітова маска фільтрації пам'яті `/proc/<pid>/coredump_filter`

Віртуальний адресний простір сучасного 64-бітного процесу може сягати терабайтів, однак не всі області пам'яті однаково важливі для локалізації причин аварії. Параметр `/proc/<pid>/coredump_filter` (або загальносистемне замовчування `/proc/sys/vm/coredump_filter`) дозволяє гнучко керувати тим, які саме класи віртуальних областей пам'яті (VMA) будуть вивантажені у сегменти `PT_LOAD` дампа.

Параметр задається у вигляді шістнадцяткової бітової маски. Кожен біт відповідає за певний тип пам'яті:

### Детальний опис бітових прапорців coredump_filter

- **Bit 0 (`0x01`) — Anonymous Private Memory**: Включає анонімну приватну пам'ять (динамічну купу heap, стек процесів, пам'ять, виділену через `malloc()` або `mmap(MAP_PRIVATE | MAP_ANONYMOUS)`). Це найважливіша частина пам'яті для зневадження, яка містить стан локальних і динамічних змінних.
- **Bit 1 (`0x02`) — Anonymous Shared Memory**: Включає анонімну спільну пам'ять (`mmap(MAP_SHARED | MAP_ANONYMOUS)`), яка використовується для міжпроцесної взаємодії (IPC).
- **Bit 2 (`0x04`) — File-backed Private Memory**: Відповідає за приватні мапінги файлів на диску (`mmap(MAP_PRIVATE)`). За замовчуванням **вимкнено**, оскільки вміст файлів можна прочитати з файлової системи, що значно економить розмір дампа.
- **Bit 3 (`0x08`) — File-backed Shared Memory**: Відповідає за спільні файлові мапінги (`mmap(MAP_SHARED)`). За замовчуванням **включено**.
- **Bit 4 (`0x10`) — ELF Headers**: Включає заголовки виконуваних ELF-файлів та відображених у пам'ять бінарних бібліотек. Необхідно для коректного виявлення версій завантажених `.so` модулів.
- **Bit 5 (`0x20`) — Private HugeTLB Pages**: Включає сторінки пам'яті великого розміру (Huge Pages 2МБ / 1ГБ), виділені через `hugetlbfs`. За замовчуванням вимкнено для запобігання створенню гігантських дампів.
- **Bit 6 (`0x40`) — Shared HugeTLB Pages**: Включає спільні великі сторінки пам'яті.
- **Bit 7 (`0x80`) — DAX Pages**: Включає сторінки файлів безпосереднього доступу (Direct Access / NVDIMM энергонезалежна пам'ять).
- **Bit 8 (`0x100`) — ARM64 MTE Memory Tags**: Спеціальний біт для архітектури ARM64, який включає теги захисту пам'яті Memory Tagging Extension.

Детальна підсумкова таблиця бітових прапорців:

| Біт | Маска | Клас віртуальної пам'яті (VMA) | Системне значення за замовчуванням |
| :--- | :--- | :--- | :--- |
| Bit 0 | `0x01` | Anonymous private (heap, stack, malloc) | **Включено** |
| Bit 1 | `0x02` | Anonymous shared (`MAP_SHARED \| MAP_ANONYMOUS`) | **Включено** |
| Bit 2 | `0x04` | File-backed private (`MAP_PRIVATE`) | Виключено |
| Bit 3 | `0x08` | File-backed shared (`MAP_SHARED`) | **Включено** |
| Bit 4 | `0x10` | ELF Headers та заголовки бінарників | **Включено** |
| Bit 5 | `0x20` | Private HugeTLB pages (2MB / 1GB) | Виключено |
| Bit 6 | `0x40` | Shared HugeTLB pages | Виключено |
| Bit 7 | `0x80` | DAX memory (NVDIMM / Persistent RAM) | Виключено |
| Bit 8 | `0x100` | ARM64 MTE Memory Tags | **Включено** |

Значення за замовчуванням у сучасних ядрах Linux становить `0x33` (включає біти 0, 1, 4 та 5).

Приклад динамічного налаштування фільтра для конкретного процесу з PID 8900:
```bash
# Перевірити поточне значення фільтра
$ cat /proc/8900/coredump_filter
00000033

# Включити абсолютно всі типи пам'яті (включно з файловими мапінгами та HugePages)
$ echo 0x7f > /proc/8900/coredump_filter
```

## 3. Режими безпеки та привілеїв `/proc/sys/fs/suid_dumpable`

Параметр ядра `/proc/sys/fs/suid_dumpable` регулює поведінку ядра при виникненні аварійних ситуацій у процесів, які змінили свої ідентифікатори користувачів чи груп (UID/GID), виконуються з setuid/setgid бітами (наприклад `/usr/bin/passwd` або `sudo`), чи володіють привілеями POSIX capabilities.

Параметр може набувати одного з трьох системних значень:

1. **`0` (`disabled`) — Повна заборона**: Системне значення за замовчуванням для більшості захищених систем. Дампи для привілейованих чи SUID-процесів **не створюються за жодних умов**. Це унеможливлює витік чутливих даних (таких як хеші паролів із `/etc/shadow`) у файли, доступні звичайним користувачам.
2. **`1` (`debug`) — Дозвіл без обмежень**: Створення дампів дозволено для всіх процесів системи незалежно від привілеїв. Файл дампа створюється у поточному каталозі з правами поточного ефективного UID процесу. Цей режим є **небезпечним** і рекомендується виключно для локальних розробницьких стендів.
3. **`2` (`suidsafe`) — Безпечний режим привілейованого дампа**: Дамп створюється лише тоді, коли у `core_pattern` вказано абсолютний шлях (починаючи з `/`) або конвеєр `|`. Файл дампа записується з власником `root` і правами доступу `0600` (читання дозволено тільки користувачу root). Це гарантує можливість налагодження системних служб без загрози безпеці даних.

## 4. Налаштування системного демона `/etc/systemd/coredump.conf`

При використанні підсистеми `systemd-coredump` додаткові параметри збереження, стискання та ротації регулюються конфігураційним файлом `/etc/systemd/coredump.conf` (або дроп-інами у `/etc/systemd/coredump.conf.d/*.conf`).

Основні директиви конфігурації:

- **`Storage=external`**: Визначає спосіб збереження дампів. Значення `external` зберігає стиснені файли у `/var/lib/systemd/coredump/`, значення `journal` зберігає дампи безпосередньо у журналі `systemd-journald`, значення `none` вимикає збереження файлів (залишаючи лише логування фактів аварії).
- **`Compress=yes`**: Вмикає стискання файлів дампів на льоту за допомогою алгоритму `zstd` (або `lz4`).
- **`ProcessSizeMax=2G`**: Максимальний розмір нес тисненого дампа в пам'яті, який `systemd-coredump` погоджується обробляти. Дампи більшого розміру ігноруються.
- **`ExternalSizeMax=2G`**: Максимальний розмір стисненого файла дампа, який може бути збережений на диск.
- **`MaxUse=10G`**: Обмеження на сумарний обсяг дискового простору у `/var/lib/systemd/coredump/`. При перевищенні цієї межі `systemd-coredump` автоматично видаляє найстаріші файли дампів.
- **`KeepFree=15%`**: Мінімальний відсоток вільного дискового простору, який сервіс зобов'язаний залишати на файловій системі.
