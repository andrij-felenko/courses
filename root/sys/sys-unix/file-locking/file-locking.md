Коли кілька процесів одночасно читають і оновлюють той самий файл — наприклад, збільшують лічильник або вносять запис у спільний журнал, — виникає стан перегонів. Якщо один процес читає значення, а другий у цей же момент пише нове, результат першого запису перезапишеться й зникне. Жоден окремий системний виклик `read` чи `write` не рятує від цієї проблеми: між читанням і подальшим записом минає час, протягом якого значення у файлі вже змінилося.

Для безпечної паралельної роботи потрібний механізм, який діє протягом усієї критичної ділянки — від першого прочитаного байта до останнього записаного.

## Чому прапорці у файловій системі не працюють

Перша ідея, яка виникає для координації доступу, — створювати окремий файл-прапорець (наприклад, `app.lock`) за допомогою атомарного виклику `open(path, O_CREAT | O_EXCL)`. Якщо файл-позначка вже існує, виклик повертає помилку `EEXIST`, і процес чекає.

Головна вада цього підходу виявляється при аварійному завершенні процесу. Якщо програма гине від сигналу `SIGKILL`, помилки пам'яті або раптового знеструмлення, створений файл-позначка залишається на диску. Наступні запуски вважатимуть, що файл усе ще зайнятий, і зависнуть у чеканні назавжди.

Спроби записувати у файл номер процесу (`PID`) і перевіряти, чи він ще живий, не вирішують проблему: операційна система з часом перевикористовує номери процесів. До того ж сама перевірка «чи живий власник» і подальше вилучення застарілого файлу — це дві окремі дії з проміжком часу, у який знову встигає вклинитися інший процес.

Надійний замок має керуватися стороною, яка гарантовано дізнається про смерть процесу й автоматично прибере замок. В операційній системі такою стороною є лише ядро. Тому файлові замки в Unix є об'єктами всередині ядра, прив'язаними до системних ресурсів.

## Кому належить замок: три моделі в Linux

Ядро Linux підтримує три види файлових замків. Головна відмінність між ними полягає в тому, що саме ядро вважає власником замка.

### 1. flock: замок на опис відкритого файлу

З'явився у BSD Unix. Замикає файл цілком і прив'язується до **опису відкритого файлу** (open file description):

:::tabs
```c
#include <sys/file.h>

/* Взяти виключний замок (чекати за потреби) */
flock(fd, LOCK_EX);

/* Зняти замок */
flock(fd, LOCK_UN);
```
```cpp
#include <sys/file.h>
#include <system_error>

/* Взяти виключний замок у C++ */
void lock_exclusive(int fd) {
    while (flock(fd, LOCK_EX) != 0) {
        if (errno == EINTR) continue;
        throw std::system_error(errno, std::generic_category(), "flock LOCK_EX failed");
    }
}

void unlock(int fd) {
    flock(fd, LOCK_UN);
}
```
:::

Оскільки власником є опис відкритого файлу, замок має такі принципові властивості:
- Після `fork()` дочірній процес ділить той самий замок із батьківським, бо обидва посилаються на один опис файлу.
- Після `exec()` замок зберігається, якщо дескриптор не позначено прапорцем `FD_CLOEXEC`.
- Якщо процес відкриває той самий файл вдруге через новий `open()`, створюється новий опис файлу, який буде конфліктувати з першим.
- Замок автоматично знімається ядром, коли закривається останній дескриптор цього опису або коли процес помирає.
- Перехід із читацького замка `LOCK_SH` на виключний `LOCK_EX` не є атомарним: ядро спершу знімає старий замок, а потім бере новий, залишаючи вікно перегонів.

Це робить `flock` найпростішим інструментом для захисту служб від повторного запуску або для координації роботи з цілими файлами.

### 2. POSIX-замки: замок на діапазон і процес

Визначені стандартом POSIX через системний виклик `fcntl()`. Вони дозволяють блокувати окремі діапазони байтів (байтові замки), що важливо для паралельної роботи баз даних.

Власником POSIX-замка ядро вважає **пару «процес + inode»**. Це створює дві серйозні проблеми:
1. **Зникнення замка при будь-якому `close()`:** якщо процес має два відкритих дескриптори на один і той самий файл і закриває будь-який із них, ядро тихо знімає **всі** POSIX-замки цього процесу на цей файл.
2. **Відсутність захисту між потоками:** потоки одного процесу мають однаковий `PID`, тому для ядра вони є одним власником. Один потік не може заблокувати діапазон байтів від іншого потоку того ж процесу.

На відміну від `flock`, зміна типу POSIX-замка на діапазоні є атомарною і не втрачає захисту.

### 3. OFD-замки (Open File Description locks)

Додані в Linux 3.15 (і включені до POSIX.1-2024). Вони поєднують найкраще від двох попередніх підходів: працюють із діапазонами байтів, як POSIX-замки, але власником є **опис відкритого файлу**, як у `flock`.

:::tabs
```c
#define _GNU_SOURCE
#include <fcntl.h>

struct flock fl = {
    .l_type   = F_WRLCK,
    .l_whence = SEEK_SET,
    .l_start  = 0,
    .l_len    = 0,       /* 0 — до кінця файлу */
    .l_pid    = 0        /* Обов'язково 0 для OFD */
};

/* Взяти OFD-замок */
fcntl(fd, F_OFD_SETLKW, &fl);
```
```cpp
#define _GNU_SOURCE
#include <fcntl.h>
#include <system_error>

void lock_ofd_range(int fd, off_t start, off_t len, short type) {
    struct flock fl{};
    fl.l_type = type;
    fl.l_whence = SEEK_SET;
    fl.l_start = start;
    fl.l_len = len;
    fl.l_pid = 0;

    while (fcntl(fd, F_OFD_SETLKW, &fl) == -1) {
        if (errno == EINTR) continue;
        throw std::system_error(errno, std::generic_category(), "F_OFD_SETLKW failed");
    }
}
```
:::

OFD-замки не зникають при випадковому закритті сусіднього дескриптора й дозволяють потокам одного процесу виключати одне одного, якщо кожен потік відкрив файл окремим викликом `open()`.

## Замки є консультативними

Усі три види замків у сучасній Linux є **консультативними** (advisory). Це означає, що ядро перевіряє наявність замка тільки тоді, коли процес сам звертається по замок через `flock` чи `fcntl`. Якщо сторонній процес відкриє файл і почне читати чи писати без запиту замка, ядро дозволить цю операцію.

Файловий замок — це домовленість між програмами, які погодилися дотримуватися правил. Примусове блокування (mandatory locking) виявилося ненадійним — запис через відображення файлу в пам'ять узагалі не проходив перевірки, а між перевіркою й самим доступом лишалася та сама гонка, — і його остаточно вилучили з ядра Linux 5.15.

## Інспекція замків у системі

Інформація про всі активні замки в системі доступна у віртуальному файлі `/proc/locks`. У ньому відображаються вид замка (`FLOCK`, `POSIX`, `OFDLCK`), режим доступу (`READ` або `WRITE`), PID процесу-власника (або `-1` для OFD) та межі замкненого діапазону. Зручніший інтерфейс для огляду замків дає утиліта `lslocks`, яка зіставляє PID і inode із реальними іменами процесів та шляхами до файлів.

## Як обрати потрібний механізм

1. **`flock`** — коли потрібно заблокувати файл цілком і важлива простота (наприклад, перевірка єдиного примірника демона чи одноразовий запуск скрипту).
2. **OFD-замки** — сучасно й надійно для роботи з діапазонами байтів у багатопотокових або багатопроцесних програмах на Linux (POSIX.1-2024).
3. **POSIX-замки** — блокування діапазонів на старих Unix-системах, де OFD-замків немає; вимагає суворого контролю відкриття й закриття дескрипторів (не відкривати той самий файл двічі в одному процесі).
