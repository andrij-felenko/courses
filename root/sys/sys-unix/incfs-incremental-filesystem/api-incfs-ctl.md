# 📋 Специфікація Control-файлів та ioctl-інтерфейсу IncFS

При монтуванні інкрементальної файлової системи IncFS у кожній точці монтування створюються спеціальні службові псевдофайли контролю (`.pending_reads`, `.log`, `.index`), а файлова система надає розширений набір команд `ioctl` для створення псевдофайлів, заповнення відсутніх блоків даними, інспектування стану сторінок та передачі прав доступу. Нижче наведено повну специфікацію системних структур даних та команд керування IncFS ядра Linux згідно із заголовним файлом ядра `<linux/incrementalfs.h>`.

## Службові Control-файли в корені монтування

Всі службові файли знаходяться у кореневому каталозі змонтованого екземпляра IncFS і мають імена, що починаються з крапки. Вони слугують основними каналами зв'язку між підсистемою ядра та користувацьким сервісом дозавантаження.

### 1. Псевдофайл `.pending_reads`

Спеціальний пристроєвий файл подій. Демон користувацького простору (`IncrementalService` або `DataLoader`) відкриває цей файл у режимі читання (`O_RDONLY`) для отримання сповіщень про потоки ядра, що заблокувалися на очікуванні відсутніх блоків даних.

Псевдофайл повністю підтримує механізм неблокуючого введення-виведення через системні виклики `poll()`, `select()` та `epoll()`. Файл генерує подію `EPOLLIN`, коли в черзі ядра з'являється принаймні один незадоволений запит на читання від будь-якого процесу в системі.

Зчитування з файла повертає масив структур `incfs_pending_read_info` (або `incfs_pending_read_info2` в новіших версіях ядра), які містять точні координати відсутнього блоку.

Цитата UAPI-структури із заголовочного файлу ядра `<linux/incrementalfs.h>`:

```c
/* Заголовок ядра <linux/incrementalfs.h> — Структура інформації про запит читання */
struct incfs_pending_read_info {
    __u64 file_id_low;     /* Нижні 64 біти 128-бітного UUID файлу */
    __u64 file_id_high;    /* Верхні 64 біти 128-бітного UUID файлу */
    __u32 timestamp_us;    /* Мікросекундна позначка часу виникнення запиту */
    __u32 block_index;     /* Індекс відсутнього 4KB блоку у файлі */
};
```

В оновленій версії IncFS (v2) додано розширену структуру `incfs_pending_read_info2`, яка додатково передає uid процесу, що зробив запит, та ідентифікатор сесії читання, що дозволяє пріоритетизувати завантаження даних для активного додатку на передньому плані.

### 2. Псевдофайл `.log`

Файл журналу операцій читання. Використовується для реалізації випереджального дозавантаження (*predictive prefetching*).

При зчитуванні з `.log` демон отримує записи про всі спроби читання блоків (як успішні, так і заблоковані). Це дозволяє фоновому сервісу аналізувати послідовність звернень додатку до ресурсів і завчасно замовляти з мережі наступні блоки (наприклад, файли текстур наступної ігрової локації) до того, як потік користувача наткнеться на відсутню сторінку.

Цитата UAPI-структури із заголовочного файлу ядра `<linux/incrementalfs.h>`:

```c
/* Заголовок ядра <linux/incrementalfs.h> — Запис у журналі читання */
struct incfs_log_record {
    __u64 file_id_low;     /* Нижні 64 біти UUID */
    __u64 file_id_high;    /* Верхні 64 біти UUID */
    __u32 block_index;     /* Індекс зчитаного блоку */
    __u32 flags;           /* Прапори типу операції (просте читання / mmap) */
    __u32 timestamp_us;    /* Час операції */
};
```

### 3. Каталог `.index`

Спеціальний каталог індексації за унікальним ідентифікатором файлу (File ID).

Він містить посилання, імена яких відповідають шістнадцятковому представленню 128-бітного File ID. Це дозволяє демон-процесу відкривати файл за його унікальним UUID незалежно від того, в якому підкаталозі чи під якою назвою файл знаходиться в дереві VFS, усуваючи загрозу збоїв при перейменуванні файлів додатком.

## Інтерфейс команд ioctl

Операції керування IncFS виконуються через `ioctl()` на одному з двох дескрипторів: кореневого каталогу монтування — створення файлів і передача права заповнення, або самого інкрементального файлу — заповнення блоків та інспекція їхнього стану.

При успішному виконанні `INCFS_IOC_FILL_BLOCKS` відбуваються наступні атомні кроки в ядрі:

1. Ядро записує наданий блок у базову файлову систему.
2. Внутрішній бітмап наявності блоків файлу оновлюється (біт блоку стає рівним 1).

## Інспекція через sysfs та procfs

Діагностика стану IncFS у запущеній системі Linux здійснюється через інтерфейс `procfs` та `sysfs`:

- **Параметри монування у `/proc/mounts`:**
  Показує опції монтування екземпляра IncFS: `read_timeout_ms` (таймаут блокування потоку у мілісекундах), `read_log_buffer_pages` (розмір кільцевого буфера журналу читання), `report_perms` (режим звітності прав доступу).

- **Статус підсистеми у `/sys/fs/incremental-fs/`:**
  Каталог `/sys/fs/incremental-fs/features/` містить прапорці доступних у цій збірці ядра можливостей: `corefs` (є завжди), `v2`, `zstd`. Крім того, монтування з опцією `sysfs_name=<ім'я>` створює окремий вузол `/sys/fs/incremental-fs/instances/<ім'я>` зі статистикою саме цього екземпляра.

## Таблиця помилок системних викликів IncFS

| Код помилки | Константа C | Опис причини виникнення |
| :--- | :--- | :--- |
| **`62`** | `ETIME` | Потік читання заблокувався на відсутньому блоці, і час очікування (`read_timeout_ms`) вичерпався до того, як демон заповнив блок. |
| **`5`** | `EIO` | Не вдалося записати блок у базову файлову систему або дані від демона пошкоджені. Блок, що не збігся з деревом Меркла, ядро теж відкидає з помилкою — точний код залежить від версії. |
| **`22`** | `EINVAL` | Некоректний розмір блоку (не кратний 4096 байтам), або спроба заповнити блок поза межами розміру файлу. |
| **`17`** | `EEXIST` | Спроба повторно створити файл з існуючим у файловій системі File ID. |
