# 📜 Історія створення IncFS та Android Incremental Delivery

Мобільні ігри класу AAA та сучасні інтерактивні додатки досягли обсягів, які раніше були притаманні лише настільним ПК та консолям. Коли розмір ігрового дистрибутива перевищує 15–20 гігобайт, традиційна модель завантаження «завантаж повністю — тоді грай» перетворюється на нездоланний бар'єр. Користувач, який бачить вимогу чекати пів години або годину перед першим запуском, часто скасовує встановлення. Інженери Google зіштовхнулися з цією проблемою під час підготовки Android 11 і створили технологію **Android Incremental Delivery**, серцем якої стала спеціалізована файлова система ядра Linux — **IncFS** (*Incremental File System*).

## Еволюція дистрибуції додатків у екосистемі Android

У перших версіях операційної системи Android розмір установочного файлу APK (*Android Package*) обмежувався 50 мегабайтами. Зі зростанням роздільної здатності екранів, складності тривимірної графіки та якості звукового супроводу цей ліміт швидко вичерпався. Розробники ігор змушені були пакувати ресурси у зовнішні файли розширення OBB (*Opaque Binary Blob*) вагою до 2 гігобайт кожен.

Згодом Google запровадила формат Android App Bundle (AAB) та сервіс Play Asset Delivery (PAD). Вони дозволили динамічно компонувати APK під конкретну архітектуру графічного процесора, мовні пакунки та щільність пікселів екрана.

Однак фундаментальна проблема дистрибуції лишалася недоторканою: процес `pm install` (пакетний менеджер Android) вимагав наявності повного файлу APK та усіх його ресурсів на дисковому накопичувачі пристрою до моменту запуску програми. 

Для мобільних ігор на рушіях Unreal Engine та Unity це створювало критичний бар'єр у воронці залучення користувачів (*user acquisition funnel*):

```
Традиційний підхід (Android 1.0 - 10.0):
[ Завантаження 100% (20 ГБ) ] ──> [ Перевірка та pm install ] ──> [ Перший запуск ]
Час очікування до першого запуску: 45–60 хвилин

Incremental Delivery (Android 11+ / IncFS):
[ Завантаження 10% (2 ГБ) ] ──> [ Миттєвий запуск ігрового меню ] ──> [ Потокове дозавантаження 90% ]
Час очікування до першого запуску: 3–5 хвилин
```

Щоб скоротити час від натискання кнопки «Встановити» до появи початкового екрана гри, виникла ідея *інкрементального запуску*: дозволити операційній системі виконувати код додатку та читати ресурси початкових рівнів тоді, коли решта 90% даних ще знаходяться на віддалених серверах дистрибуції або передаються через кабель USB.

## Пошук архітектурного рішення: Чому наявні інструменти не підійшли

Розробники Android у компанії Google розглядали декілька існуючих у ядрі Linux механізмів для реалізації лінивого завантаження даних, проте кожен із них мав критичні недоліки, що унеможливлювали їх використання у мобільній ОС.

### 1. FUSE (Filesystem in Userspace)

Найбільш очевидним вибором здавалася файлова система у просторі користувача [FUSE](root:sys-unix/fuse-userspace-filesystems). Підсистема FUSE дозволяє перехоплювати всі файлові операції VFS і передавати їх у демон користувацького простору через пристроєвий файл `/dev/fuse`.

**Чому відмовилися:** FUSE створює колосальне накладне навантаження на підсистему введення-виведення. Кожне читання сторінки пам'яті через `read()` або підкачування сторінки при [відображенні mmap](root:sys-unix/mmap-model) вимагає подвійного переключення контексту між ядром та користувацьким простором, пересилання повідомлень через черги та копіювання буферів. Для 3D-ігор, які виконують тисячі операцій IOPS при зчитуванні текстур та аудіофайлів з архівних контейнерів (файли `.pak` або `.assets`), FUSE спричиняв просідання частоти кадрів (FPS) на 30–50% та надмірне споживання енергії акумулятора.

### 2. Механізм userfaultfd

Механізм `userfaultfd` дозволяє демон-процесу користувача обробляти збої сторінок (*page faults*) у віртуальній пам'яті інших процесів.

**Чому відмовилися:** Механізм `userfaultfd` працює виключно на рівні віртуальної пам'яті процесу, а не на рівні файлової системи та сторінкового кешу ядра (*page cache*). Він не інтегрується з системними викликами `read()`, `preadv()`, `readdir()`, не підтримує спільне використання сторінок між різними процесами та вимагає спеціальних привілеїв ядра (`CAP_SYS_PTRACE`), що неприпустимо з міркувань суворої системи розмежування прав Android Sandbox.

### 3. Пряма модифікація ext4 або f2fs

Пряма модифікація основних дискових файлових систем Android (ext4 або f2fs) дозволила б реалізувати відсутні блоки безпосередньо в інодах накопичувача.

**Чому відмовилися:** Це порушило б модульність ядра Linux та концепцію Generic Kernel Image (GKI). Зміни в дисковому форматі ext4 або f2fs унеможливили б апстрім у звичайне ядро Linux та створили б проблему сумісності при оновленні версій ядра мобільними вендорами (Samsung, Qualcomm, MediaTek).

## Народження IncFS (Incremental File System)

Команда Android-інженерів Google запропонувала принципово новий підхід: створити легку **шарувату файлову систему ядра** (*stacked VFS filesystem*). Перші патчі IncFS надіслав до списку розсилки `linux-fsdevel` у травні 2019 року інженер Google Євген Земцов (Eugene Zemtsov), проте робота від початку була командною.

Файлова система IncFS монтується поверх існуючого каталогу основної файлової системи (ext4 або f2fs), використовує її для збереження фізичних блоків даних, але повністю контролює віртуальне дерево файлів, стан наявності блоків та черги очікування потоків у ядрі.

```
+-------------------------------------------------------+
|            Додаток (Користувацький простір)           |
+-------------------------------------------------------+
                           | sys_read() / page fault
                           v
+-------------------------------------------------------+
|                     Ядро: VFS                         |
+-------------------------------------------------------+
                           |
                           v
+-------------------------------------------------------+
|                    Модуль IncFS                       |
|   (Блокує потік, якщо блок відсутній на диску)        |
+-------------------------------------------------------+
        |                                   |
        | ioctl / .pending_reads            | фізичний запис
        v                                   v
+-----------------------+       +-----------------------+
| Incremental Service   |       |  Базова FS (ext4/f2fs)|
| (Завантажує з мережі) |       |  (Зберігає блоки)     |
+-----------------------+       +-----------------------+
```

Основні віхи розвитку IncFS:

- **2019 рік:** Публікація перших патчів IncFS у поштовому розсиланні Linux Kernel Mailing List (LKML) та інтеграція в гілку ядра Android 4.19 / 5.4.
- **2020 рік (Android 11):** Дебют Android Incremental Delivery. Інструмент `adb install-incremental` дозволив розробникам завантажувати ігри на тестові пристрої в 5–10 разів швидше через інструментарій розробника.
- **2021 рік (Android 12):** Вихід другої версії IncFS (v2). Інтеграція IncFS із підсистемою [fs-verity](root:sys-unix/fs-verity) для перевірки криптографічних хеш-дерев Меркла під час дозавантаження блоків та додавання підтримки прозорого стиснення LZ4/ZSTD.
- **Android 13+:** IncFS стала обов'язковим компонентом вимог Android Compatibility Definition Document (CDD) для всіх пристроїв, що поставляються з новими версіями ядра Linux.

Завдяки тому, що IncFS реалізована як внутрішній модуль ядра, вона досягає нативної швидкості читання вже заповнених блоків без жодних накладних витрат FUSE, забезпечуючи прозорий доступ до даних для будь-яких стандартних викликів POSIX.
