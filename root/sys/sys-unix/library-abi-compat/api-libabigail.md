# 📋 Довідник інструментарію libabigail для аналізу ABI

Інструментарій **libabigail** (Application Binary Interface Analysis and Instrumentation Generic Analysis Infrastructure Library) є створеним компанією Red Hat набором C++ бібліотек та утиліт командного рядка для автоматичного виявлення та запобігання несумісним змінам в ABI між різними версіями спільних бібліотек у форматі ELF. На відміну від простих утиліт текстового порівняння заголовків C/C++, libabigail будує внутрішнє аналітичне дерево розібраних типів даних, сигнатур функцій та розмірів об'єктів на основі відлагоджувальної інформації DWARF, яка вбудовується у бінарні `.so` файли під час компіляції з прапорцем `-g`.

## Принцип роботи з відлагоджувальною інформацією DWARF

Під час компіляції сирцевих файлів із прапорцем `-g` компілятори GCC та Clang записують у спеціальні секції ELF-файлу (`.debug_info`, `.debug_abbrev`, `.debug_str`, `.debug_types`) точний опис усіх типів даних, полів структур із їхніми фізичними зсувами (offsets), параметрів функцій, констант та вирівнювань.

Утиліти `libabigail` зчитують ці секції і конструюють внутрішню модель інтерфейсу бібліотеки у вигляді графа типів (Intermediate Representation, IR). При порівнянні двох версії бібліотеки інструмент зіставляє кожну структуру, об'єднання, перелічення, сигнатуру функції та глобальну змінну, шукаючи зміну розмірів, вирівнювання, зсуви полів чи виключення функцій з експорту.

## Основні утиліти командного рядка

### 1. `abidiff` — порівняння двох бінарних файлів

Головна утиліта `abidiff` порівнює ABI двох бинарних файлів (`.so`, виконуваних файлів або об'єктних `.o`), які скомпільовані з відлагоджувальними символами DWARF.

```bash
abidiff [опції] <lib_v1.so> <lib_v2.so>
```

#### Ключові прапорці та параметри `abidiff`

- `--suppressions <file.suppr>` — застосувати XML-файл пригнічення сповіщень. Це дозволяє приховати сповіщення про свідомі зміни або внутрішні неекспортовані типи, які не ламають публічний ABI.
- `--headers-dir1 <dir>` та `--headers-dir2 <dir>` — вказати каталоги публічних заголовкових файлів C/C++ для відповідних версій бібліотеки. Завдяки цьому `abidiff` аналізує лише ті типи та функції, які дійсно є доступними для зовнішніх користувачів у публічному API, відсікаючи приватні внутрішні деталі реалізації.
- `--drop-private-types` — повністю ігнорувати зміни у внутрішніх приватних типах даних, які не є часткою експортованої поверхні API.
- `--impacted-interfaces` — обмежити звіт лише тими змінами у типах та структурах, які безпосередньо впливають на сигнатури публічно експортованих функцій.
- `--dump-diff-tree` — виводити деталізоване внутрішнє дерево відмінностей ABI для глибокого аналізу механіки несумісності.
- `--stat` — виводити лише стислу підсумкову статистику змінених типів, доданих та вилучених символів без розгортання структур.

#### Значення кодів повернення `abidiff`

Під час роботи у системі автоматичного збирання CI/CD утиліта `abidiff` сигналізує про результат через стандартний код повернення (exit code) процесу:

- `0` — бінарний інтерфейс повністю сумісний. Змін в ABI не виявлено.
- `1` — виявлено критичну несумісність ABI (ABI break). Збірка в CI має вважатися невдалою.
- `2` — помилка виконання самої утиліти (наприклад, невірно вказано шляхи до файлів або у бінарних файлах відсутній розділ `.debug_info` DWARF).
- `4` — виявлено зміни в ABI, але вони є сумісними розширеннями (наприклад, додавання абсолютно нових символів без зміни існуючих типів).

### 2. `abidw` — генерація та збереження XML-зліпку ABI

Утиліта `abidw` аналізує бінарний файл бібліотеки і зберігає повне представлення її ABI у вигляді XML-документа спеціального формату (ABIXML). Це дозволяє зберегти легкий текстовий зліпок ABI у репозиторії сирцевого коду, щоб перевіряти нові збірки без збереження старих бінарних `.so` файлів.

У XML-структурі ABIXML фіксуються всі відношення між типами: розміри в бітах, розташування полів у структурах, таблиці символів ELF та версії у секції `.gnu.version`.

```bash
# Створення XML-зліпку ABI для випуску версії 1.0
abidw --out-file libfoo-1.0.xml libfoo.so.1.0.0

# Порівняння нової версії бібліотеки зі збереженим XML-зліпком
abidiff libfoo-1.0.xml libfoo.so.2.0.0
```

### 3. `abicompat` — перевірка сумісності виконуваного файлу з бібліотекою

Утиліта `abicompat` перевіряє, чи буде конкретна скомпільована програма продовжувати працювати з новою версією спільної бібліотеки. Вона читає залежності програми та перевіряє, чи надає нова бібліотека всі необхідні символи та типи даних без порушення зсувів.

```bash
abicompat app_binary libfoo.so.2.0.0
```

### 4. `abipkgdiff` — порівняння бінарних пакетів дистрибутиву

Утиліта `abipkgdiff` витягує спільні бібліотеки та їхні відлагоджувальні символи безпосередньо з пакетів системних менеджерів (RPM або DEB) і виконує перевірку сумісності між версіями пакетів. Інструмент автоматично знаходить відповідні підпакети з відлагоджувальними символами (debuginfo / dbgsym) та порівнює кожен експортований файл `.so`.

```bash
abipkgdiff --package1 libfoo-1.0-1.x86_64.rpm --package2 libfoo-1.1-1.x86_64.rpm
```

### 5. `kabi-dw` — аналіз ABI ядра Linux (KABI)

Спеціалізована утиліта для контролю бінарного інтерфейсу модулів ядра Linux (Kernel ABI). Вона порівнює експортовані символи ядра `EXPORT_SYMBOL` та внутрішні структури даних ядерних драйверів, дозволяючи системним адміністраторам гарантувати сумісність драйверів при оновленнях ядра.

## Конфігурація правил пригнічення (Suppressions XML)

При розвитку бібліотеки виникнення деяких попереджень про зміни ABI є очікуваним (наприклад, видалення приватних внутрішніх полів або застарілих функцій, які не входили у стабільну угоду). Щоб `abidiff` не блокував пайплайн CI/CD на таких змінах, створюють файл XML-конфігурації правил пригнічення.

Правила дозволяють фільтрувати сповіщення за категоріями: за назвою структури, іменем функції, зміною розміру або приватним статусом типу.

```xml
<abi-suppr>
  <!-- Ігнорувати зміни у внутрішній приватній структурі private_data_t -->
  <type-suppr 
    type-kind='struct'
    name='private_data_t'
    is-private='yes'/>

  <!-- Пригнітити сповіщення про вилучення застарілої функції legacy_init -->
  <function-suppr
    name='legacy_init'
    change-kind='function-removed'/>

  <!-- Свідоме ігнорування зміни розміру структури ConfigContext -->
  <type-suppr
    type-kind='struct'
    name='ConfigContext'
    has-size-change='yes'/>

  <!-- Пригнітити зміни у функціях за регулярним виразом імені -->
  <function-suppr
    name-regexp='^internal_.*'/>

  <!-- Пригнітити зміни у файлах конкретного модуля -->
  <file-suppr
    source-file-path-regexp='src/internal/.*'/>
</abi-suppr>
```

### Синтаксис основних елементів пригнічення

- `<type-suppr>`: Фільтрує типи (struct, class, union, enum). Підтримує атрибути `name`, `name-regexp`, `type-kind`, `has-size-change`, `is-private`.
- `<function-suppr>`: Фільтрує функції. Підтримує атрибути `name`, `name-regexp`, `change-kind` (значення: `function-removed`, `function-added`, `parameter-change`).
- `<variable-suppr>`: Фільтрує глобальні змінні. Підтримує атрибути `name`, `name-regexp`, `type-name`.

## Інтеграція перевірок ABI у пайплайн CI/CD

Автоматизована перевірка ABI включається у скрипти збирання проєкту (наприклад, GitHub Actions або GitLab CI).

Нижче наведено практичний приклад кроку CI для автоматичної перевірки збереження сумісності динамічної бібліотеки при створенні пулл-реквесту:

```bash
#!/usr/bin/env bash
set -euo pipefail

# 1. Збирання поточного коду з прапорцями DWARF
gcc -g -O2 -shared -fPIC -Wl,-soname,libtarget.so.1 -o build_new/libtarget.so src/*.c

# 2. Витягування еталонного зліпку ABI з репозиторію
ABIDIFF_SUPPR="config/abi-suppressions.suppr"
REFERENCE_ABI="config/reference-abi-1.0.xml"

# 3. Виконання перевірки abidiff
if ! abidiff --suppressions "${ABIDIFF_SUPPR}" "${REFERENCE_ABI}" build_new/libtarget.so; then
    echo "ERROR: ABI break detected! Please review structural changes or update SONAME version."
    exit 1
fi

echo "SUCCESS: ABI compatibility confirmed."
```

Використання XML-файлів пригнічення у поєднанні з автоматизованими скриптами CI/CD дозволяє розробникам системних бібліотек розділити критичні небажані порушення ABI від свідомих та узгоджених етапів еволюції програмного інтерфейсу.
