# 📜 Історія зламу C++11 ABI у GCC: перехід від COW до SSO в std::string

Історичний випадок зміни бінарного інтерфейсу (ABI) у стандартній бібліотеці C++ (`libstdc++`) компілятора GCC показує, як зміна вимог мовного стандарту C++11 примусила розробників системного програмного забезпечення змінити внутрішню структуру фундаментального класу `std::string`, створивши найбільший ризик бінарної несумісності в історії Linux-екосистеми.

## Оптимізація Copy-on-Write (COW) у C++98 та її передумови

У 1990-х роках під час розробки стандарту C++98 оперативна пам'ять комп'ютерів була відносно повільною та обмеженою за обсягом, а багатопотокові процесори ще не набули масового поширення. Компіляційні бібліотеки прагнули оптимізувати копіювання рядків. Більшість реалізацій стандартної бібліотеки C++, зокрема GNU `libstdc++` (GCC v3 та v4), реалізували оптимізацію **Copy-on-Write (COW)** для класу `std::basic_string`.

Основна ідея COW полягала у тому, що при виконанні присвоєння або копіювання рядків (`std::string s2 = s1;`) виділення нової динамічної пам'яті та фізичне копіювання символів не виконувалися.

Замість цього сам об'єкт `std::string` у пам'яті мав мінімальний фізичний розмір — лише один вказівник (8 байтів на 64-бітній архітектурі x86_64). Цей вказівник посилався на єдину спільну структуру в купі, яка містила метадані (лічильник посилань `refcount`, ємність буфера `capacity` та довжину рядка `length`) та безпосередній масив символів:

```
Об'єкт s1 (8 B) ──┐
                  ├─► Буфер у купі:
Об'єкт s2 (8 B) ──┘   [ refcount=2 | capacity=16 | length=11 | "Hello World\0" ]
```

Справжнє виділення нової пам'яті та дублювання символів відбувалося лише у той момент, коли один із рядків намагався модифікувати свій вміст (наприклад, при виклику `s2[0] = 'h'`).

## Конфлікт стандарту C++11 та багатопотоковості

З появою стандарту C++11 у 2011 році використання оптимізації COW у `std::string` виявилося повністю несумісним із новими вимогами мови до багатопотоковості та гарантій для ітераторів.

### Поломка інвалідації ітераторів та посилань

Стандарт C++11 (розділ 21.4.1) чітко встановив правила щодо інвалідації посилань та ітераторів: неконстантні виклики `operator[]` або `begin()` повертають посилання на символ, яке не повинно інвалідуватися при подальшому читанні з інших екземплярів рядка.

У підході COW виклик неконстантного `s1[0]` для читання не міг заздалегідь знати, чи збирається викликаючий код модифікувати символ через отримане посилання `char&`. Тому компілятор був змушений негайно виконувати розділення буфера (unshare) та копіювання пам'яті. Це призводило до того, що просте читання символу через `s1[0]` могло непередбачувано інвалідувати посилання `s2[0]`, отримане з іншого об'єкта, що посилався на той самий буфер.

### Накладні витрати на атомарне синхронування

Другою фундаментальною проблема стала підтримка багатопотоковості. Оскільки об'єкти `std::string` могли передаватися між різними потоками виконання, будь-яка зміна лічильника посилань `refcount` вимагала використання важких атомарних системних інструкцій (`lock cmpxchg` на x86_64).

В атомарній підтримці COW витрати часу на міжпроцесорну синхронізацію та ефекти хибного розділення кеш-ліній (false sharing) повністю знищили початковий виграш у швидкості від відсутності копіювання пам'яті.

У результаті комітет стандартизації C++11 зафіксував вимоги до `std::basic_string`, які зробили оптимізацію COW нелегальною. Бібліотеки були змушені перейти на оптимізацію малих рядків — **SSO (Short String Optimization)**.

## Зміна внутрішньої структури у пам'яті (Memory Layout)

У реалізації SSO малі рядки (до 15 символів на 64-бітних системах) зберігаються безпосередньо у внутрішньому локальному масиві усередині самого об'єкта `std::string` без виклику розроджувальних системних алокаторів `malloc()`.

Це викликало катастрофічну зміну фізичного розміру та структури класу `std::string`:

- **Старий COW std::string (GCC 4.x):** Фізичний розмір об'єкта дорівнював **8 байтам** (один вказівник на буфер).
- **Новий SSO std::string (GCC 5+):** Фізичний розмір об'єкта зріс до **32 байтів** (вказівник на буфер, розмір `size`, ємність `capacity` та локальний масив `char buffer[16]`).

Уявіть ситуацію у системі Linux: старий виконуваний файл, скомпільований компілятором GCC 4.8 під старий COW ABI, передає за посиланням `std::string` у нову динамічну бібліотеку `.so`, зібрану GCC 5.1 під новий SSO ABI.

Стара програма виділяє на своєму стеку лише 8 байтів під об'єкт `std::string`. Нова бібліотека приймає об'єкт і намагається прочитати поля `capacity` та `buffer`, звертаючись за зсувами від `0x08` до `0x20`. Бібліотека читає та записує довільні дані на стеку старої програми. Результатом є негайне руйнування пам'яті (memory corruption) та аварійне завершення `SIGSEGV`.

## Дуальний ABI у GCC 5 та специфікатори `[abi:cxx11]`

Для того щоб уникнути одночасного зламу всіх скомпільованих бінарних файлів у Linux-дистрибутивах, розробники компілятора GCC 5.1 запровадили масштабний механізм дуального ABI (Dual ABI).

Замість прямої заміни класу у заголовкових файлах, у бібліотеці `libstdc++` було створено новий клас усередині inline-простору імен: `std::__cxx11::basic_string`.

Завдяки механізму inline namespaces у C++, новий код компілюється із використанням `std::__cxx11::string`, а компілятор додає до кожної функції, яка приймає або повертає новий рядок, спеціальний атрибут ABI-тегу `[abi:cxx11]`:

```cpp
// Манґльований символ у старому ABI (COW, GCC 4.x):
// _Z3fooPSt12basic_stringIcSt11char_traitsIcESaIcEE

// Манґльований символ у новому ABI (SSO C++11, GCC 5+):
// _Z3fooB5cxx11PNSt7__cxx1112basic_stringIcSt11char_traitsIcESaIcEEE
```

Компілятор GCC надав спеціальний макрос для вибору ABI під час збирання проєкту:

```cpp
// Використання старого COW ABI (для сумісності з застарілими бінарними бібліотеками)
#define _GLIBCXX_USE_CXX11_ABI 0

// Використання нового SSO C++11 ABI (значення за замовчуванням починаючи з GCC 5)
#define _GLIBCXX_USE_CXX11_ABI 1
```

Динамічна бібліотека стандартної системи `libstdc++.so.6` одночасно експортувала дві повноцінні версії символів для кожної функції. Якщо старий бінарний файл викликав функцію, динамічний лінкер спрямовував виклик до старої версії із COW-рядками, а нові бінарні файли лінкувалися з новими символами SSO.

## Міграція Linux-дистрибутивів

Перехід на новий C++11 ABI вимагав координації розробників усіх провідних дистрибутивів Linux (Red Hat Enterprise Linux, Fedora, Debian, Ubuntu).

Дистрибутивам довелося повністю перекомпільовувати тисячі системних бібліотек та пакетів (зокрема Boost, Qt, GTK), щоб перевести їх на новий SSO ABI. Ця міграція розтягнулася на кілька років (2015–2018 роки).

Перехід від COW до SSO у `std::string` продемонстрував розробникам системного програмного забезпечення, що зміна внутрішнього memory layout фундаментальних типів мови вимагає розробки глобальних адаптаційних шарів на рівні компілятора та системного динамічного завантажувача.
