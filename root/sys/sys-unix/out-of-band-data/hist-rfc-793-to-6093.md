# 📜 Еволюція термінових даних TCP: від RFC 793 до RFC 6093

Розбіжність у трактуванні покажчика терміновости TCP між ранніми специфікаціями RFC 793 та RFC 1122 призвела до трьох десятиліть несумісності між операційними системами, уразливостей брандмауерів та остаточного визнання механізму застарілим у RFC 6093.

Історія позасмугових даних у мережевих протоколах сягає часів мережі ARPANET та протоколу NCP (Network Control Protocol), який передував сучасному стеку TCP/IP. У 1970-х роках при використанні віддалених терміналів (Telnet) виникла гостра потреба переривати обчислювальні процеси на мейнфреймах. Якщо віддалена програма потрапляла в нескінченний цикл і заповнювала мережевий канал кілобайтами тексту, користувач не міг зупинити її зі свого термінала, оскільки команда скасування натисканням клавіш `Ctrl+C` чекала б у черзі доставки годинами.

## 1. Народження специфікацій: RFC 761 та RFC 793

У вересні 1981 року під керівництвом Джона Постела (Jon Postel) було опубліковано фундаментальний стандарт **RFC 793** ("Transmission Control Protocol"), який остаточно зафіксував архітектуру TCP. Задум авторів полягав у тому, щоб надати прикладним протоколам (Telnet, FTP, Rlogin) універсальний інструмент просування пріоритетних команд.

В ARPANET Telnet було визначено дві основні командні послідовності:
- **`IP` (Interrupt Process):** Вимога негайно зупинити виконання поточного процесу.
- **`AO` (Abort Output):** Вимога припинити вивід даних на термінал користувача, зберегши при цьому сам процес.

Для передачі цих команд розробники TCP ввели в заголовок протоколу однобітний прапорець `URG` (Urgent Flag) та 16-бітне беззнакове поле `Urgent Pointer`. Ідея полягала в тому, що відправник міг у будь-який момент позначити наступний байт як терміновий і відправити сегмент із `URG=1`.

Проте у тексті RFC 793 формулювання щодо обчислення покажчика терміновості виявилося неоднозначним і містило фатальну текстову суперечність:

> "The urgent pointer points to the sequence number of the octet following the urgent data."

Згідно з цим первинним формулюванням (RFC 793), якщо порядковий номер сегмента дорівнює `1000`, а терміновий байт знаходиться за зміщенням `2` (тобто байт з номером sequence `1002`), значення `Urgent Pointer` має дорівнювати `3` (вказуючи на перший байт *після* термінових даних, тобто `1003`).

## 2. Великий розкол BSD та помилка 4.2BSD UNIX

У 1983 році Дослідницька група комп'ютерних систем (CSRG) університету Берклі випустила операційну систему **4.2BSD UNIX**, яка містила першу комерційно успішну реалізацію стека TCP/IP, написану Біллом Джоєм (Bill Joy) та Семюелом Леффлером (Samuel Leffler).

Під час реалізації мережевого коду в ядрі BSD розробники витлумачили інструкцію RFC 793 інакше: вони вирішили, що `Urgent Pointer` повинен вказувати безпосередньо **на останній байт самих термінових даних**. Тобто для термінового байта з порядковим номером `1002` у заголовку TCP записувалося значення `Urgent Pointer = 2`.

```
Схема розбіжності покажчика терміновости:

[Seq 1000] [Seq 1001] [Seq 1002 (OOB)] [Seq 1003]
                        |               |
                        |               +-- Urgent Pointer = 3 (RFC 793 / RFC 1122 Standard)
                        +------------------ Urgent Pointer = 2 (4.2BSD / Windows Winsock Implementation)
```

Код 4.2BSD та 4.3BSD став основою для більшості комерційних операційних систем того часу: SunOS від Sun Microsystems, Ultrix від DEC, HP-UX від Hewlett-Packard, AIX від IBM, а пізніше — і для мережевого стека Microsoft Windows Sockets (Winsock). 

У результаті помилкова реалізація BSD поширилася по всьому світу і стала фактичним стандартом де-факто (De Facto Standard).

## 3. Спроба стандартизації в RFC 1122 та поява параметр tcp_stdurg

У жовтні 1989 року Роберт Браден (Robert Braden) випустив специфікацію **RFC 1122** ("Requirements for Internet Hosts -- Communication Layers"). Розділ 4.2.2.4 цього документа спробував поставити крапку в суперечках і офіційно підтвердив строгу версію RFC 793:

> "The urgent pointer points to the sequence number of the octet following the urgent data... An implementation MUST support this interpretation."

Проте було занадто пізно. Виправлення цього поля в існуючих операційних системах зламало б сумісність із мільйонами розгорнутих UNIX-серверів та персональних комп'ютерів.

Коли в 1990-х роках розроблявся мережевий стек ядра Linux (під керівництвом Алана Кокса та Олексія Кузнецова), було прийнято компромісне інженерне рішення:
- За замовчуванням стек Linux працює за BSD-інтерпретацією (мінус 1 байт від RFC 1122).
- Додано глобальний системний параметр `/proc/sys/net/ipv4/tcp_stdurg`. Якщо переключити його в `1`, ядро починає дотримуватися суворого стандарту RFC 1122.

## 4. Ера мережевих атак: WinNuke та обхід NIDS

Розбіжність у специфікаціях створила фундаментальні проблеми для безпеки комп'ютерних мереж у 1990-х та 2000-х роках.

### 4.1. Атака WinNuke (1997)

У травні 1997 року в мережі Інтернет поширився експлойт під назвою **WinNuke** (`winnuke.c`). Атака полягала в надсиланні одного TCP-пакета з прапорцем `URG=1` на порт 139 (NetBIOS Session Service) комп'ютера під управлінням Windows 95 або Windows NT 4.0.

Через помилку перевірки меж у драйвері `TCPIP.SYS` обробка покажчика терміновості викликала вихід за межі масиву пам'яті ядра, що призводило до негайного падіння системи в "синій екран смерті" (BSOD). Ця атака показала, наскільки вразливою є обробка виняткових станів TCP-заголовків.

### 4.2. Обхід систем виявлення вторгнень (NIDS Evasion)

У 1998 році Томас Птачек (Thomas Ptacek) та Тімоті Ньюшем (Timothy Newsham) опублікували класичну працю *"Insertion, Evasion, and Denial of Service: Eluding Network Intrusion Detection"*.

Автори довели, що різниця в інтерпретації `Urgent Pointer` між NIDS (які аналізували трафік за RFC 1122) та цільовими ОС (які виконували код BSD/Linux) дозволяє атакуючим непомітно проводити будь-які експлойти через мережеві брандмауери Snort чи ISS RealSecure. Зсуваючи бінарну сигнатуру атаки на 1 байт за допомогою прапорця `URG`, зловмисник змушував NIDS бачити один потік байтів, а цільовий сервер — зовсім інший.

## 5. Фінальний вердикт: RFC 6093

До початку 2010-х років накопичилося забагато аргументів проти подальшого використання механізму `MSG_OOB`:
1. **Ненадійність доставки при Zero-Window:** Якщо вікно TCP закрите, OOB-байт застрягає в мережі.
2. **Неможливість передачі структур:** Механізм гарантує збереження лише 1 байта.
3. **Блокування Middlebox-пристроями:** Мережеві екрани почали масово обнуляти прапорець `URG` для нейтралізації NIDS-атак.

У травні 2011 року Робоча група IETF з транспорту опублікувала **RFC 6093** (*"On the Implementation of the TCP Urgent Mechanism"*), авторами якого виступили Фернандо Гонт (Fernando Gont) та Андрій Юрченко (Andrew Yourtchenko).

Специфікація RFC 6093 офіційно оголосила механізм TCP Urgent Pointer **застарілим (Deprecated)** для створення нових прикладних протоколів. Сучасна мережева архітектура остаточно перейшла на використання окремих керуючих TCP-сокетів (Control Plane) або мультплексованих потоків фреймів у протоколах HTTP/2, HTTP/3 та QUIC.
