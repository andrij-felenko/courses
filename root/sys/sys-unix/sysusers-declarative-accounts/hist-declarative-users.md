# 📜 Історія еволюції управління системними акаунтами в UNIX: від імперативних скриптів до sysusers.d

Управління системними користувачами та групами в операційних системах UNIX пройшло еволюційний шлях від ручного редагування текстових конфігурацій у 1970-х роках та використання імперативних інсталяційних скриптів до впровадження декларативного стандарту `sysusers.d` у сучасній екосистемі systemd.

## Перші десятиліття UNIX: ручне редагування та текстова база даних

У ранніх версіях Research Unix (1970-ті роки) модель ідентифікації користувачів спиралася на два прості текстові файли: `/etc/passwd` для користувачів та `/etc/group` для груп. Кожен запис містив текстовий логін, числовий ідентифікатор UID або GID, домашній каталог та системну оболонку. Оскільки кількість системних служб у тогочасних комп'ютерах вимірювалася одиницями (демон друку `lpd`, поштовий агент `cron`, службовий акаунт `daemon`), розподіл UID здійснювався вручну системним адміністратором.

Адміністратор просто відкривав файл у текстовому редакторі (наприклад, `ed` або `vi`) або використовував утиліти формату `vipw` для забезпечення виключного блокування файлу під час редагування. Стандартні системні користувачі (`root` з UID 0, `bin` з UID 1, `daemon` з UID 2) мали фіксовані номери, прописані у первинному дистрибутиві системних вихідних кодів AT&T Unix.

З появою комерційних Unix-систем (BSD, SunOS, HP-UX, AIX) та перших дистрибутивів Linux на початку 1990-х років кількість службових процесів почала стрімко зростати. Для автоматизації додавання користувачів у системні файли було створено імперативні утиліти `useradd`, `groupadd` та `usermod`. Вони брали на себе роботу з читання поточного стану `/etc/passwd`, пошуку першого вільного UID у визначеному діапазоні та додавання нового рядка.

## Ера пакетних менеджерів: імперативні скрипти під час інсталяції

У середині 1990-х років розвиток дистрибутивів Linux (Debian, Red Hat Linux, Slackware) привів до появи пакетних менеджерів (`dpkg`, `rpm`). Кожен демон або вебсервер (наприклад, `Apache HTTPd`, `PostgreSQL`, `BIND`) поставлявся у вигляді пакету. Для виконання принципу найменших привілеїв службові демони більше не могли запускатися від імені `root`. Їм потрібні були власні непривілейовані акаунти — `www-data`, `postgres`, `named`.

Оскільки дистрибутиви підтримували процедуру встановлення пакетів у живій системі, створення користувачів було покладено на скрипти поізольованої інсталяції (`postinst` у Debian або `%pre` / `%post` у RPM). Типовий скрипт пакету виглядав так:

```bash
if ! getent passwd postgres >/dev/null 2>&1; then
    useradd -r -g postgres -d /var/lib/postgresql -s /bin/false postgres
fi
```

Цей імперативний підхід створив низку фундаментальних проблем, які турбували мейнтейнерів дистрибутивів протягом двох десятиліть:

1. **Недетермінованість UID та GID між машинами.** Якщо в кластері з десяти серверів пакет `postgres` встановлювався на перший сервер до пакета `redis`, то `postgres` отримував UID 998, а `redis` — UID 997. На другому сервері порядок інсталяції міг бути протилежним: `redis` отримував UID 998, а `postgres` — 997. Це спричиняло критичні збої при використанні мережевих файлових систем (NFS), коли права доступу до файлів визначалися числовими UID, а не текстовими іменами.
2. **Складність прибирання та деінсталяції.** Видалення пакету за допомогою `apt remove` або `rpm -e` зазвичай не видаляло системного користувача з міркувань безпеки (щоб не залишити "сирітських" файлів, якими пізніше міг би заволодіти новий користувач із тим самим UID). Проте імперативні скрипти не залишали жодного метаданого слідку про те, який саме пакет створив даного користувача.
3. **Гонка ресурсів (Race Conditions).** При паралельному встановленні кількох пакетів декілька скриптів одночасно викликали `useradd`. Попри використання файлових блокувань у `useradd`, скрипти часто завершувалися з помилкою або залишали бази даних `/etc/passwd` у неузгодженому стані.
4. **Спроби централізованої статичної резервації.** Дистрибутив Debian намагався розв'язати проблему за допомогою пакету `base-passwd`, який жорстко зафіксував діапазон UID від 0 до 99 за конкретними службами. Проте списку статичних UID не вистачало для тисяч сучасних пакетів, а додавання кожного нового користувача вимагало оновлення базового пакету дистрибутива.

## Поява систем без стану (Stateless OS) та образного розгортання

На початку 2010-х років інфраструктура розгортання Linux пережила парадигмальний зсув. З'явилися концепції "Immutable Infrastructure", контейнеризації (Docker, LXC) та операційні системи з незмінним (read-only) системним розділом `/usr` (CoreOS, ChromeOS, пізніше Fedora Silverblue, SteamOS, MicroOS).

У таких системах каталог `/etc` розглядається як локальна конфігурація адміністратора, яка на новоствореному екземплярі системи може бути абсолютно порожньою (`/etc` без `/etc/passwd` та `/etc/group`). Під час першого завантаження операційна система повинна автоматично згенерувати мінімально необхідні облікові записи для роботи фундаментальних системних служб.

Імперативні скрипти пакета `useradd` виявилися повністю непридатними для цієї моделі:
* Під час збирання образу дистрибутива (наприклад, за допомогою `mkosi` або `btrfs snapshot`) `useradd` вимагав запуску повного середовища chroot та наявності інтерпретатора оболонки `bash`.
* У разі скидання системи до заводських налаштувань (Factory Reset шляхом очищення `/etc`) імперативні скрипти більше не запускалися, оскільки пакунки вже були розпаковані в `/usr`.

## Народження systemd-sysusers

У 2014 році в рамках проєкту systemd Леннарт Поттерінг (Lennart Poettering) запропонував механізм `systemd-sysusers`. Ідея полягала у переході від імперативних команд до декларативних маніфестів стану, за аналогією з тим, як `systemd-tmpfiles` керує тимчасовими файлами та каталогами.

Замість того щоб виконувати кодові скрипти, кожен пакет поставляє простий декларативний файл конфігурації у `/usr/lib/sysusers.d/<package>.conf`. Цей файл описує бажаний кінцевий стан: "У системі повинен існувати користувач `postgres` з описаним описом, домашнім каталогом та приналежністю до груп".

Впровадження `systemd-sysusers` забезпечило три ключові переваги:

* **Декларативність та атомарність.** Бінарна утиліта `systemd-sysusers` зчитує всі файли конфігурації за один прохід, будує в пам'яті повну граф-структуру необхідних користувачів і груп, перевіряє наявні записи в `/etc/passwd` та вносить необхідні доповнення за один атомарний крок.
* **Підтримка монтажу Read-Only та Stateless Boot.** Якщо `/etc/passwd` відсутній на момент завантаження, `systemd-sysusers` автоматично створює новий базовий файл `/etc/passwd`, заповнюючи його на основі конфігурацій із `/usr/lib/sysusers.d/`. Це дозволило реалізувати повноцінне завантаження безстанових систем (Stateless Systems).
* **Сумісність із генерацією образів (Offline Image Provisioning).** Розробники операційних систем отримали можливість викликати `systemd-sysusers --root=/target/rootfs` під час збирання образів на сервері збірки без використання chroot чи виконання сторонніх скриптів.

Сьогодні декларативний підхід `sysusers.d` став стандартом де-факто в більшості провідних дистрибутивів Linux (Arch Linux, Fedora, openSUSE, Debian), забезпечуючи надійну та передбачувану роботу системного рівня ОС.
