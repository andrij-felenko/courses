Автоматизований скрипт щоночі підключається до репліки бази даних для створення резервної копії. Якщо з'єднання вимагає введення пароля, процес зупиняється на очікуванні вводу в порожньому терміналі; якщо ж зашити пароль у скрипт чи змінні середовища, перший-ліпший витік логів або читання пам'яті процесу віддає доступ зловмиснику. Коли ж адміністратор налаштовує безпарольний вхід за ключем, але хмарний провайдер перестворює віртуальну машину з новою мережевою адресою, підключення раптово аварійно завершується червоним попередженням про зміну ідентифікатора віддаленого вузла, повністю блокуючи конвеєр копіювання.

Ці дві ситуації демонструють обидва боки однієї фундаментальної проблеми розподілених систем: як довести серверу, що клієнт має право виконувати команди від імені конкретного користувача, і як клієнту переконатися, що трафік надсилається саме цільовому серверу, а не проміжному маршрутизатору перехоплювача.

Протокол SSH розв'язує обидві задачі за допомогою асиметричної криптографії, розділяючи процес на два незалежні механізми: автентифікацію клієнта через список дозволених публічних ключів у файлі `~/.ssh/authorized_keys` та перевірку автентичності сервера через базу довірених хост-ключів у файлі `~/.ssh/known_hosts`.

## Криптографічні алгоритми ключів: від факторів RSA до кривих Едвардса

Асиметрична криптографія в SSH застосовується для двох різних цілей: узгодження сеансового ключа симетричного шифрування під час обміну ключами (Key Exchange, KEX) та підтвердження ідентичності сторін через цифрові підписи. Для підпису сторона використовує пару з закритого (private) та відкритого (public) ключів: закритий ключ тримається в таємниці й ніколи не передається мережею, а відкритий публікується для перевірки підписів.

Історично в OpenSSH використовувалися чотири сімейства асиметричних алгоритмів: RSA, DSA, ECDSA та Ed25519. Їхня математична основа, розміри та стійкість до атак кардинально різняться.

### Алгоритм RSA: факторизація великих чисел

Криптосистема RSA базується на складності факторизації великого складеного числа `n = p * q`, де `p` і `q` — великі випадкові прості числа. Відкритий ключ містить модуль `n` та відкриту експоненту `e` (зазвичай 65537), а закритий ключ містить секретну експоненту `d`, обчислену через модулярне обернення `e mod phi(n)`.

Підпис RSA для хешу повідомлення `m` обчислюється як `s = m^d mod n`. Перевірка полягає у піднесенні до степеня з відкритим ключем: `m_check = s^e mod n`.

Головний недолік RSA — швидкість деградації стійкості проти факторизації за допомогою загального решета числового поля (GNFS). Якщо для стійкості 128 бітів симетричного шифру достатньо 256-бітного ключа на еліптичній кривій, то для досягнення такого самого рівня безпеки RSA вимагає розміру модуля не менше 3072 бітів (а для 256-бітного рівня безпеки — понад 15360 бітів).

Великі модулі RSA (3072–4096 бітів) створюють значні накладні витрати:
1. Генерація пари ключів вимагає тривалого пошуку простих чисел і перевірки їх на простоту тестами Міллера — Рабіна.
2. Розмір публічного ключа становить сотні байтів, а підпис займає від 384 до 512 байтів у кожному пакеті автентифікації.
3. Піднесення до степеня з великим секретним числом `d` вимагає застосування захисту від атак за часом (blinding), інакше час виконання модулярного множення розкриває біти числа `d`.

Крім того, застарілий алгоритм підпису `ssh-rsa` використовував хеш-функцію SHA-1. Через практичну реалізацію колізій SHA-1 проєкт OpenSSH у версії 8.8 (жовтень 2021 року) вимкнув `ssh-rsa` за замовчуванням. Сучасні інсталяції підтримують RSA лише з хешами SHA-2 (`rsa-sha2-256` та `rsa-sha2-512`), проте сам формат RSA розглядається як спадковий (legacy).

### Алгоритм DSA та його вилучення

Алгоритм цифрового підпису DSA (Digital Signature Algorithm, FIPS 186-2) був обов'язковим стандартом на етапі створення SSH-2 (RFC 4253). DSA базується на обчисленні дискретного логарифма у скінченному полі `F_p`.

Стандарт FIPS 186-2 жорстко обмежував розмір простого модуля `p` значенням 1024 біти, а розмір підгрупи `q` — 160 бітами (у парі з SHA-1). Це обмежувало максимальну криптостійкість ключа критично низьким значенням у 80 бітів.

Найнебезпечнішою властивістю DSA виявилася потреба у виборі криптографічно випадкового числа `k` для кожного підпису. Якщо генератор випадкових чисел реалізовано з дефектом, і те саме значення `k` використано двічі для підпису різних повідомлень, закритий ключ відновлюється за допомогою простого ділення у полі за кілька мікросекунд. Ба більше, навіть витік кількох бітів `k` дозволяє знайти ключ за допомогою розв'язання задачі прихованого числа (Hidden Number Problem) на ґратках.

Через комбінацію малого розміру модуля та критичної вразливості до якості генератора випадкових чисел підтримку DSA було вимкнено в OpenSSH 7.0 (2015 рік) і повністю видалено з джерельного коду в OpenSSH 9.8 (2024 рік). Детальний аналіз історії цієї кризи викладено в [📜 Історичний розвиток ключів SSH: від DSA й підозр до кривих NIST до тріумфу Ed25519](root:sys-unix/ssh-keys-and-host-trust/hist-dsa-and-nist-curves.md).

### Алгоритм ECDSA на кривих NIST

Стандартизований у RFC 5656 алгоритм ECDSA переніс математику підпису DSA на групи точок еліптичних кривих форми Вейєрштрасса:

```text
y^2 = x^3 - 3x + b (mod p)
```

Для SSH було стандартизовано три криві Федерального агентства стандартів США (NIST): `ecdsa-sha2-nistp256` (P-256 / secp256r1), `ecdsa-sha2-nistp384` (P-384) та `ecdsa-sha2-nistp521` (P-521).

ECDSA скоротив розмір відкритого ключа до 64 байтів (для P-256) при високій теоретичній стійкості (128 бітів), проте зберіг усі вразливості DSA щодо одноразового числа `k`. Повторне використання `k` або витік навіть 2–3 бітів ентропії під час підпису повністю розкриває закритий ключ користувача.

Додатково криві форми Вейєрштрасса мають різні математичні формули для додавання двох різних точок (`P + Q`) та подвоєння однієї точки (`2P`). Якщо реалізація скалярного множення не є абсолютно константною за часом (constant-time), процесорні кеші та передбачувачі переходів створюють витоки інформації про біти закритого ключа через побічні канали виконання (side-channel attacks).

### Алгоритм Ed25519: сучасний інженерний стандарт

Алгоритм Ed25519 (EdDSA над скрученою кривою Едвардса Curve25519), створений Даніелем Бернштейном, Танею Ланге та колегами, позбавлений усіх недоліків попередників.

Крива визначається рівнянням над скінченним полем простого числа 2^255 - 19:

```text
-x^2 + y^2 = 1 - (121665 / 121666) * x^2 * y^2
```

Ключові архітектурні переваги Ed25519:

1. **Детерміністичний розрахунок підпису:** Замість запиту до генератора випадкових чисел під час кожного підпису, число `r` обчислюється як криптографічний хеш `r = SHA-512(private_seed || message)`. Це унеможливлює атаку повторного використання `k`: однакове повідомлення завжди дає однаковий підпис, а різні повідомлення гарантовано отримують різні `r`, навіть якщо генератор випадкових чисел ядра завис або пошкоджений.
2. **Повні закони додавання (Complete Addition Formulas):** Формула додавання точок на кривій Едвардса є єдиною для будь-яких пар точок (`P == Q` або `P != Q`) і не містить особливих точок ділення на нуль. Це дозволяє реалізувати криптографічні операції за фіксовану кількість тактів процесора (constant-time), гарантуючи захист від атак за часом і витоків через кеш-пам'ять.
3. **Компактність і швидкість:** Публічний ключ займає рівно 32 байти (стиснута координата `y` плюс знаковий біт `x`), а підпис — 64 байти. Операції перевірки та створення підпису виконуються в рази швидше за RSA та ECDSA.

Усі нові ключі в сучасних Unix/Linux інфраструктурах слід генерувати виключно за алгоритмом Ed25519.

## Безпечна генерація ключів і внутрішній формат OpenSSH

Генерація пари ключів на робочій станції виконується за допомогою утиліти `ssh-keygen`. Стандартний виклик для створення надійної пари ключів Ed25519:

```bash
$ ssh-keygen -t ed25519 -a 100 -C "bohdan@workstation-2026" -f ~/.ssh/id_ed25519
```

Ця команда створює два файли у каталозі `~/.ssh`:
- `id_ed25519` — приватний закритий ключ з правами `0600` (читання/запис лише для власника).
- `id_ed25519.pub` — відкритий публічний ключ з правами `0644`.

### Анатомія рядка публічного ключа

Файл `id_ed25519.pub` містить один текстовий рядок, розбитий пробілами на три поля:

```text
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIG54U1...zR9Q bohdan@workstation-2026
```

1. **Тип ключа (`ssh-ed25519`):** Ідентифікатор криптографічного алгоритму за стандартом IANA/SSH.
2. **Тіло відкритого ключа у Base64:** Двійковий блок у кодуванні SSH wire format. Для Ed25519 цей блок складається з довжини рядка типу ключа (4 байти uint32 Big-Endian), рядка `ssh-ed25519` (11 байтів), довжини відкритого ключа (4 байти uint32 зі значенням 32) та власне 32 байтів відкритого ключа. Загальний розмір двійкового блоку становить 51 байт (68 символів у Base64).
3. **Коментар (`bohdan@workstation-2026`):** Довільний рядок опису, який не впливає на криптографічну перевірку, але полегшує адміністрування та аудит списків дозволених ключів.

### Новий двійковий формат приватного ключа проти застарілого PEM

Історично утиліти OpenSSH використовували формат OpenSSL PEM (PKCS#1 / PKCS#8), що починався рядком `-----BEGIN RSA PRIVATE KEY-----`. У форматі PEM шифрування закритого ключа парольною фразою виконувалося через застарілу схему KDF (Key Derivation Function) на базі хешів MD5 або одного раунду SHA-1. Через низьку обчислювальну складність таких хешів зловмисник, викравши зашифрований файл ключа з диска, міг перебирати мільярди варіантів парольних фраз на секунду за допомогою графічних процесорів (GPU).

Починаючи з версії 6.5, OpenSSH перейшов на власний двійковий формат (`-----BEGIN OPENSSH PRIVATE KEY-----`), внутрішню структуру якого показано нижче.

![Внутрішня структура нового двійкового формату приватних ключів OpenSSH](/root/sys/sys-unix/ssh-keys-and-host-trust/img/ssh-key-file-format.svg)
*Двійкова структура нового формату приватного ключа OpenSSH: відкритий заголовок метаданих, виведення ключів через KDF bcrypt та розшифрований блок перевірки цілісності.*

Формат файлу відкрито починається з магічного заголовка `openssh-key-v1\0` та незашифрованого блоку метаданих:
- `cipher_name` (string): Алгоритм шифрування закритого тіла (зазвичай `aes256-ctr` або `chacha20-poly1305@openssh.com`, або `none` для ключа без парольної фрази).
- `kdf_name` (string): Функція виведення ключа (зазвичай `bcrypt` або `none`).
- `kdf_options` (string): Блок параметрів KDF, що містить 16 байтів випадкової солі (`salt`) та 32-бітне ціле число раундів обчислень (`rounds`).
- `num_keys` (uint32): Кількість ключів у контейнері (зазвичай 1).
- `public_key` (string): Копія відкритого ключа суб'єкта у незашифрованому вигляді. Це дозволяє демону `ssh-agent` зчитувати відбиток і публічний ключ без запиту парольної фрази у користувача.

### Роль параметра `-a 100` (KDF bcrypt)

Зашифроване тіло приватного ключа захищається симетричним шифром (AES-256-CTR). Симетричний ключ і вектор ініціалізації (IV) генеруються з парольної фрази користувача за допомогою функції `bcrypt_pbkdf`:

```text
key, iv = bcrypt_pbkdf(passphrase, salt, rounds, key_len + iv_len)
```

Функція `bcrypt_pbkdf` базується на алгоритмі шифрування Blowfish зі зміненим розкладом ключів, який вимагає постійного випадкового доступу до 4 КіБ таблиць S-box у пам'яті. Це робить перебір на спеціалізованих мікросхемах ASIC та відеокартах надзвичайно дорогим.

За замовчуванням `ssh-keygen` використовує лише 16 раундів KDF bcrypt. Прапорець `-a 100` (або `-a 250`) збільшує кількість раундів до 100. На сучасному процесорі генерація та розшифрування ключа затримується на комфортні 0.1–0.3 секунди для живої людини, проте підбір парольної фрази зловмисником офлайн сповільнюється у сотні разів, перетворюючи навіть відносно прості парольні фрази на стійкий захист.

### Перевірка цілісності після дешифрування (checkints)

Усередині розшифрованого блоку першими йдуть два 32-бітних випадкових цілих числа: `checkint1` та `checkint2`. Під час створення файлу вони генеруються однаковими. Коли користувач вводить парольну фразу, OpenSSH розшифровує перші 8 байтів і перевіряє умову `checkint1 == checkint2`. Якщо числа збігаються, парольна фраза вважається вірною, і парсер переходить до читання закритого ключа. Якщо числа різні, програма миттєво повідомляє про невірний пароль (`incorrect passphrase`) без спроби інтерпретувати наступні пошкоджені байти.

## Авторизація клієнта: файл authorized_keys та конвеєр обмежень

Коли клієнт ініціює підключення, він надсилає запит `SSH_MSG_USERAUTH_REQUEST` із типом `publickey`, передаючи свій відкритий ключ. Сервер звіряє наданий ключ зі списком у файлі `~/.ssh/authorized_keys` цільового користувача. Якщо ключ знайдено, сервер генерує challenge — блок даних, що містить унікальний ідентифікатор сеансу (`Session ID`), сформований на фазі KEX. Клієнт підписує цей challenge закритим ключем і повертає підпис. Сервер перевіряє підпис відкритим ключем і, у разі успіху, вважає автентифікацію пройденою.

Клієнт у жодний момент не передає закритий ключ серверу, що робить автентифікацію за ключем стійкою до компрометації навіть у разі підключення до недовірених серверів.

![Механіка авторизації клієнта та конвеєр обмежень у authorized_keys](/root/sys/sys-unix/ssh-keys-and-host-trust/img/authorized-keys-flow.svg)
*Конвеєр автентифікації клієнта: перевірка прав StrictModes у файловій системі, криптографічна перевірка challenge та застосування списку обмежень authorized_keys.*

### Права доступу у файловій системі та перевірка StrictModes

Файл `authorized_keys` є найвищим рубежем захисту облікового запису. Якщо інший локальний процес може змінити цей файл, він отримує повний контроль над акаунтом.

Тому демон `sshd` за замовчуванням містить директиву `StrictModes yes`. Перед відкриттям `authorized_keys` демон виконує системний виклик `stat()` для самого файлу та кожного батьківського каталогу у шляху (`/home/user/.ssh`, `/home/user`, `/home`, `/`):

1. Власником усіх каталогів у шляху має бути або цільовий користувач (`UID == target_user`), або суперкористувач `root` (`UID == 0`).
2. Каталог `~/.ssh` повинен мати права `0700` (`rwx------`). Права `0755` допустимі, лише якщо група та інші не мають біта запису (`w`).
3. Файл `authorized_keys` повинен мати права `0600` (`rw-------`) або `0644`.
4. Домашній каталог користувача (`/home/user`) **не повинен** мати біта запису для групи або інших (`chmod g-w,o-w /home/user`).

Якщо хоча б один каталог (наприклад, `/home/user`) має права `0775` чи `0777` (група чи будь-хто має право запису), `sshd` відмовляється відкривати файл і повертає помилку в системний журнал:

```text
sshd[1042]: Authentication refused: bad ownership or modes for directory /home/bohdan
```

Ця поведінка захищає систему: якби каталог мав право запису для групи, будь-який інший процес цієї групи міг би перейменувати каталог `.ssh`, створити власний з потрібним `authorized_keys` і миттєво захопити акаунт.

### Обмежувальні опції authorized_keys

Файл `authorized_keys` дозволяє не лише дозволити доступ за ключем, але й жорстко обмежити можливості сеансу, причепивши до рядка ключа список опцій через кому.

#### 1. Примусове виконання команди (`command`)

Для службових ключів (резервне копіювання, CI/CD, моніторинг) категорично заборонено надавати інтерактивну оболонку. Опція `command` змушує сервер виконувати лише зазначену команду:

```text
command="/usr/local/bin/backup-rdr.sh",no-pty ssh-ed25519 AAAAC3NzaC1lZDI1NTE5... backup@backup-srv
```

Хоч би яку команду передав клієнт (`ssh user@host rm -rf /`), сервер виконає виключно `/usr/local/bin/backup-rdr.sh`. Початкова команда клієнта зберігається у змінній середовища `SSH_ORIGINAL_COMMAND`, де скрипт може перевірити її аргументи за суворим білим списком.

#### 2. Мережеве обмеження джерела (`from`)

Опція `from` обмежує IP-адреси, з яких дозволено автентифікацію за цим ключем:

```text
from="192.168.1.0/24,10.0.5.12,!192.168.1.5" ssh-ed25519 AAAAC3NzaC1lZDI1NTE5...
```

Якщо підключення надійде з іншої IP-адреси, `sshd` відмовить у використанні цього ключа, навіть якщо клієнт володіє валідним закритим ключем.

#### 3. Блокування каналів і терміналів

За замовчуванням успішна автентифікація дозволяє відкривати довільні вторинні канали всередині SSH-з'єднання. Для ізоляції автоматизованих систем застосовують обмежувальні прапорці:
- `no-port-forwarding`: Забороняє клієнту створювати локальні (`-L`), віддалені (`-R`) та динамічні SOCKS-тунелі (`-D`).
- `no-X11-forwarding`: Забороняє прокидання графічного протоколу X11 (`-X`).
- `no-agent-forwarding`: Забороняє клієнту передавати сокет свого `ssh-agent` на віддалену сторону (`-A`). Це критично для запобігання атакам, коли скомпрометований сервер використовує чужий агент для автентифікації на інших машинах інфраструктури.
- `no-pty`: Забороняє створення псевдотермінала (`pty`). Клієнт може передавати лише сирий потік даних stdin/stdout.

#### 4. Канонічний підхід: прапорець `restrict`

Сучасний стандарт безпеки OpenSSH рекомендує починати опис сервісного ключа з макро-опції `restrict`, яка вмикає всі блокування одночасно (`no-pty`, `no-port-forwarding`, `no-X11-forwarding`, `no-agent-forwarding`, `no-user-rc`), після чого повертати лише необхідний мінімум:

```text
restrict,command="/opt/scripts/sync-storage.sh",from="10.20.0.0/16" ssh-ed25519 AAAAC3NzaC1lZDI1NTE5...
```

Повний формальний перелік усіх опцій та їхніх параметрів наведено у [📋 Довідник опцій authorized_keys, форматів known_hosts і параметрів ssh-keygen](root:sys-unix/ssh-keys-and-host-trust/api-authorized-keys-and-ssh-keygen.md).

## Модель довіри до сервера: TOFU та файл known_hosts

Автентифікація клієнта є лише половиною протоколу. Клієнт зі свого боку зобов'язаний переконатися, що підключається до справжнього сервера, а не до зловмисника, який перехопив DNS чи маршрутизацію (атака Man-in-the-Middle, MITM).

Під час узгодження сеансу сервер передає свій відкритий хост-ключ (`/etc/ssh/ssh_host_ed25519_key.pub`) і підписує обмін ключами KEX. Клієнт звіряє отриманий публічний ключ із базою даних довірених серверів у файлі `~/.ssh/known_hosts`.

![Скінченний автомат перевірки довіри до хоста за моделлю TOFU та захист від MITM](/root/sys/sys-unix/ssh-keys-and-host-trust/img/ssh-tofu-mitm-matrix.svg)
*Скінченний автомат перевірки довіри до хоста: обробка відомих ключів, інтерактивний запит TOFU при першому контакті та аварійне блокування при виявленні MITM-атаки.*

### Принцип TOFU (Trust On First Use)

Оскільки в традиційній мережі немає центрального посвідчувального центру для SSH, OpenSSH використовує модель довіри при першому використанні (Trust On First Use, TOFU):

1. При першому підключенні до нового сервера (`ssh server.example.com`) клієнт бачить, що запис про цей хост у `known_hosts` відсутній.
2. Програма генерує SHA-256 відбиток (fingerprint) публічного ключа сервера і зупиняється, запитуючи підтвердження у користувача:

```text
The authenticity of host 'db-prod-01.internal (10.0.1.5)' can't be established.
ED25519 key fingerprint is SHA256:d8N1+m8L5wX7g...
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

3. Якщо користувач вводить `yes`, OpenSSH додає запис у `~/.ssh/known_hosts` і завершує з'єднання.
4. При всіх наступних підключеннях клієнт автоматично звіряє хост-ключ із збереженим записом без жодних запитів.

Слабке місце TOFU полягає у першому кроці: якщо атака MITM відбувається в момент першого підключення, а користувач сліпо вводить `yes` без звірки відбитка через захищений канал зв'язку, клієнт назавжди зберігає ключ зловмисника як довірений.

### Розпізнавання атак Man-in-the-Middle (MITM)

Якщо запис про хост уже є у `known_hosts`, але під час чергового з'єднання сервер повертає інший публічний ключ, OpenSSH переходить у стан тривоги:

```text
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
Someone could be eavesdropping on you right now (man-in-the-middle attack)!
It is also possible that a host key has just been changed.
The fingerprint for the ED25519 key sent by the remote host is
SHA256:x9K...
Please contact your system administrator.
Add correct host key in /home/bohdan/.ssh/known_hosts to get rid of this message.
Offending ED25519 key in /home/bohdan/.ssh/known_hosts:42
Host key for db-prod-01.internal has changed and you have requested strict checking.
Host key verification failed.
```

При виявленні невідповідності ключа клієнт негайно припиняє роботу з кодом виходу `255`, повністю блокуючи інтерактивний вхід і передачу паролів. Це запобігає перехопленню секретів зловмисником, який підробив ARP/BGP таблиці чи DNS-відповіді.

### Конфіденційність імен у known_hosts (HashKnownHosts)

За замовчуванням файл `known_hosts` містив відкриті імена серверів та їхні IP-адреси:

```text
db-01.corp.lan,10.0.1.15 ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI...
```

Якщо ноутбук інженера викрадено або скомпрометовано непривілейованим шкідливим процесом, зловмисник отримував повну топологію корпоративної інфраструктури та перелік внутрішніх адрес.

Для захисту приватності використовується директива `HashKnownHosts yes`. При додаванні нового хоста OpenSSH генерує індивідуальну 16-байтну сіль (`salt`) і замінює ім'я хоста на рядок HMAC-SHA1:

```text
|1|F8j2xL...salt...=|mK9w1...hash...= ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI...
```

Зловмисник не може відновити список адрес із такого файлу без перебору за словником. Для пошуку чи видалення записів у хешованому файлі використовуються вбудовані команди:
- `ssh-keygen -F db-01.corp.lan` — знайти запис хоста за його іменем.
- `ssh-keygen -R db-01.corp.lan` — видалити застарілий ключ хоста з `known_hosts`.
- `ssh-keygen -H` — хешувати всі наявні відкриті записи у файлі `known_hosts`.

### Планова ротація ключів сервера: UpdateHostKeys

Коли на сервері планово змінюється операційна система або проводиться ротація хост-ключів, старий запис у `known_hosts` клієнтів викликає блокування. Для автоматизації ротації OpenSSH підтримує протокол `UpdateHostKeys yes` (у клієнтському `~/.ssh/config`).

Коли клієнт підключається до сервера за старим валідним ключем, сервер через уже встановлений захищений канал надсилає пакет із переліком своїх нових публічних ключів. Клієнт автоматично додає нові ключі у `~/.ssh/known_hosts`. Коли адміністратор остаточно вимикає старий ключ, клієнт продовжує підключатися за новим без виникнення попереджень про злам.

## Масштабування довіри: DNSSEC (SSHFP) та SSH Certificate Authority

Модель TOFU ідеально працює для кількох десятків серверів. Проте в інфраструктурах з тисячами віртуальних машин, динамічним автоскейлінгом у хмарах та великими штатами інженерів модель TOFU колапсує:
1. Інженери щодня бачать десятки попереджень TOFU для новостворених вузлів і звикають механічно вводити `yes`, повністю нівелюючи захист від MITM.
2. Додавання нового співробітника або зміна його ключа вимагає оновлення файлів `authorized_keys` на тисячах серверів.
3. Звільнення співробітника вимагає екстреної синхронізації всіх хостів для видалення його ключа; якщо один сервер пропущено, звільнений працівник зберігає доступ.

Для масштабування довіри застосовують два принципово різні підходи: перевірку відбитків через DNSSEC (SSHFP) та інфраструктуру центрів сертифікації SSH (SSH CA).

![Архітектура централізованої довіри на базі SSH Certificate Authority](/root/sys/sys-unix/ssh-keys-and-host-trust/img/ssh-ca-infrastructure.svg)
*Архітектура масштабування довіри: публікація відбитків у DNSSEC (SSHFP) та централізована модель SSH CA з розподілом на Host CA та User CA.*

### Публікація хост-ключів у DNSSEC (записи SSHFP)

Стандарт RFC 4255 описує механізм публікації відбитків хост-ключів у системі доменних імен (DNS) за допомогою ресурсних записів типу `SSHFP`.

Генерація запису SSHFP для сервера виконується командою:

```bash
$ ssh-keygen -r srv-db.example.com. -f /etc/ssh/ssh_host_ed25519_key.pub
srv-db.example.com. IN SSHFP 4 2 d8f5e7c8a1b2... (хеш SHA-256)
```

Поля запису SSHFP:
- **Алгоритм ключа:** 1 = RSA, 2 = DSA, 3 = ECDSA, 4 = Ed25519.
- **Тип хешу:** 1 = SHA-1 (застарілий), 2 = SHA-256.
- **Відбиток:** Шістнадцятковий дамп хешу відкритого ключа.

Якщо доменна зона підписана за стандартом **DNSSEC**, клієнт SSH із налаштуванням `VerifyHostKeyDNS yes` (або `ask`) у `~/.ssh/config` отримує запис SSHFP через локальний валідуючий резолвер. Якщо відбиток у DNSSEC збігається з ключем, наданим сервером, OpenSSH довіряє хосту **автоматично**, не вимагаючи від користувача підтвердження TOFU і не створюючи шуму у `known_hosts`.

### Інфраструктура SSH Certificate Authority (SSH CA)

Найбільш досконалим рішенням для корпоративних інфраструктур є використання вбудованого в OpenSSH механізму сертифікатів (SSH Certificates, специфікація `PROTOCOL.certkeys`).

SSH-сертифікати кардинально відрізняються від сертифікатів X.509 (TLS/HTTPS):
- Вони мають надзвичайно просту двійкову структуру і не використовують складний формат ASN.1/DER (головне джерело вразливостей в OpenSSL).
- Вони не мають багаторівневих ланцюжків довіри: сертифікат підписується безпосередньо кореневим ключем CA.
- Вони містять вбудовані поля авторизації: список дозволених логінів (`principals`), критичні обмеження та час життя.

Інфраструктура будується на двох незалежних центрах сертифікації:

#### 1. Host CA: централізована довіра до серверів

1. Організація створює пару ключів Host CA: `ssh_host_ca` (закритий) та `ssh_host_ca.pub` (відкритий).
2. Кожен новий сервер під час розгортання генерує локальний хост-ключ, який підписується ключем Host CA:

```bash
$ ssh-keygen -s /path/to/ssh_host_ca -I "srv-prod-01" -h \
    -n "srv-prod-01,srv-prod-01.infra.corp,10.0.1.10" -V "+365d" \
    /etc/ssh/ssh_host_ed25519_key.pub
```

Прапорець `-h` вказує, що створюється хост-сертифікат, а `-n` задає список доменних імен та IP, для яких цей сертифікат дійсний. Сервер отримує файл `/etc/ssh/ssh_host_ed25519_key-cert.pub` і підключає його у `sshd_config`:

```text
HostCertificate /etc/ssh/ssh_host_ed25519_key-cert.pub
```

3. На робочих станціях усіх інженерів у файл `~/.ssh/known_hosts` додається **рівно один рядок**:

```text
@cert-authority *.infra.corp,10.0.* ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... (вміст ssh_host_ca.pub)
```

Після цього будь-який клієнт без жодних діалогів TOFU довіряє будь-якому з тисяч серверів, якщо його сертифікат підписано цим Host CA, а запитане ім'я входить до списку `principals`.

#### 2. User CA: централізована автентифікація інженерів

1. Організація створює пару ключів User CA: `ssh_user_ca` та `ssh_user_ca.pub`.
2. На всіх серверах інфраструктури у `/etc/ssh/sshd_config` прописується один рядок:

```text
TrustedUserCAKeys /etc/ssh/ssh_user_ca.pub
```

3. Інженер генерує локальний публічний ключ і щоранку звертається до корпоративного порталу автентифікації (SSO/IdP + Vault). Портал перевіряє багатофакторну автентифікацію (MFA) і видає сертифікат з коротким часом життя (наприклад, 8 годин):

```bash
$ ssh-keygen -s /path/to/ssh_user_ca -I "alice@corp" \
    -n "ubuntu,deploy,alice" -V "+8h" ~/.ssh/id_ed25519.pub
```

Сертифікат зберігається у файлі `~/.ssh/id_ed25519-cert.pub`. Клієнт автоматично використовує його при вході. Сервер перевіряє підпис User CA і дозволяє вхід під користувачами `ubuntu` або `deploy`, якщо поточний час вкладається у 8-годинний ліміт.

Переваги моделі User CA:
- На серверах взагалі не потрібно створювати та синхронізувати файли `authorized_keys`.
- Права доступу зникають автоматично після закінчення 8 годин.
- При звільненні співробітника достатньо заблокувати його акаунт в IdP: наступного дня він просто не зможе отримати новий сертифікат.

#### 3. Відкликання сертифікатів (Key Revocation List)

Якщо ноутбук інженера викрадено під час дії 8-годинного вікна, сертифікат можна відкликати достроково за допомогою списку відкликаних ключів (KRL). Список генерується командою:

```bash
$ ssh-keygen -k -f /etc/ssh/revoked_keys.krl -u compromised-cert.pub
```

На серверах директива `RevokedKeys /etc/ssh/revoked_keys.krl` блокує будь-які сертифікати, занесені до цього двійкового списку.

Повну покрокову автоматизацію та програмний парсер двійкового wire-формату сертифікатів наведено у [⚙️ Автоматизація інфраструктури SSH Certificate Authority](root:sys-unix/ssh-keys-and-host-trust/proj-ssh-ca-authority.md).
