# 📜 Історія виникнення та еволюції ptrace

Еволюція системного виклику `ptrace` відображає чотири десятиліття розвитку підсистем спостережуваності та налагодження в Unix-подібних операційних системах. Створений у 1979 році для базової зупинки процесів та покрокового виконання інструкцій на PDP-11, цей механізм пройшов шлях від синхронного інспектування пам'яті через уніфікований інтерфейс викликів до гнучкого розмежування прав доступу через Yama LSM і подальшої заміни асинхронними підсистемами трасування на базі `eBPF` та `uprobes`.

Конструктивний шлях `ptrace` визначався постійним пошуком балансу між трьома вимогами: забезпеченням повного контролю налагоджувача над регістрами процесора, мінімізацією накладних витрат перемикання контексту та захистом процесів у багатокористувацькому середовищі.

---

## 1. Витоки: PDP-11 та 7-ма редакція Unix (1979)

У 1970-х роках творці Unix Кен Томпсон (Ken Thompson) та Денніс Рітчі (Dennis Ritchie) зіткнулися з практичною потребою створення інтерактивних інструментів аналізу виконання програм — перших налагоджувачів `adb` (Absolute Debugger) та `sdb`. Для розслідування причин аварійного завершення бінарних файлів на комп'ютерах PDP-11 налагоджувачу була потрібна можливість зупиняти процес, зчитувати стан його регістрів процесора та модифікувати машинний код у пам'яті для встановлення точок зупину.

У Version 7 Unix (1979 рік) було вперше реалізовано системний виклик `ptrace()` (від англійського *process trace*). Його початковий дизайн був тісно прив'язаний до простіших апаратних архітектур PDP-11 та VAX-11:

- Трасування працювало виключно між прямим батьківським і дочірнім процесом.
- Уся взаємодія виконувалася через єдиний системний виклик `ptrace(request, pid, addr, data)`.
- Кожна операція — прочитання одного 16-бітного чи 32-бітного слова пам'яті або виконання одної інструкції коду — вимагала окремого системного виклику з перемиканням контексту між користувацьким простором та ядром.

Для компактних систем із єдиним процесором таке рішення було просте й ефективне. Проте воно заклало фундаментальні обмеження швидкодії, які проявили себе через десятиліття з появою багатоядерних систем та великих обсягів оперативної пам'яті.

## 2. Великий розкол Unix: SysV `/proc` проти BSD `ptrace`

У 1980-х роках під час розколу операційних систем сімейства Unix на дві основні гілки — System V (AT&T) та BSD (University of California, Berkeley) — розробники сформулювали два принципово різні підходи до розв'язання проблеми інспектування процесів:

### Гілка System V (AT&T Bell Labs та Sun Microsystems)
Інженери Том Кілліан (Tom J. Killian) у 8-й редакції Research Unix та розробники SunOS/Solaris у складі System V Release 4 (SVR4) усвідомили, що `ptrace()` створив важке вузьке місце для продуктивності. Кожне читання пам'яті по одному слову через `ptrace` вимагало мільйонів переходів у ядро.

У відповідь вони запропонували нову революційну концепцію: представити запущені процеси у вигляді віртуальної файлової системи `/proc`. Замість використання специфічного системного виклику `ptrace()`, налагоджувач міг просто відкрити файл `/proc/<pid>/mem` і читати або писати довільні блоки пам'яті цільового процесу за допомогою звичайних високошвидкісних викликів `read()` та `write()`.

### Гілка BSD (UC Berkeley)
Розробники 4.3BSD та 4.4BSD зберегли класичний `ptrace()`, розширивши його підтримкою нових архітектур процесорів та сигнальної системи.

Коли Лінус Торвальдс у 1991 році створював ядро Linux, він проаналізував обидва підходи і для першої реалізації в коді ядра (`kernel/ptrace.c`) обрав модель `ptrace()` з BSD через її відносну простість реалізації у викликах `waitpid()`. Згодом Linux запозичив і концепцію `/proc` із System V, об'єднавши обидва підходи в єдиній системі.

## 3. Криза безпеки 2000-х років та розробка Yama LSM

Протягом 1990-х та 2000-х років системний виклик `ptrace()` перетворився на одне з найвразливіших місць в операційній системі з точки зору кібербезпеки. Можливість одного процесу довільно зчитувати й перезаписувати пам'ять іншого процесу того самого користувача створила потужний вектор для локального підвищення привілеїв (Local Privilege Escalation, LPE).

Дослідники з безпеки та зловмисники розробили серію експлойтів (зокрема відомі вразливості CVE-2001-0144, CVE-2010-3301 та витоки привілеїв у системному виклику `kcmp`), які використовували `PTRACE_ATTACH` для впровадження стороннього машинного коду (shellcode) у привілейовані процеси (setuid-програми, фонові демони SSH-агентів чи веб-браузери).

Для усунення цієї систематичної загрози у ядрі Linux 3.4 (2012 рік) розробники впровадили модуль безпеки **Yama LSM** (Linux Security Module). Yama ввів гнучке регулювання доступу через системний параметр `/proc/sys/kernel/ptrace_scope`:

- **Режим 0 (Classic):** Традиційна поведінка Unix. Будь-який процес користувача може трасувати будь-який інший процес того самого користувача.
- **Режим 1 (Restricted):** Сучасний стандарт більшості дистрибутивів Linux (Ubuntu, Debian, Fedora). Процес може трасувати лише свої прямо породжені дочірні процеси. Приєднання за PID до стороннього процесу (`gdb -p <pid>`) заборонено, якщо цільовий процес не надав явного дозволу через `prctl(PR_SET_PTRACER, pid)`.
- **Режим 2 (Admin only):** Трасування дозволено лише процесам із мандатним привілеєм `CAP_SYS_PTRACE` (зазвичай користувач `root`).
- **Режим 3 (No ptrace):** `ptrace` повністю заблоковано в системі до перезавантаження (викликається лише на критично захищених серверах).

## 4. Еволюція спостережуваності: Перехід до eBPF та Uprobes

У сучасній системній інженерії високонавантажених серверів класичний `ptrace()` виявився непридатним для масового моніторингу системних викликів у реальному часі. Чотири перемикання контексту на один системний виклик (Tracee → Kernel → Tracer → Kernel → Tracee) спричиняють уповільнення цільових додатків у 10–100 разів.

Це змусило спільноту розробників ядра Linux створити нове покоління підсистем спостережуваності (Observability):

- **Tracepoints (2008):** Статичні точки трасування в ядрі з нульовими накладними витратами в неактивному стані.
- **Kprobes та Uprobes (2006–2012):** Динамічна ін'єкція точок перехоплення у код ядра та користувацьких бібліотек без використання `ptrace`.
- **eBPF (Extended Berkeley Packet Filter, 2014):** Виконання байт-коду трасування безпосередньо всередині ядра Linux без перемикання контексту у користувацький простір.

Хоча eBPF захопив сферу системного моніторингу та APM, `ptrace()` залишається безальтернативною основою для інтерактивних налагоджувачів `gdb` та `lldb`, оскільки лише він забезпечує повний контроль над процесорним стеком та кроковим виконанням інструкцій.
