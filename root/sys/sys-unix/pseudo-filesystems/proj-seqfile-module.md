# ⚙️ Свій файл у /proc: сорок рядків, у яких видно, що вмісту не існує

Найшвидший спосіб повірити, що файл у `/proc` не має вмісту між читаннями, — зробити такий файл самому. Нижче — робочий [модуль ядра](root:sys-unix/kernel-modules), у якому текст народжується у вас на очах, і три властивості procfs, які з нього видно не як твердження, а як вивід команди.

## Задача

Поставити в `/proc` файл `heartbeat`, що на кожне читання віддає кілька рядків із живими числами. Далі — довести три речі, кожну окремим спостереженням:

- `ls -l` покаже нуль байтів, а `wc -c` — шістдесят шість;
- функція показу біжить під час `read`, а не під час `open`, і біжить у контексті **того, хто читає**;
- коли вміст переростає сторінку пам'яті, він приїжджає порціями, і між порціями ядро нічого не тримає замкненим — тобто розірване читання можна відтворити на замовлення, а не чекати випадку.

Мову тут диктує домен, і вибору немає. Код виконується в ядрі, торкається його структур і має бути зібраний тим самим компілятором і тими самими заголовками, що й саме ядро. Це C.

## Ідея: реєструємо не байти, а функцію

Створити файл у `/proc` — означає покласти в дерево procfs запис із набором функцій, які ядро викличе, коли до цього імені хтось звернеться. Набір описано окремим типом:

```c
struct proc_ops {
    unsigned int proc_flags;
    int     (*proc_open)(struct inode *, struct file *);
    ssize_t (*proc_read)(struct file *, char __user *, size_t, loff_t *);
    ssize_t (*proc_write)(struct file *, const char __user *, size_t, loff_t *);
    loff_t  (*proc_lseek)(struct file *, loff_t, int);
    int     (*proc_release)(struct inode *, struct file *);
    /* … */
};
```

Заповнювати всі ці поля вручну не треба, і — забігаючи наперед — не варто. Для файлів, вміст яких складається з тексту, у ядрі є помічник `seq_file`: ви пишете лише функцію `show()`, яка друкує потрібне, а `seq_file` бере на себе буфер, позицію, часткові читання й ознаку кінця файлу. Готових зв'язок дві:

- **`single_open()`** — коли весь вміст логічно один шматок. `show()` викликається один раз і друкує все; далі `seq_file` роздає надруковане читачеві стількома `read`, скільки той захоче.
- **`seq_open()` з повним набором `start` / `next` / `stop` / `show`** — коли вміст є **списком** записів. Тоді `seq_file` обходить список і друкує запис за записом, доки не заповнить буфер.

Різниця між цими двома зв'язками — не про зручність. Вона визначає, чи буде ваш файл цілісним знімком, чи потягне за собою розірване читання. Це й з'ясуємо.

## Модуль

Для демонстрації роботи ітератора `seq_file` реалізуємо модуль `heartbeat.c`, який створює псевдо-файл у `/proc` і формує його вміст на льоту під час кожного читання:

```c
/* heartbeat.c — файл у /proc, вміст якого народжується під час читання */
#include <linux/atomic.h>
#include <linux/init.h>
#include <linux/jiffies.h>
#include <linux/module.h>
#include <linux/proc_fs.h>
#include <linux/sched.h>
#include <linux/seq_file.h>

#define PROC_NAME "heartbeat"

static struct proc_dir_entry *entry;
static atomic_t shows = ATOMIC_INIT(0);   /* скільки разів кликали show() */

static int hb_show(struct seq_file *m, void *v)
{
    seq_printf(m, "uptime_ms   %u\n", jiffies_to_msecs(jiffies - INITIAL_JIFFIES));
    seq_printf(m, "reader_pid  %d\n", current->pid);
    seq_printf(m, "reader_comm %s\n", current->comm);
    seq_printf(m, "shows       %d\n", atomic_inc_return(&shows));
    return 0;
}

static int hb_open(struct inode *inode, struct file *file)
{
    return single_open(file, hb_show, NULL);
}

static const struct proc_ops hb_ops = {
    .proc_open    = hb_open,
    .proc_read    = seq_read,
    .proc_lseek   = seq_lseek,
    .proc_release = single_release,
};

static int __init hb_init(void)
{
    entry = proc_create(PROC_NAME, 0444, NULL, &hb_ops);
    if (!entry)
        return -ENOMEM;
    return 0;
}

static void __exit hb_exit(void)
{
    proc_remove(entry);
}

module_init(hb_init);
module_exit(hb_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Файл у /proc, вміст якого не існує між читаннями");
```

Тут варто затриматися на `current->pid` і `current->comm`. `current` — це процес, у контексті якого зараз виконується ядро. Оскільки `read` є синхронним викликом, ядро обробляє його **на тому самому потоці**, що зробив виклик. Отже, `hb_show()` побачить не якийсь службовий потік, а того самого `cat`, який щойно набрали в оболонці. Ця дрібниця й буде найкоротшим доказом, що функція біжить у мить читання.

## Збірка

Модуль збирається не сам по собі, а системою збирання ядра — вона знає прапорці, заголовки й ABI саме тієї версії, у яку модуль потім вантажать. Файл `Makefile` поруч із `heartbeat.c`:

```makefile
obj-m := heartbeat.o

KDIR ?= /lib/modules/$(shell uname -r)/build

all:
	$(MAKE) -C $(KDIR) M=$(CURDIR) modules

clean:
	$(MAKE) -C $(KDIR) M=$(CURDIR) clean
```

`obj-m := heartbeat.o` — єдиний рядок, який стосується вашого коду: «зібрати `heartbeat` як окремий модуль». Решта — переадресація виклику в дерево ядра. `KDIR` вказує на заголовки поточного ядра (пакет зветься `linux-headers-$(uname -r)` або `kernel-devel`), `M=$(CURDIR)` каже, де лежить чужий модуль. Про те, звідки береться це дерево і чому версія має збігатися до символів, — [збирання й конфігурація ядра](root:sys-unix/kernel-config-and-build).

```sh
$ make
$ sudo insmod heartbeat.ko
$ ls -l /proc/heartbeat
-r--r--r-- 1 root root 0 сер  7 12:31 /proc/heartbeat
$ cat /proc/heartbeat
uptime_ms   1842517
reader_pid  9317
reader_comm cat
shows       1
$ cat /proc/heartbeat
uptime_ms   1846093
reader_pid  9319
reader_comm cat
shows       2
```

Два `cat` поспіль дали різні числа, різні `pid` і лічильник, що виріс. Між ними в системі не було жодного байта цього файлу.

## Три твердження, перевірені наживо

### Розмір нуль — бо його справді ніхто не знає

Щоб переконатися у відсутності фіксованого розміру для псевдо-файлу у `/proc`, перевіримо метадані та вичитаємо вміст за допомогою команд `stat` і `wc`:

```sh
$ stat -c '%s' /proc/heartbeat
0
$ wc -c < /proc/heartbeat
66
```

Нуль тут не помилка й не домовленість. Створюючи запис, `proc_create()` не має жодного способу передбачити довжину майбутнього тексту: її визначить `hb_show()`, а `hb_show()` ще не бігла й побіжить лише тоді, коли хтось прочитає. Поле `st_size` лишається нулем, бо чесної відповіді немає.

Збрехати можна свідомо — `proc_set_size(entry, 4096)` проставить у запис довільне число, і `ls -l` почне його показувати. Ядро користується цим для файлів на кшталт `/proc/kcore`, де розмір хоч приблизно осмислений. Але число від цього не стає правдою: воно так само не пов'язане з тим, що віддасть наступне читання.

Практичний наслідок один і жорсткий: **читати треба в циклі до нуля**. Програма, яка виділяє буфер за `st_size` і робить один `read`, отримає порожньо; програма, яка перевіряє «чи змінився файл» за розміром, не побачить нічого ніколи.

### show() біжить на read, а не на open

Щоб це побачити, треба розсунути `open` і `read` у часі — `cat` робить їх упритул. Ось невелика програма, яка тримає **один** дескриптор і читає з нього двічі:

/* reader.c — коли саме ядро складає текст? */
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>

static void dump(const char *tag, int fd)
{
    char buf[8192];
    lseek(fd, 0, SEEK_SET);                  /* почати вміст спочатку */
    ssize_t n = read(fd, buf, sizeof buf);
    if (n <= 0)

    printf("--- %s ---\n%.*s", tag, (int)n, buf);

int main(void)
{
    int fd = open("/proc/heartbeat", O_RDONLY);
    dump("одразу після open", fd);

// reader.cpp — той самий приклад з ідіоматичним RAII у C++
#include <fcntl.h>
#include <unistd.h>
#include <iostream>
#include <string_view>

class UniqueFd {
    int fd_ = -1;
public:
    explicit UniqueFd(const char* path, int flags) : fd_(::open(path, flags)) {}
    ~UniqueFd() { if (fd_ >= 0) ::close(fd_); }
    int get() const { return fd_; }
    explicit operator bool() const { return fd_ >= 0; }
};

static void dump(std::string_view tag, int fd) {
    char buf[8192];
    ::lseek(fd, 0, SEEK_SET);                  // почати вміст спочатку
    ssize_t n = ::read(fd, buf, sizeof(buf));
    if (n > 0) {
        std::cout << "--- " << tag << " ---\n";
        std::cout.write(buf, static_cast<std::streamsize>(n));
    }
}

int main() {
    UniqueFd fd("/proc/heartbeat", O_RDONLY);
    if (!fd) return 1;
    dump("одразу після open", fd.get());
    ::sleep(3);
    dump("через три секунди, той самий дескриптор", fd.get());
    return 0;
}

Дескриптор один, `open` був один, а `show()` відпрацювала двічі — лічильник виріс, і `uptime_ms` пересунувся на всю паузу. Тобто `open` не породжує вмісту: він лише готує машинерію `seq_file`. Вміст виникає з першим читанням від початку файлу, і саме тому `lseek` назад на нуль дає не «те саме, що було», а **новий знімок**. Позиція, з якої читають, належить [опису відкритого файлу](root:sys-unix/open-file-description), і скидання її повертає `seq_file` у стан «ще нічого не показано».

Той самий висновок видно й ззовні, [через `strace`](root:sys-unix/syscall-tracing) — сам `open` не читає нічого й нічого не коштує:

```sh
$ strace -e trace=openat,read,lseek,close ./reader
openat(AT_FDCWD, "/proc/heartbeat", O_RDONLY) = 3
lseek(3, 0, SEEK_SET)                   = 0
read(3, "uptime_ms   1901004\nreader_pid  "..., 8192) = 70
lseek(3, 0, SEEK_SET)                   = 0
read(3, "uptime_ms   1904011\nreader_pid  "..., 8192) = 70
close(3)                                = 0
```

### Сторінка як межа порції

Тепер друга зв'язка. Замінімо `single_open` на повний ітератор, який друкує список записів — стільки, щоб він не влазив у сторінку.

```c
/* доповнення до heartbeat.c: список замість одного знімка */
#include <linux/mutex.h>

static unsigned int rows = 200;
module_param(rows, uint, 0444);
MODULE_PARM_DESC(rows, "скільки рядків друкувати");

static DEFINE_MUTEX(hb_lock);
static atomic_t generation = ATOMIC_INIT(1);

static void *hb_start(struct seq_file *m, loff_t *pos)
{
    mutex_lock(&hb_lock);            /* замок беремо тут… */
    if (*pos >= rows)
        return NULL;
    return pos;                      /* курсор — сам лічильник позиції */
}

static void *hb_next(struct seq_file *m, void *v, loff_t *pos)
{
    ++*pos;
    return (*pos >= rows) ? NULL : pos;
}

static void hb_stop(struct seq_file *m, void *v)
{
    mutex_unlock(&hb_lock);          /* …і віддаємо тут */
}

static int hb_row(struct seq_file *m, void *v)
{
    seq_printf(m, "row %4lld  generation %d\n",
               *(loff_t *)v, atomic_read(&generation));
    return 0;
}

static const struct seq_operations hb_seq_ops = {
    .start = hb_start,
    .next  = hb_next,
    .stop  = hb_stop,
    .show  = hb_row,
};

static int hb_open(struct inode *inode, struct file *file)
{
    return seq_open(file, &hb_seq_ops);      /* замість single_open */
}
```

У `proc_ops` тепер `.proc_release = seq_release`. Рядок має сталу довжину, тож можна порахувати наперед, де саме розірветься читання:

```
довжина рядка   "row  177  generation 1\n"
                4 + 4 + 2 + 11 + 1 + 1 = 23 байти

буфер seq_file на старті — рівно одна сторінка: 4096 байтів

  ⌊4096 ÷ 23⌋ = 178        178 · 23 = 4094 ≤ 4096   ✔ уміщається
  179-й рядок дав би       179 · 23 = 4117 > 4096   ✘ переповнення

отже  read №1 → 4094 байти (рядки 0…177)
      read №2 →  506 байтів (рядки 178…199)
      read №3 →    0
```

І саме це видно, хоч читач просить одразу вісім кілобайтів:

```sh
$ strace -e trace=read ./reader-all
read(3, "row    0  generation 1\nrow    1 "..., 8192) = 4094
read(3, "row  178  generation 1\nrow  179 "..., 8192) = 506
read(3, "", 8192)                       = 0
```

Просити більше не допомогло. `seq_file` віддає рівно те, що встигло вміститися в **його** буфер, а буфер цей — одна сторінка. Збільшується він лише в одному випадку: коли **один окремий запис** не влазить цілком. Тоді `seq_file` викидає буфер, бере вдвічі більший і друкує запис наново. Тому всередині свого буфера він тримає тільки цілі записи: обірваних рядків там не буває.

> 🔧 **Навіщо це.** Цілі записи `seq_file` гарантує лише **у своєму** буфері — у ваш він копіює рівно стільки, скільки ви попросили. Попросите 1024 байти, коли в порції лежить 4094, — дістанете 1024 байти, останній рядок обірветься посеред слова, а хвіст приїде наступним `read`. Звідси правило розбору таких файлів: накопичувати все прочитане й різати на рядки **після** `EOF`, а не після кожного виклику. `wc -l /proc/self/maps` завжди правий саме тому, що рахує символи переведення рядка в потоці й порціями не переймається; самописний парсер, який робить `split('\n')` одразу після кожного `read`, ловить обірваний рядок рівно на межі порції — а межа ця залежить і від розміру вашого буфера, і від довжини записів, тож у тестах на маленькому процесі не відтворюється ніколи.

## Розірване читання на замовлення

Тепер найцікавіше. `hb_start()` бере замок, `hb_stop()` його віддає — здавалося б, список захищено. Але подивіться на схему ще раз: `start` і `stop` викликаються **на кожен `read` окремо**. Між двома читаннями замка немає, бо `seq_file` навмисно копіює дані в простір користувача **після** `stop`.

Це не недогляд, а вимушений розв'язок. Копіювання в чужу пам'ять може [викликати сторінковий збій](root:sf-os/page-fault) і приспати потік; робити це під замком означало б тримати замок невідомо скільки, поки читач розбереться зі своєю пам'яттю. Тому `seq_file` розводить дві дії: спершу набити свій буфер під замком, потім віддати замок, потім копіювати. Ціною є те, що замок ніяк не може накрити весь файл — [замки в ядрі](root:sys-unix/kernel-locking) захищають одну порцію, а не всю відповідь.

Перевірмо. Додамо обробник запису, що збільшує `generation`, і прочитаємо файл з паузою між порціями:

```sh
# термінал 1: читач, що робить паузу між read()
$ ./reader-slow
row    0  generation 1
row    1  generation 1
…
row  177  generation 1
row  178  generation 2      ← межа порції
row  179  generation 2
…
row  199  generation 2

# термінал 2, у паузі між першим і другим read()
$ echo bump > /proc/heartbeat
```

Ось воно, слово в слово те, про що попереджають щодо `/proc/<pid>/maps`: **жоден рядок не пошкоджений** — кожен був правдою у свою мить. Неправдою є їхня сукупність: у зібраному тексті немає жодного моменту часу, у який система виглядала б саме так.

Ця вправа показує ще одну річ. Розрив стався не тому, що файл великий, а тому, що вміст **обходиться списком**. `single_open` такого не має: там `show()` друкує все за один прохід, і подальші `read` лише роздають готовий буфер. Тому вибір між двома зв'язками — це вибір між цілісністю знімка й пам'яттю: `single_open` мусить утримати весь вміст одночасно, зате віддає його узгодженим.

## Запис — одна цілісна команда

Щоб команда `echo bump` вище справді доходила до модуля, треба ще дві правки: додати в `hb_ops` поле `.proc_write = hb_write` і послабити права у `proc_create()` з `0444` на `0644`. Права тут — звичайні [біти дозволів](root:sys-unix/permission-bits) на вузлі, і ядро перевіряє їх ще до того, як загляне у ваш набір функцій.

```c
#include <linux/string.h>    /* strim */
#include <linux/uaccess.h>   /* copy_from_user */

static ssize_t hb_write(struct file *file, const char __user *ubuf,
                        size_t count, loff_t *ppos)
{
    char cmd[16], *p;

    if (count == 0 || count >= sizeof cmd)
        return -EINVAL;              /* не влізло — це помилка, а не «запишемо частину» */
    if (copy_from_user(cmd, ubuf, count))
        return -EFAULT;
    cmd[count] = '\0';
    p = strim(cmd);                  /* прибрати \n, який додає echo */

    if (!strcmp(p, "bump"))
        atomic_inc(&generation);
    else if (!strcmp(p, "reset"))
        atomic_set(&generation, 1);
    else
        return -EINVAL;

    return count;                    /* спожито все */
}
```

Три рішення в цих рядках варті пояснення, бо кожне суперечить звичкам, узятим зі звичайних файлів.

**`*ppos` не використано взагалі.** У звичайному файлі позиція каже, куди класти байти. Тут класти нікуди: байти є наказом, а не вмістом. Тому дописування в кінець, `O_TRUNC` і `lseek` перед записом не мають сенсу — і код їх свідомо ігнорує, замість того щоб вдавати, ніби розуміє.

**Завелика команда — відмова, а не обрізання.** Спокуса взяти `min(count, sizeof cmd - 1)` і працювати з тим, що влізло, дасть найгіршу з можливих поведінок: `echo bumppppppp` тихо спрацює як `bump`. Наказ або зрозумілий цілком, або не виконується.

**Повертати треба `count`, і тільки `count`.** Значення, що повертає `write`, означає «стільки байтів спожито». Повернете менше — і бібліотека простору користувача (той самий `echo`) чесно допише **залишок** новим викликом `write`. Ваш обробник побачить його як окрему команду — хвіст попередньої, який ні на що не схожий, — і поверне `EINVAL`. Звідси й правило, яке в статтях про `sysfs` виглядає безпідставним: **значення пишеться одним викликом цілком**. Обробник викликається рівно раз на кожен `write` і бачить рівно те, що приніс саме цей виклик; склеювати два записи в одну команду немає де — між ними ядро не тримає жодного стану.

І сама межа тут не декоративна: `ubuf` — вказівник у чужий адресний простір, і розіменувати його прямо не можна. `copy_from_user()` — єдиний законний спосіб перейти [межу між ядром і простором користувача](root:sys-unix/kernel-and-userspace), бо він перевіряє права на ділянку й уміє коректно впасти з `EFAULT`, якщо процес підсунув сміття.

## Пастки

### Чому не можна віддавати вміст із наперед заповненого буфера

Найпряміша ідея новачка — завести статичний масив, набити його при завантаженні модуля й у `.proc_read` просто скопіювати його читачеві. Вона розвалюється в чотирьох різних місцях, і кожне варте того, щоб його знати.

**Дані застаріють у ту саму мить.** Це очевидно, але важливо назвати причину правильно: сенс цієї гілки псевдо-ФС не в тому, що дані «десь лежать у пам'яті ядра», а в тому, що їх **немає**, доки не спитали. Готовий буфер повертає нас у гілку, де вміст зберігається, — тільки без жодної з її переваг.

**`cat` зациклиться.** Ось найпоширеніша помилка в цій темі. Наївний `.proc_read` копіює свій буфер і повертає його довжину — щоразу. `cat` читає, отримує 66, читає знову, отримує 66, і так довіку, бо ознаки кінця файлу немає. Ознакою є повернений нуль, а щоб зрозуміти, коли його повернути, треба чесно вести `*ppos`: скільки вже віддано, скільки лишилося, скільки просять. Уся ця арифметика зі зсувами й частковими копіюваннями і є той код, який `seq_file` пише за вас. Якщо ви таки віддаєте готовий шматок пам'яті, у ядрі для цього є рівно один правильний рядок:

```c
return simple_read_from_buffer(ubuf, count, ppos, my_data, my_len);
```

**Один буфер на всіх — це гонитва.** Статичний масив спільний для всіх читачів. Два `cat` водночас — і другий затре текст, який перший ще не дочитав. `seq_file` виділяє буфер **на кожен `open`** і серіалізує роботу з ним власним м'ютексом усередині `struct seq_file`. Тобто одночасні читачі не заважають одне одному не тому, що їм пощастило, а тому, що для цього є механізм.

**Фіксований розмір тихо ріже правду.** Виріс список — і кінець вмісту просто зникає, без жодної ознаки помилки. `seq_file` натомість помічає переповнення й подвоює буфер, доки один запис не вміститься цілком.

### Що станеться з відкритим дескриптором, якщо модуль вивантажити

Ось де procfs поводиться не так, як це описують у більшості посібників із модулів ядра.

Класичний механізм захисту виглядає так: у `struct file_operations` є поле `owner`, куди пишуть `THIS_MODULE`; коли VFS відкриває файл, він бере посилання на цей модуль, і `rmmod` при відкритому дескрипторі відмовляє з `EBUSY`. Саме так захищено [символьні пристрої](root:sys-unix/device-file-model).

У `struct proc_ops` поля `owner` **немає взагалі**. Це не забудькуватість: тип `proc_ops` і з'явився для того, щоб відчепити procfs від `file_operations` — коміт «proc: decouple proc from VFS with `struct proc_ops`» (автор Alexey Dobriyan) свідомо викинув із нього все, чим procfs не користується, зокрема й вказівник на модуль. Перевірити версію легко: у `include/linux/proc_fs.h` ядра 5.5 `proc_create()` ще приймає `const struct file_operations *`, у 5.6 — уже `const struct proc_ops *`.

Замість посилання на модуль procfs рахує користувачів самого запису. Перед кожним викликом вашої функції він робить `use_pde()`, після — `unuse_pde()`. А `proc_remove()` робить дві речі поспіль:

1. позначає запис як приречений, так що всі **нові** звертання відмовляються одразу;
2. **чекає**, доки завершаться ті виклики, що вже всередині, і потім силою закриває всі відкриті дескриптори.

З цього випливають три наслідки, які краще знати заздалегідь.

**`rmmod` може зависнути.** Якщо в цю мить хтось сидить усередині вашої `show()` — скажімо, вона взяла замок і чекає, — `proc_remove()` не повернеться, доки та не вийде. Отже, `show()`, яка довго не повертає керування, перетворює вивантаження модуля на зависання — і винен тут не `rmmod`, а ваш код.

**`rmmod` пройде навіть при відкритому дескрипторі.** І це, мабуть, найнесподіваніше:

```sh
$ ./hold-open /proc/heartbeat &        # відкрив і спить, не читаючи
[1] 9631
$ sudo rmmod heartbeat                 # проходить, без жодного EBUSY
$ kill -USR1 9631                      # просимо його прочитати зараз
read: Input/output error
```

`EIO` тут не збій, а точна відповідь: запису, з якого читали, більше немає, і функції, що мала б відповісти, теж немає. Програма, яка тримає дескриптор у `/proc` довго, мусить бути готова дістати `EIO` зненацька — це нормальний режим роботи системи, у якій модулі приходять і йдуть.

**Порядок прибирання визначений сам собою.** Оскільки `proc_remove()` повертається лише тоді, коли жодного виклику вже немає всередині, після нього безпечно звільняти все, чого торкалася `show()`. Тому в `hb_exit()` `proc_remove()` стоїть **першим** рядком. Зробите навпаки — звільните структури, а потім знімете запис — і читач, який саме зараз усередині `show()`, працюватиме зі звільненою пам'яттю.

## Де цей інтерфейс перестає працювати

Зібравши модуль, ви заразом намацали межу самої затії. Доки віддаєте кілька рядків, `single_open` дає чесний узгоджений знімок і не коштує майже нічого. Щойно вміст став списком, який не влазить у сторінку, ви роздаєте читачеві текст без жодних гарантій цілісності — і поправити це з боку модуля неможливо: розрив закладений не у ваш код, а в сам спосіб віддавати дані порціями через спільний буфер, який звільняють між читаннями.

Тому перед тим, як заводити свій файл у `/proc`, варто чесно спитати, скільки в ньому буде рядків і чи мусять вони бути узгодженими між собою. Якщо відповідь «багато» і «мусять» — це вже не задача для файлового інтерфейсу, а територія, де великий зв'язний стан віддають [структурованими повідомленнями](root:sys-unix/netlink-protocol).
