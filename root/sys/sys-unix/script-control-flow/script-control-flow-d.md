Командна оболонка Unix не має вбудованого типу даних для логічних величин (boolean). У мовах системного програмування на зразок C або Rust умовні оператори аналізують значення виразу в оперативній пам'яті: нуль інтерпретується як хиба, а будь-яке ненульове число — як істина. В оболонці Unix ситуація дзеркально протилежна: єдиним носієм істинності є **код виходу (exit status)** виконаного процесу. Будь-яка конструкція розгалуження чи циклу — від простого `if` до складного `while read` — є інструкцією ядра та парсера виконати команду, дочекатися завершення процесу та перевірити 8-бітне число, повернуте системним викликом `waitpid`.

Якщо процес завершився з кодом `0`, оболонка вважає умову успішною (істина). Будь-який інший код від `1` до `255` сигналізує про помилку, збій або аварійне переривання сигналом (хиба). З цього фундаментального принципу випливає вся екосистема керування потоком виконання: утиліти перевірки файлів і рядків, синтаксичні розширення Bash, зіставлення за шаблонами та потокові цикли обробки даних.

## 1. Концепція умов у Unix: семантика коду завершення

Синтаксична структура `if` у shell не створює математичного контексту для обчислення формул. Її граматична форма у стандарті POSIX визначається як послідовність виконання списків команд:

```sh
if список_команд_1; then
    список_команд_2
elif список_команд_3; then
    список_команд_4
else
    список_команд_5
fi
```

Коли інтерпретатор зустрічає ключове слово `if`, він послідовно виконує `список_команд_1`. Цим списком може бути будь-яка зовнішня утиліта, конвеєр або вбудована функція. Оболонка оцінює статус завершення **останньої** команди у списку:

* Якщо код повернення `$? == 0`, керування передається у гілку `then`.
* Якщо код повернення `$? != 0`, оболонка переходить до перевірки наступного блоку `elif` або виконує гілку за замовчуванням `else`.

![Оцінка умовних конструкцій в оболонці](/root/sys/sys-unix/script-control-flow/img/shell-conditional-eval.svg)
*Механізм умовного розгалуження: виконання команди з оцінкою коду виходу (POSIX) проти внутрішнього розбору виразу ключовим словом парсера (Bash).*

Через таку семантику системні утиліти Unix самі по собі є повноцінними предикатами. Немає потреби запускати допоміжні перевірки, якщо сама команда повертає змістовний статус:

```sh
# Пошук без виводу в термінал: grep -q повертає 0, якщо знайдено збіг
if grep -q "root:" /etc/passwd; then
    echo "Обліковий запис root присутній у системі"
fi

# Створення каталогу: якщо успішно, створюємо конфігураційний файл
if mkdir -p /var/log/app 2>/dev/null; then
    touch /var/log/app/app.log
fi
```

### Конвеєри та масив PIPESTATUS у Bash

Коли умовний блок містить конвеєр команд (`if cmd1 | cmd2; then`), за стандартом POSIX статус завершення всього конвеєра визначається статусом виключно **останньої** команди `cmd2`. Якщо перша команда `cmd1` впала з критичною помилкою (наприклад, не знайшла вхідний файл), але `cmd2` успішно опрацювала порожній потік, загальний статус конвеєра дорівнюватиме `0`, і блок `then` буде виконано.

Для точного відстеження збоїв у конвеєрах GNU Bash надає два спеціальні механізми:
1. **Масив `PIPESTATUS`**: вбудований масив, що містить коди виходу всіх процесів останнього виконаного конвеєра. Наприклад, вираз `${PIPESTATUS[0]}` містить статус `cmd1`, а `${PIPESTATUS[1]}` — статус `cmd2`.
2. **Опція `set -o pipefail`**: перемикає логіку обчислення статусу конвеєра. Якщо хоча б одна команда завершилася з ненульовим кодом, загальним кодом конвеєра стає код виходу останньої невдалої команди.

### Ланцюжки `&&` та `||` як скорочена форма розгалуження

Стандарт POSIX визначає логічні оператори списків команд `&&` (AND-list) та `||` (OR-list). Вони реалізують логіку короткого замикання (англ. *short-circuit evaluation*):

* `команда1 && команда2` — `команда2` виконується **лише тоді**, коли `команда1` завершилася з кодом `0`.
* `команда1 || команда2` — `команда2` виконується **лише тоді**, коли `команда1` повернула ненульовий код помилки.

Це дозволяє замінювати громіздкі блоки `if-then-fi` компактними ідіомами:

```sh
# Перевірка наявності файлу перед читанням
[ -r /etc/hosts ] && cat /etc/hosts

# Зупинка виконання скрипту при критичній помилці
cd /opt/deploy || exit 1
```

### Інверсія статусу через оператор `!`

Префіксний оператор `!` (знак оклику), відділений від команди пробілом, інвертує код повернення: якщо команда повертає `0`, оператор перетворює результат на `1`, а якщо команда повертає будь-яке ненульове число — на `0`:

```sh
if ! id -u admin >/dev/null 2>&1; then
    echo "Користувач admin відсутній"
fi
```

## 2. Еволюція перевірок: утиліта test та псевдонім [ ]

Оскільки `if` вміє лише запускати команди, виникла потреба в універсальній програмі, здатності якої охоплювали б інспекцію файлової системи, порівняння текстових рядків та перевірку чисел. Так з'явилася утиліта `test` та її символічний аналог `[` (квадратна дужка).

Детальний історичний шлях від зовнішнього бінарника до вбудованої команди викладено у вставці [Еволюція перевірок: від окремої утиліти до ключового слова парсера](root:sys-unix/script-control-flow/hist-test-and-brackets-evolution.md).

З погляду системної архітектури конструкція `[ ... ]` — це звичайний виклик команди з аргументами:
1. Оболонка бачить перше слово `[` як ім'я команди.
2. Інтерпретатор виконує всі стандартні етапи підстановки: розгортання змінних (parameter expansion), розбиття на окремі слова за символами `IFS` (word splitting) та заміну масок файлів (globbing).
3. Сформований масив аргументів передається у внутрішню функцію `test`. Останнім елементом масиву обов'язково має бути рядок `]`, інакше утиліта повертає синтаксичну помилку.

### Пастка незалапкованих змінних у [ ]

Оскільки підстановка параметрів відбувається **до** передачі аргументів у команду `[`, відсутність подвійних лапок довкола змінних є джерелом найпоширеніших збоїв у скриптах.

Розглянемо вираз:

```sh
if [ $USER_INPUT = "admin" ]; then
    echo "Доступ надано"
fi
```

Якщо змінна `USER_INPUT` не визначена або містить порожній рядок `""`, оболонка розгортає її у порожнечу під час фази розбиття на слова. Масив аргументів команди `[` набуває вигляду:

```
argv[0] = "["
argv[1] = "="
argv[2] = "admin"
argv[3] = "]"
```

Команда `[` намагається розібрати перший аргумент `=` як унарний предикат і аварійно завершується з помилкою: `[: =: unary operator expected`.

Якщо ж змінна містить пробіли (наприклад, `USER_INPUT="John Doe"`), поділ на слова створить два окремих аргументи:

```
argv[0] = "["
argv[1] = "John"
argv[2] = "Doe"
argv[3] = "="
argv[4] = "admin"
argv[5] = "]"
```

Результат: помилка `[: too many arguments`.

Ще небезпечніший випадок виникає, коли незалапкована змінна містить символ маски файлів `*` (наприклад, `USER_INPUT="*"`). Під час фази розгортання імен файлів (globbing) зірочка замінюється списком усіх файлів поточного робочого каталогу, перетворюючи команду `[` на непередбачуване полотно з десятків аргументів.

Єдиний безпечний спосіб використання команди `[` у стандарті POSIX — брати кожну змінну у подвійні лапки:

```sh
if [ "$USER_INPUT" = "admin" ]; then
    echo "Доступ надано"
fi
```

### Захист від дефісів: історичний трюк `x"$var"`

У ранніх реалізаціях Bourne shell утиліта `[` могла дати збій, якщо вміст змінної починався з символу дефісу (наприклад, `USER_INPUT="-f"` або `USER_INPUT="!"`). Програма плутала значення рядка з власними опціями перевірки файлів або логічним запереченням.

Для нейтралізації цієї проблеми системні програмісти застосовували префіксний символ `x`:

```sh
if [ "x$USER_INPUT" = "xadmin" ]; then
    echo "Безпечне порівняння"
fi
```

Якщо `USER_INPUT` дорівнює `-f`, вираз перетворюється на порівняння рядків `"x-f"` та `"xadmin"`, що позбавляє парсер спокуси інтерпретувати `-f` як перевірку існування файлу.

### Криза операторів `-a` та `-o` у стандарті POSIX

Утиліта `test` історично підтримувала об'єднання умов за допомогою операторів `-a` (логічне І) та `-o` (логічне АБО), а також групування дужками `\( ... \)`:

```sh
# ПОТЕНЦІЙНО НЕБЕЗПЕЧНО у чистому POSIX sh
[ -f "$file" -a -r "$file" ]
```

Стандарт POSIX.1-2008 офіційно визнав оператори `-a` та `-o` застарілими (obsolescent). Причина — принципова неможливість побудувати однозначне синтаксичне дерево для виразів із понад 4 аргументами, якщо рядки всередині змінних збігаються з назвами операторів (наприклад, `[` `"$a"` `-a` `"$b"` `]`, де `$a` містить значення `"` `!` `"`).

У переносному коді POSIX складні умови слід будувати виключно через ланцюжки окремих команд:

```sh
# Канонічний надійний підхід POSIX
[ -f "$file" ] && [ -r "$file" ]
```

Повний перелік усіх підтримуваних операторів та прапорців зібрано у довіднику [Повний довідник операторів test, [ ], [[ ]] та (( ))](root:sys-unix/script-control-flow/api-test-and-bracket-operators.md).

## 3. Ключове слово [[ ]] у Bash: захист парсера та розширені оператори

Для розв'язання вроджених проблем утиліти `[` у KornShell та GNU Bash було створено розширену умовну конструкцію `[[ ... ]]`.

Критична відмінність: `[[` — це **не команда**, а **зарезервоване ключове слово парсера (keyword / compound command)**.

Коли лексичний аналізатор Bash зустрічає токен `[[`, він змінює режим трансляції всього вмісту до закриваючого `]]`:
1. **Вимкнено розбиття на слова (word splitting)**: якщо змінна не взята у подвійні лапки або містить пробіли, вона не розділяється на кілька аргументів `argv`.
2. **Вимкнено розгортання імен файлів (globbing)** для лівого операнда: рядок із символом `*` не підміняється списком файлів з поточного каталогу.
3. **Обчислення короткого замикання (short-circuit)**: вирази з операторами `&&` та `||` виконуються всередині одного процесу без створення додаткових команд.

```bash
# Абсолютно безпечно в Bash, навіть якщо $name порожнє або містить пробіли
if [[ $name == "John Doe" && -f $file ]]; then
    echo "Коректно"
fi
```

### Зіставлення з glob-шаблонами

Оператори `==` та `!=` всередині `[[ ... ]]` підтримують зіставлення з масками оболонки (англ. *pattern matching*). Якщо правий операнд **не взятий у лапки**, він інтерпретується як glob-шаблон:

```bash
filename="backup_2026_08.tar.gz"

# Перевірка наявності префікса та суфікса
if [[ $filename == backup_*.tar.gz ]]; then
    echo "Це архів резервної копії"
fi

# Лапки вимикають шаблон і вимагають точного збігу:
if [[ $filename == "backup_*.tar.gz" ]]; then
    echo "Цей рядок ніколи не виконається, якщо в імені немає буквальної зірочки"
fi
```

### Регулярні вирази через оператор `=~` та масив `BASH_REMATCH`

Починаючи з версії Bash 3.0, конструкція `[[` отримала оператор `=~`, що виконує зіставлення рядка з розширеним регулярним виразом POSIX ERE (Extended Regular Expressions, аналогічно до системної бібліотечної функції `regexec`).

При успішному збігу підрядки, захоплені круглими дужками `( ... )`, автоматично поміщаються у вбудований масив `BASH_REMATCH`:
* `BASH_REMATCH[0]` — увесь фрагмент рядка, що збігся з повним регулярним виразом.
* `BASH_REMATCH[1]` — перший захоплений групою фрагмент.
* `BASH_REMATCH[N]` — N-й захоплений фрагмент.

```bash
log_entry="[2026-08-25 14:32:01] ERROR: Connection timeout on port 8080"
regex='^\[([0-9]{4}-[0-9]{2}-[0-9]{2}) [^]]+\] ([A-Z]+): (.*)$'

if [[ $log_entry =~ $regex ]]; then
    date="${BASH_REMATCH[1]}"
    level="${BASH_REMATCH[2]}"
    message="${BASH_REMATCH[3]}"

    printf "Дата: %s | Рівень: %s | Текст: %s\n" "$date" "$level" "$message"
fi
```

> ⚠️ **Пастка лапок у регулярних виразах**: у версіях Bash 3.2+ взяття правого операнда оператора `=~` у лапки (наприклад, `[[ $str =~ "^[0-9]+$" ]]`) змушує інтерпретатор трактувати всі метасимволи `^`, `[`, `+`, `$` як **звичайні буквальні символи**. Регулярний вираз слід завжди зберігати в окремій змінній без лапок або писати без лапок безпосередньо у виразі.

## 4. Арифметичний контекст: (( )) та $(( ))

Для математичних розрахунків та порівняння цілих чисел у Bash застосовується конструкція подвійних круглих дужок `(( ... ))`. Вона створює повноцінне C-подібне обчислювальне середовище, де діють звичні оператори `>`, `<`, `>=`, `<=`, `==`, `!=`, а змінні не потребують префікса `$`.

```bash
count=42
limit=100

if (( count * 2 > limit && count % 2 == 0 )); then
    echo "Умова виконана"
fi
```

### Основи числення та побітові операції

Усередині `(( ... ))` підтримуються різні системи числення:
* Десяткові: `100`.
* Вісімкові (префікс `0`): `0755` (число `493`).
* Шістнадцяткові (префікс `0x`): `0xFF` (число `255`).
* Довільна база від 2 до 64 (синтаксис `база#значення`): `2#101010` (число `42`), `16#1F` (число `31`).

Побітові оператори дозволяють перевіряти бітові маски системних прапорців:

```bash
flags=0x25  # 00100101 у двійковому вигляді
if (( (flags & 0x04) != 0 )); then
    echo "Третій біт активовано"
fi
```

### Парадокс коду повернення в арифметиці

Арифметична конструкція `(( вираз ))` повертає статус виходу за спеціальним правилом:
* Якщо підсумкове числове значення виразу **не дорівнює нулю** (non-zero), статус виходу становить `0` (істина / успіх).
* Якщо значення виразу **дорівнює нулю** (`0`), статус виходу становить `1` (хиба / помилка).

Звідси виникає класична пастка при ввімкненому режимі зупинки на помилках `set -e`:

```bash
set -e
i=0
(( i++ ))  # АВАРІЙНИЙ ВИХІД СКРИПТУ!
```

Оскільки постфіксний інкремент `i++` спочатку повертає старе значення `i` (тобто `0`), результатом виразу є `0`. Конструкція `(( 0 ))` повертає код виходу `1`, що змушує `set -e` негайно перервати виконання сценарію. Безпечний запис: `(( i += 1 ))` або `(( ++i ))`.

## 5. Структури розгалуження: if-then-elif-else та оператор case

Коли логіка сценарію вимагає множинного вибору за значенням одного рядка, багаторазові блоки `if-elif-else` стають важкими для читання та повільними через послідовне багаторазове розгортання змінних.

Оператор `case` реалізує зіставлення значення виразу зі списком glob-шаблонів на рівні синтаксичного дерева:

```sh
case "$expression" in
    шаблон1)
        список_команд_1
        ;;
    шаблон2|шаблон3)
        список_команд_2
        ;;
    *)
        команди_за_замовчуванням
        ;;
esac
```

### Розбір варіантів та патерн-матчинг у case

Шаблони в `case` підтримують повний синтаксис globbing:
* `*` — будь-яка кількість будь-яких символів.
* `?` — рівно один довільний символ.
* `[a-z]` та `[!0-9]` — діапазони та заперечення класів символів.
* `|` — логічне об'єднання альтернатив в одній гілці.

```sh
file_type="archive.tar.gz"

case "$file_type" in
    *.tar.gz|*.tgz)
        tar -xzf "$file_type"
        ;;
    *.zip)
        unzip -q "$file_type"
        ;;
    *.deb|*.rpm)
        echo "Пакет встановлення ПЗ"
        ;;
    *)
        echo "Невідомий формат файлу" >&2
        exit 1
        ;;
esac
```

### Розширені шаблони extglob у case

Якщо увімкнено розширений режим globbing через `shopt -s extglob`, шаблони `case` підтримують квантифікатори:
* `?(list)` — нуль або один збіг.
* `*(list)` — нуль або більше збігів.
* `+(list)` — один або більше збігів підряд.
* `@(list)` — рівно один точний збіг.
* `!(list)` — усе, крім зазначених варіантів.

```bash
shopt -s extglob
input="server_node_01.prod"

case "$input" in
    server_+(node|worker)_+([0-9]).@(prod|stage))
        echo "Валідний сервер кластера"
        ;;
    *)
        echo "Невідомий тип хоста"
        ;;
esac
```

### Спеціальні термінатори гілок у Bash (;;, ;&, ;;&)

Стандартний термінатор `;;` працює як оператор `break`: після виконання відповідної гілки керування негайно передається за межі блоку `esac`.

Bash версій 4.0+ надає додаткові інструменти керування:

1. **`;&` (fallthrough)**: виконує команди поточної гілки та безумовно провалюється у тіло **наступної** гілки без перевірки її шаблону.
2. **`;;&` (resume testing)**: виконує команди поточної гілки, але **не зупиняє** роботу оператора, а продовжує тестувати решту нижчих шаблонів.

```bash
# Демонстрація ;;& для послідовного накопичення властивостей
feature="PROD_LOG_DEBUG"

case "$feature" in
    *PROD*)
        echo "Середовище: Production"
        ;;&
    *LOG*)
        echo "Увімкнено логування"
        ;;&
    *DEBUG*)
        echo "Увімкнено детальний режим"
        ;;
esac
```

> 🔧 **Навіщо це.**
> Оператор `case` незамінний для аналізу позиційних параметрів та прапорців запуску сценарію (`$1`, `$2`), обробки сигналів або визначення типу операційної системи (`case "$(uname -s)" in Linux) ... ;; Darwin) ... ;; esac`). На відміну від `if`, парсер будує для `case` оптимізовану таблицю переходів, що суттєво пришвидшує роботу в циклах.

## 6. Різновиди циклів: for, while та until

Оболонка надає три базові конструкції організації повторюваних операцій: циклічний перебір списку (`for`), цикл з передумовою успіху (`while`) та цикл до настання успіху (`until`).

### 1. Ітерація списків: цикл `for in`

Класичний цикл `for` обходить список слів, розділених пробілами або символами `IFS`:

```sh
for item in word1 word2 word3; do
    echo "Елемент: $item"
done
```

Якщо секцію `in список` повністю опущено, цикл за замовчуванням ітерується по масиву позиційних параметрів `"$@"`:

```sh
# for arg еквівалентно for arg in "$@"; do
for arg; do
    echo "Аргумент скрипту: $arg"
done
```

> ⚠️ **Критична помилка `for file in $(ls *.txt)`**:
> Ніколи не використовуйте підстановку виводу команди `ls` у циклі `for`. Якщо ім'я файлу містить пробіл або символ нового рядка (наприклад, `My Report 2026.txt`), етап розбиття на слова розділить його на три окремі ітерації: `My`, `Report` та `2026.txt`.
>
> Правильний спосіб обходу файлів — прямий globbing:
> ```sh
> for file in *.txt; do
>     [ -e "$file" ] || continue  # Захист на випадок, якщо збігів немає і шаблон лишився *.txt
>     process "$file"
> done
> ```

### 2. Арифметичний C-style цикл у Bash

Bash підтримує трикомпонентний цикл з ініціалізацією, перевіркою межі та кроком ітерації:

```bash
for (( i = 0, j = 10; i <= 10; i++, j-- )); do
    printf "i = %-2d | j = %-2d\n" "$i" "$j"
done
```

### 3. Цикли `while` та `until`

* `while команда; do ... done` — виконує тіло циклу доти, доки `команда` повертає статус `0` (істина).
* `until команда; do ... done` — виконує тіло циклу доти, доки `команда` повертає ненульовий статус помилки (поки не стане `0`).

```sh
# Очікування готовності мережевого порту сервісу
until nc -z 127.0.0.1 5432 2>/dev/null; do
    echo "Очікування запуску бази даних..."
    sleep 1
done
echo "База даних доступна"
```

### Нескінченні цикли та вбудована команда `:`

Для побудови постійно діючих демонів застосовують конструкцію `while :; do ... done`. Двокрапка `:` — це вбудована нульова команда POSIX (null command), яка нічого не робить і гарантовано повертає код виходу `0`. Вона працює швидше за команду `while true`, оскільки в деяких мінімальних оболонках `true` може викликати зовнішній бінарник.

### Керування ітераціями: `break` та `continue`

Оператори `break` та `continue` дозволяють примусово переривати цикл або переходити до наступної ітерації. Обидва оператори приймають необов'язковий числовий аргумент `n`, який задає глибину переривання у випадку вкладених циклів:

```sh
# Вихід із двох рівнів вкладених циклів одночасно
for i in 1 2 3; do
    for j in A B C; do
        if [ "$i" -eq 2 ] && [ "$j" = "B" ]; then
            break 2  # Перериває як внутрішній, так і зовнішній цикл
        fi
        echo "Вузол: $i-$j"
    done
done
```

## 7. Канонічний патерн читання потоку: while IFS= read -r line

Обробка текстових файлів та конвеєрів рядок за рядком є одним із найвідповідальніших завдань у системному адмініструванні. Будь-яка помилка в налаштуванні команди `read` призводить до пошкодження даних: обрізання пробілів, спотворення зворотних слешів або втрати останнього рядка файлу.

Єдиним надійним і безпечним шаблоном читання є:

```sh
while IFS= read -r line || [ -n "$line" ]; do
    printf "%s\n" "$line"
done < input.txt
```

![Анатомія потокового читання рядків](/root/sys/sys-unix/script-control-flow/img/while-read-pipeline.svg)
*Анатомія безпечного читання потоку: взаємодія опції -r, очищення IFS та запобіжника непорожнього рядка при EOF.*

Розберемо детально призначення кожного з трьох компонентів цієї конструкції.

### 1. Роль опції `-r` (Raw Mode)

За замовчуванням команда `read` сприймає символ зворотного слешу `\` як символ екранування (escape character).
* Якщо рядок містить послідовність `\t`, `read` видаляє слеш і залишає лише літеру `t`.
* Якщо зворотний слеш стоїть наприкінці рядка перед переведенням рядка `\ \n`, `read` сприймає це як продовження рядка і зливає наступний рядок із поточним.

Прапорець `-r` (raw) вимикає обробку екранування: зворотні слеші зчитуються як буквальні символи без жодних змін. Це критично для читання шляхів Windows, регулярних виразів, коду C/C++ та LaTeX-розмітки.

### 2. Роль префікса `IFS=`

Змінна `IFS` (англ. *Internal Field Separator*) за замовчуванням містить пробіл, табуляцію та новий рядок (`<space><tab><newline>`). Команда `read` використовує символи `IFS` для розбиття вичитаного рядка на слова та автоматично **видаляє всі початкові та кінцеві пробіли**.

Якщо файл містить рядок із відступами:
`    int main() {`

Без `IFS=` змінна `line` отримає обрізане значення `int main() {`.
Встановлення префікса `IFS=` перед командою `read` очищає роздільник полів для конкретного виклику вбудованої команди. Усі пробіли та символи табуляції на початку й наприкінці рядка залишаються недоторканими.

### 3. Роль запобіжника `|| [ -n "$line" ]`

Команда `read` зчитує символи доти, доки не зустріне символ нового рядка `\n` або маркер кінця файлу EOF (End Of File).

Якщо останній рядок файлу не має завершального переходу рядка `\n` (поширена поведінка багатьох текстових редакторів або конкатенованих потоків):
1. `read` зчитує доступні байти у змінну `line`.
2. Оскільки потік завершився символом EOF замість `\n`, команда `read` повертає **ненульовий код статусу** (`$? == 1`).
3. Без додаткової перевірки цикл `while` негайно переривається.
4. **Наслідок**: останній рядок файлу ніколи не потрапляє в тіло циклу і безслідно губиться!

Конструкція `|| [ -n "$line" ]` рятує цей рядок: навіть якщо `read` завершився з кодом `1`, оператор `||` перевіряє, чи змінна `line` не є порожньою (`strlen > 0`). Якщо в ній залишилися зчитані байти, умова циклу стає істинною, тіло циклу успішно обробляє останній рядок, а на наступній ітерації `read` поверне `1` при порожньому рядку, і цикл коректно зупиниться.

### Читання потоків із нульовим байтом: `read -d ''`

Якщо дані містять довільні символи включно з переводами рядків (наприклад, список файлів, згенерований `find -print0`), використовують опцію `read -d ''`. Вона встановлює роздільником нульовий байт (`\0`), що забезпечує 100% надійність при роботі з будь-якими іменами файлів на диску:

```bash
while IFS= read -r -d '' file || [ -n "$file" ]; do
    printf "Обробка файлу: %s\n" "$file"
done < <(find . -type f -name "*.log" -print0)
```

## 8. Проблема подоболонки при конвеєрі та шляхи її вирішення

Типова системна пастка виникає при спробі передати потік у цикл через конвеєр:

```sh
count=0

# НЕБЕЗПЕЧНО: конвеєр у POSIX sh породжує подоболонку
cat /etc/passwd | while IFS=: read -r user pass uid gid rest; do
    if [ "$uid" -ge 1000 ]; then
        count=$((count + 1))
    fi
done

echo "Знайдено користувачів: $count"
```

При запуску цього скрипту змінна `count` завжди виведе `0`.

Причина криється в архітектурі виконання конвеєрів (pipelines): стандарт POSIX дозволяє оболонці виконувати кожну команду конвеєра в окремому дочірньому процесі через системний виклик `fork()`. Цикл `while` виконується в ізольованому адресному просторі подоболонки (subshell). Коли цикл завершується, його процес знищується разом з усіма зміненими змінними. Батьківський процес оболонки зберігає своє початкове значення `count=0`.

### Спосіб 1: Пряме перенаправлення файлу у цикл (POSIX-сумісний)

```sh
count=0
while IFS=: read -r user pass uid gid rest; do
    if [ "$uid" -ge 1000 ]; then
        count=$((count + 1))
    fi
done < /etc/passwd

echo "Знайдено користувачів: $count"  # Коректно виведе пораховану кількість
```

### Спосіб 2: Підстановка процесів Process Substitution (Bash / Zsh)

Якщо вхідні дані генеруються складною командою або фільтром:

```bash
count=0
while IFS= read -r line; do
    (( count++ ))
done < <(grep "ERROR" /var/log/syslog | awk '{print $5}')

echo "Усього помилок: $count"
```

Конструкція `< <(команда)` створює анонімний FIFO або дескриптор у `/dev/fd/N` і перенаправляє його у вхідний потік основного процесу циклу без створення субшелу для `while`.

### Спосіб 3: Опція `shopt -s lastpipe` (Bash 4.2+)

Вимкнення створення субшелу для останнього елемента конвеєра (діє лише в неінтерактивних скриптах із вимкненим job control):

```bash
shopt -s lastpipe

count=0
cat /etc/passwd | while IFS= read -r line; do
    (( count++ ))
done

echo "Усього рядків: $count"  # Працює коректно
```

Повний працюючий приклад парсера з валідацією полів та аналогами на C і C++ наведено у проекті [Надійний потоковий парсер на Bash та C/C++](root:sys-unix/script-control-flow/proj-safe-stream-parser.md).

## 9. Зведена таблиця інженерної дисципліни

| Завдання | Рекомендований інструмент | Чому саме він | Чого слід уникати |
| :--- | :--- | :--- | :--- |
| Базові перевірки в POSIX sh | `[ "$var" = "val" ]` | Максимальна переносність (POSIX) | Незалапковані змінні `[ $var = val ]`, оператори `-a`/`-o` |
| Складні умови у Bash | `[[ $var == pattern ]]` | Захист від розбиття слів, regex `=~`, globbing | Використання застарілого `[` у коді Bash |
| Робота з числами | `(( a > b && c == 0 ))` | Природний синтаксис C, безпека обчислень | `[ "$a" -gt "$b" ]` у Bash |
| Множинний вибір рядків | `case "$val" in ... esac` | Швидкодія, наочність, globbing, альтернативи | Нескінченні ланцюжки `if-elif-elif-else` |
| Обхід файлів | `for f in *.log; do ... done` | Безпека при наявності пробілів у назвах | Розбір виводу через `for f in $(ls *.log)` |
| Потокове читання | `while IFS= read -r l \|\| [ -n "$l" ]` | Збереження пробілів, слешів, останнього рядка | Звичайний `read l` без `-r` та `IFS=` |
| Збереження змінних циклу | `while ... done < <(cmd)` | Запобігає ізоляції змінних у subshell | `cmd \| while read ...` без `lastpipe` |
