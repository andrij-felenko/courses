# 📜 Історія raw-пристроїв, devfs та становлення udev

У первинній архітектурі Unix пристрої ділилися на символьні та блочні за жорстким правилом: символьний пристрій обробляв потік байтів без кешування, а блочний проходив через ядерний буферний кеш (buffer cache). Проте наприкінці 1980-х і впродовж 1990-х років ця елегантна двокомпонентна схема зіткнулася з двома проблемами: високопродуктивними базами даних, які вимагали прямого доступу до носія без посередництва ядра, та вибуховим зростанням кількості периферійних пристроїв, що зробило статичну каталог-модель `/dev` непридатною.

Розуміння того, як Linux пройшов шлях від спеціальних «сирих» пристроїв (`/dev/raw/rawN`) та вбудованої у ядро файлової системи `devfs` до сучасного дуету `sysfs` і `udev`, пояснює, чому нинішня модель пристроїв влаштована саме так.

## Проблема буферного кеша та виникнення Raw-пристроїв

Коли файлова система або програма читає дані з блочного пристрою `/dev/sda`, ядро Unix проганяє ці дані через власний буферний кеш (пізніше об'єднаний у сторінковий кеш, page cache). Для більшості програм це прискорює повторний доступ у сотні разів.

Проте для великих реляційних систем керування базами даних (СУБД, таких як Oracle Database, IBM DB2 чи Sybase) ядерний кеш створював три критичні проблеми:

1. **Подвійне кешування (Double Buffering):** СУБД має власну складну систему кешування у пам'яті (SGA у Oracle чи Buffer Pool у DB2), налаштовану під її власні шаблони доступу. Подвійне копіювання даних (з диска в ядерний кеш, а звідти в буфер СУБД) марнувало оперативну пам'ять та процесорні такти.
2. **Втрата контролю над скиданням (Flush Control):** СУБД вимагають гарантії запису транзакційних логів (Write-Ahead Logging, WAL) на фізичний диск до того, як транзакція вважатиметься завершеною. Ядерний буферний кеш відкладав запис на диск на власний розсуд, що загрожувало пошкодженням бази даних при збої живлення.
3. **Обхід обмежень файлової системи:** У 1990-х роках багато файлових систем мали обмеження на максимальний розмір файла (наприклад, 2 ГіБ у 32-бітних системах) та оверхед на оновлення метаданих (метадані інодів оновлювалися синхронно).

Щоб обійти ці проблеми, в Unix системи (Solaris, AIX, HP-UX) ввели так звані **сирі пристрої (raw devices)**. У Linux це реалізували через підсистему `/dev/raw/rawN` та утиліту `raw(8)`.

```bash
# Прив'язка блочного пристрою sda1 до сирого символьного пристрою raw1
raw /dev/raw/raw1 /dev/sda1
```

Символьний вузол `/dev/raw/raw1` мав власні номери символьного драйвера `raw` (major 162), а команда `raw` лише прив'язувала до нього `dev_t` цільового блочного пристрою; VFS відкривала цей вузол як символьний (`S_IFCHR`). Драйвер raw-пристрою перехоплював системні виклики `read()` та `write()`, формував буфери I/O безпосередньо у пам'яті користувацького процесу і відправляв їх прямо в чергу контролера диска, минаючи ядерний кеш.

### Чому Raw-пристрої занепали й поступилися `O_DIRECT`

Попри популярність серед адміністраторів СУБД у 1990-х роках, артефакт `/dev/raw` виявився громіздким і негнучким. Для кожного диска чи розділу доводилося створювати додатковий символьний вузол, налаштовувати права доступу і стежити за відповідністю між `/dev/sdaN` та `/dev/raw/rawN`.

На початку 2000-х серед розробників ядра утвердилася думка, що окремий тип символьного пристрою заради обходу кеша — це помилка дизайну. Правильніше було надати прикладній програмі можливість самостійно вказувати бажаний режим відкриття звичайного блочного файла чи диска. Так у гілці 2.4, на наполягання постачальників СУБД, з'явився `O_DIRECT` — інтерфейс, про який сам Лінус Торвальдс відгукувався різко, але який усе одно витіснив raw-пристрої.

Так у системному виклику `open()` з'явився прапорець **`O_DIRECT`**. При відкритті блочного файла або звичайного файла на файловій системі з прапорцем `O_DIRECT`, ядро виконує Direct I/O:
- Дані передаються через DMA безпосередньо між буфером у просторі користувача та дисковим контролером.
- Сторінковий кеш не залучається.
- Операція вимагає вирівнювання буфера пам'яті, зсуву у файлі та розміру передачі за межею логічного сектора (зазвичай 512 або 4096 байтів).

З появою `O_DIRECT` потреба в підсистемі `/dev/raw` зникла. У ядрі Linux 2.6.3 утиліту `raw` оголосили застарілою (deprecated), а в Linux 5.14 (серпень 2021 року) підсистему `/dev/raw` остаточно видалили з ядра.

## Криза статичного `/dev` та поразка `devfs`

У класичних системах Unix (AT&T System V, BSD) каталог `/dev` був звичайним розділом на жорсткому диску, де зберігалися тисячі статично створених вузлів пристроїв (`mknod`). Поставлявся спеціальний скрипт `MAKEDEV`, який створював файли для всіх можливих нових дисковводів, послідовних портів та псевдотерміналів.

До кінця 1990-х років ця схема розвалилася з кількох фундаментальних причин:

1. **Експоненційне зростання апаратури:** З появою шин гарячого підключення (PCMCIA, USB, IEEE1394/FireWire) пристрої почали динамічно з'являтися та зникати під час роботи системи. Статична таблиця не могла передбачити номери для нових пристроїв.
2. **Вичерпання діапазону Major/Minor:** У старому Linux номери пристроїв були 16-бітними (8 біт major, 8 біт minor). Молодших номерів 256 катастрофічно бракувало для систем із десятками SCSI дисків та розділів.
3. **Захаращення ФС:** Статичний каталог `/dev` містив десятки тисяч файлів інодів, навіть якщо в реальному комп'ютері був встановлений лише один диск. Це сповільнювало пошук файлів і займало місце на кореневому носії.

### Експеримент `devfs` (1999–2006)

У 1999 році австралійський розробник Річард Ґуч (Richard Gooch) запропонував розв'язати проблему за допомогою **`devfs`** (Device Filesystem) — спеціальної віртуальної файлової системи, вбудованої безпосередньо у ядро Linux (включена у гілку ядра 2.3.46). Ідея полягала в тому, що ядро самостійно створювало файли пристроїв у каталозі `/dev` у момент їх реєстрації драйвером і видаляло їх при відключенні.

Однак реалізація `devfs` виявилася невдалим архітектурним рішенням і викликала гострі суперечки серед розробників ядра:

- **Політика у просторі ядра:** Назви пристроїв (наприклад, `/dev/scsi/host0/bus0/target0/lun0/disc`) формувалися всередині коду ядра. Це порушувало канонічний принцип Unix: *ядро надає механізми, а простір користувача визначає політику*. Змінити схему найменування або створити власні зручні синоніми без перекомпіляції ядра було неможливо.
- **Взаємні блокування (Deadlocks):** Створення вузла пристрою у `devfs` вимагало захоплення замків VFS всередині контексту виклику драйвера пристрою, що часто призводило до deadlocks під час обробки переривань гарячого підключення.
- **Відсутність подій для користувача:** `devfs` не мала надійного асинхронного механізму сповіщення демонів у просторі користувача про зміну стану пристрою або зміну власника та прав доступу (`chmod`/`chown`).

Внаслідок цих дефектів провідні розробники ядра (зокрема Ґреґ Кроа-Гартман та Кай Сіверс) визнали `devfs` тупиковою гілкою. У ядрі Linux 2.6.13 `devfs` оголосили застарілою, а в 2.6.18 (вересень 2006 року) повністю видалили з сирцевого коду.

## Перемога підсистеми `udev` та `sysfs`

У 2003 році було створено нову, принципово іншу архітектуру керування пристроями, яка діє в Linux і досі. Вона базується на чіткому розділенні обов'язків між ядром та простором користувача:

1. **`sysfs` (віртуальна ФС у ядрі):** Ядро експортує ієрархічну структуру всіх зареєстрованих пристроїв, шин та драйверів у вигляді файлового дерева у `/sys/`. Кожен пристрій має атрибути `dev` (що містить Major:Minor), `uevent` та параметри драйвера.
2. **`netlink` (kobject_uevent):** Коли апаратура з'являється або зникає, ядро надсилає повідомлення у простір користувача через сокет `NETLINK_KOBJECT_UEVENT`.
3. **`udev` (демон у просторі користувача):** Демон `udevd` перехоплює події `netlink`, зчитує конфігураційні правила з `/etc/udev/rules.d/`, зчитує атрибути пристрою з `/sys/` і створює відповідний файл пристрою у ФС **`devtmpfs`** (спеціальна мінімальна пам'ятнева ФС для `/dev`).

```
+-------------------------------------------------------------+
|                     Простір користувача                     |
|                                                             |
|   +---------------+     правила     +-------------------+   |
|   |  udevd daemon | <-------------- | /etc/udev/rules.d |   |
|   +-------+-------+                 +-------------------+   |
|           |                                                 |
|           | створює/видаляє вузли                           |
|           v                                                 |
|   +---------------+                                         |
|   |   /dev (ФС)   |                                         |
|   +---------------+                                         |
+-----------|-------------------------------------------------+
|           | Netlink uevents         ^                       |
|           v                         | зчитування атрибутів  |
+-------------------------------------|-----------------------+
|   +---------------+         +-------+-------+               |
|   |  devtmpfs     |         |    sysfs      |               |
|   +---------------+         +---------------+               |
|                                                             |
|                    Простір ядра (Kernel)                    |
+-------------------------------------------------------------+
```

Для оптимізації швидкості завантаження системи в Linux 2.6.32 Кай Сіверс створив **`devtmpfs`** — внутрішню ядерну ФС для `/dev`. Тепер ядро миттєво створює базовий вузол пристрою з дефолтним іменем одразу після ініціалізації драйвера, а вже потім демон `udev` перейменовує його, створює символічні посилання (наприклад, `/dev/disk/by-uuid/...`) та роздає права доступу згідно з правилами адміністратора.

Ця еволюція продемонструвала фундаментальну мудрість Unix-архітектури: ядро Linux звільнилося від обов'язку формувати текстові шляхи та правила доступу до файлів `/dev`. Ядро лише реєструє абстрактні символьні або блочні пристрої, присвоює їм пари Major:Minor та сповіщає про це у простір користувача, де демони `udev` реалізують будь-яку довільну політику найменування, створення симлінків та роздачі прав доступу.
