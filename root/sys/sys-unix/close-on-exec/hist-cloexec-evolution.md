# 📜 Від ioctl(FIOCLEX) до атомарного O_CLOEXEC: історія закриття дескрипторів

У ранніх версіях Unix успадкування всіх відкритих файлів через виклики `fork` та `exec` вважалося головною архітектурною перевагою системи. Саме на цьому трималася магія командної оболонки Кena Томпсона: оболонка створювала канал, розставляла стандартні потоки вводу-виводу через системні виклики `dup` і підміняла образ програми за допомогою `exec`, не змінюючи жодного рядка в утилітах `cat`, `grep` чи `wc`.

Проте коли Unix вийшов за межі лабораторних експериментів і став основою для багатокористувацьких серверів із мережевими демонами та базами даних, це саме правило перетворилося на хронічне джерело витоків і вразливостей.

## Перші спроби: ioctl(FIOCLEX) у BSD

Наприкінці 1970-х років у шостій і сьомій редакціях Research Unix (V6 та V7) механізму вибіркового закриття дескрипторів не існувало взагалі. Якщо програма відкривала конфіденційний файл налаштувань чи внутрішній журнал, єдиним способом не віддати його сторонній утиліті було явне закриття дескриптора руками між викликами `fork` та `exec`.

У складних програмах це призводило до помилок: розробники забували про дескриптори, відкриті глибоко у допоміжних бібліотеках, і ті непомітно переходили до дочірніх процесів.

Перше рішення запропонували розробники Університету Каліфорнії в Берклі під час створення 4.1cBSD та 4.2BSD (1982–1983 роки). Вони додали два спеціальні запити до універсального виклику керування пристроями `ioctl`:

:::tabs
```c
#include <sys/ioctl.h>

ioctl(fd, FIOCLEX, 0);   /* File IO Close on Exec — увімкнути закриття */
ioctl(fd, FIONCLEX, 0);  /* File IO No Close on Exec — вимкнути закриття */
```
```cpp
#include <sys/ioctl.h>
#include <system_error>

void set_bsd_fioclex(int fd) {
    if (::ioctl(fd, FIOCLEX, 0) == -1) {
        throw std::system_error(errno, std::generic_category(), "ioctl(FIOCLEX) failed");
    }
}
```
:::

Ці макроси маніпулювали внутрішнім прапорцем у дескрипторній таблиці процесу. Але використання `ioctl` для керування дескрипторами виглядало чужорідним: `ioctl` призначався для специфічних операцій над драйверами пристроїв, а дескрипторні прапорці були властивістю ядра загального призначення.

## Стандартизація POSIX.1-1988: поява fcntl та FD_CLOEXEC

Коли комітет IEEE розпочав роботу над стандартом POSIX (IEEE Std 1003.1-1988), механізм беркліївського `FIOCLEX` вирішили стандартизувати й перенести в системний виклик `fcntl` (англ. *file control*).

Саме тоді з'явилася команда `F_SETFD` і перший (і довгий час єдиний) дескрипторний прапорець:

:::tabs
```c
#include <fcntl.h>

int flags = fcntl(fd, F_GETFD);
fcntl(fd, F_SETFD, flags | FD_CLOEXEC);
```
```cpp
#include <fcntl.h>
#include <system_error>

void set_posix_cloexec(int fd) {
    int flags = ::fcntl(fd, F_GETFD);
    if (flags == -1 || ::fcntl(fd, F_SETFD, flags | FD_CLOEXEC) == -1) {
        throw std::system_error(errno, std::generic_category(), "fcntl failed");
    }
}
```
:::

Архітектурно це виглядало завершеним і витонченим рішенням для однопотокових систем кінця 1980-х років. Батьківський процес міг одразу після `open` або `socket` позначити дескриптор як «приватний», і ядро гарантувало його автоматичне знищення під час будь-якого наступного `execve`.

## Поява POSIX Threads і криза неатомарності

У середині 1990-х років стандарт POSIX.1c-1995 ввів у Unix підтримку багатопотоковості (Pthreads). Усі потоки одного процесу отримали спільний адресний простір і **спільну таблицю файлових дескрипторів**.

Ось тут конструкція `open` + `fcntl(FD_CLOEXEC)` миттєво зламалася.

Між поверненням дескриптора з виклику `open` у Потоці 1 і наступним викликом `fcntl` у тому ж потоці проходило кілька десятків або сотень тактів процесора. Якщо в цей мікроскопічний проміжок часу Потік 2 викликав `fork` і запускав зовнішню утиліту через `execve`, дочірній процес клонував таблицю дескрипторів до того, як Потік 1 устигав виставити `FD_CLOEXEC`.

Дескриптор неминуче витікав у чужу програму. Найгіршим було те, що жодна бібліотека не могла захиститися від цього локальним м'ютексом: сторонній потік у чужій бібліотеці того ж процесу нічого не знав про внутрішні блокування.

## Ініціатива Ульріха Дреппера та Linux 2.6.27 (2007–2008)

У 2007 році провідний супровідник GNU C Library (glibc) Ульріх Дреппер (Ulrich Drepper) опублікував низку пропозицій та патчів до ядра Linux. Він довів, що стан гонитви принципово неможливо усунути у просторі користувача без підтримки з боку системних викликів створення дескрипторів.

Ядро мусило навчитися виставляти біт `close_on_exec` **атомарно в момент виділення дескриптора**, до того як його номер стане видимим для користувацького коду.

Починаючи з версії Linux 2.6.27 (жовтень 2008 року), ядро отримало ціле сімейство розширених системних викликів:
- Прапорець `O_CLOEXEC` для системних викликів `open`, `openat`;
- Новий виклик `pipe2`, що приймає прапорці `O_CLOEXEC` та `O_NONBLOCK`;
- Виклик `dup3` та команду `F_DUPFD_CLOEXEC` для `fcntl`;
- Прапорці `SOCK_CLOEXEC` та `SOCK_NONBLOCK` для `socket` і `socketpair`.

У ядрі Linux 2.6.28 додався виклик `accept4`, а далі — `epoll_create1`, `signalfd4`, `timerfd_create`, `eventfd2` та `inotify_init1`.

## Стандартизація в POSIX.1-2008

Ініціатива Linux була настільки критичною для безпеки та стабільності системного програмування, що The Open Group та IEEE негайно включили прапорець `O_CLOEXEC`, виклики `openat` і команду `F_DUPFD_CLOEXEC` до стандарту **POSIX.1-2008 (IEEE Std 1003.1-2008, Issue 7)**.

Сьогодні правило «завжди відкривати з O_CLOEXEC за замовчуванням» є фундаментальною нормою проєктування надійного системного програмного забезпечення на Unix-подібних платформах.
