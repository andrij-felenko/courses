# 📋 Інтерфейси керування netns: системні виклики, Netlink та sysfs

Цей довідник містить систематизований опис усіх програмних інтерфейсів ядра Linux, які використовуються для створення, перемикання, налаштування та моніторингу мережевих просторів імен (Network Namespaces). У матеріалі розкрито системні виклики, файлові інтерфейси VFS та `procfs`, бінарні атрибути `rtnetlink`, області видимості `sysctl` та точки трасування ядра.

---

## 1. Архітектурні основи та системні виклики ядра

Управління мережевими просторами імен у ядрі Linux реалізовано через уніфіковану підсистему `nsproxy`. За зміну або виділення мережевого стека відповідає прапорець `CLONE_NEWNET` (значення `0x40000000`, яке визначено у системному заголовку `<sched.h>`).

Коли процес звертається до підсистеми просторів імен, ядро оперує трьома основними системними викликами: `clone(2)`, `unshare(2)` та `setns(2)`.

### 1.1. Системний виклик `clone(2)` / `clone3(2)`

Системний виклик `clone()` створює новий дочірній процес і атомарно поміщає його у новостворений мережевий простір імен.

:::tabs
```c
#include <sched.h>

int clone(int (*fn)(void *), void *child_stack, int flags, void *arg, ...);
```
```cpp
#include <sched.h>
#include <system_error>

pid_t safe_clone(int (*fn)(void*), void* stack, int flags, void* arg) {
    pid_t pid = ::clone(fn, stack, flags, arg);
    if (pid < 0) {
        throw std::system_error(errno, std::generic_category(), "Помилка системного виклику clone()");
    }
    return pid;
}
```
:::

Під час виконання `clone()` з прапорцем `CLONE_NEWNET` ядро викликає внутрішню функцію `copy_namespaces()`. Вона перевіряє наявність прапорця та ініціює виклики створення нових підсистем.

* **Параметр `flags`:** Бітова маска, що мусить містити `CLONE_NEWNET`. Вона може вільно комбінуватися з іншими прапорцями ізоляції ядра: `CLONE_NEWPID` (ізоляція таблиці процесів), `CLONE_NEWNS` (ізоляція точок монтування VFS), `CLONE_NEWIPC` (міжпроцесна взаємодія POSIX/SysV), `CLONE_NEWUTS` (імена хоста та домену) та `CLONE_NEWUSER` (простір ідентифікаторів користувачів UID/GID).
* **Повертане значення:** Повертає PID новоствореного дочірнього процесу у контексті батьківського простору процесів у разі успіху; `-1` повертається у разі помилки, а глобальна змінна `errno` встановлюється у відповідне значення.
* **Вимоги до привілеїв:** Створення мережевого простору вимагає саме `CAP_SYS_ADMIN` у діючому User Namespace (`CAP_NET_ADMIN` для цього не досить — він керує вже наявними пристроями й правилами). Якщо `CLONE_NEWNET` використовується разом із `CLONE_NEWUSER`, привілей перевіряється у контексті нового User Namespace, що дозволяє створювати мережеві простори непривілейованим користувачам.

### 1.2. Системний виклик `unshare(2)`

Системний виклик `unshare()` відокремлює поточний потік виконання від його поточного мережевого простору та виділяє для нього новий ізольований простір без створення нового дочірнього процесу.

:::tabs
```c
#include <sched.h>

int unshare(int flags);
```
```cpp
#include <sched.h>
#include <system_error>

void safe_unshare(int flags) {
    if (::unshare(flags) != 0) {
        throw std::system_error(errno, std::generic_category(), "Помилка системного виклику unshare()");
    }
}
```
:::

* **Параметр `flags`:** Бітова маска, що містить прапорець `CLONE_NEWNET`.
* **Внутрішній механізм ядра:** Виклик ініціює функцію `unshare_nsproxy_namespaces()`, яка через `create_new_namespaces()` доходить до `copy_net_ns()`. Ядро виділяє нову структуру `struct net` у SLAB-кеші `net_cachep`, присвоює їй унікальний ідентифікатор Inode у файловій системі `nsfs` та виконує послідовний виклик підсистеми ініціалізації `setup_net()`. Під час цієї ініціалізації створюється віртуальний пристрій `loopback` (`lo`), який за замовчуванням залишається у вимкненому стані (`DOWN`), та створюються порожні таблиці маршрутизації FIB.
* **Повертане значення:** `0` при успішному завершенні; `-1` у разі виникнення помилки.

### 1.3. Системний виклик `setns(2)`

Системний виклик `setns()` приєднує поточний процес до вже наявного мережевого простору імен, ідентифікованого відкритим файловим дескриптором.

:::tabs
```c
#include <sched.h>

int setns(int fd, int nstype);
```
```cpp
#include <sched.h>
#include <system_error>

void safe_setns(int fd, int nstype) {
    if (::setns(fd, nstype) != 0) {
        throw std::system_error(errno, std::generic_category(), "Помилка системного виклику setns()");
    }
}
```
:::

* **Параметр `fd`:** Відкритий файловий дескриптор, що вказує на псевдофайл простору імен (наприклад, `/proc/[pid]/ns/net` або закріплений файл у каталозі `/var/run/netns/`).
* **Параметр `nstype`:** Передайте константу `CLONE_NEWNET` для явного контролю того, що файловий дескриптор дійсно посилається на мережевий простір імен. Якщо тип не відповідає очікуваному, виклик поверне помилку `EINVAL`. Якщо передати значення `0`, перевірка типу не виконується.
* **Повертане значення:** `0` при успішному приєднанні; `-1` у разі помилки.

### 1.4. Деталізований перелік кодів помилок

Під час роботи із системними викликами просторів імен ядро може повертати такі коди помилок через змінну `errno`:

* **`EPERM`:** Викликаючий процес не має `CAP_SYS_ADMIN` у відповідному User Namespace.
* **`EINVAL`:** Передано некоректну маску прапорців; або дескриптор `fd` у виклику `setns()` не посилається на дійсний об'єкт `nsfs`; або переданий `nstype` не відповідає типу простору.
* **`ENOMEM`:** Операційній системі не вдалося виділити необхідний обсяг оперативної пам'яті для створення структури `struct net` чи її внутрішніх таблиць маршрутизації та сокетів.
* **`ENOSPC`:** Досягнуто ліміту кількості мережевих просторів для даного користувача (`/proc/sys/user/max_net_namespaces`) — `unshare()` та `clone()` повертають саме цю помилку, а не `ENOMEM`.
* **`EBADF`:** Файловий дескриптор `fd`, переданий у `setns()`, є недійсним або відкритим у некоректному режимі доступу.
* **`EACCES`:** Відсутні права на читання відповідного псевдофайла `/proc/[pid]/ns/net`.

## 2. Файлова система VFS, nsfs та procfs інтерфейси

Мережеві простори імен тісно інтегровані з файловою системою Linux через віртуальну файлову систему `nsfs` (Namespace Filesystem) та інформаційний каталог `/proc`.

### 2.1. Структура `nsfs` та псевдофайли `/proc/[pid]/ns/net`

Кожен процес у файловій системі `/proc` має каталог `/proc/[pid]/ns/`, у якому експортується символьне посилання `net`:

```bash
ls -l /proc/self/ns/net
# lrwxrwxrwx 1 root root 0 net -> net:[4026531992]
```

Число у квадратних дужках (`4026531992`) являє собою унікальний номер Inode, виділений підсистемою `nsfs`. Цей номер використовується ядром для порівняння екземплярів просторів. Двоє процесів працюють у єдиному мережевому просторі тоді й лише тоді, коли їхні номери Inode у файлах `/proc/[pid]/ns/net` повністю збігаються.

Кожен об'єкт простору в ядрі містить вкладену структуру `struct ns_common`, яка включає:
* `const struct proc_ns_operations *ops`: Вказівник на таблицю операцій (для мережевого простору це `netns_operations`).
* `unsigned int inum`: Системний номер Inode.
* `refcount_t count`: Лічильник посилань на об'єкт.

### 2.2. Закріплення просторів (Bind Mount) та життєвий цикл

Якщо останній процес у просторі імен завершує свою роботу, ядро автоматично знищує цей простір, якщо на нього немає інших посилань. Щоб зберегти мережевий простір живим для подальшого використання, застосовується механізм закріплення (bind mount):

```bash
# Створення цільового файла та закріплення дескриптора простору
touch /var/run/netns/demo_ns
mount --bind /proc/self/ns/net /var/run/netns/demo_ns
```

Операція `mount --bind` створює у файловій системі VFS відкритий вузол монтування, який утримує посилання на `struct net` через структуру `struct path` та збільшує лічильник `net->count`. Для знищення закріпленого простору необхідно виконати демонування `umount /var/run/netns/demo_ns` та видалити файл.

### 2.3. Команди `ioctl(2)` на файлових дескрипторах `nsfs`

Починаючи з версії ядра Linux 4.9, дескриптори файлів просторів імен підтримують спеціальні команди `ioctl()` для інспекції власника та зв'язків:

:::tabs
```c
#include <sys/ioctl.h>
#include <linux/nsfs.h>

int user_ns_fd = ioctl(netns_fd, NS_GET_USERNS);
int ns_type = ioctl(netns_fd, NS_GET_NSTYPE);   /* поверне CLONE_NEWNET */
```
```cpp
#include <sys/ioctl.h>
#include <linux/nsfs.h>
#include <system_error>

int safe_nsfs_ioctl(int netns_fd, unsigned long request) {
    int res = ::ioctl(netns_fd, request);
    if (res < 0) {
        throw std::system_error(errno, std::generic_category(), "nsfs ioctl failed");
    }
    return res;
}
```
:::

* **`NS_GET_USERNS` (`0xb701`):** Повертає новий файловий дескриптор User Namespace, якому належить даний мережевий простір імен. Це дозволяє перевірити, який саме простір користувачів має права керування даним мережевим стеком.
* **`NS_GET_NSTYPE` (`0xb703`, від ядра 4.11):** Повертає тип простору, на який вказує дескриптор (для мережевого — `CLONE_NEWNET`). Зручно для перевірки перед `setns()`.
* **`NS_GET_PARENT` (`0xb702`):** Повертає дескриптор батьківського простору, але **лише для ієрархічних** типів — PID та User. Мережеві простори не утворюють ієрархії: вони всі рівноправні, а «батьківство» для них не визначене, тож на `netns`-дескрипторі цей `ioctl` завершується помилкою `EINVAL`. Спорідненість мережевих просторів простежують через `NS_GET_USERNS` (хто ним володіє) і через `nsid` у Netlink (хто з ким з'єднаний veth-парою).

## 3. Бінарний протокол RtNetlink та налаштування netns

Керування мережевими пристроями, призначення IP-адрес та переміщення інтерфейсів між мережевими просторами імен виконується у користувацькому просторі через сокети Netlink (родину адрес `AF_NETLINK` та протокол `NETLINK_ROUTE`).

Спілкування відбуваються шляхом обміну бінарними пакетами, що складаються із заголовка `struct nlmsghdr`, опису пристрою `struct ifinfomsg` та набору змінних атрибутів `struct rtattr`.

### 3.1. Ключові атрибути `RTM_NEWLINK` для керування `netns`

У разі надсилання повідомлення `RTM_NEWLINK` ядро приймає та обробляє такі атрибути з заголовка `<linux/if_link.h>`:

| Атрибут (`rtattr.rta_type`) | Тип даних | Детальний опис та функціональне призначення |
| :--- | :--- | :--- |
| `IFLA_NET_NS_PID` | `uint32_t` | Переміщує вказаний мережевий інтерфейс у мережевий простір процесу з даним PID. |
| `IFLA_NET_NS_FD` | `int32_t` | Переміщує мережевий інтерфейс у простір імен, вказаний відкритим файловим дескриптором. |
| `IFLA_IFNAME` | `string` | Задає ім'я мережевого інтерфейсу у цільовому просторі. |
| `IFLA_LINKINFO` | `nested` | Вкладений атрибут конфігурації віртуального пристрою (`veth`, `macvlan`, `ipvlan`). |
| `IFLA_IFALIAS` | `string` | Задає текстову примітку або альтернативну назву для інтерфейсу. |
| `IFLA_MASTER` | `uint32_t` | Прив'язує мережевий інтерфейс як ведений (slave) до моста `br0` або `bond0`. |
| `IFLA_ADDRESS` | `bytes` | Встановлює апаратну MAC-адресу мережевого пристрою. |

### 3.2. Вкладена структура атрибута `IFLA_LINKINFO` для veth-пар

Під час створення віртуальної пари `veth` через Netlink за один виклик передається вкладене повідомлення, яке дозволяє відразу розташувати один кінцевий інтерфейс у потрібному мережевому просторі:

```
IFLA_LINKINFO (Тип атрибута)
  ├── IFLA_INFO_KIND -> "veth" (Текстовий ідентифікатор драйвера ядра)
  └── IFLA_INFO_DATA (Дані конфігурації драйвера veth)
        └── VETH_INFO_PEER (Опис периферійного кінця пари)
              ├── struct ifinfomsg (Базовий заголовок пристрою)
              ├── IFLA_IFNAME -> "veth-inside" (Ім'я у цільовому netns)
              └── IFLA_NET_NS_FD -> target_netns_fd (Дескриптор цільового netns)
```

Такий підхід забезпечує атомарне створення пристрою без проміжних станів на хості.

## 4. Область видимості параметрів sysctl у `/proc/sys/net/`

Операційна система Linux класифікує параметри ядра у `/proc/sys/net/` за рівнем їхньої ізоляції: частина параметрів є строго локальною для кожного мережевого простору (`Per-Namespace`), тоді як інші параметри є глобальними для всієї операційної системи (`Host Global`).

### 4.1. Детальна класифікація параметрів sysctl

Структура `struct net` містить у собі вкладені модульні структури конфігурації sysctl:

1. **`net->ipv4.sysctl_ip_forward`:** Локальний прапорець маршрутизації IPv4. Дозволяє вмикати роутинг у контейнері без зміни налаштувань хоста.
2. **`net->ipv4.sysctl_tcp_rmem` та `sysctl_tcp_wmem`:** Масиви з трьох 32-бітних чисел, які задають мінімальний, типовий та максимальний буфери сокетів TCP у байтах для процесів даного простору.
3. **`net->core.sysctl_somaxconn`:** Верхня межа для аргументу `backlog` виклику `listen()` — тобто розмір черги вже встановлених з'єднань, які чекають на `accept()`.
4. **`net->ipv4.ip_local_ports`:** Початок і кінець діапазону ефемерних портів, з якого ядро добирає номер вихідного порту для клієнтських сокетів даного простору.

### Таблиця класифікації параметрів sysctl

| Параметр sysctl | Область видимості | Функціональне призначення та вплив на систему |
| :--- | :--- | :--- |
| `net.ipv4.ip_forward` | **Per-Namespace** | Дозволяє або забороняє L3-маршрутизацію пакетів між пристроями даного `netns`. |
| `net.ipv4.conf.<if>.forwarding` | **Per-Namespace** | Вмикає перенаправлення пакетів для конкретного мережевого інтерфейсу у межах `netns`. |
| `net.ipv4.tcp_rmem` | **Per-Namespace** | Мінімальний, типовий та максимальний розміри буферів прийому TCP для сокетів `netns`. |
| `net.ipv4.tcp_wmem` | **Per-Namespace** | Буфери передачі TCP сокетів у контексті даного мережевого простору. |
| `net.core.somaxconn` | **Per-Namespace** | Верхня межа черги готових з'єднань, що чекають на `accept()`, для сокетів `netns`. |
| `net.ipv4.ip_local_port_range` | **Per-Namespace** | Діапазон ефемерних портів, які використовуються для вихідних TCP/UDP з'єднань `netns`. |
| `net.ipv4.ping_group_range` | **Per-Namespace** | Діапазон груп користувачів (GID), яким дозволено створювати непривілейовані ICMP сокети. |
| `net.core.netdev_max_backlog` | **Глобальний (Host)** | Максимальна кількість пакетів у черзі прийому CPU для фізичних мережевих карт хоста. |
| `net.core.rmem_max` / `wmem_max` | **Глобальний (Host)** | Абсолютна верхня межа розміру буферів сокетів для всієї операційної системи. |
| `net.netfilter.nf_conntrack_max` | **Глобальний (Host)** | Загальний ліміт таблиці з'єднань Conntrack у пам'яті ядра для всіх просторів. |

## 5. Трасування створення та знищення просторів

Окремої підсистеми точок трасування для просторів імен у ядрі **немає**: у `/sys/kernel/tracing/events/` каталогу `netns` не існує, і файл `net/core/net_namespace.c` не містить жодного `trace_`-виклику. Це часте джерело плутанини — очікувані «`netns:net_ns_create`» та «`netns:net_ns_release`» у системі не знайдуться.

Тому життєвий цикл `struct net` трасують динамічними зондами по внутрішніх функціях ядра:

```bash
# Створення простору: copy_net_ns() → setup_net()
bpftrace -e 'kprobe:copy_net_ns { printf("%s створює netns\n", comm); }'

# Відкладене знищення: cleanup_net() з черги netns_wq
bpftrace -e 'kprobe:cleanup_net { printf("cleanup_net запущено\n"); }'
```

Для самого трафіку між просторами вже є справжні, стабільні точки трасування підсистеми `net`:

* **`net:netif_rx`:** Фіксує момент, коли `veth` кладе `sk_buff` у чергу прийому на приймальному боці пари.
* **`net:net_dev_xmit`:** Спрацьовує на передавальному боці й повертає код результату — так видно скинуті на межі кадри.
* **`skb:kfree_skb`:** Показує місце й причину (`reason`) знищення пакета, зокрема коли парний кінець `veth` перебуває у стані `DOWN`.

Оскільки kprobe прив'язується до імені внутрішньої функції, а не до стабільного ABI, такі скрипти можуть зламатися після оновлення ядра; точки трасування підсистеми `net` таких гарантій не порушують.

---

## 6. Інтерфейси файлової системи sysfs (`/sys/class/net/`)

Усі мережеві пристрої, доступні у поточному мережевому просторі імен, відображаються у віртуальній файловій системі `sysfs` за шляхом `/sys/class/net/`.

Кожен каталог пристрою містить такі важливі псевдофайли:
* `/sys/class/net/<ifname>/ifindex`: Унікальний числовий системний індекс інтерфейсу у поточному `netns`.
* `/sys/class/net/<ifname>/iflink`: Індекс парного інтерфейсу. Для `veth`-пари значення `iflink` вказує на індекс парного пристрою на хості або в іншому просторі.
* `/sys/class/net/<ifname>/operstate`: Текстовий стан пристрою (`up`, `down`, `unknown`).
* `/sys/class/net/<ifname>/mtu`: Значення максимального блоку передачі в байтах.

## 7. Розширений аналіз запитів RtNetlink та статистика `IFLA_STATS64`

Під час опитування стану інтерфейсів у мережевих просторах утиліти викликами `RTM_GETLINK` запитують розширену 64-бітну статистику лічильників прийому та передачі:

:::tabs
```c
struct rtattr *stats_attr; // Атрибут IFLA_STATS64
struct rtnl_link_stats64 *stats = (struct rtnl_link_stats64 *)RTA_DATA(stats_attr);

printf("Прийнято байтів: %llu, Передано байтів: %llu\n", 
       stats->rx_bytes, stats->tx_bytes);
```
```cpp
#include <iostream>

const auto* stats = reinterpret_cast<const rtnl_link_stats64*>(RTA_DATA(stats_attr));
std::cout << "Прийнято байтів: " << stats->rx_bytes 
          << ", Передано байтів: " << stats->tx_bytes << '\n';
```
:::

Для `veth`-пар за нормальної роботи `rx_bytes` одного кінця збігається з `tx_bytes` протилежного. Саме тому розбіжність цих двох чисел і є діагностичним сигналом: кадр порахували на передачу, але він не дійшов — парний кінець `DOWN`, розмір перевищив MTU приймального боку або спрацював фільтр.

## 8. Запити `NLM_F_DUMP` та інспекція таблиць маршрутизації

Для одержання повного переліку пристроїв або маршрутів у контексті поточного мережевого простору користувацький процес відправляє Netlink-запит із прапорцем `NLM_F_DUMP`.

Процес дампування маршрутів:
1. Програма формує заголовок `nlmsghdr` із `nlmsg_type = RTM_GETROUTE` та `nlmsg_flags = NLM_F_REQUEST | NLM_F_DUMP`.
2. Ядро повертає серію повідомлень `RTM_NEWROUTE`, кожне з яких описує один маршрут із таблиць `RT_TABLE_MAIN` або `RT_TABLE_LOCAL` даного мережевого простору.
3. Послідовність завершується повідомленням типу `NLMSG_DONE`.

Цей механізм дозволяє моніторинговим агентам швидко зчитувати повну таблицю FIB конкретного мережевого простору без опитування через `procfs`.

## 9. Інтеграція BPF Hook-точок у мережевих просторах

Трафік процесів усередині мережевого простору можна фільтрувати eBPF-програмами, прив'язаними до cgroup v2. Важливо не сплутати рівні: сама точка прив'язки належить cgroup, а не `netns`, — програма спрацьовує на сокетах процесів цієї cgroup у тому просторі, де ці сокети створено.

Ключові точки прив'язки eBPF:
* **`BPF_CGROUP_INET_INGRESS`:** Перехоплює всі вхідні IP-пакети до моменту їх обробки сокетами у даному `netns`.
* **`BPF_CGROUP_INET_EGRESS`:** Перехоплює вихідний трафік процесів даного простору.
* **`BPF_CGROUP_INET_SOCK_CREATE`:** Відслідковує момент виконання системного виклику `socket()` всередині простору і дозволяє динамічно блокувати створення певних типів сокетів (наприклад, RAW-сокетів).

---

## 10. Управління фільтрами фаєрвола nftables та iptables у netns

Підсистема Netfilter підтримує ізольовані екземпляри таблиць правил для кожного `struct net`.

Особливості роботи nftables у мережевих просторах:
* Таблиці та ланцюжки nftables, створені у просторі `netns-A`, повністю невидимі у просторі `netns-B`.
* Таблиця Conntrack (`net->ct`) є розділеною, тому сокетні з'єднання у `netns-A` не споживають ліміти Conntrack у `netns-B`.
* Правила маскування (NAT) обробляються локально: пакет піддається трансляції адреси лише під час проходження пост-маршрутизації (Postrouting hook) у тому просторі, де ввімкнено NAT.

## 11. Підсистема iproute2 та високорівнева бібліотека libnl

Розробка низькорівневих C/C++ додатків для роботи з Netlink може супроводжуватися рутинним кодом розпакування TLV-структур. Для спрощення у виробничих системних проєктах використовується бібліотека `libnl-route-3` (`libnl`).

`libnl` надає високорівневі обгортки для роботи з об'єктами мережевого простору:
* `nl_socket_alloc()`: Виділення та ініціалізація Netlink-сокета.
* `rtnl_link_veth_add()`: Високорівнева функція створення `veth`-пари; цільовий простір задається **PID** процесу, що в ньому працює (`IFLA_NET_NS_PID`), а не дескриптором.
* `rtnl_link_set_ns_fd()`: Переміщення створеного пристрою у простір за його дескриптором.

## 12. Параметр сокетів SO_BINDTODEVICE у контексті netns

Системна опція сокета `setsockopt(fd, SOL_SOCKET, SO_BINDTODEVICE, "eth0", ...)` дозволяє прив'язати сокет до конкретного мережевого інтерфейсу.

При використанні мережевих просторів імен:
1. Пошук пристрою `eth0` виконується виключно в межах того `struct net`, де створено сокет.
2. Якщо пристрій переміщено в інший простір, сокет втрачає пристрій прив'язки і спроба виклику `sendto()` повертає помилку `ENODEV`.

---

## 13. Особливості UNIX Domain Sockets та перетин межі просторів

Сокети UNIX Domain Sockets (`AF_UNIX`) у файловому режимі (Path-based sockets) ідентифікуються шляхом у VFS (наприклад, `/tmp/app.sock`).

* Якщо два процеси перебувають у різних мережевих просторах імен, але ділять спільний Mount Namespace, вони можуть вільно зв'язуватися через файловий UNIX-сокет. Мережева ізоляція `netns` не блокує UNIX domain sockets, оскільки вони не використовують стек IP.
* Проте сокети абстрактного простору імен (Abstract Domain Sockets, що починаються з байта `\0`) є строго ізольованими у межах кожної структури `struct netns_unix`.

---

## 14. Моніторинг системних подій Netlink через сокети `AF_NETLINK`

Програми моніторингу мережі можуть підписуватися на групи розсилки Netlink (Multicast Groups) — `RTNLGRP_LINK` та `RTNLGRP_IPV4_IFADDR` (у застарілому інтерфейсі `nl_groups` їм відповідають бітові маски `RTMGRP_LINK` і `RTMGRP_IPV4_IFADDR`).

Під час появи чи переміщення пристрою `veth` ядро розсилає повідомлення `RTM_NEWLINK` усім сокетам, підписаним на цю групу **в тому самому мережевому просторі**: розсилка не перетинає межу `netns`, тож демон на хості не побачить подій усередині контейнера. Це дозволяє демонам автоматизації мережі (наприклад, Kubernetes CNI) реагувати на появу нових мережевих пристроїв за мілісекунди без використання циклів опитування (polling).

## 15. Зіставлення CLI-команд `ip netns` із системними викликами

Команди користувацької утиліти `ip netns` з пакета `iproute2` прозоро транслюються у розглянуті системні виклики ядра:

```bash
# 1. Створення простору (unshare(CLONE_NEWNET) + mount(MS_BIND) у /var/run/netns/red)
ip netns add red

# 2. Сканування каталогів /var/run/netns/ для виводу списку активних просторів
ip netns list

# 3. Переміщення veth1 у простір (сокет AF_NETLINK, RTM_NEWLINK з атрибутом IFLA_NET_NS_FD)
ip link set veth1 netns red

# 4. Виконання команди (open(/var/run/netns/red) + setns(fd, CLONE_NEWNET) + execvp())
ip netns exec red ip link set lo up

# 5. Видалення простору (umount(/var/run/netns/red) && unlink(/var/run/netns/red))
ip netns del red
```
