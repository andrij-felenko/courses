Спроба видалити старі архіви у виробничому каталозі за допомогою типової конструкції командного рядка `for file in $(ls /var/backups); do rm -f "/var/backups/$file"; done` миттєво перетворюється на аварію, якщо хоча б один архів містить у назві пробіл або символ переносу рядка, наприклад `db backup 2026-08-25.tar.gz`. Командний інтерпретатор розбиває вивід утиліти `ls` за символами змінної `IFS` (Internal Field Separator: пробіл, табуляція, новий рядок), виконуючи послідовно три незалежні операції `rm -f /var/backups/db`, `rm -f /var/backups/backup` та `rm -f /var/backups/2026-08-25.tar.gz`. Схожа катастрофа виникає при спробі перевірити залишок дискового простору скриптом, який зчитує вивід `df -h` і порівнює значення `10G` з порогом `9.5G`: у текстовому порівнянні Bash рядок `"10G"` виявляється лексикографічно меншим за `"9.5G"`, через що сповіщення про вичерпання диска не надсилається взагалі.

Ці збої є проявом фундаментальної проблеми інтерфейсу командного рядка (Command Line Interface, CLI). Класична філософія Unix проголошує: «Усе є текстом, а програми повинні з'єднуватися через текстові канали». Проте текст, оптимізований для швидкого сприйняття людським оком, кардинально суперечить тексту, необхідному для надійного автоматичного синтаксичного розбору (парсингу). Людський вивід прагне вирівняних стовпчиків, кольорових ANSI-акцентів, скорочених двійкових префіксів та інтерактивних прогрес-барів. Машинний вивід вимагає непорушних структур, строгої типізації, незмінних розділювачів та абсолютної повторюваності незалежно від розміру екрана чи версії операційної системи.

*Дуальність CLI: інтерактивний сеанс оператора з кольорами й форматуванням проти чистого машинного потоку даних у конвеєрі.*

## 1. Анатомія людського виводу CLI: чому зручність для очей вбиває скрипти

Щоб зрозуміти, чому парсинг утиліт людського призначення у скриптах є критичним джерелом багів, необхідно простежити, які саме перетворення виконує утиліта під час підготовки даних для відображення на екрані.

### Втрата розмірності та математичної точності
Прапорці `-h` та `--human-readable` утиліт `df`, `du`, `ls`, `free` та `lsblk` перетворюють 64-бітне ціле число байтів на скорочений текстовий рядок із плаваючою крапкою та суфіксом. Це перетворення несе три небезпечні вади:

1. **Необоротна втрата точності**: Значення розміру розділу `4 509 715 660` байтів виводиться як `4.2G` або `4.3G` залежно від алгоритму округлення. Отримавши такий рядок назад у скрипті, неможливо відновити точну кількість вільних байтів, що унеможливлює точний розрахунок розміщення файлів чи резервування томів.
2. **Розбіжність двійкових та десяткових префіксів**: Різні інструменти використовують різні стандарти одиниць. Стандарт Міжнародної електротехнічної комісії (IEC 60027-2) визначає коефіцієнт 1024 (кібібайти `KiB = 2¹⁰`, мебібайти `MiB = 2²⁰`, гібібайти `GiB = 2³⁰`). Міжнародна система одиниць (SI) оперує степенями десяти (1000: кілобайти `kB = 10³`, мегабайти `MB = 10⁶`, гігабайти `GB = 10⁹`). Якщо одна утиліта повертає `4.2G` (маючи на увазі `4.2 · 1024³`), а скрипт множить її на `10⁹`, виникає системна похибка у 7.37%, яка зростає до 9.95% на терабайтах та 12.59% на петабайтах.
3. **Локалізація десяткових розділювачів**: Залежно від системної змінної `LC_NUMERIC`, числове значення форматується з крапкою (`4.2G` для локалі `en_US.UTF-8`) або з комою (`4,2G` для української `uk_UA.UTF-8` або німецької `de_DE.UTF-8`). Потоковий калькулятор `bc` або мова `awk` розглядають кому як синтаксичну помилку або як розділювач полів, повністю руйнуючи математичну обробку.

### Динамічна зміна ширини стовпців та перенесення рядків
Утиліти, призначені для оператора (наприклад, `ps aux`, `systemctl list-units`, `docker ps`), розраховують ширину колонок на основі довжини найдовшого значення у поточному наборі даних або зчитують ширину термінала через системний виклик `ioctl(STDOUT_FILENO, TIOCGWINSZ, &ws)` чи змінну оточення `COLUMNS`.

Якщо на сервері з'являється процес із довгим іменем користувача (наприклад, `systemd-coredump` замість `root`), утиліта `ps` автоматично розширює першу колонку `USER` на кілька пробілів праворуч. Усі наступні позиції (`PID`, `%CPU`, `%MEM`, `VSZ`, `RSS`) зсуваються на невизначену кількість символів. Сценарій, який використовував фіксоване позиційне зрізання рядків утилітою `cut -c 10-15` або розбиття через `awk '{print $5}'`, починає зчитувати фрагменти сусідніх стовпців замість потрібного поля.

### Засмічення потоку ANSI Escape-послідовностями
Для привернення уваги людини сучасні CLI-утиліти активно використовують кольорове підсвічування статусів, помилок та типів файлів. На фізичному рівні потік виводу поповнюється байтовими послідовностями стандарту ECMA-48 (ANSI escape codes):

```
\033[31mCRITICAL\033[0m  ->  [ESC][31m (Червоний колір) + "CRITICAL" + [ESC][0m (Скидання стилю)
```

Якщо програма-генератор не вимикає генерацію escape-кодів при виводі в канал зв'язку (`pipe`), наступна утиліта в конвеєрі отримує не 8 байтів рядка `"CRITICAL"`, а 17 сирих байтів: `\x1b\x5b\x33\x31\x6d\x43\x52\x49\x54\x49\x43\x41\x4c\x1b\x5b\x30\x6d`. В результаті строге порівняння в умовній конструкції оболонки `if [ "$status" = "CRITICAL" ]` завжди повертає хибність (`false`), а фільтр `grep "^CRITICAL"` не знаходить жодного збігу через наявність невидимого байта `ESC` на початку рядка.

### Псевдографіка та декоративні елементи
Інструменти на кшталт `pstree` або `lsblk` за замовчуванням будують візуальні дерева залежностей за допомогою юнікод-символів псевдографіки (`├─`, `└─`, `│  `). Ці символи стають невіддільною частиною назви пристрою чи процесу при наївному текстовому читанні, що призводить до спроб відкрити неіснуючий файл пристрою `/dev/├─sda1` замість `/dev/sda1`.

## 2. Механізм визначення середовища: isatty() та поведінка ядра

Щоб уникнути ручного налаштування користувачем кожного виклику, якісні системні утиліти реалізують автоматичну адаптацію поведінки: вони визначають, чи виводиться потік безпосередньо у вікно емулятора термінала, чи спрямовується в конвеєр або файл.

Головним системним інструментом для цієї детекції є функція стандартної бібліотеки C `isatty(int fd)`.

![Механізм визначення типу пристрою через системний виклик isatty](/root/sys/sys-unix/machine-readable-output/img/isatty-kernel-flow.svg)
*Шлях системного виклику isatty(): трансляція через ioctl TCGETS у ядрі Linux та розгалуження поведінки для TTY і конвеєрів.*

### Внутрішня механіка isatty() у просторі ядра
У ядрі Linux немає окремого однойменного системного виклику `sys_isatty`. Бібліотека `libc` реалізує функцію `isatty(fd)` як спробу виконати запит отримання параметрів термінала через системний виклик керування пристроями `ioctl`:

:::tabs
```c
/* Системна перевірка дескриптора на належність до термінала мовою C */
#include <unistd.h>
#include <termios.h>
#include <sys/ioctl.h>
#include <errno.h>

int check_descriptor_is_tty(int fd) {
    struct termios t;
    if (ioctl(fd, TCGETS, &t) == 0) {
        return 1; /* Дескриптор вказує на активний TTY */
    }
    if (errno == ENOTTY) {
        return 0; /* Дескриптор вказує на pipe, регулярний файл або сокет */
    }
    return -1; /* Помилка EBADF (недійсний дескриптор) */
}
```
```cpp
// C++20 еквівалент перевірки дескриптора через POSIX ioctl
#include <unistd.h>
#include <termios.h>
#include <sys/ioctl.h>
#include <cerrno>
#include <expected>

enum class DescriptorType {
    Terminal,
    NonTerminalStream,
    Invalid
};

[[nodiscard]] std::expected<DescriptorType, int> check_descriptor_is_tty(int fd) noexcept {
    struct termios t{};
    if (ioctl(fd, TCGETS, &t) == 0) {
        return DescriptorType::Terminal;
    }
    if (errno == ENOTTY) {
        return DescriptorType::NonTerminalStream;
    }
    return std::unexpected(errno);
}
```
:::

Послідовність виконання операції всередині операційної системи розгортається наступним чином:

1. Процес виконує інструкцію асемблера `syscall` із номером `__NR_ioctl`, передаючи номер файлового дескриптора `fd`, константу команди `TCGETS` (`0x5401` на архітектурі x86_64) та покажчик на структуру `struct termios` у пам'яті процесу.
2. Ядро Linux через віртуальну файлову систему (Virtual File System, VFS) знаходить у таблиці дескрипторів процесу структуру `struct file`, асоційовану з цим номером.
3. Ядро звертається до таблиці покажчиків на файлові операції `file->f_op->unlocked_ioctl`.
4. **Випадок TTY**: Якщо дескриптор вказує на файл псевдотермінала (`/dev/pts/*`), обробник `tty_ioctl()` у драйвері терміналів ядра (`drivers/tty/tty_io.c`) розпізнає команду `TCGETS`, копіює параметри термінальної лінії зі структури `tty_struct` у буфер користувача та повертає статус `0` (успіх).
5. **Випадок каналу або файлу**: Якщо дескриптор вказує на анонімний канал `pipefs`, регулярний файл файлової системи `ext4`/`btrfs` або мережевий сокет, у таблиці операцій драйвера відсутній обробник `TCGETS`. VFS повертає код помилки `-ENOTTY` ("Inappropriate ioctl for device").
6. Бібліотека `libc` аналізує результат: якщо `ioctl` повернув `0`, функція `isatty()` повертає `1` (істина); якщо повернено `-ENOTTY`, встановлюється змінна `errno = ENOTTY`, а функція повертає `0` (хибність).

### Наслідки результату isatty() для компонентів програми
На основі перевірки `isatty(STDOUT_FILENO)` професійно спроєктовані утиліти миттєво змінюють чотири критичні підсистеми виконання:

#### 1. ANSI-кольори та стилі
При `isatty() == 1` утиліта дозволяє вивід керуючих послідовностей кольору. При переході в канал (`isatty() == 0`) усі коди кольору повністю вилучаються з виводу, запобігаючи спотворенню даних для наступного фільтра.

#### 2. Інтерактивні пейджери (Less / More)
Такі інструменти, як `git diff`, `systemctl status` або `journalctl`, автоматично перенаправляють свій вивід через пейджер `less`, якщо обсяг тексту перевищує висоту екрана. Проте пейджер запускається **лише за умови**, що одночасно виконуються дві перевірки:
:::tabs
```c
/* Умова безпечного запуску пейджера мовою C */
if (isatty(STDOUT_FILENO) && isatty(STDIN_FILENO)) {
    /* Запуск less через pipe() та fork() */
}
```
```cpp
// Умова безпечного запуску пейджера мовою C++
if (isatty(STDOUT_FILENO) == 1 && isatty(STDIN_FILENO) == 1) {
    // Безпечна ініціалізація дочірнього процесу less
}
```
:::
Якщо вивід перенаправлено у файл `systemctl status nginx > log.txt` або команда виконується всередині скрипту (де `isatty(STDOUT_FILENO) == 0`), запуск `less` блокується, а весь текст негайно виливається у потік без інтерактивного очікування натискання клавіші `q`.

#### 3. Анімація прогрес-барів та переписування рядка
У терміналі інструменти завантаження (`curl`, `wget`, `docker pull`) оновлюють прогрес-бар на місці за допомогою символу повернення каретки `\r` (Carriage Return) або ANSI-команд переміщення курсора вгору `\033[A`.
Якщо таку програму запустити у фоні з перенаправленням у файл журналу `curl url > download.log 2>&1`, символ `\r` записується у файл як звичайний байт `0x0D`. При перегляді такого журналу виникають тисячі сміттєвих рядків. Тому при `isatty() == 0` якісна утиліта або повністю вимикає відображення прогресу, або переходить на дискретне текстове логування з часовими мітками (наприклад, запис рядка кожні 10% прогресу).

#### 4. Режими буферизації стандартної бібліотеки stdio
Стандартна бібліотека C автоматично змінює стратегію буферизації потоку `stdout` залежно від результату детекції термінала:
- **Рядкова буферизація (`_IOLBF`)**: призначається для TTY. Буфер очищується і надсилається ядру системним викликом `write()` після кожного виведеного символу `\n`. Це забезпечує плавний і негайний вивід рядків на екран оператора.
- **Повна блокова буферизація (`_IOFBF`)**: призначається для каналів та файлів. Бібліотека libc виділяє буфер пам'яті розміром 4096 або 8192 байти й викликає `write()` лише тоді, коли буфер заповнюється повністю, або при завершенні процесу (`exit()`). Це мінімізує накладні витрати перемикання контексту ядра при передачі великих обсягів даних у конвеєрі.

Повний технічний опис системних викликів, керуючих структур `termios` та матриці станів дескрипторів наведено у [довіднику API визначення термінала](root:sys-unix/machine-readable-output/api-isatty-and-terminal-detection.md).

## 3. Пастки розділювачів та надійні стандарти машинної взаємодії

Будь-який машинний конвеєр Unix спирається на розбиття вхідного потоку байтів на окремі атомарні елементи (записи, поля, шляхи файлів). Неправильний вибір символу-розділювача є наймасовішою причиною вразливостей та помилок автоматизації.

![Пастки розділювачів у конвеєрі Unix](/root/sys/sys-unix/machine-readable-output/img/whitespace-delimiter-traps.svg)
*Вразливість конвеєрів при розбитті за пробілами та надійність розділювача NUL (\0) при обробці довільних імен файлів.*

### Чому пробіли та переноси рядків руйнують конвеєри
Стандарт POSIX визначає, що коректне ім'я файлу на файловій системі Unix може містити **будь-який довільний 8-бітний байт**, за винятком рівно двох символів:
1. Байта скісної риски `/` (`0x2F`), який є системним розділювачем рівнів дерева каталогів.
2. Нульового байта NUL `\0` (`0x00`), який слугує термінатором рядків у мові C.

Це означає, що ім'я файлу може абсолютно легально містити пробіли, табуляції, керуючі символи повернення каретки `\r` і навіть символи нового рядка `\n`.

Коли традиційний скрипт виконує команду `find . -name "*.log"` або `ls`, кожне ім'я виводиться у новому рядку (`\n`). Якщо ім'я файлу містить символ `\n` (наприклад, `"access\nerror.log"`), інструмент наступної ланки сприйме один фізичний файл як два незалежні файли: `"access"` та `"error.log"`. Спроба обробити такий потік через `xargs` або цикл `while read -r file` призведе до збою, пошкодження даних або несанкціонованого виконання коду.

### Нульовий байт NUL (`\0`) як єдиний непорушний розділювач
Оскільки байт `0x00` фізично заборонено зберігати всередині імен файлів на рівні ядра Linux та VFS, він є єдиним математично гарантованим і безпечним розділювачем у файлових операціях.

Сучасні утиліти підтримують стандартизований набір прапорців для роботи з нуль-термінованими потоками даних:
- `find . -type f -print0`: завершує кожен знайдений шлях байтом `\0` замість `\n`.
- `xargs -0`: зчитує вхідні аргументи, розглядаючи виключно байт `\0` як межу елементів, повністю ігноруючи лапки, пробіли та переноси рядків всередині аргументів.
- `git status -z` та `git diff -z`: формують машинночитані записи файлів репозиторію, розділені нульовим байтом.
- `sort -z` та `uniq -z`: сортують та фільтрують потоки з нульовими розділювачами.
- `read -d '' item`: вбудована команда оболонки Bash, яка зчитує черговий запис із потоку до першого байта `\0`.

### Еталонний безпечний цикл обробки потоку в POSIX Shell:
```bash
# Абсолютно надійна обробка довільних шляхів файлів із будь-якими спецсимволами
find /data/incoming -type f -name "*.dat" -print0 | while IFS= read -r -d '' filepath; do
    printf 'Обробка файлу: %s\n' "$filepath"
    process_data_file "$filepath"
done
```

### Табуляція (TSV) проти розділювачів пробілами
Для передачі структурованих таблиць із кількома полями (наприклад, `PID`, `USER`, `COMMAND`) використання кількох пробілів як розділювача колонок є джерелом помилок: якщо саме значення (наприклад, команда `nginx: worker process`) містить пробіли, утиліта `awk` розбиває це значення на три окремі колонки `$3`, `$4`, `$5`.

Формат значень, розділених табуляцією (**TSV, Tab-Separated Values**), є золотим стандартом машинного плоского тексту в Unix:
- Рівно один символ табуляції `\t` (`0x09`) розділяє сусідні колонки.
- Будь-яка кількість пробілів всередині поля розглядається як частина даних.
- Програма `cut -d$'\t' -f 2` або `awk -F'\t' '{print $2}'` детерміновано видобуває точне значення другого стовпця незалежно від вмісту інших полів.

### Стандартизовані прапорці машинної взаємодії
При розробці системних утиліт та написанні скриптів адміністратори спираються на домовлені стандарти прапорців інтерфейсу командного рядка:

| Прапорець | Призначення | Приклад утиліти | Ефект у машинному конвеєрі |
|---|---|---|---|
| `--no-heading`, `--no-headers`, `-h` | Придушення шапки таблиці | `ps -h`, `lsblk --noheadings` | Виключає необхідність додавання `tail -n +2` або фільтрації заголовків через `grep -v PID`. |
| `-o`, `--output`, `--columns` | Явне задання списку та порядку колонок | `ps -o pid,user,comm=`, `lsblk -o NAME,SIZE,TYPE` | Гарантує, що порядок та склад колонок не залежить від системних конфігурацій за замовчуванням. |
| `-b`, `--bytes`, `-B1`, `--block-size=1` | Сирі байти замість скорочень | `lsblk -b`, `df -B1`, `du -b` | Виводить точні цілі числа без скорочень K/M/G та без похибок округлення. |
| `-r`, `--raw` | Сирий плоский формат без декорацій | `lsblk -r`, `git diff --raw` | Вимикає юнікод-псевдографіку дерев, замінюючи її на плоскі пари ключ-значення. |

## 4. Механізми стабілізації машинного інтерфейсу в інструментах Unix

Для забезпечення надійної автоматизації інженери створили спеціалізовані машинні протоколи всередині провідних системних інструментів.

### 1. Git: Архітектура Plumbing проти Porcelain
Творець Git Лайнус Торвальдс заклав утиліту з двома рівнями команд:
- **Plumbing ("Водогінні труби")**: Низькорівневі бінарні утиліти (`git rev-parse`, `git cat-file`, `git update-ref`, `git write-tree`), які ніколи не змінюють свій формат виводу, не поважають естетичні налаштування користувача з `~/.gitconfig` і призначені для роботи скриптів.
- **Porcelain ("Порцеляна")**: Високорівневі команди для людей (`git status`, `git branch`, `git log`, `git checkout`), вивід яких оптимізований для зручності оператора і може змінюватися з кожним релізом.

Оскільки користувачі часто намагалися викликати `git status` у своїх скриптах, виник прапорець `--porcelain`. Опція `git status --porcelain=v1` та `v2` гарантує:
1. Абсолютну стабільність синтаксису між будь-якими версіями Git.
2. Повне ігнорування кольорів та декорацій конфігурації `color.status`.
3. Фіксовані 2-символьні коди стану файлів (`XY`: `X` — індекс, `Y` — робоче дерево).
4. Підтримку прапорця `-z`, який вимикає екранування не-ASCII символів (запобігає появі вісімкових кодів `\340\265...` у назвах файлів із кирилицею чи пробілами).

### 2. Мережевий стек `iproute2` проти застарілого `net-tools`
Стара утиліта `ifconfig` виводила неструктурований текстовий блок, у якому IP-адреси, маски та лічильники пакетів перемішувалися зі словами `"inet"`, `"netmask"`, `"broadcast"`. Для видобування IP-адреси скрипти будували громіздкі конструкції регулярних виразів:
```bash
# Крихкий наївний парсинг старого ifconfig
ifconfig eth0 | grep 'inet ' | awk '{print $2}' | sed 's/addr://'
```

Сучасна утиліта `ip` з пакету `iproute2` підтримує прапорці `-j` та `-json`, повертаючи суворий валідний документ JSON:
```bash
# Надійне машинне видобування IP-адреси через iproute2 та jq
ip -j address show dev eth0 | jq -r '.[0].addr_info[] | select(.family == "inet") | .local'
```
Цей виклик є на 100% захищеним від зміни кількості пробілів, зміни мови системи чи додавання нових прапорців драйвера інтерфейсу.

### 3. Дискова підсистема: `lsblk -J`
Замість парсингу складної псевдографіки утиліта `lsblk -J -b` повертає повне дерево блокових пристроїв, де розділи диска представлені як вкладений масив `children`, а розміри — як точні 64-бітні числа:
```bash
$ lsblk -J -b -o NAME,SIZE,MOUNTPOINT
{
   "blockdevices": [
      {
         "name": "sda",
         "size": 2000398934016,
         "mountpoint": null,
         "children": [
            {
               "name": "sda1",
               "size": 536870912,
               "mountpoint": "/boot/efi"
            },
            {
               "name": "sda2",
               "size": 1999860498432,
               "mountpoint": "/"
            }
         ]
      }
   ]
}
```

### 4. Хмарні інструменти: Шаблонізація виводу
Утиліти оркестрації та контейнеризації (`docker`, `podman`, `kubectl`) спочатку проєктувалися з урахуванням потреби машинного виклику, реалізуючи прапорці форматування на основі Go-шаблонів та JSONPath:
```bash
# Отримання списку ID контейнерів через табуляційний шаблон
docker ps --format '{{.ID}}\t{{.Names}}\t{{.Status}}'

# Точне видобування IP-адреси Pod у Kubernetes
kubectl get pod web-server -o jsonpath='{.status.podIP}'
```

### 5. Структурований системний журнал: Systemd Journald
Традиційні текстові файли логів (`/var/log/syslog`) записували події в один рядок довільного формату. Системний журнал `systemd-journald` зберігає події як набір строго типізованих бінарних полів (Field-Value pairs): `_PID`, `_UID`, `_SYSTEMD_UNIT`, `MESSAGE`, `PRIORITY`, `_COMM`.

Утиліта `journalctl` надає прапорці для машинного експорту:
- `journalctl -u nginx.service -o json`: формує потік NDJSON (Newline Delimited JSON), де кожен лог-запис є окремим валідним JSON-об'єктом в один рядок. Це дозволяє обробляти гігабайти журналів у потоковому режимі без завантаження всього масиву в оперативну пам'ять.
- `journalctl -o cat`: повертає виключно сирий текст поля `MESSAGE` без часових міток і метаданих, що спрощує передачу сирих корисних даних у пайп.

## 5. Розділення потоків даних: STDOUT проти STDERR

Ще однією критичною помилкою при автоматизації конвеєрів є змішування потоків даних і діагностики за допомогою конструкції `2>&1`:

```bash
# Небезпечне змішування потоків
result=$(my_tool --json 2>&1)
echo "$result" | jq .
```

Якщо утиліта `my_tool` стикається з некритичним попередженням (наприклад, `WARNING: configuration file has loose permissions`) або виводить повідомлення про оновлення версії, текст попередження надсилається у дескриптор `STDERR` (дескриптор 2). Конструкція `2>&1` спрямовує цей текст у початок дескриптора `STDOUT` (дескриптор 1). У результаті парсер `jq` отримує рядок:

```
WARNING: configuration file has loose permissions
{
  "status": "success",
  "data": 42
}
```

Синтаксичний аналізатор негайно падає з помилкою `parse error: Invalid numeric literal at line 1, column 8`, і весь автоматизований процес зупиняється.

### Інженерне правило розділення потоків
- **STDOUT (дескриптор 1)**: Призначений **виключно для корисних даних**, що відповідають заявленому машинного формату (чистий JSON, чистий TSV або двійковий потік). Жоден символ налагодження чи коментаря не має права потрапляти в цей потік.
- **STDERR (дескриптор 2)**: Призначений для **повідомлень про помилки, попереджень, інформаційних логів та інтерактивних прогрес-барів**. Навіть якщо STDOUT перенаправлено у файл або конвеєр, STDERR може залишатися підключеним до термінала оператора для відображення ходу виконання.

## 6. Стандартизація поведінки через змінні середовища

Окрім перевірки дескрипторів та прапорців командного рядка, сучасний CLI-інструмент повинен підпорядковуватися загальноприйнятим стандартам конфігурації оточення:

### 1. Стандарт `NO_COLOR`
Специфікація [no-color.org](https://no-color.org) визначає конвенцію між розробниками утиліт:
- Якщо змінна `NO_COLOR` встановлена в оточенні процесу і її значення **не є порожнім рядком** (`NO_COLOR != ""`), програма повинна повністю вимкнути генерацію ANSI escape-кодів кольору та стилю, навіть якщо вивід здійснюється безпосередньо в активний TTY-термінал.
- Значення змінної не має значення: `NO_COLOR=1`, `NO_COLOR=true`, `NO_COLOR=0` — будь-яке непорожнє значення вимикає колір.

### 2. Специфікація `CLICOLOR` та `CLICOLOR_FORCE`
Стандарт, поширений в екосистемах BSD та macOS:
- `CLICOLOR=0`: забороняє використання кольорів.
- `CLICOLOR=1`: дозволяє кольори за умови `isatty(STDOUT_FILENO) == 1`.
- `CLICOLOR_FORCE=1`: примушує програму виводити кольорові ANSI-коди навіть тоді, коли `STDOUT` перенаправлено у канал (`pipe`) або файл. Ця опція критично необхідна для серверів CI/CD (GitHub Actions, GitLab Runner), які зберігають кольорові журнали збірки для веб-інтерфейсу.
- **Пріоритет**: Специфікація `NO_COLOR` має абсолютний пріоритет над `CLICOLOR_FORCE`.

### 3. Змінна `TERM=dumb`
Якщо змінна `TERM` має значення `dumb`, утиліта має сприймати пристрій виводу як примітивний телетайпний термінал: вимикаються кольори, вимикається очищення екрана та повністю блокується запуск інтерактивних анімацій або прогрес-барів.

## 7. Інженерний синтез: принципи проєктування стабільного CLI

При створенні власної системної утиліти інженер повинен розділяти два різних інтерфейсних контракти:

```
                            ┌───────────────────────────────┐
                            │    Архітектура CLI-контракту  │
                            └───────────────┬───────────────┘
                                            │
               ┌────────────────────────────┴────────────────────────────┐
               ▼                                                         ▼
    ┌─────────────────────────────┐                           ┌─────────────────────────────┐
    │    Людський контракт (UX)   │                           │    Машинний контракт (API)  │
    ├─────────────────────────────┤                           ├─────────────────────────────┤
    │ • Суб'єктивний, візуальний  │                           │ • Суворий системний контракт│
    │ • Може змінюватися в релізах│                           │ • Breaking Changes заборонені│
    │ • Кольори, таблиці, відступи│                           │ • JSON, TSV, сирі байти     │
    │ • Дозволяє пейджери й \r    │                           │ • NUL-розділювачі (-z)      │
    └─────────────────────────────┘                           └─────────────────────────────┘
```

1. **Людський контракт є естетичним і може еволюціонувати**: Вирівнювання таблиць, кольори, підсвічування та інтерактивні підказки призначені виключно для оператора. Їх можна змінювати між мінорними релізами утиліти, покращуючи зручність користування.
2. **Машинний контракт є публічним API**: Формат прапорців `--json`, `--porcelain`, `--raw` або поведінка при `isatty() == 0` є зафіксованим протоколом взаємодії. Будь-яка зміна назви поля у JSON, видалення колонки в TSV або зміна одиниць вимірювання з байтів на кілобайти є порушенням зворотної сумісності (Breaking Change) і вимагає зміни мажорної версії утиліти.

Повна практична реалізація системної утиліти моніторингу з інтеграцією перевірки термінала, змінних `NO_COLOR`, режимів JSON, TSV та NUL-розділювача представлена у [практичному проєкті дуального CLI](root:sys-unix/machine-readable-output/proj-dual-mode-cli.md).
