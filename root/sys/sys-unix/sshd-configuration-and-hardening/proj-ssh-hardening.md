# ⚙️ Практичний проєкт: безпечне налаштування, аудит та захист демона OpenSSH

Захист сервера від несанкціонованого віддаленого доступу вимагає комплексної ешелонованої оборони (Defense in Depth). Розгортання відкритого демона OpenSSH із конфігурацією за замовчуванням наражає інфраструктуру на масове автоматизоване сканування, атаки перебору облікових даних, DoS-напади на вичерпання пулу процесів та експлуатацію застарілих криптографічних алгоритмів.

Цей інженерний проєкт реалізує повний життєвий цикл загартування OpenSSH: від архітектурного розділення ролей серверів і бастіонних шлюзів до автоматизованого аудиту конфігурації за стандартами CIS Benchmark та ANSSI, фільтрації криптографічного стека, дворівневого захисту від брутфорсу (ядро Linux через `nftables` та простір користувача через `fail2ban`), аналізу системних журналів `journalctl` і впровадження валідаційних гейтів у конвеєри CI/CD.

## 1. Архітектурна модель загартування: виробничі сервери та бастіони (Jump Hosts)

У сучасній інфраструктурі сервери поділяються на дві функціональні категорії з принципово різними моделями загроз і матрицями дозволів:
1. **Внутрішні робочі вузли (Application / Database Nodes):** розміщуються в ізольованих приватних підмережах (VPC / VLAN). Вони не повинні мати прямих публічних IP-адрес і зобов'язані приймати SSH-з'єднання виключно з довірених адрес бастіонних хостів або внутрішньої VPN.
2. **Бастіонні шлюзи (Bastion / Jump Hosts):** єдині точки входу в захищений периметр, доступні із зовнішньої мережі. Їхнє завдання — тунелювати трафік автентифікованих інженерів до внутрішніх вузлів, не відкриваючи доступу до локальної операційної системи самого бастіона.

```
                  ЗОВНІШНЯ МЕРЕЖА (ПУБЛІЧНИЙ ІНТЕРНЕТ)
                                    │
                                    │  ssh -J jump.corp.net db.internal
                                    ▼
       ┌─────────────────────────────────────────────────────────┐
       │             БАСТІОННИЙ ШЛЮЗ (JUMP HOST)                 │
       │  • Порт доступу: відкритий назовні (або VPN)            │
       │  • Автентифікація: виключно Ed25519 / FIDO2             │
       │  • Дозволи: AllowTcpForwarding (лише до цільових IP)    │
       │  • Заборонено: Shell (PermitTTY no), X11, AgentForward  │
       │  • Захист L3/L4: nftables rate-limit + fail2ban         │
       └────────────────────────────┬────────────────────────────┘
                                    │  Наскрізний зашифрований тунель (L4)
                                    ▼
       ┌─────────────────────────────────────────────────────────┐
       │             ВНУТРІШНІ СЕРВЕРИ (APP / DB NODES)          │
       │  • Адресація: приватна підмережа (10.0.1.0/24)          │
       │  • Доступ: лише з IP бастіонного шлюзу                  │
       │  • Дозволи: інтерактивна оболонка адміністратора        │
       │  • Заборонено: AllowTcpForwarding, PasswordAuth         │
       │  • Захист: Seccomp-пісочниця, StrictModes, cgroups      │
       └─────────────────────────────────────────────────────────┘
```

### Загроза SSH Agent Forwarding та перевага моделі ProxyJump

Історично для доступу до внутрішніх серверів через бастіон використовували перенаправлення SSH-агента (`ssh -A`). При увімкненні Agent Forwarding клієнтський демон передає свій локальний UNIX-сокет аутентифікації на проміжний сервер. Якщо бастіонний шлюз буде скомпрометовано (наприклад, зловмисник отримає на ньому права `root`), атакуючий може підключитися до відкритого сокета `/tmp/ssh-XXXXXX/agent.XXXX` у файловій системі бастіона і від імені легітимного користувача підписати запити автентифікації до будь-яких внутрішніх систем без знання закритого ключа.

Сучасний інженерний стандарт замінює Agent Forwarding на наскрізне тунелювання через **ProxyJump** (прапорець клієнта `-J` або директива `ProxyJump` у `~/.ssh/config`):

```text
# ~/.ssh/config на машині адміністратора
Host jump.corp.net
    User bastion-admin
    IdentityFile ~/.ssh/id_ed25519_bastion
    Port 22

Host *.internal
    User sysadmin
    IdentityFile ~/.ssh/id_ed25519_internal
    ProxyJump jump.corp.net
```

При використанні `ProxyJump` клієнт спочатку встановлює стандартне SSH-з'єднання з бастіоном і запитує відкриття TCP-каналу до цільового внутрішнього хоста через стандартний виклик `direct-tcpip` (аналог `ssh -W host:port`). Отримавши цей прозорий канал, клієнт ініціює нове незалежне SSH-рукостискання безпосередньо з кінцевим сервером. Бастіон виконує роль простого ретранслятора байтів на транспортному рівні (L4). Він не має доступу до криптографічних ключів користувача, не може прочитати зашифрований трафік і не створює небезпечних UNIX-сокетів у файловій системі.

Тому на рівні конфігурації бастіона директива `AllowAgentForwarding no` є обов'язковою, тоді як `AllowTcpForwarding` обмежується виключно списком дозволених цільових адрес через директиву `PermitOpen`.

## 2. Механіка аудиту через нормалізований дамп `sshd -T` та скрипт перевірки

Прямий синтаксичний розбір текстового файлу `/etc/ssh/sshd_config` сторонніми скриптами або регулярними виразами не дає достовірної картини з таких причин:
* **Compiled-in Defaults:** якщо критичний параметр (наприклад, `PermitRootLogin` чи `StrictModes`) не записаний у текстовому файлі явно, демон застосовує своє вбудоване значення за замовчуванням, яке звичайний текстовий парсер вважатиме відсутнім;
* **Порядок директив `Include`:** файли в каталозі `/etc/ssh/sshd_config.d/*.conf` завантажуються в лексикографічному порядку (за алфавітом);
* **Правило першого входження (First Match Wins):** якщо параметр оголошено декілька разів у різних файлах чи блоках, `sshd` фіксує значення при першому читанні й повністю ігнорує всі наступні рядки з цим ім'ям;
* **Блоки динамічного контексту `Match`:** параметри всередині умовних секцій перевизначають базові значення лише для конкретних користувачів, груп або підмереж.

Єдиним надійним методом аудиту є виклик бінарного файлу `sshd -T`. У цьому режимі демон завантажує всю конфігураційну ієрархію, розкриває макроси, застосовує дефолтні значення і друкує в `stdout` канонічний словник активних налаштувань. Усі ключі нормалізуються до нижнього регістру, а значення приводяться до єдиного формату.

### Детальний розбір реалізації аудитора `main.py`

Архітектура утиліти побудована на модульному порівнянні конфігураційного стану з декларативним безпековим профілем:

1. **Декларативний словник `SECURITY_BASELINE`:**
   Кожне правило описує очікуваний стан директиви, рівень критичності (`CRITICAL`, `HIGH`, `MEDIUM`, `LOW`) та інженерний опис ризику. Словник підтримує три формати очікуваних значень:
   * *Точний рядок:* наприклад `"passwordauthentication": {"expected": "no"}` — вимагає суворої рівності рядкових значень;
   * *Список допустимих варіантів:* наприклад `"permitrootlogin": {"expected": ["no", "prohibit-password"]}` — дозволяє як повне відключення входу root, так і вхід виключно за відкритими ключами;
   * *Предикат-функція (callable):* наприклад `"maxauthtries": {"expected": lambda v: int(v) <= 3, "expected_str": "<= 3"}` — дозволяє гнучко перевіряти числові діапазони та ліміти таймаутів.

2. **Криптографічний фільтр `WEAK_CRYPTO`:**
   Словник містить чорні списки підрядків для категорій `ciphers`, `kexalgorithms` та `macs`. Алгоритм перевірки розбиває значення кожної директиви по комі (`split(",")`) і перевіряє кожен окремий алгоритм на входження заборонених фрагментів (наприклад, алгоритми обміну ключами з хешем `sha1`, блокові шифри в режимі `cbc` або застарілі 64-бітні шифри `3des`, `blowfish`).

3. **Функція збору конфігурації `get_sshd_config()`:**
   Викликає `sshd -T` через безпечний інтерфейс `subprocess.run` із перехопленням потоків `stdout` та `stderr`. Скрипт обробляє два критичні винятки:
   * `FileNotFoundError` — виникає, якщо бінарний файл `sshd` не встановлено в системних шляхах `PATH`;
   * `CalledProcessError` — виникає, якщо конфігураційні файли містять синтаксичні помилки або демон не має прав на читання файлів ключів хоста (у цьому випадку повідомлення `sshd` з `stderr` виводиться безпосередньо в консоль).

4. **Функція аналізу `audit_config()`:**
   Звіряє активну конфігурацію з базовими правилами: фіксує відсутні обов'язкові параметри, зіставляє типи значень і накопичує список виявлених дефектів.

5. **Інтеграція та коди завершення (`main()`):**
   Утиліта форматує виявлені зауваження у вигляді структурованого звіту з тегами критичності. У разі повної відповідності скрипт завершується з кодом `0`, а при виявленні бодай одного порушення повертає код `1`, що дозволяє вбудовувати скрипт у конвеєри автоматичної валідації та системи перевірки комплаєнсу.

### Ізоляція привілеїв: від UsePrivilegeSeparation до Seccomp Sandbox

В історичних версіях OpenSSH директива `UsePrivilegeSeparation sandbox` керувала створенням ізольованого непривілейованого дочірнього процесу під час автентифікації. Починаючи з OpenSSH 7.5, розділення привілеїв (Privilege Separation) стало фундаментальною невід'ємною частиною архітектури сервера, а саму директиву було визнано застарілою й видалено.

Сучасний механізм ізоляції спирається на Seccomp BPF (Secure Computing Mode) у ядрі Linux. Після прийняття вхідного з'єднання дочірній процес скидає привілеї на невільного системного користувача (UID `sshd`), виконує `chroot` у порожній каталог `/run/sshd` і завантажує суворий BPF-фільтр системних викликів. Процесу дозволяється виконувати лише мінімальний набір системних викликів, необхідних для криптографічного обміну та спілкування з батьківським процесом-монітором через `socketpair()`.

Перевірити активацію Seccomp-пісочниці для активних мережевих процесів `sshd` можна безпосередньо через інтерфейс `procfs`:

```bash
# Знайти PID дочірнього непривілейованого процесу sshd
pgrep -u sshd

# Перевірити статус Seccomp для знайденого процесу (повинно бути 2 = seccomp filter)
grep Seccomp /proc/$(pgrep -u sshd | head -n 1)/status
# Очікуваний вивід: Seccomp: 2
#                   Seccomp_filters: 1
```

## 3. Криптографічний гарденінг: фільтрація алгоритмів та захист від нових загроз

Протокол SSH узгоджує криптографічні параметри сесії за чотирма незалежними списками алгоритмів. Зловмисник типу «людина посередині» (MitM) або сторонній спостерігач шукає найслабший підтримуваний алгоритм, щоб здійснити атаку на пониження версії (downgrade attack). Безпековий профіль сервера зобов'язаний явно обмежувати доступні примітиви.

### 1. Алгоритми обміну ключами (`KexAlgorithms`)

Обмін ключами створює спільний симетричний секрет між клієнтом і сервером через відкритий канал зв'язку.

* **Видалені слабкі алгоритми:** `diffie-hellman-group1-sha1` (1024-бітні групи, вразливі до атак класу Logjam), `diffie-hellman-group14-sha1` (використання скомпрометованого хешу SHA-1) та `diffie-hellman-group-exchange-sha1`.
* **Затверджені безпечні алгоритми:**
  * `curve25519-sha256`, `curve25519-sha256@libssh.org` — швидкий і стійкий обмін ключами на еліптичній кривій Curve25519 із хешуванням SHA-256;
  * `diffie-hellman-group16-sha512` (група MODP 4096 біт) та `diffie-hellman-group18-sha512` (група MODP 8192 біти) — надійні класичні схеми Діффі-Хеллмана для клієнтів, що не підтримують еліптичні криві;
  * `sntrup761x25519-sha512@openssh.com` — гібридний постквантовий алгоритм.

#### Постквантовий захист через sntrup761x25519-sha512

Гібридний обмін ключами поєднує класичну криву X25519 з решітковим криптографічним алгоритмом Streamlined NTRU Prime (`sntrup761`). Клієнт і сервер паралельно генерують два спільні секрети: один за класичною схемою, другий — за постквантовою. Результуючий сесійний ключ обчислюється через спільний хеш від обох секретів.

Це гарантує захист від стратегії **Harvest Now, Decrypt Later** (зберігай зараз — розшифровуй потім): навіть якщо зловмисник запише зашифрований мережевий трафік сьогодні, він не зможе розшифрувати його в майбутньому за допомогою квантового комп'ютера алгоритмом Шора, оскільки решіткова складова NTRU Prime залишається математично стійкою до квантового криптоаналізу.

### 2. Симетричні шифри (`Ciphers`) та захист від атаки Terrapin

Симетричний шифр відповідає за конфіденційність переданих даних після завершення обміну ключами.

* **Повна заборона блокових шифрів у режимі CBC (`*-cbc`):** усі варіанти CBC вразливі до атак із оракулом доповнення (Padding Oracle) та атак відновлення відкритого тексту через аналіз часових затримок обробки помилок цілісності.
* **Повна заборона 64-бітних блокових шифрів (`3des-cbc`, `blowfish-cbc`, `cast128-cbc`):** шифри з малим розміром блоку вразливі до колізійних атак на основі парадоксу днів народження (атака Sweet32, CVE-2016-2183), що дозволяє відновити сесійні cookie або фрагменти автентифікаційних даних після передачі приблизно 32 ГБ трафіку в межах однієї сесії.
* **Затверджені автентифіковані шифри (AEAD):**
  * `chacha20-poly1305@openssh.com` — потоковий шифр ChaCha20 у поєднанні з одноразовим автентифікатором Poly1305. Демонструє найвищу швидкодію на системах без апаратного модуля прискорення AES;
  * `aes256-gcm@openssh.com`, `aes128-gcm@openssh.com` — блоковий шифр AES у режимі Галуа/Лічильника (GCM). Забезпечує шифрування та перевірку автентичності за один прохід, досягаючи пропускної здатності в десятки гігабіт на секунду за наявності апаратних інструкцій Intel AES-NI або ARMv8 Cryptography Extensions.
* **Резервні шифри режиму лічильника:** `aes256-ctr`, `aes192-ctr`, `aes128-ctr`.

#### Механізм атаки Terrapin (CVE-2023-48795) та розширення Strict KEX

Наприкінці 2023 року дослідники з Рурського університету в Бохумі опублікували атаку **Terrapin**. Її суть полягає в маніпуляції 32-бітними лічильниками послідовностей пакетів (packet sequence numbers) під час незашифрованого етапу рукостискання SSH.

У протоколі SSH лічильник пакетів є неявним: він інкрементується з кожним відправленим та отриманим пакетом і використовується як додатковий вхідний параметр для перевірки цілісності MAC або автентифікатора Poly1305. Атакуючий у позиції MitM може вставити фіктивне повідомлення (наприклад, `SSH2_MSG_IGNORE`) на відкритому етапі або видалити повідомлення `SSH2_MSG_EXT_INFO`. У шифрах `chacha20-poly1305@openssh.com` та CBC з Encrypt-then-MAC це призводить до зміщення внутрішнього лічильника послідовностей без порушення цілісності перших зашифрованих пакетів. У результаті зловмисник може непомітно видалити пакети розширення протоколу, заблокувавши увімкнення сучасних механізмів захисту від підбору прапорців або змусивши клієнта використовувати менш безпечні алгоритми автентифікації.

Для повної нейтралізації атаки Terrapin у сучасному OpenSSH реалізовано розширення **Strict KEX** (псевдоалгоритми `kex-strict-s-v00@openssh.com` на стороні сервера та `kex-strict-c-v00@openssh.com` на стороні клієнта). При узгодженні Strict KEX:
1. Обидві сторони примусово скидають лічильники послідовностей пакетів у нуль у момент відправлення та отримання повідомлення `SSH2_MSG_NEWKEYS` (перемикання на шифрований канал).
2. Демон негайно розриває з'єднання з фатальною помилкою, якщо під час рукостискання отримано будь-який неочікуваний пакет (наприклад, некоректний `SSH2_MSG_IGNORE` або `SSH2_MSG_DEBUG`).

### 3. Коди автентифікації повідомлень (`MACs`)

Для шифрів у режимі лічильника (`aes256-ctr`) цілісність кожного пакета гарантується алгоритмом MAC.

* **Небезпека традиційного MAC (Encrypt-and-Authenticate):** в оригінальній специфікації SSHv2 MAC обчислювався над відкритим текстом до шифрування, а під час отримання сервер спочатку розшифровував пакет і лише потім перевіряв MAC. Це створювало можливість для атак на підсистему дешифрування.
* **Перевага схеми Encrypt-then-MAC (суфікс `-etm`):** сервер спочатку перевіряє криптографічний хеш над зашифрованим блоком даних. Якщо блок було підроблено або пошкоджено в мережі, пакет негайно відкидається без передачі даних на дешифрування, що повністю захищає криптографічний парсер від пошкодження пам'яті.
* **Затверджений набір MACs:** `hmac-sha2-512-etm@openssh.com`, `hmac-sha2-256-etm@openssh.com`, `umac-128-etm@openssh.com`.

### 4. Алгоритми ключів хоста (`HostKeyAlgorithms`)

Ключі хоста підтверджують автентичність сервера перед клієнтом.
* Застарілі алгоритми `ssh-dss` (DSA 1024 біти) та `ssh-rsa` (RSA з хешем SHA-1) мають бути повністю відключені.
* Рекомендовано видалити файли старих ключів `/etc/ssh/ssh_host_dsa_key*` та `/etc/ssh/ssh_host_ecdsa_key*`, залишивши єдиний чистий ключ Ed25519:

```bash
# Видалення застарілих та потенційно вразливих ключів хоста
sudo rm -f /etc/ssh/ssh_host_dsa_key* /etc/ssh/ssh_host_ecdsa_key* /etc/ssh/ssh_host_rsa_key*

# Генерація нового високостійкого ключа Ed25519
sudo ssh-keygen -t ed25519 -f /etc/ssh/ssh_host_ed25519_key -N "" -C "host-ed25519-$(hostname -s)" < /dev/null

# Генерація резервного RSA-4096 ключа з підписом SHA-2 (для застарілих клієнтів)
sudo ssh-keygen -t rsa -b 4096 -f /etc/ssh/ssh_host_rsa_key -N "" -C "host-rsa-$(hostname -s)" < /dev/null
```

## 4. Еталонні конфігурації: робочі сервери та бастіони Jump Host

Для підтримання стабільності та чистоти системи конфігураційні зміни вносяться виключно через drop-in файли в каталозі `/etc/ssh/sshd_config.d/`. Головний файл `/etc/ssh/sshd_config` повинен містити лише один початковий рядок `Include /etc/ssh/sshd_config.d/*.conf`.

### Еталон 1: Загартована конфігурація робочого сервера (`99-hardening-server.conf`)

Цей профіль призначений для внутрішніх серверів баз даних, мікросервісів та обчислювальних нод:

```text
# /etc/ssh/sshd_config.d/99-hardening-server.conf
# Еталонний безпековий профіль для внутрішніх серверів (CIS Level 2 / ANSSI High)

# 1. Мережеві обмеження та керування сесіями
Port 22
Protocol 2
AddressFamily inet
LoginGraceTime 30
MaxAuthTries 3
MaxSessions 2
MaxStartups 10:30:60

# 2. Сувора автентифікація та права доступу
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitEmptyPasswords no
PermitRootLogin no
StrictModes yes
IgnoreRhosts yes
HostbasedAuthentication no

# 3. PAM-інтеграція (забезпечує ліміти ресурсів cgroups та сесійний аудит)
UsePAM yes

# 4. Обмеження середовища та заборона тунелювання на робочих серверах
X11Forwarding no
AllowTcpForwarding no
AllowAgentForwarding no
PermitUserEnvironment no
DisableForwarding yes
PermitTunnel no

# 5. L7 Keepalive та контроль завислих з'єднань
ClientAliveInterval 300
ClientAliveCountMax 2

# 6. Сучасний криптографічний набір (Post-Quantum Hybrid + AEAD + Strict KEX)
KexAlgorithms sntrup761x25519-sha512@openssh.com,curve25519-sha256,curve25519-sha256@libssh.org,diffie-hellman-group16-sha512,diffie-hellman-group18-sha512
Ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com,aes128-gcm@openssh.com,aes256-ctr,aes192-ctr,aes128-ctr
MACs hmac-sha2-512-etm@openssh.com,hmac-sha2-256-etm@openssh.com,umac-128-etm@openssh.com
HostKeyAlgorithms ssh-ed25519,rsa-sha2-512,rsa-sha2-256

# 7. Журналювання подій автентифікації для систем SIEM/Fail2ban
LogLevel VERBOSE
```

### Еталон 2: Спеціалізована конфігурація бастіонного шлюзу (`99-bastion.conf`)

Конфігурація бастіона відрізняється використанням умовних блоків `Match`. Вона дозволяє прокидання TCP-з'єднань виключно авторизованій інженерній групі до визначеного списку внутрішніх вузлів, повністю блокуючи виділення термінала (PTY) та запуск будь-яких команд на самому бастіоні:

```text
# /etc/ssh/sshd_config.d/99-bastion.conf
# Спеціалізований профіль безпеки для бастіонного шлюзу (Jump Host)

# Глобальні налаштування шлюзу
Port 22
Protocol 2
AddressFamily inet
LoginGraceTime 30
MaxAuthTries 3
MaxStartups 20:30:100
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitEmptyPasswords no
PermitRootLogin no
StrictModes yes
UsePAM yes
LogLevel VERBOSE

# Глобально відключаємо всі небезпечні можливості
X11Forwarding no
AllowAgentForwarding no
PermitUserEnvironment no
PermitTunnel no

# Сучасний криптографічний профіль
KexAlgorithms sntrup761x25519-sha512@openssh.com,curve25519-sha256,curve25519-sha256@libssh.org,diffie-hellman-group16-sha512,diffie-hellman-group18-sha512
Ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com,aes128-gcm@openssh.com
MACs hmac-sha2-512-etm@openssh.com,hmac-sha2-256-etm@openssh.com
HostKeyAlgorithms ssh-ed25519,rsa-sha2-512

# ==============================================================================
# Умовна конфігурація для групи інженерів тунелювання
# ==============================================================================
Match Group jump-users
    # Дозволити лише L4 TCP-прокидання для ProxyJump
    AllowTcpForwarding yes
    
    # Суворий білий список дозволених цільових адрес і портів
    # Забороняє сканування довільних адрес внутрішньої підмережі через шлюз
    PermitOpen 10.0.1.10:22 10.0.1.11:22 10.0.1.20:22 10.0.2.50:5432
    
    # Категорична заборона інтерактивного термінала та запуску оболонок
    PermitTTY no
    X11Forwarding no
    AllowAgentForwarding no
    
    # Повідомлення при спробі прямого відкриття термінала
    ForceCommand /usr/local/bin/bastion-deny-shell.sh
```

Текст допоміжного скрипта-заглушки `/usr/local/bin/bastion-deny-shell.sh`:

```bash
#!/bin/sh
echo "----------------------------------------------------------------------"
echo "УВАГА: Цей сервер працює як ізольований бастіонний шлюз (Jump Host)."
echo "Інтерактивний доступ до термінальної оболонки заборонено політикою безпеки."
echo "Використовуйте цей хост виключно як проміжний вузол через 'ssh -J'."
echo "----------------------------------------------------------------------"
exit 1
```

### Протокол безпечного оновлення без ризику втрати доступу

Будь-яка помилка в синтаксисі або правах доступу до файлів ключів може призвести до ізоляції адміністратора від віддаленого сервера. Процедура оновлення конфігурації виконується за суворим чотирикроковим регламентом:

1. **Синтаксичний тест конфігурації:**
   ```bash
   sudo sshd -t
   ```
   Команда викликає вбудований парсер OpenSSH. Якщо виявлено синтаксичну помилку, утиліта повертає ненульовий код і виводить точний номер рядка дефекту. Перезавантажувати службу в разі помилки суворо заборонено.

2. **Відкриття паралельної резервної сесії:**
   Перед надсиланням керуючого сигналу адміністратор відкриває додаткове вікно термінала з активним підключенням до сервера і залишає його відкритим. Якщо нова конфігурація заблокує нові входи, активна сесія дозволить відновити працездатний конфіг.

3. **Безпечне перезавантаження через сигнал `SIGHUP`:**
   ```bash
   sudo systemctl reload sshd
   ```
   Команда надсилає головному процесу-монітору сигнал `SIGHUP`. Демон перечитує конфігураційні файли виключно для майбутніх вхідних з'єднань. Усі відкриті термінали, сесії користувачів та активні канали продовжують працювати без розриву зв'язку.

4. **Тест нового з'єднання з детальним дебагом:**
   У новому вікні виконується перевірка входу з підвищеною деталізацією:
   ```bash
   ssh -vvv -i ~/.ssh/id_ed25519 admin@server.corp.net
   ```
   У журналі виводу адміністратор перевіряє узгоджений алгоритм KEX (`kex: algorithm: sntrup761x25519-sha512@openssh.com`), симетричний шифр (`server-to-client: chacha20-poly1305@openssh.com`), тип ключа хоста (`host key algorithm: ssh-ed25519`) та успішне проходження автентифікації за ключем. Лише після цього резервну сесію можна закривати.

## 5. Захист від брутфорсу та вичерпання ресурсів: nftables, Fail2ban та аналіз журналів

Захист від несанкціонованого доступу та атак вичерпання ресурсів організовується на двох системних рівнях:

```
[РІВЕНЬ 1: Ядро Linux (Netfilter / nftables)]
Мережевий пакет -> Hook Input -> Dynamic Set Meter (rate > 4/min) -> DROP у ядрі
(Затримка < 1 мкс, 0 викликів fork(), захист від SYN-флуду та DoS-сканування)

                                    │ Пакети в межах ліміту
                                    ▼
[РІВЕНЬ 2: Простір користувача (sshd -> systemd-journald -> fail2ban)]
sshd автентифікація -> невдала спроба -> journald сокет -> Fail2ban (агресивний фільтр) -> nftables ban
(Аналіз семантики: підбір неіснуючих логінів, неавторизовані ключі, бан на 1 годину)
```

### 1. Захист на рівні ядра через динамічні набори `nftables`

Традиційні сканери (Masscan, ZMap) надсилають сотні TCP SYN-пакетів за секунду. Якщо кожне з'єднання досягатиме демона `sshd`, операційна система витрачатиме пам'ять і процесорний час на виклики `fork()`, виділення буферів сокетів та ініціалізацію Seccomp-пісочниць.

Підсистема `nftables` ядра Linux дозволяє фільтрувати зловмисні джерела з нульовою затримкою:

```text
#!/usr/sbin/nft -f
# /etc/nftables/ssh-guard.nft
# Захист порту SSH на рівні ядра через динамічні набори та лічильники

table inet ssh_guard {
    # Динамічний набір заблокованих IP-адрес із таймаутом життя 10 хвилин
    set ssh_denylist {
        type ipv4_addr
        size 65535
        flags timeout
    }

    # Динамічний лічильник частоти нових підключень
    set ssh_meter {
        type ipv4_addr
        size 65535
        flags dynamic, timeout
        timeout 60s
    }

    chain input {
        type filter hook input priority filter; policy accept;

        # 1. Миттєво відкидати пакети від джерел, що вже перебувають у denylist
        ip saddr @ssh_denylist drop

        # 2. Дозволити встановлені та споріднені з'єднання
        ct state established,related accept

        # 3. Обробка нових TCP-з'єднань до порту SSH (22)
        tcp dport 22 ct state new {
            # Якщо з однієї IP-адреси надходить більше 4 нових з'єднань за 60 секунд:
            # - адреса додається в @ssh_denylist на 10 хвилин;
            # - подія записується в кільцевий буфер ядра dmesg;
            # - пакет відкидається.
            update @ssh_meter { ip saddr limit rate over 4/minute } add @ssh_denylist { ip saddr timeout 10m } log prefix "[SSH_KERNEL_DROP]: " drop
            
            # Дозволити легітимні з'єднання в межах ліміту
            accept
        }
    }
}
```

**Переваги фільтрації `nftables` у ядрі:**
* Пакет знищується на рівні мережевого драйвера до передачі в сокетний буфер TCP;
* Жоден дочірній процес `sshd` не створюється, що повністю нейтралізує DoS-атаки на вичерпання таблиці процесів (`PID exhaustion`);
* Заблоковані IP-адреси автоматично вивільняються з пам'яті ядра після завершення 10-хвилинного таймауту без запуску фонових cron-задач.

### 2. Захист на рівні простору користувача: конфігурація `Fail2ban`

Якщо атакуючий розподіляє підключення з великого ботнету (по 1 спробі з тисячі різних IP-адрес, щоб не перевищити ліміт ядра), у дію вступає `Fail2ban`. Він аналізує зміст журналу автентифікації, виявляє спроби підбору імен користувачів або надання неавторизованих ключів і блокує хост на тривалий час.

Конфігурація джейлу `/etc/fail2ban/jail.d/sshd.local`:

```ini
# /etc/fail2ban/jail.d/sshd.local
# Інтеграція Fail2ban із systemd-journald та nftables

[sshd]
enabled = true
port = 22
backend = systemd

# Агресивний режим: відстежує не лише паролі, а й підбір ключів та неіснуючих користувачів
filter = sshd[mode=aggressive]

# Ліміти та часові вікна
maxretry = 3
findtime = 600
bantime = 3600

# Дія блокування: додавання правила в ланцюжок nftables
banaction = nftables-multiport
action = %(action_mwl)s
```

Параметр `backend = systemd` змушує Fail2ban вичитувати бінарний журнал безпосередньо через сокет `systemd-journald`, уникаючи затримок запису на диск традиційного текстового файлу `/var/log/auth.log`.

### 3. Моніторинг та аналіз системних журналів через `journalctl -u ssh`

Системний журнал фіксує детальний контекст кожної спроби підключення. Ключові маркери подій у журналі:

* `Failed publickey for user from 192.0.2.15 port 45212 ssh2` — спроба входу з неавторизованим відкритим ключем (можливий підбір ключів або помилка конфігурації клієнта);
* `Invalid user deployer from 198.51.100.42 port 51110` — спроба входу під обліковим записом, якого не існує в системній базі NSS;
* `Connection closed by authenticating user root 203.0.113.10 port 38990 [preauth]` — скидання з'єднання на етапі автентифікації через таймаут `LoginGraceTime` або блокування директивою `PermitRootLogin`;
* `Authentication refused: bad ownership or modes for file /home/user/.ssh/authorized_keys` — спрацювання перевірки `StrictModes` через некоректні права доступу на файловій системі.

#### Практичні інженерні команди аналізу журналів

```bash
# 1. Топ-10 IP-адрес із найбільшою кількістю невдалих спроб за останні 24 години
sudo journalctl -u ssh --since "24 hours ago" \
  | grep -E "Failed|Invalid user" \
  | awk '{for(i=1;i<=NF;i++) if($i=="from") print $(i+1)}' \
  | sort | uniq -c | sort -nr | head -n 10

# 2. Моніторинг спроб несанкціонованого входу в реальному часі
sudo journalctl -u ssh -f -o short-iso | grep -E "Failed|Invalid|Accepted|refused"

# 3. Перевірка спрацювання захисту StrictModes (пошук помилок прав файлової системи)
sudo journalctl -u ssh -g "Authentication refused" --since "7 days ago"

# 4. Перевірка списку IP-адрес, заблокованих ядром через nftables
sudo nft list set inet ssh_guard ssh_denylist
```

## 6. Інтеграція перевірок у конвеєр автоматизації CI/CD та тест-харнес

У сучасній практиці Infrastructure as Code (IaC) конфігураційні файли OpenSSH генеруються автоматично через Ansible, Terraform або cloud-init. Будь-яка зміна в шаблонах конфігурації повинна проходити обов'язкову валідацію в тестовому середовищі перед розгортанням у робочі кластери.

Для перевірки результуючої поведінки конфігурації для різних контекстів застосовують виклик `sshd -T` із прапорцем емуляції `-C`:

```bash
# 1. Емуляція звичайного підключення внутрішнього користувача:
#    Перевірка заборони паролів та root-доступу
sshd -T -C "user=alice,host=app01.corp,addr=10.0.1.15" | grep "passwordauthentication no"
sshd -T -C "user=root,host=app01.corp,addr=10.0.1.15" | grep "permitrootlogin no"

# 2. Емуляція підключення інженера до бастіонного шлюзу:
#    Перевірка дозволу тунелювання та заборони PTY
sshd -T -C "user=bob,group=jump-users,host=bastion.corp,addr=203.0.113.5" | grep "allowtcpforwarding yes"
sshd -T -C "user=bob,group=jump-users,host=bastion.corp,addr=203.0.113.5" | grep "permittty no"

# 3. Емуляція підключення з невідомої зовнішньої адреси:
#    Перевірка ліміту спроб автентифікації
sshd -T -C "user=unknown,host=unknown,addr=198.51.100.99" | grep "maxauthtries 3"
```

### Автоматизований валідаційний крок у CI/CD Pipeline

Приклад інтеграції аудитора `main.py` та синтаксичних перевірок у крок конвеєра збирання системних образів (GitHub Actions / GitLab CI):

```yaml
# Приклад кроку валідації конфігурації OpenSSH у пайплайні CI/CD
validate_ssh_hardening:
  stage: test
  image: debian:bookworm-slim
  before_script:
    - apt-get update && apt-get install -y openssh-server python3
  script:
    - echo "=== 1. Синтаксична валідація sshd_config ==="
    - cp configs/99-hardening-server.conf /etc/ssh/sshd_config.d/
    - sshd -t

    - echo "=== 2. Запуск скрипта безпекового аудиту ==="
    - python3 proj-ssh-hardening/py/main.py

    - echo "=== 3. Контекстне тестування блоків Match ==="
    - sshd -T -C "user=admin,host=srv.corp,addr=10.0.1.5" | grep "passwordauthentication no"
    - sshd -T -C "user=admin,host=srv.corp,addr=10.0.1.5" | grep "permitrootlogin no"
```

Якщо будь-який із кроків повертає ненульовий код помилки (наприклад, випадково відновлено `PasswordAuthentication yes` або увімкнено слабкий шифр у шаблоні), пайплайн негайно зупиняється. Це унеможливлює вихід у робоче середовище образів із дефектами безпеки.

## 7. Інженерні крайові випадки (Edge Cases) та пастки адміністрування

Під час впровадження суворого профілю загартування виникають типові критичні ситуації:

### 1. Пастка `UsePAM no`
Існує помилкова думка, що для максимальної безпеки директиву `UsePAM` слід вимикати. На практиці `UsePAM no` ламає системну інтеграцію Linux:
* Модуль `pam_systemd.so` не реєструє користувацькі сесії в `systemd-logind`, через що процеси користувача не потрапляють у виділений контрольний слайс `cgroups` (`user-1000.slice`) і не очищаються після завершення з'єднання;
* Модуль `pam_limits.so` не застосовує ліміти системних ресурсів (`/etc/security/limits.conf`), через що користувач може вичерпати системні дескриптори або ліміти відкритих файлів (`nofile`);
* Вимикається сесійний аудит у підсистемі ядра `auditd`.

*Правильне рішення:* залишати `UsePAM yes`, але блокувати парольні модулі через `PasswordAuthentication no` та `KbdInteractiveAuthentication no`.

### 2. Пастка прав файлової системи при `StrictModes yes`
Якщо домашній каталог користувача `/home/username` або каталог `~/.ssh` має права запису для групи чи інших користувачів (`chmod g+w` або права `0775`/`0777`), `sshd` відмовляється відкривати файл `authorized_keys`. Сервер повертає клієнту помилку `Permission denied (publickey)`, а в журнал записує повідомлення:
`Authentication refused: bad ownership or modes for directory /home/username`.

*Правильне рішення:* суворо виставляти права:
```bash
sudo chown root:root /home
sudo chmod 755 /home
sudo chown username:username /home/username
sudo chmod 750 /home/username
sudo chmod 700 /home/username/.ssh
sudo chmod 600 /home/username/.ssh/authorized_keys
```

### 3. Пастка налаштування `ChrootDirectory` для SFTP
При налаштуванні ізольованого SFTP-каталогу (`ChrootDirectory /var/sftp/%u`) системний виклик ядра `chroot()` завершується аварійно з помилкою `fatal: bad ownership or modes for chroot directory`, якщо хоча б один каталог у повному ланцюжку шляху (від `/` до точки монтування) доступний для запису будь-кому, крім `root:root`.

*Правильне рішення:* усі каталоги ланцюжка chroot повинні належати виключно `root:root` з маскою `0755`. Користувацький каталог для завантаження файлів створюється підкаталогом нижчого рівня:
```bash
sudo chown root:root /var/sftp /var/sftp/client1
sudo chmod 755 /var/sftp /var/sftp/client1
sudo mkdir -p /var/sftp/client1/data
sudo chown client1:client1 /var/sftp/client1/data
sudo chmod 700 /var/sftp/client1/data
```
