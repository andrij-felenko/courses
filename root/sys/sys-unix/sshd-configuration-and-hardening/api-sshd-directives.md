# 📋 Довідник директив конфігурації sshd_config

Файл конфігурації демона OpenSSH (`/etc/ssh/sshd_config`) та модульні файли каталогу `/etc/ssh/sshd_config.d/*.conf` визначають правила роботи сервера від моменту відкриття мережевого сокета до передачі керування сесійній оболонці користувача. Цей довідник містить технічну специфікацію директив, їхні значення за замовчуванням, контекст застосування, токени підстановки, криптографічні правила, параметри ізоляції підсистем SFTP, налаштування тунелювання та інтерфейс командного рядка для валідації й симуляції конфігурації.

---

## 1. Загальні правила парсингу та структура файлу

### Механіка обробки директив
* **Правило першого входження (First Match Wins):** якщо директива повторюється в глобальній області видимості або в кількох підключених файлах, демон `sshd` фіксує значення з першого прочитаного рядка. Усі наступні визначення цього ж параметра в глобальному контексті мовчки ігноруються. Винятком є умовні блоки `Match`, які обчислюються динамічно під час підключення клієнта.
* **Регістронезалежність:** назви директив нечутливі до регістру символів (`PasswordAuthentication`, `passwordauthentication` та `PASSWORDAUTHENTICATION` еквівалентні). Аргументи директив (шляхи файлової системи, команди, імена користувачів та груп, списки криптографічних алгоритмів) є чутливими до регістру.
* **Синтаксис рядка:** аргументи відокремлюються від назви директиви пробілом або знаком табуляції. Рядки, що починаються з символу `#`, та порожні рядки ігноруються як коментарі.
* **Формати часу:** числові часові інтервали задаються в секундах або з суфіксами: `s` (секунди), `m` (хвилини), `h` (години), `d` (дні), `w` (тижні). Наприклад, `LoginGraceTime 1m 30s` або `LoginGraceTime 90`.
* **Формати розміру даних:** розміри в байтах або з суфіксами: `K` або `k` (кілобайти), `M` або `m` (мегабайти), `G` або `g` (гігабайти), `T` або `t` (терабайти). Наприклад, `RekeyLimit 1G 1h`.

### Модульне підключення: директива `Include`
```text
Include /etc/ssh/sshd_config.d/*.conf
```
* **Синтаксис:** `Include шлях_або_маска`
* **Контекст:** Глобальний (поза блоками `Match`)
* **Специфікація:** завантажує додаткові конфігураційні файли. Якщо шлях відносний, він обчислюється від каталогу `/etc/ssh`. Файли, що відповідають масці (globbing pattern), обробляються у суворому лексикографічному порядку (за таблицею ASCII). Оскільки діє правило першого входження, параметри у файлі `01-hardening.conf` перекривають параметри файлу `99-custom.conf` та основного `sshd_config`.

### Токени підстановки (специфікатори формату)
У директивах, які приймають шляхи до файлів, каталоги або команди (`AuthorizedKeysFile`, `AuthorizedPrincipalsFile`, `ChrootDirectory`, `ForceCommand`, `Subsystem` тощо), підтримуються змінні підстановки:

| Токен | Опис значення |
|---|---|
| `%u` | Ім'я користувача, що проходить автентифікацію. |
| `%U` | Числовий ідентифікатор користувача (UID) цільового облікового запису. |
| `%h` | Домашній каталог цільового користувача (визначений у `/etc/passwd`). |
| `%k` | Відкритий ключ хоста або клієнта (залежно від контексту). |
| `%f` | Криптографічний відбиток (fingerprint) ключа клієнта. |
| `%H` | Ім'я або адреса хоста, отримані через резолвінг. |
| `%i` | Ідентифікатор ключа (Key ID) або серійний номер SSH-сертифіката. |
| `%K` | Відкритий ключ Центру Сертифікації (CA), що підписав сертифікат. |
| `%T` | Локальна дата й час виконання у форматі ISO 8601. |
| `%%` | Екранування символу відсотка (`%`). |

## 2. Мережеві директиви, сокети та керування ресурсами

```
Клієнт (TCP SYN)
       │
       ▼
┌─────────────────────────────────────────────────────────────┐
│ Port / ListenAddress / AddressFamily                        │
│ Створення сокетів bind(), фільтрація сімейства адрес (AF)   │
└─────────────────────────────────────────────────────────────┘
       │
       ▼
┌─────────────────────────────────────────────────────────────┐
│ MaxStartups (start:rate:full) / PerSourceMaxStartups        │
│ Контроль пулу неавтентифікованих з'єднань (PrivSep монітор) │
└─────────────────────────────────────────────────────────────┘
       │
       ▼
┌─────────────────────────────────────────────────────────────┐
│ LoginGraceTime / MaxAuthTries / TCPKeepAlive / ClientAlive  │
│ Тайм-аути, перевірка каналу L4/L7, ліміти спроб введення    │
└─────────────────────────────────────────────────────────────┘
```

### `Port`
* **Синтаксис:** `Port номер_порту`
* **Значення за замовчуванням:** `22`
* **Контекст:** Глобальний
* **Специфікація:** номер TCP-порту, на якому демон відкриває слухаючий сокет. Дозволяється багаторазове визначення директиви у файлі конфігурації: у такому разі `sshd` створює окремий сокет для кожного зазначеного порту. Значення має бути в діапазоні від 1 до 65535. Для портів менше ніж 1024 процес монітора повинен мати привілей `CAP_NET_BIND_SERVICE` або стартувати з правами UID 0 (`root`).

### `ListenAddress`
* **Синтаксис:** `ListenAddress host|IPv4|IPv6 [port port]` або `ListenAddress [host]:port`
* **Значення за замовчуванням:** `0.0.0.0` (усі доступні IPv4-інтерфейси) та `::` (усі IPv6-інтерфейси)
* **Контекст:** Глобальний
* **Специфікація:** задає локальну IP-адресу мережевого інтерфейсу, до якого прив'язується сокет `sshd`. Підтримується багаторазове визначення. Якщо порт не вказано явно, використовується значення директиви `Port`. Для IPv6-адрес із явно визначеним портом обов'язковими є квадратні дужки: `ListenAddress [2001:db8::1]:2222`. Якщо вказано ім'я хоста замість IP-адреси, демон виконує системний DNS-резолвінг під час ініціалізації; у разі помилки резолвінгу запуск служби завершується аварійно.

### `AddressFamily`
* **Синтаксис:** `AddressFamily any | inet | inet6`
* **Значення за замовчуванням:** `any`
* **Контекст:** Глобальний
* **Специфікація:** обмежує сімейство адрес під час створення сокетів.
  * `any` — відкриває сокети як для IPv4 (`AF_INET`), так і для IPv6 (`AF_INET6`);
  * `inet` — примусово використовує виключно IPv4-стек;
  * `inet6` — примусово використовує виключно IPv6-стек.

### `TCPKeepAlive`
* **Синтаксис:** `TCPKeepAlive yes | no`
* **Значення за замовчуванням:** `yes`
* **Контекст:** Глобальний
* **Специфікація:** вмикає прапорець `SO_KEEPALIVE` на рівні системного TCP-сокета ядра (L4). Ядро періодично надсилає контрольні TCP ACK-пакети віддаленій стороні. Якщо зв'язок обірвався або віддалений хост перезавантажився без надсилання RST/FIN-пакетів, сокет закривається автоматично.
* **Відмінність від `ClientAlive*`:** `TCPKeepAlive` працює на транспортному рівні без криптографічного захисту (пакети не шифруються). Проміжні маршрутизатори з NAT або stateful firewall можуть підробляти або скидати непідписані TCP ACK-пакети. Для надійного контролю на рівні додатку застосовують директиви `ClientAliveInterval` та `ClientAliveCountMax`.

### `ClientAliveInterval` та `ClientAliveCountMax`
* **Синтаксис:** `ClientAliveInterval секунди`, `ClientAliveCountMax кількість`
* **Значення за замовчуванням:** `ClientAliveInterval 0` (вимкнено), `ClientAliveCountMax 3`
* **Контекст:** Глобальний
* **Специфікація:** механізм контролю доступності клієнта на рівні протоколу SSH (L7 Keepalive).
  * `ClientAliveInterval`: інтервал у секундах, після якого сервер надсилає зашифрований контрольний запит протоколу (`keepalive@openssh.com`) через існуючий сесійний тунель, якщо від клієнта не надходило корисних даних.
  * `ClientAliveCountMax`: максимальна кількість послідовних контрольних запитів без відповіді від клієнта.
  * **Формула тайм-ауту:** якщо клієнт не відповідає протягом `ClientAliveInterval × ClientAliveCountMax` секунд, демон розриває TCP-з'єднання, звільняє дескриптори, псевдотермінали (PTY) та завершує дочірні сесійні процеси.

### `MaxStartups`
* **Синтаксис:** `MaxStartups start:rate:full` або `MaxStartups число`
* **Значення за замовчуванням:** `10:30:100`
* **Контекст:** Глобальний
* **Специфікація:** обмежує кількість одночасних неавтентифікованих підключень (з'єднань, що перебувають на стадії криптографічного рукостискання, вибору KEX або введення пароля). Захищає непривілейовані процеси Privilege Separation від вичерпання системних дескрипторів та DoS-атак.
  * `start` (10) — кількість одночасних з'єднань, до якої всі запити приймаються без обмежень;
  * `rate` (30%) — відсоток випадкового скидання нових підключень (шляхом `close()` сокета) при досягненні порогу `start`. Ймовірність відхилення лінійно зростає від 0% при `start` до 100% при `full`;
  * `full` (100) — верхня абсолютна межа активних неавтентифікованих сесій. При досягненні значення `full` 100% усіх нових підключень миттєво відкидаються сервером.

### `PerSourceMaxStartups` та `PerSourceNetBlockSize`
* **Синтаксис:** `PerSourceMaxStartups число | none`, `PerSourceNetBlockSize IPv4:IPv6`
* **Значення за замовчуванням:** `PerSourceMaxStartups none`, `PerSourceNetBlockSize 32:128`
* **Контекст:** Глобальний
* **Специфікація:** обмежує кількість одночасних неавтентифікованих з'єднань, ініційованих з однієї вихідної IP-адреси або підмережі.
  * `PerSourceMaxStartups`: максимальна кількість з'єднань на стадії автентифікації від одного джерела. Запобігає вичерпанню загального пулу `MaxStartups` єдиним атакуючим хостом.
  * `PerSourceNetBlockSize`: визначає маску підмережі CIDR для групування адрес джерел (за замовчуванням `32` для IPv4 — поодинокий хост, `128` для IPv6).

### `MaxSessions`
* **Синтаксис:** `MaxSessions число`
* **Значення за замовчуванням:** `10`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** визначає максимальну кількість відкритих сесійних мультиплексованих каналів (інтерактивних оболонок, виконання окремих команд або підсистем SFTP), дозволених у межах одного встановленого TCP-з'єднання. Обмеження стає критичним при використанні клієнтського мультиплексування (`ssh -M` або `ControlMaster`), блокуючи спроби виснаження пам'яті процесу-монітора через відкриття сотень паралельних сесій через єдине автентифіковане підключення.

### `LoginGraceTime`
* **Синтаксис:** `LoginGraceTime час`
* **Значення за замовчуванням:** `120` (2 хвилини)
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** граничний час, який надається клієнту для успішного завершення процедури автентифікації після відкриття TCP-з'єднання. Якщо клієнт не встиг автентифікуватися за цей час, процес-монітор примусово закриває сесію через надсилання сигналу `SIGALRM` дочірньому невільному процесу. Значення `0` повністю вимикає тайм-аут (не рекомендовано, оскільки відкриває можливість утримання відкритих сокетів назавжди).

### `MaxAuthTries`
* **Синтаксис:** `MaxAuthTries число`
* **Значення за замовчуванням:** `6`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** максимальна кількість невдалих спроб автентифікації на одну TCP-сесію. Після досягнення половини цього значення (`MaxAuthTries / 2`) демон фіксує кожну наступну невдалу спробу в журналі `auth.log` / `syslog`. При перевищенні ліміту з'єднання негайно розривається з кодом помилки `SSH2_DISCONNECT_BY_APPLICATION`. Це запобігає масовому автоматизованому опитуванню всіх ключів, завантажених у клієнтський `ssh-agent`.

## 3. Автентифікація, авторизація та сертифікати

```
Клієнт надсилає облікові дані
       │
       ▼
┌─────────────────────────────────────────────────────────────┐
│ RevokedKeys: перевірка публічного ключа або KRL-списку     │
│ (якщо знайдено у списку — негайне відхилення до криптографії)│
└─────────────────────────────────────────────────────────────┘
       │
       ▼
┌─────────────────────────────────────────────────────────────┐
│ StrictModes: перевірка прав файлової системи                │
│ (~/.ssh, authorized_keys, %h не мають бути world/group-write)│
└─────────────────────────────────────────────────────────────┘
       │
       ▼
┌─────────────────────────────────────────────────────────────┐
│ TrustedUserCAKeys / AuthorizedPrincipalsFile                │
│ Верифікація цифрового підпису CA та зіставлення principals  │
└─────────────────────────────────────────────────────────────┘
       │
       ▼
┌─────────────────────────────────────────────────────────────┐
│ AuthenticationMethods (MFA конвеєр: publickey,keyboard-...) │
│ Послідовна перевірка обов'язкових ланцюжків методів         │
└─────────────────────────────────────────────────────────────┘
```

### `PermitRootLogin`
* **Синтаксис:** `PermitRootLogin yes | prohibit-password | without-password | forced-commands-only | no`
* **Значення за замовчуванням:** `prohibit-password`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** визначає умови та обмеження входу для облікового запису суперкористувача (`root`, UID 0).
  * `yes` — дозволяє вхід `root` з використанням будь-якого дозволеного методу автентифікації (включно з паролями).
  * `prohibit-password` (синонім `without-password`) — повністю забороняє парольну та інтерактивну клавіатурну автентифікацію для `root`. Дозволяє вхід за відкритими ключами, сертифікатами OpenSSH, GSSAPI або hostbased-методами.
  * `forced-commands-only` — дозволяє вхід за відкритими ключами виключно за умови, що для відповідного ключа у файлі `authorized_keys` або сертифікаті явно прописано опцію `command="команда"`. Довільний запуск команд або інтерактивної оболонки блокується.
  * `no` — повністю забороняє будь-який прямий вхід користувача `root` через протокол SSH незалежно від методу.

### `PubkeyAuthentication`
* **Синтаксис:** `PubkeyAuthentication yes | no | unbound | host-bound`
* **Значення за замовчуванням:** `yes`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** вмикає або блокує автентифікацію за асиметричними відкритими ключами та апаратними токенами FIDO2 (`sk-ssh-ed25519@openssh.com`, `sk-ecdsa-sha2-nistp256@openssh.com`). Варіант `host-bound` активує перевірку розширення OpenSSH для захисту від перехоплення та повторного використання підписів на сторонніх хостах.

### `PubkeyAcceptedAlgorithms`
* **Синтаксис:** `PubkeyAcceptedAlgorithms [+| -| ^]список`
* **Значення за замовчуванням:** за замовчуванням OpenSSH включає Ed25519, ECDSA, RSA-SHA2 (rsa-sha2-512, rsa-sha2-256) та FIDO2-ключі. Алгоритм `ssh-rsa` (SHA-1) типово вимкнено.
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** перелік алгоритмів цифрового підпису відкритих ключів користувача, які сервер приймає під час запиту `SSH_MSG_USERAUTH_REQUEST`. Дозволяє примусово заблокувати застарілі та слабкі формати ключів на рівні сервера.

### `PasswordAuthentication`
* **Синтаксис:** `PasswordAuthentication yes | no`
* **Значення за замовчуванням:** `yes`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** керує перевіркою паролів користувача за протоколом SSH. При встановленні в `no` демон не пропонує метод `password` у списку доступних автентифікаторів клієнту, блокуючи прямий перебір паролів.

### `KbdInteractiveAuthentication`
* **Синтаксис:** `KbdInteractiveAuthentication yes | no`
* **Значення за замовчуванням:** `yes` (у застарілих версіях використовувався аліас `ChallengeResponseAuthentication`)
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** дозволяє використання діалогової клавіатурно-інтерактивної автентифікації згідно з RFC 4256. Механізм дозволяє серверу надсилати довільну кількість текстових підказок і зчитувати відповіді клієнта. Застосовується для модулів PAM, що реалізують одноразові паролі (TOTP, Google Authenticator), апаратні виклики або діалог зміни пароля.
* **Взаємодія з паролями:** якщо `PasswordAuthentication no`, але `KbdInteractiveAuthentication yes`, PAM-модуль `pam_unix.so` може все одно запитати стандартний системний пароль. Для повної заборони парольного входу обидві директиви мають бути переведені в стан `no`.

### `AuthenticationMethods`
* **Синтаксис:** `AuthenticationMethods список1 [список2 ...]`
* **Значення за замовчуванням:** `any` (достатньо успішного проходження одного дозволеного методу)
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** задає обов'язкові ланцюжки автентифікації для реалізації багатофакторної перевірки (MFA).
  * **Кома (послідовність):** методи, розділені комою, вимагають обов'язкового послідовного успішного виконання кожного з них. Наприклад, `publickey,keyboard-interactive:pam` зобов'язує користувача спершу надати цифровий підпис ключа, а потім пройти одноразовий код TOTP через PAM.
  * **Пробіл (альтернатива):** списки методів, розділені пробілом, надають альтернативні шляхи проходження перевірки. Достатньо виконати будь-який один повний ланцюжок.
  * **Приклад MFA з альтернативою:**
    ```text
    AuthenticationMethods publickey,keyboard-interactive:pam publickey,password
    ```

### `PermitEmptyPasswords`
* **Синтаксис:** `PermitEmptyPasswords yes | no`
* **Значення за замовчуванням:** `no`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** блокує автентифікацію для облікових записів, у яких парольний хеш у файлі `/etc/shadow` відсутній або дорівнює порожньому рядку.

### `StrictModes`
* **Синтаксис:** `StrictModes yes | no`
* **Значення за замовчуванням:** `yes`
* **Контекст:** Глобальний
* **Специфікація:** перевіряє права доступу та власників файлової системи перед читанням ключів у каталозі `~/.ssh` та файлі `authorized_keys`. Демон відмовляється приймати ключ, якщо:
  1. Каталог користувача (`%h`), каталог `~/.ssh` або файл ключів доступні для запису групі чи стороннім користувачам (`chmod g+w, o+w`);
  2. Власник цих шляхів не збігається з UID користувача, що підключається, або з UID 0 (`root`).
  Це захищає обліковий запис від підкидання сторонніх відкритих ключів іншими локальними процесами.

### `AuthorizedKeysFile`
* **Синтаксис:** `AuthorizedKeysFile шлях1 [шлях2 ...]`
* **Значення за замовчуванням:** `.ssh/authorized_keys .ssh/authorized_keys2`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** визначає шляхи до файлів, що містять відкриті ключі, дозволені для автентифікації користувача. Відносні шляхи обчислюються від домашнього каталогу (`%h`). Якщо задано абсолютний шлях (наприклад, `/etc/ssh/authorized_keys/%u`), керування ключами виноситься з-під контролю самого користувача до системного адміністратора, що запобігає закріпленню зловмисника у системі після компрометації домашнього каталогу.

### `AuthorizedPrincipalsFile`
* **Синтаксис:** `AuthorizedPrincipalsFile шлях`
* **Значення за замовчуванням:** `none`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** визначає шлях до файлу, який містить дозволені імена суб'єктів (principals) при використанні сертифікатів OpenSSH (OpenSSH Certificates). Демон перевіряє, чи містить підписаний сертифікат клієнта хоча б одне ім'я principal, записане у цьому файлі (по одному на рядок). Підтримує макроси `%u` та `%h` (наприклад, `/etc/ssh/principals/%u` або `.ssh/authorized_principals`).

### `TrustedUserCAKeys`
* **Синтаксис:** `TrustedUserCAKeys шлях`
* **Значення за замовчуванням:** `none`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** абсолютний шлях до файлу, що містить відкриті ключі Центрів Сертифікації (CA), яким сервер беззастережно довіряє для підпису сертифікатів клієнтів. Якщо директива активна, клієнт може пройти автентифікацію за сертифікатом, підписаним відповідним CA, без потреби копіювати відкритий ключ клієнта у файл `authorized_keys`. Сервер перевіряє цифровий підпис CA, термін дії сертифіката (validity interval) та відповідність дозволених principals.

### `RevokedKeys`
* **Синтаксис:** `RevokedKeys шлях`
* **Значення за замовчуванням:** `none`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** шлях до відкритого текстового файлу відкритих ключів або скомпільованого бінарного списку відкликаних ключів KRL (Key Revocation List, згенерованого через `ssh-keygen -k`). Якщо відкритий ключ або сертифікат клієнта міститься у цьому списку, `sshd` негайно відхиляє спробу входу до початку обчислення цифрових підписів або перевірки паролів.

### `HostbasedAuthentication` та `IgnoreRhosts`
* **Синтаксис:** `HostbasedAuthentication yes | no`, `IgnoreRhosts yes | no`
* **Значення за замовчуванням:** `HostbasedAuthentication no`, `IgnoreRhosts yes`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** керує автентифікацією на основі довіри до ключів хоста клієнта (`/etc/ssh/ssh_known_hosts` та `.rhosts` / `.shosts`). У загартованих конфігураціях `HostbasedAuthentication` залишається вимкненою (`no`), а `IgnoreRhosts` активною (`yes`), оскільки автентифікація за IP-адресою та ім'ям хоста є вразливою до спуфінгу та отруєння DNS.

## 4. Сесійне середовище, аудит, журналювання та запуск процесів

### `UsePAM`
* **Синтаксис:** `UsePAM yes | no`
* **Значення за замовчуванням:** `no` (у дистрибутивах Linux скомпільовано з підтримкою PAM і типово виставлено в `yes`)
* **Контекст:** Глобальний
* **Специфікація:** підключає підсистему Pluggable Authentication Modules (PAM) через конфігурацію `/etc/pam.d/sshd`.
  * При значенні `yes` демон виконує повний життєвий цикл PAM:
    1. `pam_authenticate()` — перевірка облікових даних;
    2. `pam_acct_mgmt()` — перевірка блокування облікового запису, терміну дії пароля, обмежень часу та файлу `nologin`;
    3. `pam_open_session()` — ініціалізація системних обмежень ресурсів (`pam_limits.so`), реєстрація сеансу в cgroups та `systemd-logind` (`pam_systemd.so`), моніторинг аудиту;
    4. `pam_close_session()` — коректне вивільнення ресурсів при завершенні.
  * Якщо `UsePAM no`, демон не викликає PAM-сесії: системні ліміти `limits.conf` не застосовуються, а змінні оточення PAM ігноруються.

### `LogLevel`
* **Синтаксис:** `LogLevel QUIET | FATAL | ERROR | INFO | VERBOSE | DEBUG | DEBUG1 | DEBUG2 | DEBUG3`
* **Значення за замовчуванням:** `INFO`
* **Контекст:** Глобальний
* **Специфікація:** визначає рівень деталізації системного журналу подій демона `sshd`.
  * `INFO` — фіксує успішні підключення, розриви сесій та критичні помилки автентифікації;
  * `VERBOSE` — обов'язковий вибір для аудиту безпеки: додатково логує криптографічні відбитки (fingerprint) та типи ключів клієнтів, використані під час успішного або невдалого входу;
  * `DEBUG` / `DEBUG1`..`DEBUG3` — призначені виключно для тимчасового відлагодження. На робочих серверах заборонені, оскільки можуть призводити до витоку конфіденційної інформації у системні логи.

### `SyslogFacility`
* **Синтаксис:** `SyslogFacility DAEMON | USER | AUTH | AUTHPRIV | LOCAL0 | LOCAL1 | LOCAL2 | LOCAL3 | LOCAL4 | LOCAL5 | LOCAL6 | LOCAL7`
* **Значення за замовчуванням:** `AUTH`
* **Контекст:** Глобальний
* **Специфікація:** встановлює категорію (facility code) системного журналу `syslog`, за якою демон маркує всі власні повідомлення. Використання категорій на кшталт `AUTHPRIV` або `LOCAL0` дозволяє демонам `rsyslog` або `journald` направляти журнал доступу в окремий захищений файл (наприклад, `/var/log/auth.log` або віддалений SIEM-колектор).

### `PermitUserEnvironment`
* **Синтаксис:** `PermitUserEnvironment yes | no | маска_змінних`
* **Значення за замовчуванням:** `no`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** дозволяє чи забороняє демону зчитувати та застосовувати змінні середовища, визначені клієнтом у файлі `~/.ssh/environment` або через опцію `environment="VAR=val"` у `authorized_keys`.
* **Загроза безпеці:** значення `yes` створює критичний вектор локального підвищення привілеїв: зловмисник може встановити змінні `LD_PRELOAD`, `LD_LIBRARY_PATH` або специфічні змінні інтерпретатора, які будуть виконані під час виклику сторонніх утиліт або `sudo`. У сучасних версіях OpenSSH підтримується безпечна маска (наприклад, `PermitUserEnvironment GIT_*,LC_*`), що суворо обмежує простір імен дозволених змінних.

### `AcceptEnv`
* **Синтаксис:** `AcceptEnv шаблон1 [шаблон2 ...]`
* **Значення за замовчуванням:** не встановлено (клієнтські змінні не приймаються)
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** список назв змінних середовища або масок із символами `*` та `?`, які клієнт передає серверу під час відкриття сесії через запити протоколу `SSH_MSG_CHANNEL_REQUEST` типу `env`. Зазвичай використовується для передачі налаштувань локалізації: `AcceptEnv LANG LC_*`. Усі змінні, що не відповідають шаблонам, мовчки відкидаються сервером.

### `SetEnv`
* **Синтаксис:** `SetEnv ЗМІННА=значення [ЗМІННА2=значення2 ...]`
* **Значення за замовчуванням:** не встановлено
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** примусово встановлює одну або кілька статичних змінних середовища для сесійного процесу користувача. Застосовується в блоках `Match` для маркування середовища (наприклад, `SetEnv DEPLOY_ENV=production`) або обмеження поведінки скриптів без втручання в системні профілі оболонки.

### `PermitTTY`
* **Синтаксис:** `PermitTTY yes | no`
* **Значення за замовчуванням:** `yes`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** визначає, чи дозволено виділення псевдотермінала (PTY) для сесії клієнта. Значення `no` блокує інтерактивний вхід у командну оболонку (запити `pty-req`), залишаючи можливість лише для тунелювання портів, передачі файлів через SFTP або виконання одиночних автоматизованих команд.

### `Banner` та `PrintMotd`
* **Синтаксис:** `Banner шлях | none`, `PrintMotd yes | no`, `PrintLastLog yes | no`
* **Значення за замовчуванням:** `Banner none`, `PrintMotd yes`, `PrintLastLog yes`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:**
  * `Banner`: абсолютний шлях до текстового файлу, вміст якого надсилається клієнту перед початком процедури автентифікації. Застосовується для юридичних попереджень про заборону несанкціонованого доступу.
  * `PrintMotd`: чи повинен демон самостійно друкувати вміст файлу `/etc/motd` після успішного входу (якщо використовується PAM з модулем `pam_motd.so`, цю директиву часто вимикають для уникнення подвійного виводу).
  * `PrintLastLog`: керує виводом дати й IP-адреси попереднього входу користувача в систему.

## 5. Криптографічний стек та керування списками алгоритмів

### Механіка модифікаторів списків (`+`, `-`, `^`)
Директиви `KexAlgorithms`, `Ciphers`, `MACs`, `HostKeyAlgorithms`, `CASignatureAlgorithms` та `PubkeyAcceptedAlgorithms` підтримують префіксний синтаксис для керування списками без необхідності повного ручного перелічування всіх значень:

* **Без префікса (`алгоритм1,алгоритм2`):** повна заміна системного списку OpenSSH за замовчуванням на вказаний перелік;
* **Префікс `+` (`+алгоритм1,алгоритм2`):** додавання зазначених алгоритмів у кінець списку за замовчуванням;
* **Префікс `-` (`-алгоритм1,алгоритм2`):** видалення зазначених алгоритмів зі списку за замовчуванням (підтримуються маски, наприклад `-*sha1*`, `-*cbc*`);
* **Префікс `^` (`^алгоритм1,алгоритм2`):** вставка зазначених алгоритмів на початок списку за замовчуванням (надання їм найвищого пріоритету під час узгодження).

```
Синтаксис префіксів OpenSSH:

Базовий список за замовчуванням: [AlgA, AlgB, AlgC]

1. Без префікса: "AlgX,AlgY"  --> [AlgX, AlgY]
2. Префікс '+':   "+AlgX"      --> [AlgA, AlgB, AlgC, AlgX]
3. Префікс '-':   "-AlgB"      --> [AlgA, AlgC]
4. Префікс '^':   "^AlgX"      --> [AlgX, AlgA, AlgB, AlgC]
```

### `KexAlgorithms`
* **Синтаксис:** `KexAlgorithms [+| -| ^]список`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** визначає алгоритми обміну ключами (Key Exchange). У процесі KEX сторони узгоджують сесійні симетричні ключі шифрування.
  * **Рекомендовані безпечні алгоритми:**
    * `sntrup761x25519-sha512@openssh.com` — постквантовий гібридний алгоритм (Streamlined NTRU Prime + X25519);
    * `mlkem768x25519-sha256` — постквантовий гібрид стандарту NIST ML-KEM (Kyber-768);
    * `curve25519-sha256`, `curve25519-sha256@libssh.org` — класичний протокол ECDH на кривій Montgomery 25519;
    * `diffie-hellman-group16-sha512`, `diffie-hellman-group18-sha512` — класичний Diffie-Hellman з розміром груп 4096 та 8192 біти.
  * **Заборонені застарілі алгоритми:** `diffie-hellman-group1-sha1` (1024 біти, SHA-1), `diffie-hellman-group14-sha1`, `diffie-hellman-group-exchange-sha1`.
  * **Захист Strict KEX:** для запобігання атаці Terrapin (CVE-2023-48795) сучасні версії OpenSSH автоматично додають протокольний псевдоалгоритм `kex-strict-s-v00@openssh.com`.

### `Ciphers`
* **Синтаксис:** `Ciphers [+| -| ^]список`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** визначає симетричні шифри для захисту конфіденційності та цілісності корисного навантаження сесії.
  * **Рекомендовані автентифіковані шифри (AEAD):**
    * `chacha20-poly1305@openssh.com` — потоковий шифр ChaCha20 з автентифікатором Poly1305 (висока швидкість на процесорах без апаратного AES);
    * `aes256-gcm@openssh.com`, `aes128-gcm@openssh.com` — блоковий шифр AES у режимі Galois/Counter Mode (максимальна продуктивність при наявності інструкцій AES-NI).
  * **Дозволені шифри в режимі лічильника (CTR):** `aes256-ctr`, `aes192-ctr`, `aes128-ctr`.
  * **Суворо заборонені:** усі варіанти в режимі зчеплення блоків CBC (`aes256-cbc`, `3des-cbc`), оскільки вони вразливі до атак типу Padding Oracle, а також потокові шифри RC4 (`arcfour`).

### `MACs`
* **Синтаксис:** `MACs [+| -| ^]список`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** коди автентифікації повідомлень (Message Authentication Codes), які використовуються для контролю цілісності при застосуванні шифрів у режимі CTR.
  * **Парадигма Encrypt-then-MAC (суфікс `-etm`):** обов'язковий вибір для загартованих конфігурацій (`hmac-sha2-512-etm@openssh.com`, `hmac-sha2-256-etm@openssh.com`, `umac-128-etm@openssh.com`). Обчислення MAC виконується над зашифрованими даними, що усуває можливість експлуатації помилок у модулі дешифрування.
  * **Заборонені:** алгоритми на основі MD5 (`hmac-md5*`) та SHA-1 (`hmac-sha1*`).
  * *Примітка:* при узгодженні AEAD-шифрів (`chacha20-poly1305`, `aes-gcm`) перевірка MAC вбудована безпосередньо в шифр, тому налаштування директиви `MACs` для такого з'єднання не застосовуються.

### `HostKeyAlgorithms`
* **Синтаксис:** `HostKeyAlgorithms [+| -| ^]список`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** перелік алгоритмів цифрового підпису, які сервер пропонує клієнту для підтвердження автентичності хоста (host authentication).
  * **Рекомендовані:** `ssh-ed25519`, `ssh-ed25519-cert-01@openssh.com`, `rsa-sha2-512`, `rsa-sha2-256`, `rsa-sha2-512-cert-01@openssh.com`, `rsa-sha2-256-cert-01@openssh.com`.
  * **Заборонені:** застарілий підпис RSA з хешем SHA-1 (`ssh-rsa`), а також алгоритм DSA (`ssh-dss`).

### `CASignatureAlgorithms`
* **Синтаксис:** `CASignatureAlgorithms [+| -| ^]список`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** перелік алгоритмів цифрового підпису, які дозволено використовувати Центрам Сертифікації (CA) для генерації сертифікатів користувачів. Блокує прийняття сертифікатів, підписаних застарілими алгоритмами хешування (наприклад, `ssh-rsa` на базі SHA-1). Рекомендований набір: `ssh-ed25519,rsa-sha2-512,rsa-sha2-256`.

### `FingerprintHash`
* **Синтаксис:** `FingerprintHash sha256 | md5`
* **Значення за замовчуванням:** `sha256`
* **Контекст:** Глобальний
* **Специфікація:** алгоритм хешування, що використовується для генерації та відображення криптографічних відбитків (fingerprints) ключів у системних журналах `syslog` та діагностичному виводі. Значення `md5` є застарілим через колізійну нестійкість.

### `RekeyLimit`
* **Синтаксис:** `RekeyLimit [default | розмір] [час]`
* **Значення за замовчуванням:** `default none`
  * Для блокових шифрів та шифрів з довжиною блоку 128 біт (AES) внутрішній поріг `default` становить 1 Гб (або 4 Гб для деяких AEAD), а часовий інтервал не обмежений (`none`).
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** задає максимальний обсяг переданих даних та часовий інтервал, після вичерпання яких `sshd` ініціює обов'язкову процедуру повторного узгодження ключів (session re-keying).
* **Механіка роботи:**
  1. Демон відстежує лічильники переданих та отриманих байтів і таймер від моменту останнього обміну ключами;
  2. При досягненні будь-якого з порогів (розміру даних або часу) `sshd` надсилає повідомлення протоколу `SSH2_MSG_KEXINIT` безпосередньо всередині активного зашифрованого тунелю;
  3. Сторони повторно виконують узгодження KEX (Diffie-Hellman або ECDH), обчислюють новий спільний секрет і генерують свіжі симетричні сесійні ключі шифрування та вектори ініціалізації (IV);
  4. Сеанс користувача, відкриті TCP-тунелі та передача файлів не перериваються і не вимагають повторного введення паролів чи підписів.
* **Безпекова необхідність:**
  * **Захист від виснаження простору IV/лічильників:** у режимах CTR або GCM повторне використання одного й того самого вектора ініціалізації з однаковим ключем призводить до катастрофічної втрати конфіденційності (можливість відновлення відкритого тексту).
  * **Обмеження обсягу криптоаналізу:** обмежує кількість зашифрованого матеріалу, доступного зловмиснику на єдиній парі сесійних ключів.
* **Приклади конфігурації:**
  ```text
  # Примусовий rekeying кожні 512 Мб або щогодини
  RekeyLimit 512M 1h

  # Стандартний ліміт за обсягом даних, але з ротацією кожні 30 хвилин
  RekeyLimit default 30m

  # Примусовий rekeying кожні 2 Гб без часового ліміту
  RekeyLimit 2G none
  ```

## 6. Підсистема передачі файлів SFTP та директива `Subsystem`

```
Клієнт (SSH_MSG_CHANNEL_REQUEST "subsystem" sftp)
                       │
                       ▼
      ┌─────────────────────────────────┐
      │ Директива Subsystem sftp        │
      └────────────────┬────────────────┘
                       │
       ┌───────────────┴───────────────┐
       ▼                               ▼
┌─────────────────────────────┐ ┌─────────────────────────────┐
│ Зовнішній sftp-server       │ │ internal-sftp (in-process)  │
│ • fork() + execve()         │ │ • Виконується в пам'яті     │
│ • Потребує бінарників, libc │ │   самого процесу sshd       │
│ • Не працює в порожньому    │ │ • Ідеально для ізоляції     │
│   chroot без бібліотек      │ │   ChrootDirectory           │
└─────────────────────────────┘ └─────────────────────────────┘
```

### Директива `Subsystem`
* **Синтаксис:** `Subsystem ім'я_підсистеми шлях_до_бінарника [аргументи]` або `Subsystem sftp internal-sftp [прапорці]`
* **Значення за замовчуванням:** `none` (у більшості дистрибутивів за замовчуванням встановлено `Subsystem sftp /usr/lib/openssh/sftp-server` або `Subsystem sftp internal-sftp`)
* **Контекст:** Глобальний
* **Специфікація:** реєструє іменовану підсистему протоколу SSH. Коли клієнт надсилає канальний запит типу `subsystem` з відповідним іменем (найчастіше `sftp`), демон запускає зазначену команду та зв'язує її стандартні потоки введення/виведення з SSH-каналом.

### Архітектурне порівняння: `internal-sftp` проти `sftp-server`
1. **Зовнішній бінарний файл (`sftp-server`):**
   * Запускається через системні виклики `fork()` та `execve()`;
   * Вимагає наявності виконуваного файлу `/usr/lib/openssh/sftp-server` (або `/usr/libexec/openssh/sftp-server`), динамічного завантажувача `ld-linux.so`, системної бібліотеки `libc.so` та файлів середовища;
   * Якщо на сесію накладено обмеження `ChrootDirectory`, демон не зможе запустити зовнішній бінарник без попереднього монтування або копіювання всіх бібліотек усередину ізольованого каталогу (помилка `execve failed: No such file or directory`).
2. **Вбудована підсистема (`internal-sftp`):**
   * Реалізована безпосередньо всередині кодової бази `sshd` як функція;
   * Обробка SFTP-протоколу виконується в пам'яті самого сесійного процесу без виклику `execve()`;
   * Не потребує жодних сторонніх бінарних файлів, інтерпретаторів оболонки чи каталогів `/dev` та `/lib` усередині chroot-середовища.

### Специфікація прапорців та аргументів `internal-sftp` / `sftp-server`

Директива `Subsystem sftp internal-sftp [прапорці]` або використання `ForceCommand internal-sftp [прапорці]` підтримує такі параметри командного рядка:

| Прапорець | Опис контракту | Приклад використання |
|---|---|---|
| `-u umask` | Встановлює вісімкову маску прав створення файлів і каталогів (`umask`). Якщо прапорець не задано, використовується стандартна маска користувача з `/etc/login.defs` або PAM (зазвичай `0022`). | `-u 0027` (каталоги `0750`, файли `0640`) |
| `-d start_dir` | Визначає початковий робочий каталог після автентифікації. Підтримує макроси `%h` (домашній каталог) та `%u` (користувач). Якщо шлях відносний, він обчислюється відносно домашнього каталогу або кореня chroot. | `-d /incoming` або `-d %h` |
| `-l log_level` | Задає рівень деталізації журналювання підсистеми (`QUIET`, `FATAL`, `ERROR`, `INFO`, `VERBOSE`, `DEBUG`, `DEBUG1`, `DEBUG2`, `DEBUG3`). | `-p requests` | Білий список (allowed list): дозволяє виключно зазначені запити SFTP-протоколу, блокуючи всі інші. | `-p open,read,close,stat` |

| `-h` | Виводить довідку щодо доступних прапорців підсистеми та завершує роботу. | `-h` |

## 7. Контроль доступу, ізоляція, тунелювання та умовні блоки `Match`

### Алгоритм фільтрації: `AllowUsers`, `DenyUsers`, `AllowGroups`, `DenyGroups`
Директиви приймають список імен або шаблонів із символами `*` та `?`, а також підтримують зіставлення хостів через символ `@` (наприклад, `admin@10.0.0.0/8`, `deployer@*.internal`).

**Порядок обчислення при спробі підключення:**
1. `DenyUsers` — якщо користувач відповідає списку, доступ **негайно відхиляється**;
2. `AllowUsers` — якщо директива визначена і користувач **не входить** до списку, доступ **відхиляється**;
3. `DenyGroups` — якщо первинна або додаткова група користувача є в списку, доступ **відхиляється**;
4. `AllowGroups` — якщо директива визначена і **жодна** з груп користувача не входить до списку, доступ **відхиляється**;
5. Якщо всі перевірки пройдено успішно, клієнт допускається до етапу автентифікації.

### Умовні блоки `Match`
Блок `Match` дозволяє перевизначати параметри конфігурації для певних користувачів, груп, хостів або мережевих діапазонів.

* **Синтаксис:** `Match [!]критерій1 патерн1 [!]критерій2 патерн2 ...`
* **Критерії зіставлення:**
  * `User` — ім'я користувача (список через кому або шаблони);
  * `Group` — системна група користувача (звіряється за `/etc/group` та додатковими GID);
  * `Host` — ім'я хоста клієнта (отримане через зворотний DNS-пошук);
  * `Address` — IP-адреса або безкласова підмережа CIDR клієнта (наприклад, `192.168.1.0/24`, `10.10.0.0/16`, `2001:db8::/64`);
  * `LocalAddress` — локальна IP-адреса інтерфейсу сервера, на яку надійшло з'єднання;
  * `LocalPort` — номер локального порту сервера;
  * `All` — застосовується для всіх з'єднань (використовується для відкриття загального сектора наприкінці конфігурації).
* **Оператор заперечення `!`:** інвертує результат перевірки критерію (наприклад, `Match Group developers !User lead-dev`).
* **Межі блоку:** блок `Match` діє від рядка оголошення до наступного рядка `Match` або до кінця файлу (`EOF`).

```text
# Приклад ізольованого блоку для групи SFTP-користувачів
Match Group sftponly
    PasswordAuthentication yes
    ChrootDirectory /var/sftp/%u
    ForceCommand internal-sftp -u 0027 -l VERBOSE -d /incoming
    AllowTcpForwarding no
    AllowStreamLocalForwarding no
    GatewayPorts no
    PermitTunnel no
    X11Forwarding no
    AllowAgentForwarding no
    PermitTTY no
```

### Директиви, дозволені в блоках `Match`
Усередині секцій `Match` дозволено використовувати:
`AllowAgentForwarding`, `AllowStreamLocalForwarding`, `AllowTcpForwarding`, `AuthenticationMethods`, `AuthorizedKeysFile`, `AuthorizedPrincipalsFile`, `Banner`, `ChrootDirectory`, `ClientAliveCountMax`, `ClientAliveInterval`, `Ciphers`, `DenyGroups`, `DenyUsers`, `ForceCommand`, `GatewayPorts`, `GSSAPIAuthentication`, `HostbasedAuthentication`, `HostbasedAcceptedAlgorithms`, `HostKeyAlgorithms`, `KbdInteractiveAuthentication`, `KexAlgorithms`, `LogLevel`, `MACs`, `MaxAuthTries`, `MaxSessions`, `PasswordAuthentication`, `PermitEmptyPasswords`, `PermitListen`, `PermitOpen`, `PermitRootLogin`, `PermitTTY`, `PermitTunnel`, `PermitUserEnvironment`, `PubkeyAcceptedAlgorithms`, `PubkeyAuthentication`, `RekeyLimit`, `RevokedKeys`, `RDomain`, `SetEnv`, `StreamLocalBindMask`, `StreamLocalBindUnlink`, `TrustedUserCAKeys`, `X11DisplayOffset`, `X11Forwarding`, `X11UseLocalhost`.

### Ізоляція файлової системи та обмеження сесій

#### `ChrootDirectory`
* **Синтаксис:** `ChrootDirectory шлях`
* **Значення за замовчуванням:** `none`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** виконує системний виклик `chroot()` після успішної автентифікації, змінюючи кореневий каталог файлової системи для сесійного процесу. Підтримує макроси `%h` (домашній каталог), `%u` (користувач), `%U` (UID).
* **Вимоги безпеки файлової системи (Security Invariant):**
  * **Права власності:** кожен каталог в абсолютному шляху — від системного кореня `/` до цільового каталогу включно — зобов'язаний належати суперкористувачу `root:root` (UID 0: GID 0);
  * **Маска прав доступу:** жоден із проміжних або кінцевих каталогів у шляху не повинен мати прав на запис для групи чи інших користувачів (`chmod 0755` або `chmod 0750`). Маски `g+w` або `o+w` суворо заборонені.
* **Механізм перевірки та поведінка при помилці:**
  1. Перед викликом `chroot()` демон виконує `stat()` для кожного компонента шляху;
  2. Якщо `(st_mode & 022) != 0` або `st_uid != 0`, `sshd` негайно перериває сесію;
  3. У системний журнал записується критична помилка:
     ```text
     fatal: bad ownership or modes for chroot directory "/var/sftp/user1"
     ```
  4. Клієнт отримує код відключення `SSH2_DISCONNECT_BY_APPLICATION` із закриттям сокета.
* **Організація запису для користувачів:** оскільки сам chroot-корінь належить `root` і доступний звичайному користувачу лише для читання, для завантаження файлів усередині створюють підкаталог із правами користувача:
  ```bash
  # Каталог chroot-ізоляції:
  sudo chown root:root /var/sftp/john
  sudo chmod 0755 /var/sftp/john

  # Підкаталог для завантаження файлів:
  sudo mkdir /var/sftp/john/uploads
  sudo chown john:sftponly /var/sftp/john/uploads
  sudo chmod 0750 /var/sftp/john/uploads
  ```
* **Вимоги для інтерактивної оболонки проти SFTP:**
  * Якщо користувачу надається доступ до shell, усередині chroot-каталогу мають бути створені пристрої `/dev/null`, `/dev/zero`, `/dev/ptmx`, каталог `/bin` з оболонкою та всі динамічні бібліотеки `libc.so`, `ld-linux.so`;
  * Якщо використовується `ForceCommand internal-sftp`, жодних пристроїв та файлів створювати не потрібно — сервер працює в повністю ізольованому каталозі.

#### `ForceCommand`
* **Синтаксис:** `ForceCommand команда`
* **Значення за замовчуванням:** `none`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** ігнорує будь-яку команду, передану клієнтом за протоколом SSH, або запит на запуск інтерактивної оболонки, і примусово виконує вказану бінарну програму або команду.
  * Початкова команда, надіслана клієнтом, зберігається в змінній середовища `SSH_ORIGINAL_COMMAND`.
  * Значення `internal-sftp` активує вбудовану підсистему SFTP безпосередньо всередині процесу `sshd`, що дозволяє організувати безпечний chroot-доступ для передачі файлів.

#### `DisableForwarding`
* **Синтаксис:** `DisableForwarding yes | no`
* **Значення за замовчуванням:** `no`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** єдиний глобальний вимикач усіх типів тунелювання та перенаправлення. Значення `yes` еквівалентне одночасному встановленню `AllowTcpForwarding no`, `AllowAgentForwarding no`, `X11Forwarding no`, `AllowStreamLocalForwarding no` та `PermitTunnel no`.

### Директиви тунелювання, прокидання портів та сокетів

#### `PermitTunnel`
* **Синтаксис:** `PermitTunnel yes | point-to-point | ethernet | no`
* **Значення за замовчуванням:** `no`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** керує створенням віртуальних мережевих інтерфейсів рівня L3 (IP) або L2 (Ethernet) через тунельний механізм OpenSSH (опція клієнта `ssh -w any:any хост`).
  * `point-to-point` — дозволяє створення тунельних інтерфейсів типу `tun` (L3, передача чистих IP-пакетів без Ethernet-кадрів);
  * `ethernet` — дозволяє створення інтерфейсів типу `tap` (L2, передача Ethernet-кадрів із заголовками канального рівня, підтримка bridging);
  * `yes` — дозволяє як `point-to-point`, так і `ethernet` тунелі;
  * `no` — повністю забороняє створення віртуальних мережевих тунелів TUN/TAP.
* **Вимоги до привілеїв:** створення пристроїв `tunX`/`tapX` у системі вимагає доступу до пристрою ядра `/dev/net/tun` та привілею `CAP_NET_ADMIN` (або запуску під UID 0) як на клієнтському, так і на серверному боці.

#### `GatewayPorts`
* **Синтаксис:** `GatewayPorts yes | no | clientspecified`
* **Значення за замовчуванням:** `no`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** визначає, до яких мережевих адрес прив'язується сокет віддаленого прокидання портів (`ssh -R`).
  * `no` — демон примусово прив'язує прокинутий порт виключно до адреси локального інтерфейсу зворотного зв'язку `127.0.0.1` (або `::1`). Доступ до прокинутого порту мають лише локальні процеси самого сервера;
  * `yes` — демон примусово прив'язує порт до універсальної wildcard-адреси `0.0.0.0` (або `::`). Прокинутий порт стає відкритим для з'єднань з усіх вузлів зовнішньої мережі;
  * `clientspecified` — демон дозволяє клієнту самостійно вказати бажану адресу прив'язки у запиті `-R [адреса:]порт:хост:порт`. Якщо клієнт не вказав адресу явно, порт прив'язується до `127.0.0.1`.

#### `AllowTcpForwarding`
* **Синтаксис:** `AllowTcpForwarding yes | no | local | remote`
* **Значення за замовчуванням:** `yes`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** визначає можливість довільного прокидання TCP-портів:
  * `yes` — дозволено як локальне (`-L`), так і віддалене (`-R`) та динамічне SOCKS-проксі (`-D`) тунелювання;
  * `local` — дозволено лише клієнтське локальне прокидання портів (`-L`) та socks (`-D`);
  * `remote` — дозволено лише зворотне прокидання портів (`-R`);
  * `no` — повністю забороняє будь-яке TCP-тунелювання через сервер.

#### `AllowStreamLocalForwarding`
* **Синтаксис:** `AllowStreamLocalForwarding yes | all | no | local | remote`
* **Значення за замовчуванням:** `yes`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** керує перенаправленням сокетів домену UNIX (UNIX domain stream sockets) через розширення протоколу `streamlocal-forward@openssh.com`.
  * `yes` (синонім `all`) — дозволяє як локальне (`ssh -L /шлях/локальний.sock:/шлях/віддалений.sock`), так і віддалене (`ssh -R /шлях/віддалений.sock:/шлях/локальний.sock`) прокидання UNIX-сокетів;
  * `local` — дозволяє лише клієнтське перенаправлення сокетів;
  * `remote` — дозволяє лише віддалене зворотне перенаправлення сокетів;
  * `no` — повністю блокує прокидання сокетів домену UNIX.
* **Сценарії застосування:** безпечне прокидання сокета віддаленого демона Docker (`/var/run/docker.sock`) або локального агента GnuPG (`~/.gnupg/S.gpg-agent`) без відкриття відкритих TCP-портів у мережі.

#### `StreamLocalBindMask` та `StreamLocalBindUnlink`
* **Синтаксис:** `StreamLocalBindMask вісімкова_маска`, `StreamLocalBindUnlink yes | no`
* **Значення за замовчуванням:** `StreamLocalBindMask 0177`, `StreamLocalBindUnlink no`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:**
  * `StreamLocalBindMask`: встановлює маску прав доступу (`umask`), яка застосовується під час створення файлу UNIX-сокета на сервері при віддаленому прокиданні. За замовчуванням `0177` (права `0600` — доступ лише для власника сокета).
  * `StreamLocalBindUnlink`: якщо встановлено в `yes`, демон перед створенням нового сокета перевіряє наявність існуючого файлу сокета з таким самим шляхом і автоматично видаляє його (`unlink()`). При значенні `no` спроба прив'язки до вже існуючого сокета завершується помилкою `bind: Address already in use`.

#### `PermitOpen` та `PermitListen`
* **Синтаксис:** `PermitOpen host:port [host:port ...] | any | none`, `PermitListen [host:]port [[host:]port ...] | any | none`
* **Значення за замовчуванням:** `PermitOpen any`, `PermitListen any`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:**
  * `PermitOpen`: білий список цільових хостів та портів, куди дозволено відкривати локальні та динамічні TCP-тунелі (`-L`, `-D`, а також переходи `ssh -W` / `ProxyJump`). Будь-який запит на підключення до непереліченого хоста відхиляється.
  * `PermitListen`: білий список адрес та портів на стороні сервера, які клієнту дозволено відкривати для віддаленого зворотного прокидання (`-R`).

#### `AllowAgentForwarding`
* **Синтаксис:** `AllowAgentForwarding yes | no`
* **Значення за замовчуванням:** `yes`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** блокує або дозволяє прокидання сокета локального агента ключів `ssh-agent` на сервер (`ssh -A`). Значення `no` є обов'язковим для виробничих серверів та бастіонів: при прокиданні агента будь-який користувач з правами `root` на цільовому сервері отримує прямий доступ до Unix-сокета агента в каталозі `/tmp` і може підписувати запити до інших машин від імені клієнта, поки з'єднання залишається відкритим.

#### `X11Forwarding`, `X11DisplayOffset`, `X11UseLocalhost`
* **Синтаксис:** `X11Forwarding yes | no`, `X11DisplayOffset число`, `X11UseLocalhost yes | no`
* **Значення за замовчуванням:** `X11Forwarding no` (у деяких дистрибутивах `yes`), `X11DisplayOffset 10`, `X11UseLocalhost yes`
* **Контекст:** Глобальний та в блоках `Match`
* **Специфікація:** керує створенням зашифрованих каналів для графічних додатків X Window System.
  * `X11Forwarding no` захищає робочу станцію клієнта від перехоплення буфера обміну, введення з клавіатури та зняття знімків екрана скомпрометованим сервером.
  * `X11UseLocalhost yes` прив'язує графічний X11-дисплей (`DISPLAY=localhost:10.0`) виключно до інтерфейсу зворотного зв'язку сервера, блокуючи прямий доступ до графічного сокета іншим машинам мережі.

## 8. Режими перевірки, діагностики та симуляції підключень (CLI Contract)

Бінарний файл `sshd` надає набір прапорців для валідації синтаксису конфігурації, інспекції результуючих налаштувань та емуляції поведінки блоків `Match`.

```
                  Режими діагностики sshd CLI:
                  
         sshd -t                sshd -T                sshd -T -C "..."
            │                      │                          │
            ▼                      ▼                          ▼
┌───────────────────────┐ ┌─────────────────────────┐ ┌────────────────────────┐
│  Синтаксична перевірка│ │   Дамп розрахованої     │ │  Симуляція з'єднання   │
│  дерева файлів, прав  │ │   конфігурації          │ │  для обчислення        │
│  доступу та ключів    │ │   (нормалізований стан) │ │  умовних блоків Match  │
└───────────────────────┘ └─────────────────────────┘ └────────────────────────┘
```

### Валідація синтаксису: `sshd -t`
```bash
sudo sshd -t
sudo sshd -t -f /etc/ssh/sshd_config.d/01-hardening.conf
```
* **Призначення:** перевіряє коректність синтаксису головного конфігураційного файлу та всіх підключених файлів `Include`, валідує наявність обов'язкових ключів хоста та перевіряє права доступу до них.
* **Коди виходу:**
  * `0` — конфігурація синтаксично бездоганна (вивід порожній);
  * `>0` (помилка) — повідомлення про дефект, номер рядка та шлях до проблемного файлу друкуються в потік `stderr`.
* **Використання в скриптах:** обов'язковий перевірочний крок перед виконанням `systemctl reload sshd` або `kill -HUP $(cat /run/sshd.pid)`.

### Дамп обчисленої конфігурації: `sshd -T`
```bash
sudo sshd -T
sudo sshd -T | grep -E "passwordauthentication|permitrootlogin|ciphers|rekeylimit"
```
* **Призначення:** зчитує всі конфігураційні файли, розкриває підключення `Include`, застосовує внутрішні значення за замовчуванням для невизначених параметрів і виводить повний словник активних налаштувань демона у потік `stdout`.
* **Формат виводу:** кожен рядок містить назву директиви в нижньому регістрі та її фінальне нормалізоване значення, розділені пробілом:
  ```text
  port 22
  addressfamily any
  permitrootlogin prohibit-password
  passwordauthentication no
  pubkeyauthentication yes
  ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com,aes256-ctr
  rekeylimit 1073741824 3600
  ```

### Симуляція клієнтського підключення: `sshd -T -C`
```bash
sudo sshd -T -C "user=deployer,host=bastion.internal,addr=192.168.1.50,laddr=10.0.0.1,lport=22"
```
* **Синтаксис специфікації підключення (`-C`):** рядок пар `ключ=значення`, розділених комами:
  * `user=ім'я` — ім'я користувача;
  * `host=хост` — ім'я хоста клієнта;
  * `addr=IP` — IP-адреса клієнта;
  * `laddr=IP` — локальна IP-адреса інтерфейсу сервера;
  * `lport=порт` — локальний TCP-порт сервера.
* **Призначення:** емулює вхідне мережеве з'єднання з заданими параметрами й виконує обчислення всіх блоків `Match`. Це дозволяє протестувати, які саме правила ізоляції, методи автентифікації чи обмеження тунелів будуть застосовані до конкретного користувача чи IP-адреси без реального відкриття SSH-сесії.
* **Приклад діагностики:**
  ```bash
  # Перевірка, чи вимкнено парольний вхід для користувача deployer з зовнішньої мережі:
  sudo sshd -T -C "user=deployer,addr=203.0.113.10" | grep passwordauthentication
  ```

### Інтерактивний режим відлагодження: `sshd -d`
```bash
sudo /usr/sbin/sshd -d -p 2222
sudo /usr/sbin/sshd -ddd -p 2222
```
* **Призначення:** запускає екземпляр сервера в однопотоковому інтерактивному режимі без відгалуження у фон (`no fork/daemonize`). Демон слухає вказаний порт, приймає рівно одне підключення, виводить детальне трасування всіх фаз протоколу (узгодження KEX, криптографічні підписи, виклики PAM, сесійні канали) у потік `stderr` і автоматично завершує роботу після закриття сесії. Рівні деталізації: `-d` (інформаційний), `-dd` (розширений дебаг), `-ddd` (максимальний дебаг включно з розбором окремих пакетів).

### Сигнали керування та безпечне перезавантаження
* `SIGHUP` (`kill -HUP <pid>` або `systemctl reload sshd`): демон перечитує конфігураційні файли. Активні з'єднання не перериваються; нові налаштування застосовуються виключно до наступних вхідних підключень.
* `SIGTERM` (`systemctl stop sshd`): коректне завершення роботи головного слухаючого процесу.
