Сценарій автоматичного резервного копіювання отримує параметри запуску: назву цільового каталогу, прапорець примусового перезапису та список файлів. Якщо адміністратор викликає команду `./backup.sh -f --dest "/mnt/backup storage" "Daily Report.pdf" "Budget 2026.xlsx"`, а всередині сценарію автор передає аргументи команді архівування як `tar -czf $TARGET_DIR/out.tar.gz $*`, виконання миттєво зазнає аварії. Замість одного шляху `/mnt/backup storage` команда `tar` отримує два незалежні аргументи `/mnt/backup` та `storage`, після чого марно намагається знайти неіснуючий файл `Daily`, створює пошкоджений архів і завершується з ненульовим кодом помилки. Будь-який пробіл, символ табуляції або знак нового рядка всередині значення параметра перетворюється на межу розриву, якщо інтерпретатор не отримав чіткої інструкції щодо збереження цілісності елементів.

Обробка аргументів командного рядка в Unix-подібних операційних системах — це фундаментальний інтерфейс взаємодії між користувачем, системними службами та кодом сценарію. На відміну від високорівневих мов програмування, де параметри відразу потрапляють у структуровані масиви чи колекції об'єктів, командна оболонка (POSIX Shell, Bash, Dash, Zsh) є текстовим макропроцесором. Кожен переданий параметр проходить крізь багаторівневий конвеєр синтаксичного розбору, підстановки змінних, розбиття на поля (word splitting) та розкриття шаблонів імен файлів (globbing).

## 1. Анатомія позиційних параметрів: від execve() до внутрішніх структур оболонки

Життєвий цикл будь-якого аргументу починається задовго до того, як інтерпретатор оболонки виконає перший рядок коду. Коли батьківський процес запускає скрипт, він звертається до системного виклику `execve()`, передаючи ядру Linux масив вказівників на нуль-терміновані рядки `char *argv[]`.

Якщо файл сценарію починається з рядка shebang (наприклад, `#!/bin/sh`), бінарний завантажувач ядра Linux (функція `load_script()` у ядровому файлі `fs/binfmt_script.c`) зчитує перші байти файлу (структура `linux_binprm`), витягує шлях до інтерпретатора та перебудовує масив аргументів на верхівці стека користувача. Інтерпретатор `/bin/sh` стає новим виконуваним образом процесу, а початкові аргументи зміщуються:

```text
Виклик користувача:   ./deploy.sh --prod "web server"
Ядро формує argv:    argv[0] = "/bin/sh"
                     argv[1] = "./deploy.sh"
                     argv[2] = "--prod"
                     argv[3] = "web server"
```

Коли інтерпретатор ініціалізує своє внутрішнє середовище, він відокремлює власні службові прапорці та ім'я файлу скрипту від користувацьких параметрів. У вихідному коді класичних оболонок (наприклад, `dash` у файлі `src/var.c` або `bash` у файлі `variables.c`) параметри зберігаються у внутрішній структурі — **масиві позиційних параметрів** (`shellparam` або `dollar_vars`). Ця структура містить масив вказівників на виділені рядки `char **pats` та лічильник кількості елементів `nparam`.

```
+-------------------------------------------------------------------------+
|                        Внутрішній стан оболонки                         |
+-------------------------------------------------------------------------+
| $0 = "./deploy.sh" (Ім'я програми / шлях виклику)                        |
| $1 = "--prod"      (Перший позиційний параметр)                         |
| $2 = "web server"  (Другий позиційний параметр)                         |
| $# = 2             (Загальна кількість позиційних параметрів)            |
+-------------------------------------------------------------------------+
```

### Природа та поведінка змінної $0

Змінна `$0` не належить до масиву позиційних параметрів `$1`..`$N` і не враховується лічильником `$#`. Вона містить ім'я або шлях, за яким було викликано сам сценарій (значення `argv[0]` для скрипту).

Поведінка `$0` залежить від способу виклику:
- Якщо скрипт викликано безпосередньо через шлях (`/usr/local/bin/backup.sh` або `./backup.sh`), `$0` містить саме цей переданий шлях.
- Якщо скрипт запущено через явний виклик інтерпретатора (`sh /opt/scripts/run.sh`), `$0` отримає значення `/opt/scripts/run.sh`.
- Якщо оболонка є сеансом входу (login shell), перший символ `$0` традиційно містить дефіс (наприклад, `-bash` або `-sh`), що сигналізує про необхідність зчитування конфігураційних файлів `/etc/profile` та `~/.profile`.
- Якщо код виконується всередині функції оболонки в стандарті POSIX, `$0` продовжує вказувати на ім'я головного сценарію, а не на ім'я функції (на відміну від масиву `$1`..`$N`, який у тілі функції локально заміщується аргументами цієї функції).

### Індексація: від $1 до $9 та синтаксична пастка ${10}

Оболонка надає прямий доступ до перших дев'яти аргументів за допомогою однозначних ідентифікаторів від `$1` до `$9`. Проте спроба звернутися до десятого аргументу як `$10` є однією з найпоширеніших класичних помилок у скриптах Unix.

Згідно з граматикою стандарту POSIX (IEEE Std 1003.1, розділ «Parameter Expansion»), лексичний аналізатор без фігурних дужок розпізнає символ долара `$` у поєднанні з рівно однією наступною цифрою як однозначний позиційний параметр. Будь-які наступні символи вважаються звичайним літеральним текстом.

```
Синтаксичний розбір виразу $10:
  1. Інтерпретатор виділяє токен параметра: $1
  2. Значення $1 підставляється у рядок
  3. Символ '0' дописується як звичайний текст
  Результат: "${1}0" (значення першого аргументу, після якого стоїть цифра нуль)
```

Якщо сценарію передано аргументи `arg1`, `arg2`, ..., `arg10`, звернення `$10` поверне рядок `arg10` лише випадково, якщо перший аргумент дорівнював `arg1`. Якщо ж перший параметр дорівнював `alpha`, вираз `$10` розгорнеться у рядок `alpha0`.

Щоб однозначно вказати інтерпретатору на багатозначний числовий індекс, позиційний параметр обов'язково беруть у фігурні дужки:

```sh
# Помилково: еквівалентно "$1" і символ "0"
TENTH_ARG=$10

# Правильно: звернення до десятого елемента позиційного масиву
TENTH_ARG=${10}
ELEVENTH_ARG=${11}
```

### Кількість аргументів: змінна $#

Спеціальна змінна `$#` (argument count) зберігає поточну кількість позиційних параметрів, доступних сценарію або функції у поточній області видимості.

- Якщо скрипт запущено без аргументів, `$#` дорівнює `0`.
- Змінна `$#` є динамічною: її значення зменшується під час виконання команди `shift` або повністю змінюється при виклику `set --`.
- Значення `$#` часто використовується як первинний захисний бар'єр на початку виконання програми:

```sh
if [ "$#" -lt 2 ]; then
    printf "Помилка: потрібно щонайменше 2 аргументи (отримано %d)\n" "$#" >&2
    printf "Використання: %s <джерело> <призначення>\n" "$0" >&2
    exit 1
fi
```

## 2. Чотири грані розгортання: $* проти $@, "$*" проти "$@"

Передача всього списку отриманих аргументів іншій утиліті або внутрішній функції — найчастіша операція в сценаріях-обгортках (wrapper scripts). Мова оболонки пропонує для цього чотири схожі на вигляд конструкції: `$*`, `$@`, `"$*"` та `"$@"`. Проте за схожістю прихована принципова різниця в семантиці розбиття на поля.

![Порівняння розкриття $* та $@](/root/sys/sys-unix/script-arguments/img/expansion-comparison-ifs.svg)
*Схематичне порівняння чотирьох варіантів розгортання аргументів: неекрановані форми руйнують межі слів через механізм IFS, "$*" зливає все в один рядок, а "$@" гарантує точне збереження масиву елементів.*

### Фази обробки командного рядка в POSIX Shell

Щоб зрозуміти причину різниці між цими розгортаннями, слід розглянути 7 послідовних кроків, які виконує інтерпретатор перед викликом команди:

1. **Розкриття тильди (`~`)**: заміна на домашній каталог користувача.
2. **Розкриття параметрів та змінних (`$VAR`, `$1`, `$*`, `$@`)**: заміна імен на їхні текстові значення.
3. **Підстановка команд (`$(cmd)` або `` `cmd` ``)**: виконання команди та захоплення виводу.
4. **Арифметичні обчислення (`$((expr))`)**: математичні операції над цілими числами.
5. **Розбиття на поля (Field Splitting / Word Splitting)**: сканування згенерованого тексту на наявність символів із системної змінної `IFS`.
6. **Розкриття імен файлів (Pathname Expansion / Globbing)**: підстановка списків файлів замість символів `*`, `?`, `[...]`.
7. **Видалення лапок (Quote Removal)**: зняття лапок `"`, `'` та зворотних слешів `\`.

### Неекрановані форми: $* та $@

Коли інтерпретатор зустрічає вираз `$*` або `$@` без подвійних лапок, отриманий після другого кроку текст **обов'язково потрапляє на кроки 5 та 6** (розбиття на поля та підстановка файлів).

Змінна `IFS` (Internal Field Separator) за замовчуванням містить пробіл, табуляцію та символ нового рядка (`$' \t\n'`). Якщо користувач передав параметр `"My Documents"`, на кроці 5 цей аргумент розривається по пробілу на два окремі токени: `My` та `Documents`.

Ба більше, якщо значення містить символи шаблонів (наприклад `"*.log"` або `"2 * 2"`), крок 6 виконає підстановку імен файлів з диска. Якщо в поточному каталозі лежать файли `app.log` та `sys.log`, вираз розгорнеться у два імена файлів замість одного рядка.

Через це неекрановані `$*` та `$@` ніколи не застосовуються для передачі масиву аргументів.

### Склеєний рядок: "$*"

Коли вираз `$*` поміщено у подвійні лапки `"$*"`, інтерпретатор вимикає розбиття на поля (крок 5) та розкриття імен файлів (крок 6). Усі позиційні параметри від `$1` до `$N` склеюються в **один єдиний рядок**.

Як роздільник між аргументами використовується **перший символ змінної середовища IFS**. Якщо `IFS` містить стандартні значення, аргументи об'єднуються через звичайний пробіл:

```
$1 = "alpha beta"
$2 = "gamma"
$3 = "delta"

"$*"  ===>  "alpha beta gamma delta"  (Один рядок, рівно один аргумент для execve)
```

Якщо змінну `IFS` змінено, форма `"$*"` адаптує свій роздільник:

```sh
join_by_comma() {
    old_ifs="$IFS"
    IFS=","
    result="$*"
    IFS="$old_ifs"
    printf "%s\n" "$result"
}

# Виклик: join_by_comma "Київ" "Львів" "Одеса"
# Виведе: Київ,Львів,Одеса
```

Якщо змінну `IFS` повністю очищено (`IFS=""`), `"$*"` склеїть аргументи взагалі без проміжних знаків: `"alphabetagammadelta"`.

### Збереження масиву: "$@" — Золотий стандарт POSIX

Спеціальна конструкція `"$@"` є нормативним винятком у синтаксисі POSIX. Коли подвійні лапки охоплюють `$@`, інтерпретатор генерує масив окремих захищених токенів:

```
"$@"  ===>  "$1" "$2" "$3" ... "$N"
```

Кожен позиційний параметр розглядається як окреме замкнене слово. Символи пробілів, табуляцій або переходу рядка всередині конкретного аргументу залишаються недоторканими, а розбиття на поля для них блокується:

```sh
# Надійний запуск іншої утиліти з абсолютною передачею параметрів:
exec /usr/bin/target_program "$@"
```

### Граничний випадок: поведінка "$@" при порожньому списку аргументів ($# == 0)

В історичних версіях Bourne Shell на ранніх Unix-системах (Version 7 Unix, System V Release 2) існувала неприємна вада реалізації: якщо `$# == 0` (сценарій викликано без аргументів), вираз `"$@"` розгортався у один порожній аргумент `""` (рядок нульової довжини), замість того щоб зникнути безслідно. Це змушувало програмістів писати громіздкі конструкції виду `${1+"$@"}`.

Стандарт POSIX суворо зафіксував сучасну поведінку: **якщо позиційні параметри відсутні (`$# == 0`), конструкція `"$@"` розгортається у нуль слів**. Жодних порожніх рядків у масив `argv` наступного процесу не додається. Конструкція `${1+"$@"}` у сучасному коді вважається застарілим рудиментом.

| Конструкція | Захист від Word Splitting | Захист від Globbing | Збереження окремих аргументів | Типове застосування |
| :--- | :--- | :--- | :--- | :--- |
| `$*` | Ні | Ні | Ні (руйнує поля) | Майже ніколи (потенційно небезпечно) |
| `$@` | Ні | Ні | Ні (руйнує поля) | Майже ніколи (потенційно небезпечно) |
| `"$*"` | **Так** | **Так** | Ні (зливає в 1 рядок) | Логування, друк усього рядка виклику, CSV |
| `"$@"` | **Так** | **Так** | **Так (еталон)** | **Передача параметрів утилітам, циклам for** |

## 3. Маніпуляція стеком аргументів: shift та set --

Під час послідовної обробки командного рядка виникає потреба вилучати вже оброблені прапорці або повністю замінювати список позиційних параметрів новими даними. Для цього мова оболонки надає вбудовані команди `shift` та `set --`.

![Масив позиційних параметрів та зсув через shift](/root/sys/sys-unix/script-arguments/img/positional-parameters-stack.svg)
*Зсув масиву позиційних параметрів за допомогою команди shift: аргументи переміщуються ліворуч, лічильник $# декрементується, а $0 залишається незмінним.*

### Механіка команди shift

Вбудована команда `shift [n]` виконує зсув масиву позиційних параметрів ліворуч на `n` позицій (за замовчуванням `n=1`):

```
Початковий стан:    $1="alpha",  $2="beta",  $3="gamma",  $#=3
Виконання:          shift
Новий стан:         $1="beta",   $2="gamma",              $#=2
```

Параметр `$1` безповоротно перезаписується значенням `$2`, параметр `$2` — значенням `$3` і так далі. Значення лічильника `$#` зменшується на `n`. Змінна `$0` жодним чином не модифікується.

Зсув на довільну кількість елементів `n` зручний тоді, коли оброблена опція потребувала обов'язкового значення:

```sh
case "$1" in
    -o|--output)
        OUTPUT_FILE="$2"
        shift 2   # Зсуваємо і саму опцію (-o), і її аргумент ($2)
        ;;
esac
```

#### Крайовий випадок: спроба shift за межі $#

Якщо скрипт виконує команду `shift n`, де `n` перевищує поточне значення `$#` (або `n < 0`), команда зазнає невдачі й повертає ненульовий статус виходу (`>0`).

У неінтерактивній оболонці стандарту POSIX виконання некоректного `shift` вважається спеціальною фатальною помилкою вбудованої команди (Special Builtin Error), яка призводить до **негайного аварійного завершення роботи всього сценарію**. Тому перед виконанням зсуву на `2` або більше позицій завжди слід перевіряти залишок аргументів:

```sh
if [ "$#" -lt 2 ]; then
    printf "Помилка: опція %s вимагає значення\n" "$1" >&2
    exit 1
fi
OUTPUT="$2"
shift 2
```

### Перевизначення позиційних параметрів через set --

Команда `set` у командній оболонці виконує дві різні функції: налаштування прапорців інтерпретатора (наприклад, `set -e`, `set -u`) та явне перевизначення масиву позиційних параметрів.

Коли команді `set` передається спеціальний маркер `--`, усі наступні аргументи стають новими позиційними параметрами `$1`, `$2`... для поточного скрипту або функції:

```sh
# Повністю замінюємо позиційні параметри сценарію трьома новими значеннями
set -- "перший аргумент" "другий аргумент з пробілом" "третій"

printf "Кількість аргументів: %d\n" "$#"   # Виведе: 3
printf "Параметр 1: [%s]\n" "$1"          # Виведе: [перший аргумент]
printf "Параметр 2: [%s]\n" "$2"          # Виведе: [другий аргумент з пробілом]
```

Маркер `--` є критично важливим. Якби ми написали `set -x "файл.txt"`, інтерпретатор сприйняв би `-x` як опцію увімкнення трасування коду (xtrace), а не як перший аргумент. Маркер `--` вимикає розпізнавання опцій у команді `set` і трактує навіть рядки, що починаються з дефіса (наприклад, `set -- -f -v`), виключно як текстові позиційні параметри.

Повний опис контрактів усіх вбудованих змінних і команд маніпуляції аргументами доступний у довіднику [Довідник позиційних параметрів та утиліти getopts](root:sys-unix/script-arguments/api-getopts-and-positional.md).

## 4. Вбудований парсер getopts: синтаксис та змінні стану

Коли утиліта приймає значну кількість прапорців (наприклад, `-v`, `-h`, `-f`, `-o output.txt`), ручний розбір через позиційні змінні стає перевантаженим. Прапорці можуть комбінуватися у кластери (запис `-v -f -x` еквівалентний `-vfx`), значення опцій можуть передаватися як окремим словом (`-o file.txt`), так і злитно (`-ofile.txt`).

Для стандартизації цього процесу в стандарт POSIX було включено вбудовану команду `getopts` (на заміну застарілої зовнішньої бінарної утиліти `/usr/bin/getopt`).

![Внутрішній автомат розбору опцій getopts](/root/sys/sys-unix/script-arguments/img/getopts-state-machine.svg)
*Схема внутрішнього автомата станів getopts: ітеративний аналіз символів опцій, переходи при знаходженні аргументів та обробка помилок у тихому й багатослівному режимах.*

### Синтаксис специфікації optstring

Команда `getopts` приймає рядок специфікації дозволених опцій (`optstring`) та назву змінної, у яку записуватиметься поточний знайдений прапорець:

```sh
getopts optstring variable_name [arguments...]
```

Рядок `optstring` складається з літерних символів та двокрапок:
- **Звичайна літера** (наприклад, `"v"` або `"h"`): Опція є булевим прапорцем. Вона не приймає додаткових значень.
- **Літера з двокрапкою після неї** (наприклад, `"f:"` або `"o:"`): Опція вимагає обов'язкового значення аргументу.
- **Провідна двокрапка на початку рядка** (наприклад, `":vho:f:"`): Вмикає **тихий режим обробки помилок** (Silent Error Handling).

### Тріада змінних стану: OPTIND, OPTARG, OPTERR

Робота `getopts` базується на трьох спеціальних змінних, які інтерпретатор автоматично підтримує між ітераціями:

1. **`OPTIND` (Option Index)**:
   - Зберігає числовий індекс наступного елемента масиву `argv`, який буде оброблено.
   - Під час старту скрипту `OPTIND=1`.
   - Коли `getopts` обробляє кластеризовані прапорці (наприклад, `-vxf`), він обробляє символи по черзі за допомогою внутрішнього посимвольного зміщення і збільшує `OPTIND` лише після того, як вичерпано всі літери поточного слова.
2. **`OPTARG` (Option Argument)**:
   - Якщо опція вимагала значення (наприклад, `-o filename`), `getopts` записує знайдений рядок `filename` у змінну `OPTARG`.
   - У тихому режимі, якщо виявлено невідому опцію або пропущено аргумент, `OPTARG` містить символ проблемної опції.
3. **`OPTERR` (Option Error)**:
   - Прапорець (`1` або `0`), що керує стандартним виводом повідомлень про помилки у потік `stderr`. За замовчуванням дорівнює `1`.

### Внутрішня механіка кластеризації: прихований стан nextchar

Багато інженерів дивуються: якщо команда `getopts` обробляє кластер прапорців `-vxf archive.tar.gz`, чому змінна `OPTIND` не збільшується після розпізнавання літери `v`?

Усередині кожної POSIX-оболонки поряд із глобальною змінною `OPTIND` існує внутрішня статична змінна вказівника (у вихідному коді `dash` та `busybox` це покажчик `optptr` або індекс `nextchar`). 
- Коли `getopts` бачить слово `-vxf`, він фіксує `OPTIND=1` і встановлює `optptr` на другий символ (`'v'`).
- На першій ітерації змінній `opt` присвоюється символ `'v'`, а `optptr` зміщується на символ `'x'`. Значення `OPTIND` залишається рівним `1`.
- На другій ітерації змінній `opt` присвоюється символ `'x'`, а `optptr` зміщується на `'f'`.
- На третій ітерації виявляється, що опція `'f'` вимагає аргументу (`f:`). Інтерпретатор перевіряє, чи є символи після `'f'` у поточному слові. Оскільки це був останній символ слова, `getopts` бере наступний елемент `argv[2]` (`archive.tar.gz`), поміщає його в `OPTARG`, скидає внутрішній `optptr` і збільшує `OPTIND` відразу до `3`.

### Багатослівний проти тихого режиму обробки помилок

Стандартний (багатослівний) режим діє тоді, коли рядок `optstring` не починається з двокрапки:

```sh
# Багатослівний режим: getopts "o:vh" opt
```

У цьому режимі при виявленні невідомого прапорця (`-z`) або відсутності обов'язкового аргументу (`-o` без файлу) утиліта `getopts` самостійно друкує системне повідомлення у `stderr` (наприклад, `sh: illegal option -- z`), встановлює змінну `opt` у символ `?` та очищує `OPTARG`.

Професійні сценарії майже завжди використовують **тихий режим** (провідна двокрапка `:o:vh`), оскільки він дозволяє реалізувати власний уніфікований формат діагностики помилок:

```sh
# Тихий режим: на початку optstring стоїть двокрапка ':'
while getopts ":f:o:vh" opt; do
    case "$opt" in
        f)
            FORCE_FILE="$OPTARG"
            ;;
        o)
            OUTPUT_FILE="$OPTARG"
            ;;
        v)
            VERBOSE=1
            ;;
        h)
            show_help
            exit 0
            ;;
        :)
            # Опція вимагала аргумент, але користувач його не вказав
            printf "Помилка: опція '-%s' вимагає значення аргументу.\n" "$OPTARG" >&2
            exit 1
            ;;
        \?|*)
            # Вказано невідомий прапорець
            printf "Помилка: невідома опція '-%s'.\n" "$OPTARG" >&2
            printf "Використовуйте -h для перегляду списку опцій.\n" >&2
            exit 1
            ;;
    esac
done
```

### Фінальне очищення: зсув операндів

Команда `getopts` зупиняє свою роботу та повертає код виходу `>0` (хибність), як тільки зустрічає перший позиційний аргумент, що не є опцією (не починається з дефіса), або коли зустрічає спеціальний роздільник `--`.

Після завершення циклу `while getopts` змінні опцій уже збережені, але в масиві `$1`..`$N` усе ще залишаються оброблені прапорці. Щоб отримати чистий список залишкових операндів (наприклад, імен файлів для обробки), виконують зсув на кількість пройдених елементів:

```sh
# Відкидаємо всі оброблені getopts прапорці та їхні аргументи
shift "$((OPTIND - 1))"

# Тепер $1 вказує на перший справжній операнд після опцій
printf "Залишилося операндів для обробки: %d\n" "$#"
for operand in "$@"; do
    process_file "$operand"
done
```

> 🔧 **Скидання OPTIND у функціях оболонки**
> Якщо ви викликаєте `getopts` всередині користувацької функції кілька разів під час роботи одного сценарію, змінна `OPTIND` зберігає глобальний стан між викликами. Перед початком повторного розбору аргументів у функції **обов'язково** скидайте індекс: `OPTIND=1`. В іншому разі `getopts` вважатиме, що аргументи вже вичерпано, і цикл взагалі не виконається.

## 5. Подолання обмежень: довгі опції та комбінований розбір

Незважаючи на зручність, стандартна утиліта `getopts` у стандарті POSIX має принципове обмеження: **вона підтримує виключно односимвольні короткі опції** (наприклад, `-h`, `-o`). Вона не підтримує довгі прапорці у стилі GNU (наприклад, `--help`, `--output=file.txt`).

### Чому не варто покладатися на зовнішній /usr/bin/getopt

Існує зовнішня бінарна утиліта GNU `getopt` (пакет `util-linux`), яка вміє перевпорядковувати командний рядок та підтримує довгі опції через синтаксис `getopt -o vho: -l version,help,output: -- "$@"`.

Проте використання зовнішнього `getopt` у переносних скриптах створює серйозні проблеми:
1. **Непереносність**: Реалізація `getopt` у системах BSD та macOS (Darwin) не підтримує довгі опції й поводиться принципово інакше, ніж GNU `getopt` у Linux.
2. **Небезпека eval**: Щоб застосувати результат роботи `getopt`, скрипт змушений виконувати небезпечну конструкцію `eval set -- "$PARSED"`. Якщо аргументи містять спеціальні символи або лапки, помилка в екрануванні в `eval` відкриває пряму вразливість до виконання довільного коду (Arbitrary Code Execution).

### Канонічний патерн: комбінований цикл while + case

Найбільш надійним, швидким і на 100% переносним способом підтримки як коротких, так і довгих опцій у чистому POSIX `sh` є комбінований цикл `while [ $# -gt 0 ]` у поєднанні з конструкцією `case "$1" in`:

```sh
#!/bin/sh
set -eu

OUTPUT_PATH=""
DRY_RUN=0

while [ $# -gt 0 ]; do
    case "$1" in
        -h|--help)
            printf "Використання: %s [ОПЦІЇ] [ФАЙЛИ...]\n" "$0"
            exit 0
            ;;
        -n|--dry-run)
            DRY_RUN=1
            shift
            ;;
        -o|--output)
            # Обробка формату з роздільним значенням: --output /tmp/file
            if [ $# -lt 2 ]; then
                printf "Помилка: опція '%s' вимагає аргументу.\n" "$1" >&2
                exit 1
            fi
            OUTPUT_PATH="$2"
            shift 2
            ;;
        --output=*)
            # Обробка формату зі знаком рівності: --output=/tmp/file
            OUTPUT_PATH="${1#*=}"
            shift
            ;;
        --)
            # Явний маркер кінця опцій
            shift
            break
            ;;
        -*)
            printf "Помилка: невідома опція '%s'\n" "$1" >&2
            exit 1
            ;;
        *)
            # Перший не-опціональний аргумент
            break
            ;;
    esac
done

# Усі залишки в "$@" тепер є суто позиційними операндами
```

Цей патерн елегантно обробляє обидва формати довгих опцій:
- Запис `--output path` перехоплюється гілкою `-o|--output`, де значення зчитується з `$2`, а стек зсувається на 2 позиції через `shift 2`.
- Запис `--output=path` перехоплюється шаблоном `--output=*`, де значення витягується за допомогою стандартної підстановки параметра `${1#*=}` (видалення префікса до знака `=` включно) без потреби у виклику зовнішніх утиліт `sed` чи `cut`.

Повноцінний промисловий приклад розбору аргументів зі сценарієм перевірки та обробкою винятків наведено у матеріалі [Практикум: Створення надійного парсера аргументів командного рядка](root:sys-unix/script-arguments/proj-argument-parser.md).

## 6. Системний вимір: C та C++ еквіваленти розбору аргументів

На системному рівні C-бібліотеки (glibc, musl) надають прямий інтерфейс до розбору аргументів через функцію `getopt_long()` із заголовка `<getopt.h>`.

Для порівняння архітектури нижче наведено реалізацію розбору тих самих параметрів мовами C та сучасним C++:

:::tabs
```c
/* Розбір аргументів мовою C за допомогою POSIX getopt_long */
#include <stdio.h>
#include <stdlib.h>
#include <getopt.h>

int main(int argc, char *argv[]) {
    int opt;
    const char *output = NULL;
    int verbose = 0;

    static struct option long_options[] = {
        {"help",    no_argument,       NULL, 'h'},
        {"verbose", no_argument,       NULL, 'v'},
        {"output",  required_argument, NULL, 'o'},
        {NULL,      0,                 NULL, 0}
    };

    while ((opt = getopt_long(argc, argv, ":hvo:", long_options, NULL)) != -1) {
        switch (opt) {
        case 'h':
            printf("Використання: %s [-v] [-o FILE] [OPERANDS...]\n", argv[0]);
            return 0;
        case 'v':
            verbose = 1;
            break;
        case 'o':
            output = optarg;
            break;
        case ':':
            fprintf(stderr, "%s: опція '-%c' вимагає значення\n", argv[0], optopt);
            return 1;
        case '?':
            fprintf(stderr, "%s: невідома опція\n", argv[0]);
            return 1;
        default:
            return 1;
        }
    }

    /* Обробка залишкових операндів */
    for (int i = optind; i < argc; ++i) {
        printf("Позиційний операнд: %s\n", argv[i]);
    }
    return 0;
}
```
```cpp
// Ідіоматичний розбір аргументів мовою C++20 із застосуванням std::string_view
#include <iostream>
#include <string_view>
#include <vector>
#include <optional>
#include <getopt.h>

struct ProgramOptions {
    bool verbose{false};
    std::optional<std::string_view> output;
    std::vector<std::string_view> operands;
};

int main(int argc, char *argv[]) {
    static const struct option long_opts[] = {
        {"help",    no_argument,       nullptr, 'h'},
        {"verbose", no_argument,       nullptr, 'v'},
        {"output",  required_argument, nullptr, 'o'},
        {nullptr,   0,                 nullptr, 0}
    };

    ProgramOptions config;
    int opt;

    while ((opt = ::getopt_long(argc, argv, ":hvo:", long_opts, nullptr)) != -1) {
        switch (opt) {
        case 'h':
            std::cout << "Використання: " << argv[0] << " [-v] [-o FILE] [OPERANDS...]\n";
            return 0;
        case 'v':
            config.verbose = true;
            break;
        case 'o':
            config.output = std::string_view(optarg);
            break;
        case ':':
            std::cerr << argv[0] << ": опція вимагає значення аргументу\n";
            return 1;
        case '?':
            std::cerr << argv[0] << ": виявлено невідому опцію\n";
            return 1;
        default:
            return 1;
        }
    }

    for (int i = optind; i < argc; ++i) {
        config.operands.emplace_back(argv[i]);
    }

    return 0;
}
```

## 7. Діагностика та інспектування аргументів у налагодженні

Коли у складному сценарії виникають підозри щодо спотворення меж аргументів або некоректної роботи розкриття змінних, інженер має у своєму розпорядженні кілька інструментів діагностики.

### Трасування через set -x та налаштування префікса PS4

Увімкнення режиму трасування `set -x` (або запуск `sh -x script.sh`) змушує інтерпретатор друкувати кожну команду у `stderr` безпосередньо перед її виконанням, уже **після** здійснення всіх підстановок, розбиття на поля та розкриття шляхів.

Для отримання детальної інформації про номер рядка та вкладеність викликів налаштовують змінну запрошення `PS4`:

```sh
# Налаштування інформативного префікса трасування:
export PS4='+ ${BASH_SOURCE:-$0}:${LINENO}: '
set -x
```

### Безпечний друк меж аргументів через printf %s

Для точної візуальної перевірки того, скільки саме аргументів надійшло у функцію або скрипт і де проходять їхні межі, використовують форматований вивід `printf`:

```sh
debug_args() {
    printf "Кількість отриманих аргументів: %d\n" "$#"
    printf -- "--- Початок списку ---\n"
    # Шаблон виводить кожен елемент "$@" в окремому рядку всередині квадратних дужок
    printf "  arg: [%s]\n" "$@"
    printf -- "--- Кінець списку ---\n"
}
```

Якщо користувач викликав команду з аргументами `"перший файл"` та `"другий файл"`, виклик `debug_args "$@"` чітко покаже рівно два рядки `[перший файл]` та `[другий файл]`. Якщо ж помилково було передано неекранований `$*`, утиліта негайно надрукує чотири рядки: `[перший]`, `[файл]`, `[другий]`, `[файл]`.

### Низькорівневе інспектування системних викликів через strace

Якщо скрипт викликає зовнішні бінарні утиліти, точний зріз сформованого масиву `argv` можна зафіксувати на межі переходу в ядро за допомогою утиліти `strace`:

```bash
strace -f -e trace=execve ./backup.sh -o "/tmp/backup dir" "test file.txt"
```

У лозі `strace` буде відображено точний системний виклик `execve()` з фіксацією кожного нуль-термінованого рядка масиву `argv`, що дозволяє остаточно переконатися у відсутності витоків або спотворень даних.

## 8. Зведена матриця надійності обробки аргументів

Для побудови відмовостійких системних сценаріїв інженер повинен керуватися наступними правилами вибору інструментів:

| Завдання | Рекомендований механізм | Небезпечна / Помилкова альтернатива | Чому саме так |
| :--- | :--- | :--- | :--- |
| **Передача списку аргументів іншій програмі** | `command "$@"` | `command $*` або `command $@` | `"$@"` захищає пробіли та символи нового рядка всередині аргументів від Word Splitting та Globbing. |
| **Звернення до параметрів > 9** | `${10}`, `${11}` | `$10`, `$11` | `$10` розгортається у `$1` + рядок `"0"`. |
| **Розбір стандартних коротких прапорців** | `while getopts ":f:o:vh" opt; do` | Ручні цикли або зовнішній `/usr/bin/getopt` | `getopts` вбудовано в шелл, підтримує кластери `-vxf` та не потребує небезпечного `eval`. |
| **Підтримка довгих опцій у POSIX sh** | `while [ $# -gt 0 ]` + `case "$1" in` | `eval set -- "$(getopt ...)"` | Повна переносність на будь-яку POSIX систему (Linux, FreeBSD, macOS) без вразливостей `eval`. |
| **Очищення оброблених прапорців** | `shift "$((OPTIND - 1))"` | Ручний підрахунок кількості `shift` | `OPTIND` точно знає кількість спожитих слів `argv` з урахуванням кластеризації. |
| **Завершення введення опцій** | Обробка маркера `--` | Ігнорування дефісних імен файлів | Дозволяє користувачеві безпечно передавати файли на кшталт `-rf` або `--file.txt`. |
