# 📋 Поверхня ядра Linux: API та структури blk_mq_tag_set

Вставка розкриває програмний контракт рівня підсистеми `blk-mq` у ядрі Linux, деталізуючи конфігураційні структури даних `struct blk_mq_tag_set`, таблицю операцій `struct blk_mq_ops`, внутрішній стан апаратного контексту `struct blk_mq_hw_ctx`, допоміжні структури передачі даних `struct blk_mq_queue_data`, функції керування життєвим циклом пулів тегів та поверхню спостереження з простору користувача (каталоги sysfs у `/sys/block/<dev>/mq/`, статистику debugfs і трасувальні точки tracepoints). Вона слугує прямою довідковою опорою для розробників драйверів блокових пристроїв та системних програмістів підсистеми вводу-виводу.

---

## 1. Головна конфігураційна структура: `struct blk_mq_tag_set`

Центральним об'єктом, який об'єднує всі апаратні черги, алгоритми виділення слотів команд та параметри контролера накопичувача, є структура `struct blk_mq_tag_set`. Вона оголошена в заголовку `<linux/blk-mq.h>`.

Нижче наведено її визначення, скорочене до полів, які заповнює або читає драйвер (суто внутрішні поля ядра — лічильники, RCU-захист, кеш спільних тегів — опущено):

:::code api-blk-mq-tag-set-surface/c/1-holovna-konfihuratsiina.c

### Деталізація полів `blk_mq_tag_set`

1. **`ops`**: Вказівник на таблицю колбеків. Драйвер зобов'язаний реалізувати як мінімум метод `queue_rq` для відправки команд у фізичний накопичувач.
2. **`nr_hw_queues`**: Визначає кількість апаратних контекстів `blk_mq_hw_ctx`. Наприклад, для NVMe-накопичувача це значення зазвичай відповідає кількості переривань MSI-X або кількості доступних процесорних ядер.
3. **`queue_depth`**: Скільки команд одночасно тримає в роботі ОДНА апаратна черга — саме так це поле описане в ядрі («number of tags per hardware queue, reserved tags included»). Воно задає розмір бітової карти `sbitmap` для однієї `hctx`, а межа всього пристрою виходить множенням на `nr_hw_queues`.
4. **`reserved_tags`**: Захисна зона тегів. Ці слоти виділяються лише під службові операції (скидання кешу `flush`, скидання контролера при збоях, виконання passthrough `ioctl`). Без reserved-тегів при повному заповненні черги звичайними запитами читання/запису системні команди скидання кешу потрапляють у взаємне блокування (deadlock).
5. **`cmd_size`**: Шар `blk-mq` виділяє пам'ять під кожну структуру `struct request` разом із додатковим "хвостом" (tail buffer) розміром `cmd_size`. Драйвер зберігає там свої приватні структури (наприклад, NVMe command dword, списки розсіяння-збирання SGL або DMA-дескриптори) без необхідності додаткових викликів `kmalloc`.
6. **`map[HCTX_MAX_TYPES]`**: Ядро Linux підтримує до трьох різних мап відображення CPU на `hctx`:
   - `HCTX_TYPE_DEFAULT`: Стандартні черги для змішаного читання та запису.
   - `HCTX_TYPE_READ`: Окремі черги виключно під операції читання — щоб синхронне читання, на яке процес чекає, не стояло за пакетом фонового запису.
   - `HCTX_TYPE_POLL`: Окремі апаратні черги без обробників переривань, призначені для підсистеми асинхронного опитування (I/O polling / `io_uring`).

## 2. Прапори конфігурації поведінки: `flags`

Поле `flags` у структурі `blk_mq_tag_set` керує внутрішньою логікою обробки запитів на рівні шару `blk-mq`:

- **`BLK_MQ_F_SHOULD_MERGE`**: Вмикав програмну перевірку на злиття суміжних `bio` (bio merging) у програмній черзі `blk_mq_ctx`: без нього кожен `bio` одразу ставав окремою `struct request`. Прапор жив до ядра 6.13 включно — від 6.14 його прибрали, бо його виставляли майже всі драйвери; злиття тепер увімкнене завжди, а вимикається воно з простору користувача через `/sys/block/<dev>/queue/nomerges`.
- **`BLK_MQ_F_TAG_QUEUE_SHARED`**: Вказує ядру, що декілька незалежних черг пристроїв (`request_queue`) ділять один і той самий пул тегів `blk_mq_tag_set`. Це активує динамічне зважування та обмеження тегів між пристроями, запобігаючи ситуації, коли один диск захоплює 100% слотів спільного контролера.
- **`BLK_MQ_F_BLOCKING`**: Сигналізує, що колбек драйвера `queue_rq()` має право переходити у стан сну (наприклад, брати м'ютекси, чекати на блокуваннях або виконувати виклики виділення пам'яті, що можуть заснути). За замовчуванням `queue_rq()` виконується в атомарному контексті — під `rcu_read_lock()`, де спати заборонено.
- **`BLK_MQ_F_NO_SCHED`**: Забороняє підключення зовнішніх I/O планувальників (таких як `kyber` або `bfq`) до цієї черги. Використовується для пристроїв, де планування на рівні ядра лише створює накладні витрати (наприклад, ramdisk або zram).
- **`BLK_MQ_F_ALLOC_POLICY_START_BIT`**: Не окремий прапор-перемикач, а позиція бітового поля, в яке драйвер кладе політику пошуку тегів (ширина поля — `BLK_MQ_F_ALLOC_POLICY_BITS`). Значень два: `BLK_TAG_ALLOC_FIFO` — за замовчуванням, пошук щоразу починається від нуля; `BLK_TAG_ALLOC_RR` — по колу, від останнього виданого тегу. Кругова політика потрібна там, де швидке перевикористання того самого тегу шкодить (класичний випадок — SCSI-пристрої, чутливі до повторної видачі щойно звільненого слота).

### Структура `struct blk_mq_queue_data`

При виклику `queue_rq()` ядро передає драйверу об'єкт `struct blk_mq_queue_data`:

```c
struct blk_mq_queue_data {
    struct request *rq;   /* Вказівник на підготовлений запит із присвоєним тегом */
    bool last;            /* Прапор: true, якщо це останній запит у поточному батчі */
};
```

Прапор `last` дозволяє драйверу оптимізувати відправку: якщо `last == false`, драйвер записує команду в PCIe-кільце Submission Queue, але відкладає оновлення MMIO-регістра `doorbell`. Лише коли приходить запит із `last == true` (або викликається `commit_rqs()`), драйвер виконує один виклик `doorbell`, відправляючи весь пакет команд за одну операцію на шині PCIe.

### Коди повернення `blk_status_t` у виклику `queue_rq`

Коли шар `blk-mq` викликає `ops->queue_rq()`, драйвер намагається записати команду в апаратне кільце (Submission Queue). Залежно від стану накопичувача, метод повертає один із таких статусів:

- **`BLK_STS_OK`**: Команду успішно прийнято пристроєм.
- **`BLK_STS_RESOURCE`**: Не вистачило ресурсу, ширшого за сам пристрій — памʼяті ядра, DMA-мапінгу, запису в пул. Завершення вже виданих команд такий ресурс не поверне (його могло не бути в польоті взагалі), тож `blk-mq` кладе запит назад у `dispatch list` і сам перезапускає чергу через коротку затримку (`BLK_MQ_RESOURCE_DELAY`, 3 мс).
- **`BLK_STS_DEV_RESOURCE`**: Закінчився ресурс саме цього пристрою (заповнене кільце Submission Queue, вичерпані апаратні дескриптори), і драйвер цим кодом ГАРАНТУЄ: ресурс звільниться із завершенням команд, що вже в польоті, а отже чергу буде перезапущено з обробника завершення. Таймер на всяк випадок тут зайвий — саме цим цей код і відрізняється від `BLK_STS_RESOURCE`.
- **`BLK_STS_IOERR`**: Критична апаратна помилка шини або контролера. Запит негайно завершується з помилкою вводу-виводу для користувацького процесу.
- **`BLK_STS_AGAIN`**: Відмова для запиту з прапором `REQ_NOWAIT` — так блоковий шар позначає ввід-вивід, який заборонено присипляти (`RWF_NOWAIT` у `preadv2`/`pwritev2`, неблокувальні спроби `io_uring`). Замість чекати на вільний тег чи ресурс, ядро одразу віддає застосунку `EAGAIN`.

## 6. Поверхня спостереження: sysfs та debugfs

Внутрішній стан черг видно з простору користувача, але поділ між двома файловими системами тут строгий, і плутати їх дорого: у `sysfs` лежить лише **стабільний контракт** — три атрибути на апаратну чергу, на які можна спиратися у скриптах; усе решта, аж до сирих бітових карт, живе в `debugfs` і не має жодних гарантій сумісності між версіями ядра.

### Стабільна частина: `/sys/block/<dev>/mq/`

```text
/sys/block/nvme0n1/mq/
├── 0/                      # Каталог апаратної черги hctx 0
│   ├── nr_tags             # Загальна кількість тегів у цій hctx
│   ├── nr_reserved_tags    # Скільки з них зарезервовано під службові команди
│   └── cpu_list            # Список ядер, мапованих на цю hctx ("0, 1")
└── 1/                      # Каталог апаратної черги hctx 1
```

Більше в цьому каталозі немає нічого: масив `default_hw_ctx_attrs` у `blk-mq-sysfs.c` містить рівно ці три атрибути, усі лише на читання. Налаштування активного планувальника — не тут, а в `/sys/block/<dev>/queue/iosched/`; глибина черги — у `/sys/block/<dev>/queue/nr_requests`.

### Діагностична частина: `/sys/kernel/debug/block/<dev>/`

Каталог зʼявляється лише при `CONFIG_BLK_DEBUG_FS=y` і містить по підкаталогу `hctx0`, `hctx1`, … на кожну апаратну чергу:

```text
/sys/kernel/debug/block/nvme0n1/hctx0/
├── state                   # Прапорці BLK_MQ_S_* (зокрема STOPPED)
├── flags                   # Прапорці BLK_MQ_F_* цього tag_set
├── type                    # Тип черги: default, read або poll
├── dispatch                # Запити, що зараз лежать у dispatch list
├── dispatch_busy           # Ковзне середнє «зайнятості» відправки (BLK_STS_RESOURCE)
├── busy                    # Запити, видані драйверу й ще не завершені
├── active                  # Лічильник активних запитів для спільного tag_set
├── ctx_map                 # Бітова карта програмних черг ctx, що мають роботу
├── tags                    # Зведення по sbitmap: глибина, wake_batch, alloc_hint
├── tags_bitmap             # Сирий вміст бітової карти тегів
├── sched_tags              # Те саме для окремого пулу тегів планувальника
└── sched_tags_bitmap       # Сира бітова карта тегів планувальника
```

Саме `dispatch_busy` тут — головний робочий сигнал: він росте, коли драйвер раз за разом відповідає `BLK_STS_RESOURCE`, тобто пристрій уже не приймає команди, і шар `blk-mq` змушений відкладати відправку.

### Точки трасування

Ядро експортує стандартні точки трасування (tracepoints) для `ftrace`, `perf` та `eBPF`:
- `block:block_rq_issue`: Фіксує момент передачі запиту з `hctx` у драйвер `queue_rq()`.
- `block:block_rq_complete`: Фіксує момент обробки переривання завершення та повернення тегу.
- `block:block_rq_requeue`: Фіксує повернення запиту назад у чергу — саме сюди потрапляють відмови `BLK_STS_RESOURCE`, коли слотів не вистачило.

Окремої точки трасування на сон в очікуванні вільного тегу ядро не має: цей стан видно непрямо — з `tags` у `debugfs` (карта заповнена) і з `block:block_rq_requeue` разом із `dispatch_busy`.

Тут наведено лише те, що стосується тегів і апаратних черг. Повний обхід поверхні спостереження блокового шару — усі атрибути `/sys/block/<dev>/queue/`, решта вузлів debugfs і рецепти `bpftrace` — належить темі [Багаточергова підсистема блокового вводу-виводу (blk-mq)](root:sys-unix/block-layer-mq).
