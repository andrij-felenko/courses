# 📜 Еволюція стекування LSM: від одного слота до повноцінного накладання

Історія стекування модулів безпеки в ядрі Linux (Linux Security Modules, LSM) відображає фундаментальну трансформацію архітектури ядра: від жорсткої монополії одного головного модуля безпеки до гнучкої, об'єднаної, багатошарової екосистеми. Перехід від єдиного слота до повноцінного накладання зумовлений гострими інженерними конфліктами, складністю розподілу пам'яті контекстів безпеки та багаторічною працею розробників підсистеми безпеки ядра Linux з подолання обмежень моделі єдиного головного модуля.

## Початкова відмова та поява LSM (2001–2003)

Улітку 2001 року на саміті розробників ядра Linux (Linux Kernel Summit) та Симпозіумі Linux в Оттаві (Ottawa Linux Symposium) Агентство національної безпеки США (NSA) презентувало проєкт Security-Enhanced Linux (SELinux). Задум інженерів NSA полягав у безпосередньому вбудовуванні архітектури мандатного контролю доступу (MAC) Flask безпосередньо в основний код ядра Linux.

Лінус Торвальдс (Linus Torvalds) рішуче відкинув ідею включення SELinux як єдиної жорстко вшитої моделі безпеки в ядрі. Причиною відмови була не якість коду SELinux, а принципова архітектурна позиція: монолітне ядро Linux не повинно нав'язувати розробникам дистрибутивів та системним адміністраторам одну конкретну філософію безпеки. Торвальдс зазначив, що SELinux є лише однією з можливих моделей (Type Enforcement), тоді як інші розробники висуватимуть власні концепції (наприклад, перевірка шляхів файлів у AppArmor або простіші спрощені правила в Smack).

Торвальдс висунув чітку вимогу: ядро має надати абстрактний, загальний уніфікований інтерфейс перехоплення дій (hooks), до якого будь-який зовнішній або вбудований модуль безпеки зможе підключити власні перевірки.

У відповідь на цей виклик було сформовано робочу групу під керівництвом Кріса Райта (Chris Wright) і Кріспіна Кована (Crispin Cowan, компанія WireX) та за участі провідних розробників підсистем безпеки (включно із Джеймсом Моррісом / James Morris та Грегом Кроа-Гартманом / Greg Kroah-Hartman). Вони розробили першу версію каркасу Linux Security Modules. У ядрі Linux 2.6.0 (грудень 2003 року) фреймворк LSM був офіційно включений до основного дерева сирцевого коду.

```
       [ Запит на операцію в VFS / Syscall ]
                         │
                         ▼
             [ Традиційна перевірка DAC ]
                         │ (дозволено)
                         ▼
             [ LSM Hook (security.c) ]
                         │
        ┌────────────────┴────────────────┐
        │ Стара модель 2.6 (Один слот)    │
        ▼                                 ▼
[ SELinux / AppArmor ]             [ cap_lsm (minor) ]
```

## Проблема «одного головного слота» (Major/Minor LSMs)

У первісній реалізації LSM у ядрі 2.6 структура `struct security_operations` являла собою єдиний глобальний покажчик на таблицю функцій. Ядро дозволяло зареєструвати лише **один** так званий «головний» (major) модуль безпеки (SELinux, AppArmor, Smack або TOMOYO).

Причина такого обмеження була суто технічною та пов'язаною з виділенням пам'яті:
1. **Конфлікт за покажчик `void *security`:** Структури даних ядра (`struct task_struct`, `struct inode`, `struct file`, `struct cred`) мали лише один непрозорий покажчик `void *security`. Модуль, який ініціалізувався першим, повністю займав цей покажчик для збереження власного безпекового контексту (Security Identifier, SID, або мітки профілю). Спроба другого модуля записати власні дані за цією ж адресою призводила до витоку пам'яті або краху ядра.
2. **Продуктивність на гарячих шляхах:** Перевірка доступу відбувається на найгостріших шляхах виконання VFS та мережевих сокетів. Непрямі виклики функцій через масив покажчиків спричиняли промахи в кеші інструкцій (L1 instruction cache misses).

Для подолання цього обмеження розробники ядра запровадили так звані «допоміжні» (minor) модулі. Модулі на кшталт Yama (доданий у Linux 3.4 у 2012 році під керівництвом Кіса Кука для захисту від ptrace-атак на процеси) або базовий модуль Capabilities реалізовувалися як окремі додаткові перевірки, жорстко вшиті у виклики до чи після головного модуля. Проте створити довільну повноцінну комбінацію з SELinux та AppArmor у системі було технічно неможливо.

Спроби створити сторонній модуль-проксі під назвою `stacker` (2004–2005 роки), який би перенаправляв виклики двом іншим модулям, провалилися. Модуль `stacker` викликав гонки за пам'ять (race conditions) при виділенні контекстів об'єктів і створював діри в безпеці через відсутність атомарності при оновленні облікових даних процесів.

## Багаторічна боротьба за справжнє стекування (2012–2019)

Ідея справжнього, прозорого стекування (LSM Stacking) полягала в тому, щоб дозволити довільній кількості модулів безпеки реєструватися одночасно, гарантуючи безумовне виконання перевірок кожного з них у визначеній послідовності.

Головними рушійними силами цієї розробки стали Кейсі Шауфлер (Casey Schaufler, автор підсистеми Smack) та Кіс Кук (Kees Cook, керівник ініціативи Kernel Self-Protection Project у Google та Linux Foundation). 

Процес розробки тривав понад сім років і вимагав повної реструктуризації внутрішніх механізмів ядра Linux:

1. **Централізоване управління пам'яттю (`security blob`):** Замість того, щоб дозволяти кожному модулю самостійно виділяти пам'ять і записувати її в покажчик `void *security`, ядро перебрало повністю управління цим покажчиком на себе. Під час старту ядра кожен модуль повідомляє свої потреби в байтах для кожного типу об'єкта. Ядро вираховує суму цих розмірів, виділяє єдиний неперервний блок пам'яті (blob) для кожного об'єкта й надає кожному модулю його персональне фіксоване зміщення (offset).
2. **Уніфікація ідентифікаторів безпеки (`secid` / `secctx`):** Різні модулі використовували різні числові ідентифікатори `secid` для маркування мережевих пакетів (NetLabel / CIPSO / CALIPSO) та міжпроцесної взаємодії (IPC). Кейсі Шауфлер розробив механізм підсистеми `lsm_id` та абстракцію трансляції контекстів, яка дозволила ядрам ідентифікувати, якому саме модулю належить той чи інший мережевий контекст.

```
       [ Еволюція представлення пам'яті в об'єктах ядра ]

  Linux 2.6 – 4.19 (Один покажчик):
  struct inode ──► [ void *security ] ──► [ Власна структура SELinux ]

  Linux 5.1+ (Спільний Blob):
  struct inode ──► [ void *security ] ──► ┌───────────────────────────┐
                                          │ Offset 0 : SELinux Context│
                                          ├───────────────────────────┤
                                          │ Offset 8 : AppArmor Label │
                                          ├───────────────────────────┤
                                          │ Offset 16: Landlock Domain│
                                          └───────────────────────────┘
```

У випуску ядра Linux 4.20 було завершено масштабний рефакторинг інфраструктури списків гачків, а в Linux 5.1 (травень 2019 року) до основного дерева ввійшла інфраструктура спільних блоків пам'яті — та сама, що зробила стекування можливим. Це був не фініш: поєднати два повноцінні MAC-модулі (скажімо, SELinux і AppArmor) у мейнлайновому ядрі не можна й досі, тож стекування працює для всього, крім пари «головних» систем.

## Сучасний етап: BPF-LSM, Landlock та LSM Syscalls (2020–2024+)

Реалізація стекування відкрила шлях для появи нових типів модулів безпеки, які раніше конфліктували б із класичними дистрибутивними MAC-системами:

- **BPF-LSM (Linux 5.7, 2020 рік):** Дозволив прикріплювати динамічні BPF-програми безпосередньо до будь-яких гачків `security_hook_heads`. Це надало можливість додавати та оновлювати кастомні правила безпеки "на льоту" без перекомпіляції ядра та без завантаження зовнішніх LKM-модулів.
- **Landlock Sandboxing (Linux 5.13, 2021 рік):** Запровадив непривілейований модуль безпеки, який дозволяє звичайним користувацьким процесам обмежувати власні права файлової системи (створювати пісочниці) без прав `CAP_SYS_ADMIN`, працюючи паралельно із системним AppArmor чи SELinux.
- **LSM System Calls API (Linux 6.8, 2024 рік):** Розв'язав останню проблему стекування — конфлікти у віртуальній файловій системі `/proc/self/attr/`. Нові системні виклики `lsm_get_self_attr`, `lsm_set_self_attr` та `lsm_list_modules` надали прикладним програмам конфліктно-безпечний UAPI-інтерфейс для прямої взаємодії з конкретними модулями в багатошаровому стеку.

Завдяки еволюції LSM Stacking, сучасні операційні системи Linux (такі як Ubuntu, Fedora, Android, Android Automotive, ChromeOS) можуть одночасно виконувати Lockdown, Yama, SELinux/AppArmor, Landlock та eBPF-LSM без жодних архітектурних конфліктів чи втрати продуктивності.
