Коли сервіс у виробничому середовищі аварійно завершує роботу через помилку сегментації (сигнал `SIGSEGV`), журнал ядра `dmesg` або системний налагоджувач `gdb` фіксує лише шістнадцяткову адресу інструкції: `[<0x00000000004011e5>] ??? () from /usr/bin/service`. Процесор під час виконання машинних інструкцій оперує виключно 64-бітними числовими адресами лічильника команд `rip`, зміщеннями відносно регістра кадру стека `rbp` та покажчиками на сторінки віртуальної пам'яті. Імена функцій, назви типів структур, межі локальних змінних та номери рядків сирцевого коду відсутні в опкодах процесора x86-64 чи ARM64. Якщо скомпільований файл очищено від діагностичних таблиць, аварійний дамп пам'яті (*core dump*) перетворюється на масив безіменних байтів, що унеможливлює швидку діагностику збою.

Пряме збереження всієї налагоджувальної інформації всередині робочих бінарників створює іншу інженерну проблему — вибухове зростання обсягу файлів. Скомпільована програма на C++ розміром 4 МБ разом із метаданими налагодження розростається до 80–150 МБ. У масштабах операційної системи, що містить тисячі утиліт і спільних бібліотек, це означає витрату сотень гігабайтів дискового простору, надлишкове споживання пропускної здатності мережі під час розгортання контейнерів та додаткове навантаження на підсистему кешування сторінок (*page cache*) під час первинного зчитування заголовків файлів. Системна архітектура Unix розв'язує цю дилему шляхом суворого розділення символів виконання та налагодження, створення криптографічних відбитків збірки та динамічного завантаження діагностичних файлів за запитом.

## 1. Анатомія символів в ELF: поділ між `.dynsym`, `.symtab` і DWARF

Формат виконуваних та компонованих файлів ELF (*Executable and Linkable Format*, від грец. *ἐκτελεστός* — здійсненний) має двоїсту структуру: вигляд компонування (*Linker View*) на основі таблиці секцій (*Section Header Table*) та вигляд виконання (*Loader View*) на основі таблиці сегментів (*Program Header Table*). Символи, що містяться у бінарнику, поділяються на три принципово різні категорії залежно від того, кому саме вони призначені — динамічному завантажувачу ядра `ld.so`, налагоджувачу `gdb` чи інженеру під час аналізу сирців.

### Таблиця динамічних символів `.dynsym`

Секція `.dynsym` (від лат. *symbolum*, що походить від грец. *σύμβоλον* — умовний знак) містить мінімальний набір імен, обов'язковий для функціонування динамічного зв'язування. Коли програма викликає функцію `malloc()` зі стандартної бібліотеки `libc.so.6`, динамічний лінкер `ld.so` під час запуску процесу повинен знайти цю назву в таблиці експорту бібліотеки та підставити реальну адресу в глобальну таблицю зміщень (*Global Offset Table*, GOT).

Секція `.dynsym` володіє атрибутом `SHF_ALLOC` (виділення пам'яті). Це означає, що ядро Linux під час системного виклику `execve` відображає цю секцію у віртуальний адресний простір процесу у складі сегмента `PT_LOAD` або `PT_DYNAMIC`. Текстові рядки імен зберігаються у сусідній виділеній секції `.dynstr`. У `.dynsym` потрапляють лише:
1. Експортовані глобальні функції та змінні спільної бібліотеки (символи зі специфікатором видимості `STV_DEFAULT`).
2. Імпортовані нерозв'язані символи, на які посилаються релокаційні секції `.rela.plt` та `.rela.dyn`.

Видалити секцію `.dynsym` із динамічно скомпонованого бінарника неможливо: без неї `ld.so` поверне фатальну помилку і процес не запуститься.

### Повна таблиця символів `.symtab`

Секція `.symtab` містить вичерпний перелік усіх символічних імен, згенерованих компілятором і транслятором асемблера. На відміну від `.dynsym`, секція `.symtab` **не має** прапорця `SHF_ALLOC`. Вона ніколи не завантажується ядром в оперативну пам'ять під час звичайного запуску програми й не впливає на витрату пам'яті процесу. Рядки її імен розміщуються у нерозподіленій секції `.strtab`.

У таблиці `.symtab` зберігаються:
* Внутрішні функції з модифікатором `static` (локальні для одиниці трансляції).
* Локальні й статичні глобальні змінні.
* Символи з прихованою видимістю `__attribute__((visibility("hidden")))`.
* Назви секцій та допоміжні мітки асемблерних блоків.

Кожен запис у `.symtab` та `.dynsym` для 64-бітної архітектури описується системною структурою `Elf64_Sym` розміром 24 байти:

```c
typedef struct {
    Elf64_Word    st_name;  /* Зміщення рядка в .strtab або .dynstr */
    unsigned char st_info;  /* Тип символу (STT_FUNC, STT_OBJECT) та зв'язування (STB_GLOBAL, STB_LOCAL) */
    unsigned char st_other; /* Видимість символу (STV_DEFAULT, STV_HIDDEN) */
    Elf64_Section st_shndx; /* Індекс секції, де визначено символ (або SHN_UNDEF) */
    Elf64_Addr    st_value; /* Віртуальна адреса або зміщення всередині секції */
    Elf64_Xword   st_size;  /* Розмір об'єкта чи функції в байтах */
} Elf64_Sym;
```

Якщо інженер аналізує трасування стека (*stack trace*) в утиліті `perf` або `gdb`, налагоджувач за відсутності коду DWARF бере адресу інструкції (наприклад, `0x4011e0`), шукає в `.symtab` символ з умовами `st_value <= 0x4011e0 < (st_value + st_size)` і відновлює ім'я внутрішньої функції `process_packet`.

### Секції стандарту DWARF (`.debug_*`)

Таблиця `.symtab` дає лише плоский список адрес та імен, але не містить відомостей про аргументи, типи чи рядки сирцевого тексту. Цю інформацію забезпечує формат DWARF (*Debugging With Attributed Record Formats*). Метадані DWARF записуються в окремі секції з префіксом `.debug_`, які також не мають прапорця `SHF_ALLOC` і зберігаються виключно на диску:

* `.debug_info`: ієрархічний граф інформаційних дескрипторів (англ. *Debugging Information Entry*, DIE). Кожен вузол графа описує одиницю трансляції (`DW_TAG_compile_unit`), функцію (`DW_TAG_subprogram`), аргумент (`DW_TAG_formal_parameter`) або тип даних (`DW_TAG_base_type`, `DW_TAG_structure_type`) з відповідними атрибутами діапазонів адрес (`DW_AT_low_pc`, `DW_AT_high_pc`). Більшість числових значень та зміщень кодуються за схемою LEB128 (*Little-Endian Base 128*), що дозволяє зберігати цілі числа змінної довжини від 1 до 5 байтів.
* `.debug_line`: матриця відповідності адрес інструкцій номерам рядків і колонок сирцевих файлів. Вона закодована як програма для спеціалізованої віртуальної машини DWARF. Байткод-інструкції (наприклад, `DW_LNS_advance_pc`, `DW_LNS_advance_line` або спеціальні компактні опкоди) покроково відновлюють таблицю відповідності: віртуальна адреса процесора `0x4012a4` відповідає рядку 42 файлу `parser.c`.
* `.debug_loc` / `.debug_loclists`: списки розташування змінних у регістрах процесора або комірках стека, що змінюються під час виконання функції внаслідок оптимізацій компілятора (`-O2`). Якщо змінну було витіснено з регістра `rax` у стек за адресою `[rbp-0x18]`, DWARF повідомляє налагоджувачу, де саме шукати значення залежно від поточного лічильника команд `rip`.
* `.debug_frame` та `.eh_frame`: правила розгортання кадрів стека (*Call Frame Information*, CFI). Коли код скомпільовано без збереження покажчика кадру стека (`-fomit-frame-pointer`, що є стандартом для архітектури x86-64), регістр `rbp` використовується як звичайний регістр загального призначення. Відновити ланцюжок викликів функцій у стеку стає можливим лише за допомогою таблиць CFI. Вони складаються із записів опису загальної інформації (CIE — *Common Information Entry*) та описів кадрів функцій (FDE — *Frame Description Entry*). Секція `.eh_frame` (від англ. *exception handling*) має прапорець `SHF_ALLOC`, оскільки потрібна середовищу виконання C++ для розгортання винятків (*stack unwinding*), тоді як `.debug_frame` використовується виключно налагоджувачем.
* `.debug_str` та `.debug_str_offsets`: пул унікальних текстових рядків назв змінних і типів зі спільним доступом.

Детальніше про те, як формати налагодження еволюціонували від перших структур Unix V6 до сучасного DWARF 5, описано у вставці про [еволюцію налагоджувальних форматів](root:sys-unix/debug-symbols-and-build-id/hist-debuginfo-evolution.md).

## 2. Очищення бінарників: утиліта `strip` і збереження лінкування

Утиліта `strip` (від англ. *to strip* — здирати, оголювати) призначена для фізичного видалення нерозподілених секцій символів та налагодження з готових об'єктних файлів, спільних бібліотек і виконуваних бінарників.

### Механізм роботи `strip`

Коли утиліта `strip` обробляє файл ELF, вона виконує низькорівневу модифікацію його бінарного макету:
1. Зчитує заголовок ELF (`Elf64_Ehdr`) та таблицю заголовків секцій (SHT).
2. Ідентифікує секції, призначені для видалення (наприклад, `.symtab`, `.strtab`, усі `.debug_*`, коментарі компілятора `.comment`).
3. Вилучає тіла цих секцій із дискового образу файлу.
4. Перераховує зміщення `sh_offset` для секцій, що залишилися, вирівнюючи їх відповідно до вимог архітектури.
5. Оновлює таблицю SHT, поле кількості секцій `e_shnum`, зміщення таблиці рядків імен секцій `e_shstrndx` і змінює загальний розмір файлу системним викликом `ftruncate`.

При цьому сегменти завантаження `PT_LOAD`, таблиця динамічних символів `.dynsym`, таблиця рядків `.dynstr`, хеш-таблиці символів `.gnu.hash` та код секцій `.text` і `.data` залишаються абсолютно незмінними. Програма повністю зберігає здатність запускатися ядром і компонуватися з іншими бібліотеками під час виконання.

```
Початковий бінарник: [ELF Hdr | PT_LOAD (.text, .dynsym) | .symtab | .debug_info | SHT]
                                          │
                                 Утиліта strip
                                          ▼
Очищений бінарник:   [ELF Hdr | PT_LOAD (.text, .dynsym) | SHT]
```

### Режими очищення

Поведінка `strip` регулюється прапорцями командного рядка:

```bash
# 1. Повне очищення (за замовчуванням): видаляє .symtab, .strtab та всі .debug_*
strip /usr/bin/app

# 2. Видалення виключно секцій DWARF зі збереженням локальних символів .symtab
strip --strip-debug /usr/bin/app

# 3. Видалення символів, не потрібних для обробки релокацій (стандарт збірки дистрибутивів)
strip --strip-unneeded /usr/lib/libcustom.so

# 4. Видалення специфічних секцій метаданих
strip -R .comment -R .note.ABI-tag /usr/bin/app
```

> 🔧 **Навіщо це.**
> Режим `strip --strip-debug` часто застосовується на проміжних серверах тестування: видалення секцій DWARF скорочує розмір файлу на 80%, проте збережена таблиця `.symtab` дозволяє системним утилітам `perf top` або `trace-cmd` будувати людиночитні профілі виконання функцій без потреби у важких зовнішніх пакетах.

## 3. Відокремлення налагоджувальних символів: `objcopy` та `.gnu_debuglink`

Повне видалення налагоджувальної інформації унеможливлює розслідування інцидентів у продакшені. Інженерне рішення полягає у фізичному розділенні бінарника на дві частини: легкий очищений файл, який встановлюється на цільову систему, та повний файл символів, який зберігається на сервері збірок чи у репозиторії.

Для цього використовується утиліта `objcopy` з пакету GNU Binutils:

```bash
# Крок 1: Копіювання всіх налагоджувальних секцій в окремий файл app.debug
objcopy --only-keep-debug /usr/bin/app /usr/lib/debug/app.debug

# Крок 2: Очищення робочого бінарника
strip --strip-unneeded /usr/bin/app

# Крок 3: Вбудовування посилання на відокремлений файл у робочий бінарник
objcopy --add-gnu-debuglink=/usr/lib/debug/app.debug /usr/bin/app
```

Під час виконання команди `objcopy --only-keep-debug` створюється файл `app.debug`, де секції машинного коду та даних (`.text`, `.rodata`, `.data`) отримують спеціальний тип `SHT_NOBITS` замість `SHT_PROGBITS`. Це означає, що їхні віртуальні адреси, зміщення та розміри зберігаються в заголовках, але тіло секцій займає 0 байтів у дисковому просторі. Усі ж налагоджувальні секції DWARF та таблиця `.symtab` переносяться повністю.

### Структура секції `.gnu_debuglink`

Секція `.gnu_debuglink` додається до очищеного бінарника. Вона має простий бінарний макет:
1. Рядок імені відокремленого файлу (наприклад, `app.debug\0`), завершений нульовим байтом.
2. Байти доповнення нулями (*padding*) для вирівнювання на 4-байтову межу.
3. 4 байти контрольної суми CRC-32 (поліном IEEE 802.3 `0xEDB88320`), обчисленої від повного вмісту файлу `app.debug`.

```
Секція .gnu_debuglink:
┌──────────────────────────────────────────────┬───────────────┬─────────────────┐
│ Назва debug-файлу: "app.debug\0" (ASCII)     │ Падінг (0x00) │ CRC-32 (4 байта)│
└──────────────────────────────────────────────┴───────────────┴─────────────────┘
```

![Пошук символів за debuglink та Build ID](/root/sys/sys-unix/debug-symbols-and-build-id/img/build-id-and-debuglink.svg)
*Алгоритми зіставлення та пошуку відокремлених файлів налагодження*

### Алгоритм пошуку за `.gnu_debuglink`

Коли налагоджувач GDB завантажує очищений бінарник `/usr/bin/app`, він зчитує секцію `.gnu_debuglink` і виконує пошук файлу за фіксованим списком каталогів у такому порядку:
1. У тому самому каталозі, де розташовано бінарник: `/usr/bin/app.debug`.
2. У підкаталозі `.debug`: `/usr/bin/.debug/app.debug`.
3. У глобальному системному дереві налагодження з відтворенням повного шляху: `/usr/lib/debug/usr/bin/app.debug`.

Знайшовши файл, налагоджувач обчислює його контрольну суму CRC32 і порівнює зі значенням у секції `.gnu_debuglink`. Якщо файл було модифіковано або замінено новішою версією, GDB відхиляє його з попередженням про невідповідність контрольної суми (*CRC mismatch*), запобігаючи невірному зіставленню адрес.

### Обмеження `.gnu_debuglink`

Механізм debuglink має суттєві недоліки:
* Він спирається на ім'я файлу: якщо бінарник перейменовано (наприклад, `app-v2`), зв'язок втрачається.
* Він вимагає жорсткої прив'язки до структури файлових шляхів `/usr/lib/debug/`.
* Контрольна сума CRC-32 є криптографічно слабкою та допускає колізії на великих масивах даних.

## 4. Унікальний відбиток збірки: секція `.note.gnu.build-id`

Для подолання недоліків debuglink у компонувальнику GNU `ld` та LLVM `lld` розробили технологію Build ID (прапорець `-Wl,--build-id`).

Build ID — це 160-бітний криптографічний хеш SHA-1 (або 128-бітний MD5/UUID), який компонувальник обчислює під час фінальної генерації бінарника від нормалізованого вмісту заголовків ELF та тіл секцій. Компонувальник бере всі секції вихідного файлу, що мають атрибут `SHF_ALLOC`, пропускає поля дескриптора самої секції примітки (щоб уникнути циклічної залежності обчислення хешу від самого себе) та секції налагодження, і рахує підсумковий дайджест. Будь-яка зміна в сирцевому коді, опціях оптимізації, версії компілятора чи статичних бібліотеках гарантовано змінює цей хеш.

### Структура секції примітки `.note.gnu.build-id`

Секція `.note.gnu.build-id` отримує тип `SHT_NOTE` та прапорець `SHF_ALLOC`. Вона розміщується всередині сегмента завантаження `PT_NOTE`, тому доступна як на диску, так і безпосередньо в оперативній пам'яті процесу.

Формат примітки стандартизовано в ABI ELF:

```c
typedef struct {
    Elf64_Word n_namesz; /* Довжина імені власника (4 байти для "GNU\0") */
    Elf64_Word n_descsz; /* Довжина дескриптора хешу (20 байтів для SHA-1) */
    Elf64_Word n_type;   /* Тип примітки: NT_GNU_BUILD_ID (значення 3) */
} Elf64_Nhdr;
```

Безпосередньо за заголовком слідує 4-байтовий рядок `"GNU\0"`, а за ним — 20 байтів сирого бінарного хешу.

```
Секція .note.gnu.build-id:
┌──────────────┬──────────────┬──────────────┬─────────────┬──────────────────────────┐
│ n_namesz = 4 │ n_descsz = 20│ n_type = 3   │ "GNU\0"     │ SHA-1 бінарний хеш (20B) │
└──────────────┴──────────────┴──────────────┴─────────────┴──────────────────────────┘
```

Практичну програмну реалізацію зчитування цих структур мовами C та C++ наведено у вставці про [парсер секції .note.gnu.build-id](root:sys-unix/debug-symbols-and-build-id/proj-build-id-extractor.md).

### Адресація за вмістом у `/usr/lib/debug/.build-id/`

Завдяки криптографічній унікальності відбитка відпала потреба прив'язуватися до імен чи шляхів бінарників. В операційній системі налагоджувальні файли зберігаються за адресацією за вмістом (*content-addressable storage*):

Для бінарника з Build ID `7a9f1b2c4d8e3f015a6b7c8d9e0f1a2b3c4d5e6f`:
1. Перші два символи шістнадцяткового рядка стають назвою підкаталогу: `/usr/lib/debug/.build-id/7a/`.
2. Решта 38 символів утворюють ім'я файлу з суфіксом `.debug`: `9f1b2c4d8e3f015a6b7c8d9e0f1a2b3c4d5e6f.debug`.
3. Додатково створюються символьні посилання без суфікса `.debug`, які вказують на оригінальний виконуваний файл: `/usr/lib/debug/.build-id/7a/9f1b2c4d8e... -> /usr/bin/app`.

Коли налагоджувач досліджує очищений бінарник чи core dump, він:
1. Зчитує хеш із секції `.note.gnu.build-id` або сегмента `PT_NOTE` образу пам'яті.
2. Відкриває файл `/usr/lib/debug/.build-id/7a/9f1b2c4d8e3f015a6b7c8d9e0f1a2b3c4d5e6f.debug`.

Цей зв'язок є однозначним, детермінованим і повністю стійким до перейменування чи переміщення файлів.

## 5. Традиційні debuginfo-пакунки та їхні експлуатаційні обмеження

У класичних дистрибутивах Linux (RHEL, Fedora, Debian, Ubuntu, openSUSE) збірка програмного забезпечення автоматизована:
* Пакетні менеджери RPM запускають макрос `%prep` / `%build` / `%install` та утиліту `find-debuginfo.sh`.
* Система збірки відокремлює символи, генерує каталог `/usr/lib/debug/.build-id/` і формує два вихідних пакети: робочий `nginx-1.24.0.rpm` та налагоджувальний `nginx-debuginfo-1.24.0.rpm` (або `nginx-dbgsym` у Debian).

```
Складальний конвеєр:
Вихідний код C/C++ ──► Компіляція (-g) ──► Бінарник з DWARF
                                                │
                       ┌────────────────────────┴────────────────────────┐
                       ▼                                                 ▼
            Утиліта find-debuginfo                            Утиліта strip
                       │                                                 │
                       ▼                                                 ▼
           nginx-debuginfo.rpm                                   nginx.rpm
    (секції DWARF, .symtab, сирці)                        (очищений бінарник)
```

### Експлуатаційні проблеми класичних debuginfo

Незважаючи на впорядкованість, класична схема має високу експлуатаційну ціну під час підтримки систем у продакшені:
1. **Рутинна синхронізація версій**: Щоб проаналізувати аварію сервісу, інженер повинен встановити `debuginfo`-пакунки не лише для самої програми, а й для всіх залежних спільних бібліотек (`glibc-debuginfo`, `openssl-debuginfo`, `libstdc++-debuginfo`) абсолютно ідентичних релізів аж до номера збірки.
2. **Дисковий оверхед**: Встановлення debuginfo для системних компонентів вимагає десятків гігабайтів дискового простору.
3. **Хмарні обмеження**: У сучасних контейнерах (Kubernetes, Docker) коренева файлова система часто змонтована в режимі лише для читання (*read-only rootfs*), а встановлення пакетів через `dnf` або `apt` заблоковане політиками безпеки.

## 6. Сучасна парадигма: мережева служба `debuginfod`

У 2019 році в рамках проєкту `elfutils` було створено сервіс `debuginfod` (від англ. *debugging information daemon*), який усунув необхідність ручного завантаження та встановлення пакетів символів.

`debuginfod` — це клієнт-серверна система, що поширює налагоджувальні дані через звичайний протокол HTTP за запитом клієнта на основі Build ID.

![Архітектура debuginfod](/root/sys/sys-unix/debug-symbols-and-build-id/img/debuginfod-workflow.svg)
*Взаємодія діагностичних утиліт через libdebuginfod з локальним кешем та віддаленими HTTP-серверами*

### Архітектура та принцип роботи

1. **Сервер `debuginfod`**:
   * Фоновий демон сканує вказані каталоги з бінарниками, сховища пакетів RPM/DEB або репозиторії сирцевого коду.
   * Демон вичитує секції `.note.gnu.build-id` з усіх знайдених файлів і створює швидку індексну базу даних на базі SQLite.
   * Сервер надає простий HTTP REST API, де ресурси адресуються за відбитком збірки:
     * `GET /buildid/{buildid}/debuginfo` — повертає відокремлений DWARF ELF-файл.
     * `GET /buildid/{buildid}/executable` — повертає оригінальний бінарник.
     * `GET /buildid/{buildid}/source/{path}` — повертає сирцевий файл.
   * Якщо на сервер надходить запит на файл, запакований усередині RPM або DEB, `debuginfod` автоматично розпаковує потрібний шматок архіву на льоту в пам'яті та передає клієнту.

2. **Клієнт `libdebuginfod`**:
   * Системна бібліотека C `libdebuginfod.so` інтегрована безпосередньо в налагоджувач `gdb`, профілювальник `perf`, інструмент виявлення витоків пам'яті `valgrind`, трасувальник `bpftrace` та утиліти з пакету `elfutils` (`addr2line`, `stack`).
   * Клієнт налаштовується через змінну середовища `DEBUGINFOD_URLS`:
     ```bash
     export DEBUGINFOD_URLS="https://debuginfod.fedoraproject.org/ https://debuginfod.ubuntu.com/"
     ```
   * Коли GDB або perf завантажує модуль пам'яті з Build ID `f78a2e...`, клієнт спершу перевіряє локальний кеш користувача в каталозі `~/.cache/debuginfod_client/`.
   * Якщо символ відсутній у кеші, `libdebuginfod` виконує HTTP-запит до серверів, зазначених у `DEBUGINFOD_URLS`, завантажує потрібний файл, зберігає його в локальний кеш і повертає налагоджувачу відкритий файловий дескриптор.
   * Налагоджувач миттєво показує повний стек викликів із назвами функцій, типами змінних та підсвічуванням сирцевого коду.

Повний технічний опис маршрутів, кодів помилок та C API викладено у [специфікації REST-ендпоїнтів та C API debuginfod](root:sys-unix/debug-symbols-and-build-id/api-debuginfod-protocol.md).

## 7. Профілювання й трасування на продакшені: perf, eBPF та systemd-coredump

Інфраструктура Build ID та `debuginfod` є фундаментом для сучасного низькооверхедного профілювання та моніторингу виробничих систем.

### Профілювання за допомогою `perf`

Підсистема ядра `perf_events` записує вибірки (*samples*) лічильника команд `rip` у кільцевий буфер пам'яті безпосередньо в контексті переривання таймера або подій процесора. Ядро зберігає лише сирі числові адреси та ідентифікатор простору назв процесу:

```bash
# Запис профілю виконання процесу з частотою 99 Гц
perf record -F 99 -p $(pgrep my_service) -g -- sleep 10
```

Під час генерації звіту утиліта `perf report`:
1. Зчитує записи `PERF_RECORD_MMAP2` із файлу `perf.data`, де зафіксовано відповідність діапазонів пам'яті конкретним файлам ELF та їхні Build ID.
2. Використовує `libdebuginfod` для отримання символів і розгортання вбудованих функцій (*inlined functions*).
3. Будує точні граматичні дерева викликів і теплокарти (*Flame Graphs*).

### eBPF та безперервне профілювання (Continuous Profiling)

Сучасні системи неперервного профілювання в хмарі (наприклад, Parca, Polar Signals, Pyroscope) використовують програми ядра eBPF, які зчитують стек викликів кожні 10 мс через помічники `bpf_get_stackid()`. 

Ядро збирає виключно масив 64-бітних адрес віртуальної пам'яті. Демон у просторі користувача зчитує цей масив, дивиться у `/proc/$PID/maps`, знаходить відображені бінарники, вичитує їхні `.note.gnu.build-id` і надсилає запит до внутрішнього сервера `debuginfod`. Символізація відбувається асинхронно у фоні на окремому сервері аналітики, не створюючи жодного навантаження на робочі вузли кластера.

### Збір аварій через `systemd-coredump`

Коли процес падає, ядро передає образ пам'яті через конвеєр (`/proc/sys/kernel/core_pattern`) демону `systemd-coredump`. Демон:
1. Парсить сегменти `PT_NOTE` та секцію метаданих `NT_FILE` в аварійному дампі.
2. Витягує Build ID виконуваного файлу та всіх завантажених спільних бібліотек.
3. Записує ці відбитки в журнал `journald` у вигляді структурованих полів `COREDUMP_BUILD_ID`.
4. За викликом `coredumpctl debug <PID>` автоматично запускає GDB з активованим debuginfod, дозволяючи відновити повний стек викликів навіть на хості, де не встановлено сирцевий код програми.

## 8. Практичний інструментарій діагностики та крайові випадки

Для швидкого аналізу символьної структури бінарників у терміналі Linux використовують стандартні утиліти:

```bash
# Перевірка наявності та типу Build ID
readelf -n /usr/bin/app | grep "Build ID"

# Перегляд усіх секцій бінарника (пошук .symtab та .debug_*)
readelf -S /usr/bin/app

# Перевірка статусу бінарника (stripped / not stripped)
file /usr/bin/app

# Ручне завантаження DWARF-файлу за відомим Build ID через debuginfod
debuginfod-find debuginfo 7a9f1b2c4d8e3f015a6b7c8d9e0f1a2b3c4d5e6f

# Перевірка зв'язку між очищеним бінарником і його символами
eu-unstrip -n -e /usr/bin/app
```

### Крайові випадки та пастки

1. **Очищення релокаційних об'єктних файлів (`.o`) та статичних бібліотек (`.a`)**: Виконання команди `strip --strip-all` над проміжним об'єктним файлом `file.o` видаляє локальні символи, необхідні компонувальнику для обчислення відносних переходів. Такий файл більше неможливо скомпонувати у фінальну бібліотеку. Для об'єктних файлів слід використовувати виключно `strip --strip-debug` або `strip --strip-unneeded`.
2. **Стиснені секції DWARF**: Сучасні компілятори GCC та Clang підтримують прапорець `-gz=zstd` або `-gz=zlib`, який стискає секції DWARF безпосередньо у бінарнику (секції отримують прапорець `SHF_COMPRESSED` або префікс `.zdebug_`). Старі утиліти розбору ELF без підтримки zstd не зможуть прочитати такі символи.
3. **Розділений DWARF (Split DWARF / `-gsplit-dwarf`)**: Компілятор виносить DWARF безпосередньо під час збірки в окремі файли `.dwo`, а в основний об'єктний файл записує секцію `.debug_addr`. Це прискорює компонування гігантських проєктів, проте вимагає збереження `.dwo`-файлів під час архівування.

Розподіл символів на оперативні таблиці динамічного завантаження та відокремлені сховища DWARF з адресацією через Build ID і службу `debuginfod` забезпечує баланс між мінімальним розміром бінарників у продакшені та миттєвою доступністю повної діагностики під час збоїв.
