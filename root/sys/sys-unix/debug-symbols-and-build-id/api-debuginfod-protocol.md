# 📋 Протокол HTTP REST та клієнтський інтерфейс debuginfod

Мережева служба `debuginfod` стандартизує централізоване поширення налагоджувальних символів, виконуваних бінарників та файлів сирцевого коду за моделлю «запит-відповідь» через протокол HTTP/HTTPS. Клієнтськими застосунками виступають системні налагоджувачі (GDB, LLDB), профілювальники ядра та користувацького простору (perf), аналізатори коректності роботи з пам'яттю (valgrind), середовища динамічного трасування (bpftrace) та сервіси автоматизованого збору аварійних дампів (systemd-coredump). Усі вони взаємодіють із серверами через уніфіковану клієнтську бібліотеку `libdebuginfod`.

---

## 1. Специфікація маршрутів HTTP REST

Сервер `debuginfod` очікує у запитах 160-бітний (20 байтів) або 128-бітний (16 байтів) шістнадцятковий рядок Build ID у нижньому регістрі. Усі маршрути є ідемпотентними операціями `GET` або `HEAD`.

| Маршрут HTTP | Опис запитуваного ресурсу | Формат і MIME-тип відповіді |
|---|---|---|
| `GET /buildid/{buildid}/debuginfo` | Окремий ELF-файл із повними секціями DWARF (`.debug_*`) та повною таблицею символів `.symtab` для вказаного відбитка збірки | `application/octet-stream` (сирий бінарний потік ELF) |
| `GET /buildid/{buildid}/executable` | Повний виконуваний бінарник або динамічна бібліотека. Використовується, коли налагоджувачу чи дизасемблеру потрібен машинний код секцій `.text` | `application/octet-stream` (виконуваний ELF) |
| `GET /buildid/{buildid}/source/{path}` | Текстовий файл сирцевого коду. Параметр `{path}` — це канонічний абсолютний або відносний шлях до файлу, зафіксований у DWARF-секції `.debug_line` | `text/plain` або `application/octet-stream` |
| `GET /buildid/{buildid}/section/{name}` | Окрема вилучена ELF-секція (наприклад, `.debug_frame`, `.eh_frame` або індексна таблиця `.gdb_index`) | `application/octet-stream` |

### Заголовки HTTP-відповідей сервера

Під час успішної віддачі ресурсу сервер додає розширені HTTP-заголовки, що описують джерело походження артефакту:

* `X-DEBUGINFOD-SIZE`: числовий розмір розпакованого цільового файлу в байтах. Дозволяє клієнту перевірити доступний простір на диску до початку повного завантаження.
* `X-DEBUGINFOD-FILE`: оригінальне ім'я файлу в архіві або файловій системі сервера (наприклад, `libc-2.38.so.debug`).
* `X-DEBUGINFOD-ARCHIVE`: назва архіву чи пакета, з якого динамічно видобуто ресурс (наприклад, `glibc-debuginfo-2.38-1.fc39.x86_64.rpm` або `libssl3_3.0.10-1_amd64.deb`).
* `Content-Type`: тип вмісту (`application/octet-stream` для бінарників ELF або `text/plain` для сирцевих текстів).
* `Content-Length`: розмір переданого HTTP-тіла в байтах.
* `Cache-Control`: політика кешування (за замовчуванням `public, max-age=604800`, оскільки артефакти з однаковим Build ID є абсолютно незмінними за своєю природою).

### Коди стану HTTP та негативне кешування

* `200 OK`: ресурс успішно знайдено, бінарний або текстовий потік передається клієнту.
* `404 Not Found`: ресурс із вказаним Build ID або зазначений файл сирцевого коду відсутній в індексі сервера. Клієнтська бібліотека `libdebuginfod` фіксує цю відповідь у локальному кеші шляхом створення порожнього файлу-маркера (негативний кеш), що запобігає повторним мережевим запитам під час наступних запусків налагоджувача.
* `503 Service Unavailable`: сервер перевантажений або виконує фонову повну переіндексацію сховищ. Клієнт у цьому випадку повторює спробу пізніше або звертається до наступного сервера у списку.

## 2. Федерація серверів і проксування запитів

Сервери `debuginfod` підтримують багаторівневу ієрархічну федерацію. Локальний або корпоративний сервер, встановлений усередині захищеного контуру компанії, налаштовується прапорцем upstream-перенаправлення:

```bash
debuginfod -U https://debuginfod.fedoraproject.org/ \
           -U https://debuginfod.ubuntu.com/ \
           -d /var/cache/debuginfod/corp.sqlite \
           -F /var/builds/internal-services/
```

Коли клієнт запитує Build ID, відсутній у внутрішніх сховищах `/var/builds/`, локальний сервер автоматично опитує вищестоящі репозиторії дистрибутивів, кешує отриманий результат у своїй базі даних і повертає файл клієнту. Це знижує навантаження на зовнішні мережеві канали та усуває потребу прямого виходу в інтернет для робочих станцій розробників.

Для захисту від циклічного проксування сервери додають до HTTP-запитів заголовок `X-Forwarded-For` та перевіряють глибину ланцюжка перенаправлень.

## 3. Змінні середовища клієнта libdebuginfod

Поведінка клієнтської бібліотеки `libdebuginfod` повністю контролюється змінними середовища процесу. Будь-яка утиліта, скомпонована з `libdebuginfod`, автоматично зчитує ці налаштування під час ініціалізації сесії.

| Змінна середовища | Тип і значення за замовчуванням | Повна технічна дія |
|---|---|---|
| `DEBUGINFOD_URLS` | Рядок URL, розділених пробілами | Перелік адрес серверів debuginfod (наприклад, `"https://debuginfod.fedoraproject.org https://debuginfod.archlinux.org"`). Запити до серверів виконуються паралельно з використанням механізму неблокуючого введення-виведення. |
| `DEBUGINFOD_CACHE_PATH` | Шлях до каталогу (`$HOME/.cache/debuginfod_client`) | Каталог зберігання локального кешу. Структура підкаталогів: `{cache_path}/{buildid}/{debuginfo,executable,source/...}`. |
| `DEBUGINFOD_TIMEOUT` | Ціле число, секунди (замовчування: `90`) | Максимальний інтервал очікування відповіді від віддаленого сервера. Значення `0` вимикає будь-яку мережеву активність і обмежує пошук лише локальним кешем. |
| `DEBUGINFOD_PROGRESS` | Прапорець `1` або `0` | Вмикає відображення індикатора прогресу завантаження у терміналі (часто використовується інтерактивним GDB). |
| `DEBUGINFOD_VERBOSE` | Ціле число `0`..`3` | Рівень деталізації діагностичного протоколювання `libdebuginfod` у системний потік `stderr`. |
| `DEBUGINFOD_MAXSIZE` | Число байтів (суфікси `K`, `M`, `G`) | Поріг розміру файлу: якщо заголовок `X-DEBUGINFOD-SIZE` перевищує це значення, клієнт миттєво перериває з'єднання, захищаючи диск від переповнення. |
| `DEBUGINFOD_MAXTIME` | Ціле число, секунди (замовчування: `604800`, 7 днів) | Максимальний час життя кешованого файлу. Файли, до яких не зверталися довше цього терміну, видаляються під час автоматичного очищення. |
| `DEBUGINFOD_HEADERS_FILE` | Абсолютний шлях до текстового файлу | Дозволяє передавати додаткові HTTP-заголовки авторизації (наприклад, `Authorization: Bearer <token>` або `X-API-Key`) під час роботи з приватними захищеними реєстрами пакетів. |

## 4. Програмний інтерфейс C (libdebuginfod C API)

Заголовковий файл: `<elfutils/debuginfod.h>`.  
Компонування: `-ldebuginfod`.

Бібліотека надає функції пошуку артефактів за відбитком Build ID. Усі функції повертають відкритий файловий дескриптор `fd >= 0`, готовий для системних викликів `read()` або `mmap()`, або від'ємне число `-errno` у разі помилки.

```c
#include <elfutils/debuginfod.h>

/* Створення дескриптора сесії клієнта */
debuginfod_client *debuginfod_begin(void);

/* Звільнення ресурсів сесії клієнта */
void debuginfod_end(debuginfod_client *client);

/* Прив'язка довільних контекстних даних користувача */
void debuginfod_set_user_data(debuginfod_client *client, void *data);
void *debuginfod_get_user_data(debuginfod_client *client);

/* Реєстрація функції зворотного виклику для відстеження прогресу */
typedef int (*debuginfod_progressfn_t)(debuginfod_client *client, long a, long b);
void debuginfod_set_progressfn(debuginfod_client *client, debuginfod_progressfn_t fn);

/* Пошук DWARF-файлу символів за Build ID */
int debuginfod_find_debuginfo(debuginfod_client *client,
                             const unsigned char *build_id,
                             int build_id_len,
                             char **path);

/* Пошук оригінального скомпільованого бінарника за Build ID */
int debuginfod_find_executable(debuginfod_client *client,
                              const unsigned char *build_id,
                              int build_id_len,
                              char **path);

/* Пошук сирцевого файлу за Build ID та шляхом */
int debuginfod_find_source(debuginfod_client *client,
                          const unsigned char *build_id,
                          int build_id_len,
                          const char *filename,
                          char **path);

/* Пошук окремої секції ELF за Build ID та назвою */
int debuginfod_find_section(debuginfod_client *client,
                           const unsigned char *build_id,
                           int build_id_len,
                           const char *section,
                           char **path);
```

### Семантика параметрів та керування пам'яттю

1. `build_id`: вказівник на сирий масив байтів або шістнадцятковий ASCII-рядок відбитка збірки.
2. `build_id_len`: довжина масиву в байтах. Якщо передано значення `0`, функція розглядає `build_id` як завершений нулем текстовий рядок шістнадцяткових цифр.
3. `path`: адреса покажчика на рядок (`char **`). Якщо передано ненульову адресу, функція виділяє буфер пам'яті через системний виклик `malloc()` і записує туди абсолютний шлях до цільового файлу у локальному кеші. Викликач зобов'язаний звільнити цю пам'ять за допомогою виклику `free()`.
4. `fn` (progress callback): функція викликається періодично під час передачі даних. Параметр `a` позначає кількість завантажених байтів, а `b` — загальний очікуваний розмір. Якщо функція повертає ненульове значення, бібліотека негайно анулює HTTP-запит і повертає помилку `-ECANCELED`.
5. **Потокобезпечність**: Об'єкт `debuginfod_client` не є потокобезпечним. У багатопотокових програмах кожен робочий потік зобов'язаний створити власний екземпляр через `debuginfod_begin()` або синхронізувати виклики через м'ютекс.

## 5. Внутрішня структура бази даних та механізм індексації

Серверний демон `debuginfod` будує реляційну базу даних на базі рушія SQLite (файл `index.sqlite`). База оптимізована для швидкого пошуку за фіксованими 40-символьними рядками Build ID:

1. **Таблиця `buildids`**: Зіставляє унікальний рядок Build ID із числовим ідентифікатором файлу, типом ресурсу (`debuginfo`, `executable`, `source`) та внутрішнім зміщенням, якщо об'єкт запаковано всередині архіву RPM або DEB.
2. **Таблиця `files`**: Зберігає повні шляхи до фізичних файлів на диску, час останньої модифікації (`mtime`) та номер іноду (`inode`). Завдяки цьому сервер під час періодичного пересканування перевіряє лише змінені файли без повторного повного парсингу гігабайтних сховищ.
3. **Таблиця `archives`**: Індексує складові частини архівів (`.tar`, `.cpio`, `.deb`, `.rpm`), зберігаючи таблицю зміщень стиснених потоків. Це дозволяє серверу за лічені мілісекунди видобувати конкретний файл `.debug` без повного розпакування 500-мегабайтного пакунка на диск.

## 6. Опції серверного демона debuginfod та метрики Prometheus

Серверний демон сканує каталоги з бінарниками, сховища пакетів RPM/DEB та архіви, формуючи локальний реляційний індекс SQLite:

```bash
debuginfod -p 8002 \
           -d /var/cache/debuginfod/index.sqlite \
           -c 8 \
           -t 300 \
           -F -R /srv/repos/fedora/ /srv/repos/custom/ \
           -Z .tar.gz -Z .tar.xz \
           -v
```

* `-p PORT`: порт прослуховування TCP для вхідних HTTP-з'єднань (типово `8002`).
* `-d DB_PATH`: абсолютний шлях до файлу реляційної бази даних SQLite.
* `-c NUM_THREADS`: кількість робочих потоків пулу для паралельного сканування та обробки HTTP-запитів.
* `-t SECONDS`: період періодичного пересканування вказаних каталогів у секундах (за замовчуванням `300` с).
* `-F`: активація сканування звичайних файлових каталогів із розпакованими бінарниками.
* `-R`: рекурсивний розбір та індексація архівів пакунків RPM та DEB без їх попереднього розпакування на диск.
* `-Z EXT`: автоматична індексація стиснених архівів із зазначеними розширеннями.
* `-v`: докладний журнал подій індексації та HTTP-трафіку.

Крім того, сервер `debuginfod` містить вбудований ендпоїнт телеметрії `GET /metrics`, який експортує показники продуктивності у форматі Prometheus: кількість оброблених запитів (`http_requests_total`), тривалість сканування сховищ (`scanned_bytes_total`), розмір індексу SQLite та кількість знайдених відбитків Build ID.
