# 📜 Історія розвитку P2P DMA: від специфічних хаків до стандартизації в ядрі Linux

Технологія прямого передавання даних між периферійними пристроями на шині PCI без участі центрального процесора та оперативної пам'яті пройшла складний шлях від вузькоспеціалізованих апаратних експериментів до строго стандартизованої підсистеми ядра Linux. У цьому нарисі розглянуто історичні передумови появи Peer-to-Peer DMA, апаратні обмеження перших поколінь PCIe, появу буферів CMB в специфікації NVMe та еволюцію програмної підтримки в ядрі Linux від проприєтарних драйверних хаків до офіційного підсистемного фреймворку `pci-p2pdma`.

## Ранні дні: PCI 2.2, FireWire та AGP

Перші ідеї передавання даних безпосередньо між пристроями виникли ще на паралельній шині PCI у пізніх 1990-х роках. Специфікація PCI 2.2 передбачала можливість для пристрою в режимі Bus Master ініціювати транзакцію читання або запису пам'яті (Memory Read/Write), де адресою призначення виступав діапазон BAR іншого пристрою на тій самій шині. Утім, на паралельній шині PCI всі пристрої ділили спільні лінії даних та адреси, а арбітраж шини на материнській платі часто викликав колізії, що робило P2P-передачі нестабільними.

Паралельно з цим інтерфейс IEEE 1394 (FireWire) унаслідував апаратну підтримку Direct Memory Access між пристроями за задумом Apple та Texas Instruments. Дві відеокамери FireWire могли передавати потік даних безпосередньо між собою. Проте з поширенням шини PCI Express (PCIe) у 2003 році топологія змінилася з розшареної шини на високошвидкісні послідовні з'єднання «точка-точка».

Шина PCIe ввела поняття Transaction Layer Packets (TLP) та маршрутизацію за адресою. Теоретично будь-який пристрій PCIe міг відправити TLP запиту запису пам'яті (`Memory Write`), адресований у діапазон BAR іншого пристрою. Однак на практиці виробники чіпсетів та процесорів протягом першого десятиліття PCIe ставилися до P2P-трафіку як до потенційного джерела збоїв або загрози безпеці.

## Проблема Access Control Services (ACS) та "Root Complex Trap"

У середині 2000-х років, із поширенням віртуалізації (KVM, Xen, VMware ESXi) та шинних IOMMU (Intel VT-d, AMD-Vi), у специфікацію PCIe PCI-SIG було додано розширення Access Control Services (ACS). Метою ACS було забезпечення суворої ізоляції між віртуальними машинами.

За замовчуванням ACS перехоплював усі TLP-пакети між периферійними пристроями та примусово направляв їх вгору по дереву PCIe до Root Complex (функція ACS Direct Translation та P2P Request Redirect). Це робилося для того, щоб IOMMU перевірив права доступу пристрою до вказаної фізичної адреси.

Однак більшість тогочасних процесорів (зокрема процесори Intel Core та Xeon до архітектури Nehalem/Westmere) не вміли перенаправляти TLP-пакети назад у шину PCIe, якщо вони надходили від одного з портів Root Complex і призначалися іншому. Отримавши P2P-пакет у Root Complex, процесор просто повертав помилку Unsupported Request (UR) або мовчки скидав пакет. У результаті будь-яка спроба виконати P2P DMA між двома пристроями на різних портах Root Complex завершувалася крахом системного драйвера або "зависанням" шини PCIe.

Єдиним надійним шляхом для P2P DMA лишалося підключення обох пристроїв під один зовнішній PCIe Switch (наприклад, чіпи PLX/Broadcom), який перенаправляв TLP локально між своїми Downstream-портами до того, як пакет досягав Root Complex.

## Ера GPUDirect v1 та проприєтарні хаки

Зі зростанням популярності обчислень на графічних процесорах (GPGPU, NVIDIA CUDA) у 2010–2012 роках, вимога швидкого обміну даними між мережевими адаптерами InfiniBand та відеокартами стала критичною для суперкомп'ютерів.

У 2011 році компанія NVIDIA представила перше покоління технології GPUDirect (GPUDirect v1). Вона дозволяла двом GPU на одній шині PCIe ділитися буферами пам'яті через копіювання в запінених сторінках хоста. У GPUDirect v2 з'явилася підтримка прямого Peer-to-Peer між GPU під керуванням CUDA. Однак для роботи з мережевими картами InfiniBand (Mellanox) драйвери змушені були використовувати приватні, недокументовані API ядра Linux.

Розробники сторонніх драйверів вдавалися до небезпечних дій:
1. Ручна маніпуляція регігістрами PCIe BAR для отримання фізичних адрес пам'яті I/O.
2. Підробка структур `struct page` або використання хаку `page_to_pfn()` на адресах MMIO, що призводило до краху ядра (Kernel Panic) при спробі системних підсистем (типу сторінкового кешу або dma-mapping) звернутися до цих сторінок як до звичайної RAM.
3. Примусове вимкнення бітів ACS у конфігураційному просторі PCIe через утиліти на кшталт `setpci`, що порушувало ізоляцію IOMMU та створювало вразливості в середовищах віртуалізації.

Репозиторії kernels містили десятки конкуруючих і несумісних між собою виправлень ("out-of-tree patches"), які намагалися прокинути DMA-буфери між відеокартами та мережевими адаптерами.

## Поява NVMe CMB та PMR

У 2015 році в специфікацію NVMe 1.2 було включено революційне доповнення — Controller Memory Buffer (CMB). Виробники накопичувачів NVMe почали розміщувати на платі SSD невеликий обсяг високошвидкісної статичної пам'яті (SRAM) або DRAM, яка експонувалася безпосередньо через Base Address Register (BAR 2 або BAR 4) пристрою PCIe.

CMB дозволяв хосту або іншим пристроям розміщувати черги подання команд (Submission Queues) та буфери даних прямо на самому SSD. А в специфікації NVMe 1.4 (2019 рік) з'явився Persistent Memory Region (PMR) — енергонезалежний регіон пам'яті на SSD, доступний через BAR.

Виникла нагальна потреба: як дозволити мережевій карті SmartNIC або GPU записувати дані безпосередньо в CMB NVMe-накопичувача через стандартні API ядра Linux, без специфічних драйверів під кожного конкретного вендора?

## Розробка підсистеми `pci-p2pdma` у ядрі Linux

У 2017 році інженер Логан Ганторп (Logan Gunthorpe) із компанії Microsemi (пізніше Microchip) запропонував фундаментальне вирішення проблеми. Він розробив і подав до розсилки Linux Kernel Mailing List (LKML) патчсет під назвою **PCIe Peer-to-Peer DMA framework**.

Головні ідеї підсистеми `pci-p2pdma`:
1. **Інтеграція з `ZONE_DEVICE`:** Використання інфраструктури `ZONE_DEVICE` у менеджері пам'яті Linux (MM). Пам'ять PCIe BAR (CMB, PMR, VRAM) реєструється в ядрі з типом `MEMORY_DEVICE_PCI_P2PDMA`. Для кожної 4-кілобайтної сторінки MMIO створюється справжня структура `struct page`. Це дозволило передавати ці сторінки в існуючі підсистеми ядра (`scatterlist`, `bio`, `io_uring`) без ризику зламати ядерну логіку перевірки типів пам'яті.
2. **Алгоритм автоматичного визначення топології:** Створення функції `pci_p2pdma_distance_many()`, яка при підключенні двох пристроїв аналізує дерево PCIe, перевіряє стан прапорців ACS на всіх проміжних мостах та обчислює, чи можливий P2P DMA між пристроями.
3. **Стандартизоване мапування:** Створення спец-функції `pci_p2pdma_map_sg()`, яка замінює `dma_map_sg()`. Якщо пристрої знаходяться під одним PCIe Switch, функція просто підставляє фізичні адреси BAR (Bus Address) без задіяння IOMMU.

Патчсет Логана Ганторпа було офіційно прийнято в ядро **Linux 4.20** у грудні 2018 року.

## Подальша еволюція: Linux 5.x та 6.x

Після виходу Linux 4.20 підсистема P2PDMA постійно вдосконалювалася:
- **Linux 5.3–5.8:** Додано підтримку P2PDMA в цільову підсистему NVMe over Fabrics (NVMe-oF Target). Мережева карта RDMA отримала можливість записувати дані з мережі безпосередньо в CMB локального NVMe SSD.
- **Linux 5.19:** Додано підтримку P2P DMA у підсистему `dma-buf`, що дозволило обмінюватися буферами пам'яті між різними GPU та прискорювачами AI у системі.
- **Linux 6.2:** Логан Ганторп та розробники з NVMe/PCIe робочої групи додали підтримку P2PDMA для блокового рівня (Block Layer) та підсистеми `io_uring`. З цього моменту програми простору користувача отримали можливість виконувати прямому P2P I/O між NVMe SSD та GPU без проміжних хаків, використовуючи стандартні системні виклики.

Завдяки стандартизації P2PDMA в Linux, сучасні технології на кшталт NVIDIA GPUDirect Storage (GDS) та AMD ROCm Direct RDMA перейшли від ламких проприєтарних модулів ядра до чистої роботи поверх загальносистемного фреймворку `pci-p2pdma`.
