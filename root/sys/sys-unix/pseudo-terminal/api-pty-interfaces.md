# 📋 Що стирчить назовні: виклики й `ioctl` псевдотермінала

Довідка за контрактом: якими викликами відкривають пару кінців, що кожен із них робить насправді під обгорткою, які `ioctl` ядро дає понад звичайний термінал, які ручки має файлова система `devpts` і де стеля на кількість пар. Питання, на яке ця довідка відповідає найчастіше, звучить так: чому потрібен саме цей порядок дій — і що буде, коли якийсь крок пропустити.

## Чотири виклики, якими відкривають пару

```c
#define _XOPEN_SOURCE 600
#include <stdlib.h>    /* grantpt, unlockpt, ptsname, ptsname_r */
#include <fcntl.h>

int   posix_openpt(int flags);
int   grantpt(int fd);
int   unlockpt(int fd);
char *ptsname(int fd);                                 /* MT-Unsafe race:ptsname */
int   ptsname_r(int fd, char *buf, size_t buflen);     /* потребує _GNU_SOURCE */
```

| виклик | що робить під обгорткою | помилки |
|---|---|---|
| `posix_openpt` | у Linux — рівно `open("/dev/ptmx", flags)` | усі коди `open` (`EMFILE`, `ENFILE`, `EACCES`) плюс `ENOSPC` від драйвера |
| `grantpt` | у сучасному Linux — нічого: власника й права `0620` вузол дістає при створенні | `EBADF`, `EINVAL`, `EACCES` |
| `unlockpt` | `ioctl(fd, TIOCSPTLCK, &(int){0})` | `EBADF`, `EINVAL`; від ядра — `ENOTTY` |
| `ptsname` | `ioctl(fd, TIOCGPTN, &n)` і склеювання рядка `/dev/pts/n` у статичному буфері бібліотеки | `ENOTTY` |
| `ptsname_r` | те саме, але у ваш буфер | `ENOTTY`, `ERANGE` |

Стандарт визнає для `flags` лише два значення — `O_RDWR` і `O_NOCTTY`. У Linux проходить будь-який прапорець `open`, бо це і є `open`; на цьому тримається звичка писати `O_RDWR | O_NOCTTY | O_CLOEXEC`, хоч переносною вона не є.

`grantpt` виглядає ритуалом і ним майже став: `devpts` віддає вузол потрібному власникові ще при створенні, тож функції нема чого правити. Історія її була гучнішою — до glibc 2.33 бібліотека тримала для неї допоміжну програму `pt_chown` із бітом `setuid`, і саме її звідти прибрали. Викидати виклик із коду все одно не варто: він переносний, а на інших системах усе ще щось робить.

Перевіряти результат `ptsname_r` треба обережно: він **повертає код помилки, а не −1**, і glibc заразом кладе той самий код у `errno`. Звична форма `if (ptsname_r(...) < 0)` тихо пропустить помилку повз себе.

```c
#define _XOPEN_SOURCE 600
#include <fcntl.h>
#include <stdlib.h>
#include <sys/ioctl.h>
#include <unistd.h>

/* Повертає дескриптор ведучого кінця; ім'я підлеглого кладе в name. */
int pty_open(char *name, size_t n) {
    int m = posix_openpt(O_RDWR | O_NOCTTY | O_CLOEXEC);
    if (m < 0) return -1;
    if (grantpt(m) < 0 || unlockpt(m) < 0) goto fail;
    if (ptsname_r(m, name, n) != 0) goto fail;
    return m;
fail:
    close(m);
    return -1;
}
```

Замок, який знімає `unlockpt`, стоїть із самого створення пари й перевіряється при **кожному** способі відкрити підлеглий кінець. Забули `unlockpt` — і `open` за іменем, і `ioctl(TIOCGPTPEER)` повернуть `EIO`, причому повідомлення жодним чином не натякне на замок.

## Обгортка libutil

```c
#include <pty.h>            /* збирати з -lutil */
#include <utmp.h>           /* login_tty */

int   openpty(int *amaster, int *aslave, char *name,
              const struct termios *termp, const struct winsize *winp);
pid_t forkpty(int *amaster, char *name,
              const struct termios *termp, const struct winsize *winp);
int   login_tty(int fd);
```

`openpty` — це весь чотирикроковий ритуал плюс `open` підлеглого кінця; `termp` і `winp` дозволяють одразу покласти [початковий стан термінала](root:sys-unix/tty-and-termios) й розмір вікна, `NULL` лишає типові. `login_tty` виконує три дії, які інакше пишуть руками: `setsid`, `ioctl(TIOCSCTTY)` і `dup2` на дескриптори 0, 1, 2. `forkpty` = `openpty` + `fork` + `login_tty` у дитині; повертає нуль дитині й `pid` батькові.

Аргумент `name` в обох — задокументована пастка: жодна з функцій не знає розміру вашого буфера й нічого не перевіряє, тож туди передають `NULL`, а ім'я, якщо треба, беруть окремим `ptsname_r`. Помилки скупі: `openpty` віддає `ENOENT`, коли вільних пар не лишилося, `forkpty` — те, чим завершився `openpty` або `fork`.

## `ioctl` понад звичайний термінал

Усі запити з таблиці йдуть [керуючим каналом до драйвера](root:sys-unix/ioctl-interface) й адресовані **ведучому** кінцю, крім чотирьох останніх рядків — ті стосуються будь-якого термінала.

| запит | аргумент | що робить | з якої версії |
|---|---|---|---|
| `TIOCGPTN` | `unsigned int *` | номер підлеглого кінця | |
| `TIOCSPTLCK` | `const int *` | нуль знімає замок, ненуль ставить назад | |
| `TIOCGPTLCK` | `int *` | прочитати стан замка | Linux 3.8 |
| `TIOCGPTPEER` | `int` **за значенням**: прапорці як в `open` | новий дескриптор підлеглого кінця, повз імена | Linux 4.13 |
| `TIOCPKT` | `const int *` | увімкнути / вимкнути пакетний режим | |
| `TIOCGPKT` | `int *` | чи ввімкнено пакетний режим | Linux 3.8 |
| `TIOCSIG` | `int` за значенням: номер сигналу | послати сигнал передній групі на тому боці | |
| `TIOCSCTTY` | `int` за значенням: `0` або `1` | зробити цей термінал керуючим для сеансу | |
| `TIOCNOTTY` | — | відпустити керуючий термінал | |
| `TIOCGWINSZ` / `TIOCSWINSZ` | `struct winsize *` | розмір вікна — спільний на всю пару | |
| `TIOCSTI` | `const char *` | покласти один байт у вхідну чергу термінала | обмежено з Linux 6.2 |

`TIOCGPTPEER` вибивається з ряду двічі: аргумент передають числом, а не вказівником, і повертає він не нуль, а сам дескриптор. Це єдиний спосіб дістати підлеглий кінець, не називаючи його на ім'я.

> 🔧 **Навіщо це.** Ім'я `/dev/pts/3` має сенс лише в тому [просторі імен монтування](root:sys-unix/namespaces), де живе потрібний примірник `devpts`. Коли супервізор готує термінал для контейнера, шлях від `ptsname` він розв'язує **у себе**, а вміст `/dev/pts` під ним контролює вже недовірений бік — і замість символьного пристрою там може виявитися посилання куди завгодно. `TIOCGPTPEER` знімає питання цілком: ядро видає дескриптор напарника з дескриптора ведучого кінця, у дереві імен нічого не шукаючи. Ціна одна — ядро від 4.13; тому середовища запуску контейнерів пробують цей запит і мовчки відкочуються на `ptsname`, коли ядро відповідає `ENOTTY` (так виглядає невідомий йому `ioctl`).

`TIOCSCTTY` вимагає, щоб той, хто кличе, був **лідером сеансу без керуючого термінала**, — звідси обов'язковий `setsid` перед ним. Якщо термінал уже керуючий для іншого [сеансу](root:sys-unix/sessions-and-process-groups), приходить `EPERM`; аргумент `1` дозволяє його **відібрати**, але лише власникові `CAP_SYS_ADMIN`, і тоді всі, для кого він був керуючим, його втрачають. `TIOCNOTTY` робить зворотне, і в лідера сеансу має гучний побічний ефект: групі переднього плану летять `SIGHUP` і `SIGCONT`, а керуючого термінала позбувається весь сеанс.

Числа за іменами наводимо лише для читання висновку `strace`, не для коду: на x86 і ARM `TIOCSCTTY` — `0x540E`, `TIOCNOTTY` — `0x5422`, `TIOCGWINSZ` — `0x5413`, `TIOCSWINSZ` — `0x5414`, `TIOCSTI` — `0x5412`, `TIOCPKT` — `0x5420`, `TIOCGPTPEER` — `0x5441`, а `TIOCGPTN` і `TIOCSPTLCK` закодовані як `_IOR('T', 0x30, unsigned int)` і `_IOW('T', 0x31, int)`, тобто `0x80045430` і `0x40045431`. На MIPS, SPARC, Alpha та PA-RISC ці ж імена мають зовсім інші значення.

`TIOCSIG` — єдиний з переліку, якого немає в довідкових сторінках; він дає ведучому кінцю послати сигнал передній групі підлеглого, не проганяючи байт крізь лінійну дисципліну. Дозволено рівно три сигнали — `SIGINT`, `SIGQUIT`, `SIGTSTP`, — усе інше приходить назад як `EINVAL`. Потрібен він там, де сигнал прилетів іззовні, а не з клавіатури: наприклад, коли керівник контейнера дістав `SIGINT` сам і мусить передати його всередину.

`TIOCSTI` з Linux 6.2 вимагає `CAP_SYS_ADMIN` — доки не ввімкнено [системну ручку](root:sys-unix/sysctl-tunables) `dev.tty.legacy_tiocsti`, яка повертає стару поведінку. Єдина помилка, яку описує документація, — `EPERM`.

Розмір вікна в пари **один на двох**: `TIOCSWINSZ` на будь-якому з кінців кладе ті самі числа обом і будить `SIGWINCH` у передніх групах обох боків. Дві тонкощі звідси випливають одразу. Перша: якщо новий розмір збігається зі старим до останнього поля, ядро не робить нічого — жодного сигналу не буде, і програма, яка перевстановлює той самий розмір заради перемальовування, чекатиме марно. Друга: поля `ws_xpixel` і `ws_ypixel` теж беруть участь у цьому порівнянні, тож зайве сміття в них перетворює «той самий розмір» на «інший».

## Пакетний режим

`TIOCPKT` міняє формат того, що читається з ведучого кінця: тепер **кожен** `read` віддає щонайменше один службовий байт попереду.

```
без пакетного режиму:   d a t a . . .
з пакетним режимом:     0x00 d a t a . . .   ← дані з нульовим префіксом
                        0x02                 ← сам лише байт стану, даних нема
```

| байт стану | значення | що сталося на підлеглому кінці |
|---|---|---|
| `TIOCPKT_DATA` | 0 | далі йдуть звичайні дані |
| `TIOCPKT_FLUSHREAD` | 1 | вхідну чергу термінала скинуто |
| `TIOCPKT_FLUSHWRITE` | 2 | вихідну чергу термінала скинуто |
| `TIOCPKT_STOP` | 4 | вивід спинено (`^S`) |
| `TIOCPKT_START` | 8 | вивід поновлено (`^Q`) |
| `TIOCPKT_NOSTOP` | 16 | символи «спинити / пустити» більше не `^S`/`^Q` |
| `TIOCPKT_DOSTOP` | 32 | вони знову `^S`/`^Q` |
| `TIOCPKT_IOCTL` | 64 | на підлеглому кінці змінили `termios` (`tcsetattr` і подібне) |

Байти стану без даних видно як **позачергову умову**: `select` чекає на них у наборі винятків, `poll` — за подією `POLLPRI`. Придумали це для `rlogin`, якому треба було знати про зупинку виведення на тому боці, щоб не гнати даремно байти в мережу; сьогодні тим самим користуються термінальні мультиплексори, аби вчасно скинути власний буфер.

## `devpts`: параметри монтування й межі

| параметр | типове | що робить |
|---|---|---|
| `uid=`, `gid=` | `0`, `0` | власник і група нових вузлів `/dev/pts/N` |
| `mode=` | `0600` | права нових вузлів |
| `ptmxmode=` | `0000` | права вузла `/dev/pts/ptmx` усередині примірника |
| `max=` | абсолютна стеля мінорів (2²⁰) | скільки пар дозволено цьому примірникові |
| `newinstance` | — | історичний; ядро розбирає його й не робить нічого |

Дистрибутиви монтують `devpts` із `gid=5,mode=620`: група `tty`, право писати — групі. Саме на цьому [доступі за групою](root:sys-unix/device-access-groups) тримається `write` та `wall`, а `mesg n` знімає з вузла біт запису.

`ptmxmode=0000` виглядає дивно, доки не згадати, що кожне монтування створює власний вузол `/dev/pts/ptmx`, а звичний `/dev/ptmx` (символьний пристрій 5:2) лежить окремо. Хто відв'язує `/dev/ptmx` від глобального вузла — робить його посиланням на `pts/ptmx` і тоді мусить дати `ptmxmode=0666`, інакше відкрити не зможе ніхто.

Рядок про `newinstance` варто прочитати уважно, бо документація тут відстала. Колись цей параметр вмикав окрему нумерацію й вимагав `CONFIG_DEVPTS_MULTIPLE_INSTANCES` — і `mount(8)` досі так пише. Насправді кожне монтування `devpts` тепер самостійне без жодних умов: у `fs/devpts/inode.c` розбір цього імені складається з одного `break`. Параметр лишили, щоб не ламати старі рядки монтування.

Межі системні, і їх три — усі в [`/proc/sys/kernel/pty/`](root:sys-unix/sysctl-tunables):

```
kernel.pty.max     = 4096   загальна стеля на всю систему
kernel.pty.reserve = 1024   з них залишено початковому простору імен
kernel.pty.nr               скільки зайнято зараз (лише читання)
```

`reserve` — не резерв «про запас», а захист від вичерпання: примірники поза початковим простором імен не можуть узяти останню тисячу пар, тож контейнер, що масово плодить термінали, не залишить хост без жодного. Коли пари скінчилися, `posix_openpt` повертає `ENOSPC` — код, який легко сплутати з нестачею місця на диску.

Що з цього справді чинне на живій машині, показують три команди: `findmnt -no OPTIONS /dev/pts` віддає [параметри монтування](root:sys-unix/mount-model) як їх бачить ядро, `stat -c '%U %G %a' /dev/pts/0` — кому дістався щойно створений вузол, `cat /proc/sys/kernel/pty/nr` — скільки пар зайнято просто зараз.

## Коди помилок, які плутають

| код | звідки | що насправді означає |
|---|---|---|
| `ENOTTY` | будь-який `ioctl`, `ptsname` | дескриптор дійсний, але за ним не той тип термінала (часто — підлеглий кінець замість ведучого) |
| `EINVAL` | `grantpt`, `unlockpt`, `TIOCSIG` | дескриптор не від ведучого кінця; для `TIOCSIG` — сигнал не з трьох дозволених |
| `EIO` | `open` підлеглого кінця, `TIOCGPTPEER` | замок не знято `unlockpt` — або напарник уже закритий |
| `EIO` | `read` з ведучого кінця | підлеглий кінець закрили; POSIX тут дозволяє й нуль, тож переносний цикл мусить приймати обидві відповіді |
| `EPERM` | `TIOCSCTTY`, `TIOCSTI` | термінал уже керуючий для чужого сеансу; для `TIOCSTI` — бракує `CAP_SYS_ADMIN` |
| `ENOSPC` | `posix_openpt` | вичерпано `kernel.pty.max` або `max=` цього примірника |
| `EAGAIN` | `read` з ведучого кінця | з `O_NONBLOCK`: даних поки немає, кінець живий |

Три перші рядки варто тримати в голові разом, бо різницю між ними видно лише зсередини. `ENOTTY` каже «не той пристрій», `EINVAL` — «не той кінець», `EIO` — «пристрій той, але відкривати його зараз не можна». Жоден із трьох не згадає слова «замок», хоча саме він стоїть за доброю половиною випадків `EIO`.

## Старі імена BSD

До клон-пристрою `/dev/ptmx` пари не створювали, а перебирали серед наперед зроблених вузлів: ведучі звалися `/dev/pty[p-za-e][0-9a-f]`, підлеглі — `/dev/tty[p-za-e][0-9a-f]`. Шістнадцять літер (`p`…`z`, далі `a`…`e`) на шістнадцять шістнадцяткових цифр дають рівно 256 пар — те саме число досі стоїть типовим у `CONFIG_LEGACY_PTY_COUNT`.

Сам механізм лишився параметром збирання `CONFIG_LEGACY_PTYS`, і власна довідка ядра радить його вимкнути. Причина не в кількості, а в способі пошуку: вільну пару шукали циклом `open` по всіх іменах поспіль, а між невдалим `open` конкурента й вдалим вашим завжди лишалася шпарина. Права теж доводилося роздавати всім 256 вузлам одразу й чистити їх після кожного користувача. У сучасних дистрибутивах цих файлів немає взагалі, і зустріти їх можна хіба в старих сценаріях та в коді, який ще пам'ятає перебір.
