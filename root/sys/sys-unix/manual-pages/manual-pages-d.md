- [POSIX: що саме стандартизовано](root:sys-unix/posix-standard) — стандартні інтерфейси C, утиліти оболонки та переносність викликів.

Коли системний розробник намагається з'ясувати точну сигнатуру, поведінку під час переривання сигналом або коди помилок функції зчитування даних із файлового дескриптора і вводить у терміналі команду `man read`, екран відображає документацію вбудованої команди командної оболонки `read [-ers] [-u fd] [name ...]`. Замість опису низькорівневого інтерфейсу ядра процесор показує довідку інтерпретатора командного рядка Bash. Якщо ж у коді використовується буферизоване введення або інтерактивне читання термінала, розробнику потрібна бібліотечна функція `fread` зі стандартної бібліотеки C або функція `readline` бібліотеки GNU Readline, кожна з яких має кардинально різні контракти пам'яті, правила буферизації та механізми сигналізації помилок.

Ця колізія ілюструє фундаментальну проблему самоопису операційних систем сімейства Unix. В єдиному просторі імен системи одночасно співіснують однойменні користувацькі утиліти, системні виклики ядра, функції базової бібліотеки мови C, спеціальні вузли файлової системи пристроїв, формати конфігураційних файлів та описи мережевих протоколів. Для однозначної ідентифікації кожного інтерфейсу та усунення неоднозначностей Unix використовує систему нумерованих розділів сторінок документації (`manual pages`, або `man`), де кожна назва інтерпретується в контексті її точного положення в архітектурі системи.

## 1. Архітектура та конвеєр відтворення сторінок довідки

Сторінки `man` є не просто статичними довідковими текстами, а невіддільною частиною дистрибуції операційної системи. На відміну від онлайн-посібників чи веб-документації, вміст локальних сторінок `man` строго відповідає версії встановленого ядра Linux, конкретній збірці стандартної бібліотеки C (`glibc` або `musl`) та версіям інстальованих утиліт. Якщо ядро системи було зібрано без підтримки певного прапорця системного виклику або бібліотека була скомпільована з іншими налаштуваннями, документація на хості є єдиним авторитетним джерелом правди про доступний двійковий інтерфейс (ABI) та інтерфейс прикладного програмування (API).

Фізично сторінки довідки зберігаються у файловій системі за стандартними шляхами (типово `/usr/share/man/` та `/usr/local/share/man/`). Кожен документ являє собою текстовий файл, стиснений алгоритмом gzip (`.gz`), який містить розмітку однією з двох мов макросів:
1. **Традиційний пакет `man(7)`**: історичний формат, заснований на візуальних директивах форматування (`.TH` для заголовка, `.SH` для секцій, `.B` для жирного шрифту, `.I` для курсиву, `.TP` для списків параметрів).
2. **Семантичний пакет `mdoc(7)`**: розроблений у середовищі BSD формат, орієнтований на структурований опис сутностей (`.Nm` для імен програм, `.Fl` для прапорців, `.Ar` для аргументів користувача, `.Fn` для функцій C, `.Er` для кодів помилок `errno`).

Детальний аналіз еволюції форматерів тексту — від перших реалізацій на комп'ютерах PDP-11 до сучасних синтаксичних аналізаторів — викладено в матеріалі [📜 Від RUNOFF до mandoc: як Unix винайшов документацію разом із кодом](root:sys-unix/manual-pages/hist-roff-and-man.md).

Коли користувач виконує запит `man 2 read`, утиліта `man` запускає конвеєр обробки тексту, показаний на нижченаведеній схемі.

![Конвеєр обробки та візуалізації сторінок man](/root/sys/sys-unix/manual-pages/img/man-rendering-pipeline.svg)
*Конвеєр обробки сторінок man: від стиснених вихідних файлів roff/mdoc через форматери groff або mandoc до термінального пейджера less та індексної бази mandb.*

Конвеєр складається з чітко розмежованих етапів:
- **Пошук та розпакування**: Утиліта `man` сканує каталоги змінної `MANPATH`, знаходить файл `/usr/share/man/man2/read.2.gz` і розпаковує потік даних через `zcat` або внутрішні механізми `libz`.
- **Синтаксичний аналіз та верстка**: Форматер — `mandoc` або `groff` (з прапорцем `-mandoc`, який автоматично розпізнає макроси `man` чи `mdoc`) — будує абстрактне синтаксичне дерево документа, розраховує ширину стовпчиків під поточний розмір вікна термінала та виконує перенесення слів.
- **Генерація термінальних керуючих послідовностей**: Драйвер пристрою (`grotty` у складі GNU groff або внутрішній термінальний модуль `mandoc`) замінює логічні стилі оформлення на послідовності ANSI SGR (Select Graphic Rendition) — наприклад, `\e[1m` для жирного накреслення та `\e[4m` для підкреслення. Якщо термінал працює в застарілому режимі, форматер генерує символи зворотного кроку (*backspace overstrike*, наприклад `c\bc` для жирного накреслення літери `c` та `_\bc` для підкреслення).
- **Посторінкова навігація**: Сформований потік передається системному пейджеру (за замовчуванням `less -R`, де прапорець `-R` дозволяє інтерпретувати «сирі» керівні послідовності кольорів ANSI), який надає користувачеві можливість скролінгу, пошуку за регулярними виразами через клавішу `/` та переходу за мітками.

## 2. Вісім класичних розділів довідника та розв'язання колізій

Структура довідника Unix із 1971 року розбита на нумеровані розділи (*sections*). Номер розділу вказує на рівень абстракції та системну роль описуваного компонента. 

Повний довідник макросів розмітки, спеціалізованих підрозділів (`0p`, `3p`, `9`) та таблиць прапорців доступний у вставці [📋 Довідник розділів, макросів розмітки та конвенцій man](root:sys-unix/manual-pages/api-man-sections-and-synopsis.md).

```
   ┌─────────────────────────────────────────────────────────────┐
   │             КЛАСИЧНІ РОЗДІЛИ ДОКУМЕНТАЦІЇ UNIX              │
   ├───────┬───────────────────────────┬─────────────────────────┤
   │ Розд. │ Категорія вмісту          │ Типовий контекст        │
   ├───────┼───────────────────────────┼─────────────────────────┤
   │   1   │ Команди користувача       │ ls, grep, bash, tar     │
   │   2   │ Системні виклики ядра     │ open, read, fork, mmap  │
   │   3   │ Бібліотечні функції C     │ printf, malloc, qsort   │
   │   4   │ Спеціальні файли (/dev)   │ null, zero, tty, random │
   │   5   │ Формати файлів і таблиць  │ passwd, shadow, fstab   │
   │   6   │ Ігри та заставки          │ fortune, factor, tetris │
   │   7   │ Огляди, протоколи, норми  │ ip, tcp, epoll, signal  │
   │   8   │ Системне адміністрування  │ systemd, mount, iptables│
   └───────┴───────────────────────────┴─────────────────────────┘
```

Розгляньмо інженерне призначення кожної секції:

1. **Розділ 1: Команди користувача та утиліти оболонки**. Описує виконувані файли та вбудовані команди, доступні звичайним користувачам без привілеїв суперкористувача. Сюди належать базові інструменти маніпуляції текстом (`sed`, `awk`), компілятори (`gcc`, `clang`), архіватори та інтерпретатори.
2. **Розділ 2: Системні виклики (System Calls)**. Описує інтерфейс ядра Linux/Unix. Це точка входу, де процесор перемикає рівень привілеїв із Ring 3 (користувацький простір) у Ring 0 (простір ядра). Усі виклики розділу 2 документують безпосередні операції над структурами ядра: керування процесами (`fork`, `execve`), файловий ввід-вивід (`read`, `write`, `ioctl`), віртуальну пам'ять (`mmap`, `brk`) та міжпроцесну взаємодію (`socket`, `pipe`).
3. **Розділ 3: Бібліотечні виклики (Library Functions)**. Документує функції високого рівня, що реалізовані в просторі користувача поверх системних викликів або автономно всередині бібліотек `glibc`, `libpthread`, `libcrypto`, `libm`. На відміну від розділу 2, функції розділу 3 містять власну логіку буферизації (`stdio`), динамічного виділення пам'яті (`malloc`, `free`), математичних розрахунків (`sin`, `cos`) або абстракцій вищого рівня.
4. **Розділ 4: Спеціальні файли та пристрої (`/dev`)**. Описує файлові інтерфейси драйверів ядра, віртуальні та псевдопристрої. Тут роз'яснюється семантика вузлів `/dev/null`, `/dev/zero`, `/dev/urandom`, а також інтерфейси терміналів `/dev/tty` та блокових накопичувачів.
5. **Розділ 5: Формати файлів і конфігурації**. Описує синтаксис статичних файлів конфігурації операційної системи та бінарних форматів даних. Коли адміністратору потрібно з'ясувати структуру полів у `/etc/passwd`, формат розкладу `/etc/crontab` або структуру заголовків двійкових файлів `elf(5)`, відповідь міститься саме в розділі 5.
6. **Розділ 6: Ігри та розваги**. Історичний розділ, де зібрані текстові ігри, генератори цитат (`fortune`) та демонстраційні анімації.
7. **Розділ 7: Оглядові статті, мережеві протоколи та стандарти**. Містить теоретичні огляди підсистем ядра, архітектурні концепції та специфікації стеків зв'язку. Тут документуються протоколи `ip(7)`, `tcp(7)`, `unix(7)`, огляд системних сигналів `signal(7)`, семантика механізмів очікування подій `epoll(7)` та стандарти оформлення самої документації `man-pages(7)`.
8. **Розділ 8: Системне адміністрування та службові демони**. Описує утиліти та фонові служби, призначені виключно для керування операційною системою від імені користувача `root`. Сюди входять демони ініціалізації (`systemd(8)`), утиліти монтування дисків (`mount(8)`), конфігуратори міжмережевих екранів (`iptables(8)`, `nft(8)`) та засоби відновлення файлових систем (`fsck(8)`).

### Механіка розв'язання колізій імен

Якщо ім'я сутності повторюється в різних розділах, прямий запит `man <ім'я>` змушує утиліту переглядати розділи у порядку, визначеному параметром `SECTION_LIST` у системному конфігураційному файлі `/etc/manpath.config` (типово `1, n, l, 8, 3, 0, 2, 5, 4, 9, 6, 7`).

![Розв'язання колізій імен та порядок пошуку за розділами man](/root/sys/sys-unix/manual-pages/img/section-collision-resolution.svg)
*Схема порядку пошуку розділів man та розв'язання колізій імен на прикладі команди read(1), системного виклику read(2) та бібліотечної функції readline(3).*

Оскільки розділ 1 перевіряється першим, команда `man read` знаходить `read(1)` і зупиняє пошук. Щоб відкрити системний виклик або бібліотечну функцію, розробник зобов'язаний явно передати номер розділу першим аргументом:

```bash
$ man 2 read      # Системний виклик ядра: int fd -> kernel -> buffer
$ man 3 readline  # Бібліотечна функція GNU Readline: інтерактивний ввід
$ man 1 read      # Вбудована команда Bash
$ man 7 epoll     # Загальний огляд підсистеми асинхронних подій ядра
$ man 5 passwd    # Формат файлу облікових записів /etc/passwd
```

## 3. Граматика секції SYNOPSIS

Секція `SYNOPSIS` (конспект / сигнатура виклику) являє собою формальний контракт використання утиліти або функції. Вона записується за суворими граматичними правилами, похідними від форми Бекуса — Наура (BNF) та конвенцій командного рядка POSIX.

Наступна діаграма розкладає правила читання синтаксичних конструкцій для команд термінала та мови C.

![Граматичні домовленості розділу SYNOPSIS](/root/sys/sys-unix/manual-pages/img/synopsis-anatomy.svg)
*Анатомія секції SYNOPSIS: розбір шрифтових виділень, обов'язкових та опційних блоків, виключного вибору і C-сигнатур.*

### Граматичні правила для утиліт командного рядка (Розділи 1 та 8)

Під час читання сигнатури утиліти діють п'ять базових правил:

1. **Жирний шрифт (`bold`)**: Позначає **дослівний текст**. Це ім'я самої програми, підкоманди, назви опцій та прапорці, які користувач повинен вводити в терміналі символ у символ без змін:
   ```bash
   tar -v
   git commit
   ```
2. **Курсив або підкреслення (`italic` / `underline`)**: Позначає **змінні параметри користувача**. Це заповнювачі (*placeholders*), замість яких користувач повинен підставити конкретне значення — ім'я файлу, шлях до каталогу, числове значення або рядок:
   ```
   tar -f ARCHIVE
   kill -s SIGNAL PID
   ```
   У наведеному прикладі `ARCHIVE`, `SIGNAL` та `PID` — змінні, що мають бути замінені на конкретні значення, наприклад `backup.tar.gz`, `SIGTERM` та `4102`.
3. **Квадратні дужки `[ ]`**: Позначають **опційні елементи**. Усе, що міститься всередині квадратних дужок, можна опустити під час запуску програми:
   ```
   tar [-v] [-f ARCHIVE] [FILE...]
   ```
   Тут прапорець `-v` є необов'язковим. Опція `-f ARCHIVE` також є необов'язковою, але якщо користувач вирішив її використати, він зобов'язаний передати параметр `ARCHIVE`.
4. **Фігурні дужки `{ }` та вертикальна риска `|`**: Позначають **взаємовиключний вибір (XOR)**. Користувач зобов'язаний обрати **рівно один** варіант із наведеного переліку:
   ```
   tar { -c | -x | -t } [OPTIONS]
   ```
   Запис вимагає обов'язкової наявності або прапорця створення архіву (`-c`), або розпакування (`-x`), або перегляду вмісту (`-t`), але забороняє їхню одночасну відсутність.
5. **Трикрапка `...`**: Позначає **повторюваність попереднього елемента**. Елемент перед трикрапкою може повторюватися один або декілька разів:
   ```
   cat FILE...           # Вимагає щонайменше один FILE (FILE, FILE2, FILE3...)
   grep [OPTION...] PATTERN [FILE...]  # Нуль або більше опцій, обов'язковий шаблон, нуль або більше файлів
   ```

### Групування та форми опцій

- **Короткі опції (Short options)**: Однолітерні прапорці, що починаються з одного дефіса. Якщо в сигнатурі вказано `[-a] [-b] [-c]`, стандарт POSIX дозволяє групувати їх в один блок: `-abc`.
- **Опції з аргументами**:
  - `[-o OUTPUT]`: прапорець вимагає обов'язковий аргумент (наприклад `-o file.bin`).
  - `[-o[OUTPUT]]`: аргумент опції є необов'язковим (якщо значення опустити, утиліта застосує стандартне значення).
- **Довгі опції GNU**: Починаються з двох дефісів. Запис `--output=FILE` вимагає явного присвоєння значення через знак рівності або пробіл.

### Граматичні правила для C-функцій (Розділи 2 та 3)

Секція `SYNOPSIS` для системних викликів та функцій C містить три критичні компоненти, необхідні компілятору:

```synopsis
#include <unistd.h>

ssize_t read(int fd, void *buf, size_t count);
```

1. **Заголовкові файли (`#include <...>`)**: Перелік стандартних або системних заголовків, які необхідно підключити у вихідному коді для імпорту сигнатури функції та визначення типів даних.
2. **Макроси тестування функціональності (Feature Test Macros)**: Якщо функція вимагає специфічного стандарту або розширення GNU/BSD, перед заголовками вказується необхідна директива препроцесора:
   ```synopsis
   #define _GNU_SOURCE         /* Див. feature_test_macros(7) */
   #include <fcntl.h>
   ```
   Якщо проігнорувати цей макрос, компілятор видасть попередження про неоголошену функцію (`implicit function declaration`).
3. **Сигнатура функції**:
   - **Тип повернення**: Вказує тип результату (наприклад, `ssize_t` для кількості зчитаних байтів зі знаком, де від'ємне значення кодує помилку).
   - **Кваліфікатори типів**: `const void *buf` вказує, що функція лише читає пам'ять буфера і гарантує його незмінність, тоді як `void *buf` вказує на зміну буфера. Кваліфікатор `restrict` (введений у C99) сигналізує компілятору, що вказівники не перекривають спільні ділянки пам'яті, відкриваючи можливості для агресивної векторної оптимізації.

## 4. Пошуковий апарат: apropos, whatis, mandb та маршрутизація MANPATH

Коли розробник не знає точної назви системного виклику або шукає всі доступні інструменти для роботи з певним ресурсом (наприклад, сокетами або таймерами), прямий виклик `man` безсилий. Для цього операційна система надає підсистему індексації та повнотекстового пошуку.

### Пошук за ключовими словами: `apropos` та `man -k`

Команда `apropos` (еквівалентна `man -k`) виконує пошук за регулярним виразом або ключовим словом серед однорядкових описів усіх сторінок, зареєстрованих у системі:

```bash
$ apropos "timer create"
timer_create (2)     - create a POSIX per-process timer
timerfd_create (2)   - timers that notify via file descriptors
```

Якщо потрібно перевірити точний збіг імені програми чи функції, використовується команда `whatis` (еквівалентна `man -f`):

```bash
$ whatis read
read (1)             - read a line from standard input
read (2)             - read from a file descriptor
read (3p)            - read from a file
```

### Внутрішня будова бази даних `mandb`

Блискавична швидкість роботи `apropos` та `whatis` забезпечується тим, що ці команди не сканують тисячі стиснених файлів `.gz` на диску в момент запиту. Вони звертаються до попередньо скомпільованої індексної бази даних (типово `/var/cache/man/index.db`), яка реалізована на основі GDBM або Berkeley DB.

Формування бази здійснюється фоновою службою `mandb` (або `makewhatis` у BSD-системах), яка періодично запускається через системний таймер `systemd` (`man-db.timer`) або задачі `cron`. Утиліта `mandb` виконує такі кроки:
1. Сканує всі каталоги, перелічені у файлі `/etc/manpath.config`;
2. Розпаковує заголовок кожного файлу і витягує секцію `.SH NAME` (або `.Sh NAME`);
3. Розбирає рядок виду `назва, синонім - короткий опис призначення`;
4. Зберігає нормалізовані записи в хеш-таблицю `index.db`, зв'язуючи ключові слова з фізичним розташуванням файлів на диску.

Якщо розробник встановив нову бібліотеку чи пакет утиліт вручну (наприклад, у `/usr/local/`), база `mandb` може не знати про нові сторінки. Для примусового оновлення кешу індексів виконується команда:

```bash
$ sudo mandb -u
```

### Діагностика шляхів та змінна MANPATH

Щоб дізнатися, де саме на диску розташований фізичний файл man-сторінки, використовується ключ `-w` (`--where`) або `-W`:

```bash
$ man -w 2 read
/usr/share/man/man2/read.2.gz

$ man -w -a read
/usr/share/man/man1/read.1.gz
/usr/share/man/man2/read.2.gz
/usr/share/man/man3p/read.3p.gz
```

Маршрути пошуку визначаються змінною середовища `MANPATH`. Якщо ця змінна не встановлена в термінальній сесії, `man` автоматично генерує список каталогів на основі поточної змінної `PATH`, використовуючи правила відображення директиви `MANPATH_MAP` у конфігураційному файлі `/etc/manpath.config`:

```
# Відображення бінарних каталогів на каталоги документації:
MANPATH_MAP    /bin            /usr/share/man
MANPATH_MAP    /usr/bin        /usr/share/man
MANPATH_MAP    /usr/local/bin  /usr/local/share/man
MANPATH_MAP    /opt/cuda/bin   /opt/cuda/share/man
```

Якщо користувач визначає власну змінну `MANPATH`, додавання двокрапки на початку або наприкінці рядка (`export MANPATH="$HOME/.local/share/man:"`) наказує системі додати користувацький каталог до стандартного системного шляху, а не замінити його повністю.

## 5. Читання розділу 2 проти розділу 3: контракти виконання, помилки та безпека

Найважливіша інженерна навичка під час роботи з довідником Unix — розрізняти правила системних викликів (Розділ 2) та бібліотечних функцій (Розділ 3). Хоча зовні обидві категорії виглядають як звичайні функції мови C, їхні контракти виконання, взаємодія з пам'яттю та способи обробки аварійних станів принципово відрізняються.

```
   ┌─────────────────────────────────────────────────────────────┐
   │            РОЗДІЛ 2 (ЯДРО) vs РОЗДІЛ 3 (LIBC / БІБЛІОТЕКИ)  │
   ├───────────────────────────┬─────────────────────────────────┤
   │ Системний виклик (Розд. 2)│ Бібліотечна функція (Розд. 3)   │
   ├───────────────────────────┼─────────────────────────────────┤
   │ Перемикання Ring 3 → Ring 0│ Виконання суто в User Space     │
   │ Не виділяє пам'ять у купі │ Може викликати malloc / realloc │
   │ Повертає -1, ставить errno│ Повертає NULL, EOF, коди або -1 │
   │ Буферизація відсутня      │ Власна буферизація (FILE*)      │
   │ Прямий доступ до дескрипт.│ Абстракція високого рівня       │
   └───────────────────────────┴─────────────────────────────────┘
```

### Секція RETURN VALUE та діагностика через `errno`

У системних викликах розділу 2 стандартом де-факто є повернення цілого числа:
- Невегативне значення (`>= 0`): успіх операції (для `open` — номер дескриптора, для `read`/`write` — кількість переданих байтів, для `fork` — PID процесу).
- Значення `-1`: виникнення помилки. У цьому випадку ядро через асемблерну обгортку `glibc` записує позитивний числовий код у потоко-локальну глобальну змінну `errno`, а сама функція повертає `-1`.

:::tabs
@tab C
```c
/* Перевірка помилки повернення системного виклику */
ssize_t bytes = read(fd, buf, count);
if (bytes == -1) {
    if (errno == EINTR) {
        /* Системний виклик перервано сигналом до передачі даних */
    }
}
```
@tab C++
```cpp
// Ідіоматична перевірка системної помилки через std::error_code
const ssize_t bytes = ::read(fd, buf, count);
if (bytes == -1) {
    if (errno == EINTR) {
        // Системний виклик перервано сигналом до передачі даних
    }
}
```
:::

У розділі 3 правила повернення визначаються автором бібліотеки і вимагають ретельного читання документації:
- Функції роботи з пам'яттю (`malloc`) повертають покажчик на виділений блок або `NULL` при вичерпанні пам'яті (встановлюючи `errno = ENOMEM`).
- Функції потокового вводу-виводу (`fread`, `fwrite`) повертають кількість успішно оброблених елементів, а для перевірки помилки вимагають окремого виклику функцій `ferror(stream)` або `feof(stream)`.
- **Функції з дійсним поверненням `-1`**: Деякі виклики ядра та бібліотеки (наприклад, `getpriority(2)` або `strtol(3)`) можуть легітимно повертати значення `-1` як коректний результат роботи. Для таких функцій секція `RETURN VALUE` вимагає особливого патерну: **перед викликом обнулити `errno = 0`**, виконати виклик і лише за умови повернення `-1` перевірити, чи змінилося значення `errno != 0`.

### Секція ERRORS: ключові коди помилок

Секція `ERRORS` містить вичерпний алфавітний перелік констант `errno`, які може згенерувати цей виклик:
- `EINTR` (*Interrupted function call*): виклик було перервано доставкою асинхронного сигналу до того, як ядро встигло передати бодай один байт даних. Програма зобов'язана повторити виклик у циклі.
- `EAGAIN` або `EWOULDBLOCK` (*Resource temporarily unavailable*): дескриптор відкрито в неблокуючому режимі (`O_NONBLOCK`), і операція не може бути завершена негайно без блокування потоку.
- `EBADF` (*Bad file descriptor*): переданий файловий дескриптор не є відкритим або не відповідає режиму операції (наприклад, спроба запису в дескриптор, відкритий лише для читання).
- `EFAULT` (*Bad address*): переданий вказівник буфера вказує за межі доступного віртуального адресного простору процесу.
- `EINVAL` (*Invalid argument*): передано неприпустимі прапорці або невалідне вирівнювання пам'яті.
- `ENOMEM` (*Cannot allocate memory*): ядру забракло фізичної пам'яті або сторінок для виконання запиту.

### Секція ATTRIBUTES: матриця безпеки виконання

Секція `ATTRIBUTES` містить стандартизовану таблицю безпеки функції для багатопотокових та асинхронних середовищ:

```
┌─────────────────────────────────────────────────────────────┐
│ Interface  │ Attribute     │ Value                          │
├────────────┼───────────────┼────────────────────────────────┤
│ strtok()   │ Thread safety │ MT-Unsafe race:strtok          │
│ strtok_r() │ Thread safety │ MT-Safe                        │
│ getenv()   │ Thread safety │ MT-Unsafe env                  │
│ fork()     │ Thread safety │ MT-Safe AS-Safe AC-Safe        │
└────────────┴───────────────┴────────────────────────────────┘
```

Розшифрування атрибутів:
1. **`MT-Safe` (Multi-Thread Safe)**: Функцію можна одночасно викликати з багатьох потоків виконання без ризику пошкодження пам'яті чи станів гонитви.
2. **`MT-Unsafe`**: Одночасний виклик із кількох потоків призведе до непередбачуваної поведінки. Позначка `race:strtok` вказує, що функція використовує спільний статичний внутрішній буфер. Для таких функцій бібліотека майже завжди надає реентрантну версію із суфіксом `_r` (наприклад, `strtok_r`, `asctime_r`), яка вимагає передачі контексту через аргументи.
3. **`AS-Safe` (Async-Signal-Safe)**: Функцію дозволено викликати всередині обробників сигналів (`signal handlers`). Функції типу `printf` або `malloc` є `AS-Unsafe`, оскільки вони захоплюють глобальні м'ютекси розподільника пам'яті: якщо сигнал перерве виконання основного потоку під час утримання м'ютекса, повторна спроба виділити пам'ять в обробнику сигналу спричинить дедлок (*deadlock*).
4. **`AC-Safe` (Async-Cancel-Safe)**: Функція є безпечною у випадку, якщо потік переривається асинхронно через механізм `pthread_cancel`.

### Секції CONFORMING TO та VERSIONS

Секція `CONFORMING TO` (у нових сторінках — `STANDARDS`) визначає переносність інтерфейсу:
- **POSIX.1-2001, POSIX.1-2008**: функція є загальноприйнятим стандартом і гарантовано доступна на Linux, FreeBSD, OpenBSD, macOS, Solaris.
- **C99, C11**: функція є частиною стандарту мови C (ISO/IEC 9899).
- **Linux-specific**: виклик присутній виключно в ядрі Linux (наприклад, `epoll_create1`, `signalfd`, `copy_file_range`). Його використання унеможливлює пряму компіляцію програми на інших Unix-платформах.

## 6. Практичний приклад: читання дескриптора з обробкою сигнатури man

Проілюструємо застосування правил розділу 2 на практичному прикладі системного виклику `read(2)`. Секція `ERRORS` сторінки `read(2)` зобов'язує надійний системний код обробляти три специфічні ситуації:
1. Переривання виклику доставкою сигналу (`errno == EINTR`): операція має бути автоматично перезапущена;
2. Відсутність готових даних у неблокуючому сокеті (`errno == EAGAIN` або `EWOULDBLOCK`): потік має перейти в режим очікування або виконати іншу корисну роботу;
3. Повернення значення `0`: однозначний сигнал досягнення кінця файлу (`EOF` — End of File) або закриття віддаленого з'єднання сокета.

:::tabs
@tab C
```c
#define _POSIX_C_SOURCE 200809L
#include <unistd.h>
#include <errno.h>
#include <string.h>
#include <stdio.h>
#include <stdbool.h>

/* Безпечне зчитування блоку даних за специфікацією read(2) */
ssize_t safe_read_exact(int fd, void *buffer, size_t count) {
    size_t bytes_read_total = 0;
    char *dest = (char *)buffer;

    while (bytes_read_total < count) {
        ssize_t result = read(fd, dest + bytes_read_total, count - bytes_read_total);

        if (result > 0) {
            bytes_read_total += (size_t)result;
            continue;
        }

        if (result == 0) {
            /* Кінець файлу (EOF) або сокет закрито віддаленою стороною */
            break;
        }

        /* Обробка системних помилок через перевірку errno */
        if (errno == EINTR) {
            /* Системний виклик перервано сигналом: перезапускаємо читання */
            continue;
        }

        if (errno == EAGAIN || errno == EWOULDBLOCK) {
            /* Дескриптор у неблокуючому режимі O_NONBLOCK: ресурс зайнятий */
            if (bytes_read_total > 0) {
                return (ssize_t)bytes_read_total;
            }
            return -1;
        }

        /* Критична системна помилка (EBADF, EFAULT, EIO тощо) */
        return -1;
    }

    return (ssize_t)bytes_read_total;
}
```
@tab C++
```cpp
#include <unistd.h>
#include <cerrno>
#include <system_error>
#include <expected>
#include <span>
#include <cstddef>

enum class ReadError {
    Interrupted,
    ResourceUnavailable,
    SystemFailure,
    UnexpectedEof
};

// Ідіоматична C++ обгортка системного виклику read(2) на базі std::span
[[nodiscard]] auto safe_read_span(int fd, std::span<std::byte> destination) 
    -> std::expected<std::size_t, std::error_code> 
{
    std::size_t total_read = 0;

    while (total_read < destination.size()) {
        const auto remaining = destination.subspan(total_read);
        const auto result = ::read(fd, remaining.data(), remaining.size());

        if (result > 0) {
            total_read += static_cast<std::size_t>(result);
            continue;
        }

        if (result == 0) {
            // EOF досягнуто за специфікацією read(2)
            break;
        }

        const int current_error = errno;
        if (current_error == EINTR) {
            // Переривання доставкою сигналу: повторюємо спробу
            continue;
        }

        if (current_error == EAGAIN || current_error == EWOULDBLOCK) {
            if (total_read > 0) {
                return total_read;
            }
            return std::unexpected(std::make_error_code(std::errc::resource_unavailable_try_again));
        }

        return std::unexpected(std::error_code(current_error, std::generic_category()));
    }

    return total_read;
}
```
:::

## 7. Практичні підсумки читання сторінок довідки

Здатність коректно орієнтуватися у сторінках `man` є базовою інженерною дисципліною в середовищі Unix/Linux. Щоб вичерпно інтерпретувати будь-який опис інтерфейсу, слід дотримуватися чіткої послідовності аналізу:

1. **Ідентифікувати розділ**: Завжди перевіряти цифру в дужках поруч із назвою (`read(2)` чи `read(1)`). Якщо ім'я може бути перевантажене, явно викликати потрібний номер секції.
2. **Перевірити передумови `SYNOPSIS`**: Звернути увагу на обов'язкові заголовкові файли `#include` та макроси `_GNU_SOURCE` чи `_POSIX_C_SOURCE`, без яких компілятор згенерує некоректний бінарний код.
3. **Звірити контракт `RETURN VALUE`**: З'ясувати, яке саме число чи покажчик сигналізує про помилку, чи може `-1` бути валідним значенням, і чи не вимагає виклик попереднього обнулення `errno = 0`.
4. **Вивчити секцію `ATTRIBUTES`**: Переконатися, що функція є `MT-Safe` перед викликом із робочих потоків, або `AS-Safe` перед викликом із обробника сигналів `sigaction`.
5. **Оцінити переносність за `STANDARDS`**: Перевірити, чи є виклик стандартом POSIX, чи специфічним розширенням ядра Linux, плануючи можливу підтримку інших операційних систем.
