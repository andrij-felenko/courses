# 📋 Інтерфейси системного тиску: /proc/pressure та cgroup v2

Довідник системного інтерфейсу Pressure Stall Information (PSI) описує точний формат даних псевдофайлів `/proc/pressure/*` та `cgroup.pressure`, синтаксис налаштування порігових тригерів, параметри ядра, структури даних у просторі ядра та події трасування.

## 1. Вузли віртуальної файлової системи /proc/pressure

Підсистема PSI експортує метрики тиску ресурсу через віртуальну файлову систему procfs у директорії `/proc/pressure/`. Ці вузли створені для забезпечення швидкого доступу у режимі читання до стану системного голодування, а також для реєстрації подієвих тригерів реального часу через операцію запису.

### 1.1. Перелік глобальних вузлів

| Шлях до файлу | Відстежуваний ресурс | Підтримувані типи станів | Примітка |
| :--- | :--- | :--- | :--- |
| `/proc/pressure/cpu` | Процесорний час (CPU) | `some` | Метрика `full` відсутня, оскільки простій усіх процесів означає відсутність потреб у CPU |
| `/proc/pressure/memory` | Оперативна пам'ять (RAM) | `some`, `full` | Враховує затримки на reclaim, swap, compaction та thrashing |
| `/proc/pressure/io` | Дискова підсистема (I/O) | `some`, `full` | Враховує затримки на синхронне читання/запис та swap I/O |

Кожен із цих вузлів надає глобальний зріз стану всього вузла (node-level). Для ресурсу CPU існує лише рядок `some`, оскільки простій процесора означає, що жодне завдання не очікує на виконання. Натомість для пам'яті та дискового введення-виведення присутні обидва рядки: `some` (частина задач заблокована) та `full` (усі активні задачи заблоковані, CPU повністю простоює).

### 1.2. Формат виводу даних

Читання будь-якого з вузлів `/proc/pressure/{cpu,memory,io}` повертає від одного до двох рядків у залежності від ресурсу.

Приклад виводу `/proc/pressure/memory`:
```syslog
some avg10=0.04 avg60=0.12 avg300=0.05 total=1420582
full avg10=0.00 avg60=0.02 avg300=0.01 total=312044
```

Кожен рядок починається з ідентифікатора типу стану (`some` або `full`), після чого йдуть три згладжені середні показники за останні 10, 60 та 300 секунд, а наприкінці — абсолютний монотонний лічильник накопиченого часу голодування.

### 1.3. Детальна анатомія полів виводу

| Поле | Тип даних | Діапазон / Одиниці | Опис значення |
| :--- | :--- | :--- | :--- |
| `some` | Рядок-тег | N/A | Індикатор затримок, коли *принаймні один* потік заблоковано на ресурсі |
| `full` | Рядок-тег | N/A | Індикатор затримок, коли *усі активні потоки* заблоковано (CPU повністю простоює) |
| `avg10` | Дійсне число | `0.00` – `100.00` (%) | Експоненціально згладжений відсоток часу затримки за останні **10 секунд** |
| `avg60` | Дійсне число | `0.00` – `100.00` (%) | Експоненціально згладжений відсоток часу затримки за останні **60 секунд** |
| `avg300` | Дійсне число | `0.00` – `100.00` (%) | Експоненціально згладжений відсоток часу затримки за останні **300 секунд** (5 хвилин) |
| `total` | Ціле число | Мікросекунди (μs) | Монотонно зростаючий лічильник загального часу затримки з моменту завантаження ядра |

Показники `avg10`, `avg60` та `avg300` є згладженими рухомими середніми величинами. Значення `avg10=12.50` означає, що протягом останніх 10 секунд процеси провели у стані голодування в середньому 12.5% часу. Поле `total` вимірює абсолютний час у мікросекундах (1 секунда = 1 000 000 μs) і не скидається до нуля, що робить його ідеальним для збору системами Prometheus / Grafana Telegraf за допомогою розрахунку `rate(total)`.

## 2. Ієрархічний інтерфейс cgroup v2 (cgroup.pressure)

У системах із підтримкою уніфікованої ієрархії cgroup v2 кожна контрольна група містить власні файли моніторингу PSI. Це забезпечує точний розподіл метрик голодування між окремими контейнерами, слайсами systemd або призначеними користувачами.

### 2.1. Шляхи до вузлів cgroup v2

Глобальний корінь cgroup v2 розташований за шляхом `/sys/fs/cgroup/`. Усередині кожної піддиректорії (наприклад, `/sys/fs/cgroup/system.slice/systemd-journald.service/`) присутні наступні файли моніторингу тиску:

- `cpu.pressure` — експортує тиск процесора для процесів даної cgroup.
- `memory.pressure` — експортує тиск оперативної пам'яті для процесів даної cgroup.
- `io.pressure` — експортує тиск дискового введення-виведення для процесів даної cgroup.

Формат даних у файлах `cgroup.pressure` повністю ідентичний файлам у `/proc/pressure/`. При цьому метрики ізольовані: затримки I/O в одному Docker-контейнері не впливають на показники `memory.pressure` сусіднього контейнера, якщо тільки тиск не поширюється на вищий батьківський вузол cgroup.

### 2.2. Наслідування та агрегація у cgroup v2

У дереві cgroup v2 події тиску агрегуються знизу вгору (bottom-up):
1. Голодування потоку в дочірній cgroup збільшує лічильники цієї cgroup.
2. Голодування одночасно додається до лічильників усіх батьківських cgroups аж до кореневої cgroup.
3. Це дозволяє встановити глобальний тригер на рівні всієї системи, або точний тригер на рівні конкретного подвійного контейнера.

## 3. API тригерів реального часу (PSI Triggers)

PSI дозволяє процесам у просторі користувача реєструвати асинхронні тригери за допомогою операцій запису у файлові дескриптори `/proc/pressure/*` або `cgroup.pressure`, після чого очікувати на сповіщення через системні виклики `poll()`, `select()` або `epoll()`.

### 3.1. Механізм реєстрації тригера

Програма відкриває файл тиску у режимі читання та запису (`O_RDWR` або `O_WRONLY`) і виконує системний виклик `write()` з наступним текстовим рядком специфікації:

`"<some|full> <stall_thresh_us> <window_us>"`

Опис складових елементів синтаксису:
- **`state`**: Тип відстежуваного стану (`"some"` або `"full"`).
- **`stall_thresh_us`**: Поріг накопиченого часу затримки в мікросекундах (μs), після перевищення якого генератор подій надсилає сповіщення.
- **`window_us`**: Розмір рухомого вікна спостереження в мікросекундах (μs).

Обмеження параметрів ядерного детектора:
- Мінімальний розмір вікна `window_us`: `50 000` μs (50 мс).
- Максимальний розмір вікна `window_us`: `10 000 000` μs (10 секунд).
- Поріг `stall_thresh_us` повинен бути суворо меншим за `window_us` (наприклад, 150 мс затримки у вікні 1000 мс).
- Один відкритий файловий дескриптор може асоціюватися лише з одним тригером. Запропонована спроба повторного виклику `write()` у той самий fd поверне помилку `EINVAL`.

Приклади налаштування тригерів:
- `"some 150000 1000000"` — генерація події, якщо процеси чекали на ресурс 150 мс у межах вікна в 1 секунду.
- `"full 50000 500000"` — генерація події, якщо вся система була повністю паралізована на 50 мс у межах вікна 500 мс.

### 3.2. Подієвий цикл epoll / poll та прапорці подій

Після успішного запису специфікації файловий дескриптор стає джерелом подій реального часу:

:::tabs
```c
struct epoll_event ev;
memset(&ev, 0, sizeof(ev));
ev.events = EPOLLPRI; // Прапорець високопріоритетних даних (POLLPRI)
ev.data.fd = psi_fd;
epoll_ctl(epoll_fd, EPOLL_CTL_ADD, psi_fd, &ev);
```
```cpp
epoll_event ev{};
ev.events = EPOLLPRI; // Прапорець високопріоритетних даних (POLLPRI)
ev.data.fd = psi_fd;
epoll_ctl(epoll_fd, EPOLL_CTL_ADD, psi_fd, &ev);
```
:::

Важливі особливості обробки подій у просторі користувача:
1. Подія генерації тригера повертається з прапорцем **`POLLPRI`** (або **`EPOLLPRI`** у випадку `epoll`).
2. Читання файлового дескриптора після спрацьовування тригера не є обов'язковим для очищення стану: факт виклику `poll()` / `epoll_wait()` скидає подію.
3. Сповіщення захищені від "шторму подій" (rate-limiting): після спрацьовування тригера ядро пригнічує подальші сповіщення до завершення поточного вікна `window_us`.

## 4. Ядерні структури даних (<linux/psi_types.h>)

Для внутрішнього обліку станів голодування ядро Linux использует структури даних, визначені в заголовочному файлі `include/linux/psi_types.h`.

### 4.1. Перелічення станів тиску (enum psi_states)

```c
enum psi_states {
    PSI_IO_SOME,
    PSI_IO_FULL,
    PSI_MEM_SOME,
    PSI_MEM_FULL,
    PSI_CPU_SOME,
    PSI_NONIDLE,
    NR_PSI_STATES,
};
```

Елемент `PSI_NONIDLE` відстежує загальний стан, коли принаймні один потік у системі виконує корисну роботу на CPU або чекає на ресурс.

### 4.2. Попроцесорна структура обліку (struct psi_group_cpu)

Ядро зберігає стан голодування окремо для кожного логічного процесора (per-CPU storage) для усунення блокувань на гарячих шляхах планувальника:

```c
struct psi_group_cpu {
    /* Кількість потоків у кожному стані на цьому CPU */
    unsigned int tasks[NR_PSI_TASK_COUNTS];

    /* Бітова маска активних станів тиску */
    u32 state_mask;

    /* Часові мітки та накопичений час у мікросекундах */
    u64 state_start;
    u64 times[NR_PSI_STATES];
};
```

### 4.3. Агрегуюча структура групи (struct psi_group)

Глобальний стан та стан cgroup описуються структурою `struct psi_group`:

```c
struct psi_group {
    /* Попроцесорні масиви лічильників */
    struct psi_group_cpu __percpu *pcpu;

    /* Фоновий таймер обчислення згладжених метрик */
    struct timer_list poll_timer;
    u64 poll_min_update;

    /* Збережені згладжені значення avg10, avg60, avg300 */
    unsigned long avg[NR_PSI_STATES][3];
    u64 total[NR_PSI_STATES];

    /* Список зареєстрованих користувацьких тригерів */
    struct list_head triggers;
    u32 trigger_mask;
};
```

## 5. Системний тюнінг та конфігурація ядра

### 5.1. Опції компіляції ядра (Kconfig)

Під час збирання ядра Linux підсистема PSI керується наступними прапорцями конфігуратора:
- `CONFIG_PSI=y` — вмикає код підсистеми Pressure Stall Information у ядрі.
- `CONFIG_PSI_DEFAULT_DISABLED=y/n` — визначає, чи буде підсистема PSI вимкнена за замовчуванням при старті системи.

### 5.2. Параметри командного рядка ядра (cmdline)

Управління підсистемою PSI під час завантаження системи здійснюється через файл `/proc/cmdline`:
- `psi=1` — примусово вмикає підсистему PSI при старті.
- `psi=0` — повністю вимикає підсистему PSI, усуваючи накладні витрати на переключення контексту (економія біля 0.5% CPU).

Перевірка поточного стану підсистеми у запущеній системі здійснюється через sysfs:
```bash
$ cat /sys/module/PSI/parameters/enabled
Y
```

## 6. Точки трасування ядра (Tracepoints)

Підсистема PSI експортує точки трасування для інструментів `ftrace`, `perf` та eBPF:

- `psi_event` — викликається у момент спрацьовування користувацького тригера.
- `psi_window_change` — викликається при зміні або оновленні вікна розрахунку тиску.

Приклад відстеження подій PSI за допомогою `tracefs`:
```bash
$ echo 1 > /sys/kernel/tracing/events/psi/psi_event/enable
$ cat /sys/kernel/tracing/trace_pipe
```

## 7. Діагностика помилок та коди повернення системних викликів

При роботі з інтерфейсом `/proc/pressure/*` системні виклики можуть повертати наступні коди помилок:

- **`EINVAL`**: Некоректний синтаксис тригерного рядка (невідомий стан, від'ємний поріг, або `stall_thresh_us >= window_us`), спроба повторного `write()` у вже зареєстрований файловий дескриптор, або виклик тригера `full` для вузла CPU.
- **`EOPNOTSUPP`**: Підсистему PSI вимкнено за допомогою параметра ядра `psi=0`.
- **`ENOMEM`**: Нестача ядерної пам'яті для виділення внутрішньої структури `struct psi_trigger`.
- **`EBUSY`**: Спроба реєстрації нового тригера у момент видалення або перебудови ієрархії cgroup v2.
