# 📋 Довідник прапорів та атрибутів динамічного лінкера

Цей довідник містить систематизовані таблиці та детальні технічні описи змінних середовища динамічного завантажувача (`ld.so`), атрибутів видимості компілятора GCC/Clang, прапорців статичного та динамічного компонувальника (`ld`), а також констант програмного інтерфейсу `dlopen`/`dlsym`.

Оскільки динамічний лінкер операційної системи є центральним вузлом розв'язання символів у просторі користувача, його поведінка регулюється за допомогою низки змінних середовища та специфічних прапорів компіляції. Розуміння кожного з цих параметрів необхідне для безпечного розгортання системних перехоплювачів, оптимізації швидкості завантаження процесів, зменшення споживання оперативної пам'яті та забезпечення стабільності розширеного ABI.

## 1. Змінні середовища динамічного завантажувача (ld.so)

Змінні середовища динамічного завантажувача дозволяють змінювати порядок пошуку та зв'язування об'єктів у просторі віртуальної пам'яті процесу без здійснення перекомпіляції бінарних файлів. Динамічний завантажувач читає ці змінні на самому початку фази ініціалізації процесу у функції `_dl_sysdep_start` перед тим, як передати керування на точку входу `_start` головної програми.

Однак з міркувань захисту цілісності системи операційна система обмежеє застосування більшості із цих змінних для привілейованих процесів за допомогою системного виклику `secure_getenv()`.

У таблиці нижче зведено всі ключові змінні середовища Linux, які керують пошуком, розв'язанням символів, трасуванням та налагодженням динамічного лінкера `ld.so`.

| Змінна середовища | Призначення та поведінка | Безпека у setuid |
| :--- | :--- | :--- |
| `LD_PRELOAD` | Список бібліотек (через двоеточіє або пробіл), які завантажуються першими. Їхні символи мають найвищий пріоритет у глобальній таблиці. | Ігнорується, якщо не входить у `/etc/ld.so.preload` чи системні шляхи. |
| `LD_LIBRARY_PATH` | Каталоги для пошуку спільних `.so` бібліотек перед системними шляхами `/lib`, `/usr/lib`. | Ігнорується в режимі secure-execution. |
| `LD_BIND_NOW` | Якщо задано (непорожнє значення), примушує динамічний лінкер розв'язувати всі PLT-символи одразу під час старту (миттєве зв'язування замість lazy binding). | Безпечна, дозволена у setuid. |
| `LD_DYNAMIC_WEAK` | Якщо встановлено у `1`, дозволяє сильному символу з пізніше завантаженої бібліотеки перекривати слабкий символ з раніше завантаженої. За замовчуванням (0) використовується перший знайдений символ. | Ігнорується у setuid. |
| `LD_DEBUG` | Виводить діагностичні повідомлення лінкера у `stderr`. Значення: `all`, `bindings`, `symbols`, `reloc`, `files`, `versions`, `scopes`, `help`. | Ігнорується у setuid. |
| `LD_DEBUG_OUTPUT` | Перенаправляє вивід `LD_DEBUG` у файл із заданим префіксом (додається PID процесу). | Ігнорується у setuid. |
| `LD_PROFILE` | Ім'я спільної бібліотеки для профілювання викликів через gmon. | Ігнорується у setuid. |

### Механізми безпеки при обробці змінних середовища
Коли процес запускається з увімкненим бітом `setuid` чи `setgid` або володіє розширеними POSIX capabilities (наприклад, `CAP_NET_RAW` або `CAP_SYS_ADMIN`), динамічний лінкер автоматично перемикається у режим **secure execution** (перевірка `__libc_enable_secure` у glibc та прапорця `AT_SECURE` в Auxiliary Vector).

У режимі secure execution:
1. Змінні середовища `LD_PRELOAD`, `LD_LIBRARY_PATH`, `LD_DEBUG` та `LD_DYNAMIC_WEAK` мовчки відкидаються і не мають жодного впливу на пошук символів.
2. Для завантаження прелоад-бібліотек перевіряється виключно системний конфігураційний файл `/etc/ld.so.preload`, доступ до запису у який має лише користувач `root`.
3. Пошук спільних бібліотек обмежується стандартними системними каталогами (`/lib64`, `/usr/lib64`) та шляхами, записаними у секції `DT_RUNPATH` з абсолютними адресами.

Змінна `LD_BIND_NOW` залишається дозволеною у привілейованому режимі, оскільки вона не дозволяє підміняти код, а лише примушує виконати всі релокації заздалегідь, підвищуючи безпеку процесу проти атак на переповнення буфера у GOT (GOT-overwrite attacks).

Змінна `LD_DEBUG` підтримує комбінування режимів через кому. Наприклад, `LD_DEBUG=bindings,symbols` виводить деталізований покроковий журнал того, у яких саме `.so` файлах `ld.so` шукає кожен конкретний символ та які віртуальні адреси записуються у таблицю GOT.

## 2. Атрибути видимості компілятора (ELF Symbol Visibility)

Керування видимістю символів на рівні компілятора дозволяє розробникам суттєво оптимізувати розмір динамічної таблиці `.dynsym` та прискорити виконання програми. Якщо символ позначено як `hidden`, компілятор знає, що цей символ не може бути перекритий ззовні (носій не допускає interposition), і генерує прямі відносні інструкції виклику (PC-relative) замість використання повільних таблиць індирекції GOT/PLT.

Атрибут `__attribute__((visibility("...")))` у компіляторах GCC та Clang дозволяє розробнику керувати появою символів у динамічній таблиці `.dynsym` та їхньою участю у перекритті.

| Атрибут | Опис поведінки в ELF | Занесення в `.dynsym` | Дозволяє interposition |
| :--- | :--- | :--- | :--- |
| `visibility("default")` | Публічний символ. Видимий для інших DSO (Dynamic Shared Objects). Бере участь у перекритті символів через GOT/PLT. | Так | Так |
| `visibility("hidden")` | Символ не експортується за межі поточного DSO. Усі виклики всередині модуля компілюються як прямі відносні адресації без GOT/PLT. | Ні | Ні |
| `visibility("protected")` | Символ експортується для зовнішніх модулів, але виклики зсередини даного DSO завжди зв'язуються з локальним визначенням (ігнорують `LD_PRELOAD`). | Так | Ні (для локальних викликів) |
| `visibility("internal")` | Аналогічно `hidden`, але здатний додатково оптимізуватися архітектурно-специфічними інструкціями компілятора. | Ні | Ні |

### Практичний вплив атрибутів видимості на генерацію коду
Для великих проєктів рекомендовано компілювати увесь код із глобальним прапорцем компілятора `-fvisibility=hidden`, явно експортуючи лише публічні функції інтерфейсу через макрос з атрибутом `__attribute__((visibility("default")))`.

Використання `visibility("hidden")` дає три системні переваги:
1. **Зменшення розміру бінарника:** Динамічна таблиця символів `.dynsym` та таблиця рядків `.dynstr` суттєво зменшуються, оскільки внутрішні функції модуля не потребують текстових імен у метаданих.
2. **Прискорення запуску процесу:** Динамічний лінкер `ld.so` здійснює значно менше релокацій `R_X86_64_JUMP_SLOT` під час завантаження програми.
3. **Прямі інструкції виклику:** Замість двох етапів (виклик переходу через PLT-трамплін та читання адреси з GOT) компілятор генерує пряму інструкцію `call offset`, де смещение обчислюється відносно поточного лічильника команд `RIP`.

Атрибут `visibility("protected")` займає проміжне становище: символ експортується назовні і його можуть викликати інші DSO, але внутрішні виклики всередині того самого DSO не піддаються перекриттю через `LD_PRELOAD`. Це запобігає атак на внутрішні допоміжні функції бібліотеки.

## 3. Прапорці компонувальника (Linker Flags)

Під час збірки виконуваних файлів та спільних бібліотек прапорці статичного компонувальника `ld` визначають правила формування таблиць релокації, вирішення сильних та слабких символів, а також поведінку динамічного завантажувача.

У таблиці нижче наведено основні прапорці `ld`, які керують розв'язанням та експортом символів.

| Прапорець компонувальника | Синтаксис GCC / Clang | Функціональне призначення |
| :--- | :--- | :--- |
| `--wrap=symbol` | `-Wl,--wrap,malloc` | Підміняє всі неконкретизовані виклики `symbol` на `__wrap_symbol`. Початкова функція доступна під іменем `__real_symbol`. |
| `-Bsymbolic` | `-Wl,-Bsymbolic` | Примушує динамічний лінкер спочатку шукати символи у власному DSO перед глобальним пошуком. Пригнічує перекриття глобальних функцій. |
| `-Bsymbolic-functions` | `-Wl,-Bsymbolic-functions` | Подібно до `-Bsymbolic`, але застосовується лише до функціональних символів (код), залишаючи глобальні змінні перекриваними. |
| `--dynamic-list` | `-Wl,--dynamic-list=list.txt` | Задає текстовий файл зі списком символів, які мають бути винесені в динамічну таблиці `.dynsym` (інші стають прихованими). |
| `-E` / `--export-dynamic` | `-Wl,-E` | Додає **усі** глобальні символи виконуваного бінарника до `.dynsym` (дозволяє `.so` бібліотекам викликати функції головної програми). |
| `-z defs` | `-Wl,-z,defs` | Видає помилку компонування, якщо у створюваній shared-бібліотеці залишаються нерозв'язані (undefined) символи. |

### Особливості прапорців --wrap та -Bsymbolic
Прапорець `--wrap=symbol` є унікальним інструментом статичного лінкера `ld`. На відміну від динамічного перекриття `LD_PRELOAD`, підміна `--wrap` відбувається повністю під час компіляції. Компонувальник змінює записи в таблиці релокацій об'єктного файла:
- Усі посилання на `symbol` перенаправляються на `__wrap_symbol`.
- Усі посилання на `__real_symbol` перенаправляються на оригінальне визначення `symbol`.

Це дозволяє будувати статичні перехоплювачі без використання бібліотеки `libdl.so` та викликів `dlsym`.

Прапорець `-Wl,-Bsymbolic` змінює прапорці в секції `DT_FLAGS` динамічного об'єкта, додаючи прапорець `DF_SYMBOLIC`. Це вказує динамічному лінкеру `ld.so` змінити алгоритм пошуку символів для даної бібліотеки: спочатку перевіряється власна таблиця `.dynsym` даного DSO, і лише якщо символ не знайдений усередині, пошук продовжується у global search scope.

Використання прапорця `-Wl,-z,defs` є обов'язковою кращою практикою при створенні плагінів та спільних бібліотек, оскільки воно запобігає появі прихованих нерозв'язаних посилань, які виявляються лише під час виконання програми в продакшені при виклику відсутньої функції.

## 4. Константи API dlfcn.h

Програмний інтерфейс `dlfcn.h` дозволяє динамічно завантажувати бібліотеки та шукати символи безпосередньо з C/C++ коду під час виконання (Run-time Dynamic Linking).

Функції `dlopen()` та `dlsym()` використовують прапорці та псевдо-дескриптори для налаштування середовища розв'язання символів під час виконання програми.

### 4.1 Прапорці завантаження (dlopen)

Спеціальні константи прапорців передаються другим аргументом у функцію `dlopen(const char *filename, int flags)` і визначають порядок релокацій та видимість завантажуваних символів у процесі.

| Константа | Опис дії на простір імен символів |
| :--- | :--- |
| `RTLD_LAZY` | Виконувати ліниве зв'язування функцій. Виклики PLT розв'язуються лише в момент першого виклику. |
| `RTLD_NOW` | Розв'язати всі неконкретизовані символи у DSO одразу під час виклику `dlopen()`. Якщо хоча б один символ відсутній — повертає `NULL`. |
| `RTLD_GLOBAL` | Експортувати символи з цієї бібліотеки у глобальний простір пошуку (global search scope). Наступні завантажені бібліотеки зможуть виконувати резолюцію проти них. |
| `RTLD_LOCAL` | Символи бібліотеки залишаються приватними для неї та її прямих залежностей (за замовчуванням). |
| `RTLD_NODELETE` | Не вивантажувати бібліотеку з пам'яті при виклику `dlclose()`. Корисно, якщо бібліотека має статичні деструктори або локальні дані thread-local. |
| `RTLD_NOLOAD` | Не завантажувати бібліотеку заново, а лише перевірити, чи вона вже завантажена у процес, і повернути її дескриптор. |

Вибір між `RTLD_LAZY` та `RTLD_NOW` визначає баланс між швидкістю відкриття бібліотеки та надійністю. Прапорець `RTLD_NOW` дозволяє виявити відсутність необхідних символів одразу в момент виклику `dlopen()`, у той час як `RTLD_LAZY` пришвидшує запуск, але може призвести до аварійного завершення програми пізніше під час виклику відсутньої функції.

Прапорець `RTLD_GLOBAL` робить символи завантаженого модулю доступними для наступних викликів `dlopen()` та для інших DSO у процесі. За замовчуванням використовується `RTLD_LOCAL`, що забезпечує ізоляцію простору імен символів між окремими плагінами.

### 4.2 Псевдо-дескриптори пошуку (dlsym)

Псевдо-дескриптори `RTLD_NEXT` та `RTLD_DEFAULT` передаються першим аргументом у функцію `dlsym(void *handle, const char *symbol)` замість дескриптора, повернутого `dlopen()`.

| Псевдо-дескриптор | Алгоритм пошуку символу |
| :--- | :--- |
| `RTLD_NEXT` | Шукати символ у наступному DSO у списку завантаження (search scope), пропустивши бібліотеку, яка викликає `dlsym()`. Базова основа для `LD_PRELOAD` hooks. |
| `RTLD_DEFAULT` | Шукати символ за стандартним глобальним порядком (починаючи з `LD_PRELOAD`, головного бінарника та перших завантажених `.so`). |

Псевдо-дескриптор `RTLD_NEXT` є критично важливим для створення прозорих перехоплювачів пам'яті та системних викликів, оскільки він дозволяє обійти власний hook і знайти наступне визначення символу у списку search scope динамічного лінкера.

У разі виникнення помилки при пошуку символу `dlsym()` повертає `NULL`. Для відрізнення дійсного значення `NULL` від помилки розв'язання слід викликати `dlerror()`, яка повертає текстовий рядок з описом останньої помилки або `NULL`, якщо помилки не було.
