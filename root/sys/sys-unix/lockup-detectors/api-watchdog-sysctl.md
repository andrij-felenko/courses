# 📋 Інтерфейс конфігурації та моніторингу детекторів зависань

Підсистеми виявлення зависань ядра Linux (Soft Lockup, Hard Lockup та Hung Task) надають системному адміністратору та інженеру надійності широкий набір інтерфейсів для динамічного налаштування порогів чутливості, вибору політики реагування (логування чи аварійна паніка) та отримання діагностичної телеметрії. Усі ці параметри доступні через віртуальну файлову систему `procfs` у каталозі `/proc/sys/kernel/`, а також можуть бути зафіксовані на етапі завантаження ядра через аргументи командного рядка завантажувача (GRUB/systemd-boot).

Конфігурація сторожових таймерів безпосередньо впливає на надійність інфраструктури: зависокий поріг затримує аварійне перемикання (failover) кластера високої доступності під час збою, тоді як занизький поріг у поєднанні з інтенсивним навантаженням або віртуалізацією може призвести до хибних панік ядра (false positive panics). Нижче наведено повну довідкову специфікацію параметрів керування, інтерфейсів примусової діагностики, діагностичних лічильників переривань, правил обробки подій гарячого підключення процесорів (CPU Hotplug) та правил їх взаємного узгодження.

## 1. Параметри ядра в `/proc/sys/kernel/`

Параметри конфігурації детекторів зависань згруповані у просторі `sysctl` під префіксами `kernel.watchdog*`, `kernel.softlockup*`, `kernel.hardlockup*`, `kernel.nmi_watchdog` та `kernel.hung_task*`. Зміни, внесені через команду `sysctl -w` або прямий запис у файли `/proc/sys/kernel/`, обробляються ядерними функціями-обробниками (наприклад, `proc_dointvec_minmax`, `proc_dointvec_softlockup`) і набувають чинності миттєво без перезавантаження операційної системи.

| Параметр sysctl | Тип даних | Замовчування | Допустимі значення | Призначення та механізм дії |
| :--- | :--- | :--- | :--- | :--- |
| `kernel.watchdog` | ціле (`int`) | `1` | `0` або `1` | Глобальний головний перемикач усіх сторожових таймерів ядра (як Soft Lockup, так і Hard Lockup). Запис `0` зупиняє всі ядерні потоки `watchdog/K`, знімає таймери `hrtimer` та звільняє лічильники `perf_event`. Запис `1` перезапускає всю підсистему заново. |
| `kernel.watchdog_thresh` | ціле (`int`) | `10` | `1 .. 60` (сек) | Базовий часовий поріг у секундах для детекторів. Hard Lockup фіксується через `watchdog_thresh` секунд без переривань. Soft Lockup фіксується через `2 * watchdog_thresh` секунд (типово 20 с) недосяжності kthread. Період вибірки `hrtimer` розраховується як `(watchdog_thresh * 2) / 5` (типово 4 с). |
| `kernel.watchdog_cpumask` | бітова маска (`cpumask`) | усі активні CPU | Hex-маска або діапазон (наприклад, `0-15`) | Визначає підмножину логічних процесорів, на яких дозволено роботу сторожових таймерів. Корисно для систем реального часу (RT), де виділені ядра ізольовані від таймерів ядра (`nohz_full`, isolcpus). |
| `kernel.soft_watchdog` | ціле (`int`) | `1` | `0` або `1` | Локальний перемикач виключно детектора Soft Lockup. Дозволяє вимкнути програмний наглядач, зберігши активним апаратний NMI Watchdog. |
| `kernel.nmi_watchdog` | ціле (`int`) | `1` | `0` або `1` | Локальний перемикач детектора Hard Lockup (NMI Watchdog). Запис `0` звільняє апаратні лічильники продуктивності PMU, що необхідно для запуску профайлерів `perf top` або `vtune`. |
| `kernel.softlockup_panic` | ціле (`int`) | `0` | `0` або `1` | Визначає дію при виявленні Soft Lockup. Якщо `0` — ядро друкує попередження `BUG: soft lockup` та стек у `dmesg` і продовжує роботу. Якщо `1` — негайно викликається `panic()`, що ініціює перезавантаження або зняття дампа через `kdump`. |
| `kernel.hardlockup_panic` | ціле (`int`) | `1` (або `0` залежно від дистрибутива) | `0` або `1` | Визначає дію при фіксації Hard Lockup через NMI. У високодоступних серверах типово встановлюється в `1`, оскільки ядро з вимкненими IRQ не здатне відновитися самостійно. |
| `kernel.softlockup_all_cpu_backtrace` | ціле (`int`) | `0` | `0` або `1` | Якщо `1`, ядро при фіксації Soft Lockup надсилає міжпроцесорне переривання NMI IPI на всі інші ядра процесора для одночасного зняття дампів їхніх стеків (допомагає знайти ядро, яке утримує заблокований спінлок). |
| `kernel.hardlockup_all_cpu_backtrace` | ціле (`int`) | `0` | `0` або `1` | Якщо `1`, ядро при фіксації Hard Lockup надсилає NMI на всі інші ядра CPU для збереження глобального зрізу стану всієї SMP-системи. |
| `kernel.hung_task_timeout_secs` | ціле (`ulong`) | `120` | `0 .. LONG_MAX` (сек) | Максимальний допустимий час безперервного перебування задачі у стані непереривного сну `TASK_UNINTERRUPTIBLE` (D-state) без жодного перемикання контексту. Значення `0` повністю вимикає роботу демона `khungtaskd`. |
| `kernel.hung_task_panic` | ціле (`int`) | `0` | `0` або `1` | Викликати системну паніку `panic()` при виявленні завислої в D-state задачі. За замовчуванням `0` (лише друк попередження в `dmesg`). |
| `kernel.hung_task_check_count` | ціле (`ulong`) | `PID_MAX_LIMIT` (4194304) | `1 .. ULONG_MAX` | Максимальна кількість задач і потоків, яку демон `khungtaskd` перевіряє за один прохід циклу сканування (захист від тривалого утримання RCU-блокування на великих серверах). |
| `kernel.hung_task_warnings` | ціле (`ulong`) | `10` | `0 .. ULONG_MAX` | Максимальна кількість попереджень про завислі задачі, яку ядро записує в системний журнал до припинення виводу (захист буфера `dmesg` від переповнення). Значення `-1` означає нескінченний ліміт. |
| `kernel.hung_task_check_interval_secs` | ціле (`ulong`) | `0` | `0 .. ULONG_MAX` | Інтервал сну демона `khungtaskd`. Якщо встановлено в `0`, ядро автоматично вираховує його як `hung_task_timeout_secs / 2` (типово 60 с). |
| `kernel.hung_task_selective_monitoring` | ціле (`int`) | `0` | `0` або `1` | Якщо `1`, демон `khungtaskd` перевіряє не всі підряд процеси в системі, а лише ті, у яких виставлено спеціальний прапорець моніторингу в `task_struct`. |

## 2. Механіка динамічного перерахунку часових інтервалів

Коли системний адміністратор змінює параметр `kernel.watchdog_thresh`, ядро виконує каскад внутрішніх оновлень. Базове значення `watchdog_thresh` визначає математичні пропорції всіх інших часових вікон:

1. **Інтервал таймера `watchdog_hrtimer`:**
   Таймер високої точності спрацьовує з періодом `sample_period = (watchdog_thresh * 2) / 5`. При стандартному порозі 10 секунд період дорівнює 4 секундам. Якщо поріг зменшити до 5 секунд (для надшвидкого виявлення збоїв на телеком-вузлах), період таймера автоматично скорочується до 2 секунд, що збільшує частоту перевірок і створює додаткове навантаження на систему переривань.
2. **Поріг спрацьовування Soft Lockup:**
   Розраховується як подвійне значення базового порогу: `softlockup_thresh = watchdog_thresh * 2`. Це гарантує, що потік ядра `watchdog/K` має щонайменше 5 послідовних шансів отримати квант процесорного часу між перевірками таймера перед тим, як ядро оголосить тривогу.
3. **Період переповнення лічильника `perf_event`:**
   Функція `hw_nmi_get_sample_period(watchdog_thresh)` перераховує кількість тактів CPU між двома NMI-перериваннями. Якщо номінальна частота процесора становить 3.0 ГГц, лічильник програмується на переповнення через кожні `3.0 * 10^9 * watchdog_thresh` тактів.
4. **Поведінка під час гарячого підключення процесорів (CPU Hotplug):**
   Підсистема сторожових таймерів підписана на системні повідомлення ланцюжка `cpuhp` (CPU Hotplug). Коли нове ядро переходить у стан `CPUHP_AP_ONLINE`, ядро автоматично виділяє для нього структуру події `perf_event`, створює прив'язаний потік `watchdog/K` та запускає локальний таймер `watchdog_hrtimer`. При відключенні ядра (`CPUHP_AP_OFFLINE`) потік коректно завершується, а лічильники повертаються до пулу вільних ресурсів.

## 3. Керування маскою процесорів `watchdog_cpumask`

Параметр `kernel.watchdog_cpumask` приймає шістнадцятковий бітовий вектор або текстовий список діапазонів процесорів. Цей механізм є критично важливим для конфігурації систем реального часу (RT) та телекомунікаційних додатків на базі DPDK:

```bash
# Приклад: увімкнути watchdog лише на ядрах 0-3 на 16-ядерній машині
sysctl -w kernel.watchdog_cpumask="0-3"

# Еквівалентний запис у шістнадцятковій формі (біти 0..3 активні -> 0x000f):
echo 000f > /proc/sys/kernel/watchdog_cpumask
```

Коли ядро вилучається з маски `watchdog_cpumask`, підсистема негайно призупиняє таймер `hrtimer` та звільняє апаратний лічильник PMU на цьому ядрі. Це гарантує, що ізольоване процесорне ядро (`isolcpus`), на якому виконується цикл обробки мережевих пакетів або критичний цикл керування робототехнікою, не отримуватиме сторонніх переривань NMI та не витрачатиме такти на перемикання контексту з потоком `watchdog/K`.

## 4. Параметри командного рядка завантажувача (Boot Parameters)

Якщо системний збій виникає на ранніх етапах ініціалізації ядра (до монтування кореневої файлової системи та виконання сценаріїв `systemd-sysctl`), конфігурувати сторожові таймери необхідно безпосередньо через параметри командного рядка ядра в конфігурації завантажувача GRUB у рядку `GRUB_CMDLINE_LINUX`.

```text
# Приклад конфігурації завантаження для високодоступного кластерного вузла:
console=ttyS0,115200 nmi_watchdog=1 softlockup_panic=1 hardlockup_panic=1 hung_task_panic=1 watchdog_thresh=5
```

### Специфікація параметрів завантаження:

1. `nowatchdog`
   Повністю відключає ініціалізацію підсистеми watchdog (як Soft Lockup, так і Hard Lockup детекторів) під час старту ядра. Дозволяє завантажити ядро на несправному або нестандартному апаратному забезпеченні, де некоректно працює емуляція Local APIC.
2. `noswatchdog`
   Відключає лише Soft Lockup Detector (не створює per-CPU потоки `watchdog/K` та не запускає відповідні `hrtimer`).
3. `nohwatchdog`
   Відключає лише Hard Lockup Detector (не виділяє апаратні лічильники `perf_event` та не реєструє NMI-обробники).
4. `nmi_watchdog=1` або `nmi_watchdog=0`
   Примусово активує (`1`) або деактивує (`0`) NMI Watchdog на базі апаратних лічильників Local APIC.
5. `nmi_watchdog=panic`
   Вмикає NMI Watchdog і одночасно виставляє параметр `hardlockup_panic=1`.
6. `watchdog_thresh=N`
   Встановлює базовий часовий інтервал детектора у `N` секунд (еквівалентно запису в `kernel.watchdog_thresh`).
7. `softlockup_panic=1` / `softlockup_panic=0`
   Вмикає або вимикає виклик фатальної паніки `panic()` при фіксації Soft Lockup.
8. `hung_task_panic=1` / `hung_task_panic=0`
   Вмикає або вимикає виклик `panic()` при виявленні задачі, що застрягла у стані `TASK_UNINTERRUPTIBLE`.

## 5. Діагностичні лічильники в `/proc/interrupts` та SysRq

Для перевірки функціонування апаратних немаскованих переривань NMI системний інженер може інспектувати файл `/proc/interrupts`. У ньому відображається кількість переривань кожного типу, оброблених кожним логічним ядром процесора від моменту старту системи.

```text
$ grep -E "NMI|LOC" /proc/interrupts
 NMI:       1420       1398       1411       1405   Non-maskable interrupts
 LOC:   89214502   84102911   87341209   86510423   Local timer interrupts
```

- **Рядок `NMI`:** Якщо значення лічильника в стовпцях процесорів рівномірно зростають (приблизно на 1 переривання кожні `watchdog_thresh` секунд), апаратний Hard Lockup Detector успішно запрограмований і активний. Якщо лічильник дорівнює нулю або не змінюється — NMI Watchdog вимкнено або апаратний PMU недоступний (наприклад, у віртуальній машині без емуляції vPMU).
- **Рядок `LOC`:** Показує спрацьовування локального таймера APIC, від якого залежить виконання обробника `watchdog_hrtimer`.

### Примусова діагностика через `/proc/sysrq-trigger`

Якщо операційна система перестала відповідати на мережеві запити або команди термінала, але ядро ще здатне обробляти апаратні переривання клавіатури або послідовної консолі, діагностичну інформацію можна отримати через механізм **Magic SysRq**:

```bash
# Зняти стек викликів (Call Trace) активних процесів на всіх ядрах CPU через NMI IPI:
echo l > /proc/sysrq-trigger

# Вивести список усіх задач у системі та їхній стан (R, S, D, Z) зі стеком викликів:
echo t > /proc/sysrq-trigger

# Вивести список усіх блокувань (locks), утримуваних процесами (вимагає CONFIG_LOCKDEP):
echo d > /proc/sysrq-trigger

# Примусово ініціювати фатальну паніку ядра для отримання дампа vmcore:
echo c > /proc/sysrq-trigger
```

## 6. Специфікація форматів виводу логів у `dmesg`

Кожен із трьох детекторів має власний стандартизований формат повідомлення про аварійний стан, оптимізований для автоматичного парсингу системами моніторингу та агрегаторами логів (`systemd-journald`, `Vector`, `Promtail`, `kdump-tools`):

### Шаблон заголовка Soft Lockup:
```text
BUG: soft lockup - CPU#<ID> stuck for <N>s! [<COMM>:<PID>]
```
- `<ID>`: Номер процесорного ядра, на якому застряг потік.
- `<N>`: Кількість секунд, протягом яких потік `watchdog/<ID>` не отримував процесорний час.
- `<COMM>`: Назва виконуваного файлу або ядерного потоку, що виконувався в момент зрізу.
- `<PID>`: Ідентифікатор процесу або потоку.

### Шаблон заголовка Hard Lockup:
```text
Watchdog detected hard LOCKUP on cpu <ID>
```
Повідомлення генерується в контексті NMI-обробника. Слідом за ним негайно виводиться дамп регістрів процесора (RIP, RSP, EFLAGS) та розкрутка стека виконання перерваного ядра.

### Шаблон заголовка Hung Task:
```text
INFO: task <COMM>:<PID> blocked for more than <N> seconds.
      "echo 0 > /proc/sys/kernel/hung_task_timeout_secs" disables this message.
```
Виводиться демоном `khungtaskd` разом зі стеком блокування функції (наприклад, `io_schedule()`, `mutex_lock()`, `down()`), що дає змогу точно встановити системний виклик або точку блокування на дисковому I/O.
