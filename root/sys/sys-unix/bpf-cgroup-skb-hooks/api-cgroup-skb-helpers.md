# 📋 Інтерфейс та хелпери BPF_CGROUP_INET_INGRESS/EGRESS

Повний довідник інтерфейсів, системних викликів, полів контексту `struct __sk_buff` та функцій-хелперів ядра Linux для розробки eBPF-програм типу `BPF_PROG_TYPE_CGROUP_SKB` та інших cgroup-хуків.

## 1. Архітектурний контракт та класифікація cgroup-хуків

Технологія прикріплення eBPF-програм до ієрархії Control Groups v2 надає інтерфейс інтерцепції мережевих подій безпосередньо на межі процесів контейнера або системної служби. На відміну від класичних мережевих хуків (таких як XDP чи TC clsact), які прив'язані до конкретного мережевого адаптера (`struct net_device`), cgroup-хуки прив'язуються до файлового дескриптора каталогу cgroupv2 в об'єктній файловій системі `cgroupfs`.

Підсистема ядра розрізняє кілька основних типів програм eBPF для cgroup, кожен з яких оперує власним спеціалізованим контекстом виконання та викликається на відповідних стадіях життєвого циклу мережевих з'єднань і пакетів:

1. **`BPF_PROG_TYPE_CGROUP_SKB`:** Основний тип програм для фільтрації готових мережевих пакетів (`struct sk_buff`). Вони викликаються під час проходження пакетів у напрямках `BPF_CGROUP_INET_INGRESS` та `BPF_CGROUP_INET_EGRESS`.
2. **`BPF_PROG_TYPE_CGROUP_SOCK`:** Програми аналізу та контролю створення та закриття сокетів (`BPF_CGROUP_INET_SOCK_CREATE` та `BPF_CGROUP_INET_SOCK_RELEASE`). Вони працюють із контекстом `struct bpf_sock`.
3. **`BPF_PROG_TYPE_CGROUP_SOCK_ADDR`:** Програми перехоплення та прозорого перерозподілу адрес під час системних викликів `bind()`, `connect()`, `sendto()`, `recvfrom()` (`BPF_CGROUP_INET4_BIND`, `BPF_CGROUP_INET6_BIND`, `BPF_CGROUP_INET4_CONNECT`, `BPF_CGROUP_INET6_CONNECT`, `BPF_CGROUP_UDP4_SENDMSG`, `BPF_CGROUP_UDP6_SENDMSG`).

### Специфікація режимів прикріплення (Attach Types)

Кожен тип прикріплення має чітко визначену точку виклику в коді ядра Linux та свій контекст даних.

#### BPF_CGROUP_INET_INGRESS
* **Точка перехоплення у ядрі:** Викликається у транспортному стеку (в коді `tcp_v4_rcv`, `udp_rcv`, `raw_rcv`) безпосередньо після того, як ядро виконало пошук локального сокета-одержувача в хеш-таблиці `inet_lookup`, але до того, як пакет буде вставлено у вхідну чергу сокета (`sk_receive_queue`).
* **Контекст виконання:** Вказівник на структуроване представлення `struct __sk_buff*`.
* **Дозволені дії:** Перевірка IP-адрес, портів, протоколу, міток пакета, читання даних пакета.
* **Семантика повернення:** Значення `1` дозволяє передачу пакета сокету. Значення `0` відкидає пакет; ядро звільняє пам'ять `skb`, а процес-одержувач не отримує сповіщення.

#### BPF_CGROUP_INET_EGRESS
* **Точка перехоплення у ядрі:** Викликається на етапі відправлення вихідного пакета (в коді `ip_build_and_send_pkt`, `tcp_transmit_skb`, `ip6_xmit`) після формування заголовків транспортного та мережевого рівнів, але до обчислення IP-маршрутизації та передачі пакета в підсистему Qdisc / TC.
* **Контекст виконання:** Вказівник на `struct __sk_buff*`. На цьому етапі Ethernet-заголовок ще відсутній, тому `skb->data` вказує безпосередньо на IP-заголовок (`struct iphdr` або `struct ipv6hdr`).
* **Семантика повернення:** Значення `1` дозволяє подальшу маршрутизацію пакета. Значення `0` негайно припиняє обробку пакета й повертає системному виклику `sendmsg()` або `write()` помилку `EPERM` (Operation not permitted).

#### BPF_CGROUP_INET_SOCK_CREATE
* **Точка перехоплення у ядрі:** Викликається під час виконання системного виклику `socket(domain, type, protocol)` у функції ядра `inet_create()`, після виділення структури сокета `struct socket`, але до його підключення до таблиць ядра та повернення файлового дескриптора в user-space.
* **Контекст виконання:** Вказівник на структуру `struct bpf_sock*`, яка містить поля `family`, `type`, `protocol`, `src_ip4`, `src_ip6`, `src_port`.
* **Семантика повернення:** Значення `1` дозволяє створення сокета. Значення `0` перериває системний виклик `socket()` і повертає застосунку помилку `EPERM`.

#### BPF_CGROUP_INET4_CONNECT / BPF_CGROUP_INET6_CONNECT
* **Точка перехоплення у ядрі:** Викликається в коді `__sys_connect()` під час ініціалізації з'єднання.
* **Контекст виконання:** Структура `struct bpf_sock_addr*`.
* **Особливість:** Програма має право модифікувати поля `user_ip4`, `user_ip6` та `user_port`. Це дає змогу реалізувати прозорий балансувальник навантаження (Transparent Service Load Balancer), який перенаправляє запит на іншу IP-адресу без використання NAT у Netfilter.

## 2. Прапорці прикріплення та алгоритм обчислення ієрархії (Attach Flags)

При прикріпленні eBPF-програми до cgroupv2 за допомогою системного виклику `bpf(BPF_PROG_ATTACH, ...)` або `bpf_prog_attach()` розробник вказує комбінацію бітових прапорців `attach_flags`. Ці прапорці визначають можливість комбінування та перевизначення програм уздовж дерева cgroup.

### Повний опис прапорців `linux/bpf.h`

```c
#define BPF_F_ALLOW_OVERRIDE    (1U << 0)
#define BPF_F_ALLOW_MULTI       (1U << 1)
#define BPF_F_REPLACE           (1U << 2)
```

#### 1. Ексклюзивний режим (Режим за замовчуванням: `attach_flags = 0`)
* **Механізм:** Прикріплює програму як єдиного володаря даного хука на вказаному вузлі cgroup.
* **Обмеження:** Якщо на будь-якому з батьківських або дочірніх вузлів ієрархії вже є прикріплена програма для цього хука, системний виклик прикріплення завершиться з помилкою `-EBUSY` або `-EEXIST`.

#### 2. Режим `BPF_F_ALLOW_OVERRIDE`
* **Механізм:** Дозволяє прикріпити програму на вищому рівні cgroup, але дає дозвіл дочірнім cgroups прикріплювати власні програми для цього ж хука, які повністю **перекриють** (override) дію батьківської програми.
* **Поведінка:** Якщо процес знаходиться всередині дочірньої cgroup, яка встановила власну програму з перевизначенням, ядро виконає лише дочірню програму. Батьківська програма буде ігноруватися.

#### 3. Режим `BPF_F_ALLOW_MULTI`
* **Механізм:** Дозволяє прикріплювати кілька eBPF-програм до одного хука на одному вузлі cgroup, а також утворювати послідовні ланцюжки обчислень уздовж всієї ієрархії cgroup v2.
* **Алгоритм виконання ядра:**
  1. Ядро будує внутрішній впорядкований масив програм `struct bpf_prog_array`.
  2. Виконання здійснюється послідовно від дочірньої cgroup до кореневої cgroup (або навпаки).
  3. Для кожного елемента масиву виконується JIT-скомпільована програма eBPF.
  4. Застосовується строго короткозамикальна логіка «І» (Short-circuit AND):
     * Якщо програма повертає `1`, ядро негайно передає керування наступній програмі у масиві.
     * Якщо програма повертає `0`, ядро негайно перериває виконання ланцюжка, відкидає пакет і більше не викликає решту програм.

### Коди помилок при операціях прикріплення

* `-EBUSY`: Спроба прикріпити програму з прапорцем `BPF_F_ALLOW_MULTI` до cgroup, де вже є програма, прикріплена в ексклюзивному режимі (або навпаки).
* `-EEXIST`: Спроба повторно прикріпити ту саму програму без використання прапорця `BPF_F_REPLACE`.
* `-EINVAL`: Некоректний дескриптор cgroup, непідтримуваний `attach_type`, або несумісні прапорці.
* `-EPERM`: Брак прав доступу (потрібно мати привілей `CAP_BPF` або `CAP_SYS_ADMIN` у початковому просторі імен користувачів).

## 3. Контекст структури __sk_buff для BPF_PROG_TYPE_CGROUP_SKB

Коли викликається програма типу `BPF_PROG_TYPE_CGROUP_SKB`, верифікатор BPF надає їй безпечний доступ до полів метаданих пакета через структуру `struct __sk_buff`. Вона є дзеркальним відображенням внутрішньої структури ядра `struct sk_buff`.

### Повна структура `struct __sk_buff` (`<linux/bpf.h>`)

```c
struct __sk_buff {
    __u32 len;
    __u32 pkt_type;
    __u32 protocol;
    __u32 mark;
    __u32 queue_mapping;
    __u32 priority;
    __u32 ingress_ifindex;
    __u32 ifindex;
    __u32 tc_index;
    __u32 cb[5];
    __u32 napi_id;
    __u32 wire_len;
    __u32 gso_segs;
    __u32 gso_size;
    __u32 tstamp;
    __u32 data;
    __u32 data_end;
    __u32 local_ip4;
    __u32 remote_ip4;
    __u32 local_ip6[4];
    __u32 remote_ip6[4];
    __u32 local_port;
    __u32 remote_port;
    __u32 family;
};
```

### Детальний аналіз полів та їхніх обмежень

* `len` (`__u32`): Загальна довжина пакета в байтах (включаючи заголовки та корисне навантаження). Доступне лише для читання.
* `pkt_type` (`__u32`): Категорія вхідного пакета (`PACKET_HOST`, `PACKET_BROADCAST`, `PACKET_MULTICAST`, `PACKET_OTHERHOST`).
* `protocol` (`__u32`): Мережевий протокол пакета у мережевому порядку байтів (Big-Endian). Для IPv4 містить значення `bpf_htons(ETH_P_IP)` (`0x0800`), для IPv6 — `bpf_htons(ETH_P_IPV6)` (`0x86DD`).
* `mark` (`__u32`): 32-бітна мітка skb mark. Може читатися програмою для прийняття рішень.
* `ifindex` (`__u32`): Системний індекс мережевого інтерфейсу, пов'язаного з пакетом.
* `data` (`__u32`): 32-бітне числове значення, яке під час виконання приводиться до вказівника на початок даних пакета (`void *`).
  * Для `BPF_CGROUP_INET_EGRESS` вказівник `data` вказує на початок IP-заголовка (`struct iphdr` або `struct ipv6hdr`).
  * Для `BPF_CGROUP_INET_INGRESS` вказівник `data` також вказує на IP-заголовок.
* `data_end` (`__u32`): Вказівник на кінець лінійної пам'яті пакета. Перед будь-яким розпакуванням даних програма **зобов'язана** виконувати перевірку меж для верифікатора: `data + sizeof(struct iphdr) <= data_end`.
* `cb[5]` (`__u32`): Масив із п'яти 32-бітних регістрів Scratchpad Control Block. Програма може вільно читати та записувати значення в `cb[]` для передачі стану між хвостовими викликами (`bpf_tail_call`).
* `family` (`__u32`): Родина адрес сокета, який створив пакет (`AF_INET` для 2, `AF_INET6` для 10).
* `local_ip4` / `remote_ip4` (`__u32`): Локальна та віддалена IPv4-адреса сокета у мережевому порядку байтів.
* `local_ip6` / `remote_ip6` (`__u32[4]`): Локальна та віддалена IPv6-адреса сокета (масив із чотирьох 32-бітних слів).
* `local_port` / `remote_port` (`__u32`): Локальний та віддалений мережевий порт у мережевому порядку байтів (значення локального порту зберігається у хостовому або мережевому порядку залежно від версії ядра, тому рекомендується читати транспортні заголовки через `bpf_skb_load_bytes`).

## 4. Каталог хелперів ядра для BPF_PROG_TYPE_CGROUP_SKB

Програми типу `BPF_PROG_TYPE_CGROUP_SKB` мають доступ до строго обмеженого набору хелперів ядра, перерахованих у таблиці викликів `cg_skb_func_proto()`.

### 1. Хелпери читання даних пакета

#### `bpf_skb_load_bytes`
```c
long bpf_skb_load_bytes(const struct __sk_buff *skb, u32 offset, void *to, u32 len);
```
* **Призначення:** Безпечно копіює `len` байтів із мережевого пакета `skb`, починаючи з відносного зміщення `offset`, у буфер `to` на стеку BPF-програми.
* **Перевага:** Дозволяє читати дані з нелінійних та фрагментованих пакетів (skb paged buffers), де прямий доступ через `data` та `data_end` виходить за межі першої сторінки.
* **Повертає:** `0` при успішному зчитуванні; `-EFAULT` або `-EINVAL`, якщо `offset + len` перевищує довжину пакета.

#### `bpf_skb_load_bytes_relative`
```c
long bpf_skb_load_bytes_relative(const struct __sk_buff *skb, u32 offset, void *to, u32 len, u32 start_header);
```
* **Призначення:** Читає байти відносно вказаного заголовка `start_header`. Аргумент `start_header` може набувати значень:
  * `BPF_HDR_START_MAC` (0): Відносно заголовка L2 (Ethernet).
  * `BPF_HDR_START_NET` (1): Відносно заголовка L3 (IP).

### 2. Хелпери роботи з BPF Maps

#### `bpf_map_lookup_elem`
```c
void *bpf_map_lookup_elem(struct bpf_map *map, const void *key);
```
* **Призначення:** Шукає елемент за ключем `key` у мапі `map`.
* **Повертає:** Вказівник на значення у пам'яті мапи або `NULL`, якщо елемент відсутній. Перед використанням повернутого вказівника програма **зобов'язана** перевірити його на `NULL`.

#### `bpf_map_update_elem`
```c
long bpf_map_update_elem(struct bpf_map *map, const void *key, const void *value, u64 flags);
```
* **Призначення:** Додає або оновлює елемент у мапі BPF.
* **Прапорці:** `BPF_ANY` (0) — оновити або створити; `BPF_NOEXIST` (1) — створити лише якщо відсутній; `BPF_EXIST` (2) — оновити лише наявний.

#### `bpf_map_delete_elem`
```c
long bpf_map_delete_elem(struct bpf_map *map, const void *key);
```
* **Призначення:** Видаляє елемент із ключем `key` із мапи.

### 3. Хелпери отримання контексту сокетів та cgroup

#### `bpf_get_current_cgroup_id`
```c
u64 bpf_get_current_cgroup_id(void);
```
* **Призначення:** Повертає 64-бітний глобальний ідентифікатор cgroup v2 для поточного процесу, який згенерував мережеву подію.

#### `bpf_get_socket_cookie`
```c
u64 bpf_get_socket_cookie(void *ctx);
```
* **Призначення:** Повертає унікальний 64-бітний монотонний ідентифікатор (cookie) сокета, асоційованого з пакетом `skb`. Дозволяє відстежувати належність пакетів до одного сокета протягом його життя.

#### `bpf_sk_storage_get`
```c
void *bpf_sk_storage_get(struct bpf_map *map, void *sk, void *value, u64 flags);
```
* **Призначення:** Отримує або ініціалізує локальне сховище сокета в мапі типу `BPF_MAP_TYPE_SK_STORAGE`. Це забезпечує швидке збереження довільних метаданих безпосередньо в структурі сокета ядра з константним часом доступу `O(1)`.

#### `bpf_sk_storage_delete`
```c
long bpf_sk_storage_delete(struct bpf_map *map, void *sk);
```
* **Призначення:** Видаляє метадані, збережені у локальному сховищі сокета `sk`.

### 4. Хелпери роботи з опціями сокетів

#### `bpf_getsockopt` / `bpf_setsockopt`
```c
long bpf_getsockopt(void *bpf_socket, int level, int optname, void *optval, int optlen);
long bpf_setsockopt(void *bpf_socket, int level, int optname, void *optval, int optlen);
```
* **Призначення:** Дозволяє cgroup BPF-програмам читати та змінювати налаштування сокета (наприклад, `SO_MARK`, `TCP_NODELAY`, `SO_BINDTODEVICE`) безпосередньо в момент підключення або зв'язування.

### 5. Хелпери трасування та подій

#### `bpf_perf_event_output`
```c
long bpf_perf_event_output(void *ctx, struct bpf_map *map, u64 flags, void *data, u64 size);
```
* **Призначення:** Відправляє бінарну структуру `data` розміром `size` у кільцевий буфер Perf Event Array (`BPF_MAP_TYPE_PERF_EVENT_ARRAY`) для асинхронного читання в user-space.

#### `bpf_trace_printk`
```c
long bpf_trace_printk(const char *fmt, u32 fmt_size, ...);
```
* **Призначення:** Записує форматований рядок у відлагоджувальний лог ядра `/sys/kernel/tracing/trace_pipe`. У виробничому коді не рекомендується через обмеження швидкодії.

#### `bpf_trace_vprintk`
```c
long bpf_trace_vprintk(const char *fmt, u32 fmt_size, const void *data, u32 data_len);
```
* **Призначення:** Розширений аналог `bpf_trace_printk`, який приймає масив параметрів `data` довільної довжини, дозволяючи форматувати складні повідомлення відлагодження eBPF-програм у відлагоджувальному лозі ядра Linux.

#### `bpf_ktime_get_ns`
```c
u64 bpf_ktime_get_ns(void);
```
* **Призначення:** Повертає монотонний час системного годинника ядра у наносекундах (від моменту завантаження системи). Використовується для вимірювання затримок обробки та інтервалів між пакетами.

## 5. Обмеження верифікатора BPF та правила стек-пам'яті

При розробці eBPF-програм типу `BPF_PROG_TYPE_CGROUP_SKB` верифікатор ядра Linux (BPF Verifier) застосовує суворі перевірки безпеки виконання:

1. **Обмеження розміру стеку (512 байтів):** Загальний обсяг локальних змінних eBPF-програми не повинен перевищувати 512 байтів. Великі структури (наприклад, `struct iphdr` або буфери логування) слід розміщувати локально і не дублювати. Для збереження великих проміжних даних використовуються мапи `BPF_MAP_TYPE_PERCPU_ARRAY`.
2. **Перевірка меж читання пам'яті:** Верифікатор відстежує стан кожного регістру. Читання пам'яті через вказівник `data` вимагає обов'язкової попередньої перевірки `data + offset <= data_end` в тій самій гілці виконання безпосередньо перед інструкцією читання.
3. **Обмеження на цикли (Loop Limits):** Усі цикли в програмі повинні мати вказані статичні межі, відомі на етапі компіляції (за допомогою макросу `#pragma unroll`), щоб верифікатор міг довести гарантоване завершення програми за скінченну кількість інструкцій.
4. **Заборона модифікації пакета:** Верифікатор відхиляє будь-які спроби використання модифікуючих хелперів (наприклад, `bpf_l3_csum_replace` або `bpf_skb_store_bytes`) у програмах `CGROUP_SKB`, оскільки контекст є строго Read-Only.

## 6. User-space Libbpf API та Системні Виклики

У просторі користувача розробники взаємодіють із cgroup BPF за допомогою бібліотеки `libbpf` або прямого системного виклику `bpf()`.

### 1. Системний виклик `bpf()` (`<linux/bpf.h>`)

При використанні низькорівневого виклику `sys_bpf` структура атрибутів ініціалізується таким чином:

```c
union bpf_attr attr = {};
attr.attach_type = BPF_CGROUP_INET_EGRESS;
attr.target_fd   = cgroup_fd; // FD відкритого каталогу cgroupv2
attr.attach_bpf_fd = prog_fd;  // FD завантаженої eBPF програми
attr.attach_flags  = BPF_F_ALLOW_MULTI;

int ret = syscall(__NR_bpf, BPF_PROG_ATTACH, &attr, sizeof(attr));
```

### 2. Виклики High-Level Libbpf (`<bpf/libbpf.h>`)

#### `bpf_prog_attach`
```c
int bpf_prog_attach(int prog_fd, int target_fd, enum bpf_attach_type type, unsigned int flags);
```
* **Призначення:** Прикріплює BPF-програму `prog_fd` до cgroup-каталогу `target_fd` для вказаного `type` з бітовими прапорцями `flags`.

#### `bpf_prog_detach2`
```c
int bpf_prog_detach2(int prog_fd, int target_fd, enum bpf_attach_type type);
```
* **Призначення:** Відкріплює програму з дескриптором `prog_fd` від хука `type` на cgroup `target_fd`.

#### `bpf_prog_query`
```c
int bpf_prog_query(int target_fd, enum bpf_attach_type type, __u32 query_flags,
                   __u32 *attach_flags, __u32 *prog_ids, __u32 *prog_cnt);
```
* **Призначення:** Повертає список ідентифікаторів (ID) eBPF-програм, прикріплених до cgroup `target_fd` для хука `type`. Аргумент `prog_cnt` передає розмір масиву `prog_ids` і приймає кількість реально знайдених програм.

## 7. Інспекція та діагностика за допомогою bpftool

Системна утиліта `bpftool` є основным інструментом для огляду прикріплених cgroup-програм у реальній системі.

### Основні діагностичні команди

#### 1. Дерево cgroup та прикріплені BPF-програми
```bash
bpftool cgroup tree
```
* Виводить ієрархію cgroupv2 та показує ID прикріплених BPF-програм, їхні типи та прапорці прикріплення.

#### 2. Перегляд програм для конкретного каталогу
```bash
bpftool cgroup show /sys/fs/cgroup/kubepods.slice/
```
* Показує список ID усіх прикріплених BPF-програм для даної cgroup.

#### 3. Дамп JIT-скомпільованого коду програми
```bash
bpftool prog dump jited id 42
```
* Виводить ассемблерні інструкції x86_64/ARM64 для JIT-скомпільованої eBPF-програми з ID 42.

#### 4. Дамп трансльованого байткоду BPF (xlated)
```bash
bpftool prog dump xlated id 42 visual
```
* Виводить байткод BPF після оптимізацій верифікатора. Опція `visual` будує граф потоку керування (Control Flow Graph) для Graphviz.

Цей довідник охоплює повний спектр системних викликів, типів мап, бітових прапорців та функцій-хелперів, які використовуються системними розробниками при створенні, налагодженні, автоматичному юніт-тестуванні та високопродуктивній діагностиці cgroup BPF програм у сучасній системній інфраструктурі операційних систем Linux, гарантуючи надійне виконання політик мережевої безпеки та повний контроль над проходженням трафіку через ядро.
