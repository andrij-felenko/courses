# ⚙️ Розбираємо готовий образ домівки: що видно до пароля й що після

Беремо живий файл `/home/andrij.home` і знімаємо з нього шар за шаром інструментами, які про `homed` не знають нічого — `losetup`, `sfdisk`, `cryptsetup`, `mount`, `jq`. Мета одна: побачити на власні очі, де саме проходить межа, яку проводить пароль. До неї сторонній читає з файла чимало; за нею — усе решта, і між цими двома станами немає нічого проміжного.

## Спершу вимкнути домівку

Поки домівка активна, цей файл — змонтований блоковий пристрій, у який пишуть просто зараз. Прочитаний з-під працюючої системи, він дасть рвані сторінки й брудний журнал усередині. Тому першою дією — вимкнення, і воно важливіше за всі команди нижче.

```bash
$ homectl deactivate andrij
$ mount | grep -c /home/andrij
0
$ ls -l --block-size=1 /home/andrij.home; du -h /home/andrij.home
-rw------- 1 root root 21474836480 сер  6 21:41 /home/andrij.home
3,4G	/home/andrij.home
```

Два числа не збігаються, і це не помилка: образ — [розріджений файл](root:sys-unix/sparse-files), у якому виділено лише написані блоки. Двадцять гібібайтів — це стеля, яку побачить ядро всередині; на носії зайнято 3,4.

## Файл стає диском

```bash
$ sudo losetup --find --show --partscan --read-only /home/andrij.home
/dev/loop7
$ lsblk -o NAME,SIZE,RO,PARTTYPENAME,PARTLABEL,FSTYPE,LABEL /dev/loop7
NAME      SIZE RO PARTTYPENAME PARTLABEL FSTYPE      LABEL
loop7      20G  1
└─loop7p1  20G  1 Linux home   andrij    crypto_LUKS andrij
```

Ключ `--partscan` тут не прикраса: без нього ядро подасть файл суцільним пристроєм і `loop7p1` не з'явиться зовсім — [таблицю розділів](root:sys-unix/disk-partitions) усередині [loop-пристрою](root:sys-unix/loop-device) читають лише на прохання. `--read-only` — запобіжник: він робить недоступним для запису весь ланцюжок, що виросте далі.

Ім'я типу `Linux home` придумав не `homed` — так `util-linux` називає конкретний UUID зі свого власного списку:

```bash
$ sudo sfdisk --part-type /dev/loop7 1
773F91EF-66D4-49B5-BD83-D683BF40AD16
```

Отже, ще нічого не відмикаючи, ми вже знаємо дві речі: це домівка й вона Андрієва. Витік навмисний — інакше вікно входу не мало б звідки взяти ім'я, а машина не мала б як упізнати вставлену флешку.

## Заголовок LUKS2: маркер видно, вміст — ні

```bash
$ sudo cryptsetup luksDump /dev/loop7p1
LUKS header information
Version:       	2
UUID:          	7c0a2f5e-1d84-4b1a-9f3c-2ae6d0b47f11
Label:         	andrij
Subsystem:     	(no subsystem)

Data segments:
  0: crypt
	offset: 16777216 [bytes]
	length: (whole device)
	cipher: aes-xts-plain64
	sector: 512 [bytes]

Keyslots:
  0: luks2
	Key:        512 bits
	PBKDF:      argon2id
	Time cost:  4
	Memory:     1048576
	Threads:    4
Tokens:
  0: systemd-homed
Digests:
  0: pbkdf2
```

`luksDump` називає тип маркера й на цьому спиняється: вмісту чужих маркерів він не показує, бо не знає, що з ним робити. Сам вміст лежить у ділянці метаданих у вигляді JSON, і його дістають окремим ключем:

```bash
$ sudo cryptsetup luksDump --dump-json-metadata /dev/loop7p1 | jq '.tokens'
{
  "0": {
    "type": "systemd-homed",
    "keyslots": [],
    "record": "wYb1n4lQe0Xj5tKcR2vP8mAz…(кілька кілобайтів)…9dHs=",
    "iv": "Yk8xU2p0bVc3RHFaNw=="
  }
}
```

Порожній `keyslots` тут промовистий. У LUKS2 маркер зазвичай приписують до ключових слотів, які він уміє відмикати, — так працюють маркери апаратних ключів: `cryptsetup` бачить приписку, кличе відповідний обробник і дістає пароль сам. Тут приписки немає жодної, тобто `cryptsetup` цим маркером не скористається ніколи й ні за яких обставин. Поле відведено суто під зберігання: служба читає його своїми руками, а формат LUKS2 люб'язно возить чужі байти в заголовку, не питаючи, що в них.

Дампу заголовка, до речі, пароль не потрібен зовсім — читається лише ділянка метаданих на початку тому. Саме тому все, що ми побачили дотепер, побачить і будь-хто, кому дістався файл.

## base64 — це не замок

Тепер найповчальніший крок усього розбору. Поле `record` виглядає як шифр, але base64 шифром не є: це спосіб записати довільні байти друкованими символами, і зворотний хід відкритий кожному.

```bash
$ sudo cryptsetup luksDump --dump-json-metadata /dev/loop7p1 \
    | jq -r '.tokens["0"].record' | base64 -d > /tmp/record.bin
$ file /tmp/record.bin
/tmp/record.bin: data
$ head -c 24 /tmp/record.bin | xxd
00000000: 9c3f a1e7 0b52 d8c4 71ff 3a06 be29 0d8a  .?...R..q.:..)..
00000010: 5741 e3b2 6c00 91df                      WA..l...
$ jq . /tmp/record.bin
jq: error (at /tmp/record.bin:0): Invalid numeric literal at line 1, column 2
```

Розкодування вдалося з першого разу й без жодного пароля — і дало шум. Це і є суть: base64 знято, під ним шифротекст. Запис зашифровано ключем тому — тим самим, яким закриті й дані, — з власним вектором `iv`; а ключ тому лежить за ключовим слотом, тобто за паролем. Ніякого «прихованого поля» тут немає; поле є, воно ціле й доступне, воно просто позбавлене сенсу без ключа.

Підсумуймо, що сторонній вичитав із замкненого образу: це домівка `homed`, звати власника `andrij`, том двадцять гібібайтів, шифр `aes-xts-plain64`, виведення ключа — `argon2id` із гібібайтом пам'яті на спробу (звідси й помітна пауза на вході — вона куплена навмисно, [перебір коштує саме цієї пам'яті](root:sys-unix/dm-crypt)), вхід один — єдиний ключовий слот. І нічого більше: ні справжнього імені, ні оболонки, ні номера, ні груп, ні жодної назви файла, ні навіть їх кількости.

## Пароль — і той самий запис читається

```bash
$ sudo cryptsetup open /dev/loop7p1 peek
Enter passphrase for /dev/loop7p1:
$ sudo mount -o ro /dev/mapper/peek /mnt
$ ls /mnt
andrij
$ sudo jq -r '.userName, .realName, .disposition, .lastChangeUSec' /mnt/andrij/.identity
andrij
Andrij Felenko
regular
1754470920045391
```

Ім'я `peek` вигадали ми; служба про цей пристрій не знає нічого — ми тут сторонні, які знають пароль, і цього досить. А `~/.identity` — це той самий запис, що не читався із заголовка. Звіримо його з тим, що видає машина:

```bash
$ diff <(sudo jq -S '{userName,realName,disposition,lastChangeUSec}' /mnt/andrij/.identity) \
       <(homectl inspect andrij -j | jq -S '{userName,realName,disposition,lastChangeUSec}') \
  && echo "той самий запис"
той самий запис
```

Збігається дослівно, бо це буквально одна річ, покладена в різні місця. А коли копії таки розійдуться — запис змінили на іншій машині або при вимкненій домівці, — розсудить їх `lastChangeUSec`: перемагає найновіша.

А ось те, чого в подорожній частині немає й бути не може:

```bash
$ homectl inspect andrij -j | jq '.binding[] | {uid,gid,storage,imagePath,luksUuid}'
{
  "uid": 60013,
  "gid": 60013,
  "storage": "luks",
  "imagePath": "/home/andrij.home",
  "luksUuid": "7c0a2f5e-1d84-4b1a-9f3c-2ae6d0b47f11"
}
```

Секція `binding` ключована ідентифікатором машини, і `luksUuid` у ній — той самий рядок, який ми прочитали з заголовка ще до пароля. Ось як машина впізнає образ, не відмикаючи його. Те саме число віддають і всім іншим — через [службу userdb](root:sys-unix/userdb-varlink), причому при вимкненій домівці:

```bash
$ userdbctl user andrij --json=short | jq '.userName, .binding[].uid, .status[].state'
"andrij"
60013
"inactive"
```

## Чиїм ключем це підписано

```bash
$ sudo diff <(sudo jq -r '.signature[0].key' /mnt/andrij/.identity) \
            /var/lib/systemd/home/local.public \
  && echo "підписано ключем цієї машини"
підписано ключем цієї машини
```

У записі лежить не лише [підпис](root:sf-security/hash-and-digital-signature), а й відкритий ключ, яким його перевіряти, — у вигляді звичайного PEM. Тому питання «чи прийме ця машина цю домівку» розв'язується одним `diff` файлів: якщо жоден із `*.public` не збігається, локальний вхід не відбудеться.

## Числа всередині

```bash
$ sudo ls -ln /mnt/andrij | head -3
drwx------  9 60013 60013  4096 сер  6 21:40 .cache
drwx------ 14 60013 60013  4096 сер  6 21:41 .config
-rw-------  1 60013 60013  2214 сер  6 09:02 .identity
$ sudo find /mnt/andrij -uid 60013 | wc -l
41822
```

Числа `60013` немає в подорожній частині запису — воно прийшло з `binding` саме цієї машини. На іншій машині служба візьме своє вільне число з діапазону 60001…60513, побачить у метаданих чуже і при першому ж відмиканні перепише власника всьому дереву. Тепер ціна переїзду перестала бути словами: сорок одна тисяча вісімсот двадцять два виклики `lchown`, по одному на кожен об'єкт. І це не незграбність `homed`: [власник файла — число в метаданих](root:sys-unix/uid-gid-identity-model), імен ядро не знає взагалі, тож змінити власника без обходу дерева нема як.

## Прибрати за собою

```bash
$ sudo umount /mnt
$ sudo cryptsetup close peek
$ sudo losetup -d /dev/loop7
$ losetup -a | grep -c andrij.home
0
```

## Пастки

**Домівка мусить бути вимкненою — і це перевіряють, а не припускають.** Читати образ активної домівки безглуздо: файлова система всередині живе, частина змін ще в сторінковому кеші, а [журнал ext4](root:sys-unix/journaling-consistency) брудний. Тому `mount -o ro` на такому томі або відмовиться, або зажадає програти журнал — а на пристрої, відкритому лише для читання, це неможливо. Порада «додайте `-o ro,noload`» розв'язує симптом і ховає причину: ви читатимете завідомо неузгоджену файлову систему. Вимкніть домівку — і `-o ro` стане чесним.

**`losetup -d` — не косметика, а дві різні потреби.** Забутий loop-пристрій тримає файл зайнятим, і наступна спроба `homectl activate` впаде. Гірше інше: забутий відкритий `dm`-пристрій тримає ключ тому в пам'яті ядра — рівно те, що служба прибирає при виході останнього сеансу. Розбір, після якого ключ лишився жити, скасовує саме ту властивість, заради якої все це збудовано.

**Заголовок руками не правити.** Спокуса додати собі ключовий слот через `cryptsetup luksAddKey` виглядає нешкідливо, а насправді робить другі двері, яких немає в обліковому записі: лічильники вдалих і невдалих спроб та обмеження частоти живуть у записі, і про ці двері вони не дізнаються ніколи. Правити сам маркер ще безнадійніше — його `record` є шифротекстом, і без ключа тому зашифрувати змінений запис назад нічим.

**Копіювати образ — з огляду на дірки.** Простий `cat` або `dd` перетворить 3,4 ГіБ на носії у всі двадцять: розрідженість не є вмістом файла, її треба відтворювати свідомо. Робочі варіанти — `cp --sparse=always` або `cp --reflink=auto` в межах однієї файлової системи.

**Та сама драбина працює й без файла.** Якщо домівку тримають на флешці, `losetup` просто випадає з початку: `lsblk` покаже `sdb1` із тим самим типом `Linux home` і тією самою міткою, `luksDump` — той самий маркер. Один формат на два випадки — це не побажання зі специфікації, а спостережуваний факт: усі команди нижче першої лишаються дослівно тими самими.

> 🔧 **Навіщо це.** Уміння знімати шари стороннім інструментом варте більшого за конкретний `homed`. Межі форматів проходять рівно там, де інструмент перестає розуміти вміст і починає його просто возити: `losetup` не знає про розділи, `sfdisk` не знає про шифр, `cryptsetup` не знає про облікові записи. І кожен шар, поки він зовнішній, віддає свої метадані задарма. Питання «що витікає без ключа» завжди має ту саму відповідь — усе, що потрібно було наступному шарові, щоб його взагалі знайшли.

**Ціна.** Уся драбина до пароля читає лічені кілобайти: таблицю розділів і заголовок LUKS2, незалежно від того, двадцять гібібайтів в образі чи двісті. Дорогих кроків рівно два, і обидва по той бік межі — виведення ключа з пароля (гібібайт пам'яті на кожну спробу, за дампом заголовка) і зміна власника при переїзді, лінійна від кількости об'єктів.
