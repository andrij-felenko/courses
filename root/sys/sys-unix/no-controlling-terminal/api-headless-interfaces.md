# 📋 Системні виклики, інтерфейси ядра та конфігурація безтермінальних процесів

У цій довідковій вставці детально систематизовано сигнатури низькорівневих системних викликів, функцій стандартної бібліотеки C, коди помилок ядра та директиви менеджерів ініціалізації (systemd), які визначають поведінку процесів під час роботи без керуючого термінала. Кожен розділ описує як формальний інтерфейс, так і внутрішній механізм ядра, взаємодію з підсистемами керування завданнями, роботу віртуальної файлової системи `procfs` та специфічні крайові випадки.

## 1. Системні виклики керування сеансами та групами

Керування сеансами в ядрі Linux регулюється стандартом POSIX.1 і спирається на ієрархію «процес → група процесів → сеанс». Процес без термінала обов'язково ізолюється у власному сеансі, де він або стає лідером, або живе як рядовий нащадок лідера.

### `setsid(2)` — Створення нового сеансу
Системний виклик `setsid` є головним інструментом від'єднання від керуючого термінала на рівні ядра.

```c
#include <unistd.h>

pid_t setsid(void);
```

#### Механізм виконання в ядрі
Коли процес викликає `setsid()`, ядро перевіряє, чи не збігається його ідентифікатор процесу `PID` з ідентифікатором його поточної групи `PGID`:
1. Якщо `PID == PGID`, процес уже є лідером групи процесів. Перенесення лідера в новий сеанс зруйнувало б зв'язок з іншими процесами старої групи, тому ядро забороняє цю операцію і повертає помилку `EPERM`. Саме тому перед викликом `setsid()` обов'язково виконують `fork()`, де дочірній процес гарантовано має `PID != PGID`.
2. Якщо перевірка успішна, ядро створює новий сеанс, призначає `SID = PID`, створює нову групу процесів із `PGID = PID`, а покажчик на керівний термінал у структурі `signal_struct` процесу обнуляє (`tty = NULL`).
3. Викликач стає єдиним процесом у новоствореній групі та сеансі.

| Параметр / Результат | Опис |
|---|---|
| **Повертає (успіх)** | `pid_t` — новий ідентифікатор сеансу (`SID`), що дорівнює `PID` викликача. Процес стає єдиним членом нової групи (`PGID = PID`) і повністю втрачає зв'язок зі старим керуючим терміналом. |
| **Повертає (помилка)** | `-1`, встановлюючи змінну `errno`. |
| `EPERM` | Процес уже є лідером групи процесів (`PID == getpgrp()`). Для подолання помилки процес повинен розгалузитися через `fork()`, а виклик має здійснювати дочірній процес. |

---

### `getsid(2)` — Отримання ідентифікатора сеансу
Дозволяє визначити, до якого сеансу належить довільний процес у системі.

```c
#include <unistd.h>

pid_t getsid(pid_t pid);
```

| Аргумент | Значення |
|---|---|
| `pid` | `0` — отримати ідентифікатор сеансу для поточного процесу; `> 0` — отримати `SID` цільового процесу за його номером. |
| `ESRCH` | Процес із вказаним числовим ідентифікатором `pid` не знайдено в таблиці процесів ядра. |
| `EPERM` | Цільовий процес існує, але належить до іншого сеансу, і поточному процесу бракує прав на інспекцію його дескриптора. |

## 2. Діагностика термінала та керування буферизацією

Стандартна бібліотека C надає функції для перевірки типу пристрою, за яким закріплено дескриптор, та для зміни режиму накопичення даних перед відправленням у ядро.

### `isatty(3)` та `ttyname(3)` — Перевірка та ідентифікація TTY
Функція `isatty` визначає, чи веде відкритий файловий дескриптор до термінального пристрою (фізичної консолі, псевдотермінала або послідовного порту).

```c
#include <unistd.h>

int isatty(int fd);
char *ttyname(int fd);
int ttyname_r(int fd, char *buf, size_t buflen);
```

#### Внутрішня реалізація
Функція `isatty(fd)` виконує системний виклик `ioctl(fd, TCGETS, &termios)` (або `TCGETA` на старих системах). Якщо дескриптор веде до регулярного файлу, анонімного каналу (`pipe`) або сокета, драйвер ядра повертає код помилки `ENOTTY` або `EINVAL`. Бібліотека інтерпретує це як відсутність термінала і повертає `0`.

| Функція | Повернене значення | Помилки (`errno`) |
|---|---|---|
| `isatty(fd)` | `1` — якщо `fd` посилається на дійсний термінальний пристрій; `0` — якщо ні. | `EBADF` (дескриптор не відкритий), `ENOTTY` (дескриптор відкритий на файл, сокет, канал або `/dev/null`). |
| `ttyname(fd)` | Покажчик на статичний буфер із назвою пристрою (наприклад, `"/dev/pts/2"`). Небезпечний для багатопотокових програм. | `EBADF` (недійсний дескриптор), `ENOTTY` (не є терміналом), `ENODEV` (пристрій відсутній). |
| `ttyname_r(fd, buf, len)` | `0` у разі успіху; додатне значення помилки (`errno`) у разі збою. Потокобезпечна версія. | `ERANGE` (переданий буфер замалий для запису шляху), `EBADF`, `ENOTTY`. |

---

### `tcgetpgrp(3)` та `tcsetpgrp(3)` — Керування групою переднього плану
Ці виклики визначають або призначають групу процесів переднього плану (*foreground process group*) для вказаного термінала.

```c
#include <unistd.h>

pid_t tcgetpgrp(int fd);
int tcsetpgrp(int fd, pid_t pgrp);
```

#### Поведінка в безтермінальному контексті
Якщо дескриптор `fd` веде до сокета, каналу або файлу `/dev/null`, виклик `tcgetpgrp(fd)` негайно повертає `-1` із помилкою `ENOTTY`. Якщо ж дескриптор веде до дійсного термінала, але сам викликач працює у фоновій групі або належить до іншого сеансу, спроба виконати `tcsetpgrp()` спричиняє надсилання сигналу `SIGTTOU` всій фоновій групі. Якщо сигнал не перехоплено і не проігноровано, процес миттєво зупиняється ядром.

---

### `ctermid(3)` — Отримання імені керуючого термінала
Функція повертає рядок шляху до керуючого термінала процесу за стандартом POSIX.

```c
#include <stdio.h>

char *ctermid(char *s);
```

#### Пастка використання
За стандартом функція `ctermid(s)` завжди повертає статичний рядок `"/dev/tty"`, навіть якщо поточний процес взагалі не має керуючого термінала. Вона не виконує реальної перевірки стану ядра, а лише повертає стандартне системне ім'я вузла. Спроба спиратися на успішне повернення `ctermid` як на доказ наявності TTY є поширеною помилкою: подальший `open("/dev/tty")` все одно завершиться помилкою `ENXIO`.

### `setvbuf(3)` — Налаштування буферизації стандартних потоків
Контролює момент скидання буферів простору користувача у системні виклики `write(2)`.

```c
#include <stdio.h>

int setvbuf(FILE *stream, char *buf, int mode, size_t size);
void setbuf(FILE *stream, char *buf);
```

#### Пояснення режимів буферизації
- `_IONBF` (*Unbuffered*): Буферизація відсутня. Кожен окремий символ або рядок передається в ядро окремим викликом `write()`. Режим за замовчуванням для `stderr`.
- `_IOLBF` (*Line buffered*): Дані накопичуються у внутрішньому буфері до моменту появи символу нового рядка `\n` або переповнення буфера. Режим за замовчуванням для `stdout`, якщо `isatty(1) == 1`.
- `_IOFBF` (*Fully buffered*): Дані накопичуються блоками фіксованого розміру (зазвичай 4096 байтів). Символ `\n` не призводить до скидання. Режим за замовчуванням для `stdout`, якщо `isatty(1) == 0`.

| Режим (`mode`) | Константа | Поведінка | Типове застосування |
|---|---|---|---|
| **Без буферизації** | `_IONBF` | Кожен виклик запису негайно транслюється в системний виклик `write(2)`. | Потік `stderr` для критичних помилок. |
| **Лінійна буферизація** | `_IOLBF` | Буфер скидається при появі символу `'\n'` або при читанні з термінала. | Потік `stdout` в інтерактивній сесії. |
| **Повна (блочна) буферизація** | `_IOFBF` | Буфер скидається лише після накопичення повного блоку або примусового виклику `fflush()`. | Потік `stdout` у cron, systemd, pipe, файлах. |

## 3. Спеціальний файл `/dev/tty` та коди помилок ядра

Файл `/dev/tty` (зі старшим номером пристрою `major 5` та молодшим `minor 0`) є синонімом керуючого термінала процесу.

```c
int fd = open("/dev/tty", O_RDWR | O_NOCTTY | O_CLOEXEC);
```

#### Логіка обробки в підсистемі TTY
Під час звернення до `/dev/tty` ядро звертається до поля `current->signal->tty`. Якщо покажчик дорівнює `NULL` (процес не має керуючого термінала), ядро не має куди спрямувати запит на відкриття і негайно повертає код `-ENXIO`.

| Код помилки (`errno`) | Значення | Причина виникнення у безтермінальному середовищі |
|---|---|---|
| `ENXIO` | *No such device or address* | Процес не має керуючого термінала (`task->signal->tty == NULL`). Типово для systemd юнітів, cron, CI/CD раннерів та демонів після виклику `setsid()`. |
| `ENODEV` | *No such device* | Ядро скомпільовано без підтримки підсистеми віртуальних терміналів або вузол видалено з файлової системи `devtmpfs`. |
| `EACCES` | *Permission denied* | Права доступу на вузол термінала не дозволяють читання чи запис поточному користувачеві (UID/GID). |
| `EIO` | *Input/output error* | Процес у фоновій групі намагається виконати операцію читання з термінала за умов, коли сигнали керування завданнями `SIGTTIN` або `SIGTTOU` заблоковано чи сеанс став сиротою. |

## 4. Запити `ioctl` для прямого керування TTY

У низькорівневому системному програмуванні для явного від'єднання або захоплення термінала використовуються специфічні запити введення-виведення:

### `TIOCNOTTY` та `TIOCSCTTY`

```c
#include <sys/ioctl.h>

int ioctl(int fd, int cmd, ...);
```

| Команда `ioctl` | Призначення та семантика |
|---|---|
| `TIOCNOTTY` | **Примусове від'єднання термінала:** Виконується на відкритому дескрипторі `/dev/tty`. Якщо викликач є лідером сеансу, ядро від'єднує керівний термінал від усього сеансу й надсилає сигнал `SIGHUP` усій групі процесів переднього плану. Історичний метод BSD для демонізації до стандартизації `setsid`. |
| `TIOCSCTTY` | **Примусове призначення керуючого термінала:** Призначає термінал, відкритий за дескриптором `fd`, керуючим терміналом поточного сеансу. Вимагає, щоб процес був лідером сеансу і не мав іншого термінала. Якщо передано третій аргумент `1`, процес із привілеєм `CAP_SYS_ADMIN` може відібрати термінал у попереднього сеансу. |

## 5. Інтерфейси інспекції в системній файловій системі `/proc`

Ядро Linux експортує повну інформацію про стан термінальних прив'язок та дескрипторів процесів через віртуальну файлову систему `/proc`:

### `/proc/[pid]/stat`
Сьоме числове поле псевдофайлу кодує апаратний номер керуючого термінала процесу (`tty_nr`).
- Якщо `tty_nr == 0`, процес повністю ізольований від керуючих терміналів.
- Якщо `tty_nr > 0`, старший байт числа кодує старший номер символьного пристрою (*major device number*, наприклад `136` для `/dev/pts/X`), а молодший байт кодує номер лінії (*minor device number*).

### `/proc/[pid]/fd/`
Каталог містить символічні посилання на відкриті файли. У безтермінальному середовищі:
- `0 -> /dev/null`
- `1 -> socket:[inode]` (або `pipe:[inode]`)
- `2 -> socket:[inode]` (або `pipe:[inode]`)

## 6. Директиви systemd для налаштування дескрипторів та TTY

У юніт-файлах `systemd` секція `[Service]` або `[Execution]` містить розширений набір директив, які контролюють стандартні потоки введення-виведення, взаємодію з системним журналом та виділення віртуальних консолей для служб:

| Директива | Допустимі значення | Поведінка та призначення |
|---|---|---|
| `StandardInput=` | `null`, `tty`, `tty-force`, `socket`, `data`, `file:/path` | Джерело дескриптора `0`. Значення за замовчуванням для служб — `null` (підключає `/dev/null`). Значення `tty` виділяє термінал, вказаний у `TTYPath`. |
| `StandardOutput=` | `journal`, `journal+console`, `syslog`, `kmsg`, `file:/path`, `socket`, `null` | Призначення дескриптора `1`. Значення за замовчуванням — `journal` (підключає сокет `systemd-journald`). |
| `StandardError=` | `journal`, `syslog`, `kmsg`, `file:/path`, `null`, `inherit` | Призначення дескриптора `2`. За замовчуванням — `inherit` (дублює дескриптор, налаштований для `StandardOutput`). |
| `TTYPath=` | `/dev/tty1`, `/dev/console`, `/dev/ttyS0` | Конкретний шлях до вузла термінала, який передається службі при виборі директиви `StandardInput=tty`. |
| `TTYReset=` | `yes`, `no` | Чи скидати параметри структури termios термінала до стандартних значень перед передачею службі. |
| `TTYVHangup=` | `yes`, `no` | Чи надсилати віртуальний розрив лінії (*vhangup*) перед відкриттям термінала для примусового завершення завислих процесів попереднього сеансу. |
| `TTYVTDisallocate=` | `yes`, `no` | Чи очищати віртуальну графічну/текстову консоль після штатної або аварійної зупинки служби. |

## 7. Протокол повідомлення готовності `sd_notify`

Для сучасних служб з типом запуску `Type=notify` процес без термінала повідомляє супервізор про завершення ініціалізації та поточний стан через сокет дейтаграм UNIX, шлях до якого передається у змінній середовища `NOTIFY_SOCKET`.

```c
#include <systemd/sd-daemon.h>

int sd_notify(int unset_environment, const char *state);
```

#### Формат повідомлень
Аргумент `state` складається з текстових рядків у форматі `КЛЮЧ=ЗНАЧЕННЯ`, розділених символом `\n`. Функція самостійно створює тимчасовий сокет і відправляє дейтаграму на адресу, задану в `$NOTIFY_SOCKET`.

| Рядок стану (`state`) | Призначення та реакція супервізора |
|---|---|
| `READY=1` | Служба завершила завантаження конфігурації, відкрила всі необхідні порти й готова приймати запити. Менеджер знімає блокування із залежних юнітів. |
| `RELOADING=1` | Служба розпочала перезавантаження конфігурації (наприклад, після сигналу `SIGHUP`). |
| `STOPPING=1` | Служба розпочала штатне завершення роботи й закриває підключення. |
| `ERRNO=22` | Передає числовий код системної помилки (`EINVAL`), яка спричинила збій ініціалізації. |
| `MAINPID=1234` | Оновлює головний числовий ідентифікатор процесу, за яким стежить супервізор (якщо служба породжує робітників). |
| `WATCHDOG=1` | Регулярний сигнал життєздатності для сторожового таймера `systemd` (*keep-alive ping*), що запобігає перезапуску завислої служби. |
| `STATUS=Текст` | Довільний однорядковий опис поточного стану для відображення в команді `systemctl status`. |
