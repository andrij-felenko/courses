Сценарій розгортання або системна служба, яка бездоганно працює під час ручного запуску в інтерактивному сеансі оболонки, раптово зазнає фатального краху о третій годині ночі під керуванням планувальника `cron` або всередині контейнера Docker без прапорця `-t`. Програма намагається звернутися до сховища ключів, запитати пароль дешифрування чи вивести перший рядок діагностичного журналу, але замість виконання завдання негайно завершується з системною помилкою `ENXIO: No such device or address`, або ж годинами накопичує вивід у пам'яті, не скидаючи жодного байта в системний журнал до моменту аварійної зупинки.

Ця поведінка не є випадковим збоєм: процес опинився в середовищі без керуючого термінала (*controlling terminal*). У світі Unix керівний термінал є не просто вікном на екрані чи послідовним кабелем, а фундаментальною конструкцією ядра, яка зв'язує групу процесів із фізичним або псевдотермінальним пристроєм, керує генерацією сигналів клавіатури (`SIGINT`, `SIGTSTP`) і диктує стандартній бібліотеці режим буферизації потоків введення-виведення.

Коли процес запускається без термінала — як системний демон під керуванням `systemd`, фонове завдання `cron`, крок пайплайну в CI/CD чи воркер веб-сервера, — ядро та бібліотека C докорінно змінюють правила гри. Розуміння цих змін дає змогу будувати надійні системні сервіси, які не зависають у буферах і не падають від відсутності інтерактивного користувача.

## Запуск «без голови»: де зникає керівний термінал

У типовому інтерактивному сеансі (наприклад, під час входу через SSH або у вікні емулятора термінала) процес оболонки має чітку прив'язку до пристрою псевдотермінала (наприклад, `/dev/pts/3`). Цей зв'язок зафіксовано на рівні внутрішніх структур ядра: у дескрипторі процесу `task_struct` покажчик `signal->tty` посилається на екземпляр структури `struct tty_struct`.

У безтермінальному (*headless*) контексті цей зв'язок повністю розірвано. Існує кілька типових середовищ, де процес із самого початку народжується без термінала:

1. **Системні служби (`systemd units`):** Менеджер ініціалізації запускає дочірній процес сервісу через системні виклики `fork()` та `execve()`, попередньо виконавши `setsid()` для ізоляції в новому сеансі без термінала.
2. **Планувальники завдань (`cron`, `anacron`, `at`):** Завдання виконуються демоном у фоновому сеансі. Стандартні дескриптори перенаправляються в канали (*pipes*) або файли для подальшого надсилання звіту електронною поштою чи запису в журнал.
3. **Контейнеризація (`Docker`, `Podman`, `containerd`):** Запуск контейнера командою `docker run -d` або без прапорця `-t` (`--tty`) створює ізольований простір імен, де контейнеризований процес не отримує виділеного псевдотермінала.
4. **Агенти CI/CD (`GitHub Actions`, `GitLab Runner`, `Jenkins`):** Кроки збірки та тестування виконуються неінтерактивними демонами-виконавцями, де ввід-вивід перехоплюється через канали.
5. **Веб-сервери та процеси застосунків (`PHP-FPM`, `uWSGI`, `Gunicorn`, `CGI`):** Робочі процеси обробки HTTP-запитів функціонують як демонізовані пули воркерів.

![Анатомія процесу в ядрі: наявність проти відсутності керуючого термінала](/root/sys/sys-unix/no-controlling-terminal/img/process-terminal-link.svg)
*Порівняння структури інтерактивного процесу та процесу без керуючого термінала в ядрі.*

Коли вказівник `signal->tty` в ядрі дорівнює `NULL`, процес зазнає істотних структурних обмежень:
- **Відсутність лінійної дисципліни (`line discipline`):** Немає проміжного програмного драйвера (зазвичай `N_TTY`), який би здійснював попередню обробку вводу, стирання символів клавішею Backspace чи перетворення символів нового рядка `\r` на `\n`.
- **Відсутність сигналів переривання від клавіатури:** Комбінації клавіш на кшталт `Ctrl+C` або `Ctrl+Z` не генерують сигналів `SIGINT`, `SIGQUIT` чи `SIGTSTP`, оскільки немає пристрою, який транслює символи керування в асинхронні повідомлення ядра.
- **Відсутність геометричного контексту:** Системний виклик `ioctl(fd, TIOCGWINSZ, &ws)` для визначення кількості рядків і стовпчиків завершується помилкою `ENOTTY`, а сигнал зміни розміру вікна `SIGWINCH` ніколи не генерується.

## Поведінка стандартних дескрипторів і пастка буферизації

Кожен новостворений процес у системі Linux успадковує від свого батька таблицю відкритих файлових дескрипторів. У безтермінальному середовищі перші три дескриптори (`0` — `stdin`, `1` — `stdout`, `2` — `stderr`) налаштовуються супервізором у специфічний спосіб:

- **Дескриптор `0` (`stdin`):** Найчастіше відкривається на псевдопристрій `/dev/null` у режимі тільки для читання. Будь-яка спроба читання з такого дескриптора негайно повертає `0` байтів, що інтерпретується процесом як ознака кінця файлу (`EOF`). Якщо процес очікує інтерактивного вводу без перевірки на `EOF`, він ризикує увійти в нескінченний цикл із 100% завантаженням процесора.
- **Дескриптори `1` та `2` (`stdout`, `stderr`):** У сучасних дистрибутивах під керуванням `systemd` ці дескриптори підключаються до сокета доменного простору UNIX (`AF_UNIX`), через який логи напряму передаються службі `systemd-journald`. У середовищі `cron` або звичайних конвеєрах оболонки вони спрямовуються в анонімний канал (`pipe`) або регулярний файл на диску.

### Зміна режиму буферизації `stdio`

Найпідступнішим наслідком втрати термінала є автоматична зміна поведінки буферизації у стандартній бібліотеці C (`glibc`, `musl`).

Стандартна бібліотека C під час ініціалізації стандартного виводу виконує перевірку:

:::tabs
```c
/* Логіка стандартної бібліотеки C під час вибору буферизації stdout */
if (isatty(fileno(stdout))) {
    setvbuf(stdout, NULL, _IOLBF, 0);       /* Термінал: лінійна буферизація */
} else {
    setvbuf(stdout, NULL, _IOFBF, BUFSIZ);  /* Канал/файл/сокет: блочна буферизація */
}
```
```cpp
// Еквівалентна перевірка дескриптора засобами POSIX у середовищі C++
if (::isatty(::fileno(stdout))) {
    std::setvbuf(stdout, nullptr, _IOLBF, 0);
} else {
    std::setvbuf(stdout, nullptr, _IOFBF, BUFSIZ);
}
```
:::

Функція `isatty(3)` всередині виконує системний виклик `ioctl(fd, TCGETS, &termios)`. Якщо дескриптор веде до сокета, каналу чи файлу `/dev/null`, драйвер повертає помилку `ENOTTY`, і `isatty()` повертає `0`.

![Пастка буферизації стандартного виводу: термінал проти каналу або файлу](/root/sys/sys-unix/no-controlling-terminal/img/stdio-buffering-trap.svg)
*Пастка буферизації stdio: зміна поведінки з лінійної на блочну за відсутності TTY.*

Це призводить до перемикання з **лінійної буферизації** (`_IOLBF`) на **повну блочну буферизацію** (`_IOFBF`), де розмір буфера `BUFSIZ` зазвичай становить 4096 або 8192 байти:
1. **В інтерактивному режимі:** Кожен виклик `printf("Подія сталася\n")` містить символ переведення рядка `\n`, що змушує бібліотеку негайно виконати системний виклик `write(1, ...)`. Користувач бачить повідомлення в ту саму мілісекунду.
2. **У безтермінальному режимі:** Той самий виклик `printf()` просто дописує байти у внутрішній буфер пам'яті процесу. Системний виклик `write()` не виконуватиметься доти, доки застосунок не згенерує повні 4096 байтів тексту або явно не викличе `fflush(stdout)`.

### Практичні наслідки блочної буферизації

- **Зависання логів:** Адміністратор запускає діагностику служби через `journalctl -u my-service -f` або дивиться `docker logs -f`, але бачить абсолютну тишу. Служба активно працює, проте її логи застрягли у буфері простору користувача.
- **Втрата критичних повідомлень про збій:** Якщо програма виконує кілька операцій, записує в лог `printf("Критична помилка: невірний покажчик\n")`, а наступним рядком отримує сигнал `SIGSEGV` через помилку адресації, процес негайно завершується ядром. Буфери простору користувача знищуються разом із пам'яттю процесу, так і не потрапивши до ядра. У системному журналі не залишиться жодного сліду останніх дій програми перед аварією.

### Методи примусового скидання буфера

Щоб запобігти застряганню діагностичних повідомлень у неінтерактивному середовищі, застосовують такі підходи:

1. **Явне налаштування буферизації на старті програми:**
:::tabs
```c
#include <stdio.h>

void configure_headless_logging(void) {
    /* Перемикаємо stdout на лінійну буферизацію незалежно від наявності TTY */
    setvbuf(stdout, NULL, _IOLBF, 0);
    /* Або повністю вимикаємо буферизацію */
    /* setvbuf(stdout, NULL, _IONBF, 0); */
}
```
```cpp
#include <cstdio>
#include <iostream>

void configure_headless_logging() {
    // Синхронізація C++ потоків із системними буферами C
    std::setvbuf(stdout, nullptr, _IOLBF, 0);
    // Вимикаємо блочну буферизацію для std::cout
    std::ios_base::sync_with_stdio(true);
}
```
:::

2. **Використання дескриптора помилок (`stderr`):** Потік `stderr` за стандартом POSIX завжди ініціалізується в небуферизованому режимі (`_IONBF`). Повідомлення, надіслані у `stderr`, потрапляють до ядра негайно.
3. **Зовнішні утиліти корекції буферизації:** Якщо джерельний код змінити неможливо, програму запускають через утиліту `stdbuf` (яка за допомогою механізму `LD_PRELOAD` перехоплює ініціалізацію потоків) або встановлюють змінну середовища `PYTHONUNBUFFERED=1` для скриптів Python:
   ```console
   $ stdbuf -oL -eL ./my_legacy_daemon
   ```

Детальний аналіз та інспекцію середовища зібрано в практичній вставці [⚙️ Дослідник середовища без термінала: від перевірки isatty() до безпечного введення пароля](root:sys-unix/no-controlling-terminal/proj-headless-inspector.md).

## Спроба доступу до `/dev/tty` та системна помилка `ENXIO`

У файловій системі Linux існує спеціальний символьний вузол пристрою `/dev/tty` (зі старшим номером пристрою `major 5` та молодшим `minor 0`). Цей вузол є так званим «магічним синонімом» або порталом до керуючого термінала конкретного процесу.

Коли програма відкриває файл `/dev/tty`:
:::tabs
```c
int fd = open("/dev/tty", O_RDWR | O_NOCTTY | O_CLOEXEC);
```
```cpp
int fd = ::open("/dev/tty", O_RDWR | O_NOCTTY | O_CLOEXEC);
```
:::

Драйвер TTY ядра Linux (`drivers/tty/tty_io.c`) обробляє системний виклик `open()` через внутрішню функцію `tty_open_current_tty()`. Ядро виконує перевірку:

```c
/* drivers/tty/tty_io.c у просторі ядра */
struct tty_struct *tty;

tty = get_current_tty();
if (!tty) {
    return -ENXIO; /* No such device or address */
}
```

Якщо процес належить до сеансу, який не має керуючого термінала (`current->signal->tty == NULL`), системний виклик негайно завершується з кодом помилки `ENXIO` (*No such device or address*).

### Чому падають програми, що запитують автентифікацію

Багато стандартних утиліт безпеки — зокрема `ssh`, `sudo`, `gpg`, `git` (під час запиту парольної фрази до SSH-ключа) та графічні агенти введення паролів `pinentry` — розроблені з урахуванням захисту від перехоплення вводу.

Якщо користувач запускає конвеєр:
```console
$ cat data.txt | my_tool
```
Розробники `sudo` або `gpg` не можуть читати пароль зі стандартного вводу `stdin` (дескриптор `0`), оскільки він зайнятий даними з `data.txt`. Читання з `stdin` призвело б до того, що випадкові байти з файлу були б сприйняті як пароль. Тому автентифікаційні утиліти свідомо ігнорують дескриптор `0` і намагаються напряму відкрити `/dev/tty`, щоб поспілкуватися безпосередньо з людиною за клавіатурою.

Коли такий інструмент викликається з-під `cron`, `systemd` або в автоматизованому CI/CD раннері:
1. Програма робить виклик `open("/dev/tty", O_RDWR)`.
2. Ядро повертає помилку `ENXIO`.
3. Утиліта, не маючи змоги гарантувати безпечний інтерактивний ввід, негайно аварійно завершує роботу:
   ```text
   sudo: a terminal is required to read the password; either use the -S option to read from standard input or configure an askpass helper
   gpg: signing failed: Inappropriate ioctl for device
   ```

### Правильна адаптація утиліт для роботи без TTY

Щоб автоматизовані процеси не зазнавали аварій у безтермінальному середовищі:
- Для `sudo` використовують прапорець `-S` (`--stdin`), який наказує утиліті читати пароль зі стандартного потоку вводу замість спроби відкрити `/dev/tty`.
- Для `gpg` встановлюють прапорець `--pinentry-mode loopback`, що змушує утиліту приймати пароль через дескриптор конвеєра.
- Для `ssh` налаштовують автентифікацію виключно за відкритими ключами без парольних фраз або використовують змінну середовища `SSH_ASKPASS` разом із фоновим агентом `ssh-agent`.

Повний перелік параметрів викликів, прапорців та кодів помилок викладено в довіднику [📋 Системні виклики, інтерфейси ядра та конфігурація безтермінальних процесів](root:sys-unix/no-controlling-terminal/api-headless-interfaces.md).

## Безпекові переваги відсутності термінала: захист від ін'єкцій `TIOCSTI`

Відсутність керуючого термінала в системних службах є не лише технічною особливістю середовища, а й критичним рубежем безпеки операційної системи.

Історично драйвер термінала Unix підтримував запит введення-виведення `ioctl(fd, TIOCSTI, &byte)` (*Terminal I/O Control Simulate Terminal Input*). Цей виклик дозволяв будь-якому процесу, який має доступ до дескриптора TTY, програмно вставляти довільні байти безпосередньо у вхідну чергу термінала так, ніби їх фізично надрукував користувач на клавіатурі.

Якщо непривілейований процес (наприклад, веб-воркер або демон, запущений від користувача `nobody`) зберігав відкритий дескриптор до термінала адміністратора, зловмисник міг виконати ін'єкцію рядка `rm -rf /\n` або `sudo adduser hacker\n`. Щойно сеанс повертався до адміністративної оболонки, ці команди автоматично виконувалися з правами `root` (відома вразливість CVE-2016-2779).

Повне від'єднання демона від керуючого термінала (`tty = NULL`) та ізоляція дескрипторів на `/dev/null` робить виконання `ioctl(TIOCSTI)` принципово неможливим, оскільки ядро не має цільової черги вводу для підміни байтів. У сучасних ядрах Linux цей виклик додатково обмежено параметром ядра `dev.tty.tiocsti = 0`, проте базовим системним захистом залишається саме перебування демонів у безтермінальному стані.

## Класична демонізація: повна анатомія від'єднання

До появи системних менеджерів на кшталт `systemd` програми повинні були самостійно перетворювати себе на демонів — фонові процеси, повністю ізольовані від термінала користувача та сеансу оболонки. Ця процедура отримала назву **традиційної Unix-демонізації** (*daemonization*).

Класичний обряд демонізації складається з чіткої послідовності системних викликів. Пропуск хоча б одного з них залишає приховану вразливість або потенційну точку відмови.

![Класичний обряд подвійного fork: навіщо потрібен кожен крок](/root/sys/sys-unix/no-controlling-terminal/img/double-fork-steps.svg)
*Етапи подвійного розгалуження та ізоляції файлових дескрипторів.*

Розглянемо кожен крок цього механізму детально:

### 1. Перший `fork()` і завершення батька
Процес викликає системний виклик `fork()`, після чого батьківський процес негайно викликає `exit(0)`.
- **Звільнення оболонки:** Якщо програму було запущено з командного рядка, термінальна оболонка бачить, що процес-нащадок завершився, і повертає користувачеві запрошення командного рядка (`prompt`).
- **Гарантія не-лідера групи:** За правилами POSIX дочірній процес успадковує ідентифікатор групи процесів (`PGID`) свого батька, але отримує новий, унікальний ідентифікатор процесу (`PID`). Оскільки `PID != PGID`, дочірній процес гарантовано **не є лідером групи процесів**. Це критично важливо для успішного виконання наступного кроку.

### 2. Виклик `setsid()`: створення нового сеансу
Дочірній процес викликає системний виклик `setsid(2)`.
- Якщо процес не є лідером групи, ядро виконує три операції:
  1. Створює новий сеанс, у якому викликач стає лідером сеансу (`SID = PID`).
  2. Створює нову групу процесів, де викликач є лідером групи (`PGID = PID`).
  3. **Повністю скидає асоціацію з керуючим терміналом:** Покажчик `signal->tty` скидається в `NULL`. Відтепер процес від'єднаний від старого TTY.
- Якби процес спробував викликати `setsid()`, будучи лідером групи (без попереднього `fork()`), системний виклик завершився б помилкою `EPERM`.

### 3. Другий `fork()` і завершення лідера сеансу
Новостворений лідер сеансу викликає `fork()` ще раз і негайно завершується через `exit(0)`. Онук продовжує виконання.
- **Чому це необхідно:** На операційних системах сімейства System V Release 4 (SVR4), якщо процес є лідером сеансу без керуючого термінала, перший же виклик `open()` на будь-якому термінальному пристрої (наприклад, модемі, послідовному порту `/dev/ttyS0` або віртуальному терміналі) без явного прапорця `O_NOCTTY` **автоматично призначає цей термінал керуючим для всього сеансу**.
- Онук, хоч і живе в новому сеансі, має `PID != SID`, тобто за визначенням **не є лідером сеансу**. За правилами ядро ніколи не призначить керівний термінал процесу, який не є лідером сеансу. Онук стає повністю захищеним від випадкового набуття нового термінала.

Історію протистояння семантики терміналів BSD та System V, яка призвела до обов'язковості другого `fork`, викладено в історичному нарисі [📜 Чому подвійний fork став обов'язковим: розбіжність BSD та System V](root:sys-unix/no-controlling-terminal/hist-why-double-fork.md).

### 4. Очищення середовища: `umask(0)` та `chdir("/")`
- **Скидання маски створення файлів:** Демон викликає `umask(0)`, щоб скинути успадковану від оболонки маску прав доступу. Тепер під час створення файлів журнал чи сокет отримають саме ті права, які демон явно передасть у системні виклики `open()` чи `creat()`.
- **Зміна робочого каталогу:** Виклик `chdir("/")` переводить процес у кореневий каталог. Якщо залишити поточний каталог у точці монтування (наприклад, `/home/user/app` або `/mnt/storage`), демон утримуватиме файлову систему зайнятою (`EBUSY`), блокуючи спроби адміністратора виконати команду `umount`.

### 5. Перенаправлення стандартних файлових дескрипторів
Просте закриття дескрипторів `close(0)`, `close(1)`, `close(2)` є грубою помилкою. Якщо дескриптори `0, 1, 2` закрити, то наступний системний виклик `open()` (наприклад, відкриття файлу конфігурації або сокета бази даних) гарантовано займе найменший вільний номер — дескриптор `0`. Якщо після цього якась стороння бібліотека викличе `printf()`, вона спрямує текстовий вивід прямо у відкритий файл бази даних або сокет, зруйнувавши дані.

Правильне очищення вимагає відкриття `/dev/null` та заміни дескрипторів через `dup2(2)`:

:::tabs
```c
/* Приклад класичної демонізації на мові C */
#include <fcntl.h>
#include <signal.h>
#include <stdlib.h>
#include <sys/stat.h>
#include <unistd.h>

int daemonize_traditional(void) {
    /* 1. Перший fork */
    pid_t pid = fork();
    if (pid < 0) return -1;
    if (pid > 0) _exit(0); /* Батько завершується */

    /* 2. Створення нового сеансу */
    if (setsid() < 0) return -1;

    /* Ігноруємо сигнал SIGHUP при завершенні лідера сеансу */
    signal(SIGHUP, SIG_IGN);

    /* 3. Другий fork */
    pid = fork();
    if (pid < 0) return -1;
    if (pid > 0) _exit(0); /* Лідер сеансу завершується */

    /* 4. Очищення umask і каталогу */
    umask(0);
    if (chdir("/") < 0) return -1;

    /* 5. Перенаправлення дескрипторів 0, 1, 2 на /dev/null */
    int null_fd = open("/dev/null", O_RDWR);
    if (null_fd < 0) return -1;

    dup2(null_fd, STDIN_FILENO);
    dup2(null_fd, STDOUT_FILENO);
    dup2(null_fd, STDERR_FILENO);

    if (null_fd > STDERR_FILENO) {
        close(null_fd);
    }

    return 0;
}
```
```cpp
// Приклад традиційної демонізації на C++20 з RAII та expected
#include <cerrno>
#include <csignal>
#include <expected>
#include <fcntl.h>
#include <sys/stat.h>
#include <system_error>
#include <unistd.h>

namespace sys {

[[nodiscard]] std::expected<void, std::error_code> daemonize_traditional() noexcept {
    // 1. Перший fork
    pid_t pid = ::fork();
    if (pid < 0) {
        return std::unexpected(std::make_error_code(static_cast<std::errc>(errno)));
    }
    if (pid > 0) {
        ::_exit(0);
    }

    // 2. Створення нового сеансу
    if (::setsid() < 0) {
        return std::unexpected(std::make_error_code(static_cast<std::errc>(errno)));
    }

    ::signal(SIGHUP, SIG_IGN);

    // 3. Другий fork
    pid = ::fork();
    if (pid < 0) {
        return std::unexpected(std::make_error_code(static_cast<std::errc>(errno)));
    }
    if (pid > 0) {
        ::_exit(0);
    }

    // 4. Скидання umask та зміна каталогу
    ::umask(0);
    if (::chdir("/") < 0) {
        return std::unexpected(std::make_error_code(static_cast<std::errc>(errno)));
    }

    // 5. Перенаправлення 0, 1, 2 на /dev/null
    int null_fd = ::open("/dev/null", O_RDWR);
    if (null_fd < 0) {
        return std::unexpected(std::make_error_code(static_cast<std::errc>(errno)));
    }

    ::dup2(null_fd, STDIN_FILENO);
    ::dup2(null_fd, STDOUT_FILENO);
    ::dup2(null_fd, STDERR_FILENO);

    if (null_fd > STDERR_FILENO) {
        ::close(null_fd);
    }

    return {};
}

} // namespace sys
```

## Сучасна парадигма systemd: відмова від самодемонізації

У сучасній екосистемі Linux класична ручна демонізація офіційно визнана шкідливим антипатерном (*daemonization anti-pattern*). Менеджер ініціалізації `systemd` бере на себе всю роботу з ізоляції середовища, перетворюючи розробку служб на чистий і прямолінійний процес.

### Чому подвійний fork заважає системі

1. **Втрата контролю та стану гонки:** Коли служба розгалужується двічі, батьківський процес завершується до того, як онук завершить ініціалізацію (наприклад, відкриє мережевий порт). Сценарій запуску вважає службу успішно стартованою, хоча насправді вона може впасти через секунду під час зчитування конфігурації.
2. **Проблема відстеження процесів:** Раніше демони записували свій PID у файл (наприклад, `/run/nginx.pid`). Якщо демон завершувався аварійно, PID-файл залишався на диску. Пізніше система могла призначити цей PID іншому сторонньому процесу, і скрипт зупинки `kill $(cat /run/nginx.pid)` помилково знищував невинну програму.
3. **Контрольні групи (`cgroups v2`):** `systemd` розміщує кожну службу у власній контрольній групі (`cgroup`). Навіть якщо процес розгалузиться сотню разів або згенерує сиріт, усі вони залишаються всередині одного дерева cgroup, що дозволяє менеджеру гарантовано зупинити всі дочірні процеси без залишку зомбі чи сиріт.

### Парадигми `Type=simple` та `Type=notify`

Сучасні системні демони мають виконуватися на передньому плані (*foreground*), не викликаючи ані `fork()`, ані `setsid()`, ані перенаправлення дескрипторів.

```ini
# /etc/systemd/system/my-service.service
[Unit]
Description=Сучасна служба без самодемонізації
After=network.target

[Service]
Type=notify
ExecStart=/usr/local/bin/my_service
Restart=always
StandardInput=null
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

- **`Type=simple`:** Найпростіший варіант. `systemd` виконує `execve()` бінарника безпосередньо. Служба вважається запущеною відразу після успішного старту процесу. Дескриптори `1` і `2` автоматично зв'язуються з сокетом `systemd-journald`, а `0` спрямовується на `/dev/null`.
- **`Type=notify`:** Золотий стандарт надійності. Служба запускається на передньому плані, виконує всю складну ініціалізацію (зчитує конфігурацію, створює пули пам'яті, підключається до бази даних) і лише після повної готовності надсилає повідомлення `READY=1` через UNIX-сокет дейтаграм, вказаний у змінній оточення `$NOTIFY_SOCKET`:

:::tabs
```c
#include <systemd/sd-daemon.h>
#include <stdio.h>
#include <unistd.h>

int main(void) {
    /* Налаштовуємо буферизацію */
    setvbuf(stdout, NULL, _IOLBF, 0);

    printf("Ініціалізація компонентів...\n");
    sleep(1); /* Емуляція завантаження */

    /* Повідомляємо systemd про повну готовність */
    sd_notify(0, "READY=1\nSTATUS=Обробка клієнтських запитів");

    /* Головний цикл обробки */
    while (1) {
        sleep(10);
    }
    return 0;
}
```
```cpp
#include <systemd/sd-daemon.h>
#include <chrono>
#include <iostream>
#include <thread>

int main() {
    std::setvbuf(stdout, nullptr, _IOLBF, 0);

    std::cout << "Ініціалізація компонентів C++...\n";
    std::this_thread::sleep_for(std::chrono::seconds(1));

    // Сповіщаємо супервізор про готовність
    ::sd_notify(0, "READY=1\nSTATUS=Обробка клієнтських запитів (C++20)");

    while (true) {
        std::this_thread::sleep_for(std::chrono::seconds(10));
    }
    return 0;
}
```
:::

Завдяки механізму `sd_notify` залежні служби чекають реальної готовності сервісу без будь-яких станів гонки та без необхідності самостійно скидати керівний термінал.

### Активація через сокети (Socket Activation)

Ще однією перевагою відмови від самостійної демонізації є підтримка активації через сокети (*Socket Activation*). 

Менеджер `systemd` створює слухаючий мережевий сокет (`.socket` юніт), прив'язує його до порту (наприклад, TCP порт 80) і викликає `listen()`. Сам сервіс при цьому може бути навіть не запущений. Коли приходить перший TCP-пакет (SYN), ядро утримує з'єднання в черзі очікування (*backlog*), а `systemd` негайно запускає відповідний `.service` юніт і передає йому вже готовий відкритий файловий дескриптор під номером `3` (`SD_LISTEN_FDS_START`).

Демон не відкриває терміналів, не слухає порти і не розгалужується: він просто читає сокет з дескриптора `3`, обробляє клієнтів і завершує роботу, якщо активність зникає.

## Інженерна діагностика: інспекція стану без термінала

Для системного інженера чи адміністратора важливо вміти швидко діагностувати стан процесів у працюючій системі.

### 1. Перевірка через `/proc/<pid>/stat`
Сьоме поле у псевдофайлі `/proc/<pid>/stat` містить десяткове число `tty_nr` — номер керуючого термінала пристрою в ядрі:
```console
$ cat /proc/$(pgrep -f my_service)/stat | awk '{print "PID:", $1, "Name:", $2, "TTY_NR:", $7}'
PID: 4128 Name: (my_service) TTY_NR: 0
```
Значення `TTY_NR: 0` є незаперечним доказом того, що ядро зафіксувало стан `task->signal->tty == NULL`.

### 2. Перевірка файлових дескрипторів через `/proc/<pid>/fd`
Інспекція каталогу `/proc/<pid>/fd/` показує, куди реально підключені стандартні потоки:
```console
$ ls -l /proc/$(pgrep -f my_service)/fd/
lr-x------ 1 root root 64 сер 25 12:00 0 -> /dev/null
l-wx------ 1 root root 64 сер 25 12:00 1 -> socket:[28491]
l-wx------ 1 root root 64 сер 25 12:00 2 -> socket:[28491]
```
Стрілка `socket:[...]` свідчить про пряме підключення до сокета журналювання `systemd-journald`.

### 3. Перевірка утилітою `ps`
Команда `ps` позначає процеси без керуючого термінала символом знака питання `?` у колонці `TTY`:
```console
$ ps -eo pid,tty,stat,comm | grep my_service
   4128 ?        Ssl  my_service
```

Розуміння відмінностей між інтерактивним виконанням і роботою без термінала дає змогу уникнути типових пасток із завислими буферами логів, аваріями під час читання паролів та застарілими механізмами демонізації, гарантуючи стабільну роботу сервісів у будь-якому оточенні сучасного Linux.
