# 📋 Інтерфейс ioctl підсистеми /dev/iommufd

Символьний пристрій `/dev/iommufd` надає простору користувача уніфікований інтерфейс системних викликів `ioctl()` для прямого маніпулювання адресними просторами вводу-виводу (IOAS), апаратними таблицями сторінок (HWPT), чергами обробки сторінкових помилок (Fault Queue) та прив'язкою фізичних периферійних пристроїв. Усі структури даних, бітові маски прапорців та числові коди команд визначено в стандартному заголовному файлі ядра Linux `<linux/iommufd.h>`.

Ця довідка містить вичерпний опис сигнатур, структур параметрів, семантики полів, прапорців, правил життєвого циклу об'єктів та кодів помилок системного інтерфейсу IOMMUFD.

## 1. Загальна конвенція викликів ioctl та версіонування структур

Усі керуючі структури IOMMUFD починаються з обов'язкового 32-бітного поля `size`, яке повинно точно дорівнювати розміру відповідної структури в байтах: `sizeof(struct ...)`. 

Ядро Linux використовує це поле для забезпечення прямої та зворотної двійкової сумісності (ABI compatibility). Якщо простір користувача компілюється зі старішою версією заголовних файлів і передає менший розмір структури, драйвер ядра обробляє лише відомі йому поля першої версії, а нові поля ініціалізує нульовими значеннями за замовчуванням. Якщо ж програма передає розмір, більший за той, що підтримує поточне ядро, або заповнює ненульовими значеннями невідомі прапорці чи зарезервовані байти вирівнювання, системний виклик миттєво відхиляється з помилкою `E2BIG` або `EINVAL`.

```c
int ioctl(int iommufd, unsigned int cmd, void *arg);
```

| Код команди `ioctl` | Структура аргументу | Призначення та вплив на структури ядра |
| :--- | :--- | :--- |
| `IOMMU_IOAS_ALLOC` | `struct iommu_ioas_alloc` | Створення нового логічного адресного простору IOAS з власним деревом IOPT |
| `IOMMU_IOAS_FREE` | `struct iommu_ioas_free` | Знищення адресного простору IOAS та звільнення внутрішніх дескрипторів |
| `IOMMU_IOAS_MAP` | `struct iommu_ioas_map` | Закріплення пам'яті хоста та відображення віртуальних адрес HVA в IOVA |
| `IOMMU_IOAS_UNMAP` | `struct iommu_ioas_unmap` | Видалення відображення діапазону IOVA та розкріплення фізичних сторінок |
| `IOMMU_IOAS_COPY` | `struct iommu_ioas_copy` | Атомарне дублювання діапазону мапінгу між двома різними об'єктами IOAS |
| `IOMMU_DEVICE_GET_INFO` | `struct iommu_device_get_info` | Опитування апаратних можливостей контролера IOMMU для конкретного пристрою |
| `IOMMU_HWPT_ALLOC` | `struct iommu_hwpt_alloc` | Виділення фізичного апаратного домену сторінок HWPT або вкладеної таблиці |
| `IOMMU_HWPT_INVALIDATE` | `struct iommu_hwpt_invalidate` | Пряме скидання записів кешу трансляцій IOTLB фізичного IOMMU |
| `IOMMU_FAULT_QUEUE_ALLOC` | `struct iommu_fault_alloc` | Створення черги асинхронної доставки сторінкових помилок пристрою у userspace |

## 2. Керування логічними адресними просторами IOAS

Об'єкт `IOAS` (I/O Address Space) представляє абстрактну карту віртуальної пам'яті вводу-виводу. Всередині ядра Linux кожен IOAS містить власне червоно-чорне дерево інтервалів `iopt_pages`, яке веде єдиний облік закріплених сторінок пам'яті хоста (`pin_user_pages()`), повністю відокремлюючи цей процес від апаратних особливостей конкретних контролерів IOMMU.

### 2.1. `IOMMU_IOAS_ALLOC`
Виділяє новий об'єкт `iommufd_ioas` усередині контексту файлового дескриптора `/dev/iommufd`.

```c
struct iommu_ioas_alloc {
    __u32 size;
    __u32 flags;
    __u32 out_ioas_id;
};
```

* `size`: Розмір структури `sizeof(struct iommu_ioas_alloc)`.
* `flags`: Бітова маска параметрів конфігурації. У поточній версії ядра зарезервовано для майбутніх оптимізацій (повинно дорівнювати 0).
* `out_ioas_id`: Вихідне поле. Ядро генерує та записує сюди унікальний у межах даного файлового дескриптора 32-бітний числовий дескриптор створеного IOAS.

**Коди помилок:**
* `EINVAL`: Некоректний розмір `size` або ненульові біти у полі `flags`.
* `ENOMEM`: Недостатньо пам'яті ядра для виділення внутрішньої структури `struct iommufd_ioas` та ініціалізації дерева трансляції сторінок `IOPT`.

---

### 2.2. `IOMMU_IOAS_MAP`
Виконує жорстке закріплення оперативної пам'яті процесу в фізичній RAM (`pin_user_pages()`) та вносить відповідність між віртуальною адресою вводу-виводу (IOVA) і віртуальною адресою процесу (HVA) у дерево трансляцій. Якщо до цього IOAS уже підключені апаратні пристрої, ядро одночасно програмує фізичні таблиці відповідних контролерів IOMMU.

```c
struct iommu_ioas_map {
    __u32 size;
    __u32 flags;
    __u32 ioas_id;
    __u32 __reserved;
    __u64 user_va;
    __u64 length;
    __u64 iova;
};
```

* `size`: `sizeof(struct iommu_ioas_map)`.
* `flags`: Бітова маска параметрів відображення:
  * `IOMMU_IOAS_MAP_FIXED_IOVA` (`1 << 0`): Вимагає розміщення мапінгу за точно вказаною в полі `iova` адресою. Якщо цей прапорець не виставлено, ядро самостійно знаходить вільний діапазон у просторі IOVA та повертає його значення у полі `iova`.
  * `IOMMU_IOAS_MAP_READABLE` (`1 << 1`): Надає периферійному пристрою дозвіл на читання даних з пам'яті хоста через транзакції DMA Read (`MRd`).
  * `IOMMU_IOAS_MAP_WRITEABLE` (`1 << 2`): Надає периферійному пристрою дозвіл на запис даних у пам'ять хоста через транзакції DMA Write (`MWr`).
* `ioas_id`: Числовий ідентифікатор цільового об'єкта IOAS.
* `__reserved`: Поле вирівнювання (повинно дорівнювати 0).
* `user_va`: Віртуальна адреса початку буфера пам'яті в адресному просторі поточного процесу (HVA). Адреса повинна бути строго вирівняна по межі сторінки апаратного MMU (4096 байтів або 2 MB / 1 GB для Hugepages).
* `length`: Довжина області пам'яті в байтах. Розмір повинен бути кратним розміру сторінки.
* `iova`: Бажана віртуальна адреса вводу-виводу (при активному прапорці `FIXED_IOVA`) або вихідне поле, куди ядро записує виділену адресу.

**Коди помилок:**
* `ENOENT`: Вказаного ідентифікатора `ioas_id` не існує в цьому контексті.
* `EEXIST`: Запитаний діапазон IOVA частково або повністю перетинається з уже наявним мапінгом при встановленому прапорці `IOMMU_IOAS_MAP_FIXED_IOVA`.
* `EFAULT`: Вказана адреса `user_va` не належить адресному простору викликаючого процесу або сторінки не можуть бути прочитані/записані згідно з правами VMA.
* `ENOMEM`: Виклик перевищує системний ліміт заблокованої пам'яті процесу `RLIMIT_MEMLOCK` або в системі вичерпано фізичні сторінки RAM.
* `EINVAL`: Неправильне вирівнювання адреси чи довжини буфера.

---

### 2.3. `IOMMU_IOAS_UNMAP`
Видаляє відображення зазначеного діапазону IOVA, видаляє записи з апаратних таблиць IOMMU, інвалідує відповідні кеші IOTLB на шині PCIe та зменшує лічильник закріплення фізичних сторінок, повертаючи пам'ять під загальне керування підсистеми управління пам'яттю ядра.

```c
struct iommu_ioas_unmap {
    __u32 size;
    __u32 ioas_id;
    __u64 iova;
    __u64 length;
};
```

* `size`: `sizeof(struct iommu_ioas_unmap)`.
* `ioas_id`: Ідентифікатор адресного простору IOAS.
* `iova`: Початкова адреса діапазону IOVA для видалення.
* `length`: Довжина діапазону в байтах.

---

### 2.4. `IOMMU_IOAS_COPY`
Копіює існуючі відображення з одного об'єкта IOAS в інший IOAS у межах того самого файлового дескриптора без повторного закріплення пам'яті в ядрі.

```c
struct iommu_ioas_copy {
    __u32 size;
    __u32 flags;
    __u32 dst_ioas_id;
    __u32 src_ioas_id;
    __u64 length;
    __u64 dst_iova;
    __u64 src_iova;
};
```

Ця операція є фундаментальною для швидкого клонування адресних карт при створенні тіньових таблиць або паралельних середовищ обробки без додаткових накладних витрат на виклики `pin_user_pages()`.

## 3. Апаратні таблиці сторінок HWPT та вкладена віртуалізація

Об'єкт `HWPT` (Hardware Page Table) інкапсулює реальну фізичну таблицю трансляцій конкретного апаратного контролера IOMMU (Intel VT-d Root/Context/SLPT, AMD-Vi DevTable, ARM SMMUv3 STE/CD).

### 3.1. `IOMMU_HWPT_ALLOC`
Створює явний об'єкт апаратної таблиці сторінок. Застосовується для конфігурації спеціалізованих апаратних режимів, активації відстеження брудних сторінок або створення двостадійних вкладених доменів (Nested Paging).

```c
struct iommu_hwpt_alloc {
    __u32 size;
    __u32 flags;
    __u32 dev_id;
    __u32 pt_id;
    __u32 out_hwpt_id;
    __u32 hwpt_type;
    __u32 data_len;
    __aligned_u64 data_uptr;
};
```

* `flags`:
  * `IOMMU_HWPT_ALLOC_NESTED_PARENT` (`1 << 0`): Створює HWPT як батьківський домен Стадії 2 (Stage 2 GPA → HPA). До цього домену надалі можна підключати вкладені таблиці Стадії 1 гостьової ОС.
  * `IOMMU_HWPT_ALLOC_DIRTY_TRACKING` (`1 << 1`): Вмикає апаратне протоколювання сторінок, модифікованих пристроєм через DMA, що необхідно для живої міграції віртуальних машин без зупинки гостя.
* `dev_id`: Дескриптор прив'язаного фізичного пристрою, чиї апаратні властивості та драйвер IOMMU визначатимуть формат сторінкової таблиці.
* `pt_id`: Ідентифікатор батьківського об'єкта. Якщо створюється звичайний або Stage 2 HWPT, сюди передається `ioas_id`. Якщо створюється гостьовий вкладений HWPT Stage 1, сюди передається `hwpt_id` батьківського домену Stage 2.
* `hwpt_type`: Тип створюваної структури:
  * `IOMMU_HWPT_TYPE_DEFAULT` (`0`): Стандартна таблиця ядра Linux.
  * `IOMMU_HWPT_TYPE_VTD_S1` (`1`): Вкладена таблиця Intel VT-d Stage 1 (структура контексту PASID).
  * `IOMMU_HWPT_TYPE_ARM_SMMUV3` (`2`): Вкладена таблиця ARM SMMUv3 Stage 1 (дескриптор контексту CD).
* `data_len`: Розмір переданої архітектурної структури конфігурації.
* `data_uptr`: Покажчик простору користувача на структуру параметрів, специфічну для конкретного процесора (наприклад, `struct iommu_hwpt_vtd_s1`).
* `out_hwpt_id`: Вихідний ідентифікатор створеної таблиці `HWPT`.

**Коди помилок:**
* `EOPNOTSUPP`: Апаратний IOMMU хоста не підтримує запитаний тип таблиці (наприклад, апаратна вкладена трансляція відсутня в даній ревізії кремнію).
* `EINVAL`: Некоректні параметри або конфлікт прапорців конфігурації.

---

### 3.2. `IOMMU_HWPT_INVALIDATE`
Передає запит на скидання записів кешу трансляцій IOTLB безпосередньо у фізичний контролер IOMMU. Використовується гостьовими гіпервізорами при зміні гостьових таблиць Stage 1 для збереження когерентності апаратури.

```c
struct iommu_hwpt_invalidate {
    __u32 size;
    __u32 hwpt_id;
    __aligned_u64 data_uptr;
    __u32 data_type;
    __u32 entry_len;
    __u32 entry_num;
    __u32 __reserved;
};
```

* `hwpt_id`: Ідентифікатор цільової вкладеної таблиці HWPT.
* `data_uptr`: Покажчик на масив структур запитів інвалідації.
* `data_type`: Формат записів інвалідації (наприклад, `IOMMU_HWPT_INVALIDATE_DATA_VTD_S1`).
* `entry_len`: Розмір одного запису в масиві.
* `entry_num`: Кількість записів у пакеті інвалідації. Пакетна передача дозволяє очистити сотні діапазонів сторінок за один системний виклик `ioctl`, значно зменшуючи кількість перемикань контексту ядра.

## 4. Черги апаратних сторінкових помилок (Fault Queue)

Для підтримки технології Shared Virtual Addressing (SVA) та обробки запитів на підвантаження сторінок за запитом від пристроїв (PCIe Page Request Interface — PRI) у підсистемі IOMMUFD реалізовано механізм черг помилок.

### `IOMMU_FAULT_QUEUE_ALLOC`
Створює спеціальний асинхронний канал передачі сторінкових промахів пристрою у простір користувача.

```c
struct iommu_fault_alloc {
    __u32 size;
    __u32 flags;
    __u32 out_fault_id;
    __u32 out_fault_fd;
};
```

* `out_fault_id`: Внутрішній числовий ідентифікатор черги помилок.
* `out_fault_fd`: Новий анонімний файловий дескриптор, який підтримує механізми `poll()`, `epoll()` та операцію `read()`. Коли периферійний пристрій генерує запит до сторінки, яка ще не виділена в RAM, контролер IOMMU поміщає дескриптор події в чергу. Процес простору користувача читає подію з `out_fault_fd`, підвантажує пам'ять у робочий набір процесу і підтверджує готовність сторінки ядру.

## 5. Інтеграція з дескрипторами пристроїв VFIO

Прив'язка фізичних пристроїв PCIe здійснюється за допомогою розширеного набору викликів `ioctl` над дескриптором самого пристрою VFIO:

| Код команди `ioctl` | Структура аргументу | Опис операції |
| :--- | :--- | :--- |
| `VFIO_DEVICE_BIND_IOMMUFD` | `struct vfio_device_bind_iommufd` | Реєструє дескриптор пристрою у файловому контексті IOMMUFD та повертає числовий `dev_id`. |
| `VFIO_DEVICE_UNBIND_IOMMUFD` | відсутня | Відв'язує пристрій від підсистеми IOMMUFD. |
| `VFIO_DEVICE_ATTACH_IOMMUFD_PT` | `struct vfio_device_attach_iommufd_pt` | Приєднує пристрій до вказаного `ioas_id` або `hwpt_id`, програмуючи апаратний IOMMU. |
| `VFIO_DEVICE_DETACH_IOMMUFD_PT` | `struct vfio_device_detach_iommufd_pt` | Від'єднує пристрій від поточної таблиці трансляцій. |

## 6. Правила життєвого циклу та залежностей між об'єктами

Внутрішня модель IOMMUFD побудована на строгій ієрархії володіння з підрахунком посилань (`kref`):

1. **Контекст файлу (`iommufd_ctx`):** Закриття файлового дескриптора `/dev/iommufd` миттєво ініціює каскадне очищення. Якщо до контексту все ще прив'язані пристрої, ядро примусово від'єднує їх від апаратних таблиць сторінок, скидає всі налаштовані IOTLB та розкріплює фізичну пам'ять.
2. **Блокування видалення IOAS (`EBUSY`):** Неможливо знищити об'єкт IOAS за допомогою `IOMMU_IOAS_FREE`, якщо до нього підключено хоча б один активний пристрій `dev_id` або від нього залежить дочірня таблиця `HWPT`. Програма зобов'язана спочатку виконати `DETACH` або знищити дочірні HWPT.
3. **Безпека при аварійному збої (Crash Safety):** Якщо користувацький процес аварійно завершується (наприклад, через сигнал `SIGSEGV` або `SIGKILL`), ядро Linux гарантує повну атомарну ізоляцію шини: пристрій скидається (Function Level Reset або переведення в стан D3hot), щоб запобігти неконтрольованому транзитному запису DMA в пам'ять хоста.
