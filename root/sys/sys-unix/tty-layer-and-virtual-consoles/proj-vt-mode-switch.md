# Реалізація сесійного перемикання VT і керування режимом клавіатури

Будь-який графічний сервер (Wayland-композитор на базі wlroots, Weston чи Mutter, сервер Xorg, вбудована графічна бібліотека DirectFB або системна консоль kmscon), що працює безпосередньо поверх апаратного вузла відеокарти `/dev/dri/card0` та віртуальних терміналів ядра Linux, стикається з необхідністю низькорівневої диспетчеризації ресурсів дисплея та пристроїв введення. Якщо графічний процес просто відкриє дескриптор віртуального термінала `/dev/tty1` і запустить цикл рендерингу без спеціального узгодження з ядром, у системі виникає потрійний апаратний конфлікт:

1. **Конфлікт обробки введення:** за замовчуванням клавіатура обслуговується драйвером `drivers/tty/vt/keyboard.c` та лінійною дисципліною `N_TTY`. Коли користувач у графічному вікні вводить текст, сканкоди клавіш одночасно потрапляють до підсистеми `evdev` (звідки їх зчитує `libinput` для потреб графічного оточення) і в буфер лінійної дисципліни `N_TTY` фонової консолі. У результаті фонова командна оболонка (`bash` чи `zsh`) сприймає ці символи як команди й починає виконувати неконтрольовані дії наосліп у фоні.
2. **Конфлікт доступу до відеопам'яті:** ядро Linux підтримує апаратне перемикання віртуальних консолей комбінаціями клавіш `Ctrl+Alt+F1`..`Ctrl+Alt+F12`. За стандартного автоматичного режиму (`VT_AUTO`) ядро перемикає покажчик активної консолі миттєво. Текстовий драйвер консолі (`fbcon` або `vgacon`) починає записувати символи у відеопам'ять саме тоді, коли графічний процесор (GPU) виконує тривимірний конвеєр рендерингу (Vulkan або OpenGL) чи атомарний переворот кадрових буферів (KMS Page Flip). Це призводить до спотворення зображення, пошкодження внутрішніх таблиць відеопам'яті та апаратного скидання відеодрайвера (*GPU hang / TDR*).
3. **Ексклюзивність прав DRM-майстра:** у підсистемі ядра Direct Rendering Manager (DRM/KMS) статус головного розпорядника пристрою (`DRM_MASTER`) може належати лише одному файловому дескриптору на кожен первинний вузол `/dev/dri/cardN`. Цей статус надає виключне право конфігурувати режими монітора (CRTC, розгортку, площини та апаратні курсори). Щоб інша сесія або текстова консоль ядра змогла переналаштувати екран, активний графічний процес зобов'язаний добровільно відмовитися від статусу майстра.

Нижче наведено повну реалізацію низькорівневого диспетчера сесій мовами C та C++, що реалізує протокол узгодженого перемикання віртуальних терміналів ядра Linux.

## Механіка захоплення та конфігурації VT

Процес ініціалізації сесійного диспетчера починається з відкриття термінального вузла. Якщо графічний сервер запускається з дисплейного менеджера (GDM, SDDM, LightDM) або системної служби без жорсткої прив'язки до номера консолі, він звертається до псевдопристрою `/dev/tty0` (який завжди вказує на поточну активну віртуальну консоль) викликом `open("/dev/tty0", O_RDWR | O_CLOEXEC)`.

Керівний виклик `ioctl(tty0_fd, VT_OPENQRY, &free_vt)` сканує внутрішню бітову маску виділених консолей ядра у файлі `drivers/tty/vt/vt_ioctl.c` і повертає номер першого вільного, ще не відкритого термінала (наприклад, `7` або `8`). Отримавши номер, процес відкриває відповідний вузол `/dev/tty7` із прапорцями `O_RDWR | O_NOCTTY | O_CLOEXEC`. Прапорець `O_NOCTTY` є критично важливим: він забороняє ядру призначати цю відкриту консоль керуючим терміналом сесії процесу, що захищає диспетчер від отримання сторонніх сигналів керування завданнями (`SIGINT`, `SIGTSTP`, `SIGHUP`).

Після відкриття термінала диспетчер перемикає активний екран на виділений номер викликом `ioctl(tty0_fd, VT_ACTIVATE, free_vt)` і блокує потік до завершення операції ядром через `ioctl(tty0_fd, VT_WAITACTIVE, free_vt)`.

### Придушення текстового курсора та виводу ядра: `KDSETMODE`

Щоб текстовий шар ядра не втручався у вивід пікселів, диспетчер перемикає режим відображення консолі викликом `ioctl(tty_fd, KDSETMODE, KD_GRAPHICS)`.

У режимі `KD_GRAPHICS` підсистема віртуальних консолей ядра:
- Повністю вимикає апаратний та програмний таймер текстового курсора (`vt_cursor`). У текстовому режимі `KD_TEXT` курсор постійно блимає поверх пам'яті кадру, змінюючи атрибути знакомісць та пошкоджуючи графічні буфери.
- Блокує виведення текстових повідомлень драйвером консолі `fbcon` (включно з повідомленнями ядра `printk`), перенаправляючи системний журнал виключно в кільцевий буфер `dmesg`.
- Призупиняє операції прокручування екрана та скидає буфери відображення знакогенератора.

При штатному або аварійному виході з програми диспетчер зобов'язаний повернути режим `ioctl(tty_fd, KDSETMODE, KD_TEXT)`, інакше після повернення в командний рядок користувач не побачить текстового курсора та виводу символів.

### Ізоляція клавіатури: `K_OFF`, `K_RAW` та передача керування в `evdev`

Щоб натискання клавіш не породжували символи в черзі лінійної дисципліни `N_TTY`, диспетчер перемикає режим трансляції клавіатури. Перед модифікацією обов'язково зчитується та зберігається початковий режим роботи через `ioctl(tty_fd, KDGKBMODE, &orig_kb_mode)`, після чого викликається `ioctl(tty_fd, KDSKBMODE, K_OFF)`.

Ядро підтримує кілька режимів трансляції сканкодів:
- `K_RAW` (`0x00`): драйвер `keyboard.c` передає сирі 1-байтові сканкоди стандарту XT Set 1 у чергу читання TTY (із встановленням 7-го біта при відпусканні клавіші). Цей режим використовувався серверами X11 до появи уніфікованої підсистеми `evdev`.
- `K_MEDIUMRAW` (`0x02`): проміжний режим сканкодів, що транслює коди клавіш від 0 до 255 в 1- або 2-байтові послідовності, згладжуючи відмінності між різними типами клавіатурних контролерів.
- `K_XLATE` (`0x01`) та `K_UNICODE` (`0x03`): стандартні режими текстової трансляції з використанням ядерних таблиць розкладок `key_maps` та генерацією символів UTF-8.
- `K_OFF` (`0x04`): повне вимкнення генерації подій у чергу TTY. Драйвер консолі ігнорує всі апаратні переривання клавіатури й не надсилає жодного байта лінійній дисципліні.

Сучасні графічні сервери встановлюють саме режим `K_OFF`. Усе введення (клавіатури, миші, сенсорні екрани) перехоплюється безпосередньо з вузлів пристроїв `/dev/input/event*` за допомогою підсистеми `evdev` та бібліотеки `libinput`. Обробка розкладок, модифікаторів та комбінацій клавіш виконується в просторі користувача бібліотекою `libxkbcommon`, повністю відокремлюючи графічний інтерфейс від застарілих ядерних таблиць відображення.

## Протокол узгодженого перемикання `VT_PROCESS`

За замовчуванням віртуальний термінал перебуває в автоматичному режимі `VT_AUTO`. У цьому режимі комбінація клавіш `Ctrl+Alt+Fn` або виклик команди `chvt` змушує ядро негайно перепризначити покажчик поточної активної консолі.

Для безпечного перемикання диспетчер переводить термінал у кооперативний режим `VT_PROCESS`, заповнюючи структуру `struct vt_mode` (`mode = VT_PROCESS`, `relsig = SIGUSR1`, `acqsig = SIGUSR2`, `waitv = 0`, `frsig = 0`) і викликаючи `ioctl(tty_fd, VT_SETMODE, &vtm)`.

Поле `mode = VT_PROCESS` вказує ядру, що перемикання консолі має відбуватися виключно за згодою процесу. Поля `relsig` та `acqsig` призначають сигнали POSIX, якими ядро сповіщатиме процес про запит на звільнення (`release`) та повернення (`acquire`) віртуальної консолі.

### Фаза звільнення дисплея (`VT_RELEASE_SIGNAL` / `SIGUSR1`)

Коли користувач натискає комбінацію перемикання на іншу консоль (або надходить виклик `VT_ACTIVATE` від іншого процесу):

```
Користувач (Ctrl+Alt+F2)
       │
       ▼
Ядро Linux (drivers/tty/vt/vt_ioctl.c)
       │
       ├─► Надсилає сигнал SIGUSR1 процесу-володарю VT
       │
       ▼
Графічний диспетчер (простір користувача)
       │
       ├─ 1. Встановлює прапорець is_active = false (зупиняє рендеринг кадру)
       ├─ 2. Призупиняє опитування пристроїв введення evdev (libinput_suspend)
       ├─ 3. Викликає drmDropMaster(drm_fd) (віддає апаратний доступ до GPU)
       ├─ 4. Викликає ioctl(tty_fd, VT_RELDISP, 1) (підтверджує звільнення)
       │
       ▼
Ядро Linux завершує перемикання та активує цільову консоль TTY2
```

Якщо процес отримав `relsig`, але не викликав `ioctl(tty_fd, VT_RELDISP, 1)`, ядро не завершить перемикання. Якщо ж передати `ioctl(tty_fd, VT_RELDISP, 0)`, диспетчер відхилить запит на зміну консолі (це застосовується у випадках, коли виконується критична транзакція запису у відеопам'ять, яку не можна переривати).

### Фаза відновлення консолі (`VT_ACQUIRE_SIGNAL` / `SIGUSR2`)

Коли користувач повертається на графічну консоль (наприклад, через `Ctrl+Alt+F7`):

```
Користувач (Ctrl+Alt+F7)
       │
       ▼
Ядро Linux активує TTY7 і надсилає SIGUSR2 процесу-володарю
       │
       ▼
Графічний диспетчер (простір користувача)
       │
       ├─ 1. Викликає drmSetMaster(drm_fd) (повертає статус DRM-майстра)
       ├─ 2. Перевіряє чергу відкладених подій hotplug від libudev
       ├─ 3. Відновлює стан KMS: переналаштовує CRTC, кадровий буфер та розгортку
       ├─ 4. Відновлює опитування evdev (libinput_resume)
       ├─ 5. Викликає ioctl(tty_fd, VT_RELDISP, VT_ACKACQ) (підтверджує готовність)
       ├─ 6. Встановлює is_active = true та відновлює цикл рендерингу
       │
       ▼
Графічний інтерфейс відновлює показ зображення на екрані
```

Виклик `drmSetMaster()` повертає процесу право виконувати системні виклики керування режимами KMS (`DRM_IOCTL_MODE_SETCRTC`, `DRM_IOCTL_MODE_ATOMIC_COMMIT`). Відновлення конфігурації кадрового буфера та площин є обов'язковим, оскільки інший процес (або текстовий драйвер `fbcon`) міг змінити роздільну здатність екрана чи формат кольору під час перебування на іншій консолі.

Підтвердження `ioctl(tty_fd, VT_RELDISP, VT_ACKACQ)` повідомляє ядру, що процес успішно відновив свій внутрішній графічний стан.

## Динамічне виявлення пристроїв через `libudev` та ізоляція `evdev`

Справжній диспетчер робочої станції не може обмежуватися фіксованим списком пристроїв, відкритих під час запуску. Користувач може підключити зовнішній монітор через DisplayPort/HDMI, від'єднати кабель USB-C док-станції, увімкнути бездротову мишу або під'єднати зовнішню відеокарту (eGPU) в будь-який момент — включно з тим часом, коли графічна сесія перебуває у фоні на неактивному VT.

Для відстеження апаратних змін використовується бібліотека `libudev`, яка слухає широкомовні повідомлення ядра через мережевий сокет `NETLINK_KOBJECT_UEVENT`.

### Інтеграція сокета `udev_monitor` в мультиплексор `epoll`

Ініціалізація монітора вимагає створення контексту `udev` та фільтрації подій за потрібними підсистемами:

1. **Створення екземпляра монітора:** виклик `udev_monitor_new_from_netlink(udev, "udev")` створює дескриптор слухача udev-демона.
2. **Встановлення фільтрів підсистем:** за допомогою викликів `udev_monitor_filter_add_match_subsystem_devtype(mon, "drm", NULL)` та `udev_monitor_filter_add_match_subsystem_devtype(mon, "input", NULL)` монітор обмежує потік подій виключно відеокартами (`/dev/dri/card*`) та пристроями введення (`/dev/input/event*`), відсікаючи надлишкові повідомлення від блокових накопичувачів та мережевих адаптерів.
3. **Активація прийому:** виклик `udev_monitor_enable_receiving(mon)` переводить сокет у робочий стан.
4. **Реєстрація дескриптора в `epoll`:** файловий дескриптор сокета, отриманий через `udev_monitor_get_fd(mon)`, додається до головного екземпляра `epoll` з маскою `EPOLLIN`.

Коли в системі відбувається апаратна зміна, `epoll_wait` сигналізує про готовність читання з сокета udev. Диспетчер вичитує об'єкт `struct udev_device *dev = udev_monitor_receive_device(mon)` та аналізує дію `udev_device_get_action(dev)` (`"add"`, `"remove"`, `"change"`).

### Асинхронна обробка Hotplug під час зміни VT: стан активності

Критичним інженерним нюансом є залежність реакції на udev-події від поточного стану активності консолі (`is_active`):

- **Подія на активній консолі (`is_active == true`):**
  - Якщо надійшла дія `"change"` для підсистеми `drm` (наприклад, підключення монітора до роз'єму DP-1), процес володіє статусом `DRM_MASTER`. Він має повне право негайно виконати зондування конекторів (`drmModeGetConnector` із примусовим опитуванням EDID), перерахувати доступні відеорежими, створити новий кадровий буфер та застосувати оновлену конфігурацію екрана.
  - Якщо надійшла дія `"add"` для підсистеми `input`, процес відкриває новий вузол `/dev/input/eventX` та додає його до контексту `libinput`.
- **Подія на фоновій / неактивній консолі (`is_active == false`):**
  - Якщо монітор підключили або від'єднали, коли користувач працював у сусідньому текстовому терміналі TTY1, графічний процес **не є DRM-майстром**. Спроба викликати будь-який модифікуючий або апаратно-залежний керівний виклик KMS поверне системну помилку `-EACCES` або `-EBUSY`.
  - У цьому стані диспетчер не виконує важких операцій конфігурації. Він виставляє внутрішній атомарний прапорець `hotplug_pending = true` (або зберігає маску змінених пристроїв у черзі відкладених оновлень).
  - Коли користувач повертається на графічну консоль і процес отримує сигнал `VT_ACQUIRE_SIGNAL` (`SIGUSR2`), диспетчер спершу повертає статус майстра викликом `drmSetMaster()`, а вже потім перевіряє `hotplug_pending`. Якщо прапорець встановлений, виконується повна повторна інвентаризація відеовиходів та актуалізація конфігурації дисплеїв перед показом першого кадру.

### Захист пристроїв введення та монопольне захоплення `EVIOCGRAB`

Вимкнення клавіатури у віртуальному терміналі через `ioctl(tty_fd, KDSKBMODE, K_OFF)` запобігає потраплянню символів у лінійну дисципліну `N_TTY`, але **жодним чином не зупиняє генерацію подій у підсистемі `evdev`**.

Вузли `/dev/input/event*` продовжують транслювати пакети `struct input_event` незалежно від стану активної VT. Якби графічний сервер продовжував вичитувати події у фоні:
1. Виникав би витік конфіденційних даних: графічний композитор реєстрував би натискання клавіш, коли користувач вводить пароль суперкористувача у сусідній текстовій консолі TTY1.
2. Рухи миші у фоновому сеансі призводили б до невидимого зміщення курсора та помилкового спрацьовування елементів керування у згорнутих вікнах.

Щоб уникнути цього, диспетчер зобов'язаний реалізувати протокол призупинення введення:
- **При отриманні `relsig` (звільнення VT):** диспетчер викликає `libinput_suspend(li)` або для кожного відкритого дескриптора `evdev_fd` знімає монопольне захоплення викликом `ioctl(evdev_fd, EVIOCGRAB, 0)` і припиняє обробку подій `EPOLLIN` від вузлів введення.
- **При отриманні `acqsig` (відновлення VT):** диспетчер відновлює роботу підсистеми введення викликом `libinput_resume(li)` або повторно встановлює монопольний захват `ioctl(evdev_fd, EVIOCGRAB, 1)`. Виклик `EVIOCGRAB` гарантує, що події від конкретної клавіатури чи миші надходитимуть виключно цьому дескриптору й не дублюватимуться іншим процесам користувача.

## Багатомоніторні конфігурації: збереження та відновлення стану KMS (CRTC, Connector, Plane)

У сучасних робочих станціях відеокарта обслуговує топологію з кількох фізичних дисплеїв із різними роздільними здатностями, частотами оновлення та колірними просторами. В архітектурі Linux DRM/KMS апаратний конвеєр відображення розбитий на базові об'єкти:

```
[Кадрові буфери (FB)] ──► [Площини (Planes)] ──► [Контролери (CRTC)] ──► [Енкодери] ──► [Конектори (Connectors)]
```

- **Connector (конектор):** фізичний відеороз'єм (eDP-1, DP-1, HDMI-A-1), що зчитує блок EDID монітора та відстежує статус фізичного з'єднання (`DRM_MODE_CONNECTED`).
- **CRTC (дисплейний контролер):** апаратний блок відеокарти, який формує розгортку заданої роздільної здатності й частоти (Pixel Clock, HSync, VSync) та вичитує растрові дані з площин.
- **Plane (площина відображення):** апаратний шар змішування (Primary Plane для головного зображення, Cursor Plane для апаратного курсора, Overlay Planes для відеопотоків).

### Чому стан KMS руйнується під час перемикання консолей

Коли користувач перемикається на текстову консоль ядра (наприклад, TTY1):
1. Драйвер текстової консолі `fbcon` захоплює перший доступний CRTC (зазвичай CRTC 0), переналаштовує його таймінги на стандартну роздільну здатність кадрового буфера ядра (наприклад, 1024x768@60Hz) і прив'язує його до внутрішнього монохромного або 8-бітного буфера шрифтів.
2. Усі додаткові CRTC, підключені до другого та третього моніторів, `fbcon` зазвичай або вимикає (переводить у стан енергозбереження DPMS Off), або дублює на них зображення первинної консолі з порушенням нативних таймінгів панелей.
3. Інший графічний сервер (наприклад, паралельно запущена сесія Xorg чи інший Wayland-композитор на TTY3) може кардинально змінити маршрутизацію енкодерів до CRTC, виставити колірні профілі HDR або змінити формати пікселів із `DRM_FORMAT_XRGB8888` на `DRM_FORMAT_XBGR2101010`.

Якщо після сигналу `VT_ACQUIRE_SIGNAL` графічний диспетчер просто відновить рендеринг без повторної ініціалізації KMS, зображення на додаткових моніторах залишиться вимкненим, а на основному моніторі з'являться артефакти невідповідності розміру кадрового буфера поточній розгортці CRTC.

### Модель фіксації стану: Legacy KMS проти Atomic KMS

Для збереження та відновлення конфігурації використовується один із двох підходів:

#### 1. Класичний інтерфейс Legacy KMS (`drmModeSetCrtc`)
Диспетчер перед першим перемиканням зчитує конфігурацію кожного активного дисплея структурою `drmModeCrtcPtr crtc = drmModeGetCrtc(drm_fd, crtc_id)`. Він зберігає:
- `crtc->buffer_id` (ідентифікатор кадрового буфера FB ID);
- координати зміщення `x`, `y`;
- геометрію та прапорці режиму `crtc->mode` (`struct drm_mode_modeinfo`);
- список підключених конекторів `uint32_t connector_ids[]`.

При поверненні на консоль після виклику `drmSetMaster()` диспетчер ітерує по всіх збережених дисплеях і примусово відновлює стан системним викликом `drmModeSetCrtc(drm_fd, crtc_id, fb_id, x, y, connector_ids, count, &saved_mode)`.

#### 2. Сучасний інтерфейс Atomic KMS (`drmModeAtomicCommit`)
Сучасні композитори вмикають розширення Atomic API викликами `drmSetClientCap(drm_fd, DRM_CLIENT_CAP_UNIVERSAL_PLANES, 1)` та `drmSetClientCap(drm_fd, DRM_CLIENT_CAP_ATOMIC, 1)`.

У цій моделі диспетчер підтримує вектор цільового стану дисплеїв у пам'яті. При отриманні `SIGUSR2` формується єдина атомарна транзакція `drmModeAtomicReqPtr req = drmModeAtomicAlloc()`:

1. Для кожного **CRTC**:
   - Властивість `"ACTIVE"` = `1`.
   - Властивість `"MODE_ID"` = ідентифікатор блобу збереженого відеорежиму (`drmModeCreatePropertyBlob`).
2. Для кожного **Connector**:
   - Властивість `"CRTC_ID"` = цільовий ідентифікатор CRTC.
   - Властивість `"link-status"` = `DRM_MODE_LINK_STATUS_GOOD` (примушує драйвер повторно виконати узгодження каналу DisplayPort Link Training, якщо сигнал згас під час перебування у фоні).
   - Властивість `"DPMS"` = `DRM_MODE_DPMS_ON`.
3. Для головної **Primary Plane**:
   - Властивість `"FB_ID"` = дескриптор актуального кадрового буфера.
   - Властивість `"CRTC_ID"` = ідентифікатор прив'язаного CRTC.
   - Координати джерела (`"SRC_X"`, `"SRC_Y"`, `"SRC_W"`, `"SRC_H"`) та призначення (`"CRTC_X"`, `"CRTC_Y"`, `"CRTC_W"`, `"CRTC_H"`).

Транзакція виконується атомарним системним викликом `drmModeAtomicCommit(drm_fd, req, DRM_MODE_ATOMIC_ALLOW_MODESET, NULL)`, після чого запит звільняється викликом `drmModeAtomicFree(req)`.

Прапорець `DRM_MODE_ATOMIC_ALLOW_MODESET` є обов'язковим: він дозволяє драйверу ядра повністю зупинити та повторно запустити конвеєри синхронізації дисплейних контролерів і скинути PLL-генератори тактової частоти.

### Гібридна графіка (Multi-GPU та PRIME Offloading)

У ноутбуках та серверах із двома графічними адаптерами (наприклад, інтегрований Intel/AMD iGPU та дискретний NVIDIA/AMD dGPU) виникає розподіл обов'язків:
- **Первинний контролер дисплея (Primary KMS):** зазвичай iGPU (`/dev/dri/card0`), до якого фізично підведені лінії монітора та роз'єми материнської плати. Лише дескриптор цього вузла вимагає керування статусом `drmDropMaster` / `drmSetMaster` та прив'язується до перемикання VT.
- **Вторинний рендер-вузол (Secondary Render Node):** вузол дискретної відеокарти (`/dev/dri/renderD128`). Рендер-вузли взагалі позбавлені функцій керування режимами дисплея (Modesetting) і не використовують механізм DRM-майстра.
- **Синхронізація буферів PRIME:** графічний сервер виділяє текстури та виконує обчислення на вторинному GPU, експортує пам'ять у файлові дескриптори `dmabuf` через `drmPrimeHandleToFD()`, імпортує їх у первинний GPU викликом `drmPrimeFDToHandle()` і виводить на екран.

Під час перемикання VT скидання майстра виконується виключно на вузлі `card0`. Однак графічний сервер зобов'язаний скинути черги асинхронних парканів синхронізації (`sync_file` / `dma_fence`), щоб незавершені операції рендерингу дискретного GPU не заблокували процес у момент відпускання консолі.

## Синхронізація сигналів: чому `signalfd` та `epoll`

У класичній моделі POSIX обробка сигналів здійснюється реєстрацією функції через `sigaction`. Однак у графічних серверах використання традиційних асинхронних обробників створює небезпечні стани гонитви:

- **Обмеження async-signal-safety:** обробник сигналу виконується асинхронно на поточному стеку потоку в довільний момент часу. Стандарт POSIX суворо забороняє викликати з обробника функції, що не входять до списку безпечних (*async-signal-safe*). Виклики `ioctl`, `drmDropMaster`, `drmSetMaster`, операції виділення динамічної пам'яті (`malloc`, `free`), операції з об'єктами C++ чи вивід у потік (`printf`, `std::cout`) не є безпечними для сигналів. Якщо сигнал `SIGUSR1` надійде в момент, коли потік виконує виділення пам'яті й утримує внутрішній м'ютекс розподільника, спроба виклику `drmDropMaster` або форматування рядка всередині обробника призведе до взаємного блокування (*deadlock*).
- **Руйнування конвеєра рендерингу:** асинхронний виклик `drmDropMaster` посеред формування списку команд GPU спричиняє скидання дескриптора пристрою під час активного запису в кільцевий буфер команд (*command ring buffer*).

Щоб вирішити цю проблему, диспетчер блокує асинхронну доставку сигналів `SIGUSR1`, `SIGUSR2`, `SIGINT` та `SIGTERM` через `sigprocmask(SIG_BLOCK, &mask, NULL)`, після чого створює дескриптор `signalfd(-1, &mask, SFD_NONBLOCK | SFD_CLOEXEC)`.

Файловий дескриптор `signalfd` реєструється в мультиплексорі `epoll` на подію `EPOLLIN`. Коли ядро генерує сигнал перемикання або завершення, `epoll_wait` пробуджує головний потік. Диспетчер зчитує структуру `struct signalfd_siginfo` з дескриптора `sfd` і викликає обробники перемикання синхронно в загальному циклі подій разом із таймерами, дескрипторами `evdev`, сокетом `udev_monitor` та подіями VBlank від DRM.

## Порівняльний аналіз реалізацій C та C++

Наведені реалізації демонструють два підходи до керування ресурсами системного рівня:

### Реалізація мовою C (`c/main.c`)
- Стан сесії інкапсульовано в структурі `struct vt_session`, яка зберігає всі відкриті дескриптори (`tty_fd`, `drm_fd`, `sfd`, `epoll_fd`), початкові конфігурації термінала (`orig_kb_mode`, `orig_vt_mode`) та статус активності.
- Ініціалізація в `vt_session_init` виконується лінійно: кожен системний виклик перевіряє код повернення. У разі виникнення помилки функція послідовно закриває вже відкриті дескриптори та повертає `-1`.
- Очищення ресурсів у `vt_session_cleanup` гарантує відновлення `VT_SETMODE` та `KDSKBMODE` перед закриттям файлових дескрипторів.

### Реалізація мовою C++ (`cpp/main.cpp`)
- **Ідіома RAII та безпека дескрипторів:** клас `UniqueFd` інкапсулює володіння файловим дескриптором. Конструктор копіювання та оператор присвоєння копіюванням видалено (`= delete`), що виключає подвійне закриття дескриптора (*double close*). Переміщення реалізовано через оператор переміщення із передачею володіння та обнуленням джерела. Деструктор автоматично викликає `::close()` при виході з області видимості.
- **Обробка винятків:** конструктор `VtSessionManager` перевіряє результати системних викликів і генерує `std::system_error` із системним кодом помилки `errno` та описом контексту збою.
- **Гарантоване відновлення термінала:** відновлення режимів винесено в метод `restoreConsole() noexcept`, який викликається безпосередньо в деструкторі `~VtSessionManager()`. Якщо під час роботи головного циклу виникне неперехоплений виняток, механізм розгортання стека (*stack unwinding*) автоматично викличе деструктор і поверне термінал у вихідний стан.

## Відмовостійкість, аварійне відновлення та крайові випадки

Робота з низькорівневим терміналом вимагає врахування нештатних ситуацій, коли процес не встигає виконати штатну процедуру очищення:

1. **Аварійне падіння процесу (`SIGSEGV`, `SIGBUS`, `SIGKILL`):** якщо графічний сервер падає через помилку сегментації або завершується сигналом `SIGKILL`, деструктори не виконуються. Ядро автоматично закриває файлові дескриптори процесу, але стан TTY залишається в режимі `K_OFF` та `KD_GRAPHICS`. У результаті користувач бачить чорний екран або запрошення оболонки, але клавіатура повністю заблокована.
   - **Реанімація через Magic SysRq:** комбінація клавіш `Alt+SysRq+R` надсилає ядру пряму апаратну команду перемкнути клавіатуру активної консолі в режим `K_XLATE`. Після цього комбінація `Alt+SysRq+K` завершує всі процеси поточної консолі (*Secure Access Key*), змушуючи `systemd` перезапустити `getty`.
   - **Дистанційне відновлення через SSH:** якщо система доступна по мережі, стан консолі відновлюється командами:
     ```bash
     sudo kbd_mode -u -C /dev/tty1
     sudo chvt 1
     ```
2. **Таймаут відповіді на `VT_RELDISP`:** якщо графічний сервер завис у нескінченному циклі або заблокований на операції введення-виведення й не надсилає підтвердження `ioctl(tty_fd, VT_RELDISP, 1)`, ядро запускає внутрішній таймер очікування. За кілька секунд драйвер `drivers/tty/vt/vt_ioctl.c` примусово скидає монополію процесу й здійснює перемикання на цільову консоль, щоб запобігти повному зависанню робочої станції.

## Сучасна альтернатива: безпривілейовані сесії та `systemd-logind` / `seatd`

У сучасних дистрибутивах Linux пряме відкриття `/dev/tty0` та виклики `ioctl(VT_SETMODE)` вважаються застарілим підходом, оскільки вимагають запуску графічного сервера від імені суперкористувача (`root`) або наявності привілею `CAP_SYS_ADMIN`.

Сучасна архітектура базується на сесійних диспетчерах простору користувача (`systemd-logind`, `elogind` або легковагий `seatd`):

```
Графічний сервер (Wayland-композитор від звичайного користувача)
       │
       ├─ 1. Підключається до D-Bus (org.freedesktop.login1)
       ├─ 2. Викликає TakeControl() та TakeDevice(major, minor)
       │
       ▼
systemd-logind (працює як root, володіє VT та апаратурою)
       │
       ├─ Відкриває /dev/dri/card0 та /dev/input/event*
       ├─ Передає відкриті дескриптори клієнту через UNIX-сокет (SCM_RIGHTS)
       │
       ├─ При перемиканні VT: надсилає клієнту сигнал D-Bus PauseDevice()
       └─ При поверненні VT: надсилає сигнал ResumeDevice()
```

У цій моделі графічний сервер взагалі не взаємодіє з викликами `VT_*` напряму: усіма операціями захоплення консолі та керування статусом DRM-майстра керує сесійний демон.

## Практикум: збірка, запуск та трасування ftrace і udevadm

Для компіляції проєктів необхідні заголовні файли бібліотек `libdrm` та `libudev`:

```bash
# Збірка реалізації мовою C
gcc -O2 -Wall proj-vt-mode-switch/c/main.c -o vt_switch_c $(pkg-config --cflags --libs libdrm libudev)

# Збірка реалізації мовою C++
g++ -O2 -Wall proj-vt-mode-switch/cpp/main.cpp -o vt_switch_cpp $(pkg-config --cflags --libs libdrm libudev)
```

Запуск програми вимагає прав суперкористувача (для безпосереднього доступу до керівних викликів TTY та DRM) і виконується з віртуальної консолі:

```bash
sudo ./vt_switch_c /dev/tty3 /dev/dri/card0
```

### Відстеження перемикань через системний трейсер `ftrace`

Ядро Linux надає вбудовані точки трасування (*tracepoints*) для підсистеми віртуальних терміналів у `debugfs`. Для спостереження за перемиканням консолей у реальному часі:

```bash
# Увімкнення точок трасування VT
echo 1 | sudo tee /sys/kernel/debug/tracing/events/vt/vt_switch/enable
echo 1 | sudo tee /sys/kernel/debug/tracing/events/vt/vt_setmode/enable

# Зчитування журналу подій ядра
sudo cat /sys/kernel/debug/tracing/trace_pipe
```

При перемиканні між консолями (`Ctrl+Alt+F1` -> `Ctrl+Alt+F3`) журнал `ftrace` фіксує точні події зміни активного термінала та реєстрації сигналів процесу:

```text
vt_setmode: mode=1 relsig=10 acqsig=12 frsig=0
vt_switch: from=1 to=3
vt_switch: from=3 to=1
```

### Відстеження подій пристроїв через `udevadm monitor`

Для одночасного спостереження за генерацією uevent-повідомлень ядра при гарячому підключенні моніторів або USB-клавіатур:

```bash
sudo udevadm monitor --environment --subsystem-match=drm --subsystem-match=input
```

При підключенні монітора під час активної сесії утиліта виводить блок події ядра та udev:

```text
KERNEL[142.102345] change   /devices/pci0000:00/0000:00:02.0/drm/card0 (drm)
ACTION=change
DEVNAME=/dev/dri/card0
DEVTYPE=drm_minor
HOTPLUG=1
SUBSYSTEM=drm
```

### Інспекція стану Atomic KMS через `debugfs`

Поточну прив'язку площин, розгортку CRTC та активні конектори для поточної активної сесії можна переглянути у системному налагоджувальному файлі:
