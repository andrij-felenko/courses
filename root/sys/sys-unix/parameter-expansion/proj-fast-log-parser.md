# Високопродуктивний розбір структурованих логів та URI на чистій підстановці параметрів

У задачах системного адміністрування, моніторингу сервісів та аналізу телеметрії часто виникає необхідність обробляти великі масиви текстових даних: журнали доступу вебсерверів (Nginx, Apache, Envoy), потоки подій системного журналу або складні мережеві URI. Типовою архітектурною помилкою в сценаріях автоматизації є виклик зовнішніх утиліт (`cut`, `sed`, `awk`, `tr`, `basename`, `dirname`) усередині ітеративного циклу читання рядків `while IFS= read -r line`.

Кожен такий виклик усередині циклу змушує ядро Linux виконувати системний виклик `clone(2)` (або `fork(2)`), дублювати структури пам'яті процесу, завантажувати бінарний файл через `execve(2)`, викликати динамічний компонувальник `ld-linux.so` та створювати канали міжпроцесної взаємодії `pipe(2)`. На масиві всього у 10 000 рядків запуск трьох утиліт на ітерацію генерує 30 000 процесів, що призводить до катастрофічного падіння продуктивності та навантаження на планувальник завдань ядра.

Цей проєкт демонструє створення повнофункціонального, захищеного від збоїв та високошвидкісного парсера логів і параметрів URI мовою Bash. Уся обробка побудована виключно на операторах розкриття параметрів у пам'яті (Parameter Expansion) без жодного створення підпроцесів.

---

## 1. Архітектура та формат вхідних даних

Для аналізу обрано комбінований формат журналу доступу вебсервера Nginx, що містить IP-адресу клієнта (IPv4 або IPv6 у квадратних дужках), часову мітку у квадратних дужках, повний HTTP-запит у лапках, статус відповіді, кількість переданих байтів та час обробки:

```text
192.168.1.105 - - [25/Aug/2026:14:32:10 +0300] "GET /api/v2/telemetry/sensors.json?device_id=node-42&interval=5s&format=raw HTTP/1.1" 200 4096 "https://dashboard.internal/overview" "Agent/3.1" 0.012
```

Завдання парсера полягає у послідовній деконструкції рядка на структуровані поля:
1. **Клієнтський IP**: перший токен до пробілу. Для IPv6 адрес враховується можливість наявності двокрапок усередині адреси.
2. **Часова мітка**: вміст між символами `[` та `]`.
3. **HTTP-запит**: вміст між подвійними лапками, який далі розкладається на HTTP-метод, URI та версію протоколу.
4. **Деконструкція URI**:
   - Відокремлення базового шляху від рядка запиту (query string) за роздільником `?`.
   - Виділення каталогу (аналог `dirname`) та імені файлу (аналог `basename`) за роздільником `/`.
   - Виділення розширення файлу за символом `.`.
5. **Токенізація параметрів запиту**: розбиття рядка `key1=val1&key2=val2` на асоціативний масив пар ключ-значення, декодування символів `+` у пробіли та заміна базових процентних escape-послідовностей.

## 2. Реалізація високопродуктивного парсера

Нижче наведено повний скрипт парсера. Зверніть увагу, що кожна операція виділення підрядків використовує оператори `${var%%pattern}`, `${var#pattern}`, `${var##pattern}` та `${var%pattern}`, які працюють безпосередньо з буферами пам'яті процесу:

```bash
#!/usr/bin/env bash
set -euo pipefail

# Функція токенізації рядка параметрів URI (query string)
# Використовує посилання за ім'ям (nameref) для заповнення асоціативного масиву
parse_query_params() {
    local query="${1:-}"
    declare -n out_map="$2"
    out_map=()

    [[ -z "$query" ]] && return 0

    local pair key value
    while [[ -n "$query" ]]; do
        # Виділяємо першу пару до роздільника '&'
        pair="${query%%&*}"
        
        # Обрізаємо виділену пару з вихідного рядка query
        if [[ "$query" == *"&"* ]]; then
            query="${query#*&}"
        else
            query=""
        fi

        # Розділяємо пару на ключ і значення по першому '='
        if [[ "$pair" == *"="* ]]; then
            key="${pair%%=*}"
            value="${pair#*=}"
        else
            key="$pair"
            value=""
        fi

        # Заміна URL-кодованих плюсів на пробіли
        value="${value//+/ }"
        
        # Заміна базових шістнадцяткових escape-послідовностей
        value="${value//%20/ }"
        value="${value//%2F//}"
        value="${value//%3A/:}"

        out_map["$key"]="$value"
    done
}

# Функція деконструкції окремого рядка журналу доступу
parse_log_entry() {
    local line="$1"

    # 1. Виділення IP-адреси (все до першого пробілу)
    local ip="${line%% *}"
    local rest="${line#* }"

    # 2. Виділення часової мітки з квадратних дужок
    local timestamp="${rest#*\[}"
    timestamp="${timestamp%%\]*}"
    rest="${rest#*\] \"}"

    # 3. Виділення HTTP-запиту з подвійних лапок
    local request="${rest%%\"*}"
    rest="${rest#*\" }"

    # Розбиття запиту на метод, URI та протокол
    local method="${request%% *}"
    local req_tail="${request#* }"
    local uri="${req_tail% *}"
    local proto="${req_tail##* }"

    # 4. Деконструкція URI
    local raw_path="${uri%%\?*}"
    local query_string=""
    if [[ "$uri" == *"\?"* ]]; then
        query_string="${uri#*\?}"
    fi

    # Виділення каталогу та файлу (ідіоми dirname та basename)
    local dir_path="${raw_path%/*}"
    dir_path="${dir_path:-/}"
    local filename="${raw_path##*/}"
    
    local file_ext=""
    if [[ "$filename" == *"."* ]]; then
        file_ext="${filename##*.}"
    fi

    # 5. Виділення HTTP-статусу та кількості байтів
    local status="${rest%% *}"
    rest="${rest#* }"
    local body_bytes="${rest%% *}"

    # Вивід результатів аналізу
    echo "--------------------------------------------------"
    echo "Клієнт:     $ip"
    echo "Час:        $timestamp"
    echo "Метод:      $method"
    echo "Протокол:   $proto"
    echo "Шлях:       $raw_path"
    echo "Каталог:    $dir_path"
    echo "Файл:       $filename (тип: ${file_ext:-none})"
    echo "Статус:     $status (${body_bytes} байтів)"

    # Обробка параметрів запиту, якщо вони присутні
    if [[ -n "$query_string" ]]; then
        declare -A query_params
        parse_query_params "$query_string" query_params
        echo "Параметри запиту:"
        for k in "${!query_params[@]}"; do
            echo "  * $k => ${query_params[$k]}"
        done
    fi
}

# Демонстраційний запуск на тестовому записі
test_line='192.168.1.105 - - [25/Aug/2026:14:32:10 +0300] "GET /api/v2/telemetry/sensors.json?device_id=node-42&interval=5s&format=raw HTTP/1.1" 200 4096 "https://dashboard.internal/overview" "Agent/3.1" 0.012'
parse_log_entry "$test_line"
```

## 3. Методика тестування та порівняльний бенчмарк

Для об'єктивного вимірювання продуктивності було згенеровано тестовий файл `access.log` обсягом **10 000 рядків**, що містить варіативні HTTP-запити з різною довжиною шляхів та параметрів запиту.

Було реалізовано два незалежні тестові сценарії:
1. **Сценарій А (Subprocess Pipeline)**: у циклі `while IFS= read -r line` кожне поле виділяється окремою командою `echo "$line" | cut ...`, `dirname "$path"`, `basename "$path"` та `sed`.
2. **Сценарій Б (In-Memory Parameter Expansion)**: виділення виконується функцією `parse_log_entry` без зовнішніх викликів.

Запуск тестів здійснювався за допомогою системного профайлера `/usr/bin/time -v`, який зчитує системні лічильники структури `struct rusage` після завершення процесу:

```bash
# Тест підходу з конвеєром підпроцесів:
/usr/bin/time -v ./benchmark_subprocesses.sh access.log

# Тест підходу з підстановкою параметрів:
/usr/bin/time -v ./benchmark_pure_bash.sh access.log
```

## 4. Системний аналіз причин прискорення

Колосальна різниця у часі виконання пояснюється внутрішньою архітектурою ядра Linux та підсистеми управління віртуальною пам'яттю:
1. **Усунення викликів ядра**: При підстановці `${line%% *}` інтерпретатор Bash виконує пошук символу пробілу у власному буфері `char*` та виставляє нульовий байт або копіює підрядок. Це відбувається на рівні інструкцій CPU в просторі користувача (user space) без переходів у режим ядра (kernel mode).
2. **Відсутність навантаження на MMU та TLB**: Кожен системний виклик `fork(2)` вимагає дублювання таблиць віртуальних сторінок процесу. При наступному `execve(2)` ці таблиці скидаються, що інвалідує буфер асоціативної трансляції (TLB) процесора і спричиняє масові промахи апаратного кешу інструкцій та даних L1/L2/L3.
3. **Відсутність синхронізації IPC**: Використання конвеєрів `|` створює дескриптори труб `pipe(2)`, які вимагають синхронізації блокувань spinlock та mutex між процесом, що пише, і процесом, що читає, перериваючи виконання на очікуванні буфера введення-виведення.

## 5. Обробка крайових випадків та помилок формату

У реальних виробничих середовищах логи можуть містити пошкоджені рядки, аномальні шляхи без назв файлів або порожні параметри запиту. Розглянемо стійкість вбудованих операторів до таких дефектів:

1. **Відсутність параметрів запиту**: Якщо рядок URI не містить знака `?`, умова `[[ "$uri" == *"\?"* ]]` оцінюється як хибна, а вираз `raw_path="${uri%%\?*}"` повертає весь початковий рядок URI без модифікацій.
2. **Кореневі шляхи (`/`)**: Якщо `raw_path` дорівнює `/index.html`, вираз `dir_path="${raw_path%/*}"` повертає порожній рядок `""`. Використання захисного дефолту `dir_path="${dir_path:-/}"` відновлює правильне значення кореневого каталогу.
3. **Файли без розширення**: Якщо ім'я файлу не містить крапки (`Makefile`), умова `[[ "$filename" == *"."* ]]` запобігає помилковому виділенню розширення, лишаючи змінну `file_ext` порожньою.
4. **Повторювані роздільники в параметрах**: Якщо рядок запиту містить подвійний амперсанд `id=1&&mode=test`, алгоритм на операторах обрізання автоматично ігнорує порожню пару, не порушуючи цілісності асоціативного масиву.

## 6. Практичні рекомендації для системних інженерів

- **Обрізання префіксів до першого роздільника**: використовуйте `${var%% *}` для отримання першого слова і `${var#* }` для отримання залишку рядка.
- **Обрізання суфіксів після останнього роздільника**: використовуйте `${var%/*}` як заміну `dirname` та `${var##*/}` як заміну `basename`.
- **Вилучення розширень**: використовуйте `${var%.*}` для видалення останнього розширення та `${var%%.*}` для отримання базового імені без жодних розширень.
- **Масштабування на гігабайтні масиви**: Якщо обсяг вхідних даних перевищує мільйони рядків, чистий цикл оболонки починає обмежуватися однопотоковою інтерпретацією байт-коду Bash. У таких випадках слід запускати **єдиний потоковий процес** `awk` або скомпільовану бінарну утиліту (C/C++/Rust) для всього файлу, але в жодному разі не повертатися до виклику утиліт усередині циклу `while read`.
