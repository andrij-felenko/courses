# Довідник синтаксису підстановки параметрів POSIX та Bash

Підстановка параметра (Parameter Expansion) — це вбудований у командні оболонки сімейства Bourne/POSIX механізм маніпуляції рядками, структурами даних та метаданими змінних безпосередньо в адресному просторі процесу інтерпретатора. Операції виконуються на етапі розгортання слів (Word Expansion) без створення підпроцесів (`fork(2)`/`execve(2)`), міжпроцесних каналів (`pipe(2)`) чи перемикання контексту ядра.

Цей документ є вичерпною технічною специфікацією синтаксичних форм, внутрішньої семантики, інваріантів, обчислювальної складності та міжплатформної сумісності операторів підстановки параметрів для стандартів POSIX.1-2017 / POSIX.1-2024, розширень GNU Bash (версій 2.0–5.2+), Ksh93, Zsh, Dash та BusyBox ash.

---

## 1. Граматика та місце в конвеєрі розгортання слів

### 1.1. Формальна граматика розкриття параметрів (EBNF)

Синтаксичний аналізатор командної оболонки розпізнає конструкції підстановки параметрів за такою формальною граматикою:

```text
ParameterExpansion ::= '$' ParameterName
                     | '${' ParameterBody '}'

ParameterBody      ::= Parameter [ ':' ] ConditionalOp Word
                     | '#' Parameter
                     | Parameter TrimmingOp Pattern
                     | Parameter ':' Offset [ ':' Length ]
                     | Parameter '/' [ '/' | '#' | '%' ] Pattern [ '/' [ Replacement ] ]
                     | Parameter ( '^' [ '^' ] | ',' [ ',' ] | '~' [ '~' ] ) [ Pattern ]
                     | '!' ParameterName
                     | '!' PrefixOp ( '*' | '@' )
                     | '!' ArrayName '[' ( '@' | '*' ) ']'
                     | Parameter '@' TransformOp

Parameter          ::= Identifier | PositionalParam | SpecialParam | ArrayElement
ConditionalOp      ::= '-' | '=' | '?' | '+'
TrimmingOp         ::= '#' | '##' | '%' | '%%'
PrefixOp           ::= IdentifierPrefix
TransformOp        ::= 'Q' | 'E' | 'P' | 'A' | 'a' | 'k' | 'K' | 'u' | 'U' | 'L'
```

### 1.2. Фазовий порядок конвеєра розгортання слів (Word Expansion Pipeline)

Згідно зі стандартом POSIX.1-2017 (§2.6) та специфікаціями розширень GNU Bash, кожне нелапковане або частково лапковане слово командного рядка під час трансляції синтаксичного дерева (AST) у вектор аргументів `argv[]` проходить суворий семиетапний конвеєр обробки. Підстановка параметрів не є ізольованою процедурою: її поведінка прямо залежить від результатів попередніх фаз та визначає стан вхідних даних для наступних фаз.

```text
[Вхідний потік токенів AST]
  │
  ├─► 1. Brace Expansion (Bash/Ksh/Zsh): {a,b,c}, {1..5}
  │      └─► Генерує множинні слова ДО будь-яких підстановок змінних
  │
  ├─► 2. Tilde Expansion: ~ -> $HOME, ~user -> /home/user, var=~:~/bin
  │      └─► Розгортає префіксний символ тильди на початку слова або після ':'
  │
  ├─► 3. Parameter, Command, Arithmetic Expansion (в один прохід зліва направо):
  │      ├─ Parameter Expansion: ${var:-def}, ${var#pat}, ${var:0:5}
  │      ├─ Command Substitution: $(cmd), `cmd`
  │      └─ Arithmetic Expansion: $((expr))
  │
  ├─► 4. Process Substitution (Bash/Ksh/Zsh): <(cmd), >(cmd)
  │      └─► Створює FIFO або /dev/fd/N дескриптори в адресному просторі
  │
  ├─► 5. Word Splitting (Field Splitting за IFS) — лише для нелапкованих результатів
  │      └─► Сканує згенеровані байти на наявність роздільників $IFS
  │
  ├─► 6. Pathname Expansion (Globbing): *, ?, [...]
  │      └─► Зіставляє нелапковані метасимволи з файловою системою через glob(3)
  │
  └─► 7. Quote Removal: зняття неанульованих '', "", \
         └─► Видаляє захисні лапки перед передачею у системний виклик execve(2)
  │
[Фінальний вектор аргументів argv[] для системного виклику execve]
```

#### 1.2.1. Покрокова анатомія етапів конвеєра

1. **Фаза 1: Brace Expansion (розкриття фігурних дужок)**
   - Відбувається на суто текстовому рівні синтаксичного аналізатора до того, як інтерпретатор перевіряє наявність знака `$`.
   - Конструкція `{a,b,c}` або `{1..5}` дублює навколишній контекст і розбиває один токен AST на `N` незалежних токенів.
   - **Фазовий бар'єр**: Оскільки Brace Expansion виконується першою, будь-який синтаксис дужок, що утворюється в результаті підстановки параметра (наприклад, `VAR="{a,b}"; echo $VAR` або `${VAR:-{a,b}}`), **ніколи не розгортається у два слова**. Текст `{a,b}` залишається буквальним рядком, оскільки Фаза 1 для цього виразу вже минула.

2. **Фаза 2: Tilde Expansion (розкриття тильди)**
   - Інтерпретатор перевіряє, чи першим символом слова є нелапкований `~`. Якщо так, до першого слеша `/` рядок інтерпретується як ім'я користувача і замінюється на його домашній каталог через `$HOME` або `getpwnam(3)`.
   - У контексті присвоєння змінних (`PATH=~/bin:~other/bin`) розкриття тильди додатково виконується після кожного нелапкованого знака двокрапки `:`.

3. **Фаза 3: Parameter Expansion, Command Substitution, Arithmetic Expansion**
   - Усі три типи розгортання виконуються **в один прохід сканування рядка зліва направо** функцією `expand_word_internal()`.
   - Якщо оператор містить вкладені вирази (наприклад, `${var:-$(date +%Y)}` або `${arr[$((i+1))]}`), внутрішні вирази обчислюються ліниво — лише якщо відповідна гілка активується логікою оператора.

4. **Фаза 4: Process Substitution (підстановка процесів)**
   - Доступна в Bash, Ksh93 та Zsh на системах із підтримкою `/dev/fd` або іменованих каналів (FIFO).
   - Виконується паралельно з Фазою 3, замінюючи `<(cmd)` на шлях до файлового дескриптора (наприклад, `/dev/fd/63`).

5. **Фаза 5: Word Splitting (розбиття на поля за `$IFS`)**
   - Застосовується **виключно до результатів Фаз 3 і 4, які не були взяті в подвійні лапки**.
   - Рядки скануються на символи, присутні у змінній `IFS` (за замовчуванням: пробіл `\x20`, табуляція `\t`, новий рядок `\n`).
   - Будь-який текст, що був присутній у вихідному коді як літерал (наприклад, нелапкований `echo hello world`), не розбивається повторно на фазі 5, оскільки він уже був розбитий на слова лексером.

6. **Фаза 6: Pathname Expansion (розкриття файлових шляхів / Globbing)**
   - Сканує нелапковані слова на наявність метасимволів `*`, `?`, `[...]` (та розширень `extglob`).
   - Якщо збіги у файловій системі знайдені, токен замінюється відсортованим списком імен файлів. Якщо збігів немає, поведінка визначається прапорцями оболонки (`nullglob`, `failglob`, `nomatch`).

7. **Фаза 7: Quote Removal (видалення лапок)**
   - Фінальний прохід перед побудовою масиву `argv[]`.
   - Усі символи одинарних лапок `'`, подвійних лапок `"` та неанульовані зворотні слеші `\`, які використовувалися для екранування метасимволів на попередніх фазах, видаляються з пам'яті токена.

#### 1.2.2. Покрокове трасування складного багатофазового виразу

Розглянемо трасування конвеєра для виразу:
```bash
PREFIX=""
DATA="payload"
# Командний рядок:
cmd ~/"${PREFIX:-{bin,opt}}"/$((1 + ${#DATA}))/"$(echo "log file")"/*.{log,txt}
```

| Фаза конвеєра | Стан потоку слів / токенів | Виконана трансформація та системна поведінка |
| :--- | :--- | :--- |
| **0. Вхідний токен AST** | `~/"${PREFIX:-{bin,opt}}"/$((1 + ${#DATA}))/"$(echo "log file")"/*.{log,txt}` | Один токен AST перед розгортанням. |
| **1. Brace Expansion** | **Слово 1**: `~/"${PREFIX:-{bin,opt}}"/$((1 + ${#DATA}))/"$(echo "log file")"/*.log`<br>**Слово 2**: `~/"${PREFIX:-{bin,opt}}"/$((1 + ${#DATA}))/"$(echo "log file")"/*.txt` | Розгортається лише нелапкований `*.{log,txt}`. Шаблон `{bin,opt}` захищений `${...}` і лапками — залишається незмінним. |
| **2. Tilde Expansion** | **Слово 1**: `/home/user/"${PREFIX:-{bin,opt}}"/$((1 + ${#DATA}))/"$(echo "log file")"/*.log`<br>**Слово 2**: `/home/user/"${PREFIX:-{bin,opt}}"/$((1 + ${#DATA}))/"$(echo "log file")"/*.txt` | Початковий `~/` замінюється значенням `$HOME` (`/home/user/`). |
| **3. Parameter / Cmd / Arith** | **Слово 1**: `/home/user/"{bin,opt}"/8/"log file"/*.log`<br>**Слово 2**: `/home/user/"{bin,opt}"/8/"log file"/*.txt` | 1. `${PREFIX:-{bin,opt}}` -> `"{bin,opt}"` (дефолт);<br>2. `${#DATA}` = 7, `$((1 + 7))` -> `8`;<br>3. `$(echo "log file")` -> `"log file"`. |
| **4. Process Subst** | Без змін | Відсутні конструкції `<(...)` чи `>(...)`. |
| **5. Word Splitting** | **Слово 1**: `/home/user/"{bin,opt}"/8/"log file"/*.log`<br>**Слово 2**: `/home/user/"{bin,opt}"/8/"log file"/*.txt` | Подвійні лапки захищають `"log file"` та `"{bin,opt}"` від поділу за `$IFS`. Кількість слів: 2. |
| **6. Pathname Expansion** | **Якщо збіг існує**:<br>`/home/user/{bin,opt}/8/log file/app.log`<br>`/home/user/{bin,opt}/8/log file/sys.txt`<br>*(якщо файлів немає — шаблони лишаються)* | Нелапковані `*.log` та `*.txt` зіставляються з файловою системою через `glob(3)`. |
| **7. Quote Removal** | `/home/user/{bin,opt}/8/log file/app.log`<br>`/home/user/{bin,opt}/8/log file/sys.txt` | Видаляються зовнішні лапки навколо `"{bin,opt}"` та `"log file"`. |
| **Фінальний `argv[]`** | `argv[0] = "cmd"`<br>`argv[1] = "/home/user/{bin,opt}/8/log file/app.log"`<br>`argv[2] = "/home/user/{bin,opt}/8/log file/sys.txt"` | Масив покажчиків передається у системний виклик `execve(2)`. |

#### 1.2.4. Механіка Word Splitting та взаємодія з `$IFS`

Після розгортання параметра без подвійних лапок інтерпретатор розщеплює згенерований рядок на окремі слова на основі поточної маски роздільників у змінній `IFS` (Internal Field Separator). Стандарт POSIX чітко розрізняє **пробільні (IFS White Space)** та **непробільні (IFS Non-White Space)** символи:

1. **Пробільні символи IFS** (пробіл `\x20`, табуляція `\t`, новий рядок `\n`):
   - Будь-яка послідовність із кількох пробільних символів IFS підряд розглядається як **один роздільник**.
   - Провідні (початкові) та кінцеві пробільні символи IFS на початку й у кінці розгорнутого рядка **ігноруються (strip)** і не утворюють порожніх слів.
   - Якщо результат підстановки складається виключно з пробільних символів IFS (наприклад, `VAR="   "; cmd $VAR`), результатом стає **0 аргументів** (слово повністю анігілюється).

2. **Непробільні символи IFS** (наприклад, `IFS=":"` або `IFS=","`):
   - Кожен окремий непробільний символ діє як суворий роздільник полів.
   - Дві коми чи двокрапки підряд `::` утворюють **порожнє поле** `""` (порожній аргумент у `argv[]`).
   - Провідні та кінцеві непробільні роздільники створюють порожні поля на початку та в кінці списку:
     ```bash
     IFS=":"
     DATA=":foo::bar:"
     set -- $DATA
     # Отримуємо 5 позиційних параметрів:
     # $1="" (порожній), $2="foo", $3="" (порожній), $4="bar", $5="" (порожній)
     ```

3. **Спеціальний випадок: `IFS=""` (порожній рядок)**:
   - Поділ на слова повністю вимикається для всього сценарію. Навіть нелапковані результати підстановки `${var}` передаються як єдине цілісне слово без поділу за пробілами.

### 1.3. Внутрішній алгоритм синтаксичного та лексичного розбору `${...}` (Lexer & State Machine)

Лексичний та синтаксичний аналізатор інтерпретатора командної оболонки (на рівні ядра `parse.y` та модуля розкриття підстановок `subst.c` у GNU Bash / Dash) перемикається у спеціалізований режим сканування, щойно у вхідному потоці токенів зустрічає комбінацію символів `$` та `{`.

#### Стейт-машина виділення меж виразу (`extract_dollar_brace_string`)

Оскільки всередині фігурних дужок можуть міститися лапки, вкладені підстановки команд `$(...)`, арифметичні вирази `$((...))`, символи екранування `\` та вкладені дужки `${...}`, простий пошук першого символу `}` призвів би до синтаксичного збою. Інтерпретатор запускає скінченний автомат (FSM), який підтримує стек станів та лічильники глибини:

```text
Вхідний потік: ${var:-$(echo "val_${inner:-1}")}
                │   │ │      │   │         ││││
                │   │ │      │   │         │││└─► Фінальне закриття: depth = 0 -> кінець виразу
                │   │ │      │   │         ││└──► Закриття подвійних лапок
                │   │ │      │   │         │└───► Закриття вкладеної ${inner:-1}: depth=1
                │   │ │      │   │         └────► Відкриття вкладеної ${inner:-1}: depth=2
                │   │ │      │   └──────────────► Відкриття подвійних лапок (IN_DOUBLE_QUOTE)
                │   │ │      └──────────────────► Закриття $(...): subshell_depth = 0
                │   │ └─────────────────────────► Відкриття $(...): subshell_depth = 1
                │   └───────────────────────────► Оператор дефолту (перехід до парсингу word)
                └───────────────────────────────► Початок Parameter Expansion: depth = 1
```

Стейт-машина обробляє потік символів за такими інваріантами:

1. **Контекст одинарних лапок (`IN_SINGLE_QUOTE`)**: Усередині `'...'` усі символи (включаючи `$`, `\`, `{`, `}`) сприймаються як буквальні байти даних. Лічильники глибини дужок не змінюються, доки не зустрінеться парна неанульована одинарна лапка.
2. **Контекст подвійних лапок (`IN_DOUBLE_QUOTE`)**: Усередині `"..."` дозволені вкладені розкриття параметрів `${...}`, команд `$(...)` та арифметики `$((...))`. Символ `}` всередині подвійних лапок зменшує лічильник `brace_depth` лише у разі, якщо він відповідає поточному рівню вкладеності виразу.
3. **Контекст підстановки команд (`IN_COMMAND_SUBST`)**: Зустріч `$( ` переводить автомат у режим відстеження круглих дужок (`paren_depth`). Будь-який символ `}` усередині тіла команди підпроцесу (наприклад, `${var:-$(echo {})}`) трактується як частина тексту команди і не закриває зовнішній блок параметра, доки `paren_depth > 0`.
4. **Контекст арифметичних виразів (`IN_ARITHMETIC`)**: При переході у `$(( ` автомат відстежує вкладеність круглих дужок арифметичного групування `((...))` для запобігання передчасному зіставленню дужок операторів.
5. **Контекст індексів масивів (`IN_ARRAY_SUBSCRIPT`)**: Усередині квадратних дужок `var[...]` символи роздільників (`:`, `/`, `%`, `#`) не інтерпретуються як оператори підстановки, що дозволяє використовувати вирази на зразок `${arr[i:2]}` або `${arr[a/b]}`.
6. **Лічильник глибини фігурних дужок (`brace_depth`)**: Кожна незакватована комбінація `${` збільшує `brace_depth` на `1`, а кожен незакватований символ `}` зменшує його на `1`. Розбір виразу завершується тоді й тільки тоді, коли `brace_depth` стає рівним `0`.

#### Правила усунення синтаксичних неоднозначностей (Disambiguation)

- **Колізія від'ємного зрізу та оператора дефолту**: Комбінація `:-` у `${var:-5}` згідно з граматикою розпізнається як єдиний атомарний токен оператора `USE_DEFAULT_VALUES`. Для того, щоб двокрапка була розпізнана як оператор зрізу (Substring Slicing), після неї обов'язково має бути пробіл `${var: -5}` або відкриваюча дужка арифметичного виразу `${var:(-5)}`. Лексичний аналізатор виконує жадібний lookahead на один символ: якщо наступний символ після `:` — це `-`, вираз однозначно трактується як умовний дефолт.
- **Екранування закриваючої фігурної дужки `\}`**: Якщо у правій частині (шаблоні чи тексті заміни) потрібен літеральний символ `}`, він екранується зворотним слешем `\}`. Автомат пропускає його без декременту лічильника `brace_depth`, а на фінальній фазі Quote Removal символ `\` знімається.
- **Розпізнавання префіксного оператора довжини `${#var}`**: Якщо перший символ після `{` — це `#`, лексичний аналізатор перевіряє наступний символ. Якщо за ним іде валідний ідентифікатор змінної або спеціальний параметр (`*`, `@`, `#`, `?`, `-`, `$`, `!`, цифра), конструкція однозначно парситься як оператор вимірювання довжини (`OP_LENGTH`). Якщо ж далі йде інший оператор обрізання або закриваюча дужка, вираз парситься згідно з граматикою спеціального параметра `$#` (наприклад, `${##}` — довжина значення `$#`).

## 2. Базові форми та перевірка наявності/непорожності (POSIX Baseline)

Стандарт POSIX.1-2017 (§2.6.2 «Parameter Expansion») фіксує вісім умовних форм, що спираються на стан змінної в таблиці символів інтерпретатора.

### 2.1. Архітектура таблиці символів, стек контекстів та стани змінних (Symbol Table & Scope Frames)

Внутрішня організація пам'яті інтерпретатора командної оболонки (на прикладі GNU Bash та POSIX-оболонок) базується на динамічних хеш-таблицях символів (`HASH_TABLE`) та ієрархічному стеку контекстів виклику (`VAR_CONTEXT`).

#### Структури пам'яті інтерпретатора (`HASH_TABLE`, `BUCKET_CONTENTS` та `SHELL_VAR`)

Усі ідентифікатори змінних та масивів зберігаються у хеш-таблиці `shell_variables`. Вона складається з динамічного масиву кошиків `BUCKET_CONTENTS **bucket_array` із колізіями, що вирішуються однозв'язними списками:

```text
/* Внутрішня структура кошика хеш-таблиці оболонки (hashlib.h) */
typedef struct bucket_contents {
    struct bucket_contents *next; /* Покажчик на наступний вузол у ланцюжку колізій */
    char *key;                    /* Ім'я змінної (рядок у heap) */
    void *data;                   /* Покажчик на структуру SHELL_VAR */
    int times_found;              /* Лічильник звернень для евристичної оптимізації */
} BUCKET_CONTENTS;

/* Головний дескриптор хеш-таблиці */
typedef struct hash_table {
    BUCKET_CONTENTS **bucket_array; /* Масив покажчиків на кошики */
    int nbuckets;                   /* Поточна кількість кошиків (степені 2 або прості числа) */
    int nentries;                   /* Загальна кількість збережених змінних */
} HASH_TABLE;
```

Кожна змінна описується екземпляром структури `SHELL_VAR` (`struct variable` у вихідному коді Bash `variables.h`):

```text
typedef struct variable {
    char *name;                         /* Ім'я ідентифікатора (null-terminated char*) */
    char *value;                        /* Значення змінної (скалярний рядок або покажчик на ARRAY/HASH_TABLE) */
    char *exportstr;                    /* Кешований рядок "NAME=VALUE" для envp[] у системному виклику execve */
    sh_var_value_func_t *dynamic_value; /* Колбек динамічного читання (SECONDS, RANDOM, LINENO) */
    sh_var_assign_func_t *assign_func;  /* Колбек динамічного запису */
    int attributes;                     /* Бітова маска прапорців стану та типів */
    int context;                        /* Глибина контексту виклику (ідентифікатор фрейму стека) */
} SHELL_VAR;
```

Поле `attributes` кодує повний системний стан змінної через бітові прапорці:
- `att_exported` (`0x00000001`): змінна передається у вектор оточення `envp[]` дочірнім процесам.
- `att_readonly` (`0x00000002`): змінна заблокована для мутацій та видалення через `unset`.
- `att_integer` (`0x00000008`): арифметичний тип (будь-яке присвоєння автоматично обчислюється через `evalexp()`).
- `att_array` (`0x00000004`): індексований розріджений масив (`ARRAY*` у полі `value`).
- `att_assoc` (`0x00000040`): асоціативний масив (`HASH_TABLE*` у полі `value`).
- `att_nameref` (`0x00000080`): непряме посилання на ім'я іншої змінної (`declare -n`).
- `att_local` (`0x00000100`): змінна прив'язана до локального контексту поточної функції.
- `att_lowercase` (`0x00000800`): автопереведення значень у нижній регістр при записі (`declare -l`).
- `att_uppercase` (`0x00001000`): автопереведення значень у верхній регістр при записі (`declare -u`).

#### Динамічний стек контекстів виклику (Dynamic Scope Frames & `VAR_CONTEXT`)

Оболонка Bash реалізує динамічну область видимості (Dynamic Scoping). Локальні змінні функцій, оголошені через `local`, `declare` або `typeset`, не замінюють глобальну хеш-таблицю, а реєструються у поточному фреймі контексту `VAR_CONTEXT`:

```text
[Глобальний контекст: global_variables] (context = 0)
   ▲
   │ (up)
[Фрейм функції func_A: VAR_CONTEXT] (scope = 1, table = HASH_TABLE_1)
   ▲
   │ (up)
[Фрейм вкладеної функції func_B: VAR_CONTEXT] (scope = 2, table = HASH_TABLE_2) ◄── current_var_context
```

1. **Вхід у функцію (`push_var_context()`)**: При виклику функції інтерпретатор створює новий вузол `VAR_CONTEXT`, збільшує лічильник глибини стека `variable_context++`, виділяє локальну хеш-таблицю `table` та перемикає покажчик `current_var_context`.
2. **Пошук змінної (`find_variable(name)`)**: Сканування починається з локальної хеш-таблиці `current_var_context->table`. Якщо ідентифікатор не знайдено, ітератор піднімається за покажчиком `context->up` крізь усі батьківські фрейми аж до глобального `global_variables`. Це означає, що функція бачить локальні змінні функцій, які її викликали, якщо вони не перекриті власним оголошенням.
3. **Затінення змінних (Variable Shadowing)**: Оголошення `local VAR="foo"` у внутрішній функції створює новий запис `SHELL_VAR` у поточній локальній хеш-таблиці з прапорцем `att_local` та `context = variable_context`. Батьківський або глобальний запис із тим самим іменем лишається незмінним у зовнішній таблиці.
4. **Вихід із функції (`pop_var_context()`)**: Після завершення виконання тіла функції інтерпретатор обходить локальну хеш-таблицю `current_var_context->table`, звільняє пам'ять виділених рядків (`free(var->value)`), деалокує саму таблицю та повертає `current_var_context = current_var_context->up`. Усі затінені змінні зовнішнього контексту автоматично знову стають видимими.

#### Організація змінних середовища (`environ`) та синхронізація експорту

При запуску процесу оболонки функція ініціалізації `initialize_shell_variables(char **env)` ітерує масив `environ`, розбиває кожен рядок `KEY=VALUE` за першим символом `=`, виділяє структуру `SHELL_VAR` та маркує її прапорцями `att_exported | att_imported`.

Для мінімізації накладних витрат при наступних викликах зовнішніх бінарників оболонка використовує ліниве кешування експортного буфера:
- У полі `var->exportstr` зберігається готовий сформований рядок `NAME=VALUE`.
- Якщо значення змінної змінюється через присвоєння або оператор підстановки `${var:=val}`, буфер інвалідується (`free(var->exportstr); var->exportstr = NULL`).
- Перед системним викликом `execve(2)` функція `make_env_array_from_var_hash()` обходить таблиці символів, знаходить усі структури з виставленим бітом `att_exported` і збирає масив покажчиків `char **envp`. Якщо `exportstr` валідний, він використовується повторно без повторної алокації та виклику `sprintf()`.

#### Захист від модифікації (`readonly`) на рівні внутрішнього API

Змінні, позначені прапорцем `att_readonly` (через `readonly var`, `declare -r var` або `${var@a}` з бітом `r`), блокуються на рівні ядра інтерпретатора:
- Функція запису `bind_variable(name, value, flags)` перед модифікацією виконує перевірку:
  ```text
  if (var && (var->attributes & att_readonly)) {
      report_error("%s: readonly variable", name);
      return (var);
  }
  ```
- Функція знищення `makunbound(name, shell_variables)` блокує видалення: виклик `unset RO_VAR` або непряме обнулення повертає ненульовий код помилки `1`.
- Прапорець `att_readonly` є незворотним: команда `declare +r var` завершується помилкою синтаксису, оскільки зняття атрибута readonly заборонено архітектурою безпеки оболонки.

#### Організація масивів у пам'яті (`ARRAY` та `HASH_TABLE`)

У полі `SHELL_VAR.value` для скалярних змінних зберігається звичайний вказівник на рядок `char*`. Для складених типів інтерпретатор розміщує покажчики на спеціалізовані структури даних:

1. **Індексовані масиви (`declare -a`)**: Зберігаються у структурі `ARRAY`, яка містить двобічно зв'язаний список або сегментований масив елементів `ARRAY_ELEMENT`:
   ```text
   typedef struct array_element {
       array_ind_t ind;             /* 64-бітний цілочисельний індекс елемента */
       char *value;                 /* Рядкове значення елемента в heap */
       struct array_element *next;  /* Наступний елемент списку */
       struct array_element *prev;  /* Попередній елемент списку */
   } ARRAY_ELEMENT;

   typedef struct array {
       ARRAY_ELEMENT *head;         /* Покажчик на перший елемент */
       ARRAY_ELEMENT *last;         /* Покажчик на останній елемент для швидкого append */
       array_ind_t num_elements;    /* Фактична кількість ініціалізованих елементів */
       array_ind_t max_index;       /* Максимальний зайнятий індекс */
   } ARRAY;
   ```
   Завдяки зв'язному списку елементів індексовані масиви у Bash є **розрідженими (sparse)**: присвоєння `arr[1000000]="val"` виділяє пам'ять лише під один вузол `ARRAY_ELEMENT`, не витрачаючи мегабайти на порожні проміжні комірки.
2. **Асоціативні масиви (`declare -A`)**: У полі `SHELL_VAR.value` зберігається покажчик на окремий екземпляр `HASH_TABLE`. Кожен строковий ключ хешується через алгоритм розрахунку хешу рядків, а значення зберігаються у внутрішніх кошиках `BUCKET_CONTENTS`.

#### Три стани змінної в таблиці символів

З погляду операторів розгортання параметрів інтерпретатор розрізняє три взаємовиключні стани змінної:
1. **Unset (не встановлено)** — запис у таблиці символів відсутній (структура `SHELL_VAR` не створена взагалі або деалокована викликом `unset var`). Покажчик `find_variable(name)` повертає `NULL`.
2. **Set & Null (встановлено, але порожнє)** — структура `SHELL_VAR` присутня у хеш-таблиці, але покажчик `var->value` вказує на нульовий рядок (`value[0] == '\0'`, довжина 0).
3. **Set & Non-Null (встановлено зі значенням)** — структура `SHELL_VAR` присутня у хеш-таблиці, а `var->value` містить щонайменше один ненульовий байт даних (`value[0] != '\0'`).

Двокрапка (`:`) у синтаксисі оператора є **модифікатором перевірки на порожнечу**:
- **Форма без двокрапки** (`-`, `=`, `?`, `+`) реагує **виключно** на стан *Unset*. Якщо змінна встановлена як порожній рядок `var=""`, вона вважається валідною.
- **Форма з двокрапкою** (`:-`, `:=`, `:?`, `:+`) об'єднує стани *Unset* та *Set & Null*, трактуючи порожній рядок як неініціалізований стан.

### 2.2. Повна матриця умовних операторів

| Синтаксис | Стан: Unset | Стан: Set & Null (`var=""`) | Стан: Set & Non-Null (`var="abc"`) | Побічна дія (мутація таблиці символів) | Код помилки / Завершення |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `${var-word}` | `word` | `""` (порожній) | `abc` | Немає | 0 |
| `${var:-word}` | `word` | `word` | `abc` | Немає | 0 |
| `${var=word}` | `word` | `""` (порожній) | `abc` | При *Unset*: записує `var="word"` у пам'ять | 0 |
| `${var:=word}` | `word` | `word` | `abc` | При *Unset* або *Null*: записує `var="word"` у пам'ять | 0 |
| `${var?word}` | Друк `word` у `stderr`, фатальна зупинка | `""` (порожній) | `abc` | Аварійне переривання при *Unset* | Помилка (1–127) |
| `${var:?word}` | Друк `word` у `stderr`, фатальна зупинка | Друк `word` у `stderr`, фатальна зупинка | `abc` | Аварійне переривання при *Unset* або *Null* | Помилка (1–127) |
| `${var+word}` | `""` (порожній) | `word` | `word` | Немає | 0 |
| `${var:+word}` | `""` (порожній) | `""` (порожній) | `word` | Немає | 0 |

### 2.3. Семантика обчислення правої частини `word`

Права частина `word` піддається розкриттю лише у разі, якщо умова оператора вимагає її використання (Short-circuit Evaluation / Lazy Evaluation):
1. **Етапи розкриття всередині `word`**: під час обчислення `word` виконуються Tilde Expansion, Parameter Expansion, Command Substitution та Arithmetic Expansion. Поділ на слова (Word Splitting) та розкриття шляхів (Globbing) над `word` у процесі присвоєння **не виконуються**.
2. **Пропуск обчислення `word`**: Якщо `var` містить непорожній рядок, у виразі `${var:-$(rm -rf /tmp/test)}` підстановка команди `$(...)` не виконується взагалі, жоден дочірній процес не створюється.

```bash
# Приклад 1: Ліниве обчислення дефолтного значення
SESSION_ID="${AUTH_TOKEN:-$(generate_ephemeral_token)}"

# Приклад 2: Динамічне каскадне присвоєння порту сервісу
# Якщо HTTP_PORT не встановлено або порожнє, записує 8080 у змінну HTTP_PORT
: "${HTTP_PORT:=8080}"
```

### 2.4. Обмеження операторів присвоєння `${var=word}` та `${var:=word}`

Оператори мутації середовища підпорядковуються суворим системним інваріантам:
1. **Заборона модифікації позиційних параметрів**: Спроба виконати `${1:=default}` або `${2=fallback}` призводить до неперехоплюваної синтаксичної помилки `cannot assign to positional parameter` та аварійного завершення сценарію. Для читання аргументів використовується виключно немодифікуюча форма: `PARAM1="${1:-default}"`.
2. **Заборона модифікації спеціальних параметрів**: Записи `${@:=def}`, `${*:=def}`, `${#:=0}`, `${?:=0}`, `${$$:=1}`, `${!:=0}`, `${-:=x}` є невалідними.
3. **Змінні лише для читання (`readonly`)**: Застосування `${RO_VAR:=val}` до змінної з прапорцем `att_readonly` породжує фатальну помилку середовища `RO_VAR: is read-only` з кодом виходу `1`.

### 2.5. Семантика операторів перевірки помилок `${var?word}` та `${var:?word}`

1. **Якщо `word` вказано**: текст розгортається і друкується у стандартний потік помилок `stderr` у форматі:
   ```text
   sh: var: <розгорнутий_word>
   ```
2. **Якщо `word` опущено**: оболонка друкує повідомлення за замовчуванням:
   ```text
   sh: var: parameter null or not set
   ```
3. **Поведінка інтерактивної проти неінтерактивної оболонки**:
   - *Неінтерактивний скрипт*: негайно перериває виконання всього сценарію з ненульовим кодом виходу (зазвичай `1` або `2`).
   - *Інтерактивна сесія*: друкує повідомлення про помилку, перериває виконання поточної команди, але **не завершує сесію оболонки**.

### 2.6. Взаємодія з режимом `set -u` (`set -o nounset`)

Режим суворої перевірки `set -u` вимагає ініціалізації всіх змінних перед читанням. Стандарт POSIX чітко специфікує винятки:
- **Усі 8 умовних операторів** (`${var-def}`, `${var:-def}`, `${var=def}`, `${var:=def}`, `${var?err}`, `${var:?err}`, `${var+alt}`, `${var:+alt}`) **не викликають помилки `unbound variable`** при доступі до неоголошеної змінної `var`. Вони є легітимним стандартизованим способом опитування неініціалізованого стану під дією `set -u`.
- Звичайне розкриття `$var`, визначення довжини `${#var}` (у Dash та деяких версіях POSIX sh), оператори обрізання `${var#pat}` та зрізи `${var:0:2}` при неоголошеній `var` під дією `set -u` негайно завершують процес з кодом помилки `unbound variable`.

## 3. Вимірювання довжини та обрізання шаблонів (Trimming)

### 3.1. Визначення довжини рядка `${#var}`

Конструкція `${#var}` повертає довжину рядкового значення `var`.

| Форма виклику | Семантика | Результат при `var="Київ"` (UTF-8) | Результат при `var=""` | Результат при Unset |
| :--- | :--- | :---: | :---: | :---: |
| `${#var}` | Довжина рядка у символах | `4` (в UTF-8 локалі) / `8` (в C локалі) | `0` | `0` |
| `${#*}` або `${#@}` | Загальна кількість позиційних параметрів | Числове значення `$#` | `$#` | `0` (якщо аргументів немає) |
| `${#array[@]}` | Кількість елементів масиву (Bash/Ksh/Zsh) | Кількість ініціалізованих елементів | `0` | `0` |
| `${#array[index]}` | Довжина конкретного елемента масиву | Довжина рядка за вказаним індексом | `0` | `0` |

#### Механізм роботи з багатобайтовими кодуваннями:
- Якщо `LC_ALL=C` або `LC_CTYPE=C`, довжина розраховується як кількість байтів через `strlen(3)`.
- Якщо встановлена UTF-8 локаль (`uk_UA.UTF-8`, `en_US.UTF-8`), оболонка виконує ітеративне декодування символів через `mbrtowc(3)` або внутрішній UTF-8 декодер, повертаючи реальну кількість символів (code points).

### 3.2. Оператори обрізання префіксів і суфіксів (Pattern Trimming)

Стандарт POSIX визначає чотири оператори видалення підрядків за шаблоном зіставлення імен файлів (Shell Globbing Pattern):

| Синтаксис | Назва операції | Алгоритм зіставлення | Область видалення |
| :--- | :--- | :--- | :--- |
| `${var#pattern}` | Strip Shortest Prefix | Нежадібний (найкоротший збіг зліва) | Початок рядка (префікс) |
| `${var##pattern}` | Strip Longest Prefix | Жадібний (найдовший збіг зліва) | Початок рядка (префікс) |
| `${var%pattern}` | Strip Shortest Suffix | Нежадібний (найкоротший збіг справа) | Кінець рядка (суфікс) |
| `${var%%pattern}` | Strip Longest Suffix | Жадібний (найдовший збіг справа) | Кінець рядка (суфікс) |

```text
Рядок: /usr/local/bin/app.tar.gz

${var#*/}   ──►  usr/local/bin/app.tar.gz  (найкоротший префікс до '/')
${var##*/}  ──►  app.tar.gz                (найдовший префікс до '/') -> аналог basename
${var%/*}   ──►  /usr/local/bin            (найкоротший суфікс від '/') -> аналог dirname
${var%%/*}  ──►  ""                        (найдовший суфікс від першого '/')
${var%.*}   ──►  /usr/local/bin/app.tar    (найкоротший суфікс від '.')
${var%%.*}  ──►  /usr/local/bin/app        (найдовший суфікс від першої '.')
```

#### Синтаксис шаблонів `pattern`:
1. **Метасимволи**: `*` (будь-яка кількість символів, включаючи нуль), `?` (рівно один довільний символ), `[...]` (діапазон або набір символів).
2. **POSIX класи символів**: `[[:alnum:]]`, `[[:alpha:]]`, `[[:blank:]]`, `[[:cntrl:]]`, `[[:digit:]]`, `[[:graph:]]`, `[[:lower:]]`, `[[:print:]]`, `[[:punct:]]`, `[[:space:]]`, `[[:upper:]]`, `[[:xdigit:]]`.
3. **Екранування метасимволів**: Якщо шаблон містить літеральні символи `*`, `?` або `[`, їх необхідно екранувати зворотним слешем `\*` або огортати змінну шаблону в подвійні лапки: `${var#"$prefix"}`.
4. **Векторизація над масивами та аргументами**:
   - `"${@#pattern}"` застосовує обрізання префікса до кожного позиційного параметра індивідуально.
   - `"${array[@]%pattern}"` обрізає суфікс кожного елемента масиву.

### 3.4. Механіка локалей та багатобайтового кодування: LC_CTYPE, UTF-8, UTF-16, GB18030, Shift-JIS

Робота інтерпретатора командної оболонки з текстовими рядками під час розгортання параметрів фундаментально залежить від конфігурації підсистеми локалізації операційної системи (POSIX Locale Subsystem) та стандартної бібліотеки C (`libc`).

#### 3.4.1. Архітектура локалей POSIX та стан libc (`LC_ALL`, `LC_CTYPE`, `LANG`, `MB_CUR_MAX`)

Під час запуску процесу оболонка викликає системну функцію `setlocale(LC_ALL, "")` або `setlocale(LC_CTYPE, "")`, яка опитує змінні середовища та ініціалізує внутрішні таблиці класифікації символів і кодувань:

- **Ієрархія змінних оточення**:
  `LC_ALL` *(найвищий пріоритет)* ──► `LC_CTYPE` / `LC_COLLATE` ──► `LANG` *(дефолт)*.
  Якщо `LC_ALL` встановлено, вона примусово перевизначає будь-які значення `LC_CTYPE`, `LC_COLLATE` чи `LANG`.
- **Макрос `MB_CUR_MAX`**:
  Визначає максимальну кількість байтів, необхідних для представлення одного широкого символу (`wchar_t`) у поточній локалі:
  - `MB_CUR_MAX = 1` у локалях `C`, `POSIX`, `ISO-8859-1`, `KOI8-U`.
  - `MB_CUR_MAX = 4` у кодуваннях `UTF-8` та `GB18030`.
  - `MB_CUR_MAX = 2` у японських кодуваннях `Shift-JIS` (CP932) та `EUC-JP`.
- **Внутрішній стан декодера (`mbstate_t`)**:
  Для потокового декодування послідовностей байтів інтерпретатор викликає функції `mbrtowc(3)` та `wcrtomb(3)`. Об'єкт `mbstate_t` зберігає поточний стан зсуву (shift state) для контекстно-залежних або багатобайтових кодувань.

#### 3.4.2. Обчислення довжини рядка `${#var}` у багатобайтових кодуваннях

Алгоритм роботи префіксного оператора довжини `${#var}` залежить від активного стану локалі:

1. **Однобайтний режим (`LC_ALL=C` або `LC_CTYPE=C`)**:
   - Оболонка викликає швидку функцію `strlen(3)` або зчитує довжину з внутрішнього скалярного дескриптора.
   - Кожен байт рядка розглядається як один символ.
   - Часова складність: `O(1)` або `O(N)` (із використанням SIMD-інструкцій AVX-512/AVX2 у сучасних реалізаціях `glibc`).
2. **Багатобайтний режим (`UTF-8`, `uk_UA.UTF-8` тощо)**:
   - Інтерпретатор виконує ітеративний прохід по буферу пам'яті, декодуючи кожен символ через `mbrtowc(3)`:
     ```text
     size_t calculate_shell_strlen(const char *s) {
         size_t char_count = 0;
         mbstate_t ps;
         memset(&ps, 0, sizeof(ps));
         size_t bytes_left = strlen(s);
         const char *p = s;

         while (bytes_left > 0) {
             wchar_t wc;
             size_t n = mbrtowc(&wc, p, bytes_left, &ps);
             if (n == (size_t)-1 || n == (size_t)-2) {
                 /* Невалідна або обірвана послідовність:
                    рахуємо байт як 1 символ для стійкості, скидаємо стан */
                 char_count++;
                 p++;
                 bytes_left--;
                 memset(&ps, 0, sizeof(ps));
             } else if (n == 0) {
                 break; /* Термінальний '\0' */
             } else {
                 char_count++;
                 p += n;
                 bytes_left -= n;
             }
         }
         return char_count;
     }
     ```
3. **Стійкість до некоректних послідовностей (Encoding Error Resilience)**:
   - Якщо рядок містить випадкові бінарні дані, ізольовані continuation-байти (`0x80..0xBF`) чи обірвані UTF-8 послідовності (`0xF0 0x90`), POSIX-інтерпретатори **не викидають винятків і не аварійно зупиняють процес**.
   - Кожен нерозпізнаний байт інкрементує лічильник довжини на `1` і пропускається як одиничний символ. Це гарантує цілісність буферів під час обробки сирих бінарних файлів.
4. **Кодові точки Unicode (Code Points) проти графемних кластерів (Grapheme Clusters)**:
   - Оператор `${#var}` вимірює кількість **скалярних значень Unicode (Code Points)**, а не візуальних символів (Grapheme Clusters) чи ширини знакомісць термінала (`wcwidth(3)`).
   - **Комбіновані діакритичні знаки**: Рядок `"e\u0301"` (літера `e` `U+0065` + комбінований акут `U+0301`) візуально рендериться як один символ `é`, але `${#var}` повертає `2`. Натомість прекомпонований символ `"é"` (`U+00E9`) повертає довжину `1`.
   - **Складені емодзі та послідовності ZWJ**: Символ прапора або родини, сформований через Zero Width Joiner (`U+200D`), складається з кількох кодових точок (наприклад, 4 персони + 3 ZWJ = 7 кодових точок). Вираз `${#var}` повертає `7`.

#### 3.4.3. Багатобайтове зіставлення шаблонів та обрізання (`${var#pat}`, `${var%pat}`)

- **Посимвольне зіставлення**: Внутрішній модуль зіставлення glob-шаблонів (`strmatch()` у Bash) у багатобайтовій локалі транслює вхідні патерни та цільові рядки у послідовності `wchar_t`. Метасимвол `?` завжди відповідає **рівно одній багатобайтовій кодовій точці**, а не довільному байту.
- **Класи символів та локаль**: Вираз `${var#[[:lower:]]}` в українській локалі `uk_UA.UTF-8` коректно зіставляє всі літери від `а` до `я`, включаючи специфічні символи `є`, `і`, `ї`, `ґ`, спираючись на функцію `iswlower(3)`.
- **Діапазони `[a-z]` та `LC_COLLATE`**: Встановлення `LC_COLLATE=C` гарантує зіставлення за числовими кодами ASCII (`0x61..0x7A`). У деяких національних локалях порядок сортування (Collation Sequence) може включати великі літери або лігатури всередині діапазону `[a-z]`.

#### 3.4.4. Порівняльний аналіз архітектури кодувань

| Властивість кодування | UTF-8 | UTF-16 (BE/LE) | GB18030 | Shift-JIS (CP932) | ISO-8859-1 / C |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **Розмір символу (байти)** | 1, 2, 3 або 4 | 2 або 4 (сурогатні пари) | 1, 2 або 4 | 1 або 2 | Рівно 1 |
| **Сумісність з ASCII (0x00..0x7F)** | 100% сумісність | Несумісне (нуль-байти) | 100% сумісність | Сумісне (крім `0x5C`/`0x7E`)* | 100% сумісність |
| **Самосинхронізація (Self-Sync)** | **Так**: префікс байта визначає роль | **Ні** | **Так** | **Ні**: байт `0x5C` повторюється | Не застосовується |
| **Колізія з синтаксисом оболонки** | **Відсутня**: байти `0x00..0x7F` унікальні | Критична (містить нуль-байти `\0`) | **Відсутня** | **Критична**: суфіксний байт `0x5C` (`\`) | Відсутня |
| **Підтримка в POSIX Shell** | Повна стандартна | Не підтримується (руйнує C-рядки) | Повна в POSIX/Linux | Потребує `mbstate_t` парсера | Повна нативна |

#### 3.4.5. Пастка суфіксного байта `0x5C` у Shift-JIS (The 0x5C Hazard)

Японський стандарт Shift-JIS кодує ієрогліфи кандзі двома байтами: старший байт лежить у межах `0x81..0x9F` або `0xE0..0xFC`, а молодший (другий) байт — у діапазоні `0x40..0x7E` або `0x80..0xFC`.

- **Суть колізії**: Байт `0x5C` в ASCII відповідає символу зворотного слеша `\`, який в оболонці слугує символом екранування.
- Популярні кандзі містять байт `0x5C` як свою другу половину:
  - `表` (`0x95 0x5C`) — стіл, поверхня;
  - `能` (`0x93 0x5C`) — здатність;
  - `構` (`0x8D 0x5C`) — структура;
  - `十` (`0x8F 0x5C`) — десять.
- **Що відбувається при наївному побайтовому розборі**:
  Якщо операція обрізання або пошуку суфікса (наприклад, `${var%/*}` чи `${var#*\\}`) реалізована через побайтове сканування без використання багатобайтового декодера `mbrtowc`, другий байт ієрогліфа `0x5C` інтерпретується як символ зворотного слеша `\`.
  ```bash
  # У Shift-JIS середовищі:
  FILE="data_表.txt" # "data_\x95\x5C.txt"
  # Наївна заміна слеша замість екранування руйнує ієрогліф:
  CLEAN="${FILE//\\/_}" # Знищує другу половину кандзі '表', лишаючи байт 0x95!
  ```
- **Захисний механізм**: Повнофункціональні інтерпретатори (Bash з макросом `HANDLE_MULTIBYTE`, Zsh) виконують синхронізацію меж символів перед застосуванням операторів заміни та обрізання, гарантуючи, що байти всередині багатобайтової послідовності не розглядаються як метасимволи оболонки.

#### 3.4.6. Перетворення регістру `${var^^}` / `${var,,}` у багатобайтовому середовищі

Оператори трансформації регістру використовують системні функції `towupper(3)` та `towlower(3)`:

1. **Залежність від активної локалі `LC_CTYPE`**:
   - У локалі `C` / `POSIX`: модифікація застосовується **виключно** до латинських літер `a-z` (`0x61..0x7A`). Рядок кирилиці `TEXT="привіт"; echo "${TEXT^^}"` у локалі `C` залишиться незмінним `"привіт"`.
   - У локалі `uk_UA.UTF-8`: функція `towupper` коректно конвертує всі українські літери (`"привіт"` -> `"ПРИВІТ"`).
2. **Проблема турецької літери I (The Turkish-I Problem)**:
   - У більшості світових мов мала літера `i` (`U+0069`) переходить у велику `I` (`U+0049`).
   - У турецькій та азербайджанській локалях (`tr_TR.UTF-8`, `az_AZ.UTF-8`):
     - Мала `i` (`U+0069`) перетворюється на велику `İ` з крапкою (`U+0130`, в UTF-8: `\xC4\xB0`).
     - Мала `ı` без крапки (`U+0131`) перетворюється на велику `I` (`U+0049`).
   - **Системний ризик**: Якщо системний скрипт нормалізує імена мережевих протоколів чи команд:
     ```bash
     CMD="ping"
     EXEC_NAME="${CMD^^}" # У tr_TR.UTF-8 перетвориться на "PİNG" (з крапкою над I)!
     "$EXEC_NAME"         # Помилка: command not found: PİNG
     ```
   - **Інженерна вимога**: Усі системні скрипти, парсери конфігурацій та мережеві модулі, що виконують регістронезалежне зіставлення ASCII-протоколів, зобов'язані примусово виставляти `LC_ALL=C` або `LC_CTYPE=C`.
3. **Обмеження розміру буфера при зміні регістру (1-to-Many Mappings)**:
   - Окремі символи в Unicode при переведенні у верхній регістр розширюються у декілька літер: німецька мала літера `ß` (Eszett, `U+00DF`) за правилами граматики перетворюється на `SS`.
   - Оскільки стандартний C API `towupper(wint_t wc)` повертає рівно одне значення `wint_t`, вираз `${var^^}` у середовищі glibc повертає `'ß'` або велику `ẞ` (`U+1E9E`), зберігаючи розмір рядка в пам'яті без динамічної релокації буфера.

## 4. Зрізи підрядків та масивів (Substring Slicing)

Синтаксис зрізів доступний у Bash (2.0+), Ksh93 та Zsh. Індексація за замовчуванням ведеться від `0` (в Zsh — з `1`, якщо не увімкнено `KSH_ARRAYS`).

### 4.1. Специфікація форм зрізу

| Синтаксис | Опис семантики | Підтримка |
| :--- | :--- | :--- |
| `${var:offset}` | Підрядок від зміщення `offset` до кінця рядка. | Bash 2.0+, Ksh93, Zsh |
| `${var:offset:length}` | Підрядок довжиною `length` символів від зміщення `offset`. | Bash 2.0+, Ksh93, Zsh |
| `${var: -offset}` або `${var:(-offset)}` | Зріз з від'ємним зміщенням (відраховується від кінця рядка). Обов'язковий пробіл після першої двокрапки або круглі дужки! | Bash 2.0+, Ksh93, Zsh |
| `${var:offset:-drop}` | Підрядок від `offset`, з кінця якого відкинуто `drop` символів. | Bash 4.2+, Ksh93, Zsh |

### 4.2. Правила обчислення `offset` та `length`

1. **Арифметичний контекст**: Значення `offset` та `length` обчислюються як цілочисельні арифметичні вирази C-типу (аналогічно `$((...))`). У них дозволено використовувати змінні без знака `$`, тернарні оператори та арифметичні дії:
   ```bash
   START=2
   SIZE=4
   DATA="0123456789ABCDEF"
   echo "${DATA:START*2:SIZE+2}" # offset=4, length=6 -> "456789"
   ```
2. **Синтаксична колізія від'ємного зміщення**: Якщо написати `${var:-3}`, парсер розпізнає це як оператор дефолтного значення `${var:-word}` і поверне `"3"`, якщо `var` порожня. Щоб вказати від'ємний індекс, **обов'язково** ставити пробіл `${var: -3}` або брати вираз у дужки `${var:(-3)}`.
3. **Межі діапазонів (Out of Bounds)**:
   - Якщо `offset >= length(var)`, повертається порожній рядок `""`.
   - Якщо `offset < 0` і `|offset| > length(var)`, зміщення нормалізується або викликає помилку залежно від версії оболонки.
   - Якщо `length > (length(var) - offset)`, повертається залишок рядка від `offset` без помилки.
   - Якщо у Bash 4.2+ вказано від'ємний `length` (`:-drop`), і величина `drop` перевищує залишок довжини від `offset`, вираз обчислюється як помилковий або повертає `""`.

### 4.3. Зрізи над позиційними параметрами та масивами

```bash
# Зріз позиційних параметрів:
# ${@:offset:length}
# УВАГА: Якщо offset == 0, нульовим елементом виступає $0 (ім'я скрипта)!
echo "${@:1:3}"   # перші три позиційні параметри: $1 $2 $3
echo "${@: -2}"   # останні два позиційні параметри

# Зріз індексованого масиву:
declare -a NODES=("node-0" "node-1" "node-2" "node-3" "node-4")
SUB_NODES=("${NODES[@]:1:3}") # містить ("node-1" "node-2" "node-3")
```

## 5. Пошук і заміна за шаблоном (Pattern Substitution)

Оператори пошуку та заміни виконують зіставлення шаблону в рядку та модифікацію знайдених входжень. Підтримуються Bash (2.0+), Ksh93 та Zsh.

### 5.1. Реєстр операторів заміни

| Синтаксис | Режим заміни | Опис операції |
| :--- | :--- | :--- |
| `${var/pattern/string}` | First Match | Замінює **перший** знайдений збіг `pattern` на `string`. |
| `${var//pattern/string}` | Global Match | Замінює **всі** знайдені збіги `pattern` на `string`. |
| `${var/#pattern/string}` | Prefix Anchor | Замінює збіг, лише якщо він розташований на **початку** рядка (якір `^`). |
| `${var/%pattern/string}` | Suffix Anchor | Замінює збіг, лише якщо він розташований у **кінці** рядка (якір `$`). |
| `${var/pattern}` | First Deletion | Видаляє **перший** збіг `pattern` (заміна на порожній рядок). |
| `${var//pattern}` | Global Deletion | Видаляє **всі** збіги `pattern`. |

### 5.2. Правила екранування та захисту символів у `pattern`

1. **Прямий слеш `/`**: Оскільки `/` є роздільником між оператором, шаблоном та заміною, будь-який літеральний слеш усередині шаблону **мусить бути екранований** `\/`:
   ```bash
   PATH_VAL="/var/log/app/service.log"
   # Заміна всіх слешів на двокрапки:
   echo "${PATH_VAL//\//:}" # ":var:log:app:service.log"
   ```
2. **Якорі `#` та `%` як літерали**: Якщо шаблон починається з літерального символу `#` або `%`, його слід екранувати `\#` або `\%`, щоб парсер не сприйняв його як префіксний/суфіксний якір:
   ```bash
   TAG="#v1.0.0"
   echo "${TAG/\#v/ver-}" # "ver-1.0.0"
   ```
3. **Літеральний пошук за змінною**: Якщо змінна `$SEARCH` містить символи glob (`*`, `?`, `[`), для буквального пошуку її необхідно брати в подвійні лапки всередині фігурних дужок:
   ```bash
   DATA="cost is 100*200 total"
   PATTERN="100*200"
   # Без лапок '*' стане glob-маскою і зіставить "100*200 total":
   echo "${DATA/"$PATTERN"/20000}" # "cost is 20000 total"
   ```
4. **Поелементна заміна в масивах**:
   ```bash
   declare -a URLS=("http://srv1" "http://srv2" "https://srv3")
   SECURE_URLS=("${URLS[@]/#http:\/\//https:\/\/}")
   ```

## 6. Модифікація регістру символів (Case Modification)

Вбудовані оператори модифікації регістру підтримуються у GNU Bash (4.0+) та Zsh. Перетворення здійснюється безпосередньо в буфері пам'яті процесу згідно з системними правилами поточної локалі `LC_CTYPE` через бібліотечні виклики `towupper(3)` та `towlower(3)` (докладний аналіз багатобайтових особливостей, турецької крапкової I та 1-до-багатьох трансформацій див. у §3.4.6).

### 6.1. Специфікація операторів регістру

| Синтаксис | Операція | Опис семантики | Приклад виклику | Результат |
| :--- | :--- | :--- | :--- | :--- |
| `${var^^}` | Upper All | Усі символи рядка переводяться у верхній регістр | `v="srv"; echo "${v^^}"` | `SRV` |
| `${var,,}` | Lower All | Усі символи рядка переводяться у нижній регістр | `v="SRV"; echo "${v,,}"` | `srv` |
| `${var^}` | Upper First | Лише **перший** символ рядка переводиться у верхній регістр (капіталізація) | `v="host"; echo "${v^}"` | `Host` |
| `${var,}` | Lower First | Лише **перший** символ рядка переводиться у нижній регістр | `v="Host"; echo "${v,}"` | `host` |
| `${var^^pattern}` | Upper Matching | Переводить у верхній регістр лише ті символи, що відповідають `pattern` | `v="test"; echo "${v^^[et]}"` | `TEsT` |
| `${var,,pattern}` | Lower Matching | Переводить у нижній регістр лише ті символи, що відповідають `pattern` | `v="TEST"; echo "${v,,[ET]}"` | `tESt` |
| `${var~pattern}` | Toggle First | Інвертує регістр першого символу при збігу (Ksh93 / Bash 5.1+) | `v="Host"; echo "${v~}"` | `host` |
| `${var~~pattern}` | Toggle All | Інвертує регістр усіх символів (Ksh93 / Bash 5.1+) | `v="Host"; echo "${v~~}"` | `hOST` |

#### Застосування до масивів:
```bash
declare -a HEADERS=("content-type" "authorization" "x-request-id")
UPPER_HEADERS=("${HEADERS[@]^^}")
# UPPER_HEADERS містить ("CONTENT-TYPE" "AUTHORIZATION" "X-REQUEST-ID")
```

## 7. Оператори трансформації значень Bash 4.4+ та 5.x (`${var@op}`)

Синтаксис `${var@operator}` застосовує спеціальні внутрішні алгоритми серіалізації, екранування, інтроспекції та форматування значень.

### 7.1. Повна технічна специфікація операторів `@`

| Оператор | Назва операції | Контракт поведінки та специфікація формату | Мінімальна версія |
| :--- | :--- | :--- | :--- |
| `${var@Q}` | **Quoting for Re-evaluation** | Екранує рядок у безпечну форму для повторного парсингу командним інтерпретатором (огортає в `''` або `$''`). Запобігає Shell Injection під час генерації коду для `eval` або віддаленого SSH-виклику. | Bash 4.4+ |
| `${var@E}` | **Escape Sequence Expansion** | Розгортає керівні послідовності зворотного слеша (`\n`, `\t`, `\r`, `\xHH`, `\uHHHH`, `\e`) аналогічно до синтаксису рядкових літералів ANSI-C `$''`. | Bash 4.4+ |
| `${var@P}` | **Prompt String Evaluation** | Обчислює рядок як системний шаблон запрошення оболонки (розгортає метасимволи `PS1`: `\u` — user, `\h` — hostname, `\w` — cwd, `\t` — time, `\$` — uid marker, `\D{...}`). | Bash 4.4+ |
| `${var@A}` | **Assignment Statement** | Генерує повну команду оголошення змінної разом із її атрибутами та поточним значенням (еквівалент формату `declare -p var`). Придатна для збереження стану та серіалізації. | Bash 4.4+ |
| `${var@a}` | **Attribute Flags** | Повертає рядок прапорців атрибутів змінної: `a` (індексований масив), `A` (асоціативний масив), `i` (integer), `l` (lowercase), `u` (uppercase), `n` (nameref), `r` (readonly), `x` (export), `t` (trace). | Bash 4.4+ |
| `${var@k}` | **Key-Value Flattening** | Розгортає асоціативний або індексований масив у черговані слова: `ключ1 значення1 ключ2 значення2`. | Bash 5.1+ |
| `${var@K}` | **Quoted Key-Value Pairs** | Розгортає масив у черговані закватовані пари ключ-значення, безпечні для передачі в `eval` або повторного присвоєння. | Bash 5.1+ |
| `${var@U}` | **Transform Uppercase** | Переводить усі символи рядка у верхній регістр (ідентично `${var^^}`). | Bash 5.1+ |
| `${var@u}` | **Transform Capitalize** | Переводить перший символ рядка у верхній регістр (ідентично `${var^}`). | Bash 5.1+ |
| `${var@L}` | **Transform Lowercase** | Переводить усі символи рядка у нижній регістр (ідентично `${var,,}`). | Bash 5.1+ |

### 7.2. Детальна специфікація та механіка оператора інспекції атрибутів `${var@a}`

Оператор `${var@a}` здійснює пряме опитування бітового поля `attributes` структури `SHELL_VAR` у таблиці символів інтерпретатора і повертає рядок, сформований із символьних кодів прапорців.

#### Специфікація прапорців атрибутів у `${var@a}`

| Символ | Прапорець `declare` | Бітова маска (C) | Тип / Властивість | Вплив на операції запису та підстановки |
| :---: | :---: | :--- | :--- | :--- |
| `a` | `declare -a` | `att_array` (`0x04`) | Індексований масив | Доступ за числовим індексом `arr[0]`, розріджена структура. |
| `A` | `declare -A` | `att_assoc` (`0x40`) | Асоціативний масив | Доступ за рядковим ключем `arr["key"]`, внутрішня хеш-таблиця. |
| `i` | `declare -i` | `att_integer` (`0x08`) | Цілочисельний тип | Присвоєння автоматично обчислює арифметичний вираз через `evalexp()`. |
| `l` | `declare -l` | `att_lowercase` (`0x800`) | Автоматичний нижній регістр | Будь-який запис у змінну автоматично конвертується через `towlower(3)`. |
| `u` | `declare -u` | `att_uppercase` (`0x1000`) | Автоматичний верхній регістр | Будь-який запис у змінну автоматично конвертується через `towupper(3)`. |
| `n` | `declare -n` | `att_nameref` (`0x80`) | Посилання (Nameref) | Двосторонній псевдонім для цільової змінної. |
| `r` | `declare -r` / `readonly` | `att_readonly` (`0x02`) | Лише для читання | Заборона модифікації значення та оператора `unset`. Незворотний. |
| `x` | `declare -x` / `export` | `att_exported` (`0x01`) | Експорт у довкілля | Змінна включається в масив `envp[]` при системному виклику `execve(2)`. |
| `t` | `declare -t` | `att_trace` (`0x10`) | Трасування функцій | Успадкування пастки `DEBUG` функціями. |

#### Механіка взаємодії прапорців із підстановками та мутаціями пам'яті

1. **Прапорець `export` (`-x`, атрибут `x`)**:
   - При виставленні `declare -x VAR="data"` інтерпретатор маркує структуру бітом `att_exported`.
   - Якщо значення модифікується мутуючим оператором (наприклад, `${VAR:=fallback}` або `VAR="new"`), кешований рядок експорту `var->exportstr` інвалідується і звільняється з купи (`free(var->exportstr); var->exportstr = NULL`).
   - Перед наступним запуском дочірньої програми через `execve(2)` оболонка формує новий рядок `"VAR=new"` і передає його у векторі `envp[]`.
2. **Прапорець `integer` (`-i`, атрибут `i`)**:
   - Присвоєння змінній із прапорцем `i` перехоплюється внутрішнім обробником `bind_variable_value()`, який передає праву частину у синтаксичний аналізатор арифметичних виразів `evalexp()`:
     ```bash
     declare -i CALC
     CALC="10 + 5 * 2"  # CALC набуває значення "20" без синтаксису $((...))
     CALC="0x1F"        # CALC набуває значення "31" (шістнадцятковий розбір)
     CALC="8#70"        # CALC набуває значення "56" (вісімковий розбір)
     ```
   - Оператори умовного присвоєння `${CALC:=2**8}` записують канонічний десятковий рядок `"256"`.
   - Якщо присвоюваний рядок містить невалідний арифметичний вираз (наприклад, `CALC="abc"` при неоголошеній `abc`), вираз обчислюється як `0`.
3. **Прапорці регістру `lowercase` (`-l`, атрибут `l`) та `uppercase` (`-u`, атрибут `u`)**:
   - На відміну від одноразових операторів трансформації `${var,,}` та `${var^^}`, атрибути `l` та `u` діють постійно на всі наступні мутації змінної:
     ```bash
     declare -l PROTO="HTTPS"
     echo "$PROTO"       # "https"
     PROTO="FTP_TLS"
     echo "$PROTO"       # "ftp_tls" (автоматична нормалізація при кожному записі)
     ```
   - При спробі одночасного встановлення `declare -l -u VAR` активним стає останній вказаний прапорець, оскільки внутрішній алгоритм знімає біт `att_lowercase` при встановленні `att_uppercase`.
4. **Прапорець `nameref` (`-n`, атрибут `n`)**:
   - Змінна-посилання зберігає ім'я цільової змінної у своєму рядковому буфері `var->value`.
   - **Особливість інтроспекції**: У Bash 4.4+ оператор `${ref@a}` повертає атрибути **цільової змінної**, на яку вказує посилання, а не самого `ref`:
     ```bash
     declare -i TARGET_VAL=42
     declare -n REF=TARGET_VAL
     echo "${REF@a}"     # Виведе "i" (атрибут TARGET_VAL), а не "n"!
     ```
   - Для безпосередньої перевірки прапорця `n` у самого посилання використовується `declare -p REF` або конструкція `[[ "${!REF@a}" == *"n"* ]]`.
5. **Прапорець `readonly` (`-r`, атрибут `r`)**:
   - Біт `att_readonly` не може бути скинутий командою `declare +r` (повертає помилку `cannot be unset: readonly variable`).
   - Будь-яка спроба мутації через `${RO_VAR:=val}` негайно перериває неінтерактивний сценарій.
6. **Множинні комбінації атрибутів (Bitmask Combinations)**:
   - Атрибути комбінуються в одному бітовому полі. Наприклад:
     ```bash
     declare -ilrx SYS_LIMIT=1024
     echo "${SYS_LIMIT@a}" # Повертає "ilrx" (integer + lowercase + readonly + export)
     ```
   - Порядок символів у рядку виводу `${var@a}` є детермінованим і відповідає порядку бітових прапорців у вихідному коді Bash: `a`, `A`, `i`, `l`, `n`, `r`, `t`, `u`, `x`.

## 8. Непряма адресація, Namerefs та інтроспекція простору імен

### 8.1. Специфікація непрямого розгортання та Nameref

| Конструкція | Механізм | Опис і контракт | Підтримка |
| :--- | :--- | :--- | :--- |
| `${!var}` | **Indirect Expansion** | Значення `var` інтерпретується як ім'я цільової змінної. Якщо `target="PORT"` і `PORT=9000`, вираз `${!target}` повертає `9000`. | Bash 2.0+, Ksh93, Zsh (`${(P)var}`) |
| `declare -n ref=target` | **Name Reference (Nameref)** | Створює двосторонній псевдонім `ref` для `target`. Будь-яке читання чи запис у `ref` безпосередньо мутує `target`. | Bash 4.3+, Ksh93 (`typeset -n`) |
| `${!prefix*}` | **Prefix Matching (Joined)** | Розгортається в імена всіх існуючих змінних, що починаються з `prefix`, об'єднані через `$IFS[0]` (при взятті в лапки `"${!prefix*}"`). | Bash 3.0+, Ksh93 |
| `${!prefix@}` | **Prefix Matching (Words)** | Розгортається в імена всіх змінних з префіксом `prefix` як окремі закватовані слова (при взятті в лапки `"${!prefix@}"`). | Bash 3.0+, Ksh93 |
| `${!array[@]}` / `"${!array[*]}"` | **Array Keys / Indices** | Повертає список усіх числових індексів (для `declare -a`) або рядкових ключів (для `declare -A`). | Bash 3.0+, Ksh93, Zsh (`${(k)array}`) |

### 8.2. Інтроспекція ключів та розріджені масиви (Sparse Arrays)

Індексовані масиви в Bash є розрідженими (sparse): неініціалізовані елементи не займають пам'ять. Конструкція `${!array[@]}` повертає виключно існуючі індекси:

### 8.3. Пастки та безпека Namerefs

1. **Циклічні посилання**: Спроба прив'язати `declare -n ref=ref` або ланцюжок `a -> b -> a` породжує попередження середовища `warning: ref: circular name reference` і повертає порожній результат.
2. **Колізія локальних змінних функцій (Self-Shadowing)**: Якщо функція оголошує `local -n out_var="$1"`, а викликається з іменем змінної, яке збігається з іменем nameref (`out_var`), функція створює локальне циклічне посилання на саму себе замість змінної вищого скоупу.
   ```bash
   # ПРАВИЛЬНИЙ ПІДХІД: унікальний системний префікс для локальних nameref
   set_value() {
       local -n __set_value_dest_ref="$1"
       __set_value_dest_ref="SUCCESS"
   }
   ```

### 8.4. Механіка векторного розкриття масивів та позиційних параметрів

Маніпуляція масивами (`declare -a`, `declare -A`) та позиційними параметрами (`$1..$N`) підпорядковується фундаментальній різниці між скалярним склеюванням (`*`) та збереженням векторних меж слів (`@`).

#### Специфікація форм `"${arr[*]}"` проти `"${arr[@]}"`

| Форма виклику | Контекст лапок | Семантика генерації слів | Роль роздільника `IFS` | Кількість слів при 3 елементах | Поведінка при порожньому масиві (`N=0`) |
| :--- | :--- | :--- | :--- | :---: | :---: |
| `"${arr[*]}"` | Подвійні лапки | **Склеювання в одне слово** (Joined Scalar) | Елементи об'єднуються через перший символ змінної `$IFS` (`IFS[0]`). | **1 слово** | Порожній рядок `""` (1 слово довжини 0) |
| `"${arr[@]}"` | Подвійні лапки | **Векторне розкриття слів** (Word Vector) | `IFS` ігнорується. Кожен елемент стає **окремим аргументом** `argv[i]`. | **3 слова** | **0 слів** (жоден аргумент не передається) |
| `${arr[*]}` | Без лапок | Склеювання + поділ на слова + Globbing | Рядок розбивається на нові слова за всіма символами `IFS`. | Залежить від вмісту | 0 слів |
| `${arr[@]}` | Без лапок | Вектор + поділ на слова + Globbing | Кожен елемент додатково розбивається за всіма символами `IFS`. | Залежить від вмісту | 0 слів |

#### Механізм об'єднання через `IFS[0]` у `"${arr[*]}"`

1. **Якщо `IFS` встановлено**: використовується виключно **перший байт** значення `IFS`. Решта символів у `IFS` ігноруються при склеюванні.
   ```bash
   declare -a IPS=("192.168.1.1" "10.0.0.1" "172.16.0.1")
   IFS=";,\t"
   echo "${IPS[*]}" # "192.168.1.1;10.0.0.1;172.16.0.1" (використано лише ';')
   ```
2. **Якщо `IFS` не встановлено (`unset IFS`)**: інтерпретатор використовує за замовчуванням стандартний пробіл ASCII (`0x20`).
3. **Якщо `IFS` встановлено як порожній рядок (`IFS=""`)**: елементи зливаються без жодного проміжного роздільника (`"192.168.1.110.0.0.1172.16.0.1"`).

#### Збереження меж аргументів у `"${arr[@]}"`

Форма `"${arr[@]}"` (як і `"$@"`) є єдиним стандартизованим механізмом передачі списку аргументів без втрати вбудованих пробілів, табуляцій, символів нового рядка `\n` чи небажаного розкриття glob-масок:

```bash
declare -a FILES=("config file.json" "data\nwith\nnewlines.txt" "*.log")

# Кожен елемент передається у команду суворо як окремий аргумент argv:
process_batch "${FILES[@]}"
# argv[1] = "config file.json"
# argv[2] = "data\nwith\nnewlines.txt"
# argv[3] = "*.log" (не розкривається у список файлів файлової системи)
```

#### Робота з порожніми масивами, розрідженими індексами та `set -u`

1. **Порожній масив у циклі `for`**: конструкція `for item in "${EMPTY[@]}"` не породжує жодного слова, тому тіло циклу не виконується **жодного разу**. Натомість `for item in "${EMPTY[*]}"` завжди дає рівно одне слово — порожній рядок, — тому цикл робить **одну зайву ітерацію** зі значенням `item=""`.
2. **Внутрішня організація розріджених індексів (Sparse Arrays)**:
   У GNU Bash індексований масив зберігається як зв'язний список або деревоподібна структура `ARRAY_ELEMENT`:
   ```text
   [ARRAY struct]
      │
      ├─► [ARRAY_ELEMENT: ind=0,   value="first"]
      ├─► [ARRAY_ELEMENT: ind=42,  value="middle"]
      └─► [ARRAY_ELEMENT: ind=999, value="last"]
   ```
   Проміжні неініціалізовані індекси (`1..41`, `43..998`) не займають пам'ять і не створюють вузлів у купі. При виконанні `"${arr[@]}"` внутрішній ітератор `array_walk()` проходить виключно по існуючих вузлах у порядку зростання числових індексів, генеруючи рівно 3 аргументи.
3. **Захисна ідіома для сумісності з `set -u` (Bash < 4.4)**:
   В історичних версіях GNU Bash (до 4.4) звернення до порожнього масиву `"${arr[@]}"` при увімкненому прапорці `set -u` призводило до фатальної помилки `arr: unbound variable`. Для кросплатформної сумісності використовується захисна форма умовного розкриття:
   ```bash
   # Якщо arr оголошено (навіть порожній), розгортає "${arr[@]}", інакше нічого не генерує:
   cmd "${arr[@]+"${arr[@]}"}"
   ```

### 8.5. Системні оптимізації, локальні змінні та запобігання переповненню стеку інтерпретатора (Recursion Stack & Nameref Safety)

Використання рекурсивних функцій оболонки у поєднанні з локальними змінними (`local`, `typeset`) та непрямими посиланнями (`declare -n`) створює значне навантаження на підсистему керування пам'яттю інтерпретатора.

#### 8.5.1. Модель пам'яті C-стека проти динамічного контексту `VAR_CONTEXT` у купі

При виклику будь-якої користувацької функції інтерпретатор GNU Bash проходить внутрішній шлях виконання `execute_command()` ──► `execute_function()` (`execute_cmd.c`):

1. **Споживання C-стека процесу**:
   - Кожен рівень виклику функції виділяє новий стек-фрейм мови C у просторі пам'яті потоку процесу.
   - Фрейм містить локальні змінні ядра, покажчики на абстрактне синтаксичне дерево (`COMMAND*`), списки розгорнутих слів (`WORD_LIST*`) та структури середовища.
   - Розмір одного C-фрейму виклику становить від 1 до 2 КБ пам'яті.
2. **Споживання купи (Heap) для таблиці символів**:
   - Оголошення локальних змінних через `local` викликає функцію `push_var_context()`, яка виділяє у купі дескриптор `VAR_CONTEXT` та локальну хеш-таблицю `HASH_TABLE`.
   - Змінні та їхні рядкові значення алокуються окремими блоками через `xmalloc(3)`.
3. **Анатомія переповнення стека (`SIGSEGV` та `ulimit -s`)**:
   - За замовчуванням у дистрибутивах Linux ліміт розміру стека процесу (`ulimit -s`) встановлено у `8192 KiB` (8 МБ).
   - Інтерпретатор Bash **не підтримує оптимізацію хвостової рекурсії (Tail Call Optimization / TCO)**. Будь-яка рекурсивна функція утримує весь ланцюг фреймів виклику C аж до базового випадку.
   - Досягнення глибини рекурсії у 4 000–8 000 викликів неминуче вичерпує виділений стек ядра і призводить до фатального аварійного завершення процесу із сигналом `SIGSEGV` (Segmentation fault), навіть якщо вільна оперативна пам'ять системи (RAM) вимірюється гігабайтами.

#### 8.5.2. Алгоритм розв'язання ланцюжків Namerefs та ліміт глибини `MAX_NAMEREF_DEPTH`

Розв'язання непрямих посилань здійснюється внутрішньою функцією `find_variable_nameref()` (`variables.c`):

```text
SHELL_VAR *find_variable_nameref(SHELL_VAR *var) {
    int depth = 0;
    while (var && (var->attributes & att_nameref)) {
        if (depth++ > MAX_NAMEREF_DEPTH) {
            internal_warning("%s: circular name reference", var->name);
            return ((SHELL_VAR *)NULL);
        }
        if (var->value == 0 || *var->value == '\0')
            return ((SHELL_VAR *)NULL);
        var = find_variable(var->value);
    }
    return var;
}
```

- **Захисний ліміт**: Константа `MAX_NAMEREF_DEPTH = 100` запобігає зависанню інтерпретатора у нескінченному циклі пошуку при виявленні циклічних залежностей (`declare -n a=b; declare -n b=a`).
- **Складність пошуку**: Розв'язання ланцюжка посилань довжиною `K` вимагає `K` послідовних пошуків у хеш-таблицях стека контекстів, що має складність `O(K × D)`, де `D` — глибина стека контекстів виклику.

#### 8.5.3. Пастка динамічного затінення (Dynamic Scope Variable Capture Hazard)

У моделі динамічної видимості пошук змінної `find_variable()` завжди починається з найглибшого локального контексту `current_var_context` і рухається вгору за покажчиками `context->up`.

- **Суть колізії**: Якщо функція створює локальний nameref `local -n ref="$1"`, а ім'я цільової змінної, передане викликачем, збігається з іменем локальної змінної, оголошеної у цій самій функції (або у проміжній функції в ланцюжку викликів), посилання **захоплює локальну змінну** замість очікуваної зовнішньої. Тимчасова змінна проміжної функції з «природною» короткою назвою (`count`, `value`, `line`) перехоплює запис, а викликач бачить свою змінну незмінною.
- **Інженерне правило захисту**: Для запобігання випадковому затіненню всі локальні змінні-посилання та тимчасові змінні у бібліотечних функціях повинні мати префікс з унікальним простором імен (наприклад, `local -n __fn_target_ref="$1"`).
- **Пряме читання через непряму адресацію**: Якщо функція потребує лише читання даних без модифікації, замість `declare -n` використовується вираз прямої непрямої підстановки `${!param_name}`, що повністю виключає ризик циклічних посилань або помилкової мутації таблиці символів.

#### 8.5.4. Трансформація рекурсивних функцій в ітеративні алгоритми на базі Parameter Expansion

Оператори обрізання та зрізів (`${var#*.}`, `${var%/*}`, `${var:off:len}`) дозволяють замінити будь-які рекурсивні парсери (розбір шляхів, токенізація списків, розбір JSON/логів) на високоефективні ітеративні цикли.

| Критерій оцінки | Рекурсивний підхід | Ітеративний підхід на Parameter Expansion |
| :--- | :---: | :---: |
| **Глибина C-стека** | `O(N)` (1–2 КБ на виклик) | **`O(1)` (рівно 1 фрейм)** |
| **Використання купи (Heap)** | `N` дескрипторів `VAR_CONTEXT` та таблиць | **`O(1)` (один фіксований буфер)** |
| **Ризик `SIGSEGV` (Stack Overflow)** | **Критичний** при `N > 4000` | **Повністю відсутній** |
| **Швидкодія на 10 000 елементів** | 2.40 с (з високим GC overhead) | **0.03 с (~80x прискорення)** |

#### 8.5.5. Керування пам'яттю та деалокація фреймів у глибоких викликах

Під час повернення з функції ядро інтерпретатора виконує детерміноване очищення ресурсів:
1. Функція `pop_var_context()` ітерує всі елементи локальної `HASH_TABLE`, звільняє пам'ять виділених рядкових значень (`free(var->value)`), деалокує масив кошиків таблиці та звільняє дескриптор `VAR_CONTEXT`.
2. Тимчасові структури списків слів `WORD_LIST*`, згенеровані операціями підстановки, знищуються викликом `dispose_words()` одразу після завершення поточної інструкції AST. Це забезпечує стабільний розмір Resident Set Size (RSS) процесу оболонки під час тривалої роботи в режимі демона.

## 11. Аналіз складності та системні витрати

### 11.1. Асимптотична складність операцій у пам'яті

Нехай `N` — довжина вхідного рядка у байтах, `M` — довжина шаблону пошуку, `K` — довжина результуючого зрізу.

| Операція | Синтаксис | Часова складність | Додаткова пам'ять (Heap Allocation) |
| :--- | :--- | :---: | :---: |
| Читання змінної | `$var`, `${var}` | `O(1)` | `0` (покажчик на існуючий буфер) |
| Довжина рядка (C-локаль) | `${#var}` | `O(1)` або `O(N)` | `0` |
| Довжина рядка (UTF-8) | `${#var}` | `O(N)` | `0` |
| Зріз підрядка | `${var:off:len}` | `O(K)` | `O(K)` |
| Обрізання префікса/суфікса (літерал) | `${var#str}`, `${var%str}` | `O(M)` | `O(N - M)` |

| Екранування `@Q` | `${var@Q}` | `O(N)` | `O(N)` (до 4x при екрануванні) |

### 11.3. Анатомія накладних витрат ядра: чому зовнішні утиліти програють у циклах

Колосальний розрив у продуктивності зумовлений системними накладними витратами на рівні ядра операційної системи при виконанні конструкцій виду `$(cmd)` або `echo "$str" | util`:

```text
[Виклик $(echo "$str" | sed 's/foo/bar/g') на 1 ітерацію]
 |-- 1. clone(2)/fork(2) x2 -> Створення 2 процесів (subshell + sed)
 |-- 2. pipe(2)             -> Виділення анонімного каналу IPC (64 KB кільцевий буфер)
 |-- 3. dup2(2) x4          -> Перенаправлення stdout/stdin між процесами
 |-- 4. execve(2)           -> Пошук у $PATH, парсинг ELF, mmap бінарника
 |-- 5. ld-linux.so.2       -> Динамічне завантаження libc.so, релокація GOT/PLT
 |-- 6. write(2) / read(2)  -> Копіювання рядка в буфер ядра та назад у user-space
 |-- 7. Context Switches    -> Перемикання контексту CPU (Ring 3 <-> Ring 0)
 |-- 8. exit_group(2) x2    -> Звільнення VMA та дескрипторів
 \-- 9. wait4(2) x2         -> Обробка сигналів SIGCHLD батьківським процесом
```

#### Повний ланцюг системних операцій ядра:

1. **Створення структур процесу (`clone(2)` / `fork(2)`)**:
   Ядро виділяє в просторі ядра дескриптор процесу `task_struct`, стек ядра та структуру обліку ресурсів `thread_info`. Створюється копія структури віртуальної пам'яті `mm_struct`, а всі записи таблиці сторінок віртуальної пам'яті (Page Table Entries) маркуються як Copy-On-Write (COW). Процесу виділяється новий PID у таблиці процесів, що супроводжується блокуванням списків планувальника завдань.
2. **Завантаження бінарного файлу та динамічне компонування (`execve(2)`)**:
   Ядро ітерує шляхи зі змінної `$PATH` через виклики `openat(2)` / `newfstatat(2)`. Завантажувач ELF (`fs/binfmt_elf.c`) парсить заголовок виконуваного файлу, перевіряє магічні байти та відображає сегменти пам'яті (`.text`, `.rodata`, `.data`, `.bss`) через системний виклик `mmap(2)`. Керування передається динамічному компонувальнику `ld-linux-x86-64.so.2`, який парсить секцію `.dynamic`, завантажує залежні бібліотеки (`libc.so.6`), налаштовує таблиці глобальних зміщень (GOT) та процедурних переходів (PLT) і ініціалізує локальну пам'ять потоку (TLS).
3. **Міжпроцесна комунікація та буферизація (`pipe(2)`)**:
   Створюється пара дескрипторів анонімного каналу з виділенням кільцевого буфера в пам'яті ядра (за замовчуванням 64 КБ). Передача даних між процесами супроводжується системними викликами `write(2)` та `read(2)`, що змушує процесор виконувати інструкції `SYSCALL`/`SYSRET` для переходу між Ring 3 (User Space) та Ring 0 (Kernel Space), призводячи до скидання конвеєра інструкцій та кешу трансляції адрес (TLB).
4. **Завершення процесу та збирання стану (`exit_group(2)` / `wait4(2)`)**:
   Після завершення роботи утиліта викликає `exit_group(2)`. Ядро звільняє структури пам'яті процесу (`exit_mmap`), закриває файлові дескриптори та переводить дескриптор у стан `EXIT_ZOMBIE`, надсилаючи сигнал `SIGCHLD` батьківській оболонці. Батьківський процес виходить зі стану сну, обробляє сигнал і викликає `wait4(2)` для отримання коду завершення та статистики `rusage`.

#### Механізм роботи підстановки в пам'яті процесу (In-Memory Expansion):

- **Локальність кешу процесора (L1/L2 Cache Locality)**: Усі рядки змінних уже розміщені в купі (heap) поточного процесу оболонки. Буфери обробки розміром у кілька десятків чи сотень байтів гарантовано поміщаються в L1-кеш даних процесора (зазвичай 32–48 КБ на ядро), що забезпечує доступ до пам'яті з латентністю ~4 такти CPU (менше 1 наносекунди).
- **Пряма вказівникова арифметика**: Оператори підстановки реалізовані мовою C через прямі виклики швидких функцій сканування та копіювання пам'яті (`strchr`, `memchr`, `memcpy`, `memmove`). Обрізання суфікса `${path%/*}` зводиться до одного виклику пошуку останнього входження байта `strrchr(path, '/')` та запису нуль-байта `\0`.
- **Нульові витрати ядра**: Кількість системних викликів до ядра дорівнює **0**, кількість перемикань контексту — **0**, кількість звернень до файлової системи — **0**.

### 11.4. Профіль пам'яті: C-стек проти локальних фреймів купи у рекурсивних викликах

Внутрішня архітектура виконання функцій у POSIX-оболонках розмежовує системний C-стек процесу та динамічні структури `VAR_CONTEXT` у купі:

```text
[Виклик рекурсивної функції глибиною N = 5000]
 ├── C-стек процесу (фіксований ліміт ulimit -s = 8192 KiB):
 │    ├── Frame 0: execute_function() -> 1.5 KiB
 │    ├── Frame 1: execute_function() -> 1.5 KiB
 │    │   ...
 │    └── Frame 5000 -> СУМАРНО: 7.5 MiB ──► ПЕРЕПОВНЕННЯ СТЕКА -> SIGSEGV (Crash)
 │
 └── Купа (Heap) процесу:
      ├── VAR_CONTEXT 0 -> HASH_TABLE { local x, local y }
      ├── VAR_CONTEXT 1 -> HASH_TABLE { local x, local y }
      │   ...
      └── VAR_CONTEXT 5000 -> 5000 х 512 байтів = 2.5 MiB (RAM вільна, але процес падає через C-стек)
```

1. **Відсутність TCO (Tail Call Optimization)**:
   На відміну від інтерпретаторів компільованих мов, Bash та Dash не замінюють поточний фрейм стека при хвостовому виклику `return func "$@"`. Кожен рекурсивний крок зберігає повний стан C-функцій `execute_cmd.c`.
2. **Перевага операторів Parameter Expansion в ітераціях**:
   Заміна рекурсивного розбору на ітеративний цикл із виразами `${stream#*delim}` та `${stream%delim*}` утримує споживання C-стека на рівні константи `O(1)` (1 фрейм ~1.5 КБ) і не створює нових вузлів `VAR_CONTEXT` у купі, дозволяючи обробляти необмежені обсяги даних без ризику деградації пам'яті чи падіння середовища.

## 12. Каталог типових помилок, синтаксичних пасток та вразливостей

### Пастка 1: Колізія від'ємного зміщення з оператором дефолтного значення
- **Симптом**: `${var:-5}` повертає `"5"` замість останніх 5 символів рядка.
- **Причина**: Парсер інтерпретує комбінацію `:-` як перевірку дефолтного значення.
- **Виправлення**: Додавати пробіл `${var: -5}` або брати від'ємне число в круглі дужки `${var:(-5)}`.

### Пастка 2: Поділ на слова (Word Splitting) через відсутність подвійних лапок
- **Симптом**: `TARGET=${path%/*}` при наявності пробілів у шляху розбиває результат на декілька аргументів у подальших командах (`rm $TARGET`).
- **Причина**: Нелапковані результати підстановки проходять фазу Word Splitting (фаза 5 конвеєра).
- **Виправлення**: Завжди огортати підстановки у подвійні лапки: `TARGET="${path%/*}"`.

### Пастка 3: Ненавмисне розкриття Glob-масок у виразах пошуку та заміни
- **Симптом**: Якщо змінна пошуку містить зірочку `PATTERN="*"`, вираз `${DATA/$PATTERN/REPL}` замінює весь рядок від початку до кінця.
- **Причина**: Значення незахищеної змінної в полі шаблону інтерпретується як Shell Globbing маска.
- **Виправлення**: Огортати змінну шаблону в лапки: `${DATA/"$PATTERN"/REPL}`.

### Пастка 4: Спроба мутації позиційних параметрів оператором `:=`
- **Симптом**: Скрипт аварійно завершується з помилкою `bash: 1: cannot assign to positional parameter`.
- **Причина**: Позиційні параметри `$1..$N` є read-only вказівниками на вектор `argv` поточного фрейму.
- **Виправлення**: Використовувати умовне читання без мутації: `ARG1="${1:-default_value}"`.

### Пастка 5: Плутанина між `"${array[*]}"` та `"${array[@]}"`
- **Симптом**: Цикл `for item in "${array[*]}"; do` виконується лише один раз, отримуючи всі елементи, злиті в один рядок через `$IFS[0]`.
- **Причина**: Форма `*` виконує склеювання вектора, тоді як `@` зберігає межі кожного слова.
- **Виправлення**: Завжди використовувати `"${array[@]}"` для ітерацій по масиву.

### Пастка 6: Вразливість Shell Injection при динамічній генерації коду
- **Симптом**: Користувацький ввід `input="test; rm -rf /"` виконує деструктивну команду при передачі в `eval "cmd $input"`.
- **Причина**: Небезпечна конкатенація рядків без захисного екранування метасимволів.
- **Виправлення**: Використовувати оператор екранування `${input@Q}`: `eval "cmd ${input@Q}"`.

### Пастка 7: Порожні масиви під `set -u` у застарілих версіях Bash (< 4.4)
- **Симптом**: Вираз `"${empty_arr[@]}"` викликає фатальну зупинку `empty_arr: unbound variable`.
- **Причина**: Історичний дефект парсера Bash до версії 4.4.
- **Виправлення**: Використовувати захисну форму `"${empty_arr[@]+"${empty_arr[@]}"}"` для максимальної переносимості.

### Пастка 8: Колізія другого байта `0x5C` у кодуванні Shift-JIS
- **Симптом**: При спробі видалити зворотний слеш або обрізати суфікс `${var%/*}` у японському тексті руйнуються символи кандзі (наприклад, `表` перетворюється на невалідний байт `0x95`).
- **Причина**: Другий байт у кодуванні Shift-JIS збігається з ASCII-кодом зворотного слеша `\x5C`, який наївний побайтовий парсер сприймає як символ екранування.
- **Виправлення**: Використовувати UTF-8 локаль (`LC_ALL=C.UTF-8` або `ja_JP.UTF-8`) або перевіряти підтримку багатобайтової обробки `HANDLE_MULTIBYTE`.

### Пастка 9: Захоплення локальних змінних (Variable Capture) при передачі Nameref
- **Симптом**: Функція з `local -n ref="$1"` мутує не змінну викликача, а власну локальну змінну або викликає попередження `warning: circular name reference`.
- **Причина**: Модель динамічної видимості (Dynamic Scoping) розв'язує імена, починаючи з найглибшого локального фрейму, захоплюючи однойменну локальну змінну.
- **Виправлення**: Додавати системний префікс до імен локальних посилань: `local -n __fn_output_ref="$1"`.

### Пастка 10: Переповнення C-стека інтерпретатора (`SIGSEGV`) при глибокій рекурсії
- **Симптом**: Рекурсивна функція обробки списків або файлових дерев аварійно завершується без повідомлення про помилку або з `Segmentation fault` при досягненні 4 000+ елементів.
- **Причина**: Вичерпання ліміту пам'яті стека ядра (`ulimit -s`) через відсутність Tail Call Optimization.
- **Виправлення**: Переписувати алгоритми на ітеративні цикли `while [[ -n "$str" ]]` з використанням операторів `${str#*delim}` та `shift`.
