# ⚙️ Лабораторія зомбі: зробити, обстріляти, розібрати

Тут повний код невеликої програми на C, яка робить зомбі на твоїй машині й дає його помацати: вистрілити в нього `SIGKILL` упритул і побачити, що виклик удався, а не сталося нічого; прочитати, що саме лишилося від процесу в `/proc`, а що звідти вже зникло; змусити п'ять смертей злитися в один `SIGCHLD`; і безпечно виміряти, скільки зомбі витримає система, не зачепивши при цьому нікого, крім самої лабораторії.

Усе, що описують словами про зомбі, у цій програмі стає рядком виведення, який видно на своїй машині за півсекунди.

## Умова

Лабораторія має показати чотири речі, і кожну — не переказом, а числом чи буквою на екрані:

- зомбі з'являється **в мить виходу дитини**, а не тоді, коли хтось про нього дізнався;
- `kill -9` на зомбі повертає успіх і не робить нічого — і те, й те одночасно;
- у `/proc` лишається запис, у якому одні файли порожні, інших полів немає взагалі, а лічильники часу є;
- кілька смертей поспіль дають **менше** сигналів, ніж смертей.

Понад це — одна вимога до самої лабораторії: жоден її дослід не сміє нашкодити машині, на якій його запускають. Дослід «наробити зомбі, доки система не почне задихатися» звучить повчально рівно доти, доки не спробуєш його на робочому ноутбуці; нижче він зроблений так, що впирається у **власну** огорожу, а не в чужу.

## Ідея: спостерігач і піддослідні в одній програмі

Спокуса зробити лабораторію з двох терміналів — в одному програма, в другому `ps` і `cat` — велика, але хибна. Річ у тім, що **дивитися на зомбі має право не будь-хто, а той, хто впевнений у тотожності номера**. Доки номер тримає наш власний непохований зомбі, він гарантовано наш; щойно ми його прибрали, те саме число система вільна віддати комусь іншому, і `cat /proc/<номер>/stat`, набраний у другому терміналі на секунду пізніше, покаже вже сторонню програму.

Тому спостерігач тут — сам батько. Він народжує піддослідних, чекає, доки вони стануть зомбі, читає їхні записи в `/proc`, стріляє в них і тільки наприкінці кличе `wait`. Усе відбувається у вікні, де номер належить нам, а отже, всі спостереження стосуються саме тієї дитини, яку ми зробили.

Мова тут не обирається: `fork`, `waitpid`, `sigprocmask`, `setrlimit` — це системні виклики, і природний спосіб їх покликати один. Файл нижче збирається цілком, кожен шматок іде в нього по порядку.

## Помічники: читати `/proc` і дочекатися стану Z

Уся лабораторія тримається на одному питанні до системи: «у якому стані зараз ця задача?» Відповідь лежить у `/proc/<pid>/stat` третім полем ([/proc: процеси як файли](root:sys-unix/proc-reading-process-and-kernel-state) — каталог на кожен процес, у якому файли не лежать на диску, а формуються ядром у мить читання).

```c
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/resource.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

/* Прочитати невеликий файл цілком. Повертає кількість байтів або −1. */
static ssize_t slurp(const char *path, char *buf, size_t cap)
{
    int fd = open(path, O_RDONLY | O_CLOEXEC);
    if (fd < 0) return -1;
    ssize_t n = read(fd, buf, cap - 1);
    close(fd);
    if (n < 0) return -1;
    buf[n] = '\0';
    return n;
}

/* Стан задачі: 'R', 'S', 'Z'… або 0, якщо запису в /proc уже немає. */
static char proc_state(pid_t pid)
{
    char path[64], buf[512];
    snprintf(path, sizeof path, "/proc/%d/stat", (int)pid);
    if (slurp(path, buf, sizeof buf) < 0) return 0;

    char *p = strrchr(buf, ')');   /* ім'я команди може містити і пробіли, і дужки */
    if (!p) return 0;
    return p[2];                   /* "…) Z 51233 …" — за дужкою пробіл, далі стан */
}

static void sleep_ms(long ms)
{
    struct timespec ts = { ms / 1000, (ms % 1000) * 1000000L };
    nanosleep(&ts, NULL);           /* може обірватися сигналом — тут це не шкодить */
}

/* Чекати, доки дитина не стане зомбі. Безпечно рівно тому, що ми — її батько
   і ще не кликали wait: номер нікуди не подінеться. */
static void wait_until_zombie(pid_t pid)
{
    while (proc_state(pid) != 'Z')
        sleep_ms(1);
}
```

Рядок із `strrchr` — не примха. Перше поле `stat` — номер, друге — ім'я команди **в дужках**, і ядро друкує його як є: якщо програма називається `my prog (test)`, у файлі опиниться `1234 (my prog (test)) Z 1200 …`. Розбір пробілами по порядку на такому рядку зсувається й дає сміття, тому єдиний правильний спосіб — знайти **останню** дужку й читати від неї. Ця пастка коштувала помилок не одному моніторингові.

Чекання циклом по мілісекунді виглядає грубо, але воно тут краще за будь-який `sleep(1)`: дослід стає **детермінованим**. Ми не сподіваємося, що дитина «напевно вже встигла», а точно знаємо, що вона вже зомбі.

## Крок 1. Зробити зомбі й вистрілити в нього

```c
static void proc_report(pid_t pid);   /* тіло — нижче */

static int lab_one(void)
{
    pid_t child = fork();
    if (child < 0) { perror("fork"); return 1; }
    if (child == 0)
        _exit(3);            /* саме _exit: буфери stdio успадковані, вони батькові */

    wait_until_zombie(child);
    printf("дитина %d: стан %c\n", (int)child, proc_state(child));

    if (kill(child, SIGKILL) == 0)
        printf("kill(SIGKILL) повернув 0 — стан лишився %c\n", proc_state(child));
    if (kill(child, 0) == 0)
        printf("kill(pid, 0) повернув 0 — номер зайнятий, права є\n");

    proc_report(child);

    int status = 0;
    pid_t got = waitpid(child, &status, 0);
    printf("waitpid → %d, вийшла сама: %d, код %d\n",
           (int)got, WIFEXITED(status), WEXITSTATUS(status));
    printf("після wait: запис у /proc %s\n",
           proc_state(child) ? "ще є" : "зник");
    return 0;
}
```

Дитина робить `_exit(3)` і більше нічого. Цього досить: зомбі народжується не від складності, а від самого факту виходу.

Виклик `_exit` тут обов'язковий, і не заради чистоти. Дитина після `fork` дістала копію батькових буферів `stdio`, а `exit` ці буфери спорожнює — тобто надрукувала б удруге все, що батько встиг накопичити й ще не вивів ([буферизація stdio](root:sys-unix/stdio-buffering) — вивід у файл чи канал накопичується поблоково, і скидається він не тоді, коли ти написав `printf`). Запусти лабораторію з перенаправленням у файл — і з `exit` замість `_exit` побачиш подвоєні рядки.

Два виклики `kill` поспіль показують те, чого не показує жоден опис. `kill(child, SIGKILL)` **повертає нуль**: з погляду виклику все правильно — номер існує, права надіслати сигнал є, ядро сигнал прийняло. І нічого не сталося: ядро бачить, що цей процес уже завершується, і сигнал просто викидає — приймати його нікому, бо в зомбі немає ані коду, який міг би виконатися, ані стека, на якому це можна було б зробити. Успіх виклику й відсутність наслідку — не суперечність, а точний опис реальності. Другий рядок, `kill(child, 0)`, теж повертає нуль і каже інше: номер **зайнятий**. Він зайнятий саме зомбі й нікому іншому не дістанеться, доки ми не покличемо `wait`.

## Крок 2. Що лишилося в `/proc`

```c
static void proc_report(pid_t pid)
{
    char path[64], buf[8192];
    ssize_t n;

    snprintf(path, sizeof path, "/proc/%d/cmdline", (int)pid);
    n = slurp(path, buf, sizeof buf);
    printf("cmdline: %zd байтів\n", n);          /* 0 — тому ps і пише <defunct> */

    snprintf(path, sizeof path, "/proc/%d/maps", (int)pid);
    n = slurp(path, buf, sizeof buf);
    printf("maps:    %zd байтів\n", n);          /* 0 — відображень немає */

    snprintf(path, sizeof path, "/proc/%d/statm", (int)pid);
    slurp(path, buf, sizeof buf);
    printf("statm:   %s", buf);                  /* 0 0 0 0 0 0 0 */

    int vm_lines = 0;
    snprintf(path, sizeof path, "/proc/%d/status", (int)pid);
    slurp(path, buf, sizeof buf);
    for (char *l = strtok(buf, "\n"); l; l = strtok(NULL, "\n")) {
        if (!strncmp(l, "Vm", 2)) { vm_lines++; continue; }
        if (!strncmp(l, "State:", 6) || !strncmp(l, "PPid:", 5) ||
            !strncmp(l, "Threads:", 8))
            printf("status:  %s\n", l);
    }
    printf("status:  рядків Vm*: %d\n", vm_lines);

    /* поля stat після дужки: state ppid pgrp session tty tpgid flags
       minflt cminflt majflt cmajflt utime stime … */
    snprintf(path, sizeof path, "/proc/%d/stat", (int)pid);
    slurp(path, buf, sizeof buf);
    char *p = strrchr(buf, ')');
    char st; long ppid; unsigned long ut = 0, kt = 0;
    if (p && sscanf(p + 2, "%c %ld %*d %*d %*d %*d %*u %*lu %*lu %*lu %*lu %lu %lu",
                    &st, &ppid, &ut, &kt) == 4)
        printf("stat:    стан %c, батько %ld, utime %lu, stime %lu (тиків по 1/%ld с)\n",
               st, ppid, ut, kt, sysconf(_SC_CLK_TCK));
}
```

Виведення цієї функції — найкоротший опис того, чим зомбі є насправді.

`cmdline` порожній. Рядок аргументів лежав у пам'яті самого процесу, а пам'яті вже немає, тож ядру нема звідки його взяти. Саме звідси береться `<defunct>` у `ps`: утиліта питає командний рядок, дістає нуль байтів і підставляє позначку замість імені.

`maps` порожній, `statm` — суцільні нулі. Це відповідь на поширену підозру, ніби зомбі «тримає пам'ять процесу»: ядро друкує ці числа з опису адресного простору, а опису немає взагалі, тому в полях не «мало», а точний нуль.

У `status` немає **жодного** рядка `Vm*` — не нульових, а взагалі. Різниця важлива: нуль означав би «є простір, у ньому нічого», а відсутність рядка означає «нема чого описувати». Зате `State:`, `PPid:` і `Threads:` на місці — тотожність зомбі зберігає повністю.

І найцікавіше — `utime` та `stime` в `stat` не нульові. Час, який дитина встигла з'їсти, лежить у записі й чекає. Він дістанеться батькові рівно в мить прибирання й ляже в його рахунок за дітей — тому програма, що не кличе `wait`, не лише лишає зомбі, а й не знає, скільки часу з'їли її діти.

Те саме збоку, з оболонки, доки лабораторія тримає паузу:

```sh
ps -o pid,ppid,stat,rss,cmd -p 51234
#     PID    PPID STAT   RSS CMD
#   51234   51233 Z+       0 [zlab] <defunct>

ls /proc/51234/task/           # каталог задачі є
wc -c /proc/51234/cmdline      # 0
```

Буква `Z` у стані ні з чим не сплутається, а нульовий `RSS` поряд із нею — та сама відсутність адресного простору, лише переказана утилітою ([стани процесу і що означає стан D](root:sys-unix/process-states) — літера стану каже, чого саме задача зараз чекає й чи здатна вона взагалі щось робити).

## Крок 3. Прибирання і зникнення номера

Останні три рядки `lab_one()` — це другий крок смерті, зроблений вручну. `waitpid` повертає номер і статус, а зразу після нього `proc_state` уже не знаходить файлу: `open` дає `ENOENT`, бо запису більше немає.

```
waitpid → 51234, вийшла сама: 1, код 3
після wait: запис у /proc зник
```

Між цими двома рядками — вся тема. До `waitpid` номер наш, запис існує, статус доступний. Після — немає ні номера, ні запису, і система вільна видати те саме число будь-кому наступному.

## Крок 4. П'ять смертей — один сигнал

Тепер найкорисніший дослід, бо він ловить помилку, яку не видно на тестах із однією дитиною.

Щоб побачити злиття надійно, а не сподіватися на випадковий збіг у часі, треба зробити його неминучим: **зачинити двері**. Заблокуємо `SIGCHLD` у батька, наробимо дітей, дочекаємося, доки всі стануть зомбі (сигнали при цьому вже згенеровані, але доправити їх нікуди), заглянемо в набір відкладених — і лише тоді відчинимо ([маскування сигналів і signalfd](root:sys-unix/signal-mask-signalfd) — заблокований сигнал не втрачається, а позначається як відкладений і чекає на зняття блокування).

Поряд у той самий дослід вставлено контрольний зразок: кожна дитина перед смертю ще й надсилає батькові сигнал реального часу `SIGRTMIN`. Умови однакові до останньої мілісекунди, механізм зберігання — різний, і саме це зробить видимою причину, а не лише наслідок.

```c
static volatile sig_atomic_t chld_hits;
static volatile sig_atomic_t rt_hits;

static void on_chld(int sig) { (void)sig; chld_hits++; }
static void on_rt(int sig)   { (void)sig; rt_hits++;   }

static int lab_burst(int n)
{
    if (n < 1 || n > 64) n = 5;

    struct sigaction sa;
    memset(&sa, 0, sizeof sa);
    sigemptyset(&sa.sa_mask);
    sa.sa_handler = on_chld;  sigaction(SIGCHLD,  &sa, NULL);
    sa.sa_handler = on_rt;    sigaction(SIGRTMIN, &sa, NULL);

    sigset_t block, old;
    sigemptyset(&block);
    sigaddset(&block, SIGCHLD);
    sigaddset(&block, SIGRTMIN);
    sigprocmask(SIG_BLOCK, &block, &old);          /* двері зачинено */

    pid_t kids[64];
    for (int i = 0; i < n; i++) {
        kids[i] = fork();
        if (kids[i] < 0) { perror("fork"); return 1; }
        if (kids[i] == 0) {
            union sigval v; v.sival_int = i;
            sigqueue(getppid(), SIGRTMIN, v);      /* контрольний зразок */
            _exit(0);
        }
    }
    for (int i = 0; i < n; i++)
        wait_until_zombie(kids[i]);                /* усі n мертві, сигнали за дверима */

    sigset_t pend;
    sigpending(&pend);
    printf("померло дітей: %d\n", n);
    printf("SIGCHLD відкладено: %s\n",
           sigismember(&pend, SIGCHLD) ? "так — один-єдиний біт" : "ні");

    sigprocmask(SIG_SETMASK, &old, NULL);          /* двері відчинено */
    for (int i = 0; i < 200 && rt_hits < n; i++)
        sleep_ms(1);                               /* доганяємо чергу RT-сигналів */

    printf("обробник SIGCHLD спрацював разів:  %d\n", (int)chld_hits);
    printf("обробник SIGRTMIN спрацював разів: %d\n", (int)rt_hits);

    int reaped = 0, status;
    while (waitpid(-1, &status, WNOHANG) > 0)
        reaped++;
    printf("прибрано одним циклом WNOHANG: %d\n", reaped);
    return 0;
}
```

Виведення на п'ятьох дітях:

```
померло дітей: 5
SIGCHLD відкладено: так — один-єдиний біт
обробник SIGCHLD спрацював разів:  1
обробник SIGRTMIN спрацював разів: 5
прибрано одним циклом WNOHANG: 5
```

Різниця між першим і другим числом обробників — це і є вся суть. Звичайні сигнали ядро тримає **бітовою маскою**: біт «є непоправлений `SIGCHLD`» або стоїть, або не стоїть, і другий, третій, п'ятий раз поставити той самий біт — те саме, що поставити його вперше. Сигнали реального часу мають чергу, тому п'ять надісланих `SIGRTMIN` дають п'ять доставок. Умови досліду для обох були однакові — отже, різницю дала не швидкість дітей і не планувальник, а спосіб зберігання.

Звідси зрозуміла й ціна помилки. Обробник, який кличе `waitpid` один раз, у цьому досліді забрав би одну дитину з п'яти, а четверо лишилися б зомбі назавжди — і жодного другого сигналу, який нагадав би про них, уже не буде. Тому цикл `while (waitpid(-1, &status, WNOHANG) > 0)` — не стиль, а єдина правильна форма.

Прапорець `WNOHANG` у цьому циклі теж не косметика: без нього останній оберт, коли готових дітей не лишилося, заблокувався б **усередині обробника сигналу**, спинивши всю програму невідомо надовго ([що взагалі можна робити в обробнику сигналу](root:sys-unix/async-signal-safety) — обробник перериває програму в довільній інструкції, тому в ньому дозволений лише вузький перелік дій, і `printf` до нього не належить — саме тому обробники тут лише збільшують лічильник).

Коротка петля `sleep_ms(1)` після відчинення дверей потрібна через дрібну, але реальну обіцянку стандарту: POSIX гарантує, що після зняття блокування доправлять **принаймні один** відкладений сигнал, а не всі одразу. На практиці Linux віддає їх усі поспіль, але покладатися на це не варто. Сама `nanosleep` при цьому раз у раз обриватиметься на доставці — і це не заважає, бо петля просто зробить ще один оберт ([EINTR: перервані виклики й перезапуск](root:sys-unix/eintr-and-restart) — сигнал, що прийшов під час очікування, повертає виклик достроково з помилкою, і повторити його мусить програма).

## Крок 5. Скільки їх влізе — і що саме закінчується

Останній дослід відповідає на питання «чим шкідливі зомбі, якщо вони не їдять ні пам'яті, ні процесора». Робити його наосліп не можна: якщо просто плодити зомбі, доки не перестане, ти впираєшся в ліміт **користувача**, а під тим самим користувачем працює і твоя оболонка, і редактор, і браузер. Тому лабораторія спершу ставить огорожу собі.

```c
static int lab_flood(long fence)
{
    struct rlimit rl;
    getrlimit(RLIMIT_NPROC, &rl);
    printf("було: RLIMIT_NPROC м'який %ld, жорсткий %ld\n",
           (long)rl.rlim_cur, (long)rl.rlim_max);

    rl.rlim_cur = fence;                  /* власна огорожа, нижча за системну */
    if (setrlimit(RLIMIT_NPROC, &rl) < 0) { perror("setrlimit"); return 1; }
    printf("поставили собі: %ld\n", fence);

    int made = 0;
    for (;;) {
        pid_t p = fork();
        if (p == 0) _exit(0);
        if (p < 0) {
            int e = errno;
            printf("fork зупинився на %d зомбі: %s\n", made, strerror(e));
            break;
        }
        made++;
        wait_until_zombie(p);
    }
    if (made == 0)
        printf("огорожа нижча за поточне число процесів користувача — підніми її\n");

    int reaped = 0, status;
    while (waitpid(-1, &status, 0) > 0)
        reaped++;
    printf("прибрано: %d\n", reaped);
    return 0;
}
```

Типове виведення на робочій машині:

```
було: RLIMIT_NPROC м'який 63417, жорсткий 63417
поставили собі: 200
fork зупинився на 178 зомбі: Resource temporarily unavailable
прибрано: 178
```

Числа тут кажуть більше, ніж здається. По-перше, `fork` завершився помилкою `EAGAIN` — тобто зомбі **рахуються** проти ліміту нарівні з живими процесами: лічильник зменшується не тоді, коли дитина перестала виконуватися, а тоді, коли її прибрали. По-друге, зупинилися ми на 178, а не на 200: ліміт `RLIMIT_NPROC` стосується **всіх** процесів цього справжнього користувача в системі, а не лише дітей нашої програми, тож двадцять два із двохсот витратила решта твого сеансу разом із самою лабораторією ([ліміти ресурсів: rlimit і ulimit](root:sys-unix/resource-limits) — кожен ліміт має м'яке й жорстке значення, і знижене м'яке вільно повернути назад лише до жорсткого). Той самий лічильник ще й окремо ведеться контролером `pids` у контрольній групі — у контейнері першим спрацює саме він ([cgroups: облік і обмеження ресурсів](root:sys-unix/cgroups-resource-model) — межа, у якій рахують і обмежують ресурси групи процесів разом).

Огорожа з `setrlimit` тримається лише на тому, що лабораторія працює від звичайного користувача: для процесів із `CAP_SYS_ADMIN`, `CAP_SYS_RESOURCE` або справжнім UID 0 `RLIMIT_NPROC` не перевіряється взагалі. Запустивши цей режим від root, ти нічого не «перевіриш чесніше» — ти просто дійдеш до `pid_max` і забереш номери в усієї системи.

## Як зібрати й запустити

Останній шматок файлу — розподільник:

```c
int main(int argc, char **argv)
{
    const char *mode = argc > 1 ? argv[1] : "one";
    if (!strcmp(mode, "one"))   return lab_one();
    if (!strcmp(mode, "burst")) return lab_burst(argc > 2 ? atoi(argv[2]) : 5);
    if (!strcmp(mode, "flood")) return lab_flood(argc > 2 ? atol(argv[2]) : 200);
    fprintf(stderr, "usage: zlab one | burst [N] | flood [ліміт]\n");
    return 2;
}
```

```sh
cc -O2 -Wall -Wextra -o zlab zlab.c
./zlab one
./zlab burst 5
./zlab flood 200
```

Щоб побачити ті самі події збоку, тим самим прогоном:

```sh
strace -f -e trace=%process ./zlab one
```

У виведенні буде видно рівно те, про що йшлося: `clone` (у нього перетворюється `fork`), потім `exit_group` у дитини, потім `--- SIGCHLD {si_code=CLD_EXITED, si_status=3} ---` у батька і аж наприкінці `wait4` ([трасування системних викликів](root:sys-unix/syscall-tracing) — перехоплення викликів збоку, без правки самої програми).

## Що це коштує

```
один зомбі:
  структури ядра        кілька кілобайтів (запис задачі; стека ядра вже немає)
  номер                 1 із pid_max (типово 32768)
  RLIMIT_NPROC          1 із ліміту КОРИСТУВАЧА — не «програми»
  pids.current у cgroup 1
  пам'ять процесу       0    (statm суцільні нулі)
  процесорний час       0    (задача не виконується взагалі)

прибирання:
  waitpid на одну дитину           O(1)
  цикл WNOHANG на k готових        O(k)
  сигналів на k смертей            від 1 до k — і ніколи більше
```

Найважливіший рядок — третій. Пам'яті зомбі не тримає, процесора не їсть, тож у `top` його не видно ніяк; єдине, що він витрачає, — це **право когось запустити**, причому не своєї програми, а всього, що працює під тим самим користувачем. Тому служба, яка плодить зомбі, ламається не сама: спершу під тим самим користувачем перестає запускатися будь-що стороннє, і аж далі стає зле всій системі.

## Пастки

**`exit` замість `_exit` у дитині.** Дитина успадкувала копію буферів `stdio`, і `exit` їх спорожнить — усе, що батько накопичив і ще не вивів, надрукується вдруге. У терміналі вивід порядковий, тому помилка не видно; варто перенаправити в файл — і рядки подвоюються.

**Читання `/proc/<pid>` після `wait`.** Доки зомбі не прибрано, номер наш і жодні спостереження за ним не брешуть. Після `waitpid` те саме число система може видати комусь іншому вже за мілісекунди — і той самий `cat /proc/<pid>/stat` покаже чужу програму, нічим не позначивши підміну. Правило просте: або читаєш до прибирання, або тримаєш посилання, а не число.

**Розбір `stat` пробілами зліва направо.** Ім'я команди в другому полі друкується як є, разом із пробілами й дужками. Розбирати треба від **останньої** дужки, інакше на процесі з «незручним» іменем усі подальші поля зсунуться, а помилка спливе тільки в проді.

**`SIG_IGN` на `SIGCHLD` десь у програмі.** Якщо диспозиція явно поставлена в «ігнорувати», ядро прибиратиме дітей саме, і лабораторія не покаже жодного зомбі: `wait_until_zombie` крутитиметься вічно, бо стану `Z` просто не буде. Це не збій досліду, а інша гілка поведінки, і відрізняється вона від типової диспозиції однією константою ([диспозиція сигналу: обробник, ігнорування, типова дія](root:sys-unix/signal-disposition) — типова дія «нічого не робити» і явне «ігнорувати» для `SIGCHLD` дають різний результат).

**Обробник, що робить більше, ніж лічильник.** У цій лабораторії обробники лише збільшують `volatile sig_atomic_t` — і саме тому вони правильні. Щойно туди потрапить `printf`, програма стане такою, що падає раз на тисячу запусків у геть іншому місці.

**Лабораторія прибирає за собою сама — і це теж дослід.** Убий `zlab` у режимі `flood` посеред роботи (`Ctrl+C`), і всі його зомбі зникнуть миттєво: зі смертю батька вони перечепляться до найближчого підбирача або до PID 1, а той негайно покличе `wait` ([сироти й перепідпорядкування](root:sys-unix/orphan-reparenting) — дитина ніколи не лишається без батька, її передають угору по дереву). Саме тому «полагодити» зомбі перезапуском служби завжди виходить, і саме тому такий перезапуск нічого не лікує: причина лишається в коді батька.
