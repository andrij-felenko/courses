# ⚙️ Практичний менеджер cgroups v2 мовами C та C++

Створення та управління дочірніми cgroups у просторі користувача безпосередньо через системні виклики Linux є фундаментальною компетенцією розробників системного програмного забезпечення, контейнерних рушіїв (таких як `runc`, `crun` чи `youki`), демонів системної ініціалізації (`systemd`) та високозавантажених серверних платформ.

При прямому керуванні файловою системою `cgroup2` програма змушена самостійно забезпечувати атомарність операцій, перевіряти сумісність змонтованого режиму ядра, контролювати витоки дескрипторів файлів та суворо дотримуватися правила *No Internal Processes*.

У цій проектній вставці ми побудуємо повнофункціональний менеджер cgroups v2 двома мовами — системною C та ідіоматичною об'єктно-орієнтованою C++20. Ми детально розберемо створення дочірньої ієрархії, активацію контролерів, встановлення обмежень пам'яті та процесора, переміщення процесів та налаштування асинхронного моніторингу подій тиску ресурсу (PSI Pressure Stall Information) за допомогою системного виклику `epoll()`.

## 1. Архітектурна послідовність дій та алгоритм роботи

Програмний менеджер виконує послідовну серію операцій над файловою системою `/sys/fs/cgroup`:

1. **Валідація точки монтування**: Перевірка за допомогою системного виклику `statfs()`, що за шляхом `/sys/fs/cgroup` насправді змонтовано файлову систему типу `cgroup2` (визначену константою `CGROUP2_SUPER_MAGIC = 0x63677232`).
2. **Створення внутрішнього батьківського вузла**: Створення директорії `myapp` за допомогою `mkdir()`. Цей вузол виступатиме магістральним шлюзом розподілу ресурсів.
3. **Делегування та активація контролерів**: Запис рядка `+memory +cpu` у файл `myapp/cgroup.subtree_control`. Це створює керуючі файли пам'яті та процесора у всіх майбутніх дочірніх групах вузла `myapp`.
4. **Створення листового вузла**: Створення директорії `myapp/leaf`. Оскільки батьківський вузол `myapp` тепер має активовані дочірні контролери, він стає внутрішнім вузлом. Дотримуючись правила *No Internal Processes*, процеси дозволено розміщувати лише у листовому вузлі `myapp/leaf`.
5. **Конфігурування ресурсних лімітів**:
   - Запис обсягу `268435456` (256 МіБ у байтах) у керуючий файл `myapp/leaf/memory.max`.
   - Запис рядка `50000 100000` у керуючий файл `myapp/leaf/cpu.max` (надання 50 мілісекунд квоти CPU за кожні 100 мілісекунд періоду, що еквівалентно 0.5 процесорного ядра).
6. **Приєднання процесу**: Запис PID поточного процесу (отриманого викликом `getpid()`) у файл `myapp/leaf/cgroup.procs`.
7. **Асинхронний моніторинг PSI через epoll**:
   - Відкриття файлу `myapp/leaf/memory.pressure` у режимі читання-запису.
   - Запис рядка специфікації тригера: `"some 150000 1000000"` (сповістити, якщо затримка очікування пам'яті перевищує 150 мілісекунд у межах 1-секундного вікна).
   - Створення селектора `epoll_create1(EPOLL_CLOEXEC)` та реєстрація файлового дескриптора з прапорцем `EPOLLPRI`.
   - Очікування на події ядерного сповіщення викликом `epoll_wait()`.

```c
/* cgroup2_manager.c — Програмне керування cgroups v2 мовою C */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/stat.h>
#include <sys/epoll.h>
#include <sys/vfs.h>
#include <errno.h>

#define CGROUP_ROOT "/sys/fs/cgroup"
#define CGROUP_MAGIC 0x63677232 /* CGROUP2_SUPER_MAGIC */

/* Допоміжна функція відкриття та запису у файли керування cgroup */
static int write_file(const char *path, const char *val) {
    int fd = open(path, O_WRONLY | O_CLOEXEC);
    if (fd < 0) {
        perror("open failed");
        return -1;
    }
    ssize_t len = strlen(val);
    if (write(fd, val, len) != len) {
        perror("write failed");
        close(fd);
        return -1;
    }
    close(fd);
    return 0;
}

int main(void) {
    struct statfs st;
    if (statfs(CGROUP_ROOT, &st) != 0 || st.f_type != CGROUP_MAGIC) {
        fprintf(stderr, "Помилка: %s не є змонтованою cgroup2\n", CGROUP_ROOT);
        return EXIT_FAILURE;
    }

    /* 1. Створення батьківської cgroup */
    if (mkdir(CGROUP_ROOT "/myapp", 0755) != 0 && errno != EEXIST) {
        perror("mkdir myapp failed");
        return EXIT_FAILURE;
    }

    /* 2. Активація контролерів для дочірніх груп */
    if (write_file(CGROUP_ROOT "/myapp/cgroup.subtree_control", "+memory +cpu") != 0) {
        fprintf(stderr, "Не вдалося увімкнути контролери у subtree_control\n");
        return EXIT_FAILURE;
    }

    /* 3. Створення листової cgroup для процесів */
    if (mkdir(CGROUP_ROOT "/myapp/leaf", 0755) != 0 && errno != EEXIST) {
        perror("mkdir leaf failed");
        return EXIT_FAILURE;
    }

    /* 4. Встановлення ліміту пам'яті (256 МіБ) та квоти CPU (50% одного ядра) */
    if (write_file(CGROUP_ROOT "/myapp/leaf/memory.max", "268435456") != 0 ||
        write_file(CGROUP_ROOT "/myapp/leaf/cpu.max", "50000 100000") != 0) {
        fprintf(stderr, "Не вдалося встановити ресурсні ліміти\n");
        return EXIT_FAILURE;
    }

    /* 5. Переміщення поточного процесу у листовий вузол */
    char pid_str[32];
    snprintf(pid_str, sizeof(pid_str), "%d", getpid());
    if (write_file(CGROUP_ROOT "/myapp/leaf/cgroup.procs", pid_str) != 0) {
        fprintf(stderr, "Не вдалося перемістити процес у cgroup.procs\n");
        return EXIT_FAILURE;
    }

    printf("Процес %d успішно переміщено в " CGROUP_ROOT "/myapp/leaf\n", getpid());

    /* 6. Реєстрація PSI сповіщення через epoll */
    int press_fd = open(CGROUP_ROOT "/myapp/leaf/memory.pressure", O_RDWR | O_CLOEXEC);
    if (press_fd >= 0) {
        /* Тригер: Деякі процеси заблоковані (some) понад 150мс за вікно 1с */
        const char *trigger = "some 150000 1000000";
        if (write(press_fd, trigger, strlen(trigger)) > 0) {
            int epfd = epoll_create1(EPOLL_CLOEXEC);
            struct epoll_event ev = { .events = EPOLLPRI, .data.fd = press_fd };
            epoll_ctl(epfd, EPOLL_CTL_ADD, press_fd, &ev);

            printf("Моніторинг PSI тиску пам'яті запущено...\n");
            struct epoll_event events[1];
            int nfds = epoll_wait(epfd, events, 1, 2000); /* чекаємо 2 секунди */
            if (nfds > 0) {
                printf("УВАГА: Отримано PSI сповіщення про брак пам'яті!\n");
            } else {
                printf("Тиск пам'яті у нормі.\n");
            }
            close(epfd);
        }
        close(press_fd);
    }

    return EXIT_SUCCESS;
}
```

```cpp
// cgroup2_manager.cpp — Об'єктно-орієнтоване управління cgroups v2 мовою C++20
#include <iostream>
#include <fstream>
#include <string>
#include <string_view>
#include <filesystem>
#include <system_error>
#include <memory>
#include <chrono>
#include <unistd.h>
#include <fcntl.h>
#include <sys/stat.h>
#include <sys/epoll.h>
#include <sys/vfs.h>

namespace fs = std::filesystem;

/* Обгортка RAII для файлових дескрипторів Linux */
class scoped_fd {
    int m_fd{-1};
public:
    explicit scoped_fd(int fd) noexcept : m_fd(fd) {}
    ~scoped_fd() { if (m_fd >= 0) ::close(m_fd); }
    scoped_fd(const scoped_fd&) = delete;
    scoped_fd& operator=(const scoped_fd&) = delete;
    scoped_fd(scoped_fd&& o) noexcept : m_fd(o.m_fd) { o.m_fd = -1; }
    scoped_fd& operator=(scoped_fd&& o) noexcept {
        if (this != &o) {
            if (m_fd >= 0) ::close(m_fd);
            m_fd = o.m_fd;
            o.m_fd = -1;
        }
        return *this;
    }
    [[nodiscard]] int get() const noexcept { return m_fd; }
    [[nodiscard]] bool valid() const noexcept { return m_fd >= 0; }
};

/* Клас управління листовим вузлом cgroups v2 */
class cgroupv2_leaf {
    fs::path m_path;
public:
    static constexpr uint64_t cgroup2_magic = 0x63677232;

    explicit cgroupv2_leaf(const fs::path& parent_name, const fs::path& leaf_name) {
        fs::path root = "/sys/fs/cgroup";
        struct statfs st{};
        if (::statfs(root.c_str(), &st) != 0 || st.f_type != cgroup2_magic) {
            throw std::runtime_error("Файлова система /sys/fs/cgroup не є cgroup2");
        }

        fs::path parent = root / parent_name;
        fs::create_directories(parent);

        /* Активація контролерів у батьківському вузлі */
        write_control(parent / "cgroup.subtree_control", "+memory +cpu");

        m_path = parent / leaf_name;
        fs::create_directories(m_path);
    }

    void set_memory_max(size_t bytes) {
        write_control(m_path / "memory.max", std::to_string(bytes));
    }

    void set_cpu_quota(uint64_t max_us, uint64_t period_us) {
        std::string val = std::to_string(max_us) + " " + std::to_string(period_us);
        write_control(m_path / "cpu.max", val);
    }

    void attach_current_process() {
        write_control(m_path / "cgroup.procs", std::to_string(::getpid()));
    }

    void monitor_psi_memory(std::chrono::milliseconds timeout) {
        scoped_fd pfd(::open((m_path / "memory.pressure").c_str(), O_RDWR | O_CLOEXEC));
        if (!pfd.valid()) return;

        std::string_view trigger = "some 150000 1000000";
        if (::write(pfd.get(), trigger.data(), trigger.size()) <= 0) return;

        scoped_fd epfd(::epoll_create1(EPOLL_CLOEXEC));
        if (!epfd.valid()) return;

        epoll_event ev{.events = EPOLLPRI, .data{.fd = pfd.get()}};
        ::epoll_ctl(epfd.get(), EPOLL_CTL_ADD, pfd.get(), &ev);

        epoll_event events[1];
        int nfds = ::epoll_wait(epfd.get(), events, 1, static_cast<int>(timeout.count()));
        if (nfds > 0) {
            std::cout << "[C++] Увага: Зареєстровано PSI поріг тиску пам'яті!\n";
        } else {
            std::cout << "[C++] Стан пам'яті cgroup стабільний.\n";
        }
    }

private:
    static void write_control(const fs::path& p, std::string_view val) {
        std::ofstream ofs(p);
        if (!ofs) {
            throw std::system_error(errno, std::generic_category(), "Не вдалося відкрити " + p.string());
        }
        ofs << val;
        if (!ofs) {
            throw std::runtime_error("Помилка запису у " + p.string());
        }
    }
};

int main() {
    try {
        cgroupv2_leaf cg("myapp_cpp", "worker");
        cg.set_memory_max(256 * 1024 * 1024); // 256 МіБ
        cg.set_cpu_quota(50000, 100000);       // 50% CPU
        cg.attach_current_process();
        std::cout << "[C++] Процес " << ::getpid() << " переміщено у cgroup\n";

        cg.monitor_psi_memory(std::chrono::milliseconds(2000));
    } catch (const std::exception& e) {
        std::cerr << "Помилка: " << e.what() << '\n';
        return EXIT_FAILURE;
    }
    return EXIT_SUCCESS;
}
```

## 3. Покроковий розбір системних викликів та ядерних механізмів

Розглянемо детально, що саме відбувається у ядрі Linux під час виконання кожної фази нашого програмного менеджера.

### 3.1 Перевірка магічного числа файлової системи (`statfs`)

Системний виклик `statfs()` повертає статистику змонтованої файлової системи у структурі `struct statfs`. Найважливішим полем для валідації є `f_type`. У ядрі Linux кожна віртуальна та фізична файлова система визначає унікальне магічне число. Для `cgroup2` це число константне і дорівнює `CGROUP2_SUPER_MAGIC = 0x63677232`.

Попередня перевірка `f_type` є суворим стандартом безпечного системного програмування. Якщо середовище запущено у старій системі з гібридним режимом або cgroups v1, за шляхом `/sys/fs/cgroup` може бути змонтовано віртуальну ФС типу `tmpfs` (`0x01021994`). Спроба запису у такий каталог просто створить у ньому звичайні файли, які не матимуть жодного впливу на підсистему планувальника або контролер пам'яті ядра.

Під час виконання `statfs()` ядро бере поле `f_type` із суперблока змонтованої ФС — для `cgroup2` його виставляє при монтуванні структура `cgroup2_fs_type`. Оскільки псевдофайлова система `cgroup2` живе цілком у пам'яті ядра, перевірка не спричиняє жодної операції дискового вводу-виводу.

### 3.2 Прапорець `O_CLOEXEC` та безпека дескрипторів

У всіх викликах `open()` та `epoll_create1()` використовується прапорець `O_CLOEXEC` (Close-on-exec). Якщо програма створює новий керуючий файл cgroup і згодом породжує дочірній процес за допомогою `fork()` + `execve()`, відкритий файловий дескриптор без `O_CLOEXEC` успадковується дочірнім процесом.

У багатопотокових серверах це створює важку проблему: дочірній процес утримує відкритим дескриптор `cgroup.procs` або `memory.pressure`, через що спроба вилучити cgroup за допомогою `rmdir()` повертатиме помилку `EBUSY` навіть після того, як основний демон завершив свою роботу. Використання `O_CLOEXEC` та `EPOLL_CLOEXEC` забезпечує атомарне закриття файлів при виклику `execve()`.

Крім того, PSI-тригер прив'язується не до самого файлу, а до конкретного відкритого опису файлу (`struct file`) `memory.pressure`: ядро знищує тригер тоді, коли закривається останній дескриптор, що на цей опис посилається. Якщо дескриптор протік у дочірній процес через `fork()`, закриття його в батькові не обнуляє `file->f_count`, і тригер лишається живим та зареєстрованим.

### 3.3 Внутрішня механіка запису у `cgroup.procs`

Коли програма виконує системний виклик `write()` для запису PID у `cgroup.procs`, ядро Linux переходить у простір ядра та виконує послідовність внутрішніх операцій:

1. **Пошук процесу (`find_task_by_vpid`)**: Пошук задачі за числом PID у межах PID-простору того, хто пише.
2. **Отримання контексту (`pid_task`)**: Отримання вказівника на головну задачу групи потоків `struct task_struct`.
3. **Перевірка прав та правил (`cgroup_attach_task`)**:
   - Перевірка, що процес-ініціатор має `CAP_SYS_ADMIN` або володіє файлом `cgroup.procs` цільової групи.
   - Перевірка правила *No Internal Processes*: якщо цільова cgroup є некореневою і має активовані контролери у своєму `cgroup.subtree_control`, виклик повертає `EBUSY`.
4. **Атомарна зміна `css_set`**:
   - Ядро звертається до ядерної хеш-таблиці `css_set` і знаходить або конструує новий екземпляр `css_set`, який відповідає новій cgroup.
   - Під захистом RCU-блокування вказівник `task_struct->cgroups` оновлюється для всіх потоків даного процесу.
   - Потоки видаляються з попередніх списків спостереження та реєструються у нових лічильниках статистики цільової cgroup.

Під час зміни `css_set` ядро гарантує, що жоден потік не залишиться в проміжному стані: семафор `cgroup_threadgroup_rwsem` (пара `cgroup_threadgroup_change_begin()`/`_end()`) блокує паралельне виконання `clone()` чи `pthread_create()` у цільовому процесі на увесь час оновлення вказівників `task_struct->cgroups`.

### 3.4 Механізм PSI тригерів та `EPOLLPRI`

Реєстрація сповіщень про брак ресурсів (Pressure Stall Information) через `epoll()` є однією з найефективніших технологій асинхронного моніторингу в Linux.

Коли програма записує рядок тригера (наприклад `"some 150000 1000000"`) у відкритий файловий дескриптор `memory.pressure`, ядро викликає внутрішню функцію `psi_trigger_create()`. Вона створює об'єкт `struct psi_trigger`, який реєструється у ядерній системі опитування стану підсистеми пам'яті.

Поки тригер живий, ядро перераховує тиск частіше за звичайні усереднення — приблизно десять разів за вікно тригера (для вікна 1 с це раз на 100 мс). Щойно сумарна затримка у вікні перевищує поріг (150 мс із 1000 мс), ядро будить усіх, хто чекає на цьому дескрипторі, — так само, як на позасмугових даних.

У селекторі `epoll()` ця подія позначається маскою `EPOLLPRI` (Priority Data). `epoll_wait()` миттєво повертає контроль програмі простору користувача, не чекаючи тайм-ауту, що дозволяє реагувати на дефіцит ресурсу за мілісекунди до виклику ядерного OOM killer.

Структура `struct epoll_event` при цьому містить прапор `EPOLLPRI`, який повідомляє обробнику подій, що на файловому дескрипторі з'явилися виняткові дані високого пріоритету. При прочитанні дескриптора програма отримує поточний текст статистики PSI без необхідності перезапису тригера.

У серйозних демонах дескриптор додають у `epoll()` з `EPOLLET` — сповіщенням за фронтом, а не за рівнем. Завдяки цьому системний демон очікує лише на зміни тиску пам'яті, уникаючи повторних сповіщень на кожній ітерації циклу подієвої петлі (event loop).

### 3.5 Переваги C++20 RAII та обробка винятків

У версії C++ реалізовано клас `scoped_fd`, який застосовує ідіому RAII (Resource Acquisition Is Initialization). У випадку виникнення винятку (наприклад, якщо `write_control` кидає `std::system_error` через недостатньо прав), деструктор `scoped_fd` автоматично гарантує виклик `close()` для всіх відкритих дескрипторів `epoll` та PSI-файлів. Це запобігає витокам ресурсів системи навіть при аварійному завершенні блоку `try-catch`.

Конструктор переміщення `scoped_fd(scoped_fd&&)` маркує джерельний дескриптор як `-1`, запобігаючи подвійній спробі закриття (`double close`) при передачі дескриптора у функції або контейнери `std::vector`.

Увімкнення `std::filesystem::create_directories` спрощує роботу зі шляхами VFS, автоматично створюючи всі необхідні проміжні директорії в ієрархії cgroups v2. Використання `std::string_view` у виклику `write_control` дозволяє передавати текстові константи без зайвого виділення динамічної пам'яті в купі (heap allocation).

Обробка помилок спирається на тип `std::system_error`, який автоматом транслює системні коди `errno` (такі як `EACCES` чи `EBUSY`) у зрозумілі повідомлення винятків із прив'язкою до системних категорій POSIX.

## 4. Модель безпривілейованого делегування (Delegation)

У багатьох сучасних архітектурах створення cgroups виконується без залучення прав користувача `root`. Цей підхід лежить в основі роботи Rootless Podman, Docker у режимі без привілеїв та безпривілейованих LXC-контейнерів.

### 4.1 Права володіння VFS та директива `Delegate=yes`

Для делегування піддерева cgroups v2 системний менеджер `systemd` створює групу у зрізі `user.slice` (наприклад `/sys/fs/cgroup/user.slice/user-1000.slice/user@1000.service/`) та виконує системний виклик `chown()` для файлів керування.

Власником передаються наступні керуючі файли:
- `cgroup.procs`: Дозволяє безпривілейованому користувачеві розміщувати власні процеси у делегованому піддереві.
- `cgroup.subtree_control`: Дозволяє вмикати та вимикати доступні контролери для дочірніх cgroups.
- `cgroup.threads`: Дозволяє керувати окремими потоками у потоковому режимі.

При цьому файли `cgroup.controllers` та батьківські обмежувальні файли (`memory.max`, `cpu.max`) залишаються у власності `root`. Непривілейований користувач не може збільшити ліміт пам'яті вище межі, встановленої системним адміністратором, але може довільно ділити виділений йому ресурс між власними дочірніми контейнерами.

При виконанні виклику `chown()` системний демон надає UID користувача права володіння файлами VFS, однак ядро додатково перевіряє маску `cgroup.subtree_control` батька. Якщо батьківський вузол не увімкнув контролер `memory`, безпривілейований процес дістає помилку `ENOENT` при спробі записати `+memory` у делеговане піддерево: контролера просто немає у списку `cgroup.controllers`.

### 4.2 Специфікація OCI Runtimes та `crun` / `runc`

Під час запуску контейнера OCI-рушій (`runc` або `crun`) зчитує специфікацію `config.json` та конструює піддерево cgroups v2 у делегованому зрізі користувача:

1. **Реєстрація у systemd через DBus**: Рушій надсилає повідомлення у `systemd --user` для створення відповідного Scope-юніта.
2. **Конфігурація cgroup**: Запис параметрів `memory.max`, `cpu.weight`, `pids.max` у листовий вузол контейнера.
3. **Запуск контейнерного процесу**: Виконання викликів `clone(CLONE_NEWPID | CLONE_NEWNS)` та переміщення PID у `cgroup.procs` контейнера.

Порівняно із застарілими бібліотеками `libcgroup` v1, сучасному системному програмному забезпеченню більше не потрібні додаткові проміжні абстракції. Пряма робота з VFS cgroups v2 через системні виклики POSIX забезпечує максимальну швидкодію та гарантує повний контроль над ресурсами системи.

Такий дизайн дозволяє будувати високопродуктивні хмарні операційні середовища. Системний простір користувача отримує прозорий інструмент вимірювання витрат дискового вводу-виводу та пам'яті.

## 5. Пастки та підводні камені реалізації

У практичній розробці реальних системних демонів та контейнерних рушіїв виникають наступні крайові випадки:

1. **Помилка `EBUSY` при створенні ієрархії**:
   - Причина: Спроба запису `+memory` у `cgroup.subtree_control` батьківського вузла, у якому вже є живий процес.
   - Рішення: Менеджер повинен спочатку створити листовий каталог (наприклад `leaf`), перемістити туди процес шляхом запису у `leaf/cgroup.procs`, і лише після цього активувати контролери у батьківському вузлі.

2. **Гонка процесів при `fork()` (Race Condition)**:
   - Причина: Батьківський процес створює дитину `fork()`, але дитина встигає виконати важку роботу або народити власні потоки до того, як батько записав її PID у `cgroup.procs`.
   - Рішення: Стандартний шаблон контейнерних OCI-рушіїв: батько створює сигнальний канал `pipe()`, робить `fork()`. Дитина блокується на зчитуванні з `pipe()`. Батько записує PID дитини у `cgroup.procs`, налаштовує `memory.max` та `cpu.max`, і лише після цього відправляє байт у `pipe()`, розблоковуючи дитину для виконання `execve()`.

3. **Видалення порожніх cgroups (`rmdir`)**:
   - Помилка: Системний виклик `rmdir()` повертає `EBUSY`, якщо cgroup містить хоч один живий процес або якщо її дочірні cgroups ще не вилучені.
   - Рішення: Видалення піддерева cgroups v2 має виконуватися виключно знизу вгору (bottom-up post-order traversal). Спочатку всі процеси переміщуються у батьківську cgroup або завершуються сигналом `SIGKILL`. Потім менеджер очікує, поки файл `cgroup.events` поверне `populated 0`, і лише після цього викликає `rmdir()`.

4. **Обробка некоректних PID при чищенні процесів**:
   - Причина: Спроба запису PID у `cgroup.procs`, який вже завершив виконання у ядрі, повертає помилку `ESRCH` або `ENOENT`.
   - Рішення: Менеджер cgroups повинен перевіряти наявність PID у `/proc/[pid]` або ігнорувати помилку `ESRCH` при масовому переміщенні короткоживучих задач.

5. **Прив'язка розширених програм eBPF (`BPF_PROG_ATTACH`)**:
   - Причина: Завантаження BPF-фільтрів мережевих сокетів (`BPF_PROG_TYPE_CGROUP_SKB`) вимагає відкриття файлового дескриптора каталогу cgroup v2 за допомогою виклику `open(..., O_DIRECTORY)`.
   - Рішення: Менеджер повинен перевіряти права доступу до файлового дескриптора каталогу cgroup перед викликом `bpf(BPF_PROG_ATTACH, ...)` для запобігання помилкам `EPERM`.

6. **Синхронізація сигналів обробки завершення контейнера**:
   - Причина: При зупинці контейнера OCI-рушій надсилає `SIGTERM` головному процесу в `cgroup.procs`. Якщо процес ігнорує сигнал, рушій повинен очікувати заданий тайм-аут перед надсиланням `SIGKILL`.
   - Рішення: Менеджер виконує опитування файлу `cgroup.events` через `epoll()` на прапорець `populated`. Коли `populated 0`, ядро гарантує, що у піддереві не залишилося жодного живого процесу чи потоку.

7. **Необхідність обробки помилок відсутності підтримуваних контролерів**:
   - Причина: При спробі увімкнути `+io` або `+cpuset` у системі з обмеженою конфігурацією ядра системний виклик `write()` повертає `ENOENT` (контролера немає у `cgroup.controllers`) або `EINVAL` (назву не розпізнано).
   - Рішення: Програмний менеджер повинен зчитати вміст `cgroup.controllers` перед модифікацією `cgroup.subtree_control` для виявлення реального набору завантажених ядерних модулів.

8. **Атомарний запуск контейнерів у безпривілейованому режимі**:
   - Причина: Запуск безпривілейованих контейнерів під керуванням `systemd` вимагає узгодження прав на рівні User Namespace (UID mapping) та VFS ACL.
   - Рішення: Створення специфікації юніта через D-Bus API `systemd` дозволяє налаштувати параметри `Delegate=yes` та `User=` ще до того, як у `cgroup.procs` потраплять процеси.

9. **Запобігання дрифту параметрів конфігурації**:
   - Причина: Паралельні процеси системного моніторингу або ручні виклики `cgset` можуть змінювати параметри `memory.max` або `cpu.max` без відома основного менеджера.
   - Рішення: єдиний власник конфігурації і власне блокування поза cgroupfs (наприклад, `flock()` на окремому файлі-замку в `/run`): сама `cgroup2` жодних блокувань не надає, і останній запис у керуючий файл просто перетирає попередній.

10. **Обробка вкладеної ієрархії під час гарячого перезавантаження**:
    - Причина: Оновлення версії системного демона без зупинки працюючих контейнерів вимагає збереження наявного піддерева cgroups.
    - Рішення: Демон зчитує вкладену структуру каталогу `/sys/fs/cgroup` та відновлює зв'язки процесів з їхніми листовими вузлами за допомогою відстеження `cgroup.procs`.

11. **Узгодження квот при зміні кількості апаратних ядер**:
    - Причина: При гарячому вилученні ядер CPU (hotplug) встановлене значення `cpu.max` може перевищити загальну обчислювальну потужність сервера.
    - Рішення: Демон підписується на події `udev` та динамічно перераховує параметри квотування `cpu.max` та відносної ваги `cpu.weight` відповідно до актуальної кількості доступних ядер у `cpuset.cpus.effective`.

12. **Ізоляція ресурсів при виконанні високонавантажених обчислень**:
    - Причина: Паралельне виконання багатьох задач створення короткоживучих процесів призводить до сплесків виділення пам'яті slab у ядрі Linux.
    - Рішення: Встановлення відповідних параметрів `memory.high` разом із моніторингом PSI дозволяє динамічно регулювати навантаження на систему без ризику падіння через OOM killer.

13. **Контроль затримки при роботі з мережевими сокетами**:
    - Причина: Окремі мережеві з'єднання можуть споживати значний обсяг буферів оперативної пам'яті в підсистемі ядра.
    - Рішення: Використання контролера пам'яті cgroups v2 дозволяє враховувати обсяг `sock` у загальному ліміті `memory.max`, запобігаючи неконтрольованому виснаженню пам'яті ядра при мережевих атаках.
