# 📋 Довідник інтерфейсів та конфігурації динамічного завантажувача ld.so

Цей довідник описує керуючі структури ELF, змінні середовища, конфігураційні директиви та програмовані API динамічного завантажувача `ld.so` у Linux.

Динамічний завантажувач у системі GNU/Linux виступає мостом між статичним двійковим файлом на диску та готовим до виконання процесом у віртуальній пам'яті. Його поведінка керується метаданими, записаними у самому ELF-файлі на етапі компоновки, глобальними конфігураційними файлами системного адміністратора, а також змінними середовища оточення користувача. Ниче розібрано повний перелік керуючих структур, форматів конфігурації та системних заголовочних типів.

## 1. Заголовки ELF та теги динамічної секції

Під час збірки динамічного бінарника компонувальник (linker) формує спеціальний сегмент `PT_DYNAMIC`, який у секційній таблиці відповідає секції `.dynamic`. Цей сегмент являє собою масив елементів типу `Elf64_Dyn` (або `Elf32_Dyn` для 32-бітних архітектур). Кожен елемент має фіксований розмір і складається з поля тегу `d_tag` та об'єднаного значення `d_un` (`d_val` або `d_ptr`).

Динамічний завантажувач при старті процесу сканує цей масив від початку до кінцевого елемента з тегом `DT_NULL`, збираючи інструкції про необхідні бібліотеки, адреси таблиць символів та шляхи пошуку.

| Тег `d_tag` | Числове значення | Опис та призначення |
| :--- | :--- | :--- |
| `DT_NEEDED` | `1` | Ім'я необхідної розділюваної бібліотеки (зсув у таблиці рядків `.dynstr`). Створюється для кожного прапорця `-l`. |
| `DT_RPATH` | `15` | Рядок шляхів пошуку бібліотек у стилі SVR4 (через двокрапку). Ігнорується, якщо наявний `DT_RUNPATH`. |
| `DT_RUNPATH` | `29` | Рядок шляхів пошуку бібліотек у стилі POSIX/Solaris. Обробляється після `LD_LIBRARY_PATH`. |
| `DT_FLAGS` | `30` | Старі прапорці динамічного лінкування (наприклад, `DF_BIND_NOW`, `DF_ORIGIN`). |
| `DT_FLAGS_1` | `0x6ffffffb` | Сучасні розширені прапорці динамічного лінкування (ELF flags 1). |
| `DT_STRTAB` | `5` | Вказівник на віртуальну адресу таблиці рядків `.dynstr`, з якої зчитуються імені бібліотек і символів. |
| `DT_STRSZ` | `10` | Загальний розмір таблиці рядків `.dynstr` у байтах. |
| `DT_SYMTAB` | `6` | Вказівник на віртуальну адресу таблиці динамічних символів `.dynsym`. |
| `DT_PLTGOT` | `3` | Вказівник на глобальну таблицю зсувів GOT (Global Offset Table) та таблицю связування процедур PLT. |

### Прапорці `DT_FLAGS_1` (ELF Flags 1)

Поле `DT_FLAGS_1` містить бітову маску розширених режимів виконання завантажувача. Ці прапорці дозволяють розробнику жорстко зафіксувати поведінку зв'язування безпосередньо у бінарнику:

- `DF_1_NOW` (`0x00000001`): Вимагає від завантажувача негайного розв'язання всіх PLT-символів під час старту програми. Повністю відключає ліниве зв'язування (lazy binding) та ігнорує відсутність `LD_BIND_NOW`.
- `DF_1_NODEFLIB` (`0x00000400`): Наказує завантажувачу повністю пропустити пошук у стандартних системних каталогах (`/lib64`, `/usr/lib64`) та бінарному кеші `/etc/ld.so.cache`. Завантажувач шукатиме бібліотеки виключно у шляхах `RPATH`/`RUNPATH` та `LD_LIBRARY_PATH`.
- `DF_1_NOOPEN` (`0x00000040`): Забороняє явне завантаження даної бібліотеки через виклик `dlopen()`. При спробі відкрити файл з цим прапорцем `dlopen()` повертає помилку.
- `DF_1_ORIGIN` (`0x00000001`): Інформує завантажувач про те, що бінарник або бібліотека містить токен `$ORIGIN` у своїх шляхах, і завантажувач повинен обчислити абсолютний шлях каталогу файлу ще до початку пошуку залежностей.
- `DF_1_NODELETE` (`0x00000008`): Вказує завантажувачу, що модуль не повинен вивантажуватися з пам'яті при виклику `dlclose()`.

## 2. Змінні середовища динамічного завантажувача

Динамічний завантажувач `ld.so` підтримує багатий набір змінних середовища для діагностики, моніторингу та корекції порядку завантаження. Ці змінні зчитуються завантажувачем на найраннішому етапі ініціалізації процесу, ще до передачі управління функції `main()`.

> [!WARNING]
> Усі змінні середовища, позначені як потенційно небезпечні для системної безпеки, автоматично видаляються або повністю ігноруються завантажувачем, якщо процес виконується у захищеному режимі `AT_SECURE=1` (SUID/SGID бінарники, наявність Linux capabilities).

Таблиця нижче деталізує призначення та поведінку ключових змінних завантажувача:

| Змінна середовища | Скидається при `AT_SECURE` | Опис та призначення |
| :--- | :---: | :--- |
| `LD_LIBRARY_PATH` | Так | Список каталогів (через двокрапку `:`), які перевіряються перед `DT_RUNPATH` та системним кешем. |
| `LD_PRELOAD` | Так | Список додаткових бібліотек, які завантажуються **до** будь-яких інших бібліотек. Дозволяє перехоплювати функції. |
| `LD_DEBUG` | Ні | Вмикає детальне діагностичне логування `ld.so` у `stderr`. Значення: `libs`, `files`, `symbols`, `bindings`, `versions`, `all`, `help`. |
| `LD_DEBUG_OUTPUT` | Ні | Файловий префікс для запису діагностичних логів `LD_DEBUG` у файл замість стандартного потоку `stderr`. |
| `LD_BIND_NOW` | Ні | Якщо значення не порожнє, примусово розв'язує всі GOT/PLT-символи при старті процесу (відключає ліниве зв'язування `lazy binding`). |
| `LD_AUDIT` | Так | Список бібліотек аудіту (Link-Map Audit API, `rtld-audit`), що відстежують події завантаження та розв'язання символів. |
| `LD_ORIGIN_PATH` | Так | Перевизначає абсолютне значення каталогу, яке використовується завантажувачем для розкриття токена `$ORIGIN`. |
| `LD_SHOW_AUXV` | Ні | Якщо дорівнює `1`, виводить повний вміст допоміжного вектора ядра (Auxiliary Vector) у `stderr` при старті програми. |
| `LD_PROFILE` | Так | Вказує ім'я розділюваної бібліотеки для збору профайлінгу викликів функцій (створює файл профілю у `/var/tmp`). |
| `LD_DYNAMIC_WEAK` | Так | Якщо встановлено, дозволяє слабким символам (weak symbols) перевизначати звичайні символи при розв'язанні залежностей. |

Поведінка утиліти `LD_DEBUG` є головним інструментом системного інженера. Вона приймає списки ключів через кому. Наприклад, виклик `LD_DEBUG=libs,files ./app` змусить `ld.so` послідовно виводити повний шлях до кожного відкритого файлу, результати перевірок кешу та причини відмови при відкритті неіснуючих каталогів.

## 3. Конфігураційні файли /etc/ld.so.conf та кеш /etc/ld.so.cache

Системний кеш `/etc/ld.so.cache` розроблений для того, щоб позбавити `ld.so` від необхідності сканувати дискові каталоги при кожному запуску будь-якої програми у системі. Джерелом даних для побудови цього кешу є текстовий конфігураційний файл `/etc/ld.so.conf`.

### Синтаксичні директиви ld.so.conf

Текстовий файл `/etc/ld.so.conf` обробляється утилітою `ldconfig` зверху вниз відповідно до наступних правил синтаксису:

1. **Символи коментарів**: Будь-який рядок, що починається з решітки `#`, або текст після символу `#` вважається коментарем і ігнорується.
2. **Абсолютні шляхи**: Рядок, що містить шлях до каталогу (наприклад, `/usr/local/lib64`), вказує утиліти `ldconfig` внести цей каталог та всі розділювані бібліотеки в ньому до кешу.
3. **Директива `include`**: Дозволяє імпортувати вміст інших конфігураційних файлів за використанням системного розширення маски glob:
   ```text
   include /etc/ld.so.conf.d/*.conf
   ```
4. **Директива `hwcap`**: Задає специфічні апаратні вимоги (Hardware Capabilities) для вибіркового завантаження оптимізованих бібліотек:
   ```text
   hwcap 0 avx2
   ```

### Формат двійкового кешу ld.so.cache

У сучасних дистрибутивах Linux утиліта `ldconfig` створює кеш у форматі `ld_socache_100`. Файл відображається завантажувачем у пам'ять через системний виклик `mmap()` у режимі read-only.

Внутрішня структура кешу включає:

- **Магічний заголовок**: Фіксований рядок `glibc-ld.so.cache1.0`, за яким завантажувач перевіряє сумісність версії кешу.
- **Лічильник записів `nlibs`**: Загальна кількість індексованих розділюваних бібліотек у системі.
- **Таблиця індексів `entry_t`**: Масив структур, де кожен запис містить:
  - `flags`: Бітова маска ABI та архітектури (наприклад, `FLAG_ELF_LIBC6`, `FLAG_X8664_LIB64`).
  - `kptr`: Зсув у таблиці рядків до назви SONAME (наприклад, `libc.so.6`).
  - `vptr`: Зсув у таблиці рядків до абсолютного шляху файлу (наприклад, `/lib/x86_64-linux-gnu/libc.so.6`).
- **Строковий блоковий масив**: Суцільний блок пам'яті, що містить null-терміновані рядки імен та шляхів.

Оскільки всі рядки відсортовані за алфавітом, динамічний завантажувач знаходить потрібний SONAME за допомогою швидкого бінарного пошуку за logarithmic time `O(log N)`.

## 4. Програмований інтерфейс dlinfo (RTLD_DI)

Для програмного аналізу завантажених бібліотек та огляду шляхів їх пошуку безпосередньо з C або C++ коду використовується розширення C-бібліотеки glibc — функція `dlinfo()`. Вона оголошена у заголовочному файлі `<dlfcn.h>`.

Сигнатура функції та основний контракт виклику:

```c
#define _GNU_SOURCE
#include <dlfcn.h>

int dlinfo(void *handle, int request, void *info);
```

Функція приймає вказівник `handle`, отриманий від виклику `dlopen()` (або псевдо-дескриптор `RTLD_DEFAULT`/`RTLD_NEXT`), код запиту `request` та вказівник на буфер `info`, у який записується результат. При успіху повертає `0`, при помилці — від'ємне число, а детальну причину збою можна прочитати через `dlerror()`.

### Список кодів запитів `request`

- `RTLD_DI_LMID` (`1`): Повертає ідентифікатор простору назв завантаження (`Lmid_t`), у якому знаходиться вказаний модуль.
- `RTLD_DI_LINKMAP` (`2`): Записує у вказівник `info` адресу внутрішньої структури завантажувача `struct link_map`, яка містить базову адресу завантаження модуля (`l_addr`), його ім'я (`l_name`) та вказівник на секцію `.dynamic` (`l_ld`).
- `RTLD_DI_SERINFO` (`3`): Заповнює попередньо виділену структуру `Dl_serinfo` повним списком каталогів пошуку, які `ld.so` використовує для цього модуля.
- `RTLD_DI_SERINFOSIZE` (`4`): Обчислює загальний розмір пам'яті у байтах, необхідний для збереження структури `Dl_serinfo` з усім списком каталогів, і записує це значення у поле `dls_size`.
- `RTLD_DI_ORIGIN` (`6`): Копіює в буфер `info` абсолютний шлях каталогу, у який розгортається токен `$ORIGIN` для даного модуля.

### Опис типів даних Dl_serinfo та Dl_serpath

Двокрокова процедура запиту `RTLD_DI_SERINFO` вимагає спочатку викликати `RTLD_DI_SERINFOSIZE`, виділити пам'ять потрібного розміру, і лише потім викликати `RTLD_DI_SERINFO`.

```c
typedef struct {
    size_t dls_size;           /* Загальний розмір буфера в байтах */
    unsigned int dls_cnt;      /* Кількість елементів у масиві dls_serpath */
    Dl_serpath dls_serpath[1]; /* Масив змінної довжини із записами шляхів */
} Dl_serinfo;

typedef struct {
    char *dls_name;            /* Абсолютний шлях до каталогу пошуку */
    unsigned int dls_flags;    /* Джерело походження шляху */
} Dl_serpath;
```

Значення поля `dls_flags` визначає джерело походження конкретного каталогу:

- `LA_SER_RPATH` (`0x01`): Каталог отримано з тегу `DT_RPATH`.
- `LA_SER_LIBPATH` (`0x02`): Каталог отримано зі змінної середовища `LD_LIBRARY_PATH`.
- `LA_SER_RUNPATH` (`0x04`): Каталог отримано з тегу `DT_RUNPATH`.
- `LA_SER_CONFIG` (`0x08`): Каталог отримано з кешу `/etc/ld.so.cache` або конфігурації `/etc/ld.so.conf`.
- `LA_SER_DEFAULT` (`0x40`): Стандартний системний каталог за замовчуванням (`/lib64`, `/usr/lib64`).

## 5. Безпечний режим AT_SECURE та secure_getenv

Операційна система Linux гарантує ізоляцію привілеїв при виконанні процесів із підвищеними правами. Для цього ядро під час виклику системного виклику `execve` формує у стеку нового процесу допоміжний вектор (Auxiliary Vector, `auxv`).

Одним із ключових елементів цього вектора є тег `AT_SECURE`:

```c
#include <sys/auxv.h>

unsigned long secure = getauxval(AT_SECURE);
```

Ядро виставляє `AT_SECURE = 1` у наступних чотирьох випадках:

1. **Зміна ідентифікатора користувача**: Ефективний UID процесу не збігається з реальним UID (`euid != ruid`).
2. **Зміна ідентифікатора групи**: Ефективний GID процесу не збігається з реальним GID (`egid != rgid`).
3. **Наявність capabilities**: Процес отримав додаткові привілеї через файлові можливості Linux Capabilities (наприклад, прапорці `setcap cap_net_raw+ep`).
4. **Спеціальні режими LSM**: Модуль безпеки Linux (AppArmor, SELinux) примусово наказав ядру активувати режим безпечного виконання.

### Функція secure_getenv

Для захисту від читання потенційно підроблених змінних оточення C-бібліотека надає функцію `secure_getenv()`:

```c
#define _GNU_SOURCE
#include <stdlib.h>

char *path = secure_getenv("LD_LIBRARY_PATH");
```

Якщо `getauxval(AT_SECURE)` повертає `0`, функція `secure_getenv()` працює точно так само, як і звичайна `getenv()`. Якщо ж `AT_SECURE == 1`, вона миттєво повертає `NULL`, запобігаючи використанню неконтрольованих даних користувача у привілейованому контексті.
