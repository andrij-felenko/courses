# ⚙️ Аудит ширини зсуву: обидві біди на власні очі

Тут зібрано чотири невеликі програми мовою C, які перетворюють розмову про ширину `off_t` на числа на екрані: перша каже, чим є `off_t` саме у вашій збірці й де стоїть стеля, друга створює тригігабайтний файл, не витрачаючи диска, третя показує, що перевірка при відкритті — знімок, а не гарантія, а четверта склеює дві одиниці трансляції з різною шириною зсуву й друкує неправильні числа, яких не помітили ані компілятор, ані компонувальник. Читати про розбіжність двійкової угоди й побачити, як функція отримує `back = 0` замість `4096`, — різні речі; друге запам'ятовується назавжди.

## Де це взагалі можна відтворити

Усе нижче має сенс **лише в 32-бітному просторі користувача**. На `x86-64` чи `arm64` `off_t` широкий від початку, `_FILE_OFFSET_BITS` не робить нічого, і всі дві збірки виявляться однаковими.

Найдешевший шлях на 64-бітній машині — попросити компілятор породити 32-бітний код:

```sh
$ sudo apt install gcc-multilib      # Debian/Ubuntu, для -m32 на amd64
$ cc -m32 hello.c -o hello
```

Для повноцінного досліду (з бібліотеками, `getconf`, пакунками) зручніший цілий 32-бітний простір користувача поверх того самого 64-бітного ядра — це працює завдяки [шару сумісності `compat`](root:sys-unix/compat-32-on-64), який перекладає 32-бітні системні виклики на внутрішні структури ядра:

```sh
$ docker run --rm -it --platform linux/386 debian:bookworm
# apt update && apt install -y gcc make coreutils
```

Третій варіант — справжня 32-бітна плата: `armv7`, роутер, промисловий контролер. Там числа будуть трохи інші (інша двійкова угода передавання аргументів), а висновки — ті самі.

## Частина перша: чим є `off_t` у ЦІЙ збірці

Перше, що треба вміти, — спитати програму про ширину її власного світу. Не подивитися в заголовки, не здогадатися з архітектури, а надрукувати.

Тут одразу спотикаються об дрібницю: **надрукувати `off_t` нічим**. Для нього немає ані окремої літери формату, ані макроса на кшталт `PRId64` — POSIX його не визначає, бо ширина типу невідома наперед. Портативний спосіб один: привести до `intmax_t` і друкувати через `%jd`. Так само немає й `OFF_MAX`, тож найбільше додатне значення доводиться обчислювати самому — і робити це так, щоб проміжний результат сам не переповнився:

```c
/* Найбільше додатне значення цілого типу зі знаком, без припущень про ширину
   й без переповнення: (1 << (N−2)) − 1, подвоїти, додати 1 = 2^(N−1) − 1. */
#define SIGNED_MAX(T) \
    ((T)(((((uintmax_t)1 << (sizeof(T) * CHAR_BIT - 2)) - 1) * 2) + 1))
```

Зсув на один менше за потрібний і подвоєння наприкінці тут не кокетство: вираз `(uintmax_t)1 << (N−1)` для найширшого типу вже вийшов би за межу, а так усі проміжні значення лишаються законними.

### Великий файл, який не займає місця

Щоб було на чому пробувати, потрібен файл понад 2 ГіБ. Записувати три гігабайти нулів безглуздо — вистачить [розрідженого файлу](root:sys-unix/sparse-files): файлова система запам'ятовує заявлений розмір, не виділяючи блоків під ділянки, у які ніхто не писав.

```sh
$ truncate -s 3G /var/tmp/big.bin
$ du -h --apparent-size /var/tmp/big.bin ; du -h /var/tmp/big.bin
3.0G	/var/tmp/big.bin
0	/var/tmp/big.bin
```

Заявлених три гігабайти, зайнятих — нуль. (Потрібна файлова система, яка вміє діри: `ext4`, `xfs`, `btrfs` уміють, `vfat` — ні, там `truncate` чесно запише всі три гігабайти або впаде.)

Те саме мовою C варте окремого погляду, бо в ньому ховається кільцева пастка: `ftruncate` теж приймає `off_t`, отже **програма, яка створює великий файл, сама мусить бути зібрана з широким зсувом** — інакше вона не назве потрібний розмір:

### Що друкують дві збірки

Вузька збірка на 32-бітній системі:

```
ширина типів у цій збірці
  sizeof(off_t)          = 4
  sizeof(struct stat)    = 88
  offsetof(stat,st_size) = 44
  найбільший зсув        = 2147483647
  _FILE_OFFSET_BITS      не визначено
  O_LARGEFILE            = 32768

файл: /var/tmp/big.bin
  open → Value too large for defined data type (errno=75)
  ← відмовило ЯДРО: розмір не вміщається в st_size цієї збірки
```

Широка збірка тих самих сирців, тим самим компілятором, на тій самій машині:

```
ширина типів у цій збірці
  sizeof(off_t)          = 8
  sizeof(struct stat)    = 96
  offsetof(stat,st_size) = 44
  найбільший зсув        = 9223372036854775807
  _FILE_OFFSET_BITS      = 64
  O_LARGEFILE            = 32768

файл: /var/tmp/big.bin
  open → успіх, fd=3
  st_size          = 3221225472
  st_blocks · 512  = 4096 (справді зайнято на носії)
  lseek(2147483648) → 2147483648
```

(Точні розміри `struct stat` залежать від libc і архітектури — у вашій системі числа можуть бути інші. Важить не величина, а те, що вони **різні**: одна й та сама структура має дві розкладки.)

Найцікавіше в цих двох виводах — те, чого у вузькому немає. Рядка про `lseek` там взагалі не буде, і не тому, що виклик не вдався. **Його не було.** Програма спинилася раніше: вона не змогла назвати ціль. І ще раніше не змогла відкрити файл — але то вже інша відмова, від іншої сторони.

## Три різні відмови, які легко сплутати

Розберімо їх нарізно, бо лікуються вони по-різному.

**Стеля у програмі.** Потрібного числа не існує в типі. Жодного системного виклику не відбувається, `errno` не змінюється, ядро про подію не знає. Симптом — не помилка, а мовчазно неправильна арифметика: обчислили зсув, він переповнився, отримали від'ємне число, і `lseek` слухняно повернув `EINVAL` про щось, чого ви не просили.

**Відмова ядра при відкритті.** Файл більший за `2³¹ − 1`, а програма не поставила `O_LARGEFILE` — ядро повертає `EOVERFLOW` (у Linux це `errno = 75`, а `strerror` перекладає його як «Value too large for defined data type»). Прапорець ставить не програміст: його додає libc, коли заголовки скомпільовано з широким зсувом.

**Відмова при роботі з уже відкритим файлом.** Ось тут ховається неочевидне: перевірка при `open` — це **знімок стану на мить відкриття**, а не гарантія на весь час життя дескриптора. Файл, відкритий вузькою збіркою, поки він був малий, може вирости під нею — і всі наступні дії почнуть спотикатися:

:::code proj-offset-audit/c/growprobe.c

```
$ : > /var/tmp/grow.bin
$ ./growprobe /var/tmp/grow.bin
відкрито; кінець файлу на 0
тепер розширте файл ЗЗОВНІ (truncate -s 3G /var/tmp/grow.bin) і тисніть Enter…
                                    ← у другому терміналі: truncate -s 3G …
lseek(SEEK_END) → -1, Value too large for defined data type
```

Виклик до ядра тут відбувся й повернув чесні три гігабайти — а не вмістила їх уже libc, на межі між ядром і програмою: результат не влазить у вузький `off_t`, і замість обрізаного числа вона віддає `EOVERFLOW`. Практичний наслідок: вузька програма, яка довго тримає відкритим файл журналу, зламається не при старті, а посеред ночі, коли журнал дорос до двох гігабайтів.

```sh
$ cc -m32 main.o audit.o -o mix-b
```

### Що вони друкують

Збірка A:

```
[main.c] sizeof(off_t)=8  sizeof(struct span)=16
  [audit.c] sizeof(off_t)=4  size=1000000  back=0
  tail_offset(1000000, 4096) → ‹щоразу інше велике число›   (мало бути 995904)
  [audit.c] sizeof(struct span)=12
  span: start=30064775168  records=1  truncated=0   (мало бути 4096/7/1)
```

Збірка B:

```
[main.c] sizeof(off_t)=4  sizeof(struct span)=12
  [audit.c] sizeof(off_t)=8  size=17592187044416  back=‹сміття зі стека›
  tail_offset(1000000, 4096) → ‹щоразу інше число›   (мало бути 995904)
  [audit.c] sizeof(struct span)=16
  span: start=4096  records=0  truncated=7   (мало бути 4096/7/1)
```

Кожне число тут можна порахувати рукою — і варто, бо саме в цьому рахунку зникає відчуття магії.

**Аргументи.** У двійковій угоді `i386` аргументи їдуть стеком, і восьмибайтове значення займає два слоти замість одного. У збірці A широкий `main.c` кладе `size` у два слоти, потім `back` ще у два. Вузький `audit.c` читає по одному слоту на аргумент: у `size` йому дістається молодша половина справжнього `size` (це випадково правильні 1000000), а в `back` — **старша половина того самого `size`**, тобто нуль. Функція, якій передали `4096`, бачить `0`. У збірці B все дзеркально: вузький викликач кладе по одному слоту на аргумент, а широкий приймач читає перший аргумент як два слоти й склеює з них одне 64-бітне число:

```
слот 1 = 1000000    (те, що клали як size)
слот 2 = 4096       (те, що клали як back)

широкий приймач читає обидва як одне 64-бітне число, молодший слот перший:
  size = 4096·2³² + 1000000
       = 17592186044416 + 1000000
       = 17592187044416
```

А другий аргумент широкий приймач бере зі слотів, яких викликач узагалі не заповнював, — там лежить те, що лишилося на стеку від попередніх дій. [Розкладка аргументів по регістрах і стеку](root:sf-lang/abi-calling-convention) для кожної архітектури своя: на `arm` восьмибайтові значення їдуть парами регістрів із вирівнюванням на парний номер, тож неправильні числа вийдуть інші — але неправильними вони будуть так само.

**Повернення.** Тут непередбачуваність повна. У збірці A вузька функція кладе результат у чотирибайтовий регістр, а широкий викликач читає пару регістрів — старша половина просто не заповнювалася. У збірці B навпаки: широка функція віддає повний результат, а вузький викликач бере лише молодшу половину. Те, що неправильне число **не відтворюється від запуску до запуску**, — саме по собі діагноз: ви читаєте пам'ять чи регістр, який ніхто не писав.

**Структура.** Оце — найгірше, і воно цілком детерміноване. У двійковій угоді `i386` восьмибайтове ціле вирівнюється на чотири байти (а не на вісім, як на `x86-64`), тож `struct span` виходить рівно 12 байтів у вузькій збірці й рівно 16 у широкій, без дірок. Далі — арифметика байтів:

```
збірка A: audit.c (12 байтів) записує, main.c (16 байтів) читає

  байти 0…3   ← start     = 4096
  байти 4…7   ← records   = 7
  байти 8…11  ← truncated = 1
  байти 12…15   ніхто не писав (main.c їх занулив)

  main.c читає start як 8 байтів, молодший спершу:
    start = 7·2³² + 4096 = 30064771072 + 4096 = 30064775168
  далі все зсунуте: records бере те, що було truncated (1),
  а truncated бере занулений хвіст (0)
```

![Один і той самий об'єкт у пам'яті: вузька збірка кладе start у байти 0…3, records у 4…7, truncated у 8…11 і пише 12 байтів; широка збірка читає start як байти 0…7, отримуючи 7·2³² + 4096, а решту полів бере зі зсувом; у зворотному напрямку широка збірка пише 16 байтів у 12-байтовий об'єкт і виходить за його межі](img/struct-byte-map.svg)

*Розбіжність ширини не «псує число» — вона зсуває всі поля після нього, а в один бік ще й виводить запис за межі об'єкта.*

Збірка B детермінована так само, і тим підступніша: `start` там **випадково правильний** (4096 вміщається в молодші чотири байти), тож побіжна перевірка «перше поле на місці — значить, працює» проходить успішно. Псуються поля, до яких дійшли пізніше.

І ще одне, страшніше за неправильні числа: у збірці B `fill_span` пише 16 байтів в об'єкт, який `main.c` створив на 12. Чотири байти лягають **за межі об'єкта** — це вже не хибне значення, а пошкодження чужої пам'яті. Щоб дослід не перетворився на випадкове падіння, зберіть `main.c` із `-fsanitize=address`: [санітайзер адрес](root:sf-release/address-sanitizer) назве і місце запису, і кількість зайвих байтів.

## Чому компонувальник має право мовчати

Причина не в лінощах інструмента, а в тому, чим є символ у C. [Компонувальник зіставляє визначення з викликами винятково за іменем](root:sys-unix/symbol-resolution): у таблиці об'єктного файлу лежить рядок `tail_offset` і адреса — типів аргументів там немає й ніколи не було. Кожна [одиниця трансляції](root:sf-lang/translation-unit) компілюється окремо, кожна вірить своєму заголовку, а прапорець препроцесора діє рівно в межах одного проходу — тож `audit.o` і `main.o` мають різне уявлення про той самий заголовок і жодного способу дізнатися про це.

Для функцій самої libc біди немає, і причина повчальна: там кожній ширині відповідає **своє ім'я**. Під широким прапорцем заголовки glibc перенаправляють `lseek` у символ `lseek64`, `open` у `open64` і так далі. Розбіжність ширини перетворюється на розбіжність імен, а її компонувальник уже бачить.

Це дає готовий інструмент аудиту: імена, які об'єктний файл вимагає ззовні, і є свідченням того, з якими прапорцями його зібрано.

```sh
$ cc -m32 -c offsetprobe.c -o narrow.o
$ cc -m32 -D_FILE_OFFSET_BITS=64 -c offsetprobe.c -o wide.o

$ nm -u narrow.o | grep -E 'lseek|open'
                 U lseek
                 U open
$ nm -u wide.o   | grep -E 'lseek|open'
                 U lseek64
                 U open64
```

Той самий прийом працює на готовому виконуваному файлі чи бібліотеці: `nm -D --undefined-only ./prog | grep 64$` показує, чи звертається двійковий файл до широких інтерфейсів. Це не доводить, що *ваші* функції узгоджені, — але одразу викриває змішану збірку в проєкті, де половина об'єктних файлів кличе `lseek`, а половина `lseek64`.

## Як зробити так, щоб мовчання скінчилося

Три засоби, від найдешевшого до найнадійнішого.

**Один прапорець на весь проєкт, узятий у системи.** Це не порада, а єдиний спосіб, у якому взагалі немає ризику: макрос [належить прапорцям збирання](root:sys-bsystem/build-flags), а не рядкові `#define` у якомусь одному файлі. Джерело значення теж не слід вигадувати — його віддає `getconf`:

```make
CFLAGS := -m32 -Wall -Wextra -g $(shell getconf LFS_CFLAGS)

all: probe makebig
probe:   offsetprobe.c ; $(CC) $(CFLAGS) $< -o $@
makebig: makebig.c     ; $(CC) $(CFLAGS) $< -o $@
```

Якщо ваш код — бібліотека, чиї публічні заголовки згадують `off_t`, прапорець мусить діставатися ще й **усім, хто з вами лінкується**, бо двійкова угода спільна. У CMake це [вимога вживання](root:sys-bsystem/usage-requirements), а не приватна властивість цілі:

```cmake
# PUBLIC, не PRIVATE: цей макрос — частина нашої двійкової угоди
target_compile_definitions(audit PUBLIC _FILE_OFFSET_BITS=64)
```

**Перевірка під час компіляції.** Дисципліна ламається; хай тоді ламається збірка, а не поведінка. Система збирання бібліотеки записує свій вибір у згенерований заголовок, а публічний заголовок звіряється з ним:

```c
/* audit-config.h — генерує система збирання під час встановлення бібліотеки */
#define AUDIT_OFF_T_SIZE 8
```

```c
/* audit.h */
#include "audit-config.h"
#include <sys/types.h>

_Static_assert(sizeof(off_t) == AUDIT_OFF_T_SIZE,
    "audit зібрано з off_t іншої ширини: додайте `getconf LFS_CFLAGS` до CFLAGS");
```

[Статичне твердження](root:sf-lang/static-assert) обчислюється компілятором і нічого не коштує під час виконання. Тепер розбіжність, яку компонувальник не помічав, стає помилкою компіляції з осмисленим текстом. На 64-бітних платформах перевірка інертна — `off_t` там широкий завжди, — і саме тому її варто ставити: вона нічого не заважає, доки не з'явиться 32-бітна ціль.

**Оптимізація на етапі компонування як побічний детектор.** Коли обидві одиниці трансляції зібрано з `-flto` і зліплено теж з `-flto`, GCC порівнює типи глобальних оголошень із різних одиниць і попереджає про розбіжність (`-Wlto-type-mismatch`, увімкнене за замовчуванням):

```sh
$ cc -m32 -flto -D_FILE_OFFSET_BITS=64 -c main.c  -o main.o
$ cc -m32 -flto                        -c audit.c -o audit.o
$ cc -m32 -flto main.o audit.o -o mix-lto
audit.h:12:7: warning: type of 'tail_offset' does not match original declaration
```

Засіб корисний, але не рятівний: він вимагає, щоб **увесь** код проходив через LTO, а з наперед зібраною системною бібліотекою це не працює за побудовою.

## І окремо — власні формати

Останній висновок із усього досліду не про збирання, а про дані. Ширина `off_t` є властивістю **збірки**, а не файлу. Отже, у форматі, який записують на диск чи шлють у мережу, цьому типу не місце: сторона, що пише, і сторона, що читає, — це знову дві незалежні збірки, тільки цього разу між ними ще й час і мережа.

```c
struct index_entry {
    int64_t  offset;    /* саме так: ширина не залежить ні від чиїх прапорців */
    int64_t  length;
    uint32_t flags;
} __attribute__((packed));
```

Тип `int64_t` із `<stdint.h>` має рівно шістдесят чотири біти на будь-якій платформі, де він взагалі існує. Порядок байтів усередині поля так само треба задати явно ([розкладка полів у форматі](root:com-protocol/wire-format-packing) — окрема тема з власними пастками вирівнювання й доповнення), але принцип уже видно: у пам'яті процесу зсув має природну ширину платформи, а на носії — оголошену ширину формату, і перетворення між ними робиться явно, у місці, де його видно.

> 🔧 **Навіщо це.** Аудит змішаної збірки зводиться до трьох команд і однієї вставки в заголовок: `getconf LFS_CFLAGS` — щоб узяти правильний прапорець, `nm -u *.o | grep -E 'lseek|open'` — щоб побачити, чи всі об'єктні файли говорять однією мовою, `_Static_assert(sizeof(off_t) == …)` — щоб наступного разу зламалася збірка, а не поведінка. Усе інше — вміння прочитати `EOVERFLOW` як «стеля в програмі, а не на диску».
