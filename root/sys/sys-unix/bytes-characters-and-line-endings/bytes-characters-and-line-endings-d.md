Адміністратор налаштовує автоматичний сценарій розгортання на сервері Ubuntu Linux. Сценарій створюється на робочій станції у Windows, передається через Git або SCP і запускається командою `./deploy.sh`. Замість виконання оновлення термінал повертає помилку:

```sh
$ ./deploy.sh
bash: ./deploy.sh: /bin/bash^M: bad interpreter: No such file or directory
```

Адміністратор перевіряє наявність файлу `/bin/bash` — він на місці, має права `rwxr-xr-x` і працює бездоганно. Проте системний виклик `execve()` відхиляє запуск сценарію, оскільки з погляду ядра Linux шлях до інтерпретатора складається не з 9 символів `/bin/bash`, а з 10 байтів `/bin/bash\r`, де останній байт — це невидимий символ повернення каретки `0x0D` (Carriage Return). Файлу з таким іменем на диску не існує.

Цей збій викриває фундаментальний принцип архітектури Unix: операційна система оперує виключно неінтерпретованими масивами байтів (байтовими потоками). Поняття «символ», «рядок», «кодування» та «вирівнювання колонок» не існують усередині ядра — вони є абстракціями простору користувача, бібліотеки `libc`, термінальних емуляторів та прикладних парсерів.

## 1. Байти проти символів: де пролягає межа ядра

Усі системні виклики вводу-виводу в Linux та POSIX — `open()`, `read()`, `write()`, `rename()`, `stat()`, `execve()` — приймають аргументи у вигляді покажчиків `const char*` або `const void*` разом із лічильником довжини `size_t count`.

Для віртуальної файлової системи (VFS) та дискових драйверів (ext4, XFS, Btrfs) будь-який файл — це лінійний масив 8-бітних октетів (`uint8_t[]`). Ядро не знає, чи містить цей масив текст англійською мовою в ASCII, український текст у UTF-8, японські ієрогліфи в Shift-JIS, скомпільований бінарний образ ELF чи стиснений архів tar.gz.

![Архітектурний розподіл обов'язків між простором користувача та ядром](/root/sys/sys-unix/bytes-characters-and-line-endings/img/kernel-opaque-bytes.svg)

*Ядро оперує «сліпим» потоком байтів і знає лише роздільники NUL та косу риску; інтерпретація в символи та гліфи відбувається суто у просторі користувача.*

У просторі імен файлової системи ядро контролює рівно два спеціальні байти:

1. **Байт `0x00` (NUL, `\0`):** Завершувач рядка у мові C. Він сигналізує ядру про закінчення шляху або аргументу в системному виклику. Через це байт `0x00` є єдиним октетом, який принципово не може бути частиною імені файлу або каталогу.
2. **Байт `0x2F` (`/`, коса риска):** Роздільник компонентів ієрархічного шляху у VFS. Він відокремлює назву батьківського каталогу від дочірнього елемента.

Усі інші 254 значення байтів (від `0x01` до `0x2E` та від `0x30` до `0xFF`) ядро записує у каталог дослівно. Ви можете створити файл, ім'я якого містить символи табуляції, повернення каретки `\r`, символ нового рядка `\n`, керівні escape-послідовності ANSI для зміни кольору термінала або некоректні уривки UTF-8. З погляду ядра це валідний 8-бітний ідентифікатор запису каталогу (`dentry`).

### Три рівні абстракції: байт, кодова точка, гліф

Плутанина між довжиною даних і кількістю знаків виникає через змішування трьох різних понять:

- **Байт (Byte / Octet):** Фізична одиниця зберігання інформації, що складається з 8 бітів (значення від `0` до `255`, або від `0x00` до `0xFF`). Саме байти рахують системні виклики `read()` та функція `strlen()`.
- **Кодова точка (Unicode Code Point):** Абстрактний числовий номер символу в просторі стандартів Unicode (від `U+0000` до `U+10FFFF`). Наприклад, літера «ї» — це кодова точка `U+0457`.
- **Гліф (Glyph):** Візуальне зображення символу на екрані чи папері, що малюється растровим або векторним рушієм шрифтів.

Один гліф може складатися з кількох кодових точок (графема, grapheme cluster), а одна кодова точка може кодуватися кількома байтами.

Розглянемо рядок `Привіт`:
- Кількість візуальних гліфів (символів на екрані): 6.
- Кількість кодових точок Unicode: 6 (`U+041F`, `U+0440`, `U+0438`, `U+0432`, `U+0456`, `U+0442`).
- Кількість байтів у пам'яті (UTF-8): 12 (`D0 9F D1 80 D0 B8 D0 B2 D1 96 D1 82`).

```sh
$ str="Привіт"
$ echo -n "$str" | wc -m    # Рахує символи (кодові точки) відповідно до LC_CTYPE
6
$ echo -n "$str" | wc -c    # Рахує сирі байти
12
```

Якщо програма на C виділяє буфер під рядок як `malloc(strlen(s) + 1)`, вона виділяє 13 байтів (12 байтів даних + 1 байт NUL), що коректно для зберігання. Проте якщо утиліта форматування тексту обчислює позицію табуляції в терміналі через `strlen()`, вона припустить, що слово займає 12 колонок замість 6, і таблиця на екрані перекоситься. Для обчислення екранної ширини символів у просторі користувача призначена бібліотечна функція `wcwidth()` або `wcswidth()`, яка враховує нульову ширину комбінованих діакритичних знаків та подвійну ширину східноазійських ієрогліфів.

## 2. Архітектура кодування UTF-8: перемога в екосистемі Unix

На початку 1990-х років консорціум Unicode запропонував 16-бітне фіксоване кодування UCS-2 (яке згодом еволюціонувало в UTF-16). Корпорація Microsoft інтегрувала UCS-2 у ядро Windows NT, компанія Sun Microsystems — у мову Java, а Apple — у середовище NeXTSTEP/Cocoa.

Це рішення породило важку проблему зворотної сумісності. У 16-бітному кодуванні кожен звичайний латинський символ ASCII вимагав двох байтів (наприклад, літера `'A'` записувалася як `0x00 0x41` або `0x41 0x00`). Нульовий байт `0x00` з'являвся всередині кожного другого символу. Для системних викликів Unix, стандартної бібліотеки C та всіх утиліт обробки тексту (`grep`, `sed`, `awk`, `cat`) нульовий байт означав миттєве дострокове завершення рядка. Перехід на UTF-16 вимагав би повної перезбірки та переписування ядра Unix і мільйонів рядків наявного коду.

У вересні 1992 року Кен Томпсон і Роб Пайк (творці Unix і операційної системи Plan 9) під час вечері в ресторані спроєктували нове кодування, яке отримало назву **UTF-8** (Universal Character Set Transformation Format — 8-bit).

![Структура кодування UTF-8 та бітові діапазони](/root/sys/sys-unix/bytes-characters-and-line-endings/img/utf8-byte-layout.svg)

*Структура октетів у кодуванні UTF-8: старші біти першого байта визначають загальну довжину, а біти 10xxxxxx гарантують самосинхронізацію.*

### Чотири інженерні властивості UTF-8

1. **Абсолютна сумісність з 7-бітним ASCII:** Будь-який символ з кодом від `0` до `127` (`U+0000`..`U+007F`) кодується рівно одним байтом зі старшим бітом `0` (`0xxxxxxx`). Будь-який існуючий файл ASCII є на 100% валідним файлом UTF-8.
2. **Прозорість системних символів:** Жоден мультибайтовий символ не містить у своєму складі байтів зі значенням менше `128` (`0x80`). Це означає, що байт `0x00` (NUL), байт `0x2F` (`/`), пробіл `0x20` чи `\n` (`0x0A`) ніколи не можуть з'явитися всередині або наприкінці іншого юнікодного символу. Утиліти VFS та парсери шляхів можуть безпечно шукати косу риску або нульовий байт звичайними функціями `strchr()` чи `memchr()`, не декодуючи весь текст.
3. **Самосинхронізація (Self-synchronization):** За будь-яким окремим байтом у потоці можна миттєво визначити його роль:
   - `0xxxxxxx` (`0x00`..`0x7F`) — одиночний 1-байтовий символ ASCII.
   - `110xxxxx` (`0xC0`..`0xDF`) — початок 2-байтової послідовності.
   - `1110xxxx` (`0xE0`..`0xEF`) — початок 3-байтової послідовності.
   - `11110xxx` (`0xF0`..`0xF7`) — початок 4-байтової послідовності.
   - `10xxxxxx` (`0x80`..`0xBF`) — байт-продовження (continuation byte).

   Якщо під час передачі через мережу чи пошкоджений файл один байт загубився або спотворився, декодер не втрачає зв'язку з усім подальшим текстом. Достатньо пропустити пошкоджені байти до найближчого октету, що не починається з префікса `10`, щоб відновити читання з наступного валідного символу.
4. **Збереження порядку байтового порівняння:** Якщо дві кодові точки порівняти чисельно (`cp1 < cp2`), лексикографічне побайтове порівняння їхніх UTF-8 представлень функцією `strcmp()` чи `memcmp()` дасть точно такий самий результат.

### Правила валідації та заборона наддовгих послідовностей

Кодування кожної кодової точки в UTF-8 має бути мінімально можливим. Теоретично кодову точку `U+002F` (`/`) можна було б записати двома байтами: `11000000 10101111` (`0xC0 0xAF`). Це називається **наддовгим кодуванням** (overlong encoding).

Наддовгі кодування становлять критичну загрозу безпеці. Якщо міжмережевий екран або шлюз перевіряє шлях на заборонену послідовність `../` за байтами `0x2F`, він пропустить послідовність `0xC0 0xAF`. Якщо бекенд-додаток потім декодує `0xC0 0xAF` у `/`, атакуючий успішно обійде перевірку безпеки (це викликало знамениті вразливості обходу каталогів на початку 2000-х).

Стандарт RFC 3629 суворо забороняє наддовгі послідовності:
- Стартові байти `0xC0` та `0xC1` вважаються повністю невалідними.
- Послідовності, що декодуються у сурогатні пари UTF-16 (`U+D800`..`U+DFFF`), є невалідними.
- Кодові точки, більші за `U+10FFFF` (стартові байти від `0xF5` до `0xFF`), є невалідними.

Повний алгоритм побайтової валідації з аналізом бітових масок та тестів на безпеку розібрано у проекті [Швидкий валідатор UTF-8 та санітайзер рядків](root:sys-unix/bytes-characters-and-line-endings/proj-utf8-validator.md).

## 3. Маркер порядку байтів (BOM) і катастрофа Shebang

У кодуваннях UTF-16 та UTF-32 одиниці кодування мають розмір 16 або 32 біти. Залежно від архітектури процесора (Little-Endian на x86/ARM або Big-Endian на SPARC/MIPS) два байти одного 16-бітного слова можуть записуватися на диск у різному порядку:

- Старший байт спочатку (Big-Endian, BE): `0xFE 0xFF`.
- Молодший байт спочатку (Little-Endian, LE): `0xFF 0xFE`.

Щоб програми могли автоматично визначати порядок байтів у файлі, у стандарт Unicode було введено спеціальну кодову точку `U+FEFF` — **маркер порядку байтів** (Byte Order Mark, BOM, або Zero Width No-Break Space). Якщо програма читає на початку файлу байти `0xFF 0xFE`, вона знає, що файл збережено у UTF-16LE.

### Чому BOM у UTF-8 є технічною помилкою

У кодуванні UTF-8 базовою одиницею є 8-бітний байт. Порядок слів у пам'яті процесора ніяк не впливає на потік байтів: послідовність байтів у UTF-8 завжди однакова на всіх архітектурах. Тому UTF-8 не потребує жодного маркера порядку байтів.

Проте редактори у середовищі Windows (зокрема «Блокнот» / Notepad) історично почали додавати кодову точку `U+FEFF`, закодовану в UTF-8 як три байти `0xEF 0xBB 0xBF`, на початок кожного текстового файлу, щоб відрізняти UTF-8 від успадкованих кодових сторінок ANSI (наприклад, Windows-1251).

Для систем Unix поява трьох байтів `\xEF\xBB\xBF` на початку файлу призводить до катастрофічних наслідків у роботі сценаріїв.

### Як ядро Linux завантажує виконувані скрипти

Коли процес викликає системний виклик `execve("/path/to/script.sh", argv, envp)`, керування передається у функцію ядра `do_execveat_common()`. Ядро відкриває файл і зчитує його перші 256 байтів у буфер `bprm->buf`.

Далі ядро перебирає зареєстровані обробники виконуваних форматів (`struct linux_binfmt`). Один із них — обробник текстових сценаріїв `binfmt_script.c`:

```text
/* Фрагмент ядра Linux: fs/binfmt_script.c */
static int load_script(struct linux_binprm *bprm)
{
    const char *i_name, *i_sep, *i_arg, *i_end, *cp;
    
    /* Перевірка рівно перших двох байтів магічного числа: '#' та '!' */
    if ((bprm->buf[0] != '#') || (bprm->buf[1] != '!'))
        return -ENOEXEC;
    
    /* ... розбір шляху інтерпретатора після #! ... */
}
```

Обробник перевіряє рівно перші два байти:
- Якщо `bprm->buf[0] == '#'` (`0x23`) та `bprm->buf[1] == '!'` (`0x21`), файл визнається скриптом. Ядро витягує шлях до інтерпретатора (наприклад, `/bin/bash`) і просить підсистему завантажити цей інтерпретатор, передавши йому шлях до скрипту як аргумент.
- Якщо на початку файлу стоїть маркер BOM, перші байти буфера мають значення `0xEF 0xBB 0xBF 0x23 0x21`. Перші два байти — це `0xEF 0xBB`.

```
Файл без BOM:    [ 0x23 ] [ 0x21 ] [ 0x2F ] [ 0x62 ] ...  -->  #! / b ...  (УСПІХ)
Файл з BOM:      [ 0xEF ] [ 0xBB ] [ 0xBF ] [ 0x23 ] ...  -->  ... # ...   (ЗБІЙ)
```

Ядро бачить, що перші два байти не збігаються з `#!`, відхиляє формат із кодом помилки `-ENOEXEC` (Exec format error) і намагається перевірити інші формати (ELF, binfmt_misc). Коли жоден бінарний завантажувач не впізнає файл, `execve()` повертає помилку. Якщо запуск виконувався з термінала Bash, оболонка намагається інтерпретувати файл самостійно, розглядаючи перші байти як команду. У результаті оболонка намагається виконати бінарне сміття і видає помилку синтаксису.

Виявити наявність BOM можна утилітою `file` або `hexdump -C`:

```sh
$ file script.sh
script.sh: UTF-8 Unicode (with BOM) text executable

$ hexdump -C script.sh | head -n 1
00000000  ef bb bf 23 21 2f 62 69  6e 2f 62 61 73 68 0a     |...#!/bin/bash.|
```

Видалення BOM виконується утилітою `dos2unix -r` або потоковим редактором `sed -i '1s/^\xEF\xBB\xBF//' script.sh`.

## 4. Війна кінців рядків: LF проти CRLF

Історичне розділення стандартів перенесення рядків бере свій початок у конструкції електромеханічних телепринтерів 1960-х років, де для нового рядка були потрібні дві фізичні операції: повернення каретки (Carriage Return, CR, `0x0D`, `\r`) та прокручування валика з папером (Line Feed, LF, `0x0A`, `\n`). Детальний розбір механіки телетайпа Teletype Model 33 та економічних причин вибору Bell Labs наведено у вставці [Механіка каретки: як телетайп визначив кінець рядка](root:sys-unix/bytes-characters-and-line-endings/hist-line-ending-wars.md).

У результаті світ інформаційних технологій розколовся на два табори:
- **Unix / Linux / macOS (починаючи з OS X):** використовує один байт **LF** (`\n`, `0x0A`).
- **CP/M / MS-DOS / Microsoft Windows:** використовує пару байтів **CRLF** (`\r\n`, `0x0D 0x0A`).
- **Classic Mac OS (до версії 9):** використовував один байт **CR** (`\r`, `0x0D`).

![Механіка кінців рядків і пастка shebang](/root/sys/sys-unix/bytes-characters-and-line-endings/img/line-ending-mechanics.svg)

*Фізичні керуючі коди телетайпа та системний збій під час пошуку інтерпретатора з байтом `\r` в ядрі Linux.*

### Як символ `\r` руйнує роботу в середовищі Linux

Коли текстовий файл з кінцями рядків Windows CRLF потрапляє в Linux, для утиліт Unix символ `\r` (`0x0D`) не є частиною синтаксису кінця рядка. Для них кінець рядка — це виключно байт `\n` (`0x0A`). Тому `\r` сприймається як звичайний літерний символ, що стоїть останнім у рядку.

Це викликає чотири класичні інженерні збої:

#### 1. Помилка пошуку інтерпретатора (Bad Interpreter)

Якщо перший рядок сценарію містить `#!/bin/sh\r\n`, парсер ядра `fs/binfmt_script.c` зчитує шлях до інтерпретатора від символу `#!` аж до першого знайденого байта `\n`. Оскільки `\r` стоїть перед `\n`, він включається до рядка шляху:

```text
/* Ядро намагається відкрити файл: */
sys_open("/bin/sh\r", O_RDONLY);
```

Файлова система шукає бінарний файл з 8-байтовим іменем `sh\r`. Такого файлу не існує, і системний виклик повертає код помилки `ENOENT` (No such file or directory). Оболонка виводить користувачеві повідомлення:

```sh
$ ./test.sh
bash: ./test.sh: /bin/sh^M: bad interpreter: No such file or directory
```

Символ `^M` — це термінальне позначення коду `Ctrl+M` (код ASCII 13, тобто `\r`).

#### 2. Перетирання тексту та пошкодження виводу в терміналі

Коли термінальний емулятор отримує байт `\r`, він повертає курсор у крайній лівий стовпець поточного рядка без переходу вниз. Якщо скрипт формує рядок або виводить змінну, що закінчується на `\r`, весь наступний текст перетирає початок рядка:

```sh
$ host=$(printf "server-01\r")
$ echo "Connecting to host: $host... Failed!"
... Failed!ing to host: server-01
```

Рядок `... Failed!` надрукувався з нульової позиції поверх фрази `Connecting to host: server-01`. Для налагодження таких виводів потік слід перенаправити у `cat -v` або `od -c`:

```sh
$ echo "Connecting to host: $host... Failed!" | cat -v
Connecting to host: server-01^M... Failed!
```

#### 3. Збій регулярних виразів у grep, sed та awk

Утиліти фільтрації прив'язують якір кінця рядка `$` до символу `\n`. Якщо рядок завершується на `\r\n`, вираз `error$` шукає слово `error`, за яким одразу йде `\n`. Але у файлі стоїть `error\r\n`, тому шаблон ніколи не спрацьовує:

```sh
# Файл містить рядок "FATAL ERROR\r\n"
$ grep "ERROR$" logs_windows.txt    # Нічого не повертає!
$ grep "ERROR\r$" logs_windows.txt  # Знаходить рядок
```

#### 4. Некоректні аргументи у конфігураційних файлах

Якщо сервіс читає конфігураційний файл рядок за рядком через функцію `fgets()`, рядок `port=8080\r` розбирається як значення порту `"8080\r"`. Функція `atoi("8080\r")` може випадково спрацювати, але виклик `gethostbyname("localhost\r")` зазнає повної невдачі.

### Методи лікування та санітизації кінців рядків

Для усунення символів `\r` застосовуються спеціалізовані утиліти, системні фільтри або конфігурація контролю версій. Зведений опис параметрів та поведінки інструментів наведено в довіднику [Інструменти потокової обробки: кодування, кінці рядків і NUL-роздільники](root:sys-unix/bytes-characters-and-line-endings/api-text-stream-tools.md).

Найпоширеніші команди для щоденної роботи:

```sh
# 1. Спеціалізована утиліта (рекомендовано для файлів на диску)
dos2unix filename.sh

# 2. Потоковий редактор sed (видаляє \r лише наприкінці рядка)
sed -i 's/\r$//' filename.sh

# 3. Швидкий фільтр tr у конвеєрі (видаляє всі входження \r)
tr -d '\r' < input.txt > output.txt
```

У спільних Git-репозиторіях для запобігання потраплянню CRLF у кодову базу обов'язково налаштовують файл `.gitattributes` у корені проєкту:

```gitattributes
# Автоматична нормалізація всіх текстових файлів
* text=auto

# Примусовий формат LF для всіх сценаріїв оболонок
*.sh text eol=lf
*.bash text eol=lf
```

## 5. Нульовий байт як єдиний надійний роздільник у конвеєрах

Головний інтерфейс взаємодії між програмами в Unix — це конвеєр текстових рядків, розділених символом нового рядка `\n` (`0x0A`).

Проте у файлових операціях виникає фундаментальна небезпека: **символ `\n` є валідним байтом у назвах файлів Unix**. Крім того, імена файлів часто містять пробіли, табуляції, лапки (`"`, `'`), зворотні косі риски (`\`) та символи підстановки.

![Конвеєри: небезпека перенесення рядків проти NUL-роздільника](/root/sys/sys-unix/bytes-characters-and-line-endings/img/nul-separated-pipeline.svg)

*Порівняння конвеєрів: стандартний поділ за пробілами/переносами рядків руйнує дані; потік із NUL-роздільником гарантує цілісність.*

### Катастрофа наївного конвеєра: `find | xargs`

Розглянемо типову команду автоматичного очищення тимчасових каталогів:

```sh
find /tmp/uploads -type f -name "*.tmp" | xargs rm
```

Якщо користувач створив файл з іменем `my report 2026.tmp`, утиліта `find` виведе в конвеєр один рядок: `/tmp/uploads/my report 2026.tmp\n`.

Утиліта `xargs` за замовчуванням розбиває вхідний потік на окремі аргументи за будь-якими пробільними символами (пробіл, табуляція, `\n`). У результаті `xargs` виконає команду:

```sh
rm /tmp/uploads/my report 2026.tmp
```

Команда `rm` спробує видалити три незалежні файли: `/tmp/uploads/my`, `report` та `2026.tmp`. Якщо файл з іменем `report` випадково існував у поточному каталозі, він буде безповоротно знищений.

Ще небезпечнішим є випадок, коли зловмисник створює файл з іменем `-rf /\n.tmp` або файл, що містить лапки. Утиліта `xargs` інтерпретує лапки як групування, повідомить про помилку синтаксису `xargs: unmatched single quote` і пропустить видалення файлів або виконає непередбачувану дію.

### NUL-роздільники: `-print0` та `xargs -0`

Єдиним байтом, який на 100% гарантовано не може зустрітися в імені файлу Unix за специфікацією POSIX, є нульовий байт `0x00` (NUL).

Для побудови безпечних конвеєрів стандартні утиліти Unix підтримують режим нульового роздільника:

```sh
# find виводить записи, розділені байтом 0x00
# xargs -0 розбиває аргументи виключно по байту 0x00
find /tmp/uploads -type f -name "*.tmp" -print0 | xargs -0 rm -f
```

Коли `find -print0` передає файл `my report 2026.tmp\0`, утиліта `xargs -0` зчитує весь блок даних між сусідніми `\0` як єдиний неподільний рядок і передає його у системний виклик `execve()` як один елемент масиву `argv`:

```
argv[0] = "rm"
argv[1] = "-f"
argv[2] = "/tmp/uploads/my report 2026.tmp"
argv[3] = NULL
```

Жоден пробіл, символ перенесення рядка чи лапка всередині імені не розривають аргумент.

### NUL-конвеєри в інших утилітах

Сучасний набір утиліт Linux надає системні прапорці для наскрізної обробки NUL-потоків:

- **Сортування (`sort -z`):** Дозволяє коректно сортувати шляхи, навіть якщо вони містять переноси рядків:
  ```sh
  find . -type f -print0 | sort -z | xargs -0 -r md5sum
  ```
- **Фільтрація (`grep -Z` або `grep -lZ`):** Виводить нульовий байт після імені файлу:
  ```sh
  grep -lZ "CONFIDENTIAL" /docs/* | xargs -0 -r chmod 600
  ```
- **Вибірка полів (`cut -z`):** Працює з записами, розділеними `\0`:
  ```sh
  find /var/backups -maxdepth 2 -print0 | cut -z -d '/' -f 4-
  ```
- **Читання в циклах оболонки (`read -d ''`):**
  ```sh
  while IFS= read -r -d '' filepath; do
      printf "Обробка файлу: %s\n" "$filepath"
  done < <(find . -type f -name "*.dat" -print0)
  ```

### Системне читання NUL-розділених потоків у C та C++

У системних програмах читання NUL-розділеного потоку з дескриптора файлу або каналу реалізується за допомогою функції `getdelim()` (POSIX.1-2008) або потокових ітераторів C++.

:::tabs
```c
/* read_nul_stream.c — Безпечне читання NUL-розділеного потоку через getdelim().
 * Збірка: cc -std=c99 -Wall -Wextra -O2 read_nul_stream.c -o read_nul_stream
 */

#define _POSIX_C_SOURCE 200809L
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void) {
    char *entry = NULL;
    size_t cap = 0;
    ssize_t len;
    size_t count = 0;

    /* Читання потоку stdin з роздільником NUL (байт 0x00) */
    while ((len = getdelim(&entry, &cap, '\0', stdin)) != -1) {
        count++;
        printf("[%zu] Запис (%zd байтів): %s\n", count, len, entry);
    }

    free(entry);
    return 0;
}
```
```cpp
// read_nul_stream.cpp — Безпечне читання NUL-потоку в C++20.
// Збірка: g++ -std=c++20 -Wall -Wextra -O2 read_nul_stream.cpp -o read_nul_stream

#include <iostream>
#include <string>
#include <vector>

int main() {
    // Вимикаємо синхронізацію з stdio для максимальної швидкості
    std::ios_base::sync_with_stdio(false);
    std::cin.tie(nullptr);

    std::string entry;
    size_t count = 0;

    // Читаємо стандартний ввід до кожного знайденого нульового байта '\0'
    while (std::getline(std::cin, entry, '\0')) {
        ++count;
        std::cout << '[' << count << "] Запис (" << entry.size() << " байтів): " 
                  << entry << '\n';
    }

    return 0;
}
```

## 6. Інженерний підсумок: залізна дисципліна текстових інтерфейсів

Щоб системні конвеєри, сценарії розгортання та утиліти обробки даних у Linux працювали передбачувано і без збоїв, інженер повинен дотримуватися п'яти правил:

1. **Пам'ятати про сліпоту ядра:** Ядро оперує сирими октетами `char*`. Перетворення між байтами, кодовими точками та гліфами контролюється суто простором користувача і локаллю `LC_CTYPE`.
2. **UTF-8 як єдиний канон:** Усі текстові файли, змінні оточення та протоколи конвеєрів повинні зберігатися у кодуванні UTF-8 без використання наддовгих послідовностей та сурогатів.
3. **Жодного BOM у Linux:** Маркер `\xEF\xBB\xBF` є неприпустимим у текстових конфігураціях та сценаріях, оскільки він ламає парсинг заголовка shebang `#!` у системному виклику `execve()`.
4. **Суворий LF для кінців рядків:** Усі сценарії оболонок та конфігураційні файли повинні мати завершувач `\n` (`0x0A`). Для запобігання потраплянню `\r` репозиторії мають фіксувати правила через `.gitattributes`.
5. **NUL-роздільники для шляхів:** Будь-який конвеєр масової обробки файлів зобов'язаний використовувати нульовий байт як роздільник записів (`find -print0 | xargs -0`), що виключає вразливості та помилки при наявності пробілів і спецсимволів в іменах.
