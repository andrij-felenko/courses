# 📜 Механіка каретки: як телетайп визначив кінець рядка

У середині XX століття термінал не мав екрана, графічного процесора чи кадрового буфера. Терміналом був електромеханічний телепринтер — апарат на зразок Teletype Model 33 ASR (виробництва Teletype Corporation, 1963 рік), який друкував символи фарбувальною стрічкою безпосередньо на рулонному папері. Швидкість передачі становила 110 бод, тобто 10 символів за секунду (100 мілісекунд на один знак).

Кожен надрукований рядок вимагав двох незалежних механічних дій від машини.

Перша дія — обертання гумового валика (platen), який підтягував папір угору на один крок, звільняючи місце для наступного рядка тексту. Ця дія називалася **подачею рядка** (Line Feed, код ASCII `0x0A`, `\n`). Вона виконувалася відносно легко й займала приблизно один цикл передачі (до 100 мс).

Друга дія — повернення масивного друкуючого вузла або каретки (carriage) з правого краю сторінки в крайній лівий початок рядка. Ця дія називалася **поверненням каретки** (Carriage Return, код ASCII `0x0D`, `\r`). На відміну від валика, каретка мала помітну масу та механічну інерцію: сталевий вузол приводився в рух поворотною пружиною або тросиком під дією електромагнітної муфти. Щоб повернутися з 72-ї колонки на 0-ву позицію, каретці було потрібно від 150 до 250 мілісекунд.

```
+----------------------------------------------------------------+
|  Паперовий валик: LF (0x0A) прокручує папір униз на 1 рядок    |
|  Каретка:         CR (0x0D) тягне друкуючу голівку ліворуч     |
+----------------------------------------------------------------+
```

Якщо телетайп отримував наступний літерний символ до того, як каретка доїхала до лівого упору, друкуючий молоточок бив по паперу прямо під час руху. У результаті перші кілька літер нового рядка лягали одна на одну по діагоналі в центрі сторінки, утворюючи нерозбірливу пляму фарби.

Щоб запобігти змазуванню тексту, інженери телетайпів ввели обов'язкову пару керуючих кодів `CR + LF`. Крім того, на високих швидкостях після цієї пари передавачу доводилося штучно відправляти один або два символи-заповнювачі NUL (`0x00`) або DEL (`0x7F`), які не викликали друку й давали каретці додатковий час повернутися ліворуч. Послідовність `CR LF` стала апаратним стандартом телеграфного зв'язку та ранніх мереж, таких як ARPANET (що зафіксовано в протоколах Telnet RFC 854 та SMTP RFC 821).

## Економіка пам'яті: рішення Кена Томпсона й Денніса Рітчі

Наприкінці 1960-х років у лабораторіях Bell Labs Кен Томпсон (Ken Thompson) і Денніс Рітчі (Dennis Ritchie) створювали операційну систему Unix на комп'ютері DEC PDP-7, а згодом портували її на PDP-11/20.

Комп'ютер PDP-7 мав лише 8 кілослів 18-бітної пам'яті (близько 16 КіБ), а ранній PDP-11 — 24 КіБ пам'яті, з яких ядро займало майже половину. Дисковий простір перших накопичувачів RK05 вимірювався одиницями мегабайтів.

У системі Multics, над якою вчені Bell Labs працювали раніше, текст уже розглядався як потік, що завершується єдиним символом Newline (`\n`, `0x0A`). Томпсон і Рітчі свідомо перенесли цю модель в Unix, відкинувши обов'язкове збереження пари `CRLF` у файлах:

1. **Пряма економія носія:** У текстовому файлі на кілька тисяч рядків збереження двох байтів `\r\n` замість одного `\n` збільшувало розмір файлу на 5–10%. За умов жорсткого дефіциту дисків це була недопустима марнотратність.
2. **Спрощення парсерів у мові C:** Утилітам Unix (компілятору `cc`, редактору `ed`, асемблеру `as`) набагато простіше шукати єдиний роздільник рядка `\n` за допомогою простого `while (*p != '\n')`, ніж тримати стан для виявлення двобайтової послідовності `\r\n`.
3. **Відокремлення логічного тексту від фізичного пристрою:** Файл на диску містить абстрактний текст, де `\n` означає суто «новий рядок». Якщо текст потрібно вивести на фізичний телепринтер, за перетворення `\n` → `\r\n` повинен відповідати драйвер термінала (`tty`), а не файл.

Саме так у драйвері терміналів Unix з'явився режим обробки виводу `ONLCR` (Map NL to CR-NL on output), що зберігається в структурі `termios` до сьогодні. Ядро та файли зберігали чистий `\n`, а послідовний порт автоматично додавав `\r` перед відправленням байтів на дріт телетайпа.

## Лінія CP/M, MS-DOS та спадщина Windows

Поки Bell Labs розвивала Unix на мінікомп'ютерах, у 1974 році Гері Кілдолл (Gary Kildall) створив операційну систему CP/M (Control Program for Microcomputers) для 8-бітних мікропроцесорів Intel 8080.

Кілдолл орієнтувався на архітектуру операційних систем компанії DEC — RT-11 та TOPS-10, якими він користувався в університеті штату Вашингтон. В архітектурі RT-11 текстові файли зберігалися саме у форматі `CRLF`, оскільки операційна система орієнтувалася на пряму сумісність із принтерами без проміжних рівнів абстракції драйверів. Крім того, у CP/M файли читалися блоками по 128 байтів, а логічний кінець тексту позначався символом `Ctrl+Z` (`0x1A`), тоді як кожен рядок завершувався парою `0x0D 0x0A`.

```
Історичне розгалуження стандартів кінця рядка:

  Телетайпи Teletype Model 33 (CR + LF апаратно)
         /                                \
        / (1969, Bell Labs)                \ (1974, Digital Research)
     Unix (PDP-7/11)                         CP/M (Intel 8080)
        |                                      |
     POSIX / Linux                          QDOS / MS-DOS (1981)
     (Тільки LF: \n)                           |
                                            Windows NT / 10 / 11
                                            (Пара CRLF: \r\n)
```

У 1980 році Тім Патерсон (Tim Paterson) зі Seattle Computer Products створив систему QDOS (Quick and Dirty Operating System, пізніше 86-DOS), розроблену як 16-бітний клон API CP/M. Компанія Microsoft придбала 86-DOS, перетворивши її на MS-DOS для персональних комп'ютерів IBM PC (1981 рік).

MS-DOS повністю успадкувала механізм кінців рядків CP/M: усі текстові файли зберігалися з парою `0x0D 0x0A`. Коли на зміну DOS прийшла родина Windows NT, архітектори Microsoft зберегли формат CRLF заради повної зворотної сумісності з величезною екосистемою програм для DOS та Win16.

Так виникло розгалуження, яке існує вже понад пів століття: Unix-подібні системи (Linux, macOS, BSD) використовують один байт `\n`, тоді як світ Windows зберігає пару `\r\n`. Спроба об'єднати ці світи в кросплатформних мережах, репозиторіях вихідного коду та системних конвеєрах залишається постійним джерелом помилок, коли символ `\r` сприймається Unix-утилітами не як кінець рядка, а як звичайні сміттєві дані.
