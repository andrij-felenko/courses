# 🧮 Математична модель стекування профілів: алгебра перетинів та ґрати безпеки

Формалізація перевірки прав доступу в AppArmor під час стекування профілів описується алгеброю перетинів множин та теорією ґрат (lattice theory, зокрема класичною моделлю ґрат безпеки Деннінг). Математична модель гарантує монотонне звуження привілеїв при додаванні нових профілів у стек та унеможливлює розширення прав за рахунок комбінування політик.

### 1. Формальне визначення універсуму прав та профілю

Нехай `U` — універсум усіх можливих впорядкованих трійок операцій `(op, path, mask)`, де:
- `op ∈ Operations` — тип системної операції (наприклад, `file_open`, `sys_ptrace`, `net_bind`, `cap_capable`).
- `path ∈ Paths` — канонічний VFS-шлях або об'єктний ідентифікатор мережевого чи IPC-ресурсу.
- `mask ∈ AccessMasks` — бітова маска запитуваних мандатних прав (наприклад, `r`, `w`, `x`, `append`, `link`).

Для довільного профілю AppArmor `P[i]` визначено функцію дозволу `Permitted(P[i]) ⊆ U`, яка повертає підмножину всіх трійок операцій, дозволених даним профілем під час його самостійного виконання.

### 2. Алгебра перетинів дозволів у мітці стеку

Коли процес працює під політичним контекстом, вираженим стекованою міткою `L = P[1] //& P[2] //& ... //& P[n]`, підсумкова множина дозволених операцій `Permitted(L)` обчислюється як точний перетин множин дозволів усіх складових профілів:

```
Permitted(L) = Permitted(P[1]) ∩ Permitted(P[2]) ∩ ... ∩ Permitted(P[n])
```

З фундаментальних властивостей перетину множин у булевій алгебрі безпосередньо випливає теорема про монотонність обмеження:

```
∀ i ∈ {1, ..., n}: Permitted(L) ⊆ Permitted(P[i])
```

Це означає, що додавання будь-якого нового профілю `P[n+1]` у стек `L` може лише зменшити або залишити незмінною множину дозволених дій, але ніколи не здатне розширити привілеї процесу:

```
Permitted(L //& P[n+1]) = Permitted(L) ∩ Permitted(P[n+1]) ⊆ Permitted(L)
```

Такий підхід гарантує принцип мінімальних привілеїв: процес, що виконується в стеку, не може обійти обмеження жорсткішого профілю за рахунок приєднання м'якшого.

### 3. Теорія ґрат безпеки та комутативність стекування

Множина всіх можливих політичних контекстів у поєднанні з оператором перетину утворює напівґратку нижньої межі (meet-semilattice), де точна нижня межа (infimum, позначувана як `∧`) двох профілів описує їхнє стекування:

```
P[1] ∧ P[2] = P[1] //& P[2]
```

Оператор стекування володіє властивостями комутативності та асоціативності з точки зору фінальної множини дозволів:

```
Permitted(P[1] //& P[2]) = Permitted(P[2] //& P[1])
Permitted((P[1] //& P[2]) //& P[3]) = Permitted(P[1] //& (P[2] //& P[3]))
```

Порядок додавання профілів у стек не впливає на кінцевий вердикт авторизації: підсумкова підмножина дозволених системних викликів залишається абсолютно ідентичною.

### 4. Предикат оцінки правила з урахуванням явних відмов (Deny Rules)

Усередині окремого профілю AppArmor `P[i]` правила обчислюються за допомогою двох множин: явних дозволів `Allow(P[i])` та явних заборон `Deny(P[i])`. Згідно з специфікацією AppArmor, явна заборона має абсолютний пріоритет над дозволом у межах того самого профілю:

```
Permitted(P[i]) = Allow(P[i]) \ Deny(P[i])
```

Предикат авторизації конкретної операційної дії `req = (op, path, mask)` для стекованої мітки `L = P[1] //& P[2] //& ... //& P[n]` обчислюється за формулою:

```
Authorize(L, req)
= ⋀_{i=1}^n ( (req ∈ Allow(P[i])) ∧ (req ∉ Deny(P[i])) )
```

Розкриємо логічний вираз крок за кроком для випадку стекування двох профілів `L = P[1] //& P[2]`:

```
Authorize(P[1] //& P[2], req)
= [req ∈ Permitted(P[1])] ∧ [req ∈ Permitted(P[2])]       [визначення перетину мітки]
= [(req ∈ Allow(P[1])) ∧ (req ∉ Deny(P[1]))] 
  ∧ [(req ∈ Allow(P[2])) ∧ (req ∉ Deny(P[2]))]           [розкладання за правилами Allow/Deny]
= (req ∈ Allow(P[1])) ∧ (req ∈ Allow(P[2])) 
  ∧ ¬(req ∈ Deny(P[1]) ∨ req ∈ Deny(P[2]))               [закон Де Моргана для відмов]
```

Отже, системна операція дозволяється ядром тоді й лише тоді, коли вона явно дозволена в кожному профілі стеку І не заборонена жодним із профілів.

### 5. Декартовий добуток автоматів DFA під час обчислення шляхів

Кожен профіль AppArmor компілюється в детермінований скінченний автомат (DFA). Під час аналізу VFS-шляху для стекованої мітки `L = P[1] //& ... //& P[n]` ядро ефективно обчислює переходи в декартовому добутку автоматів:

```
DFA_stack = DFA(P[1]) × DFA(P[2]) × ... × DFA(P[n])
```

Стан стеку `S` у момент часу `t` визначається кортежем станів окремих автоматів:

```
S(t) = (s[1](t), s[2](t), ..., s[n](t))
```

Для кожного символу `c` у текстовому шляху VFS функція переходу стеку `δ_stack` виконується паралельно для всіх компонентів:

```
δ_stack(S(t), c) = ( δ[1](s[1](t), c), δ[2](s[2](t), c), ..., δ[n](s[n](t), c) )
```

Складність простору станів у найгіршому випадку виражається як добуток кількості станів окремих автоматів `O(|Q[1]| · |Q[2]| · ... · |Q[n]|)`. Однак ядро Linux обчислює переходи ліниво (on-demand), виконуючи лише паралельні кроки по поточних таблицях DFA без реальної побудови об'єднаного автомата в пам'яті.

Якщо під час сканування хоча б один автомат `δ[i]` потрапляє в термінальний стан відмови (match error або відсутність відповідного ребра в таблиці DFA), підсумковий стан стеку миттєво переходить у стан `DENIED`.

### 6. Неперехідність відмовляючих переходів та доведення незворотності

Стекування забезпечує алгебраїчну властивість неперехідності (non-transitivity) привілеїв при спробі скидання чи переходу між профілями.

Якщо процес, що працює у мітці `P[host] //& P[container]`, намагається виконати системний виклик `aa_change_profile("P[target]")`, ядро будує нову мітку покомпонентно — обчислює перехід для КОЖНОГО профілю мітки й зливає результати:

```
New_Label = Transition(P[host], P[target]) //& Transition(P[container], P[target])
```

Якщо хоча б один компонент не має правила `change_profile` на вказану ціль, увесь перехід відхиляється. Складова при цьому ніколи не зникає: `Transition` відображає профіль у профіль, а не в порожню множину, — тож перехід здатен замінити чи поглибити стек, але не вкоротити його. Профіль `P[host]` до того ж завантажено в батьківському просторі імен, і процес усередині `:container-ns:` не може навіть назвати його у специфікаторі мітки. Це доводить незворотність ізоляції: процес нижчого рівня не здатний підвищити власні привілеї або вийти з-під контролю хостової політики.

### 7. Еквівалентність комбінованих міток та мінімізація вектора

Якщо під час стекування додається профіль `P[k]`, який є ідентичним або математично слабшим за вже присутній у стеку профіль `P[j]` (тобто `Permitted(P[j]) ⊆ Permitted(P[k])`), перетин множин не змінюється:

```
Permitted(P[j] //& P[k]) = Permitted(P[j])
```

Ядро цієї рівності само не виводить: порівняти `Permitted` двох профілів означало б порівняти їхні DFA, і на кожному переході це надто дорого. Вектор `struct aa_label` тримається впорядкованим, і ядро вилучає з нього лише ТОТОЖНІ елементи — той самий `struct aa_profile`, що потрапив у стек двічі. Семантично надлишковий, але інший профіль лишається у векторі й чесно проходить перевірку разом з рештою.
