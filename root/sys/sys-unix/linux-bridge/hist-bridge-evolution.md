# 📜 Еволюція Linux Bridge: від brctl до VLAN-filtering та Switchdev

Мережевий міст у Linux пройшов шлях від простого експериментального модуля ядра, що замінював дорогі апаратні концентратори на початку 2000-х років, до центральної підсистеми віртуалізації, контейнерних мереж та апаратного керування комутаторами центрів обробки даних. Кожна зміна в його архітектурі була відповіддю на конкретну кризу масштабованості: спочатку це була боротьба за продуктивність багатопроцесорних серверів, згодом — вибух віртуалізації та контейнеризації, а пізніше — необхідність керувати кремнієвими чіпами комутації на швидкостях у сотні гігабіт на секунду.

---

## 1. Поява програмного комутатора: епоха Linux 2.2 та 2.4

Наприкінці 1990-х років корпоративні та університетські комп'ютерні мережі переживали перехід від спільних коаксіальних шин (10BASE2 та 10BASE5) до структурованих кабельних систем на витій парі (10BASE-T та 100BASE-TX Fast Ethernet). Коаксіальний кабель являв собою єдиний спільний колізійний домен: станції слухали ефір за протоколом CSMA/CD, і з ростом кількості машин колізії паралізували мережу. Поява комутаторів дозволила виділити кожен порт в окремий домен колізій із повнодуплексним режимом (Full Duplex).

Проте апаратні комутатори наприкінці 90-х були дорогими пропрієтарними пристроями. Якщо адміністратору потрібно було прозоро об'єднати кілька фізичних кабельних сегментів в один спільний канальний домен (Layer 2), варіантів було небагато. Маршрутизація третього рівня (Layer 3 IP Routing) вимагала розбиття мережі на окремі IP-підмережі та налаштування шлюзів, що руйнувало роботу популярних тоді багатопротокольних середовищ без підтримки маршрутизації (IPX/SPX у мережах Novell NetWare, AppleTalk у комп'ютерах Macintosh, NetBEUI у доменах Windows NT). Потрібен був прозорий міст на рівні MAC-адрес (Transparent Learning Bridge), який працював би на базі звичайного комп'ютера з Linux та кількома мережевими картами.

### Робота Леннерта Буйтенвека та модуль bridge.o

Перші спроби створити міст для Linux робилися ще в ядрі 2.0 та 2.2 за участю Алана Кокса (Alan Cox), однак вони мали характер експериментальних латок, не забезпечували повної відповідності стандарту IEEE 802.1D і не підтримували динамічну зміну топології.

У 1999–2000 роках нідерландський розробник Леннерт Буйтенвек (Lennert Buytenhek) повністю переписав реалізацію моста. Спочатку вона поширювалася як автономний патч для Linux 2.2, а з виходом стабільної гілки Linux 2.4 (2001 рік) увійшла до основного дерева ядра як модуль `bridge.o` (згодом `bridge.ko` у каталозі `net/bridge/`).

```
+--------------------------------------------------------------------+
|  Простір користувача: утиліта brctl (пакет bridge-utils)           |
|  Керування через системні виклики ioctl(sock, SIOCDEVPRIVATE, ...) |
+--------------------------------------------------------------------+
                                | ioctl (SIOCGIFBR, SIOCSIFBR)
                                v
+--------------------------------------------------------------------+
|  Ядро Linux 2.4: модуль bridge.o                                   |
|  - Віртуальний пристрій struct net_device (роль Master)            |
|  - Фізичні порти в нерозбірливому режимі (dev_set_promiscuity)     |
|  - Перехоплення трафіку у функції netif_rx (br_handle_frame_hook)  |
|  - Таблиця комутації FDB на геш-таблиці з aging-таймером           |
|  - Вбудований монолітний автомат 802.1D STP (net/bridge/br_stp.c)  |
|  - Глобальне блокування spin_lock_bh(&br->lock)                    |
+--------------------------------------------------------------------+
```

Архітектура рішення базувалася на таких базових механізмах:

1. **Логічний пристрій моста (`struct net_bridge`)**: ядро створювало віртуальний мережевий інтерфейс `struct net_device` (наприклад, `br0`). Він виступав майстром (Master) для підпорядкованих фізичних карт (Slave Ports, представлених структурами `struct net_bridge_port`).
2. **Нерозбірливий режим (`promiscuous mode`)**: апаратний мережевий контролер за замовчуванням відкидає всі кадри, MAC-адреса призначення яких не збігається з його власною апаратною адресою (за винятком широкомовних broadcast). Щоб міст міг аналізувати та комутувати транзитний трафік між іншими хостами сегмента, ядро при підключенні інтерфейсу до моста примусово активувало прапорець `IFF_PROMISC` викликом `dev_set_promiscuity(dev, 1)`.
3. **Хук перехоплення кадрів (`br_handle_frame_hook`)**: у ядрі 2.4 функція обробки вхідних пакетів `netif_rx()` містила глобальний вказівник на функцію `br_handle_frame_hook`. Якщо модуль моста було завантажено й інтерфейс належав мосту, вхідний кадр `sk_buff` перехоплювався цим хуком до передачі у протокольні черги L3 (IP або ARP) і надходив безпосередньо в комутаційний рушій `br_handle_frame()`.
4. **База даних комутації FDB (Forwarding Database)**: ядро підтримувало динамічну геш-таблицю (`struct net_bridge_fdb_entry`), де ключем була 6-байтова MAC-адреса, а значенням — вказівник на порт моста та час останнього оновлення. При надходженні кадру міст фіксував адресу джерела (`Source MAC`) і оновлював таймер старіння (aging timer, за замовчуванням 300 секунд). Якщо порт для адреси призначення (`Destination MAC`) був відомий, кадр пересилався лише в цей порт викликом `br_forward()`. Якщо ж адреса була невідомою або кадр був широкомовним чи мультикастним (`is_multicast_ether_addr()`), запускався механізм затоплення (`br_flood()`) — створення копій кадру та розсилка в усі активні порти моста, крім порту надходження.

Керування з простору користувача виконувалося через сокетний інтерфейс `ioctl()` з використанням спеціального діапазону команд `SIOCDEVPRIVATE`. Для цього Леннерт Буйтенвек створив окремий пакет утиліт `bridge-utils` із командним інструментом `brctl` (`brctl addbr br0`, `brctl addif br0 eth0`, `brctl showmacs br0`).

### Вузькі місця першого покоління мостів

Незважаючи на простоту та зручність, архітектура Linux 2.4 містила критичні вузькі місця, які стали очевидними з поширенням гігабітних мереж та багатопроцесорних серверів (SMP):

1. **Глобальне блокування ядра (`br->lock`)**: увесь стан моста — список портів, таймери та вся таблиця FDB — захищався єдиним спінлоком `spin_lock_bh(&br->lock)`. Кожен оброблений пакет, оновлення таймера старіння або вивчення нового MAC вимагали захоплення цього блокування. На серверах із кількома процесорами ядра CPU витрачали значну частину тактів на очікування звільнення спінлока (Lock Contention), що різко обмежувало пропускну здатність комутації.
2. **Низька ефективність інтерфейсу `ioctl`**: системні виклики `ioctl` оперували фіксованими бінарними структурами мови C. Читання таблиці комутації через `SIOCBRGETFDB` вимагало виділення буфера фіксованого розміру в просторі користувача. Якщо мережа налічувала тисячі MAC-адрес, вичитування перетворювалося на повільну ітеративну процедуру, що блокувала міст. До того ж `ioctl` був виключно синхронним інтерфейсом запит-відповідь: простір користувача не міг підписатися на асинхронні події ядра (наприклад, падіння лінка чи зміну топології) і мусив постійно опитувати ядро в нескінченному циклі.
3. **Монолітний код STP у просторі ядра**: алгоритм Spanning Tree було жорстко зашито всередину модуля `bridge.o`.

## 2. Запобігання петлям: від ядрового 802.1D STP до простору користувача

Канальний рівень Ethernet не має вбудованого механізму захисту від зациклення. На відміну від протоколів мережевого рівня IPv4 (поле Time-To-Live, TTL) та IPv6 (Hop Limit), які зменшують лічильник на кожному маршрутизаторі та знищують пакет при досягненні нуля, 14-байтовий заголовок Ethernet (`Destination MAC [6] + Source MAC [6] + EtherType [2]`) взагалі не містить поля часу життя.

```
       +-----------------------+
       |   Linux Bridge br0    |
       |  (MAC: 00:aa:bb:cc:01) |
       +---+---------------+---+
           |               |
     Порт eth1           Порт eth2
           |               |
           |   ФІЗИЧНА     |
           |    ПЕТЛЯ      |
           | (КІЛЬЦЕ ЛІНКІВ)|
           |               |
     Порт eth1           Порт eth2
           +---+---------------+---+
       |   Linux Bridge br1    |
       |  (MAC: 00:aa:bb:cc:02) |
       +-----------------------+
```

Якщо між портами двох мостів або комутаторів випадково утворюється замкнене фізичне кільце, перший же широкомовний кадр (наприклад, звичайний ARP-запит `who-has 192.168.1.1`) запускає ланцюгову реакцію:
- Міст `br0` приймає кадр на порті `eth1` і транслює його копію у порт `eth2`;
- Міст `br1` приймає копію на порті `eth2` і транслює її назад у порт `eth1`;
- Обидва мости знову приймають власні копії та повторюють розсилку, подвоюючи кількість кадрів на кожній ітерації.

За лічені мілісекунди виникає **широкомовний шторм (Broadcast Storm)**. Мережева смуга забивається на 100%, переривання від мережевих карт перевантажують процесори хостів, а таблиця FDB починає безперервно переписуватися (MAC Table Flapping), оскільки одна й та сама MAC-адреса надходить то з одного, то з іншого порту щомікросекунди. Без автоматичного виявлення та розриву петель робота комутованої мережі стає неможливою.

### Алгоритм Радії Перлман у ядрі Linux

Для автоматичного розриву петель інженер Радія Перлман (Radia Perlman) у 1985 році винайшла алгоритм Spanning Tree Protocol, згодом стандартизований як **IEEE 802.1D**. Алгоритм перетворює довільний граф мережі зі зворотними зв'язками на логічне дерево без петель шляхом блокування резервних портів.

У модулі `bridge.o` ядра Linux 2.4 алгоритм 802.1D було повністю реалізовано всередині ядра (`net/bridge/br_stp.c`, `net/bridge/br_stp_timer.c`, `net/bridge/br_stp_bpdu.c`).

```
[ Disabled ] (Порт вимкнено або без лінка)
     |
     v
[ Blocking ] (Дроп кадрів, прийом BPDU)
     |
     v (Визначено роль порту)
[ Listening ] (15 секунд: прослуховування BPDU, без навчання MAC)
     |
     v (Закінчився Forward Delay)
[ Learning ]  (15 секунд: вивчення Source MAC у FDB, дроп даних)
     |
     v (Закінчився Forward Delay)
[ Forwarding ] (Нормальна комутація та передача трафіку)
```

Ядро кожні 2 секунди (`Hello Time`) формувало спеціальні кадри керування — **BPDU (Bridge Protocol Data Units)** — і надсилало їх на зарезервовану стандартом групову канальну адресу `01:80:C2:00:00:00`. Мости обмінювалися даними, обирали кореневий міст (Root Bridge) за найменшим ідентифікатором `Bridge ID = Priority + MAC`, розраховували вартість шляхів (Path Cost) та переводили порти у відповідні стани:

1. **Disabled**: порт вимкнено адміністративно;
2. **Blocking**: порт блокує передачу та прийом звичайних кадрів, слухаючи лише службові BPDU;
3. **Listening (15 секунд)**: порт бере участь у виборах топології, але не вивчає MAC-адреси і не пересилає кадри;
4. **Learning (15 секунд)**: порт починає заповнювати таблицю FDB на основі вхідного трафіку, але ще не пересилає дані, щоб уникнути лавинного затоплення після відкриття порту;
5. **Forwarding**: повноцінний робочий стан передачі даних.

Сумарний час відкриття порту складав від 30 до 50 секунд (`2 × Forward Delay + Max Age`).

### Криза ядрового STP та нові стандарти

На початку 2000-х затримка збіжності у 50 секунд стала неприпустимою для промислових дата-центрів. Інститут IEEE розробив принципово нові протоколи:

- **IEEE 802.1w (Rapid Spanning Tree Protocol, RSTP, 2001 рік)**: замість пасивного очікування таймерів запроваджено активне рукостискання «пропозиція/підтвердження» (Proposal/Agreement Handshake) на лінках точка-точка. Час реакції на зміну топології скоротився до часток секунди (< 1 с). Було введено граничні порти (Edge Ports / PortFast) для кінцевих серверів, які переходять у режим Forwarding миттєво.
- **IEEE 802.1s (Multiple Spanning Tree Protocol, MSTP, 2002 рік)**: об'єднав віртуальні мережі VLAN у групи інстансів MSTI (Multiple Spanning Tree Instances) поверх загального дерева CIST (Common and Internal Spanning Tree). Це дозволило балансувати навантаження по лінках для різних груп VLAN без необхідності запуску окремого екземпляра STP для кожного з тисячі VLAN (як це робив пропрієтарний Cisco PVST+).

Спроба перенести RSTP та MSTP у ядро Linux створила серйозний архітектурний конфлікт:
- Специфікації RSTP/MSTP містили десятки взаємопов'язаних кінцевих автоматів (State Machines), численні прапорці узгодження, перевірку пріоритетних векторів та складний синтаксис пакетів.
- Перенесення цієї логіки в ядро прямо порушувало базовий принцип архітектури Linux: ядро має бути максимально простим і відповідати виключно за швидкий шлях обробки даних (Data Plane), тоді як складна протокольна політика (Control Plane) повинна жити в ізольованому просторі користувача. Будь-яка помилка або вразливість у складному автоматі RSTP призвела б до паніки ядра (Kernel Panic) та падіння всього сервера.

### Відокремлення Control Plane від Data Plane: параметр stp_state та mstpd

Для вирішення цієї проблеми у ядрі Linux 2.6.28 було реалізовано механізм делегування STP простору користувача. За допомогою параметра `/sys/class/net/<br>/bridge/stp_state` зі значенням `2` (або через Netlink-атрибут `IFLA_BR_STP_STATE`) ядро переводиться в режим керованого виконавця:

```
+--------------------------------------------------------------------+
|  Простір користувача: демон mstpd / rstpd                          |
|  - Повна реалізація кінцевих автоматів IEEE 802.1D, 802.1w, 802.1s |
|  - Парсинг та генерація BPDU (01:80:C2:00:00:00)                   |
|  - Обчислення топології дерев MSTI / CIST                          |
+--------------------------------------------------------------------+
       ^                                              |
       | BPDU через raw-сокет                         | Директиви Netlink
       | або Netlink-канал                            | (IFLA_BRPORT_STATE)
       v                                              v
+--------------------------------------------------------------------+
|  Ядро Linux (Data Plane):                                          |
|  - Перехоплення BPDU (01:80:C2:00:00:00) та відправка демону       |
|  - Швидка зміна стану порту: BLOCKING / LEARNING / FORWARDING       |
|  - Високошвидкісна комутація транзитних пакетів                    |
+--------------------------------------------------------------------+
```

1. Ядро вимикає власний спрощений модуль `br_stp.c` і припиняє генерацію внутрішніх BPDU;
2. Усі вхідні кадри на адресу `01:80:C2:00:00:00` перехоплюються на рівні драйвера і передаються через сокет простору користувача демону `mstpd` або `rstpd`;
3. Демон `mstpd` у просторі користувача виконує розрахунок топології дерев, узгоджує стан портів за протоколом RSTP/MSTP;
4. Після ухвалення рішення демон надсилає ядру директивну команду через Netlink (`RTM_SETLINK` з атрибутом `IFLA_BRPORT_STATE`), наказуючи миттєво перевести конкретний порт у стан `BR_STATE_BLOCKING` або `BR_STATE_FORWARDING`.

Якщо демон у просторі користувача аварійно завершує роботу, сервер не падає, а продовжує передавати трафік у поточному стані до перезапуску служби системою ініціалізації.

## 3. Вибух віртуалізації та криза каскадних мостів (2007–2014)

У 2006–2007 роках індустрія серверного обладнання зазнала тектонічного зсуву завдяки появі технологій апаратної віртуалізації процесорів Intel VT-x та AMD-V. Розробник Аві Ківіті (Avi Kivity) створив підсистему KVM (Kernel-based Virtual Machine), включену в ядро Linux 2.6.20 (2007 рік). Одночасно з'явилися інструменти контейнеризації на базі просторів імен (namespaces) та контрольних груп (cgroups) — OpenVZ, LXC (2008 рік), а згодом Docker (2013 рік).

```
+--------------------------------------------------------------------+
| Хост-система Linux (KVM Hypervisor / Docker Daemon)                |
|                                                                    |
|  +---------------------+                  +---------------------+  |
|  | Віртуальна машина   |                  | Контейнер Docker    |  |
|  | (QEMU / KVM)        |                  | (Network Namespace) |  |
|  | [ eth0 у гості ]    |                  | [ eth0 у контейнері]|  |
|  +----------+----------+                  +----------+----------+  |
|             |                                        |             |
|             | /dev/net/tun                           | veth-peer   |
|             v                                        v             |
|        [ tap0 ]                                 [ veth-host ]      |
|             \                                        /             |
|              \                                      /              |
|               +-----------------+------------------+               |
|                                 |                                  |
|                     +-----------v-----------+                      |
|                     | Linux Bridge (docker0)|                      |
|                     +-----------+-----------+                      |
|                                 |                                  |
|                         [ Фізичний eth0 ]                          |
+---------------------------------+----------------------------------+
```

Для підключення віртуальних машин та контейнерів до мережі знадобилися спеціальні програмні мережеві пристрої:

- **TAP-інтерфейси (`/dev/net/tun`)**: віртуальні Ethernet-пристрої канального рівня. Процес емулятора (QEMU) відкриває файловий дескриптор `/dev/net/tun`. Коли віртуальна машина надсилає Ethernet-кадр, QEMU записує його у цей дескриптор, і ядро сприймає його як кадр, що щойно надійшов від фізичної мережевої карти `tap0`.
- **veth-пари (Virtual Ethernet Pairs)**: віртуальні кабелі, що з'єднують простори імен мережі. Створюються парою інтерфейсів (`ip link add veth0 type veth peer name veth-peer`). Один кінець поміщається всередину простору імен контейнера як `eth0`, а інший залишається в головному просторі імен хоста і підключається до моста `docker0`.

Міст Linux Bridge природним чином став стандартним комутатором за замовчуванням для гіпервізорів KVM/QEMU та контейнерних рушіїв Docker/LXC.

### Проблема багатоклієнтської ізоляції та каскадні мости

У хмарних платформах (AWS, OpenStack, CloudStack) на одному фізичному сервері одночасно працювали сотні віртуальних машин різних клієнтів (Tenants). Трафік різних клієнтів вимагав суворої ізоляції за допомогою тегів стандарту IEEE 802.1Q VLAN (VID 1–4094).

Однак класичний міст Linux Bridge залишався повністю «невідомим до VLAN» (VLAN-unaware): він поводився як простий некерований хаб і не мав внутрішньої логіки розбору 4-байтних тегів 802.1Q. Якщо в один міст підключалися інтерфейси з тегованим трафіком різних клієнтів, кадри могли комутуватися між ними або виходити назовні нетегованими.

Щоб забезпечити ізоляцію, системні адміністратори та скрипти оркестрації будували громіздкі ієрархічні конструкції, відомі як **каскадні мости (Cascading Bridges / Bridge-per-VLAN)**:

```
                          +------------------------+
                          | Фізичний інтерфейс eth0|
                          +-----------+------------+
                                      |
              +-----------------------+-----------------------+
              | Сабінтерфейси 802.1Q                          |
              v                                               v
        [ eth0.100 ]                                    [ eth0.200 ]
              | (Тегування VLAN 100)                          | (Тегування VLAN 200)
              v                                               v
        +-----------+                                   +-----------+
        |   br100   | (Міст для VLAN 100)               |   br200   | (Міст для VLAN 200)
        +-----+-----+                                   +-----+-----+
              |                                               |
              v                                               v
           [ tap0 ]                                        [ tap1 ]
      (VM Клієнта 1)                                  (VM Клієнта 2)
```

Для створення такої схеми:
1. Фізичний інтерфейс `eth0` розбивався на десятки сабінтерфейсів `eth0.VID` за допомогою утиліти `vconfig` або `ip link add link eth0 name eth0.100 type vlan id 100`;
2. Під кожен окремий VLAN створювався окремий міст (`br100`, `br200`, `br300`...);
3. До відповідного моста підключався сабінтерфейс `eth0.VID` та порти `tap`/`veth` відповідних клієнтів.

### Архітектурний колапс каскадної моделі

Коли на одному сервері запускалися сотні віртуальних машин у десятках різних VLAN, каскадна модель призводила до вичерпання ресурсів хоста:

1. **Вибухове споживання пам'яті ядра**: у Linux кожен інтерфейс `eth0.VID` та кожен міст `brVID` є повноцінним екземпляром важкої структури ядра `struct net_device`. Він виділяє власні черги передачі/прийому (`struct netdev_queue`), об'єкти віртуальної файлової системи sysfs, структури статистики `pcpu_dstats` та блокування. Тисячі таких об'єктів безцільно спалювали сотні мегабайт незмінної пам'яті ядра (Kernel Slab/RAM).
2. **Руйнування кешу процесора (CPU Cache Thrashing) та зростання затримок**:
   Шлях кожного кадру від віртуальної машини до дроту перетворювався на довгий ланцюг транзитів:
   - Процес QEMU записує пакет у дескриптор `tap0`;
   - Ядро виділяє сокетний буфер `sk_buff` і викликає `netif_rx()` на інтерфейсі `tap0`;
   - Кадр надходить у функцію комутації моста `br100`, де виконується пошук у FDB;
   - Міст передає кадр у чергу передачі сабінтерфейсу `eth0.100` через `dev_queue_xmit()`;
   - Драйвер сабінтерфейсу модифікує заголовок (вставляє 4 байти тегу 802.1Q) і викликає наступний `dev_queue_xmit()` уже на фізичному адаптері `eth0`;
   - Пакет потрапляє в чергу передачі апаратного драйвера мережевої карти.
   
   Кожен такий перехід між віртуальними інтерфейсами проходив через повний стек обробки мережевих пристроїв, скидав L1/L2 кеші процесора хоста і суттєво збільшував затримку передачі (Latency).
3. **Поява Open vSwitch (OVS, 2009 рік)**:
   Через нездатність класичного Linux Bridge масштабуватися у хмарних середовищах інженери компанії Nicira (Мартін Касадо — Martin Casado, Джастін Петтіт — Justin Pettit, Бен Пфафф — Ben Pfaff) створили проект **Open vSwitch**.
   OVS запропонував революційний підхід:
   - Розподіл на контролер простору користувача `ovs-vswitchd` (Control Plane) та швидкий ядровий модуль `openvswitch.ko` (Data Plane);
   - Нативну підтримку 802.1Q тегування/розтегування всередині одного віртуального комутатора;
   - Підтримку протоколу OpenFlow, оверлейних тунелів (GRE, VXLAN, Geneve) та обробку пакетів за розширеними таблицями потоків (Flow Tables) на базі аналізу 12-полів заголовків.

OVS став стандартом для хмарного оркестратора OpenStack Neutron та корпоративних систем віртуалізації. Проте OVS залишався складною зовнішньою системою з високим порогом входження, власним модулем ядра та значними накладними витратами на обробку промахів кешу потоків (Upcalls до `ovs-vswitchd` через Netlink). Спільнота розробників ядра усвідомила гостру необхідність фундаментальної модернізації вбудованого Linux Bridge.

## 4. Відхід від ioctl та sysfs: перехід на Netlink ABI в iproute2

У процесі розвитку підсистем ядра Linux 2.6 та 3.x стало остаточно зрозуміло, що методи конфігурації мережі через виклики `ioctl` та файлову систему `sysfs` зайшли в глухий кут.

```
Еволюція інструментів конфігурації:
[ 2000: ioctl + brctl ]  --->  [ 2004: sysfs + brctl ]  --->  [ 2012+: Netlink + iproute2 ]
- Фіксовані бінарні C-структури  - Текстові файли /sys/class/net - Двійкові TLV-повідомлення
- Обмеження розміру буферів      - 20+ syscalls на один порт     - Атомарні транзакції
- Немає сповіщень про події      - Високий оверхед VFS           - Асинхронні події (RTNLGRP)
```

### Криза ioctl та sysfs

1. **Обмеження `ioctl`**:
   - Системні виклики `ioctl` базуються на жорстко зафіксованих структурах мови C. Будь-яке розширення інтерфейсу (наприклад, додавання прапорця фільтрації мультикасту чи підтримки нового режиму) вимагало зміни розміру бінарної структури, що ламало сумісність простору користувача зі старими ядрами (ABI Incompatibility).
   - `ioctl` не дозволяв безпечно вивантажувати масиви змінного розміру. Якщо таблиця FDB містила 50 000 записів, виклик `SIOCBRGETFDB` міг переповнити виділений користувацький буфер або призвести до тривалого блокування ядра під час копіювання пам'яті через `copy_to_user()`.
2. **Обмеження `sysfs`**:
   - У ядрі 2.6 параметри моста було винесено у віртуальну файлову систему: `/sys/class/net/<br>/bridge/` (параметри комутатора: `ageing_time`, `forward_delay`, `priority`, `stp_state`) та `/sys/class/net/<br>/brif/<port>/` (параметри портів: `path_cost`, `priority`, `hairpin_mode`).
   - Налаштування одного порту вимагало виконання десятків системних викликів `open()`, `write()`, `close()` для окремих псевдофайлів. Кожна така операція проходила крізь підсистему VFS ядра, виділяла структури dentry/inode, захоплювала блокування файлової системи та витрачала процесорний час на конвертацію рядків ASCII у двійкові числа (`kstrtoint`, `sscanf`).
   - У високонавантажених вузлах Kubernetes або Docker, де щосекунди створювалися та видалялися десятки контейнерів, операції з `sysfs` створювали суттєве навантаження на CPU і унеможливлювали атомарну зміну кількох параметрів одночасно.

### Стандартизація на базі Netlink (rtnetlink)

Мережева підсистема ядра стандартизувала конфігурацію на основі бінарного протоколу **RTNETLINK** (сімейство сокетів `AF_NETLINK` з типом `NETLINK_ROUTE`).

Netlink вирішив усі проблеми попередніх інтерфейсів завдяки гнучкій архітектурі:

1. **Формат атрибутів TLV (Type-Length-Value)**:
   Повідомлення Netlink містять заголовок `struct nlmsghdr` та ланцюжок вкладених атрибутів `struct nlattr`. Якщо ядро додає новий параметр конфігурації, воно просто реєструє новий номер атрибута. Старі утиліти просто ігнорують невідомі їм теги, не ламаючи бінарної сумісності.
2. **Атомарність конфігурації**:
   Створення моста та встановлення всіх його початкових параметрів передаються ядру в одному єдиному бінарному повідомленні `RTM_NEWLINK` під єдиним блокуванням `rtnl_lock()`.
3. **Посторінкове вивантаження FDB (Multipart Dumps)**:
   Для отримання великих таблиць FDB використовується механізм `RTM_GETNEIGH` із прапорцем `NLM_F_DUMP`. Ядро надсилає дані частинами у вигляді серії повідомлень `NLM_F_MULTI`, не перевантажуючи пам'ять і не блокуючи комутаційний рушій.
4. **Асинхронні сповіщення (Push Notifications)**:
   Програми простору користувача (демони маршрутизації, оркестратори контейнерів) відкривають Netlink-сокет і підписуються на мультикаст-групи `RTNLGRP_LINK` та `RTNLGRP_NEIGH`. Коли змінюється стан порту, підключається новий лінк або вивчається нова MAC-адреса, ядро миттєво надсилає подію відповідному демону без потреби у безперервному опитуванні (polling).

Утиліту `brctl` із пакету `bridge-utils` було офіційно оголошено застарілою (deprecated), а в сучасних дистрибутивах Linux керування повністю перейшло до утиліт пакету `iproute2`:
- `ip link add name br0 type bridge` — створення екземпляра моста;
- `bridge fdb show` — робота з таблицею комутації;
- `bridge vlan show` — конфігурація членства у віртуальних мережах VLAN;
- `bridge link set dev eth0 ...` — налаштування прапорців та властивостей портів.

## 5. Революція VLAN Filtering (Linux 3.8+)

У 2012–2013 роках розробники Влад Ясевич (Vlad Yasevich, компанія Red Hat), Стівен Хеммінгер (Stephen Hemminger, Vyatta/Brocade) та Рупа Прабху (Roopa Prabhu, Cumulus Networks) запропонували фундаментальне архітектурне оновлення, яке було інтегровано в ядро Linux 3.8 під прапорцем конфігурації **`CONFIG_BRIDGE_VLAN_FILTERING`**.

Цей механізм перетворив Linux Bridge із простого хабу на повноцінний керований комутатор стандарту IEEE 802.1Q з апаратною логікою фільтрації, тегування та розтегування трафіку на кожному окремому порті.

```
+--------------------------------------------------------------------+
|                         Linux Bridge br0                           |
|                      (vlan_filtering = 1)                          |
|                                                                    |
|  Таблиця FDB з двовимірним пошуком: Ключ = { MAC-адреса, VID }      |
+--------------------+-----------------------+-----------------------+
| Порт eth0          | Порт tap0 (VM 1)      | Порт tap1 (VM 2)      |
| Режим: Trunk       | Режим: Access         | Режим: Access         |
| Дозволені: 100,200 | PVID: 100             | PVID: 200             |
|                    | Egress: untagged      | Egress: untagged      |
+--------------------+-----------------------+-----------------------+
        ^                       ^                       ^
        |                       |                       |
[ Теговані кадри ]     [ Нетеговані кадри ]    [ Нетеговані кадри ]
  VLAN 100, 200            (Клієнт 1)              (Клієнт 2)
```

### Механізм роботи VLAN Filtering

Замість створення сотень віртуальних мостів під кожен окремий VLAN створюється **один єдиний екземпляр моста** `br0` з увімкненою фільтрацією:
```bash
ip link add name br0 type bridge vlan_filtering 1
```

Кожен порт моста отримує компактну внутрішню таблицю членства у VLAN (`struct net_bridge_vlan_group`), що містить бітові маски та конфігураційні прапорці для кожного діапазону тегів від 1 до 4094:

1. **PVID (Port VLAN ID)**:
   Призначений для портів доступу (Access Ports). Коли від віртуальної машини або контейнера надходить звичайний нетегований кадр Ethernet, міст у точці входу перевіряє значення PVID порту і призначає кадру внутрішній тег `VID` (записуючи його у метадані сокетного буфера `skb->vlan_tci`). Якщо кадр нетегований, а на порті немає PVID, міст відкидає такий пакет.
2. **Контроль входу (Ingress Filter)**:
   Якщо на порт надходить кадр, який уже містить 4-байтний заголовок 802.1Q, міст перевіряє, чи входить зазначений `VID` до списку дозволених для цього порту (`br_vlan_allowed_ingress()`). Якщо порт не є членом цього VLAN, кадр скидається негайно.
3. **Egress Untagged**:
   Наказує комутатору автоматично знімати заголовок 802.1Q під час передачі кадру в напрямку клієнта. Віртуальна машина або контейнер отримує чистий стандартний Ethernet-кадр, навіть не підозрюючи про внутрішню структуру тегування в мережі хоста.
4. **Магістральні порти (Trunk Ports)**:
   Фізичні аплінки (наприклад, `eth0`) налаштовуються зі списком дозволених VLAN (наприклад, 100–200) без прапорця Egress Untagged. Кадри передаються на фізичний комутатор зі збереженням оригінальних 4-байтних тегів 802.1Q.

### Двовимірна таблиця FDB {MAC, VID}

Найважливішою зміною стала трансформація таблиці комутації FDB:
- У класичному мості ключ пошуку складався лише з 6 байтів MAC-адреси;
- У мості з підтримкою VLAN Filtering ключем FDB стала комбінація `{MAC-адреса, VLAN ID}` (8 байтів).

```
+-------------------+---------+-----------+-----------------------+
|    MAC-адреса     | VLAN ID |   Порт    |      Тип запису       |
+-------------------+---------+-----------+-----------------------+
| 52:54:00:12:34:56 |   100   |   tap0    | Dynamic (Клієнт 1)    |
| 52:54:00:12:34:56 |   200   |   tap1    | Dynamic (Клієнт 2)    |
| 00:11:22:33:44:55 |   100   |   eth0    | Dynamic (Аплінк)      |
+-------------------+---------+-----------+-----------------------+
```

Це повністю розв'язало проблему ізоляції клієнтів. Два різні клієнти у різних VLAN можуть випадково або навмисно використовувати повністю ідентичні MAC-адреси (наприклад, дефолтні адреси віртуальних маршрутизаторів). Оскільки пошук у геш-таблиці моста розділено за `VID`, конфлікту записів не виникає, а трафік гарантовано не потрапляє до чужого сегмента.

### Результати впровадження VLAN Filtering

1. **Однопрохідна обробка пакетів**: пакет проходить крізь ядро рівно за один виклик функції `br_handle_frame()` — без каскадного стрибання через проміжні інтерфейси `eth0.X` та окремі мости;
2. **Колосальна економія пам'яті**: замість створення тисяч важких об'єктів `struct net_device` хост використовує один міст, усередині якого пам'ять під VLAN виділяється у вигляді компактних бітових масивів та структур `struct net_bridge_vlan`;
3. **Зниження затримки та розвантаження CPU**: усунення проміжних черг скоротило накладні витрати CPU у щільних віртуалізованих середовищах на 40–60%, забезпечивши максимальну локальність даних у кешах L1/L2 процесора.

## 6. Ера Switchdev та апаратне розвантаження (Linux 4.x+)

У 2014–2016 роках у дата-центрах розпочалася хвиля відкритого мережевого обладнання (Open Networking) під егідою Open Compute Project (OCP). Великі провайдери та хмарні платформи відмовилися від дорогих закритих комутаторів із пропрієтарними операційними системами на користь комутаторів без попередньо встановленого ПЗ (Whitebox Switches).

Такі пристрої комплектувалися надшвидкими кремнієвими чіпами комутації — **ASIC (Application-Specific Integrated Circuits)** від виробників Mellanox/Nvidia (Spectrum), Broadcom (Trident, Tomahawk), Marvell (Prestera) або Barefoot (Tofino). Вони були здатні комутувати кадри на апаратному рівні на повній швидкості дроту (Line Rate) — від 100 Гбіт/с до десятків терабіт на секунду.

```
+--------------------------------------------------------------------+
|  Control Plane (Простір користувача Linux):                        |
|  - Утиліти iproute2 (ip link, bridge vlan, bridge fdb)             |
|  - Демони маршрутизації BGP/OSPF (FRRouting, BIRD), демон mstpd    |
+--------------------------------------------------------------------+
                                | Стандартний Netlink API
                                v
+--------------------------------------------------------------------+
|  Control Plane (Ядро Linux):                                       |
|  - Підсистема Linux Bridge (FDB, VLAN Filtering, STP)              |
|  - Маршрутизація IPv4/IPv6 (FIB), класифікація трафіку (TC)        |
+--------------------------------------------------------------------+
                                | Події підсистеми Switchdev
                                | (SWITCHDEV_OBJ_PORT_VLAN, FDB_ADD)
                                v
+--------------------------------------------------------------------+
|  Драйвер комутаційного чіпа (mlxsw, prestera, rocker)              |
+--------------------------------------------------------------------+
                                | Регістри керування, DMA, TCAM
                                v
+--------------------------------------------------------------------+
|  Data Plane: Апаратний кремнієвий ASIC (Line Rate 100G / 400G+)    |
|  - Апаратна комутація L2/L3 без участі центрального процесора      |
|  - Апаратне вивчення MAC та фільтрація VLAN                        |
+--------------------------------------------------------------------+
```

### Філософія Switchdev проти пропрієтарних SDK

Спочатку виробники обладнання пропонували керувати ASIC-чіпами за допомогою пропрієтарних бібліотек простору користувача (User-space SDK / SAI). Це повністю відрізало стандартні інструменти Linux: ядро не бачило портів комутатора, утиліти `ip`, `bridge`, `tcpdump` не працювали, а системні адміністратори були змушені використовувати чужі нестандартні CLI-оболонки.

Розробники мережевого стека ядра (Іржі Пірко — Jiri Pirko, Ідо Шіммель — Ido Schimmel, Скотт Фельдман — Scott Feldman) наполягли на фундаментальному принципі Linux: **апаратний комутатор повинен розглядатися як звичайний мережевий адаптер Linux**. 

У 2015 році в ядро Linux 4.x було впроваджено підсистему **Switchdev**. Вона перетворила стандартний Linux Bridge на універсальний програмний рівень керування (Control Plane) для апаратних комутаторів.

### Двостороння модель синхронізації Switchdev

Підсистема Switchdev організовує безшовну двосторонню взаємодію між ядром операційної системи та залізом:

1. **Фізичні порти як мережеві інтерфейси `net_device`**:
   Кожен фізичний порт на передній панелі комутатора реєструється в ядрі Linux як звичайний мережевий інтерфейс (наприклад, `swp1`, `swp2`, `swp3`).
2. **Керування від Control Plane до кремнію**:
   Адміністратор або оркестратор об'єднує порти у звичайний міст Linux і налаштовує VLAN стандартними командами:
   ```bash
   ip link set dev swp1 master br0
   bridge vlan add dev swp1 vid 100
   ```
   Підсистема Linux Bridge через ланцюжок нотифікаторів `switchdev` перехоплює кожну операцію (`SWITCHDEV_OBJ_PORT_VLAN`, `SWITCHDEV_FDB_ADD_TO_DEVICE`) і передає її драйверу апаратного чіпа (наприклад, `mlxsw`). Драйвер записує правила у внутрішні апаратні таблиці TCAM та пам'ять комутатора.
3. **Синхронізація від кремнію до ядра**:
   Коли комутатор на апаратному рівні вивчає новий MAC-адрес на швидкості 100 Гбіт/с, чіп генерує переривання/DMA-повідомлення до драйвера. Драйвер надсилає подію `SWITCHDEV_FDB_ADD_TO_BRIDGE` у підсистему Linux Bridge, автоматично наповнюючи таблицю FDB ядра з прапорцем `offload`.
4. **Розподіл на швидкий та повільний шляхи**:
   - **Fast Path (Апаратний шлях)**: 99.999% користувацького трафіку комутується всередині кремнієвого чіпа на швидкості дроту з нульовим залученням процесора хоста і субмікросекундними затримками;
   - **Slow Path (Повільний шлях винятків)**: службовий трафік (кадри STP BPDU, пакети протоколів маршрутизації BGP/OSPF, кадри LACP для агрегації лінків або пакети з невідомими заголовками) чіп перенаправляє в черги ядра Linux. Демони простору користувача (`mstpd`, `FRRouting`, `lldpd`) обробляють їх через стандартні сокети.

Завдяки Switchdev відкриті мережеві операційні системи (SONiC від Microsoft, Cumulus Linux, Dent OS на базі Linux Foundation) отримали можливість працювати поверх стандартного ядра Linux без пропрієтарних прошарків.

Еволюція Linux Bridge відображає фундаментальну тенденцію розвитку ядра Linux: рух від простого монолітного коду, написаного під вузьку задачу локальної мережі, до модульної, строго розділеної на рівні Control/Data Plane архітектури, здатної керувати інфраструктурою дата-центрів.
