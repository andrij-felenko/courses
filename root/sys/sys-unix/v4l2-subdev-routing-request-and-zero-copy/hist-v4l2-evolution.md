# 📜 Історія еволюції Video4Linux: від BT848 до Media Controller

Наприкінці 1990-х років відеозахоплення у ПК асоціювалося переважно з ТБ-тюнерами та аналоговими PCI-карточками на базі чипів Brooktree BT848 або BT878. Для обслуговування цих пристроїв у ядрі Linux 2.1 з'явилася перша версія підсистеми — **Video4Linux (V4L1)**. Вона надавала просту модель: пристрій представлений файлом `/dev/video0`, читання кадру здійснювалося через системний виклик `read()` або базовий `mmap()`, а налаштування каналу чи гучності ТБ-сигналу проходили через набір фундаментальних `ioctl`.

Модель V4L1 чудово працювала з аналоговими відеодекодерами того часу, однак мала критичні архітектурні вади. По-перше, системний виклик `read()` вимагав постійного копіювання даних із простору ядра у простір користувача, що при роздільній здатності 640×480 та частоті 30 кадрів на секунду створювало відчутне навантаження на системну шину та ЦП. По-друге, API не мав механізму узгодження піксельних форматів (format negotiation): застосунок не міг дізнатися, які формати підтримує апаратура, без спроб застосувати конкретний режим.

У 1999 році розробники Білл Дірп (Bill Dirks) та Майкл Шмаль (Michael Schimek) розпочали роботу над новою версією — **Video4Linux2 (V4L2)**, яка увійшла до основного дерева ядра у версії Linux 2.5.67 (і була бекпортована у 2.4). V4L2 внесла революційні для свого часу покращення:
- Окремий механізм ідентифікації форматів через чотирибайтові коди **FourCC** (наприклад `V4L2_PIX_FMT_YUYV` чи `V4L2_PIX_FMT_MJPEG`).
- Запити та узгодження форматів через ioctls `VIDIOC_ENUM_FMT`, `VIDIOC_G_FMT` та `VIDIOC_S_FMT`.
- Фреймворк управління буферами за допомогою кільцевих черг (ring buffers) та викликів `VIDIOC_REQBUFS`, `VIDIOC_QBUF`, `VIDIOC_DQBUF`.
- Ієрархію V4L2 controls (`VIDIOC_QUERYCTRL`, `VIDIOC_S_CTRL`) для гнучкого регулювання параметрів зображення (яскравість, контраст, експозиція).

Протягом майже десятиліття V4L2 залишався взірцевим API для будь-яких USB веб-камер (особливо після стандартизації USB Video Class, UVC) та аналогових грабберів.

## Криза мобільних SoC (2008–2010)

Ситуація докорінно змінилася з початком ери смартфонів та вбудованих систем на кристалі (SoC). Мобільні процесори OMAP3 від Texas Instruments, Exynos від Samsung та Tegra від Nvidia більше не мали справи з інтегрованою веб-камерою, яка віддає готовий стиснутий потік.

Замість цього апаратна частина камери смартфона перетворилася на складну розподілену мережу:
1. Сенсор камери (наприклад Omnivision чи Sony) підключався через серійну шину MIPI CSI-2 для даних та I2C для керування регістрами.
2. Лінії MIPI підключалися до апаратного блоку CSI-2 Receiver у SoC.
3. Отриманий сирий кадр (Bayer RAW) прямував до Image Signal Processor (ISP), який виконував апаратну дебайєризацію, дезашумлення, корекцію лінзи, автофокус (AF) та автоекспозицію (AE).
4. З ISP виходило кілька паралельних потоків: потік високої роздільної здатності для запису фото, потік низької роздільної здатності для прев'ю на екрані, та потік статистичних даних для алгоритмів 3A.

Спроба запхати таку топологію у класичну концепцію V4L2, де кожен файл у `/dev/videoX` описував «монолітну камеру», призвела до хаосу. Драйвери SoC почали створювати власні приватні `ioctl` для налаштування маршрутизації між сенсором та ISP. Кожен виробник плати реалізовував свій велосипед, користувацький простір втратив універсальність, а драйвери ядра перетворилися на непідтримувані моноліти («spaghetti code»).

## Народження Media Controller та Subdevice API

Революційне рішення запропонував розробник ядра Лоран Піншар (Laurent Pinchart). У 2010 році він представив концепцію **Media Controller API**, яка була офіційно включена до ядра Linux 2.6.39.

Головна філософська зміна полягала у розділенні відповідальності:
- V4L2 відповідає за передачу буферів пам'яті між ядром та користувачем (DMA video nodes `/dev/videoX`).
- **Media Controller API** відповідає за відкриття «чорного ящика» апаратури: він описує топологію у вигляді графа сутностей (entities), їхніх контактних майданчиків (pads) та зв'язків (links) через файл `/dev/mediaX`.
- **V4L2 Subdevice API** дозволяє налаштовувати формати та параметри кожного внутрішнього блоку (сенсора, ISP) окремо через файли `/dev/v4l2-subdevX`.

Такий підхід дозволив розробникам ядра прибрати з драйверів припущень про жорстко зафіксовану конфігурацію апаратури. Користувацький простір отримав можливість динамічно конфігурувати зв'язки: наприклад, пустити кадри від сенсора напряму у пам'ять в режимі RAW, або спрямувати їх через ISP у формат YUV.

## Сучасний стан та еволюція до libcamera

Поява Media Controller успішно вирішила проблему абстракції в ядрі, однак переклала величезний обсяг роботи на простір користувача. Якщо раніше застосунку достатньо було відкрити `/dev/video0` і викликати `VIDIOC_S_FMT`, то у світі Media Controller застосунок повинен самостійно знайти граф пристроїв, обійти всі pads, узгодити Media Bus Codes на кожному переході, увімкнути потрібні links та налаштувати 3A-алгоритми.

Це призвело до нового витка еволюції: створення проектів **PipeWire** та **libcamera**. Сучасний стек Linux розглядає V4L2 та Media Controller не як прикладне API для звичайних розробників ПЗ, а як низькорівневий системний ABI ядра. Тісна інтеграція з фреймворком `dma-buf` та Media Request API завершила формування сучасного відеостеку, який забезпечує нульове копіювання (Zero-Copy) від сенсора камери до GPU та дисплея.
