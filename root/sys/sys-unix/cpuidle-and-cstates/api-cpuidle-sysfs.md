# 📋 Довідка: cpuidle у sysfs, `/dev/cpu_dma_latency` і ключі завантаження

Керування простоєм відкрите назовні трьома засобами — деревом файлів у sysfs (прочитати таблицю станів зі статистикою й перемкнути керувальник на ходу), символьним пристроєм `/dev/cpu_dma_latency` (заявити гранично допустимий час виходу) і кількома параметрами командного рядка ядра (обрізати глибину ще до того, як драйвер зареєструється). Нижче — точні імена файлів, одиниці значень і протокол кожного з трьох.

## Дерево sysfs

```
/sys/devices/system/cpu/
├─ cpuidle/
│  ├─ current_driver         intel_idle | acpi_idle | processor_idle | …
│  ├─ current_governor       menu | teo | ladder | haltpoll   (пишеться)
│  ├─ current_governor_ro    те саме значення, лише читання
│  └─ available_governors    перелік через пробіл
├─ cpu0/
│  ├─ cpuidle/
│  │  ├─ state0/   ← найменша глибина (звично POLL)
│  │  ├─ state1/
│  │  └─ stateN/   ← найбільша глибина
│  │     ├─ name  desc  latency  residency  power
│  │     ├─ usage  time  above  below  rejected
│  │     ├─ disable  default_status
│  │     └─ s2idle/{usage,time}
│  └─ power/
│     └─ pm_qos_resume_latency_us
└─ cpu1/ … cpuN/                (таке саме дерево на кожному ядрі)
```

Число в `stateM` — індекс у таблиці драйвера, і таблиця впорядкована за зростанням глибини, тож `state0` завжди найлегший стан. Прив'язки до імені немає: `state3` на одній машині буде `C6`, на іншій — `C3`. Читати треба `name`, а не номер. Тека повторюється на кожному ядрі, бо всі лічильники — свої на ядро, і `disable` теж діє лише на своє ядро. Загальну механіку цих файлів-атрибутів описує [модель пристроїв у sysfs](topic:sys-unix/sysfs-device-model).

## Загальні файли підсистеми

| Файл | Що показує | Запис |
|---|---|---|
| `current_driver` | ім'я драйвера, що зареєструвався; `none`, якщо підсистему вимкнено | — |
| `available_governors` | усі зібрані в ядрі керувальники, через пробіл | — |
| `current_governor` | чинний керувальник | ім'я з переліку — перемикає **одразу на всій машині** |
| `current_governor_ro` | те саме значення | — |

## Атрибути стану

| Файл | Що це | Одиниця |
|---|---|---|
| `name` | коротке ім'я: `POLL`, `C1`, `C1E`, `C6`, платформне | рядок |
| `desc` | довший опис; `intel_idle` кладе туди підказку `MWAIT 0x20`, `acpi_idle` — спосіб входу з таблиць прошивки | рядок |
| `latency` | час виходу зі стану | мкс |
| `residency` | мінімальний виправданий простій | мкс |
| `power` | споживання в цьому стані; майже завжди `0`, бо виробники поля не заповнюють | мВт |
| `usage` | скільки разів це ядро просило залізо ввійти сюди | лічильник |
| `time` | сумарний час у стані **за виміром ядра** | мкс |
| `above` | просили цей стан, а простій вийшов явно закороткий для нього | лічильник |
| `below` | просили цей стан, а глибший підійшов би краще | лічильник |
| `rejected` | запит на вхід відхилено | лічильник |
| `disable` | `0` / `1` — чи вимкнено стан на цьому ядрі | **єдиний, що пишеться** |
| `default_status` | `enabled` / `disabled` — з чим стан з'явився | рядок |
| `s2idle/usage`, `s2idle/time` | те саме, але пораховане окремо за час [призупинення в простій](topic:sf-os/suspend-and-resume) | лічильник, мкс |

Три речі, без яких ці числа читаються хибно. По-перше, лічильники монотонні від завантаження й не скидаються нічим — міряти можна лише різницею двох знімків. По-друге, `time` — не апаратний лічильник резидентності, а вимір ядра від команди входу до пробудження; залізо могло не піти так глибоко, як його просили. По-третє, `above` і `below` рахують **промахи керувальника**, а не помилки заліза: великий `below` на мілкому стані означає, що керувальник систематично не досипає, великий `above` на глибокому — що пірнає марно.

## Мінімальний зріз

```sh
cd /sys/devices/system/cpu/cpu0/cpuidle
for s in state*/; do
    printf '%-7s %-5s lat=%-5s res=%-5s usage=%-9s above=%-8s below=%s\n' \
        "${s%/}" "$(cat "$s/name")"  "$(cat "$s/latency")" "$(cat "$s/residency")" \
        "$(cat "$s/usage")" "$(cat "$s/above")" "$(cat "$s/below")"
done
```

```
state0  POLL  lat=0     res=0     usage=14211     above=0        below=0
state1  C1    lat=2     res=2     usage=1892344   above=1204     below=98211
state2  C1E   lat=10    res=20    usage=744102    above=88431    below=210554
state3  C6    lat=85    res=200   usage=2310887   above=331209   below=0
```

## Керування станами

```sh
# вимкнути найглибший стан на ВСІХ ядрах (тимчасово, до перезавантаження)
for d in /sys/devices/system/cpu/cpu*/cpuidle/state3; do echo 1 | sudo tee "$d/disable"; done

# перемкнути керувальник на ходу — одразу на всю машину
cat /sys/devices/system/cpu/cpuidle/available_governors   # menu teo ladder
echo teo | sudo tee /sys/devices/system/cpu/cpuidle/current_governor
```

## `/dev/cpu_dma_latency`: вимога до часу виходу

| Що | Як |
|---|---|
| відкриття | `open("/dev/cpu_dma_latency", O_RDWR)` — сам факт відкриття вже додає вимогу до глобального списку (з усталеним значенням) |
| запис двійковий | **рівно 4 байти** — знакове 32-бітове ціле в машинному порядку байтів |
| запис рядком | будь-яка інша довжина розбирається як число **в шістнадцятковій системі**: `0x00000032` → 50 |
| одиниця | мікросекунди; це верхня межа для `latency` станів, які керувальник має право вибирати |
| повторний запис | оновлює вимогу; закривати й відкривати не треба |
| читання | повертає 4 байти — **чинну межу на машині** (мінімум усіх вимог), а не вашу власну |
| зняття | закриття дескриптора, зокрема смертю процесу; жодного «файлу з налаштуванням» не лишається |
| усталене | `2000000000` мкс — тобто «межі немає» |

```c
/* latency-hold.c — тримає вимогу, доки жива програма.  cc -o latency-hold latency-hold.c */
#include <fcntl.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(int argc, char **argv)
{
        int32_t want = (argc > 1) ? atoi(argv[1]) : 0;   /* мкс; 0 — «без сну взагалі» */
        int32_t effective;

        int fd = open("/dev/cpu_dma_latency", O_RDWR);
        if (fd < 0) { perror("open"); return 1; }

        if (write(fd, &want, sizeof want) != sizeof want) { perror("write"); return 1; }

        if (read(fd, &effective, sizeof effective) == sizeof effective)
                printf("чинна межа на машині: %d мкс\n", effective);

        pause();          /* вимога чинна рівно доти, доки відкрито fd */
        close(fd);
        return 0;
}
```

Те саме з оболонки — важливо тримати дескриптор відкритим, а не писати перенаправленням:

```sh
exec 3<>/dev/cpu_dma_latency   # відкрили — вимога існує
printf '0x00000032' >&3        # 50 мкс
# … критична за затримкою робота …
exec 3<&-                      # закрили — вимогу знято
```

Дві пастки того самого протоколу. `echo 50 > /dev/cpu_dma_latency` не працює двічі: перенаправлення закриває дескриптор одразу після запису (вимога живе мілісекунду), а сам рядок `50` розбереться як шістнадцятковий і дасть 80 мкс. І навпаки: рядок довжиною **рівно чотири байти** (скажімо, `1000`) ядро прийме за двійкове число й отримає сміття. Нуль означає «жодного стану з ненульовим часом виходу» — лишається `POLL`, і машина в простої споживає стільки ж, скільки під навантаженням.

Поряд є вимога на **одне** ядро: `/sys/devices/system/cpu/cpuN/power/pm_qos_resume_latency_us` — знакове 32-бітове число мікросекунд у текстовій формі. Керувальник бере мінімум із глобальної межі й цієї. Різниця принципова: цей файл — звичайне налаштування sysfs, воно лишається чинним і після того, як програма, що його записала, померла.

## Ключі командного рядка ядра

Подаються [завантажувачем у рядку ядра](topic:sys-unix/bootloader-and-cmdline); чинні значення параметрів модулів видно в `/sys/module/intel_idle/parameters/` — [так само, як у будь-якого модуля](topic:sys-unix/kernel-modules).

| Параметр | Що робить |
|---|---|
| `cpuidle.off=1` | вимикає підсистему цілком; цикл простою падає на типовий архітектурний шлях (на x86 — `hlt`) |
| `cpuidle.governor=teo` | назвати керувальник на старті |
| `idle=poll` | ніякого сну: порожній цикл; `intel_idle` і `acpi_idle` не реєструються |
| `idle=halt` | лише `hlt`, без `mwait` і без цих драйверів |
| `idle=nomwait` | заборонити `mwait`: `acpi_idle` бере `hlt`, `intel_idle` не вмикається |
| `intel_idle.max_cstate=2` | відкинути стани, глибші за вказаний індекс; `0` — драйвер не зареєструється взагалі |
| `intel_idle.states_off=3` | бітова маска станів, вимкнених від початку (`3` = стани 0 і 1); видно як `default_status=disabled`, вмикається назад через `disable` |
| `processor.max_cstate=1` | те саме обрізання, але для `acpi_idle` |
| `nohz=off` | не спиняти тик у простої — глибокі стани перестають окупатися |

## Спостереження

| Джерело | Що дає |
|---|---|
| `power:cpu_idle` | поля `state` (u32) і `cpu_id` (u32); при вході `state` — індекс стану, при виході — `4294967295` (тобто −1). Пара подій дає точну тривалість кожного простою |
| `power:cpu_idle_miss` | ядро само повідомляє про промах: `cpu_id`, `state` і бік помилки (`below` — узяли замілко) |
| `power:pm_qos_update_target` | момент, коли чинна межа затримки змінилася, і на яке значення |

```sh
echo 1 > /sys/kernel/tracing/events/power/cpu_idle/enable
cat /sys/kernel/tracing/trace_pipe
#  <idle>-0  [002] d..1  914.402118: cpu_idle: state=3 cpu_id=2
#  <idle>-0  [002] d..1  914.403994: cpu_idle: state=4294967295 cpu_id=2
```

Механіку самого трасування розбирає [ftrace і трасувальні точки ядра](topic:sys-unix/ftrace-kernel-tracing).

`turbostat` показує **два різні набори колонок**, і плутати їх не можна:

| Колонка | Звідки | Що означає |
|---|---|---|
| `C1`, `C1E`, `C6` | sysfs `usage` | скільки разів Linux **просив** цей стан |
| `C1%`, `C1E%`, `C6%` | sysfs `time` | яку частку часу Linux **записав** у цей стан |
| `CPU%c1`, `CPU%c6`, `CPU%c7` | апаратні лічильники (MSR) | скільки ядро **справді** пробуло в апаратному стані |
| `Pkg%pc2`, `Pkg%pc6` | апаратні лічильники (MSR) | те саме для всього пакета |
| `Busy%`, `Bzy_MHz`, `Avg_MHz` | MSR | частка часу з виконанням інструкцій і частота — сама або з урахуванням простою |
| `IRQ` | лічильники переривань | скільки переривань обслужило ядро за інтервал |
| `PkgWatt`, `CorWatt` | лічильники енергії | ватти на весь пакет і на його ядерну частину |

```sh
turbostat --quiet --show Busy%,Bzy_MHz,IRQ,C1%,C6%,CPU%c1,CPU%c6,Pkg%pc6,PkgWatt sleep 10
```

`powertop` дивиться в ті самі sysfs-лічильники, але подає їх зручніше: вкладка **Idle stats** — таблиця станів по ядрах і по пакету, **Overview** — рейтинг того, хто саме будить машину. Звіт за проміжок: `powertop --time=20 --html=idle.html`.

> 🔧 **Навіщо це.** Розбіжність двох наборів колонок і є головним діагностичним сигналом. Якщо `C6%` близько ста, а `CPU%c6` — одиниці, ядро **просило** глибокий сон, а залізо туди не потрапляло: щось будило його швидше, ніж він устигав відбутися. Далі дивляться `IRQ` і `above` у `state*/`, а хто саме будить — знаходять по `power:cpu_idle`. Якщо ж навпаки, `Pkg%pc6` майже нуль при високих `CPU%c6` на всіх ядрах, — сплять ядра, але не пакет, і винне щось спільне: неспинений таймер, пристрій на шині, одне ядро, що не спить. Обидва випадки виглядають однаково в споживанні й лікуються по-різному, а `PkgWatt` покаже, чи справді щось змінилося.
