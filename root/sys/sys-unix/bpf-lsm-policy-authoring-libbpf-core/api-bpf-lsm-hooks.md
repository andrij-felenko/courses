# 📋 Каталог LSM-хуків для BPF-LSM: параметри, контекст та права

Цей довідник описує повну поверхню програмного інтерфейсу (API) точок перехоплення (LSM hooks) ядра Linux, які доступні для підключення eBPF-програм типу `BPF_PROG_TYPE_LSM`. Він містить розкладку сигнатур функцій ядра, аналіз переданих структур даних, розбір семантики повернення кодів помилок, каталог спеціалізованих BPF-хелперів та опис специфічних контрактів безпеки, які необхідно враховувати при розробці надійних політик безпеки.

## 1. Загальний контракт та принцип роботи BPF-LSM програм

Кожен LSM-хук у ядрі Linux виступає як точна точка перевірки прав безпосередньо перед виконанням потенційно небезпечної операції у внутрішньоядерних підсистемах (VFS, підсистема обробки процесів, мережевий стек, IPC). Програма BPF-LSM оголошується за допомогою секції `SEC("lsm/<hook_name>")` та описується спеціальним макросом `BPF_PROG(prog_name, args...)`, який розпаковує оригінальні параметри функції ядра у зручні аргументи мови C.

### 1.1. Семантика кодів повернення та ланцюжок виконання

Код повернення BPF-LSM програми визначає підсумкове рішення щодо системного виклику, який спровокував виклик хука:

* **`0` (Zero / Success):** Операцію дозволено. Перевірка даної BPF-політики пройшла успішно. Ядро передає контроль наступним завантаженим модулям у ланцюжку LSM (наприклад, `capability`, `apparmor`, `landlock`) або продовжує безпосереднє виконання системного виклику.
* **`-EPERM` (Operation not permitted, `-1`):** Операцію категорично заборонено. Ядро припиняє виконання системного виклику і повертає цей код помилки користувацькому процесу. Використовується для блокування дій, що суперечать встановленій політиці безпеки.
* **`-EACCES` (Permission denied, `-13`):** Альтернативний код відмови в доступі. Зазвичай повертається при VFS-перевірках файлових операцій для збереження повної POSIX-сумісності.
* **`-ENOMEM`, `-EINVAL`, `-E2BIG`:** Від'ємні коди внутрішніх помилок, які повертаються у разі вичерпання ресурсів пам'яті або подачі некоректних аргументів.

> ⚠️ **Правило найсуворішого обмеження (LSM Stacking):** Якщо у системі завантажено кілька модулів LSM (наприклад, `capability`, `landlock`, `bpf`), діє правило логічного "І": якщо хоча б один модуль повертає від'ємне значення, ядро негайно блокує операцію та перериває системний виклик.

## 2. Повний каталог критичних LSM-хуків ядра

### 2.1. Підсистема управління процесами та виконанням

#### `bprm_check_security`
Викликається в системних викликах `execve()` та `execveat()` після того, як ядро успішно розібрало виконуваний файл і підготувало внутрішньоядерну структуру `linux_binprm`. Це головна точка для побудови політик контролю запуску бінарних файлів та аналізу командного рядка.

* **Сигнатура ядра:** `int security_bprm_check(struct linux_binprm *bprm)`
* **Аналіз структур даних:**
  * `bprm->filename` (`const char *`): Шлях до файлу або інтерпретатора скриптів (наприклад, `/usr/bin/python3`).
  * `bprm->file` (`struct file *`): VFS-дескриптор виконуваного об'єкта, з якого можна витягти inode, права доступу та конфігурацію файлової системи.
  * `bprm->cred` (`struct cred *`): Нова структура credentials, які процес отримає після успішного запуску (зокрема UID, GID, EUID, EGID та розширені capabilities).
  * `bprm->argc`, `bprm->envc` (`int`): Кількість аргументів командного рядка та змінних оточення.
* **Контекст безпеки та перевірка:** BPF-програма може безпечно зчитувати `bprm->filename`, але модифікація полів `bprm` заборонена верифікатором. Для отримання повного канонічного VFS-шляху об'єкта використовується BPF-хелпер `bpf_d_path(&bprm->file->f_path, buf, size)`.

#### `task_alloc`
Викликається під час створення нового процесу або потоку в системних викликах `fork()`, `vfork()`, `clone()` та `clone3()`.

* **Сигнатура ядра:** `int security_task_alloc(struct task_struct *task, unsigned long clone_flags)`
* **Параметри:**
  * `task` (`struct task_struct *`): Вказівник на структуру нового процесу-нащадка, що створюється в ядрі.
  * `clone_flags` (`unsigned long`): Бітова маска прапорців клонування (`CLONE_NEWPID`, `CLONE_NEWNET`, `CLONE_NEWNS`, `CLONE_VM`, `CLONE_THREAD`).
* **Контекст безпеки:** Дозволяє ефективно регулювати створення процесів, запобігати DoS-атакам типу `fork`-бомба та контролювати створення нових ізольованих просторів імен (namespaces).

#### `task_fix_setuid`
Викликається при спробі зміни ідентифікаторів користувача (UID/EUID/SUID) через системні виклики `setuid()`, `setreuid()`, `setresuid()`.

* **Сигнатура ядра:** `int security_task_fix_setuid(struct cred *new, const struct cred *old, int flags)`
* **Параметри:**
  * `new` (`struct cred *`): Запропонована нова структура привілеїв процесу.
  * `old` (`const struct cred *`): Поточна структура привілеїв.
  * `flags` (`int`): Прапорці типу зміни (`LSM_SETID_ID`, `LSM_SETID_RE`, `LSM_SETID_RES`).
* **Контекст безпеки:** Надає можливість блокувати спроби підвищення привілеїв до `UID 0` (root) навіть якщо бінарний файл має встановлений прапорець `SUID`.

### 2.2. Віртуальна файлова система (VFS) та операції з inode

#### `file_open`
Викликається при відкритті файлу через системні виклики `open()`, `openat()`, `openat2()` після успішного проходження перевірок DAC.

* **Сигнатура ядра:** `int security_file_open(struct file *file)`
* **Поля структури `struct file`:**
  * `file->f_path` (`struct path`): Комбінована структура, що містить вказівники на `dentry` та `vfsmount` об'єкта.
  * `file->f_flags` (`unsigned int`): Прапорці режимів відкриття (`O_RDONLY`, `O_WRONLY`, `O_RDWR`, `O_CREAT`, `O_TRUNC`, `O_APPEND`).
  * `file->f_cred` (`const struct cred *`): Структура привілеїв суб'єкта, який запитує доступ до файлу.
* **Контекст безпеки:** Ідеальне місце для контролю доступу до конфіденційних файлів (наприклад, конфігураційних файлів, ключів SSH, системних баз даних) та блокування відкриття на запис у режимі read-only.

#### `inode_permission`
Низькорівневий хук VFS, що викликається при кожній перевірці прав доступу до inode об'єкта.

* **Сигнатура ядра:** `int security_inode_permission(struct inode *inode, int mask)`
* **Параметри:**
  * `inode` (`struct inode *`): Вказівник на об'єкт inode файлової системи.
  * `mask` (`int`): Маска запитуваних дій (`MAY_READ`, `MAY_WRITE`, `MAY_EXEC`, `MAY_ACCESS`).

#### `mmap_file`
Викликається при відображенні файлу у віртуальну пам'ять процесу через системний виклик `mmap()`.

* **Сигнатура ядра:** `int security_mmap_file(struct file *file, unsigned long reqprot, unsigned long prot, unsigned long flags)`
* **Параметри:**
  * `reqprot` / `prot` (`unsigned long`): Запропоновані та підсумкові права захисту сторінок пам'яті (`PROT_READ`, `PROT_WRITE`, `PROT_EXEC`).
  * `flags` (`unsigned long`): Прапорці мапування (`MAP_SHARED`, `MAP_PRIVATE`, `MAP_ANONYMOUS`).
* **Контекст безпеки:** Дозволяє виявляти атаки типу W^X (Write XOR Execute), блокуючи створення сторінок пам'яті, які одночасно мають права на запис та виконання (`PROT_WRITE | PROT_EXEC`).

### 2.3. Мережева підсистема та операції з сокетами

#### `socket_connect`
Перехоплює спроби встановлення вихідних мережевих з'єднань через виклик `connect()`.

* **Сигнатура ядра:** `int security_socket_connect(struct socket *sock, struct sockaddr *address, int addrlen)`
* **Параметри:**
  * `sock` (`struct socket *`): Структура сокета ядра. Внутрішнє поле `sock->sk` вказує на `struct sock`, з якої можна прочитати протокол (`IPPROTO_TCP`, `IPPROTO_UDP`) та тип сокета (`SOCK_STREAM`, `SOCK_DGRAM`).
  * `address` (`struct sockaddr *`): Адреса призначення. Cast-иться до `struct sockaddr_in*` для IPv4 або `struct sockaddr_in6*` для IPv6 для витягування IP-адреси та порту.
* **Контекст безпеки:** Реалізація динамічного фаєрволу на рівні процесів (Process-Aware Egress Firewall).

#### `socket_bind`
Перехоплює спроби прив'язки сокета до локальної адреси/порту через виклик `bind()`.

* **Сигнатура ядра:** `int security_socket_bind(struct socket *sock, struct sockaddr *address, int addrlen)`
* **Контекст безпеки:** Блокування захоплення привілейованих портів (0-1023) непривілейованими сервісами.

---

### 2.4. Перевірка привілеїв (`capable`)

#### `capable`
Викликається кожного разу, коли ядро перевіряє наявність у процесу конкретного привілею POSIX capability через `capable()` чи `ns_capable()`.

* **Сигнатура ядра:** `int security_capable(const struct cred *cred, struct user_namespace *tns, int cap, unsigned int opts)`
* **Параметри:**
  * `cred` (`const struct cred *`): Credentials процесу.
  * `cap` (`int`): Числовий ідентифікатор привілею (`CAP_SYS_ADMIN`, `CAP_NET_ADMIN`, `CAP_SYS_PTRACE`, `CAP_BPF`).
  * `opts` (`unsigned int`): Прапорці аудиту (`CAP_OPT_NONE`, `CAP_OPT_NOAUDIT`).
* **Контекст безпеки:** Дозволяє здійснювати вибіркове позбавлення привілеїв (Capability Trimming). Програма може повернути `-EPERM` для конкретної перевірки `CAP_SYS_ADMIN`, навіть якщо процес запущено від `root`.

## 3. Спеціалізовані BPF-хелпери для LSM програм

Усередині BPF-LSM програм розробник має доступ до багатого набору спеціалізованих BPF-хелперів ядра:

| BPF Хелпер | Сигнатура | Призначення |
| :--- | :--- | :--- |
| `bpf_get_current_uid_gid` | `u64 bpf_get_current_uid_gid(void)` | Повертає UID у молодших 32 бітах та GID у старших 32 бітах процесу. |
| `bpf_get_current_pid_tgid` | `u64 bpf_get_current_pid_tgid(void)` | Повертає TGID (PID процесу) у старших 32 бітах та PID потоку у молодших. |
| `bpf_get_current_comm` | `int bpf_get_current_comm(void *buf, u32 size)` | Записує ім'я виконуваного файлу процесу (до 16 байтів) у буфер. |
| `bpf_d_path` | `int bpf_d_path(struct path *path, char *buf, int sz)` | Переводить структуру `struct path` у повний канонічний VFS-шлях файлу. |
| `bpf_probe_read_kernel_str` | `int bpf_probe_read_kernel_str(void *dst, u32 size, const void *unsafe_ptr)` | Безпечно копіює рядкові дані з пам'яті ядра в BPF-буфер. |
| `bpf_ringbuf_reserve` | `void *bpf_ringbuf_reserve(void *ringbuf, u64 size, u64 flags)` | Резервує ділянку пам'яті в Ring Buffer для відправки події в User Space. |
| `bpf_ringbuf_submit` | `void bpf_ringbuf_submit(void *data, u64 flags)` | Фіксує відправку зарезервованої події у Ring Buffer. |
| `bpf_snprintf_btf` | `int bpf_snprintf_btf(char *str, u32 str_size, struct btf_ptr *ptr, u32 btf_ptr_size, u64 flags)` | Форматує будь-яку структуру ядра у текстовий вигляд на основі BTF-типів. |

### 3.1. Детальні контракти використання BPF-хелперів

1. **Контракт `bpf_d_path`:** Працює лише для обмеженого списку LSM-хуків та підтримуваних файлових систем. Вказівник на `struct path` мусить бути валідним VFS-дескриптором. У разі невдачі повертає від'ємний код помилки (наприклад, `-EINVAL` або `-ENAMETOOLONG`).
2. **Контракт `bpf_ringbuf_reserve` та `bpf_ringbuf_submit`:** Після успішного резервування пам'яті через `bpf_ringbuf_reserve()` розробник зобов'язаний викликати або `bpf_ringbuf_submit()` для публікації події, або `bpf_ringbuf_discard()` для її скасування. Вихід із BPF-програми без виклику однієї з цих функцій буде заблокований BPF Verifier-ом під час завантаження.

## 4. Особливості розв'язання файлових шляхів та крайові випадки VFS

При обробці файлових операцій у хуках `file_open` та `bprm_check_security` розробник політики повинен враховувати специфіку розв'язання шляхів у ядрі Linux:

### 4.1. Символьні посилання та Chroot
Просте порівняння рядка `bprm->filename` може бути обійдено за допомогою відносних шляхів (`./chmod`), символьних посилань або зміненого кореневого каталогу через `chroot()`. 

Для отримання абсолютного канонічного шляху слід завжди використовувати хелпер `bpf_d_path(&file->f_path, buf, size)`. Він проходить ієрархію `dentry` аж до кореня поточного Mount Namespace процесу, виключаючи маніпуляції з відносними шляхами.

### 4.2. Простори імен (Namespaces) та Контейнеризація
Усередині контейнерів Docker чи Kubernetes процес може мати `UID 0` у власному User Namespace, але відповідати непривілейованому UID на хост-системі. При написанні політик BPF-LSM слід зчитувати `global_uid` або аналізувати ідентифікатор Mount/PID Namespace через структуру `task_struct->nsproxy`.

## 5. Захист від атак типу TOCTOU (Time-of-Check to Time-of-Use)

Однією з головних переваг прив'язки політик безпосередньо до LSM-хуків (порівняно з kprobes або tracepoints на системних викликах) є надійний захист від атак стану гонки (Race Conditions) типу TOCTOU.

При використанні kprobe на вході в `sys_openat` програма бачить лише вказівник на рядок шляху, що лежить у пам'яті користувацького процесу. У проміжку часу між тим, як kprobe зчитає цей рядок, і тим, як ядро розбере VFS-inode, паралельний потік користувача може підмінити його вміст (Memory Aliasing Attack).

LSM-хуки (такі як `file_open` або `bprm_check_security`) викликаються **після** того, як ядро повністю резолвило VFS-об'єкт та створило внутрішньоядерні структури `struct file` та `struct linux_binprm`. BPF-програма аналізує структури, які ядро вже зафіксувало у власній пам'яті, тож підмінити шлях чи аргументи з користувацького простору після перевірки неможливо.

## 6. Налагодження та аналіз логів BPF Verifier

При завантаженні BPF-LSM програми в ядро верифікатор виконує глибокий статичний аналіз байткоду. Якщо програма відхиляється ядром (помилка `EINVAL`), детальний причинний лог можна витягнути через лог-буфер `libbpf` або утиліту `bpftool`.

### 6.1. Аналіз JIT-інструкцій через bpftool

JIT-компілятор ядра транслює абстрактний eBPF-байткод у нативні інструкції ЦПУ (наприклад, x86_64 або arm64), а верифікатор під час завантаження переписує окремі інструкції — скажімо, звертання до мап — на швидші еквіваленти. Аналіз `xlated` (трансформованого верифікатором eBPF-коду) та `jited` (нативного машинного коду) дозволяє переконатися, що у підсумковому коді відсутні зайві інструкції розгалуження та що перевірки безпеки виконуються з максимальною продуктивністю.

Для перегляду скомпільованого машинного коду завантаженої політики використовуються команди `bpftool`:

```bash
# Дамп трансляції eBPF інструкцій після оптимізацій верифікатора
sudo bpftool prog dump xlated id <prog_id>

# Дамп нативного машинного коду (x86_64 / arm64)
sudo bpftool prog dump jited id <prog_id>
```

### 6.2. Діагностика BTF та релокацій CO-RE
Якщо завантаження відхиляється через невідповідність типів ядра, перевірте наявність BTF метаданих ядра через файлову систему `/sys/kernel/btf/vmlinux`. У разі відсутності BTF переконайтеся, що ядро зібрано з опцією `CONFIG_DEBUG_INFO_BTF=y`.

## 7. Зведена специфікація параметрів та поведінки хуків

| Найменування LSM-хука | Точка виклику в системному виклику | Головний об'єкт перевірки | Код відмови за замовчуванням |
| :--- | :--- | :--- | :--- |
| `bprm_check_security` | `execve()`, `execveat()` | `struct linux_binprm *` | `-EPERM` (-1) |
| `file_open` | `open()`, `openat()`, `openat2()` | `struct file *` | `-EACCES` (-13) |
| `task_alloc` | `clone()`, `clone3()`, `fork()` | `struct task_struct *` | `-ENOMEM` / `-EPERM` |
| `task_fix_setuid` | `setuid()`, `setresuid()` | `struct cred *` | `-EPERM` (-1) |
| `socket_connect` | `connect()` | `struct sockaddr *` | `-ECONNREFUSED` / `-EPERM` |
| `socket_bind` | `bind()` | `struct sockaddr *` | `-EACCES` (-13) |
| `capable` | `capable()`, `ns_capable()` | `int cap` | `-EPERM` (-1) |
| `mmap_file` | `mmap()` | `struct file *`, `prot` | `-EACCES` (-13) |
| `path_unlink` | `unlink()`, `unlinkat()` | `struct path *`, `dentry *` | `-EPERM` (-1) |
