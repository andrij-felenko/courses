# ⚙️ Реалізація потокового пошуку: буферизація та алгоритм Боєра-Мура

Створення ефективного пошукового фільтра вимагає вирішення двох фундаментальних задач системного програмування: мінімізації кількості системних викликів введення-виведення та усунення зайвого копіювання даних у пам'яті. Наївна реалізація пошуку через функції `fgets()` або `std::getline()` виконує динамічне виділення пам'яті в купі (heap) на кожен рядок, здійснює блокування м'ютексів структури `FILE*` і перевіряє кожен байт щонайменше двічі: спочатку шукаючи символ нового рядка `\n`, а потім скануючи байти рядка шаблоном. На гігабайтних і терабайтних потоках такий підхід призводить до катастрофічної деградації пропускної здатності.

Високопродуктивний рушій пошуку `mini-grep` будується на протилежних інженерних принципах: блоковому зчитуванні через ковзний буфер фіксованого розміру, алгоритмі швидкого пошуку підрядків Боєра — Мура — Горспула (*Boyer-Moore-Horspool*), принципі нульового копіювання (*zero-copy line slicing*) та модульній інтеграції з рушіями регулярних виразів POSIX і PCRE2.

## Архітектура ковзного буфера та механіка розрізання рядків

Потоковий фільтр не знає розміру вхідного файлу заздалегідь: джерелом даних може бути як статичний файл на NVMe-накопичувачі, так і нескінченний конвеєр `pipe` від іншого процесу чи сокет міжпроцесної взаємодії.

```
Вхідний потік (fd)
       │
       ▼  read(fd, buffer + carryover, 64KB - carryover)
┌──────────────────────────────────────────────────────────────┐
│ [Залишок рядка] │         Новозчитані байти блоку           │  Буфер 64 КБ
└──────────────────────────────────────────────────────────────┘
  ▲              ▲
  │              │
line_start   memchr('\n') ──► Знайдено рядок: [line_start .. line_end]
                                │
                                ▼
                     HorspoolMatcher / Regex
                                │ (якщо знайдено збіг)
                                ▼
                     write(STDOUT_FILENO, ...)
```

### Вибір розміру буфера та локальність пам'яті

Вхідні дані надходять у програму блоками по 64 КБ (`65536` байтів). Цей розмір є стандартом для системних утиліт Unix з трьох причин:
1. **Кратність сторінкам віртуальної пам'яті:** Розмір 64 КБ кратно ділиться на стандартний розмір сторінки ядра Linux (4 КБ = 16 сторінок), що дозволяє підсистемі керування пам'яттю (VMM) оптимізувати операції введення-виведення без дроблення сторінкових структур.
2. **Узгодженість із місткістю каналів pipe:** Стандартна місткість кільцевого буфера анонімного каналу `pipe` в ядрі Linux (параметр `F_GETPIPE_SZ`) за замовчуванням становить саме 65536 байтів. Зчитування порціями по 64 КБ дозволяє спорожняти буфер каналу за один системний виклик `read()`, запобігаючи переповненню та блокуванню процесу-генератора.
3. **Локальність кешу процесора:** Буфер обсягом 64 КБ повністю вміщується в кеш пам'яті другого рівня (L2 Cache) сучасних процесорів, що виключає затримки на звернення до повільної оперативної пам'яті (RAM) під час сканування.

### Життєвий цикл ковзного вікна та інваріанти залишку

Оскільки блок фіксованого розміру розриває потік у довільному місці, символ завершення рядка `\n` (`0x0A`) може опинитися на будь-якій позиції блоку, а в кінці зчитаного буфера майже завжди залишається незавершений фрагмент рядка.

Механізм ковзного вікна працює за суворим детермінованим алгоритмом:
1. Залишок незавершеного рядка довжиною `carryover` з попередньої ітерації переміщується на початок буфера викликом `memmove(buffer, buffer + line_start, carryover)`. Використовується саме `memmove()`, оскільки області пам'яті джерела та призначення перекриваються. Ця операція є надзвичайно швидкою: залишок рядка зазвичай не перевищує 80–200 байтів і повністю знаходиться у гарячому кеші L1 процесора.
2. Системний виклик `read()` заповнює вільну частину буфера розміром `BUFFER_CAPACITY - carryover` новими байтами безпосередньо з файлового дескриптора.
3. Вказівник `line_start` послідовно рухається по буферу. Межа кожного рядка визначається викликом `memchr()`, який повертає адресу найближчого символу `\n`.
4. Кожен знайдений рядок передається в модуль зіставлення як пара покажчик-довжина `(buffer + line_start, line_len)` або легковажний `std::string_view` без створення тимчасових об'єктів і без виділення пам'яті в купі.
5. Якщо модуль виявляє збіг — рядок записується у вихідний потік через `write(STDOUT_FILENO, ...)`.
6. Після завершення всіх повних рядків у блоці обчислюється новий залишок `carryover = total_in_buffer - line_start`, і цикл повторюється.

### Порівняння блокового `read()` та відображення в пам'ять `mmap()`

Альтернативою блоковому `read()` є відображення файлу в адресний простір процесу за допомогою системного виклику `mmap(NULL, file_size, PROT_READ, MAP_PRIVATE, fd, 0)`. 

Відображення `mmap()` дозволяє процесу звертатися до вмісту файлу як до єдиного монолітного масиву пам'яті в адресному просторі користувача безпосередньо через дисковий кеш ядра (page cache), усуваючи проміжне копіювання байтів із ядра в буфер користувача.

Однак у загальному випадку `mmap()` має серйозні обмеження:
- **Несумісність із потоками та сокетами:** Виклик `mmap()` вимагає позиціонованого файлового вузла і принципово не може бути застосований до стандартного входу `stdin`, анонімних каналів `pipe`, іменованих каналів `FIFO` або мережевих сокетів, де розмір потоку невідомий і дані генеруються на льоту.
- **Ризик аварійного завершення через `SIGBUS`:** Якщо відображений файл скорочується або обрізається іншим процесом під час сканування (наприклад, активний лог-файл під дією ротації), спроба читання за межами нового розміру генерує апаратний виняток сторінки, який ядро транслює процесу як сигнал `SIGBUS` (Bus Error), що без спеціального обробника миттєво вбиває процес.
- **Накладні витрати на обхід багатьох файлів:** При скануванні тисяч дрібних файлів накладні витрати на створення структур VMA (*Virtual Memory Area*), обробку сторінкових промахів (*page faults*) та скидання записів TLB (*Translation Lookaside Buffer*) перевищують виграш від усунення копіювання.

Блоковий `read()` із ковзним буфером є універсальним і надійним фундаментом для пошукової утиліти, що однаково ефективно працює як із дисковими файлами, так і з конвеєрами довільної довжини.

## Векторизоване виявлення меж рядків та підрахунок ліній через `memchr()`

Пошук символу переведення рядка `\n` є найчастішою операцією у внутрішньому циклі фільтрації: для файлу обсягом 1 ГБ утиліта повинна перевірити мільйони символів розділювачів.

Скалярний побайтовий цикл пошуку символу `\n` (`while (ptr < end && *ptr != '\n') { ptr++; }`) виконує одну перевірку за ітерацію та створює високе навантаження на блок передбачення переходів (branch predictor) процесора.

Замість побайтового сканування використовується функція стандартної бібліотеки `memchr()`, яка в сучасних реалізаціях `glibc` та `musl` побудована на векторних SIMD-інструкціях (AVX2, AVX-512 на x86-64 та Neon на AArch64).

```
Векторний регістр %ymm0 (32 копії 0x0A):
[ 0x0A | 0x0A | 0x0A | 0x0A | ... | 0x0A | 0x0A ]

Векторний регістр %ymm1 (32 байти тексту):
[ 'T'  | 'e'  | 'x'  | '\n' | ... | 'a'  | 'b'  ]

Результат vpcmpeqb (%ymm2):
[ 0x00 | 0x00 | 0x00 | 0xFF | ... | 0x00 | 0x00 ]

vpmovmskb ──► 32-бітне число: 0b0000...00001000
tzcnt     ──► Індекс першого '\n' = 3 (за 1 такт)
```

Векторизований алгоритм завантажує 32 байти тексту за один раз у 256-бітний регістр `%ymm1` інструкцією `vmovdqu`. Інструкція `vpcmpeqb` паралельно порівнює всі 32 байти з маскою шуканого символу в регістрі `%ymm0`. Інструкція `vpmovmskb` згортає старші біти результату в 32-бітний скалярний регістр, а апаратна інструкція підрахунку кінцевих нулів `tzcnt` (*trailing zero count*) миттєво повертає зміщення першого знайденого символу `\n`.

Це забезпечує швидкість сканування меж рядків на рівні 25–35 ГБ/с, повністю утилізуючи пропускну здатність шини оперативної пам'яті.

### Швидкий підрахунок номерів рядків для прапорця `-n`

Коли користувач передає прапорець `-n` (*line number*), утиліта зобов'язана виводити порядковий номер кожного знайденого рядка.

Наївний підхід полягає в інкременті лічильника `line_number++` на кожному знайденому рядку. Проте коли збіги відбуваються рідко (наприклад, один збіг на 100 000 рядків), покроковий інкремент у скалярному коді сповільнює роботу.

Оптимальна архітектура використовує відкладений векторизований підрахунок:
1. Лічильник поточного номера рядка оновлюється лише тоді, коли у поточному блоці знайдено рядок зі збігом.
2. Кількість рядків між попереднім збереженим зсувом і поточним збігом обчислюється швидким викликом `memchr()` у циклі підрахунку символів `\n` над проміжним блоком байтів.
3. Оскільки SIMD-сканер `memchr()` обробляє до 32 або 64 байтів за такт, підрахунок номерів рядків для прапорця `-n` практично не створює накладних витрат на загальну швидкість фільтрації.

## Алгоритмічний попередній фільтр: Боєр — Мур — Горспул та Ахо — Корасік

Пошук тексту за шаблоном ділиться на два класи задач: пошук точного підрядка та пошук за регулярним виразом.

Наївний алгоритм пошуку підрядка довжиною `M` у тексті довжиною `N` перевіряє кожну позицію тексту, виконуючи до `O(N · M)` порівнянь. У гіршому випадку (пошук шаблону `"aaaaab"` у послідовності з мільйонів символів `'a'`) наївний пошук перевіряє кожен символ тексту багаторазово.

### Алгоритм Боєра — Мура — Горспула (Boyer-Moore-Horspool)

Алгоритм Боєра — Мура базується на двох спостереженнях:
1. Порівняння символів шаблону з текстом слід виконувати **справа наліво** — від останнього символу шаблону до першого.
2. Якщо на певній позиції виявлено невідповідність, інформацію про символ тексту, що спричинив розбіжність, можна використати для здійснення великого стрибка вперед через кілька байтів тексту без їхнього поодинокого читання.

Спрощена модифікація алгоритму, запропонована Найджелом Горспулом (Nigel Horspool), використовує виключно таблицю евристики поганого символу (*Bad Character Shift Table*).

```
Таблиця зсувів shift_table[256]:
Для байта c: shift_table[c] = відстань від правого краю шаблону

Текст:    [ e ] [ r ] [ r ] [ o ] [ r ] [ _ ] [ c ] [ o ] [ d ] [ e ]
Шаблон:   [ c ] [ o ] [ d ] [ e ]
Індекси:    0     1     2     3  (M = 4)

Крок 1:   Порівняння тексту[3] ('o') з шаблоном[3] ('e') ──► Розбіжність!
          Символ тексту навпроти правого краю: 'o'.
          За таблицею: shift_table['o'] = 2.
          Стрибок на 2 позиції праворуч!

Крок 2:   Текст:   [ e ] [ r ] [ r ] [ o ] [ r ] [ _ ] [ c ] [ o ] [ d ] [ e ]
          Шаблон:              [ c ] [ o ] [ d ] [ e ]
          Порівняння тексту[5] ('_') з шаблоном[3] ('e') ──► Розбіжність!
          Символ '_' відсутній у шаблоні ──► shift_table['_'] = 4.
          Стрибок на всі 4 позиції праворуч!

Крок 3:   Текст:   [ e ] [ r ] [ r ] [ o ] [ r ] [ _ ] [ c ] [ o ] [ d ] [ e ]
          Шаблон:                                  [ c ] [ o ] [ d ] [ e ]
          Порівняння: 'e'=='e', 'd'=='d', 'o'=='o', 'c'=='c' ──► ЗБІГ ЗНАЙДЕНО!
```

#### Будова таблиці зсувів та інваріант виключення останнього символу

Таблиця зсувів має фіксований розмір 256 елементів типу `size_t` — по одному слоту на кожен можливий байт значення `uint8_t`:

:::tabs
```c
typedef struct {
    size_t shift_table[256];
    const char *pattern;
    size_t pattern_len;
} HorspoolMatcher;

static void matcher_init(HorspoolMatcher *m, const char *pattern) {
    m->pattern = pattern;
    m->pattern_len = strlen(pattern);
    const size_t len = m->pattern_len;

    /* 1. За замовчуванням будь-який невідомий символ дає зсув на всю довжину M */
    for (size_t i = 0; i < 256; ++i) {
        m->shift_table[i] = len;
    }

    /* 2. Для символів шаблону обчислюємо відстань від правого краю */
    if (len > 0) {
        for (size_t i = 0; i < len - 1; ++i) {
            uint8_t byte = (uint8_t)pattern[i];
            m->shift_table[byte] = len - 1 - i;
        }
    }
}
```
```cpp
class HorspoolMatcher {
public:
    explicit HorspoolMatcher(std::string_view pattern)
        : pattern_(pattern), pattern_len_(pattern.size()) {
        shift_table_.fill(pattern_len_);

        if (pattern_len_ > 0) {
            for (size_t i = 0; i < pattern_len_ - 1; ++i) {
                auto byte_val = static_cast<uint8_t>(pattern_[i]);
                shift_table_[byte_val] = pattern_len_ - 1 - i;
            }
        }
    }

private:
    std::string_view pattern_;
    size_t pattern_len_{0};
    std::array<size_t, 256> shift_table_{};
};
```
:::

> ⚠️ **Критичний інваріант безпеки:**
> Другий цикл ініціалізації проходить строго до індексу `len - 2`, **виключаючи останній символ шаблону `pattern[len - 1]`**.
> Якщо останній символ зустрічався раніше у шаблоні (наприклад, перший символ у слові `"test"`), його зсув дорівнюватиме відстані до попереднього входження `len - 1 - i > 0`. Якщо ж останній символ є унікальним, його зсув залишиться рівним `len`.
> Це гарантує, що величина зсуву для будь-якого символу завжди становить щонайменше `1`, унеможливлюючи нульовий зсув і нескінченне зациклення сканера.

#### Гарячий цикл сканування

Функція пошуку перевіряє рядок тексту, зіставляючи суфікс:

:::tabs
```c
static bool matcher_find(const HorspoolMatcher *m, const char *text, size_t text_len) {
    const size_t p_len = m->pattern_len;
    if (p_len == 0) return true;
    if (text_len < p_len) return false;

    const char *p = m->pattern;
    size_t i = p_len - 1;

    while (i < text_len) {
        size_t k = 0;
        /* Порівняння справа наліво */
        while (k < p_len && p[p_len - 1 - k] == text[i - k]) {
            k++;
        }
        if (k == p_len) {
            return true; /* Збіг знайдено */
        }
        /* Зсув за символом тексту, що стоїть на позиції правого краю шаблону */
        uint8_t bad_byte = (uint8_t)text[i];
        i += m->shift_table[bad_byte];
    }
    return false;
}
```
```cpp
[[nodiscard]] bool HorspoolMatcher::contains_in(std::string_view text) const noexcept {
    if (pattern_len_ == 0) return true;
    if (text.size() < pattern_len_) return false;

    size_t i = pattern_len_ - 1;
    while (i < text.size()) {
        size_t k = 0;
        while (k < pattern_len_ && pattern_[pattern_len_ - 1 - k] == text[i - k]) {
            ++k;
        }
        if (k == pattern_len_) {
            return true;
        }
        auto bad_byte = static_cast<uint8_t>(text[i]);
        i += shift_table_[bad_byte];
    }
    return false;
}
```
:::

Середня обчислювальна складність алгоритму становить:
```text
Складність пошуку Horspool = O(N / M)
```
Завдяки цьому пошук є сублінійним: що довший шуканий підрядок `M`, то більші стрибки робить сканер, пропускаючи до 80–90% байтів тексту без їхнього читання.

### Багатошаблонний пошук: Автомат Ахо — Корасік (Aho-Corasick)

Коли утиліта викликається з опцією `-F` та списком із сотень або тисяч фіксованих рядків (через прапорець `-f pattern_file`), послідовний виклик алгоритму Боєра — Мура для кожного підрядка окремо призвів би до деградації швидкодії до `O(K · N)`, де `K` — кількість шаблонів.

Для одночасного пошуку множини слів будується скінченний детермінований автомат Ахо — Корасік:
1. **Префіксне дерево (Trie):** Усі шукані підрядки вставляються у префіксний бір, де кожен вузол відповідає певному префіксу одного чи кількох слів.
2. **Суфіксні переходи при невдачі (*Failure Links*):** За допомогою пошуку в ширину (BFS) для кожного вузла обчислюється посилання невдачі, яке вказує на найдовший префікс іншого слова в борі, що є суфіксом поточного шляху.
3. **Вихідні зв'язки (*Dictionary / Output Links*):** Кожен стан пов'язується зі списком знайдених патернів.

```
       (корінь)
      /        \
    'h'        's'
    /            \
  'e'            'h'
  / \              \
'r' 'a'            'e' (вихід: "she")
 |    \              │
's'   't'            └── failure link ──► вузол "he"
(вихід: "hers")
```

Текст сканується **рівно один раз**: автомат переходить між станами бора зі швидкістю `O(N)` незалежно від того, скільки слів шукається — 5 чи 50 000.

### Стратегія попередньої фільтрації для регулярних виразів (Literal Pre-Filtering)

Повноцінний рушій регулярних виразів є ресурсомістким: побудова NFA/DFA станів або виконання коду віртуальної машини зі зворотним поверненням вимагає суттєвих витрат процесорного часу на кожен байт.

Сучасні високопродуктивні реалізації `grep` застосовують двокрокову архітектуру фільтрації:
1. **Виділення обов'язкового літералу (*Literal Extraction*):** Під час аналізу регулярного виразу парсер виділяє найдовший фіксований підрядок, без присутності якого вираз гарантовано не може зіставитися. Наприклад:
   - Для виразу `^[0-9]{4}-[0-9]{2}-[0-9]{2} ERROR: .*` обов'язковим літералом є `" ERROR: "`.
   - Для виразу `(foo|bar)_critical_event` виділяється підрядок `"_critical_event"`.
2. **Грубе відсікання через Horspool / Aho-Corasick:** Кожен рядок вхідного потоку спочатку перевіряється надшвидким алгоритмом пошуку підрядків на наявність виділеного літерала.
3. **Точна перевірка регулярним рушієм:** Якщо обов'язковий підрядок відсутній — рядок негайно відкидається. Важкий регулярний рушій викликається лише для тих рядків-кандидатів, які пройшли попередній фільтр.

Це дозволяє відсіяти до 98–99% тексту на максимальній швидкості апаратури, звертаючись до складного регулярного аналізатора лише в поодиноких випадках.

## Інтеграція рушіїв регулярних виразів: POSIX та PCRE2 API

Для складних шаблонів, що містять класи символів, чергування та квантифікатори, `mini-grep` підключає стандартні рушії регулярних виразів через системні API бібліотек C/C++.

### Рушій POSIX Regex API (`<regex.h>`)

Стандарт POSIX визначає API для роботи з базовими (BRE) та розширеними (ERE) регулярними виразами через структуру `regex_t`.

:::tabs
```c
#include <regex.h>
#include <stdio.h>

/* Життєвий цикл POSIX регулярного виразу */
regex_t compiled_regex;

/* 1. Компіляція шаблону */
int cflags = REG_EXTENDED | REG_NOSUB | REG_NEWLINE;
int err = regcomp(&compiled_regex, "^[a-zA-Z0-9_]+@[a-z]+\\.[a-z]{2,4}$", cflags);
if (err != 0) {
    char err_buf[256];
    regerror(err, &compiled_regex, err_buf, sizeof(err_buf));
    fprintf(stderr, "Помилка компіляції регулярного виразу: %s\n", err_buf);
    return 2;
}

/* 2. Виконання зіставлення для кожного рядка */
int match = regexec(&compiled_regex, line_ptr, 0, NULL, 0);
if (match == 0) {
    /* Збіг знайдено */
}

/* 3. Звільнення виділеної пам'яті */
regfree(&compiled_regex);
```
```cpp
#include <regex.h>
#include <string_view>
#include <stdexcept>

class PosixRegex {
public:
    explicit PosixRegex(const char* pattern, int flags = REG_EXTENDED | REG_NOSUB | REG_NEWLINE) {
        if (::regcomp(&re_, pattern, flags) != 0) {
            throw std::runtime_error("Помилка компіляції POSIX regex");
        }
    }

    ~PosixRegex() noexcept {
        ::regfree(&re_);
    }

    [[nodiscard]] bool matches(const char* null_terminated_line) const noexcept {
        return ::regexec(&re_, null_terminated_line, 0, nullptr, 0) == 0;
    }

private:
    regex_t re_{};
};
```
:::

Ключові параметри компіляції `cflags`:
- `REG_EXTENDED` — вмикає синтаксис розширених регулярних виразів (ERE: дужки `()`, квантифікатори `+`, `?`, оператор `|` активні без зворотних слешів).
- `REG_NOSUB` — **критична оптимізація продуктивності**. Інструктує рушій лише повертати факт збігу (так/ні), не зберігаючи позиції захоплених підгруп у масиві `regmatch_t`. Це усуває накладні витрати на виділення пам'яті та трекінг індексів під час обходу автомата.
- `REG_NEWLINE` — коректно обробляє символи переведення рядка: оператори `^` та `$` прив'язуються до початку і кінця рядків усередині тексту, а крапка `.` не зіставляється з `\n`.
- `REG_ICASE` — вимикає чутливість до регістру символів.

### Рушій PCRE2 API (`<pcre2.h>`)

Бібліотека PCRE2 (Perl Compatible Regular Expressions) підтримує розширені можливості: ретроспективні та випереджувальні перевірки (*lookaround assertions*), ліниві квантифікатори `.*?` та JIT-компіляцію (*Just-In-Time*).

Конвеєр роботи з PCRE2 у C/C++ складається з чотирьох фаз:

:::tabs
```c
#define PCRE2_CODE_UNIT_WIDTH 8
#include <pcre2.h>

pcre2_code *re;
pcre2_match_data *match_data;
int errorcode;
PCRE2_SIZE erroroffset;

/* 1. Компіляція шаблону в байт-код */
uint32_t compile_options = PCRE2_UTF | PCRE2_MULTILINE;
re = pcre2_compile(
    (PCRE2_SPTR)"(?<=token=)[0-9a-fA-F]+",
    PCRE2_ZERO_TERMINATED,
    compile_options,
    &errorcode,
    &erroroffset,
    NULL
);

/* 2. JIT-компіляція у нативний машинний код */
pcre2_jit_compile(re, PCRE2_JIT_COMPLETE);

/* 3. Створення структури для результатів */
match_data = pcre2_match_data_create_from_pattern(re, NULL);

/* 4. Виконання зіставлення на рядку */
int rc = pcre2_match(
    re,
    (PCRE2_SPTR)line_ptr,
    line_len,
    0,                    /* Початковий зсув */
    0,                    /* Опції пошуку */
    match_data,
    NULL
);

if (rc >= 0) {
    /* Збіг знайдено */
}

/* 5. Звільнення ресурсів */
pcre2_match_data_free(match_data);
pcre2_code_free(re);
```
```cpp
#define PCRE2_CODE_UNIT_WIDTH 8
#include <pcre2.h>
#include <string_view>
#include <memory>
#include <stdexcept>

class Pcre2Matcher {
public:
    explicit Pcre2Matcher(std::string_view pattern) {
        int errcode = 0;
        PCRE2_SIZE erroffset = 0;
        code_.reset(pcre2_compile(
            reinterpret_cast<PCRE2_SPTR>(pattern.data()),
            pattern.size(),
            PCRE2_UTF | PCRE2_MULTILINE,
            &errcode,
            &erroffset,
            nullptr
        ));
        if (!code_) {
            throw std::runtime_error("Помилка компіляції PCRE2");
        }
        pcre2_jit_compile(code_.get(), PCRE2_JIT_COMPLETE);
        match_data_.reset(pcre2_match_data_create_from_pattern(code_.get(), nullptr));
    }

    [[nodiscard]] bool matches(std::string_view text) const noexcept {
        int rc = pcre2_match(
            code_.get(),
            reinterpret_cast<PCRE2_SPTR>(text.data()),
            text.size(),
            0,
            0,
            match_data_.get(),
            nullptr
        );
        return rc >= 0;
    }

private:
    struct CodeDeleter { void operator()(pcre2_code* p) const noexcept { pcre2_code_free(p); } };
    struct DataDeleter { void operator()(pcre2_match_data* p) const noexcept { pcre2_match_data_free(p); } };

    std::unique_ptr<pcre2_code, CodeDeleter> code_;
    std::unique_ptr<pcre2_match_data, DataDeleter> match_data_;
};
```
:::

#### Перевага JIT-компіляції

Виклик `pcre2_jit_compile(re, PCRE2_JIT_COMPLETE)` транслює дерево синтаксичного аналізу регулярного виразу безпосередньо в нативні інструкції процесора (x86-64 або AArch64).

Під час виклику `pcre2_match()` виконання відбувається не через інтерпретатор віртуальної машини з таблицею розгалужень, а прямим стрибком на згенерований машинний код. Це прискорює зіставлення у 4–8 разів, наближаючи швидкість PCRE2 до детермінованих автоматів DFA.

## Підтримка контекстних рядків `-A`, `-B`, `-C` та кільцевий буфер

При аналізі системних логів та діагностиці відмов користувачеві потрібен контекст навколо знайденого рядка:
- `-B <N>` (*Before*) — вивести `N` рядків, що передують рядку зі збігом;
- `-A <N>` (*After*) — вивести `N` рядків після рядка зі збігом;
- `-C <N>` (*Context*) — симетричне вікно з `N` рядків до і після збігу (еквівалент `-B N -A N`).

```
                    ┌─────────────────────────┐
                    │ Рядок 10 (поза вікном)  │
                    ├─────────────────────────┤
                    │ Рядок 11 (до-контекст)  │ ◄── Вивантажується з кільцевого буфера
                    │ Рядок 12 (до-контекст)  │
                    ├─────────────────────────┤
                    │ Рядок 13: ЗБІГ!         │ ◄── Друкується з префіксом ':'
                    ├─────────────────────────┤
                    │ Рядок 14 (після-контекст)│ ◄── Лічильник after_remaining = 2
                    │ Рядок 15 (після-контекст)│ ◄── Лічильник after_remaining = 1
                    ├─────────────────────────┤
                    │ -- (розділювач груп)    │ ◄── Друкується при розриві контексту
                    └─────────────────────────┘
```

### Архітектура кільцевого буфера рядків (Ring Buffer)

Складність реалізації параметра `-B N` полягає в тому, що на момент виявлення збігу на поточному рядку попередні `N` рядків уже були зчитані й відкинуті. Повернення назад по файловому дескриптору (через `lseek()`) неможливе, оскільки вхідний потік може надходити з непозиціонованого каналу `pipe` або сокета.

Для збереження передісторії реалізується кільцевий буфер рядків (*Circular Line Buffer*):
1. Виділяється масив метаданих фіксованої місткості `N`. Кожен елемент кільця зберігає покажчик на скопійовані байти рядка та його довжину.
2. Вказівник голови `ring_head` інкрементується за модулем: `ring_head = (ring_head + 1) % N`.
3. Загальна кількість збережених рядків обмежена `count = min(count + 1, N)`.
4. Коли черговий рядок не містить збігу, він записується в поточну позицію кільцевого буфера, заміщуючи найстаріший рядок.
5. Щойно виявлено рядок зі збігом, утиліта по черзі вивантажує й друкує всі `count` рядків із кільцевого буфера (позначаючи їх дефісом `-` замість двокрапки `:` у режимі виводу номерів рядків), спорожняє кільцевий буфер і друкує сам знайдений рядок.

### Скінченний автомат після-контексту та злиття вікон

Для виводу `N` рядків після збігу (`-A N`) використовується цілочисельний лічильник `after_remaining`:
1. При виявленні збігу лічильник встановлюється у значення `after_remaining = A`.
2. Кожен наступний зчитаний рядок, навіть якщо він не містить шуканого шаблону, автоматично друкується у вихідний потік, а лічильник декрементується: `after_remaining--`.
3. **Логіка злиття перекритих вікон (Overlap Merging):** Якщо новий збіг трапляється до того, як лічильник `after_remaining` досяг нуля, лічильник скидається назад у повне значення `A`. Це забезпечує плавне об'єднання сусідніх зон інтересу в єдиний неперервний блок замість друку розірваних фрагментів.
4. **Друк групового розділювача `--`:** Якщо між двома послідовними блоками збігів є розрив у тексті, утиліта виводить стандартний рядок `--` для візуального відокремлення непов'язаних контекстних груп.

### Детальний розбір реалізації мовою C (`c/main.c`)

1. **Структура `HorspoolMatcher`:**
   Містить статичний масив `shift_table[256]` та вказівник на рядок шаблону. Пам'ять таблиці зсувів розміщується безпосередньо у структурі (на стеку функції `main()`), що гарантує відсутність алокацій у купі.
2. **Гарячий цикл `matcher_find()`:**
   Зіставляє суфікси справа наліво. У разі невідповідності індекс зміщується на `shift_table[(uint8_t)text[i]]`. Оскільки вказівники на байти не потребують завершального нульового байта `\0`, функція безпечно працює з довільними бінарними послідовностями.
3. **Цикл потокового читання `process_stream()`:**
   Виділяє стековий буфер `buffer[BUFFER_CAPACITY + 1]`. Системний виклик `read()` зчитує дані з дескриптора `fd`. Векторизований пошук `memchr()` нарізає буфер на окремі рядки.
4. **Зсув залишку через `memmove()`:**
   Якщо після обробки останнього повного рядка в кінці буфера лишаються байти, виклик `memmove(buffer, buffer + line_start, carryover)` переносить їх на початок масиву для наступної ітерації.
5. **Прямі виклики системного виводу:**
   У разі виявлення збігу рядок негайно відправляється у стандартний потік через `write(STDOUT_FILENO, ...)`. Відмова від буферизованих бібліотечних функцій `printf()` або `puts()` усуває подвійне копіювання даних.

### Детальний розбір реалізації мовою C++ (`cpp/main.cpp`)

1. **Інкапсуляція стану в класі `HorspoolMatcher`:**
   Використовує `std::string_view` для представлення шаблону та фіксований контейнер `std::array<size_t, 256>` для таблиці зсувів. Метод `contains_in()` позначений атрибутом `[[nodiscard]]` та специфікатором `noexcept`, що допомагає оптимізатору компілятора генерувати код без перевірок винятків.
2. **Клас `StreamProcessor`:**
   Інкапсулює буфер введення через `std::vector<char> buffer(BufferCapacity + 1)`. 
3. **Zero-copy абстракція через `std::string_view`:**
   Кожен знайдений рядок обгортається в легковажний об'єкт `std::string_view(start_ptr, line_len)`. Це дозволяє передавати підрядки в пошуковий рушій за сталий час `O(1)` без виділення динамічної пам'яті.
4. **Використання прямих системних викликів `::read` та `::write`:**
   C++ реалізація навмисно уникає використання `std::cin` та `std::cout`. Навіть при виклику `std::ios::sync_with_stdio(false)`, потоки `std::iostream` мають значні внутрішні накладні витрати на форматування та обробку локалі. Прямі виклики POSIX API забезпечують максимальну швидкість обробки на рівні чистого C.

## Аналіз крайових випадків, надійності та компіляції

При розробці системного фільтра надійність на нестандартних вхідних даних є такою ж важливою, як і швидкість.

### 1. Файли без завершального символу `\n`

Якщо останній рядок файлу не закінчується символом переведення рядка `\n`, виклик `memchr()` не знайде розділювача, а наступний виклик `read()` поверне `0` (кінець файлу, EOF).

У коді реалізовано спеціальну перевірку стану завершення:
:::tabs
```c
if (!newline_ptr) {
    if (bytes_read == 0) {
        /* Кінець потоку без завершального \n */
        size_t line_len = total_in_buffer - line_start;
        if (matcher_find(matcher, buffer + line_start, line_len)) {
            write(STDOUT_FILENO, buffer + line_start, line_len);
            write(STDOUT_FILENO, "\n", 1);
            any_match_found = true;
        }
        line_start = total_in_buffer;
    }
    break;
}
```
```cpp
if (!newline_ptr) {
    if (bytes_read == 0) {
        /* Кінець потоку без завершального \n */
        std::string_view last_line(start_ptr, remaining);
        if (matcher_.contains_in(last_line)) {
            [[maybe_unused]] auto w1 = ::write(STDOUT_FILENO, last_line.data(), last_line.size());
            [[maybe_unused]] auto w2 = ::write(STDOUT_FILENO, "\n", 1);
            any_match = true;
        }
        line_start = total_in_buffer;
    }
    break;
}
```
:::
Програма зіставляє залишок даних як повноцінний останній рядок і самостійно дописує символ `\n` у вихідний потік при збігу. Це запобігає «злипанню» виводу із запрошенням командної оболонки або спотворенню наступного процесу в конвеєрі.

### 2. Рядки, що перевищують розмір буфера (Monolithic Long Lines)

Якщо вхідний потік містить суцільний монолітний рядок без жодного символу `\n` довжиною понад 64 КБ (наприклад, згенерований мініфікований JSON-файл або дамп бази даних), залишок `carryover` досягає максимальної місткості `BUFFER_CAPACITY`.

Наївні парсери в такій ситуації або падають через переповнення стека/буфера, або виділяють нескінченну пам'ять у купі.

У нашій реалізації детектується стан `carryover == BUFFER_CAPACITY`:
- Наявна частина монолітного рядка перевіряється на збіг із шаблоном;
- У разі виявлення збігу частина рядка скидається у вихідний потік;
- Лічильник `carryover` скидається в `0`, звільняючи буфер для наступної порції того самого рядка.

Це гарантує стабільну роботу програми з фіксованим споживанням пам'яті `O(1)` навіть на файлах із терабайтними монолітними рядками.

### 3. Безпека бінарних даних та нульові байти `0x00`

Багато реалізацій на мові C використовують стандартні функції обробки рядків `strlen()`, `strcpy()`, `strstr()`, які сприймають нульовий байт `\0` як маркер завершення рядка. Якщо такій програмі передати скомпільований бінарний файл або стиснений архів, рядок обірветься на першому ж нульовому байті, і пошук пропустить решту даних.

Обидві наші реалізації (C та C++) працюють строго з парами покажчик-довжина `(char*, size_t)` та байтами `uint8_t`. Кожен байт від `0x00` до `0xFF` є рівноправним, що забезпечує коректний та безпечний пошук у бінарних файлах.

### 4. Прапорці компіляції та оптимізація генерації коду

Для отримання максимальної швидкодії компіляцію слід виконувати з оптимізаціями рівня `-O3` та увімкненням генерації інструкцій під цільову архітектуру:

```bash
# Компіляція C версії
gcc -O3 -march=native -fno-omit-frame-pointer -flto -o mini_grep_c proj-mini-grep/c/main.c

# Компіляція C++ версії
g++ -O3 -march=native -std=c++20 -fno-omit-frame-pointer -flto -o mini_grep_cpp proj-mini-grep/cpp/main.cpp
```

Вплив прапорців компілятора:
- `-O3`: Вмикає агресивне розгортання циклів (*loop unrolling*), векторизацію та інлайнінг функцій `matcher_find()` безпосередньо в тіло циклу обробки потоку.
- `-march=native`: Дозволяє компілятору генерувати нативні інструкції AVX2 / AVX-512 / BMI2, наявні на процесорі комп'ютера, на якому виконується збірка.
- `-flto` (*Link-Time Optimization*): Виконує наскрізний аналіз та міжпроцедурну оптимізацію на етапі компонування бінарного файлу.
- `-fno-omit-frame-pointer`: Зберігає покажчик кадру стека `%rbp`, що дозволяє знімати точні профілі продуктивності за допомогою утиліт `perf` та eBPF без втрати швидкості виконання.
