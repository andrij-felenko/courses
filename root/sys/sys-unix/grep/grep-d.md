У типовій серверній системі журнали подій та текстові потоки генерують гігабайти неструктурованих даних щохвилини. Якщо для пошуку одного критичного запису про помилку спробувати завантажити такий журнал цілком у пам'ять, процес швидко вичерпає ліміти оперативної пам'яті (англ. *Out Of Memory*, OOM) і буде примусово знищений ядром. Обробка текстових масивів будь-якого масштабу вимагає потокового підходу: програма повинна зчитувати дані фіксованими порціями, негайно відсікати зайві рядки та передавати відібраний результат наступному процесу через конвеєр.

Саме таку роль виконує `grep` — фундаментальний потоковий фільтр середовища Unix. Його завдання полягає у послідовному скануванні байтового потоку або файлової ієрархії, зіставленні кожного рядка із заданим шаблоном і генерації вибірки за сталий час та з фіксованим обсягом пам'яті `O(1)` відносно загального розміру вхідних даних.

## Концепція та походження: від команди редактора до фільтра

Назва утиліти походить від синтаксису команди глобального пошуку в оригінальному текстовому редакторі `ed`: `g/re/p` (*global / regular expression / print*). У ранніх версіях Unix для пошуку тексту користувачі були змушені завантажувати файл у буфер редактора `ed` і виконувати команду друку рядків, що збігаються з регулярним виразом. Проте редактор `ed` зберігав весь документ у пам'яті у вигляді зв'язаного списку, що робило його непридатним для аналізу великих файлів на апаратурі з обмеженою пам'яттю.

У 1973 році Кен Томпсон (Ken Thompson) виділив рушій регулярних виразів із `ed` в окрему утиліту, оптимізовану під лінійне потокове читання без проміжного збереження всього файлу в пам'яті. Детальний історичний контекст виникнення утиліти для аналізу «Записок Федераліста» описано у матеріалі [📜 Команда g/re/p в ed: як текстовий редактор породив незалежний фільтр](root:sys-unix/grep/hist-ed-g-re-p.md).

У філософії Unix `grep` став зразком базового фільтра. Він приймає потік байтів зі стандартного входу (дескриптор `0`), розбиває його на дискретні записи за символом нового рядка `\n` (ASCII `0x0A`), зіставляє кожен запис із регулярним виразом або точним підрядком і скидає відповідні рядки у стандартний вивід (дескриптор `1`).

```
[Джерело даних] ---> stdout ---> stdin ---> [ grep "ERROR" ] ---> stdout ---> [ Аналізатор ]
(cat / dmesg)                                                      (awk / sort)
```

Завдяки такій побудові `grep` не залежить від джерела даних: ним може бути статичний файл на диску, сокет міжпроцесної взаємодії або неперервний вивід ядра.

## Архітектура потокового буфера та розпізнавання меж рядків

Продуктивність потокового фільтра визначається двома факторами: мінімізацією системних викликів введення-виведення та ефективністю виявлення роздільників рядків.

![Архітектура потокового конвеєра grep: обробка блоків та фільтрація рядків](/root/sys/sys-unix/grep/img/grep-pipeline-model.svg)
*Потоковий конвеєр grep: блокове зчитування через ковзний буфер, SIMD-сканування символів нового рядка, зіставляння з регулярним виразом та генерація статусів.*

### Робота з ковзним буфером (Sliding Buffer)

Зчитування файлу по одному символу або через високорівневі бібліотечні функції на кшталт `fgets()` генерує неприпустимі накладні витрати на блокування м'ютексів потоку `FILE*` та зайві перевірки стану. Сучасний `grep` виділяє у просторі користувача буфер фіксованого розміру (зазвичай 32 КБ або 64 КБ) і зчитує дані великими блоками за допомогою системного виклику `read(fd, buffer, capacity)`.

Оскільки блок фіксованого розміру розриває потік у довільному місці, рядок тексту може починатися в одному блоці й закінчуватися в наступному. Для обробки таких розривів використовується алгоритм ковзного вікна:
1. Буфер заповнюється новими даними через системний виклик `read()`.
2. Сканер знаходить усі повні рядки від початку буфера до останнього виявленого символу `\n`.
3. Залишок блоку після останнього `\n` копіюється на початок буфера за допомогою швидкої функції `memmove()`.
4. Наступний виклик `read()` дописує нову порцію даних у буфер одразу за збереженим залишком.

### Векторизований пошук роздільників `\n` через SIMD

Для розрізання буфера на рядки `grep` використовує високооптимізовану функцію `memchr()`, яка на сучасних процесорах реалізована за допомогою векторних SIMD-інструкцій (англ. *Single Instruction, Multiple Data* — AVX2, AVX-512 на архітектурі x86-64 або ARM Neon на AArch64).

Замість побайтового порівняння у скалярному циклі процесор виконує паралельну обробку блоку:
- Векторний регістр (наприклад, 256-бітний `%ymm0` в AVX2) заповнюється байтовою маскою з 32 копій шуканого символу `\n` (`0x0A`).
- Інструкція `vmovdqu` завантажує 32 байти тексту з пам'яті в регістр `%ymm1`.
- Інструкція `vpcmpeqb` порівнює всі 32 байти одночасно за один такт процесора, записуючи маску `0xFF` у байти збігів та `0x00` в інші.
- Інструкція `vpmovmskb` згортає старші біти байтів у 32-бітний скалярний регістр загального призначення.
- Інструкція `tzcnt` (*trailing zero count*) миттєво обчислює індекс першого знайденого символу `\n` за кількістю нульових бітів.

Це дозволяє знаходити межі рядків зі швидкістю понад 20–30 ГБ/с, впираючись лише у пропускну здатність шини пам'яті комп'ютера.

## Діалекти регулярних виразів: BRE, ERE та PCRE

Регулярний вираз (лат. *regularis* — впорядкований, згідно з правилом) — це формальна алгебра для опису множини рядків за допомогою скінченного набору символів і операторів конкатенації (лат. *concatenatio* — зчеплення), чергування та замикання Кліні (повторення).

Історичний розвиток утиліти призвів до формування трьох чітко розмежованих діалектів синтаксису та відповідних обчислювальних рушіїв.

![Ієрархія діалектів регулярних виразів та рушіїв у grep](/root/sys/sys-unix/grep/img/grep-regex-dialects.svg)
*Чотири режими пошуку у grep: зіставлення алгоритмічної складності, синтаксису екранування та можливостей рушіїв.*

### Базові регулярні вирази: BRE (Basic Regular Expressions)

Режим за замовчуванням у стандарті POSIX (`grep` або `grep -G`). Створений у часи раннього Unix, синтаксис BRE виходив із припущення, що більшість символів у тексті є звичайними літералами. Тому всі оператори групування та розширені квантифікатори вимагають обов'язкового екранування зворотним слешем `\`:

- `\(` та `\)` — групування виразів і збереження підрядків;
- `\{m,n\}` — інтервальний квантифікатор (від `m` до `n` повторень);
- `\1` .. `\9` — зворотні посилання (*backreferences*) на захоплені групи;
- `.`, `*`, `^`, `$` — активні як метасимволи без слешів;
- Символи `+`, `?`, `|` у класичному BRE вважаються звичайними літералами (хоча GNU `grep` підтримує їх через `\+`, `\?`, `\|` як розширення).

```bash
# Пошук рядка, де повторюється двозначне число через дефіс: 12-12
grep '^\([0-9]\{2\}\)-\1$' input.txt
```

### Розширені регулярні вирази: ERE (Extended Regular Expressions)

Режим вмикається прапорцем `-E` (або викликом застарілої утиліти-симлінка `egrep`). Синтаксис ERE усуває необхідність зворотних слешів для базових алгебраїчних операцій над регулярними виразами:

- `(` та `)` — відкривають і закривають групи без екранування;
- `{m,n}` — квантифікатор повторень без слешів;
- `+` — один або більше повторів (еквівалент `aa*`);
- `?` — нуль або один повтор (опціональний елемент);
- `|` — логічне чергування (альтернатива: `шаблонA|шаблонB`).

```bash
# Пошук рядків з префіксами HTTP або HTTPS та кодами 404 або 500
grep -E '^https?://.* (404|500) ' access.log
```

Головна перевага ERE — математична строгість. Класичний ERE без зворотних посилань повністю описується детермінованим скінченним автоматом (англ. *Deterministic Finite Automaton*, DFA). Рушій DFA компілює регулярний вираз у таблицю переходів між станами. Час зіставлення рядка довжиною `N` гарантовано є строго лінійним:

```text
Час виконання DFA = O(N)
```

Незалежно від складності шаблону чи кількості вкладених дужок, час обробки залежить виключно від кількості байтів у тексті. DFA не може зависнути або сповільнитися через невдалий підбір шаблону. GNU `grep` реалізує так звану ліниву генерацію станів DFA (англ. *lazy DFA state construction*): стани автомата обчислюються і кешуються динамічно лише тоді, коли відповідний шлях зустрічається у реальному тексті.

### Perl-сумісні регулярні вирази: PCRE (`grep -P`)

GNU `grep` підтримує рушій бібліотеки PCRE2 через опцію `-P`. PCRE суттєво розширює виразні можливості, додаючи конструкції, які неможливо виразити класичною теорією скінченних автоматів:

- Нежадібні (ліниві) квантифікатори: `.*?`, `.+?`;
- Позитивні та негативні випереджувальні перевірки (*lookahead*): `(?=...)`, `(?!...)`;
- Ретроспективні перевірки (*lookbehind*): `(?<=...)`, `(?<!...)`;
- Спеціальні символьні класи: `\d` (цифри), `\s` (пробільні символи), `\w` (букви, цифри, підкреслення).

```bash
# Витягти значення поля token=..., ігноруючи лапки навколо нього
grep -oP '(?<=token=")[^"]+' auth.log
```

Ціною високої виразності PCRE є зміна архітектури рушія: замість детермінованого автомата PCRE використовує віртуальну машину зі зворотним поверненням (англ. *backtracking VM*). У разі використання складних комбінацій вкладених жадібних квантифікаторів (наприклад, `(a+)+$`) на рядках із невідповідностями наприкінці, рушій починає перебирати всі експоненційні комбінації шляхів.

Це призводить до катастрофічного зворотного повернення (*Catastrophic Backtracking*), коли час зіставлення короткого рядка з 30 символів зростає до `O(2^N)` і займає години процесорного часу. Цей ефект лежить в основі атак типу ReDoS (*Regular Expression Denial of Service*).

> 🔧 **Правило вибору рушія в автоматизації:**
> Для потокової фільтрації у виробничих скриптах слід надавати перевагу `grep -E` (ERE) або `grep -F`. Прапорець `grep -P` виправданий лише тоді, коли потрібні специфічні оператори lookaround або ліниві квантифікатори, і тільки на перевірених вхідних даних.

## Фіксовані рядки: `grep -F` та алгоритмічна оптимізація

Коли критерієм пошуку є точний підрядок (наприклад, конкретна IP-адреса, ім'я змінної або хеш), використання рушія регулярних виразів створює зайві обчислювальні накладні витрати на побудову автомата і посимвольну диспетчеризацію станів.

Опція `-F` (історично окрема утиліта `fgrep`, від *Fixed grep*) вимикає інтерпретацію будь-яких символів як метасимволів. Крапка `.`, зірочка `*`, квадратні дужки `[` та слеші розглядаються як звичайні байти.

```bash
# Знайти точний рядок "192.168.1.1" без інтерпретації крапки як будь-якого символу
grep -F "192.168.1.1" connections.log
```

### Алгоритм Боєра-Мура-Горспула для одного підрядка

Для пошуку одного фіксованого слова `grep -F` використовує модифікацію алгоритму Боєра-Мура (зокрема варіант Боєра-Мура-Горспула або Sunday).

![Оптимізація пошуку в grep -F: алгоритм Боєра-Мура-Горспула](/root/sys/sys-unix/grep/img/grep-boyer-moore-stream.svg)
*Алгоритм Боєра-Мура-Горспула в grep -F: порівняння з правого краю шаблону та стрибок через невідповідні байти тексту за таблицею зсувів.*

Основна ідея полягає у порівнянні шаблону довжиною `M` із текстом **з правого кінця наліво**:
1. Сканер встановлює шаблон на початок буфера і перевіряє символ тексту, що відповідає останньому символу шаблону (позиція `M - 1`).
2. Якщо символ тексту не збігається і взагалі відсутній у шаблоні, шаблон можна безпечно зсунути праворуч одразу на всі `M` позицій.
3. Якщо символ тексту присутній у шаблоні на позиції `k`, шаблон зсувається так, щоб вирівняти найправіше входження цього символу.

Завдяки цьому алгоритм у середньому пропускає більшість байтів вхідного потоку, не читаючи їх взагалі, і досягає сублінійної складності `O(N / M)`. Що довший шуканий підрядок, то швидше працює пошук.

### Алгоритм Ахо-Корасік для множини підрядків

Якщо `grep -F` викликається зі списком з сотень або тисяч слів (через `-f words.txt`), наївне послідовне сканування тексту кожним словом окремо призвело б до складності `O(K · N)`, де `K` — кількість слів.

Замість цього `grep -F` будує скінченний автомат Ахо-Корасік (*Aho-Corasick*):
- Усі пошукові слова об'єднуються в єдиний префіксний бір (англ. *trie*);
- Між вузлами бора обчислюються суфіксні супровідні переходи (англ. *failure links*), які вказують на найдовший префікс іншого слова, якщо поточний збіг обірвався;
- Вхідний текст сканується **рівно один раз**: автомат переходить між станами бора зі швидкістю `O(N)` незалежно від того, шукається 5 слів чи 50 000.

Повну системну реалізацію потокового сканера та алгоритму Боєра-Мура на мовах C та C++ розібрано у проектній вставці [⚙️ Реалізація потокового пошуку: буферизація та алгоритм Боєра-Мура](root:sys-unix/grep/proj-mini-grep.md).

## Керування виводом та фільтрацією

Крім базового відбору рядків, `grep` надає набір прапорців, що керують форматом виводу, агрегацією та взаємодією з оболонкою.

Повний перелік параметрів та змінних середовища систематизовано у довіднику [📋 Інтерфейс утиліти grep: опції, діалекти, змінні оточення та коди виходу](root:sys-unix/grep/api-grep-flags.md).

### Інверсія вибірки: `-v`

Прапорець `-v` (*invert match*) перевертає логіку фільтрації: утиліта відкидає рядки, що збігаються з шаблоном, і пропускає всі інші. Це класичний спосіб очищення даних від коментарів і службових записів:

```bash
# Видалити порожні рядки та рядки, що починаються з символу решітки '#'
grep -v '^[[:space:]]*#' /etc/nginx/nginx.conf | grep -v '^[[:space:]]*$'
```

### Виокремлення самого збігу: `-o`

За замовчуванням `grep` повертає рядок цілком. Опція `-o` (*only matching*) змушує утиліту друкувати **тільки ту частину рядка, яка безпосередньо збіглася з шаблоном**. Якщо в одному рядку знайдено кілька входжень, кожне виводиться на окремому новому рядку.

Це перетворює `grep` на легковажний потоковий токенізатор:

```bash
# Витягти всі IPv4-адреси з системного журналу
grep -oE '[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}' /var/log/syslog
```

### Обмеження кількості та ранній вихід: `-m`

Прапорець `-m <кількість>` (*max count*) інструктує `grep` припинити читання поточного файлу, щойно буде знайдено вказане число рядків зі збігами.

Це важлива оптимізація введення-виведення: якщо потрібна лише перша помилка у 100-гігабайтному дампі, `grep -m 1 "FATAL"` прочитає лише перші кілька кілобайт і негайно завершить процес, не змушуючи операційну систему піднімати гігабайти сторінок з дискового кешу.

### Контекстні вікна: `-A`, `-B`, `-C`

При аналізі стектрейсів помилок або конфігурацій сам рядок зі збігом часто позбавлений сенсу без оточення. Для отримання контексту використовуються прапорці:
- `-B <N>` (*Before*) — надрукувати `N` рядків, що передують збігу;
- `-A <N>` (*After*) — надрукувати `N` рядків після збігу;
- `-C <N>` (*Context*) — надрукувати симетричне вікно з `N` рядків до і після збігу.

Для реалізації прапорця `-B` `grep` підтримує в пам'яті кільцевий буфер (*circular line buffer*) на `N` рядків. Кожен новий прочитаний рядок записується в кільце. Якщо знайдено збіг, утиліта вивантажує вміст кільцевого буфера, друкує сам збіг і вмикає лічильник після-контексту для прапорця `-A`.

```bash
# Показати помилку NullPointerException та 5 рядків коду після неї
grep -A 5 "NullPointerException" server.log
```

### Тихий режим для розгалужень у скриптах: `-q`

Прапорець `-q` (*quiet / silent*) повністю вимикає будь-яке виведення у стандартний потік `stdout`. Утиліта негайно перериває сканування при виявленні першого збігу і повертає відповідний код завершення:
- `0` — шаблон знайдено;
- `1` — шаблон не знайдено;
- `2` — сталася помилка доступу або синтаксису.

Це стандартний ідіоматичний спосіб перевірки умов в командних оболонках:

```bash
if grep -q "CONFIG_KVM=y" /boot/config-$(uname -r); then
    echo "Віртуалізацію KVM увімкнено в ядрі"
fi
```

Конструкція `if grep -q` ефективніша за перенаправлення `grep ... > /dev/null`, оскільки прапорець `-q` зупиняє читання на першому збігу без виклику системних функцій запису.

## Рекурсивний обхід дерева каталогів

При переході від одного файлу до сканування файлової системи виникають задачі рекурсивного спуску по дереву каталогів та розрізнення типів файлових вузлів.

![Рекурсивний обхід дерева каталогів: фізичний (-r) проти логічного (-R)](/root/sys/sys-unix/grep/img/grep-symlinks-traversal.svg)
*Рекурсивне сканування файлової ієрархії: фізичний обхід -r без переходу за посиланнями проти логічного -R із захистом від зациклення за таблицею inode.*

### Фізичний обхід `-r` проти логічного розіменування `-R`

Стандарт POSIX та реалізація GNU чітко розрізняють два режими рекурсії:
1. **`-r` (`--recursive` або `--no-dereference`):** Фізичний обхід. Утиліта рекурсивно заходить у підкаталоги, але **ігнорує символічні посилання на каталоги**. Символічні посилання на файли читаються, але посилання на каталоги не розгортаються.
2. **`-R` (`--dereference-recursive`):** Логічний обхід. Утиліта розкриває всі символічні посилання і переходить за ними, навіть якщо вони вказують на зовнішні каталоги або інші точки монтування.

### Захист від зациклення (Symlink Loops)

У режимі `-R` існує ризик виникнення циклічних посилань (наприклад, посилання `/var/log/backup/current -> /var/log`). Без спеціального захисту наївний рекурсивний алгоритм потрапляє в нескінченний цикл, вичерпуючи стек викликів або пам'ять.

Для захисту від циклів `grep` зчитує метадані кожного каталогу через системний виклик `fstat()` або `statx()` і зберігає кортеж `(st_dev, st_ino)` — ідентифікатор пристрою та номер індексного дескриптора inode у хеш-таблиці. Якщо поточний каталог уже присутній у таблиці відвіданих вузлів поточної гілки, `grep` виводить діагностичне попередження про циклічне посилання і зупиняє спуск цією гілкою.

### Фільтрація шляхів та бінарні файли

При рекурсивному скануванні проектів критично важливо відсікати бінарні артефакти компіляції та службові каталоги систем контролю версій:

```bash
grep -rnE --include="*.c" --include="*.h" --exclude-dir=".git" --exclude-dir="build" "mutex_lock" .
```

Для виявлення бінарних файлів `grep` застосовує евристику: після зчитування першого блоку даних (зазвичай 1024 або 4096 байтів) буфер сканується на наявність нульового байта `\0` (ASCII NUL). Якщо знайдено `\0`, файл маркується як бінарний.

Поведінка регулюється прапорцями:
- `-I` — повністю пропускати бінарні файли (еквівалент `--binary-files=without-match`);
- `-a` (`--text`) — примусово обробляти бінарні файли як текст, друкуючи рядок зі збігом навіть за наявності недрукованих символів.

## Продуктивність: локаль, кодування та системні виклики

Часто розробники спостерігають ситуацію, коли на одному й тому самому 10-гігабайтному лог-файлі `grep` працює 30 секунд в одному терміналі й лише 3 секунди в іншому. Причиною такої різниці є конфігурація локалі операційної системи.

### Вплив змінної `LC_ALL=C`

За замовчуванням у більшості дистрибутивів Linux встановлено локаль UTF-8 (наприклад, `en_US.UTF-8` або `uk_UA.UTF-8`). Відповідно до стандарту POSIX, у такій локалі `grep` зобов'язаний:
1. Перевіряти коректність кожного багатобайтового символу UTF-8;
2. Враховувати правила еквівалентності символів та сортування (*collation rules*);
3. При використанні діапазонів на кшталт `[a-z]` зіставляти всі літери з діакритичними знаками, що входять у цей діапазон за правилами мови.

Ця валідація вимагає звернення до таблиць декодування на кожному кроці сканування, руйнуючи конвеєр процесора.

Якщо встановити змінну середовища `LC_ALL=C` (або `LC_ALL=C.UTF-8`), утиліта перемикається в режим класичного 8-бітного кодування ASCII:
- Кожен символ гарантовано займає рівно 1 байт;
- Діапазон `[a-z]` перетворюється на просту перевірку кодів від `0x61` до `0x7A`;
- Вимикаються всі таблиці мовного порівняння, а сканування зводиться до швидких операцій над масивом пам'яті.

```bash
# Прискорення пошуку в 5-10 разів на великих масивах даних
LC_ALL=C grep "TRANSACTION_SUCCESS" /var/log/payment_audit.log
```

### Порівняння `read()` та `mmap()`

Історично розробники експериментували з відображенням файлів у пам'ять через `mmap()`, щоб усунути операцію копіювання даних із системного кешу сторінок у буфер процесу. Проте у сучасних версіях `grep` за замовчуванням використовується звичайний системний виклик `read()`.

Причини відмови від `mmap()` для загального пошуку:
1. **Накладні витрати на сторінкові структури ядра:** Створення та знищення областей віртуальної пам'яті (`struct vm_area_struct`) через `mmap`/`munmap` для тисяч дрібних файлів створює значне навантаження на підсистему пам'яті ядра та спричиняє скидання записів TLB (англ. *Translation Lookaside Buffer*).
2. **Обробка виняткових ситуацій:** Якщо файл на диску обрізається іншим процесом у момент сканування через `mmap`, звернення до пам'яті генерує апаратний сигнал `SIGBUS`, що вимагає складних обробників сигналів.
3. **Ефективність випереджувального читання (Readahead):** Механізм послідовного випереджувального читання ядра Linux автоматично підвантажує сторінки файлу в Page Cache ще до того, як `read()` запитає наступний блок.

### Простеження системних викликів: `strace`

Аналіз виконання `grep` через `strace` демонструє внутрішню динаміку взаємодії з ядром Linux:

```text
openat(AT_FDCWD, "app.log", O_RDONLY)   = 3
fstat(3, {st_mode=S_IFREG|0644, st_size=104857600, ...}) = 0
read(3, "2026-08-25 12:00:01 INFO Start\n"..., 65536) = 65536
write(1, "2026-08-25 12:00:01 ERROR DB\n", 29) = 29
read(3, "2026-08-25 12:00:02 INFO Tick\n"..., 65536) = 65536
close(3)                                = 0
exit_group(0)                           = 0
```

Програма мінімізує кількість перемикань контексту між простором користувача і простором ядра, завантажуючи дані буферами по 64 КБ і використовуючи прямий дескриптор `stdout` для запису знайдених рядків.

## Робота з регулярними виразами через системний API

Для програмного використання регулярних виразів стандарт POSIX надає функції `regcomp()` та `regexec()`. Нижче наведено зіставлення класичного підходу C з ідіоматичним інтерфейсом C++ на основі RAII-обгортки.

:::tabs
```c
#include <stdio.h>
#include <stdlib.h>
#include <regex.h>
#include <string.h>

int match_line_posix(const char *pattern, const char *text) {
    regex_t regex;
    int ret;

    /* Компіляція розширеного регулярного виразу (ERE) */
    ret = regcomp(&regex, pattern, REG_EXTENDED | REG_NOSUB);
    if (ret != 0) {
        char err_buf[256];
        regerror(ret, &regex, err_buf, sizeof(err_buf));
        fprintf(stderr, "Помилка компіляції виразу: %s\n", err_buf);
        return -1;
    }

    /* Зіставлення тексту */
    ret = regexec(&regex, text, 0, NULL, 0);
    regfree(&regex);

    return (ret == 0) ? 1 : 0;
}

int main(void) {
    const char *pattern = "^[0-9]{4}-[0-9]{2}-[0-9]{2}";
    const char *line = "2026-08-25 [INFO] Сервіс запущено";

    int res = match_line_posix(pattern, line);
    if (res == 1) {
        printf("Знайдено дату на початку рядка\n");
    }
    return 0;
}
```

```cpp
#include <iostream>
#include <string_view>
#include <regex>
#include <system_error>
#include <regex.h>

class PosixRegexMatcher {
public:
    explicit PosixRegexMatcher(std::string_view pattern, bool extended = true) {
        int flags = REG_NOSUB;
        if (extended) {
            flags |= REG_EXTENDED;
        }

        // Копіюємо string_view у null-terminated рядок для POSIX C-API
        std::string pattern_str(pattern);
        int ret = ::regcomp(&compiled_regex_, pattern_str.c_str(), flags);
        if (ret != 0) {
            char err_buf[256];
            ::regerror(ret, &compiled_regex_, err_buf, sizeof(err_buf));
            throw std::runtime_error(std::string("Regex compilation error: ") + err_buf);
        }
        is_valid_ = true;
    }

    ~PosixRegexMatcher() noexcept {
        if (is_valid_) {
            ::regfree(&compiled_regex_);
        }
    }

    PosixRegexMatcher(const PosixRegexMatcher&) = delete;
    PosixRegexMatcher& operator=(const PosixRegexMatcher&) = delete;

    PosixRegexMatcher(PosixRegexMatcher&& other) noexcept
        : compiled_regex_(other.compiled_regex_), is_valid_(other.is_valid_) {
        other.is_valid_ = false;
    }

    PosixRegexMatcher& operator=(PosixRegexMatcher&& other) noexcept {
        if (this != &other) {
            if (is_valid_) {
                ::regfree(&compiled_regex_);
            }
            compiled_regex_ = other.compiled_regex_;
            is_valid_ = other.is_valid_;
            other.is_valid_ = false;
        }
        return *this;
    }

    [[nodiscard]] bool matches(std::string_view text) const noexcept {
        if (!is_valid_) return false;
        std::string text_str(text);
        return ::regexec(&compiled_regex_, text_str.c_str(), 0, nullptr, 0) == 0;
    }

private:
    regex_t compiled_regex_{};
    bool is_valid_{false};
};

int main() {
    try {
        PosixRegexMatcher matcher("^[0-9]{4}-[0-9]{2}-[0-9]{2}");
        std::string_view line = "2026-08-25 [INFO] Сервіс запущено";

        if (matcher.matches(line)) {
            std::cout << "Знайдено дату на початку рядка\n";
        }
    } catch (const std::exception& e) {
        std::cerr << "Помилка: " << e.what() << '\n';
        return 1;
    }
    return 0;
}
```

## Сучасні альтернативи: ripgrep (`rg`)

Незважаючи на зрілість GNU `grep`, для інтерактивної розробки та пошуку у великих репозиторіях коду стандартом став `ripgrep` (`rg`), написаний мовою Rust. Його перевага базується на низці архітектурних рішень:

1. **Паралельний обхід каталогів із пулом потоків:** `ripgrep` використовує крадіжку завдань (*work-stealing thread pool*). Один потік сканує каталоги через `getdents64`, а пул робочих потоків паралельно обробляє чергу файлів, повністю навантажуючи всі ядра процесора та швидкі NVMe SSD.
2. **Вбудований аналіз `.gitignore`:** Утиліта за замовчуванням парсить файли правил ігнорування та автоматично пропускає бінарні файли, приховані каталоги та залежності (`node_modules`, `target`), зменшуючи обсяг зчитуваних даних на 90%.
3. **Гібридний SIMD-рушій `regex-automata`:** Використання AVX-512 та алгоритму Teddy для паралельного пошуку кількох підрядків одночасно.

Для класичних скриптів автоматизації та конвеєрів POSIX `grep` залишається незамінним через гарантовану присутність на будь-якому Unix-сервері, тоді як `ripgrep` виступає високопродуктивним інструментом для робочого середовища інженера.

## Типові пастки та правила використання в продакшені

### Буферизація в конвеєрах реального часу

За замовчуванням бібліотека стандартного виводу C (`stdio`) застосовує **блокову буферизацію** (розміром 4 КБ або 8 КБ), якщо дескриптор `stdout` підключено до каналу (pipe), а не до термінала.

Якщо запустити конвеєр для моніторингу подій:

```bash
# Помилка: повідомлення затримуються в буфері й з'являються пачками через хвилини
tail -f /var/log/nginx/access.log | grep "502 Bad Gateway" | mail -s "Alert" admin@example.com
```

Процес `grep` не скидатиме знайдені рядки в поштовий клієнт доти, доки не заповнить 4096 байтів буфера. Для вирішення цієї проблеми слід примусово вмикати порядкову буферизацію через прапорець `--line-buffered`:

```bash
# Правильно: кожен знайдений рядок негайно скидається в конвеєр
tail -f /var/log/nginx/access.log | grep --line-buffered "502 Bad Gateway" | mail -s "Alert" admin@example.com
```

### Робота з нульовими роздільниками: `-z`

При взаємодії з утилітами пошуку файлів (`find -print0`) або обробки аргументів (`xargs -0`) роздільником записів виступає не символ нового рядка `\n`, а нульовий байт `\0`.

Опція `-z` (`--null-data`) перемикає внутрішній розпізнавач меж рядків `grep` на байт `\0`:

```bash
# Знайти всі файли, в іменах яких є пробіли, і відфільтрувати ті, що містять слово "backup"
find . -type f -print0 | grep -z "backup" | xargs -0 ls -l
```

### Передача змінних оболонки, що починаються з дефіса

Якщо шаблон формується динамічно зі змінної, значення якої починається з дефіса (наприклад, `pattern="-v"`), `grep` сприйме це значення як прапорець командного рядка і завершиться з помилкою.

Для безпечної передачі параметрів завжди використовуйте явну опцію `-e` або маркер завершення опцій `--`:

```bash
# Безпечний пошук довільного значення змінної
grep -e "$USER_SEARCH_QUERY" data.txt
grep -- "$USER_SEARCH_QUERY" data.txt
```
