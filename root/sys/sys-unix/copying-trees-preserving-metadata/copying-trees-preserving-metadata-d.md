## Наївне копіювання та приховане руйнування стану

Спроба скопіювати робоче середовище служби звичайною командою `cp -r /var/lib/postgresql /backup/db` завершується без жодної помилки в терміналі, але розгортання цієї копії ламає базу даних. Служба PostgreSQL не запускається, оскільки конфігураційний файл із приватним сертифікатом замість початкових суворих прав `0600` отримує `0644` через поточну маску процесу `umask 022`, і сервер відмовляється читати ключ із міркувань безпеки. Усі файли табличних просторів отримують числовий UID користувача, який запустив команду копіювання, тому системний демон `postgres` втрачає право запису до власних каталогів. Жорсткі посилання між архівними сегментами журналів попереднього запису (WAL) перетворюються на дубльовані фізичні файли, подвоюючи зайнятий простір, а розріджений файл віртуального диска обсягом 100 ГБ, у якому реально було зайнято лише 5 ГБ, вичитується гігабайтами нулів і повністю забиває вільне місце на цільовому накопичувачі.

Ця аварія демонструє головну властивість файлових систем Unix: **файл не є лише послідовністю байтів корисного навантаження**. Звичайний системний виклик `read()` повертає винятково потік даних, ігноруючи весь навколишній контекст ядра VFS (Virtual Filesystem Switch). Коли програма створює новий файл через `open()` із прапорцем `O_CREAT`, ядро виділяє новий інод, призначає йому поточний системний час, поточні ідентифікатори процесу (UID/GID) та накладає фільтр `umask`. Щоб створити точний двійковий зліпок файлового дерева, утиліта повинна явно прочитати, зберегти й повторно відтворити всю структурну інформацію інода.

*Порівняння наслідків наївного копіювання (cp -r) та повного збереження метаданих VFS (cp -a, rsync -aHAX).*

## Анатомія метаданих Linux VFS

Для точного клонування каталогу необхідно контролювати шість незалежних вимірів стану інода, кожен із яких обслуговується окремими системними викликами ядра.

```
+-------------------------------------------------------------------------+
|                               INODE VFS                                 |
|                                                                         |
|  [Тип та права]      st_mode: тип (файл/каталог/symlink/fifo/dev)       |
|                               права (0755), SUID (04000), SGID (02000)  |
|  [Ідентичність]      st_uid, st_gid (власник та група)                  |
|  [Мітки часу]        st_atim (доступ), st_mtim (модифікація даних),     |
|                      st_ctim (зміна інода), st_btime (народження)       |
|  [Топологія]         st_dev, st_ino, st_nlink (структура hardlinks)     |
|  [Атрибути xattr]    user.*, system.posix_acl_*, security.selinux,      |
|                      security.capability, trusted.*                     |
|  [Розподіл блоків]   карта екстентів, дірки (holes), CoW-рефлінки       |
+-------------------------------------------------------------------------+
```

### 1. Режим і права доступу (`st_mode`)

Поле `st_mode` містить двійкову маску, яка кодує тип об'єкта (звичайний файл `S_IFREG`, каталог `S_IFDIR`, символьне посилання `S_IFLNK`, іменований канал `S_IFIFO`, блоковий `S_IFBLK` або символьний `S_IFCHR` пристрій, сокет `S_IFSOCK`) та 12 бітів прав доступу:
- 9 класичних бітів прав читання, запису та виконання для власника, групи та інших (`rwxrwxrwx`);
- біт встановлення ідентифікатора користувача при виконанні SUID (`04000`);
- біт встановлення ідентифікатора групи SGID (`02000`);
- біт обмеження видалення Sticky (`01000`).

Коли файл створюється викликом `open(path, O_CREAT | O_WRONLY, mode)`, ядро вираховує фактичні права за формулою `mode & ~umask`. Якщо процес мав маску `022`, біти запису для групи та інших скидаються. Щоб відновити початкові права, утиліта копіювання повинна викликати `fchmodat()` або явно скинути власну маску процесу через `umask(0)` перед початком операцій.

### 2. Ідентифікатори власника та групи (`st_uid`, `st_gid`)

Інод зберігає числові ідентифікатори користувача (UID) та групи (GID). Звичайний неіндивідуальний користувач не має права передавати володіння файлом іншій особі (виклик `fchownat()` повертає помилку `EPERM`). Тільки процес із адміністративною можливістю `CAP_CHOWN` (зазвичай суперкористувач `root`) може змінювати власника.

Важлива деталь взаємодії підсистем ядра: під час зміни власника через `fchownat()` ядро Linux з міркувань безпеки **автоматично скидає біти SUID та SGID**, щоб звичайний користувач не міг створити привілейований виконуваний двійковий файл від імені іншого користувача. Через це правильний алгоритм відновлення метаданих зобов'язаний спочатку змінювати власника (`fchownat`), і лише після цього встановлювати права доступу (`fchmodat`).

### 3. Часові позначки (`atime`, `mtime`, `ctime`, `btime`)

Ядро підтримує чотири часові мітки:
- `atime` (`st_atim`) — час останнього читання даних;
- `mtime` (`st_mtim`) — час останньої модифікації вмісту файлу;
- `ctime` (`st_ctim`) — час останньої зміни метаданих самого інода (прав, власника, кількості посилань);
- `btime` / `crtime` — час створення інода (доступний у файлових системах ext4, Btrfs, XFS через сучасний виклик `statx`).

У просторі користувача не існує системного виклику, який дозволяв би довільно встановити `ctime`: ядро завжди оновлює `ctime` до поточного системного годинника при будь-якій операції запису або зміні атрибутів. Натомість мітки `atime` та `mtime` відновлюються з наносекундною точністю за допомогою виклику `utimensat()`. Оскільки будь-який запис даних чи зміна прав через `fchmodat` негайно перезаписує `mtime` і `ctime`, виклик `utimensat` завжди повинен бути **останнім кроком** у ланцюжку створення файлу.

### 4. Розширені атрибути (`xattr`) та списки контролю доступу (ACL)

Розширені атрибути дозволяють пов'язувати з інодом довільні пари «ім'я → бінарне значення». Вони розділені на чотири ізольовані простори імен:
- `user.*` — довільні прикладні метадані (наприклад, MIME-типи, хеш-суми, контрольні мітки);
- `system.*` — системні структури ядра, насамперед POSIX Access ACL (`system.posix_acl_access`) та Default ACL для каталогів (`system.posix_acl_default`);
- `security.*` — мітки обов'язкового контролю доступу SELinux (`security.selinux`), профілі AppArmor та файлові можливості виконуваних бінарників (`security.capability`);
- `trusted.*` — службові дані, доступні лише процесам із `CAP_SYS_ADMIN` (використовуються, наприклад, у шарах OverlayFS).

Звичайне копіювання байтів повністю втрачає xattr. Утиліта повинна вичитувати список імен через `llistxattr()`, отримувати байти значень через `lgetxattr()` і записувати їх на цільовий інод через `lsetxattr()`.

### 5. Топологія жорстких та символьних посилань

Жорстке посилання (hardlink) — це додатковий запис у таблиці каталогу, що вказує на вже наявний номер інода (`st_ino`) на тому самому пристрої (`st_dev`). Якщо дерево містить файл із кількома жорсткими посиланнями (`st_nlink > 1`), просте копіювання створить стільки ж незалежних інодів із копіями даних. Для збереження топології утиліта повинна вести в оперативній пам'яті таблицю відповідності пар `(st_dev, st_ino)` створеним цільовим шляхам. Коли інод зустрічається вперше, його вміст копіюється; при наступних зустрічах замість створення файлу викликається `linkat()`.

Символьне посилання (symlink) містить усередині текст шляху. Якщо утиліта відкриває symlink стандартним викликом `open()` без прапорця `O_NOFOLLOW`, ядро розіменовує його й читає цільовий файл. Це призводить або до нескінченної рекурсії (при циклічних посиланнях), або до дублювання великих файлів, або до створення некоректних посилань, якщо шлях був відносним.

### 6. Структура блоків: розрідженість (Sparse) та Copy-on-Write

Розріджений файл містить «дірки» — нерозподілені логічні діапазони, які при читанні повертають нулі, але не займають фізичних секторів на диску. Програма, що читає такий файл лінійно, отримує гігабайти нульових байтів і записує їх у цільовий файл, фізично виділяючи блоки диска. Для збереження розрідженості ядро надає механізм пошуку меж дірок через `lseek()` із параметрами `SEEK_DATA` та `SEEK_HOLE`.

Сучасні файлові системи (Btrfs, XFS) підтримують клонування екстентів без дублювання фізичних блоків (Reflink / Copy-on-Write). Системний виклик `copy_file_range()` або `ioctl(fd, FICLONE, src_fd)` дозволяє створити новий файл, що посилається на ті самі блоки диска, що виконується миттєво і не витрачає дисковий простір до моменту першої зміни даних.

Детальний перелік відповідних прапорців і системних викликів дивіться у вставці [порівняльну таблицю параметрів утиліт та системних викликів ядра](root:sys-unix/copying-trees-preserving-metadata/api-copy-tools-matrix.md), а програмну реалізацію повного циклу обробки інода наведено у вставці [робочий інструмент точного клонування вузлів VFS на C та C++](root:sys-unix/copying-trees-preserving-metadata/proj-metadata-tree-cloner.md).

## Локальне архівне копіювання: механіка `cp -a`

Утиліта GNU `cp` є основним інструментом локального клонування на рівні однієї операційної системи.

```sh
# Повне точне клонування структури каталогу
cp -a /source/tree /destination/tree
```

### Розгортання прапорця `-a`

Прапорець `-a` (`--archive`) у реалізації GNU coreutils є точним еквівалентом комбінації:

```
cp -dR --preserve=all
```

Розберемо значення кожного компонента:
1. **`-d`** — еквівалент `-P --preserve=links`:
   - `-P` (`--no-dereference`) — забороняє перехід за символьними посиланнями: вони копіюються як символьні посилання, а не як файли, на які вони вказують;
   - `--preserve=links` — утиліта відстежує пари `(dev, ino)` і відтворює жорсткі посилання між файлами в цільовому дереві;
2. **`-R`** (`-r`, `--recursive`) — рекурсивний обхід каталогів та копіювання спеціальних файлів (FIFO, блокових і символьних пристроїв);
3. **`--preserve=all`** — обов'язкова вимога зберегти повний спектр атрибутів:
   - `mode` — права доступу, включно зі спеціальними бітами SUID/SGID/Sticky;
   - `ownership` — UID та GID власника;
   - `timestamps` — наносекундні мітки `atime` та `mtime`;
   - `xattr` — усі розширені атрибути, включно з POSIX ACL;
   - `context` — контексти безпеки SELinux;
   - `links` — топологія жорстких зв'язків.

### Розріджені файли та Copy-on-Write

За замовчуванням GNU `cp` використовує евристику `--sparse=auto`: утиліта сканує прочитаний буфер даних на наявність суцільних послідовностей нульових байтів. Якщо виявлено блок нулів, замість виклику `write()` виконується `lseek(dst_fd, len, SEEK_CUR)`, що створює дірку на файловій системі приймача. За потреби можна вказати `--sparse=always` (примусово шукати дірки навіть у файлах, які спочатку не були розрідженими) або `--sparse=never` (заповнювати дірки реальними нулями).

Для файлових систем із підтримкою CoW (Btrfs, XFS) сучасна версія `cp` за замовчуванням намагається використати виклик `copy_file_range()`. Якщо передати прапорець:

```sh
cp -a --reflink=auto /data/vms /backup/vms
```

утиліта спробує створити миттєві аліаси фізичних блоків на рівні файлової системи. Якщо джерело й приймач розташовані на різних файлових системах або накопичувач не підтримує `FICLONE`, режим `auto` плавно відкочується до звичайного поблокового копіювання. Прапорець `--reflink=always` видає помилку та перериває операцію, якщо швидке CoW-клонування неможливе.

### Порядок відновлення метаданих для каталогів (Post-Order Traversal)

Особливою проблемою під час копіювання дерев є каталоги. Якщо утиліта створить каталог `mkdir("dest/dir")`, негайно встановить його права `0555` (тільки читання) і налаштує `mtime`, наступна спроба створити всередині нього файл `dest/dir/file.txt` завершиться помилкою доступу `EACCES`. Крім того, створення нового файлу всередині каталогу змінює вміст каталогу як таблиці імен, тому ядро автоматично оновить `mtime` каталогу до поточного системного часу, знищивши збережену часову позначку.

Через це GNU `cp` реалізує двоетапний обхід:
1. Під час спуску деревом каталоги створюються з тимчасовими правами, що дозволяють запис (`0700` або вихідні права з бітом `w`), а їхній початковий стан зберігається у внутрішньому стеку обходу;
2. Створюються та заповнюються всі вкладені файли, відновлюються їхні права, власники й мітки часу;
3. Під час підйому деревом назад (постфіксний обхід) для каталогів виконується фінальна корекція: викликається `fchmodat()` для встановлення точних прав і `utimensat()` для фіксації `atime`/`mtime`.

### Захист від перетину меж монтування: `--one-file-system`

Під час резервного копіювання системного кореня `/` рекурсивний обхід може випадково зайти у віртуальні псевдофайлові системи (`/proc`, `/sys`, `/dev`), призвести до читання нескінченних потоків `/dev/zero` або спробувати скопіювати змонтовані мережеві ресурси NFS. Прапорець:

```sh
cp -a --one-file-system / /mnt/backup/rootfs
```

змушує `cp` запам'ятовувати ідентифікатор пристрою `st_dev` початкового каталогу. Якщо в процесі обходу зустрічається точка монтування з іншим `st_dev`, утиліта ігнорує її вміст.

## Потокова серіалізація та конвеєри: класичний `tar`

Команда `cp` оптимізована для локального використання на одній машині, де файли створюються безпосередньо у цільовій VFS. Проте при передачі дерева через мережу або між ізольованими просторами імен потрібна **серіалізація**: перетворення складної ієрархії файлів, каталогів, метаданих та спеціальних вузлів у єдиний послідовний потік байтів без створення проміжних архівів на диску.

Класичний конвеєр Unix вирішує цю задачу за допомогою архіватора `tar`:

```sh
tar -cf - -C /source . | (cd /destination && tar -xpf -)
```

Або у сучаснішому синтаксисі:

```sh
tar -cf - -C /source . | tar -xpf - -C /destination
```

```
[ Джерело: /source ]
       │
       ▼ (читання VFS, кодування метаданих)
┌──────────────┐
│  tar -cf -   │ ──(stdout)──► [ Міжпроцесний канал: Pipe ]
└──────────────┘                                │
                                                ▼ (stdin)
                                         ┌──────────────┐
                                         │  tar -xpf -  │
                                         └──────────────┘
                                                │
                                                ▼ (декодування, створення вузлів VFS)
                                        [ Приймач: /destination ]
```

### Еволюція форматів та обмеження стандартів

Утиліта `tar` (від *Tape Archive*) спочатку створювалася для запису на магнітні стрічки. Потік `tar` складається з послідовності блоків фіксованого розміру по 512 байтів. Кожен файл починається із заголовка, за яким ідуть блоки даних файлу, вирівняні до 512 байтів.

Історичний стандарт POSIX.1-1988 (формат `ustar`) має жорсткі обмеження, через які точне копіювання сучасних систем ламається:
- максимальний розмір файлу обмежений 8 ГБ (поле розміру займає 11 вісімкових символів);
- максимальна довжина шляху обмежена 256 символами (100 символів імені + 155 символів префікса каталогу);
- мітки часу зберігаються лише з точністю до секунди (наносекунди відкидаються);
- розширені атрибути (xattr), ACL та мітки SELinux не підтримуються взагалі.

Сучасні дистрибутиви Linux використовують формат **POSIX.1-2001 (`pax`)** або розширений формат **GNU tar**. Вони вирішують проблему обмежень за допомогою спеціальних розширених заголовків (типу `x` або `g`), у яких довільні пари «ключ=значення» записуються у форматі UTF-8 необмеженої довжини.

### Необхідні прапорці GNU `tar` для збереження метаданих

Щоб конвеєр `tar` не втратив жодної деталі VFS, команда розгортання та пакування повинна містити розширені ключі:

```sh
tar --create --file=- \
    --directory=/source \
    --acls \
    --xattrs \
    --selinux \
    --sparse \
    . | tar --extract --file=- \
            --directory=/destination \
            --preserve-permissions \
            --same-owner \
            --acls \
            --xattrs \
            --selinux \
            --sparse
```

Розбір критичних прапорців:
- **`-p`** (`--preserve-permissions`) — відновлює повну маску прав доступу, ігноруючи `umask` процесу розпакування;
- **`--same-owner`** — відновлює числові UID/GID (для суперкористувача увімкнено за замовчуванням);
- **`--acls`** — пакує та розгортає розширені списки контролю доступу;
- **`--xattrs`** — зберігає всі розширені атрибути файлів;
- **`--selinux`** — зберігає контексти безпеки SELinux;
- **`-S`** (`--sparse`) — детектує дірки у файлах і пакує їх як розріджені структури, відновлюючи розрідженість на приймачі;
- **`-C /dir`** — безпечна зміна робочого каталогу перед виконанням операцій, що уникає збереження абсолютних шляхів.

### Передача через SSH та компресія

Головна перевага серіалізації `tar` — легкість інтеграції з мережевими протоколами. Перенесення дерева на віддалений сервер виконується через захищений канал SSH:

```sh
tar -cf - --acls --xattrs -C /source . | ssh root@remote.host "tar -xpf - --acls --xattrs -C /destination"
```

У високошвидкісних локальних мережах (10 GbE / 40 GbE) передача **незжатого** потоку є найшвидшим варіантом, оскільки алгоритми компресії вперуться в продуктивність одного ядра процесора. У повільних каналах зв'язку (WAN, Інтернет) у конвеєр додається швидкий паралельний архіватор:

```sh
tar -cf - --acls --xattrs -C /source . | zstd -T0 -3 | ssh root@remote.host "zstd -d | tar -xpf - --acls --xattrs -C /destination"
```

### Крайові випадки: файли, що змінюються під час читання

Якщо під час роботи `tar` активний процес дописує дані у файл (наприклад, у журнал бази даних), розмір файлу збільшується або змінюється його `mtime`. Архіватор виявляє розбіжність між заголовком і фактично прочитаною кількістю байтів, видає попередження:

```
tar: file changed as we read it
```

і завершує роботу з ненульовим кодом повернення (`exit status 1`). У сценаріях автоматизованого резервування це вимагає або створення знімків файлової системи (LVM / Btrfs / ZFS snapshot) перед копіюванням, або використання інструментів, які вміють виконувати повторні синхронізаційні проходи.

## Універсальний стандарт синхронізації: `rsync`

Команда `cp -a` переписує файли наново, а конвеєр `tar` повторно передає весь потік байтів. Якщо дерево обсягом 1 ТБ уже було скопійовано вчора, і сьогодні змінилося лише 100 МБ даних у різних файлах, обидва інструменти виконуватимуть повну роботу від початку.

Утиліта `rsync` вирішує задачу точного копіювання з кардинально іншою філософією: вона знаходить різницю між двома деревами каталогів і передає винятково змінені байти, гарантуючи при цьому повне відновлення структури метаданих.

```sh
rsync -aHAX --sparse --numeric-ids /source/ /destination/
```

> ⚠️ **Слеш наприкінці шляху джерела має вирішальне значення:**
> - `rsync -a /source/ /dest/` копіює **вміст** каталогу `source` безпосередньо в каталог `dest`;
> - `rsync -a /source /dest/` створює підкаталог `dest/source` і поміщає дані всередину нього.

### Набір прапорців максимальної точності: `-aHAX`

Золотим стандартом точного копіювання є комбінація прапорців `-aHAX`:

```
rsync -aHAX -S --numeric-ids
```

1. **`-a`** (`--archive`) — базова основа, що розгортається у сім прапорців:
   - `-r` (`--recursive`) — рекурсивний обхід підкаталогів;
   - `-l` (`--links`) — копіювання символьних посилань як символьних посилань;
   - `-p` (`--perms`) — збереження прав доступу `st_mode`;
   - `-t` (`--times`) — збереження міток модифікації `mtime`;
   - `-g` (`--group`) — збереження групи володіння;
   - `-o` (`--owner`) — збереження власника інода (лише для суперкористувача);
   - `-D` (`--devices --specials`) — збереження файлів символьних і блокових пристроїв та спеціальних вузлів (FIFO, сокети).
2. **`-H`** (`--hard-links`) — відстежує зв'язки між інодами й відтворює жорсткі посилання на приймачі.
   *Ціна прапорця:* rsync зберігає в оперативній пам'яті таблицю всіх пар `(dev, ino)`. Для дерев із десятками мільйонів файлів прапорець `-H` потребує додаткових гігабайтів оперативної пам'яті.
3. **`-A`** (`--acls`) — зберігає розширені списки контролю доступу (POSIX ACL), автоматично вмикаючи прапорець `--perms`.
4. **`-X`** (`--xattrs`) — зберігає всі розширені атрибути файлів.
5. **`-S`** (`--sparse`) — детектує послідовності нулів і перетворює їх на розріджені дірки на приймачі.
6. **`--numeric-ids`** — передає числові значення UID та GID без спроби зіставити їх з іменами користувачів на приймачі через системну базу `/etc/passwd`. Це критично важливо під час перенесення кореневих файлових систем або контейнерів, де UID 1000 на вихідній машині може відповідати зовсім іншому користувачеві на цільовому сервері.

### Алгоритм дельта-передачі блоків (Rsync Delta Algorithm)

Головна інженерна перевага `rsync` — унікальний блоковий дельта-алгоритм передачі, розроблений Ендрю Тріджеллом і Полом Маккеррасом.

![Принцип роботи блочного дельта-алгоритму rsync](/root/sys/sys-unix/copying-trees-preserving-metadata/img/rsync-delta-algorithm.svg)

*Схема взаємодії компонентів rsync: обчислення ковзної суми Adler-32 та блочного хешу MD5 для мінімізації переданих даних.*

Процес синхронізації файлу виконується наступним чином:
1. **Швидка перевірка (Quick Check):** За замовчуванням `rsync` порівнює розмір файлу та мітку часу модифікації `mtime`. Якщо вони повністю збігаються, файл вважається незміненим і пропускається без читання даних (якщо не передано прапорець `-c`, `--checksum`, що примушує рахувати хеші всіх файлів).
2. **Блокове хешування на стороні приймача (Receiver):** Якщо файл на приймачі існує, але має відмінний розмір або час, Receiver розбиває свій наявний файл на неперетинні блоки фіксованого розміру `S` (зазвичай від 1 КБ до 8 КБ). Для кожного блоку обчислюються дві контрольні суми:
   - швидка 32-бітна **ковзна контрольна сума (Rolling Checksum)** на основі алгоритму Adler-32;
   - стійкий 128-бітний хеш MD4 або MD5.
   Receiver відправляє цю компактну таблицю хешів Відправнику (Sender).
3. **Побайтовий пошук на стороні відправника (Sender):** Sender починає обчислювати ковзну контрольну суму для вікна розміром `S`, зміщуючи його на **кожен один байт** у вихідному файлі.
   - Завдяки властивості ковзного хешування, обчислення суми для нового зміщення `i+1` не вимагає перечитування всього блоку: старий байт, що випав із лівого краю вікна, віднімається, а новий байт праворуч додається за `O(1)` операцій:

```
R(offset + 1) = ( R(offset) - byte_out + byte_in ) mod M
```

   - Якщо 32-бітний хеш збігається з одним із блоків приймача, Sender обчислює для цього вікна важкий 128-бітний хеш MD5. Якщо й сильний хеш збігається, фіксується тотожний блок, і вікно зміщується одразу на розмір `S`.
   - Якщо збігу немає, поточний байт вважається зміненим і накопичується в буфері літеральних даних.
4. **Передача дельти та реконструкція:** Sender передає мережею лише нові сирі байти та номери блоків, які Receiver може скопіювати сам у себе зі свого старого локального файлу.

### Надійність, атомарність та докачування

За замовчуванням `rsync` забезпечує повну атомарність оновлення:
1. Новий файл збирається у тимчасовий прихований файл виду `.filename.XXXXXX` у тому самому каталозі призначення;
2. Після успішного запису всіх блоків та звірки контрольної суми викликається системний виклик `rename()`, який атомарно підміняє старий файл новим;
3. На тимчасовий вузол накладаються збережені розширені атрибути, права та часові позначки `utimensat()`.

Якщо мережеве з'єднання обривається під час передачі багатогігабайтного файлу, тимчасовий файл за замовчуванням видаляється. Щоб зберегти завантажені байти для наступного відновлення, застосовують прапорці:

```sh
# Збереження недокачаних файлів у спеціальний прихований каталог
rsync -aHAX --partial --partial-dir=.rsync-partial /src/ user@host:/dst/
```

Для файлів баз даних або образів віртуальних машин, які оновлюються шляхом простого дописування в кінець (append-only), корисним є прапорець `--append-verify`: `rsync` припускає, що початковий сегмент файлу на приймачі тотожний джерелу, порівнює його розмір і докачує лише нові байти з обов'язковою верифікацією повного файлу наприкінці.

## Порівняльний інженерний вибір та архітектура конвеєрів

Вибір між `cp`, `tar` та `rsync` залежить від розташування даних, пропускної здатності каналу та наявності попередніх копій.

![Архітектура трьох конвеєрів копіювання: cp, tar, rsync](/root/sys/sys-unix/copying-trees-preserving-metadata/img/copy-pipelines-architecture.svg)

*Архітектурні моделі трьох підходів: локальний CoW у ядрі, серіалізація в конвеєрі та клієнт-серверна дельта-синхронізація.*

### Порівняльна матриця інструментів

| Критерій | `cp -a --reflink=auto` | `tar -cf - ... \| tar -xpf -` | `rsync -aHAX --sparse` |
| :--- | :--- | :--- | :--- |
| **Основне призначення** | Локальне копіювання на одній машині | Потокова передача / міграція через мережу | Інкрементна синхронізація та бекапи |
| **Швидкість при першому копіюванні (локально)** | **Максимальна** (миттєво при CoW, прямий I/O ядра) | Висока (послідовний потік, накладні витрати pipe) | Середня (витрати на сканування та порівняння) |
| **Швидкість при повторному копіюванні** | Повне переписування | Повна повторна передача | **Екстремально висока** (дельта-алгоритм) |
| **Накладні витрати пам'яті (RAM)** | Мінімальні (лише стек обходу каталогів) | Мінімальні (буфер конвеєра 64 КБ) | Високі при `-H` (таблиця всіх інодів у RAM) |
| **Підтримка CoW / Reflink** | **Так** (`copy_file_range`, `ioctl FICLONE`) | Ні (потік розгортається у звичайні байти) | Ні (створюються нові незалежні файли) |
| **Мережева передача** | Не підтримується напряму | Ідеально через SSH або сокет `netcat` | Нативно через SSH або rsync daemon |
| **Стійкість до обривів** | Немає (копіювання починається заново) | Немає (потік переривається) | **Повна** (прапорці `--partial`, `--append`) |
| **Атомарність оновлення** | Ні (файли змінюються на місці) | Ні (файли розпаковуються на місці) | **Так** (запис у `.tmp` + атомарний `rename`) |

### Інженерні рекомендації щодо вибору інструмента

1. **Клонування каталогів у межах одного сервера / накопичувача:**
   Використовуйте `cp -a --reflink=auto`. На сучасних файлових системах (Btrfs, XFS) операція виконується за мілісекунди без навантаження на диск, а на традиційних (ext4) досягає граничної пропускної здатності шини NVMe.
2. **Одноразове перенесення великого обсягу даних (терабайти) через швидку локальну мережу (LAN 10G+):**
   Використовуйте конвеєр `tar -cf - ... | ssh host 'tar -xpf - ...'` без увімкнення компресії. Це забезпечує чистий послідовний I/O без надлишкових обчислень контрольних сум дельта-алгоритму, які можуть перевантажити процесор.
3. **Регулярне резервне копіювання, WAN-канали, нестабільні мережі та докачування:**
   Використовуйте `rsync -aHAX --sparse --numeric-ids --partial`. Це єдиний інструмент, який мінімізує мережевий трафік, гарантує безпечне оновлення через тимчасові файли та дозволяє відновити перерваний процес із точки зупинки.
