# ⚙️ Низькорівневе клонування вузла VFS: повне збереження метаданих на C та C++

Копіювання файлового дерева в середовищі Linux на рівні користувацького простору часто сприймається як тривіальний цикл обходу каталогів та побайтового перенесення вмісту файлів через системні виклики `read()` та `write()`. Проте наївне читання корисного навантаження повністю ігнорує шар метаданих віртуальної файлової системи (VFS): маски прав доступу, біти SUID/SGID/Sticky, числові ідентифікатори власника (UID) та групи (GID), наносекундні часові мітки `atime`/`mtime`, розширені атрибути `xattr`, списки контролю доступу POSIX ACL, контексти безпеки SELinux, файлові можливості (capabilities), розріджені діапазони (sparse holes), топологію жорстких посилань (hardlinks) та спеціальні файли пристроїв. Втрата будь-якого з цих компонентів руйнує цілісність клонованої системи — сервіси втрачають доступ до конфігурацій, виконувані бінарники втрачають привілеї, бази даних аварійно зупиняються, а розріджені образи дисків роздуваються до повного фізичного обсягу накопичувача.

Створення точного двійкового зліпка вимагає оркестрації низькорівневих системних викликів ядра родини `*at`, суворого дотримання послідовності модифікацій інода, використання апаратних механізмів Copy-on-Write (CoW), паралельного обходу дерева через неблокуючі черги завдань, захисту від динамічних станів гонитви (TOCTOU) та постфіксного закриття ієрархії каталогів.

## Архітектурний конвеєр реплікації інода

Кожен об'єкт файлової системи Linux представлений у ядрі структурою індексного вузла (inode). Процес точного клонування одного вузла розгортається у детермінований конвеєр системних викликів:

```
[Джерело VFS]
      │
      ▼
[1. statx(AT_SYMLINK_NOFOLLOW)] ──► Зчитування типу, прав, UID/GID, timestamps, size, dev_major/minor
      │
      ▼
[2. Створення вузла-приймача]
   ├── S_ISREG   ──► openat(O_CREAT | O_WRONLY | O_TRUNC, 0600)  [безпечні початкові права]
   ├── S_ISDIR   ──► mkdirat(dst_path, 0700)                      [права на запис для наповнення]
   ├── S_ISLNK   ──► readlinkat() + symlinkat()                   [текст цілі symlink]
   ├── S_ISFIFO  ──► mkfifoat() або mknodat(S_IFIFO)              [іменований канал без I/O блокування]
   ├── S_ISCHR   ──► mknodat(S_IFCHR, makedev(maj, min))          [символьний пристрій, CAP_MKNOD]
   ├── S_ISBLK   ──► mknodat(S_IFBLK, makedev(maj, min))          [блоковий пристрій, CAP_MKNOD]
   └── S_ISSOCK  ──► Пропуск із попередженням                     [IPC-ендпоінт активного процесу]
      │
      ▼
[3. Перенесення даних] 
   ├── Спроба CoW reflink ──► copy_file_range() / ioctl(FICLONE)
   └── Fallback: Sparse   ──► lseek(SEEK_DATA/SEEK_HOLE) + read/write + ftruncate()
      │
      ▼
[4. Розширені атрибути] ──► llistxattr() ──► lgetxattr() ──► lsetxattr()
      │                      (включно з system.posix_acl_* та security.*)
      ▼
[5. Власник та група]   ──► fchownat(AT_SYMLINK_NOFOLLOW)
      │                      (ядро автоматично скидає біти SUID/SGID!)
      ▼
[6. Відновлення прав]   ──► fchmodat(mode & 07777)
      │                      (фіксація SUID/SGID/Sticky після fchownat)
      ▼
[7. Часові позначки]    ──► utimensat(AT_SYMLINK_NOFOLLOW, [atime, mtime])
                             (завжди ОСТАННІЙ крок: фіксує наносекунди)
```

## Причинно-наслідкова послідовність викликів ядра

Порядок системних викликів у конвеєрі є критично важливим. Будь-яка перестановка кроків призводить до скидання або спотворення метаданих на рівні VFS ядра.

### 1. Зчитування розширеного стану через `statx`

Замість застарілих системних викликів `stat`, `fstat` та `lstat` сучасний рушій клонування використовує системний виклик `statx()`, введений у ядрі Linux 4.11:

```
int statx(int dirfd, const char *pathname, int flags,
          unsigned int mask, struct statx *statxbuf);
```

- **Прапорець `AT_SYMLINK_NOFOLLOW`:** гарантує, що якщо джерелом є символьне посилання, системний виклик поверне атрибути самого symlink-вузла (його права, власника, розмір, що дорівнює довжині рядка цілі в байтах), а не кінцевого файлу, на який воно вказує. Без цього прапорця symlink буде незворотно розіменовано, перетворивши посилання на дублікат цільового файлу;
- **Маска `mask`:** дозволяє явно замовити потрібні поля (`STATX_TYPE | STATX_MODE | STATX_UID | STATX_GID | STATX_ATIME | STATX_MTIME | STATX_SIZE | STATX_INO`), уникаючи надлишкових звернень до повільних дискових структур або віддалених мережевих файлових систем;
- **Наносекундні поля `stx_atime` та `stx_mtime`:** містять структури `statx_timestamp` із полями `tv_sec` (секунди) та `tv_nsec` (наносекунди), що забезпечує точність часових позначок без втрати інформації;
- **Ідентифікатори пристроїв:** для спеціальних файлів поля `stx_rdev_major` та `stx_rdev_minor` повертають точні мажорні та мінорні номери драйверів.

### 2. Створення вузла-приймача та реплікація спеціальних файлів VFS

Створення вузла залежить від типу `stx_mode & S_IFMT`:

- **Звичайні файли (`S_ISREG`):** відкриваються викликом `openat()` із прапорцями `O_CREAT | O_WRONLY | O_TRUNC` та навмисно обмеженими початковими правами `0600` (читання та запис тільки для власника). Це усуває стан гонитви (Time-of-Check to Time-of-Use, TOCTOU): якби файл створювався одразу з вихідними широкими правами (наприклад, `0644` чи `0777`), сторонній непривілейований процес у системі встиг би прочитати проміжний стан конфіденційних даних до того, як на файл буде накладено списки ACL та фінальний режим доступу;
- **Каталоги (`S_ISDIR`):** створюються викликом `mkdirat()` із тимчасовими правами `0700` (`rwx------`). Тимчасовий повний доступ потрібен для того, щоб процес міг безперешкодно наповнювати каталог вкладеними файлами й підкаталогами, навіть якщо за початковою специфікацією каталог повинен мати права `0555` (тільки читання) або `0400`;
- **Символьні посилання (`S_ISLNK`):** вміст symlink (шлях, на який він вказує) вичитується системним викликом `readlinkat()`, після чого новий вузол створюється через `symlinkat()`. В ОС Linux символьні посилання не мають власних незалежних прав доступу (VFS завжди ігнорує біти прав symlink при переході), тому зміна режиму через `chmod` для них не застосовується.

#### Іменовані канали FIFO (`S_ISFIFO`) та уникнення блокування

Іменовані канали створюються системним викликом `mkfifoat(dst_dirfd, name, 0600)` або універсальним `mknodat(dst_dirfd, name, S_IFIFO | 0600, 0)`. Створення FIFO не потребує суперкористувацьких привілеїв `CAP_MKNOD`, вимагаючи лише прав запису в цільовий каталог.

Критичною інженерною пасткою при роботі з FIFO є операції вводу-виводу:
1. Клонувальник **ніколи не повинен відкривати FIFO для читання або запису** стандартним викликом `open(path, O_RDONLY)` без прапорця `O_NONBLOCK`. За стандартом POSIX спроба відкрити канал тільки на читання блокує викликаючий потік ядра доти, доки інший процес не відкриє той самий канал на запис;
2. Якщо утиліта спробує перенести дані з джерельного FIFO через цикл `read()`/`write()`, потік назавжди зависне в неперервному очікуванні (`uninterruptible sleep`, стан `D` у таблиці процесів);
3. Буфер каналу розміром 64 КБ живе виключно в оперативній пам'яті ядра під час активного обміну між процесами і не є частиною збереженого дискового стану. Рушій клонування лише відтворює інод каналу в таблиці каталогу, копіює його метадані (власника, права, xattr, часові мітки) і завершує обробку вузла без виконання I/O.

#### Символьні та блокові пристрої (`S_ISCHR`, `S_ISBLK`)

Спеціальні файли пристроїв представляють інтерфейси зв'язку ядра з драйверами апаратних компонентів або віртуальних підсистем. Створення таких вузлів здійснюється викликом:

```
dev_t dev = makedev(stx.stx_rdev_major, stx.stx_rdev_minor);
mknodat(dst_dirfd, name, (stx.stx_mode & S_IFMT) | 0600, dev);
```

Внутрішня організація номерів пристроїв у Linux базується на 64-бітному типі `dev_t` (макроси з `<sys/sysmacros.h>`):
- **Мажорний номер (`major`):** ідентифікує тип драйвера в ядрі (наприклад, `8` для SCSI/SATA дисків `sd`, `259` для накопичувачів NVMe, `1` для системних символьних пристроїв `/dev/null`, `/dev/urandom`, `4` для терміналів TTY);
- **Мінорний номер (`minor`):** вказує на конкретний фізичний екземпляр або дисковий розділ, керований цим драйвером (наприклад, `/dev/sda1` має major 8, minor 1; `/dev/sda2` — major 8, minor 2).

> 🔒 **Вимоги безпеки та привілей `CAP_MKNOD`:**
> Створення вузлів блокових та символьних пристроїв є прямою загрозою безпеці ОС, оскільки наявність файлу пристрою з довільними номерами дозволяє непривілейованому процесу читати й перезаписувати блоки фізичного накопичувача в обхід прав VFS. Через це ядро Linux дозволяє виклик `mknodat` для `S_IFCHR`/`S_IFBLK` **винятково процесам з адміністративною можливістю `CAP_MKNOD`** (або користувачу `root`).
> 
> Якщо копіювання запускається звичайним користувачем або всередині непривілейованого контейнера (де `CAP_MKNOD` скинуто в просторі імен користувачів user namespace), `mknodat()` негайно повертає помилку `EPERM`. Утиліта повинна мати налаштовану політику деградації: або пропускати файли пристроїв із діагностичним попередженням (поведінка `rsync --no-specials`), або аварійно завершувати процес, якщо створення точного зліпка системного дерева `/dev` є критичною умовою бекапу.

#### Сокети домену Unix (`S_ISSOCK`)

Сокети локальної міжпроцесної взаємодії (UNIX domain sockets, IPC) існують у просторі імен VFS як точки підключення клієнтів до серверних процесів (наприклад, `/run/systemd/private` або `/tmp/.X11-unix/X0`).

Спроба створити сокет системним викликом `mknodat(dst_dirfd, name, S_IFSOCK | 0600, 0)` у Linux **заборонена ядром і повертає помилку `EINVAL`** (на відміну від деяких BSD-систем). В ОС Linux файл сокета у VFS створюється винятково парою системних викликів `socket(AF_UNIX, SOCK_STREAM, 0)` та `bind(sockfd, (struct sockaddr*)&addr, len)`.

Проте навіть якщо утиліта створить сокет через `bind()`, результуючий вузол на диску буде «мертвим» (unbound): будь-яка спроба клієнтської програми підключитися через `connect()` поверне помилку `ECONNREFUSED`, оскільки за сокетом не закріплено активного процесу ядра, що виконує `listen()` або `accept()`. Всі промислові утиліти копіювання (`cp`, `rsync`, `tar`) за замовчуванням **пропускають файли сокетів**, реєструючи це в журналі подій, оскільки міграція стану відкритих дескрипторів міжпроцесного зв'язку є прерогативою систем збереження стану процесів (CRIU, Checkpoint/Restore In Userspace), а не файлових клонувальників.

### 3. Оптимізація перенесення даних: Reflink та розріджені дірки

Перенесення тіла файлу розділене на два послідовні рівні: швидкий апаратний CoW-шлях та надійний розріджений I/O-цикл.

```
[Початок копіювання даних]
           │
           ▼
[copy_file_range(src_fd -> dst_fd)] ──(успіх, len == size)──► [Дані скопійовано миттєво через CoW]
           │
      (помилка EXDEV, ENOTSUP або неповний запис)
           │
           ▼
[Скидання покажчиків: lseek(0, SEEK_SET)]
           │
           ▼
┌──► [lseek(src_fd, offset, SEEK_DATA)] ──(ENXIO: більше немає даних)──► [ftruncate(dst_fd, total_size)]
│          │
│     (знайдено зміщення початку блоку даних)
│          │
│          ▼
│    [lseek(src_fd, data_start, SEEK_HOLE)] ──► (знайдено кінець блоку даних)
│          │
│          ▼
│    [lseek(dst_fd, data_start, SEEK_SET)] ──► (синхронізація позиції запису)
│          │
│          ▼
│    [Цикл read() -> write() для діапазону (hole_start - data_start)]
│          │
└──────────┴── offset = hole_start
```

#### Швидкий шлях: Copy-on-Write через `copy_file_range`

Системний виклик `copy_file_range()` (або виклик керування вводом-виводом `ioctl(dst_fd, FICLONE, src_fd)`) дозволяє виконати нуль-копійне клонування екстентів на рівні ядра без завантаження блоків у користувацький буфер. На сучасних файлових системах (Btrfs, XFS, OCFS2) ядро просто збільшує лічильники посилань на спільні фізичні блоки у B-дереві файлової системи. Багатогігабайтний файл клонується за мікросекунди без витрат дискового простору.

Якщо файли розташовані на різних точках монтування (помилка `EXDEV`), цільова ФС не підтримує спільні екстенти (`ENOTSUP` / `EOPNOTSUPP`) або виклик переніс лише частину байтів, алгоритм повертає покажчики файлів у нульову позицію через `lseek(fd, 0, SEEK_SET)` і переходить до поблокового розрідженого копіювання.

#### Збереження розрідженості (Sparse Files) через `SEEK_DATA` / `SEEK_HOLE`

Звичайне лінійне читання розрідженого файлу (наприклад, віртуального диска QCOW2/RAW обсягом 100 ГБ, де зайнято лише 2 ГБ) вичитує гігабайти нулів і фізично виділяє дискові сектори на приймачі, повністю забиваючи носій.

Функція `copy_sparse_data` використовує системні розширення `lseek()`:
1. `lseek(src_fd, offset, SEEK_DATA)`: запитує в драйвера ФС зміщення найближчого блока, який реально містить дані на диску. Якщо даних попереду немає, ядро повертає помилку `ENXIO`, що свідчить про те, що вся решта файлу є суцільною діркою;
2. `lseek(src_fd, data_start, SEEK_HOLE)`: знаходить зміщення найближчої дірки (кінця блоку даних);
3. Покажчик запису приймача переміщується на початок даних: `lseek(dst_fd, data_start, SEEK_SET)`, пропускаючи нерозподілений простір без виконання системного виклику `write()`;
4. Діапазон між `data_start` та `hole_start` переноситься порціями буфера розміром 64 КБ (`COPY_BUF_SIZE`);
5. Після завершення обходу викликається `ftruncate(dst_fd, total_size)`: це гарантує, що якщо файл завершувався «висячою» діркою, його логічний розмір на приймачі точно відповідатиме оригіналу.

### 4. Реплікація розширених атрибутів (xattr) та POSIX ACL

Розширені атрибути зберігають пари «ім'я → бінарні дані» і розділені на простори імен:
- `user.*` — прикладні метадані (хеш-суми, мітки програм);
- `system.*` — системні структури ядра, насамперед POSIX ACL (`system.posix_acl_access`, `system.posix_acl_default`);
- `security.*` — мітки безпеки SELinux (`security.selinux`), файлові можливості двійкових файлів (`security.capability`).

Копіювання атрибутів здійснюється у два проходи:
1. `llistxattr(src_path, NULL, 0)`: виклик із нульовим буфером повертає розмір у байтах, необхідний для розміщення списку імен усіх наявних атрибутів;
2. Виділяється динамічний буфер, і викликом `llistxattr(src_path, list, list_len)` отримується список імен, розділених нульовими байтами (`\0`);
3. Алгоритм ітерується списком імен. Для кожного імені викликається `lgetxattr(src_path, attr_name, NULL, 0)` для визначення довжини бінарного значення, виділяється пам'ять, значення зчитується та записується на цільовий інод через `lsetxattr(dst_path, attr_name, val, val_len, 0)`.

Якщо цільова файлова система не підтримує xattr (наприклад, VFAT або змонтований застарілий NFS), виклики повертають `ENOTSUP` або `EOPNOTSUPP`. Клонувальник перехоплює ці коди як допустимі обмеження носія й продовжує роботу.

### 5. Встановлення власника та пастка `ATTR_KILL_SUID` / `ATTR_KILL_SGID`

Виклик `fchownat(AT_FDCWD, dst_path, stx.stx_uid, stx.stx_gid, AT_SYMLINK_NOFOLLOW)` призначає ідентифікатори власника (UID) та групи (GID).

> ⚠️ **Критичний зв'язок безпеки в ядрі Linux:**
> Коли системний виклик `chown` змінює власника файлу, підсистема VFS ядра (`fs/attr.c:notify_change()`) з міркувань безпеки **примусово очищує біти `S_ISUID` (04000) та `S_ISGID` (02000)** (внутрішні прапорці ядра `ATTR_KILL_SUID` / `ATTR_KILL_SGID`). Це запобігає атаці, коли звичайний користувач міг би призначити власником свого скомпільованого setuid-бінарника користувача `root` і отримати несанкціоноване підвищення привілеїв.
> 
> Через це системний виклик `fchmodat()` **зобов'язаний виконуватися суворо після `fchownat()`**. Якби відновлення прав доступу відбувалося перед зміною власника, ядро Linux безслідно стерло б біти SUID/SGID.

Якщо процес працює без привілею `CAP_CHOWN`, виклик `fchownat()` повертає `EPERM`. Утиліти зазвичай м'яко ігнорують цю помилку для звичайних користувачів, залишаючи файл у власності поточного процесу.

### 6. Відновлення маски прав доступу через `fchmodat`

Після фіксації власника викликається `fchmodat(AT_FDCWD, dst_path, stx.stx_mode & 07777, 0)`. Маска `07777` включає:
- 9 стандартних бітів доступу (`rwxrwxrwx`);
- Спеціальні біти SUID (`04000`), SGID (`02000`) та Sticky (`01000`).

Для символьних посилань виклик `fchmodat()` пропускається (`if (!S_ISLNK(type))`), оскільки в Linux спроба викликати `fchmodat` на symlink із прапорцем `AT_SYMLINK_NOFOLLOW` повертає помилку `EOPNOTSUPP`.

### 7. Фіксація наносекундних часових позначок через `utimensat`

Системний виклик `utimensat()` є **завершальним кроком** обробки файлу:

```
int utimensat(int dirfd, const char *pathname,
              const struct timespec times[2], int flags);
```

Кожна попередня операція — запис корисних даних (`write()`, `copy_file_range()`), зміна довжини (`ftruncate()`), встановлення xattr (`lsetxattr()`), зміна власника чи прав (`fchownat()`, `fchmodat()`) — змушує драйвер файлової системи негайно оновити час модифікації даних `mtime` та час зміни стану інода `ctime` до поточного значення системного таймера. Встановлення міток часу на будь-якому ранньому етапі було б миттєво перезаписане наступними системними викликами.

Масив `struct timespec times[2]` передає:
- `times[0]` — час останнього доступу `atime` (`stx_atime`);
- `times[1]` — час останньої модифікації вмісту `mtime` (`stx_mtime`).

Прапорець `AT_SYMLINK_NOFOLLOW` гарантує оновлення часових міток безпосередньо символьного посилання, а не об'єкта, на який воно вказує. Час зміни інода `ctime` не встановлюється напряму простором користувача — ядро виставляє його автоматично в момент виконання виклику `utimensat`.

## Збереження топології жорстких посилань (Hardlinks)

Жорстке посилання — це додатковий запис у таблиці каталогу, що посилається на вже наявний номер інода (`stx_ino`) на тому самому пристрої (`stx_dev_major:stx_dev_minor`). Якщо дерево містить файли з кількома жорсткими зв'язками (`stx_nlink > 1`), наївне копіювання призведе до створення окремих фізичних інодів, розриваючи зв'язок між ними та множачи зайняте місце на диску.

Для збереження топології клонувальник підтримує глобальну хеш-таблицю відповідності:

```
Хеш-ключ:   std::tuple<uint32_t /*dev_major*/, uint32_t /*dev_minor*/, uint64_t /*ino*/>
Значення:   std::string (шлях до вже створеного файлу-приймача)
```

Алгоритм обробки вузла:

```
[stx.stx_nlink > 1]
        │
        ▼
[Пошук ключа (dev, ino) у хеш-таблиці]
   ├── ЗНАЙДЕНО:
   │     │
   │     ▼
   │   [linkat(AT_FDCWD, target_path, AT_FDCWD, new_dst_path, 0)]
   │     │
   │     ▼
   │   [Завершити обробку вузла: дані та метадані вже створені]
   │
   └── НЕ ЗНАЙДЕНО:
         │
         ▼
       [Виконати повне клонування вузла: дані + метадані]
         │
         ▼
       [Зберегти (dev, ino) -> new_dst_path у таблицю]
```

Оскільки жорсткі посилання не можуть перетинати межі різних файлових систем (системний виклик `linkat()` повертає помилку `EXDEV`), збереження комбінації `(dev, ino)` є строго обов'язковим для уникнення колізій номерів інодів між різними точками монтування.

У багатопотоковому середовищі звернення до цієї таблиці вимагає синхронізації. Використання єдиного глобального м'ютекса стає вузьким місцем при високій паралельності, тому застосовується шардована хеш-таблиця (Striped Hash Table) із фіксованою кількістю сегментів (наприклад, 256 або 1024), де кожен кошик захищений власним легковажним спінлоком або `std::shared_mutex`.

## Постфіксний обхід каталогів (Post-Order Traversal Stack)

Особливою архітектурною задачею є обхід і створення каталогів. Якщо каталог створити й одразу застосувати до нього суворі вихідні права (наприклад, `0555` — тільки читання та виконання) та зафіксувати його часові мітки `mtime`:
1. Наступна спроба створити файл або підкаталог усередині нього зазнає невдачі з помилкою `EACCES` (відмовлено в доступі);
2. Створення нового елемента всередині каталогу модифікує сам каталог як таблицю імен, тому ядро автоматично оновить `mtime` каталогу до поточного часу, знищивши збережену мітку часу.

Щоб вирішити цю проблему, обхід дерева розбивається на дві фази за допомогою стека відкладеної фіксації каталогів:

```
Фаза 1: Спуск деревом (Префіксний етап)
  ├── Зустріли каталог:
  │     1. mkdirat(dst_path, 0700) [дозвіл на запис усім наступним дітям]
  │     2. Записати (dst_path, stx_mode, stx_uid, stx_gid, stx_atime, stx_mtime) у стек
  └── Зустріли файл / symlink / FIFO / device:
        Повне створення, перенесення даних, запис xattr, chown, chmod, utimensat

Фаза 2: Підйом деревом назад (Постфіксний етап — LIFO стек)
  └── Витягуємо каталоги від найглибших до кореневого:
        1. copy_xattrs(src_dir, dst_dir)
        2. fchownat(dst_dir, uid, gid)
        3. fchmodat(dst_dir, final_mode) [наприклад, 0555]
        4. utimensat(dst_dir, [atime, mtime]) [фіксація фінального часу каталогу]
```

Такий підхід гарантує, що жоден запис файлів не порушить часові позначки батьківських каталогів після їхньої фінальної фіксації.

## Паралельний обхід дерева: Work-Stealing черга та масштабування

Сучасні NVMe-накопичувачі демонструють продуктивність понад 1 000 000 IOPS при паралельному доступі. Проте класичний послідовний однопотоковий обхід дерева каталогів через `readdir()` та лінійний цикл копіювання утилізує менше 5% пропускної здатності шини PCIe. Масштабування клонування на багатоядерних процесорах вимагає паралельного планувальника завдань на базі черги крадіжки завдань (Work-Stealing Pool).

```
[Робочий потік 0]             [Робочий потік 1]             [Робочий потік N]
  ┌──────────────┐              ┌──────────────┐              ┌──────────────┐
  │ Локальна DEQ │              │ Локальна DEQ │              │ Локальна DEQ │
  ├──────────────┤              ├──────────────┤              ├──────────────┤
  │ Каталог /sub1│              │ Каталог /var │              │  (ПОРОЖНЬО)  │
  │ Каталог /sub2│              │ Каталог /etc │              │              │
  │ Файл data.bin│              │ Файл log.txt │              │              │
  └──────┬───────┘              └──────────────┘              └──────┬───────┘
         │ LIFO                                                      │
         ▼ (локальна робота)                                         │ КРАДІЖКА
   [Виконання вузла]                                                 │ (FIFO, top)
         │                                                           ▼
         └───────────────────────────────────────────────────► [Крадіжка /sub1]
```

### Архітектура черги Chase-Lev

Наївне створення окремого системного потоку `std::thread` на кожен підкаталог призводить до вичерпання дескрипторів потоків ОС (thread exhaustion) та деградації планувальника ядра через перемикання контекстів. Використання єдиної глобальної черги завдань із централізованим м'ютексом спричиняє жорстку конкуренцію за блокування (lock contention) при кількості потоків понад 8.

Оптимальним рішенням є неблокуюча черга крадіжки завдань (Chase-Lev Work-Stealing Deque):
1. Кожен робочий потік пулу володіє власною локальною двобічною чергою (deque);
2. **Локальний пуш та поп (LIFO):** під час вичитування каталогу знайдений підкаталог додається в кінець (bottom) власної черги потоку. Сам потік вибирає наступні завдання також з кінця своєї черги (LIFO, Last-In-First-Out). Це максимізує просторову та часову локальність кешу процесора (L1/L2 data cache): структури `dentry`, іноди та дескриптори щойно відкритого каталогу залишаються гарячими в кеші, а обхід іде в глибину (Depth-First Search);
3. **Крадіжка завдань (FIFO):** коли локальна черга потоку стає порожньою, він перетворюється на «злодія» (thief) і обирає випадковий потік-жертву. Крадіжка виконується з протилежного кінця черги (top) за принципом FIFO (First-In-First-Out). На вершині черги знаходяться найстаріші завдання — тобто підкаталоги найвищого рівня ієрархії. Захопивши одне велике кореневе піддерево, потік отримує самостійний обсяг роботи на тисячі файлів, мінімізуючи частоту повторних міжпотокових синхронізацій.

### Гібридний поділ навантаження: дрібні файли проти гігабайтних об'єктів

Структура файлового дерева неоднорідна: вона поєднує мільйони дрібних конфігураційних файлів (I/O metadata-bound) та одиничні гігабайтні архіви чи образи дисків (I/O bandwidth-bound).

Для збалансованого завантаження застосовується комбіноване планування:
- **Дрібні файли (< 64 МіБ):** обробляються безпосередньо в контексті потоку, що виконує сканування каталогу, або об'єднуються у пакетні мікрозавдання (batch tasks), усуваючи накладні витрати на атомарні операції черги;
- **Великі файли (≥ 64 МіБ):** щоб один потік не монополізував ядро на тривалий час, копіюючи 100 ГБ образ, файл розбивається на незалежні паралельні чанки (наприклад, по 64 МіБ). Окремі задачі чанків публікуються в чергу і виконуються різними потоками через паралельні позиційні системні виклики `copy_file_range(src_fd, &in_off, dst_fd, &out_off, chunk_len, 0)` або `pread()` / `pwrite()`.

### Асинхронна постфіксна фіксація через лічильники нащадків

У багатопотоковому середовищі класичний LIFO-стек постфіксного закриття каталогів стає непридатним, оскільки підкаталоги обробляються потоками асинхронно та завершуються в довільному порядку.

Фіксація реалізується через граф залежностей із атомарними лічильниками (Atomic Child-Counter):

```
         [Каталог A (pending=2)]
                │
        ┌───────┴───────┐
        ▼               ▼
   [Файл file1]   [Каталог B (pending=1)]
                        │
                        ▼
                  [Файл file2]
```

1. При створенні каталогу `mkdirat(dst, 0700)` створюється структура вузла з полем `std::atomic<uint32_t> pending_children`, де фіксується кількість прямих записів (файлів та підкаталогів), а також зберігається покажчик на батьківський каталог `parent`;
2. Кожен потік, завершивши копіювання файлу, виконує атомарне зменшення лічильника свого безпосереднього каталогу: `parent->pending_children.fetch_sub(1, std::memory_order_acq_rel)`;
3. Потік, чиє зменшення скинуло лічильник до нуля (`fetch_sub == 1`), є останнім активним обробником цього каталогу. Саме він ініціює фінальну постфіксну фазу каталогу: застосовує розширені атрибути `copy_xattrs()`, встановлює власника `fchownat()`, накладає фінальні права `fchmodat()` та фіксує часові мітки `utimensat()`;
4. Після завершення фіналізації каталогу потік рекурсивно декрементує `pending_children` батьківського каталогу рівнем вище. Фіксація піднімається вгору деревом природно й без блокувань.

## Динамічні стани гонитви живої файлової системи (Live Filesystem Races)

Копіювання активної робочої системи без попереднього створення апаратного чи файлового снапшота (LVM Snapshot, Btrfs/ZFS Subvolume Snapshot) піддає процес ризику станів гонитви (Race Conditions) та вразливостей TOCTOU (Time-of-Check to Time-of-Use).

```
   statx(path) ──────────────► [Зловмисник: unlink(path) + symlink("/etc/shadow", path)]
        │                                                     │
        ▼ (інтервал гонитви TOCTOU)                          │
   openat(dst, path, ...) ◄───────────────────────────────────┘
   [Безпекова катастрофа без O_NOFOLLOW: перезапис або витік /etc/shadow]
```

### 1. Атаки підміни на символьні посилання (Symlink Race Attack)

Якщо утиліта розділяє етап зчитування метаданих `statx(path)` та відкриття дескриптора `open(path)` через строкові шляхи, сторонній процес може замінити цільовий файл або один із проміжних компонентів шляху на символьне посилання між цими викликами.

Захист від TOCTOU на рівні ядра:
1. **Використання дескрипторів каталогів (`dirfd`):** обхід дерева виконується виключно через системні виклики родини `*at` (`openat`, `fstatat`, `mkdirat`), передаючи дескриптор відкритого батьківського каталогу замість конкатенації абсолютних рядкових шляхів;
2. **Обов'язковий прапорець `O_NOFOLLOW`:** виклик `openat(dirfd, filename, O_RDONLY | O_NOFOLLOW | O_CLOEXEC)` змушує ядро завершитися з помилкою `ELOOP`, якщо кінцевий елемент є символьним посиланням;
3. **Верифікація інода після відкриття:** після отримання дескриптора виконується `fstat(fd, &opened_st)` із перевіркою відповідності ідентифікаторів: `opened_st.st_dev == stx.stx_dev_major:minor` та `opened_st.st_ino == stx.stx_ino`. Якщо комбінація змінилася, файл було підмінено, і дескриптор негайно закривається.

### 2. Зміна розміру файлу на льоту (Truncate / Append)

Під час читання великого файлу активний сервіс (наприклад, демон ротації журналів або база даних) може модифікувати його обсяг:

- **Раптове обрізання (`truncate`):** цикл читання зустрічає несподіваний кінець файлу (`read()` повертає 0) раніше, ніж було прочитано початковий обсяг `stx_size`. Якщо цільовий файл створювався розрідженим або з попереднім виділенням блоків через `fallocate()`, невичитана хвостова частина залишиться заповненою нулями. Рушій клонування зобов'язаний виконати виклик `ftruncate(dst_fd, actual_bytes_written)`, щоб логічний розмір копії точно відповідав фактично отриманим даним на момент читання;
- **Паралельне дописування (`append`):** якщо файл зростає під час зчитування (активний лог), спроба читати до нескінченності призведе до створення копії, неузгодженої з початковими метаданими `stx_size`. Клонувальник обмежує читання обсягом `stx_size` або, якщо обрано режим повної синхронізації, після завершення I/O виконує повторний виклик `statx()`, оновлюючи фінальний розмір та мітки часу.

### 3. Зникнення або перейменування файлів (`ENOENT` / `ESTALE`)

Файл, повернений системним викликом `readdir()`, може бути видалений (`unlink`) або переміщений (`rename`) паралельним процесом до того, як потік клонувальника встигне виконати `statx()` або `openat()`.

У цьому випадку виклики повертають код помилки `ENOENT` (або `ESTALE` на мережевих файлових системах NFS). Промисловий рушій клонування не повинен переривати обхід усього дерева. Помилка класифікується як динамічна зміна стану (Vanished File, аналог коду завершення 24 в `rsync`), реєструється в журналі попереджень, і потік продовжує виконання наступних завдань черги.

### 4. Запобігання оновленню часу читання джерела через `O_NOATIME`

Стандартне відкриття файлу для читання змушує драйвер файлової системи джерела генерувати операцію запису для оновлення мітки `atime` (якщо розділ не змонтовано з опцією `noatime`). При копіюванні мільйонів файлів це створює колосальне паразитарне I/O-навантаження на накопичувач-джерело.

Для усунення цього ефекту файл відкривається з прапорцем `O_NOATIME`:
```
int src_fd = openat(dirfd, filename, O_RDONLY | O_NOFOLLOW | O_NOATIME | O_CLOEXEC);
```
Якщо процес не є власником файлу і не має адміністративної можливості `CAP_FOWNER`, ядро повертає помилку `EPERM`. Утиліта перехоплює цей код і автоматично повторює виклик `openat()` без прапорця `O_NOATIME`, забезпечуючи прозору роботу для непривілейованих користувачів.

## Порівняльний аналіз реалізацій C та C++

Обидва варіанти коду виконують однаковий набір низькорівневих системних викликів, проте демонструють суттєву різницю в підходах до управління ресурсами та обробки виняткових ситуацій:

1. **Управління ресурсами дескрипторів (RAII vs ручне закриття):**
   - У мові **C** дескриптори `src_fd` та `dst_fd` закриваються вручну на кожному шляху повернення або через структуру переходу `goto`. Пропуск виклику `close()` в одній із гілок обробки помилок призводить до витоку дескриптора (file descriptor exhaustion);
   - У мові **C++20** клас `ScopedFd` інкапсулює дескриптор за принципом RAII (Resource Acquisition Is Initialization). Конструктор переміщення `ScopedFd(ScopedFd&&)` та оператор переміщення передають володіння ресурсом, а деструктор гарантовано викликає `::close()` при розкрутці стека під час генерації будь-якого винятку;

2. **Обробка помилок та передача контексту:**
   - У **C** функції повертають числові коди `-1`, а деталі збою визначаються через глобальну змінну `errno`. Це вимагає ретельної перевірки кожного системного виклику на рівні окремих умовних операторів;
   - У **C++** застосовано стандартні винятки `std::system_error` у поєднанні з `std::generic_category()`. Виняток зберігає оригінальний код `errno` ядра Linux і супроводжується текстовим описом шляху, що спрощує діагностику та локалізацію аварій;

3. **Робота з динамічною пам'яттю під час вичитування xattr:**
   - У **C** двопрохідний виклик `llistxattr` вимагає ручного виділення пам'яті через `malloc()` та її гарантованого звільнення через `free()`. При розборі імен атрибутів використовується арифметика покажчиків;
   - У **C++** буфери для списків та значень атрибутів інкапсульовані в динамічні контейнери `std::vector<char>`, що автоматично звільняють пам'ять при виході з області видимості функції.

## Обробка крайових випадків уводу-виводу

Низькорівневе клонування у виробничих умовах стикається з типовими позаштатними ситуаціями підсистеми POSIX I/O:

- **Переривання системних викликів сигналами (`EINTR`):** виклики `read()`, `write()`, `copy_file_range()` можуть бути перервані надходженням асинхронного сигналу ядра (наприклад, `SIGWINCH` або `SIGALRM`) до завершення передачі блоку. Код зобов'язаний перевіряти `errno == EINTR` і продовжувати виконання циклу;
- **Неповний запис (Short Writes):** системний виклик `write()` не гарантує запис усього запитаного буфера за один крок (наприклад, через обмеження внутрішніх буферів сокетів/каналів або наближення до дискової квоти). Внутрішній цикл запису постійно зміщує покажчик `buffer + written` на величину фактично записаних байтів;
- **Переповнення носія (`ENOSPC`) та квоти (`EDQUOT`):** деструктори RAII-класів гарантують, що при викиданні винятку нестачі місця на диску всі відкриті файли будуть закриті, усуваючи блокування файлових систем.

## Діагностика та трасування системних викликів через `strace`

Працездатність утиліти та дотримання послідовності системних викликів можна перевірити за допомогою трасувальника `strace`:

```sh
# Збірка C++ версії з підтримкою стандарту C++20
g++ -std=c++20 -O2 proj-metadata-tree-cloner/cpp/main.cpp -o vfs_cloner

# Трасування послідовності викликів
strace -e trace=statx,openat,copy_file_range,lseek,llistxattr,lgetxattr,lsetxattr,fchownat,fchmodat,utimensat ./vfs_cloner /var/log/app.log /backup/app.log
```

У журналі `strace` спостерігається детермінована послідовність кроків:

```
statx(AT_FDCWD, "/var/log/app.log", AT_SYMLINK_NOFOLLOW, STATX_ALL, {stx_mask=STATX_ALL, stx_mode=S_IFREG|0640, stx_size=1048576, ...}) = 0
openat(AT_FDCWD, "/var/log/app.log", O_RDONLY|O_NOFOLLOW) = 3
openat(AT_FDCWD, "/backup/app.log", O_WRONLY|O_CREAT|O_TRUNC, 0600) = 4
copy_file_range(3, [0], 4, [0], 1048576, 0) = 1048576
close(3) = 0
close(4) = 0
llistxattr("/var/log/app.log", NULL, 0) = 32
llistxattr("/var/log/app.log", "security.selinux\0user.checksum\0", 32) = 32
lgetxattr("/var/log/app.log", "security.selinux", NULL, 0) = 37
lgetxattr("/var/log/app.log", "security.selinux", "system_u:object_r:var_log_t:s0", 37) = 37
lsetxattr("/backup/app.log", "security.selinux", "system_u:object_r:var_log_t:s0", 37, 0) = 0
fchownat(AT_FDCWD, "/backup/app.log", 1000, 1000, AT_SYMLINK_NOFOLLOW) = 0
fchmodat(AT_FDCWD, "/backup/app.log", 0640) = 0
utimensat(AT_FDCWD, "/backup/app.log", [{tv_sec=1724930000, tv_nsec=123456789}, {tv_sec=1724930500, tv_nsec=987654321}], AT_SYMLINK_NOFOLLOW) = 0
```

Цей вивід підтверджує: файл спочатку отримує захисний режим `0600`, потім дані миттєво шаряться через CoW `copy_file_range`, копіюються розширені атрибути SELinux, встановлюється власник, відновлюються права `0640`, і фінальним системним викликом `utimensat` наносекундні мітки часу фіксуються в індексному вузлі VFS.
