# ⚙️ Робоча функція: узяти n випадкових байтів і не збрехати

Потрібна одна функція — `get_secure_bytes(void *buf, size_t n)`, яка або кладе в буфер рівно n непередбачних байтів, або чесно каже «не вийшло»; чого вона не сміє робити ніколи — то це мовчки покласти передбачне. Питання «звідки брати» вже вирішене на користь `getrandom`, і складність не в ньому. Складність у тому, що цей виклик має чотири різні способи повернути не те, чого ви просили, і кожен із них колись обертався чиїмись однаковими ключами.

Перелічмо їх, бо саме з них виростає весь код.

**Коротке повернення.** Виклик повертає кількість покладених байтів, і вона може бути меншою за замовлену. Гарантія тут вужча, ніж здається: якщо генератор уже засіяно й запит не більший за 256 байтів, ядро віддає все й не перериває виклику сигналом. Для більшого буфера жодних обіцянок немає — сигнал ріже виклик посередині, і ви отримуєте частину.

**`EINTR`.** Поки генератор не засіяно, виклик спить. Сигнал будить його з цією помилкою, і байтів немає взагалі — навіть частини ([EINTR і перезапуск викликів](root:sys-unix/eintr-and-restart)).

**`ENOSYS`.** Виклику немає: ядро старіше за 3.17 (жовтень 2014). Той самий код віддає й фільтр [seccomp](root:sys-unix/seccomp-filter-mechanism), який вирізав виклик у пісочниці, — а вирізають його частіше, ніж хотілося б.

**`EAGAIN`** — лише тоді, коли ви самі попросили не чекати.

## Ідея

Два правила, і код — прямий їх наслідок. Перше: часткове ніколи не рахувати за повне — звідси цикл, який рахує вже покладені байти. Друге: запасний шлях мусить бути готовий **до** тієї миті, коли він знадобиться, — звідси дескриптор `/dev/urandom`, відкритий на старті програми, а не тоді, коли `getrandom` уперше відмовив.

## Старт: підготувати запасний шлях

```c
#define _GNU_SOURCE
#include <sys/random.h>
#include <sys/stat.h>
#include <sys/sysmacros.h>
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <string.h>
#include <stdint.h>

static int urandom_fd = -1;

/* Викликати РІВНО один раз, найпершою дією в main() — до chroot,
   до зниження прав, до створення потоків. 0 — запасний шлях готовий. */
int random_init(void)
{
    int fd = open("/dev/urandom", O_RDONLY | O_CLOEXEC | O_NOCTTY);
    if (fd < 0)
        return -1;

    struct stat st;
    if (fstat(fd, &st) < 0) {
        close(fd);
        return -1;
    }

    /* Мусить бути символьний пристрій 1:9, а не підкладений файл. */
    if (!S_ISCHR(st.st_mode) ||
        major(st.st_rdev) != 1 || minor(st.st_rdev) != 9) {
        close(fd);
        errno = ENODEV;
        return -1;
    }

    urandom_fd = fd;
    return 0;
}
```

Тепер про кожне рішення в цих двадцяти рядках, бо жодне з них не косметичне.

**Чому на старті, а не в мить потреби.** Відкриття файлу — дія, яка вміє не вдатися, і невдача приходить саме тоді, коли найгірше. Процес, що вичерпав [ліміт відкритих дескрипторів](root:sys-unix/resource-limits), не відкриє нічого — а бібліотеці шифрування ключ потрібен саме зараз. У [chroot](root:sys-unix/chroot) чи в мінімальному образі контейнера теки `/dev` часто просто немає, і шлях не вирішиться. Відкривши дескриптор першою дією, ви переносите всі ці невдачі в один контрольований момент: програма падає на старті з виразною скаргою, а не тихо ламається на середині роботи. Сам дескриптор після цього переживає і `chroot`, і зниження прав, бо він посилається не на ім'я, а на вже відкритий пристрій ([відкритий файловий опис](root:sys-unix/open-file-description)).

**Чому `fstat`.** Ім'я `/dev/urandom` нічого не гарантує. У підготованому кимось кореневому дереві за цим іменем може лежати звичайний файл із наперед відомим вмістом — і читання з нього виглядатиме бездоганно успішним. Перевірка звіряє те, що ви справді відкрили: символьний пристрій зі старшим номером 1 і молодшим 9 ([старший і молодший номери](root:sys-unix/major-minor-numbers)). Перевіряти треба `fstat` на вже відкритому дескрипторі, а не `stat` на шляху: між двома викликами шлях можна підмінити, дескриптор — ні.

> 🔧 **Навіщо це.** Ці п'ять рядків перетворюють найтихішу з можливих катастроф — програму, що роками роздає «випадкові» ключі з підкладеного файлу, — на гучну відмову за півсекунди до першого корисного рядка в журналі. Ціна перевірки: один системний виклик за весь час життя процесу.

`O_CLOEXEC` тримає дескриптор при собі: без нього він протече в кожен породжений процес, а кількість дескрипторів у чужих процесах — рівно те, чого ви не контролюєте. `O_NOCTTY` знешкоджує окремий випадок підміни, коли за іменем ховається термінал.

## Робота: цикл із запасним шляхом

```c
int get_secure_bytes(void *buf, size_t n)
{
    uint8_t *p = buf;
    size_t got = 0;

    while (got < n) {
        ssize_t r = getrandom(p + got, n - got, 0);
        if (r > 0)  { got += (size_t)r; continue; }
        if (r == 0) { errno = EIO; goto fail; }   /* не буває, але цикл мусить кінчатися */
        if (errno == EINTR)  continue;            /* сигнал під час очікування */
        if (errno == ENOSYS || errno == EPERM) break;  /* виклику немає — далі запасним */
        goto fail;                                /* EFAULT і подібне — помилка в нас */
    }
    if (got == n)
        return 0;

    if (urandom_fd < 0) { errno = ENOSYS; goto fail; }

    while (got < n) {
        ssize_t r = read(urandom_fd, p + got, n - got);
        if (r > 0)  { got += (size_t)r; continue; }
        if (r == 0) { errno = EIO; goto fail; }   /* кінця в /dev/urandom не буває */
        if (errno == EINTR) continue;
        goto fail;
    }
    return 0;

fail: {
        int saved = errno;
        explicit_bzero(buf, n);   /* напівзаповнений буфер не сміє піти в діло */
        errno = saved;
        return -1;
    }
}
```

Прапорців у виклику немає — і це найважливіше рішення в усій функції. Порожній набір означає «зачекай, поки генератор буде готовий, а після того не чекай ніколи»: рівно те, чого хоче програма, якій потрібен ключ. На системі, що працює хоч секунду, цей виклик не спить взагалі.

`explicit_bzero` на шляху відмови — не педантизм. Звичайний `memset` перед `return` компілятор має право викинути як запис у пам'ять, якої більше ніхто не читає; `explicit_bzero` (glibc 2.25 і новіші) існує саме для того, щоб такого права не було. Викликач, отримавши −1, не має заглядати в буфер — але половина відмов у безпеці й починається з того, що хтось таки заглянув.

Якщо ваша libc старіша за glibc 2.25 і обгортки `getrandom` не має, її роль виконує рядок `syscall(SYS_getrandom, buf, len, flags)` з `<sys/syscall.h>` — далі код той самий.

Дескриптор після `random_init` тільки читають, тож замка тут не потрібно: `/dev/urandom` не має позиції, і паралельні читання з різних потоків не заважають одне одному.

## Дві діри в тому вузькому проміжку

Прапорці `getrandom` міняють поведінку лише до першого засівання генератора — і побачити їхню різницю можна тільки там.

```c
uint8_t b[16];

/* 1. Не чекати. До готовності — EAGAIN, байтів немає. */
if (getrandom(b, sizeof b, GRND_NONBLOCK) < 0 && errno == EAGAIN)
    /* роботу ВІДКЛАСТИ; не підміняти чимось із time() */;

/* 2. Не чекати й узяти що є. Завжди 16 байтів, до готовності — передбачних. */
getrandom(b, sizeof b, GRND_INSECURE);
```

`GRND_NONBLOCK` потрібен там, де заснути не можна конструктивно: у циклі обробки подій, у ранньому коді першого процесу системи, у сторожовій службі, яка мусить відповідати. `EAGAIN` тут читається як «ще ні», а не «ніколи», і єдина правильна відповідь на нього — відкласти саму роботу. Підмінити відсутню випадковість поточним часом означає перетворити чесну затримку на тихий злам.

`GRND_INSECURE` (з ядра 5.6) розв'язує зворотну задачу: байти потрібні негайно, а передбачність байдужа. Заповнити внутрішні структури на старті, розкидати спроби повтору в часі, дати суфікс тимчасовому файлу — для цього чекати на засівання безглуздо. Назва каже все: у ключі ці байти не йдуть. Разом із `GRND_RANDOM` цей прапорець не поєднується — вимоги протилежні, і ядро відповідає `EINVAL`.

Дрібниця, на якій легко згаяти вечір: на робочій системі всі три варіанти поводяться однаково. Щоб побачити різницю, програму треба запустити в перші секунди після завантаження — з initramfs або як одну з найперших служб.

## Скільки це коштує і що змінив vDSO

Кожне звертання по байти — це перехід у ядро з усією його ціною ([механіка системного виклику](root:sys-unix/syscall-mechanics)). У Linux 6.11 (2024) код `getrandom` поклали у [vDSO](root:sys-unix/vdso), і для програми це означає, що байти можуть народжуватися просто в її адресному просторі, без переходу взагалі.

Різницю видно тим самим кодом, якщо порівняти дві форми виклику:

```c
#include <sys/syscall.h>
#include <sys/random.h>
#include <unistd.h>
#include <time.h>
#include <stdio.h>
#include <stdint.h>

static double now_ns(void)
{
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec * 1e9 + t.tv_nsec;
}

static ssize_t raw_getrandom(void *b, size_t n, unsigned f)
{
    return syscall(SYS_getrandom, b, n, f);   /* завжди справжній виклик */
}

int main(void)
{
    enum { N = 1000000 };
    uint8_t key[32];

    double t0 = now_ns();
    for (long i = 0; i < N; i++) getrandom(key, sizeof key, 0);
    double t1 = now_ns();
    for (long i = 0; i < N; i++) raw_getrandom(key, sizeof key, 0);
    double t2 = now_ns();

    printf("libc: %.1f нс   виклик: %.1f нс\n",
           (t1 - t0) / N, (t2 - t1) / N);
    return 0;
}
```

Що саме ви поміряєте, залежить від пари «ядро + libc». Швидкий шлях вмикається, коли ядро не старіше за 6.11, а бібліотека вміє його знайти — у glibc це вміння з'явилося у версії 2.41. Не збіглося щось одне — обидва рядки покажуть однакове число, і це вже корисна відповідь.

Числа наводити не буду навмисне: вони помітно різняться між процесорами й особливо між наборами ввімкнених пом'якшень спекулятивних атак, які дорожчають саме вхід у ядро. Важлива не цифра, а те, з чого вона складається. У повільній формі час майже цілком іде на перехід туди й назад, і від розміру запиту він майже не залежить. У швидкій переходу немає взагалі: витрачається кілька блоків потокового шифру просто в пам'яті процесу, тож ціна росте з кількістю байтів, а не з кількістю звертань. Порядок різниці на дрібних запитах — десятковий.

## Пастка, заради якої це все

Побачивши ціну переходу, програміст першою думкою хоче кеш: узяти чотири кілобайти за один раз і роздавати з буфера. Логіка бездоганна, наслідок — катастрофа, і саме на ній ловилися серйозні бібліотеки.

Ламає її [fork](root:sys-unix/fork-semantics). Нащадок дістає копію пам'яті батька — разом із буфером і разом із позицією в ньому. Далі обидва процеси роздають **ті самі байти**: два з'єднання з однаковим ключем, дві сесії з однаковим маркером. Помилки в коді немає жодної, тестами вона не ловиться, і виявляють її зазвичай сторонні люди.

Латка існує: буфер можна тримати в окремому [відображенні пам'яті](root:sys-unix/mmap-model), поміченому `MADV_WIPEONFORK` (з ядра 4.14). Тоді нащадок бачить на цьому місці нулі, програма впізнає їх за міткою й заводить кеш наново. Через `pthread_atfork` те саме зробити не вдасться надійно — обробники минають того, хто створює процес прямим викликом `clone`.

Але й це не рятує від другої пастки. Знімок віртуальної машини, розгорнутий двічі, роздвоює процес без жодного `fork` — пам'ять просто триває далі в двох машинах, і жодне відображення про це не дізнається. Ядро тут має те, чого ваша програма не має: гіпервізор повідомляє йому про клонування, ядро перезаряджає генератор, підвищує номер покоління, і примірники стану в просторі користувача самі бачать, що застаріли. Ваш кеш такого сигналу не отримує ніколи.

Звідси й висновок про кеш: він потрібен, він уже написаний і він у вас уже є. Швидкий шлях крізь vDSO — це рівно той самий кеш, тільки в пам'яті, яку ядро зобов'язалося обнулити і при `fork`, і при клонуванні машини, з розгортанням ключа, що не лишає слідів позаду ([швидке стирання ключа](root:sf-security/csprng/proj-fast-key-erasure.md)). Свій кеш поверх цього додає рівно нуль швидкості на новому ядрі — і дві пастки на будь-якому.

Остання пастка — найпоширеніша й найдешевша на вигляд: `if (get_secure_bytes(...) < 0) srand(time(NULL));`. М'якої деградації в цій функції немає й бути не може. Відсутність випадковості — привід зупинитися з гучною скаргою, а не привід узяти те, що вгадується з півсекунди.

## Коли коротше можна

Якщо байтів треба не більше за 256 — а ключ, сіль чи маркер сесії в цю межу вкладаються завжди, — весь цикл згортається в один виклик `getentropy(buf, n)`. Він частин не повертає, `EINTR` не віддає й прапорців не має; більше за 256 просить — дістає `EIO`. Обгортка з glibc 2.25.

А якщо libc не старіша за glibc 2.36, є ще коротший шлях: `arc4random_buf(buf, n)` віддає байти від ядра, сам ходить крізь `getrandom` із поверненням на `/dev/urandom` і сам розбирається з усім переліченим ([libc як брама до ядра](root:sys-unix/libc-as-gateway)). Функція з початку цієї статті потрібна тим, чий код мусить працювати й там, де таких зручностей немає, — але знати, що на свіжій системі це один рядок, варто заздалегідь.
