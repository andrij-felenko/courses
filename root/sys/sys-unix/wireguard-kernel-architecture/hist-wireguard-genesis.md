# 📜 Генезис WireGuard: революція мінімалізму проти монстрів IPsec та OpenVPN

Історія створення тунельних мережевих протоколів у системному програмуванні наочно демонструє, як намагання створити універсальний інструмент на всі випадки життя перетворює програмне забезпечення на громіздкий та небезпечний моноліт. Усі VPN-рішення (від англ. *Virtual Private Network*), що існували в екосистемі Unix та Linux до 2016 року, потерпали від фундаментального компромісу: вони або жертвували продуктивністю заради безпечної обробки трафіку у просторі користувача, або розплачувалися колосальною архітектурною складністю та фатальним роздуттям бази коду в ядрі операційної системи.

## 1. Епоха OpenVPN та глухий кут віртуальних пристроїв TUN/TAP

Проєкт OpenVPN, започаткований інженером Джеймсом Йонаном у 2001 році, пішов шляхом ізоляції прикладного коду від критичних підсистем ядра. Для передачі пакетів використовувався універсальний драйвер віртуальних мережевих пристроїв `TUN` (для L3-пакетів IP) та `TAP` (для L2-кадрів Ethernet). Архітектура казалась ідеальною з точки зору безпеки розмежування привілеїв: криптографічна обробка, обмін ключами через OpenSSL, аутентифікація користувачів та парсинг складних конфігураційних файлів виконувалися в окремому демонічному процесі у просторі користувача (User Space).

Проте за цю ізоляцію довелося розплачуватися важким системним оверхедом. Передача кожного мережевого пакета через віртуальний символьний пристрій `/dev/net/tun` вимагала виконання довгої послідовності системних операцій:

1. Мережевий пакет `sk_buff`, надісланий прикладним застосунком, потрапляв у драйвер `TUN` всередині ядра.
2. Драйвер побудував чергу даних і розбуджував демон OpenVPN, який перебував у стані очікування системного виклику `read()` або `select()`.
3. Операційна система виконувала контекстне перемикання (User-to-Kernel) та копіювала байтовий масив пакета з оперативної пам'яті ядра у буфер простору користувача.
4. Демон OpenVPN виконував шифрування за допомогою бібліотеки OpenSSL, додавав власні заголовки та надсилав зашифровану дейтаграму назад у ядро за допомогою системного виклику `write()` або `sendmsg()`.
5. Ядро знову виконувало контекстне перемикання (Kernel-to-User) і копіювало дані у звичайний сокет UDP для відправки через фізичний мережевий адаптер.

На кожен тунельований пакет припадало щонайменше чотири контекстні перемикання процесора та дві повноцінні операції копіювання пам'яті крізь межу системних викликів. На гігабітних мережевих каналах це призводило до колосального навантаження на процесор (CPU contention), постійного скидання кешів інструкцій L1/L2 та різкого падіння пропускної здатності тунелю до 100–300 Мбіт/с навіть на потужних серверних платформах.

## 2. IPsec та підсистема XFRM: пастка гнучкості та криптографічної агрегації

Для подолання проблем із продуктивністю у 2002 році в ядро Linux 2.6 було інтегровано підсистему XFRM (від англ. *transform*), яка забезпечувала апаратну обробку протоколу IPsec безпосередньо у внутрішніх чергах ядра. Завдяки відсутності копіювання даних через `TUN/TAP` IPsec демонстрував високу швидкість обробки пакетів.

Однак IPsec створювався у середині 1990-х років комітетом IETF у рамках концепції "crypto agility" — підтримки максимальної кількості комбінацій криптографічних алгоритмів, шифрів, режимів аутентифікації та варіантів інкапсуляції. IPsec включав у себе два окремі транспорти (AH та ESP), два режими роботи (транспортний та тунельний), сотні алгоритмів шифрування (DES, 3DES, AES-CBC, AES-GCM, Blowfish, Camellia) та надскладний протокол встановлення ключів IKE (IKEv1 та IKEv2).

Ця гнучкість мала катастрофічні наслідки для архітектури ядра:

- Для роботи IPsec у ядрі довелося створити Базу політик безпеки (SPD) та Базу станів безпеки (SAD). Для кожного пакета ядро повинно було виконувати складний пошук по таблицях політик, порівнюючи селектори (IP-адреси, порти, протоколи).
- Оскільки підсистема ядра XFRM не вміла самостійно домовлятися про ключі, у просторі користувача обов'язково повинен був функціонувати важкий демон обміну ключами (наприклад, `strongSwan`, `Pluto` або `racoon`). Демон спілкувався з ядром через специфічний сокет `NETLINK_XFRM`, динамічно додаючи та видаляючи стани безпеки.
- Обсяг коду підсистеми XFRM у ядрі Linux разом із демонами обміну ключами перевищував 100 000 рядків коду на мові C.

Наявність сотен варіантів конфігурації відкривала величезний простір для атак на пониження версії алгоритмів (downgrade attacks), таких як Logjam, FREAK або DROWN. Жодна організація у світі не могла дозволити собі проведення повноцінного аудиту безпеки 100 000 рядків коду IPsec.

## 3. Поява WireGuard та філософія Джейсона Доненфельда

У 2016 році інженер і дослідник у галузі інформаційної безпеки Джейсон Доненфельд (Jason A. Donenfeld) представив проєкт WireGuard, який кардинально змінив погляди системних програмістів на побудову мережевих тунелів.

Доненфельд сформулював концепцію, згідно з якою криптографічний протокол не повинен надавати користувачеві вибір шифрів. Можливість вибору створює підґрунтя для помилок конфігурації та роздуває кодову базу за рахунок непотрібних абстракцій. Замість "crypto agility" WireGuard упровадив концепцію фіксованого криптографічного набору (Fixed Cryptographic Suite):

- **Curve25519:** асиметрична криптографія на еліптичних кривих для обміну ключами (ECDH).
- **ChaCha20:** симетричний потоковий шифр, що забезпечує однаково високу швидкість обробки як на потужних процесорах x86_64, так і на недорогих ARM-мікроконтролерах без апаратної підтримки AES-NI.
- **Poly1305:** код автентифікації повідомлень (MAC) для створення блоків AEAD.
- **BLAKE2s:** надшвидка криптографічна хеш-функція, що працює швидше за SHA-3.
- **SipHash24:** спеціалізована хеш-функція для захисту внутрішніх хеш-таблиць від DoS-атак методом колозій.

Головним архітектурним відкриттям Доненфельда став механізм Cryptokey Routing (криптографічна маршрутизація). Він прибрав розрив між маршрутизацією та шифруванням, прив'язавши публічні ключі безпосередньо до IP-адрес у префіксному дереві. Завдяки цьому WireGuard став повністю "stateless" з точки зору користувача: тунельний інтерфейс поводиться як звичайний Ethernet-кабель, який завжди увімкнений і не потребує процедур встановлення чи розриву з'єднання.

Початкова реалізація WireGuard у ядрі складалася всього з близько 4 000 рядків коду на мові C. Для порівняння:
- OpenVPN + OpenSSL: понад 600 000 рядків коду.
- IPsec (XFRM + strongSwan): понад 100 000 рядків коду у ядрі та півмільйона в демоні.
- WireGuard: ~4 000 рядків коду у ядрі.

Таку базу коду один кваліфікований спеціаліст з безпеки може повністю вивчити та перевірити за один-два дні.

## 4. Шлях до ядра Linux та визнання спільноти

У 2018 році творець операційної системи Linux Лінус Торвальдс (Linus Torvalds) публічно прокоментував вихід WireGuard у поштовій розсилці LKML (Linux Kernel Mailing List):

> *"Чи можу я знову висловити свою любов до WireGuard та сподівання, що він незабаром буде злитий у ядро? Код може бути не ідеальним, але порівняно з жахіттям IPsec та OpenVPN це справжній витвір мистецтва."*

Проте інтеграція в офіційне ядро виявилася непростою. Початково Доненфельд створив власну криптографічну бібліотеку Zinc для швидкого обчислення ChaCha20-Poly1305 у ядрі. Це викликало тривалу дискусію з розробниками підсистеми Crypto API ядра Linux (зокрема з Гербертом Сюеном та Дейвом Міллером). Зрештою було досягнуто компромісу: підсистему Crypto API ядра було частково рефакторизовано для забезпечення низькозатримного виклику шифрів без зайвих алокацій пам'яті.

У березні 2020 року відбувся офіційний реліз ядра **Linux 5.6**, у якому WireGuard став офіційним внутрішньоядерним модулем `drivers/net/wireguard/`. Сьогодні WireGuard є стандартом де-факто для побудови корпоративних мереж, мобільних VPN-клієнтів та захищених тунелів між дата-центрами.
