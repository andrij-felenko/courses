# ⚙️ Двофазне скидання привілеїв у демонах: алгоритм та безпечний код

При виконанні мережевих демонів та системних служб поширеним патерном є початкова ініціалізація від імені `root` (для відкриття привілейованих портів `< 1024`, читання конфігурацій та відкриття приватних ключів TLS з `/etc/ssl/private`), після чого процес мусить остаточно та незворотно відмовитися від усіх системних привілеїв перед обробкою вхідних мережевих запитів.

Неправильна послідовність скидання привілеїв є однією з найгостріших класичних уразливостей Unix-систем: якщо розробник викликає `setuid()` **до** `setgid()` або забуває про очищення додаткових груп (`setgroups`), процес втрачає привілеї користувача `root`, але зберігає привілейовані групи (наприклад, `shadow`, `disk` чи `wheel`), що створює прямий вектор для несанкціонованого підняття привілеїв.

## Алгоритм безпечного остаточного скидання привілеїв

Схема фаз виконання та перевірок описує послідовний перехід стану процесу під час відмови від прав:

```
+-------------------------------------------------------+
|  Фаза 1: Привілейований стан (root, euid=0, egid=0)  |
|  - Відкриття сокета (port 443), читання TLS-ключів   |
+---------------------------+---------------------------+
                            |
                            v
+-------------------------------------------------------+
|  Фаза 2: Очищення та завантаження додаткових груп     |
|  - initgroups("nobody", nobody_gid) або setgroups(0)  |
+---------------------------+---------------------------+
                            |
                            v
+-------------------------------------------------------+
|  Фаза 3: Остаточна зміна GID                           |
|  - setresgid(gid, gid, gid)                           |
+---------------------------+---------------------------+
                            |
                            v
+-------------------------------------------------------+
|  Фаза 4: Остаточна зміна UID                           |
|  - setresuid(uid, uid, uid)                           |
+---------------------------+---------------------------+
                            |
                            v
+-------------------------------------------------------+
|  Фаза 5: Захист пам'яті та перевірка закриття дверей  |
|  - seteuid(0) -> EPERM (перевірка неможливості root)   |
|  - prctl(PR_SET_DUMPABLE, 0) (захист від core dump)   |
+-------------------------------------------------------+
```

З цієї схеми фаз виводиться суворий п'ятикроковий алгоритм дій для повного позбавлення процесу системних привілеїв:

1. **Ініціалізація додаткових груп цільового користувача** через `initgroups()` або їх повне очищення через `setgroups(0, NULL)`. Якщо демон запускається для конкретного користувача (наприклад, `nobody` чи `nginx`), `initgroups()` завантажує всі групи з `/etc/group`, до яких входить цей користувач.
2. **Скидання ідентифікаторів груп** через `setresgid(target_gid, target_gid, target_gid)` або `setgid(target_gid)`. Зміна GID виконується **обов'язково до** зміни UID: зміна GID вимагає `CAP_SETGID`, а скидання UID на ненульове значення стирає ефективні привілеї процесу — після нього `setgid()` уже поверне `EPERM`.
3. **Скидання ідентифікаторів користувача** через `setresuid(target_uid, target_uid, target_uid)` або `setuid(target_uid)`. Після цього виклику процес втрачає привілей `CAP_SETUID` та можливість будь-яких подальших змін груп чи користувачів.
4. **Верифікація неможливості повернення привілеїв** через спробу виклику `seteuid(0)` — вона обов'язково мусить завершитися помилкою `EPERM`.
5. **Налаштування прапорця дампу пам'яті (`PR_SET_DUMPABLE`)**, щоб запобігти зняттю core dump непривілейованим користувачем, якщо в пам'яті процесу залишилися конфіденційні ключі або password-хеші.

## Глибокий аналіз безпекових пасток та крайніх випадків

### 1. Пастка порядку викликів: `setuid` перед `setgid`

Найпоширеніша катастрофічна помилка в C/C++ програмах — виконання `setuid()` до виклику `setgid()` або `initgroups()`:

Спроба виконати `setuid(1000)` спочатку призводить до того, що процес миттєво стає непривілейованим і втрачає привілей `CAP_SETGID`. Наступна спроба викликати `setgid(1000)` зазнає невдачі з помилкою `EPERM`. Якщо програма не перевіряє код повернення `setgid()`, вона продовжує виконання з ефективним `egid = 0` (група `root`), що дає доступ до всіх файлів, відкритих для групи `root`.

Коректна послідовність вимагає очищення та налаштування додаткових груп через `initgroups()` або `setgroups()`, після чого змінюється GID, і лише в самому кінці змінюється UID.

### 2. Атака через вичерпання `RLIMIT_NPROC`

Системні виклики `setuid()` та `setresuid()` перевіряють ліміт кількості процесів `RLIMIT_NPROC` для цільового користувача. 

Якщо зловмисник у системі заздалегідь запускає тисячі процесів від імені користувача `nobody` (досягаючи стелі `NPROC`), а після цього привілейований демон намагається скинути свої привілеї до того самого користувача `nobody`, системний виклик `setresuid()` повертає помилку `EAGAIN` і **взагалі не змінює UID**. 

Якщо демон ігнорує повернену помилку та продовжує обробляти мережевий сокет, він обробляє запити атакера з повними привілеями `root`. Саме тому сувора перевірка повертаного значення `setresuid()` є обов'язковою вимогою безпеки.

### 3. Проблема додаткових груп (Supplementary Groups)

Виклики `setuid()` та `setgid()` змінюють лише основні ідентифікатори процесу, але залишають недоторканим масив додаткових груп (Supplementary Groups). Якщо демон був запущений із доданою групою `disk` чи `docker`, після виклику `setuid(1000)` процес отримує UID 1000, але залишається членом групи `disk`, зберігаючи прямий доступ до сирого читання блокових пристроїв `/dev/sda`.

Обов'язковим рішенням є виклик `initgroups(username, gid)` або `setgroups(0, NULL)` перед будь-якою зміною UID.

### 4. Дамп пам'яті (Core Dump) та витік секретів

Коли процес запускається від імені `root`, читає приватний ключ RSA/ED25519 з `/etc/ssl/private`, а потім скидає привілеї до користувача `nobody`, ці приватні ключі залишаються у віртуальній пам'яті процесу.

Якщо звичайний користувач `nobody` надішле процесу сигнал `SIGSEGV` або `SIGABRT`, ядро за певних налаштувань створить дамп пам'яті (core dump) туди, куди вказує `kernel.core_pattern` — у робочий каталог процесу або в обробник на кшталт `systemd-coredump`. Сама зміна креденшелів скидає прапорець `dumpable`, тож типово дамп такого процесу не створюється; але `fs.suid_dumpable = 1` знімає цей захист, а програма може ввімкнути `dumpable` назад заради відлагодження — і тоді непривілейований користувач отримує приватні ключі `root`.

Виклик `prctl(PR_SET_DUMPABLE, 0, 0, 0, 0)` або `setrlimit(RLIMIT_CORE, &zero)` забороняє ядру створювати core dump для даного процесу, закриваючи цей вектор витоку даних.

### 5. Аудит та перевірка стану через sysfs та procfs

Для перевірки результату виконання алгоритму скидання привілеїв у середовищі розробки використовується інспекція системного файлу `/proc/[pid]/status`. У цьому файлі рядки `Uid:` та `Gid:` відображають усі чотири ідентифікатори: Real, Effective, Saved, та Filesystem.

Після успішного незворотного скидання привілеїв усі чотири числа в рядку `Uid:` мусять бути однаковими (наприклад, `1000 1000 1000 1000`). Наявність `0` у третьому стовпчику (`suid`) свідчить про те, що процес зберігає збережену копію привілеїв і спроможний відновити права `root` викликом `seteuid(0)`.

Додатково перевіряється прапорець `Dumpable:` у файлі `/proc/[pid]/status`. Значення `Dumpable: 0` гарантує, що процес захищений від витоку пам'яті через аварійні дампи та недоступний для приєднання відлагоджувачів без наявності глобального `CAP_SYS_PTRACE`.
