Коли системний адміністратор у середині 1990-х років відкривав віддалену консоль через протоколи Telnet або BSD Rlogin, кожен байт введення — ім'я користувача, пароль облікового запису та команди керування системою — пакувався в незашифровані TCP-сегменти та передавався локальною чи глобальною мережею відкритим текстом. Будь-який проміжний маршрутизатор або зловмисник із пасивним аналізатором мережевого трафіку (`tcpdump`, `snoop`) у спільному сегменті Ethernet перехоплював облікові дані в момент їхнього введення. Ба більше, протокол TCP не містить вбудованих механізмів автентифікації джерела окремих пакетів, що дозволяло зловмиснику виконувати активну атаку підміни сеансу (TCP session hijacking): перехопити порядкові номери TCP (sequence numbers), примусово скинути легітимний клієнтський зв'язок пакетом RST і відправляти довільні команди на виконання від імені вже автентифікованого адміністратора.

Для усунення цих фундаментальних вразливостей фінський дослідник Тату Ільонен у 1995 році розробив першу версію протоколу Secure Shell (SSH-1). Проте перша версія протоколу страждала на серйозні недоліки архітектури: монолітну структуру без чіткого розмежування обов'язків, слабкий контроль цілісності (вразливість атаки вставки CRC32, яка дозволяла непомітно модифікувати зашифрований потік) та неможливість безпечного переузгодження ключів без розриву з'єднання. Консорціум IETF повністю переглянув концепцію захищеного віддаленого доступу, затвердивши у 2006 році стандарт **SSH-2** у серії документів RFC 4251–4254. 

Головний інженерний принцип SSH-2 полягає в тому, що протокол відмовляється від монолітності та розбивається на три суворо ізольовані рівні абстракції. Крім того, протокол забороняє клієнту розкривати будь-які секретні дані автентифікації користувача (паролі чи цифрові підписи) доти, доки віддалений сервер криптографічно не доведе свою справжність і не буде створено надійно зашифрований, захищений від підміни та модифікацій транспортний тунель.

## Трирівнева архітектура протоколу SSH-2

Протокол SSH-2 побудований за модульним принципом, де кожен наступний рівень спирається на гарантії безпеки та функціонал попереднього.

![Трирівнева архітектура протоколу SSH-2](/root/sys/sys-unix/ssh-remote-session/img/ssh-layer-stack.svg)
*Трирівнева архітектура протоколу SSH-2: відокремлення транспорту, автентифікації користувача та мультиплексованого канального рівня.*

### 1. Транспортний рівень (Transport Layer, RFC 4253)

Транспортний рівень розгортається поверх єдиного двостороннього надійного потоку байтів (зазвичай це TCP-з'єднання на стандартний порт 22/tcp). Його завдання — узгодити криптографічні алгоритми, виконати безпечний обмін ключами, перевірити автентичність віддаленого хоста, увімкнути симетричне шифрування й автентифікацію повідомлень, а також забезпечити захист від повторного відтворення (replay attacks).

#### Двійковий пакетний протокол (Binary Packet Protocol, BPP)
Усі дані на транспортному рівні структуруються у двійкові пакети єдиного формату:
1. `packet_length` (uint32, 4 байти) — довжина пакета в байтах без урахування самого поля довжини та поля MAC.
2. `padding_length` (byte, 1 байт) — довжина випадкового вирівнювального заповнення (від 4 до 255 байтів).
3. `payload` (корисне навантаження) — службове повідомлення SSH або прикладні дані.
4. `random padding` — випадкові байти для вирівнювання загального розміру пакета до кратності розміру блоку шифру (зазвичай 8 або 16 байтів) або для приховування точного розміру переданих даних від атак на основі аналізу трафіку.
5. `MAC` (Message Authentication Code) — тег автентифікації повідомлення або цифровий підпис цілісності.

#### Узгодження алгоритмів та обмін ключами (KEX)
Одразу після встановлення TCP-з'єднання сторони обмінюються текстовими рядками ідентифікації версії (наприклад, `SSH-2.0-OpenSSH_9.6`). Після цього кожна сторона надсилає пакет `SSH_MSG_KEXINIT` (тип повідомлення 20), який містить 16-байтний випадковий вектор (cookie) та списки підтримуваних алгоритмів у порядку спадання пріоритету:
- алгоритми обміну ключами (`kex_algorithms`, наприклад `sntrup761x25519-sha512@openssh.com`, `curve25519-sha256`);
- алгоритми ключів сервера (`server_host_key_algorithms`, наприклад `ssh-ed25519`, `rsa-sha2-512`);
- алгоритми симетричного шифрування для кожного напрямку (`encryption_algorithms_client_to_server` та `server_to_client`, наприклад `chacha20-poly1305@openssh.com`, `aes256-gcm@openssh.com`);
- алгоритми контролю цілісності (`mac_algorithms`, наприклад `hmac-sha2-512-etm@openssh.com`);
- алгоритми компресії (`compression_algorithms`, наприклад `none`, `zlib@openssh.com`).

Сторони обирають перший алгоритм зі списку клієнта, який також підтримується сервером. Далі запускається протокол Діффі-Геллмана (на еліптичних кривих ECDH або постквантовий гібрид). У результаті математичного обміну клієнт і сервер обчислюють однаковий спільний секретний результат K (Shared Secret) та геш сеансу H (Exchange Hash), який обчислюється як криптографічний геш від усіх переданих на етапі ініціалізації параметрів: версій клієнта і сервера, їхніх пакетів KEXINIT, публічного ключа сервера та відкритих ключів KEX.

#### Автентифікація хоста
Сервер підписує отриманий геш H своїм приватним ключем хоста (Host Private Key) і надсилає підпис разом зі своїм публічним ключем клієнту. Клієнт перевіряє цифровий підпис за допомогою публічного ключа сервера. Оскільки геш H включає спільний секрет K, який відомий тільки учасникам з'єднання, успішна перевірка підпису гарантує дві речі: сервер дійсно володіє заявленим ключем хоста, і між клієнтом та сервером немає активного посередника (Man-in-the-Middle), який намагався б підмінити ключі KEX.

Клієнт звіряє отриманий публічний ключ сервера з локальною базою довірених хостів `~/.ssh/known_hosts`. Якщо ключ хоста зустрічається вперше, клієнт реалізує модель TOFU (Trust On First Use) — запитує підтвердження в користувача через відбиток (fingerprint). Якщо ключ хоста змінився, клієнт блокує з'єднання попередженням про можливу атаку перехоплення.

#### Генерація сеансових ключів і захист від Replay
Зі спільного секрету K та гешу H криптографічною функцією розширення виводиться шість незалежних сеансових ключів:
1. Ключ шифрування від клієнта до сервера.
2. Ключ шифрування від сервера до клієнта.
3. Ключ MAC від клієнта до сервера.
4. Ключ MAC від сервера до клієнта.
5. Вектор ініціалізації IV від клієнта до сервера.
6. Вектор ініціалізації IV від сервера до клієнта.

Обидві сторони надсилають повідомлення `SSH_MSG_NEWKEYS` (тип 21). Усі наступні пакети шифруються виключно згенерованими сеансовими ключами.

Для захисту від повторного відтворення (replay attack) та порушення послідовності кожен пакет транспорту неявно прив'язаний до 32-бітного лічильника послідовності (`sequence_number`), який стартує з 0 і збільшується на 1 після кожного надісланого пакета. Лічильник не передається відкрито мережею, але включається в обчислення MAC/AEAD тегу. Якщо зловмисник спробує перехопити валідний пакет і надіслати його повторно, або поміняти пакети місцями, значення лічильника на стороні отримувача не співпаде, тег автентифікації виявиться недійсним, і з'єднання буде миттєво розірвано.

#### Симетричні шифри: еволюція від CBC до AEAD
У ранніх версіях SSH-2 застосовувався режим CBC з автентифікацією за схемою Encrypt-and-MAC. Це призводило до вразливостей типу Padding Oracle, коли помилка розшифрування вирівнювання розкривала байти відкритого тексту. У сучасному OpenSSH реалізовано дві безпечні схеми:
1. **Encrypt-then-MAC (EtM):** Пакет спочатку шифрується (наприклад, `aes256-ctr`), після чого MAC обчислюється від уже зашифрованого шифротексту та поля довжини. Отримувач спочатку перевіряє MAC і відкидає підроблені пакети ще до передачі їх блоку розшифрування.
2. **Автентифіковане шифрування з додатковими даними (AEAD):** Режими `chacha20-poly1305@openssh.com` та `aes256-gcm@openssh.com`. У ChaCha20-Poly1305 використовується два незалежні екземпляри шифру: перший шифрує 4-байтне поле довжини пакета (що унеможливлює аналіз довжини пакетів стороннім спостерігачем), а другий шифрує корисне навантаження та генерує 16-байтний поліноміальний тег автентифікації Poly1305.

#### Переузгодження ключів (Rekeying)
При тривалій передачі великих обсягів даних вичерпується унікальність простору векторів ініціалізації IV, що створює загрозу криптоаналізу. Тому транспортний рівень автоматично ініціює повторний KEX (повідомленням `SSH_MSG_KEXINIT`) після передачі кожного гігабайта даних або після однієї години роботи (параметр `RekeyLimit` у конфігурації). Під час переузгодження передача прикладних даних короткочасно призупиняється, обчислюються нові симетричні ключі, і сеанс продовжується без розриву логічних каналів.

### 2. Рівень автентифікації користувача (User Authentication Layer, RFC 4252)

Після того, як транспортний рівень встановив зашифроване з'єднання, клієнт запитує запуск служби автентифікації повідомленням `SSH_MSG_SERVICE_REQUEST` із назвою `"ssh-userauth"`. Сервер відповідає `SSH_MSG_SERVICE_ACCEPT`.

Рівень автентифікації користувача виконує перевірку прав клієнта на доступ до запитаного облікового запису операційної системи. Специфікація стандарту підтримує кілька методів:

```
                  +-----------------------------------+
                  |   SSH_MSG_SERVICE_REQUEST         |
                  |   "ssh-userauth"                  |
                  +-----------------+-----------------+
                                    |
                                    v
                  +-----------------------------------+
                  |  SSH_MSG_USERAUTH_REQUEST         |
                  |  user, service, method            |
                  +--------+--------+--------+--------+
                           |        |        |
        +------------------+        |        +------------------+
        |                           |                           |
        v                           v                           v
+---------------+           +---------------+           +---------------+
|   publickey   |           |   password    |           |  keyboard-    |
| (Ed25519/RSA) |           | (PAM / hash)  |           |  interactive  |
| підпис ses_id |           | перевірка pw  |           | (TOTP/MFA/PAM)|
+---------------+           +---------------+           +---------------+
```

1. **Метод `publickey` (Асиметричні ключі):**
   Найбільш захищений і рекомендований метод. Клієнт надсилає повідомлення `SSH_MSG_USERAUTH_REQUEST` із зазначенням імені користувача, назви сервісу (`"ssh-connection"`), назви методу (`"publickey"`), відкритого ключа та цифрового підпису.
   
   Критично важлива деталь архітектури: клієнт формує підпис не від довільного тексту, а від бінарної структури, що містить ідентифікатор сеансу **`session_id`** (який дорівнює гешу первинного обміну ключами H). Оскільки H є унікальним для кожного конкретного TCP-з'єднання і залежить від випадкових параметрів обох сторін, створений цифровий підпис дійсний виключно для поточного сеансу. Зловмисник не може перехопити цей підпис і використати його для входу на інший сервер або навіть для повторного входу на цей самий сервер.
   
   Сервер перевіряє підпис клієнта, після чого зчитує файл `~/.ssh/authorized_keys` (або запитує авторизаційний демон чи каталог облікових записів) і перевіряє наявність відкритого ключа та встановлених для нього обмежень (`command=`, `from=`, `no-pty`).

2. **Метод `password`:**
   Клієнт передає відкритий текстовий пароль користувача. Оскільки передача відбувається всередині вже зашифрованого транспорту, пароль захищений від перехоплення в мережі. Сервер перевіряє пароль через підсистему PAM (`/etc/pam.d/sshd`) або локальну базу `/etc/shadow`.

3. **Метод `keyboard-interactive` (RFC 4256):**
   Універсальний протокол виклику-відповіді. Сервер може надсилати клієнту довільну кількість текстових запитань (prompts), на які користувач повинен надати відповіді. Саме цей метод використовується для інтеграції багатофакторної автентифікації (MFA): запиту одноразових паролів Time-based One-Time Password (TOTP, Google Authenticator), апаратних ключів YubiKey або систем єдиного входу.

4. **Методи `hostbased` та `gssapi-with-mic`:**
   Використовуються в корпоративних мережах для реалізації наскрізної автентифікації (Single Sign-On, SSO) на основі квитків Kerberos 5 або взаємної довіри серверів кластера.

Якщо автентифікація успішна, сервер надсилає `SSH_MSG_USERAUTH_SUCCESS` (тип 52), і протокол переходить до канального рівня. Якщо спроба невдала, сервер повертає `SSH_MSG_USERAUTH_FAILURE` зі списком методів, які ще можна спробувати.

### 3. Рівень з'єднань та каналів (Connection Layer, RFC 4254)

Після завершення автентифікації клієнт отримує доступ до Connection Layer. Головна задача цього рівня — **мультиплексування**: розбиття єдиного зашифрованого TCP-з'єднання на довільну кількість незалежних логічних каналів передачі даних.

Кожен логічний канал ідентифікується двома 32-бітними числовими дескрипторами:
- `sender_channel` — номер каналу на локальній стороні;
- `recipient_channel` — номер каналу на віддаленій стороні.

Коли клієнт або сервер надсилає дані, він вказує номер каналу отримувача (`recipient_channel`). Це дозволяє обом сторонам виділяти локальні номери каналів незалежно, без ризику колізій і без потреби централізованої координації номерів.

#### Керування потоком даних на рівні каналів (Flow Control)
Оскільки всі канали ділять між собою єдиний спільний TCP-сокет, повільний споживач даних в одному каналі міг би переповнити буфери сокета й заблокувати передачу даних для всіх інших каналів. Щоб цього уникнути, SSH реалізує механізм ковзного вікна прийому для кожного каналу окремо:
- Під час відкриття каналу сторона оголошує свій початковий розмір вікна прийому (`initial_window_size`, наприклад 2 МБ) та максимальний розмір одного пакета (`maximum_packet_size`, наприклад 32 КБ).
- Відправник має право надсилати байти в канал лише доти, доки обсяг переданих непідтверджених даних не перевищить доступне вікно прийому отримувача.
- Коли прикладний процес зчитує байти з буфера, отримувач надсилає повідомлення `SSH_MSG_CHANNEL_WINDOW_ADJUST` (тип 93), збільшуючи доступний ліміт відправника на вказану кількість байтів.

#### Типи каналів зв'язку
SSH-2 стандартизує кілька фундаментальних типів каналів:
- **`session`** — виконання віддаленої інтерактивної командної оболонки, окремих команд без термінала або запуск системних підсистем (наприклад, SFTP).
- **`direct-tcpip`** — локальне прокидання портів (клієнтська опція `-L`). Клієнт слухає локальний порт і транслює TCP-з'єднання через тунель до віддаленого хоста.
- **`forwarded-tcpip`** — віддалене прокидання портів (клієнтська опція `-R`). Сервер відкриває порт на віддаленому боці та передає вхідні з'єднання клієнту.
- **`x11`** — перенаправлення графічного протоколу X Window System (клієнтська опція `-X` / `-Y`).
- **`auth-agent@openssh.com`** — прокидання сокета агента ключів `ssh-agent` (клієнтська опція `-A`), що дозволяє віддаленому серверу запитувати підписи локального агента без копіювання приватних ключів на сервер.

## Життєвий цикл сеансу: канал session, виділення PTY та потоки даних

Найважливішим практичним застосуванням канального рівня є створення каналу типу `session`. Життєвий цикл віддаленого сеансу складається з чіткої послідовності кроків між клієнтом, демоном `sshd` та ядром операційної системи.

![Потік даних інтерактивного SSH-сеансу з PTY](/root/sys/sys-unix/ssh-remote-session/img/ssh-session-pty-flow.svg)
*Архітектура та потік даних інтерактивного SSH-сеансу з виділенням псевдотермінала (PTY).*

### 1. Відкриття сесійного каналу
Клієнт надсилає повідомлення `SSH_MSG_CHANNEL_OPEN` із рядком типу `"session"`, своїм локальним номером каналу та розміром вікна. Сервер створює структуру керування каналом і відповідає `SSH_MSG_CHANNEL_OPEN_CONFIRMATION`.

### 2. Запит псевдотермінала (`pty-req`)
Якщо користувач запускає SSH у режимі інтерактивного сеансу (`ssh user@server`), клієнтський додаток перед запуском оболонки надсилає запит `SSH_MSG_CHANNEL_REQUEST` із типом `"pty-req"`. Цей пакет передає такі критичні атрибути:
- Назва типу термінала (`TERM`, наприклад `xterm-256color` або `vt100`).
- Розміри вікна в символах (кількість стовпців `columns` та рядків `rows`, наприклад 80×24).
- Розміри вікна в графічних пікселях (зазвичай 0×0, якщо емулятор не повідомляє графічну роздільність).
- Закодований масив термінальних режимів `termios` (біти керування канонічним режимом `ICANON`, локальним ехо `ECHO`, генерацією сигналів `ISIG` та кодами спеціальних клавіш `VINTR=0x03`, `VERASE=0x7F`, `VEOF=0x04`).

### 3. Механіка виділення PTY на стороні сервера (`sshd`)
Отримавши запит `pty-req`, демон `sshd` звертається до ядра операційної системи для створення псевдотермінала:
1. `sshd` відкриває майстер-дескриптор пристрою клонування `/dev/ptmx` (`open("/dev/ptmx", O_RDWR | O_NOCTTY)`).
2. За допомогою викликів `grantpt()` та `unlockpt()` демон змінює права доступу до створеного вузла та розблоковує парний підлеглий пристрій (PTY slave).
3. Викликом `ptsname()` демон отримує шлях до підлеглого пристрою в системній ієрархії devpts (наприклад, `/dev/pts/3`).
4. `sshd` викликає системний виклик `fork()` для створення дочірнього процесу користувача:
   - **У дочірньому процесі:**
     - Викликається `setsid()` для створення нової сесії Unix і повного від'єднання від керуючого термінала батьківського демона `sshd`.
     - Відкривається підлеглий файл `/dev/pts/3`, і системним викликом `ioctl(slave_fd, TIOCSCTTY, 0)` він призначається керуючим терміналом (Controlling Terminal) для нової сесії.
     - За допомогою системного виклику `dup2()` підлеглий дескриптор копіюється на стандартні файлові дескриптори: `0` (stdin), `1` (stdout) та `2` (stderr).
     - Застосовуються отримані від клієнта налаштування `termios` через `tcsetattr()`.
     - Знижуються привілеї до UID/GID користувача (`setgid`, `initgroups`, `setuid`).
     - Запускається реєстраційна оболонка користувача (наприклад, `/bin/bash`) через системний виклик `execve()`.
   - **У батьківському процесі `sshd`:**
     - Підлеглий дескриптор закривається, а майстер-дескриптор `/dev/ptmx` реєструється в системному циклі очікування подій (`epoll` або `poll`) разом із мережевим сокетом клієнта.

### 4. Робота локального термінала в Raw-режимі
Щоб забезпечити повну прозорість інтерактивної взаємодії, клієнт `ssh` на локальній машині повинен змінити режим свого власного термінала:
1. Клієнт зберігає поточні атрибути термінала викликом `tcgetattr(STDIN_FILENO, &orig_termios)`.
2. Клієнт переводить локальний термінал у **сирий режим (Raw Mode)** функцією `cfmakeraw()`:
   - вимикається канонічний режим (`ICANON=0`) — ядро перестає буферизувати символи до натискання Enter і віддає кожен байт негайно;
   - вимикається локальне ехо (`ECHO=0`) — символи не друкуються двічі (ехо друкуватиме віддалений сервер);
   - вимикається обробка керуючих сигналів (`ISIG=0`) — натискання `Ctrl+C` (байт `0x03`) або `Ctrl+Z` (байт `0x1A`) не надсилає локальних сигналів `SIGINT`/`SIGTSTP` процесу клієнта `ssh`.
3. Кожен введений користувачем байт клієнт негайно зчитує зі свого `stdin` і запаковує в повідомлення `SSH_MSG_CHANNEL_DATA` (тип 94).
4. Сервер `sshd`, отримавши цей пакет, розпаковує байти й записує їх у майстер-дескриптор `/dev/ptmx`.
5. Дисципліна ліній ядра віддаленого сервера (`n_tty`) отримує байти, генерує ехо-відповідь назад у `/dev/ptmx` (яка повертається клієнту для відображення на екрані) та передає введення підлеглому пристрою `/dev/pts/3`. Якщо прийшов байт `0x03`, саме ядро сервера генерує сигнал `SIGINT` групі процесів переднього плану віддаленого термінала.

### 5. Динамічна зміна розміру вікна (`window-change`)
Якщо користувач змінює розмір вікна свого графічного емулятора термінала (наприклад, розгортає вікно на весь екран):
1. Локальне ядро надсилає процесу клієнта `ssh` сигнал `SIGWINCH` (Window Size Change).
2. Обробник сигналу в клієнті викликає системний виклик `ioctl(STDIN_FILENO, TIOCGWINSZ, &ws)`, отримуючи нові значення стовпців і рядків.
3. Клієнт надсилає у сесійний канал повідомлення `SSH_MSG_CHANNEL_REQUEST` із типом `"window-change"`.
4. Сервер `sshd`, отримавши повідомлення, виконує системний виклик `ioctl(master_fd, TIOCSWINSZ, &ws)` на своєму майстер-дескрипторі `/dev/ptmx`.
5. Ядро сервера автоматично генерує сигнал `SIGWINCH` для віддаленої групи процесів. Програми з повноекранним інтерфейсом (`vim`, `tmux`, `htop`, `less`) перехоплюють цей сигнал і миттєво перемальовують екран під нові габарити.

### 6. Неінтерактивний режим (Виконання команд без PTY)
Коли клієнт викликає команду безпосередньо, наприклад:
```bash
ssh user@server "tar -czf - /var/log" > logs.tar.gz
```
клієнт OpenSSH **не надсилає** запит `pty-req`, а одразу надсилає запит `"exec"` із текстом команди.

Відсутність PTY в цьому випадку критично важлива з інженерної точки зору:
- **Двійкова прозорість:** Дисципліна ліній PTY за замовчуванням перетворює байти переведення рядка `\n` (LF) на пару `\r\n` (CR-LF) для сумісності з терміналами. У неінтерактивному режимі сервер з'єднує процес користувача через звичайні анонімні канали (Pipes). Байти двійкових даних (архіви, зображення, дампи баз даних) передаються байт-у-байт без спотворень.
- **Розділення stdout та stderr:** У PTY стандартний вивід і стандартний потік помилок зливаються в один термінальний пристрій. У неінтерактивному сеансі SSH стандартний вивід передається в пакетах `SSH_MSG_CHANNEL_DATA`, а потік помилок передається в розширених пакетах `SSH_MSG_CHANNEL_EXTENDED_DATA` (тип 95) з типом даних `SSH_EXTENDED_DATA_STDERR` (значення 1). Клієнт записує дані першого типу у свій локальний дескриптор 1 (stdout), а другого типу — у дескриптор 2 (stderr).
- **Повернення коду завершення:** Після завершення команди сервер надсилає запит `SSH_MSG_CHANNEL_REQUEST` типу `"exit-status"` з 32-бітним цілим числом статусу завершення процесу (код виходу), після чого закриває канал пакетами `SSH_MSG_CHANNEL_EOF` та `SSH_MSG_CHANNEL_CLOSE`. Локальний клієнт `ssh` завершує власну роботу з точно таким самим кодом повернення.

Повний довідковий перелік двійкових повідомлень, форматів полів каналу та таблицю параметрів наведено у вставці [📋 Протокол каналу session та ескейп-керування OpenSSH](root:sys-unix/ssh-remote-session/api-ssh-escape-and-session-channel.md).

## Передача середовища та конфігурація локалей

Під час створення сеансу клієнт може надіслати запити `SSH_MSG_CHANNEL_REQUEST` із типом `"env"`, передаючи пари `ім'я_змінної=значення`, які він просить встановити в оточенні створюваної оболонки.

Ця можливість регулюється двома директивами конфігурації:
- на стороні клієнта (`ssh_config`): директива `SendEnv`;
- на стороні сервера (`sshd_config`): директива `AcceptEnv`.

За замовчуванням у більшості дистрибутивів Linux директиви налаштовані на передачу виключно змінних мовної локалі:
```
# /etc/ssh/ssh_config
SendEnv LANG LC_*

# /etc/ssh/sshd_config
AcceptEnv LANG LC_*
```

### Чому передаються змінні локалі?
Якщо локальна машина налаштована на українську локаль `uk_UA.UTF-8`, а віддалений сервер працює в мінімальній конфігурації `POSIX` або `C`, без передачі `LANG` та `LC_CTYPE` програми на сервері не знатимуть поточної кодової сторінки. У результаті утиліти виводу спотворюватимуть кириличні символи, сортування рядків у `sort` відбуватиметься за числовими кодами ASCII, а програми редагування некоректно оброблятимуть багатобайтні послідовності UTF-8. Передача `LC_*` забезпечує прозору мовну сумісність між клієнтом і сервером.

### Загрози безпеки та небезпечні змінні
Сервер `sshd` суворо фільтрує змінні середовища і відхиляє будь-які імена, які не входять у білий список директиви `AcceptEnv`. Спроба дозволити передачу довільних змінних директивою `AcceptEnv *` становить **критичну вразливість безпеки операційної системи**:

1. **Ін'єкція динамічного завантажувача (`LD_PRELOAD`, `LD_LIBRARY_PATH`):**
   Якщо зловмисник зможе передати `LD_PRELOAD=/tmp/evil.so`, динамічний компонувальник `ld.so` завантажить шкідливу бібліотеку в адресний простір кожної програми, яку виконує користувач. Навіть для непривілейованих користувачів це дозволяє обходити обмежені оболонки (restricted shells, `rbash`).
2. **Маніпуляція шляхами пошуку (`PATH`):**
   Передача зміненого `PATH` дозволяє змусити системні сценарії ініціалізації запускати підроблені бінарні файли з тимчасових каталогів `/tmp` замість стандартних `/usr/bin`.
3. **Керування поведінкою командних інтерпретаторів (`BASH_ENV`, `ENV`, `IFS`):**
   Змінна `BASH_ENV` змушує інтерпретатор Bash виконувати вказаний файл скрипта перед запуском будь-якого неінтерактивного сценарію, що призводить до прихованого виконання коду. Змінна `IFS` (Internal Field Separator) може змінити правила розбиття рядків на аргументи, зламавши логіку системних утиліт.

Тому демон `sshd` відкидає всі неавторизовані змінні середовища і формує мінімальне чисте оточення (`PATH`, `USER`, `HOME`, `SHELL`, `LOGNAME`, `MAIL`), доповнюючи його лише дозволеними змінними з `AcceptEnv` та системними змінними самого SSH (`SSH_CLIENT`, `SSH_CONNECTION`, `SSH_TTY`).

## Керуючі ескейп-послідовності клієнта OpenSSH

Оскільки в інтерактивному сеансі локальний термінал переведено в сирий режим (Raw Mode), а всі керуючі комбінації клавіш (`Ctrl+C`, `Ctrl+Z`, `Ctrl+\`) транслюються віддаленому серверу, виникає фундаментальна проблема: **як повернути керування локальному клієнту, якщо віддалений сервер або мережевий канал завис?**

Якщо проміжний маршрутизатор перестав передавати пакети, віддалене ядро зазнало паніки (kernel panic) або завис мережевий інтерфейс, натискання `Ctrl+C` не дасть жодного результату — байти `0x03` надсилаються в буфер мертвого TCP-сокета, а локальний клієнт продовжує нескінченно очікувати відповіді.

Для розв'язання цієї проблеми клієнт OpenSSH містить вбудований **скінченний автомат ескейп-послідовностей**, який перехоплює спеціальний керівний символ (за замовчуванням тильда `~`).

![Скінченний автомат ескейп-послідовностей клієнта OpenSSH](/root/sys/sys-unix/ssh-remote-session/img/ssh-escape-state-machine.svg)
*Скінченний автомат обробки ескейп-послідовностей клієнта OpenSSH на початку рядка.*

### Логіка роботи ескейп-автомата
1. **Стан NORMAL (Звичайне введення):** Будь-які символи, введені користувачем усередині рядка (включно із символом `~`), негайно запаковуються в пакети `SSH_MSG_CHANNEL_DATA` і надсилаються в мережу.
2. **Стан START_OF_LINE (Початок нового рядка):** Автомат переходить у цей стан одразу після натискання клавіші `Enter` (байтів `\r` або `\n`) або безпосередньо в момент відкриття сеансу.
3. **Стан ESCAPE_PENDING (Очікування команди):** Якщо першим символом нового рядка введено `~`, клієнт **не надсилає його в мережу**, а тимчасово буферизує в пам'яті й очікує наступного натискання клавіші:
   - Якщо наступним символом натиснуто **`.` (крапка)** (`~.`): клієнт негайно ініціює аварійний розрив з'єднання (*Emergency Disconnect*), закриває мережевий сокет, відновлює локальний термінал із raw-режиму у вихідний канонічний стан через `tcsetattr()` і повертає керування локальній консолі.
   - Якщо натиснуто **`Ctrl+Z`** (`~^Z`): клієнт відновлює локальний термінал і надсилає сигнал `SIGTSTP` власному процесу `ssh`. Процес переходить у фоновий режим локальної оболонки (job control). Користувач може виконати локальні команди (перевірити мережу, скопіювати файл) і повернутися до завислого або працюючого віддаленого сеансу командою `$ fg`.
   - Якщо натиснуто **`#` (решітка)** (`~#`): клієнт виводить на екран список усіх відкритих у цьому з'єднанні мультиплексованих каналів і прокидань портів.
   - Якщо натиснуто **`C` (велика латинська C)** (`~C`): відкривається вбудований командний рядок `ssh>`. У ньому можна на льоту додати нове локальне прокидання (`-L 8080:localhost:80`), віддалене прокидання (`-R 9000:localhost:3000`) або динамічний SOCKS-проксі (`-D 1080`) без потреби розривати поточний сеанс.
   - Якщо натиснуто **`~` (подвійна тильда)** (`~~`): клієнт розуміє, що користувач дійсно хотів надрукувати тильду на початку рядка, відправляє один символ `~` у віддалений канал і повертається в стан NORMAL.
   - Якщо натиснуто будь-який інший невідомий символ: клієнт відправляє в мережу буферизований символ `~`, слідом за ним щойно введений символ і переходить у стан NORMAL.

## Діагностика збоїв, таймаути та живучість сеансу

При тривалій роботі через нестабільні мережі або через брандмауери з механізмом трансляції адрес (NAT) сеанси SSH можуть несподівано зависати без повідомлень про помилку. Причина полягає в тому, що таблиці стану NAT-роутерів автоматично видаляють записи про з'єднання, якщо через них не проходив трафік протягом певного часу (зазвичай від 5 до 30 хвилин).

Для запобігання «тихому» розриву та своєчасного виявлення збоїв застосовуються два рівні контролю доступності:

1. **Системний рівень TCP Keepalive (`SO_KEEPALIVE`):**
   Керується опцією `TCPKeepAlive yes`. Ядро надсилає порожні TCP-зонди ACK. Недолік методу: зонди генеруються мережевим стеком ядра і підтверджуються ядром віддаленого сервера навіть тоді, коли сам процес демона `sshd` завис або заблокований дисковим вводом/виводом.
2. **Прикладний криптографічний рівень OpenSSH Keepalive:**
   Керується директивами `ServerAliveInterval` / `ServerAliveCountMax` (на стороні клієнта) та `ClientAliveInterval` / `ClientAliveCountMax` (на стороні сервера).
   
   Кожні N секунд клієнт або сервер формує зашифрований пакет `SSH_MSG_GLOBAL_REQUEST` із рядком `"keepalive@openssh.com"` і прапорцем `want_reply=TRUE`. Віддалена сторона зобов'язана відповісти повідомленням `SSH_MSG_REQUEST_FAILURE` або `SUCCESS` через прикладний шар `sshd`. Якщо M запитів поспіль залишаються без відповіді, сторона фіксує обрив зв'язку, звільняє ресурси та коректно завершує сеанс.

Коли демон `sshd` фіксує закриття каналу або розрив мережевого сокета, він закриває майстер-дескриптор `/dev/ptmx`. Ядро операційної системи фіксує обрив лінії на підлеглому пристрої `/dev/pts/N` і автоматично надсилає сигнал **`SIGHUP`** лідеру сесії (реєстраційній оболонці). Оболонка, у свою чергу, пересилає `SIGHUP` усім запущеним у ній фоновим процесам, завершуючи роботу сеансу.

## Практична реалізація: виділення PTY та переведення термінала у Raw Mode

Нижче наведено практичну реалізацію мінімального диспетчера сеансу на C та сучасному C++, яка ілюструє ядро роботи клієнта та сервера: відкриття пари master/slave PTY, переведення локального термінала в сирий режим (raw mode) зі збереженням та гарантованим відновленням термінальних атрибутів, а також мультиплексування потоків вводу/виводу через `poll()`.

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>
#include <termios.h>
#include <sys/ioctl.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <pty.h>
#include <poll.h>
#include <errno.h>

static struct termios g_orig_termios;
static int g_raw_mode_active = 0;

static void restore_terminal_mode(void) {
    if (g_raw_mode_active) {
        tcsetattr(STDIN_FILENO, TCSAFLUSH, &g_orig_termios);
        g_raw_mode_active = 0;
    }
}

static int enable_raw_mode(void) {
    if (tcgetattr(STDIN_FILENO, &g_orig_termios) == -1) {
        return -1;
    }
    struct termios raw = g_orig_termios;
    cfmakeraw(&raw);
    if (tcsetattr(STDIN_FILENO, TCSAFLUSH, &raw) == -1) {
        return -1;
    }
    g_raw_mode_active = 1;
    atexit(restore_terminal_mode);
    return 0;
}

int main(void) {
    int master_fd = -1;
    struct winsize ws;
    if (ioctl(STDIN_FILENO, TIOCGWINSZ, &ws) == -1) {
        ws.ws_col = 80;
        ws.ws_row = 24;
    }

    pid_t pid = forkpty(&master_fd, NULL, NULL, &ws);
    if (pid < 0) {
        perror("forkpty");
        return 1;
    }

    if (pid == 0) {
        // Дочірній процес: керуючий термінал налаштовано ядром
        char *shell = getenv("SHELL");
        if (!shell) shell = "/bin/sh";
        execlp(shell, shell, "-l", NULL);
        _exit(127);
    }

    // Батьківський процес: переводимо локальний термінал у raw mode
    if (enable_raw_mode() == -1) {
        perror("enable_raw_mode");
        kill(pid, SIGTERM);
        return 1;
    }

    struct pollfd fds[2];
    fds[0].fd = STDIN_FILENO;
    fds[0].events = POLLIN;
    fds[1].fd = master_fd;
    fds[1].events = POLLIN;

    char buffer[4096];
    int running = 1;

    while (running) {
        int ret = poll(fds, 2, -1);
        if (ret < 0) {
            if (errno == EINTR) continue;
            break;
        }

        // Введення від користувача -> запис у майстер PTY
        if (fds[0].revents & POLLIN) {
            ssize_t n = read(STDIN_FILENO, buffer, sizeof(buffer));
            if (n <= 0) break;
            // Перевірка на локальну аварійну послідовність (імітація ~.)
            if (n == 2 && buffer[0] == '~' && buffer[1] == '.') {
                break;
            }
            if (write(master_fd, buffer, (size_t)n) != n) break;
        }

        // Вивід від дочірнього процесу через PTY -> stdout користувача
        if (fds[1].revents & POLLIN) {
            ssize_t n = read(master_fd, buffer, sizeof(buffer));
            if (n <= 0) break;
            if (write(STDOUT_FILENO, buffer, (size_t)n) != n) break;
        }

        if (fds[1].revents & (POLLHUP | POLLERR)) {
            running = 0;
        }
    }

    restore_terminal_mode();
    close(master_fd);
    int status = 0;
    waitpid(pid, &status, 0);
    return WIFEXITED(status) ? WEXITSTATUS(status) : 1;
}
```

```cpp
#include <iostream>
#include <array>
#include <span>
#include <string>
#include <string_view>
#include <memory>
#include <system_error>
#include <cstdlib>
#include <unistd.h>
#include <termios.h>
#include <sys/ioctl.h>
#include <sys/wait.h>
#include <pty.h>
#include <poll.h>

namespace sys {

class TerminalGuard {
public:
    TerminalGuard() {
        if (::isatty(STDIN_FILENO)) {
            if (::tcgetattr(STDIN_FILENO, &orig_termios_) == 0) {
                active_ = true;
            }
        }
    }

    ~TerminalGuard() noexcept {
        restore();
    }

    TerminalGuard(const TerminalGuard&) = delete;
    TerminalGuard& operator=(const TerminalGuard&) = delete;

    void enable_raw_mode() {
        if (!active_) return;
        struct termios raw = orig_termios_;
        ::cfmakeraw(&raw);
        if (::tcsetattr(STDIN_FILENO, TCSAFLUSH, &raw) == -1) {
            throw std::system_error(errno, std::generic_category(), "tcsetattr raw mode failed");
        }
        raw_enabled_ = true;
    }

    void restore() noexcept {
        if (active_ && raw_enabled_) {
            ::tcsetattr(STDIN_FILENO, TCSAFLUSH, &orig_termios_);
            raw_enabled_ = false;
        }
    }

private:
    struct termios orig_termios_{};
    bool active_{false};
    bool raw_enabled_{false};
};

struct UniqueFd {
    int fd{-1};

    UniqueFd() noexcept = default;
    explicit UniqueFd(int f) noexcept : fd(f) {}
    ~UniqueFd() noexcept { reset(); }

    UniqueFd(const UniqueFd&) = delete;
    UniqueFd& operator=(const UniqueFd&) = delete;

    UniqueFd(UniqueFd&& other) noexcept : fd(other.fd) { other.fd = -1; }
    UniqueFd& operator=(UniqueFd&& other) noexcept {
        if (this != &other) {
            reset(other.fd);
            other.fd = -1;
        }
        return *this;
    }

    void reset(int new_fd = -1) noexcept {
        if (fd >= 0) ::close(fd);
        fd = new_fd;
    }

    [[nodiscard]] int get() const noexcept { return fd; }
};

struct PtySession {
    UniqueFd master;
    pid_t child_pid{-1};
};

PtySession spawn_pty_session(std::string_view shell_path) {
    struct winsize ws{};
    if (::ioctl(STDIN_FILENO, TIOCGWINSZ, &ws) == -1) {
        ws.ws_col = 80;
        ws.ws_row = 24;
    }

    int master_fd = -1;
    pid_t pid = ::forkpty(&master_fd, nullptr, nullptr, &ws);
    if (pid < 0) {
        throw std::system_error(errno, std::generic_category(), "forkpty failed");
    }

    if (pid == 0) {
        // Дочірній процес у власному просторі сесії з PTY
        std::string path(shell_path.empty() ? "/bin/sh" : shell_path);
        ::execlp(path.c_str(), path.c_str(), "-l", nullptr);
        ::_exit(127);
    }

    return PtySession{UniqueFd(master_fd), pid};
}

void run_event_loop(int master_fd) {
    std::array<struct pollfd, 2> fds{{
        {STDIN_FILENO, POLLIN, 0},
        {master_fd, POLLIN, 0}
    }};

    std::array<char, 4096> buffer{};

    while (true) {
        int ret = ::poll(fds.data(), static_cast<nfds_t>(fds.size()), -1);
        if (ret < 0) {
            if (errno == EINTR) continue;
            break;
        }

        // Ввід користувача -> передача у майстер PTY
        if (fds[0].revents & POLLIN) {
            ssize_t n = ::read(STDIN_FILENO, buffer.data(), buffer.size());
            if (n <= 0) break;
            if (n == 2 && buffer[0] == '~' && buffer[1] == '.') {
                // Аварійний розрив сеансу
                break;
            }
            if (::write(master_fd, buffer.data(), static_cast<size_t>(n)) != n) break;
        }

        // Вивід програми -> передача на екран термінала
        if (fds[1].revents & POLLIN) {
            ssize_t n = ::read(master_fd, buffer.data(), buffer.size());
            if (n <= 0) break;
            if (::write(STDOUT_FILENO, buffer.data(), static_cast<size_t>(n)) != n) break;
        }

        if (fds[1].revents & (POLLHUP | POLLERR)) {
            break;
        }
    }
}

} // namespace sys

int main() {
    try {
        sys::TerminalGuard term_guard;
        const char* shell_env = std::getenv("SHELL");
        std::string_view shell = shell_env ? shell_env : "/bin/sh";

        auto session = sys::spawn_pty_session(shell);
        term_guard.enable_raw_mode();

        sys::run_event_loop(session.master.get());

        term_guard.restore();
        int status = 0;
        ::waitpid(session.child_pid, &status, 0);
        return WIFEXITED(status) ? WEXITSTATUS(status) : 1;
    } catch (const std::exception& e) {
        std::cerr << "Помилка сеансу: " << e.what() << '\n';
        return 1;
    }
}
```
