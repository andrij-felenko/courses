# 📋 Протокол каналу session та ескейп-керування OpenSSH

Специфікація каналу `session` у стандарті SSH-2 (RFC 4254) визначає двійковий контракт узгодження терміналів, передачі змінних середовища, запуску процесів та повернення кодів завершення, а вбудований у клієнт OpenSSH драйвер ескейп-послідовностей надає механізм локального та віддаленого втручання в активні мультиплексовані потоки.

Цей документ фіксує точні формати пакетів двійкового протоколу, числові коди повідомлень, опкоди кодування термінальних режимів `termios`, синтаксис керуючих послідовностей та правила формування конфігураційних директив клієнта і сервера OpenSSH.

---

## Правила серіалізації типів даних (RFC 4251)

Усі двійкові структури канального рівня SSH-2 використовують строго типізоване представлення даних із прямим порядком байтів (Big-Endian / Network Byte Order). Двійковий потік формується з таких базових примітивів:

- **`byte`** — беззнакове 8-бітне ціле число (1 октет).
- **`boolean`** — один байт, де значення `0` позначає `FALSE`, а значення `1` (або будь-яке ненульове число) позначає `TRUE`.
- **`uint32`** — беззнакове 32-бітне ціле число (4 октети у форматі big-endian; старший байт передається першим).
- **`uint64`** — беззнакове 64-бітне ціле число (8 октет у форматі big-endian).
- **`string`** — довільний масив байтів, перед яким обов'язково записується його довжина у вигляді поля `uint32`. Текстові рядки передаються у кодуванні UTF-8 без завершального нульового байта (null-terminator). Якщо довжина рядка дорівнює нулю, поле складається виключно з чотирьох нульових байтів довжини `0x00000000`.
- **`mpint`** — ціле число довільної розрядності зі знаком (Multiple Precision Integer), що кодується у форматі доповнення до двійки з префіксом довжини `uint32`.
- **`name-list`** — список імен, розділених комами, закодований як стандартний `string` (наприклад, `"aes128-ctr,aes256-ctr"`).

## Таблиця керуючих ескейп-послідовностей клієнта OpenSSH

Керівний ескейп-символ (за замовчуванням тильда `~`, що налаштовується директивою `EscapeChar`) активується клієнтом OpenSSH виключно тоді, коли він введений **першим символом безпосередньо після початку нового рядка** (після натискання клавіші `Enter`, тобто отримання байта `\r` або `\n`). Якщо символ введено всередині рядка або після пробілу, клієнт не активує внутрішній автомат і транслює тильду у віддалений канал як звичайний символ тексту.

У таблиці нижче наведено повний перелік підтримуваних ескейп-команд OpenSSH:

| Послідовність | Назва операції | Механізм виконання та системна дія |
|---|---|---|
| `~.` | Аварійний розрив зв'язку (*Terminate session*) | Клієнт негайно закриває мережевий сокет TCP, відновлює початкові атрибути локального термінала (`tcsetattr`) та завершує процес з ненульовим кодом. Застосовується, коли сервер або канал завис і не реагує на стандартні сигнали. |
| `~^Z` (`~` + `Ctrl+Z`) | Призупинення клієнта (*Suspend client*) | Клієнт відновлює локальний термінал із сирого режиму (raw mode) у канонічний і надсилає сигнал `SIGTSTP` власному процесу. Керування повертається до локальної оболонки. Повернення у сеанс здійснюється вбудованою командою `$ fg`. |
| `~#` | Список відкритих каналів (*List forwarded channels*) | Клієнт виводить у термінал діагностичну таблицю всіх активних у межах поточного TCP-з'єднання логічних каналів: сеансів, локальних (`-L`), віддалених (`-R`) та динамічних SOCKS (`-D`) прокидань із зазначенням локальних та віддалених портів. |
| `~C` | Вбудований командний рядок (*Open command line*) | Відкриває інтерактивний командний рядок `ssh>`, у якому можна на льоту без перезапуску з'єднання додавати або видаляти тунелі: `-L 8080:db:5432`, `-R 9000:localhost:3000`, `-D 1080`, `-KL 8080` (скасування локального прокидання), `-KR 9000` (скасування віддаленого). |
| `~&` | Фонування при завершенні (*Background on EOF*) | Переводить сеанс SSH у фоновий режим операційної системи під час очікування закриття дочірніх процесів або перенаправлених дескрипторів, якщо основна команда вже завершила роботу. |
| `~?` | Виведення довідки (*Help*) | Друкує у потік виводу повний перелік усіх доступних гарячих клавіш клієнта OpenSSH та їхнє коротке призначення. |
| `~v` | Зниження рівня деталізації логів (*Decrease verbosity*) | Зменшує рівень журналювання OpenSSH (`LogLevel`) на один ступінь без перезапуску з'єднання. |
| `~V` | Підвищення рівня деталізації логів (*Increase verbosity*) | Збільшує рівень журналювання (`LogLevel`) на один ступінь (аналог динамічного додавання прапорця `-v` під час роботи для діагностики помилок). |
| `~B` | Надсилання сигналу BREAK (*Send BREAK*) | Формує та надсилає у віддалений канал повідомлення `SSH_MSG_CHANNEL_REQUEST` типу `"break"`, що транслюється віддаленим PTY у розрив лінії термінала (break condition). |
| `~R` | Запит переузгодження ключів (*Request rekeying*) | Примусово ініціює повторний обмін криптографічними ключами (Key Re-exchange, KEX) на транспортному рівні з'єднання. |
| `~~` | Введення літеральної тильди (*Literal escape character*) | Відправляє один символ `~` у віддалений канал зв'язку на початку рядка, запобігаючи перехопленню ескейп-автоматом. |

### Вкладені сеанси (SSH Chaining / Jump Hosts)

Під час підключення ланцюжком (наприклад, `локальний хост -> хост A -> хост B`) кожен проміжний клієнт `ssh` перехоплює перший символ тильди на початку рядка:
- Розрив першого з'єднання (до хоста A): `Enter` `~` `.`
- Розрив другого з'єднання (між хостом A та хостом B): `Enter` `~` `~` `.` (перший клієнт перетворює `~~` на один `~` і шле в канал; другий клієнт бачить `~.` на початку рядка і розриває свій сеанс).
- Розрив третього рівня: `Enter` `~` `~` `~` `~` `.` (чотири тильди).

## Двійкові повідомлення каналу session (RFC 4254)

Усі повідомлення канального рівня передаються всередині зашифрованого транспортного протоколу BPP (Binary Packet Protocol). Тип повідомлення кодується першим однобайтним полем `byte`.

### Базові керуючі повідомлення каналу

```
byte      SSH_MSG_CHANNEL_OPEN                  = 90
byte      SSH_MSG_CHANNEL_OPEN_CONFIRMATION     = 91
byte      SSH_MSG_CHANNEL_OPEN_FAILURE          = 92
byte      SSH_MSG_CHANNEL_WINDOW_ADJUST         = 93
byte      SSH_MSG_CHANNEL_DATA                  = 94
byte      SSH_MSG_CHANNEL_EXTENDED_DATA         = 95
byte      SSH_MSG_CHANNEL_EOF                   = 96
byte      SSH_MSG_CHANNEL_CLOSE                 = 97
byte      SSH_MSG_CHANNEL_REQUEST               = 98
byte      SSH_MSG_CHANNEL_SUCCESS               = 99
byte      SSH_MSG_CHANNEL_FAILURE               = 100
```

### Формат відкриття каналу (SSH_MSG_CHANNEL_OPEN)

Для створення інтерактивного сеансу або виконання команди клієнт надсилає запит на відкриття каналу з типом `"session"`:

```
byte      SSH_MSG_CHANNEL_OPEN (90)
string    "session"
uint32    sender_channel_id        (локальний номер каналу на стороні клієнта)
uint32    initial_window_size      (початковий розмір вікна прийому в байтах, напр. 2097152)
uint32    maximum_packet_size      (максимальний розмір корисного навантаження, напр. 32768)
```

Сервер відповідає повідомленням `SSH_MSG_CHANNEL_OPEN_CONFIRMATION`:

```
byte      SSH_MSG_CHANNEL_OPEN_CONFIRMATION (91)
uint32    recipient_channel_id     (номер каналу клієнта)
uint32    sender_channel_id        (номер каналу на стороні сервера)
uint32    initial_window_size      (початковий розмір вікна сервера)
uint32    maximum_packet_size      (максимальний розмір пакета сервера)
```

Якщо сервер відхиляє запит (наприклад, вичерпано ліміт відкритих сесій `MaxSessions`), повертається повідомлення `SSH_MSG_CHANNEL_OPEN_FAILURE` (код 92), що містить числовий код причини відмови (Reason Code) та зрозумілий текст помилки.

## Специфікація запитів каналу (SSH_MSG_CHANNEL_REQUEST)

Після підтвердження відкриття каналу клієнт надсилає запити конфігурації сеансу. Загальний заголовок повідомлення має вигляд:

```
byte      SSH_MSG_CHANNEL_REQUEST (98)
uint32    recipient_channel_id
string    request_type             ("pty-req", "env", "shell", "exec", "subsystem", "window-change", "signal")
boolean   want_reply               (TRUE, якщо клієнт очікує SSH_MSG_CHANNEL_SUCCESS / FAILURE)
...       специфічні поля корисного навантаження (payload)
```

### 1. Запит псевдотермінала ("pty-req")

Запит виділяє на стороні сервера пару псевдотерміналів `/dev/ptmx` і передає початкові параметри геометрії вікна та прапорці `termios`:

```
string    "pty-req"
boolean   want_reply
string    term_environment_variable  (наприклад, "xterm-256color")
uint32    terminal_width_characters   (кількість стовпців, наприклад 80)
uint32    terminal_height_rows        (кількість рядків, наприклад 24)
uint32    terminal_width_pixels       (ширина в пікселях, 0 якщо невідомо)
uint32    terminal_height_pixels      (висота в пікселях, 0 якщо невідомо)
string    encoded_terminal_modes      (закодований бінарний масив параметрів termios)
```

Структура `encoded_terminal_modes` складається з послідовності пар `[opcode (1 byte)][argument (4 bytes uint32)]`, що обов'язково завершується байтом `TTY_OP_END (0)`:

- `VINTR (1)` — символ переривання (типово `0x03` для `Ctrl+C`).
- `VQUIT (2)` — символ аварійного виходу (`0x1C` для `Ctrl+\`).
- `VERASE (3)` — символ забою (`0x7F` або `0x08`).
- `VKILL (4)` — символ очищення поточного рядка (`0x15` для `Ctrl+U`).
- `VEOF (5)` — символ кінця файлу (`0x04` для `Ctrl+D`).
- `VEOL (6)` — додатковий символ кінця рядка (`0x00`).
- `VEOL2 (7)` — другий додатковий символ кінця рядка (`0x00`).
- `VSTART (8)` — символ відновлення виводу (`0x11` для `Ctrl+Q`).
- `VSTOP (9)` — символ зупинки виводу (`0x13` для `Ctrl+S`).
- `VSUSP (10)` — символ призупинення процесу (`0x1A` для `Ctrl+Z`).
- `ECHO (53)` — прапорець локального ехо-друку (`1` — увімкнено, `0` — вимкнено).
- `ECHOE (54)` — візуальне стирання символу забоєм (`1` — стирати пробілом).
- `ECHOK (55)` — переведення рядка після стирання всього рядка.
- `ECHONL (56)` — ехо-друк символу нового рядка навіть при вимкненому `ECHO`.
- `ICANON (57)` — канонічний построковий режим ядра (`1` — построково з редагуванням, `0` — сирий режим).
- `ISIG (58)` — розпізнавання керуючих сигнальних символів `INTR`, `QUIT`, `SUSP`.
- `NOFLSH (59)` — заборона скидання черг введення/виведення після генерації сигналу.
- `TTY_OP_ISPEED (128)` — швидкість вхідного термінального потоку в бодах.
- `TTY_OP_OSPEED (129)` — швидкість вихідного термінального потоку в бодах.

### 2. Передача змінної середовища ("env")

Дозволяє клієнту встановити змінну оточення перед запуском процесу:

```
string    "env"
boolean   want_reply
string    variable_name               (наприклад, "LANG")
string    variable_value              (наприклад, "uk_UA.UTF-8")
```

Якщо передача змінної заборонена політикою безпеки сервера (`AcceptEnv`), сервер повертає повідомлення `SSH_MSG_CHANNEL_FAILURE` (код 100), якщо було встановлено `want_reply=TRUE`.

### 3. Запуск інтерактивної оболонки ("shell")

Запитує запуск стандартної реєстраційної оболонки користувача:

```
string    "shell"
boolean   want_reply
```

Сервер зчитує поле реєстраційної оболонки з бази `/etc/passwd` або підсистеми NSS (наприклад, `/bin/bash`), налаштовує дескриптори `0`, `1`, `2` на підлеглий PTY і виконує системний виклик `execve()`.

### 4. Виконання конкретної команди ("exec")

Запитує виконання команди без запуску інтерактивної оболонки:

```
string    "exec"
boolean   want_reply
string    command                     (рядок команди: "find /var/log -type f -name '*.log'")
```

Команда передається системній оболонці через аргумент `-c` (наприклад, `/bin/sh -c "find ..."`).

### 5. Запуск підсистеми ("subsystem")

Запитує запуск стандартизованої системної служби:

```
string    "subsystem"
boolean   want_reply
string    subsystem_name              (наприклад, "sftp" або "netconf")
```

Сервер знаходить відповідний виконуваний файл у директиві `Subsystem` конфігурації `/etc/ssh/sshd_config` (наприклад, `/usr/lib/openssh/sftp-server`) і запускає його з прямим підключенням до каналу зв'язку.

### 6. Динамічна зміна розміру термінала ("window-change")

Надсилається клієнтом асинхронно при отриманні сигналу `SIGWINCH` від локальної операційної системи:

```
string    "window-change"
boolean   FALSE                       (відповідь зазвичай не вимагається)
uint32    terminal_width_columns      (нові стовпці, наприклад 120)
uint32    terminal_height_rows        (нові рядки, наприклад 40)
uint32    terminal_width_pixels       (0)
uint32    terminal_height_pixels      (0)
```

Сервер виконує виклик `ioctl(master_fd, TIOCSWINSZ, &ws)` на майстер-дескрипторі PTY, що змушує ядро згенерувати сигнал `SIGWINCH` процесам сесії.

### 7. Повернення коду завершення процесу ("exit-status")

Надсилається сервером клієнту після завершення дочірнього процесу:

```
string    "exit-status"
boolean   FALSE
uint32    exit_status                 (код повернення процесу: 0 при успіху, 1-255 при помилці)
```

### 8. Завершення через сигнал ядра ("exit-signal")

Надсилається, якщо дочірній процес було аварійно вбито неперехопленим сигналом ядра:

```
string    "exit-signal"
boolean   FALSE
string    signal_name                 (назва сигналу без "SIG": "KILL", "SEGV", "TERM", "ABRT")
boolean   core_dumped                 (TRUE, якщо ядро створило дамп пам'яті coredump)
string    error_message               (текстовий опис помилки людинозрозумілою мовою)
string    language_tag                (мовний тег за стандартом BCP 47, наприклад "uk" або "")
```

## Таблиця конфігураційних параметрів сеансу OpenSSH

### Параметри клієнта (`~/.ssh/config` або `/etc/ssh/ssh_config`)

| Директива | Типове значення | Опис інженерної поведінки |
|---|---|---|
| `RequestTTY` | `auto` | Керує виділенням віддаленого PTY: `no` (ніколи не виділяти), `yes` (виділяти завжди), `force` (виділяти навіть без локального tty), `auto` (виділяти лише для інтерактивного сеансу без вказаної команди). |
| `SendEnv` | `LANG LC_*` | Перелік змінних середовища клієнта, які запитуватимуться для передачі на сервер через запит `env`. Підтримує маски (`LC_*`). |
| `SetEnv` | *(порожньо)* | Дозволяє явно визначити пари `FOO=bar`, які клієнт передасть на віддалений сервер безпосередньо. |
| `ServerAliveInterval` | `0` (вимкнено) | Інтервал у секундах між надсиланням клієнтом службових пакетів перевірки зв'язку (`keepalive@openssh.com`) через зашифрований транспортний рівень. |
| `ServerAliveCountMax` | `3` | Кількість поспіль непідтверджених запитів `ServerAliveInterval`, після яких клієнт фіксує обрив зв'язку та аварійно завершує сеанс. |
| `EscapeChar` | `~` | Визначає керівний символ ескейп-послідовностей. Значення `none` повністю вимикає обробку ескейпів (прозорий двійковий режим). |
| `SessionType` | `default` | Дозволяє обмежити призначення з'єднання: `default` (стандартний сеанс), `subsystem` (тільки підсистема), `none` (блокувати виділення сеансу, застосовується для суто тунельних з'єднань). |

### Параметри сервера (`/etc/ssh/sshd_config`)

| Директива | Типове значення | Опис інженерної поведінки |
|---|---|---|
| `AcceptEnv` | `LANG LC_*` | Білий список імен змінних середовища, які сервер `sshd` дозволяє імпортувати від клієнта у простір змінних дочірньої оболонки. |
| `ClientAliveInterval` | `0` (вимкнено) | Інтервал у секундах, через який сервер надсилає клієнту криптографічний запит `keepalive@openssh.com` для перевірки доступності клієнтського вузла. |
| `ClientAliveCountMax` | `3` | Кількість втрачених відповідей клієнта, після яких `sshd` примусово надсилає сигнал `SIGHUP` сесії та закриває TCP-з'єднання. |
| `PermitTTY` | `yes` | Дозволяє або забороняє виділення псевдотерміналів (`pty-req`). При значенні `no` користувач може запускати лише неінтерактивні команди або прокидати порти. |
| `PermitUserEnvironment` | `no` | Дозволяє або забороняє демону `sshd` зчитувати файл `~/.ssh/environment` під час входу користувача. За замовчуванням вимкнено з міркувань безпеки. |

## Практична діагностика та простеження пакетів каналу

Для інженерного аналізу та налагодження життєвого циклу каналу `session` клієнт OpenSSH надає режим детального діагностичного протоколювання (прапорці `-v`, `-vv`, `-vvv`).

При запуску клієнта з максимальним рівнем деталізації (`ssh -vvv user@server`):
1. **Транспортний шар:**
   ```
   debug1: kex: algorithm: curve25519-sha256
   debug1: kex: host key algorithm: ssh-ed25519
   debug1: kex: server->client cipher: chacha20-poly1305@openssh.com
   debug1: SSH2_MSG_NEWKEYS sent
   debug1: SSH2_MSG_NEWKEYS received
   ```
2. **Автентифікаційний шар:**
   ```
   debug1: Authentications that can continue: publickey,password
   debug1: Offering public key: /home/user/.ssh/id_ed25519 ED25519 ...
   debug1: Server accepts key: /home/user/.ssh/id_ed25519 ED25519 ...
   debug1: Authentication succeeded (publickey).
   ```
3. **Канальний шар та виділення PTY:**
   ```
   debug1: channel 0: new [client-session]
   debug1: Requesting no-more-sessions@openssh.com
   debug1: Entering interactive session.
   debug1: Sending environment.
   debug1: channel 0: setting env LANG = "uk_UA.UTF-8"
   debug1: Sending window change: 120 columns, 40 rows
   debug1: channel 0: request pty-req confirm 1
   debug1: channel 0: request shell confirm 1
   debug2: channel 0: rcvd adjust 2097152
   ```

Журнал наочно демонструє сувору послідовність кроків: спочатку повна фіксація транспортного криптографічного контексту (`SSH2_MSG_NEWKEYS`), потім підтвердження автентичності користувача за відкритим ключем, і лише після цього — відкриття логічного каналу 0 (`client-session`), передача змінних середовища `LANG`, запит виділення `pty-req` та старт реєстраційного процесу `shell`.
