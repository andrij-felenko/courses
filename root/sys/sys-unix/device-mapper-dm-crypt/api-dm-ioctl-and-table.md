# 📋 Специфікація таблиць Device Mapper та IOCTL

Взаємодія між простором користувача та ядром у підсистемі Device Mapper відбувається через спеціальний символьний пристрій `/dev/mapper/control` за допомогою системного виклику `ioctl`. Далі — точні структури даних із `<linux/dm-ioctl.h>` і формат текстових таблиць відображення для основних цільових драйверів (targets): саме ці поля й рядки треба заповнити, щоб віртуальний пристрій узагалі з'явився.

## Системний інтерфейс /dev/mapper/control та узгодження версій

Пристрій `/dev/mapper/control` слугує єдиною точкою входу для керування віртуальними блоковими пристроями в Linux. Будь-яка високорівнева команда (створення тома, завантаження нової таблиці секторів, заморожування уводу-виводу чи вилучення пристрою) перетворюється утилітами `lvm2`, `cryptsetup` чи `dmsetup` на послідовність викликів `ioctl` над цим файловим дескриптором.

Першим кроком при відкритті пристрою управління завжди є узгодження версій API між бібліотекою простору користувача (`libdevmapper`) та модулем ядра `dm-mod`. Програма надсилає заповнену структуру зі вказанням власної версії у полі `version`, після чого ядро вписує в те саме поле свою поточну версію. Звіряються два числа з трьох. **Старший** (major) номер має збігтися точно. **Молодший** (minor) не може перевищувати той, який знає ядро: старіше ядро не вміє того, чого просить новіша бібліотека. Порушення будь-якої з цих двох умов — і виклик відхиляється з `EINVAL`, ще до розбору решти буфера. Патч-рівень ядро не звіряє взагалі: воно просто вписує свій, щоб бібліотека знала, з чим має справу.

Основні коди команд `ioctl` (визначені в системному заголовку `<linux/dm-ioctl.h>`):
- `DM_DEV_CREATE` — створює новий порожній віртуальний блоковий пристрій у пам'яті ядра з унікальним іменем.
- `DM_TABLE_LOAD` — завантажує нову таблицю відображення секторів у неактивний слот (*inactive slot*) пристрою.
- `DM_DEV_SUSPEND` — одна команда на дві протилежні дії, і вибирає між ними прапорець `DM_SUSPEND_FLAG` у полі `flags`. Прапорець виставлено — обробку нових I/O запитів призупинено (чергу `bio` заморожено). Прапорець знято — ядро переносить неактивну таблицю в активні, знищує стару й відновлює обробку. Окремої команди `DM_DEV_RESUME` в заголовку **немає**.
- `DM_DEV_REMOVE` — вилучає віртуальний пристрій із ядра після закриття всіх відкритих дескрипторів.
- `DM_TABLE_STATUS` — запитує поточний стан, лічильники помилок та конфігурацію секторів активного пристрою.

При виконанні гарячої заміни конфігурації утиліти дотримуються суворого порядку викликів. Спочатку `DM_TABLE_LOAD` завантажує нову таблицю у неактивний слот пристрою. Потім `DM_DEV_SUSPEND` із виставленим `DM_SUSPEND_FLAG` заморожує I/O. І нарешті той самий `DM_DEV_SUSPEND` зі знятим прапорцем перемикає покажчик активної таблиці й розблоковує виконання запитів — жоден `bio` при цьому не губиться.

## Текстовий синтаксис таблиць відображення

Утиліта `dmsetup` використовує зручний текстовий формат опису таблиць секторів. Кожен рядок конфігурує один діапазон секторів віртуального пристрою і має загальний шаблон:

```text
<start_sector> <num_sectors> <target_name> <target_params...>
```

### 1. Target linear (лінійне склеювання секторів)

Драйвер `linear` виконує пряму трансляцію секторів віртуального пристрою на сектори реального диска-носія зі вказаним зсувом.

**Формат аргументів:**
```text
<device_path_or_maj:min> <offset_sector>
```

**Приклад мультидискової конфігурації:**
```text
0 2097152 linear /dev/sda1 2048
2097152 4194304 linear /dev/sdb1 0
```
*Пояснення:* Перший ГіБ даних (2097152 сектори) адресується на пристрій `/dev/sda1` починаючи зі зсуву 2048 секторів (1 МіБ від початку диска для вирівнювання). Наступні 2 ГіБ даних прозоро адресуються на початок пристрою `/dev/sdb1`.

### 2. Target striped (RAID0 смугування)

Драйвер `striped` розбиває потік I/O запитів на однакові порції (страйпи) і розподіляє їх між кількома фізичними дисками паралельно.

**Формат аргументів:**
```text
<num_stripes> <chunk_size_sectors> <dev1> <offset1> <dev2> <offset2> ...
```

**Приклад конфігурації:**
```text
0 8388608 striped 2 128 /dev/sda2 0 /dev/sdb2 0
```
*Пояснення:* Віртуальний пристрій обсягом 4 ГіБ смугує дані між пристроями `/dev/sda2` та `/dev/sdb2`. Розмір порції (chunk size) становить 128 секторів (64 КіБ).

### 3. Target crypt (Шифрування dm-crypt)

Драйвер `crypt` перехоплює кожну структуру `bio` і здійснює прозоре посекторне шифрування та розшифрування за допомогою Kernel Crypto API.

**Формат аргументів:**
```text
<cipher> <key> <iv_offset> <device_path> <offset_sector> [<num_optional_args> <optional_arg1> ...]
```

**Деталізація параметрів:**
- `<cipher>` — специфікація шифру у форматі `алгоритм-режим_шифрування-режим_iv` (наприклад `aes-xts-plain64` або `aes-cbc-essiv:sha256`).
- `<key>` — шістнадцятковий (hex) рядок мастер-ключа або посилання на ключ у ключнику ядра у форматі `:<розмір_ключа>:logon:<опис>` (тоді сам ключ у таблиці не з'являється зовсім).
- `<iv_offset>` — базове число, яке додається до номера фізичного сектора при обчисленні вектора ініціалізації IV (зазвичай `0`).
- `<device_path>` — шлях до пристрою-носія зашифрованого корисного навантаження (payload).
- `<offset_sector>` — зсув у секторах на пристрої-носії до початку зашифрованого payload (пропускає заголовок LUKS).
- `[optional_args]` — додаткові прапорці налаштування продуктивності ядра:
  - `allow_discards` — дозволяє проходження команд TRIM/DISCARD до SSD.
  - `same_cpu_crypt` — примусово виконує шифрування на тому ж ядрі CPU, яке ініціювало I/O запит.
  - `submit_from_crypt_cpus` — відправляє зашифровані `bio` запити на диск безпосередньо з потоків обробки `kcryptd`.
  - `no_read_workqueue` / `no_write_workqueue` — обходить черги потоків `kcryptd` для надшвидких NVMe накопичувачів.

**Приклад повного рядка dm-crypt:**
```text
0 4096000 crypt aes-xts-plain64 000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f202122232425262728292a2b2c2d2e2f303132333435363738393a3b3c3d3e3f 0 /dev/nvme0n1p2 32768 1 allow_discards
```
*Пояснення:* ключ тут — 128 hex-символів, тобто 64 байти: XTS бере два ключі по 256 біт, тож це AES-256-XTS. Зсув `32768` секторів — 16 МіБ, типове місце початку payload одразу за заголовком LUKS2.

При побудові власного інструментарію управління блоковими пристроями рекомендується використовувати бібліотеку `libdevmapper` замість прямих викликів `ioctl`, оскільки вона гарантує коректне вирівнювання полів структури `struct dm_ioctl` та безпечне обнулення криптографічних ключів у буферах пам'яті.
