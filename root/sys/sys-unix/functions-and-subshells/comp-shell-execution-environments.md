# 🔌 Порівняння середовищ виконання: Bash, Dash, Ksh93 та Zsh

Розробка переносних та високоефективних системних сценаріїв у Unix вимагає глибокого розуміння того, як різні реалізації командних оболонок керують процесами, ізолюють пам'ять та обробляють конвеєри. Попри те, що всі сучасні оболонки декларують відповідність базовому стандарту POSIX.1-2017, їхня внутрішня архітектура щодо підоболонок, областей видимості та оптимізацій суттєво відрізняється.

---

## 1. Виконання останнього елемента конвеєра

Головна архітектурна відмінність між оболонками полягає у виборі процесу, який виконує праву (останню) ланку конвеєра `cmd1 | cmd2 | ... | cmdN`.

```text
Bash (дефолт) / Dash:    [cmd1 (subshell)] ──► [cmd2 (subshell)] ──► [cmdN (subshell)]
Ksh93 / Zsh:             [cmd1 (subshell)] ──► [cmd2 (subshell)] ──► [cmdN (in-process)]
Bash (shopt -s lastpipe):[cmd1 (subshell)] ──► [cmd2 (subshell)] ──► [cmdN (in-process)]
```

### Поведінка у різних сімействах оболонок

1. **Dash (Debian Almquist Shell) та базовий POSIX sh**:
   Усі елементи конвеєра без винятку виконуються у форкнутих дочірніх процесах. Будь-які модифікації змінних, зміна робочого каталогу через `cd` або відкриття нових дескрипторів усередині циклу, підключеного через конвеєр, безповоротно втрачаються після виходу з циклу. Увімкнути виконання останнього елемента в поточному процесі неможливо — стандарт POSIX прямо дозволяє виконувати кожен елемент конвеєра в окремому середовищі виконання.

2. **KornShell (`ksh93`) та Zsh**:
   В обох оболонках остання ланка конвеєра за замовчуванням виконується безпосередньо в батьківському процесі інтерпретатора. Попередні ланки форкаються у підоболонки, але остання команда зчитує вхідні дані через канал `pipe` in-process. Завдяки цьому конструкція `cat file.txt | while read -r line; do counter=$((counter + 1)); done` природно зберігає значення змінної `$counter` після завершення циклу.

3. **GNU Bash**:
   За замовчуванням Bash суворо слідує поведінці Bourne shell: усі ланки конвеєра запускаються як окремі дочірні процеси. Це зумовлено підтримкою керування завданнями (Job Control), де кожному конвеєру призначається власний ідентифікатор групи процесів (PGID). Проте починаючи з версії Bash 4.2 додано опцію `shopt -s lastpipe`, яка активує виконання останнього елемента in-process за умови, що Job Control вимкнено (що є типовим для неінтерактивних скриптів).

## 2. Оптимізація створення підоболонок: реальний `fork()` проти Virtual Subshell

Коли оболонка зустрічає команду у круглих дужках `( command )` або підстановку команди `$( command )`, традиційний підхід вимагає системного виклику `fork()` (або `clone()`) для створення нового дочірнього процесу в таблиці процесів ядра.

```text
Традиційна підоболонка (Bash / Dash):
  Поточний процес ──► fork() ──► Дочірній процес (нові сторінки, новий PID, таблиця дескрипторів)

Віртуальна підоболонка (Ksh93 / Zsh):
  Поточний процес ──► Журнал транзакцій ──► Виконання in-process ──► Відкат пам'яті (без fork!)
```

### Віртуальні підоболонки у KornShell (`ksh93`)

`ksh93` реалізує передову оптимізацію — **віртуальні підоболонки (fork-less virtual subshells)**. Інтерпретатор уникає виклику `fork()`, якщо блок у дужках не містить операцій, що змінюють глобальний стан операційної системи (наприклад, запуск фонових процесів `&` або виклик зовнішніх бінарних файлів).

Внутрішній алгоритм віртуальної підоболонки:
- Перед входом у блок інтерпретатор створює точку збереження (savepoint) у стеку транзакцій.
- Усі операції модифікації змінних та локальних перенаправлень дескрипторів записуються у журнал змін.
- Команди блоку виконуються безпосередньо процесором в адресному просторі батька з максимальною швидкістю.
- При виході з дужок оболонка автоматично застосовує журнал відкату, повертаючи всі змінні та дескриптори до початкового стану.
- Реальний виклик `fork()` виконується ліниво (lazy fork) лише тоді, коли віртуальна підоболонка намагається викликати зовнішню програму або створити групу процесів.

Завдяки цьому виконання блоків `( x=1; y=2 )` у `ksh93` працює у 30–50 разів швидше, ніж у `bash` або `dash`.

### Реальний `fork()` у Bash та Dash

У `bash` та `dash` будь-яка конструкція в круглих дужках `( ... )` гарантовано викликає системний виклик `fork()`. Це забезпечує абсолютну ізоляцію пам'яті на рівні сторінок пам'яті ядра Linux через механізм Copy-on-Write (COW). Проте копіювання таблиць сторінок пам'яті процесора створює відчутні накладні витрати часу, особливо у скриптах, які споживають сотні мегабайтів пам'яті.

## 3. Моделі області видимості змінних: Dynamic vs Lexical

Оболонки застосовують принципово різні механізми пошуку та зв'язування імен змінних у функціях.

### Динамічна видимість (Bash, Dash, BusyBox Ash)

Усі локальні змінні, оголошені за допомогою `local` або `declare`, розміщуються у динамічному стеку викликів. Будь-яка викликана дочірня функція бачить локальні змінні функції, яка її викликала.

```sh
# Поведінка у Bash та Dash
helper() {
    echo "helper reads x: $x"  # Бачить 'parent_val', якщо викликана з parent!
}

parent() {
    local x="parent_val"
    helper
}

x="global_val"
parent
```
Вивід у Bash/Dash: `helper reads x: parent_val`. Дочірня функція `helper` не має власного лексичного захисту і неявно залежить від контексту виклику. Якщо викликач не оголосив `x`, функція звернеться до глобальної змінної.

### Статична лексична видимість (Ksh93 синтаксис `function`)

У `ksh93` при використанні синтаксису `function name { ... }` реалізовано справжнє статичне лексичне замикання:

```ksh
# Поведінка у Ksh93 (function syntax)
function helper {
    echo "helper reads x: $x"  # Бачить ВИКЛЮЧНО глобальну 'x'!
}

function parent {
    typeset x="parent_val"
    helper
}

x="global_val"
parent
```
Вивід у Ksh93: `helper reads x: global_val`. Функція `helper` повністю ізольована від змінних `parent`, що відповідає поведінці функцій у таких мовах, як C, Python або Rust.

## 4. Ізоляція обробників сигналів (Trap Scoping)

Поведінка обробників сигналів (`trap`) при вході у функції суттєво відрізняється між оболонками:

1. **POSIX sh та стандартний Bash**:
   Обробники сигналів є глобальними для всього процесу. Якщо функція встановлює `trap 'rm -f /tmp/lock' EXIT`, цей обробник перезаписує глобальну пастку скрипту і спрацює лише при повному завершенні процесу оболонки, а не при виході з функції.
2. **KornShell (`ksh93`)**:
   У функціях із синтаксисом `function name` пастки `trap` є локальними для фрейму функції. Обробник `trap ... EXIT` виконується автоматично в момент завершення функції через `return`, після чого відновлюється попередня пастка викликача.
3. **Zsh**:
   Підтримує спеціальну опцію `setopt localtraps`. Якщо опцію увімкнено, будь-які зміни `trap` усередині функції автоматично відкочуються до початкових значень при виході з фрейму.

## 5. Порівняльна матриця можливостей оболонок

| Властивість / Механізм | GNU Bash 5.2 | Dash 0.5.12 (POSIX) | Ksh93u+m | Zsh 5.9 |
|---|---|---|---|---|
| **Оголошення локальних змінних** | `local`, `declare`, `typeset` | `local` (розширення) | `typeset` | `local`, `typeset`, `declare` |
| **Модель області видимості** | Динамічна (Dynamic) | Динамічна (Dynamic) | Лексична (`function`) / Динамічна (`name()`) | Динамічна за замовчуванням |
| **Масиви (індексовані та асоціативні)** | Так (`declare -a`, `declare -A`) | Ні (лише позиційні `$1..$n`) | Так (`typeset -a`, `typeset -A`) | Так (1-індексовані за замовчуванням) |
| **Посилання за іменем (namerefs)** | Так (`declare -n ref=var`) | Ні | Так (`typeset -n ref=var`) | Ні (використовує `${(P)var}`) |
| **Спеціальна змінна реального PID** | `$BASHPID` | Відсутня (лише `$$`) | `.sh.pid` | `$$` (змінюється у subshell) |
| **Лічильник глибини підоболонок** | `$BASH_SUBSHELL` | Відсутня | `.sh.subshell` | `$ZSH_SUBSHELL` |
| **Стек викликів для налагодження** | `$FUNCNAME`, `$BASH_SOURCE` | Відсутній | `.sh.fun`, `.sh.file` | `$funcstack`, `$functrace` |
| **Локалізація обробників сигналів (trap)** | Глобальні (якщо не `set -T`) | Завжди глобальні | Локальні у `function name` | Опція `setopt localtraps` |
| **Виконання останнього кроку пайпу** | Subshell (in-process з `lastpipe`) | Завжди Subshell | Завжди in-process | Завжди in-process |
| **Накладні витрати на виклик функції** | ~1.5 мкс | ~0.4 мкс (дуже швидка) | ~0.8 мкс | ~1.2 мкс |
| **Накладні витрати на виклик `( )`** | ~800 мкс (через `fork`) | ~350 мкс (через `fork`) | ~12 мкс (Virtual subshell) | ~400 мкс (через `fork`) |

## 6. Практичні рекомендації щодо переносності

1. **Для строгої переносності на чистий POSIX `/bin/sh` (Debian Dash, Alpine BusyBox, FreeBSD sh)**:
   - Не використовуйте масиви, конструкції `declare -n` та синтаксис `function fname`.
   - Завжди розділяйте оголошення локальної змінної та присвоєння результату підстановки команди:
     ```sh
     # Небезпечно (маскує помилку підстановки):
     local output=$(faulty_command)
     
     # Безпечно:
     local output
     output=$(faulty_command) || return 1
     ```
   - Замість конвеєрів передавайте дані у цикли через перенаправлення вхідного потоку: `while read -r line; do ...; done < input.txt`.

2. **Для високопродуктивних скриптів у Bash (4.2+)**:
   - Завжди вмикайте `shopt -s lastpipe` у неінтерактивних скриптах, які агрегують статистику з конвеєрів.
   - Застосовуйте групування у фігурних дужках `{ cmd; }` замість круглих дужок `( cmd )` для групових операцій вводу-виводу, щоб уникнути сотень мікросекунд накладних витрат на системний виклик `fork()`.
