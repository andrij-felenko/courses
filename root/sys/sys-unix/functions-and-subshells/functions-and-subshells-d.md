Розглянемо типовий сценарій обробки системних логів, з яким стикається кожен системний інженер. Скрипт повинен підрахувати кількість записів із помилками, прочитавши файл через конвеєр:

```sh
#!/bin/sh
error_count=0

cat /var/log/nginx/error.log | while read -r line; do
    case "$line" in
        *"[error]"*) error_count=$((error_count + 1)) ;;
    esac
done

echo "Total errors found: $error_count"
```

Скрипт успішно обробляє гігабайтний файл, цикл чесно виконує мільйон ітерацій, але фінальний рядок незмінно друкує: `Total errors found: 0`. Жодної синтаксичної помилки в коді немає, арифметика працює бездоганно, проте змінна `$error_count` після завершення циклу виявляється незайманою.

Причина цієї поведінки криється у фундаментальній відмінності між процедурними викликами у звичайних мовах програмування та моделлю процесів операційної системи Unix. Оболонка Unix не є монолітним інтерпретатором: вона делегує паралелізм та ізоляцію завдань безпосередньо ядру операційної системи. Кожен елемент конвеєра та кожна конструкція в круглих дужках перетворюються на окремий системний процес — **підоболонку (subshell)**, чия віртуальна пам'ять надійно відрізана від батьківської програми. Натомість **функції** оболонки виконуються всередині того самого адресного простору, створюючи інший виклик: за замовчуванням усі їхні змінні є глобальними та можуть непомітно спотворити стан усієї програми.

## Анатомія функцій у POSIX Shell та Bash

Функція в командній оболонці — це іменований блок команд, який інтерпретатор зчитує в пам'ять під час парсингу скрипту і виконує безпосередньо в адресному просторі поточного процесу. На відміну від зовнішніх бінарних програм або окремих скриптів у каталогах `PATH`, виклик функції не створює нових процесів ядра і не потребує системних викликів `fork()` та `execve()`.

### Синтаксис оголошення та збереження в пам'яті

Стандарт POSIX.1-2017 визначає єдиний переносний синтаксис оголошення функції:

```sh
fname() compound_command [redirection]
```

Найчастіше як `compound_command` використовують блок у фігурних дужках `{ ...; }`, проте стандарт дозволяє будь-яку складену команду:

```sh
# Стандартна POSIX-форма
calculate_total() {
    local_sum=$(( $1 + $2 ))
    echo "$local_sum"
}

# Допустима форма: тіло функції як підоболонка в круглих дужках
isolated_work() (
    cd /tmp || exit 1
    rm -f *.cache
)

# Функція з постійним перенаправленням потоку виводу
log_notice() {
    printf "[%s] %s\n" "$(date +%T)" "$*"
} >> /var/log/service.log 2>&1
```

У Bash та KornShell існує альтернативний синтаксис із ключовим словом `function`: `function fname { ... }` або `function fname() { ... }`. Повна історія того, як виникали ці синтаксичні гілки та чому вони призвели до розколу моделей видимості, розглянута у матеріалі [📜 Відсутність функцій у V7 sh до розколу між лексичною та динамічною видимістю в ksh93 та Bash](root:sys-unix/functions-and-subshells/hist-subshell-and-scoping-evolution.md).

Коли інтерпретатор зустрічає визначення функції, він парсить її текст в абстрактне синтаксичне дерево (AST) і розміщує структуру в хеш-таблиці функцій процесу. При наступному введенні слова `calculate_total` оболонка виконує пошук команди за суворим пріоритетом:
1. **Спеціальні вбудовані команди** (`break`, `: `, `eval`, `exec`, `exit`, `return`, `set`, `shift`, `trap`).
2. **Функції оболонки** (користувацькі та завантажені бібліотечні функції).
3. **Звичайні вбудовані команди** (`cd`, `echo`, `read`, `kill`).
4. **Зовнішні виконувані файли** у каталогах змінної `$PATH`.

Завдяки цьому функція може підміняти поведінку зовнішніх утиліт або системних команд. Якщо ви оголосите функцію `cd() { builtin cd "$@" && ls; }`, оболонка викликатиме саме вашу функцію, а для звернення до оригінальної команди доведеться явно писати `builtin cd`.

### Стек позиційних параметрів

При вході у функцію оболонка створює новий локальний фрейм для позиційних аргументів:
- Змінні `$1`, `$2`, ..., `$9`, `${10}` набувають значень аргументів, переданих функції під час виклику.
- Змінна `$#` показує кількість аргументів, переданих конкретно цій функції.
- Спеціальний масив `"$@"` містить список аргументів поточної функції.
- Змінна `$0` **не змінюється**: вона продовжує вказувати на ім'я самого скрипту або назву поточної оболонки.

```sh
demonstrate_args() {
    echo "Function \$0 is: $0"
    echo "Function \$# is: $#"
    echo "Function \$1 is: $1"
    shift
    echo "After shift, \$1 is: $1"
}

# Виклик:
demonstrate_args "alpha" "beta" "gamma"
```

Коли інтерпретатор заходить у тіло функції, він зберігає попередній масив аргументів скрипту у внутрішньому стеку. Команда `shift` всередині функції зсуває виключно аргументи поточної функції. Щойно функція завершує роботу, оболонка відновлює попередній масив аргументів викликача.

### Повернення статусу: `return` проти `exit`

Функції оболонки принципово відрізняються від функцій високорівневих мов: вони не можуть повертати довільні об'єкти, рядки чи масиви через інструкцію повернення. Єдиним значенням, яке повертає функція, є **числовий код завершення (exit status)** в діапазоні від `0` до `255`.

```sh
validate_user() {
    username="$1"
    [ -z "$username" ] && return 2       # Неприпустимий аргумент
    id "$username" >/dev/null 2>&1 || return 1 # Користувача не існує
    return 0                             # Успіх
}
```

- **`return [N]`**: негайно припиняє виконання поточної функції та повертає керування у точку виклику. Статус `$?` встановлюється у значення `N`. Якщо `N` не вказано, `$?` дорівнює коду виходу останньої виконаної у функції команди.
- **`exit [N]`**: **вбиває весь процес оболонки**. Якщо викликати `exit 1` всередині вкладеної функції, завершиться не функція, а весь ваш скрипт разом із основним процесом.

Якщо функції потрібно повернути текстові дані або складну структуру, застосовують один із двох шаблонів:
1. **Вивід у стандартний потік (stdout)** із перехопленням через підстановку команди: `result=$(calculate_data arg1)`. Цей підхід створює підоболонку і канал `pipe`.
2. **Запис у змінну за домовленістю** або через посилання за іменем (`declare -n` у Bash 4.3+).

## Область видимості змінних: Global vs Dynamic Scoping

Найнебезпечніша пастка під час написання функцій у командних оболонках — це глобальна область видимості за замовчуванням.

```sh
process_files() {
    for i in /tmp/*.dat; do
        format_file "$i"
    done
}

format_file() {
    # Помилка: 'i' не оголошено локальною!
    for i in 1 2 3; do
        printf "."
    done
}
```

У цьому прикладі виклик `format_file` всередині першої ж ітерації `process_files` перезапише змінну `i` значенням `3`. Зовнішній цикл `for i in /tmp/*.dat` отримає спотворений лічильник і передчасно завершить обробку.

### Ключове слово `local` та динамічна область видимості

Для ізоляції змінних у функціях використовується команда `local` (або `declare` / `typeset` у Bash):

```sh
safe_format_file() {
    local i
    local filename="$1"
    local timestamp
    timestamp=$(date +%s)
    
    for i in 1 2 3; do
        printf "."
    done
}
```

Проте область видимості у Bash, Dash та Almquist shell є не статичною (лексичною), а **динамічною (dynamic scoping)**. 

У мовах зі статичною областю видимості (C, C++, Rust, Python) область доступності змінної визначається місцем її оголошення у тексті програми. У моделі динамічної видимості доступність змінної визначається **стеком викликів у рантаймі**.

![Стек викликів та динамічна область видимості у Bash](/root/sys/sys-unix/functions-and-subshells/img/dynamic-scoping-stack.svg)
*Стек викликів та динамічна область видимості у Bash: локальні змінні outer_func залишаються видимими для дочірньої функції inner_func через пошук змінних у стеку викликів.*

Якщо функція `outer()` оголошує `local token="secret"`, а потім викликає функцію `inner()`, то функція `inner()` **бачить і може змінювати** змінну `$token`, навіть якщо сама її не оголошувала!

```sh
inner_func() {
    # 'token' не оголошено тут як local
    echo "inner_func reads token: $token"
    token="modified_by_inner" # Змінює локальну змінну outer_func!
}

outer_func() {
    local token="secret_auth_key"
    inner_func
    echo "outer_func token is now: $token"
}

token="global_default"
outer_func
echo "global token is: $token"
```

Результат виконання цього скрипту:
```text
inner_func reads token: secret_auth_key
outer_func token is now: modified_by_inner
global token is: global_default
```

Функція `inner_func` під час читання `$token` перевіряє власний фрейм локальних змінних. Не знайшовши запису, інтерпретатор спускається на один рівень нижче по стеку викликів до фрейму `outer_func`, де знаходить локальну змінну `token`. Глобальна змінна `token="global_default"` лишається непошкодженою.

Порівняння того, як ця поведінка відрізняється від лексичної моделі KornShell (`ksh93`) та середовища Zsh, наведено у довіднику [🔌 Порівняння виконання конвеєрів та моделей видимості в Bash, Dash, Ksh93 та Zsh](root:sys-unix/functions-and-subshells/comp-shell-execution-environments.md).

### Передача масивів та посилання за іменем (`declare -n`)

Оскільки позиційні параметри `$1..$N` передаються виключно як плаский список рядків, передача масивів у функції у ранніх версіях оболонок вимагала небезпечного розгортання через `eval` або передачі через змінні оточення. Починаючи з Bash 4.3 з'явився механізм **посилань за іменем (namerefs)**:

```sh
# Передача масиву за посиланням
append_timestamp() {
    local -n target_array="$1" # target_array стає аліасом змінної, переданої першим аргументом
    target_array+=("$(date +%T)")
}

my_log_entries=("Server started" "Port 8080 open")
append_timestamp my_log_entries

# Масив my_log_entries містить три елементи!
printf "Entry: %s\n" "${my_log_entries[@]}"
```

Проте динамічна видимість створює небезпечну пастку колізії імен при використанні `declare -n`: якщо ім'я локальної змінної-посилання збігається з ім'ям змінної, що передається ззовні (наприклад, функція оголошує `local -n var="$1"`, а користувач викликає `func var`), виникає **циклічне посилання (circular reference)**. Bash виявляє таку помилку під час виконання і завершує вираз із повідомленням `warning: var: circular name reference`. Для запобігання цій проблемі в бібліотечних функціях імена посилань префіксують унікальними назвами (наприклад, `__lib_ref_target`).

### Рекурсія, ліміти викликів та змінна `FUNCNEST`

Оболонка підтримує рекурсивний виклик функцій. Проте кожен виклик функції розміщує новий фрейм позиційних параметрів та локальних змінних у пам'яті процесу. Безконтрольна нескінченна рекурсія призводить до вичерпання пам'яті інтерпретатора або аварійного завершення через падіння стека (Stack Overflow).

Для захисту від нескінченної рекурсії у Bash передбачено спеціальну змінну **`FUNCNEST`**:

```sh
# Обмежуємо максимальну глибину рекурсії 50 викликами
FUNCNEST=50

infinite_recursion() {
    infinite_recursion
}

infinite_recursion
# Виведе: bash: infinite_recursion: maximum function nesting level exceeded (50)
```

Встановлення `FUNCNEST` є обов'язковою практикою у високонадійних скриптах, що обробляють рекурсивні дерева файлів або парсять вкладені структури конфігурацій.

### Експорт функцій через оточення та феномен Shellshock

Унікальною властивістю GNU Bash є можливість експортувати визначення функцій у дочірні процеси за допомогою команди `export -f func_name`.

```sh
my_utility() {
    echo "Running internal utility on host: $(hostname)"
}
export -f my_utility

# Дочірній процес bash отримує функцію автоматично:
bash -c 'my_utility'
```

На рівні операційної системи Linux змінне оточення процесу (`envp[]`) є масивом простих рядків формату `NAME=VALUE`. Щоб передати складне синтаксичне дерево функції крізь системний виклик `execve()`, Bash серіалізує тіло функції у спеціальний рядок оточення виду `BASH_FUNC_my_utility%%=() { echo ...; }`. Коли новий екземпляр `bash` ініціалізується, він сканує змінні оточення і, знаходячи такий запис, автоматично парсить і виконує його для відновлення функції в пам'яті.

Саме цей механізм став джерелом критичної вразливості **Shellshock (CVE-2014-6271)**: через помилку в парсері інтерпретатор виконував будь-які додаткові команди, записані після закриваючої фігурної дужки тіла функції у змінній оточення, що дозволяло зловмисникам виконувати довільний код через веб-сервери або SSH-сесії. Сучасні версії Bash містять надійні перевірки імен та виключають автопарсинг некоректно оформлених блоків.

### Інспекція стека викликів: `FUNCNAME`, `BASH_SOURCE`, `BASH_LINENO`

Для діагностики складних системних скриптів та побудови трасувальників помилок Bash надає трійку спеціальних паралельних масивів:
- **`${FUNCNAME[@]}`**: масив імен функцій у поточному стеку. Елемент `${FUNCNAME[0]}` — поточна функція, `${FUNCNAME[1]}` — функція, яка її викликала, `${FUNCNAME[n]}` — `main`.
- **`${BASH_SOURCE[@]}`**: шляхи до файлів, у яких було викликано відповідні функції.
- **`${BASH_LINENO[@]}`**: номери рядків у вихідних файлах, де здійснено кожен виклик.

```sh
print_stack_trace() {
    local frame=0
    echo "=== Stack Traceback (most recent call first) ==="
    while [ $frame -lt ${#FUNCNAME[@]} ]; do
        local func="${FUNCNAME[$frame]}"
        local file="${BASH_SOURCE[$frame+1]}"
        local line="${BASH_LINENO[$frame]}"
        [ -z "$file" ] && file="${BASH_SOURCE[$frame]}"
        printf "  [%d] %s() at %s:%d\n" "$frame" "$func" "$file" "$line"
        frame=$((frame + 1))
    done
}
```

Цей механізм дозволяє реалізувати повноцінний фреймворк журналювання помилок, який при спрацюванні `trap 'print_stack_trace' ERR` показує точне місце аварійного виходу скрипту.

## Анатомія підоболонок (Subshells)

Підоболонка — це новий, повністю ізольований дочірній процес командної оболонки, створений системним викликом `fork()` (або `clone()` у Linux) для виконання окремого фрагмента коду.

### Явні та неявні причини створення підоболонок

Інтерпретатор створює підоболонки у таких випадках:

1. **Явні круглі дужки `( commands )`**: блок коду навмисно ізолюється від поточного процесу.
2. **Конвеєри `cmd1 | cmd2 | ... | cmdN`**: у стандарті POSIX та за замовчуванням у Bash **кожна ланка конвеєра виконується в окремій підоболонці**.
3. **Підстановка команди `$(commands)` або `` `commands` ``**: запускає команди в окремому процесі, підключає його `stdout` до анонімного каналу `pipe` і повертає текст у точку розкриття.
4. **Підстановка процесу `<(commands)` або `>(commands)`**: створює дочірній процес, чий ввід або вивід підключається до FIFO-іменованого каналу або файлового дескриптора в `/dev/fd/`.
5. **Асинхронний запуск у фоні `commands &`**: створює фонову підоболонку без очікування завершення.

![Ізоляція адресного простору та спільні дескриптори при створенні підоболонки](/root/sys/sys-unix/functions-and-subshells/img/subshell-fork-cow.svg)
*Ізоляція адресного простору та спільні дескриптори при створенні підоболонки: ядро клонує віртуальну пам'ять через COW, тому модифікація змінних у дочірньому процесі не повертається у батьківську оболонку.*

### Фізика ядра: чому зміни у підоболонці зникають

Повернемося до проблеми лічильника логів на початку статті:

```sh
cat /var/log/nginx/error.log | while read -r line; do
    error_count=$((error_count + 1))
done
```

Ось що відбувається на рівні системних викликів ядра Linux:

1. Батьківський процес оболонки (PID 1000) викликає `pipe()`, створюючи дескриптори каналу.
2. Оболонка викликає `fork()` для створення першої дитини (PID 1001), яка виконує `cat /var/log/nginx/error.log` і перенаправляє `stdout` у канал.
3. Оболонка викликає `fork()` другий раз для створення другої дитини (PID 1002).
4. Процес PID 1002 отримує точну копію адресного простору батька: у його пам'яті змінна `error_count` дійсно існує і дорівнює `0`.
5. Процес PID 1002 виконує цикл `while read`, зчитує рядки з каналу і щоразу модифікує сторінку пам'яті зі змінною `error_count`. Завдяки механізму ядра **Copy-on-Write (COW)** ядро створює для процесу PID 1002 приватну фізичну копію сторінки оперативної пам'яті.
6. Коли файл закінчується, цикл завершується, і процес PID 1002 викликає системний виклик `exit(0)`.
7. **Ядро Linux повністю знищує адресний простір процесу PID 1002** разом із модифікованою сторінкою пам'яті, де зберігалося число `1000000`.
8. Батьківський процес PID 1000, який весь цей час мирно спав у виклику `waitpid()`, прокидається. Його власна сторінка оперативної пам'яті зі змінною `error_count` жодного разу не модифікувалася і все ще містить початкове значення `0`.

Ця ізоляція є залізною: процес не має жодної можливості безпосередньо змінити віртуальну пам'ять батьківського процесу.

Повний розбір практичної емуляції цього механізму через низькорівневі системні виклики на мовах C та C++ зведено у практикумі [⚙️ Практикум: емуляція підоболонок через fork() та порівняння накладних витрат у C та C++](root:sys-unix/functions-and-subshells/proj-subshell-tracer.md).

## Успадкування контексту: що саме копіюється при `fork()`

Коли оболонка розгалужується на підоболонку, новий процес не стартує «з нуля». Системний виклик `fork()` створює точний зліпок стану батька.

| Компонент стану | Доля у підоболонці (Subshell) | Механізм взаємодії |
|---|---|---|
| **Змінні оболонки** | Копіюються всі (експортовані й неекспортовані) | Ізоляція через Copy-on-Write; зміни в subshell не повертаються |
| **Функції оболонки** | Копіюються повністю | Доступні для виклику всередині subshell |
| **Файлові дескриптори** | Дублюються таблиці FD | Вказують на **ті самі Open File Descriptions** у ядрі (спільний `offset`!) |
| **Поточний каталог (CWD)** | Успадковується значення | Виклик `cd` всередині subshell не змінює каталог батька |
| **Маска створення файлів (`umask`)** | Успадковується значення | Зміна `umask` всередині subshell не впливає на батька |
| **Обмеження ресурсів (`rlimit`)** | Успадковуються повністю | Встановлення лімітів діє лише на підоболонку та її дітей |
| **Обробники сигналів (`trap`)** | Скидаються до `SIG_DFL` або `SIG_IGN` | Пастки на сигнали, перехоплені батьком, скидаються до дефолтних |

### Пастка спільних файлових дескрипторів

Хоча адресні простори пам'яті ізольовані, файлові дескриптори дочірнього процесу посилаються на ті самі структури відкритих файлів (`struct file`) у просторі ядра. Це означає, що **файловий покажчик зміщення (offset) є спільним**:

```sh
# Батько відкриває файл на читання
exec 3< /tmp/data.txt

# Підоболонка читає перший рядок через дескриптор 3
(
    read -r line_child <&3
    echo "Child read: $line_child"
)

# Батько читає наступний рядок
read -r line_parent <&3
echo "Parent read: $line_parent"

exec 3<&-
```

Оскільки підоболонка зсунула покажчик читання у спільній структурі ядра, батьківський процес прочитає саме **другий** рядок файлу, а не перший!

### Ідентифікація процесів: `$$` проти `$BASHPID`

У класичних Unix-оболонках спеціальна змінна `$$` зберігає ідентифікатор процесу (PID). Проте у стандарті POSIX закладено несподіване правило: **значення `$$` залишається незмінним у всіх підоболонках**.

```sh
echo "Parent PID: $$"
(
    echo "Subshell \$$ is: $$"         # Надрукує ТОЙ САМИЙ PID батька!
    echo "Actual kernel PID: $BASHPID" # Надрукує СПРАВЖНІЙ PID дочірнього процесу!
)
```

Змінна `$$` спеціально зафіксована для того, щоб скрипти могли створювати тимчасові файли виду `/tmp/app_$$.tmp`, не боячись, що ім'я файлу зміниться при випадковому переході у підоболонку.

Якщо вам потрібен реальний PID поточного системного процесу, у Bash використовують змінну `$BASHPID`. Крім того, змінна `$BASH_SUBSHELL` показує поточну глибину вкладеності підоболонок: `0` для основного процесу скрипту, `1` для першого рівня `( )`, `2` для вкладених дужок `(( ))` тощо.

### Обробники сигналів (Traps) та поведінка `set -e`

Взаємодія обробників сигналів `trap` із підоболонками та функціями вимагає суворого врахування трьох правил ядра та інтерпретатора:

1. **Пастки сигналів ОС (`SIGINT`, `SIGTERM`, `SIGHUP`)**:
   Якщо батьківський процес встановив спеціальний обробник на `SIGINT`, при створенні підоболонки цей сигнал скидається до стандартної системної дії `SIG_DFL` (завершення процесу). Виняток становлять сигнали, які батько явно ігнорує (`SIG_IGN`): дочірній процес успадковує стан ігнорування згідно з правилами POSIX.
2. **Пастка виходу `trap ... EXIT`**:
   Усередині функції обробник `EXIT` **не викликається** при звичайному виході через `return`. Він спрацює лише тоді, коли весь скрипт завершить роботу. Але якщо встановити `trap ... EXIT` усередині підоболонки `( )`, цей обробник виконається в момент виходу з дужок, оскільки для ядра вихід із підоболонки є повноцінним завершенням процесу!
3. **Успадкування режиму зупинки при помилках `set -e` (`errexit`)**:
   Якщо у скрипті увімкнено `set -e`, будь-яка команда, що повернула ненульовий статус, спричиняє негайний вихід. Проте всередині підстановок команд `$(cmd)` історично дія `set -e` вимикалася. Щоб поширити суворий контроль помилок на підстановки команд у сучасних версіях Bash, активують опцію `shopt -s inherit_errexit`.

Повний довідник системних змінних середовища та вбудованих інструментів наведено у матеріалі [📋 Довідник вбудованих інструментів, синтаксису функцій та змінних середовища виконання](root:sys-unix/functions-and-subshells/api-functions-and-subshells-reference.md).

## Групування у поточному процесі та збереження стану

Коли інженеру потрібно виконати кілька дій як єдиний блок, але створення підоболонки небажане через накладні витрати або потребу зберегти змінні, використовують **групування у фігурних дужках `{ ...; }`**.

```text
Круглі дужки ( command; )   ──► Створюють підоболонку (Subshell) через fork()
Фігурні дужки { command; }  ──► Групують команди в ПОТОЧНОМУ процесі (in-process)
```

### Синтаксичні правила фігурних дужок

На відміну від круглих дужок, які є спеціальними символами синтаксису оболонки, фігурна дужка `{` є зарезервованим словом. Через це діють два обов'язкові правила:
1. Після відкриваючої дужки `{` обов'язково має стояти **пробіл** або новий рядок.
2. Перед закриваючою дужкою `}` обов'язково має стояти **крапка з комою `;`** або новий рядок.

```sh
# Помилка синтаксису:
{ echo "one"; echo "two" }  # Синтаксична помилка: дужка злиплася або немає ';'

# Правильний синтаксис:
{ echo "one"; echo "two"; }
```

### Групове перенаправлення без створення процесів

Фігурні дужки дозволяють атомарно перенаправити ввід-вивід для десятка команд за один системний виклик, не викликаючи `fork()`:

```sh
generate_report() {
    {
        printf "=== SYSTEM STATUS REPORT ===\n"
        printf "Generated: %s\n" "$(date)"
        printf "Disk Usage:\n"
        df -h /
        printf "Memory Usage:\n"
        free -m
    } > /var/log/system_report.log 2>&1
}
```

Усі команди всередині блоку записують свій вивід у файл `/var/log/system_report.log`, але сам блок виконується безпосередньо в основному процесі оболонки.

## Розв'язання проблеми конвеєрів

Як подолати втрату змінних у циклах, що обробляють вивід команд? Існує три перевірених інженерних рішення.

![Порівняння виконання конвеєра: стандартний режим проти lastpipe](/root/sys/sys-unix/functions-and-subshells/img/pipeline-lastpipe-comparison.svg)
*Порівняння виконання конвеєра: у стандартному режимі остання стадія форкається в окремий subshell і втрачає стан змінних, а при опції shopt -s lastpipe вона виконується безпосередньо в батьківському процесі.*

### Варіант 1: Перенаправлення вхідного потоку у цикл (POSIX-сумісний)

Замість передачі даних через `cat file | while`, файл перенаправляють безпосередньо у цикл за допомогою оператора `<`:

```sh
#!/bin/sh
error_count=0

while read -r line; do
    case "$line" in
        *"[error]"*) error_count=$((error_count + 1)) ;;
    esac
done < /var/log/nginx/error.log

echo "Total errors found: $error_count" # Працює на 100% у будь-якому sh!
```

Оскільки цикл `while` не стоїть у конвеєрі, він виконується в поточному процесі оболонки, і змінна `$error_count` зберігає своє фінальне значення.

### Варіант 2: Підстановка процесу (Process Substitution у Bash/Zsh)

Якщо вхідні дані генеруються складною командою (наприклад, `find` або `grep`), замість каналу використовують підстановку процесу `<(...)`:

```sh
#!/bin/bash
total_bytes=0

while read -r size filename; do
    total_bytes=$((total_bytes + size))
done < <(find /data -type f -printf "%s %p\n")

echo "Total storage consumed: $total_bytes bytes"
```

Команда `find` запускається у фоновому дочірньому процесі, а цикл `while` виконується в основному процесі, зчитуючи дані з файлового дескриптора `/dev/fd/xx`.

### Варіант 3: Оптимізація `shopt -s lastpipe` (Bash 4.2+)

У GNU Bash версії 4.2 та новіших з'явилася можливість увімкнути виконання останнього елемента конвеєра в поточному процесі за допомогою опції `lastpipe`:

```sh
#!/bin/bash
# Важливо: lastpipe працює лише при вимкненому Job Control (за замовчуванням у скриптах)
shopt -s lastpipe

error_count=0
cat /var/log/nginx/error.log | while read -r line; do
    case "$line" in
        *"[error]"*) error_count=$((error_count + 1)) ;;
    esac
done

echo "Total errors: $error_count" # Змінна збережена!
```

Ця опція перетворює поведінку Bash на поведінку KornShell та Zsh, де остання команда конвеєра за замовчуванням виконується in-process.

## Шаблони оркестрації та ізоляція побічних ефектів

Попри високі накладні витрати системного виклику `fork()`, підоболонки є потужним інструментом системного проєктування, коли потрібно реалізувати **контрольовану ізоляцію побічних ефектів (Side-Effect Sandboxing)**.

### 1. Безпечна зміна робочого каталогу

Часто системному скрипту потрібно перейти в тимчасовий каталог, скомпілювати або розпакувати артефакт і повернутися назад. Класичний підхід із викликом `cd /path` та подальшим `cd -` або `cd "$OLDPWD"` є крихким: якщо проміжна команда впаде через помилку або спрацює переривання, скрипт залишиться у непередбачуваній точці файлової системи.

Використання явної підоболонки вирішує цю проблему атомарно:

```sh
# Батьківський процес перебуває в /var/www/app
(
    cd /tmp/build_sandbox || exit 1
    tar -xzf package.tar.gz
    make release
    cp output/bin/* /opt/bin/
)
# Після виходу з дужок батьківський процес ГАРАНТОВАНО лишається в /var/www/app!
```

Будь-які аварійні виходи `exit` всередині блоку завершують лише дочірній процес, не порушуючи поточний каталог та глобальні змінні батьківської програми.

### 2. Тимчасова модифікація змінних середовища та лімітів

Якщо зовнішній утиліті потрібні специфічні локалі, права доступу чи обмеження пам'яті, їх встановлюють усередині підоболонки:

```sh
generate_csv_data() {
    (
        # Локаль LC_ALL=C гарантує використання крапки як десяткового роздільника
        export LC_ALL=C
        # Встановлюємо жорстке обмеження віртуальної пам'яті 512MB
        ulimit -v 524288
        # Встановлюємо сувору маску створення файлів
        umask 077
        
        python3 process_financial_records.py > /tmp/export.csv
    )
}
```

Жодна зі змін (`LC_ALL`, ліміт `ulimit`, маска `umask`) не виходить за межі дужок і не спотворює середовище батьківського скрипту.

## Простеження та вимір накладних витрат

Для глибокого розуміння ціни викликів у реальній системі розглянемо трасування виконання за допомогою утиліти `strace`:

```bash
strace -f -e trace=clone,fork,pipe2,dup2,close,execve bash -c '
func() { :; };
func;
( :; );
'
```

Трасограма показує разючий контраст:
1. **Виклик функції `func`**: у виводі `strace` немає **жодного системного виклику**. Процесор просто переставляє лічильник інструкцій (Instruction Pointer) у віртуальній пам'яті інтерпретатора.
2. **Виклик підоболонки `( :; )`**: генерує виклики `clone()` (або `fork()`), виділення таблиці сторінок, синхронізацію сигналів та виклики `wait4()`.

### Бенчмарк швидкодії

При виконанні 10 000 ітерацій на сучасному процесорі x86-64 (AMD Ryzen 9 або Intel Xeon):
- **10 000 викликів функції in-process**: займають близько **15 мілісекунд** (~1.5 мкс на виклик).
- **10 000 підоболонок у круглих дужках `( )`**: займають близько **6500 мілісекунд** (~650 мкс на виклик).

Накладні витрати на системне створення процесів перевищують вартість виклику функції у **400–500 разів**. Необдумане використання круглих дужок або підстановок команд `$(...)` усередині високонавантажених циклів обробки даних здатне уповільнити виконання сценарію на порядки.

## Підсумковий інженерний синтез

Вибір між функціями, підоболонками та блоками групування визначається вимогами до ізоляції стану та продуктивності:

1. **Функції (`fname() { ... }`)**: основний інструмент модульності. Виконуються in-process з мінімальними накладними витратами. Вимагають обов'язкового використання `local` для всіх внутрішніх змінних через наявність динамічної області видимості.
2. **Блоки вільних дужок (`{ ...; }`)**: застосовуються для групового перенаправлення вводу-виводу або об'єднання команд без створення системних процесів та зі збереженням стану.
3. **Підоболонки (`( ... )`)**: застосовуються виключно тоді, коли потрібна **навмисна ізоляція побічних ефектів** (наприклад, зміна робочого каталогу через `cd`, встановлення тимчасових змінних середовища чи зміна лімітів пам'яті), які не повинні торкнутися основного процесу.
4. **Конвеєри (`|`)**: забезпечують потокову обробку великих обсягів даних через буфери ядра, але вимагають використання `while ... done < file`, process substitution `<(...)` або опції `shopt -s lastpipe`, якщо результати обчислень всередині циклу мають зберегтися у батьківській програмі.
