# 📋 Специфікація та довідник макросів секцій ініціалізації ядра

Макроси ініціалізації ядра Linux (`include/linux/init.h`) слугують інтерфейсом між вихідним кодом мовою C та системним компонувальником (linker), який забезпечує розміщення коду й даних у тимчасових секціях пам'яті для подальшого апаратного звільнення. Цей довідник містить вичерпний опис макросів, їхнє розгортання в атрибути компілятора GCC/Clang, відповідні секції ELF та зміну прав доступу сторінок пам'яті (PTE) до й після виконання функції `free_initmem()`.

## 1. Базові макроси ініціалізації (`__init`, `__initdata`, `__initconst`)

Ця група макросів призначена для позначення функцій, змінних та констант, які необхідні виключно під час завантаження ядра (boot phase) і більше ніколи не викликаються після передачі управління процесу `/sbin/init` чи `systemd`.

```c
#include <linux/init.h>

/* Приклад використання в коді драйвера ядра */
static int __init demo_driver_init(void);
static int demo_buffer[512] __initdata;
static const char demo_name[] __initconst = "demo_subsystem";
```

### `__init`
- **Призначення**: Позначення функцій ініціалізації підсистем і драйверів.
- **Розгортання у препроцесорі**: `__attribute__((__section__(".init.text"))) __cold __section_memnoclone`.
- **Секція ELF**: `.init.text`.
- **Права доступу сторінок до `free_initmem()`**: Executable, Read-Only (RX).
- **Поведінка після `free_initmem()`**: Пам'ять передається до сторінкового алокатора. Будь-який виклик такої функції згодом призведе до Kernel Panic або Page Fault через відсутність сторінки в адресному просторі ядра.

Додатковий атрибут `__cold` підказками компілятору інформує гілочний прогностик процесора (branch predictor), що ця функція є малоймовірною для повторного виклику, а атрибут `__section_memnoclone` запобігає клонуванню функції під час агресивних міжпроцедурних оптимізацій (IPO).

### `__initdata`
- **Призначення**: Позначення змінних, таблиць, масивів та структур даних, що змінюються під час ініціалізації.
- **Розгортання у препроцесорі**: `__attribute__((__section__(".init.data")))`.
- **Секція ELF**: `.init.data`.
- **Права доступу сторінок до `free_initmem()`**: Read-Write, Non-Executable (RW, NX).
- **Поведінка після `free_initmem()`**: Повноцінно видаляється з пам'яті разом із кодом.

Використання атрибута `__initdata` є обов'язковим для тимчасових масивів налаштування, парсерів командного рядка та буферів декомпресії. Якщо змінна не позначена цим макросом, вона назавжди залишається у постійній секції `.data`, збільшуючи обсяг невільного оперативної пам'яті ядра.

### `__initconst`
- **Призначення**: Позначення константних даних (`const`), необхідних лише під час завантаження.
- **Розгортання у препроцесорі**: `__attribute__((__section__(".init.rodata")))`.
- **Секція ELF**: `.init.rodata`.
- **Права доступу сторінок до `free_initmem()`**: Read-Only, Non-Executable (RO, NX).
- **Поведінка після `free_initmem()`**: Звільняється разом з усіма секціями ініціалізації.

Цей макрос застосовується для опису статичних таблиць конфігурацій шин PCI/ACPI, незмінних рядкових констант та описувачів пристроїв, які парсяться лише один раз при старті.

## 2. Макроси завершення та вивантаження (`__exit`, `__exitdata`, `__exit_p`)

Ця група макросів регулює код і дані, необхідні для вивантаження завантажуваних модулів ядра (LKM) або деініціалізації підсистем.

```c
static void __exit demo_driver_exit(void);
static int exit_stats[64] __exitdata;
```

### `__exit`
- **Призначення**: Позначення функцій деініціалізації модуля.
- **Розгортання у препроцесорі**: `__attribute__((__section__(".exit.text")))`.
- **Секція ELF**: `.exit.text`.
- **Особливість для built-in коду**: Якщо код компілюється безпосередньо в монолітний образ `vmlinux` (`CONFIG_MODULES=n` або статичний драйвер), функція `__exit` **повноцінно ігнорується й відкидається компонувальником** на етапі лінкування. Це відбувається тому, що статичний драйвер ніколи не вивантажується з пам'яті.
- **Особливість для модулів (`.ko`)**: У завантажуваному модулі зберігається в окремій секції й викликається при виконанні утиліти `rmmod` чи системного виклику `delete_module`.

### `__exitdata`
- **Призначення**: Змінні та структури даних, що використовуються виключно у функціях `__exit`.
- **Розгортання у препроцесорі**: `__attribute__((__section__(".exit.data")))`.
- **Секція ELF**: `.exit.data`.
- **Особливість**: Повністю видаляється компонувальником для статично вкомпільованого коду ядра.

### `__exit_p(fn)`
- **Призначення**: Безпечне передавання вказівника на функцію `__exit` у структури драйверів (наприклад, у поле `.remove` структури `struct platform_driver`).
- **Розгортання у препроцесорі**:
  - Для built-in драйверів: розгортається в `NULL` (компілятор оптимізує та вилучає недійсний вказівник).
  - Для завантажуваних модулів: розгортається безпосередньо в `fn`.

Пристосування макроса `__exit_p` дозволяє уникнути помилок Section Mismatch, коли поле структури драйвера намагається зберегти адресу функції із відкинутої секції `.exit.text`.

## 3. Спеціальні макроси захисту, гарячого підключення та анотації ref

### `__ro_after_init`
- **Призначення**: Позначення структур даних, які заповнюються під час ініціалізації ядра, але **ніколи не змінюються** після завершення завантаження.
- **Розгортання у препроцесорі**: `__attribute__((__section__(".data..ro_after_init")))`.
- **Секція ELF**: `.data..ro_after_init`.
- **Права доступу сторінок до `free_initmem()`**: Read-Write (RW).
- **Права доступу сторінок після `free_initmem()`**: **Read-Only (RO)** (встановлюються функцією `mark_rodata_ro()`).
- **Звільнення пам'яті**: Пам'ять **НЕ звільняється**, вона залишається доступною для читання протягом усього часу роботи ядра. Це ключовий елемент апаратного захисту критичних структур від перезапису під час атак.

Застосування `__ro_after_init` є одним із фундаментальних вимог безпеки Linux Security Modules (LSM), оскільки воно захищає таблиці системних викликів, вказівники на процедури перевірки прав та таблиці IDT/GDT від модифікації експлойтами.

### `__meminit`, `__meminitdata`, `__meminitconst`
- **Призначення**: Використовуються підсистемою управління пам'яттю для коду, який виконується під час завантаження або під час гарячого підключення пам'яті (Memory Hotplug).
- **Особливість**: Якщо конфігурація ядра підтримує Memory Hotplug (`CONFIG_MEMORY_HOTPLUG=y`), ці секції зберігаються у пам'яті. Якщо підтримка відсутня, вони поводяться як звичайні `__init` і звільняються.

### `__ref`, `__refdata`, `__refconst`
- **Призначення**: Анотації для пригнічення попереджень інструменту `modpost` про Section Mismatch.
- **Використання**: Застосовується до функцій із постійної секції `.text`, які свідомо та безпечно звертаються до коду чи даних `__init` (наприклад, низькорівневий диспетчер завантаження, який перевіряє стан ініціалізації перед викликом).

## 4. Зведена таблиця властивостей секцій ядра

Властивості основних секцій ініціалізації та їхній стан протягом життєвого циклу ядра Linux:

| Макрос | Секція ELF | Початкові права PTE | Права після boot | Доля пам'яті в RAM |
| :--- | :--- | :--- | :--- | :--- |
| `__init` | `.init.text` | Read, Exec (RX) | N/A | **Звільняється** через `free_initmem()` |
| `__initdata` | `.init.data` | Read, Write (RW) | N/A | **Звільняється** через `free_initmem()` |
| `__initconst` | `.init.rodata` | Read-Only (RO) | N/A | **Звільняється** через `free_initmem()` |
| `__exit` (built-in) | `.exit.text` | Вилучається | N/A | Відкидається при лінкуванні vmlinux |
| `__exit` (module) | `.exit.text` | Read, Exec (RX) | RX | Зберігається в модулі до `rmmod` |
| `__ro_after_init` | `.data..ro_after_init` | Read, Write (RW) | **Read-Only (RO)** | **Зберігається** в пам'яті назавжди |
| `subsys_initcall` | `.initcall4.init` | Read-Only (RO) | N/A | **Звільняється** через `free_initmem()` |

## 5. Порядок розташування `initcalls` та прапорці рівня ініціалізації

Підсистема `initcall` використовує 8 рівнів послідовності завантаження. Для кожного рівня існує власний макрос, який розміщує вказівник у відповідну підсекцію:

1. `pure_initcall`: Секція `.initcall0.init` — ранні базові налаштування ядра.
2. `core_initcall`: Секція `.initcall1.init` — архітектурне ядро та менеджер пам'яті.
3. `postcore_initcall`: Секція `.initcall2.init` — ранні драйвери шин.
4. `arch_initcall`: Секція `.initcall3.init` — низькорівнева підтримка CPU та підсистеми переривань.
5. `subsys_initcall`: Секція `.initcall4.init` — мережевий стек, VFS, IPC.
6. `fs_initcall`: Секція `.initcall5.init` — файлові системи.
7. `device_initcall`: Секція `.initcall6.init` — основні драйвери пристроїв (`module_init`).
8. `late_initcall`: Секція `.initcall7.init` — пізні перевірки та фінальне монтування.

Усі ці секції збираються лінкером у загальний блок `.initcall.init`, розташований між `__init_begin` та `__init_end`, і видаляються разом із рештою init-коду.

## 6. Діагностика Section Mismatch інструментом modpost

Під час складання ядра інструмент `modpost` аналізує таблиці символів та релокацій у згенерованих ELF-файлах, перевіряючи коректність посилань між секціями.

### Класичні дефекти посилань між секціями:
1. **Постійний код кличе init-код**: Функція зі стандартної секції `.text` намагається викликати функцію з `.init.text`. Після виклику `free_initmem()` такий виклик призведе до Kernel Oops.
2. **Збереження вказівника на init-дані**: Глобальна змінна у постійній секції `.data` зберігає адресу масиву з `.init.data`.
3. **Безпідставне застосування `__ref`**: Приховання попередження замість виправлення збереження тимчасового вказівника.

Під час збирання ядра слід звертати увагу на попередження `WARNING: vmlinux.o: Section mismatch` та усувати некоректні посилання між секціями до релізу.
