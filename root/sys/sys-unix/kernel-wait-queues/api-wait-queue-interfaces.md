# 📋 Інтерфейси черг очікування: підписи, повернені значення й маски станів

Це контракт, за яким код ядра засинає на об'єкті й будить сплячих: повний перелік макросів `wait_event*` і `wake_up*`, низькорівнева пара «стати в чергу — вийти з неї», поля структур і прапорці записів, сусідні контракти `completion` та `swait` — і, головне, **що саме кожен виклик повертає й що викликач зобов'язаний із цим зробити**. Більшість помилок у роботі з чергами — це не помилки логіки, а неспівпадіння двох чисел: маски стану, у якому задача заснула, і маски, з якою її будять.

Усе нижче звірене з деревом ядра: `include/linux/wait.h`, `kernel/sched/wait.c`, `include/linux/completion.h`, `kernel/sched/completion.c`, `include/linux/swait.h`, `include/linux/sched.h`.

## Домовленості, без яких таблиці читаються криво

### Стан задачі — це бітова маска, а не число

Усе сімейство черг стоїть на одному рядку всередині `try_to_wake_up()`: задачу буде розбуджено тоді й лише тоді, коли її поточний стан має спільний біт із маскою пробудження.

```
розбудити ⟺ (стан задачі & маска пробудження) ≠ 0
```

Тому й таблиця бітів потрібна раніше за все інше — [стани процесу](topic:sys-unix/process-states) назовні виглядають однією літерою в `ps`, а всередині це набір прапорців.

| прапорець | значення | що означає |
|---|---|---|
| `TASK_RUNNING` | `0x0000` | у черзі готових або на процесорі |
| `TASK_INTERRUPTIBLE` | `0x0001` | переривний сон; будь-який сигнал обриває |
| `TASK_UNINTERRUPTIBLE` | `0x0002` | непереривний сон; сигнали не доходять |
| `TASK_WAKEKILL` | `0x0100` | «мене можна розбудити смертельним сигналом» — сам по собі не стан, а домішка |
| `TASK_NOLOAD` | `0x0400` | не рахувати цю задачу в середньому навантаженні |
| `TASK_FREEZABLE` | `0x2000` | задачу дозволено заморозити на час приспання системи |

Складені значення, які фактично й підставляють у виклики:

```c
#define TASK_KILLABLE  (TASK_WAKEKILL | TASK_UNINTERRUPTIBLE)   /* 0x0102 */
#define TASK_IDLE      (TASK_UNINTERRUPTIBLE | TASK_NOLOAD)     /* 0x0402 */
#define TASK_NORMAL    (TASK_INTERRUPTIBLE | TASK_UNINTERRUPTIBLE) /* 0x0003 */
```

Звідси одразу видно те, що коштує людям найбільше часу: **`TASK_KILLABLE` не має біта `TASK_INTERRUPTIBLE`**. Задача, приспана через `wait_event_killable()`, лежить у пам'яті як непереривна, і `wake_up_interruptible()` її не побачить. Так само не побачить і `TASK_IDLE`.

Смертельний сигнал розрізняється не маскою пробудження, а окремою перевіркою в `signal_pending_state()`: якщо в стані немає біта `TASK_INTERRUPTIBLE`, сон обривається лише тоді, коли сигнал фатальний. Тобто «killable» — це не спосіб бути розбудженим, а спосіб вийти з циклу очікування.

### Такти, тайм-аути й нуль

Усі тайм-аути в цьому контракті — у **тактах системного годинника** (jiffies), а не в секундах чи мілісекундах; ціна такту залежить від `HZ`, тож константи в коді забороняються — [як ядро рахує час](topic:sys-unix/kernel-timekeeping).

| вираз | що дає |
|---|---|
| `msecs_to_jiffies(500)` | півсекунди в тактах, з правильним заокругленням |
| `usecs_to_jiffies(n)` | те саме з мікросекунд |
| `HZ` | тактів на секунду; `5 * HZ` — п'ять секунд |
| `MAX_SCHEDULE_TIMEOUT` | `LONG_MAX`, тобто «фактично назавжди» |
| `0` | не спати взагалі: макрос лише перевірить умову й одразу поверне 1 або 0 |

Останній рядок — не курйоз, а робочий прийом: одним і тим самим кодом обслуговують і блокувальний, і неблокувальний режим, підставляючи в тайм-аут нуль для `O_NONBLOCK` (див. [блокувальний і неблокувальний ввід-вивід](topic:sys-unix/blocking-and-nonblocking)).

### Коди помилок

`-ERESTARTSYS` — внутрішнє значення ядра, і назовні воно **ніколи не потрапляє**. Шар системних викликів побачить його при поверненні й або перезапустить виклик з початку, або віддасть програмі `EINTR` — залежно від диспозиції сигналу, який урвав сон ([перервані виклики й перезапуск](topic:sys-unix/eintr-and-restart)). Обов'язок драйвера рівно один: **повернути це значення нагору незміненим і не робити перед цим нічого незворотного**.

## Заведення черги й запису

Голова черги живе в об'єкті, якого чекають; запис — на стеку того, хто чекає.

| конструкція | де вживається |
|---|---|
| `DECLARE_WAIT_QUEUE_HEAD(name);` | статична голова на рівні файлу або як поле, що ініціалізується статично |
| `DECLARE_WAIT_QUEUE_HEAD_ONSTACK(name);` | голова як локальна змінна; відрізняється лише правильною реєстрацією в перевірці замків |
| `init_waitqueue_head(&obj->readq);` | голова всередині динамічно виділеного об'єкта — звичайний випадок драйвера |
| `DEFINE_WAIT(wait);` | запис на стеку з `func = autoremove_wake_function` і `private = current` |
| `DEFINE_WAIT_FUNC(wait, my_fn);` | те саме з власною функцією пробудження |
| `init_waitqueue_entry(&w, task);` | заповнити наявний запис: `default_wake_function` і задана задача |
| `init_waitqueue_func_entry(&w, fn);` | запис-гачок: `private = NULL`, спрацьовує чужа функція |

`init_waitqueue_head()` — макрос, а не функція, і це не примха: він заводить статичний ключ класу замків для кожного місця виклику, щоб перевірка порядку замків розрізняла черги різних драйверів.

### Поля структур

```c
struct wait_queue_head {
    spinlock_t        lock;   /* захищає список; беруть з вимкненням перервань */
    struct list_head  head;   /* двозв'язний список записів */
};

struct wait_queue_entry {
    unsigned int      flags;    /* WQ_FLAG_* */
    void             *private;  /* зазвичай task_struct того, хто чекає */
    wait_queue_func_t func;     /* що робити, коли чергу обходять */
    struct list_head  entry;
};

typedef int (*wait_queue_func_t)(struct wait_queue_entry *wq_entry,
                                 unsigned mode, int flags, void *key);
```

| прапорець | значення | хто ставить і навіщо |
|---|---|---|
| `WQ_FLAG_EXCLUSIVE` | `0x01` | «будити мене лише як єдиного»; запис іде **в хвіст** списку, і обхід зупиняється після заданої кількості таких |
| `WQ_FLAG_WOKEN` | `0x02` | «побудка вже приходила»; ставить `woken_wake_function`, читає й скидає `wait_woken` |
| `WQ_FLAG_BOOKMARK` | `0x04` | службовий: закладка, якою обхід дуже довгого списку розбивають на порції, щоб не тримати замок черги надто довго |
| `WQ_FLAG_CUSTOM` | `0x08` | службовий: у чергах очікування на сторінку означає, що охочий хоче отримати сам біт блокування, а не просто дізнатися про подію |
| `WQ_FLAG_DONE` | `0x10` | службовий: підтвердження, що біт передано саме цьому охочому |
| `WQ_FLAG_PRIORITY` | `0x20` | ставить `add_wait_queue_priority()`; запис лягає в **голову** списку, попереду всіх |

Останні чотири прапорці драйверу ставити не доводиться: `BOOKMARK` належить самому обходові списку, `CUSTOM` і `DONE` — протоколу чесної передачі блокування сторінки всередині керування пам'яттю, `PRIORITY` — кільком внутрішнім користувачам ядра.

## Сімейство `wait_event*`

Кожен макрос розгортається в той самий цикл «стати в чергу — оголосити стан — перевірити умову — заснути» і відрізняється трьома речами: у якому стані спить, що дозволено обірвати сон і що саме повертає.

Спільна для всіх швидка дорога: якщо умова істинна **до** входу, макрос не чіпає ані черги, ані замка, ані бар'єрів — просто йде далі.

### Без тайм-ауту

| макрос | стан сну | сон обриває | повертає |
|---|---|---|---|
| `wait_event(wq, cond)` | `TASK_UNINTERRUPTIBLE` | нічого | нічого (оператор, не вираз) |
| `wait_event_interruptible(wq, cond)` | `TASK_INTERRUPTIBLE` | будь-який сигнал | `int`: `0` або `-ERESTARTSYS` |
| `wait_event_killable(wq, cond)` | `TASK_KILLABLE` | лише смертельний сигнал | `int`: `0` або `-ERESTARTSYS` |
| `wait_event_idle(wq, cond)` | `TASK_IDLE` | нічого | нічого |
| `wait_event_freezable(wq, cond)` | `TASK_INTERRUPTIBLE` + `TASK_FREEZABLE` | сигнал; на приспанні задачу морозять | `int`: `0` або `-ERESTARTSYS` |
| `wait_event_state(wq, cond, state)` | заданий явно | за маскою стану | `int`: `0` або `-ERESTARTSYS` |
| `io_wait_event(wq, cond)` | `TASK_UNINTERRUPTIBLE` | нічого | нічого; час іде в облік очікування вводу-виводу |

`io_wait_event()` відрізняється від `wait_event()` рівно одним: усередині стоїть `io_schedule()` замість `schedule()`, і саме звідси береться стовпчик `wa` в `vmstat` та поле `iowait` у [обліку процесорного часу](topic:sys-unix/cpu-time-accounting). Для очікування на пристрій беруть саме його, інакше система звітує, що процесор просто простоює.

### З тайм-аутом

| макрос | повертає (`long`, крім `hrtimeout`) |
|---|---|
| `wait_event_timeout(wq, cond, t)` | `0` — час вичерпано, умова хибна; `1` — умова стала істинною рівно на межі; `≥1` — лишок тактів |
| `wait_event_interruptible_timeout(wq, cond, t)` | те саме плюс `-ERESTARTSYS` |
| `wait_event_killable_timeout(wq, cond, t)` | те саме плюс `-ERESTARTSYS` на смертельний |
| `wait_event_idle_timeout(wq, cond, t)` | `0` / `1` / лишок тактів |
| `wait_event_hrtimeout(wq, cond, ktime)` | `int`: `0` — умова істинна; `-ETIME` — час вичерпано |
| `wait_event_interruptible_hrtimeout(wq, cond, ktime)` | `int`: `0`, `-ETIME` або `-ERESTARTSYS` |

Значення `1` в окремому рядку стоїть навмисне: воно означає «час уже минув, але на останній перевірці умова таки виявилася істинною». Тобто **нуль — це єдиний код тайм-ауту**, а будь-яке додатне число, включно з одиницею, каже «дочекалися».

Версії з `hrtimeout` міряють час не тактами, а `ktime_t` — там, де потрібна точність, недосяжна для `HZ`, і повертають вони не лишок, а простий код.

### Виключні

Виключний сон гасить [гримучу отару](topic:sf-distributed/thundering-herd): такий запис лягає в хвіст черги й будиться по одному.

| макрос | стан сну | повертає |
|---|---|---|
| `wait_event_interruptible_exclusive(wq, cond)` | `TASK_INTERRUPTIBLE` | `int`: `0` або `-ERESTARTSYS` |
| `wait_event_killable_exclusive(wq, cond)` | `TASK_KILLABLE` | `int`: `0` або `-ERESTARTSYS` |
| `wait_event_idle_exclusive(wq, cond)` | `TASK_IDLE` | нічого |
| `wait_event_idle_exclusive_timeout(wq, cond, t)` | `TASK_IDLE` | `long`: `0` / `1` / лишок |
| `wait_event_freezable_exclusive(wq, cond)` | `TASK_INTERRUPTIBLE` + `TASK_FREEZABLE` | `int` |
| `wait_event_exclusive_cmd(wq, cond, cmd1, cmd2)` | `TASK_UNINTERRUPTIBLE` | нічого; `cmd1` виконується перед сном, `cmd2` — після |

Простого `wait_event_exclusive()` **не існує** — і це не пропуск у переліку, а наслідок призначення. Виключність має сенс там, де на одну здобич змагаються багато однакових охочих: сотня робочих процесів на `accept()`, купа читачів однієї черги. Такі очікування завжди тривалі й завжди мусять бути перериваними, інакше перший же збій пристрою дає сотню процесів у стані `D`. Хто справді потребує непереривного виключного сну, бере `wait_event_exclusive_cmd()` з порожніми командами.

### З уже взятим спін-замком

Окрема гілка для випадку, коли умову можна прочитати лише під власним замком об'єкта: макрос сам відпускає замок перед сном і бере назад після пробудження.

| макрос | повертає |
|---|---|
| `wait_event_lock_irq(wq, cond, lock)` | нічого |
| `wait_event_lock_irq_cmd(wq, cond, lock, cmd)` | нічого; `cmd` виконується вже після відпускання замка, перед сном |
| `wait_event_interruptible_lock_irq(wq, cond, lock)` | `int`: `0` або `-ERESTARTSYS` |
| `wait_event_interruptible_lock_irq_cmd(wq, cond, lock, cmd)` | `int` |
| `wait_event_interruptible_lock_irq_timeout(wq, cond, lock, t)` | `long`: `0`, лишок тактів або `-ERESTARTSYS` |

Дві вимоги тут жорсткі, і їх не перевіряє компілятор.

Перша: замок мусить бути взятий саме через `spin_lock_irq()`, бо всередині макрос робить `spin_unlock_irq()` і `spin_lock_irq()`. Узятий через `spin_lock_irqsave()` замок ці макроси зіпсують — збережений стан прапорців перервань буде втрачено. Що це за різниця й чому вона важить — у темі про [замки в ядрі](topic:sys-unix/kernel-locking).

Друга: у цих макросах немає `might_sleep()`, який стоїть у решті сімейства. Тобто перевірка «а чи не заснув ти в атомарному контексті» тут вимкнена свідомо — саме тому, що цей замок ви тримаєте навмисне. Поручитися, що поруч не лишилося ще одного замка чи атомарної ділянки, доводиться вже самому.

### Що викликач зобов'язаний зробити з поверненим значенням

| значення | що сталося | обов'язок викликача |
|---|---|---|
| `0` з `int`-макроса | умова істинна | працювати далі |
| `-ERESTARTSYS` | сон обірвав сигнал | негайно повернути нагору; жодних побічних дій, бо виклик може бути перезапущено з нуля |
| `0` з `long`-макроса | тайм-аут; умова хибна | обробити як відмову — типово `-ETIMEDOUT` для програми |
| `≥1` з `long`-макроса | умова істинна; стільки тактів лишилося | працювати далі; лишок віддають наступному очікуванню в тому самому виклику |
| `-ETIME` | тайм-аут у `hrtimeout`-версії | те саме, що й нуль вище |

Порядок перевірок значущий, і хибний порядок — найпоширеніший спосіб отримати процес, який не вбивається:

```c
long left = wait_event_interruptible_timeout(dev->readq,
                                             dev->bytes_ready, msecs_to_jiffies(500));
if (left < 0)
    return left;              /* сигнал: -ERESTARTSYS нагору як є */
if (left == 0)
    return -ETIMEDOUT;        /* час вичерпано */
/* далі: умова істинна, у left — лишок тактів */
```

Записане натомість `if (left <= 0) return -ETIMEDOUT;` ковтає сигнал: програма отримує помилку замість `EINTR`, виклик не перезапускається, а якщо навколо стоїть цикл повторів — процес крутиться в ньому й не реагує на `Ctrl+C`.

### Умову обчислюють багато разів

`cond` — це фрагмент тексту, який препроцесор підставляє щонайменше двічі, а фактично на кожному оберті циклу. Звідси два незмінні правила.

**Жодних побічних дій.** `wait_event(wq, kfifo_get(&fifo, &v))` виглядає елегантно й ламається одразу: значення виймуть на швидкій дорозі, потім ще раз усередині, і частина даних зникне безслідно.

**Читання мусить бути безпечним без замка.** Умову обчислюють, не тримаючи ані замка черги, ані вашого — тому поле читають через `READ_ONCE()`, роблять атомарним, або переходять на `*_lock_irq`-гілку, де замок тримається по-справжньому. Чому просте читання поля тут недостатньо — у темі про [бар'єри та впорядкування пам'яті](topic:sf-tasks/memory-ordering-barriers).

### Мінімальний робочий виклик

```c
struct mydev {
    struct wait_queue_head readq;
    spinlock_t             lock;
    unsigned int           bytes_ready;
};

/* ініціалізація пристрою */
init_waitqueue_head(&dev->readq);
spin_lock_init(&dev->lock);

/* бік того, хто чекає: read() у контексті процесу */
static ssize_t mydev_read(struct file *f, char __user *buf, size_t n, loff_t *off)
{
    struct mydev *dev = f->private_data;
    int ret;

    if (f->f_flags & O_NONBLOCK) {
        if (!READ_ONCE(dev->bytes_ready))
            return -EAGAIN;
    } else {
        ret = wait_event_interruptible(dev->readq, READ_ONCE(dev->bytes_ready));
        if (ret)
            return ret;              /* -ERESTARTSYS нагору незміненим */
    }
    return copy_ready_bytes(dev, buf, n);
}

/* бік того, хто будить: обробник перервання */
static irqreturn_t mydev_isr(int irq, void *data)
{
    struct mydev *dev = data;

    spin_lock(&dev->lock);
    dev->bytes_ready += drain_fifo(dev);   /* умова стала істинною */
    spin_unlock(&dev->lock);

    if (wq_has_sleeper(&dev->readq))       /* бар'єр + перевірка списку */
        wake_up_interruptible(&dev->readq);
    return IRQ_HANDLED;
}
```

Пара станів тут збігається дослівно: заснули через `_interruptible`, будимо через `wake_up_interruptible()`. Обробник виконується не від імені жодної задачі — про це в темі про [перервання й нижні половини](topic:sys-unix/interrupts-bottom-halves).

## Низькорівневий шар

Макроси покривають дев'яносто відсотків потреб. Решта — коли між «стати в чергу» і «заснути» треба виконати щось власне: відпустити м'ютекс, надіслати команду пристрою, перевірити стан по шині.

| функція | повертає | що робить |
|---|---|---|
| `add_wait_queue(wq, e)` | `void` | знімає `WQ_FLAG_EXCLUSIVE`, ставить запис у **голову** під замком |
| `add_wait_queue_exclusive(wq, e)` | `void` | ставить `WQ_FLAG_EXCLUSIVE`, запис іде в **хвіст** |
| `add_wait_queue_priority(wq, e)` | `void` | ставить `WQ_FLAG_PRIORITY`, запис іде в голову попереду всіх |
| `remove_wait_queue(wq, e)` | `void` | виймає запис під замком |
| `prepare_to_wait(wq, e, state)` | `void` | знімає `WQ_FLAG_EXCLUSIVE`; додає в голову, **якщо запису ще нема в списку**; ставить стан задачі — усе під замком черги |
| `prepare_to_wait_exclusive(wq, e, state)` | `bool` | те саме, але прапорець ставиться, запис іде в хвіст; повертає, **чи черга була порожня** до цього — тобто чи ви перший охочий |
| `prepare_to_wait_event(wq, e, state)` | `long` | те, що всередині макросів: спершу перевіряє сигнал за маскою стану — якщо є, **виймає запис** і повертає `-ERESTARTSYS`; інакше додає й ставить стан, повертає `0` |
| `finish_wait(wq, e)` | `void` | ставить `TASK_RUNNING` і виймає запис, якщо він ще в списку |
| `wait_woken(e, mode, timeout)` | `long` | ставить стан `mode`; спить **лише якщо не стоїть `WQ_FLAG_WOKEN`**; прокинувшись, скидає прапорець і повертає лишок тактів |

Три деталі, які легко проґавити.

`prepare_to_wait()` перевіряє `list_empty(&e->entry)` — тому повторний виклик у циклі не додає запис удруге, і саме тому цикл пишеться без жодного прибирання всередині.

`finish_wait()` **обов'язковий на всіх виходах із циклу**, включно з виходом по помилці. Запис лежить на стеку; якщо функція повернеться, лишивши його в чужому списку, наступний обхід черги викличе `func` за адресою, де вже давно чужі дані. Це не «витік», а порча пам'яті ядра з довільним наслідком.

`prepare_to_wait_event()` виймає запис із черги, коли бачить сигнал, — і робить це раніше, ніж поверне `-ERESTARTSYS`. Тому в макросах `finish_wait()` після циклу лишається дешевою перевіркою, а не другим проходом під замком.

### Канонічний цикл на `prepare_to_wait`

```c
DEFINE_WAIT(wait);
int ret = 0;

for (;;) {
    prepare_to_wait(&dev->readq, &wait, TASK_INTERRUPTIBLE);
    if (READ_ONCE(dev->bytes_ready))
        break;
    if (signal_pending(current)) { ret = -ERESTARTSYS; break; }
    submit_next_request(dev);       /* власна дія перед сном */
    schedule();
}
finish_wait(&dev->readq, &wait);
return ret;
```

### Цикл на `wait_woken`

Потрібен тоді, коли перевірка умови довга й ненадійна: побудка, що прилетіла посеред неї, не губиться, бо лишає позначку `WQ_FLAG_WOKEN` у самому записі. Запис при цьому **лишається** в черзі весь час — тому додають і виймають його руками.

```c
DEFINE_WAIT_FUNC(wait, woken_wake_function);
long timeo = msecs_to_jiffies(2000);

add_wait_queue(&dev->readq, &wait);
while (!poll_device_over_slow_bus(dev)) {   /* довга перевірка */
    timeo = wait_woken(&wait, TASK_INTERRUPTIBLE, timeo);
    if (!timeo || signal_pending(current))
        break;
}
remove_wait_queue(&dev->readq, &wait);
```

### Функції пробудження

Значення, яке повертає `func`, керує обходом черги.

| функція | що робить | запис після пробудження |
|---|---|---|
| `default_wake_function` | будить задачу з `e->private` за маскою `mode` | лишається в черзі |
| `autoremove_wake_function` | те саме, і якщо задачу справді збудило — виймає запис | виймається |
| `woken_wake_function` | бар'єр, ставить `WQ_FLAG_WOKEN`, далі як `default` | лишається; лишається й позначка |
| власна | будь-що: перекласти елемент у свій список, порівняти ключ, відмовитися будити | на ваш розсуд |

| значення `func` | як його читає обхід |
|---|---|
| `> 0` | «збудив»; якщо запис виключний — зменшити лічильник |
| `0` | «не збудив» (чужа подія, не збігся ключ); обхід іде далі, лічильник не рухається |
| `< 0` | «припинити обхід негайно» — так гальмує черга сторінок, коли біт блокування вже зайнято |

## Сімейство `wake_up*`

Усе сімейство — обгортки над одним викликом `__wake_up(wq, mode, nr_exclusive, key)`, і різняться вони рівно трьома аргументами.

| макрос | маска станів | скільки виключних | ключ |
|---|---|---|---|
| `wake_up(x)` | `TASK_NORMAL` | 1 | немає |
| `wake_up_nr(x, nr)` | `TASK_NORMAL` | `nr` | немає |
| `wake_up_all(x)` | `TASK_NORMAL` | **0 = усіх** | немає |
| `wake_up_interruptible(x)` | `TASK_INTERRUPTIBLE` | 1 | немає |
| `wake_up_interruptible_nr(x, nr)` | `TASK_INTERRUPTIBLE` | `nr` | немає |
| `wake_up_interruptible_all(x)` | `TASK_INTERRUPTIBLE` | 0 = усіх | немає |
| `wake_up_sync(x)` | `TASK_NORMAL` | 1 | немає, плюс підказка `WF_SYNC` |
| `wake_up_interruptible_sync(x)` | `TASK_INTERRUPTIBLE` | 1 | те саме |
| `wake_up_poll(x, m)` | `TASK_NORMAL` | 1 | маска подій `EPOLL*` |
| `wake_up_interruptible_poll(x, m)` | `TASK_INTERRUPTIBLE` | 1 | те саме |
| `wake_up_interruptible_sync_poll(x, m)` | `TASK_INTERRUPTIBLE` | 1 | те саме плюс `WF_SYNC` |
| `wake_up_locked(x)` | `TASK_NORMAL` | 1 | немає; **замок черги вже тримає викликач** |
| `wake_up_all_locked(x)` | `TASK_NORMAL` | 0 = усіх | те саме |
| `wake_up_locked_poll(x, m)` | `TASK_NORMAL` | 1 | маска подій; замок тримає викликач |

Чотири речі в цій таблиці варті окремого рядка.

**Нуль означає «всіх», а не «нікого».** Лічильник зменшується лише на записах із `WQ_FLAG_EXCLUSIVE`, які справді збудилися; лічильник, що почався з нуля, після першого ж зменшення стає від'ємним і нулем більше не буде, тож обхід іде до кінця списку. Не-виключні записи будяться завжди й лічильника не торкаються — тому `wake_up()` на черзі без виключних записів будить усіх, попри одиницю в аргументі.

**`_locked` — інша сигнатура за змістом.** Ці варіанти не беруть спін-замок черги, бо його вже тримає викликач. Викликати їх без замка — тиха порча списку; викликати звичайний `wake_up()`, тримаючи замок черги, — самоблокування на місці. Плутанина тут не діагностується нічим, крім читання коду.

**`_sync` — це підказка планувальнику**, а не інший спосіб будити. Вона каже: «я зараз сам засну або віддам процесор, не витісняй мене заради розбудженого прямо тут». Класичний споживач — [канали](topic:sys-unix/pipe-and-fifo), де записувач будить читача й одразу лягає сам; без підказки система робила б два зайві перемикання контексту.

**Ключ передає причину.** `wake_up_poll(&wq, EPOLLIN)` кладе маску подій у аргумент `key`, і власна функція пробудження [епола](topic:sys-unix/select-poll-epoll) читає її, щоб не будити тих, хто чекає на запис, коли надійшли дані для читання. Черга при цьому лишається однією.

### Що з чим збігається

| стан, у якому спить задача | `wake_up*` (`TASK_NORMAL`) | `wake_up_interruptible*` |
|---|---|---|
| `TASK_INTERRUPTIBLE` | будить | будить |
| `TASK_UNINTERRUPTIBLE` | будить | **не будить** |
| `TASK_KILLABLE` | будить | **не будить** |
| `TASK_IDLE` | будить | **не будить** |
| `TASK_INTERRUPTIBLE` + `TASK_FREEZABLE` | будить | будить |

Практичне правило, яке покриває всю таблицю: **`wake_up()` будить усіх, кого взагалі можна розбудити через чергу; `wake_up_interruptible()` — лише переривних.** Тому невідповідність можлива тільки в один бік, і саме вона й трапляється: приспали непереривно, будите переривно.

### Чи є взагалі кого будити

Обидві перевірки читають список **без замка**, і в цьому весь сенс — вони мають коштувати одне читання вказівника на гарячому шляху.

| виклик | бар'єр | коли брати |
|---|---|---|
| `waitqueue_active(&wq)` | немає | лише коли повний бар'єр уже зроблено чимось іншим поруч — наприклад, ви щойно відпустили спін-замок, під яким змінили умову, і компілятор із процесором вже не можуть переставити ці дії |
| `wq_has_sleeper(&wq)` | `smp_mb()` перед перевіркою | в усіх інших випадках — тобто за домовленістю |
| `wq_has_single_sleeper(&wq)` | немає | оптимізація «охочий рівно один», коли треба вирішити, чи варто щось готувати для решти |

Різниця між першими двома — один бар'єр, і саме він відрізняє драйвер, що працює, від драйвера, що раз на тиждень вішає застосунок. Без бар'єра процесор має право виконати читання списку **раніше** за запис умови, і тоді обидві сторони побачать старе: охочий вирішить, що даних нема, той, хто будить, — що чекати нікому.

> 🔧 **Навіщо це.** У правках, які приходять у драйвери, `waitqueue_active()` замінюють на `wq_has_sleeper()` частіше, ніж будь-що інше в цьому контракті. Якщо ви бачите `waitqueue_active()` у чужому коді, поставте одне питання: чи є між зміною умови й цією перевіркою хоч щось із повним бар'єром — відпускання спін-замка, атомарна операція з поверненням значення, явний `smp_mb()`. Немає — це та сама помилка.

## Сусідній контракт: `completion`

Коли подія трапляється рівно один раз — DMA-передача скінчилася, модуль ініціалізувався, потік ядра стартував — черга очікування зайва, бо разом з умовою треба нести й пам'ять про те, що подія вже була. `completion` носить її сам, у лічильнику.

```c
struct completion {
    unsigned int            done;   /* скільки подій сталося й ще не спожито */
    struct swait_queue_head wait;
};
```

| виклик | повертає | що робить |
|---|---|---|
| `DECLARE_COMPLETION(x);` | — | статичне заведення |
| `DECLARE_COMPLETION_ONSTACK(x);` | — | заведення локальної змінної з правильною реєстрацією в перевірці замків |
| `init_completion(&x)` | `void` | `done = 0` і заведення черги — для динамічно виділених |
| `reinit_completion(&x)` | `void` | лише `done = 0`; чергу не чіпає — для повторного вжитку тієї самої структури |
| `complete(&x)` | `void` | збільшує `done` на одиницю (не перевищуючи `UINT_MAX`) і будить **одного** охочого |
| `complete_all(&x)` | `void` | ставить `done = UINT_MAX` і будить **усіх**; після цього очікування ніколи не блокує |
| `wait_for_completion(&x)` | `void` | непереривний сон, доки `done` не стане ненульовим; споживає одиницю |
| `wait_for_completion_io(&x)` | `void` | те саме, але час іде в облік очікування вводу-виводу |
| `wait_for_completion_interruptible(&x)` | `int` | `0` або `-ERESTARTSYS` |
| `wait_for_completion_killable(&x)` | `int` | `0` або `-ERESTARTSYS` на смертельний |
| `wait_for_completion_state(&x, state)` | `int` | сон у заданому стані; `0` або `-ERESTARTSYS` |
| `wait_for_completion_timeout(&x, t)` | `unsigned long` | `0` — тайм-аут; `≥1` — лишок тактів |
| `wait_for_completion_io_timeout(&x, t)` | `unsigned long` | те саме з обліком вводу-виводу |
| `wait_for_completion_interruptible_timeout(&x, t)` | `long` | `0`, лишок тактів або `-ERESTARTSYS` |
| `wait_for_completion_killable_timeout(&x, t)` | `long` | те саме |
| `try_wait_for_completion(&x)` | `bool` | не спить: `true`, якщо було що спожити (і споживає); `false` інакше |
| `completion_done(&x)` | `bool` | `true`, якщо `done` ненульовий, тобто охочих зараз немає |

Три відмінності від черги очікування, заради яких `completion` і існує.

**Перегони розв'язано лічильником, а не порядком дій.** Якщо `complete()` спрацював до того, як хтось узагалі почав чекати, `done` вже дорівнює одиниці, і `wait_for_completion()` не засне зовсім. Ставати в чергу до перевірки тут не потрібно, бо перевіряють не зовнішню умову, а власне поле структури під її ж замком.

**Умови в макросі немає — і циклу теж.** Тут його не пишуть: `done` і є вся істина, і споживається вона атомарно.

**`complete()` і `complete_all()` — різні контракти, а не два стилі.** Перший видає одну «порцію» одному охочому: два виклики `complete()` розбудять двох. Другий переводить структуру в стан «назавжди готово», і будь-яке подальше очікування пройде наскрізь — саме це потрібне для «модуль ініціалізувався», де охочих може бути скільки завгодно й будь-коли.

Окрема пастка — `completion` на стеку. `DECLARE_COMPLETION_ONSTACK()` дозволений і поширений, але той, хто чекає, **не має права повернутися з функції, доки `complete()` не завершився цілком**: збудивши задачу, `complete()` ще дотикається до полів структури, а стек до того часу може вже належати іншому кадру. Найпростіший спосіб не наступити — не поєднувати очікування на стеку з тайм-аутом: вийшовши по тайм-ауту, ви лишаєте вказівник на мертвий стек у руках того, хто ось-ось викличе `complete()`.

## Сусідній контракт: `swait`

`swait` (simple wait) — навмисно обрізана черга для коду, якому потрібні **передбачувані межі часу**, проведеного із вимкненими перерваннями й під замком: [реального часу](topic:sys-unix/kernel-preemption) і віртуалізації.

```c
struct swait_queue_head {
    raw_spinlock_t   lock;        /* саме raw_: не перетворюється на м'ютекс у PREEMPT_RT */
    struct list_head task_list;
};

struct swait_queue {
    struct task_struct *task;     /* тільки задача — жодного func */
    struct list_head    task_list;
};
```

| виклик | відповідник у звичайній черзі |
|---|---|
| `DECLARE_SWAIT_QUEUE_HEAD(name);` / `init_swait_queue_head(&q)` | `DECLARE_WAIT_QUEUE_HEAD` / `init_waitqueue_head` |
| `swait_event_exclusive(q, cond)` | `wait_event` |
| `swait_event_interruptible_exclusive(q, cond)` | `wait_event_interruptible` |
| `swait_event_timeout_exclusive(q, cond, t)` | `wait_event_timeout` |
| `swait_event_interruptible_timeout_exclusive(q, cond, t)` | `wait_event_interruptible_timeout` |
| `swait_event_idle_exclusive(q, cond)` | `wait_event_idle` |
| `swake_up_one(&q)` | `wake_up` |
| `swake_up_all(&q)` | `wake_up_all` |
| `swake_up_locked(&q, flags)` | `wake_up_locked` |
| `swait_active(&q)` / `swq_has_sleeper(&q)` | `waitqueue_active` / `wq_has_sleeper` |
| `prepare_to_swait_exclusive` / `prepare_to_swait_event` / `finish_swait` | `prepare_to_wait_exclusive` / `prepare_to_wait_event` / `finish_wait` |

Чого тут немає — і саме цим вимірюється різниця:

- **немає власних функцій пробудження** — обхід списку не може викликати чужий код невідомої тривалості;
- **немає не-виключних записів** — усі охочі рівні, звідси `_exclusive` у кожній назві;
- **немає змішування переривного й непереривного сну на одній черзі** — маска більше нічого не фільтрує;
- **`swake_up_all()` заборонено з вимкненими перерваннями** — щоб довгий обхід не з'їв усю затримку системи.

Найпомітніший користувач `swait` — саме `completion`: його поле `wait` має тип `struct swait_queue_head`.

## Таблиця типових помилок

| симптом | причина | лікування |
|---|---|---|
| процес назавжди в стані `D`, `wchan` вказує на драйвер, події приходять | приспали через `wait_event()` (непереривно), а будите `wake_up_interruptible()` — маски не перетинаються | звести пару докупи: `wait_event_interruptible` + `wake_up_interruptible`, або `wait_event` + `wake_up` |
| те саме, але сон був `wait_event_killable()` | `TASK_KILLABLE` не має біта `TASK_INTERRUPTIBLE` | будити `wake_up()`, а не `wake_up_interruptible()` |
| раз на тиждень зависання під навантаженням, відтворити не вдається | `waitqueue_active()` замість `wq_has_sleeper()` — читання списку випередило запис умови | `wq_has_sleeper()` або явний `smp_mb()` між зміною умови й перевіркою |
| задача прокидається, бачить, що даних нема, і йде працювати з порожнім буфером | `if (!cond) { prepare…; schedule(); }` замість циклу | цикл `for (;;)`: побудка означає «перевір», а не «дочекався» |
| дані час від часу зникають | побічна дія в тексті умови (`kfifo_get`, читання регістра зі скиданням) | умова лише читає; забирають дані вже після виходу з очікування |
| порча пам'яті ядра через якийсь час після помилкового виходу | вихід із циклу без `finish_wait()` — запис лишився в черзі, а стек уже інший | `finish_wait()` на **всіх** шляхах виходу, включно з поверненням помилки |
| програма отримує `ETIMEDOUT` замість `EINTR`, процес не реагує на сигнали | `if (ret <= 0) return -ETIMEDOUT;` — від'ємне значення злилося з нулем | спершу `ret < 0`, окремо `ret == 0` |
| `BUG: scheduling while atomic` | очікування під спін-замком або в обробнику перервання | винести очікування з атомарного контексту або взяти `*_lock_irq`-варіант, який сам відпускає замок |
| зіпсований стан прапорців перервань після очікування | `wait_event_lock_irq()` на замку, взятому через `spin_lock_irqsave()` | ці макроси працюють лише з `spin_lock_irq()` |
| дочекалися по тайм-ауту, але дані таки є | нуль сплутано з «умова хибна назавжди» | нуль означає лише «на момент останньої перевірки було хибно»; після нуля умову перевіряють ще раз, якщо це щось міняє |
| `complete()` пише в чужий стек | `wait_for_completion_timeout()` на `DECLARE_COMPLETION_ONSTACK` і вихід по тайм-ауту | не поєднувати стек із тайм-аутом; або тримати `completion` у структурі, що живе довше за обох |
| один охочий прокидається, решта висить, хоча подія спільна | `complete()` там, де потрібне `complete_all()` | одноразова подія для багатьох — завжди `complete_all()` |
| сотня процесів прокидається на одну подію | усі записи не-виключні | `wait_event_interruptible_exclusive()` у тих, хто змагається за одну здобич |

Останній рядок відрізняється від інших тим, що це не поламаний код, а лише дорогий: система працює правильно, просто платить сотнею перемикань контексту за кожну подію. Побачити це можна тим самим інструментом, що й решту, — [трасуванням подій планувальника](topic:sys-unix/ftrace-kernel-tracing): на одну подію в записі буде сто `sched_wakeup` і жодного корисного наслідку в дев'яноста дев'яти з них.
