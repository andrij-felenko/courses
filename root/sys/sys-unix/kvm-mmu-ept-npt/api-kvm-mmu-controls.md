# 📋 Інтерфейси керування KVM MMU: параметри ядра, ioctl, Hugepages та діагностика

Підсистема віртуалізації пам'яті KVM надає чотири взаємопов'язані рівні керування та діагностики: параметри завантаження та виконання модулів ядра хоста (`kvm`, `kvm_intel`, `kvm_amd`), набір системних викликів `ioctl` для простору користувача гіпервізора (VMM) над дескрипторами віртуальної машини, механізми виділення та конфігурації великих сторінок (Hugepages через `madvise` та `hugetlbfs`), а також інтерфейси телеметрії та динамічного спостереження за подіями MMU через `DebugFS` і точки трасування ядра (`tracefs`).

## Параметри модулів ядра Linux

Параметри модулів визначають глобальну архітектурну поведінку підсистеми пам'яті KVM для всіх віртуальних машин на хості. Їх задають під час завантаження ядра в командному рядку (наприклад, `kvm_intel.ept=1 kvm.tdp_mmu=1 kvm.nx_huge_pages=auto`) або змінюють динамічно через псевдофайлову систему `/sys/module/<модуль>/parameters/`.

### Механізми апаратного прискорення Intel: EPTAD та PML

Параметр `eptad` перемикає поведінку MMU процесора при встановленні прапорців звернення до пам'яті:
- Коли `eptad=0`, будь-яке перше читання або запис у сторінку, де в записі EPT відсутній біт `Accessed` або `Dirty`, викликає апаратний вихід `EPT Violation`. Ядро KVM мусить самостійно встановити біт у пам'яті та перезапустити vCPU.
- Коли `eptad=1`, процесор самостійно виставляє біт 8 (A) або біт 9 (D) в атомний спосіб без виходу з гостьового режиму.

Параметр `pml` (Page Modification Logging) оптимізує відстеження брудних сторінок (Dirty Logging) під час живої міграції:
- Замість зняття біта запису `W` з мільйонів записів EPT (що провокує масові виходи `EPT Violation` при кожному записі), KVM залишає сторінки доступними на запис і налаштовує апаратний буфер PML у структурі VMCS.
- При записі гостя процесор записує адресу фрейму `GPA >> 12` у 512-елементний масив пам'яті. Лише коли буфер заповнюється, генерується `VM-exit` із кодом `0x3E` (`EXIT_REASON_PML_FULL`), і KVM переносить одразу 512 адрес у бітову карту брудних сторінок за один вихід.

### Захист від атак спекулятивного виконання: nx_huge_pages, iTLB Multihit та mitigations

Апаратні вразливості мікроархітектурного перекладу пам'яті вимагають спеціалізованого захисту на стику апаратного MMU та гіпервізора.

#### 1. Вразливість iTLB Multihit (CVE-2018-12207) та параметр nx_huge_pages

Апаратний дефект у буфері трансляції інструкцій (iTLB) процесорів Intel Core (до 10-го покоління включно) та Intel Xeon (до мікроархітектури Ice Lake) виникає, коли процесор одночасно кешує трансляції різного розміру (4 КіБ та 2 МіБ / 1 ГіБ) для однієї й тієї самої лінійної адреси.

Якщо гостьова ОС змінює властивості сторінки або транслює лінійну адресу через 4KB-сторінки в гості, але на рівні EPT ця ділянка відображена монолітною 2MB-сторінкою, апаратний iTLB може отримати подвійне збігання (Multihit) при читанні інструкцій. Це призводить до невиправного апаратного виключення Machine Check Exception (`#MC`) та аварійної зупинки фізичного сервера (хоста). Неривілейований гостьовий код може свідомо викликати зависання всього гіпервізора.

Параметр `kvm.nx_huge_pages` усуває вразливість на рівні рушія KVM MMU:
- `auto` (2, за замовчуванням): KVM опитує апаратні прапорці ядра `boot_cpu_has_bug(X86_BUG_ITLB_MULTIHIT)`. Якщо процесор вразливий і не містить апаратного виправлення, захист вмикається автоматично; на процесорах AMD та неушкоджених CPU Intel захист лишається вимкненим.
- `always` (1): Примусове ввімкнення захисту для всіх віртуальних машин незалежно від типу процесора.
- `never` (0): Повне вимкнення мітигації. Дозволяє виконання коду на великих сторінках EPT/NPT, але створює ризик фатального збою хоста при виконанні ненадійного гостьового коду.

**Механізм роботи захисту**:
1. Щоразу, коли KVM відображає сторінку 2 МіБ або 1 ГіБ у деревах EPT/NPT, запис `SPTE` формується зі скинутим бітом виконання (`X=0` на Intel EPT або `NX=1` на AMD NPT). Читання та запис даних відбуваються з повною швидкістю Hugepages.
2. Щойно гостьовий vCPU намагається виконати машинну інструкцію з цієї сторінки, апаратний блок EPT генерує `EPT Violation` з прапорцем спроби виконання (`Execute Fault`).
3. Диспетчер KVM MMU перехоплює збій і виконує примусове розбиття сторінки (Page Splitting): 2MB-дескриптор замінюється на покажчик на нову таблицю EPT PT з 512 сторінками по 4 КіБ.
4. На 4KB-сторінці встановлюється дозвіл на виконання (`X=1`). Оскільки код виконується виключно з 4-кілобайтних фреймів, утворення конфліктних записів в iTLB стає неможливим.

#### 2. Фонове відновлення великих сторінок: nx_huge_pages_recovery_ratio

Розбиття 2MB-сторінок на 4KB-фрейми захищає від атаки, але позбавляє систему переваг великих сторінок при подальшому читанні даних (зростає кількість промахів dTLB та кроків 2D-обходу). Якщо гостьова програма виконала код лише один раз під час ініціалізації модуля, ділянка пам'яті може роками залишатися фрагментованою.

Для автоматичної дефрагментації KVM запускає фоновий потік ядра `kvm-nx-lpage-recovery`:
- Параметр `nx_huge_pages_recovery_ratio` визначає частку розбитих сторінок, яку потік намагається відновити за один 60-секундний інтервал.
- За замовчуванням значення дорівнює `60`. Щомінутно потік бере `1 / 60` (близько 1.67%) зі списку розбитих сторінок VM (`possible_nx_huge_page_recovery_ratio`) та повертає їх у статус нездійсненних 2MB-сторінок (`NX=1`).
- Якщо гостьова ОС знову передасть туди керування, сторінка знову прозоро розпадеться на 4KB. Якщо ж сторінка використовується суто для даних, вона залишається монолітною 2MB-сторінкою, повертаючи максимальну швидкодію TLB.
- Значення `0` повністю деактивує фоновий потік відновлення.

#### 3. Взаємодія з глобальним параметром ядра mitigations

Параметр завантаження ядра хоста `mitigations=auto` (або `mitigations=off`) централізовано синхронізує налаштування безпеки підсистеми KVM:
- **При `mitigations=auto`**:
  - `kvm.nx_huge_pages` виставляється в `auto`, нейтралізуючи iTLB Multihit.
  - Активується захист від L1TF (L1 Terminal Fault / Foreshadow-NG, CVE-2018-3620): параметр `kvm-intel.vmentry_l1d_flush=cond` скидає L1 Data Cache хоста перед `VM-entry`, запобігаючи читанню гостем чужої пам'яті зі спекулятивних кешів.
  - Налаштовується очищення буферів процесора для MDS (Microarchitectural Data Sampling) та TAA (TSX Asynchronous Abort).
  - Вмикається бар'єрна ізоляція спекулятивного передбачення розгалужень між гостем і хостом (STIBP / IBRS).
- **При `mitigations=off`**:
  - `kvm.nx_huge_pages` перемикається в `never`.
  - Вимикаються всі скидання L1D кешу та мікрокодові очищення буферів перед входом у vCPU. Забезпечує граничну швидкодію віртуалізації для довірених ізольованих середовищ ціною зняття міжгостьових та гость-хост бар'єрів безпеки.

## Інтерфейс ioctl керування пам'яттю з простору користувача

Гіпервізор простору користувача (QEMU, Cloud Hypervisor, crosvm, Firecracker) керує відображенням пам'яті гостя за допомогою системних викликів `ioctl` над файловим дескриптором віртуальної машини `vm_fd` (отриманим через `open("/dev/kvm")` та `ioctl(kvm_fd, KVM_CREATE_VM, 0)`).

### 1. Реєстрація слотів пам'яті: KVM_SET_USER_MEMORY_REGION та KVM_SET_USER_MEMORY_REGION2

Системні виклики `KVM_SET_USER_MEMORY_REGION` (класичний) та `KVM_SET_USER_MEMORY_REGION2` (розширений, починаючи з Linux 6.8) є основним засобом побудови фізичного адресного простору гостя (`GPA`). Вони прив'язують лінійний діапазон фізичних адрес гостя до виділеного віртуального буфера процесу VMM (`HVA`).

#### Поля структури та прапорці:

- `slot` (`__u32`): Унікальний числовий індекс слота в діапазоні `0 .. KVM_USER_MEM_SLOTS - 1` (зазвичай 512 слотів). Старші 16 бітів можуть кодувати ідентифікатор адресного простору (`as_id`), наприклад, `1` для захищеного режиму SMM (System Management Mode).
- `flags` (`__u32`): Бітова маска конфігурації слота пам'яті:
  - `KVM_MEM_LOG_DIRTY_PAGES` (`1 << 0`): Вмикає відстеження модифікацій пам'яті (Dirty Logging). KVM скидає біти запису `W` у таблицях EPT/NPT для цього регіону або активує логування через буфер PML.
  - `KVM_MEM_READONLY` (`1 << 1`): Позначає регіон як доступний гостю лише для читання. Спроба запису викликає `EPT Violation` і перенаправляється в емулятор MMIO. Використовується для емуляції мікропрограм BIOS/UEFI ROM.
  - `KVM_MEM_GUEST_MEMFD` (`1 << 2`): Вказує, що пам'ять прив'язана до спеціального анонімного файлового дескриптора `guest_memfd` для конфіденційних віртуальних машин (AMD SEV-SNP, Intel TDX). Пам'ять не відображається у віртуальний простір процесу хоста (`userspace_addr` ігнорується або дорівнює нулю).
- `guest_phys_addr` (`__u64`): Початкова фізична адреса гостя (`GPA`). Обов'язково повинна бути вирівняна за межею сторінки 4 КіБ (`guest_phys_addr & 0xFFF == 0`).
- `memory_size` (`__u64`): Розмір діапазону пам'яті в байтах. Повинен бути кратним 4 КіБ. Передача `memory_size = 0` видаляє раніше зареєстрований слот.
- `userspace_addr` (`__u64`): Початкова віртуальна адреса процесу гіпервізора (`HVA`), повернута викликом `mmap()`. Повинна бути вирівняна за межею 4 КіБ.
- `guest_memfd_offset` (`__u64`): Зсув у файловому дескрипторі `guest_memfd` (лише для `KVM_SET_USER_MEMORY_REGION2`).
- `guest_memfd` (`__u32`): Файловий дескриптор анонімної конфіденційної пам'яті.

#### Життєвий цикл слота та правила валідації KVM:

1. **Створення або розширення**: VMM викликає `ioctl(vm_fd, KVM_SET_USER_MEMORY_REGION2, &region)`. KVM перевіряє відсутність перекриття діапазону `GPA` з іншими активними слотами, виділяє внутрішню структуру `struct kvm_memory_slot` та оновлює таблицю слотів за допомогою RCU.
2. **Видалення слота**: Передача структури з тим самим індексом `slot`, але зі значенням `memory_size = 0`. KVM негайно ініціює скидання та звільнення всіх відповідних записів у деревах EPT/NPT (`zapping`), видаляє зворотні відображення та очікує завершення RCU-періоду (`synchronize_srcu`).
3. **Коди повернення помилок**:
   - `0`: Успішна реєстрація чи видалення слота.
   - `-EINVAL`: Порушено вимогу вирівнювання 4 КіБ для `guest_phys_addr`, `memory_size` або `userspace_addr`; недійсний номер `slot` (≥ 512); непідтримувані прапорці у `flags`.
   - `-EEXIST`: Заданий діапазон `GPA` перетинається з уже зареєстрованим слотом пам'яті.
   - `-EFAULT`: Вказана адреса `userspace_addr` виходить за межі адресного простору процесу VMM.
   - `-ENOMEM`: Недостатньо пам'яті ядра для виділення внутрішніх структур слота або бітових карт брудних сторінок.

#### Порівняння механізмів KVM_GET_DIRTY_LOG та KVM_CLEAR_DIRTY_LOG:

- **Класичний KVM_GET_DIRTY_LOG**:
  - Приймає структуру `struct kvm_dirty_log`, де поле `dirty_bitmap` вказує на виділений процесом буфер розміром щонайменше `(memory_size / PAGE_SIZE + 63) / 64 * 8` байтів.
  - Атомарно копіює бітову карту брудних сторінок у простір користувача та одночасно очищає внутрішній журнал ядра, повертаючи захист від запису на **всі** сторінки слота.
  - Недолік: на великих VM (сотні гігабайтів RAM) виклик спричиняє тривале монопольне блокування vCPU та масові сплески затримок при поверненні захисту.
- **Масштабований KVM_CLEAR_DIRTY_LOG (Linux 4.19+)**:
  - Вимагає попередньої активації можливості `KVM_CAP_MANUAL_DIRTY_LOG_PROTECT2` через `ioctl(vm_fd, KVM_ENABLE_CAP, ...)`.
  - Дозволяє VMM вичитувати бітову карту викликом `KVM_GET_DIRTY_LOG` без автоматичного скидання захисту запису.
  - Потім VMM надсилає порцію сторінок мережею і викликає `KVM_CLEAR_DIRTY_LOG`, вказуючи точний діапазон `[first_page, first_page + num_pages)` та бітову маску очищених сторінок.
  - Поле `first_page` має бути кратним 64; `num_pages` має бути кратним 64 (або дорівнювати залишку сторінок у слоті).
  - KVM повертає захист від запису лише на ті сторінки, які були реально скопійовані, розподіляючи навантаження в часі без зупинки vCPU.

### 3. Емуляція трансляції адрес: KVM_TRANSLATE

Системний виклик `ioctl(vcpu_fd, KVM_TRANSLATE, struct kvm_translation *)` виконує детермінований програмний обхід гостьових таблиць сторінок силами ядра KVM, транслюючи віртуальну адресу гостя (`GVA`) у фізичну адресу гостя (`GPA`) відповідно до поточної конфігурації регістрів віртуального процесора.

:::code api-kvm-mmu-controls/c/3-emuliatsiia-transliatsii.c

#### Поля структури та контракт виклику:

- `linear_address` (`__u64`): Вхідна лінійна/віртуальна адреса гостя (`GVA`), яку необхідно перекласти.
- `physical_address` (`__u64`): Вихідне поле. Містить обчислену фізичну адресу гостя (`GPA`). Значення є дійсним лише тоді, коли `valid == 1`.
- `valid` (`__u8`): `1` — трансляція успішна (шлях у гостьових таблицях знайдено, сторінка присутня); `0` — звернення до цієї адреси спричинить виключення Page Fault (`#PF`) усередині гостьової ОС (сторінка відсутня, порушено захист або виявлено заборонені зарезервовані біти).
- `writeable` (`__u8`): `1` — запис у сторінку дозволено за всіма рівнями гостьової ієрархії сторінок (з урахуванням прапорців `R/W` на рівнях PML4/PML5, PDPT, PD, PT та біта захисту супервізора `CR0.WP`).
- `usermode` (`__u8`): `1` — сторінка позначена як доступна з непривілейованого режиму користувача Ring 3 (прапорець `U/S == 1` встановлено на всіх рівнях трансляції).
- `pad[5]` (`__u8[5]`): Службове вирівнювання структури до 64-бітної межі в пам'яті.

#### Архітектурні особливості та граничні випадки:

1. **Режими адресації та керуючі регістри**:
   - Обхід гостьового дерева виконується функцією ядра `kvm_mmu_gva_to_gpa_read()` / `paging64_gva_to_gpa()`.
   - Якщо в гості вимкнено сторінкову адресацію (`CR0.PG == 0`, реальний або непагінований захищений режим), трансляція вироджується в тотожну: `GPA = GVA`, а прапорці `valid`, `writeable` та `usermode` завжди повертаються рівними `1`.
   - Враховуються прапорці 4-рівневої (`CR4.PAE=1, CR4.LA57=0`) та 5-рівневої адресації (`CR4.LA57=1`, 57-бітний лінійний простір PML5), розширення розміру сторінок (`CR4.PSE`), біти заборони виконання коду (`IA32_EFER.NXE`), а також апаратні бар'єри захисту виконання та доступу ядра (`CR4.SMEP`, `CR4.SMAP`).
2. **Ізоляція від стану процесора**:
   - Виклик не виконує жодної реальної інструкції vCPU і не призводить до ін'єкції виключення `#PF` у гостьову ОС, навіть якщо `valid == 0`.
   - Не оновлює апаратні біти Accessed / Dirty у гостьовій пам'яті та не інвалідує буфери TLB хоста чи гостя.
   - Не транслює `GPA` у `HPA` (для перетворення `GPA -> HVA -> HPA` гіпервізор застосовує власну таблицю memslots).
3. **Застосування**:
   - Інтегровані сервери відлагодження GDB у гіпервізорах (розв'язання адрес точок зупинки та читання пам'яті процесів гостя).
   - Системи безпеки та інтроспекції віртуальних машин (VMI — Virtual Machine Introspection).

:::tabs
```c
#include <linux/kvm.h>
#include <sys/ioctl.h>
#include <stdbool.h>
#include <stdint.h>

/* Програмний переклад GVA у GPA через KVM_TRANSLATE */
bool kvm_translate_gva(int vcpu_fd, uint64_t gva, uint64_t *out_gpa, bool *out_writeable) {
    struct kvm_translation tr = {
        .linear_address = gva,
    };

    if (ioctl(vcpu_fd, KVM_TRANSLATE, &tr) < 0) {
        return false;
    }

    if (!tr.valid) {
        return false; /* Трансляція недійсна: сторінка не замапована в гості */
    }

    if (out_gpa) {
        *out_gpa = tr.physical_address;
    }
    if (out_writeable) {
        *out_writeable = (tr.writeable != 0);
    }
    return true;
}
```

### 4. Керування подіями vCPU та ін'єкція збоїв сторінок: KVM_GET_VCPU_EVENTS та KVM_SET_VCPU_EVENTS

Системні виклики `ioctl(vcpu_fd, KVM_GET_VCPU_EVENTS, ...)` та `ioctl(vcpu_fd, KVM_SET_VCPU_EVENTS, ...)` керують станом очікуваних або відкладених апаратних переривань, виключень процесора (зокрема збою сторінки `#PF`) та спеціальних режимів SMI/NMI/SIPI.

#### Структура struct kvm_vcpu_events та поля збоїв MMU:

Структура `struct kvm_vcpu_events` описує стан виключень ядра:

- `exception.injected` (`__u8`): `1` — виключення поставлено в чергу на негайну ін'єкцію в гостя перед наступним входом у vCPU (`VM-entry`).
- `exception.nr` (`__u8`): Номер вектора переривання/виключення IDT. Для збою сторінки `#PF` вектор дорівнює `14` (`EXCEPTION_PF`).
- `exception.has_error_code` (`__u8`): `1` — процесор вимагає заштовхування апаратного коду помилки в стек гостя перед викликом обробника IDT (для `#PF` обов'язково `1`).
- `exception.error_code` (`__u32`): Апаратний 32-бітний бітовий код збою `#PF`:
  - Біт 0 (`P`, Present): `0` — сторінка відсутня у таблицях; `1` — порушення прав доступу на наявній сторінці.
  - Біт 1 (`W/R`, Write/Read): `0` — збій під час читання; `1` — збій під час запису.
  - Біт 2 (`U/S`, User/Supervisor): `0` — доступ виконувався у режимі ядра CPL < 3; `1` — доступ із простору користувача Ring 3.
  - Біт 3 (`RSVD`, Reserved bit): `1` — у дескрипторах гостьових таблиць знайдено зарезервований біт із недозволеним значенням.
  - Біт 4 (`I/D`, Instruction/Data): `1` — збій спровоковано вибіркою машинної інструкції (порушення біта `NX` або правила `CR4.SMEP`).
  - Біт 5 (`PK`, Protection Key): `1` — порушення прав доступу за ключем захисту сторінки (PKEYs/PKU/PKS).
  - Біт 6 (`SS`, Shadow Stack): `1` — збій доступу до тіньового стека повернень (Intel CET).
  - Біт 15 (`SGX`): `1` — порушення доступу до анклаву пам'яті SGX EPC.
- `exception_payload` (`__u64`): Зберігає значення лінійного збійного регістра `CR2` (адреса, яка викликала `#PF`) або регістра зневадження `DR6` для виключення `#DB`.
- `flags` (`__u32`): Прапорці валідності полів. Ключовим є прапорець `KVM_VCPUEVENT_FLAG_PAYLOAD_VALID` (`1 << 2`). Якщо його встановлено, KVM передає значення з `exception_payload` безпосередньо у віртуальний регістр `CR2` гостя під час ін'єкції виключення.

#### Серіалізація стану під час живої міграції та збереження знімків:

1. **Збереження стану**: Перед зупинкою віртуальної машини VMM викликає `KVM_GET_VCPU_EVENTS`. Якщо в момент паузи vCPU отримав `#PF` від KVM MMU, але ще не встиг виконати першу інструкцію обробника вектора 14, виключення фіксується зі статусом `injected = 1`, точним `error_code` та адресою `CR2` у `exception_payload`.
2. **Відновлення на цільовому хості**: VMM записує структуру викликом `KVM_SET_VCPU_EVENTS` із прапорцем `KVM_VCPUEVENT_FLAG_PAYLOAD_VALID`. Якщо знехтувати цим прапорцем, регістр `CR2` гостя не оновиться, і обробник ядра гостьової ОС отримає застарілу або нульову адресу збою, що призведе до падіння гостьового ядра (Kernel Panic / Null Pointer Dereference).

:::tabs
```c
#include <linux/kvm.h>
#include <sys/ioctl.h>
#include <stdint.h>

/* Програмна ін'єкція збою сторінки #PF у гостьовий vCPU */
int kvm_inject_page_fault(int vcpu_fd, uint64_t fault_gva, uint32_t error_code) {
    struct kvm_vcpu_events events;

    if (ioctl(vcpu_fd, KVM_GET_VCPU_EVENTS, &events) < 0) {
        return -1;
    }

    events.flags |= KVM_VCPUEVENT_FLAG_PAYLOAD_VALID;
    events.exception.injected = 1;
    events.exception.nr = 14;              /* Вектор 14: #PF */
    events.exception.has_error_code = 1;
    events.exception.error_code = error_code;
    events.exception_payload = fault_gva;  /* Адреса CR2 у гості */

    return ioctl(vcpu_fd, KVM_SET_VCPU_EVENTS, &events);
}
```
```cpp

    struct kvm_vcpu_events events{};

        throw std::system_error(errno, std::generic_category(), "KVM_SET_VCPU_EVENTS failed");
    }
}
```

## Апаратні розширення захисту та контролю виконання: Intel MBEC та PKEYs/PKU/PKS

Сучасні процесори розширюють можливості двовимірної трансляції EPT/NPT апаратними механізмами диференційованого захисту виконання та ізоляції пам'яті за ключами.

### 1. Intel Mode-Based Execute Control (MBEC) у віртуалізації EPT

Технологія MBEC (введена в архітектурі Intel Kaby Lake / Xeon Scalable) призначена для усунення критичних накладних витрат у гостьових операційних системах із підвищеними вимогами до цілісності коду ядра (наприклад, Windows Virtualization-Based Security — VBS, та Hypervisor-Protected Code Integrity — HVCI).

#### Проблема класичного EPT

У стандартному записі EPT SPTE присутній лише один біт дозволу на виконання коду — `Execute access` (`X`, біт 2). Цей біт діє одночасно як на код режиму користувача Ring 3, так і на код ядра Ring 0.

Для захисту від виконання непідписаного коду в режимі ядра (W^X для ядра) гіпервізор змушений забороняти виконання на змінюваних сторінках (`X=0`). Проте процеси простору користувача (Ring 3) повинні мати змогу вільно виконувати динамічний JIT-код (наприклад, JavaScript у браузерах або середовища .NET).

Без підтримки MBEC гіпервізор змушений перехоплювати кожне перемикання контексту гостя між Ring 3 та Ring 0, модифікувати біти `X` у таблицях EPT та скидати TLB. Це призводило до сотень тисяч `VM-exit` на секунду та падіння продуктивності гостя на 30–50%.

#### Апаратний механізм MBEC

MBEC активується бітом 22 у вторинному реєстрі керування виконанням VMCS (`Secondary Processor-Based VM-Execution Controls: Mode-based execute control for EPT`).

При увімкненому MBEC апаратний MMU замінює єдиний біт `X` двома незалежними бітами в дескрипторі EPT:
- **Біт 2 (`XU`)**: `Execute access for user-mode linear addresses` — дозвіл на виконання інструкцій для сторінок, позначених у гостьових таблицях як сторінки користувача (`U/S == 1`).
- **Біт 10 (`XS`)**: `Execute access for supervisor-mode linear addresses` — дозвіл на виконання для сторінок рівня супервізора (`U/S == 0`).

```
Звернення гостя за інструкцією (Instruction Fetch)
                │
                ▼
   Перевірка біта U/S у гостьовій таблиці сторінок
          ┌─────┴─────┐
          │           │
     U/S == 1    U/S == 0
    (User page) (Supervisor page)
          │           │
          ▼           ▼
   Перевірка біта   Перевірка біта
   EPT SPTE[2] (XU) EPT SPTE[10] (XS)
          │           │
          └─────┬─────┘
                ▼
   Дозволено? ──► ТАК ──► Виконання інструкції в гості
                └──► НІ  ──► VM-exit: EPT Violation (Exit Qual bit 12: User vs Super)
```

#### Інтеграція в KVM

KVM експортує MBEC гостю через біти можливостей CPUID та синтетичні розширення Hyper-V (`hv_enforce_mbec`, `hv_passthrough`). Ядро KVM оновлює дескриптори `SPTE` функціями `make_spte()` з урахуванням маски `shadow_user_mask` та `shadow_svs_mask`. Це забезпечує повноцінну апаратну підтримку Windows 11 / Windows Server 2022 з увімкненою ізоляцією ядра (Core Isolation) без падіння швидкодії.

### 2. Ключі захисту пам'яті (PKEYs / PKU та PKS) у гостьовому MMU

Апаратні ключі захисту дозволяють змінювати права доступу (читання/запис) до сторінок пам'яті без модифікації самих таблиць сторінок та без повільного скидання буферів TLB (`INVLPG`).

- **Intel PKU / Memory Protection Keys for User Pages** (Intel Xeon Scalable, AMD Zen 3+): захист сторінок режиму користувача.
- **Intel PKS / Protection Keys for Supervisor Pages** (Intel Sapphire Rapids+, Linux 5.14+, KVM 5.15+): захист сторінок режиму супервізора (ядра).

#### Формат кодування в таблицях сторінок:

У 64-бітних листових дескрипторах гостьових таблиць сторінок (PTE 4KB, PDE 2MB, PDPTE 1GB) біти `62:59` відведено під 4-бітний числовий індекс ключа захисту `Protection Key` (значення від `0` до `15`).

#### Апаратні регістри контролю:

1. **`PKRU` (User Protection Key Register)**: 32-бітний регістр процесора, що містить шістнадцять 2-бітних пар для ключів `0 .. 15`:
   - Біт `2*i` (`AD_i`, Access Disable): блокує як читання, так і запис для сторінок із ключем `i`.
   - Біт `2*i + 1` (`WD_i`, Write Disable): блокує запис для сторінок із ключем `i`.
2. **`IA32_PKRS` MSR (`0x000006E1`)**: 64-бітний MSR-регістр супервізора, що задає маски `AD` та `WD` для сторінок ядра з ключами 0..15.
3. **Керуючі біти**: `CR4.PKE` (біт 22) вмикає підтримку PKU; `CR4.PKS` (біт 24) активує PKS.

#### Віртуалізація в KVM:

- Ключі захисту перевіряються процесором на **першому рівні трансляції** (GVA -> GPA). При спробі несанкціонованого доступу апаратний MMU миттєво генерує виключення `#PF` безпосередньо в гості, виставляючи **біт 5 (`PK`)** у коді помилки `#PF`. Виходу в гіпервізор `VM-exit` не відбувається.
- Під час збереження/відновлення стану vCPU регістр `PKRU` є компонентом 9 розширеного стану `XSAVE` (`XCR0[9]`), підтримуваного викликами `KVM_GET_XSAVE` / `KVM_SET_XSAVE`.
- Регістр `IA32_PKRS` завантажується та зберігається через механізм VMX MSR-load/store list або швидке пряме перемикання при `VM-entry`/`VM-exit`.
- Внутрішній емулятор інструкцій KVM та виклик `KVM_TRANSLATE` враховують стан гостьових регістрів `CR4.PKE`/`CR4.PKS` та значення `PKRU`/`PKRS`, забезпечуючи повну відповідність поведінки апаратному кремнію.

## Конфігурація та прапорці пам'яті Hugepages на хості

Для зменшення затримок двовимірного обходу EPT/NPT гіпервізор виділяє оперативну пам'ять для віртуальної машини сторінками розміром 2 МіБ або 1 ГіБ. Linux надає для цього два взаємодоповнюючих механізми.

### 1. Прозорі великі сторінки (Transparent Huge Pages, THP) та виклик madvise

Процес VMM виділяє звичайну анонімну пам'ять за допомогою `mmap(NULL, size, PROT_READ|PROT_WRITE, MAP_ANONYMOUS|MAP_PRIVATE, -1, 0)` та інформує підсистему керування пам'яттю ядра за допомогою системного виклику `madvise()`:

:::tabs
```c
#include <sys/mman.h>

/* Повідомити ядро про бажаність використання 2MB сторінок */
int ret = madvise(hva_ptr, memory_size, MADV_HUGEPAGE);

/* Заборонити використання великих сторінок для чутливих до затримок MMIO буферів */
int ret_no = madvise(mmio_ptr, mmio_size, MADV_NOHUGEPAGE);
```
```cpp
#include <sys/mman.h>
#include <system_error>
#include <span>

void advise_hugepages(std::span<std::byte> memory, bool enable) {
    const int advice = enable ? MADV_HUGEPAGE : MADV_NOHUGEPAGE;
    if (::madvise(memory.data(), memory.size(), advice) != 0) {
        throw std::system_error(errno, std::generic_category(), "madvise failed");
    }
}
```
:::

- `MADV_HUGEPAGE` (значення `14`): Реєструє адресний простір для обробки фоновим демоном ядра `khugepaged`. Працює навіть якщо глобальна політика `/sys/kernel/mm/transparent_hugepage/enabled` встановлена в режим `madvise`. Ядро намагається виділяти сторінки 2 МіБ безпосередньо під час Page Fault, а також періодично склеює суміжні 4-кілобайтні фрейми.
- `MADV_NOHUGEPAGE` (значення `15`): Забороняє агрегацію сторінок. Застосовується для структур, де розбиття великої сторінки (Page Splitting) під час модифікацій спричиняло б небажані накладні витрати.
- **Розбиття сторінок під час Dirty Logging**: Якщо KVM виявляє запис у 2MB сторінку при увімкненому відстеженні брудності, рушій TDP MMU прозоро замінює запис рівня EPT PDE покажчиком на нову таблицю EPT PT із 512 записами по 4 КіБ. Демон `khugepaged` відновлює 2MB сторінку лише після вимкнення логування.

### 2. Виділена пам'ять Hugepages через hugetlbfs

Використання файлової системи `hugetlbfs` забезпечує виділення фіксованих фізично неперервних сторінок розміром 2 МіБ або 1 ГіБ, гарантуючи відсутність фрагментації та затримок дефрагментації хоста:

1. **Попереднє резервування пулу сторінок у ядрі**:
   ```bash
   # Виділити 2048 сторінок по 2 МіБ (разом 4 ГіБ)
   echo 2048 > /sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages

   # Виділити 4 сторінки по 1 ГіБ (разом 4 ГіБ)
   echo 4 > /sys/kernel/mm/hugepages/hugepages-1048576kB/nr_hugepages
   ```
2. **Монтування точки доступу**:
   ```bash
   mount -t hugetlbfs -o pagesize=2M none /dev/hugepages
   mount -t hugetlbfs -o pagesize=1G none /dev/hugepages-1G
   ```
3. **Виділення пам'яті у VMM через mmap**:
:::tabs
```c
/* Виділення анонімної пам'яті безпосередньо через системні прапорці mmap */
void *addr = mmap(NULL, size, PROT_READ | PROT_WRITE,
                  MAP_ANONYMOUS | MAP_PRIVATE | MAP_HUGETLB | MAP_HUGE_2MB,
                  -1, 0);

/* Для сторінок 1 ГіБ використовується прапорець MAP_HUGE_1GB */
void *addr_1g = mmap(NULL, size, PROT_READ | PROT_WRITE,
                     MAP_ANONYMOUS | MAP_PRIVATE | MAP_HUGETLB | MAP_HUGE_1GB,
                     -1, 0);
```
```cpp
#include <sys/mman.h>
#include <system_error>
#include <memory>

struct MmapDeleter {
    size_t length{0};
    void operator()(std::byte *ptr) const noexcept {
        if (ptr != MAP_FAILED && ptr != nullptr) {
            ::munmap(ptr, length);
        }
    }
};

using UniqueHugeMapping = std::unique_ptr<std::byte[], MmapDeleter>;

UniqueHugeMapping allocate_hugepages_2m(size_t size) {
    void *ptr = ::mmap(nullptr, size, PROT_READ | PROT_WRITE,
                       MAP_ANONYMOUS | MAP_PRIVATE | MAP_HUGETLB | MAP_HUGE_2MB,
                       -1, 0);
    if (ptr == MAP_FAILED) {
        throw std::system_error(errno, std::generic_category(), "mmap 2M hugepages failed");
    }
    return UniqueHugeMapping{static_cast<std::byte*>(ptr), MmapDeleter{size}};
}
```
:::

## Інтерфейси діагностики та статистики: DebugFS та KVM_GET_STATS_FD

Ядро KVM експортує глобальні лічильники та внутрішню статистику підсистеми MMU через віртуальну файлову систему DebugFS (за замовчуванням монтується в `/sys/kernel/debug/kvm/`) та бінарний дескрипторний інтерфейс `KVM_GET_STATS_FD`.

Для кожної запущеної віртуальної машини в DebugFS створюється окрема тека `/sys/kernel/debug/kvm/<pid>-<fd>/`.

| Назва лічильника | Шлях у DebugFS | Тип | Діагностичне значення та інтерпретація |
| :--- | :--- | :--- | :--- |
| `mmu_shadow_zapped` | `.../mmu_shadow_zapped` | `u64` | Кількість видалених (занулених) службових сторінок дерев сторінок KVM MMU. Збільшується при зміні/видаленні memslot, вивільненні пам'яті хостом або демонтажі віртуальної машини. |
| `mmu_pte_write` | `.../mmu_pte_write` | `u64` | Кількість прямих записів гостя у власні таблиці сторінок, перехоплених Shadow MMU. У конфігураціях із чистим EPT/NPT дорівнює `0`. Високі значення свідчать про активну роботу програмної емуляції тіньових таблиць. |
| `mmu_pde_zapped` | `.../mmu_pde_zapped` | `u64` | Кількість скинутих дескрипторів каталогів сторінок другого рівня (PDE). Фіксує розбиття великих блоків на сторінки меншого розміру під час захисту пам'яті. |
| `mmu_flooded` | `.../mmu_flooded` | `u64` | Кількість подій «затоплення тіньових сторінок» (Shadow Page Flooding). Спрацьовує, коли гість виконує лавину записів у сторінку власних таблиць; KVM тимчасово знімає захист від запису (unshadow), щоб уникнути нескінченних `VM-exit`. |
| `tdp_mmu_mapped_2m` | `.../tdp_mmu_mapped_2m` | `u64` | Поточна кількість сторінок розміром 2 МіБ, активних у таблицях EPT/NPT масштабованого рушія TDP MMU. Дозволяє оцінити ефективність використання Hugepages. |
| `tdp_mmu_mapped_1g` | `.../tdp_mmu_mapped_1g` | `u64` | Поточна кількість гігабайтних сторінок (1 ГіБ), відображених у деревах TDP MMU. |
| `mmu_recycled` | `.../mmu_recycled` | `u64` | Кількість тіньових сторінок, примусово вивільнених та повторно використаних через досягнення ліміту `shadow_mem_size`. |
| `mmu_cache_miss` | `.../mmu_cache_miss` | `u64` | Кількість промахів внутрішнього кешу структур сторінок KVM під час пошуку вільного дескриптора `struct kvm_mmu_page`. |
| `hugepages` | `.../hugepages` | `u64` | Загальна кількість успішних спроб відображення великих сторінок (2M/1G) під час обробки збоїв трансляції. |

### Бінарний інтерфейс телеметрії: KVM_GET_STATS_FD (Linux 5.15+)

Читання текстових файлів у DebugFS створює відчутні накладні витрати (парсинг ASCII, багатократне відкриття дескрипторів). Починаючи з Linux 5.15, гіпервізор може отримати доступ до всієї телеметрії VM або окремого vCPU за один виклик `ioctl(vm_fd, KVM_GET_STATS_FD, NULL)`.

Виклик повертає анонімний файловий дескриптор `stats_fd`, з якого можна прочитати бінарний заголовок та масив дескрипторів:

1. **Заголовок `struct kvm_stats_header`**:
   - `flags` (`__u32`): Прапорці формату.
   - `num_desc` (`__u32`): Кількість доступних дескрипторів метрик.
   - `id_offset` (`__u32`): Зсув рядка ідентифікатора VM у буфері.
   - `desc_offset` (`__u32`): Зсув масиву дескрипторів `struct kvm_stats_desc`.
   - `data_offset` (`__u32`): Зсув блоку 64-бітних числових значень лічильників.
2. **Дескриптор метрики `struct kvm_stats_desc`**:
   - `flags` (`__u32`): Тип метрики (кумулятивний лічильник `KVM_STATS_TYPE_CUMULATIVE`, поточний рівень `KVM_STATS_TYPE_INSTANT`, пік `KVM_STATS_TYPE_PEAK`, лінійна або логарифмічна гістограма) та одиниці виміру (`KVM_STATS_UNIT_BYTES`, `KVM_STATS_UNIT_CYCLES`, `KVM_STATS_UNIT_SECONDS`, `KVM_STATS_UNIT_NONE`).
   - `exponent` (`__s16`): Десятковий масштаб показника (наприклад, `-9` для наносекунд).
   - `size` (`__u16`): Кількість елементів у масиві значень.
   - `offset` (`__u32`): Зсув значення метрики всередині блоку `data_offset`.
   - `name[KVM_STATS_NAME_SIZE]` (`char[64]`): Символьна назва метрики (наприклад, `"tdp_mmu_mapped_2m"` або `"pages_4k"`).

Отримання даних з `stats_fd` виконується звичайним атомарним системним викликом `read()` або `pread()`, що дозволяє знімати телеметрію MMU з частотою 1000 Гц без сповільнення роботи гостьових процесорів.

:::tabs
```c
#include <linux/kvm.h>
#include <sys/ioctl.h>
#include <unistd.h>
#include <stdint.h>

/* Отримання дескриптора бінарної статистики віртуальної машини */
int kvm_open_stats_fd(int vm_or_vcpu_fd) {
    return ioctl(vm_or_vcpu_fd, KVM_GET_STATS_FD, NULL);
}
```
```cpp
#include <linux/kvm.h>
#include <sys/ioctl.h>
#include <unistd.h>
#include <system_error>

/* RAII-дескриптор інтерфейсу бінарної статистики KVM */
class KvmStatsFile {
    int fd_{-1};
public:
    explicit KvmStatsFile(int vm_or_vcpu_fd) {
        fd_ = ::ioctl(vm_or_vcpu_fd, KVM_GET_STATS_FD, nullptr);
        if (fd_ < 0) {
            throw std::system_error(errno, std::generic_category(), "KVM_GET_STATS_FD failed");
        }
    }
    ~KvmStatsFile() noexcept {
        if (fd_ >= 0) {
            ::close(fd_);
        }
    }
    int get() const noexcept { return fd_; }
};
```
:::

## Точки динамічного трасування (Tracepoints)

Підсистема KVM MMU експортує набір точок динамічного перехоплення через інтерфейс `tracefs` (за замовчуванням монтується в `/sys/kernel/tracing/events/kvm/`). Вони дозволяють аналізувати продуктивність та локалізувати проблеми віртуалізації без модифікації коду ядра.

| Назва точки трасування | Формат події та ключові поля | Умови виникнення та діагностичне значення |
| :--- | :--- | :--- |
| `kvm_exit` | `unsigned int exit_reason`, `unsigned long guest_rip`, `u32 isa`, `u64 info1`, `u64 info2` | Фіксує будь-який вихід із гостьового режиму (`VM-exit`). На Intel EPT код `0x30` (48) означає `EPT_VIOLATION`, код `0x31` (49) — `EPT_MISCONFIG`, а код `0x3E` (62) — `PML_FULL`. На AMD-V код `0x400` (1024) означає `VMEXIT_NPF`. Поле `info1` містить кваліфікацію виходу, `info2` — фізичну адресу `GPA`. |
| `kvm_page_fault` | `u64 fault_address`, `u32 error_code` | Виникає при виявленні потреби у виділенні сторінки або розв'язанні конфлікту прав доступу в KVM MMU. |
| `kvm_mmu_page_fault` | `unsigned long gva`, `u32 error_code` | Початок роботи внутрішнього диспетчера обробки збоїв пам'яті KVM. |
| `kvm_tdp_mmu_spte_changed` | `int as_id`, `gfn_t gfn`, `int level`, `u64 old_spte`, `u64 new_spte` | Спрацьовує в масштабованому TDP MMU щоразу, коли запис таблиці (`SPTE`) оновлюється атомарною операцією `cmpxchg` (встановлення відображення, розбиття 2MB-сторінки або скидання прапорця запису). |
| `kvm_mmu_get_page` | `unsigned long gfn`, `int level`, `int created` | Запит на отримання або створення службової структури `struct kvm_mmu_page` для проміжного вузла дерева сторінок. |
| `kvm_mmu_prepare_zap_page` | `unsigned long gfn`, `int level` | Підготовка до видалення (занулення) сторінки або цілого піддерева з таблиць KVM MMU під час скидання слота пам'яті, ballooning чи відключення пристрою. |
| `kvm_mmu_spte_requested` | `u64 spte`, `u64 addr` | Діагностична подія формування нового дескриптора сторінки перед його записом у фізичну пам'ять EPT. |
| `kvm_pml_full` | `unsigned int vcpu_id` | Виникає при заповненні апаратного буфера логування сторінок PML (512 записів) перед скиданням у бітову карту ядра. |

### Практичний рецепт фільтрації подій через CLI

Для швидкого перегляду виходів з причини EPT Violation без написання сторонніх утиліт використовують текстові фільтри ядра:

```bash
# Увімкнути фільтрацію виходів лише для EPT Violation (код 48 / 0x30)
echo "exit_reason == 48" > /sys/kernel/tracing/events/kvm/kvm_exit/filter
echo 1 > /sys/kernel/tracing/events/kvm/kvm_exit/enable

# Читання потоку подій у реальному часі
cat /sys/kernel/tracing/trace_pipe
```

Під час аналізу поле `info2` містить точну адресу `GPA`, яка спровокувала збій, а `info1` кодує бітову маску причини (читання відсутньої сторінки, спроба запису або виконання коду).

Після завершення діагностики обов'язково вимкніть трасування:

```bash
echo 0 > /sys/kernel/tracing/events/kvm/kvm_exit/enable
echo > /sys/kernel/tracing/events/kvm/kvm_exit/filter
```
