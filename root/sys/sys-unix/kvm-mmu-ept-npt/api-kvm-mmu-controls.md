# 📋 Інтерфейси керування KVM MMU: параметри ядра, ioctl і події tracefs

Підсистема віртуалізації пам'яті KVM надає три рівні керування та діагностики: параметри завантаження та виконання модулів ядра хоста (`kvm`, `kvm_intel`, `kvm_amd`), набір системних викликів `ioctl` для простору користувача гіпервізора (VMM) над дескрипторами віртуальної машини, а також інтерфейс динамічного спостереження за подіями MMU через точки трасування ядра (`tracepoints`).

## Параметри модулів ядра Linux

Параметри модулів визначають глобальну архітектурну поведінку підсистеми пам'яті KVM для всіх віртуальних машин, запущених на хості. Їх можна задавати під час завантаження ядра в командному рядку (наприклад, `kvm.tdp_mmu=Y`) або змінювати динамічно через файли в псевдофайловій системі `/sys/module/<модуль>/parameters/`.

| Параметр | Модуль ядра | Тип | Замовчування | Детальний опис та призначення |
| :--- | :--- | :--- | :--- | :--- |
| `tdp_mmu` | `kvm` | `bool` | `Y` (1) | Вмикає сучасний масштабований рушій Two-Dimensional Paging MMU (на базі RCU та атомарного CAS). При значенні `N` KVM використовує спадковий рушій із монопольним замком `mmu_lock`. |
| `ept` | `kvm_intel` | `bool` | `Y` (1) | Дозволяє апаратну трансляцію Extended Page Tables на процесорах Intel VT-x. При значенні `N` KVM примусово деградує до програмних тіньових таблиць (Shadow Page Tables). |
| `eptad` | `kvm_intel` | `bool` | `Y` (1) | Дозволяє апаратне встановлення бітів Accessed (A) та Dirty (D) у дескрипторах EPT силами самого MMU процесора. Знижує кількість `VM-exit` при перших доступах до пам'яті. |
| `npt` | `kvm_amd` | `bool` | `1` (Y) | Дозволяє апаратну трансляцію Nested Page Tables (Rapid Virtualization Indexing) на процесорах AMD-V. |
| `mmu_audit` | `kvm` | `bool` | `N` (0) | Активує внутрішній діагностичний аудит дерев сторінок KVM після кожної модифікації. Призначений виключно для розробників ядра; викликає помітне сповільнення роботи. |
| `nx_huge_pages` | `kvm` | `bool` / `int` | `auto` | Захист від апаратної вразливості iTLB Multihit (CVE-2018-12207): забороняє виконання коду на сторінках 2MB/1GB, автоматично розбиваючи їх на сторінки 4KB при спробі виконання. |
| `nx_huge_pages_recovery_ratio` | `kvm` | `uint` | `60` | Керує періодичністю відновлення великих сторінок фоновим потоком після того, як виконання коду на них припинилося. |
| `shadow_mem_size` | `kvm` | `ulong` | `0` | Фіксує максимальний розмір оперативної пам'яті хоста, який дозволено виділяти під структури тіньових таблиць або службові сторінки KVM MMU. |

Ці параметри дозволяють тонко налаштовувати баланс між безпекою (захист від iTLB multihit), швидкістю первинного доступу до пам'яті та масштабованістю під час запуску сотень паралельних потоків гостя.

## Інтерфейс ioctl керування пам'яттю з простору користувача

Гіпервізор простору користувача (QEMU, Cloud Hypervisor, crosvm або Firecracker) керує відображенням пам'яті гостя за допомогою системних викликів `ioctl` над файловим дескриптором віртуальної машини `vm_fd` (створеним через `open("/dev/kvm")` та `ioctl(kvm_fd, KVM_CREATE_VM, 0)`).

### 1. Реєстрація слотів пам'яті: KVM_SET_USER_MEMORY_REGION2

Системний виклик `KVM_SET_USER_MEMORY_REGION2` (розширення класичного виклику `KVM_SET_USER_MEMORY_REGION`) є основним методом побудови фізичного адресного простору гостя (`GPA`). Він пов'язує лінійний діапазон фізичних адрес гостя з виділеним віртуальним буфером у процесі VMM (`HVA`).

```c
#include <linux/kvm.h>

/* Базова структура першої версії (для зворотної сумісності) */
struct kvm_userspace_memory_region {
    __u32 slot;
    __u32 flags;
    __u64 guest_phys_addr;
    __u64 memory_size;
    __u64 userspace_addr;
};

/* Розширена структура другої версії (Linux 6.8+) */
struct kvm_userspace_memory_region2 {
    __u32 slot;            /* Унікальний індекс слота (0 .. KVM_USER_MEM_SLOTS - 1) */
    __u32 flags;           /* Конфігураційні прапорці слота пам'яті */
    __u64 guest_phys_addr; /* Початкова фізична адреса гостя (GPA, вирівняна на 4 КіБ) */
    __u64 memory_size;     /* Розмір регіону в байтах (повинен бути кратним 4 КіБ) */
    __u64 userspace_addr;  /* Віртуальна адреса буфера хоста (HVA, повернута mmap) */
    __u64 guest_memfd_offset; /* Зсув у файлі guest_memfd (для конфіденційних VM) */
    __u32 guest_memfd;     /* Файловий дескриптор анонімної пам'яті guest_memfd */
    __u32 pad1;
    __u64 pad2[14];
};

/* Приклад виклику в гіпервізорі */
int ret = ioctl(vm_fd, KVM_SET_USER_MEMORY_REGION2, &region);
```

#### Життєвий цикл слота та правила валідації KVM:
- **Обмеження кількості слотів**: Ядро Linux обмежує максимальну кількість одночасно зареєстрованих слотів пам'яті константою `KVM_USER_MEM_SLOTS` (зазвичай 512 слотів). Цього достатньо для розміщення RAM, відеопам'яті VGA, регіонів PCI MMIO та декількох гаряче підключених модулів NVDIMM/RAM.
- **Вимоги до вирівнювання**: Адреса `guest_phys_addr` та розмір `memory_size` обов'язково мають бути вирівняні за межею системної сторінки (4096 байтів). При порушенні вирівнювання ядро повертає помилку `-EINVAL`.
- **Перевірка адреси простору користувача**: Значення `userspace_addr` повинно вказувати на дійсний анонімний або файловий діапазон віртуальної пам'яті процесу VMM. Якщо адреса недоступна або порушує права доступу сторінок хоста, під час першого ж звернення гостя ядро згенерує помилку `-EFAULT`.
- **Перекриття діапазонів**: Два активних слоти пам'яті не можуть перекриватися за адресами `GPA`. Спроба зареєструвати регіон, який перетинається з уже наявним слотом, завершується помилкою `-EEXIST`.
- **Створення або розширення слота**: Коли VMM виділяє діапазон пам'яті (наприклад, додає планку віртуального ОЗП), він заповнює поля `guest_phys_addr` та `memory_size` ненульовими значеннями.
- **Видалення слота**: Щоб вилучити регіон пам'яті, достатньо передати структуру з тим самим індексом `slot`, але встановити `memory_size = 0`. KVM негайно ініціює очищення відповідних записів у деревах EPT (`zapping`).

#### Прапорці `flags`:
- `KVM_MEM_LOG_DIRTY_PAGES` (`1 << 0`): Вмикає відстеження модифікацій пам'яті (Dirty Logging). При активації цього прапорця KVM скидає біти запису `W` у записах EPT/NPT для цього слота. Будь-яка подальша спроба запису гостя викличе `EPT Violation`, зафіксує номер сторінки в бітовій карті брудних сторінок і поновить дозвіл на запис.
- `KVM_MEM_READONLY` (`1 << 1`): Позначає весь діапазон пам'яті як доступний гостю лише для читання. Будь-який запис викликає помилку або емуляцію MMIO. Використовується для емуляції мікропрограм BIOS/UEFI ROM.
- `KVM_MEM_GUEST_MEMFD` (`1 << 2`): Вказує, що пам'ять прив'язана до спеціального ізольованого файлового дескриптора `guest_memfd` (Linux 6.8+). Ця пам'ять недоступна для читання процесу хоста і використовується технологіями конфіденційних обчислень (AMD SEV-SNP, Intel TDX).

### 2. Отримання та очищення карти брудних сторінок

Під час живої міграції віртуальної машини гіпервізор циклічно копіює змінені сторінки на цільовий сервер. Для цього використовуються виклики `KVM_GET_DIRTY_LOG` та високоефективний атомарний виклик `KVM_CLEAR_DIRTY_LOG`.

```c
struct kvm_dirty_log {
    __u32 slot;            /* Номер слота пам'яті */
    __u32 padding1;
    union {
        void *dirty_bitmap; /* Вказівник на виділений буфер бітової карти */
        __u64 padding2;
    };
};

struct kvm_clear_dirty_log {
    __u32 slot;            /* Номер слота пам'яті */
    __u32 num_pages;       /* Кількість сторінок для скидання */
    __u64 first_page;      /* Індекс першої сторінки діапазону */
    union {
        void *dirty_bitmap; /* Вказівник на бітову маску очищених сторінок */
        __u64 padding2;
    };
};
```

Виклик `KVM_CLEAR_DIRTY_LOG` є величезним кроком уперед порівняно зі застарілим `KVM_GET_DIRTY_LOG`. Замість того, щоб зупиняти всі vCPU, скидати захист з усього адресного простору і копіювати гігабайтні бітові карти за один раз, `KVM_CLEAR_DIRTY_LOG` дозволяє гіпервізору очищати прапорці брудності невеликими порціями (наприклад, по 64 сторінки) безпосередньо перед відправленням їх мережею. Це усуває сплески затримок гостя та дозволяє завершувати живу міграцію без відчутних пауз у роботі сервісів.

### 3. Емуляція трансляції адрес: KVM_TRANSLATE

Виконується над файловим дескриптором віртуального процесора `vcpu_fd` для програмного перекладу віртуальної адреси гостя (`GVA`) у фізичну адресу гостя (`GPA`). Це дозволяє зневаджувачам (GDB stub у QEMU) інспектувати структури даних гостьової ОС без виконання інструкцій гостьовим процесором.

```c
struct kvm_translation {
    /* Вхідне поле */
    __u64 linear_address;  /* Віртуальна адреса гостя (GVA) */

    /* Вихідні поля стану */
    __u64 physical_address;/* Фізична адреса гостя (GPA) */
    __u8  valid;           /* 1 — трансляція успішна, 0 — виник page fault */
    __u8  writeable;       /* 1 — сторінка дозволена на запис */
    __u8  usermode;        /* 1 — сторінка доступна з неривілейованого Ring 3 */
    __u8  pad[5];
};

/* Виклик трансляції адреси */
int ret = ioctl(vcpu_fd, KVM_TRANSLATE, &translation);
```

Якщо трансляція завершується успішно (`valid == 1`), поле `physical_address` містить значення `GPA`. Якщо гостьові таблиці не містять відповідного відображення, поле `valid` отримує значення `0`, дозволяючи гіпервізору точно зрозуміти, чи доступна пам'ять процесу гостя.

## Точки динамічного трасування (Tracepoints)

Підсистема KVM MMU експортує набір точок динамічного перехоплення через інтерфейс `tracefs` (за замовчуванням монтується в `/sys/kernel/tracing/events/kvm/`). Вони дозволяють аналізувати продуктивність та локалізувати проблеми віртуалізації без модифікації коду ядра.

| Назва точки трасування | Формат події та ключові поля | Умови виникнення та діагностичне значення |
| :--- | :--- | :--- |
| `kvm_exit` | `unsigned int exit_reason`, `unsigned long guest_rip`, `u32 isa`, `u64 info1`, `u64 info2` | Фіксує будь-який вихід із гостьового режиму (`VM-exit`). На Intel EPT код `0x30` (48) означає `EPT_VIOLATION`, а код `0x31` (49) — `EPT_MISCONFIG`. Поле `info1` містить кваліфікацію виходу, `info2` — фізичну адресу `GPA`. |
| `kvm_page_fault` | `u64 fault_address`, `u32 error_code` | Виникає при виявленні потреби у виділенні сторінки або розв'язанні конфлікту прав доступу в KVM MMU. |
| `kvm_mmu_page_fault` | `unsigned long gva`, `u32 error_code` | Початок роботи внутрішнього диспетчера обробки збоїв пам'яті KVM. |
| `kvm_tdp_mmu_spte_changed` | `int as_id`, `gfn_t gfn`, `int level`, `u64 old_spte`, `u64 new_spte` | Спрацьовує в масштабованому TDP MMU щоразу, коли запис таблиці (`SPTE`) оновлюється атомарною операцією `cmpxchg` (встановлення відображення, розбиття 2MB-сторінки або скидання прапорця запису). |
| `kvm_mmu_get_page` | `unsigned long gfn`, `int level`, `int created` | Запит на отримання або створення службової структури `struct kvm_mmu_page` для проміжного вузла дерева сторінок. |
| `kvm_mmu_prepare_zap_page` | `unsigned long gfn`, `int level` | Підготовка до видалення (занулення) сторінки або цілого піддерева з таблиць KVM MMU під час скидання слота пам'яті чи відключення пристрою. |
| `kvm_mmu_spte_requested` | `u64 spte`, `u64 addr` | Діагностична подія формування нового дескриптора сторінки перед його записом у фізичну пам'ять EPT. |

### Зв'язок із динамічним роздуванням пам'яті (Memory Ballooning)

Коли драйвер `virtio-balloon` повертає сторінки хосту за допомогою інструкції вивільнення пам'яті (MADV_DONTNEED / guest ballooning), ядро KVM генерує лавину подій `kvm_mmu_prepare_zap_page`. Спостереження за цими подіями у зв'язці з `kvm_tdp_mmu_spte_changed` дозволяє оцінити швидкість реакції гіпервізора на динамічну зміну доступного обсягу пам'яті під навантаженням.

### Практичний рецепт фільтрації подій через CLI

Для швидкого перегляду виходів з причини EPT Violation без написання власних програм достатньо налаштувати текстові фільтри ядра:

```bash
# Увімкнути фільтрацію виходів лише для EPT Violation (код 48 / 0x30)
echo "exit_reason == 48" > /sys/kernel/tracing/events/kvm/kvm_exit/filter
echo 1 > /sys/kernel/tracing/events/kvm/kvm_exit/enable

# Читання потоку подій у реальному часі
cat /sys/kernel/tracing/trace_pipe
```

Під час аналізу звертайте увагу на поле `info2`: воно містить точну адресу `GPA`, яка спровокувала збій. Порівнявши цю адресу з картою пам'яті в `/proc/iomem` або виводом `qemu-system-x86_64 -d mmu`, можна точно з'ясувати, який компонент гостя або емульований пристрій спричинив навантаження.

Після завершення діагностики обов'язково вимкніть трасування, записавши `0` у файл `enable`, щоб уникнути зайвого споживання процесорного часу.
