# ⚙️ Дослідження поведінки KVM MMU: трасування EPT-подій і вимірювання затримок

Коли гостьова операційна система активно виділяє пам'ять, модифікує таблиці сторінок або бере участь у живій міграції (Live Migration), апаратний блок MMU та гіпервізор KVM виконують сотні тисяч подій `EPT Violation`, оновлень дескрипторів сторінок (`SPTE`) та операцій розбиття великих сторінок (Page Splitting). Інструмент нижче демонструє, як з простору користувача хоста в реальному часі зчитувати, агрегувати та аналізувати метрики KVM MMU через інтерфейс ядра `tracefs`.

## Задача та архітектура інструменту трасування

Діагностика підсистеми віртуалізації пам'яті вимагає спостереження за двовимірною трансляцією адрес (`GVA -> GPA -> HPA`) без внесення відчутного оверхеду в роботу гостьових навантажень. Для повного аудиту життєвого циклу сторінок KVM системному інженеру необхідно відстежувати такі ключові метрики:

1. **Кількість апаратних виходів vCPU через EPT Violation** (код виходу `0x30` / 48 на Intel VT-x або `VMEXIT_NPF` на AMD-V). Спрацьовують при відкладеному виділенні сторінок (Demand Paging), первинному доступі до виділеної пам'яті та модифікації сторінок, захищених від запису механізмом Dirty Logging.
2. **Частоту виникнення EPT Misconfiguration** (код виходу `0x31` / 49 на Intel). Виникають як швидкий шлях диспетчеризації звернень до емульованих пристроїв MMIO (Fast MMIO), або сигналізують про критичні помилки некоректного форматування бітів у дескрипторах EPT.
3. **Загальну кількість збоїв сторінок (Page Faults)**, переданих у диспетчер KVM MMU (`kvm_page_fault` / `kvm_mmu_page_fault`).
4. **Частоту структурних змін дерева сторінок**: створення нових проміжних таблиць (`kvm_mmu_get_page`) та атомарні зміни листових дескрипторів (`kvm_tdp_mmu_spte_changed` або `kvm_mmu_set_spte`).

```
┌──────────────────────────────────────────────────────────────┐
│                    Простір користувача                       │
│                                                              │
│   kvm_mmu_tracer (C / C++20)                                 │
│   ├── Відкриття /sys/kernel/tracing/trace_pipe               │
│   ├── Парсинг рядків подій (kvm_exit, kvm_page_fault)        │
│   └── Секундне вікно агрегації (Violations/s, Misconfigs/s)  │
└──────────────────────────────▲───────────────────────────────┘
                               │ Потік текстових подій (trace_pipe)
═══════════════════════════════╪════════════════════════════════
┌──────────────────────────────┴───────────────────────────────┐
│                         Ядро Linux                           │
│                                                              │
│   Кільцеві буфери Ftrace (Per-CPU Ring Buffers)              │
│   ├── events/kvm/kvm_exit (exit_reason=48/49, GPA, RIP)      │
│   ├── events/kvm/kvm_page_fault (gva, error_code)            │
│   └── events/kvm/kvm_tdp_mmu_spte_changed (gfn, old/new SPTE)│
│                              ▲                               │
│   Підсистема KVM MMU         │ Запис у кільцевий буфер       │

│                              ▲                               │
│   Апаратний процесор (VT-x)  │ VM-exit (EPT Violation / Misconfig)
│   └── vCPU execution (Guest Virtual ──> Guest Physical ──> Host Physical)
└──────────────────────────────────────────────────────────────┘
```

### Вибір між інтерфейсом tracefs та BPF

Для інструментів моніторингу віртуалізації існує два основних підходи:
- **Потоковий інтерфейс `tracefs` / `trace_pipe`**: Не потребує сторонніх бібліотек, заголовків ядра чи компіляторів на хості. Утиліта збирається звичайним компілятором C/C++ у статичний або динамічний бінарник мінімального розміру й миттєво запускається в апаратних гіпервізорах, контейнерах обслуговування чи мінімалістичних дистрибутивах (Alpine Linux, Yocto, Bare-metal hypervisors), де LLVM/Clang та Clang BPF toolchain недоступні.
- **Внутрішньоядерне агрегування через eBPF / BPF tracepoints**: Доцільне при підрахунку високочастотних гістограм затримок (наприклад, точного часу виконання функції `tdp_page_fault` на рівні наносекунд для кожного окремого vCPU), де передача мільйонів рядків у простір користувача створила б зайве навантаження на шину пам'яті.

Розглянута нижче утиліта реалізує перший підхід: нульові зовнішні залежності, гарантоване очищення стану через обробку сигналів або ідіоматичний C++ RAII та висока швидкість зчитування.

## Точки трасування KVM MMU та їхній контракт даних

Підсистема KVM MMU експортує у псевдофайлову систему `tracefs` низку спеціалізованих точок перехоплення. Кожна точка відповідає певному етапу обробки двовимірної трансляції в ядрі.

```
                  Гостьовий vCPU звертається до пам'яті
                                    │
                                    ▼
                         [ Промах у TLB гостя ]
                                    │
                                    ▼
                         [ Апаратний 2D Walk ]
                                    │
                         ┌──────────┴──────────┐
                EPT Запис відсутній     Формат запису EPT
                або порушено права      містить Reserved Bits
                         │                     │
                         ▼                     ▼
              VM-exit: EPT Violation   VM-exit: EPT Misconfiguration
              (Exit Reason = 48)       (Exit Reason = 49)
                         │                     │
  kvm_exit ──────────────┤                     ├────────────── kvm_exit
                         ▼                     ▼
              kvm_mmu_page_fault()     handle_fast_mmio()
                         │                     │
  kvm_page_fault ────────┤                     └─ [ Завершення MMIO ]
                         ▼
              tdp_page_fault()
                         │
  kvm_mmu_get_page ──────┼─ [ Виділення нової таблиці EPT ]
                         │
  kvm_tdp_mmu_spte_changed ─ [ Атомарне встановлення зв'язку GPA -> HPA ]
                         │
                         ▼
              vCPU повертається в гостя
```

### 1. `kvm_exit` — фіксація апаратного виходу vCPU

Точка трасування верхнього рівня вхідного диспетчера віртуалізації. Генерується під час повернення керування з гостьового режиму в гіпервізор хоста.

- **Розташування в tracefs**: `events/kvm/kvm_exit/`
- **Формат полів події**:
  - `unsigned int exit_reason` — числовий код причини виходу (на Intel VT-x: `0x30` / 48 — `EXIT_REASON_EPT_VIOLATION`, `0x31` / 49 — `EXIT_REASON_EPT_MISCONFIG`; на AMD-V: `0x400` — `VMEXIT_NPF`).
  - `unsigned long guest_rip` — значення гостьового лічильника інструкцій на момент виникнення події.
  - `u32 isa` — архітектура апаратного розширення (`1` для `KVM_ISA_VMX`, `2` для `KVM_ISA_SVM`).
  - `u64 info1` — бітова кваліфікація виходу (`Exit Qualification` зі структури VMCS), яка описує тип спроби доступу (читання, запис або виконання коду, стан трансляції гостьового лінійного простору).
  - `u64 info2` — фізична адреса гостя (`GPA`), звернення до якої спровокувало збій.

### 2. `kvm_page_fault` та `kvm_mmu_page_fault` — диспетчеризація збою сторінки

Спрацьовують на початку виконання внутрішніх функцій KVM MMU при вході в обробник збою:

- **Розташування**: `events/kvm/kvm_page_fault/` та `events/kvm/kvm_mmu_page_fault/`
- **Формат полів**:
  - `u64 fault_address` / `unsigned long gva` — адреса пам'яті, що спричинила збій.
  - `u32 error_code` — бітова маска помилки (наявність сторінки, спроба запису `PFERR_WRITE_MASK`, виконання інструкції `PFERR_FETCH_MASK`, рівень доступу користувача або суперкористувача).

### 3. `kvm_mmu_get_page` — створення та отримання структури таблиці сторінок

Фіксує роботу з вузлами ієрархії сторінкових структур KVM (`struct kvm_mmu_page`):

- **Розташування**: `events/kvm/kvm_mmu_get_page/`
- **Формат полів**:
  - `unsigned long gfn` — номер гостьового фрейму пам'яті (Guest Frame Number, `GPA >> 12`), для якого створюється або шукається проміжна таблиця.
  - `int level` — рівень створюваної таблиці в дереві EPT (рівень 4 для PML4, 3 для PDPT, 2 для PD, 1 для PT).
  - `int created` — бінарний прапорець: значення `1` свідчить про виділення нового фізичного фрейму хоста під таблицю сторінок; значення `0` вказує на повторне використання вже наявної структури в кеші KVM MMU.

### 4. `kvm_mmu_spte_requested` та `kvm_mmu_set_spte` — конструювання дескриптора

Точки трасування класичного рушія KVM MMU (Legacy Shadow/EPT MMU), які фіксують формування 64-бітного значення дескриптора `SPTE` перед його записом у пам'ять:

- **Розташування**: `events/kvm/kvm_mmu_spte_requested/` та `events/kvm/kvm_mmu_set_spte/`
- **Формат полів**: `u64 spte` (нове бітове значення дескриптора з правами `R/W/X` та фізичною адресою `HPA`) та `u64 addr` / `gfn_t gfn`.

### 5. `kvm_tdp_mmu_spte_changed` — атомарна зміна запису в TDP MMU

Ключова точка сучасного масштабованого рушія Two-Dimensional Paging MMU (в ядрі Linux 5.10+). Фіксує успішне оновлення дескриптора сторінки за допомогою атомарної інструкції `cmpxchg64`:

- **Розташування**: `events/kvm/kvm_tdp_mmu_spte_changed/`
- **Формат полів**:
  - `int as_id` — числовий ідентифікатор адресного простору (Address Space ID).
  - `gfn_t gfn` — базовий номер гостьового фрейму.
  - `int level` — рівень таблиці EPT (`1` — сторінка 4 КіБ, `2` — сторінка 2 МіБ, `3` — 1 ГіБ).
  - `u64 old_spte` — попереднє бітове значення дескриптора.
  - `u64 new_spte` — нове встановлене значення дескриптора.

Аналіз переходів `old_spte -> new_spte` дозволяє безпосередньо бачити життєвий цикл пам'яті:
- **Первинне виділення (Demand Paging)**: `old_spte == 0`, `new_spte != 0` (сторінка присутня, встановлено біти `R/W/X`).
- **Встановлення захисту від запису (Write Protection)**: `old_spte` містить біт запису `W=1`, у `new_spte` біт `W=0` (активація Dirty Logging під час Live Migration).
- **Розбиття великої сторінки (Page Splitting)**: `old_spte` мав встановлений біт великої сторінки `PS=1` на рівні `level=2`, а `new_spte` стає покажчиком на нову таблицю рівня `level=1`.
- **Звільнення сторінки (Zapping / Unmapping)**: `old_spte != 0`, `new_spte == 0` (повернення пам'яті через virtio-balloon або видалення слота).

## Розрахунок метрик: кроки 2D Page Walk та типи виходів

### Кількість кроків трансляції (Page Walk Steps)

Коли гостьовий віртуальний процесор виконує звернення до пам'яті, якого немає в буфері асоціативної трансляції (TLB), апаратний блок MMU процесора виконує дворівневий обхід (Two-Dimensional Page Walk). Кількість звернень до фізичної пам'яті хоста визначається формулою:

```
N = (n + 1) · (m + 1) - 1   [двовимірний обхід пам'яті]
```

де `n` — кількість рівнів гостьових таблиць сторінок, а `m` — кількість рівнів хостових таблиць EPT/NPT.

- **Класична адресація 4 КіБ (`n = 4, m = 4`)**:
  `N = (4 + 1) · (4 + 1) - 1 = 24` послідовних звернення до оперативної пам'яті хоста DRAM на один апаратний промах TLB.
- **Сторінки Hugepages 2 МіБ (`n = 3, m = 3`)**:
  `N = (3 + 1) · (3 + 1) - 1 = 15` звернень до пам'яті (скорочення глибини обходу на 37.5%).
- **Гігабайтні сторінки 1 ГіБ (`n = 2, m = 2`)**:
  `N = (2 + 1) · (2 + 1) - 1 = 8` звернень до пам'яті (скорочення глибини обходу на 66.7%).

Детальний математичний аналіз вартості обходу та моделі кешування представлено у [математичному аналізі 2D-обходу та ціни промахів TLB](root:sys-unix/kvm-mmu-ept-npt/math-2d-walk-cost.md).

### Апаратний 2D Walk проти програмного обробника KVM Page Fault

Важливо розрізняти дві принципово різні затримки трансляції:
1. **Апаратний обхід (Hardware 2D Walk)**: Виконується кремнієвим блоком Page Table Walker без виходу з віртуальної машини. Затримка становить від 30 до 75 нс (100–250 тактів процесора) за наявності проміжних записів у кешах процесора L2/L3.
2. **Програмний збій KVM MMU (EPT Violation)**: Викликає повноцінний вихід із віртуальної машини `VM-exit`, збереження контексту регістрів у VMCS, перехід у режим ядра хоста, виклик диспетчера `tdp_page_fault`, пошук `memslot`, виділення фрейму `HPA` та повернення у гостя `VM-entry`. Затримка одного такого збою становить від 1.5 до 5 мкс (4000–15000 тактів ЦП).

Лічильник `EPT Violations/s` у нашій утиліті вимірює саме другу, найдорожчу категорію подій.

### EPT Violation (код 48) проти EPT Misconfiguration (код 49)

- **EPT Violation (0x30 / 48)**: Запит на легітимну трансляцію, яка наразі не прописана в апаратних таблицях (Demand Paging), або спроба запису в пам'ять, позначену прапорцем Write Protection.
- **EPT Misconfiguration (0x31 / 49)**: Виникає, коли апаратний MMU зустрічає в дескрипторі EPT неприпустиме поєднання бітів або встановлений зарезервований біт (Reserved Bit).
  - *Fast MMIO*: KVM навмисно записує зарезервований біт у дескриптори MMIO-діапазонів пристроїв. Під час доступу процесор миттєво генерує `EPT Misconfiguration`, що дозволяє KVM викликати швидкий обробник `handle_fast_mmio()` в обхід повільного розбору структури кваліфікації виходу.
  - *Помилка конфігурації*: Якщо Misconfigurations виникають за межами зареєстрованих MMIO-слотів — це ознака бага в драйвері пам'яті або несумісності типів пам'яті MTRR/PAT.

Детальний перелік структур і прапорців ядра задокументовано в [довіднику інтерфейсів керування KVM MMU](root:sys-unix/kvm-mmu-ept-npt/api-kvm-mmu-controls.md).

## Аналіз впливу Hugepages на затримки обробки збоїв

Розмір сторінок пам'яті кардинально змінює навантаження на підсистему KVM MMU як під час первинного заповнення пам'яті, так і під час фонової роботи гіпервізора.

| Розмір сторінки | Кількість EPT Violations на 1 ГіБ пам'яті | Сумарний час VM-exits на ініціалізацію (при 3 мкс/збій) | Глибина 2D Walk при промаху TLB | Навантаження на `kvm_tdp_mmu_spte_changed` |
| :--- | :--- | :--- | :--- | :--- |
| **4 КіБ (Стандартна)** | 262 144 подій | ≈ 786 мс | 24 звернення | Масове оновлення 262 144 листових записів на рівні `level=1` |
| **2 МіБ (Huge Pages / THP)** | 512 подій | ≈ 1.53 мс | 15 звернень | Лише 512 оновлень дескрипторів на рівні `level=2` (512-кратне скорочення) |
| **1 ГіБ (Gigantic Pages)** | 1 подія | ≈ 0.003 мс (3 мкс) | 8 звернень | 1 атомарний запис на рівні `level=3` |

### Затримки розбиття великих сторінок (Page Splitting)

Коли для віртуальної машини з пам'яттю 2 МіБ вмикається відстеження брудних сторінок (Dirty Logging під час Live Migration), KVM не може захистити від запису весь блок 2 МіБ, оскільки це призвело б до надлишкового копіювання велетенських обсягів незмінених даних мережею.

KVM виконує операцію **Page Splitting**:
1. При першій спробі запису в 2-мегабайтну сторінку виникає `EPT Violation`.
2. KVM виділяє новий фізичний фрейм хоста під таблицю рівня `EPT PT` (генерується подія `kvm_mmu_get_page` з параметрами `level=1, created=1`).
3. Заповнюються 512 записів нової таблиці для кожного 4-кілобайтного піддіапазону.
4. Запис у таблиці `EPT PD` замінюється: скидається прапорець `PS` (подія `kvm_tdp_mmu_spte_changed` на рівні `level=2`), перетворюючи велику сторінку на вказівник на піддерево PT.
5. Здійснюється скидання кешу трансляції інструкцією `INVEPT`.

Цей процес спричиняє характерний короткочасний сплеск частоти `kvm_tdp_mmu_spte_changed` та `kvm_mmu_get_page`, за яким за допомогою нашої утиліти можна точно зафіксувати початок інтенсивної фази міграції. Подальше склеювання сторінок (Collapsing) виконується фоновим демоном ядра `khugepaged`. Детальний огляд еволюції механізмів наведено в [історичному нарисі еволюції віртуалізації пам'яті](root:sys-unix/kvm-mmu-ept-npt/hist-shadow-to-ept.md), а загальні принципи роботи великих сторінок описано в [темі про Huge Pages та досяжність TLB](root:sys-unix/huge-pages-tlb-reach).

## Механіка роботи кільцевого буфера trace_pipe

Ядро Linux виділяє для підсистеми Ftrace ізольований кільцевий буфер (Per-CPU Ring Buffer) на кожне логічне процесорне ядро хоста. Коли віртуальний процесор vCPU генерує подію `VM-exit`, обробник переривання в ядрі записує компактний бінарний дескриптор події в локальний буфер відповідного процесора.

Файл `trace_pipe` працює як потоковий інтерфейс над цими буферами:
- **Деструктивне читання**: Щойно рядок вичитано процесом користувача, ядро негайно вивільняє відповідний слот пам'яті в кільцевому буфері Ftrace.
- **Втрата подій (Lost Events)**: Якщо події надходять швидше, ніж застосунок у просторі користувача встигає їх парсити через системний виклик `read()`, ядро відкидає старі записи й повертає спеціальний рядок-маркер `CPU X: [LOST N EVENTS]`.
- **Блокуюча семантика**: Системний виклик `read()` (або функція `fgets()` / `getline()`) переводить потік у стан очікування події, доки хоча б одне процесорне ядро хоста не запише нову інформацію в кільцевий буфер.

### Архітектурні рішення в коді

1. **Динамічний пошук точки монтування tracefs**: Обидві програми спершу перевіряють стандартний шлях `/sys/kernel/tracing`, а в разі його відсутності звертаються до спадкового шляху `/sys/kernel/debug/tracing`. Якщо обидва шляхи недоступні або відсутні права суперкористувача, утиліта коректно завершується з інформативним повідомленням про помилку.
2. **Гарантоване вимкнення точок трасування**:
   - У версії на **C** встановлюються обробники сигналів `SIGINT` та `SIGTERM` через `signal(..., sig_handler)`. Змінна прапорця зупинки визначена як `volatile sig_atomic_t g_running`, що гарантує коректну обробку переривання процесу з подальшим записом `"0"` у файли `enable` точок трасування.
   - У версії на **C++20** керування життєвим циклом точок трасування інкапсульовано в RAII-клас `TracepointGuard`. Конструктор класу відкриває файли конфігурації через `std::ofstream` і вмикає події, а деструктор гарантовано вимикає їх при виході з блоку `try` або генерації винятків.
3. **Безперервне секундне агрегування**: Замість виклику блокуючих затримок `sleep()`, які перервали б зчитування з `trace_pipe`, утиліта перевіряє часовий інтервал (`time(NULL)` у C або `std::chrono::steady_clock::now()` у C++) на кожній ітерації циклу обробки рядків. Це дозволяє в реальному часі оновлювати лічильники в терміналі за допомогою керуючого символу повернення каретки `\r` без дрейфу таймінгу.
4. **Розбір рядків подій**: Програма виконує пошук сигнатур `kvm_exit:` та `kvm_page_fault:`. Для виходів `kvm_exit` проводиться перевірка числових шістнадцяткових кодів (`reason 0x30`, `reason 0x31`) та їхніх текстових мнемонік (`EPT_VIOLATION`, `EPT_MISCONFIG`), забезпечуючи сумісність з різними версіями ядер Linux (від 4.x до 6.x+).

## Інтерпретація метрик та практичні висновки

1. **Стрибки EPT Violations**: Якщо під час старту застосунків у гості частота EPT Violations сягає 40 000–100 000 подій на секунду, це свідчить про активну роботу Demand Paging. Якщо висока частота тримається стабільно протягом тривалого часу — увімкнено відстеження брудних сторінок (Dirty Logging під час живої міграції або створення бекапу наживо).
2. **Співвідношення з Huge Pages**: Перехід гостя на сторінки 2 МіБ зменшує кількість первинних EPT Violations у 512 разів, оскільки один збій виділяє одразу великий неперервний блок пам'яті замість 512 окремих 4-кілобайтних запитів.
3. **Наявність EPT Misconfigurations**: Поява Misconfigurations за відсутності високого навантаження на емульовані пристрої свідчить про наявність помилок у налаштуванні типів пам'яті MTRR/PAT або вичерпання підтримуваних залізом бітів фізичної адресації.

```bash
# Збірка версії на C:
gcc -O2 -Wall kvm_mmu_tracer.c -o kvm_mmu_tracer

# Збірка версії на C++20:
g++ -std=c++20 -O2 -Wall kvm_mmu_tracer.cpp -o kvm_mmu_tracer_cpp
```

### Запуск трасування та генерація навантаження

Запустіть утиліту на хості з правами суперкористувача:

```bash
sudo ./kvm_mmu_tracer
```

Щоб спровокувати спалах подій EPT Violation, запустіть синтетичний генератор навантаження на пам'ять безпосередньо всередині гостьової віртуальної машини:

```bash
# Всередині гостьової віртуальної машини:
# Виділення та активний запис у 4 ГіБ оперативної пам'яті
stress-ng --vm 4 --vm-bytes 1G --vm-method all --timeout 30s
```

### Спостереження реального виводу в терміналі

Під час виконання тесту на хості утиліта покаже характерну зміну метрик у реальному часі:

```text
Розпочато трасування KVM MMU подій (Ctrl+C для виходу)...
[KVM MMU] EPT Violations: 74210/s | Page Faults: 74210/s | Misconfigs: 142/s | Інші виходи: 1850/s
[KVM MMU] EPT Violations: 68930/s | Page Faults: 68930/s | Misconfigs: 156/s | Інші виходи: 1720/s
[KVM MMU] EPT Violations: 12/s    | Page Faults: 12/s    | Misconfigs: 138/s | Інші виходи: 1640/s
[KVM MMU] EPT Violations: 0/s     | Page Faults: 0/s     | Misconfigs: 140/s | Інші виходи: 1590/s
```

На етапі первинного заповнення сторінок частота `EPT Violations` сягає десятків тисяч на секунду, після чого падає майже до нуля, коли всі фізичні сторінки `HPA` закріплюються в таблицях EPT. Фонова частота `Misconfigs` (130–160 на секунду) відповідає штатним зверненням віртуальної машини до емульованого таймера або vAPIC через Fast MMIO.

### Додаткова верифікація через інструменти ядра

Для детального зіставлення результатів нашої утиліти з внутрішніми лічильниками продуктивності KVM можна паралельно скористатися системними утилітами ядра:

```bash
# Підрахунок статистики виходів vCPU за допомогою perf kvm:
perf kvm stat live

# Запис подій KVM MMU через trace-cmd для наступного аналізу:
trace-cmd record -e kvm:kvm_exit -e kvm:kvm_page_fault -e kvm:kvm_tdp_mmu_spte_changed sleep 10
trace-cmd report | head -n 30
```

## Підводні камені та пастки трасування

- **Блокування читання з trace_pipe**: Потік `trace_pipe` працює як блокуючий канал (pipe). Якщо у віртуальній машині немає активності й процесори перебувають у стані сну `HLT`, нові події не генеруються, і рядок статусу в терміналі оновиться лише після надходження наступного таймерного переривання або зовнішнього мережевого пакета.
- **Оверхед глобального трасування**: Активація точки трасування `kvm_exit` без використання фільтра ядра поширюється на всі віртуальні машини та всі ядра vCPU хоста. На високонавантажених серверах із сотнями vCPU потік текстових подій може перевантажити кільцевий буфер Ftrace (викликаючи появу маркерів втрати подій `[LOST EVENTS]`) та збільшити навантаження на процесори хоста на 5–15%.
  - *Оптимізація фільтрацією*: Для високопродуктивних серверів рекомендується перед увімкненням записувати вираз фільтрації безпосередньо в ядро:
    ```bash
    echo "exit_reason == 48 || exit_reason == 49" > /sys/kernel/tracing/events/kvm/kvm_exit/filter
    ```
- **Конкуренція за потік trace_pipe**: Оскільки читання з `trace_pipe` є деструктивним, одночасний запуск двох процесів зчитування призведе до розриву даних (половина подій потрапить в один процес, половина — в інший).
- **Привілеї доступу**: Будь-які операції запису у файли конфігурації `tracefs` вимагають прав суперкористувача `root` або наявності можливості `CAP_SYS_ADMIN`.
