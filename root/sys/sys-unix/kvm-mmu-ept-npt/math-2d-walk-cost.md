# 🧮 Математика двовимірного обходу: комбінаторика звернень, затримка TLB та вигода Huge Pages

Апаратна віртуалізація пам'яті (Intel EPT та AMD NPT) звільняє гіпервізор від перехоплення змін регістрів `CR3`, проте перекладає обчислювальний тягар трансляції адрес на апаратний блок обходу таблиць — Page Table Walker. При кожному промаху буфера асоціативної трансляції (TLB) процесор змушений виконувати двовимірний обхід пам'яті (Two-Dimensional Page Walk), а у випадках вкладеної віртуалізації — тривимірний обхід (3D Page Walk).

Нижче наведено строгий математичний аналіз комбінаторики звернень до фізичної пам'яті хоста, формальну модель 2D- та 3D-обходу для 4- та 5-рівневої адресації, матрицю оптимізацій через сторінки Huge Pages, багаторівневу ймовірнісну модель часу доступу (EMAT) з урахуванням кешів трансляції, а також розрахунок витрат на оновлення апаратних бітів Accessed/Dirty та модель охоплення TLB.

## Формальна модель двовимірного обходу пам'яті (2D Page Walk)

Нехай гостьова операційна система використовує `g`-рівневу структуру таблиць сторінок для перетворення віртуальної адреси гостя (`GVA`) у фізичну адресу гостя (`GPA`). Нехай апаратний блок розширених таблиць хоста (Intel EPT або AMD NPT) використовує `h`-рівневу структуру для перетворення проміжної адреси `GPA` у реальну фізичну адресу хоста (`HPA`).

Будь-яка адреса, якою оперує гостьовий процесор (значення регістра `CR3` та покажчики на дескриптори всіх проміжних рівнів), належить до гостьового фізичного адресного простору `GPA`. Перед тим як апаратний транслятор зможе прочитати бодай один байт гостьової таблиці, він мусить перекласти відповідну адресу `GPA` через усі `h` рівнів хостової таблиці EPT.

Позначимо кількість звернень до фізичної пам'яті хоста на кожному етапі трансляції при холодному промаху всіх кешів:

```
Крок 0 (Початкова трансляція гостьового покажчика CR3):
N₀ = h                                      [трансляція GPA кореня PML4 гостя через h рівнів хостового EPT]

Кроки 1 .. g (Трансляція проміжних та листових гостьових таблиць):
N₁ = 1 + h                                  [1 читання PML4E + h звернень EPT для трансляції GPA таблиці PDPT]
N₂ = 1 + h                                  [1 читання PDPTE + h звернень EPT для трансляції GPA каталогу PD]
N₃ = 1 + h                                  [1 читання PDE + h звернень EPT для трансляції GPA таблиці PT]
...
N_g = 1 + h                                 [1 читання листового PTE + h звернень EPT для трансляції фінального GPA сторінки]
```

Загальна кількість звернень до фізичної оперативної пам'яті DRAM виключно для виконання обходу таблиць MMU (`W`):

```
W = N₀ + ∑_{k=1}^{g} N_k
= h + g · (1 + h)                           [підставили N₀ = h та g однакових кроків (1 + h)]
= h + g · h + g                             [розкрили дужки]
= (g + 1) · h + g                           [згрупували доданки за множником (g + 1)]
= (g + 1) · h + (g + 1) - 1                 [додали та відняли одиницю]
= (g + 1) · (h + 1) - 1                     [винесли спільний множник (g + 1)]
```

Якщо врахувати одне фінальне звернення процесора до цільової комірки даних за вже обчисленою адресою HPA (`N_data = 1`), повна кількість звернень до шини пам'яті становить:

```
N_total = W + N_data
= (g + 1) · (h + 1) - 1 + 1                 [додали читання корисних даних]
= (g + 1) · (h + 1)                         [повна кількість звернень на одну інструкцію]
```

### Розрахунок для 4-рівневої адресації (x86-64 4-Level Paging)

У стандартній 64-розрядній архітектурі x86-64 зі сторінками по 4 КіБ маємо `g = 4` (рівні гостя PML4 → PDPT → PD → PT) та `h = 4` (рівні хоста EPT PML4 → EPT PDPT → EPT PD → EPT PT):

```
W_4k = (4 + 1) · 4 + 4
= 5 · 4 + 4                                 [множення]
= 24                                        [звернень до DRAM для 2D-обходу таблиць]

N_total_4k = (4 + 1) · (4 + 1)
= 5 · 5                                     [множення]
= 25                                        [загальна кількість звернень разом із даними]
```

У невіртуалізованій фізичній машині (Native) трансляція регістра `CR3` не потрібна (він уже містить фізичну адресу HPA), а кожен рівень гостьових таблиць читається за 1 звернення. Тому накладні витрати нативного обходу складають `W_native = g = 4` (разом з даними `N_native = 5`).

Коефіцієнт зростання оверхеду обходу під час холодної віртуалізації:

```
K_walk = W_4k / W_native
= 24 / 4                                    [ділення]
= 6.0                                       [шестикратне зростання кількості звернень до DRAM]
```

### Розрахунок для 5-рівневої адресації (5-Level Paging / LA57)

Сучасні серверні процесори підтримують розширення 5-рівневої сторінкової адресації (Paging Level 5 / PML5 з 57-бітним простором віртуальних і фізичних адрес обсягом до 4 петабайтів), де `g = 5` та `h = 5`:

```
W_5lvl = (5 + 1) · 5 + 5
= 6 · 5 + 5                                 [множення]
= 35                                        [звернень до DRAM для 2D-обходу таблиць]

N_total_5lvl = (5 + 1) · (5 + 1)
= 6 · 6                                     [множення]
= 36                                        [загальна кількість звернень разом із даними]
```

Порівняно з нативною 5-рівневою трансляцією (`W_native_5lvl = 5`):

```
K_walk_5lvl = W_5lvl / W_native_5lvl
= 35 / 5                                    [ділення]
= 7.0                                       [семикратне зростання оверхеду на холодному промаху]
```

Формула `W = (g + 1) · h + g = g · h + g + h` має властивість повної симетрії відносно `g` та `h`: внесок гостьових і хостових рівнів математично еквівалентний. Член `g · h` описує двовимірну сітку трансляцій EPT, а член `g + h` — граничні умови (трансляцію кореня CR3 та читання самих дескрипторів гостя).

## Тривимірний обхід у вкладеній віртуалізації (3D Page Walk у Nested KVM)

У сценаріях вкладеної віртуалізації (Nested Virtualization) фізичний сервер (`L0`) запускає проміжний гіпервізор (`L1`), усередині якого функціонує вкладена віртуальна машина (`L2`).

У такій системі існує три незалежні рівні трансляції:
1. **Гостьові таблиці L2 (`g₂` рівнів)**: перетворюють віртуальну адресу `L2 GVA` у гостьову фізичну адресу `L2 GPA`.
2. **Вкладений EPT гіпервізора L1 (`e₁` рівнів, EPT12)**: перетворює `L2 GPA` у проміжну фізичну адресу `L1 GPA`.
3. **Апаратний EPT гіпервізора хоста L0 (`e₀` рівнів, EPT01)**: перетворює `L1 GPA` у кінцеву фізичну адресу оперативної пам'яті хоста `L0 HPA`.

### Виведення формули 3D-обходу

Будь-яке звернення за адресою простору `L2 GPA` (наприклад, читання дескриптора таблиці L2 або завантаження покажчика `CR3_L2`) потребує повного 2D-обходу через структури EPT12 та EPT01:

```
T_{2D}(e₁, e₀) = (e₁ + 1) · (e₀ + 1) - 1    [вартість перетворення одного L2 GPA в L0 HPA]
```

Розгорнемо повний цикл трансляції для адреси `L2 GVA`:
1. **Крок 0 (Початкова трансляція регістра CR3_L2)**:
   Значення `CR3_L2` є адресою простору `L2 GPA`. Для отримання фізичної адреси кореня таблиць L2 у DRAM хоста необхідно виконати `T_{2D}(e₁, e₀)` звернень.
2. **Кроки 1 .. g₂ (Трансляція проміжних та листових рівнів L2)**:
   На кожному кроці `k ∈ {1 .. g₂}` процесор читає дескриптор таблиці L2 (1 звернення до DRAM за вже обчисленою на попередньому кроці адресою `L0 HPA`) та видобуває покажчик на наступну таблицю простору `L2 GPA`.
   Трансляція цього нового `L2 GPA` знову вимагає `T_{2D}(e₁, e₀)` звернень через EPT12 та EPT01.
   Вартість кожного кроку: `N_k = 1 + T_{2D}(e₁, e₀)`.

Сумарна кількість звернень до оперативної пам'яті хоста `L0 DRAM` для повного 3D-обходу (`W_3D`):

```
W_3D = T_{2D}(e₁, e₀) + ∑_{k=1}^{g₂} (1 + T_{2D}(e₁, e₀))
= T_{2D} + g₂ · (1 + T_{2D})                  [підставили стале значення доданків суми]
= (g₂ + 1) · T_{2D} + g₂                      [винесли спільний множник (g₂ + 1)]
= (g₂ + 1) · ((e₁ + 1) · (e₀ + 1) - 1) + g₂   [підставили формулу T_2D]
= (g₂ + 1) · (e₁ + 1) · (e₀ + 1) - (g₂ + 1) + g₂ [розкрили дужки біля -1]
= (g₂ + 1) · (e₁ + 1) · (e₀ + 1) - 1          [скоротили -g₂ - 1 + g₂]
```

Повна кількість звернень до шини пам'яті разом із фінальним читанням цільових даних (`N_data = 1`):

```
N_total_3D = W_3D + 1
= (g₂ + 1) · (e₁ + 1) · (e₀ + 1) - 1 + 1     [додали звернення за даними]
= (g₂ + 1) · (e₁ + 1) · (e₀ + 1)             [елегантна тривимірна комбінаторна формула]
```

### Розрахунок для 4-рівневої архітектури вкладеності (4-Level Nested Walk)

Для стандартної 64-розрядної конфігурації зі сторінками 4 КіБ на всіх трьох рівнях (`g₂ = 4, e₁ = 4, e₀ = 4`):

```
W_3D_4k = (4 + 1) · (4 + 1) · (4 + 1) - 1
= 5 · 5 · 5 - 1                              [піднесення до куба]
= 125 - 1
= 124                                        [звернень до DRAM для трансляції одного промаху TLB]

N_total_3D_4k = (4 + 1) · (4 + 1) · (4 + 1)
= 5 · 5 · 5
= 125                                        [загальна кількість звернень разом із даними]
```

Коефіцієнт зростання оверхеду трансляції L2 гостя порівняно з нативною машиною (`W_native = 4`) та звичайною віртуальною машиною L1 (`W_2D = 24`):

```
K_walk_3D_vs_native = W_3D_4k / W_native
= 124 / 4                                    [ділення]
= 31.0                                       [у 31 раз більше звернень до пам'яті, ніж нативне виконання]

K_walk_3D_vs_2D = W_3D_4k / W_4k
= 124 / 24                                   [ділення]
≈ 5.17                                       [у 5.17 раза повільніше за звичайну однорівневу віртуалізацію]
```

Для 5-рівневої адресації LA57 (`g₂ = 5, e₁ = 5, e₀ = 5`):

```
W_3D_5lvl = (5 + 1) · (5 + 1) · (5 + 1) - 1
= 6 · 6 · 6 - 1                              [обчислення 6³ - 1]
= 216 - 1
= 215                                        [звернень до DRAM на один промах]

K_walk_3D_5lvl = 215 / 5
= 43.0                                       [43-кратне зростання оверхеду]
```

Через катастрофічний обсяг у 124 звернення до DRAM сучасні гіпервізори KVM у режимі вкладеної віртуалізації використовують тіньові таблиці EPT (Shadow EPT, де KVM створює об'єднану структуру `EPT02 = EPT01 ∘ EPT12`). Це згортає 3D-обхід апаратного транслятора назад до 2D-обходу ціною витрат на синхронізацію та валідацію `EPT02` при змінах у гості L1.

## Матриця скорочення глибини обходу за допомогою Huge Pages

Застосування великих сторінок (Huge Pages) розміром 2 МіБ та 1 ГіБ скорочує кількість ієрархічних рівнів трансляції:
- Сторінка 2 МіБ усуває рівень Page Table (PT), зменшуючи глибину на 1 рівень (`g = 3` або `h = 3`).
- Сторінка 1 ГіБ усуває рівні Page Directory (PD) та Page Table (PT), зменшуючи глибину на 2 рівні (`g = 2` або `h = 2`).

### Покроковий розрахунок комбінацій сторінок

1. **Конфігурація 2 МіБ у гості (`g = 3`) та 4 КіБ на хості (`h = 4`)**:
```
W = (3 + 1) · 4 + 3
= 4 · 4 + 3                                 [множення]
= 19                                        [звернень до DRAM]
```

2. **Конфігурація 4 КіБ у гості (`g = 4`) та 2 МіБ на хості (`h = 3`)**:
```
W = (4 + 1) · 3 + 4
= 5 · 3 + 4                                 [множення]
= 19                                        [звернень до DRAM]
```

3. **Конфігурація 2 МіБ у гості (`g = 3`) та 2 МіБ на хості (`h = 3`)**:
```
W = (3 + 1) · 3 + 3
= 4 · 3 + 3                                 [множення]
= 15                                        [звернень до DRAM]
```

4. **Конфігурація 1 ГіБ у гості (`g = 2`) та 1 ГіБ на хості (`h = 2`)**:
```
W = (2 + 1) · 2 + 2
= 3 · 2 + 2                                 [множення]
= 8                                         [звернень до DRAM]
```

5. **Вкладена конфігурація 3D Walk з 2 МіБ на всіх рівнях (`g₂ = 3, e₁ = 3, e₀ = 3`)**:
```
W_3D_2M = (3 + 1) · (3 + 1) · (3 + 1) - 1
= 4 · 4 · 4 - 1                             [обчислення 4³ - 1]
= 64 - 1
= 63                                        [скорочення зі 124 до 63 звернень, −49.2%]
```

6. **Вкладена конфігурація 3D Walk з 1 ГіБ на всіх рівнях (`g₂ = 2, e₁ = 2, e₀ = 2`)**:
```
W_3D_1G = (2 + 1) · (2 + 1) · (2 + 1) - 1
= 3 · 3 · 3 - 1                             [обчислення 3³ - 1]
= 27 - 1
= 26                                        [скорочення зі 124 до 26 звернень, −79.0%]
```

## Багаторівнева ймовірнісна модель часу доступу (Hierarchical Stochastic EMAT)

Сучасний процесор ніколи не виконує 2D-обхід наосліп у DRAM для кожної інструкції. Апаратна підсистема MMU містить складну ієрархію спеціалізованих кешів:

1. **L1 Data TLB (DTLB)**: Кеш першого рівня на 64–128 записів. Кешує пряму трансляцію `GVA → HPA` (Combined TLB з тегами VPID/PCID). Час звернення `t_L1 ≈ 1` такт (≈ 0.3 нс).
2. **L2 Unified TLB (STLB)**: Кеш другого рівня на 1024–2048 записів. Також кешує повні трансляції `GVA → HPA`. Час звернення `t_L2 ≈ 12` тактів (≈ 3.6 нс).
3. **Page Walk Cache (PWC / Paging-Structure Caches)**: Спеціалізовані внутрішні апаратні кеші Page Table Walker, що зберігають покажчики верхніх рівнів гостьових таблиць (`PML4-PWC`, `PDP-PWC`, `PD-PWC`) та розширених таблиць EPT. При влучанні в PWC апаратний блок пропускає верхні рівні трансляції.
4. **Кеші даних процесора (L2/L3 Data Cache)**: Дескриптори сторінок (PTE, PDE, PDPTE, PML4E, SPTE) є звичайними 64-бітними словами в пам'яті. Коли процесор їх читає, вони осідають у загальному кеші L3 (Last-Level Cache, LLC) з латентністю `t_L3 ≈ 40` тактів (≈ 12 нс) замість повного звернення до DRAM `t_dram ≈ 180–200` тактів (≈ 60 нс).

### Формалізація математичного сподівання затримки

Позначимо:
- `h₁` — коефіцієнт влучання в L1 DTLB (`P(Hit_L1)`);
- `h₂` — умовний коефіцієнт влучання в L2 STLB при промаху L1 (`P(Hit_L2 | Miss_L1)`);
- `h_pwc` — середня частка кроків 2D-обходу, що фільтруються кешами структури сторінок PWC;
- `h_llc` — імовірність знаходження дескриптора таблиці сторінок у кеші L3 замість оперативної пам'яті DRAM;
- `t_mem` — час читання кінцевих даних (якщо дані в кеші L3 — `t_L3`, якщо в DRAM — `t_dram`).

Математичне сподівання повного часу доступу до пам'яті (Effective Memory Access Time, EMAT):

```
E[T_access] = h₁ · t_L1 + (1 - h₁) · h₂ · (t_L1 + t_L2) + (1 - h₁) · (1 - h₂) · (t_L1 + t_L2 + E[T_walk] + t_mem)
```

Математичне сподівання тривалості апаратного 2D-обходу `E[T_walk]`:

```
E[T_walk] = W_eff · t_step
= (W · (1 - h_pwc)) · (h_llc · t_L3 + (1 - h_llc) · t_dram)
```

Де:
- `W_eff = W · (1 - h_pwc)` — ефективна кількість кроків, що дійсно потребують читання дескрипторів із пам'яті після фільтрації через PWC;
- `t_step = h_llc · t_L3 + (1 - h_llc) · t_dram` — математичне сподівання латентності одного кроку читання дескриптора.

### Порівняльний розрахунок для холодного обходу (Cold Walk)

У найгіршому сценарії (холодний старт процесу, промах усіх рівнів кешів: `h_pwc = 0, h_llc = 0` при `t_dram = 60 нс`):

```
t_walk_native_cold = 4 · 60 нс = 240 нс      [фізичний сервер, 4 рівні]
t_walk_ept_4k_cold = 24 · 60 нс = 1440 нс   [віртуальна машина EPT 4K + 4K]
t_walk_ept_2m_cold = 15 · 60 нс = 900 нс    [віртуальна машина EPT 2M + 2M]
t_walk_ept_1g_cold = 8 · 60 нс = 480 нс     [віртуальна машина EPT 1G + 1G]
t_walk_3d_4k_cold = 124 · 60 нс = 7440 нс   [вкладена віртуальна машина L2 Nested 4K]
```

### Практичний розрахунок середнього часу доступу при теплих кешах

Розглянемо типове робоче навантаження корпоративного сервера:
- `h₁ = 0.95` (95% запитів задовольняються L1 DTLB за 0.3 нс);
- `h₂ = 0.90` (з решти 5% промахів 90% знаходять трансляцію в L2 STLB за 3.6 нс);
- Сумарна ймовірність повного промаху TLB: `P_miss = (1 - h₁) · (1 - h₂) = 0.05 · 0.10 = 0.005` (0.5% промахів);
- Ефективність проміжних кешів: `h_pwc = 0.50` (PWC відсікає 50% кроків обходу);
- Попадання дескрипторів у кеш L3 хоста: `h_llc = 0.70` (70% у L3 за 12 нс, 30% у DRAM за 60 нс);
- Час читання цільових даних `t_mem = 60 нс`.

Обчислимо середню латентність одного кроку транслятора:

```
t_step = 0.70 · 12 нс + 0.30 · 60 нс
= 8.4 + 18.0                                [множення доданків]
= 26.4 нс                                   [середній час одного звернення за дескриптором]
```

```
E[T_walk_native]:

= 124 · (1 - 0.50) · 26.4 нс

```

```
= 0.285 + 0.045 · 3.9
```

## Математична модель інвалідації TLB: вартість INVEPT та INVVPID

У віртуалізованому середовищі модифікація структур сторінок або перемикання контексту віртуальних процесорів (vCPU) вимагає узгодженого скидання кешів трансляції. Для цього архітектура x86-64 надає спеціалізовані інструкції керування буфером: `INVVPID` (інвалідація за ідентифікатором віртуального процесора) та `INVEPT` (інвалідація за покажчиком EPT).

### Класифікація операцій інвалідації

1. **Інструкція `INVVPID` (Virtual-Processor Invalidation)**:
   - **Тип 0 (`INVVPID_INDIV_ADDR`)**: селективна інвалідація запису для конкретної лінійної адреси `GVA` та заданого тегу `VPID`. Пряма апаратна латентність: `C_invvpid_indiv ≈ 120` тактів ЦП.
   - **Тип 1 (`INVVPID_SINGLE_CONTEXT`)**: скидання всіх відображень, прив'язаних до конкретного vCPU (`VPID`). Пряма латентність: `C_invvpid_single ≈ 280` тактів ЦП.
   - **Тип 2 (`INVVPID_ALL_CONTEXTS`)**: глобальне скидання всіх тегованих записів для всіх віртуальних процесорів. Пряма латентність: `C_invvpid_all ≈ 450` тактів ЦП.
   - **Тип 3 (`INVVPID_SINGLE_CONTEXT_RETAINING_GLOBALS`)**: скидання контексту зі збереженням глобальних трансляцій (`PTE.G = 1`). Пряма латентність: `C_invvpid_glob ≈ 260` тактів ЦП.

2. **Інструкція `INVEPT` (Extended Page-Table Invalidation)**:
   - **Тип 1 (`INVEPT_SINGLE_CONTEXT`)**: інвалідація всіх трансляцій `GPA → HPA` та асоційованих записів комбінованого TLB для конкретного покажчика `EPTP`. Пряма латентність: `C_invept_single ≈ 450` тактів ЦП.
   - **Тип 2 (`INVEPT_ALL_CONTEXTS`)**: повне скидання всіх EPT-відображень та кешів структури сторінок PWC на фізичному ядрі. Пряма латентність: `C_invept_all ≈ 750` тактів ЦП.

### Модель повної вартості інвалідації: прямі та непрямі втрати

Повна вартість операції інвалідації TLB складається з прямої затримки виконання машинної інструкції (`C_direct`) та непрямих втрат продуктивності (`ΔT_indirect`), зумовлених повторним прогріванням спустошеного буфера трансляції (TLB Pollution Penalty):

```
T_total_inv = C_direct / F_cpu + ΔT_indirect
```

Непрямі втрати обчислюються як математичне сподівання часу додаткових промахів для записів, які були викинуті з кешу, але знову знадобляться процесору в найближчий період виконання:

```
ΔT_indirect = N_evicted · P_reuse · (E[T_walk] - t_hit)
```

Де:
- `N_evicted` — кількість видалених записів із кешів L1/L2 TLB;
- `P_reuse` — коефіцієнт повторного використання записів (зазвичай `P_reuse ≈ 0.60–0.80` для типових серверних процесів);
- `E[T_walk]` — математичне сподівання латентності 2D-обходу при промаху;
- `t_hit` — латентність попадання в TLB (`≈ 0.3 нс`).

### Порівняння селективного та глобального скидання

Розглянемо процесор з L1 TLB (64 записи) та L2 TLB (1536 записів), де сумарна місткість `N_TLB = 1600` записів, частота `F_cpu = 3.3 ГГц`, коефіцієнт `P_reuse = 0.70`, а обхід виконується через EPT 4K (`E[T_walk] = 316.8 нс`):

1. **Глобальне скидання (Global Flush / Type 2 INVEPT або VM-Exit без VPID)**:
```
N_evicted = 1600 записів

Пряма затримка інструкції:
T_direct_global = 750 / (3.3 · 10⁹)
≈ 227.3 нс

Непрямі втрати на прогрів TLB:
ΔT_indirect_global = 1600 · 0.70 · (316.8 - 0.3) нс
= 1120 · 316.5
= 354 480 нс
≈ 354.5 мкс                                  [понад 1.17 мільйона тактів ЦП на відновлення TLB!]

Сумарна вартість глобального скидання:
T_total_global = 227.3 нс + 354 480 нс
≈ 354.7 мкс
```

2. **Селективна інвалідація однієї сторінки (`INVVPID_INDIV_ADDR`)**:
```
N_evicted = 1 запис

Пряма затримка інструкції:
T_direct_indiv = 120 / (3.3 · 10⁹)
≈ 36.4 нс

Непрямі втрати на прогрів TLB:
ΔT_indirect_indiv = 1 · 0.70 · (316.8 - 0.3) нс
= 0.70 · 316.5
= 221.55 нс                                  [лише 731 такт ЦП]

Сумарна вартість селективного скидання:
T_total_indiv = 36.4 нс + 221.55 нс
≈ 258.0 нс
```

Коефіцієнт ефективності селективного керування TLB:

```
K_invalidation_speedup = T_total_global / T_total_indiv
= 354 700 / 258
≈ 1374.8                                     [селективне скидання в 1375 разів дешевше за глобальне]
```

Математичний розрахунок наочно демонструє, чому технологія VPID та гранулярні інструкції `INVVPID/INVEPT` є критично важливими для швидкодії віртуалізації: глобальний flush перетворює кожне перемикання контексту на важку мікросекундну затримку через вимушений холодний 2D-обхід для всього робочого набору.

## Стохастична модель енергетичних витрат пам'яті (DRAM Energy per Walk)

Обхід таблиць сторінок створює не лише затримку конвеєра ЦП, а й прямі енергетичні витрати. Кожне звернення до DRAM-масиву активує ємнісні лінії вибірки, підсилювачі зчитування (Sense Amplifiers) та буфери введення-виведення інтерфейсу пам'яті.

### Енергетична модель елементарного звернення

Відповідно до специфікацій JEDEC для пам'яті DDR4/DDR5 (енергетичні параметри `IDD0`, `IDD4R`, `IDD2N`), енергія, необхідна для зчитування однієї 64-байтної кеш-лінії з мікросхем DRAM, становить:

```
E_dram = E_ACT + E_RD + E_PRE + E_PHY_bus
```

Де:
- `E_ACT` — енергія активації рядка матриці пам'яті (Row Activation, зарядка wordline): `≈ 2.8 нДж`;
- `E_RD` — енергія команди зчитування стовпця (Column Read, перемикання bitline): `≈ 1.8 нДж`;
- `E_PRE` — енергія відновлення та передзаряду ліній (Precharge): `≈ 1.2 нДж`;
- `E_PHY_bus` — енергія високошвидкісного інтерфейсу передачі даних шини пам'яті (PHY transceiver): `≈ 0.7 нДж`.

Сумарна динамічна енергія одного звернення до фізичної пам'яті:

```
E_dram = 2.8 + 1.8 + 1.2 + 0.7
= 6.5 нДж                                   [енергія одного читання 64-байтної кеш-лінії з DRAM]
```

Для порівняння, енергія звернення до внутрішніх кешів процесора:
- L1 Cache hit: `E_L1 ≈ 0.005 нДж` (5 пДж);
- L2 Cache hit: `E_L2 ≈ 0.05 нДж` (50 пДж);
- L3 LLC hit: `E_L3 ≈ 0.5 нДж` (500 пДж).

### Енергетичні витрати холодного обходу таблиць

Енергія, що розсіюється підсистемою пам'яті виключно на виконання обходу структури сторінок (`E_walk`):

```
E_walk(W) = W · E_dram
```

Порівняємо енергетичні витрати для різних режимів трансляції:

```
Нативна машина (W_native = 4):
E_walk_native = 4 · 6.5 нДж
= 26.0 нДж

Віртуальна машина EPT 4K (W = 24):
E_walk_ept_4k = 24 · 6.5 нДж
= 156.0 нДж                                 [у 6.0 разів більше за нативний обхід]

Віртуальна машина EPT 2M (W = 15):
E_walk_ept_2m = 15 · 6.5 нДж
= 97.5 нДж                                  [економія 37.5% енергії пам'яті]

Віртуальна машина EPT 1G (W = 8):
E_walk_ept_1g = 8 · 6.5 нДж
= 52.0 нДж                                  [економія 66.7% енергії пам'яті]

Вкладена віртуальна машина 3D Walk 4K (W_3D = 124):
E_walk_3d_4k = 124 · 6.5 нДж
= 806.0 нДж                                 [≈ 0.81 мкДж на один промах TLB, у 31 раз більше за нативну пам'ять!]
```

### Стохастична модель середніх енергетичних витрат

Математичне сподівання енергії на одну операцію звернення до пам'яті (`E[E_access]`):

```
E[E_access] = h₁ · E_L1 + (1 - h₁) · h₂ · (E_L1 + E_L2) + (1 - h₁) · (1 - h₂) · (E_L1 + E_L2 + E[E_walk] + E_data)
```

Де середні енергетичні витрати на крок обходу з урахуванням кешу L3:

```
E_step = h_llc · E_L3 + (1 - h_llc) · E_dram
= 0.70 · 0.5 + 0.30 · 6.5
= 0.35 + 1.95
= 2.30 нДж

E[E_walk] = (W · (1 - h_pwc)) · E_step
```

Обчислимо енергію обходу для нативного доступу та EPT 4K при `h_pwc = 0.50` та `E_data = 6.5 нДж`:

```
E[E_walk_native] = 4 · (1 - 0.50) · 2.30 нДж
= 2 · 2.30
= 4.60 нДж

E[E_walk_ept_4k] = 24 · (1 - 0.50) · 2.30 нДж
= 12 · 2.30
= 27.60 нДж

Базова енергія влучань (L1 + L2):
E_base = 0.95 · 0.005 + 0.05 · 0.90 · (0.005 + 0.05)
= 0.00475 + 0.045 · 0.055
= 0.00475 + 0.002475
= 0.007225 нДж

E[E_access_native]:
= 0.007225 + 0.005 · (0.005 + 0.05 + 4.60 + 6.5)
= 0.007225 + 0.005 · 11.155
= 0.007225 + 0.055775
= 0.063 нДж на операцію

E[E_access_ept_4k]:
= 0.007225 + 0.005 · (0.005 + 0.05 + 27.60 + 6.5)
= 0.007225 + 0.005 · 34.155
= 0.007225 + 0.170775
= 0.178 нДж на операцію
```

Коефіцієнт енергетичного зростання:

```
K_energy = E[E_access_ept_4k] / E[E_access_native]
= 0.178 / 0.063
≈ 2.83                                       [майже трикратне зростання середнього енергоспоживання пам'яті]
```

### Вплив на потужність серверної стійки (Thermal Design Power)

Для високоінтенсивного серверного навантаження (наприклад, in-memory база даних), що генерує `N_miss = 100 · 10⁶` промахів TLB на секунду на сокет, потужність, яка розсіюється контролерами пам'яті та модулями DRAM виключно на обслуговування Page Walk:

```
P_walk_ept_4k = N_miss · E_walk_ept_4k
= (100 · 10⁶) · (156.0 · 10⁻⁹ Дж)
= 15.6 Вт                                    [паразитне тепловиділення лише на обхід EPT 4K]

P_walk_ept_1g = N_miss · E_walk_ept_1g
= (100 · 10⁶) · (52.0 · 10⁻⁹ Дж)
= 5.2 Вт                                     [економія понад 10 Вт на сокет при використанні Huge Pages 1GB]
```

Перехід на великі сторінки дозволяє заощадити понад 10 Вт електричної потужності на кожному процесорному сокеті в масштабах дата-центру, що знижує витрати на охолодження та збільшує щільність розміщення віртуальних машин.

## Апаратне оновлення бітів Accessed та Dirty: аналіз затримок

Під час кожного звернення процесора до сторінки апаратний MMU мусить виставити біт звернення (Accessed, A) у дескрипторі сторінки, а при операції запису — біт модифікації (Dirty, D).

Існує два принципових режими функціонування EPT:

1. **Програмне оновлення (`eptad=0` / без апаратної підтримки A/D)**:
   - При першій спробі читання або запису у сторінку, для якої відповідний біт у таблиці EPT ще не виставлений, процесор генерує перехоплення `EPT Violation` (код 48).
   - Відбувається перемикання контексту у VMX root mode: збереження стану vCPU (`T_exit ≈ 500` тактів).
   - Обробник KVM у ядрі хоста знаходить запис `SPTE`, виставляє біт `A` або `D`, оновлює права доступу (`T_handler ≈ 400` тактів).
   - Виконується повернення у гостьовий режим `VM-entry` (`T_entry ≈ 500` тактів).
   - Сумарна затримка: `T_soft_ad ≈ 1400` тактів ЦП (≈ 420 нс при 3.3 ГГц).

2. **Апаратне оновлення (`eptad=1` / Intel PML / A/D Bits Enabled у полі EPTP)**:
   - Апаратний Page Table Walker безпосередньо в процесі 2D-обходу виконує атомарну транзакцію на шині (Atomic Read-Modify-Write / Lock Bus) для оновлення бітів `A` та `D` у пам'яті хостової таблиці EPT.
   - Вихід із віртуальної машини (`VM-exit`) не відбувається.
   - Сумарна затримка: `T_hard_ad ≈ 40` тактів ЦП (≈ 12 нс).

### Модель навантаження на процесор при інтенсивному виділенні пам'яті

Нехай гостьове програмне забезпечення активно виділяє пам'ять з інтенсивністю `λ` нових сторінок за секунду. Частка обчислювального часу одного процесорного ядра з тактовою частотою `F_cpu = 3.3 · 10⁹` Гц, що витрачається виключно на обслуговування бітів A/D:

```
U_soft = (λ · T_soft_ad) / F_cpu
U_hard = (λ · T_hard_ad) / F_cpu
```

Коефіцієнт прискорення:

```
S = U_soft / U_hard
= T_soft_ad / T_hard_ad
= 1400 / 40                                 [ділення]
= 35.0                                      [35-кратне скорочення накладних витрат]
```

Для інтенсивного навантаження (наприклад, скидання буфера бази даних на диск або запуск нового процесу з виділенням `λ = 500 000` сторінок/с):

```
U_soft = (500 000 · 1400) / (3.3 · 10⁹)
= 700 · 10⁶ / (3.3 · 10⁹)
≈ 0.212                                     [21.2% усього часу ядра ЦП згорає у VM-exits]

U_hard = (500 000 · 40) / (3.3 · 10⁹)
= 20 · 10⁶ / (3.3 · 10⁹)
≈ 0.006                                     [лише 0.6% ядра ЦП]
```

Апаратне відстеження бітів A/D усуває до 20% паразитних накладних витрат CPU під час інтенсивних операцій алокації гостьової пам'яті.

## Охоплення буфера асоціативної трансляції (TLB Reach) та стохастичне моделювання

Охопленням буфера трансляції (TLB Reach) називається сумарний обсяг пам'яті, адреси якого одночасно зберігаються в TLB без виникнення промахів:

```
Reach = N_TLB · S_page
```

Де:
- `N_TLB` — кількість записів у відповідному рівні кешу TLB;
- `S_page` — розмір однієї сторінки.

### Розрахунок охоплення для L1 DTLB (64 записи) та L2 STLB (1536 записів)

```
L1 DTLB Reach (N = 64):
Reach_L1_4K = 64 · 4 КіБ = 256 КіБ          [не вміщує навіть L2 кеш даних]
Reach_L1_2M = 64 · 2 МіБ = 128 МіБ          [покриває робочий набір більшості мікросервісів]
Reach_L1_1G = 64 · 1 ГіБ = 64 ГіБ           [перекриває оперативну пам'ять робочої станції]

L2 STLB Reach (N = 1536):
Reach_L2_4K = 1536 · 4 КіБ = 6.0 МіБ        [не вміщує робочий набір жодної промислової СУБД]
Reach_L2_2M = 1536 · 2 МіБ = 3072 МіБ = 3.0 ГіБ [покриває основний кеш застосунку]
Reach_L2_1G = 1536 · 1 ГіБ = 1536 ГіБ = 1.5 ТіБ [повністю перекриває пам'ять великого вузла]
```

### Стохастична модель поведінки при великих робочих наборах (WSS)

Нехай робочий набір даних застосунку (Working Set Size, `WSS`) має обсяг `M`. За умови рівномірного випадкового доступу до пам'яті (Uniform Random Access), якщо `M > Reach`, імовірність знаходження адреси в кеші трансляції становить:

```
P(Hit) ≈ Reach / M
P(Miss) = 1 - P(Hit) ≈ (M - Reach) / M
```

Розглянемо сервер бази даних із робочим буферним пулом `M = 16 ГіБ = 16 384 МіБ` на vCPU з L2 STLB на 1536 записів:

```
Сторінки 4 КіБ (Reach = 6 МіБ):
P(Miss_4K) = (16384 - 6) / 16384
= 16378 / 16384
≈ 0.99963                                   [99.96% звернень викликають 2D-обхід на 24 кроки]

Сторінки 2 МіБ (Reach = 3072 МіБ):
P(Miss_2M) = (16384 - 3072) / 16384
= 13312 / 16384
≈ 0.81250                                   [81.25% промахів, кожен промах триває лише 15 кроків]

Сторінки 1 ГіБ (Reach = 1536 ГіБ >> 16 ГіБ):
P(Miss_1G) = 0.00000                        [0% промахів після прогріву, TLB-оверхед зникає]
```

При стандартних сторінках 4 КіБ навантаження з великим робочим набором практично повністю паралізує підсистему пам'яті безперервним 24-кроковим обходом таблиць сторінок. Переведення пам'яті віртуальної машини на Huge Pages усуває цей ефект, забезпечуючи максимальну пропускну здатність шини DRAM.
