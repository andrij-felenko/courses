# 📋 Специфікація API debugfs та керувальних інтерфейсів tracefs

Цей довідник описує основні функції C API ядра Linux для реєстрації вузлів у віртуальній файловій системі `debugfs`, а також синтаксис налаштувань, керувальних файлів та динамічних зондів у файловій системі `tracefs`.

---

## 1. C API ядра Linux для debugfs (<linux/debugfs.h>)

Інтерфейс програмування `debugfs` призначений для швидкого експорту внутрішніх змінних ядра та реєстрації користувацьких точок читання і запису. Виклики створення файлів однакові за формою: ім'я елемента, маска прав доступу POSIX, вказівник на батьківську структуру `dentry` та адреса експортованих даних. Виняток — `debugfs_create_dir()`: каталогові ні прав, ні даних не передають. Якщо параметр батьківського каталогу дорівнює `NULL`, ядро створює новий вузол у кореневому каталозі файлової системи `/sys/kernel/debug`.

### Механізми обробки помилок та повертаних значень

На відміну від більшості традиційних підсистем ядра, де невдалий виклик повертає вказівник `NULL`, ті функції `debugfs`, що взагалі щось повертають, віддають маскований вказівник на помилку `ERR_PTR`. Це зроблено для того, щоб розробник міг відрізнити випадок, коли файлова система `debugfs` взагалі вимкнена в ядрі на етапі конфігурації (параметр `CONFIG_DEBUG_FS=n`, за якого працює порожня inline-заглушка з `ERR_PTR(-ENODEV)`), від випадку, коли не вдалося виділити пам'ять під новий елемент каталогу.

Для перевірки результату виконання виклику у коді драйвера застосовуються спеціалізовані макроси ядра:
- `IS_ERR(dentry)` — повертає `true`, якщо повернене значення містить код помилки (наприклад, `-ENOMEM` або `-EEXIST`).
- `PTR_ERR(dentry)` — вилучає числовий код помилки зі структури вказівника для подальшого повернення в обробнику ініціалізації модуля.

**Межа за версією ядра.** Скалярні створювачі перевели на `void` по одному протягом серії 5.x: `debugfs_create_u8/u16/u64` і `debugfs_create_atomic_t` — у 5.5, `debugfs_create_u32` — у 5.7, `debugfs_create_bool` — у 5.14. У старших ядрах усі вони ще повертали `struct dentry *`. Сенс переходу простий: перевіряти там нічого — драйвер зобов'язаний працювати й тоді, коли `debugfs` вимкнено або вузол не створився. Вказівник і далі віддають `debugfs_create_dir()`, `debugfs_create_file()` та `debugfs_create_blob()` — його потрібно зберегти, щоб потім передати у `debugfs_remove()`.

Окремої згадки вартий `debugfs_create_atomic_t()`: він читає значення через `atomic_read()`, тож у багатопроцесорній системі (SMP) звіт не спіймає напівоновленого лічильника. Для `debugfs_create_u32()` та решти цілочислових обгорток такої обіцянки немає — вони просто друкують поточний вміст змінної, і узгодженість із рештою стану драйвер має забезпечувати сам.

### Довідник основних функцій створення та видалення вузлів

| Сигнатура функції / Макрос | Параметри та призначення | Повертане значення та обробка помилок |
| :--- | :--- | :--- |
| `debugfs_create_dir(name, parent)` | **name:** ім'я каталогу.<br>**parent:** батьківський `struct dentry*` (якщо `NULL`, створюється в корені `/sys/kernel/debug`). | Повертає `struct dentry*`. При помилці — `ERR_PTR` (зокрема `ERR_PTR(-ENODEV)`, якщо debugfs вимкнено в ядрі: за `CONFIG_DEBUG_FS=n` працює порожня inline-заглушка). Перевіряється макросом `IS_ERR()`. |

| `debugfs_create_u64(name, mode, parent, value)` | Експорт 64-бітного цілого числа (`u64*`). | `void` (до 5.5 — `struct dentry*`). |

### Послідовний вивід великих структур даних через seq_file

Коли обсяг експортованого тексту перевищує розмір однієї системної сторінки пам'яті (зазвичай 4096 байтів), стандартні обробники `read` стають схильними до помилок через складність розрахунку поточного зміщення `loff_t *ppos`. Для вирішення цієї задачі застосовується підсистема `seq_file`.

При реєстрації користувацького файлу викликом `debugfs_create_file()` у структуру `struct file_operations` підключаються готові системні обробники:

```c
static const struct file_operations my_debugfs_fops = {
    .owner   = THIS_MODULE,
    .open    = my_driver_single_open,
    .read    = seq_read,
    .llseek  = seq_lseek,
    .release = single_release,
};
```

Функція `single_open(file, show, data)` зв'язує відкритий файл із функцією показу `show`, яку пише сам драйвер, і передає їй довільний вказівник `data` — той приходить у поле `m->private` структури `struct seq_file`. Далі `seq_read` сама керує внутрішнім буфером: якщо звіт не вмістився, буфер подвоюється і `show` викликається знову, тож обрізаних даних і ручних розрахунків зміщення не буває.

## 2. Керувальні файли та налаштування tracefs (/sys/kernel/tracing/)

Віртуальна файлова система `tracefs` експортує файли конфігурації та зчитування для трасувальника `ftrace`. Кожен файл представляє конкретний вузол керування кільцевим буфером або фільтрацією подій.

### Механіка керування пам'яттю кільцевих буферів

Кільцевий буфер ftrace виділяється окремо для кожного процесорного ядра системи (per-CPU buffer). Розмір одного буфера регулюється через файл `buffer_size_kb`. За замовчуванням ядро виділяє по 1408 КіБ на кожне процесорне ядро. На сервері зі 128 апаратними потоками це дає 128 × 1408 КіБ = 180 224 КіБ, тобто 176 МіБ оперативної пам'яті лише під буфери трасування.

При виникненні переповнення кільцевого буфера ядро за замовчуванням працює в режимі перезапису (overwrite mode): найновіші події заміщують найстаріші. Цю поведінку можна змінити через файл `options/overwrite`, встановивши `0`, що змусить ядро відкидати нові події при заповненні буфера.

Запис власних логів із простору користувача у трасувальний потік здійснюється через спеціальний файл `trace_marker`. Наприклад, системний демон може виконати системний виклик `write()` у `/sys/kernel/tracing/trace_marker`, що дозволяє точно синхронізувати події користувацького додатка з подіями ядра за спільними часовими мітками.

### Специфікація основних керувальних файлів tracefs

Права в таблиці — ті, з якими вузли створює ядро до 5.16. Від 5.16 біти «інших» знято: файли лише для читання отримують `0440`, файли читання-запису — `0640` (константи `TRACE_MODE_READ` і `TRACE_MODE_WRITE`), тож доступ лишається в root і групи-власника, яку задають опцією монтування `gid=`. Виняток — `trace_marker`: він і був, і лишається `0220`, бо писати мітки має право саме група.

| Файл у tracefs | Тип / Права | Синтаксис використання та опис |
| :--- | :--- | :--- |
| `available_tracers` | RO (0444) | Перелік підтримуваних трасувальників у поточному ядрі.<br>Приклад виводу: `hwlat blk mmiotrace function_graph wakeup_dl wakeup_rt wakeup function nop` |
| `current_tracer` | RW (0644) | Активний трасувальник.<br>Приклад увімкнення: `echo function_graph > current_tracer`<br>Скидання в пасивний режим: `echo nop > current_tracer` |
| `tracing_on` | RW (0644) | Глобальний вимикач запису в кільцевий буфер.<br>`1` — запис дозволено.<br>`0` — запис призупинено (накопичений вміст буфера зберігається). |
| `trace` | RW (0644) | Статичний зріз вмісту per-CPU кільцевих буферів.<br>Зчитування: `cat trace` (не видаляє дані).<br>Очищення буфера: `echo > trace` |
| `trace_pipe` | RO (0444) | Потоковий блокуючий інтерфейс зчитування.<br>Зчитування `cat trace_pipe` видаляє опрацьовані дані з буфера в реальному часі. |
| `trace_marker` | WO (0220) | Інтерфейс запису користувацьких міток у трасувальний лог ядра.<br>Приклад: `echo "Start benchmark" > trace_marker` |
| `set_ftrace_filter` | RW (0644) | Фільтрація функцій для трасувальника `function`.<br>Приклад: `echo 'vfs_*' > set_ftrace_filter` (трасувати лише функції VFS). |
| `set_ftrace_notrace` | RW (0644) | Виключення функцій із трасування (чорний список).<br>Приклад: `echo 'spin_*' > set_ftrace_notrace` |
| `set_ftrace_pid` | RW (0644) | Фільтрація трасування за PID процесів.<br>Приклад: `echo 1234 > set_ftrace_pid` |
| `buffer_size_kb` | RW (0644) | Розмір кільцевого буфера в кілобайтах **на кожен CPU core**.<br>Приклад: `echo 4096 > buffer_size_kb` (виділити по 4 МіБ на ядро). |

## 3. Ієрархія підсистеми подій та динамічних зондів

Статичні точки трасування (tracepoints) організовано в ієрархічні каталоги підсистем у `/sys/kernel/tracing/events/`. Вони розробляються авторами ядра і розміщуються в критичних місцях підсистем керування пам'яттю, мережевого стека, планувальника та системних викликів.

### Структура керування точками подій (events/<subsystem>/<event>/)

Для кожної конкретної події (наприклад, `events/sched/sched_switch`) доступні такі файли керування:

1. **enable** — бінарний вимикач події. Запис `1` вмикає трасування події, `0` — вимикає.
2. **filter** — вираз фільтрації події за значеннями її полів. Підтримує логічні оператори `&&`, `||`, `!`, а також порівняння чисел та рядків.
   - Синтаксис: `echo 'common_pid == 1024 || common_pid == 2048' > filter`
   - Скидання фільтра: `echo 0 > filter`
3. **format** — файл лише для читання, який описує бінарний макет (layout) структури події. У ньому вказуються зміщення полів у байтах, їхні розміри та знаковість. Опис використовують `perf`, `trace-cmd` і частина eBPF-інструментів для автоматичної десеріалізації полів; libbpf із CO-RE бере ті самі типи з BTF (`/sys/kernel/btf/vmlinux`).
4. **trigger** — налаштування автоматичних дій при настанні події (наприклад, увімкнення іншого трасувальника, запис трасування стеку викликів `stacktrace` або створення зрізу буфера).

### Специфікація динамічних зондів kprobe_events

Файл `/sys/kernel/tracing/kprobe_events` дозволяє створювати динамічні точки перехоплення у будь-якому місці ядра Linux без перекомпіляції його вихідного коду. Механізм `kprobe` підміняє інструкцію за вказаною адресою на точку зупинки (break instruction), перехоплює виконання, витягує значення регістрів і повертає контроль ядру.

#### Формат запису kprobe_events:

```text
p[:[GRP/][EVENT]] [MOD:]SYM[+offs]|MEMADDR [FETCHARGS]  # Вхід у функцію (kprobe)
r[MAXACTIVE][:[GRP/][EVENT]] [MOD:]SYM[+0] [FETCHARGS]  # Повернення з функції (kretprobe)
-:[GRP/][EVENT]                                         # Вилучення зонда
```

Зверніть увагу на асиметрію: kprobe можна поставити на будь-яке зміщення всередині функції або просто на адресу, а kretprobe — лише на символ із нульовим зміщенням, бо перехоплюється повернення, а не довільна інструкція. Необов'язкове число `MAXACTIVE` після `r` задає, скільки одночасних викликів функції зонд здатен відстежити.

#### Пояснення полів та аргументів витягування:

- **p / r** — тип зонду (`p` — kprobe при вході у функцію, `r` — kretprobe при поверненні з функції).
- **GRP/EVENT** — ім'я групи та події у `/sys/kernel/tracing/events/kprobes/`. Якщо ім'я не вказано, ядро створює ім'я автоматично.
- **SYM+OFFS** — ім'я символу ядра з таблиці `kallsyms` та зміщення в байтах від початку функції (наприклад, `do_sys_open+0x0`).
- **FETCHARGS** — аргументи для витягування значень з регістрів або пам'яті:
  - `%ax`, `%di`, `%si`, `%dx` — зчитування значення архітектурного регістра процесора.
  - `+0(%sp)` — зчитування даних зі зміщенням від вказівника стеку.
  - `+0(%di):string` — розіменування вказівника та зчитування рядка з пам'яті.
  - `:s32`, `:u64`, `:x32` — примусове приведення типу аргументу.

#### Покроковий приклад створення та вилучення kprobe у терміналі:

```bash
# 1. Переконатися, що символ узагалі є в цьому ядрі (інакше запис поверне EINVAL)
$ sudo grep ' do_sys_open$' /proc/kallsyms

# 2. Створення kprobe на функцію do_sys_open із витягуванням першого аргументу (dfd)
#    %di — регістр першого аргументу x86_64; форма +0(%di) розіменувала б його як вказівник
$ echo 'p:my_open_probe do_sys_open dfd=%di:s32' | sudo tee /sys/kernel/tracing/kprobe_events

# 3. Перевірка створення події в ієрархії events
$ ls -l /sys/kernel/tracing/events/kprobes/my_open_probe/

# 4. Увімкнення створеного динамічного зонду
$ echo 1 | sudo tee /sys/kernel/tracing/events/kprobes/my_open_probe/enable

# 5. Перегляд згенерованих подій
$ sudo cat /sys/kernel/tracing/trace_pipe

# 6. Вимкнення та вилучення створеного зонду
$ echo 0 | sudo tee /sys/kernel/tracing/events/kprobes/my_open_probe/enable
$ echo '-:kprobes/my_open_probe' | sudo tee /sys/kernel/tracing/kprobe_events
```

### Специфікація динамічних зондів uprobe_events

Файл `/sys/kernel/tracing/uprobe_events` використовується для динамічного трасування функцій у виконуваних бінарних файлах ELF та спільних бібліотеках простору користувача. На відміну від kprobes, для uprobes вказується шлях до файла у файловій системі та зміщення вхідної точки інструкції в байтах від початку файлу.

#### Формат запису uprobe_events:

```text
p[:[GRP/][EVENT]] PATH:OFFSET [FETCHARGS]  # Вхід у функцію простору користувача
r[:[GRP/][EVENT]] PATH:OFFSET [FETCHARGS]  # Повернення з функції
```

`OFFSET` тут — зміщення **у файлі**, а не адреса в пам'яті процесу. Для звичайно злінкованої бібліотеки вони збігаються, бо лінкувальник кладе виконуваний сегмент так, що `p_offset` дорівнює `p_vaddr`; якщо ні — різницю сегмента видно у виводі `readelf -l`.

#### Приклад створення uprobe для моніторингу викликів malloc у бінарному файлі libc:

```bash
# 1. Знаходження зміщення функції malloc у системній бібліотеці libc.
#    Значення залежить від конкретної збірки glibc — беріть своє, а не з прикладу
$ nm -D /lib/x86_64-linux-gnu/libc.so.6 | grep ' malloc$'
```
