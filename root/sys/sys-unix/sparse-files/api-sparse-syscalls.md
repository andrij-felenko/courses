# 📋 Контракт розріджених операцій: `lseek`, `fallocate`, FIEMAP, `stat`

Про порожнечу у файлі програма розмовляє з файловою системою чотирма інтерфейсами: два питання `lseek` («де межа»), дев'ять режимів `fallocate` («зроби так»), один `ioctl` FIEMAP («віддай карту») і три поля `stat` («скільки насправді зайнято»). Сигнатури, значення констант, вимоги до вирівнювання, коди помилок і таблиці підтримки — усе те, що доводиться звіряти щоразу, коли пишеш код, який має спрацювати не лише на своїй машині.

Найкоротший орієнтир, з якого починається вибір:

| задача | чим | ключова обмовка |
|---|---|---|
| знайти, де у файлі дані | `lseek` із `SEEK_DATA`/`SEEK_HOLE` | пересуває позицію дескриптора, це не чисте питання |
| дістати повну карту з ознаками | `ioctl(fd, FS_IOC_FIEMAP, …)` | дір у відповіді немає — вони між екстентами |
| звільнити блоки всередині файлу | `fallocate` + `FALLOC_FL_PUNCH_HOLE` | обов'язково разом із `FALLOC_FL_KEEP_SIZE` |
| зарезервувати місце наперед | `fallocate` із `mode = 0` | розрідженість після цього зникає |
| дізнатися, скільки зайнято | `st_blocks` зі `stat` | одиниця завжди 512 Б, ніколи не розмір блока ФС |

## `lseek`: два питання про найближчу межу

```c
#define _GNU_SOURCE
#include <unistd.h>

off_t lseek(int fd, off_t offset, int whence);
```

Значення `whence` — звичайні цілі, і два останні цікавлять саме тут:

```c
#define SEEK_SET   0   /* від початку файлу */
#define SEEK_CUR   1   /* від поточної позиції */
#define SEEK_END   2   /* від кінця */
#define SEEK_DATA  3   /* до наступних даних */
#define SEEK_HOLE  4   /* до наступної діри */
```

| `whence` | питання | що повертає |
|---|---|---|
| `SEEK_DATA` | «де найближчі дані, починаючи від `offset`?» | зсув початку даних; якщо `offset` уже стоїть на даних — сам `offset` |
| `SEEK_HOLE` | «де найближча діра, починаючи від `offset`?» | зсув початку діри; якщо `offset` уже в дірі — сам `offset`; якщо дір далі немає — `st_size` |

Обидва повертають новий зсув або `-1` з виставленим `errno`.

Три властивості контракту, на яких найчастіше спотикаються.

**Це не запит, а переміщення.** `lseek` міняє позицію в [описі відкритого файлу](root:sys-unix/open-file-description) — тій спільній структурі, від якої відлічують `read` і `write`. Обхід карти файлу пересуває позицію так само, як звичайний `lseek`, тож або збережіть її на початку й поверніть у кінці, або читайте потім через `pread`, який позиції не чіпає.

**Кінець файлу завжди вважається початком діри.** Тому `SEEK_HOLE` має що повернути для будь-якого припустимого `offset` і ніколи не зациклює обхід. Це неявна діра: жодних блоків за `st_size` немає й бути не може.

**`ENXIO` — це не поломка, а сигнал «далі нічого».** Ядро повертає його, коли `offset ≥ st_size`, причому для обох режимів: `generic_file_llseek_size` перевіряє саме `offset >= eof` і виходить із `-ENXIO` ще до того, як спитає файлову систему. Для `SEEK_DATA` те саме буває й усередині розміру — коли від `offset` до кінця тягнеться суцільна діра.

| помилка | умова |
|---|---|
| `ENXIO` | `offset` за кінцем файлу (або дорівнює `st_size`); для `SEEK_DATA` — ще й коли `offset` у дірі, що доходить до кінця |
| `EINVAL` | `whence` не з переліку — саме це віддають ядра, старіші за 3.1, і саме на `EINVAL` перевіряють наявність можливості |
| `EOVERFLOW` | результат не вміщається в `off_t` — привіт від [великих файлів](root:sys-unix/large-file-support), де 32-бітний `off_t` уривається на 2 ГіБ |
| `ESPIPE` | `fd` веде на канал, сокет або FIFO — там позиції немає |
| `EBADF` | `fd` не є відкритим дескриптором |

### Хто це вміє

`SEEK_DATA` і `SEEK_HOLE` з'явилися в Linux 3.1 (жовтень 2011), у POSIX увійшли аж у редакції 2024 року; поза Linux вони давно є в Solaris, FreeBSD і DragonFly BSD. Файлові системи набирали підтримку поступово:

| файлова система | від якої версії ядра |
|---|---|
| Btrfs | 3.1 |
| OCFS2 | 3.2 |
| XFS | 3.5 |
| ext4, tmpfs/shmem | 3.8 |
| NFS (v4.2) | 3.18 |
| FUSE | 4.5 |
| GFS2 | 4.15 |

**Файлова система не зобов'язана знаходити діри.** Стандарт вимагає лише несуперечливості, і найпростіша чесна реалізація виглядає так: `SEEK_DATA` завжди повертає переданий `offset`, `SEEK_HOLE` завжди повертає `st_size`. Тобто «увесь файл — дані, діра одна, у самому кінці». Формально це правильна відповідь, і код, який будує карту, мусить її пережити — просто карта вийде з одного суцільного шматка.

У протилежний бік хибило б відкладене виділення блоків: дані, щойно записані й ще не осілі на носій, блоків не мають, тож назвати їх дірою було б формально чесно. Ext4, XFS і Btrfs так не відповідають — перед відповіддю вони звіряються з [кешем сторінок](root:sys-unix/page-cache-durability) і рахують такі ділянки даними. Гарантії немає лише там, де відповідає не ядро (FUSE) або де ядро старе, — тож `fsync` перед обходом лишається дешевим способом зняти питання. Карта, здобута цими викликами, описує поточний стан метаданих, а не вміст.

### Мінімальний виклик

```c
#include <errno.h>

/* Де починаються дані після зсуву pos? Повертає -1, якщо далі їх немає. */
off_t next_data(int fd, off_t pos)
{
    off_t d = lseek(fd, pos, SEEK_DATA);
    if (d < 0 && errno == ENXIO) return -1;   /* далі до кінця сама діра */
    if (d < 0 && errno == EINVAL) return pos; /* ядро/ФС не вміє — вважаємо все даними */
    return d;
}
```

## `fallocate(2)`: один виклик, дев'ять кодових точок

```c
#define _GNU_SOURCE
#include <fcntl.h>
#include <linux/falloc.h>   /* якщо glibc старіша за 2.18 */

int fallocate(int fd, int mode, off_t offset, off_t len);
```

Сам виклик з'явився в Linux 2.6.23 і в glibc 2.10; константи `FALLOC_FL_*` потрапили в заголовки glibc лише у 2.18, тому переносний код часто вмикає `<linux/falloc.h>` напряму. Повертає `0` або `-1` з `errno`.

`mode` — набір бітів, але майже всі режими взаємно виключні: реально комбінується тільки `FALLOC_FL_KEEP_SIZE` з кількома іншими.

| константа | значення | від якої версії | що робить із `st_size` | що робить із `st_blocks` |
|---|---|---|---|---|
| `FALLOC_FL_ALLOCATE_RANGE` | `0x00` | 2.6.23 | росте до `offset+len` | росте: блоки виділено, позначено невиписаними |
| `FALLOC_FL_KEEP_SIZE` | `0x01` | 2.6.23 | не міняється | — (модифікатор до інших) |
| `FALLOC_FL_PUNCH_HOLE` | `0x02` | 2.6.38 | не міняється | падає: цілі блоки звільнено |
| `FALLOC_FL_NO_HIDE_STALE` | `0x04` | — | зарезервована кодова точка, у головній гілці не реалізована | |
| `FALLOC_FL_COLLAPSE_RANGE` | `0x08` | 3.15 | зменшується рівно на `len` | падає на вирізане |
| `FALLOC_FL_ZERO_RANGE` | `0x10` | 3.15 | росте до `offset+len`, якщо немає `KEEP_SIZE` | не падає: блоки лишаються, стають невиписаними |
| `FALLOC_FL_INSERT_RANGE` | `0x20` | 4.1 | збільшується рівно на `len` | не міняється: вставлено діру |
| `FALLOC_FL_UNSHARE_RANGE` | `0x40` | 4.9 | не міняється | росте: спільні блоки стають власними |
| `FALLOC_FL_WRITE_ZEROES` | `0x80` | 6.17 | росте до `offset+len` | росте: блоки виділено й позначено записаними |

![Чотири рядки, у кожному ліворуч назва режиму fallocate з версією ядра, посередині смуга файлу «було» з трьох ділянок даних A, B і C, праворуч смуга «стало». PUNCH_HOLE перетворює середню ділянку на діру. ZERO_RANGE перетворює середню ділянку на нулі, залишаючи блоки. COLLAPSE_RANGE викидає середню ділянку і зсуває хвіст ліворуч, файл коротшає. INSERT_RANGE вставляє діру, зсуваючи хвіст праворуч, файл довшає. Під смугою «було» позначено діапазон запиту від offset до offset плюс len, під смугою «стало» — що сталося зі st_size і st_blocks. Унизу пояснення кольорів і застереження, що два останні режими пересувають увесь хвіст файлу](img/range-ops.svg)

*Перші два режими міняють лише вміст діапазону, зсуви решти файлу лишаються на місці. Два останні пересувають хвіст — і роблять недійсними всі зсуви, які програма запам'ятала раніше.*

### Правила сполучення

- `FALLOC_FL_PUNCH_HOLE` **мусить** бути в парі з `FALLOC_FL_KEEP_SIZE`, інакше `EINVAL`. Причина проста: пробивання звільняє блоки, а не вкорочує файл, і `st_size` мусить лишитися незмінним навіть тоді, коли пробивають найостаннішу ділянку.
- `FALLOC_FL_COLLAPSE_RANGE` і `FALLOC_FL_INSERT_RANGE` мають іти **самі**: будь-який інший біт у `mode` — `EINVAL`.
- `FALLOC_FL_ZERO_RANGE` із `KEEP_SIZE` не подовжить файл, без нього — подовжить, якщо `offset+len` більше за `st_size`.
- `FALLOC_FL_UNSHARE_RANGE` дозволено лише з режимом виділення (`0` або `KEEP_SIZE`); із пробиванням, зануленням, згортанням чи вставлянням — не поєднується.
- `FALLOC_FL_WRITE_ZEROES` із `KEEP_SIZE` не поєднується.

### Вирівнювання

| режим | вимога |
|---|---|
| `PUNCH_HOLE`, `ZERO_RANGE` | приймають будь-які `offset` і `len`, але звільняють/перетворюють лише **цілі** блоки ФС; часткові блоки на краях занулюються справжнім записом |
| `COLLAPSE_RANGE`, `INSERT_RANGE` | і `offset`, і `len` мусять бути кратні розміру блока ФС, інакше `EINVAL` |

Наслідок для дрібних діапазонів рахується так:

```
блок ФС                = 4096 байтів
запит                  = offset 5000, len 3000  → байти 5000..7999
цілих блоків усередині = 0   (усе лежить у блоці №1)
звільнено байтів       = 0
записано нулів         = 3000
```

Тобто пробивання діри на діапазоні, меншому за блок, — це операція **запису**, а не звільнення.

### Підтримка по файлових системах

Перелік із man-сторінки, тобто «щонайменше ці» — [родини файлових систем](root:sys-unix/filesystem-families) додають режими у власному темпі, і поза цим списком підтримка теж буває.

| режим | де і від якої версії ядра |
|---|---|
| `PUNCH_HOLE` | XFS 2.6.38 · ext4 3.0 · tmpfs 3.5 · Btrfs 3.7 · GFS2 4.16 |
| `ZERO_RANGE` | XFS 3.15 · ext4 (лише файли на екстентах) 3.15 · SMB3 3.17 · Btrfs 4.16 |
| `COLLAPSE_RANGE` | ext4 (лише файли на екстентах) 3.15 · XFS 3.15 |
| `INSERT_RANGE` | XFS 4.1 · ext4 4.2 |
| `UNSHARE_RANGE` | XFS 4.9, разом із появою [копій із поділом блоків](root:sys-unix/reflink-copies); man-сторінка повного переліку не подає |
| `WRITE_ZEROES` | ext4 6.17 |

Немає підтримки — `EOPNOTSUPP`, і це не аварія, а звичайна відповідь, під яку в коді мусить бути запасна гілка.

### Коди помилок

| `errno` | умова |
|---|---|
| `EBADF` | `fd` не дескриптор або відкритий не на запис |
| `EFBIG` | `offset+len` перевищує максимальний розмір файлу; для `INSERT_RANGE` — розмір файлу плюс `len` |
| `EINTR` | під час виконання зловлено сигнал |
| `EINVAL` | `offset < 0` або `len ≤ 0`; для `COLLAPSE_RANGE` — діапазон доходить до кінця файлу або за нього; для `INSERT_RANGE` — `offset` доходить до кінця або за нього; для обох — `offset` чи `len` не кратні блоку ФС, або в `mode` є ще якісь біти; для `COLLAPSE_RANGE`, `ZERO_RANGE` й `INSERT_RANGE` — файл не звичайний |
| `EIO` | помилка вводу-виводу на носії |
| `ENODEV` | `fd` веде не на звичайний файл і не на каталог |
| `ENOSPC` | на пристрої не лишилося місця |
| `ENOSYS` | ядро не має `fallocate` узагалі |
| `EOPNOTSUPP` | файлова система не підтримує виклик або конкретний режим |
| `EPERM` | файл позначено незмінним (immutable); або режим — `PUNCH_HOLE`/`COLLAPSE_RANGE`/`INSERT_RANGE`, а файл лише для дописування (append-only); або операцію заборонила печатка на файлі (seal) |
| `ESPIPE` | `fd` веде на канал або FIFO |
| `ETXTBSY` | `COLLAPSE_RANGE` чи `INSERT_RANGE` над файлом, який зараз виконується |

### Мінімальні виклики

```c
/* Пробити діру: 1 МіБ, починаючи зі зсуву 4096. */
if (fallocate(fd, FALLOC_FL_PUNCH_HOLE | FALLOC_FL_KEEP_SIZE, 4096, 1 << 20) < 0) {
    if (errno == EOPNOTSUPP) {
        /* ФС не вміє: або лишаємо як є, або чесно пишемо нулі */
    } else {
        perror("punch");
    }
}

/* Зарезервувати 4 ГіБ під файл, щоб запис у них уже не впав з ENOSPC. */
if (fallocate(fd, 0, 0, 4ULL << 30) < 0)
    perror("preallocate");
```

### `posix_fallocate(3)` — і пастка в ньому

```c
#include <fcntl.h>
int posix_fallocate(int fd, off_t offset, off_t len);
```

Переносний варіант із двома відмінностями, які легко проґавити. По-перше, він **повертає код помилки як значення** і не чіпає `errno`. По-друге, коли системний виклик відмовляє з `EOPNOTSUPP`, glibc не здається, а **дописує потрібні байти вручну** — і швидке резервування місця перетворюється на повноцінний запис усього діапазону, що на мережевій файловій системі коштує рівно стільки, скільки важить файл. Утиліта `fallocate(1)` вмикає цю саму поведінку прапорцем `-x`, і робить це навмисно: у режимі POSIX операція «завжди завершується, але може тривати довше».

## `ioctl(FS_IOC_FIEMAP)`: повна карта екстентів

Коли двох питань `lseek` замало — потрібні не лише межі, а й ознаки кожної ділянки, — карту віддає [керувальний виклик](root:sys-unix/ioctl-interface) FIEMAP, який з'явився в Linux 2.6.28.

```c
#include <linux/fiemap.h>
#include <linux/fs.h>    /* FS_IOC_FIEMAP _IOWR('f', 11, struct fiemap) */

struct fiemap_extent {
    __u64 fe_logical;    /* зсув у файлі, байти */
    __u64 fe_physical;   /* зсув на носії, байти */
    __u64 fe_length;     /* довжина, байти */
    __u64 fe_reserved64[2];
    __u32 fe_flags;
    __u32 fe_reserved[3];
};

struct fiemap {
    __u64 fm_start;              /* від якого зсуву питаємо */
    __u64 fm_length;             /* яку довжину покрити; FIEMAP_MAX_OFFSET = ~0ULL */
    __u32 fm_flags;              /* вхід: прапорці запиту */
    __u32 fm_mapped_extents;     /* вихід: скільки екстентів заповнено */
    __u32 fm_extent_count;       /* вхід: скільки місця у буфері */
    __u32 fm_reserved;
    struct fiemap_extent fm_extents[];
};
```

**Головне про формат відповіді: дір у ній немає.** Ядро повертає лише екстенти з блоками; діра — це проміжок між кінцем одного екстента й початком наступного, і викликач мусить вирахувати її сам. Це протилежність `SEEK_HOLE`, який про діру каже прямо.

**Виклик робиться двічі.** Спершу з `fm_extent_count = 0`: ядро нічого не копіює, лише кладе в `fm_mapped_extents` потрібну кількість. Потім виділяється буфер на `sizeof(struct fiemap) + n · sizeof(struct fiemap_extent)`, `fm_extent_count` ставиться в `n`, і виклик повторюється.

| прапорець запиту | значення | що робить |
|---|---|---|
| `FIEMAP_FLAG_SYNC` | `0x1` | скинути файл на носій перед побудовою карти — знімає питання відкладеного виділення |
| `FIEMAP_FLAG_XATTR` | `0x2` | віддати карту дерева розширених атрибутів, а не даних |
| `FIEMAP_FLAG_CACHE` | `0x4` | наповнити кеш стану екстентів |

Незрозумілий ядру прапорець дає `EBADR`, причому в `fm_flags` лишаються саме ті біти, яких воно не підтримує, — так і з'ясовують, що прибрати з запиту.

| прапорець екстента | значення | що означає |
|---|---|---|
| `FIEMAP_EXTENT_LAST` | `0x0001` | останній екстент у файлі — умова виходу з циклу |
| `FIEMAP_EXTENT_UNKNOWN` | `0x0002` | розташування невідоме |
| `FIEMAP_EXTENT_DELALLOC` | `0x0004` | виділення відкладено; ставиться разом з `UNKNOWN` |
| `FIEMAP_EXTENT_ENCODED` | `0x0008` | дані не є простими блоками ФС: стиснуті чи закодовані |
| `FIEMAP_EXTENT_DATA_ENCRYPTED` | `0x0080` | зашифровано; ставиться разом з `ENCODED` |
| `FIEMAP_EXTENT_NOT_ALIGNED` | `0x0100` | зсуви й довжина не вирівняні по блоку |
| `FIEMAP_EXTENT_DATA_INLINE` | `0x0200` | дані лежать усередині блока метаданих; тягне `NOT_ALIGNED` |
| `FIEMAP_EXTENT_DATA_TAIL` | `0x0400` | хвіст файлу впакований у блок разом із чужими даними; тягне `NOT_ALIGNED` |
| `FIEMAP_EXTENT_UNWRITTEN` | `0x0800` | блоки виділені, але вміст не ініціалізовано — той самий невиписаний екстент |
| `FIEMAP_EXTENT_MERGED` | `0x1000` | ФС екстентів не має, і карту зліплено з окремих блоків |
| `FIEMAP_EXTENT_SHARED` | `0x2000` | блоки спільні з іншим файлом |

Саме `UNWRITTEN` — та єдина ознака, якою карта відрізняє «блоки є, але порожні» від «блоки є з даними»; жоден `read` цієї різниці не покаже.

### Готові читачі

Писати свій обхід зазвичай не треба — карту вже друкують інші:

```sh
$ filefrag -v disk.img
Filesystem type is: ef53
File size of disk.img is 1099511627776 (268435456 blocks of 4096 bytes)
 ext:     logical_offset:        physical_offset: length:   expected: flags:
   0:        0..       9:      34816..     34825:     10:
   1:   131072..  131098:      51200..     51226:     27:      34826: last
disk.img: 2 extents found
```

Зсуви тут — у блоках тієї одиниці, яку `filefrag` назвав у другому рядку, а не в байтах. Два екстенти на терабайтний файл означають, що між блоком 9 і блоком 131072 карта не має нічого: це діра, і в самій таблиці рядка про неї немає. Позначки `eof` на останньому екстенті теж немає — `filefrag` ставить її, лише коли екстент дотягується до `st_size`, а тут за ним лежить іще одна діра, до самого кінця файлу.

| ключ `filefrag` | що дає |
|---|---|
| `-v` | подробиці: таблиця екстентів, а не самий підсумок |
| `-e` | завжди у форматі екстентів, навіть для ФС без них |
| `-s` | зробити `sync` перед запитом (той самий `FIEMAP_FLAG_SYNC`) |
| `-x` | карта розширених атрибутів |
| `-X` | номери блоків шістнадцятково |
| `-k`, `-b<розмір>` | у якій одиниці друкувати зсуви (типово 1024 Б) |
| `-B` | примусово через старий `FIBMAP` — для звірки |

Для XFS ту саму карту, але з явними рядками `hole`, друкує `xfs_bmap -vvp файл`.

## Що про це каже `stat` і `statx`

```c
struct stat {
    off_t     st_size;      /* докуди тягнеться файл, байти */
    blksize_t st_blksize;   /* бажаний розмір порції вводу-виводу */
    blkcnt_t  st_blocks;    /* скільки одиниць по 512 Б віддано файлу */
};
```

| поле | одиниця | обмовка |
|---|---|---|
| `st_size` | байти | обіцянка простору зсувів, а не зайнятого місця |
| `st_blocks` | **завжди 512 байтів** | цю одиницю називає макрос `S_BLKSIZE` з `<sys/stat.h>`, і він дорівнює 512; зв'язку з розміром блока ФС немає жодного |
| `st_blksize` | байти | підказка «якими порціями зі мною зручно працювати», а **не** розмір блока ФС — той дає `statfs` у полі `f_bsize` |

У [розширеному запиті атрибутів](root:sys-unix/statx-mask-and-unknown-values) ті самі три числа звуться `stx_size`, `stx_blocks` і `stx_blksize`, просяться масками `STATX_SIZE` та `STATX_BLOCKS` (обидві входять у `STATX_BASIC_STATS`), а одиниця `stx_blocks` так само зафіксована на 512 байтах. Man-сторінка формулює наслідок прямо: число блоків буває меншим за `stx_size/512`, коли у файлі є діри.

Звідси груба перевірка на розрідженість — та сама, якою користуються майже всі інструменти:

```
зайнято_байтів = st_blocks · 512

st_blocks · 512  ≪  st_size   →  усередині майже напевно є діри
st_blocks · 512  ≥  st_size   →  дір або немає, або вони дрібні
```

Чотири випадки, у яких ця перевірка бреше:

- `st_blocks` рахує **й блоки метаданих** — дерево екстентів чи непрямі блоки, — тому в щільного великого файлу зайняте буває трохи більшим за `st_size`;
- дані, вкладені просто в inode (`inline_data` в ext4, малі файли в Btrfs), дають ненульовий `st_size` при `st_blocks == 0` — дір немає, а перевірка кричить, що вони є;
- стиснення (Btrfs, ZFS) зменшує `st_blocks` без жодної діри; ознака `STATX_ATTR_COMPRESSED` у `statx` про це попереджає;
- блоки, спільні з іншим файлом після reflink, зараховуються обом файлам повністю, тож сума `du` по теці перевищить реально зайняте місце.

З оболонки те саме дістається одним рядком, без арифметики в голові:

```sh
$ stat -c '%n: %s байтів, зайнято %b×%B' disk.img
disk.img: 1099511627776 байтів, зайнято 296×512
```

## Утиліти й прапорці

**`fallocate(1)`** — тонка обгортка над системним викликом, режим задається прапорцем:

| ключ | режим |
|---|---|
| `-o`, `--offset` / `-l`, `--length` | межі діапазону (приймають суфікси `K`, `M`, `G`) |
| `-n`, `--keep-size` | `FALLOC_FL_KEEP_SIZE` |
| `-p`, `--punch-hole` | `FALLOC_FL_PUNCH_HOLE` (сам додає `KEEP_SIZE`) |
| `-z`, `--zero-range` | `FALLOC_FL_ZERO_RANGE` |
| `-c`, `--collapse-range` | `FALLOC_FL_COLLAPSE_RANGE` |
| `-i`, `--insert-range` | `FALLOC_FL_INSERT_RANGE` |
| `-d`, `--dig-holes` | не режим ядра: утиліта сама шукає нульові ділянки й пробиває їх на місці — так наявний щільний файл робиться розрідженим без копіювання |
| `-x`, `--posix` | семантика `posix_fallocate`: операція завершиться завжди, хай і повільно |

**`truncate(1)`** — задає `st_size`, не торкаючись жодного блока: `-s РОЗМІР` (з `+`/`-` — відносно поточного), `-r ФАЙЛ` — узяти розмір із зразка, `-c` — не створювати відсутній файл, `-o` — рахувати розмір у блоках вводу-виводу.

**Копіювання й передача.** Кожен інструмент має власний перемикач, і без нього діри перетворюються на записані нулі:

| інструмент | ключ | як саме шукає порожнечу |
|---|---|---|
| `cp` | `--sparse=auto` (типово), `always`, `never` | ходить по карті через `SEEK_HOLE`, де ФС це вміє; інакше шукає ряди нулів. `always` пробує зробити розрідженим навіть щільне джерело |
| `tar` | `-S`, `--sparse` | без ключа розріджений файл потрапляє в архів повним розміром |
| `rsync` | `-S`, `--sparse` | перетворює ряди нулів на діри в місці призначення |
| `dd` | `conv=sparse` | замість запису блока з самих нулів робить `seek`; над наявним файлом працює лише разом із `conv=notrunc` і не звільняє вже виділені блоки |
| `du` | `--apparent-size` | показати `st_size` замість `st_blocks · 512`, тобто те, що показує `ls` |
| `ls` | `-s` | перший стовпчик — зайняте місце (типово в одиницях по 1024 Б), а не розмір |

Різниця між цими рядками одна, і вона вирішує вибір інструмента: **у наявному файлі, на місці, діру пробиває тільки `fallocate`** — прапорцем `--punch-hole` за точними межами або `--dig-holes` по всіх нульових ділянках. Усе інше в таблиці працює лише під час копіювання: воно або зберігає розрідженість джерела, або створює її в **копії** з нульових рядів, а сам оригінал лишає таким, як був.
