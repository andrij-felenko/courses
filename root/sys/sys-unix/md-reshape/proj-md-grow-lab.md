# ⚙️ Практикум: міграція RAID1 → RAID5 → RAID6 та відновлення після збою

У цьому практичному дослідженні розбирається повний життєвий цикл динамічної перебудови програмного дискового масиву в операційній системі Linux. Ми розгорнемо ізольоване тестове середовище на основі віртуальних блокових пристроїв loopback, зберемо дзеркальний масив RAID1, наповнимо його контрольними бінарними даними, а потім поетапно здійснимо міграцію рівнів у RAID5 та RAID6 зі збільшенням кількості дисків без розмонтування файлової системи та без зупинки вводу/виводу.

На завершення ми змоделюємо аварійне зникнення живлення системи посеред перебудови з використанням зовнішнього резервного файлу (`--backup-file`) та детально розберемо покрокову процедуру відновлення цілісності даних.

---

## 1. Підготовка віртуальних накопичувачів

Для безпечного проведення експериментів без ризику пошкодження фізичних дисків хостової системи створимо п'ять файлів-образів фіксованого розміру (по 1 Гігабайту кожен). Для швидкого виділення розрідженого дискового простору використаємо утиліту `truncate`, після чого зв'яжемо створені файли з петльовими блоковими пристроями ядра через підсистему `loop`:

У результаті виконання цих команд ядро призначить віртуальні пристрої, наприклад `/dev/loop0`, `/dev/loop1`, `/dev/loop2`, `/dev/loop3` та `/dev/loop4`. Кожен із них повноцінно емулює дисковий накопичувач із підтримкою стандартних черг запитів блокового шару Linux.

## 2. Створення RAID1, файлова система та фіксація контрольних сум

Створимо класичне 2-дискове дзеркало RAID1 на базі накопичувачів `/dev/loop0` та `/dev/loop1`, використовуючи стандартний формат метаданих `1.2`. ## 3. Етап 1: Міграція RAID1 → 2-дисковий RAID5

Пряма трансформація дзеркала RAID1 у повноцінний 3-дисковий масив RAID5 за одну команду не підтримується рушієм `mdadm`, оскільки зміна рівня масиву та додавання дисків є двома різними фазами геометричної перебудови.

Першим кроком ми перетворюємо дзеркало RAID1 на масив RAID5 із двох дисків. У 2-дисковому RAID5 перший накопичувач несе корисні дані, а другий містить обчислену парність XOR. Оскільки для двох дисків сума XOR за модулем два тотожна копіюванню (`P = D ⊕ 0 = D`), фізичне розміщення даних на дисках не змінюється:

```bash
# Перемикаємо рівень масиву на RAID5 наживо
sudo mdadm --grow /dev/md0 --level=5

# Перевіряємо оновлений статус у файлі /proc/mdstat
cat /proc/mdstat
```

Ядро миттєво перемикає внутрішній обробник із модуля `raid1.ko` на `raid5.ko`. При цьому файлова система не зазнає жодних пауз у роботі, а час перемикання становить менше 10 мілісекунд.

---

## 4. Етап 2: Розширення RAID5 до 3 дисків (живий reshape)

Тепер під'єднаємо третій накопичувач `/dev/loop2` і запустимо процедуру розширення масиву до трьох активних дисків. Це подвоїть доступний корисний простір сховища (з 1 ГіБ до 2 ГіБ) та активує перерозподіл смуг:

```bash
# 1. Додаємо новий диск як запасний (spare)
sudo mdadm --add /dev/md0 /dev/loop2

# 2. Запускаємо перебудову на 3 активні накопичувачі
sudo mdadm --grow /dev/md0 --raid-devices=3

# 3. Відстежуємо роботу фонового процесу перебудови
watch -n 0.5 'cat /proc/mdstat; echo "---"; cat /sys/block/md0/md/sync_action; cat /sys/block/md0/md/sync_completed'
```

Під час перебудови псевдофайл `/proc/mdstat` відображає роботу внутрішнього рушія `reshape`:

```
md0 : active raid5 loop2[2] loop0[0] loop1[1]
      2095104 blocks super 1.2 level 5, 512k chunk, algorithm 2 [3/3] [UUU]
      [===>.................]  reshape = 18.4% (193024/1047552) finish=0.3min speed=48256K/sec
```

У той час як ядро перераховує парність і розкладає смуги по трьох накопичувачах, файлова система залишається повністю доступною для операцій читання та запису. Перевіримо цілісність еталонного файлу безпосередньо під час активного перенесення блоків:

```bash
# Перевірка хешу файлу наживо під час перебудови
sha256sum /mnt/raid-test/testdata.bin
```

Контрольна сума збігається з еталоном байт-у-байт. Після завершення перебудови розширюємо файлову систему ext4 на весь доданий обсяг без розмонтування:

```bash
# Розширюємо файлову систему ext4 наживо
sudo resize2fs /dev/md0

# Перевіряємо новий доступний простір
df -h /mnt/raid-test
```

Розмір змонтованої файлової системи збільшився з 1 ГіБ до 2 ГіБ без переривання доступу користувачів.

## 5. Етап 3: Міграція RAID5 → RAID6 (додавання другого захисту Q)

Для забезпечення стійкості до одночасної відмови двох накопичувачів виконаємо міграцію масиву з RAID5 у RAID6 з додаванням четвертого диска `/dev/loop3`:

```bash
# Додаємо четвертий диск у масив
sudo mdadm --add /dev/md0 /dev/loop3

# Переводимо масив у RAID6 на 4 накопичувачі
sudo mdadm --grow /dev/md0 --level=6 --raid-devices=4

# Спостерігаємо за обчисленням другого синдрому парності Q
watch -n 1 'cat /proc/mdstat'
```

Драйвер ядра генерує таблиці синдромів Ріда–Соломона в скінченному полі Галуа GF(2⁸), розраховує другий блок парності Q для кожної смуги та записує нову геометрію на диски. Після завершення масив витримує одночасну втрату двох будь-яких дисків.

## 6. Експеримент: симуляція аварійного краху з `--backup-file`

Для перевірки роботи механізму резервного файлу в умовах критичного перекриття смуг створимо окремий тестовий масив RAID5 зі старим форматом метаданих `1.0` (який розміщує суперблок у кінці диска й не має вільного запасу `data_offset` на початку, що робить зовнішній резервний файл обов'язковим):

:::code proj-md-grow-lab/sh/6-eksperyment-symuliatsiia.sh

Масив залишився в незавершеному стані: частина смуг уже була перезаписана, оригінальні блоки збережені у файлі `/tmp/raid-lab/reshape.bak`, а суперблок на дисках містить прапорець `MD_FEATURE_RESHAPE_ACTIVE`.

Спроба зібрати такий масив звичайною командою без надання резервного файлу буде заблокована утилітою `mdadm` для захисту від остаточного руйнування даних:

```bash
# Спроба збирання без backup-file (буде відхилено утилітою mdadm)
sudo mdadm --assemble /dev/md1 /dev/loop0 /dev/loop1 /dev/loop2
```

Виконуємо правильне відновлення масиву з використанням збереженого резервного файлу:

```bash
# Коректне збирання з відновленням перерваної смуги
sudo mdadm --assemble --backup-file=/tmp/raid-lab/reshape.bak /dev/md1 \
    /dev/loop0 /dev/loop1 /dev/loop2

# Перевіряємо відновлення та продовження процесу перебудови
cat /proc/mdstat
```

Утиліта `mdadm` зчитує збережені блоки з файлу `reshape.bak`, відновлює пошкоджену в момент аварії смугу на дисках, повертає масив у консистентний стан і передає керування ядру, яке успішно доводить процес перебудови до 100%.

## 7. Діагностика метаданих через `mdadm --examine`

Для детальної перевірки внутрішнього стану накопичувачів після завершення всіх етапів перебудови виконаємо інспекцію метаданих суперблока на одному з дисків-учасників:

```bash
# Детальний перегляд суперблока
sudo mdadm --examine /dev/loop0
```

У виводі команди звернемо увагу на такі критичні поля:
* `Raid Level` — відображає кінцевий активний рівень масиву (наприклад, `raid6`).
* `Raid Devices` — поточна кількість активних накопичувачів (наприклад, `4`).
* `Reshape pos` — значення позиції перебудови, яке після успішного завершення містить `0` або `none`, що свідчить про відсутність активних транзакцій перенесення даних.
* `Data Offset` — зміщення першого сектора даних від початку розділу накопичувача.
