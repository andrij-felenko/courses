# 📋 Стрими в xHCI: поля контекстів, номери на дротах, виклики ядра

Номер стриму — єдине, що тримає всю конструкцію вкупі, і дорогою від драйвера до дротів він устигає полежати в кількох різних місцях: у контексті кінцевої точки, у масиві контекстів стримів, у регістрі-дзвінку, у заголовку пакета. Нижче — розкладка кожного з цих місць за специфікаціями xHCI 1.2 та USB 3.2 і за кодом ядра Linux 6.x, а також те, чого на цій дорозі **немає**, — бо саме через це драйвер мусить робити зайву роботу.

Опис спирається на будову контролера: контекст кінцевої точки, кільце заявок, кільце подій і регістр-дзвінок як спосіб сказати «є робота» — усе це заведено в [драйвері контролера хоста USB](topic:sys-unix/usb-host-controller).

## Контекст кінцевої точки: вмикач стримів

Два поля в контексті точки вирішують, чи ввімкнено стрими й скільки їх, а разом з ними змінюється й зміст поля `deq`: воно починає вказувати не на кільце, а на масив.

**DWORD 0** (`ep_info` в термінах ядра):

| Біти | Поле | Значення |
| --- | --- | --- |
| 2:0 | EP State | 0 disabled · 1 running · 2 halted · 3 stopped · 4 error |
| 7:3 | RsvdZ | — |
| 9:8 | Mult | для ізохронних |
| 14:10 | **MaxPStreams** | 0 — стримів немає; n > 0 — записів у первинному масиві |
| 15 | **LSA** | 1 — плаский масив; 0 — дозволено вторинні масиви |
| 23:16 | Interval | для періодичних |
| 31:24 | Max ESIT Payload Hi | для періодичних |

```
записів у первинному масиві = 2^(MaxPStreams + 1)

MaxPStreams = 0   →  стримів немає, deq вказує просто на кільце
MaxPStreams = 4   →  32 записи
MaxPStreams = 15  →  65536 записів (стеля за специфікацією; 16…31 зарезервовано)
```

Зворотний перерахунок у ядрі робиться пошуком старшого встановленого біта: `max_primary_streams = fls(num_stream_ctxs) - 2`, тобто для 32 контекстів у поле лягає 4.

**DWORD 1** (`ep_info2`) цікавий одним бітом:

| Біти | Поле | Значення |
| --- | --- | --- |
| 2:1 | CErr | лічильник дозволених помилок |
| 5:3 | EP Type | 2 — Bulk OUT · 6 — Bulk IN (стрими лише для цих двох) |
| 7 | **HID** — Host Initiate Disable | 1 — хостові заборонено починати рух самотужки |
| 15:8 | Max Burst Size | |
| 31:16 | Max Packet Size | |

`HID` — це і є заборона хостової ініціативи, і живе вона саме тут, у контексті xHCI, а не в дескрипторі пристрою. Поставлена одиниця лишає хостові єдиний спосіб достукатися — службовий номер Prime. У драйвері Linux для цього біта немає навіть макроса: поле завжди лишається нулем, тож ініціатива хоста дозволена скрізь.

## Контекст стриму: шістнадцять байтів на кільце

| Біти | Поле |
| --- | --- |
| 0 | **DCS** — очікуваний біт циклу вказівника прочитаного |
| 3:1 | **SCT** — тип запису |
| 63:4 | адреса кільця або вкладеного масиву |
| 127:64 | RsvdZ, віддано контролерові під внутрішні потреби |

Адреса й службові біти лежать в одному 64-бітному слові саме тому, що кільце вирівняне, і молодші біти адреси однаково нульові. Ядро складає слово однією операцією:

```c
addr = cur_ring->first_seg->dma | SCT_FOR_CTX(SCT_PRI_TR) | cur_ring->cycle_state;
stream_info->stream_ctx_array[cur_stream].stream_ring = cpu_to_le64(addr);
```

Кодування `SCT` відповідає на питання «що на іншому кінці вказівника»:

| SCT | Назва | Що за вказівником |
| --- | --- | --- |
| 0 | Secondary Transfer Ring | кільце; сам запис лежить у вторинному масиві |
| 1 | Primary Transfer Ring | кільце; запис лежить у первинному масиві |
| 2 | Primary Stream Array, 8 | вторинний масив на 8 записів |
| 3 | Primary Stream Array, 16 | 16 записів |
| 4 | Primary Stream Array, 32 | 32 записи |
| 5 | Primary Stream Array, 64 | 64 записи |
| 6 | Primary Stream Array, 128 | 128 записів |
| 7 | Primary Stream Array, 256 | 256 записів |

```
для SCT ≥ 2:  записів у вторинному масиві = 2^(SCT + 1)
```

Нульовий запис масиву не заповнюють ніколи — цикл розподілу в ядрі починається з одиниці, бо номер стриму 0 зарезервовано.

## Стеля з боку контролера

Скільки записів первинного масиву контролер узагалі витягує, сказано в його параметрах — регістрі `HCCPARAMS1`:

| Біти | Поле | Значення |
| --- | --- | --- |
| 7 | NSS — No Secondary SID Support | 1 — вторинних масивів контролер не вміє |
| 15:12 | **MaxPSASize** | стеля первинного масиву |

```
стеля записів = 2^(MaxPSASize + 1)

MaxPSASize = 0   →  стримів контролер не підтримує
MaxPSASize = 4   →  32
MaxPSASize = 15  →  65536
```

## Де номер є, а де його немає

**Регістр-дзвінок** — на кожен слот свій; номер стриму приїхав у старшу половину:

| Біти | Поле |
| --- | --- |
| 7:0 | DB Target — індекс точки в контексті пристрою (DCI) |
| 15:8 | RsvdZ |
| 31:16 | **DB Stream ID** |

```c
#define DB_VALUE(ep, stream)   ((((ep) + 1) & 0xff) | ((stream) << 16))
```

Молодша половина — не номер кінцевої точки з дескриптора, а її індекс у контексті пристрою:

```
DCI = 2 · номер точки + (1 для IN, 0 для OUT)
DCI = 1 для нульової точки керування

bulk-IN № 2   →  DCI = 5
bulk-OUT № 2  →  DCI = 4
```

Для точки без стримів у старшу половину пишуть нуль.

**Подія про завершення передачі номера стриму не несе.** Поля для нього в Transfer Event TRB немає: там є вказівник на TRB, довжина, код завершення, номер точки й номер слота — і все. Тому драйвер відновлює стрим навпаки, з адреси: за DMA-адресою з події він знаходить, якому кільцю належить цей відрізок пам'яті.

```c
ep_trb_dma = le64_to_cpu(event->buffer);
ep_ring = xhci_dma_to_transfer_ring(ep, ep_trb_dma);   /* пошук за адресою */
```

У `xhci_dma_to_transfer_ring()` точка зі стримами йде в дерево `stream_info->trb_address_map`, де за старшими бітами адреси сегмента лежить потрібне кільце. Ціна — пошук по дереву на кожну подію, а подій за секунду сотні тисяч.

Явне поле номера є ще в команді **Set TR Dequeue Pointer** — тій, якою після зупинки точки пересувають вказівник прочитаного:

| Слово | Біти | Поле |
| --- | --- | --- |
| DW0–DW1 | 0 · 3:1 · 63:4 | DCS · SCT · нова адреса — розкладка контексту стриму |
| DW2 | 31:16 | **Stream ID** — котре саме кільце пересуваємо |
| DW3 | 20:16 · 31:24 | Endpoint ID · Slot ID |

## Що обіцяє пристрій

Кількість стримів пристрій заявляє в дескрипторі-компаньйоні кінцевої точки SuperSpeed (`bDescriptorType` = 0x30), який іде одразу за звичайним дескриптором точки:

| Зсув | Поле | Для bulk |
| --- | --- | --- |
| 0 | `bLength` | 6 |
| 1 | `bDescriptorType` | 0x30 |
| 2 | `bMaxBurst` | пакетів у пачці мінус один |
| 3 | `bmAttributes` | **біти 4:0 — MaxStreams**, біти 7:5 не вживані |
| 4–5 | `wBytesPerInterval` | 0 |

```
стримів у пристрою = 2^MaxStreams

MaxStreams = 0        →  стримів немає
MaxStreams = 5        →  32
MaxStreams = 16       →  65536 (стеля за специфікацією)
MaxStreams = 17…31    →  зарезервовано
```

## Номери на дротах

Шістнадцять бітів у заголовку пакета SuperSpeed дають 65536 значень, але три з них службові:

| Номер | Призначення |
| --- | --- |
| 0 | зарезервовано: «без стриму», звичайна bulk-передача |
| 1 … 65533 | робочі номери — саме вони адресують кільця |
| 0xFFFE | **Prime** — хост будить пристрій: «у мене є для тебе робота» |
| 0xFFFF | зарезервовано, жодного кільця не адресує |

Робочий номер називає пристрій пакетом ERDY, і саме він вирішує, чия черга; докладніше про сам рівень сигналів — у [фізиці USB 3](topic:com-devices/usb3-physical).

## Виклики ядра

`usbcore` дає рівно два виклики; обидва працюють не з однією точкою, а з **набором** точок одного інтерфейсу, бо номер стриму мусить означати те саме на всіх них.

```c
int usb_alloc_streams(struct usb_interface *interface,
                      struct usb_host_endpoint **eps, unsigned int num_eps,
                      unsigned int num_streams, gfp_t mem_flags);

int usb_free_streams(struct usb_interface *interface,
                     struct usb_host_endpoint **eps, unsigned int num_eps,
                     gfp_t mem_flags);
```

`num_streams` — скільки робочих номерів потрібно; заведені номери будуть від 1 до отриманого значення. Повертається **фактична** кількість — найменше з трьох стель: запит драйвера, `2^MaxStreams` із дескриптора пристрою, `2^(MaxPSASize+1)` із параметрів контролера. Від'ємне значення — код помилки.

**Скільки насправді дістанеться драйверові, який просить 256.**

```
запит драйвера                         = 256
дескриптор пристрою, MaxStreams = 5    = 2^5   = 32
параметри контролера, MaxPSASize = 15  = 2^16  = 65536
                                         ───────────────────────
фактично заведено                      = min(256, 32, 65536) = 32

робочі номери            →  1 … 32
записів у масиві         →  32 + 1 = 33, угору до степеня двійки = 64
у поле MaxPStreams ляже  →  fls(64) - 2 = 5,  бо 2^(5+1) = 64
```

Зайвий запис береться під нульовий номер, який не адресує нічого: масив завжди на степінь двійки, тож під 32 робочих номери йде 64 записи. Через це й стеля контролера рахується в записах, а не в робочих номерах — за `2^(MaxPSASize+1)` записів робочих номерів лишається на один менше. Драйвер, який припустив, що дістав запитані 256, зіпсує кожну команду з номером понад 32.

Номер на окремій заявці задають одним полем:

```c
unsigned int stream_id;   /* (in) stream ID */
```

Умови, за яких виклик має право спрацювати:

| Умова | Наслідок порушення |
| --- | --- |
| `num_streams > 1` | `-EINVAL` |
| точка bulk і швидкість SuperSpeed | `-EINVAL` |
| на точках ще немає стримів | `-EINVAL`; спершу `usb_free_streams()` |
| контролер без прапорця `XHCI_BROKEN_STREAMS` | `-EINVAL` |
| вистачає пам'яті на масив і кільця | `-ENOMEM` |
| на точках немає жодної живої заявки | коду помилки на це немає: контекст точки перебудовується на ходу, тож заявки драйвер мусить скасувати сам і наперед |

## Коди завершення про стрими

| Код | Назва | Коли |
| --- | --- | --- |
| 6 | Stall Error | зупиняє **всю** точку разом з усіма стримами |
| 10 | Invalid Stream Type Error | `SCT` у записі не узгоджений з тим, що описує `LSA` |
| 34 | **Invalid Stream ID Error** | пристрій назвав номер, для якого хост не заводив запису |

> 🔧 **Навіщо це.** Заявлену пристроєм стелю видно без жодного коду: `lsusb -v` на дескрипторі-компаньйоні друкує рядок `MaxStreams`, а поруч `bMaxBurst`. Якщо там нуль, далі можна не шукати — ані прошивка, ані драйвер стримів не дадуть, і черга до диска лишиться одиничною.
