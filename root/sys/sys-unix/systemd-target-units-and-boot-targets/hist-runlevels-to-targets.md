# 📜 Від чисел до графа: еволюція від SysVinit Runlevels до systemd Targets

Цей історичний документ описує еволюційний шлях від лінійних числових рівнів виконання SysVinit до графових цільових юнітів systemd, пояснюючи причини відмови від монолітної схеми `/etc/inittab` та переходу до декларативних моделей станів.

---

## Парадигма SysVinit: числові рівні та сценарії Shell

У традиційних операційних системах UNIX та ранніх дистрибутивах Linux (таких як Debian, Red Hat Enterprise Linux 5, Slackware, CentOS 5) керування станами ініціалізації базувалося на системі **SysVinit** (від англ. *System V Initialization*), розробленій для систем UNIX AT&T System V у 1980-х роках.

Основою цієї архітектури був концепт **рівнів виконання** (runlevels, від англ. *run level* — рівень роботи) — заздалегідь визначених глобальних числових станів операційної системи від `0` до `6`, а також спеціального рівня `S` або `1` для однокористувацького відновлення:

- **Runlevel 0**: Зупинка операційної системи та підготовка до вимкнення живлення (Halt).
- **Runlevel 1 / S**: Однокористувацький режим (Single-User Mode / Rescue). Використовувався для відновлення файлових систем та зміни паролів суперкористувача root без запуску мережі.
- **Runlevel 2**: Багатокористувацький режим без підтримки мережевих файлових систем NFS (у дистрибутивах Debian — повноцінний режим за замовчуванням).
- **Runlevel 3**: Повноцінний багатокористувацький режим із підтримкою мережі та консольним текстовим інтерфейсом (CLI). Стандартний режим для серверних систем.
- **Runlevel 4**: Зарезервований або призначений для спеціальних користувацьких потреб.
- **Runlevel 5**: Графічний режим (GUI) з автоматичним запуском графічного сервера X11 та дисплейного менеджера (XDM, GDM, KDM).
- **Runlevel 6**: Перезавантаження операційної системи (Reboot).

Головним конфігураційним файлом системного демона `init` слугував `/etc/inittab`. У цьому файлі визначався глобальний рівень за замовчуванням через спеціальну директиву `id:3:initdefault:`, а також налаштовувалися інструкції щодо виклику керуючого сценарію для кожного рівня: `l3:3:wait:/etc/rc.d/rc 3`.

### Механізм каталогів /etc/rcN.d/

Зміна рівня виконання зводилася до виклику головного командного сценарію `/etc/rc`, який отримував номер цільового рівня та послідовно виконував Shell-скрипти з відповідного каталогу `/etc/rc<N>.d/`:

1. Спочатку запускалися всі скрипти, що починалися з літери `K` (від англ. *Kill* — зупинити), для припинення роботи служб, відсутніх у новому рівні виконання.
2. Потім запускалися всі скрипти, що починалися з літери `S` (від англ. *Start* — запустити), для активації нових необхідних служб.

Порядок виконання визначений двозначним числовим префіксом у назві символьного посилання. Наприклад, у каталозі `/etc/rc3.d/`:
- `K15httpd` виконувався раніше за `K20mysqld`;
- `S10network` виконувався раніше за `S55sshd`.

```
/etc/rc3.d/
├── S10network -> ../init.d/network
├── S20syslog  -> ../init.d/syslog
├── S55sshd    -> ../init.d/sshd
└── S80apache2 -> ../init.d/apache2
```

## Фундаментальні обмеження чисельної ініціалізації

Попри простоту та зрозумілість для системних адміністраторів, лінійна модель рівнів виконання SysVinit зіткнулася з критичними обмеженнями під час стрімкого розвитку багатоядерних обчислювальних систем та систем гарячого підключення обладнання (Hotplug):

### 1. Відсутність явного графа залежностей
Порядок запусків через префікси `S10`, `S15` був жорстко зафіксований адміністратором або мейнтейнером пакета. Скрипт `S55sshd` не мав реального механізму перевірки, чи дійсно мережевий інтерфейс у `S10network` отримав IP-адресу, або чи запустився демон системного логування `S20syslog`. Якщо один зі скриптів падав або зависав, уся послідовність завантаження блокувалася на невизначений час.

### 2. Строго послідовне виконання
Сценарії Shell виконувалися послідовно в одному потоці. Усі операції введення-виведення (читання конфігурацій з диска, очікування відповіді від мережевих socket-інтерфейсів) виконувалися синхронно, що призводило до тривалого часу завантаження системи (від 40 секунд до кількох хвилин).

### 3. Жорсткість та обмеженість станів
Числова шкала 0–6 не дозволяла описувати ортогональні або проміжні стани системи. Неможливо було створити незалежний стан «система готова для прийому мережевого трафіку, але без локальних звукових служб» або «стан діагностики дискового масиву». Система була обмежена виключно 7 глобальними конфігураціями.

### 4. Ненадійність транзакцій при зміні рівнів
Виконання команди `init 3` після `init 5` вимагало запуску десятків скриптів зупинки та старту. Якщо під час виконання одного зі скриптів ставалася помилка, система залишалася в неокресленому «проміжному» стані, оскільки SysVinit не мав механізму відкочування (rollback) та не відстежував дочірні процеси (PID), запущені скриптами.

## Пошук альтернатив та поява systemd Targets

У середині 2000-х років розробники дистрибутивів Linux розпочали пошук нових архітектурних рішень:

- **Apple launchd (2005)**: Впровадив концепцію активації за сокетами та відмови від послідовних сценаріїв ініціалізації в macOS, продемонструвавши можливість швидкого завантаження.
- **Ubuntu Upstart (2005)**: Асинхронна подійна система (Event-driven init), де служби запускалися у відповідь на події ядра (`hardware-attached`, `network-up`). Однак складна павутина подій у великих системах ставала важконалагоджуваною та призводила до гонок умов (Race Conditions).
- **systemd (2010)**: Леннарт Поттерінг (Lennart Poettering) та Кай Сіверс (Kay Sievers) запропонували відмовитися як від числових рівнів, так і від подійного хаосу на користь **спрямованого ациклічного графа (DAG — Directed Acyclic Graph)** станів.

### Заміна runlevels на target-юніти

Замість глобальних чисел у systemd було впроваджено **цільові юніти (`.target`)** — декларативні вузли синхронізації графа. 

Рівень виконання перестає бути статичним числом і стає назвою цільового стану. Наприклад, замість `runlevel 5` використовується `graphical.target`, який явно вказує у своєму графі:
- `Wants=multi-user.target`
- `Requires=display-manager.service`
- `After=multi-user.target display-manager.service`

Такий підхід дозволив розбити процес завантаження на паралельні гілки, де PID 1 обчислює точний порядок виконання на основі графа залежностей, а не текстових префіксів у назвах файлів. Рівні виконання SysVinit стали лише сумісними символьними посиланнями на відповідні цільові юніти systemd.
