# 📋 Специфікація текстової бази даних dpkg status

Цей довідник містить технічний опис структури полів, автоматів станів та файлового індексу системної бази даних dpkg (`/var/lib/dpkg/status`), необхідний для розуміння внутрішнього устрою низькорівневих пакетних менеджерів.

## 1. Загальна форма запису та синтаксис Deb822

Файл `/var/lib/dpkg/status` є текстовою базою даних, побудованою на основі формату Deb822. Цей формат походить від мережевого стандарту повідомлень RFC 822 / RFC 5322 і являє собою послідовність блоків метаданих, відокремлених один від одного порожніми рядками. Кожен блок відповідає одному пакунку, збереженому в базі даних системи.

Усередині кожного блоку інформація кодується у вигляді пар «Ключ: Значення». Заголовки полів не чутливі до регістру символів (хоча за традицією використовуються стандартні заголовки з великої літери). Значення поля може бути як однорядковим, так і багаторядковим. Якщо значення поля займає кілька рядків (як-от опис пакунка `Description` або списки конфігураційних файлів `Conffiles`), кожен наступний рядок зобов'язаний починатися з неменше ніж одного символу пробілу або табуляції. Порожній рядок усередині багаторядкового поля позначається поодинокою крапкою ` .`, перед якою стоїть пробіл.

### Детальний розбір полів специфікації Deb822

Поле `Package` є обов'язковим першим заголовочним полем у кожному записі. Воно визначає унікальне ім'я пакунка в системі. Ім'я пакунка мусить складатися виключно з малих букв латинського алфавіту, цифр та символів дефісу і плюса. Розділові символи підкреслення або пробіли в імені пакунка суворо заборонені, оскільки вони використовуються як роздільники у внутрішніх індексах та іменах створених архівних файлів `.deb`.

Поле `Status` є центральним атрибутом, який описує поточний стан пакунка у файловій системі та намір системного адміністратора. Воно містить три суворі текстові прапорці, розділені пробілами, що формують тривимірний автомат станів.

Поле `Priority` вказує на рівень важливості пакунка для функціонування операційної системи. Значення `required` надається пакункам, без яких завантаження ядра та базової командної оболонки є неможливим (наприклад, `sysvinit`, `dpkg`, `base-files`). Значення `important` охоплює мінімальний набір інструментів Unix, необхідний для роботи адміністратора. Значення `standard` включає стандартне оточення CLI (редактори, мережеві утиліти). Значення `optional` є найпоширенішим і використовується для всього прикладного програмного забезпечення (веб-сервери, графічні оболонки, компилятори). Значення `extra` раніше застосовувалося для пакунків, що конфліктують із базовими.

Поле `Section` описує категорію програмного забезпечення у складі дистрибутиву. Воно використовується високорівневими менеджерами (такими як APT чи Synaptic) для групування пакунків за призначенням: `admin` (системне адміністрування), `devel` (інструменти розробки), `doc` (документація), `editors` (текстові редактори), `libs` (спільні динамічні бібліотеки), `net` (мережеві утиліти), `web` (веб-сервери та браузери).

Поле `Installed-Size` зберігає ціле число, яке описує дисковий простір у кілобайтах (KiB), який буде зайнято файлами пакунка після його повного розпакування на файлову систему. Це значення використовується менеджером залежностей для попередньої перевірки наявності вільного місця на точці монтування перед початком інсталяції.

Поле `Maintainer` містить текстовий рядок з ім'ям та контактною адресою електронної пошти особи або команди мейнтейнерів, відповідальних за збирання та підтримку даного пакунка в дистрибутиві.

Поле `Architecture` вказує цільову апаратну платформу, для якої було скомпільовано виконувані бінарні файли у складі корисного навантаження (`amd64` для 64-бітових процесорів x86-64, `arm64` для архітектури ARMv8, `i386` для застарілих 32-бітних систем). Якщо пакунок містить суто архітектурно-незалежні дані (як-от скрипти Python, конфігурації, шрифти чи документацію), використовується значення `all`.

Поле `Version` містить рядок версії пакунка. Граматика поля версії складається з трьох частин: епохи (`epoch`), основної версії розробника (`upstream_version`) та версії ревізії пакувальника (`debian_revision`).

Поле `Config-Version` з'являється у записі тоді, коли пакунок перебуває в стані оновлення або часткової конфігурації. Воно зберігає точну версію пакунка, яка первинно згенерувала збережені конфігураційні файли у каталозі `/etc`.

Поле `Provides` оголошує список віртуальних пакетів або псевдонімів, які надає цей пакунок. Віртуальні пакети дозволяють кільком різним програмам декларувати виконання однієї системної ролі. Наприклад, сервери `nginx`, `apache2` та `lighttpd` описують поле `Provides: httpd`. Завдяки цьому інші пакунки можуть декларувати залежність від абстрактного `httpd`, не прив'язуючись до конкретної реалізації веб-сервера.

Поле `Conffiles` містить список абсолютних шляхів до файлів налаштувань у каталозі `/etc`, за якими закріплено режим тристороннього зіставлення (three-way merge). Поруч із кожним шляхом записується еталонний хеш MD5, обчислений у момент збирання оригінального `.deb` пакунка.

## 2. Тривимірний автомат станів у полі Status

Поле `Status` в базі даних `/var/lib/dpkg/status` не є простим текстовим описом, а являє собою комбінацію трьох незалежних змінних стану:

1. **Бажаний стан користувача (Desired State):** Перше слово запису відображає намір адміністратора щодо пакунка. Значення `install` означає, що пакунок має бути встановлений або оновлений. Значення `hold` вказує пакетному менеджеру заблокувати поточну версію пакунка і не оновлювати його автоматично навіть при виконанні глобальних команд оновлення дистрибутиву. Значення `deinstall` вимагає вилучення бінарних файлів із збереженням конфігурацій у `/etc`. Значення `purge` вимагає повного знищення пакунка разом із його конфігураціями та логами.

2. **Прапорець цілісності та помилок (Error Flag):** Друге слово описує наявність збоїв у минулих транзакціях. Значення `ok` означає, що попередня операція пройшла без помилок і пакунок перебуває в узгодженому стані. Значення `reinstreq` (reinstallation required) сигналізує про критичний збій: процес розпакування або виконання скриптів було перервано на такій фазі, що пакунок залишив файлову систему у зламаному або нестабільному стані. У цьому стані `dpkg` відмовляється виконувати будь-які інші операції з цим пакунком, окрім примусової переінсталяції (`--reinstall`).

3. **Інсталяційний стан (Installation State):** Третє слово є поточним індикаторним станом пакунка у файловій системі:
   - `not-installed`: Пакунок відсутній у системі, його файли не розпаковувалися, конфігів немає.
   - `config-files`: Файли програми вилучені з диска, але збережені конфігураційні файли в `/etc`.
   - `half-installed`: Розпакування пакунка було розпочато, але перервалося до завершення запису всіх файлів на диск.
   - `unpacked`: Усі файли з payload успішно скопійовані у файлову систему, але скрипт керування `postinst` ще не запускався.
   - `half-configured`: Скрипт `postinst` розпочав виконання, але завершився з ненульовим кодом помилки.
   - `triggers-awaited`: Пакунок очікує завершення відкладених обробників (тригерів) від інших пакунків.
   - `triggers-pending`: Пакунок активував тригери і сам потребує виклику власного обробника тригерів.
   - `installed`: Пакунок повністю розпакований, сконфігурований, усі тригери виконані, програма готова до роботи.

## 3. Супутні індекси та механізми підміни шляхів (Diversions & Statoverride)

База даних `dpkg` складається не лише з одного файлу `status`. У каталозі `/var/lib/dpkg/` функціонують додаткові підсистеми, які вирішують складні конфлікти у файловій системі VFS.

### Механізм підміни файлів (File Diversions)
Файл `/var/lib/dpkg/diversions` зберігає індекс підміни шляхів (file diversions), який керується утилітою `dpkg-divert`. Оскільки пакетний менеджер суворо забороняє двох різним пакункам володіти одним і тим самим файлом, виникає проблема: що робити, коли один пакунок вимагає замінити виконуваний файл іншого пакунка (наприклад, підмінити системну оболонку `/bin/sh` на `/bin/dash` або розробницьку версію компілятора)?

Механізм диверсії дозволяє перейменувати оригінальний файл, записаний пакунком `A`, відвівши його за новою адресою (наприклад, `/bin/sh.distrib`), тоді як новий пакунок `B` прописує свій файл за стандартним шляхом `/bin/sh`. База даних `diversions` зберігає записи вигляду:

```text
/bin/sh
/bin/sh.distrib
dash
```

При оновленні або переінсталяції пакунка `A` пакетний менеджер звіряється з цим індексом і розпаковує оригінальний файл не за його стандартним шляхом, а за відведеним шляхом диверсії `/bin/sh.distrib`. Завдяки цьому оновлення пакунка `A` не затирає файл, встановлений пакунком `B`.

### Перевизначення атрибутів доступу (Statoverride)
Файл `/var/lib/dpkg/statoverride` керується утилітою `dpkg-statoverride` і розв'язує проблему збереження привілейованих прав доступу. Деякі системні програми (наприклад, `/usr/bin/ping`, `/usr/bin/crontab` або `/usr/bin/su`) вимагають спеціальних прав доступу: встановленого біта SetUID/SetGID (`chmod 4755`) або володіння конкретною системною групою (наприклад, `raw-network` чи `crontab`).

Якщо адміністратор або безпекова політика системи змінює права на такий файл, звичайне оновлення пакунка скинуло б ці права назад до дефолтних атрибутів з пакунка. Файл `statoverride` діє як глобальне перевизначення: перед завершенням розпакування `dpkg` зчитує `statoverride` і примусово застосовує вказаного власника, групу та права доступу до файла на диску.

### Підсистема відкладених дій (Triggers Engine)
Каталог `/var/lib/dpkg/triggers/` та супутні індекси `trigdef` і `trigdeferred` реалізують асинхронні гачки. Якщо 50 різних пакунків інсталюють нові графічні іконки у каталог `/usr/share/icons/hicolor/`, старий пакетний менеджер був змушений викликати важку утиліту оновлення кешу іконок `gtk-update-icon-cache` 50 разів поспіль після інсталяції кожного пакунка.

Тригерна система `dpkg` дозволяє пакункам декларувати інтерес до каталогів (наприклад, `interest-noawait /usr/share/icons/hicolor`). Під час розпакування 50 пакунків `dpkg` лише реєструє активацію тригера у файлі `trigdeferred`. Після завершення всієї транзакції інсталяції `dpkg` викликає обробник тригера один-єдиний раз для всіх 50 пакунків разом, що прискорює інсталяцію в десятки разів.
