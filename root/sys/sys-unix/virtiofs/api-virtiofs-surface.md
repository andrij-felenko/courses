# 📋 Контракт virtiofs: пристрій, демон, монтування

Щоб тека господаря з'явилася в гості, мусять зійтися три речі: поля, які пристрій оголошує гостьовому драйверові, ключі запуску демона `virtiofsd` і рядки QEMU, що поєднують одне з одним. Тут зібрано всі три — з номерами, типами й типовими значеннями.

## Пристрій: що гість бачить на шині

Ідентифікатор пристрою virtio — **26**. На PCI модель називається `vhost-user-fs-pci`.

### Прапорці можливостей

| Прапорець | Біт | Що означає |
|---|---|---|
| `VIRTIO_FS_F_NOTIFICATION` | 0 | пристрій має чергу сповіщень і вміє слати повідомлення FUSE у зворотний бік — не у відповідь на запит |

Статус треба назвати чесно: у специфікації virtio прапорець є, а в драйвері основного ядра (`fs/fuse/virtio_fs.c`) таблиця можливостей порожня — тобто він не узгоджується ніколи. Черга сповіщень і повідомлення `FUSE_NOTIFY_LOCK`, заради якого її вигадали, лишаються серією латок 2019–2021 років, не влитою в основне дерево. Практичний наслідок: [блокування з очікуванням](topic:sys-unix/file-locking), тобто `fcntl(F_SETLKW)`, — саме те, чого на звичайній парі «ядро плюс virtiofsd» немає.

### Розкладка черг

| Індекс | Черга | Умова |
|---|---|---|
| 0 | `hiprio` — `FUSE_FORGET`, `FUSE_INTERRUPT` | завжди |
| 1 | черга сповіщень | **лише** коли узгоджено `VIRTIO_FS_F_NOTIFICATION` |
| 1…n | черги запитів | коли прапорець не узгоджено |
| 2…n | черги запитів | коли узгоджено |

Нумерація зсувається — це головна пастка розкладки. Драйвер основного ядра має `VQ_HIPRIO = 0` і `VQ_REQUEST = 1`, тобто другого випадку в ньому не буває. Кількість черг він бере з конфігурації й обрізає до кількості процесорів гостя:

```
nvqs = 1 + min(num_request_queues, nr_cpu_ids)
```

### Конфігураційний простір (`struct virtio_fs_config`)

| Зміщення | Поле | Тип | Значення |
|---|---|---|---|
| 0…35 | `tag` | `char[36]` | мітка у UTF-8, **без завершального нуля**, добита нулями до 36 байтів |
| 36 | `num_request_queues` | `le32` | скільки черг запитів має пристрій |
| 40 | `notify_buf_size` | `le32` | розмір буфера сповіщення; поле присутнє **лише** за узгодженого `VIRTIO_FS_F_NOTIFICATION` |

Мітка — не шлях і не адреса: гість шукає на шині пристрій, у якого це поле збігається з джерелом монтування.

## DAX-вікно: область спільної пам'яті 0

| Що | Значення |
|---|---|
| Ідентифікатор області спільної пам'яті | `0` (`VIRTIO_FS_SHMCAP_ID_CACHE`) |
| `FUSE_SETUPMAPPING` | опкод 48 |
| `FUSE_REMOVEMAPPING` | опкод 49 |
| Версія протоколу FUSE | 7.31 — тоді з'явилися обидва запити й `map_alignment` |

Запит на відображення адресує дві точки одразу: місце у файлі й місце у вікні.

```c
struct fuse_setupmapping_in {
    uint64_t fh;       /* відкритий файл на боці демона            */
    uint64_t foffset;  /* зміщення у файлі                         */
    uint64_t len;      /* довжина ділянки                          */
    uint64_t flags;    /* FUSE_SETUPMAPPING_FLAG_WRITE = 1ull << 0
                          FUSE_SETUPMAPPING_FLAG_READ  = 1ull << 1 */
    uint64_t moffset;  /* куди саме у вікні покласти               */
};
```

Знімають відображення пачкою — за лічильником іде масив однакових записів:

```c
struct fuse_removemapping_in  { uint32_t count; };
struct fuse_removemapping_one { uint64_t moffset; uint64_t len; };
```

Вирівнювання узгоджують один раз, під час `FUSE_INIT`: демон ставить прапорець `FUSE_MAP_ALIGNMENT` (`1 << 26`) і кладе в поле `map_alignment` **показник степеня двійки**, а не самі байти. Гостьове ядро роздає вікно шматками по `FUSE_DAX_SZ`, і звідси вимога:

```
FUSE_DAX_SHIFT = 21
FUSE_DAX_SZ    = 1 << 21 = 2097152 байтів = 2 МіБ = 512 сторінок по 4 КіБ

умова: map_alignment ≤ 21   (вирівнювання демона не грубіше за 2 МіБ)
```

Не збіглося — ядро відмовляє в DAX замість того, щоб тихо працювати неправильно.

Одна засторога до всієї цієї таблиці: пристрій `vhost-user-fs` із основного дерева QEMU області спільної пам'яті не реєструє взагалі. Гостьова половина [прямого звертання до пам'яті](topic:sys-unix/dax-direct-access) в ядрі є з 5.10, а вікна на звичайній дистрибутивній парі немає — просити його нема в кого.

## Господар: ключі `virtiofsd`

Демон — окремий процес, що говорить із гіпервізором за домовленістю [vhost-user](topic:sys-unix/vhost-and-vdpa): гіпервізор віддає йому черги й дескриптор об'єкта з пам'яттю гостя.

**Обов'язкове:**

| Ключ | Значення |
|---|---|
| `--shared-dir <шлях>` | тека, яку віддають гостю; вона стане його коренем цієї файлової системи |
| `--socket-path <шлях>` | сокет vhost-user — демон його створює й слухає |
| `--fd <n>` | замість `--socket-path`: готовий дескриптор слухача від системи запуску; ключі взаємно виключні |
| `--tag <мітка>` | мітка, яку демон оголошує через vhost-user; підтримку з боку гіпервізора мають не всі версії, тож надійніше задавати `tag=` на пристрої QEMU |

**Кеш і дані:**

| Ключ | Типово | Значення |
|---|---|---|
| `--cache never\|metadata\|auto\|always` | `auto` | `never` — кожна операція йде до демона; `metadata` — кешувати імена й атрибути, вміст ні; `auto` — атрибути живуть обмежений час (типово секунду), вміст кешується, поки файл відкритий; `always` — без строку придатності, і тека мусить бути віддана машині безроздільно |
| `--writeback` | вимкнено | відкладений запис у гостьовому кеші |
| `--allow-direct-io` | вимкнено | шанувати `O_DIRECT` гостя |
| `--allow-mmap` | вимкнено | дозволити `mmap` у режимах `metadata` і `never` |
| `--thread-pool-size <n>` | `0` | `0` — пула немає, черги обслуговують запити власними потоками |
| `--readonly` | вимкнено | заборонити гостю запис |

**Ізоляція від гостя, якому не вірять:**

| Ключ | Типово | Значення |
|---|---|---|
| `--sandbox namespace\|chroot\|none` | `namespace` | `namespace` — власні [простори імен](topic:sys-unix/namespaces) із підміною кореня; `chroot` — лише зміна кореня; `none` — жодної ізоляції |
| `--seccomp none\|kill\|log\|trap` | `kill` | що робити з системним викликом поза дозволеним набором — [фільтр seccomp](topic:sys-unix/seccomp-filter-mechanism) |
| `--modcaps <±назва:…>` | — | доточити набір [привілеїв](topic:sys-unix/capabilities), напр. `+sys_admin:-chown` |

**Атрибути, монтування, inode:**

| Ключ | Типово | Значення |
|---|---|---|
| `--xattr` | вимкнено | увімкнути [розширені атрибути](topic:sys-unix/acl-and-xattr) взагалі |
| `--xattrmap <правила>` | — | перейменування атрибутів на льоту, щоб гість не розставляв мітки безпеки на файлах господаря |
| `--security-label` | вимкнено | приймати від гостя мітку `security.selinux` і ставити її на створюваний файл |
| `--posix-acl` | вимкнено | передавати списки доступу; вмикає за собою й `--xattr` |
| `--announce-submounts` / `--no-announce-submounts` | увімкнено | оголошувати гостю межі вкладених файлових систем, щоб два різні файли не дістали однакового номера inode |
| `--inode-file-handles never\|fallback\|prefer\|mandatory` | `prefer` | тримати замість відкритих дескрипторів [стійкі посилання на файл](topic:sys-unix/file-handles) — інакше кожен згаданий гостем inode з'їдає дескриптор |

## QEMU: два об'єкти й один пристрій

```sh
host$ virtiofsd --socket-path=/tmp/vfsd.sock --shared-dir=/srv/share --cache=auto &

host$ qemu-system-x86_64 -accel kvm -m 4G \
    -object memory-backend-memfd,id=mem,size=4G,share=on \
    -numa node,memdev=mem \
    -chardev socket,id=char0,path=/tmp/vfsd.sock \
    -device vhost-user-fs-pci,chardev=char0,tag=myfs,queue-size=1024 \
    -drive if=virtio,file=guest.qcow2
```

Порядок тут не косметичний: демон мусить уже слухати сокет, коли стартує гіпервізор, бо приєднується саме гіпервізор.

| Властивість `vhost-user-fs-pci` | Типово | Обмеження |
|---|---|---|
| `chardev` | — | обов'язкова |
| `tag` | — | обов'язкова, непорожня, не довша за 36 байтів поля `tag` |
| `num-request-queues` | `1` | більше нуля |
| `queue-size` | `128` | степінь двійки, не більша за 1024 |

Пам'ять гостя мусить лежати в об'єкті, придатному до розділення: `memory-backend-memfd` із `share=on` (це [безіменний файл у пам'яті](topic:sys-unix/memfd-create)) або `memory-backend-file` з `mem-path=/dev/shm,share=on`. І її треба справді віддати машині рядком `-numa node,memdev=…` — самого лише `-object` замало.

*Чотири пари імен; помилка в будь-якій дає ту саму зовнішню картину — гість не бачить теки.*

> 🔧 **Навіщо це.** Коли монтування не вдається, шукати причину зручно точно в цьому порядку: чи піднявся демон **до** гіпервізора, чи збігається шлях сокета з `path=` у `-chardev`, чи збігається `id=` з `chardev=` пристрою, чи збігається `tag=` з джерелом у `mount`, і чи має пам'ять `share=on` разом із `-numa node,memdev=`. П'ять звірянь імен закривають майже всі випадки, а «повільно» і «не працює зовсім» тут різні хвороби: перше — про режим кешу, друге — завжди про одне з цих п'яти.

## Гість: монтування

```sh
guest# mount -t virtiofs myfs /mnt
```

Джерело — мітка з поля `tag`, а не шлях. Своїх параметрів монтування virtiofs має рівно один:

| Параметр | Значення |
|---|---|
| `dax` | те саме, що `dax=always` |
| `dax=always` | вести через вікно все, що в нього вміщається |
| `dax=never` | не вживати вікно ніколи |
| `dax=inode` | вживати вікно лише для тих файлів, які демон позначив придатними |

Більше нічого свого немає: звичні ключі FUSE на кшталт `allow_other` чи `user_id` тут не приймаються, бо демон належить господареві, а не тому, хто монтує.
