# 🧮 Розрахунок пропускної здатності шини та хронометражу відеорежимів

Під час валідації атомарної транзакції у фазі `DRM_MODE_ATOMIC_TEST_ONLY` драйвер ядра Linux перевіряє, чи здатні підсистема пам'яті та дисплейний контролер GPU (CRTC) обробити необхідний потік піксельних даних. Якщо сумарна швидкість читання з пам'яті для всіх активних площин (Planes) перевищує максимальну пропускну здатність системної шини RAM або відеопам'яті VRAM, ядро відхиляє запит із помилкою `-EBUSY` або `-EINVAL`.

Нижче наведено математичний розрахунок хронометражу кадру (Display Timings) та сумарного обсягу читання з пам'яті під час апаратного розгортання (Scanout Memory Bandwidth).

---

## 1. Структура кадрової розгортки та інтервали гасіння (Blanking Intervals)

Повний кадровий прямокутник у дисплейному контролері складається з двох основних частин:
1. **Active Area (Активна область):** Зображення, яке безпосередньо відображається на матриці монітора (`H_active × V_active`).
2. **Blanking Intervals (Інтервали гасіння):** Службові паузи у розгортці, під час яких пікселі не виводяться на екран (`H_blank`, `V_blank`). У сучасних інтерфейсах HDMI та DisplayPort під час інтервалів гасіння передаються пакети аудіоданих, метадані HDR та сигнали кадрової синхронізації.

Кожен інтервал гасіння розбивається на три підкомпоненти:
- **Front Porch (Передній майданчик):** Пауза між завершенням виводу активного рядка та початком синхроімпульсу.
- **Sync Pulse (Синхроімпульс):** Імпульс рядкової (`HSync`) або кадрової (`VSync`) синхронізації.
- **Back Porch (Задній майданчик):** Пауза між закінченням синхроімпульсу та початком наступного активного рядка.

Сумарний розмір кадрової матриці обчислюється додаванням інтервалів гасіння до активної області:

```
H_total = H_active + H_blank
V_total = V_active + V_blank
```

## 2. Розрахунок тактової частоти пікселів (Pixel Clock)

Тактова частота генератора пікселів `Pixel_Clock` (вимірюється в герцах, Гц) показує, скільки пікселів (включаючи інтервали гасіння) дисплейний контролер мусить сформувати за одну секунду. Вона дорівнює добутку повних розмірів кадрової розгортки на частоту оновлення екрана `Refresh_Rate`:

```
Pixel_Clock = H_total · V_total · Refresh_Rate
```

Стандарт VESACVT-RB (Coordinated Video Timings — Reduced Blanking) оптимізує інтервали гасіння для цифрових моніторів, зменшуючи `H_blank` та `V_blank` для зниження вимог до тактової частоти генератора PLL.

### Покроковий приклад обчислення для відеорежиму 4K (3840×2160 при 60 Гц, CVT-RB timing)

Вихідні параметри розгортки для режиму 3840×2160 зі зменшеним гасінням:
- Активна ширина: `H_active = 3840` пікселів;
- Інтервал рядкового гасіння: `H_blank = 160` пікселів;
- Повна ширина розгортки: `H_total = 3840 + 160 = 4000` пікселів;
- Активна висота: `V_active = 2160` рядків;
- Інтервал кадрового гасіння: `V_blank = 62` рядки;
- Повна висота розгортки: `V_total = 2160 + 62 = 2222` рядки;
- Частота оновлення: `Refresh_Rate = 60` Гц.

Обчислення генерації частоти пиксельного клока:

```
Pixel_Clock
= H_total · V_total · Refresh_Rate
= 4000 · 2222 · 60                [множення розмірів розгортки на частоту кадру]
= 533280000 Гц                    [533.28 МГц]
```

Для підтримки цього відеорежиму фазове автопідстроювання частоти (PLL) дисплейного енкодера GPU мусить згенерувати тактовий сигнал `533.28 МГц`.

## 3. Розрахунок пропускної здатності шини пам'яті (Scanout Bandwidth)

Під час сканування кадру дисплейний контролер (CRTC) мусить постійно зчитувати піксельні дані з кадрових буферів (Planes) у системній оперативній пам'яті (RAM) або у відеопам'яті (VRAM). Сумарна швидкість читання даних `Bandwidth_Total` (у байтах за секунду, Б/с) дорівнює сумі потоків читання всіх активних площин:

```
Bandwidth_Total = ∑ (SRC_W[i] · SRC_H[i] · Bpp[i] · Refresh_Rate)
```

де:
- `SRC_W[i]`, `SRC_H[i]` — ширина та висота прямокутника вибірки з `i`-ї площини в пікселях;
- `Bpp[i]` — кількість байтів на піксель для колірного формату данної площини;
- `Refresh_Rate` — частота оновлення кадру (Гц).

### Визначення щільності даних `Bpp` для типових DRM-форматів:
- `DRM_FORMAT_ARGB8888` / `XRGB8888` (8 біт на канал): `4` байти на піксель;
- `DRM_FORMAT_RGB565` (16 біт на піксель): `2` байти на піксель;
- `DRM_FORMAT_NV12` (YUV 4:2:0 напівпланарний, 8 біт): `1.5` байта на піксель;
- `DRM_FORMAT_P010` (YUV 4:2:0 HDR, 10 біт у 16-бітному контейнері): `3` байти на піксель;
- `DRM_FORMAT_ARGB2101010` (10 біт на RGB канал): `4` байти на піксель;
- `DRM_FORMAT_RGBA16F` (16-бітний плаваючий RGB HDR): `8` байтів на піксель.

---

### Приклад розрахунку багатоплощинної конфігурації (Primary 4K + Overlay 1080p + Cursor)

Розглянемо робочу станцію з монітором 4K на частоті 120 Гц із трьома одночасно активними апаратними площинами:

#### 1. Primary Plane (Основний робочий стіл 4K в ARGB8888):
- `SRC_W = 3840`, `SRC_H = 2160`, `Bpp = 4` байти, `Refresh_Rate = 120` Гц.

```
BW_Primary
= 3840 · 2160 · 4 · 120
= 8294400 · 480                  [площа кадру · байт/кадр]
= 3981312000 Б/с                 [≈ 3.981 ГБ/с]
```

#### 2. Overlay Plane (Відеоплеєр 1080p у форматі NV12):
- `SRC_W = 1920`, `SRC_H = 1080`, `Bpp = 1.5` байта, `Refresh_Rate = 120` Гц.

```
BW_Overlay
= 1920 · 1080 · 1.5 · 120
= 2073600 · 180                  [площа кадру · байт/кадр]
= 373248000 Б/с                  [≈ 0.373 ГБ/с]
```

#### 3. Cursor Plane (Апаратний курсор миші 64×64 в ARGB8888):
- `SRC_W = 64`, `SRC_H = 64`, `Bpp = 4` байти, `Refresh_Rate = 120` Гц.

```
BW_Cursor
= 64 · 64 · 4 · 120
= 4096 · 480                     [площа кадру · байт/кадр]
= 1966080 Б/с                    [≈ 0.002 ГБ/с]
```

#### Сумарна швидкість читання з пам'яті:

```
Bandwidth_Total
= BW_Primary + BW_Overlay + BW_Cursor
= 3981312000 + 373248000 + 1966080 [додавання потоків трьох площин]
= 4356526080 Б/с                   [≈ 4.357 ГБ/с]
```

Таким чином, лише для забезпечення сканування кадру на монітор дисплейний контролер GPU повинен безперервно зчитувати з шини пам'яті близько `4.357 ГБ/с` чистого трафіку.

## 4. Алгоритм валідації в драйвері ядра (`atomic_check`)

Під час виконання виклику `drmModeAtomicCommit` з прапорцем `DRM_MODE_ATOMIC_TEST_ONLY` драйвер ядра (наприклад, `amdgpu` або `i915`) виконує розрахунок доступного ресурсу пам'яті.

Доступна смуга читання пам'яті `BW_Available` обчислюється з урахуванням пікової пропускної здатності шини `Max_Memory_BW` та коефіцієнта ефективності арбітражу `k_eff` (який зазвичай становить `0.70`–`0.85` через затримки регенерації DRAM та перемикання банків):

```
BW_Available = Max_Memory_BW · k_eff
```

Умова успішного проходження перевірки транзакції:

```
Bandwidth_Total ≤ BW_Available
```

Якщо зазначена умова порушується (`Bandwidth_Total > BW_Available`), або якщо наповнення внутрішніх апаратних буферів FIFO дисплейного контролера (Watermarks) стає неможливим через затримку системної пам'яті, функція `atomic_check` повертає помилку `-EBUSY`.

Отримавши `-EBUSY`, композитор простору користувача знає, що апаратне забезпечення не здатне вивести обрану комбінацію площин. Композитор оптимізує запит: вимикає оверлейну площину, об'єднує відео з робочим столом за допомогою 3D-прискорювача у єдиний буфер і повторює атомарний коміт для однієї Primary-площини.

Простежити стан валідації та причини відмови в драйверах ядра можна через відлагоджувальну файлову систему tracefs за допомогою подій `ftrace`:

```bash
# Ввімкнення трасування атомарних комітів DRM
echo 1 > /sys/kernel/tracing/events/drm/drm_atomic_commit/enable
cat /sys/kernel/tracing/trace_pipe
```
