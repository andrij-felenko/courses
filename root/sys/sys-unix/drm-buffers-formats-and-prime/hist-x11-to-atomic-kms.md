# 📜 Від UMS у X11 до Atomic KMS: еволюція управління дисплеєм у Linux

У 1990-х та на початку 2000-х років підсистема графіки в операційних системах Linux функціонувала за схемою UMS (User Mode Setting — встановлення відеорежимів у просторі користувача). Графічний сервер XFree86 (а пізніше X.Org Server) працював як монолітний суперпроцес із привілеями суперкористувача (`root`). Сервер X11 самостійно відкривав фізичні адреси пам'яті через виклик `mmap()` над пристроєм `/dev/mem`, напряму записував у регістри розширень PCI BAR0/BAR1 та безпосередньо програмував внутрішні генератори частот (PLL) відеокарти через портони вводу-виводу x86 (`inb`/`outb`).

Ядро Linux у цій системі виступало лише як пасивний посередник, який віддавав простору користувача прямий доступ до апаратних портів вводу-виводу та базового сирого фреймбуфера (`vesafb` або `vga16fb`).

Такий підхід спричиняв деструктивні наслідки для стабільності та безпеки всієї системи:

1. **Руйнування текстових консолей при збоях:** Якщо X-сервер аварійно завершував роботу (наприклад, через помилку в драйвері графічного прискорювача), відеокарта залишалася в невідомому проміжному стані. Регістри CRTC не відновлювалися, текстова консоль ядра перетворювалася на «чорний екран» або сміття з кольорових пікселів, а єдиним способом повернути контроль над машиною залишалося сліпе введення команд відключення або жорстке перезавантаження кнопкою Reset.
2. **Перегони при перемиканні віртуальних терміналів (VT Switch):** При натисканні комбінації клавіш `Ctrl+Alt+F1` для переходу з графічного оточення у текстову консоль X-сервер мусив призупинити малювання, зберегти сотні регістрів GPU та передати контроль ядерному драйверу консолі. Цей процес супроводжувався мерехтінням екрана тривалістю в кілька секунд, а найменший збій синхронізації між X-сервером та ядром призводив до повного зависання графічної шини PCI/AGP.
3. **Монополізація прискорювача та безпекові ризики:** Робота X-сервера з правами `root` створювала велетенську поверхню атак. Будь-яка вразливість у драйвері X11 дозволяла звичайній програмі отримати повне управління над оперативною пам'яттю та процесором комп'ютера.

```
+-------------------------------------------------------------------+
|                        СХЕМА UMS (до 2008)                        |
|                                                                   |
|  [ X.Org Server (root) ] --(direct PCI /dev/mem)--> [ GPU Regs ] |
|            |                                             |        |
|     (Mode Setting)                                  (Video Out)   |
|            v                                             v        |
|  [ Linux Kernel (vesafb) ] --(конфлікт за регістри)--> [ Screen ] |
+-------------------------------------------------------------------+
```

Для покращення 3D-продуктивності у 1999 році компанія Precision Insight (Дженс Оуен, Кевін Мартін, Браян Пол) створила архітектуру DRI (Direct Rendering Infrastructure). DRI1 дозволила 3D-застосункам OpenGL малювати напряму у відеопам'ять, минаючи протокол X11, а в ядрі з'явився модуль DRM (Direct Rendering Manager). Проте перші версії DRM відповідали виключно за арбітраж контекстів 3D-команд між застосунками та GPU, а керування моніторами, роздільною здатністю та виходами залишалося за монолітним X-сервером.

## Поява Kernel Mode Setting (KMS) у Linux 2.6.29

У 2008 році розробники ядерного графічного стеку — Дейв Ерлі (Dave Airlie), Якоб Борнекранц (Jakob Bornecrantz), Крістіан Хьогсберг (Kristian Høgsberg) та Джессі Барнес (Jesse Barnes) — запропонували фундаментальну реформацію: перенесення ініціалізації та конфігурації відеорежимів усередину ядра Linux. Технологія отримала назву **Kernel Mode Setting (KMS)** і була офіційно включена до ядра Linux версії 2.6.29.

З появою KMS ядро Linux повністю вилучило у простору користувача право прямого запису в регістри відеокарти. Драйвер ядра (`i915`, `radeon`, `nouveau`) став єдиним господарем апаратного забезпечення. 

Це забезпечило три ключові переваги:

- **Плавне завантаження без мерехтіння:** Проєкт Plymouth отримав можливість малювати графічний індикатор завантаження відразу після старта ядра без жодного перемикання режимів.
- **Безпека та ізоляція:** X-сервер втратив потребу працювати від імені `root` і був переведений у статус звичайного некористувача без привілеїв.
- **Надійність текстових консолей:** У разі падіння графічного сервера ядро миттєво повертало контроль над консоллю, відображаючи дамп помилки (kernel panic) безпосередньо на моніторі.

```
+-------------------------------------------------------------------+
|                        СХЕМА KMS (з 2008)                         |
|                                                                   |
|  [ Wayland / Xorg (user) ] --(DRM ioctl)--> [ Linux DRM/KMS ]     |
|                                                    |              |
|                                              (exclusive)          |
|                                                    v              |
|                                             [ GPU Hardware ]      |
+-------------------------------------------------------------------+
```

## Обмеження Legacy KMS та шлях до Atomic KMS

Початковий API KMS (який сьогодні називають Legacy KMS) успадкував імперативний характер. Для зміни конфігурації дисплея простір користувача виконував серію окремих викликів `ioctl`:

- `DRM_IOCTL_MODE_SETCRTC` — встановити роздільну здатність та буфер для CRTC;
- `DRM_IOCTL_MODE_SETPLANE` — змінити положення або буфер оверлейної площини;
- `DRM_IOCTL_MODE_CURSOR` — пересунути курсор миші;
- `DRM_IOCTL_MODE_PAGE_FLIP` — запланувати перемикання буферів на кадровому імпульсі VBlank.

Імперативний Legacy KMS API викликав дві критичні проблеми при розробці сучасних графічних композиторів (Wayland та X11):

First, **відсутність атомарності кадру**. Якщо композитор оновлював основний буфер робочого столу через `PAGE_FLIP`, а курсор миші пересував через `SETCURSOR`, ядро виконувало ці операції незалежно. Якщо виклик курсора відпрацьовував до кадрового розгортання, а перемикання буфера — після, на екрані виникав візуальний розрив (tearing): курсор зміщувався на новий кадр, тоді як зображення під ним залишалося зі старого кадру.

Second, **неможливість попередньої перевірки конфігурації (Check-and-Commit)**. Дисплейні контролери сучасних GPU мають жорсткі апаратні обмеження. Наприклад, GPU може підтримувати масштабування відео лише на одній оверлейній площині, або обмежувати максимальну ширину буфера при включенні другого монітора через пропускну здатність шини пам'яті. У Legacy KMS композитор дізнавався про те, що апаратне забезпечення не здатне відобразити обрану комбінацію площин, лише під час виконання `SETCRTC` або `SETPLANE`. Виклик повертав помилку `EINVAL`, але екран уже міг вимкнутися або перейти в неробочий стан. Композитори були змушені писати евристичні хаки під кожне сімейство відеокарт, щоб угадати, чи спрацює виклик.

## Народження Atomic KMS (Linux 4.2)

Для подолання цих обмежень Даніель Веттер (Daniel Vetter) з Intel, Густаво Падован (Gustavo Padovan) з Collabora, Пекка Пааланен (Pekka Paalanen) та Маартен Ланкхорст (Maarten Lankhorst) розробили підсистему **Atomic KMS**, яка увійшла до ядра Linux 4.2 у 2015 році.

Atomic KMS перевів підсистему дисплея з імперативної моделі викликів на транзакційну модель об'єктно-орієнтованих властивостей. Усі елементи конвеєра (Plane, CRTC, Connector) були представлені як об'єкти з набором числових властивостей (Properties). Замість виклику десятків окремих `ioctl` простір користувача формує один атомарний запит, додає туди всі зміни й відправляє його ядру через єдиний виклик `DRM_IOCTL_MODE_ATOMIC`.

Ядро гарантує двофазне виконання атомарної транзакції:

1. **Фаза валідації (`DRM_MODE_ATOMIC_TEST_ONLY`):** Драйвер ядра перевіряє всю запропоновану конфігурацію в режимі «сухого прогону» (dry-run). Перевіряються клоки PLL, смуга пропускання шини пам'яті, обмеження сканування площин та колірні конвертери. Якщо комбінація непідтримувана, ядро повертає помилку негайно, не торкаючись жодного апаратного регістра. Композитор отримує можливість прозоро повернутися до програмного змішування (software composition fallback).
2. **Фаза атомарної фіксації (Atomic Commit):** Якщо конфігурація валідна, той самий запит передається без прапорця `TEST_ONLY`. Ядро Linux записує всі регістри GPU в межах одного вікна кадрового гасіння VBlank. Перемикання всіх площин, курсора та відеорежимів відбувається синхронно й без жодного розриву зображення.

Завдяки переходу від UMS до Atomic KMS графічний стек Linux отримав монолітний, безпечний та транзакційний фундамент, необхідний для роботи сучасних композиторів Wayland, ігор із високою частотою оновлення та систем мультимедіа з високим динамічним діапазоном (HDR).
