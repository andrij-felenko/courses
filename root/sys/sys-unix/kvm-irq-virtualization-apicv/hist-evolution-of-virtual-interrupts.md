# 📜 Еволюція віртуалізації переривань: від штормів TPR до кремнієвих конвеєрів

Доставка апаратних переривань у гостьову операційну систему тривалий час залишалася найбільш витратною операцією у віртуалізації архітектури x86. Якщо обчислювальні інструкції процесор виконував безпосередньо у режимі прямого виконання (Direct Execution), а сторінкова трансляція пам'яті отримала апаратні дворівневі таблиці (Intel EPT та AMD NPT), то обробка сигналів введення-виведення вимагала постійного перемикання контексту між гостем і гіпервізором.

Щоб зрозуміти, чому доставка одного мережевого пакета чи дискового блоку здатна була зупинити роботу багатоядерного сервера, необхідно простежити еволюцію контролерів переривань від класичного IBM PC до сучасних багатосокетних систем.

---

## 1. Каскад 8259A PIC та народження APIC

В оригінальному комп'ютері IBM PC/AT керування апаратними перериваннями покладалося на два каскадно з'єднаних чипи Intel 8259A PIC (Programmable Interrupt Controller). Контролер підтримував лише 15 незалежних ліній переривань (IRQ 0–15), використовував фіксовану пріоритетність ліній та вимагав побайтового введення-виведення через повільні I/O-порти `0x20`/`0x21` (Master PIC) і `0xA0`/`0xA1` (Slave PIC).

З появою багатопроцесорних систем (SMP) архітектура 8259A виявилася абсолютно непридатною: вона не вміла розподіляти навантаження між різними процесорними ядрами і не підтримувала передачу міжпроцесорних повідомлень (IPI, Inter-Processor Interrupts).

```
   [Периферійні пристрої] ─── Лінії INTx / MSI ───> [I/O APIC]
                                                         │
                                               Шина APIC / Системна шина
                                                         │
                     ┌───────────────────────────────────┴───────────────────────────────────┐
                     ▼                                                                       ▼
           [Local APIC (vCPU 0)]                                                   [Local APIC (vCPU 1)]
         ┌───────────────────────┐                                               ┌───────────────────────┐
         │ TPR, PPR, EOI, ICR    │                                               │ TPR, PPR, EOI, ICR    │
         │ IRR, ISR, TMR, LVT    │                                               │ IRR, ISR, TMR, LVT    │
         └───────────────────────┘                                               └───────────────────────┘
```

У середині 1990-х років компанія Intel представила архітектуру **APIC (Advanced Programmable Interrupt Controller)**, розділивши підсистему на два функціональні блоки:

1. **I/O APIC:** Зовнішній контролер на материнській платі (пізніше інтегрований у чипсет/південний міст), який приймає апаратні лінії від пристроїв, формує 32-бітні повідомлення та відправляє їх системною шиною.
2. **Local APIC (LAPIC):** Індивідуальний контролер, інтегрований безпосередньо в кожне процесорне ядро. Local APIC відповідає за фільтрацію переривань за пріоритетом, доставку вектору в процесорне ядро (через таблицю переривань IDT), підтвердження завершення обробки (EOI, End of Interrupt) та генерацію міжпроцесорних переривань через регістр команд ICR (Interrupt Command Register).

Взаємодія операційної системи з Local APIC здійснювалася через область пам'яті MMIO (Memory-Mapped I/O), розташовану за замовчуванням за фізичною адресою `0xFEE00000`.

## 2. Програмна емуляція та катастрофа «шторму TPR»

Коли наприкінці 1990-х та на початку 2000-х років з'явилися перші програмні гіпервізори (VMware Workstation/ESX, пізніше Xen і KVM), єдиним способом забезпечити роботу гостьової ОС була повна програмна емуляція Local APIC та I/O APIC.

Гіпервізор виділяв у пам'яті структуру даних, яка відтворювала внутрішній стан регістрів APIC, а сторінку за адресою `0xFEE00000` позначав як недоступну (невідображену або доступну лише для читання) у таблицях тіньових сторінок (Shadow Page Tables) або пізніше в EPT.

Щойно гостьове ядро намагалося прочитати або записати регістр APIC:
1. Апаратне забезпечення генерувало сторінкову помилку або перехоплення (Page Fault / VM-Exit).
2. Процесор зупиняв виконання гостя, зберігав гостьові регістри та передавав керування коду гіпервізора.
3. Гіпервізор розбирав інструкцію гостя (дизасемблював машинний код `mov`), визначав цільовий регістр APIC, змінював емульований стан у пам'яті.
4. Гіпервізор відновлював контекст vCPU та повертався в гостьовий режим (VM-Entry).

### Анатомія проблеми TPR

Особливо катастрофічною ця схема виявилася для сімейства операційних систем Windows NT (Windows 2000, XP, Server 2003, Windows 7).

Архітектура ядра Windows активно використовує рівні запитів переривань (**IRQL**, Interrupt Request Level) для синхронізації критичних секцій. Щоразу, коли потік у ядрі Windows захоплює або відпускає звичайний спінлок (`KSPIN_LOCK`), ядро підвищує поточний рівень IRQL до `DISPATCH_LEVEL` (2), щоб запобігти витісненню потоку іншими завданнями на цьому ж ядрі.

В архітектурі x86 рівень IRQL безпосередньо відображається на регістр **TPR (Task Priority Register)** локального APIC. У 32-розрядному режимі Windows записувала значення в пам'ять за адресою `0xFEE00080` (MMIO TPR). У 64-розрядному режимі x86_64 інженери AMD та Intel додали регістр керування `CR8`, що транслюється в TPR.

```
Частота операцій захоплення спінлоків у навантаженому ядрі:
100 000 – 500 000 операцій на секунду на ОДНЕ ядро.

При кожній операції:
Захоплення спінлока:  mov cr8, 2   ──>   VM-Exit (1500 нс)
Критична секція:     mov [data], 1 ──>   Пряме виконання (1 нс)
Звільнення спінлока:  mov cr8, 0   ──>   VM-Exit (1500 нс)

Підсумок: до 80% процесорного часу марнувалося на перемикання контексту гіпервізора!
```

Це явище отримало назву **TPR Storm (Шторм регістру пріоритету завдань)**. Віртуальні машини з багатоядерною конфігурацією під керуванням Windows працювали у віртуалізованому середовищі у 3–5 разів повільніше, ніж на голому залізі, навіть якщо виконували суто обчислювальні завдання без реального введення-виведення.

Аналогічна проблема існувала і з підтвердженням переривань: після виконання кожного обробника переривання (ISR) гостьовий Linux або Windows виконує запис значення `0` в регістр `EOI` (`0xFEE000B0`), що також викликало безумовний VM-Exit.

## 3. Паравіртуальні та програмні спроби порятунку

До появи повноцінної апаратної підтримки розробники гіпервізорів та операційних систем створили цілу низку обхідних технологій:

1. **Динамічна бінарна трансляція (VMware Binary Translation):** Гіпервізор на льоту сканував гостьовий машинний код ядра Windows. Усі інструкції запису в TPR/CR8 замінювалися на прямі записи у виділену комірку звичайної віртуальної пам'яті (тіньовий TPR), уникаючи апаратних пасток.
2. **Паравіртуалізований EOI (KVM PV-EOI):** Ядро Linux KVM та гостьовий драйвер домовлялися про спільну область пам'яті (1 біт на vCPU). Гостьовий обробник перевіряв біт: якщо нових переривань у черзі не було, гость скидав біт без звернення до MMIO APIC, усуваючи вихід у гіпервізор на виході з ISR.
3. **Microsoft Hyper-V Enlightened APIC:** Спеціальні гіпервиклики (Hypercalls) та синтетичні контролери переривань (SynIC), які змушували гостьову Windows відмовитися від прямого використання Local APIC на користь оптимізованих паравіртуальних інтерфейсів.

Хоча ці заходи полегшили ситуацію для модифікованих гостьових ОС, вони не вирішували проблему фундаментально: гостьова ОС вимагала спеціальних драйверів, а немодифіковані операційні системи чи застарілі інсталятори продовжували страждати від катастрофічних затримок.

## 4. Кремнієва революція: Intel APICv та AMD AVIC

Фундаментальний злам стався тоді, коли логіку роботи з регістрами переривань перенесли безпосередньо у кремній центрального процесора.

| Рік | Платформа | Технологія | Головне досягнення |
| :--- | :--- | :--- | :--- |
| **2008** | Intel Nehalem | **TPR Shadowing** | Апаратний тіньовий регістр TPR у керуючій структурі VMCS; усунення VM-Exit при зміні `CR8`. |
| **2012** | Intel Ivy Bridge | **APIC-v (Virtual APIC)** | Сторінка APIC-access, апаратна віртуалізація регістрів vEOI/vISR/vIRR, доставка віртуальних переривань без виходу в гіпервізор. |
| **2013** | Intel Haswell | **Posted Interrupts (IPI)** | Апаратна передача міжпроцесорних переривань між vCPU через дескриптор PIR без VM-Exit. |
| **2015** | Intel Broadwell / Skylake | **VT-d Posted Interrupts** | Пряма доставка апаратних переривань від фізичних пристроїв PCIe (SR-IOV / VFIO) через IOMMU без участі хоста. |
| **2016** | AMD Zen (Carrizo/Naples) | **AMD AVIC / x2AVIC** | Апаратна таблиця фізичних та логічних APIC ID, доставка IPI між vCPU на кремнієвому рівні. |

Завдяки впровадженню APICv та Posted Interrupts вартість доставки переривання скоротилася з кількох мікросекунд (2500–5000 нс) до кількох десятків наносекунд — практично зрівнявшись із продуктивністю фізичного обладнання.
