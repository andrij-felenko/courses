</preknowlist>

Коли розробник підключається до віддаленого сервера через протокол SSH, запускає тривалу компіляцію великого проекту чи міграцію бази даних, а за пів години закриває кришку ноутбука, розрив мережевого з'єднання миттєво знищує всі запущені процеси. З точки зору користувача сталася прикра втрата обчислювального прогресу; з точки зору ядра Linux відбулася штатна каскадна процедура очищення ресурсів сеансу. Операційна система зафіксувала закриття термінального каналу, згенерувала сигнал розриву зв'язку `SIGHUP` (Signal Hangup) і доставила його всім процесам, прив'язаним до закритого термінала.

Розуміння того, як ядро обробляє втрату термінала і які інструменти існують для захисту процесів — утиліта `nohup`, вбудована команда оболонки `disown`, системний виклик створення сеансу `setsid` та від'єднання файлових дескрипторів — дозволяє створювати автономні фонові служби та безпечно керувати життєвим циклом обчислень у середовищі Unix.

## 1. Анатомія розриву сесії: від закриття PTY Master до реакції ядра

Щоб зрозуміти причину раптової загибелі фонових програм, необхідно простежити повний ланцюжок подій усередині підсистеми терміналів ядра Linux при від'єднанні клієнта.

### Крок 1: Знищення керівного кінця псевдотермінала

Усі сучасні віддалені сесії (через `sshd`) та графічні віконні термінали (GNOME Terminal, Alacritty, Kitty) працюють через абстракцію **псевдотермінала (PTY)**. Ця абстракція складається з двох взаємопов'язаних пристроїв:
- **Master (керівний бік)**: файловий дескриптор, відкритий процесом сервера `sshd` або віконного емулятора через спеціальний системний вузол `/dev/ptmx`;
- **Slave (підлеглий бік)**: віртуальний пристрій `/dev/pts/N`, що виступає керівним терміналом для командної оболонки `bash` та всіх її дочірніх процесів.

Коли мережеве TCP-з'єднання обривається або користувач закриває вікно термінала, процес-емулятор виходить або закриває файловий дескриптор master-боку:

```text
close(master_fd);
```

### Крок 2: Драйвер PTY та функція ядра `tty_vhangup`

Усередині ядра Linux драйвер псевдотерміналів `drivers/tty/pty.c` реєструє зменшення лічильника посилань на файловий дескриптор master-боку до нуля. Викликається функція `pty_close()`, яка запускає ядерну процедуру примусового відключення термінальної лінії — `tty_vhangup()` (або `tty_hangup()`):

```text
/* Логіка ядра у drivers/tty/tty_io.c */
void tty_vhangup(struct tty_struct *tty) {
    /* 1. Позначити лінію як розірвану */
    set_bit(TTY_HUPPED, &tty->flags);

    /* 2. Надіслати SIGHUP лідеру сесії */
    if (tty->session) {
        kill_pgrp(tty->session, SIGHUP, 1);
        kill_pgrp(tty->session, SIGCONT, 1);
    }

    /* 3. Очистити буфери дисципліни лінії n_tty */
    tty_ldisc_hangup(tty);
}
```

Драйвер ядра виставляє на структурі `struct tty_struct` прапорець `TTY_HUPPED`. З цього моменту підлеглий бік термінала `/dev/pts/N` переходить у стан мертвого каналу:
- Будь-який подальший системний виклик `read()` з дескриптора цього термінала негайно повертає `0` (що сигналізує про кінець файлу, EOF) або помилку `EIO` (Input/output error);
- Будь-який системний виклик `write()` у цей дескриптор завершується з помилкою `EIO`.

### Крок 3: Доставка сигналу `SIGHUP` лідеру сесії

Ядро знаходить сеанс, прив'язаний до цього термінала (`tty->session`), та його лідера — **Session Leader** (процес оболонки `bash`, чий `PID` дорівнює `SID` сеансу). Ядро надсилає цьому процесу сигнал `SIGHUP` (Signal 1).

![Каскад розриву сесії в ядрі Linux](/root/sys/sys-unix/hangup-and-survival/img/terminal-hangup-chain.svg)
*Каскад подій при закритті термінала: драйвер ядра фіксує закриття Master PTY, маркує лінію станом TTY_HUPPED, надсилає SIGHUP лідеру сесії, який транслює сигнал підлеглим групам процесів.*

### Крок 4: Розповсюдження сигналу командною оболонкою

Отримавши `SIGHUP` або виявивши `EOF` на стандартному вводі, інтерактивна оболонка ініціює процедуру власного завершення. За канонічним стандартом POSIX оболонка повинна сповістити всі процеси, якими вона керує.

Оболонка перебирає свою внутрішню таблицю завдань (**Jobs Table**) і надсилає сигнал `SIGHUP` кожній активній групі процесів:

```text
/* Логіка обходу завдань у Bash при завершенні */
for (i = 0; i < js.j_njobs; i++) {
    if (jobs[i] && (jobs[i]->flags & J_NOHUP) == 0) {
        killpg(jobs[i]->pgrp, SIGHUP);
    }
}
```

У результаті сигнал розриву отримують не лише програми переднього плану (foreground), а й процеси, запущені у фоні через амперсанд (`./script.sh &`). Оскільки типова дія за замовчуванням (`SIG_DFL`) для сигналу `SIGHUP` — це негайне припинення виконання (`terminate`), усі процеси сесії гинуть.

### Крок 5: Захист від зависання зупинених процесів (Orphaned Process Groups)

Окремим тонким крайовим випадком є процеси, призупинені комбінацією `Ctrl+Z` (стан `TASK_STOPPED` від сигналу `SIGTSTP`). 

Якщо сесійний лідер (оболонка) завершується, група процесів стає **осиротілою (orphaned process group)**: у ній більше немає жодного процесу, чий батьківський процес перебував би у тому самому сеансі, але в іншій групі процесів. 

Якби зупинений процес залишився в пам'яті у стані `TASK_STOPPED`, він завис би назавжди, оскільки більше не існує батьківської оболонки, здатної відправити йому команду `fg` або сигнал `SIGCONT`. 

Щоб запобігти накопиченню мертвих зупинених процесів, ядро Linux перевіряє стан групи: якщо осиротіла група містить хоча б один зупинений процес, ядро надсилає усій групі процесів спочатку сигнал `SIGHUP`, а потім сигнал `SIGCONT`. Сигнал `SIGCONT` примусово пробуджує процес, щоб той міг негайно обробити доставлений `SIGHUP` і штатно завершити виконання.

## 2. Сигнал SIGHUP: історичне коріння та дуалізм семантики

Сигнал `SIGHUP` має номер `1` у системній таблиці сигналів Unix. Його назва походить від англійського *Hang Up* — покласти телефонну слухавку на важіль апарата. 

Детально історію апаратного виявлення несучої частоти модема Bell 103, контакт DCD в інтерфейсі RS-232 та перехід до псевдотерміналів описано у [історичній вставці](root:sys-unix/hangup-and-survival/hist-modem-hangup.md).

З точки зору програмної архітектури Linux сигнал `SIGHUP` має унікальну подвійну природу:

```
                            ┌───────────────────────────────────────────────┐
                            │                Сигнал SIGHUP                  │
                            └──────────────────────┬────────────────────────┘
                                                   │
                   ┌───────────────────────────────┴───────────────────────────────┐
                   ▼                                                               ▼
 ┌───────────────────────────────────┐                           ┌───────────────────────────────────┐
 │       Інтерактивні процеси        │                           │         Системні демони           │
 │       (прив'язані до TTY)         │                           │   (controlling TTY == NULL)       │
 ├───────────────────────────────────┤                           ├───────────────────────────────────┤
 │ • Джерело: драйвер ядра / Shell   │                           │ • Джерело: адміністратор / IPC    │
 │ • Диспозиція: SIG_DFL (аварія)    │                           │ • Диспозиція: користувацький обр. │
 │ • Мета: завершити роботу          │                           │ • Мета: перечитати конфігурацію   │
 └───────────────────────────────────┘                           └───────────────────────────────────┘
```

1. **Для інтерактивних термінальних утиліт**: диспозиція сигналу залишається стандартною (`SIG_DFL`). Отримання `SIGHUP` означає фізичну або логічну втрату зв'язку з користувачем і призводить до негайного завершення процесу.
2. **Для системних демонів** (Nginx, Apache, sshd, BIND, systemd): фонові демони створюються через `setsid()` і не мають керівного термінала. Вони ніколи не отримують `SIGHUP` від ядра внаслідок закриття сесій користувачів. Тому розробники серверного програмного забезпечення традиційно використовують `SIGHUP` як стандартний сигнал для **перечитування файлів конфігурації на льоту** та ротації файлів журналів без зупинки процесу і без розриву відкритих мережевих сокетів.

### Внутрішні структури ядра: диспозиції та доставка сигналів

Усередині структури `struct task_struct` ядра Linux інформація про обробку сигналів розподілена між двома ключовими структурами:
- `task->signal`: містить спільні лічильники сигналів для всієї групи потоків, зв'язок із групою процесів (`pgrp`), сеансом (`session`) та вказівник на термінал `tty`;
- `task->sighand`: таблиця дій `action[64]`, яка визначає реакцію на кожен із 64 сигналів POSIX та реального часу.

Для сигналу `SIGHUP` поле `sa_handler` у структурі `struct k_sigaction` може приймати одне з трьох значень:
1. `SIG_DFL`: ядро виконує функцію `do_group_exit()`, переводячи всі потоки процесу у стан завершення;
2. `SIG_IGN`: ядро перевіряє стан у функції `sig_ignored()` і негайно відкидає сигнал без додавання його до черги очікування (`pending signals`);
3. Адреса користувацької функції: при поверненні процесу з простору ядра в простір користувача формується сигнальний кадр на стеку (`signal frame`), і керування передається на зареєстровану функцію.

### Багатопотокові процеси та доставка SIGHUP

Якщо програма використовує кілька потоків виконання (POSIX threads), сигнал `SIGHUP`, надісланий групі процесів або через виклик `kill(pid, SIGHUP)`, є процесно-орієнтованим. Ядро обирає перший доступний потік, у якого сигнал `SIGHUP` не заблокований у масці сигналів (`sigprocmask`/`pthread_sigmask`). Якщо всі потоки заблокували `SIGHUP`, сигнал залишається у спільній черзі `signal->shared_pending` до моменту розблокування будь-яким із потоків.

## 3. Механіка захисту `nohup`: ігнорування сигналу та ізоляція дескрипторів

Утиліта `nohup` (No Hangup) є найстарішим стандартизованим способом (POSIX.1) запуску команд, стійких до закриття термінала.

### Як працює `nohup`

Коли користувач виконує команду `nohup long_job.sh &`, утиліта `nohup` виконує три операції перед тим, як передати керування цільовій програмі:

1. **Встановлення диспозиції `SIG_IGN`**:
   `nohup` викликає системний виклик зміни обробника сигналу:

:::tabs
```c
#include <signal.h>

/* Встановлення ігнорування SIGHUP мовою C */
signal(SIGHUP, SIG_IGN);
```
```cpp
#include <csignal>

// Встановлення ігнорування SIGHUP мовою C++
std::signal(SIGHUP, SIG_IGN);
```
:::

   У моделі сигналів POSIX стан ігнорування сигналу (`SIG_IGN`) має фундаментальну властивість: на відміну від вказівників на власні функції-обробники (які при виклику `execve` скидаються до `SIG_DFL`), **стан ігнорування зберігається крізь системний виклик `execve()`**. Коли `nohup` завантажує виконуваний файл `long_job.sh`, новий образ процесу продовжує повністю ігнорувати сигнал `SIGHUP`.

2. **Перенаправлення стандартного введення `stdin`**:
   Якщо дескриптор `0` веде у термінал (`isatty(0) == true`), `nohup` перевідкриває його з `/dev/null`:

:::tabs
```c
#include <unistd.h>
#include <fcntl.h>

int null_fd = open("/dev/null", O_RDONLY);
if (null_fd >= 0) {
    dup2(null_fd, STDIN_FILENO);
    close(null_fd);
}
```
```cpp
#include <unistd.h>
#include <fcntl.h>
#include <system_error>

int null_fd = ::open("/dev/null", O_RDONLY);
if (null_fd < 0) {
    throw std::system_error(errno, std::generic_category(), "open /dev/null failed");
}
::dup2(null_fd, STDIN_FILENO);
::close(null_fd);
```
:::

   Це гарантує, що фоновий процес не заблокується на спробі зчитати дані з термінала.

3. **Перенаправлення стандартного виведення `stdout` та помилок `stderr`**:
   Якщо дескриптори `1` або `2` підключені до термінала, `nohup` створює файл `nohup.out` у поточному робочому каталозі (або в `$HOME/nohup.out`, якщо поточний каталог доступний лише для читання) з правами доступу `0600` і перенаправляє потоки туди:

:::tabs
```c
#include <unistd.h>
#include <fcntl.h>
#include <sys/stat.h>

int out_fd = open("nohup.out", O_WRONLY | O_CREAT | O_APPEND, S_IRUSR | S_IWUSR);
if (out_fd >= 0) {
    dup2(out_fd, STDOUT_FILENO);
    dup2(out_fd, STDERR_FILENO);
    close(out_fd);
}
```
```cpp
#include <unistd.h>
#include <fcntl.h>
#include <sys/stat.h>
#include <system_error>

int out_fd = ::open("nohup.out", O_WRONLY | O_CREAT | O_APPEND, S_IRUSR | S_IWUSR);
if (out_fd < 0) {
    throw std::system_error(errno, std::generic_category(), "open nohup.out failed");
}
::dup2(out_fd, STDOUT_FILENO);
::dup2(out_fd, STDERR_FILENO);
::close(out_fd);
```
:::

*Пастка дескрипторів мертвого термінала: процес, який ігнорує SIGHUP, але не перенаправив дескриптори вводу-виводу, гине від помилки EIO при спробі запису у закритий PTY Slave.*

### Чому перенаправлення дескрипторів критичне

Багато початківців припускаються помилки, вважаючи, що достатньо лише заблокувати сигнал `SIGHUP`. Однак якщо процес продовжує тримати відкритими дескриптори `1` (`stdout`) та `2` (`stderr`), що вказують на пристрій `/dev/pts/N`, після закриття емулятора цей пристрій переходить у стан `TTY_HUPPED`. 

Щойно працююча програма викличе функцію `printf()` або запише черговий рядок логу у дескриптор `1`, системний виклик `write()` поверне помилку `-1` із кодом `EIO` (або процес отримає сигнал `SIGPIPE`/`SIGTTOU`). 

Більшість стандартних бібліотек інтерпретують помилку запису у стандартний вивід як критичний збій середовища виконання і негайно аварійно завершують процес. `nohup` запобігає цій катастрофі, завчасно відв'язуючи дескриптори від файлу пристрою термінала.

### Підводні камені фонового вводу-виводу: `SIGTTIN`, `SIGTTOU` та нескінченні цикли

Коли процес працює у фоновому режимі термінальної сесії без повного перенаправлення дескрипторів, виникають дві характерні проблеми арбітражу введення-виведення:

1. **Спроба фонового читання (`SIGTTIN`)**:
   Якщо фоновий процес намагається прочитати дані зі стандартного введення `stdin`, яке все ще вказує на керівний термінал, драйвер термінала генерує для всієї фонової групи процесів сигнал `SIGTTIN`. За замовчуванням дія сигналу `SIGTTIN` полягає у **зупиненні процесу** (`TASK_STOPPED`). Процес миттєво зависає і чекає переведення на передній план командою `fg`. Якщо термінал після цього закривається, зупинений процес перетворюється на осиротілий і знищується ядром. Перенаправлення `stdin` з `/dev/null` перетворює будь-яке читання на повернення `0` (EOF), що дозволяє програмам коректно обробити відсутність вхідного потоку.
2. **Нескінченний цикл на мертвому дескрипторі**:
   Якщо програма реалізована за принципом опитування введення в циклі:

:::tabs
```c
#include <stdio.h>

int c;
while ((c = getchar()) != EOF) {
    /* Обробка символу */
}
```
```cpp
#include <iostream>

char ch;
while (std::cin.get(ch)) {
    // Обробка символу
}
```
:::

   Якщо розробник помилково не перевірив значення `EOF` або припустився помилки приведення типу (`char c` замість `int c` у C), при отриманні постійного `EOF` від мертвого TTY або `/dev/null` процес увійде в нескінченний цикл, утилізуючи 100% ядра процесора.
3. **Фоновий запис та прапорець `TOSTOP` (`SIGTTOU`)**:
   Якщо у термінальних налаштуваннях `termios` увімкнено прапорець `TOSTOP`, будь-яка спроба фонового запису у термінал генерує сигнал `SIGTTOU`, який також призупиняє процес. Перенаправлення `stdout` у файл журналу повністю знімає це обмеження.

## 4. Внутрішній механізм оболонки `disown`

На відміну від зовнішньої утиліти `nohup`, яка налаштовує середовище процесу **до** його старту, команда `disown` є вбудованою функцією (builtin) оболонки Bash, Zsh або Ksh і дозволяє врятувати процес **постфактум**, коли він уже запущений у фоні.

### Таблиця завдань (Jobs Table) проти таблиці процесів ядра

Ядро операційної системи Linux нічого не знає про концепцію «завдання» (job `%1`, `%2`). Для ядра існують лише окремі процеси (`PID`), групи процесів (`PGID`) та сеанси (`SID`).

Таблиця завдань — це внутрішня структура даних у пам'яті оболонки (масив або зв'язаний список об'єктів `struct job`). Коли користувач запускає команду у фоні (`python train.py &`), оболонка додає запис у свою таблицю завдань:

```text
[Завдання %1] PID=18492, PGID=18492, Стан=Running, Команда="python train.py"
```

Коли користувач вводить команду `exit` або коли оболонка отримує `SIGHUP`, вона перебирає саме цей внутрішній масив і розсилає `SIGHUP` усім знайденим групам процесів.

### Варіанти використання команди `disown`

1. **`disown %1` (або `disown PID`)**:
   Оболонка повністю вилучає завдання з внутрішньої таблиці завдань. Завдання зникає зі списку команди `jobs`. Коли оболонка завершує роботу, вона більше не знає про існування процесу `18492` і, відповідно, **не надсилає йому сигнал `SIGHUP`**. Процес залишається працювати, переходячи під опіку батьківського процесу PID 1 (`systemd` або `init`).
2. **`disown -h %1` (прапорець `--nohangup`)**:
   Завдання залишається в таблиці завдань оболонки (його видно у виводі команди `jobs`, ним можна керувати через команди `fg` та `bg`). Проте оболонка виставляє на цьому завданні внутрішній прапорець `J_NOHUP` (`JOB_NOSIGHUP`). Під час виходу з оболонки функція розсилки сигналів перевіряє цей прапорець і пропускає вказане завдання.
3. **`disown -a`**: застосувати дію до всіх завдань у таблиці.
4. **`disown -r`**: застосувати дію лише до тих завдань, що перебувають у стані активного виконання (Running).

```bash
# Приклад порятунку вже запущеного фонового процесу:
$ ./data_sync.sh &
[1] 34910

# Робимо процес нечутливим до закриття поточної оболонки
$ disown -h %1

# Перевіряємо статус у таблиці завдань
$ jobs -l
[1]+ 34910 Running                 ./data_sync.sh &
```

### Поведінка опції `huponexit` у Bash

Поведінка командної оболонки Bash при штатному виході користувача (`exit` або закриття за `Ctrl+D`) залежить від конфігурації оболонки:
- Для login-оболонок (наприклад, початкова сесія SSH) за замовчуванням у багатьох дистрибутивах активна розсилка сигналів фоновим завданням;
- Для не-login інтерактивних оболонок опція `huponexit` за замовчуванням вимкнена (`off`). Якщо користувач завершує таку оболонку командою `exit`, фонові процеси не отримують `SIGHUP`. Проте, якщо закривається сам віконний емулятор (розрив PTY), ядро надсилає `SIGHUP` безпосередньо самій оболонці, що активує обробник `hangup_all_jobs()` і безумовно знищує всі фонові процеси.

Команда `shopt -s huponexit` або `shopt -u huponexit` дозволяє явно налаштувати цю поведінку.

### Підводний камінь `disown`: незакриті потоки виведення

Головна небезпека використання команди `disown` полягає в тому, що вона змінює лише логіку розсилки сигналів оболонкою, але **не змінює стан файлових дескрипторів процесу**.

Якщо процес було запущено просто як `./data_sync.sh &` без явного перенаправлення потоків виведення (`> sync.log 2>&1`), його дескриптори `0`, `1` та `2` залишаються спрямованими у підлеглий псевдотермінал `/dev/pts/N`. 

Після закриття вікна термінала процес успішно переживе відсутність сигналу `SIGHUP`, але впаде від помилки `EIO` у момент першого ж виклику `write()` у закритий дескриптор термінала. Тому надійне використання `disown` вимагає запуску процесу з завчасним перенаправленням стандартних потоків:

```bash
$ ./data_sync.sh > sync.log 2>&1 &
$ disown %1
```

## 5. Повна ізоляція через `setsid` та від'єднання дескрипторів

Найвищим рівнем автономності процесу в середовищі Unix є його повне виведення в новий сеанс за допомогою системного виклику `setsid(2)`.

### Системний виклик `setsid`

```text
#include <unistd.h>

pid_t setsid(void);
```

Системний виклик `setsid()` виконує такі атомарні перетворення в ядрі:
1. Створює **новий сеанс**, у якому викликаючий процес стає сесійним лідером (`SID = PID`);
2. Створює **нову групу процесів**, де процес стає лідером групи (`PGID = PID`);
3. Повністю **скидає зв'язок із будь-яким керівним терміналом** (`controlling TTY = NULL`).

Оскільки процес більше не має керівного термінала, ядро операційної системи в принципі не зможе згенерувати для нього сигнал `SIGHUP` при закритті будь-яких зовнішніх емуляторів або SSH-з'єднань.

```
Обов'язкова умова успіху: викликаючий процес НЕ повинен бути лідером своєї групи процесів (PID != PGID).
Якщо PID == PGID, системний виклик setsid() повертає -1 і виставляє errno = EPERM.
```

Для гарантованого виконання цієї умови перед викликом `setsid()` обов'язково виконують виклик `fork()`, а батьківський процес завершують.

### Внутрішні перетворення ядра: функція `disassociate_ctty`

Коли процес викликає `setsid()` або виконує від'єднання від термінала через керівний виклик `ioctl(fd, TIOCNOTTY)`, підсистема TTY ядра Linux запускає функцію `disassociate_ctty()`:

```text
/* Спрощена логіка ядра drivers/tty/tty_io.c */
void disassociate_ctty(int on_exit) {
    struct tty_struct *tty = get_current_tty();
    if (!tty) return;

    /* Звільнити сесійний зв'язок */
    write_lock_irq(&tasklist_lock);
    current->signal->tty = NULL;
    tty->session = NULL;
    tty->pgrp = NULL;
    write_unlock_irq(&tasklist_lock);

    /* Звільнити ресурси драйвера термінала */
    tty_kref_put(tty);
}
```

Ця операція розриває будь-яку можливість отримання асинхронних сигналів клавіатури (`SIGINT` від `Ctrl+C`, `SIGQUIT` від `Ctrl+\`, `SIGTSTP` від `Ctrl+Z`) та сигналів розриву зв'язку від драйвера термінала.

### Утиліта командного рядка `setsid`

Для запуску програм у новому сеансі без написання C-коду використовується стандартна системна утиліта `setsid(1)`:

```bash
$ setsid ./my_service > /var/log/service.log 2>&1 < /dev/null &
```

Опція `setsid -f` (`--fork`) змушує саму утиліти виконати системний виклик `fork()`, гарантуючи, що дочірній процес гарантовано не буде лідером поточної групи процесів.

Детальний опис усіх параметрів виклику, системних кодів помилок та взаємодії з драйвером термінала через `ioctl` наведено у [довідці системних інтерфейсів](root:sys-unix/hangup-and-survival/api-survival-prctl-and-signals.md).

Повний практичний приклад створення системного демона з подвійним розгалуженням (double fork), безпечним скиданням маски `umask` та перенаправленням дескрипторів мовами C та C++ розібрано у [практичному проекті](root:sys-unix/hangup-and-survival/proj-session-daemonizer.md).

## 6. Простеження подій через Ftrace та системні журнали

Для глибокого діагностування та верифікації поведінки ядра при розриві сеансу можна скористатися підсистемою динамічного трасування **ftrace** або утилітою `perf`.

### Спостереження за генерацією сигналів у ядрі

Увімкнувши трасування точок подій `signal_generate` та `signal_deliver` у системній псевдофайловій системі `/sys/kernel/tracing/`, ми можемо побачити точну послідовність доставки `SIGHUP`:

```bash
# Увімкнення трасування сигналів
$ echo 1 > /sys/kernel/tracing/events/signal/signal_generate/enable
$ echo 1 > /sys/kernel/tracing/events/signal/signal_deliver/enable
$ cat /sys/kernel/tracing/trace_pipe
```

У момент закриття термінального вікна у журналі трасування з'являються записи:

```text
sshd-14202 [002] .... 12845.102914: signal_generate: sig=1 errno=0 code=1 comm=bash pid=14205 grp=1 res=0
bash-14205 [003] d... 12845.103002: signal_deliver:  sig=1 errno=0 code=1 sa_handler=55d28a011040
bash-14205 [003] .... 12845.103115: signal_generate: sig=1 errno=0 code=0 comm=worker pid=14290 grp=1 res=0
worker-14290 [001] d... 12845.103140: signal_deliver:  sig=1 errno=0 code=0 sa_handler=0
```

Цей журнал чітко демонструє дві фази:
1. Рядок `12845.102914`: ядро надсилає `sig=1` (`SIGHUP`) процесу `bash` (PID 14205, лідер сесії);
2. Рядок `12845.103115`: процес `bash` транслює `sig=1` фоновому процесу `worker` (PID 14290);
3. Рядок `12845.103140`: оскільки процес `worker` мав стандартну дію `sa_handler=0` (`SIG_DFL`), ядро завершує його роботу.

Якщо процес був запущений через `nohup`, запис `signal_generate` все одно генерується, але `signal_deliver` не з'являється, оскільки ядро відкидає сигнал на етапі перевірки `sig_ignored()`.

## 7. Порівняння рівнів ізоляції та інженерний вибір

Вибір методу збереження процесу залежить від того, на якому етапі життєвого циклу перебуває програма і яка глибина автономності від неї вимагається.

![Порівняння рівнів ізоляції процесів](/root/sys/sys-unix/hangup-and-survival/img/survival-mechanisms-comparison.svg)
*Порівняння рівнів ізоляції: звичайний процес гине разом із сесією; nohup та disown рятують процес у межах старої сесії; setsid забезпечує повну ізоляцію ядра.*

Нижче наведено зведену матрицю поведінки та характеристик кожного інструменту:

| Критерій | Звичайний запуск (`cmd &`) | `nohup cmd &` | `cmd & disown -h` | `setsid cmd` / Демон | Термінальний мультиплексор (`tmux`) |
|---|---|---|---|---|---|
| **Сеанс (SID)** | Сеанс оболонки | Сеанс оболонки | Сеанс оболонки | **Новий незалежний сеанс** | Сеанс сервера tmux |
| **Керівний TTY** | Прив'язаний `/dev/pts/N` | Прив'язаний `/dev/pts/N` | Прив'язаний `/dev/pts/N` | **Відсутній (`NULL`)** | Віртуальний TTY всередині tmux |
| **Диспозиція SIGHUP** | `SIG_DFL` (загибель) | `SIG_IGN` (ігнорування) | Не змінюється | Не змінюється (сигнал не приходить) | Не надсилається при від'єднанні |
| **Стандартні дескриптори** | Ведуть у TTY (ризик `EIO`) | Перенаправлені в `nohup.out` | Залишаються у TTY (потрібне `> file`) | Перенаправляються у `/dev/null` | Залишаються у віртуальному вікні |
| **Коли застосовувати** | Короткі задачі під наглядом | Швидкий запуск тривалої задачі | Порятунок уже запущеного процесу | Системні служби та фонові демони | Інтерактивні тривалі задачі з консоллю |

## 8. Сучасні альтернативи: Systemd Scope та термінальні мультиплексори

У сучасному інженерному середовищі Linux пряме використання `nohup` та ручна демонізація дедалі частіше замінюються декларативними системними механізмами:

### 1. Тимчасові служби та області `systemd-run`

Замість запуску через `nohup` користувач може передати керування процесом безпосередньо системному менеджеру `systemd`:

```bash
$ systemd-run --user --scope python3 train_model.py
Running scope as unit: run-r8491029194819.scope
```

Переваги такого підходу:
- Процес негайно переміщується в окрему контрольну групу (cgroup);
- Журнали автоматично збираються підсистемою `systemd-journald` (`journalctl --user -u run-r8491029194819.scope`);
- Повне від'єднання від термінальної сесії без ризику втрати дескрипторів.

### 2. Термінальні мультиплексори (`tmux` та `screen`)

Для завдань, які вимагають періодичного перегляду інтерактивного виводу, введення паролів або роботи з консольними дашбордами, найкращим рішенням є **термінальний мультиплексор**:
- Демон-сервер `tmux` створює власний постійний сеанс ядра без прив'язки до зовнішнього SSH;
- Кожне вікно всередині `tmux` є повноцінним віртуальним псевдотерміналом;
- При розриві SSH-з'єднання клієнтська частина `tmux` завершується, але серверний процес продовжує виконувати всі програми всередині віртуальних терміналів;
- Після відновлення зв'язку команда `tmux attach` миттєво повертає користувача до робочого стану екрана.

### 3. Особливості OCI-контейнерів та PID 1

У середовищі контейнеризації (Docker, Podman, Kubernetes) процес з ідентифікатором `PID 1` володіє особливою сигнальною семантикою: ядро Linux блокує доставку будь-яких сигналів, для яких у процесі `PID 1` не зареєстровано явний обробник. Якщо скрипт-обгортка контейнера завершується без належного перенаправлення сигналів, дочірні процеси можуть або зависнути, або миттєво отримати `SIGKILL` від середовища виконання контейнерів. Використання спеціалізованих ініціалізаційних утиліт (наприклад, `tini` або `dumb-init`) відновлює коректне каскадне розповсюдження сигналів `SIGHUP` та `SIGTERM` усередині простору імен процесів контейнера.

> 🔧 **Навіщо це.**
> У реальній практиці системного адміністрування та бекенд-розробки:
> 1. Якщо ви **вже запустили** довгий скрипт у консолі, забувши про `nohup`, і вам потрібно терміново відключитися від сервера — натисніть `Ctrl+Z` (призупинити), переведіть у фон командою `bg`, виконайте `disown -h %1` і спокійно закривайте сесію;
> 2. Якщо ви запускаєте фоновий скрипт через скрипти автоматизації або cron — використовуйте `nohup command > log.txt 2>&1 &` або `setsid`;
> 3. Якщо ви створюєте системну службу або сервіс мовами C/C++ чи Go — забезпечуйте повну ізоляцію через системний виклик `setsid` та перенаправлення дескрипторів;
> 4. Для інтерактивної роботи (налагодження, перегляд логів у реальному часі, робота у віконних редакторах) найкращим стандартом є термінальні мультиплексори (`tmux` або `screen`), які підтримують постійну активну сесію на сервері незалежно від стану мережі клієнта.
