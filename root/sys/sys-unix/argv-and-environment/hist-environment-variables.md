# 📜 Історія виникнення змінних середовища та допоміжного вектора

Передача операційного контексту між процесами в операційних системах сімейства Unix пройшла еволюцію від жорстко обмежених аргументів командного рядка перших версій 1970-х років до появи універсального масиву змінних середовища у Version 7 Unix та подальшої розробки допоміжного вектора в System V Release 4 для підтримки динамічного зв'язування ELF. Кожен із цих етапів виникав як відповідь на технічні обмеження попереднього механізму завантаження та виконання програм.

## 1. Перші роки Unix: Проблема жорсткого контексту (1971–1978)

У ранніх версіях операційної системи Unix (від First Edition 1971 року до Sixth Edition / V6 1975 року), розроблених Кентом Томпсоном (Ken Thompson) та Деннісом Рітчі (Dennis Ritchie) в лабораторіях Bell Labs на 16-бітних комп'ютерах PDP-11, передача параметрів між програмами була надзвичайно мінімалістичною. Системний виклик `exec()` приймав лише шлях до виконуваного файлу та масив покажчиків на аргументи `argv`.

Кожен системний інструмент дотримувався філософії Unix: виконувати одну задачу добре й приймати параметри виключно через позиційні аргументи командного рядка. Проте у міру зростання складності системи та виникнення багатокористувацьких середовищ з'явилася гостра проблема: як передати програмам загальносистемні налаштування (наприклад, тип поточного термінала, домашній каталог користувача чи шляхи пошуку системних утиліт) без примусового додавання цих параметрів до кожного виклику кожної утиліти?

У Unix V6 розробники намагалися вирішувати це питання трьома незручними способами:
1. Запис налаштувань у тимчасові файли у каталозі `/tmp`. Це створювало величезні накладні витрати на дисковий ввід-вивід (який у 1970-х роках здійснювався на повільних магнітних барабанах та дисках).
2. Зашивання конфігураційних шляхів безпосередньо у сирцевий код C. Це вимагало перезбірки системних утиліт при найменшій зміні конфігурації.
3. Використання спеціальних глобальних файлів налаштувань для кожної утиліти окремо, що засмічувало файлову систему.

Командна оболонка не мала жодного стандартного механізму для того, щоб прозоро передати свій поточний стан або операційний контекст дитячим процесам, які вона запускала.

## 2. Прорив у Version 7 Unix: Створення масиву environ (1979)

Під час підготовки шоломної версії 7th Edition Unix (V7), випущеної у 1979 році, Стівен Борн (Stephen R. Bourne, автор класичної оболонки `sh`) та Денніс Рітчі запропонували революційне вирішення: створення глобального масиву змінних середовища у форматі `KEY=VALUE`, який автоматично копіюється ядром при виконанні системного виклику `execve()`.

Це нововведення миттєво розв'язало кілька ключових архітектурних проблем системного програмування:
- **Ізоляція інтерфейсу користувача**: Програмам більше не потрібно було розбирати десятки прапорців командного рядка для базових системних налаштувань. Змінні `PATH`, `HOME`, `TERM`, `SHELL` та `USER` стали глобальним контекстом виконання.
- **Прозорість успадкування**: Коли оболонка викликала `fork()`, дитячий процес отримував точну копію середовища. Зміни, внесені в середовище перед `execve()`, передавалися новій програмі без зміни її двійкового коду чи сирців.
- **Гнучкість локалізації та кастомізації**: Будь-який користувач міг перевизначити `PATH` або `TERM` у своєму сеансі, не впливаючи на інших користувачів системи.

Змінні середовища стали одним із найуспішніших архітектурних рішень у дизайні Unix. Вони увійшли до стандарту POSIX.1 та використовуються в усіх сучасних операційних системах — від Linux та macOS до Microsoft Windows.

## 3. Епоха ELF та System V Release 4: Допоміжний вектор auxv (1989)

Наприкінці 1980-х років операційні системи Unix здійснювали перехід від старого формату виконуваних файлів `a.out` до нового, гнучкішого формату ELF (Executable and Linkable Format), а також впроваджували концепцію динамічного зв'язування бібліотек (`.so`).

При запуску двійкового файлу ELF ядро більше не завантажувало програму повністю готовою до виконання. Натомість ядро повинно було завантажити динамічний лінкер (наприклад, `ld-linux.so`) і передати йому критичну метаінформацію про систему:
- Де саме у віртуальній пам'яті розташовані заголовки програмного образу (Program Headers)?
- Який точний розмір сторінки пам'яті у цій конкретній апаратній архітектурі?
- Які апаратні розширення процесора (наприклад, FPU, SIMD або векторні інструкції) доступні на цій машині?
- Яка базова адреса завантаження самого динамічного лінкера?

Передавати ці параметри через `argv` або `environ` було неможливо: рядки середовища призначалися для програм користувача, а не для низькорівневої інфраструктури виконання. Створення ж серії нових системних викликів для зчитування кожного параметра суттєво уповільнювало б запуск кожного процесу через накладні витрати на перетин межі ядра.

У 1989 році в операційній системі AT&T System V Release 4 (SVR4) розробники запровадили **Auxiliary Vector (auxv)** — масив структур `Elf32_auxv_t` / `Elf64_auxv_t`, який ядро розміщує на стеку нового процесу одразу над масивом `environ`.

Допоміжний вектор дозволив ядру прозоро передавати динамічному лінкеру та бібліотеці C (libc) всі необхідні атрибути виконання за один крок без жодного додаткового системного виклику. Згодом у Linux через `auxv` почали передавати дані для захисту від переповнення буфера (випадковий байтовий вектор `AT_RANDOM` для stack canary) та прапорець безпечного режиму `AT_SECURE` для SetUID-програм.
