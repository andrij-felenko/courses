## 1. Від клавіші Tab до системних викликів: низькорівнева механіка Readline

Коли інтерактивна оболонка очікує на команду користувача, драйвер термінала TTY переводиться бібліотекою редагування рядка у неканонічний "сирий" режим (raw/cbreak mode). У цьому режимі драйвер ядра вимикає локальне відлуння (echo) і построкову буферизацію: кожен байт передається процесу оболонки негайно після натискання клавіші на клавіатурі.

На рівні структури `struct termios` оболонка скидає прапорець `ICANON` і `ECHO`, встановлюючи параметри `c_cc[VMIN] = 1` та `c_cc[VTIME] = 0`. Це гарантує, що системний виклик `read(STDIN_FILENO, &buf, 1)` блокується ядром рівно до надходження одного байта від апаратного термінала або емулятора псевдотермінала (PTY).

Натискання клавіші Tab генерує керівний символ ASCII `0x09` (`\t`). Бібліотека GNU Readline перехоплює цей байт у своєму головному циклі подій `rl_read_key()` і зіставляє його з таблицею прив'язок клавіш (keymap). За замовчуванням у режимі Emacs символ `\t` асоційований із внутрішньою C-функцією `rl_complete()`.

### Внутрішні структури даних буфера Readline

Бібліотека Readline оперує символьним масивом у пам'яті процесу, стан якого описується кількома глобальними змінними:
- `rl_line_buffer`: покажчик на динамічно виділений C-рядок, що містить поточний текст усього командного рядка;
- `rl_point`: цілочисельний індекс, який позначає позицію курсора (у байтах від початку `rl_line_buffer`);
- `rl_end`: загальна довжина тексту в буфері;
- `rl_completer_word_break_characters`: символьний набір роздільників, які визначають початок і кінець окремих слів.

### Життєвий цикл функції rl_complete()

Обробка запиту на доповнення усередині Readline складається з п'яти послідовних кроків:

1. **Визначення меж поточного слова**: Readline сканує буфер рядка `rl_line_buffer` назад від поточної позиції курсора `rl_point` доти, доки не зустріне символ із таблиці роздільників `rl_completer_word_break_characters` (за замовчуванням це пропуски, знаки табуляції, лапки, символи перенаправлення `><=;|&(:`). Отримані координати позначаються як `start` та `end`.
2. **Перевірка наявності хука програмованого доповнення**: Readline перевіряє глобальний покажчик на функцію `rl_attempted_completion_function`. Якщо оболонка (наприклад, Bash) зареєструвала свій обробник, керування передається йому.
3. **Резервний генератор за замовчуванням**: Якщо хук повертає покажчик `NULL` або взагалі не встановлений, Readline переходить до стандартного генератора імен файлів `rl_filename_completion_function()`. Цей генератор відкриває поточний робочий каталог через системний виклик `opendir()`, послідовно читає записи за допомогою `readdir()` та фільтрує їх за введеним префіксом.
4. **Обчислення найдовшого спільного префікса (LCP)**: Якщо генератор повертає список із кількох варіантів (наприклад, `config.yaml`, `config.json`, `config.bak`), Readline посимвольно обчислює їхній спільний префікс (`config.`). Якщо цей префікс довший за вже введене слово, він автоматично дописується в буфер `rl_line_buffer`, а курсор зміщується вправо.
5. **Обробка неоднозначності**: Якщо найдовший спільний префікс збігається з уже введеним текстом:
   - Одне натискання Tab видає звуковий або візуальний сигнал дзвінка (terminal bell `\a`, ASCII `0x07`);
   - Повторне швидке натискання Tab запускає функцію `rl_display_match_list()`, яка форматує всі доступні варіанти у компактну стовпчикову сітку та виводить їх у термінал, після чого повторно малює введений користувачем рядок із відновленням позиції курсора.

### Контракт пам'яті масиву matches

Хук `rl_attempted_completion_function` повертає масив покажчиків на рядки `char**`. Цей масив має сувору структуру:
- Елемент `matches[0]` містить рядок заміни. Якщо знайдено кілька варіантів, `matches[0]` містить їхній найдовший спільний префікс (LCP). Якщо збіг рівно один, `matches[0]` містить повний підставлений рядок.
- Елементи `matches[1]` ... `matches[N]` містять індивідуальні варіанти збігів для відображення у списку.
- Масив обов'язково завершується покажчиком `NULL` (`matches[N+1] == NULL`).
- Кожен рядок та сам масив виділяються у динамічній пам'яті через `malloc()`, а бібліотека Readline бере на себе зобов'язання звільнити цю пам'ять через `free()` після завершення операції.

Нижче наведено приклад інтеграції власного генератора автодоповнення мовами C та C++ з використанням API GNU Readline.

:::tabs
```c
/* Приклад реєстрації генератора варіантів через GNU Readline мовою C */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <readline/readline.h>
#include <readline/history.h>

static const char *commands[] = {
    "status", "start", "stop", "restart", "reload", "isolate", NULL
};

/* Генератор-ітератор: повертає один варіант за виклик */
static char *command_generator(const char *text, int state) {
    static int list_index, len;
    const char *name;

    if (!state) {
        list_index = 0;
        len = strlen(text);
    }

    while ((name = commands[list_index++])) {
        if (strncmp(name, text, len) == 0) {
            return strdup(name);
        }
    }
    return NULL;
}

/* Хук верхнього рівня для розпізнавання контексту */
static char **custom_completion(const char *text, int start, int end) {
    /* Якщо слово на початку рядка (start == 0) — доповнюємо команди */
    if (start == 0) {
        return rl_completion_matches(text, command_generator);
    }
    /* Інакше дозволяємо Readline виконати стандартне доповнення файлів */
    return NULL;
}

int main(void) {
    rl_attempted_completion_function = custom_completion;
    
    char *input;
    while ((input = readline("my-shell> ")) != NULL) {
        if (*input) {
            add_history(input);
            printf("Виконання: %s\n", input);
        }
        free(input);
    }
    return 0;
}
```
```cpp
// Ідіоматична C++ обгортка для реєстрації генератора GNU Readline
#include <iostream>
#include <vector>
#include <string>
#include <string_view>
#include <memory>
#include <cstring>
#include <readline/readline.h>
#include <readline/history.h>

class ShellCompleter {
public:
    static inline const std::vector<std::string> kCommands = {
        "status", "start", "stop", "restart", "reload", "isolate"
    };

    static char* Generator(const char* text, int state) {
        static size_t index = 0;
        static size_t len = 0;

        if (state == 0) {
            index = 0;
            len = std::strlen(text);
        }

        while (index < kCommands.size()) {
            const auto& candidate = kCommands[index++];
            if (candidate.compare(0, len, text) == 0) {
                // Readline вимагає пам'ять, виділену через malloc
                char* match = static_cast<char*>(std::malloc(candidate.size() + 1));
                if (match) {
                    std::strcpy(match, candidate.c_str());
                }
                return match;
            }
        }
        return nullptr;
    }

    static char** AttemptedCompletion(const char* text, int start, int /*end*/) {
        if (start == 0) {
            return rl_completion_matches(text, Generator);
        }
        return nullptr; // Перехід до стандартного пошуку файлів
    }
};

int main() {
    rl_attempted_completion_function = ShellCompleter::AttemptedCompletion;

    while (true) {
        std::unique_ptr<char, void(*)(void*)> input(readline("my-shell> "), std::free);
        if (!input) {
            break;
        }
        if (*input.get() != '\0') {
            add_history(input.get());
            std::cout << "Виконання: " << input.get() << '\n';
        }
    }
    return 0;
}
```

## 2. Вбудовані механізми Bash: complete, compgen та compopt

Коли оболонка GNU Bash ініціалізує свою роботу в інтерактивному режимі, вона перехоплює хук `rl_attempted_completion_function`, спрямовуючи його на власну підсистему програмованого автодоповнення (Programmable Completion).

Bash підтримує внутрішню геш-таблицю специфікацій доповнення. Кожен запис цієї таблиці зіставляє ім'я утиліти з правилом генерації варіантів. Керування цією таблицею здійснюється за допомогою вбудованої команди `complete`.

![Архітектура системи програмованого доповнення Bash](/root/sys/sys-unix/shell-completion/img/bash-completion-architecture.svg)
*Архітектура системи програмованого доповнення Bash: взаємодія таблиці специфікацій, контекстних змінних та рушія compgen.*

### Вбудована команда complete

Команда `complete` реєструє дію для конкретної команди. Якщо для команди `tar` зареєстровано розширення файлів, оболонка не запускатиме зовнішні сценарії, а виконає внутрішню оптимізовану C-підпрограму Bash:

```bash
# Доповнення аргументів tar лише файлами архівів
complete -f -X '!*.@(tar|tar.gz|tgz|tar.bz2|tar.xz)' tar

# Доповнення аргументів команди man назвами існуючих команд
complete -c man

# Доповнення аргументів ssh іменами хостів із конфігурації
complete -A hostname ssh
```

Коли Bash шукає правило для введеного слова, він виконує пошук у наступному порядку пріоритету:
1. Точний збіг імені команди у геш-таблиці специфікацій `complete`;
2. Спеціальне правило для початкового слова команди (зареєстроване через `complete -I`);
3. Глобальне правило за замовчуванням (зареєстроване через `complete -D`).

Детальний перелік усіх прапорців, дій та модифікаторів команди наведено у вставці [Довідник інтерфейсу complete та compgen](root:sys-unix/shell-completion/api-bash-completion-builtin.md).

### Обчислювальний рушій compgen

Якщо команда `complete` визначає *декларацію правил*, то вбудована команда `compgen` є безпосереднім *виконавчим механізмом*. Вона приймає набір прапорців фільтрації та шукане слово, здійснюючи зіставлення за префіксом усередині простору пам'яті процесу Bash без виклику зовнішніх утиліт:

```bash
# Генерація варіантів із фіксованого списку слів за префіксом "dis"
compgen -W "enable disable status restart mask" -- "dis"
# Результат у стандартному виводі:
# disable

# Генерація імен користувачів системи за префіксом "dae"
compgen -u -- "dae"
# Результат:
# daemon
```

Під капотом `compgen` розгортає переданий рядок слів `-W` за правилами розбиття змінної `IFS`. Якщо у списку присутні змінні або вирази підстановки команд `$(...)`, вони обчислюються у момент виклику. Після цього внутрішній цикл порівнює кожне отримане слово з останнім аргументом `-- word` за допомогою функції `strncmp()`. Усі слова, які збіглися з префіксом, передаються у стандартний потік виводу по одному на рядок.

### Динамічне керування поведінкою через compopt

У версії Bash 4.0 з'явилася вбудована команда `compopt`, яка дозволяє змінювати параметри доповнення динамічно під час виконання функції генерації. 

Типовий випадок — доповнення шляхів до файлів або ключів конфігурації, де після знака рівності `=` або двокрапки `:` заборонено ставити автоматичний пропуск. За допомогою `compopt -o nospace` функція сигналізує бібліотеці Readline, що підставлений результат не є фінальним словом, і курсор повинен залишитися впритул до щойно вставленого фрагмента.

## 3. Анатомія власної функції доповнення: змінні COMP_* та масив COMPREPLY

Найпотужнішим способом генерації варіантів є зв'язування команди з користувацькою функцією Bash через прапорець `-F`:

```bash
complete -F _custom_deploy_helper deploy
```

Коли користувач натискає Tab у командному рядку `deploy --cluster `, Bash виконує наступну послідовність дій:

1. Оболонка формує набір спеціальних глобальних змінних, що описують поточний рядок введення:
   - `COMP_LINE`: повний символьний рядок буфера (наприклад, `"deploy --cluster pr"`);
   - `COMP_POINT`: числова позиція курсора у байтах від початку рядка (наприклад, `20`);
   - `COMP_WORDS`: індексований масив слів, отриманий у результаті токенізації рядка `COMP_LINE`;
   - `COMP_CWORD`: цілочисельний індекс у масиві `COMP_WORDS`, який вказує на токен, де зараз знаходиться курсор (у цьому прикладі `2`);
   - `COMP_WORDBREAKS`: рядок символів-роздільників, що використовувалися для розбиття рядка на слова.
2. Bash обнуляє глобальний масив `COMPREPLY`.
3. Викликається функція `_custom_deploy_helper`.
4. Після завершення функції Bash зчитує вміст масиву `COMPREPLY` і передає його елементи бібліотеці Readline для здійснення автопідстановки.

```
Вхідний рядок:  deploy   --cluster   production
                ──────   ─────────   ──────────
COMP_WORDS:       [0]       [1]          [2]
                                          ▲
                                          └── COMP_CWORD = 2
```

### Проблема роздільників слів: COMP_WORDBREAKS

Найскладнішим підводним каменем при написанні сценаріїв під Bash є поведінка змінної `COMP_WORDBREAKS`. За замовчуванням вона містить символ двокрапки `:` та знака рівності `=`.

Якщо користувач вводить команду з адресою порту:

```bash
connect --host=localhost:8080
```

Readline розіб'є цей фрагмент на окремі токени:
`COMP_WORDS=("connect" "--host" "=" "localhost" ":" "8080")`

У цьому випадку індекс `COMP_CWORD` вказуватиме на `5` (`"8080"`), а попереднім словом `COMP_CWORD-1` виявиться двокрапка `:`. Якщо функція доповнення спробує повернути повний рядок `localhost:8080`, Readline вважатиме початком заміни позицію після двокрапки й продублює хост: `localhost:localhost:8080`.

Для розв'язання цієї проблеми стандартний пакет `bash-completion` містить спеціальні макроси:
- `_init_completion -n ":="`: динамічно склеює токени навколо двокрапок та знаків рівності у правильні довгі слова всередині змінних `cur`, `prev`, `words`, `cword`;
- `__ltrim_colon_completions "$cur"`: видаляє зайвий префікс до двокрапки з елементів масиву `COMPREPLY` перед поверненням результату в Readline.

Повний інженерний розбір створення багаторівневого комплішена з обробкою прапорців, підкоманд та кешуванням наведено у вставці [Розробка комплішена для CLI-утиліти з підкомандами](root:sys-unix/shell-completion/proj-custom-subcommand-completion.md).

## 4. Архітектура системного пакету bash-completion та обробка складних підкоманд

На сучасному сервері Linux встановлено тисячі консольних утиліт (`ip`, `nmcli`, `iptables`, `systemctl`, `journalctl`, `podman`, `git`). Якщо оболонка під час старту зчитуватиме сценарії доповнення для всіх наявних програм через системний виклик `source`, час запуску інтерактивної сесії зросте з 5 мілісекунд до кількох секунд, а споживання оперативної пам'яті процесом оболонки перевищить 50 Мегабайтів.

Для усунення цієї затримки системний пакет `bash-completion` реалізує архітектуру **динамічного завантаження на вимогу** (Dynamic Auto-Loading).

### Механізм динамічного завантаження

Під час старту Bash файл конфігурації `/etc/bash_completion` (або `/usr/share/bash-completion/bash_completion`) реєструє єдиний універсальний генератор за замовчуванням:

```bash
complete -D -F _completion_loader
```

Коли користувач вперше вводить команду `docker <Tab>`:
1. Bash шукає правило для `docker` у геш-таблиці та не знаходить його.
2. Спрацьовує обробник за замовчуванням `_completion_loader`.
3. Функція перевіряє наявність файлу в каталогах пошуку:
   - `~/.local/share/bash-completion/completions/docker`
   - `/usr/local/share/bash-completion/completions/docker`
   - `/usr/share/bash-completion/completions/docker`
4. Якщо файл знайдено, `_completion_loader` завантажує його в пам'ять процесу через `.` (`source`). Сценарій усередині файлу реєструє справжню функцію (наприклад, `complete -F _docker docker`).
5. `_completion_loader` викликає щойно зареєстровану функцію `_docker` для обробки поточного натискання Tab. Усі наступні виклики `docker` обслуговуються зареєстрованою функцією напряму без звернення до завантажувача.

```
[Ввід: git check <Tab>] ──► [Перевірка таблиці complete] 
                                    │
                  ┌─────────────────┴─────────────────┐
           [Правило знайдено]                  [Правило відсутнє]
                  │                                   │
                  ▼                                   ▼
         [Виклик _git()]                     [Виклик _completion_loader]
                  │                                   │
                  │                          [source .../completions/git]
                  │                                   │
                  │                          [Реєстрація complete -F _git]
                  │                                   │
                  └─────────────────┬─────────────────┘
                                    ▼
                         [Формування COMPREPLY]
```

### Обробка складних підкоманд: приклад Git та Systemd

Складні інструменти організовані у вигляді синтаксичних дерев. Наприклад, утиліта `systemctl` може приймати глобальні опції (`--user`, `--host=remote`), підкоманди (`start`, `stop`, `status`, `enable`, `set-property`) та аргументи юнітів різних типів (`service`, `socket`, `target`, `mount`).

Сценарій доповнення `systemctl` виконує синтаксичний аналіз:
1. Сканує масив `COMP_WORDS` від початку, ігноруючи відомі глобальні прапорці (`--system`, `--user`, `--host`);
2. Знаходить перший невідомий позиційний аргумент і фіксує його як головну підкоманду (`$verb`);
3. Залежно від `$verb` змінює джерело генерації:
   - Для `start` або `restart` генеруються імена неактивних та активних юнітів через виклик D-Bus утиліти `systemctl list-unit-files --no-legend`;
   - Для `set-property` пропонуються параметри конфігурації Cgroups (`CPUQuota=`, `MemoryMax=`, `TasksMax=`);
   - Для `cat` або `edit` дозволяється доповнення будь-яких відомих системних юнітів.

Приклад виклику підкоманд у Git демонструє роботу автомата станів: для `git checkout <Tab>` скрипт аналізує вміст псевдокаталогу `.git/refs/heads/`, упакованого файлу `.git/packed-refs` та віддалених гілок у `.git/refs/remotes/`, виключаючи внутрішні службові теги й формуючи вичерпний перелік гілок за лічені мілісекунди без повільного запуску `git branch -a`.

Аналогічно, автодоповнення для клієнта `ssh` аналізує не лише системну базу імен хостів `/etc/hosts`, а й розбирає користувацький файл конфігурації `~/.ssh/config`, витягуючи ключові слова `Host` та відкидаючи маски з підстановочними знаками на зразок `Host *` або `Host 192.168.*`.

## 5. Порівняння систем доповнення: підхід Bash проти системи Zsh

Незважаючи на здатність Bash вирішувати задачі доповнення через розгалужені скрипти, його архітектура обмежена рядковою моделлю бібліотеки GNU Readline. Сучасні альтернативні оболонки (насамперед Z Shell) пропонують принципово інший рівень абстракції.

![Порівняння архітектури доповнення: Текстовий Bash проти Типізованого Zsh](/root/sys/sys-unix/shell-completion/img/bash-vs-zsh-pipeline.svg)
*Порівняння архітектурних конвеєрів: плаский масив рядків Bash проти контекстно-типізованого графа Zsh.*

### Обмеження Bash-підходу

1. **Одновимірність даних**: Масив `COMPREPLY` передає у Readline виключно "сирі" рядки. Readline не має інформації про те, чим є рядок — файлом, мережевим хостом, командою чи опцією.
2. **Відсутність описів варіантів**: Користувач Bash бачить список слів, але не може отримати коротку довідку про призначення кожного прапорця у момент вибору.
3. **Ручний парсинг**: Сценарії для Bash змушені власноруч емулювати граматичний парсер через нескінченні цикли `for`/`case` над масивом слів.

### Модель Zsh compsys

Підсистема `compsys` у Zsh реалізує декларативний синтаксичний аналіз за допомогою функції `_arguments`:

```zsh
# Декларативний опис інтерфейсу утиліти в Zsh
_arguments -s \
    '(-h --help)'{-h,--help}'[Показати довідку]' \
    '(-v --verbose)'{-v,--verbose}'[Увімкнути детальний вивід]' \
    '--format=[Формат звіту]:формат:(json yaml text)' \
    '1:дія:(start stop status restart)' \
    '*:файли конфігурації:_files -g "*.conf"'
```

Переваги підсистеми Zsh полягають у наступному:
- **Групування та описи**: Кожен варіант супроводжується текстовим описом (наприклад, `--help [Показати довідку]`), а варіанти автоматично розбиваються на візуальні секції (команди, прапорці, файли);
- **Інтерактивне меню (menu-select)**: Замість друку статичного тексту Zsh вмикає двовимірне меню, де користувач може переміщатися між варіантами стрілками клавіатури, бачити підсвічування поточного вибору та читати динамічні описи параметрів;
- **Кольорове форматування**: Підтримка змінної `ZLS_COLORS` дозволяє забарвлювати варіанти доповнення за типами файлів та статусами служб аналогічно до виводу утиліти `ls --color`.

Глибокий структурний аналіз відмінностей між двома моделями представлено у вставці [Архітектурне порівняння систем доповнення Bash та Zsh](root:sys-unix/shell-completion/comp-bash-vs-zsh-completion.md).

## 6. Продуктивність та оптимізація скриптів доповнення

Оскільки автодоповнення є частиною інтерактивного циклу введення тексту, затримка між натисканням Tab і оновленням екрана не повинна перевищувати 50–100 мілісекунд. Затримка понад 200 мс сприймається користувачем як гальмування термінала.

Основними джерелами затримок у скриптах доповнення є:

1. **Створення процесів через підстановку команд `$(...)`**: Кожен виклик подоболонки вимагає виконання системних викликів `fork()`, `execve()` та очищення пам'яті. Використання вбудованих можливостей Bash (наприклад, підстановки параметрів `${var#prefix}` замість `$(echo "$var" | sed ...)` чи `$(cut ...)`) прискорює обчислення в сотні разів.
2. **Мережеві запити та звернення до важких баз даних**: Доповнення імен контейнерів через виклик `docker ps` або статусів віртуальних машин через `virsh` виконує IPC-запити до системних демонів. Якщо демон перевантажений або заблокований дисковим вводом-виводом, термінал зависає. Промислові сценарії застосовують тимчасові файли кешування у `/tmp` зі строком актуальності 10–30 секунд.
3. **Надмірний пошук у файловій системі**: Виклик `find / -name ...` усередині автодоповнення є неприпустимим. Для пошуку файлів використовується або обмеження поточним каталогом через вбудований генератор `compgen -f`, або спеціалізовані індексовані бази (наприклад, `locate` чи `mlocate`).

## 7. Безпека у сценаріях автодоповнення

Оскільки автодоповнення виконується автоматично під час набору тексту, воно створює специфічний вектор атак, якщо сценарій написаний без урахування безпеки:

1. **Виконання коду через небезпечне екранування**: Якщо сценарій використовує конструкцію `eval` або не захищає масиви змінних подвійними лапками, ім'я файлу на диску на кшталт `$(reboot).txt` або `` `rm -rf /` `` може бути виконано інтерпретатором Bash безпосередньо у момент натискання Tab.
2. **Підміна бінарників у поточному каталозі**: Якщо функція комплішена викликає системні утиліти без абсолютного шляху або якщо поточний каталог `.` помилково додано до змінної `PATH`, натискання Tab у завантаженому каталозі невідомого джерела може призвести до запуску шкідливого скрипту.
3. **Ескалація привілеїв у сесіях root**: При виконанні команд під обліковим записом `root` функції доповнення виконуються з повними системними привілеями. Тому всі скрипти у `/usr/share/bash-completion/` повинні мати права доступу, доступні на запис лише суперкористувачеві (`chmod 644`), що захищає систему від несанкціонованої модифікації генераторів доповнення.

---

Автодоповнення в сучасних Unix-системах перетворилося з допоміжної функції бібліотеки рядкового введення на повноцінний інтерфейс взаємодії людини з операційною системою. Грамотне поєднання низькорівневих можливостей Readline, декларативних інструментів `complete`/`compgen` та оптимізованих функцій контекстного розбору забезпечує швидке, безпечне та безпомилкове керування складними багатокомпонентними сервісами операційної системи.
