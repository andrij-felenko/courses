# 📜 Історія IPsec у Linux: від FreeS/WAN та KLIPS до ядерного каркаса XFRM

Формування захищених мережевих каналів на рівні IP-протоколу (IPsec) у 1990-х роках вимагало від операційних систем кардинальної перебудови мережевого стеку. У вихідній архітектурі Linux серій 2.0 та 2.2 не існувало жодного механізму для криптографічного перетворення пакетів «на льоту». Першим масштабним рішенням цієї проблеми став проект **FreeS/WAN** (Free Secure Wide Area Network), заснований у 1996 році Джоном Ґілмором (John Gilmore) та Г'ю Даніелем (Hugh Daniel). Метою проекту було забезпечення масового шифрування інтернет-трафіку для протидії суцільному стеженню та захисту приватного життя громадян у цифровому просторі.

## Патч KLIPS та модель віртуальних інтерфейсів

Реалізація IPsec від FreeS/WAN спиралася на модуль ядра **KLIPS** (Kernel Linux IPsec Code). KLIPS діяв за інтуїтивно зрозумілою на той час концепцією віртуального мережевого пристрою. Модуль створював у системі псевдо-інтерфейси вида `ipsec0`, `ipsec1` тощо.

Схема роботи KLIPS спиралася на стандартну маршрутизацію:
1. Звичайна таблиця маршрутизації спрямовувала трафік, який потребував захисту, у віртуальний пристрій `ipsec0`.
2. Драйвер пристрою `ipsec0` перехоплював пакет, шукав відповідні ключі шифрування у власних внутрішніх таблицях, інкапсулював його в ESP/AH-заголовок і виконував криптографічні операції.
3. Сформований новий зашифрований IP-пакет відправлявся повторно у мережевий стек для передачі через реальний фізичний інтерфейс (наприклад, `eth0`).

Хоча ця модель була зрозумілою для системних адміністраторів (оскільки криптографія виглядала як ще один мережевий інтерфейс), вона мала серйозні внутрішні архітектурні вади:

- **Подвійні накладні витрати CPU**: Передача корисного навантаження вимагала повторного проходження пакета через повний мережевий стек ядра. Кожен пакет копіювався між буферами `sk_buff`, спричиняючи значні затримки та перевитрату оперативної пам'яті.
- **Проблема підтримки коду**: KLIPS існував виключно у вигляді громіздких зовнішніх патчів ядра. З кожним оновленням ядра Linux підтримка патчів ставала дедалі важчою, а розробники ядра відмовлялися приймати KLIPS у mainline-гілку через його порушення монолітної архітектури маршрутизації FIB.
- **Обмеженість масштабування**: Для кожного нового тунелю або підмережі вимагалося створення окремого віртуального інтерфейсу, що створювало високе навантаження при наявності тисяч одночасних VPN-з'єднань.

## Вплив стеку KAME та розробка XFRM

Паралельно у світі BSD розгортався проект **KAME** — консорціум японських компаній та дослідників, що створювали еталонну реалізацію IPv6 та IPsec для FreeBSD, NetBSD та OpenBSD. KAME відмовився від концепції віртуальних інтерфейсів на користь розділення політик та станів безпеки (SPD/SAD) згідно зі специфікаціями RFC 2401, використовуючи сокети керування `PF_KEYv2` (RFC 2367).

На початку 2000-х років розробники мережевого стеку Linux — **Олексій Кузнецов** (Alexey Kuznetsov), який створив сучасну підсистему маршрутизації FIB та інструментарій `iproute2`, та **Девід Міллер** (David S. Miller), мейнтейнер мережевої підсистеми ядра, — розпочали повну переробку IPsec для майбутньої гілки ядра Linux 2.6.

Кузнецов та Міллер усвідомлювали: IPsec у своїй суті є не пристроєм, а **перетворенням** (transformation) даних під час проходження через стек. Вони розробили підсистему **XFRM** (скорочення від *transform*), яка кардинально змінила підхід до шифрування:

- **Інтеграція в кєш маршрутизації (`dst_entry`)**: Замість перенаправлення пакета на віртуальний пристрій, рішення про перетворення приймається під час стандартного пошуку маршруту. Якщо політика вимагає IPsec, підсистема підміняє вказівник функції вихідного маршруту на криптографічний обробник XFRM.
- **Розділення станів (SA) та політик (SP)**: Стан безпеки (ключі, SPI, алгоритми) і політика (який трафік захищати) стали повністю незалежними об'єктами в ядрі.
- **Відмова від `PF_KEY` на користь Netlink**: Хоча XFRM зберіг сумісність із сокетами `PF_KEYv2` для підтримки старих демонів, основним інтерфейсом керування став високопродуктивний протокол Netlink (`NETLINK_XFRM`).

## Визнання у ядрі 2.6 та сучасний стан

У грудні 2003 року вийшло ядро Linux 2.6.0, де XFRM став офіційним еталонним каркасом IPsec. Проекти FreeS/WAN та його наступники Openswan і strongSwan поступово портували свої користувацькі демони обміну ключами (IKE) на використання сокетів Netlink XFRM.

У ядрі Linux 4.19 підсистема зробила ще один виток еволюції: було додано інтерфейси **XFRM-I** (`ip link add type xfrm`). Це повернуло можливість працювати з IPsec як з інтерфейсом для віртуальних мереж (Route-based VPN), але вже без архітектурних костилів KLIPS — нові інтерфейси працюють як легкі обгортки над тим самим базовим каркасом XFRM.
