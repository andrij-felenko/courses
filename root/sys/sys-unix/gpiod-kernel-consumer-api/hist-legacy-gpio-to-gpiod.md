# 📜 Еволюція від integer-based GPIO API (<linux/gpio.h>) до дескрипторів gpiod

Архітектурний глухий кут глобального числового простору `gpio_request(int gpio, ...)` виявився головним гальмівним фактором розвитку підсистеми GPIO в ядрі Linux під час масового переходу на багатоплатформні системи-на-кристалі (SoC). Прив'язка апаратних ліній до простих цілих чисел створювала колізії нумерації при динамічному завантаженні драйверів, унеможливлювала автоматичне перенесення коду між різними платами та спричинила вибухоподібне розростання плат-файлів (`board-*.c`) у каталозі `arch/arm/`. Для подолання цієї кризи підсистему `gpiolib` було повністю рефакторено з переходом від застарілого числового API `<linux/gpio.h>` до непрозорих дескрипторів `struct gpio_desc *` у `<linux/gpio/consumer.h>`.

---

## 1. Ера цілочисельного API: Простота, що перетворилася на системну кризу

На початку 2000-х років, у часи ядер Linux серії 2.6.x, робота з лініями загального призначення (GPIO) здавалася відносно простою задачею. Для керування фізичними виводами процесора розробникам надавався заголовковий файл `<linux/gpio.h>` з лаконічним набором функцій:

```c
int gpio_request(unsigned gpio, const char *label);
void gpio_free(unsigned gpio);
int gpio_direction_input(unsigned gpio);
int gpio_direction_output(unsigned gpio, int value);
int gpio_get_value(unsigned gpio);
void gpio_set_value(unsigned gpio, int value);
```

Вся модель базувалася на припущенні, що кожна лінія GPIO у всій операційній системі має унікальний цілочисельний номер — від `0` до `ARCH_NR_GPIOS - 1`. На простих персональних комп'ютерах чи перших промислових контролерах з десятком виводів це працювало задовільно. Однак із бурхливим розвитком мобільних пристроїв, систем на кристалі (SoC, таких як TI OMAP, Samsung Exynos, Allwinner, Rockchip та Broadcom BCM2835), а також із появою численних розширювачів портів на шинах I2C та SPI, глобальний цілочисельний простір став джерелом постійних системних збоїв.

### 1.1. Проблема динамічної нумерації та колізій

У старому API драйвери контролерів GPIO (`struct gpio_chip`) реєстрували свої діапазони чисел під час завантаження ядра. Якщо базовий контролер SoC надавав 32 лінії (`0..31`), а зовнішній розширювач портів на шині I2C додавав ще 8 ліній, ядро виділяло для них наступний вільний діапазон (наприклад, `32..39`).

Проте порядок ініціалізації драйверів шин I2C/SPI та контролерів SoC залежить від порядку завантаження модулів ядра, асинхронного сканування шин та наявності відкладених спроб ініціалізації (`-EPROBE_DEFER`). Якщо в новій версії ядра драйвер I2C завантажувався раніше за другий контролер SoC, нумерація ліній зміщувалася.

В результаті номер `42`, який у попередній збірці ядра відповідав лінії скидання (`reset`) зовнішнього мережевого адаптера, міг раптово стати лінією керування силовим живленням процесора. Спроба драйвера виставити `gpio_set_value(42, 1)` призводила до того, що система замість скидання мережевої карти перемикала лінію керування живленням і знеструмлювала цілком робочий вузол.

### 1.2. Прокляття "Board Files" та вибух у коді ARM

До впровадження Дерева пристроїв (Device Tree) описи апаратних платформ зберігалися у вихідних файлах ядра C у теці `arch/arm/mach-*/board-*.c`. У цих файлах розробники жорстко прописували цілі числа:

```c
/* Старий board file для ARM-платформи */
static struct platform_device my_sensor_device = {
    .name = "acme-sensor",
    .id = -1,
    .dev = {
        .platform_data = &(struct my_sensor_platform_data) {
            .reset_gpio = 42,   /* Жорстко прив'язаний номер */
            .irq_gpio   = 43,
        },
    },
};
```

Драйвер периферійного пристрою був вимушений витягувати ці числа з `platform_data` та передавати їх у `gpio_request()`. Якщо один і той самий датчик підключали до іншого виводу на іншій ревізії плати, доводилося перекомпілювати все ядро. Драйвер не мав жодної абстракції від фізичної топології платформи.

До 2011 року кількість таких `board-*.c` файлів у ядрі Linux досягла критичної позначки: каталоги `arch/arm/` містили сотні тисяч рядків дубльованого коду, де кожен виробник плати прописував власні масиви цілих чисел. Це спонукало Лінуса Торвальдса опублікувати знаменитий гострий заклик до спільноти з вимогою негайно припинити засмічення ядра та реструктуризувати підтримку ARM-архітектури.

## 2. Відсутність метаданих: Полярність та електричні режими

Другим суттєвим недоліком старого API була неможливість зберегти метадані лінії всередині ядерної підсистеми.

### 2.1. Ручна інверсія Active Low у драйверах

Багато апаратних компонентів (наприклад, піни скидання `RESET#` або вибору чіпа `CS#`) керуються інвертованим сигналом: низький напруговий рівень (`0V` / LOW) означає "активний стан" (активовано), а високий (`3.3V` / HIGH) — "неактивний".

У старій системі драйвер мусив самостійно відстежувати цю особливість. У кожному місці коду розробник писав умовні оператори:

```c
/* Код драйвера зі старим integer API */
if (priv->is_active_low)
    gpio_set_value(priv->reset_gpio, 0); /* Активація скидання */
else
    gpio_set_value(priv->reset_gpio, 1);
```

Це призводило до захаращення коду драйверів дубльованою логікою перевірок. Якщо розробник драйвера забував врахувати прапор `active_low`, пристрій працював у протифазі, що викликало важкодіагностовані помилки при ініціалізації.

### 2.2. Ігнорування відкритого стоку та придушення брязкоту

Старе API `gpio_direction_output(gpio, val)` приймало лише бінарне значення `0` або `1`. Воно не дозволяло вказати ядру, що лінія має працювати в режимі відкритого стоку (Open Drain) або відкритого витоку (Open Source). Якщо для шини I2C або лінії переривання вимагався режим Open Drain, драйвер мав додатково викликати специфічні для конкретного SoC функції або налаштовувати регістри через окремі хаки, що руйнувало переносимість коду.

## 3. Великий рефакторинг gpiolib: Поява `struct gpio_desc`

У 2013 році, у циклі розробки ядра Linux 3.13, супровідник підсистеми GPIO Лінус Валлей (Linus Walleij) розпочав масштабну перебудову `gpiolib`. Метою було повне вилучення глобальних цілих чисел з API драйверів периферії та перехід на непрозорі дескриптори `struct gpio_desc *`.

### 3.1. Концепція непрозорого вказівника

Замість цілого числа драйвер периферійного пристрою почав отримувати вказівник на структуру `struct gpio_desc`. Внутрішня будова цієї структури була прихована від драйверів і доступна лише коду всередині `drivers/gpio/gpiolib.c`.

У `struct gpio_desc` ядро об'єднало всі апаратні та системні атрибути лінії:
1. Вказівник на базовий контролер `struct gpio_chip *`, який безпосередньо керує регістрами.
2. Апаратний індекс лінії всередині цього контролера.
3. Маску бітових прапорів стану: `FLAG_REQUESTED`, `FLAG_IS_OUT`, `FLAG_ACTIVE_LOW`, `FLAG_OPEN_DRAIN`, `FLAG_OPEN_SOURCE`, `FLAG_BIAS_PULL_UP`, `FLAG_BIAS_PULL_DOWN`.
4. Текстову мітку споживача (`label`), надану при отриманні лінії.

### 3.2. Автоматична трансляція з Device Tree та ACPI

Новий API `gpiod_get(dev, "reset", flags)` позбавив драйвер необхідності знати номери пінів. Драйвер звертається до ядра з описовим ім'ям функціональної ролі лінії (наприклад, `"reset"` або `"enable"`).

Ядро автоматично:
- Шукає у дереві пристроїв для даного вузла властивість `reset-gpios` або `reset-gpio`.
- Розбирає посилання (`phandle`) на вузол контролера разом з аргументами (`<&gpio1 10 ...>`).
- Витягує апаратні прапори, такі як `GPIO_ACTIVE_LOW` або `GPIO_PULL_UP`.
- Ініціалізує дескриптор і повертає його драйверу з уже встановленим напрямком та початковим значенням.

### 3.3. Період сумісності та трансляція старого API

Щоб зберегти працездатність тисяч існуючих драйверів під час перехідного періоду, підсистема `gpiolib` була переписана так, що старий цілочисельний API став лише "тонкою обгорткою" поверх нового дескрипторного API:

```c
/* Внутрішній перехідник у gpiolib.c */
void gpio_set_value(unsigned gpio, int value)
{
    struct gpio_desc *desc = gpio_to_desc(gpio);
    if (desc)
        gpiod_set_raw_value(desc, value);
}
```

Спеціальна функція `gpio_to_desc(gpio)` здійснює пошук дескриптора за старим цілим номером у внутрішній таблиці ядра. Це дозволило розробникам ядра поступово, драйвер за драйвером, переводити підсистеми на `gpiod` без зупинки розробки ядра.

## 4. Еволюція користувацьких інтерфейсів: Від SysFS до Chardev ABI v2

Паралельно з рефакторингом внутрішнього ядерного API змінювався і користувацький інтерфейс доступності GPIO з простору користувача (Userspace):

1. **Застарілий SysFS (`/sys/class/gpio`):** З'явився у Linux 2.6.27 (2008 рік). Працював через текстові файли `export`, `direction`, `value`. Мав критичні недоліки: повільність (ASCII-перетворення), відсутність атомарності, ризик короткочасних імпульсів при виборі напрямку та відсутність авто-очищення ресурсів при краху процесів. Оголошений застарілим (Deprecated) у Linux 4.8.
2. **Символьний пристрій ABI v1 (`/dev/gpiochipN`):** Доданий у Linux 4.8 (2016 рік). Впровадив роботу через файлові дескриптори та виклики `ioctl()`, прив'язавши життєвий цикл ліній до процесів.
3. **Символьний пристрій ABI v2 (`/dev/gpiochipN`):** Прийнятий у Linux 5.10 (2020 рік). Уніфікував керування лініями та моніторинг подій у єдиному файловому дескрипторі `struct gpio_v2_line_request`, додавши підтримку апаратного придушення брязкоту (debounce), вибору джерела міток часу та гнучких атрибутів підтягування.

## 5. Підсумки еволюції: Порівняльний аналіз підходів

Перехід від integer-based API до `gpiod` став ключовим етапом модернізації ядра Linux. Нижче наведено зведену таблицю порівняння двох архітектурних підходів:

```
+---------------------------+-----------------------------------+-----------------------------------+
| Параметр                  | Старий API (<linux/gpio.h>)       | Сучасний API (<linux/gpio/consumer.h>) |
+---------------------------+-----------------------------------+-----------------------------------+
| Ідентифікатор лінії      | Ціле число (int / unsigned)       | Вказівник struct gpio_desc *      |
| Простір назв              | Глобальний (ризик колізій)        | Локальний (ізольований gpiolib)   |
| Зв'язування з апаратурою  | Board files / Ручні номери        | Device Tree / ACPI / Lookup Tables|
| Керування полярністю      | Ручне у коді драйвера             | Автоматичне (Logical Active/Inactive)|
| Контекст життєвого циклу | Ручні gpio_request / gpio_free    | Автоматичний devm_gpiod_get (Devres)|
| Безпека типів             | Низька (будь-яке int передається) | Висока (непрозорий вказівник)     |
+---------------------------+-----------------------------------+-----------------------------------+
```

Завдяки впровадженню `gpiod` драйвери периферійних пристроїв у сучасному ядрі Linux стали повністю незалежними від конкретної топології плати, а розробка драйверів позбулася цілого класу помилок, пов'язаних із гонками ініціалізації та невірною полярністю сигналів.
