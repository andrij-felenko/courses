# 📜 Історія виникнення debugfs: вільне вікно без кайданів ABI

Історія debugfs пояснює, чому у 2004 році розробники ядра Linux відмовилися від жорстких вимог до стабільності ABI заради швидкості діагностики та як виник свідомий компроміс між procfs, sysfs та незахищеним інструментарієм розробника ядра.

## Захаращення procfs та криза початку 2000-х років

Наприкінці 1990-х та на початку 2000-х років у ядрі Linux 2.2 та 2.4 існував лише один загальноприйнятий механізм експорту даних у простір користувача — віртуальна файлова система `/proc` (procfs). Початково спроектована у традиції Plan 9 для відображення метаданих про процеси (Process File System), procfs швидко перетворилася на звалище для будь-якої діагностичної інформації. Розробники мережевих стеків, SCSI-драйверів, підсистем керування живленням (APM/ACPI), звукових карт та пристроїв PCI масово створювали власні файли та каталоги безпосередньо в корені `/proc`.

У результаті каталог `/proc` утратив будь-яку виразну структуру. Читання `/proc/cpuinfo` або `/proc/meminfo` межувало з читанням виводу внутрішніх структур окремих контролерів. Ба більше, кожен розробник драйвера вигадував власний текстовий формат: хтось виводив дані у вигляді послідовності `ключ: значення`, хтось — у формі неструктурованих таблиць, а хтось експортував дамп бінарних регістрів. Спроби системних утиліт (`ps`, `top`, `free`, `netstat`) парсити цей різношерстий вивід постійно ламалися при кожному оновленні ядра, бо не існувало єдиного формату чи стандарту.

Ця ситуація викликала гостре обурення Лінуса Торвальдса та провідних мейнтейнерів VFS. Наприкінці 2001 року було проголошено курс на очищення `/proc` та повернення її до початкового призначення — обслуговування інформації про процеси (`/proc/[pid]`).

## Революція sysfs та її суворі ланцюги

Розв'язанням кризи procfs мала стати файлова система **sysfs**, яка з'явилася в ядрі Linux 2.5 та стала фундаментальною частиною релізу 2.6.0 у грудні 2003 року. Авторству Патріка Мошеля (Patrick Mochel) та Грега Кроа-Гарртмана (Greg Kroah-Hartman) належала ідея тісного зв'язку віртуальної файлової системи з новою моделлю пристроїв ядра (Device Model) через ієрархію об'єктів `kobject`.

sysfs запровадила жорстку дисциплінну філософію:
1. **Один атрибут — один файл (One value per file):** кожен файл у sysfs мав містити лише одне текстове або числове значення (наприклад, температуру, статус живлення чи лічильник помилок). Текстові дампи зі складними таблицями суворо заборонялися.
2. **Строгий зв'язок із дрібною ієрархією пристроїв:** кожен вузол у sysfs відображав реальний пристрій, шину чи драйвер у дереві `kobject`. Створення файлу вимагало опису структури `attribute` чи `attribute_group`.
3. **Непорушність ABI (Strict ABI stability):** головне правило Лінуса Торвальдса «Never break userspace» поширювалося на sysfs у повній мірі. Якщо файл з'явився у `/sys/devices/`, його шлях, ім'я та формат значення ставали публічним контрактом ядра. Вилучити чи перейменувати файл у sysfs означало потенційно зламати утиліти інфраструктури (на кшталт `udev` чи `systemd`).

Ця модель ідеально спрацювала для стабільної конфігурації системи, але створила нестерпне тертя для розробників драйверів під час активного відлагодження.

```
+-----------------------------------------------------------------------+
|                         ЕВОЛЮЦІЯ ВФС ЯДРА                             |
+-----------------------------------------------------------------------+
|  procfs (1991+)    | sysfs (2003)         | debugfs (2004)            |
|  Звалище даних    | Жорстке ABI          | Повний хаос і свобода     |
|  Без стандарту     | 1 файл = 1 значення  | Без гарантій стабільності |
+-----------------------------------------------------------------------+
```

## Дилема розробника у 2004 році

У 2004 році розробники складних підсистем ядра опинилися у глухому куті. Припустимо, розробник пише новий драйвер для бездротового адаптера WiFi (підсистема `mac80211`) або графічного прискорювача DRM/Intel. Під час пошуку помилок та оптимізації продуктивності йому потрібно щомиті оглядати десятки внутрішніх структур: стан кілець дескрипторів DMA, вміст понад сотні внутрішніх регістрів чипу, таблиці асоціації точок доступу та внутрішню статистику перемикання каналів.

Як експортувати ці дані?
- **Через sysfs?** За правилом «один файл — одне значення» створення 200 відлагоджувальних файлів вимагало б написання тисяч рядків boilerplate-коду C для кожної структури `kobj_attribute`. Понад те, коли розробник завтра змінить алгоритм і видалить непотрібний лічильник, він порушить ABI sysfs, і його патч буде відхилено мейнтейнерами.
- **Через procfs?** Патчі із додаванням нових каталогів у `/proc` блокувалися Лінусом Торвальдсом, оскільки procfs оголосили закритою для довільних відлагоджувальних експериментів.
- **Через printk?** Запис мільйонів рядків у лог ядра (`dmesg`) перевантажував кільцевий буфер журналювання та зрізав швидкодію системи до нуля.

Ядру бракувало «безпечного пісочничного майданчика» — файлової системи, де можна було б публікувати будь-яку діагностичну інформацію без жодних гарантій для користувацького простору.

## Маніфест Грега Кроа-Гарртмана та народження debugfs

У листопаді 2004 року під час розробки ядра Linux 2.6.10-rc3 Грег Кроа-Гарртман запропонував радикальне рішення — **debugfs**.

У своєму анонсі в списку розсилки Linux Kernel Mailing List (LKML) Грег написав, що debugfs створюється як проста, RAM-базована файлова система, призначена виключно для відлагодження, зі свідомим маніфестом: **«У debugfs немає жодних правил»**.

Головні засади debugfs, закладені при створенні:
1. **Відсутність гарантій ABI:** розробник ядра має повне право змінити формат файлу, перейменувати його чи видалити взагалі у будь-якій наступній версії ядра або навіть у наступному збірці. Жодна програма простору користувача не повинна будувати свою постійну роботу на файлах з debugfs.
2. **Мінімалістичний C API:** створення файлу для відлагодження змінної цілого типу вимагає лише одного виклику `debugfs_create_u32()`, без оголошення системних об'єктів `kobject`, атрибутів чи складних операцій VFS.
3. **Обмежений доступ:** оскільки файли можуть містити внутрішні вказівники пам'яті та дампи регістрів, точка монтування за замовчуванням (`/sys/kernel/debug`) має бути доступна лише користувачеві `root` (права `0700`).

Початковий C API debugfs був настільки лаконічним, що містив лише п'ять базових функцій: для створення каталогів, довільних файлів та простих типів даних (`u8`, `u16`, `u32`).

## Суперечки в LKML та боротьба з «сміттєзвалищем»

Прийняття debugfs у мейнстрім ядра не пройшло без гострих дискусій. Частина розробників (зокрема Крістоф Гельвіґ) висловлювали побоювання, що debugfs перетвориться на «помитник ледачих програмістів». Скептики стверджували, що розробники драйверів перестануть проектувати якісні та стабільні sysfs-інтерфейси, скидаючи увесь функціонал у debugfs під приводом «це просто для відлагодження».

Аби запобігти цьому, спільнота ядра ухвалила незаписане, але суворе правило розробки:
- Якщо файл потрібен для повсякденної роботи системного демона або конфігурації обладнання — він зобов'язаний жити в **sysfs** або реалізовуватися через **netlink/ioctl**.
- Якщо файл висвітлює внутрішній тимчасовий стан драйвера, використовується при розробці або для розслідування падінь у полі — його місце в **debugfs**.

Згодом цей поділ виправдав себе на 100%. Підсистеми DRM (Direct Rendering Manager для відеокарт AMD, Intel, Nvidia), бездротові стеки `mac80211`, регулятори плановика задач `sched`, інструменти аналізу пам'яті KMEMLEAK та KASAN отримали зручне вікно для експорту сотень кілобайтів діагностичних даних.

## Віокремлення tracefs та еволюція захисту (2015–2019)

З розвитком підсистеми трасування ядра (ftrace) під керівництвом Стівена Ростедта (Steven Rostedt) уся конфігурація трасувальників, точок пробудження (tracepoints) та подій тривалий час розміщувалася у каталозі `/sys/kernel/debug/tracing`. 

Однак до 2015 року стало зрозуміло, що трасування є фундаментальним інструментом моніторингу системи в продакшені, тоді як debugfs часто вимикається з міркувань безпеки. У версії Linux 3.19 (лютий 2015 року) Стівен Ростедт виокремив **tracefs** в окрему віртуальну файлову систему. Режим сумісності зберегли через автоматичне підмонтовування tracefs у `/sys/kernel/debug/tracing`, але тепер її можна монтувати незалежно у `/sys/kernel/tracing`.

Паралельно зростали вимоги до безпеки. Оскільки debugfs містила дампи фізичної пам'яті, внутрішні адреси ядерних структур (що дозволяло обходити захист KASLR) та важелі прямого запису в регістри пристроїв, вона стала улюбленою мішенню для експлойтів локального підвищення привілеїв (Local Privilege Escalation).

Це призвело до двох важливих етапів еволюції безпеки debugfs:
1. **Інтеграція з Kernel Lockdown (Linux 5.4, 2019):** при увімкненні механізму Lockdown у режимі `confidentiality` доступ до debugfs повністю блокується навіть для користувача `root`, аби унеможливити зчитування секретів ядра або модифікацію його коду через відлагоджувальні файли.
2. **Введення прапорців монтування ядра (Linux 5.7, 2020):** з'явився параметр завантаження ядра `debugfs=on|off|no-mount`, який дозволив адміністраторам повністю відключати ініціалізацію debugfs на продакшн-серверах.

Історія debugfs демонструє важливий архітектурний прагматизм ядра Linux: іноді свідомий відмова від жорстких рамок і правил є єдиним шляхом зберегти швидкість розробки та прозорість складної системи.
