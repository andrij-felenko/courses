# 📋 Довідник інтерфейсів підсистеми подій tracefs та макросів TRACE_EVENT

Підсистема статичних точок трасування ядра Linux надає дворівневий інтерфейс: внутрішній програмний API макросів препроцесора C для розробників ядра і модулів, а також файловий інтерфейс віртуальної файлової системи `tracefs` для діагностичних інструментів простору користувача. За замовчуванням `tracefs` монтується за шляхом `/sys/kernel/tracing/` (або за застарілим шляхом `/sys/kernel/debug/tracing/`).

Нижче наведено повну специфікацію файлових вузлів, двійкових структур записів, граматики фільтрів, синтаксису розширених hist-тригерів та внутрішнього API макросів ядра.

## 1. Ієрархія та призначення файлових вузлів подій

Кожна зареєстрована в ядрі статична точка трасування автоматично отримує власний підкаталог у дереві `/sys/kernel/tracing/events/<підсистема>/<подія>/`. Крім того, на кожному рівні ієрархії діють групові перемикачі.

| Шлях до файлового вузла | Режим | Призначення та семантика операцій |
| :--- | :--- | :--- |
| `events/enable` | R/W | Глобальне керування: запис `1` активує всі точки трасування всіх підсистем ядра; `0` — деактивує їх. Читання повертає `1` (якщо всі події увімкнено), `0` (якщо всі вимкнено) або `X` (якщо активна лише частина). |
| `events/<subsys>/enable` | R/W | Групове вмикання або вимикання всіх точок конкретної підсистеми (наприклад, `sched`, `net`, `block`, `syscalls`). |
| `events/<subsys>/filter` | R/W | Встановлення групового фільтра: предикат застосовується одночасно до всіх подій підсистеми, які містять зазначені у виразі поля. |
| `events/<subsys>/<event>/enable` | R/W | Активація (`1`) або зупинка (`0`) запису конкретної події. Зміна прапорця ініціює атомарний патчинг коду інструкції (Static Key NOP/JMP). |
| `events/<subsys>/<event>/filter` | R/W | Предикатний вираз фільтрації в просторі ядра. Події, що не відповідають умові, відкидаються до запису в кільцевий буфер. |
| `events/<subsys>/<event>/format` | RO | Повний опис структури двійкового запису події: зміщення полів, їхні розміри, наявність знака та рядок форматування для парсерів. |
| `events/<subsys>/<event>/id` | RO | Унікальний числовий ідентифікатор події (ціле число без знака), який передається у системний виклик `perf_event_open()`. |
| `events/<subsys>/<event>/trigger` | R/W | Реєстрація активних дій (тригерів), що спрацьовують при виникненні події: знімки пам'яті, стекові сліди, увімкнення інших точок, гістограми. |
| `events/<subsys>/<event>/hist` | RO | Текстове відображення поточної агрегованої хеш-таблиці та лічильників для активного hist-тригера. |

## 2. Структура файлу `format` та розташування полів у пам'яті

Файл `format` є машинно-читабельним контрактом, який дозволяє утилітам простору користувача декодувати сирі байти з кільцевого буфера ядра без необхідності компіляції із заголовками поточної версії ядра.

Запис події завжди складається з двох послідовних частин:
1. **Загальний заголовок ядра (`common_*`):** присутній у абсолютно всіх подіях ftrace і містить метадані контексту виконання процесора в момент генерації події.
2. **Корисне навантаження події:** поля, визначені автором конкретної точки трасування в макросі `TP_STRUCT__entry`.

```text
name: sched_switch
ID: 314
format:
	field:unsigned short common_type;	offset:0;	size:2;	signed:0;
	field:unsigned char common_flags;	offset:2;	size:1;	signed:0;
	field:unsigned char common_preempt_count;	offset:3;	size:1;	signed:0;
	field:int common_pid;	offset:4;	size:4;	signed:1;

	field:char prev_comm[16];	offset:8;	size:16;	signed:0;
	field:pid_t prev_pid;	offset:24;	size:4;	signed:1;
	field:int prev_prio;	offset:28;	size:4;	signed:1;
	field:long prev_state;	offset:32;	size:8;	signed:1;
	field:char next_comm[16];	offset:40;	size:16;	signed:0;
	field:pid_t next_pid;	offset:56;	size:4;	signed:1;
	field:int next_prio;	offset:60;	size:4;	signed:1;

print fmt: "prev_comm=%s prev_pid=%d prev_prio=%d prev_state=%s ==> next_comm=%s next_pid=%d next_prio=%d", REC->prev_comm, REC->prev_pid, REC->prev_prio, ...
```

### Призначення полів заголовка `common_*`

* `common_type`: 16-бітний числовий ID типу події. Дозволяє парсеру буфера ftrace визначити, яка саме подія міститься в черговому двійковому блоці.
* `common_flags`: 8-бітова маска стану процесора.
* `common_preempt_count`: значення лічильника витіснення поточного ядра. Дозволяє виявити, чи виконувався код із заблокованим витісненням або всередині критичної секції RCU.
* `common_pid`: числовий ідентифікатор завдання (PID / TGID) поточного виконуваного потоку на поточному ядрі CPU.

### Бітові прапорці стану процесора `common_flags`

Поле `common_flags` кодує апаратний та програмний контекст переривань:

* `0x01` (`TRACE_FLAG_IRQS_OFF`): локальні апаратні переривання ядра були заблоковані (`local_irq_disable`).
* `0x02` (`TRACE_FLAG_IRQS_NOSUPPORT`): апаратна архітектура не підтримує швидку перевірку стану переривань.
* `0x04` (`TRACE_FLAG_NEED_RESCHED`): встановлено прапорець вимоги виклику планувальника завдань (`TIF_NEED_RESCHED`).
* `0x08` (`TRACE_FLAG_HARDIRQ`): код точки трасування виконується всередині обробника апаратного переривання (Top Half).
* `0x10` (`TRACE_FLAG_SOFTIRQ`): код виконується всередині обробника програмного переривання (SoftIRQ, Tasklet або Timer).
* `0x20` (`TRACE_FLAG_PREEMPT_RESCHED`): запит перепланування викликано в контексті коду ядра з підтримкою витіснення (`PREEMPT_RT` або конфігурація `PREEMPT`).
* `0x40` (`TRACE_FLAG_NMI`): виконання відбувається всередині немаскованого переривання (Non-Maskable Interrupt).

### Динамічні поля змінної довжини (`__data_loc`)

Якщо подія містить рядки змінної довжини або динамічні масиви (`__string`, `__dynamic_array`), у статичній секції запису виділяється 32-бітне службове поле `__data_loc_<name>`.
Це 4-байтове число кодує два 16-бітних значення:
* **Молодші 16 біт (`val & 0xFFFF`):** байтове зміщення від початку всього запису події до місця, де лежить нуль-термінований рядок або масив.
* **Старші 16 біт (`(val >> 16) & 0xFFFF`):** довжина динамічних даних у байтах.

Сам динамічний вміст розміщується наприкінці запису події, що забезпечує компактне пакування даних у кільцевому буфері без резервування надлишкової пам'яті.

## 3. Граматика та оператори двигуна фільтрації (`filter`)

Двигун фільтрації подій ftrace обчислює предикати безпосередньо в просторі ядра перед резервуванням пам'яті в кільцевому буфері. Якщо фільтр не збігається, запис не здійснюється, що мінімізує вплив трасування на продуктивність.

### Таблиця операторів фільтрації

| Оператор | Типи даних | Приклад використання | Опис поведінки |
| :--- | :--- | :--- | :--- |
| `==` | Числа, рядки | `prev_pid == 1024` або `prev_comm == "worker"` | Точна рівність значень. Рядки обов'язково беруться у подвійні лапки. |
| `!=` | Числа, рядки | `common_pid != 0` | Нерівність значень. |
| `<`, `<=` | Числа | `prev_prio <= 100` | Числове порівняння «менше» / «менше або дорівнює». |
| `>`, `>=` | Числа | `bytes_req >= 4096` | Числове порівняння «більше» / «більше або дорівнює». |
| `&` | Цілі числа | `(prev_state & 1) != 0` | Побітове «І». Використовується для перевірки бітових масок станів процесів та дескрипторів сокетів. |
| `~` | Рядки | `next_comm ~ "kworker/*"` | Зіставлення за маскою (glob matching). Підтримує символ підстановки `*`. |
| `!~` | Рядки | `next_comm !~ "systemd*"` | Заперечення збігу за маскою. |
| `&&` | Логічні вирази | `prev_pid > 100 && prev_prio < 120` | Логічна кон'юнкція (І). |
| `\|\|` | Логічні вирази | `common_pid == 1 \|\| common_pid == 2` | Логічна диз'юнкція (АБО). |
| `( )` | Вирази | `(prev_pid == 0 \|\| prev_pid == 1) && prev_prio > 50` | Групування та визначення пріоритету операцій. |

Для очищення фільтра достатньо записати символ `0` у файл: `echo 0 > filter`. Запис некоректного синтаксису призводить до повернення системної помилки `EINVAL` (Invalid argument), а детальне повідомлення про помилку записується у сам файл `filter`.

## 4. Специфікація та команди тригерів подій (`trigger`)

Тригери розширюють функціональність точок трасування, дозволяючи виконувати дії при кожному проходженні фільтра без передачі даних у простір користувача.

### Базові команди

* `traceon` / `traceoff`: керування глобальним записом у кільцевий буфер. Можна вказати лічильник спрацьовувань: `echo 'traceoff:3' > trigger` (вимкнути запис після 3 подій).
* `snapshot`: атомарно копіює поточний вміст кільцевого буфера у статичний буфер `snapshot` і заморожує його для подальшого аналізу.
* `stacktrace`: зберігає трасування стека викликів ядра (kernel backtrace) для кожної події.
* `enable_event:<subsys>:<event>` / `disable_event:<subsys>:<event>`: динамічно активує або деактивує іншу точку трасування.

### Розширені Hist-тригери (Histogram Triggers)

Hist-тригери створюють у пам'яті ядра асоціативні масиви для агрегації числових даних у реальному часі.

```text
hist:keys=<field1>[,<field2>...]:values=<val1>...[:sort=<key|val>...][:size=<entries>][:pause][:continue][:clear]
```

#### Модифікатори полів у hist-тригерах

Модифікатори додаються через крапку до імені поля:

* `.hex`: форматування числових адрес у шістнадцятковому вигляді.
* `.sym`: перетворення адреси в назву функції ядра за допомогою внутрішньої таблиці `kallsyms`.
* `.sym-offset`: трансляція адреси у вигляд `назва_функції+зміщення/розмір`.
* `.execname`: відображення імені процесу замість числового PID.
* `.syscall`: трансляція номера системного виклику в його назву (наприклад, `0` → `sys_read`).
* `.log2`: логарифмічне квантування зі ступенем двійки. Створює логарифмічні кошики (buckets) для аналізу латентності.
* `.buckets=<N>`: лінійне розбиття значень на інтервали розміром `N`.
* `.usecs`: автоматичне масштабування часових міток із наносекунд у мікросекунди.

#### Розширені дії (Actions)

* `onmatch(<subsys>.<event>).trace(<synth_event>, <params>...)`: генерація синтетичної події при збігу ключів між двома точками.
* `onmax(<field>).save(<fields>...)`: збереження значень полів запису, в якому зафіксовано абсолютний максимум вказаної метрики.
* `onchange(<field>).save(<fields>...)`: збереження параметрів при будь-якій зміні значення вказаного поля.

## 5. Внутрішній C-макрос API ядра для визначення подій

Для створення нової статичної точки трасування використовується сімейство макросів у `include/linux/tracepoint.h` та `include/trace/define_trace.h`.

```c
TRACE_EVENT(name,
    TP_PROTO(proto),
    TP_ARGS(args),
    TP_STRUCT__entry(fields),
    TP_fast_assign(assignments),
    TP_printk(format, args)
);
```

### Допоміжні макроси визначення структури `TP_STRUCT__entry`

* `__field(type, name)`: просте скалярне поле фіксованого розміру (наприклад, `int`, `u64`, `pid_t`).
* `__array(type, name, len)`: масив фіксованої довжини `len` (наприклад, `char comm[16]`).
* `__string(name, src)`: рядок змінної довжини, що виділяється у динамічній секції `__data_loc`.
* `__dynamic_array(type, name, len)`: динамічний масив елементів типу `type` довжиною `len`.

### Допоміжні макроси блоку `TP_fast_assign`

* `__entry->name = val`: пряме присвоєння значень скалярних полів.
* `__assign_str(name, src)`: безпечне копіювання рядка в область динамічних даних `__data_loc`.
* `__assign_str_len(name, src, len)`: копіювання рядка обмеженої довжини.
* `__get_str(name)`: отримання покажчика на динамічний рядок всередині `TP_printk`.

## 6. Програмне парсування структури подій з простору користувача

Для універсальних утиліт моніторингу важливо динамічно вичитувати розміри та зміщення полів подій безпосередньо з файлу `format`.

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

void parse_event_format(const char *path) {
    FILE *f = fopen(path, "re");
    if (!f) {
        perror("Помилка відкриття format файлу");
        return;
    }

    char line[256];
    printf("Розбір структури події: %s\n", path);
    while (fgets(line, sizeof(line), f)) {
        char field_name[64];
        int offset = 0, size = 0, is_signed = 0;
        
        if (strstr(line, "field:") && !strstr(line, "common_")) {
            char *field_start = strstr(line, "field:") + 6;
            char *semicolon = strchr(field_start, ';');
            if (semicolon) {
                *semicolon = '\0';
                sscanf(semicolon + 1, "\toffset:%d;\tsize:%d;\tsigned:%d;",
                       &offset, &size, &is_signed);
                printf("  Поле: %-25s | Зміщення: %3d | Розмір: %2d байт | Знак: %d\n",
                       field_start, offset, size, is_signed);
            }
        }
    }
    fclose(f);
}

int main(void) {
    parse_event_format("/sys/kernel/tracing/events/sched/sched_switch/format");
    return 0;
}
```

```cpp
#include <iostream>
#include <fstream>
#include <string>
#include <string_view>
#include <vector>
#include <regex>
#include <filesystem>

namespace fs = std::filesystem;

struct EventField {
    std::string declaration;
    int offset{0};
    int size{0};
    bool is_signed{false};
};

void parse_event_format(const fs::path& format_path) {
    std::ifstream file(format_path);
    if (!file.is_open()) {
        std::cerr << "Не вдалося відкрити: " << format_path << '\n';
        return;
    }

    std::cout << "Розбір структури події: " << format_path.string() << '\n';
    
    // field:char next_comm[16];\toffset:40;\tsize:16;\tsigned:0;
    std::regex field_regex(R"(field:([^;]+);\s+offset:(\d+);\s+size:(\d+);\s+signed:(\d+);)");
    std::string line;

    while (std::getline(file, line)) {
        if (line.find("common_") != std::string::npos) {
            continue; // Пропускаємо загальні службові поля заголовка
        }

        std::smatch match;
        if (std::regex_search(line, match, field_regex)) {
            EventField field{
                .declaration = match[1].str(),
                .offset = std::stoi(match[2].str()),
                .size = std::stoi(match[3].str()),
                .is_signed = (match[4].str() == "1")
            };

            std::cout << "  Поле: " << field.declaration
                      << " | Зміщення: " << field.offset
                      << " | Розмір: " << field.size << " байт"
                      << " | Знак: " << (field.is_signed ? "signed" : "unsigned") << '\n';
        }
    }
}

int main() {
    parse_event_format("/sys/kernel/tracing/events/sched/sched_switch/format");
    return 0;
}
```
