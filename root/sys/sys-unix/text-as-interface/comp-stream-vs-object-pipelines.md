# ⚖️ Парадигми міжпроцесної взаємодії: потік байтів Unix, об'єкти PowerShell та структурований JSON

Міжпроцесна взаємодія в середовищі операційної системи визначає спосіб декомпозиції складних завдань на простіші компоненти. В історії системної архітектури сформувалися три фундаментальні парадигми передачі даних між утилітами командного рядка:

1. **Сирий байтовий потік (Raw Text Stream) Unix:** Програми обмінюються неструктурованими масивами символів, де логічні межі задаються конвенційними байтами-роздільниками (`\n`, `\t`, `:`, `\0`).
2. **Об'єктний конвеєр (Object Pipeline) PowerShell:** Програми передають живі посилання на типізовані екземпляри класів середовища виконання .NET (`PSObject`), зберігаючи повні метадані про типи, властивості та методи.
3. **Структурований текстовий потік (Structured Stream / JSON Lines):** Гібридна модель, де кожен рядок являє собою валідний серіалізований документ (JSON, YAML, MessagePack), що поєднує універсальність тексту з машинною структурованістю.

---

## Порівняльна таблиця архітектурних характеристик

| Критерій | Сирий текст Unix (POSIX CLI) | Об'єкти PowerShell (.NET) | Структурований JSONL / ndjson |
|---|---|---|---|
| **Модель даних** | Нетипізований масив байтів (`char*`) | Типізовані об'єкти (`System.Object`) | Ієрархічні структури (ключ-значення, масиви) |
| **Перевірка типів** | Відсутня (все є рядком) | Сувора під час виконання (Runtime Typing) | Слабкі типи JSON (string, number, bool, null) |
| **Зв'язність компонентів** | Абсолютно слабка (Loose Coupling) | Сильна прив'язка до CLR/.NET | Слабка, залежить від схеми ключів |
| **Мовна незалежність** | Повна (будь-яка мова, C, Go, Rust, Python) | Обмежена екосистемою .NET | Повна (JSON підтримується всіма мовами) |
| **Споживання пам'яті** | `O(1)` — фіксований буфер під один рядок | `O(N)` — накладні витрати на об'єкти та збирач сміття (GC) | `O(1)` на рівні рядка, `O(M)` на розбір об'єкта |
| **Втрати на серіалізацію** | Мінімальні (байти пишуться напряму) | Нульові в межах процесу; високі при IPC/SSH (CLIXML) | Середні (парсинг JSON на кожному кроці конвеєра) |
| **Налагодження людиною** | Тривіальне (`cat`, `less`, `head`, `tee`) | Вимагає форматування (`Format-Table`, `Out-String`) | Легке за допомогою утиліт форматування (`jq .`) |
| **Безпека пробілів/спецсимволів** | Вразлива (потребує `find -print0 \| xargs -0`) | Абсолютна (властивості інкапсульовані в об'єкт) | Абсолютна (рядки екрануються за стандартом JSON) |

## 1. Сирий текст Unix: максимальна декомпозиція та нульові залежності

У класичній моделі Unix ядро розглядає конвеєр як кільцевий буфер пам'яті (`pipe_buffer`), що передає байти від дескриптора `stdout` першого процесу до дескриптора `stdin` другого процесу.

```
+-----------+    байтовий потік (ASCII/UTF-8)    +-----------+
|  ps aux   | ─────────────────────────────────> | grep root |
+-----------+                                    +-----------+
```

### Переваги моделі:
- **Універсальний спільний знаменник:** Будь-яка програма, написана на асемблері, C, Python чи Shell, може читати та писати в потік без потреби в спільних бібліотеках типів чи спільних віртуальних машинах.
- **Потоковість без затримок:** Обробка починається з першого отриманого рядка. Утиліті `grep` не потрібно чекати, поки процес-генератор завершить роботу та згенерує весь масив даних.
- **Стабільність на десятиліття:** Формат виводу системних утиліт не змінюється десятиліттями, що забезпечує функціонування скриптів, написаних 30 років тому.

### Недоліки та слабкі місця:
- **Ламкість синтаксичного аналізу (Fragile Parsing):** Зміна форматування (додавання додаткового пробілу, нового стовпця або локалізованого заголовка) може зламати регулярний вираз або скрипт `awk`.
- **Втрата типу:** Числа, адреси пам'яті та часові мітки передаються як текст. Програма-отримувач змушена щоразу виконувати зворотне перетворення рядка в число (`atoi`, `strtol`), що створює зайві накладні витрати CPU.

## 2. Об'єктний конвеєр PowerShell: типобезпека та багатий стан

Розроблена Джеффрі Сновером (Jeffrey Snover) архітектура PowerShell відмовилася від тексту на користь об'єктної передачі в межах загального середовища виконання .NET Common Language Runtime (CLR).

```powershell
# Отримання списку процесів та фільтрація без парсингу тексту
Get-Process | Where-Object { $_.WorkingSet64 -gt 100MB } | Select-Object -Property Id, ProcessName, CPU
```

У цьому прикладі команда `Get-Process` повертає колекцію об'єктів типу `System.Diagnostics.Process`. Наступний командлет `Where-Object` звертається напряму до числової властивості `.WorkingSet64`, яка є цілим числом типу `Int64`. Жоден рядок тексту не парситься, а вирівнювання колонок та одиниці виміру не впливають на результат обчислень.

```
+---------------+      об'єкти .NET (PSObject)      +------------------+
|  Get-Process  | ────────────────────────────────> |   Where-Object   |
+---------------+                                   +------------------+
```

### Переваги моделі:
- **Абсолютна надійність фільтрації:** Відсутність помилок розщеплення слів (word splitting) або спотворення даних через пробіли в іменах файлів та процесів.
- **Самодокументування та автодоповнення:** Інженер у командному рядку може дослідити структуру об'єкта через `Get-Member` і отримати список усіх доступних полів, властивостей та методів.
- **Багата семантика типів:** Можливість прямої маніпуляції об'єктами дат (`DateTime`), IP-адрес (`IPAddress`) та розмірів пам'яті без ручної конвертації.

### Межі застосування та ціна архітектури:
- **Прив'язка до важкого середовища:** Кожна утиліта повинна виконуватися всередині середовища .NET. Передати живий об'єкт класичній скомпільованій програмі на C або Go неможливо без серіалізації.
- **Високі накладні витрати:** Створення сотень тисяч об'єктів у керованій купі пам'яті створює тиск на збирач сміття (Garbage Collector) і споживає в десятки разів більше оперативної пам'яті, ніж байтовий потік Unix.
- **Проблема міжхостової взаємодії:** При передачі через мережу (WinRM/SSH) об'єкти десеріалізуються у статичні «знекровлені» зліпки властивостей (CLIXML), втрачаючи методи та динамічний зв'язок з системою.

## 3. Структуровані текстові потоки: сучасний компроміс

Для подолання недоліків обох світів у сучасних розподілених системах та хмарних середовищах набув поширення формат **JSON Lines (`ndjson` / `jsonl`)**.

Кожен окремий рядок є повноцінним документом JSON, розділеним звичайним символом переносу рядка `\n`. Це дозволяє зберегти як потокову природу Unix-конвеєрів, так і багату структуру об'єктних моделей.

```bash
# Потокова обробка подій Docker у форматі JSON за допомогою jq
docker events --format '{{json .}}' | jq -r 'select(.Action == "start") | .from'
```

Також з'явилися інструменти-транслятори, такі як `jc` (JSON CLI), що перетворюють вивід класичних утиліт Unix (`ls`, `ps`, `df`, `dig`, `ip`) у валідний JSON:

```bash
# Перетворення виводу df у структурований JSON та вибірка залишку місця
df -h | jc --df | jq '.[0].available'
```

### Продуктивність та нові інструменти: Nushell та SIMD-парсинг

Розвиток сучасного системного інструментарію привів до появи оболонок нового покоління, таких як **Nushell** (написаної на мові Rust). Вона використовує типізовані таблиці як базову абстракцію конвеєра, поєднуючи швидкість скомпільованого коду без важкого збирача сміття з безпекою об'єктних полів:

```bash
# Фільтрація процесів у Nushell без зовнішніх утиліт
ps | where cpu > 10 | sort-by mem --reverse
```

Паралельно поява алгоритмів швидкісного векторного розбору JSON (зокрема бібліотеки `simdjson`) дозволила обробляти гігабайти структурованого тексту на секунду на сучасних ядрах x86-64 та ARM64, усунувши історичний розрив у продуктивності між бінарними та текстовими форматами.

## Інженерний підсумок вибору парадигми

- **Unix Text Stream** залишається неперевершеним стандартом для високоефективного, низькорівневого та довговічного системного програмування, де важливі мінімальне споживання ресурсів та повна мовна незалежність.
- **PowerShell Objects** забезпечують найвищу швидкість та безпеку розробки складних сценаріїв адміністрування у межах керованої інфраструктури Windows.
- **JSON Lines та структуровані CLI-інструменти** виступають сучасним стандартом інтеграції мікросервісів, контейнерних платформ та систем збору метрик і журналів, поєднуючи універсальність потоку з точністю схеми даних.
