# 📋 Виклики передачі без копіювання: підписи, зсуви, помилки

Контракт п'яти системних викликів, які переносять байти між дескрипторами без буфера в програмі — `sendfile`, `splice`, `tee`, `vmsplice`, `copy_file_range`: прототипи, правила зсувів, дозволені пари дескрипторів, прапорці й коди помилок. Версії ядра вказано там, де поведінка мінялася, — а мінялася вона в кожного з п'яти.

## Спільна форма

Усі п'ять мають однаковий силует: два кінці, до двох зсувів, скільки байтів і прапорці. Повертають `ssize_t` — кількість **реально** перенесених байтів, або −1 і `errno`.

| Виклик | Заголовок | Макрос | З ядра | З glibc |
|---|---|---|---|---|
| `sendfile` | `<sys/sendfile.h>` | — | 2.2 | 2.1 |
| `splice` | `<fcntl.h>` | `_GNU_SOURCE` | 2.6.17 | 2.5 |
| `tee` | `<fcntl.h>` | `_GNU_SOURCE` | 2.6.17 | 2.5 |
| `vmsplice` | `<fcntl.h>` | `_GNU_SOURCE` | 2.6.17 | 2.5 |
| `copy_file_range` | `<unistd.h>` | `_GNU_SOURCE` | 4.5 | 2.27 |

Перше правило, спільне для всіх: **менше за замовлене — це не помилка**. Черга сокета скінченна, місткість каналу скінченна, і кожен із цих викликів повертається з тим, що влізло. Усі вони живуть у циклі.

Друге правило — про зсув, і воно однакове скрізь, де зсув узагалі є. Передали `NULL` — виклик бере й посуває власну позицію дескриптора. Передали вказівник — виклик читає з указаного місця, **сам** посуває вашу змінну на кількість перенесеного, а позицію дескриптора не чіпає взагалі.

## Що з чим взагалі можна з'єднати

Три жорсткі обмеження задають усю картину. `sendfile` вимагає, щоб джерело вміло віддати сторінки через відображення в пам'ять — на практиці це звичайний файл ([відображення файлу в пам'ять](root:sys-unix/mmap-model) — механізм, який робить сторінки файлу видимими як пам'ять; сокет і канал його не мають, тому джерелом бути не можуть). `splice` вимагає, щоб **хоча б один** із двох дескрипторів був каналом. `copy_file_range` вимагає, щоб обидва були звичайними файлами.

| Що переносимо | Чим | Скільки викликів на порцію |
|---|---|---|
| звичайний файл → сокет | `sendfile` | 1 |
| звичайний файл → звичайний файл | `copy_file_range` | 1, часто без вводу-виводу взагалі |
| звичайний файл → будь-який файл | `sendfile` (з 2.6.33) | 1 |
| звичайний файл → канал | `splice` | 1 |
| канал → сокет або файл | `splice` | 1 |
| сокет → сокет, сокет → файл | `splice` через власний канал | 2 |
| канал → канал, з дублюванням | `tee` | 1 |
| пам'ять програми → канал | `vmsplice` | 1 |
| сокет → пам'ять програми | нічим із цього списку | — |

Останній рядок не помилка: зворотного шляху без копії тут немає. Прочитати з сокета в свою пам'ять можна лише `read`/`recv`, а `vmsplice` у бік читання, попри симетричний вигляд, дані просто копіює.

## sendfile

```c
#include <sys/sendfile.h>

ssize_t sendfile(int out_fd, int in_fd, off_t *offset, size_t count);
```

Порядок як у `memcpy`: спершу куди, потім звідки. `in_fd` мусить бути відкритий на читання й підтримувати відображення в пам'ять; сокет джерелом бути не може. `out_fd` до ядра 2.6.33 мусив бути сокетом, після — будь-який файл. З ядра 5.12, коли `out_fd` виявляється каналом, ядро виконує виклик через `splice`.

За один виклик передається щонайбільше **0x7ffff000 байтів** (2 147 479 552) — тобто навіть файл на 4 ГіБ теоретично не віддати менш ніж трьома викликами.

| `errno` | Коли |
|---|---|
| `EAGAIN` | сокет неблокуючий, черга передачі повна |
| `EBADF` | `in_fd` не на читання або `out_fd` не на запис |
| `EINVAL` | `in_fd` не вміє віддати сторінки; на `out_fd` стоїть `O_APPEND`; від'ємний `count` |
| `EIO` | помилка читання з `in_fd` |
| `EOVERFLOW` | `count` виходить за межі розмірів файлу |
| `ESPIPE` | `offset` не `NULL`, а `in_fd` не підтримує позиціювання |
| `EFAULT`, `ENOMEM` | зіпсована адреса, брак пам'яті |

`EINVAL` і `ENOSYS` тут — не привід рвати з'єднання, а сигнал перейти на `read`/`write`: та сама програма може роздавати файли з різних файлових систем, і не кожна вміє віддавати сторінки.

На 32-бітних збірках `off_t` за замовчуванням теж 32-бітний, і файл понад 2 ГіБ дасть `EOVERFLOW` ([великі файли](root:sys-unix/large-file-support) — 64-бітні варіанти викликів і макрос `_FILE_OFFSET_BITS=64`, який перемикає на них увесь код).

Прототип **не переносний**. У FreeBSD і macOS це `int sendfile(int fd, int s, off_t offset, size_t nbytes, struct sf_hdtr *hdtr, off_t *sbytes, int flags)` — файл першим, сокет другим, тобто рівно навпаки до Linux, плюс окремі поля для заголовка й хвоста та повернений `int` замість кількості байтів. Переносний код не пише один виклик на обидві системи: він пише два під `#ifdef`.

## splice

```c
#define _GNU_SOURCE
#include <fcntl.h>

ssize_t splice(int fd_in, off_t *off_in, int fd_out, off_t *off_out,
               size_t len, unsigned int flags);
```

Хоча б один кінець мусить бути каналом; з ядра 2.6.31 обидва можуть бути каналами, але не одним і тим самим. Для кінця, який є каналом, відповідний зсув мусить бути `NULL` — інакше `ESPIPE`.

| Прапорець | Що робить |
|---|---|
| `SPLICE_F_MOVE` | **нічого** з ядра 2.6.21; лишили заради сумісності |
| `SPLICE_F_NONBLOCK` | не засинати на каналі; на самі файли й сокети не діє — їм потрібен `O_NONBLOCK` |
| `SPLICE_F_MORE` | підказка «далі буде ще»; для сокета те саме, що `MSG_MORE` |
| `SPLICE_F_GIFT` | для `splice` не вживається, лише для `vmsplice` |

Помилки: `EAGAIN` (просили не блокувати, а зараз нічого зробити не можна), `EBADF` (дескриптор недійсний або відкритий не в той бік), `EINVAL` (жоден кінець не канал; обидва кінці — той самий канал; файлова система не підтримує операції; `O_APPEND` на `fd_out`; зсув для пристрою, який не вміє позиціюватися), `ESPIPE`, `ENOMEM`.

Практичну стелю однієї порції задає не `len`, а місткість каналу ([канали](root:sys-unix/pipe-and-fifo) — пара дескрипторів із кільцем записів у ядрі; місткість читається й міняється через `fcntl`):

```
типова місткість каналу       = 16 сторінок × 4096 = 65536 байтів
змінюється                    = fcntl(fd, F_SETPIPE_SZ, розмір)
стеля для непривілейованого   = /proc/sys/fs/pipe-max-size = 1048576
```

`SPLICE_F_NONBLOCK` і `O_NONBLOCK` — це дві різні речі, і плутанина між ними дає найдовші розслідування. Перший стосується лише каналу, другий — самого файлу чи сокета ([блокуючий і неблокуючий режим](root:sys-unix/blocking-and-nonblocking) — з `O_NONBLOCK` виклик не засинає, а повертає −1 з `errno == EAGAIN`). До того ж на звичайні файли `O_NONBLOCK` не діє взагалі: якщо потрібних сторінок немає в кеші, виклик чекатиме на диск незалежно від будь-яких прапорців.

Між цими двома викликами немає розриву в реалізації. `sendfile` у ядрі виконується функцією `do_splice_direct`, яка бере канал із кешу самого процесу й проганяє дані крізь нього — тобто робить рівно те, що зробила б пара `splice` у програмі. Різниця лише в кількості перетинів межі: один системний виклик замість двох. Тож обирають між ними не за швидкістю переміщення сторінок — вона однакова, — а за тим, чи вписується пара дескрипторів у жорсткі вимоги `sendfile`.

## tee і vmsplice

```c
/* заголовок і макрос ті самі, що в splice */

ssize_t tee(int fd_in, int fd_out, size_t len, unsigned int flags);

ssize_t vmsplice(int fd, const struct iovec *iov, size_t nr_segs,
                 unsigned int flags);
```

`tee` дублює записи між двома **каналами** — обидва кінці мусять бути каналами й різними каналами. Дані при цьому лишаються й у джерелі: це не переміщення, а розгалуження потоку. Прапорці приймає ті самі, що й `splice`, але діє лише `SPLICE_F_NONBLOCK`. Помилки: `EAGAIN`, `EINVAL`, `ENOMEM`.

`vmsplice` працює тільки з каналом і тільки в один бік по-справжньому. Канал, відкритий на запис: сторінки програми, описані масивом `iovec`, підшиваються в канал без копії. Канал, відкритий на читання: дані з каналу **копіюються** в пам'ять програми — симетричний вигляд, несиметрична ціна. Кількість елементів масиву обмежена `IOV_MAX` із `<limits.h>` (нині 1024).

`SPLICE_F_GIFT` віддає сторінки ядру назовсім: після цього програма не має права їх чіпати ніколи, бо кеш сторінок і те, що на диску, розійдуться. Адреса й довжина мусять бути вирівняні на сторінку, інакше `EINVAL`. Помилки: `EAGAIN`, `EBADF` (дескриптор не канал), `EINVAL`, `ENOMEM`.

## copy_file_range

```c
#define _GNU_SOURCE
#include <unistd.h>

ssize_t copy_file_range(int fd_in, off_t *off_in, int fd_out, off_t *off_out,
                        size_t len, unsigned int flags);
```

Єдиний із п'яти, що не тільки прибирає копію, а може прибрати й сам ввід-вивід: файлова система вправі виконати запит посиланням на ті самі блоки замість переписування ([копії через посилання на блоки](root:sys-unix/reflink-copies) — два inode ділять одні блоки на диску, а розходяться лише при записі). Мережеві файлові системи натомість перекладають копіювання на сервер. `flags` мусить бути рівно `0`.

| `errno` | Коли |
|---|---|
| `EINVAL` | `flags` не нуль; діапазони перекриваються в межах одного файлу; кінець не є звичайним файлом |
| `EBADF` | дескриптор відкритий не в той бік або на `fd_out` стоїть `O_APPEND` |
| `EXDEV` | до 5.3 — різні файлові системи; з 5.19 — різні **типи** файлових систем |
| `EOPNOTSUPP` | з 5.19: файлова система не підтримує операції |
| `EISDIR`, `ETXTBSY` | кінець — каталог або активний файл підкачки |
| `EPERM`, `ENOSPC`, `EFBIG`, `EOVERFLOW`, `EIO`, `ENOMEM` | незмінний файл, брак місця, перевищення стелі розміру, ввід-вивід, пам'ять |

Версійна історія тут важить більше, ніж зазвичай. glibc 2.27–2.29 мала запасну реалізацію в просторі користувача, тож на старому ядрі виклик просто працював повільно; з glibc 2.30 її прибрали, і без підтримки ядра він повертає `ENOSYS`. Ядро 5.3 дозволило копіювання між різними файловими системами, а 5.19 звузило дозвіл до однакових типів. Тому запасний шлях через звичайне читання-запис тут обов'язковий, а не бажаний.

## Нуль у поверненому значенні

Найпідступніша частина контракту: нуль означає в кожного свою річ, і скрізь його треба опрацьовувати окремою гілкою. Помилки в `errno` при цьому немає — там лишається сміття від попереднього виклику, тож перевіряти `errno` після нуля марно.

| Виклик | Що означає повернений `0` |
|---|---|
| `sendfile`, `copy_file_range` | джерело вичерпано: зсув уже на кінці файлу або далі |
| `splice` | кінець вхідного потоку; якщо джерело — канал, то ще й «писарів у нього більше немає» |
| `tee` | даних зараз немає, і чекати немає сенсу: у джерела не лишилося писарів |
| `vmsplice` | нічого не перенесено |

Найчастіша жертва — цикл, який рахує залишок від розміру, узятого зі `stat` на початку: варто комусь урізати файл посеред віддачі, і умова «віддано менше за розмір» лишається істинною назавжди при незмінно нульовому поверненні.

## Мінімальний робочий виклик

Копіювання файлу цілком, із правильним обліком зсуву й запасним шляхом:

```c
#define _GNU_SOURCE
#include <unistd.h>
#include <errno.h>

/* 1 — скопійовано, 0 — виклик недоступний тут, −1 — помилка */
int copy_whole(int in, int out, off_t size)
{
    off_t off_in = 0, off_out = 0;

    while (size > 0) {
        ssize_t n = copy_file_range(in, &off_in, out, &off_out,
                                    (size_t)size, 0);
        if (n > 0) {
            size -= n;               /* зсуви ядро посунуло само */
            continue;
        }
        if (n == 0)
            return -1;               /* файл зрізали під нами */
        if (errno == EINTR)
            continue;
        if (errno == EXDEV || errno == EOPNOTSUPP ||
            errno == ENOSYS || errno == EINVAL)
            return 0;                /* тут не працює — на read/write */
        return -1;
    }
    return 1;
}
```

Три деталі роблять цей код правильним. Після успіху немає `off_in += n` — ядро вже посунуло обидві змінні, і додавання вручну дало б подвійний облік. Нуль має власну гілку, бо за таблицею вище він означає вичерпане джерело, а не помилку, — і в `errno` йому шукати нічого. І чотири «помилки» останньої гілки насправді означають одне: цей виклик тут не застосовний, копіювати треба звичайним способом — не рвати роботу, а змінити спосіб.
