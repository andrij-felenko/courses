# 📜 Еволюція таблиць символів ядра Linux: від System.map до kallsyms

У перших версіях Linux 1990-х років ядро не зберігало жодних імен функцій у пам'яті RAM. Еволюція від статичного текстового файлу `System.map` до вбудованого стисненого масиву `kallsyms` відображає фундаментальні зміни в вимогах до автономності, безпеки та продуктивності операційної системи.

---

## 1. Ера статичних карт: System.map та демон klogd (1991–2003)

На початку існування операційної системи Linux (версії від 0.99 до серії 2.4) ядро було розроблене максимально компактним. Будь-який додатковий кілобайт пам'яті RAM у 1990-х роках мав величезне значення для продуктивності персональних комп'ютерів. Тому ранній Linux не зберігав імена функцій чи змінних всередині зкомпільованого образу ядра (`vmlinux` або `vmlinuz`). 

Коли у процесі виконання ядра виникала помилка (дискримінація покажчика, розіменування `NULL` чи апаратне переривання збою), ядро виводило у кільцевий буфер `dmesg` так званий дамп сухих адрес:

```
Oops: 0000 [#1]
CPU: 0
EIP: 0010:[<c0114a80>]
EAX: c0234000 EBX: 00000000 ECX: c0114a80 EDX: c0248a00
```

Для системного адміністратора або розробника адреса `0xc0114a80` не несла жодної інформації без контексту. Щоб перетворити цю адресу на назву функції, використовувався зовнішній інструментарій користувацького простору.

Під час збірки ядра утиліта `nm` (з пакету GNU Binutils) зчитувала відлагоджувальну таблицю ELF-символів незачищеного бінарника `vmlinux` і створювала текстовий файл `System.map`:

```
c0114990 T sys_open
c0114a80 T vfs_read
c0114bd0 T sys_read
```

У системі запускався системний демон `klogd` (частина пакету `sysklogd`). Демон зчитував сирі повідомлення ядра з пристрою `/proc/kmsg`, аналізував рядки з шістнадцятковими адресами у дужках `[<...>]`, відкривав файл `/boot/System.map-$(uname -r)`, робив бінарний пошук адреси й підставляв ім'я функції у текстовий лог перед записом у `/var/log/messages`.

```
стало:   vfs_read+0x43/0x140
замість: [<c0114a80>]
```

### Чому ця схема зламалася?

Схема із `System.map` та демоном `klogd` мала три фундаментальні вади, які стали критичними на початку 2000-х років при масштабуванні Linux на сервери:

1. **Паніка до моменту завантаження файлової системи.** Якщо ядро панікувало на етапі ініціалізації драйверів контролера диска або монтування кореневої файлової системи (`rootfs`), демон `klogd` ще не існував у пам'яті, а файл `System.map` був недоступний на диску. На екрані консолі лишалися лише сирі адреси, що ускладнювало налагодження ранніх збоїв завантаження.
2. **Динамічно завантажувані модулі ядра (`.ko`).** З появою підсистеми модулів ядра (Linux 1.2 / 2.0) код драйверів почав завантажуватися у пам'яті динамічно за допомогою системного виклику `init_module()`. Адреси функцій модуля визначалися в момент завантаження і відрізнялися при кожному запуску системи. Файл `System.map` описував лише статичне ядро `vmlinux` і взагалі не містив символів модулів.
3. **Рассинхронізація файлів.** Адміністратори часто оновлювали ядро, забуваючи скопіювати відповідний `System.map` у каталог `/boot`. Якщо версія `System.map` не відповідала запущеному ядру, `klogd` підставляв хибні імена функцій, дезорієнтуючи інженерів при розборі системних аварій.

## 2. Революція 2.6: Вбудований kallsyms та алгоритм Расті Расселла (2003)

Під час розробки ядра Linux 2.5/2.6 видатний розробник підсистеми модулів Расті Расселл (англ. *Rusty Russell*) разом із Каєм Ґермашевскі (англ. *Kai Germaschewski*) запропонували радикальне рішення: вбудувати таблицю символів безпосередньо всередину образу ядра у секцію даних лише для читання (`.rodata`). Механізм отримав назву **kallsyms** (від англ. *kernel all symbols* — усі символи ядра).

Головним викликом була збереження пам'яті. Звичайний текстовий список усіх символів ядра Linux обсягом у 50 000+ імен зайняв би понад 2–3 мегабайти нерозвантажуваної оперативної пам'яті ядра. Для розв'язання цієї проблеми Расті Расселл розробив двопрохідну систему збірки ядра та спеціальний алгоритм префіксного стиснення лексем (англ. *token compression dictionary*).

### Двопрохідна збірка ядра у kbuild

Утиліта `scripts/kallsyms.c` була інтегрована у процес збірки ядра:

1. **Перший прохід (Pass 1):** Ліінкер `ld` збирає попередній файл `vmlinux`. Утиліта `scripts/kallsyms` витягує всі символи та створює ассемблерний файл `kallsyms.S`.
2. **Компіляція таблиць:** Файл `kallsyms.S` компілюється в об'єктний файл `kallsyms.o` і лінкується разом із бінарником ядра у другому проході (Pass 2).
3. **Коригування адрес:** Оскільки додавання таблиці `kallsyms.o` змінює зміщення та адреси наступних символів у пам'яті, процес компіляції іноді виконує третій прохід (Pass 3), поки адреси усіх символів не стабілізуються остаточно.

Завдяки стисненню 8-бітними токенами та таблиці індексної індексації маркерів (`kallsyms_markers` кожні 256 символів), розмір таблиці символів зменшився у 3.5 рази, зробивши вбудовування символів прийнятним для всіх дистрибутивів.

## 3. Ера захисту: KASLR, kptr_restrict та деекспорт у 5.7 (2011–2020)

Зростання популярності Linux на серверах та мобільних пристроях (Android) зробило ядро головною мішенню для кібератак. Довгий час файл `/proc/kallsyms` був відкритий для звичайних користувачів і містив точні адреси всіх функцій ядра в оперативній пам'яті.

Це відкрило шлях для атак класу ROP (англ. *Return-Oriented Programming*). Зловмиснику достатньо було прочитати `/proc/kallsyms`, знайти адреси потрібних ядерних гаджетів (наприклад, `commit_creds` та `prepare_kernel_cred`) та сформувати експлойт для підвищення привілеїв до суперкористувача (`root`).

### Запровадження kptr_restrict (Linux 2.6.38, 2011)

У відповідь на хвилю експлойтів розробник безпеки Ден Розенберг (англ. *Dan Rosenberg*) у березні 2011 року додав рубільник безпеки sysctl `/proc/sys/kernel/kptr_restrict`. При значенні `1` або `2` ядро маскує всі адреси у `/proc/kallsyms` нулями (`0000000000000000`) для звичайних процесів без мандата `CAP_SYSLOG`.

### Поява KASLR та відносні зміщення (Linux 3.14, 2014)

У Linux 3.14 Кис Кук (англ. *Kees Cook*) реалізував для x86_64 рандомізацію розкладки адресного простору ядра — KASLR (англ. *Kernel Address Space Layout Randomization*). При кожному завантаженні системи базова адреса ядра зсувається на випадковий офсет у діапазоні пам'яті.

Це вимагало зміни формату `kallsyms`: замість абсолютних 64-бітних адрес у таблиці `kallsyms_addresses` ядро перейшло на відносні 32-бітні зміщення від базової адреси `_stext` (`CONFIG_KALLSYMS_BASE_RELATIVE=y`). Це не лише дозволило коректно працювати з KASLR (додаючи базовий зсув під час виконання), але й заощадило ще 50% обсягу таблиці адрес!

### Закриття kallsyms_lookup_name() (Linux 5.7, 2020)

Найбільш резонансною подією в історії `kallsyms` став випуск ядра Linux 5.7 у травні 2020 року. Упродовж багатьох років розробники зовнішніх модулів ядра та шкідливого ПЗ (руткітів) використовували функцію `kallsyms_lookup_name()` для обходу обмежень експорту символів.

Якщо ядро не експортувало таблицю системних викликів `sys_call_table` через макрос `EXPORT_SYMBOL`, модуль просто кликав:

```c
sys_call_table = (void *)kallsyms_lookup_name("sys_call_table");
```

Після цього модуль міг підміняти вказівники на системні виклики (хукінг), перехоплюючи відкриття файлів та виконання команд.

У ядрах Linux 5.7+ Вілл Дікон (англ. *Will Deacon*) та Крістоф Геллвіґ (англ. *Christoph Hellwig*) видалили макрос `EXPORT_SYMBOL_GPL(kallsyms_lookup_name)`. Цей крок остаточно закрив можливість для позадеревних модулів розшукувати довільні закриті структури ядра під час виконання. Легітимні підсистеми спостережуваності (на кшталт `kprobes`, `ftrace` та eBPF) отримали суворо контрольовані ядерні API, а використання `kallsyms_lookup_name()` стало можливим лише зсередини самого образу ядра.
