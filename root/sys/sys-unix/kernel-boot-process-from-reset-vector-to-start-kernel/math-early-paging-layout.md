# 🧮 Розрахунок раннього транслятора адрес і таблиць сторінок

Цей математичний та бітовий аналіз розкриває обчислення індексів таблиць сторінок (PML4, PUD, PMD, PTE) під час створення ранніх таблиць відображення `early_top_pgt` для переходу процесора x86_64 у віртуальний простір ядра High Canonical Memory.

Коли ядро готується до стрибка в 64-бітну High Memory, воно мусить перекласти віртуальну адресу `0xFFFFFFFF81000000` на відповідну фізичну адресу завантаження (наприклад, `0x01000000`). Для цього процесор розбиває 64-бітну віртуальну адресу на бітові поля згідно зі структурою чотирирівневої сторінкової адресації (4-level paging) або п'ятирівневої адресації (5-level paging / LA57).

## Архітектура канонічних адрес x86_64

На 64-бітній архітектурі x86_64 шина віртуальних адрес фактично використовує лише 48 бітів (у 4-рівневому режимі) або 57 бітів (у 5-рівневому режимі LA57). Решта старших бітів (від 48 до 63 у 4-рівневому режимі) зобов'язані бути точною копією 47-го біта. Це правило називається **знаковим розширенням адреси** (Sign Extension).

У результаті цього математичного обмеження віртуальний простір ділиться на дві канонічні області:
1. **Нижня канонічна область (User Space)**: від `0x0000000000000000` до `0x00007FFFFFFFFFFF`. 47-й біт дорівнює `0`, тому старші біти 48..63 заповнені нулями. Максимальний обсяг адресовної віртуальної пам'яті в цій області становить 128 Терабайтів.
2. **Верхня канонічна область (Kernel Space)**: від `0xFFFF800000000000` до `0xFFFFFFFFFFFFFFFF`. 47-й біт дорівнює `1`, тому старші біти 48..63 заповнені одиницями. Обсяг цієї області також становить 128 Терабайтів.

Проміжок між `0x00007FFFFFFFFFFF` та `0xFFFF800000000000` є неканонічною «діркою» розміром у 16 Ексабайтів. Якщо програма або ядро спробує виконати звернення за неканонічною адресою (наприклад, `0x0001000000000000`, де біти не є однакової знаковості), процесор апаратно згенерує виняток загального захисту пам'яті (`#GP` — General Protection Fault).

У 5-рівневому режимі адресації (LA57) межа канонічності розширюється до 57 бітів, що збільшує обсяг віртуальної пам'яті для кожної зони до 64 Петабайтів (від `0x0000000000000000` до `0x00FFFFFFFFFFFFFF` та від `0xFF00000000000000` до `0xFFFFFFFFFFFFFFFF`).

## Розкладання 64-бітної віртуальної адреси

64-бітна віртуальна адреса на архітектурі x86_64 розбивається на п'ять бітових полів:

```
[63 .. 48] : Знакове розширення (Sign Extension, 16 бітів, усі 1 для High Space)
[47 .. 39] : Індекс PML4 (Page Map Level 4 Index, 9 бітів, діапазон 0..511)
[38 .. 30] : Індекс PUD  (Page Upper Directory Index, 9 бітів, діапазон 0..511)
[29 .. 21] : Індекс PMD  (Page Middle Directory Index, 9 бітів, діапазон 0..511)
[20 .. 12] : Індекс PTE  (Page Table Entry Index, 9 бітів, діапазон 0..511)
[11 ..  0] : Зсув усередині сторінки (Page Offset, 12 бітів, діапазон 0..4095)
```

Кожен рівень таблиць сторінок являє собою масив із 512 записів. Оскільки кожен запис має розмір 8 байтів (64 біти), одна таблиця сторінок будь-якого рівня займає рівно `512 · 8 = 4096` байтів — тобто одну фізичну сторінку пам'яті.

Математичні формули маскування та бітового зсуву для обчислення кожного індексу виглядають так:

```
PML4_index = (VirtAddr >> 39) & 0x1FF     [бітовий зсув на 39 бітів та маска 9 бітів]
PUD_index  = (VirtAddr >> 30) & 0x1FF     [бітовий зсув на 30 бітів та маска 9 бітів]
PMD_index  = (VirtAddr >> 21) & 0x1FF     [бітовий зсув на 21 біт та маска 9 бітів]
PTE_index  = (VirtAddr >> 12) & 0x1FF     [бітовий зсув на 12 бітів та маска 9 бітів]
```

При використанні 5-рівневої адресації між PML4 та PUD додається ще один рівень P4D (Page 4th Directory), чий індекс обчислюється як `P4D_index = (VirtAddr >> 48) & 0x1FF`. У 4-рівневому режимі шар P4D згортається компілятором у прямий псевдонім PML4.

## Крок 1. Обчислення індексів для базованої High Memory ядра

Візьмемо віртуальну адресу старту ядра `0xFFFFFFFF81000000` у двоєчковому і шістнадцятковому вигляді.

Шістнадцятковий вигляд:
```
0xFFFFFFFF81000000 = 1111 1111 1111 1111 1111 1111 1111 1111 1000 0001 0000 0000 0000 0000 0000 0000 (двійковий)
```

Здійснимо розрахунок індексів покроково:

```
PML4_index
= (0xFFFFFFFF81000000 >> 39) & 0x1FF
= 0x1FF                                 [511 у десятковій системі, найостанніший запис PML4]

PUD_index
= (0xFFFFFFFF81000000 >> 30) & 0x1FF
= (1111 1111 1111 1111 1111 1111 1111 1111 1000 0001 0000 0000 0000 0000 0000 0000 >> 30) & 0x1FF
= 0x1FE                                 [510 у десятковій системі, передостанній запис PUD]

PMD_index
= (0xFFFFFFFF81000000 >> 21) & 0x1FF
= (0x81000000 >> 21) & 0x1FF
= (0x408) & 0x1FF
= 0x008                                 [8-й запис у каталозі PMD]
```

Отже, для відображення віртуальної адреси `0xFFFFFFFF81000000` ядро заповнює наступні комірки таблиць:
- `PML4[511]` посилається на фізичну адресу таблиці `level3_kernel_pgt`.
- `level3_kernel_pgt[510]` посилається на фізичну адресу таблиці `level2_kernel_pgt`.
- `level2_kernel_pgt[8]` містить запис великої сторінки (2 Мегабайти, прапор `_PAGE_PSE`), який прямує безпосередньо на фізичну адресу завантаження ядра `0x01000000`.

Завдяки використанню прапора `_PAGE_PSE` (Page Size Extension, біт 7 у записі PMD), трансляція зупиняється на рівні PMD. Процесор адресно додає нижчі 21 біт віртуальної адреси до фізичної адреси з запису PMD. Це дозволяє покрити 2 Мегабайти пам'яті одним записом без створення таблиці четвертого рівня (PTE), що заощаджує RAM і зменшує навантаження на буфер трансляції адрес (TLB).

## Крок 2. Обчислення індексів для прямих мап пам'яті

Окрім коду самого ядра (`__START_KERNEL_map`), ядро створює пряме відображення всієї фізичної пам'яті системи (Direct Physical Mapping / page_offset_base) за віртуальною адресою `0xFFFF888000000000`.

Обчислимо індекси для цієї зони:

```
PML4_index (Direct Mapping)
= (0xFFFF888000000000 >> 39) & 0x1FF
= (0x111) & 0x1FF
= 273                                   [273-й запис у таблиці PML4]

PUD_index (Direct Mapping)
= (0xFFFF888000000000 >> 30) & 0x1FF
= 0                                     [0-й запис у таблиці PUD]
```

Завдяки тому, що Direct Mapping починається з індексу 273, ядро може довільно конвертувати фізичну адресу в віртуальну за допомогою найпростішої формули: `VirtAddr = PhysAddr + PAGE_OFFSET`.

## Крок 3. Обчислення індексів для тимчасового Identity Mapping

Для того щоб інструкція стрибка не викликала помилку відсутності сторінки (Page Fault), ядро також будує Identity Mapping для низької фізичної адреси `0x01000000`:

```
PML4_index (Identity)
= (0x0000000001000000 >> 39) & 0x1FF
= 0                                     [0-й запис PML4]

PUD_index (Identity)
= (0x0000000001000000 >> 30) & 0x1FF
= 0                                     [0-й запис PUD]

PMD_index (Identity)
= (0x0000000001000000 >> 21) & 0x1FF
= 8                                     [8-й запис PMD, оскільки 0x01000000 / 2MB = 8]
```

## Математика скидання TLB та знищення Identity Mapping

Після виконання непрямого стрибка `jmp` лічильник інструкцій процесора опиняється в області `0xFFFFFFFF81xxxxxx`. Нижнє відображення `PML4[0]` більше не потрібне для виконання коду і стає загрозою для безпеки ядра.

Ассемблерний код записує нуль у перший елемент масиву: `early_top_pgt[0] = 0`. Проте кєш трансляції адрес процесора (TLB — Translation Lookaside Buffer) досі зберігає старі записи трансляції для низьких адрес у своїх внутрішніх кеш-лініях.

Щоб примусово вичистити старі записи з TLB, ядро перезавантажує керівний регістр `CR3` тим самим значенням:

```assembly
movq %cr3, %rax
movq %rax, %cr3
```

Запис у регістр `CR3` спричиняє апаратне скидання всіх неетикованих записів TLB (за винятком сторінок із прапором `_PAGE_GLOBAL`). Завдяки цьому при спробі подальшого звернення до низьких адрес `0x0000000001000000` процесор негайно згенерує помилку сторінки `#PF`, а фізична адреса невдалої трансляції буде збережена у керівному регістрі `CR2`.

## Резюме обчислення подвійного відображення

Завдяки цьому математичному розрахунку одна й та сама 2-мегабайтна сторінка фізичної пам'яті (`0x01000000`) виявляється доступною за двома віртуальними адресами одночасно:

1. `0x0000000001000000` (через `PML4[0]`) — діє під час виконання перших інструкцій з увімкненим CR3.
2. `0xFFFFFFFF81000000` (через `PML4[511]`) — діє постійно після виконання непрямого стрибка `jmp`.

Після переходу виконання в верхню пам'ять ядро записує `0` у `PML4[0]` і викликає інструкцію інвалідації буфера TLB `invlpg` (або перезавантажує CR3), остаточно виключаючи низьку пам'ять із віртуального простору ядра.
