# 📋 Специфікація boot_params та setup_header в Linux Boot Protocol

Цей довідник описує точну структуру даних `boot_params` (історично відому як Zero Page) та її внутрішній заголовок `setup_header`, через які завантажувач передає ядру Linux конфігурацію системи, параметри пам'яті, командний рядок та адресу initramfs.

Усі завантажувачі Linux (GRUB, systemd-boot, QEMU direct kernel boot, EFI Stub) зобов'язані виділити одну 4096-байтну сторінку пам'яті у фізичному адресному просторі, занулити її, заповнити заголовок `setup_header` і передати її фізичну адресу в регістрі `rsi` (на x86_64) або `x0` (на ARM64 під час роботи з FDT) при вході в ядро.

## Призначення та вимоги до Zero Page

Структура `boot_params` отримала назву Zero Page тому, що перед заповненням завантажувач зобов'язаний повністю заповнити всі її 4096 байтів нулями. Це гарантує, що неініціалізовані поля не міститимуть «сміття» від попередньо виконуваного коду прошивки чи BIOS.

Оперативна пам'ять для Zero Page виділяється у фізичній зоні, яка не перекривається з кодом самого ядра, кодом розпакувальника або тимчасовим буфером `initramfs`. На 32-бітних архітектурах ця сторінка повинна розміщуватися нижче межі 1 Гігабайта, тоді як 64-бітні завантажувачі можуть розміщувати `boot_params` у довільному місці адресовної фізичної пам'яті.

## Структура `boot_params` (Zero Page)

Головна структура визначена в вихідному файлі ядра `arch/x86/include/uapi/asm/bootparam.h`. Вона займає рівно 4096 байтів і лежить на межі сторінки пам'яті.

| Зсув (Hex) | Поле у `struct boot_params` | Тип | Опис |
| :--- | :--- | :--- | :--- |
| `0x0000` | `screen_info` | `struct screen_info` | Параметри ранньої текстової/графічної консолі (VESA/GOP mode, розміри, буфер). |
| `0x0040` | `apm_bios_info` | `struct apm_bios_info` | Спадкова інформація про керування живленням APM BIOS. |
| `0x01E0` | `e820_entries` | `__u8` | Кількість дійсних записів у таблиці мапи пам'яті `e820_table`. |
| `0x01E1` | `eddbuf_entries` | `__u8` | Кількість записів у буфері BIOS EDD (Enhanced Disk Drive). |
| `0x01F1` | `hdr` | `struct setup_header` | **Ключовий заголовок протоколу завантаження** (деталізовано нижче). |
| `0x02D0` | `e820_table` | `struct boot_e820_entry[128]` | Таблиця фізичної мапи пам'яті E820 (RAM, Reserved, ACPI Data, NVDIMM). |
| `0x0800` | `eddbuf` | `struct edd_info[6]` | Інформація про геометрію дисків EDD. |

## Детальний розбір підструктур Zero Page

Структура `boot_params` містить кілька принципових блоків даних, кожен із яких передає ядру параметри конкретної підсистеми апаратури.

### 1. Блок конфігурації відеорежиму (`screen_info`)

Поле `screen_info` розміщене на самому початку Zero Page (зсув `0x0000`). Воно використовується ранніми драйверами консолі ядра (`earlyprintk`, `earlycon`, `vgacon`, `efifb`) для виводу текстових повідомлень до того, как буде завантажено повноцінні графічні драйвери DRM/KMS.

Ключові поля `screen_info` включають:
- `orig_video_mode`: номер текстового або VESA-відеорежиму BIOS.
- `orig_video_cols` та `orig_video_lines`: кількість символів у рядку та кількість рядків текстової консолі (зазвичай 80x25 або 80x50).
- `lfb_base`: 32-бітна фізична адреса лінійного графічного відеобуфера (Linear Framebuffer Base).
- `ext_lfb_base`: старші 32 біти адреси відеобуфера для 64-бітних графічних карт PCIe.
- `lfb_width`, `lfb_height`, `lfb_depth`: роздільна здатність екрана у пікселях (наприклад, 1920x1080) та глибина кольору (32 біти BGRX/RGBX).
- `orig_video_isVGA`: типізація відеоконтролера (`VIDEO_TYPE_VGAC`, `VIDEO_TYPE_VLFB`, `VIDEO_TYPE_EFI`).

Рання графічна консоль ядра спирається на параметри `lfb_base` та `lfb_linelength` для безпосереднього запису пікселів у пам'ять графічного адаптера. Це дозволяє показувати консольні повідомлення відразу після ввімкнення MMU, навіть якщо повноцінний драйвер відеокарти ще не ініціалізовано.

### 2. Таблиця фізичної пам'яті (`e820_table`)

За зсувом `0x02D0` міститься масив із 128 елементів `struct boot_e820_entry`. Це головне джерело відомостей про фізичну пам'ять комп'ютера. Кожен запис має розмір 20 байтів і містить початкову адресу регіону, його розмір у байтах та тип.

Основні значення поля типу відповідно до специфікації ACPI та E820:
- `E820_TYPE_RAM` (`1`): придатна для використання оперативна пам'ять (Usable RAM).
- `E820_TYPE_RESERVED` (`2`): зарезервована системна область (ROM, MMIO пристроїв, пропалена прошивкою пам'ять).
- `E820_TYPE_ACPI` (`3`): класи ACPI Reclaimable Memory, які ядро може звільнити після зчитування ACPI-таблиць.
- `E820_TYPE_NVS` (`4`): ACPI Non-Volatile Storage (пам'ять, що зберігається при гібернації).
- `E820_TYPE_UNUSABLE` (`5`): пошкоджена або непридатна RAM (Bad Memory).
- `E820_TYPE_PMEM` (`7`): енергонезалежна оперативна пам'ять NVDIMM / Persistent Memory.

Під час виконання `setup_arch()` ядро викликає функцію `sanitize_e820_map()`, яка сортує записи E820 за початковою адресою, об'єднує суміжні однакові регіони та відсікає некоректні перекриття. Очищена таблиця E820 стає основою для раннього розподільника пам'яті `memblock`.

## Структура `setup_header` (зсув `0x01F1`)

Заголовок `setup_header` є єдиною точкою узгодження версій між завантажувачем і ядром. Завантажувач зчитує цей заголовок безпосередньо з файла `vmlinuz` перед завантаженням.

| Зсув від `hdr` | Поле | Тип | Опис та сигнатури |
| :--- | :--- | :--- | :--- |
| `0x00` (`0x01F1`) | `setup_sects` | `__u8` | Кількість 512-байтових секторів реального режиму. Якщо 0, то використовується значення 4. |
| `0x06` (`0x01F7`) | `syssize` | `__u32` | Розмір коду захищеного режиму в 16-байтових параграфах. |
| `0x10` (`0x0201`) | `version` | `__u16` | **Версія протоколу завантаження** (наприклад, `0x020f` = протокол 2.15). |
| `0x14` (`0x0205`) | `realmode_swtch` | `__u32` | Тимчасове hook-посилання реального режиму. |
| `0x18` (`0x0209`) | `start_sys_seg` | `__u16` | Застарілий сегмент завантаження. |
| `0x1C` (`0x020D`) | `type_of_loader` | `__u8` | **Ідентифікатор завантажувача** (`0x10` = LILO, `0x70` = GRUB2, `0x80` = QEMU). |
| `0x1D` (`0x020E`) | `loadflags` | `__u8` | Бітові прапори завантаження (`LOADED_HIGH`, `KASLR_FLAG`, `QUIET_FLAG`). |
| `0x22` (`0x0213`) | `code32_start` | `__u32` | **Фізична адреса точки входу** 32-бітного/64-бітного коду розпакування. |
| `0x26` (`0x0217`) | `ramdisk_image` | `__u32` | **32-бітна фізична адреса** завантаженого в RAM образу `initramfs`. |
| `0x2A` (`0x021B`) | `ramdisk_size` | `__u32` | Розмір образу `initramfs` у байтах. |
| `0x36` (`0x0227`) | `header` | `__u32` | **Магічна сигнатура ядра**: `"HdrS"` (значення `0x53726448`). |
| `0x3A` (`0x022B`) | `cmd_line_ptr` | `__u32` | **32-бітна фізична адреса** нуль-термінованого рядка параметрів ядра. |
| `0x3E` (`0x022F`) | `initrd_addr_max` | `__u32` | Максимально припустима фізична адреса для розміщення `initramfs`. |
| `0x4C` (`0x023C`) | `pref_address` | `__u64` | **Бажана адреса завантаження ядра** (Preferred alignment, зазвичай 16 MB). |
| `0x54` (`0x0244`) | `initrd_addr_max_64` | `__u64` | 64-бітна максимальна адреса для initramfs (протоколи 2.15+). |

## Еволюція версій протоколу завантаження

Протокол завантаження ядра Linux розвивався протягом понад двох десятиліть. Кожна нова версія протоколу додавала нові поля в заголовок `setup_header`, зберігаючи абсолютну сумісність із попередніми завантажувачами.

Версія протоколу описується полями `version` за зсувом `0x0201` (значення `0x020F` означає версію протоколу 2.15).

Головні етапи еволюції протоколу:
- **Версія 2.00**: базовий заголовок з підтримкою 16-бітного real mode та 32-бітного коду ядра.
- **Версія 2.02**: додано поле `cmd_line_ptr`, що дозволило передавати командний рядок довільної довжини у верхній пам'яті замість застарілого зсуву в сегменті реального режиму.
- **Версія 2.03**: додано поле `initrd_addr_max`, яке вказало завантажувачу верхню межу адресування фізичної пам'яті для розміщення архіву `initramfs`.
- **Версія 2.04**: додано бітові прапори `loadflags` (зокрема `LOADED_HIGH`, що означав завантаження коду вище 1 Мегабайта).
- **Версія 2.10**: додано поля `pref_address` та `relocatable_kernel`. Ядро отримало можливість релокації у фізичній пам'яті під час роботи захисту KASLR.
- **Версія 2.15**: додано 64-бітне поле `initrd_addr_max_64`, що зняло 32-бітне обмеження (2 ГБ) на розміщення `initramfs` у 64-бітній пам'яті.

## Договір передачі прапорів `loadflags`

Байт `loadflags` (зсув `0x020E`) містить конфігураційні біти, які контролюють поведінку ядра під час старту.

Значення окремих бітів прапорів `loadflags`:
- Біт 0 (`LOADED_HIGH`): якщо встановлено у `1`, код захищеного режиму завантажено за адресою `0x100000` (вище 1 Мегабайта). Якщо `0`, код лежить у низькій пам'яті `0x10000`.
- Біт 5 (`QUIET_FLAG`): якщо встановлено у `1`, розпакувальник пригнічує рання діагностичні повідомлення в серійний порт під час декомпресії.
- Біт 7 (`CAN_BE_RELOCATED`): вказує завантажувачу, що код розпакувальника ядра підтримує релокацію у довільне місце фізичної пам'яті (необхідно для роботи KASLR).

Якщо завантажувач передає параметри в ядро, він зобов'язаний виділити буфер під командний рядок, записати його фізичну адресу в `cmd_line_ptr`, виділити пам'ять під initramfs, вказати її в `ramdisk_image` та `ramdisk_size`, після чого встановити сигнатуру `header = 0x53726448`. Якщо сигнатура "HdrS" відсутня, ядро вважає завантажувач несумісним і зупиняє виконання (Kernel Panic).
