# 📋 SELinux: контекст, правила й команди

Довідка за клавіатурою: з чого складено контекст, якою граматикою записані правила, чим подивитися чинний стан, чим переставити мітку, чим перемкнути булевий вимикач і як із рядка журналу дійти до власного модуля політики. Лише SELinux — про AppArmor тут нічого.

## Контекст: чотири поля

```
system_u : system_r : httpd_t : s0
   │          │          │       │
   │          │          │       └── рівень: чутливість[-чутливість][:категорії]
   │          │          └────────── тип; у процесу його звуть доменом
   │          └───────────────────── роль
   └──────────────────────────────── користувач SELinux
```

| поле | що це | приклади | чим керують |
|---|---|---|---|
| `user` | користувач SELinux — окрема сутність, не запис із `/etc/passwd`; визначає, які ролі доступні | `system_u` `unconfined_u` `staff_u` | `semanage login -a -s staff_u alice` |
| `role` | набір доменів, у які цей користувач може перейти; на всіх об'єктах завжди `object_r` | `system_r` `unconfined_r` `staff_r` | `semanage user -l` |
| `type` | те, про що говорять правила | `httpd_t` `httpd_sys_content_t` | `semanage fcontext`, `chcon` |
| `level` | MCS/MLS: чутливість і категорії | `s0` · `s0:c12,c47` · `s0-s0:c0.c1023` | `semanage user`, `chcon -l` |

У рівні `.` означає діапазон категорій, `,` — перелік. У цільовій політиці, яку возять Fedora й RHEL, чутливість завжди `s0`, а категорії працюють як розділювач примірників: два процеси з **однаковим** типом, але неперетинними наборами категорій не дістануться один до одного. Саме цим відокремлено контейнери, підняті з одного образу.

Іменування типів має сталу форму, і за нею тип читається без довідника: `_t` наприкінці — будь-який тип, `_exec_t` — виконуваний файл, що є входом у домен, `_port_t` — номери портів.

| тип | чим мічено |
|---|---|
| `httpd_t` | домен процесів веб-сервера |
| `httpd_exec_t` | `/usr/sbin/httpd` — вхід у цей домен |
| `httpd_sys_content_t` | вміст сайту; серверові лише на читання |
| `httpd_sys_rw_content_t` | те саме, але й на запис |
| `httpd_log_t` · `httpd_config_t` | журнали · `/etc/httpd` |
| `user_home_t` · `tmp_t` · `shadow_t` | домашні файли · `/tmp` · `/etc/shadow` |
| `http_port_t` | номери портів, на які веб-серверові вільно стати |
| `container_t` · `container_file_t` | процеси й дані контейнерів |
| `unconfined_t` | домен, якому дозволено практично все |

## Граматика правил

```
allow      джерело ціль : клас { дозволи };
dontaudit  джерело ціль : клас { дозволи };
auditallow джерело ціль : клас { дозволи };
neverallow джерело ціль : клас { дозволи };

type_transition джерело ціль : клас новий_тип [ "ім'я" ];
```

`allow` — єдине з чотирьох, що дає право. Слова `deny` в мові немає й бути не може: усе, чого не дозволено, і так заборонено, тож забороняти нічого. `dontaudit` рішення не міняє — він лише прибирає запис із журналу, і через нього трапляються відмови без жодного сліду. `auditallow` дзеркальний: права не додає, а записує в журнал успішну дію — так наглядають за рідкісними повноваженнями. `neverallow` до ядра взагалі не потрапляє: це твердження для збирача політики, і політика, яка його порушує, просто не збереться.

`type_transition` називає тип, який має вийти: для класу `process` — домен після `exec`, для `file`/`dir` — тип новоствореного об'єкта в цьому каталозі. Необов'язковий останній аргумент робить перехід іменним — за конкретним іменем файлу, а не за всім каталогом:

```
type_transition httpd_t var_run_t : file httpd_var_run_t "httpd.pid";
```

Клас каже, **про що саме** йдеться, і кожен клас має власний набір дозволів.

| клас | дозволи, які трапляються найчастіше |
|---|---|
| `file` | `read write append create unlink open getattr setattr` · `execute` · `execute_no_trans` · `entrypoint` · `map` |
| `dir` | `search add_name remove_name rmdir` — і `search` потрібен на **кожному** складнику шляху |
| `process` | `transition sigchld signal ptrace setexec execmem execstack dyntransition` |
| `tcp_socket` · `udp_socket` | `create connect listen accept` · `name_bind` (стати на порт) · `name_connect` (з'єднатися з портом) |
| `capability` | `dac_override net_bind_service sys_admin` — ті самі [можливості](topic:sys-unix/capabilities), але під наглядом політики |
| `filesystem` | `mount unmount associate` |
| `unix_stream_socket` | `connectto` — постукати в чужий сокет |

Два дозволи класу `file` варто розрізняти: `execute` дає право запустити файл, а `execute_no_trans` — право лишитися при цьому у своєму домені. Домен, що має `execute` без `execute_no_trans`, зобов'язаний перейти, і якщо переходу для цієї пари не описано, запуск обірветься.

Чинні правила читають із завантаженої політики (пакунок `setools-console`):

```
sesearch -A -s httpd_t -t httpd_sys_content_t -c file
seinfo -t | grep httpd        # усі типи за зразком
seinfo -b | grep httpd        # усі булеві вимикачі
```

## Чинний стан

| команда | що покаже або зробить |
|---|---|
| `getenforce` | `Enforcing` · `Permissive` · `Disabled` |
| `setenforce 0` / `1` | перемкнути режим до перезавантаження |
| `sestatus -v` | повний стан: чи змонтовано `selinuxfs`, яка політика, режим із файлу |
| `ls -lZ` · `ps -eZ` · `id -Z` | контексти файлів · процесів · поточної оболонки |
| `runcon -t тип -- команда` | запустити в іншому контексті, якщо політика такий перехід дозволяє |
| `semanage permissive -a httpd_t` | один домен у дозвільний режим, решта системи лишається в примусі |
| `/etc/selinux/config` | режим при старті: `SELINUX=` (`enforcing` · `permissive` · `disabled`) і `SELINUXTYPE=` (`targeted` · `mls`) |

Про останній рядок є свіжа деталь. Від ядра 6.4 змогу вимикати SELinux на ходу прибрали зовсім (її позначили застарілою ще 2020 року, а прибрали, щоб гачки безпеки можна було зробити незмінними після старту). Тому `SELINUX=disabled` у файлі більше не вимикає механізм: система стартує з увімкненим SELinux, у якому просто не завантажено політики. Справжнє вимикання лишилося одне — параметр ядра `selinux=0`. Перемикання `enforcing` ↔ `permissive` це не зачепило.

## Мітки: база, xattr і чому `chcon` недовговічний

Мітка на файлі живе у [розширеному атрибуті](topic:sys-unix/acl-and-xattr) `security.selinux`, і саме її ядро читає на кожній перевірці. Але поруч є друге сховище — база відповідностей «зразок шляху → тип», з якої мітку **відновлюють**.

![Два сховища, у яких лежить мітка. Ліворуч дві команди. Верхня, semanage fcontext з типом і зразком шляху, стрілкою веде до блоку бази відповідностей: file_contexts і локальні додатки, правило виду зразок шляху дає тип. Від бази вниз іде стрілка з підписом праворуч: restorecon читає базу й переписує мітку. Стрілка веде до другого блоку — мітка на самому inode у розширеному атрибуті security.selinux, і саме її читає ядро на перевірці. Нижня команда, chcon із типом і файлом, веде стрілкою прямо в цей другий блок, оминаючи базу. Унизу підсумок: переставляння міток бере тип із бази й переписує ним xattr, тому мітка від chcon, не занесена в базу, зникає](img/label-stores.svg)

*`chcon` пише в inode, `semanage fcontext` — у базу. Переставляння міток іде з бази в inode, тож перше без другого не переживає навіть одного `restorecon -R`.*

| команда | що робить |
|---|---|
| `semanage fcontext -a -t тип "/web(/.*)?"` | додати правило в базу; **зразок — регулярний вираз**, а не шаблон оболонки |
| `semanage fcontext -a -e /home /home1` | еквівалентність: `/home1` мітити за правилами `/home` |
| `semanage fcontext -l -C` | лише локальні додатки, без базової політики |
| `restorecon -Rv /web` | привести мітки під базу |
| `restorecon -nv /web` | нічого не міняти, лише показати, що змінилося б |
| `restorecon -RF /web` | скинути й `user` з `role`, не тільки тип |
| `chcon -t тип файл` · `chcon --reference=зразок файл` | поставити тип напряму · скопіювати контекст сусіда |
| `matchpathcon /web/index.html` | що каже про цей шлях база (утиліта застаріла, її заступає `selabel_lookup`) |
| `fixfiles -R пакунок restore` | перемітити файли одного пакунка |
| `touch /.autorelabel && reboot` | повне переставляння міток усієї системи при старті |

Звідси й правило про копіювання. `cp` створює новий inode, і той дістає тип за правилом каталогу-приймача — тобто правильний. `cp -a` чи `cp --preserve=context` тягне тип із джерела. `mv` у межах однієї файлової системи не створює нічого й лишає стару мітку недоторканою; після нього `restorecon` обов'язковий.

## Булеві вимикачі

| команда | що робить |
|---|---|
| `getsebool -a` · `getsebool httpd_can_network_connect` | стан усіх · одного |
| `setsebool httpd_can_network_connect on` | до перезавантаження |
| `setsebool -P …` | назавжди: політику перезбирають, тому помітно повільніше |
| `semanage boolean -l` | поточне й збережене значення плюс опис словами |

Вимикач — це умова, вписана в політику наперед: усередині неї лежать готові правила, які автори політики вже написали й перевірили. Тому «серверові треба ходити в мережу» майже завжди розв'язується одним `setsebool -P`, а не власним модулем — і `semanage boolean -l` варто прочитати перед тим, як писати правила руками.

## Порти

Стати на порт — це дозвіл `name_bind` класу `tcp_socket` над типом самого номера порту. Тому у [`bind`](topic:sys-unix/socket-api-linux) на нетиповий номер відмовляють не через права на файл, а через мітку порту.

```
semanage port -l | grep http           # які номери яким типом мічено
semanage port -a -t http_port_t -p tcp 8080
semanage port -m -t http_port_t -p tcp 8080   # коли номер уже описано в базовій політиці
semanage port -d -p tcp 8080                  # прибрати локальне правило
```

Порядок тут такий: `-a` для номера, якого політика ще не знає; якщо номер уже комусь належить (а 8080 типово належить `http_cache_port_t`), `-a` відмовить, і потрібен `-m`.

## Від запису в журналі до модуля

Кожна відмова лягає в [підсистему аудиту](topic:sys-unix/audit-framework) записом `AVC`.

```
ausearch -m AVC,USER_AVC,SELINUX_ERR -ts recent
ausearch -m AVC -c nginx -ts today
ausearch -m AVC -ts recent | audit2why
ausearch -m AVC -c nginx -ts recent | audit2allow -M nginx-local
semodule -i nginx-local.pp
```

`audit2why` відповідає на питання **чому** і мусить іти першим: він розрізняє «правила немає», «правило є, але вимкнене булевим», «домен дозвільний» і «порушено обмеження (constraint)» — і в доброї половині випадків відповіддю виявиться вимикач, а не новий модуль.

`audit2allow -M ім'я` кладе поруч два файли: `ім'я.te` — вихідний текст правил і `ім'я.pp` — зібраний модуль. **`.te` треба прочитати перед завантаженням.** Ця утиліта не знає, що безпечно: вона механічно перекладає журнал у `allow`, тож відмова, спричинена неправильною міткою, перетвориться на правило, яке назавжди відчинить домену цілий чужий тип.

| команда | що робить |
|---|---|
| `semodule -l` | перелік завантажених модулів |
| `semodule -i файл.pp` · `semodule -r ім'я` | завантажити · вивантажити |
| `semodule -X 300 -i файл.pp` | завантажити з пріоритетом 300 — так локальний модуль заступає однойменний із дистрибутива |
| `semodule -DB` | перезібрати політику **без** `dontaudit` — щоб побачити приглушені відмови |
| `semodule -B` | перезібрати звичайно й повернути глушники |

Стан без `dontaudit` переживає перезавантаження й тримається до наступного перезбирання політики — тобто до `semodule -B`, `semodule -i` чи `setsebool -P`. Тримати систему в ньому довго не варто: журнал заллє шумом, заради приглушення якого ці правила й писали.

> 🔧 **Навіщо це.** Порядок дій при відмові економить найбільше часу, коли його дотримано з першого разу. `getenforce` — чи взагалі увімкнено примус. `ausearch -m AVC -ts recent` — чи є запис; порожньо при ввімкненому примусі означає або `dontaudit` (знімається `semodule -DB`), або що відмова прийшла зовсім не від SELinux. Далі `audit2why` — і лише якщо він каже «правила немає», порівняти `tcontext` файлу з міткою сусіднього робочого файлу: розбіжність лікується `restorecon`, а не новим правилом. `audit2allow` — остання дія, а не перша, і його `.te` читають очима.
