# 📜 Еволюція мережевого керування Linux: від ioctl/net-tools до Netlink/iproute2

Історична модель конфігурації мережевих інтерфейсів у Unix формувалася на початку 1980-х років у рамках операційної системи BSD UNIX (особливо у релізах 4.2BSD та 4.3BSD). Ця модель спиралася на універсальний системний виклик `ioctl()` над мережевими сокетами та набір консольних утиліт з пакета `net-tools` (`ifconfig`, `route`, `arp`, `netstat`). Протягом майже двох десятиліть ця архітектура залишалася єдиним способом налаштування мережі в Unix-подібних системах. Проте зі стрімким розвитком локальних і глобальних мереж, появою багаторазової адресації, віртуалізації та високошвидкісних магістралей модель `ioctl()` виявила фундаментальні структурні обмеження, які призвели до розробки підсистеми Netlink та пакета `iproute2`.

## Витоки BSD-моделі та однопроцесорна епоха 1980-х років

Коли в Університеті Каліфорнії у Берклі розроблялася перша реалізація стеків TCP/IP для VAX-машин, архітектура обчислювальних систем істотно відрізнялася від сучасних серверів. Комп'ютери того часу мали один центральний процесор, одну або максимум дві фізичні мережеві карти і підключалися до простих однорангових мереж.

У цьому середовищі концепція «один пристрій — одна адреса — один системний виклик» була цілком виправданою. Системний виклик `ioctl()` з кодами керування на кшталт `SIOCSIFADDR` давав змогу швидко встановити IP-адресу на мережевому адаптері. Розробники не передбачили викликів для отримання подій від ядра, оскільки фізичний стан лінка в ті часи не відстежувався на програмному рівні: кабелі Ethernet (товстий та тонкий коаксіал 10BASE5 / 10BASE2) не мали сигналів автоузгодження Link Pulse, які з'явилися пізніше в стандарті 10BASE-T.

## Модель ioctl та її обмежувальні бар'єри

У класичній Unix-моделі взаємодія простору користувача з мережевими інтерфейсами здійснювалася через створення безпротокольного сокета (наприклад, `int fd = socket(AF_INET, SOCK_DGRAM, 0)`) та подальший виклик функцій `ioctl(fd, request, &ifr)`. Аргументом виклику слугувала уніфікована структура `struct ifreq` або `struct ifconf`.

```
[Пользовательский процесс (ifconfig)]
               │
               ▼ ioctl(fd, SIOCGIFFLAGS, &ifr)
    ┌──────────────────────┐
    │     Ядро Linux       │
    │  (struct net_device) │
    └──────────────────────┘
```

Кожна операція `ioctl()` призначалася для виконання суворо однієї атомарної дії: прочитати прапорці інтерфейсу (`SIOCGIFFLAGS`), встановити IP-адресу (`SIOCSIFADDR`), змінити маску підмережі (`SIOCSIFNETMASK`) або прочитати апаратну MAC-адресу (`SIOCGIFHWADDR`). Цей підхід мав декілька системних вад, які з часом перетворилися на непрохідний бар'єр для розвитку мережевої підсистеми ядра Linux.

### 1. Синхронний опитальний характер (Polling) та відсутність подій

Найсерйознішим недоліком `ioctl()` була відсутність будь-якого механізму сповіщень (Event Notifications) з боку ядра у простір користувача. Якщо кабель Ethernet витягували з мережевої карти, підключався новий бездротовий адаптер або демон DHCP отримував нову IP-адресу, інші процеси в системі не мали жодного способу дізнатися про цю подію асинхронно.

Щоб відстежувати стан мережі, демони керування (такі як застарілі мережеві менеджери 1990-х років) змушені були виконувати постійний періодичний опитувальний цикл (Polling Loop). Вони щосекунди викликали `ioctl()` для кожного інтерфейсу системи. Це створювало непотрібне навантаження на процесор, збільшувало кількість перемикань контексту між простором користувача та ядром і виснажувало батареї мобільних пристроїв.

### 2. Архітектурне обмеження "одна адреса на інтерфейс" та псевдоніми eth0:1

Початкова структура `struct net_device` у ядрі Linux містила вказівник лише на один об'єкт IP-адреси. Зі зростанням вимог до вебсерверів (де на одному фізичному сервері виникала потреба хостити сотні сайтів із власними IP-адресами) розробникам ядра довелося створити костиль у вигляді псевдонімів інтерфейсів (Network Interface Aliases).

Щоб призначити другу IPv4-адресу пристрою `eth0`, створювався штучний псевдонім з назвою `eth0:1`, для третьої — `eth0:2` і так далі. З погляду системного інструментарію `ifconfig` ці псевдоніми виглядали як абсолютно окремі мережеві пристрої з власними назвами, хоча в ядрі вони прив'язувалися до того самого фізичного адаптера. Це створювало плутанину у таблицях маршрутизації, ускладнювало розбір текстового виводу утиліт та унеможливлювало атомне вилучення адрес.

### 3. Фіксована бінарна структура та проблема розширення ABI

Структура `struct ifreq` має жорстко зафіксований розмір пам'яті. Рядкове поле `ifr_name` має розмір `IFNAMSIZ` (16 байтів). Спроби передати через `ioctl()` нові типи параметрів (наприклад, налаштування віртуальних мереж VLAN IEEE 802.1Q, атрибути VXLAN тунелів, конфігурацію дисциплін черг Traffic Control або метрики маркування пакетів) вимагали створення нових унікальних структур даних та додавання сотень нових кодів керування `SIOCDEVPRIVATE` у заголовочні файли ядра.

Це призвело до хаосу в таблиці системних викликів і робило інтерфейс ядра крихким: зміна будь-якого поля в структурі ламала двобінарну сумісність (ABI) із вже скомпільованими утилітами користувацького простору.

### 4. Несумісність із багатотабличною маршрутизацією (Policy Routing)

У ядрі Linux 2.2 з'явилася підсистема політики маршрутизації (RPDB — Routing Policy Database), яка давала змогу використовувати до 255 незалежних таблиць маршрутизації. Класична утиліта `route` з пакета `net-tools` оперувала виключно однією головною таблицею `main`. Вона не мала бінарних структур для опису правил селекції маршрутів на основі IP-адреси відправника, міток файрволу (fwmark) або індексу вхідного інтерфейсу. Спроби розширити `ioctl()` для керування сотнями таблиць маршрутизації провалилися через обмеженість бінарних структур.

### 5. Несумісність із протоколом IPv6

Коли в середині 1990-х років розроблялася специфікація протоколу IPv6, стало очевидним, що модель `ifconfig` абсолютно непридатна для нової адресації. За стандартом IPv6 кожен інтерфейс повинен одночасно мати принаймні одну Link-Local адресу (`fe80::/10`), одну або декілька Global Unicast адрес, а також набір мультикаст-адрес. Модель `ifconfig`, розрахована на поодинокі IPv4-адреси та штучні псевдоніми, не могла природно відобразити багаторівневу структуру IPv6.

### 6. Розпорошеність інструментів та текстове парсування

У пакеті `net-tools` кожна задача виконувалася окремою утилітою:
* `ifconfig` відповідала за L2/L3 конфігурацію інтерфейсу;
* `route` маніпулювала таблицею маршрутизації IPv4;
* `arp` переглядала та правила ARP-кеш локальних MAC-адрес;
* `slattach` та `plipconfig` керували послідовними каналами.

Ці утиліти не мали спільного коду, використовували різні форматування даних і виводили інформацію у вигляді текстових таблиць. Системні скрипти змушені були парсити цей вивід за допомогою `awk`, `grep` та `sed`. Найменша зміна у форматуванні рядків виводу `ifconfig` при зміні версії дистрибутива ламала скрипти автоматизації по всій системі.

## Поява RTNETLINK та Alexey Kuznetsov (1999)

Під час підготовки ядра Linux 2.2 у 1999 році розробник Олексій Кузнєцов (Alexey Kuznetsov) виконав повний перепис мережевої підсистеми маршрутизації та конфігурації ядра. Замість розширення застарілого `ioctl()` він впровадив принципово новий механізм IPC — сокетну родину `AF_NETLINK` із протокольним модулем `NETLINK_ROUTE` (RTNETLINK).

Netlink замінив синхронні блоки `ioctl()` на повнодуплексний асинхронний бінарний протокол на основі сокетів типу Datagram. Замість монолітних фіксованих структур даних RTNETLINK використовує гнучкий потік повідомлень із змінною кількістю атрибутів у форматі TLV (Type-Length-Value).

Паралельно з ядром Олексій Кузнєцов випустив новий пакет утиліт користувацького простору — **`iproute2`**. Одна універсальна утиліта `ip` повністю замінила весь інвентар `net-tools`:

* `ifconfig` → `ip link` (керування L2 пристроями та прапорцями) та `ip addr` (керування L3 IPv4/IPv6 адресами);
* `route` → `ip route` (управління кількома таблицями маршрутизації);
* `arp` → `ip neigh` (керування таблицею сусідів ARP/NDP).

## Порівняльний аналіз із підходами BSD (PF_ROUTE) та Solaris (DLPI)

Цікаво відзначити, що інші операційні системи роду Unix вирішували проблему обмеженості `ioctl()` власними шляхами.

Системи сімейства BSD (FreeBSD, OpenBSD, NetBSD) впровадили сокети маршрутизації `PF_ROUTE`. Цей механізм також спирається на передачу бінарних кадрів через сокет, проте використовує фіксовані заголовочні структури `struct rt_msghdr` та `struct if_msghdr`. Операційна система Solaris впровадила Data Link Provider Interface (DLPI) над підсистемою STREAMS.

Розробники Linux обрали унікальний шлях у вигляді сокетів `AF_NETLINK` завдяки їхній максимальній гнучкості: схема TLV-атрибутів дає змогу додавати нові типи мережевих параметрів у ядро Linux без будь-яких змін у коді наявних утиліт чи бібліотек.

## Епоха контейнеризації та остаточний вихід net-tools з ужитку

З появою технологій контейнеризації (LXC, Docker, Podman) та облачних оркестраторів (Kubernetes) мережева підсистема Linux зазнала чергової революції. У контейнерних середовищах кожна ізольована сутність отримує власний мережевий простір назв (Network Namespace), у якому динамічно створюються віртуальні Ethernet-пари (`veth`), мости (`bridge`), overlay-тунелі (`vxlan`, `geneve`) та BPF-фільтри.

Усі ці віртуальні сутності створюються, переміщуються між просторами назв та видаляються виключно через асинхронний бінарний протокол RTNETLINK. Застарілий інструментарій `net-tools` виявився принципово не здатним працювати з мережевими просторами назв, тунелями VXLAN чи eBPF-гаками.

У 2010-х роках провідні корпоративні дистрибутиви Linux (Red Hat Enterprise Linux починаючи з версії 7, Debian починаючи з Stretch, Ubuntu з релізу 16.04 LTS та Alpine Linux) припинили включення пакета `net-tools` до базового складу системи. Сучасні хмарні дистрибутиви та мінімальні образи контейнерів взагалі не містять бінарних файлів `ifconfig` чи `route`.

## Порівняльний аналіз моделей конфігурації

Таблиця підсумовує системні та архітектурні відмінності між класичним підходом `net-tools` та сучасним `iproute2`:

| Характеристика | Класична модель (`net-tools` / `ioctl`) | Сучасна модель (`iproute2` / Netlink) |
| :--- | :--- | :--- |
| **Транспорт даних** | Системний виклик `ioctl()` над сокетом | Двосторонній сокет `AF_NETLINK` |
| **Формат метаданих** | Фіксована структура `struct ifreq` | Змінні TLV-атрибути (`struct nlattr`) |
| **Сповіщення про події** | Відсутні (потрібен періодичний Polling) | Мультикаст-групи подій ядра (RTNLGRP_LINK тощо) |
| **Множинні IP-адреси** | Штучні псевдоніми (`eth0:1`) | Динамічний список `struct in_ifaddr` на одному `net_device` |
| **Розширюваність** | Додавання нових `SIOC*` констант ламає ABI | Додавання нових типів атрибутів розширює потік без зламу сумісності |
| **Багатотаблична маршрутизація** | Не підтримується (лише одна таблиця) | Підтримується (до 255 незалежних таблиць routing policy) |
| **Швидкодія** | Високі накладні витрати на виклики `ioctl()` | Пакетна (batched) передача масивів атрибутів у єдиному буфері |

Сьогодні пакет `net-tools` визнано застарілим (deprecated) у всіх ключових дистрибутивах Linux. Сучасні системні демони — NetworkManager, systemd-networkd, Kubernetes CNI плагіни (Calico, Cilium), FRRouting — працюють виключно через асинхронний сокетний інтерфейс RTNETLINK.
