# 📜 Від UMS і TTM до GEM та PRIME: еволюція пам'яті графічного стека Linux

Графічний процесор у сучасній системі оперує гігабайтами текстур, вершинних буферів і поверхонь відтворення, переміщуючи їх між локальною відеопам'яттю та системним ОЗП на швидкостях у сотні гігабайтів за секунду. Проте на початку 2000-х років ядро Linux взагалі не мало єдиного уявлення про графічну пам'ять: кожен відеодрайвер керував регістрами на власний розсуд, а сервер віконної системи працював із привілеями суперкористувача `root`, безпосередньо відображаючи фізичні діапазони шини PCI у свій адресний простір. Розуміння того, як стек Linux пройшов шлях від прямого доступу до «заліза» через UMS до спеціалізованого менеджера трансляцій TTM, простого об'єктного інтерфейсу GEM і міжпідсистемного стандарту PRIME, розкриває причини сучасного поділу обов'язків між простором користувача та ядром.

## Ера прямого доступу та монополія X-сервера

У традиційній моделі X Window System (XFree86, а згодом ранній X.Org) ядро операційної системи розглядало графічний адаптер лише як стандартний PCI-пристрій із діапазонами вводу-виводу (англ. *Base Address Registers*, BAR). Усе керування конфігурацією відеорежимів здійснювалося в просторі користувача — такий підхід отримав назву **налаштування режимів у просторі користувача** (англ. *User Modesetting*, UMS).

Сервер X відкривав спеціальний файл `/dev/mem` або звертався до пристроїв через бібліотеку `libpciaccess`, щоб відобразити відеопам'ять і керуючі регістри чипа у свій віртуальний простір. У такій архітектурі існував лише один повноцінний розпорядник пам'яті — сам процес X-сервера. Якщо прикладній програмі (наприклад, тривимірній грі через OpenGL) був потрібен прямий доступ до апаратного прискорювача без пересилання кожного трикутника через сокет X11, використовувалася інфраструктура прямого рендерингу (англ. *Direct Rendering Infrastructure*, DRI1).

```
Модель DRI1 / UMS (до 2008 року):
+-------------------------------------------------------------+
| Простір користувача:                                        |
|   +-----------------------+     +-----------------------+   |
|   | 3D Додаток (libGL)    |     | X Server (root)       |   |
|   +-----------+-----------+     +-----------+-----------+   |
|               | (прямий доступ)             | (монополія)   |
+---------------|-----------------------------|---------------+
| Ядро Linux:   v                             v               |
|   +-----------------------------------------------------+   |
|   | Старий DRM: SAREA (спільна область), блокування      |   |
|   | Немає віртуалізації пам'яті, збої кладуть усю ОС    |   |
|   +-----------------------------------------------------+   |
+-------------------------------------------------------------+
```

У DRI1 ядро через ранній модуль DRM (англ. *Direct Rendering Manager*) надавало лише примітивні механізми синхронізації та спільну ділянку пам'яті (англ. *Shared Anonymous Real-time Exchange Area*, SAREA). Проте розподіл адрес відеопам'яті залишався статичним. Якщо два 3D-додатки одночасно виділяли пам'ять під текстури, координати розміщення в локальній пам'яті GPU узгоджувалися через блокування SAREA.

Ця схема мала критичні вади:
1. **Відсутність ізоляції пам'яті**: будь-який клієнт OpenGL міг прочитати або перезаписати екранні буфери іншого клієнта чи самого X-сервера, знаючи фізичне зміщення.
2. **Фрагментація та нестача пам'яті**: пам'ять виділялася суцільними фізичними блоками; коли обсяг текстур перевищував розмір локальної VRAM, драйвер був змушений зупиняти конвеєр і виконувати ручне копіювання даних через повільну шину AGP/PCI.
3. **Нестабільність системи**: падіння клієнта під час утримання блокування апаратного контексту призводило до мертвого зависання всієї графічної підсистеми та вимагало жорсткого перезавантаження комп'ютера.

## Проєкт TTM: універсальний менеджер трансляційних таблиць

З появою шини PCI Express і ускладненням графічних процесорів, здатних адресувати як власну виділену відеопам'ять (VRAM), так і системну оперативну пам'ять через системні таблиці трансляції графічних адрес (англ. *Graphics Translation Table*, GTT), виникла потреба в повноцінному менеджері відеопам'яті всередині ядра.

У 2006–2007 роках компанія *Tungsten Graphics* на замовлення виробників обладнання розробила підсистему **TTM** (англ. *Translation Table Manager*). Її провідними авторами стали Томас Гельстрьом (Thomas Hellström) та Ерік Енхольт (Eric Anholt). TTM проектувався як гранично потужний і універсальний фреймворк, здатний працювати з будь-якою апаратною архітектурою GPU — від інтегрованих рішень до складних дискретних карт із кількома незалежними банками пам'яті та кеш-доменами.

Ключовою ідеєю TTM стало поняття **доменів розміщення пам'яті** (англ. *placement memory domains*):
* `TTM_PL_VRAM`: швидка локальна пам'ять відеокарти;
* `TTM_PL_TT`: системна оперативна пам'ять, що відображена в адресний простір GPU через IOMMU або апаратний GTT;
* `TTM_PL_SYSTEM`: звичайні сторінки системної RAM, не прив'язані до GPU, які можуть бути вивантажені у swap.

TTM узяв на себе складну математику витіснення (англ. *eviction*): коли черговий виклик створення буфера не вміщався у VRAM, менеджер автоматично знаходив найменш використовувані буфери, ставив у чергу GPU команду DMA-копіювання їхнього вмісту в системну RAM, оновлював внутрішні таблиці сторінок пристрою та перепризначав пам'ять.

Проте TTM мав серйозний недолік: його інтерфейс із простором користувача (UAPI) був надзвичайно складним і багатослівним. Щоб виконати найпростішу операцію, драйвер користувача мусив передавати складні структури з описами конфігурацій доменів, прапорців когерентності кешу та таблиць валідації. Для інтегрованих графічних процесорів (наприклад, Intel GMA), де фізично не було окремої VRAM, а вся пам'ять була системною, оверхед TTM виявився надмірним.

## Народження GEM: простота та інтеграція з ядром

У 2008 році інженери корпорації Intel — Кіт Пакард (Keith Packard) та Ерік Енхольт — запропонували принципово простішу та елегантнішу модель, яку назвали **GEM** (англ. *Graphics Execution Manager*). Вона дебютувала в ядрі Linux 2.6.28 у грудні 2008 року.

```
Архітектурне спрощення GEM (Linux 2.6.28+):
+-------------------------------------------------------------------+
| Простір користувача:                                              |
|   Виклик створення: ioctl(fd, DRM_I915_GEM_CREATE, size)          |
|   -> Повертає простий числовий handle (1, 2, 3...)                |
+-------------------------------------------------------------------+
| Ядро Linux:                                                       |
|   1. struct drm_gem_object: спільний базовий контейнер            |
|   2. Бекенд shmem: сторінки беруться зі звичайного файлу tmpfs    |
|   3. Відсутність глобальних локів: прив'язка до drm_file          |
|   4. Синхронізація виконання та валідація при подачі команд       |
+-------------------------------------------------------------------+
```

Замість побудови складного монолітного диспетчера пам'яті із загальними правилами для всіх чипів, GEM запропонував розділити задачу на дві частини:
1. **Уніфікований об'єктний шар ядра**: кожен буфер відеопам'яті представляється структурою `struct drm_gem_object`. Він має розмір, лічильник посилань (`kref`) і унікальний локальний числовий ідентифікатор (*handle*) у межах відкритого файлового дескриптора процесу `/dev/dri/cardX`.
2. **Драйверо-специфічне виділення та розміщення**: драйвер кожного чипа реалізує власні системні виклики `ioctl` для створення буферів з урахуванням особливостей апаратного тайлінгу (англ. *tiling*), кешування та вирівнювання.

Для систем з інтегрованою графікою GEM використав перевірений механізм віртуальної пам'яті ядра — анонімну підсистему пам'яті `shmem` (англ. *shared memory / tmpfs*). Кожен GEM-об'єкт створював всередині ядра анонімний файл `struct file`, що дозволило автоматично задіяти стандартні механізми ядра Linux: виділення сторінок на вимогу (англ. *demand paging*), сторінкові збої (*page faults*), дисковий свопінг та облік лімітів пам'яті через cgroups.

## Конвергенція: TTM як бекенд для GEM

Поява GEM викликала жваву дискусію серед розробників графічного стека Linux. Драйвери для дискретних відеокарт AMD (Radeon) та NVIDIA (Nouveau) потребували складної логіки керування різними типами VRAM і не могли обмежитися лише анонімними сторінками `shmem`.

Рішенням став компроміс, який сформував архітектуру підсистеми DRM на наступні десятиліття:
* **Зовні (для простору користувача)** усі драйвери підтримують стандартну об'єктну модель **GEM** — програми оперують числовими хендлами, передають їх у команди малювання та відображають у пам'ять через стандартизовані виклики `mmap`.
* **Всередині ядра** драйвери дискретних відеокарт використовують **TTM як внутрішній бекенд** для GEM-об'єктів (`struct ttm_buffer_object` вкладається всередину або асоціюється з `struct drm_gem_object`). Драйвери ж інтегрованих чипів (Intel, ARM Mali, VC4) використовують простий `shmem`- або `dma-coherent`-бекенд.

## Проблема спільного використання та ера dma-buf/PRIME

До 2011 року GEM-об'єкти були суворо ізольованими: числовий хендл буфера мав сенс лише всередині того процесу, який відкрив відповідний вузол `/dev/dri/cardX`. Проте розвиток віконних систем нового покоління (Wayland), поява ноутбуків із гібридною графікою (Nvidia Optimus — інтегрований чип Intel виводить зображення, а дискретний чип Nvidia виконує рендеринг) та мультимедійних конвеєрів (захоплення відео з камери V4L2 прямо в текстуру OpenGL) вимагали прямого обміну пам'яттю між різними процесами й різними пристроями.

Раніше для передачі буфера використовувалися глобальні імена GEM (англ. *GEM flink names*) — 32-бітні глобальні числа. Проте механізм `flink` не мав контролю доступу: будь-який локальний процес міг перебрати числа, підключитися до чужого буфера кадру й таємно зчитувати зображення користувача.

У 2011–2012 роках зусиллями Суміта Семвала (Sumit Semwal), Інки Де (Inki Dae), Роба Кларка (Rob Clark) та Даніеля Веттера (Daniel Vetter) було розроблено універсальний механізм ядра `dma-buf`, а для графічної підсистеми DRM — розширення **PRIME**.

```
Еволюція обміну буферами в Linux DRM:
1. DRI1 SAREA (2000): Спільний незахищений блок пам'яті, блокування
2. GEM flink (2008): Глобальні 32-бітні ID (небезпечно, атака перебором)
3. PRIME / dma-buf (2012+): Передача володіння через файлові дескриптори (fd) та UNIX-сокети
```

PRIME дозволив конвертувати локальний числовий хендл GEM у стандартний анонімний файловий дескриптор `dma-buf`. Оскільки дескриптор є повноцінним об'єктом файлової системи VFS, процес може безпечно передати його іншому процесу (наприклад, клієнт передає свій буфер кадру серверу Wayland) через локальний UNIX-сокет за допомогою повідомлення `SCM_RIGHTS`. Жоден сторонній процес у системі не здатний отримати доступ до цієї пам'яті без явного дозволу власника.

Сьогодні зв'язка GEM, TTM, dma-buf та PRIME становить фундамент усього графічного та обчислювального простору Linux, забезпечуючи високу швидкість обробки даних від вбудованих контролерів до датацентрових прискорювачів штучного інтелекту.
