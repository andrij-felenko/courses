# 📋 Контракт POSIX AIO: вісім викликів, дві структури, коди відмов

Довідка для звіряння: повні сигнатури всіх функцій `aio_*`, кожне поле `struct aiocb` і `struct sigevent`, коди повернення й відмов, межі, які стандарт справді гарантує, і налаштування пулу в glibc. Потрібна тоді, коли код уже пишеться й треба точно знати, хто яке поле читає, що саме повертає виклик і чим відмова **подання** відрізняється від відмови **операції**.

Це розділення варто тримати в голові під час читання всіх таблиць нижче. Кожна операція має дві точки відмови. Перша: `aio_read` повертає `-1` і ставить `errno`, коли запит не вдалося навіть поставити в чергу. Друга: помилку самого читання віддає згодом `aio_error`. Набори кодів у цих двох точок різні й перетинаються лише частково.

---

## Заголовок, бібліотека, розрядність

```c
#define _GNU_SOURCE       /* потрібне ЛИШЕ для aio_init — і саме ПЕРЕД включеннями */
#include <aio.h>          /* усі вісім функцій, обидві структури, усі константи */
```

Довідкові сторінки досі кажуть збирати з `-lrt`, і для glibc до 2.34 це обов'язково. Починаючи з glibc 2.34 символи `aio_*` перенесено у версію `GLIBC_2.34` самої libc, а `librt.so` лишилася порожньою заглушкою заради вже злінкованих програм. Тобто на свіжій системі ключ не потрібен, але й не шкодить — лінкер приєднає порожню бібліотеку ([статичне й динамічне лінкування](topic:sys-unix/static-and-dynamic-linking) — коли символ шукається під час збірки, а коли під час запуску). Портативна збірка тримає `-lrt`.

На 32-бітних збірках із `_FILE_OFFSET_BITS=64` glibc підмінює всі вісім імен на варіанти з суфіксом `64` (`aio_read64`, `lio_listio64`, …) і `struct aiocb` на `struct aiocb64` — саме тому `strace` покаже там інші імена ([великі файли](topic:sys-unix/large-file-support) — як `off_t` розширювався до 64 бітів і що робить цей макрос). На 64-бітних платформах пари імен тотожні.

## Вісім функцій

| Виклик | Сигнатура | Повертає |
|---|---|---|
| `aio_read` | `int aio_read(struct aiocb *cb)` | `0` — стало в чергу; `-1` + `errno` |
| `aio_write` | `int aio_write(struct aiocb *cb)` | те саме |
| `aio_fsync` | `int aio_fsync(int op, struct aiocb *cb)` | те саме; `op` — `O_SYNC` або `O_DSYNC` |
| `aio_error` | `int aio_error(const struct aiocb *cb)` | стан запиту (див. нижче); `-1` + `errno` |
| `aio_return` | `ssize_t aio_return(struct aiocb *cb)` | те, що повернув би `read`/`write`/`fsync`; `-1` |
| `aio_suspend` | `int aio_suspend(const struct aiocb *const list[], int n, const struct timespec *timeout)` | `0` — щось завершилося; `-1` + `errno` |
| `aio_cancel` | `int aio_cancel(int fd, struct aiocb *cb)` | `AIO_CANCELED` / `AIO_NOTCANCELED` / `AIO_ALLDONE`; `-1` |
| `lio_listio` | `int lio_listio(int mode, struct aiocb *const list[], int n, struct sigevent *sevp)` | `0`; `-1` + `errno` |

`aio_cancel(fd, NULL)` скасовує **всі** запити на дескрипторі. `aio_suspend` із `timeout`, що задає нульовий проміжок, перетворюється на опитування без сну.

## `struct aiocb` — поле за полем

```c
struct aiocb {
    int             aio_fildes;     /* дескриптор */
    off_t           aio_offset;     /* абсолютне зміщення у файлі */
    volatile void  *aio_buf;        /* буфер */
    size_t          aio_nbytes;     /* скільки байтів */
    int             aio_reqprio;    /* наскільки ЗНИЗИТИ пріоритет запиту */
    struct sigevent aio_sigevent;   /* як сповістити про завершення */
    int             aio_lio_opcode; /* LIO_READ / LIO_WRITE / LIO_NOP */
    /* далі — внутрішні поля реалізації */
};
```

Порядок полів реалізацією не гарантований, тож ініціалізація списком через кому непортативна. Заповнюють поіменно, попередньо обнуливши структуру.

| Поле | `aio_read` | `aio_write` | `aio_fsync` | `lio_listio` |
|---|---|---|---|---|
| `aio_fildes` | так | так | **так** | так |
| `aio_offset` | так | так, крім `O_APPEND` | ігнорується | так |
| `aio_buf` | так | так | ігнорується | так |
| `aio_nbytes` | так | так | ігнорується | так |
| `aio_reqprio` | так | так | ігнорується | так |
| `aio_sigevent` | так | так | **так** | так, на КОЖЕН елемент окремо |
| `aio_lio_opcode` | ігнорується | ігнорується | ігнорується | **так** |

Три речі в цій таблиці мають нюанси, які легко проґавити.

**`aio_offset`** — абсолютне, як у `pread`: зміщення дескриптора не читається й не зсувається. Але якщо в дескрипторі стоїть `O_APPEND`, `aio_write` це поле **ігнорує** й дописує в кінець у порядку викликів. Так само для дескрипторів, у яких позиції немає взагалі (канали, сокети, термінали) — там запис теж просто дописується.

**`aio_reqprio`** може пріоритет лише **знизити**, ніколи не підняти: за стандартом запит виконується з пріоритетом «пріоритет процесу мінус `aio_reqprio`». Там, де набір реалізовано пулом потоків у просторі користувача (Linux, glibc), поле до пристрою не доходить — воно лише впорядковує чергу всередині бібліотеки. Припустимий діапазон — від нуля до `sysconf(_SC_AIO_PRIO_DELTA_MAX)`; вихід за нього дає `EINVAL` ([пріоритети, nice і реальночасові класи](topic:sys-unix/priority-nice-realtime) — з чого складається пріоритет задачі й хто має право його змінювати).

**Час життя.** Якщо `aio_buf` або сама `aiocb` перестають бути дійсними адресами до завершення операції, поведінка не визначена — це формулювання POSIX, а не порада. Так само не визначено подання того самого блока вдруге, поки перший запит у польоті, і зміну блока чи буфера в цей час.

## `struct sigevent` — як просити сповіщення

```c
union sigval {
    int   sival_int;
    void *sival_ptr;
};

struct sigevent {
    int              sigev_notify;              /* SIGEV_NONE / SIGNAL / THREAD */
    int              sigev_signo;               /* який сигнал                  */
    union sigval     sigev_value;               /* довільне значення програми   */
    void           (*sigev_notify_function)(union sigval);
    pthread_attr_t  *sigev_notify_attributes;   /* NULL — типові атрибути       */
    pid_t            sigev_notify_thread_id;    /* лише POSIX-таймери           */
};
```

| `sigev_notify` | Що робить | Які поля читає |
|---|---|---|
| `SIGEV_NONE` | нічого; стан питають самі | жодного |
| `SIGEV_SIGNAL` | надсилає процесові сигнал | `sigev_signo`, `sigev_value` |
| `SIGEV_THREAD` | викликає функцію, ніби вона — початок нового потоку | `sigev_notify_function`, `sigev_value`, `sigev_notify_attributes` |
| `SIGEV_THREAD_ID` | розширення Linux; **для AIO не вживається** | `sigev_notify_thread_id` |

Ця структура спільна з POSIX-таймерами й чергами повідомлень, і саме звідти в ній останнє поле ([таймери процесу](topic:sys-unix/process-timers) — той самий `sigevent` під `timer_create`).

`sigev_value` — єдиний канал, яким сповіщення каже, **який саме** запит скінчився. Під `SIGEV_SIGNAL` обробник має бути встановлений із `SA_SIGINFO` і читає значення з `info->si_value`; під `SIGEV_THREAD` те саме значення приходить єдиним аргументом функції. Звична схема — покласти туди `sival_ptr` на власну `aiocb`.

Обробник під `SIGEV_SIGNAL` виконується посеред довільного місця програми, тож у ньому дозволено лише вузький перелік функцій ([що можна робити в обробнику сигналу](topic:sys-unix/async-signal-safety) — чому `malloc` і `printf` там заборонені).

Під `SIGEV_THREAD` `sigev_notify_attributes` — це покажчик на `pthread_attr_t`, тобто ті самі атрибути, що й у `pthread_create`; `NULL` означає типові. Одну властивість цих атрибутів варто прочитати уважно: потік сповіщення ніхто не приєднує, тому стандарт вимагає створювати його **відокремленим**, а якщо в атрибутах виставлено `PTHREAD_CREATE_JOINABLE` — поведінка не визначена. Найчастіше атрибути тут задають заради розміру стека, бо усталений стек на кожне сповіщення — помітна витрата, коли завершень багато.

## Стан і результат

`aio_error` можна кликати скільки завгодно разів; `aio_return` — рівно один раз і лише після того, як `aio_error` перестала віддавати `EINPROGRESS`.

| `aio_error` віддала | Значення | Що робити далі |
|---|---|---|
| `EINPROGRESS` | запит ще в польоті | чекати; `aio_return` кликати не можна |
| `0` | завершено успішно | `aio_return` дасть кількість байтів |
| `ECANCELED` | запит скасовано | `aio_return` дасть `-1`; забрати все одно треба |
| інший код | операція відмовила | той самий код, що поставив би `errno` синхронний `read`/`write`/`fsync` |
| `-1` | відмовила **сама `aio_error`** | `errno`: `EINVAL` — блок не описує чинного запиту або результат уже забрано |

Із таблиці випливає правило, яке рятує від витоків: результат треба забрати навіть у скасованого й у невдалого запиту, бо `aio_return` — це водночас і «віддай значення», і «звільни запис про запит».

## `lio_listio`: пачка

| Константа | Роль | Дія |
|---|---|---|
| `LIO_WAIT` | `mode` (`0`) | чекати, доки виконаються всі; `sevp` ігнорується |
| `LIO_NOWAIT` | `mode` (`1`) | повернутися негайно; `sevp` сповіщає про завершення **всієї пачки** |
| `LIO_READ` | `aio_lio_opcode` (`0`) | елемент читає, як `aio_read` |
| `LIO_WRITE` | `aio_lio_opcode` (`1`) | елемент пише, як `aio_write` |
| `LIO_NOP` | `aio_lio_opcode` (`2`) | елемент пропустити — дірка в масиві без перебудови |

Код повернення описує лише сам виклик, а не долю окремих операцій: навіть після `0` під `LIO_WAIT` кожен елемент треба звірити своїм `aio_error`. `EIO` означає рівно те саме навпаки — «принаймні одна відмовила, розбирайтеся поелементно».

Сповіщень тут два різні рівні, і плутати їх дорого. Аргумент `sevp` спрацьовує **один раз**, коли доробить уся пачка. Поле `aio_sigevent` кожного елемента спрацьовує **на своєму** запиті. Обидва механізми чинні одночасно: якщо блоки прийшли з коду для `aio_read` і в кожному лишився `SIGEV_SIGNAL`, програма отримає `n` окремих сигналів плюс іще один від `sevp`. Коли потрібне лише групове сповіщення, у кожному елементі ставлять `SIGEV_NONE`.

## `aio_cancel`: три відповіді

| Відповідь | Значення | Стан запитів |
|---|---|---|
| `AIO_CANCELED` (`0`) | скасовано все, що просили | `aio_error` → `ECANCELED`, `aio_return` → `-1` |
| `AIO_NOTCANCELED` (`1`) | принаймні один уже в роботі | його доведеться дочекатися звичайним шляхом |
| `AIO_ALLDONE` (`2`) | усе вже виконалося раніше | результати чекають на `aio_return` |
| `-1` | відмовив сам виклик | `errno`: `EBADF` |

## Коди відмов

| Код | Де | Причина |
|---|---|---|
| `EAGAIN` | `aio_read`, `aio_write`, `aio_fsync`, `lio_listio` | забракло ресурсів на постановку в чергу; для `lio_listio` — ще й перевищення `AIO_MAX` |
| `EAGAIN` | `aio_suspend` | вийшов `timeout`, а не завершився жоден запит |
| `EBADF` | `aio_read` | дескриптор не відкрито на читання |
| `EBADF` | `aio_write`, `aio_fsync` | дескриптор недійсний або не відкритий на запис |
| `EBADF` | `aio_cancel` | `fd` не є дійсним дескриптором |
| `EINVAL` | `aio_read`, `aio_write` | неприпустимі `aio_offset`, `aio_reqprio` чи `aio_nbytes` |
| `EINVAL` | `aio_fsync` | `op` не `O_SYNC` і не `O_DSYNC`, або файлова система такого не вміє |
| `EINVAL` | `aio_error`, `aio_return` | блок не описує чинного запиту — зокрема тому, що результат уже забрано |
| `EINVAL` | `lio_listio` | невідомий `mode` або `n` більший за `AIO_LISTIO_MAX` |
| `EINTR` | `aio_suspend`, `lio_listio` під `LIO_WAIT` | прийшов сигнал — можливо, **сигнал завершення одного з власних запитів** |
| `EIO` | `lio_listio` | принаймні одна операція пачки відмовила |
| `EOVERFLOW` | `aio_read` | зміщення плюс довжина виходить за максимальне зміщення файлу |
| `ENOSYS` | будь-який | функції в системі немає взагалі |

Пастка з `EINTR` тут своя, не загальна. Сповіщення про завершення саме є сигналом, і воно ж уриває `aio_suspend`, яка на це завершення й чекала. Тому цикл із перезапуском обов'язковий, а перевіряти після нього треба стан запитів, а не код повернення ([EINTR: перервані виклики й перезапуск](topic:sys-unix/eintr-and-restart) — чому виклик віддає помилку замість результату й хто мусить його поновити).

Ще одне обмеження реалізації довідка glibc визнає прямо, у розділі вад: `aio_suspend` **не є async-signal-safe**, усупереч вимозі POSIX. Отже кликати її з обробника сигналу не можна — саме там, де найбільше кортить, бо обробник під `SIGEV_SIGNAL` виглядає природним місцем дочекатися решти пачки.

## Межі стандарту

```c
#include <unistd.h>   /* _POSIX_ASYNCHRONOUS_IO, sysconf */
#include <limits.h>   /* AIO_MAX, AIO_LISTIO_MAX — якщо визначені */
```

| Що питаємо | `sysconf` | Мінімум за POSIX | Linux + glibc |
|---|---|---|---|
| набір узагалі є | `_SC_ASYNCHRONOUS_IO` | опція | `200809L` (макрос `_POSIX_ASYNCHRONOUS_IO` визначено) |
| запитів у польоті | `_SC_AIO_MAX` | `_POSIX_AIO_MAX` = **1** | `-1` — межа невизначена |
| елементів у `lio_listio` | `_SC_AIO_LISTIO_MAX` | `_POSIX_AIO_LISTIO_MAX` = **2** | `-1` — межа невизначена |
| наскільки можна знизити пріоритет | `_SC_AIO_PRIO_DELTA_MAX` | `0` | `20` |

Дві клітинки з `-1` читаються не як помилка, а як «межі немає»: `sysconf` віддає `-1`, не чіпаючи `errno`, коли константи в `<limits.h>` немає. Щоб відрізнити це від справжньої відмови, `errno` обнуляють **перед** викликом і дивляться на нього після.

Перевірок наявності набору теж дві, і жодна не заміняє іншу. Під час компіляції дивляться на макрос `_POSIX_ASYNCHRONOUS_IO` у `<unistd.h>`: він каже лише, що заголовки й прототипи є. Під час виконання відповідь дає `ENOSYS` від першої ж функції — цим кодом система заявляє, що інтерфейс оголошено, але не реалізовано. Тому `ENOSYS` у таблиці відмов стоїть навпроти «будь-який»: це не помилка конкретного запиту, а відповідь про сам набір ([POSIX: що саме стандартизовано](topic:sys-unix/posix-standard) — обов'язкові частини стандарту й ті, що лишилися необов'язковими опціями).

> 🔧 **Навіщо це.** Дві жирні цифри в колонці мінімумів — головне, що ця таблиця має сказати. Портативна програма має право розраховувати рівно на **один** запит у польоті й **два** елементи в списку; усе понад це — ласка конкретної системи. Тому переносний код, який хоче глибокої черги, мусить не питати межу, а бути готовим до `EAGAIN` на кожному поданні й подавати рештки згодом.

## `aio_init`: розширення glibc

Оскільки в Linux набір реалізовано пулом потоків у просторі користувача, glibc дає позастандартний важіль до цього пулу:

```c
#define _GNU_SOURCE
#include <aio.h>

void aio_init(const struct aioinit *init);

struct aioinit {
    int aio_threads;    /* стеля робочих потоків;      усталено 20, мінімум 1  */
    int aio_num;        /* очікуваних одночасних запитів; усталено 64, мін. 32 */
    int aio_locks;      /* не вживається */
    int aio_usedba;     /* не вживається */
    int aio_debug;      /* не вживається */
    int aio_numusers;   /* не вживається */
    int aio_idle_time;  /* секунд простою до смерті потоку; усталено 1         */
    int aio_reserved;
};
```

Викликати треба **до** першої функції набору — пізніше воно не подіє. Менше за 32 в `aio_num` округлюється вгору; `aio_idle_time` з'явилося в glibc 2.4. Функції немає ні в POSIX, ні в BSD, тож її ховають за `#ifdef __GLIBC__`.

## Мінімальний робочий виклик

Нижче — повний цикл із коректним часом життя блоків, перезапуском після сигналу й забиранням кожного результату рівно один раз.

```c
#include <aio.h>
#include <errno.h>
#include <fcntl.h>
#include <signal.h>      /* SIGEV_*: glibc віддає їх і через <aio.h>, POSIX — звідси */
#include <stdio.h>
#include <string.h>
#include <unistd.h>

#define N   4
#define BLK 4096

int main(void)
{
    int fd = open("data.bin", O_RDONLY);
    if (fd < 0) { perror("open"); return 1; }

    /* блоки й буфери мусять пережити виклик, тому не в кадрі, що зникне */
    static struct aiocb cb[N];
    static char         buf[N][BLK];
    const struct aiocb *list[N];

    for (int i = 0; i < N; i++) {
        memset(&cb[i], 0, sizeof cb[i]);          /* обнулення — умова контракту */
        cb[i].aio_fildes = fd;
        cb[i].aio_buf    = buf[i];
        cb[i].aio_nbytes = BLK;
        cb[i].aio_offset = (off_t)i * BLK;        /* абсолютне зміщення */
        cb[i].aio_sigevent.sigev_notify = SIGEV_NONE;
        list[i] = &cb[i];
        if (aio_read(&cb[i]) == -1) { perror("aio_read"); return 1; }
    }

    for (int left = N; left > 0; ) {
        if (aio_suspend(list, N, NULL) == -1 && errno != EINTR) {
            perror("aio_suspend");                /* EAGAIN не буває: timeout = NULL */
            return 1;
        }
        for (int i = 0; i < N; i++) {
            if (list[i] == NULL) continue;        /* результат уже забрано */
            int e = aio_error(&cb[i]);
            if (e == EINPROGRESS) continue;
            ssize_t n = aio_return(&cb[i]);       /* рівно один раз на запит */
            if (n == -1) fprintf(stderr, "запит %d: %s\n", i, strerror(e));
            else         printf("запит %d: %zd байтів\n", i, n);
            list[i] = NULL;                       /* NULL у списку дозволено */
            left--;
        }
    }
    close(fd);                                    /* лише коли забрано все */
    return 0;
}
```

```
$ cc -o r r.c -lrt && ./r
запит 0: 4096 байтів
запит 1: 4096 байтів
запит 2: 4096 байтів
запит 3: 1024 байтів
```

Останній рядок показує коротке читання на кінці файлу — `aio_return` віддає ту саму усічену кількість, що й звичайний `read`, і це не помилка. А `close` стоїть після циклу не для охайності: стандарт не зобов'язує закриття ні скасовувати висячі запити, ні чекати на них, тож дескриптор закривають лише тоді, коли по кожному запиту вже викликано `aio_return`.
