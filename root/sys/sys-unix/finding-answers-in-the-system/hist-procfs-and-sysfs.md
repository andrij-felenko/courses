# 📜 Від /dev/kmem до kobjects: як Unix навчився описувати себе

У ранніх версіях Unix (Research Unix V7 та 3BSD на рубежі 1970–1980-х років) операційна система не мала жодного штатного механізму для того, щоб процес міг запитати в ядра його поточний стан людською мовою. Коли утилітам `ps`, `pstat`, `vmstat` чи `netstat` потрібно було дізнатися список запущених процесів, відкриті сокети або використання пам'яті, вони робили щось дике за сучасними мірками: відкривали спеціальний файл символьного пристрою `/dev/kmem` (прямий доступ до віртуальної пам'яті ядра) або `/dev/mem` (фізична оперативна пам'ять) і зчитували сирі байти безпосередньо зі структур мови C у просторі ядра.

Щоб знати, за якими саме адресами в пам'яті лежать глобальні масиви `proc`, `file` чи змінні `nswap` та `avenrun`, системна утиліта мусила виконати низку підготовчих дій: відкрити скомпільований бінарний файл ядра на диску (`/vmunix` або `/boot/vmlinux`), вичитати з нього таблицю символів за допомогою бібліотечної функції `nlist()` (англ. *name list*), витягнути абсолютну віртуальну адресу потрібної структури, а потім викликати `lseek()` на дескрипторі `/dev/kmem` і зчитати структуру прямо у свій буфер.

```
        ┌───────────────────────────────────────────────┐
        │        Утиліта ps у Research Unix V7          │
        └───────┬───────────────────────────────┬───────┘
                │ 1. nlist("/vmunix")           │ 2. lseek() + read()
                ▼                               ▼
    ┌───────────────────────┐       ┌───────────────────────┐
    │  Файл ядра на диску   │       │ Пряма пам'ять ядра    │
    │  /vmunix (a.out/ELF)  │       │ /dev/kmem (сирі байти)│
    │  [таблиця символів]   │       │ [масив struct proc]   │
    └───────────────────────┘       └───────────────────────┘
```

Цей підхід мав три фундаментальні вади, які перетворювали системне адміністрування на мінне поле:

1. **Фатальна бінарна крихкість (ABI-залежність)**: найменша зміна конфігурації ядра, додавання поля у внутрішню структуру мови C, зміна вирівнювання компілятором чи перекомпіляція ядра з іншим набором опцій зміщували адреси полів у пам'яті. Утиліта `ps`, скомпільована для попередньої збірки ядра, читала дані за застарілими зміщеннями й виводила безглуздий набір символів або аварійно завершувалася із `SIGSEGV`. Кожне оновлення ядра вимагало синхронної перекомпіляції всього діагностичного інструментарію системи.
2. **Дірки в системній безпеці**: читання `/dev/kmem` вимагало повних привілеїв суперкористувача або встановлення біта `setgid` на групу `kmem` (чи `setuid root` на бінарник утиліти). Оскільки `ps` була повсякденною командою загального користування, будь-яка вразливість у її коді (переповнення буфера, помилки парсингу змінних оточення чи прапорців) миттєво давала зловмиснику змогу читати довільну пам'ять ядра, модифікувати таблицю дескрипторів або переписати власний `struct proc`, отримавши права `root`.
3. **Неузгодженість та гонки читання (dirty reads)**: утиліта читала масив процесів `proc[]` поелементно через серію викликів `read()`. Якщо під час цього циклу ядро перемикало контекст, виконувало `fork()` або видаляло завершений процес (`exit()`), утиліта отримувала «розірваний» стан — напівзаповнені структури та недійсні покажчики на адресні простори.

## Поява procfs: процес як віртуальний файл і каталог

У 1984 році Том Кілліан (Tom Killian) з Bell Laboratories представив на літній конференції USENIX доповідь *«Processes as Files»*, у якій запропонував радикальну альтернативу прямому читанню пам'яті: віртуальну файлову систему процесів `procfs`. Її монтували у каталог `/proc`, і кожен активний процес в операційній системі Eighth Edition Research Unix отримував власний файл, названий його числовим ідентифікатором (наприклад, `/proc/01234`).

Головною метою Кілліана було створення надійного середовища для зневаджувача `pi`, розробленого Томом Каргіллом (Tom Cargill). До цього налагодження програм спиралося на системний виклик `ptrace()`, який був повільним і незручним: кожна операція читання або запису одного машинного слова вимагала окремого системного виклику та перемикання контексту ядра. У реалізації Кілліана зневаджувач просто відкривав `/proc/<PID>` через стандартний виклик `open()`:
* Виклик `read()` на файлі процесу читав його адресний простір блоками довільного розміру;
* Виклик `write()` дозволяв модифікувати змінні та вставляти інструкції точок зупину (`breakpoint`);
* Системні виклики `ioctl()` над дескриптором файлу надавали повне керування процесом: команди `PIOCSTOP` (зупинити виконання), `PIOCRUN` (відновити роботу), `PIOCGREG` (зчитати регістри CPU), `PIOCSREST` (відновити регістри), `PIOCTRACE` (перехоплювати системні виклики).

```
 ┌───────────────────────────────────────────────────────────┐
 │       Eighth Edition Unix (1984, Tom Killian):            │
 │       /proc/<PID>  ───> єдиний файл образу процесу        │
 │       (читання/запис пам'яті + керування через ioctl)     │
 └─────────────────────────────┬─────────────────────────────┘
                               │
                               ▼
 ┌───────────────────────────────────────────────────────────┐
 │       Plan 9 from Bell Labs (кінець 1980-х):              │
 │       /proc/<PID>/ ───> каталог спеціалізованих файлів    │
 │       ├── ctl     (текстові команди: "stop", "kill")      │
 │       ├── status  (текстовий рядок стану та CPU-часу)     │
 │       ├── mem     (образ пам'яті для зневадження)         │
 │       ├── note    (черга вхідних сигналів)                │
 │       └── segment (опис ділянок пам'яті)                  │
 └─────────────────────────────┬─────────────────────────────┘
                               │
                               ▼
 ┌───────────────────────────────────────────────────────────┐
 │       System V Release 4 / Solaris (1989–1990):           │
 │       /proc/<PID>/ ───> каталог типізованих бінарних структур│
 │       ├── psinfo  (struct psinfo для ps)                  │
 │       ├── status  (struct prstatus: регістри, сигнали)    │
 │       └── map     (структури struct prmap адресного простору)│
 └───────────────────────────────────────────────────────────┘
```

Ідею розділення образу процесу на окремі аспекти довели до досконалості творці операційної системи Plan 9 у Bell Labs (Роб Пайк, Кен Томпсон, Денніс Рітчі). У Plan 9 процес перестав бути монолітним файлом і став каталогом. Замість непрозорих бінарних `ioctl()`-команд керування здійснювалося записом звичайних ASCII-рядків у файл `ctl` (наприклад, `echo kill > /proc/123/ctl`), а текстовий файл `status` дозволяв дізнатися ім'я програми та витрачений час CPU без використання компілятора мови C.

Комерційні гілки Unix, зокрема System V Release 4 (SVR4, розробка AT&T під керівництвом Роджера Фолкнера та Рона Гомеса) і SunOS/Solaris, адаптували концепцію каталогу процесів, але зробили ставку на **структуровані бінарні файли**. Файли `/proc/<PID>/psinfo` та `/proc/<PID>/status` повертали фіксовані C-структури ядра (`struct psinfo`, `struct prstatus`). Це забезпечувало високу швидкість виконання для системних утиліт, але зберігало жорстку прив'язку утиліт до системних заголовкових файлів `<sys/procfs.h>`.

## Перенесення у Linux: вибір тексту та великий хаос у /proc

У вересні 1992 року (починаючи з ядра Linux 0.97.3) Лінус Торвальдс (Linus Torvalds) та перші розробники ядра включили підтримку `procfs` до Linux. 

Торвальдс обрав інший вектор розвитку, ніж автори SVR4: **усі файли у `/proc` мали бути потоками відкритого ASCII-тексту**.

Це рішення мало глибокі наслідки для екосистеми:
1. **Прозорість та доступність без компіляції**: будь-який інженер чи shell-сценарій міг прочитати стан процесу за допомогою `cat`, профільтрувати рядки через `grep` або розпарсити значення через `awk` без необхідності компілювати спеціальні C-програми зі складними системними заголовками.
2. **Архітектурна незалежність**: текстовий інтерфейс згладжував відмінності між 32-бітними та 64-бітними архітектурами, порядком байтів (Little-Endian / Big-Endian) і специфічним вирівнюванням структур у пам'яті на x86, Alpha, SPARC чи m68k.

```
                    ┌────────────────────────────────┐
                    │     Linux procfs (1993+)       │
                    │   Текстові ASCII-потоки VFS    │
                    └───────────────┬────────────────┘
                                    │
          ┌─────────────────────────┴─────────────────────────┐
          ▼                                                   ▼
┌───────────────────────────────────┐       ┌───────────────────────────────────┐
│     Процесний вимір (/proc/<PID>/)│       │    Системна діагностика ядра      │
│  ├── cmdline (аргументи запуску)  │       │  ├── /proc/cpuinfo (процесор)     │
│  ├── status  (зведений зріз стану)│       │  ├── /proc/meminfo (деталі RAM)   │
│  ├── maps    (віртуальна пам'ять) │       │  ├── /proc/net/    (мережевий стек)│
│  └── fd/     (відкриті дескриптори)│      │  └── /proc/sys/    (вузли sysctl) │
└───────────────────────────────────┘       └───────────────────────────────────┘
```

Проте зручність текстового `/proc` зіграла з архітектурою ядра злий жарт. Оскільки в Linux 1.x та 2.0 не існувало єдиного стандартизованого механізму для конфігурації та опису апаратного забезпечення, розробники підсистем ядра почали використовувати `/proc` як універсальне сховище для будь-якої діагностики:
* **Апаратне забезпечення**: `/proc/cpuinfo`, `/proc/interrupts`, `/proc/ioports`, `/proc/dma`, `/proc/pci`, `/proc/mtrr`;
* **Мережевий стек**: `/proc/net/tcp`, `/proc/net/dev`, `/proc/net/arp`, `/proc/net/route`, `/proc/net/snmp`;
* **Керування пам'яттю та кешами**: `/proc/meminfo`, `/proc/slabinfo`, `/proc/swaps`, `/proc/buddyinfo`;
* **Накопичувачі та шини**: `/proc/partitions`, `/proc/ide/`, `/proc/scsi/`, `/proc/bus/`;
* **Глобальні налаштування ядра**: дерево `/proc/sys/` (проєкція механізму `sysctl`).

До кінця 1990-х років (ядра серії Linux 2.2 та 2.4) `/proc` перетворився на некероване звалище. Кожен автор драйвера вигадував власний унікальний формат:
* Один драйвер виводив таблицю з фіксованими пробілами між колонками;
* Другий розділяв поля символами табуляції;
* Третій друкував багаторядковий описовий текст із двокрапками;
* Четвертий скидав шістнадцяткові дампи регістрів.

Будь-яка спроба системних утиліт (`procps`, `net-tools`, `hdparm`, `ifconfig`) отримати дані перетворювалася на крихкий парсинг через `sscanf()` або регулярні вирази. Якщо розробник ядра додавав нову колонку у `/proc/net/dev` або змінював заголовок у `/proc/meminfo`, системні утиліти раптово ламалися або інтерпретували одні лічильники замість інших.

Ба більше, сама назва `/proc` (*process filesystem*) втратила первісний зміст: у файловій системі процесів більшість вузлів описувала термодавачі процесора, таймінги шини IDE, правила міжмережевого екрана та черги переривань. Системі була потрібна нова, сувора архітектурна модель.

## Об'єктна революція: kobject, Driver Model та народження sysfs

Каталізатором змін на початку 2000-х років стала криза керування живленням та підтримка «гарячого» підключення обладнання (ACPI, USB, CardBus/PCMCIA, PCI Hotplug).

У старих ядрах Linux пристрої існували як розрізнені структури, розкидані по коду конкретних драйверів. Коли ноутбук переходив у режим сну (suspend to RAM), ядро мусило вимкнути живлення всіх компонентів. Проте зробити це простим лінійним перебором списку драйверів неможливо:
* Якщо вимкнути кореневий міст PCI раніше за підключений до нього USB-контролер, драйвер USB зависне під час спроби зберегти стан регістрів через знеструмлену шину;
* Якщо вимкнути SATA-контролер раніше за жорсткий диск, диск не встигне запаркувати головки й скинути кеш запису.

Для коректного керування енергоспоживанням ядро мусило знати **точну топологічну ієрархію**: при переході в сон пристрої вимикаються строго знизу вгору (від листя дерева до кореня), а під час пробудження (resume) ініціалізуються строго згори вниз (від кореневих шин до кінцевих пристроїв).

Під час розробки Linux 2.5 (2001–2003 роки) Патрік Мошель (Patrick Mochel) за активної участі Грега Кроа-Гартмана (Greg Kroah-Hartman) та Рассела Кінга (Russell King) спроєктував єдину модель пристроїв — **Linux Driver Model**.

В її основу було закладено фундаментальну структуру **`struct kobject`**:

```
                    ┌────────────────────────────────┐
                    │       struct kobject           │
                    │  - struct kref (лічильник ref) │
                    │  - struct kobject *parent      │
                    │  - struct kobj_type *ktype     │
                    │  - struct sysfs_ops *sysfs_ops │
                    └───────────────┬────────────────┘
                                    │
          ┌─────────────────────────┴─────────────────────────┐
          ▼                                                   ▼
┌───────────────────────────────────┐       ┌───────────────────────────────────┐
│     Ієрархія в пам'яті ядра       │       │    Проєкція у VFS (/sys)          │
│  [pci_root_bridge]                │       │  /sys/devices/pci0000:00/         │
│         │                         │       │         │                         │
│         ▼                         │       │         ▼                         │
│  [pci_sata_controller]            │       │  ├── 0000:00:1f.2/ (контролер)    │
│         │                         │       │         │                         │
│         ▼                         │       │         ▼                         │
│  [ata_disk_device]                │       │  └── ata1/host0/target0:0:0/block/│
└───────────────────────────────────┘       └───────────────────────────────────┘
```

Структура `kobject` реалізувала чотири базові механізми:
1. **Контроль часу життя об'єкта**: вбудований лічильник посилань `struct kref`. Пам'ять об'єкта ядра ніколи не звільняється, доки на нього посилається хоча б один відкритий дескриптор у просторі користувача або інша підсистема ядра.
2. **Ієрархічні зв'язки**: покажчик `parent` зв'язує об'єкти в орієнтоване дерево топології.
3. **Експорт у файлову систему**: кожен зареєстрований `kobject` автоматично стає каталогом у VFS, а його поля — файлами атрибутів (`struct attribute`), читання й запис яких викликають прив'язані обробники `show()` та `store()`.
4. **Розсилка подій підключення (uevent)**: поява чи видалення `kobject` генерує сповіщення через Netlink-сокет у простір користувача, які приймає демон `udev` для динамічного створення вузлів у `/dev` і завантаження модулів.

Для візуалізації цього об'єктного дерева на початку 2002 року Мошель створив віртуальну файлову систему: спочатку вона мала назву `ddfs` (Device Driver Filesystem), згодом `driverfs` (Linux 2.5.1, січень 2002), а у жовтні 2002 року (Linux 2.5.45) після виокремлення від суто драйверних структур дістала остаточну назву **`sysfs`**. У фінальному релізі ядра Linux 2.6 (грудень 2003) `sysfs` стала стандартом і була змонтована у `/sys`.

### Залізні правила sysfs

Щоб запобігти повторенню хаосу `/proc`, автори `sysfs` встановили жорсткі архітектурні інваріанти:

* **Один атрибут — один файл**: кожен файл у `/sys` містить рівно одне текстове значення чи число, завершене символом переведення рядка (`\n`). Жодних складних таблиць, заголовків колонок та багатосторінкових описів. Якщо пристрій має швидкість (`speed`), режим дуплексу (`duplex`) та робочий стан (`operstate`), це три окремі файли в каталозі інтерфейсу.
* **Обмеження розміру у сторінку**: розмір згенерованого вмісту одного атрибута не може перевищувати розмір апаратної сторінки пам'яті (`PAGE_SIZE`, типово 4096 байтів). Це усуває складні буферизації та гарантує передбачуваність роботи пам'яті ядра.
* **Суворе розділення за ортогональними вимірами**:
  * `/sys/devices/` — єдине канонічне фізичне дерево всього підключеного обладнання;
  * `/sys/bus/` — каталоги шин (`pci`, `usb`, `i2c`, `platform`), що пов'язують шинні пристрої з відповідними драйверами;
  * `/sys/class/` — класифікація за функціональним призначенням (`net`, `block`, `tty`, `drm`, `power_supply`), де вузли є символьними посиланнями на відповідні фізичні записи у `/sys/devices/`.

Використання символьних посилань дозволило операційній системі мати одночасно кілька логічних проєкцій того самого заліза без дублювання об'єктів у пам'яті ядра.

## Спеціалізація просторів: debugfs, tracefs, cgroupfs та configfs

Поява `sysfs` встановила високий стандарт дисципліни: будь-який атрибут, розміщений у `/sys`, стає частиною публічного інтерфейсу ядра (Kernel ABI). Розробники ядра не мають права змінювати його назву, формат або семантику, оскільки це зламає утиліти простору користувача (`udev`, `ip`, `lsblk`).

Проте ядру була потрібна гнучкість для експериментів, зневадження та специфічних задач керування. Це спричинило появу спеціалізованих віртуальних файлових систем нового покоління:

```
 ┌────────────────────────────────────────────────────────────────────────┐
 │        Спеціалізація віртуальних файлових систем у сучасному Linux     │
 ├──────────────┬────────────────────────┬────────────────────────────────┤
 │   Шлях VFS   │     Тип файлової       │      Призначення та семантика  │
 │              │        системи         │                                │
 ├──────────────┼────────────────────────┼────────────────────────────────┤
 │ /proc/       │ procfs                 │ Стан процесів (task_struct) та │
 │              │                        │ глобальні лічильники ядра      │
 ├──────────────┼────────────────────────┼────────────────────────────────┤
 │ /sys/        │ sysfs (kobject)        │ Стабільна об'єктна модель      │
 │              │                        │ пристроїв, шин та драйверів    │
 ├──────────────┼────────────────────────┼────────────────────────────────┤
 │ /sys/kernel/ │ debugfs                │ Вільне поле для експериментів  │
 │ debug/       │ (Greg Kroah-Hartman)   │ та зневадження (без гарантій   │
 │              │                        │ стабільності ABI, root-only)   │
 ├──────────────┼────────────────────────┼────────────────────────────────┤
 │ /sys/kernel/ │ tracefs                │ Інтерфейс підсистеми Ftrace,   │
 │ tracing/     │ (Steven Rostedt)       │ точок трасування та kprobes    │
 ├──────────────┼────────────────────────┼────────────────────────────────┤
 │ /sys/fs/     │ cgroupfs (v1/v2)       │ Ієрархічне обмеження ресурсів  │
 │ cgroup/      │                        │ (CPU, RAM, I/O) через каталоги │
 ├──────────────┼────────────────────────┼────────────────────────────────┤
 │ /sys/kernel/ │ configfs               │ Створення об'єктів ядра з user-│
 │ config/      │ (Joel Becker)          │ space за допомогою mkdir/rmdir │
 └──────────────┴────────────────────────┴────────────────────────────────┘
```

1. **`debugfs` (Linux 2.6.11, 2004 рік, Грег Кроа-Гартман)**: створена як свідомий антипод `sysfs`. У `debugfs` діє єдине правило: **жодних правил і жодних гарантій стабільності**. Вона монтується за адресою `/sys/kernel/debug/` з правами доступу лише для адміністратора (`0700`). Тут автори драйверів можуть вільно експортувати внутрішні діагностичні змінні, сирі дампи пам'яті та точки ін'єкції збоїв (`fault_injection`), не турбуючись про збереження сумісності у наступних релізах.
2. **`tracefs` (Linux 4.1, 2015 рік, Стівен Ростедт)**: спочатку підсистема динамічного трасування ядра Ftrace жила всередині `debugfs` (`/sys/kernel/debug/tracing/`). Проте доступ до Ftrace був потрібен утилітам моніторингу та профілювання (наприклад, `perf` чи `trace-cmd`), тоді як відкривати повний доступ до `debugfs` на бойових серверах було небезпечно. Ростедт виокремив трасування у незалежну файлову систему `tracefs`, яка монтується у `/sys/kernel/tracing/` і має власну гранулярну модель прав доступу.
3. **`cgroupfs` (контрольні групи cgroups v1 у Linux 2.6.24 та cgroups v2 у Linux 4.5)**: представляє ієрархію ресурсних обмежень процесу через каталоги. Створення підкаталогу у `/sys/fs/cgroup/` створює нову контрольну групу, а запис PID у файл `cgroup.procs` мігрує процес під обмеження пам'яті (`memory.max`), частоти CPU (`cpu.max`) чи швидкості диска (`io.max`).
4. **`configfs` (Linux 2.6.16, 2006 рік, Джоел Бекер)**: якщо `sysfs` відображає об'єкти, які створює та контролює саме ядро, то `configfs` працює у зворотний бік. Простір користувача створює нові об'єкти ядра викликом `mkdir` і видаляє їх через `rmdir`. Це використовується для динамічного створення цілей iSCSI, конфігурації USB-гаджетів (USB Gadget ConfigFS) та завантаження накладок дерева пристроїв (Device Tree overlays).

Паралельно для високошвидкісного обміну структурованими даними розвинулися бінарні сокетні протоколи ядра: сімейство **Netlink** та **Generic Netlink (`genetlink`)** замінили текстове опитування файлів у задачах мережевого налаштування (`iproute2`), керування бездротовими інтерфейсами (`nl80211`) та отримання телеметрії аудиту.

## Від текстових логів до структурованого журналу

Паралельно з еволюцією статичного та динамічного стану ядра відбувалася трансформація журналювання подій. Протокол `syslog`, створений Еріком Оллманом (Eric Allman) для поштового сервера Sendmail у 1980 році в 4.3BSD (згодом зафіксований у RFC 3164), на понад тридцять років закріпив формат системних журналів як неструктурований потік текстових рядків:

```text
Oct 14 12:43:05 host nginx[4512]: connection refused to backend 127.0.0.1:8080
```

У цій схемі текстовий демон (`syslogd`, `rsyslog`) зчитував сирі рядки з локального сокета `/dev/log`, додавав позначку часу й записував у плоскі текстові файли `/var/log/syslog` чи `/var/log/messages`. 

Ця модель мала критичну вразливість: **відсутність автентичності метаданих**. Оскільки сокет приймав звичайний текстовий потік, будь-який непривілейований процес міг надіслати у сокет рядок, підробивши назву програми (наприклад, написавши `sshd[100]: Accepted password for root`), і демон записував це без жодної перевірки.

У 2011 році Леннарт Поеттерінг (Lennart Poettering) та Кей Сіверс (Kay Sievers) реалізували у складі проєкту `systemd` підсистему `systemd-journald`. Замість плоского тексту журнал перетворився на сховище структурованих бінарних записів — множин пар «КЛЮЧ=ЗНАЧЕННЯ».

Головним нововведенням стало те, що метадані процесу додаються **самим ядром** під час передавання дейтаграми через Unix-сокет за допомогою системного виклику `getsockopt(..., SO_PEERCRED)` та аналізу структур cgroup:
* `_PID` — верифікований ядром числовий ідентифікатор процесу;
* `_UID`, `_GID` — реальні ідентифікатори користувача та групи власника процесу;
* `_SYSTEMD_UNIT` — юніт `systemd`, якому належить процес;
* `_COMM` та `_EXE` — точне ім'я та абсолютний шлях до виконуваного бінарного файлу на диску;
* `_SELINUX_CONTEXT` — мітка безпеки процесу;
* `_BOOT_ID` — унікальний ідентифікатор завантаження системи.

Жоден користувацький процес не має технічної змоги підробити поля, які починаються із символу підкреслення (`_`). Окрім того, `journald` запровадив механізм криптографічної фіксації журналу (Forward Secure Sealing, FSS): кожні кілька хвилин створюється новий підпис стану файлу, а старий закритий ключ незворотно знищується. Навіть якщо зловмисник отримає повний рутовий доступ до сервера, він не зможе непомітно модифікувати записи, зроблені до моменту компрометації.

---

Історична дуга самоопису Unix пройшла фундаментальний шлях за сорок років: від небезпечного вичитування сирої пам'яті через `/dev/kmem`, через хаотичний текстовий `/proc`, до строго типізованої об'єктної моделі `sysfs`, спеціалізованих VFS-просторів (`debugfs`, `tracefs`, `cgroupfs`) та криптографічно захищеного структурованого журналу `journald`. Системна правда перестала бути небезпечною хакерською здогадкою й стала надійною інженерною угодою.
