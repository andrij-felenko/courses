# ⚙️ Інспекція багатошарового стану системи

Коли високонавантаженому демону, агенту моніторингу або інструменту системної діагностики потрібно отримати інформацію про власний стан пам'яті, конфігурацію мережевого інтерфейсу чи критичні повідомлення ядра, виклик зовнішніх утиліт на кшталт `system("cat /proc/meminfo")` або `popen("ip link show", "r")` є неприйнятним інженерним рішенням.

Кожен виклик `popen()` або `system()` створює підпроцес за допомогою системних викликів `fork()` та `execve()`. Це змушує ядро дублювати таблиці сторінок віртуальної пам'яті (навіть з оптимізацією Copy-On-Write), створювати нову структуру `task_struct`, запускати командну оболонку `/bin/sh`, шукати бінарний файл в ієрархії каталогів `PATH`, виділяти нові дескриптори каналу та парсити текстовий потік. Для програми, яка опитує метрики сотні разів на секунду, такі накладні витрати призводять до деградації продуктивності, сплесків перемикання контексту та відкривають вектор уразливостей через ін'єкцію команд.

Пряме читання віртуальних файлових систем (`procfs`, `sysfs`) та символьних пристроїв ядра (`/dev/kmsg`) через базові системні виклики `open()`, `read()`, `close()` виконується за лічені мікросекунди, не потребує створення процесів і гарантує безпосередній доступ до структур пам'яті ядра.

## Архітектура кроків та механізми вилучення даних

Утиліта опитування системного стану реалізує чотири незалежні діагностичні операції на різних рівнях абстракції операційної системи:

1. **Процесний шар (`procfs`)**: читання розміру резидентної пам'яті (`VmRSS`) та кількості активних потоків (`Threads`) зі зведеного файлу `/proc/self/status`. На відміну від файлу `/proc/self/stat`, де півсотні числових полів розділені пробілами, `/proc/self/status` містить текстові пари «Ключ: Значення», що робить його читання стійким до додавання нових полів у майбутніх версіях ядра. Для аналізу переданих параметрів програма читає `/proc/self/cmdline`, розбираючи масив рядків, розділених нульовими байтами (`\0`).
2. **Апаратний шар (`sysfs`)**: отримання робочого стану лінку (`operstate`) та максимального розміру корисного навантаження (`mtu`) для локального інтерфейсу зворотного зв'язку (`lo`) з каталогу `/sys/class/net/lo/`. Кожен файл у `sysfs` містить рівно один рядок або число, тому буфер фіксованого розміру (наприклад, 64 байти) надійно вміщує відповідь ядра без потреби у складному синтаксичному аналізі.
3. **Рантайм-шар (`tmpfs` у `/run`)**: перевірка наявності та доступності активного каталогу системного ініціалізатора `/run/systemd/system` за допомогою системного виклику `access()`.
4. **Телеметрія ядра (`/dev/kmsg`)**: неблокуюче відкриття символьного пристрою `/dev/kmsg` з прапорцем `O_NONBLOCK` та читання одного свіжого повідомлення з кільцевого буфера `printk`. Формат виводу `/dev/kmsg` стандартизований ядром: рядок починається з метаданих `priority,sequence,timestamp_us,flags;`, за якими після крапки з комою йде тіло повідомлення.

## Інженерний аналіз реалізацій: C проти C++

Розподіл обов'язків у наведених програмах демонструє два фундаментальні підходи до системного програмування під Linux: прямий низькорівневий POSIX-контроль у C та безпечне керування ресурсами через ідіоми C++.

### Реалізація на C: мінімалізм та нульові динамічні алокації

Утиліта на C побудована навколо роботи з буферами фіксованого розміру на стеку (`char line[256]`, `char buf[1024]`, `char buf[2048]`). Це критично важливий патерн для системних моніторів: відмова від динамічного виділення пам'яті через `malloc()` у гарячому циклі усуває ризик фрагментації купи (heap fragmentation) та виключає затримки на блокування внутрішніх м'ютексів алокатора `glibc`.

* **Потокове читання текстових полів (`read_proc_status_field`)**: використання бібліотечної функції `fgets()` дозволяє зчитувати файл `/proc/self/status` порядково без завантаження всього файлу в пам'ять. Функція `strncmp(line, key, key_len)` перевіряє збіг ключа, після чого вказівник зсувається праворуч від двокрапки та пропускає пробільні символи. Завершальний перенос рядка `\n` явно замінюється на нульовий термінатор `\0`.
* **Парсинг нуль-розділених байтів (`print_proc_cmdline`)**: файл `/proc/self/cmdline` не містить символів переносу рядка — аргументи процесу розділені байтами `\0`. Системний виклик `read()` зчитує весь блок даних у буфер, після чого цикл переміщує покажчик на `strlen(&buf[i]) + 1` байтів уперед, поки не буде досягнуто кінця зчитаного масиву `bytes_read`.
* **Неблокуючий доступ до логів ядра (`read_single_kmsg`)**: відкриття `/dev/kmsg` з прапорцем `O_NONBLOCK` гарантує, що якщо в кільцевому буфері `printk` немає нових повідомлень, виклик `read()` не заблокує потік виконання, а негайно поверне помилку `EAGAIN` або `EWOULDBLOCK`. Якщо у процесу відсутні привілеї читання (захист `kernel.dmesg_restrict = 1`), код коректно обробляє помилку `EACCES`.

### Реалізація на C++: RAII та нульове копіювання через string_view

Версія на C++ вирішує ті самі низькорівневі задачі, але використовує механізми сучасної типізації для унеможливлення витоків ресурсів:

* **Клас `FileDescriptor` як гарантія вивільнення (RAII)**: обгортка інкапсулює цілочисельний дескриптор `int fd_`. Конструктор копіювання та оператор присвоєння копіюванням видалені (`= delete`), що виключає випадкове подвійне закриття дескриптора (double close bug). Натомість реалізовано семантику переміщення (move semantics), яка передає володіння дескриптором. Деструктор автоматично викликає `::close(fd_)`, коли об'єкт виходить з області видимості, навіть якщо в коді функції сталася помилка або згенеровано виняток.
* **Безпечний розбір командного рядка (`readCmdline`)**: заповнення динамічного масиву `std::vector<std::string>` здійснюється методом `args.emplace_back(&buffer[start])`. Конструктор рядка зчитує нуль-терміновану послідовність від поточного зміщення без ручного виклику `strlen()`.
* **Розбір метаданих через `std::string_view`**: під час аналізу рядка з `/dev/kmsg` конструкція `std::string_view raw(buffer.data(), n)` створює неволодіючий зріз пам'яті поверх стекового буфера. Метод `raw.find(';')` знаходить роздільник метаданих і тексту, а `raw.substr()` формує підрядки без жодного виділення пам'яті на купі.

### Чому віртуальні файли не підтримують mmap()

Часто виникає спокуса прискорити читання великих файлів `/proc` чи `/sys` через виклик відображення пам'яті `mmap()`. Проте для більшості синтетичних вузлів VFS спроба виконати `mmap(NULL, size, PROT_READ, MAP_SHARED, fd, 0)` завершиться помилкою `ENODEV` (No such device) або `EINVAL` (Invalid argument).

Причина полягає у внутрішній будові VFS: для роботи `mmap()` драйвер файлової системи повинен надати структуру операцій адресної пам'яті `struct address_space_operations` з реалізованим методом `fault()`, який обробляє сторінкові переривання (page faults) та завантажує дискові блоки в оперативну пам'ять. Віртуальні файли не мають дискового бекенду; їхній зміст генерується ядром «на льоту» у відповідь на виклик `read()`. Тому звичайний виклик `read()` у буфер фіксованого розміру залишається єдиним штатним способом вилучення інформації.

## Парсинг та обчислення процесорних метрик: /proc/[pid]/stat та jiffies

Файл `/proc/[pid]/status` зручний для читання людиною, але створення повноцінного монітора навантаження процесора (аналога `top` або `htop`) вимагає роботи з машинним джерелом правди: файлом `/proc/[pid]/stat`.

### Анатомія рядка /proc/[pid]/stat та пастка поля comm

Файл `/proc/[pid]/stat` містить 52 поля, розділені пробілами, що описують стан задачі на рівні планувальника ядра. Наївний парсинг цього файлу через виклик `sscanf(buf, "%d %s %c %d ...", &pid, comm, &state, ...)` є грубою інженерною помилкою, що призводить до аварійних збоїв та вразливостей.

Поле 2 (`comm`) містить назву виконуваного файлу процесу, обмежену 16 байтами (константа ядра `TASK_COMM_LEN`), і береться в круглі дужки: `(process_name)`. Проте користувач або сам процес може змінити ім'я через системний виклик `prctl(PR_SET_NAME)`. Назва може містити пробіли, круглі дужки чи символи табуляції (наприклад, `(worker (1) run)`). Якщо застосувати стандартне розділення за пробілами, кожен внутрішній пробіл або закриваюча дужка зсуне індексацію всіх наступних 50 числових полів.

Правильний алгоритм розбору рядка `/proc/[pid]/stat`:
1. Знайти першу відкриваючу дужку `(` зліва за допомогою покажчика `char *start = strchr(buf, '(')`.
2. Знайти останню закриваючу дужку `)` справа за допомогою покажчика `char *end = strrchr(buf, ')')`.
3. Усі символи між `start + 1` та `end` є гарантованим ім'ям `comm`.
4. Парсинг числових полів починається строго після знайденої правої дужки `end + 2`.

```
12345 (worker (thread)) S 1 12345 12345 0 -1 4194304 120 0 0 0 450 150 0 0 20 0 4 ...
^ PID ^------ comm ----^ ^ State                          ^ utime ^ stime
                         |                                |       |
                         Поле 3 (end + 2)                 Поле 14 Поле 15
```

### Стани процесу та час виконання в jiffies

Поле 3 визначає поточний стан процесу в планувальнику:
* `R` (*Running / Runnable*): процес виконується на ядрі CPU або стоїть у черзі виконання `runqueue`, очікуючи виділення кванта часу.
* `S` (*Interruptible Sleep*): процес заблокований в очікуванні події (читання з сокета, завершення таймера, блокування м'ютекса). Реагує на надходження сигналів POSIX.
* `D` (*Uninterruptible Sleep*): процес перебуває у глибинах системного виклику ядра (найчастіше очікування блокового введення-виведення диска чи відповіді NFS) і не може бути перерваний навіть сигналом `SIGKILL`. Процеси в стані `D` безпосередньо збільшують показник системного навантаження Load Average.
* `Z` (*Zombie*): процес завершив виконання через `exit()`, його пам'ять і дескриптори звільнені, але запис у таблиці процесів ядра зберігається, доки батьківський процес не прочитає код завершення через системний виклик `waitpid()`.
* `T` (*Stopped / Traced*): виконання призупинено сигналом (`SIGSTOP`, `SIGTSTP`) або процес зупинено зневаджувачем `gdb` через інтерфейс `ptrace`.

Ключовими метриками процесорного часу є:
* **Поле 14 (`utime`)**: кількість квантів часу (*clock ticks / jiffies*), проведених процесом у просторі користувача (*user mode*);
* **Поле 15 (`stime`)**: кількість квантів, проведених у просторі ядра (*kernel mode*) під час обслуговування системних викликів процесу;
* **Поле 16 (`cutime`)** та **Поле 17 (`cstime`)**: час у режимі користувача та ядра всіх дочірніх процесів, які завершилися і стан яких було прочитано через `waitpid()`.

### Розрахунок завантаження CPU у відсотках

Одиницею виміру часу в планувальнику Linux є системний квант таймера — `jiffy`. Кількість квантів у секунді фіксується під час збірки ядра і зчитується з простору користувача через системну конфігурацію:

```
CLK_TCK = sysconf(_SC_CLK_TCK)    [типово 100 Гц на x86_64, тобто 1 jiffy = 10 мс]
```

Сумарний процесорний час, спожитий процесом від моменту його створення, обчислюється як:

```
t_process_sec = (utime + stime) / (double)CLK_TCK
```

Для обчислення миттєвого відсотка завантаження процесора (% CPU) монітор робить два послідовні заміри з часовим інтервалом `Δt` (виміряним за допомогою високоточного монотонного годинника `clock_gettime(CLOCK_MONOTONIC)`):

```
Δproc_jiffies = (utime₂ + stime₂) - (utime₁ + stime₁)
Δwall_sec = (t₂_wall.tv_sec - t₁_wall.tv_sec) + (t₂_wall.tv_nsec - t₁_wall.tv_nsec) / 1e9
CPU_usage_% = ((Δproc_jiffies / (double)CLK_TCK) / Δwall_sec) · 100%
```

Якщо процес є багатопотоковим і завантажує кілька ядер, значення `CPU_usage_%` може перевищувати 100% (наприклад, 400% на 4 ядрах). Для нормалізації відносно загальної потужності машини результат ділять на кількість активних логічних процесорів: `sysconf(_SC_NPROCESSORS_ONLN)`.

## Глибока інспекція пам'яті: status, smaps та smaps_rollup

Оцінка використання пам'яті процесом ускладнюється тим, що віртуальний адресний простір містить як приватні дані, так і спільні сторінки пам'яті, розділені з іншими процесами.

### Розшифровка полів /proc/[pid]/status

Файл `/proc/[pid]/status` містить детальний зріз підсистеми управління віртуальною пам'яттю (VMM):

| Поле | Назва | Фізична суть |
|---|---|---|
| `VmSize` | Virtual Memory Size | Сумарний розмір усіх виділених областей VMA (код, стек, купа, відображені файли, зарезервована пам'ять). |
| `VmRSS` | Resident Set Size | Обсяг фізичної пам'яті (RAM), відображеної в таблиці сторінок процесу на даний момент. |
| `RssAnon` | Anonymous RSS | Сторінки без файлового бекенду: динамічна купа `malloc()`, стеки потоків, анонімні відображення `mmap(MAP_ANONYMOUS)`. |
| `RssFile` | File-backed RSS | Сторінки виконуваного ELF-файлу та спільних бібліотек `.so`, підтягнуті з кешу сторінок (*Page Cache*). |
| `RssShmem` | Shared Memory RSS | Сторінки спільної пам'яті `shmget`, `tmpfs` та регіони `mmap(MAP_SHARED)`. |
| `VmPeak` | Peak Virtual Size | Максимальний розмір віртуальної пам'яті, зафіксований за весь час життя процесу. |
| `VmSwap` | Swapped Memory | Обсяг анонімної пам'яті процесу, скинутої підсистемою ядра у swap-розділ. |

### Пастка VmRSS та обчислення PSS / USS

Якщо на сервері працює 50 однакових процесів веб-сервера, кожен із яких підключає бібліотеку `libcrypto.so` розміром 4 МіБ, просте сумування значень `VmRSS` покаже:

```
50 · 4 МіБ = 200 МіБ
```

Проте фізично в оперативній пам'яті знаходиться лише один примірник сторінок бібліотеки розміром 4 МіБ, оскільки ядро розділяє сторінки, доступні лише для читання, між усіма процесами. Цей феномен має назву *проблеми подвійного обліку* (Double Counting).

Для отримання реальної картини використовуються дві метрики:
* **USS (Unique Set Size)**: пам'ять, яка належить виключно даному процесу (`Private_Clean + Private_Dirty`). Якщо процес буде завершено, саме цей обсяг оперативної пам'яті негайно повернеться операційній системі.
* **PSS (Proportional Set Size)**: пропорційний розмір пам'яті. Для кожної сторінки пам'яті її розмір ділиться на кількість процесів, що одночасно утримують цю сторінку:

```
PSS = Private_Pages + ∑ (Shared_Page / Page_Share_Count)
```

Історично для розрахунку PSS доводилося вичитувати величезний файл `/proc/[pid]/smaps`, який містить детальний опис кожного VMA-регіону процесу. Для процесу зі складним адресним простором розмір `smaps` досягає десятків мегабайтів, а його генерація створює важке блокування семафора пам'яті `mmap_lock`, сповільнюючи сам цільовий процес.

Починаючи з Linux 4.14, ядро надає оптимізований файл **`/proc/[pid]/smaps_rollup`**. Він підсумовує всі VMA-регіони безпосередньо у внутрішніх структурах ядра і повертає єдиний компактний звіт:

```
Rss:                18432 kB
Pss:                 8120 kB
Pss_Anon:            4096 kB
Pss_File:            3024 kB
Pss_Shmem:           1000 kB
Shared_Clean:       10312 kB
Shared_Dirty:           0 kB
Private_Clean:       2048 kB
Private_Dirty:       6072 kB
```

Завдяки `smaps_rollup` системний монітор отримує точні значення `Pss` та `USS` (обчислюється як `Private_Clean + Private_Dirty`) за один системний виклик `read()` тривалістю у кілька мікросекунд.

## Відстеження відкритих дескрипторів та заблокованих ресурсів

Каталог `/proc/[pid]/fd/` надає повне відображення таблиці дескрипторів файлів процесу. Кожен запис у цьому каталозі є спеціальним символьним посиланням, ім'я якого відповідає числовому дескриптору (`0`, `1`, `2`, `3`...).

### Робота з readlink() та виявлення видалених файлів

Для отримання реального шляху, на який вказує файловий дескриптор, використовується системний виклик `readlink()`:

:::tabs
```c
char target[PATH_MAX];
ssize_t len = readlink("/proc/self/fd/3", target, sizeof(target) - 1);
if (len > 0) {
    target[len] = '\0'; /* readlink не додає завершальний нуль! */
}
```
```cpp
// У C++ читання символьного посилання виконується через std::filesystem
std::error_code ec;
auto target = std::filesystem::read_symlink("/proc/self/fd/3", ec);
if (!ec) {
    // target містить об'єкт std::filesystem::path без ручного виділення буфера
}
```
:::

Під час аналізу відкритого дескриптора можливі три типи цільових шляхів:
1. **Канонічний шлях до файлу на диску**: наприклад, `/var/log/app.log` або `/etc/hosts`.
2. **Видалений файл (Deleted Inode)**: якщо файл було відкрито процесом, а потім видалено з диска утилітою `rm` або викликом `unlink()`, ядро знищує запис у каталозі (`dentry`), але зберігає структуру `inode` і дискові блоки, доки лічильник відкритих дескрипторів `file->f_count > 0`. У такому випадку ядро дописує до цільового шляху суфікс:
   ```
   /var/log/app.log (deleted)
   ```
   Це головна причина класичної системної проблеми: утиліта `df` показує 100% заповнення дискового розділу, тоді як утиліта `du -sh /*` показує, що сума всіх наявних файлів займає мінімум місця. Знайти процес, який утримує видалені блоки, можна швидким скануванням цілей у `/proc/*/fd/*`.
3. **Анонімні канали та сокети**: посилання мають спеціальний вигляд `pipe:[123456]` або `socket:[789012]`, де число у квадратних дужках є номером `inode` об'єкта в оперативній пам'яті ядра.

### Зв'язування каналів і сокетів

Отримавши дескриптор каналу `pipe:[123456]`, програма може знайти другий процес, що бере участь у міжпроцесній взаємодії (IPC), виконавши пошук по всіх підкаталогах `/proc/<OTHER_PID>/fd/`. Процес, що має дескриптор з ідентичним номером `inode`, є протилежним кінцем каналу (наприклад, читачем або письменником).

Для сокетів `socket:[789012]` номер `inode` зіставляється з таблицями активних мережевих з'єднань ядра у `/proc/net/tcp`, `/proc/net/tcp6`, `/proc/net/udp` або через протокол Netlink `NETLINK_INET_DIAG`. Знайшовши рядок із відповідним `inode`, програма отримує локальну та віддалену IP-адресу, порт та поточний стан TCP-з'єднання (`ESTABLISHED`, `LISTEN`, `TIME_WAIT`).

### Додаткові метадані дескриптора у /proc/[pid]/fdinfo/

Для кожного відкритого дескриптора каталог `/proc/[pid]/fdinfo/<FD>` надає внутрішні параметри відкритого файлового опису (`struct file`):
* `pos:` — поточне зміщення вказівника читання/запису у байтах (file offset);
* `flags:` — вісімкове представлення прапорців відкриття файлу (`O_RDONLY = 00`, `O_WRONLY = 01`, `O_RDWR = 02`, `O_NONBLOCK = 04000`, `O_APPEND = 02000`);
* `mnt_id:` — ідентифікатор точки монтування у файлі `/proc/self/mountinfo`;
* `eventfd-count:` — поточне значення лічильника (для дескрипторів, створених через `eventfd()`);
* `tfd:` та `events:` — список цільових дескрипторів та бітових масок очікуваних подій (для екземплярів `epoll_create()`).

## Дослідження апаратної топології та пристроїв у /sys

Файлова система `sysfs` моделює внутрішнє дерево об'єктів ядра `struct kobject`, відкриваючи доступ до топології процесорів, кешів, пам'яті NUMA та лічильників мережевих інтерфейсів.

### Топологія ядер, кешів та NUMA у /sys/devices/system/cpu/

Каталог `/sys/devices/system/cpu/` відображає конфігурацію обчислювальних ядер:

1. **Динамічні частоти та політики регулювання (`cpu<N>/cpufreq/`)**:
   * `scaling_cur_freq` — поточна частота ядра в кГц;
   * `scaling_min_freq` / `scaling_max_freq` — апаратні межі зміни частоти;
   * `scaling_governor` — активний алгоритм керування частотою: `performance` (постійна максимальна частота), `powersave` (мінімальна частота), `schedutil` (динамічна зміна частоти на основі навантаження `util_avg` планувальника CFS).
2. **Ієрархія кеш-пам'яті (`cpu<N>/cache/index<M>/`)**:
   * `level` — рівень кешу (1, 2, 3);
   * `type` — призначення (`Data`, `Instruction`, `Unified`);
   * `size` — обсяг кешу (наприклад, `32K`, `512K`, `32768K`);
   * `shared_cpu_list` — список логічних процесорів, які спільно використовують цей рівень кешу (наприклад, `0,4` для кешу L2 між двома потоками SMT одного фізичного ядра, або `0-7` для монолітного кешу L3 в межах одного кристалу CCX);
   * `coherency_line_size` — розмір рядка кешу (типово 64 байти).
3. **Фізична топологія та Hyper-Threading (`cpu<N>/topology/`)**:
   * `physical_package_id` — номер фізичного процесорного сокета на материнській платі;
   * `core_id` — унікальний ідентифікатор фізичного ядра всередині сокета;
   * `thread_siblings_list` / `core_cpus_list` — список логічних процесорів, що виконуються на одному фізичному ядрі як потоки Hyper-Threading (SMT).
4. **Неоднорідна пам'ять NUMA (`/sys/devices/system/node/node<N>/`)**:
   * `cpulist` — список ядер, прив'язаних до локального контролера пам'яті цього NUMA-вузла;
   * `meminfo` — фізичний обсяг пам'яті вузла (`MemTotal`, `MemFree`);
   * `distance` — матриця відносної затримки доступу до пам'яті між вузлами. Звернення до локальної пам'яті вузла має базову вартість `10`, тоді як звернення до пам'яті сусіднього сокета через шину міжпроцесорного зв'язку (Intel UPI / AMD Infinity Fabric) має вартість `20` або більше. Якщо багатопотокова програма виділяє пам'ять на одному вузлі NUMA, а виконується на іншому, затримка доступу до RAM зростає майже вдвічі, що знижує загальну пропускну здатність системи.

### Діагностика мережевих інтерфейсів у /sys/class/net/<iface>/

Інспекція мережевих адаптерів через `sysfs` дозволяє перевіряти фізичний стан лінку та знімати лічильники помилок без виклику важкої утиліти `ip`:

* **Стан з'єднання**:
  * `operstate` — операційний стан інтерфейсу (`up`, `down`, `dormant`, `lowerlayerdown`);
  * `carrier` — фізична наявність сигналу несучої в середовищі передачі (`1` — фізичний лінк встановлено, `0` — кабель від'єднано або відсутній оптичний сигнал);
  * `speed` — узгоджена швидкість лінку в Мбіт/с (`1000`, `10000`, `25000`, `100000`);
  * `duplex` — режим дуплексу (`full`, `half`).
* **Лічильники трафіку та помилок (`statistics/`)**:
  * `rx_packets` / `tx_packets` — кількість успішно прийнятих та відправлених Ethernet-кадрів;
  * `rx_bytes` / `tx_bytes` — сумарний обсяг переданих даних у байтах;
  * `rx_errors` / `tx_errors` — загальна кількість помилкових кадрів;
  * `rx_dropped` / `tx_dropped` — кадри, відкинуті ядром через брак буферів у пам'яті (переповнення кільцевого дескрипторного буфера RX Ring Buffer мережевої карти або черги ядра `netdev_max_backlog`);
  * `rx_crc_errors` — кадри з пошкодженою контрольною сумою FCS (Frame Check Sequence), що є прямим індикатором фізичного пошкодження патч-корду, поганого контакту в роз'ємі RJ-45 або сильних електромагнітних наводок;
  * `rx_fifo_errors` — переповнення вбудованого апаратного буфера FIFO мережевого чіпа через затримки в шині PCIe або блокування переривань.

Для розрахунку поточної швидкості передачі даних (пропускної здатності) та відсотка втрат пакетів програма знімає дельту лічильників за інтервал часу `Δt`:

```
Throughput_Mbps = ((Δrx_bytes + Δtx_bytes) · 8) / (Δt_sec · 1000000)
Drop_Rate_% = (Δrx_dropped / (Δrx_packets + Δrx_dropped)) · 100%
```

## Внутрішня механіка VFS та оптимізація dentry-кешу

Коли користувацький код звертається до шляхів `/proc` або `/sys`, ядро не створює постійних структур на дисковому носії. Проте для прискорення повторного доступу підсистема VFS використовує кеш записів каталогів (`dentry_cache`).

Для віртуальних файлових систем `procfs` та `sysfs` реалізовано спеціальні правила інвалідації:
* **Динамічні dentry з операцією `d_delete`**: записи каталогів для тимчасових процесів (`/proc/<PID>/`) автоматично позначаються як недійсні, щойно процес завершує виконання. Це гарантує, що ядро не витрачає оперативну пам'ять на утримання кешу давно закритих задач;
* **Пряме відображення об'єктів `kobject`**: у `sysfs` кожна операція читання безпосередньо викликає функцію `sysfs_ops->show()`, пов'язану з відповідним драйвером пристрою. Це забезпечує нульову затримку між зміною фізичного стану заліза (наприклад, від'єднанням кабелю Ethernet) та його відображенням у файлі `operstate`.
* **Відсутність кешування сторінок (Page Cache Bypass)**: на відміну від дискових файлових систем (ext4, XFS), які кешують зчитані блоки у пам'яті, синтетичні файли VFS не розміщують сторінки у Page Cache. Кожен системний виклик `read()` безпосередньо звертається до обробника ядра, гарантуючи абсолютно свіжі дані без необхідності скидання кешів.

## Порівняння продуктивності: прямий VFS проти створення підпроцесів

Вимірювання часу виконання на типовому сучасному сервері демонструє колосальну різницю між прямими системними викликами та викликом зовнішніх бінарників:

| Метод отримання метрики | Використовувані системні виклики | Середній час виконання | Навантаження на пам'ять |
|---|---|---|---|
| Пряме читання `/proc/self/status` | `open()` + `read()` + `close()` | **1.2 мікросекунди** | 0 додаткових байтів |
| Пряме читання `/sys/class/net/lo/mtu` | `open()` + `read()` + `close()` | **0.8 мікросекунди** | 0 додаткових байтів |
| Запуск `popen("cat /proc/self/status", "r")` | `pipe()` + `fork()` + `execve()` + `wait4()` | **480.0 мікросекунд** | Створення нового адресного простору |
| Запуск утиліти `ps` через оболонку | `fork()` + `execve("/bin/sh")` + `execve("ps")` | **2300.0 мікросекунд** | Клонування процесу, завантаження ELF |

Пряме читання VFS працює майже у 400 разів швидше за `popen()` і у 2000 разів швидше за виклик `ps`, виключаючи будь-які паразитарні навантаження на планувальник операційної системи.

## Багатопотоковий вимір: підкаталог /proc/<PID>/task/

Якщо процес використовує потоки виконання (threads, створені через виклик `clone()` або `pthread_create()`), кожен потік реєструється ядром як окрема задача `struct task_struct` із власним числовим ідентифікатором потоку (TID, Thread ID).

Для детальної інспекції потоків процес надає підкаталог:

```
/proc/<PID>/task/<TID>/
```

Усередині кожного каталогу потоку доступні індивідуальні файли стану:
* `status` — індивідуальне використання часу CPU (користувацького та системного), стан сну (`State: S (sleeping)` чи `State: R (running)`);
* `stat` — точні лічильники квантів планувальника, пріоритету реального часу та прив'язки до процесорного ядра (поле 39 `processor`);
* `stack` — поточний стек викликів ядра (якщо ядро зібрано з підтримкою `CONFIG_STACKTRACE`), що дозволяє точно побачити, у якому системному виклику або блокуванні застряг потік;
* `wchan` — назва конкретної функції ядра, у якій потік перейшов у стан сну (наприклад, `futex_wait_queue_me` або `ep_poll`).

## Крайові випадки та системні пастки

Під час практичного використання коду інспекції VFS інженер стикається з низкою специфічних системних пасток:

1. **Нульовий розмір файлів у виклику `stat()` та неможливість `lseek(SEEK_END)`**: усі файли в `/proc` та `/sys` мають поле `st_size = 0` у структурі `struct stat`. Ядро не знає наперед довжини згенерованого тексту, доки не почнеться виконання файлових операцій `read()`. Спроба визначити розмір буфера за допомогою `stat()` перед викликом `malloc()` виділить 0 байтів. Аналогічно, виклик `lseek(fd, 0, SEEK_END)` повертає 0 або помилку `ESPIPE`. Правильний підхід — використовувати буфери фіксованого розміру на стеку (наприклад, 4096 байтів) або читати файл потоково блоками до отримання `0` (ознака кінця файлу EOF).
2. **Стан гонки TOCTOU та раптове зникнення процесу**: якщо утиліта сканує каталог `/proc` у циклі за допомогою функції `readdir()` і знаходить підкаталог `/proc/12345/`, спроба відкрити `/proc/12345/status` може повернути помилку `ENOENT` (файл не знайдено) або `ESRCH` (процес не існує), якщо цільовий процес завершився за мікросекунду між `readdir()` та `open()`. Код системного моніторингу повинен завжди розглядати ці коди помилок як штатну ситуацію, а не як аварійний збій. Для мінімізації накладних витрат рекомендується використовувати системний виклик `openat()`, відкриваючи каталог процесу один раз і далі звертаючись до його файлів за відносними дескрипторами.
3. **Обмеження безпеки на відкриття `/dev/kmsg`**: починаючи з ядер Linux 4.8, неблокуюче читання `/dev/kmsg` для непривілейованих процесів регулюється значенням параметра `sysctl` під назвою `kernel.dmesg_restrict`. Якщо `kernel.dmesg_restrict = 1`, виклик `open("/dev/kmsg", O_RDONLY)` поверне помилку `EACCES` для будь-якого процесу, що не володіє системним привілеєм `CAP_SYSLOG`. Програма повинна перевіряти це значення й за потреби запитувати підвищення привілеїв.
4. **Розриви послідовності в кільцевому буфері**: при надзвичайно високому потоці логів (наприклад, шторм мережевих помилок) кільцевий буфер `printk` може перезаписати старі повідомлення швидше, ніж застосунок встигне їх вичитати. У такій ситуації черговий виклик `read()` на дескрипторі `/dev/kmsg` поверне помилку `EPIPE`, сигналізуючи, що між попереднім і поточним читанням частину повідомлень було втрачено. Після отримання `EPIPE` застосунок повинен повторити виклик `read()`, який поверне наступне наявне в буфері повідомлення з актуальним порядковим номером (`sequence`).
5. **Приховування процесів через опцію hidepid**: якщо файлова система `/proc` змонтована з опцією `hidepid=1` або `hidepid=2` (поширене налаштування на захищених багатокористувацьких серверах), звичайний непривілейований користувач бачить у `/proc/` виключно власні процеси. Усі підкаталоги інших користувачів приховані (повертають `ENOENT` або `EACCES`), що унеможливлює побудову загальносистемного монітора без привілеїв `root` або членства у спеціальній групі (параметр монтування `gid=...`).
6. **Неатомарність читання великих файлів VFS**: віртуальні файли розміром понад 4 КіБ (наприклад, `/proc/[pid]/maps` або `/proc/kallsyms`) генеруються ядром частинами під час кожного виклику `read()`. Якщо цільовий процес викликає `mmap()` або `munmap()` просто під час того, як монітор вичитує середину файлу `maps`, згенерований зріз виявиться неузгодженим (рядки можуть повторюватися або пропускатися). Системні зневаджувачі усувають це, тимчасово призупиняючи виконання процесу сигналом `SIGSTOP` або через `ptrace(PTRACE_ATTACH)` перед інспекцією його адресного простору.
