У конвеєрі неперервної інтеграції нічний сценарій розгортання мікросервісів раптово зупиняється на стадії міграції бази даних із лаконічним записом `exit status 1` у системному журналі, не залишаючи жодної вказівки на те, яка саме з двохсот команд зазнала збою. У класичних компільованих мовах розробник отримує точний файл, рядок і тип помилки ще на етапі компіляції або вичерпний стек викликів під час аварійного дампу пам'яті. Командна оболонка Unix позбавлена попередньої трансляції: вона інтерпретує кожен рядок тексту безпосередньо в момент виконання, динамічно підставляючи значення змінних, виконуючи підстановку команд і генеруючи аргументи системних викликів на льоту.

Коли в такому динамічному середовищі виникає логічна помилка чи збій зовнішньої утиліти, звичайне додавання викликів `echo` швидко перетворюється на джерело нових проблем: воно спотворює стандартний потік виводу, руйнує роботу конвеєрів і затирає код завершення `$?` попередньої операції. Побудова надійних сценаріїв вимагає системного підходу до діагностики, що поєднує три взаємодоповнюючі рівні інтроспекції: статичний аналіз коду перед запуском через ShellCheck, синтаксичну верифікацію інтерпретатором через `bash -n`, динамічне трасування розгорнутих інструкцій через `set -x` із налаштуванням діагностичного префіксу `PS4`, а також програмне перехоплення аварійних подій за допомогою пасток `trap` для сигналів `DEBUG` та `ERR`.

## Специфіка інтерпретованого середовища: чому shell-скрипти ламаються непомітно

Головна складність діагностики сценаріїв оболонки полягає в тому, що вихідний текст програми не транслюється у статичну таблицю символів чи машинний код. Рядок у скрипті — це динамічний шаблон, який проходить складний багатофазний конвеєр перетворень перед тим, як перетворитися на масив аргументів системного виклику `execve(2)` або аргументи внутрішньої функції.

![Конвеєр обробки інструкції інтерпретатором Bash](/root/sys/sys-unix/script-debugging/img/shell-execution-and-trace-pipeline.svg)
*Послідовність обробки командної інструкції інтерпретатором Bash та точки вклинення діагностичних механізмів.*

У процесі виконання одного рядка оболонка здійснює розгортання фігурних дужок, тильди, параметрів, підстановку команд, арифметичні обчислення, поділ результату на слова за роздільниками змінної `IFS` (Word Splitting) та розгортання імен файлів за масками (Globbing). Помилка в будь-якій із цих фаз призводить до мутації вектора аргументів `argv[]`, про яку розробник навіть не здогадується, дивлячись на статичний вихідний код.

Сценарії оболонки стикаються з трьома принципово різними категоріями дефектів:

1. **Синтаксичні помилки інтерпретатора (Parse Errors):** незакриті лапки, пропущені ключові слова `then`, `fi`, `done`, незбалансовані дужки. Інтерпретатор не може побудувати синтаксичне дерево команди й негайно зупиняє роботу або відмовляється завантажувати файл.
2. **Семантичні помилки розгортання (Expansion Errors):** незалапкована змінна, що містить пробіли, розпадається на кілька незалежних аргументів; неініціалізована змінна розгортається в порожнечу; маска `*.log` за відсутності збігів залишається сирим рядком `*.log`. Оболонка сприймає таку мутацію як синтаксично коректну й передає спотворені аргументи далі.
3. **Помилки середовища та кодів повернення (Runtime Execution Errors):** зовнішня програма, запущена через системний виклик, повертає ненульовий статус (наприклад, `grep` не знайшов збігів із кодом `1`, або `curl` не зміг встановити з'єднання з кодом `7`). Оболонка за замовчуванням ігнорує ці статуси й продовжує лінійне виконання наступних рядків.

Утиліта `echo`, яку традиційно застосовують для швидкого пошуку дефектів, має критичні обмеження. Вона виводить значення змінної так, як її бачить користувач, але приховує межі між елементами масиву, приховує наявність невидимих керуючих символів, змінює код повернення `$?` (оскільки сам виклик `echo` майже завжди повертає `0`) та спрямовує налагоджувальний текст у потік `stdout`, ламаючи конвеєри обробки структурованих даних на кшталт JSON чи CSV.

### Процесна модель: батьківські процеси, підоболонки та втрата мутацій

Особливе джерело прихованих помилок у shell-скриптах криється в невидимому створенні підоболонок (subshells). Щоразу, коли оболонка виконує вираз у круглих дужках `( cmd )`, підстановку команди `$( cmd )`, процес заміщення `<( cmd )` або елемент конвеєра `cmd1 | cmd2` (у стандартному режимі POSIX), ядро викликає `fork()`.

Підоболонка отримує повну копію адресного простору батьківського процесу: змінні, функції, відкриті файлові дескриптори. Проте будь-які зміни стану всередині підоболонки — присвоєння нових значень змінним, зміна поточного каталогу через `cd`, модифікація масивів — відбуваються виключно в пам'яті дочірнього процесу. Після завершення підоболонки всі мутації безслідно зникають:

```bash
counter=0
cat /etc/hosts | while read -r line; do
    (( counter++ ))
done
echo "Оброблено рядків: ${counter}"  # Надрукує 0! Цикл while виконувався у fork'нутій підоболонці
```

Без інструментів динамічного трасування такий розрив пам'яті виглядає як незрозуміле «зникнення» даних між рядками коду.

## Синтаксична валідація без виконання: `bash -n` (`noexec`)

Першим бар'єром захисту від грубих дефектів є режим перевірки синтаксису без запуску коду. Передача прапорця `-n` (або виклик `set -n` / `set -o noexec`) перемикає інтерпретатор у режим пасивного синтаксичного аналізу.

```bash
# Перевірка коректності граматичної структури сценарію
bash -n deploy_cluster.sh
```

У цьому режимі лексер і парсер оболонки читають потік символів, перевіряють баланс керуючих конструкцій (`if ... then ... else ... fi`, `for ... in ... do ... done`, `case ... in ... esac`), валідують синтаксис оголошення функцій і будують абстрактне синтаксичне дерево. Проте інтерпретатор повністю блокує фази розгортання параметрів, підстановку команд і системні виклики `fork()` та `execve()`.

Перевага `bash -n` полягає в абсолютній безпеці: скрипт, який містить деструктивні команди на кшталт `rm -rf "${TARGET_DIR}"` або `mkfs.ext4`, можна сміливо перевіряти на будь-якому сервері без ризику пошкодження даних.

### Межі можливостей синтаксичного аналізатора `bash -n`

Попри свою користь, перевірка `bash -n` є суто синтаксичною і не здатна виявити більшість логічних дефектів:

- **Підстановка команд у підоболонках `$(...)`:** парсер перевіряє базовий баланс дужок, але не виконує вкладені команди, тому помилки в їхніх аргументах залишаються непоміченими;
- **Невизначені змінні:** парсер не перевіряє наявність або коректність змінних, навіть якщо активовано `set -u`;
- **Наявність бінарних файлів:** парсер не перевіряє, чи існують викликані утиліти в каталогах змінної `$PATH` і чи є вони виконуваними;
- **Динамічний синтаксис `eval`:** будь-який код, що генерується динамічно всередині рядків для подальшого виконання командою `eval`, перебуває поза увагою статичного парсера.

### Прапорці діагностики читання: `set -v` проти `set -x`

Оболонка підтримує два прапорці виводу інструкцій під час виконання, які часто плутають, але які працюють на принципово різних стадіях конвеєра:

| Прапорець | Режим (`set -o`) | Момент виводу в діагностичний потік | Стан аргументів |
| :--- | :--- | :--- | :--- |
| `set -v` | `verbose` | Одразу після зчитування рядка лексером з файлу або вводу. | Сирий вихідний код так, як він написаний у файлі (з `$VAR`, `$(cmd)`). |
| `set -x` | `xtrace` | Після проходження ВСІХ етапів розгортання, безпосередньо перед запуском команди. | Повністю розгорнуті літеральні значення параметрів та списки файлів. |

Використання `set -v` зручне для відстеження того, який саме блок багаторядкового файлу зараз читається, тоді як `set -x` є головним інструментом динамічного відлагодження, оскільки показує реальний вектор аргументів, що передається системі.

Повний перелік параметрів оболонки та системних змінних наведено у [довіднику прапорців та змінних інтроспекції](root:sys-unix/script-debugging/api-shell-debug-options-and-vars.md).

## Динамічне трасування виконання: прапорець `set -x` (xtrace)

Прапорець `set -x` (або активація через шебанг `#!/usr/bin/env -S bash -x`) вмикає режим `xtrace`. Перед виконанням кожної простої команди інтерпретатор розгортає префіксний рядок `PS4`, підставляє фактичні значення всіх змінних, розгортає маски файлів і друкує підсумкову команду в потік діагностики (за замовчуванням `stderr`).

Розглянемо демонстраційний фрагмент обробки конфігураційних файлів:

```bash
#!/usr/bin/env bash
set -euo pipefail

backup_dir="/var/backups/cluster"
service_name="auth-api"
archive_name="${service_name}_$(date +%Y%m%d).tar.gz"

set -x  # Вмикаємо трасування для критичної секції
mkdir -p "${backup_dir}"
tar -czf "${backup_dir}/${archive_name}" -C "/etc/${service_name}" conf.d
set +x  # Вимикаємо трасування
```

Під час виконання блоку між `set -x` та `set +x` у стандартний потік помилок надходить вичерпний протокол з реальними значеннями параметрів:

```text
+ mkdir -p /var/backups/cluster
++ date +%Y%m%d
+ tar -czf /var/backups/cluster/auth-api_20260825.tar.gz -C /etc/auth-api conf.d
+ set +x
```

Зверніть увагу на подвійний плюс `++`: оболонка автоматично додає додатковий символ префіксу для позначення команд, що виконуються у вкладеній підоболонці під час підстановки `$(date +%Y%m%d)`.

### Локалізація трасування та керування шумом

У великих сценаріях увімкнення `set -x` на рівні всього файлу призводить до генерації сотень мегабайтів логів, у яких розробник тоне під час аналізу циклів на тисячі ітерацій. Патерн локального трасування вирішує цю проблему:

```bash
process_records() {
    local record_id="$1"
    
    # Трасуємо лише специфічний проблемний запис
    if [[ "${record_id}" -eq 404 ]]; then
        set -x
    fi

    perform_complex_calculation "${record_id}"

    if [[ "${record_id}" -eq 404 ]]; then
        set +x
    fi
}
```

### Захист чутливих даних у логах неперервної інтеграції

Критичною небезпекою `set -x` є ненавмисний витік секретів (паролів до баз даних, API-токенів, приватних ключів) у відкриті логи CI/CD систем на кшталт GitHub Actions чи GitLab CI. Оскільки `set -x` друкує команду після розгортання всіх змінних, рядок `curl -H "Authorization: Bearer ${SECRET_TOKEN}" https://api.service.internal` розкриє повний токен усім, хто має доступ до перегляду журналу збірки.

Для запобігання витоку застосовують тимчасове відключення трасування або перенаправлення діагностичного потоку:

```bash
# Безпечний патерн виконання операції з секретом
{
    # Тимчасово вимикаємо трасування, якщо воно було активне
    { set +x; } 2>/dev/null
    
    # Виконуємо операцію з секретом у закритому режимі
    curl -sSf -H "Authorization: Bearer ${VAULT_SECRET_TOKEN}" \
         "https://vault.internal.net/v1/secret/data/db" > /tmp/db_creds.json
         
    # Відновлюємо трасування, якщо необхідно
    set -x
}
```

### Ізоляція потоку трасування через `BASH_XTRACEFD`

За замовчуванням вивід `set -x` змішується зі звичайним потоком помилок `stderr` (дескриптор 2). Якщо сценарій аналізує вивід помилок зовнішньої утиліти або перенаправляє `2>&1` у конвеєр, рядки трасування забруднюють бізнес-дані програми.

Починаючи з версії 4.1, Bash надає спеціальну змінну `BASH_XTRACEFD`. Якщо цій змінній присвоїти номер відкритого файлового дескриптора, інтерпретатор автоматично спрямовуватиме всі службові повідомлення `set -x` виключно в цей дескриптор:

```bash
#!/usr/bin/env bash
set -euo pipefail

# Відкриваємо дескриптор 19 для запису у виділений файл трасування
exec 19> "/tmp/deployment_trace_$$.log"
export BASH_XTRACEFD=19

set -x
echo "Цей рядок іде у стандартний вивід"
ls /etc/hosts
# Усі службові рядки '+' опиняються у файлі /tmp/deployment_trace_$$.log
```

## Контекстний префікс `PS4`: інтроспекція викликів, часу та процесів

Стандартний префікс трасування `+ ` не містить інформації про те, у якому саме файлі вихідного коду, на якому рядку чи всередині якої функції виконується інструкція. За форматування цього префіксу відповідає системна змінна `PS4` (Prompt String 4).

Унікальна особливість `PS4` у Bash полягає в тому, що її значення піддається повному розгортанню параметрів, арифметики та команд щоразу перед виведенням чергового рядка трасування. Це дозволяє вбудовувати в префікс системні змінні інтроспекції:

| Змінна інтроспекції | Тип даних | Опис значення |
| :--- | :--- | :--- |
| `${BASH_SOURCE[0]}` | Рядок | Шлях до файлу вихідного коду, де розташована поточна інструкція. |
| `${LINENO}` | Число | Номер рядка у вихідному файлі. |
| `${FUNCNAME[0]}` | Рядок | Назва поточної функції (порожня на рівні головного тіла скрипту). |
| `${BASH_SUBSHELL}` | Число | Рівень вкладеності підоболонок (`0` для основного процесу, `1+` для `(...)`). |
| `${BASHPID}` | Число | Реальний ідентифікатор поточного процесу (PID), що оновлюється у підоболонках. |
| `${EPOCHREALTIME}` | Дробове число | Системний час у секундах із мікросекундною точністю (`секунди.мікросекунди`). |

### Побудова інформативного промислового префіксу

Сконструюємо професійний префікс для налагодження складних модульних сценаріїв:

```bash
export PS4='+ [${EPOCHREALTIME}] [pid:${BASHPID}|sub:${BASH_SUBSHELL}] [${BASH_SOURCE[0]##*/}:${LINENO}] ${FUNCNAME[0]:+${FUNCNAME[0]}(): }'
```

Розберемо роботу цієї конструкції:
1. `+ `: перший символ префіксу. За правилами POSIX оболонка дублює перший символ (`+`, `++`, `+++`) відповідно до глибини вкладеності підоболонок;
2. `[${EPOCHREALTIME}]`: фіксує точний системний час виконання кожної інструкції, що дає змогу миттєво знаходити вузькі місця затримок;
3. `[pid:${BASHPID}|sub:${BASH_SUBSHELL}]`: показує, чи виконується команда в основному процесі, чи у відгалуженій підоболонці;
4. `[${BASH_SOURCE[0]##*/}:${LINENO}]`: виводить ім'я файлу без повного каталожного шляху та номер рядка;
5. `${FUNCNAME[0]:+${FUNCNAME[0]}(): }`: якщо команда викликана всередині функції, виводить її назву з круглими дужками, інакше підставляє порожній рядок.

Приклад виводу трасування з таким префіксом:

```text
+ [1724594102.348102] [pid:41022|sub:0] [cluster.sh:42] init_network(): ip link set dev eth0 up
+ [1724594102.351290] [pid:41022|sub:0] [cluster.sh:43] init_network(): ip addr add 192.168.1.50/24 dev eth0
++ [1724594102.354811] [pid:41025|sub:1] [cluster.sh:48] check_gateway(): ping -c 1 -W 1 192.168.1.1
```

Різниця між часовими позначками `1724594102.351290` та `1724594102.348102` показує, що операція конфігурації інтерфейсу зайняла рівно 3.188 мілісекунди.

### Профілювання тривалості виконання інструкцій

Наявність `${EPOCHREALTIME}` у `PS4` дозволяє не лише читати послідовність викликів, а й аналізувати продуктивність сценарію за допомогою простих потокових фільтрів `awk`. Зберігши вивід `xtrace` у файл, можна автоматично обчислити дельту часу між кожними двома послідовними рядками та відсортувати команди за спаданням тривалості:

```bash
# Пошук найповільніших інструкцій у журналі трасування
awk -F'[\\[\\]]' '/^\+/ {
    t = $2;
    if (prev_t > 0) {
        delta = t - prev_t;
        if (delta > 0.05) {  # Відбираємо команди, що тривали понад 50 мс
            printf "%8.4f c | %s\n", delta, prev_cmd;
        }
    }
    prev_t = t;
    prev_cmd = $0;
}' /tmp/trace.log | sort -rn | head -n 10
```

Цей метод дозволяє миттєво локалізувати неочікувані блокування введення-виведення, мережеві таймаути чи важкі обчислення без залучення зовнішніх профілювальників.

## Пастки інтроспекції `trap`: DEBUG, ERR та реконструкція бектрейсу

Трасування `set -x` генерує пасивний журнал. Для активного перехоплення позаштатних ситуацій, інтерактивного керування та автоматичного збору стек-трейсів застосовується механізм пасток `trap`.

![Інтроспекція стека викликів у Bash](/root/sys/sys-unix/script-debugging/img/bash-call-stack-arrays.svg)
*Зв'язок масивів інтроспекції Bash та алгоритм відновлення стека викликів під час аварійної зупинки.*

Bash підтримує внутрішні масиви викликів, які оновлюються динамічно:
- `${FUNCNAME[@]}`: стек функцій, де індекс `0` — поточна підпрограма, а останній індекс — `main`;
- `${BASH_SOURCE[@]}`: шляхи до файлів, де визначені відповідні функції;
- `${BASH_LINENO[@]}`: номери рядків, у яких здійснено виклик функції `${FUNCNAME[i]}` з файлу `${BASH_SOURCE[i+1]}`.

### Перехоплення події `DEBUG` для покрокового контролю

Пастка `trap '...' DEBUG` виконується інтерпретатором перед кожною простою інструкцією. У цей момент змінна `${BASH_COMMAND}` містить точний рядок команди, яка має виконатися наступною.

За замовчуванням функції не успадковують обробник `DEBUG`. Щоб пастка діяла всередині підпрограм, необхідно встановити прапорець функціонального трасування `set -T` (або `set -o functrace`).

```bash
#!/usr/bin/env bash
set -T

# Простий лічильник команд та протоколювання інструкцій
__trace_instruction() {
    local cmd="${BASH_COMMAND}"
    local line="${BASH_LINENO[0]}"
    local src="${BASH_SOURCE[1]}"
    echo ">> [DEBUG] Виконується: '${cmd}' на рядку ${src}:${line}" >&2
}

trap '__trace_instruction' DEBUG

x=10
y=20
z=$(( x + y ))
```

Якщо увімкнути режим `shopt -s extdebug`, обробник `DEBUG` отримує суперсилу: якщо функція-обробник повертає числовий код `2`, Bash **пропускає виконання поточної команди** і переходить до наступної, що дозволяє створювати мок-середовища та перехоплювати небезпечні операції.

### Перехоплення збоїв через сигнал `ERR`

Сигнал `ERR` викликається інтерпретатором щоразу, коли проста команда повертає статус виходу, відмінний від нуля (`$? != 0`). 

Для того щоб пастка `ERR` надійно перехоплювала збої всередині функцій і підоболонок, сценарій повинен увімкнути прапорець трасування помилок `set -E` (або `set -o errtrace`).

```bash
#!/usr/bin/env bash
set -Eeuo pipefail

on_error_backtrace() {
    local exit_code="$1"
    local failed_cmd="$2"
    local failed_line="$3"
    local failed_file="$4"

    # Вимикаємо ERR-пастку для запобігання рекурсивним збоям усередині обробника
    trap '' ERR

    echo -e "\n[АВАРІЙНИЙ СТЕК-ТРЕЙС] Код помилки: ${exit_code}" >&2
    echo "  Збій команди: '${failed_cmd}'" >&2
    echo "  Локація:      ${failed_file}:${failed_line}" >&2
    echo "  Стек викликів:" >&2

    local depth=${#FUNCNAME[@]}
    for (( i=1; i<depth; i++ )); do
        local fn="${FUNCNAME[$i]}"
        local file="${BASH_SOURCE[$i]}"
        local line="${BASH_LINENO[$((i-1))]}"
        echo "    #$((i-1)) ${fn}() у ${file}:${line}" >&2
    done
    exit "${exit_code}"
}

trap 'on_error_backtrace "$?" "${BASH_COMMAND}" "${LINENO}" "${BASH_SOURCE[0]}"' ERR
```

Повний робочий код інтерактивного крокового налагоджувача та автономного модуля бектрейсу реалізовано у вставці [модуль автоматичного бектрейсу та покроковий відлагоджувач](root:sys-unix/script-debugging/proj-bash-stacktrace-and-step-debugger.md). Історію появи змінної `PS4`, масивів інтроспекції та пасток викликів описано у вставці [історія еволюції засобів діагностики оболонки](root:sys-unix/script-debugging/hist-shell-debugging-evolution.md).

## Статичний аналіз коду через `ShellCheck`

Динамічне налагодження дозволяє знайти причину збою, коли він уже стався під час виконання. Проте найнебезпечніші дефекти в shell-скриптах криються в крайових випадках, які не проявляються під час стандартного ручного тестування.

![Статичний аналіз сценаріїв через ShellCheck](/root/sys/sys-unix/script-debugging/img/shellcheck-ast-analysis.svg)
*Архітектура статичного аналізатора ShellCheck: побудова AST та виявлення типових пасток середовища.*

**ShellCheck** — це спеціалізований статичний аналізатор вихідного коду для сценаріїв оболонки (підтримує діалекти `sh`, `bash`, `dash`, `ksh`). Він парсить текст програми, будує абстрактне синтаксичне дерево (AST) та проводить перевірку контекстів обчислень і потоків даних.

Розглянемо найнебезпечніші пастки, які ShellCheck виявляє автоматично.

### SC2086: Незалапковані змінні (Double quote to prevent globbing and word splitting)

Це найбільш розповсюджена та небезпечна вразливість у shell-програмуванні.

```bash
# Дефектний код:
rm -rf $TARGET_DIR/cache

# Безпечний еквівалент:
rm -rf "${TARGET_DIR}/cache"
```

**Механізм пастки:** якщо змінна `TARGET_DIR` містить пробіли (наприклад, `/var/app data`), розгортання без лапок призведе до того, що команда `rm` отримає два окремих аргументи: `/var/app` та `data/cache`. Якщо ж змінна `TARGET_DIR` взагалі виявиться порожньою (унаслідок друкарської помилки або збою попереднього кроку), вираз `$TARGET_DIR/cache` перетвориться на `/cache`, і команда знищить системний кореневий каталог кешу. Подвійні лапки гарантують, що результат розгортання передається системному виклику як єдиний аргумент `argv[i]`.

### SC2046: Розщеплення підстановки команд (Quote this to prevent word splitting)

```bash
# Дефектний код:
for file in $(find /tmp/uploads -type f); do
    process_file "$file"
done

# Безпечний еквівалент:
while IFS= read -r -d '' file; do
    process_file "${file}"
done < <(find /tmp/uploads -type f -print0)
```

**Механізм пастки:** вивід команди `$(find ...)` підставляється в тіло циклу `for` і піддається розщепленню за пробілами, табуляціями та символами нового рядка (роздільниками `IFS`). Якщо ім'я файлу містить пробіл (`User Invoice 2026.pdf`), цикл `for` виконає три окремі ітерації для `User`, `Invoice` та `2026.pdf`.

### SC2155: Маскування коду повернення при оголошенні `local` (Declare and assign separately)

Ця пастка регулярно призводить до катастрофічних збоїв у сценаріях, захищених прапорцем `set -e`.

```bash
# Дефектний код:
fetch_metrics() {
    local metrics_data=$(curl -sSf "https://metrics.service.internal/api")
    echo "Дані отримано: ${metrics_data}"
}

# Безпечний еквівалент:
fetch_metrics() {
    local metrics_data
    metrics_data=$(curl -sSf "https://metrics.service.internal/api")
    echo "Дані отримано: ${metrics_data}"
}
```

**Механізм пастки:** інструкція `local` — це самостійна вбудована команда оболонки (builtin). Коли оголошення та присвоєння об'єднані в один рядок `local var=$(cmd)`, оболонка спочатку виконує команду `cmd` (яка, наприклад, падає з кодом `22`), а потім передає результат вбудованій команді `local`. Команда `local` успішно створює локальну змінну і завершується з кодом **`0`**. 

У результаті підсумковий статус виходу рядка дорівнює `0`, і прапорець `set -e`, як і пастка `trap '...' ERR`, **не спрацьовують**, маскуючи повний крах мережевого запиту. Розділення оголошення `local var` та присвоєння `var=$(cmd)` на два окремих рядки повертає справжній статус команди підстановки.

### SC2168: Використання `local` поза межами функцій

```bash
# Дефектний код у тілі глобального скрипту:
#!/usr/bin/env bash
local config_file="/etc/app.conf"

# ShellCheck діагностує:
# SC2168: 'local' is only valid in functions.
```

**Механізм пастки:** ключове слово `local` за стандартом оболонки існує виключно всередині стека функцій. Виклик `local` на рівні файлу викликає помилку інтерпретатора під час виконання.

### SC2034 та SC2181: Невикористані змінні та перевірка `$?`

Правило **SC2034** ловить друкарські помилки в іменах параметрів (`DATABASE_PRT=5432` замість `DATABASE_PORT=5432`) або відсутність обов'язкового `export` для змінних, які очікують дочірні бінарні процеси.

Правило **SC2181** виявляє антипатерн перевірки результату команди через проміжне звернення до `$?`:

```bash
# Антипатерн (SC2181):
run_backup
if [ $? -ne 0 ]; then
    echo "Збій!"
fi

# Ідіоматична перевірка:
if ! run_backup; then
    echo "Збій!"
fi
```

Пряма перевірка команди в умові `if ! run_backup` є надійною, оскільки виключає випадкове затирання `$?` проміжними інструкціями (наприклад, фоновими викликами або командами логування).

### SC1090 та SC1091: Контроль динамічного підключення файлів (`source`)

Коли сценарій підключає зовнішні модулі через `source "${CONFIG_PATH}"`, статичний аналізатор не може автоматично визначити шлях до файлу. ShellCheck вимагає явної вказівки директиви пошуку:

```bash
# Вказівка шляху до модуля для статичного перегляду:
# shellcheck source=lib/database_helpers.sh
source "${LIB_DIR}/database_helpers.sh"
```

Це дозволяє ShellCheck завантажити абстрактне синтаксичне дерево підключеного файлу і перевірити коректність викликів усіх функцій та експортованих змінних між модулями проєкту.

### Інтеграція ShellCheck у конвеєри CI/CD та Pre-commit

Автоматична перевірка всього репозиторію сценаріїв інтегрується в систему контролю версій перед злиттям змін.

Приклад конфігурації завдання перевірки для GitHub Actions (`.github/workflows/lint-scripts.yml`):

```yaml
name: Lint Shell Scripts
on: [push, pull_request]

jobs:
  shellcheck:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Run ShellCheck
        run: |
          # Перевіряємо всі файли з розширенням .sh та виконувані bash-файли
          find . -type f -name "*.sh" -exec shellcheck -f gcc --severity=style {} +
```

Формат `-f gcc` генерує стандартні звіти у вигляді `файл:рядок:колонка: рівень: опис [SCxxxx]`, які автоматично парсяться редакторами коду (VS Code, Neovim) та системами перегляду коду.

Якщо певне попередження є свідомим інженерним рішенням (наприклад, навмисне розбиття слів аргументів), його можна локально придушити за допомогою директиви коментаря безпосередньо перед проблемним рядком:

```bash
# Безпечне придушення попередження з обов'язковим обґрунтуванням:
# shellcheck disable=SC2086 -- аргументи компілятора мають бути розбиті на окремі прапорці
gcc ${COMPILER_FLAGS} -o output main.c
```

## Зведена матриця інструментів та стратегія комплексного відлагодження

Надійна експлуатація скриптів вимагає комбінування всіх розглянутих засобів на відповідних фазах життєвого циклу розробки.

| Інструмент / Метод | Етап застосування | Об'єкт діагностики | Накладні витрати на виконання |
| :--- | :--- | :--- | :--- |
| **ShellCheck** | Редагування, Git pre-commit, CI/CD | Синтаксис AST, розбиття слів, маскування статусів, переносимість. | Нульові (виконується офлайн до запуску коду). |
| **`bash -n`** | Pre-deploy валідація артефактів | Цілісність синтаксичних блоків без виконання системних дій. | Мінімальні (парсинг без запуску процесів). |
| **`set -x` + `PS4`** | Тестові стенди, аналіз збоїв CI | Послідовність розгорнутих команд, час виконання, вкладеність викликів. | Низькі (друк службових рядків у дескриптор). |
| **`trap ... ERR`** | Продакшн-середовище | Автоматичний бектрейс при аварійній зупинці процесу. | Нульові у штатному режимі (виклик лише при збої). |
| **`trap ... DEBUG`** | Локальна розробка та налагодження | Покрокове трасування, інспекція змінних, точки зупинки. | Високі (виклик обробника перед кожною інструкцією). |

### Промисловий шаблон безпечного та діагностованого сценарію

Об'єднаємо розглянуті інструменти в єдиний стандартизований шаблон для написання стійких до збоїв сценаріїв:

```bash
#!/usr/bin/env bash
# ==============================================================================
# Промисловий шаблон системного сценарію з повною діагностикою
# ==============================================================================
set -Eeuo pipefail
shopt -s inherit_errexit 2>/dev/null || true

# 1. Налаштування детального префіксу трасування
export PS4='+ [${EPOCHREALTIME:-0}] [pid:${BASHPID}] [${BASH_SOURCE[0]##*/}:${LINENO}] ${FUNCNAME[0]:+${FUNCNAME[0]}(): }'

# 2. Обробник аварійного стек-трейсу
__emergency_backtrace() {
    local err_code="$1"
    local cmd="$2"
    local line="$3"
    local src="$4"
    trap '' ERR

    echo -e "\n\033[1;31m[CRITICAL FAILURE]\033[0m Сценарій завершився з кодом ${err_code}" >&2
    echo "  Невдала інструкція: '${cmd}'" >&2
    echo "  Файл та рядок:      ${src}:${line}" >&2
    echo "  Стек викликів:" >&2

    local depth=${#FUNCNAME[@]}
    for (( i=1; i<depth; i++ )); do
        echo "    #$((i-1)) ${FUNCNAME[$i]}() у ${BASH_SOURCE[$i]}:${BASH_LINENO[$((i-1))]}" >&2
    done
    exit "${err_code}"
}

# 3. Реєстрація пастки
trap '__emergency_backtrace "$?" "${BASH_COMMAND}" "${LINENO}" "${BASH_SOURCE[0]}"' ERR

# 4. Основна логіка сценарію
main() {
    local target_env="${1:-production}"
    echo "Запуск сценарію для середовища: ${target_env}"
    # Бізнес-логіка...
}

main "$@"
```

Завдяки поєднанню попередньої статичної валідації ShellCheck, вичерпного динамічного трасування через розширений `PS4` та автоматичної інтроспекції через пастки `ERR`, сценарії оболонки трансформуються з непередбачуваних чорних скриньок на прозорі, керовані та надійні компоненти операційної системи.
