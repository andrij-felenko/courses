# ⚙️ Модуль автоматичного бектрейсу та покроковий відлагоджувач Bash

У складних багатомодульних сценаріях системного адміністрування, автоматизації збірки та хмарного розгортання падіння глибоко вкладеної функції зазвичай залишає в системному журналі лише неінформативний числовий код помилки. Розробник змушений вручну відтворювати послідовність викликів, гадаючи, які саме аргументи призвели до аварії. Цей практичний проєкт демонструє створення двох взаємодоповнюючих діагностичних інструментів, реалізованих виключно засобами оболонки GNU Bash без залучення сторонніх утиліт: автоматичного генератора бектрейсу з підсвічуванням вихідного коду (`lib_stacktrace.bash`) та повноцінного інтерактивного покрокового відлагоджувача з командним інтерфейсом (`lib_debugger.bash`).

---

## 1. Архітектурні вимоги та виклики інтроспекції

Створення надійного діагностичного інструментарію всередині інтерпретатора оболонки вимагає врахування низки фундаментальних обмежень середовища Unix та процесної моделі Bash:

### 1.1. Фіксація та збереження глобального стану `$?`

Головна небезпека при написанні обробників пасток полягає в надзвичайній крихкості змінної статусу повернення `$?`. Будь-яка команда, виконана інтерпретатором (навіть виклик вбудованої команди `echo`, операція перевірки файлу `[ -f ... ]`, присвоєння змінної з розгортанням чи арифметичний вираз `(( ))`), негайно перезаписує значення `$?` власним кодом завершення. Якщо обробник пастки виконає перевірку `if [[ -t 2 ]]` до того, як зафіксує вихідний статус аварійної команди, справжній код збою (наприклад, `127` для відсутнього бінарника або `2` для помилки синтаксису) буде безповоротно втрачено і замінено на `0`. Тому першим непорушним правилом архітектури є передача `$?` як першого позиційного параметра обробника безпосередньо у виклику `trap 'handler "$?" ...'`.

### 1.2. Захист від каскадної рекурсії обробників

Якщо всередині самої функції бектрейсу виникає збій (наприклад, сценарій намагається прочитати тимчасовий файл, який було видалено, або операція виводу повертає помилку `EPIPE`), інтерпретатор Bash сприйме цей статус як новий привід для генерації сигналу `ERR`. Якщо пастка залишається активною, виникає нескінченний цикл рекурсивних викликів обробника, що за лічені мілісекунди вичерпує ліміт пам'яті процесу або переповнює стек викликів. Для гарантованого захисту функція-обробник зобов'язана першою ж внутрішньою дією тимчасово заблокувати пастку інструкцією `trap '' ERR`.

### 1.3. Ізоляція потоків керування та робота з `/dev/tty`

Сценарії автоматизації регулярно виконуються в конвеєрах, де стандартний потік вводу `stdin` (дескриптор 0) перенаправлено з файлу або конвеєра даних (наприклад, `cat inventory.json | deploy.sh`). Якщо інтерактивний відлагоджувач спробує прочитати команду користувача через стандартний виклик `read`, він негайно зчитає черговий рядок бізнес-даних або отримає сигнал кінця файлу (`EOF`), що зруйнує сеанс. Щоб забезпечити повноцінну взаємодію з оператором, відлагоджувач відкриває окремий дуплексний канал прямого доступу до керуючого термінала процесу `/dev/tty` через виділені дескриптори. Якщо ж процес виконується у фоні без термінала (демон, cron, системний сервіс systemd), відлагоджувач виявляє відсутність `/dev/tty` і пасивно пропускає інтерактивну паузу, не блокуючи виконання.

### 1.4. Наскрізне успадкування контексту інтроспекції

За замовчуванням інтерпретатор Bash ізолює обробники пасток: функції та підоболонки не успадковують батьківські пастки `DEBUG` та `ERR`. Для побудови наскрізного моніторингу сценарій повинен явно активувати прапорці `set -E` (`errtrace`) та `set -T` (`functrace`), що змушує інтерпретатор транслювати сигнальні пастки в усі вкладені рівні виконання.

### 2.1. Детальний аналіз алгоритму обходу масивів

Робота обробника спирається на внутрішню домовленість інтерпретатора щодо формування діагностичних масивів:
1. Масив `FUNCNAME` зберігає імена підпрограм у порядку заглиблення стека. Елемент з індексом `0` завжди представляє сам обробник `__stacktrace_handler`. Елемент `FUNCNAME[1]` є функцією, де безпосередньо сталася аварія, а останній елемент масиву відповідає точці входу верхнього рівня.
2. Масиви `BASH_SOURCE` та `BASH_LINENO` містять зміщення: інструкція для виклику функції `FUNCNAME[i]` фізично розташована у файлі `BASH_SOURCE[i]` на рядку `BASH_LINENO[i-1]`.
3. Витяг рядків коду здійснюється за допомогою потокового читача `while read`, що усуває потребу у виклику зовнішніх процесів `sed` чи `awk`. Це критично для системної стабільності, оскільки під час збоїв пам'яті чи перевищення ліміту відкритих дескрипторів спроба створити новий процес через `fork()` завершилася б невдачею.

### 4.1. Результати роботи та аналіз накладних витрат

При виникненні аварії `lib_stacktrace.bash` миттєво формує деталізований звіт:

```text
════════════════════════════════════════════════════════════════════════════

  Команда:   ls "/неіснуючий/системний/шлях/до/ресурсу"
  Місце:     test_app.sh:17

  Контекст вихідного коду:
      15 |     echo "Підключення до ${endpoint} (таймаут ${timeout_sec}с)..."
      16 |     
  ►   17 |     ls "/неіснуючий/системний/шлях/до/ресурсу"
      18 | }
      19 | 

  Стек викликів (Call Stack):
    #0  fetch_remote_resource() у test_app.sh:26
    #1  sync_pipeline() у test_app.sh:31
    #2  <корінь сценарію>() у test_app.sh:35
════════════════════════════════════════════════════════════════════════════
```

У штатному режимі роботи генератор бектрейсу має нульові накладні витрати часу процесора, оскільки обробник `trap ERR` викликається лише в момент виникнення збою. Інтерактивний відлагоджувач у режимі `continue` додає незначну затримку (близько 15–20 мікросекунд на інструкцію для перевірки списку точок зупинки), що робить його придатним для діагностики складних логічних помилок у реальному часі.
