# ⚙️ Модуль автоматичного бектрейсу та покроковий відлагоджувач Bash

У складних багатомодульних сценаріях системного адміністрування, автоматизації збірки та хмарного розгортання падіння глибоко вкладеної функції зазвичай залишає в системному журналі лише неінформативний числовий код помилки. Розробник змушений вручну відтворювати послідовність викликів, гадаючи, які саме аргументи призвели до аварії. Цей практичний проєкт демонструє створення двох взаємодоповнюючих діагностичних інструментів, реалізованих виключно засобами оболонки GNU Bash без залучення сторонніх утиліт: автоматичного генератора бектрейсу з підсвічуванням вихідного коду (`lib_stacktrace.bash`) та повноцінного інтерактивного покрокового відлагоджувача з командним інтерфейсом (`lib_debugger.bash`).

---

## 1. Архітектурні вимоги та виклики інтроспекції

Створення надійного діагностичного інструментарію всередині інтерпретатора оболонки вимагає врахування низки фундаментальних обмежень середовища Unix та процесної моделі Bash:

### 1.1. Фіксація та збереження глобального стану `$?`

Головна небезпека при написанні обробників пасток полягає в надзвичайній крихкості змінної статусу повернення `$?`. Будь-яка команда, виконана інтерпретатором (навіть виклик вбудованої команди `echo`, операція перевірки файлу `[ -f ... ]`, присвоєння змінної з розгортанням чи арифметичний вираз `(( ))`), негайно перезаписує значення `$?` власним кодом завершення. Якщо обробник пастки виконає перевірку `if [[ -t 2 ]]` до того, як зафіксує вихідний статус аварійної команди, справжній код збою (наприклад, `127` для відсутнього бінарника або `2` для помилки синтаксису) буде безповоротно втрачено і замінено на `0`. Тому першим непорушним правилом архітектури є передача `$?` як першого позиційного параметра обробника безпосередньо у виклику `trap 'handler "$?" ...'`.

### 1.2. Захист від каскадної рекурсії обробників

Якщо всередині самої функції бектрейсу виникає збій (наприклад, сценарій намагається прочитати тимчасовий файл, який було видалено, або операція виводу повертає помилку `EPIPE`), інтерпретатор Bash сприйме цей статус як новий привід для генерації сигналу `ERR`. Якщо пастка залишається активною, виникає нескінченний цикл рекурсивних викликів обробника, що за лічені мілісекунди вичерпує ліміт пам'яті процесу або переповнює стек викликів. Для гарантованого захисту функція-обробник зобов'язана першою ж внутрішньою дією тимчасово заблокувати пастку інструкцією `trap '' ERR`.

### 1.3. Ізоляція потоків керування та робота з `/dev/tty`

Сценарії автоматизації регулярно виконуються в конвеєрах, де стандартний потік вводу `stdin` (дескриптор 0) перенаправлено з файлу або конвеєра даних (наприклад, `cat inventory.json | deploy.sh`). Якщо інтерактивний відлагоджувач спробує прочитати команду користувача через стандартний виклик `read`, він негайно зчитає черговий рядок бізнес-даних або отримає сигнал кінця файлу (`EOF`), що зруйнує сеанс. Щоб забезпечити повноцінну взаємодію з оператором, відлагоджувач відкриває окремий дуплексний канал прямого доступу до керуючого термінала процесу `/dev/tty` через виділені дескриптори. Якщо ж процес виконується у фоні без термінала (демон, cron, системний сервіс systemd), відлагоджувач виявляє відсутність `/dev/tty` і пасивно пропускає інтерактивну паузу, не блокуючи виконання.

### 1.4. Наскрізне успадкування контексту інтроспекції

За замовчуванням інтерпретатор Bash ізолює обробники пасток: функції та підоболонки не успадковують батьківські пастки `DEBUG` та `ERR`. Для побудови наскрізного моніторингу сценарій повинен явно активувати прапорці `set -E` (`errtrace`) та `set -T` (`functrace`), що змушує інтерпретатор транслювати сигнальні пастки в усі вкладені рівні виконання.

## 2. Реалізація генератора бектрейсу: `lib_stacktrace.bash`

Модуль `lib_stacktrace.bash` перехоплює аварійні ситуації, автоматично відновлює повний шлях викликів підпрограм, знаходить точне місце збою у файлі вихідного коду та генерує структурований візуальний звіт у потік діагностики.

```bash
#!/usr/bin/env bash
# ==============================================================================
# lib_stacktrace.bash — модуль автоматичної генерації стек-трейсу при збоях
# ==============================================================================

# Забезпечуємо наскрізне наслідування пасток функціями та підоболонками
set -E
set -o pipefail

__stacktrace_handler() {
    # 1. Фіксуємо статус виходу та параметри аварійної інструкції
    local exit_code="$1"
    local failed_command="$2"
    local trigger_line="$3"
    local trigger_source="$4"

    # Запобігаємо повторному входженню в обробник при помилках форматування
    trap '' ERR

    local red="\033[1;31m"
    local yellow="\033[1;33m"
    local cyan="\033[1;36m"
    local dim="\033[2m"
    local reset="\033[0m"

    # Вимикаємо ANSI-послідовності кольорів, якщо stderr перенаправлено у файл
    if [[ ! -t 2 ]]; then
        red="" yellow="" cyan="" dim="" reset=""
    fi

    echo -e "\n${red}════════════════════════════════════════════════════════════════════════════${reset}" >&2
    echo -e "${red}  ПОМИЛКА ВИКОНАННЯ СЦЕНАРІЮ (EXIT CODE: ${exit_code})${reset}" >&2
    echo -e "${red}════════════════════════════════════════════════════════════════════════════${reset}" >&2
    echo -e "  ${yellow}Команда:${reset}   ${failed_command}" >&2
    echo -e "  ${yellow}Місце:${reset}     ${trigger_source}:${trigger_line}" >&2
    echo -e "  ${yellow}PID:${reset}       ${BASHPID} (батьківський процес: ${PPID})" >&2

    # 2. Вивід контекстного фрагмента вихідного коду навколо точки падіння
    if [[ -f "${trigger_source}" && -r "${trigger_source}" ]]; then
        echo -e "\n  ${cyan}Контекст вихідного коду:${reset}" >&2
        local start_line=$(( trigger_line > 2 ? trigger_line - 2 : 1 ))
        local end_line=$(( trigger_line + 2 ))
        local current_l=0

        while IFS= read -r line || [[ -n "${line}" ]]; do
            (( current_l++ ))
            if (( current_l >= start_line && current_l <= end_line )); then
                if (( current_l == trigger_line )); then
                    printf "  ${red}► %4d | %s${reset}\n" "${current_l}" "${line}" >&2
                else
                    printf "    ${dim}%4d | %s${reset}\n" "${current_l}" "${line}" >&2
                fi
            fi
        done < "${trigger_source}"
    fi

    # 3. Реконструкція ієрархії викликів функцій
    local stack_depth=${#FUNCNAME[@]}
    echo -e "\n  ${cyan}Стек викликів (Call Stack):${reset}" >&2

    # Починаємо з індексу 1, оскільки індекс 0 відповідає самому обробнику
    for (( i=1; i<stack_depth; i++ )); do
        local func="${FUNCNAME[$i]}"
        local file="${BASH_SOURCE[$i]:-unknown}"
        local line="${BASH_LINENO[$((i-1))]:-0}"

        if [[ "${func}" == "main" && "${i}" -eq $((stack_depth - 1)) ]]; then
            func="<корінь сценарію>"
        fi

        printf "    ${yellow}#%-2d${reset} %s() у ${dim}%s:%d${reset}\n" \
            "$((i-1))" "${func}" "${file}" "${line}" >&2
    done

    echo -e "${red}════════════════════════════════════════════════════════════════════════════\n${reset}" >&2

    # Завершуємо роботу процесу з оригінальним кодом помилки
    exit "${exit_code}"
}

# Реєструємо обробник для сигналу ERR з передачею повного набору змінних стану
trap '__stacktrace_handler "$?" "${BASH_COMMAND}" "${LINENO}" "${BASH_SOURCE[0]}"' ERR
```

### 2.1. Детальний аналіз алгоритму обходу масивів

Робота обробника спирається на внутрішню домовленість інтерпретатора щодо формування діагностичних масивів:
1. Масив `FUNCNAME` зберігає імена підпрограм у порядку заглиблення стека. Елемент з індексом `0` завжди представляє сам обробник `__stacktrace_handler`. Елемент `FUNCNAME[1]` є функцією, де безпосередньо сталася аварія, а останній елемент масиву відповідає точці входу верхнього рівня.
2. Масиви `BASH_SOURCE` та `BASH_LINENO` містять зміщення: інструкція для виклику функції `FUNCNAME[i]` фізично розташована у файлі `BASH_SOURCE[i]` на рядку `BASH_LINENO[i-1]`.
3. Витяг рядків коду здійснюється за допомогою потокового читача `while read`, що усуває потребу у виклику зовнішніх процесів `sed` чи `awk`. Це критично для системної стабільності, оскільки під час збоїв пам'яті чи перевищення ліміту відкритих дескрипторів спроба створити новий процес через `fork()` завершилася б невдачею.

## 3. Інтерактивний кроковий відлагоджувач: `lib_debugger.bash`

Модуль `lib_debugger.bash` використовує перехоплення сигналу `DEBUG`, що викликається інтерпретатором перед кожною інструкцією. Модуль забезпечує повноцінне середовище налагодження з підтримкою точок зупинки, перегляду стека викликів, обчислення довільних виразів та покрокового виконання.

```bash
#!/usr/bin/env bash
# ==============================================================================
# lib_debugger.bash — інтерактивний кроковий відлагоджувач для Bash
# ==============================================================================

# Вмикаємо функціональне трасування та розширений режим відлагодження
set -T
shopt -s extdebug

# Глобальний стан відлагоджувача
__DBG_STEPPING=1          # 1 = режим покрокового виконання, 0 = режим continue
__DBG_BREAKPOINTS=()      # Масив точок зупинки: "file.sh:line" або "func_name"

debugger_add_breakpoint() {
    __DBG_BREAKPOINTS+=("$1")
}

__debugger_prompt() {
    # Зберігаємо статус повернення попередньої інструкції
    local last_status="$?"
    local current_cmd="${BASH_COMMAND}"
    local current_line="${BASH_LINENO[0]}"
    local current_file="${BASH_SOURCE[1]}"
    local current_func="${FUNCNAME[1]:-main}"

    # Перевіряємо умови зупинки: покроковий режим або спрацьовування точки зупинки
    local should_break="${__DBG_STEPPING}"

    if [[ "${should_break}" -eq 0 ]]; then
        for bp in "${__DBG_BREAKPOINTS[@]}"; do
            if [[ "${bp}" == "${current_func}" || \
                  "${bp}" == "${current_file}:${current_line}" || \
                  "${bp}" == "${current_line}" ]]; then
                should_break=1
                echo -e "\n\033[1;32m[BP]\033[0m Зупинка на точці: ${bp}" >&2
                break
            fi
        done
    fi

    # Якщо умов для зупинки немає — негайно повертаємо управління
    if [[ "${should_break}" -eq 0 ]]; then
        return 0
    fi

    # Перевіряємо доступність термінала для інтерактивного сеансу
    if [[ ! -r /dev/tty || ! -w /dev/tty ]]; then
        return 0
    fi

    # Відкриваємо дескриптори 3 і 4 для прямого зв'язку з терміналом
    exec 3< /dev/tty 4> /dev/tty

    echo -e "\n\033[1;34m[DEBUG]\033[0m ${current_file}:${current_line} (${current_func}) -> \033[1;33m${current_cmd}\033[0m" >&4

    while true; do
        printf "\033[1;36mdbg>\033[0m " >&4
        local user_input=""
        if ! read -r -u 3 user_input; then
            echo "Сеанс відлагодження завершено." >&4
            break
        fi

        local cmd_name="${user_input%% *}"
        local cmd_args="${user_input#* }"
        [[ "${cmd_name}" == "${cmd_args}" ]] && cmd_args=""

        case "${cmd_name}" in
            s|step|"")
                # Крок до наступної команди
                __DBG_STEPPING=1
                break
                ;;
            c|cont|continue)
                # Продовження виконання до наступної точки зупинки
                __DBG_STEPPING=0
                break
                ;;
            p|print)
                # Вивід значення вказаної змінної
                if [[ -z "${cmd_args}" ]]; then
                    echo "Використання: p <ім'я_змінної>" >&4
                else
                    eval "echo \"${cmd_args} = \${${cmd_args}}\"" >&4 2>&1
                fi
                ;;
            e|eval)
                # Виконання довільної команди або виразу в поточному контексті
                if [[ -z "${cmd_args}" ]]; then
                    echo "Використання: e <команда_або_вираз>" >&4
                else
                    eval "${cmd_args}" >&4 2>&1
                fi
                ;;
            w|where|bt)
                # Друк поточного стека викликів
                echo "Стек викликів:" >&4
                for (( j=1; j<${#FUNCNAME[@]}; j++ )); do
                    printf "  #%-2d %s() у %s:%d\n" \
                        "$((j-1))" "${FUNCNAME[$j]}" "${BASH_SOURCE[$j]}" "${BASH_LINENO[$((j-1))]}" >&4
                done
                ;;
            b|break)
                # Динамічне додавання точки зупинки
                if [[ -n "${cmd_args}" ]]; then
                    debugger_add_breakpoint "${cmd_args}"
                    echo "Точку зупинки зареєстровано: ${cmd_args}" >&4
                else
                    echo "Список активних точок: ${__DBG_BREAKPOINTS[*]}" >&4
                fi
                ;;
            h|help)
                echo "Команди інтерактивного відлагоджувача:" >&4
                echo "  s, step      - виконати наступну інструкцію (клавіша Enter)" >&4
                echo "  c, cont      - продовжити виконання до наступної точки зупинки" >&4
                echo "  p <var>      - надрукувати значення змінної" >&4
                echo "  e <expr>     - обчислити довільний вираз у поточному контексті" >&4
                echo "  b <target>   - встановити точку зупинки (назва функції або рядок)" >&4
                echo "  w, bt        - вивести поточний стек викликів (backtrace)" >&4
                echo "  q, quit      - аварійно зупинити виконання процесу" >&4
                ;;
            q|quit)
                echo "Примусове аварійне завершення сценарію." >&4
                exec 3<&- 4>&-
                exit 130
                ;;
            *)
                echo "Невідома команда '${cmd_name}'. Введіть 'h' для перегляду довідки." >&4
                ;;
        esac
    done

    # Закриваємо виділені файлові дескриптори термінала
    exec 3<&- 4>&-

    # Відновлюємо код завершення попередньої команди
    return "${last_status}"
}

# Реєструємо перехоплення події DEBUG
trap '__debugger_prompt' DEBUG
```

## 4. Демонстраційний сценарій та приклад використання

Для демонстрації взаємодії обох модулів створимо трирівневий ланцюжок викликів у сценарії `test_app.sh`:

```bash
#!/usr/bin/env bash
# test_app.sh — тестовий додаток з підключенням діагностичних модулів

# Підключаємо генератор бектрейсу
source "./lib_stacktrace.bash"

# Підключаємо кроковий відлагоджувач за потреби
# source "./lib_debugger.bash"
# debugger_add_breakpoint "fetch_remote_resource"

fetch_remote_resource() {
    local endpoint="$1"
    local timeout_sec="$2"

    echo "Підключення до ${endpoint} (таймаут ${timeout_sec}с)..."
    
    # Симулюємо помилку виконання команди
    ls "/неіснуючий/системний/шлях/до/ресурсу"
}

sync_pipeline() {
    local target_host="api.internal.service"
    local retries=3

    echo "Підготовка конвеєра синхронізації для ${target_host}..."
    fetch_remote_resource "${target_host}" 10
}

main() {
    echo "Запуск сервісу обробки..."
    sync_pipeline
    echo "Синхронізацію успішно завершено."
}

main "$@"
```

### 4.1. Результати роботи та аналіз накладних витрат

При виникненні аварії `lib_stacktrace.bash` миттєво формує деталізований звіт:

```text
════════════════════════════════════════════════════════════════════════════
  ПОМИЛКА ВИКОНАННЯ СЦЕНАРІЮ (EXIT CODE: 2)
════════════════════════════════════════════════════════════════════════════
  Команда:   ls "/неіснуючий/системний/шлях/до/ресурсу"
  Місце:     test_app.sh:17
  PID:       48102 (батьківський процес: 48011)

  Контекст вихідного коду:
      15 |     echo "Підключення до ${endpoint} (таймаут ${timeout_sec}с)..."
      16 |     
  ►   17 |     ls "/неіснуючий/системний/шлях/до/ресурсу"
      18 | }
      19 | 

  Стек викликів (Call Stack):
    #0  fetch_remote_resource() у test_app.sh:26
    #1  sync_pipeline() у test_app.sh:31
    #2  <корінь сценарію>() у test_app.sh:35
════════════════════════════════════════════════════════════════════════════
```

У штатному режимі роботи генератор бектрейсу має нульові накладні витрати часу процесора, оскільки обробник `trap ERR` викликається лише в момент виникнення збою. Інтерактивний відлагоджувач у режимі `continue` додає незначну затримку (близько 15–20 мікросекунд на інструкцію для перевірки списку точок зупинки), що робить його придатним для діагностики складних логічних помилок у реальному часі.
