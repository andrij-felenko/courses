# 📜 Еволюція засобів діагностики оболонки: від echo до AST-аналізу

Розвиток інструментів діагностики та налагодження командних оболонок Unix відображає фундаментальну еволюцію самої оболонки: від примітивного інтерактивного запускача бінарних файлів у перших версіях Research Unix до повнофункціонального середовища системного програмування, на якому тримається автоматизація сучасної хмарної інфраструктури.

---

## 1. Перші оболонки Unix: епоха німого виконання (1971–1977)

У ранніх версіях Unix (від First Edition до Sixth Edition) командна оболонка Кselect Кена Томпсона (`/bin/sh`) була вкрай простим інтерпретатором. Вона не підтримувала змінних оточення, умовних конструкцій `if/then/else`, циклів і функцій. Сценарій являв собою простий лінійний список команд, які оболонка читала рядок за рядком і передавала системному виклику `exec()`.

У такому середовищі поняття інструментального налагодження було відсутнє як клас:
- єдиним засобом контролю була утиліта `echo`, яка виводила повідомлення про проходження етапів;
- будь-яка синтаксична помилка або відсутній файл спричиняли мовчазний збій або аварійне завершення без збереження контексту;
- системні адміністратори були змушені аналізувати системні виклики через модифікації ядра або трасування ядра операційної системи.

---

## 2. Прорив Стівена Борна: поява `set -x`, `set -v` та пасток `trap` (1979)

Повноцінна мова сценаріїв народилася у 1979 році з виходом Seventh Edition Unix (V7), де дебютувала оболонка Борна — **Bourne Shell** (`sh`), створена Стівеном Борном у Bell Labs. Борн спроєктував оболонку як повноцінну алголоподібну мову програмування зі змінними, циклами, функціями та механізмом обробки сигналів.

Саме Стівен Борн заклав фундамент динамічного трасування, реалізувавши два взаємодоповнюючі прапорці:
1. **`set -v` (`verbose`):** оболонка друкувала вхідний потік символів безпосередньо в момент його зчитування лексером до виконання будь-яких підстановок;
2. **`set -x` (`xtrace`):** оболонка виводила розгорнуту команду безпосередньо перед її виконанням, додаючи на початку жорстко закодований символ `+`.

Крім того, Борн представив вбудовану команду `trap`, яка дозволяла прив'язувати команди оболонки до числових номерів сигналів ядра Unix (зокрема `trap 'rm -f /tmp/lock' 0` для перехоплення завершення процесу `EXIT`). Однак у Bourne Shell ще не було механізму інтроспекції: скрипт не мав доступу до поточного номера рядка чи назви виконуваного файлу, а вивід `set -x` завжди спрямовувався у спільний `stderr`.

## 3. Девід Корн та ksh88: народження змінної `PS4` та сигналу `DEBUG` (1983–1988)

У 1980-х роках у Bell Labs Девід Корн розробив **KornShell** (`ksh88`), яка стала стандартом для комерційних Unix-систем (AT&T System V, AIX, Solaris, HP-UX) і лягла в основу стандарту POSIX.2 (IEEE 1003.2).

Корн усвідомив, що жорстко зашитий префікс `+` у виводі `set -x` не дає змоги зрозуміти, у якому файлі чи функції виник збій у складних модульних системах. Він зробив два революційних нововведення:
- **Змінна `PS4` (Prompt String 4):** Корн зробив префікс трасування настроюваним. Більше того, оболонка стала повторно розгортати значення `PS4` перед кожним друком команди, що дозволило вставляти туди значення змінних під час виконання.
- **Вбудована змінна `LINENO`:** скрипти отримали здатність дізнаватися свій поточний номер рядка.
- **Псевдосигнал `DEBUG`:** Корн розширив механізм `trap`, додавши можливість перехоплювати кожну команду перед її виконанням. Це відкрило шлях до створення перших покрокових налагоджувачів для скриптів.

## 4. GNU Bash та Чет Рамі: розширені масиви інтроспекції та трасування помилок (1989–2010-ті)

У межах проєкту GNU Браян Фокс (Brian Fox) та згодом Чет Рамі (Chet Ramey), який став головним архітектором і мейнтейнером GNU Bash з 1990 року, суттєво розширили діагностичні можливості оболонки:

1. **Масиви контексту викликів (Bash 2.0+):** було додано змінні `${BASH_SOURCE[@]}`, `${FUNCNAME[@]}` та `${BASH_LINENO[@]}`, які вперше надали розробникам повний доступ до стека викликів функцій усередині самого інтерпретатора.
2. **Пастка `ERR` та прапорець `errtrace` (`set -E`):** Bash надав можливість перехоплювати будь-який ненульовий статус завершення без аварійного виходу з процесу.
3. **Ізоляція трасування через `BASH_XTRACEFD` (Bash 4.1, 2009):** з'явилася можливість відокремити потік діагностики `set -x` від загального `stderr` програми, спрямувавши його у виділений файловий дескриптор.
4. **Мікросекундний час `${EPOCHREALTIME}` (Bash 5.0, 2019):** вбудована підтримка точного системного таймера уможливила профілювання тривалості кожного кроку скрипту без виклику зовнішньої утиліти `date`.

## 5. Ера статичного аналізу: ShellCheck Відара Голена (2012–сучасність)

Незважаючи на потужні засоби динамічного трасування, інтерпретована природа shell-скриптів залишалася джерелом критичних інцидентів: помилка в лапках навколо змінної у `rm -rf $DIR/` могла знищити кореневу файлову систему, якщо змінна `$DIR` виявлялася порожньою. Динамічне тестування часто не покривало такі крайові випадки.

У 2012 році норвезький інженер Відар Голен (Vidar Holen) представив **ShellCheck** — статичний аналізатор коду для shell-скриптів, написаний мовою Haskell.

```text
[1971] Thompson Shell   ──►  Тільки echo, виконання наосліп
[1979] Bourne Shell     ──►  set -x, set -v, примітивні trap (V7 Unix)
[1988] KornShell (ksh)  ──►  Кастомізація PS4, змінна LINENO, trap DEBUG
[1995] GNU Bash 2.0+    ──►  Стекові масиви FUNCNAME/BASH_SOURCE, trap ERR
[2009] GNU Bash 4.1+    ──►  BASH_XTRACEFD (ізоляція логів трасування)
[2012] ShellCheck       ──►  Статичний аналіз AST, виявлення пасток до запуску
```

ShellCheck здійснив концептуальний зсув у системному адмініструванні:
- Замість спроб зловити баг під час виконання на "живому" сервері, інструмент будує повне абстрактне синтаксичне дерево (AST) скрипту з урахуванням нюансів різних стандартів (POSIX `sh`, Bash, Dash, Ksh).
- ShellCheck формалізував каталог сотень типових пасток (нестикування типів, розбиття слів через незахищені лапками змінні, маскування статусів виходу командою `local`, проблеми переносимості).
- Інструмент став обов'язковим стандартом у конвеєрах неперервної інтеграції (CI/CD) та перевірках коду (linters), перетворивши написання shell-скриптів із небезпечної лотереї на дисципліновану інженерну практику.
