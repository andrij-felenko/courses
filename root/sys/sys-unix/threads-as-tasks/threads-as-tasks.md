Запустіть багатопотокову програму й подивіться на неї кількома командами. Команда `ps -p 1200` покаже один рядок. Але `ps -p 1200 -L` покаже кілька рядків із тим самим номером 1200 у першій колонці та різними номерами в другій. Команда `kill 1200` завершить усі ці рядки разом, а `taskset` може прив'язати конкретний рядок до окремого ядра процесора.

Виникає запитання: що з цього ядро вважає справжнім суб'єктом? Планувальник ядра тримає єдиний список **задач** (`task_struct`) — кожна має свій лічильник команд, свої регістри й свій стан у черзі. Планувальник не знає про «потоки» як окремий полегшений тип істот. Для нього потік — це звичайна задача, яка ділить ресурси й ідентичність із сусідами. А «процес» — це група таких задач.

## Спільна пам'ять — це ще не потік

Якщо створити задачу викликом `clone()` із прапорцем `CLONE_VM`, вона ділитиме той самий адресний простір (`mm_struct`) з батьківською програмою. Зміни в глобальних змінних однієї задачі миттєво бачить інша.

Проте без додаткових прапорців така задача залишається окремим процесом з власною ідентичністю:
- вона має власний номер PID;
- при її смерті батькові надходить сигнал `SIGCHLD`, і її треба збирати через `wait()`;
- вона має окрему таблицю файлових дескрипторів та власні ліміти ресурсів.

Спільна пам'ять робить можливим швидкий обмін даними, але не створює потоку. Бракує спільної ідентичності.

## Ідентичність і CLONE_THREAD

Справжнім потоком задачу робить прапорець `CLONE_THREAD`. Він заносить нову задачу в **групу задач** (англ. *thread group*) тієї, яка її створила.

Усі задачі групи мають спільний номер — **TGID** (англ. *thread group identifier*). Саме цей номер повертає системний виклик `getpid()`, і саме його бачить користувач як номер процесу. Власний номер задачі повертає `gettid()` (англ. *thread ID*). У першої задачі групи — **лідера групи** — номери `TGID` і `TID` збігаються, тому для однопотокових програм класичний `getpid()` працює без змін.

:::tabs
```c
#define _GNU_SOURCE
#include <pthread.h>
#include <stdio.h>
#include <unistd.h>
#include <sys/syscall.h>

static void *worker(void *arg)
{
    (void)arg;
    printf("потік:   getpid()=%d  gettid()=%ld\n",
           getpid(), (long)syscall(SYS_gettid));
    return NULL;
}

int main(void)
{
    pthread_t t;
    printf("головний: getpid()=%d  gettid()=%ld\n",
           getpid(), (long)syscall(SYS_gettid));
    pthread_create(&t, NULL, worker, NULL);
    pthread_join(t, NULL);
    return 0;
}
```
```cpp
#include <iostream>
#include <thread>
#include <unistd.h>
#include <sys/syscall.h>

int main()
{
    auto print_ids = [](const char *label) {
        std::cout << label << ": getpid()=" << getpid()
                  << "  gettid()=" << syscall(SYS_gettid) << '\n';
    };

    print_ids("головний");
    std::thread t([print_ids] { print_ids("потік"); });
    t.join();
}
```
:::

Прапорець `CLONE_THREAD` зв'язаний жорстким ланцюгом вимог ядра: `CLONE_THREAD` потребує `CLONE_SIGHAND` (спільна таблиця обробників сигналів), а той вимагає `CLONE_VM` (спільна пам'ять). Обробники сигналів є адресами функцій у пам'яті, тому спільно обробляти сигнали можна лише в єдиному адресному просторі.

Спільна ідентичність дає три головні наслідки:
- **Завершення задачі мовчки.** Коли потік помирає, батьківському процесу не приходить `SIGCHLD`, і `wait()` його не збирає. Батько дізнається про смерть тільки після виходу останнього потоку групи.
- **Спільні рахунки.** Ліміти ресурсів (`RLIMIT_NOFILE`, `RLIMIT_NPROC`) та облік процесорного часу живуть у єдиній структурі `signal_struct`.
- **Спільна смерть.** Системний виклик `exit_group()` (який викликають `exit()` та `_exit()`) завершує всі задачі групи одночасно.

## Що в потоку спільне, а що власне

Модель потоків у Linux базується на чіткому розмежуванні ресурсів між спільною групою та окремою задачею.

**Спільні ресурси групи (через лічильники посилань у ядрі):**
- **Віртуальна пам'ять (`mm_struct`):** глобальні змінні, купа (heap), відображені файли.
- **Файлові дескриптори (`files_struct`):** відкритий у першому потоці файл одразу доступний у другому за тим самим номером.
- **Таблиця обробників сигналів (`sighand_struct`):** реакція на сигнали однакова для всіх.
- **Контекст файлової системи (`fs_struct`):** поточний каталог (`chdir()`) та `umask` змінюються для всієї програми.

**Власні ресурси кожної задачі (всередині `task_struct`):**
- **Регістри процесора та стек ядра (16 КіБ на x86-64):** потрібні для незалежного виконання інструкцій та системних викликів.
- **Стек користувача:** ядро не вміє ростити кілька стеків в одному адресному просторі. Тому стеки потоків виділяє бібліотека (glibc) через `mmap()` фіксованого розміру (типово 8 МіБ згідно з `RLIMIT_STACK`). Знизу кожного стека бібліотека ставить **сторінку-вартового** (`---p` без прав доступу), щоб переповнення стека перетворювалося на негайний збій (`SIGSEGV`), а не псувало чужі дані.
- **Локальні дані потоку (TLS):** змінні `thread_local` та `errno` адресуються через спеціальний регістр процесора (`%fs` на x86-64), який вказує на блок TLS даного потоку.
- **Маска сигналів:** які саме сигнали зараз заблоковано — особиста справа кожного потоку.
- **Параметри планування:** пріоритет (`nice`), політика планувальника та маска дозволених ядер (`sched_setaffinity`) належать задачі.

Слід зважати на розходження між моделлю ядра й стандартом POSIX щодо прав доступу: у ядрі структура `cred` (UID, GID, можливості) належить окремій задачі, а не групі. Щоб дотриматися вимог POSIX, бібліотека glibc при системному виклику `setuid()` надсилає внутрішній зарезервований сигнал (`SIGSETXID`) усім потокам програми, змушуючи кожен потік змінити власні права.

## Сигнали в багатопотоковій програмі

Сигнали в Linux бувають двох типів за адресатом:

1. **Адресовані групі (`kill(pid, sig)`):** ядро кладе сигнал у спільну чергу групи й доправляє його **будь-якому одному потоку**, який не тримає цей сигнал заблокованим у своїй масці.
2. **Адресовані задачі (`pthread_kill()`, `tgkill()`):** сигнал лягає в приватну чергу конкретної задачі й чекає на розмаскування саме в ній.

Синхронні сигнали від помилок процесора (`SIGSEGV`, `SIGFPE`) ядро завжди надсилає тій задачі, чия інструкція схибила. Але оскільки типова диспозиція цих сигналів — завершення, то гине вся група задач. Саме тому падіння одного потоку, для якого програма не поставила власного обробника, валить усю програму.

Надійний спосіб роботи із сигналами в багатопотоковому середовищі — заблокувати потрібні сигнали в усіх потоках до їхнього запуску (маска успадковується при `pthread_create`), після чого обробляти їх в одному виділеному потоці через `sigwaitinfo()` або `signalfd`.

## Створення, вихід і пастка fork()

Створення потоку через `pthread_create()` викликає `clone3()` з набором прапорців `CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD | CLONE_SETTLS`. Операція дешева, бо ядро не копіює таблиці сторінок віртуальної пам'яті й не розставляє позначок для копіювання при записі. Завершені стеки бібліотека кешує й перевикористовує для нових потоків.

Одну задачу завершує системний виклик `exit` — саме до нього зводиться `pthread_exit()`. Якщо головний потік завершується через `pthread_exit()`, решта потоків продовжує працювати, але сам лідер групи залишається в стані зомбі (`Z`), поки живий хоч один потік — його номер `TGID` не можна звільняти, бо він є номером усієї програми.

Найнебезпечніша пастка виникає при виклику `fork()` у багатопотоковій програмі. Системний виклик `fork()` копіює **тільки той потік, який його викликав**. Решта потоків у дитині просто зникає. Якщо один із зниклих потоків у цей момент тримав захоплений м'ютекс (наприклад, усередині `malloc()`), у дитині цей м'ютекс назавжди залишиться заблокованим неіснуючим потоком. Перша ж спроба виділити пам'ять у дитині призведе до вічного зависання (deadlock).

Тому в дитині багатопотокової програми дозволено робити лише асинхронно-сигнально-безпечні виклики та одразу виконувати `execve()`. Частково цю проблему розв'язує `pthread_atfork()`, який дозволяє зареєструвати функції для захоплення м'ютексів перед розгалуженням та їх відпускання після нього в батькові й дитині. Проте це зачіпає лише явні м'ютекси програми, а не сторонні бібліотеки. Надійнішою альтернативою в сучасних програмах є `posix_spawn()`.

## Простеження та діагностика

З'ясувати стан задач програми можна через файлову систему `/proc`:
- `/proc/<pid>/task/` містить підкаталог для кожного `TID` у групі;
- `top -H` показує завантаження процесора окремими потоками;
- `ps -eLf` виводить списки всіх потоків із їхніми LWP (TID).

Питання «а що станеться, якщо…» майже завжди зводиться до одного: де лежить те, про що йдеться. Спільна структура з лічильником посилань — річ спільна на всю програму; поле в `task_struct` — річ окрема в кожної нитки.
