# 📜 Історія еволюції printk: від єдиного спінлока до lockless-буфера

Функція журналювання ядра `printk()` приймає префікс рівня важливості (від аварійного `KERN_EMERG` до відлагоджувального `KERN_DEBUG`, що на текстовій консолі виділяються кольоровими мітками) і записує повідомлення у кільцевий буфер пам'яті. Звідти дані одночасно зчитуються демонами простору користувача та виводяться на фізичні консольні пристрої. Розвиток цієї підсистеми від перших версій Linux до сучасних ядер 6.x випливав із фундаментальної суперечності: гарантувати збереження системних логів під час критичних аварій і водночас не допустити фатальних взаємоблокувань (deadlocks) чи невизначених затримок у системах реального часу.

## Ранні дні: один глобальний замок та статичний буфер

У перших версіях Linux (починаючи з 0.01 та ранніх гілок 1.x/2.x) механізм `printk()` був влаштований гранично просто. Вся система журналювання спиралася на два основних елементи: єдиний статичний символний масив `__log_buf` у пам'яті ядра та глобальний спінлок `logbuf_lock`.

Коли будь-який компонент ядра бажав вивести рядок через `printk()`, алгоритм був лінійним і синхронним:
1. Захопити глобальний замок `logbuf_lock` із відключенням локальних переривань (`spin_lock_irqsave`).
2. Записати байтовий потік форматованого рядка в кільцевий масив `__log_buf`.
3. Не відпускаючи замка, пройтися по списку зареєстрованих консолей (наприклад, драйверу VGA/FB або послідовного порту `ttyS0`) і викликати їхній метод `write()` для негайного друку символів на екран або в дріт.
4. Звільнити спінлок `logbuf_lock` та відновити стан переривань (`spin_unlock_irqrestore`).

На однопроцесорних (UP) системах 1990-х років ця схема працювала бездоганно. Обсяги журналів були невеликими, а швидкість процесорів істотно перевищувала потребу в друку декількох системних повідомлень під час завантаження.

## Ера SMP: криза продуктивності та каскадні взаємоблокування

Із поширенням багатопроцесорних (SMP) систем і багатоядерних архітектур на початку 2000-х років схема з єдиним спінлоком почала руйнуватися. Виявилося три фундаментальні вади синхронного `printk()`:

### 1. Проблема повільних консолей (Serial Console Bottleneck)
Послідовний порт (`ttyS0` / RS-232) традиційно використовується на серверах та в embedded-пристроях для збору логів ядра. Стандартна швидкість передачі становить 115 200 бод (бітів на секунду). Це означає, що відправка одного рядка довжиною в 100 символів займає близько 8.7 мілісекунд.

Якщо потік на Ядрі #0 викликав `printk()` із повідомленням на 100 символів, він тримав `logbuf_lock` усі 8.7 мілісекунд. У цей час Ядра #1, #2, #3, намагаючись зробити будь-який виклики `printk()`, впадали у жорсткий спінінг (spin-wait) на замку. Замість корисної роботи потужні процесори марнували мільйони циклів, очікуючи, поки повільний UART відправить байти.

### 2. Взаємоблокування в контексті переривань (printk Deadlocks)
Найбільш фатальні збої виникали, коли `printk()` викликався з різних контекстів виконання:
- Потік процесів ядра захоплює `logbuf_lock`.
- У цей момент на цьому ж процесорі виникає апаратне переривання (HardIRQ) або немасковане переривання (NMI — Non-Maskable Interrupt).
- Обробник NMI намагається вивести діагностичне повідомлення й викликає `printk()`.
- Оскільки NMI не може бути заблокований і виконується на тому самому процесорі, він намагається захопити `logbuf_lock`, який вже утримається перерваним потоком.
- Виникає класичне самовзаємоблокування (self-deadlock): процесор назавжди зависає у нескінченному циклі спінінгу.

### 3. Проблема рекурсивного printk
Якщо під час виконання самого коду `printk()` (або внутрішніх процедур драйвера консолі) траплялася помилка (наприклад, звернення за невалідним вказівником чи зауваження від підсистеми перевірки блокувань Lockdep), ядро намагалося сповістити про це… через ще один виклик `printk()`. Це спричиняло нескінченну рекурсію, переповнення стека та миттєве падіння системи.

## Натиск PREEMPT_RT та пошук альтернатив

Розвиток патчсета реального часу (PREEMPT_RT) висунув до ядра Linux жорстку вимогу: визначена детермінована затримка (bounded latency). У системах реального часу жодна операція не повинна блокувати виконання високопріоритетного потоку на невизначений час.

Класичний `printk()` порушував правила PREEMPT_RT фундаментально:
- Виклик `printk()` із критичного потоку міг заблокуватися на спінлоці через те, що фоновий потік із низьким пріоритетом саме друкував довгий текст у послідовний порт.
- Драйвери консолей виконували вивід із вимкненими перериваннями, що призводило до неприпустимих піків затримки (latency spikes) у десятки мілісекунд.

Протягом багатьох років розробники ядра намагалися залатати цю проблему тимчасовими заходами:
- **Передача відповідальності (Console Handover):** потік, який захопив спінлок, намагався передати обов'язок виводу на консоль іншому процесору, якщо той теж кликав `printk()`. Це дещо зменшувало затримки, але ускладнило код до нечитабельності.
- **Буфери NMI (nmi_printk):** для немаскованих переривань виділили окремі пер-процесорні буфери, з яких дані переливалися в основний буфер пізніше. Це вирішило частину взаємоблокувань, але роздробило систему логування.

Потрібне було радикальне переосмислення: відокремити збереження повідомлення в буфер від його фактичного виводу на пристрої.

## Революція Джон Огнесса: Lockless Ringbuffer (Linux 5.10+)

У 2018–2020 роках розробник ядра Джон Огнесс (John Ogness) запропонував кардинально нову архітектуру `printk`, яка увійшла в ядро Linux починаючи з версії 5.10.

Головна ідея нової архітектури — повністю вилучити спінлок `logbuf_lock` із гарячого шляху запису повідомлення.

### Двокільцева lockless-структура (PRDB)
Новий буфер логів `printk_ringbuffer` складається з двох пов'язаних кільцевих буферів, маніпуляції з якими виконуються виключно за допомогою атомарних операцій (Atomic Compare-And-Swap, `atomic_cmpxchg`):

1. **Буфер дескрипторів (Descriptor Ring):** масив структур фіксованого розміру `struct prb_desc`. Кожен дескриптор містить метадані (послідовний номер `seq`, мітку часу, рівень важливості, ID процесора й потоку, а також стан запису — *reserved*, *committed*, *finalized*).
2. **Буфер даних (Data Ring):** безструктурний масив байтів, у якому зберігається безпосередній текст повідомлень.

```
+-------------------------------------------------------------------+
|                     printk_ringbuffer (PRDB)                      |
|                                                                   |
|  [Буфер дескрипторів]                                             |
|  +--------------+--------------+--------------+-----------------+ |
|  | Desc 1 (seq) | Desc 2 (seq) | Desc 3 (seq) | Desc 4 (free)   | |
|  +------+-------+------+-------+------+-------+-----------------+ |
|         |              |              |                           |
|         v              v              v                           |
|  [Буфер даних]                                                    |
|  +--------------------------------------------------------------+ |
|  | "eth0: link down\0" | "nvme0: timeout\0" | "CPU2: kworker\0" | |
|  +--------------------------------------------------------------+ |
+-------------------------------------------------------------------+
```

Коли потік чи обробник переривання викликає `printk()`:
1. За допомогою атомарної операції резервується дескриптор у буфері дескрипторів (`prb_reserve`).
2. Атомарно виділяється необхідний обсяг байтів у буфері даних.
3. Текст копіюється в виділену ділянку пам'яті.
4. Запис атомарно помічається як завершений (`prb_commit`).

Ця операція виконується за фіксований час `O(1)` і **ніколи не блокується**. Навіть якщо 64 процесори одночасно викликають `printk()`, вони не заважають один одному: кожен атомарно зсуває вказівники та пише у власну ділянку буфера.

## Майбутнє: non-blocking consoles (nbcon)

Завдяки беззамокному буферу запис у журнал став безпечним і швидким. Останнім етапом еволюції (що розгортається в ядрах гілки 6.x) є впровадження **інфраструктури atomic/non-blocking consoles (`nbcon`)**.

У новій системі кожен консольний драйвер має власний фоновий потік (kthread). Ці потоки зчитують записи з локлес-буфера й повільно виводять їх на пристрої у просторі користувача, не затримуючи процесори, які виконують основну роботу ядра. 

У випадку ж катастрофічного збою (Kernel Panic або NMI) система `nbcon` дає змогу аварійному процесору безпечно «перехопити» (takeover) консоль і синхронно видрукувати останні секунди життя системи, гарантуючи, що жоден лог не втратиться.
