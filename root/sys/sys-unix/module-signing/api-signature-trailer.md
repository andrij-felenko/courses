# 📋 Контракт підпису модуля: хвіст файлу, параметри збирання, коди відмови

Це довідка точних форм: скільки байтів займає кожна частина хвоста `.ko`, як звуться параметри збирання, якою командою накладають підпис, що про нього показує `modinfo` і що означає кожен код, яким ядро відмовляє. Усе перевірено за поточним деревом ядра — імена й числа тут такі, що їх можна набирати не переказуючи.

## Хвіст файлу

Ядро читає хвіст із кінця, бо початку хвоста не знає наперед. Порядок читання — знизу вгору по таблиці.

| зміщення від кінця | розмір, байтів | вміст |
|---|---|---|
| −28 | 28 | маркер `~Module signature appended~\n` |
| −40 | 12 | `struct module_signature` |
| −40 − `sig_len` | `sig_len` | повідомлення PKCS#7 у кодуванні DER |
| 0 | решта | тіло модуля — рівно ті байти, що під хешем |

Опис підпису лежить у `include/uapi/linux/module_signature.h` і має сталий розмір 12 байтів:

```c
struct module_signature {
	__u8	algo;		/* алгоритм відкритого ключа [0] */
	__u8	hash;		/* алгоритм хешування [0] */
	__u8	id_type;	/* тип ідентифікації ключа [MODULE_SIGNATURE_TYPE_PKCS7] */
	__u8	signer_len;	/* довжина імені підписанта [0] */
	__u8	key_id_len;	/* довжина ідентифікатора ключа [0] */
	__u8	__pad[3];
	__be32	sig_len;	/* довжина підпису */
};
```

Значуще поле тут одне — `sig_len`, і воно в мережевому порядку байтів (`__be32`), а не в порядку машини. `id_type` мусить дорівнювати `MODULE_SIGNATURE_TYPE_PKCS7`, тобто **2**. Решта семи байтів (`algo`, `hash`, `signer_len`, `key_id_len` і три байти набивки) мусять бути нулями: у нинішньому форматі і алгоритм, і ім'я підписанта живуть усередині самого PKCS#7, а ненульове значення означало б розкладку, якої це ядро вже не розуміє.

**Модуль розміром F байтів.**

```
тіло під хешем  =  F − 28 − 12 − sig_len
```

Дві умови цілості ядро перевіряє до будь-якої криптографії:

```
F − 28 >  12                    інакше −EBADMSG (файл коротший за опис)
sig_len < F − 28 − 12           інакше −EBADMSG (підпис не влазить у файл)
```

## Параметри збирання

Механізм і політика — у `kernel/module/Kconfig`:

| параметр | тип | що робить |
|---|---|---|
| `CONFIG_MODULE_SIG` | bool | вмикає перевірку взагалі; без нього ядро хвоста не помічає |
| `CONFIG_MODULE_SIG_FORCE` | bool | примус, зашитий в образ: м'які невдачі стають відмовою |
| `CONFIG_MODULE_SIG_ALL` | bool, типово `y` | підписати всі модулі під час `make modules_install` |

Ключ і алгоритм — у `certs/Kconfig`:

| параметр | тип | що робить |
|---|---|---|
| `CONFIG_MODULE_SIG_KEY` | string, типово `certs/signing_key.pem` | файл PEM, що містить і приватний ключ, і сертифікат, **або** URI PKCS#11 за RFC 7512 |
| `KBUILD_SIGN_PIN` | змінна оточення | пароль до зашифрованого PEM або PIN до токена PKCS#11 |
| `CONFIG_MODULE_SIG_KEY_TYPE_RSA` / `_ECDSA` | choice | тип пари, яку збірка згенерує сама, якщо файла за `MODULE_SIG_KEY` немає |
| `CONFIG_MODULE_SIG_SHA256` / `_SHA384` / `_SHA512` / `_SHA3_256` / `_SHA3_384` / `_SHA3_512` | choice, типово `SHA512` | хеш під підписом |
| `CONFIG_MODULE_SIG_HASH` | string | назва обраного хешу; саме її бере `make modules_install` |

Варіантів SHA-1 і SHA-224 у сучасному дереві вже немає — їх прибрали разом із рештою підписів на застарілих хешах.

> 🔧 **Навіщо це.** Обраний хеш мусить бути **вкомпільований** у ядро, а не зібраний модулем: щоб перевірити підпис модуля, ядру потрібен алгоритм, а щоб дістати алгоритм із модуля, треба спершу перевірити підпис того модуля. Тому вибір у `choice` заразом робить `select CRYPTO_SHA512` і подібні. [Криптографічна підсистема ядра](topic:sys-unix/kernel-crypto-api) називає алгоритми рядками на кшталт `sha512` і вміє мати кілька реалізацій одного імені — але вбудованою мусить бути хоча б одна.

Кільця ключів — теж `certs/Kconfig` і `security/integrity/Kconfig`:

| параметр | кільце чи дія |
|---|---|
| `CONFIG_SYSTEM_TRUSTED_KEYRING` | заводить `.builtin_trusted_keys` |
| `CONFIG_SYSTEM_TRUSTED_KEYS` | string: шлях до PEM із додатковими сертифікатами, які вкомпілюють в образ |
| `CONFIG_SYSTEM_EXTRA_CERTIFICATE` (+ `_SIZE`, типово 4096) | резервує місце в образі, щоб сертифікат вставити вже після збирання |
| `CONFIG_SECONDARY_TRUSTED_KEYRING` | заводить `.secondary_trusted_keys` |
| `CONFIG_INTEGRITY_MACHINE_KEYRING` | заводить `.machine`; вимагає `SECONDARY_TRUSTED_KEYRING`, `SYSTEM_BLACKLIST_KEYRING`, `INTEGRITY_ASYMMETRIC_KEYS` і `LOAD_UEFI_KEYS` або `LOAD_PPC_KEYS` |
| `CONFIG_INTEGRITY_CA_MACHINE_KEYRING` | у `.machine` беруть лише сертифікати центрів сертифікації |
| `CONFIG_INTEGRITY_CA_MACHINE_KEYRING_MAX` | звужує ще: обов'язкові `CA:TRUE` і `keyCertSign`, а сертифікати з `digitalSignature` відкидають |
| `CONFIG_SYSTEM_BLACKLIST_KEYRING` | заводить `.blacklist` |
| `CONFIG_SYSTEM_BLACKLIST_HASH_LIST` | string: файл із хешами, які вбудують в образ як заборонені |
| `CONFIG_SYSTEM_REVOCATION_LIST` / `_KEYS` | відкликані ключі, вбудовані в образ |

Що це за кільця й за якими правилами до них щось потрапляє на ходу — у [кільцях ключів ядра](topic:sys-unix/kernel-keyrings): ядро тримає ключі у власних іменованих сховищах, кожне зі своїм правилом прийому, і сторонній процес бачить їх лише через `keyctl`.

## Накладання підпису

```
scripts/sign-file [-dp] <хеш> <ключ> <сертифікат> <модуль.ko> [<результат>]
scripts/sign-file -s <готовий-підпис> <хеш> <сертифікат> <модуль.ko> [<результат>]
```

Без `<результат>` файл переписують на місці — хвіст дописують у кінець.

| ключ | дія |
|---|---|
| `-p` | додатково зберегти повідомлення PKCS#7 у `<модуль.ko>.p7s` |
| `-d` | лише підписати: записати `.p7s` і не чіпати сам модуль |
| `-s` | підпис уже зроблено деінде (наприклад, апаратним модулем); першим аргументом іде файл із сирими байтами підпису, приватний ключ не потрібен |
| `-k` | у повідомленні CMS назвати підписанта ідентифікатором ключа замість пари «видавець + серійний номер» |

Найкоротший робочий шлях від нуля до підписаного модуля:

```bash
# 1. пара ключів і самопідписаний сертифікат ЦС (для .machine потрібен саме ЦС)
openssl req -new -x509 -newkey rsa:4096 -nodes -days 36500 \
    -subj "/CN=Module signing key/" \
    -addext "basicConstraints=critical,CA:TRUE" \
    -addext "keyUsage=critical,keyCertSign" \
    -keyout MOK.priv -out MOK.pem

# 2. форма DER — саме її приймає mokutil
openssl x509 -in MOK.pem -outform DER -out MOK.der

# 3. підпис; назва хешу мусить збігтися з вбудованим у це ядро
/usr/src/linux-headers-$(uname -r)/scripts/sign-file sha512 \
    MOK.priv MOK.pem ./mydriver.ko
```

Підпис накладають **останнім**. Будь-яке дальше перетворення файлу — `strip`, `objcopy`, стиснення — або зриває хвіст, або лишає його не відповідним тілу.

## Що показує `modinfo`

П'ять полів; усі п'ять `kmod` розбирає з самого повідомлення PKCS#7, а не з 12-байтового опису, де вони нулі.

| поле | вміст |
|---|---|
| `sig_id` | тип ідентифікації — для нинішнього формату завжди `PKCS#7` |
| `signer` | ім'я підписанта, взяте з сертифіката |
| `sig_key` | ідентифікатор ключа або серійний номер, шістнадцятковими парами через двокрапку |
| `sig_hashalgo` | назва хешу: `sha256`, `sha512`, `sm3` тощо |
| `signature` | самі байти підпису |

```
$ modinfo ./mydriver.ko | tail -5
sig_id:         PKCS#7
signer:         Module signing key
sig_key:        3A:9F:...:C1
sig_hashalgo:   sha512
signature:      30:82:01:D6:06:09:2A:86:...
```

У непідписаного модуля цих рядків просто немає — окремої ознаки «не підписано» не існує. Одне поле дістають ключем `-F`: `modinfo -F sig_hashalgo ./mydriver.ko`.

## Важелі часу виконання

| важіль | коли діє | особливість |
|---|---|---|
| `CONFIG_MODULE_SIG_FORCE` | зашито при збиранні | зняти нічим |
| `module.sig_enforce=1` | [командний рядок ядра](topic:sys-unix/bootloader-and-cmdline) — рядок параметрів, який завантажувач передає ядру на старті | діє від самого початку завантаження |
| `/sys/module/module/parameters/sig_enforce` | на працюючій системі, права `0644` | лише перехід 0→1; запис `0` після одиниці повертає `-EROFS` |
| режим блокування | LSM | у варіантах `integrity` і `confidentiality` підпис вимагається незалежно від `sig_enforce` |
| `/proc/sys/kernel/tainted` | читання | біт 13, вага 8192, літера `E` — «завантажено непідписаний модуль» |

Односторонність третього рядка не політика адміністратора, а тип параметра: він оголошений через `param_set_bool_enable_only`, і саме там стоїть перевірка «не давати зняти те, що вже стоїть». [Режим блокування ядра](topic:sys-unix/kernel-lockdown) закриває всі шляхи, якими root міг би дістатися до пам'яті ядра, тож на дистрибутивному ядрі примус часто діє й тоді, коли `sig_enforce` показує нуль. Що ще піднімає [прапорці заплямованості](topic:sys-unix/kernel-taint) і як їх читати числом — окремо.

## Коди відмови

Три невдачі м'які: вони означають «зарахувати файл до довіреного не вдалося», і чи це причина відмовити — вирішує режим примусу. Дві тверді відхиляють завжди.

| код | коли | твердість |
|---|---|---|
| `-ENODATA` | маркера в кінці немає; або образ подали з проханням не звіряти `vermagic`/версії символів | м'яка |
| `-ENOPKG` | `id_type` ≠ 2; або потрібного алгоритму немає в цьому ядрі | м'яка |
| `-ENOKEY` | сертифіката підписанта немає в кільцях, які питає перевірка | м'яка |
| `-EBADMSG` | файл коротший за опис; `sig_len` не влазить; ненульові поля опису; нерозбірливий DER | тверда |
| `-EKEYREJECTED` | хеш не збігся з підписом; **або** будь-яка м'яка невдача за ввімкненого примусу | тверда |

Рядки в журналі, за якими ці коди впізнають:

```
module: not signed with expected PKCS#7 message              → −ENOPKG
module: PKCS#7 signature info has unexpected non-zero params → −EBADMSG

Loading of unsigned module is rejected                       → примус, −ENODATA
Loading of module with unsupported crypto is rejected        → примус, −ENOPKG
Loading of module with unavailable key is rejected           → примус, −ENOKEY

<назва>: module verification failed: signature and/or
required key missing - tainting kernel                       → без примусу, м'яка
```

Останній рядок друкують один раз за час роботи системи (`pr_notice_once`), тож другий непідписаний модуль мовчки додасть той самий прапорець без нового запису в журналі.

Те, що бачить користувач, — це вже переклад коду на текст стандартною бібліотекою:

| код | текст `insmod`/`modprobe` |
|---|---|
| `-ENODATA` | `No data available` |
| `-ENOPKG` | `Package not installed` |
| `-ENOKEY` | `Required key not available` |
| `-EBADMSG` | `Bad message` |
| `-EKEYREJECTED` | `Key was rejected by service` |
