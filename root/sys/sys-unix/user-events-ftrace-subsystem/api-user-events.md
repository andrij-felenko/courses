# 📋 Інтерфейс ABI підсистеми User Events: ioctl, mmap та формат даних

Ця вставка є вичерпною технічною довідкою двійкового інтерфейсу прикладного програмування (ABI) підсистеми User Events ядра Linux. У ній детально розібрано системні константи, структури даних мовами C та C++, протоколи викликів `ioctl`, формат організації сторінки статусу в спільній пам'яті (`mmap`), правила бінарного кодування полів у пакунках даних (`writev`), а також вичерпну таблицю кодів помилок системних викликів та системних параметрів `sysctl`.

## 1. Заголовний файл, файлові шляхи та доступи

Для взаємодії з підсистемою User Events у системі Linux виділено спеціалізований віртуальний файловий об'єкт у складі файлової системи `tracefs`:

- **Основний шлях до файлу пристрою:** `/sys/kernel/tracing/user_events_data` (або за застарілим символьним посиланням `/sys/tracing/user_events_data`).
- **Файл відображення статусу (Legacy):** `/sys/kernel/tracing/user_events_status`.
- **Каталог зареєстрованих подій:** `/sys/kernel/tracing/events/user_events/`.
- **Заголовний файл ядра:** `<linux/user_events.h>`.

Якщо середовище розробки або дистрибутив містить застарілі заголовки ядра (раніші за версію Linux 5.18), розробник має можливість самостійно визначити необхідні константи та структури у власному вихідному коді, оскільки ABI ядра Linux зберігає сувору зворотно-бінарну сумісність.

Для відкриття файла `/sys/kernel/tracing/user_events_data` програма повинна мати відповідні привілеї доступу. За замовчуванням файл доступний лише користувачу `root`. Надання доступу звичайним користувачам здійснюється налаштуванням прав файлової системи або наданням процесу POSIX-капабіліті `CAP_PERFMON` чи `CAP_SYS_ADMIN`.

## 2. Команди ioctl та структура реєстрації user_reg

Управління життєвим циклом користувацьких подій (створення, налаштування та видалення) здійснюється через системний виклик `ioctl()`, що виконується над відкритим файловим дескриптором `/sys/kernel/tracing/user_events_data`.

### Системні константи керування ioctl

Усі управляючі команди підсистеми User Events кодуються за допомогою стандартизованих макросів ядра Linux `<sys/ioctl.h>` з використанням магічного байта `DIAG_IOC_MAGIC` (`0x82`):

| Константа | Магічний код | Напрямок даних | Опис та призначення |
| :--- | :--- | :--- | :--- |
| `DIAG_IOC_MAGIC` | `0x82` | — | Магічний ідентифікатор підсистеми user_events |
| `DIAG_IOCSREG` | `_IOWR(0x82, 0, struct user_reg)` | Читання та запис (`_IOWR`) | Реєстрація нової події або запит індексів наявної |
| `DIAG_IOCSDEL` | `_IOW(0x82, 1, char*)` | Запис (`_IOW`) | Динамічне видалення зареєстрованої події за іменем |

### Структура реєстрації `struct user_reg`

Під час виконання керуючого виклику `DIAG_IOCSREG` прикладний застосунок заповнює і передає за вказівником структуру `struct user_reg`. Ядро перевіряє передані параметри, створює відповідні внутрішні об'єкти `tracepoint` і повертає заповнену структуру з розрахованими індексами.

:::tabs
```c
#include <linux/types.h>
#include <linux/ioctl.h>

#ifndef DIAG_IOCSREG
#define DIAG_IOC_MAGIC 0x82
#define DIAG_IOCSREG _IOWR(DIAG_IOC_MAGIC, 0, struct user_reg)
#define DIAG_IOCSDEL _IOW(DIAG_IOC_MAGIC, 1, char*)
#endif

struct user_reg {
    __u32 size;            /* [IN]  Розмір структури в байтах: sizeof(struct user_reg) */
    __u8  enable_bit;      /* [OUT] Порядковий номер біта у байті статусу (зазвичай 0) */
    __u8  enable_size;     /* [OUT] Розмір поля статусу в байтах (1, 2 або 4) */
    __u16 flags;           /* [IN]  Прапорці конфігурації реєстрації (за замовчуванням 0) */
    __u64 name_args;       /* [IN]  Вказівник на нуль-термінований C-рядок специфікації */
    __u32 status_index;    /* [OUT] Зсув у байтах у mmap-сторінці статусу */
    __u32 write_index;     /* [OUT] 32-бітний ID події для перших 4 байтів writev() */
};
```
```cpp
#include <cstdint>
#include <sys/ioctl.h>

#ifndef DIAG_IOCSREG
#define DIAG_IOC_MAGIC 0x82
#define DIAG_IOCSREG _IOWR(DIAG_IOC_MAGIC, 0, struct user_reg)
#define DIAG_IOCSDEL _IOW(DIAG_IOC_MAGIC, 1, char*)
#endif

struct user_reg {
    std::uint32_t size;            // [IN]  Розмір структури sizeof(user_reg)
    std::uint8_t  enable_bit;      // [OUT] Номер біта в байті статусу
    std::uint8_t  enable_size;     // [OUT] Розмір поля статусу в байтах
    std::uint16_t flags;           // [IN]  Прапорці конфігурації реєстрації
    std::uint64_t name_args;       // [IN]  Вказівник на рядок специфікації події
    std::uint32_t status_index;    // [OUT] Зсув у байтах у mmap-масиві статусу
    std::uint32_t write_index;     // [OUT] 32-бітний ID події для заголовка writev()
};
```
:::

### Детальний аналіз полів structures `user_reg`

- **`size` (Вхідне поле):** Застосунок обов'язково повинен встановити `reg.size = sizeof(struct user_reg)`. Це поле використовується ядром Linux для забезпечення зворотної та форвардної сумісності ABI: якщо у майбутніх версіях ядра структура буде розширена новими полями, ядро визначатиме версію клієнтської програми за цим розміром.
- **`enable_bit` (Вихідне поле):** Номер біта всередині байта статусу. Для перших версій підсистеми це значення зазвичай дорівнює `0`, а сам байт повністю використовується як прапорець активності.
- **`enable_size` (Вихідне поле):** Розмір елемента статусу у сторінці пам'яті у байтах (найчастіше дорівнює `1`).
- **`flags` (Вхідне поле):** Бітова маска прапорців конфігурації. Включає додаткові режими роботи, такі як `USER_EVENT_REG_PERSIST` (збереження події у ядрі навіть після закриття файлового дескриптора програмою).
- **`name_args` (Вхідне поле):** 64-бітне ціле число, у яке приводиться вказівник (`uintptr_t`) на C-рядок у пам'яті користувача. Рядок містить назву події та оголошення її типізованих полів.
- **`status_index` (Вихідне поле):** Порядковий зсув у байтах від початку сторінки спільної пам'яті (`mmap`), за яким прикладний застосунок повинен зчитувати поточний стан активності цієї події.
- **`write_index` (Вихідне поле):** Унікальний 32-бітний ідентифікатор події у контексті поточного відкритого файлового дескриптора. Значення цього поля програма повинна записувати у перші 4 байти вектора `writev()` при кожній генеруванні події.

## 3. Синтаксис опису полів та типізація (name_args)

Рядок специфікації, на який вказує `name_args`, визначає ім'я події та бінарний формат полів:

```text
назва_події [тип_поля1 ім'я_поля1; тип_поля2 ім'я_поля2; ...]
```

Назва події має відповідати правилам іменування ідентифікаторів у C (дозволено букви, цифри та символ підкреслення). Назва не повинна конфліктувати з існуючими системними tracepoints ядра.

### Таблиця підтримуваних скалярних типів даних

Ядро Linux парсить рядок специфікації та відображає його на внутрішні скалярні типи даних ядра:

| Тип у специфікації | Відповідний тип C/C++ | Розмір | Діапазон значень / Опис |
| :--- | :--- | :--- | :--- |
| `u8` / `char` | `uint8_t` / `unsigned char` | 1 байт | 0 … 255 |
| `s8` | `int8_t` / `signed char` | 1 байт | -128 … 127 |
| `u16` / `short` | `uint16_t` / `unsigned short`| 2 байти | 0 … 65 535 |
| `s16` | `int16_t` / `short` | 2 байти | -32 768 … 32 767 |
| `u32` / `int` | `uint32_t` / `unsigned int` | 4 байти | 0 … 4 294 967 295 |
| `s32` | `int32_t` / `int` | 4 байти | -2 147 483 648 … 2 147 483 647 |
| `u64` / `long long` | `uint64_t` / `unsigned long long`| 8 байтів | 0 … 18 446 744 073 709 551 615 |
| `s64` | `int64_t` / `long long` | 8 байтів | -9.22e18 … 9.22e18 |
| `char[N]` | `char[N]` | N байтів | Фіксований рядок символів завдовжки N байтів |
| `u8[N]` | `uint8_t[N]` | N байтів | Фіксований бінарний масив байтів завдовжки N |

### Динамічні типи даних змінної довжини (`__data_loc`)

Для передачі рядків або бінарних масивів змінної довжини використовується модифікатор `__data_loc`:

- `__data_loc char[] field_name` — динамічний текстовий рядок.
- `__data_loc u8[] field_name` — динамічний бінарний масив.

При використанні `__data_loc` у фіксованій частині структури під поле виділяється **4 байти** (32-бітний локатор `u32 loc`), який описує розташування даних у хвості пакета:

```
+--------------------------------+--------------------------------+
|  Довжина даних (len, 16 біт)   | Зсув від початку (off, 16 біт) |
+--------------------------------+--------------------------------+
 31                            16 15                             0
```

Для обчислення значення `loc` у коді C/C++ застосовується макрос:

:::tabs
```c
#define USER_EVENT_LOC(offset, len) (((uint32_t)(len) << 16) | ((uint32_t)(offset) & 0xFFFF))
```
```cpp
constexpr std::uint32_t user_event_loc(std::uint16_t offset, std::uint16_t len) noexcept {
    return (static_cast<std::uint32_t>(len) << 16) | (static_cast<std::uint32_t>(offset) & 0xFFFF);
}
```

## 4. Спільна пам'ять статусу через mmap()

Для забезпечення перевірки стану активності події з нульовими витратами процесорного часу прикладний застосунок виконує системний виклик `mmap()` безпосередньо на відкритий файловий дескриптор `/sys/kernel/tracing/user_events_data`.

:::tabs
```c
#include <sys/mman.h>
#include <unistd.h>
#include <stdio.h>

/* Отримання точного розміру системної сторінки пам'яті */
size_t page_size = (size_t)sysconf(_SC_PAGESIZE);

/* Отображення сторінки статусу у режим PROT_READ */
char *status_map = (char *)mmap(NULL, page_size, PROT_READ, MAP_SHARED, fd, 0);

if (status_map == MAP_FAILED) {
    perror("Помилка виконання mmap на user_events_data");
    /* Обробка помилки */
}

/* Інлайн-функція для перевірки стану в гарячому циклі */
static inline int is_user_event_enabled(const char *map, uint32_t index) {
    return map[index] != 0;
}
```
```cpp
#include <sys/mman.h>
#include <unistd.h>
#include <system_error>
#include <cstdint>

class UserEventsMemoryMap {
    char* status_map_{static_cast<char*>(MAP_FAILED)};
    std::size_t page_size_{0};

public:
    explicit UserEventsMemoryMap(int fd) {
        page_size_ = static_cast<std::size_t>(::sysconf(_SC_PAGESIZE));
        void* ptr = ::mmap(nullptr, page_size_, PROT_READ, MAP_SHARED, fd, 0);
        if (ptr == MAP_FAILED) {
            throw std::system_error(errno, std::generic_category(), "Не вдалося виконати mmap статусу");
        }
        status_map_ = static_cast<char*>(ptr);
    }

    ~UserEventsMemoryMap() noexcept {
        if (status_map_ != MAP_FAILED) {
            ::munmap(status_map_, page_size_);
        }
    }

    [[nodiscard]] inline bool is_enabled(std::uint32_t status_index) const noexcept {
        return status_map_[status_index] != 0;
    }
};
```
:::

Коли трасування події вимкнено у ftrace, відповідний байт `status_map[status_index]` містить `0`. Оскільки пам'ять відображена у простір процесу, зчитування значення виконується з кешу L1 без виконання системних викликів.

## 5. Двійкове кодування вектора writev()

Генерація події виконується векторним викликом `writev(fd, iov, count)`. Загальна схема вектора `iovec` виглядає так:

```text
iovec[0]: [ write_index (4 байти, u32) ]
iovec[1]: [ Фіксована структура полів (скаляри + __data_loc локатори) ]
iovec[2]: [ Динамічні буфери даних (рядки/масиви) ]
```

### Приклад розкладки полів у пам'яті з урахуванням вирівнювання (Alignment)

Для специфікації `"http_request u32 status_code; u64 latency_ns; __data_loc char[] url"` фіксована частина у `iovec[1]` повинна дотримуватися вимог вирівнювання полів процесора (компілятор зазвичай додає `padding` перед 64-бітними цілими числами):

```text
Зсув у байтах  Розмір  Назва поля        Опис
-----------------------------------------------------------------------------------
0x00           4 байти status_code       u32 значення (наприклад, 200)
0x04           4 байти [padding]         Заповнення для вирівнювання u64 за адресою /8
0x08           8 байтів latency_ns        u64 значення у наносекундах
0x10           4 байти url_loc           u32 локатор (offset=20, len=18)
0x14           18 байт url_data          Символи рядка "/api/v1/checkout\0" у iovec[2]
```

## 6. Таблиця кодів помилок системних викликів (errno)

Під час виконання системних викликів `ioctl()` або `writev()` ядро Linux може повертати значення `-1` та встановлювати наступні коди у системній змінній `errno`:

| Код помилки | Системна назва | Основна причина виникнення у User Events |
| :--- | :--- | :--- |
| `EPERM` / `EACCES` | Permission denied | Відсутні права доступу до `/sys/kernel/tracing/user_events_data`. Необхідно мати права root або капсулу `CAP_PERFMON`. |
| `EINVAL` | Invalid argument | Передано неприпустимий розмір `struct user_reg`, синтаксичну помилку у рядку полів, або некоректний `write_index` у `writev()`. |
| `E2BIG` | Argument list too long | Рядок специфікації події перевищує розмір сторінки пам'яті (4096 байтів), або розмір payload у `writev()` перевищує 64 КБ. |
| `EBUSY` | Device or resource busy | Спроба зареєструвати подію з ім'ям, яке вже існує в ядрі, але має іншу бінарну конфігурацію полів. |
| `ENOSPC` | No space left on device | Перевищено системний ліміт кількості зареєстрованих подій у ядрі (параметр `user_events_max`). |
| `EFAULT` | Bad address | Передано невалідний вказівник у користувацькій пам'яті для `name_args` або масиву `iovec`. |
| `ENOMEM` | Out of memory | У ядрі недостатньо вільної пам'яті для виділення внутрішніх структур `tracepoint` та об'єктів `tracefs`. |

## 7. Системні параметри конфігурації sysctl

Глобальні ліміти підсистеми User Events контролюються через інтерфейс `sysctl` у віртуальній файловій системі `/proc`:

- **`/proc/sys/kernel/user_events_max`:** Максимальна кількість подій користувача, яка може бути одночасно зареєстрована у ядрі для всіх процесів системи. Значення за замовчуванням становить `32768`. Системний адміністратор може збільшити це значення за допомогою команди:

```bash
sudo sysctl -w kernel.user_events_max=65536
```
