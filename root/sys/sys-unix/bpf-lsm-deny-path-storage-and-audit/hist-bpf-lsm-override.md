# 📜 Від kprobe error injection до BPF LSM: еволюція перехоплення та перевизначення у ядрі Linux

Вставка описує детальний історичний шлях розробки та становлення механізмів модифікації поведінки ядра Linux — від ранніх спроб ін'єктування помилок через kprobes та ftrace до сучасної безпечної архітектури BPF LSM у складі фреймворку Linux Security Modules.

## Передісторія: Проблема вибіркового контролю та поява LSM (2001 рік)

У 1990-х роках єдиним механізмом розмежування прав у Linux залишався вибірковий контроль доступу (DAC — Discretionary Access Control), який спирався на ідентифікатори користувачів (UID), груп (GID) та три групи бітів дозволів `rwxrwxrwx`. Зі зростанням популярності Linux у серверних середовищах виявилося, що компрометація єдиного процесу, який працює від імені суперкористувача `root` (UID 0), дає зловмиснику необмежений контроль над усією операційною системою.

Для вирішення цієї проблеми Агентство національної безпеки США (NSA) та розробники Linux почали обговорення мандатного контролю доступу (MAC). На саміті Linux Kernel Summit 2001 року Лінус Торвальдс відхилив включення конкретної реалізації SELinux безпосередньо у вихідний код ядра, заявивши, що ядро не повинно віддавати перевагу одній моделі безпеки. Натомість було вирішено створити універсальний фреймворк — Linux Security Modules (LSM).

Фреймворк LSM надав ядру набір точок контролю (LSM hooks), розміщених у критичних місцях системних викликів VFS, підсистеми процесів та мережевого стеку. Перші модулі (SELinux, AppArmor, Smack, TOMOYO) реалізовували свої політики як статичні C-структури, компільовані разом із ядром або завантажувані у вигляді модулів ядра.

Проте статичність LSM виявилася важким тягарем. Будь-яка зміна правил вимагала або перекомпіляції бінарних профілів, або складного перейменування типів SELinux. Коли у 2010-х роках почалася ера контейнеризації та мікросервісів, виникла потреба у динамічному контролі доступу, який міг би змінювати правила на льоту без перезавантаження демонів безпеки.

## Перші спроби перехоплення: Kprobes, Ftrace та `bpf_override_return()`

Паралельно з розвитком LSM у ядрі Linux формувалася підсистема трасування eBPF. Починаючи з версії Linux 3.18, eBPF дозволяв завантажувати безпечні програми для моніторингу мережевих пакетів та аналізу продуктивності. Інженери з безпеки швидко помітили можливість підключати BPF-програми типу `BPF_PROG_TYPE_KPROBE` до внутрішніх функцій ядра за допомогою інфраструктури kprobes.

Kprobes дозволяли вставити точку зупинки (інструкцію `int3` на x86_64) у будь-яку точку ядра. Якщо BPF-програма підключалася до kprobe, вона могла зчитувати аргументи функції та записувати трасувальні логи. Але для повноцінного захисту цього було замало: трасувальні BPF-програми не могли зупинити виконання системного виклику або змінити результат перевірки.

У випуску Linux 4.16 (квітень 2018 року) розробник Джозеф Бачик (Josef Bacik) додав до BPF новий хелпер: `bpf_override_return()` — доступний лише у збірках із `CONFIG_BPF_KPROBE_OVERRIDE`.

```c
// Сигнатура хелпера у ядрі Linux 4.16
long bpf_override_return(struct pt_regs *regs, unsigned long rc);
```

Механізм роботи `bpf_override_return()` був агресивним та прямолінійним:
1. BPF-програма перехоплювала вхід у функцію ядра через `kprobe`.
2. За допомогою `bpf_override_return()` програма змінювала значення у регістрі повернення результату процесора (наприклад, `%rax` на архітектурі x86_64).
3. Хелпер змінював лічильник інструкцій (Instruction Pointer `%rip`), змушуючи процесор негайно перестрибнути через тіло функції безпосередньо на інструкцію повернення `ret`.

Первісною метою `bpf_override_return()` була відлагоджувальна симуляція відмов (*fault injection*). Тест-інженери хотіли перевірити, як файлові системи (btrfs, ext4, xfs) обробляють брак пам'яті або відмови дискового читання, примусово повертаючи коди `-ENOMEM` або `-EIO` з внутрішніх функцій виділення ресурсів.

## Криза стабільності та запровадження `ALLOW_ERROR_INJECTION()`

Майже одразу після виходу Linux 4.16 розробники ядра виявили, що `bpf_override_return()` відкрив скриню Пандори. Недосвідчені розробники BPF-скриптів почали використовувати підміну повернення для блокування викликів ядра, що призводило до катастрофічних наслідків для стабільності операційної системи.

Причини системних збоїв при використанні kprobe-override:

1. **Порушення симетрії заповнення та звільнення пам'яті**: Якщо підмінити код повернення функції, яка вже встигла виділити буфер через `kmalloc()`, але ще не встигла записати поінтер у структуру, пам'ять залишалася назавжди втраченою, створюючи критичні витоки.
2. **Незбалансовані критичні секції**: Якщо BPF-програма переривала функцію після виклику `spin_lock()`, але до виклику `spin_unlock()`, спінлок залишався захопленим назавжди. Наступний потік, який намагався його взяти, крутився в очікуванні з вимкненим витісненням — і система ставала мертвою (`kernel deadlock`).
3. **Обхід очищення стек-фрейму**: На деяких архітектурах зміна Instruction Pointer минала інструкції епілогу функції, порушуючи вирівнювання стека процесора.

Супровідник підсистеми VFS Ал Віро (Al Viro) та Лінус Торвальдс висунули жорсткі вимоги щодо обмеження цього механізму. В результаті у вихідний код ядра було введено макрос `ALLOW_ERROR_INJECTION(function, TYPE)` та відповідний білий список у верифікаторі.

Верифікатор BPF став суворо перевіряти: якщо функція ядра не відмічена у сирцевому коді макросом `ALLOW_ERROR_INJECTION()`, виклик `bpf_override_return()` для неї категорично заборонений на етапі завантаження програми. Оскільки функції VFS, системні виклики та більшість безпекових хуків не містили цієї позначки, використовувати `bpf_override_return()` для побудови корпоративних систем захисту стало неможливо.

## Народження BPF LSM (Linux 5.7)

У 2019 році інженер із безпеки компанії Google KP Singh разом із розробниками eBPF (Олексій Старовойтов, Даніель Боркман) висунув концепцію принципово іншого підходу. Замість того, щоб намагатися ламати хід виконання функцій ядра через kprobes та маніпуляції з інструкціями процесора, eBPF повинен стати інтегрованою частиною самого фреймворку LSM.

Патчі BPF LSM були опубліковані в поштовій розсилці `linux-kernel` наприкінці 2019 року й викликали бурхливе обговорення. Архітектура спиралася на розроблений раніше механізм LSM Stacking (Linux 5.1), який дозволяв одночасно виконувати декілька модулів безпеки.

Ключові архітектурні рішення BPF LSM:

1. **Відмова від `bpf_override_return()`**: Програми BPF LSM не підміняють регістри процесора. Вони викликаються ядром як штатні C-функції у ланцюжку хуків `security_*`. Якщо програма повертає від'ємне ціле число (наприклад, `-EACCES`), фреймворк LSM перехоплює його та природним шляхом повертає у VFS як стандартний код помилки системного виклику.
2. **Використання BTF та BPF CO-RE**: Завдяки BPF Type Format BPF-програма LSM отримує безпосередній доступ до аргументів хука з повною перевіркою типів під час завантаження.
3. **Інтеграція з `security_blob_sizes`**: BPF LSM отримав власний механізм BPF Local Storage, який підключається безпосередньо до ядерних security-блоків у `struct inode`, `struct task_struct` та `struct sock`, забезпечуючи миттєвий доступ до міток безпеки за час `O(1)`.

У травні 2020 року з виходом Linux 5.7 патчі BPF LSM були офіційно включені до головної гілки ядра Linux. Це позначило початок нової ери програмованого мандатного контролю доступу, де динамічні політики безпеки поєднують швидкість машинного коду, безпеку BPF-верифікатора та гнучкість простору користувача.
