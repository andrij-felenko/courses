Веб-сервер відправляє у системний конвеєр журнал доступу, де кожне звернення містить шлях `/api/v1/orders?filter=status:new,user:hanna`, HTTP-код `200` та затримку виконання `142.5ms`. Команда `cut -d',' -f2` повинна була витягнути друге поле запису, але замість імені користувача розірвала рядок запиту всередині параметра `filter`, безповоротно змістивши всі наступні стовпці. Утиліта `grep "200"` знайшла не лише успішні відповіді, а й випадкові збіги в ідентифікаторах замовлень та таймстемпах. Конвеєр, побудований на припущенні про простий текст із роздільником, розпався на першому ж реальному пакеті даних.

Класичний Unix-конвеєр створювався для обробки одновимірних потоків символів, де запис відокремлювався байтом нового рядка `0x0A` (`\n`), а поля всередині запису — пробілом або табуляцією. У сучасних інженерних системах одиницею обміну стали типізовані ієрархічні документи: JSON у веб-сервісах, YAML у маніфестах інфраструктури, CSV за стандартом RFC 4180 у великих датасетах та XML у корпоративних протоколах. Спроба розбирати ці формати за допомогою примітивного зіставлення байтів призводить до систематичних збоїв парсингу та критичних вразливостей.

## Імпедансний розрив: чому плаский рядок не тримає дерево

Механічна невідповідність між класичними утилітами (`grep`, `sed`, `awk`, `cut`) та сучасними форматами даних лежить у топології самих структур:

1. **Багатовимірність проти одновимірності.** Традиційний потік сприймає дані як послідовність лінійних рядків. Документи JSON та YAML є деревами довільної вкладеності. Одне й те саме ім'я поля (наприклад, `id` або `status`) може одночасно існувати на рівні кореневого документа, всередині метаданих сесії та в кожному елементі масиву замовлень. Лінійний пошук за підрядком не здатний визначити семантичний контекст знайденого ключа.
2. **Варіативність синтаксичного представлення.** JSON дозволяє записати об'єкт у вигляді одного суцільного рядка без пробілів або розгорнути його на сотні рядків із довільною кількістю відступів. Зміна форматування форматувальником або бібліотекою серіалізації повністю ламає вирази `awk` та `sed`, хоча саме інформаційне наповнення документа не змінюється.
3. **Екранування та внутрішні роздільники.** У форматі CSV поле законно містить кому, якщо воно обрамлене подвійними лапками (`"Kyiv, Ukraine"`). Усередині JSON-рядків регулярно зустрічаються символи переходу на новий рядок (`\n`), лапки (`\"`) та послідовності Unicode (`\u0020`). Наївний поділ за роздільником не враховує контекст лапок і руйнує межі записів.

![Еволюція конвеєра: від плаского байтового потоку до типізованих дерев та ndjson](/root/sys/sys-unix/structured-text-in-pipelines/img/pipeline-evolution.svg)

*Еволюція конвеєра: байтовий потік символів проти структурованих дерев та ndjson.*

Системний виклик ядра `pipe(2)` залишається незмінним: це байтовий канал без типізації з кільцевим буфером розміром 64 КіБ (який можна налаштувати через `fcntl` із прапорцем `F_SETPIPE_SZ`). Змінюється поведінка програм на кінцях каналу. Замість лінійного сканування до байта `0x0A` утиліти запускають синтаксичні кінцеві автомати (FSM), здатні підтримувати стек вкладеності, обробляти екранування та контролювати типи даних. Докладний розбір того, як індустрія перейшла від неструктурованих рядків до синтаксичних дерев, викладено в [історичному нарисі еволюції конвеєра](root:sys-unix/structured-text-in-pipelines/hist-structured-pipeline-roots.md).

### Межі атомарності: PIPE_BUF та мультипродюсерні канали

Коли кілька процесів одночасно записують дані в один спільний конвеєр або іменований канал (FIFO), постає питання атомарності записів.

Стандарт POSIX гарантує, що системний виклик `write(2)` є атомарним лише тоді, коли розмір блоку, що записується, не перевищує системну константу `PIPE_BUF`. У ядрі Linux `PIPE_BUF` становить 4096 байтів (4 КіБ). Якщо процес записує структурований JSON-рядок або рядок CSV розміром менше 4096 байтів, ядро гарантує, що байти запису не будуть перемішані з байтами паралельного процесу.

Якщо ж розмір серіалізованого JSON-документа перевищує 4096 байтів, ядро має право розбити запис на фрагменти, чергуючи їх із записами інших процесів. У результаті читач отримує пошкоджений потік, де один неповний JSON-об'єкт вклинюється в середину іншого. Тому при паралельному зборі логів через спільний канал розмір компактного запису ndjson завжди утримують у межах 4 КіБ або застосовують проміжну агрегацію через локальні сокети `AF_UNIX`.

## JSON у конвеєрі: потоковий та функціональний розбір через jq

Утиліта `jq` (від JSON query) є повноцінною мовою функціонального програмування, спроєктованою для маніпуляції абстрактними синтаксичними деревами JSON. У моделі `jq` будь-яка операція є фільтром, який приймає на вхід одне JSON-значення і повертає потік із 0, 1 або багатьох вихідних значень.

### Базові селектори та ітерація по масивах

Символ крапки `.` позначає поточний вхідний контекст (ідентичний оператор). Навігація по ключах об'єкта здійснюється додаванням імені поля:

```bash
# Отримання вкладеного поля
echo '{"user": {"name": "Hanna", "role": "admin"}}' | jq '.user.name'
# Виведе: "Hanna"
```

Коли полем є масив, оператор `[]` виконує розгортання масиву (stream flattening): він перетворює масив із `N` елементів на потік із `N` незалежних JSON-об'єктів, які проходять через наступні фільтри конвеєра по черзі:

```bash
# Розгортання масиву об'єктів у потік
echo '{"items": [{"id": 1}, {"id": 2}, {"id": 3}]}' | jq '.items[].id'
# Виведе:
# 1
# 2
# 3
```

Оператор каналу `|` всередині виразу `jq` працює аналогічно конвеєру POSIX, але передає між функціями не байти, а типізовані структури даних.

### Фільтрація предикатами та конструювання об'єктів

Функція `select(умова)` приймає логічний вираз і працює як шлюз: якщо вираз повертає `true`, вхідне значення пропускається далі по конвеєру; якщо `false` або `null`, значення відкидається (генерується 0 виходів).

Для зміни схеми даних утиліта дозволяє створювати нові об'єкти безпосередньо у виразі за допомогою літералів `{}`:

```bash
# Фільтрація помилок сервера та створення нового об'єкта
curl -s https://api.example.com/events | jq '
  .events[]
  | select(.status >= 500 and .latency_ms > 1000)
  | {
      timestamp: .ts,
      endpoint: .path,
      error_code: .status,
      duration_sec: (.latency_ms / 1000)
    }
'
```

![Функціональна модель виконання jq: генератор потоку від одного входу до 0..N виходів](/root/sys/sys-unix/structured-text-in-pipelines/img/jq-execution-model.svg)

*Модель виконання jq: синтаксичний фільтр як чистий генератор вихідного потоку.*

### Рекурсивний обхід, модифікація та стрип-парсер

Мова `jq` містить потужні оператори для обробки глибоко вкладених структур:
- **Рекурсивний спуск `..`**: знаходить усі значення на будь-якій глибині вкладеності. Наприклад, вираз `.. | .id? // empty` знаходить усі ключі `id` у документі незалежно від рівня ієрархії.
- **Оновлення вузлів `|=` та видалення `del()`**: оператор оновлення застосовує трансформацію до вказаного шляху, зберігаючи решту дерева незмінною (`.database.port |= 5432` або `del(.metadata.internal_debug)`).
- **Потоковий парсер `jq --stream`**: режим, у якому `jq` розкладає документ на потік пар `[шлях, значення]`. Це дозволяє обробляти монолітні 100-гігабайтні JSON-файли без побудови DOM у пам'яті, зчитуючи лише зазначені шляхи вузлів.

### Режими I/O: сирий вивід, потоковість та пастка -s

Форматування виводу та режим використання пам'яті контролюються прапорцями командного рядка:

- `-r` (`--raw-output`): відкидає лапки навколо рядкових значень та інтерпретує escape-послідовності. Це обов'язковий прапорець, коли результат передається утилітам POSIX (`xargs`, `curl`, `ssh`):
  ```bash
  # Безпечне витягування списку IP-адрес для передачі в системний блокувальник
  jq -r '.banned_ips[]' response.json | xargs -I {} iptables -A INPUT -s {} -j DROP
  ```
- `-c` (`--compact-output`): згортає кожен вихідний JSON-об'єкт у суцільний однорядковий текст без відступів. Цей прапорець перетворює ієрархічний JSON на потік JSON Lines.
- `-s` (`--slurp`): вичитує весь вхідний потік до досягнення `EOF` і збирає всі окремі об'єкти в єдиний масив `[...]`.

> ⚠️ **Архітектурна пастка прапорця `-s`:**
> Прапорець `-s` ламає потоковість конвеєра. Якщо через канал проходить потік журналів обсягом 50 Гб, утиліта з прапорцем `-s` буде накопичувати всі 50 Гб в оперативній пам'яті доти, доки джерело не закриє дескриптор запису. Це неминуче призводить до аварійного завершення процесу через вичерпання пам'яті (OOM Killer).
> Для потокової обробки безмежних потоків слід використовувати комбінацію `-c` та конструкцію `.[] | select(...)`, що гарантує константну пам'ять `O(1)` на кожен оброблений запис.

Повний перелік прапорців, кодів повернення та правил обробки помилок задокументовано в [інтерфейсній довідці з утиліт структурованого тексту](root:sys-unix/structured-text-in-pipelines/api-structured-cli-tools.md).

## Формат JSON Lines (ndjson) як ідеальний міст

Формат **JSON Lines** (також відомий як `ndjson` — newline-delimited JSON або `jsonl`) розв'язує фундаментальний конфлікт між деревами об'єктів та лінійним конвеєром Unix.

Правила формату ndjson гранично прості:
1. Кожен окремий рядок є синтаксично повним і валідним документом JSON.
2. Кожен рядок завершується символом переходу на новий рядок `\n` (`0x0A`).
3. Будь-які символи переходу на новий рядок усередині рядкових значень обов'язково екрануються як два байти `\n` (`0x5C 0x6E`).

```json
{"ts":"2026-08-25T10:00:00Z","level":"INFO","msg":"Сервіс запущено","code":200}
{"ts":"2026-08-25T10:00:01Z","level":"ERROR","msg":"Збій з'єднання з БД\nTimeout 5s","code":503}
{"ts":"2026-08-25T10:00:02Z","level":"WARN","msg":"Повторна спроба","code":429}
```

Завдяки такій структурі конвеєр повертає всі переваги моделі Unix:
- **Константна пам'ять:** Процеси зчитують потік построково, обробляють один об'єкт і негайно передають його далі. Використання RAM не залежить від того, чи триває конвеєр 5 секунд, чи 5 місяців.
- **Миттєва реакція на сигнали (`SIGPIPE`):** Якщо на виході конвеєра стоїть утиліта обмеження виводу `head -n 10`, вона закриває дескриптор читання після десятого рядка. Ядро надсилає сигнал `SIGPIPE` процесору `jq`, і той негайно перериває читання гігабайтного входу, не виконуючи зайвої роботи.
- **Сумісність зі стандартними утилітами:** Потік ndjson можна паралелити утилітою `parallel --pipe`, розбивати на частини утилітою `split -l` або виконувати грубу фільтрацію швидкісним `grep`.

Практичну реалізацію власного високошвидкісного потокового фільтра ndjson із нульовим копіюванням розібрано в [практичному проєкті створення потокового процесора](root:sys-unix/structured-text-in-pipelines/proj-ndjson-stream-processor.md).

## YAML і файли конфігурацій: стан, коментарі та yq

Формат YAML (YAML Ain't Markup Language) став фактичним стандартом конфігурації хмарних середовищ завдяки високій читабельності людиною, підтримці коментарів та чутливості до відступів (whitespace indentation). Проте саме ці властивості роблять його складним для потокової обробки.

### Відмінності реалізацій: Go vs Python

В екосистемі Linux існують дві принципово різні утиліти під назвою `yq`:
1. **Python-версія (`kislyuk/yq`):** є тонкою обгорткою над `jq`. Вона конвертує вхідний YAML у тимчасовий JSON, передає його у бінарник `jq`, а потім конвертує результат назад у YAML. Недолік підходу: повна втрата всіх коментарів, зміна порядку ключів і втрата специфічних типів YAML.
2. **Go-версія (`mikefarah/yq`):** самостійний бінарний компілятор, що будує власне синтаксичне дерево з підтримкою коментарів як властивостей вузлів AST. Саме вона використовується в сучасній інфраструктурі.

### Модифікація конфігурацій на місці (-i)

Редагування маніфестів безпосередньо на диску виконується прапорцем `-i` (`--inplace`):

```bash
# Оновлення версії образу в маніфесті Kubernetes зі збереженням коментарів
yq -i '.spec.template.spec.containers[0].image = "registry.example.com/app:v2.4.0"' deployment.yaml
```

Механіка атомарного оновлення `yq -i`:
1. Утиліта створює тимчасовий файл у тій самій теці (наприклад, `.deployment.yaml.tmp`).
2. Виконує парсинг, оновлює вузол синтаксичного дерева і серіалізує документ у тимчасовий файл.
3. Викликає системний виклик `fsync(2)` для гарантування запису блоків на фізичний диск.
4. Виконує системний виклик `rename(2)`, замінюючи оригінальний файл тимчасовим. Завдяки атомарності `rename` процес ніколи не залишить конфігураційний файл напівстертим у разі збою живлення чи переривання сигналу `SIGKILL`.

### Трансляція між форматами та семантичні пастки

Трансляція між форматами YAML та JSON виконується прапорцями `-o=json` та `-p=json -o=yaml`:

```bash
# Перетворення YAML-конфігурації в JSON для подальшої обробки через jq
yq -o=json service.yaml | jq '.metadata.labels'
```

Під час трансляції слід враховувати небезпечні крайові випадки:
- **The Norway Problem (проблема Норвегії):** За стандартом YAML 1.1 нелапкові значення `y`, `Y`, `yes`, `Yes`, `YES`, `n`, `N`, `no`, `No`, `NO` парсяться як булеві `true` та `false`. Двобуквений код країни Норвегія (`country: NO`) при трансляції в JSON автоматично перетворюється на `{"country": false}`, якщо значення не було явно взято в подвійні лапки.
- **Розгортання якорів (YAML Entity Expansion):** YAML підтримує перевикористання блоків через якорі (`&base`) та посилання (`*base`). Спроба розпарсити шкідливий маніфест із циклічними або експоненційними посиланнями (Billion Laughs Attack) може призвести до споживання гігабайтів оперативної пам'яті під час серіалізації в JSON.

## Високопродуктивна обробка CSV: xsv

Табличні дані у форматі CSV (Comma-Separated Values) широко використовуються для експорту баз даних, білінгу та звітів аналітики. Розмір таких файлів часто перевищує обсяг доступної оперативної пам'яті сервера (10–100 Гб).

Класичні інструменти розбиття рядків (`cut -d','` або `awk -F','`) не відповідають стандарту RFC 4180: вони ламаються, коли значення містять коми всередині лапок (`"120,50"`) або коли текстове поле містить реальний символ нового рядка.

### Архітектура утиліти xsv

Утиліта `xsv` написана мовою Rust і забезпечує обробку CSV зі швидкістю, близькою до пропускної здатності шини пам'яті, за рахунок векторних інструкцій SIMD та нульового динамічного виділення пам'яті на рядок.

Основні операції `xsv`:
```bash
# Проєкція колонок за назвами або номерами
xsv select "UserID,Status,Amount" transactions.csv > summary.csv

# Обчислення зведеної статистики по всіх стовпцях без завантаження файлу в RAM
xsv stats transactions.csv | xsv table

# Фільтрація рядків за регулярним виразом у конкретному стовпці
xsv search -s "Status" "^(FAILED|ERROR)$" transactions.csv
```

### Механізм індексації та довільний доступ (Random Access)

Головною інновацією `xsv` є підкоманда `xsv index`. Вона створює супровідний бінарний файл `<ім'я_файлу>.csv.idx`:

```bash
xsv index large_dataset.csv
```

![Індексація великих CSV-файлів у xsv: перехід від лінійного O(N) сканування до O(1) seek](/root/sys/sys-unix/structured-text-in-pipelines/img/xsv-index-seek.svg)

*Індексація та довільний доступ у xsv: бінарна таблиця зміщень дозволяє миттєвий lseek(2).*

Індекс являє собою щільну таблицю 64-бітних цілих чисел, де для кожного номера рядка збережено його абсолютне байтове зміщення (byte offset) від початку файлу.

Коли індекс створено:
1. Підкоманда `xsv count` повертає точну кількість записів миттєво, зчитуючи розмір індексу без відкриття самого CSV-файлу.
2. Підкоманда `xsv slice -i 5000000 -l 10` (витягнути 10 рядків, починаючи з 5-мільйонного) зчитує зміщення для рядка 5 000 000 з індексу, виконує системний виклик `lseek(fd, offset, SEEK_SET)` і читає рівно 1 КіБ даних. Операція займає менше 1 мілісекунди на 50-гігабайтному файлі.
3. Підкоманда `xsv sample` виконує рівномірну випадкову вибірку без послідовного сканування всього диска.

### Обробка крайових випадків RFC 4180

Стандарт RFC 4180 визначає формальні правила оформлення CSV-таблиць:
- **Перенесення рядків усередині полів:** Текстове значення може містити фізичні символи `CRLF` або `LF`, якщо воно закрите у подвійні лапки. Будь-який побуквений сканер зобов'язаний розрізняти межу поля та межу запису, спираючись на парність лапок.
- **Екранування лапок:** Якщо лапка зустрічається всередині значення в лапках, вона записується як дві лапки поспіль (`""`).
- **Символ порядку байтів (BOM):** Файли, експортовані з Microsoft Excel або Windows-систем, часто починаються з трьох байтів UTF-8 BOM (`0xEF 0xBB 0xBF`). Якщо парсер не вміє відкидати BOM автоматично, перший стовпець отримує пошкоджену назву (наприклад, `ufeffID` замість `ID`), що ламає всі подальші селектори `select`. Утиліта `xsv` коректно розпізнає та зрізає BOM на етапі ініціалізації потоку.

## Дерева XML та простори імен: xmlstarlet

Формат XML (eXtensible Markup Language) є основою протоколів SOAP, конфігурацій корпоративного ПЗ та банківських систем. XML поєднує строгу типізацію атрибутів, парні теги, коментарі та простори імен (namespaces).

Парсинг XML за допомогою регулярних виразів є математично неможливим через рекурсивну природу мови (XML не є регулярною мовою у сенсі теорії автоматів Хомського).

Утиліта `xmlstarlet` використовує системну бібліотеку `libxml2` і надає повноцінний рушій обчислення виразів XPath 1.0:

```bash
# Вибірка атрибута id та тексту імені для всіх активних користувачів
xmlstarlet sel -t \
  -m "//users/user[@active='true']" \
  -v "@id" -o ":" -v "name" -n \
  users.xml
```

### Робота з просторами імен (Namespaces)

У складних XML-документах (наприклад, WSDL або SAML-відповідях) однакові теги розрізняються просторами імен:

```xml
<root xmlns:env="http://schemas.xmlsoap.org/soap/envelope/"
      xmlns:m="http://example.com/orders">
  <env:Body>
    <m:GetOrderResponse>
      <m:OrderID>98432</m:OrderID>
    </m:GetOrderResponse>
  </env:Body>
</root>
```

Для вибірки вузла необхідно явно зареєструвати префікс простору імен через ключ `-N`:

```bash
xmlstarlet sel \
  -N env="http://schemas.xmlsoap.org/soap/envelope/" \
  -N m="http://example.com/orders" \
  -t -v "//m:GetOrderResponse/m:OrderID" \
  response.xml
```

### Безпека XML у конвеєрі: запобігання атакам XXE

XML підтримує механізм визначення зовнішніх сутностей (DTD External Entities). Якщо небезпечний XML-документ обробляється утилітою без обмежень, парсер може спробувати завантажити локальні файли або ініціювати мережеві з'єднання (атака XXE — XML External Entity Injection):

```xml
<?xml version="1.0"?>
<!DOCTYPE test [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<user><name>&xxe;</name></user>
```

Для запобігання витокам утиліту `xmlstarlet` запускають без підвантаження DTD або перевизначають змінні каталогу `XML_CATALOG_FILES`, ізолюючи парсер від зовнішніх ресурсів операційної системи.

> ⚠️ **Обмеження пам'яті DOM у XMLStarlet:**
> Бібліотека `libxml2` будує повне об'єктне дерево документа (DOM) в оперативній пам'яті. Для XML-файлу розміром 1 Гб побудоване дерево DOM зазвичай займає від 4 до 8 Гб RAM. Обробка великих XML-файлів через `xmlstarlet` у конвеєрі вимагає обережності; для гігабайтних XML-потоків застосовують потокові SAX/StAX-парсери.

## Безпека конвеєрів: анатомія ін'єкцій та параметризація

Найпоширенішою вразливістю при написанні скриптів автоматизації є небезпечна підстановка змінних оболонки безпосередньо в текст синтаксичного виразу фільтра (Expression Injection).

### Анатомія jq-ін'єкції

Розглянемо типовий фрагмент сценарію авторизації:

```bash
# ВРАЗЛИВИЙ КОД: конкатенація змінної оболонки у вираз jq
USER_NAME="$1"
jq ".users[] | select(.name == \"$USER_NAME\") | .email" database.json
```

Якщо користувач передає легітимне ім'я `hanna`, оболонка формує вираз:
`.users[] | select(.name == "hanna") | .email`.

Якщо ж зловмисник передає рядок:
`admin") | .secret_token // ("`

Оболонка виконує підстановку тексту, і команда перетворюється на:
```bash
jq '.users[] | select(.name == "admin") | .secret_token // ("") | .email' database.json
```

Синтаксичне дерево виразу розірвано. Рядковий літерал закрився передчасно, вставився новий фільтр `.secret_token`, і утиліта повертає секретні ключі доступу замість адреси пошти.

![Анатомія ін'єкцій у конвеєрах: руйнування AST при конкатенації рядків проти строгої параметризації](/root/sys/sys-unix/structured-text-in-pipelines/img/injection-vs-param.svg)

*Запобігання ін'єкціям у конвеєрах структурованих даних: строга типізована передача через --arg.*

### Безпечна параметризація через --arg та --argjson

Для повного усунення загрози ін'єкцій дані повинні передаватися окремо від синтаксичного коду програми через спеціальні інтерфейсні прапорці:

```bash
# БЕЗПЕЧНИЙ КОД: використання аргументу --arg
USER_NAME="$1"
jq --arg target_name "$USER_NAME" '
  .users[]
  | select(.name == $target_name)
  | .email
' database.json
```

Механізм роботи `--arg`:
1. Утиліта `jq` компілює текст програми в абстрактне синтаксичне дерево (AST) один раз до початку читання даних.
2. Змінна `$target_name` фіксується в таблиці символів як незмінний вузол значення (Value Node).
3. Байти з аргументу оболонки записуються безпосередньо у внутрішню структуру типу `jv_string`. Жодні лапки, вертикальні риски чи круглі дужки всередині значення не можуть змінити структуру скомпільованого AST.

Аналогічно для типізованих структур застосовується прапорець `--argjson`:
```bash
# Безпечна передача масиву дозволених статусів
ALLOWED_STATUSES='[200, 201, 204]'
jq --argjson valid "$ALLOWED_STATUSES" '
  .events[] | select(.status as $s | $valid | index($s))
' stream.ndjson
```

Для передачі вмісту великих файлів без навантаження на список аргументів командного рядка (`ARG_MAX`) застосовуються прапорці `--rawfile` (читання всього файлу як тексту) та `--slurpfile` (читання як JSON-масиву).

## Високонавантажені патерни конвеєризації в Linux

Коли через структурований конвеєр проходять десятки гігабайтів подій на годину, звичайної послідовної передачі команд недостатньо. Інженери застосовують спеціалізовані шаблони оптимізації пропускної здатності та контролю помилок:

### 1. Паралелізація потоків через GNU Parallel

Утиліта `jq` є однопотоковою програмою, яка впирається в продуктивність одного ядра CPU. Щоб задіяти всі ядра сервера, потік ndjson ділять на блоки та розподіляють між процесами `jq` за допомогою `parallel --pipe`:

```bash
# Розподіл 20 Гб ndjson-потоку по всіх доступних ядрах процесора блоками по 16 Мб
cat access_huge.ndjson \
  | parallel --pipe --block 16M --round-robin \
      jq -c 'select(.status >= 500) | {ip: .ip, path: .path}' \
  | gzip -c > filtered_errors.ndjson.gz
```

### 2. Керування буферизацією за допомогою mbuffer

При передачі даних через мережу або повільні накопичувачі різниця у швидкості між продюсером і консьюмером може викликати періодичні блокування. Утиліта `mbuffer` створює виділений кільцевий буфер в оперативній пам'яті:

```bash
# Згладжування стрибків навантаження буфером 512 Мб
curl -sN "https://stream.example.com/events" \
  | mbuffer -m 512M -q \
  | jq -c 'select(.latency > 2000)' \
  | xsv select "id,latency" > slow.csv
```

### 3. Контроль статусів завершення в Bash

За замовчуванням конвеєр повертає код виходу останньої виконаної команди. Якщо проміжна ланка `jq` впала з помилкою через пошкоджений JSON, конвеєр `curl | jq | gzip` поверне `0`, приховавши факт аварії.

Для гарантування надійності у сценаріях завжди активують прапорець `set -o pipefail` та аналізують масив `${PIPESTATUS[@]}`:

```bash
set -o pipefail

curl -s "https://api.example.com/data.json" \
  | jq -e '.data[] | select(.valid == true)' \
  | gzip -c > output.gz

PIPE_STATUS=("${PIPESTATUS[@]}")
if [ "${PIPE_STATUS[0]}" -ne 0 ] || [ "${PIPE_STATUS[1]}" -ne 0 ]; then
  echo "[CRITICAL] Помилка завантаження або фільтрації JSON" >&2
  exit 1
fi
```

## Синтез: еталонний виробничий конвеєр даних

Об'єднання розглянутих інструментів дозволяє побудувати надійний, високопродуктивний конвеєр моніторингу та агрегації в середовищі Linux:

```bash
#!/usr/bin/env bash
set -euo pipefail

# Конвеєр аналізу журналів доступу API в режимі реального часу:
# 1. curl отримує потік подій у форматі ndjson;
# 2. jq виконує безпечну параметризовану фільтрацію та проєкцію;
# 3. yq перетворює критичні інциденти у формат YAML для систем сповіщення.

LOG_ENDPOINT="https://logs.internal.net/stream"
MIN_LATENCY=1500

curl -sN "${LOG_ENDPOINT}" \
  | jq -c --unbuffered --argjson min_lat "${MIN_LATENCY}" '
      select(.status >= 500 or .latency_ms > $min_lat)
      | {
          alert: "CRITICAL_LATENCY",
          service: .service_name,
          endpoint: .path,
          status: .status,
          latency: .latency_ms,
          timestamp: .ts
        }
    ' \
  | yq -p=json -o=yaml -
```

У цій архітектурі кожен компонент виконує свою роль: ядро забезпечує блокування та зворотний тиск буферів через системний канал, `jq` гарантує ізоляцію та типізацію даних без витоку пам'яті, а кінцевий вивід формується у стандартизованому, безпечному для читання форматі.
