# 📜 Від байтових потоків до текстових дерев: еволюція конвеєра

Конвеєр як механізм міжпроцесної взаємодії народився з потреби з'єднати вивід однієї програми зі входом іншої без проміжних тимчасових файлів на диску. У 1964 році Дуглас Макілрой (Malcolm Douglas McIlroy) у внутрішньому меморандумі Bell Labs сформулював ідею: «Ми повинні мати спосіб з'єднувати програми, як садовий шланг, коли дані течуть від одного сегмента до іншого». Коли у 1972–1973 роках Кен Томпсон реалізував системний виклик `pipe(2)` у третій редакції Unix, операційна система отримала найпростіший можливий інтерфейс: неструктурований потік байтів, де єдиною семантичною домовленістю між утилітами став символ переходу на новий рядок (`\n`, байт `0x0A`).

Ця простота забезпечила небачену гнучкість. Утиліти `grep`, `sed`, `awk`, `cut` та `sort` працювали з текстом як з одновимірним масивом рядків. Проте простота приховувала архітектурне припущення: дані є пласкими записами, де кожне поле відокремлене фіксованим символом (пробілом, табуляцією або двокрапкою), а сам запис ніколи не містить роздільника всередині свого значення.

## Спроби впровадження типізованих потоків у наукових ОС

Уже наприкінці 1970-х років розробники зіткнулися з крихкістю текстових конвеєрів. Якщо ім'я файлу містило пробіл, конвеєр `find . | xargs rm` міг видалити не ті файли або завершитися помилкою. Постало питання: чи не має операційна система передавати між процесами типізовані структури замість неструктурованого потоку байтів?

У лабораторіях Bell Labs під час розробки операційної системи Plan 9 у 1980-х роках дослідники розглядали введення формату типізованих записів (record streams). Проте команда Кена Томпсона, Роба Пайка та Дениса Рітчі відмовилася від типізації на рівні ядра. Причина полягала в універсальності: байтовий потік не потребує узгодження схем між програмами, написаними різними мовами чи в різні десятиліття. Будь-яка схема даних, зашита в системний виклик ядра, застаріває швидше, ніж живе сама операційна система.

Іншим напрямком стала система Nemesis (Кембриджський університет, 1990-ті) та пізніше об'єктний конвеєр Monad, створений Джеффрі Сновером у Microsoft (2002), який ліг в основу PowerShell. Monad пішов протилежним шляхом: замість тексту конвеєр передає посилання на «живі» об'єкти середовища CLR (.NET). Команда `Get-Process | Where-Object WorkingSet -gt 100MB` не парсить текст, а звертається до типізованого поля об'єкта в оперативній пам'яті. Це вирішило проблему роздільників і екранування, але зробило конвеєр жорстко прив'язаним до єдиного середовища виконання (.NET VM) та унеможливило пряму взаємодію з довільними бінарними утилітами, скомпільованими з C чи Rust.

## Поява веб-API та криза плаского тексту

На початку 2000-х років розвиток розподілених систем, мікросервісів та хмарної інфраструктури докорінно змінив природу даних, що циркулюють у терміналі. На зміну локальним конфігураціям `/etc/passwd` та простим журнальним файлам прийшли REST API, RPC-виклики та розподілені сховища.

Дані стали багатовимірними. Відповідь сервера представляла собою ієрархічне дерево з вкладеними об'єктами, масивами, полями довільної довжини, датами та булевими прапорцями. Спроба обробити відповідь HTTP-сервера у форматі XML або JSON за допомогою класичних утиліт `grep` та `awk` призводила до систематичних збоїв:

1. **Нелінійність структури:** одне й те саме поле могло з'являтися на різних рівнях вкладеності з різним семантичним значенням.
2. **Варіативність форматування:** JSON дозволяє записувати об'єкт в один рядок або розбивати його на десятки рядків із довільними відступами. Регулярний вираз у `grep`, розрахований на один рядок, ламався при зміні відступів форматувальником.
3. **Екранування та спеціальні символи:** рядкові поля всередині JSON чи CSV законно містять коми, лапки, переноси рядків (`\n`) та символи Unicode. Розділення рядка за комою через `cut -d','` безповоротно пошкоджувало вміст.

## Поява мов запитів для структурованого тексту

Спільнота Unix відмовилася від переписування ядра і зберегла байтовий канал `pipe(2)`, але оновила набір утиліт фільтрації. Замість загальних строкових фільтрів з'явилися спеціалізовані синтаксичні процесори для кожного стандартного формату даних:

- **XMLStarlet (2002, Михайло Грінберг):** надав командному рядку можливості XPath та XSLT, спираючись на системну бібліотеку `libxml2`. Це дозволило навігувати по DOM-деревах XML-документів без написання коду на Perl чи Python.
- **jq (2012, Стівен Долан):** став революцією для JSON у терміналі. Стівен Долан (Stephen Dolan) спроєктував `jq` як повноцінну функціональну мову програмування з лінивими потоками генераторів. `jq` сприймає JSON не як текст, а як абстрактне синтаксичне дерево, дозволяючи фільтрувати, проєктувати, згортати та комбінувати дані в термінах алгебри типів JSON.
- **yq (2017, Майк Фарах):** переніс парадигму `jq` на світ YAML, який став стандартом конфігурації у Kubernetes, CI/CD-конвеєрах та інфраструктурі як коді. На відміну від ранніх обгорток на Python, версія на Go зберігає коментарі, порядок ключів та структуру документів при редагуванні файлів на місці (`-i`).
- **xsv (2015, Ендрю Галлант):** переосмислив обробку табличних даних (CSV/TSV). Написаний на Rust, `xsv` поєднав суворе дотримання стандарту RFC 4180 з високою швидкістю завдяки векторним інструкціям SIMD та введенню бінарних індексних файлів зміщень для швидкого довільного доступу до гігабайтних датасетів.

## JSON Lines як історичний консенсус

Кульмінацією цієї еволюції стало оформлення формату **JSON Lines** (ndjson / jsonl). Він об'єднав найкраще з обох світів:
1. Збережено модель потокової побудови конвеєра Unix: кожен рядок завершується байтом `0x0A`, що дозволяє утилітам ядра передавати дані блоками, не накопичуючи гігабайти в оперативній пам'яті.
2. Збережено багатство типів та ієрархію: кожен окремий рядок є повноцінним, замкненим JSON-документом, який може містити довільну глибину вкладеності.

Текстовий конвеєр Unix пройшов шлях від неструктурованого ASCII-потоку до системи обробки розподілених типізованих документів, зберігши свою головну перевагу — компонованість незалежних процесів через прості та відкриті протоколи передачі даних.
