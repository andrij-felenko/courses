Коли системний адміністратор відкриває кілька паралельних сесій SSH для усунення аварії на сервері, знаходить і виправляє критичну помилку в одному вікні, а згодом закриває всі термінали, під час наступного входу він часто виявляє, що введена послідовність команд безслідно зникла. Останній закритий процес оболонки тихо перезаписав файл `~/.bash_history` власним буфером пам'яті, стерши діагностичні записи інших вікон. В іншій ситуації інженер передає пароль бази даних безпосередньо у параметрах виклику `mysql -u root -p'SecretPass123'`, і конфіденційний секрет назавжди осідає відкритим текстом на диску у журналі команд, доступному для резервного копіювання чи випадкового перегляду іншими користувачами системи.

Обидві проблеми є прямим наслідком внутрішнього влаштування підсистеми історії команд (від грецького *historia* — розпитування, літопис). Інтерактивна оболонка Unix (Bash, Zsh) повинна вирішувати суперечливі інженерні завдання: надавати миттєвий доступ до тисяч попередніх викликів без затримок введення та блокування вводу-виводу, захищати конфіденційні дані від компрометації та забезпечувати узгоджене збереження стану між десятками паралельних термінальних процесів одного користувача.

Для досягнення цієї мети механізм історії реалізовано як дворівневу архітектуру, що розділяє швидкодіючу структуру даних у віртуальній пам'яті процесу та довготривале дискове сховище у файловій системі.

## 1. Дворівнева архітектура: пам'ять процесу проти файлу на диску

В інтерактивних оболонках сімейства GNU/Linux підсистема історії реалізована через бібліотеку `libhistory` (компонент GNU Readline). Вона працює за принципом повного розділення операцій реального часу та операцій дискової синхронізації.

![Дворівнева архітектура історії: буфер пам'яті та файл на диску](/root/sys/sys-unix/command-history/img/history-memory-vs-file.svg)
*Дворівнева архітектура історії команд: відокремлення динамічного масиву the_history у купі процесу від довготривалого файлу ~/.bash_history на диску.*

Під час запуску нового інтерактивного сеансу оболонка виділяє в купі (heap) процесу динамічний масив покажчиків на структури записів історії `HIST_ENTRY`. Пам'ять процесу стає головним оперативним джерелом даних: будь-яке натискання клавіш «Стрілка вгору», «Стрілка вниз» або пошук `Ctrl+R` сканує виключно цей внутрішній масив, не звертаючись до диска через системні виклики VFS.

```
Структура запису історії в пам'яті (C / POSIX):
typedef struct _hist_entry {
    char *line;          /* Символьний рядок команди в купі */
    char *timestamp;     /* Символьне представлення мітки часу або NULL */
    histdata_t data;     /* Додаткові прапорці та контекстні дані */
} HIST_ENTRY;
```

У бібліотеці GNU History цей буфер організовано як динамічний вектор `the_history` із лічильником записів та покажчиком поточної позиції навігації.

:::tabs
```c
/* Взаємодія з буфером libhistory мовою C */
#include <stdio.h>
#include <readline/history.h>

void record_command(const char *cmd_text) {
    using_history();
    /* Додавання рядка до кільцевого масиву пам'яті */
    add_history(cmd_text);
    
    /* Збереження вмісту пам'яті у постійний файл */
    if (write_history("/home/user/.bash_history") != 0) {
        perror("write_history failed");
    }
}
```
```cpp
// Ідіоматична обгортка історії команд на C++20
#include <string>
#include <string_view>
#include <vector>
#include <chrono>
#include <fstream>
#include <stdexcept>
#include <iostream>

class CommandHistory {
public:
    struct Entry {
        std::string command;
        std::chrono::system_clock::time_point timestamp;
    };

    void add_entry(std::string_view cmd) {
        if (cmd.empty()) return;
        entries_.push_back(Entry{
            std::string(cmd),
            std::chrono::system_clock::now()
        });
    }

    void save_to_file(const std::string &path) const {
        std::ofstream out(path, std::ios::out | std::ios::trunc);
        if (!out.is_open()) {
            throw std::runtime_error("Failed to open history file for writing: " + path);
        }
        for (const auto &entry : entries_) {
            auto epoch = std::chrono::duration_cast<std::chrono::seconds>(
                entry.timestamp.time_since_epoch()
            ).count();
            out << '#' << epoch << '\n' << entry.command << '\n';
        }
    }

private:
    std::vector<Entry> entries_;
};
```

### Розрахунок накладних витрат пам'яті

Розподіл пам'яті під буфер історії є надзвичайно економним. На 64-бітній архітектурі x86_64 кожен запис складається з таких компонентів:

1. Покажчик у головному масиві `HIST_ENTRY** the_history`: 8 байтів.
2. Сама структура `HIST_ENTRY`: три 8-байтові поля (`line`, `timestamp`, `data`), тобто 24 байти.
3. Текстовий рядок команди: довжина символів `L + 1` байт для нульового байта завершення `\0`.
4. Метадані алокатора `ptmalloc` у C-бібліотеці glibc: кожен окремий виклик `malloc()` потребує 16 байтів службового заголовка чанка пам'яті та вирівнюється по межі 16 байтів.

Для середньої команди довжиною 35 символів один запис історії споживає:

```
8 (покажчик) + [24 + 16] (структура з заголовком) + [36 + 16] (рядок з заголовком) = 100 байтів
```

Збереження буфера на 10 000 команд вимагає приблизно 1 мегабайт оперативної пам'яті. Це доводить, що збільшення розміру оперативної історії не створює суттєвого навантаження на підсистему пам'яті сучасних комп'ютерів, тоді як дискові операції введення-виведення залишаються головним фактором затримок.

### Системні виклики та життєвий цикл сесії

Життєвий цикл команди в історії проходить три фундаментальні стадії, які можна безпосередньо спостерігати за допомогою утиліти трасування системних викликів `strace`:

1. **Фаза ініціалізації сесії**: Під час старту оболонка викликає функцію `read_history(histfile)`. Вона відкриває файл `~/.bash_history` системним викликом `openat(AT_FDCWD, "/home/user/.bash_history", O_RDONLY)`, зчитує рядки порціями через `read()`, розбирає часові мітки та заповнює оперативний масив `the_history` в межах ліміту змінної `HISTSIZE`.
2. **Фаза інтерактивного циклу (REPL)**: Після того як користувач вводить рядок і натискає Enter, оболонка виконує розкриття історії, перевіряє правила фільтрації `HISTCONTROL` / `HISTIGNORE` і передає готовий рядок функції `add_history()`. Виділяється пам'ять під новий об'єкт `HIST_ENTRY`, а покажчик додається в кінець масиву `the_history`. На диск у цей момент нічого не записується.
3. **Фаза завершення сесії (Exit)**: Коли процес оболонки отримує команду `exit`, стандартний обробник завершення викликає `write_history(histfile)`. Функція відкриває файл `~/.bash_history` із прапорцем `O_WRONLY|O_CREAT|O_TRUNC`, записує туди вміст оперативного буфера та викликає функцію `history_truncate_file()`, яка обрізає файл на диску системним викликом `ftruncate()` до максимальної довжини, визначеної змінною `HISTFILESIZE`.

### Стандартизація POSIX: утиліта fc

У стандарті POSIX (IEEE Std 1003.1) пряме керування історією стандартизовано через утиліту `fc` (Fix Commands). Стандарт вимагає підтримки змінних `HISTFILE` та `HISTSIZE`, але замість окремої вбудованої команди `history` формально визначає режими роботи `fc`:

* `fc -l [first [last]]` (List): Виводить список збережених команд із номерами рядків.
* `fc -s [old=new] [first]` (Substitute): Повторно виконує команду, замінюючи перший збіг підрядка `old` на `new` (аналог швидкої заміни `^old^new^`).
* `fc -e editor [first [last]]` (Edit): Відкриває вказані команди у текстовому редакторі (значення змінної `FCEDIT` або `EDITOR`), а після збереження та закриття редактора негайно запускає модифіковані рядки на виконання.

Вбудована команда `history` у Bash та Zsh є зручною розширеною надбудовою над стандартом POSIX, що реалізує прямий доступ до внутрішніх методів маніпуляції буфером пам'яті.

Детальний аналіз зародження цього механізму в системі BSD та його відокремлення у незалежні бібліотеки наведено у вставці [Від телетайпів 2BSD csh до GNU Readline: історія розкриття команд](root:sys-unix/command-history/hist-csh-and-readline-history.md).

## 2. Керування збереженням: параметри та змінні середовища

Керування виділенням пам'яті, глибиною журналу та форматуванням часових позначок здійснюється через набір змінних середовища та внутрішніх прапорців оболонки.

### HISTSIZE проти HISTFILESIZE

Головна відмінність між `HISTSIZE` та `HISTFILESIZE` полягає в тому, до якого шару дворівневої моделі застосовується кожен параметр:

* `HISTSIZE` (розмір черги в пам'яті): Визначає максимальну кількість команд, що одночасно утримуються в адресному просторі процесу оболонки. Якщо кількість введених за сесію команд перевищує `HISTSIZE`, найстаріші записи звільняються з пам'яті викликом `free()` і витісняються новішими. Значення `HISTSIZE=0` повністю відключає збереження історії в поточному процесі. Якщо змінну не встановлено, Bash за замовчуванням виділяє пам'ять під 500 записів (у нових версіях — 1000). Встановлення від'ємного значення (наприклад, `HISTSIZE=-1`) у версіях Bash 4.3+ робить розмір пам'яті історії необмеженим.
* `HISTFILESIZE` (ліміт рядків у файлі на диску): Визначає максимальну кількість рядків, яку файл `~/.bash_history` може містити після завершення сесії. Коли оболонка завершує роботу, функція `history_truncate_file()` перевіряє фізичну кількість рядків на диску, відраховує останні `HISTFILESIZE` записів і відсікає стару частину файлу. Якщо у файлі зберігаються часові мітки, кожен логічний запис займає два рядки, тому реальна кількість збережених команд дорівнюватиме `HISTFILESIZE / 2`.

```
Співвідношення місткості шарів:
[ Оперативна пам'ять процесу ] ── HISTSIZE=5000 ──► 5 000 активних команд
[ Файл ~/.bash_history на диску ] ── HISTFILESIZE=20000 ──► 20 000 збережених рядків
```

### Багаторядкові команди: cmdhist та lithist

В інтерактивній роботі користувачі часто вводять складні багаторядкові конструкції: цикли `for`, умовні блоки `if` або визначення функцій. Bash надає дві додаткові опції ядра оболонки (`shopt`) для контролю їхнього представлення:

* `shopt -s cmdhist`: Увімкнено за замовчуванням. Bash намагається перетворити багаторядкову команду на єдиний рядок історії, автоматично вставляючи крапки з комою `;` у місцях перенесення рядків. Це дозволяє викликати весь цикл однією командою зі списку.
* `shopt -s lithist`: Працює лише у зв'язці з `cmdhist`. Замість заміни перенесень рядків на крапки з комою, оболонка зберігає команди у файлі історії з буквальними символами нового рядка `\n`. Під час навігації стрілками вся структура коду розгортається у багаторядковому буфері редагування точно в тому вигляді, як її було набрано.

### Формат часових міток: HISTTIMEFORMAT

За замовчуванням історія зберігає лише сирий текст команди. Це унеможливлює точний ретроспективний аналіз інцидентів, оскільки інженер не може визначити, коли саме було виконано деструктивну дію.

Встановлення змінної `HISTTIMEFORMAT` активує фіксацію часу в системі:

```bash
export HISTTIMEFORMAT="%F %T "
```

Коли ця змінна не є порожньою, бібліотека історії перемикається в режим розширеного запису:

1. **У пам'яті**: Під час створення структури `HIST_ENTRY` поле `timestamp` заповнюється поточним системним часом Unix через виклик `time(NULL)`.
2. **На диску**: Перед самим текстом команди у файл `~/.bash_history` записується окремий рядок-коментар із префіксом `#` та числовим значенням секунд від початку епохи Unix (Unix Epoch, 1 січня 1970 року):

```
#1724589001
git status
#1724589015
make -j8
```

Під час зчитування файлу `read_history()` парсер перевіряє перший символ кожного рядка. Якщо рядок починається з символу `#`, за яким ідуть виключно цифри, значення інтерпретується як мітка часу для наступної за ним команди. Якщо користувач ввів звичайний коментар (наприклад, `# backup database`), парсер розпізнає нечислові символи й трактує його як текст команди. Під час виконання вбудованої команди `history` рядок формату передається у функцію C-бібліотеки `strftime()`, формуючи зрозуміле представлення дати й часу:

```
$ history 3
 1042  2026-08-25 15:30:01 git status
 1043  2026-08-25 15:30:15 make -j8
 1044  2026-08-25 15:30:42 ./app test
```

### Фільтрація дублікатів та пробілів: HISTCONTROL

Змінна `HISTCONTROL` задає бітову маску поведінки оболонки перед передачею введеного рядка до функції `add_history()`:

* `ignorespace`: Рядки, що починаються з одного або кількох символів пробілу чи табуляції, не додаються до списку історії взагалі.
* `ignoredups`: Запобігає збереженню команди, якщо вона повністю ідентична безпосередньо попередній виконаній команді (`line[N] == line[N-1]`). Якщо користувач виконає `ls`, потім `pwd`, а потім знову `ls`, збережуться всі три записи, оскільки дублікати не були послідовними.
* `ignoreboth`: Зручне скорочення для комбінації `ignorespace:ignoredups`.
* `erasedups`: Найагресивніший режим фільтрації. Перед додаванням нової команди оболонка перебирає весь активний масив `the_history`, знаходить усі попередні випадки входження цього самого рядка у будь-якій позиції історії, видаляє їх із пам'яті, зміщує елементи масиву та записує команду в кінець списку. Це гарантує, що кожна унікальна команда представлена у пам'яті лише один раз у позиції її найостаннішого виклику.

### Маски ігнорування: HISTIGNORE

Змінна `HISTIGNORE` визначає список шаблонів підстановки (`glob`), розділених двокрапками, при збігу з якими команда ігнорується:

```bash
export HISTIGNORE="ls:ll:bg:fg:history*:exit:[ ]*"
```

Під час обробки кожного рядка функція фільтрації порівнює його з кожним шаблоном зі списку за допомогою системної функції `fnmatch()`. Якщо команда збігається хоча б з однією маскою (наприклад, `history -c` підпадає під маску `history*`), вона негайно відкидається і не потрапляє ні до пам'яті, ні у файл на диску.

## 3. Безпека, конфіденційність та гігієна історії

Файл історії команд є однією з головних цілей під час аудиту безпеки та несанкціонованого підвищення привілеїв у системі. Системні інженери регулярно вводять команди, що містять секрети: ключі API, паролі до баз даних, маркери доступу (Bearer tokens) утиліти `curl` або змінні середовища із закритими ключами SSH.

*Конвеєр обробки введеного рядка: розкриття історії виконується найпершим, після чого фільтри HISTCONTROL/HISTIGNORE вирішують долю запису в пам'яті.*

### Запобігання витоку секретів

Для гарантування безпеки робочого середовища застосовують кілька рівнів захисту:

1. **Використання префікса пробілу (`HISTCONTROL=ignorespace`)**: Найпростіший спосіб запобігти збереженню чутливої команди — ввести перед нею пробіл:
   ```bash
   $  export AWS_SECRET_ACCESS_KEY="AKIAIOSFODNN7EXAMPLE"
   ```
   Якщо прапорець `ignorespace` увімкнено, рядок виконається процесом оболонки, але функція `add_history()` буде проігнорована.
2. **Глобальні патерни маскування (`HISTIGNORE`)**: Додавання патернів `*PASSWD*`, `*SECRET*`, `*TOKEN*`, `export *` автоматично блокує збереження команд, що містять характерні ключові слова.
3. **Тимчасове вимкнення історії**: Команда `set +o history` тимчасово вимикає функцію збереження історії для поточної сесії. Після виконання чутливих дій функцію можна повторно активувати викликом `set -o history`.
4. **Ефемерні сесії через HISTFILE**: Встановлення порожнього шляху або псевдопристрою `/dev/null` повністю забороняє запис історії на диск:
   ```bash
   $ export HISTFILE=/dev/null
   ```

> 🔧 **Межа захисту: історія проти аргументів процесу.** Важливо пам'ятати, що приховування команди з файлу історії не захищає секрети від локальних процесів під час їхнього виконання. Коли програма запускається системним викликом `execve()`, її аргументи копіюються у початковий стек процесу та стають доступними через псевдофайлову систему `/proc/[pid]/cmdline` для будь-якої іншої утиліти (наприклад, `ps aux`). Для повної конфіденційності секрети слід передавати через змінні середовища або стандартний потік введення (stdin).

### Аудит ядра проти історії оболонки

Історія команд не є надійним засобом аудиту безпеки, оскільки користувач із правами запису може модифікувати або очистити власний файл `~/.bash_history`. У промислових середовищах для невідхильного аудиту дій застосовують спеціалізовані інструменти ядра:

* **Модуль pam_tty_audit**: Дозволяє фіксувати кожен натиснутий користувачем символ безпосередньо на рівні драйвера термінала ядра через стек PAM, записуючи події в системний журнал аудиту.
* **Підсистема auditd**: Фіксує системні виклики `execve()` та `execveat()` із повними масивами аргументів, унеможливлюючи приховування команд пробілами чи маніпуляціями з `HISTFILE`.

### Очищення та локальне редагування

Якщо конфіденційний рядок уже потрапив до історії, необхідно видалити його як з оперативної пам'яті процесу, так і з постійного носія:

* `history -d <номер_рядка>`: Видаляє окремий запис із внутрішнього масиву `the_history`. У Bash 5.0+ підтримується відлік із кінця: `history -d -1` миттєво видаляє останню виконану команду.
* `history -c`: Повністю очищає буфер пам'яті поточної оболонки. Проте слід пам'ятати: `history -c` видаляє записи лише в оперативній пам'яті процесу. Якщо попередні сесії вже зберегли дані у `~/.bash_history`, файл на диску залишиться незмінним, доки його не буде примусово перезаписано командою `history -w` або очищено утилітою `shred ~/.bash_history`.

Права доступу до файлу історії повинні обмежувати читання іншими користувачами системи. Стандартна конфігурація вимагає встановлення прав `chmod 600 ~/.bash_history`, що забороняє читання та запис для групи та інших облікових записів (UID/GID). Для аудиту змін можна налаштувати розширені атрибути файлової системи (chattr): прапорець `chattr +a ~/.bash_history` забороняє перезапис або скорочення файлу, дозволяючи виключно дописування нових рядків у режимі append.

## 4. Синтаксис розкриття історії (History Expansion)

Розкриття історії — це механізм символьної підстановки попередніх команд або окремих слів, запозичений з оболонки C-Shell (`csh`). Символ знака оклику `!` є метасимволом, що запускає процес вибірки.

> 🔧 **Місце в конвеєрі виконання.** Розкриття історії виконується **найпершим кроком** обробки командного рядка — до розкриття змінних `$VAR`, підстановки результатів команд `$(...)`, розділення слів (word splitting) та обробки лапок. Через це подвійні лапки `"echo !foo"` не захищають знак оклику від розкриття. Повне екранування досягається лише одинарними лапками `'echo !foo'` або зворотним слешем `\!`. Якщо історія в скриптах або неінтерактивних сеансах не потрібна, її вимикають командою `set +H` (або `set +o histexpand`).

Повний вираз розкриття складається з трьох елементів: **Селектор події** + **Селектор слова** + **Модифікатор**.

### Селектори подій (Event Designators)

Селектор події вказує, який саме рядок з історії обирається:

* `!!` (подвійний знак оклику): Вибирає попередню виконану команду (повний синонім виразу `!-1`). Найвідоміший приклад використання — повторний запуск команди, що завершилася з помилкою прав доступу `Permission denied`:
  ```bash
  $ apt update
  E: Could not open lock file - open (13: Permission denied)
  $ sudo !!
  sudo apt update
  ```
* `!n`: Вибирає команду з абсолютним номером `n` зі списку `history`.
* `!-n`: Вибирає команду, виконану `n` кроків тому.
* `!string`: Знаходить найновішу команду, яка **починається** з текстового префікса `string` (наприклад, `!systemctl` повторить останній виклик керування службами).
* `!?string[?]`: Знаходить найновішу команду, яка містить `string` у **будь-якій частині** рядка.
* `!#`: Представляє весь рядок, набраний у поточному командному рядку до поточної позиції курсора (дозволяє повторити аргумент у межах того самого виклику, наприклад `cp long_file_name.txt /tmp/!#:1.bak`).

### Селектори слів та аргументів (Word Designators)

Селектор слів відділяється від події двокрапкою `:` і витягує конкретні аргументи з вибраного рядка:

* `!$` (останній аргумент попередньої команди): Дозволяє швидко повторно використати створений каталог або переданий файл:
  ```bash
  $ mkdir -p /var/log/custom-service
  $ cd !$
  cd /var/log/custom-service
  ```
* `!^` (перший аргумент попередньої команди): Вибирає аргумент із позицією `1` (одразу після імені самої команди).
* `!:n`: Вибирає аргумент за точним числовим індексом `n` (`!:0` повертає ім'я команди, `!:2` — другий параметр).
* `!*`: Вибирає всі аргументи команди, починаючи від першого (`1`) до останнього (`$`). Корисно для передачі набору файлів іншій утиліті:
  ```bash
  $ ls file1.c file2.c file3.c
  $ git add !*
  git add file1.c file2.c file3.c
  ```
* `!:x-y`: Вибирає діапазон слів від індексу `x` до `y` включно (наприклад, `!:1-2`).
* `!:x*`: Скорочення для вибору слів від індексу `x` до кінця рядка (`x-$`).

### Модифікатори та швидка заміна

Модифікатори додаються через додаткові двокрапки `:` та модифікують виділені текстові фрагменти:

* `:h` (Head): Відкидає останній компонент шляху, залишаючи каталог (еквівалент утиліти `dirname`).
* `:t` (Tail): Відкидає префікс каталогу, залишаючи лише ім'я файлу (еквівалент `basename`).
* `:r` (Root): Відкидає розширення файлу після останньої крапки.
* `:e` (Extension): Залишає виключно суфікс розширення.
* `:p` (Print): Роздруковує сформовану команду в терміналі, додає її в історію, але **не запускає на виконання**. Це критично важливо під час конструювання складних небезпечних операцій (`rm`, `dd`), щоб переконатися у правильності підстановки:
  ```bash
  $ !rm:p
  rm -rf /var/log/service/*
  ```
* `:q` (Quote): Бере виділені слова в лапки, запобігаючи їхньому подальшому розділенню оболонкою.
* `:s/старе/нове/` (Заміна): Замінює перший збіг підрядка. Замість слеша можна використовувати будь-який розділювач (наприклад, `:s#old#new#`).
* `:gs/старе/нове/` (Глобальна заміна): Замінює всі входження підрядка у вибраному рядку.
* `^старе^нове^` (Швидка підстановка): Спеціальний синтаксис виправлення одруківок у попередній команді:
  ```bash
  $ gti status
  bash: gti: command not found
  $ ^gti^git^
  git status
  ```

Повний перелік синтаксичних конструкцій та модифікаторів наведено у вставці [Довідник синтаксису розкриття історії та модифікаторів](root:sys-unix/command-history/api-history-expansion.md).

## 5. Проблема паралельних сесій та синхронізація

Найбільш підступною проблемою стандартної конфігурації Unix-оболонок є стан гонитви (race condition) між незалежними процесами терміналів, запущеними в емуляторах термінала, мультиплексорах `tmux` або вкладках графічного інтерфейсу.

![Конкуренція терміналів та синхронізація через PROMPT_COMMAND](/root/sys/sys-unix/command-history/img/history-session-sync.svg)
*Синхронізація сесій: паралельні процеси оболонки дописують нові рядки у спільний файл history -a та зчитують оновлення history -n перед кожним запрошенням.*

### Механізм втрати історії

За замовчуванням у Bash поведінка збереження визначається такими факторами:

1. Кожен екземпляр оболонки при старті зчитує файл `~/.bash_history` у власний ізольований масив `the_history` у віртуальній пам'яті.
2. Протягом сесії процеси не знають про команди, які виконуються у сусідніх терміналах.
3. Під час закриття сесії оболонка виконує виклик `write_history()`, який за замовчуванням відкриває `~/.bash_history` у режимі перезапису (`O_TRUNC`).

В результаті термінал, який закривається останнім, повністю затирає файл історії на диску своїм власним буфером, безповоротно знищуючи команди, що були записані сесіями, які завершилися раніше.

### Поведінка під час перемикання користувачів (sudo)

Окремим джерелом плутанини в історії є зміна облікового запису. Коли адміністратор виконує `sudo -s`, оболонка суперкористувача успадковує середовище з `HOME=/home/user`, відкриваючи файл звичайного користувача від імені root. Наступні команди зберігаються з правами суперкористувача, змінюючи власника файлу `~/.bash_history` на `root:root` (права `0600`). Після повернення у звичайний сеанс користувач втрачає право запису у власний файл історії (помилка `Permission denied`). Використання повноцінного входу `sudo -i` або `sudo su -` повністю скидає змінну `HOME` до `/root`, гарантуючи ізоляцію файлів журналів.

### Рішення 1: Режим дописування (histappend)

Першим кроком до розв'язання проблеми є активація прапорця `histappend`:

```bash
shopt -s histappend
```

Коли опцію `histappend` увімкнено, під час виходу з оболонки Bash викликає системну функцію `append_history()`, яка відкриває файл із прапорцем ядра `O_APPEND`. Нові команди поточної сесії дописуються в кінець файлу, не знищуючи записи інших терміналів.

### Рішення 2: Миттєва синхронізація через PROMPT_COMMAND

Хоча `histappend` рятує від втрати даних при виході, він не дозволяє використовувати команду, щойно введену в сусідньому вікні `tmux`, доки те вікно не буде закрито. Для організації спільної історії реального часу використовують спеціальну змінну `PROMPT_COMMAND`, яка виконує сценарій оболонки перед кожним виведенням основного запрошення командного рядка (`PS1`).

Існує дві основні інженерні моделі синхронізації:

#### Модель А: Інкрементальне дописування та зчитування нових рядків

```bash
# Додати у ~/.bashrc
shopt -s histappend
export PROMPT_COMMAND="history -a; history -n; ${PROMPT_COMMAND:-}"
```

Як працює цей ланцюг системних викликів:
1. `history -a` (Append): Оболонка визначає, скільки нових команд було введено з моменту останнього запису, відкриває `~/.bash_history` і дописує лише ці нові рядки на диск.
2. `history -n` (Read New): Оболонка перевіряє розмір файлу на диску, зчитує системним викликом `read()` виключно ті рядки, які були додані іншими паралельними процесами, та додає їх у кінець поточного списку в пам'яті.

*Перевага*: Мінімальне навантаження на підсистему вводу-виводу VFS та збереження локального порядку навігації стрілками для поточної сесії.

#### Модель Б: Повна синхронізація зі скиданням буфера

```bash
# Додати у ~/.bashrc
shopt -s histappend
export PROMPT_COMMAND="history -a; history -c; history -r; ${PROMPT_COMMAND:-}"
```

Ця модель працює радикальніше:
1. `history -a`: Дописує нові команди на диск.
2. `history -c` (Clear): Повністю очищає масив пам'яті `the_history` поточного процесу.
3. `history -r` (Re-read): Повністю перечитує весь дисковий файл `~/.bash_history` з нуля.

*Перевага*: Всі термінали мають абсолютно ідентичний наскрізний хронологічний порядок історії. *Недолік*: При великих значеннях `HISTFILESIZE` (понад 50 000 рядків) повторне читання та парсинг файлу перед кожним натисканням Enter може спричиняти помітні мікрозатримки інтерфейсу на повільних накопичувачах або мережевих файлових системах (NFS).

### Синхронізація в оболонці Zsh

В оболонці Zsh проблему паралелізму вирішено на рівні архітектури за допомогою спеціальних опцій ядра оболонки:

```zsh
# Конфігурація ~/.zshrc
HISTFILE=~/.zsh_history
HISTSIZE=10000
SAVEHIST=10000
setopt INC_APPEND_HISTORY        # Дописувати команду у файл негайно після введення
setopt SHARE_HISTORY             # Спільна історія: імпорт нових команд з файлу в реальному часі
setopt HIST_IGNORE_ALL_DUPS      # Видаляти старі дублікати
setopt HIST_SAVE_NO_DUPS         # Не зберігати дублікати у файл
setopt HIST_REDUCE_BLANKS        # Видаляти зайві пробіли
```

Опція `SHARE_HISTORY` у Zsh не просто дописує рядки, а використовує блокування файлів (через системні виклики `fcntl()` або `flock()`) та розширений формат збереження з тривалістю виконання:

```
: 1724589600:2;sudo systemctl restart nginx
```

Тут перше число — це час початку в секундах Unix Epoch, друге число — тривалість виконання команди в секундах, а після крапки з комою зберігається сам текст команди. Оболонка гарантує коректне злиття паралельних потоків без пошкодження структури файлу.

## 6. Інтерактивний пошук та сучасні інструменти навігації

Навігація історією лише за допомогою клавіш «Стрілка вгору» (`previous-history`) та «Стрілка вниз» (`next-history`) стає неефективною, коли розмір журналу перевищує кілька сотень команд.

### Інкрементальний пошук Readline (Ctrl+R)

Стандартним методом швидкого пошуку в GNU Readline є зворотний інкрементальний пошук (`reverse-search-history`), що активується комбінацією клавіш `Ctrl+R`.

```
(reverse-i-search)`docker': docker compose -f docker-compose.prod.yml up -d
```

Під час введення символів бібліотека Readline у режимі реального часу сканує текстові поля `line` структур `HIST_ENTRY` від найновішого запису до найстарішого. Повторне натискання `Ctrl+R` переходить до наступного збігу вглиб історії. Натискання Enter негайно виконує знайдену команду, а клавіша Esc або `Ctrl+G` скасовує пошук, повертаючи початковий рядок.

> 🔧 **Проблема блокування термінала комбінацією Ctrl+S.** Прямий пошук уперед (`forward-search-history`) прив'язаний до комбінації `Ctrl+S`. Проте в терміналах Unix комбінація `Ctrl+S` історично зарезервована драйвером TTY для апаратного/програмного контролю потоку передачі даних (сигнал `XOFF` — зупинка передачі символів). Натискання `Ctrl+S` повністю заморожує вивід термінала, створюючи враження зависання системи (розблокування виконується комбінацією `Ctrl+Q` — `XON`). Щоб дозволити використання `Ctrl+S` для пошуку в історії, необхідно вимкнути програмний контроль потоку в драйвері TTY командою `stty -ixon`.

### Префіксний пошук за початком рядка

Зручною альтернативою `Ctrl+R` є прив'язка стрілок до функцій префіксного пошуку `history-search-backward` та `history-search-forward`. Якщо користувач вводить перші літери команди (наприклад, `dock`) і натискає «Стрілка вгору», оболонка перебирає виключно ті команди з історії, які починаються з цього префікса:

```bash
# Налаштування у ~/.inputrc або ~/.bashrc
bind '"\e[A": history-search-backward'
bind '"\e[B": history-search-forward'
```

### Нечіткий пошук через fzf

Сучасним промисловим стандартом роботи з історією є інтеграція утиліти нечіткого пошуку `fzf` (Fuzzy Finder). Замість строгого пошуку підрядків `fzf` використовує алгоритм розрахунку відстані Левенштейна та вагових коефіцієнтів збігу символів.

Інтеграція реалізується через підміну стандартної прив'язки клавіш Readline:

```bash
# Механізм інтеграції fzf у Bash
bind -x '"\C-r": __fzf_history_custom'
```

Спеціальна функція оболонки `__fzf_history_custom` витягує історію через вбудовану команду `history`, передає потік через конвеєр у процес `fzf`, а результат вибору записує безпосередньо у внутрішні змінні Readline `READLINE_LINE` та `READLINE_POINT`, дозволяючи миттєво відредагувати вибрану команду перед її запуском.

---

Механізм історії команд в операційних системах Unix демонструє класичний інженерний компроміс між швидкістю доступу та надійністю персистентного збереження. Завдяки розумінню взаємодії оперативної пам'яті процесу `HISTSIZE`, довготривалого журналу `HISTFILESIZE`, правил фільтрації `HISTCONTROL` та команд атомарної синхронізації `history -a` / `history -n`, системний інженер отримує повний контроль над збереженням та безпекою своєї щоденної термінальної роботи.
