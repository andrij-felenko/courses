# 📋 Специфікація синтаксису CLI: стандарти POSIX та GNU

Контракт командного рядка — це формальний протокол взаємодії між користувачем, оболонкою операційної системи, сценаріями автоматизації та процесом, що виконується в просторі користувача. Якщо розробники не дотримуються загальноприйнятих правил розбору аргументів, утиліта стає непередбачуваною при роботі в конвеєрах, руйнує обробку спеціальних символів і унеможливлює автоматизовану генерацію довідки. Нижче наведено повну інженерну специфікацію синтаксичних правил POSIX Utility Syntax Guidelines (IEEE Std 1003.1-2017), розширень GNU Coding Standards та правил взаємодії зі стандартними потоками введення-виведення.

## Настанови синтаксису утиліт POSIX (Guidelines 1–13)

Стандарт POSIX.1-2017 (Розділ 12.2 «Utility Syntax Guidelines») визначає тринадцять обов'язкових правил побудови командного рядка для всіх стандартних системних програм. Ці правила гарантують однакову поведінку сотень інструментів у різних середовищах.

### Правило 1: Дозволений набір символів для назви утиліти
Назва виконуваного файлу повинна складатися виключно з літер базового латинського алфавіту та цифр. Рекомендована довжина назви становить від двох до дев'яти символів. Назва не повинна містити пробілів, розділових знаків чи недрукованих керуючих символів, оскільки це ускладнює екранування в командних інтерпретаторах.

### Правило 2: Дефіс як універсальний префікс коротких опцій
Кожна коротка опція вводиться символом дефіса `-`. Історичні варіанти виклику без дефіса (як у ранніх реалізаціях `ps` чи `tar` із версії Unix V7) вважаються застарілими й не повинні впроваджуватися в нових утилітах.

### Правило 3: Односимвольне позначення коротких опцій
Назва короткої опції завжди складається з одного алфавітно-цифрового символу з переліку `[a-zA-Z0-9]`. Використання кількох літер після одного дефіса (наприклад, `-display` або `-geometry` в бібліотеках X11/Xt) суворо заборонено, оскільки це порушує базовий принцип конкатенації прапорців.

### Правило 4: Конкатенація (групування) прапорців без аргументів
Якщо кілька опцій не вимагають передачі значень (прапорці-перемикачі логічного типу), вони можуть довільно групуватися після одного початкового дефіса. Тобто послідовність виклику `-a -b -c` є абсолютно тотожною компактному запису `-abc` або `-cba`.

### Правило 5: Ізоляція опцій з обов'язковими аргументами
Опції, що вимагають передачі аргументів, не можуть склеюватися між собою в один ланцюжок. Якщо опція `-f` приймає ім'я файлу, а опція `-o` — шлях виводу, їх заборонено записувати у вигляді `-fo file out`. Кожна така опція вимагає власного дефіса: `-f file -o out`.

### Правило 6: Роздільний та злитий формат передачі аргументів
Для коротких опцій із параметрами парсер зобов'язаний підтримувати як розділення аргументу пробілом (`-o output.txt`), так і пряме приєднання аргументу до символу опції без пробілу (`-ooutput.txt`). Обидва варіанти мають сприйматися утилітою абсолютно однаково.

### Правило 7: Заборона необов'язкових аргументів для коротких опцій
У стандарті POSIX коротка опція або завжди вимагає значення, або ніколи його не приймає. Необов'язкові аргументи для коротких прапорців заборонені через фундаментальну неоднозначність розбору: у виразі `-o file` неможливо детерміновано визначити, чи `file` є аргументом прапорця `-o`, чи це наступний незалежний позиційний файл.

### Правило 8: Розділення складних списків значень
Якщо один аргумент опції передає кілька сутностей (наприклад, перелік номерів колонок або типів подій), вони повинні розділятися комами (`-f 1,3,5`) або пробілами всередині лапок (`-f "1 3 5"`).

### Правило 9: Фіксований порядок слідування опцій та операндів
Усі опції та їхні аргументи повинні передувати будь-яким позиційним операндам (шляхам до файлів, цільовим назвам). Формальний вигляд команди: `команда [опції] [позиційні_операнди]`. Перший же аргумент, який не починається з дефіса і не є значенням попередньої опції, позначає початок списку операндів.

### Правило 10: Маркер безумовного завершення списку опцій `--`
Аргумент, що складається рівно з двох дефісів `--` без жодних інших символів, позначає остаточне завершення списку прапорців. Після маркера `--` жоден наступний рядок у масиві `argv` не може трактуватися як опція, навіть якщо він починається з дефіса. Це критично для безпечної обробки файлів з іменами на кшталт `-rf` або `-data.txt`.

### Правило 11: Незалежність від порядку розташування неконфліктуючих опцій
Порядок вказання взаємно незалежних прапорців не повинен впливати на результат роботи. Команди `ls -l -a` та `ls -a -l` дають ідентичний вивід. Якщо ж опції взаємовиключні (наприклад, `--verbose` та `--quiet`), діє стандартне правило перевизначення: активним стає значення останнього прапорця в командному рядку.

### Правило 12: Значущість порядку слідування позиційних операндів
На відміну від прапорців, порядок позиційних операндів має принципове значення для логіки виконання. Для команди `cp src dst` операнд `src` є джерелом, а `dst` — приймачем копіювання.

### Правило 13: Позначення стандартних потоків одинарним дефісом `-`
Якщо замість обов'язкового шляху до файлу в командному рядку вказано одинарний дефіс `-`, програма повинна інтерпретувати його як читання зі стандартного вводу `stdin` або запис у стандартний вивід `stdout`.

## Стандарти довгих опцій GNU (GNU Long Options)

Проект GNU розширив синтаксис POSIX, вирішивши проблему браку однолітерних прапорців та значно покращивши читабельність системних сценаріїв:

1. **Синтаксис подвійного дефіса (`--`):** Довгі опції складаються з повних описових слів нижнього регістру, розділених дефісами: `--all`, `--ignore-case`, `--max-depth`.
2. **Формати передачі аргументів:**
   - Для обов'язкових аргументів дозволені як зв'язування знаком рівності (`--output=file.txt`), так і передача окремим токеном (`--output file.txt`).
   - Для опціональних аргументів (*optional argument*) дозволено **виключно зв'язування знаком рівності**: `--color[=WHEN]`. Виклик `--color` використовує значення за замовчуванням `auto`, а виклик `--color=never` передає явний параметр. Роздільний запис `--color never` для опціональних аргументів заборонено стандартом GNU, оскільки `never` буде розцінено як ім'я наступного позиційного файлу.
3. **Підтримка унікальних префіксів:** Парсер `getopt_long` дозволяє вводити скорочені префікси довгих опцій, якщо вони однозначно вказують на конкретну дію (наприклад, `--verb` замість `--verbose`). Проте в довговічних скриптах завжди слід вказувати повне ім'я опції, щоб уникнути збоїв при додаванні нових параметрів у майбутніх версіях утиліти.
4. **Перестановка аргументів (*Argument Permutation*):** Бібліотека `glibc` за замовчуванням дозволяє користувачеві вказувати опції після позиційних аргументів: `grep pattern file1.txt -i file2.txt`. Парсер GNU динамічно модифікує масив `argv`, переміщуючи прапорець `-i` на початок. Цю поведінку можна вимкнути змінною оточення `POSIXLY_CORRECT=1`.

## Контракт системних потоків та кодів завершення

Надійна інтеграція утиліти в конвеєри операційної системи вимагає дотримання суворих правил маршрутизації інформаційних потоків і формування кодів виходу (*exit status*):

| Сценарій запуску програми | Цільовий потік виводу | Код повернення | Інженерне обґрунтування |
|---|---|---|---|
| Явний виклик `--help` або `-h` | `stdout` | `0` | Запит довідки є успішною штатною операцією. Вивід повинен передаватися в пейджер або фільтр: `cmd --help \| less`. |
| Явний виклик `--version` або `-V` | `stdout` | `0` | Отримання версії використовується автоматизованими системами моніторингу та пакетними менеджерами. |
| Помилка синтаксису прапорців (невідомий ключ) | `stderr` | `2` | Помилка конфігурації виклику. Друкується коротка діагностика та рядок: `Try 'cmd --help' for more information.`. Повний `--help` не друкується, щоб не засмічувати журнал термінала. |
| Відсутність обов'язкового аргументу опції | `stderr` | `2` | Помилка валідації CLI. Виводиться діагностика в потік помилок `stderr`. |
| Помилка вхідних даних (файл не знайдено, доступ заборонено) | `stderr` | `1` (або `> 0`) | Помилка середовища виконання при коректно розібраних опціях командного рядка. |

### Буферизація стандартних потоків введення-виведення

При розробці системних утиліт необхідно враховувати режими буферизації стандартної бібліотеки C (`glibc` / `musl`):
- Якщо `stdout` підключено до термінала (`isatty(STDOUT_FILENO) == true`), потік працює в режимі порядкової буферизації (*line buffered*). Кожен символ нового рядка `\n` негайно скидає буфер на екран.
- Якщо `stdout` переспрямовано у файл або канал (`pipe`), потік автоматично перемикається в режим повної буферизації (*fully buffered*) з розміром блоку 4 КБ або 8 КБ. Це максимізує швидкість передачі даних у конвеєрах, але може затримувати появу записів у реальному часі.
- Потік діагностики `stderr` **завжди є небуферизованим** (*unbuffered* або *line buffered*), що гарантує негайний запис аварійних повідомлень на диск чи екран навіть при раптовому аварійному завершенні процесу (`abort()` або `SIGSEGV`).
