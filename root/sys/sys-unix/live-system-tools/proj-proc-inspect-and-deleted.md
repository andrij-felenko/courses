# ⚙️ Практикум: інспекція /proc, розрахунок метрик та виявлення видалених файлів

На виробничому сервері дисковий простір розділу з логами раптово падає до нуля: моніторинг б'є на сполох про системну помилку `ENOSPC` (No space left on device), а черговий інженер виконує `rm /var/log/app.log`, намагаючись швидко звільнити 80 ГБ. Утиліта `ls` підтверджує, що файлу більше немає в каталозі, а `du -sh /var/log` показує лише кілька мегабайтів. Проте системний виклик `df -h` продовжує показувати 100% заповнення розділу, і жоден новий запис не може бути здійснений на диск. Сервіс продовжує утримувати відкритий файловий дескриптор, записуючи дані в невидиму іноду, дискові блоки якої заблоковані на рівні ядра.

Для локалізації та автоматизованого усунення таких критичних аварій потрібен спеціалізований інструмент системного аудиту. Цей практикум розбирає побудову низькорівневого інспектора процесів мовами C та C++, який сканує псевдофайлову систему `/proc`, аналізує метрики задач у `/proc/[pid]/stat`, виявляє видалені, але відкриті дескриптори у `/proc/[pid]/fd/` з міткою `(deleted)`, оцінює реальний обсяг заблокованих дискових блоків та інспектує відображення пам'яті `/proc/[pid]/maps` для знаходження застарілих виконуваних модулів після системних оновлень.

## 1. Архітектура VFS та механіка блокування видалених файлів

Щоб зрозуміти, чому видалений файл продовжує споживати фізичні блоки накопичувача, необхідно простежити взаємодію трьох ключових структур ядра Linux на рівні віртуальної файлової системи (Virtual File System, VFS): елемента каталогу (`struct dentry`), індексного дескриптора (`struct inode`) та відкритого файлового об'єкта (`struct file`).

### Як ядро формує символічні посилання у /proc/[pid]/fd/

Каталог `/proc/[pid]/fd/` є динамічним вузлом псевдофайлової системи `procfs`. Він не зберігається на блоковому пристрої, а генерується ядром «на льоту» під час звернення користувацького процесу:

1. Коли діагностична утиліта виконує системний виклик `opendir()` та `readdir()` на шляху `/proc/[pid]/fd/`, обробник `procfs` звертається до структури ядра `task_struct`, яка описує цільовий процес.
2. Через покажчик `task->files` ядро переходить до таблиці дескрипторів `struct files_struct` та витягує масив відкритих файлів `fdtable`.
3. Для кожного зайнятого числового індексу дескриптора (0, 1, 2, 3 тощо) ядро повертає запис каталогу, який веде до відкритого об'єкта `struct file`.
4. Коли програма виконує системний виклик `readlink()` на дескрипторному файлі (наприклад, `/proc/4821/fd/3`), внутрішня ядерна функція `proc_fd_link()` викликає VFS-функцію `d_path(&file->f_path, buffer, buflen)`.
5. Функція `d_path()` рекурсивно піднімається вгору деревом записів каталогів `struct dentry` до кореня точки монтування, склеюючи повний абсолютний шлях до файлу на файловій системі.

### Розрив зв'язку (unlink) проти звільнення блоків: чому розходяться df та du

У файлових системах POSIX (ext4, XFS, Btrfs) операція «видалення» файлу насправді є операцією розриву зв'язку — системним викликом `unlink()`:

```text
[Виконання команди rm /var/log/app.log]
1. Системний виклик unlink() видаляє запис dentry з хеш-таблиці каталогу.
2. Лічильник жорстких посилань іноди зменшується: inode->i_nlink = 0.
3. Елемент dentry отримує прапорець d_unhashed(dentry) = true.
4. Файл зникає з виводу ls та дерева пошуку утиліти du.

[Перевірка умов звільнення дискових блоків]
Умова вивільнення екстентів: (inode->i_nlink == 0) && (file->f_count == 0)
- Якщо процес утримує FD відкритим: file->f_count > 0.
- Драйвер файлової системи НЕ викликає ext4_truncate / xfs_inactive.
- Усі фізичні дискові блоки залишаються алокованими в бітовій мапі суперблока.
```

Коли утиліта `readlink()` викликає `d_path()` для відкритого файлу, у якого `d_unhashed(dentry)` є істинним або `i_nlink == 0`, функція ядра автоматично дописує в кінець рядка суфікс `" (deleted)"`.

Це пояснює конфлікт інструментів:
- **Утиліта `du` (Disk Usage):** Виконує рекурсивний обхід дерева каталогів за допомогою викликів `fstatat()` або `lstat()`. Оскільки зв'язок у каталозі розірвано, `du` не може знайти файл і не враховує його розмір.
- **Утиліта `df` (Disk Free):** Виконує системний виклик `statvfs()`, який опитує суперблок файлової системи. Суперблок відстежує глобальні лічильники виділених та вільних блоків, у яких заблоковані екстенти продовжують числитися як зайняті.

### Алгоритмічний конвеєр інспектора

Щоб автоматизовано виявити всі приховані витоки дискової пам'яті, утиліта реалізує чотириетапний алгоритмічний конвеєр:

1. **Ітерація простору задач:** Обхід кореневого каталогу `/proc` системним викликом `opendir()`. Фільтрація записів, назви яких містять виключно цифри (ідентифікатори процесів TGID/PID).
2. **Розбір метаданих задачі (`/proc/[pid]/stat`):** Виділення імені виконуваного файлу `comm` з урахуванням довільних символів та дужок, визначення стану процесу (`state`) та перевірка на наявність завислих процесів у стані дискового сну (`TASK_UNINTERRUPTIBLE`, стан `D`).
3. **Сканування дескрипторів (`/proc/[pid]/fd/`):** Зчитування символічних посилань усіх відкритих дескрипторів процесу за допомогою `readlink()` та фільтрація цільових рядків за наявністю суфікса ` (deleted)`.
4. **Вимірювання заблокованого простору:** Виконання системного виклику `stat()` безпосередньо на дескрипторному вузлі `/proc/[pid]/fd/[N]` для отримання логічного розміру файлу (`st_size`) та фізично зайнятих блоків (`st_blocks`).

## 3. Детальний аналіз реалізацій та крайових випадків

Обидві реалізації проєкту оптимізовані для безпечної роботи на високонавантажених живих серверах, де помилки парсингу чи невдалі системні виклики не повинні призводити до аварійного завершення діагностики.

### Фільтрація каталогів PID та захист від гонок зникнення задач (ENOENT)

Каталог `/proc` містить як числові каталоги процесів, так і загальносистемні псевдофайли та службові підкаталоги (`sys/`, `net/`, `fs/`, `bus/`, `driver/`, `self/`, `thread-self/`).

У реалізації C фільтрація виконується функцією `is_numeric_dir()`, яка перевіряє кожен символ імені через `isdigit((unsigned char)*name)`. У версії C++ цей самий інваріант перевіряється алгоритмом `std::all_of(filename.begin(), filename.end(), ::isdigit)`.

Головна пастка під час обходу `/proc` — це стан гонки (Race Condition) зникнення процесу. Між моментом, коли функція `readdir()` повернула числовий запис PID, та моментом виклику `fopen()` або `opendir()` на каталозі дескрипторів, процес може завершити виконання або бути знищеним планувальником. У цьому разі системний виклик `open()` повертає помилку `ENOENT` (No such file or directory).

Обидві програми розглядають повернення `NULL` у C або невдале відкриття потоку `std::ifstream` у C++ як штатну ситуацію, миттєво пропускаючи неіснуючий процес без зупинки сканування.

### Парсинг поля comm у /proc/[pid]/stat через граничні дужки

Друге поле файлу `/proc/[pid]/stat` містить назву команди `comm`, укладену в круглі дужки. Процес може встановити будь-яку довільну назву через системний виклик `prctl(PR_SET_NAME, "worker (db) #1")`. Якщо назва містить пробіли або додаткові круглі дужки, прямий розбір рядка за допомогою `sscanf(buffer, "%d %s %c ...")` неминуче зміщує позиції всіх наступних колонок і призводить до зчитування спотворених числових даних.

Алгоритм парсингу розв'язує цю проблему пошуком крайніх меж: у C функціями `open_paren = strchr(buffer, '(')` та `close_paren = strrchr(buffer, ')')`, а в C++ методами `openParen = line.find('(')` та `closeParen = line.rfind(')')`.

Увесь текст між цими двома покажчиками гарантовано належить назві `comm`. Числові поля стану процесу (`state`), ідентифікатора батька (`ppid`), лічильників процесорного часу (`utime`, `stime`) та сторінок пам'яті (`rss`) зчитуються функцією `sscanf()` строго зі зміщення `close_paren + 2`, що гарантує 100% стабільність парсингу для будь-яких імен бінарників.

Якщо поле стану задачі дорівнює символу `'D'`, утиліта генерує попередження `[UNINTERRUPTIBLE D-STATE]`. Процеси у стані безперервного сну заблоковані в операціях дискового чи мережевого драйвера (наприклад, завислий NFS-клієнт). Вони не реагують навіть на сигнал `SIGKILL` (`kill -9`) і можуть спричиняти блокування файлових ресурсів на рівні VFS.

### Інспекція дескрипторів та відмінність логічного розміру від фізичних блоків (st_size проти st_blocks)

Для кожного відкритого дескриптора програма формує шлях виду `/proc/[pid]/fd/[FD]` і виконує системний виклик `readlink()` (у C) або `fs::read_symlink()` (у C++). Якщо повернутий рядок містить підрядок `"(deleted)"`, утиліта викликає `stat()` на цьому шляху.

Оскільки VFS автоматично розв'язує символічне посилання на дескриптор безпосередньо до живої структури `struct inode` в оперативній пам'яті ядра, виклик `stat()` повертає актуальні метадані файлу, навіть якщо його вже вилучено з усіх каталогів, а поле `st_size` структури `struct stat` містить реальний розмір заблокованого файлу в байтах.

Під час аналізу заблокованого простору важливо розрізняти два поля структури `struct stat`:
1. **`st_size` (номінальний логічний розмір):** Показує кількість байтів від нульового зміщення до останнього байта файлу.
2. **`st_blocks` (фактично виділені дискові блоки):** Кількість 512-байтних секторів, фізично алокованих на накопичувачі (`st_blocks * 512` байтів).

Ці два значення можуть суттєво відрізнятися у двох випадках:
- **Розріджені файли (Sparse Files):** Якщо процес створив файл і перемістив покажчик запису на велику відстань системним викликом `lseek(fd, 10737418240, SEEK_SET)` (10 ГБ), записавши туди лише 1 КБ даних, ядро створює логічну «дірку» (Hole). Для неї не виділяються дискові блоки. У цьому разі `st_size` дорівнює 10 ГБ, але `st_blocks` становить лише 8 блоків (4 КБ). Реальне блокування диска визначається саме через `st_blocks`.
- **Попередньо виділені екстенти (Preallocated Extents):** Якщо сервер бази даних викликав системний виклик `fallocate()` для резервування простору під майбутній запис, `st_blocks * 512` може значно перевищувати поточний `st_size`.

### Безпечна робота з привілеями: обмеження EACCES та Linux Capabilities

Каталог `/proc/[pid]/fd/` захищений системними правами доступу `0700` і доступний для читання лише власнику процесу (UID) або суперкористувачу `root`. Під час запуску від імені звичайного користувача спроба відкрити каталоги дескрипторів системних демонів (наприклад, `systemd`, `postgres` чи `nginx`) завершиться помилкою `EACCES` (Permission denied).

У реалізації C++ ця поведінка штатно обробляється прапорцем ітератора `directory_options::skip_permission_denied`. Якщо прав недостатньо, ітератор безпечно пропускає дескриптори без аварійного завершення.

Для роботи утиліти в режимі моніторингу без надання повних привілеїв суперкористувача `root` бінарному файлу призначаються точкові Linux Capabilities:

```bash
# Надання прав обходу захищених каталогів та читання символічних посилань процесів
$ sudo setcap cap_dac_read_search,cap_sys_ptrace+ep ./proc_inspector_c
```

- `CAP_DAC_READ_SEARCH` — дозволяє обходити перевірки прав доступу на читання та пошук у каталогах файлової системи (включаючи `/proc/[pid]/fd/`).
- `CAP_SYS_PTRACE` — дозволяє інспектувати деталі процесів інших користувачів через `procfs`.

## 4. Зіставлення з мапами пам'яті (/proc/[pid]/maps): виявлення застарілих бібліотек

Блокування видалених файлів виникає не лише через звичайні файлові дескриптори, але й через файлові відображення пам'яті (Memory Mappings), створені системним викликом `mmap()`.

### Утримання видалених файлів через VMA після оновлення пакетів

Коли адміністратор виконує оновлення системних пакетів на живому сервері (`apt upgrade`, `dnf update` або ручну заміну бінарних файлів), менеджер пакетів розпаковує нові версії динамічних бібліотек (`.so`) та виконуваних файлів.

Менеджер пакетів записує нову версію бібліотеки (наприклад, `/usr/lib/x86_64-linux-gnu/libssl.so.3`) під новим номером іноди, а старий файл від'єднує системним викликом `unlink()`.

Якщо довгоживучий демон (наприклад, веб-сервер, поштовий сервер або брокер повідомлень) був запущений до оновлення, він утримує сторінки старого коду у своєму віртуальному адресному просторі через структури ядерних областей пам'яті `struct vm_area_struct` (VMA).

```text
[Оновлення бібліотеки OpenSSL на живому сервері]
Пакетний менеджер: записує нову libssl.so.3 (inode 819201) -> unlink старої libssl.so.3 (inode 740112).
Демон Nginx:       утримує VMA з vma->vm_file -> стара інода 740112 (i_nlink = 0).
Наслідки:          1. Демон продовжує виконувати старий вразливий код у RAM (вразливість не усунуто!).
                   2. Старий бінарний файл продовжує утримувати дисковий простір та пам'ять.
```

### Структура записів /proc/[pid]/maps та механіка утиліт needrestart / checkrestart

Псевдофайл `/proc/[pid]/maps` відображає всі області віртуальної пам'яті процесу. Якщо файл, відображений у пам'ять через `mmap()`, було видалено з диска, ядро додає до шляху вже знайомий суфікс ` (deleted)`:

```text
7f9b8a200000-7f9b8a250000 r-xp 00000000 08:01 740112   /usr/lib/x86_64-linux-gnu/libssl.so.3 (deleted)
7f9b8a250000-7f9b8a270000 r--p 00050000 08:01 740112   /usr/lib/x86_64-linux-gnu/libssl.so.3 (deleted)
7f9b8a270000-7f9b8a278000 rw-p 00070000 08:01 740112   /usr/lib/x86_64-linux-gnu/libssl.so.3 (deleted)
```

Формат полів у кожному рядку `/proc/[pid]/maps`:
- `7f9b8a200000-7f9b8a250000` — діапазон адрес віртуальної пам'яті (Virtual Address Range).
- `r-xp` — права доступу до сторінок: `r` (read), `w` (write), `x` (execute), `p` (private/copy-on-write) або `s` (shared).
- `00000000` — зміщення (offset) від початку вихідного файлу.
- `08:01` — мажорний та мінорний номери блокового пристрою (старший:молодший номер диска).
- `740112` — номер іноди на файловій системі.
- `/usr/lib/... (deleted)` — шлях до файлу з позначкою видалення.

Системні утиліти діагностики живого сервера на зразок `needrestart` та `checkrestart` сканують псевдофайли `/proc/[pid]/maps` усіх активних процесів. Вони шукають рядки з міткою `(deleted)`, які мають прапорець виконання `x` (`r-xp`) або відповідають сегментам бібліотек. Знайшовши такий процес, утиліта повідомляє адміністратора про необхідність перезапуску конкретного системного сервісу (`systemctl restart <service>`) для застосування виправлень безпеки та звільнення пам'яті.

## 5. Безпечне вивільнення заблокованого простору на живому сервері

Коли інспектор виявив процес, що утримує гігабайти видаленого файлу, виникає практична інженерна задача: звільнити дискові блоки, не зупиняючи критичний виробничий сервіс і не обриваючи активні клієнтські з'єднання.

### Чому створення нового файлу не розв'язує проблему

Типова помилка адміністраторів-початківців полягає у спробі створити новий файл на місці видаленого:
```bash
# Помилкова спроба: створення нового файлу
$ touch /var/log/app.log
$ chmod 0644 /var/log/app.log
```

Команда `touch` створює у каталозі **абсолютно новий** запис `dentry` та виділяє **нову іноду** з іншим номером. Проте працюючий процес уже відкрив старий файл і утримує покажчик на стару структуру `struct file` та стару іноду. Процес продовжує записувати байти у стару невидиму іноду, заблокований простір продовжує зростати, а створений новий файл `/var/log/app.log` залишається порожнім з розміром 0 байтів.

Так само команда `cat /dev/null > /var/log/app.log` не впливає на видалений файл, оскільки вона очищає лише нову іноду, якщо файл уже було розірвано через `unlink()`.

### Пряме усікання іноди через дескриптор (/proc/[pid]/fd/[N])

Єдиним способом прямого звільнення виділених дискових блоків без перезапуску процесу є системний виклик `truncate()` або `ftruncate()` на дескрипторному вузлі процесу в `procfs`:

```bash
# Звільнення дискового простору шляхом усікання утримуваного дескриптора до 0 байтів
$ truncate -s 0 /proc/4821/fd/3
```

Механізм роботи усікання на рівні ядра:
1. Системний виклик `truncate` розв'язує шлях `/proc/4821/fd/3` до відкритої структури `struct file` процесу `PID 4821`.
2. Ядро захоплює семафор блокування іноди `inode->i_rwsem`.
3. VFS звертається до операцій драйвера файлової системи, викликаючи функцію усікання розміру (наприклад, `ext4_truncate()` для ext4 або `xfs_setattr_size()` для XFS).
4. Драйвер файлової системи звільняє всі виділені дискові блоки екстентів, повертає їх у бітову мапу вільного простору суперблока та встановлює `inode->i_size = 0`.
5. Показник вільного місця утиліти `df -h` миттєво збільшується на весь обсяг видаленого файлу.

### Вплив прапорця O_APPEND та утворення розріджених файлів (Sparse Files)

Подальша поведінка запису залежить від того, з якими прапорцями процес відкрив дескриптор:

- **Файл відкрито з прапорцем `O_APPEND` (стандарт для лог-серверів):** За стандартом POSIX, перед виконанням кожного системного виклику `write()` ядро автоматично скидає файлове зміщення до поточного кінця файлу: `file->f_pos = inode->i_size`. Оскільки `i_size` було скинуто до 0, процес негайно починає писати наступний рядок з нульового байта. Логи продовжують писатися без жодних збоїв чи втрат.
- **Файл відкрито без прапорця `O_APPEND`:** Процес зберігає старе значення зміщення `file->f_pos` (наприклад, 40 ГБ). Наступний виклик `write()` запише дані за зміщенням 40 ГБ. Драйвер файлової системи створить **розріджений файл (sparse file)**: від 0 до 40 ГБ утвориться порожня дірка, яка не займає фізичних блоків на диску, а реальні блоки виділятимуться лише під нові дані. Простір залишається звільненим.

### Сигнали ротації логів: обробка SIGHUP та контрольований перезапуск

Щоб уникнути ручного втручання через `truncate`, системні сервіси проєктуються з підтримкою сигналів ротації журналів:

- **Сигнал `SIGHUP` (Signal Hangup) або `SIGUSR1`:** Такі демони, як Nginx, Apache, Rsyslog або Logrotate, мають власний обробник сигналу. Отримавши `SIGHUP` (або `SIGUSR1` для Nginx), демон виконує таку послідовність дій:
  1. Закриває старий файловий дескриптор системним викликом `close(fd)`.
  2. Лічильник посилань `file->f_count` падає до 0.
  3. Оскільки `inode->i_nlink == 0`, ядро остаточно видаляє іноду та звільняє дискові блоки.
  4. Демон повторно викликає `open("/var/log/app.log", O_WRONLY | O_CREAT | O_APPEND, 0644)`, створюючи новий чистий файл на диску.

```bash
# Коректна ротація логів через сигнал без перезапуску сервісу
$ kill -HUP 4821       # або kill -USR1 $(cat /run/nginx.pid)
```

- **Контрольоване завершення `SIGTERM`:** Якщо сервіс не підтримує онлайн-ротацію дескрипторів, надсилається сигнал `SIGTERM` (`kill -15 <PID>`). Процес штатно закриває дескриптори, завершує клієнтські транзакції та звільняє заблоковану іноду під час виклику `exit_group()`.

# Збирання версії на C

### Створення тестового витоку дискового простору

Для емуляції реальної виробничої аварії створимо тестовий процес на мові Python або Bash, який відкриває великий файл на запис і утримує його відкритим після видалення:

```bash
# Запуск фонового процесу, що створює і видаляє відкритий файл
$ python3 -c '
import time, os
f = open("/tmp/leak_test.log", "w")
f.write("A" * 50 * 1024 * 1024) # Запис 50 МБ
f.flush()
os.unlink("/tmp/leak_test.log")   # Видалення файлу з каталогу
print(f"Holding unlinked file in PID: {os.getpid()} on FD: {f.fileno()}")
time.sleep(300)
' &
# [1] 19842
# Holding unlinked file in PID: 19842 on FD: 3
```

### Запуск діагностичного інспектора

Запускаємо скомпільований інспектор з правами читання дескрипторів:

```bash
$ sudo ./proc_inspector_c
```

Зразок виводу програми в терміналі:

```text
=== SCANNING SYSTEM PROCESSES & UNLINKED OPEN FILES ===
[DELETED FILE LEAK] PID: 19842  | Comm: python3         | FD: 3   | Size:   52428800 bytes | File: /tmp/leak_test.log (deleted)
```

Інспектор миттєво локалізував процес `PID 19842`, номер дескриптора `FD 3`, точний розмір утримуваного файлу (50 МБ) та оригінальний шлях з міткою `(deleted)`.

### Онлайн-усунення витоку та підтвердження результату

Виконуємо скидання розміру заблокованої іноди без завершення тестового процесу:

```bash
$ sudo truncate -s 0 /proc/19842/fd/3
```

Повторний запуск інспектора фіксує успішне звільнення простору:

```text
=== SCANNING SYSTEM PROCESSES & UNLINKED OPEN FILES ===
[DELETED FILE LEAK] PID: 19842  | Comm: python3         | FD: 3   | Size:          0 bytes | File: /tmp/leak_test.log (deleted)
```

Розмір заблокованого простору впав до 0 байтів, дискові екстенти повернені файловій системі, а процес продовжує виконуватися без аварійних зупинок.
