- [Системний виклик ioctl](root:sys-unix/ioctl-interface) — канал керування параметрами пристрою та драйвера поза байтовим потоком `read`/`write`.

- [База terminfo](root:sys-unix/terminfo-database) — база можливостей терміналів, рядові та числові можливості екрана (`cols`, `lines`, `smcup`, `rmcup`).
</preknowlist>

Користувач відкриває утиліту `htop` або текстовий редактор `vim`, тягне мишею за правий нижній кут вікна емулятора термінала, і таблиця процесів миттєво перебудовується: додаються нові стовпці, графіки завантаження ядер процесора розтягуються на всю ширину, а інформаційні рядки не ламаються й не з'їжджають. Коли ж користувач натискає клавішу `q`, екран миттєво очищується, повертаючи попередній командний рядок разом із повною історією команд і неушкодженим буфером прокрутки. Але якщо написати власну програму, яка виводить текст у координати `(x, y)` без системної підготовки, і перервати її комбінацією `Ctrl+C` — термінал залишається «мертвим»: натиснуті літери не друкуються на екрані, клавіша Enter переносить курсор униз без повернення до лівого краю, а сам курсор стає невидимим.

Уся ця поведінка тримається на трьох взаємопов'язаних механізмах ядра та термінального емулятора: збереженні геометрії вікна в драйвері TTY, перемиканні між основним та альтернативним екранними буферами й суворому контролі лінійної дисципліни `termios`.

## Механіка геометрії в ядрі: де живе розмір вікна

Фізичний термінал (лат. *terminalis* — кінцевий, прикордонний) був залізним апаратом із фіксованим склом: наприклад, катодно-променева трубка DEC VT100 завжди мала 24 рядки та 80 стовпців. Драйвер послідовного порту в ядрі взагалі не знав розмірів екрана, бо передавав лише потік байтів крізь дріт.

У сучасному середовищі графічний емулятор термінала (Alacritty, xterm, GNOME Terminal) під'єднується до процесів через [псевдотермінал](root:sys-unix/pseudo-terminal). Розмір вікна тепер змінюється мишею або віконним менеджером. Щоб прикладні програми могли дізнатися поточну сітку знакомісць, ядро операційної системи зберігає геометрію (грец. *γεωμετρία* — вимірювання землі) всередині внутрішньої структури драйвера TTY — `struct tty_struct`.

Опис цієї геометрії міститься у структурі `struct winsize`, визначеній у заголовному файлі `<sys/ioctl.h>`:

:::tabs
```c
#include <sys/ioctl.h>

struct winsize {
    unsigned short ws_row;    /* кількість рядків у символьних комірках */
    unsigned short ws_col;    /* кількість стовпців у символьних комірках */
    unsigned short ws_xpixel; /* горизонтальний розмір вікна у пікселях */
    unsigned short ws_ypixel; /* вертикальний розмір вікна у пікселях */
};
```
```cpp
#include <sys/ioctl.h>
#include <cstdint>

// У C++ структура struct winsize доступна через <sys/ioctl.h>
struct TerminalWindowSize {
    std::uint16_t ws_row{0};
    std::uint16_t ws_col{0};
    std::uint16_t ws_xpixel{0};
    std::uint16_t ws_ypixel{0};
};
```
:::

Структура оперує двома вимірами:
1. **Символьна сітка (`ws_row`, `ws_col`):** дискретна кількість рядків і стовпців моноширинного тексту. Саме за цими полями програми розраховують розміри панелей, таблиць і довжину рядків.
2. **Піксельні розміри (`ws_xpixel`, `ws_ypixel`):** фізичний розмір клієнтської області вікна в графічному сервері (X11 або Wayland). Більшість емуляторів заповнюють ці поля, хоча класичні консольні утиліти спираються суто на кількість комірок.

Коли користувач змінює розмір вікна емулятора, графічна програма бере нові піксельні координати вікна, ділить їх на ширину та висоту гліфа поточного шрифту й виконує системний виклик `ioctl(ptmx_fd, TIOCSWINSZ, &ws)` на головному дескрипторі псевдотермінала.

![Шлях зміни розміру термінала від вікна GUI до SIGWINCH і перемалювання TUI](/root/sys/sys-unix/terminal-size-and-modes/img/winsize-kernel-flow.svg)

*Ланцюг подій при зміні розміру вікна: емулятор записує нову геометрію в ядро через TIOCSWINSZ, ядро надсилає сигнал SIGWINCH активному процесу, а програма перечитує розмір через TIOCGWINSZ.*

Ядро Linux отримує запит `TIOCSWINSZ` у функції `tiocswinsz()` підсистеми TTY (`drivers/tty/tty_io.c`). Воно порівнює нові значення з наявними в `tty->winsize`. Якщо хоча б одне поле змінилося, ядро оновлює структуру й надсилає усій групі процесів переднього плану термінала спеціальний сигнал сповіщення — `SIGWINCH`.

Історію переходу від фіксованих екранів VT100 до появи структури `winsize` та сигналу зміни вікна в BSD описано окремо ([історичний контекст SIGWINCH та режимів екрана](root:sys-unix/terminal-size-and-modes/hist-sigwinch-and-alternate-screen.md) — еволюція від 80×24 у 1970-х до 4.3BSD Reno та стандартизації Xterm).

## Отримання та оновлення розмірів: ioctl проти змінних середовища

Прикладна програма (наприклад, текстовий процесор або утиліта моніторингу) зчитує поточний розмір екрана за допомогою виклику [ioctl](root:sys-unix/ioctl-interface) із командою `TIOCGWINSZ` (Get Window Size):

:::tabs
```c
#include <stdio.h>
#include <sys/ioctl.h>
#include <unistd.h>

int main(void) {
    struct winsize ws;
    if (ioctl(STDIN_FILENO, TIOCGWINSZ, &ws) == -1) {
        perror("ioctl(TIOCGWINSZ)");
        return 1;
    }
    printf("Розмір термінала: %d рядків × %d стовпців (%d×%d px)\n",
           ws.ws_row, ws.ws_col, ws.ws_xpixel, ws.ws_ypixel);
    return 0;
}
```
```cpp
#include <iostream>
#include <system_error>
#include <sys/ioctl.h>
#include <unistd.h>

int main() {
    struct winsize ws{};
    if (::ioctl(STDIN_FILENO, TIOCGWINSZ, &ws) == -1) {
        std::error_code ec(errno, std::generic_category());
        std::cerr << "Помилка ioctl: " << ec.message() << '\n';
        return 1;
    }
    std::cout << "Розмір термінала: " << ws.ws_row << " рядків × "
              << ws.ws_col << " стовпців (" << ws.ws_xpixel << "×"
              << ws.ws_ypixel << " px)\n";
    return 0;
}
```
:::

### Чому змінні середовища LINES та COLUMNS ненадійні

У багатьох сценаріях розробники намагаються зчитувати змінні оточення `getenv("LINES")` та `getenv("COLUMNS")`. Це породжує небезпечні помилки через фундаментальну будову процесів Unix.

Змінні середовища передаються процесу **один раз** — під час створення образу програми через системний виклик `execve`. Вони зберігаються у приватному адресному просторі процесу. Коли користувач змінює розмір вікна термінала прямо під час виконання програми:
1. Ядро не має доступу до пам'яті користувацького процесу і не може змінити масив рядків `environ`.
2. Батьківський процес (командна оболонка `bash` чи `zsh`) також не може модифікувати змінні середовища своїх нащадків.
3. Якщо вивід програми перенаправлено через конвеєр (наприклад, `ps | grep ...`), оболонка може взагалі не експортувати `LINES` і `COLUMNS` у дочірній процес.

> 🔧 **Навіщо це.** Єдине джерело правди про геометрію інтерактивного екрана — системний виклик `ioctl(fd, TIOCGWINSZ, &ws)`. Змінні `LINES` та `COLUMNS` використовують виключно як останній запасний варіант (fallback), коли програма працює через специфічний емулятор без емуляції TTY або через послідовний дріт, де драйвер повертає нулі.

Якщо `ioctl` повертає нульові розміри (наприклад, на сирому послідовному порту старої апаратури), надійна програма застосовує такий ланцюжок відкату:
1. Перевірка `ioctl(fd, TIOCGWINSZ, &ws)`: якщо `ws_row > 0` та `ws_col > 0` — використовуємо їх.
2. Перевірка змінних оточення `LINES` та `COLUMNS`.
3. Звернення до бази [terminfo](root:sys-unix/terminfo-database) за числовими параметрами `lines` та `cols`.
4. Стандартне значення за замовчуванням: 80 стовпців на 24 рядки.

### Асинхронний сигнал SIGWINCH

Коли розмір вікна змінюється в процесі роботи, ядро надсилає активному процесу сигнал `SIGWINCH` (Window Change, номер 28). За замовчуванням дія цього сигналу в POSIX — ігнорування (`SIG_IGN`).

Щоб реагувати на зміну геометрії без перезапуску, програма встановлює обробник через `sigaction`:

:::tabs
```c
#include <signal.h>
#include <stdbool.h>

static volatile sig_atomic_t g_window_resized = 0;

static void handle_sigwinch(int sig) {
    (void)sig;
    g_window_resized = 1;
}

void setup_signals(void) {
    struct sigaction sa;
    sa.sa_handler = handle_sigwinch;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    sigaction(SIGWINCH, &sa, NULL);
}
```
```cpp
#include <csignal>
#include <atomic>

inline std::atomic<bool> g_window_resized{false};

extern "C" void handle_sigwinch(int) noexcept {
    g_window_resized.store(true, std::memory_order_relaxed);
}

void setup_signals() noexcept {
    struct sigaction sa{};
    sa.sa_handler = handle_sigwinch;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    ::sigaction(SIGWINCH, &sa, nullptr);
}
```
:::

Через правила безпеки асинхронних сигналів (англ. *async-signal safety*) всередині функції `handle_sigwinch` категорично заборонено викликати `printf`, виділяти пам'ять через `malloc`/`new` чи перебудовувати структури даних. Обробник лише виставляє прапорець `g_window_resized = 1`.

У сучасному Linux ще надійнішим підходом є створення файлового дескриптора сигналів через `signalfd(2)`. Це дозволяє заблокувати `SIGWINCH` у масці процесу й отримувати сповіщення про зміну розміру безпосередньо у головному циклі опитування (`poll`/`epoll`/`select`), що повністю усуває стан перегонів (race conditions).

Повний перелік структур, кодів викликів `ioctl` та параметрів помилок зібрано в [довіднику параметрів розміру та режимів](root:sys-unix/terminal-size-and-modes/api-screen-modes-reference.md).

## Екранні буфери: основний проти альтернативного

Коли ви викликаєте утиліту `ls` або `cat`, текст друкується знизу, зміщуючи попередні рядки вгору. Ці рядки не зникають: вони потрапляють у кільцевий буфер прокрутки (англ. *scrollback buffer*) емулятора термінала. Користувач може піднятися вгору коліщатком миші або клавішами `Shift+PageUp` і переглянути вивід компілятора чи історію команд за останні кілька годин.

Якби повноекранна програма (наприклад, редактор `nano` чи системний монітор `top`) працювала у цьому ж просторі, кожне її перемалювання кадру або вихід залишали б сотні рядків інтерфейсу в історії сеансу, безповоротно затираючи попередні результати роботи.

Для вирішення цієї проблеми кожен сучасний емулятор підтримує два незалежні екранні буфери:
1. **Основний буфер екрана (Primary Screen Buffer):** стандартний робочий простір. Має підключений буфер прокрутки необмеженого або великого розміру (зазвичай 10 000+ рядків).
2. **Альтернативний буфер екрана (Alternate Screen Buffer):** окрема ізольована матриця розміром рівно `ws_row × ws_col`. У ньому **немає історії прокрутки**: будь-які рядки, що виходять за нижню межу, втрачаються або ігноруються.

![Перемикання між основним та альтернативним екранними буферами термінала](/root/sys/sys-unix/terminal-size-and-modes/img/screen-buffers-switch.svg)

*Взаємодія основного та альтернативного буферів: послідовність \e[?1049h зберігає стан курсора і перемикає екран на чистий буфер TUI; послідовність \e[?1049l очищує буфер TUI та повертає вихідний екран оболонки.*

### Керуюча послідовність \e[?1049h та \e[?1049l

Перемикання між буферами виконується за допомогою спеціальних приватних режимів DEC (англ. *DEC Private Modes*), які передаються безпосередньо у потік стандартного виводу:

- **Вхід в альтернативний екран:** `\e[?1049h` (CSI ? 1049 h).
  Ця команда змушує емулятор термінала виконати три послідовні дії:
  1. Зберегти поточні координати курсора, активні кольори та атрибути основного екрана.
  2. Перемкнути внутрішній вказівник кадрового буфера на альтернативну матрицю.
  3. Повністю очистити альтернативний екран і встановити курсор у верхній лівий кут `(1, 1)`.

- **Повернення в основний екран:** `\e[?1049l` (CSI ? 1049 l).
  Емулятор виконує зворотну операцію:
  1. Очищує альтернативний екран, звільняючи тимчасовий кадровий стан.
  2. Перемикає вказівник відображення назад на основний буфер.
  3. Відновлює збережені координати, кольори й атрибути курсора основного екрана.

В результаті командна оболонка користувача виглядає так, ніби повноекранна програма взагалі не запускалася: на екрані залишаються саме ті команди та текст, які були присутні до запуску `vim` чи `htop`.

## Керування курсором та режимами відображення

Окрім перемикання екранних буферів, повноекранний додаток повинен керувати видимістю апаратного курсора (лат. *cursor* — бігун) та режимами адресації комірок.

### Приховування курсора: усунення мерехтіння

Під час рендерингу складного інтерфейсу програма виводить сотні керуючих команд позиціонування (наприклад, `\e[10;5H` для малювання тексту в 10-му рядку, потім `\e[20;1H` для малювання статусної смуги). Якщо курсор залишається видимим, емулятор малює його в кожній проміжній точці між оновленнями кадру. Для ока користувача це виглядає як хаотичне мерехтіння по всьому екрану.

Для запобігання мерехтінню застосовують приватний режим `DECTCEM` (DEC Text Cursor Enable Mode):
- **Сховати курсор:** `\e[?25l` (CSI ? 25 l).
- **Показати курсор:** `\e[?25h` (CSI ? 25 h).

Ідіоматичний патерн рендерингу кадру в TUI:
1. Відправити `\e[?25l` (якщо курсор ще не сховано).
2. Вивести оновлений буфер кадру з усіма кольорами та координатами.
3. Перемістити курсор у позицію активного редагування (наприклад, у рядок введення команди) і надіслати `\e[?25h` лише тоді, коли програма очікує вводу користувача.

### Адресація та очищення комірок

Для точного позиціонування елементів інтерфейсу використовуються базові послідовності стандарту ANSI / ECMA-48:
- `\e[<row>;<col>H` — встановити курсор у рядок `row` та стовпець `col` (відлік ведеться з `1, 1` для лівого верхнього кута).
- `\e[2J` — очистити весь видимий екран.
- `\e[2K` — очистити поточний рядок повністю.
- `\e[0m` — скинути всі атрибути оформлення (колір тексту, фон, жирність, підкреслення).

## Лінійна дисципліна, сирий режим і захист від зламаного термінала

За замовчуванням термінал перебуває в **канонічному режимі** (грец. *κανονικός* — згідний із правилом). Це означає, що драйвер TTY у ядрі накопичує вхідні символи у внутрішньому буфері, дозволяє редагувати рядок клавішею Backspace, автоматично відображає на екрані кожну натиснуту клавішу (`ECHO`) і передає байти у виклик `read()` лише тоді, коли користувач натисне клавішу Enter (`\n`).

Для інтерактивного TUI-додатка канонічний режим непридатний: якщо користувач натискає стрілку вгору або клавішу `j`, програма повинна зреагувати миттєво, без очікування натискання Enter і без друку літери `j` на екрані.

### Перехід у сирий режим (Raw Mode)

Щоб отримати повний контроль над вводом, програма налаштовує параметри лінії через інтерфейс `termios`.

![Життєвий цикл стану термінала: вхід у сирий режим, TUI та гарантоване відновлення](/root/sys/sys-unix/terminal-size-and-modes/img/terminal-mode-transition.svg)

*Етапи життя термінала: захоплення вихідного стану tcgetattr, перемикання у сирий режим та альтернативний буфер, активна робота TUI і гарантоване відновлення налаштувань.*

Класична функція переведення в сирий режим (аналог системної `cfmakeraw`) виконує такі бітові маніпуляції:

:::tabs
```c
#include <termios.h>
#include <unistd.h>

void enable_raw_mode(int fd, const struct termios *orig, struct termios *raw) {
    *raw = *orig;

    /* Вхідні прапорці: вимикаємо перетворення CR у NL, перевірку парності та XON/XOFF */
    raw->c_iflag &= ~(BRKINT | ICRNL | INPCK | ISTRIP | IXON);

    /* Вихідні прапорці: вимикаємо системну пост-обробку виводу (перетворення \n у \r\n) */
    raw->c_oflag &= ~(OPOST);

    /* Прапорці керування лінією: 8 біт на символ */
    raw->c_cflag |= (CS8);

    /* Локальні прапорці: вимикаємо відлуння, канонічний режим та обробку сигналів */
    raw->c_lflag &= ~(ECHO | ICANON | IEXTEN | ISIG);

    /* Керуючі символи: блокуючий read() повертає результат при появі 1 байта */
    raw->c_cc[VMIN] = 1;
    raw->c_cc[VTIME] = 0;

    /* Застосовуємо налаштування зі скиданням вхідної черги */
    tcsetattr(fd, TCSAFLUSH, raw);
}
```
```cpp
#include <termios.h>
#include <unistd.h>

void enable_raw_mode(int fd, const struct termios& orig, struct termios& raw) noexcept {
    raw = orig;

    // Вхідні прапорці: вимикаємо перетворення CR у NL, перевірку парності та XON/XOFF
    raw.c_iflag &= ~(BRKINT | ICRNL | INPCK | ISTRIP | IXON);

    // Вихідні прапорці: вимикаємо системну пост-обробку виводу (перетворення \n у \r\n)
    raw.c_oflag &= ~(OPOST);

    // Прапорці керування лінією: 8 біт на символ
    raw.c_cflag |= (CS8);

    // Локальні прапорці: вимикаємо відлуння, канонічний режим та обробку сигналів
    raw.c_lflag &= ~(ECHO | ICANON | IEXTEN | ISIG);

    // Керуючі символи: блокуючий read() повертає результат при появі 1 байта
    raw.c_cc[VMIN] = 1;
    raw.c_cc[VTIME] = 0;

    // Застосовуємо налаштування зі скиданням вхідної черги
    ::tcsetattr(fd, TCSAFLUSH, &raw);
}
```
:::

Дія `TCSAFLUSH` є критично важливою: вона очікує відправки всіх вихідних даних на екран і **повністю відкидає (скидає)** всі непрочитані символи, які користувач міг випадково набрати до запуску програми. Це гарантує, що старі натискання клавіш не будуть сприйняті TUI як команди.

### Анатомія «зламаного термінала» та патерни відновлення

Якщо програма перевела термінал у сирий режим (`~ECHO`, `~ICANON`, `~OPOST`), увімкнула альтернативний буфер (`\e[?1049h`) і приховала курсор (`\e[?25l`), а потім раптово впала через помилку сегментації (`SIGSEGV`) або була зупинена сигналом `SIGINT` (Ctrl+C), термінал залишається в модифікованому стані:
1. **Відсутність відлуння:** користувач вводить команди в оболонці, але на екрані нічого не відображається.
2. **Зламані переноси рядків («сходинки»):** оскільки прапорець `OPOST` або `ONLCR` вимкнено, символ `\n` більше не переміщує курсор до першого стовпця. Текст починає друкуватися драбинкою.
3. **Невидимий курсор:** користувач не бачить поточної позиції введення.

Для захисту від такого стану надійний додаток будує трирівневий контур безпеки:

1. **Реєстрація обробника через `atexit()`:** функція відновлення реєструється на самому початку роботи й автоматично викликається при будь-якому штатному виклику `exit()` або поверненні з `main()`.
2. **Перехоплення термінальних сигналів (`SIGINT`, `SIGTERM`, `SIGHUP`, `SIGQUIT`):** обробники цих сигналів викликають процедуру відновлення термінала перед завершенням процесу.
3. **Обробка аварійних сигналів (`SIGSEGV`, `SIGBUS`, `SIGABRT`):** навіть у разі критичного збою відновлення скидає термінал, після чого передає керування стандартному обробнику сигналу для створення дампу пам'яті (core dump).

Послідовність скидання термінала завжди виконується у чіткому порядку:

:::tabs
```c
#include <termios.h>
#include <unistd.h>

void restore_terminal(int fd, const struct termios *orig) {
    /* 1. Показуємо курсор, повертаємо основний екран, скидаємо кольори */
    const char reset_seq[] = "\x1b[?25h\x1b[?1049l\x1b[0m";
    (void)write(fd, reset_seq, sizeof(reset_seq) - 1);

    /* 2. Відновлюємо прапорці termios */
    tcsetattr(fd, TCSAFLUSH, orig);
}
```
```cpp
#include <termios.h>
#include <unistd.h>
#include <string_view>

void restore_terminal(int fd, const struct termios& orig) noexcept {
    // 1. Показуємо курсор, повертаємо основний екран, скидаємо кольори
    constexpr std::string_view reset_seq = "\x1b[?25h\x1b[?1049l\x1b[0m";
    [[maybe_unused]] auto _ = ::write(fd, reset_seq.data(), reset_seq.size());

    // 2. Відновлюємо прапорці termios
    ::tcsetattr(fd, TCSAFLUSH, &orig);
}
```
:::

Якщо аварія все ж сталася (наприклад, процес було вбито командою `kill -9`, яку неможливо перехопити), користувач може вручну відновити термінал наосліп, набравши команду:

```sh
stty sane
```

або виконавши команду `reset`, яка повністю скидає стан драйвера та надсилає послідовність апаратного перезапуску термінала.

Повну робочу реалізацію захисного каркаса на C та ідіоматичного класу-вартового `TerminalGuard` на C++23 наведено у [проєкті надійного каркаса TUI](root:sys-unix/terminal-size-and-modes/proj-fullscreen-tui-guard.md) — робочий код обробки resize-подій, signalfd та RAII-відновлення стану.

## Суспенд і відновлення: обробка SIGTSTP та SIGCONT

Коли користувач працює у повноекранному редакторі й натискає комбінацію клавіш `Ctrl+Z`, ядро надсилає активній групі процесів сигнал `SIGTSTP` (Terminal Stop), який за замовчуванням зупиняє виконання процесу й повертає користувача в командний рядок оболонки.

Якщо TUI-додаток дозволяє призупинення (suspension), він зобов'язаний коректно обробити пару сигналів `SIGTSTP` та `SIGCONT`:

1. **Перед зупиненням (`SIGTSTP`):**
   - Відновити оригінальні параметри лінії `termios` (увімкнути `ECHO`, `ICANON`, `OPOST`).
   - Повернутися в основний екранний буфер (`\e[?1049l`) і зробити курсор видимим (`\e[?25h`).
   - Скинути обробник `SIGTSTP` у стан за замовчуванням `SIG_DFL` і повторно надіслати сигнал самому собі через `raise(SIGTSTP)`, щоб ядро дійсно призупинило процес.

2. **Після відновлення (`SIGCONT`):**
   - Процес прокидається після команди `fg` у командному рядку.
   - Повторно перевести термінал у сирий режим через `tcsetattr(fd, TCSAFLUSH, &raw)`.
   - Знову увімкнути альтернативний екран `\e[?1049h` і сховати курсор `\e[?25l`.
   - Заново опитати розмір екрана через `ioctl(fd, TIOCGWINSZ, &ws)` (оскільки користувач міг змінити розмір вікна, поки процес спав у фоні).
   - Повністю перемалювати все вікно програми.

Така двофазна обробка гарантує безшовну інтеграцію TUI-додатків із механізмом керування завданнями (job control) операційної системи Unix.

## Простеження роботи термінала: strace та ftrace

Для діагностики взаємодії програми з терміналом корисним інструментом є `strace`. Запуск редактора або TUI-утиліти з фільтрацією викликів `ioctl` та сигналів дозволяє побачити повний життєвий цикл сеансу:

```sh
strace -e ioctl,signal,write -o term.log vim main.c
```

У лозі чітко простежується послідовність дій:
1. Запит `ioctl(0, TIOCGWINSZ, {ws_row=45, ws_col=160, ...}) = 0` на початку ініціалізації.
2. Серія викликів `ioctl(0, TCGETS, ...)` та `ioctl(0, TCSETSW / TCSETSF, ...)` для конфігурації сирого режиму.
3. Запис послідовності `\33[?1049h\33[?25l` у дескриптор `1`.
4. При перетягуванні вікна — перехоплення сигналу `--- SIGWINCH {si_signo=SIGWINCH, si_code=SI_KERNEL} ---` з наступним повторним викликом `ioctl(0, TIOCGWINSZ, ...)`.
5. При виході — запис `\33[?25h\33[?1049l\33[0m` та повернення початкових налаштувань `TCSETSF`.

Розуміння цієї низхідної механіки дозволяє інженеру створювати стійкі консольні інтерфейси, здатні надійно працювати в будь-якому середовищі — від локального емулятора до віддалених SSH-сесій і термінальних мультиплексорів.
