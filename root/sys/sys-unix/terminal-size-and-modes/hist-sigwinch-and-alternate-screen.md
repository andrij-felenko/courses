# 📜 Від фіксованого скла до динамічного вікна: як народилися SIGWINCH і Alternate Screen

Фізичний відеотермінал DEC VT100, випущений восени 1978 року, мав незмінну катодно-променеву трубку (CRT, англ. *cathode-ray tube*). Його електроніка формувала рівно 24 рядки тексту по 80 символів у кожному (із можливістю перемкнутися на 132 стовпці ціною чіткості знаків). Програми на мейнфреймах і серверах VAX знали цю геометрію наперед: розмір екрана був такою ж апаратною константою машини, як частота мережі живлення. Ядро операційної системи взагалі не зберігало кількість рядків чи стовпців термінала, оскільки послідовний порт (`/dev/tty*`) був лише двостороннім каналом передачі байтів, якому байдуже до розташування літер на склі.

Ситуація змінилася в середині 1980-х років із появою графічних робочих станцій Sun Microsystems, Apollo та графічного сервера X Window System у Массачусетському технологічному інституті (MIT). Емулятор термінала перетворився на звичайне вікно графічного інтерфейсу (англ. *window manager*), розмір якого користувач міг довільно змінювати мишею в будь-який момент.

## Проблема плаваючого вікна та 4.3BSD Reno

Перші емулятори термінала (зокрема `shelltool` у системі SunView та перші версії `xterm` для X11) зіткнулися з тим, що програми продовжували вважати екран 80×24. Коли користувач розтягував вікно на весь монітор (наприклад, 120 стовпців на 50 рядків), текстові редактори `vi` або `emacs` продовжували переносити рядки на 80-й позиції, залишаючи праву половину вікна порожньою. Якщо ж вікно звужували, вивід програм виходив за видимі межі, руйнуючи форматування.

Спроби передавати розмір через змінні середовища `LINES` та `COLUMNS` виявилися глухим кутом: змінні середовища копіюються процесу лише один раз — у момент виклику [execve](root:sys-unix/exec-semantics). Коли користувач тягнув мишею рамку вже запущеного вікна, жоден процес усередині не міг дізнатися про зміну пам'яті свого батька.

Рішення створили інженери Каліфорнійського університету в Берклі (UC Berkeley) під час розробки релізу **4.3BSD Reno** (1990 рік). Вони розширили підсистему терміналів BSD двома речами:
1. Додали в ядро структуру `struct winsize` і два виклики [ioctl](root:sys-unix/ioctl-interface): `TIOCSWINSZ` (Set Window Size) для емулятора, що володіє головним кінцем псевдотермінала, та `TIOCGWINSZ` (Get Window Size) для прикладних програм на підлеглому кінці.
2. Створили новий сигнал ядра — `SIGWINCH` (Window Change, номер 28). Щоразу, коли емулятор викликає `TIOCSWINSZ` із новими розмірами, ядро автоматично надсилає цей сигнал усій групі процесів переднього плану термінала.

Завдяки цьому механізму редактори отримали змогу реагувати на зміну геометрії миттєво, перечитуючи розмір екрана в обробнику сигналу та перемальовуючи інтерфейс.

## Поява Alternate Screen Buffer: від VT100 до DEC Private Mode 1049

Оригінальні апаратні термінали мали лише один кадровий буфер у внутрішній пам'яті RAM. Коли програма очищувала екран (послідовністю `ESC [ 2 J`), попередній текст затирався назавжди.

В емуляторах термінала з'явилася історія прокрутки (англ. *scrollback buffer*), де зберігалися тисячі попередніх рядків сеансу. Проте виник новий конфлікт: коли користувач запускав повноекранний редактор (як-от `vi` або переглядач `less`), він заповнював видиму частину екрана власним текстом. Після виходу з програми цей текст залишався у вікні та забруднював історію прокрутки термінала, зсуваючи команди та результати компіляції далеко вгору.

Розробники `xterm` вирішили цю проблему впровадженням **альтернативного екранного буфера** (англ. *Alternate Screen Buffer*). Емулятор почав тримати в оперативній пам'яті два незалежні масиви комірок:
- **Основний буфер (Primary Screen Buffer):** зв'язаний із кільцевим буфером прокрутки, використовується командною оболонкою (shell).
- **Альтернативний буфер (Alternate Screen Buffer):** окрема плоска сітка без власної історії прокрутки, призначена суто для повноекранних TUI-додатків.

Еволюція керуючих послідовностей для цього перемикання пройшла три етапи:
1. **Режим 47 (`\e[?47h` / `\e[?47l`):** перший варіант у ранніх версіях `xterm`. Він перемикав видимий буфер, але не зберігав координати курсора основного екрана, через що після виходу курсор опинявся у випадковому місці.
2. **Режим 1047 та 1048 (`\e[?1047h` та `\e[?1048h`):** розділення збереження курсора (`1048`) та перемикання буфера з очищенням (`1047`).
3. **Комбінований режим 1049 (`\e[?1049h` / `\e[?1049l`):** стандартизований Едвардом Моєм (Edward Moy) та Томасом Дікі (Thomas Dickey) у 1990-х роках. Послідовність `\e[?1049h` одночасно зберігає позицію курсора основного екрана, перемикає термінал на альтернативний буфер і очищує його. Послідовність `\e[?1049l` очищує альтернативний буфер, повертає термінал до основного екрана та відновлює збережені координати й атрибути курсора.

Сьогодні приватний режим DEC `?1049` підтримується практично кожним емулятором термінала у світі (xterm, GNOME Terminal, Alacritty, Kitty, WezTerm, Windows Terminal, iTerm2), ставши стандартом де-факто для всіх TUI-бібліотек.
