# 📜 Від KVM Device Assignment до VFIO: Еволюція парапрохідності

Історія розвитку парапрохідності (прокидання) периферійних пристроїв у ядрі Linux є яскравим прикладом того, як підсистема ядра пройшла шлях від тимчасових специфічних хаків усередині конкретного гіпервізора до елегантного, універсального та апаратно захищеного фреймворку простору користувача.

---

## 1. Рання ера віртуалізації та поява перших IOMMU (2006–2008)

На світанку апаратної віртуалізації x86 (після появи технологій Intel VT-x та AMD-V у 2005–2006 роках) віртуальні машини функціонували виключно за допомогою програмної емуляції периферійних пристроїв. Гіпервізор KVM та емулятор QEMU відтворювали в пам'яті поведінку класичних PCI-пристроїв, таких як мережевий адаптер `Realtek RTL8139`, `Intel e1000` або IDE-контролер диску. Кожне звернення гостьової системи до регістрів такого пристрою спричиняло вихід у гіпервізор (VM-Exit) — для MMIO через порушення доступу в таблицях EPT/NPT, для портів вводу-виводу через перехоплення інструкцій `in`/`out`, — де програмний код емулятора інтерпретував операцію читання чи запису.

Цей підхід забезпечував високу сумісність, проте ціна продуктивності була високою: накладні витрати на переключення контексту між гостем і хостом нищили пропускну здатність, а затримки операцій введення-виведення зростали на два порядки порівняно з роботою на фізичному залізі. Для високопродуктивних серверних застосувань та мережевих систем спроможність обробляти мільйони пакетів на секунду була недосяжною.

Виробники процесорів усвідомлювали це обмеження й випустили перше покоління апаратних контролерів розмежування пам'яті для периферії:
* **Intel VT-d** (Virtualization Technology for Directed I/O) — специфікацію опубліковано в середині 2000-х, апаратна підтримка прийшла із серверними чипсетами того ж покоління, а перенаправлення переривань (Interrupt Remapping) додали наступні редакції архітектури наприкінці 2000-х;
* **AMD-Vi** (також відома як AMD IOMMU Architecture) — специфікацію опубліковано в другій половині 2000-х, апаратна підтримка з'явилася в серверних чипсетах платформи Opteron.

Поява IOMMU вперше надала апаратному забезпеченню здатність трансляції віртуальних адрес периферійних пристроїв (IOVA) у хостові фізичні адреси (HPA) на рівні системної шини.

## 2. Механізм KVM Device Assignment (`pci-assign`)

Для швидкої інтеграції нової апаратної підтримки розробники ядра Linux створили підсистему **KVM Device Assignment** (у коді ядра це був файл `virt/kvm/assigned-dev.c` усередині `kvm.ko`, а у просторі користувача QEMU — пристрій `-device pci-assign`).

Архітектурно `pci-assign` був тісно інтегрований безпосередньо у модуль ядра `kvm.ko`. Драйвер працював за такою схемою:
1. Застосунок QEMU відчиняв дескриптор `/dev/kvm` і надсилав спеціальний системний виклик `ioctl(KVM_ASSIGN_PCI_DEVICE)`, передаючи адреси PCI шини пристрою (Domain:Bus:Device:Function).
2. Модуль ядра `kvm.ko` шукав пристрій на шині PCI, силоміць відв'язував від нього штатний драйвер ядра Linux і перехоплював контроль над конфігураційним простором PCI.
3. Модуль ядра KVM безпосередньо викликав загальний IOMMU API ядра (`iommu_domain_alloc()`, `iommu_map()`), за яким стояли драйвери Intel VT-d чи AMD-Vi, і будував таблиці трансляції, що відображали гостьові фізичні адреси (GPA) у хостові фізичні (HPA).
4. Переривання INTx та MSI прив'язувалися до внутрішніх векторів гіпервізора KVM для прямої ін'єкції в гостя.

## 3. Критичні вади та обмеження `pci-assign`

Незважаючи на те, що `pci-assign` виконував своє головне завдання — забезпечував високу швидкість передачі даних без емуляції — підхід мав фундаментальні недоліки, які з часом зробили його небезпечним для використання у продакшн-середовищах.

### 3.1. Жорстка монолітна прив'язка до KVM
Драйвер `pci-assign` існував виключно всередині підсистеми KVM. Якщо розробникам потрібно було отримати прямий високошвидкісний доступ до PCI-пристрою з простору користувача *без використання віртуальних машин* (наприклад, для створення високошвидкісних мережевих обробників DPDK або систем зберігання SPDK), `pci-assign` був абсолютно безпорадним. Інші гіпервізори чи користувацькі процеси не мали доступу до його інтерфейсів.

### 3.2. Ігнорування топології PCIe та P2P-атак
Найбільш критична проблема `pci-assign` полягала у повній відсутності аналізу апаратної топології шини PCIe. Драйвер дозволяв прокидати будь-який окремий пристрій або функцію PCI, навіть якщо цей пристрій перебував за PCIe-комутатором (switch) чи мостом без підтримки Access Control Services (ACS).

У такій конфігурації два пристрої (наприклад, прокинута у ВМ відеокарта A та мережева карта B хоста) могли виконувати транзакції Peer-to-Peer (P2P) DMA безпосередньо через комутатор. Оскільки P2P-транзакції локально маршрутизувалися всередині комутатора й **ніколи не досягали Root Complex та IOMMU**, компрометація гостьової віртуальної машини дозволяла зловмиснику через прокинутий пристрій A зчитати або перезаписати пам'ять пристрою B на хості. `pci-assign` не мав жодних механізмів виявлення або запобігання цьому ризику.

### 3.3. Ненадійне керування пам'яттю та ресурсами
Закріплення сторінок оперативної пам'яті (Memory Pinning), яке запобігає витісненню DMA-буферів у файл підкачки `swap`, виконувалося монолітно всередині KVM. Це призводило до складнощів із розрахунком системних лімітів `RLIMIT_MEMLOCK`, частих витоків виділеної пам'яті при некоректному завершенні QEMU та відсутності єдиної підсистеми обліку ресурсів пам'яті між різними пристроями.

## 4. Створення та архітектурна перемога VFIO (Linux 3.6)

Перший варіант нової підсистеми — **VFIO (Virtual Function I/O)** — 2010 року опублікував інженер Cisco Том Лайон (Tom Lyon). Довести її до вигляду, де межею доступу стала IOMMU-група, випало інженерові Red Hat Алексові Вільямсону (Alex Williamson): саме його редакція, зроблена у 2011–2012 роках, увійшла до основного стовбура ядра Linux у релізі 3.6 (вересень 2012 року).

VFIO переосмислив парапрохідність, розділивши відповідальність за взаємодію із залізом на три непорушні принципи:

1. **Повна незалежність від гіпервізора:** VFIO — це універсальний керований інтерфейс ядра для простору користувача. Для VFIO не має значення, хто саме запитує доступ до пристрою — QEMU/KVM, Cloud Hypervisor, запуск DPDK-додатку чи тест периферії. Усі користуються єдиним API через символьні пристрої `/dev/vfio/`.
2. **IOMMU-групи як непорушна межа ізоляції:** Ядро Linux аналізує топологію шини PCIe та наявність ACS. На основі цього ядро формує `IOMMU Groups` — мінімальні апаратні домени ізоляції. VFIO запровадив суворе правило: доступ до пристроїв надається **тільки на рівні всієї IOMMU-групи**. Якщо хоч один пристрій у групі контролюється штатним драйвером хоста, VFIO відхиляє спробу відкрити групу.
3. **Модульний розподіл обов'язків:**
   * `vfio_iommu_type1` опікується виключно трансляцією адрес, закріпленням сторінок пам'яті та програмуванням апаратного IOMMU;
   * `vfio-pci` керує конфігураційним простором PCI, регістрами BAR та сигналізацією переривань;
   * `vfio` надає безпечний контрольний інтерфейс `ioctl` для простору користувача.

Завдяки своїй надійності та безпеці VFIO швидко витіснив застарілий `pci-assign`. У версії ядра Linux 4.12 код `pci-assign` був остаточно вилучений із джерел ядра. Сьогодні VFIO є фундаментом прокидання пристроїв для всієї екосистеми Linux.

## 5. Сучасний стан та еволюція VFIO

Сьогодні підсистема VFIO продовжує розвиватися, адаптуючись до нових апаратних технологій:
* **VFIO Mediated Devices (`vfio-mdev`):** Дозволяє віртуалізувати графічні процесори (NVIDIA vGPU, Intel GVT-g), ділячи один фізичний GPU між багатьма ВМ із збереженням IOMMU-ізоляції;
* **Підтримка PCIe PASID (Process Address Space ID):** Дозволяє пристроям використовувати віртуальний адресний простір процесів без попереднього закріплення всієї фізичної RAM (Shared Virtual Memory — SVM);
* **Інтеграція з CXL (Compute Express Link):** Дозволяє прокидати пристрої з підтримкою кеш-когерентної ко-процесорної пам'яті.
