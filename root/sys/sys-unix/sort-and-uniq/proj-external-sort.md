# Зовнішнє сортування злиттям: повна системна реалізація

Повна інженерна реалізація алгоритму зовнішнього сортування злиттям (англ. *External Merge Sort*) для обробки текстових файлів довільного розміру, обсяг яких значно перевищує доступну оперативну пам'ять процесу.

## Архітектура зовнішнього сортування за дефіциту оперативної пам'яті

Класичні алгоритми внутрішнього сортування — швидке сортування (`qsort()`, Quicksort), сортування купою (Heapsort) або інтроспективне сортування (`std::sort()`, Introsort) — спроєктовані з розрахунку на прямий і довільний доступ до комірок оперативної пам'яті (RAM). Для їхньої роботи весь масив елементів разом із масивом покажчиків повинен одночасно розташовуватися в адресному просторі процесу.

Коли розмір вхідного масиву сягає десятків або сотень гігабайтів на сервері з кількома гігабайтами RAM, пряма спроба виділити пам'ять через системний виклик `malloc()` або оператор `new` призводить до тяжких системних наслідків:
1. **Вимивання сторінкового кешу (Page Cache Thrashing)**: Ядро операційної системи намагається компенсувати дефіцит фізичної пам'яті за допомогою розділу підкачки (swap). Оскільки алгоритми довільного сортування хаотично стрибають між адресами пам'яті для вибору опорних елементів та перерозподілу підмасивів, кожне таке звернення генерує промах сторінки пам'яті (page fault).
2. **Деградація дискової підсистеми**: Швидкість виконання падає на кілька порядків через неперервні блокуючі операції зчитування та запису сторінок swap-розділу на диск.
3. **Аварійне знищення процесу (Out-Of-Memory Killer)**: Якщо підкачка вимкнена або вичерпана, ядро Linux активує механізм OOM-killer, який примусово надсилає процесу сигнал `SIGKILL` (`kill -9`), повністю перериваючи роботу.

Алгоритм External Merge Sort усуває цю проблему за рахунок розділення процесу впорядкування на дві ізольовані системні фази з суворим контролем використання пам'яті: фазу нарізання на відсортовані блоки (серії) та фазу їх багатовходового потокового злиття.

### Бюджет пам'яті та накладні витрати структур даних

Ключовим інженерним завданням при проектуванні рушія є точний облік використаної оперативної пам'яті (англ. *memory accounting*). Задання ліміту пам'яті (наприклад, 4 МБ або 2 ГБ) не означає, що можна просто підсумовувати довжину корисного тексту `strlen(line)`.

Фактичний обсяг споживаної пам'яті складається з кількох компонентів:
- **Корисне навантаження**: байти текстових рядків разом із завершальним нульовим байтом `\0` або символом переведення рядка `\n`.
- **Покажчики адресації**: для кожного рядка утримується покажчик `char*` у внутрішньому динамічному масиві (8 байтів на 64-бітній архітектурі) або структура `std::string` (24–32 байти в C++ залежно від реалізації стандартної бібліотеки, яка містить покажчик на буфер, розмір та місткість для оптимізації малих рядків SSO).
- **Службові заголовки алокатора**: системний розподільник пам'яті (`glibc ptmalloc`) виділяє для кожного окремого блоку `malloc()` службовий заголовок (chunk header) розміром 8–16 байтів та округлює розмір виділення до меж вирівнювання (16 байтів). У результаті динамічне виділення мільйона коротких рядків по 20 байтів може споживати не 20 МБ, а понад 48 МБ фізичної пам'яті.
- **Ємність динамічних масивів**: векторні структури (`char**` або `std::vector`) збільшують свою місткість удвічі при заповненні, створюючи тимчасовий резерв невикористаної виділеної пам'яті.

Реалізація зовнішнього сортування враховує ці накладні витрати на кожному кроці зчитування, гарантуючи, що сумарний розмір порції в RAM не перетне встановлену межу `mem_limit`.

## Фаза 1: розбиття на серії та керування пам'яттю RAM

Перша фаза алгоритму трансформує неструктурований вхідний потік довільного розміру у множину локально впорядкованих файлів фіксованого розміру на диску, які називаються **серіями** або **прогонами** (англ. *runs*).

### Механіка накопичення та сортування в пам'яті

1. **Потокове зчитування**: Процес відкриває вхідний дескриптор (файл на диску або потік `stdin`) і читає дані рядками у фіксований стековий буфер через `fgets()` або `std::getline()`.
2. **Динамічне наповнення**: Кожен прочитаний рядок копіюється в динамічну пам'ять і додається до списку рядків поточного блоку. До лічильника `current_mem` додається фактична довжина рядка разом із накладними витратами покажчика `sizeof(char*)` або структури рядка.
3. **Внутрішнє сортування**: Щойно накопичений обсяг `current_mem` досягає порогу `mem_limit`:
   - Наповнення призупиняється.
   - Масив покажчиків сортується повністю в оперативній пам'яті за допомогою швидкого внутрішнього алгоритму: `qsort()` у мові C або `std::sort()` у мові C++.
   - Важлива деталь: сортуються виключно покажчики на рядки, а не самі текстові байти в пам'яті. Це мінімізує кількість переміщень байтів у RAM і забезпечує найвищу швидкість впорядкування завдяки високій локальності даних у кеші процесора L1/L2.

### Скидання серії на диск та звільнення пам'яті

Відсортований блок рядків скидається на диск у новий тимчасовий файл:
1. Процес формує унікальний шлях до файлу (наприклад, `/tmp/extsort_run_<PID>_<INDEX>.tmp`), використовуючи ідентифікатор поточного процесу `getpid()` та монотонно зростаючий індекс серії.
2. Файл відкривається на запис, і всі рядки послідовно виводяться через буферизований потік введення-виведення.
3. Одразу після запису кожного рядка зайнята ним динамічна пам'ять негайно звільняється викликом `free()` (у C) або очищенням контейнера `buffer.clear()` (у C++).
4. Тимчасовий файл закривається за допомогою `fclose()` або закриттям `std::ofstream`, щоб гарантувати скидання всіх внутрішніх буферів користувацького простору на рівень сторінкового кешу ядра (VFS Page Cache) та зафіксувати метадані файлу на диску.
5. Шлях до створеної серії зберігається у списку активних тимчасових файлів для наступної фази.
6. Лічильники скидаються в нуль, і процес продовжує зчитувати наступну порцію вхідного потоку.

### Обробка залишкового хвоста (Leftover Tail Run)

Коли вхідний потік повністю вичерпується (досягнуто кінця файлу `EOF`), у динамічній пам'яті майже завжди залишається остання порція рядків, обсяг якої менший за `mem_limit`. 

Реалізація обов'язково перевіряє стан буфера після виходу з основного циклу читання: якщо в буфері залишився бодай один рядок, виконується фінальне внутрішнє сортування та скидання на диск останньої, меншої за розміром серії.

У результаті першої фази вхідний файл розміром `N` за ліміту пам'яті `M` перетворюється на множину з `K = ceil(N / M)` незалежно відсортованих тимчасових файлів на файловій системі.

## Фаза 2: K-шляхове злиття через пріоритетну чергу

Друга фаза поєднує всі згенеровані серії в єдиний глобально впорядкований вихідний потік. Замість наївного попарного злиття файлів (яке вимагало б багаторазового перечитування всього масиву з диска), алгоритм застосовує **багатошляхове k-входове злиття** (англ. *K-way merge*), здатне об'єднати всі `K` серій за один єдиний прохід.

### Структура потоку серії (RunStream)

Для одночасного читання кількох серій кожен відкритий тимчасовий файл огортається у спеціальну структуру стану — `RunStream`:

- `file`: відкритий файловий дескриптор `FILE*` (у C) або файловий потік `std::ifstream` (у C++).
- `path`: абсолютний або відносний шлях до тимчасового файлу на диску для подальшого видалення.
- `current_line`: локальний префетч-буфер, що містить поточний активний рядок із цього файлу.
- `is_active`: логічний прапорець, що сигналізує, чи містить потік доступні дані (скидається в `0` при досягненні кінця файлу).

Під час ініціалізації з кожного з `K` тимчасових файлів зчитується рівно один перший рядок. Оскільки кожен файл уже локально відсортовано на першій фазі, цей перший рядок гарантовано є найменшим елементом свого файлу.

### Пріоритетна черга: мін-купа (Min-Heap) та дерево вибування

Для вибору глобально найменшого елемента серед усіх активних файлів на кожному кроці використовується структура даних **мін-купа** (англ. *min-heap*), організована у вигляді двійкового дерева на неперервному масиві покажчиків розміром `K`.

```
Індексація масиву купи:
- Корінь (мінімум): index = 0
- Лівий нащадок:     left = 2 * index + 1
- Правий нащадок:    right = 2 * index + 2
- Батьківський вузол: parent = (index - 1) / 2
```

Інваріант мін-купи гарантує, що рядок у батьківському вузлі завжди лексикографічно менший або дорівнює рядкам у його нащадках: `strcmp(heap[parent]->current_line, heap[child]->current_line) <= 0`.

У C++ для цієї мети використовується стандартний адаптер `std::priority_queue`. Оскільки за замовчуванням він будує макс-купу (повертаючи найбільший елемент через оператор `<`), передача інвертованого компаратора `StreamComparator` з оператором `>` трансформує контейнер у високоефективну мін-купу.

### Потоковий цикл злиття

Основний цикл злиття працює до повного спорожнення купи:

1. **Вилучення мінімуму (`O(1)` читання, `O(log K)` перебудова)**:
   - Корінь купи, що містить потік із найменшим поточним рядком серед усіх `K` серій, вилучається з вершини (`heap_pop()` або `min_heap.pop()`).
   - Останній елемент масиву купи переноситься на місце кореня, після чого запускається процедура просіювання вниз (`heapify_down` або Sift-Down) для відновлення інваріанта купи за час `O(log K)`.
2. **Пряме потокове виведення**:
   - Вилучений мінімальний рядок негайно записується у вихідний потік (`stdout` або цільовий файл). Дані не накопичуються в пам'яті, що забезпечує стабільний потоковий режим роботи з фіксованим споживанням RAM.
3. **Поповнення потоку**:
   - З того самого файлу, звідки надійшов щойно виведений рядок, зчитується наступний запис за допомогою `fgets()` або `advance()`.
   - Якщо новий рядок успішно прочитано: потік повертається в купу через операцію вставки (`heap_push()` або `min_heap.push()`), яка виконує просіювання вгору (`heapify_up` або Sift-Up) за час `O(log K)`.
   - Якщо у файлі досягнуто кінця даних (`EOF`): потік закривається викликом `fclose()` / закриттям `std::ifstream`, його прапорець `is_active` скидається, а розмір купи зменшується на 1. Порожній потік більше не повертається в чергу.
4. **Очищення тимчасових файлів**:
   - Після повного завершення циклу злиття (коли купа стає порожньою) процес ітерує список шляхів тимчасових файлів і видаляє кожен із них системним викликом `unlink()` (у C) або функцією `std::filesystem::remove()` (у C++).

Загальна алгоритмічна складність фази злиття складає `O(N log K)` операцій порівняння, де `N` — загальна кількість рядків, а `K` — кількість сформованих серій. Детальний математичний аналіз кількості дискових I/O операцій за моделлю Аґґарвала–Віттера наведено у супутній статті [Математичний аналіз складності зовнішнього сортування](root:sys-unix/sort-and-uniq/math-external-sort-complexity.md).

## Розбір архітектурних рішень у коді C та C++

### Низькорівнева реалізація мовою C (main.c)

1. **Керування пам'яттю рядків у `generate_runs()`**:
   - Зчитування виконується через `fgets()` у стековий буфер розміром 4096 байтів.
   - Рядки дублюються в динамічну купу за допомогою `strdup()`.
   - Масив покажчиків `lines` динамічно подвоює свій розмір (`lines_cap *= 2`) через виклики `realloc()`, що забезпечує амортизовану складність додавання `O(1)`.
   - Лічильник пам'яті підсумовує довжину рядка та розмір самого покажчика: `current_mem += len + sizeof(char*)`.
2. **Ізоляція та звільнення пам'яті в `write_temp_run()`**:
   - Сортування виконується стандартною функцією `qsort()` із компаратором `compare_strings()`, що викликає швидкий системний `strcmp()`.
   - Під час запису у тимчасовий файл кожен рядок звільняється викликом `free(lines[i])` одразу після виклику `fputs()`. Це гарантує, що пам'ять під рядки повністю повертається системному алокатору перед початком зчитування наступної серії.
3. **Ручна реалізація мін-купи в `MinHeap`**:
   - Масив покажчиків на структури `RunStream*` дозволяє переставляти в купі лише легкі 8-байтні адреси замість копіювання цілих структур або рядків.
   - Функція `heapify_down()` знаходить найменший елемент серед поточного вузла та двох його нащадків і рекурсивно опускає його вниз по дереву при порушенні інваріанта.

### Об'єктно-орієнтована реалізація мовою C++ (main.cpp)

1. **Інкапсуляція стану в класі `ExternalMergeSort`**:
   - Клас інкапсулює параметр обмеження пам'яті `mem_limit_` та надає єдиний публічний метод `sort(std::istream&, std::ostream&)`. Це дозволяє використовувати сортувальник як для файлів на диску, так і для потокових конвеєрів `std::cin` / `std::cout`.
2. **Семантика володіння та RAII**:
   - Структура `RunStream` автоматично відкриває файл у конструкторі та закриває його у деструкторі.
   - Пріоритетна черга зберігає потоки у вигляді розумних покажчиків `std::unique_ptr<RunStream>`. Це унеможливлює випадкове копіювання важких файлових потоків і гарантує детерміноване вивільнення пам'яті при видаленні елементів.
   - Метод `advance()` повертає `bool`, сигналізуючи про наявність наступного рядка, що спрощує логіку оновлення купи в циклі злиття.
3. **Високоефективне введення-виведення**:
   - У функції `main()` викликається `std::ios_base::sync_with_stdio(false)` та `std::cin.tie(nullptr)`. Це вимикає синхронізацію між потоками C++ iostream та класичними буферами C stdio, прискорюючи текстове введення-виведення до швидкості низькорівневих системних викликів.
4. **Кросплатформна робота з файловою системою**:
   - Використання бібліотеки `std::filesystem` дозволяє визначати шлях до системного каталогу тимчасових файлів `fs::temp_directory_path()` незалежно від операційної системи (Linux `/tmp`, Windows `AppData\Local\Temp` тощо) та безпечно видаляти файли через `fs::remove()`.

## Системні виклики ядра, буферизація та каскадне злиття

Під час промислової експлуатації рушія зовнішнього сортування критично важливо враховувати архітектурні обмеження ядра Linux та апаратні характеристики підсистеми введення-виведення.

### 1. Ліміт відкритих дескрипторів файлів (RLIMIT_NOFILE)

Якщо розмір вхідного файлу становить 1 ТБ, а розмір RAM-буфера обмежено 100 МБ, фаза розбиття згенерує `K = 10 000` тимчасових серій.

У стандартній конфігурації ядра Linux ліміт на кількість одночасно відкритих файлових дескрипторів для одного процесу (`ulimit -n` або системний параметр `RLIMIT_NOFILE`) становить **1024** (з яких дескриптори 0, 1, 2 зарезервовані під `stdin`, `stdout`, `stderr`).

Спроба одночасно відкрити всі 10 000 файлів на початку фази злиття неминуче призведе до аварійного завершення функції `fopen()` або конструктора `std::ifstream` з помилкою ядра:

```
EMFILE (Too many open files)
```

#### Каскадне багаторівневе злиття (Cascading Multi-pass Merge)

Для подолання цієї проблеми промислові системи (зокрема утиліта GNU `sort`) реалізують багаторівневе ієрархічне злиття, кероване параметром розміру пакета (`--batch-size`, зазвичай від 16 до 64):

1. Якщо загальна кількість початкових серій `K` перевищує доступний безпечний ліміт відкритих дескрипторів `B_batch` (наприклад, `B_batch = 32`), пряме фінальне злиття не запускається.
2. Процес розбиває множину з `K` серій на групи по `B_batch` файлів.
3. Кожна група зливається через мін-купу в новий проміжний тимчасовий файл вищого покоління (серію 2-го рівня), після чого початкові `B_batch` файлів негайно видаляються з диска.
4. Кількість проміжних файлів зменшується у `B_batch` разів.
5. Процедура повторюється рекурсивно або ітеративно за кілька проходів (`P = ceil(log_B(K))`), доки кількість файлів не стане меншою або рівною `B_batch`. Останній прохід зливає фінальну групу безпосередньо у цільовий вихідний файл або потік `stdout`.

```
Рівень 0 (початкові серії): [run_0] ... [run_31]  [run_32] ... [run_63] ... [run_9999]
                                  │                     │
                                  ▼                     ▼
Рівень 1 (проміжні серії):   [pass1_run_0]         [pass1_run_1]       ... (313 файлів)
                                  │                     │
                                  └──────────┬──────────┘
                                             ▼
Рівень 2 (фінальне злиття):          [відсортований результат]
```

### 2. Буферизація введення-виведення та налаштування setvbuf()

Зчитування та запис даних дрібними порціями по кілька байтів або по одному рядку створюють колосальне навантаження на процесор через неперервні системні виклики `read()` та `write()`. Кожен системний виклик супроводжується перемиканням контексту процесора (User Mode ↔ Kernel Mode), збереженням регістрів та перевіркою прав доступу ядра.

Для мінімізації кількості системних викликів необхідно застосовувати явне налаштування розміру буферів введення-виведення користувацького простору:

:::tabs

@tab C (POSIX setvbuf)
```c
char stream_buffer[64 * 1024]; // 64 КБ буфер
setvbuf(file_ptr, stream_buffer, _IOFBF, sizeof(stream_buffer));
```

@tab C++ (std::filebuf pubsetbuf)
```cpp
char file_buffer[64 * 1024];
std::ifstream stream;
stream.rdbuf()->pubsetbuf(file_buffer, sizeof(file_buffer));
stream.open(path);
```

:::

Виділення буфера розміром від 64 КБ до 1 МБ на кожен відкритий дескриптор узгоджує роботу процесу з розміром сторінок дискового кешу ядра Linux (Page Cache) та оптимізує черги запитів контролерів сучасних SSD/NVMe-накопичувачів завдяки послідовному блоковому зчитуванню (Sequential Read-Ahead).

## Обробка сигналів POSIX та гарантоване очищення тимчасових файлів

Під час сортування великих масивів даних процес створює на файловій системі десятки або сотні тимчасових файлів сумарним обсягом у десятки гігабайтів.

Якщо роботу процесу буде раптово перервано оператором через комбінацію клавіш `Ctrl+C` у терміналі (сигнал `SIGINT`), системним моніторингом (`SIGTERM`), закриттям сесії терміналу (`SIGHUP`) або розривом конвеєра при читанні утилітою `head` (`SIGPIPE`), аварійне завершення без спеціальної обробки призведе до засмічення каталогу `/tmp` гігабайтами залишкових тимчасових файлів.

### Механізм безпечного очищення через sigaction()

Для запобігання витокам дискового простору надійна інженерна реалізація реєструє системний обробник сигналів:

:::tabs

@tab C (POSIX sigaction)
```c
#include <signal.h>
#include <unistd.h>
#include <string.h>

static char **g_temp_files = NULL;
static size_t g_temp_count = 0;

static void emergency_cleanup_handler(int signo) {
    // В асинхронному обробнику сигналів дозволено викликати ЛИШЕ async-signal-safe функції
    if (g_temp_files) {
        for (size_t i = 0; i < g_temp_count; ++i) {
            if (g_temp_files[i]) {
                unlink(g_temp_files[i]); // Системний виклик unlink() є async-signal-safe
            }
        }
    }
    _exit(128 + signo); // Негайне завершення процесу без виклику небезпечних деструкторів
}

void register_signal_handlers(void) {
    struct sigaction sa;
    memset(&sa, 0, sizeof(sa));
    sa.sa_handler = emergency_cleanup_handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESETHAND; // Після першого виклику скидати обробник на системний дефолт

    sigaction(SIGINT, &sa, NULL);
    sigaction(SIGTERM, &sa, NULL);
    sigaction(SIGHUP, &sa, NULL);
    sigaction(SIGPIPE, &sa, NULL);
}
```

@tab C++ (C++20 / POSIX)
```cpp
#include <csignal>
#include <unistd.h>
#include <cstring>
#include <vector>
#include <string>

namespace {
    std::vector<std::string> g_temp_files;

    void emergency_cleanup_handler(int signo) noexcept {
        // В асинхронному обробнику викликаються лише async-signal-safe виклики ядра
        for (const auto& path : g_temp_files) {
            if (!path.empty()) {
                unlink(path.c_str()); // unlink() гарантовано async-signal-safe
            }
        }
        _exit(128 + signo);
    }
}

void register_signal_handlers() {
    struct sigaction sa{};
    sa.sa_handler = emergency_cleanup_handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESETHAND;

    sigaction(SIGINT, &sa, nullptr);
    sigaction(SIGTERM, &sa, nullptr);
    sigaction(SIGHUP, &sa, nullptr);
    sigaction(SIGPIPE, &sa, nullptr);
}
```

:::

> ⚠️ **Асинхронно-сигнальна безпека (Async-Signal Safety)**: Всередині обробника сигналів суворо заборонено викликати функції `malloc()`, `free()`, `printf()` або `exit()`, оскільки вони використовують внутрішні м'ютекси і можуть призвести до взаємного блокування процесу (deadlock), якщо сигнал надійшов під час виконання операції виділення пам'яті. Системний виклик `unlink()` та низькорівневе завершення `_exit()` належать до списку стандарту POSIX `async-signal-safe` і гарантовано виконуються безпечно.

У мові C++ додатковий захист забезпечується ідіомою RAII: при виникненні винятків (`std::bad_alloc`, помилки файлової системи) деструктори керуючих об'єктів автоматично викликають `fs::remove()` під час розкрутки стека (stack unwinding).

## Збірка, запуск, простеження через strace та валідація

### Компільовані команди збірки

Обидва модулі компілюються стандартними компіляторами GCC або Clang з увімкненими прапорцями оптимізації рівня `-O3`:

```bash
# Збірка реалізації мовою C (стандарт C11 / POSIX)
gcc -O3 -std=c11 -Wall -Wextra proj-external-sort/c/main.c -o extsort_c

# Збірка реалізації мовою C++ (стандарт C++20)
g++ -O3 -std=c++20 -Wall -Wextra proj-external-sort/cpp/main.cpp -o extsort_cpp
```

### Генерація тестового набору даних великого обсягу

Для перевірки роботи рушія згенеруємо тестовий текстовий файл із 5 000 000 випадкових числових або рядкових записів загальним обсягом близько 100 МБ:

```bash
# Генерація 5 мільйонів випадкових псевдотекстових рядків через awk
awk 'BEGIN {
    srand();
    for (i = 1; i <= 5000000; i++) {
        printf("record_%08d_value_%04d\n", int(rand() * 10000000), int(rand() * 10000));
    }
}' > dataset_large.txt
```

### Запуск сортування та моніторинг ресурсів

Запустимо зовнішнє сортування з вимірюванням часу виконання та пікового споживання пам'яті утилітою `/usr/bin/time`:

```bash
# Запуск сортування з обмеженням RAM у 4 МБ
/usr/bin/time -v ./extsort_c dataset_large.txt > sorted_c.txt
/usr/bin/time -v ./extsort_cpp dataset_large.txt > sorted_cpp.txt
```

У звіті утиліти параметр `Maximum resident set size (kbytes)` наочно підтверджує, що навіть при сортуванні 100-мегабайтного або 10-гігабайтного файлу процес споживає лише кілька мегабайтів фізичної оперативної пам'яті (відповідно до заданого ліміту `mem_limit`), а не завантажує весь масив у RAM.

### Системне простеження через strace

Щоб побачити життєвий цикл тимчасових файлів, створення серій та їх злиття, запустимо процес під системним трасувальником `strace`:

```bash
strace -e trace=openat,unlink,read,write ./extsort_c dataset_large.txt > /dev/null
```

У системному журналі спостерігаються характерні послідовності викликів ядра:
1. `openat(AT_FDCWD, "/tmp/extsort_run_12345_0.tmp", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3` — створення та відкриття на запис першої відсортованої серії.
2. `write(3, "record_00001234_value_5678\n...", 4096) = 4096` — скидання відсортованого в пам'яті блоку на диск.
3. `close(3)` — завершення запису серії.
4. Повторення циклу створення проміжних серій `run_1`, `run_2`, ..., `run_K`.
5. Послідовне відкриття всіх серій на читання: `openat(AT_FDCWD, "/tmp/extsort_run_12345_0.tmp", O_RDONLY) = 3`, `openat(..., "run_1.tmp", O_RDONLY) = 4`, ...
6. Основний цикл K-way злиття: потокове зчитування блоків через `read(3, ...)`, `read(4, ...)` та прямий запис найменших елементів у вихідний дескриптор `write(1, ...)`.
7. `unlink("/tmp/extsort_run_12345_0.tmp") = 0` — детерміноване видалення відпрацьованих тимчасових файлів після вичерпання їхнього вмісту.

### Валідація коректності результату

Перевірка правильності роботи алгоритму здійснюється за допомогою стандартної утиліти `sort` з прапорцем перевірки `-C` (`--check=silent`):

```bash
# Перевірка правильності лексикографічного впорядкування вихідного файлу
sort -C sorted_c.txt && echo "C реалізація: сортування успішне та коректне!"
sort -C sorted_cpp.txt && echo "C++ реалізація: сортування успішне та коректне!"

# Порівняння результату з еталонним системним sort
LC_ALL=C sort dataset_large.txt > sorted_ref.txt
diff -u sorted_ref.txt sorted_c.txt && echo "Результат 100% ідентичний еталонному GNU sort!"
```

Якщо `sort -C` повертає статус `0` без виводу діагностичних повідомлень, файл повністю та строго впорядковано за зростанням лексикографічного порядку.
