# Математичний аналіз складності зовнішнього сортування

Аналітичний розрахунок часової, просторової та дискової складності алгоритму External Merge Sort у моделі зовнішньої пам'яті Аґґарвала–Віттера (Aggarwal-Vitter External Memory Model).

## 1. Модель зовнішньої пам'яті Аґґарвала–Віттера

Класична модель обчислень із довільним доступом до пам'яті (RAM model) припускає, що звернення до будь-якої адреси виконується за сталий час `O(1)`. Коли розмір масиву даних перевищує фізичний обсяг оперативної пам'яті, це припущення повністю руйнується: звернення до дискового накопичувача (HDD або SSD) вимагає від сотень тисяч до мільйонів тактів процесора на переміщення голівок, очікування обертання пластин або відпрацювання транзакцій flash-контролера.

Для математично точного аналізу алгоритмів обробки великих даних використовують дворівневу модель пам'яті Аґґарвала–Віттера (Alok Aggarwal, Jeffrey Vitter, 1988), яка формалізує передачу інформації між швидкою внутрішньою пам'яттю та необмеженою повільною зовнішньою пам'яттю:

- `N` — загальний розмір вхідного набору даних у байтах (або `n = N / L` елементів, де `L` — середній розмір одного запису чи рядка).
- `M` — обсяг швидкої оперативної пам'яті (RAM), виділений процесу для сортування (`sort -S`). За фундаментальною умовою зовнішнього сортування `M < N`.
- `B` — фіксований розмір блоку введення-виведення (I/O block size / page size), який апаратно або через сторінковий кеш ядра VFS зчитується чи записується за одне дискове звернення.
- `k` — коефіцієнт злиття (fan-in / merge order), тобто кількість незалежних потоків серій, які алгоритм одночасно об'єднує в один потік.

```
+-------------------------------------------------------------+
|                     ПРОЦЕСОР ТА КЕШІ                        |
|                     (L1, L2, L3 Кеші)                       |
+-------------------------------------------------------------+
                              ▲
                              │   Слово за такт O(1)
                              ▼
+-------------------------------------------------------------+
|                ВНУТРІШНЯ ПАМ'ЯТЬ (RAM): M байтів             |
|              Містить ⌊M / B⌋ блоків розміром B              |
+-------------------------------------------------------------+
                              ▲
                              │   Блоковий трансфер розміром B
                              ▼   (I/O операція: сотні тисяч тактів)
+-------------------------------------------------------------+
|                ЗОВНІШНЯ ПАМ'ЯТЬ (ДИСК / SSD): N байтів      |
|              Містить ⌈N / B⌉ блоків розміром B              |
+-------------------------------------------------------------+
```

Вхідний масив займає `⌈N / B⌉` дискових блоків, а внутрішня оперативна пам'ять здатна одночасно вмістити `⌊M / B⌋` блоків. Головною метрикою продуктивності є **I/O складність** (I/O complexity) — сумарна кількість блокових операцій читання та запису між диском і RAM, тоді як кількість процесорних порівнянь є вторинною оцінкою.

Розподіл виділеного бюджету пам'яті `M` під час виконання фаз сортування підпорядковується балансу компонентів:

```
M = M_data + M_structures + M_system

де:
M_data       — буфери введення-виведення блоків даних (k вхідних + 1 вихідний)
M_structures — службові покажчики, вузли дерева злиття та заголовки алокатора
M_system     — внутрішні буфери дескрипторів файлів ядра та бібліотеки stdio
```

## 2. Фаза 1: Генерація серій та аналіз довжини прогону

На першому етапі вхідний потік даних розбивається на локально впорядковані послідовності — **серії** (runs), які записуються у тимчасові файли на диску.

### Стандартне блокове розбиття (Fixed-size Chunking)

Найпростіший підхід завантажує порцію даних обсягом `M` у внутрішню пам'ять, виконує сортування вбудованим алгоритмом (Quicksort або Timsort) і вивантажує готовий відсортований блок на диск.

Кількість сформованих серій `K` дорівнює:

```
K = ⌈N / M⌉
```

Для створення всіх `K` серій алгоритм один раз повністю зчитує весь вхідний потік розміром `N` байтів (`⌈N / B⌉` блоків) і один раз повністю записує `N` байтів відсортованих серій на диск:

```
I/O_phase1 = ⌈N / B⌉ + ⌈N / B⌉
           = 2 · ⌈N / B⌉
```

### Оптимізація: Турнірне сортування заміщенням (Replacement Selection)

Замість фіксованого завантаження блоків розміром `M` Дональд Кнут запропонував алгоритм сортування заміщенням (Replacement Selection), побудований на структурі турнірного дерева вибору або дерева тих, хто програв (Loser Tree), розміром `m = M / L` елементів у пам'яті.

Механізм працює за такими правилами:
1. Буфер пам'яті повністю заповнюється першими `m` елементами вхідного файлу, над якими будується турнірне дерево.
2. Мінімальний елемент дерева `x` вилучається і записується у поточну серію на диску.
3. З вхідного потоку негайно зчитується наступний елемент `y`:
   - Якщо `y ≥ x`, елемент `y` може законно продовжити поточну зростаючу серію. Він поміщається в активне турнірне дерево на місце вилученого `x` із тегом поточної серії `r`.
   - Якщо `y < x`, елемент `y` порушує монотонність поточної серії, оскільки значення, менші за `y`, уже записані на диск. Елемент `y` отримує тег наступної серії `r + 1` і поміщається в дерево як неактивний для поточного прогону.
4. Усі порівняння в дереві ведуться за складеним ключем `(tag, value)`: будь-який елемент із тегом `r` вважається строго меншим за будь-який елемент із тегом `r + 1`.
5. Коли всі `m` позицій дерева набувають тегу `r + 1` (усі активні елементи поточної серії вичерпано), поточна серія на диску закривається. Тег `r + 1` стає активним тегом `r`, створюється новий тимчасовий файл, і генерація наступної серії продовжується без простою пам'яті.

```
Вхідний потік: [7, 3, 9, 2, 8, 1, 5, 4]  (m = 3)

Крок 1: Заповнення дерева (m = 3): [7, 3, 9] (усі тег 1)
        Вихід на диск: 3 (поточний мінімум x = 3).
Крок 2: Читаємо y = 2. Оскільки 2 < 3, елемент 2 отримує тег 2.
        Дерево: [7(тег 1), 2(тег 2), 9(тег 1)]
        Вихід на диск: 7 (x = 7).
Крок 3: Читаємо y = 8. Оскільки 8 ≥ 7, елемент 8 отримує тег 1.
        Дерево: [8(тег 1), 2(тег 2), 9(тег 1)]
        Вихід на диск: 8 (x = 8).
Крок 4: Читаємо y = 1. Оскільки 1 < 8, елемент 1 отримує тег 2.
        Дерево: [1(тег 2), 2(тег 2), 9(тег 1)]
        Вихід на диск: 9 (x = 9).
Крок 5: Читаємо y = 5. Оскільки 5 < 9, елемент 5 отримує тег 2.
        Дерево: [1(тег 2), 2(тег 2), 5(тег 2)]
        УСІ ЕЛЕМЕНТИ МАЮТЬ ТЕГ 2 -> Серію 1 закрито! Згенеровано: [3, 7, 8, 9] (довжина 4 > 3).
        Початок серії 2: вихід 1 (x = 1).
```

### Модель снігоочисника та математичне виведення очікуваної довжини 2M

Чому середня довжина серії при сортуванні заміщенням для рівномірно розподілених випадкових даних становить саме `2M`? Для наочного доведення Кнут запропонував аналогію зі снігоочисником на кільцевій трасі.

#### Неперервна фізична аналогія (Snowplow Analogy)

Уявімо кругову дорогу одиничної довжини `[0, 1]`, на яку з постійною густиною падає сніг. Снігоочисник рухається по колу зі сталою кутовою швидкістю, згрібаючи весь сніг, що лежить перед його відвалом.

1. Місткість відвалу снігоочисника відповідає обсягу оперативної пам'яті `M`.
2. Положення очисника на колі в точці `x ∈ [0, 1]` відповідає поточному значенню ключа, що скидається на диск.
3. Коли очисник починає прохід від точки 0, на дорозі вже рівномірно лежить сніг шаром масою `M`.
4. Поки очисник здійснює один повний оберт від 0 до 1, на дорогу випадає додатковий сніг загальною масою `M_new`.
5. Оскільки сніг падає рівномірно за часом і площею, рівно половина нового снігу випадає на ділянки, які очисник уже проїхав (позаду відвалу), а рівно половина — на ділянки, де очисник ще не був (попереду відвалу).
6. Сніг позаду відвалу залишається лежати до наступного кола (наступна серія з тегом `r + 1`), тоді як сніг попереду відвалу негайно згрібається в поточному колі (поточна серія).
7. За повний оберт очисник збирає:

```
L_run = M_початковий + M_новий_попереду
      = M + (1/2) · M_новий_сумарний
```

Оскільки система перебуває у динамічній рівновазі, маса снігу, зібрана за оберт, дорівнює масі снігу, що випадає за час одного оберту: `M_новий_сумарний = L_run`. Підставляючи це значення:

```
L_run = M + (1/2) · L_run
L_run - (1/2) · L_run = M
(1/2) · L_run = M
L_run = 2M
```

#### Дискретний імовірнісний вивід

Нехай поточний записаний на диск елемент є випадковою величиною `x ∈ [0, 1]`. Кожен новий елемент `y ∈ [0, 1]` є незалежною рівномірною величиною:
- Ймовірність того, що `y ≥ x` (успіх: елемент потрапляє в поточну серію), дорівнює `1 - x`.
- Ймовірність того, що `y < x` (невдача: елемент блокує одну позицію пам'яті до наступної серії), дорівнює `x`.

Оскільки значення `x` монотонно зростає від 0 до 1 під час формування серії, математичне сподівання поточного значення дорівнює `E[x] = 1/2`.

Звідси середня ймовірність потрапляння нового елемента в поточну серію становить:

```
P(успіх) = 1 - E[x]
         = 1 - 1/2
         = 1/2

P(невдача) = E[x]
           = 1/2
```

Серія завершується рівно тоді, коли трапиться `m` подій блокування (усі `m` комірок пам'яті заповняться елементами наступної серії). Кількість успішних елементів до накопичення `m` невдач підпорядковується від'ємному біноміальному розподілу `NB(m, 1/2)`:

```
E[L_run] = m + E[успішних додань]
         = m + m · (P(успіх) / P(невдача)) [властивість від'ємного біноміального розподілу]
         = m + m · ((1/2) / (1/2))          [підстановка ймовірностей]
         = m + m · 1                        [спрощення частки]
         = 2m                               [очікувана кількість елементів у серії]
```

У байтовому еквіваленті середня довжина серії складає:

```
E[L_bytes] = 2M
```

Це скорочує кількість початкових серій рівно вдвічі:

```
K_RS ≈ ⌈N / (2M)⌉
```

#### Поведінка на крайових розподілах вхідних даних

1. **Повністю впорядкований масив (Best Case)**: кожен новий елемент `y ≥ x`, жодна комірка пам'яті не блокується. Генерується **одна єдина серія** довжиною `N` (`K = 1`). Фаза злиття взагалі не потрібна, загальний I/O становить лише `2 · ⌈N / B⌉`.
2. **Зворотно впорядкований масив (Worst Case)**: кожен новий елемент `y < x`, кожен елемент негайно блокує пам'ять. Довжина кожної серії строго дорівнює `M` (`K = ⌈N / M⌉`).
3. **Майже відсортовані дані (k-sorted / локальні інверсії)**: якщо локальні перестановки не перевищують `m` позицій, сортування заміщенням повністю виправляє їх за один прохід у пам'яті, генеруючи серії довжиною від `2M` до `N`.

## 3. Фаза 2: Багатошляхове злиття (K-Way Merge)

На другій фазі `K` сформованих серій поєднуються у фінальний відсортований потік шляхом багатовходового злиття.

### Розподіл пам'яті та обмеження коефіцієнта злиття k

Щоб одночасно зливати `k` серій, оперативна пам'ять `M` розбивається на окремі блокові буфери:
- `k` вхідних буферів розміром `B` кожен (по одному для підкачування блоків із кожного активного тимчасового файлу).
- 1 вихідний буфер розміром `B` для накопичення відсортованих записів перед їх скиданням на диск повним блоком.

Сумарне використання пам'яті під буфери задається нерівністю:

```
(k + 1) · B ≤ M  ===>  k ≤ ⌊M / B⌋ - 1
```

Якщо використовується подвійна буферизація (Double Buffering) для асинхронного паралельного зчитування блоків під час роботи процесора, під кожен потік виділяється по 2 буфери (один заповнюється контролером DMA/NVMe через асинхронний I/O, другий обробляється алгоритмом):

```
2 · (k + 1) · B ≤ M  ===>  k_async ≤ ⌊M / (2B)⌋ - 1
```

### Математична модель багатопрохідного злиття (Multi-Pass Cascading Merge)

Якщо кількість початкових серій `K ≤ k`, злиття виконується за **один прохід** (Single-pass merge): усі файли відкриваються одночасно, і результат одразу записується у вихідний потік.

Якщо `K > k`, одночасне відкриття та злиття всіх серій неможливе через дефіцит RAM для блокових буферів розміром `B` або вичерпання ліміту дескрипторів ядра. Алгоритм будує ієрархічне дерево злиття (Cascading Multi-pass Merge).

На кожному проході серії поточного рівня розбиваються на групи по `k` штук і зливаються у більші проміжні серії наступного рівня:

```
Рівень 0 (вихід фази 1): K_0 = K серій розміром S_0 = M (або 2M).
Рівень 1:               K_1 = ⌈K_0 / k⌉ проміжних серій розміром S_1 = k · S_0.
Рівень 2:               K_2 = ⌈K_1 / k⌉ проміжних серій розміром S_2 = k² · S_0.
...
Рівень j:               K_j = ⌈K_(j-1) / k⌉ серій розміром S_j = kʲ · S_0.
Рівень d:               K_d = 1 фінальний відсортований файл розміром N.
```

Кількість рівнів дерева злиття (проходів) `d` визначається логарифмічною глибиною стискання:

```
d = ⌈log_k K⌉ = ⌈log_k ⌈N / M⌉⌉
```

При використанні сортування заміщенням кількість проходів зменшується:

```
d_RS = ⌈log_k K_RS⌉ = ⌈log_k ⌈N / (2M)⌉⌉
```

На кожному з `d` проміжних проходів увесь масив даних розміром `N` байтів (`⌈N / B⌉` блоків) один раз повністю зчитується з тимчасових файлів попереднього рівня і один раз повністю записується у файли наступного рівня.

```
Дисковий I/O одного проходу = ⌈N / B⌉ (читання) + ⌈N / B⌉ (запис)
                             = 2 · ⌈N / B⌉ блокових операцій
```

### Оптимізація балансування першого проходу (Dummy Runs / Knuth Balance)

Коли кількість серій `K` не є точним степенем `k` (тобто `K ≠ kᵈ`), наївне розбиття на групи по `k` на кожному рівні призводить до того, що на останньому проході зливається менше ніж `k` серій. Це неоптимально, оскільки злиття виконується над великими важкими файлами.

Згідно з принципом Кнута–Гванга–Ліна (Knuth, Hwang, Lin), для мінімізації загального дискового I/O перший прохід злиття повинен об'єднати спеціально розраховану меншу кількість серій `K'`:

```
K' = ((K - 1) mod (k - 1)) + 1
```

Після злиття цих перших `K'` найменших серій (розміром `M`) в один файл, загальна кількість серій, що залишилися, стає строго кратною `k - 1`:

```
K_нова = (K - K') + 1
```

Усі наступні проходи гарантовано зливають рівно по `k` серій за один крок, зменшуючи кількість файлів на `k - 1` на кожному кроці, і фінальне злиття відбувається над повним набором `k` потоків без холостих витрат I/O на переписування важких проміжних файлів.

## 4. Обмеження операційної системи: дескриптори файлів та RLIMIT_NOFILE

У теоретичних моделях параметр `k` обмежується лише обсягом пам'яті `M` та розміром блоку `B`. У реальних операційних системах сімейства Unix/Linux виникає жорстке системне обмеження на кількість одночасно відкритих файлових дескрипторів (File Descriptors, FD).

### Структура дескрипторної таблиці ядра Linux

Кожен процес у просторі користувача має власну дескрипторну таблицю `struct files_struct` у ядрі:

```
struct task_struct (процес)
       │
       └──► struct files_struct
                   │
                   └──► struct fdtable
                              │
                              ├──► fd[0] ──► struct file (stdin)
                              ├──► fd[1] ──► struct file (stdout)
                              ├──► fd[2] ──► struct file (stderr)
                              ├──► fd[3] ──► struct file (tmp run_0)
                              ├──► fd[4] ──► struct file (tmp run_1)
                              │    ...
                              └──► fd[k+2] ─► struct file (tmp run_k-1)
```

Максимальна кількість файлових дескрипторів контролюється системним лімітом `RLIMIT_NOFILE`:
- **Soft Limit** (`ulimit -Sn`): поточний ліміт процесу (за замовчуванням у багатьох дистрибутивах Linux дорівнює 1024).
- **Hard Limit** (`ulimit -Hn`): максимальна межа, до якої звичайний непривілейований процес може підняти свій soft limit викликом `setrlimit()` (типово 4096 або 1 048 576).

Спроба виконати системний виклик `open()` або `fopen()` для `(k + 1)`-го файлу після досягнення ліміту завершується помилкою ядра:

```
errno = EMFILE (Too many open files)
```

### Розрахунок безпечного коефіцієнта злиття k_effective

Для запобігання падінню з помилкою `EMFILE` коефіцієнт злиття повинен враховувати службові дескриптори:

```
k_FD = RLIMIT_NOFILE - FD_reserved

де:
FD_reserved = FD_std (stdin, stdout, stderr = 3)
            + FD_output (вихідний файл або pipe = 1)
            + FD_directory (дескриптор каталогу тимчасових файлів = 1)
            + FD_safety_margin (резерв під внутрішні канали бібліотек/сигналів = 11)
            = 16 дескрипторів
```

При стандартному ліміті `RLIMIT_NOFILE = 1024`:

```
k_FD = 1024 - 16 = 1008
```

Фактичний робочий коефіцієнт злиття `k_effective` обирається як мінімум трьох обмежень:

```
k_effective = min(k_mem, k_FD, k_batch_size)

де:
k_mem        = ⌊M / B⌋ - 1           [обмеження за доступною оперативною пам'яттю]
k_FD         = RLIMIT_NOFILE - 16    [обмеження ядра операційної системи]
k_batch_size = значення --batch-size [явне налаштування утиліти, типово 16..64]
```

### Вплив ліміту дескрипторів на дисковий трафік

Якщо обсяг пам'яті великий (`M = 4 GB`), а розмір блоку `B = 64 KB`, обмеження пам'яті дозволило б зливати:

```
k_mem = ⌊4 GB / 64 KB⌋ - 1 = 65 535 файлів
```

Проте за стандартного `RLIMIT_NOFILE = 1024` або безпечного значення `--batch-size = 32`, коефіцієнт злиття примусово знижується з 65 535 до 32. 

Для масиву з `K = 2048` серій це збільшує кількість проходів:

```
Без обмеження FD (k = 65 535): d = ⌈log_65535 2048⌉ = 1 прохід  (I/O = 4 · N)
З обмеженням FD   (k = 32):     d = ⌈log_32 2048⌉     = 3 проходи (I/O = 8 · N)
```

Обмеження файлових дескрипторів подвоює фізичний обсяг дискового трафіку з `4N` до `8N` байтів, що вимагає явного налаштування `ulimit -n` на високонавантажених серверах обробки даних.

## 5. Процесорна складність: Дерево тих, хто програв (Loser Tree)

Окрім дискового обміну, алгоритм виконує порівняння ключів усередині оперативної пам'яті під час вибору мінімального елемента серед `k` відкритих потоків.

### Структура Loser Tree проти класичної мін-купи

Для багатовходового злиття використовують одну з двох структур даних:

```
                КЛАСИЧНА МІН-КУПА                      ДЕРЕВО ТИХ, ХТО ПРОГРАВ (LOSER TREE)
             (Binary Min-Heap, k = 4)                                (k = 4)

                     [ КОРІНЬ: 2 ]                                [ ПЕРЕМОЖЕЦЬ: Потік 0 (знач 2) ]
                      /         \                                                │
                 [ 5 ]           [ 3 ]                                    [ Вузол 1: Потік 2 (знач 3) ]
                 /   \           /   \                                           /                    \
              [ 8 ]  [ 7 ]    [ 4 ]  [ 6 ]                        [ Вузол 2: Потік 1 ]        [ Вузол 3: Потік 3 ]
                                                                       (знач 5)                    (знач 6)
                                                                      /        \                  /        \
  Пошук мінімуму: O(1)                                         [ Потік 0 ]  [ Потік 1 ]    [ Потік 2 ]  [ Потік 3 ]
  Sift-down при заміні кореня:                                   (знач 2)     (знач 5)       (знач 3)     (знач 6)
  2 порівняння на рівень:
  1) cmp(left, right)                                      Пошук мінімуму: O(1)
  2) cmp(min_child, parent)                                Оновлення при заміні переможця:
  Сумарно: 2 · ⌈log₂ k⌉ порівнянь                          РІВНО 1 порівняння на рівень: cmp(новий, вузол[v])
                                                           Сумарно: РІВНО ⌈log₂ k⌉ порівнянь
```

1. **Звичайна бінарна мін-купа (Binary Min-Heap)**:
   - Корінь містить глобальний мінімум.
   - Після вилучення кореня на його місце ставиться наступний елемент з відповідного файлу, і виконується просіювання вниз (`sift-down`).
   - На кожному рівні бінарного дерева алгоритм мусить порівняти двох нащадків між собою (1 порівняння), а потім меншого з них порівняти з поточним елементом (ще 1 порівняння).
   - Кількість порівнянь на один виведений рядок: `2 · ⌈log₂ k⌉`.

2. **Дерево тих, хто програв (Loser Tree / Tournament Tree)**:
   - Повне бінарне дерево з `k` листками. Внутрішні вузли зберігають індекс того потоку, який *програв* порівняння на даному рівні, а переможець (менший елемент) автоматично піднімається вище.
   - Корінь `tree[0]` зберігає абсолютного переможця турніру.
   - Коли з потоку-переможця зчитується новий елемент, він піднімається від відповідного листка до кореня по єдиному фіксованому шляху довжиною `⌈log₂ k⌉`.
   - На кожному рівні новий елемент порівнюється **рівно один раз** зі збереженим у вузлі переможеним елементом. Менший продовжує рух угору, а більший записується у вузол як новий переможений.
   - Кількість порівнянь на один виведений рядок: **рівно `⌈log₂ k⌉`**.

Застосування Loser Tree скорочує кількість процесорних порівнянь у фазі злиття рівно вдвічі порівняно з мін-купою.

### Апаратна ефективність Loser Tree: передбачення переходів і кеш CPU

Loser Tree має дві вирішальні переваги на сучасних суперскалярних процесорах:
1. **Детерміністична траєкторія обходу**: Шлях від листка `i` до кореня є статичним: `parent = ⌊(i - 1) / 2⌋`. Процесорний апаратний префетчер (Hardware Prefetcher) заздалегідь підкачує потрібні вузли в L1D-кеш, усуваючи затримки доступу до пам'яті.
2. **Мінімізація промахів передбачення переходів (Branch Misprediction)**: У звичайній купі подвійне порівняння `min(left, right)` генерує хаотичні розгалуження, які скидають конвеєр процесора (штраф 15–20 тактів за промах). У Loser Tree на кожному кроці виконується одне лінійне порівняння, яке ефективно транслюється компілятором у безумовну інструкцію умовного копіювання `cmov` (Conditional Move).

### Повне виведення сумарної кількості процесорних порівнянь

Обчислимо сумарну кількість процесорних операцій для вхідного масиву з `n = N / L` елементів:

**Фаза 1 (генерація серій):**
Сортування `K` блоків по `m = M / L` елементів внутрішнім алгоритмом вимагає:

```
T_comp_phase1 = K · O(m · log₂ m)
              = (n / m) · O(m · log₂ m) [підстановка K = n / m]
              = O(n · log₂ m)           [скорочення m]
```

*(При сортуванні заміщенням через Loser Tree кожен із `n` елементів проходить через дерево розміром `m`, що дає таку саму кількість порівнянь: `n · log₂ m`)*.

**Фаза 2 (багатопрохідне злиття):**
На кожному з `d` проходів кожен із `n` елементів проходить через Loser Tree розміром `k`:

```
T_comp_phase2 = d · (n · log₂ k)
              = ⌈log_k (n / m)⌉ · n · log₂ k      [підстановка d = ⌈log_k K⌉]
              = (log₂(n / m) / log₂ k) · n · log₂ k [перехід до основи 2]
              = n · log₂(n / m)                   [скорочення множника log₂ k]
              = O(n · log₂ (N / M))
```

**Підсумкова кількість процесорних порівнянь:**

```
Total_Comp = T_comp_phase1 + T_comp_phase2
           = n · log₂ m + n · log₂(n / m)   [сума порівнянь обох фаз]
           = n · (log₂ m + log₂ n - log₂ m) [властивість логарифма частки: log₂(n/m) = log₂ n - log₂ m]
           = n · log₂ n                     [взаємне знищення +log₂ m та -log₂ m]
           = O(n · log₂ n)
```

External Merge Sort строго досягає фундаментального інформаційного теоретичного мінімуму `O(n · log₂ n)` для алгоритмів сортування на основі порівнянь.

## 6. Повний обсяг дискового I/O та теорема Аґґарвала–Віттера

### Точний вивід сумарної кількості операцій I/O

Обчислимо сумарну кількість переданих блоків для повного циклу зовнішнього сортування:

```
Total_I/O = I/O_phase1 + I/O_phase2                       [сума операцій обох фаз]
          = 2 · ⌈N / B⌉ + d · (2 · ⌈N / B⌉)               [на кожному з d проходів весь масив N читається й записується]
          = 2 · ⌈N / B⌉ · (1 + d)                         [винесення спільного множника 2·⌈N/B⌉]
          = 2 · ⌈N / B⌉ · (1 + ⌈log_k ⌈N / M⌉⌉)           [підстановка d = ⌈log_k K⌉]
          = 2 · ⌈N / B⌉ · (1 + ⌈log_(⌊M/B⌋ - 1) ⌈N / M⌉⌉) [підстановка k_mem = ⌊M/B⌋ - 1]
```

Сумарний фізичний обсяг байтів, прочитаних та записаних через дискову підсистему:

```
Total_Bytes = 2 · N · (1 + d)
```

Кожен додатковий прохід злиття збільшує загальний обсяг дискового трафіку на `2N` байтів (один повний цикл читання всього набору даних і один повний цикл запису).

### Зв'язок із фундаментальною межею Аґґарвала–Віттера

Аґґарвал і Віттер довели теорему про нижню межу дискової складності будь-якого алгоритму порівняльного сортування у зовнішній пам'яті:

```
Sort_I/O(N, M, B) = Θ((N / B) · log_(M / B) (N / B))
```

Покажемо строгий алгебраїчний перехід від нашої точної формули проходів до цієї асимптотичної межі:

```
1 + log_k (N / M)
= 1 + (ln(N / M) / ln k)                   [перехід до натуральних логарифмів]
= 1 + (ln((N / B) / (M / B)) / ln(M / B))  [ділення чисельника й знаменника аргументу на B при k ≈ M/B]
= 1 + ((ln(N / B) - ln(M / B)) / ln(M / B)) [властивість логарифма частки: ln(a/b) = ln a - ln b]
= 1 + (ln(N / B) / ln(M / B)) - 1          [розбиття дробу на два доданки]
= ln(N / B) / ln(M / B)                    [взаємне знищення +1 та -1]
= log_(M / B) (N / B)                      [згортання за новою основою M/B]
```

Множачи цей результат на кількість блоків `2 · (N / B)`, отримуємо точний збіг:

```
Total_I/O = 2 · (N / B) · log_(M / B) (N / B)
          = Θ((N / B) · log_(M / B) (N / B))
```

Це доводить, що External Merge Sort є **асимптотично оптимальним алгоритмом сортування в зовнішній пам'яті**: не існує алгоритму на основі порівнянь, який міг би виконати сортування за меншу кількість дискових I/O операцій.

## 7. Оптимізація коефіцієнта злиття k: компроміс часу позиціювання

На практиці час виконання сортування визначається не лише кількістю переданих байтів, а й фізичною природою операцій дискового накопичувача.

### Фізична модель затримки I/O (Seek Time проти пропускної здатності)

Час виконання однієї дискової операції читання або запису блоку розміром `B` складається із затримки позиціювання та безпосередньої передачі даних:

```
T_block(B) = T_latency + (B / R_transfer)
```

де:
- `T_latency` — час довільного доступу (для механічних HDD це сума часу переміщення голівки `T_seek ≈ 4–10 ms` та часу очікування обертання пластини `T_rot ≈ 2–4 ms`; для NVMe SSD це затримка контролера та флеш-пам'яті `T_lat ≈ 10–30 μs`).
- `R_transfer` — швидкість лінійного послідовного читання/запису носія (150–250 МБ/с для HDD, 3000–7000 МБ/с для NVMe PCIe 4.0).

Для передачі всього масиву `N` блоками розміром `B` загальний час одного дискового проходу становить:

```
T_pass(B) = (N / B) · T_latency + (N / R_transfer)
```

### Математична формалізація оптимізації

Оскільки пам'ять обмежена величиною `M`, збільшення коефіцієнта злиття `k` змушує зменшувати розмір буфера кожного потоку:

```
B = M / (k + 1)
```

Підставляючи це значення у формулу повного часу злиття, отримуємо цільову функцію оптимізації:

```
T_total(k) = 2 · (1 + ⌈log_k (N / M)⌉) · [ ((N · (k + 1)) / M) · T_latency + (N / R_transfer) ]
```

Тут виникає фундаментальний інженерний компроміс:
1. **Зростання `k` зменшує кількість проходів `d = ⌈log_k (N / M)⌉`**, що скорочує загальний обсяг даних, які потрібно прочитати й записати.
2. **Зростання `k` зменшує розмір блоку `B`**, через що кількість випадкових позиціювань `(N / B) · T_latency` зростає лінійно пропорційно до `k`.

```
                  Час виконання T_total
                            ▲
                            │          /  (замалий B -> домінує Seek Time)
                            │         /
                            │  \     /
                            │   \   /
                            │    \_/  <-- ТОЧКА ОПТИМУМУ k_opt
                            │     │
            (замалий k ->   │     │
             багато проходів)     │
                            └─────┴──────────────► Коефіцієнт злиття k
```

### Відмінності для HDD та NVMe SSD

1. **Механічні жорсткі диски (HDD)**:
   - Через високий `T_latency ≈ 10 ms` критично тримати `B ≥ 256 KB ... 1 MB`. Якщо зменшити `B` до 4 KB, диск витрачатиме 95% часу на позиціювання голівок, а реальна швидкість передачі впаде з 200 МБ/с до кількох мегабайтів на секунду.
   - Тому на HDD оптимальний коефіцієнт злиття обирають невеликим: `k = 16 ... 64`.

2. **Твердотільні накопичувачі (NVMe SSD)**:
   - Затримка доступу мізерна (`T_latency < 30 μs`), тому розмір блоку можна безпечно зменшувати до `B = 32 KB ... 64 KB` без істотної деградації швидкості.
   - Це дозволяє встановлювати високий коефіцієнт злиття `k = 256 ... 1024`, гарантуючи завершення злиття за один-два проходи навіть для багатотерабайтних наборів даних.

## 8. Практичні комплексні числові розрахунки

### Сценарій 1: Однопрохідне злиття 100 ГБ лог-файлу

**Параметри задачі:**
- Розмір файлу: `N = 100 GB`.
- Доступна пам'ять під sort: `M = 4 GB` (`sort -S 4G`).
- Розмір блоку введення-виведення: `B = 64 KB`.
- Системний ліміт дескрипторів: `RLIMIT_NOFILE = 1024`.

**Покроковий розрахунок:**

1. Кількість початкових серій:
   - Стандартне блокове розбиття:
     ```
     K = ⌈N / M⌉ = ⌈100 GB / 4 GB⌉ = 25 серій
     ```
   - Сортування заміщенням (Replacement Selection):
     ```
     K_RS ≈ ⌈N / (2M)⌉ = ⌈100 GB / 8 GB⌉ = 13 серій
     ```

2. Обмеження коефіцієнта злиття:
   - За пам'яттю: `k_mem = ⌊M / B⌋ - 1 = ⌊4 GB / 64 KB⌋ - 1 = 65 535`.
   - За дескрипторами: `k_FD = 1024 - 16 = 1008`.
   - Фактичний коефіцієнт: `k_effective = min(65535, 1008) = 1008`.

3. Кількість проходів злиття:
   ```
   d = ⌈log_1008 25⌉ = 1 прохід
   ```
   Оскільки `K = 25 ≤ k_effective = 1008`, алгоритм вкладається в **один прохід злиття**.

4. Баланс дискового I/O:
   - Фаза 1: 100 GB читання вхідного файлу + 100 GB запису 25 серій = 200 GB.
   - Фаза 2: 100 GB читання 25 серій + 100 GB запису результату = 200 GB.
   - Загальний дисковий трафік: `2 · N · (1 + 1) = 400 GB` (`4 · N`).
   - Кількість блокових I/O операцій: `2 · ⌈100 GB / 64 KB⌉ · 2 = 6 553 600` операцій.

### Сценарій 2: Багатопрохідне злиття 1 ТБ масиву при обмеженій пам'яті та ліміті дескрипторів

**Параметри задачі:**
- Розмір файлу: `N = 1 TB = 1024 GB`.
- Доступна пам'ять RAM: `M = 512 MB`.
- Розмір блоку I/O: `B = 128 KB`.
- Системне налаштування утиліти: `--batch-size = 32`.

**Покроковий розрахунок:**

1. Кількість початкових серій:
   ```
   K = ⌈N / M⌉ = ⌈1024 GB / 512 MB⌉ = 2048 серій
   ```

2. Коефіцієнт злиття:
   - За пам'яттю: `k_mem = ⌊512 MB / 128 KB⌋ - 1 = 4095`.
   - За параметром batch-size: `k = 32`.

3. Кількість проходів злиття при `k = 32`:
   ```
   d = ⌈log_32 2048⌉ = ⌈ln(2048) / ln(32)⌉ = ⌈11 / 5⌉ = ⌈2.2⌉ = 3 проходи
   ```

4. Оптимізація балансування першого проходу (Кнут):
   ```
   K' = ((K - 1) mod (k - 1)) + 1
      = ((2048 - 1) mod (32 - 1)) + 1
      = (2047 mod 31) + 1
      = 1 + 1
      = 2 серії
   ```
   На першому проміжному кроці зливаються лише 2 початкові серії по 512 МБ в один файл 1 ГБ, залишаючи `2046 + 1 = 2047` серій, що строго кратно 31. Усі наступні злиття використовують повний коефіцієнт `k = 32`.

5. Ієрархія злиття по рівнях:
   - **Рівень 0 (вихід фази 1):** 2048 початкових серій по 512 MB.
   - **Прохід злиття 1:** злиття групами по 32 → 64 проміжні серії по 16 GB.
   - **Прохід злиття 2:** злиття 64 серій групами по 32 → 2 великі серії по 512 GB.
   - **Прохід злиття 3 (фінальний):** злиття останніх 2 серій в 1 підсумковий відсортований файл розміром 1 ТБ.

6. Загальний дисковий I/O:
   ```
   Total_Bytes = 2 · N · (1 + d) = 2 · 1 TB · (1 + 3) = 8 TB
   ```

### Сценарій 3: Сортування 10 ТБ масиву на Enterprise NVMe накопичувачах

**Параметри задачі:**
- Розмір файлу: `N = 10 TB = 10 240 GB`.
- Доступна пам'ять RAM: `M = 64 GB`.
- Розмір блоку I/O: `B = 256 KB`.
- Системний ліміт дескрипторів: `ulimit -n 65536`.

**Покроковий розрахунок:**

1. Кількість початкових серій:
   - Зі стандартним розбиттям: `K = ⌈10 240 GB / 64 GB⌉ = 160 серій`.
   - З сортуванням заміщенням: `K_RS ≈ ⌈10 240 GB / 128 GB⌉ = 80 серій`.

2. Допустимий коефіцієнт злиття за пам'яттю:
   ```
   k_mem = ⌊64 GB / 256 KB⌋ - 1 = 262 144 - 1 = 262 143
   ```
   З огляду на `RLIMIT_NOFILE = 65 536`, обираємо безпечний робочий коефіцієнт `k = 1024`.

3. Кількість проходів злиття:
   ```
   d = ⌈log_1024 160⌉ = 1 прохід
   ```
   Оскільки `K = 160 ≤ k = 1024`, 10 терабайтів даних сортуються за **один єдиний прохід злиття**!

4. Підсумковий баланс дискового I/O та тривалості:
   - Загальний обсяг переданих даних: `2 · N · (1 + 1) = 4 · 10 TB = 40 TB`.
   - За швидкості масиву NVMe `R_transfer = 5 GB/s`:
     ```
     Час виконання T ≈ 40 000 GB / 5 GB/s = 8000 секунд ≈ 2.22 години
     ```
   Якби через низький ліміт дескрипторів (`k = 16`) алгоритм виконував 2 проходи (`d = 2`), обсяг дискового трафіку зріс би до 60 ТБ, а час сортування збільшився б до 3.33 годин.
