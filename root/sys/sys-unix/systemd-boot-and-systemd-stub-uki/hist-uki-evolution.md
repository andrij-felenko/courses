# 📜 Від gummiboot до UKI: еволюція завантаження в UEFI

Припустимо, адміністратор сервера увімкнув режим UEFI Secure Boot і перевірив, що підпис ядра Linux збігається з ключем у базі довіри `db`. Тим часом на диску поруч із ядром лежать два інші файли: `initramfs.img` та командний рядок у конфігурації завантажувача. Якщо зловмисник змінить `initramfs` або додасть у командний рядок `init=/bin/sh`, прошивка під час наступного запуску слухняно перевірить підпис ядра, переконається в його правильності й виконає модифікований сценарій із правами root. Secure Boot спрацював без помилок, але безпеку системи було повністю зламано.

Цей сценарій роками залишався головною криптографічною дірою у завантаженні Linux. Шлях від перших днів UEFI до створення атомарних образів Unified Kernel Images (UKI) — це історія того, як просте меню завантаження трансформувалося в цілісний механізм захисту ланцюга довіри.

## Епоха монолітних завантажувачів та обмеження BIOS

У часи спадщини BIOS завантажувачі мали вирішувати задачу виживання в умовах жорстких обмежень пам'яті та 16-бітного реального режиму процесора x86. Перший ступінь завантажувача (Stage 1) мусив уміститися у 512 байтів першого сектора MBR (Master Boot Record). Його єдиним завданням було завантажити через переривання прошивки `INT 13h` другий ступінь (Stage 1.5 або Stage 2), який містився у незайнятих секторах між MBR та першим розділом диска.

У завантажувачі LILO (Linux Loader) це вирішувалося жорстким запіканням абсолютних фізичних номерів секторів диска (LBA) у тіло завантажувача. Будь-яке дефрагментування або переміщення файла ядра на диску вимагало обов'язкового повторного запуску утиліти `lilo`, інакше машина ставала невмикаємою.

З появою завантажувача GRUB 2 його архітектура перетворилася на повноцінну міні-операційну систему. Щоб знайти файл ядра на довільному розділі диска, всередину бінарника GRUB 2 вбудували власні драйвери десятків файлових систем (ext2/3/4, xfs, btrfs, zfs), програмних масивів RAID (mdadm), томів LVM і навіть дублюючі стеки для розшифрування томів LUKS.

З появою специфікації UEFI середовище виконання кардинально змінилося. Прошивка більше не була обмежена 16-бітним режимом і навчилася самостійно читати розділи диска з файловою системою VFAT (EFI System Partition, ESP), розуміти таблиці партицій GPT та виконувати файли у стандартному форматі PE/COFF.

Попри нові можливості прошивки, GRUB 2 просто портували як програму UEFI. Він продовжував тягнути власні драйвери файлових систем і будувати складні конфігураційні файли `grub.cfg`, які генерувалися громіздкими сценаріями `grub-mkconfig`.

Складність коду завантажувача призвела до серії небезпечних вразливостей. Наприклад, уразливість Boothole (CVE-2020-10713) у вихідному коді парсера `grub.cfg` дозволяла викликати переповнення буфера у купі та виконати довільний код на етапі до завантаження ядра навіть при увімкненому Secure Boot. Для виправлення проблеми довелося випускати масові оновлення та додавати сотні підписів і хешів у бази відкликання `dbx` у пам'яті NVRAM материнських плат по всьому світу, що на багатьох платах спричинило переповнення незмінної пам'яті.

## Народження gummiboot та Boot Loader Specification

У 2012 році розробники Кай Сіверс (Kay Sievers) та Гаральд Хоєр (Harald Hoyer) із компанії Red Hat запропонували альтернативну філософію. Якщо прошивка UEFI вже вміє читати файлову систему VFAT та завантажувати виконувані файли PE/COFF, навіщо завантажувачу дублювати ці функції та мати власні драйвери дискових структур?

Вони створили проект `gummiboot` (у перекладі з німецької — «гумовий човен», як натяк на легкість і мінімалізм). `gummiboot` не містив жодного драйвера дискових структур. Він розпізнавав лише розділ ESP, читав звичайні текстові конфігураційні файли й використовував виклики UEFI Boot Services для запуску ядра.

Разом із `gummiboot` з'явилася специфікація Boot Loader Specification (BLS). Вона визначала формат опису пунктів меню (Type #1 entries): замість одного загального конфігураційного файлу кожне ядро або дистрибутив поставляв власний фрагмент у директорію `/loader/entries/*.conf`:

```text
title      Fedora Linux (6.10.3)
version    6.10.3-200.fc40.x86_64
linux      /vmlinuz-6.10.3-200.fc40.x86_64
initrd     /initramfs-6.10.3-200.fc40.x86_64.img
options    root=UUID=a1b2c3d4-e5f6-4a5b-8c9d-0123456789ab ro quiet
```

Це вирішило проблему конфліктів під час оновлення кількох ядер: додавання чи видалення ядра зводилося до створення або вилучення одного файла без ризику пошкодити загальну конфігурацію завантаження.

У травні 2015 року, з виходом релізу systemd v220, проект `gummiboot` було офіційно включено до основного репозиторію systemd під назвою `systemd-boot`.

## Криптографічний розрив Secure Boot

З широким упровадженням Secure Boot виявилася фундаментальна слабкість схеми з окремими файлами. Ядро Linux отримало власний модуль `EFISTUB` (автор Рой Франц, Roy Franz), який дозволив прошивці UEFI запускати файл `vmlinuz` безпосередньо як PE/COFF бінарник.

Коли `systemd-boot` (або GRUB) запускав ядро через `EFISTUB`, перевірка Secure Boot відбувалася лише для самого файла `vmlinuz`. Однак для повноцінного старту ядру потрібні ще два компоненти:
1. Образ `initramfs`, який містить модулі дискових контролерів та сценарії мовою shell.
2. Рядок аргументів ядра (`cmdline`), у якому вказано UUID кореня та параметри безпеки.

Обійшовши підпис ядра, зловмисник міг модифікувати командний рядок, передавши параметри `init=/bin/sh`, `rd.break`, `systemd.debug_shell=1` або `selinux=0`. Це відкривало інтерактивну командну стрічку root у початковій файловій системі до введення будь-яких паролів.

Оскільки прошивка UEFI нічого не знала про формат `initramfs`, вона не могла перевірити його цифровий підпис. Будь-який користувач із фізичним доступом або шкідливе ПЗ із правами root у застарілій ОС могли замінити `initramfs` на модифікований архів із клавіатурним шпигуном чи зворотним шеллом.

Ланцюг довіри ламався на найвідповідальнішому місці: перевірений завантажувач передавав керування перевіреному ядру, але з повністю неперевіреним оточенням.

## Народження systemd-stub та концепція UKI

Для розв'язання цієї проблеми спільнота systemd під керівництвом Леннарта Поттерінга розробила концепцію Unified Kernel Image (UKI), яка увійшла до специфікації BLS як Type #2 entries.

Ідея UKI полягає в тому, щоб об'єднати всі компоненти завантаження в **єдиний атомарний бінарний файл** формату PE/COFF:

1. `systemd-stub` — маленька заглушка UEFI, яка слугує точкою входу бінарника.
2. Двійковий образ ядра Linux (`vmlinuz`).
3. Початкова файлова система (`initramfs`).
4. Вшитий командний рядок (`cmdline`).
5. Метадані системи (`/etc/os-release`).
6. Сертифікати та ключі для виміряного завантаження (TPM2 PCR).

Цей об'єднаний файл підписується **одним цифровим підписом Authenticode** під час збірки на захищеному сервері або при інсталяції в дистрибутиві. 

Коли прошивка UEFI завантажує UKI, вона перевіряє підпис усього файла разом із прихованими всередині `initramfs` та `cmdline`. Зміна бодай одного байта в командному рядку чи всередині архіву `initramfs` призводить до того, що підпис PE/COFF стає недійсним, і прошивка відмовляється запускати файл.

## Еволюція у поєднанні з TPM2 та Measured Boot

Поява UKI також відкрила шлях до справжнього виміряного завантаження (Measured Boot). Компонент `systemd-stub` під час свого виконання розпаковує секції UKI в пам'яті й послідовно розраховує криптографічні хеші кожної секції (`.linux`, `.initrd`, `.cmdline`, `.osrel`). Ці хеші записуються в регістр TPM2 PCR 11.

Завдяки цьому люкс-шифрування диска (LUKS2) через `systemd-cryptsetup` отримало змогу автоматично запечатувати ключі розшифрування у чипі TPM2. Ключ видається лише тоді, коли регістр PCR 11 містить хеші точно того UKI, який пройшов усі перевірки.

Таким чином, розробка від легкого меню `gummiboot` до специфікації UKI перетворила завантажувач Linux із простого інструменту вибору операційної системи на захищений вузол апаратно-програмного ланцюга довіри.
