# 📋 Виклики ідентичності: що саме ставить кожен і чим падає

Це довідник по родині системних викликів, якими процес читає й міняє свої UID, GID і список груп: на кожен виклик — що він ставить з привілеєм і що без нього, як розуміє `-1`, якими помилками падає й чи взагалі вміє повідомити про невдачу. Тримати його поруч варто тому, що більшість дір у цьому місці береться не з нерозуміння моделі, а з того, що виклик тихо зробив менше, ніж здавалося авторові коду.

Скрізь нижче «привілейований» означає рівно одне: процес має [можливість](topic:sys-unix/capabilities) `CAP_SETUID` (для групових викликів — `CAP_SETGID`) **у своєму просторі імен користувачів**.

## Читання: виклики, що не вміють помилитися

```c
#define _GNU_SOURCE
#include <unistd.h>

uid_t getuid(void);    uid_t geteuid(void);
gid_t getgid(void);    gid_t getegid(void);

int getresuid(uid_t *ruid, uid_t *euid, uid_t *suid);
int getresgid(gid_t *rgid, gid_t *egid, gid_t *sgid);
```

| виклик | що дає | помилки |
|---|---|---|
| `getuid`, `geteuid`, `getgid`, `getegid` | одне число | **жодних**: ці чотири завжди успішні й не чіпають `errno` |
| `getresuid`, `getresgid` | усі три числа за один захід | `EFAULT` — вказівник за межами адресного простору |

Наслідок першого рядка треба знати напам'ять: `geteuid()` не має значення-помилки, тож перевіряти його результат на `-1` безглуздо — `(uid_t)-1` тут просто велике число. `getresuid()` натомість повертає `0` або `-1`, як усі нормальні виклики; він з'явився в Linux 2.1.44 (glibc 2.3.2), довго був лінуксовим розширенням і потрапив у POSIX аж у редакції 2024 року, тому вимагає `_GNU_SOURCE`.

Виклику, що читав би **файловий** UID, немає взагалі — його дістають або з `/proc/self/status`, або хитрощами з `setfsuid()` (нижче).

```c
#define _GNU_SOURCE
#include <unistd.h>
#include <grp.h>
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    uid_t r, e, s;  gid_t rg, eg, sg;
    if (getresuid(&r, &e, &s) || getresgid(&rg, &eg, &sg))
        return 1;
    printf("uid %u/%u/%u  gid %u/%u/%u\n", r, e, s, rg, eg, sg);

    int n = getgroups(0, NULL);            /* спершу питаємо, скільки їх */
    if (n < 0) return 1;
    gid_t *g = calloc(n ? n : 1, sizeof *g);
    if (!g) return 1;
    n = getgroups(n, g);                   /* і аж тоді читаємо */
    for (int i = 0; i < n; i++)
        printf("%s%u", i ? " " : "groups ", g[i]);
    putchar('\n');
    free(g);
    return 0;
}
```

Два запити поспіль тут безпечні без жодного замка: повноваження задачі має право міняти лише вона сама, тож в однопотоковій програмі між `getgroups(0, NULL)` і другим викликом список змінитися не може.

## Запис: хто що ставить

Порівнюйте рядки цієї таблиці не за назвами, а за колонкою «збережений» — саме там ховається різниця, через яку зниження прав виявляється зворотним.

| виклик | привілейований ставить | без привілею | збережений (`suid`/`sgid`) |
|---|---|---|---|
| `setuid(uid)` | реальний, діючий і збережений — усі три | лише **діючий**, і лише в реальний або збережений | **не чіпає** — саме тут і лишається дорога назад |
| `setgid(gid)` | те саме для групи | лише діючий, у реальний або збережений | не чіпає |
| `seteuid(euid)`, `setegid(egid)` | діючий | діючий, у реальний, діючий або збережений | **ніколи не чіпає**: від glibc 2.1 це обгортка над `setresuid(-1, euid, -1)` |
| `setreuid(r, e)` | обидва довільно | `e` — у будь-яке з трьох; `r` — тільки в реальний або діючий | ставить у **новий діючий**, якщо `r ≠ -1` або новий діючий не дорівнює **попередньому реальному** |
| `setresuid(r, e, s)` | усі три довільно | кожне з трьох — у будь-яке з поточних трьох | ставить рівно те, що просили |
| `setfsuid(fsuid)` | файловий | файловий, якщо число збігається з реальним, діючим, збереженим або поточним файловим | не чіпає |

`setresuid`/`setresgid` — єдина пара, де правило зміни збереженого читається з коду, а не виводиться. Тому канонічна форма незворотного зниження записується саме нею, а не `setuid()`.

Кожен рядок «u»-половини має точного двійника для групи — `setgid`, `setegid`, `setregid`, `setresgid`, `setfsgid` — з тими самими правилами, тією самою роллю `-1` і `CAP_SETGID` замість `CAP_SETUID`. Відмінностей рівно дві, обидві важать на практиці. Перша: групові виклики не мають `EAGAIN` (див. нижче). Друга: вони **не чіпають списку додаткових груп** — жоден із них. Опустити `setgroups()` і думати, що `setresgid()` прибрав зайве членство, — типова помилка, і побачити її можна тільки прочитавши список назад.

Окремо, і це стосується **всіх** викликів «u»-половини, крім `setfsuid`: щоразу, коли міняється діючий UID, ядро автоматично тягне за ним і файловий. Тому `setfsuid()` має сенс лише **після** решти — інакше наступний же `setresuid()` затре його результат.

### Значення −1

| контекст | що означає `-1` |
|---|---|
| `setreuid`, `setregid`, `setresuid`, `setresgid` | «це число не чіпати» |
| `setuid`, `setgid` | звичайний аргумент — але `(uid_t)-1` зарезервоване як «недійсний ідентифікатор», тож виклик поверне `EINVAL` |
| `setfsuid`, `setfsgid` | так само звичайний аргумент, який гарантовано не пройде — і саме на цьому побудовано спосіб дізнатися поточний файловий UID |

### Помилки

| помилка | у кого | причина |
|---|---|---|
| `EPERM` | усі `set*`, крім `setfsuid`/`setfsgid` | немає потрібної можливості, а ціль не входить у дозволений набір поточних чисел |
| `EAGAIN` | `setuid`, `setreuid`, `setresuid` | міняється **реальний** UID, і в нового власника вже стільки процесів, що перевищує `RLIMIT_NPROC` викликача ([ліміти ресурсів](topic:sys-unix/resource-limits)); або ядру не вдалося виділити структуру обліку користувача |
| `EINVAL` | усі, що приймають число | число не має відображення в поточному [просторі імен користувачів](topic:sys-unix/namespaces) |
| `EFAULT` | `getres*`, `getgroups`, `setgroups` | вказівник за межами адресного простору |
| `ENOMEM` | `setgroups` | немає пам'яті під новий список |

Групові виклики `EAGAIN` не мають узагалі: ліміт на кількість процесів рахується за реальним **UID**, а групи його не торкають. Звідси й практичне правило порядку — групові зміни не можуть провалитися через чужі процеси, а `setresuid()` може, і саме він мусить бути останнім кроком, після якого йде звірка.

## Єдиний виклик, що не вміє сказати «ні»

```c
#include <sys/fsuid.h>

int setfsuid(uid_t fsuid);
int setfsgid(gid_t fsgid);
```

І в разі успіху, і в разі невдачі ця пара повертає **попереднє** значення. Коду ні за чим відрізнити «я поставив, що просив» від «мені не дозволили»: обидва результати виглядають однаково. Помилок вона не визначає взагалі — за задумом, і це визнано вадою інтерфейсу, яку не виправити, бо ABI до простору користувача не ламають.

Робочий обхід спирається на те, що `setfsuid(-1)` не спрацює ніколи, а отже поверне поточне значення:

```c
/* 0 — файловий UID справді став want, -1 — не став. */
static int set_fsuid_checked(uid_t want)
{
    (void) setfsuid(want);                 /* результат нічого не каже */
    return setfsuid((uid_t) -1) == want ? 0 : -1;
}
```

Виклик з'явився в Linux 1.2 заради сервера NFS. Від Linux 2.0 правило перевірки права на сигнал змінили, потреба в окремому файловому UID відпала, і документація прямо радить не вживати `setfsuid()` у новому коді — але сам виклик лишиться назавжди.

## Групи

```c
#include <unistd.h>
int getgroups(int size, gid_t list[]);

#define _GNU_SOURCE
#include <grp.h>
int setgroups(size_t size, const gid_t *list);
int initgroups(const char *user, gid_t group);
```

| виклик | контракт |
|---|---|
| `getgroups(0, NULL)` | `list` не чіпає, повертає **кількість** додаткових груп — цим і починають |
| `getgroups(size, list)` | `size` менший за кількість (і не нульовий) → `EINVAL`; чи входить у список **діючий GID**, стандарт лишає невизначеним, тож будувати на цьому логіку не можна |
| `setgroups(size, list)` | замінює список **цілком**, потребує `CAP_SETGID`; `size` більший за `NGROUPS_MAX` → `EINVAL` |
| `initgroups(user, group)` | бібліотечна: бере **ім'я**, збирає через [базу облікових записів](topic:sys-unix/user-database-nss) усі групи, де ця людина є членом, додає `group` і викликає `setgroups()` — звідти ж і `EPERM` |

| межа | значення |
|---|---|
| `NGROUPS_MAX` | 32 до Linux 2.6.4; **65536** від 2.6.4 |
| `/proc/sys/kernel/ngroups_max` | те саме число, **лише для читання** (від Linux 2.6.4) |
| `sysconf(_SC_NGROUPS_MAX)` | той самий ліміт із програми, без читання `/proc` |
| `/proc/PID/setgroups` | у просторі імен користувачів: `deny` (типово) → `setgroups()` віддає `EPERM` (від Linux 3.19). Переписати на `allow` можна, лише поки `gid_map` ще не записано і маючи право в батьківському просторі |

Останній рядок виглядає химерно, доки не побачити його причину: **прибирання групи буває підвищенням прав**. Файл із правами `----rwx---` забороняє доступ саме членам групи, і непривілейований, що вміє викинути групу зі свого списку, обійшов би цю заборону. Тому в непривілейованому просторі імен списку не дають ставити взагалі.

## Що видно ззовні: `/proc/PID/status`

Ці рядки [псевдо-файлової системи](topic:sys-unix/pseudo-filesystems) читаються без жодного привілею для будь-якого процесу — ідентичність у Unix не є таємницею.

```
Uid:	1000	1000	1000	1000
Gid:	1000	1000	1000	1000
Groups:	4 24 27 1000
CapEff:	0000000000000000
NoNewPrivs:	0
```

| поле | зміст |
|---|---|
| `Uid:`, `Gid:` | чотири числа в фіксованому порядку: **реальний, діючий, збережений, файловий** |
| `Groups:` | додаткові групи через пробіл |
| `Ngid:` | **пастка**: не «кількість груп», а ідентифікатор NUMA-групи (від Linux 3.13), `0` — немає |
| `CapEff:` | шістнадцятковий набір діючих можливостей; `CAP_SETGID` — біт 6 (`0x40`), `CAP_SETUID` — біт 7 (`0x80`), тож право міняти обидві ідентичності дає молодший байт `c0` |
| `NoNewPrivs:` | `1` означає, що [біт set-user-ID](topic:sys-unix/setuid-and-privilege) на файлах для цього процесу й усіх його нащадків уже нічого не дає |

## Число переповнення

Коли ядру треба показати ідентифікатор, який у поточному контексті не виражається, воно підставляє **число переповнення** — типово `65534`.

| параметр | коли вживається |
|---|---|
| `/proc/sys/kernel/overflowuid`, `…/overflowgid` | 32-бітне число віддають через старий 16-бітний інтерфейс (архітектури `arm`, `i386`, `m68k`, `sh`, `sparc32`), **або** воно не має відображення в просторі імен користувачів |
| `/proc/sys/fs/overflowuid`, `…/overflowgid` | окрема пара з тим самим типовим значенням: те, що запишеться на носій, якщо файлова система вміє тільки 16-бітні числа |

Практичний висновок один: `65534` у виводі `ls -l` чи `stat` майже ніколи не означає «власником є користувач `nobody`». Майже завжди це означає «справжнє число сюди не пролізло».
