# 📋 Інтерфейс та системні виклики BPF Arena (API Reference)

Довідник описує повну поверхню системного API, інтерфейсів програмування, структур даних ядра, кваліфікаторів адресного простору LLVM та параметрів конфігурації ОС Linux (версії 6.8 та новіші) для роботи з розрідженим спільним регіоном пам'яті `BPF_MAP_TYPE_ARENA`. Матеріал розроблено для системних інженерів, архітекторів високопродуктивних мережевих служб та розробників засобів спостережуваності (observability), яким необхідна вичерпна специфікація системних викликів, параметрів виділення фізичних сторінок пам'яті у ядрі, правил маскування вказівників JIT та методів обробки помилок сумісності C/C++.

## 1. Специфікація типу мапи та прапори створення

Карта BPF Arena реєструється в ядрі Linux через системний виклик `bpf(BPF_MAP_CREATE, union bpf_attr *attr, unsigned int size)` або за допомогою хелперів декларативного створення мап у бібліотеці `libbpf`. Створення арени ініціалізує у ядрі внутрішню структуру `struct bpf_arena`, яка утримує зарезервоване діапазон віртуальних адрес ядра (`kern_vm_start`) та відстежує списки виділених фізичних сторінок.

### 1.1 Структура декларативного оголошення мапи у C та C++

При використанні макросів `libbpf` мапа описується у секції `.maps` ELF-файла BPF-програми.

```c
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

struct {
    __uint(type, BPF_MAP_TYPE_ARENA);
    __uint(map_flags, BPF_F_MMAPABLE | BPF_F_SEGV_ON_FAULT);
    __uint(max_entries, 1048576); /* Максимальна кількість сторінок (4 ГБ при 4 KB/page) */
    __uint(map_extra, 0x100000000ULL); /* Бажана віртуальна адреса у userspace */
} shared_arena SEC(".maps");
```

### 1.2 Деталізація полів `union bpf_attr` для `BPF_MAP_CREATE`

Системний виклик `bpf()` очікує заповнену структуру `union bpf_attr`. Для мапи типу `BPF_MAP_TYPE_ARENA` встановлюються наступні вимоги до полів:

- **`map_type` (`__u32`)**: Повинно мати значення `BPF_MAP_TYPE_ARENA` (числовий константний ідентифікатор `34` у `enum bpf_map_type`).
- **`map_flags` (`__u32`)**: Бітова маска прапорів створення мапи. Обов'язково встановлюється прапор `BPF_F_MMAPABLE` (значення `0x400`), який дозволяє відображення мапи у простір користувача. До додаткових прапорів належать:
  - `BPF_F_NUMA_NODE` (`0x4`): вказує ядру прив'язати первинне виділення сторінок до конкретного NUMA-вузла, заданого у полі `numa_node`.
  - `BPF_F_SEGV_ON_FAULT` (`0x800`): вимагає від ядра надсилати сигнал `SIGSEGV` процесу користувача при спробі розіменування адреси в арені, для якої не виділено фізичну сторінку, замість повернення нульового значення.
  - `BPF_F_ZERO_SEED` (`0x40`): ініціалізує генератор псевдовипадкових чисел для внутрішніх алокаторів фіксованим зерном.
- **`max_entries` (`__u32`)**: Визначає максимальний обсяг віртуального адресного простору арени у **кількості сторінок пам'яті ядра** (page count). Оскільки на архітектурах x86-64 та ARM64 стандартний розмір сторінки дорівнює 4096 байт (`4 KB`), значення `1048576` задає зарезервований діапазон обсягом рівно 4 Гігобайти (`4 * 1024 * 1024 * 1024` байт).
- **`key_size` (`__u32`)**: Повинно суворо дорівнювати `0`. Арена є суцільним або розрідженим масивом пам'яті і не використовує ключі пошуку.
- **`value_size` (`__u32`)**: Повинно суворо дорівнювати `0`. Арена не має фіксованої структури елемента.
- **`map_extra` (`__u64`)**: Додаткове 64-бітне поле конфігурації. У контексті `BPF_MAP_TYPE_ARENA` значення `map_extra` інтерпретується як бажана стартова віртуальна адреса процесу користувача (`user_vm_start`). Якщо задано значення `0`, ядро самостійно обирає вільний діапазон віртуальних адрес під час виклику `mmap()`.

## 2. Системний виклик `mmap()` у просторі користувача

Для ініціалізації віртуального адресного простору арени у процесі користувача застосовується стандартний POSIX системний виклик `mmap()`, який виконується над файловим дескриптором мапи (`map_fd`), отриманим від системного виклику `bpf()`.

### 2.1 Сигнатура та семантика параметрів

```c
void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset);
```

- **`addr`**: Бажана віртуальна адреса у просторі користувача. Якщо розробник бажає жорстко зафіксувати початкову адресу (наприклад, для співпадіння з `map_extra`), передається конкретний вказівник. У більшості випадків передається `NULL`, що дозволяє ядру обрати оптимальну вирівняну адресу.
- **`length`**: Загальний обсяг зарезервованого віртуального простору в байтах. Значення має бути кратним розміру сторінки ядра (`PAGE_SIZE`) і обчислюється як `max_entries * PAGE_SIZE`.
- **`prot`**: Прапори захисту сторінок віртуальної пам'яті. Повинні включати `PROT_READ | PROT_WRITE`. Прапор `PROT_EXEC` заборонений із міркувань безпеки ядра.
- **`flags`**: Обов'язково повинен містити `MAP_SHARED`. Використання прапора `MAP_PRIVATE` викликає помилку `EINVAL`, оскільки приватні копії сторінок у режимі copy-on-write руйнують транзитивність C-вказівників між ядром та користувацьким простором.
- **`fd`**: Валідний файловий дескриптор відкритої мапи `BPF_MAP_TYPE_ARENA`.
- **`offset`**: Зсув у файлі мапи. Завжди повинен дорівнювати `0`.

### 2.2 Системні коди помилок `mmap()` та діагностика

При невдалому виконанні системний виклик `mmap()` повертає спеціальний вказівник `MAP_FAILED` (значення `(void *)-1`) і встановлює глобальну змінну `errno`.

| Код помилки (`errno`) | Фундаментальна причина дефекту | Алгоритм діагностики та виправлення |
| --- | --- | --- |
| `EINVAL` | Мапа не містить прапора `BPF_F_MMAPABLE`, параметр `offset != 0`, або використано `MAP_PRIVATE`. | Перевірити прапори при створенні мапи `bpf_map_create` та переконатися у використанні `MAP_SHARED` та `offset = 0`. |
| `ENOMEM` | Недостатньо безперервного віртуального адресного простору у процесі або перевищено ліміт `vm.max_map_count`. | Перевірити розмір адресного простору процесу, зменшити `max_entries` або збільшити лиміт `sysctl -w vm.max_map_count=262144`. |
| `EPERM` | Процес не має достатніх привілеїв `CAP_BPF` / `CAP_SYS_ADMIN` або обмежено `RLIMIT_MEMLOCK`. | Запустити процес з підвищеними правами або налаштувати `setrlimit(RLIMIT_MEMLOCK, ...)` на `RLIM_INFINITY`. |
| `EACCES` | Файловий дескриптор `fd` відкрито тільки у режимі читання, а `prot` вимагає `PROT_WRITE`. | Перевірити прапори відкриття дескриптора мапи у `bpf_obj_get()` або `bpf_map_create()`. |

## 3. Допоміжні функції ядра (eBPF Kernel Helpers)

Під час виконання BPF-програми у контексті ядра розробник може динамічно керувати виділенням та звільненням фізичних сторінок пам'яті усередині зарезервованого віртуального простору арени.

### 3.1 Хелпер `bpf_arena_alloc_pages`

Функція `bpf_arena_alloc_pages` здійснює динамічне виділення послідовної групи фізичних сторінок оперативної пам'яті у розрідженому просторі арени.

```c
void *bpf_arena_alloc_pages(void *map, void *addr, __u32 page_cnt, int node_id, __u64 flags);
```

- **`map`**: Вказівник на екземпляр мапи `BPF_MAP_TYPE_ARENA`.
- **`addr`**: Бажана адреса всередині віртуального простору арени. Якщо передано `NULL`, ядро автоматично знаходить перший вільний підрядний блок потрібного розміру. Якщо передано конкретну адресу у межах арени, ядро намагається виділити сторінки саме за цим оффсетом.
- **`page_cnt`**: Кількість послідовних фізичних сторінок пам'яті (4 KB), які необхідно виділити та відобразити.
- **`node_id`**: Ідентифікатор NUMA-вузла для виділення фізичної пам'яті. Значення `-1` (`NUMA_NO_NODE`) вказує виділяти пам'ять на тому NUMA-вузлі, де в даний момент виконується поточне ядро CPU.
- **`flags`**: Зарезервований бітовий прапор для майбутніх розширень ядра. У поточній версії ядра Linux (6.8+) повинен дорівнювати `0`.
- **Повертане значення**: Прямий 64-бітний C-вказівник з кваліфікатором `__arena` на початок виділеного регіону пам'яті. У разі відсутності вільної пам'яті чи некоректних параметрів повертається `NULL`.

### 3.2 Хелпер `bpf_arena_free_pages`

Функція `bpf_arena_free_pages` повертає раніше виділені фізичні сторінки пам'яті з розрідженого простору арени назад до загального пулу оперативної пам'яті ядра Linux.

```c
void bpf_arena_free_pages(void *map, void *addr, __u32 page_cnt);
```

- **`map`**: Вказівник на екземпляр мапи `BPF_MAP_TYPE_ARENA`.
- **`addr`**: Вказівник на початок регіону в арені, отриманий раніше від `bpf_arena_alloc_pages`.
- **`page_cnt`**: Кількість сторінок пам'яті, які необхідно звільнити.

## 4. Кваліфікатори LLVM/Clang та інструкції маскування JIT

Для забезпечення безпечного доступу до пам'яті арени за прямими C-вказівниками розробник зобов'язаний інформувати компілятор Clang про використання специфічного адресного простору BPF Arena.

### 4.1 Макровизначення кваліфікатора `__arena`

У мові C для BPF-цілі використовується атрибут `address_space(1)`:

```c
#if defined(__BPF__)
  #define __arena __attribute__((address_space(1)))
#else
  #define __arena
#endif
```

При компіляції коду Clang позначає всі операції завантаження (`load`) та збереження (`store`) за цими вказівниками спеціальним метатегом в LLVM IR (`addrspace(1)`). Це дає можливість BPF Verifier статично ідентифікувати звернення до арени та перевіряти коректність оффсетів.

### 4.2 Генерація машинних інструкцій JIT на x86-64 та ARM64

Під час JIT-компіляції BPF JIT engine перетворює абстрактні інструкції розіменування у захищену послідовність машинних команд процесора.

На архітектурі **x86-64** інструкція запису значення `data->value = 100` через вказівник арени розгортається у наступний асемблерний блок:

```assembly
; %rax містить 64-бітне значення вказівника арени
mov %eax, %eax        ; Занулення старших 32 біт %rax (примусове маскування 32-бітного offset)
add %r12, %rax        ; Додавання бази kern_vm_start (регістр %r12 зафіксовано під базу арени)
movq $100, (%rax)     ; Запис 64-бітного значення за обчисленою адресою фізичної сторінки
```

На архітектурі **ARM64 (AArch64)** використовується аналогічний механізм маскування з використанням регістра бази `x29` чи `x28` та інструкції `ubfx` (Unsigned Bitfield Extract):

```assembly
ubfx x0, x0, #0, #32  ; Витягнення нижніх 32 біт адреси (обнулення верхніх 32 біт)
add x0, x28, x0       ; Додавання бази kern_vm_start з регістра x28
str x1, [x0]          ; Збереження значення регістра x1 у пам'ять арени
```

Завдяки першій інструкції обнулення старших біт будь-яка спроба сформувати за межами арени пошкоджену адресу примусово згортається у межі зарезервованого 4-гігабайтного діапазону.

## 5. Системні параметри ядра Linux та sysctl

Налаштування поведінки BPF Arena та обмежень безпеки здійснюється через інтерфейс pseudo-файлової системи `/proc/sys/`.

### 5.1 Основні системні тунабли (`sysctl`)

- **/proc/sys/kernel/unprivileged_bpf_disabled**:
  - Значення `0`: дозволяє користувачам без привілеїв створювати арени та завантажувати BPF-програми.
  - Значення `1` або `2`: створення `BPF_MAP_TYPE_ARENA` вимагає наявності прав `CAP_BPF` або `CAP_SYS_ADMIN`.
- **/proc/sys/net/core/bpf_jit_enable**:
  - Повинно дорівнювати `1` або `2`. BPF Arena працює **виключно** при увімкненому JIT-компіляторі. Інтерпретатор BPF не підтримує розіменування прямих вказівників арени.
- **/proc/sys/vm/max_map_count**:
  - Визначає максимальну кількість регіонів віртуальної пам'яті, які процес може відобразити через `mmap()`. При створенні багатьох арена-регіонів це значення може вимагати збільшення (наприклад, `sysctl -w vm.max_map_count=262144`).

## 6. Зведення помилок верифікатора BPF та методів їх усунення

Під час завантаження BPF-програми з мапою арени верифікатор проводить статичний аналіз коду. У таблиці наведено типові текстові повідомлення про помилки та причини їх виникнення.

| Повідомлення верифікатора (`bpf_verifier_log`) | Фундаментальна причина дефекту | Спосіб усунення |
| --- | --- | --- |
| `R1 pointer arithmetic on arena_ptr prohibited` | Спроба виконання непідтримуваної математичної операції над базовим вказівником арени без маскування. | Використовувати кваліфікатор `__arena` або явно приводити типи через `(uintptr_t)`. |
| `arena access out of bounds` | Верифікатор виявив можливість виходу константного оффсету за межі зарезервованого розміру `max_entries`. | Перевірити межі масиву або додати явну перевірку `if (offset < ARENA_SIZE)`. |
| `cannot use arena without JIT` | Система запущена з вимкненим JIT-компілятором BPF. | Увімкнути JIT прапором `sysctl net.core.bpf_jit_enable=1`. |
| `invalid address_space ID` | Використано невірний числовий ідентифікатор адресного простору (наприклад `address_space(2)` замість `1`). | Використовувати суворо `__attribute__((address_space(1)))`. |

## 7. Практичні рекомендації щодо сумісності C та C++

При збірці проекту, що використовує BPF Arena, заголовочні файли зі структурами даних повинні бути сумісними як з C-компілятором Clang для цілі BPF, так і з C++17/C++20 компілятором простору користувача.

```cpp
#ifndef SHARED_ARENA_TYPES_H
#define SHARED_ARENA_TYPES_H

#include <stdint.h>

#if defined(__cplusplus)
extern "C" {
#endif

#if defined(__BPF__)
  #define BPF_ARENA_PTR(type) type __attribute__((address_space(1))) *
#else
  #define BPF_ARENA_PTR(type) type *
#endif

struct arena_header {
    uint32_t magic;
    uint32_t version;
    uint64_t total_pages;
    uint64_t allocated_bytes;
};

struct arena_node {
    uint64_t id;
    uint64_t payload;
    BPF_ARENA_PTR(struct arena_node) next;
};

#if defined(__cplusplus)
}
#endif

#endif /* SHARED_ARENA_TYPES_H */
```

Такий підхід забезпечує абсолютну бінарну сумісність C-структур даних без розсунення полів через розбіжності кваліфікаторів адресного простору між компілятором ядра та простору користувача.
