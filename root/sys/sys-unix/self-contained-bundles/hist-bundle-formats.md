# 📜 Історія самодостатніх пакунків: від Klik та Zero Install до AppImage, Flatpak і Snap

Еволюція форматів самодостатніх пакунків у Linux — це двадцятирічна історія спроб подолати суворі обмеження файлової ієрархії FHS та традиційних пакетних менеджерів, які вимагали єдиного версіонування системних бібліотек для всієї операційної системи.

## Передумови: Біль класичного лінкування у світі FHS та стандартизації LSB

На початку 1990-х років дистрибутиви Linux (Debian, Red Hat, Slackware, Mandrake) сформували класичну модель розповсюдження програмного забезпечення. У цій моделі кожна програма розпаковувалася у спільне файлове дерево FHS: виконувані бінарники розміщувалися у `/usr/bin`, бібліотеки — у `/usr/lib`, конфігураційні файли — у `/etc`, а ресурси та локалізації — у `/usr/share`.

Поки дистрибутив залишався замкненою монолітною екосистемою із фіксованим репозиторієм, така система працювала ідеально, економлячи оперативну пам'ять та дисковий простір за рахунок спільного використання динамічних `.so`-бібліотек. Проте спроба незалежного розробника випустити нову версію застосунку для кількох дистрибутивів одразу наражалася на нездоланні перешкоди:

1. **Фрагментація C-бібліотек та ABI:** Бінарник, зкомпільований у Fedora під певну версію `glibc`, відмовлявся запускатися в Debian або Slackware через розбіжності символів ABI C-бібліотеки.
2. **Конфлікти версій залежностей (Dependency Hell):** Одна програма вимагала для роботи `libpng 1.2`, а інша — новішу `libpng 1.6`. Встановити обидві програми у системні каталоги `/usr/lib` без пошкодження залежностей було неможливо.
3. **Провал стандарту LSB (Linux Standard Base):** Спроба створити єдину базову специфікацію ABI для всіх дистрибутивів виявилася занадто жорсткою та повільною: розробники дистрибутивів оновлювали бібліотеки швидше, ніж комітет LSB затверджував нові стандарти.
4. **Потреба в привілеях root:** Встановлення звичайного користувацького застосунку вимагало прав адміністратора системи (`sudo apt install` або `rpm -i`), що створювало ризики для стабільності всієї ОС.

Пошук альтернатив почався з ідеї: програма має нести власні залежності із собою та запускатися без модифікації базової системи.

## Перші експерименти: Klik (2004)

У 2004 році німецький розробник Саймон Пітер (Simon Peter) започаткував проект **Klik** (інколи описувався як `klik`). Ідея Klik була революційною для свого часу: користувач завантажував один файл з розширенням `.cmg`, робив його виконуваним і запускав подвійним клацанням миші в графічному середовищі.

Під капотом `.cmg`-файл являв собою стиснений образ файлової системи `cramfs` (пізніше `isofs` та `cromfs`). При запуску спеціальний скрипт утилізував механізм `appelf` або логіку `LD_PRELOAD`, щоб перехоплювати системні виклики відкриття файлів та перенаправляти їх усередину змонтованого образу в `/tmp/klik/`.

Klik довів, що концепція «один файл = один застосунок» життєздатна на Linux. Проте проект мав серйозні обмеження:
* Потребував встановленого в систему фонового демона та налаштованого FUSE. На ядрах Linux 2.4/2.6 FUSE ще не мав сучасної стабільності.
* Не мав жодної ізоляції чи пісочниці: програма мала повні права користувача, який її запустив.
* Механізм перехоплення шляхів через `LD_PRELOAD` часто ламався на бінарниках із зі складним динамічним завантаженням через `dlopen()`.

## Децентралізація без FUSE: Zero Install (2005)

Приблизно в той самий час Томас Леонард (Thomas Leonard) розробляє **Zero Install (0install)**. Проект підійшов до проблеми з іншого боку: замість пакування бінарників у єдиний образ файлової системи, Zero Install запропонував мережево-центричну модель розгортання.

У Zero Install кожна програма та кожна бібліотека описувалися XML-маніфестом, доступним за URL-адресою. Коли користувач запускав програму за її URL-адресою:
1. `0install` завантажував XML-опис програми.
2. Алгоритм вирішення залежностей (SAT-solver) обчислював граф сумісних версій бібліотек.
3. Потрібні архіви завантажувалися у локальний криптографічно захищений кеш користувача (`~/.cache/0install.net/`).
4. Застосунок запускався з модифікованими змінними середовища (`LD_LIBRARY_PATH`, `PATH`), які вказували на розпаковані дерев'яні кеші бібліотек.

Zero Install уперше реалізував повністю децентралізоване розгортання ПЗ без root-прав із математично вивіреним вирішенням конфліктів залежностей. Проте необхідність постійного мережевого інструментарію та відсутність стандартного рантайму графічних бібліотек завадили масовому прийняттю 0install звичайними користувачами.

## Концепція спільних рантаймів: Limba та xdg-app (2011–2015)

До 2010-х років стало зрозуміло: якщо пакувати *абсолютно всі* бібліотеки у кожну програму, розмір пакунків стає гігантським, а дублювання GTK/Qt та системних графічних стеків виснажує оперативну пам'ять.

У 2014 році Маттіас Клумпп (Matthias Klumpp), відомий за проектом AppStream, започаткував проект **Limba**. Limba використовувала концепцію атомних пакунків на основі файлової системи SquashFS та надавала чітку мову маніфестів. Основне досягнення Limba полягало у введенні поняття **рантаймів (Runtimes)**: базових комплектів бібліотек (наприклад, "GNOME 3.16 Runtime"), від яких могли залежати окремі пакунки.

Майже одночасно Александр Ларссон (Alexander Larsson) із компанії Red Hat розпочав роботу над проектом **xdg-app**. Ларссон пішов далі: окрім спільних рантаймів він інтегрував у xdg-app новітні механізми ізоляції ядра Linux — простори імен (namespaces), `cgroups` та утиліту `bubblewrap`.

У 2016 році проект `xdg-app` пройшов ребрендинг і отримав назву **Flatpak**. Створення відкритого каталогу **Flathub** у 2017 році зробило Flatpak головним стандартом ізольованої дистрибуції десктопних застосунків для GNOME, KDE та більшості незалежних Linux-дистрибутивів.

## Поява AppImage v2 (2016)

Саймон Пітер не покинув ідею Klik. Переосмисливши досвід десятиліття, у 2016 році він випустив **AppImageKit** другого покоління (AppImage v2).

AppImage відмовився від складної архітектури демонів та пісочниць на користь максимальної простоти:
* Файл AppImage став гібридом ELF-бінарника та образу SquashFS.
* ELF-заголовок містив вбудовану компактну бібліотеку FUSE (`squashfuse`), яка монтувала решту файлу прямо в `/tmp`.
* Програма не вимагала встановлення жодного системного пакунка: запустити `.AppImage` можна було на будь-якому Linux-дистрибутиві, де працював FUSE та сумісна версія `glibc`.

AppImage здобув величезну популярність серед розробників портативного ПЗ, утиліт для усунення несправностей, утиліт розгортання та крос-платформних інструментів (Krita, Inkscape, Cura, LibreOffice).

## Спеціалізація Canonical: Click, Snappy та Snap (2014–2016)

Компанія Canonical (розробник Ubuntu) у 2013-2014 роках зіштовхнулася з необхідністю оновлення ПЗ на мобільній платформі Ubuntu Touch. Традиційний `apt`/`.deb` не гарантував атомарності оновлень і міг пошкодити пристрій при раптовому вимкненні живлення. Перша спроба створення пакунків Click для мобільних систем показала потребу в більш потужному інструменті.

Для вирішення цієї задачі Canonical створила систему **Snappy**, пізніше перейменовану на **Snap**.
На відміну від Flatpak, який від початку створювався виключно для графічних застосунків десктопа, Snap розроблявся як універсальний формат:
* Здатний пакувати системні демони, фонові служби (Nextcloud, Docker, Database engines), серверні CLI-інструменти та системні ядра.
* Використовував AppArmor замість `bubblewrap` для контролю доступу на рівні ядра Linux.
* Забезпечував автоматичне оновлення у фоновому режимі з можливістю миттєвого відкату (`snap revert`).

Примусова інтеграція Snap в Ubuntu (зокрема переведення пакетів Chromium та Firefox на Snap) викликала гострі дискусії в спільноті через пропрієтарну природу сервера Snap Store та повільніший перший запуск, проте Snap міцно закріпився як стандарт в Ubuntu Server та Ubuntu Core.

## Підсумок еволюції

Історичний шлях самодостатніх пакунків у Linux демонструє визрівання трьох чітких архітектурних концепцій:

| Ера / Проект | Ключова технологічна ідея | Головний недолік або виклик |
| :--- | :--- | :--- |
| **Klik (2004)** | Динамічне перехоплення шляхів через `LD_PRELOAD` та `cramfs` | Ламкість при складному `dlopen`, відсутність ізоляції |
| **Zero Install (2005)** | Децентралізований криптографічний кеш бібліотек за URL | Складність для звичайного користувача, відсутність стандарту графічного рантайму |
| **Limba (2014)** | Спільні Runtimes + SquashFS пакунки під управлінням PackageKit | Складність інтеграції з дистрибутивами |
| **AppImage (2016)** | Автономний ELF-враппер + SquashFS через FUSE у 1 файлі | Відсутність пісочниці за замовчуванням та автоматичної дедуплікації |
| **Flatpak (2016)** | Спільні рантайми OSTree + ізоляція Bubblewrap + Portals | Обмеженість десктопним ПЗ, відсутність підтримки серверних демонів |
| **Snap (2016)** | Loop-пристрої SquashFS + підсистема `snapd` + AppArmor | Централізований Store, підвищена затримка першого запуску |

Сьогодні всі три формати співіснують в екосистемі Linux, покриваючи різні ніші: AppImage — для автономних портативних програм, Flatpak — для безпечного десктопу, Snap — для системного та серверного ПЗ в інфраструктурі Ubuntu.
