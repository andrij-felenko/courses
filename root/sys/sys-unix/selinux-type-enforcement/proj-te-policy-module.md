# ⚙️ Розробка, компіляція та підключення модуля політики Type Enforcement

Цей практичний проєкт демонструє повний цикл розробки власного модуля політики SELinux для ізоляції власного демона простору користувача. У цьому керівництві розглядаються створення вихідних файлів правил Type Enforcement (`.te`) та специфікації контекстів файлової системи (`.fc`), використання компілятора `checkmodule` та пакувальника `semodule_package`, завантаження політики у ядро та перевірка обмежень доступу за допомогою тестової програми мовами C та C++.

## 1. Постановка задачі та архітектура модуля

Під час розробки власних мережевих служб або системних демонів стандартна цільова політика дистрибутива не містить готового домену для нової програми. Якщо виконати програму без створення власного модуля політики, вона запускатиметься у домені `unconfined_t` (де відсутній захист Type Enforcement) або у домені `initrc_t` (де доступ обмежений загальними правилами, що спричинить численні AVC denial).

Розглянемо практичний сценарій: ми розробляємо сервісний демон `mydaemon`, який поводиться так:
1. Виконується з бінарного файла за шляхом `/usr/bin/mydaemon`.
2. Зчитує конфігураційний файл `/etc/mydaemon/mydaemon.conf`.
3. Пише журнали дій у файл `/var/log/mydaemon.log`.
4. Відкриває та слухає мережевий TCP-порт `9999`.

Головна мета політики SELinux — ізолювати цей процес у власному домені `mydaemon_t` так, щоб демон міг читати лише свій конфігураційний файл, писати лише у свій лог-файл і слухати лише свій порт. Навіть якщо процес буде скомпрометований через вразливість у коді, ядро Linux блокуватиме будь-яку спробу прочитати чужі файли в `/etc/`, дістатися до `/etc/shadow` чи виконати командну оболонку `/bin/sh`.

Для побудови надійної системи ізоляції ми повинні чітко розібрати кожен етап створення правил, розібратися у механізмах макросів SELinux Reference Policy, а також вивчити процес компіляції та завантаження модуля у ядро.

При проєктуванні архітектури нового модуля політики спочатку потрібно визначити всі сутності файлової системи та мережеві ресурси, з якими взаємодіє демон. Кожен ресурс повинен отримати свій унікальний тип. Якщо два файли мають різний ступінь критичності (наприклад, конфігураційний файл тільки для читання та лог-файл для запису), їм обов'язково призначаються різні типи (`mydaemon_conf_t` та `mydaemon_log_t`). Це дотримується фундаментального принципу найменших привілеїв (Principle of Least Privilege).

Крім того, варто заздалегідь зважити на можливість взаємодії з іншими системними службами. Наприклад, якщо демон надсилає системні логи через сокет `/dev/log`, модулю знадобляться правила взаємодії з доменом `syslogd_t`. Якщо демон запускається менеджером systemd, перехід домену буде ініційовано від `init_t`. Чітке визначення меж домену є першим кроком розробки безпечної політики.

Альтернативним шляхом інтеграції з менеджером systemd є використання директиви `SELinuxContext=` у юніт-файлі сервісу (`/etc/systemd/system/mydaemon.service`). При наявності цієї директиви systemd виконує виклик `setexeccon()` до запуску `execve()`, що гарантує перехід у заданий домен навіть за відсутності автоматичного виклику `type_transition`. Проте створення явних правил у мові `.te` залишається стандартним і більш надійним підходом.

## 2. Створення вихідних файлів модуля політики

Для створення та збирання модуля політики SELinux потрібні два файли: файл правил Type Enforcement (`mydaemon.te`) та файл специфікації контекстів файлової системи (`mydaemon.fc`).

### 2.1. Файл політики Type Enforcement (`mydaemon.te`)

Файл `.te` описує оголошення типів, асоціацію з ролями та явні правила дозволу `allow`.

Розберемо макроси політики більш детально. Інструкція `policy_module(mydaemon, 1.0.0)` задає унікальне ім'я модуля у системному реєстрі та його семантичну версію. Під час завантаження менеджер політик перевіряє версію модуля і замінює існуючі правила, якщо модуль із таким ім'ям вже було встановлено раніше.

Макрос `init_daemon_domain(mydaemon_t, mydaemon_exec_t)` розгортається під час компіляції у групу правил, серед яких обов'язкові:
1. Призначення атрибута `domain` для `mydaemon_t` та атрибута `exec_type` для `mydaemon_exec_t`.
2. Правило `type_transition init_t mydaemon_exec_t : process mydaemon_t;`, яке автоматично переключає домен процесу при запуску через `init_t`.
3. Дозвіл `allow mydaemon_t mydaemon_exec_t : file entrypoint;`, який оголошує бінарний файл легітимною точкою входу.
4. Дозвіл `allow init_t mydaemon_t : process transition;`, який дозволяє системі ініціалізації перемикати контекст.
5. Дозвіл успадкування файлових дескрипторів та відправки сигналів завершення `sigchld`.

Макрос `files_type(mydaemon_conf_t)` зв'язує тип конфігураційних файлів із системним атрибутом `file_type` та `non_security_file_type`, що дозволяє іншим загальним правилам політики (наприклад, правилам резервного копіювання) правильно взаємодіяти з цим файлом без порушення цілісності.

Додатково, макрос `logging_log_file(mydaemon_log_t)` надає типу логів атрибути `log_file_type`. Це автоматично підключає правила ротації журналів демоном `logrotate`, дозволяючи ротаційним службам перейменовувати та стискати файли у `/var/log/` без виникнення відмов доступу.

Сформований на основі цих макросів файл політики `mydaemon.te` має наступний вигляд:

```pp
policy_module(mydaemon, 1.0.0)

########################################
# Оголошення типів та доменів
########################################

# Оголошення домену процесу та виконуваного файла
type mydaemon_t;
type mydaemon_exec_t;

# Макрос ініціалізації домену демона (створює правила entrypoint та transition від init_t)
init_daemon_domain(mydaemon_t, mydaemon_exec_t)

# Оголошення типу для конфігураційних файлів
type mydaemon_conf_t;
files_type(mydaemon_conf_t)

# Оголошення типу для файлів журналів
type mydaemon_log_t;
logging_log_file(mydaemon_log_t)

########################################
# Правила Type Enforcement (allow)
########################################

# Дозволити домену mydaemon_t пошук у каталогах та читання власного конфіга
allow mydaemon_t mydaemon_conf_t : file { read getattr open };
allow mydaemon_t mydaemon_conf_t : dir { search getattr };

# Дозволити домену mydaemon_t створення та запис у власний лог-файл
allow mydaemon_t mydaemon_log_t : file { create write append getattr open };
allow mydaemon_t mydaemon_log_t : dir { write add_name search };

# Дозволити створення, прив'язку та слухання мережевого TCP-сокета
allow mydaemon_t self : tcp_socket { create bind listen accept read write };

# Порт 9999 дістає власний тип, і прив'язка дозволена саме до нього.
# Сам номер порту реєструється командою:
#   semanage port -a -t mydaemon_port_t -p tcp 9999
type mydaemon_port_t;
corenet_port(mydaemon_port_t)
allow mydaemon_t mydaemon_port_t : tcp_socket name_bind;
```

У складніших модулях політики Reference Policy також створюється третій файл — файл інтерфейсів `mydaemon.if`. У ньому оголошуються багаторазові макроси (інтерфейси), які дозволяють іншим модулям взаємодіяти з `mydaemon`. Наприклад, якщо іншому домену потрібно читати конфігураційний файл `mydaemon_conf_t`, у `mydaemon.if` створюється макрос `mydaemon_read_config(domain)`, який усередині розгортає правило `allow $1 mydaemon_conf_t : file read_file_perms;`.

Файл інтерфейсів `.if` використовує препроцесор `m4` для підстановки аргументів. Використання стандартних інтерфейсів замість сирих правил `allow` є золотим стандартом розробки політик під SELinux Reference Policy, оскільки воно запобігає прямому зверненню до приватних типів інших модулів і забезпечує інкапсуляцію типів.

### 2.2. Файл контекстів файлової системи (`mydaemon.fc`)

Файл `.fc` описує відповідність між регулярними виразами шляхів на диску та контекстами безпеки, які призначаються утилітою `restorecon`.

Синтаксис специфікації файлових контекстів використовує розширені регулярні вирази POSIX. Символи `--` вказують, що правило застосовується лише до звичайних файлів (регулярні файли). Якби нам потрібно було позначити весь каталог та його вміст, використовувався б регулярний вираз `/var/log/mydaemon(/.*)?`.

Макрос `gen_context(system_u:object_r:mydaemon_exec_t,s0)` забезпечує сумісність як із цільовою політикою `targeted` (де використовується рівень `s0`), так і з повними військовими конфігураціями `mls`, підставляючи необхідні параметри чутливості за замовчуванням.

Специфікація контекстів обробляється функцією `selabel_lookup()` бібліотеки `libselinux`. Коли додаток або команда `restorecon` запитує правильний тип для файла, бібліотека порівнює абсолютний шлях із регулярними виразами у файлі `.fc`. У разі перекриття декількох виразів перемагає більш специфічний регулярний вираз (правило з більшою довжиною точного збігу символів).

З урахуванням цих механізмів приклад специфікації у файлі `mydaemon.fc` має наступний вигляд:

```
/usr/bin/mydaemon          -- gen_context(system_u:object_r:mydaemon_exec_t,s0)
/etc/mydaemon/mydaemon\.conf -- gen_context(system_u:object_r:mydaemon_conf_t,s0)
/var/log/mydaemon\.log     -- gen_context(system_u:object_r:mydaemon_log_t,s0)
```

## 3. Конвеєр компіляції, пакування та завантаження

Збирання та активація модуля політики SELinux виконується за чотири послідовні кроки у терміналі:

1. **Компіляція вихідного тексту `.te` у бінарний модуль `.mod`:**
   ```bash
   checkmodule -M -m -o mydaemon.mod mydaemon.te
   ```
   Утиліта `checkmodule` здійснює синтаксичний аналіз файлу `.te` й будує проміжний бінарний модуль `mydaemon.mod`. Правила `neverallow` базової політики на цьому кроці ще не перевіряються: модуль компілюється сам по собі, а суперечності виявляються пізніше, коли `semodule` зв'язує його з рештою політики. Прапорець `-M` вмикає підтримку MLS/MCS, а прапорець `-m` вказує створити окремий завантажувальний модуль.

2. **Пакування модуля `.mod` та опису контекстів `.fc` у файл пакета `.pp`:**
   ```bash
   semodule_package -o mydaemon.pp -m mydaemon.mod -f mydaemon.fc
   ```
   Утиліта `semodule_package` об'єднує бінарний модуль політики та специфікацію контекстів файлів у єдиний файл пакета `mydaemon.pp` (Policy Package).

3. **Інсталяція та завантаження модуля у ядро Linux:**
   ```bash
   sudo semodule -i mydaemon.pp
   ```
   Утиліта `semodule` вставляє новий модуль у системне сховище модулів (`/var/lib/selinux/targeted/active/modules/`), виконує лінкування з іншими модулями, будує підсумковий бінарний файл політики та записує його у ядро через `/sys/fs/selinux/load`.

4. **Застосування правильних контекстів до файлів на диску:**
   ```bash
   sudo restorecon -v /usr/bin/mydaemon /etc/mydaemon/mydaemon.conf /var/log/mydaemon.log
   ```
   Утиліта `restorecon` прочитує нові правила з бази даних файлових контекстів і оновлює атрибут `security.selinux` для відповідних інодів.

Під час виконання `semodule -i` у сучасних дистрибутивах (таких як RHEL 9 або Fedora) використовується внутрішній транслятор CIL (Common Intermediate Language). Бінарні файли `.pp` розпаковуються і перетворюються у вихідні інструкції CIL, після чого монолітний бінарний файл політики ядра `policy.33` компілюється в оперативній пам'яті й записується через псевдофайл `/sys/fs/selinux/load`. Цей процес є атомарним: якщо у модулі виявлено помилку, ядро зберігає попередню версію політики і не порушує роботу працюючих служб.

Сховище модулів політики розташоване у файловій системі за шляхом `/var/lib/selinux/targeted/active/modules/100/mydaemon/`. У цьому каталозі зберігаються компресовані файли інструкції `cil`, файли контекстів `file_contexts` та описи відношень. Завдяки цій структурі адміністратор може в будь-який момент переглянути список інстальованих кастомних модулів або видалити конкретний модуль за допомогою команди `semodule -r mydaemon`.

Якщо в процесі інсталяції `semodule -i` виникає помилка конфлікту типів (наприклад, `duplicate declaration of type mydaemon_t`), це свідчить про те, що інший модуль політики вже оголосив тип із таким самим іменем. Для вирішення таких колізій у мові CIL застосовуються простори імен (namespaces) та блоки `block`, які ізолюють оголошення типів усередині окремого контексту модуля.

При створенні складних системних модулів часто використовується автоматизований конвеєр на основі `Makefile`. Команда `make -f /usr/share/selinux/devel/Makefile mydaemon.pp` дозволяє виконати всі кроки попередньої обробки `m4`, компіляції `checkmodule` та пакування `semodule_package` однією інструкцією.

Для розгортання модулів політики у масштабованих інфраструктурах (з використанням Ansible або Puppet) розробники запаковують готовий `.pp` файл у RPM-пакет програми. У пост-інсталяційному скрипті RPM-пакета (`%post`) виконуються виклики `semodule -n -i mydaemon.pp` (де ключ `-n` скасовує негайне перезавантаження політики у ядро), а потім один підсумковий `load_policy` та `restorecon`. Це прискорює встановлення й запобігає багаторазовому скиданню кешу AVC.

Важливим кроком валідації зібраного модуля є перевірка відсутності порушень правил `neverallow`. Команда `sepolgen-ifgen` генерує індекс наявних інтерфейсів для `audit2allow -R`, а самі `neverallow` перевіряються під час складання підсумкової політики командою `semodule -i`: якщо модуль надає доступ до критичних типів на кшталт `shadow_t` чи `kmem_t`, встановлення провалюється й у ядро нічого не потрапляє.

## 4. Перевірка обмежень доступу (Test Harness)

Нижче наведено код тестового додатка `mydaemon`, який виконує дві дії: намагається записати рядок у свій лог-файл `/var/log/mydaemon.log` та намагається прочитати файл `/etc/shadow`.

При виконанні у домені `mydaemon_t` перша дія завершується успішно, а друга викликає відмову `EACCES` під дією SELinux Type Enforcement.

:::tabs
```c
/* C: Тестовий демон для перевірки обмежень SELinux Type Enforcement */
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>
#include <errno.h>

int main(void) {
    printf("=== Запуск перевірки доступу демона mydaemon ===\n");

    /* 1. Спроба запису у власний лог-файл (Дозволено правилом allow у mydaemon.te) */
    const char *log_path = "/var/log/mydaemon.log";
    int log_fd = open(log_path, O_WRONLY | O_CREAT | O_APPEND, 0640);
    if (log_fd < 0) {
        fprintf(stderr, "[ПОМИЛКА] Запис у лог %s відхилено: %s\n", log_path, strerror(errno));
    } else {
        const char *msg = "Демон успішно стартував і записав лог під доменом mydaemon_t.\n";
        write(log_fd, msg, strlen(msg));
        close(log_fd);
        printf("[ОК] Запис у власний лог-файл пройшов успішно.\n");
    }

    /* 2. Спроба читання чужого файла /etc/shadow (Заборонено політики SELinux TE) */
    const char *shadow_path = "/etc/shadow";
    int shadow_fd = open(shadow_path, O_RDONLY);
    if (shadow_fd < 0) {
        printf("[ОК] Спробу читання %s заблоковано SELinux! Причина: %s (errno=%d)\n", 
               shadow_path, strerror(errno), errno);
    } else {
        fprintf(stderr, "[УВАГА] Порушення безпеки: демон зміг прочитати %s!\n", shadow_path);
        close(shadow_fd);
    }

    return 0;
}
```

```cpp
// C++: Ідіоматична реалізація тестового демона з RAII та обробкою помилок через std::system_error
#include <iostream>
#include <fstream>
#include <string>
#include <system_error>
#include <cerrno>

class daemon_tester {
public:
    static void test_log_access(const std::string& log_path) {
        std::ofstream log_stream(log_path, std::ios::app);
        if (!log_stream.is_open()) {
            std::cerr << "[ПОМИЛКА] Не вдалося відкрити лог " << log_path << ": "
                      << std::system_error(errno, std::generic_category()).what() << "\n";
            return;
        }
        log_stream << "C++ Демон успішно записав рядок у лог під доменом mydaemon_t.\n";
        std::cout << "[ОК] Запис у власний лог-файл пройшов успішно.\n";
    }

    static void test_unauthorized_access(const std::string& secret_path) {
        std::ifstream secret_stream(secret_path);
        if (!secret_stream.is_open()) {
            std::cout << "[ОК] Спробу читання " << secret_path 
                      << " заблоковано SELinux! Причина: "
                      << std::system_error(errno, std::generic_category()).what() 
                      << " (errno=" << errno << ")\n";
        } else {
            std::cerr << "[УВАГА] Помилка безпеки: відкрити " << secret_path << " вдалося!\n";
        }
    }
};

int main() {
    std::cout << "=== Запуск C++ перевірки доступу демона mydaemon ===\n";

    daemon_tester::test_log_access("/var/log/mydaemon.log");
    daemon_tester::test_unauthorized_access("/etc/shadow");

    return 0;
}
```
:::

Простежимо, що саме відбувається всередині ядра при виклику `open("/etc/shadow", O_RDONLY)` з точки зору перевірки прав:

1. Стандартна підсистема VFS отримує виклик `sys_openat()` і виконує розбір шляху.
2. Проводиться первинна перевірка прав DAC на основі `uid`, `gid` та бітів режиму `0000` для не-root процесів.
3. Оскільки процес виконується з правами root або має `CAP_DAC_OVERRIDE`, перевірка DAC переходить до виклику гачка LSM `security_file_open()`.
4. Модуль SELinux витягує `sid` процесу (домен `mydaemon_t`) та `sid` інода `/etc/shadow` (тип `shadow_t`).
5. Викликається функція `avc_has_perm(mydaemon_t_sid, shadow_t_sid, SECCLASS_FILE, FILE__READ)`.
6. Пошук у кеші AVC повертає відсутність дозволеного біта `FILE__READ`.
7. Системний виклик повертає відмову `-EACCES`, а підсистема аудиту записує повідомлення про відмову у лог аудиту.

При запуску тестової програми під утилітою `runcon` можна явно перевірити роботу в домені без створення системного юніта systemd:
```bash
# Запуск тестової програми у домені mydaemon_t
runcon -t mydaemon_t ./mydaemon
```

Якщо домен `mydaemon_t` було скомпоновано правильно, консольний вивід підтвердить успішне створення лог-файлу та успішне блокування спроби читання файла `/etc/shadow`.

Корисним прийомом під час розробки нових політик є тимчасове переведення конкретного домену в режим Permissive без переведення всієї системи. Команда `semanage permissive -a mydaemon_t` вказує ядру логувати всі відмови для домену `mydaemon_t`, але не блокувати їх. Це дозволяє розробникові зібрати повне трасування системних викликів застосунку за один прохід, після чого згенерувати фінальний список правил `allow` за допомогою `audit2allow` і скасувати permissive-режим командою `semanage permissive -d mydaemon_t`.

Коли додаток використовує додаткові системні ресурси (наприклад, відкриває UNIX-сокети для відправки логів у `rsyslogd` або підключається до бази даних PostgreSQL), у логах з'являться нові AVC denial. Замість додавання сирих правил `allow` до `.te` вручну, розробник аналізує вивід `audit2allow -i /var/log/audit/audit.log` і замінює сирі правила відповідними макросами Reference Policy (наприклад, `sysnet_dns_name_resolve(mydaemon_t)` замість серії низькорівневих `allow` для сокетів DNS).

Важливо пам'ятати про перевірку правильної ротації лог-файлів при розробці. Якщо у списку правил модуля відсутній дозвіл `unlink` або `rename` для `mydaemon_log_t`, демон `logrotate` під час нічної ротації не зможе перейменувати `/var/log/mydaemon.log` у `/var/log/mydaemon.log.1`. Підключення стандартизованого макроса `logging_log_file(mydaemon_log_t)` запобігає цій проблемній ситуації, автоматично надаючи необхідні права системній службі логування.

Підсумкова верифікація модуля проводиться перевіркою контексту за допомогою `ps -eZ | grep mydaemon` під час роботи демона під управлінням systemd. Це гарантує, що сервіс закритий у власному домені й повністю ізольований від інших процесів у системі. Практичне тестування у Permissive режимі дає змогу виявити непередбачені системні виклики та додати потрібні вектори доступу до офіційного релізу модуля політики SELinux.

## 5. Перевірка статусу завантаженого модуля та видалення

Управління станом модуля у ядрі вимагає узгодженого оновлення двійкової політики та кешуючих структур. При видаленні модуля утиліта `semodule` автоматично вилучає його правила з активного ядра, очищає записи в кеші AVC і перераховує залежності типів. Якщо на типи цього модуля посилаються інші встановлені модулі, `semodule` повідомить про незадоволену залежність і скасує видалення, щоб у політиці не лишилося посилань на неоголошені типи.

Видалення модуля негайно вилучає його правила з активного ядра, а наступні виклики демона `mydaemon` будуть блокуватися або переходити у дефолтний домен.

Для перевірки наявності модуля у списку завантажених та його вилучення після завершення тестування застосовуються відповідні команди утиліти `semodule`:

```bash
# Перевірка наявності модуля у списку
sudo semodule -l | grep mydaemon

# Видалення модуля політики після завершення тестування
sudo semodule -r mydaemon
```
