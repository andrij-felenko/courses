# 📋 Інтерфейси віддаленої атестації: /dev/sev-guest та /dev/tdx-guest

У гостьовій операційній системі під керуванням Linux взаємодія програми простору користувача з апаратними співпроцесорами та прошивками безпеки реалізована через концепцію системних символьних пристроїв (Character Devices). Для захищених віртуальних машин на базі технології AMD SEV-SNP таким пристроєм є `/dev/sev-guest`, а для машин на базі Intel TDX — пристрій `/dev/tdx-guest`.

Ці драйвери ядерного рівня виконують роль безпечного посередника між простором користувача гостя та закритими інструкціями мікрокоду процесора. Вони надають стандартний системний інтерфейс викликів `ioctl()`, дозволяючи прикладним програмам або агентам атестації передавати до апаратури довільний криптографічний вектор (nonce) та отримувати у відповідь підписаний апаратний звіт (Attestation Report чи TD Quote), який містить стан початкового виміру пам'яті (Launch Digest).

---

## 1. Архітектура та програмний контракт AMD SEV-SNP (`/dev/sev-guest`)

Драйвер ядра Linux `sev-guest` (вихідний код у `drivers/virt/coco/sev-guest/sev-guest.c`) реєструє символьний пристрій `/dev/sev-guest`. Він працює поверх підсистеми взаємодії з апаратним співпроцесором AMD Secure Processor (ASP), використовуючи спеціальний зв'язаний буфер GHCB (Guest-Hypervisor Communication Block).

### Механізм захисту від атак повтору через лічильники послідовностей

Під час ініціалізації гостьової ВМ процесор ASP узгоджує з гостьовим ядром чотири унікальні симетричні ключі перевірки — **VMPCK0, VMPCK1, VMPCK2, VMPCK3** (по одному для кожного рівня привілеїв VMPL). Кожне повідомлення, що відправляється через `/dev/sev-guest` до ASP, шифрується алгоритмом AES-256-GCM.

Щоб запобігти атакам повторного відтворення (replay attack) з боку компрометованого гіпервізора, драйвер ядра підтримує монотонно зростаючий лічильник послідовності `vmpck_seq`. Якщо гіпервізор відхилить або повторно подасть записаний раніше зашифрований пакет, процесор ASP виявить розбіжність лічильника послідовності та відкине повідомлення як підробку.

### Системні структури даних заголовка `<linux/sev-guest.h>`

Взаємодія з пристроєм виконується через керуючу структуру `snp_guest_request_ioctl`, яка загортає запит та відповідь:

:::tabs
```c
struct snp_guest_request_ioctl {
    /* Версія протоколу повідомлення (зазвичай 1) */
    __u8 msg_version;
    
    /* Указівник на структуру запиту користувача в пам'яті (struct snp_report_req*) */
    __u64 req_data;
    
    /* Указівник на буфер відповіді в пам'яті (struct snp_report_resp*) */
    __u64 resp_data;
    
    /* Код помилки, повернутий прошивкою AMD ASP у разі апаратного збою */
    __u64 fw_error;
};

struct snp_report_req {
    /* 64 байти випадкових користувацьких даних (nonce або хеш публічного ключа TLS) */
    __u8 user_data[64];
    
    /* Рівень привілеїв ВМ, для якого запитується звіт (VMPL 0..3) */
    __u32 vmpl;
    
    /* Зарезервовані байти для майбутніх розширень (заповнюються нулями) */
    __u8 rsvd[28];
};

struct snp_report_resp {
    /* Сирий буфер підписаного звіту атестації (1184 байти корисного навантаження) */
    __u8 data[4000];
};
```
```cpp
namespace sev {

struct alignas(8) snp_guest_request_ioctl {
    uint8_t msg_version{1};
    uint64_t req_data{0};
    uint64_t resp_data{0};
    uint64_t fw_error{0};
};

struct snp_report_req {
    std::array<uint8_t, 64> user_data{};
    uint32_t vmpl{0};
    std::array<uint8_t, 28> rsvd{};
};

struct snp_report_resp {
    std::array<uint8_t, 4000> data{};
};

} // namespace sev
```
:::

### Детальна розкладка полів звіту `snp_attestation_report` (1184 байти)

Після успішного виконання `ioctl(fd, SNP_GET_REPORT, &ioctl_req)` у буфері `resp.data` повертається криптографічно підписана бінарна структура з такою точною розкладкою полів:

| Зсув | Тип даних | Назва поля | Опис та семантика вмісту |
| :--- | :--- | :--- | :--- |
| `0x000` | `uint32_t` | `version` | Версія структури звіту (значення `1` або `2`) |
| `0x004` | `uint32_t` | `guest_svn` | Security Version Number гостьової системи |
| `0x008` | `uint64_t` | `policy` | Бітова маска політики безпеки (Debug, SMT, Single Socket) |
| `0x010` | `uint8_t[16]`| `family_id` | Унікальний ідентифікатор родини гостьових ВМ |
| `0x020` | `uint8_t[16]`| `image_id` | Унікальний ідентифікатор образу гостя |
| `0x030` | `uint32_t` | `vmpl` | Рівень VMPL, на якому було згенеровано звіт |
| `0x034` | `uint32_t` | `signature_algo` | Алгоритм цифрового підпису (`1` = ECDSA P-384 з SHA-384) |
| `0x038` | `uint64_t` | `current_tcb` | Поточний рівень TCB прошивки та мікрокоду процесора |
| `0x040` | `uint64_t` | `platform_info` | Прапорці стану платформи (TSME, SMT enabled) |
| `0x048` | `uint32_t` | `author_key_en` | Прапор активності ключа автора образу (0 або 1); далі 4 зарезервовані байти |
| `0x050` | `uint8_t[64]`| `report_data` | **Ехо користувацьких даних**: 64 байти `user_data` із запиту |
| `0x090` | `uint8_t[48]`| `measurement` | **Launch Digest**: SHA-384 хеш початкового стану DRAM |
| `0x0C0` | `uint8_t[32]`| `host_data` | 32 байти додаткових даних, переданих гіпервізором при старті |
| `0x0E0` | `uint8_t[48]`| `id_key_digest`| SHA-384 хеш публічного ключа ідентифікації ID Key |
| `0x110` | `uint8_t[48]`| `author_key_digest`| SHA-384 хеш публічного ключа автора |
| `0x140` | `uint8_t[32]`| `report_id` | Унікальний ідентифікатор даного конкретного звіту |
| `0x160` | `uint8_t[32]`| `report_id_ma`| Ідентифікатор звіту для процедури Live Migration |
| `0x180` | `uint64_t` | `reported_tcb` | Рівень TCB, з яким підписано звіт |
| `0x2A0` | `uint8_t[512]`| `signature` | **Апаратний підпис ECDSA P-384**: компоненти R та S |

Команда `ioctl`:
- `SNP_GET_REPORT` — розраховується як `_IOWR('S', 0x0, struct snp_guest_request_ioctl)`

## 2. Архітектура та програмний контракт Intel TDX (`/dev/tdx-guest`)

У середовищі Intel TDX взаємодія з підсистемою атестації реалізована через драйвер ядра `tdx-guest` (файл `drivers/virt/coco/tdx-guest/tdx-guest.c`) та символьний пристрій `/dev/tdx-guest`.

### Двоступенева модель атестації Intel: `TDREPORT` та `TD Quote`

На відміну від AMD, де апаратний співпроцесор ASP одразу формує асиметричний підпис ECDSA, компанія Intel реалізувала двоступеневу схему віддаленої атестації для оптимізації швидкодії:

1. **Локальний звіт `TDREPORT`**: Гостьова ВМ викликає інструкцію `TDCALL[TDG.MR.REPORT]`. Модуль TDX Module у режимі SEAM миттєво генерує структуру `TDREPORT` (1024 байти) і підписує її **симетричним ключем HMAC-SHA-384**, доступним лише даному процесору. Це відбувається за частки мікросекунди.
2. **Асиметрична котировка `TD Quote`**: Оскільки симетричний MAC-підпис не може бути перевірений зовнішньою третьою стороною (бо ключ MAC не можна відкривати світу), гостьова ОС передає `TDREPORT` через спеціальний сокет хоста до службового анклаву **Intel SGX Quoting Enclave (QGS)**. Анклав QGS перевіряє HMAC-підпис локально, і якщо він дійсний, перепідписує звіт асиметричним ECDSA-ключами **PCK (Provisioning Certification Key)**, отримуючи фінальний документ — `TD Quote`.

### Структури даних заголовка `<linux/tdx-guest.h>`

Для отримання локального звіту з ядра гостя використовується структура `tdx_report_req`:

:::tabs
```c
struct tdx_report_req {
    /* 64 байти користувацьких даних (nonce або ефемерний хеш) */
    __u8 reportdata[64];
    
    /* Вихідний буфер для прийняття апаратного звіту TDREPORT (1024 байти) */
    __u8 tdreport[1024];
};
```
```cpp
namespace tdx {

struct tdx_report_req {
    std::array<uint8_t, 64> reportdata{};
    std::array<uint8_t, 1024> tdreport{};
};

} // namespace tdx
```
:::

Команда `ioctl`:
- `TDX_CMD_GET_REPORT0` — розраховується як `_IOWR('T', 0x1, struct tdx_report_req)`

### Формат структури `TDREPORT` (1024 байти)

Структура `TDREPORT` складається з чотирьох основних блоків:

```
+------------------------------------------------------------------+
| REPORTMACSTRUCT (256 байтів) -> HMAC-SHA-384, CPU TCB і всередині |
|                                 нього REPORTDATA (64 байти nonce) |
+------------------------------------------------------------------+
| TEE_TCB_INFO    (239 байтів) -> Версії прошивок та мікрокоду     |
+------------------------------------------------------------------+
| RESERVED        (17 байтів)  -> Нульове вирівнювання             |
+------------------------------------------------------------------+
| TDINFO          (512 байтів) -> Виміри MRTD, RTMR[0..3] та атрибути|
+------------------------------------------------------------------+
```

Найважливішим блоком для перевірки довіри є підструктура **`TDINFO`**:

| Поле у `TDINFO` | Розмір | Опис |
| :--- | :--- | :--- |
| `ATTRIBUTES` | 8 байтів | Атрибути домену (Debug Mode, SEPT VE Disable та інші прапорці) |
| `XFAM` | 8 байтів | Extended Features Available Mask (AVX-512, AMX state) |
| `MRTD` | 48 байтів | **Measurement of TD**: SHA-384 хеш початкового коду ВМ |
| `MRCONFIGID` | 48 байтів | Хеш конфігураційного опису ВМ |
| `MROWNER` | 48 байтів | Хеш ідентифікатора власника Trust Domain |
| `MROWNERCONFIG` | 48 байтів | Додатковий конфігураційний хеш власника |
| `RTMR[0]` | 48 байтів | **Runtime Measurement Register 0**: завантажувач та прошивка |
| `RTMR[1]` | 48 байтів | **Runtime Measurement Register 1**: ядро Linux та initramfs |
| `RTMR[2]` | 48 байтів | **Runtime Measurement Register 2**: конфігурація операційної системи |
| `RTMR[3]` | 48 байтів | **Runtime Measurement Register 3**: користувацькі динамічні розширення |

## 3. Діагностика помилок та розшифровка кодів повернення

Під час виконання системних викликів `ioctl()` до захищених пристроїв можливі два рівні помилок: помилки системного виклику ядра Linux (`errno`) та помилки апаратного мікрокоду прошивки.

### Помилки системного виклику ядра (`errno`)

- **`EACCES` (Permission Denied)**: Спроба відкрити символьний пристрій без привілеїв суперкористувача `root`. За замовчуванням udev призначає пристроям маску прав `0600`.
- **`ENODEV` / `ENXIO` (No such device)**: Модуль ядра `sev-guest` або `tdx-guest` не завантажено, або ядро працює на звичайній віртуальній машині без підтримки конфіденційних обчислень.
- **`EFAULT` (Bad Address)**: Передано некоректний вказівник на структуру в користувацькій пам'яті (помилка мапування сторінок у просторі користувача).
- **`EINVAL` (Invalid Argument)**: Некоректний розмір буфера або непідтримуване значення `msg_version`.

### Специфічні коди помилок прошивки AMD ASP (`fw_error`)

Якщо `ioctl()` завершується помилкою, а поле `ioctl_req.fw_error` містить ненульове значення, причина — у відмові апаратного співпроцесора ASP. Числові значення цих кодів задає ABI прошивки SEV-SNP і від версії до версії вони змінюються, тому в коді слід звірятися з константою, а не з «магічним» числом:

| Константа прошивки | Причина та спосіб усунення |
| :--- | :--- |
| `SUCCESS` (нуль) | Операцію виконано успішно |
| `INVALID_PARAM` | Некоректні параметри у структурі запиту `snp_report_req` — зокрема запитаний рівень VMPL, вищий за поточний |
| `INVALID_LEN` | Наданий буфер відповіді замалий для звіту цієї версії |
| `BUSY` | Співпроцесор ASP зайнятий обробкою іншого криптографічного запиту — потрібен повтор із затримкою |
