# 📜 Як з'явився devres: боротьба з «goto err_*» та народження керованих ресурсів

На зламі 2006–2007 років ядро Linux 2.6 стрімко розширювало підтримку різноманітного обладнання. Кількість драйверів пристроїв у дереві вихідного коду перевищила половину всього кодового масиву ядра. З появою шин гарячого підключення (USB, IEEE 1394, CardBus), систем динамічного керування живленням та мобільних процесорів (ARM SoC) життєвий цикл драйвера перестав бути статичним: пристрої тепер постійно з'являлися, ініціалізувалися, засинали, прокидалися та відключалися наживо під час роботи операційної системи.

## Епідемія помилок у коді ініціалізації

Традиційна функція `probe()` для ініціалізації типового пристрою виглядала як довгі «сходи» захоплення системних ресурсів: виділення структури приватного стану, блокування та відображення діапазонів фізичної пам'яті MMIO, отримання тактових генераторів, резервування ліній GPIO, налаштування регуляторів напруги, запит ліній переривань та реєстрація у відповідному класі ядра (мережевий інтерфейс, блоковий пристрій або датчик).

Кожен із цих кроків міг завершитися помилкою: шинний діапазон міг бути вже зайнятий іншим драйвером, тактовий сигнал ще не ініціалізований, а пам'ять ядра — вичерпана. Щоб коректно повернути ядро в чистий початковий стан, розробник мусив у кожній точці відмови відкотити назад рівно ті операції, які вже були успішно виконані, і саме у зворотному порядку.

Єдиним доступним інструментом у мові C був ланцюжок міток `goto`:

```c
static int legacy_probe(struct platform_device *pdev)
{
	/* 1. Пам'ять */
	priv = kzalloc(sizeof(*priv), GFP_KERNEL);
	if (!priv)
		return -ENOMEM;

	/* 2. MMIO */
	res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
	if (!res) {
		ret = -EINVAL;
		goto err_free_priv;
	}
	priv->regs = ioremap(res->start, resource_size(res));
	if (!priv->regs) {
		ret = -ENOMEM;
		goto err_free_priv;
	}

	/* 3. Тактування */
	priv->clk = clk_get(&pdev->dev, NULL);
	if (IS_ERR(priv->clk)) {
		ret = PTR_ERR(priv->clk);
		goto err_unmap;
	}

	/* 4. Переривання */
	ret = request_irq(priv->irq, isr_handler, 0, "legacy", priv);
	if (ret)
		goto err_put_clk;

	return 0;

err_put_clk:
	clk_put(priv->clk);
err_unmap:
	iounmap(priv->regs);
err_free_priv:
	kfree(priv);
	return ret;
}
```

На практиці цей підхід спричинив масштабну кризу надійності:

1. **Невідповідність черговості:** під час доопрацювання драйвера розробники додавали новий ресурс (наприклад, регулятор живлення) посеред функції, але забували додати відповідний `goto` або розташовували мітку очищення в хибній точці хвоста функції.
2. **Асиметрія між відмовою та вивантаженням:** код відкату при помилці в `probe()` дублював логіку функції `remove()`, але писався вручну окремо. У результаті одна функція звільняла ресурси правильно, а інша пропускала виклик `clk_put()` або `iounmap()`.
3. **Непомітність дефектів під час тестування:** аварійні гілки `probe()` рідко спрацьовують на етапі розробки (на стенді інженера залізо зазвичай справне і пам'яті вистачає). Дефекти очищення залишалися прихованими, доки драйвер не стикався з нестачею пам'яті у реальному продакшені або відкладеною ініціалізацією (`-EPROBE_DEFER`).

Перші статичні аналізатори коду ядра (зокрема Smatch та Coverity) у 2005–2006 роках знаходили сотні витоків ресурсів саме в обробниках помилок `probe()`.

## Ініціатива Теджуна Хьо

У грудні 2006 року інженер Теджун Хьо (Tejun Heo), який активно займався розробкою підсистеми `libata` (SATA-контролери) та шини PCI, опублікував патч-серію з концепцією **Device Resource Management (devres)**.

Ідея полягала в тому, щоб прив'язати життєвий цикл кожного виділеного ресурсу безпосередньо до базової структури `struct device`. Оскільки кожен драйвер у моделі пристроїв Linux прив'язується до конкретного екземпляра `struct device` на час своєї роботи, ядро може автоматично відстежувати всі створені цим драйвером залежності.

Якщо `probe()` завершується успішно, ресурси залишаються активними до моменту вилучення пристрою або вивантаження модуля. Якщо ж `probe()` повертає будь-який від'ємний код помилки, ядро драйверів самостійно викликає централізовану функцію розмотування `devres_release_all()`, яка послідовно виконує деструктори зареєстрованих об'єктів у строгому порядку LIFO (Last In, First Out).

## Дискусії на LKML та прийняття канону

Патч викликав жваве обговорення в розсилці ядра (Linux Kernel Mailing List). Основними запереченнями опонентів були:

- **Приховані дії («Магія»):** традиційний підхід ядра вимагав абсолютної прозорості кожного виклику. Деякі мейнтейнери побоювалися, що розробники перестануть розуміти, коли саме звільняється пам'ять чи знімається переривання.
- **Накладні витрати на пам'ять:** для кожного керованого об'єкта підсистема виділяє службовий заголовок `struct devres_node`, що додає 32–48 байтів накладних витрат у пам'яті SLAB на кожен ресурс.
- **Накладні витрати процесора:** пошук та проходження по зв'язаному списку `devres_head` під час вивантаження вимагали взяття спін-блокування `devres_lock`.

Теджун Хьо та прихильники підходу (зокрема Грег Кроа-Гартман, Greg Kroah-Hartman) навели переконливі контраргументи:

1. Функція `probe()` викликається лише під час виявлення пристрою, а `remove()` — під час його відключення. Це «холодні» шляхи виконання (control path), де кілька десятків мікросекунд і кілька сотень байтів пам'яті є мізерною ціною за стовідсоткову гарантію відсутності витоків пам'яті та завислих переривань.
2. Порядок LIFO точно відповідає правилам конструювання та знищення об'єктів у надійних архітектурах (подібно до деструкторів у RAII).

У версії ядра **Linux 2.6.21** (квітень 2007 року) підсистему `devres` було офіційно включено до основного дерева ядра.

## Еволюція та сучасний стан

Після успішного старту з функцій `devm_kzalloc()` та `devm_ioremap()` концепція охопила всі підсистеми ядра:

- **2011–2013 роки:** впровадження стандартизованого помічника `devm_ioremap_resource()`, який об'єднав перевірку меж, резервування шинного регіону та відображення MMIO з поверненням типізованого коду помилки `ERR_PTR`.
- **2013–2015 роки:** Ларс-Петер Клаузен (Lars-Peter Clausen) запропонував механізм універсальних користувацьких дій `devm_add_action()` та `devm_add_action_or_reset()`. Це дозволило перетворювати будь-яку нестандартну функцію звільнення чи деініціалізації заліза на керований ресурс без написання складного низькорівневого коду `devres_alloc()`.
- **Сучасне ядро (6.x):** з'явилися помічники високого рівня на зразок `devm_clk_get_enabled()`, `devm_regulator_get_enable()` та автоматичне керування доменами живлення (Runtime PM via devm).

Завдяки `devres` обсяг типового платформеного драйвера в ядрі Linux скоротився на 30–50%, а складні функції `remove()` у більшості драйверів сенсорів, годинників реального часу (RTC) та інтерфейсів шин стали або тривіальними, або взагалі порожніми.
