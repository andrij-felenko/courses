Копіювання системного образу розміром 40 гігабайтів на віддалений сервер через ненадійний трансатлантичний лінк переривається на 98% через короткочасний тайм-аут мережі. Якщо передавання велося наївним потоковим інструментом без збереження стану, весь обсяг доведеться перекачувати з першого байта, витративши ще дві години каналу. Якщо ж для копіювання дистрибутива застосувати утиліту зі скиданням бітів прав, виконувані бінарники втратять прапорець `chmod +x`, а символьні посилання перетворяться на важкі дублікати файлів.

Ще критичнішою стає ціна небезпечних інструментів: запуск класичного копіювання з підстановкою шаблону шляху на скомпрометований сервер дозволяє віддаленій системі тихо перезаписати локальний конфігураційний файл `~/.bashrc` або ключі `authorized_keys` на комп'ютері адміністратора.

Передавання даних через захищений протокол SSH вирішує ці задачі через три принципово різні архітектурні моделі: неструктурований конвеєр виконання процесів (`scp`), бінарний клієнт-серверний протокол файлових запитів зі станом (`sftp`) та розподілену систему дельта-синхронізації з ковзним хешуванням (`rsync`).

*Три архітектурні моделі передачі через SSH: конвеєрний запуск через оболонку (класичний SCP), бінарний фреймовий RPC-протокол підсистеми (SFTP) та дельта-синхронізація через захищений пайп (Rsync).*

## Три підходи до транспорту файлів

Будь-яке передавання файлів через комп'ютерну мережу зводиться до розв'язання чотирьох задач: як доставити масив байтів, як узгодити структуру каталогів і метадані, як захистити потік від підміни та що робити при повторній передачі частково змінених даних.

SSH бере на себе криптографічний транспорт — взаємну автентифікацію хостів, шифрування каналу та перевірку цілісності повідомлень. Проте те, як саме файли формуються, відкриваються й відновлюються, повністю визначається протоколом прикладного рівня:

1. **Потокова передача без стану (класичний протокол SCP):** Програма відкриває SSH-сеанс, запускає на віддаленій машині командну оболонку з процесом приймача і викачує послідовність байтів із примітивними текстовими заголовками. Процес не має випадкового доступу до довільного місця файлу, не вміє перевіряти стан цілі й не підтримує докачування.
2. **Файлова RPC-підсистема (протокол SFTP):** Клієнт запитує запуск спеціалізованої підсистеми SSH (`subsystem sftp`). Взаємодія відбувається через бінарні пакети фіксованого формату: відкрити дескриптор, прочитати порцію за зміщенням, записати блок, прочитати запис каталогу, закрити дескриптор. Це повноцінна віддалена файлова система, пристосована для ізоляції користувачів у межах обмеженого дерева `chroot`.
3. **Дельта-синхронізація блоків (Rsync over SSH):** Клієнт запускає віддалений екземпляр `rsync --server` і з'єднує локальний та віддалений процеси двостороннім каналом зв'язку (пайпом). Обидві сторони обчислюють сигнатури блоків наявних файлів і передають через мережу виключно різницю між ними, оновлюючи цільові файли атомарно.

Розуміння меж кожного з цих трьох інструментів починається з аналізу того, чому найстаріший із них — утиліта `scp` — виявився архітектурним глухим кутом.

## Класичний SCP: спадок RCP, віддалена оболонка та вразливості

Історично утиліта `scp` з'явилася 1995 року як пряма заміна нешифрованої утиліти `rcp` з операційної системи 4.2BSD (1983 рік). Замість розробки нового файлового протоколу творець першої версії SSH Тату Ілонен просто переніс код протоколу RCP всередину шифрованого SSH-каналу.

Детальний історичний шлях еволюції протоколів, від Berkeley r-commands до критичних звітів з безпеки, викладено в [історичній розвідці про перехід від rcp до SFTP](root:sys-unix/file-transfer-over-ssh/hist-rcp-to-sftp.md).

### Механізм виконання віддаленої команди

Коли користувач виконував команду завантаження:

```bash
scp user@server.remote:/var/log/app/*.log /local/backup/
```

клієнтська програма `scp` не відправляла структурованого запиту до файлової служби. Вона конструювала текстовий рядок для запуску на сервері:

```bash
ssh user@server.remote "scp -f /var/log/app/*.log"
```

Прапорець `-f` (*from*) вказував віддаленому бінарнику `scp` працювати в режимі джерела даних (для вивантаження на сервер використовувався прапорець `-t`, тобто *to/target*).

Демон `sshd` на сервері приймав запит на відкриття сеансу, автентифікував користувача і запускав його системну оболонку входу:

```bash
$SHELL -c "scp -f /var/log/app/*.log"
```

Саме оболонка сервера (наприклад, `/bin/bash` або `/bin/sh`) виконувала розкриття маски шляху `*.log` у конкретний список файлів і передавала їх через масив аргументів `argv` процесу `scp -f`. Після цього серверний `scp` надсилав у потік stdout текстові рядки протоколу RCP:

```text
C0644 14502 app.log\n
<14502 байти вмісту app.log>
\0
```

де `C` — створення файлу, `0644` — вісімкові біти прав, `14502` — довжина вмісту в байтах, після чого передавалися сирі байти даних, а клієнт підтверджував прийом нульовим байтом `\0`.

### Чому ця схема зламалася

У такій архітектурі були закладені три фундаментальні вади:

1. **Ін'єкція команд через імена файлів:** Якщо назва файлу на віддаленому сервері містила пробіли, лапки або спецсимволи командної оболонки (наприклад, `file$(reboot).txt`), недбало викликана оболонка інтерпретувала вставку як запуск команди. Щоб уникнути помилок, користувачам доводилося застосовувати потрійне екранування лапками або бекслешами.
2. **Підміна шляхів клієнта (CVE-2019-6111):** Протокол RCP не мав жодної прив'язки між файлом, який запитав клієнт, і файлом, який йому повернув сервер. Клієнт надсилав запит `scp -f *.log`. Якщо віддалений сервер було зламано зловмисником, підроблений процес сервера замість файлів логів міг надіслати директиву `C0644 2048 ../.bashrc\n` з шкідливим вмістом. Локальний процес `scp` читав це ім'я і сліпо перезаписував файл конфігурації оболонки поточного користувача.
3. **Маніпуляція виводом термінала (CVE-2019-6109):** Сервер міг включити керуючі послідовності ANSI у назву файлу, через що локальний прогрес-бар у консолі перемальовувався так, що користувач бачив завантаження нешкідливого `test.txt`, хоча у фоновому режимі записувалися системні файли.

### Перехід OpenSSH 9.0+ на протокол SFTP

У релізі OpenSSH 9.0 (квітень 2022 року) розробники ухвалили радикальне рішення: **утиліту `scp` переписали так, щоб під капотом вона використовувала підсистему SFTP як транспорт за замовчуванням**.

Сучасний клієнт `scp`:
- Відкриває захищений SSH-канал підсистеми `sftp` без запуску віддаленої оболонки `$SHELL`.
- Передає шляхи безпосередньо у бінарних викликах протоколу SFTP, де вони не проходять через парсер оболонки.
- Обходить каталоги за допомогою викликів `SSH_FXP_READDIR`, самостійно контролюючи відповідність імен шаблонам на клієнтському боці.
- Зберігає звичний користувацький інтерфейс (`scp -r user@host:/dir /local`).

Для взаємодії зі старими маршрутизаторами або вбудованими пристроями, де немає сервера SFTP, залишено аварійний прапорець `-O` (*legacy SCP protocol*), який змушує клієнт використовувати старий небезпечний протокол RCP.

## Підсистема SFTP: архітектура, internal-sftp та ізоляція ChrootDirectory

SFTP (*SSH File Transfer Protocol*) — це незалежний бінарний клієнт-серверний протокол прикладного рівня, який працює поверх довільного надійного двостороннього потоку байтів, найчастіше всередині мультиплексованого каналу SSH.

Повний перелік параметрів конфігурації, прапорців CLI та статус-кодів протоколу наведено у [довіднику параметрів SFTP та прапорців rsync](root:sys-unix/file-transfer-over-ssh/api-sftp-subsystem-and-rsync.md).

### Бінарні фрейми та модель запит-відповідь

На відміну від неструктурованого потоку `scp`, кожне повідомлення SFTP упаковане в суворий бінарний фрейм:

```text
+-------------------+------------------+-------------------+-----------------------+
| Довжина (uint32)  |  Тип (uint8)     | Request ID (u32)  |   Дані (Payload)      |
|    4 байти        |     1 байт       |     4 байти       |     N байтів          |
+-------------------+------------------+-------------------+-----------------------+
```

1. **Довжина:** точний розмір решти пакета в байтах.
2. **Тип повідомлення:** байтовий код операції (наприклад, `SSH_FXP_OPEN = 3`, `SSH_FXP_READ = 5`, `SSH_FXP_WRITE = 6`, `SSH_FXP_STATUS = 101`, `SSH_FXP_DATA = 103`).
3. **Request ID:** унікальний числовий ідентифікатор запиту, який генерує клієнт.

Завдяки наявності `Request ID` протокол SFTP підтримує **асинхронну чергу запитів (pipelining)**: клієнт не зобов'язаний чекати на відповідь після кожного відправленого блоку. Він може відправити одночасно 16 або 32 запити `SSH_FXP_READ` на різні зміщення файлу (паралельні чанки по 32 КБ) і приймати відповіді в міру їх надходження, утилізуючи повну пропускну здатність мережі з великою затримкою (RTT).

### sftp-server проти internal-sftp

У конфігурації демона `sshd` (`/etc/ssh/sshd_config`) підсистема оголошується директивою `Subsystem`:

```text
# Варіант 1: Зовнішній бінарний сервер
Subsystem sftp /usr/lib/openssh/sftp-server

# Варіант 2: Вбудований обробник (рекомендований)
Subsystem sftp internal-sftp -l VERBOSE
```

Різниця між ними є принциповою для адміністрування та безпеки:

- `/usr/lib/openssh/sftp-server` — це окремий виконуваний бінарник. Коли клієнт запитує підсистему, `sshd` викликає `fork()`, виконує автентифікацію, створює оточення користувача і кличе `execve("/usr/lib/openssh/sftp-server")`. Якщо користувач ізольований у каталозі `chroot`, усередині цього ізольованого дерева повинні бути присутні динамічний завантажувач, спільні бібліотеки `libc.so`, `/dev/null` та системні конфіги.
- `internal-sftp` — це модуль, скомпільований безпосередньо всередині самого бінарника `sshd`. При підключенні `sshd` не викликає жодної зовнішньої програми. Після успішного виклику системного виклику `chroot()` процес переходить у цикл обробки SFTP-пакетів. **Усередині ізольованого каталогу користувача не потрібно створювати жодного системного файлу, пристрою чи бібліотеки.**

![Ізоляція користувача SFTP у ChrootDirectory за допомогою internal-sftp](/root/sys/sys-unix/file-transfer-over-ssh/img/sftp-chroot-jail.svg)

*Модель безпеки ChrootDirectory: жорстка вимога права власності root:root 0755 для кореневого jail-каталогу та надання доступу на запис лише у вкладені підкаталоги.*

### Налаштування безпечного SFTP-Jail (ChrootDirectory)

Типова задача системного адміністрування — надати зовнішньому користувачеві чи сервісу доступ для завантаження файлів, повністю заборонивши інтерактивний термінальний доступ до операційної системи.

Конфігурація у `/etc/ssh/sshd_config`:

```text
# Вимикаємо оболонку для групи sftponly
Match Group sftponly
    ChrootDirectory /var/sftp/%u
    ForceCommand internal-sftp -u 0022 -l INFO
    AllowTcpForwarding no
    X11Forwarding no
    AllowAgentForwarding no
    PasswordAuthentication yes
```

Залізне правило безпеки `ChrootDirectory`:
`sshd` перед входом користувача рекурсивно перевіряє право власності на всі компоненти шляху `ChrootDirectory`. **Каталог `/var/sftp/%u` і кожен його батьківський каталог (`/var`, `/var/sftp`) повинні належати виключно користувачеві `root:root` і не мати права на запис для інших (`chmod 0755`).**

Якщо це правило порушено (наприклад, `/var/sftp/user` належить самому користувачеві `user`), `sshd` відмовить у підключенні з помилкою в системному журналі:

```text
fatal: bad ownership or modes for chroot directory "/var/sftp/user"
```

Це обмеження захищає систему від атаки виходу з `chroot`: якби користувач міг писати в корінь свого ізольованого дерева, він міг би підмінити файли конфігурації або бібліотеки, якими користується привілейований процес.

Для організації завантаження адміністратор створює окремий вкладений каталог:

```bash
# 1. Створення користувача без права входу в командну оболонку
useradd -m -g sftponly -s /usr/sbin/nologin sftpuser

# 2. Налаштування кореня chroot (тільки root!)
chown root:root /var/sftp/sftpuser
chmod 0755 /var/sftp/sftpuser

# 3. Створення каталогу для файлів із правами користувача
mkdir -p /var/sftp/sftpuser/uploads
chown sftpuser:sftponly /var/sftp/sftpuser/uploads
chmod 0775 /var/sftp/sftpuser/uploads
```

Користувач після підключення бачить каталог `/var/sftp/sftpuser` як корінь `/`, не може вийти вище нього, не має доступу до утиліт оболонки і може записувати дані в каталог `/uploads`.

### Автоматизація через пакетний режим (Batch Mode)

Для автоматичних завдань резервного копіювання чи деплою `sftp` підтримує виконання командних файлів через прапорець `-b`:

```bash
sftp -b /opt/scripts/backup_task.sftp -i /etc/backup/id_ed25519 backup_bot@storage.internal
```

Вміст файлу `backup_task.sftp`:

```text
# Створення каталогу дати
-mkdir backups/2026-08-25
cd backups/2026-08-25
# Вивантаження зі збереженням атрибутів
put -p /var/backups/db_dump.sql.zst
put -p /var/backups/etc_backup.tar.zst
# Перевірка вільного місця на сховищі
df -h
quit
```

Префікс дефіса `-` перед командою (наприклад, `-mkdir`) наказує клієнту проігнорувати можливу помилку (каталог уже існує) і продовжувати виконання наступних інструкцій.

## Синхронізація дерев через rsync поверх SSH

Коли стоїть завдання синхронізувати складні ієрархії каталогів із мільйонами файлів або оновити великі бінарні бази даних, де зміни торкнулися лише кількох відсотків вмісту, звичайне копіювання через `scp` або `sftp` марнує гігабайти трафіку, передаючи кожен файл повторно.

Утиліта `rsync` (автори Ендрю Тріджелл та Пол Маккерас) вирішує цю проблему за допомогою дельта-алгоритму передачі блоків через захищений SSH-канал зв'язку.

![Трифазний дельта-алгоритм синхронізації rsync](/root/sys/sys-unix/file-transfer-over-ssh/img/rsync-delta-cycle.svg)

*Три фази роботи дельта-алгоритму rsync: генерація таблиці сигнатур цільового файлу, побайтовий пошук збігів ковзним вікном і реконструкція нового файлу з локальних блоків та мережевих літералів.*

### Архітектура процесу та взаємодія через пайп

Синхронізація `rsync` через SSH не використовує спеціалізованих демонів на сервері (якщо не задіяно режим standalone rsync daemon). Вона працює повністю через стандартний клієнт `ssh`:

```bash
rsync -avz -e "ssh -i /path/to/key" /local/data/ user@remote.server:/remote/data/
```

Під капотом відбуваються такі системні виклики:
1. Локальний процес `rsync` (клієнт/відправник) викликає `pipe()` для створення двох пар файлових дескрипторів, робить `fork()` і запускає через `execvp()` клієнт SSH:
   ```bash
   ssh -l user remote.server rsync --server -logDtprze.iLsfxCIvu . /remote/data/
   ```
2. SSH-клієнт з'єднується з віддаленим сервером, автентифікується і просить серверний `sshd` запустити процес `rsync --server`.
3. Усі наступні керуючі повідомлення та блоки даних циркулюють виключно через стандартні потоки вводу-виводу (stdin/stdout) між двома екземплярами `rsync`, зашифровані проміжним транспортним тунелем SSH.

### Дельта-алгоритм: три фази оновлення файлу

Якщо цільовий файл із таким самим ім'ям уже існує на сервері, але відрізняється вмістом, rsync не передає його цілком. Запускається трифазний дельта-алгоритм:

#### Фаза 1: Генерація сигнатур блоків (Receiver / Generator)
Одержувач розбиває свій старий файл розміром N_B на блоки фіксованого розміру S (зазвичай від 512 до 2048 байтів). Для кожного i-го блоку обчислюються два хеші:
1. **Слабкий 32-бітний ковзний хеш (rollsum):** швидка сума за алгоритмом типу Adler-32.
2. **Сильний 128-бітний хеш:** криптографічний хеш (MD4, MD5 або xxHash у сучасних версіях).

Одержувач відправляє таблицю цих хешів назад відправнику через SSH-пайп.

#### Фаза 2: Сканування ковзним вікном (Sender)
Відправник бере свій свіжий файл A і починає рухатися по ньому вікном розміру S, починаючи зі зміщення 0:
- На кожному кроці обчислюється 32-бітний `rollsum` поточного вікна.
- Перерахунок `rollsum` при зсуві на 1 байт виконується за **сталий час O(1)**: від значення суми віднімається старий байт, що вийшов з вікна, і додається новий байт, що увійшов.
- Якщо поточний `rollsum` збігається з одним із хешів у таблиці одержувача, відправник обчислює над цим вікном сильний 128-бітний хеш.
- Якщо сильний хеш також збігся — знайдено точний збіг блоку. Відправник надсилає одержувачу команду `MATCH(block_index)`, пересуває вікно вперед на S байтів і скидає ковзну суму.
- Якщо збігу немає — поточний байт додається до буфера незбіжних даних (*literal data*), а вікно зсувається всього на 1 байт праворуч.

Алгоритмічна структура ковзного хешування та повний робочий код генератора дельти на C і C++ наведені у [практичній реалізації ковзного хешу rsync](root:sys-unix/file-transfer-over-ssh/proj-rolling-checksum-sync.md).

#### Фаза 3: Реконструкція файлу та атомарна заміна (Receiver)
Одержувач створює новий прихований файл у тому самому каталозі з назвою вигляду `.filename.XXXXXX`.
- Отримавши токен `MATCH(i)`, одержувач зчитує i-й блок із наявного локального старого файлу і записує його у тимчасовий файл.
- Отримавши токен `LITERAL(bytes)`, одержувач записує сирі байти, надіслані через мережу.
- Коли збирання завершено, одержувач обчислює цілісний хеш усього відновленого файлу і звіряє його з контрольним хешем відправника.
- Якщо хеш зійшовся, виконується системний виклик `rename(".filename.XXXXXX", "filename")`. Завдяки властивостям файлової системи POSIX оновлення файлу відбувається **атомарно**: сторонні процеси, які читають старий файл, не побачать напівзаписаного стану.

### Збереження метаданих: розбір прапорців `-aHAX`

Режим архівування `rsync -a` (`--archive`) є найчастішим вибором для резервного копіювання, оскільки об'єднує сім обов'язкових параметрів:

```text
-a  ===  -r (рекурсія) + -l (симлінки) + -p (права) + -t (час mtime) + -g (група) + -o (власник) + -D (пристрої/спеціальні)
```

Проте для повноцінного перенесення системних образів і резервних копій прапорця `-a` недостатньо. Необхідно додавати специфічні модифікатори:

| Прапорець | Призначення та поведінка |
|---|---|
| `-H` (`--hard-links`) | Збереження жорстких посилань. Без цього прапорця два файли з однаковим номером inode будуть скопійовані як два окремі незалежні файли, збільшивши зайнятий дисковий простір. |
| `-A` (`--acls`) | Збереження розширених списків контролю доступу POSIX ACL. |
| `-X` (`--xattrs`) | Збереження розширених атрибутів файлової системи, включно з контекстами безпеки SELinux/AppArmor та кастомними атрибутами `user.*`. |
| `--numeric-ids` | Збереження числових ідентифікаторів UID та GID без перекладу в імена через системну службу NSS на цільовій машині. Запобігає спотворенню прав, якщо ім'я користувача на сервері має інший числовий UID. |
| `--delete` | Видалення на цільовому боці тих файлів, які були видалені у джерелі, забезпечуючи точне дзеркальне відображення дерева. |
| `--partial-dir=.rsync-partial` | Збереження недокачаного фрагмента файлу в разі розриву мережі в окремому прихованому каталозі, що дозволяє миттєво продовжити передачу при наступному запуску команди. |
| `--delay-updates` | Усі оновлені файли спочатку збираються у тимчасові, а їхнє масове перейменування відбувається в самому кінці успішного сеансу. Запобігає пошкодженню працездатності сервісів при раптовому обриві зв'язку посеред синхронізації. |

> ⚠️ **Слеш наприкінці шляху джерела:**
> В утиліті `rsync` слеш наприкінці шляху змінює поведінку:
> - `rsync -a /src/dir /dst/` — створює підкаталог `/dst/dir/` (копіює сам каталог).
> - `rsync -a /src/dir/ /dst/` — копіює **вміст** каталогу `/src/dir/` безпосередньо всередину `/dst/`.

## Продуктивність, шифри та накладні витрати на високих швидкостях

При передаванні терабайтних обсягів через високошвидкісні канали 10 Gbps і вище швидкість копіювання через SSH часто впирається не в фізичну пропускну здатність мережевої карти чи дискового масиву NVMe, а в **потужність центрального процесора, зайнятого криптографією та контекстними перемиканнями**.

### Вибір алгоритму симетричного шифрування

Кожен байт, що проходить через SSH, шифрується симетричним алгоритмом і захищається кодом автентифікації. Сучасні версії OpenSSH пропонують кілька шифрів із різним профілем навантаження на процесор:

1. `aes128-gcm@openssh.com` / `aes256-gcm@openssh.com`:
   - Використовує режим Galois/Counter Mode (AEAD), який одночасно забезпечує конфіденційність і перевірку автентичності.
   - На сучасних процесорах x86_64 та ARMv8 виконується з апаратним прискоренням через інструкції **AES-NI** та множення поліномів **CLMUL / PMULL**.
   - Продуктивність шифрування досягає 4–8 ГБ/с на одне ядро CPU, що дозволяє легко насичувати лінк 10–25 Gbps.
2. `chacha20-poly1305@openssh.com`:
   - Програмний потоковий шифр, розроблений Даніелем Бернштейном.
   - Не вимагає спеціалізованих апаратних інструкцій шифрування і демонструє високу швидкість на мобільних, вбудованих пристроях чи старих серверах без AES-NI.
   - На серверах із підтримкою AES-NI працює дещо повільніше за апаратно прискорений AES-GCM.

Для максимізації пропускної здатності в локальних швидких мережах рекомендується явно вказувати шифр через параметри SSH:

```bash
rsync -av -e "ssh -c aes128-gcm@openssh.com -o Compression=no" /data/ host:/data/
```

### Пастка стиснення на льоту (`-C` / `-z`)

Увімкнення прапорця компресії на льоту (`ssh -C` або `rsync -z`) здається універсальною оптимізацією, але на практиці часто стає причиною різкого падіння швидкості.

- **Коли стиснення допомагає:** передавання неструктурованих текстових логів, дампів SQL-баз, файлів JSON/XML або нестиснених образів віртуальних машин через вузькі повільні канали (менше 50 Мбіт/с). Зменшення обсягу даних у 3–5 разів компенсує витрати CPU на стиснення.
- **Коли стиснення шкодить:** передавання вже стиснених архівів (`.tar.gz`, `.zst`), медіафайлів (JPEG, MP4) або робота в гігабітних мережах LAN / 10GbE. Алгоритм компресії `zlib` витрачає 100% одного ядра процесора, видаючи максимум 40–80 МБ/с компресованого потоку, перетворюючи швидкий 10-гігабітний канал на пляшкове горло.

В rsync версії 3.2+ додано підтримку алгоритму компресії `zstd` (`--compress-choice=zstd`), який забезпечує в рази вищу швидкість стиснення порівняно з класичним `gzip`, значно відсуваючи поріг процесорного насичення.

## Підсумок: правила вибору інструмента

1. **Одноразове швидке копіювання кількох файлів вручну:** Утиліта `scp` (OpenSSH 9.0+) або `sftp` — мінімальний синтаксичний оверхед, звична поведінка для розробників та адміністраторів.
2. **Ізольований доступ для завантаження файлів (Jail / CI):** Підсистема `internal-sftp` у поєднанні з `Match Group`, `ChrootDirectory` та `ForceCommand` — максимальна безпека без відкриття оболонки на хості та без необхідності дублювати системні бібліотеки в ізольованому каталозі.
3. **Регулярне резервне копіювання, деплой та синхронізація великих дерев:** Утиліта `rsync -aHAX --numeric-ids --delay-updates -e ssh` — єдиний стандарт для перенесення структури каталогів, збереження жорстких посилань, списків доступу ACL, розширених атрибутів xattr та економії трафіку за рахунок дельта-алгоритму блоків.
