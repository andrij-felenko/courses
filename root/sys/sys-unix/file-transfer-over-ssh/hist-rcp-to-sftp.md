# 📜 Від rcp до SFTP: як сорокарічний спадок змусив переписати scp

Ця історична розвідка показує, як архітектурне рішення 1983 року — утиліта `rcp` з Берклі — без змін перекочувало в перший випуск SSH 1995 року, породило серію критичних вразливостей через тридцять п'ять років і зрештою змусило розробників OpenSSH у версії 9.0 повністю замінити рушій `scp` на протокол SFTP.

## Народження утиліти віддаленого копіювання: 1983 рік

На початку 1980-х років у Каліфорнійському університеті в Берклі під керівництвом Білла Джоя (Bill Joy) створювався реліз операційної системи 4.2BSD. Разом із реалізацією стека протоколів TCP/IP розробники створили сімейство так званих `r-commands` для роботи у локальних мережах довірених університетських хостів: `rlogin` для віддаленого термінала, `rsh` для віддаленого виконання команд і `rcp` (*remote copy*) для передавання файлів.

Модель `rcp` була гранично простою: позбутися складного діалогу протоколу FTP і дозволити копіювати файли між машинами за синтаксисом, схожим на звичайний локальний `cp`:

```bash
rcp file.txt host2:/var/backups/
rcp host1:/var/log/messages .
```

Під капотом клієнт `rcp` відкривав TCP-з'єднання до порту 514 демона `rshd`, автентифікувався за файлом довірених хостів `/etc/hosts.equiv` або домашнім `~/.rhosts` (без жодного пароля чи криптографічного ключа) і запускав на віддаленій машині прихований екземпляр `rcp` у спеціальному режимі:
- `rcp -t /var/backups/` (*target* — режим приймача даних);
- `rcp -f /var/log/messages` (*from* — режим джерела даних).

Сам протокол RCP являв собою неструктурований текстово-бінарний потік над тим самим сокетом. Передавач надсилав директиву у форматі ASCII:

```text
C0644 10240 report.pdf\n
```

де `C` позначало створення файлу (*create*), `0644` — вісімкові біти прав доступу, `10240` — точний розмір у байтах, а `report.pdf` — назву файлу. Далі сервер відповідав нульовим байтом підтвердження `\0`, після чого передавач викачував рівно 10240 сирих байтів файлу і знову чекав на завершальний `\0`. Для каталогів використовувалися директиви `D0755 0 dirname\n` і вихід із каталогу `E\n`.

Ніяких фреймів, ніяких кодів запиту/відповіді, ніякої перевірки цілісності — потік байтів лився просто в сокет. У локальних мережах 1983 року між машинами VAX це працювало блискавично.

## 1995 рік: Тату Ілонен і поява scp

У 1995 році після серії інцидентів із перехопленням паролів у мережі Гельсінського технологічного університету Тату Ілонен (Tatu Ylönen) розробив протокол SSH (Secure Shell) для захисту відкритого трафіку.

Для забезпечення можливості безпечного копіювання файлів Ілонен не став проєктувати новий протокол передачі з нуля. Він узяв перевірений часом код утиліти `rcp` з BSD і замінив транспорт `rsh` на захищений криптографічний сеанс SSH. Нова утиліта отримала назву `scp` (*secure copy*).

Замість прямого TCP-з'єднання до порту 514 клієнт `scp` викликав команду:

```bash
ssh user@remote_host "scp -t /destination/path"
```

Дані передавалися через стандартні потоки вводу-виводу (stdin/stdout) каналу сеансу SSH, зашифровані симетричним шифром і захищені автентифікаційним кодом повідомлення (MAC). Здавалося, що проблему вирішено назавжди: інтерфейс залишився звичним для всіх системних адміністраторів Unix, а безпеку каналу гарантував SSH.

Проте всередині `scp` залишилася фатальна архітектурна спадщина протоколу RCP.

## Архітектурна пастка: віддалена оболонка та розкриття масок

Головна вада дизайну полягала в тому, як саме передавалися шляхи файлів. Коли користувач виконував команду:

```bash
scp user@server:/var/log/*.log .
```

клієнт `scp` локально не міг знати, які файли відповідають масці `*.log` на віддаленому сервері. Тому клієнт формував командний рядок для запуску через SSH:

```bash
ssh user@server "scp -f /var/log/*.log"
```

Демон `sshd` на сервері після автентифікації користувача запускав його оболонку входу за замовчуванням:

```bash
$SHELL -c "scp -f /var/log/*.log"
```

Оболонка сервера (наприклад, `/bin/bash` або `/bin/sh`) розкривала шаблон `*.log` у список конкретних файлів і передавала їх аргументами процесу `scp -f`.

З цього випливали дві проблеми фундаментального характеру:

1. **Ін'єкція команд через імена файлів:** Якщо шлях до файлу містив пробіли, лапки або спецсимволи командної оболонки (наприклад, файл називався `report$(reboot).pdf` або `test;rm -rf /`), недбало екранований виклик оболонки міг виконати довільний код на віддаленому сервері. Користувачам доводилося застосовувати потрійне екранування лапками.
2. **Залежність від типу оболонки:** Якщо у віддаленого користувача типовою оболонкою був встановлений `csh`, `tcsh`, `fish` чи кастомний restricted shell (`rbash`), правила розкриття масок і поведінка спецсимволів різко відрізнялися від POSIX `sh`.

Але справжня катастрофа чекала на клієнтському боці.

## Вразливість CVE-2019-6111: сліпа довіра приймача

У січні 2019 року фінський дослідник безпеки Гаррі Сінтонен (Harry Sintonen) з компанії F-Secure оприлюднив комплекс фундаментальних вразливостей у протоколі SCP, серед яких головною стала **CVE-2019-6111**.

З'ясувалося, що клієнт `scp` при завантаженні файлів повністю довіряв іменам, які віддалений сервер надсилав у директивах протоколу `C0644`.

Сценарій атаки виглядав так:
1. Адміністратор завантажує текстові файли з віддаленого сервера, який може бути скомпрометований зловмисником:
   ```bash
   scp admin@untrusted-server:*.txt /home/admin/documents/
   ```
2. Клієнт запускає на сервері `scp -f *.txt`.
3. Замість файлів `notes.txt` підроблений серверний процес надсилає послідовність директив:
   ```text
   C0644 5432 notes.txt\n
   <вміст notes.txt>
   C0644 128 ../.bashrc\n
   <шкідливий код для виконання при вході користувача>
   C0644 456 ../.ssh/authorized_keys\n
   <публічний ключ зловмисника>
   ```
4. Клієнтський процес `scp` читав директиву `C0644 128 ../.bashrc`, створював файл у локальному каталозі за відносним шляхом і перезаписував `~/.bashrc` локального адміністратора.

Протокол RCP не містив жодного криптографічного чи логічного зв'язку між тим, що клієнт *просив*, і тим, що сервер йому *віддав*. Клієнт вважав, що віддалений процес працює чесно.

Крім того, виявилася вразливість **CVE-2019-6109**: сервер міг маніпулювати відображенням прогресу завантаження в терміналі за допомогою керуючих ANSI-послідовностей у назвах файлів, приховуючи факт завантаження зайвих об'єктів.

## Спроби лікування та глухий кут

Розробники OpenSSH терміново випустили патчі. У клієнт `scp` додали перевірку: чи відповідає кожне отримане від сервера ім'я файлу початковому шаблону за допомогою функції `fnmatch()`.

Проте це створило нові проблеми:
- Якщо клієнт використовував маски POSIX, а віддалена оболонка (наприклад, `zsh` з увімкненим extended globbing) розгортала їх за іншими правилами, клієнт `scp` відхиляв цілком легітимні файли, вважаючи їх атакою підміни шляху.
- Символьні посилання, переходи по каталогах і рекурсивне копіювання (`-r`) утворювали стільки крайових випадків, що код валідації перетворився на джерело постійних нових помилок.

Стало очевидно: протокол RCP сорокарічної давності не підлягає надійному виправленню. Будь-яка спроба латати текстовий потік без типізованих повідомлень і структурованих запитів була боротьбою з симптомами.

## Перехід OpenSSH 9.0+ на SFTP

У квітні 2022 року відбувся реліз **OpenSSH 9.0**, де розробники оголосили про фундаментальну зміну: **утиліта `scp` переведена на використання протоколу SFTP за замовчуванням**.

Замість запуску `scp -t` через віддалений командний рядок клієнт `scp` тепер:
1. Відкриває SSH-канал і надсилає запит на запуск підсистеми: `SSH_MSG_CHANNEL_REQUEST` з підсистемою `sftp`.
2. Взаємодіє з сервером через суворо типізований бінарний протокол SFTP (де кожна дія — це окремий пакет: `SSH_FXP_OPEN`, `SSH_FXP_READ`, `SSH_FXP_WRITE`, `SSH_FXP_STATUS`).
3. Виконує обхід каталогів і узгодження масок без участі віддаленої оболонки, запитуючи список файлів через `SSH_FXP_READDIR`.
4. Зберігає для користувача звичний інтерфейс командного рядка: прапорці `-p`, `-r`, `-C`, `-l` працюють точно так само, але під капотом працює надійний фреймовий транспорт.

Для взаємодії зі старими вбудованими пристроями, мережевими комутаторами або серверами без підтримки підсистеми SFTP у команду додали прапорець `-O` (*legacy SCP protocol*):

```bash
scp -O firmware.bin admin@legacy-switch:/flash/
```

Прапорець `-O` повертає утиліту до старого протоколу RCP, але вимагає від адміністратора свідомого рішення взяти на себе відомі ризики безпеки.

Таким чином сорокарічна епоха протоколу RCP в операційних системах Unix остаточно завершилася, поступившись місцем структурованим протоколам SFTP та Rsync.
