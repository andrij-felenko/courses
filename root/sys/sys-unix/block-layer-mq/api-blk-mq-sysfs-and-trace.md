# 📋 Інтерфейси спостереження та інспектування blk-mq (sysfs, debugfs, tracepoints)

Ця вставка надає повний довідковий огляд системних інтерфейсів ядра Linux, призначених для моніторингу, інспектування та глибокого аналізу внутрішнього стану підсистеми `blk-mq`. Вона охоплює структуру псевдофайлової системи `sysfs`, діагностичні вузли `debugfs`, точний контракт точок простеження `ftrace`/`tracepoints`, а також наводить практичні сценарії профілювання за допомогою eBPF-інструментів для вимірювання затримок обробки операцій вводу-виводу.

## 1. Поверхня sysfs: `/sys/block/<device>/mq/` та `/sys/block/<device>/queue/`

Для кожного блокового пристрою, який працює під управлінням підсистеми `blk-mq`, ядро створює спеціальне дерево атрибутів у файловій системі `sysfs`. Воно поділяється на загальні параметри черги пристрою (`queue/`) та специфічні атрибути апаратних контекстів `blk-mq` (`mq/`).

```
/sys/block/nvme0n1/
├── queue/
│   ├── scheduler
│   ├── nr_requests
│   ├── io_poll
│   ├── io_poll_delay
│   ├── max_sectors_kb
│   ├── max_hw_sectors_kb
│   ├── logical_block_size
│   ├── physical_block_size
│   ├── rq_affinity
│   ├── nomerges
│   ├── wbt_lat_usec
│   └── rotational
└── mq/
    ├── nr_hw_queues
    ├── 0/
    │   ├── cpu_list
    │   ├── nr_reserved_tags
    │   ├── nr_tags
    │   └── tags
    ├── 1/
    │   └── ...
    └── ...
```

### Контракт атрибутів каталогу `/sys/block/<device>/queue/`

* **`scheduler`** (`read-write`, `string`):
  Перелік доступних та поточного активованого планирувальника I/O. Активований планирувальник виділяється квадратними дужками.
  *Приклади значень*: `[none] kyber bfq mq-deadline`. 
  *Запис*: `echo kyber > /sys/block/nvme0n1/queue/scheduler`. Перемикання відбувається динамічно на льоту без зупинки роботи диска. Значення `none` вимикає планирувальник і переводить пристрій у режим прямого проходження запитів.

* **`nr_requests`** (`read-write`, `unsigned int`):
  Верхня межа кількості внутрішніх запитів (`struct request`), які можуть бути виділені та перебувати у програмних чергах (`blk_mq_ctx`) та планирувальнику для кожної апаратної черги. 
  *Значення за замовчуванням*: зазвичай 128 або 256. Збільшення значення дозволяє краще накопичувати запити для злиття при високому навантаженні, але підвищує споживання оперативної пам'яті.

* **`io_poll`** (`read-write`, `boolean`):
  Вмикає підтримку гібридного або чистого опитування (IO polling) для блокового пристрою.
  *Значення*: `0` — опитування вимкнено (обробка лише через апаратні переривання); `1` — опитування дозволено. Використовується в поєднанні з `io_uring` та прапорцем `IOCB_HIPRI` для досягнення суб-мікросекундних затримок.

* **`io_poll_delay`** (`read-write`, `int`):
  Затримка в мікросекундах перед початком цикла polling після відправки запиту. Значення `-1` вмикає класичне опитування; значення `0` або більше вмикає гібридне опитування, де ядро спочатку засинає на прогнозований час, а потім опитує накопичувач.

* **`max_sectors_kb`** (`read-write`, `unsigned int`):
  Максимальний розмір одного запиту I/O в кілобайтах, який файлова система або подія direct I/O може згенерувати за один раз. Не може перевищувати апаратний ліміт `max_hw_sectors_kb`.

* **`rq_affinity`** (`read-write`, `unsigned int`):
  Поведінка спорідненості завершення запитів (CPU affinity).
  * `0`: Запит завершується на тому процесорі, який отримав апаратне переривання.
  * `1`: Запит завершується на того логічному CPU, який ініціював `submit_bio()`.
  * `2` (force): Запит примусово переноситься для завершення на ініціюючий CPU за допомогою `IPI` (Inter-Processor Interrupt).

* **`nomerges`** (`read-write`, `unsigned int`):
  Керує алгоритмами злиття запитів (I/O Merging).
  * `0`: Дозволити всі види злиття (Back Merge, Front Merge, Elevator Merge).
  * `1`: Дозволити лише просте злиття на рівні `bio` (Back/Front Merge).
  * `2`: Повністю вимкнути злиття запитів для мінімізації витрат CPU при випадковому вводі-виводі.

* **`wbt_lat_usec`** (`read-write`, `int`):
  Затримка для механізму `Writeback Throttling` (WBT). Вона визначає цільову затримку читання у мікросекундах. Якщо фоновий запис брудних сторінок призводить до зростання затримки читання понад `wbt_lat_usec`, підсистема `blk-mq` обмежує кількість фонових записів.

### Контракт атрибутів каталогу `/sys/block/<device>/mq/<N>/`

Каталог `mq/` містить підкаталоги для кожної апаратної черги диспетчеризації (`hctx`), де `<N>` — це порядковий номер апаратної черги від `0` до `nr_hw_queues - 1`.

* **`nr_hw_queues`** (`read-only`, `unsigned int`):
  Загальна кількість апаратних черг диспетчеризації (`hctx`), створених драйвером пристрою.

* **`cpu_list`** (`read-only`, `string`):
  Список номерів логічних процесорів (CPU), чиї per-CPU програмні черги (`blk_mq_ctx`) мапляться на дану апаратну чергу `N`.
  *Приклад виводу*: `0, 4, 8, 12` або `0-7`.

* **`nr_tags`** (`read-only`, `unsigned int`):
  Загальна кількість слотів команд (тегів), виділена для цієї апаратної черги в бітовій карті `sbitmap`.

* **`nr_reserved_tags`** (`read-only`, `unsigned int`):
  Кількість зарезервованих тегів у наборі, призначених виключно для високопріоритетних ядерних запитів (наприклад, флеш-команд або керуючих ioctl).

## 2. Глибока діагностика через `debugfs`: `/sys/kernel/debug/block/<device>/`

Коли ядро Linux скомпільовано з опцією `CONFIG_BLK_DEBUG_FS=y`, у монтованій файловій системі `debugfs` відкривається доступ до внутрішніх структур даних ядра в реальному часі.

```
/sys/kernel/debug/block/nvme0n1/
├── state
├── hctx0/
│   ├── active
│   ├── cpu0/
│   │   └── rq_list
│   ├── cpu1/
│   │   └── rq_list
│   ├── dispatch
│   ├── dispatch_busy
│   ├── flags
│   ├── run
│   ├── state
│   ├── tags
│   └── type
└── hctx1/
    └── ...
```

### Вузли інспектування `debugfs`

1. **`hctxN/cpuM/rq_list`**:
   Показує список запитів (`struct request`), які на даний момент знаходяться у програмній черзі `blk_mq_ctx` процесора `M`.
   *Нормальний стан*: за відсутності блокувань або насичення пристрою цей список є порожнім, оскільки запити миттєво виштовхуються в `hctx`.

2. **`hctxN/dispatch`**:
   Перелік запитів, що знаходяться безпосередньо в списку відправки апаратної черги `hctxN` і чекають виклику `queue_rq()`. Наявність великої кількості елементів у цьому файлі свідчить про те, що контролер пристрою не встигає приймати команди (апаратне насичення).

3. **`hctxN/tags`**:
   Виводить детальний стан бітової карти `sbitmap` та черги очікування тегів `sbitmap_queue`.

*Приклад вмісту `hctx0/tags`*:
```text
depth=64
busy=12
active_queues=1
bitmap_tags:
  depth=64 shift=6 map_nr=1
  alloc_hint={0, 4, 12, 18}
  map[0]=0x0000000000000fff
```
У цьому прикладі із 64 слотів наразі 12 тегів є активними (`busy=12`), а бітова маска `map[0]` показує перші 12 встановлених бітів (0xefff).

4. **`hctxN/state`**:
   Відображає внутрішні прапорці стану апаратного контексту:
   * `STOPPED`: черга зупинена драйвером (наприклад, під час скидання контролера).
   * `ORPHAN`: черга відключена від процесора (при hotplug).
   * `TAG_WAITING`: процеси чекають на звільнення слотів тегів у `sbitmap`.

## 3. Точки простеження ftrace (`tracepoints`)

Для точного профілювання затримок та відстеження життєвого циклу запитів підсистема `blk-mq` експортує серію стандартних подій ядра (`tracepoints`), які знаходяться в підсистемі `block`.

### Контракт подій `block` tracepoints

```text
block:block_bio_queue      (dev_t dev, sector_t sector, unsigned int nr_sector, char rwbs)
block:block_bio_backmerge  (dev_t dev, sector_t sector, unsigned int nr_sector, char rwbs)
block:block_bio_frontmerge (dev_t dev, sector_t sector, unsigned int nr_sector, char rwbs)
block:block_rq_insert      (dev_t dev, sector_t sector, unsigned int nr_sector, char *cmd)
block:block_rq_issue       (dev_t dev, sector_t sector, unsigned int nr_sector, char *cmd)
block:block_rq_complete    (dev_t dev, sector_t sector, unsigned int nr_sector, int error)
```

### Семантика прапорців `rwbs`

У подіях простеження поле `rwbs` описує тип операції у вигляді символьного рядка:
* `R`: Читання (`REQ_OP_READ`).
* `W`: Запис (`REQ_OP_WRITE`).
* `D`: Дискард / TRIM (`REQ_OP_DISCARD`).
* `F`: Синхронізація кешу / Flush (`REQ_PREFLUSH`).
* `N`: Немає даних / Null operation.
* `A`: Асинхронний I/O (`REQ_RAHEAD`).
* `S`: Синхронний I/O (`REQ_SYNC`).

### Приклад реального логу `ftrace`

При виконанні послідовного запису процес формує події в такій послідовності:

```text
  kworker/0:1-42  [000] d..1 1024.100101: block_bio_queue: 259,0 W 2048 + 8 [kworker/0:1]
  kworker/0:1-42  [000] d..1 1024.100105: block_bio_backmerge: 259,0 W 2056 + 8 [kworker/0:1]
  kworker/0:1-42  [000] d..1 1024.100120: block_rq_insert: 259,0 WS 2048 + 16 [kworker/0:1]
  kworker/0:1-42  [000] d..1 1024.100135: block_rq_issue: 259,0 WS 2048 + 16 [kworker/0:1]
 <idle>-0         [000] d.h2 1024.100210: block_rq_complete: 259,0 WS 2048 + 16 [0]
```

Тлумачення логу:
1. `block_bio_queue`: Надходить початковий `bio` на сектор 2048 розміром 8 секторів (4KB).
2. `block_bio_backmerge`: Наступний `bio` на сектор 2056 зливається в кінець існуючого запиту (Back Merge).
3. `block_rq_insert`: Злитий запит розміром 16 секторів (8KB) вставляється у чергу `blk_mq_ctx`.
4. `block_rq_issue`: Запит передається драйверу накопичувача (`queue_rq`).
5. `block_rq_complete`: Апаратне переривання сповіщає про успішне завершення операції через 75 мікросекунд (100210 - 100135 = 75 мкс).

## 4. Профілювання затримок через eBPF (bpftrace)

Сучасний моніторинг `blk-mq` виконується безпосередньо у просторі ядра за допомогою eBPF, що усуває накладні витрати на запис логів на диск.

Нижче наведено робочий скрипт `bpftrace` для побудови гістограми затримок виконання запитів (`issue` -> `complete`) у мікросекундах для диска `nvme0n1`:

```bash
sudo bpftrace -e '
tracepoint:block:block_rq_issue
{
    @start[args->dev, args->sector] = nsecs;
}

tracepoint:block:block_rq_complete
/@start[args->dev, args->sector]/
{
    $lat_us = (nsecs - @start[args->dev, args->sector]) / 1000;
    @latency_us = hist($lat_us);
    delete(@start[args->dev, args->sector]);
}

END
{
    clear(@start);
}
'
```

*Приклад виводу гістограми `bpftrace`*:
```text
@latency_us: 
[16, 32)            124 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
[32, 64)             45 |@@@@@@@@@@@@@@@@@@@                                 |
[64, 128)            12 |@@@@@                                               |
[128, 256)            2 |                                                    |
```

Цей інструмент дозволяє системному інженеру миттєво визначити наявність "хвостів затримок" (tail latency) підсистеми `blk-mq` на продакшн-серверах без зупинки сервісів.
