# 📜 Еволюція блокового шару Linux: від єдиної черги до blk-mq

Вставка описує виникнення та трансформацію блокового підрівня Linux під тиском зміни апаратних технологій зберігання даних. Вона пояснює, чому монолітна архітектура з єдиним блокуванням (single-queue), яка ефективно працювала з механічними жорсткими дисками протягом десятиліть, раптово зазнала масштабного колапсу продуктивності після появи твердотілих накопичувачів PCIe SSD та NVMe, і як розробка підсистеми `blk-mq` під керівництвом Йенса Аксбо (Jens Axboe) врятувала Linux від роли «вузького місця» під час операцій вводу-виводу.

## Ера обертальних дисків та спинлоків (Linux 2.4 — 3.12)

На світанку розвитку ядра Linux операції вводу-виводу до блокових пристроїв розроблялися з розрахунку на жорсткі диски (HDD) та магнітні стрічки. Позиціонування механічної зчитувальної голівки диска над потрібним треком вимагало часу в межах від 5 до 15 мілісекунд. Через це типовий накопичувач був здатний виконувати лише від 100 до 200 операцій вводу-виводу за секунду (IOPS — *Input/Output Operations Per Second*, англ. «операції вводу-виводу за секунду»).

За таких умов обчислювальні накладні витрати ядра Linux на обробку одного запиту були мізерними порівняно з фізичною затримкою самого накопичувача. Для управління запитами використовувалася одна глобальна черга запитів — `struct request_queue`. Всі процесори (CPU) у системі, бажаючи надіслати запит на читання чи запис, повинні були захопити єдиний спінлок — `request_queue->queue_lock`.

```
[ CPU 0 ] ──┐
[ CPU 1 ] ──┼──> ( Spinlock: queue_lock ) ──> [ Єдина черга request_queue ] ──> [ HDD Controller ]
[ CPU 2 ] ──┘
```

Монолітна черга дозволяла класичним планирувальникам I/O (таким як CFQ — *Completely Fair Queueing*, або Deadline) легко сортувати запити за допомогою алгоритму ліфта (Elevator Algorithm), мінімізуючи стрибки магнітних головок диска. Конкуренція за спінлок `queue_lock` була непомітною, оскільки CPU проводили в черзі наносекунди, тоді як диск відпрацьвував запит за мілісекунди.

## Криза продуктивності з появою SSD та PCIe (2010–2012)

На початку 2010-х років ринок корпоративних систем зберігання даних пережив революцію з появою флеш-пам'яті NAND та накопичувачів Fusion-io, виведених через шину PCI Express. Затримка зчитування впала з 10 000 мікросекунд до 50 мікросекунд, а кількість IOPS зросла від сотень до сотень тисяч.

У цей момент традиційний блоковий шар Linux зіштовхнувся з бар'єром масштабованості. На багатоядерних серверах (32, 64 чи більше логічних ядер) сотні паралельних потоків намагалися одночасно виконувати виклики `submit_bio()`. Всі вони впиралися в один і той самий спінлок `queue_lock`.

Виник негативний ефект *cache-line bouncing* (інвалідація кеш-ліній між ядрами): рядок пам'яті, що містив спінлок черги, безперервно переміщувався між L1/L2 кешами різних ядер процесора. CPU витрачали до 90% робочого часу не на корисну роботу або передачу даних, а на очікування в циклі `spin_lock_irq()`.

Вимірювання Йенса Аксбо у 2012 році показали тривожну картину: одна єдина монолітна черга ядра Linux не могла видати більше ніж ~800 000 IOPS на систему, незалежно від того, скільки швидких SSD чи процесорних ядер було встановлено на сервері. Апаратне забезпечення стало значно швидшим за блоковий шар операційної системи.

## Архітектурний перелом: Народження blk-mq (2013)

Для розв'язання цієї кризи інженер компанії Fusion-io (а пізніше Facebook) Йенс Аксбо разом із Матіасом Бйорлінгом (Matias Bjørling) запропонували фундаментально нову підсистему — **blk-mq** (*Multi-Queue Block Layer*, багаточерговий блоковий шар).

Головна концепція blk-mq полягала в повній відмові від єдиного блокування шляхом розщеплення черги на два незалежні рівні:

1. **Per-CPU Software Staging Queues**: Кожне логічне ядро процесора отримало власну програмну чергу. Коли процес на CPU 4 генерує I/O, запит потрапляє в чергу CPU 4 без жодного міжпроцесорного блокування.
2. **Per-Hardware Dispatch Queues**: Апаратні черги, що напряму мапляться на багаточергові контролери (на той час розроблявся специфікат NVMe — *Non-Volatile Memory Express*, розрахований на підтримку до 65 535 апаратних черг по 65 536 команд у кожній).

```
[ CPU 0 ] ──> [ Soft Queue 0 ] ──┐
[ CPU 1 ] ──> [ Soft Queue 1 ] ──┼──> [ Hard Dispatch Queue 0 ] ──> [ NVMe Controller ]
[ CPU 2 ] ──> [ Soft Queue 2 ] ──┘
```

Початковий патчсет для blk-mq було влито в ядро Linux 3.13 у грудні 2013 року. Перші тестові прогони показали вражаючий результат: лінійне масштабування продуктивності на 48-ядерному сервері з показниками понад 8 000 000 IOPS при мінімальному завантаженні CPU в ядрі.

## Еволюція розробки та вилучення застарілого коду (Linux 3.16 — 5.0)

Впровадження `blk-mq` вимагало масштабно переписати не лише базовий блоковий шар, а й драйвери всіх існуючих контролерів та пристроїв зберігання.

У період з Linux 3.16 по Linux 4.15 спільнота розробників ядра реалізувала підтримку `blk-mq` для драйверів SCSI (підсистема `scsi_mq`), VirtIO-block для віртуалізованих середовищ KVM/QEMU, а також для застарілих контролерів ATA/SATA. Для пристроїв з однією фізичною чергою ядро почало створювати єдину апаратну чергу `hctx`, на яку мапилися всі програмні черги `blk_mq_ctx`. Це дозволило зберегти переваги локального накопичення та злиття запитів без міжпроцесорного загарбання спінлоків навіть на звичайних SATA HDD.

У релізі Linux 4.20 розробники остаточно оновили або вилучили застарілі монолітні планирувальники I/O (CFQ, Noop, Deadline), замінивши їх багаточерговими аналогами (BFQ, Kyber, mq-deadline).

Нарешті, у релізі **Linux 5.0** (березень 2019 року) вихідний код Single-Queue Block Layer було повністю вилучено з ядра Linux. Відтоді **усі** блокові пристрої в Linux — від SD-карт і SATA HDD до enterprise NVMe накопичувачів — працюють виключно через підсистему `blk-mq`.

Перехід на `blk-mq` не лише підготував Linux до ери NVMe та io_uring, але й продемонстрував важливий принцип системного програмування: при переході на нові швидкості апаратного забезпечення кометичний оптимізаційний ремонт старого коду є безперспективним — необхідна повна зміна архітектурних парадигм синхронізації.
