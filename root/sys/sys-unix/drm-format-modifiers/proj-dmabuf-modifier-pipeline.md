# ⚙️ Створення тайлованого буфера GBM, експорт dma-buf та імпорт у KMS FB2

У сучасному графічному стеку Linux створення кадрового буфера з апаратним тайлінгом та передавання його дисплейному контролеру вимагає узгодженої взаємодії трьох ключових рівнів архітектури:

1. **Generic Buffer Management (GBM / Mesa):** простір користувача запитує виділення відеопам'яті у графічного процесора, передаючи список бажаних 64-бітних модифікаторів DRM (наприклад, Intel Tile4, Y-Tile або резервний `DRM_FORMAT_MOD_LINEAR`). Драйвер GPU обирає найбільш енергоефективний та швидкісний варіант серед тих, які підтримуються апаратно.
2. **Експорт дескрипторів dma-buf:** для кожної логічної площини (пікселі основного кольору, допоміжні метадані стиснення CCS/DCC, теги швидкого очищення) драйвер повертає файловий дескриптор [dma-buf](root:sys-unix/dma-buf), крок рядка (stride / pitch) та зміщення в байтах від початку буфера.
3. **Імпорт у конвеєр відображення DRM KMS:** композитор викликає системний виклик `DRM_IOCTL_MODE_ADDFB2` із прапорцем `DRM_MODE_FB_MODIFIERS`, реєструючи єдиний об'єкт `drmModeFB` для безпосереднього апаратного сканування дисплейною площиною.

## Архітектура нуль-копійного графічного конвеєра (Zero-Copy Pipeline)

Сучасний графічний конвеєр робочого столу або мультимедійної системи Linux об'єднує кілька незалежних апаратних пристроїв:
* **Графічний процесор (GPU):** виконує тривимірний рендеринг у Vulkan або OpenGL;
* **Відеопроцесор (VPU / NPU):** апаратно декодує стиснений відеопотік (H.264, HEVC, AV1) у напівпланарні YUV-кадри через підсистеми [V4L2](root:sys-unix/media-controller-graph) чи VA-API;
* **Дисплейний контролер (Display Controller / DPU / DCN):** зчитує готові пікселі з пам'яті через прямий доступ (DMA) та формує вихідний відеосигнал для монітора (HDMI, DisplayPort, eDP).

Коли кадр із роздільністю 4K (3840×2160) у форматі ARGB8888 оновлюється з частотою 120 Гц, простий перегін нестисненого масиву пікселів між відеопам'яттю та дисплеєм створює потік понад 8 ГБ/с. Будь-яке проміжне копіювання чи програмне компонування центральним процесором миттєво вичерпує пропускну здатність системної шини та спричиняє затримку введення (input lag).

Механізм **Zero-Copy Direct Scanout** дозволяє уникнути будь-якого копіювання: буфер, виділений у відеопам'яті графічним драйвером або відеодекодером, передається дисплейному контролеру як єдине незмінне посилання. Роль універсального мосту виконує підсистема ядра [dma-buf](root:sys-unix/dma-buf), яка загортає діапазон фізичних сторінок пам'яті в анонімний файловий дескриптор POSIX.

```
+-------------------------------------------------------------------------------+
|  Виробник (Producer: Vulkan / EGL / VA-API / GBM)                             |
|  Виділяє фізичні сторінки (VRAM / GTT) через GEM                              |
+-------------------------------------------------------------------------------+
                                      |
                                      | 1. Експорт: DRM_IOCTL_PRIME_HANDLE_TO_FD
                                      v
+-------------------------------------------------------------------------------+
|  Ядро Linux: об'єкт struct dma_buf (Анонімний файловий дескриптор FD)         |
|  Утримує спільні фізичні сторінки та таблицю розсіювання-збирання (sg_table)   |
+-------------------------------------------------------------------------------+
                                      |
                                      | 2. Передача FD через сокет (Wayland) або
                                      |    імпорт: DRM_IOCTL_PRIME_FD_TO_HANDLE
                                      v
+-------------------------------------------------------------------------------+
|  Споживач (Consumer: Віконний композитор / DRM KMS Display Controller)        |
|  Реєструє кадровий буфер: DRM_IOCTL_MODE_ADDFB2 (FourCC + 64-бітний modifier)  |
|  Апаратне сканування площиною CRTC напряму з фізичної пам'яті (Zero-Copy)     |
+-------------------------------------------------------------------------------+
```

### Чому коду FourCC недостатньо без 64-бітного модифікатора

32-бітний код FourCC (наприклад, `DRM_FORMAT_XRGB8888` або `DRM_FORMAT_NV12`) визначає виключно логічну семантику бітів: скільки бітів виділено на червоний, зелений, синій канали чи яскравість, і в якому порядку вони розташовані в машинному слові процесора.

Проте сучасні GPU ніколи не зберігають пікселі послідовними рядками. Задля локальності просторової вибірки та зменшення промахів кешу L1/L2 пікселі групуються у двовимірні блоки — **тайли** (Intel X-Tile, Y-Tile, Tile4, AMD GFX9/GFX10 64K, Arm AFBC). Ба більше, блоки пікселів додатково стискаються апаратними алгоритмами без втрат (Intel CCS, AMD DCC), утворюючи окремі допоміжні поверхні метаданих.

Якщо передати контролеру дисплея тайлований або стиснений буфер із вказівкою лише коду FourCC `DRM_FORMAT_XRGB8888` (очікуючи лінійний порядок), дисплейний блок прочитає перемішані байти й стиснені заголовки як випадковий графічний шум, або зазнає апаратного скидання через некоректні адреси вибірки.

Саме тому стандарт DRM вимагає передавати пару: **32-бітний FourCC + 64-бітний модифікатор розкладки**. Старші 8 бітів модифікатора кодують ідентифікатор виробника (`DRM_FORMAT_MOD_VENDOR_INTEL`, `DRM_FORMAT_MOD_VENDOR_AMD`, `DRM_FORMAT_MOD_VENDOR_ARM`), а молодші 56 бітів однозначно задають алгоритм тайлінгу, крок допоміжних площин та режим стиснення.

## Механізм узгодження модифікаторів (Modifier Negotiation)

Оскільки виробник буфера (GPU чи VPU) прагне використати максимально агресивний тайлінг і стиснення, а споживач (дисплейний контролер) обмежений можливостями конкретного блоку CRTC на відеовиході, графічний стек виконує процедуру **узгодження модифікаторів** (англ. *Modifier Negotiation*).

```
  Споживач (KMS Plane)                              Виробник (GPU / GBM / Vulkan)
  ====================                              ============================
  Зчитує блоб IN_FORMATS:                           Опитує апаратні можливості:
  [Tile4_CCS, Tile4, Linear]                        [Tile4_CCS, Tile4, Y-Tile, Linear]
            \                                                   /
             \_________________ Перетин списків _______________/
                                       |
                                       v
                          Обрано: Tile4_CCS (Найвищий)
                                       |
                           gbm_bo_create_with_modifiers2()
                                       |
                              Експорт dma-buf FD
                                       |
                           drmModeAddFB2WithModifiers()
                                       |
                          drmModeAtomicCommit(TEST_ONLY)
                                 [Успіх: 0]
                                       |
                              Прямий вивід на екран
```

### 1. Опитування можливостей площини KMS

Композитор або програма ініціалізації дисплея з'ясовує підтримувані розкладки через інтерфейс KMS:
1. Викликає `drmModeGetPlaneResources(drm_fd)` для отримання списку всіх апаратних площин (`struct drm_plane`).
2. Для обраної площини запитує список властивостей через `drmModeObjectGetProperties(drm_fd, plane_id, DRM_MODE_OBJECT_PLANE)`.
3. Знаходить властивість з ім'ям `IN_FORMATS` та отримує числовий ID бінарного блобу.
4. Викликає `drmModeGetPropertyBlob(drm_fd, blob_id)` і парсить структуру `struct drm_format_modifier_blob`.

Блоб містить масив підтримуваних FourCC-кодів та масив структур `struct drm_format_modifier`, де кожному 64-бітному модифікатору відповідає бітова маска форматів, із якими він сумісний на цій площині.

### 2. Перетин списків та вибір оптимуму

Отриманий від дисплея список модифікаторів передається виробнику — у виклик `gbm_bo_create_with_modifiers2()`, розширення EGL `EGL_EXT_image_dma_buf_import_modifiers` або структуру `VkImageDrmFormatModifierListCreateInfoEXT` у Vulkan.

Драйвер виробника знаходить **перетин множин** (англ. *intersection*) підтримуваних ним модифікаторів та списку споживача, після чого обирає варіант із найвищим пріоритетом продуктивності:
* `Intel Tile4 + CCS` (найвища економія пропускної здатності шини);
* `Intel Tile4` або `Intel Y-Tile` (висока 2D-локальність для текстурування);
* `DRM_FORMAT_MOD_LINEAR` (гарантований універсальний резерв, сумісний з будь-яким залізом та прямим доступом CPU).

### 3. Перевірка параметрів зареєстрованого буфера через GETFB2

Після імпорту буфера простір користувача або діагностичні утиліти можуть перевірити фактично зареєстровані параметри через системний виклик `DRM_IOCTL_MODE_GETFB2`. Структура `struct drm_mode_fb_cmd2` заповнюється ядром: вона повертає FourCC, розміри, масив модифікаторів `modifier[4]`, кроки рядків `pitches[4]` та зміщення `offsets[4]`. Це дозволяє переконатися, що ядро коректно розпізнало багатоплощинну геометрію.

## Покроковий розбір кодової бази проєкту

Розглянемо ключові рішення та інженерні механізми, реалізовані у вихідному коді проєкту.

### 1. Зв'язка прапорців GBM_BO_USE_RENDERING та GBM_BO_USE_SCANOUT

У виклику `gbm_bo_create_with_modifiers2()` критично важливо одночасно вказати обидва прапорці:
* `GBM_BO_USE_RENDERING`: повідомляє драйверу GPU (Mesa), що буфер слугуватиме метою рендерингу (color render target) для 3D-рушія, тому виділена область пам'яті повинна відповідати вимогам вирівнювання кешів растеризатора.
* `GBM_BO_USE_SCANOUT`: гарантує, що фізичні сторінки буфера будуть виділені в неперервній або доступній для IOMMU пам'яті, а крок рядка та зміщення допоміжних площин задовольнять обмеження контролера дисплея.

Якщо опустити `GBM_BO_USE_SCANOUT`, драйвер GPU може обрати специфічний тайлінг, який підтримується обчислювальними блоками, але не може бути прочитаний дисплейним блоком сканування.

### 2. Багатоплощинний експорт dma-buf та імпорт у GEM

Кожен створений буферний об'єкт `struct gbm_bo` може містити від 1 до 4 фізичних площин:
* Для `DRM_FORMAT_MOD_LINEAR` кількість площин дорівнює 1 (або 2 для напівпланарного `NV12`);
* Для тайлованих форматів зі стисненням метаданих (Intel CCS, AMD DCC) функція `gbm_bo_get_plane_count(bo)` повертає 2 або 3 площини.

Для кожної площини `p` виконується цикл:
1. `gbm_bo_get_fd_for_plane(bo, p)`: експортує дескриптор `dma-buf`. Під капотом драйвер викликає системний `DRM_IOCTL_PRIME_HANDLE_TO_FD`.
2. `gbm_bo_get_stride_for_plane(bo, p)` та `gbm_bo_get_offset(bo, p)`: повертають точний крок рядка та зміщення байтів від початку виділеної області.
3. `drmPrimeFDToHandle(drm_fd, fd, &handles[p])`: імпортує переданий `dma-buf` дескриптор у цільовий графічний контекст ядра, перетворюючи його на локальний числовий GEM-хендл (`DRM_IOCTL_PRIME_FD_TO_HANDLE`).

### 3. Реєстрація у KMS та негайне закриття GEM-хендлів

Функція `drmModeAddFB2WithModifiers()` передає масиви `handles`, `strides`, `offsets` та `mods` у системний виклик ядра `DRM_IOCTL_MODE_ADDFB2`.

Одразу після успішного повернення `fb_id` програма викликає `DRM_IOCTL_GEM_CLOSE` для кожного елемента `handles[p]`. Це принциповий момент:
* Створений у ядрі об'єкт кадрового буфера `struct drm_framebuffer` збільшує власний лічильник посилань `kref` на відповідні внутрішні GEM-об'єкти (`struct drm_gem_object`).
* Простір користувача більше не потребує локальних числових GEM-хендлів. Якщо їх не закрити, у таблиці дескрипторів процесу в ядрі виникне витік (handle leak), що призведе до помилки `-ENOSPC` при відкритті нових вікон.

### 4. Ідіоматичний C++20 дизайн конвеєра

У C++ версії конвеєра реалізовано суворе володіння ресурсами:
* **Клас `UniqueFd`:** реалізує семантику переміщення (move-only) над файловими дескрипторами POSIX. Деструктор автоматично викликає `::close()`, запобігаючи витоку дескрипторів `plane_fds` при виникненні винятків під час реєстрації FB.
* **Кастомний делетер `GbmBoDeleter`:** забезпечує автоматичне знищення об'єкта `gbm_bo` через `gbm_bo_destroy()` у розумному покажчику `UniqueGbmBo`.
* **Клас `KmsFramebuffer`:** утримує числовий `fb_id_` та вектор відкритих дескрипторів `plane_fds_`. Його деструктор викликає `drmModeRmFB()`, гарантуючи детерміноване видалення буфера з конвеєра дисплея.
* **`std::span<const uint64_t>`:** забезпечує безпечну передачу списку модифікаторів довільної довжини без накладних витрат на копіювання чи виділення динамічної пам'яті.

## Геометрія пам'яті: розрахунок страйдів, оффсетів та допоміжних площин

Коли буфер виділяється для напівпланарних форматів (YUV NV12, P010) або коли тайлований буфер містить апаратні метадані стиснення (Intel CCS, AMD DCC), розрахунок кроку рядка (`stride` / `pitch`), ефективної висоти та байтових зміщень (`offset`) підпорядковується суворим математичним правилам вирівнювання заліза. Порушення бодай одного кроку вирівнювання призводить до негайної відмови ядра з помилкою `-EINVAL`.

### Математика напівпланарних форматів NV12 та P010

У напівпланарному форматі `DRM_FORMAT_NV12` колірний простір субдискретизовано за схемою 4:2:0 (на кожні чотири пікселі яскравості припадає одна пара колірності U та V). Буфер складається з двох основних площин:
* **Площина 0 (Luma / Y):** роздільність `W × H`, кожен піксель займає 1 байт (`8 bpp`).
* **Площина 1 (Chroma / UV):** роздільність `(W / 2) × (H / 2)` макропікселів, де колірні компоненти U та V чергуються побайтово (`U0 V0 U1 V1 ...`). Ширина рядка в байтах становить `(W / 2) · 2 = W` байтів, а кількість рядків дорівнює `H / 2`.

Для 10-бітного формату високого динамічного діапазону `DRM_FORMAT_P010` кожен піксельний компонент зберігається у 16-бітному машинному слові `uint16_t` (старші 10 бітів кодують значення кольору, молодші 6 бітів заповнені нулями):
* **Площина 0 (Y):** `W × H` пікселів, ширина рядка в байтах становить `W · 2` байтів.
* **Площина 1 (UV):** `H / 2` рядків, ширина рядка становить `(W / 2) · 4 = W · 2` байтів.

#### Розрахунок геометрії лінійного буфера NV12 для кадру 4K (3840×2160)

```
stride_0 (Luma)  = ALIGN(W · 1, 64)
                 = ALIGN(3840 · 1, 64)                   [вирівнювання за кеш-лінією 64 байти]
                 = 3840 байтів

height_0 (Luma)  = ALIGN(H, 16)
                 = ALIGN(2160, 16)                       [вирівнювання висоти відеокодека]
                 = 2160 рядків

size_0 (Luma)    = stride_0 · height_0
                 = 3840 · 2160
                 = 8294400 байтів (8100 КБ)

offset_1 (Chroma)= ALIGN(size_0, 4096)                   [вирівнювання зміщення за сторінкою MMU]
                 = ALIGN(8294400, 4096)
                 = 8294400 байтів

stride_1 (Chroma)= stride_0                              [крок UV площини дорівнює кроку Y]
                 = 3840 байтів

height_1 (Chroma)= H / 2
                 = 2160 / 2
                 = 1080 рядків

size_1 (Chroma)  = stride_1 · height_1
                 = 3840 · 1080
                 = 4147200 байтів (4050 КБ)

total_size       = offset_1 + size_1
                 = 8294400 + 4147200
                 = 12441600 байтів (11.865 МБ)
```

Для 10-бітного формату `P010` ширина кожного елемента подвоюється, тому `stride_0 = ALIGN(3840 · 2, 64) = 7680` байтів, а загальний обсяг пам'яті сягає 23.73 МБ.

### Розрахунок площин стиснення Intel CCS (RC CCS та MC CCS)

Коли для буфера увімкнено стиснення кольору (Render Compression — RC CCS для 3D GPU, або Media Compression — MC CCS для апаратного декодера відео VPU), структура пам'яті ускладнюється:
1. **Основна поверхня даних:** пікселі організуються у тайли (наприклад, Intel Tile4 або Y-Tile). Тайл Tile4 має розмір 4096 байтів (`64 байти завширшки × 64 рядки заввишки` для 8 bpp Luma, або `128 байтів завширшки × 32 рядки заввишки` для 16 bpp P010 та 32 bpp ARGB).
2. **Допоміжна поверхня метаданих стиснення (CCS):** кожні 64 байти поверхні CCS описують 16384 байти (16 КБ, 4 основні тайли по 4 КБ) первинних піксельних даних. Це задає фіксований коефіцієнт стиснення метаданих `1:256` за обсягом пам'яті.

При використанні модифікатора `I915_FORMAT_MOD_4_TILED_MTL_MC_CCS` на напівпланарному відеопотоці NV12 у виклику `ADDFB2` формуються **чотири окремі логічні площини**:
* **Площина 0:** Luma Y у розкладці Tile4;
* **Площина 1:** Chroma UV у розкладці Tile4;
* **Площина 2:** Поверхня метаданих CCS для площини Luma Y;
* **Площина 3:** Поверхня метаданих CCS для площини Chroma UV.

#### Розрахунок геометрії тайлованого буфера Tile4 з MC CCS для кадру 4K

```
tile_w_bytes     = 64 байта                              [ширина тайла Tile4 для 8 bpp Luma]
tile_h_lines     = 64 рядка                              [висота тайла Tile4 для 8 bpp Luma]

stride_0 (Luma)  = ALIGN(W, tile_w_bytes)
                 = ALIGN(3840, 64)
                 = 3840 байтів (60 тайлів у рядку)

height_0 (Luma)  = ALIGN(H, tile_h_lines)
                 = ALIGN(2160, 64)
                 = 2176 рядків (34 тайли у висоту)

size_0 (Luma)    = stride_0 · height_0
                 = 3840 · 2176
                 = 8355840 байтів (2040 тайлів)

stride_1 (Chroma)= ALIGN(W, 128)                         [для UV: 2 байти на пару, тайл 128x32]
                 = ALIGN(3840, 128)
                 = 3840 байтів

height_1 (Chroma)= ALIGN(H / 2, 32)
                 = ALIGN(1080, 32)
                 = 1088 рядків

offset_1 (Chroma)= ALIGN(size_0, 64 · 1024)              [вирівнювання дискретного GPU Arc: 64 КБ]
                 = ALIGN(8355840, 65536)
                 = 8388608 байтів (8 МБ)

size_1 (Chroma)  = stride_1 · height_1
                 = 3840 · 1088
                 = 4177920 байтів

stride_2 (CCS Y) = ALIGN((stride_0 / (tile_w_bytes · 4)) · 64, 64)
                 = ALIGN((3840 / 256) · 64, 64)
                 = ALIGN(15 · 64, 64)
                 = 960 байтів

height_2 (CCS Y) = ALIGN(height_0 / tile_h_lines, 4)
                 = ALIGN(34, 4)
                 = 36 рядків

offset_2 (CCS Y) = ALIGN(offset_1 + size_1, 65536)
                 = ALIGN(8388608 + 4177920, 65536)
                 = ALIGN(12566528, 65536)
                 = 12582912 байтів (12 МБ)

size_2 (CCS Y)   = stride_2 · height_2
                 = 960 · 36
                 = 34560 байтів

offset_3 (CCS UV)= ALIGN(offset_2 + size_2, 65536)
                 = ALIGN(12582912 + 34560, 65536)
                 = 12648448 байтів
```

Якщо передати у виклик `ADDFB2` зміщення `offset_2`, не вирівняне на 64 КБ (або 4 КБ для інтегрованих чипів), конструктор ядра негайно відхилить буфер із кодом `-EINVAL`.

### Геометрія метаданих AMD DCC та вирівнювання заліза

В архітектурі AMD RDNA (GFX10/GFX11) апаратне стиснення Delta Color Compression (DCC) також вимагає окремої поверхні метаданих. На відміну від Intel CCS, архітектура AMD підтримує незалежні блоки вибірки розміром 64 або 128 байтів (`DCC_INDEPENDENT_64B`, `DCC_INDEPENDENT_128B`), що регулюється відповідними бітами 64-бітного модифікатора.

Коефіцієнт розміру DCC становить `1/256` від основного розміру буфера. Проте контролер пам'яті дисплея DCN (Display Core Next) вимагає, щоб поверхня DCC була вирівняна за макро-тайлами 64 КБ (`AMD_FMT_MOD_TILE_GFX9_64K_D`) та піддавалася операції перетайлінгу (`DCC_RETILE`), якщо екранний контролер сканує кадр напряму.

Крок рядка метаданих DCC обчислюється як:

```
stride_dcc = ALIGN(stride_primary / 256, dcc_block_alignment)
```

де `dcc_block_alignment` залежить від кількості каналів пам'яті (Memory Channels) та активного прапорця перемішування `PIPE_XOR_BITS`.

## Що відбувається всередині ядра при виклику AddFB2

Коли простір користувача передає структуру `drm_mode_fb_cmd2` у системний виклик `DRM_IOCTL_MODE_ADDFB2`, підсистема ядра DRM KMS виконує сувору багатоступеневу верифікацію:

1. **Перевірка формату та прапорців:** ядро переконується, що переданий FourCC зареєстровано у глобальній таблиці форматів ядра (`drm_fourcc.c`). Якщо встановлено прапорець `DRM_MODE_FB_MODIFIERS`, ядро вимагає, щоб усі задіяні площини мали валідні значення модифікаторів (значення `DRM_FORMAT_MOD_INVALID` у цьому виклику заборонене).
2. **Пошук GEM-об'єктів за хендлами:** ядро перетворює числові значення `handles[p]` у покажчики на внутрішні структури `struct drm_gem_object`. Для кожної площини перевіряється, чи належить GEM-об'єкт поточному файловому дескриптору процесу та чи достатній його фізичний розмір для розміщення площини із заданим кроком `pitches[p]` та зміщенням `offsets[p]`.
3. **Виклик драйверо-специфічного конструктора:** ядро передає команду у зворотний виклик драйвера відеокарти (наприклад, `intel_user_framebuffer_create` у драйвері i915/Xe або `amdgpu_display_user_framebuffer_create` у amdgpu). Драйвер виконує апаратну перевірку:
   * Чи підтримує графічний чип саме цей модифікатор (наприклад, чи не намагається користувач виділити Intel Tile4 на старій архітектурі Skylake, де підтримується максимум Y-Tile).
   * Чи відповідає вирівнювання зміщень та кроку вимогам апаратного блоку сканування (наприклад, крок тайла Tile4 має бути строго кратним 512 байтам, а зміщення площини метаданих CCS — кратним 4096 байтам або 64 КБ).
4. **Створення екземпляра `struct drm_framebuffer`:** ядро створює довгоживучий об'єкт кадрового буфера, інкрементує лічильники посилань на відповідні GEM-об'єкти та повертає простору користувача унікальний числовий ідентифікатор `fb_id`.

## Синхронізація конвеєра: Explicit Sync, IN_FENCE_FD та OUT_FENCE_FD

Реєстрація кадрового буфера у KMS повертає `fb_id`, проте це не означає, що GPU вже завершив малювати пікселі в цей буфер. Оскільки графічні команди виконуються в чергах асинхронно, спроба вивести буфер на екран негайно призведе до артефактів **tearing** (розриву кадру) або відображення недомальованих трикутників.

### Від неявної резервації dma_resv до явної передачі sync_file

Історично в Linux застосовувалася **неявна синхронізація (Implicit Sync)**:
* Кожен об'єкт пам'яті `struct drm_gem_object` містить структуру `struct dma_resv` (Reservation Object).
* Драйвер дисплея KMS автоматично витягував активний фенс запису (`dma_fence`) з об'єкта `dma_resv` перед виконанням Page Flip і чекав завершення рендерингу перед перемиканням адреси сканування.

Неявна синхронізація мала суттєві недоліки: композитор не міг точно знати, який саме процес тримає буфер заблокованим, а будь-яке фонове читання буфера могло заблокувати графічний конвеєр.

Сучасний графічний стек (Wayland-протокол `linux-drm-syncobj-v1`, Vulkan та Atomic KMS) повністю перейшов на **явну синхронізацію (Explicit Sync)** за допомогою дескрипторів `sync_file` POSIX:

```
  Клієнт (Vulkan / EGL)                 Композитор (Wayland)              Ядро Linux (Atomic KMS)
  =====================                 ====================              =======================
  Рендерить 3D-сцену
  Створює in_fence_fd
  Надсилає: buffer + in_fence_fd  --->  Отримує буфер і FD
                                        Додає властивості:
                                        PLANE.IN_FENCE_FD = in_fence_fd
                                        CRTC.OUT_FENCE_PTR = &out_fence_fd
                                        drmModeAtomicCommit() --------->  Перетворює in_fence_fd у dma_fence
                                                                          Створює новий out_fence_fd
                                        Отримує out_fence_fd <----------  Повертає керування (NONBLOCK)
  Отримує out_fence_fd <--------------  Передає out_fence_fd клієнту
  [Чекає out_fence_fd перед                                               [Апаратне очікування in_fence]
   перезаписом буфера]                                                    [VBLANK: адресний фліп]
                                                                          [Сигналізує out_fence_fd]
```

### Алгоритм підключення фенсів у drmModeAtomicCommit

Під час підготовки атомарного запиту `drmModeAtomicReq` композитор зв'язує вхідні та вихідні дескриптори фенсів:

1. **Властивість площини `IN_FENCE_FD`:**
   * Композитор передає отриманий від клієнта файловий дескриптор синхронізації `in_fence_fd`.
   * Ядро перетворює цей файловий дескриптор на внутрішній покажчик `struct dma_fence` і приєднує його до стану площини `plane_state->fence`.
   * Апаратний дисплейний блок гарантовано чекає переходу цього фенса у стан сигналу (signaled) перед тим, як надіслати команду адресного перемикання (Page Flip) контролеру DMA дисплея.
2. **Властивість CRTC `OUT_FENCE_PTR`:**
   * Композитор передає адресу 64-бітної локальної змінної `uint64_t out_fence_ptr = (uint64_t)&out_fence_fd`.
   * Ядро виділяє новий об'єкт `struct dma_fence`, загортає його в анонімний файловий дескриптор `sync_file` і записує отримане ціле число за вказаною адресою простору користувача.
3. **Неблокуючий комміт:**
   * Виклик `drmModeAtomicCommit(drm_fd, req, DRM_MODE_ATOMIC_NONBLOCK | DRM_MODE_PAGE_FLIP_EVENT, user_data)` негайно повертає успіх `0`, не блокуючи головний потік віконного композитора.

### Життєвий цикл кадру та передача out-fence клієнту

Коли попередня операція сканування завершується і промінь розгортки проходить зону гасячого імпульсу (VBLANK), контролер дисплея перемикається на новий кадровий буфер.

У цей момент ядро переводить `out_fence` у стан сигналу. Отримавши цей сигнал через `poll()` або прив'язавши його до черги Vulkan через `VkTimelineSemaphore`, клієнтський додаток знає: попередній кадровий буфер більше не сканується контролером монітора, і його фізичну пам'ять можна безпечно перевикористати для рендерингу наступного кадру.

## Відновлення після помилок та обробка відхилень атомарного коміту

Навіть якщо виклик `drmModeAddFB2WithModifiers()` повернув валідний `fb_id`, спроба відобразити цей кадровий буфер через `drmModeAtomicCommit()` може бути відхилена ядром.

Надійний графічний сервер або віконний композитор зобов'язаний обробляти типові коди помилок та реалізовувати багаторівневу стратегію аварійного перемикання (fallback strategy).

```
                            drmModeAtomicCommit(TEST_ONLY)
                                          |
                        +-----------------+-----------------+
                        |                                   |
                   Успіх (0)                           Помилка (< 0)
                        |                                   |
             Direct Scanout активний                        v
                                               +------------------------+
                                               | Аналіз errno           |
                                               +------------------------+
                                                /          |           \
                                       -EINVAL /    -EBUSY |    -ENOSPC \
                                              v            v             v
                                     +-------------+ +-------------+ +-------------+
                                     | Перехід на  | | Відкласти   | | Вимкнути    |
                                     | GPU Render  | | на наступний| | оверлеї /   |
                                     | Compositing | | такт VBLANK | | знизити FPS |
                                     +-------------+ +-------------+ +-------------+
                                            |
                                            v
                                     +-------------+
                                     | Оновити     |
                                     | Wayland     |
                                     | Feedback    |
                                     +-------------+
```

### Діагностика кодів повернення: EINVAL, EBUSY, ENOSPC та ERANGE

1. **Помилка `-EINVAL` (Invalid Argument):**
   * **Причина:** Несумісна комбінація модифікатора та формату для обраної площини CRTC, або порушення апаратних обмежень геометрії (наприклад, спроба масштабування оверлею з коефіцієнтом понад 4×, або спроба розмістити буфер із тайлінгом Tile4 на старій площині курсора, що вимагає лінійного формату).
   * **Дія:** Композитор миттєво відмовляється від прямого виведення (Direct Scanout) для цього клієнтського вікна.
2. **Помилка `-EBUSY` (Resource Busy):**
   * **Причина:** Попередній неблокуючий атомарний коміт для цього CRTC все ще виконується в апаратній черзі (in-flight atomic state), або виник конфлікт за спільний блок тактового генератора (Shared PLL) між двома моніторами.
   * **Дія:** Композитор не відкидає кадр, а стає в чергу очікування системної події VBLANK через `drmHandleEvent()` або дескриптор `out_fence_fd`.
3. **Помилка `-ENOSPC` або `-ERANGE` (No Space / Result Out of Range):**
   * **Причина:** Перевищення сумарної пропускної здатності шини контролера дисплея (Display FIFO Bandwidth Underrun). Якщо увімкнути три незалежні 4K-оверлеї на частоті 120 Гц, внутрішня пропускна здатність контролера DCN/DPU вичерпується.
   * **Дія:** Контролер відхиляє активацію додаткових оверлейних площин. Композитор переводить частину поверхонь у режим фонового GPU-рендерингу.

### Багаторівнева стратегія fallback у віконному композиторі

Якщо тестовий виклик із прапорцем `DRM_MODE_ATOMIC_TEST_ONLY` завершується помилкою, конвеєр виконує чотири кроки відновлення:

1. **Крок 1: Тестова валідація (Pre-flight Test):**
   Перед зміною стану дисплея надсилається запит `drmModeAtomicCommit(..., DRM_MODE_ATOMIC_TEST_ONLY)`. Цей виклик перевіряє всю конфігурацію в ядрі без перемикання реальних апаратних регістрів.
2. **Крок 2: Відкат до 3D-компонування (Render Pass Fallback):**
   Якщо тест провалився, композитор монтує клієнтський `dma-buf` як звичайну вхідну текстуру (EGLImage / VkImage) у свій внутрішній рендерер. Композитор малює вікно клієнта на власному головному кадровому буфері стільниці, який гарантовано підтримується дисплеєм.
3. **Крок 3: Переузгодження через Wayland Feedback:**
   Композитор надсилає клієнту оновлену подію `wp_linux_dmabuf_feedback_v1.tranche_flags` без прапорця `SCANOUT` для цієї площини. Клієнтський графічний рушій при наступному виділенні буфера відмовляється від конфліктного модифікатора на користь підтримуваного базового тайлінгу.
4. **Крок 4: Захист від витоку дескрипторів:**
   Якщо реєстрація зазнає збою на проміжних етапах, програма негайно закриває відкриті файлові дескриптори `plane_fds` та звільняє тимчасові хендли `DRM_IOCTL_GEM_CLOSE`.

Для налагодження роботи модифікаторів та перевірки активного стану конвеєра на рівні ядра використовують системні інструменти та інтерфейси `debugfs`.

## Підводні камені та практичні пастки

1. **Час життя файлових дескрипторів та GEM-хендлів:**
   * Виклик `drmPrimeFDToHandle()` створює локальний GEM-хендл у файловому описі DRM. Після того, як `drmModeAddFB2WithModifiers()` успішно повертає `fb_id`, сам об'єкт кадрового буфера ядра збільшує лічильник посилань на відповідні об'єкти пам'яті.
   * Простір користувача **зобов'язаний** закрити тимчасові хендли викликом `DRM_IOCTL_GEM_CLOSE`, інакше у системі виникне витік хендлів ядра (handle leak). Таблиця хендлів процесу в ядрі обмежена, і її переповнення призведе до помилок `-ENOSPC` у наступних графічних викликах.
   * Водночас файлові дескриптори `plane_fds` можна або закрити одразу, або зберегти (наприклад, якщо композитор планує передати їх іншому процесу через сокет домену Unix за протоколом Wayland).

2. **Один спільний dma-buf проти кількох фізичних файлів:**
   * Для буферів із допоміжними площинами стиснення (як-от Intel CCS чи AMD DCC) функція `gbm_bo_get_fd_for_plane(bo, 0)` та `gbm_bo_get_fd_for_plane(bo, 1)` найчастіше повертають два **незалежні файлові дескриптори**, які насправді посилаються на один і той самий анонімний об'єкт `struct dma_buf` у ядрі, але мають різні зміщення `offsets[p]`.
   * Кожен із цих числових дескрипторів є окремим записом у таблиці дескрипторів процесу, тому закривати їх потрібно окремо. Некоректне закриття лише нульового дескриптора залишає відкритими дескриптори допоміжних площин.

3. **Попередня перевірка через атомарний тестовий комміт:**
   * Навіть якщо ядро успішно виконало `drmModeAddFB2WithModifiers`, це не гарантує, що конкретна апаратна площина CRTC здатна показати цей буфер за поточної тактової частоти піксельного генератора (dotclock), поточної глибини кольору чи активного апаратного масштабування.
   * Перед виведенням на екран надійний композитор виконує тестовий виклик `drmModeAtomicCommit()` із прапорцем `DRM_MODE_ATOMIC_TEST_ONLY`. Якщо повертається `-EINVAL` або `-ERANGE`, композитор миттєво перемикається на програмне або GPU-компонування кадру без візуального мерехтіння дисплея.

4. **Прямий доступ центрального процесора (CPU mmap) та відсутність детайлінгу:**
   * Якщо програма спробує відобразити виділений буфер у свій адресний простір через `mmap()` на дескриптор `dma-buf`, процесор отримає прямий доступ до фізичних сторінок пам'яті.
   * Для лінійного модифікатора `DRM_FORMAT_MOD_LINEAR` процесор може читати й записувати пікселі як стандартний двовимірний масив.
   * Проте для будь-якого тайлованого чи стисненого модифікатора (наприклад, Intel Tile4 або Arm AFBC) байти в пам'яті фізично перемішані згідно з кривими Мортона або блоковими заголовками. Спроба записати туди пікселі процесором напряму призведе до повного руйнування зображення, оскільки CPU не має апаратного блоку детайлінгу (англ. *detiling engine*). Для модифікованих буферів запис здійснюється виключно через графічні API (Vulkan, OpenGL, EGL) або за допомогою апаратного блітера ядра.

5. **Несумісність модифікаторів у Multi-GPU конфігураціях (PRIME Offloading):**
   * У ноутбуках із двома відеокартами (наприклад, дискретний GPU AMD/NVIDIA рендерить гру, а інтегрований чип Intel керує виходом на екран) виникає крос-пристроєвий конфлікт.
   * Інтегрований контролер дисплея Intel принципово не здатний прочитати пропрієтарний тайлінг `AMD_FMT_MOD_TILE_GFX9_64K` чи метадані DCC.
   * У цьому випадку графічний стек Mesa автоматично виконує крок детайлінгу (resolve pass): дискретний GPU малює кадр у внутрішній тайлований буфер, а перед експортом копіює його апаратним блітером у спільний буфер із модифікатором `DRM_FORMAT_MOD_LINEAR` або стандартним `I915_FORMAT_MOD_X_TILED`.

6. **Суворі вимоги до вирівнювання кроку (Stride Alignment):**
   * Для тайлованих поверхонь крок рядка `pitch` не може дорівнювати довільному значенню `width * bytes_per_pixel`.
   * Для тайлів Intel Tile4 крок повинен бути строго кратним 512 байтам, а висота — кратною 32 або 64 рядкам.
   * Для площин стиснення CCS зміщення `offsets[1]` зобов'язане вирівнюватися за межею сторінки 4096 байтів або 64 КБ. Спроба передати невирівняне зміщення у виклик `ADDFB2` повертає помилку `-EINVAL` безпосередньо з конструктора драйвера.
