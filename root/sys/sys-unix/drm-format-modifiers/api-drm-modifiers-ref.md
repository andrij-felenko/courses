## 1. Реєстр кодувань форматів пікселів DRM FourCC

Формати пікселів у підсистемі DRM ядра Linux базуються на чотирисимвольних кодах FourCC (англ. *Four Character Code*). Код пакується у беззнакове 32-бітне ціле число в порядку байтів Little-Endian за допомогою макроса ядра, визначеного у файлі заголовків `<drm/drm_fourcc.h>`:

```
#define fourcc_code(a, b, c, d) \
    ((uint32_t)(a) | ((uint32_t)(b) << 8) | \
    ((uint32_t)(c) << 16) | ((uint32_t)(d) << 24))
```

Для систем із прямим порядком байтів (Big-Endian) стандарт DRM надає спеціальний модифікуючий бітовий прапорець:

```
#define DRM_FORMAT_BIG_ENDIAN (1U << 31)
```

Якщо старший біт 31 не встановлено, формат вважається канонічним Little-Endian.

### Анатомія системних назв та порядок байтів у пам'яті

Найменування форматів у DRM FourCC описує розташування бітових полів усередині цілочисельного машинного слова процесора (`uint16_t`, `uint32_t` або `uint64_t`), прочитаного з пам'яті за адресою Little-Endian. Перша літера назви позначає найстарші біти регістра, а остання — наймолодші біти.

Через це на архітектурах Little-Endian (x86_64, AArch64, RISC-V) порядок бітів у регістрі та послідовність байтів у фізичній пам'яті RAM є дзеркальними:

* Для формату `DRM_FORMAT_ARGB8888` (`fourcc_code('A','R','2','4')`):
  * Регістр CPU `uint32_t`: альфа-канал займає біти `[31:24]`, червоний (R) — `[23:16]`, зелений (G) — `[15:8]`, синій (B) — `[7:0]`.
  * Фізичні байти в RAM за зростанням адрес:
    * Байт 0 (молодша адреса `ptr + 0`): Синій канал (Blue, біти `[7:0]`).
    * Байт 1 (`ptr + 1`): Зелений канал (Green, біти `[15:8]`).
    * Байт 2 (`ptr + 2`): Червоний канал (Red, біти `[23:16]`).
    * Байт 3 (`ptr + 3`): Альфа-канал (Alpha, біти `[31:24]`).

## 2. 64-бітне кодування модифікаторів DRM

Модифікатор формату зберігається у 64-бітному полі `uint64_t modifier`. Старші 8 бітів (біти `[63:56]`) виділені під ідентифікатор виробника (Vendor ID), а молодші 56 бітів (біти `[55:0]`) — під вендорно-специфічний опис геометрії блоків, перемішування бітів (swizzling) та допоміжних площин стиснення.

```
+------------------------+-------------------------------------------------------------+
| Vendor ID (8 бітів)    | Код розкладки, тайлінгу та параметрів стиснення (56 бітів)  |
| Біти 63 .. 56          | Біти 55 .. 0                                                |
+------------------------+-------------------------------------------------------------+
```

Такий поділ виключає конфлікти числових просторів імен між різними виробниками апаратного забезпечення.

### Ідентифікатори виробників графічних процесорів

```
#define DRM_FORMAT_MOD_VENDOR_NONE      0x00
#define DRM_FORMAT_MOD_VENDOR_INTEL     0x01
#define DRM_FORMAT_MOD_VENDOR_AMD       0x02
#define DRM_FORMAT_MOD_VENDOR_NVIDIA    0x03
#define DRM_FORMAT_MOD_VENDOR_SAMSUNG   0x04
#define DRM_FORMAT_MOD_VENDOR_QCOM      0x05
#define DRM_FORMAT_MOD_VENDOR_VIVANTE   0x06
#define DRM_FORMAT_MOD_VENDOR_BROADCOM  0x07
#define DRM_FORMAT_MOD_VENDOR_ARM       0x08
#define DRM_FORMAT_MOD_VENDOR_ALLWINNER 0x09
#define DRM_FORMAT_MOD_VENDOR_AMLOGIC   0x0a
```

### Макроси формування та виділення модифікаторів

```
#define fourcc_mod_code(vendor, val) \
    ((((uint64_t)DRM_FORMAT_MOD_VENDOR_##vendor) << 56) | \
     ((val) & 0x00ffffffffffffffULL))

#define fourcc_mod_get_vendor(modifier) \
    (((modifier) >> 56) & 0xff)

#define fourcc_mod_is_vendor(modifier, vendor) \
    (fourcc_mod_get_vendor(modifier) == DRM_FORMAT_MOD_VENDOR_##vendor)
```

### Універсальні стандартизовані модифікатори

У просторі `DRM_FORMAT_MOD_VENDOR_NONE` зафіксовано два фундаментальні загальносистемні модифікатори:

* **`DRM_FORMAT_MOD_INVALID`:** значення `((1ULL << 56) - 1)` (`0x00ffffffffffffffULL`).
  * **Семантика:** слугує маркером «модифікатор не вказано або невідомий». Використовується застарілим програмним забезпеченням як запит до драйвера обрати неявну внутрішню розкладку (driver-private implicit tiling).
  * **Нормативне обмеження ABI:** передача значення `DRM_FORMAT_MOD_INVALID` у системний виклик `DRM_IOCTL_MODE_ADDFB2` із встановленим прапорцем `DRM_MODE_FB_MODIFIERS` є неприпустимою і завжди повертає помилку `-EINVAL`.
* **`DRM_FORMAT_MOD_LINEAR`:** значення `0ULL` (`fourcc_mod_code(NONE, 0)`).
  * **Семантика:** гарантує строгий растровий порядок рядків пам'яті:
    `адреса(x, y) = base_ptr + (y * pitch) + (x * bpp / 8)`
  * **Властивості:** не містить тайлінгу, перемішування бітів чи стиснення. Дозволяє прямий доступ центрального процесора через `mmap()`, не потребує допоміжних площин і підтримується будь-яким дисплейним контролером, програмним растеризатором та пристроєм захоплення відео.

#### Специфікація розкладки тайла Intel Tile4

Розкладка Tile4 оптимізована для кешів останнього рівня L3 (LLC). Тайл розміром 4096 байтів формується з 64 суб-тайлів по 64 байти. Кожен суб-тайл має розмір 16 байтів завширшки на 4 рядки заввишки. Суб-тайли розташовуються у шаховому порядку, усуваючи просторові асиметрії під час вибірки 2D-текстур.

#### Специфікація допоміжних площин Intel CCS та Clear Color

* **Площина 0 (Primary Data):** містить піксельні дані, організовані у відповідні тайли (Tile4 або Y-Tile).
* **Площина 1 (Auxiliary CCS):** містить бітові карти метаданих стиснення. Для архітектури Gen12 / Xe кожні 64 байти площини CCS кодують стан стиснення для 16384 байтів (4 тайли) основної пам'яті.
* **Площина 2 (Clear Color):** містить 64 байти метаданих, де збережено 32-бітне або 64-бітне значення колірного очищення (Native Clear Color RGBA). Дисплейний блок зчитує це значення під час сканування блоків, позначених у CCS як очищені, уникаючи читання основного тіла кадру.

### Модифікатори AMD (`<drm/drm_fourcc.h>`)

Модифікатори AMD кодують покоління мікроархітектури, параметри тайлінгу, стиснення Delta Color Compression (DCC) та конфігурацію перемішування адрес між банками та конвеєрами (Pipe/Bank XOR Swizzling).

#### Структура бітових полів AMD у 56-бітному корисному навантаженні

```
+-----------+--------+-----+------------+---------------+--------------------+---------------+---------------+---------+----+------+
| TILE_VER  | TILE   | DCC | DCC_RETILE | DCC_PIPE_ALGN | DCC_INDEP_64B/128B | PIPE_XOR_BITS | BANK_XOR_BITS | PACKERS | RB | PIPE |
| [2:0]     | [7:3]  | [8] | [9]        | [12:10]       | [13:14]            | [19:16]       | [22:20]       | [25:23] |[28:26]|[31:29]|
+-----------+--------+-----+------------+---------------+--------------------+---------------+---------------+---------+----+------+
```

* `TILE_VERSION` (`біти [2:0]`): `1` = GFX9 (Vega), `2` = GFX10 (RDNA1), `3` = GFX10_RBPLUS (RDNA2), `4` = GFX11 (RDNA3), `5` = GFX12 (RDNA4).
* `TILE` (`біти [7:3]`): базовий режим тайлінгу:
  * `AMD_FMT_MOD_TILE_GFX9_64K_S` (`0x09`): стандартний мікро/макро-тайл 64 КБ (Standard 64K) для 3D-шейдерів.
  * `AMD_FMT_MOD_TILE_GFX9_64K_D` (`0x0a`): дисплейний тайл 64 КБ (Display 64K).
  * `AMD_FMT_MOD_TILE_GFX9_64K_R` (`0x0b`): Render Target 64K.
  * `AMD_FMT_MOD_TILE_GFX103_64K_R_X`: тайл 64 КБ архітектури RDNA2/RDNA3 (GFX10.3) з перемішуванням конвеєрів (Pipe XOR Swizzle).
  * `AMD_FMT_MOD_TILE_GFX11_256K_R_X`: тайл 256 КБ архітектури RDNA3 (GFX11) зі swizzling.
* `DCC` (`біт 8`): встановлено в `1`, якщо буфер має додаткову площину метаданих стиснення Delta Color Compression.
* `DCC_RETILE` (`біт 9`): вмикає перетайлінг DCC-метаданих для можливості прямого читання дисплейним процесором DCN (Display Core Next).
* `DCC_PIPE_ALIGN` (`біти [12:10]`): вирівнювання метаданих за конвеєрами контролера пам'яті.
* `DCC_INDEPENDENT_64B` (`біт 13`) / `DCC_INDEPENDENT_128B` (`біт 14`): блокує залежність між сусідніми стисненими блоками, забезпечуючи вибірку текстур блоками по 64 або 128 байтів.
* `PIPE_XOR_BITS` (`біти [19:16]`), `BANK_XOR_BITS` (`біти [22:20]`): бітові маски операцій XOR над адресами сторінок DRAM для запобігання апаратним колізіям банків пам'яті.

### Модифікатори Arm AFBC (Arm FrameBuffer Compression)

Формат AFBC розроблено компанією Arm для графічних процесорів Mali та дисплейних контролерів DPU (Display Processing Unit). Буфер AFBC розміщується в єдиній області пам'яті або розділяється на заголовки та тіло і складається з двох зон:
1. **AFBC Header:** масив 16-байтних заголовків суперблоків (16 байтів на кожен блок 16×16 або 32×8 пікселів). Заголовок містить 32-бітне байтове зміщення тіла суперблока від початку буфера, бітові теги довжин суб-блоків та метадані одноколірної заливки (Solid Color).
2. **AFBC Body:** область стиснених суб-блоків змінної довжини.

Формування 64-бітного модифікатора здійснюється макросом `DRM_FORMAT_MOD_ARM_AFBC(flags)`:

```
#define DRM_FORMAT_MOD_ARM_CODE(val, val_hi) \
    fourcc_mod_code(ARM, ((uint64_t)(val) | ((uint64_t)(val_hi) << 32)))

#define DRM_FORMAT_MOD_ARM_AFBC(flags) \
    DRM_FORMAT_MOD_ARM_CODE(DRM_FORMAT_MOD_ARM_TYPE_AFBC, (flags))
```

#### Бітові поля геометрії суперблока (`біти [3:0]` у flags)

```
#define AFBC_FORMAT_MOD_BLOCK_SIZE_MASK      0xf
#define AFBC_FORMAT_MOD_BLOCK_SIZE_16x16     0x1
#define AFBC_FORMAT_MOD_BLOCK_SIZE_32x8      0x2
#define AFBC_FORMAT_MOD_BLOCK_SIZE_64x4      0x3
#define AFBC_FORMAT_MOD_BLOCK_SIZE_32x8_64x4 0x4
```

* `AFBC_FORMAT_MOD_BLOCK_SIZE_16x16` (`0x01`): суперблоки розміром 16×16 пікселів (квадратний блок; базовий стандарт для 3D-графіки Mali Bifrost та Valhall).
* `AFBC_FORMAT_MOD_BLOCK_SIZE_32x8` (`0x02`): суперблоки розміром 32×8 пікселів (оптимізовано під рядкову розгортку дисплейних процесорів DPU та відеопотоки VPU).
* `AFBC_FORMAT_MOD_BLOCK_SIZE_64x4` (`0x03`): суперблоки 64×4 пікселі для спеціалізованих конвеєрів камер.
* `AFBC_FORMAT_MOD_BLOCK_SIZE_32x8_64x4` (`0x04`): гібридний розмір блоків.

#### Бітові прапорці алгоритмів та розширень AFBC (`біти [55:4]`)

```
#define AFBC_FORMAT_MOD_YTR            (1ULL << 4)
#define AFBC_FORMAT_MOD_SPARSE         (1ULL << 5)
#define AFBC_FORMAT_MOD_CBR            (1ULL << 6)
#define AFBC_FORMAT_MOD_SPLIT_BLOCK    (1ULL << 7)
#define AFBC_FORMAT_MOD_TILED          (1ULL << 8)
#define AFBC_FORMAT_MOD_SC             (1ULL << 9)
#define AFBC_FORMAT_MOD_DB             (1ULL << 10)
#define AFBC_FORMAT_MOD_BCH            (1ULL << 11)
#define AFBC_FORMAT_MOD_USM            (1ULL << 12)
#define AFBC_FORMAT_MOD_TILED_HEADER   (1ULL << 13)
#define AFBC_FORMAT_MOD_CROP           (1ULL << 14)
#define AFBC_FORMAT_MOD_32_BYTE_ALIGN  (1ULL << 15)
```

* `AFBC_FORMAT_MOD_YTR` (Reversible Color Space Transform): оборотне перетворення простору RGB у внутрішній простір YUV у цілих числах без втрат:
  `Y = floor((R + 2*G + B) / 4)`, `U = R - G`, `V = B - G`
  Знижує ентропію каналів і покращує коефіцієнт стиснення на 20–35%.
* `AFBC_FORMAT_MOD_SPARSE`: розріджена алокація. Порожні суперблоки кодуються нульовим зміщенням у 16-байтному заголовку без виділення фізичних сторінок пам'яті в тілі буфера.
* `AFBC_FORMAT_MOD_CBR`: режим фіксованого бітрейту (Constant Bitrate) для дисплейних каналів із гарантованою пропускною здатністю.
* `AFBC_FORMAT_MOD_SPLIT_BLOCK`: роздільне пакування суб-блоків. Колірні канали або компоненти яскравості/колірності упаковуються у незалежні бітові потоки всередині суперблока.
* `AFBC_FORMAT_MOD_TILED`: суперблоки розташовуються не лінійно, а у 2D-макротайлах 8×8 суперблоків (розмір 128×128 або 256×64 пікселів) для підвищення кеш-локальності Mali L2.
* `AFBC_FORMAT_MOD_SC` (Solid Color): якщо всі пікселі суперблока мають один колір, 32-бітний колір записується безпосередньо у 16-байтний заголовок AFBC, а тіло блока взагалі не записується у пам'ять.
* `AFBC_FORMAT_MOD_DB`: подвійна буферизація заголовків суперблоків.
* `AFBC_FORMAT_MOD_BCH`: блочно-стиснений заголовок (Block Compressed Header).
* `AFBC_FORMAT_MOD_USM`: нестиснений розріджений режим (Uncompressed Sparse Mode).
* `AFBC_FORMAT_MOD_TILED_HEADER`: заголовки суперблоків упорядковуються у пам'яті не растрово, а у тайловому порядку, ідентичному розкладці суперблоків тіла буфера. Режим впроваджено в GPU Mali-G72/G76/G78/G715 для усунення перехресних промахів кешу між заголовками й тілом.
* `AFBC_FORMAT_MOD_CROP`: підтримка кадрування (Crop). Розміри корисного навантаження суперблоків вирівнюються на межі суб-блоків, що дозволяє дисплейному контролеру сканувати кадровий буфер із довільним зміщенням вікна без повної декомпресії граничних суперблоків.
* `AFBC_FORMAT_MOD_32_BYTE_ALIGN`: примусове вирівнювання розміру стисненого тіла кожного суперблока на 32 байти (розмір шинної транзакції AXI).

#### Структура 16-байтного заголовка суперблока AFBC

Кожен суперблок розміром 16×16 або 32×8 пікселів описується структурою у таблиці заголовків:

```
+------------------------------------+------------------------------------+
| Байти 3 .. 0 (uint32_t Little-End) | Байт 4 .. Байт 15                  |
| Зміщення тіла блока (Base Offset)  | Теги розмірів суб-блоків 0..3 або  |
| від початку області тіла AFBC      | RGBA значення Solid Color          |
+------------------------------------+------------------------------------+
```

### Модифікатори Vivante (`<drm/drm_fourcc.h>`)

Графічні ядра VeriSilicon Vivante (GC-серія у SoC NXP i.MX6/i.MX8, StarFive JH7110) використовують 4×4 піксельні мікро-тайли та 64×64 піксельні супер-тайли:

```
#define DRM_FORMAT_MOD_VIVANTE_TILED             fourcc_mod_code(VIVANTE, 1)
#define DRM_FORMAT_MOD_VIVANTE_SUPER_TILED       fourcc_mod_code(VIVANTE, 2)
#define DRM_FORMAT_MOD_VIVANTE_SPLIT_TILED       fourcc_mod_code(VIVANTE, 3)
#define DRM_FORMAT_MOD_VIVANTE_SPLIT_SUPER_TILED fourcc_mod_code(VIVANTE, 4)
```

* `DRM_FORMAT_MOD_VIVANTE_TILED`: 2D-тайлінг 4×4 пікселі. Кожен тайл містить 16 пікселів, упорядкованих неперервно у пам'яті.
* `DRM_FORMAT_MOD_VIVANTE_SUPER_TILED`: дворівневий супер-тайлінг 64×64 пікселі. Супер-тайл складається з 16×16 базових тайлів 4×4, розташованих у порядку Z-кривої.
* `DRM_FORMAT_MOD_VIVANTE_SPLIT_TILED`: тайлінг 4×4 пікселі, розщеплений між двома паралельними піксельними конвеєрами GPU (Dual Pipe). Парні й непарні рядки тайлів спрямовуються у різні банки пам'яті.
* `DRM_FORMAT_MOD_VIVANTE_SPLIT_SUPER_TILED`: розщеплений супер-тайлінг 64×64 пікселі для двоконвеєрних та чотириконвеєрних ядер Vivante GC7000.

Для апаратного стиснення тайлів Vivante застосовує розширення стану тайлів (Tile Status / DEC400): прапорці додаються макросами масок у молодші біти коду модифікатора, вказуючи крок та наявність буфера TS (Tile Status Buffer).

### Модифікатори Broadcom VideoCore (`<drm/drm_fourcc.h>`)

Підсистема графіки Broadcom для чипів VideoCore IV / VI / VII (чипи BCM2835–BCM2712 у платах Raspberry Pi 1–5) містить спеціалізовані розкладки для 3D-ядер, дисплейних блоків та апаратних відеодекодерів:

#### Broadcom T-Tiled

```
#define DRM_FORMAT_MOD_BROADCOM_VC4_T_TILED fourcc_mod_code(BROADCOM, 1)
```

* `DRM_FORMAT_MOD_BROADCOM_VC4_T_TILED`: розкладка T-Tiling відеоядра VideoCore IV (VC4). Пам'ять організована у макро-тайли розміром 4 КБ (128×32 байти для 32bpp або 256×16 байтів для 16bpp). Кожен макро-тайл 4 КБ складається з чотирьох суб-тайлів по 1 КБ, розташованих у шаховому порядку з мікро-перемішуванням бітів (Micro-Tile Swizzle).

#### Broadcom SAND (Stride And No Downsample)

Розкладка SAND оптимізована для блоків апаратного декодування відео (H.264, HEVC, VP9) та камерних ISP. Пам'ять розбивається на вертикальні стовпці (колонки) фіксованої ширини (32, 64, 128 або 256 байтів), а висота колонки вказується у рядках макросом:

```
#define DRM_FORMAT_MOD_BROADCOM_SAND32_COL_HEIGHT(h)  fourcc_mod_code(BROADCOM, (2 | ((h) << 8)))
#define DRM_FORMAT_MOD_BROADCOM_SAND64_COL_HEIGHT(h)  fourcc_mod_code(BROADCOM, (3 | ((h) << 8)))
#define DRM_FORMAT_MOD_BROADCOM_SAND128_COL_HEIGHT(h) fourcc_mod_code(BROADCOM, (4 | ((h) << 8)))
#define DRM_FORMAT_MOD_BROADCOM_SAND256_COL_HEIGHT(h) fourcc_mod_code(BROADCOM, (5 | ((h) << 8)))

#define DRM_FORMAT_MOD_BROADCOM_SAND32  DRM_FORMAT_MOD_BROADCOM_SAND32_COL_HEIGHT(0)
#define DRM_FORMAT_MOD_BROADCOM_SAND64  DRM_FORMAT_MOD_BROADCOM_SAND64_COL_HEIGHT(0)
#define DRM_FORMAT_MOD_BROADCOM_SAND128 DRM_FORMAT_MOD_BROADCOM_SAND128_COL_HEIGHT(0)
#define DRM_FORMAT_MOD_BROADCOM_SAND256 DRM_FORMAT_MOD_BROADCOM_SAND256_COL_HEIGHT(0)
```

Значення висоти колонки `h = 0` означає стандартну висоту 128 рядків. Усі пікселі всередині однієї колонки записуються зверху вниз, після чого починається наступна вертикальна колонка. Така геометрія усуває потребу у проміжному перевпорядкуванні байтів під час прямого сканування декодованого кадру дисплейним процесором HVS (Hardware Video Scaler).

#### Broadcom UIF (Unified Intermediate Format)

```
#define DRM_FORMAT_MOD_BROADCOM_UIF fourcc_mod_code(BROADCOM, 6)
```

* `DRM_FORMAT_MOD_BROADCOM_UIF`: уніфікований проміжний формат для GPU VideoCore VII / V3D (Raspberry Pi 5). Складається з мікро-тайлів 4×4 пікселі, згрупованих у макро-тайли 64 КБ зі збалансованим чергуванням банків SDRAM.

### Модифікатори NVIDIA Block-Linear (`<drm/drm_fourcc.h>`)

NVIDIA організовує графічну пам'ять у блоки GOB (Group of Bytes) розміром 512 байтів: 64 байти завширшки на 8 ліній заввишки. GOB розбивається на 16 секторів по 32 байти (4 сектори завширшки на 4 рядки заввишки), всередині яких біти координат перемішуються апаратним блоком растеризації.

Модифікатор кодується макросом:

```
#define DRM_FORMAT_MOD_NVIDIA_BLOCK_LINEAR_2D(c, s, f, e, h) \
    fourcc_mod_code(NVIDIA, (0x10 | \
        ((h) & 0xf) | \
        (((f) & 0x7) << 20) | \
        (((e) & 0x1) << 23) | \
        (((c) & 0x7) << 24) | \
        (((s) & 0x1) << 28)))
```

* `h` (`біти [3:0]`): висота блоку у кількості GOB (логарифм за основою 2):
  * `h = 0`: висота 1 GOB (8 рядків кадру).
  * `h = 1`: висота 2 GOBs (16 рядків).
  * `h = 2`: висота 4 GOBs (32 рядки).
  * `h = 3`: висота 8 GOBs (64 рядки).
  * `h = 4`: висота 16 GOBs (128 рядків).
  * `h = 5`: висота 32 GOBs (256 рядків).
* `f` (`біти [22:20]`): тип формату / kind у підсистемі MMU GPU NVIDIA.
* `e` (`біт 23`): прапорець конфігурації секторів пам'яті.
* `c` (`біти [26:24]`): тип стиснення кольору та метаданих Fast Clear.
* `s` (`біт 28`): бітовий режим чергування банків (Sub-slice / Bank Swizzling) для дискретних GPU (Tegra K1/X1/Orin та архітектури GeForce Kepler, Maxwell, Pascal, Volta, Turing, Ampere, Ada Lovelace, Blackwell).

### Модифікатори Allwinner та Amlogic

* `DRM_FORMAT_MOD_ALLWINNER_TILED` (`fourcc_mod_code(ALLWINNER, 1)`): тайлінг MB32 (макроблоки 32×32 байти) апаратного відеодекодера Allwinner CedarX.
* `DRM_FORMAT_MOD_AMLOGIC_FBC(mode, layout)` (`fourcc_mod_code(AMLOGIC, ...)`): пропрієтарне стиснення кадрового буфера Amlogic FBC для процесорів S905 / A311D.

## 4. Системні виклики та структури DRM UAPI ядра Linux

### Реєстрація кадрового буфера `drm_mode_fb_cmd2` та `DRM_IOCTL_MODE_ADDFB2`

Реєстрація об'єкта кадрового буфера у підсистемі KMS ядра Linux виконується за допомогою системного виклику `ioctl(drm_fd, DRM_IOCTL_MODE_ADDFB2, &cmd)`:

```
struct drm_mode_fb_cmd2 {
    uint32_t fb_id;          /* [out] Призначений ядром ідентифікатор кадрового буфера */
    uint32_t width;          /* Ширина буфера в пікселях */
    uint32_t height;         /* Висота буфера в пікселях */
    uint32_t pixel_format;   /* 32-бітний код DRM FourCC (наприклад, DRM_FORMAT_ARGB8888) */
    uint32_t flags;          /* Бітові прапорці конфігурації (DRM_MODE_FB_*) */

    uint32_t handles[4];     /* GEM-хендли пам'яті для кожної з площин (до 4 площин) */
    uint32_t pitches[4];     /* Крок рядка (stride) у байтах для кожної площини */
    uint32_t offsets[4];     /* Зміщення площини від початку відповідного GEM-об'єкта */
    uint64_t modifier[4];    /* 64-бітний DRM Format Modifier для кожної площини */
};
```

#### Прапорці конфігурації `flags`

* `DRM_MODE_FB_INTERLACED` (`0x01`): буфер містить черезрядкову розгортку.
* `DRM_MODE_FB_MODIFIERS` (`0x02`): вказує ядру зчитувати значення з масиву `modifier[4]`. Якщо прапорець відсутній, ядро ігнорує масив модифікаторів і застосовує неявну лінійну розкладку або застарілий драйверний тайлінг.

#### Алгоритм валідації виклику ADDFB2 всередині ядра

Коли процес викликає `DRM_IOCTL_MODE_ADDFB2`, ядро виконує перевірки у такій послідовності:

1. **Перевірка формату FourCC:** ядро шукає `pixel_format` у глобальній таблиці `drm_fourcc.c`. Якщо формат не зареєстровано — виклик завершується з `-EINVAL`.
2. **Перевірка прапорців та модифікаторів:**
   * Якщо прапорець `DRM_MODE_FB_MODIFIERS` встановлено, значення `modifier[0]` не може дорівнювати `DRM_FORMAT_MOD_INVALID` (повертає `-EINVAL`).
   * Для багатоплощинних форматів усі задіяні площини одного кадрового буфера повинні мати ідентичне значення модифікатора (якщо інше явно не дозволено драйвером).
   * Усі невикористані елементи масивів (`handles[p]`, `pitches[p]`, `offsets[p]`, `modifier[p]` для індексів `p >= num_planes`) зобов'язані містити суворе значення `0`.
3. **Резолвінг GEM-хендлів:** числові дескриптори `handles[p]` перетворюються на внутрішні покажчики `struct drm_gem_object`. Ядро перевіряє, що GEM-об'єкт належить файловому дескриптору викликаючого процесу.
4. **Контроль меж пам'яті:** ядро перевіряє, що розмір виділеного GEM-об'єкта достатній для розміщення площини:
   `розмір_GEM >= offsets[p] + (висота_площини * pitches[p])`
5. **Драйверна верифікація:** керування передається у зворотний виклик драйвера `funcs->fb_create`. Драйвер перевіряє апаратну підтримку комбінації `(FourCC, modifier)`, вирівнювання `pitches[p]` за шириною апаратного тайла та вирівнювання `offsets[p]` за сторінками MMU.
6. **Створення кадрового буфера:** ядро виділяє об'єкт `struct drm_framebuffer`, інкрементує лічильники посилань на GEM-об'єкти та повертає простору користувача числовий `fb_id`.

#### Коди помилок системного виклику ADDFB2

* `-EINVAL`: непідтримуваний FourCC; некоректні прапорці; передача `DRM_FORMAT_MOD_INVALID` із прапорцем `DRM_MODE_FB_MODIFIERS`; невідповідне вирівнювання `offsets` або `pitches` вимогам тайла; відмінні модифікатори для площин одного буфера.
* `-ENOENT`: числовий GEM-хендл у масиві `handles[]` не існує або не належить цьому процесу.
* `-ENOSPC`: фізичний розмір GEM-об'єкта менший за область, яку вимагає геометрія площини разом із метаданими.
* `-ERANGE`: ширина або висота перевищують апаратні ліміти сканування дисплейного блоку (Max Scanout Resolution).
* `-ENOMEM`: вичерпано пам'ять ядра для створення структури `struct drm_framebuffer`.
* `-EOPNOTSUPP`: драйвер не підтримує роботу з явними модифікаторами або не реалізує інтерфейс KMS.

### Запит конфігурації кадрового буфера `drm_mode_fb_cmd2` та `DRM_IOCTL_MODE_GETFB2`

Опитування параметрів зареєстрованого об'єкта кадрового буфера виконується за допомогою системного виклику `ioctl(drm_fd, DRM_IOCTL_MODE_GETFB2, &cmd)` (впроваджено в ядрі Linux 5.7). На відміну від застарілого виклику `DRM_IOCTL_MODE_GETFB` (структура `struct drm_mode_fb_cmd`), який підтримував лише одну площину пам'яті й не був здатний повертати 64-бітні модифікатори та кроки багатоплощинних YUV/допоміжних поверхонь CCS/DCC, виклик `GETFB2` використовує структуру `struct drm_mode_fb_cmd2`:

```
struct drm_mode_fb_cmd2 cmd = {
    .fb_id = target_fb_id, /* [in] Ідентифікатор кадрового буфера для опитування */
};
ioctl(drm_fd, DRM_IOCTL_MODE_GETFB2, &cmd);
```

#### Семантика полів структури `drm_mode_fb_cmd2` у виклику GETFB2

* `fb_id` (`[in]`): числовий ідентифікатор цільового кадрового буфера KMS.
* `width`, `height` (`[out]`): геометричні розміри кадрового буфера в пікселях.
* `pixel_format` (`[out]`): 32-бітний код DRM FourCC (наприклад, `DRM_FORMAT_NV12` або `DRM_FORMAT_ARGB8888`).
* `flags` (`[out]`): бітові прапорці конфігурації:
  * `DRM_MODE_FB_INTERLACED` (`0x01`): встановлено для черезрядкових буферів.
  * `DRM_MODE_FB_MODIFIERS` (`0x02`): сигналізує, що масив `modifier[]` містить дійсні явні 64-бітні модифікатори DRM.
* `handles[4]` (`[out]`): масив числових GEM-хендлів відповідних площин буфера у просторі імен викликаючого процесу.
* `pitches[4]` (`[out]`): крок рядка (stride) у байтах для кожної активної площини.
* `offsets[4]` (`[out]`): байтове зміщення площини від початку відповідного GEM-об'єкта.
* `modifier[4]` (`[out]`): 64-бітні модифікатори DRM для кожної площини. Якщо буфер було зареєстровано без явних модифікаторів (без прапорця `DRM_MODE_FB_MODIFIERS`), драйвер повертає значення `DRM_FORMAT_MOD_INVALID` або `DRM_FORMAT_MOD_LINEAR`.

#### Модель безпеки та розмежування прав доступу до GEM-хендлів

Для запобігання несанкціонованому перехопленню вмісту чужих вікон або робочого столу ядро Linux застосовує вибіркову фільтрацію полів `handles[]`:

1. **Привілейований процес (DRM Master або творець буфера):** якщо процес має статус DRM Master (`drmIsMaster()`, наприклад, активний віконний композитор Wayland/X11) або запитує буфер, створений у межах власного відкритого файлового дескриптора `drm_fd`, ядро створює нові GEM-хендли в таблиці дескрипторів процесу (`drm_gem_handle_create`) та заповнює масив `handles[]`.
2. **Непривілейований процес (сторонній клієнт / діагностична утиліта):** якщо сторонній процес викликає `GETFB2` для чужого `fb_id`, ядро **обнуляє всі елементи `handles[]`** (`handles[p] = 0`), проте **успішно повертає всі метадані** (`width`, `height`, `pixel_format`, `flags`, `pitches[]`, `offsets[]`, `modifier[]`). Це дозволяє системним моніторам (наприклад, утиліті `drm_info`) інспектувати геометрію та конфігурацію тайлінгу дисплейних площин без порушення ізоляції пам'яті процесів.

#### Алгоритм обробки виклику GETFB2 всередині ядра

1. Пошук об'єкта `struct drm_framebuffer` за переданим `fb_id` у внутрішній таблиці IDR пристрою. Якщо буфер не знайдено — повернення помилки `-ENOENT`.
2. Заповнення полів `width`, `height`, `pixel_format` (`fb->format->format`) та `flags` (`fb->flags`).
3. Для кожної активної площини `0 <= p < fb->format->num_planes`:
   * Призначення `pitches[p] = fb->pitches[p]`.
   * Призначення `offsets[p] = fb->offsets[p]`.
   * Призначення `modifier[p] = fb->modifier`.
   * Перевірка прав: якщо процес є майстром або власником буфера — виклик `drm_gem_handle_create(file_priv, fb->obj[p], &cmd->handles[p])`, інакше запис `cmd->handles[p] = 0`.
4. Обнулення невикористаних площин `fb->format->num_planes <= p < 4` у масивах `handles`, `pitches`, `offsets`, `modifier`.
5. Повернення успішного статусу `0`.

#### Коди помилок системного виклику GETFB2

* `-ENOENT`: кадровий буфер із зазначеним `fb_id` не існує або вже був видалений.
* `-EINVAL`: некоректні параметри або пошкоджений стан внутрішніх структур ядра.
* `-EOPNOTSUPP` / `-ENOTTY`: системний виклик `GETFB2` не підтримується драйвером або версією ядра (ядро старше за 5.7).
* `-ENOMEM`: вичерпано пам'ять ядра під час виділення записів у таблиці GEM-хендлів процесу.

Після завершення роботи з отриманими GEM-хендлами простір користувача зобов'язаний звільнити всі ненульові дескриптори `handles[p]` викликом `DRM_IOCTL_GEM_CLOSE`.

### Системні виклики PRIME: імпорт та експорт пам'яті dma-buf

Механізм PRIME забезпечує передачу буферів пам'яті між різними графічними процесорами, віконними композиторами та дисплейними контролерами через файлові дескриптори [dma-buf](root:sys-unix/dma-buf).

Взаємодія регулюється двома викликами `ioctl` зі структурою `struct drm_prime_handle`:

```
struct drm_prime_handle {
    uint32_t handle; /* GEM-хендл пам'яті */
    uint32_t flags;  /* Бітові прапорці */
    int32_t fd;      /* Файловий дескриптор dma-buf */
};
```

#### Експорт GEM-хендлу у dma-buf: `DRM_IOCTL_PRIME_HANDLE_TO_FD`

```
struct drm_prime_handle args = {
    .handle = gem_handle,
    .flags = DRM_CLOEXEC | DRM_RDWR,
    .fd = -1,
};
ioctl(drm_fd, DRM_IOCTL_PRIME_HANDLE_TO_FD, &args);
int dmabuf_fd = args.fd;
```

* **Прапорці `flags`:**
  * `DRM_CLOEXEC` (`0x02`): створює файловий дескриптор із прапорцем `O_CLOEXEC` (автоматичне закриття при викликах родини `execve`).
  * `DRM_RDWR` (`0x04`): надає дескриптору права на читання та запис.
* **Семантика:** ядро експортує драйверний GEM-об'єкт, створюючи новий анонімний файл `struct dma_buf`, та повертає файловий дескриптор процесу.

#### Імпорт dma-buf у GEM-хендл: `DRM_IOCTL_PRIME_FD_TO_HANDLE`

```
struct drm_prime_handle args = {
    .handle = 0,
    .flags = 0, /* Зарезервовано, повинно дорівнювати 0 */
    .fd = dmabuf_fd,
};
ioctl(drm_fd, DRM_IOCTL_PRIME_FD_TO_HANDLE, &args);
uint32_t gem_handle = args.handle;
```

* **Семантика та дедуплікація хендлів:** ядро імпортує `dma-buf` у простір імен GEM викликаючого процесу. Якщо той самий дескриптор `dma-buf` імпортується повторно у той самий відкритий файл DRM (`drm_fd`), ядро повертає **той самий числовий GEM-хендл**, збільшуючи внутрішній лічильник посилань на об'єкт.

#### Закриття хендлів: `DRM_IOCTL_GEM_CLOSE`

```
struct drm_gem_close {
    uint32_t handle; /* GEM-хендл для звільнення */
    uint32_t pad;
};
```

Після успішного виклику `DRM_IOCTL_MODE_ADDFB2` сам об'єкт кадрового буфера ядра утримує прямі посилання на пам'ять. Простір користувача зобов'язаний негайно закрити тимчасові GEM-хендли викликом `DRM_IOCTL_GEM_CLOSE`, інакше виникає витік у таблиці хендлів процесу ядра, що призводить до відмови наступних викликів із помилкою `-ENOSPC`.

### Синхронізація доступу процесора до пам'яті: `DMA_BUF_IOCTL_SYNC` та `struct dma_buf_sync`

Прямий доступ центрального процесора (CPU) до пам'яті буфера [dma-buf](root:sys-unix/dma-buf) через відображення `mmap()` вимагає явної синхронізації апаратних кешів CPU (L1/L2/L3) та очікування черг апаратного рендерингу GPU/VPU. Стандарт UAPI підсистеми DMA-BUF (`<linux/dma-buf.h>`) визначає системний виклик `DMA_BUF_IOCTL_SYNC`:

```
#define DMA_BUF_BASE 'b'
#define DMA_BUF_IOCTL_SYNC _IOW(DMA_BUF_BASE, 0, struct dma_buf_sync)

struct dma_buf_sync {
    uint64_t flags; /* Бітові прапорці конфігурації бар'єра синхронізації */
};
```

#### Реєстр бітових прапорців `flags` (`<linux/dma-buf.h>`)

| Прапорець | Числове значення | Семантика операції синхронізації |
| :--- | :--- | :--- |
| `DMA_BUF_SYNC_READ` | `1U << 0` (`0x01`) | Доступ процесора на читання пам'яті буфера |
| `DMA_BUF_SYNC_WRITE` | `2U << 0` (`0x02`) | Доступ процесора на запис у пам'ять буфера |
| `DMA_BUF_SYNC_RW` | `(1U << 0) \| (2U << 0)` (`0x03`) | Двонаправлений доступ процесора (читання та запис) |
| `DMA_BUF_SYNC_START` | `0U << 2` (`0x00`) | Початок критичної секції звернення процесора до пам'яті |
| `DMA_BUF_SYNC_END` | `1U << 2` (`0x04`) | Завершення критичної секції звернення процесора до пам'яті |
| `DMA_BUF_SYNC_VALID_FLAGS_MASK` | `0x07` (`RW \| END`) | Маска валідних прапорців UAPI (інші біти заборонено) |

#### Механізм кеш-когерентності та взаємодії з резервуванням DMA (`dma_resv`)

1. **Вхідний бар'єр читання (`DMA_BUF_SYNC_START | DMA_BUF_SYNC_READ`):**
   * Ядро звертається до об'єкта резервування `struct dma_resv` буфера `dma-buf`.
   * Блокує виконання процесу (виклик `dma_resv_wait_timeout`), очікуючи сигналізації всіх активних ексклюзивних апаратних парканів запису (`DMA_RESV_USAGE_WRITE`), встановлених GPU чи відеодекодером.
   * Виконує інвалідацію кеш-ліній процесора (CPU Cache Invalidation через виклик `dma_sync_sg_for_cpu`), гарантуючи, що подальші інструкції читання процесора завантажать свіжі байти з фізичної пам'яті або VRAM, а не застарілі дані з кешу.
2. **Вхідний бар'єр запису (`DMA_BUF_SYNC_START | DMA_BUF_SYNC_WRITE`):**
   * Ядро очікує завершення всіх активних парканів як читання (`DMA_RESV_USAGE_READ`), так і запису (`DMA_RESV_USAGE_WRITE`). Це гарантує, що процесор не перетре пам'ять, яку в цей момент сканує дисплейний контролер або читає текстурний блок GPU.
   * Підготовляє сторінки пам'яті до модифікації процесором.
3. **Вихідний бар'єр запису (`DMA_BUF_SYNC_END | DMA_BUF_SYNC_WRITE`):**
   * Виконує примусове вимивання брудних кеш-ліній процесора (CPU Cache Flush / Clean через виклик `dma_sync_sg_for_device` або апаратні інструкції на кшталт `clflushopt` / `dc cvac`).
   * Забезпечує, щоб наступні операції DMA-вибірки апаратного дисплейного контролера (KMS Scanout) чи GPU зчитували оновлені процесором пікселі без розривів та спотворень зображення.
4. **Вихідний бар'єр читання (`DMA_BUF_SYNC_END | DMA_BUF_SYNC_READ`):**
   * Завершує сеанс читання, відновлюючи статус володіння пам'яттю апаратним пристроєм.

#### Нормативне правило парних бар'єрів (Bracket Rule)

Будь-яка операція читання чи запису в область пам'яті, отриману через `mmap(dmabuf_fd, ...)`, зобов'язана виконуватися суворо всередині пари викликів `DMA_BUF_SYNC_START` та `DMA_BUF_SYNC_END`:

```
/* 1. Початок читання/запису */
struct dma_buf_sync sync_start = {
    .flags = DMA_BUF_SYNC_START | DMA_BUF_SYNC_RW,
};
while (ioctl(dmabuf_fd, DMA_BUF_IOCTL_SYNC, &sync_start) < 0) {
    if (errno == EINTR) continue; /* Повтор при перериванні сигналом */
    break;
}

/* 2. Безпосередня модифікація пікселів у пам'яті процесором */
render_software_fallback(mapped_ptr, width, height, stride);

/* 3. Фіналізація запису та скидання кешів у фізичну пам'ять */
struct dma_buf_sync sync_end = {
    .flags = DMA_BUF_SYNC_END | DMA_BUF_SYNC_RW,
};
while (ioctl(dmabuf_fd, DMA_BUF_IOCTL_SYNC, &sync_end) < 0) {
    if (errno == EINTR) continue;
    break;
}
```

#### Коди помилок системного виклику DMA_BUF_IOCTL_SYNC

* `-EINVAL`: у полі `flags` встановлено заборонені біти (поза маскою `DMA_BUF_SYNC_VALID_FLAGS_MASK`), або не вказано жодного напрямку доступу (`READ` чи `WRITE`).
* `-EBADF`: переданий файловий дескриптор є закритим або некоректним.
* `-ENOTTY` / `-EINVAL`: файловий дескриптор не є об'єктом ядра `dma-buf`.
* `-EINTR` / `-ERESTARTSYS`: очікування апаратних парканів GPU у просторі ядра було перервано доставкою сигналу процесу. Простір користувача зобов'язаний повторити виклик `ioctl` при отриманні `errno == EINTR`.
* `-ETIMEDOUT`: вичерпано граничний час очікування готовності апаратного пристрою.

### Інспекція та явна синхронізація DMA-BUF: `sync_file`, `SYNC_IOC_FILE_INFO` та міст до DRM Syncobj

Підсистема явної асинхронної синхронізації Linux базується на анонімних файлових дескрипторах `sync_file` (`<linux/sync_file.h>`), які інкапсулюють один або кілька ядерних парканів `struct dma_fence`. Вони використовуються для неблокуючого моніторингу готовності буферів у подієвих циклах `poll()`/`epoll()`, передачі точок завершення рендерингу між процесами (Wayland Presentation Time, Vulkan semaphores `VK_KHR_external_semaphore_fd`) та діагностики затримок конвеєра.

#### Структури даних інспекції парканів (`<linux/sync_file.h>`)

```
#define SYNC_IOC_MAGIC '>'
#define SYNC_IOC_FILE_INFO _IOWR(SYNC_IOC_MAGIC, 4, struct sync_file_info)
#define SYNC_IOC_MERGE     _IOWR(SYNC_IOC_MAGIC, 3, struct sync_merge_data)

struct sync_file_info {
    char     name[32];         /* [out] Символьне ім'я sync_file або таймлайну */
    int32_t  status;           /* [out] Стан готовності: 0 = активний, 1 = сигналізований, < 0 = помилка */
    uint32_t flags;            /* [out] Прапорці sync_file */
    uint32_t num_fences;       /* [in/out] Вхід: ємність буфера; Вихід: реальна кількість парканів */
    uint32_t pad;              /* Вирівнювання структури (повинно дорівнювати 0) */
    uint64_t sync_fence_info;  /* [in] Покажчик (uintptr_t) на масив struct sync_fence_info[] */
};

struct sync_fence_info {
    char     obj_name[32];     /* [out] Ім'я контексту/таймлайну (наприклад, "i915_render", "gfx_0.0") */
    char     driver_name[32];  /* [out] Назва драйвера ядра (наприклад, "i915", "amdgpu", "panfrost") */
    int32_t  status;           /* [out] Стан паркана: 0 = pending, 1 = signaled, < 0 = код помилки (-EIO) */
    uint32_t flags;            /* [out] Прапорці індивідуального паркана dma-fence */
    uint64_t timestamp_ns;     /* [out] Монотонна мітка часу спрацювання (CLOCK_MONOTONIC, наносекунди) */
};
```

#### Двоетапний протокол опитування `SYNC_IOC_FILE_INFO`

1. **Етап 1 (Визначення кількості парканів та глобального статусу):**
   Програма ініціалізує структуру нульовим розміром масиву `num_fences = 0` та нульовим покажчиком `sync_fence_info = 0`:
   ```
   struct sync_file_info info = {0};
   ioctl(sync_fd, SYNC_IOC_FILE_INFO, &info);
   ```
   Ядро заповнює загальний статус `info.status` (`1` — усі внутрішні операції завершено, `0` — триває апаратна обробка, від'ємне значення — сталася апаратна помилка або зависання GPU), записує символьне ім'я `info.name` та повертає в `info.num_fences` точну кількість складових парканів.
2. **Етап 2 (Отримання детальної інформації про кожен складовий паркан):**
   Програма виділяє масив структур `struct sync_fence_info` розміром `info.num_fences`, записує його адресу в поле `sync_fence_info` і повторно викликає `SYNC_IOC_FILE_INFO`:
   ```
   struct sync_fence_info *fences = calloc(info.num_fences, sizeof(struct sync_fence_info));
   info.sync_fence_info = (uint64_t)(uintptr_t)fences;
   ioctl(sync_fd, SYNC_IOC_FILE_INFO, &info);
   ```
   Ядро копіює дані кожного паркана: назву апаратного конвеєра (`obj_name`), драйвер (`driver_name`), стан (`status`) та точну системну мітку часу спрацювання переривання апаратного вузла `timestamp_ns` за годинником `CLOCK_MONOTONIC`.

#### Об'єднання точок синхронізації: системний виклик `SYNC_IOC_MERGE`

Системний виклик `SYNC_IOC_MERGE` об'єднує два незалежні дескриптори `sync_file` у єдиний результуючий `sync_file`:

```
struct sync_merge_data {
    char     name[32]; /* [in] Символьна назва об'єднаного sync_file */
    int32_t  fd2;      /* [in] Файловий дескриптор другого sync_file */
    int32_t  fence;    /* [out] Створений файловий дескриптор об'єднаного sync_file */
    uint32_t flags;    /* Зарезервовано */
    uint32_t pad;
};
```

Результуючий дескриптор сигналізує готовність тоді й лише тоді, коли завершуються апаратні операції **обох** вихідних парканів.

#### Міст між об'єктами DRM Syncobj та дескрипторами `sync_file`

Підсистема DRM UAPI (`<drm/drm.h>`) надає механізм двосторонньої конвертації між точками синхронізації DRM Syncobj та дескрипторами `sync_file`:

```
struct drm_syncobj_handle {
    uint32_t handle; /* GEM/KMS Syncobj хендл */
    uint32_t flags;  /* Прапорці операції конвертації */
    int32_t  fd;      /* Файловий дескриптор sync_file */
    uint32_t pad;
};
```

* **Експорт Syncobj у `sync_file` (`DRM_IOCTL_SYNCOBJ_HANDLE_TO_FD`):**
  Встановлення прапорця `DRM_SYNCOBJ_HANDLE_TO_FD_FLAGS_EXPORT_SYNC_FILE` (`1U << 0`) витягує поточний корисний стан паркана `dma_fence` із DRM Syncobj і створює новий дескриптор `sync_file`.
* **Імпорт `sync_file` у Syncobj (`DRM_IOCTL_SYNCOBJ_FD_TO_HANDLE`):**
  Встановлення прапорця `DRM_SYNCOBJ_FD_TO_HANDLE_FLAGS_IMPORT_SYNC_FILE` (`1U << 0`) встановлює паркан із дескриптора `sync_file` у зазначений об'єкт DRM Syncobj.
* **Таймлайн-синхронізація (Timeline Syncobj):**
  Розширення таймлайнів дозволяє оперувати 64-бітними монотонними лічильниками точок синхронізації через системні виклики `DRM_IOCTL_SYNCOBJ_TIMELINE_WAIT` (структура `struct drm_syncobj_timeline_wait`), `DRM_IOCTL_SYNCOBJ_TIMELINE_SIGNAL` (структура `struct drm_syncobj_timeline_array`) та `DRM_IOCTL_SYNCOBJ_TRANSFER` (структура `struct drm_syncobj_transfer`), транслюючи конкретні точки монотонної шкали у дескриптори `sync_file`.

#### Коди помилок операцій із sync_file

* `-EBADF`: передано недійсний або закритий файловий дескриптор.
* `-ENOTTY` / `-EINVAL`: дескриптор не підтримує інтерфейс `sync_file`.
* `-EFAULT`: адреса покажчика `sync_fence_info` вказує за межі доступного адресного простору процесу.
* `-ENOMEM`: вичерпано пам'ять ядра для створення нових структур парканів або дескрипторів файлів.

### Властивість площини `IN_FORMATS` та бінарний блоб

Кожна апаратна площина KMS (`struct drm_plane`) публікує незмінну властивість із назвою `IN_FORMATS`. Значення властивості містить числовий ID блобу `struct drm_format_modifier_blob`, що описує підтримувані пари «формат-модифікатор»:

```
struct drm_format_modifier_blob {
    uint32_t version;          /* Версія формату блобу (поточна версія: 1) */
    uint32_t flags;            /* Зарезервовано */
    uint32_t count_formats;    /* Кількість елементів у масиві formats[] */
    uint32_t formats_offset;   /* Зміщення в байтах від початку структури до uint32_t formats[] */
    uint32_t count_modifiers;  /* Кількість елементів у масиві modifiers[] */
    uint32_t modifiers_offset; /* Зміщення в байтах до struct drm_format_modifier modifiers[] */
};

struct drm_format_modifier {
    uint64_t formats;          /* 64-бітна маска індексів форматів */
    uint32_t offset;           /* Зміщення вікна маски форматів */
    uint32_t pad;              /* Вирівнювання структури */
    uint64_t modifier;         /* 64-бітне значення модифікатора */
};
```

#### Алгоритм перевірки сумісності у просторі користувача

1. Програма зчитує покажчик на блоб через `drmModeGetPropertyBlob()`.
2. Отримує масив підтримуваних FourCC форматів:
   ```
   const uint32_t *formats = (const uint32_t *)((const char *)blob + blob->formats_offset);
   ```
3. Знаходить індекс `idx` шуканого формату (наприклад, `DRM_FORMAT_XRGB8888`) у діапазоні `0 <= idx < blob->count_formats`.
4. Перебирає масив модифікаторів `mods`:
   ```
   const struct drm_format_modifier *mods = 
       (const struct drm_format_modifier *)((const char *)blob + blob->modifiers_offset);
   ```
5. Модифікатор `mods[m].modifier` підтримується для формату `formats[idx]` тоді й лише тоді, коли:
   `idx >= mods[m].offset && idx < (mods[m].offset + 64) && (mods[m].formats & (1ULL << (idx - mods[m].offset))) != 0`

## 5. Інтерфейс бібліотеки Generic Buffer Management (GBM)

Бібліотека `libgbm` (частина проєкту Mesa) надає інтерфейс виділення графічних буферів із точним зазначенням списку дозволених модифікаторів розкладки:

```
/* Створення буфера із переліком дозволених модифікаторів */
struct gbm_bo *gbm_bo_create_with_modifiers2(
    struct gbm_device *gbm,
    uint32_t width,
    uint32_t height,
    uint32_t format,
    const uint64_t *modifiers,
    const unsigned int count,
    uint32_t flags
);

/* Отримання остаточно обраного драйвером 64-бітного модифікатора */
uint64_t gbm_bo_get_modifier(struct gbm_bo *bo);

/* Отримання кількості фізичних площин буфера (включно з допоміжними площинами CCS/DCC) */
int gbm_bo_get_plane_count(struct gbm_bo *bo);

/* Експорт файлового дескриптора dma-buf для конкретної площини */
int gbm_bo_get_fd_for_plane(struct gbm_bo *bo, int plane);

/* Отримання кроку рядка в байтах для площини */
uint32_t gbm_bo_get_stride_for_plane(struct gbm_bo *bo, int plane);

/* Отримання байтового зміщення площини від початку буфера */
uint32_t gbm_bo_get_offset(struct gbm_bo *bo, int plane);

/* Звільнення об'єкта буфера GBM */
void gbm_bo_destroy(struct gbm_bo *bo);
```

### Прапорці призначення буфера `flags` (`enum gbm_bo_flags`)

* `GBM_BO_USE_SCANOUT` (`1U << 0`): буфер виділяється для прямого виведення на дисплейну площину KMS. Драйвер забороняє розкладки, які не підтримуються блоком сканування.
* `GBM_BO_USE_RENDERING` (`1U << 2`): буфер призначено для 3D-рендерингу через OpenGL, Vulkan або EGL.
* `GBM_BO_USE_WRITE` (`1U << 3`): буфер буде записуватися центральним процесором.
* `GBM_BO_USE_LINEAR` (`1U << 4`): примусове виділення лінійної пам'яті (`DRM_FORMAT_MOD_LINEAR`).
* `GBM_BO_USE_TEXTURING` (`1U << 5`): буфер призначено для читання як текстури в шейдерах.
* `GBM_BO_USE_PROTECTED` (`1U << 6`): захищена пам'ять (контент DRM / HDCP).
* `GBM_BO_USE_FRONT_RENDERING` (`1U << 7`): прямий рендеринг у передній буфер без подвійної буферизації.

## 6. Специфікація розширень Wayland: `zwp_linux_dmabuf_v1` та `zwp_linux_dmabuf_feedback_v1`

Протокол Wayland стандартизує передачу буферів [dma-buf](root:sys-unix/dma-buf) та узгодження модифікаторів за допомогою інтерфейсів `zwp_linux_dmabuf_v1` (версії 1–5, де версія 4 впровадила об'єкти Feedback).

### Інтерфейс фабрики буферів `zwp_linux_dmabuf_v1`

Головний глобальний інтерфейс композитора надає методи створення тимчасових параметрів виділення буфера та підписки на зворотний зв'язок:

#### Запити (Requests)

* `destroy()`: знищує проксі-об'єкт `zwp_linux_dmabuf_v1`.
* `create_params(params_id)`: створює об'єкт `zwp_linux_buffer_params_v1` для збирання файлових дескрипторів площин перед створенням `wl_buffer`.
* `get_default_feedback(id)` (v4+): створює об'єкт `zwp_linux_dmabuf_feedback_v1`, що повертає глобальні рекомендації композитора для фонових та звичайних поверхонь.
* `get_surface_feedback(id, surface)` (v4+): створює об'єкт `zwp_linux_dmabuf_feedback_v1`, прив'язаний до конкретної поверхні `wl_surface`. Композитор динамічно оновлює рекомендації траншів залежно від того, чи відображається поверхня на інтегрованому дисплеї, дискретному GPU, чи потрапляє у прямий апаратний скан-аут (Zero-Copy Direct Scanout).

### Складання кадру: `zwp_linux_buffer_params_v1`

Об'єкт накопичує площини кадру перед перетворенням на `wl_buffer`:

#### Запити `zwp_linux_buffer_params_v1`

* `add(fd, plane_idx, offset, stride, modifier_hi, modifier_lo)`:
  * `fd`: файловий дескриптор `dma-buf` площини.
  * `plane_idx`: індекс площини (`0 <= plane_idx < 4`).
  * `offset`: зміщення початку площини у байтах від початку буфера `dma-buf`.
  * `stride`: крок рядка площини у байтах.
  * `modifier_hi`: старші 32 біти 64-бітного модифікатора (`modifier >> 32`).
  * `modifier_lo`: молодші 32 біти модифікатора (`modifier & 0xffffffff`).
* `create(width, height, format, flags)`: асинхронний запит на створення `wl_buffer`. Композитор відповідає подією `created` або `failed`.
* `create_immed(buffer_id, width, height, format, flags)`: синхронний запит (створює `wl_buffer` негайно). Якщо параметри некоректні, композитор генерує фатальну помилку протоколу.
* `destroy()`: звільняє об'єкт параметрів.

#### Прапорці конфігурації `flags` (`enum zwp_linux_buffer_params_v1_flags`)

* `ZWP_LINUX_BUFFER_PARAMS_V1_FLAGS_Y_INVERT` (`0x01`): буфер має інвертовану вісь Y (початок координат у лівому нижньому куті, характерно для класичного OpenGL).
* `ZWP_LINUX_BUFFER_PARAMS_V1_FLAGS_INTERLACED` (`0x02`): черезрядковий відеокадр.
* `ZWP_LINUX_BUFFER_PARAMS_V1_FLAGS_BOTTOM_FIRST` (`0x04`): нижнє напівполе сканується першим.

### Інтерфейс зворотного зв'язку `zwp_linux_dmabuf_feedback_v1`

Об'єкт зворотного зв'язку передає клієнту таблицю форматів та впорядкований набір траншів (Tranches).

#### Послідовність подій протоколу

1. **`format_table(fd, size)`:**
   Передає файловий дескриптор спільної пам'яті (shm memfd / `mmap()`) розміром `size` байтів. Таблиця містить неперервний масив записів `struct zwp_linux_dmabuf_feedback_v1_format_table_entry`:
   ```
   struct zwp_linux_dmabuf_feedback_v1_format_table_entry {
       uint32_t format;    /* 32-бітний код DRM FourCC (Little-Endian) */
       uint32_t padding;   /* 32 біти вирівнювання (повинно дорівнювати 0) */
       uint64_t modifier;  /* 64-бітний DRM Format Modifier */
   };
   ```
   Кількість записів у таблиці обчислюється як `size / sizeof(struct zwp_linux_dmabuf_feedback_v1_format_table_entry)`.
2. **`main_device(device)`:**
   Передає 8 байтів, що кодують системний `dev_t` ідентифікатор головного пристрою рендерингу (мажорний і мінорний номери вузла `/dev/dri/renderD*`). Клієнт зобов'язаний відкрити саме цей GPU для виділення спільної відеопам'яті.
3. **`tranche_target_device(device)`:**
   Вказує `dev_t` ідентифікатор цільового пристрою, для якого скомпільовано наступний транш пріоритетів (наприклад, дисплейний вузол KMS `/dev/dri/card0`).
4. **`tranche_flags(flags)`:**
   Бітові прапорці поточного траншу:
   * `ZWP_LINUX_DMABUF_FEEDBACK_V1_TRANCHE_FLAGS_SCANOUT` (`0x01`): транш містить модифікатори, що гарантують пряме апаратне виведення дисплейною площиною KMS (Direct Scanout) без проміжного композитингу. Клієнти віддають перевагу цьому траншу для повноекранних ігор та медіаплеєрів.
5. **`tranche_formats(indices)`:**
   Передає масив 16-бітних беззнакових цілих чисел `uint16_t[]`, кожне з яких є індексом у глобальній таблиці `format_table`. Індекси розташовані у порядку суворого спадання пріоритету: модифікатор під індексом 0 є найефективнішим (наприклад, стиснений тайл Tile4 / AFBC), а лінійний резервний варіант стоїть останнім.
6. **`tranche_done()`:**
   Сигналізує про завершення опису одного траншу.
7. **`done()`:**
   Фіналізує передачу пакета траншів. Усі отримані транші стають атомарно активними.

## 7. Специфікація розширень EGL та Vulkan для роботи з модифікаторами

### 7.1 EGL: `EGL_EXT_image_dma_buf_import` та `EGL_EXT_image_dma_buf_import_modifiers`

Розширення EGL стандартизують імпорт дескрипторів `dma-buf` з явними 64-бітними модифікаторами DRM у дескриптори `EGLImageKHR` для використання в контекстах OpenGL та OpenGL ES.

#### Опитування підтримуваних форматів та модифікаторів драйвера

```
/* Отримання списку підтримуваних DRM FourCC форматів */
EGLBoolean eglQueryDmaBufFormatsEXT(
    EGLDisplay dpy,
    EGLint max_formats,
    EGLint *formats,
    EGLint *num_formats
);

/* Отримання списку модифікаторів для заданого FourCC формату */
EGLBoolean eglQueryDmaBufModifiersEXT(
    EGLDisplay dpy,
    EGLint format,
    EGLint max_modifiers,
    EGLuint64KHR *modifiers,
    EGLBoolean *external_only,
    EGLint *num_modifiers
);
```

* `external_only`: вихідний масив булевих прапорців. Якщо для модифікатора прапорець встановлено в `EGL_TRUE`, результуюче зображення `EGLImage` може бути зв'язане лише з текстурним таргетом `GL_TEXTURE_EXTERNAL_OES` (заборонено використання як `GL_TEXTURE_2D` або приєднання до фреймбуфера `GL_COLOR_ATTACHMENT0`).

#### Створення `EGLImageKHR` із дескрипторів площин dma-buf

```
EGLImageKHR eglCreateImageKHR(
    EGLDisplay dpy,
    EGLContext ctx,          /* Повинно дорівнювати EGL_NO_CONTEXT */
    EGLenum target,          /* Повинно дорівнювати EGL_LINUX_DMA_BUF_EXT */
    EGLClientBuffer buffer,  /* Повинно дорівнювати NULL */
    const EGLint *attrib_list
);
```

#### Реєстр атрибутів списку `attrib_list`

Кожен атрибут складається з пари `(ключ, значення)`, а список завершується маркером `EGL_NONE`:

| Атрибут EGL | Тип значення | Опис семантики |
| :--- | :--- | :--- |
| `EGL_WIDTH` | `EGLint` | Ширина зображення в пікселях (обов'язковий) |
| `EGL_HEIGHT` | `EGLint` | Висота зображення в пікселях (обов'язковий) |
| `EGL_LINUX_DRM_FOURCC_EXT` | `EGLint` | 32-бітний код DRM FourCC (обов'язковий) |
| `EGL_DMA_BUF_PLANE0_FD_EXT` | `EGLint` | Файловий дескриптор dma-buf площини 0 (обов'язковий) |
| `EGL_DMA_BUF_PLANE0_OFFSET_EXT` | `EGLint` | Зміщення площини 0 у байтах від початку dma-buf |
| `EGL_DMA_BUF_PLANE0_PITCH_EXT` | `EGLint` | Крок рядка (stride) площини 0 у байтах (обов'язковий) |
| `EGL_DMA_BUF_PLANE0_MODIFIER_LO_EXT` | `EGLint` | Молодші 32 біти модифікатора площини 0 |
| `EGL_DMA_BUF_PLANE0_MODIFIER_HI_EXT` | `EGLint` | Старші 32 біти модифікатора площини 0 |
| `EGL_DMA_BUF_PLANE1_FD_EXT` | `EGLint` | Дескриптор dma-buf площини 1 (для багатоплощинних форматів) |
| `EGL_DMA_BUF_PLANE1_OFFSET_EXT` | `EGLint` | Зміщення площини 1 у байтах |
| `EGL_DMA_BUF_PLANE1_PITCH_EXT` | `EGLint` | Крок рядка площини 1 у байтах |
| `EGL_DMA_BUF_PLANE1_MODIFIER_LO_EXT` | `EGLint` | Молодші 32 біти модифікатора площини 1 |
| `EGL_DMA_BUF_PLANE1_MODIFIER_HI_EXT` | `EGLint` | Старші 32 біти модифікатора площини 1 |
| `EGL_DMA_BUF_PLANE2_*` | `EGLint` | Параметри площини 2 (аналогічно площині 1) |
| `EGL_DMA_BUF_PLANE3_*` | `EGLint` | Параметри площини 3 (аналогічно площині 1) |
| `EGL_YUV_COLOR_SPACE_HINT_EXT` | `EGLint` | Колірний простір: `EGL_ITU_REC601_EXT`, `EGL_ITU_REC709_EXT`, `EGL_ITU_REC2020_EXT` |
| `EGL_SAMPLE_RANGE_HINT_EXT` | `EGLint` | Діапазон квантування: `EGL_YUV_FULL_RANGE_EXT` (0..255) або `EGL_YUV_NARROW_RANGE_EXT` (16..235) |
| `EGL_YUV_CHROMA_HORIZONTAL_SITING_HINT_EXT` | `EGLint` | Горизонтальна прив'язка колірності: `EGL_YUV_CHROMA_SITING_0_EXT` (cosited) або `EGL_YUV_CHROMA_SITING_0_5_EXT` |
| `EGL_YUV_CHROMA_VERTICAL_SITING_HINT_EXT` | `EGLint` | Вертикальна прив'язка колірності: `EGL_YUV_CHROMA_SITING_0_EXT` або `EGL_YUV_CHROMA_SITING_0_5_EXT` |

#### Коди помилок `eglGetError()`

* `EGL_BAD_ATTRIBUTE`: некоректний або невідомий атрибут; відсутність обов'язкових полів `EGL_WIDTH`, `EGL_HEIGHT`, `EGL_LINUX_DRM_FOURCC_EXT`, `PLANE0_FD` або `PLANE0_PITCH`.
* `EGL_BAD_MATCH`: конфлікт між модифікатором та геометрією буфера; несумісні прапорці для різних площин одного кадру.
* `EGL_BAD_PARAMETER`: комбінація FourCC та модифікатора не підтримується драйвером GPU.
* `EGL_BAD_ALLOC`: вичерпано ресурси пам'яті GPU або системні дескриптори.

### 7.2 Vulkan: Розширення `VK_EXT_image_drm_format_modifier`

Розширення Vulkan `VK_EXT_image_drm_format_modifier` надає низькорівневий інтерфейс для контролю над DRM-модифікаторами під час створення об'єктів `VkImage` та експорту/імпорту пам'яті `VkDeviceMemory`.

#### Запит властивостей модифікаторів фізичного пристрою

Опитування виконується через ланцюжок `pNext` виклику `vkGetPhysicalDeviceFormatProperties2()`:

```
typedef struct VkDrmFormatModifierPropertiesListEXT {
    VkStructureType                  sType; /* VK_STRUCTURE_TYPE_DRM_FORMAT_MODIFIER_PROPERTIES_LIST_EXT */
    void*                            pNext;
    uint32_t                         drmFormatModifierCount;
    VkDrmFormatModifierPropertiesEXT* pDrmFormatModifierProperties;
} VkDrmFormatModifierPropertiesListEXT;

typedef struct VkDrmFormatModifierPropertiesEXT {
    uint64_t                drmFormatModifier;
    uint32_t                drmFormatModifierPlaneCount;
    VkFormatFeatureFlags    drmFormatModifierTilingFeatures;
} VkDrmFormatModifierPropertiesEXT;
```

* `drmFormatModifier`: 64-бітний числовий модифікатор DRM.
* `drmFormatModifierPlaneCount`: кількість фізичних площин пам'яті, які цей модифікатор створює для обраного `VkFormat` (включно з допоміжними площинами стиснення CCS/DCC).
* `drmFormatModifierTilingFeatures`: бітова маска підтримуваних операцій конвеєра:
  * `VK_FORMAT_FEATURE_SAMPLED_IMAGE_BIT`: читання у шейдерах як текстури.
  * `VK_FORMAT_FEATURE_STORAGE_IMAGE_BIT`: довільний запис/читання в обчислювальних шейдерах (Compute Shaders).
  * `VK_FORMAT_FEATURE_COLOR_ATTACHMENT_BIT`: рендеринг у буфер як фреймбуфер.
  * `VK_FORMAT_FEATURE_COLOR_ATTACHMENT_BLEND_BIT`: апаратне змішування альфа-каналу (Blending).
  * `VK_FORMAT_FEATURE_TRANSFER_SRC_BIT` / `TRANSFER_DST_BIT`: операції копіювання `vkCmdCopyImage`.

#### Створення `VkImage` з модифікатором розкладки

Під час створення зображення поле `VkImageCreateInfo::tiling` встановлюється у значення:

```
tiling = VK_IMAGE_TILING_DRM_FORMAT_MODIFIER_EXT;
```

У ланцюжок `pNext` структури `VkImageCreateInfo` передається одна з двох взаємовиключних структур:

##### 1. Автоматичний вибір драйвером зі списку кандидатів: `VkImageDrmFormatModifierListCreateInfoEXT`

Застосовується виробником буфера (наприклад, віконним клієнтом), коли точна розкладка обирається драйвером із набору, узгодженого з дисплейним сервером:

```
typedef struct VkImageDrmFormatModifierListCreateInfoEXT {
    VkStructureType    sType; /* VK_STRUCTURE_TYPE_IMAGE_DRM_FORMAT_MODIFIER_LIST_CREATE_INFO_EXT */
    const void*        pNext;
    uint32_t           drmFormatModifierCount;
    const uint64_t*    pDrmFormatModifiers;
} VkImageDrmFormatModifierListCreateInfoEXT;
```

##### 2. Явне задання розкладки площин: `VkImageDrmFormatModifierExplicitCreateInfoEXT`

Застосовується споживачем буфера під час імпорту вже створеного зовнішнього дескриптора `dma-buf` із фіксованою пам'яттю та кроками рядків:

```
typedef struct VkImageDrmFormatModifierExplicitCreateInfoEXT {
    VkStructureType                sType; /* VK_STRUCTURE_TYPE_IMAGE_DRM_FORMAT_MODIFIER_EXPLICIT_CREATE_INFO_EXT */
    const void*                    pNext;
    uint64_t                       drmFormatModifier;
    uint32_t                       drmFormatModifierPlaneCount;
    const VkSubresourceLayout*     pPlaneLayouts;
} VkImageDrmFormatModifierExplicitCreateInfoEXT;
```

#### Структура геометрії площини `VkSubresourceLayout`

```
typedef struct VkSubresourceLayout {
    VkDeviceSize    offset;      /* Зміщення початку площини у байтах від початку буфера */
    VkDeviceSize    size;        /* Загальний розмір площини у байтах */
    VkDeviceSize    rowPitch;    /* Крок рядка площини (stride) у байтах */
    VkDeviceSize    arrayPitch;  /* Крок шару масиву зображення у байтах */
    VkDeviceSize    depthPitch;  /* Крок по глибині для 3D-зображень у байтах */
} VkSubresourceLayout;
```

#### Отримання обраного модифікатора та розкладки створеного `VkImage`

Після створення зображення через `VkImageDrmFormatModifierListCreateInfoEXT` застосунок зчитує призначений драйвером модифікатор та точні параметри площин:

```
/* 1. Отримання 64-бітного модифікатора */
VkImageDrmFormatModifierPropertiesEXT modProps = {
    .sType = VK_STRUCTURE_TYPE_IMAGE_DRM_FORMAT_MODIFIER_PROPERTIES_EXT,
    .pNext = NULL,
};
vkGetImageDrmFormatModifierPropertiesEXT(device, image, &modProps);
uint64_t chosenModifier = modProps.drmFormatModifier;

/* 2. Отримання кроку рядка та зміщення кожної площини */
VkImageSubresource subresource = {
    .aspectMask = VK_IMAGE_ASPECT_MEMORY_PLANE_0_BIT_EXT, /* Для площини 1: MEMORY_PLANE_1_BIT_EXT */
    .mipLevel = 0,
    .arrayLayer = 0,
};
VkSubresourceLayout layout;
vkGetImageSubresourceLayout(device, image, &subresource, &layout);
```

* `aspectMask` для модифікаторів приймає нормативні константи:
  * `VK_IMAGE_ASPECT_MEMORY_PLANE_0_BIT_EXT`
  * `VK_IMAGE_ASPECT_MEMORY_PLANE_1_BIT_EXT`
  * `VK_IMAGE_ASPECT_MEMORY_PLANE_2_BIT_EXT`
  * `VK_IMAGE_ASPECT_MEMORY_PLANE_3_BIT_EXT`

#### Імпорт та експорт пам'яті dma-buf у Vulkan

Зв'язування виділеного файлового дескриптора `dma-buf` із пам'яттю `VkDeviceMemory` виконується через розширення `VK_KHR_external_memory_fd`:

```
VkImportMemoryFdInfoKHR importInfo = {
    .sType = VK_STRUCTURE_TYPE_IMPORT_MEMORY_FD_INFO_KHR,
    .pNext = NULL,
    .handleType = VK_EXTERNAL_MEMORY_HANDLE_TYPE_DMA_BUF_BIT_EXT,
    .fd = dmabuf_fd,
};

VkMemoryAllocateInfo allocInfo = {
    .sType = VK_STRUCTURE_TYPE_MEMORY_ALLOCATE_INFO,
    .pNext = &importInfo,
    .allocationSize = total_size,
    .memoryTypeIndex = memoryTypeIndex,
};

VkDeviceMemory memory;
vkAllocateMemory(device, &allocInfo, NULL, &memory);
vkBindImageMemory(device, image, memory, 0);
```
