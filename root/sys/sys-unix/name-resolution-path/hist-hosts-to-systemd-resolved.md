# 📜 Від HOSTS.TXT до systemd-resolved: еволюція розв'язання імен у Unix

У перші роки існування мережі ARPANET (на початку 1970-х років) проблеми розв'язання та маршрутизації доменних імен у сучасному розумінні не існувало. Усі вузли мережі вимірювалися десятками, а згодом сотнями машин. Для перетворення зрозумілих людям описових імен комп'ютерів на їхні двійкові мережеві адреси використовувався єдиний централізований текстовий файл під назвою `HOSTS.TXT`.

Цей файл централізовано вела служба Network Information Center у Стэнфордському дослідному інституті (SRI-NIC). Порядок оновлення був суворо адміністративним: системні адміністратори з усього світу раз на тиждень або два завантажували оновлену версію `HOSTS.TXT` через протокол FTP. Файл містив простий список рядків у форматі «IP-адреса — офіційне ім'я — псевдоніми (aliases)».

```text
# Фрагмент історичного HOSTS.TXT (SRI-NIC, 1980 рік)
10.0.0.51      SRI-NIC.ARPA NIC
10.2.0.71      MIT-MULTICS.ARPA MULTICS
```

Зі стрімким зростанням кількості під'єднаних комп'ютерів на початку 1980-х років централізована схема розвалилася через три фундаментальні обмеження:

1. **Трафік та мережеве навантаження:** Сервер SRI-NIC опинився під постійною виснажливою атакою запитів на завантаження файла `HOSTS.TXT`. Смуга пропускання мережевих каналів витрачалася не на корисні обчислення, а на постійну синхронізацію одного й того самого файла.
2. **Конфлікти імен та відсутність ієрархії:** Не існувало ієрархічної системи просторів імен. Якщо одна лабораторія називала свій сервер `GATEWAY`, інша не могла використовувати таке саме ім'я, що спричиняло постійні адміністративні суперечки.
3. **Затримка оновлення даних:** Додавання нового вузла або зміна IP-адреси вимагали днів або тижнів чекання, поки оновлений файл пройде нову ітерацію публікації та розповсюдження по всіх комп'ютерах мережі.

У 1983 році Пол Мокапетріс (Paul Mockapetris) запропонував принципово нову концепцію — Domain Name System (DNS), опис якої увійшов до документів RFC 882 та RFC 883 (згодом виправлених та деталізованих у RFC 1034 та RFC 1035). DNS замінила монолітну текстову базу даних на розподілену ієрархічну базу даних деревної структури. Замість того, щоб тримати всі імена світу в одному файлі, відповідальність була делегована авторитетним серверам доменних зон. Корінь мережі підтримував список авторитетних серверів для доменів верхнього рівня (`.com`, `.edu`, `.org`), а ті своєю чергою делегували повноваження конкретним організаціям.

Першою еталонною реалізацією DNS для операційних систем Unix стала програма BIND (Berkeley Internet Name Domain), розроблена у 1984 році студентами Каліфорнійського університету в Берклі. Демон `named` читав текстові конфігураційні файли зон та виконував рекурсивні мережеві запити. Для підтримки взаємодії C-бібліотека Unix отримала перші виклики системного розв'язання імен — `gethostbyname()` та `gethostbyaddr()`.

Однак у середині 1990-х років виникла нова проблема. Мережеві системи розросталися: крім традиційних локальних файлів `/etc/hosts` та мережевих DNS-запитів, з'явилися корпоративні каталоги імен — NIS (Network Information Service від Sun Microsystems), NIS+, а пізніше LDAP. Кожен розробник програмного забезпечення або системної бібліотеки зашивав порядок опитування локальних файлів та мережевих служб на етапі компіляції програми. Якщо додаток хотів шукати користувачів або хости спочатку в NIS, а потім у DNS, розробникам доводилося писати власні розгалужені умови безпосередньо в коді додатків.

Для вирішення цієї роздрібненості у 1994 році компанія Sun Microsystems випустила операційну систему SunOS 5.4 (Solaris 2.4), у якій дебютував механізм Name Service Switch (NSS). Замість жорстко зафіксованої у коді логіки C-бібліотека отримувала файл конфігурації `/etc/nsswitch.conf`. NSS дозволив динамічно завантажувати бібліотеки-плагіни (`libnss_*.so`) під час виконання програми за допомогою викликів `dlopen()` та `dlsym()`. Це відокремило логіку розв'язання імен від коду самих додатків.

У 1997 році проект GNU C Library (glibc) перейняв архітектуру NSS у версії glibc 2.0. Це зробило розв'язання імен у Linux повністю модульним: додавання нового джерела джерел (наприклад, mDNS для локальних мереж або розв'язання імен у контейнерах Docker/Podman) більше не вимагало перекомпліляції glibc чи системних додатків. Розробникам достатньо було написати новий shared-об'єкт `libnss_custom.so.2` і прописати його назву в `/etc/nsswitch.conf`.

З появою мобільних комп'ютерів, бездротових мереж Wi-Fi, VPN-тунелів та технологій контейнеризації на початку 2010-х років класична модель NSS + `/etc/resolv.conf` наразилася на нові системні виклики:

* **Відсутність системного кешування:** Традиційний розв'язувач glibc не кешував DNS-відповіді. Кожен виклик `getaddrinfo()` генерував новий мережевий UDP-пакет, що споживало батарею мобільних пристроїв та створювало зайве навантаження на мережу.
* **Багатоінтерфейсні конфігурації (Split-DNS):** Якщо ноутбук під'єднано до корпоративного VPN-тунелю (із власними внутрішніми DNS-серверами) та одночасно до публічної мережі Wi-Fi, стандартний файл `/etc/resolv.conf` не мав механізму для відправки запитів `.internal.corp` на VPN-інтерфейс, а решти запитів — на Wi-Fi роутер.
* **Динамічний churn конфігурації:** Мережеві демони (NetworkManager, systemd-networkd, dhclient) постійно переписували `/etc/resolv.conf`, створюючи гонки даних (race conditions) для процесів, що вже відкрили файл.

У 2014 році в рамках проекту systemd Леннарт Пьоттерінг (Lennart Poettering) та Кай Зіверс (Kay Sievers) представили сервіс `systemd-resolved`. Він об'єднав системне кешування, спліт-DNS маршрутизацію між мережевими інтерфейсами, підтримку DNSSEC, mDNS, LLMNR та DNS-over-TLS (DoT) у єдиному системному демоні.

Для сумісності з NSS `systemd-resolved` надав модуль `libnss_resolve.so.2`, який перехоплює запити `getaddrinfo()` через системну шину D-Bus, а для сумісності зі старими програмами піднімає локальний DNS-заглушку (stub resolver) на адресі `127.0.0.53:53`. Таким чином, шлях розв'язання імен у Linux пройшов повну еволюційну спіраль: від єдиного текстового файла `HOSTS.TXT` до складної асоціативної системи динамічних плагінів та шинних демонів.
