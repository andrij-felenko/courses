# 📋 Ядра процесора назовні: файли sysfs, виклики, утиліти, події

Тут зібрано весь контракт, яким система показує стан ядер процесора й дозволяє його міняти: чотири файли-маски й точний формат діапазонів у них, вимикач `cpuN/online` з повним переліком кодів помилок і умов, за яких кожен виникає, керування одночасною багатонитковістю, службові файли для покрокового проходу машиною станів, а далі — бібліотечні виклики, які на ці файли спираються, утиліти `lscpu` та `chcpu` й події udev із їхніми полями. Довідка потрібна тоді, коли код уже пишеться або скрипт уже падає, і треба точно знати, що прочитати, що записати й що означає те, що повернулося.

Усе нижче лежить під `/sys/devices/system/cpu/` — далі цей префікс скорочено до `…/` ([модель пристроїв у sysfs](topic:sys-unix/sysfs-device-model) — дерево, у якому кожен пристрій має теку, а кожна його властивість — файл).

## Карта інтерфейсу

| що треба | файл | доступ |
|---|---|---|
| номери, які взагалі колись можуть з'явитися | `…/possible` | читання |
| ядра процесора, фізично наявні зараз | `…/present` | читання |
| ядра процесора, що виконують код | `…/online` | читання |
| ядра процесора, вимкнені або відрізані межею збірки | `…/offline` | читання |
| стеля, зашита в збірку ядра системи (`NR_CPUS − 1`) | `…/kernel_max` | читання |
| увімкнути або вимкнути одне ядро процесора | `…/cpuN/online` | читання + запис |
| чи працює зараз одночасна багатонитковість | `…/smt/active` | читання |
| увімкнути, вимкнути або заборонити багатонитковість | `…/smt/control` | читання + запис |
| перелік зареєстрованих станів із номерами | `…/hotplug/states` | читання |
| у якому стані ядро процесора зараз | `…/cpuN/hotplug/state` | читання |
| до якого стану його вести | `…/cpuN/hotplug/target` | читання + запис |
| у якому стані навмисне зламати наступний перехід | `…/cpuN/hotplug/fail` | читання + запис |
| узяти ядро процесора з пулу гіпервізора (s390) | `…/cpuN/configure` | читання + запис |
| перешукати ядра процесора заново (s390) | `…/rescan` | запис |

Три останні групи існують не завжди. Тека `hotplug/` з'являється лише за `CONFIG_HOTPLUG_CPU`; `smt/` — лише там, де архітектура вміє керувати багатонитковістю; `configure` і `rescan` — це s390, де гіпервізор справді роздає й забирає ядра процесора.

## Чотири маски і формат діапазонів

Усі чотири файли віддають той самий формат — **список номерів за зростанням, суцільні відрізки згорнуто через дефіс, групи розділено комою, без пробілів, з переводом рядка в кінці**:

```
$ cat /sys/devices/system/cpu/possible
0-15
$ cat /sys/devices/system/cpu/present
0-15
$ cat /sys/devices/system/cpu/online
0-5,7-15
$ cat /sys/devices/system/cpu/offline
6
$ cat /sys/devices/system/cpu/kernel_max
8191
```

Одна пастка формату коштує більше за решту разом: **порожня маска — це порожній рядок, а не нуль**. Коли вимкнених ядер процесора немає, `cat …/offline` друкує самий лише перевід рядка. Розбирач, який очікує число, або впаде, або мовчки прочитає сміття; правильна поведінка — «нічого не прочитали, отже нуль».

Ці ж чотири маски рухають три параметри завантаження ([командний рядок ядра](topic:sys-unix/bootloader-and-cmdline) — рядок, який завантажувач передає ядру системи й з якого воно бере всі свої початкові рішення):

| параметр | що робить | яку маску міняє |
|---|---|---|
| `nr_cpus=n` | обмежує загальну кількість ядер процесора, яку ядро системи взагалі підтримуватиме | скорочує `possible` |
| `maxcpus=n` | піднімає на завантаженні лише перші `n` | лишає решту в `present`, але поза `online` — їх можна ввімкнути потім |
| `possible_cpus=n` | штучно роздуває `possible` наперед (лише x86 і s390) | збільшує `possible` понад `present` |

Різниця між першим і другим практична: після `nr_cpus=4` решти ядер процесора не існує для системи взагалі й підняти їх нічим, після `maxcpus=4` вони чекають у `present` і піднімаються звичайним записом у `cpuN/online`.

## `cpuN/online`: єдиний вимикач

```sh
echo 0 > /sys/devices/system/cpu/cpu6/online     # вимкнути
echo 1 > /sys/devices/system/cpu/cpu6/online     # увімкнути
```

Файл розбирає значення як логічне: приймає `0`/`1`, а також `n`/`y`, `off`/`on` у будь-якому регістрі. Читання дає `0` або `1`.

**Файлу може не бути зовсім.** Ядро системи створює `online` лише для тих ядер процесора, які позначені як придатні до вимикання. На типовому сучасному x86 нульове ядро процесора таким не позначене, тож у `cpu0/` цього файлу просто немає — і скрипт, який обходить усі `cpuN/online` циклом, мусить бути готовий до відсутності першого.

**Запис того, що вже є, — успіх без жодних дій.** Запис `1` в увімкнене ядро процесора повертає успіх, не викликає жодного колбека й не породжує події udev. Те саме симетрично для `0`.

Коди помилок запису:

| код | текст оболонки | що насправді сталося |
|---|---|---|
| `EPERM` | `Operation not permitted` | ядро системи вважає це ядро процесора непридатним до підняття. Найчастіша причина — вимкнена багатонитковість: піднімати сестринську нитку заборонено, доки `smt/control` не скаже `on` |
| `EBUSY` | `Device or resource busy` | ввімкнене ядро процесора лишилося одне; **або** гарячі зміни тимчасово заборонені зсередини (так робить код засинання на час переходу); **або** без цього ядра процесора решті не вистачить процесорного часу, обіцяного задачам класу дедлайну |
| `EINVAL` | `Invalid argument` | номера немає в `possible` чи в `present`; або записаний рядок узагалі не логічне значення |
| `EOPNOTSUPP` | `Operation not supported` | платформа не дозволяє вимикати ядра процесора в принципі. Так позначають себе гості Intel TDX: розбуджене методом ACPI MADT wakeup ядро процесора вимкнути назад технічно неможливо, і ядро системи відрізняє це від тимчасової невдачі окремим кодом |
| `EAGAIN` | `Resource temporarily unavailable` | перехід зламано навмисне через `cpuN/hotplug/fail` — про це нижче |

Розрізняти `EBUSY` й `EOPNOTSUPP` варто саме тому, що вони кажуть протилежне: перший означає «спробуйте пізніше», другий — «не пробуйте ніколи».

## Одночасна багатонитковість: `smt/control` і `smt/active`

Два файли роблять різні речі, і плутати їх не варто: `control` — це **намір**, `active` — це **факт**.

`…/smt/active` доступний лише для читання й дає `1`, коли багатонитковість увімкнена **і** хоч одна пара сестринських ниток справді працює; інакше `0`.

`…/smt/control` читається одним із шести значень:

| значення | означає |
|---|---|
| `on` | увімкнено, працюють усі нитки, які має процесор |
| `off` | вимкнено вручну — усі нитки, крім першої на кожному фізичному ядрі, виведено в offline |
| `<N>` | увімкнено з `N` нитками на фізичне ядро (з ядра 6.6). Число видно лише тоді, коли `N` менше за максимум машини; за повного числа файл каже `on`, щоб не ламати давніх читачів |
| `forceoff` | вимкнено назавжди до перезавантаження — назад дороги немає |
| `notsupported` | процесор багатонитковості не має |
| `notimplemented` | архітектура не вміє перемикати її на ходу (ядро системи зібране без `CONFIG_HOTPLUG_SMT`) |

Записати можна `on`, `off`, `forceoff` або число від `1` до кількості ниток, яку підтримує машина; `1` — синонім `off`. Помилки:

| код | коли |
|---|---|
| `EPERM` | поточний стан — `forceoff` |
| `ENODEV` | поточний стан — `notsupported`, або ядро системи зібране без підтримки перемикання |
| `EINVAL` | рядок не розпізнано, або число не є припустимою кількістю ниток для цієї машини |
| помилка самого вимикання | якщо котресь із сестринських ядер процесора не вдалося вимкнути, повертається його власний код |

Механічно тут не відбувається нічого окремого: запис `off` проходить по всіх ядрах процесора, які не є першою ниткою свого фізичного ядра, і **вимикає їх звичайним шляхом**, тим самим, що й `echo 0 > cpuN/online`. Тому після цього вони зникають із `…/online`, з'являються в `…/offline` і породжують події udev — усе як від ручного вимикання. Різниця лише в наслідку: доки `control` не скаже `on`, підняти котрусь із них поодинці не можна, і спроба поверне `EPERM`.

Ті самі два стани задаються при завантаженні: `nosmt` — це `off`, `nosmt=force` — це `forceoff`.

> 🔧 **Навіщо це.** Пара `control`/`active` — єдиний надійний спосіб перевірити, чи справді захист від атак через [побічний канал у кеші](topic:sf-security/cache-side-channel) увімкнено на цій машині. Читати `on` з `control` замало: значення `on` означає лише, що вимикача ніхто не смикав, тоді як [одночасна багатонитковість](topic:hw-arch/simultaneous-multithreading) могла бути вимкнена в налаштуваннях прошивки — і тоді `control` покаже `notsupported`, а `active` чесно скаже `0`. Перевіряти треба `active`.

## Машина станів назовні: `states`, `state`, `target`, `fail`

Ця четвірка існує для тестування колбеків, і без потреби її краще не чіпати.

`…/hotplug/states` перелічує всі зареєстровані стани у форматі `%3d: назва`:

```
$ cat /sys/devices/system/cpu/hotplug/states
  0: offline
  1: perf/x86/amd/uncore:prepare
...
138: mm/vmscan:online
139: mm/vmstat:online
140: lib/percpu_cnt:online
...
169: online
```

Два зауваження про ці номери. Стани без назви у виводі не з'являються взагалі, тож нумерація **не суцільна**. І вона **не стала**: додайте модуль, змініть конфігурацію збірки — і числа поїдуть. Знаходити свій стан треба за назвою, а не за номером.

`…/cpuN/hotplug/state` (лише читання) — номер, у якому ядро процесора зараз. `…/cpuN/hotplug/target` — номер, до якого його ведуть; запис у нього запускає перехід.

**Проміжні цілі типово заборонені.** У звичайному ядрі системи `target` приймає рівно два числа: `0` (тобто `CPUHP_OFFLINE`) і номер стану `online` — тобто робить те саме, що `cpuN/online`, лише числами. Щоб писати туди проміжні номери, ядро системи має бути зібране з `CONFIG_CPU_HOTPLUG_STATE_CONTROL` — це параметр із розділу зневадження, залежний від `DEBUG_KERNEL`, типово вимкнений ([конфігурація і збірка ядра](topic:sys-unix/kernel-config-and-build) — як із дерева з тисячами вимикачів виходить одна конкретна збірка). Крім того, цільовий стан мусить мати назву й не бути позначеним як такий, що не має права зупиняти прохід; інакше — `EINVAL`.

`…/cpuN/hotplug/fail` каже машині станів **навмисне зламати** наступний перехід у вказаній точці, щоб побачити, чи правильно відкочується ваша частина:

| що записано | результат |
|---|---|
| `-1` | скинути; штучних відмов не буде |
| номер поза відрізком `0…CPUHP_ONLINE` | `EINVAL` |
| номер із секції, що виконується з вимкненими перериваннями | `EINVAL` — ці колбеки не мають права падати за побудовою |
| номер `≤ CPUHP_BRINGUP_CPU`, коли ядро процесора вже вище за нього | `EINVAL` — коли ядро процесора мертве, відступати нікуди |
| номер стану, у якому не зареєстровано жодного колбека | `EINVAL` |
| решта | збережено |

Спрацьовує це **один раз**: щойно перехід дійде до позначеного стану, ядро системи повертає `-EAGAIN` і **саме скидає** `fail` назад у `-1`. Тобто кожна перевірка вимагає окремого запису.

**Умова: ядро системи з `CONFIG_CPU_HOTPLUG_STATE_CONTROL=y`; перевіряємо відкат власного колбека на ядрі процесора 4.**

```sh
# 1. знайти свій стан за НАЗВОЮ
grep percpu_cnt /sys/devices/system/cpu/hotplug/states
# 140: lib/percpu_cnt:online

# 2. опустити ядро процесора рівно до нього й підняти назад
echo 140 > /sys/devices/system/cpu/cpu4/hotplug/target
cat /sys/devices/system/cpu/cpu4/hotplug/state     # 140
echo 169 > /sys/devices/system/cpu/cpu4/hotplug/target

# 3. зламати перехід саме в цій точці
echo 140 > /sys/devices/system/cpu/cpu4/hotplug/fail
echo 0 > /sys/devices/system/cpu/cpu4/online
# -bash: echo: write error: Resource temporarily unavailable
cat /sys/devices/system/cpu/cpu4/hotplug/fail      # -1: спрацювало й скинулося
```

Що саме виконувалося й з якими кодами повернення, видно через точки трасування `cpuhp` — `cpuhp_enter`, `cpuhp_exit`, `cpuhp_multi_enter` ([ftrace і точки трасування](topic:sys-unix/ftrace-kernel-tracing) — вбудовані в ядро системи місця, у яких можна ввімкнути запис подій без перезбирання).

## Скільки ядер процесора: виклики простору користувача

```c
#include <unistd.h>
long sysconf(int name);           /* _SC_NPROCESSORS_ONLN, _SC_NPROCESSORS_CONF */

#include <sys/sysinfo.h>
int get_nprocs(void);             /* те саме, що _SC_NPROCESSORS_ONLN */
int get_nprocs_conf(void);        /* те саме, що _SC_NPROCESSORS_CONF */
```

У POSIX цих двох імен немає взагалі — це спільне розширення glibc, musl, macOS і Solaris, і кожна бібліотека відповідає на них по-своєму. Тому корисна не назва, а те, **який саме файл читається**:

| питання | чим питати | що читається насправді |
|---|---|---|
| скільки ядер процесора зараз працює | `sysconf(_SC_NPROCESSORS_ONLN)`, `get_nprocs()` | `…/online`; якщо не вдалося — `/proc/stat`, далі `sched_getaffinity` |
| скільки ядер процесора може бути | `sysconf(_SC_NPROCESSORS_CONF)`, `get_nprocs_conf()` | з glibc 2.36 — `…/possible`; до 2.36 — перелік тек `cpuN`, тобто `present` |
| скільки дозволено **саме мені** | `sched_getaffinity(0, …)` і `CPU_COUNT_S` | ядро системи повертає `p->cpus_mask & cpu_active_mask` |
| на якому ядрі процесора я зараз | `sched_getcpu()` | vDSO або системний виклик `getcpu` |

Три подробиці, кожна з яких уже коштувала комусь помилки.

**`_SC_NPROCESSORS_CONF` змінив сенс усередині glibc.** До версії 2.36 функція рахувала теки `cpuN` у sysfs — тобто відповідала числом наявних ядер процесора. З 2.36 вона читає `…/possible` (виправлення помилки 28991, березень 2022). Той самий бінарник на тій самій машині віддає різні числа залежно від того, з якою бібліотекою його запустили, і на віртуальній машині з роздутим `possible` різниця буває кратною.

**musl відповідає на обидва питання третім числом.** І `_SC_NPROCESSORS_ONLN`, і `_SC_NPROCESSORS_CONF` там реалізовані однаково: викликається `sched_getaffinity` і рахуються біти. У контейнері з чотирма дозволеними ядрами процесора з шістдесяти обидві відповіді — `4`, і жодна з них не описує машину.

**`sched_getaffinity` ніколи не показує вимкнених ядер процесора.** Ядро системи віддає не збережену маску задачі, а її перетин із маскою активних. Наслідок приємний: після `echo 1` ядро процесора з'явиться у відповіді саме собою, без жодних дій із боку програми, бо збережена маска його пам'ятала весь час. Наслідок неприємний: `/proc/<pid>/status` друкує ту саму маску **без перетину**, тож поля `Cpus_allowed_list` і відповідь системного виклику можуть чесно розходитися, і жодне з них не бреше.

Виняток із цієї симетрії один. Якщо вимикають **останнє** дозволене задачі ядро процесора, ядро системи не має куди її подіти й розриває прив'язку, залишаючи в журналі рядок виду `process 1841 (worker) no longer affine to cpu6`. Повернення ядра процесора цього не скасовує: маску вже перезаписано.

Повні підписи, макроси `cpu_set_t`, коди помилок і поведінку `sched_getcpu` описано окремо — [інтерфейси прив'язки до ядер](topic:sys-unix/cpu-affinity/api-affinity-interfaces.md).

> 🔧 **Навіщо це.** Розмір пулу потоків беруть з одного числа, і майже завжди беруть не те. `_SC_NPROCESSORS_ONLN` описує машину, а не вас: під `taskset`, у контейнері чи в контрольній групі воно скаже шістдесят, тоді як бігати ви зможете на чотирьох ядрах процесора. `_SC_NPROCESSORS_CONF` описує стелю, яка не міняється, — вона годиться на розмір масиву, індексованого номером ядра процесора, і зовсім не годиться на кількість потоків. Для пулу потрібне третє число — те, що дає `sched_getaffinity`.

## Мінімальна робоча програма

Програма нижче друкує всі відповіді поруч, щоб було видно, де саме вони розходяться. Розбирач списку тут не для краси: він робить те саме, що робить усередині glibc, і навмисне переживає порожній файл.

```c
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/sysinfo.h>
#include <unistd.h>

/* Порахувати номери в списку виду "0-5,7,9-15". Порожній рядок — це нуль. */
static long count_cpu_list(const char *s)
{
    long total = 0;

    while (*s) {
        char *end;
        long lo = strtol(s, &end, 10);
        if (end == s)                  /* не число — далі читати нічого */
            break;
        long hi = lo;
        s = end;

        if (*s == '-') {               /* відрізок */
            hi = strtol(s + 1, &end, 10);
            if (end == s + 1)
                break;
            s = end;
        }
        if (hi >= lo)
            total += hi - lo + 1;

        if (*s != ',')                 /* кінець рядка */
            break;
        s++;
    }
    return total;
}

static long read_cpu_list(const char *path)
{
    char buf[4096];
    FILE *f = fopen(path, "r");
    if (f == NULL)
        return -1;

    long n = fgets(buf, sizeof buf, f) ? count_cpu_list(buf) : 0;
    fclose(f);
    return n;
}

int main(void)
{
    long possible = read_cpu_list("/sys/devices/system/cpu/possible");
    long present  = read_cpu_list("/sys/devices/system/cpu/present");
    long online   = read_cpu_list("/sys/devices/system/cpu/online");
    long offline  = read_cpu_list("/sys/devices/system/cpu/offline");

    printf("possible %ld  present %ld  online %ld  offline %ld\n",
           possible, present, online, offline);
    printf("_SC_NPROCESSORS_CONF %ld  _SC_NPROCESSORS_ONLN %ld\n",
           sysconf(_SC_NPROCESSORS_CONF), sysconf(_SC_NPROCESSORS_ONLN));

    /* Набір рівно тієї ширини, яку обіцяє possible: номери 0 … possible-1. */
    if (possible < 1)
        possible = CPU_SETSIZE;

    size_t size = CPU_ALLOC_SIZE(possible);
    cpu_set_t *set = CPU_ALLOC(possible);
    if (set == NULL) {
        perror("CPU_ALLOC");
        return 1;
    }
    CPU_ZERO_S(size, set);

    if (sched_getaffinity(0, size, set) != 0) {
        perror("sched_getaffinity");   /* EINVAL тут = буфер замалий */
        return 1;
    }

    printf("дозволено нам %d, зараз біжимо на %d\n",
           CPU_COUNT_S(size, set), sched_getcpu());

    CPU_FREE(set);
    return 0;
}
```

На машині з шістнадцятьма ядрами процесора, одним вимкненим і прив'язкою до чотирьох це друкує:

```
possible 16  present 16  online 15  offline 1
_SC_NPROCESSORS_CONF 16  _SC_NPROCESSORS_ONLN 15
дозволено нам 4, зараз біжимо на 9
```

Чотири різні правильні числа в одному виводі — і жодне з них не замінює іншого. Розмір масиву, індексованого номером ядра процесора, беруть з першого; кількість потоків — з останнього.

## `lscpu` і `chcpu`

`lscpu` читає ті самі файли й показує їх людині:

```
$ lscpu | head -6
Architecture:            x86_64
CPU op-mode(s):          32-bit, 64-bit
CPU(s):                  16
  On-line CPU(s) list:   0-5,7-15
  Off-line CPU(s) list:  6
```

Рядок `CPU(s):` — це `present`, а не `online`; коли вимкнених немає, рядка `Off-line CPU(s) list` немає теж.

| ключ | що робить |
|---|---|
| `-e`, `--extended` | рядок на кожне ядро процесора зі стовпцем `ONLINE` (`yes`/`no`) |
| `-p`, `--parse` | те саме розбірним форматом через кому |
| `-a`, `--all` | і ввімкнені, і вимкнені (типово для `-e`) |
| `-b`, `--online` | лише ввімкнені (типово для `-p`) |
| `-c`, `--offline` | лише вимкнені |
| `-x`, `--hex` | маски шістнадцятково замість списків |
| `-J`, `--json` | вивід у JSON |
| `-s`, `--sysroot <тека>` | читати sysfs із іншого кореня — так дивляться зріз чужої машини |

`chcpu` — це рівно запис у ті самі файли, зроблений за вас:

| ключ | пише у | значення |
|---|---|---|
| `-e`, `--enable <список>` | `…/cpuN/online` | `1` |
| `-d`, `--disable <список>` | `…/cpuN/online` | `0` |
| `-c`, `--configure <список>` | `…/cpuN/configure` | `1` — узяти ядро процесора з пулу гіпервізора |
| `-g`, `--deconfigure <список>` | `…/cpuN/configure` | `0` — віддати назад; ядро процесора має бути вимкнене |
| `-r`, `--rescan` | `…/rescan` | `1` |
| `-p`, `--dispatch horizontal\|vertical` | `…/dispatching` | `0` / `1` |

Список номерів — через кому, з відрізками: `0,5,7,9-11`. Коди повернення відрізняють часткову невдачу від повної: `0` — усе вдалося, `1` — не вдалося нічого, `64` — вдалося не все. У скрипті, який гасить десяток ядер процесора, перевіряти треба саме на `0`, бо `64` мовчки означає, що частина лишилася працювати.

Чого `chcpu` не вміє — це багатонитковості: `…/smt/control` він не чіпає, туди пишуть руками.

## Події udev

Зміна стану ядра процесора породжує подію в моделі пристроїв ([udev](topic:sys-unix/udev-rules) — служба, що приймає від ядра системи повідомлення про пристрої й застосовує до них правила):

| `ACTION` | коли |
|---|---|
| `add`, `remove` | тека `cpuN` з'явилася або зникла — фізичне додавання, віртуальне ядро процесора в гостя |
| `online`, `offline` | змінився логічний стан — саме те, що робить запис у `cpuN/online` |

Плутати ці дві пари не варто: додане ядро процесора приходить подією `add` і залишається **вимкненим**, доки хтось не запише `1`. Поля події:

```
$ udevadm monitor --kernel --property --subsystem-match=cpu
KERNEL[8421.113] offline  /devices/system/cpu/cpu6 (cpu)
ACTION=offline
DEVPATH=/devices/system/cpu/cpu6
SUBSYSTEM=cpu
SEQNUM=4831
DRIVER=processor
MODALIAS=cpu:type:x86,ven0000fam0019mod0021:feature:,0000,0001,...
```

`DRIVER` є, коли до пристрою прив'язано драйвер; `MODALIAS` — лише за `CONFIG_GENERIC_CPU_AUTOPROBE`. Події немає взагалі, якщо стан не змінився: повторний запис `0` у вимкнене ядро процесора тихо повертає успіх і нікого не сповіщає.

Правило автоматичного піднімання нових ядер процесора — те, що вже стоїть у більшості дистрибутивів:

```
# /usr/lib/udev/rules.d/40-redhat.rules
SUBSYSTEM=="cpu", ACTION=="add", TEST=="online", ATTR{online}=="0", ATTR{online}="1"
```

Саме воно дає добре відомий рядок у журналі на машинах, завантажених із `nosmt`:

```
systemd-udevd: cpu9: /usr/lib/udev/rules.d/40-redhat.rules:9
  Failed to write ATTR{/sys/devices/system/cpu/cpu9/online}, ignoring:
  Operation not permitted
```

Це не поламане правило й не збій. Це `EPERM` із таблиці вище: udev намагається підняти сестринську нитку, а ядро системи не дозволяє, бо багатонитковість вимкнено. Правило чесно позначене як таке, що ігнорує невдачу.

Реагувати на зміну кількості ядер процесора зі свого боку можна так:

```
SUBSYSTEM=="cpu", ACTION=="online|offline", TAG+="systemd", ENV{SYSTEMD_WANTS}+="cpu-changed.service"
```

Запускати роботу через `RUN+=` тут погана думка: udev убиває довгі процеси за таймаутом, а перерахунок розмірів пулу — не та річ, яку варто робити в обробнику події.

## Де ще видно наслідки

| джерело | що бачить вимкнене ядро процесора |
|---|---|
| `/proc/cpuinfo` | не показує зовсім — перелічує лише ввімкнені |
| `/proc/stat`, підсумковий рядок `cpu` | **враховує** — сума береться по всіх можливих, тож час вимкненого не губиться |
| `/proc/stat`, рядки `cpuN` | рядок зникає — перелічуються лише ввімкнені |
| `/proc/interrupts` | стовпчик зникає |
| `…/cpuN/topology/`, `…/cpuN/cache/` | теки зникають: їх створюють і прибирають самі колбеки машини станів |
| `/proc/<pid>/status` → `Cpus_allowed_list` | показує збережену маску **без перетину** з активними — тобто вимкнені номери там лишаються |

Пара рядків `/proc/stat` — найкоротша ілюстрація правила, за яким живе весь код усередині: **підсумок збирають по всіх можливих ядрах процесора, перелік дають по ввімкнених** ([procfs](topic:sys-unix/proc-reading-process-and-kernel-state) — каталоги-вікна у структури ядра системи, що нічого не важать на диску).

## Типові помилки

| симптом | причина | що робити |
|---|---|---|
| розбирач падає на `…/offline` | коли вимкнених немає, файл містить самий перевід рядка | порожній вивід тлумачити як нуль |
| скрипт обходу всіх `cpuN/online` спотикається на нулі | на x86 у `cpu0/` цього файлу немає | перевіряти наявність файлу, а не існування теки |
| `echo 1 > cpuN/online` → `Operation not permitted` | вимкнена багатонитковість; це сестринська нитка | `echo on > …/smt/control`, і лише потім піднімати |
| `echo on > …/smt/control` → `Operation not permitted` | стан `forceoff` — його ставлять назавжди | лише перезавантаження без `nosmt=force` |
| `…/smt/control` каже `notsupported`, хоча процесор багатонитковий | багатонитковість вимкнено в прошивці — ядро системи її не бачить | вмикати в налаштуваннях прошивки |
| перевірили `control == on` і вирішили, що захисту немає | `on` означає лише «вимикача не смикали» | дивитися `…/smt/active` |
| `echo 140 > cpuN/hotplug/target` → `Invalid argument` | ядро системи зібране без `CONFIG_CPU_HOTPLUG_STATE_CONTROL` | проміжні цілі — лише в зневаджувальній збірці |
| номер стану, знайдений учора, сьогодні веде не туди | нумерація `states` залежить від конфігурації й набору модулів | шукати за назвою стану |
| `fail` спрацював раз і перестав | ядро системи скидає його в `-1` після першої ж відмови | записувати перед кожною перевіркою |
| `_SC_NPROCESSORS_CONF` дає різні числа на різних системах | до glibc 2.36 це `present`, з 2.36 — `possible`; у musl — узагалі маска прив'язки | читати `…/possible` самим, якщо потрібна саме стеля |
| пул потоків розміром на всю машину в контейнері | `_SC_NPROCESSORS_ONLN` описує машину, а не задачу | рахувати `CPU_COUNT_S` від `sched_getaffinity` |
| `sched_getaffinity` і `Cpus_allowed_list` показують різне | системний виклик перетинає маску з активними, `/proc` — ні | це не суперечність; для «де я можу бігти» правильний виклик |
| прив'язка зникла після вимикання ядра процесора й не повернулася | вимкнули останнє дозволене — ядро системи розірвало прив'язку назавжди | шукати `no longer affine` у журналі й ставити маску заново |
| `chcpu -d 4-15` начебто відпрацював, а половина ядер процесора працює | код повернення `64` — часткова невдача | перевіряти саме на `0`, не на «не одиницю» |
| нове ядро процесора з'явилося, але не працює | подія `add` не вмикає — вона лише реєструє | правило udev із `ATTR{online}="1"` або запис руками |
