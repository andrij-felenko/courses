# 📋 Довідник синтаксису фільтрів tcpdump та примітивів BPF

Пакетний аналізатор `tcpdump` використовує бібліотеку `libpcap` для компіляції високорівневих фільтрувальних виразів у двійковий байткод віртуальної машини Berkeley Packet Filter (BPF). Цей байткод завантажується в простір ядра Linux за допомогою сокетного виклику `setsockopt()` з опцією `SO_ATTACH_FILTER` і виконується над кожним вхідним мережевим кадром на рівні мережевого драйвера ще до виділення структур даних сокета чи копіювання байтів у пам'ять процесу.

Нижче наведено вичерпну інженерну довідку стандартних фільтрувальних примітивів, синтаксису двійкових зрізів заголовків Ethernet, IPv4, IPv6, TCP, UDP та ICMP, а також специфікацію системи команд віртуальної машини cBPF.

---

## Стандартні фільтрувальні примітиви

Фільтрувальний вираз `libpcap` складається з одного або кількох логічних примітивів. Кожен примітив поєднує числове або рядкове значення з трьома типами класифікаторів:

1. **Тип (`type`)**: вказує категорію об'єкта перевірки. Доступні ключові слова: `host` (окремий вузол), `net` (підмережа з маскою CIDR), `port` (номер порту 0–65535), `portrange` (діапазон портів).
2. **Напрямок (`dir`)**: задає напрямок передачі пакетів відносно вказаного об'єкта. Ключові слова: `src` (джерело), `dst` (призначення), `src or dst` (будь-який бік, значення за замовчуванням), `src and dst` (обидва боки).
3. **Протокол (`proto`)**: обмежує дію фільтра конкретним протокольним рівнем. Ключові слова: `ether`, `fddi`, `tr`, `wlan`, `ip`, `ip6`, `arp`, `rarp`, `decnet`, `tcp`, `udp`, `icmp`, `igmp`.

| Примітив | Опис семантики фільтра | Приклад виклику |
|---|---|---|
| `host <ip/name>` | Пакети, де вказана адреса є джерелом або отримувачем | `tcpdump -nn host 192.168.1.50` |
| `src host <ip>` | Фільтрація виключно за IP-адресою відправника | `tcpdump -nn src host 10.0.0.1` |
| `dst host <ip>` | Фільтрація виключно за IP-адресою отримувача | `tcpdump -nn dst host 10.0.0.2` |
| `net <cidr>` | Трафік заданої підмережі IPv4 або IPv6 | `tcpdump -nn net 172.16.0.0/16` |
| `port <n>` | Порт транспортного рівня (TCP або UDP) | `tcpdump -nn port 443` |
| `src port <n>` | Порт джерела для протоколів TCP/UDP | `tcpdump -nn src port 53` |
| `dst port <n>` | Порт призначення для протоколів TCP/UDP | `tcpdump -nn dst port 80` |
| `portrange <n1-n2>` | Діапазон портів джерела або призначення | `tcpdump -nn portrange 8000-8080` |
| `ether host <mac>` | Фільтрація за 48-бітною фізичною адресою Ethernet | `tcpdump -nn ether host 52:54:00:12:34:56` |
| `ether src <mac>` | Фільтрація за апаратною MAC-адресою джерела | `tcpdump -nn ether src 00:11:22:33:44:55` |
| `ether proto <type>` | Фільтрація за 16-бітним полем EtherType | `tcpdump -nn ether proto 0x8100` |
| `vlan [<vlan_id>]` | Захоплення кадрів з тегом 802.1Q VLAN | `tcpdump -nn vlan 100` |
| `proto <name/num>` | Фільтрація за кодом протоколу в заголовку IP | `tcpdump -nn ip proto 6` |
| `broadcast` | Широкомовні кадри канального або мережевого рівня | `tcpdump -nn ether broadcast` |
| `multicast` | Багатоадресні пакети (IP або Ethernet) | `tcpdump -nn ip multicast` |

### Логічні оператори та пріоритети

Примітиви об'єднуються у складні логічні вирази за допомогою операторів алгебри логіки. У командному рядку shell дужки необхідно екранувати зворотним слешем або брати весь фільтр в одинарні лапки:

* **Кон'юнкція (AND)**: записується як `and` або `&&` (наприклад, `src host 10.0.0.5 and dst port 80`).
* **Диз'юнкція (OR)**: записується як `or` або `||` (наприклад, `port 80 or port 443`).
* **Заперечення (NOT)**: записується як `not` або `!` (наприклад, `not port 22 and not host 127.0.0.1`).
* **Групування операторів**: дужки `\( ... \)` змінюють стандартний пріоритет операцій (де `not` має найвищий пріоритет, далі `and`, найнижчий — `or`).

## Інспекція бітових прапорців TCP

Поле прапорців TCP розташоване у 13-му байті заголовка TCP (зміщення 13 від початку заголовка). `tcpdump` надає вбудовані текстові константи для кожної бітової маски, що дозволяє виконувати побітові операції перевірки без ручного обчислення шістнадцяткових значень:

| Псевдонім | Бітова маска | Опис прапорця TCP |
|---|---|---|
| `tcp-fin` | `0x01` | Завершення сесії (Finish) |
| `tcp-syn` | `0x02` | Синхронізація порядкових номерів (Synchronize) |
| `tcp-rst` | `0x04` | Аварійне скидання з'єднання (Reset) |
| `tcp-push` | `0x08` | Негайне проштовхування буфера процесу (Push) |
| `tcp-ack` | `0x10` | Підтвердження отримання даних (Acknowledgment) |
| `tcp-urg` | `0x20` | Наявність покажчика термінових даних (Urgent) |
| `tcp-ece` | `0x40` | Явне повідомлення про затори в мережі (ECN-Echo) |
| `tcp-cwr` | `0x80` | Підтвердження зменшення вікна затору (Congestion Window Reduced) |

### Практичні BPF-шаблони для діагностики аномалій TCP

```bash
# 1. Захоплення виключно пакетів ініціалізації з'єднання (SYN без ACK)
tcpdump -nn "tcp[tcpflags] & (tcp-syn) != 0 and tcp[tcpflags] & (tcp-ack) == 0"

# 2. Відповіді сервера на запити підключення (SYN-ACK)
tcpdump -nn "tcp[tcpflags] & (tcp-syn|tcp-ack) == (tcp-syn|tcp-ack)"

# 3. Виявлення всіх пакетів скидання зв'язку (RST)
tcpdump -nn "tcp[tcpflags] & (tcp-rst) != 0"

# 4. Виявлення пакетів закриття з'єднань (FIN)
tcpdump -nn "tcp[tcpflags] & (tcp-fin) != 0"

# 5. Детекція NULL-сканування портів (усі прапорці дорівнюють нулю)
tcpdump -nn "tcp[tcpflags] == 0"

# 6. Детекція XMAS-сканування (активні прапорці FIN, PSH та URG одночасно)
tcpdump -nn "tcp[tcpflags] & (tcp-fin|tcp-push|tcp-urg) == (tcp-fin|tcp-push|tcp-urg)"

# 7. Детекція SYN-RST аномалій (некоректна комбінація SYN та RST)
tcpdump -nn "tcp[tcpflags] & (tcp-syn|tcp-rst) == (tcp-syn|tcp-rst)"
```

## Зрізи сирих заголовків: синтаксис proto[offset:size]

Якщо стандартних примітивів недостатньо для точної вибірки, BPF підтримує прямий доступ до довільного байта чи групи байтів у пакеті за допомогою оператора зрізу:

```text
Синтаксис: proto [ offset : size ]
```

* `proto`: протокольний рівень відліку зміщення (`ether`, `ip`, `ip6`, `arp`, `tcp`, `udp`, `icmp`).
* `offset`: зміщення в байтах від початку заголовка вказаного протоколу (індексація починається з 0).
* `size` *(необов'язковий)*: кількість байтів для зчитування. Допустимі значення: `1` (за замовчуванням), `2` або `4`.

### Зрізи заголовка IPv4 (`ip[...]`)

Заголовок IPv4 має базовий розмір 20 байтів і містить поля довжини, типу сервісу, фрагментації та часу життя:

| Вираз зрізу | Поле заголовка IPv4 | Інженерне призначення |
|---|---|---|
| `ip[0] & 0x0f` | Internet Header Length (IHL) | Кількість 32-бітних слів (якщо значення `> 5`, пакет містить IP Options) |
| `ip[1] & 0xfc` | DSCP / DiffServ Bits | Аналіз міток якості обслуговування QoS у трафіку |
| `ip[2:2]` | Total Length | Повний розмір IP-дейтаграми в байтах (вилов пакетів `> 1500` байтів) |
| `ip[4:2]` | Identification | Ідентифікатор IP-фрагментів для збирання пакетів |
| `ip[6:2] & 0x1fff != 0` | Fragment Offset | Виявлення фрагментованих дейтаграм та наступних фрагментів |
| `ip[6] & 0x40 != 0` | Don't Fragment (DF) біт | Перевірка функціонування механізму Path MTU Discovery |
| `ip[6] & 0x20 != 0` | More Fragments (MF) біт | Ознака наявності подальших фрагментів дейтаграми |
| `ip[8] < 5` | Time to Live (TTL) | Виявлення пакетів на межі вичерпання TTL (петлі маршрутизації) |
| `ip[9] == 6` | Protocol | Код протоколу (6 = TCP, 17 = UDP, 1 = ICMP, 47 = GRE, 50 = ESP) |
| `ip[12:4]` | Source IP Address | 32-бітне числове значення адреси відправника |
| `ip[16:4]` | Destination IP Address | 32-бітне числове значення адреси отримувача |

### Зрізи заголовка IPv6 (`ip6[...]`)

Заголовок IPv6 має фіксовану довжину 40 байтів:

| Вираз зрізу | Поле заголовка IPv6 | Інженерне призначення |
|---|---|---|
| `(ip6[0:4] & 0x0ff00000) >> 20` | Traffic Class | 8-бітне поле пріоритету та DSCP в IPv6 |
| `ip6[0:4] & 0x000fffff` | Flow Label | 20-бітний ідентифікатор потоку для комутації ECMP |
| `ip6[4:2]` | Payload Length | Розмір корисного навантаження (без 40 байтів заголовка) |
| `ip6[6]` | Next Header | Тип наступного заголовка (6 = TCP, 17 = UDP, 58 = ICMPv6) |
| `ip6[7] < 5` | Hop Limit | Лічильник переходів (аналог TTL в IPv4) |
| `ip6[8:16]` | Source IPv6 Address | 128-бітна IP-адреса відправника |
| `ip6[24:16]` | Destination IPv6 Address | 128-бітна IP-адреса отримувача |

### Зрізи заголовка TCP (`tcp[...]`)

Базовий заголовок TCP займає 20 байтів:

| Вираз зрізу | Поле заголовка TCP | Інженерне призначення |
|---|---|---|
| `tcp[0:2]` | Source Port | 16-бітний порт відправника |
| `tcp[2:2]` | Destination Port | 16-бітний порт отримувача |
| `tcp[4:4]` | Sequence Number | 32-бітний порядковий номер першого байта сегмента |
| `tcp[8:4]` | Acknowledgment Number | 32-бітний номер очікуваного байта від співрозмовника |
| `(tcp[12] & 0xf0) >> 2` | Data Offset (довжина заголовка) | Довжина заголовка TCP у байтах з урахуванням опцій |
| `tcp[14:2] == 0` | Window Size | Нульовий розмір вікна прийому (переповнення буфера застосунку) |
| `tcp[16:2]` | TCP Checksum | Контрольна сума сегмента |
| `tcp[18:2]` | Urgent Pointer | Зміщення термінових даних |

### Зрізи заголовків UDP та ICMP

```bash
# UDP: довжина дейтаграми перевищує 512 байтів (DNS over UDP ретрансляція)
tcpdump -nn "udp and udp[4:2] > 512"

# ICMP: перехоплення повідомлень Destination Unreachable (Тип 3)
tcpdump -nn "icmp and icmp[0] == 3"

# ICMP: перехоплення повідомлень Time-to-Live Exceeded (Тип 11, Код 0)
tcpdump -nn "icmp and icmp[0] == 11 and icmp[1] == 0"

# ICMP: перехоплення луна-запитів Echo Request (Тип 8)
tcpdump -nn "icmp and icmp[0] == 8"
```

## Архітектура та опкоди віртуальної машини cBPF

Класичний BPF (cBPF) є 32-бітною гарвардською регістровою віртуальною машиною. Кожна інструкція компілюється в 8-байтову структуру `struct sock_filter`.

:::tabs
```c
#include <linux/types.h>
#include <linux/filter.h>

/* Структура інструкції віртуальної машини BPF (8 байтів) */
struct sock_filter {
    __u16 code; /* Код операції (Opcode), клас та режим адресації */
    __u8  jt;   /* Зміщення переходу при істинній умові (Jump True) */
    __u8  jf;   /* Зміщення переходу при хибній умові (Jump False) */
    __u32 k;    /* Універсальний аргумент: константа, зміщення або довжина */
};

/* Контейнер програми BPF для системного виклику setsockopt */
struct sock_fprog {
    unsigned short      len;    /* Кількість інструкцій у масиві */
    struct sock_filter *filter; /* Покажчик на масив інструкцій */
};
```
```cpp
#include <cstdint>
#include <span>
#include <vector>
#include <linux/types.h>
#include <linux/filter.h>

namespace bpf {

// Ідіоматична C++ обгортка над програмою фільтрації cBPF
class BpfProgram {
public:
    explicit BpfProgram(std::vector<sock_filter> instructions)
        : instructions_{std::move(instructions)} {}

    [[nodiscard]] sock_fprog get_fprog() noexcept {
        return sock_fprog{
            .len = static_cast<unsigned short>(instructions_.size()),
            .filter = instructions_.data()
        };
    }

    [[nodiscard]] std::span<const sock_filter> instructions() const noexcept {
        return instructions_;
    }

private:
    std::vector<sock_filter> instructions_;
};

} // namespace bpf
```
:::

### Регістрова модель cBPF

1. **Акумулятор (`A`)**: 32-бітний регістр загального призначення, у якому виконуються всі арифметичні операції, логічні перевірки та завантаження даних із кадру.
2. **Індексний регістр (`X`)**: 32-бітний регістр для непрямої адресації та збереження динамічних зміщень (наприклад, змінної довжини IP-заголовка `ihl * 4`).
3. **Пам'ять тимчасового зберігання (`M[0..15]`)**: масив із 16 слів по 32 біти для збереження проміжних результатів обчислень.

### Класи інструкцій та бітові поля

Код інструкції `code` формується порозрядним логічним «АБО» трьох складових: клас команди + розмір операнда + режим адресації:

* **Класи команд (`BPF_CLASS`)**:
  - `BPF_LD` / `BPF_LDX`: завантаження значення в регістр `A` чи `X`.
  - `BPF_ST` / `BPF_STX`: збереження значення з `A` чи `X` у комірку пам'яті `M[k]`.
  - `BPF_ALU`: виконання операції в `A` (`BPF_ADD`, `BPF_SUB`, `BPF_MUL`, `BPF_DIV`, `BPF_AND`, `BPF_OR`, `BPF_XOR`, `BPF_LSH`, `BPF_RSH`, `BPF_NEG`).
  - `BPF_JMP`: інструкції умовного та безумовного переходу (`BPF_JA`, `BPF_JEQ`, `BPF_JGT`, `BPF_JGE`, `BPF_JSET`).
  - `BPF_RET`: завершення виконання програми. Регістр `A` або константа `k` повертає кількість байтів кадру для захоплення (0 — відкинути, `snaplen` — зберегти).
  - `BPF_MISC`: допоміжні інструкції перенесення значень між регістрами (`BPF_TAX` переносить `A → X`, `BPF_TXA` переносить `X → A`).

* **Розміри даних**: `BPF_W` (32-бітне слово), `BPF_H` (16-бітне півслово), `BPF_B` (8-бітний байт).
* **Режими адресації**: `BPF_IMM` (безпосередня константа `k`), `BPF_ABS` (абсолютне зміщення в пакеті `[k]`), `BPF_IND` (непряме зміщення `[X + k]`), `BPF_MEM` (комірка пам'яті `M[k]`), `BPF_LEN` (довжина пакета `skb->len`), `BPF_MSH` (спеціальний режим для швидкого обчислення довжини IP-заголовка: `4 * (packet[k] & 0xf)` у регістр `X`).

## Інженерні особливості та пастки фільтрації BPF

При складанні та застосуванні фільтрів BPF у високошвидкісних мережах необхідно враховувати особливості роботи мережевих адаптерів та протокольної інкапсуляції:

1. **Зсув зміщень при тегуванні 802.1Q VLAN**: коли мережевий інтерфейс приймає теговані Ethernet-кадри, між адресою джерела та полем EtherType вставляється 4-байтовий заголовок VLAN (тег `0x8100` або `0x88a8`). Внаслідок цього базовий фільтр на кшталт `ip and port 80` перестає працювати, оскільки BPF шукає EtherType `0x0800` на стандартному 12-му байті. Для коректного захоплення в таких середовищах використовують префікс `vlan`:
   ```bash
   tcpdump -i eth0 -nn "vlan and port 80"
   ```
2. **Вплив апаратного розвантаження GRO/LRO (Generic Receive Offload)**: сучасні мережеві карти об'єднують послідовні TCP-пакети одного потоку в гігантські псевдокадри розміром до 64 КіБ ще до передачі в ядро. Якщо адміністратор перевіряє розмір кадру через `ip[2:2] > 1500`, такий фільтр перехоплюватиме штучні GRO-пакети. Для отримання автентичних розмірів фізичних кадрів GRO тимчасово вимикають через `ethtool`:
   ```bash
   sudo ethtool -K eth0 gro off lro off
   ```
3. **Компіляція cBPF у розширений eBPF та JIT**: починаючи з ядра Linux 3.15, класичний байткод cBPF прозоро транслюється ядром у розширений eBPF (64-бітна регістрова модель з 10 регістрами `R0..R9`), після чого JIT-компілятор перетворює його на машинний код процесора. Перевірити статус увімкнення BPF JIT можна у файловій системі `procfs`:
   ```bash
   cat /proc/sys/net/core/bpf_jit_enable  # Значення 1 або 2 свідчить про активний JIT
   ```

## Рецепти діагностичних фільтрів для розслідування інцидентів

```bash
# 1. Пошук TCP-з'єднань з нульовим розміром вікна прийому (Zero Window Freeze)
tcpdump -i eth0 -nn "tcp and tcp[14:2] == 0"

# 2. Виявлення переповнення MTU та спроб фрагментації (пакети більше 1500 байтів)
tcpdump -i eth0 -nn "ip and ip[2:2] > 1500"

# 3. Виявлення повторних передач SYN (SYN retransmissions при недоступності сервісу)
tcpdump -i eth0 -nn "tcp[tcpflags] & (tcp-syn) != 0 and tcp[tcpflags] & (tcp-ack) == 0"

# 4. Виявлення штормів RST-пакетів від локального сервера
```
