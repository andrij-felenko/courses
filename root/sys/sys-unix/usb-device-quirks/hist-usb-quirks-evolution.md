# 📜 Від захардкоджених латок до динамічного реєстру quirks

Історія підсистеми обходу апаратних вад (quirks) у підсистемі USB ядра Linux — це літопис зіткнення між математично чистою інженерною специфікацією та хаотичною реальністю масового виробництва мікроелектроніки. Вона демонструє, як ядро еволюціонувало від розрізнених фрагментів коду з перевірками ідентифікаторів виробників до централізованої архітектури прапорців відхилень і динамічного керування поведінкою шини.

## Дилема стандартизації: кінець 1990-х років

Коли консорціум USB Implementers Forum (USB-IF) на чолі з Intel, Microsoft, IBM та іншими гігантами індустрії опублікував специфікацію USB 1.0 (1996 рік), а згодом доопрацьовану USB 1.1 (1998 рік), інженери очікували створення універсальної шини з чіткими кінцевими автоматами. Специфікація детально регламентувала кожен аспект: формати стандартних дескрипторів, часові діаграми скидання та стробування ліній, послідовності станів кінцевих точок (endpoints) та обов'язкові керуючі запити (Control Requests).

Реальність виявилася зовсім іншою. Наприкінці 1990-х ринок заполонили дешеві контролери для вебкамер, сканерів, цифрових фотоапаратів та перших MP3-плеєрів. Більшість виробників мікросхем не проводили офіційної сертифікації в USB-IF через високу вартість тестування. Замість цього прошивки тестувалися лише на сумісність із драйверами Windows 98 або Windows 2000. Якщо пристрій розпізнавався операційною системою від Microsoft, його випускали в масове виробництво мільйонними партіями.

Проте стек USB у Windows уже тоді містив неофіційні компенсаційні механізми. Наприклад, Windows могла не відправляти запит `SET_INTERFACE` при ініціалізації пристроїв з одним альтернативним налаштуванням або автоматично додавала затримки між запитами дескрипторів конфігурації. У результаті прошивки багатьох пристроїв просто не мали коду для обробки стандартних запитів, зависали при отриманні несподіваного пакета або потребували тривалого відновлення після скидання порту.

Коли в ядрі Linux 2.2.18 з'явилася базова підтримка USB, написана Войцехом Зайончковським (Wojtek Zajączkowski), Лінусом Торвальдсом (Linus Torvalds) та іншими ентузіастами, стек ядра працював суворо за офіційною специфікацією. Наслідок був катастрофічним: значна частина комерційних USB-пристроїв відмовлялася проходити нумерацію (enumeration), випадала в таймаут або намертво блокувала хост-контролер.

## Філософська суперечка в розробці ядра

На початку 2000-х років у списку розсилки Linux Kernel Mailing List (LKML) розгорнулася гостра дискусія. Частина розробників наполягала на «пуристичному» підході: ядро Linux повинно суворо дотримуватися специфікацій USB-IF і відмовлятися підтримувати «криве» залізо (broken hardware). Логіка полягала в тому, що толерантність до багів виробників заохочує їх випускати неякісну продукцію, тоді як масова відмова в роботі на Linux змусить вендорів виправляти прошивки.

Проте лідери підсистеми USB — Грег Кроа-Гартман (Greg Kroah-Hartman), Алан Стерн (Alan Stern), Девід Браунелл (David Brownell) та Меттью Дхарм (Matthew Dharm) — зайняли прагматичну позицію. Користувач, який під'єднує фотоапарат або флешку до Linux і бачить паніку ядра чи повідомлення `device not responding to setup address`, звинувачує саме Linux, а не безіменного виробника китайського чипа. Якщо операційна система не працює з пристроями, якими заповнений ринок, вона програє боротьбу за робочі столи та сервери.

Прагматичний підхід переміг: ядро Linux взяло на себе зобов'язання забезпечувати працездатність навіть грубо дефектного обладнання, але з умовою ізоляції таких обходів від загального коду шини.

## Народження unusual_devs.h у драйвері usb-storage

Першим полігоном для системного розв'язання проблеми став драйвер масових накопичувачів `usb-storage` у ядрі Linux 2.4. Накопичувачі USB Mass Storage базувалися на протоколі Bulk-Only Transport (BOT) та командних наборах SCSI (SPC, SBC). Багато перших флеш-контролерів та мостів USB-IDE реалізовували протокол із грубими помилками:
- не підтримували стандартну довжину команди SCSI (зависали при отриманні 6-байтових або 12-байтових команд);
- видавали фальшивий залишок передачі (residue) у статусному блоці CSW (Command Status Wrapper);
- неправильно розраховували кінцеву ємність носія, повертаючи значення на один сектор більше за реальне, що призводило до помилок I/O при монтуванні файлових систем;
- панічно реагували на запити визначення захисту від запису (`MODE_SENSE_6`).

Меттью Дхарм та Алан Стерн запропонували відокремити таблицю винятків у спеціальний заголовний файл `drivers/usb/storage/unusual_devs.h`. Замість розгалуження коду операторів `if/else` у транспортному рівні, драйвер отримав макрос `UNUSUAL_DEV()`. Кожен запис містив діапазон Vendor ID (VID), Product ID (PID), версію прошивки (bcdDevice) та набір бітових прапорців `US_FL_*` (наприклад, `US_FL_IGNORE_RESIDUE`, `US_FL_FIXED_COMMAND`, `US_FL_CAPACITY_HEURISTICS`).

Ця модель довела свою високу ефективність: додавання підтримки нового проблемного накопичувача зводилося до внесення одного рядка в таблицю без ризику зламати стабільні пристрої.

## Створення usb_quirk_list у ядрі Linux 2.6

У міру розвитку ядра стало очевидно, що хиби трапляються не лише на рівні конкретних функціональних драйверів, але й на базовому рівні ядра USB (USB Core). Дефектні пристрої порушували саму процедуру нумерації, відповіді на керуючі URB (USB Request Block) та протоколи керування живленням.

До виходу ядра Linux 2.6.22 перевірки таких вад були розкидані по файлах `drivers/usb/core/hub.c`, `drivers/usb/core/message.c` та `drivers/usb/core/config.c`. Це ускладнювало супровід і робило код заплутаним. У 2007 році Алан Стерн провів масштабний рефакторинг ядра USB, створивши виділену підсистему quirks:
1. Було виділено єдиний файл `drivers/usb/core/quirks.c` із глобальною таблицею `usb_quirk_list[]`.
2. Введено стандартизований набір прапорців `USB_QUIRK_*` у заголовному файлі `include/linux/usb/quirks.h`.
3. У структуру опису пристрою `struct usb_device` додано поле `u32 quirks`, яке ініціалізується функцією `usb_detect_quirks()` на найпершому етапі опитування дескриптора пристрою.

Будь-яка частина USB Core тепер могла виконати просту перевірку бітової маски:
```c
if (udev->quirks & USB_QUIRK_NO_SET_INTF)
    return 0;
```

## Епоха USB 3.0, UAS та динамічного конфігурування

З появою стандарту USB 3.0 та протоколу USB Attached SCSI (UAS) на початку 2010-х виникла нова хвиля апаратних проблем. Протокол UAS дозволяв використовувати черги команд апаратної оптимізації (Native Command Queuing, NCQ) через потоки USB (USB 3.0 Streams). Масові мости USB-to-SATA (такі як JMicron JMS567, ASMedia ASM1051, Realtek RTL9210) заявляли підтримку UAS у своїх дескрипторах, але під високим навантаженням або при використанні команди `TRIM` (UNMAP) втрачали пакети, скидали з'єднання чи пошкоджували файлові системи.

Для розв'язання цієї проблеми ядро отримало додаткову таблицю `drivers/usb/storage/unusual_uas.h` та механізм динамічного блокування UAS прапорцем `US_FL_IGNORE_UAS`. Якщо чип виявлявся нестабільним, ядро відхиляло прив'язку драйвера `uas` і автоматично перемикало пристрій на повільніший, але надійний класичний драйвер `usb-storage`.

Паралельно розробники вирішили проблему користувачів, які не мали можливості перезбирати ядро заради додавання нового прапорця quirk. Було впроваджено параметри командного рядка `usbcore.quirks=` та `usb-storage.quirks=`, а згодом — можливість змінювати ці параметри наживо через файлову систему `sysfs` без перезавантаження операційної системи.

Сьогодні підсистема USB quirks у ядрі Linux є зрілим захисним бар'єром. Вона дозволяє тисячам нестандартних, застарілих або бракованих пристроїв стабільно функціонувати в середовищі Linux, зберігаючи цілісність ядра та архітектурну чистоту основного коду шини.
