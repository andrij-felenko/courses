# 📜 Еволюція менеджерів шляхів у MPTCP: від ізгоя в ядрі до двох моделей у Linux 5.6

Історія створення та стандартизації протоколу Multipath TCP (MPTCP) — це повчальний приклад того, як академічний прототип із гнучкою інфраструктурою у просторі ядра перетворився на строгий комерційний стандарт операційної системи. Коли вчені з Католицького університету Лувена (UCLouvain) під керівництвом Олів'є Бонавантюра (Olivier Bonaventure), Деймона Віщика (Damon Wischik), Костіна Райчу (Costin Raiciu) та Крістофа Пааша (Christoph Paasch) розпочали розробку MPTCP у 2009–2011 роках, головною метою було довести практичну можливість об'єднання кількох мережевих інтерфейсів у межах єдиного TCP-з'єднання.

Перша публічна реалізація для ядра Linux з'явилася у вигляді позадеревного патча (out-of-tree patch) під версією 0.80. Вона швидко привертала увагу індустрії. Зокрема, у 2013 році компанія Apple впровадила MPTCP на базі власного стека у системі iOS для забезпечення безперебійної роботи голосовго помічника Siri під час перемикання між Wi-Fi та стільниковою мережею. Проте архітектура керування шляхами у цих ранніх версіях докорінно відрізнялася від сучасної реалізації в основному стовбурі (mainline) ядра Linux, починаючи з версії 5.6.

## 1. Позадеревна еру: модульні менеджери в ядрі (MPTCP v0.80–v0.95)

У ранніх позадеревних патчах MPTCP керування шляхами було повністю реалізовано всередині простору ядра. Для цього розробники створили підсистему керованих модулів ядра, побудовану за аналогією до алгоритмів контролю перевантаження TCP (TCP Congestion Control API, таких як `tcp_cubic` чи `tcp_reno`).

Системний адміністратор міг перемикати «плагіни шляхів» у реальному часі за допомогою системного параметра `sysctl`:

```bash
sysctl net.mptcp.mptcp_path_manager=fullmesh
```

У цій архітектурі існувало чотири основні підключувані модулі ядра:

1. **`default` (або `singlepath`)**: найпростіший режим, який взагалі не створював додаткових підпотоків. MPTCP працював як звичайний класичний TCP, використовуючи лише один первинний шлях.
2. **`fullmesh`**: найпопулярніший модуль для високопродуктивних тестових стендів. Він слухав події ядра `NETDEV_UP` та `NETDEV_DOWN` і автоматично будував повнозв'язну матрицю підпотоків. Якщо клієнт мав 2 локальні IP-адреси, а сервер — 3 IP-адреси, модуль `fullmesh` автоматично ініціював `2 × 3 = 6` окремих TCP-підпотоків.
3. **`ndiffports`**: спеціалізований модуль, який створював `N` підпотоків між однією й тією ж парою IP-адрес, змінюючи лише номери джерельних портів (Source Ports). Це давало змогу обходити проміжні мережеві пристрої (Middleboxes) та ефективно балансувати трафік через механізми ECMP (Equal-Cost Multi-Path) у дата-центрах.
4. **`binder`**: підхід, розроблений переважно для мобільних пристроїв, який намагався враховувати пріоритети інтерфейсів (наприклад, надавати перевагу безкоштовному Wi-Fi перед платним LTE).

### Архітектурний конфлікт та відмова спільноти Linux Kernel

Хоча ця модель чудово показувала себе у лабораторних випробуваннях, спроби внести ці патчі до основного дерева ядра Linux зустріли жорсткий опір з боку ключових підсистемних підтримувачів ядра (Kernel Maintainers), зокрема Девіда Міллера (David Miller) та Якуба Кіцинського (Jakub Kicinski).

Конфлікт лежав у фундаментальних принципах проектування операційної системи Linux:

- **Порушення принципу розділення механізму та політики (Mechanism vs Policy)**. Визначення того, коли підключати LTE, а коли відключати Wi-Fi — це бізнес-логіка (політика). Вона залежить від ціни трафіку, рівня сигналу, заряду батареї, геолокації та побажань користувача. Зашивати таку логіку в C-код модуля ядра вважалося критичною архітектурною помилкою.
- **Відсутність інтеграції із простором користувача**. Модулі ядра реагували лише на події створення мережевих пристроїв. Вони не мали доступу до метаданих системних демонів (таких як `NetworkManager` чи `systemd-networkd`) і не могли отримувати контекст від прикладних програм.
- **Відсутність ізоляції між мережевими просторами імен (Network Namespaces)**. Параметр `sysctl net.mptcp.mptcp_path_manager` діяв глобально на рівні всієї операційної системи. Це унеможливлювало використання різних політик керування шляхами для окремих ізольованих контейнерів Docker або LXC.

## 2. Стандартизація IETF: від RFC 6824 до RFC 8684

Паралельно з дискусіями щодо внутрішньої архітектури ядра відбувалася еволюція мережевого стандарту MPTCP в інженерній групі IETF (Internet Engineering Task Force).

Перша експериментальна специфікація **RFC 6824** була опублікована у січні 2013 року. Вона визначила базові опції TCP: `MP_CAPABLE` (ініціалізація MPTCP), `MP_JOIN` (приєднання нового підпотоку), `ADD_ADDR` (оголошення IP-адреси), `REMOVE_ADDR` (видалення IP-адреси) та `MP_PRIO` (зміна пріоритету).

Однак тривала експлуатація RFC 6824 у реальному інтернеті виявила низку проблем:
- **Вразливість до атак amplification та hijacking**: недостатньо суворий захист при обміні криптографічними ключами дозволяв зловмисникам підробляти опції `ADD_ADDR` і перехоплювати трафік.
- **Проблеми з проходженням Middleboxes**: проміжні пристрої та фаєрволи нерідко вирізали невідомі TCP-опції або змінювали номери послідовності (Sequence Numbers), ламаючи роботу MPTCP.

У березні 2020 року IETF опублікувала оновлений офіційний стандарт **RFC 8684** (Multipath TCP v1). У ньому було посилено криптографічну автентифікацію за допомогою HMAC-SHA256, оптимізовано обробку ідентифікаторів адрес `Address ID` та перероблено процедуру відкату (fallback) до звичайного TCP при втручанні Middlebox.

## 3. Редизайн та повернення у Mainline Linux 5.6

У 2017 році об'єднана команда розробників із Red Hat, Intel, Tessares, Apple та UCLouvain (Крістоф Пааш, Мат Мартіно, Флоріан Вестфаль, Давіде Карлі) розпочала повне переписання стека MPTCP з нуля спеціально для включення до основного ядра Linux.

Для вирішення суперечки про «механізм і політику» було прийнято безапеляційне рішення: **ядро відповідає виключно за транспортну механіку RFC 8684, а вся політика керування шляхами виноситься у простір користувача через бінарний протокол Generic Netlink**.

У березні 2020 року в ядрі **Linux 5.6** офіційно з'явився новий стек MPTCP із двома режимами керування шляхами:

1. **In-Kernel Path Manager (`pm_type=0`)**: розроблений як максимально швидка, статична заміни старому `fullmesh`. Він позбавлений довільного C-коду модулів і керується виключно статичною таблицею кінцевих точок (`endpoints`) та глобальними лімітами через команду `ip mptcp`.
2. **Userspace Path Manager (`pm_type=1`)**: повна відмова ядра від прийняття рішень про топологію. Ядро транслює асинхронні події створення та закриття сокетів у мультикаст-групу Generic Netlink (`GENL_NAME_MPTCP`), а демон у просторі користувача (такий як `mptcpd`) приймає рішення та надсилає назад командні Netlink-пакети.

## 4. Підсумкове порівняння епох розвитку

Еволюційний шлях керування шляхами в MPTCP підсумовано у порівняльній таблиці:

| Параметр порівняння | Позадеревний стек (v0.80–v0.95) | Mainline Linux Kernel (5.6+) |
| :--- | :--- | :--- |
| **Офіційний стандарт** | RFC 6824 (Experimental) | RFC 8684 (Proposed Standard) |
| **Принцип політики** | Зашита в C-код модулів ядра | Відокремлена через Generic Netlink IPC |
| **Конфігурація** | `sysctl net.mptcp.mptcp_path_manager` | `sysctl net.mptcp.pm_type` (0 або 1) |
| **Підтримка Netns** | Глобальна (одна на всю систему) | Per-netns (ізольована для кожної netns) |
| **Взаємодія з користувачем**| Відсутня | Через демони (`mptcpd`) та D-Bus/RSSI |
| **Безпека** | Базова HMAC (RFC 6824) | Посилена HMAC-SHA256 (RFC 8684) |

Завдяки цьому редизайну Linux MPTCP перетворився з експериментального академічного коду на промисловий стек, здатний працювати як на високонавантажених серверах ядра, так і на мобільних смартфонах та роутерах 5G.
