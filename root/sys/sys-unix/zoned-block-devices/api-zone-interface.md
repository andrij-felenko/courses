# 📋 Інтерфейс зон у Linux: sysfs, `ioctl`, `blkzone`

Усе, чим ядро віддає зонований носій назовні: сім чисел у `/sys/block/<dev>/queue/`, вісім запитів `ioctl` із `<linux/blkzoned.h>` і команда `blkzone` для тих самих дій з оболонки. Біля кожного важеля стоїть версія ядра, у якій він з'явився, — інтерфейс збирали десять років по частинах, і код, написаний під 4.10, на сучасному ядрі бачить хіба третину картини.

## Числа черги

Файли в `/sys/block/<dev>/queue/` — звичайні текстові, по одному значенню в кожному, усі лише на читання ([модель sysfs](root:sys-unix/sysfs-device-model): ядро показує свої об'єкти каталогами, а їхні поля — файлами, які читає `cat`).

| Файл | Одиниця | З ядра | Що означає |
|---|---|---|---|
| `zoned` | слово | 4.10 | `none` або `host-managed`. Свого часу тут могло стояти ще `host-aware`; ядро цю модель прибрало й показує такі носії як `none` — разом із керованими самим носієм |
| `chunk_sectors` | сектор (512 Б) | 4.10 | розмір зони. **Те саме поле в незонованого RAID означає смугу масиву**, тож читати його осмислено лише разом із `zoned` |
| `nr_zones` | штука | 4.20 | скільки зон усього; у незонованого — 0 |
| `max_open_zones` | штука | 5.9 | стеля на зони у станах `EXP_OPEN` + `IMP_OPEN`; 0 — межі немає |
| `max_active_zones` | штука | 5.9 | стеля на `EXP_OPEN` + `IMP_OPEN` + `CLOSED`; 0 — межі немає |
| `zone_append_max_bytes` | байт | 5.8 | найбільший дозапис у зону однією операцією; у незонованого — 0 |
| `zone_write_granularity` | байт | 5.12 | вирівнювання, якого вимагає запис у послідовну зону; у незонованого — 0 |

Розміру зони в байтах тут немає навмисно: `chunk_sectors` рахується в 512-байтових секторах незалежно від логічного блока пристрою, і множити доводиться самому. Останню зону носія ця величина може й не описувати — вона буває коротшою за решту. `zone_write_granularity` на черепичному диску дорівнює логічному блоку, а на твердотільному носії буває більшим за нього — запис, не вирівняний на це число, пристрій відхилить, хоча за розміром сектора він законний. Решту чисел черги зібрано [окремою таблицею](root:sys-unix/block-device-model/api-queue-attributes.md).

```sh
$ d=/sys/block/nullb0/queue
$ for f in zoned chunk_sectors nr_zones max_open_zones max_active_zones \
           zone_append_max_bytes zone_write_granularity; do
      printf '%-24s %s\n' "$f" "$(cat $d/$f)"
  done
zoned                    host-managed
chunk_sectors            524288
nr_zones                 32
max_open_zones           14
max_active_zones         14
zone_append_max_bytes    2097152
zone_write_granularity   4096
```

Нуль у `max_open_zones` читається не як «жодної відкритої зони не можна», а як «пристрій межі не оголосив».

Ще одна межа інтерфейсу видна не в числах, а в іменах пристроїв: усе перелічене далі працює тільки з носієм цілком. Створити розділ на зонованому пристрої ядро відмовляється (`ENXIO` із `add_partition()`), а знайдену на ньому таблицю розділів лишає без уваги, попередивши в журналі, — бо розділ розрізав би зону навпіл, а половини зони не буває. Тож дескриптор скрізь відкривають на `/dev/sda`, ніколи на `/dev/sda1`.

## Вісім запитів `ioctl`

Заголовок один — `<linux/blkzoned.h>`; дескриптор — сам блоковий пристрій, не файл на ньому ([керуючий канал `ioctl`](root:sys-unix/ioctl-interface): номер запиту кодує напрямок і тип третього аргументу, а зміст того аргументу описує кожен запит по-своєму).

| Запит | Код | Аргумент | З ядра |
|---|---|---|---|
| `BLKREPORTZONE` | `_IOWR(0x12, 130, …)` | `struct blk_zone_report *` | 4.10 |
| `BLKRESETZONE` | `_IOW(0x12, 131, …)` | `struct blk_zone_range *` | 4.10 |
| `BLKGETZONESZ` | `_IOR(0x12, 132, __u32)` | `__u32 *` — розмір зони в секторах | 4.20 |
| `BLKGETNRZONES` | `_IOR(0x12, 133, __u32)` | `__u32 *` — скільки зон усього | 4.20 |
| `BLKOPENZONE` | `_IOW(0x12, 134, …)` | `struct blk_zone_range *` | 5.5 |
| `BLKCLOSEZONE` | `_IOW(0x12, 135, …)` | `struct blk_zone_range *` | 5.5 |
| `BLKFINISHZONE` | `_IOW(0x12, 136, …)` | `struct blk_zone_range *` | 5.5 |
| `BLKREPORTZONESV2` | `_IOWR(0x12, 142, …)` | `struct blk_zone_report *` | 6.19 |

Перші два роки інтерфейс складався з двох дієслів: подивитися й скинути. Розмір зони та їхню кількість доводилося вигрібати зі звіту, доки 4.20 не дала їх окремими запитами. Явних відкриття, закриття й завершення не було до 5.5 — тобто ресурсом пристрою три роки керували тільки опосередковано, самим записом. `BLKREPORTZONESV2` відрізняється від старшого брата одним: поле `flags` він читає й на вході, і прапорець `BLK_ZONE_REP_CACHED` (`1U << 31`) просить віддати те, що ядро вже знає, не питаючи пристрій.

Ця відмінність важить більше, ніж здається, бо звіт — справжня команда до носія щоразу, а не погляд у пам'ять. На черепичному диску місткістю 20 ТБ із зонами по 256 МіБ зон близько сімдесяти п'яти тисяч, а опис кожної — 64 байти: повний обхід означає майже 5 МіБ описів і стільки команд, скільки разів доведеться наповнювати буфер. Ядро тим часом веде свій облік зон, бо без нього не встерегло б порядку запису, — кешований звіт просто дозволяє це запитати.

## Структури

```c
struct blk_zone_range {
        __u64 sector;         /* початок діапазону, 512-Б сектори */
        __u64 nr_sectors;     /* довжина діапазону */
};

struct blk_zone_report {
        __u64 sector;         /* вхід: звідки почати обхід */
        __u32 nr_zones;       /* вхід: скільки описів уміщає буфер,
                                 вихід: скільки ядро туди поклало */
        __u32 flags;          /* вихід: BLK_ZONE_REP_CAPACITY (з 5.9) */
        struct blk_zone zones[];
};

struct blk_zone {
        __u64 start;          /* перший сектор зони */
        __u64 len;            /* розмір зони, степінь двійки */
        __u64 wp;             /* вказівник запису */
        __u8  type;           /* enum blk_zone_type */
        __u8  cond;           /* enum blk_zone_cond */
        __u8  non_seq;        /* у зоні є непослідовно записане */
        __u8  reset;          /* пристрій радить скинути зону */
        __u8  resv[4];
        __u64 capacity;       /* придатне до запису, з 5.9 */
        __u8  reserved[24];
};
```

Опис зони має рівно 64 байти в кожній версії ядра: до 5.9 хвіст був суцільним `reserved[32]`, потім із нього вирізали `capacity`. Тому старий двійковий код читає нові ядра без перекомпіляції, а новий на старому ядрі побачить у `capacity` нуль. Саме для цього й потрібен прапорець — `capacity` можна брати лише тоді, коли ядро підняло `BLK_ZONE_REP_CAPACITY` у `flags` звіту; інакше придатною треба вважати всю `len`. Сучасні ядра ставлять прапорець завжди, зокрема й для черепичних дисків, де ємність дорівнює розмірові.

Поля `non_seq` і `reset` мають сенс тільки для носіїв, обізнаних із хостом: перше означає, що зону писали не по порядку й пристрій пішов на приховану трансляцію, друге — що він просить скидання, поки не стало гірше.

## Тип і стан зони

| `enum blk_zone_type` | Знач. | |
|---|---|---|
| `BLK_ZONE_TYPE_CONVENTIONAL` | `0x1` | звичайна зона: вказівника немає, писати можна куди завгодно |
| `BLK_ZONE_TYPE_SEQWRITE_REQ` | `0x2` | послідовний запис **вимагається** — зона пристрою, керованого хостом |
| `BLK_ZONE_TYPE_SEQWRITE_PREF` | `0x3` | послідовний запис **бажаний** — зона пристрою, обізнаного з хостом |

| `enum blk_zone_cond` | Знач. | |
|---|---|---|
| `BLK_ZONE_COND_NOT_WP` | `0x0` | вказівника немає — єдиний стан звичайної зони |
| `BLK_ZONE_COND_EMPTY` | `0x1` | порожня, вказівник на початку |
| `BLK_ZONE_COND_IMP_OPEN` | `0x2` | відкрита неявно — самим записом |
| `BLK_ZONE_COND_EXP_OPEN` | `0x3` | відкрита явно — командою `BLKOPENZONE` |
| `BLK_ZONE_COND_CLOSED` | `0x4` | закрита: вказівник не на початку, буфера пристрій під неї не тримає |
| `BLK_ZONE_COND_READONLY` | `0xD` | лише читання |
| `BLK_ZONE_COND_FULL` | `0xE` | повна |
| `BLK_ZONE_COND_OFFLINE` | `0xF` | відключена, даних у ній нема |
| `BLK_ZONE_COND_ACTIVE` | `0xFF` | з 6.19, лише в кешованому звіті: «неявно відкрита, явно відкрита або закрита» — ядро з пам'яті не розрізняє цих трьох, точну відповідь дасть тільки пристрій |

Разом ці два переліки дають короткий рецепт відновлення після падіння. Пройти звіт; зони типу `0x1` пропустити — до них питань немає; серед послідовних відібрати ті, чий стан не `EMPTY` і не `FULL`, — саме в них писали в мить зупинки; і продовжувати рівно з `wp`, а не з того місця, яке пам'ятає власний журнал. Пристрій тут остання інстанція: усе, що система вважала записаним за `wp`, до носія не дійшло.

## Мінімальний виклик

```c
#include <linux/blkzoned.h>
#include <sys/ioctl.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>

int fd = open("/dev/nullb0", O_RDWR);      /* керуючі запити вимагають запису */

__u32 zone_sectors, zone_count;
ioctl(fd, BLKGETZONESZ,  &zone_sectors);
ioctl(fd, BLKGETNRZONES, &zone_count);

/* буфер = шапка плюс стільки описів, скільки хочемо дістати за раз */
const __u32 want = 8;
struct blk_zone_report *rep = malloc(sizeof(*rep) + want * sizeof(struct blk_zone));

rep->sector   = 0;                         /* обхід від початку пристрою */
rep->nr_zones = want;
rep->flags    = 0;

if (ioctl(fd, BLKREPORTZONE, rep) == 0) {
        int cap_ok = rep->flags & BLK_ZONE_REP_CAPACITY;

        for (__u32 i = 0; i < rep->nr_zones; i++) {      /* уже СКІЛЬКИ віддали */
                struct blk_zone *z = &rep->zones[i];

                printf("%llu: тип=%#x стан=%#x зайнято=%llu придатно=%llu\n",
                       z->start, z->type, z->cond,
                       z->wp - z->start,
                       cap_ok ? z->capacity : z->len);
        }
}

/* скинути другу зону */
struct blk_zone_range r = { .sector = zone_sectors, .nr_sectors = zone_sectors };
ioctl(fd, BLKRESETZONE, &r);
```

Три речі, на яких спотикаються найчастіше. Діапазон у `blk_zone_range` задають **у секторах і рівно по межах зон**: `sector` мусить бути початком зони, `nr_sectors` — кратним її розмірові, інакше `EINVAL`. Скидання від сектора 0 на всю місткість пристрою ядро само перетворює на одну команду «скинути все» замість тисяч окремих. І `nr_zones` у звіті — поле подвійного призначення: на вході це місткість буфера, на виході — скільки описів ядро туди справді поклало, і воно буває меншим за просте.

| Помилка | Коли |
|---|---|
| `ENOTTY` | пристрій не зонований (`zoned` = `none`), ядро зібране без `CONFIG_BLK_DEV_ZONED`, або дескриптор указує не на блоковий пристрій |
| `EBADF` | керуючий запит (`RESET`, `OPEN`, `CLOSE`, `FINISH`) на дескрипторі, відкритому без права запису |
| `EINVAL` | нульовий вказівник аргументу, `nr_zones` = 0 у звіті або діапазон не по межах зон |
| `EFAULT` | буфер не читається чи не записується за поданою адресою |
| `ETOOMANYREFS` | пристрій відмовив: перевищено межу відкритих зон |
| `EOVERFLOW` | пристрій відмовив: перевищено межу активних зон |

Останні дві виглядають дико для операції над диском — і саме тому їх варто запам'ятати: жодного стосунку до посилань чи переповнення числа тут немає, це блоковий шар перекладає два зонові статуси в найближчі вільні коди помилок.

## `blkzone(8)`

Утиліта з util-linux нічого не вигадує понад перелічене — вона просто перекладає ті самі запити на командний рядок.

| Команда | Що робить |
|---|---|
| `blkzone report <dev>` | `BLKREPORTZONE`: рядок на зону — початок, довжина, ємність, вказівник, стан, тип |
| `blkzone capacity <dev>` | сума ємностей усіх зон у секторах, тобто скільки на носії справді придатного місця |
| `blkzone reset <dev>` | `BLKRESETZONE` |
| `blkzone open` · `close` · `finish` | `BLKOPENZONE` · `BLKCLOSEZONE` · `BLKFINISHZONE` |

| Ключ | Що робить |
|---|---|
| `-o, --offset <сектор>` | з якої зони починати; типово 0 |
| `-l, --length <сектори>` | скільки секторів охопити; несумісний з `--count` |
| `-c, --count <n>` | скільки зон охопити; несумісний з `--length` |
| `-f, --force` | дозволити зміну стану зон на пристрої, який зайнятий системою |
| `-v, --verbose` | скільки зон віддано у звіті або який діапазон скинуто |

Без `--force` команди, що міняють стан, на змонтованому пристрої працювати відмовляються, і цю обережність варто лишити ввімкненою: скидання зони не питає, чиї дані в ній лежали.

## Зонований пристрій із повітря

Черепичного диска для дослідів не треба: `null_blk` робить зонований пристрій у пам'яті, і всі перелічені важелі на ньому справжні.

```sh
$ sudo modprobe null_blk zoned=1 size=8192 zone_size=256 zone_capacity=200 \
                         zone_nr_conv=4 zone_max_open=14 zone_max_active=14
$ sudo blkzone report -c 4 /dev/nullb0
```

| Параметр | Типово | Що задає |
|---|---|---|
| `zoned=1` | 0 | зонований режим; вимагає `CONFIG_BLK_DEV_ZONED` |
| `size=<МіБ>` | 250 | місткість пристрою |
| `zone_size=<МіБ>` | 256 | розмір зони; **лише степінь двійки** |
| `zone_capacity=<МіБ>` | дорівнює `zone_size` | придатна частина зони — так у кінці кожної зони роблять дірку |
| `zone_nr_conv=<n>` | 0 | скільки перших зон зробити звичайними |
| `zone_max_open=<n>` | 0 — межі немає | що показувати в `max_open_zones` і за чим стежити |
| `zone_max_active=<n>` | 0 — межі немає | те саме для `max_active_zones` |
| `zone_append_max_sectors=<n>` | без обмеження | розмір дозапису в секторах; **0 вимикає апаратний дозапис** і змушує блоковий шар удавати його звичайними записами |
| `zone_full=1` | 0 | підняти всі послідовні зони одразу повними |

Два останні важелі варті окремої уваги того, хто перевіряє чужий код. `zone_capacity`, менша за `zone_size`, ловить припущення «зона придатна до запису вся»; `zone_append_max_sectors=0` ловить припущення «апаратний дозапис у зону є завжди». Обидва — найчастіші помилки в коді, який писали й пробували на одному-єдиному пристрої.
