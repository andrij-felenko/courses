# ⚙️ Практична реалізація паралельного обробника файлових дерев мовами C та C++

Обробка сотень тисяч та мільйонів файлів на системному рівні вимагає узгодженого поєднання трьох низькорівневих механізмів: швидкого рекурсивного обходу структури каталогів віртуальної файлової системи (VFS), формування безпечних пакетів аргументів у межах лімітів ядра `ARG_MAX` та оркестрації пулу паралельних процесів-виконавців.

Спроба розв'язати цю задачу наївними скриптами командної оболонки або неконтрольованими конвеєрами призводить або до аварійного завершення через вичерпання пам'яті стеку параметрів (`E2BIG`), або до вичерпання пулу дескрипторів (`EMFILE`), або до критичних вразливостей класу TOCTOU (Time-of-Check to Time-of-Use) через підміну символьних посилань.

Нижче наведено повний інженерний розбір та вихідний код системного генератора-диспетчера мовами C та C++, який об'єднує функції утиліт `find` та `xargs -0 -P` у межах єдиного високопродуктивного процесу.

## Чому інтегрований системний диспетчер ефективніший за конвеєр оболонки

Класичний підхід Unix передбачає розділення задачі на два незалежні процеси, з'єднані анонімним каналом:

```sh
find /var/log -type f -name "*.log" -print0 | xargs -0 -n 64 -P 4 gzip
```

Хоча такий конвеєр є виразним та модульним, на рівні взаємодії з ядром операційної системи він створює відчутні накладні витрати:

1. **Накладні витрати каналу (Pipe IPC) та подвійне копіювання:** Генератор `find` вичитує системні структури записів каталогів ядра `linux_dirent64`, перетворює їх у потік байтів із NUL-термінаторами і записує через системний виклик `write()` у буфер каналу ядра (розміром 64 KB). Процес `xargs` зчитує цей потік через `read()`, виконує побайтовий пошук символів `\0`, виділяє динамічну пам'ять та реконструює масив рядків. Це спричиняє постійні перемикання контексту між простором користувача та простором ядра (Context Switches), а також забруднює кеш процесора (L1/L2 Cache Pollution).
2. **Дублювання керування пам'яттю:** Обидва процеси паралельно алокують пам'ять під ті самі рядкові шляхи у власних адресних просторах.
3. **Опосередкований контроль життєвого циклу воркерів:** Оболонка та `xargs` не мають прямого доступу до дескрипторів файлів та контексту сканування, що ускладнює обробку помилок доступу на льоту, синхронізацію введення-виведення та гнучке динамічне регулювання розміру пакетів.
4. **Конкуренція за дискову підсистему:** Якщо обхід каталогу та читання файлів воркерами не скоординовані, неконтрольоване породження процесів на повільних накопичувачах HDD спричиняє перевантаження черги запитів (Head Thrashing).

Власна системна реалізація утиліти об'єднує ітерування по дереву VFS та диспетчеризацію завдань у єдиному адресному просторі:

```
                  +----------------------------------------------+
                  |           Єдиний процес-диспетчер            |
                  |                                              |
                  |  [ Сканування VFS: opendir / readdir / stat ]|
                  |                       |                      |
                  |             Відфільтровані шляхи             |
                  |                       v                      |
                  |  [ Накопичувальний буфер пакетів: argv[] ]   |
                  |                       |                      |
                  |         Пакет заповнено (64 файли)           |
                  |                       v                      |
                  |      [ Диспетчер пулу: fork() + execvp() ]   |
                  +----------------------------------------------+
                               /          |          \
                              /           |           \
                    +------------+  +------------+  +------------+
                    | Воркер 1   |  | Воркер 2   |  | Воркер 3   |
                    | (PID 1042) |  | (PID 1043) |  | (PID 1044) |
                    | gzip p1..  |  | gzip p2..  |  | gzip p3..  |
                    +------------+  +------------+  +------------+
```

Така архітектура усуває проміжний шар IPC, дозволяє формувати системний масив покажчиків `argv[]` безпосередньо в оперативній пам'яті процесу та забезпечує прямий моніторинг життєвого циклу процесів-нащадків через системний виклик `waitpid()`.

## Захист від вразливостей TOCTOU та атак через символьні посилання

Головна небезпека під час автоматизованого обходу файлової системи — стан гонитви класу TOCTOU (Time-of-Check to Time-of-Use). Ця вразливість виникає тоді, коли між моментом перевірки атрибутів файлу або каталогу та моментом виконання дії над ним стан файлової системи змінюється стороннім процесом.

### Механіка атаки підміни вузла (Symlink Substitution)

Уявімо системну утиліту очищення або архівації, яка працює у спільному каталозі (наприклад, `/tmp/scratch/`) і перевіряє об'єкти за їхніми абсолютними рядковими шляхами:

1. Програма знаходить запис `/tmp/scratch/session/report.log`.
2. Програма викликає системний виклик `stat("/tmp/scratch/session/report.log", &st)` і переконується, що це звичайний файл, який належить поточному користувачу.
3. У короткий проміжок часу (вікно гонитви) зловмисник видаляє каталог `session` і створює замість нього символьне посилання на конфіденційний системний каталог: `ln -s /etc/ /tmp/scratch/session`.
4. Програма виконує дію над цільовим шляхом: відкриває файл на запис або викликає команду очищення `unlink("/tmp/scratch/session/shadow")`. Операція застосовується до `/etc/shadow`.

Якщо обхід використовує функції, що приймають абсолютні рядкові шляхи, ядро Linux змушене щоразу розв'язувати шлях від кореня (`/`) або поточного робочого каталогу заново. На кожному проміжному компоненті шляху (`tmp` -> `scratch` -> `session` -> `report.log`) існує ймовірність підміни каталогу на символьне посилання.

### Дескрипторно-орієнтований обхід через сімейство системних викликів `*at`

Для повного усунення атак класу TOCTOU сучасні стандарти POSIX та ядро Linux надають сімейство системних викликів, що оперують дескрипторами каталогів:

| Класичний системний виклик | Безпечний дескрипторний аналог | Призначення |
|---|---|---|
| `open(path, flags)` | `openat(dirfd, path, flags)` | Відкриття файлу відносно закріпленого дескриптора каталогу |
| `stat(path, buf)` | `fstatat(dirfd, path, buf, flags)` | Отримання метаданих вузла без повторного розв'язання повного шляху |
| `unlink(path)` | `unlinkat(dirfd, path, flags)` | Безпечне атомарне видалення файлу з каталогу |
| `opendir(path)` | `fdopendir(dirfd)` | Створення потоку каталогу `DIR*` із уже відкритого дескриптора |

Коли каталог відкрито через `openat(AT_FDCWD, path, O_RDONLY | O_DIRECTORY | O_CLOEXEC)`, отриманий дескриптор `dirfd` надійно фіксує конкретний об'єкт dentry та індексний дескриптор inode у кеші VFS ядра Linux. Навіть якщо батьківський або сусідній каталог буде перейменовано, видалено або замінено на символьне посилання, дескриптор `dirfd` продовжує вказувати на первинний фізичний каталог.

Критичні системні прапорці безпеки:

- `O_NOFOLLOW` (для `open` / `openat`): якщо останній компонент шляху є символьним посиланням, системний виклик негайно завершується з помилкою `ELOOP`, унеможливлюючи перехід за посиланням.
- `AT_SYMLINK_NOFOLLOW` (для `fstatat` / `unlinkat`): системний виклик зчитує метадані або видаляє саме символьне посилання, а не об'єкт, на який воно вказує (аналог поведінки `lstat`).
- `O_CLOEXEC` (Close-on-Exec): гарантує, що дескриптор автоматично закриється ядром під час системного виклику `execve()`, запобігаючи витоку відкритих дескрипторів у дочірні процеси.
- `openat2()` з прапорцями структури `struct open_how`: у сучасному ядрі Linux (версії 5.6+) прапорець `RESOLVE_NO_SYMLINKS` забороняє розіменування будь-яких символьних посилань на всіх проміжних рівнях шляху, `RESOLVE_BENEATH` гарантує, що шлях не вийде за межі піддерева відкритого каталогу `dirfd`, а `RESOLVE_NO_MAGICLINKS` блокує втечу через магічні посилання `/proc/[pid]/fd/`.

Приклад безпечного дескрипторного відкриття файлу:

:::tabs
```c
int dir_fd = openat(AT_FDCWD, "/tmp/scratch", O_RDONLY | O_DIRECTORY | O_CLOEXEC);
if (dir_fd != -1) {
    /* Відкриття файлу строго всередині каталогу без переходу за symlink */
    int file_fd = openat(dir_fd, "report.log", O_RDONLY | O_NOFOLLOW | O_CLOEXEC);
    if (file_fd != -1) {
        /* Безпечні операції з дескриптором файлу */
        close(file_fd);
    }
    close(dir_fd);
}
```
```cpp
struct UniqueFd {
    int fd{-1};
    explicit UniqueFd(int descriptor) : fd(descriptor) {}
    ~UniqueFd() { if (fd != -1) ::close(fd); }
    UniqueFd(const UniqueFd&) = delete;
    UniqueFd& operator=(const UniqueFd&) = delete;
    UniqueFd(UniqueFd&& other) noexcept : fd(other.fd) { other.fd = -1; }
    UniqueFd& operator=(UniqueFd&& other) noexcept {
        if (this != &other) {
            if (fd != -1) ::close(fd);
            fd = other.fd;
            other.fd = -1;
        }
        return *this;
    }
    operator int() const noexcept { return fd; }
};

UniqueFd dir_fd(::openat(AT_FDCWD, "/tmp/scratch", O_RDONLY | O_DIRECTORY | O_CLOEXEC));
if (dir_fd != -1) {
    UniqueFd file_fd(::openat(dir_fd, "report.log", O_RDONLY | O_NOFOLLOW | O_CLOEXEC));
    if (file_fd != -1) {
        // Безпечні операції з дескриптором файлу
    }
}
```
:::

Утиліта, що демонструється нижче, використовує системний виклик `lstat()` для перевірки атрибутів безпосереднього вузла без розіменування посилань, забезпечуючи фізичний обхід (аналог прапорця `-P` у `find`).

## Захист від нескінченних циклів та графів символьних посилань

У файлових системах Unix створення жорстких посилань на каталоги суворо заборонене на рівні ядра (системний виклик `link()` повертає помилку `EPERM`), оскільки жорсткі посилання перетворили б деревоподібну ієрархію на загальний граф із можливими циклами, порушуючи коректність алгоритмів підрахунку посилань та звільнення пам'яті.

Однак символьні посилання (`symlinks`) не мають такого обмеження. Користувач або програма може легко створити циклічну структуру:

```sh
mkdir -p /tmp/tree/sub
ln -s /tmp/tree /tmp/tree/sub/infinite_loop
```

Якщо утиліта обходу виконує логічне розіменування посилань (режим `-L`) або зустрічає символьне посилання на каталог під час рекурсії, наївний алгоритм потрапляє у нескінченний цикл, що завершується вичерпанням пам'яті стеку (Stack Overflow) або вичерпанням ліміту відкритих дескрипторів (`EMFILE`).

### Чому одного номера inode недостатньо

Поширена помилка проєктування полягає у спробі ідентифікувати відвіданий каталог виключно за його номером індексного дескриптора `ino_t`.

Номер inode є строго унікальним **лише в межах однієї файлової системи (одного блокового пристрою)**. Якщо операційна система містить кілька точок монтування (наприклад, коренева файлова система `/` на пристрої `/dev/nvme0n1p2`, окремий розділ `/var` на `/dev/sda1` та тимчасова файлова система `/tmp` на `tmpfs`), номери inode на різних пристроях неминуче перетинаються. Наприклад, кореневий каталог кожного розділу ext4 традиційно має номер `st_ino = 2`.

Для гарантовано однозначної глобальної ідентифікації об'єкта в операційній системі необхідно використовувати кортеж із двох системних полів:
1. `st_dev` (тип `dev_t`) — ідентифікатор пристрою (Major та Minor номери пристрою змонтованої ФС).
2. `st_ino` (тип `ino_t`) — номер індексного дескриптора файлу чи каталогу на даному пристрої.

### Алгоритм хешування пар `(dev_t, ino_t)`

Для виявлення циклів застосовується хеш-таблиця активних вузлів. Існує дві інженерні стратегії:

1. **Стек активних предків (Active Ancestor Set):** Відстежуються лише ті каталоги, які знаходяться у поточному ланцюжку рекурсивного спуску від кореня до поточного вузла. Це запобігає нескінченним циклам, але дозволяє відвідувати один і той самий каталог з різних незалежних гілок, якщо дерево містить кілька посилань на один вузол (Directed Acyclic Graph, DAG).
2. **Глобальна множина відвіданих вузлів (Global Visited Set):** Зберігає всі коли-небудь відвідані каталоги за весь час роботи утиліти, повністю виключаючи повторну обробку ромбоподібних структур.

Комбінація полів `dev_t` та `ino_t` ефективно змішується 64-бітним хешером для швидкого пошуку в хеш-таблиці:

:::tabs
```c
#include <stdint.h>
#include <sys/types.h>

typedef struct {
    dev_t dev;
    ino_t ino;
} NodeId;

static inline uint64_t hash_node_id(dev_t dev, ino_t ino) {
    /* Змішувач SplitMix64 над упакованими полями dev_t та ino_t */
    uint64_t h = ((uint64_t)dev << 32) ^ (uint64_t)ino;
    h ^= h >> 33;
    h *= 0xff51afd7ed558ccdULL;
    h ^= h >> 33;
    h *= 0xc4ceb9fe1a85ec53ULL;
    h ^= h >> 33;
    return h;
}
```
```cpp
#include <cstdint>
#include <sys/types.h>
#include <unordered_set>

struct NodeId {
    dev_t dev;
    ino_t ino;

    bool operator==(const NodeId& other) const noexcept {
        return dev == other.dev && ino == other.ino;
    }
};

struct NodeIdHash {
    std::size_t operator()(const NodeId& node) const noexcept {
        std::uint64_t h = (static_cast<std::uint64_t>(node.dev) << 32) ^ static_cast<std::uint64_t>(node.ino);
        h ^= h >> 33;
        h *= 0xff51afd7ed558ccdULL;
        h ^= h >> 33;
        h *= 0xc4ceb9fe1a85ec53ULL;
        h ^= h >> 33;
        return static_cast<std::size_t>(h);
    }
};

// Множина активних вузлів для запобігання циклам
std::unordered_set<NodeId, NodeIdHash> visited_ancestors;
```
:::

## Механізм передачі аргументів, буфер NUL-розділювачів та ліміти ядра

Передавання імен файлів між процесами в Unix містить неочевидну пастку: єдиними забороненими байтами в іменах файлів POSIX є ASCII NUL (`0x00`) та слеш (`0x2F`, `/`). Будь-які інші символи — пробіли, символи табуляції, перенесення рядків `\n`, лапки `'` та `"`, дефіси на початку імені (наприклад, `-rf`) — є абсолютно легальними.

### Чому текстовий розбір вразливий

Якщо утиліта формує строковий потік, розділений пробілами або переносом рядка `\n`, виникає неоднозначність розбору (parsing ambiguity):

```
Файл на диску: "audit report 2026.log"
Розбір за пробілом -> аргумент 1: "audit", аргумент 2: "report", аргумент 3: "2026.log"

Файл на диску: "test\nbackup.log"
Розбір за \n       -> два спотворені рядки замість одного цілісного імені
```

Пряме формування масиву `char *argv[]` у пам'яті процесу повністю усуває необхідність текстового розбору: кожен покажчик масиву посилається на окремий блок пам'яті з NUL-термінованим рядком. Під час системного виклику `execve()` ядро копіює ці байти безпосередньо у стек нового процесу як цілісні аргументи.

### Розрахунок обмежень пам'яті ядра (`ARG_MAX` та `MAX_ARG_STRLEN`)

Під час створення нового образу процесу ядро Linux розміщує масив аргументів `argv[]`, масив оточення `envp[]` та допоміжний вектор ELF у виділеній верхній області адресного простору стеку процесу:

```
+-------------------------------------------------------------+
| 0x7FFFFFFFFFFF (Верхівка віртуальної пам'яті процесу)       |
+-------------------------------------------------------------+
| Рядки аргументів та змінних оточення (суцільний блок байтів)|
+-------------------------------------------------------------+
| Вектор допоміжної інформації ELF (Auxiliary Vector elf_info)|
+-------------------------------------------------------------+
| Покажчики char *envp[] (завершені покажчиком NULL)          |
+-------------------------------------------------------------+
| Покажчики char *argv[] (завершені покажчиком NULL)          |
+-------------------------------------------------------------+
| Лічильник аргументів int argc                               |
+-------------------------------------------------------------+
| Стек викликів функцій процесу (росте вниз <-)               |
+-------------------------------------------------------------+
```

Сумарний розмір цієї структури обмежується константою ядра:

```
Ліміт_пам'яті_параметрів = min(RLIMIT_STACK / 4, 3/4 * _STK_LIM)
```

При типовому системному ліміті стеку 8 МБ максимальний доступний обсяг для передачі параметрів становить близько 2 МБ. Окремий аргумент не може перевищувати ліміт `MAX_ARG_STRLEN` (128 KB, тобто 32 сторінки пам'яті по 4 KB).

Формування пакетів фіксованого розміру (константа `BATCH_CAPACITY = 64` файли на один запуск воркера) дає такі інженерні переваги:

1. **Скорочення накладних витрат ядра:** замість 64 окремих викликів `fork()` та `execve()` створюється лише 1 процес, що зменшує навантаження на планувальник на 98.4%.
2. **Гарантія безпеки за обсягом пам'яті:** 64 повні шляхи (навіть за максимальної довжини шляху Linux `PATH_MAX = 4096` байтів) займають щонайбільше `64 · 4096 = 262 144` байти (~256 KB), що у 8 разів менше за критичний поріг `ARG_MAX`.
3. **Передбачуваність споживання пам'яті:** пам'ять самого диспетчера залежить виключно від поточної глибини дерева каталогів `O(depth)`, а не від загальної кількості мільйонів файлів на диску.

## Детальний розбір реалізації мовою C

Реалізація мовою C (`c/main.c`) демонструє пряму роботу із системними структурами ядра Linux та низькорівневе керування ресурсами процесу.

### 1. Організація буфера пакетування `BatchBuffer`

Структура `BatchBuffer` спроєктована для мінімізації зайвих алокацій:

:::tabs
```c
typedef struct {
    char *items[BATCH_CAPACITY + 2];
    int count;
} BatchBuffer;
```
```cpp
// У C++ стан буфера накопичується у динамічному векторі
std::vector<std::string> current_batch;
current_batch.reserve(batch_size);
```
:::

Розмір масиву покажчиків складає `BATCH_CAPACITY + 2` комірки:
- `items[0]` — зберігає покажчик на ім'я цільової команди (наприклад, `"gzip"`).
- `items[1]` ... `items[BATCH_CAPACITY]` — зберігають покажчики на динамічно виділені рядки повних шляхів знайдених файлів.
- `items[count]` — зарезервована позиція для обов'язкового кінцевого покажчика `NULL`, який сигналізує функції `execvp()` про кінець списку аргументів.

Функція `init_batch()` копіює назву виконуваної команди через `strdup()` у нульову позицію та встановлює лічильник `count = 1`. 

Функція `free_batch_payload()` вивільняє пам'ять накопичених шляхів файлів (`items[1]` ... `items[count-1]`) через виклик `free()`, залишаючи рядок команди в `items[0]` недоторканим, і скидає лічильник `count` назад у значення `1`.

### 2. Керування пулом процесів та запобігання зомбі (`drain_workers`)

Функція `drain_workers()` здійснює взаємодію з планувальником ядра через системний виклик `waitpid()`:

:::tabs
```c
static void drain_workers(int *active_workers, int block_for_slot) {
    while (*active_workers > 0) {
        int status = 0;
        int flags = block_for_slot ? 0 : WNOHANG;
        pid_t pid = waitpid(-1, &status, flags);
        if (pid > 0) {
            (*active_workers)--;
            if (block_for_slot) break;
        } else {
            break;
        }
    }
}
```
```cpp
void WorkerPool::reap_one(bool blocking) {
    int status = 0;
    int flags = blocking ? 0 : WNOHANG;
    pid_t pid = ::waitpid(-1, &status, flags);
    if (pid > 0) {
        --active_workers_;
    }
}
```
:::

Механіка опитування має два взаємодоповнюючі режими:

- **Неблокуюче очищення (`block_for_slot = 0`):** прапорець `WNOHANG` наказує ядру негайно повернути керування. Якщо будь-який дочірній процес уже завершився, ядро вивільняє його запис `task_struct` із таблиці процесів ОС, повертає його PID, а диспетчер зменшує лічильник `*active_workers`. Якщо активні воркери ще працюють, `waitpid()` повертає `0`, і диспетчер продовжує обхід дерева без затримок.
- **Блокуюче очікування слота (`block_for_slot = 1`):** прапорець `0` переводить батьківський процес у стан сну `TASK_INTERRUPTIBLE`. Диспетчер призупиняється доти, доки один із воркерів не завершить виконання та не надішле сигнал `SIGCHLD`. Щойно один слот звільняється, диспетчер прокидається і завершує функцію.

### 3. Безпечний запуск воркера (`dispatch_batch`)

Функція `dispatch_batch()` перевіряє заповненість пулу: якщо кількість активних воркерів досягла ліміту `MAX_PARALLEL_WORKERS` (4 паралельні процеси), диспетчер викликає `drain_workers(..., 1)`, очікуючи звільнення щонайменше одного слота.

Далі виконується системний виклик `fork()`:
- **У дочірньому процесі (`pid == 0`):** викликається системний виклик `execvp(b->items[0], b->items)`, який повністю замінює образ дочірнього процесу на виконуваний бінарник утиліти `gzip`. Якщо виклик зазнає невдачі (наприклад, утиліту `gzip` не встановлено в системі), виконується виклик `_exit(127)`. Використання саме системного виклику `_exit()`, а не функції стандартної бібліотеки `exit()`, є критично важливим: `_exit()` не скидає буфери введення-виведення `stdio` батьківського процесу та не викликає зареєстровані обробники `atexit()`, запобігаючи пошкодженню стану пам'яті.
- **У батьківському процесі (`pid > 0`):** збільшується лічильник `active_workers`, викликається `free_batch_payload()` для очищення пам'яті відправленого пакета, і диспетчер повертається до сканування.

### 4. Рекурсивне сканування дерева (`traverse_tree`)

Функція `traverse_tree()` здійснює обхід VFS:

1. Відкриває каталог через виклик `opendir(dir_path)`.
2. У циклі зчитує елементи через `readdir(dir)`.
3. Обов'язково фільтрує псевдокаталоги `.` (поточний) та `..` (батьківський) за допомогою `strcmp()`, що запобігає нескінченній рекурсії.
4. Формує повний шлях через `snprintf(full_path, sizeof(full_path), "%s/%s", ...)`.
5. Зчитує тип вузла через системний виклик `lstat(full_path, &st)`.
6. Якщо `S_ISDIR(st.st_mode)` — рекурсивно спускається у вкладений підкаталог.
7. Якщо `S_ISREG(st.st_mode)` — перевіряє розширення через покажчик `strrchr(entry->d_name, '.')`. Якщо розширення дорівнює `".log"`, дублює рядок шляху через `strdup()` у масив `b->items`.
8. Щойно кількість елементів перевищує `BATCH_CAPACITY`, викликає `dispatch_batch()`.
9. Після завершення обходу каталогу закриває дескриптор через `closedir(dir)`.

У функції `main()` після завершення рекурсії обов'язково виконується фінальний виклик `dispatch_batch()` (для відправлення залишку файлів, якщо останній пакет містив менше ніж 64 елементи), після чого цикл `while (active_workers > 0)` очікує завершення всіх фонових воркерів.

## Детальний розбір реалізації мовою C++

Реалізація мовою C++ (`cpp/main.cpp`) вирішує ту саму задачу за допомогою сучасних ідіом безпеки пам'яті, концепції RAII (Resource Acquisition Is Initialization) та стандартної бібліотеки `std::filesystem`.

### 1. Інкапсуляція пулу процесів у класі `WorkerPool`

Клас `WorkerPool` повністю відповідає за життєвий цикл дочірніх процесів:

```cpp
class WorkerPool {
public:
    explicit WorkerPool(std::size_t max_workers) : max_workers_(max_workers) {}

    ~WorkerPool() {
        wait_all();
    }
    // ...
};
```

Критична перевага C++ — деструктор `~WorkerPool()` автоматично викликає `wait_all()`. Якщо під час роботи програми виникає виняток (наприклад, помилка виділення пам'яті `std::bad_alloc` або помилка файлової системи), процес не завершиться аварійно, залишивши після себе процеси-сироти або зомбі. Деструктор гарантовано дочекається завершення всіх активних воркерів під час розкрутки стека (stack unwinding).

### 2. Перетворення типів C++ у сумісні покажчики POSIX

Метод `spawn()` приймає типізовані структури `const std::string&` та `const std::vector<std::string>&`. Для виклику системної функції `::execvp()` формується тимчасовий плоский масив сирих покажчиків `std::vector<char*> raw_args`:

```cpp
std::vector<char*> raw_args;
raw_args.reserve(batch.size() + 2);
raw_args.push_back(const_cast<char*>(command.c_str()));
for (const auto& arg : batch) {
    raw_args.push_back(const_cast<char*>(arg.c_str()));
}
raw_args.push_back(nullptr);
```

Масив `raw_args.data()` передається у виклик `::execvp()`. Завдяки тому, що вектор рядків `batch` залишається у пам'яті батьківського процесу до завершення системного виклику `fork()`, адреси рядків `arg.c_str()` є гарантовано валідними.

У разі помилки створення процесу батьківський процес генерує типізований системний виняток:

```cpp
throw std::system_error(errno, std::generic_category(), "fork failed");
```

### 3. Ітерування по VFS через `std::filesystem::recursive_directory_iterator`

Функція `process_tree()` використовує сучасний системний ітератор:

```cpp
std::error_code ec;
auto iter = fs::recursive_directory_iterator(root, fs::directory_options::skip_permission_denied, ec);
auto end_iter = fs::recursive_directory_iterator();

for (; iter != end_iter && !ec; iter.increment(ec)) {
    if (ec) {
        ec.clear();
        continue;
    }
    const auto& entry = *iter;
    if (entry.is_regular_file(ec) && entry.path().extension() == ".log") {
        current_batch.push_back(entry.path().string());
        if (current_batch.size() >= batch_size) {
            pool.spawn(command, current_batch);
            current_batch.clear();
        }
    }
}
```

Ключові архітектурні деталі:
1. **Прапорець `skip_permission_denied`:** у разі виявлення каталогу без прав читання (помилка `EACCES`) ітератор не викидає фатальний виняток, а автоматично пропускає недоступну гілку та продовжує сканування решти дерева.
2. **Некидаюча форма `increment(ec)`:** використання об'єкта `std::error_code` замість винятків дозволяє обробляти помилки зникнення файлів або відмови доступу на рівні системного коду без накладних витрат на генерацію та перехоплення винятків у критичному циклі обходу.

## Системні пастки, крайові випадки та апаратна поведінка

Під час розгортання подібних системних диспетчерів на високонавантажених серверах необхідно враховувати низку низькорівневих крайових випадків.

### 1. Пастка зомбі-процесів та вичерпання таблиці PID

Коли дочірній процес завершує роботу через системний виклик `exit()` або сигнал, ядро Linux вивільняє майже всі його ресурси (пам'ять, відкриті дескриптори файлів, блокування). Однак структура `task_struct` процесу та його запис у таблиці процесів залишаються в системі у стані `TASK_DEAD` (відомий як стан зомбі `Z`). Це необхідно для того, щоб батьківський процес міг зчитати код повернення та статистику використання ресурсів через `waitpid()`.

Якщо диспетчер породжує тисячі процесів і не викликає `waitpid()`, у системі вичерпується пул ідентифікаторів процесів (`/proc/sys/kernel/pid_max`). Будь-який наступний системний виклик `fork()` у всій операційній системі почне повертати помилку `EAGAIN` (Resource temporarily unavailable), блокуючи роботу серверних служб.

Реалізований у наших проєктах механізм асинхронного опитування з прапорцем `WNOHANG` після кожного запуску пакета своєчасно вичищає зомбі, не дозволяючи кількості мертвих процесів перевищити ліміт воркерів.

### 2. Пастка взаємного блокування (Deadlock) через pipe-буфери виводу

Якщо дочірній процес (наприклад, утиліта компіляції чи стиснення) генерує велику кількість діагностичних повідомлень у потоки `stdout` або `stderr`, а батьківський процес під час `fork()` перенаправив їх у нечитані канали ядра `pipe`, виникає взаємне блокування (Deadlock):

```
+-------------------+           write()           +-----------------------+
|  Дочірній воркер  | --------------------------> | Буфер каналу ядра     |
|                   |                             | (Заповнено 65536 B)   |
|  [ ЗАБЛОКОВАНО ]  | <-------------------------- | [ Блокування write() ]|
+-------------------+      Очікує звільнення      +-----------------------+
          ^                                                   
          | waitpid() очікує завершення воркера               
+-------------------+                                                 
| Батько-диспетчер  |                                                 
|  [ ЗАБЛОКОВАНО ]  |                                                 
+-------------------+                                                 
```

Воркер записує дані, буфер ядра (64 KB) заповнюється, і наступний системний виклик `write()` переводить воркер у нескінченний сон. Батьківський процес диспетчера при цьому очікує завершення воркера у виклику `waitpid()`. Жодна зі сторін не може продовжити виконання.

**Інженерне розв'язання:** якщо вивід воркерів не потрібен, дочірній процес перед викликом `execvp()` повинен перенаправити стандартні потоки виводу у псевдопристрій `/dev/null`:

:::tabs
```c
int devnull = open("/dev/null", O_WRONLY);
if (devnull != -1) {
    dup2(devnull, STDOUT_FILENO);
    dup2(devnull, STDERR_FILENO);
    close(devnull);
}
```
```cpp
int devnull = ::open("/dev/null", O_WRONLY);
if (devnull != -1) {
    ::dup2(devnull, STDOUT_FILENO);
    ::dup2(devnull, STDERR_FILENO);
    ::close(devnull);
}
```
:::

Якщо ж вивід необхідний для діагностики, кожен воркер має записувати дані в окремий файл на диску (наприклад, `/tmp/worker_<pid>.log`).

### 3. Вичерпання ліміту відкритих дескрипторів (`RLIMIT_NOFILE`)

Класичний рекурсивний обхід каталогів утримує відкритим дескриптор каталогу `DIR*` на кожному рівні глибини стека викликів. На стандартних системах Linux ліміт відкритих файлів на процес становить `RLIMIT_NOFILE = 1024`.

Якщо дерево каталогів має надзвичайно глибоку вкладеність (понад 1024 рівні), черговий виклик `opendir()` поверне помилку `EMFILE` (Too many open files). Для надглибоких дерев застосовують або ітеративний обхід із власним стеком рядків (де в кожен момент часу відкрито лише один дескриптор поточного каталогу), або збільшують системний ліміт процесу через системний виклик `setrlimit(RLIMIT_NOFILE, ...)`.

### 4. Обробка сигналів та ізоляція груп процесів

Якщо користувач натискає Ctrl+C на терміналі, ядро надсилає сигнал `SIGINT` усій поточній групі термінальних процесів. Якщо диспетчер перехопить або проігнорує цей сигнал, але не повідомить воркерів, дочірні процеси можуть залишитися у системі у фоновому режимі.

Для надійної зупинки всієї інфраструктури воркерів диспетчер створює власну групу процесів через `setpgid(0, 0)` і встановлює обробник сигналів `SIGINT` та `SIGTERM`, який транслює сигнал усім дочірнім процесам групи:

:::tabs
```c
kill(-getpgrp(), SIGTERM);
```
```cpp
::kill(-::getpgrp(), SIGTERM);
```
:::

Знак мінус перед ідентифікатором групи вказує системному виклику `kill()`, що сигнал призначено всім процесам у даній групі (Process Group).

### 5. Обробка кодів завершення воркерів

Коректний збір результатів вимагає аналізу бітової маски статусу `status`, яку повертає `waitpid()`:

:::tabs
```c
int status = 0;
pid_t pid = waitpid(-1, &status, WNOHANG);
if (pid > 0) {
    if (WIFEXITED(status)) {
        int exit_code = WEXITSTATUS(status);
        if (exit_code != 0) {
            fprintf(stderr, "Воркер PID %d завершився з кодом помилки: %d\n", pid, exit_code);
        }
    } else if (WIFSIGNALED(status)) {
        int sig = WTERMSIG(status);
        fprintf(stderr, "Воркер PID %d аварійно вбито сигналом: %d\n", pid, sig);
    }
}
```
```cpp
int status = 0;
pid_t pid = ::waitpid(-1, &status, WNOHANG);
if (pid > 0) {
    if (WIFEXITED(status)) {
        int exit_code = WEXITSTATUS(status);
        if (exit_code != 0) {
            std::cerr << "Воркер PID " << pid << " завершився з кодом: " << exit_code << '\n';
        }
    } else if (WIFSIGNALED(status)) {
        int sig = WTERMSIG(status);
        std::cerr << "Воркер PID " << pid << " аварійно вбито сигналом: " << sig << '\n';
    }
}
```
:::

- `WIFEXITED(status)` — повертає `true`, якщо процес завершився нормально через виклик `exit()` або повернення з `main()`.
- `WEXITSTATUS(status)` — виділяє молодші 8 бітів коду повернення процесу.
- `WIFSIGNALED(status)` — повертає `true`, якщо процес було примусово завершено необробленим сигналом ядра (наприклад, `SIGKILL` або `SIGSEGV`).
- `WTERMSIG(status)` — повертає номер сигналу, який спричинив загибель процесу.

## Компіляція, тестування та простеження системних викликів

### 1. Збірка виконуваних файлів

Обидва варіанти збираються за допомогою оптимізуючих компіляторів GCC та Clang із увімкненням суворих діагностичних прапорців:

```sh
# Збірка версії мовою C
gcc -O2 -Wall -Wextra -pedantic proj-safe-batch-traversal/c/main.c -o batch_traversal_c

# Збірка версії мовою C++ (вимагає стандарту C++20 для std::filesystem)
g++ -O2 -std=c++20 -Wall -Wextra -pedantic proj-safe-batch-traversal/cpp/main.cpp -o batch_traversal_cpp
```

### 2. Створення синтетичного тестового стенду

Для перевірки стійкості до спеціальних символів та коректності групування сформуємо тестове дерево каталогів із проблемними іменами:

```sh
mkdir -p /tmp/test_traversal/sub1 /tmp/test_traversal/sub2/"каталог з пробілами"

# Створення звичайних лог-файлів
touch /tmp/test_traversal/app1.log /tmp/test_traversal/app2.log

# Файли з пробілами, лапками та дефісами на початку
touch "/tmp/test_traversal/sub1/access report 2026.log"
touch "/tmp/test_traversal/sub1/user's_data.log"
touch "/tmp/test_traversal/sub1/-rf.log"

# Файли інших типів, які повинні бути відфільтровані
touch /tmp/test_traversal/sub1/system.cfg /tmp/test_traversal/sub1/image.png
```

### 3. Простеження системних викликів через `strace`

Запуск під утилітою `strace` дозволяє наочно побачити взаємодію диспетчера з ядром Linux:

```sh
strace -f -e trace=clone,execve,wait4,lstat,openat,getdents64 ./batch_traversal_c /tmp/test_traversal
```

У журналі системних викликів чітко видно ланцюг подій:

```
[pid 45000] openat(AT_FDCWD, "/tmp/test_traversal", O_RDONLY|O_NONBLOCK|O_CLOEXEC|O_DIRECTORY) = 3
[pid 45000] getdents64(3, /* 5 записів */, 32768) = 160
[pid 45000] lstat("/tmp/test_traversal/app1.log", {st_mode=S_IFREG|0644, st_size=0, ...}) = 0
[pid 45000] lstat("/tmp/test_traversal/sub1", {st_mode=S_IFDIR|0755, ...}) = 0
...
[pid 45000] clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD, ...) = 45001
[pid 45001] execve("/usr/bin/gzip", ["gzip", "/tmp/test_traversal/app1.log", "/tmp/test_traversal/sub1/access report 2026.log", "/tmp/test_traversal/sub1/-rf.log", ...], ...) = 0
[pid 45000] wait4(-1, 0x7ffd1234, WNOHANG, NULL) = 0
[pid 45000] wait4(-1, [{WIFEXITED(s) && WEXITSTATUS(s) == 0}], 0, NULL) = 45001
```

З виводу `strace` видно:
1. Каталоги відкриваються та зчитуються блоками через `getdents64`.
2. Метадані файлів перевіряються через `lstat` без переходу за символьними посиланнями.
3. Дочірній процес породжується системним викликом `clone()` (внутрішня реалізація `fork` у Linux).
4. `execve` отримує масив розпакованих аргументів, де рядок `"-rf.log"` та `"access report 2026.log"` передаються як неподільні цілісні сутності без інтерпретації оболонкою.
5. Батьківський процес спочатку виконує неблокуючий виклик `wait4(..., WNOHANG)`, а на фінальному етапі коректно блокується до повного завершення нащадка.

### 4. Верифікація відсутності витоків пам'яті через Valgrind

Перевірка коректності звільнення пам'яті накопичувальних буферів та дескрипторів каталогу:

```sh
valgrind --leak-check=full --show-leak-kinds=all ./batch_traversal_c /tmp/test_traversal
```

Звіт `valgrind` підтверджує повну відсутність витоків ресурсів:

```
==45100== HEAP SUMMARY:
==45100==     in use at exit: 0 bytes in 0 blocks
==45100==   total heap usage: 48 allocs, 48 frees, 85,216 bytes allocated
==45100== All heap blocks were freed -- no leaks are possible
==45100== ERROR SUMMARY: 0 errors from 0 contexts (suppressed: 0 from 0)
```

Поєднання рекурсивного сканування VFS через дескрипторні виклики, формування масивів `argv[]` у межах системних лімітів `ARG_MAX`, виявлення циклів символьних посилань через хешування пар `(dev_t, ino_t)` та контроль за пулом процесів через неблокуючий `waitpid()` забезпечує максимальну швидкодію, стійкість до вразливостей TOCTOU та безпечну обробку файлових масивів будь-якого масштабу.
