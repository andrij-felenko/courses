# 📋 Довідник предикатів find та параметрів xargs

Системний інтерфейс утиліт `find` та `xargs` поєднує декларативну мову виразів предикатної логіки для фільтрації метаданих віртуальної файлової системи (VFS) з низькорівневим механізмом керування системними викликами `execve`, буферами пам'яті ядра та пулами паралельних процесів. Кожен предикат у виразі `find` виступає функцією зворотного виклику над структурою метаданих `struct stat`, `statx` або записом каталогу `linux_dirent64`, а параметри `xargs` регулюють токенізацію байтових потоків, розміщення масивів вказівників `argv[]` у віртуальному адресному просторі процесу та диспетчеризацію воркерів до системного ліміту `ARG_MAX`.

---

## Глобальні опції та поведінка VFS утиліти find

Глобальні опції визначають базовий алгоритм обходу дерева файлової системи, правила розв'язання символьних посилань, порядок відвідування вузлів, рівні оптимізації абстрактного синтаксичного дерева (AST) та поведінку при переході між точками монтування. Вони вказуються перед списком стартових шляхів або безпосередньо перед першим логічним виразом.

| Опція | Стандарт / Розширення | Призначення та поведінка системних викликів |
|---|---|---|
| `-P` | POSIX.1 / GNU | Фізичний обхід (поведінка за замовчуванням). Символьні посилання не розіменовуються; для перевірки метаданих викликається виключно `lstat()` або `fstatat(..., AT_SYMLINK_NOFOLLOW)`. |
| `-L` | POSIX.1 / GNU | Логічний обхід. Розіменовує всі символьні посилання; для отримання атрибутів цільового вузла викликається `stat()`. Активує внутрішній захист від зациклення. |
| `-H` | POSIX.1 / GNU | Гібридний обхід. Розіменовує символьні посилання лише у списку стартових аргументів командного рядка; всі вкладені посилання обробляються як у фізичному режимі `-P`. |
| `-mount`, `-xdev` | POSIX.1 (`-xdev`) / GNU | Обмеження поточною файловою системою. Забороняє спуск у каталоги, змонтовані на інших пристроях (перевірка рівності поля `st_dev` відносно точки входу). |
| `-depth` | POSIX.1 / GNU | Постфіксний обхід (Post-order DFS). Вміст каталогів обробляється раніше за сам каталог (обов'язково для коректної роботи дії `-delete`). |
| `-maxdepth N` | GNU / BSD | Максимальна глибина обходу. Обмежує занурення в дерево `N` рівнями каталогів відносно стартової точки (`-maxdepth 0` обмежує обхід самими аргументами). |
| `-mindepth N` | GNU / BSD | Мінімальна глибина застосування. Не застосовувати тести та дії на рівнях вкладеності менше `N` (`-mindepth 1` виключає стартові шляхи). |
| `-noleaf` | GNU extension | Вимикає оптимізацію підрахунку жорстких посилань `st_nlink - 2` для каталогів на файлових системах без стандартної семантики Unix (Btrfs, XFS, FAT, ISO9660, NFS). |
| `-ignore_readdir_race` | GNU extension | Приховує системні помилки `ENOENT`, якщо файл або каталог було видалено стороннім процесом у проміжку між `getdents64()` та `stat()`. |
| `-noignore_readdir_race` | GNU extension | Вимикає приховування помилок зникнення файлів під час обходу (поведінка за замовчуванням). |
| `-regextype type` | GNU extension | Задає синтаксис регулярних виразів для предиката `-regex` (`posix-basic`, `posix-extended`, `posix-egrep`, `posix-awk`, `emacs`, `gnu-awk`). |
| `-files0-from file` | GNU 4.9+ | Зчитує список стартових шляхів із файлу `file` з NUL-розділювачем `\0` (якщо передано `-`, зчитує зі стандартного входу `stdin`). |
| `-O0` | GNU extension | Вимикає оптимізацію AST-дерева виразів. Предикати виконуються строго у порядку запису в командному рядку. |
| `-O1` | GNU extension | Базова оптимізація (дефолт): дешеві тести за іменем (`-name`) пересуваються перед тестами метаданих (`-type`, `-size`), якщо це не порушує логіку. |
| `-O2` | GNU extension | Проміжна оптимізація: тести за `d_type` виконуються перед викликами `stat()`, дії з побічними ефектами виносяться в кінець ланцюжків. |
| `-O3` | GNU extension | Повна оптимізація: автоматичне перевпорядкування предикатів за статистичною вартістю системних викликів та частотою повернення `false`. |

### Архітектура та системний життєвий цикл обходу VFS

Рекурсивний обхід ієрархії файлової системи утилітою `find` реалізовано на основі потокового інтерфейсу POSIX Directory Streams (`DIR*`) та низькорівневих системних викликів ядра Linux:

1. **Ініціалізація та відкриття дескриптора каталогу:**
   - Для кожної точки входу процес викликає системний виклик `openat(AT_FDCWD, path, O_RDONLY | O_DIRECTORY | O_CLOEXEC)`.
   - Отриманий дескриптор `dirfd` передається у бібліотечну функцію `fdopendir(dirfd)` (або `opendir(path)`), яка алокує структуру потоку `DIR` разом із внутрішнім буфером читання фіксованого розміру (зазвичай 32 KB).
   - Використання прапорця `O_CLOEXEC` гарантує, що дескриптор каталогу не витікатиме у дочірні процеси під час виконання дій `-exec`.

2. **Пакетне вичитування записів через `readdir()` та `getdents64()`:**
   - Функція `readdir()` транслюється у прямий системний виклик `getdents64(dirfd, dirp, count)`.
   - Ядро заповнює буфер послідовністю структур `linux_dirent64`, кожна з яких містить номер індексного дескриптора `d_ino`, зміщення наступного запису `d_off`, загальний розмір запису `d_reclen`, тип вузла `d_type` та ім'я об'єкта `d_name`.
   - Рушій `find` послідовно ітерує по записах буфера. Якщо вираз користувача спирається лише на ім'я (`-name`, `-path`) або тип (`-type`), і файлова система заповнює `d_type` валідним значенням (відмінним від `DT_UNKNOWN`), `find` обчислює предикати безпосередньо з пам'яті структури без додаткових системних викликів `stat()` / `fstatat()`.

3. **Керування дескрипторами та глибиною рекурсії:**
   - Щоб уникнути вичерпання ліміту відкритих файлових дескрипторів процесу (`RLIMIT_NOFILE`, типово 1024 дескриптори) при спуску в глибокі ієрархії, сучасний GNU `find` (на базі бібліотеки `fts`) підтримує внутрішній пул активних дескрипторів та використовує відносні переходи.
   - Після повного вичитування всіх записів каталогу викликається `closedir(dirp)`, який звільняє виділений буфер у просторі користувача та закриває дескриптор `dirfd` системним викликом `close()`.

### Алгоритми обходу: Pre-order проти Post-order DFS

За замовчуванням `find` застосовує прямий обхід у глибину (Pre-order DFS):
1. Процес відкриває поточний каталог через `openat(AT_FDCWD, path, O_RDONLY | O_DIRECTORY)`.
2. Застосовує предикати та дії безпосередньо до самого каталогу.
3. Зчитує записи каталогу за допомогою `getdents64()` і рекурсивно спускається у знайдені підкаталоги.

Опція **`-depth`** перемикає алгоритм на зворотний обхід у глибину (Post-order DFS):
1. `find` спочатку рекурсивно занурюється на максимальну глибину піддерева.
2. Обробляє всі вкладені файли та підкаталоги.
3. Застосовує тести та дії до батьківського каталогу лише після завершення обробки всього його вмісту.

Цей порядок є критично необхідним для операцій очищення VFS:
- Дія **`-delete`** неявно активує опцію `-depth`. Якби застосовувався pre-order обхід, спроба видалити непорожній каталог системним викликом `rmdir()` завершилася б системною помилкою `ENOTEMPTY`.
- Предикат **`-prune`** є несумісним із режимом `-depth`: оскільки вміст каталогу вже відвіданий на момент обчислення предиката для самого каталогу, відсікання гілки стає неможливим, і `find` виводить попередження у `stderr`.

### Механізм виявлення циклів при логічному обході (`-L`) та розв'язання символьних посилань

Під час логічного обходу (`-L`) або при використанні застарілого прапорця `-follow` перехід за символьними посиланнями, які вказують на батьківські або вищі за ієрархією каталоги, створює загрозу нескінченної рекурсії, вичерпання дескрипторів та переповнення стеку пам'яті процесу.

Утиліта `find` запобігає зацикленню за допомогою комбінації дворівневого захисту:

1. **Відстеження ланцюжка предків через хеш-таблицю `(st_dev, st_ino)`:**
   - Перед кожним зануренням у каталог (як реальний, так і розв'язаний через symlink) утиліта викликає системний виклик `stat()`.
   - Отримана пара ідентифікатора блокового пристрою `st_dev` та номера індексного дескриптора `st_ino` однозначно ідентифікує фізичний вузол у межах усієї ОС.
   - Значення перевіряється за внутрішньою динамічною хеш-таблицею (або деревом) активного шляху предків від точки старту.
   - Якщо пару `(st_dev, st_ino)` уже зареєстровано в поточному ланцюжку предків, `find` виявляє циклічне посилання на каталог, негайно припиняє спуск у цю гілку, генерує діагностичне повідомлення у потік `stderr` (`find: File system loop detected; ‘./dir/link’ is part of the same file system loop as ‘./dir’`) та продовжує обхід сусідніх вузлів.
   - Після завершення обробки підкаталогу та виходу з нього (повернення вгору по дереву) пара `(st_dev, st_ino)` видаляється з активного стеку відвідування, що дозволяє повторно відвідувати той самий каталог з інших незалежних некольцевих гілок.

2. **Обробка системної помилки `ELOOP` ядра Linux:**
   - Якщо символьні посилання формують пряму циклічну петлю на рівні імен (наприклад, `symlink_a -> symlink_b` та `symlink_b -> symlink_a`) або ланцюжок посилань перевищує ліміт глибини ядра `SYMLOOP_MAX` (у ядрі Linux константа дорівнює `40` у файлі `fs/namei.c`), системний виклик `stat()` чи `openat()` повертає помилку `ELOOP` (*Too many levels of symbolic links*).
   - `find` перехоплює `ELOOP`, виводить діагностику у `stderr` і розглядає такий вузол як недосяжний, не перериваючи сканування решти дерева.

3. **Взаємодія режимів обходу з битими посиланнями:**
   - У фізичному режимі (`-P`, дефолт) для посилання виконується `lstat()`, тому навіть бите або циклічне посилання успішно повертає `DT_LNK` та статус дескриптора самого лінка.
   - У логічному режимі (`-L`) для кожного посилання викликається `stat()`. Якщо цільовий файл відсутній, системний виклик повертає помилку `ENOENT` (*Broken symlink*). Предикати типу вважають такий вузол неіснуючим або перевіряють його через `-xtype l`.

### Поведінка find при динамічній модифікації файлової системи (Concurrent FS Mutations)

Утиліта `find` проектувалася для роботи у багатозадачному середовищі Unix, де файлова система постійно мутує під дією паралельних фонових процесів (демонів запису логів, ротацій, компіляцій, тимчасових очищень). Оскільки VFS не надає механізму атомарного заморожування (снапшоту) дерева каталогів для простору користувача, послідовність системних викликів `getdents64()` та `fstatat()` піддається станам гонитви (Race Conditions).

#### 1. Поява нових файлів під час обходу каталогу

- Системний виклик `getdents64(dirfd, dirp, count)` зчитує вміст каталогу дискретними буферами. Позиція курсору фіксується у внутрішньому файловому зміщенні ядра `f_pos` (поле `d_off` у структурах записів).
- Якщо сторонній процес створює новий файл у каталозі, коли `find` уже частково зчитав його вміст:
  - На екстентних структурах із хешованими B-деревами каталогів (ext4 `htree`, XFS `B+tree`, Btrfs `subvolume tree`) новий запис вставляється у відповідний кошик за хешем його імені.
  - Якщо обчислений хеш або слот нового імені потрапляє в область зміщень **після** поточного `f_pos`, наступний виклик `getdents64()` поверне новостворений файл, і `find` застосує до нього всі предикати.
  - Якщо хеш нового запису розміщується **до** поточного `f_pos`, `find` не побачить новий файл під час поточного сканування.
- Висновок: `find` не гарантує атомарного зрізу стану каталогу на конкретний момент часу `T0`.

#### 2. Видалення та перейменування каталогів сторонніми процесами

- Якщо сторонній процес видаляє підкаталог (`rmdir()` / `unlinkat()`) у момент між тим, як `getdents64()` повернув його ім'я у буфер, і тим, як `find` намагається відкрити його для занурення (`openat(dirfd, d_name, O_RDONLY | O_DIRECTORY)`):
  - Виклик `openat()` негайно повертає помилку `ENOENT` (*No such file or directory*).
  - Якщо замість каталогу створено звичайний файл із тим самим ім'ям, `openat()` із прапорцем `O_DIRECTORY` повертає помилку `ENOTDIR` (*Not a directory*).
- Бібліотека обходу дерева `fts` у складі GNU `find` реєструє помилку та продовжує сканування наступних записів поточної черги.

#### 3. Семантика помилок ENOENT та прапорці `-ignore_readdir_race` / `-noignore_readdir_race`

- **Стандартний режим (`-noignore_readdir_race`, дефолт):**
  - Якщо `readdir()` розпізнав запис `d_name`, але наступний виклик `fstatat(dirfd, d_name, &st, AT_SYMLINK_NOFOLLOW)` завершився системною помилкою `ENOENT` (файл видалено стороннім процесом у мікросекундному вікні між читанням каталогу та перевіркою метаданих), `find` друкує повідомлення у потік `stderr`:
    ```
    find: ‘./var/log/app/transient.tmp’: No such file or directory
    ```
  - Помилка позначає обхід як частково неуспішний, через що після завершення сканування процес `find` повертає **ненульовий код завершення `> 0` (зазвичай `1`)**. Це призводить до помилкового завершення скриптів автоматизації та пайплайнів CI/CD.
- **Режим стійкості до гонитов (`-ignore_readdir_race`):**
  - GNU `find` перехоплює помилки `ENOENT`, які виникають виключно для елементів, знайдених під час читання каталогу `readdir()`.
  - Повідомлення про помилку у `stderr` пригнічується, а статус завершення утиліти залишається успішним (`0`), якщо не виникло інших системних збоїв (наприклад, помилок доступу `EACCES`).
  - *Критичний виняток:* якщо зник один зі **стартових шляхів**, явно переданих користувачем у командному рядку (наприклад, `find /var/spool/incoming ...`, де каталог `/var/spool/incoming` не існує на момент старту), помилка `ENOENT` виводиться **завжди**, незалежно від прапорця `-ignore_readdir_race`.

#### 4. Помилки ENOENT та стан гонитви TOCTOU у підпроцесах дій (`-exec`, `-execdir`, `-delete`)

- **Підпроцеси дій (`-exec cmd {} \;` та `-exec cmd {} +`):**
  - Якщо `find` успішно перевірив предикати файлу, але файл зник до того, як запущена команда (`gzip`, `chmod`, `stat`) виконала власний системний виклик `open()` / `stat()`, дочірній процес завершується з системною помилкою `ENOENT` (коди `1` або `2`).
  - У режимі `-exec cmd {} \;` дія повертає булеве `false`, що призводить до відкидання наступних предикатів поточного ланцюжка.
  - У режимі `-exec cmd {} +` невдалий код хоча б одного запущеного пакета змушує сам процес `find` завершитися з кодом `> 0`.
- **Вбудована дія `-delete`:**
  - Виконує прямий виклик `unlinkat(dirfd, d_name, flags)`.
  - Якщо файл уже видалено стороннім процесом (`unlinkat` повертає `ENOENT`), `-delete` фіксує статус `false`, виводить попередження та встановлює ненульовий підсумковий код виходу процесу `find`.
- **Ізоляція через `-execdir`:**
  - Використовує збережений дескриптор батьківського каталогу `dirfd` та відносне ім'я `./d_name`. Це виключає ризик підміни проміжних вузлів у дереві шляху (Directory Hijacking), звужуючи вікно гонитви виключно до операцій усередині поточного каталогу.

### Оптимізація підрахунку жорстких посилань каталогу (`-noleaf`) та VFS-сумісність

У класичних файлових системах Unix (ext2/ext3/ext4, UFS) кожен каталог містить як мінімум два спеціальні системні записи: `.` (жорстке посилання на себе) та `..` (жорстке посилання на батьківський каталог). Кожен новий створений підкаталог збільшує значення лічильника `st_nlink` батьківського каталогу рівно на 1 завдяки власному запису `..`.

Звідси випливає фундаментальний інваріант зв'язку лічильника посилань та кількості дочірніх каталогів:

```
Кількість_підкаталогів = st_nlink - 2
```

Оптимізатор `find` використовує цей зв'язок у механізмі **Leaf Directory Optimization**:
1. При вході в каталог `find` зчитує `st_nlink` його індексного вузла та ініціалізує лічильник `leaf_count = st_nlink - 2`.
2. Під час сканування записів через `readdir()` кожен виявлений підкаталог (`d_type == DT_DIR` або розпізнаний як каталог) зменшує `leaf_count` на 1.
3. Щойно `leaf_count` досягає `0`, `find` отримує математичну гарантію, що всі підкаталоги в поточному каталозі вже знайдено.
4. Для всіх наступних записів у цьому каталозі `find` припиняє перевіряти можливість занурення вглиб і не виконує системні виклики `stat()` / `lstat()` для перевірки типу, якщо предикати виразу не вимагають додаткових метаданих. Якщо `d_type == DT_UNKNOWN`, усі залишкових записи гарантовано вважаються листовими вузлами (Regular files або symlinks).

#### Поведінка та аномалії на сучасних файлових системах

Сучасні структури збереження даних порушують класичну семантику `st_nlink`:

- **ext4:** Суворо дотримується семантики `st_nlink` до досягнення ліміту `EXT4_LINK_MAX` (65 000 посилань). При перевищенні ліміту ext4 фіксує `st_nlink = 1` для позначення необмеженої кількості підкаталогів, що автоматично деактивує leaf-оптимізацію для конкретного надвеликого каталогу.
- **XFS:** Підтримує лічильник `st_nlink`, але на великих каталогах або в режимах оптимізованого виділення блоків може використовувати внутрішні схеми агрегації.
- **Btrfs:** Використовує архітектуру Copy-on-Write (CoW) B-дерев та механізм підтомів (subvolumes). Оновлення лічильника `st_nlink` батьківського каталогу при кожному створенні або видаленні підкаталогу створювало б колосальне блокування (Lock Contention) кореневих вузлів дерева та лавиноподібне перезаписування метаданих CoW. Тому в Btrfs значення `st_nlink` для каталогів статично зафіксоване на рівні `1` (або `2` для кореня підтому). Якби `find` застосував leaf-оптимізацію на Btrfs, розрахунок дав би `leaf_count = 1 - 2 = -1` або `0`, і утиліта вирішила б, що каталог не містить жодного підкаталогу, повністю пропустивши всі вкладені структури.
- **FAT32 / exFAT / NTFS (ntfs-3g) / CIFS / ISO9660:** Не підтримують концепцію жорстких посилань Unix і повертають фіктивне значення `st_nlink = 1` або `0`.

#### Автоматичне виявлення типу ФС та прапорець `-noleaf`

GNU `find` перед початком обходу точки монтування викликає системний виклик `statfs(path, &buf)` або `fstatfs(dirfd, &buf)` і зіставляє значення поля магічного числа `buf.f_type`:

| Файлова система | Магічне число `f_type` (hex) | Підтримка `st_nlink` | Автоматичний режим GNU find |
|---|---|---|---|
| `ext2/ext3/ext4` | `0xEF53` (`EXT4_SUPER_MAGIC`) | Так (до 65k) | Leaf Optimization активна |
| `UFS` / `FFS` | `0x00011954` | Так | Leaf Optimization активна |
| `Btrfs` | `0x9123683E` (`BTRFS_SUPER_MAGIC`) | Ні (`st_nlink == 1`) | Leaf Optimization вимкнено |
| `NFS` | `0x6969` (`NFS_SUPER_MAGIC`) | Ні (динамічний стан) | Leaf Optimization вимкнено |
| `ISO9660` | `0x9660` (`ISOFS_SUPER_MAGIC`) | Ні | Leaf Optimization вимкнено |
| `MSDOS` / `FAT` | `0x4D44` (`MSDOS_SUPER_MAGIC`) | Ні | Leaf Optimization вимкнено |
| `SMB` / `CIFS` | `0x517B` (`SMB_SUPER_MAGIC`) | Ні | Leaf Optimization вимкнено |
| `TMPFS` | `0x01021994` (`TMPFS_MAGIC`) | Так | Leaf Optimization активна |

Якщо файлова система не підтримує стандартну семантику `nlink`, GNU `find` автоматично деактивує leaf-оптимізацію для цього дерева.

Прапорець **`-noleaf`** примусово вимикає Leaf Directory Optimization глобально для всіх оброблюваних файлових систем. Це гарантує коректність обходу на віртуальних VFS, нестандартних драйверах FUSE або мережевих ресурсах, магічні константи яких відсутні у вбудованій таблиці утиліти.

## Предикати відбору за метаданими індексного вузла

Предикати виконують зіставлення полів структури `struct stat` або імені запису в каталозі з критеріями користувача і повертають булеве значення `true` або `false`.

### 1. Тип вузла файлової системи (`-type` та `-xtype`)

Предикат `-type` перевіряє значення бітової маски файлового типу в полі `st_mode` структури `struct stat` або значення поля `d_type` у структурі `linux_dirent64`. Якщо файлова система повертає `d_type` безпосередньо через `getdents64()`, `find` уникає звернення до системного виклику `stat()`. Якщо `d_type == DT_UNKNOWN` (трапляється на деяких мережевих FS або старих ядрах), `find` виконує відкатний системний виклик `fstatat(..., AT_SYMLINK_NOFOLLOW)`.

| Прапорець | Тип об'єкта в POSIX | Бітовий макрос `st_mode` | Значення `d_type` |
|---|---|---|---|
| `-type f` | Звичайний файл (Regular file) | `S_ISREG(st_mode)` | `DT_REG` (`8`) |
| `-type d` | Каталог (Directory) | `S_ISDIR(st_mode)` | `DT_DIR` (`4`) |
| `-type l` | Символьне посилання (Symbolic link) | `S_ISLNK(st_mode)` | `DT_LNK` (`10`) |
| `-type s` | Сокет домену Unix (UNIX domain socket) | `S_ISSOCK(st_mode)` | `DT_SOCK` (`12`) |
| `-type p` | Іменований канал (FIFO / Named pipe) | `S_ISFIFO(st_mode)` | `DT_FIFO` (`1`) |
| `-type b` | Блоковий пристрій (Block device) | `S_ISBLK(st_mode)` | `DT_BLK` (`6`) |
| `-type c` | Символьний пристрій (Character device) | `S_ISCHR(st_mode)` | `DT_CHR` (`2`) |
| `-type D` | Двері Solaris (Solaris Door, GNU розширення) | `S_ISDOOR(st_mode)` | `DT_UNKNOWN` |

Предикат **`-xtype c`** (розширення GNU) реалізує двонаправлену перевірку типу об'єкта, інвертуючи поведінку розв'язання символьних посилань:
- **У фізичному режимі (`-P`):** для звичайних файлів `-xtype` еквівалентний `-type`. Для символьних посилань `-xtype` виконує виклик `stat()` над цільовим файлом посилання.
- **У логічному режимі (`-L`):** для розіменованих файлів `-xtype` перевіряє тип самого символьного посилання через `lstat()`.
- **Пошук битих символьних посилань (Broken Symlinks):** команда `find . -xtype l` у фізичному режимі `-P` знаходить усі символьні посилання, цілі яких не існують у VFS (системний виклик `stat()` повертає помилку `ENOENT`).

### 2. Шаблони імен, шляхів та регулярні вирази

- **`-name pattern`** (POSIX.1) — зіставлення імені файлу (`basename`, без шляху до каталогу) із шаблоном `fnmatch(3)` (підтримуються метасимволи `*`, `?`, `[...]`).
- **`-iname pattern`** (GNU / BSD) — регістронезалежне зіставлення імені файлу (`FNM_CASEFOLD`).
- **`-path pattern`**, **`-wholename pattern`** (POSIX.1-2024 / GNU) — зіставлення повного відносного шляху із шаблоном. Символ `/` розглядається як звичайний символ (шаблон `*/test/*.c` охоплює довільну кількість проміжних каталогів).
- **`-ipath pattern`**, **`-iwholename pattern`** (GNU extension) — регістронезалежне зіставлення повного шляху.
- **`-regex pattern`** (GNU extension) — перевірка повного відносного шляху на відповідність регулярному виразу. Зіставлення виконується для всього рядка шляху від початку до кінця (не є підрядковим пошуком).
- **`-iregex pattern`** (GNU extension) — регістронезалежний регулярний вираз.
- **`-regextype type`** (GNU extension) — вибір діалекту регулярних виразів:
  - `posix-basic` (BRE, дефолт POSIX);
  - `posix-extended` (ERE, розширені регулярні вирази з `+`, `?`, `|`, `()`);
  - `posix-egrep` (ERE з підтримкою розширень `egrep`);
  - `posix-awk` (діалект утиліти `awk`);
  - `emacs` (синтаксис Emacs із групуванням `\(` `\)`);
  - `gnu-awk` (синтаксис Gawk із підтримкою спеціальних класів `\s`, `\w`, `\<`, `\>`).
- **`-empty`** (GNU extension) — перевірка на порожній об'єкт:
  - для звичайного файлу — розмір `st_size == 0`;
  - для каталогу — відсутність записів у каталозі, крім системних записів `.` та `..`;
  - для іменованих каналів (FIFO) та сокетів — відсутність активних даних у черзі.

### 3. Часові шкали та квантування інтервалів

Ядро операційної системи фіксує часові мітки в структурі `struct stat` або `struct statx`:
- `mtime` (`st_mtim.tv_sec`): час останньої модифікації байтів вмісту файлу (`write()`, `truncate()`).
- `atime` (`st_atim.tv_sec`): час останнього доступу до даних (`read()`, `execve()`, `mmap()`). Залежить від прапорців монтування VFS (`relatime`, `noatime`, `strictatime`).
- `ctime` (`st_ctim.tv_sec`): час останньої зміни метаданих або стану inode (`chmod()`, `chown()`, створення посилань, перейменування, зміна вмісту).
- `btime` / birth time (`stx_btime.tv_sec` через системний виклик `statx()` у Linux 4.11+): час фізичного створення файлу.

#### Квантування добових інтервалів (`-mtime`, `-atime`, `-ctime`)

Утиліта `find` розраховує вік файлу у 24-годинних дискретних інтервалах від моменту запуску:

```
N = ⌊(T_now - T_file) / 86400⌋
```

| Вираз | Математична умова | Часовий інтервал відносно поточного моменту |
|---|---|---|
| `-mtime N` | `N · 86400 ≤ Δt < (N + 1) · 86400` | Файл модифіковано рівно `N` діб тому (інтервал від `N·24` до `(N+1)·24` годин). |
| `-mtime -N` | `Δt < N · 86400` | Файл модифіковано суворо менше ніж `N` діб тому (останні `N·24` годин). |
| `-mtime +N` | `Δt ≥ (N + 1) · 86400` | Файл старіший за `N` повних діб (модифікація відбулася понад `(N+1)·24` годин тому). |

Практичні значення для розрахунку часових вікон:
- `-mtime 0`: модифікація в межах останніх 24 годин (`0 ≤ Δt < 24 год`).
- `-mtime -1`: модифікація менше ніж 24 години тому (`Δt < 24 год`, еквівалентно `-mtime 0`).
- `-mtime +0`: модифікація відбулася понад 24 години тому (`Δt ≥ 24 год`).
- `-mtime 1`: модифікація відбулася в інтервалі від 24 до 48 годин тому.
- `-mtime +1`: файл старіший за 48 годин (`Δt ≥ 48 год`).

#### Високоточні таймери та модифікатори часу

- **`-mmin [+/-]N`, `-amin [+/-]N`, `-cmin [+/-]N`** (GNU / BSD) — фільтрація у 60-секундних інтервалах `(⌊Δt / 60⌋)`.
  - `-mmin N`: модифіковано від `N` до `N+1` хвилин тому (`N·60 ≤ Δt < (N+1)·60`).
  - `-mmin -N`: модифіковано суворо менше ніж `N` хвилин тому (`Δt < N·60`).
  - `-mmin +N`: модифіковано понад `N` хвилин тому (`Δt ≥ (N+1)·60`).
- **`-daystart`** (GNU extension) — зсуває точку відліку часу від поточної секунди `time(NULL)` до 00:00:00 сьогоднішнього календарного дня за локальним часом системи (`tzset()`).
- **`-newer ref_file`** (POSIX.1) — повертає `true`, якщо час модифікації поточного файлу новіший за час модифікації еталонного файлу `ref_file` (`st_mtime(target) > st_mtime(ref)`).
- **`-anewer ref_file`**, **`-cnewer ref_file`** (GNU extension) — порівняння з часом доступу або зміни метаданих `ref_file`.
- **`-newerXY reference`** (GNU extension) — універсальна матриця порівняння часових міток. Літера `X` задає часову мітку досліджуваного файлу, а літера `Y` — тип еталону:
  - `a` — час доступу (`atime`);
  - `m` — час модифікації (`mtime`);
  - `c` — час зміни стану inode (`ctime`);
  - `B` — час створення файлу (`birth time`, якщо підтримується VFS та системним викликом `statx`);
  - `t` — інтерпретує `reference` як явний рядок дати й часу у форматі ISO 8601 / `strptime` (наприклад, `-newermt "2026-08-01 00:00:00"`).

Повна матриця комбінацій `-newerXY`:

| Предикат | Порівнювана мітка поточного файлу (`X`) | Еталонне значення (`Y`) |
|---|---|---|
| `-neweraa ref` | `atime` поточного файлу | `atime` файлу `ref` |
| `-neweram ref` | `atime` поточного файлу | `mtime` файлу `ref` |
| `-newerac ref` | `atime` поточного файлу | `ctime` файлу `ref` |
| `-neweraB ref` | `atime` поточного файлу | `btime` файлу `ref` |
| `-newerat str` | `atime` поточного файлу | Явний рядок дати/часу `str` |
| `-newermm ref` | `mtime` поточного файлу | `mtime` файлу `ref` (еквівалент `-newer`) |
| `-newerma ref` | `mtime` поточного файлу | `atime` файлу `ref` |
| `-newermc ref` | `mtime` поточного файлу | `ctime` файлу `ref` |
| `-newermB ref` | `mtime` поточного файлу | `btime` файлу `ref` |
| `-newermt str` | `mtime` поточного файлу | Явний рядок дати/часу `str` |
| `-newerca ref` | `ctime` поточного файлу | `atime` файлу `ref` |
| `-newercm ref` | `ctime` поточного файлу | `mtime` файлу `ref` |
| `-newercc ref` | `ctime` поточного файлу | `ctime` файлу `ref` |
| `-newercB ref` | `ctime` поточного файлу | `btime` файлу `ref` |
| `-newerct str` | `ctime` поточного файлу | Явний рядок дати/часу `str` |
| `-newerBa ref` | `btime` поточного файлу | `atime` файлу `ref` |
| `-newerBm ref` | `btime` поточного файлу | `mtime` файлу `ref` |
| `-newerBc ref` | `btime` поточного файлу | `ctime` файлу `ref` |
| `-newerBB ref` | `btime` поточного файлу | `btime` файлу `ref` |
| `-newerBt str` | `btime` поточного файлу | Явний рядок дати/часу `str` |

### 4. Розмір файлу (`-size`) та квантування обсягу

Предикат `-size` перевіряє значення поля `st_size` структури метаданих. За відсутності явного суфікса розмір інтерпретується в 512-байтових блоках.

| Суфікс | Одиниця виміру | Розмір у байтах | Приклад використання |
|---|---|---|---|
| `c` | Байт (Characters) | 1 байт | `-size 1024c` (рівно 1024 байти) |
| `w` | Двобайтове слово (Words) | 2 байти | `-size 512w` (1024 байти) |
| `b` | Блок файлової системи | 512 байтів (дефолт POSIX) | `-size 2b` (1024 байти) |
| `k` | Кілобайт (Kibibytes) | 1024 байти | `-size 10k` |
| `M` | Мегабайт (Mebibytes) | 1 048 576 байтів (1024² ) | `-size +100M` |
| `G` | Гігабайт (Gibibytes) | 1 073 741 824 байти (1024³ ) | `-size +1G` |
| `T` | Терабайт (Tebibytes) | 1 099 511 627 776 байтів (1024⁴ ) | `-size +2T` |
| `P` | Петабайт (Pebibytes) | 1 125 899 906 842 624 байти (1024⁵ ) | `-size +1P` |

#### Округлення вгору при перевірці розміру

Під час перевірки блокових одиниць (`k`, `M`, `G`, `b`) `find` обчислює кількість одиниць за формулою стелі:

```
одиниці = ⌈st_size / розмір_одиниці⌉
```

- **`-size 10M` (без знака):** повертає `true` для файлів, чий розмір потрапляє в діапазон від `(10 - 1) · 1024² + 1` до `10 · 1024²` байтів (від 9 437 185 до 10 485 760 байтів включно).
- **`-size +10M`:** суворо більший за `10 · 1024²` байтів (`st_size > 10485760`).
- **`-size -10M`:** суворо менший або рівний `(10 - 1) · 1024²` байтів (`st_size ≤ 9437184`).
- Для точного побайтового зіставлення завжди використовується суфікс `c`: `-size +10485760c`.

#### Логічний розмір проти дискових блоків (Sparse Files)

Поле `st_size` відображає логічну довжину файлу, тоді як реальний обсяг зайнятого дискового простору визначається полем `st_blocks` (кількість 512-байтових секторів, виділених під дані). Для розріджених файлів (sparse files) логічний розмір може становити терабайти, тоді як на диску виділено лише кілька блоків. Перевірити фізичний розмір дозволяє специфікатор дії `-printf "%k KB"` (`st_blocks · 512 / 1024`).

### 5. Права доступу (`-perm`) та володіння

Предикат `-perm` аналізує молодші 12 бітів поля `st_mode` структури метаданих, що охоплюють стандартні біти читання/запису/виконання (`rwxrwxrwx`) та спеціальні біти безпеки: SUID (`04000`, `S_ISUID`), SGID (`02000`, `S_ISGID`) та Sticky bit (`01000`, `S_ISVTX`).

```
  04000      02000      01000      00700      00070      00007
┌───────┬──────────┬──────────┬──────────┬──────────┬──────────┐
│ SUID  │   SGID   │  Sticky  │  Власник │  Група   │   Інші   │
│       │          │          │  (u=rwx) │  (g=rwx) │  (o=rwx) │
└───────┴──────────┴──────────┴──────────┴──────────┴──────────┘
```

#### Режими обчислення предиката `-perm`

| Синтаксис | Логічний вираз бітової маски | Семантика перевірки |
|---|---|---|
| `-perm 0644` | `(st_mode & 07777) == 0644` | Точний збіг режиму. Усі 12 бітів мають суворо відповідати значенню `0644`. Наявність будь-якого неузгодженого біта дає `false`. |
| `-perm -0644` | `(st_mode & 0644) == 0644` | Перевірка підмножини (ALL bits). Усі біти, активні в масці `0644`, обов'язково мають бути активними у файлі. Решта бітів ігнорується (файли з правами `0755` успішно пройдуть тест). |
| `-perm /0644` | `(st_mode & 0644) != 0` | Перевірка перетину (ANY bit). Повертає `true`, якщо хоча б один із бітів, активних у масці `0644`, встановлено у файлі. |
| `-perm +0644` | Застарілий синтаксис GNU | Еквівалент `/0644`. Вилучений зі стандарту POSIX та нових версій GNU Findutils через синтаксичний конфлікт із символьними правами доступу. |

Символьний запис прав підтримується в усіх трьох варіантах:
- `-perm -u+w,g+w` — власник і група одночасно мають права на запис.
- `-perm /u=x,g=x,o=x` — файл є виконуваним хоча б для однієї категорії користувачів.

#### Перевірка володіння та прав процесу

- **`-user uname`** / **`-user uid`** (POSIX.1) — файл належить користувачу з іменем `uname` або числовим ідентифікатором `uid` (`st_uid`). Розв'язання імені виконується на старті через функцію `getpwnam()`.
- **`-group gname`** / **`-group gid`** (POSIX.1) — файл належить групі `gname` або `gid` (`st_gid`). Розв'язання імені виконується через `getgrnam()`.
- **`-uid N`**, **`-gid N`** (GNU extension) — пряма числова перевірка ідентифікаторів без звернення до баз користувачів.
- **`-nouser`** (POSIX.1) — повертає `true`, якщо числовий ідентифікатор `st_uid` не має відповідного запису в системній базі користувачів `/etc/passwd` (`getpwuid(st_uid) == NULL`). Використовується для виявлення файлів видалених облікових записів.
- **`-nogroup`** (POSIX.1) — повертає `true`, якщо `st_gid` не зареєстрований у `/etc/group` (`getgrgid(st_gid) == NULL`).
- **`-readable`** (GNU extension) — перевіряє реальну доступність файлу для читання поточним процесом за допомогою системного виклику `faccessat(AT_FDCWD, path, R_OK, AT_EACCESS)`. Враховує права суперкористувача root, список додаткових груп (`getgroups()`) та прапорці монтування файлової системи `MS_RDONLY`.
- **`-writable`** (GNU extension) — перевіряє доступність для запису через `faccessat(..., W_OK, AT_EACCESS)`.
- **`-executable`** (GNU extension) — перевіряє право виконання або право проходження каталогу через `faccessat(..., X_OK, AT_EACCESS)`.

### 6. Розширені атрибути (Extended Attributes xattr) та списки контролю доступу (POSIX ACLs)

Розширені атрибути (Extended Attributes, xattr) та списки контролю доступу (Access Control Lists, POSIX ACLs) розширюють класичну модель прав доступу Unix (12 бітів `st_mode`), дозволяючи асоціювати з кожним індексним дескриптором довільні пари ключ-значення та гранулярні списки суб'єктів доступу.

```
Структура розширених метаданих вузла VFS:
┌────────────────────────────────────────────────────────────────────────┐
│ Індексний дескриптор (Inode Core):                                     │
│ ├─ st_mode (12 бітів прав: SUID, SGID, Sticky, u/g/o rwx)              │
│ ├─ st_uid / st_gid (Власник та основна група)                          │
│ └─ st_size, st_ino, st_dev, st_blocks, часові мітки                   │
├────────────────────────────────────────────────────────────────────────┤
│ Розширені простори імен xattr (Namespaces):                            │
│ ├─ user.*      (user.mime_type, user.md5, user.checksum)               │
│ ├─ security.*  (security.selinux, security.SMACK64, security.ima)      │
│ ├─ system.*    (system.posix_acl_access, system.posix_acl_default)     │
│ └─ trusted.*   (trusted.overlay.opaque, trusted.glusterfs.*)           │
└────────────────────────────────────────────────────────────────────────┘
```

#### Системні виклики VFS для роботи з xattr

Ядро Linux надає сімейство спеціалізованих системних викликів:
- `listxattr(path, list, size)` / `llistxattr()` / `flistxattr(fd, ...)` — повертає суцільний буфер імен усіх розширених атрибутів, розділених NUL-байтами `\0`.
- `getxattr(path, name, value, size)` / `lgetxattr()` / `fgetxattr()` — зчитує бінарне або рядкове значення атрибута з іменем `name`.
- `setxattr()` / `lsetxattr()` / `removexattr()` — встановлення та видалення атрибутів.

#### Простори імен (Namespaces) розширених атрибутів

1. **`user.` (Користувацькі атрибути):** Довільні метадані застосунків (наприклад, `user.mime_type` або теги файлових менеджерів). Доступ на читання та запис регулюється стандартними правами доступу до файлу (`st_mode`). На деяких старих файлових системах вимагає опції монтування `user_xattr`.
2. **`security.` (Мандатний контроль доступу LSM):** Використовується модулями безпеки ядра (SELinux context `security.selinux`, SMACK, AppArmor, цілісність IMA/EVM). Запис вимагає привілеїв `CAP_MAC_ADMIN` або `CAP_SYS_ADMIN`.
3. **`system.` (Системні списки контролю доступу):** Зберігає двійкові структури POSIX.1e ACL (`system.posix_acl_access` для файлів та `system.posix_acl_default` для каталогів).
4. **`trusted.` (Привілейовані системні атрибути):** Метадані простору користувача, доступні виключно процесам із системним привілеєм `CAP_SYS_ADMIN` (активно використовується драйверами контейнерів `overlayfs`).

#### Предикати xattr та ACL у BSD / macOS find

Утиліта `find` на платформах BSD (FreeBSD, OpenBSD) та macOS містить нативні предикати для прямої фільтрації метаданих xattr та ACL:

| Предикат | Платформа | Системний виклик / Умова | Опис поведінки |
|---|---|---|---|
| `-xattr` | BSD / macOS | `listxattr(path, NULL, 0) > 0` | Повертає `true`, якщо вузол містить хоча б один розширений атрибут будь-якого простору імен. |
| `-xattrname name` | BSD / macOS | `getxattr(path, name, NULL, 0) >= 0` | Повертає `true`, якщо вузол містить атрибут із точним іменем `name` (наприклад, `-xattrname user.checksum` або `-xattrname com.apple.quarantine`). |
| `-acl` | BSD / macOS | `acl_get_file(path, ACL_TYPE_EXTENDED)` | Повертає `true`, якщо файл або каталог містить нетривіальний розширений список контролю доступу (ACL). |

Приклади використання на BSD / macOS:
```sh
# Знайти всі завантажені файли з міткою карантину macOS
find . -type f -xattrname com.apple.quarantine -print

# Знайти всі файли, які мають розширені списки доступу ACL
find /var/shared -acl -print
```

#### Семантика та механізми перевірки в GNU Findutils (Linux)

Стандартний GNU `find` не містить вбудованих предикатів `-xattr` чи `-acl` у синтаксичному ядрі утиліти, проте надає точні механізми аудиту через предикати прав доступу, специфікатори форматування та інтеграцію із системними утилітами:

##### 1. Диференціація `-perm` проти `-readable` / `-writable` / `-executable`

Існує фундаментальна різниця у тому, як `find` оцінює права доступу при наявності списків POSIX ACL:

- **Предикат `-perm` перевіряє виключно 12 бітів `st_mode` структури inode:**
  Якщо на файл встановлено базові права `0400` (`r--------`), але через POSIX ACL користувачу `developer` надано повний доступ `user:developer:rwx`, предикат `find . -perm -0200` (перевірка права на запис) поверне **`false`**, оскільки він не аналізує атрибут `system.posix_acl_access`.
- **Предикати `-readable`, `-writable`, `-executable` використовують `faccessat()`:**
  Утиліта викликає системний виклик `faccessat(AT_FDCWD, path, W_OK, AT_EACCESS)`. Ядро Linux у системній функції `generic_permission()` виконує повноцінну перевірку ланцюжка POSIX ACL:
  1. Зіставляє UID процесу з власником файлу `st_uid`.
  2. Якщо не збігається, послідовно перевіряє всі записи `ACL_USER` в атрибуті `system.posix_acl_access`.
  3. Перевіряє записи груп `ACL_GROUP_OBJ` та додаткових груп `ACL_GROUP`, обмежуючи їх бітовою маскою `ACL_MASK`.
  4. Якщо відповідність знайдено, предикат повертає **`true`**.

##### 2. Аудит списків ACL та міток безпеки через специфікатор `-printf "%M"`

Специфікатор дії `-printf "%M"` формує 11-символьний рядок прав доступу у стандарті `ls -l`. Останній (одинадцятий) символ рядка інформує про наявність розширених атрибутів:

- **Символ `+` на 11-й позиції (наприклад, `-rw-r--r--+`):** файл містить активний розширений список контролю доступу POSIX ACL (`system.posix_acl_access`).
- **Символ `.` на 11-й позиції (наприклад, `-rwxr-xr-x.`):** файл містить мітку безпеки SELinux (`security.selinux`) або іншого LSM, але не має розширеного ACL.
- **Пробіл на 11-й позиції (наприклад, `-rw-r--r-- `):** файл використовує виключно класичні дискреційні права Unix без додаткових атрибутів.

## Логічні оператори, оптимізація AST та керування потоком

Вираз команди `find` парситься у внутрішнє бінарне дерево абстрактного синтаксису (Abstract Syntax Tree, AST). Вузли дерева представляють булеві оператори, а листки — предикати-тести та предикати-дії.

### Логічні оператори та таблиця пріоритетів

| Оператор | Альтернативний запис | Пріоритет | Асоціативність | Опис логічної операції |
|---|---|---|---|---|
| `( expr )` | `\( expr \)` | 1 (найвищий) | — | Явне групування виразів у дужки (вимагає екранування в shell). |
| `!` | `-not` | 2 | Правоасоціативна | Логічне заперечення (NOT). Інвертує результат обчислення правого виразу. |
| *(пробіл)* | `-a`, `-and` | 3 | Лівоасоціативна | Логічна кон'юнкція (AND). Обчислюється за замовчуванням між сусідніми предикатами. |
| `-o` | `-or` | 4 | Лівоасоціативна | Логічна диз'юнкція (OR). Права частина обчислюється лише якщо ліва повернула `false`. |
| `,` | *(кома)* | 5 (найнижчий) | Лівоасоціативна | Оператор списку (C comma operator). Обчислює обидва вирази, повертає результат правого. |

### Алгоритм оптимізації порядку предикатів у GNU find (Рівні -O1...-O3)

Рушій оптимізації GNU `find` динамічно перебудовує AST-дерево для мінімізації кількості дорогих системних викликів до VFS (`stat()`, `openat()`, `readlink()`).

#### 1. Класифікація обчислювальної вартості предикатів

Кожен предикат має фіксований клас вартості (Cost Class):

- **Клас 0 (Чистий парсинг у пам'яті):** Предикати, що оперують даними з адресного простору процесу або статичними рядками (`-name`, `-iname`, `-path`, `-regex`, `-true`, `-false`). Обчислення полягає у виклику `fnmatch()` або `regexec()`.
- **Клас 1 (Пряме читання `d_type` без `stat()`):** Предикати перевірки типу (`-type`, `-xtype` у фізичному режимі для не-символьних посилань). Якщо тип повернено ядром безпосередньо у структурі `linux_dirent64` через `getdents64()`, вартість перевірки дорівнює простому бітовому маскуванню в пам'яті.
- **Клас 2 (Системні виклики метаданих inode):** `stat()`, `lstat()`, `fstatat()`, `statx()` — предикати розміру (`-size`), часових міток (`-mtime`, `-atime`, `-ctime`, `-newer`, `-newerXY`), прав доступу (`-perm`), володіння (`-user`, `-group`, `-uid`, `-gid`), посилань (`-links`, `-samefile`) та дескрипторів (`-inum`, `-empty`).
- **Клас 3 (Побічні ефекти та системні виклики підпроцесів):** Предикати дій (`-exec`, `-execdir`, `-ok`, `-okdir`, `-delete`, `-print`, `-print0`, `-printf`, `-quit`). Створюють накладні витрати на виведення, дисковий запис або виклики `fork()` / `execve()`.

#### 2. Оцінка селективності (Cost-Based Estimation)

Кожен предикат наділений апріорною оцінкою ймовірності істинності `P(true)` та відсікання `P(false) = 1 - P(true)`:
- Вузькі фільтри імен (наприклад, `-name "*.log"`) мають високу селективність (`P(false) ≈ 0.90..0.98`), відсікаючи більшість об'єктів.
- Фільтри типів (наприклад, `-type f`) мають низьку селективність (`P(false) ≈ 0.10`), оскільки переважна більшість записів VFS є звичайними файлами.
- Фільтри старого віку (наприклад, `-mtime +365`) зазвичай мають високу селективність (`P(false) ≈ 0.95`).

#### 3. Правила перевпорядкування в кон'юнкціях та диз'юнкціях

- **Кон'юнктивні ланцюжки (`AND`):** Завдяки короткому замиканню ланцюжок переривається на першому предикаті, що повернув `false`. Загальна обчислювальна вартість мінімізується, якщо предикати впорядковано за спаданням коефіцієнта ефективності:

```
Ефективність_AND = P(false) / Вартість
```

Оптимізатор виносить дешеві та високоефективні фільтри (Клас 0 та Клас 1) на початок ланцюжка. Це гарантує, що дорогі системні виклики `stat()` (Клас 2) викликаються лише для тих файлів, які вже пройшли фільтрацію за ім'ям та типом.

- **Диз'юнктивні ланцюжки (`OR`):** Ланцюжок переривається на першому предикаті, що повернув `true`. Впорядкування здійснюється за спаданням відношення:

```
Ефективність_OR = P(true) / Вартість
```

- **Бар'єр побічних ефектів (Side-Effect Barrier):** Предикати з побічними ефектами (усі дії Класу 3, а також `-print`, `-printf`, `-quit`) є бар'єрами оптимізації. Вони ніколи не переставляються відносно умовних предикатів, які визначають критерій їхнього запуску, щоб не спотворити семантику команди.

#### 4. Закони де Моргана та булеві трансформації AST

Оптимізатор GNU `find` спрощує та нормалізує складні логічні вирази за правилами булевої алгебри:

- **Проштовхування заперечень (Закони де Моргана):**
  - `!(A -a B)` еквівалентно трансформується у `(!A -o !B)`
  - `!(A -o B)` еквівалентно трансформується у `(!A -a !B)`
  Це усуває вкладені дужкові конструкції із запереченням, розгортаючи їх у пласкі списки предикатів для подальшого сортування за вартістю.

- **Згортання булевих констант (Constant Folding):**
  - `-true -a expr`  ==>  `expr`
  - `-false -a expr` ==>  `-false` (правий вираз відкидається як недосяжний)
  - `-true -o expr`  ==>  `-true` (правий вираз відкидається)
  - `-false -o expr` ==>  `expr`

- **Усунення мертвого коду (Dead Node Elimination):** Гілки дерева, виконання яких математично неможливе через попередні інваріанти, повністю видаляються з пам'яті AST.

#### 5. Рівні оптимізації утиліти GNU find

- **`-O0`:** Оптимізацію повністю вимкнено. Предикати виконуються строго у порядку запису в командному рядку.
- **`-O1` (режим за замовчуванням):** Базове перевпорядкування. Дешеві тести за ім'ям (`-name`, `-path`) пересуваються перед тестами метаданих inode (`-type`, `-size`, `-mtime`), якщо між ними немає операторів `-o` або дій.
- **`-O2`:** Проміжна оптимізація. Тести за `d_type` виносяться перед системними викликами `stat()`; згортаються булеві константи; дії з побічними ефектами зміщуються в кінець ланцюжків.
- **`-O3`:** Повна оптимізація. Виконується повне перетворення AST за законами де Моргана, розрахунок матриці селективності та глобальне перевпорядкування кон'юнкцій і диз'юнкцій.

### Механізм відсікання гілок: предикат `-prune`

Предикат `-prune` наказує алгоритму обходу дерева не занурюватися у підкаталоги поточного каталогу:
- **Семантика повернення:** `-prune` завжди повертає значення `true` (за стандартом POSIX).
- **Взаємодія з `-depth`:** Якщо увімкнено опцію `-depth` (або дію `-delete`), предикат `-prune` не має жодного ефекту (ігнорується з попередженням), оскільки вкладені файли вже були оброблені до досягнення каталогу.

#### Канонічний патерн виключення каталогів

```sh
find . \( -path "./.git" -o -path "./node_modules" \) -prune -o -type f -name "*.js" -print
```

Логіка обчислення AST-дерева:
1. Для каталогу `./.git`: предикат `-path "./.git"` повертає `true`.
2. Виконується предикат `-prune`, який інструктує рушій VFS не спускатися всередину `.git`, і повертає `true`.
3. Оскільки ліва частина оператора `-o` істинна (`true`), уся права частина після `-o` (предикати `-type f -name "*.js" -print`) ігнорується за коротким замиканням.
4. Для звичайного файлу `./src/app.js`: ліва частина дужок повертає `false`, короткого замикання не відбувається, і керування переходить до правої гілки після `-o`.

### Керування потоком виконання

- **`-quit`** (GNU extension) — негайно завершує виконання утиліти `find` із нульовим кодом повернення. Усі заплановані системні виклики та черги сканування скасовуються.
- **`-true`** (GNU extension) — завжди повертає `true`.
- **`-false`** (GNU extension) — завжди повертає `false`.

## Предикати-дії (Actions)

Дії — це термінальні предикати, які виконують побічні ефекти (вивід у потік, запис у файл, видалення з VFS, виклик зовнішніх системних процесів).

| Дія | Стандарт | Опис поведінки | Код повернення |
|---|---|---|---|
| `-print` | POSIX.1 | Виводить повний відносний шлях, завершуючи символом нового рядка `\n`. | Завжди `true` |
| `-print0` | POSIX.1-2024 / GNU | Виводить повний шлях, завершуючи його ASCII NUL-байтом `\0` (0x00). Захист від ін'єкцій. | Завжди `true` |
| `-printf fmt` | GNU extension | Форматований вивід метаданих без запуску зовнішніх процесів (специфікатори нижче). | Завжди `true` |
| `-fprintf file fmt` | GNU extension | Форматований вивід метаданих безпосередньо у файл `file` (буферизований запис). | Завжди `true` |
| `-fprint file` | GNU extension | Записує знайдені шляхи у файл `file` із завершенням `\n`. | Завжди `true` |
| `-fprint0 file` | GNU extension | Записує знайдені шляхи у файл `file` із завершенням `\0`. | Завжди `true` |
| `-delete` | POSIX.1-2024 / GNU | Видаляє поточний файл або порожній каталог через системний виклик `unlinkat()` / `rmdir()`. Автоматично вмикає опцію `-depth`. | `true` при успіху, `false` при помилці |
| `-ls` | GNU / BSD | Друкує рядок метаданих у форматі утиліти `ls -dils`. | Завжди `true` |

| `-exec cmd {} \;` | POSIX.1 | Поштучний запуск `cmd` для кожного окремого файлу; `{}` замінюється на шлях. | `true`, якщо процес повернув статус 0 |
| `-exec cmd {} +` | POSIX.1 | Пакетний режим: накопичує знайдені шляхи в пакет і викликає `cmd` один раз для багатьох аргументів. `{}` має бути останнім аргументом. | Завжди `true` |

| `-execdir cmd {} +` | POSIX.1-2024 / GNU | Пакетний запуск `cmd` усередині відповідного каталогу для всіх знайдених у ньому файлів. | Завжди `true` |

| `-okdir cmd {} \;` | POSIX.1-2024 / GNU | Інтерактивна версія `-execdir \;`. | `true`, якщо підтверджено і статус 0 |

### Порівняння механік виконання команд: `-exec \;`, `-exec +` та `-execdir`

#### 1. Синхронний поштучний запуск (`-exec cmd {} \;`)
- Для кожного знайденого файлу `find` викликає системну послідовність `fork()`, `execvp()` та блокуючий `waitpid()`.
- Якщо знайдено 50 000 файлів, операційна система виконує 50 000 окремих ініціалізацій адресного простору процесу, налаштувань сторінок віртуальної пам'яті та завантажень динамічного лінкера `ld-linux.so`.
- Маркер `{}` може знаходитися у довільному місці списку аргументів.

#### 2. Пакетна агрегація аргументів (`-exec cmd {} +`)
- `find` накопичує знайдені шляхи у внутрішньому масиві `argv[]`.
- Системний виклик `execvp()` запускається лише тоді, коли розмір накопиченого буфера наближається до ліміту ядра `ARG_MAX` або після завершення обходу дерева.
- Замість 50 000 процесів створюється лише 2–4 процеси, зменшуючи час виконання на 95–99%.
- Маркер `{}` зобов'язаний стояти **суворо останнім аргументом** безпосередньо перед символом `+`.

#### 3. Дескрипторна ізоляція та захист від TOCTOU (`-execdir`)
- Перед запуском команди процес переходить у безпосередній батьківський каталог цільового файлу (`fchdir(dirfd)`).
- Аргумент `{}` підставляється не у вигляді глобального шляху `/var/data/incoming/file.txt`, а як локальне відносне ім'я `./file.txt`.
- **Безпека:** Запобігає атакам гонитви (TOCTOU), коли каталог між перевіркою та запуском підміняється символьним посиланням. Також захищає від виконання шкідливих програм, якщо ім'я файлу починається з дефіса (префікс `./` гарантує, що утиліта не розпізнає назву як власний прапорець).

#### 4. Інтерактивне виконання (`-ok` та `-okdir`)
- Перед кожним викликом команди `find` друкує сформований командний рядок у термінал і зчитує один рядок відповіді безпосередньо з керуючого термінала `/dev/tty`.
- Запуск відбувається лише за умови отримання ствердної відповіді (`y` або `yes` відповідно до поточної локалі `LC_MESSAGES` через виклик `rpmatch()`).
- Якщо користувач відхиляє запуск (`n`), дія повертає `false`, а виконання команди скасовується.

### Специфікатори форматування `-printf`

Дія `-printf` утиліти GNU `find` обробляє метадані напряму з пам'яті процесу без виклику `fork()` та без створення накладних витрат конвеєрів:

#### Шляхи та імена
- `%p` — повний відносний шлях файлу від стартової точки.
- `%P` — відносний шлях із вилученим стартовим префіксом точки входу.
- `%f` — базове ім'я файлу (basename без шляху батьківського каталогу).
- `%h` — шлях батьківського каталогу (dirname).
- `%H` — стартовий шлях (starting point), під яким об'єкт було знайдено.

#### Атрибути індексного дескриптора
- `%i` — номер індексного дескриптора inode (`st_ino`).
- `%n` — кількість жорстких посилань на файл (`st_nlink`).
- `%y` — тип файлу (літери `f`, `d`, `l`, `s`, `p`, `b`, `c`, `D`).
- `%Y` — тип файлу, на який вказує символьне посилання (розв'язує symlink; повертає `f, d, l, s, p, b, c`, `N` для битих посилань, `L` для циклів, `?` при помилці `stat()`).
- `%l` — ціль символьного посилання (порожній рядок для інших типів файлів, виклик `readlink()`).
- `%D` — номер пристрою файлової системи у десятковому форматі (`st_dev`).
- `%F` — тип файлової системи (наприклад, `ext4`, `xfs`, `btrfs`, `tmpfs`, виклик `statfs()`).

#### Права доступу та володіння
- `%m` — вісімкове представлення прав доступу без типу файлу (наприклад, `0644`).
- `%M` — символьне представлення прав доступу у стилі `ls -l` (наприклад, `-rw-r--r--`).
- `%u` / `%U` — ім'я власника файлу / числовий ідентифікатор UID (`st_uid`).
- `%g` / `%G` — ім'я групи власника файлу / числовий ідентифікатор GID (`st_gid`).

#### Розміри та блокова пам'ять
- `%s` — точний логічний розмір файлу в байтах (`st_size`).
- `%k` — розмір файлу в 1-кілобайтних блоках файлової системи (`st_blocks · 512 / 1024`).
- `%b` — кількість виділених 512-байтових блоків на диску (`st_blocks`).
- `%S` — коефіцієнт розрідженості файлу (Sparse ratio, обчислюється як `(st_blocks · 512) / st_size`).

#### Часові мітки та форматування дати
- `%t` — дата останньої модифікації `mtime` у форматі `ctime()`.
- `%a` — дата останнього доступу `atime` у форматі `ctime()`.
- `%c` — дата останньої зміни метаданих `ctime` у форматі `ctime()`.
- `%T@` / `%A@` / `%C@` — час `mtime` / `atime` / `ctime` у секундах епохи Unix із дробовою наносекундною частиною.
- Компоненти дати (для префіксів `%T` — mtime, `%A` — atime, `%C` — ctime):
  - `%TY` — 4-значний рік (наприклад, `2026`).
  - `%Tm` — місяць `01`–`12`.
  - `%Td` — день місяця `01`–`31`.
  - `%TH` — година `00`–`23`.
  - `%TM` — хвилина `00`–`59`.
  - `%TS` — секунди `00`–`59` із дробовою частиною.
  - `%TN` — наносекунди `000000000`–`999999999`.
  - `%TF` — дата у форматі ISO 8601 (`YYYY-MM-DD`).
  - `%TT` — час у форматі `HH:MM:SS.NNNNNNNNN`.
  - `%Tz` / `%TZ` — часовий пояс (числовий зсув `+0300` або назва `EEST`).

#### Керуючі символи
- `\0` — ASCII NUL-байт `0x00`.
- `\n` — символ нового рядка `0x0A`.
- `\t` — горизонтальна табуляція `0x09`.
- `\r` — повернення каретки `0x0D`.
- `\a` — звуковий сигнал (Bell).
- `\b` — забій (Backspace).
- `\v` — вертикальна табуляція.
- `\\` — зворотний слеш.

## Параметри та конфігурація утиліти xargs

Утиліта `xargs` зчитує потік токенів зі стандартного входу, формує масиви вказівників `argv[]` у межах системного ліміту пам'яті ядра та викликає системний виклик `execve()`.

| Параметр | Повна назва (GNU) | Стандарт | Призначення та механіка |
|---|---|---|---|
| `-0` | `--null` | POSIX.1-2024 / GNU | Перемикає розділювач на ASCII NUL (`0x00`). Повністю вимикає обробку одинарних/подвійних лапок, зворотних слешів та пробілів. |
| `-d delim` | `--delimiter=delim` | POSIX.1-2024 / GNU | Встановлює кастомний символ-розділювач вхідного потоку (підтримуються escape-послідовності `\n`, `\t`, `\0`, `\0NNN`). Вимикає обробку лапок. |
| `-n N` | `--max-args=N` | POSIX.1 | Передавати не більше `N` аргументів у кожен окремий виклик `execve()`. |
| `-L N` | `--max-lines=N` | POSIX.1 | Зчитувати не більше `N` непорожніх рядків для формування одного запуску. Автоматично вмикає опцію `-x`. |
| `-I str` | `--replace=str` | POSIX.1 | Підставляти аргумент замість маркера `str` у зазначені позиції команди. Автоматично вмикає `-L 1` та вимикає пакетування аргументів. |
| `-s max-chars` | `--max-chars=max` | POSIX.1 | Максимальний сумарний розмір пам'яті в байтах для масиву аргументів та змінних оточення одного запуску. |
| `-P N` | `--max-procs=N` | POSIX.1-2024 / GNU | Кількість паралельних дочірніх процесів у пулі воркерів (`-P 0` запускає максимально можливу кількість процесів одночасно). |
| `-r` | `--no-run-if-empty` | POSIX.1-2024 / GNU | Не запускати команду, якщо вхідний потік порожній (за замовчуванням POSIX xargs виконує команду один раз навіть без вхідних аргументів). |
| `-t` | `--verbose` | POSIX.1 | Друкувати сформований командний рядок у потік `stderr` перед кожним системним викликом `execve()`. |
| `-p` | `--interactive` | POSIX.1 | Запитувати інтерактивне підтвердження користувача у `/dev/tty` перед кожним запуском команди. |
| `-E eof-str` | `-e[eof-str]` | POSIX.1 | Маркер кінця вхідного потоку (End of File string). При виявленні рядка `eof-str` читання стандартного входу негайно припиняється. |
| `-x` | `--exit` | POSIX.1 | Аварійно завершувати роботу `xargs`, якщо обсяг аргументів перевищує ліміт `-s` або ліміт рядків `-L`. |
| `-a file` | `--arg-file=file` | GNU extension | Зчитувати аргументи безпосередньо з файлу `file` замість стандартного входу `stdin` (запобігає перехопленню stdin запущеними підпроцесами). |
| `--process-slot-var=var` | — | GNU extension | Експортувати номер виділеного слота процесу (від `0` до `N-1`) у змінну оточення `var` для кожного воркера паралельного пулу `-P`. |

### Токенізація за замовчуванням та небезпека whitespace

У стандартному режимі POSIX `xargs` розбиває вхідний потік даних за правилами командної оболонки Unix:
- Будь-які неекscreenовані пробіли, символи табуляції `\t` та символи нового рядка `\n` розглядаються як межі токенів (розділювачі аргументів).
- Одинарні лапки `'...'` та подвійні лапки `"..."` екранують розділювачі всередині рядка.
- Зворотний слеш `\` екранує наступний символ.

*Критична вразливість конвеєрів:* якщо файл має назву `Project Budget 2026.pdf`, наївний конвеєр `find . -name "*.pdf" | xargs rm` розіб'є його на три окремі аргументи: `Project`, `Budget` та `2026.pdf`. Якщо ж файл містить непарну одинарну лапку (наприклад, `user's_file.txt`), `xargs` перейде в режим очікування закриваючої лапки і завершиться з системною помилкою синтаксису:

```
xargs: unmatched single quote; by default quotes are special to xargs unless you use the -0 option
```

Прапорець **`-0` (`--null`)** повністю вимикає парсер лапок та слешів: єдиним валідним байтом-розділювачем стає нульовий символ `\0` (0x00), який є єдиним байтом (разом із `/`), забороненим у назвах файлів стандартом POSIX VFS.

### Механіка паралельного пулу воркерів (`-P`) та життєвий цикл процесів

Параметр `-P max-procs` активує вбудований диспетчер пулу процесів:

1. **Диспетчеризація та неблокуючий моніторинг:**
   - Диспетчер вичитує чергову порцію аргументів зі стандартного входу.
   - Викликає `fork()` та `execvp()`, реєструючи PID новоствореного воркера у внутрішньому масиві активних завдань.
   - Якщо кількість активних процесів досягла ліміту `max-procs`, головний процес переходить у режим очікування за допомогою блокуючого системного виклику `waitpid(-1, &status, 0)`.
   - Щойно будь-який воркер завершує роботу, диспетчер звільняє його слот і негайно породжує наступний процес для залишку черги аргументів.
2. **Динамічне масштабування пулу (GNU xargs):**
   - Процес `xargs` обробляє сигнали керування розміром пулу на льоту:
     - сигнал **`SIGUSR1`** збільшує ліміт одночасних процесів на `1`;
     - сигнал **`SIGUSR2`** зменшує ліміт процесів на `1` (якщо активних процесів більше за новий ліміт, `xargs` чекає на їх природне завершення, не породжуючи нових).
3. **Ідентифікація воркерів через слоти (`--process-slot-var`):**
   - При прапорці `--process-slot-var=SLOT` диспетчер присвоює кожному паралельному воркеру цілочисельний індекс слота від `0` до `max-procs - 1` та експортує його в оточення процесу. Це дозволяє воркерам без конфліктів використовувати виділені ресурси (локальні тимчасові файли, ізольовані мережеві порти, окремі схеми БД).

### Агрегування виводу, атомарність PIPE_BUF та запобігання гонитвам запису

При паралельному виконанні воркерів (`xargs -P N`) стандартні потоки виведення `stdout` та `stderr` усіх дочірніх процесів успадковують спільний дескриптор анонімного каналу (pipe) або цільового файлу.

#### 1. Проблема перемішування рядків (Torn Writes)

Якщо кілька процесів одночасно записують дані у спільний потік, фрагменти їхнього виводу можуть чергуватися на рівні окремих байтів або слів, руйнуючи структуру записів (Interleaved Output Corruption).

#### 2. Атомарність системного виклику `write()` та константа `PIPE_BUF`

Стандарт POSIX.1 гарантує атомарність запису в канал (FIFO або Anonymous Pipe) за виконання таких умов:
- Системний виклик `write(fd, buf, count)` виконується **суворо атомарно**, якщо розмір буфера `count` не перевищує константу **`PIPE_BUF`**.
- У ядрі Linux для анонімних каналів константа `PIPE_BUF` становить рівно **4096 байтів (4 KB)** (визначено в `<limits.h>` та `include/uapi/linux/limits.h`).
- Якщо розмір порції перевищує 4096 байтів (наприклад, 8192 байти), ядро має право розбити запис на кілька фрагментів, між якими вставиться вивід іншого паралельного процесу.

Звідси випливає інженерне правило безпечного конвеєра: якщо паралельні воркери формують структурований вивід (наприклад, окремі рядки JSON або CSV), і кожен окремий запис формується в пам'яті та записується одним системним викликом `write()` розміром не більше 4096 байтів, вивід у конвеєрі `xargs -P N ... | aggregator` залишається гарантовано консистентним і неперемішаним.

#### 3. Гонитви при записі у спільні регулярні файли (`O_APPEND`)

Для звичайних файлів на диску гарантія `PIPE_BUF` не діє.
- Відкриття файлу з прапорцем `O_APPEND` гарантує, що ядро перед кожним окремим системним викликом `write()` атомарно перемістить файловий покажчик `f_pos` на поточний фізичний кінець файлу.
- Однак, якщо програма-воркер генерує один логічний запис кількома послідовними викликами `write()` (наприклад, окремо ім'я файлу, окремо двокрапку, окремо результат) або використовує блокову буферизацію `printf`, операції `write()` різних процесів чергуються, руйнуючи цілісність записів.

#### 4. Патерни безпечного паралельного агрегування

Для запобігання гонитвам та перемішуванню даних застосовують три архітектурні схеми:

1. **Ізоляція через файли слотів / PID з подальшим детермінованим злиттям:**
   Кожен воркер записує свій результат в індивідуальний тимчасовий файл на основі номера слота, після чого фінальний крок об'єднує результати:
   ```sh
   find . -type f -print0 | xargs -0 -P 4 --process-slot-var=SLOT \
       sh -c 'process_file "$@" > "/tmp/out_${SLOT}_$$.tmp"' _
   cat /tmp/out_*.tmp > final_report.txt && rm /tmp/out_*.tmp
   ```

2. **Блокування на рівні файлових дескрипторів (`flock`):**
   Критична секція запису обгортається у виклик консультативного блокування `flock(fd, LOCK_EX)`:
   ```sh
   find . -type f -print0 | xargs -0 -P 4 -n 1 \
       sh -c 'res=$(process "$1"); flock -x /tmp/report.lock -c "printf \"%s\n\" \"$res\" >> /tmp/report.txt"' _
   ```

3. **Централізований процес-колектор:**
   Воркери передають атомарні NUL-розділені повідомлення через канал на вхід єдиного однопотокового агрегатора, який послідовно вичитує та зберігає дані.

### Взаємодія модифікаторів запуску: `-n`, `-L`, `-I` та `-s`

1. **`-n max-args` проти `-L max-lines`:** Опція `-n` обмежує точну кількість слів/токенів у виклику, тоді як `-L` рахує кількість непорожніх рядків вхідного потоку. Зазначення `-L` неявно активує прапорець аварійної зупинки `-x`.
2. **Шаблонна підстановка (`-I str`):** Прапорець `-I` вимикає пакетну агрегацію: для кожного вхідного рядка генерується окремий виклик `execve()`. Неявно виставляється `-L 1`.
3. **Бюджетний ліміт `-s max-chars`:** Якщо сумарна довжина сформованого масиву `argv[]` та змінних оточення перевищує `max-chars`, `xargs` розбиває аргументи на менші пакети. Якщо ж прапорець `-x` активний і один окремий аргумент перевищує `max-chars`, `xargs` завершує роботу з кодом помилки `125`.

### Промислові інженерні патерни xargs для високонавантажених конвеєрів

У промислових системах `xargs` виступає ядром пакетної обробки неструктурованих даних, паралельної компресії та мережевого трансферу. Нижче наведено вивірені інженерні схеми для трьох типових сценаріїв.

#### 1. Пакетна обробка та транзакційне виконання складних SQL-команд

Поштучне виконання мільйонів SQL-виразів (наприклад, операцій `INSERT`, `UPDATE` чи `DELETE`) через окремі виклики клієнта СУБД призводить до колапсу продуктивності: кожне підключення створює накладні витрати на TCP-рукостискання, аутентифікацію, парсинг AST-запиту та окрему фіксацію в журналі передзапису WAL (Write-Ahead Logging).

`xargs` дозволяє формувати збалансовані транзакційні пакети:

```sh
# Агрегація 100 SQL-файлів у єдиний транзакційний блок BEGIN ... COMMIT
find /var/data/sql_chunks -type f -name "*.sql" -print0 | \
    xargs -0 -n 100 -P 4 sh -c '
        (printf "BEGIN;\n"; cat "$@"; printf "COMMIT;\n") | \
        psql -U postgres -d warehouse -v ON_ERROR_STOP=1 --single-transaction
    ' _
```

*Технічні інваріанти патерну:*
- **Пакетування (`-n 100`):** `cat "$@"` конкатенує рівно 100 файлів в один безперервний потік байтів, зменшуючи кількість клієнтських транзакцій у 100 разів.
- **Транзакційне обрамлення:** вивід обгортається у `BEGIN;` та `COMMIT;`, гарантуючи атомарність усього пакета на рівні рушія БД.
- **Аварійна зупинка (`-v ON_ERROR_STOP=1`):** при виникненні будь-якої синтаксичної або констрейнт-помилки `psql` негайно перериває виконання та завершується з кодом `3`, що фіксується диспетчером `xargs` (загальний код помилки `123`).

Масовий імпорт CSV-фрагментів через команду `\copy`:

```sh
# Паралельне завантаження 8 потоками по 10 файлів на пакет
find /data/incoming -type f -name "part_*.csv" -print0 | \
    xargs -0 -n 10 -P 8 sh -c '
        for csv_file in "$@"; do
            psql -U loader -d analytics -c "\copy raw_events FROM '\''$csv_file'\'' WITH (FORMAT csv, HEADER true);" || exit 255
        done
    ' _
```

*Механізм переривання через код `255`:* якщо окремий імпорт зазнає невдачі, скрипт викликає `exit 255`. Статус `255` є спеціальним сигналом для стандарту POSIX `xargs`, який наказує утиліті негайно перервати подальше зчитування вхідного потоку і зупинити роботу пулу.

#### 2. Високопродуктивна паралельна компресія та декомпресія (Parallel Compression: gzip / zstd / pixz)

Сучасні утиліти компресії (зокрема `zstd -T0` або `pigz`) підтримують внутрішню багатопотоковість. Проте при обробці великого масиву незалежних файлів (наприклад, 100 000 файлів по 1–50 МБ) підхід із запуском пулу однопотокових процесів через `xargs -P $(nproc)` демонструє вищу швидкість та коефіцієнт стиснення:

- **Локальність кешу (Cache Locality):** кожен воркер `zstd -T1` повністю обробляє свій файл у межах L1/L2 кешу одного ядра CPU без міжядерних блокувань та синхронізації контекстів пам'яті.
- **Цілісність словника стиснення:** внутрішній багатопотік (`zstd -T0`) розбиває один файл на окремі сегменти, через що стиснення на стиках блоків погіршується. Однопотоковий процес стискає файл як єдиний суцільний потік.
- **Динамічний баланс (Work Stealing):** оскільки розміри файлів різняться, диспетчер `xargs` через виклики `waitpid()` негайно призначає нову порцію тому ядру, яке звільнилося першим, усуваючи простій процесорів (Straggler problem).

Патерн максимального паралельного стиснення:

```sh
# Стиснення архівних логів у nproc потоків пакетами по 64 файли
find /var/log/remote -type f -name "*.log" -print0 | \
    xargs -0 -n 64 -P $(nproc) zstd -q --rm -19 -T1
```

*Оптимізація розміру пакета `-n`:*
- Для дрібних файлів (< 100 KB): великий пакет `-n 64..256` амортизує витрати на виклики `fork()` / `execve()`.
- Для надвеликих файлів (> 100 MB): пакет `-n 1` або `-n 2` запобігає перекосу навантаження між ядрами.

Патерн паралельної декомпресії та потокової фільтрації на льоту:

```sh
# Паралельне розпакування збірок з об'єднанням виводу в єдиний агрегатор
find /storage/dumps -type f -name "*.zst" -print0 | \
    xargs -0 -n 16 -P 8 zstd -dcq | \
    grep --line-buffered "CRITICAL_AUTH_FAILURE" >> /var/log/security_audit.log
```

#### 3. Потокове паралельне завантаження у хмарні об'єктні сховища (S3, GCS, Ceph/MinIO)

При завантаженні сотень тисяч файлів у хмарне сховище (AWS S3, Google Cloud Storage, Ceph Object Gateway) однопотоковий клієнт витрачає понад 90% часу на мережеві затримки підтвердження запитів (RTT).

Патерн паралельного пакетного трансферу:

```sh
# Паралельне завантаження у 16 потоків з підстановкою структури каталогів
find /storage/backups -type f -print0 | \
    xargs -0 -n 25 -P 16 -I {} aws s3 cp "{}" "s3://production-backups-bucket/{}" --only-show-errors
```

Патерн потокового трансферу без проміжного запису на диск (Zero-Disk-Spill Stream Upload):

```sh
# Потокове стиснення в пам'яті та передача через стандартний вхід AWS CLI
find /var/data/raw_metrics -type f -name "*.dat" -print0 | \
    xargs -0 -n 1 -P 12 sh -c '
        base_name=$(basename "$1")
        zstd -c "$1" | aws s3 cp - "s3://metrics-lake-bucket/compressed/${base_name}.zst"
    ' _
```

*Інженерні застереження при роботі з хмарними API:*
- **Обмеження сокетів та дескрипторів:** переконайтеся, що системний ліміт `ulimit -n` (дескриптори файлів) процесу перевищує `N_workers · 4`.
- **Захист від Rate Limiting (HTTP 429 Too Many Requests / 503 Slow Down):** обмежуйте кількість паралельних воркерів (`-P 8..16`), щоб не перевищувати ліміти операцій `PUT` на рівні префіксів бакетів.
- **Експоненціальний відкат:** при виклику зовнішніх SDK/CLI налаштовуйте автоматичні повтори із випадковим джитером (Exponential Backoff with Jitter).

## Системні обмеження ядра: ARG_MAX, MAX_ARG_STRLEN та пам'ять процесу

Системний виклик `execve(const char *pathname, char *const argv[], char *const envp[])` виконує заміну адресного простору процесу. Усі передані аргументи `argv[]` та змінні оточення `envp[]` ядро копіює у верхню частину стеку нового образу процесу.

```
Верхній адресний простір стеку процесу Linux (x86_64):
┌────────────────────────────────────────────────────────┐ 0x7fffffffffff
│ ELF Auxiliary Vector (auxv_t: AT_PHDR, AT_PAGESZ, ...) │
├────────────────────────────────────────────────────────┤
│ Масив покажчиків envp[] (char *envp[M])                │
├────────────────────────────────────────────────────────┤
│ Масив покажчиків argv[] (char *argv[N])                │
├────────────────────────────────────────────────────────┤
│ Рядки змінних оточення (NULL-terminated strings)       │
├────────────────────────────────────────────────────────┤
│ Рядки аргументів командного рядка (NULL-terminated)    │
├────────────────────────────────────────────────────────┤
│ argc (int, 8 байтів вирівнювання)                      │
└────────────────────────────────────────────────────────┘
```

### Константи та динамічні ліміти (ARG_MAX, MAX_ARG_STRLEN, RLIMIT_STACK)

1. **`_POSIX_ARG_MAX`** (стандарт POSIX, `<limits.h>`): гарантований нижній ліміт для POSIX-сумісних систем становить 4096 байтів.
2. **`sysconf(_SC_ARG_MAX)`**: системний виклик повертає поточний сумарний ліміт системи. У ядрі Linux (починаючи з версії 2.6.23) максимальний розмір області аргументів і оточення визначається динамічно на основі ліміту стеку:
   - Якщо `RLIMIT_STACK` має стандартне значення (наприклад, 8 MB), ліміт простору аргументів становить **25% від розміру стеку**:
     `ARG_MAX = min(RLIMIT_STACK / 4, (3/4) · RLIMIT_STACK) = 2 MB`
   - Якщо ліміт стеку знято (`ulimit -s unlimited`), ядро встановлює абсолютний верхній ліміт `ARG_MAX` на рівні `3/4 · _STK_LIM` (зазвичай 6 MB).
3. **`MAX_ARG_STRLEN`** (ліміт довжини одного аргументу):
   - У вихідному коді ядра Linux (`fs/exec.c`) встановлено константу `MAX_ARG_STRLEN = 32 * PAGE_SIZE`. На архітектурах із розміром сторінки пам'яті 4 KB (x86_64, ARM64) це становить рівно **131 072 байти (128 KB)**.
   - Цей ліміт обмежує максимальну довжину **одного окремого рядка** у масиві `argv[]` або `envp[]`.
   - Якщо хоча б один аргумент (наприклад, гігантський шлях або вбудований blob даних) перевищує 128 KB, системний виклик `execve()` негайно завершується з помилкою `E2BIG` (Argument list too long), навіть якщо сумарний обсяг усіх аргументів складає лише кілька сотень кілобайтів і не перевищує `ARG_MAX`.

### Розрахунок бюджету пам'яті в xargs та find -exec +

Під час ініціалізації утиліти `xargs` та `find` (для режиму пакетування `-exec ... +`) обчислюють максимально доступний розмір буфера для накопичення аргументів:

```
Бюджет_аргументів = sysconf(_SC_ARG_MAX) - розмір(environ) - розмір(покажчики) - 2048 байтів
```

Резерв у 2048 байтів вимагається стандартом POSIX для гарантованого збереження допоміжного вектора ELF (`elf_info`), адресних структур та забезпечення вирівнювання стеку ядра.

Для кожного доданого токена враховуються такі накладні витрати пам'яті:
1. Довжина самого рядка разом із термінатором NUL: `strlen(arg) + 1`.
2. Розмір покажчика на рядок у масиві `char *argv[]`: `sizeof(char *)` (8 байтів на 64-бітних архітектурах x86_64 / AArch64).

Якщо додавання чергового файлу призведе до перевищення розрахованого бюджету, `xargs` або `find` закриває поточний пакет, викликає `execve()` для накопиченого масиву і починає формування нового пакета.

## Специфікація статусів завершення (Exit Codes)

### Статуси завершення утиліти find

| Код | Семантичне значення | Технічна умова виникнення |
|---|---|---|
| `0` | Повний успіх | Усі стартові шляхи та підкаталоги успішно обійдені без помилок VFS, синтаксису чи дій. |
| `>0` | Помилка обходу або виконання | Виникли помилки доступу до каталогу (`EACCES`), втрата файлів без `-ignore_readdir_race`, невалідний синтаксис виразів або дія `-exec ... +` повернула ненульовий статус. |

### Статуси завершення утиліти xargs

| Код | Стандарт | Семантичне значення | Технічна першопричина |
|---|---|---|---|
| `0` | POSIX.1 | Успіх (Success) | Усі згенеровані дочірні процеси успішно завершилися з кодом 0, або вхідний потік був порожнім при використанні прапорця `-r`. |
| `1–125` | POSIX.1 | Помилка дочірньої програми | Хоча б один запущений процес повернув ненульовий статус у діапазоні `1–125` (у послідовному режимі повертається статус останньої невдалої команди). |
| `123` | GNU extension | Помилка у пулі процесів | Один або кілька запусків повернули статус `1–125` при використанні паралельного пулу воркерів `-P`. |
| `124` | GNU extension | Зупинка конвеєра / статус 255 | Дочірня програма завершилася зі статусом `255`, або виконання було примусово перервано сигналом чи вичерпанням таймауту. |
| `125` | POSIX.1 | Внутрішній збій `xargs` | Помилка виділення динамічної пам'яті (`malloc`), перевищення ліміту розміру рядка `-s` при прапорці `-x`, або невалідні прапорці запуску. |
| `126` | POSIX.1 | Неможливо виконати | Цільовий бінарний файл знайдено у VFS, але відсутні права на запуск (`EACCES`) або файл не є виконуваним бінарним форматом (`ENOEXEC`). |
| `127` | POSIX.1 | Команду не знайдено | Цільову програму не знайдено у жодному з каталогів змінної оточення `PATH` (`ENOENT`). |
| `255` | POSIX.1 | Сигнал екстреної зупинки | Дочірній процес повернув код `255`, що змушує `xargs` негайно перервати подальше зчитування вхідного потоку і зупинити роботу конвеєра. |

### Обробка сигналів у пулі процесів

Утиліта `xargs` перехоплює системні сигнали `SIGINT` (Ctrl+C), `SIGTERM` та `SIGHUP`:
1. При отриманні сигналу `xargs` не завершується миттєво, а транслює сигнал усій групі активних дочірніх процесів (`kill(-pgid, sig)`).
2. Очікує завершення всіх активних воркерів через цикл `waitpid()`.
3. Очищує внутрішні дескриптори та аварійно завершує роботу.
4. Якщо сигнал `SIGPIPE` надходить від закритого конвеєра, `xargs` негайно припиняє читання вхідного потоку і завершує поточні процеси.
