# 🧮 Математичний аналіз вікна таймауту, джиттеру та надійності

Безперервна робота систем під управлінням Linux вимагає математично обґрунтованого розрахунку параметрів сторожового таймера. Неправильно обраний інтервал надсилання пінгів (Heartbeat) або ігнорування затримок планувальника задач (Scheduling Jitter) призводить до двох крайніх негативних наслідків: хибного перезавантаження працездатної системи під навантаженням або надто пізнього виявлення фактичного зависання. Ця вставка виводить детерміновані межі та імовірнісну модель надійності для вікна таймауту `/dev/watchdog`.

## 1. Детермінована модель вікна скидання

Позначимо основні параметри системи:
* `T_out` — апаратний інтервал таймауту сторожового таймера (секунди), після згасання якого генерується сигнал `RESET#`.
* `T_pre` — інтервал попереднього повідомлення (Pretimeout), за який до спрацювання скидання генерується NMI чи переривання ядра.
* `T_ping` — номінальний інтервал між двома послідовними викликами `WDIOC_KEEPALIVE` або повідомленнями `sd_notify`.
* `τ_max` — максимальна очікувана затримка виконання демона супервізії (включаючи затримки контекстного перемикання, блокування VFS та деградацію системного часу під високим CPU Load).
* `δ` — відносна нестабільність частоти апаратного генератора таймера (Clock Drift), де `δ > 0` означає, що лічильник іде швидше за номінал і апаратне вікно фактично коротшає — беремо саме цей, найгірший для нас, бік (зазвичай `δ ∈ [0.01, 0.05]`).

Апаратний лічильник зменшується з реальним часом `t`. Фактичний час до спрацювання апаратного скидання з урахуванням дрейфу кварцового резонатора становить:

```
T_hw_real = T_out / (1 + δ)
```

Для того щоб система **гарантовано не зазнала хибного перезавантаження**, наступний пінг повинен надійти до апаратного регістру раніше, ніж лічильник досягне позначки `T_pre`. Отже, абсолютний час прибуття пінгу `t_next = T_ping + τ_max` має задовольняти нерівність:

```
T_ping + τ_max < T_out / (1 + δ) - T_pre
```

Звідси виводиться граничний допустимий інтервал між пінгами `T_ping_max`:

```
T_ping + τ_max < (T_out - T_pre · (1 + δ)) / (1 + δ)
T_ping < (T_out - T_pre · (1 + δ)) / (1 + δ) - τ_max   [гранична нерівність безпечного пінгу]
```

Якщо Pretimeout не використовується (`T_pre = 0`), формула спрощується до вигляду:

```
T_ping_max = T_out / (1 + δ) - τ_max
```

### Коефіцієнт запасу (Safety Factor)

У практичній інженерії використовується коефіцієнт запасу `S_f = T_out / T_ping`. За стандартними рекомендаціями `S_f ≥ 2.0`, тобто номінальний інтервал пінгу обирають як половину апаратного таймауту:

```
T_ping = T_out / 2
```

При `T_ping = T_out / 2` максимальний допустимий джиттер `τ_max` до моменту хибного перезавантаження розраховується як:

```
τ_max_allowed = T_out / (1 + δ) - T_out / 2 - T_pre
```

## 2. Покроковий числовий розрахунок

Розглянемо реальний приклад конфігурації промислового контролера:
* Апаратний таймаут `T_out = 30` с.
* Інтервал Pretimeout `T_pre = 5` с.
* Максимальний дрейф частоти `δ = 0.03` (3%).
* Максимальна затримка планувальника під навантаженням `τ_max = 4` с.

Обчислимо максимальний безпечний інтервал між пінгами `T_ping_max`:

```
T_out / (1 + δ)
= 30 / (1 + 0.03)
= 30 / 1.03
= 29.126 с           [дійсний апаратний час до скидання]

T_pre_real
= T_pre · (1 + δ)
= 5 · 1.03
= 5.150 с            [ефективна висота порогу Pretimeout]

T_avail
= 29.126 - 5.150
= 23.976 с           [доступне часове вікно для пінгу]

T_ping_max
= 23.976 - τ_max
= 23.976 - 4.0
= 19.976 с           [абсолютна верхня межа інтервалу T_ping]
```

Якщо розробник встановить `T_ping = 15` секунд, система збереже запас міцності `19.976 - 15 = 4.976` секунд на додаткові випадкові затримки.

## 3. Імовірнісна модель хибного спрацювання (False Reboot)

У високонавантажених системах затримка виконання демона `τ` не є фіксованою величиною, а є випадковою величиною з щільністю розподілу ймовірностей `p(τ)`. Для систем під управлінням Linux без RT-ядра (PREEMPT_RT) затримка контекстного перемикання демона описується експоненційним розподілом або розподілом Парето (з важким хвостом при блокуваннях у VFS чи в пам'яті):

```
p(τ) = (1 / λ) · exp(-τ / λ),   де τ ≥ 0
```

Тут `λ` — середній час затримки планувальника (середнє значення `E[τ] = λ`).

Імовірність того, що окремий пінг запізниться на час, більший за критерій безпеки `ΔT = T_hw_real - T_pre - T_ping`, визначається інтегруванням хвоста розподілу:

```
P_fail = P(τ > ΔT)
       = ∫[ΔT..∞] p(τ) dτ
       = ∫[ΔT..∞] (1 / λ) · exp(-τ / λ) dτ
       = [-exp(-τ / λ)] від ΔT до ∞
       = exp(-ΔT / λ)                          [імовірність пропуску пінгу за один цикл]
```

### Розрахунок середнього часу між хибними перезавантаженнями (MTBF)

Якщо демон надсилає пінг кожні `T_ping` секунд, то кількість спроб за секунду становить `f = 1 / T_ping`. Середній час між хибними спрацьовуваннями системи (Mean Time Between False Reboots) становить:

```
MTBF_false
= T_ping / P_fail                                [визначення середнього часу за імовірністю P_fail]
= T_ping / exp(-ΔT / λ)                          [підстановка вираженої імовірності P_fail]
= T_ping · exp((T_hw_real - T_pre - T_ping) / λ) [вплив перетворення від'ємного показника степеня]
```

Проаналізуємо математичну залежність:
1. Збільшення вікна `ΔT` експоненційно підвищує `MTBF_false`.
2. Якщо середня затримка системи `λ = 0.5` с, а доступне вікно `ΔT = 5` с:

```
P_fail = exp(-5 / 0.5) = exp(-10) ≈ 4.54 × 10⁻⁵
```

Для системи із `T_ping = 10` с це дає:

```
MTBF_false = 10 / (4.54 × 10⁻⁵) ≈ 220 264 с ≈ 2.55 доби
```

Якщо ж зменшити інтервал `T_ping` до `5` секунд (збільшивши `ΔT` до `10` секунд):

```
P_fail = exp(-10 / 0.5) = exp(-20) ≈ 2.06 × 10⁻⁹
MTBF_false = 5 / (2.06 × 10⁻⁹) ≈ 2.42 × 10⁹ с ≈ 76.9 років
```

## 4. Подвійне повторення та аналіз чутливості

Для подальшого підвищення надійності системи розробники застосовують тактику повторних пінгів у межах одного вікна таймауту. Порахуємо імовірність послідовного пропуску `k` пінгів поспіль при незалежних затримках планувальника:

```
P_fail_k = (P_fail)ᵏ = exp(-k · ΔT / λ)
```

Якщо система надсилає `k = 2` пінги у проміжку до настання таймауту, імовірність одночасного пропуску обох пінгів падає до квадратично малої величини:

```
P_fail_2 = exp(-2 · 10 / 0.5) = exp(-40) ≈ 4.25 × 10⁻¹⁸
```

## 6. Математична модель вікна KExec та перезавантаження ядра

Під час використання системного виклику `kexec_load()` для перезавантаження ядра Linux без проходження через BIOS/UEFI простір користувача повністю зупиняється. Поточне ядро виконує деініціалізацію пристроїв і передає управління новому образу ядра у пам'яті. Час такої процедури становить `T_kexec`.

Щоб апаратний Watchdog не викликав апаратний скид під час того, як друге ядро ще не завантажило свій драйвер, таймаут ядра тимчасово розширюється до значення `T_kexec_timeout`:

```
T_kexec_timeout > T_kexec + T_boot_driver + τ_init
```

Де `T_boot_driver` — час від початку ініціалізації ядра до виклику `watchdog_register_device()`, а `τ_init` — затримка старту демона супервізії у новому середовищі. Якщо `T_kexec` становить 4 секунди, а стартовий час драйвера `T_boot_driver = 3` секунди, сама сума дає 7 секунд; із запасом на затримку старту демона в новому середовищі `KExecWatchdogSec` у `systemd` беруть приблизно вдвічі більшим — близько 15 секунд.

З наведених оцінок видно, що вибір частоти пінгування `T_ping = T_out / 3` або `T_ping = T_out / 2` у поєднанні з Pretimeout відсуває хибне перезавантаження на строки, незрівнянно більші за час життя самої системи, — навіть там, де затримки мають важкі хвости. Нулем ця ймовірність не стає: модель лише показує, наскільки швидко вона спадає з ростом вікна `ΔT`.
