Коли сервіс бази даних, внутрішня веб-панель керування або мікросервіс розгортаються у приватній ізольованій підмережі, прямий мережевий доступ до їхніх портів з публічного інтернету перекривається корпоративними брандмауерами та трансляторами мережевих адрес (NAT). Відкриття службових портів (таких як 5432 для PostgreSQL, 3306 для MySQL чи 6379 для Redis) на зовнішніх мережевих інтерфейсах створює пряму загрозу несанкціонованого сканування та перехоплення автентифікаційних даних. Водночас розгортання повноцінного VPN-з'єднання на рівні операційної системи нерідко є надлишковим, вимагає привілеїв суперкористувача `root` і змінює маршрутизацію всього мережевого стека машини.

Протокол SSH (Secure Shell) пропонує вбудоване альтернативне рішення — тунелювання портів (Port Forwarding). Цей механізм дозволяє прозоро інкапсулювати довільні потоки байтів протоколу TCP всередину вже встановленого, криптографічно захищеного та автентифікованого SSH-з'єднання. Клієнтська програма взаємодіє зі звичайним локальним сокетом операційної системи, навіть не підозрюючи, що її трафік шифрується, передається через стандартний порт 22 віддаленого сервера-бастіону і транслюється до кінцевого цільового вузла.

## 1. Архітектура SSH-тунелювання: Connection Layer та інкапсуляція TCP

Щоб зрозуміти внутрішню роботу тунелів, необхідно розглянути структуру протоколу SSH-2, стандартизовану документами IETF RFC 4251–4254. Архітектура протоколу розділена на три незалежні функціональні рівні:

1. **Transport Layer Protocol (RFC 4253):** Відповідає за встановлення первинного TCP-з'єднання (за замовчуванням порт 22), узгодження алгоритмів шифрування (симетричні шифри AES-GCM, ChaCha20-Poly1305), обмін криптографічними ключами за алгоритмом Діффі-Гелмана та контроль цілісності даних.
2. **User Authentication Protocol (RFC 4252):** Виконує автентифікацію клієнта на сервері (за відкритим ключем, паролем або інтерактивним методом).
3. **Connection Protocol (RFC 4254):** Працює поверх захищеного та автентифікованого транспорту, забезпечуючи мультиплексування множини логічних каналів (Channels) всередині одного фізичного TCP-потоку.

Історичні передумови створення цієї трирівневої моделі та відмова від монолітного дизайну SSH-1 детально викладені у вставці [📜 Історія появи та еволюції SSH-тунелювання: від rsh до RFC 4254](root:sys-unix/ssh-port-forwarding/hist-ssh-tunneling-evolution.md).

![Мультиплексування логічних каналів у Connection Layer протоколу SSH](/root/sys/sys-unix/ssh-port-forwarding/img/ssh-channel-multiplexing.svg)
*Мультиплексування логічних каналів усередині єдиного шифрованого SSH-з'єднання: термінальна сесія та незалежні TCP-тунелі.*

### Мультиплексування та керування каналами

Кожен логічний потік даних у SSH — будь то сеанс командної оболонки, виконання одиночної команди, графічне вікно X11 або прокинутий TCP-порт — функціонує як окремий незалежний канал. Обидві сторони з'єднання (клієнт і сервер) призначають кожному каналу власний числовий ідентифікатор (`channel number`). Це дозволяє однозначно адресувати пакети корисного навантаження всередині спільного шифрованого тунелю.

Коли прикладний застосунок ініціює з'єднання з прокинутим портом, SSH-клієнт надсилає серверу повідомлення запиту на відкриття каналу:

```
byte      SSH_MSG_CHANNEL_OPEN (код 90)
string    channel_type ("direct-tcpip" або "forwarded-tcpip")
uint32    sender_channel (локальний номер каналу)
uint32    initial_window_size (початковий розмір вікна прийому в байтах)
uint32    max_packet_size (максимальний розмір пакета корисного навантаження)
... специфічні поля адресації ...
```

Якщо сервер дозволяє операцію (наприклад, конфігурація `sshd_config` не забороняє перенаправлення TCP), він викликає системний виклик `connect()` до цільового сервісу і відповідає повідомленням `SSH_MSG_CHANNEL_OPEN_CONFIRMATION` (код 91), вказуючи призначений зі свого боку номер каналу (`recipient_channel`). Якщо з'єднання відхилено, сервер повертає `SSH_MSG_CHANNEL_OPEN_FAILURE` (код 92) з відповідним кодом причини (наприклад, `SSH_OPEN_ADMINISTRATIVELY_PROHIBITED` або `SSH_OPEN_CONNECT_FAILED`).

### Керування потоком даних на рівні каналів (Flow Control)

Протокол TCP на транспортному рівні забезпечує надійність та регулювання швидкості між клієнтом і сервером SSH в цілому. Однак, оскільки всередині єдиного TCP-з'єднання одночасно передаються десятки різних каналів, виникає потреба в індивідуальному регулюванні швидкості кожного каналу окремо. Якби один прокинутий порт почав перекачувати гігабайтний файл на максимальній швидкості, буфери сокета переповнилися б, і користувач у термінальній сесії відчув би затримку введення символів.

Для запобігання цій проблемі в RFC 4254 впроваджено механізм віконного керування потоком (Window-based Flow Control):

- Кожна сторона повідомляє партнеру значення `window_size` — кількість байтів корисного навантаження, яку вона готова прийняти для даного каналу без переповнення своїх буферів.
- Передача даних здійснюється пакетами `SSH_MSG_CHANNEL_DATA` (код 94). Щоразу, коли відправник передає `N` байтів даних, він зменшує залишок доступного вікна отримувача на `N`.
- Коли залишок вікна наближається до нуля, відправник зобов'язаний призупинити передачу.
- Як тільки отримувач зчитує дані зі свого внутрішнього буфера і звільняє пам'ять, він надсилає повідомлення `SSH_MSG_CHANNEL_WINDOW_ADJUST` (код 93), додаючи нову порцію байтів до доступного вікна.

Завдяки цьому механізму кожен логічний тунель має власну чергу та обмеження пропускної здатності, що ізолює потоки даних один від одного.

## 2. Локальне прокидання портів (`-L`): доступ до внутрішніх сервісів

Локальне прокидання портів (Local Port Forwarding) застосовується в ситуаціях, коли клієнту необхідно отримати доступ до мережевого сервісу, що розташований або безпосередньо на віддаленому сервері, або у приватній підмережі, доступній лише через цей сервер (хост-бастіон).

Синтаксис аргументу командного рядка:

```bash
ssh -L [локальна_адреса:]локальний_порт:віддалений_хост:віддалений_порт user@ssh_server
```

Якщо `локальна_адреса` не вказана, клієнт OpenSSH за замовчуванням прив'язує сокет виключно до адреси зворотного зв'язку `127.0.0.1` (loopback), що запобігає несанкціонованому доступу інших машин локальної мережі до прокинутого порту.

![Схеми трьох типів прокидання портів: локальне, віддалене та динамічне](/root/sys/sys-unix/ssh-port-forwarding/img/ssh-forwarding-types.svg)
*Три моделі прокидання портів в SSH: локальне (-L), віддалене реверсивне (-R) та динамічне SOCKS5 (-D).*

### Покрокова послідовність обробки каналу `direct-tcpip`

Розглянемо практичний сценарій: системний адміністратор хоче підключитися до бази даних PostgreSQL, запущеної на внутрішньому сервері `10.0.1.5:5432`, доступ до якого захищений SSH-шлюзом `bastion.company.com`:

```bash
ssh -L 5432:10.0.1.5:5432 user@bastion.company.com
```

Процес перенаправлення трафіку розгортається наступним чином:

1. **Створення локального слухача:** Процес клієнта `ssh` на робочій станції виконує системні виклики `socket()`, `bind()` (прив'язуючись до `127.0.0.1:5432`) та `listen()`.
2. **Підключення клієнтської програми:** Адміністратор запускає утиліту `psql -h 127.0.0.1 -p 5432 -U dbuser mydb`. Локальний клієнт PostgreSQL з'єднується з локальним портом 5432.
3. **Обробка запиту клієнтом SSH:** Процес `ssh` приймає з'єднання через системний виклик `accept()`, призначає йому внутрішній ідентифікатор каналу (наприклад, `channel 0`) та формує протокольний пакет `SSH_MSG_CHANNEL_OPEN` з типом `"direct-tcpip"`. У тілі пакета вказуються параметри:
   - `host to connect`: `"10.0.1.5"`
   - `port to connect`: `5432`
   - `originator IP address`: `"127.0.0.1"`
   - `originator port`: `48291` (порт локального клієнта psql)
4. **Трансляція через зашифрований тунель:** Пакет шифрується симетричним шифром сесії і надсилається через встановлене TCP-з'єднання на порт 22 сервера `bastion.company.com`.
5. **Встановлення з'єднання на стороні сервера:** Демон `sshd` отримує пакет, розшифровує його, перевіряє власні правила безпеки і виконує системний виклик `connect()` до сокета `10.0.1.5:5432`. Зверніть увагу: це з'єднання виконується **від імені сервера бастіону**, тобто джерелом TCP-пакетів для бази даних буде внутрішня IP-адреса бастіону.
6. **Двосторонній потік:** Після успішного `connect()` демон `sshd` надсилає клієнту `SSH_MSG_CHANNEL_OPEN_CONFIRMATION`. Починається повнодуплексна трансляція даних між сокетом `psql` на клієнті та сокетом PostgreSQL на сервері через пакети `SSH_MSG_CHANNEL_DATA`.

> 🔧 **Навіщо це.**
> Локальне прокидання портів усуває необхідність тримати відкритими порти СУБД, черг повідомлень (RabbitMQ, Kafka) або адміністративних вебінтерфейсів (Prometheus, Grafana, Kibana) на зовнішніх маршрутизаторах. Усі ці сервіси можуть слухати виключно `127.0.0.1` або внутрішню приватну мережу, а адміністратори підключаються до них безпосередньо через зашифрований SSH-сеанс.

### Сторона розпізнавання доменних імен (DNS Resolution Context)

Критично важливою особливістю синтаксису `-L` є місце розв'язання імені хоста призначення:

```bash
ssh -L 8080:intranet.internal.net:80 user@bastion.company.com
```

Ім'я хоста `intranet.internal.net` передається в пакеті `SSH_MSG_CHANNEL_OPEN` у вигляді рядка символів і **розпізнається через системний DNS-резолвер віддаленого сервера `sshd`**, а не локальної машини клієнта. Це дозволяє вказувати внутрішні корпоративні доменні імена або приватні адреси інфраструктури хмарного провайдера, які взагалі не існують у публічному глобальному DNS.

Якщо як віддалений хост вказано `localhost`:

```bash
ssh -L 8080:localhost:80 user@remote-server.com
```

Ім'я `localhost` буде інтерпретовано віддаленим сервером як його власний інтерфейс зворотного зв'язку `127.0.0.1`. Це дозволяє отримати прямий доступ до веб-сервера (наприклад, Nginx або Apache), який налаштований слухати лише `127.0.0.1` і не транслюється назовні.

### Прокидання локальних та віддалених сокетів UNIX (UNIX Domain Sockets)

Починаючи з версії OpenSSH 6.7, механізм прокидання портів було розширено підтримкою сокетів простору імен файлової системи UNIX (AF_UNIX). Це дозволяє прокидати не лише мережеві TCP-порти, а й файлові сокети між машинами:

```bash
# Прокидання віддаленого сокета Docker API на локальний сокет
ssh -L /home/user/docker.sock:/var/run/docker.sock user@remote-server

# Використання локального клієнта docker над віддаленим демоном
docker -H unix:///home/user/docker.sock ps
```

Крім того, підтримується змішане прокидання: перенаправлення локального сокета UNIX у віддалений TCP-порт (`local_socket:remote_host:port`) або навпаки (`local_port:remote_socket`). При роботі з UNIX-сокетами корисними є директиви конфігурації `StreamLocalBindUnlink=yes` (автоматичне видалення застарілого файлу сокета перед запуском) та `StreamLocalBindMask` (налаштування прав доступу до створеного сокета).

## 3. Віддалене (реверсивне) прокидання портів (`-R`): експорт локальних сервісів назовні

Віддалене, або реверсивне прокидання портів (Remote Port Forwarding) виконує дзеркальну задачу: воно відкриває мережевий слухаючий порт на стороні віддаленого SSH-сервера і перенаправляє всі вхідні підключення, що надходять на цей порт, назад через захищений тунель до локальної машини клієнта або до іншого хоста в локальній мережі клієнта.

Синтаксис аргументу командного рядка:

```bash
ssh -R [віддалена_адреса:]віддалений_порт:локальний_хост:локальний_порт user@ssh_server
```

Цей механізм є основою роботи таких сервісів публікації тунелів, як `ngrok`, `localtunnel` або `Cloudflare Tunnels`, але реалізується засобами стандартного стека OpenSSH без стороннього програмного забезпечення.

### Механізм реєстрації `forwarded-tcpip`

Розглянемо типовий сценарій розробки: розробник запустив локальний веб-сервер на `127.0.0.1:3000` (наприклад, додаток на Node.js або Django) і хоче протестувати прийом вхідних вебхуків (webhooks) від зовнішнього платіжного сервісу (наприклад, Stripe або GitHub). Робоча машина розробника перебуває за домашнім Wi-Fi роутером із динамічним NAT, тому пряме підключення з інтернету неможливе.

Розробник орендує публічний віртуальний сервер VPS із публічною статичною IP-адресою `203.0.113.10` і виконує команду:

```bash
ssh -R 8080:localhost:3000 user@203.0.113.10
```

Послідовність роботи реверсивного тунелю:

1. **Глобальний запит реєстрації:** Після успішної автентифікації клієнт OpenSSH надсилає серверу спеціальне повідомлення `SSH_MSG_GLOBAL_REQUEST` (код 80) з типом запиту `"tcpip-forward"`. У запиті передаються бажана адреса прив'язки (`address to bind`) та порт (`port number to bind = 8080`).
2. **Відкриття сокета сервером `sshd`:** Демон `sshd` на сервері викликає `socket()`, `bind()` та `listen()`, відкриваючи порт 8080. Сервер підтверджує реєстрацію повідомленням `SSH_MSG_REQUEST_SUCCESS` (код 81).
3. **Вхідне підключення з інтернету:** Зовнішній сервіс (наприклад, сервер Stripe) надсилає HTTP-запит на `http://203.0.113.10:8080`. Ядро сервера VPS приймає TCP-з'єднання через `accept()`.
4. **Ініціалізація зворотного каналу:** Демон `sshd` надсилає локальному клієнту OpenSSH повідомлення `SSH_MSG_CHANNEL_OPEN` з типом `"forwarded-tcpip"`.
5. **Трансляція на локальний сервіс:** Локальний процес `ssh` на ноутбуці розробника отримує повідомлення, виконує `connect()` до `localhost:3000` і підтверджує відкриття каналу. Трафік вебхука передається у локальний додаток, а відповідь повертається зовнішньому клієнту через SSH-тунель.

### Конфігурація сервера: директива `GatewayPorts`

За замовчуванням безпекова конфігурація демона OpenSSH забороняє віддаленим портам приймати підключення з публічних мережевих інтерфейсів. У файлі `/etc/ssh/sshd_config` директива `GatewayPorts` за замовчуванням встановлена у значення `no`:

```
# /etc/ssh/sshd_config
GatewayPorts no
```

При такому налаштуванні, навіть якщо клієнт передає команду `ssh -R 0.0.0.0:8080:localhost:3000`, демон `sshd` примусово виконає виклик `bind()` виключно на інтерфейсі зворотного зв'язку `127.0.0.1` на сервері. Це означає, що порт 8080 буде доступний лише процесам, запущеним локально на самому сервері VPS.

Щоб відкрити порт для зовнішнього світу, адміністратор сервера повинен змінити директиву `GatewayPorts`:

- `GatewayPorts yes`: Змушує `sshd` прив'язувати всі віддалені тунелі до універсальної адреси `0.0.0.0` (wildcard), роблячи їх автоматично доступними з усього інтернету.
- `GatewayPorts clientspecified`: Дозволяє клієнту самостійно контролювати адресу прив'язки. Якщо клієнт явно вказує адресу `ssh -R :8080:localhost:3000` або `ssh -R 0.0.0.0:8080:...`, сокет слухатиме всі інтерфейси. Якщо адреса опущена (`ssh -R 8080:...`), сокет слухатиме лише `127.0.0.1`.

> ⚠️ **Попередження безпеки:**
> Встановлення `GatewayPorts yes` на загальнодоступному сервері перетворює його на потенційний шлюз для публікації неперевірених внутрішніх сервісів. Будь-який користувач, що має право SSH-доступу до сервера, зможе відкрити на ньому публічний порт і перенаправити зовнішній трафік у свою локальну мережу. Для обмеження прав рекомендується використовувати директиви `AllowTcpForwarding` та секції `Match User / Match Group` у `sshd_config`.

### Динамічний вибір віддаленого порту

Якщо на віддаленому сервері одночасно працюють кілька розробників, фіксований порт (наприклад, 8080) може бути зайнятий іншим процесом. Щоб уникнути колізій, OpenSSH підтримує динамічний вибір порту:

```bash
ssh -R 0:localhost:3000 user@203.0.113.10
```

Вказівка порту `0` змушує ядро віддаленої системи призначити перший вільний ефемерний порт (наприклад, 42189). Номер призначеного порту повертається сервером у відповіді на глобальний запит і виводиться клієнтом у стандартний потік виводу:

```
Allocated port 42189 for remote forward to localhost:3000
```

## 4. Динамічне прокидання портів (`-D`): створення локального SOCKS5-проксі

Фіксовані правила `-L` та `-R` вимагають заздалегідь знати кінцеву IP-адресу або доменне ім'я цільового сервера та номер його порту. Якщо користувачу потрібно маршрутизувати весь трафік браузера або десятків різноманітних мережевих утиліт через віддалений вузол, створення окремого правила `-L` для кожного веб-сайту стає неможливим.

Для розв'язання цієї задачі застосовується динамічне прокидання портів (Dynamic Port Forwarding):

```bash
ssh -D [локальна_адреса:]локальний_порт user@remote_server
```

У цьому режимі клієнт OpenSSH самостійно запускає на локальній машині повнофункціональний проксі-сервер за стандартом SOCKS (підтримуються протоколи SOCKS4 та SOCKS5 згідно з RFC 1928).

```bash
# Запуск SOCKS5-проксі на локальному порті 1080
ssh -D 1080 -N -f user@remote-proxy.com
```

### Протокол узгодження SOCKS5 (RFC 1928)

Після запуску клієнтського процесу SSH будь-який прикладний додаток (веб-браузер Firefox/Chrome, поштовий клієнт або консольна утиліта `curl`) налаштовується на роботу через проксі-сервер `socks5://127.0.0.1:1080`.

Коли браузер намагається відкрити веб-сторінку `https://example.com`, відбувається наступний обмін даними:

1. **Рукостискання автентифікації:** Браузер з'єднується з `127.0.0.1:1080` і надсилає список підтримуваних методів автентифікації. Локальний SSH-клієнт відповідає байтом `0x00` (NO AUTHENTICATION REQUIRED).
2. **Запит на встановлення з'єднання (CONNECT):** Браузер формує бінарний запит SOCKS5:
   - `VER` (1 байт): `0x05` (версія протоколу)
   - `CMD` (1 байт): `0x01` (команда CONNECT)
   - `RSV` (1 байт): `0x00` (зарезервовано)
   - `ATYP` (1 байт): тип цільової адреси (`0x01` — IPv4, `0x03` — доменне ім'я, `0x04` — IPv6)
   - `DST.ADDR`: цільова адреса (наприклад, рядок `"example.com"`)
   - `DST.PORT` (2 байти): цільовий TCP-порт (`443`)
3. **Інкапсуляція в канал `direct-tcpip`:** Локальний SSH-клієнт зчитує поля `DST.ADDR` та `DST.PORT`, автоматично формує повідомлення `SSH_MSG_CHANNEL_OPEN` типу `direct-tcpip` і передає його на віддалений SSH-сервер.
4. **З'єднання з боку віддаленого сервера:** Сервер `sshd` виконує виклик `connect()` до `example.com:443`.
5. **Відповідь SOCKS5:** Клієнт SSH повертає браузеру пакет підтвердження SOCKS5 (`REP = 0x00` — Success). Починається прозора трансляція HTTPS-трафіку.

### Захист від витоків DNS (DNS Leak Prevention)

Однією з найнебезпечніших помилок при конфігурації динамічного тунелю є витік DNS-запитів (DNS Leak). 

Якщо клієнтський застосунок використовує локальний механізм системного розпізнавання імен (наприклад, викликає стандартну бібліотечну функцію `gethostbyname()` або `getaddrinfo()` у власній операційній системі), операційна система надсилає незашифрований UDP-запит до DNS-сервера локального провайдера, отримує IP-адресу цільового сервера і лише після цього передає запит у SOCKS5-проксі із типом адреси `ATYP = 0x01` (IPv4). У цьому разі локальний інтернет-провайдер бачить усі доменні імена веб-сайтів, які відкриває користувач, навіть якщо сам трафік потім передається зашифрованим через SSH.

Для повного захисту приватності необхідно змусити застосунок передавати **доменне ім'я** безпосередньо у SOCKS-протокол (`ATYP = 0x03` — Domain Name), щоб розпізнавання IP-адреси здійснювалося **на віддаленому SSH-сервері**:

- Утиліта `curl`: використання опції `--socks5-hostname` замість `--socks5`:
  ```bash
  curl --socks5-hostname 127.0.0.1:1080 https://api.ipify.org
  ```
- Браузер Mozilla Firefox: у розділі `about:config` параметр `network.proxy.socks_remote_dns` встановлюється у значення `true`.
- Системні утиліти: використання спеціалізованих обгорток на базі динамічного перехоплення бібліотечних викликів (наприклад, `proxychains-ng` з увімкненою опцією `proxy_dns` у конфігураційному файлі).

Повний перелік параметрів клієнта та директив безпеки сервера зібрано у довідковій вставці [📋 Довідник опцій OpenSSH для тунелювання портів і сокетів](root:sys-unix/ssh-port-forwarding/api-ssh-forwarding-options.md).

## 5. Стійкість, автоматизація та фоновий запуск тунелів

Для використання SSH-тунелів у складі виробничої інфраструктури або фонових сервісів операційної системи з'єднання має бути повністю автономним: запускатися у фоновому режимі без відкриття інтерактивного термінала, автоматично виявляти обриви зв'язку та самостійно перепідключатися.

### Прапорці фонового виконання та демонізації

Для переведення клієнта SSH у фоновий режим застосовується комбінація прапорців:

```bash
ssh -N -f -q -T -L 5432:db.internal:5432 -o ExitOnForwardFailure=yes user@gateway.domain
```

Розглянемо призначення кожного прапорця:

- `-N` (Do Not Execute Remote Command): Повідомляє серверу, що клієнт не планує відкривати сеанс командної оболонки або виконувати команди. Без цього прапорця сервер виділить процес оболонки (`/bin/bash`), який даремно споживатиме оперативну пам'ять.
- `-f` (Fork into Background): Переводить процес SSH у фоновий режим безпосередньо перед початком передачі даних. Клієнт виконує автентифікацію, узгоджує канали і лише після отримання підтвердження від сервера робить системний виклик `fork()`, повертаючи керування вихідному командному рядку.
- `-T` (Disable PTY): Вимикає виділення псевдотермінала на віддаленому сервері.
- `-q` (Quiet Mode): Пригнічує попередження та службові повідомлення.
- `-o ExitOnForwardFailure=yes`: За замовчуванням, якщо локальний порт 5432 вже зайнятий іншим процесом, клієнт `ssh` виводить коротке попередження у `stderr`, але **продовжує утримувати сесію відкритою** без прокидання порту. Опція `ExitOnForwardFailure=yes` змушує клієнт негайно завершити роботу з кодом помилки `255`, що критично для систем автоматизації та супервізорів.

![Життєвий цикл та моніторинг стійкості фонового SSH-тунелю](/root/sys/sys-unix/ssh-port-forwarding/img/ssh-tunnel-supervisor-lifecycle.svg)
*Життєвий цикл фонового SSH-тунелю: запуск, перевірка живлення за протоколом SSH, виявлення обривів і відновлення через systemd або супервізор.*

### Зондування активності з'єднання (Keepalive на рівні SSH проти TCP Keepalive)

Головною причиною «зависання» фонових тунелів є наявність проміжних брандмауерів та маршрутизаторів NAT. Якщо через тунель тривалий час не передаються дані, таблиця станів NAT-маршрутизатора видаляє запис про з'єднання через таймаут неактивності (State Timeout, зазвичай від 30 секунд до кількох хвилин). Після цього будь-які пакети, надіслані клієнтом або сервером, мовчазно відкидаються. Локальне ядро вважає сокет справним і залишається у стані `TCP_ESTABLISHED` годинами.

Стандартний механізм TCP Keepalive ядра ОС не завжди допомагає, оскільки його системний інтервал за замовчуванням у Linux становить 7200 секунд (2 години).

Для вирішення цієї проблеми OpenSSH реалізує **прикладний механізм зондування живості (Heartbeat)** безпосередньо на рівні протоколу SSH:

```
# Конфігурація клієнта (~/.ssh/config)
ServerAliveInterval 15
ServerAliveCountMax 3
```

- `ServerAliveInterval 15`: Якщо протягом 15 секунд через тунель не передавалося жодних корисних даних, клієнт SSH самостійно генерує та надсилає через зашифрований транспортний рівень службовий пакет `SSH_MSG_GLOBAL_REQUEST` із запитом `keepalive@openssh.com`.
- `ServerAliveCountMax 3`: Сервер зобов'язаний відповісти на цей запит. Якщо клієнт надсилає 3 запити поспіль (сумарно 45 секунд) і не отримує жодної відповіді, клієнт вважає мережевий зв'язок втраченим, закриває всі локальні сокети і завершує процес із кодом помилки `255`.

Аналогічні параметри існують і на стороні сервера (`ClientAliveInterval` та `ClientAliveCountMax`), що дозволяє серверу своєчасно очищати ресурси та закривати зомбі-сесії у разі раптового знеструмлення клієнта.

### Автоматизація тунелів через systemd

Найбільш надійним методом утримання постійного SSH-тунелю у виробничому середовищі Linux є оформлення його у вигляді системної служби `systemd`.

Створимо файл конфігурації юніта `/etc/systemd/system/ssh-tunnel-db.service`:

```ini
[Unit]
Description=SSH Tunnel to Production Database
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=tunneluser
Group=tunneluser

# Запуск ssh у передньому плані (БЕЗ прапорця -f!)
ExecStart=/usr/bin/ssh -N -T \
    -o ExitOnForwardFailure=yes \
    -o ServerAliveInterval=15 \
    -o ServerAliveCountMax=3 \
    -o ConnectTimeout=10 \
    -o BatchMode=yes \
    -i /home/tunneluser/.ssh/id_ed25519 \
    -L 127.0.0.1:5432:10.0.1.5:5432 \
    tunneluser@bastion.company.com

# Автоматичний перезапуск при аварійному завершенні
Restart=always
RestartSec=5s

# Обмеження прав процесу
ProtectSystem=strict
ProtectHome=read-only
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
```

Зверніть увагу на параметр `Type=simple` та відсутність прапорця `-f`. Менеджер `systemd` самостійно відстежує стан процесу через PID головного потоку. Якщо з'єднання обривається, процес `ssh` завершується через таймаут `ServerAliveInterval`, після чого `systemd` чекає 5 секунд (`RestartSec=5s`) і автоматично повторює запуск.

Для написання власних легковагих утиліт керування тунелями та моніторингу сокетів зверніться до проекту [⚙️ Проектування надійного супервізора SSH-тунелів із моніторингом сокетів](root:sys-unix/ssh-port-forwarding/proj-ssh-tunnel-supervisor.md).

## 6. Практична діагностика та системний аналіз тунелів у Linux

Для налагодження, пошуку вузьких місць та перевірки безпеки прокинутих портів системний інженер використовує набір діагностичних інструментів ядра Linux.

### Перевірка активних слухачів через `ss`

Утиліта `ss` (Socket Statistics) дозволяє перевірити, які порти відкрито процесами `ssh` або `sshd`:

```bash
# Перевірка локальних слухачів TCP із зазначенням PID та назви процесу
ss -tlpn '( sport = :5432 or sport = :1080 )'
```

Приклад типового виводу:

```
State    Recv-Q   Send-Q   Local Address:Port   Peer Address:Port   Process
LISTEN   0        128      127.0.0.1:5432       0.0.0.0:*           users:(("ssh",pid=14820,fd=4))
LISTEN   0        128      127.0.0.1:1080       0.0.0.0:*           users:(("ssh",pid=14820,fd=5))
```

З виводу чітко видно, що процес `ssh` (PID 14820) відкрив файлові дескриптори 4 та 5, які слухають з'єднання на портах 5432 та 1080 на адресі `127.0.0.1`.

### Дослідження стану дескрипторів у `/proc`

В операційній системі Linux кожен відкритий сокет відображається у віртуальній файловій системі `/proc/<PID>/fd`:

```bash
ls -l /proc/14820/fd/
```

Вивід містить посилання на сокети:

```
lrwx------ 1 user user 64 Aug 25 12:00 3 -> socket:[948123]   # TCP-з'єднання з SSH-сервером (порт 22)
lrwx------ 1 user user 64 Aug 25 12:00 4 -> socket:[948124]   # Слухач локального порту 5432
lrwx------ 1 user user 64 Aug 25 12:00 5 -> socket:[948125]   # Слухач SOCKS-порту 1080
```

Числові ідентифікатори інодів сокетів (`inode`) дозволяють знайти точний стан відповідного TCP-з'єднання у таблиці ядра `/proc/net/tcp` або через `ss -i`.

### Налагодження протоколу через прапорці деталізації (`-v`, `-vv`, `-vvv`)

Якщо з'єднання через тунель не встановлюється або обривається, запуск клієнта з прапорцем підвищеної деталізації логування `-v` (або `-vvv`) розкриває точну послідовність обміну пакетами Connection Layer:

```bash
ssh -vvv -L 5432:10.0.1.5:5432 user@bastion.company.com
```

У лозі з'являються ключові маркери життєвого циклу каналу:

```
debug1: Local connections to 127.0.0.1:5432 forwarded to 10.0.1.5:5432
debug1: Connection to port 5432 forwarding to 10.0.1.5 port 5432 requested, resolving.
debug2: fd 4 setting O_NONBLOCK
debug1: channel 0: new [direct-tcpip]
debug3: send packet: type 90 id 0 len 44
debug3: receive packet: type 91 id 0 len 28
debug1: channel 0: open confirm rwindow 2097152 rmax 32768
debug2: channel 0: rcvd adjust 2097152
debug1: channel 0: free: direct-tcpip, nchannels 1
```

Якщо віддалений сервер забороняє форвардинг, у лозі буде зафіксовано відмову:

```
debug1: channel 0: open failed: administratively prohibited: open failed
```

Це свідчить про те, що на сервері активна директива `AllowTcpForwarding no` або цільовий хост заблокований директивою `PermitOpen`.

### Динамічне додавання тунелів до існуючої сесії (SSH Escape Sequence `~C`)

Якщо користувач уже працює в активній інтерактивній термінальній сесії SSH і виникла потреба терміново прокинути додатковий порт без розриву сеансу та без відкриття нового з'єднання, можна скористатися керуючою послідовністю символів (Escape Sequence):

1. У поточному терміналі на початку нового рядка натисніть клавішу `~` (тильда), а потім велику літеру `C` (Shift+C).
2. На екрані з'явиться командний рядок вбудованого інтерпретатора OpenSSH:
   ```
   ssh> 
   ```
3. Введіть команду додавання або видалення потрібного правила:
   ```
   ssh> -L 8080:localhost:80
   Forwarding port.
   ```
   Або скасування раніше створеного правила:
   ```
   ssh> -KL 8080
   Canceled forwarding.
   ```
4. Натисніть Enter, щоб повернутися до звичайної командної оболонки. Новий порт стане доступним негайно всередині вже існуючого зашифрованого каналу.

### Керування через сокет мультиплексування (`ControlMaster`)

Якщо для підключення до сервера налаштовано майстер-з'єднання OpenSSH (`ControlMaster auto`, `ControlPath ~/.ssh/cm-%r@%h:%p`), нові тунелі можна відкривати і закривати за допомогою прапорця `-O`:

```bash
# Додати локальне прокидання до працюючого майстер-процесу
ssh -O forward -L 8080:localhost:80 user@bastion.company.com

# Скасувати прокидання
ssh -O cancel -L 8080:localhost:80 user@bastion.company.com

# Перевірити стан майстер-з'єднання
ssh -O check user@bastion.company.com
```
