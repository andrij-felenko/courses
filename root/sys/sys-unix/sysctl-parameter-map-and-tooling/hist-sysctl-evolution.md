# 📜 Еволюція sysctl: від двійкового виклику до рядкових шляхів /proc/sys

Ранні версії операційних систем Unix вимагали перекомпіляції ядра або перезавантаження всієї машини для зміни найпростіших системних параметрів, таких як максимальна кількість відкритих файлів, розмір мережевого буфера чи дозвіл маршрутизації мережевих пакетів. Коли в першій половині 1990-х років мережеві сервери почали працювати цілодобово під постійно зростаючим навантаженням в мережі Інтернет, така жорсткість стала неприпустимою вадою. Операційній системі знадобився механізм безпечного читання та модифікації внутрішніх змінних ядра «на ходу» без зупинки працюючих процесів.

У розробників операційних систем Unix було два принципово різних шляхи реалізації динамічного тюнінгу: створити спеціалізований двійковий системний виклик із числовими ідентифікаторами параметрів або використати класичну концепцію Unix «усе є файлом» і винести всі налаштування у віртуальну файлову систему. Історія розвитку Linux показує, як системна архітектура випробувала обидва підходи, відмовившись зрештою від двійкового виклику на користь текстового рядкового інтерфейсу `/proc/sys`.

## Витоки в BSD: числові масиви MIB та системний виклик sysctl(2)

Перше цілісне та систематичне рішення проблеми динамічного тюнінгу з'явилося у 1993 році в операційній системі 4.4BSD. Інженери університету Берклі створили новий системний виклик `sysctl(2)`, який приймав як ключ не ім'я файлу, а масив цілих чисел — ієрархічний шлях у дереві Management Information Base (MIB). Концепцію MIB запозичили з мережевих протоколів керування SNMP (*Simple Network Management Protocol*), що набували популярності в маршрутизаторах.

У цій системі кожен налаштовуваний параметр мав сувору числову адресу. Наприклад, параметр дозволу forwarding IPv4-пакетів описувався масивом з чотирьох цілих чисел: `{CTL_NET, PF_INET, IPPROTO_IP, IPCTL_FORWARDING}`. Кожна константа виражалася цілим числом і визначалася у спільній системній ієрархії заголовкових файлів `<sys/sysctl.h>`.

Прототип системного виклику у BSD мав такий вигляд:

```c
int sysctl(const int *name, u_int namelen, void *oldp, size_t *oldlenp,
           const void *newp, size_t newlen);
```

Аргумент `name` передавав масив цілих чисел, `namelen` — кількість елементів у масиві, `oldp` та `oldlenp` слугували для зчитування поточного значення змінної, а `newp` та `newlen` — для запису нового значення у пам'ять ядра.

```c
int name[] = { CTL_NET, PF_INET, IPPROTO_IP, IPCTL_FORWARDING };
int old_val;
size_t len = sizeof(old_val);
int new_val = 1;

if (sysctl(name, 4, &old_val, &len, &new_val, sizeof(new_val)) < 0) {
    perror("sysctl");
}
```

З точки зору швидкодії двійковий системний виклик був ідеальним. Передавання масиву з 4–5 цілих чисел у ядро відбувалося миттєво: ядрові не потрібно було розбирати текстові рядки, парсити шляхи у файловій системі, шукати дентрі чи конвертувати ASCII-символи у цілі числа. Захист пам'яті гарантувався тим, що ядро перевіряло межі масивів і копіювало дані через привілейовані функції `copy_from_user` та `copy_to_user`.

Однак за високу швидкість виконання довелося сплатити високу ціну — негнучкість розробки, складність розширення та важке обслуговування коду.

## Криза двійкового реєстру MIB

Linux перейняв цю ідею від BSD. Файл `kernel/sysctl.c` почав 24 березня 1995 року шотландський розробник ядра Стівен Твіді (*Stephen Tweedie*, згодом Red Hat) — його ім'я досі стоїть у шапці файлу; сам системний виклик `sysctl(2)` з'явився у версії Linux 1.3.57 (січень 1996 року). Система швидко зіткнулася з тими ж проблемами, які невдовзі ускладнили життя й розробникам BSD:

1. **Залежність від централізованого заголовкового файлу.** Для додавання нового параметра розробник будь-якої підсистеми ядра мусив внести нову числову константу у спільний файл `include/linux/sysctl.h`. Якщо два розробники у різних гілках розробки обирали однаковий цілочисельний ідентифікатор для різних параметрів, виникала колізія чисел MIB, яка ламала збірку системи.
2. **Проблема бінарної сумісності (ABI).** Якщо константу з часом видаляли або змінювали її порядок у масиві, користувацькі програми, зібрані зі старими заголовками, починали читати або перезаписувати зовсім інші змінні ядра. Це могло призвести до краху системи, псування пам'яті або пролому в безпеці.
3. **Неможливість динамічного виявлення (discovery).** Числовий масив не містив метаданих про типи даних, дозволені межі чи описи параметрів. Програма у просторі користувача не мала змоги «ітерувати» по дереву `sysctl` чи автоматично побудувати список доступних налаштувань, якщо не знала наперед усіх числових констант.
4. **Складність розширення для модулів ядра.** Модулі драйверів пристроїв, які завантажувалися динамічно під час роботи системи, не могли легко гарантувати собі унікальні числа MIB у загальній системній таблиці без ризику перекриття з іншими модулями.

## Народження та перемога рядкового інтерфейсу /proc/sys

Паралельно з двійковим викликом у Linux розвивалася віртуальна файлова система `procfs`. У тій же версії Linux 1.3.57 поряд із `sysctl(2)` з'явилося піддерево `/proc/sys`. Ідея полягала у тому, що кожен вузол MIB транслювався у каталог або файл у файловій системі, де числовим константам відповідали звичайні текстові назви.

Замість числового масиву `{CTL_NET, NET_IPV4, NET_IPV4_FORWARD}` параметром став простий текстовий шлях `/proc/sys/net/ipv4/ip_forward`.

Ця зміна філософії виявилася революційною для екосистеми Linux:

- **Текстова самодокументованість:** Будь-який адміністратор чи сценарій міг переглянути вміст каталогу за допомогою звичайних утиліт `ls`, `cat`, `grep` або `find`. Ієрархія стала прозорою без відкриття заголовкових файлів ядра.
- **Відсутність єдиного реєстру чисел:** Розробники підсистем та динамічних модулів ядра отримали змогу реєструвати нові параметри, просто вказуючи рядкові імена каталогів та файлів у структурі `ctl_table`. Конфлікти чисел зникли назавжди.
- **Універсальність інструментів shell:** Пропала потреба у спеціальних бінарних програмах для читання та запису параметрів — звичайний виклик `echo "1" > /proc/sys/net/ipv4/ip_forward` виконував тюнінг системи прямо зі стандартного bash-сценарію.

## Занепад та повне видалення sysctl(2) в Linux

Протягом тривалого часу у Linux існували обидва інтерфейси: системний виклик `sysctl(2)` всередині ядра звертався до тих самих внутрішніх таблиць `ctl_table`, що й файлова система `/proc/sys`. Проте з часом підтримка подвійної трансляції двійкових MIB-чисел у рядкові шляхи стала важким тягарем для розробників ядра.

У версії Linux 2.6.24 (2008 рік) підсистему sysctl почали активно рефакторити. Двійкові коди `sysctl` були оголошені застарілими (*deprecated*). Ядро виводило застереження у системний журнал `dmesg` кожного разу, коли якась застаріла програма намагалася викликати `sysctl(2)` через числові ідентифікатори:

```text
warning: process `old_app' used the deprecated sysctl system call with 1.23.
```

Числа наприкінці — це той самий MIB-масив, який програма передала ядру, надрукований через крапку.

Більшість дистрибутивів Linux заздалегідь вимикали конфігураційний параметр ядра `CONFIG_SYSCTL_SYSCALL`. Повна відмова відбувалася у два етапи:
1. Спочатку у збірках ядра залишили заглушку системного виклику `sysctl(2)`, яка завжди повертала помилку `-ENOSYS` або `-EOPNOTSUPP`.
2. Фінальна крапка була поставлена у січні 2020 року у випуску Linux 5.5: розробник Ерік Бідерман (*Eric W. Biederman*) остаточно видалив системний виклик `sysctl(2)` із коду ядра Linux, вирізавши сотні рядків застарілого коду підтримки MIB.

Бібліотека glibc також повністю вилучила функцію-обгортку `sysctl()` у випуску 2.32.

> 🔧 **Порівняння архітектур з FreeBSD.**
> У той час як Linux повністю відмовився від двійкового виклику і перейшов на рядкові файлові шляхи VFS у `/proc/sys`, система FreeBSD пішла іншим шляхом. У FreeBSD системний виклик `sysctl(2)` зберегли, а рядкові імена додали шаром вище: бібліотечні функції `sysctlbyname(3)` та `sysctlnametomib(3)` перекладають ім'я на кшталт `net.inet.ip.forwarding` у числовий MIB через службовий вузол дерева й лише тоді викликають `sysctl(2)`. Через це звертання на ім'я коштує помітно дорожче за звертання по вже відомому MIB, і програми, що читають параметр у циклі, кешують результат `sysctlnametomib()`. Це демонструє відмінність системних філософій: Linux зробив ставку на уніфікацію керування через VFS, а FreeBSD — на збереження спеціалізованого системного виклику без накладних витрат файлової системи.

Сьогодні в Linux утиліта `sysctl(8)` є звичайною текстовою обгорткою над файловою системою `/proc/sys`. Вона відкриває відповідний файл, перетворює текстовий рядок на число та записує його через стандартні системні виклики `open()`, `read()` та `write()`.
