# ⚙️ Реалізація атомарного блокування баз облікових записів (/etc/ptmp)

Файли `/etc/passwd`, `/etc/shadow`, `/etc/group` та `/etc/gshadow` є основою ідентифікації та автентифікації в операційних системах сімейства Unix/Linux. На відміну від реляційних СКБД, системні бази облікових записів не мають вбудованого рушія транзакцій із підтримкою рівнів ізоляції (ACID) чи журналу випереджального запису (WAL). Це звичайні плоскі текстові файли, розташовані в кореневій файловій системі. 

Складність полягає в асиметрії навантаження: у будь-який момент часу сотні й тисячі паралельних процесів (демони `sshd`, вебсервери, cron-завдання, системні виклики `getpwnam()`, `getpwuid()` та утиліти на зразок `ls -l`) відкривають ці файли на читання. Якщо адміністративна утиліта спробує модифікувати такий файл прямим відкриттям на запис (з прапорцями `O_WRONLY | O_TRUNC` або через `fopen(..., "w")`), це створить критичний стан гонки (race condition). У проміжку часу між зрізанням довжини файлу до нуля та завершенням запису нових рядків будь-який сторонній процес прочитає порожній або обірваний файл. Для системи це виглядатиме так, ніби системних користувачів чи групи раптово перестало існувати, що призводить до відмов в автентифікації, збоїв під час скидання прав процесу (privilege drop) та аварійних зупинок системних служб.

Щоб унеможливити конфлікти між утилітами модифікації (`useradd`, `usermod`, `userdel`, `vipw`, `chage`) і водночас гарантувати узгодженість даних для всіх паралельних читачів без деградації продуктивності, у класичному пакеті `shadow-utils` застосовується протокол блокувального файлу `.ptmp` із наступною атомарною підміною через системний виклик `rename()`.

## Архітектурний контекст: чому стандартні блокування файлів безсилі

Перше інженерне рішення, яке спадає на думку для захисту спільного файлу від одночасного запису, — це використання стандартних системних блокувань: консультативних замків `flock(2)` або `fcntl(2)` із командою `F_SETLK`. Проте в архітектурі системних баз облікових записів Unix ці механізми виявляються непридатними з двох фундаментальних причин.

### 1. Проблема продуктивності читачів (Lock Contention)
Консультативні блокування (Advisory Locking) вимагають добровільної згоди від кожного процесу, що звертається до файлу. Для коректної роботи читачі повинні були б відкривати `/etc/passwd` і ставити розділюваний замок `flock(fd, LOCK_SH)`, а процеси модифікації — ексклюзивний замок `flock(fd, LOCK_EX)`.

Проте виклики `getpwnam()` та `getpwuid()` виконуються в операційній системі мільйони разів: при кожному запуску команди в терміналі, маршрутизації мережевих з'єднань, аудиті безпеки чи розборі прав на файли. Якщо кожне читання вимагатиме системного виклику взяття та зняття файлового замка на рівні ядра, це перетворить дескриптор `/etc/passwd` на глобальну точку блокування (lock contention bottleneck) у багатопотокових високонавантажених серверах. Більше того, жодна стандартна бібліотека C (glibc, musl) не ставить блокувань під час виклику `getpwnam()`, щоб уникнути системного оверхеду. Тому читачі відкривають файл напряму в режимі `O_RDONLY` і ніколи не перевіряють консультативні замки.

### 2. Неможливість атомарної модифікації за місцем (In-Place Mutation)
Навіть якби процес модифікації захопив ексклюзивний замок `flock(LOCK_EX)` на дескрипторі `/etc/passwd`, він не може перезаписати файл миттєво. Запис нових даних через виклики `write()` відбувається блоками байтів і вимагає часу. Будь-який неблокуючий читач, що викличе `read()` у цей момент, прочитає наполовину сформований рядок, некоректні зміщення записів або порожній вміст після попереднього зрізання файлу (`ftruncate`).

Обов'язкові блокування ядра (Mandatory Locking), які колись активувалися монтуванням із прапорцем `mand` та встановленням біта `setgid` без права виконання групою, також не є вирішенням: через численні стани гонок, ризики локальної відмови в обслуговуванні (Denial of Service) та складність підтримки у ядрі Linux, починаючи з версії 5.15, обов'язкові блокування файлів було повністю видалено з ядра.

Єдиним надійним архітектурним патерном залишається **тіньова копія зі знімком стану (Shadow File Pattern)**: підготовка повного нового вмісту бази в окремому ізольованому файлі з наступною миттєвою підміною покажчика файлової системи за один неподільний крок ядра.

## Механіка файлу-блокування `.ptmp` як апаратного м'ютекса VFS

Щоб запобігти одночасній роботі двох утиліт модифікації (наприклад, паралельних викликів `useradd` та `usermod`), потрібен механізм ексклюзивної взаємної ізоляції. Цю роль виконує файл блокування.

Для кожного з чотирьох основних системних файлів конфігурації існує свій відповідний блокувальний файл:
* `/etc/passwd` ↔ `/etc/ptmp` (Password Temporary);
* `/etc/shadow` ↔ `/etc/sptmp` (Shadow Password Temporary);
* `/etc/group` ↔ `/etc/gtmp` (Group Temporary);
* `/etc/gshadow` ↔ `/etc/sgtmp` (Shadow Group Temporary).

Створення файлу блокування базується на фундаментальній атомарній операції віртуальної файлової системи (VFS) ядра Linux — виклику `open("/etc/ptmp", O_CREAT | O_EXCL | O_RDWR, 0600)`.

Семантика цієї комбінації прапорців гарантує неподільність операції на рівні ядра:
1. Ядро бере м'ютекс каталогу `/etc` (`i_rwsem` для inode каталогу).
2. Виконується пошук елемента каталогу (dentry lookup) за іменем `ptmp`.
3. Якщо запис уже існує, ядро негайно звільняє м'ютекс і повертає помилку `EEXIST` (File exists).
4. Якщо запис відсутній, ядро виділяє новий inode, створює dentry у каталозі `/etc`, відкриває дескриптор файлу і повертає його процесу, не випускаючи м'ютекс каталогу до завершення ініціалізації.

Завдяки цьому прапорець `O_EXCL` повністю ліквідує часове вікно вразливості типу TOCTOU (Time-of-Check to Time-of-Use), яке виникало б у разі окремої перевірки наявності файлу через `access()` чи `stat()` перед його створенням. Створення файлу стає бінарним м'ютексом: рівно один процес отримує валідний файловий дескриптор, а всі паралельні процеси зазнають невдачі з помилкою `EEXIST`.

Режим доступу `0600` (`-rw-------`) гарантує, що новостворений файл читатиметься й записуватиметься виключно суперкористувачем `root`. Для `/etc/sptmp` це критично важливо, оскільки запобігає витоку проміжних гешів паролів іншим локальним процесам під час формування нового файлу.

## Виявлення та безпечне розв'язання застарілих блокувань (Stale Locks)

У розподілених та виробничих системах завжди існує ризик аварійного завершення процесу-власника блокування:
* раптове вимкнення живлення сервера або паніка ядра (Kernel Panic);
* примусове знищення утиліти адміністратором або системою моніторингу через неперехоплюваний сигнал `SIGKILL` (`kill -9`);
* аварійна зупинка процесу через системний OOM Killer при вичерпанні оперативної пам'яті.

У таких випадках файл `/etc/ptmp` залишається на диску, блокуючи всі наступні виклики `useradd`, `usermod` чи `vipw`. Такий замок називається **застарілим блокуванням (Stale Lock)**.

Щоб система не зависала назавжди, пакет `shadow-utils` використовує багатоетапну стратегію ідентифікації власника та валідації блокування.

```
       +------------------------------------+
       |  Спроба open(..., O_CREAT|O_EXCL)  |
       +-----------------+------------------+
                         |
                 [EEXIST: файл є]
                         |
                         v
       +------------------------------------+
       |   Зчитування PID з /etc/ptmp та    |
       |   перевірка віку файлу через stat  |
       +-----------------+------------------+
                         |
              +----------+----------+
              |                     |
     [Вік < таймауту       [Вік > таймауту
      (15-30 сек)]          (застарілий)]
              |                     |
              v                     v
   +--------------------+  +--------------------+
   | Перевірка kill(0): |  | Перевірка kill(0)  |
   | Процес живий?      |  | та /proc/[PID]     |
   +----+----------+---+  +----+----------+---+
        |          |           |          |
      [Так]       [Ні]       [Так]       [Ні]
        |          |           |          |
        v          |           v          v
   +----------+    |     +----------+ +-----------+
   | Очікувати|    +---->| Попередити| | Безпечне  |
   | retry або|          | оператора| | видалення |
   | відмова  |          | (активний| | stale-замка|
   +----------+          | процес)  | +-----------+
                         +----------+
```

### 1. Запис PID у файл блокування
Одразу після успішного відкриття дескриптора файл не залишається порожнім. Процес зобов'язаний негайно записати в нього свій числовий ідентифікатор (PID) у текстовому форматі за допомогою системного виклику `write()` (наприклад, рядок `"41258\n"`).

### 2. Перевірка активності процесу через `kill(pid, 0)`
Коли інша утиліта натрапляє на наявний замок `ptmp`, вона відкриває його на читання і вичитує записаний туди PID. Після цього викликається системний виклик `kill(owner_pid, 0)`.

Сигнал `0` не надсилає процесу жодного реального переривання, але змушує ядро виконати повну перевірку існування цільового процесу та прав доступу до нього:
* Якщо `kill()` повертає `-1`, а змінна `errno` встановлюється в `ESRCH` (No such process), це означає, що процес із таким PID гарантовано відсутній у таблиці процесів ядра. Замок залишився після аварії і є мертвим.
* Якщо `kill()` повертає `0` або помилку `EPERM` (Operation not permitted), процес із таким PID реально існує і виконується в системі.

### 3. Пастка повторного використання PID (PID Recycling) та аналіз `/proc`
У системі Linux простір ідентифікаторів процесів є обмеженим (за замовчуванням значення `/proc/sys/kernel/pid_max` становить 32768 чи 4194304). Після завершення процесу його числовий PID через деякий час виділяється ядром для зовсім іншої новоствореної програми (наприклад, браузера чи вебсервера).

Якщо просто перевірити `kill(pid, 0)`, утиліта може помилково вирішити, що старий замок тримає живий процес `useradd`, тоді як насправді під цим PID уже працює фоновий поштовий демон. Для надійної верифікації зрілі системні інструменти виконують додаткову перевірку через псевдофайлову систему `/proc`:
1. Зчитують командний рядок процесу з `/proc/[pid]/cmdline` або ім'я виконуваного файлу через символічне посилання `/proc/[pid]/exe`.
2. Перевіряють час старту процесу (поле `starttime` у `/proc/[pid]/stat`). Якщо час старту процесу пізніший за час створення блокувального файлу (`st_mtime` у структурі `stat`), PID однозначно було перевикористано після збою оригінального власника замка.

### 4. Таймаути та політика звільнення
Утиліти пакета `shadow-utils` не видаляють чужі файли блокувань автоматично без попередження. Типовий протокол передбачає цикл очікування (зазвичай до 15–30 секунд із періодичними спробами). Якщо час модифікації файлу перевищує встановлений ліміт, а перевірки підтверджують відсутність живого процесу-власника, утиліта виводить адміністратору діагностичне повідомлення про виявлення застарілого блокування з пропозицією видалити файл `/etc/ptmp` вручну або перехоплює керування для скидання мертвого замка.

## Безпека сигналів та асинхронне очищення (Async-Signal Safety)

Процес оновлення системної бази облікових записів займає певний проміжок часу: потрібно прочитати сотні рядків, розпарсити поля, внести правки, скинути буфери на накопичувач і підмінити файл. У будь-який момент цієї послідовності користувач або зовнішній процес може надіслати сигнал завершення:
* `SIGINT` — адміністратор натиснув `Ctrl+C` у терміналі;
* `SIGTERM` — система керування службами `systemd` зупиняє завдання;
* `SIGHUP` — обірвалася сесія віддаленого термінала SSH;
* `SIGQUIT` — запит на завершення з дампом пам'яті (`Ctrl+\`).

Якщо процес завершиться за замовчуванням, файл `/etc/ptmp` залишиться на диску. Наступний виклик `useradd` отримає помилку блокування і завершить роботу з кодом `1` (`E_CANT_UPDATE`).

### Захист через `sigaction` та прапорець стану
Для запобігання появі сміттєвих замків утиліта зобов'язана реєструвати обробники критичних сигналів (`SIGINT`, `SIGHUP`, `SIGQUIT`, `SIGTERM`) за допомогою системного виклику `sigaction()`.

### Вимоги до функцій, безпечних для асинхронних сигналів
Обробник сигналу виконується асинхронно в контексті того самого потоку, перериваючи виконання основної програми в довільній точці. Це накладає суворі обмеження стандарту POSIX:

> ⚠️ **Критична вимога стандарту POSIX: Async-Signal-Safe Functions.**
> В обробнику сигналу категорично заборонено викликати небезпечні функції:
> * функції форматованого введення/виведення (`printf`, `fprintf`, `fopen`, `fclose`), оскільки вони використовують внутрішні нереентерабельні блокування потоків бібліотеки C;
> * функції динамічного виділення пам'яті (`malloc`, `free`, `realloc`), оскільки вони маніпулюють глобальними структурами купи (heap locks);
> * функцію завершення `exit()`, оскільки вона скидає буфери потоків stdio та викликає зареєстровані хуки `atexit()`.

Єдиними допустимими діями в обробнику є використання асинхронно безпечних системних викликів: `unlink()`, `close()`, `write()` та негайне завершення процесу через низькорівневий системний виклик `_exit()` (або `_Exit()`).

Для синхронізації стану між основним потоком і обробником сигналу використовується змінна-прапорець типу `volatile sig_atomic_t` (або атомарний прапорець `std::atomic<bool>`). Тип `sig_atomic_t` гарантує, що операції читання та запису значення прапорця виконуються як одна атомарна інструкція процесора без проміжних станів переривання, а ключове слово `volatile` забороняє компілятору оптимізувати доступ до змінної через регістри процесора.

Для штатних шляхів виходу без сигналів використовується реєстратор `atexit(cleanup_lock)`, який гарантує видалення файлу блокування при нормальному виході з програми або виклику стандартного `exit()`.

## Конвеєр атомарної фіксації: роль `fsync()` та семантика `rename()`

Формування файлу бази завершується фазою фіксації змін. Саме тут закладається стійкість системи до раптових апаратних збоїв.

```
       +------------------------------------------+
       | 1. Запис оновлених рядків у /etc/ptmp    |
       +--------------------+---------------------+
                            |
                            v
       +------------------------------------------+
       | 2. fflush(out): скидання буферів C stdio |
       +--------------------+---------------------+
                            |
                            v
       +------------------------------------------+
       | 3. fsync(fd): синхронізація кешу сторінок|
       |    ядра Linux з енергонезалежним диском  |
       +--------------------+---------------------+
                            |
                            v
       +------------------------------------------+
       | 4. rename("/etc/ptmp", "/etc/passwd"):   |
       |    атомарна підміна dentry у VFS         |
       +--------------------+---------------------+
                            |
                            v
       +------------------------------------------+
       | 5. Зняття прапорця g_locked = 0          |
       +--------------------+---------------------+
```

### 1. Чому виклик `fsync()` є обов'язковим
Коли програма записує дані через `write()` або `fputs()`, байти насправді не потрапляють на фізичний накопичувач миттєво. Вони осідають у дворівневому кеші:
1. **Буфер користувацького простору:** Буфер бібліотеки C (`FILE*`), розмір якого зазвичай становить 4 чи 8 КБ. Для його проштовхування в ядро потрібен виклик `fflush()`.
2. **Кеш сторінок ядра (Page Cache):** Ядро Linux позначає сторінки пам'яті як брудні (dirty pages) і відкладає їхній фізичний запис на диск на період до 30 секунд (фоновий потік ядра `flusher/pdflush`).

Якщо викликати `rename()` без попереднього виклику `fsync()`, файлова система (наприклад, ext4 чи XFS) може зафіксувати зміну метаданих каталогу в журналі раніше, ніж брудні сторінки з вмістом файлу дійдуть до фізичних комірок пам'яті NVMe/SSD. У разі раптового зникнення живлення після перезавантаження система виявить, що `/etc/passwd` вказує на новий inode, але його розмір становить 0 байтів або його блоки заповнені нулями.

Виклик `fsync(fileno(out))` примушує контролер накопичувача скинути внутрішній апаратний кеш і записати всі сторінки даних та метадані inode на енергонезалежний носій. Лише після повернення успішного статусу з `fsync()` дозволено переходити до перейменування.

### 2. Атомарність системного виклику `rename()` на рівні VFS
Системний виклик `rename(oldpath, newpath)` — це наріжний камінь атомарних файлових операцій у стандартах POSIX.

Коли цільовий файл `newpath` уже існує, ядро виконує операцію заміни за такими правилами:
1. **Неподільність dentry:** Зв'язок імені `/etc/passwd` зі старим inode розривається, і каталог починає вказувати на новий inode (той, що належав `ptmp`) в межах однієї операції блокування каталогу VFS.
2. **Відсутність вікна відсутності файлу:** У жоден момент часу файл `/etc/passwd` не зникає з файлової системи. Будь-який процес, що викликає `open("/etc/passwd", O_RDONLY)`, відкриє або стару версію файлу, або нову версію, але ніколи не отримає помилку `ENOENT`.
3. **Обслуговування відкритих дескрипторів:** Якщо якийсь читач уже мав відкритий дескриптор на старий `/etc/passwd`, він спокійно продовжує читати свій старий inode до закриття дескриптора. Лічильник посилань на старий inode зменшується, і після закриття всіма читачами ядро звільняє старі дискові блоки.

### 3. Обмеження єдиної точки монтування (`EXDEV`)
Системний виклик `rename()` гарантує атомарність лише за умови, що обидва файли (джерело і призначення) розташовані на **одній і тій самій змонтованій файловій системі** (мають однаковий ідентифікатор пристрою `st_dev`).

Якщо спробувати створити файл блокування у `/tmp` (який у сучасних дистрибутивах є окремою файловою системою в оперативній пам'яті `tmpfs`), а потім виконати `rename("/tmp/ptmp", "/etc/passwd")`, системний виклик поверне помилку `-1`, а `errno` буде встановлено в `EXDEV` (Invalid cross-device link).

Ядро не може атомарно переставити покажчики dentry між різними суперблоками: перенесення файлу між пристроями вимагає повного фізичного копіювання байтів із подальшим видаленням оригіналу, що руйнує будь-яку атомарність. Саме тому файл `/etc/ptmp` завжди зобов'язаний перебувати в тому самому каталозі `/etc`, що й цільова база.

## Практична реалізація: C та сучасний C++23

Нижче наведено повну реалізацію системної утиліти модифікації реєстраційної оболонки користувача, що втілює всі описані вище інженерні принципи: безпечне перехоплення сигналів, ексклюзивне захоплення файлу-м'ютекса, потокову обробку рядків, примусове скидання кешів через `fsync()` та атомарну підміну файлу.

Утиліта підтримує дві реалізації:
1. **Класичний C (C11):** Низькорівневе керування дескрипторами, обробниками `sigaction`, структурами `atexit` та безпечним асинхронним очищенням.
2. **Сучасний C++ (C++23):** Інкапсуляція життєвого циклу замка в RAII-клас `PasswdDatabaseLock` із забороною копіювання, семантикою переміщення (Move-only), використанням монадичного типу `std::expected<T, std::error_code>` замість винятків і безпечною фіксацією транзакції через метод `commit()`.

### Архітектурний розбір реалізації мовою C
1. **Глобальний стан та сигнали:** Змінна `g_locked` має тип `volatile sig_atomic_t`. Обробник `sig_handler` викликає `unlink(LOCK_FILE)` і негайно виконує `_exit(1)`. Це унеможливлює зависання в дедлоках обробника сигналів.
2. **Захоплення замка (`acquire_passwd_lock`):** Виклик `open(LOCK_FILE, O_CREAT | O_EXCL | O_RDWR, 0600)` повертає числовий файловий дескриптор. Запис власного PID гарантує, що діагностичні утиліти зможуть виявити власника замка.
3. **Потокова обробка:** Оригінальний файл читається через `fgets()`, кожен рядок розбирається реентерабельною функцією `strtok_r()`. Змінений рядок записується в дескриптор замка без виділення динамічної пам'яті.
4. **Синхронізація та заміна:** Комбінація `fflush(out)` і `fsync(fileno(out))` гарантує фізичну цілісність перед тим, як системний виклик `rename()` зробить новий стан доступним усій системі. Після успішного `rename()` прапорець `g_locked` скидається в `0`, що вимикає зайве видалення у фіналізаторі `atexit()`.

### Архітектурний розбір реалізації мовою C++23
1. **RAII-клас `PasswdDatabaseLock`:** Замок володіє файловим дескриптором `m_fd` та булевим прапорцем `m_locked`. Деструктор автоматично закриває дескриптор і видаляє файл блокування `::unlink(kLockPath.data())`, якщо об'єкт знищується через достроковий вихід або помилку.
2. **Move-Only семантика:** Конструктор копіювання та оператор копіювання видалені (`= delete`). Конструктор переміщення та оператор переміщення коректно передають володіння дескриптором, обнуляючи попередній екземпляр (`other.m_fd = -1; other.m_locked = false;`).
3. **Монадична обробка помилок:** Замість генерації винятків C++ (`throw`), які можуть бути небезпечними у низькорівневих системних службах, методи повертають `std::expected<PasswdDatabaseLock, std::error_code>`. Це уможливлює швидку функціональну перевірку результату без оверхеду на розгортання стека (stack unwinding).
4. **Явний коміт (`commit`):** Метод `commit()` виконує `fsync`, закриває дескриптор, робить `rename` і скидає внутрішній стан `m_locked = false`. Після цього деструктор безпечно завершує роботу, не видаляючи щойно перейменовану базу даних.

### 2. Трасування системних викликів через `strace`
Найкращий спосіб на власні очі переконатися у відсутності гонок і правильній послідовності викликів ядра — запустити утиліту під спостереженням інструмента `strace`, відфільтрувавши операції відкриття, запису, синхронізації та зміни імен:

```bash
sudo strace -e trace=openat,write,fsync,rename,unlink,rt_sigaction ./update_shell_c andrij /bin/zsh
```

Типовий протокол системних викликів демонструє весь життєвий цикл блокування:

```text
--- 1. Реєстрація безпечних обробників сигналів ---
rt_sigaction(SIGINT, {sa_handler=0x555555555230, sa_mask=[], sa_flags=0}, NULL, 8) = 0
rt_sigaction(SIGHUP, {sa_handler=0x555555555230, sa_mask=[], sa_flags=0}, NULL, 8) = 0
rt_sigaction(SIGTERM, {sa_handler=0x555555555230, sa_mask=[], sa_flags=0}, NULL, 8) = 0

--- 2. Ексклюзивне створення файлу-замка ---
openat(AT_FDCWD, "/etc/ptmp", O_RDWR|O_CREAT|O_EXCL, 0600) = 3
write(3, "41258\n", 6)                   = 6

--- 3. Відкриття джерела та запис зміненого вмісту ---
openat(AT_FDCWD, "/etc/passwd", O_RDONLY) = 4
write(3, "root:x:0:0:root:/root:/bin/bash\n"..., 1024) = 1024
write(3, "andrij:x:1001:1001::/home/andrij:/bin/zsh\n", 42) = 42

--- 4. Апаратне скидання кешів накопичувача ---
fsync(3)                                = 0

--- 5. Атомарна заміна dentry бази ---
rename("/etc/ptmp", "/etc/passwd")      = 0
+++ exited with 0 +++
```

### 3. Перевірка реакції на конкурентні конфлікти
Щоб перевірити захист від одночасного запуску двох утиліт модифікації, можна вручну створити замок і спробувати запустити утиліту:

```bash
# Симуляція блокування іншою утилітою:
sudo touch /etc/ptmp

# Спроба запуску утиліти:
sudo ./update_shell_c andrij /bin/bash
# Вивід: Помилка: файл блокування /etc/ptmp вже існує.

# Очищення замка:
sudo rm /etc/ptmp
```

Завдяки суворому дотриманню протоколу `ptmp`, скиданню кешів `fsync()` та неподільній операції `rename()` система облікових записів зберігає абсолютну консистентність даних за будь-якої інтенсивності паралельних читачів і при будь-яких аварійних зупинках процесів.
