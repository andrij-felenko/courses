# 📜 Від ptrace до seccomp: еволюція перехоплення системних викликів

Еволюція механізмів спостереження та перехоплення системних викликів у Unix та Linux охоплює понад сорок років розвитку системного програмного забезпечення — від перших інструментів налагодження 1970-х років до сучасних асинхронних супервізорів пісочниць у контейнеризованих середовищах. Розвиток операційних систем висував нові вимоги до безпеки, ізоляції процесів та продуктивності, змушуючи ядро еволюціонувати від примітивного покрокового інспектування пам'яті до високопродуктивної фільтрації виконання викликів у реальному часі.

## Витоки: ptrace у Version 7 Unix та Bell Labs

У перших версіях операційної системи Unix налагодження процесів було суттєво обмеженим. Для аналізу аварійних зупинок розробники використовували знімки пам'яті (core dump) або додавали відлагоджувальний друк безпосередньо у вихідний код. Потреба в інтерактивному аналізі стану процесів у реальному часі призвела до створення системного виклику `ptrace` (process trace), який уперше з'явився у 1979 році у системі Version 7 Unix (V7), розробленій у лабораторіях Bell Labs Деннісом Рітчі та Кеном Томпсоном.

Перша концепція `ptrace` була дуже простою: дозволити одному процесу (трасувальнику) читати й записувати значення регістрів та комірок пам'яті іншого процесу (трасованого). Оскільки архітектура тогочасних процесорів (зокрема PDP-11) мала чіткий поділ на режим користувача (User Mode) та режим ядра (Kernel Mode), системний виклик `ptrace` слугував безпечним містком, який виконував перемикання контексту й дозволяв інспектувати пам'ять без загрози краху ядра.

Однак у першій реалізації `ptrace` ще не існувало спеціалізованих команд для перехоплення системних викликів. Трасувальник міг зупинити процес лише за допомогою системних сигналів (зокрема `SIGTRAP`), що робило аналіз системної взаємодії повільним і складним.

## Поява ptrace у System V, BSD та Linux

У 1980-х роках із розколом Unix на дві головні гілки — System V та BSD — підходи до трасування розділилися:

1. **Гілка System V Release 4 (SVR4)** запропонувала альтернативну концепцію: інтерфейс `/proc`. Замість єдиного системного виклику з десятками аргументів, кожен процес представлений як файл або тека у віртуальній файловій системі `/proc`. Керування процесом здійснювалося через файлові дескриптори за допомогою викликів `ioctl()` над файлами у `/proc/<pid>/ctl`.
2. **Гілка BSD та Linux** зберегли класичний системний виклик `ptrace()`, але значно розширили його функціональність. У ядрі Linux з'явилися прапорці `PTRACE_SYSCALL` та `PTRACE_SINGLESTEP`, які дозволили фіксувати точні моменти входу процесу в ядро (`sys_enter`) та виходу з нього (`sys_exit`).

У 1991 році Пол Краненбург (Paul Kranenburg) створив утиліту `strace` для операційної системи SunOS, яка згодом була портована на Linux Вічертом Аккерманом (Wichert Akkerman). Утиліта `strace` стала основним інструментом системних адміністраторів та розробників для діагностики помилок I/O, пошуку відсутніх конфігураційних файлів та аналізу мережевих з'єднань без доступу до вихідного коду програми.

## Криза продуктивності та проблеми безпеки ptrace

Із зростанням навантаження на серверні системи на початку 2000-х років проявилися фундаментальні вади архітектури `ptrace`:

- **Величезні накладні витрати на перемикання контексту**: Кожен системний виклик трасованого процесу вимагав чотирьох перемикань контексту (tracee → ядро → tracer → ядро → tracee на вході і стільки ж на виході). Якщо програма виконувала тисячі дрібних викликів `read()` або `write()`, її продуктивність падала в десятки разів.
- **Вразливість TOCTOU (Time-of-Check to Time-of-Use)**: Оскільки `ptrace` зупиняє процес на `sys_enter`, трасувальник міг прочитати аргументи виклику (наприклад, шлях до файлу у виклику `open()`) з пам'яті трасованого процесу. Проте якщо трасований процес був багатонитковим, інша нитка могла змінити вміст цієї ж пам'яті між моментом перевірки трасувальником і моментом виконання виклику ядром.
- **Ризики ескалації привілеїв**: Дозвіл будь-якому процесу приєднуватися через `ptrace` до інших процесів того ж користувача створював вектор для атаки. Шкідливий процес міг впровадити свій код у легітимний процес (наприклад, у SSH-агент або сесію sudo). Для вирішення цієї проблеми у ядрі Linux з'явився модуль безпеки Yama LSM із параметром `ptrace_scope`.

Модуль Yama LSM ввів чотири рівні обмеження `ptrace`:
- **`0` (Classic ptrace permissions)**: Процес може трасувати будь-який інший процес свого користувача.
- **`1` (Restricted ptrace)**: Процес може трасувати лише свої прямо породжені дочірні процеси. Це поточне стандартне значення для більшості дистрибутивів Linux (Ubuntu, Debian, Fedora).
- **`2` (Admin-only ptrace)**: Лише процеси з привілеєм `CAP_SYS_PTRACE` (root) можуть використовувати `ptrace`.
- **`3` (No ptrace)**: Використання `ptrace` повністю блокується в системі до перезавантаження.

## Поява Seccomp та революція BPF-фільтрів

У 2005 році Лінус Торвальдс та Андреа Арканжелі (Andrea Arcangeli) створили механізм **Seccomp** (Secure Computing Mode) у ядрі Linux 2.6.12. Початкова мета Seccomp була надзвичайно вузькою: надати обчислювальним вузлам сітки (Grid Computing) можливість виконувати невідомий код користувача у максимальній ізоляції. У першому режимі (`SECCOMP_SET_MODE_STRICT`) процесу дозволялося виконувати лише чотири системні виклики: `read()`, `write()`, `_exit()` та `sigreturn()`. Будь-який інший виклик призводив до негайного знищення процесу сигналом `SIGKILL`.

Хоча режим Strict був абсолютно безпечним, він виявився занадто обмеженим для реальних застосунків. 

У 2012 році Вілл Дрюрі (Will Drewry) запропонував розширення **Seccomp-BPF** (`SECCOMP_SET_MODE_FILTER`). Це дозволило процесам завантажувати в ядро байт-код класичного фільтра пакетиів BPF (cBPF). Фільтр аналізував номер системного виклику та його аргументи прямо під час входу в ядро й приймав рішення: дозволити (`SECCOMP_RET_ALLOW`), заборонити з помилкою (`SECCOMP_RET_ERRNO`) чи вбити процес. Завдяки Seccomp-BPF з'явилися сучасні пісочниці у браузерах (Google Chrome, Mozilla Firefox) та контейнерних ізоляторах (Docker, podman).

## Seccomp User Notification: Асинхронний супервізор

Незважаючи на успіх Seccomp-BPF, залишалася фундаментальна проблема: BPF-фільтр у ядрі не міг розіменовувати вказівники у пам'яті користувача. Фільтр міг бачити лише чисельні аргументи (наприклад, дескриптор або прапорці), але не міг прочитати текстовий шлях до файлу у виклику `openat()`. Це унеможливлювало створення віртуальних файлових систем або емуляцію системних викликів без привілеїв root.

У 2019 році у ядрі Linux 5.0 Крістіан Браунер (Christian Brauner) та Саргун Дхіллон (Sargun Dhillon) реалізували механізм **Seccomp User Notification** (`SECCOMP_RET_USER_NOTIF`). 

Цей механізм поєднав найкраще з двох світів:
1. Високу швидкість BPF-фільтрації для звичайних викликів (які дозволяються без жодних накладних витрат).
2. Можливість передати конкретний системний виклик зовнішньому супервізору через файловий дескриптор сповіщення.

Завдяки розробці `pidfd_open` та `SECCOMP_IOCTL_NOTIF_ID_VALID` у Linux 5.3–5.5 вдалося полностью усунути атаки TOCTOU: супервізор тепер отримує доступ до пам'яті трасованого процесу через безпечний файловий дескриптор `/proc/$PID/mem` або `process_vm_readv()`, гарантуючи унікальність ідентифікатора виклику.

Сьогодні Seccomp User Notification є основою для таких проектів, як **gVisor** (Google), **systemd** (динамічна віртуалізація вузлів `/dev` та `/sys`), **LXCFS** та непривілейованих контейнерів, дозволяючи емулювати поведінку ядра без потреби в модулях чи привілеях суперкористувача.
