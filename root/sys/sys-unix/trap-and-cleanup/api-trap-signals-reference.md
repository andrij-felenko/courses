# 📋 Довідник вбудованої команди trap та системних сигналів

Вбудована команда оболонки `trap` є інтерфейсом між процесною моделлю сигналів операційної системи Unix та середовищем виконання сценаріїв. Вона керує внутрішньою таблицею диспозиції сигналів (Signal Disposition Table) інтерпретатора, дозволяючи призначати довільні списки інструкцій оболонки для виконання у відповідь на асинхронні події ядра або внутрішні стани самого інтерпретатора.

---

## Синтаксис та форми виклику

У стандартах POSIX.1-2017/2024 та інтерпретаторах Bash, Ksh та Dash синтаксис команди `trap` має таку сигнатуру:

```bash
trap [-lp] [[arg] sigspec ...]
```

### Форми аргументу дії (`arg`)

Команда `trap` інтерпретує свій перший непрапорцевий аргумент як інструкцію для внутрішнього диспетчера подій:

| Форма виклику | Дія інтерпретатора | Механізм на рівні ядра та пам'яті |
| :--- | :--- | :--- |
| `trap 'action' SIG...` | Встановлює команду `action` як обробник зазначених сигналів. | Реєстрація внутрішнього C-обробника через `sigaction(2)`, що встановлює бітовий прапорець відкладеного виконання у структурі `sigmodes[]`. |
| `trap '' SIG...` | Повністю **ігнорує** зазначений сигнал. | Системний виклик `sigaction(sig, &act{sa_handler=SIG_IGN}, ...)` у ядрі. Сигнал блокується і не доставляється процесу. |
| `trap - SIG...` | **Скидає** дію на стандартну поведінку за замовчуванням. | Системний виклик `sigaction(sig, &act{sa_handler=SIG_DFL}, ...)` або відновлення початкового стану при старті оболонки. |
| `trap` або `trap -p` | Виводить у `stdout` список усіх поточних активних пасток у форматі, придатному для повторного зчитування оболонкою (`eval "$(trap -p)"`). | Читання внутрішнього масиву рядків `trap_list[]` інтерпретатора з коректним екрануванням лапок. |
| `trap -l` | Виводить список усіх підтримуваних операційною системою сигналів та їхніх числових номерів (специфічно для Bash/Zsh). | Ітерація по системному масиву `sys_siglist` / `strsignal(3)`. |

## Внутрішній механізм: чому shell trap відрізняється від `sigaction(2)`

У низькорівневих програмах мовою C обробник сигналу, зареєстрований через системний виклик `sigaction(2)`, виконується асинхронно прямо на стеку перерваного потоку в довільний момент часу. Через це всередині C-обробника дозволено викликати виключно асинхронно-безпечні функції (Async-Signal-Safe functions) на кшталт `write(2)`, `_exit(2)` або `kill(2)`. Будь-який виклик функцій виділення пам'яті (`malloc`), форматованого вводу-виводу (`printf`) або модифікації глобальних структур призводить до стану взаємного блокування (Deadlock) або пошкодження пам'яті.

Командна оболонка Bash працює принципово інакше:

1. **Двоетапна доставка:** При отриманні асинхронного сигналу від ядра виконується крихітний внутрішній C-обробник інтерпретатора (наприклад, функція `sighandler()` у вихідному коді Bash `sig.c`). Цей обробник лише встановлює бітовий прапорець у глобальному масиві `pending_signals` та декрементує лічильники очікування, після чого негайно повертає керування ядру.
2. **Синхронне виконання рядка-пастки:** Основний цикл інтерпретатора перевіряє стан `pending_signals` у строго визначених точках безпеки — між розбором вузлів абстрактного синтаксичного дерева (AST), безпосередньо перед запуском чергової інструкції або після повернення системного виклику `waitpid(2)`.
3. **Повнота контексту:** Оскільки дія `trap` виконується у звичайному синхронному контексті інтерпретатора, всередині неї можна безпечно використовувати будь-які складні конструкції оболонки: цикли, виклики зовнішніх утиліт, монтування дисків, створення файлів та роботу зі складними масивами без ризику пошкодження пам'яті.

## Специфікація сигналів: назви проти номерів

Стандарт POSIX допускає вказування сигналів як за числовими номерами (`1`, `2`, `15`), так і за назвами без префікса `SIG` (`HUP`, `INT`, `TERM`). Сучасний стандарт та Bash також підтримують повні назви з префіксом (`SIGHUP`, `SIGINT`). 

Використання числових значень (крім `0` для `EXIT`) є **небезпечним для переносності**, оскільки номери сигналів реального часу та деяких стандартних сигналів (наприклад, `SIGUSR1`, `SIGUSR2`, `SIGPOLL`) відрізняються між архітектурами x86_64, ARM64, MIPS та SPARC.

| Назва сигналу | Номер x86_64 / ARM64 | Номер MIPS | Номер SPARC | Призначення |
| :--- | :--- | :--- | :--- | :--- |
| `SIGHUP` | 1 | 1 | 1 | Обрив зв'язку терміналу |
| `SIGINT` | 2 | 2 | 2 | Переривання з клавіатури |
| `SIGQUIT` | 3 | 3 | 3 | Аварійний вихід з дампом |
| `SIGUSR1` | 10 | 16 | 30 | Користувацький сигнал 1 |
| `SIGUSR2` | 12 | 17 | 31 | Користувацький сигнал 2 |
| `SIGPOLL` / `SIGIO` | 29 | 22 | 23 | Подія вводу-виводу |

```bash
# Переносний стандартний запис (рекомендовано POSIX):
trap cleanup INT TERM HUP

# Допустимий запис у Bash/Zsh:
trap cleanup SIGINT SIGTERM SIGHUP

# Застарілий непереносний запис (ризик збою на MIPS/SPARC):
trap cleanup 2 15 1
```

### 2. Псевдосигнали оболонки (Shell Special Traps)

Псевдосигнали не генеруються ядром і не мають записів у таблиці сигналів ОС. Це внутрішні події життєвого циклу інтерпретатора:

| Псевдосигнал | Підтримка | Умова спрацьовування | Семантика виконання |
| :--- | :--- | :--- | :--- |
| `EXIT` (або `0`) | POSIX, Bash, Zsh, Dash, Ksh | Будь-яке завершення оболонки: нормальне, через `exit`, через фатальний сигнал або `set -e`. | Виконується один раз безпосередньо перед системним викликом `_exit(2)`. Зберігає код завершення `$?` попередньої команди, якщо всередині trap явно не викликано інший `exit`. |
| `ERR` | Bash, Ksh, Zsh | Повернення будь-якою командою ненульового коду виходу `$? != 0`. | Аналог спрацьовування `set -e`, але виконує призначену дію. За замовчуванням НЕ успадковується функціями без прапорця `set -o errtrace` (`set -E`). |
| `RETURN` | Bash, Ksh, Zsh | Завершення виконання функції оболонки або файлу, завантаженого через `source` / `.`. | Виконується в контексті викликаючого середовища безпосередньо перед поверненням керування. Потребує `set -o functrace` (`set -T`) для вкладених викликів. |
| `DEBUG` | Bash, Ksh, Zsh | Перед кожною простою командою, виразом `for`, `case`, `select` або арифметичною інструкцією. | Дозволяє покрокове трасування, інспекцію змінних та реалізацію інтерактивних налагоджувачів. |

## Правила успадкування та поведінки у вкладених контекстах

Поведінка диспозицій `trap` суворо регламентується POSIX у розрізі ізоляції просторів виконання:

### 1. Форк підоболонки: `( ... )`, `$( ... )`, `<( ... )`
- **Звичайні пастки (SIGINT, SIGTERM):** У підоболонці всі власні обробники скидаються у стандартні системні диспозиції (`SIG_DFL`). Це запобігає випадковому виконанню прибирання батька всередині дочірнього процесу.
- **Ігноровані сигнали (`trap '' SIG...`):** Якщо сигнал був проігнорований у батьківському процесі перед форком, він **залишається проігнорованим** у дочірній підоболонці та у всіх програмах, запущених через `execve(2)`. Це фундаментальне правило безпеки POSIX: дочірній процес не може випадково зняти маскування сигналу, встановлене батьком.
- **Пастка `EXIT`:** Пастка `EXIT` батьківського процесу **не виконується** при завершенні підоболонки. Підоболонка може зареєструвати власний `trap ... EXIT`, який спрацює лише при виході з цієї конкретної підоболонки.

### 2. Функції оболонки
- Функції виконуються в тому самому адресному просторі, що й основна програма.
- Встановлення `trap` всередині функції змінює **глобальну таблицю диспозицій** усього скрипту, якщо функція не викликана всередині підоболонки `( func )`.

### 3. Системний виклик `exec`
- При заміні тіла оболонки бінарним образом (`exec /usr/bin/app`):
  - Усі перехоплені сигнали скидаються на `SIG_DFL`.
  - Усі проігноровані сигнали (`trap '' ...`) лишаються в стані `SIG_IGN` для нової програми.
  - Пастка `EXIT` **не викликається**, оскільки процес оболонки не завершується через `exit()`, а заміщується новим виконуваним образом.

## Взаємодія з прапорцями режиму суворості: `set -e`, `set -u` та `set -o pipefail`

При роботі в режимі суворого виконання (Strict Mode) взаємодія між пастками та прапорцями має важливі особливості:

1. **`set -e` (ERREXIT) та `trap ... EXIT`:** Якщо команда повертає ненульовий статус у режимі `set -e`, оболонка негайно припиняє виконання наступних рядків файлу і переходить до виконання зареєстрованого обробника `trap ... EXIT`. Всередині самого обробника пастки прапорець `set -e` тимчасово вимикається, щоб збій однієї команди прибирання не зірвав виконання інших.
2. **`set -e` та `trap ... ERR`:** Обробник `ERR` викликається щоразу, коли спрацьовує умова помилки, але він **не викликається** для команд, чий статус перевіряється безпосередньо у конструкціях `if`, `while`, `until` або за допомогою логічних операторів `||` та `&&`. Це сувора вимога POSIX, яка запобігає хибному спрацьовуванню обробника помилок на штатних умовних перевірках.
3. **`set -u` (NOUNSET):** Звернення до неініціалізованої змінної викликає негайне завершення інтерпретатора. При цьому пастка `EXIT` викликається гарантовано, проте змінні, що використовуються всередині коду самої пастки, також повинні бути захищені значеннями за замовчуванням (наприклад, `${TMP_DIR:-}`), інакше `set -u` зірве виконання коду очищення.

## Прапорці інтроспекції та трасування Bash

Для розширеного керування областю видимості пасток `ERR`, `RETURN` та `DEBUG` інтерпретатор Bash надає спеціальні прапорці середовища:

```bash
# 1. Успадкування trap ERR функціями, підоболонками та підстановками команд
set -o errtrace
# або короткий запис:
set -E

# 2. Успадкування trap DEBUG та trap RETURN функціями та вкладеними файлами
set -o functrace
# або короткий запис:
set -T
```

Без активації `set -E` будь-яка помилка, що сталася всередині користувацької функції, не викликає глобальний обробник `trap ... ERR`, якщо цей обробник не було перевизначено локально всередині самого тіла функції. Це найчастіша причина того, чому складні багаторівневі скрипти не реагують на аварії допоміжних підпрограм.

## Ідіома збереження та відновлення пасток (Trap Stacking)

У бібліотечних функціях часто виникає потреба тимчасово встановити власний обробник сигналу або помилки, а після виконання операції повернути початковий стан, встановлений зовнішнім кодом. Завдяки формату виводу команди `trap -p` це реалізується за допомогою шаблону динамічного збереження:

```bash
# Збереження поточної активної пастки для сигналу SIGINT
OLD_INT_TRAP=$(trap -p INT)

# Встановлення тимчасового локального обробника
trap 'echo "Операцію перервано користувачем"; return 1' INT

# Виконання критичної операції
perform_sensitive_io_operation

# Відновлення початкової пастки (або скидання, якщо пастки не було)
if [[ -n "${OLD_INT_TRAP}" ]]; then
    eval "${OLD_INT_TRAP}"
else
    trap - INT
fi
```

Команда `trap -p` гарантує, що виведений рядок містить повну команду відновлення з правильним екрануванням лапок, що унеможливлює пошкодження синтаксису під час виклику `eval`.
