# 📜 Еволюція керування обладнанням: від вендорських ACPI-методів до специфікації WMI to ACPI Mapper

Наприкінці 1990-х років ринок мобільних комп'ютерів (ноутбуків) зіштовхнувся з критичною проблемою стандартизації. Кожен OEM-виробник — Dell, HP, ASUS, IBM/Lenovo, Toshiba, Sony — додавав до своїх пристроїв унікальні апаратні можливості. Гарячі клавіші на клавіатурі (зміна яскравості екрана, регулювання гучності, перемикачі бездротових модулів Wi-Fi та Bluetooth), контролери підсвічування, додаткові датчики температури, вентилятори зі змінною швидкістю та специфічні налаштування BIOS вимагали програмного керування з боку операційної системи.

Однак специфікація ACPI (Advanced Configuration and Power Interface), розроблена спільно Intel, Microsoft, Toshiba, HP та Phoenix, визначала лише базові класи пристроїв: стандартну батарею, адаптер живлення AC, кнопки живлення/сну та термозони (thermal zones). Жодного стандарту для "увімкнути підсвічування клавіатури ASUS" чи "переключити термопрофіль вентилятора Dell" у базовому ACPI не існувало.

## Ера хаотичних ACPI-розширень (1998–2005)

До появи уніфікованих специфікацій кожен вендор вирішував проблему шляхом створення власних об'єктів у просторі імен ACPI (таблицях DSDT/SSDT). В АМЛ-коді (ACPI Machine Language) з'являлися пристрої з довільними ідентифікаторами (HID):

- **ASUS** створювала пристрої з HID `ATK0100` або `ASUS010` із власними методами на кшталт `\GMOD`, `\SMOD`.
- **Dell** використовувала виклики System Management Interrupt (SMI) через специфічні порт-адреси та ACPI-обгортки `\GSMI`.
- **HP / Compaq** додавала пристрої з HID `HPQ0004` або `Compaq_WMI`.
- **Toshiba** розгортала об'єкти `\TOSH_ACPI`.

Для розробників операційних систем (як Windows, так і Linux) це означало справжнє пекло підтримки. Для кожної ревізії материнської плати одного й того ж вендора доводилося писати окремий драйвер ядра. Будь-яка зміна назви AML-методу у новій версії BIOS призводила до того, що на ноутбуці переставали працювати гарячі клавіші регулювання яскравості чи перемикач Wi-Fi.

## Проблема System Management Mode (SMM)

Паралельно з хаотичними ACPI-методами OEM-виробники активного використовували режим SMM (System Management Mode) процесорів x86. Для зміни будь-якого конфігураційного параметра BIOS операційна система записувала дані у порт `0xb2`, викликаючи апаратне переривання SMI#. Процесор негайно призупиняв виконання усіх операційних потоків ядра на всіх ЦП-ядрах і передавав керування ізольованому коду прошивки SMRAM.

Це спричиняло важкі системні затримки (latency spikes), що робило використання Linux у завданнях реального часу (Real-Time Linux, PREEMPT_RT) абсолютно неможливим. Крім того, операційна система не мала жодної можливості аналізувати двійковий байткод, який виконувався у режимі SMM. Помилка у прошивці материнської плати призводила до мовчазного збою операційної системи без можливості відлагодження.

## Поява специфікації WMI to ACPI Mapper

Для розв'язання цієї проблеми компанія Microsoft у співпраці з Intel розробила специфікацію **WMI to ACPI Mapper Specification**. Ідея полягала у поєднанні інфраструктури WMI (Windows Management Instrumentation) — яка на той час вже була стандартом системного адміністрування в ОС Windows — із низькорівневим ACPI.

Замість того, щоб змушувати ОС знати унікальні назви AML-методів для кожної материнської плати, специфікація запропонувала абстракцію:

1. **Стандартизований ACPI пристрій:** Усі вендорські функції інкапсулюються в один стандартний ACPI пристрій із Hardware ID `PNP0C14`.
2. **Ідентифікація через GUID:** Будь-яка функція, блок даних або подія ідентифікується 128-бітним глобально унікальним ідентифікатором (GUID). Наприклад, певний GUID відповідає за терморегуляцію, а інший — за підсвічування клавіатури.
3. **Таблиця-дороговказ `_WDG`:** BIOS експортує єдиний буфер `_WDG`, який описує всі supported GUIDs та пов'язує їх з уніфікованими 2-символьними префіксами AML-методів (`WMxx`, `WQxx`, `WSxx`, `_WED`).
4. **Самодокументування через BMOF:** BIOS може містити двійковий буфер BMOF (Binary Managed Object Format), який описує структури даних та параметри методів людсько-зрозумілою мовою.

Завдяки цьому специфікація зробила апаратні розширення вендорів самоописовими та ізольованими від конкретних імен методів у DSDT.

## Становлення та еволюція WMI у ядрі Linux

Хоча WMI створювалася першочергово для Windows, розробники ядра Linux швидко усвідомили, що без підтримки цієї специфікації сучасні ноутбуки в Linux залишаться без базового функціоналу.

- **Перші реалізації (2007–2008):** Драйвер `wmi.ko` був доданий до ядра Linux розробником Меттью Гарреттом (Matthew Garrett). Початкова реалізація була процедурною: модуль парсив `_WDG` і надавав глобальні C-функції `wmi_evaluate_method()`, `wmi_install_notify_handler()` та `wmi_has_guid()`. Вендорські драйвери (`dell-wmi`, `hp-wmi`, `asus-wmi`) просто викликали ці функції за явними GUID-рядками. Інтеграцію обробки подій з підсистемою input ядра реалізував Дмитро Торохов (Dmitry Torokhov) через створення уніфікованого інтерфейсу `sparse-keymap`.
- **Шинна модель `wmi_bus_type` (Linux 4.13+, 2017 рік):** Розробник Енді Лутомірскі (Andy Lutomirski, commit 844af950da94) та колеги повністю переписали підсистему WMI, перетворивши її на повноцінну шину Linux Device Model. Кожен GUID з `_WDG` став окремим пристроєм `struct wmi_device`, а вендорські драйвери перейшли на декларативну реєстрацію `struct wmi_driver` із таблицями маппінгу `wmi_device_id`.
- **Сучасний стан:** WMI у Linux є основою для десятків драйверів у `drivers/platform/x86/`. Вона забезпечує роботу новітніх систем керування профілями живлення (platform_profile), підсвічування Alienware/ROG, обмеження заряду акумуляторів та синхронізації налаштувань BIOS безпосередньо з Linux через інтерфейс `firmware_attributes`.
