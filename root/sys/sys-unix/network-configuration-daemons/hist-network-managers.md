# 📜 Від статичних rc-скриптів до подієвих менеджерів: історія конфігурації мережі в Unix

Ця історична довідка розкриває інженерні причини, через які класичні статичні шелл-скрипти ініціалізації виявилися непридатними для динамічного мережевого середовища, та показує еволюцію підсистем керування мережею від перших реалізацій BSD UNIX до сучасних демонів NetworkManager, systemd-networkd та генератора Netplan.

---

## Епоха стаціонарних серверів: скрипти `rc` та фіксовані інтерфейси

На світанку розвитку BSD UNIX (4.2BSD, 4.3BSD) та комерційних операційних систем Unix (SunOS, IRIX, HP-UX, Ultrix) у 1980-х роках мережева топологія комп'ютерних систем вважалася абсолютно статичною. Сервери та інженерні робочі станції представляли собою масивні стаціонарні машини, фізично підключені товстим коаксіальним кабелем 10BASE5 (з характерними механічними "вампірними" відгалужувачами), тонким 10BASE2 або крученою парою 10BASE-T до єдиного фіксованого сегмента локальної мережі. Мережева карта Ethernet інсталювалася у слот розширення системної шини VMEbus, SBus, ISA або ранньої PCI один раз на весь життєвий цикл обладнання.

У такій парадигмі конфігурація мережі була тривіальною лінійною процедурою, що виконувалася один раз на етапі початкового завантаження операційної системи. Стартовий командний файл `/etc/rc` (пізніше розбитий у BSD на модульний `/etc/rc.conf` та у System V на відповідні рівні виконання `init.d`) послідовно викликав системні утиліти `ifconfig` та `route`:

```bash
# Типова лінійна ініціалізація мережі в ранніх Unix-системах
ifconfig le0 inet 192.168.1.10 netmask 255.255.255.0 up
route add default 192.168.1.1
```

Низькорівнева взаємодія цих утиліт із ядром операційної системи спиралася на системний виклик `ioctl()` поверх сокетів сімейства `AF_INET`. Утиліта заповнювала бінарну структуру `struct ifreq` і надсилала керуючі запити:
* `SIOCSIFADDR` — встановлення IPv4-адреси інтерфейсу.
* `SIOCSIFNETMASK` — задання маски підмережі.
* `SIOCSIFFLAGS` — підняття прапорців стану (зокрема `IFF_UP` та `IFF_RUNNING`).
* `SIOCADDRT` — запис статичного маршруту через структуру `struct rtentry`.

Скрипт відпрацьовував до кінця і завершував процес. Ядро операційної системи створювало структури `struct in_ifaddr` та утримувало призначені IP-адреси разом із таблицею маршрутизації в оперативній пам'яті до наступного перезавантаження або вимкнення живлення. 

У цій схемі було закладено низку фундаментальних обмежень:
1. **Відсутність механізму зворотного зв'язку**: Якщо мережевий кабель виймали з гнізда, апаратний драйвер фіксував втрату несучої частоти (Link Carrier Loss), проте жодного сповіщення у простір користувача не надходило. Ядро продовжувало зберігати IP-адресу та маршрути, намагаючись надсилати пакети у відключений лінк і викликаючи зависання клієнтських сокетів за таймаутом.
2. **Модель «один інтерфейс — одна адреса»**: Стек BSD спочатку не передбачав наявності кількох IP-адрес на одному фізичному адаптері. Коли в середині 1990-х років для віртуального веб-хостингу знадобилося призначати сотні IP на одну карту, розробники Linux створили механізм IP-аліасів (`eth0:0`, `eth0:1`), де кожен аліас реєструвався як окремий псевдо-пристрій з обмеженим функціоналом.
3. **Блокуючий характер завантаження**: Якщо утиліта налаштування чекала на відповідь віддаленого сервера або повільно ініціалізувала апаратний контролер, процес завантаження всієї операційної системи повністю зупинявся.

## Дистрибутивний розкол 1990-х: `ifupdown` проти `ifcfg-*`

Із бурхливим зростанням дистрибутивів GNU/Linux у 1990-х роках виникла гостра потреба стандартизувати декларативні описи мережевих інтерфейсів, звільнивши системних адміністраторів від ручного редагування імперативних shell-скриптів. Спільнота розділилася на два головні табори з різними філософіями конфігурації:

### 1. Debian та парадигма `ifupdown` (`/etc/network/interfaces`)

Наприкінці 1990-х років розробник Debian Ентоні Таунс (Anthony Towns) спроєктував комплекс утиліт `ifup` та `ifdown`. Головною інновацією стала централізація всієї мережевої конфігурації в єдиному декларативному файлі `/etc/network/interfaces`:

```
# /etc/network/interfaces
auto eth0
iface eth0 inet static
    address 192.168.1.10
    netmask 255.255.255.0
    gateway 192.168.1.1
    dns-nameservers 192.168.1.1

iface eth1 inet dhcp
```

`ifupdown` надав потужну систему хуків: директиви `pre-up`, `up`, `post-up`, `down` та `post-down` дозволяли виконувати довільні скрипти на кожному етапі життєвого циклу інтерфейсу (наприклад, піднімати правила фаєрволу iptables або запускати клієнт оновлення DNS).

Для відстеження стану `ifupdown` використовував текстовий файл стану `/run/network/ifstate` (або `/etc/network/run/ifstate`). Щоразу, коли адміністратор виконував `ifup eth0`, утиліта додавала рядок `eth0=eth0` до файлу. Це породжувало класичну проблему розсинхронізації: якщо інтерфейс змінював стан в обхід `ifup` (наприклад, через аварійне падіння драйвера або прямий виклик `ip link set eth0 down`), файл `ifstate` залишався у застарілому стані, і наступний виклик `ifup` відхилявся з повідомленням `ifup: interface eth0 already configured`, вимагаючи примусового прапорця `--force`.

### 2. Red Hat та екосистема `ifcfg-*` (`/etc/sysconfig/network-scripts/`)

Компанія Red Hat пішла шляхом розбиття конфігурації на окремі файли змінних оточення shell для кожного інтерфейсу (наприклад, `ifcfg-eth0`, `ifcfg-eth1`), що розміщувалися у каталозі `/etc/sysconfig/network-scripts/`:

```bash
# /etc/sysconfig/network-scripts/ifcfg-eth0
DEVICE=eth0
BOOTPROTO=static
IPADDR=192.168.1.10
NETMASK=255.255.255.0
GATEWAY=192.168.1.1
ONBOOT=yes
PEERDNS=yes
```

Ініціалізація виконувалася монолітним сервісним скриптом `/etc/rc.d/init.d/network`. Під час старту системи скрипт зчитував каталог, знаходив файли з директивою `ONBOOT=yes` і для кожного з них запускав допоміжний інтерпретований шелл-скрипт `ifup-eth`. Цей скрипт імпортував змінні через команду shell `source`, формував параметри командного рядка для `ifconfig` або викликав зовнішній демон DHCP (у різні часи це були `pump`, `dhcpcd` або ISC `dhclient`).

### Спільний тупик статичної моделі

Попри відмінності у форматі файлів, обидва підходи страждали на спільний системний недолік: вони були **синхронними, пакетними та сліпими до подій**. 

Скрипти ініціалізації розраховувалися на запуск у межах фіксованих рівнів виконання System V Init (Runlevels). Вони виходили з аксіоми, що всі фізичні пристрої вже виявлені ядром під час старту BIOS/PCI-шини до моменту виклику мережевого сервісу. Після того як `ifup` чи `/etc/init.d/network` завершували виконання, у системі не залишалося жодного наглядового фонового процесу. Будь-яка зміна фізичного стану мережі вимагала ручного втручання адміністратора з правами `root`.

## Заміна інструментарію: відмова від `net-tools` на користь `iproute2`

Паралельно з дистрибутивним розвитком назрівала криза на рівні низькорівневого мережевого стека ядра Linux. Набір утиліт `net-tools` (`ifconfig`, `route`, `arp`, `netstat`), успадкований від BSD, перестав відповідати можливостям підсистеми маршрутизації ядра.

У версіях ядра Linux 2.1 та 2.2 інженер Олексій Кузнєцов здійснив повну перебудову мережевого коду ядра, реалізувавши розширену маршрутизацію (Policy Routing), підтримку множинних таблиць маршрутизації, класифікатори трафіку (Traffic Control, `tc`) та повноцінне призначення кількох вторинних IP-адрес без використання застарілих аліасів.

Старий інтерфейс `ioctl()` не міг передавати складні структури даних нової підсистеми маршрутизації. Для вирішення цієї проблеми було створено протокол **Netlink** (`AF_NETLINK`, спеціалізоване сімейство `NETLINK_ROUTE` або `rtnetlink`) — асинхронний сокетний інтерфейс обміну бінарними повідомленнями формату TLV (Type-Length-Value) між простором користувача та ядром.

Разом із Netlink з'явився новий комплекс утиліт **`iproute2`** (команди `ip addr`, `ip route`, `ip link`, `ip rule`, `ip neigh`). Netlink дав простору користувача дві критичні можливості:
1. **Атомарне та безпечне маніпулювання параметрами**: Можливість додавати складні правила маршрутизації та атрибути інтерфейсів у єдиному системному виклику.
2. **Мультикаст-підписка на події ядра (`RTNLGRP_LINK`, `RTNLGRP_IPV4_IFADDR`)**: Процеси простору користувача вперше отримали здатність відкрити сокет Netlink і заблокуватися на системному виклику `poll()`/`epoll()`, миттєво прокидаючись при отриманні сповіщення від ядра про підключення кабелю (`RTM_NEWLINK`) або зміну адрес (`RTM_NEWADDR`).

Це створило технологічний фундамент для переходу від статичних скриптів до повноцінних подієвих демонів.

## Криза мобільності: PCMCIA, Wi-Fi та динамічне середовище

На початку 2000-х років комп'ютерна індустрія пережила вибухове зростання мобільних пристроїв: масового поширення набули ноутбуки, змінні мережеві карти шини PCMCIA (PC Card / CardBus), адаптери USB-to-Ethernet, стільникові модеми GPRS/EDGE та перші бездротові мережеві адаптери стандарту IEEE 802.11b/g (чипи Lucent Orinoco, Intersil Prism2, Atheros, Intel PRO/Wireless 2100/2200BG).

Стара статична модель мережевого керування зазнала цілковитого краху під тиском нових сценаріїв використання:

### 1. Асинхронне гаряче підключення (Hotplug)
Мережевий адаптер міг з'явитися або зникнути в системі у довільний момент після завантаження ОС, коли користувач вставляв карту PCMCIA у слот чи підключав USB-донгл. Скрипти `init.d` відпрацьовували один раз на старті машини і не могли знати про пристрої, які будуть підключені пізніше. Спроби зв'язати демон шини `cardmgr` або ранні скрипти ядра `/sbin/hotplug` із викликами `ifup` призводили до блокувань, взаємних блокувань процесів (deadlocks) та нестабільної ініціалізації драйверів.

### 2. Радіоефір і багаторівнева автентифікація
Бездротовий зв'язок принципово відрізнявся від провідного Ethernet:
* Потрібно було постійно сканувати радіоефір на наявність доступних точок доступу (BSSID/SSID).
* Якщо просте шифрування WEP налаштовувалося через розширення Wireless Extensions (`WEXT`) та утиліту `iwconfig`, то з появою стандарту безпеки WPA/WPA2 (IEEE 802.11i) виникла потреба у постійно працюючому процесі, здатному виконувати 4-етапне криптографічне рукостискання (4-Way Handshake), динамічно оновлювати групові ключі та підтримувати протоколи корпоративної автентифікації 802.1X EAP.
* У 2003 році фінський інженер Йоуні Малінен (Jouni Malinen) випустив **`wpa_supplicant`** — спеціалізований демон автентифікації Wi-Fi. Проте `wpa_supplicant` відповідав лише за рівень L2 (асоціація та шифрування) і не керував IP-адресами чи маршрутами, вимагаючи зовнішнього координатора.

### 3. Багатоінтерфейсні конфлікти та арбітраж маршрутів
Типовий мобільний користувач приходив з увімкненим ноутбуком на робоче місце:
1. Ноутбук уже мав активне з'єднання Wi-Fi через інтерфейс `wlan0` зі шлюзом за замовчуванням `192.168.1.1`.
2. Користувач підключав гігабітний провідний кабель Ethernet до порту `eth0`.
3. Клієнт DHCP на `eth0` отримував нову адресу та намагався встановити власний маршрут за замовчуванням `0.0.0.0/0 via 10.0.0.1`.
4. У системі виникав конфлікт двох маршрутів однакової вартості. Оскільки старі скрипти не вміли динамічно керувати метриками маршрутів ядра, вихідний трафік продовжував іти через повільний Wi-Fi або взагалі блокувався через асиметричну фільтрацію зворотного шляху (rp_filter).

### 4. Хаос скриптів-милиць ("Band-aids")
Спільнота намагалася врятувати ситуацію створенням спеціалізованих утиліт-демонів:
* **`ifplugd`**: Демон, що у нескінченному циклі опитував регістри мережевої карти через `ioctl(SIOCETHTOOL)` або `ioctl(SIOCGMIIREG)`, виявляв появу фізичного лінка на крученій парі та викликав `ifup eth0`.
* **`guessnet` / `whereami`**: Евристичні скрипти, які після підняття інтерфейсу розсилали тестові ARP-запити до шлюзів або сканували навколишні MAC-адреси, намагаючись вгадати поточне місце перебування ноутбука ("дім", "робота", "кафе") і підставити відповідний профіль із `/etc/network/interfaces`.
* **`wapproamd`**: Скрипт автоматичного перемикання між відкритими Wi-Fi мережами.

Ці інструменти погано взаємодіяли між собою, створювали нескінченні гонки процесів (race conditions), конкурували за перезапис файлу `/etc/resolv.conf` і вимагали від звичайного користувача глибоких знань консолі та постійного використання команди `sudo`.

## Народження NetworkManager (2004) та ера D-Bus

У 2004 році інженер компанії Red Hat Ден Вільямс (Dan Williams) у межах ініціативи створення дружнього графічного десктопу GNOME розпочав розробку проєкту **NetworkManager**.

Головна філософська ідея NetworkManager полягала у радикальній зміні принципу: **користувач не повинен вручну налаштовувати мережу — система повинна автоматично обирати найкраще доступне з'єднання та непомітно перемикатися між ними**.

```
┌─────────────────────────────────────────────────────────────┐
│ Графічний клієнт: GNOME Shell / nm-applet / KDE Plasma NM   │
└──────────────────────────────┬──────────────────────────────┘
                               │ D-Bus (org.freedesktop.NetworkManager)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                     NetworkManager                          │
│ ┌──────────────────────┐ ┌────────────────────────────────┐ │
│ │ State Machine        │ │ Connection Profiles (.nmconn)  │ │
│ └──────────┬───────────┘ └────────────────┬───────────────┘ │
│            │                              │                 │
│            ▼                              ▼                 │
│  Polkit (авторизація)        D-Bus / Netlink                │
└────────────┬──────────────────────────────┬─────────────────┘
             │                              │
     ┌───────┴────────┐            ┌────────┴────────┐
     ▼                ▼            ▼                 ▼
wpa_supplicant   ModemManager    udev (uevent)    Ядро Linux (rtnetlink)
(Wi-Fi / 802.1X) (4G/LTE / 5G)   (Hotplug адаптери) (IP, маршрути, лінк)
```

NetworkManager об'єднав ключові технології оновленого системного простору Linux:

### 1. Централізований скінченний автомат стану (State Machine)
NetworkManager перетворився на повнофункціональний системний демон, що працює у фоновому режимі з привілеями `root`. Він постійно утримує в оперативній пам'яті граф стану всіх мережевих пристроїв системи та автоматично реагує на будь-які зовнішні фактори: падіння рівня сигналу Wi-Fi, появу кабелю в гнізді чи активацію VPN.

### 2. Інтеграція з підсистемами обладнання (HAL та udev)
Демон підключився до шини виявлення обладнання — спочатку через демон `HAL` (Hardware Abstraction Layer), а після його ліквідації — напряму через сокети ядра `uevent` бібліотеки `libudev`. Щойно користувач підключав новий USB-адаптер, NetworkManager миттєво реєстрував пристрій без необхідності перезапуску сервісів.

### 3. Системна шина D-Bus та поділ привілеїв (Polkit)
NetworkManager відкрив публічне об'єктно-орієнтоване API на системній шині D-Bus під адресою `org.freedesktop.NetworkManager`. 
Це дозволило графічним середовищам (GNOME `nm-applet`, KDE Plasma NM, пізніше консольним утилітам `nmcli` та `nmtui`) відображати статус з'єднань, сканувати доступні Wi-Fi мережі у реальному часі та запитувати паролі у користувача через діалогові вікна.

Завдяки інтеграції з фреймворком авторизації **Polkit** (колишній PolicyKit), звичайний користувач графічної сесії отримав право перемикати мережеві профілі, вводити ключі WPA або запускати мобільний інтернет без отримання повних прав `root` і без запуску графічних програм з-під `sudo`.

### 4. Розмежування сутностей Device та Connection
NetworkManager запровадив чітке розділення абстракцій:
* **Device (Пристрій)**: Фізичний контролер або віртуальний мережевий інтерфейс ядра (наприклад, `wlan0`, `eth0`).
* **Connection (Профіль з'єднання)**: Набір конфігураційних параметрів (SSID, пароль WPA-PSK, статична адреса або DHCP, DNS, метрика маршруту), збережений на диску у форматі Keyfile (`/etc/NetworkManager/system-connections/*.nmconnection`).

Один фізичний адаптер `wlan0` міг динамічно зв'язуватися з сотнями різних збережених профілів залежно від поточної географічної локації. Демон самостійно розраховував пріоритети підключень (`autoconnect-priority`): наприклад, при одночасній наявності Ethernet та Wi-Fi демон автоматично присвоював провідному з'єднанню меншу числову метрику маршруту (вищий пріоритет), спрямовуючи основний трафік через швидкий канал без розриву активних з'єднань.

### 5. Оркестрація зовнішніх протокольних демонів
NetworkManager перестав дублювати низькорівневу логіку спеціалізованих протоколів. Він узяв на себе роль координатора:
* Керував демоном `wpa_supplicant` через D-Bus API, передаючи йому команди на сканування ефіру та асоціацію. З появою підсистеми ядра `nl80211` / `cfg80211` NetworkManager перевів Wi-Fi на сучасний стек, відмовившись від застарілих викликів `WEXT`.
* Інтегрував сервіс **`ModemManager`** для автоматизованої роботи з USB-модемами 3G/LTE/5G через протоколи AT, QMI та MBIM.
* Запровадив модульну систему VPN-плагінів (OpenVPN, WireGuard, StrongSwan, Cisco AnyConnect), які запускалися як ізольовані помічники за вимогою.

До кінця 2000-х років NetworkManager став фактичним стандартом для всіх настільних та мобільних дистрибутивів Linux (Fedora, Ubuntu Desktop, openSUSE, Debian Desktop).

## Серверна криза, контейнеризація та народження `systemd-networkd` (2014)

Попри тріумф NetworkManager на персональних комп'ютерах, його впровадження у серверних дата-центрах та хмарній інфраструктурі натрапило на жорсткий спротив системних адміністраторів та архітекторів високопродуктивних систем.

### Чому NetworkManager виявився непридатним для хмарних серверів

1. **Важкий стек залежностей і накладні витрати пам'яті**:
   NetworkManager створювався як частина екосистеми GNOME і спирався на бібліотеки `GLib`, `GObject`, `GIO`, систему авторизації `polkit` та шину `dbus-daemon`. Постійне споживання пам'яті на рівні 40–70 МБ (Resident Set Size, RSS) було неприпустимим марнотратством для легковажних віртуальних машин хмарних провайдерів (з 256–512 МБ RAM) та вбудованих роутерів.
2. **Невідповідність парадигми**:
   Десктопна модель NetworkManager розраховувалася на інтерактивне людське керування, автоматичне сканування радіоефіру та евристичне перемикання підключень. Серверам була потрібна суворо детермінована, безголова (headless) та декларативна модель: стан мережі мав бути зафіксований у конфігураційних файлах репозиторію без жодних спроб демона "самовільно" змінити маршрути чи надіслати запити до невідомих сервісів.
3. **Вибух контейнеризації та програмно-конфігурованих мереж (SDN)**:
   З появою технологій віртуалізації (KVM, OpenStack) та контейнеризації (LXC, systemd-nspawn, Docker, Kubernetes) топологія мережі на хості перестала бути статичною. Один сервер почав динамічно створювати та видаляти тисячі віртуальних мережевих об'єктів: пари віртуальних кабелів `veth`, програмні комутатори Linux Bridge, агрегації Bonding/Team, віртуальні локальні мережі VLAN (802.1Q), оверлейні тунелі VXLAN та криптографічні інтерфейси WireGuard.
   Коли NetworkManager бачив появу нового віртуального інтерфейсу `veth`, він намагався ініціалізувати для нього D-Bus об'єкт, зчитати системні правила та застосувати автоконфігурацію. Це спричиняло шторм повідомлень D-Bus, надмірне завантаження CPU та затримки у кілька секунд при старті кожного окремого контейнера.

### Поява `systemd-networkd` (2014)

У 2014 році норвезький інженер Том Гундерсен (Tom Gundersen) за підтримки команди розробників systemd представив **`systemd-networkd`**.

`systemd-networkd` спроєктували як спеціалізований інфраструктурний сервіс ядра операційної системи, позбавлений будь-яких графічних або інтерактивних рудиментів:

```
┌─────────────────────────────────────────────────────────────┐
│                      systemd-networkd                       │
│ ┌─────────────────────────────────────────────────────────┐ │
│ │ sd-event (асинхронний цикл обробки epoll)               │ │
│ ├─────────────────────────────────────────────────────────┤ │
│ │ sd-netlink (прямий бінарний зв'язок із ядром Linux)     │ │
│ ├─────────────────────────────────────────────────────────┤ │
│ │ Вбудований sd-dhcp-client / SLAAC / LLDP Engine         │ │
│ └────────────────────────────┬────────────────────────────┘ │
└──────────────────────────────┼──────────────────────────────┘
                               │ Netlink (RTM_NEWLINK / RTM_NEWADDR)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                         Ядро Linux                          │
│ ┌───────────────┐ ┌───────────────┐ ┌─────────────────────┐ │
│ │ Фізичні NICs  │ │ Мости br0     │ │ Контейнерні veth    │ │
│ └───────────────┘ └───────────────┘ └─────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

Ключові архітектурні принципи `systemd-networkd`:
* **Нуль залежностей від D-Bus для базової конфігурації**: Демон не використовує сторонніх шин IPC для налаштування адрес та маршрутів. Уся взаємодія з ядром реалізована через внутрішню асинхронну бібліотеку `sd-netlink` та високопродуктивний цикл подій `sd-event` на базі `epoll`.
* **Вбудовані мікросервіси замість зовнішніх процесів**: `systemd-networkd` відмовився від виклику зовнішніх процесів ISC `dhclient` або `dhcpcd`. Демон містить компактну власну бібліотеку `sd-dhcp-client` (для DHCPv4, DHCPv6 та IPv6 SLAAC), реалізацію Link-Local (IPv4LL RFC 3927) та слухача протоколу виявлення сусідів LLDP. Застосування параметрів адресації відбувається без системних викликів `fork()` та `execve()`, займаючи лічені мікросекунди.
* **Декларативні юніти `.network` та `.netdev`**: Конфігурація спирається на чіткий текстовий синтаксис юнітів systemd. Файли `.netdev` описують створення віртуальних пристроїв ядром (мости, бонди, тунелі), а файли `.network` визначають правила їхнього налаштування через гнучкі селектори секції `[Match]` (зіставлення за MAC-адресою, назвою драйвера, топологічним шляхом шини PCI або типом віртуалізації).
* **Екстремальна швидкодія та низький footprint**: Демон споживає менше 5–10 МБ оперативної пам'яті та здатний ініціалізувати сотні мережевих просторів імен (Network Namespaces) для мікросервісів Kubernetes за одиниці мілісекунд.

## Еволюція абстракцій конфігурації: Netplan та уніфікація

До середини 2010-х років екосистема Linux зіткнулася з проблемою фрагментації форматів конфігурації:
* Сервери Debian продовжували використовувати застарілий `/etc/network/interfaces`.
* Дистрибутиви сімейства Red Hat Enterprise Linux переходили від файлів `ifcfg-*` до нативних файлів NetworkManager.
* Хмарні інстанси та контейнерні хости впроваджували `systemd-networkd` (`/etc/systemd/network/`).
* Настільні робочі станції працювали під контролем NetworkManager (`.nmconnection`).

Для засобів автоматизації розгортання інфраструктури (наприклад, `cloud-init`, Ansible, Terraform) ця строкатость означала необхідність підтримувати чотири різні шаблонізатори конфігураційних файлів для кожного дистрибутиву окремо.

### Створення Netplan (2016)

У 2016 році інженерна команда Canonical на чолі з Мартіном Піттом (Martin Pitt) представила проєкт **Netplan** (первинно інтегрований у Ubuntu 16.10, а з випуску Ubuntu 18.04 LTS затверджений як стандартний мережевий інтерфейс за замовчуванням).

Netplan запропонував фундаментально інший підхід: **замість створення ще одного конкуруючого мережевого демона, створити єдиний декларативний фронтенд (генератор), що транслює стандартизований YAML-опис у нативні конфігурації існуючих бекендів**.

```
                       ┌─────────────────────────┐
                       │ /etc/netplan/*.yaml     │
                       │ (Єдиний YAML-опис)      │
                       └────────────┬────────────┘
                                    │
                                    ▼
                       ┌─────────────────────────┐
                       │    Генератор Netplan    │
                       │  (netplan generate)     │
                       └────────────┬────────────┘
                                    │
            ┌───────────────────────┴───────────────────────┐
            │ (renderer: networkd)                          │ (renderer: NetworkManager)
            ▼                                               ▼
┌───────────────────────────────┐             ┌───────────────────────────────┐
│ /run/systemd/network/*.network│             │ /run/NetworkManager/system-   │
│ (Конфігурація systemd)        │             │  connections/*.nmconnection   │
└───────────────┬───────────────┘             └───────────────┬───────────────┘
                ▼                                             ▼
┌───────────────────────────────┐             ┌───────────────────────────────┐
│       systemd-networkd        │             │        NetworkManager         │
└───────────────────────────────┘             └───────────────────────────────┘
```

Архітектура Netplan базується на кількох принципах:
1. **Єдиний синтаксис YAML**: Усі мережеві інтерфейси (фізичні Ethernet, Wi-Fi точки доступу, мости `bridges`, агрегації `bonds`, `vlans`, тунелі та статичні маршрути) описуються у каталозі `/etc/netplan/*.yaml` за єдиною структурованою схемою.
2. **Генерація конфігурацій під час завантаження (Offline Generator)**: Netplan не є постійно працюючим демоном і не споживає оперативної пам'яті. На ранньому етапі ініціалізації системи генератор Netplan компілює YAML-файли у тимчасовий каталог періоду виконання `/run/` для обраного рушія (`renderer`):
   * `renderer: networkd` — генерує файли `.network` та `.netdev` у каталозі `/run/systemd/network/` для подальшої обробки демоном `systemd-networkd`.
   * `renderer: NetworkManager` — формує keyfile-профілі у каталозі `/run/NetworkManager/system-connections/` для підсистеми `NetworkManager`.
3. **Безшовне перемикання та валідація**: Команда `netplan apply` генерує нові файли конфігурації та надсилає команду перезавантаження обраному бекенду через D-Bus або Netlink. Команда `netplan try` реалізує безпечний механізм відкату: якщо після застосування нових налаштувань мережевий зв'язок втрачено і адміністратор не підтвердив зміни за визначений таймаут, Netplan автоматично повертає попередню робочу конфігурацію.

Це дозволило хмарним системам ініціалізації (`cloud-init`) записувати єдиний універсальний YAML-файл, який на безголових серверах автоматично обслуговується легковажним `systemd-networkd`, а на графічних робочих станціях передається під керування `NetworkManager` зі збереженням доступу користувача до аплетів трею.

## Підсумок: еволюційне дерево мережевого контролю Linux

Еволюція конфігурації мережі в Unix-подібних системах пройшла повне коло розвитку, відображаючи зміну апаратних пріоритетів та інженерних вимог часу:

```
[1980-ті: Статичні сервери]
  └─► Лінійні шелл-скрипти (/etc/rc, ifconfig, route)
        └─► Низькорівневий ioctl (SIOCSIFADDR), монолітна фіксація в пам'яті

[1990-ті: Перша хвиля дистрибутивів GNU/Linux]
  └─► Пакетні дистрибутивні менеджери (ifupdown у Debian, ifcfg-* у Red Hat)
        └─► Розрив із ядром: поява протоколу Netlink та комплексу iproute2
        └─► Тупик: відсутність наглядових демонів і сліпота до подій лінії

[2000-ні: Мобільна криза та поява ноутбуків]
  └─► Подієві користувацькі менеджери (NetworkManager, 2004)
        └─► Інтеграція з D-Bus, udev/HAL, Polkit, wpa_supplicant
        └─► Розділення сутностей Device та Connection Profile

[2010-ті: Хмарна революція та контейнеризація]
  └─► Легковажні системні демони (systemd-networkd, 2014)
        └─► Відмова від D-Bus, перехід на прямий асинхронний sd-netlink/sd-event
        └─► Вбудований DHCP-клієнт, мікросекундний старт віртуальних інтерфейсів

[2016+: Хмарна стандартизація]
  └─► Декларативні генератори конфігурацій (Canonical Netplan, 2016)
        └─► Єдиний опис YAML із динамічною трансляцією у networkd або NetworkManager
```

Сьогодні в інфраструктурі Linux закріпився чіткий та збалансований інженерний розподіл ролей:
* **`NetworkManager`** домінує на десктопах, ноутбуках та мобільних шлюзах, де критично важливі інтерактивна зміна радіомереж Wi-Fi, робота зі стільниковими модемами, графічні аплети та інтеграція з VPN-клієнтами.
* **`systemd-networkd`** є де-факто стандартом для хмарних гіпервізорів, серверів баз даних, високонавантажених маршрутизаторів та контейнерних хостів, де потрібні максимальна швидкість, мінімальний оверхед оперативної пам'яті та нативна підтримка складних віртуальних топологій (VLAN, мости, bonding, VXLAN).
* **`Netplan`** забезпечує уніфікований декларативний шар поверх обох підсистем, дозволяючи системам оркестрації та адміністраторам керувати будь-яким хостом за допомогою єдиного стандарту.
