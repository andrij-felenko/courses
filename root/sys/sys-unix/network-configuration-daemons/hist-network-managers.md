# 📜 Від статичних rc-скриптів до подієвих менеджерів: історія конфігурації мережі в Unix

Ця історична довідка розкриває інженерні причини, через які класичні статичні шелл-скрипти ініціалізації виявилися непридатними для динамічного мережевого середовища, та показує еволюцію підсистем керування мережею від перших реалізацій BSD UNIX до сучасних демонів NetworkManager і systemd-networkd.

## Епоха стаціонарних серверів: скрипти `rc` та фіксовані інтерфейси

На світанку розвитку BSD UNIX та перших випусків комерційних операційних систем Unix (SunOS, IRIX, HP-UX) на початку 1980-х років мережева топологія комп'ютерних систем вважалася абсолютно статичною. Сервери та робочі станції представляли собою масивні стаціонарні машини, фізично підключені товстим коаксіальним кабелем 10BASE5 або крученою парою 10BASE-T до єдиного сегмента локальної мережі. Мережева карта Ethernet інсталювалася у слот розширення шини VMEbus, SBus або ISA один раз на весь життєвий цикл обладнання.

У такій парадигмі конфігурація мережі була тривіальною лінійною процедурою, що виконувалася один раз на етапі завантаження операційної системи. Скрипт `/etc/rc` (пізніше розбитий у BSD на модульний `/etc/rc.conf` та у System V на рівні виконання `init.d`) послідовно викликав системні утиліти `ifconfig` та `route`:

```bash
# Типова ініціалізація мережі в ранніх Unix-системах
ifconfig le0 inet 192.168.1.10 netmask 255.255.255.0 up
route add default 192.168.1.1
```

Скрипт відпрацьовував до кінця і завершував процес. Ядро операційної системи утримувало призначені IP-адреси та таблицю маршрутизації в оперативній пам'яті до наступного перезавантаження або вимкнення живлення. Якщо кабель виймали з гнізда, лінк падав, проте адреси та маршрути залишалися незмінними.

## Поява дистрибутивних стандартів: `ifupdown` та `ifcfg-*`

У 1990-х роках, із бурхливим зростанням дистрибутивів GNU/Linux, виникла потреба стандартизувати декларативні описи інтерфейсів для системних адміністраторів. Дистрибутиви розділилися на два головні табори за підходом до конфігурації:

1. **Debian та сімейство `ifupdown` (`/etc/network/interfaces`)**:
   Ентоні Таунс (Anthony Towns) наприкінці 1990-х років спроєктував комплекс утиліт `ifup` та `ifdown`. Файл `/etc/network/interfaces` описував як статичні інтерфейси, так і запуск зовнішнього клієнта DHCP для динамічного отримання параметрів.
2. **Red Hat та скрипти `ifcfg-*` (`/etc/sysconfig/network-scripts/`)**:
   Підхід базувався на множині окремих файлів змінних оточення (наприклад, `ifcfg-eth0`), які інтерпретувалися масивними скриптами `/etc/init.d/network`.

Обидві системи мали спільний фундаментальний недолік: вони були **синхронними та пакетними**. Утиліта `ifup` зчитувала файл, перевіряла наявність інтерфейсу в системі, конфігурувала його через `ioctl(SIOCSIFADDR)` або ранній `rtnetlink` і завершувала роботу. Жодного фонового процесу, який би відстежував фізичний стан лінії зв'язку після завершення `ifup`, у системі не залишалося.

## Криза мобільності: PCMCIA, Wi-Fi та динамічне середовище

На межі 2000-х років масового поширення набули ноутбуки та змінні мережеві карти шини PCMCIA (PC Card / CardBus), а трохи згодом — USB-модеми та перші бездротові адаптери стандарту IEEE 802.11b (Wi-Fi). 

Статична модель остаточно заблокувала зручне використання операційної системи:

* **Гаряче підключення (Hotplug)**: Мережевий адаптер міг з'явитися в системі в довільний момент після завантаження ОС. Скрипти ініціалізації на базі `init` запускалися задовго до того, як користувач вставляв карту.
* **Зміна радіоефіру**: Ноутбук переміщувався між домом, офісом та публічними кафе. Кожна нова локація вимагала підключення до іншого SSID, проходження автентифікації WEP/WPA через `wpa_supplicant`, отримання нової IP-адреси через DHCP та оновлення DNS.
* **Багатоінтерфейсні конфлікти**: Коли користувач підключав кабель Ethernet на робочому місці, система повинна була автоматично перемкнути маршрут за замовчуванням з повільного Wi-Fi на гігабітний провідний інтерфейс без розриву активних TCP-сесій та без втручання суперкористувача через `sudo route`.

Спроби вирішити це скриптами розпізнавання оточення (такими як `whereami`, `guessnet`, `ifplugd`) були ненадійними "костилями", які опитували стан обладнання за таймером у нескінченному циклі.

## Народження NetworkManager (2004)

У 2004 році інженер компанії Red Hat Ден Вільямс (Dan Williams) розпочав розробку проєкту **NetworkManager**. Головною ідеєю проєкту стало створення повноцінного централізованого демона простору користувача, який бере на себе абсолютний контроль над мережевими інтерфейсами та діє за подієвою моделлю.

NetworkManager об'єднав декілька ключових технологій нової екосистеми Linux:

* **udev та HAL (Hardware Abstraction Layer)** для миттєвого виявлення появи мережевих пристроїв у системі через події ядра `uevent`.
* **D-Bus** як системну шину міжпроцесної взаємодії. NetworkManager надав публічне API через D-Bus, завдяки чому графічні оточення (GNOME Control Center, аплети панелей завдань) змогли відображати список доступних Wi-Fi мереж, запитувати паролі у користувача в реальному часі та перемикати профілі без привілеїв `root` (завдяки інтеграції з Polkit).
* **Подієвий цикл Netlink**: демон відкрив постійний сокет `NETLINK_ROUTE` і підписався на мультикаст-повідомлення ядра про зміну стану лінка (`RTM_NEWLINK`).

NetworkManager розділив сутності "фізичний пристрій" (Device) та "налаштування підключення" (Connection Profile). Один і той самий адаптер `wlan0` міг автоматично застосовувати різні профілі залежно від того, яку саме бездротову точку виявив сканер радіоефіру.

## Хмарна революція та народження systemd-networkd (2014)

До 2010 року NetworkManager став абсолютним стандартом для настільних Linux-систем, але на серверах та у хмарній інфраструктурі виникли нові виклики. Почалася епоха віртуалізації (KVM, Xen), гіпервізорів та контейнеризації (LXC, systemd-nspawn, а згодом Docker та Kubernetes).

У великих дата-центрах та контейнерних хостах NetworkManager виявився надлишковим:
1. Залежність від шини D-Bus, бібліотек GLib/GIO та демона `polkit` створювала відчутний оверхед пам'яті (десятки мегабайтів на екземпляр), що було неприпустимо для легковагих контейнерів.
2. Серверам не потрібне динамічне перемикання Wi-Fi та опитування стільникових модемів. Натомість потрібна миттєва (за мілісекунди) ініціалізація тисяч віртуальних мережевих інтерфейсів — пар `veth`, мостів Linux Bridge, агрегацій Bonding/Team, тунелів VXLAN та VLAN-тегів.

У 2014 році Том Гундерсен (Tom Gundersen) за підтримки команди розробників systemd представив **systemd-networkd**. 

`systemd-networkd` став відповіддю на вимоги хмарної інфраструктури:
* Повна відмова від зовнішніх важких бібліотек на користь власної асинхронної бібліотеки `sd-netlink` та циклу подій `sd-event`.
* Декларативний синтаксис файлів `.network` та `.netdev` за зразком юнітів systemd.
* Інтеграція власного внутрішнього клієнта DHCPv4, DHCPv6 та SLAAC без необхідності форкати сторонні процеси на зразок ISC `dhclient`.
* Швидкість виконання: демон обробляє стан сотень віртуальних інтерфейсів та піднімає мережу за одиниці мілісекунд при старті контейнера.

## Сучасний баланс

Еволюція конфігурації мережі в Unix пройшла повне коло: від простих статичних скриптів через складні, багатофункціональні десктопні демони (NetworkManager) до високоефективних, декларативних інфраструктурних сервісів ядра системи (systemd-networkd). Сьогодні обидва інструменти гармонійно співіснують, закриваючи два кардинально різних класи завдань: динамічну клієнтську мобільність та масштабовану серверну автоматизацію.
