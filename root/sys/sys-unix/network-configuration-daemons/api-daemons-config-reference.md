# 📋 Довідник конфігурацій: декларативні профілі systemd-networkd та NetworkManager

Цей довідник містить вичерпний опис структури конфігураційних файлів, правила зіставлення інтерфейсів, інваріанти секцій і директив для підсистем `systemd-networkd` (формати `.network` і `.netdev`) та `NetworkManager` (формат `keyfile`), а також правила обробки помилок і пріоритетів завантаження.

## 1. Декларативна модель `systemd-networkd`

Підсистема `systemd-networkd` розбирає конфігураційні файли на етапі запуску демона та динамічно при отриманні подій ядра `RTM_NEWLINK` через сокет Netlink. Конфігурація складається з двох типів файлів: `.netdev` (створення віртуальних пристроїв) та `.network` (налаштування параметрів L2/L3 для фізичних і віртуальних інтерфейсів).

### Ієрархія розташування та правила нашарування

Файли конфігурації зчитуються з трьох системних каталогів у строгому порядку пріоритету:

1. `/etc/systemd/network/` — конфігурація локального системного адміністратора (найвищий пріоритет).
2. `/run/systemd/network/` — тимчасова конфігурація періоду виконання (runtime), що генерується хмарними агентами або генераторами ініціалізації initramfs.
3. `/usr/lib/systemd/network/` — стандартні шаблони від розробників операційної системи та дистрибутивів (найнижчий пріоритет).

Файли сортуються за лексикографічним порядком їхніх базових імен незалежно від каталогу розташування. Якщо у каталозі `/etc/systemd/network/` існує файл з точно таким самим ім'ям, як у `/usr/lib/systemd/network/` (наприклад, `99-default.network`), системний файл повністю заміщує дистрибутивний. Для повного відключення дистрибутивного конфігураційного файлу адміністратор створює символічне посилання на `/dev/null` у каталозі `/etc/systemd/network/`.

Крім повної заміни, підтримується механізм конфігураційних фрагментів (drop-in directories). Якщо поряд із файлом `10-eth0.network` створити каталог `10-eth0.network.d/`, усі файли з розширенням `.conf` усередині нього будуть розібрані в алфавітному порядку та доповнять або перекриють окремі директиви головного файлу.

### Логіка зіставлення секції `[Match]`

Коли ядро реєструє новий мережевий інтерфейс, `systemd-networkd` послідовно перевіряє всі доступні `.network` файли в алфавітному порядку. Перший файл, чия секція `[Match]` успішно узгоджується з характеристиками пристрою, застосовується до нього, а подальший пошук припиняється.

Усі директиви всередині однієї секції `[Match]` поєднуються за правилом логічного "І" (AND): пристрій повинен задовольняти кожен із зазначених критеріїв. Якщо окрема директива містить список значень, розділених пробілами (наприклад, `Name=eth0 enp3s0`), ці значення об'єднуються за правилом логічного "АБО" (OR).

| Директива | Тип значення | Опис та правила валідації |
|---|---|---|
| `Name=` | Рядок / Glob-шаблон | Ім'я інтерфейсу (`enp3s0`, `eth*`, `wlan?`, `!lo`). Підтримує заперечення через знак оклику. |
| `MACAddress=` | MAC-адреса | Апаратна адреса канального рівня (`52:54:00:12:34:56`). Дозволяє прив'язати налаштування до конкретного фізичного порту незалежно від зміни його імені ядром. |
| `Driver=` | Рядок / Glob-шаблон | Назва драйвера ядра, що обслуговує пристрій (`e1000e`, `virtio_net`, `r8169`, `iwlwifi`). |
| `Type=` | Рядок | Тип обладнання відповідно до класифікації ядра (`ether`, `wlan`, `bridge`, `bond`, `vlan`, `wireguard`, `loopback`). |
| `Path=` | Рядок / Glob-шаблон | Топологічний шлях пристрою на системній шині (`pci-0000:00:1f.6-*`). Гарантує стабільність для фіксованих слотів материнської плати. |
| `Host=` | Рядок | Мережеве ім'я машини (hostname). Застосовується для спільних образів дисків, що використовуються різними хостами. |
| `Virtualization=` | Рядок | Перевірка виконання у віртуальному середовищі (`yes`, `no`, `kvm`, `qemu`, `container`, `systemd-nspawn`, `vmware`). |

### Секція `[Network]` та параметри адресації

Секція `[Network]` визначає основний мережевий профіль пристрою: режим отримання IP-адрес, увімкнення вбудованого DHCP-клієнта, статичну маршрутизацію та членство у віртуальних мостах.

| Директива | Тип значення | Поведінка та вплив на стек ядра |
|---|---|---|
| `DHCP=` | `yes`, `no`, `ipv4`, `ipv6` | Активує внутрішній клієнт DHCP. Значення `yes` запускає одночасно DHCPv4 та IPv6 SLAAC/DHCPv6. За замовчуванням `no`. |
| `Address=` | IPv4/IPv6 у форматі CIDR | Статична IP-адреса інтерфейсу (`192.168.1.50/24`, `2001:db8::10/64`). Може зазначатися багаторазово для призначення кількох адрес одному інтерфейсу. |
| `Gateway=` | IP-адреса | Адреса шлюзу за замовчуванням (`192.168.1.1`). Демон автоматично створює маршрут `0.0.0.0/0` або `::/0` через цей шлюз. |
| `DNS=` | Список IP-адрес | Адреси DNS-серверів (`1.1.1.1 8.8.8.8`). Демон передає ці адреси сервісу `systemd-resolved` через IPC-канал. |
| `Domains=` | Список доменів | Домени пошуку та суфікси маршрутизації DNS. Префікс `~` позначає пріоритетний домен маршрутизації (Split DNS). |
| `NTP=` | Список адрес/хостів | Адреси серверів протоколу синхронізації часу NTP (передаються у `systemd-timesyncd`). |
| `IPv6AcceptRA=` | `yes`, `no` | Управління прийомом пакетів ICMPv6 Router Advertisement для безстанової автоконфігурації (SLAAC). |
| `Bridge=` | Рядок | Прив'язує поточний інтерфейс як підлеглий порт (slave) до зазначеного віртуального моста. |
| `Bond=` | Рядок | Додає поточний інтерфейс до складу агрегованої групи каналів (Bonding interface). |
| `VLAN=` | Список рядків | Імена віртуальних інтерфейсів VLAN, які ядро повинно створити та прив'язати поверх цього базового пристрою. |
| `IPForward=` | `yes`, `no`, `ipv4`, `ipv6` | Дозволяє маршрутизацію транзитного трафіку між інтерфейсами (встановлює `sysctl net.ipv4.conf.<dev>.forwarding=1`). |
| `LinkLocalAddressing=` | `yes`, `no`, `ipv4`, `ipv6` | Управління генерацією локальних адрес каналу (IPv4 Link-Local `169.254.0.0/16` згідно з RFC 3927 або IPv6 `fe80::/10`). |

### Секції тонкого тюнінгу статичної адресації та маршрутів

Коли статична адреса вимагає спеціальних прапорців (термін валідності, peer-адреса для з'єднань точка-точка або специфічний broadcast), замість директиви `Address=` у секції `[Network]` використовується виокремлена секція `[Address]`:

```ini
[Address]
Address=10.0.0.15/24
Peer=10.0.0.1/32
Broadcast=10.0.0.255
Scope=global
PreferredLifetime=86400
```

Секція `[Route]` керує налаштуванням статичних маршрутів та правил багатотабличної маршрутизації ядра (Policy Routing):

| Директива | Тип значення | Опис |
|---|---|---|
| `Destination=` | CIDR-нотація | Мережа призначення (`10.200.0.0/16` або `0.0.0.0/0` для маршруту за замовчуванням). |
| `Gateway=` | IP-адреса | Адреса наступного вузла передачі пакетів (Next Hop). |
| `GatewayOnLink=` | `yes`, `no` | Дозволяє маршрутизацію через шлюз, який не входить безпосередньо у локальну підмережу інтерфейсу. |
| `Metric=` / `Priority=` | Ціле додатне число | Числове значення метрики маршруту ядра (маршрути з меншим числом обираються ядром першими). |
| `Table=` | Ціле число або рядок | Номер таблиці маршрутизації ядра Linux (від 1 до 4294967295) для розділення потоків трафіку. |
| `Scope=` | `global`, `link`, `host` | Рівень досяжності маршруту в мережевому стеку. |

### Секція `[DHCPv4]` — поведінка клієнта протоколу DHCP

Секція `[DHCPv4]` регулює інтерпретацію опцій, отриманих від DHCP-сервера під час процедури DORA:

```ini
[DHCPv4]
ClientIdentifier=mac
UseDNS=yes
UseRoutes=yes
UseGateway=yes
RouteMetric=1024
SendHostname=yes
Hostname=node-cloud-01
RequestOptions=1 3 6 12 15 28 42
```

* `ClientIdentifier=`: Визначає формат передачі Option 61. Значення `mac` передає апаратну адресу мережевої карти, що є стандартом для більшості фізичних мереж, тоді як `duid` використовує RFC 4361 ідентифікатор клієнта.
* `UseDNS=`: При значенні `no` ігнорує Option 6 від сервера, запобігаючи несанкціонованій підміні системних DNS-серверів.
* `UseRoutes=`: Керує обробкою статичних маршрутів безкласової маршрутизації (DHCP Option 121 / 249).
* `RouteMetric=`: Примусово встановлює метрику для динамічно створеного маршруту за замовчуванням, що дозволяє підтримувати кілька активних інтерфейсів із різними пріоритетами.

### Створення віртуальних пристроїв (`.netdev`)

Файли `.netdev` зчитуються та виконуються демоном `systemd-networkd` на найпершому етапі ініціалізації, ще до обробки `.network` файлів. Демон надсилає в ядро повідомлення Netlink `RTM_NEWLINK` із прапорцем `NLM_F_CREATE`, вказуючи тип потрібного віртуального модуля драйвера.

```ini
[NetDev]
Name=br0
Kind=bridge
MTUBytes=1500
MACAddress=52:54:00:aa:bb:cc
```

Підтримувані типи пристроїв (`Kind=`): `bridge` (мережевий міст L2), `bond` (агрегація каналів LACP/RR), `vlan` (тегування 802.1Q), `vxlan` (інкапсуляція L2 поверх UDP), `wireguard` (захищений криптографічний тунель), `veth` (парний віртуальний кабель для контейнерів), `dummy` (фіктивний пристрій для маршрутизації), `macvlan`, `macvtap`, `tun`, `tap`.

:::tabs
```ini
# /etc/systemd/network/20-bond0.netdev
[NetDev]
Name=bond0
Kind=bond

[Bond]
Mode=802.3ad
MIIMonitorSec=100ms
LACPTransmitRate=fast
TransmitHashPolicy=layer2+3
```
```ini
# /etc/systemd/network/30-vlan100.netdev
[NetDev]
Name=vlan100
Kind=vlan

[VLAN]
Id=100
```
```ini
# /etc/systemd/network/50-wg0.netdev
[NetDev]
Name=wg0
Kind=wireguard

[WireGuard]
PrivateKeyFile=/etc/wireguard/private.key
ListenPort=51820

[WireGuardPeer]
PublicKey=cmlhbHNlY3VyZXB1YmxpY2tleWZvcndpcmVndWFyZA==
Endpoint=198.51.100.1:51820
AllowedIPs=10.100.0.0/24
PersistentKeepalive=25
```
:::

## 2. Специфікація конфігурацій NetworkManager (Keyfile)

Формат конфігураційних файлів `NetworkManager` базується на стандарті INI/Keyfile (специфікація бібліотеки GKeyFile). Системні з'єднання зберігаються у каталозі:
`/etc/NetworkManager/system-connections/<назва-профілю>.nmconnection`

Кожен файл у цьому каталозі повинен мати права доступу `0600` (читання/запис виключно для власника) та належати суперкористувачу `root:root`. Якщо права встановлені некоректно, NetworkManager відхиляє завантаження файлу з міркувань безпеки, оскільки конфігурація може містити незашифровані ключі доступу до Wi-Fi та облікові дані VPN.

### Архітектурний поділ на секції

Конфігураційний файл розділений на функціональні секції, які відповідають структурі D-Bus об'єктів підсистеми:

1. `[connection]` — загальні системні метадані профілю (UUID, назва, автопідключення, тип середовища).
2. `[ethernet]` або `[wifi]` — специфічні параметри канального рівня L2 (MAC-адреси, SSID, режими узгодження).
3. `[wifi-security]` — параметри автентифікації та шифрування (WPA-PSK, SAE, 802.1X Enterprise).
4. `[ipv4]` та `[ipv6]` — налаштування мережевого рівня L3 (методи адресації, статичні списки IP, DNS, маршрути).

#### Секція `[connection]`

| Параметр | Тип | Опис та інваріанти |
|---|---|---|
| `id=` | Рядок | Користувацьке ім'я профілю з'єднання. Відображається в інтерфейсах `nmcli connection show` та графічних аплетах. |
| `uuid=` | UUID v4 | Унікальний 128-бітний ідентифікатор профілю (наприклад, `7c1b52a3-64e3-4f91-89e4-d2e7d3839210`). Генерується утилітою `uuidgen`. |
| `type=` | Рядок | Базовий тип технології: `ethernet`, `wifi`, `bridge`, `bond`, `vlan`, `wireguard`, `vpn`, `gsm`. |
| `interface-name=` | Рядок | Обмежує дію профілю конкретним мережевим адаптером (`enp3s0`). Якщо параметр відсутній, профіль може застосовуватися до будь-якого сумісного пристрою. |
| `autoconnect=` | `true`, `false` | Чи повинен NetworkManager автоматично активувати цей профіль при виявленні лінка або відповідної Wi-Fi мережі. |
| `autoconnect-priority=` | Ціле число | Пріоритет вибору серед кількох доступних профілів (діапазон від -999 до 999; чим вище число, тим вищий пріоритет). |

#### Секція `[ipv4]`

| Параметр | Тип | Опис |
|---|---|---|
| `method=` | Рядок | Режим роботи підсистеми IPv4: `auto` (отримання параметрів через DHCP), `manual` (статична адресація), `link-local` (самопризначення адрес 169.254/16), `disabled` (вимкнення IPv4), `shared` (запуск внутрішнього NAT/DHCP для роздачі інтернету іншим клієнтам). |
| `address1=` | Рядок | Визначення статичної адреси, маски та шлюзу у єдиному рядку через кому: `<IP>/<Префікс>,<Шлюз>` (наприклад, `192.168.10.50/24,192.168.10.1`). Для додаткових адрес використовуються ключі `address2=`, `address3=`. |
| `dns=` | Рядок | Список адрес DNS-серверів, розділених крапкою з комою (обов'язкова крапка з комою в кінці): `1.1.1.1;8.8.8.8;`. |
| `dns-search=` | Рядок | Домени пошуку DNS через крапку з комою (`office.internal;corp.local;`). |
| `route1=` | Рядок | Статичний маршрут у форматі `<Мережа>/<Префікс>,<Шлюз>,<Метрика>` (`10.0.0.0/8,192.168.10.254,100`). |
| `never-default=` | `true`, `false` | При значенні `true` NetworkManager не встановлює маршрут за замовчуванням від цього підключення (корисно для додаткових корпоративних адаптерів або VPN). |
| `dhcp-timeout=` | Ціле число | Максимальний інтервал очікування відповіді DHCP у секундах до переходу з'єднання у стан збою. |

#### Приклад конфігурації стаціонарного Ethernet-з'єднання

```ini
[connection]
id=Static-Office-LAN
uuid=7c1b52a3-64e3-4f91-89e4-d2e7d3839210
type=ethernet
interface-name=enp3s0
autoconnect=true
autoconnect-priority=10

[ethernet]
auto-negotiate=true

[ipv4]
method=manual
address1=192.168.10.50/24,192.168.10.1
dns=1.1.1.1;1.0.0.1;
dns-search=office.internal;
route1=10.0.0.0/8,192.168.10.254,200

[ipv6]
method=auto

[proxy]
```

## 3. Зведена діагностика та керування в просторі користувача

Для діагностики та оперативного керування мережевими підсистемами системний адміністратор використовує набір спеціалізованих клієнтських утиліт:

| Завдання адміністрування | NetworkManager (`nmcli`) | systemd-networkd (`networkctl`) | systemd-resolved (`resolvectl`) |
|---|---|---|---|
| Загальний стан сервісу | `nmcli general status` | `networkctl status` | `resolvectl status` |
| Таблиця активних інтерфейсів | `nmcli device status` | `networkctl list` | `resolvectl status` |
| Детальні параметри лінка | `nmcli device show enp3s0` | `networkctl status enp3s0` | `resolvectl status enp3s0` |
| Перелік збережених профілів | `nmcli connection show` | *(Файли у `/etc/systemd/network/`)* | — |
| Активація з'єднання | `nmcli connection up <id>` | `networkctl up <dev>` | — |
| Деактивація з'єднання | `nmcli connection down <id>` | `networkctl down <dev>` | — |
| Перечитування конфігурацій | `nmcli connection reload` | `networkctl reload` | `resolvectl flush-caches` |
| Тестування DNS-резолвінгу | `getent hosts example.com` | — | `resolvectl query example.com` |
| Моніторинг подій у реальному часі | `nmcli monitor` | `networkctl monitor` | `resolvectl monitor` |

### Діагностика стану інтерфейсу через `networkctl`

Утиліта `networkctl` відображає поточний внутрішній стан інтерфейсу в скінченному автоматі `systemd-networkd`:
* `unmanaged`: Інтерфейс проігноровано, для нього немає відповідного `.network` файлу.
* `configuring`: Виконується процедура налаштування (триває обмін пакетами DHCP або очікування відповіді SLAAC).
* `configured`: Усі директиви конфігураційного файлу успішно застосовані через Netlink, але інтерфейс не має маршруту за замовчуванням.
* `routable`: Інтерфейс має призначену IP-адресу та активний маршрут до зовнішньої мережі.
* `degraded`: Один із протоколів (наприклад, IPv6) зазнав невдачі або втратив зв'язок, але базовий протокол (IPv4) функціонує.
* `failed`: Виникла критична помилка під час спроби конфігурації (наприклад, відхилення Netlink-повідомлення ядром).
