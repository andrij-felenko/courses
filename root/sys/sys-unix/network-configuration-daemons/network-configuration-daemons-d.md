# Хто налаштовує мережу: DHCP-клієнт, NetworkManager, systemd-networkd

<preknowlist>
- [Мережевий стек Linux](root:sys-unix/network-stack-architecture) — проходження пакетів через рівні L2/L3 у ядрі.
- [Інтерфейси, адреси й стан лінка](root:sys-unix/interfaces-and-addresses) — абстракція `struct net_device`, прапорці інтерфейсів і життєвий цикл лінка.
- [Протокол Netlink](root:sys-unix/netlink-protocol) — асинхронний сокетний інтерфейс обміну повідомленнями між ядром Linux та простором користувача.
</preknowlist>

Коли мережевий кабель підключається до гнізда Ethernet або бездротовий адаптер знаходить радіосигнал базової станції, драйвер мережевої карти в ядрі Linux переводить фізичний контролер у робочий стан і виставляє прапорець `IFF_RUNNING` у структурі `struct net_device`. З погляду ядра апаратний лінк канального рівня встановлено, проте мережевий стек залишається функціонально ізольованим: інтерфейс не має власної IP-адреси, у таблиці маршрутизації ядра відсутній запис про шлюз за замовчуванням, а системна бібліотека трансляції імен не знає IP-адрес DNS-серверів. Якщо простір користувача не втрутиться, стек TCP/IP відкидатиме будь-які спроби вихідних з'єднань із системною помилкою `ENETUNREACH` (Network is unreachable).

Ядро Linux навмисно реалізує виключно механізм передачі пакетів — обробку черг кільцевих буферів, таблиці комутації та правила фільтрації Netfilter. Уся політика мережевого керування — опитування оточення, узгодження параметрів адресації за протоколом DHCP, автентифікація в бездротових мережах, обробка подій гарячого підключення обладнання та оновлення конфігурацій DNS — цілком покладена на демони простору користувача (userspace).

## 1. Від статичного скрипта до подієвого циклу: межі старої моделі

У ранніх версіях Unix конфігурація мережі являла собою лінійну послідовність викликів утиліт `ifconfig` та `route` у стартовому командному файлі `/etc/rc` або в дистрибутивних скриптах на зразок `/etc/init.d/networking` та утиліти `ifupdown` (файл `/etc/network/interfaces`). 

Така схема спиралася на припущення про незмінність апаратної топології:
1. Мережева карта встановлена в системний слот раз і назавжди.
2. Пристрій завжди має одне й те саме фіксоване ім'я (наприклад, `eth0`).
3. Параметри підмережі (IP-адреса, маска, шлюз) стабільні або одноразово запитуються на етапі початкового завантаження через зовнішній клієнт DHCP.

```bash
# Класичний синхронний запуск інтерфейсу через ifupdown
ifup eth0
```

Цей підхід виявився абсолютно безсилим із появою мобільних комп'ютерів, динамічних інтерфейсів (USB-Ethernet, Thunderbolt, PCMCIA) та бездротових мереж стандарту IEEE 802.11 (Wi-Fi). У динамічному середовищі стан лінка змінюється непередбачувано: ноутбук переміщується між різними точками доступу, підключається до корпоративного VPN або перемикається на мобільний модем при зникненні провідного з'єднання. 

Синхронна утиліта `ifup`, яка виконується один раз і завершує роботу, не здатна реагувати на втрату сигналу, автоматично повторювати узгодження DHCP при зміні точки доступу чи перемикати маршрути ядра між інтерфейсами без втрати активних сокетних сесій.

Виникла потреба у постійно працюючих фонових сервісах (демонах), які працюють за подієвою моделлю (Event Loop). Замість одноразового лінійного налаштування демон відкриває спеціальний сокет ядра `NETLINK_ROUTE`, реєструє слухача системних подій і перебуває в пам'яті постійно, реагуючи на кожен сигнал зміни фізичного лінка або появу нового пристрою в системі.

Детальний опис історичних етапів переходу від ранніх скриптів ініціалізації до сучасного стека розкрито в [історії еволюції менеджерів мережі](root:sys-unix/network-configuration-daemons/hist-network-managers.md).

## 2. Протокол DHCP на практиці: послідовність DORA та анатомія опцій

Протокол динамічної конфігурації вузла (Dynamic Host Configuration Protocol, DHCP, стандартизований у RFC 2131) є головним механізмом, за допомогою якого новий вузол у локальній мережі отримує параметри адресації L3 від централізованого сервера. Протокол працює поверх транспортного протоколу UDP, використовуючи порт `67` для сервера та порт `68` для клієнта.

### Парадокс початкового підключення та сокети канального рівня

Під час першого виходу в мережу клієнт стикається з фундаментальною інженерною суперечністю: щоб надіслати IP-пакет через стандартний системний виклик `sendto()` на UDP-сокеті, інтерфейс повинен мати призначену валідну IP-адресу джерела. Проте клієнт ще не знає власної IP-адреси, не знає маски підмережі і не має інформації про адресу сервера.

Щоб подолати це обмеження, клієнти DHCP оминають стандартний мережевий стек ядра й працюють безпосередньо з канальним рівнем L2 через сокети `AF_PACKET` (режим `SOCK_RAW` або `SOCK_DGRAM`) або використовують системний виклик `setsockopt()` з прапорцем `SO_BINDTODEVICE` та фільтрами BPF (Berkeley Packet Filter). Це дозволяє програмі самостійно формувати сирі Ethernet-кадри з широкомовною MAC-адресою призначення `FF:FF:FF:FF:FF:FF` та IP-адресою джерела `0.0.0.0`.

### Чотири фази процедури DORA

Процес отримання оренди мережевої адреси складається з чотирьох послідовних повідомлень:

```
 Клієнт                                      Сервер DHCP
   │                                              │
   │─── DHCP Discover (Broadcast) ───────────────►│ (порт 67)
   │    Source: 0.0.0.0:68                        │
   │    Dest:   255.255.255.255:67                │
   │                                              │
   │◄── DHCP Offer (Unicast/Broadcast) ───────────│
   │    YIADDR: 192.168.1.100                     │
   │    Option 54: Server Identifier              │
   │                                              │
   │─── DHCP Request (Broadcast) ────────────────►│
   │    Option 50: Requested IP = 192.168.1.100   │
   │    Option 54: Selected Server IP             │
   │                                              │
   │◄── DHCP Acknowledge (ACK) ───────────────────│
   │    YIADDR: 192.168.1.100, Lease: 86400s      │
   │    Option 1: Mask, Option 3: Gateway, DNS    │
   ▼                                              ▼
```

1. **DHCP Discover (Пошук)**:
   Клієнт надсилає широкомовний запит у локальний сегмент мережі.
   * IP джерела: `0.0.0.0`, IP призначення: `255.255.255.255`.
   * Поле `XID` (Transaction ID): випадкове 32-бітне число, що пов'язує наступні відповіді із цим конкретним запитом.
   * `Option 53` (DHCP Message Type): значення `1` (DHCPDISCOVER).
   * `Option 55` (Parameter Request List): список числових кодів опцій, які клієнт очікує отримати від сервера (наприклад, маска підмережі, шлюз за замовчуванням, DNS-сервери, доменне ім'я, NTP-сервери).
   * `Option 61` (Client Identifier): апаратна MAC-адреса або унікальний ідентифікатор DUID (DHCP Unique Identifier).

2. **DHCP Offer (Пропозиція)**:
   Кожен DHCP-сервер у локальному сегменті, який має вільні адреси у пулі, формує пропозицію.
   * Поле `YIADDR` (Your IP Address): адреса, що пропонується клієнту (наприклад, `192.168.1.100`).
   * Поле `SIADDR` (Next Server IP Address): IP-адреса наступного сервера завантаження (застосовується для мережевого завантаження PXE/TFTP).
   * `Option 54` (Server Identifier): IP-адреса сервера, що сформував пропозицію.
   * `Option 51` (IP Address Lease Time): час оренди адреси в секундах (наприклад, `86400` — 24 години).

3. **DHCP Request (Запит)**:
   Клієнт обирає одну із отриманих пропозицій (зазвичай першу, що надійшла) і надсилає підтвердження. Повідомлення надсилається **широкомовно**, навіть якщо клієнт уже знає IP-адресу обраного сервера. Це необхідно для того, щоб усі інші DHCP-сервери, пропозиції яких були відхилені, дізналися про рішення клієнта і негайно повернули зарезервовані адреси назад у загальний пул.
   * `Option 50` (Requested IP Address): обрана адреса (`192.168.1.100`).
   * `Option 54` (Server Identifier): IP-адреса обраного сервера.

4. **DHCP Acknowledge (Підтвердження, ACK)**:
   Обраний сервер остаточно фіксує оренду у своїй базі даних і надсилає клієнту фінальне підтвердження разом із повним набором запитаних конфігураційних опцій. Після отримання ACK клієнт перевіряє унікальність отриманої адреси в локальному сегменті за допомогою повідомлення ARP Probe (RFC 5227). Якщо конфліктів не виявлено, клієнт застосовує адресу до інтерфейсу через Netlink.

### Анатомія конфігураційних опцій DHCP

Опції передаються всередині тіла повідомлення DHCP у форматі TLV (Type-Length-Value).

| Код опції | Назва | Призначення |
|---|---|---|
| `Option 1` | Subnet Mask | Маска підмережі (наприклад, `255.255.255.0`). |
| `Option 3` | Router | Список IP-адрес шлюзів за замовчуванням у порядку пріоритету. |
| `Option 6` | Domain Name Server | Список IP-адрес серверів DNS. |
| `Option 12` | Host Name | Мережеве ім'я клієнта, передане серверу для динамічної реєстрації у DNS. |
| `Option 15` | Domain Name | Суфікс локального домену для резолвінгу відносних імен (наприклад, `corp.lan`). |
| `Option 42` | NTP Servers | Список серверів протоколу синхронізації часу Network Time Protocol. |
| `Option 51` | Lease Time | Повний час оренди IP-адреси в секундах. |
| `Option 58` | Renewal Time (T1) | Інтервал до першої спроби продовження оренди. За замовчуванням становить `0.5 × LeaseTime`. Клієнт надсилає Unicast DHCP Request напряму своєму серверу. |
| `Option 59` | Rebinding Time (T2) | Інтервал до аварійної спроби продовження оренди. За замовчуванням становить `0.875 × LeaseTime` (7/8 часу). Клієнт надсилає Broadcast DHCP Request до будь-якого доступного сервера в мережі. |
| `Option 121` | Classless Static Route | Таблиця безкласових статичних маршрутів (префікс мережі + адреса шлюзу), що додаються у таблицю ядра. |

### Порівняння архітектур DHCP-клієнтів

У просторі користувача Linux історично закріпилися три різні реалізації клієнта DHCP, кожна з яких має свою цільову нішу та архітектурну ціну:

1. **ISC `dhclient` (Internet Systems Consortium)**:
   Класичний автономний демон. Коли `dhclient` отримує нову адресу або стикається зі зміною стану лінка, він викликає зовнішній інтерпретований шелл-скрипт `/sbin/dhclient-script`, передаючи йому параметри через змінні оточення. Скрипт виконує бінарні утиліти `ip` та напряму перезаписує файл `/etc/resolv.conf`. Постійні виклики `fork()` та `execve()` створюють відчутний накладний оверхед, що робить `dhclient` повільним у динамічних середовищах із сотнями віртуальних інтерфейсів.
2. **`udhcpc` (BusyBox)**:
   Мінімалістичний клієнт, створений для вбудованих Linux-систем (Embedded Linux, OpenWrt, Buildroot). Має крихітний бінарний розмір (декілька десятків кілобайтів) і низьке споживання оперативної пам'яті, викликає простий шелл-скрипт за подіями.
3. **Інтегрований клієнт `sd-dhcp-client` (`systemd-networkd`)**:
   Повністю вбудована бібліотечна реалізація, що працює всередині головного процесу демона `systemd-networkd`. `sd-dhcp-client` не створює нових процесів, не викликає шелл-скриптів і безпосередньо взаємодіє з ядром через Netlink-сокети та з `systemd-resolved` через D-Bus/Varlink. Застосування параметрів адреси займає мікросекунди, що критично для миттєвого старту контейнерів.

## 3. Програмний міст до ядра: системні повідомлення Netlink

Сучасні менеджери мережі (NetworkManager, `systemd-networkd`, `connman`) ніколи не викликають утиліти командного рядка на зразок `ip addr add` через системний виклик `fork()`. Формування нового процесу вимагає дублювання таблиць сторінок пам'яті, завантаження динамічного компонувальника та парсингу рядкових аргументів, що займає мілісекунди процесорного часу.

Замість цього простір користувача напряму відкриває мережевий сокет спеціального сімейства `socket(AF_NETLINK, SOCK_RAW, NETLINK_ROUTE)`.

### Структура протоколу `rtnetlink`

Спілкування через сокет `NETLINK_ROUTE` відбувається за допомогою двійкових повідомлень фіксованого формату. Кожен пакет починається зі стандартного заголовка `struct nlmsghdr` (довжина, тип операції, прапорці послідовності), за яким слідує протокольна структура та ланцюжок атрибутів у форматі TLV (`struct rtattr`).

```
┌────────────────────────────────────────────────────────────────────────┐
│                        struct nlmsghdr                                 │
│  nlmsg_len (розмір) │ nlmsg_type (RTM_NEWADDR) │ nlmsg_flags (NLM_F_*) │
├────────────────────────────────────────────────────────────────────────┤
│                        struct ifaddrmsg                                │
│  ifa_family (AF_INET)  │ ifa_prefixlen (24)   │ ifa_index (ifindex=2)  │
├────────────────────────────────────────────────────────────────────────┤
│  struct rtattr (IFA_LOCAL)     │  Дані адреси (4 байти IPv4: 10.0.0.5) │
├────────────────────────────────────────────────────────────────────────┤
│  struct rtattr (IFA_ADDRESS)   │  Дані адреси (4 байти IPv4: 10.0.0.5) │
└────────────────────────────────────────────────────────────────────────┘
```

Для керування IP-адресами використовуються типи повідомлень:
* `RTM_NEWADDR` — додати IP-адресу на мережевий інтерфейс. Тіло містить структуру `struct ifaddrmsg` та атрибути `IFA_LOCAL` (локальна адреса), `IFA_ADDRESS` (адреса підмережі/broadcast) та `IFA_CACHEINFO` (термін дії preferred/valid lifetime).
* `RTM_DELADDR` — видалити існуючу IP-адресу.

Для керування маршрутизацією використовуються типи повідомлень:
* `RTM_NEWROUTE` — додати запис до таблиці Forwarding Information Base (FIB) ядра. Тіло містить структуру `struct rtmsg` та атрибути `RTA_DST` (адреса призначення), `RTA_GATEWAY` (адреса наступного хопу шлюзу), `RTA_OIF` (числовий індекс вихідного інтерфейсу `ifindex`) та `RTA_PRIORITY` (метрика маршруту).
* `RTM_DELROUTE` — видалити маршрут.

### Підписка на мультикаст-групи ядра

Крім надсилання команд у ядро, сокет Netlink дозволяє демону підписатися на асинхронні повідомлення про зміни в системі. При прив'язці сокета через системний виклик `bind()` демон вказує бітову маску мультикаст-груп у полі `nl_groups` структури `struct sockaddr_nl`:
* `RTMGRP_LINK` (`RTNLGRP_LINK`): сповіщення про зміну адміністративного або фізичного стану кабелю (повідомлення `RTM_NEWLINK` з прапорцями `IFF_UP` та `IFF_RUNNING`).
* `RTMGRP_IPV4_IFADDR` / `RTMGRP_IPV6_IFADDR`: сповіщення про додавання або видалення IP-адрес іншими процесами.
* `RTMGRP_IPV4_ROUTE` / `RTMGRP_IPV6_ROUTE`: сповіщення про зміну системних маршрутів.

Завдяки цьому демон негайно пробуджується в системному виклику `epoll_wait()`, щойно в системі з'являється новий інтерфейс або змінюється статус лінка.

### Практичний приклад призначення IP-адреси через Netlink

Нижче наведено приклад коду, що демонструє формування та надсилання системного повідомлення `RTM_NEWADDR` для призначення адреси `192.168.10.50/24` на інтерфейс із числовим індексом `ifindex = 2`.

:::tabs
```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/socket.h>
#include <linux/netlink.h>
#include <linux/rtnetlink.h>
#include <arpa/inet.h>

struct nl_req {
    struct nlmsghdr n;
    struct ifaddrmsg ifa;
    char buf[256];
};

static void add_attr(struct nlmsghdr *n, int maxlen, int type, const void *data, int alen) {
    int len = RTA_LENGTH(alen);
    if (NLMSG_ALIGN(n->nlmsg_len) + RTA_ALIGN(len) > maxlen) return;
    struct rtattr *rta = (struct rtattr *)(((char *)n) + NLMSG_ALIGN(n->nlmsg_len));
    rta->rta_type = type;
    rta->rta_len = len;
    memcpy(RTA_DATA(rta), data, alen);
    n->nlmsg_len = NLMSG_ALIGN(n->nlmsg_len) + RTA_ALIGN(len);
}

int main(void) {
    int fd = socket(AF_NETLINK, SOCK_RAW, NETLINK_ROUTE);
    if (fd < 0) {
        perror("socket");
        return 1;
    }

    struct nl_req req;
    memset(&req, 0, sizeof(req));

    req.n.nlmsg_len = NLMSG_LENGTH(sizeof(struct ifaddrmsg));
    req.n.nlmsg_flags = NLM_F_REQUEST | NLM_F_CREATE | NLM_F_EXCL | NLM_F_ACK;
    req.n.nlmsg_type = RTM_NEWADDR;
    req.n.nlmsg_seq = 1;

    req.ifa.ifa_family = AF_INET;
    req.ifa.ifa_prefixlen = 24;
    req.ifa.ifa_flags = IFA_F_PERMANENT;
    req.ifa.ifa_scope = RT_SCOPE_UNIVERSE;
    req.ifa.ifa_index = 2; // ifindex цільового інтерфейсу

    struct in_addr addr;
    inet_pton(AF_INET, "192.168.10.50", &addr);
    add_attr(&req.n, sizeof(req), IFA_LOCAL, &addr, sizeof(addr));
    add_attr(&req.n, sizeof(req), IFA_ADDRESS, &addr, sizeof(addr));

    struct sockaddr_nl sa;
    memset(&sa, 0, sizeof(sa));
    sa.nl_family = AF_NETLINK;

    if (sendto(fd, &req, req.n.nlmsg_len, 0, (struct sockaddr *)&sa, sizeof(sa)) < 0) {
        perror("sendto");
        close(fd);
        return 1;
    }

    printf("Повідомлення RTM_NEWADDR успішно надіслано в ядро.\n");
    close(fd);
    return 0;
}
```

```cpp
#include <linux/rtnetlink.h>
#include <arpa/inet.h>

class NetlinkSocket {
    int fd_{-1};
public:
    NetlinkSocket() {
        fd_ = ::socket(AF_NETLINK, SOCK_RAW, NETLINK_ROUTE);
        if (fd_ < 0) {
            throw std::system_error(errno, std::generic_category(), "Не вдалося відкрити Netlink-сокет");
        }
    }
    ~NetlinkSocket() {
        if (fd_ >= 0) ::close(fd_);
    }
    NetlinkSocket(const NetlinkSocket&) = delete;
    NetlinkSocket& operator=(const NetlinkSocket&) = delete;

    [[nodiscard]] int get() const noexcept { return fd_; }

    void send(std::span<const std::uint8_t> buffer) const {
        struct sockaddr_nl sa{};
        sa.nl_family = AF_NETLINK;
        ssize_t sent = ::sendto(fd_, buffer.data(), buffer.size(), 0,
                                reinterpret_cast<struct sockaddr*>(&sa), sizeof(sa));
        if (sent < 0) {
            throw std::system_error(errno, std::generic_category(), "Помилка надсилання Netlink-повідомлення");
        }
    }
};

class NetlinkMessageBuilder {
    std::vector<std::uint8_t> buffer_;
public:
    NetlinkMessageBuilder(std::uint16_t type, std::uint16_t flags, std::uint32_t seq, const struct ifaddrmsg& ifa) {
        buffer_.resize(NLMSG_SPACE(sizeof(struct ifaddrmsg)), 0);
        auto* n = reinterpret_cast<struct nlmsghdr*>(buffer_.data());
        n->nlmsg_len = NLMSG_LENGTH(sizeof(struct ifaddrmsg));
        n->nlmsg_type = type;
        n->nlmsg_flags = flags;
        n->nlmsg_seq = seq;

        auto* ifa_dest = reinterpret_cast<struct ifaddrmsg*>(NLMSG_DATA(n));
        std::memcpy(ifa_dest, &ifa, sizeof(struct ifaddrmsg));
    }

    void add_attribute(std::uint16_t type, std::span<const std::uint8_t> data) {
        auto* n = reinterpret_cast<struct nlmsghdr*>(buffer_.data());
        std::size_t rta_len = RTA_LENGTH(data.size());
        std::size_t old_len = NLMSG_ALIGN(n->nlmsg_len);
        std::size_t new_len = old_len + RTA_ALIGN(rta_len);

        buffer_.resize(new_len, 0);
        n = reinterpret_cast<struct nlmsghdr*>(buffer_.data()); // Оновлюємо вказівник після resize

        auto* rta = reinterpret_cast<struct rtattr*>(buffer_.data() + old_len);
        rta->rta_type = type;
        rta->rta_len = static_cast<unsigned short>(rta_len);
        std::memcpy(RTA_DATA(rta), data.data(), data.size());

        n->nlmsg_len = static_cast<__u32>(new_len);
    }

    [[nodiscard]] std::span<const std::uint8_t> bytes() const noexcept {
        return {buffer_.data(), buffer_.size()};
    }
};

int main() {
    try {
        NetlinkSocket socket;

        struct ifaddrmsg ifa{};
        ifa.ifa_family = AF_INET;
        ifa.ifa_prefixlen = 24;
        ifa.ifa_flags = IFA_F_PERMANENT;
        ifa.ifa_scope = RT_SCOPE_UNIVERSE;
        ifa.ifa_index = 2; // ifindex цільового інтерфейсу

        NetlinkMessageBuilder builder(
            RTM_NEWADDR,
            NLM_F_REQUEST | NLM_F_CREATE | NLM_F_EXCL | NLM_F_ACK,
            1,
            ifa
        );

        struct in_addr addr{};
        if (::inet_pton(AF_INET, "192.168.10.50", &addr) != 1) {
            std::cerr << "Некоректний формат IP-адреси\n";
            return 1;
        }

        std::span<const std::uint8_t> addr_bytes(reinterpret_cast<const std::uint8_t*>(&addr), sizeof(addr));
        builder.add_attribute(IFA_LOCAL, addr_bytes);
        builder.add_attribute(IFA_ADDRESS, addr_bytes);

        socket.send(builder.bytes());
        std::cout << "Повідомлення RTM_NEWADDR успішно надіслано в ядро через C++ NetlinkSocket.\n";
    } catch (const std::exception& ex) {
        std::cerr << "Виняток: " << ex.what() << '\n';
        return 1;
    }
    return 0;
```

## 4. NetworkManager: архітектура для динамічних середовищ і робочих станцій

NetworkManager є багатокомпонентним системним демоном, створеним для динамічного та автоматизованого керування мережевими підключеннями. Він орієнтований на сценарії, де стан обладнання та фізичне оточення постійно змінюються: робочі станції, лептопи, портативні пристрої та мобільні шлюзи.

### Компонентна архітектура та зовнішні помічники

Головний процес `NetworkManager` працює як системний сервіс із привілеями суперкористувача (`root`) і делегує специфічні протокольні завдання зовнішнім спеціалізованим підсистемам:

1. **`udev`**: Відстежує події шин PCI/USB і сповіщає NetworkManager про появу нових мережевих адаптерів.
2. **`wpa_supplicant`**: Демон, що керує зв'язком канального рівня Wi-Fi (сканування радіоефіру, асоціація з точкою доступу, автентифікація WPA2/WPA3-Personal, 802.1X EAP Enterprise). NetworkManager керує процесом `wpa_supplicant` через системну шину D-Bus.
3. **`ModemManager`**: Сервіс взаємодії зі стільниковими модемами стандарту 4G/LTE та 5G (протоколи QMI, MBIM, AT-команди).
4. **Плагіни VPN**: Окремі процеси, що запускаються за вимогою (OpenVPN, WireGuard, StrongSwan, Cisco AnyConnect) і передають створені віртуальні тунельні інтерфейси під контроль NetworkManager.

### Міжпроцесна взаємодія через D-Bus

NetworkManager відкриває публічне об'єктно-орієнтоване API на системній шині D-Bus під інтерфейсом `org.freedesktop.NetworkManager`. Будь-який клієнт простору користувача може запитувати стан підсистеми, отримувати списки доступних бездротових мереж та ініціювати підключення.

Клієнтські інтерфейси NetworkManager включають:
* `nmcli` — потужна консольна утиліта для системних адміністраторів та скриптів автоматизації.
* `nmtui` — консольний псевдографічний інтерфейс на базі бібліотеки curses.
* Графічні аплети середовищ GNOME Shell, KDE Plasma та XFCE.

Завдяки інтеграції з фреймворком **Polkit**, звичайний неінтенсивний користувач графічної сесії має право перемикати мережі Wi-Fi або активувати VPN без необхідності введення пароля суперкористувача `root`.

### Модель з'єднань: розмежування Device та Connection

Ключовим архітектурним рішенням NetworkManager є суворе розмежування двох концепцій:
* **Device (Пристрій)**: Фізичний мережевий адаптер або віртуальний інтерфейс, зареєстрований ядром (наприклад, `wlan0`, `enp3s0`).
* **Connection (Профіль з'єднання)**: Набір збережених параметрів конфігурації (SSID мережі, пароль WPA, режим отримання IP — DHCP або статика, DNS-сервери, маршрути).

Один і той самий фізичний адаптер `wlan0` може почергово асоціюватися з десятками різних профілів з'єднань залежно від того, у зоні дії якої Wi-Fi мережі перебуває комп'ютер.

Конфігураційні профілі зберігаються на диску у каталозі `/etc/NetworkManager/system-connections/` у форматі Keyfile (текстові файли з розширенням `.nmconnection` та правами доступу `0600`).

Повний синтаксис секцій Keyfile та параметри керування через `nmcli` наведено у [довіднику конфігурацій](root:sys-unix/network-configuration-daemons/api-daemons-config-reference.md).

```ini
# Приклад: /etc/NetworkManager/system-connections/Home-WiFi.nmconnection
[connection]
id=Home-WiFi
uuid=9c3a8f12-2345-4a78-90bc-123456789abc
type=wifi
interface-name=wlan0
autoconnect=true
autoconnect-priority=20

[wifi]
mode=infrastructure
ssid=MyHomeNetwork

[wifi-security]
key-mgmt=wpa-psk
psk=SuperSecretPassword123

[ipv4]
method=auto

[ipv6]
method=auto
```

## 5. systemd-networkd: декларативна модель для хмар, серверів і контейнерів

У серверній інфраструктурі, хмарних віртуальних машинах (AWS EC2, Google Cloud, Azure) та контейнерних середовищах (Docker, Kubernetes, `systemd-nspawn`) динамічні десктопні можливості NetworkManager є надлишковими. Серверам не потрібне графічне API, підтримка Polkit чи сканування радіоефіру. Натомість на перший план виходять:
1. Мінімальне споживання пам'яті (RSS < 10 МБ проти 40–60 МБ у NetworkManager).
2. Відсутність сторонніх залежностей (нуль залежностей від D-Bus для базової конфігурації мережі).
3. Швидкість завантаження: застосування налаштувань за одиниці мілісекунд при масовому створенні сотень віртуальних інтерфейсів (veth, мости, VLAN).

Цим вимогам відповідає **`systemd-networkd`** — легковажний системний демон, інтегрований до складу базового комплекту `systemd`.

### Декларативні файли `.network` та `.netdev`

Конфігурація `systemd-networkd` повністю описується текстовими файлами у форматі INI-подібних юнітів systemd, що розташовуються у каталозі `/etc/systemd/network/`:

1. **Файли `.netdev` (Створення віртуальних пристроїв)**:
   Описують пристрої, які демон повинен самостійно створити в ядрі через Netlink: мережеві мости (Bridge), агреговані канали (Bonding), теговані віртуальні мережі (VLAN), криптографічні тунелі (WireGuard), віртуальні кабелі (veth) та тунелі VXLAN.
2. **Файли `.network` (Конфігурація інтерфейсів)**:
   Застосовують параметри L2/L3 до фізичних або створених віртуальних інтерфейсів.

#### Принцип зіставлення секції `[Match]`

На відміну від NetworkManager, де профіль прив'язується до пристрою через внутрішні UUID або явні команди активації, `systemd-networkd` діє декларативно: під час появи будь-якого інтерфейсу демон перебирає всі доступні файли `.network` за алфавітом і застосовує перший файл, чия секція `[Match]` збіглася з характеристиками пристрою.

```ini
# Приклад: /etc/systemd/network/10-server-lan.network
[Match]
Name=enp3s0
Type=ether

[Network]
Address=10.10.0.15/24
Gateway=10.10.0.1
DNS=10.10.0.1 1.1.1.1
Domains=corp.internal
IPv6AcceptRA=yes
```

### Скінченний автомат стану інтерфейсу

Під час життєвого циклу інтерфейс у `systemd-networkd` проходить послідовні стани скінченного автомата, які можна інспектувати за допомогою утиліти `networkctl`:
* `configuring` — триває процес отримання адреси (обмін пакетами DHCP або надсилання Router Solicitation для IPv6).
* `configured` — інтерфейс отримав адресу або статичні налаштування, але не має маршруту за замовчуванням.
* `routable` — інтерфейс повністю налаштований і має валідний маршрут для зв'язку із зовнішнім світом.
* `failed` — під час конфігурації сталася помилка (відхилення повідомлення ядром або таймаут).

### Сервіс очікування готовності мережі

Для запобігання ситуаціям, коли сервери баз даних або веб-сервіси намагаються відкрити сокети `bind()` на ще не отриманій IP-адресі, systemd надає сервіс `systemd-networkd-wait-online.service`. Цей юніт блокує виконання цілі `network-online.target` доти, доки всі керовані інтерфейси не перейдуть у стан `routable`.

## 6. Керування DNS: посередництво systemd-resolved

Коли кілька мережевих підсистем (наприклад, DHCP на Ethernet, DHCP на Wi-Fi та корпоративний VPN-клієнт WireGuard/OpenVPN) одночасно отримують адреси DNS-серверів, виникає класичний конфлікт спільного ресурсу. 

### Проблема плоского файлу `/etc/resolv.conf`

Традиційна системна бібліотека трансляції імен GNU C Library (`libresolv` / `getaddrinfo`) зчитує адреси резолверів із файлу `/etc/resolv.conf`. Цей файл має суворі архітектурні обмеження:
1. Він є плоским текстом, що вміщує щонайбільше три директиви `nameserver`.
2. Файл не підтримує пріоритетів інтерфейсів: якщо VPN-клієнт просто дописує свій сервер у кінець файлу, запити продовжуватимуть надсилатися на перші сервери локального провайдера, що призводить до витоку корпоративних DNS-запитів (DNS Leak).
3. Програми простору користувача постійно конкурують за право перезаписати файл, стираючи налаштування одна одної.

### Архітектура локального stub-резолвера

Для вирішення цієї проблеми розроблено сервіс **`systemd-resolved`**. Він бере на себе монопольне право керування системним DNS і запускає локальний кешуючий DNS-сервер на петльовому інтерфейсі за адресою `127.0.0.53:53`.

Файл `/etc/resolv.conf` стає символічним посиланням на один із файлів, що динамічно генеруються у каталозі `/run/systemd/resolve/`:
* `/run/systemd/resolve/stub-resolv.conf` — містить єдиний запис `nameserver 127.0.0.53` та перелік доменів пошуку. Це **рекомендований** режим роботи. Усі програми надсилають DNS-запити на локальний сокет `127.0.0.53`, де їх перехоплює `systemd-resolved`.
* `/run/systemd/resolve/resolv.conf` — містить прямий перелік усіх зовнішніх серверів DNS, зібраних з усіх активних інтерфейсів (застосовується для сумісності з програмами, що працюють усередині chroot або не підтримують локальний резолвер).

```
Програма (getaddrinfo)
     │
     ▼ (запит DNS на 127.0.0.53:53)
┌─────────────────────────────────────────────────────────────┐
│                      systemd-resolved                       │
│  Кеш DNS • Валідація DNSSEC • Шифрування DNS-over-TLS (DoT) │
└──────────────────────────────┬──────────────────────────────┘
                               │
            ┌──────────────────┴──────────────────┐
            │ (Split DNS Routing)                 │
            ▼                                     ▼
   Домен: *.corp.internal                Домен: всі інші (0.0.0.0/0)
   Інтерфейс: wg0 (VPN)                  Інтерфейс: enp3s0 (Ethernet)
   DNS: 10.200.0.1                       DNS: 1.1.1.1, 8.8.8.8
```

### Роздільна маршрутизація запитів (Split DNS)

Головною перевагою `systemd-resolved` є підтримка маршрутизації DNS-запитів за доменами (Routing Domains):
* Демон `systemd-networkd` або `NetworkManager` повідомляє `systemd-resolved` через D-Bus/Varlink, які саме DNS-сервери належать якому інтерфейсу.
* Якщо інтерфейс VPN повідомляє домен `~corp.internal` (префікс `~` позначає пріоритетний домен маршрутизації), усі запити до внутрішніх корпоративних ресурсів (`jira.corp.internal`) автоматично спрямовуються виключно через VPN-сервер `10.200.0.1`.
* Усі інші запити до публічного інтернету (`kernel.org`) паралельно надсилаються через швидкий публічний DNS провайдера без перевантаження корпоративного каналу.

## 7. Архітектурне зіставлення та вибір інструменту

Вибір між `NetworkManager`, `systemd-networkd` або мінімалістичними клієнтами визначається призначенням комп'ютерної системи:

| Критерій оцінки | ISC `dhclient` / `ifupdown` | NetworkManager | systemd-networkd |
|---|---|---|---|
| **Цільове призначення** | Застарілі системи, прості скрипти | Робочі станції, десктопи, лептопи | Сервери, хмари, віртуальні машини, контейнери |
| **Архітектурна модель** | Синхронний пакетний запуск скриптів | Подієвий демон + D-Bus API | Подієвий декларативний демон |
| **Споживання пам'яті (RSS)** | ~15–30 МБ (пікові сплески при fork) | ~40–70 МБ | ~5–10 МБ |
| **Керування Wi-Fi / LTE** | Складні зовнішні скрипти | Вбудована інтеграція з `wpa_supplicant` / `ModemManager` | Обмежене (потребує ручного запуску `wpa_supplicant`) |
| **Швидкість реакції на лінк** | 0.5–2 секунди (виклики шеллу) | 100–300 мілісекунд | 5–20 мілісекунд (прямий Netlink) |
| **Керування віртуальними L2/L3** | Складне (через окремі пакети) | Повне (через D-Bus / keyfile) | Нативне через декларативні файли `.netdev` |
| **Інтерфейс користувача** | Текстові файли, `ifup`/`ifdown` | `nmcli`, `nmtui`, графічні аплети | Текстові файли `.network`, `networkctl` |

### Практичні рекомендації щодо вибору

1. **Робочі станції та ноутбуки**: Однозначним вибором є **NetworkManager**. Він забезпечує прозору зміну Wi-Fi мереж, підключення до публічних хот-спотів із Captive Portal, інтеграцію зі стільниковими модемами та графічними інтерфейсами середовищ користувача.
2. **Сервери баз даних, гіпервізори KVM та хмарні інстанси**: Рекомендовано застосовувати **`systemd-networkd`** у зв'язці з **`systemd-resolved`**. Це гарантує мінімальне використання системних ресурсів, передбачуваний декларативний опис інтерфейсів у системному репозиторії та нативне створення складних мережевих топологій (VLAN, мости, bonding-агрегації).
3. **Контейнеризація та мікросервіси**: Вбудований у дистрибутиви легковажний стек `systemd-networkd` дозволяє піднімати віртуальні інтерфейси `veth` у просторах імен мережі (Network Namespaces) практично без накладних витрат CPU та пам'яті.
4. **Рівень абстракції Netplan**: У дистрибутивах Ubuntu та Debian сучасним стандартом конфігурації є утиліта **Netplan**. Вона зчитує єдиний YAML-опис мережі з каталогу `/etc/netplan/` і автоматично транслює його у нативні конфігураційні файли для обраного бекенду — `NetworkManager` для десктопів або `systemd-networkd` для серверів.
