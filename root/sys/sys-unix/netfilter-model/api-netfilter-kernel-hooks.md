# 📋 Інтерфейс хуків Netfilter та базові C-структури ядра

Довідник двоічних структур, констант та інтерфейсів підсистеми Netfilter у ядрі Linux визначає ABI-контракт між мережевим стеком ядра, модулями розширення та утилітами простору користувача. Наведені нижче оголошення описують точні типи даних із системних заголовків ядра (`<linux/netfilter.h>`, `<linux/netfilter_ipv4.h>` та `<net/netfilter/nf_conntrack.h>`).

Підсистема Netfilter працює безпосередньо у просторі ядра (Kernel Space), тому всі опис-структури та точки розширення розроблені з урахуванням мінімізації накладних витрат на виклики функцій та оптимізації роботи з пам'яттю. Кожен пакет, що проходить крізь ядро, репрезентується буфером `struct sk_buff`. Коли пакет досягає точки перехоплення (хука), Netfilter викликає послідовність зареєстрованих функцій зворотного виклику (callbacks), передаючи їм стан хука `struct nf_hook_state` та вказівник на пакет.

## 1. Точки перехоплення та вердикти Netfilter

Перехоплення пакетів у мережевому стеку IPv4/IPv6 описується перерахованим типом `enum nf_inet_hooks`. Кожна константа відповідає чітко визначеному етапу обробки буфера `struct sk_buff` усередині IP-стека ядра.

```c
enum nf_inet_hooks {
    NF_INET_PRE_ROUTING  = 0, /* Вхідний пакет після NIC, до рішення про маршрутизацію */
    NF_INET_LOCAL_IN     = 1, /* Пакет, адресований локальному хосту */
    NF_INET_FORWARD      = 2, /* Транзитний пакет, який пересилається іншому вузлу */
    NF_INET_LOCAL_OUT    = 3, /* Вихідний пакет, згенерований локальним процесом */
    NF_INET_POST_ROUTING = 4, /* Пакет перед передачею драйверу вихідного NIC */
    NF_INET_NUMHOOKS     = 5  /* Загальна кількість хуків для IP-протоколів */
};
```

Кожна точка перехоплення виконує суворо відведену роль у загальному циклі обробки мережевого трафіку:

- **`NF_INET_PRE_ROUTING`**: перша точка входу для кожного вхідного IP-пакета. Спрацьовує у функції `ip_rcv()` одразу після базової перевірки заголовка. Тут ядро ще не знає, чи пакет призначений локальному серверу, чи його треба переслати на інший інтерфейс. Усі маніпуляції з адресою призначення (Destination NAT / DNAT) мають виконуватися саме на цьому хуку, щоб підсистема маршрутизації бачила вже остаточну IP-адресу.
- **`NF_INET_LOCAL_IN`**: точку розташовано у функції `ip_local_deliver()`. Сюди потрапляють лише ті пакети, для яких підсистема маршрутизації `ip_route_input_noref()` підтвердила локальне призначення. Після успішного проходження цього хука пакет передається обробникам транспортного рівня (`tcp_v4_rcv()`, `udp_rcv()`).
- **`NF_INET_FORWARD`**: точка у функції `ip_forward()`. Сюди потрапляють транзитні пакети, адресовані іншим хостам у мережі. На цьому хуку перевіряються політики фільтрації транзитного трафіку та змінюються параметри TTL (Time To Live).
- **`NF_INET_LOCAL_OUT`**: перша точка перехоплення вихідних пакетів, згенерованих локальними сокетами у функції `ip_queue_xmit()`. Вона спрацьовує після первинного вибору маршруту, але до фактичної передачі на вихідний мережевий пристрій.
- **`NF_INET_POST_ROUTING`**: остання точка перехоплення у функції `ip_output()`. Сюди потрапляють усі вихідні пакети (як локальні, так і транзитні). Тут відомий остаточний вихідний інтерфейс, тому на цьому хуку виконується Source NAT (SNAT) та IP-маскарадинг.

Після виконання callback-функції на будь-якому з хуків, модуль зобов'язаний повернути одне з числових значень вердиктів (Netfilter Verdicts):

```c
#define NF_DROP   0 /* Негайно знищити пакет, звільнити пам'ять sk_buff */
#define NF_ACCEPT 1 /* Дозволити пакету продовжити рух далі мережевим стеком */
#define NF_STOLEN 2 /* Модуль забрав контроль над sk_buff (Netfilter припиняє обробку) */
#define NF_QUEUE  3 /* Передати пакет у чергу простору користувача (через NFQUEUE) */
#define NF_REPEAT 4 /* Повторно викликати поточний хук для цього ж пакета */
#define NF_STOP   5 /* Застарілий аналог ACCEPT (припинити виклики наступних правил) */
```

Вердикти визначають подальшу долю буфера пам'яті пакета:

- **`NF_DROP`**: підсистема Netfilter припиняє обробку інших правил на даному хуку й негайно викликає `kfree_skb()`. Пам'ять буфера вивільняється, а лічильники скинутих пакетів (drop counters) збільшуються.
- **`NF_ACCEPT`**: пакет передається наступному за пріоритетом обробнику на даному хуку. Якщо всі обробники повернули `NF_ACCEPT`, Netfilter викликає функцію продовження стека `okfn()`.
- **`NF_STOLEN`**: підсистема Netfilter «забуває» про пакет і не звільняє пам'ять `sk_buff`. Це використовується модулями, які самі асинхронно обробляють або повторно відправляють буфер (наприклад, підсистеми IP-дефрагментації або спецмодулі захоплення трафіку).
- **`NF_QUEUE`**: пакет кодується у Netlink-повідомлення й передається у чергу простору користувача (`nfnetlink_queue`). Обробка в ядрі призупиняється, поки демони користувача (наприклад, Suricata або Snort) не повернуть підтверджений вердикт через сокет Netlink.

Додатково вердикт може містити бітову маску почутого значення для черги (Queue Number):

```c
/* Вердикт із вказуванням конкретної черги nfqueue (байтовий зсув) */
#define NF_QUEUE_NR(n) (((n) << NF_VERDICT_BITS) | NF_QUEUE)
```

## 2. Структури реєстрації хуків: nf_hook_ops та nf_hook_state

Для реєстрації власного обробника пакетів модуль ядра заповнює структуру `struct nf_hook_ops` та передає її системній функції `nf_register_net_hook()`.

```c
struct nf_hook_state {
    unsigned int        hook;      /* Номер поточного хука (enum nf_inet_hooks) */
    u_int8_t            pf;        /* Родина протоколів (NFPROTO_IPV4, NFPROTO_IPV6 тощо) */
    struct net_device  *in;        /* Вхідний мережевий інтерфейс (або NULL) */
    struct net_device  *out;       /* Вихідний мережевий інтерфейс (або NULL) */
    struct sock        *sk;        /* Пов'язаний сокет (якщо є для LOCAL_IN/LOCAL_OUT) */
    struct net         *net;       /* Мережевий простір назв (Network Namespace) */
    int                (*okfn)(struct net *, struct sock *, struct sk_buff *);
                                   /* Функція продовження стека при поверненні NF_ACCEPT */
};

typedef unsigned int nf_hookfn(void *priv,
                               struct sk_buff *skb,
                               const struct nf_hook_state *state);

struct nf_hook_ops {
    nf_hookfn           *hook;     /* Вказівник на функцію зворотного виклику */
    struct net_device   *dev;      /* Обмеження конкретним пристроєм (опціонально) */
    void                *priv;     /* Приватні дані користувача, що передаються в hook() */
    u_int8_t            pf;        /* Родина протоколів (наприклад, NFPROTO_IPV4) */
    enum nf_inet_hooks  hooknum;   /* Точка перехоплення (наприклад, NF_INET_PRE_ROUTING) */
    int                 priority;  /* Числовий пріоритет виконання (менше значення = раніше) */
};
```

Поля структури `struct nf_hook_state` містять повний контекст виконання хука:
- `in`: вказівник на структуру вхідного мережевого пристрою `struct net_device`. На хуку `LOCAL_OUT` це поле завжди дорівнює `NULL`.
- `out`: вказівник на структуру вихідного мережевого пристрою. На хуках `PRE_ROUTING` та `LOCAL_IN` це поле дорівнює `NULL`, оскільки вихідний пристрій ще не визначений підсистемою маршрутизації.
- `sk`: вказівник на сокет ядра `struct sock`, який згенерував або приймає пакет.
- `net`: вказівник на мережевий простір назв (`netns`). Це дозволяє ізолювати правила брандмауера між різними контейнерами та мережевими стеками.
- `okfn`: вказівник на функцію ядра, яка буде викликана після успішного проходження всіх обробників на даному хуку (наприклад, `ip_rcv_finish()` або `ip_output_finish()`).

### Стандартні пріоритети ланцюжків ядра (`enum nf_ip_hook_priorities`)

Порядок виклику функцій на одному й тому самому хуку суворо визначається константою `priority`. Модулі з меншим значенням пріоритету виконуються раніше за модулі з більшим значенням:

```c
enum nf_ip_hook_priorities {
    NF_IP_PRI_FIRST         = INT_MIN,
    NF_IP_PRI_RAW_BEFORE_DEFRAG = -400,
    NF_IP_PRI_CONNTRACK_DEFRAG  = -400,
    NF_IP_PRI_RAW           = -300, /* Таблиця raw */
    NF_IP_PRI_SELINUX_FIRST = -225,
    NF_IP_PRI_CONNTRACK     = -200, /* Модуль nf_conntrack (ініціалізація станів) */
    NF_IP_PRI_MANGLE        = -150, /* Таблиця mangle */
    NF_IP_PRI_NAT_DST       = -100, /* Destination NAT (PREROUTING / OUTPUT) */
    NF_IP_PRI_FILTER        = 0,    /* Таблиця filter (стандартні правила брандмауера) */
    NF_IP_PRI_SECURITY      = 50,   /* Таблиця security (SELinux / SMACK) */
    NF_IP_PRI_NAT_SRC       = 100,  /* Source NAT (POSTROUTING / INPUT) */
    NF_IP_PRI_SELINUX_LAST  = 225,
    NF_IP_PRI_CONNTRACK_HELPER = 300,
    NF_IP_PRI_CONNTRACK_CONFIRM = INT_MAX  /* Підтвердження запису з'єднання при ACCEPT */
};
```

Розподіл пріоритетів гарантує правильну послідовність обробки трафіку:
1. `NF_IP_PRI_CONNTRACK_DEFRAG (-400)`: фрагментовані IP-пакети спочатку збираються у єдиний буфер, оскільки відстеження станів conntrack та фільтрація портів неможливі на окремих фрагментах.
2. `NF_IP_PRI_RAW (-300)`: перевіряються правила таблиці `raw`. Якщо пакет помічено ціллю `NOTRACK`, йому присвоюється прапорець обходу conntrack.
3. `NF_IP_PRI_CONNTRACK (-200)`: підсистема `nf_conntrack` розпізнає кортеж пакета, шукає запис у хеш-таблиці та встановлює стан (`NEW`, `ESTABLISHED`, `RELATED`, `INVALID`).
4. `NF_IP_PRI_MANGLE (-150)`: виконуються зміни заголовків та маркування пакетів (`skb->mark`).
5. `NF_IP_PRI_NAT_DST (-100)`: для пакетів у стані `NEW` виконується Destination NAT (DNAT).
6. `NF_IP_PRI_FILTER (0)`: виконується основна фільтрація правил брандмауера у таблиці `filter`.
7. `NF_IP_PRI_NAT_SRC (100)`: для вихідних пакетів у стані `NEW` виконується Source NAT (SNAT).
8. `NF_IP_PRI_CONNTRACK_CONFIRM (INT_MAX)`: після того, як усі таблиці прийняли вердикт `NF_ACCEPT`, запис про нове з'єднання остаточно підтверджується (confirm) і зберігається у глобальній хеш-таблиці `ct_hash`.

### Функції ядра для реєстрації та скасування хуків

У сучасних версіях ядра Linux всі реєстраційні функції приймають вказівник на мережевий простір назв `struct net *`:

```c
/* Реєстрація одного хука в конкретному мережевому просторі назв net */
int nf_register_net_hook(struct net *net, const struct nf_hook_ops *ops);

/* Скасування реєстрації одного хука */
void nf_unregister_net_hook(struct net *net, const struct nf_hook_ops *ops);

/* Масова реєстрація масиву хуків */
int nf_register_net_hooks(struct net *net, const struct nf_hook_ops *reg, unsigned int n);
void nf_unregister_net_hooks(struct net *net, const struct nf_hook_ops *reg, unsigned int n);
```

Під час реєстрації ядро додає структуру `struct nf_hook_ops` у впорядкований масив `struct nf_hook_entries` відповідного хука. Внутрішня реалізація використовує RCU (Read-Copy-Update) для гарантії того, що обробка пакетів у мережевих потоках виконується без блокування (lockless read path).

## 3. Структури відстеження станів conntrack

Модуль `nf_conntrack` оперує кортежами (tuples) для ідентифікації напрямків трафіку та підтримання стану сесій.

### Кортеж з'єднання: `struct nf_conntrack_tuple`

Кортеж описує один напрямок руху трафіку (прямий або зворотний). Він містить IP-адреси, порти та номер L4-протоколу.

```c
union nf_inet_addr {
    __be32          ip;
    __be32          ip6[4];
    struct in_addr  in;
    struct in6_addr in6;
};

struct nf_conntrack_man {
    union nf_inet_addr u3;         /* IP-адреса хоста */
    union {
        __be16      all;           /* Універсальний порт / ID */
        __be16      tcp_offset;
        __be16      udp_offset;
        __be16      icmp_id;
    } u;
    u_int16_t       l3num;         /* AF_INET або AF_INET6 */
};

struct nf_conntrack_tuple {
    struct nf_conntrack_man src;  /* Джерело (IP + порт/ID) */
    struct {
        union nf_inet_addr u3;     /* Призначення (IP + порт/ID) */
        union {
            __be16  all;
            __be16  tcp_offset;
            __be16  udp_offset;
            u_int8_t type;         /* Тип ICMP */
            u_int8_t code;         /* Код ICMP */
        } u;
        u_int8_t    protonum;      /* Номер L4-протоколу (IPPROTO_TCP, IPPROTO_UDP тощо) */
        u_int8_t    dir;           /* Напрямок: IP_CT_DIR_ORIGINAL або IP_CT_DIR_REPLY */
    } dst;
};
```

Поля `src` та `dst` гарантують унікальну ідентифікацію сесії. Для протоколів TCP та UDP у полі `u.all` зберігається мережевий номер порту (`__be16`), а для ICMP — ідентифікатор запиту `icmp_id` або тип і код повідомлення.

### Запис з'єднання в хеш-таблиці: `struct nf_conn`

Структура `struct nf_conn` репрезентує повний стан з'єднання. Вона об'єднує два кортежі (прямий `ORIGINAL` та зворотний `REPLY`), таймер застарівання, лічильники та статусні прапорці.

```c
enum ip_conntrack_dir {
    IP_CT_DIR_ORIGINAL = 0,        /* Напрямок від ініціатора (прямий потік) */
    IP_CT_DIR_REPLY    = 1,        /* Напрямок відповіді (зворотний потік) */
    IP_CT_DIR_MAX
};

struct nf_conntrack_tuple_hash {
    struct hlist_nulls_node   hnnode; /* Вузол зв'язаного списку хеш-кошика */
    struct nf_conntrack_tuple tuple;  /* Кортеж для даного напрямку */
};

struct nf_conn {
    struct sk_buff_head       head;
    possible_net_t            ct_net;
    
    /* Двостороння пара кортежів: [0] = ORIGINAL, [1] = REPLY */
    struct nf_conntrack_tuple_hash tuplehash[IP_CT_DIR_MAX];
    
    unsigned long             status; /* Бітова маска станів (IPS_CONFIRMED, IPS_NAT_MASK тощо) */
    typedef atomic_t          refcnt;
    struct timer_list         timeout;/* Таймер застарівання з'єднання */
    
    /* Бітові прапорці станів з'єднання */
    u_int32_t                 mark;   /* Маркер пакета (ct mark) */
    u_int32_t                 secmark;/* Сек'юріті-мітка SELinux */
    
    /* Розширення: помічники (helpers), NAT-структури, аккаунтинг */
    struct nf_ct_ext          *ext;
};
```

Прапорці поля `status` визначають поточний стан сесії у ядрі:
- `IPS_CONFIRMED`: запис підтверджено й успішно розміщено в хеш-таблиці `ct_hash`.
- `IPS_SEEN_REPLY`: ядро зафіксувало зворотний пакет у напрямку `REPLY` (перехід з `NEW` у `ESTABLISHED`).
- `IPS_SRC_NAT` / `IPS_DST_NAT`: для даного з'єднання застосовано динамічну трансляцію джерела або призначення.
- `IPS_DYING`: запис знаходиться у процесі видалення підсистемою Garbage Collector.
- `IPS_FIXED_TIMEOUT`: таймер застарівання не скидається при проходженні нових пакетів.

## 4. Конфігураційні параметри `sysctl` підсистеми `nf_conntrack`

Керування лімітами, розмірами хеш-таблиць та таймаутами відстеження здійснюється через псевдо-файлову систему `/proc/sys/net/netfilter/`. Зміна цих параметрів дозволяє адаптувати ядро під високонавантажені мережеві сервери або захистити систему від SYN-Flood атак.

| Параметр sysctl | Тип даних | Значення за замовчуванням | Опис та системний вплив |
| :--- | :--- | :--- | :--- |
| `net.netfilter.nf_conntrack_max` | integer | `262144` (залежить від RAM) | Максимальна кількість одночасних записів з'єднань у пам'яті ядра. При досягненні ліміту нові пакети відкидаються з помилкою `table full`. |
| `net.netfilter.nf_conntrack_count` | integer (read-only) | поточна кількість | Поточна кількість відстежуваних з'єднань у системі (`cat /proc/sys/net/netfilter/nf_conntrack_count`). |
| `net.netfilter.nf_conntrack_buckets` | integer | `65536` | Кількість хеш-кошиків (buckets) у таблиці `ct_hash`. Оптимальне співвідношення `max / buckets = 4`. |
| `net.netfilter.nf_conntrack_tcp_timeout_established` | seconds | `432000` (5 днів) | Час утримання запису TCP у стані `ESTABLISHED` за відсутності активності. На серверах під високим навантаженням рекомендується зменшувати до 3600-7200 с. |
| `net.netfilter.nf_conntrack_tcp_timeout_syn_sent` | seconds | `120` | Таймаут очікування відповіді SYN-ACK на надісланий SYN-пакет. Зменшення до 10-15 с пришвидшує вивільнення пам'яті при скануванні портів. |
| `net.netfilter.nf_conntrack_tcp_timeout_syn_recv` | seconds | `60` | Таймаут очікування третього пакета ACK після надісланого SYN-ACK. Зменшення допомагає при SYN-Flood атаках. |
| `net.netfilter.nf_conntrack_udp_timeout` | seconds | `30` | Таймаут для односпрямованого UDP-трафіку (до отримання зворотного пакета). |
| `net.netfilter.nf_conntrack_udp_timeout_stream` | seconds | `180` | Таймаут для зафіксованого двостороннього UDP-потоку (наприклад, DNS-сесії або DNS-over-UDP). |
| `net.netfilter.nf_conntrack_generic_timeout` | seconds | `600` | Таймаут для невідомих або неетикетних L4-протоколів. |

### Статистика роботи з'єднань у procfs (`/proc/net/stat/nf_conntrack`)

Підсистема Netfilter веде детальний по-ядерний (per-CPU) облік операцій із таблицею conntrack. Статистика доступна через псевдофайл `/proc/net/stat/nf_conntrack`:

```bash
cat /proc/net/stat/nf_conntrack
```

Формат файлу містить шістнадцяткові колонки для кожного процесора:
1. `entries`: поточна кількість записів у системі.
2. `searched`: кількість успішних пошуків у хеш-таблиці `ct_hash`.
3. `found`: кількість знайдених з'єднань.
4. `new`: кількість створених нових сесій (`NEW`).
5. `invalid`: кількість пакетів, визнаних неетикетними або пошкодженими (`INVALID`).
6. `ignore`: кількість пакетів, які пройшли без відстеження (`NOTRACK`).
7. `delete`: кількість видалених записів після закінчення таймауту.
8. `delete_list`: кількість записів, видалених механізмом ліквідації ланцюжків.
9. `insert`: кількість успішних вставок нових записів.
10. `insert_failed`: кількість збоїв вставки через колізії або переповнення пам'яті.
11. `drop`: кількість пакетів, відкинутих через переповнення таблиці conntrack (`table full`).
12. `early_drop`: кількість передчасно видалених застарілих записів при нестачі пам'яті.

Моніторинг лічильників `drop` та `early_drop` дозволяє оперативно виявляти виснаження ресурсів брандмауера та вчасно коригувати параметри `nf_conntrack_max` і `nf_conntrack_buckets`.
