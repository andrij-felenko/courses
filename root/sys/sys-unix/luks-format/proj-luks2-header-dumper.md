# ⚙️ Розбір та валідація бінарного заголовка LUKS2

Для детального розуміння внутрішньої організації шифрованого тома та механізмів його захисту від збоїв живлення нижче наведено закінчену системну утиліту низькорівневого аналізу. Вона відкриває блоковий пристрій або файл-образ, зчитує первинний та вторинний бінарні заголовки `luks2_hdr_disk`, перевіряє магічні сигнатури `LUKS\xba\xbe`, виконує транзакційний арбітраж на основі монотонного лічильника `seqid`, валідує контрольні суми та демонструє отримання розпарсених метаданих JSON.

Прямий парсинг заголовка без підключення високорівневої бібліотеки `libcryptsetup` є критично важливим для утиліт низькорівневого відновлення даних, криміналістичного аналізу (digital forensics), середовищ початкового завантаження (early boot stage / initramfs), а також вбудованих систем, де накладні витрати на динамічні залежності є неприпустимими.

## Архітектура бінарного дескриптора `luks2_hdr_disk`

Бінарний заголовок розміщується на початку кожної службової області (за зсувом 0 для первинного екземпляра та за зсувом `hdr_size`, дефолтно 4 МіБ, для вторинного) і має фіксований розмір рівно 4096 байтів.

Вибір фіксованого розміру 4096 байтів обумовлений двома апаратними факторами:
1. **Вирівнювання на сторінку пам'яті:** розмір 4 КіБ відповідає стандартному розміру сторінки віртуальної пам'яті архітектур x86_64, AArch64 та RISC-V, що дозволяє виконувати пряме відображення в пам'ять або виділення сторінкових буферів без дроблення.
2. **Апаратна атомарність секторів (Advanced Format 4Kn):** фізичні диски з розміром сектора 4096 байтів записують заголовок як єдину неподільну операцію запису на рівні пластини чи контролера флешпам'яті, уникаючи деградації продуктивності через цикл читання-модифікації-запису (Read-Modify-Write), властивий емуляції секторів 512e.

Усі цілочисельні багатобайтові поля заголовка закодовані у форматі Big-Endian (мережевий порядок байтів зі старшим байтом попереду), що гарантує незалежність двійкового образу диска від апаратної архітектури процесора.

### Анатомія та призначення полів дескриптора

Структура `luks2_hdr_disk` описана з атрибутом щільного пакування (`__attribute__((packed))` у C або `alignas(1)` у C++). Це забороняє компілятору вставляти оптимізаційні проміжки (padding bytes) між полями, гарантуючи точну відповідність пам'яті байтовому макету на диску:

1. **`magic` (6 байтів):** містить магічні байти `0x4C 0x55 0x4B 0x53 0xBA 0xBE` (`LUKS\xba\xbe`). Механізм транзакційної інвалідації полягає в тому, що утиліта `cryptsetup` перед перезаписом метаданих тимчасово інвертує перші чотири байти на `0x53 0x4B 0x55 0x4C` (`SKUL\xba\xbe`). Якщо живлення зникає посеред запису, стороннє ядро не розпізнає пошкоджений заголовок як дійсний LUKS2.
2. **`version` (2 байти):** версія специфікації LUKS. Для LUKS2 значення завжди дорівнює `2` (`0x0002` у Big-Endian).
3. **`hdr_size` (8 байтів):** загальний розмір області метаданих разом із текстовим JSON-сегментом (за замовчуванням 4 МіБ = 4 194 304 байти). Це значення визначає фізичний зсув, за яким на диску розташовується вторинний заголовок.
4. **`seqid` (8 байтів):** 64-бітний монотонно зростаючий лічильник транзакцій (Sequence Identifier). Будь-яка зміна конфігурації (додавання ключа, створення токена, зміна мітки) інкрементує це значення на 1.
5. **`label` (48 байтів):** текстова мітка тому в кодуванні ASCII/UTF-8 для ідентифікації пристрою менеджерами томів (udev, systemd).
6. **`csum_alg` (32 байти):** назва алгоритму контрольної суми у вигляді рядка (`"sha256"`, `"sha512"` або `"crc32"`).
7. **`salt` (64 байти):** криптографічна сіль, яка домішується під час обчислення контрольної суми метаданих для запобігання підміні блоків між різними томами.
8. **`uuid` (44 байти):** унікальний ідентифікатор тома у форматі UUID (RFC 4122).
9. **`subsystem` (48 байтів):** назва керуючої підсистеми (наприклад, `"systemd"` або пустий рядок).
10. **`hdr_offset` (8 байтів):** абсолютний фізичний зсув поточного дескриптора від початку блокового пристрою (`0` для первинного екземпляра та `4194304` для вторинного).
11. **`_padding` (184 байти):** зарезервована занулена зона для сумісності з майбутніми розширеннями формату.
12. **`csum` (64 байти):** контрольна сума, що захищає 4096 байтів заголовка та прилеглу область JSON.
13. **`_pad_to_4k` (3584 байти):** масив заповнення нулями (`0x00`), що доповнює бінарну структуру до розміру сторінки 4096 байтів.

## Алгоритми валідації цілісності та контрольні суми `csum`

Для забезпечення стійкості до апаратних збоїв накопичувача та виявлення розривів запису (write-tearing) ядро Linux і утиліти аналізу підтримують кілька алгоритмів перевірки цілісності метаданих:

* **CRC32 (IEEE 802.3):** стандартний 32-бітний циклічний надлишковий код із реверсним поліномом `0xEDB88320` (поліном x³² + x²⁶ + x²³ + x²² + x¹⁶ + x¹² + x¹¹ + x¹⁰ + x⁸ + x⁷ + x⁵ + x⁴ + x² + x + 1). Результат займає перші 4 байти поля `csum`. Завдяки наявності прямих апаратних інструкцій процесора (інструкція `CRC32` у наборі SSE4.2 на x86 або `CRC32X` на ARMv8) перевірка 4 МіБ метаданих виконується за лічені мікросекунди.
* **SHA-256 / SHA-512:** повноцінні криптографічні дайджести (32 або 64 байти), які гарантують захист не лише від випадкових бітових пошкоджень носія, а й від навмисної модифікації заголовків зловмисником.

### Покроковий протокол перевірки контрольної суми:

1. У пам'яті виділяється вирівняний буфер розміром `hdr_size` (зазвичай 4 МіБ).
2. Із диска в буфер зчитуються 4096 байтів бінарного заголовка та прилегла текстова область JSON-метаданих розміром `hdr_size - 4096` байтів.
3. 64-байтне поле `csum` усередині структури (байти за зсувом `0x100`..`0x13F`) тимчасово заповнюється нулями (`0x00`).
4. Ініціалізується контекст обраного алгоритму `csum_alg` (CRC32, SHA-256 або SHA-512). Якщо алгоритм передбачає використання солі, у хеш-функцію спершу передаються 64 байти з поля `salt`.
5. Обчислюється дайджест над усім 4-мегабайтним буфером (бінарний заголовок із зануленим `csum` + уся область JSON-метаданих).
6. Отриманий результат побайтово порівнюється з оригінальним значенням, збереженим у полі `csum`.

### Транзакційний арбітраж подвійного заголовка (Dual-Header Arbitration)

Наявність двох незалежних копій метаданих унеможливлює втрату доступу до тома при аварії живлення:

```
[Стан 1: Обидва заголовки дійсні]
  Primary (seqid = N)   vs   Secondary (seqid = N-1)  ──▶ Активний: PRIMARY (seqid = N)
  Primary (seqid = N)   vs   Secondary (seqid = N+1)  ──▶ Активний: SECONDARY (seqid = N+1, збій під час запису Primary)

[Стан 2: Один заголовок пошкоджено]
  Primary (CRC OK)      vs   Secondary (CRC FAIL)     ──▶ Активний: PRIMARY
  Primary (CRC FAIL)    vs   Secondary (CRC OK)       ──▶ Активний: SECONDARY

[Стан 3: Обидва заголовки пошкоджено]
  Primary (CRC FAIL)    vs   Secondary (CRC FAIL)     ──▶ Відмова монтування (Header corruption)
```

Під час оновлення конфігурації `libcryptsetup` спочатку записує новий стан у вторинний заголовок із номером `seqid + 1` і виконує скидання кешу диска (`fsync` / FUA). Лише після успішного підтвердження контролера накопичувача оновлюється первинний заголовок за нульовим зсувом.

## Потоковий розбір JSON-метаданих та об'єктна топологія

Безпосередньо за 4096-байтним дескриптором `luks2_hdr_disk` (починаючи зі зміщення `0x1000`) розташовується текстова область JSON. Вона займає весь простір до кінця зони метаданих (`hdr_size - 4096`, тобто 4 190 208 байтів) і доповнюється нульовими байтами (`0x00`).

Парсер зчитує текст від зсуву 4096 байтів до першого зустрічного символу `0x00` або використовує довжину документа, передаючи отриманий рядок UTF-8 у JSON-парсер. Метадані формують зв'язний орієнтований граф конфігурації.

```
┌───────────────────────────────────────────────────────────┐
│                       JSON METADATA                       │
│                                                           │
│  ┌──────────────┐         ┌─────────────┐                 │
│  │   tokens     │────────▶│  keyslots   │                 │
│  │ (tpm2/fido2) │         │ (Argon2id)  │                 │
│  └──────────────┘         └──────┬──────┘                 │
│                                  │                        │
│                                  ▼                        │
│                           ┌─────────────┐                 │
│                           │   digests   │                 │
│                           │  (PBKDF2)   │                 │
│                           └──────┬──────┘                 │
│                                  │                        │
│                                  ▼                        │
│                           ┌─────────────┐                 │
│                           │  segments   │                 │
│                           │(dm-crypt/XTS│                 │
│                           └─────────────┘                 │
└───────────────────────────────────────────────────────────┘
```

### Ключові об'єкти конфігураційного графа:

1. **`keyslots` (Слоти ключів):** словник замкових шпарин (`"0"`, `"1"`, ...). Кожен слот містить опис функції формування ключа KDF (Argon2id, Argon2i або PBKDF2), кількість виділеної оперативної пам'яті в кілобайтах (`memory`), кількість ітерацій (`time`), кількість паралельних потоків (`cpus`) та фізичні координати зашифрованої бінарної області смуг AFSplit на диску (`area.offset` та `area.size`).
2. **`digests` (Контрольні дайджести):** словник контрольних гешів головного ключа Master Key. Об'єкт містить параметри PBKDF2, сіль `salt` та контрольний хеш `digest`. Масиви `keyslots` та `segments` прив'язують конкретні слоти ключів до відповідних сегментів даних, дозволяючи перевірити автентичність введеного пароля без монтування дискового розділу.
3. **`segments` (Сегменти даних):** опис корисного навантаження носія. Містить абсолютний зсув початку зашифрованих даних `offset` (наприклад, 16 МіБ = 16 777 216 байтів), розмір `size` (`"dynamic"` для заповнення всього залишку пристрою), розмір сектора `sector_size` (512 або 4096 байтів) та специфікацію симетричного шифру ядра `encryption` (`"aes-xts-plain64"`).
4. **`tokens` (Апаратні плагіни):** конфігурація апаратних ключів (TPM2, FIDO2, PKCS#11). Зберігає прив'язку до слотів `keyslots` та апаратні блоби (`tpm2-blob`, `fido2-credential`).
5. **`config` (Загальна конфігурація):** ліміти пам'яті (`json_size`, `keyslots_size`) та список обов'язкових вимог `requirements` (наприклад, `"online-reencrypt-v2"`).

### Обробка бінарних даних Base64

Усі бінарні криптографічні структури всередині текстового документа JSON (солі KDF, верифікаційні дайджести, запечатані ключі TPM2) закодовані у форматі Base64 (RFC 4648).

Під час декодування парсер виконує сувору валідацію:
* Перевірка довжини вихідного буфера: для рядка довжиною L байтів розмір вихідного двійкового масиву становить не більше `(3 * L) / 4` байтів.
* Відхилення символів поза алфавітом `[A-Za-z0-9+/=]`.
* Захист від неканонічного вирівнювання: нульові біти в кінцевих символах заповнення (`=`) перевіряються на відсутність прихованого сміття (non-canonical padding bits).

## Покроковий розбір логіки роботи утиліти

1. **Відкриття дескриптора пристрою:** програма відкриває файл блокового носія у бінарному режимі лише для читання (`O_RDONLY` у C або `std::ios::binary` у C++). На рівні операційної системи Linux прямий доступ до секторів блокового пристрою (наприклад, `/dev/nvme0n1p3` або `/dev/sda2`) вимагає привілеїв суперкористувача (`root` або наявності можливості ядра `CAP_SYS_ADMIN`).
2. **Зчитування первинного сектора:** виконується позиціонування на зсув `0` за допомогою `lseek()` або `std::ifstream::seekg()` та зчитування 4096 байтів дескриптора. Перевіряється наявність 6-байтової сигнатури `LUKS\xba\xbe`. Якщо первинний заголовок валідний, програма дізнається розмір області метаданих `hdr_size` безпосередньо з дескриптора.
3. **Зчитування вторинного заголовка:** використовуючи отримане значення `hdr_size` (або дефолтне резервне значення 4 МіБ), покажчик зміщується на зсув вторинного заголовка і зчитує другу копію дескриптора.
4. **Конвертація порядку байтів (Endianness):** усі 16- та 64-бітні числа перетворюються у порядок хоста за допомогою макросів `be16toh` та `be64toh` із заголовка `<endian.h>`. На платформах x86_64 або AArch64 (Little-Endian) ці функції виконують реверс байтів (апаратні інструкції `bswap` або `rev`).
5. **Арбітраж транзакційного стану:** порівнюються значення лічильника `seqid`. Якщо обидва заголовки неушкоджені, активним визнається екземпляр із більшим `seqid`. У разі збою одного з блоків утиліта автоматично перемикається на вцілілу резервну копію.

## Обробка помилок, безпека пам'яті та прямий ввід-вивід (`O_DIRECT`)

Під час створення системних утиліт низькорівневого аналізу накопичувачів критично важливо дотримуватися суворих вимог безпеки пам'яті та враховувати специфіку взаємодії з апаратурою:

### Робота з прямим блоковим доступом (`O_DIRECT`)

При відкритті сирого пристрою з прапорцем `O_DIRECT` операції читання виконуються в обхід системного сторінкового кешу ядра (Page Cache). Це запобігає забрудненню пам'яті та гарантує читання найсвіжіших даних безпосередньо з флешпам'яті чи диска.

Використання `O_DIRECT` вимагає суворого дотримання трьох правил:
1. **Вирівнювання адреси буфера:** пам'ять під структуру `luks2_hdr_disk` зобов'язана бути вирівняна за адресою, кратною розміру фізичного сектора (4096 байтів). У C це забезпечується викликом `posix_memalign((void**)&hdr, 4096, sizeof(*hdr))`, а в C++ — за допомогою `std::aligned_alloc(4096, sizeof(HeaderDisk))` або вирівняного динамічного буфера. Порушення вирівнювання призведе до помилки системного виклику `EINVAL` (Invalid argument).
2. **Кратність зсуву позиціонування:** будь-які операції `lseek()` або `pread()` повинні здійснюватися за зсувами, строго кратними 512 або 4096 байтам.
3. **Кратність обсягу читання:** кількість байтів, що передається у `read()`, зобов'язана бути кратною розміру логічного сектора накопичувача.

### Валідація зміщень та запобігання DoS пам'яті (Offset & Bounds Validation)

Парсер не повинен довіряти полям заголовка без попередньої санітизації:

* **Перевірка фізичного зсуву (`hdr_offset`):** парсер звіряє значення поля `hdr_offset` з реальною позицією читання (`offset == be64toh(hdr->hdr_offset)`). Якщо образ диска було скопійовано утилітою `dd` з помилковим зсувом секторів або якщо таблиця розділів GPT змістилася, невідповідність поля `hdr_offset` дозволяє негайно виявити порушення геометрії до початку операцій із розділом.
* **Перевірка меж розміру метаданих (`hdr_size`):** значення `hdr_size` перевіряється на відповідність припустимим межам: `4096 <= hdr_size <= MAX_METADATA_SIZE`, де `MAX_METADATA_SIZE` зазвичай обмежено 8 МіБ або 16 МіБ. Це запобігає атакам типу відмови в обслуговуванні (Memory Exhaustion DoS), коли зловмисник записує в поле `hdr_size` значення `0xFFFFFFFFFFFFFFFF`, провокуючи виділення гігабайтів пам'яті.
* **Валідація зміщень слотів у JSON:** парсер перевіряє, що координати смуг AFSplit (`area.offset`) розміщуються за межами обох заголовків (`area.offset >= 2 * hdr_size`) і не перекривають бінарні метадані.

### Запобігання переповненню буферів та робота з рядками

Поля `label[48]`, `subsystem[48]`, `uuid[44]` та `csum_alg[32]` у бінарній структурі `luks2_hdr_disk` є фіксованими байтовими масивами. Якщо мітка займає всі 48 байтів, нульовий символ `\0` на кінці відсутній.

* У коді на C використання функції `printf("%s", hdr->label)` призведе до виходу за межі пам'яті (Buffer Over-read). Безпечний підхід вимагає використання специфікатора максимальної ширини `printf("%.48s", hdr->label)` або явного виклику `strnlen(hdr->label, 48)`.
* У коді на C++ безпека досягається конструюванням неволодіючих обгорток `std::string_view(raw.label, strnlen(raw.label, sizeof(raw.label)))` без додаткового копіювання пам'яті.

### Безпечне занулення пам'яті (Memory Sanitization)

Будь-які проміжні змінні, що містять зчитані ключові дані, солі або дешифровані блоби, перед вивільненням пам'яті повинні занулюватися за допомогою функції `explicit_bzero()` (у C) або `crypt_safe_memzero()`. Звичайний виклик `memset()` може бути повністю викинутий компілятором під час оптимізації `-O2`/`-O3` як «мертвий код» (Dead Store Elimination).

## Обчислювальна складність та асимптотика

Алгоритми аналізу заголовка та валідації цілісності мають чітко визначені характеристики часової та просторової складності:

| Етап обробки | Часова складність | Просторова складність (RAM) | Опис та характеристики |
| :--- | :--- | :--- | :--- |
| **Зчитування дескриптора `luks2_hdr_disk`** | `O(1)` | `O(1)` | Фіксоване читання рівно 4096 байтів зі зміщення `0` або `hdr_size`. |
| **Перевірка контрольної суми CRC32 / SHA-256** | `O(N)` | `O(N)` або `O(1)` | Лінійний прохід по всій області метаданих розміром `N = hdr_size` (4 МіБ). При блоковому хешуванні потребує `O(1)` пам'яті. |
| **Парсинг текстового JSON-документа** | `O(K)` | `O(K)` | Однопрохідний синтаксичний аналіз документа довжиною `K <= N - 4096` байтів. |
| **Побудова та валідація графа зв'язків** | `O(V + E)` | `O(V + E)` | Перевірка цілісності посилань між V вершинами (слоти, дайджести, сегменти, токени) та E ребрами зв'язків (V ≤ 32, час < 1 мкс). |

### Продуктивність апаратних інструкцій:

* **CRC32 (IEEE 802.3):** апаратні інструкції CPU обробляють до 8 байтів за такт процесора, забезпечуючи пропускну здатність > 10 ГБ/с. Повна верифікація 4 МіБ метаданих триває ≈ 0.3–0.4 мс.
* **SHA-256 (Intel SHA Extensions / ARMv8 Crypto):** апаратно прискорене гешування забезпечує швидкість ≈ 1.5–2.5 ГБ/с, витрачаючи на перевірку 4 МіБ метаданих ≈ 1.5–2.7 мс. На застарілих процесорах без підтримки векторних інструкцій час може зростати до 10–15 мс.

## Інструкція зі збирання та перевірки на реальному носії

Програми не потребують сторонніх зовнішніх бібліотек і збираються штатними компіляторами GCC або Clang:

```bash
# Збирання версії мовою C:
gcc -O2 -Wall -Wextra proj_luks_dump.c -o luks_dump_c

# Збирання версії мовою C++:
g++ -O2 -std=c++23 -Wall -Wextra proj_luks_dump.cpp -o luks_dump_cpp
```

### Створення тестового тому та симуляція аварії живлення

Для тестування роботи утиліти та перевірки механізму відновлення подвійного заголовка можна створити віртуальний файл-образ, ініціалізувати LUKS2 та змоделювати збій живлення:

```bash
# 1. Створення тестового образу розміром 64 МіБ
truncate -s 64M /tmp/luks2_test.img

# 2. Форматування тома утилітою cryptsetup
sudo cryptsetup luksFormat --type luks2 --label "SystemBackup" --subsystem "backup" /tmp/luks2_test.img

# 3. Запуск зібраної утиліти інспекції (штатний стан)
sudo ./luks_dump_cpp /tmp/luks2_test.img
```
