# 📋 Специфікація бінарного заголовка та JSON-метаданих LUKS2

Метадані дискового формату LUKS2 (Linux Unified Key Setup версії 2) визначають контракт низькорівневого розміщення службових структур, схему автентифікації та параметри криптографічного відображення блокових пристроїв підсистемою `dm-crypt` ядра Linux. Метадані зберігаються у відкритому вигляді безпосередньо за 4096-байтним бінарним преамбульним заголовком `luks2_hdr_disk` і являють собою валідний текстовий документ JSON у кодуванні UTF-8, доповнений нульовими байтами (`0x00`) до повного розміру службової зони `hdr_size` (за замовчуванням 4 194 304 байти = 4 МіБ). Метадані формують зв'язний спрямований ациклічний граф (DAG), у якому об'єкти посилаються один на одного за рядковими числовими ідентифікаторами.

```
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│                            ФІЗИЧНИЙ ДИСКОВИЙ ПРОСТІР LUKS2                               │
│                                                                                          │
│ ┌───────────────────────────┐ ┌───────────────────────────┐ ┌───────────────┐ ┌────────┐ │
│ │    Первинний заголовок    │ │    Вторинний заголовок    │ │ Область смуг  │ │ Дані   │ │
│ │ ┌───────────┬───────────┐ │ │ ┌───────────┬───────────┐ │ │  Keyslots     │ │        │ │
│ │ │luks2_hdr  │   JSON    │ │ │ │luks2_hdr  │   JSON    │ │ │  (AFSplit)    │ │(Payload│ │
│ │ │  (4 КіБ)  │(4 МіБ-4К) │ │ │ │  (4 КіБ)  │(4 МіБ-4К) │ │ │  (12-24 МіБ)  │ │ dm-    │ │
│ │ └───────────┴───────────┘ │ │ └───────────┴───────────┘ │ │               │ │ crypt) │ │
│ └───────────────────────────┘ └───────────────────────────┘ └───────────────┘ └────────┘ │
│ Зсув 0                      Зсув 4 МіБ                    Зсув 8-16 МіБ       Сегменти   │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

## 1. Бінарний дескриптор заголовка `struct luks2_hdr_disk`

Кожна з двох копій заголовка (первинна за зсувом `0` та вторинна за зсувом `hdr_size`) відкривається фіксованим 4096-байтним дескриптором `struct luks2_hdr_disk`. Усі багатобайтові цілі числа зберігаються у форматі зі старшим байтом попереду (**Big-Endian**, мережевий порядок байтів), що гарантує переносність образу між різними апаратними архітектурами (x86_64, AArch64, RISC-V, s390x).

### Бінарний макет структури

| Зсув (Hex) | Зсув (Dec) | Поле структури | Тип даних C | Розмір | Опис та семантика |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `0x0000` | `0` | `magic` | `char[6]` | 6 байтів | Магічна сигнатура: `"LUKS\xba\xbe"` (активний стан) або `"SKUL\xba\xbe"` (під час транзакційного запису). |
| `0x0006` | `6` | `version` | `uint16_t` | 2 байти | Версія специфікації: `0x0002` (Big-Endian). |
| `0x0008` | `8` | `hdr_size` | `uint64_t` | 8 байтів | Повний розмір області заголовка разом із JSON у байтах (типово `4194304` = 4 МіБ). |
| `0x0010` | `16` | `seqid` | `uint64_t` | 8 байтів | Монотонний 64-бітний лічильник транзакційних оновлень (Sequence ID). |
| `0x0018` | `24` | `label` | `char[48]` | 48 байтів | Текстова мітка тома у кодуванні UTF-8 (null-terminated). |
| `0x0048` | `72` | `csum_alg` | `char[32]` | 32 байти | Ідентифікатор криптографічного алгоритму контрольної суми (`"sha256"`, `"sha512"`, `"crc32"`). |
| `0x0068` | `104` | `salt` | `uint8_t[64]` | 64 байти | Псевдовипадкова криптографічна сіль для обчислення контрольної суми заголовка. |
| `0x00A8` | `168` | `uuid` | `char[44]` | 44 байти | Унікальний ідентифікатор тома у форматі UUID (наприклад, `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx\0`). |
| `0x00D4` | `212` | `subsystem` | `char[48]` | 48 байтів | Ідентифікатор підсистеми або власника конфігурації (наприклад, `"systemd"`, `"cryptsetup"` або порожній рядок). |
| `0x0104` | `260` | `hdr_offset` | `uint64_t` | 8 байтів | Очікуваний абсолютний фізичний зсув цього заголовка від початку диска в байтах (`0` або `4194304`). |
| `0x010C` | `268` | `_padding` | `uint8_t[180]` | 180 байтів | Зарезервована область вирівнювання (заповнюється байтами `0x00`). |
| `0x01C0` | `448` | `csum` | `uint8_t[64]` | 64 байти | Контрольна сума всього 4-мегабайтного блоку метаданих (розрахована при зануленому полі `csum`). |
| `0x0200` | `512` | `_pad_to_4k` | `uint8_t[3584]`| 3584 байти | Заповнення нулями до розміру апаратного сектора/сторінки пам'яті (4096 байтів). |

### Специфікація полів бінарного дескриптора

* **`magic`:** перші чотири байти містять ASCII-символи `L`, `U`, `K`, `S`, за якими йдуть два байти `0xBA`, `0xBE`. Перед початком фізичного оновлення заголовка драйвер тимчасово інвертує перші чотири байти на `S`, `K`, `U`, `L` (`"SKUL\xba\xbe"`). Якщо живлення пристрою зникає посеред запису сектора, такий заголовок не буде помилково розпізнано ядром як дійсний.
* **`version`:** беззнакове 16-бітне ціле число. Для стандарту LUKS2 завжди дорівнює `2` (`0x0002` у шістнадцятковому представленні).
* **`hdr_size`:** повний розмір дискового простору, відведеного під цей екземпляр метаданих. Визначає точку зміщення, за якою розташовано вторинний заголовок. Значення зобов'язане бути кратним 4096 байтам (за замовчуванням 4 МіБ).
* **`seqid`:** монотонний лічильник послідовності версій. Збільшується рівно на `1` при кожній зміні конфігурації (додавання або видалення пароля, прив'язка токена, зміна розміру сегмента). Використовується алгоритмом арбітражу: при монтуванні дійсним визнається заголовок із максимальним значенням `seqid`, що пройшов перевірку контрольної суми.
* **`label`:** мітка блокового тома довжиною до 47 символів плюс завершальний нульовий байт `\0`.
* **`csum_alg`:** текстовий ідентифікатор алгоритму хешування (за замовчуванням `"sha256"`). Визначає, як саме ядро та `libcryptsetup` рахують дайджест поля `csum`.
* **`salt`:** 64-байтний криптографічний масив, що подається на вхід алгоритму хешування під час розрахунку контрольної суми для захисту від випадкових колізій та міждискових підмін.
* **`uuid`:** символьний рядок формату UUID (36 символів плюс завершальні нулі). Обидва заголовки (первинний і вторинний) зобов'язані мати ідентичний UUID.
* **`subsystem`:** назва підсистеми-власника блоку метаданих. Запобігає конфліктам між різними інструментами керування дисками.
* **`hdr_offset`:** фізичне зміщення цього дескриптора на блоковому носії. Для первинного екземпляра — `0`, для вторинного — значення `hdr_size` (наприклад, `4194304`). Якщо образ скопійовано утилітою `dd` з помилковим зсувом секторів, ядро негайно фіксує помилку `hdr_offset != actual_offset` і блокує модифікацію диска.
* **`csum`:** 64-байтний масив, що містить результат обчислення гешу від усього блоку розміром `hdr_size` (4096 байтів дескриптора + прилегла область JSON). Під час обчислення саме поле `csum` у буфері пам'яті тимчасово занулюється.

### Протокол транзакційного оновлення заголовків

Подвійна схема заголовків гарантує атомарність оновлення метаданих без ризику втрати доступу до даних при раптовому вимкненні живлення:

```
1. Формування нового JSON-документа та структури luks2_hdr_disk із seqid_new = seqid_current + 1.
2. Розрахунок csum над буфером розміром hdr_size із зануленим полем csum та додаванням salt.
3. Запис вторинного заголовка (зсув hdr_size) із тимчасовою сигнатурою "SKUL\xba\xbe".
4. Скидання дискових буферів (fsync / Force Unit Access).
5. Заміна сигнатури вторинного заголовка на "LUKS\xba\xbe" та повторний fsync.
6. Запис первинного заголовка (зсув 0) із тимчасовою сигнатурою "SKUL\xba\xbe".
7. Скидання дискових буферів (fsync).
8. Заміна сигнатури первинного заголовка на "LUKS\xba\xbe" та фінальний fsync.
```

Під час відкриття пристрою ядро та `libcryptsetup` перевіряють контрольні суми обох заголовків. Якщо обидва екземпляри валідні, обирається той, у якого значення `seqid` є більшим. Якщо один із заголовків пошкоджено або він містить сигнатуру `"SKUL\xba\xbe"`, керування автоматично передається резервному неушкодженому екземпляру.

## 2. Загальна топологія та схема графа JSON-метаданих

Текстова область JSON починається за зсувом `4096` від початку кожного заголовка і триває до зсуву `hdr_size`. Вільний залишок простору після закриваючої фігурної дужки `}` обов'язково заповнюється байтами `0x00`.

Кореневий документ JSON складається з п'яти базових словників:

```json
{
  "keyslots": {},
  "tokens": {},
  "segments": {},
  "digests": {},
  "config": {}
}
```

```
┌───────────────────────────────────────────────────────────────────────────┐
│                       ОРІЄНТОВАНИЙ ГРАФ JSON-ОБ'ЄКТІВ                     │
│                                                                           │
│   ┌─────────────────────┐                 ┌─────────────────────┐         │
│   │       tokens        │────────────────▶│      keyslots       │         │
│   │ (tpm2, fido2, pkcs) │  keyslots:[]    │ (Argon2id, AFSplit) │         │
│   └─────────────────────┘                 └──────────┬──────────┘         │
│                                                      │                    │
│                                                      │ keyslots:[]        │
│                                                      ▼                    │
│                                           ┌─────────────────────┐         │
│                                           │       digests       │         │
│                                           │  (PBKDF2 validation)│         │
│                                           └──────────┬──────────┘         │
│                                                      │                    │
│                                                      │ segments:[]        │
│                                                      ▼                    │
│   ┌─────────────────────┐                 ┌─────────────────────┐         │
│   │       config        │                 │      segments       │         │
│   │(json_size, flags,   │                 │ (dm-crypt, offsets, │         │
│   │ requirements)       │                 │  integrity-journal) │         │
│   └─────────────────────┘                 └─────────────────────┘         │
└───────────────────────────────────────────────────────────────────────────┘
```

Граф зв'язків розв'язується наступним чином:
1. Автентифікація користувача або опитування токена зі словника `tokens` активує відповідну шпарину зі словника `keyslots`.
2. Шпарина розгортає розщеплені смуги AFSplit і відновлює кандидат у головний ключ (Master Key / Volume Key).
3. Відновлений кандидат верифікується через словник `digests`, який пов'язаний одночасно зі слотами `keyslots` та сегментами даних `segments`.
4. У разі збігу контрольного дайджесту ядро активує криптографічні сегменти зі словника `segments` за допомогою перевіреного ключа.

## 3. Словник `keyslots` (Слоти ключів)

Словник `keyslots` містить перелік замкових шпарин, пронумерованих рядковими ідентифікаторами (`"0"`, `"1"`, ... аж до 31). Кожен слот описує незалежний спосіб отримання Master Key.

### Базові поля слота типу `luks2`

| Поле | Тип | Обов'язкове | Опис та допустимі значення |
| :--- | :--- | :--- | :--- |
| `type` | String | Так | Тип шпарини: `"luks2"` (стандартний слот) або `"reencrypt"` (динамічний слот перешифрування). |
| `key_size` | Integer | Так | Розмір ключа розшифрування області шпарини (VKDK) у байтах (`32` для AES-128, `64` для AES-256-XTS). |
| `priority` | Integer | Так | Пріоритет перебору слота під час автоматичного відкриття: `0` — вимкнено (ignore), `1` — нормальний пріоритет, `2` — високий пріоритет. |
| `af` | Object | Так | Конфігурація алгоритму антикриміналістичного розсіювання інформації (Anti-Forensic Information Splitter). |
| `area` | Object | Так | Фізичні координати бінарного зберігання смуг на диску. |
| `kdf` | Object | Так | Параметри криптографічної функції розтягування пароля (Key Derivation Function). |

### Вкладений об'єкт `af` (Anti-Forensic Splitter)

Алгоритм AFSplit запобігає частковому відновленню зашифрованого ключа при пошкодженні навіть одного біта даних шпарини на диску:

```json
"af": {
  "type": "luks1",
  "stripes": 4000,
  "hash": "sha256"
}
```

* `type` (String) — тип алгоритму розщеплення. Наразі стандартизовано єдине значення `"luks1"`, що реалізує дифузійне каскадне розщеплення Клеменса Фрувірта.
* `stripes` (Integer) — кількість смуг розщеплення (за замовчуванням `4000`). Ключ розміром `K` байтів розгортається у дисковий масив розміром `4000 · K` байтів.
* `hash` (String) — криптографічна геш-функція дифузійного перемішування смуг (`"sha256"`, `"sha512"`).

### Вкладений об'єкт `area` (Бінарне розташування шпарини)

Об'єкт `area` описує ділянку на накопичувачі, де зберігаються бінарні смуги AFSplit:

```json
"area": {
  "type": "raw",
  "offset": "32768",
  "size": "262144",
  "encryption": "aes-xts-plain64",
  "key_size": 64
}
```

* `type` (String) — тип області зберігання (завжди `"raw"`).
* `offset` (String) — абсолютне фізичне зміщення початку області смуг від нульового байта диска. Подається у вигляді десяткового рядка 64-бітного беззнакового числа. Обов'язково вирівнюється на межу 4096 байтів.
* `size` (String) — розмір області смуг у байтах у вигляді десяткового рядка. Дорівнює добутку `stripes · key_size`, округленому вгору до кратності сектора/сторінки (наприклад, `4000 · 64 = 256000` байтів, що вирівнюється до `262144` байтів = 256 КіБ).
* `encryption` (String) — специфікація симетричного шифру ядра Linux, яким зашифровано смуги шпарини на диску (`"aes-xts-plain64"`, `"aes-cbc-essiv:sha256"`).
* `key_size` (Integer) — розмір ключа шифрування області шпарини у байтах.

### Вкладений об'єкт `kdf` (Параметри розтягування пароля)

Специфікація LUKS2 підтримує три алгоритми KDF: `argon2id`, `argon2i` та `pbkdf2`.

```json
"kdf": {
  "type": "argon2id",
  "time": 4,
  "memory": 1048576,
  "cpus": 4,
  "salt": "dGVzdHNhbHRkYXRhMTIzNA==",
  "hash": "sha256"
}
```

| Поле | Тип | Застосування | Опис |
| :--- | :--- | :--- | :--- |
| `type` | String | Усі | Алгоритм: `"argon2id"` (гібридний захист пам'яті/сторонніх каналів, рекомендований за замовчуванням), `"argon2i"` (захист від атак за сторонніми каналами) або `"pbkdf2"` (класичний обчислювальний режим сумісності). |
| `time` | Integer | Argon2 | Кількість проходів (ітерацій) за часом. |
| `memory` | Integer | Argon2 | Обсяг оперативної пам'яті в **кілобайтах** (наприклад, `1048576` відповідає 1024 МіБ = 1 ГБ). |
| `cpus` | Integer | Argon2 | Кількість паралельних потоків (lanes) обчислення матриці пам'яті. |
| `iterations` | Integer | PBKDF2 | Кількість обчислювальних ітерацій HMAC для режиму PBKDF2 (замість полів `time`/`memory`/`cpus`). |
| `salt` | String | Усі | Псевдовипадкова криптографічна сіль у кодуванні Base64 (мінімум 16 байтів). |
| `hash` | String | Усі | Внутрішня геш-функція (для PBKDF2 або базових перетворень Blake2b/Argon2). |

### 3.4. Архітектура, механіка пам'яті та захист KDF Argon2id

Криптографічна функція формування ключа KDF (Key Derivation Function) перетворює введений користувачем пароль довільної довжини на 512-бітний симетричний ключ розшифрування смуг шпарини VKDK (Volume Key Decryption Key). У форматі LUKS2 основним алгоритмом є `argon2id` (RFC 9106), що поєднує високу стійкість до апаратної паралелізації (ASIC/GPU) із захистом від атак за сторонніми каналами через кеш процесора.

#### Організація двовимірної матриці пам'яті

Пам'ять для обчислення Argon2id виділяється у вигляді двовимірного масиву блоків:
* **Базовий блок (Argon2 Block):** фіксований масив розміром рівно 1024 байти (1 КіБ), що складається зі 128 64-бітних слів (`uint64_t[128]`).
* **Паралельні смуги (`lanes`):** кількість горизонтальних рядків матриці, що задається полем `cpus` (позначимо `p`). Кожна смуга обробляється окремим потоком виконання.
* **Стовпчики та часові зрізи (`slices`):** кожна смуга містить `q = m' / p` блоків, де `m'` — розмір пам'яті `memory`, округлений вниз до кратності `4 · p`. Весь масив розбивається по вертикалі на 4 рівні часові зрізи (`slice 0` .. `slice 3`). У межах одного зрізу всі `p` потоків обчислюють блоки паралельно, а на межі зрізу виконується точка синхронізації (бар'єр потоків).

```
Смуга 0 (CPU 0) ──▶ [ Зріз 0 ] ──▶ [ Зріз 1 ] ──▶ [ Зріз 2 ] ──▶ [ Зріз 3 ]
                      │              │              │              │
                      │ синхронізація│ синхронізація│ синхронізація│
                      ▼              ▼              ▼              ▼
Смуга 1 (CPU 1) ──▶ [ Зріз 0 ] ──▶ [ Зріз 1 ] ──▶ [ Зріз 2 ] ──▶ [ Зріз 3 ]
```

Початковий блок `H_0` генерується геш-функцією Blake2b від конкатенації параметрів: пароля, солі, довжини вихідного ключа, кількості смуг `p`, обсягу пам'яті `m` та кількості проходів `t`. Перші два блоки кожної смуги заповнюються псевдовипадковими послідовностями з `H_0`.

Кожен наступний блок `B[i][j]` обчислюється як результат застосування функції стиснення `G` до двох попередніх блоків:
1. Безпосередньо попереднього блоку в тій самій смузі: `B[i][j-1]` (або останнього блоку смуги при переході на новий прохід).
2. Опорного блоку `B[i'][j']`, адреса якого обирається з раніше обчислених блоків пам'яті.

Функція стиснення `G(X, Y)` накладає вектор `R = X ⊕ Y`, розбиває його на 8 матриць розміром 4×4 слова (64 біти) і виконує раунди перестановок Blake2b над рядками та стовпчиками за допомогою операцій 64-бітного додавання по модулю 2⁶⁴, XOR та циклічного зсуву.

#### Захист від атак за сторонніми каналами (Side-Channel) та компромісів TMTO

Специфікація Argon2 визначає три варіанти індексації опорного блоку `B[i'][j']`:

1. **`Argon2d` (Data-Dependent):** адреса `(i', j')` вираховується з перших 64 бітів попереднього блоку пам'яті `B[i][j-1]`. Оскільки зловмисник не може передбачити, який сектор пам'яті знадобиться наступним, він не може вивільнити жоден блок RAM без повторного перерахунку всього ланцюга. Це забезпечує абсолютну стійкість проти атак із компромісом часу та пам'яті (Time-Memory Trade-Offs, TMTO) на графічних картах і чипах ASIC. Проте якщо шифрування відбувається на спільній системі (віртуалізація, хмарний гіпервізор або багатокористувацький сервер), сусідній небезпечний процес через затримки кешу L1/L2/L3 (Cache-Timing Side-Channel Attack) може відстежити патерн звернень до пам'яті й відновити біти пароля.
2. **`Argon2i` (Data-Independent):** адреса `(i', j')` генерується детермінованим генератором псевдовипадкових чисел від лічильників поточного проходу, смуги, зрізу та номера кроку. Патерн звернень до пам'яті є повністю статичним і однаковим для будь-яких паролів, що унеможливлює витоки через кеш-лінії. Однак статичність дозволяє побудувати алгоритм оптимізованого паралельного обчислення на ASIC із меншим обсягом фізичної пам'яті.
3. **`Argon2id` (Гібридний режим LUKS2):** об'єднує переваги обох схем. Під час першого проходу (`pass 0`):
   * **Перша половина матриці (`slice 0` та `slice 1`):** обчислюється в режимі **`Argon2i`** (Data-Independent). На цьому етапі формуються внутрішні стани пам'яті, що безпосередньо залежать від пароля користувача. Статичний доступ до пам'яті повністю захищає процес від сторонніх спостережень за лініями кешу CPU.
   * **Друга половина матриці (`slice 2` та `slice 3`) та всі наступні проходи (`pass 1 .. t-1`):** обчислюються в режимі **`Argon2d`** (Data-Dependent). Дані-залежна адресація жорстко прив'язує обчислення до всієї виділеної оперативної пам'яті, блокуючи оптимізації на GPU та ASIC.

#### Виконання у просторі користувача проти простору ядра

Пам'ятемісткі KDF навмисно не реалізуються всередині ядра Linux:
* **Запобігання виснаженню пам'яті ядра (Kernel OOM):** виділення сотень мегабайтів або гігабайта неперервного пулу `vmalloc`/`kmalloc` у контексті простору ядра створює ризик блокування системних переривань, затримки I/O-операцій та паніки ядра (Kernel Panic).
* **Ізоляція в `libcryptsetup`:** розрахунок Argon2id здійснюється виключно в просторі користувача бібліотекою `libcryptsetup` (через `libargon2` або криптопровайдер `libgcrypt`/`nettle`).
* **Блокування сторінок через `mlock()`:** під час ініціалізації буфера пам'яті `libcryptsetup` викликає системний виклик `mlock()` або `mlockall(MCL_CURRENT | MCL_FUTURE)`. Це гарантує, що операційна система не зможе скинути сторінки з паролем користувача та матрицею Argon2 у нешифрований файл або розділ підкачки (swap).
* **Гарантоване занулення буферів:** після відновлення ключа вся пам'ять матриці очищається системними викликами `explicit_bzero()` або `memzero_explicit()`, які гарантовано не викидаються оптимізатором компілятора (dead store elimination).
* **Безпечна передача ключа в ядро:** відновлений Master Key передається в ядро або через управляючий сокет Device Mapper (`ioctl(DM_TABLE_LOAD)`), або завантажується в захищену підсистему Kernel Keyring (`add_key("logon", ...)`), де зберігається в захищених структурах `struct key` без можливості прочитання звичайними процесами простору користувача.

#### Динамічне калібрування параметрів за бенчмарком

Під час створення тома утиліта `cryptsetup luksFormat` виконує автоматичний підбір параметрів `memory`, `time` та `cpus`:
1. **Визначення пам'яті `memory`:** за замовчуванням `libcryptsetup` виділяє під Argon2id до 50% поточної вільної оперативної пам'яті хоста, але не більше 1 048 576 КіБ (1 ГБ). Значення можна явно обмежити параметром `--pbkdf-memory <KB>`.
2. **Визначення потоків `cpus`:** бібліотека визначає кількість доступних онлайн-ядер CPU через `sysconf(_SC_NPROCESSORS_ONLN)` і встановлює `cpus` рівним кількості ядер (до максимуму 4, що відповідає кількості смуг).
3. **Запуск мікро-бенчмарку:** бібліотека виділяє тестовий буфер заданого обсягу пам'яті та вимірює точний час `T_pass` виконання одного повного проходу (`time = 1`) алгоритму Argon2id.
4. **Розрахунок кількості проходів `time`:** виходячи з цільового часу затримки `--iter-time` (за замовчуванням 2000 мс = 2 с), кількість ітерацій розраховується як:
   ```
   time = max(1, round(target_time_ms / T_pass_ms))
   ```
5. **Фіксація в JSON:** отримані значення `time`, `memory`, `cpus` разом із згенерованою криптографічною сіллю `salt` записуються у словник `keyslots[K].kdf`.

## 4. Спеціальний слот `reencrypt` (Онлайн-перешифрування тома)

Під час виконання операцій перешифрування тома без зупинки вводу-виводу (зміна алгоритму шифрування, зміна розміру ключа або первинне шифрування відкритого розділу) у словнику `keyslots` створюється спеціальний об'єкт типу `"reencrypt"`.

```json
"keyslots": {
  "0": {
    "type": "luks2",
    "key_size": 64,
    "priority": 1,
    "af": { "type": "luks1", "stripes": 4000, "hash": "sha256" },
    "area": { "type": "raw", "offset": "32768", "size": "262144", "encryption": "aes-xts-plain64", "key_size": 64 },
    "kdf": { "type": "argon2id", "time": 4, "memory": 1048576, "cpus": 4, "salt": "7mK+QzL08mF01xN3d4g6hw==", "hash": "sha256" }
  },
  "1": {
    "type": "reencrypt",
    "mode": "reencrypt",
    "direction": "forward",
    "resilience": "journal",
    "hash": "sha256",
    "data_size": 4194304,
    "alignment": 4096,
    "device_size": "10737418240",
    "resync_offset": "2147483648",
    "keyslot": 0
  }
}
```

### Специфікація полів слота `reencrypt`

| Поле | Тип | Опис та значення |
| :--- | :--- | :--- |
| `mode` | String | Режим трансформації даних: `"reencrypt"` (заміна ключа або шифру), `"encrypt"` (первинне шифрування відкритого розділу на льоту), `"decrypt"` (повне розшифрування тома у відкритий пристрій). |
| `direction` | String | Напрямок міграції зміщення: `"forward"` (від початку розділу до кінця) або `"backward"` (від кінця до початку). |
| `resilience` | String | Механізм захисту від збоїв живлення під час міграції: `"journal"` (транзакційний журнал гарячих блоків), `"checksum"` (контроль дайджестів без дублювання блоків), `"none"` (швидкий режим без захисту). |
| `hash` | String | Алгоритм гешування для журналу стійкості (`"sha256"`). |
| `data_size` | Integer | Розмір смуги / вікна міграції даних у байтах (наприклад, `4194304` = 4 МіБ). |
| `alignment` | Integer | Вирівнювання блоків міграції в байтах (типово `4096` або розмір смуги RAID). |
| `device_size` | String | Повний розмір корисного простору носія в байтах. |
| `resync_offset` | String | Поточне зміщення в байтах від початку розділу, до якого всі блоки гарантовано перешифровано новим ключем (у ранніх версіях також називалось `progress`). |
| `keyslot` | Integer | Ідентифікатор слота, у якому розміщено новий ключ. |

## 5. Словник `tokens` (Апаратні токени та плагіни автентифікації)

Словник `tokens` містить описи модулів розширення, що реалізують автоматичне або апаратне розблокування шпарин без ручного введення пароля (TPM2, FIDO2, PKCS#11, Kernel Keyring, Clevis/Tang).

Кожен токен містить масив `keyslots`, що вказує, які саме шпарини зі словника `keyslots` можуть бути розблоковані цим токеном.

```
┌───────────────────────────────────────────────────────────────────────────┐
│                        СХЕМА АПАРАТНИХ ТОКЕНІВ                            │
│                                                                           │
│  ┌───────────────────────┐   Unseal via PCR Policy   ┌─────────────────┐  │
│  │     systemd-tpm2      │──────────────────────────▶│ keyslot (пароль │  │
│  │ (PCR 0+7, ECC/RSA TSS)│                           │ розпечатується  │  │
│  └───────────────────────┘                           │ в пам'ять)      │  │
│                                                      └─────────────────┘  │
│  ┌───────────────────────┐   Assertion + hmac-secret ┌─────────────────┐  │
│  │     systemd-fido2     │──────────────────────────▶│ keyslot (пароль │  │
│  │(UserPresence, WebAuthn│                           │ розраховується  │  │
│  └───────────────────────┘                           │ з солі FIDO2)   │  │
│                                                      └─────────────────┘  │
│  ┌───────────────────────┐   Decrypt RSA/ECC Key     ┌─────────────────┐  │
│  │    systemd-pkcs11     │──────────────────────────▶│ keyslot (пароль │  │
│  │ (SmartCard / YubiKey) │                           │ розшифровується)│  │
│  └───────────────────────┘                           └─────────────────┘  │
│                                                                           │
│  ┌───────────────────────┐   Retrieve from Keyring   ┌─────────────────┐  │
│  │    luks2-keyring      │──────────────────────────▶│ keyslot (пароль │  │
│  │ (Linux Kernel Keyring)│                           │ передається)    │  │
│  └───────────────────────┘                           └─────────────────┘  │
└───────────────────────────────────────────────────────────────────────────┘
```

### 5.1. Токен ядра Linux (`luks2-keyring`)

Використовує підсистему Kernel Keyring для передачі кодового слова або симетричного ключа безпосередньо зі службової пам'яті ядра:

```json
"tokens": {
  "0": {
    "type": "luks2-keyring",
    "keyslots": ["0"],
    "key_description": "cryptsetup:volume-key-test"
  }
}
```

* `type` (String) — `"luks2-keyring"`.
* `keyslots` (Array of Strings) — масив прив'язаних слотів (наприклад, `["0"]`).
* `key_description` (String) — ідентифікатор ключа у службі `keyctl` ядра Linux (наприклад, `"cryptsetup:volume-key-test"`).

### 5.2. Токен TPM 2.0 (`systemd-tpm2`)

Запечатує секретний ключ шпарини у мікросхемі TPM 2.0 із прив'язкою до регістрів конфігурації платформи (PCR):

```json
"tokens": {
  "1": {
    "type": "systemd-tpm2",
    "keyslots": ["1"],
    "tpm2-blob": "AgEBMAAGCSqGSIb3DQEHA6CAMIACAQAwDQYJYIZIAWUDBAIBBQAwgg...",
    "tpm2-policy-hash": "E7B9A2F1C4E8D0B3A7F6E2C9D1B5A3F7E8D2C0B4A6F9E1C3D5B7A8F0E2C4D6B8",
    "tpm2-pcr-mask": 129,
    "tpm2-pcr-bank": "sha256",
    "tpm2-primary-alg": "ecc",
    "tpm2-pubkey": "MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE...",
    "tpm2-pubkey-pcr-mask": 129,
    "tpm2-pin": false,
    "tpm2-pcrs": [0, 7]
  }
}
```

* `type` (String) — `"systemd-tpm2"`.
* `keyslots` (Array of Strings) — масив прив'язаних слотів (наприклад, `["1"]`).
* `tpm2-blob` (String) — запечатаний апаратним чипом бінарний секрет у кодуванні Base64.
* `tpm2-policy-hash` (String) — дайджест політики авторизації TPM2 (PolicyPCR/PolicyAuth) у Base64.
* `tpm2-pcr-mask` (Integer або Array of Integers) — бітова маска номерів регістрів PCR. Наприклад, число `129` (`0x81` у двійковому вигляді `10000001₂`) відповідає регістрам PCR 0 (Core Firmware) та PCR 7 (Secure Boot State).
* `tpm2-pcr-bank` (String) — банк алгоритмів гешування регістрів PCR (`"sha256"`, `"sha1"`, `"sha384"`, `"sha512"`).
* `tpm2-primary-alg` (String) — тип асиметричного первинного ключа ієрархії зберігання TPM2 (`"ecc"` для NIST P-256 або `"rsa"` для RSA-2048).
* `tpm2-pubkey` (String) — відкритий ключ у кодуванні Base64 для перевірки підписаних політик авторизації.
* `tpm2-pubkey-pcr-mask` (Integer) — бітова маска регістрів PCR, на які поширюється підписана політика.
* `tpm2-pin` (Boolean) — вимога додаткового введення PIN-коду користувача перед розпечатуванням сесії TPM2.
* `tpm2-pcrs` (Array of Integers) — явний список номерів активних регістрів PCR (наприклад, `[0, 7]`).

### 5.3. Токен FIDO2 / Passkey (`systemd-fido2`)

Використовує апаратні ключі безпеки (YubiKey, SoloKey) через протокол CTAP2 / WebAuthn та розширення `hmac-secret`:

```json
"tokens": {
  "2": {
    "type": "systemd-fido2",
    "keyslots": ["2"],
    "fido2-credential": "k8Pm4N1qX9vL2zR7wT0yC3eF6aH9mK1sP4tY7zB0cF3eD6aH==",
    "fido2-salt": "q1W2e3R4t5Y6u7I8o9P0a1S2d3F4g5H6j7K8l9Z0x1C2v3B4n5M6==",
    "fido2-rp": "io.systemd.cryptsetup",
    "fido2-clientPin-required": true,
    "fido2-up-required": true,
    "fido2-uv-required": false
  }
}
```

* `type` (String) — `"systemd-fido2"`.
* `keyslots` (Array of Strings) — список ідентифікаторів прив'язаних шпарин.
* `fido2-credential` (String) — ідентифікатор облікового запису (Credential ID) ключа FIDO2 у Base64.
* `fido2-salt` (String) — 32-байтна випадкова сіль у Base64, яка передається токену для отримання секрету розширення `hmac-secret`.
* `fido2-rp` (String) — ідентифікатор сторони, що покладається (Relying Party ID), за замовчуванням `"io.systemd.cryptsetup"`.
* `fido2-clientPin-required` (Boolean) — вимога введення апаратного PIN-коду FIDO2.
* `fido2-up-required` (Boolean) — вимога підтвердження фізичної присутності користувача (User Presence — фізичний дотик до контакту ключа).
* `fido2-uv-required` (Boolean) — вимога біометричної верифікації користувача на ключі (User Verification — сканування відбитка пальця).

### 5.4. Токен смарткарт PKCS#11 (`systemd-pkcs11`)

Забезпечує автентифікацію за допомогою апаратних криптографічних смарткарт і токенів стандарту PKCS#11 / HSM:

```json
"tokens": {
  "3": {
```

#### 5.6.1. Криптографічний протокол сервера Tang (EC-MR-HKDF)

Сервер Tang є безстатусним (stateless) HTTP-сервісом, який не зберігає жодних клієнтських паролів чи ідентифікаторів дисків. Безпека базується на протоколі сліпого обміну ключами на еліптичних кривих **EC-MR-HKDF** (Elliptic Curve McCullagh-Rankin з функцією розгортання ключа HKDF):

1. **Ключові пари сервера:** сервер генерує дві асиметричні пари ключів на еліптичній кривій (зазвичай NIST P-521 або secp256k1):
   * **Signing Key Pair (`s_sign, P_sign`):** використовується для підпису публічних ключів сервера та формування криптографічного відбитка (Thumbprint, `thp`).
   * **Exchange Key Pair (`s_exch, P_exch`):** використовується в протоколі відновлення секрету.
2. **HTTP Endpoints сервера Tang:**
   * **`GET /adv` або `GET /adv/{thp}`:** ендпоінт публікації ключів. Повертає набір ключів JSON Web Key Set (JWKS), загорнутий у криптографічний конверт JWS (JSON Web Signature). Клієнт верифікує автентичність сервера, обчислюючи SHA-256 відбиток від відкритого ключа підпису згідно з RFC 7638 і порівнюючи його з локально збереженим значенням `thp`.
   * **`POST /rec/{thp}`:** ендпоінт сліпого відновлення. Клієнт генерує ефемерну пару ключів `(e, E = e · G)` і формує засліплену точку `x = k · G + e · P_exch`, де `k` — випадковий клієнтський скаляр, а `G` — генератор кривої. Сервер множить отриману точку на свій приватний ключ обміну: `y = s_exch · x = s_exch · k · G + s_exch · e · P_exch`, і повертає `y` клієнту.
3. **Зняття засліплення на клієнті:** клієнт віднімає засліплюючий фактор:
   ```
   K_derived = y - s_exch · e · G = s_exch · k · G = k · P_exch
   ```
   Отримане спільне значення `K_derived` передається у функцію HKDF (RFC 5869) для дешифрування вмісту конверта JWE. Сервер Tang жодного разу не бачить ні відкритого пароля, ні ключа шифрування диска.

#### 5.6.3. Політики відмовостійкості Shamir Secret Sharing (SSS)

Для усунення єдиної точки відмови (SPOF) при виході з ладу одного сервера Tang або для побудови багатофакторних умов завантаження Clevis підтримує пін **SSS** (Shamir's Secret Sharing):

Секретний пароль розбивається на `n` часток за схемою `(t, n)`-порогу над скінченним полем Галуа `GF(2⁸)`:
```
f(x) = S + a₁·x + a₂·x² + ... + a_(t-1)·x^(t-1) (mod p)
```
де `S = f(0)` — відновлюваний пароль, `t` — мінімально необхідна кількість часток (поріг `threshold`), а кожна частка `f(x_i)` зашифровується окремим вкладеним піном (окремим сервером Tang або чипом TPM2). Для відновлення секрету `S` достатньо успішного завершення операцій від будь-яких `t` довільних серверів із застосуванням інтерполяційного полінома Лагранжа:
```
S = ∑ [ f(x_j) · ∏ (-x_m) / (x_j - x_m) ]  для j = 1 .. t, m ≠ j
```

```json
"unprotected": {
  "clevis": {
    "pin": "sss",
    "sss": {
      "t": 2,
      "pins": {
        "tang": [
          {
            "url": "http://tang-dc1.internal:8888",
            "thp": "z8yB3vM01xN3d4g6hwv7R5QzK+8mF01xN3d4g6hwv7R="
          },
          {
            "url": "http://tang-dc2.internal:8888",
            "thp": "Kj9mR8wX2vL5nQ1sP4tY7zB0cF3eD6aH9mK1sP4tY7w="
          },
          {
            "url": "http://tang-dc3.internal:8888",
            "thp": "N3d4g6hwv7R5QzKw8mF01xN3d4g6hwv7R5QzKw8mF00="
          }
        ]
      }
    }
  }
}
```

Конфігурація вище забезпечує безперебійне завантаження вузла при доступності будь-яких 2 із 3 серверів Tang у різних зонах доступності.

Гібридна політика «Мережа АБО Апаратний чип TPM2» налаштовується аналогічно:
```json
"sss": {
  "t": 1,
  "pins": {
    "tang": [{ "url": "http://tang.office.network:8888", "thp": "..." }],
    "tpm2": { "pcr_bank": "sha256", "pcr_ids": "0,7" }
  }
}
```

## 6. Словник `digests` (Контрольні дайджести перевірки ключів)

Словник `digests` забезпечує миттєву верифікацію правильності відновленого Master Key без необхідності ініціалізувати та монтувати весь терабайтний розділ `dm-crypt`.

```json
"digests": {
  "0": {
    "type": "pbkdf2",
    "keyslots": ["0", "1", "2"],
    "segments": ["0"],
    "salt": "vG9kL89mF01xN3d4g6hwv7==",
    "digest": "pW7xR4tY7zB0cF3eD6aH9mK1sP4tY7zB0cF3eD6aH8=",
    "iterations": 185000,
    "hash": "sha256"
  }
}
```

### Специфікація полів дайджесту

| Поле | Тип | Обов'язкове | Опис та значення |
| :--- | :--- | :--- | :--- |
| `type` | String | Так | Алгоритм верифікації: `"pbkdf2"` (стандартний режим) або `"argon2id"` / `"argon2i"`. |
| `keyslots` | Array of Strings | Так | Масив шпарин, які захищають цей Master Key (наприклад, `["0", "1"]`). |
| `segments` | Array of Strings | Так | Масив сегментів корисних даних, які розшифровуються цим Master Key (наприклад, `["0"]`). |
| `salt` | String | Так | Криптографічна випадкова сіль у кодуванні Base64 (мінімум 16 байтів). |
| `digest` | String | Так | Результат обчислення функції `KDF(MasterKey, salt, ...)` у кодуванні Base64. |
| `iterations` | Integer | Для PBKDF2 | Кількість ітерацій PBKDF2 для розрахунку дайджесту (типово 100 000–250 000). |
| `hash` | String | Так | Алгоритм гешування (`"sha256"`, `"sha512"`). |
| `time` | Integer | Для Argon2 | Кількість проходів за часом для режиму Argon2id. |
| `memory` | Integer | Для Argon2 | Обсяг пам'яті в кілобайтах для режиму Argon2id. |
| `cpus` | Integer | Для Argon2 | Кількість обчислювальних потоків для режиму Argon2id. |

### Протокол верифікації Master Key

```
1. Пароль користувача / відповідь токена
       │
       ▼
2. KDF (Argon2id) ──▶ Ключ VKDK
       │
       ▼
3. Розшифрування області AFSplit на диску
       │
       ▼
4. Злиття смуг AFSplit ──▶ Кандидат Master Key
       │
       ▼
5. PBKDF2(Кандидат, digest.salt, digest.iterations, digest.hash)
       │
       ▼
6. Порівняння з полем digest.digest:
   ├── ЗБІГ: Ключ валідний ──▶ Передача у ядро для активації segments[0]
   └── РОЗБІЖНІСТЬ: Пароль невірний ──▶ Помилка -EPERM
```

## 7. Словник `segments` (Сегменти корисних даних та цілісність)

Словник `segments` описує фізичне розташування, розміри та криптографічні параметри відображення корисного навантаження (користувацьких даних) на блоковому носії.

### 7.1. Сегмент типу `crypt` (Зашифровані дані dm-crypt)

```json

  "0": {
    "type": "crypt",
    "offset": "16777216",

    "encryption": "aes-xts-plain64",

```

#### Поля сегмента `crypt`

| Поле | Тип | Опис та допустимі значення |
| :--- | :--- | :--- |
| `type` | String | Тип сегмента: `"crypt"`. |
| `offset` | String | Фізичний зсув початку зашифрованих даних від нульового сектора носія в байтах (десятковий рядок, наприклад `"16777216"` = 16 МіБ). |
| `size` | String | Довжина сегмента в байтах у вигляді десяткового рядка, або спеціальне ключове слово `"dynamic"` (сегмент займає весь залишок дискового простору до кінця розділу). |
| `iv_tweak` | String | Початкове зміщення для лічильника вектора ініціалізації секторів (за замовчуванням `"0"`). Дозволяє зсувати нумерацію секторів при розбитті тома на кілька сегментів. |
| `encryption` | String | Специфікація шифру ядра Linux (`"aes-xts-plain64"`, `"chacha20-poly1305"`, `"aes-cbc-essiv:sha256"`). |

| `flags` | Array of Strings | Додаткові прапорці сегмента (наприклад, `["backup-final-metadata"]` під час зміни геометрії тома або `["in-reencryption"]`). |
| `integrity` | Object | Опціональний об'єкт конфігурації модуля апаратної/програмної автентифікації даних `dm-integrity`. |

#### 7.1.1. Вкладений об'єкт `integrity` (Підсистема dm-integrity)

Якщо том створено з підтримкою контролю автентичності кожного сектора, об'єкт `integrity` визначає стек криптографічного захисту від несанкціонованої модифікації (Bit-Flipping) та збоїв живлення:

```json
"integrity": {
  "type": "hmac",
  "journal_encryption": "aes-xts-plain64",
  "journal_integrity": "hmac(sha256)",
  "journal_size": 33554432,
  "journal_watermark": 50,
  "integrity_key_size": 32,
  "sector_size": 4096
}
```

| Поле | Тип | Обов'язкове | Опис та семантика |
| :--- | :--- | :--- | :--- |
| `type` | String | Так | Тип перевірки цілісності: `"hmac"` (контроль HMAC-кодом на сектор), `"aead"` (інтегрований шифр з автентифікацією), `"journal"` (захист лише через транзакційний журнал), `"standalone"` (автономний шар). |
| `journal_encryption` | String | Ні | Специфікація шифрування дискового журналу транзакцій `dm-integrity` (наприклад, `"aes-xts-plain64"` або `"none"`). |
| `journal_integrity` | String | Ні | Алгоритм автентифікації записів журналу транзакцій (`"hmac(sha256)"`, `"crc32c"` або `"none"`). |
| `journal_size` | Integer | Ні | Загальний розмір кільцевого буфера журналу на носії в байтах (типово від 16 МіБ до 128 МіБ). |
| `journal_watermark` | Integer | Ні | Поріг заповнення журналу у відсотках (наприклад, `50`), при досягненні якого фоновий потік ядра починає примусове виштовхування (flush) даних у постійні сектори. |
| `integrity_key_size`| Integer | Для HMAC/AEAD| Розмір автентифікаційного ключа цілісності в байтах (наприклад, `32` для HMAC-SHA256). |
| `sector_size` | Integer | Так | Розмір сектора автентифікації даних (`512` або `4096` байтів). |

#### 7.1.2. Режими журналювання `dm-integrity` та архітектура стійкості до збоїв живлення

Підсистема ядра Linux `dm-integrity` функціонує як проміжний шар між фізичним накопичувачем та криптографічним модулем `dm-crypt`. Її головна інженерна функція — атомарний запис корисного навантаження сектора та відповідного йому автентифікаційного тегу (Authentication Tag, MAC) з унеможливленням розриву запису (Write-Tear).

```
┌───────────────────────────────────────────────────────────────────────────┐
│                      ДИСКОВИЙ МАКЕТ DM-INTEGRITY                          │
│                                                                           │
│ ┌──────────────┬──────────────────┬─────────────────┬───────────────────┐ │
│ │ Superblock   │  Journal Area    │ Tag Metadata    │  Data Payload     │ │
│ │  (LBA 0..7)  │ (Кільцевий буфер)│  (Таблиця тегів)│ (Зашифровані дані)│ │
│ └──────────────┴──────────────────┴─────────────────┴───────────────────┘ │
└───────────────────────────────────────────────────────────────────────────┘
```

Драйвер підтримує три фундаментальні режими журналювання:

```
┌───────────────────────────────────────────────────────────────────────────┐
│              РЕЖИМИ ЖУРНАЛЮВАННЯ DM-INTEGRITY В ЯДРІ LINUX                │
│                                                                           │
│ 1. РЕЖИМ JOURNAL (Подвійний запис)                                        │
│    bio write ──▶ [ Journal Log (Data + Tag) ] ──(FUA)──▶ [ Data + Tag ]   │
│                  └────────── Захист від write-tear ─────┘                 │
│                                                                           │
│ 2. РЕЖИМ BITMAP (Асинхронне відстеження)                                  │
│    bio write ──▶ [ Встановлення біта в RAM/Disk ] ──▶ [ Data + Tag ]      │
│                  └────────── Перерахунок тегів після аварії ─┘            │
│                                                                           │
│ 3. РЕЖИМ NONE / STANDALONE (Прямий запис)                                 │
│    bio write ───────────────────────────────────────▶ [ Data + Tag ]      │
│                  ✖ Ризик розсинхронізації тегу (-EILSEQ)                  │
└───────────────────────────────────────────────────────────────────────────┘
```

1. **Режим `journal` (Транзакційний журнал за замовчуванням):**
   * **Механізм подвійного запису (Double Write):** кожен запит на запис сторінки `struct bio` спочатку записується в кільцевий дисковий журнал `Journal Area` разом із заголовком транзакції, порядковим номером (Commit ID) та обчисленим автентифікаційним тегом.
   * **Бар'єр фіксації (FUA / Flush):** ядро посилає командний прапорець `REQ_FUA` (Force Unit Access). Після того як контролер носія підтвердить фізичне збереження запису в журналі, робочі потоки `dm-integrity` копіюють дані у робочі сектори `Data Payload`, а тег — у зону `Tag Metadata`.
   * **Відновлення після збою живлення:** якщо живлення раптово вимикається під час запису в область даних, драйвер при наступній ініціалізації зчитує валідний блок із `Journal Area` і повторно накочує (replay) транзакцію. Неузгодженість між сектором і тегом неможлива.
   * **Ціна продуктивності:** коефіцієнт підсилення запису (**Write Amplification Factor**) зростає до ≥ 2.0× для великих послідовних операцій і до 3.0×...4.0× для дрібних випадкових запитів 4 КіБ через оверхед секторів коміту. Лінійна пропускна здатність запису падає на 50–70%, а затримка зростає вдвічі.

2. **Режим `bitmap` (Асинхронна бітова карта):**
   * **Механізм бітової маски:** замість повного дублювання даних секторів `dm-integrity` виділяє компактну область бітової карти (Bitmap), де кожен біт відповідає логічному діапазону секторів (типово 1 біт на 64 КіБ або 128 КіБ).
   * **Протокол запису:** перед модифікацією сектора відповідний біт у бітовій карті позначається як брудний (`1`). Після цього дані й тег записуються напряму у фізичні області `Data Payload` та `Tag Metadata`. Коли всі сторінки скинуто на диск, біт очищається (`0`).
   * **Поведінка при аварії живлення:** якщо вузол аварійно перезавантажується, драйвер сканує бітову карту і знаходить усі незакриті брудні біти. Для відповідних блоків драйвер у фоновому режимі автоматично перераховує та перепідписує контрольні теги (resynchronization).
   * **Ціна та компроміси:** усуває подвійний запис даних, дозволяючи досягти 90–98% від сирої пропускної здатності носія NVMe. Проте якщо сектор було оновлено частково в момент знеструмлення (Torn Write), перерахунок тегу легітимізує пошкоджені байти. Тому режим `bitmap` застосовується виключно в надбудовах із надлишковим захистом вищого рівня (RAID-1 / RAID-5 / RAID-6 поверх `dm-integrity`).

3. **Режим `none` / `standalone` (Прямий запис без журналу):**
   * **Механіка:** журналювання та бітові карти повністю деактивовані. Запити вводу-виводу записують дані та теги безпосередньо на носій в один прохід.
   * **Продуктивність:** максимальна швидкодія (100% утилізація пропускної здатності шини PCIe 4.0/5.0, відсутність додаткових затримок планувальника).
   * **Критична вразливість:** відсутній захист від аварійного відключення живлення (Power-Cut Vulnerability). Якщо носій втрачає живлення в середині запису 4-кілобайтного сектора, новий вміст даних не відповідатиме старому тегу в `Tag Metadata`. Під час наступного читання цього сектора ядро виявить незбіг HMAC/Poly1305 і перерве операцію вводу-виводу з фатальною помилкою **`-EILSEQ` (Illegal byte sequence)**, що призведе до блокування файлу або переводу файлової системи в режим Read-Only.

#### 7.1.3. Порівняння характеристик режимів журналювання `dm-integrity`

| Характеристика | Режим `journal` | Режим `bitmap` | Режим `none` / `standalone` |
| :--- | :--- | :--- | :--- |
| **Write Amplification** | ≈ 2.0× – 3.5× | ≈ 1.05× – 1.1× | 1.0× (ідеально) |
| **Швидкість лінійного запису**| 30–45% від raw NVMe | 90–96% від raw NVMe | 98–100% від raw NVMe |
| **Затримка випадкового запису 4K**| Висока (2 бар'єри FUA) | Низька (прямий I/O) | Мінімальна (апаратна затримка) |
| **Стійкість до збоїв живлення**| Абсолютна (Replay журналу) | Відновлення через Resync | Відсутня (ризик помилок `-EILSEQ`) |
| **Рекомендоване середовище** | Одиночні SSD/HDD, критичні бази | Програмний RAID / Mirroring | Тестові стенди, read-only сховища |

### 7.2. Сегмент типу `linear` (Наскрізне незашифроване відображення)

Використовується для відкритих службових областей або під час міграції онлайн-дешифрування:

```json
"segments": {
  "1": {
    "type": "linear",
    "offset": "0",
    "size": "16777216",
    "flags": []
  }
}
```

* `type` (String) — `"linear"`.
* `offset` (String) — фізичний зсув ділянки в байтах від початку пристрою.
* `size` (String) — довжина ділянки в байтах або ключове слово `"dynamic"`.
* `flags` (Array of Strings) — масив прапорців сегмента.

### 7.3. Криптографічна взаємодія з ядром Linux dm-crypt та трансляція таблиці Device Mapper

Після того як користувацький простір (`libcryptsetup`) успішно виконує розтягування пароля KDF Argon2id, розшифровує бінарну область шпарини `area`, відновлює Master Key через дифузійне злиття смуг AFSplit та верифікує його валідність за допомогою контрольного словника `digests`, бібліотека переходить до безпосередньої активації віртуального блокового пристрою в ядрі Linux.

#### Архітектура взаємодії через ioctl Device Mapper

Активація шифрованого тома здійснюється через управляючий символьний пристрій `/dev/mapper/control` за допомогою послідовності системних викликів `ioctl`:

```
┌───────────────────────────────────────────────────────────────────────────┐
│              ПОСЛІДОВНІСТЬ АКТИВАЦІЇ DM-CRYPT В ЯДРІ LINUX                │
│                                                                           │
│   libcryptsetup (User Space)                  Ядро Linux (Kernel Space)   │
│ ┌─────────────────────────────┐              ┌──────────────────────────┐ │
│ │ 1. ioctl(DM_DEV_CREATE)     │─────────────▶│ Реєстрація нового вузла  │ │
│ │    (ім'я /dev/mapper/root)  │              │ блокового пристрою dm-X  │ │
│ └─────────────────────────────┘              └──────────────────────────┘ │
│                │                                           │              │
│ ┌─────────────────────────────┐              ┌──────────────────────────┐ │
│ │ 2. ioctl(DM_TABLE_LOAD)     │─────────────▶│ Парсинг рядка таблиці,   │ │
│ │    (сформований dm table)   │              │ перевірка ключів і шифру │ │
│ └─────────────────────────────┘              └──────────────────────────┘ │
│                │                                           │              │
│ ┌─────────────────────────────┐              ┌──────────────────────────┐ │
│ │ 3. ioctl(DM_DEV_SUSPEND)    │─────────────▶│ Активація (Resume)       │ │
│ │    (без прапорця SUSPEND)   │              │ робочої таблиці секторів │ │
│ └─────────────────────────────┘              └──────────────────────────┘ │
│                │                                           │              │
│ ┌─────────────────────────────┐              ┌──────────────────────────┐ │
│ │ 4. udev event (Створення    │◀─────────────│ Відправка Netlink uevent │ │
│ │    символічного лінка)      │              │ про новий блоковий диск  │ │
│ └─────────────────────────────┘              └──────────────────────────┘ │
└───────────────────────────────────────────────────────────────────────────┘
```

1. **`DM_DEV_CREATE`:** створює новий логічний пристрій Device Mapper з заданим користувачем іменем (наприклад, `cr_data`). Ядро виділяє динамічний номер вузла `major:minor` (наприклад, `253:0`).
2. **`DM_TABLE_LOAD`:** завантажує в пам'ять ядра структуру відображення цілі `dm-target-spec` та текстовий рядок параметрів драйвера `crypt`.
3. **`DM_DEV_SUSPEND` (із вимкненим бітом призупинення):** виконує операцію Resume (активацію), що перемикає щойно завантажену таблицю в активний стан. Ядро ініціалізує черги вводу-виводу та створює вузол `/dev/dm-0`.
4. **`udevadm` / `systemd-udevd`:** підсистема udev отримує повідомлення через сокет Netlink і створює символічне посилання `/dev/mapper/cr_data -> /dev/dm-0`.

#### Специфікація рядка таблиці цілі `dm-crypt`

Рядок таблиці конфігурації для модуля `dm-crypt.ko` має наступний канонічний синтаксис:

```
<logical_start_sector> <num_sectors> crypt <cipher> <key> <iv_offset> <device_path> <offset> [<#opt_params> <opt_params>]
```

#### Покрокова трансляція полів із JSON-метаданих

Кожен параметр таблиці Device Mapper обчислюється на основі JSON-дескрипторів `segments`, `config` та відновленого ключа:

| Параметр dm table | Джерело в JSON-метаданих | Правило перетворення та семантика |
| :--- | :--- | :--- |
| `<logical_start_sector>` | Контекст пристрою | Завжди `0` (початок логічного адресного простору створюваного віртуального диска). |
| `<num_sectors>` | `segments[S].size` | Довжина зашифрованої області у 512-байтних секторах. Якщо значення числове: `size / 512`. Якщо вказано `"dynamic"`, `libcryptsetup` надсилає накопичувачу `ioctl(BLKGETSIZE64, &dev_size)` і рахує: `(dev_size - offset) / 512`. |
| `crypt` | `segments[S].type` | Символьне ім'я цільового криптографічного драйвера ядра Linux (`dm-crypt`). |
| `<cipher>` | `segments[S].encryption` | Специфікація симетричного шифру, режиму зчеплення та генератора векторів ініціалізації у форматі `cipher-chainmode-ivmode[:ivoptions]` (наприклад, `aes-xts-plain64`, `chacha20-poly1305` або `aes-cbc-essiv:sha256`). |
| `<key>` | Master Key / Keyring | Симетричний ключ шифрування. Передається як рядок шістнадцяткових байтів (HEX) довжиною `2 · key_size` символів або як захищене посилання на дескриптор Kernel Keyring (наприклад, `:64:logon:cryptsetup:UUID`). |
| `<iv_offset>` | `segments[S].iv_tweak` | Зміщення лічильника секторів генератора IV (у 512-байтних секторах), отримане як `iv_tweak / 512` (типово `0`). Запобігає колізіям векторів ініціалізації при розбитті тома на кілька сегментів. |
| `<device_path>` | Контекст монтування | Шлях до базового фізичного пристрою (наприклад, `/dev/nvme0n1p3`) або його ідентифікатор `major:minor` (наприклад, `259:3`). |
| `<offset>` | `segments[S].offset` | Фізичний зсув початку зашифрованих даних на носії у 512-байтних секторах ядра: `offset_bytes / 512` (наприклад, зсув `16777216` байтів транслюється у `32768` секторів). |
| `<#opt_params>` | `config.flags` / `sector_size` | Кількість додаткових прапорців та опцій конфігурації. |
| `<opt_params>` | `config.flags` / `integrity` | Список опціональних параметрів оптимізації продуктивності та налаштування розміру сектора. |

#### Специфікація опціональних параметрів драйвера (`opt_params`)

1. **`sector_size:<bytes>`:** встановлює логічний розмір сектора криптографічного перетворення (транслюється з `segments[S].sector_size`, наприклад `sector_size:4096`). Якщо параметр відсутній, ядро застосовує застарілий розмір 512 байтів. Застосування `sector_size:4096` на сучасних накопичувачах Advanced Format / NVMe знижує навантаження на обчислення векторів ініціалізації IV у 8 разів і збільшує лінійну швидкість читання/запису на 15–25%.
2. **`allow_discards`:** транслюється з прапорця `"allow-discards"` у `config.flags`. Дозволяє проходження запитів звільнення блоків TRIM / DISCARD від файлової системи через криптографічний шар до фізичного контролера SSD. За замовчуванням вимкнено з міркувань безпеки, оскільки вивільнені блоки видають карту заповнення файлової системи (leakage of filesystem allocation patterns).
3. **`same_cpu_crypt`:** транслюється з прапорця `"same-cpu-crypt"`. Примушує ядро виконувати шифрування та дешифрування блоків у контексті того самого процесорного ядра, що й запит вводу-виводу. Зменшує між'ядерні блокування пам'яті та мінімізує промахи кешу L1/L2.
4. **`submit_from_crypt_cpus`:** транслюється з прапорця `"submit-from-crypt-cpus"`. Дозволяє криптографічним робочим потокам ядра (`kcryptd`) відправляти зашифровані структури `struct bio` безпосередньо в чергу контролера накопичувача без зворотного перемикання контексту на процесор-ініціатор.
5. **`no_read_workqueue` / `no_write_workqueue`:** вимикає використання черг відкладеної обробки `kcryptd` для операцій читання та запису. Криптографічні інструкції (AES-NI, ARMv8 Crypto) виконуються синхронно у черзі запиту блокового пристрою, що критично знижує затримку (latency) на надшвидких NVMe-накопичувачах PCIe 4.0/5.0.
6. **`integrity:<tag_size>:<alg>`:** задає параметри взаємодії з нижнім шаром автентифікації `dm-integrity` (розмір тегу автентифікації на сектор та алгоритм HMAC/Poly1305).

#### Практичний приклад трансляції та дамп таблиці

Для сегмента з `segments[0]`:
```json
{
  "type": "crypt",
  "offset": "16777216",
  "size": "dynamic",
  "iv_tweak": "0",
  "encryption": "aes-xts-plain64",
  "sector_size": 4096,
  "flags": []
}
```
і накопичувача `/dev/nvme0n1p3` загальним обсягом 100 ГБ (209 715 200 секторів по 512 байтів), бібліотека розраховує:
* `offset_sectors = 16777216 / 512 = 32768`.
* `num_sectors = 209715200 - 32768 = 209682432`.

Результуючий рядок таблиці, що передається в системний виклик `ioctl(DM_TABLE_LOAD)`:

```
0 209682432 crypt aes-xts-plain64 a7f6e2c9...b5a3 0 /dev/nvme0n1p3 32768 2 allow_discards sector_size:4096
```

При перевірці стану активного пристрою утилітою `dmsetup table --showkeys /dev/mapper/cr_data` відображається саме цей згенерований рядок відображення.

### 7.4. Апаратне прискорення криптографії ядра (Crypto API / AES-NI / ARMv8 CE / RISC-V Zkn) та вибір шифрів блочного рівня

Підсистема `dm-crypt` не реалізує криптографічні алгоритми самостійно, а делегує всі обчислення підсистемі ядра **Linux Kernel Crypto API**. Під час створення тома або трансляції рядка таблиці Device Mapper драйвер обирає алгоритм блочного чи потокового шифрування, що визначає баланс між криптографічною стійкістю, накладними витратами процесора та пропускною здатністю підсистеми вводу-виводу.

```
┌───────────────────────────────────────────────────────────────────────────┐
│              АРХІТЕКТУРА KERNEL CRYPTO API ТА АПАРАТНИХ ПРИСКОРЮВАЧІВ     │
│                                                                           │
│   dm-crypt (kcryptd) ──▶ crypto_alloc_skcipher("xts(aes)", 0, 0)          │
│                                │                                          │
│                                ▼                                          │
│   Kernel Crypto API Subsystem (вибір за cra_priority)                     │
│   ├── Priority 500: xts-aes-vaes-avx512 (Intel Xeon / AMD EPYC 512-bit)   │
│   ├── Priority 400: xts-aes-aesni       (x86_64 AES-NI 128-bit)           │
│   ├── Priority 400: xts-aes-ce          (AArch64 ARMv8-A Crypto Neon)     │
│   ├── Priority 400: xts-aes-riscv64-zkn (RISC-V Vector/Scalar Zkn)        │
│   └── Priority 100: xts(aes-generic)    (Чистий C, fallback без векторів) │
└───────────────────────────────────────────────────────────────────────────┘
```

#### 7.4.1. Специфікація алгоритмів шифрування у сегментах LUKS2

1. **`aes-xts-plain64` (Стандарт галузі за замовчуванням):**
   * **Математична модель:** симетричний блоковий шифр AES (FIPS PUB 197) у режимі XTS (IEEE Std 1619-2007). Розмір базового блоку криптоперетворення становить рівно 128 бітів (16 байтів).
   * **Розмір ключа:** 256 або 512 бітів. У конфігурації `aes-xts-plain64` із розміром ключа 512 бітів (`key_size: 64` у JSON) Master Key фактично складається з двох незалежних 256-бітних симетричних ключів: ключа шифрування корисних даних `K₁` та ключа шифрування твіка (вектора зміщення) `K₂`.
   * **Генератор IV `plain64`:** обчислює 64-бітний вектор ініціалізації у форматі Little-Endian на основі логічного номера сектора:
     ```
     IV = sector_number + iv_tweak
     T = AES_Encrypt(K₂, IV) ⊗ αʲ
     C = AES_Encrypt(K₁, P ⊕ T) ⊕ T
     ```
     де `P` — блок відкритого тексту, `C` — шифротекст, `T` — значення твіка, `α` — примітивний елемент поля Галуа `GF(2¹²⁸)`, а `j` — порядковий номер 16-байтового блоку всередині сектора.
   * **Інженерні властивості:** ідеально підходить для накопичувачів довільного доступу (NVMe/SSD). Модифікація чи пошкодження одного сектора не впливає на здатність ядра розшифрувати сусідні сектори (відсутність міжсекторного розповсюдження помилок).

2. **`chacha20-poly1305` (`capi:chacha20-poly1305-plain64`):**
   * **Математична модель:** швидкісний потоковий шифр ChaCha20 (RFC 8439) у поєднанні з одноразовим автентифікатором Poly1305.
   * **Внутрішня архітектура:** побудований на ARX-перетвореннях (Addition-Rotation-XOR) над 32-бітними машинними словами, що усуває потребу в апаратних таблицях заміни (S-box) і повністю нівелює вразливості до атак за часом кешу процесора (Cache-Timing Attacks).
   * **Область застосування:** процесори без апаратних блоків прискорення AES (бюджетні ARM SoC Cortex-A53/Cortex-A7, архітектури MIPS, мікрокомп'ютери IoT, старі процесори x86). На таких платформах ChaCha20 забезпечує у 3.5–4.5 раза вищу пропускну здатність, ніж програмна емуляція AES.

3. **`sm4-xts-plain64`:**
   * **Математична модель:** 128-бітний блоковий шифр національного комерційного криптографічного стандарту Китаю (GB/T 32907-2016) у режимі XTS.
   * **Внутрішня архітектура:** 32-раундова нелінійна зворотна структура Фейстеля з 128-бітним ключем (у режимі XTS використовується пара 128-бітних ключів загальною довжиною 256 бітів).
   * **Апаратна інтеграція:** підтримується спеціалізованими інструкціями в новітніх мікроархітектурах (інструкції SM4-NI у процесорах Intel Alder Lake/Raptor Lake, розширення ARMv8.4-A SM4, векторні інструкції RISC-V `Zks`). Застосовується в ізольованих інфраструктурах із вимогами китайської державної сертифікації безпеки.

#### 7.4.2. Апаратні інструкційні набори та мікроархітектурна оптимізація

Сучасні процесори інтегрують виділені конвеєри для виконання криптографічних операцій на швидкості оперативної пам'яті:

* **Архітектура x86_64 (Intel / AMD):**
  * **`AES-NI` (128-бітні регістри `xmm`):** набір базових інструкцій `AESENC`, `AESENCLAST`, `AESDEC`, `AESDECLAST`, `AESKEYGENASSIST`, `AESIMC`. Кожна інструкція виконує повний раунд перетворень (SubBytes + ShiftRows + MixColumns + AddRoundKey) за 3–4 такти процесора з пропускною здатністю 1 такт/інструкція завдяки глибокому конвеєру.
  * **`VAES` (Vector AES) + `AVX-512` / `AVX2` (256/512-бітні регістри `ymm`/`zmm`):** векторне розширення, що дозволяє інструкції `VAESENC` одночасно обробляти чотири 128-бітні блоки AES у 512-бітному регістрі `zmm`. Це підвищує лінійну швидкість дешифрування секторів ядра до 14–18 ГБ/с на одне процесорне ядро.
  * **`VPCLMULQDQ` / `PCLMULQDQ`:** апаратне безпереносне множення многочленів над полем `GF(2⁶⁴)` для прискорення розрахунку гешів GHASH (AES-GCM) та Poly1305.

* **Архітектура AArch64 (ARMv8-A / ARMv9-A):**
  * **`ARMv8 Crypto Extensions (CE)` (128-бітні векторні регістри Neon `v0..v31`):** інструкції `AESE` (AddRoundKey + SubBytes + ShiftRows) та `AESMC` (MixColumns) для прямого шифрування, а також `AESD` та `AESIMC` для зворотного дешифрування. Пара інструкцій `AESE + AESMC` виконує раунд AES за 2 такти.
  * **`PMULL` / `PMULL2`:** безпереносне поліноміальне множення Neon для автентифікованих режимів.
  * **`SVE2 Crypto Extensions`:** масштабовані векторні інструкції з підтримкою динамічної ширини вектора від 128 до 2048 бітів.

* **Архітектура RISC-V (RV64GC):**
  * **Скалярне розширення `Zkn` (NIST Suite):**
    * `Zkne` (Encryption): інструкції `aes64es` (раунд шифрування) та `aes64esm` (раунд шифрування з MixColumns).
    * `Zknd` (Decryption): інструкції `aes64ds` (раунд дешифрування), `aes64dsm` (дешифрування з InvMixColumns) та `aes64im` (InvMixColumns).
    * `Zknh` (SHA-2): прискорення інструкціями `sha256sig0`, `sha256sig1`, `sha256sum0`, `sha256sum1`.
    * `Zbkb` / `Zkbc`: крос-перестановки байтів та безпереносне множення.
  * **Векторне розширення `Zvkned` / `Zvknhb`:** виконує паралельне раундове шифрування векторів блоків безпосередньо у векторному співпроцесорі (VPU).

#### 7.4.3. Реєстрація та арбітраж драйверів у Kernel Crypto API

Інформація про всі зареєстровані криптографічні модулі ядра публікується у віртуальній файловій системі `/proc/crypto`:

```bash
# Перевірка активних реалізацій режиму XTS-AES у системі
cat /proc/crypto | grep -A 8 -B 2 "xts(aes)"
```

Типовий запис містить наступні ключові атрибути:

```text
name         : xts(aes)
driver       : xts-aes-vaes-avx512
module       : kernel
priority     : 500
refcnt       : 2
selftest     : passed
type         : skcipher
async        : no
blocksize    : 16
min keysize  : 32
max keysize  : 64
ivsize       : 16
chunksize    : 16
walksize     : 64
```

* **Поле `driver`:** показує конкретну апаратно-оптимізовану реалізацію драйвера.
* **Поле `priority`:** числовий пріоритет драйвера. При виклику `crypto_alloc_skcipher("xts(aes)", 0, 0)` ядро автоматично підключає драйвер із найвищим пріоритетом. Наприклад, драйвер `xts-aes-vaes-avx512` має пріоритет `500`, звичайний `xts-aes-aesni` — `400`, а базовий C-код `xts(aes-generic)` — лише `100`.
* **Поле `async`:** прапорець асинхронності. Якщо значення `yes`, операції передаються апаратному DMA-акселератору (Intel QAT, AMD CCP, ARM CryptoCell). Для синхронних CPU-інструкцій (AES-NI, ARM CE) значення дорівнює `no`.

### 7.5. Стек цілісності VFS: взаємодія LUKS2/dm-integrity із підсистемами IMA та EVM

Хоча підсистеми `dm-crypt` та `dm-integrity` у складі LUKS2 забезпечують повний захист конфіденційності та автентичності на рівні блокового пристрою, вони принципово не контролюють логічний рівень файлової системи (VFS). Інтеграція LUKS2 із підсистемами ядра Linux **IMA (Integrity Measurement Architecture)** та **EVM (Extended Verification Module)** формує наскрізний ешелонований захист (Defense-in-Depth) від блокового носія до простору виконання процесів.

```
┌───────────────────────────────────────────────────────────────────────────┐
│              ПОШАРОВИЙ СТЕК БЕЗПЕКИ ТА ЦІЛІСНОСТІ LINUX                   │
│                                                                           │
│   [Простір виконання]  execve("/usr/bin/sudo") / open(O_RDONLY)           │
│                               │                                           │
│                               ▼                                           │
│   [Підсистема IMA]     Перевірка хешу/підпису xattr security.ima          │
│                        (Автентичність двійкового коду файлу)              │
│                               │                                           │
│                               ▼                                           │
│   [Підсистема EVM]     Перевірка HMAC / цифрового підпису security.evm    │
│                        (Захист інода, прав доступу та xattr security.*)   │
│                               │                                           │
│                               ▼                                           │
│   [Рівень VFS]         ext4 / xfs / btrfs (структура файлів та каталогів) │
│                               │                                           │
│                               ▼                                           │
│   [Шар dm-integrity]   Контроль автентичності 4K-секторів (HMAC-SHA256)   │
│                        (Захист від bit-flipping та offline модифікації)   │
│                               │                                           │
│                               ▼                                           │
│   [Шар dm-crypt]       Розшифрування секторів AES-256-XTS (LUKS2)         │
│                        (Конфіденційність даних на носії)                  │
│                               │                                           │
│                               ▼                                           │
│   [Апаратний диск]     Фізичні LBA-сектори NVMe SSD / SATA                │
└───────────────────────────────────────────────────────────────────────────┘
```

#### 7.5.1. Розмежування обов'язків: блоковий рівень проти файлового рівня

* **Чому одного `dm-integrity` недостатньо:**
  Підсистема `dm-integrity` контролює цілісність окремих секторів блокового диска (LBA). Вона надійно блокує спроби атак із модифікації шифротексту на вимкненому комп'ютері. Проте `dm-integrity` не володіє семантикою файлової системи: якщо зловмисник, отримавши тимчасові права користувача у запущеній системі, підмінить бінарний файл `/usr/bin/login` або оновить файл конфігурації `/etc/sudoers`, драйвер файлової системи викличе штатний запис через VFS. `dm-integrity` розрахує новий валідний HMAC сектора й запише його на диск, легітимізуючи несанкціоновану зміну файлу.
* **Чому IMA/EVM потребують захищеного криптографічного сховища LUKS2:**
  Підсистеми IMA/EVM зберігають контрольні геші та цифрові підписи у розширених атрибутах файлів (**Extended Attributes, xattr**): `security.ima` та `security.evm`. Якщо базова файлова система лежить на відкритому незашифрованому диску, зловмисник може офлайн підключити диск до іншого хоста й безперешкодно перепідписати атрибути або вилучити захисні прапорці. LUKS2 та `dm-integrity` унеможливлюють несанкціоноване читання та підміну службових блоків на апаратному рівні.

#### 7.5.2. Специфікація та механіка підсистеми IMA (Integrity Measurement Architecture)

Підсистема IMA функціонує у двох взаємодоповнюючих режимах:

1. **`IMA-measurement` (Протоколювання вимірювань довіреного завантаження):**
   * Перед передачею керування будь-якому бінарному файлу (`execve`), динамічній бібліотеці (`mmap(PROT_EXEC)`) чи образу ядра (`kexec_load`) ядро обчислює криптографічний геш вмісту файлу (типово SHA-256).
   * Запис додається у захищений кільцевий список вимірювань ядра `/sys/kernel/security/ima/ascii_runtime_measurements`.
   * Дайджест вимірювання відправляється в апаратний чип TPM 2.0 для розширення регістру конфігурації платформи **PCR 10** (`TPM2_PCR_Extend`). Віддалений сервер верифікації (Remote Attestation Server) може отримати підписану квоту TPM2 (`TPM2_Quote`) та звірити ланцюг вимірювань, математично довівши, що на вузлі не виконувався сторонній програмний код.

2. **`IMA-appraisal` (Локальна оцінка та блокування непідписаних файлів):**
   * Ядро перевіряє вміст розширеного атрибута `security.ima` перед кожним відкриттям файлу на виконання або читання:
     * **Режим гешу (`ima_hash`):** атрибут містить рядок виду `0x01 || SHA256(file_content)`. Ядро звіряє розрахований геш із записаним у xattr.
     * **Режим цифрового підпису (`ima_signature`):** атрибут містить заголовок `0x03` та бінарний цифровий підпис RSA-2048/4096 або ECDSA, створений закритим ключем дистрибутива. Ядро перевіряє підпис за допомогою відкритого X.509 сертифіката, завантаженого в системну ключницю ядра **`.ima`** або **`.builtin_trusted_keys`**.
   * Якщо геш не збігається або цифровий підпис недійсний, ядро негайно перериває виклик `execve()` або `open()` з помилкою **`-EACCES` (Permission denied)** або **`-EPERM` (Operation not permitted)**.

#### 7.5.3. Специфікація та механіка підсистеми EVM (Extended Verification Module)

Підсистема EVM захищає від підміни розширені атрибути xattrs та службові метадані інода.

```
┌───────────────────────────────────────────────────────────────────────────┐
│              СТРУКТУРА ДАНИХ ОБЧИСЛЕННЯ ДАЙДЖЕСТУ EVM                     │
│                                                                           │
│ ┌───────────────────────────────────────────────────────────────────────┐ │
│ │ МЕТАДАНІ ІНОДА VFS:                                                   │ │
│ │  • i_ino (Номер інода)              • i_generation (Номер генерації)  │ │
│ │  • i_uid (Ідентифікатор власника)   • i_gid (Ідентифікатор групи)     │ │
│ │  • i_mode (Бітова маска прав доступу)                                 │ │
│ ├───────────────────────────────────────────────────────────────────────┤ │
│ │ ЗАХИЩЕНІ РОЗШИРЕНІ АТРИБУТИ (XATTRS):                                 │ │
│ │  • security.ima        (Геш або підпис виконавчого коду IMA)          │ │
│ │  • security.selinux    (Контекст безпеки SELinux)                     │ │
│ │  • security.SMACK64    (Мітка безпеки Smack)                          │ │
│ │  • security.apparmor   (Профіль AppArmor)                             │ │
│ │  • security.capability (Linux POSIX Capabilities, наприклад cap_net_raw│ │
│ └───────────────────────────────────────────────────────────────────────┘ │
│                                    │                                      │
│                                    ▼                                      │
│                HMAC-SHA256(Ключ .evm) / RSA Signature                     │
│                                    │                                      │
│                                    ▼                                      │
│                  Розширений атрибут: security.evm                         │
└───────────────────────────────────────────────────────────────────────────┘
```

1. **Склад структури EVM:**
   EVM обчислює контрольний HMAC-SHA256 або цифровий підпис над неперервним бінарним блоком, до якого входять:
   * Номер інода файлової системи `i_ino` та лічильник покоління `i_generation`.
   * Ідентифікатор користувача-власника `i_uid` та групи `i_gid`.
   * Біти режиму доступу `i_mode` (права `rwxr-xr-x`, біти SUID/SGID).
   * Список та бінарні значення всіх розширених атрибутів простору безпеки (`security.ima`, `security.selinux`, `security.capability` тощо).
2. **Захист від атак підміни атрибутів (Attribute Transplantation Attacks):**
   Оскільки до розрахунку HMAC включено номер інода `i_ino` та номер генерації `i_generation`, зловмисник не може скопіювати валідний атрибут `security.ima` та `security.evm` з легітимного системного бінарника (наприклад, `/bin/ls`) і прикріпити його до модифікованого шкідливого бінарного файлу. Спроба зміни прав доступу файлу (наприклад, додавання SUID-біта командою `chmod u+s`) миттєво інвалідує `security.evm` і блокує доступ до файлу.

#### 7.5.4. Практична конфігурація та налаштування стеку IMA/EVM поверх LUKS2

:::code api-luks2-json-metadata/sh/ima-evm-enroll.sh

Активація політик ядра здійснюється через параметри командного рядка під час завантаження:
```text
ima_policy=appraise_tcb ima_appraise=enforce evm=enforce
```
* `ima_policy=appraise_tcb` — обов'язкова перевірка цілісності всіх файлів, що належать користувачу `root` (Trusted Code Base).
* `ima_appraise=enforce` — блокування виконання файлів із недійсними або відсутніми підписами `security.ima` (замість простого попередження у системний журнал).
* `evm=enforce` — повна перевірка та блокування модифікації розширених атрибутів xattrs при невідповідності `security.evm`.

## 8. Словник `config` (Системна конфігурація та вимоги)

Словник `config` містить глобальні параметри виділених буферів пам'яті та список обов'язкових вимог (`requirements`) до версії драйвера.

```json
"config": {
  "json_size": "4190208",
  "keyslots_size": "12582912",
  "flags": [
    "allow-discards"
  ],
  "requirements": [
    "online-reencrypt-v2"
  ]
}
```

### Специфікація полів словника `config`

* **`json_size` (String):** точний розмір області пам'яті в байтах, виділеної під текстовий JSON-документ (за замовчуванням `4190208` = 4 МіБ мінус 4 КіБ бінарного дескриптора).
* **`keyslots_size` (String):** сумарний розмір бінарної області носія, зарезервованої під розміщення смуг слотів ключів AFSplit (наприклад, `12582912` = 12 МіБ або `25165824` = 24 МіБ).
* **`flags` (Array of Strings):** інформаційні прапорці продуктивності та планування вводу-виводу:
  * `"allow-discards"` — дозволено проходження команд TRIM/DISCARD до фізичного SSD.
  * `"same-cpu-crypt"` — виконання шифрування на тому ж ядрі процесора, що й запит вводу-виводу.
  * `"submit-from-crypt-cpus"` — оптимізація черги блокового планувальника.
  * `"no-read-workqueue"` — пряма обробка читання в контексті переривання без черги ядра.
  * `"no-write-workqueue"` — пряма обробка запису без черги ядра.
* **`requirements` (Array of Strings):** перелік обов'язкових розширень. **Якщо ядро або бібліотека `libcryptsetup` зустрічає в цьому масиві невідомий їй рядок, операція відкриття тома негайно блокується з критичною помилкою**. Це захищає том від пошкодження застарілими версіями утиліт:
  * `"online-reencrypt-v2"` — том перебуває у процесі онлайн-перешифрування новою схемою.
  * `"direct-key"` — пряме використання ключів без шару розщеплення AFSplit.
  * `"integrity"` — наявність обов'язкового шару `dm-integrity`.
  * `"unbound-keyslots"` — підтримка шпарин, не прив'язаних до жодного дайджесту.

## 10. Утиліти маніпуляцій та системні команди

Керування низькорівневими структурами LUKS2 у просторі користувача Linux здійснюється утилітами `cryptsetup`, `systemd-cryptenroll` та `clevis`.

### 10.1. Форматування тома (`cryptsetup luksFormat`)

:::code api-luks2-json-metadata/sh/luks2-format.sh

* `--type luks2` — створення тому за специфікацією LUKS2 (з двома заголовками та JSON-метаданими).
* `--cipher aes-xts-plain64` — алгоритм та режим шифрування секторів корисного навантаження.
* `--key-size 512` — повний розмір симетричного ключа Master Key у бітах (для AES-256-XTS використовується два 256-бітні ключі = 512 бітів = 64 байти).
* `--pbkdf argon2id` — використання пам'ятемісткого алгоритму Argon2id замість PBKDF2.
* `--pbkdf-memory 1048576` — фіксація ліміту пам'яті у 1024 МіБ (1 ГБ) для захисту від паралельних атак на GPU/ASIC.
* `--pbkdf-parallel 4` — кількість обчислювальних потоків KDF.
* `--iter-time 4000` — цільовий час бенчмарку підбору ітерацій KDF у мілісекундах (4 секунди).
* `--sector-size 4096` — встановлення апаратного розміру сектора криптографічного перетворення (усуває оверхед 512-байтних емуляцій).

### 10.2. Інспекція та експорт JSON-метаданих (`cryptsetup luksDump`)

```bash
# Текстовий звіт про бінарний заголовок, слоти, токени та сегменти
cryptsetup luksDump /dev/nvme0n1p3

# Експорт чистого JSON-документа метаданих у файл або конвеєр
cryptsetup luksDump --dump-json-metadata /dev/nvme0n1p3 | jq .
```

### 10.3. Резервне копіювання та відновлення заголовків (`luksHeaderBackup` / `luksHeaderRestore`)

Оскільки заголовок містить ключові структури AFSplit та Master Key, його резервна копія дозволяє миттєво відновити доступ до даних у разі пошкодження перших секторів пристрою:

```bash
# Створення бінарного дампу заголовка та смуг ключів у файл
cryptsetup luksHeaderBackup /dev/nvme0n1p3 --header-backup-file /root/luks2_header_nvme0n1p3.img

# Відновлення метаданих із файлу резервної копії на блоковий пристрій
cryptsetup luksHeaderRestore /dev/nvme0n1p3 --header-backup-file /root/luks2_header_nvme0n1p3.img
```

> ⚠️ **Безпека відновлення.** Відновлення старого заголовка з резервної копії відновлює також усі паролі та ключі, які були видалені після дати створення бекапу. Якщо пароль було скомпрометовано й замінено, відновлення старого заголовка знову зробить скомпрометований пароль дійсним.

### 10.4. Керування токенами (`cryptsetup token`)

Утиліта дозволяє маніпулювати сирими JSON-об'єктами токенів безпосередньо:

```bash
# Перегляд усіх активних токенів у томі
cryptsetup token list /dev/nvme0n1p3
# Видалення токена з ідентифікатором 0
cryptsetup token remove --token-id 0 /dev/nvme0n1p3
# Імпорт користувацького токена із JSON-файлу
cryptsetup token import --token-id 1 /dev/nvme0n1p3 < custom_token.json
# Відкриття тома за допомогою зареєстрованого токена
cryptsetup token open /dev/nvme0n1p3 crypt_volume
```

### 10.5. Миттєве знищення слота ключа (`cryptsetup luksKillSlot`)

Команда `luksKillSlot` безповоротно знищує окрему замкову шпарину:

```bash
# Миттєве стирання шпарини 2 та занулення відповідних смуг AFSplit на диску
cryptsetup luksKillSlot /dev/nvme0n1p3 2
```

Операція виконує наступні кроки:
1. Занулює область `area` на диску, де зберігалися смуги AFSplit шпарини 2.
2. Видаляє опис шпарини `"2"` зі словника `keyslots` у JSON-метаданих.
3. Видаляє індекс `"2"` з масивів `keyslots` у словниках `digests` та `tokens`.
4. Інкрементує лічильник `seqid` на 1 та транзакційно записує оновлені заголовки.

### 10.9. Специфікація онлайн-зміни розміру тома (`cryptsetup resize`)

LUKS2 підтримує динамічну зміну геометрії криптографічного пристрою на льоту без зупинки вводу-виводу (Zero-Downtime Online Resize).

```
┌───────────────────────────────────────────────────────────────────────────┐
│                 ПРОТОКОЛ ОНЛАЙН-РОЗШИРЕННЯ ТОМА LUKS2                     │
│                                                                           │
│  1. Збільшення фізичного розділу/LUN (fdisk / parted / growpart / lvextend│
│                                │                                          │
│                                ▼                                          │
│  2. Виклик: cryptsetup resize <dm_name>                                   │
│     ├── Запит нового розміру базового пристрою ioctl(BLKGETSIZE64)        │
│     ├── Перевірка segments[0].size == "dynamic"                           │
│     ├── Розрахунок num_sectors = (new_device_size - offset) / 512         │
│     ├── (Якщо активний dm-integrity) dmsetup message <int_dev> 0 resize   │
│     ├── Формування оновленого рядка таблиці dm-crypt                      │
│     ├── Завантаження таблиці ioctl(DM_TABLE_LOAD)                         │
│     └── Атомарний Resume ioctl(DM_DEV_SUSPEND без біта призупинення)     │
│                                │                                          │
│                                ▼                                          │
│  3. Розширення файлової системи (resize2fs / xfs_growfs)                  │
└───────────────────────────────────────────────────────────────────────────┘
```

#### Покроковий алгоритм розширення тома (Online Growth):

1. **Збільшення базового дискового носія:** адміністратор розширює базовий фізичний розділ або логічний том LVM:
   ```bash
   growpart /dev/nvme0n1 3
   # або для LVM: lvextend -L +100G /dev/vg_storage/lv_data
   ```
2. **Оновлення криптографічного відображення:**
   ```bash
   cryptsetup resize secure_storage
   # або з явної фіксацією кількості 512-байтних секторів:
   cryptsetup resize --size 419430400 secure_storage
   ```
   * Бібліотека `libcryptsetup` надсилає системний виклик `ioctl(BLKGETSIZE64)` до базового диска.
   * Розраховує нову кількість доступних секторів: `num_sectors = (device_size - segments[0].offset) / 512`.
   * Завантажує нову цільову таблицю Device Mapper через `ioctl(DM_TABLE_LOAD)` та виконує Resume без переривання дискових черг.
3. **Розширення файлової системи на активному томі:**
   ```bash
   # Для файлової системи ext4:
   resize2fs /dev/mapper/secure_storage

   # Для файлової системи XFS:
   xfs_growfs /mnt/secure_mountpoint
   ```

#### Специфікація стискання тома (Volume Shrink):

Операція стискання вимагає суворого дотримання послідовності кроків, щоб уникнути зрізання корисних секторів файлової системи:
1. Стискання файлової системи (підтримується в `ext4`, не підтримується в `XFS`):
   ```bash
   resize2fs /dev/mapper/secure_storage 50G
   ```
2. Стискання криптографічного відображення `dm-crypt` (розмір вказується у 512-байтних секторах, наприклад $50\text{ ГБ} \times 1024^3 / 512 = 104857600$ секторів):
   ```bash
   cryptsetup resize --size 104857600 secure_storage
   ```
3. Стискання базового блокового пристрою LVM / розділу:
   ```bash
   lvreduce -L 50G /dev/vg_storage/lv_data
   ```

### 10.10. Специфікація міграції та конвертації форматів LUKS1 ↔ LUKS2 (`cryptsetup convert`)

Утиліта `cryptsetup convert` дозволяє здійснювати in-place конвертацію службових заголовків на диску без перешифрування та переміщення терабайтів корисних даних.

```
┌───────────────────────────────────────────────────────────────────────────┐
│               СПЕЦИФІКАЦІЯ КОНВЕРТАЦІЇ LUKS1 ──▶ LUKS2                    │
│                                                                           │
│  Вхідний LUKS1: [ phdr (592B) ] [ 8 Keyslots (AFSplit) ] [ Payload (2M) ] │
│                                │                                          │
│                                ▼                                          │
│  1. Зчитування 592-байтної структури luks_phdr                            │
│  2. Визначення доступного зміщення payload_offset (наприклад, 4096 сект)  │
│  3. Розрахунок компактного hdr_size під наявне вікно (наприклад, 256 КіБ) │
│  4. Трансляція luks_keyslot[0..7] у JSON-об'єкти keyslots["0".."7"]       │
│  5. Перенесення mk_digest у словник digests["0"]                          │
│  6. Формування дескриптора segments["0"] із вказаним offset               │
│  7. Атомарний запис первинного і вторинного заголовків LUKS2              │
└───────────────────────────────────────────────────────────────────────────┘
```

#### 1. Міграція зі старого формату LUKS1 на LUKS2 (`LUKS1 -> LUKS2`)

```bash
# Обов'язкове попереднє резервне копіювання заголовка
cryptsetup luksHeaderBackup /dev/nvme0n1p3 --header-backup-file luks1_backup.img

# Конвертація закритого тома
cryptsetup convert --type luks2 /dev/nvme0n1p3
```

* **Особливість геометрії зміщення:** у чистому LUKS2 заголовки разом із ключовою зоною за замовчуванням займають 16 МіБ (4 МіБ первинний + 4 МіБ вторинний + 8 МіБ слоти). У старих розділах LUKS1 корисні дані `payload_offset` часто починалися вже за зсувом 2 МіБ (4096 секторів) або 4 МіБ. Утиліта `cryptsetup convert` не зрушує дані розділу: вона автоматично розраховує компактний розмір службової зони `hdr_size` (наприклад, 256 КіБ або 1 МіБ) та `keyslots_size`, які повністю вміщуються у наявний проміжок перед `payload_offset`.
* **Трансляція слотів та дайджестів:** кожен активний слот `struct luks_keyslot` перетворюється на об'єкт `keyslots[K]` із типом `"luks2"`, параметрами KDF `"pbkdf2"` та схемою розсіювання `af: {"type": "luks1", "stripes": 4000, "hash": "sha1"|"sha256"}`. Параметри старого `mk_digest` записуються в об'єкт `digests["0"]`.
* Після успішної конвертації користувач може перевести слоти ключів на Argon2id:
  ```bash
  cryptsetup luksChangeKey --pbkdf argon2id /dev/nvme0n1p3 --key-slot 0
  ```

#### 2. Зворотна конвертація (Даунгрейд) з LUKS2 на LUKS1 (`LUKS2 -> LUKS1`)

```bash
cryptsetup convert --type luks1 /dev/nvme0n1p3
```

**Суворі інваріанти та перевірки сумісності (Pre-flight checks):**
1. **Заборона Argon2:** усі активні слоти ключів зобов'язані використовувати `kdf.type == "pbkdf2"`. Якщо хоча б один слот використовує `argon2id` або `argon2i`, `cryptsetup` блокує конвертацію з помилкою: `Keyslot uses Argon2, which is unsupported in LUKS1`. Необхідно заздалегідь замінити KDF: `cryptsetup luksChangeKey --pbkdf pbkdf2 /dev/nvme0n1p3 --key-slot <N>`.
2. **Відсутність токенів:** словник `tokens` зобов'язаний бути порожнім `{}` (усі прив'язки TPM2, FIDO2, Clevis необхідно видалити через `cryptsetup token remove`).
3. **Відсутність перевірки цілісності:** у словнику `segments` не повинно бути об'єкта `integrity` (шар `dm-integrity` відсутній у LUKS1).
4. **Обмеження кількості шпарин:** кількість активних слотів не може перевищувати 8 (максимум для бінарного заголовка LUKS1).
5. **Розмір сектора:** `sector_size` зобов'язаний дорівнювати 512 байтам (LUKS1 не підтримує 4096-байтні сектори криптоперетворення в заголовку).
6. **Відсутність незавершеного перешифрування:** масив `requirements` не повинен містити прапорець `"online-reencrypt-v2"`.

### 1. Перевірка бінарного дескриптора `luks2_hdr_disk`

* **Сигнатура `magic`:** зобов'язана бути строго рівною `"LUKS\xba\xbe"`. Якщо виявлено `"SKUL\xba\xbe"`, екземпляр вважається незавершеною транзакцією і відкидається.
* **Версія `version`:** значення зобов'язане дорівнювати `2`.
* **Фізичний зсув `hdr_offset`:** значення зобов'язане точно збігатися з фактичною точкою зміщення читання (`0` для первинного, `hdr_size` для вторинного).
* **Контрольна сума `csum`:** результат обчислення `csum_alg(дескриптор || json)` при тимчасово зануленому полі `csum` і доданій солі `salt` зобов'язаний побайтово збігатися зі значенням у дескрипторі. Якщо виявлено невідповідність, повертається помилка пошкодження метаданих.

### 2. Валідація JSON-документа

* **Розмір:** довжина рядка JSON не може перевищувати `json_size` (`hdr_size - 4096`).
* **Занулення залишку:** усі байти після кінцевої закриваючої дужки `}` аж до кінця буфера `json_size` зобов'язані містити виключно байти `0x00`. Наявність будь-яких сторонніх даних викликає помилку відмови валідації.
* **Синтаксис:** документ зобов'язаний бути коректним UTF-8 об'єктом без повторюваних ключів.

### 3. Перехресна цілісність посилань (Referential Integrity)

* Кожен числовий індекс у масиві `digests[D].keyslots` зобов'язаний існувати як ключ у словнику `keyslots`.
* Кожен числовий індекс у масиві `digests[D].segments` зобов'язаний існувати у словнику `segments`.
* Кожен числовий індекс у масиві `tokens[T].keyslots` зобов'язаний існувати у словнику `keyslots`.
* Наявність висячих посилань або замкнених циклічних залежностей блокує ініціалізацію тома з кодом помилки `-EINVAL`.

### 4. Контроль перекриття дискових областей (Area Collision Check)

Бібліотека перевіряє просторові межі всіх дискових ділянок і гарантує відсутність колізій:
* `[0 .. hdr_size)` — Первинний заголовок та JSON.
* `[hdr_size .. 2 · hdr_size)` — Вторинний заголовок та JSON.
* `[keyslots[K].area.offset .. keyslots[K].area.offset + keyslots[K].area.size)` — Області смуг кожної активної шпарини. Вони не можуть перекриватися між собою і не можуть заходити у службову зону заголовків `[0 .. 2 · hdr_size)`.
* `[segments[S].offset .. end)` — Сегменти даних, які зобов'язані починатися за межами `keyslots_size`.

### 5. Обробка прапорців та вимог `requirements`

* Якщо словник `config` містить невідомий рядок у масиві `requirements`, драйвер негайно повертає код помилки `-EINVAL` (`Invalid argument`) і блокує відкриття пристрою, запобігаючи незворотному пошкодженню даних через несумісність форматів.

### Таблиця системних кодів помилок

| Код помилки | Символьна назва | Причина виникнення у LUKS2 |
| :--- | :--- | :--- |
| `-EINVAL` | `Invalid argument` | Порушення схеми JSON, невідома вимога у `requirements`, перекриття областей або невідповідність `hdr_offset`. |
| `-EPERM` | `Operation not permitted` | Невірний пароль, незбіг контрольного дайджесту у словнику `digests` або відхилення авторизації TPM2/FIDO2/Clevis. |
| `-ENOENT` | `No such file or directory` | Вказаний ідентифікатор слота, токена чи сегмента відсутній у метаданих. |
| `-EBADSLT` | `Invalid slot` | Спроба звернення до деактивованого або пошкодженого слота ключа. |
| `-EEXIST` | `File exists` | Спроба створення слота чи токена з ідентифікатором, який уже зайнятий. |
| `-ENOSPC` | `No space left on device` | Недостатньо місця в області `keyslots_size` для виділення нової зони `area` або вичерпано ліміт `json_size`. |
| `-EBUSY` | `Device or resource busy` | Спроба модифікації метаданих або зміни розміру сегмента під час активного процесу онлайн-перешифрування або змонтованого носія. |
| `-EILSEQ` | `Illegal byte sequence` | Незбіг контрольного автентифікаційного тегу (HMAC/Poly1305) у секторі підсистеми `dm-integrity` (спроба модифікації шифротексту або збій живлення в режимі `none`). |
| `-ERANGE` | `Numerical result out of range` | Запитаний розмір при `cryptsetup resize` перевищує фізичну місткість носія або виходить за межі вирівнювання секторів. |
| `-EOPNOTSUPP` / `-ENOTSUP` | `Operation not supported` | Спроба конвертації LUKS2 у LUKS1 за наявності Argon2, токенів або `dm-integrity`. |

## 12. Сценарії аварійного відновлення та низькорівневої реконструкції заголовків LUKS2

Пошкодження службових областей накопичувача (биті сектори на початку диска, збої контролера SSD або випадковий запис утилітою `dd`) призводить до помилок верифікації контрольних сум або порушення структури JSON. Завдяки наявності двох незалежних копій метаданих та відкритого формату текстового опису, LUKS2 дозволяє виконати повну діагностику та покрокове відновлення тома.

### 12.1. Низькорівнева інспекція структури через `hexdump` і `dd`

Для діагностики пошкоджень виконується поблокове вивантаження первинного (зсув 0) та вторинного (зсув 4 МіБ = 4 194 304 байти) заголовків у тимчасові файли:

```bash
# Дамп первинного 4-мегабайтного блоку метаданих
dd if=/dev/nvme0n1p3 of=primary_hdr.bin bs=4096 count=1024

# Дамп вторинного 4-мегабайтного блоку метаданих (пропуск 4 МіБ = 1024 блоки по 4 КіБ)
dd if=/dev/nvme0n1p3 of=secondary_hdr.bin bs=4096 skip=1024 count=1024
```

#### Побайтовий аналіз бінарного дескриптора `luks2_hdr_disk`

Перевірка перших 512 байтів дескриптора здійснюється утилітою `hexdump -C`:

```bash
hexdump -C -n 512 primary_hdr.bin
```

Ключові діагностичні точки перевірки:
1. **Зсув `0x0000..0x0005` (`magic`):** зобов'язаний містити байти `4c 55 4b 53 ba be` (`"LUKS\xba\xbe"`). Якщо виявлено `53 4b 55 4c ba be` (`"SKUL\xba\xbe"`), запис первинного заголовка було перервано збоєм живлення.
2. **Зсув `0x0006..0x0007` (`version`):** значення `00 02` (версія 2 у Big-Endian).
3. **Зсув `0x0008..0x000F` (`hdr_size`):** значення `00 00 00 00 00 40 00 00` (4 МіБ = 4 194 304 байти).
4. **Зсув `0x0010..0x0017` (`seqid`):** 64-бітне значення лічильника транзакцій. Порівнюється зі значенням `seqid` у вторинному заголовку.
5. **Зсув `0x0048..0x0067` (`csum_alg`):** ASCII-рядок алгоритму гешування (наприклад, `73 68 61 32 35 36 00...` для `"sha256"`).
6. **Зсув `0x0068..0x00A7` (`salt`):** 64 байти випадкової солі контрольної суми.
7. **Зсув `0x0104..0x010B` (`hdr_offset`):** очікуване зміщення дескриптора на диску. Для первинного заголовка зобов'язане бути `00 00 00 00 00 00 00 00`, для вторинного — `00 00 00 00 00 40 00 00`.
8. **Зсув `0x01C0..0x01DF` (`csum`):** 32 байти актуального збереженого дайджесту SHA-256.

#### Вилучення та синтаксичний аналіз текстового JSON

Текстова область починається за зсувом `4096` (`0x1000`). Її можна вилучити та передати у валідатор `jq`:

```bash
# Вилучення області JSON і перевірка валідності синтаксису
dd if=primary_hdr.bin bs=4096 skip=1 count=1023 2>/dev/null | tr -d '\0' | jq .
```

Якщо `jq` виводить деревоподібну структуру об'єктів без помилок парсингу, текстова частина метаданих є синтаксично неушкодженою.

### 12.2. Ручне редагування JSON-метаданих та перерахунок контрольної суми `csum` (SHA-256)

Якщо адміністратор вручну коригує помилкові параметри у текстовій зоні JSON (наприклад, видаляє некоректну вимогу у `requirements` чи виправляє зміщення пошкодженого сегмента), пряме збереження файлу призведе до помилки `Header checksum mismatch`, оскільки збережений дайджест `csum` перестане відповідати вмісту блоку.

#### Покроковий протокол ручного перерахунку контрольної суми:

```
┌───────────────────────────────────────────────────────────────────────────┐
│              АЛГОРИТМ ПЕРЕРАХУНКУ КОНТРОЛЬНОЇ СУМИ LUKS2                  │
│                                                                           │
│  1. Формування повного образу 4 МіБ (Дескриптор + JSON + Падинг 0x00)     │
│                                │                                          │
│                                ▼                                          │
│  2. Занулення 64 байтів поля csum (зсув 0x01C0 .. 0x01FF)                 │
│                                │                                          │
│                                ▼                                          │
│  3. Ініціалізація SHA-256 з підмішуванням 64 байтів поля salt             │
│                                │                                          │
│                                ▼                                          │
│  4. Обчислення дайджесту SHA-256 над усім 4-мегабайтним буфером           │
│                                │                                          │
│                                ▼                                          │
│  5. Запис отриманих 32 байтів дайджесту назад у поле csum за зсувом 0x01C0│
└───────────────────────────────────────────────────────────────────────────┘
```

1. **Збереження образу метаданих:**
   ```bash
   dd if=/dev/nvme0n1p3 of=header_mod.img bs=4M count=1
   ```
2. **Внесення виправлень у JSON:**
   Зміни вносяться в діапазоні між байтом `4096` та кінцевою фігурною дужкою `}`. Усі байти від кінця JSON-документа до кінця 4-мегабайтного файлу обов'язково заповнюються нульовими байтами `0x00`.
3. **Занулення поля `csum` у дескрипторі:**
   Поле `csum` розташоване за десятковим зсувом `448` (`0x01C0`) і має довжину 64 байти:
   ```bash
   dd if=/dev/zero of=header_mod.img bs=1 seek=448 count=64 conv=notrunc
   ```
4. **Обчислення нового SHA-256 дайджесту:**
   Оскільки алгоритм контрольної суми LUKS2 за замовчуванням обчислює SHA-256 над усім 4-мегабайтним буфером (із зануленим полем `csum`), новий хеш розраховується утилітою `sha256sum`:
   ```bash
   sha256sum header_mod.img
   # Приклад виводу: 7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a
   ```
5. **Запис нового дайджесту в бінарний дескриптор:**
   Отриманий 32-байтний шістнадцятковий дайджест записується у бінарному вигляді за зсувом `448`:
   ```bash
   printf '\x7f\x8a\x9b\x0c\x1d\x2e\x3f\x4a\x5b\x6c\x7d\x8e\x9f\x0a\x1b\x2c\x3d\x4e\x5f\x6a\x7b\x8c\x9d\x0e\x1f\x2a\x3b\x4c\x5d\x6e\x7f\x8a' | \
     dd of=header_mod.img bs=1 seek=448 count=32 conv=notrunc
   ```
6. **Запис виправленого заголовка на пристрій:**
   ```bash
   dd if=header_mod.img of=/dev/nvme0n1p3 bs=4M count=1 conv=notrunc
   sync
   ```

### 12.3. Відновлення з вторинного заголовка на зміщенні 4 МіБ

Якщо первинний заголовок за нульовим зсувом зруйновано внаслідок апаратного збою перших секторів або випадкового перезапису, доступ до тома можна повністю відновити з вторинного заголовка, що розташований за зсувом 4 МіБ (`0x400000`).

#### Спосіб 1. Автоматичне відновлення утилітою `cryptsetup repair`

Утиліта `cryptsetup` містить вбудований алгоритм арбітражу та самовідновлення:

```bash
cryptsetup repair /dev/nvme0n1p3
```

Внутрішня послідовність дій `cryptsetup repair`:
1. Зчитує бінарні дескриптори за зсувами `0` та `4194304`.
2. Виявляє пошкодження первинного заголовка (незбіг `csum` або бита сигнатура `magic`).
3. Валідує вторинний заголовок: перевіряє сигнатуру `"LUKS\xba\xbe"`, зміщення `hdr_offset == 4194304` та контрольну суму SHA-256.
4. Копіює 4 МіБ вторинного заголовка в нульову область.
5. Модифікує поле `hdr_offset` скопійованого блоку з `4194304` на `0`.
6. Інкрементує лічильник `seqid = seqid_secondary + 1`.
7. Перераховує контрольну суму `csum` і скидає буфери на носій за допомогою `fsync`.

#### Спосіб 2. Ручне покрокове відновлення через `dd`

Якщо відновлення виконується в мінімальному аварійному оточенні (наприклад, статичний `busybox` у середовищі `initramfs` без встановленої `libcryptsetup`), пряме копіювання вторинного заголовка за допомогою `dd` призведе до помилки відмови:

> ⚠️ **Критична помилка прямого копіювання.** Якщо просто виконати `dd if=/dev/sda bs=4M skip=1 count=1 of=/dev/sda`, скопійований заголовок міститиме поле `hdr_offset = 4194304`. Під час монтування драйвер виявить, що заголовок, прочитаний з нульового сектора, має `hdr_offset != 0`, і негайно відхилить його з помилкою `-EINVAL`.

#### Коректний протокол ручного відновлення:

1. **Вивантаження вторинного заголовка у файл:**
   ```bash
   dd if=/dev/nvme0n1p3 of=secondary_hdr.raw bs=4M skip=1 count=1
   ```
2. **Корекція поля `hdr_offset` на значення `0`:**
   8-байтне поле `hdr_offset` розташоване за зміщенням `260` (`0x0104`). Його необхідно замінити на вісім нульових байтів:
   ```bash
   printf '\x00\x00\x00\x00\x00\x00\x00\x00' | dd of=secondary_hdr.raw bs=1 seek=260 count=8 conv=notrunc
   ```
3. **Занулення поля `csum` перед перерахунком:**
   ```bash
   dd if=/dev/zero of=secondary_hdr.raw bs=1 seek=448 count=64 conv=notrunc
   ```
4. **Розрахунок нового SHA-256:**
   ```bash
   NEW_CSUM=$(sha256sum secondary_hdr.raw | awk '{print $1}')
   ```
5. **Запис нового дайджесту у відновлений дескриптор:**
   ```bash
   echo -n "$NEW_CSUM" | xxd -r -p | dd of=secondary_hdr.raw bs=1 seek=448 count=32 conv=notrunc
   ```
6. **Запис відновленого заголовка на нульове зміщення диска:**
   ```bash
   dd if=secondary_hdr.raw of=/dev/nvme0n1p3 bs=4M count=1 conv=notrunc
   sync
   ```
7. **Активація відновленого тома:**
   ```bash
   cryptsetup open /dev/nvme0n1p3 secure_volume
   ```

Після відкриття тома пристрій стає доступним у повному обсязі без втрати жодного байта користувацьких даних.

## 13. Автоматичне завантаження та конфігурація раннього простору користувача (Initramfs, Dracut, systemd-cryptsetup-generator)

Завантаження операційної системи із зашифрованого кореневого тома LUKS2 вимагає розблокування криптографічного пристрою до того, як ядро зможе змонтувати кореневу файлову систему (`rootfs`). Цю задачу виконує тимчасовий ранній простір користувача (**Early User Space**) — віртуальний диск `initramfs` (створений інструментами `dracut`, `mkinitcpio` або `initramfs-tools`), який координує роботу підсистем `udev`, `systemd` та `libcryptsetup`.

```

│                                                                           │
│   1. UEFI Firmware ──▶ Secure Boot ──▶ UKI / GRUB / systemd-boot          │
│                                │                                          │
│                                ▼                                          │
│   2. Завантаження vmlinuz + initramfs (CPIO архів у пам'яті RAM)          │
│                                │                                          │
│                                ▼                                          │
│   3. systemd усередині initrd запускає генератори:                        │
│      systemd-cryptsetup-generator сканує /etc/crypttab та /proc/cmdline   │
│                                │                                          │
│                                ▼                                          │
│   4. Динамічний синтез systemd-cryptsetup@root.service                    │

└───────────────────────────────────────────────────────────────────────────┘
```

### 13.1. Архітектура завантаження та конвеєр активації кореневого тома в initramfs

Процес розгортання криптографічного сховища на ранньому етапі ініціалізації ядра Linux підпорядкований суворій подієвій моделі:

1. **Ініціалізація шини пристроїв:** ядро монтує `devtmpfs` та передає керування процесу `systemd` усередині `initramfs`. Служба `systemd-udevd` сканує апаратні шини PCIe (NVMe) та SATA.
2. **Ідентифікація блокового носія:** правило udev `64-btrfs.rules` / `60-persistent-storage.rules` зчитує магічні байти `LUKS\xba\xbe` за допомогою вбудованої утиліти `blkid` та виставляє системні змінні оточення:
   * `ID_FS_TYPE="crypto_LUKS"`
   * `ID_FS_VERSION="2"`
   * `ID_FS_UUID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"`
3. **Запуск криптографічного сервісу:** поява відповідного вузла пристрою `dev-disk-by\x2duuid-...device` активує згенерований юніт `systemd-cryptsetup@<target>.service`.
4. **Активація через `libcryptsetup`:** демон викликає бінарний помічник `/usr/lib/systemd/systemd-cryptsetup attach <target> <device> <keyfile> <options>`.
5. **Монтування цільового кореня:** після появи блокового мапера `/dev/mapper/<target>` підсистема systemd монтує його в точку `/sysroot`, підключає вкладені точки монтування (`/sysroot/usr`, `/sysroot/var`), закриває тимчасові дескриптори `initramfs` і передає керування фінальному бінарнику `/sysroot/sbin/init`.

### 13.2. Синтаксис та контракт конфігураційного файлу `/etc/crypttab`

Конфігураційний файл `/etc/crypttab` (man 5 crypttab) визначає зіставлення між фізичними зашифрованими блоковими розділами та віртуальними пристроями Device Mapper. Кожен непорожній рядок файлу містить рівно чотири поля, розділені пробілами або символами табуляції:

```text
<target_name>    <source_device>    <key_file>    <options>
```

#### Специфікація полів `/etc/crypttab`:

1. **`<target_name>` (Рядок):** ім'я віртуального пристрою, що створюється в каталозі `/dev/mapper/` (наприклад, `root`, `swap`, `data_vol`).
2. **`<source_device>` (Рядок):** шлях або канонічний ідентифікатор вихідного зашифрованого розділу. Рекомендується використовувати стійкі UUID або PARTUUID:
   * `UUID=c2e8b0a1-4f3d-4c6e-8a9b-1d2e3f4a5b6c`
   * `PARTUUID=7f8a9b0c-01`
   * `/dev/disk/by-id/nvme-eui.002538b123456789-part3`
3. **`<key_file>` (Рядок):** абсолютний шлях до файлу з ключем розблокування, ключове слово `none` (вимагає ручного введення парольної фрази або використання апаратного токена) або `auto` (для автоматичного пошуку).
4. **`<options>` (Рядок):** список параметрів конфігурації через кому без пробілів.

#### Повна таблиця підтримуваних прапорців та опцій `/etc/crypttab`

| Опція `/etc/crypttab` | Тип значення | Опис та семантика |
| :--- | :--- | :--- |
| `tpm2-device=auto\|<path>` | Шлях / `auto` | Автоматичне розблокування запечатаним у мікросхемі TPM 2.0 ключем (`auto` для пошуку `/dev/tpmrm0`). |
| `tpm2-pcrs=<0+7+...>` | Список чисел | Перелік номерів регістрів PCR, до яких прив'язана перевірка політики авторизації TPM2. |
| `fido2-device=auto\|<path>`| Шлях / `auto` | Розблокування апаратним токеном FIDO2/Passkey через розширення `hmac-secret`. |
| `pkcs11-uri=<uri>` | Рядок RFC 7512| URI ідентифікатора закритого ключа на смарткарті стандарту PKCS#11. |
| `discard` | Прапорець | Передає прапорець `allow_discards` у `dm-crypt`, дозволяючи проходження команд TRIM для SSD. |
| `same-cpu-crypt` | Прапорець | Примушує ядро виконувати шифрування на тому ж ядрі CPU, що ініціювало ввід-вивід. |
| `submit-from-crypt-cpus` | Прапорець | Дозволяє робочим потокам `kcryptd` відправляти біо-структури напряму в чергу NVMe. |
| `no-read-workqueue` | Прапорець | Вимикає асинхронні черги читання `kcryptd`, виконуючи дешифрування в контексті переривання. |
| `no-write-workqueue` | Прапорець | Вимикає асинхронні черги запису `kcryptd`, мінімізуючи затримку на надшвидких NVMe. |
| `sector-size=<bytes>` | 512 / 4096 | Встановлює логічний розмір сектора криптоперетворення (наприклад, `sector-size=4096`). |
| `keyfile-timeout=<sec>` | Час (наприклад `10s`)| Таймаут очікування монтування зовнішнього носія з файлом ключа. |
| `keyfile-offset=<bytes>` | 64-бітне число | Зміщення в байтах від початку файлу ключа (дозволяє ховати ключ у сирому образі). |
| `keyfile-size=<bytes>` | Число байтів | Точна кількість байтів, що зчитуються з файлу ключа (запобігає читанню зайвих символів `\n`). |
| `header=<path>` | Абсолютний шлях | Вказує шлях до відокремленого заголовка LUKS2 (Detached Header), якщо він винесений окремо. |
| `tries=<N>` | Ціле число | Максимальна кількість спроб введення пароля (за замовчуванням `3`). |
| `timeout=<sec>` | Час (наприклад `60s`)| Загальний таймаут запиту парольної фрази перед переходом в аварійний режим. |
| `readonly` | Прапорець | Відкриває криптографічний пристрій у режимі тільки для читання (Write-Protect). |
| `x-systemd.device-timeout=<sec>`| Час | Таймаут очікування появи вихідного фізичного блокового носія у підсистемі udev. |
| `x-initrd.attach` | Прапорець | Обов'язкова інструкція генератору підключати цей том ще на стадії `initramfs`. |

#### Практичний приклад файлу `/etc/crypttab`

```text
# Кореневий розділ із розблокуванням через TPM2 та оптимізацією NVMe
root    UUID=c2e8b0a1-4f3d-4c6e-8a9b-1d2e3f4a5b6c    none    tpm2-device=auto,tpm2-pcrs=0+7,discard,sector-size=4096,no-read-workqueue,no-write-workqueue,x-initrd.attach

# Розділ підкачки (Swap) із випадковим ключем на кожне завантаження
swap    UUID=a1b2c3d4-e5f6-7a8b-9c0d-1e2f3a4b5c6d    /dev/urandom    swap,cipher=aes-xts-plain64,size=512,sector-size=4096

# Додаткове сховище даних з автентифікацією через FIDO2
data    /dev/disk/by-id/nvme-Samsung_SSD_980_PRO_1TB  none    fido2-device=auto,discard,timeout=30s
```

### 13.3. Механізм роботи `systemd-cryptsetup-generator` та динамічний синтез юнітів

Утиліта `/usr/lib/systemd/system-generators/systemd-cryptsetup-generator` виконується на найбільш ранньому етапі ініціалізації `systemd` (до запуску будь-яких сервісів). Вона читає конфігурацію з трьох джерел:
1. Системного файлу `/etc/crypttab` (або `/sysroot/etc/crypttab`).
2. Каталогів перекриття `/run/crypttab`, `/usr/lib/crypttab`.
3. Параметрів командного рядка ядра `/proc/cmdline` (`rd.luks.*` та `luks.*`).

```
┌───────────────────────────────────────────────────────────────────────────┐
│              ГРАФ ЗАЛЕЖНОСТЕЙ СИНТЕЗОВАНОГО СЕРВІСНОГО ЮНІТА              │
│                                                                           │
│       dev-disk-by\x2duuid-c2e8b0a1\x2d...device                           │
│                          │                                                │
│                          ▼ (BindsTo / After)                              │
│       systemd-cryptsetup@root.service                                     │
│       ExecStart=/usr/lib/systemd/systemd-cryptsetup attach root ...       │
│                          │                                                │
│                          ▼ (Before)                                       │
│       dev-mapper-root.device                                              │
│                          │                                                │
│                          ▼ (Wants / Before)                               │
│       cryptsetup.target                                                   │
│                          │                                                │
│                          ▼ (Before)                                       │
│       initrd-root-device.target ──▶ sysroot.mount                         │
└───────────────────────────────────────────────────────────────────────────┘
```

Для кожного знайденого запису генератор динамічно створює службовий юніт у каталозі тимчасової конфігурації `/run/systemd/generator/systemd-cryptsetup@<target>.service`:

```ini
# /run/systemd/generator/systemd-cryptsetup@root.service
[Unit]
Description=Cryptography Setup for %I
Documentation=man:systemd-cryptsetup@.service(8) man:crypttab(5)
DefaultDependencies=no
Conflicts=umount.target
BindsTo=dev-disk-by\x2duuid-c2e8b0a1\x2d4f3d\x2d4c6e\x2d8a9b\x2d1d2e3f4a5b6c.device
After=dev-disk-by\x2duuid-c2e8b0a1\x2d4f3d\x2d4c6e\x2d8a9b\x2d1d2e3f4a5b6c.device
Before=cryptsetup.target
Before=initrd-root-device.target
IgnoreOnIsolate=true

[Service]
Type=oneshot
RemainAfterExit=yes
TimeoutSec=0
ExecStart=/usr/lib/systemd/systemd-cryptsetup attach 'root' '/dev/disk/by-uuid/c2e8b0a1-4f3d-4c6e-8a9b-1d2e3f4a5b6c' 'none' 'tpm2-device=auto,tpm2-pcrs=0+7,discard,sector-size=4096,no-read-workqueue,no-write-workqueue'
ExecStop=/usr/lib/systemd/systemd-cryptsetup detach 'root'
```

* **Директива `BindsTo`:** жорстко пов'язує життєвий цикл сервісу з фізичним диском. Якщо апаратний NVMe-диск зникає з шини PCIe, сервіс негайно деактивується.
* **Директива `Before=initrd-root-device.target`:** гарантує, що спроба змонтувати кореневий розділ `/sysroot` не розпочнеться раніше, ніж `libcryptsetup` створить вузол `/dev/mapper/root`.

### 13.4. Параметри командного рядка ядра (Kernel Command Line) для Dracut та systemd

Параметри командного рядка ядра (передані через завантажувач у `/proc/cmdline`) мають найвищий пріоритет над записами `/etc/crypttab`. Префікс **`rd.luks.*`** застосовується виключно всередині `initramfs` для кореневого та системних томів; аналогічний префікс без `rd.` (наприклад, `luks.*`) поширюється на всю операційну систему після монтування `rootfs`.

#### Специфікація параметрів ядра:

1. **`rd.luks.uuid=<luks-UUID>`:**
   Вказує ядру розблокувати в `initramfs` виключно том із заданим UUID. Якщо параметр передано кілька разів, розблоковуються всі перелічені томи. Якщо параметр не задано взагалі, `dracut` намагається розблокувати всі знайдені на шині пристрої `crypto_LUKS`.
   * *Приклад:* `rd.luks.uuid=c2e8b0a1-4f3d-4c6e-8a9b-1d2e3f4a5b6c`
2. **`rd.luks.name=<luks-UUID>=<target-name>`:**
   Задає явне зіставлення між UUID зашифрованого тома та результуючим іменем пристрою в `/dev/mapper/`.
   * *Приклад:* `rd.luks.name=c2e8b0a1-4f3d-4c6e-8a9b-1d2e3f4a5b6c=root`
3. **`rd.luks.options=<options>` або `rd.luks.options=<luks-UUID>=<options>`:**
   Передає прапорці та параметри драйвера (ідентичні опціям `crypttab`). Якщо UUID не вказано, опції застосовуються глобально до всіх томів LUKS2 в `initramfs`.
   * *Приклад:* `rd.luks.options=discard,same-cpu-crypt,no-read-workqueue,tpm2-device=auto`
   * *Приклад:* `rd.luks.options=c2e8b0a1-4f3d-4c6e-8a9b-1d2e3f4a5b6c=discard,sector-size=4096`
4. **`rd.luks.key=<luks-UUID>=<keypath>[:<keydev>]`:**
   Визначає розташування бінарного файлу ключа на зовнішньому носії (наприклад, USB-флешці):
   * `<keypath>` — шлях до файлу ключа всередині файлової системи ключового носія.
   * `<keydev>` (опціонально) — специфікація блокового пристрою з ключем (`UUID=...`, `LABEL=...`). Якщо `<keydev>` вказано, `initramfs` тимчасово монтує носій, читає ключ, розблоковує LUKS2 і негайно демонтує пристрій.
   * *Приклад:* `rd.luks.key=c2e8b0a1-4f3d-4c6e-8a9b-1d2e3f4a5b6c=/keys/root.key:UUID=8F3A-12C9`
5. **`rd.luks.data=<luks-UUID>=<datapath>`:**
   Використовується для схем із відокремленим заголовком (**Detached Header**), коли заголовок LUKS2 розміщено на швидкому захищеному носії або вшито в образ ядра, а зашифровані дані — на окремому LUN/диску.
   * *Приклад:* `rd.luks.data=c2e8b0a1-4f3d-4c6e-8a9b-1d2e3f4a5b6c=/dev/nvme1n1`
6. **`rd.luks.crypttab=0`:**
   Повністю забороняє `systemd-cryptsetup-generator` читати файл `/etc/crypttab` усередині `initramfs`. Активація блокових дисків виконується виключно на основі параметрів командного рядка `rd.luks.*`.
7. **`rd.luks=0`:**
   Повне глобальне вимкнення обробки LUKS у ранньому просторі користувача.

### 13.5. Обробка збоїв, таймаутів та аварійний перехід на резервні методи розблокування (Fallback Protocol)

Під час автономного завантаження вузла апаратні чи мережеві токени можуть відмовити (зміна прошивки UEFI інвалідує PCR 0 у TPM2, відсутність зв'язку з сервером Tang або від'єднаний USB-ключ FIDO2). У такому разі система безпеки LUKS2 активує багаторівневий протокол відкату (Fallback Protocol):

```
┌───────────────────────────────────────────────────────────────────────────┐
│                  ПРОТОКОЛ АВАРІЙНОГО ВІДКАТУ РОЗБЛОКУВАННЯ                │
│                                                                           │
│  1. Спроба розблокування через токен (TPM2 / Tang / FIDO2)                │
│                         │                                                 │
│                         ├───▶ УСПІХ ──▶ Активація /dev/mapper/root        │
│                         │                                                 │
│                         ▼ ПОМИЛКА (-EPERM / Timeout)                      │
│  2. libcryptsetup переходить до наступної активної шпарини keyslots       │
│                         │                                                 │
│                         ▼                                                 │
│  3. Запуск агента паролів systemd-ask-password                            │
│     ├── Plymouth (Графічний екран введення пароля)                        │
│     └── TTY Console (Консольний запит: "Please enter passphrase:")        │
│                         │                                                 │
│                         ├───▶ ПАРОЛЬ ВІРНИЙ ──▶ Активація /dev/mapper/root│
│                         │                                                 │
│                         ▼ ПОМИЛКА (вичерпано tries або timeout)           │
│  4. Активація аварійного сервісу dracut-emergency.service                 │
│                         │                                                 │
│                         ▼                                                 │
│  5. Вхід у Dracut Emergency Shell (dracut:/#)                             │
│     Адміністратор вручну відновлює доступ:                                │
│     # cryptsetup open /dev/nvme0n1p3 root                                 │
│     # exit (продовження завантаження)                                     │
└───────────────────────────────────────────────────────────────────────────┘
```

1. **Нефатальна відмова токена:**
   Якщо звернення до чипа TPM2 повертає помилку авторизації `TPM_RC_POLICY_FAIL` або спливає таймаут запиту до Tang, бібліотека `libcryptsetup` не припиняє роботу аварійно. Вона повертає статус відмови токена і перемикається на перебір звичайних слотів ключів зі словника `keyslots`.
2. **Інтерактивний запит парольної фрази:**
   Служба `systemd-cryptsetup` створює сокет запиту через механізм **`systemd-ask-password`**. Запит одночасно транслюється у графічний інтерфейс завантаження (Plymouth) та у віртуальні консолі `/dev/tty1` .. `/dev/tty6`. Користувач може ввести резервний пароль або recovery-ключ аварійного відновлення.
3. **Обробка вичерпання ліміту спроб (`tries`):**
   Якщо користувач тричі ввів невірний пароль або минув встановлений ліміт часу `timeout`, юніт `systemd-cryptsetup@root.service` завершується зі статусом `failed`.
4. **Аварійна оболонка Dracut Emergency Shell:**
   Оскільки цільовий юніт `initrd-root-device.target` не може бути досягнутий, systemd зупиняє конвеєр завантаження та активує `dracut-emergency.service`. На системну консоль виводиться діагностичне повідомлення та запускається інтерактивний шелл `dracut:/#`.
   * Системний інженер може виконати ручну діагностику заголовків:
     ```bash
     # Інспекція метаданих і слотів
     cryptsetup luksDump /dev/nvme0n1p3

     # Ручне відкриття тома з аварійного слота
     cryptsetup open /dev/nvme0n1p3 root

     # Вихід з emergency shell і продовження завантаження системи
     exit
     ```
   Після виклику `exit` підсистема `systemd` повторно перевіряє наявність `/dev/mapper/root`, успішно монтує `/sysroot` і продовжує штатний запуск операційної системи.
