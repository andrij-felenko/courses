# 📜 Від фіксованих структур до гнучкого JSON: еволюція формату LUKS

Історія повнодискового шифрування в Linux — це послідовність подолання трьох криз: відсутності метаданих у ранніх драйверах ядра, краху обчислювально-орієнтованих функцій деривації ключів під натиском масивно-паралельних обчислень та відсутності криптографічного контролю цілісності на рівні секторів.

---

## Хаос раннього шифрування: cryptoloop та пастка німої помилки

Наприкінці 1990-х та на початку 2000-х років прозоре шифрування блокових пристроїв у Linux спиралося на експериментальний модуль `cryptoloop`. Він працював як надбудова над стандартним драйвером псевдопристроїв `loop.c` у ядрі серії 2.4/2.6 і перенаправляв дисковий ввід-вивід через криптографічні підсистеми ядра (CryptoAPI).

Користувач налаштовував шифрування вручну через утиліту `losetup`:

```bash
losetup -e aes /dev/loop0 /dev/hda2
```

У цій схемі введений користувачем пароль безпосередньо (через найпростіший геш або пряме обрізання байтів) перетворювався на симетричний ключ, яким шифрувалися всі сектори носія. При цьому дисковий розділ містив виключно голий шифротекст: на носії не зберігалося жодного байта службових метаданих, сигнатур чи описів параметрів.

```
┌─────────────────────────────────────────────────────────────┐
│                 СИРИЙ ДИСК CRYPTOLOOP                       │
│                                                             │
│  [Сектор 0: Шифротекст] [Сектор 1: Шифротекст] ...          │
│                                                             │
│  ✖ Немає сигнатури (Magic)                                  │
│  ✖ Немає назви шифру та режиму (AES-128? Twofish-256?)      │
│  ✖ Немає схеми генерації IV                                 │
│  ✖ Немає перевірки пароля                                   │
└─────────────────────────────────────────────────────────────┘
```

Такий підхід породжував критичні вразливості та системні ризики:

1. **Пастка німої помилки (Silent Data Corruption).** Якщо користувач помилявся бодай в одній літері пароля, обирав не той алгоритм (`aes128` замість `aes256`), плутав розмір ключа або вказував інший режим генерації вектора ініціалізації (IV), драйвер `cryptoloop` не повертав жодного повідомлення про помилку. Драйвер успішно створював віртуальний блоковий пристрій `/dev/loop0`, поверхня якого складалася з псевдовипадкового шуму. Під час монтування файлової системи або запуску автоматичної утиліти перевірки диска (`e2fsck` під час завантаження ОС) система намагалася зчитати й відновити суперблоки з цього шуму. Утиліти записували виправлені структури назад на носій, миттєво й безповоротно руйнуючи справжні суперблоки та дані розділу.
2. **Неможливість безпечної зміни пароля.** Оскільки пароль користувача був жорстко пов'язаний із ключем шифрування секторів, зміна пароля вимагала повного вивантаження всіх даних на окремий тимчасовий носій, переформатування розділу з новим паролем і повторного побайтового копіювання файлової системи.
3. **Криптографічні вади та атаки на базі водяних знаків (Watermarking Attacks).** Ранні схеми використовували режим зчеплення блоків CBC (Cipher Block Chaining) із передбачуваним лінійним вектором ініціалізації Plain IV (де IV дорівнював 32-бітному індексу сектора LBA). Австрійський криптограф Клеменс Фрювірт (Clemens Fruhwirth) довів, що передбачуваність IV у режимі CBC дозволяє зловмиснику детектувати наявність відомих патернів даних на диску. Спеціально сконструйований файл із відомим вмістом («водяний знак») створював у шифротексті секторів ідентичні блоки, що дозволяло сторонньому спостерігачеві перевірити наявність файлу без знання ключа шифрування.

У 2004 році в ядрі Linux 2.6.4 з'явився модуль `dm-crypt`, розроблений Крістофом Зауссе (Christophe Saout) на базі підсистеми Device Mapper. Це усунуло вузькі місця продуктивності та взаємні блокування потоків `loop.c`, але проблема метаданих лишилася відкритою: конфігурація та сирий шістнадцятковий ключ шифрування все одно передавалися вручну через керівний рядок таблиці відображення:

```bash
dmsetup create secure_vol --table "0 2097152 crypt aes-cbc-plain 0123456789abcdef... 0 /dev/sda1 0"
```

Спільноті був потрібен єдиний відкритий стандарт, який зберіг би параметри шифрування на самому носії, унеможливив псування файлових систем через помилки вводу та надав зручне керування паролями.

## Специфікація LUKS1: дворівневі ключі та антикриміналістичне розщеплення

У 2004 році Клеменс Фрювірт опублікував специфікацію TKS1 (*Template Key Setup*) та стандартизував формат **LUKS1** (*Linux Unified Key Setup*). Новий стандарт заклав фундаментальні принципи, які визначили розвиток шифрування накопичувачів у Linux на наступні десятиліття.

```
┌─────────────────────────────────────────────────────────────┐
│                    АРХІТЕКТУРА LUKS1                        │
│                                                             │
│  ┌──────────────┐         ┌─────────────┐                   │
│  │ Пароль 0     │────▶    │ Keyslot 0   │───┐               │
│  │ (Адміністрат)│         │ (AFSplit)   │   │               │
│  └──────────────┘         └─────────────┘   │               │
│                                             ▼               │
│  ┌──────────────┐         ┌─────────────┐  ┌─────────────┐  │
│  │ Пароль 1     │────▶    │ Keyslot 1   │─▶│ Master Key  │  │
│  │ (Користувач) │         │ (AFSplit)   │  │  (Том диска)│  │
│  └──────────────┘         └─────────────┘  └─────────────┘  │
│                                             ▲               │
│  ┌──────────────┐         ┌─────────────┐   │               │
│  │ Пароль 2     │────▶    │ Keyslot 2   │───┘               │
│  │ (Резервний)  │         │ (AFSplit)   │                   │
│  └──────────────┘         └─────────────┘                   │
└─────────────────────────────────────────────────────────────┘
```

### Дворівнева ієрархія ключів

LUKS1 відокремив пароль користувача від ключа шифрування даних. Для розділу генерується єдиний випадковий симетричний **головний ключ тому** (Master Key, MK) довжиною 128, 256 або 512 бітів. Самі сектори диску шифруються виключно цим ключем.

Паролі користувачів використовуються лише для розшифрування Master Key. Специфікація визначила 8 незалежних слотів ключів (keyslots). Це дозволило призначати окремі паролі для адміністратора, звичайного користувача чи систем автоматичного відновлення, а також змінювати або відкликати паролі за мілісекунди без перешифрування терабайтів даних.

### Структура бінарного заголовка LUKS1 (592 байти)

Формат зафіксував монолітний бінарний заголовок розміром 592 байти на початку дискового розділу (LBA 0). Заголовок містить:

* Сигнатуру `magic`: 6 байтів `'L'`, `'U'`, `'K'`, `'S'`, `0xBA`, `0xBE` та версію `1`.
* Назву шифру та режим: рядки фіксованої довжини (наприклад, `aes` та `cbc-essiv:sha256`, згодом `xts-plain64`).
* Довжину Master Key у байтах (`key_bytes`).
* Контрольний дайджест Master Key (`mk_digest`): 20-байтний HMAC/SHA-1 дайджест із сіллю та фіксованою кількістю ітерацій PBKDF2. Перед відправкою ключа в ядро `cryptsetup` розшифровує кандидат Master Key і перевіряє його за дайджестом. Якщо пароль невірний, утиліта негайно повідомляє про помилку автентифікації й не чіпає блоковий пристрій, повністю ліквідуючи ризик руйнування файлової системи.
* Вісім описів слотів ключів (`struct luks_keyslot`, по 48 байтів кожен):
  * `active`: статус слота (`0x00AC71F3` — активний, `0x0000DEAD` — вимкнений).
  * `iterations`: кількість ітерацій розтягування пароля через PBKDF2.
  * `salt`: індивідуальна 32-байтна криптографічна сіль.
  * `key_material_offset`: секторний зсув області розщеплених смуг на диску.
  * `stripes`: кількість смуг розщеплення інформації (за замовчуванням 4000).

### Алгоритм AFSplit (Anti-Forensic Information Splitting)

Пряме збереження зашифрованого Master Key в одному 512-байтовому секторі небезпечне для твердотілих накопичувачів (SSD, NVMe) та флешкарт. Алгоритми вирівнювання зносу (wear-leveling) та резервні блоки пам'яті (over-provisioning) призводять до того, що перезапис сектора контролером SSD не знищує старі комірки пам'яті фізично. Зловмисник, вилучивши чип пам'яті, міг відновити зашифрований Master Key.

Щоб гарантувати незворотне знищення ключа, Фрювірт розробив схему AFSplit. Головний ключ `K` розщеплюється на 4000 смуг (сумарно 256 КіБ на диску) за допомогою рекурсивного дифузійного ланцюга геш-функцій:

```
I[0] = 0
I[i] = Hash(I[i-1] ⊕ S[i])   для i = 1 .. 3999
S[4000] = K ⊕ I[3999]
```

Для відновлення ключа необхідно мати **всі 4000 смуг без винятку**. Якщо на носії пошкоджено або стерто хоча б один 512-байтовий сектор (який містить 8 смуг AFSplit), відсутні блоки створюють 4096 бітів абсолютної випадкової ентропії. Імовірність вгадати ключ становить `2⁻⁴⁰⁹⁶`, що робить відновлення математично неможливим. Одночасно AFSplit створив мультиплікатор складності (Work Factor Amplification): зловмисник при спробі перебору пароля змушений для кожної гіпотези обчислювати геш над усіма 4000 смугами.

### Захист від атак на CBC: схема ESSIV

Для усунення витоків передбачуваного IV у режимі CBC специфікація інтегрувала генератор ESSIV (*Encrypted Salt-Sector Initialization Vector*). Вектор ініціалізації обчислювався як шифр від номера сектора під спеціальним ключем `K_iv = Hash(MK)`:

```
IV = AES_Encrypt(K_iv, Sector_Number)
```

Це зробило вектори ініціалізації псевдовипадковими для зовнішнього спостерігача й нейтралізувало атаки водяних знаків.

Завдяки утиліті `cryptsetup-luks` формат LUKS1 став універсальним стандартом повнодискового шифрування, інтегрованим в інсталятори Red Hat, Debian, Ubuntu, openSUSE та Fedora.

## Апаратний злам PBKDF2 та архітектурна криза бінарного заголовка

До 2015 року понад десятилітня експлуатація LUKS1 виявила критичні архітектурні межі, які неможливо було розширити в межах старої бінарної структури.

```
┌─────────────────────────────────────────────────────────────┐
│                    КРИЗА АРХІТЕКТУРИ LUKS1                  │
│                                                             │
│  [LBA 0: Заголовок 592 B] ──▶ Пошкодження 1 сектора         │
│                                  │                          │
│                                  ▼                          │
│                               ✖ Повна втрата всіх терабайтів│
│                                                             │
│  [PBKDF2 KDF]             ──▶ Compute-bound (RAM < 256 B)   │
│                                  │                          │
│                                  ▼                          │
│                               ✖ Злам на GPU/ASIC фермах     │
│                                                             │
│  [Фіксовані поля 592 B]   ──▶ 8 слотів, 512 B сектори       │
│                                  │                          │
│                                  ▼                          │
│                               ✖ Немає TPM2/FIDO2, 4Kn, AEAD │
└─────────────────────────────────────────────────────────────┘
```

### 1. Єдина точка відмови (Single Point of Failure)

Заголовок LUKS1 записувався виключно в нульовий сектор пристрою (LBA 0). Будь-який збій контролера, апаратний дефект магнітної поверхні або випадкове занулення першого сектора (наприклад, помилкове виконання `dd` чи збій утиліти розмітки GPT) повністю знищувало заголовок. Разом із заголовком назавжди втрачалися всі keyslots і Master Key. Терабайтний масив даних перетворювався на невідновлюваний бінарний шум. Єдиним захистом був ручний бекап заголовка в зовнішній файл (`cryptsetup luksHeaderBackup`), про що користувачі зазвичай дізнавалися вже після катастрофи.

### 2. Крах криптографічної стійкості PBKDF2

Функція розтягування пароля PBKDF2 (RFC 2898), спроєктована у 2000 році, розраховувалася на процесори загального призначення. Вона працює шляхом багаторазового послідовного застосування псевдовипадкової функції HMAC-SHA1 або HMAC-SHA256:

```
DK = PBKDF2(HMAC, Password, Salt, Iterations, KeyLength)
```

PBKDF2 є суто **обчислювально містким** (compute-bound) алгоритмом і майже не використовує оперативну пам'ять — для обчислення одного кроку SHA-256 достатньо менше 256 байтів регістрової пам'яті.

У 2010-х роках почався стрімкий розвиток паралельних обчислень на графічних процесорах (GPU з підтримкою OpenCL/CUDA, фреймворки Hashcat) та майнінгових чипах ASIC. Архітектура GPU оптимізована для паралельного виконання тисяч простих обчислювальних потоків із високою щільністю ALU. Відеокарта або спеціалізований ASIC-кластер могли паралельно перевіряти сотні мільйонів паролів PBKDF2 на секунду.

Збільшення кількості ітерацій сповільнювало вхід на одноядерному CPU лептопа до кількох секунд, але для зловмисника з фермою GPU це створювало лише лінійну затримку, яку легко компенсували додаванням нових обчислювальних ядер.

### 3. Жорсткі обмеження бінарного формату 592 байти

Фіксована розмітка полів у заголовку унеможливила розвиток нових функцій:

* **Ліміт 8 слотів:** неможливо було виділити додаткові слоти для корпоративних ключів чи ключів відновлення.
* **Відсутність місця для довільних метаданих:** у заголовку не було місця для збереження асиметричних сертифікатів X.509, запечатаних блобів мікросхем TPM, відкритих облікових записів ключів FIDO2/WebAuthn чи описів складних топологій томів.
* **Проблема секторів 4Kn (Advanced Format):** формат LUKS1 проєктувався під сектори розміром 512 байтів. Поява дисків із фізичним сектором 4096 байтів (4Kn) призводила до проблем зсуву та втрати продуктивності під час запису смуг AFSplit.

### 4. Відсутність автентифікації даних (AEAD) та атаки Bit-Flipping

Симетричні алгоритми шифрування дисків (AES-CBC, AES-XTS) гарантують **конфіденційність**, але не забезпечують **контролю цілісності**.

Якщо зловмисник має фізичний доступ до носія (наприклад, у сценарії вилученого ноутбука або скомпрометованого серверного диска), він не може прочитати зашифровані файли, але може цілеспрямовано змінити окремі біти в шифротексті (атака *bit-flipping*). У режимах CBC та XTS зміна бітів у зашифрованому секторі призводить до передбачуваних або локалізованих змін у розшифрованому відкритому тексті. Зловмисник міг модифікувати байти системних файлів конфігурації (таких як `/etc/shadow`, конфігурації `sudoers` чи бінарний код демона `sshd`). Під час завантаження ядро дешифрувало пошкоджений сектор без жодного попередження, дозволяючи обійти автентифікацію.

### 5. Відсутність онлайн-перешифрування

Зміна алгоритму шифрування (наприклад, міграція з застарілого `aes-cbc-essiv` на сучасний `aes-xts-plain64`) або зміна скомпрометованого Master Key вимагала повної зупинки системи, створення нового розділу та тривалого копіювання даних через проміжний накопичувач.

## Революція LUKS2: транзакційний JSON, пам'ятемісткий KDF та цілісність

У 2016–2018 роках команда супроводу проєкту `cryptsetup` на чолі з Міланом Брожем (Milan Broz, Red Hat) та Ондреєм Козіною (Ondrej Kozina) спроєктувала стандарт **LUKS2**.

Замість монолітної структури LUKS2 запропонував гібридну схему: компактний 4-кілобайтний бінарний дескриптор `luks2_hdr_disk` на початку пристрою поєднується з відкритою динамічною текстовою областю метаданих у форматі JSON (розміром до 4 МіБ мінус 4 КіБ).

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      СТРУКТУРА НОСІЯ LUKS2 (8 МІБ)                      │
│                                                                         │
│  ┌───────────────────────────┐         ┌───────────────────────────┐    │
│  │     ПЕРВИННИЙ ЗАГОЛОВОК   │         │    ВТОРИННИЙ ЗАГОЛОВОК    │    │
│  │         (Зсув 0)          │         │       (Зсув 4 МіБ)        │    │
│  ├─────────────┬─────────────┤         ├─────────────┬─────────────┤    │
│  │ Бінарний    │ Метадані    │         │ Бінарний    │ Метадані    │    │
│  │ дескриптор  │ JSON        │         │ дескриптор  │ JSON        │    │
│  │ (4 КіБ)     │ (до 4 МіБ)  │         │ (4 КіБ)     │ (до 4 МіБ)  │    │
│  │ seqid: N+1  │ CRC32/SHA256│         │ seqid: N    │ CRC32/SHA256│    │
│  └─────────────┴─────────────┘         └─────────────┴─────────────┘    │
│                                                                         │
│  [Зсув 8–16 МіБ: Бінарні смуги AFSplit] [Сегмент шифрованих даних...]   │
└─────────────────────────────────────────────────────────────────────────┘
```

### Подвійний заголовок та транзакційний захист від збоїв живлення

LUKS2 повністю усунув проблему єдиної точки відмови, ввівши **два незалежні заголовки**:
* **Первинний заголовок (Primary Header):** розташований на зсуві 0 байтів.
* **Вторинний заголовок (Secondary Header):** розташований на зсуві 4 МіБ (0x400000).

Кожен заголовок містить 64-бітний монотонний лічильник послідовності транзакцій `seqid` та контрольну суму `csum` (SHA-256 або CRC32), яка покриває як 4 КіБ бінарного дескриптора, так і всю текстову область JSON.

Оновлення метаданих відбувається за суворим двоетапним протоколом:
1. Нова версія конфігурації JSON із номером `seqid_new = seqid_current + 1` та свіжою контрольною сумою записується у **вторинний заголовок**.
2. Виконується апаратне скидання кешу запису носія (операція `fsync` або команда FUA — Force Unit Access).
3. Після підтвердження запису на фізичні пластини/флешкомірки новий стан записується у **первинний заголовок** і знову скидається бар'єром пам'яті.

Якщо в будь-яку мікросекунду процесу сервер втратить живлення, один із двох заголовків завжди містить 100% неушкоджену версію метаданих. Під час відкриття пристрою бібліотека `libcryptsetup` читає обидва заголовки, валідує їхні контрольні суми й автоматично обирає екземпляр із найвищим валідним `seqid`.

Для захисту від помилок розмітки диска бінарний заголовок містить поле `hdr_offset`. Воно фіксує абсолютне зміщення, за яким має лежати цей блок (0 для первинного, 4194304 для вторинного). Якщо адміністратор переніс розділ утилітою `dd` зі зміщенням секторів, ядро виявляє розбіжність між реальною точкою читання та полем `hdr_offset` і блокує операції, запобігаючи перезапису суміжних даних.

### Графова модель JSON-метаданих

Замість фіксованих структур конфігурація тому описується у вигляді зв'язного орієнтованого графа JSON-об'єктів:

```json
{
  "keyslots": { "0": { "type": "luks2", "kdf": { "type": "argon2id", ... } } },
  "tokens": { "0": { "type": "systemd-tpm2", "keyslots": ["0"], ... } },
  "segments": { "0": { "type": "crypt", "offset": "16777216", "size": "dynamic", ... } },
  "digests": { "0": { "type": "pbkdf2", "keyslots": ["0"], "segments": ["0"], ... } },
  "config": { "json_size": "12288", "keyslots_size": "16744448" }
}
```

* **`keyslots`:** кількість слотів більше не обмежена вісьмома. Кожен слот визначає власні параметри KDF (Argon2id, Argon2i чи PBKDF2), бінарне зміщення смуг AFSplit та розмір ключа.
* **`digests`:** пов'язують конкретні слоти ключів із сегментами даних через криптографічні геші Master Key.
* **`segments`:** описують фізичну геометрію шифрованого простору, розмір сектора (512 або 4096 байтів) та алгоритм шифрування (`aes-xts-plain64`). LUKS2 дозволяє створювати складні схеми з кількома незалежними сегментами на одному носії.
* **`tokens`:** зберігають параметри зовнішніх модулів автентифікації.

### Пам'ятемісткий KDF: впровадження Argon2

Стандартом KDF за замовчуванням у LUKS2 став алгоритм **Argon2** (переможець Password Hashing Competition 2015 року, RFC 9106), реалізований у двох варіантах: **Argon2id** (гібридний режим, стандартний для LUKS2) та **Argon2i** (режим із доступом, незалежним від пароля).

Головна перевага Argon2 — **пам'ятемісткість** (memory-hardness). Під час розгортання ключа алгоритм виділяє в оперативній пам'яті велику матрицю блоків (за замовчуванням 1 ГБ) і виконує нелінійне перемішування даних на основі перестановки Blake2b.

```
┌─────────────────────────────────────────────────────────────┐
│                 МАТРИЦЯ ПАМ'ЯТІ ARGON2ID (1 ГБ)             │
│                                                             │
│  [Блок 0] ──▶ [Блок 1] ──▶ [Блок 2] ──▶ ... ──▶ [Блок M]   │
│     ▲                        │                     │        │
│     │                        ▼                     │        │
│     └──────────────── [Псевдовипадкове] ◀──────────┘        │
│                       [ перемішування ]                     │
└─────────────────────────────────────────────────────────────┘
```

Цей механізм кардинально змінив баланс сил між захисником і нападником:
* Навіть флагманський графічний процесор із 24 ГБ відеопам'яті здатен одночасно виконувати не більше 24 паралельних потоків перебору Argon2 (проти сотень мільйонів потоків для PBKDF2).
* Спроба зекономити пам'ять на GPU/ASIC змушує обчислювальний вузол повторно обчислювати проміжні блоки, що спричиняє експоненційне зростання обчислювальної складності (Time-Memory Trade-Off penalty).
* Режим Argon2id поєднує перший прохід Argon2i (захист від атак за сторонніми каналами кешу CPU) із наступними проходами Argon2d (максимальна стійкість проти GPU-ферм).

Під час створення тома `cryptsetup` запускає динамічний бенчмарк процесора, підбираючи параметри пам'яті й потоків так, щоб генерація ключа тривала рівно 2000 мілісекунд.

### Автентифіковане шифрування: інтеграція з dm-integrity

У 2017 році Мілан Брож та Мікулаш Паточка (Mikulas Patocka) інтегрували в ядро Linux 4.12 підсистему `dm-integrity`. Стандарт LUKS2 вперше дозволив формувати двошаровий стек автентифікованого шифрування (AEAD) на рівні блокового пристрою:

```
┌─────────────────────────────────────────────────────────────┐
│            СТЕК АВТЕНТИФІКОВАНОГО ШИФРУВАННЯ                │
│                                                             │
│  [Файлова система / Простір користувача]                    │
│                        │                                    │
│                        ▼                                    │
│  [Шар dm-crypt: AEAD / ChaCha20-Poly1305 / AES-GCM]         │
│                        │                                    │
│                        ▼                                    │
│  [Шар dm-integrity: Per-sector Tags + Integrity Journal]    │
│                        │                                    │
│                        ▼                                    │
│  [Фізичний накопичувач (Сектори даних + Сектори тегів)]     │
└─────────────────────────────────────────────────────────────┘
```

1. Шар `dm-integrity` виділяє для кожного сектора даних (512 або 4096 байтів) додаткові службові байти (зазвичай 28–32 байти), де зберігається криптографічний тег автентифікації (HMAC-SHA256 або Poly1305).
2. Для захисту від аварій живлення під час запису секторів використовується кільцевий журнал транзакцій цілісності (Integrity Journal), що унеможливлює розрив між оновленням даних та тегу (*write-tearing*).
3. Якщо зловмисник інвертує бодай один біт у зашифрованому секторі на носії, під час читання `dm-integrity` фіксує невідповідність тегу й негайно перериває операцію вводу-виводу з кодом помилки `-EILSEQ` (*Illegal byte sequence*). Фальсифіковані дані не потрапляють у сторінковий кеш файлової системи, що повністю блокує атаки типу *bit-flipping*.

### Вбудоване онлайн-перешифрування (Online Reencryption)

LUKS2 реалізував транзакційне перешифрування томів на льоту без виведення їх з експлуатації. У метаданих JSON створюється тимчасовий слот `"reencrypt"`, який фіксує рухому межу між старим і новим сегментами шифрування. Процес обслуговується журналом стійкості (`resilience-mode`), що гарантує збереження даних при збоях живлення посеред операції перешифрування.

## Апаратні токени та безпарольний захист платформи

Завдяки розділу `tokens` у JSON-метаданих LUKS2 трансформувався з утиліти обробки паролів у платформу для побудови захищених апаратних ланцюгів довіри.

│  │(Запечатування │   │ (Апаратний ключ │   │ (Смарткарта │  │
│  │   до PCR)     │   │   hmac-secret)  │   │  з RSA/ECC) │  │
│  └───────┬───────┘   └────────┬────────┘   └──────┬──────┘  │
│          │                    │                   │         │
│          └────────────────────┼───────────────────┘         │
│                               ▼                             │
│                  ┌─────────────────────────┐                │

### Запечатування в TPM 2.0 (`systemd-tpm2`)

Стандарт дозволив інтегрувати дискове шифрування з апаратним чипом TPM 2.0 (Trusted Platform Module) за допомогою утиліти `systemd-cryptenroll`:

```bash
systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=0+7+14 /dev/nvme0n1p3
```

Секрет розблокування keyslot запечатується (sealed) всередині захищеної пам'яті TPM2 під політику конфігураційних регістрів платформи (Platform Configuration Registers, PCR):
* **PCR 0:** геш прошивки UEFI материнської плати.
* **PCR 7:** стан сертифікатів Secure Boot та політики підпису ядра.
* **PCR 14:** стан додаткових ключів безпечного завантаження Shim (MOK).

Під час старту системи служба `systemd-cryptsetup` надсилає запечатаний блоб до TPM2. Якщо прошивка не модифікувалася і завантажується авторизоване ядро, чип розпечатує ключ, і диск монтується без участі користувача. Якщо зловмисник намагається підключити чужий накопичувач або завантажити скомпрометоване ядро, значення PCR не збігаються, і TPM2 блокує доступ до ключа.

### Апаратні ключі FIDO2 та смарткарти PKCS#11

* **FIDO2 / WebAuthn (`systemd-fido2`):** використовує розширення `hmac-secret` стандарту CTAP2. Розблокування тома вимагає наявності фізичного USB-ключа (наприклад, YubiKey) та підтвердження фізичної присутності користувача дотиком (User Presence) або PIN-кодом.
* **PKCS#11 (`systemd-pkcs11`):** секрет keyslot шифрується асиметричним відкритим ключем (RSA-4096 / ECC), збереженим на корпоративній смарткарті, і розшифровується апаратним чипом картки після введення PIN-коду.
