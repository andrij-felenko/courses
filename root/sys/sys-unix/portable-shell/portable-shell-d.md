Сценарій автоматизації або збірки, написаний на машині під керуванням Ubuntu чи Fedora, проходить усі локальні тести без жодного зауваження. Але щойно цей самий скрипт потрапляє у виробничий контейнер на базі Alpine Linux, у складальне середовище FreeBSD або в інсталяційний крок образу initramfs, виконання розвалюється на перших секундах. Інтерпретатор сипле синтаксичними помилками на кшталт `syntax error: unexpected "("`, утиліта `sed` раптово знищує файл замість заміни тексту, а операції перевірки умов мовчки повертають хибний результат і пропускають критичні кроки розгортання.

Причина таких аварій криється не у вадах цільових систем, а в оманливій природі середовища розробки. Більшість робочих станцій використовують інтерактивну оболонку GNU Bash разом із набором розширених утиліт GNU Coreutils. Інженер звикає до синтаксичного комфорту: подвійних дужок `[[ ]]`, масивів, зрізів рядків, підстановки процесів `<()` та специфічних прапорців `sed -i` чи `date -d`. Коли у заголовку сценарію ставлять шебанг `#!/bin/sh`, виникає хибна ілюзія сумісності: здається, що скрипт виконується стандартною системною оболонкою, тоді як насправді розробник використовує пропрієтарний діалект.

Переносність сценарію (portability) — це інженерний контракт між текстом скрипта та операційною системою, закріплений стандартом IEEE 1003.1 (POSIX). Щоб сценарій однаково надійно працював на серверному Linux, вбудованому BusyBox, робочій станції macOS та серверах сімейства BSD, розробник мусить чітко розрізняти три рівні: що гарантує специфікація командної мови POSIX Shell Command Language, які синтаксичні конструкції є специфічними розширеннями Bash («башизмами»), і де пролягають глибокі розбіжності між простором користувача GNU та BSD.

## Анатомія розколу: що ховається за `/bin/sh`

Історично шлях `/bin/sh` у ранніх версіях Unix вказував на командний інтерпретатор Стівена Борна (Bourne shell, 1977 рік, Version 7 Unix). З розвитком комерційних та академічних гілок Unix розробники почали розширювати мову: Девід Корн створив потужний KornShell (ksh), Кеннет Альмквіст написав легковажний клон Almquist shell (ash) для BSD, а проект GNU створив Bourne-Again Shell (Bash), додавши інтерактивні зручності та складні мовні конструкції.

Коли комітет IEEE зафіксував стандарт POSIX (зокрема розділ Shell & Utilities стандарту IEEE 1003.1 / Single UNIX Specification), за основу командної мови було взято підмножину можливостей KornShell 88 та Bourne shell. Стандарт свідомо відкинув усе, що вважалося надлишковим або специфічним для окремих постачальників. Так виник канонічний контракт: мова POSIX sh — це мінімальне, спільне ядро всіх оболонок Unix.

Еволюція стандарту пройшла кілька редакцій: POSIX.2 (IEEE Std 1003.2-1992), POSIX.1-2001 (SUSv3), POSIX.1-2008 (SUSv4 з технічними виправленнями TC1/TC2) та POSIX.1-2024 (Issue 8). Новітня редакція 2024 року стандартизувала деякі зрілі розширення — зокрема, опцію `pipefail`, утиліту `realpath`, прапорець `read -d` та `find -print0`/`xargs -0`. Проте мільйони промислових систем, контейнерів та вбудованих пристроїв працюють на базі редакції POSIX.1-2008, тому написання гарантовано переносного коду вимагає орієнтації на базовий перетин стандарту.

Сьогодні у сучасних операційних системах за шляхом `/bin/sh` ховаються кардинально різні програми:

1. **Debian та Ubuntu (`dash`)**: симлінк `/bin/sh` веде на `dash` (Debian Almquist Shell). Це прямий нащадок `ash`, скомпільований для максимальної швидкодії системного завантаження. `dash` займає у пам'яті близько 200 КБ, стартує втричі швидше за Bash і виконує виключно стандартні конструкції POSIX sh. Будь-який синтаксис поза стандартом спричиняє негайну синтаксичну помилку розбору.
2. **Alpine Linux, OpenWrt, initramfs (`busybox ash`)**: у контейнерах Alpine та вбудованих прошивках `/bin/sh` веде до мультикол-бінарника `busybox`. Вбудований аплет `ash` оптимізовано під мінімальний розмір (менше 100 КБ коду), він підтримує базовий POSIX sh і відкидає майже всі розширення.
3. **FreeBSD, NetBSD, OpenBSD (`sh`, `pdksh`)**: у системах BSD `/bin/sh` є системною оболонкою на базі Almquist sh або Public Domain Korn Shell. Вона не містить розширень GNU Bash і суворо ізольована від користувацьких оболонок.
4. **macOS (`/bin/sh` та `zsh`)**: у macOS за шляхом `/bin/sh` знаходиться застаріла версія GNU Bash 3.2. Apple заморозила версію Bash у 2006 році через небажання ліцензувати код під ліцензією GPLv3, а пізніше зробила типовою інтерактивною оболонкою `zsh`. Ця версія Bash 3.2 не підтримує навіть сучасних башизмів (як-от асоціативні масиви чи перетворення регістру), створюючи подвійну плутанину.
5. **Red Hat Enterprise Linux, Arch Linux (`bash`)**: у деяких дистрибутивах `/bin/sh` досі є символьним посиланням на `/bin/bash`.

![Спектр оболонок Unix: співвідношення строгості POSIX, швидкості та розширень](/root/sys/sys-unix/portable-shell/img/shell-dialect-spectrum.svg)

*Спектр оболонок: від мінімального спільного ядра стандарту POSIX та швидких системних sh до розширених інтерактивних інтерпретаторів.*

Головна пастка полягає у поведінці самого Bash. Коли Bash запускається через посилання `/bin/sh` або з прапорцем `--posix`, він переходить у так званий режим сумісності з POSIX (POSIX mode). Але цей режим **не перетворює Bash на чистий POSIX-інтерпретатор**. Він вимикає лише окремі речі (як-от розгортання фігурних дужок `{1..10}` за замовчуванням), але залишає активними десятки башизмів: зрізи `${var:0:5}`, оператор `==` у `test`, ключове слово `local`, специфіку `echo`. Інженер перевіряє скрипт локально під `/bin/sh -> bash`, бачить успішне виконання, а при переході на `dash` у Debian чи `ash` в Alpine отримує аварію.

> 🔧 **Навіщо це.** Швидкість запуску інтерпретатора має вирішальне значення. Виклик `dash` або `busybox ash` займає близько 1.5–2 мс процесорного часу, тоді як повний бінарник `bash` вимагає 10–15 мс на запуск і завантаження структур. У масштабних складальних конвеєрах чи скриптах завантаження системи (де викликаються тисячі дрібних shell-команд) використання легковажного POSIX sh скорочує час виконання на хвилини.

## Каталог типових башизмів та їхні безпечні еквіваленти

Башизмом (bashism) називають будь-яку синтаксичну конструкцію, оператор або вбудовану функцію, яку підтримує GNU Bash (та споріднені розширені оболонки на кшталт Zsh чи Ksh), але яка відсутня у стандарті IEEE 1003.1 (POSIX sh). Розглянемо найнебезпечніші башизми, механізм їхньої відмови та переносні заміни.

![Архітектурна заміна башизмів на переносні еквіваленти POSIX sh](/root/sys/sys-unix/portable-shell/img/bashism-replacement-patterns.svg)

*Каталог перетворення синтаксичних розширень Bash у надійні конструкції стандарту POSIX.*

### 1. Перевірка умов: `[[ ]]` проти `[ ]` та `test`

У Bash конструкція `[[ expr ]]` є **ключовим словом парсера** (keyword). Інтерпретатор обробляє вираз всередині `[[ ]]` за особливими правилами: він вимикає поділ на слова за змінною `IFS` (word splitting) та розгортання імен файлів за масками (pathname expansion/globbing). Крім того, `[[ ]]` підтримує логічні оператори `&&` і `||`, оператор зіставлення за маскою `==` та перевірку регулярних виразів `=~`.

У чистому POSIX sh конструкції `[[ ]]` не існує — вона викликає фатальну синтаксичну помилку розбору `syntax error: unexpected word`. Єдиним стандартним механізмом перевірки умов є команда `[` (синонім утиліти `test`).

Команда `[` — це **звичайна команда** (хоч і реалізована як builtin для оптимізації). Це означає, що оболонка виконує всі стандартні розгортання змінних та розщеплення на слова **до того**, як команда `[` почне аналізувати аргументи. Звідси виникають дві критичні вразливості непереносного коду:

```sh
# Помилка: неквотована змінна у [ ]
x=""
if [ -n $x ]; then
    echo "Змінна непорожня!"
fi
```

Коли змінна `$x` порожня або не визначена, оболонка розгортає рядок `[ -n $x ]` у виклик з єдиним аргументом: `[ -n ]`. За стандартом POSIX, команда `test` з одним аргументом повертає істину (`0`), якщо цей аргумент непорожній. Оскільки рядок `"-n"` сам по собі є непорожнім текстом, умова повертає істину (`true`). Виникає тиха логічна помилка: умова виконується тоді, коли змінна `$x` порожня.

За правилами POSIX sh **кожна змінна всередині `[` зобов'язана бути в лапках**: `[ -n "$x" ]`. Тоді команда бачить аргументи `[` `"-n"` `""` `]` і коректно повертає хибу (`false`).

Друга небезпека — логічні оператори `-a` (AND) та `-o` (OR) всередині `[ ]`. Стандарт POSIX оголосив використання `-a` та `-o` застарілим і невизначеним (unspecified) при кількості аргументів понад 4. Якщо змінна містить символи `=`, `!` чи `(`, парсер `test` не може відрізнити оператор від значення.

Переносне порівняння реалізується виключно роздільними командами через оператори оболонки `&&` та `||`, а порівняння рядків виконується тільки одинарним знаком `=` (оператор `==` у `[` є башизмом):

```sh
# Непереносний варіант (Bash):
# [[ "$status" == "active" && ( "$count" -gt 0 || "$force" == "true" ) ]]

# Переносний еквівалент POSIX sh:
[ "$status" = "active" ] && { [ "$count" -gt 0 ] || [ "$force" = "true" ]; }
```

Якщо потрібна перевірка відповідності рядка шаблону або регулярному виразу (аналог `=~`), у POSIX sh використовують конструкцію `case ... in`:

```sh
# Заміна regex перевірки [[ "$input" =~ ^[0-9]+$ ]]
case "$input" in
    ''|*[!0-9]*)
        echo "Помилка: $input не є числом" >&2
        return 1
        ;;
    *)
        echo "Коректне число: $input"
        ;;
esac
```

Зверніть увагу: у шаблоні `case` заперечення символьного класу записується знаком оклику `[!0-9]`, а не дашком `[^0-9]`.

### 2. Підстановка процесів `<(cmd)` та Here-Strings `<<<`

Конструкція підстановки процесів `diff <(command1) <(command2)` дозволяє передати вивід однієї або кількох програм утилітам, які очікують аргументи-шляхи до файлів. Bash реалізує це через системні псевдофайли `/dev/fd/N` або створення невидимих іменованих каналів.

У POSIX sh підстановка `<()` відсутня і викликає синтаксичну аварію. Якщо потрібно порівняти вивід двох команд, переносний скрипт явно створює тимчасові файли або іменовані канали (`FIFO`):

```sh
# Переносне порівняння виводу через тимчасові файли
tmp1=$(mktemp "${TMPDIR:-/tmp}/cmp1.XXXXXX")
tmp2=$(mktemp "${TMPDIR:-/tmp}/cmp2.XXXXXX")
trap 'rm -f "$tmp1" "$tmp2"' EXIT INT TERM HUP

command1 > "$tmp1"
command2 > "$tmp2"
diff "$tmp1" "$tmp2"
```

Аналогічно, конструкція Here-String `command <<< "$variable"` замінюється на стандартний `printf`:

```sh
# Башизм:
# grep "error" <<< "$log_data"

# Переносний POSIX sh:
printf '%s\n' "$log_data" | grep "error"
```

### 3. Пастка конвеєрів та субшелів (Subshell in Pipeline)

Один із найпідступніших башизмів пов'язаний не з синтаксисом, а з моделлю процесів. Розглянемо підрахунок кількості рядків:

```sh
total=0
printf "a\nb\nc\n" | while IFS= read -r line; do
    total=$((total + 1))
done
echo "Всього: $total"
```

У GNU Bash цей код може надрукувати `Всього: 3` (якщо увімкнено опцію `lastpipe` або в деяких внутрішніх оптимізаціях). Але за стандартом POSIX **кожен елемент конвеєра (`cmd1 | cmd2`) має право виконуватися в окремому дочірньому процесі (subshell)**.

У `dash`, FreeBSD `sh` та багатьох інших інтерпретаторах цикл `while` виконується у форкнутому субшелі. Змінна `total` всередині циклу збільшується до 3, але після завершення циклу субшел завершується, його пам'ять звільняється, а батьківський процес продовжує виконання зі старим значенням `total=0`.

Щоб змінна зберегла свій стан, перенаправлення введення виконують безпосередньо у цикл, уникаючи конвеєра:

```sh
total=0
while IFS= read -r line; do
    total=$((total + 1))
done <<EOF
a
b
c
EOF
echo "Всього: $total"  # Гарантовано надрукує 3 у всіх оболонках
```

Якщо дані надходять від команди, їх зберігають у тимчасовий файл або передають через перенаправлення всього блоку:

```sh
total=0
tmp_data=$(mktemp)
generate_items > "$tmp_data"

while IFS= read -r item; do
    [ -n "$item" ] || continue
    total=$((total + 1))
done < "$tmp_data"
rm -f "$tmp_data"
```

### 4. Оголошення функцій та ключове слово `local`

У Bash функції часто оголошують через ключове слово `function`:

```sh
function my_func() { ... }  # Башизм!
function my_func { ... }    # Башизм!
```

Стандарт POSIX визнає єдиний синтаксис оголошення функції — ім'я та порожні круглі дужки:

```sh
my_func() {
    # Тіло функції
}
```

Ще складніша ситуація з ключовим словом `local`. Стандарт POSIX IEEE 1003.1 взагалі **не містить концепції локальних змінних функцій**: усі змінні у POSIX sh є глобальними в межах поточного процесу оболонки.

Хоча більшість сучасних інтерпретаторів (`dash`, `ash`, `busybox`, `FreeBSD sh`) підтримують `local` як де-факто розширення, з ним пов'язана фатальна помилка маскування кодів виходу:

```sh
my_func() {
    local data=$(faulty_command)  # ПОМИЛКА!
    echo "Код виходу: $?"
}
```

У цьому прикладі команда `faulty_command` падає з кодом помилки `1`. Але вбудована команда `local` успішно створює локальну змінну `data` і повертає статус `0`. Інструкція `local data=$(...)` перезаписує змінну `$?` значенням `0`, маскуючи падіння команди.

У строгому переносному коді оголошення та присвоєння завжди розділяють, або ізолюють функцію у субшелі:

```sh
# Варіант 1: Роздільне оголошення (якщо local підтримується системним sh)
my_func() {
    local data
    data=$(faulty_command) || return 1
    process "$data"
}

# Варіант 2: Повна ізоляція через субшел (100% POSIX)
# Круглі дужки замість фігурних виконують тіло у форкнутому субшелі
my_isolated_func() (
    data=$(faulty_command) || exit 1
    # Усі змінні автоматично знищаться при виході з субшела
    process "$data"
)
```

### 5. Масиви проти позиційних параметрів

У Bash масиви (`arr=(a b c)`, `${arr[i]}`, `${#arr[@]}`) є незамінним інструментом для обробки списків, чиї елементи можуть містити пробіли, символи нового рядка або спецсимволи.

У чистому POSIX sh масивів немає. Але є один-єдиний стандартизований масив — **список позиційних параметрів** (`$1`, `$2`, ..., `$@`).

Будь-який список елементів з пробілами у переносному коді зберігається у позиційних параметрах через команду `set --`:

```sh
# Замість башизму: files=( "звіт за травень.txt" "дані 2026.csv" )
# POSIX sh еквівалент:
set -- "звіт за травень.txt" "дані 2026.csv"

# Додавання елемента до списку:
set -- "$@" "новий файл.log"

# Кількість елементів:
echo "Всього елементів: $#"

# Поелементна ітерація з гарантованим збереженням пробілів:
for file in "$@"; do
    printf 'Обробка: %s\n' "$file"
done
```

Специфікатор `"$@"` (обов'язково в подвійних лапках) розгортається інтерпретатором у точний список окремих аргументів `"$1"` `"$2"` ..., не розбиваючи пробіли всередині елементів.

### 6. Розширення параметрів: зрізи, заміна та регістр

Bash надає багатий арсенал операцій над рядками:
- Зрізи підрядків: `${var:offset:length}`
- Пошук і заміна: `${var//pattern/replacement}`
- Зміна регістру: `${var^^}`, `${var,,}`

Жодної з цих операцій у POSIX sh немає. Стандарт гарантує підтримку лише восьми базових форм розгортання параметрів:

| Оператор POSIX | Дія | Приклад значення (`f="path/to/file.tar.gz"`) |
|---|---|---|
| `${var#pattern}` | Видалення найкоротшого префіксу | `${f#*/}` → `"to/file.tar.gz"` |
| `${var##pattern}` | Видалення найдовшого префіксу | `${f##*/}` → `"file.tar.gz"` |
| `${var%pattern}` | Видалення найкоротшого суфіксу | `${f%.*}` → `"path/to/file.tar"` |
| `${var%%pattern}` | Видалення найдовшого суфіксу | `${f%%.*}` → `"path/to/file"` |
| `${#var}` | Довжина рядка в символах | `${#f}` → `21` |
| `${var:-default}` | Значення за замовчуванням, якщо `$var` порожня/не визначена | `${port:-8080}` |
| `${var:=default}` | Присвоїти значення, якщо `$var` порожня/не визначена | `${timeout:=30}` |
| `${var:?message}` | Зупинити скрипт з помилкою, якщо `$var` порожня | `${API_KEY:?"API_KEY обов'язковий"}` |

Якщо у переносному скрипті потрібно виділити підрядок чи виконати глобальну заміну, викликають стандартні утиліти `sed`, `cut` або `awk`:

```sh
# Заміна башизму: ext="${filename##*.}" (це підтримується POSIX!)
# Заміна зрізу ${str:0:4}:
prefix=$(printf '%s' "$str" | cut -c 1-4)

# Заміна підстановки ${str//foo/bar}:
replaced=$(printf '%s' "$str" | sed 's/foo/bar/g')
```

### 7. ANSI-C лапки `$'...'` та екранування

У Bash запис `$'hello\nworld\t\x1b[31m'` дозволяє створювати рядки з екранованими керуючими символами (переходи на новий рядок, табуляції, ANSI-кольори).

У POSIX sh (до редакції 2024 року) запис `$'...'` не є синтаксичною конструкцією: інтерпретатор сприймає знак долара як окремий символ або помилку, а вміст лапок залишає як є. Переносний спосіб створення змінних із керуючими символами полягає у виклику `printf`:

```sh
# Башизм:
# TAB=$'\t'
# NL=$'\n'

# Переносний POSIX sh:
TAB=$(printf '\t')
NL=$(printf '\n')
CR=$(printf '\r')
```

### 8. Арифметика: цілочисельні межі та відсутність систем числення

Арифметичне розширення `$(( expression ))` повністю стандартизоване у POSIX sh. Підтримуються всі стандартні цілочисельні оператори мови C: додавання `+`, віднімання `-`, множення `*`, цілочисельне ділення `/`, остача `%`, побітові операції `<<`, `>>`, `&`, `|`, `^`, `~` та тернарний оператор `? :`.

Проте виходити за межі цілих чисел стандарт забороняє:
1. **Дробові числа**: вираз `$(( 3.14 * 2 ))` викликає помилку у будь-якому sh. Для роботи з числами з плаваючою комою використовують утиліту `awk` або калькулятор `bc`:
   ```sh
   res=$(awk -v a=3.14 -v b=2 'BEGIN { printf "%.2f\n", a * b }')
   ```
2. **Базові системи числення**: запис на кшталт `$(( 16#FF ))` або `$(( 2#1010 ))` є розширенням Bash/Ksh. У POSIX sh шістнадцяткові числа записують з префіксом `0x` (`$(( 0xFF ))`), вісімкові — з префіксом `0` (`$(( 0755 ))`), а довільні основи обчислюють через `bc` чи `printf '%d'`.

### 9. Невизначеність утиліти `echo`

Команда `echo` є одним із найдавніших джерел несумісності в Unix. Історично гілка BSD підтримувала прапорець `echo -n` для запобігання переходу на новий рядок, тоді як гілка System V підтримувала екрановані послідовності `echo "text\c"`.

Стандарт POSIX зафіксував цей розкол: **поведінка `echo` при передачі прапорця `-n` або зворотних скісних рисок `\` визначається реалізацією (implementation-defined)**. У багатьох оболонках (наприклад, у `dash` або на BSD) команда `echo -n "foo"` надрукує рядок `-n foo`.

Залізне правило переносного коду: **повна відмова від `echo` на користь `printf`**. Утиліта `printf` стандартизована у POSIX до дрібниць і поводиться ідентично на всіх платформах:

```sh
# Завжди переносно:
printf '%s\n' "$message"      # Друк рядка з переходом
printf '%s' "$prompt"         # Друк без переходу на новий рядок (заміна echo -n)
printf 'Значення: %d, Рядок: %s\n' "$num" "$str"
```

## Війна утиліт: GNU Coreutils проти BSD та macOS Userland

Навіть якщо сценарій написаний чистою мовою POSIX sh без жодного башизму, він може впасти через несумісність зовнішніх утиліт оточення (userland tools). Дистрибутиви Linux постачаються з набором GNU Coreutils, тоді як macOS, FreeBSD, OpenBSD та NetBSD використовують власний набір утиліт гілки BSD.

![Розбіжності системних утиліт: GNU Coreutils проти BSD / macOS Userland](/root/sys/sys-unix/portable-shell/img/gnu-vs-bsd-utilities-matrix.svg)

*Критичні відмінності в ключах та поведінці базових утиліт між дистрибутивами Linux та BSD/macOS.*

### 1. `sed -i` (Редагування файлів на місці)

Прапорець `-i` (in-place) не входить до стандарту POSIX (у стандартному `sed` взагалі немає редагування на місці). Його реалізували обидві гілки, але з різним синтаксисом:
- **GNU sed**: аргумент суфікса резервної копії є необов'язковим. Команда `sed -i 's/foo/bar/g' config.txt` перезаписує файл без створення бекапу.
- **BSD sed (macOS / FreeBSD)**: прапорець `-i` **вимагає обов'язкового суфікса**. Щоб редагувати без створення бекапу, потрібно передати порожній рядок: `sed -i '' 's/foo/bar/g' config.txt`.

Якщо ви виконаєте `sed -i 's/foo/bar/g' config.txt` на macOS, BSD `sed` сприйме рядок `'s/foo/bar/g'` як розширення резервної копії, створить файл `config.txts/foo/bar/g`, а ім'я `config.txt` спробує виконати як команду `sed` і впаде.

Якщо ж ви виконаєте BSD-версію `sed -i '' 's/foo/bar/g' config.txt` на Linux з GNU sed, інтерпретатор сприйме `''` як вираз `sed`, впаде з помилкою `sed: -e expression #1, char 1: unknown command: '''` і зупинить скрипт.

Переносні рішення:

```sh
# Варіант 1 (Рекомендований): Тимчасовий файл (100% переносність)
sed 's/foo/bar/g' config.txt > config.txt.tmp && mv -f config.txt.tmp config.txt

# Варіант 2: Явний суфікс бекапу з подальшим видаленням
sed -i.bak 's/foo/bar/g' config.txt && rm -f config.txt.bak
```

### 2. `date` (Парсинг та форматування часових позначок)

Маніпуляція часом та обчислення Epoch відрізняються радикально:
- **GNU date**: підтримує прапорець `-d` для вільного парсингу дат (`date -d "2026-08-25 +1 day"` або `date -d "@1700000000"`).
- **BSD date**: не підтримує `-d`. Для парсингу використовує прапорці `-j -f` (`date -j -f "%Y-%m-%d" "2026-08-25" "+%s"`), а для зміщення — `-v+1d`. Для читання Epoch використовує `-r 1700000000`.

Для отримання поточного часу в секундах від початку епохи (Unix Epoch) формат `date +%s` підтримується практично скрізь як фактичний стандарт. Якщо ж потрібні складні обчислення дат у чистому POSIX, використовують `awk`:

```sh
# Переносне отримання поточної секунди Epoch без розширень date
epoch_now=$(awk 'BEGIN{srand(); print srand()}')
```

### 3. `grep` (Регулярні вирази)

Прапорець `grep -P` (Perl-Compatible Regular Expressions, PCRE) є розширенням GNU grep, що лінкується з бібліотекою `libpcre`. На BSD-системах, macOS та в BusyBox прапорець `-P` або відсутній, або вимагає встановлення сторонніх пакунків.

Переносний код використовує розширені регулярні вирази POSIX (ERE) через команду `grep -E` (або `egrep`) разом зі стандартними символьними класами:

```sh
# Непереносний GNU grep з Perl-символами \d, \s, \w:
# grep -P '^\d{4}-\d{2}-\d{2}\s+[A-Z]+' log.txt

# Переносний POSIX ERE еквівалент:
grep -E '^[0-9]{4}-[0-9]{2}-[0-9]{2}[[:space:]]+[A-Z]+' log.txt
```

### 4. `find` та `xargs`

GNU `find` містить безліч зручних прапорців, які відсутні у стандарті POSIX:
- `-maxdepth N` та `-mindepth N` (обмеження глибини обходу)
- `-delete` (видалення знайдених файлів)
- `-empty` (пошук порожніх файлів)

У чистому POSIX обхід обмежують за допомогою дії `-prune`:

```sh
# Обмеження пошуку поточним каталогом (аналог -maxdepth 1):
find . -path './*/*' -prune -o -type f -print

# Переносне безпечне видалення файлів (заміна -delete):
find . -type f -name '*.tmp' -exec rm -f {} +
```

Конструкція `-exec rm -f {} +` агрегує знайдені файли в один виклик команди (аналогічно `xargs`), що значно швидше за поелементний виклик `-exec rm -f {} \;` і гарантовано обробляє імена файлів з пробілами.

Щодо `xargs`: прапорець `xargs -r` (`--no-run-if-empty`), який забороняє запуск команди при порожньому стандартному вводі, є специфічним для GNU. BSD `xargs` за замовчуванням може виконати команду один раз без аргументів.

### 5. Пошук каталогу сценарію: `readlink -f` проти `pwd -P`

Поширена задача — дізнатися абсолютний каталог, у якому лежить сам скрипт, щоб завантажити конфігурацію чи сусідні файли. У Linux часто пишуть:

```sh
SCRIPT_DIR=$(dirname "$(readlink -f "$0")")  # Ламається на macOS!
```

На macOS утиліта `readlink` не підтримує ключ `-f`. Канонічний, 100% переносний патерн визначення каталогу скрипта без сторонніх утиліт виглядає так:

```sh
SCRIPT_DIR=$(CDPATH= cd -- "$(dirname -- "$0")" && pwd -P)
```

Розбір роботи цього рядка:
1. `CDPATH=`: очищує змінну оточення `CDPATH`, яка в деяких оболонках може перехопити команду `cd` і вивести шлях у stdout.
2. `dirname -- "$0"`: отримує каталог розташування файлу скрипта. Захисний маркер `--` гарантує, що шлях, який починається з дефісу (наприклад, `./-dir/script.sh`), не буде сприйнято як прапорець.
3. `cd ... && pwd -P`: переходить у каталог і запитує фізичний абсолютний шлях (`-P`, physical) із розгортанням усіх символьних посилань.

### 6. Перевірка наявності утиліти: `which` проти `command -v`

Утиліта `which` ніколи не була стандартизована у POSIX. На різних системах `which` є або двійковим файлом, або csh-скриптом, або аліасом. Ба більше: на деяких комерційних Unix `which` при відсутності команди повертає код виходу `0`, друкуючи повідомлення про помилку в stdout.

Стандартний і надійний спосіб перевірки наявності програми, функції чи вбудованої команди в POSIX sh — це вбудована команда `command -v`:

```sh
# Перевірка наявності утиліти jq
if command -v jq >/dev/null 2>&1; then
    printf 'jq знайдено: %s\n' "$(command -v jq)"
else
    printf 'Помилка: утиліту jq не встановлено\n' >&2
    exit 1
fi
```

Команда `command -v` повертає статус `0`, якщо команда існує у `$PATH`, і ненульовий статус, якщо ні.

### 7. Локаль і сортування (`LC_ALL=C`)

Поведінка таких утиліт як `sort`, `grep`, `awk` та діапазонів масок `[a-z]` у shell напряму залежить від активної локалі системи (`LANG`, `LC_COLLATE`).

Якщо на хості встановлено локаль `en_US.UTF-8`, сортування рядків утилітою `sort` ігнорує регістр або сортує знаки пунктуації за складними правилами словникового порядку. Ба більше: у турецькій локалі `tr_TR.UTF-8` великою літерою для `i` є `İ`, що ламає порівняння імен служб чи заголовків HTTP.

Переносний сценарій на самому початку зобов'язаний зафіксувати детерміновану стандартну локаль `C` (базовий ASCII байтовий порядок):

```sh
export LC_ALL=C
export LC_COLLATE=C
```

Це гарантує, що `sort` впорядковує байти строго за ASCII-значеннями (0..127), діапазон `[a-z]` охоплює виключно 26 малих латинських літер, а утиліта `grep` працює в рази швидше через відсутність витрат на розбір багатобайтового UTF-8.

### 8. Робота з архівами `tar`

У GNU `tar` прапорці розпакування нерідко опускають взагалі або використовують автовизначення: `tar -xf archive.tar.gz` автоматично викликає `gzip`. На старіших BSD-системах та в Solaris `tar` вимагав явного прапорця або взагалі не підтримував роботу зі стисненими архівами через ключі `-z` чи `-j`.

Гарантовано переносний спосіб розпакування будь-якого архіву — явний конвеєр:

```sh
# Розпакування gzip-архіву через стандартний потік:
gzip -dc archive.tar.gz | tar -xf -

# Створення tar.gz архіву:
tar -cf - -C "$SRC_DIR" . | gzip -9 > "$DEST_ARCHIVE"
```

## Статичний контроль та верифікація переносності

Ручний контроль кожного рядка коду на наявність башизмів є трудомістким. Для автоматичної перевірки скриптів у конвеєрах CI/CD застосовують спеціалізовані інструменти статичного аналізу та мультиядерного тестування.

### 1. Утиліта `checkbashisms`

`checkbashisms` — це скрипт на Perl з пакету `devscripts` (створений розробниками Debian для аудиту пакетних скриптів), який сканує сценарій за допомогою регулярних виразів і шукає відомі непереносні конструкції.

```sh
$ checkbashisms -p deploy.sh
possible bashism in deploy.sh line 14 (local foo=bar):
    local config=$(cat "$cfg")
possible bashism in deploy.sh line 28 ($"foo" should be eval_gettext "foo"):
    echo $"Starting service"
possible bashism in deploy.sh line 42 (type):
    type my_cmd >/dev/null 2>&1
```

Прапорці `checkbashisms`:
- `-p` (`--posix`): посилена перевірка на конструкції, які не дозволені стандартом POSIX, але підтримуються окремими діалектами.
- `-n` (`--newline`): перевірка використання неекранованих переходів рядка всередині подвійних лапок `echo "..."`.
- `-f` (`--force`): примусова перевірка навіть тоді, коли скрипт має шебанг `#!/bin/bash`.

### 2. Аналізатор `shellcheck`

`shellcheck` — це повноцінний компіляторний лінтер, який будує абстрактне синтаксичне дерево (AST) скрипта. Щоб увімкнути суворий режим перевірки на відповідність стандарту POSIX sh, передають прапорець `-s sh`:

```sh
$ shellcheck -s sh deploy.sh

In deploy.sh line 12:
    [[ -d "$target_dir" ]] || mkdir -p "$target_dir"
    ^--------------------^
SC3010 (warning): In POSIX sh, [[ ]] is undefined.

In deploy.sh line 19:
    local status="running"
    ^----------^
SC3043 (warning): In POSIX sh, 'local' is undefined.

In deploy.sh line 34:
    diff <(generate_old) <(generate_new)
         ^-------------^
SC3001 (warning): In POSIX sh, process substitution is undefined.
```

`shellcheck` кодує всі зауваження переносності діапазоном кодів `SC3000–SC3060`. У конвеєрах неперервної інтеграції (CI) перевірку оформлюють як обов'язковий гейт:

```sh
shellcheck --shell=sh --severity=warning scripts/*.sh
```

### 3. Мультиінтерпретаторна верифікація синтаксису

Найкращий спосіб переконатися, що скрипт не впаде на цільових системах — перевірити його розбір кількома реальними рушіями за допомогою прапорця `-n` (noexec, синтаксична перевірка без виконання коду):

```sh
# Перевірка синтаксису в трьох незалежних інтерпретаторах:
dash -n my_script.sh
busybox ash -n my_script.sh
ksh -n my_script.sh
```

Якщо скрипт успішно проходить `dash -n` та `shellcheck -s sh`, імовірність синтаксичних збоїв на будь-якому Unix наближається до нуля.

### 4. Вибір коректного Shebang

Шебанг на початку файлу декларує намір автора:

```sh
#!/bin/sh
```
Вказує, що сценарій написаний строго за стандартом POSIX sh. Скрипт зобов'язаний виконуватися будь-якою системною оболонкою (`dash`, `ash`, `sh`).

Якщо ж сценарій свідомо використовує розширені можливості Bash (складні асоціативні масиви, керування завданнями, regex), у шебанзі **заборонено писати `#!/bin/sh`**. Слід явно вимагати Bash, причому використовуючи утиліту `env` для переносного пошуку бінарника:

```sh
#!/usr/bin/env bash
```

Шлях `#!/usr/bin/env bash` гарантує, що інтерпретатор буде знайдено і на Linux (`/usr/bin/bash`), і на FreeBSD (`/usr/local/bin/bash`), і на NixOS чи macOS (`/opt/homebrew/bin/bash`), де бінарники Bash розташовані у нестандартних шляхах.

## Патерни побудови надійного переносного POSIX sh сценарію

Зведемо описані правила у цілісний інженерний шаблон написання виробничого переносного сценарію.

### 1. Преамбула суворого режиму та локаль

На початку скрипта встановлюють прапорці безпеки та фіксують локаль:

```sh
#!/bin/sh
set -eu
export LC_ALL=C
export LC_COLLATE=C
```

- `set -e`: зупиняє виконання сценарію при поверненні будь-якою командою ненульового коду завершення (окрім умов `if`, `while`, `until` або операцій з `||`).
- `set -u`: вважає звернення до будь-якої неініціалізованої змінної фатальною помилкою і зупиняє виконання.

> ⚠️ **Застереження щодо `set -o pipefail`.** Прапорець `pipefail` (який змушує весь конвеєр `cmd1 | cmd2` повертати статус помилки, якщо хоч один його компонент впав) не був частиною стандарту POSIX.1-2008 (його додано лише у редакцію 2024 року). Старі версії `dash` та `ash` не підтримують `set -o pipefail` і падають. Якщо підтримка pipefail бажана, але не гарантована, її вмикають захищеним викликом:

```sh
# Безпечне увімкнення pipefail за наявності підтримки
(set -o pipefail 2>/dev/null) && set -o pipefail || true
```

### 2. Структуроване логування

Вивід діагностики та повідомлень про помилки організовують через допоміжні функції, які пишуть строго у дескриптор stderr (`>&2`):

```sh
log_info() {
    printf '[INFO] %s\n' "$*" >&2
}

log_warn() {
    printf '[WARN] %s\n' "$*" >&2
}

die() {
    printf '[FATAL] %s\n' "$*" >&2
    exit 1
}
```

### 3. Атомарне блокування без `flock`

Утиліта `flock` є специфічною для пакету `util-linux` і відсутня на BSD/macOS. Єдиний переносний спосіб атомарного взаємного виключення (mutex) у POSIX — використання системного виклику `mkdir`. Створення каталогу виконується ядром атомарно на рівні VFS:

```sh
LOCKDIR="${TMPDIR:-/tmp}/my_script.lock"

acquire_lock() {
    if mkdir "$LOCKDIR" 2>/dev/null; then
        return 0
    else
        log_warn "Скрипт уже виконується (каталог блокування $LOCKDIR зайнятий)"
        return 1
    fi
}

release_lock() {
    rmdir "$LOCKDIR" 2>/dev/null || true
}
```

### 4. Обробка опцій командного рядка через `getopts`

Зовнішня утиліта `getopt` не є переносною (GNU getopt підтримує довгі опції `--option` та перестановку аргументів, тоді як BSD getopt суворо обмежений).

Стандартний переносний спосіб парсингу ключів — вбудована команда `getopts`:

```sh
VERBOSE=0
OUTPUT_FILE=""

while getopts ":hvf:o:" opt; do
    case "$opt" in
        h)
            show_help
            exit 0
            ;;
        v)
            VERBOSE=$((VERBOSE + 1))
            ;;
        f|o)
            OUTPUT_FILE="$OPTARG"
            ;;
        :)
            die "Опція -$OPTARG вимагає аргументу."
            ;;
        \?)
            die "Невідома опція -$OPTARG."
            ;;
    esac
done
# Зсув оброблених опцій: далі у $@ залишаються тільки позиційні аргументи
shift "$((OPTIND - 1))"
```

Символ двокрапки на початку рядка опцій (`":hvf:o:"`) вмикає так званий тихий режим (silent mode), дозволяючи скрипту самостійно перехоплювати відсутні аргументи (`:`) та невідомі прапорці (`\?`).

### 5. Створення тимчасових каталогів та прибирання ресурсів

Надійне прибирання ресурсів реєструється через `trap`:

```sh
TMPDIR="${TMPDIR:-/tmp}"
# Переносне створення захищеного тимчасового каталогу
WORKDIR=$(mktemp -d "${TMPDIR}/app.XXXXXX" 2>/dev/null || mktemp -d -t 'app')

cleanup() {
    exit_code=$?
    release_lock
    rm -rf "$WORKDIR"
    exit "$exit_code"
}
# Реєстрація сигналів за стандартними символьними іменами (без префіксу SIG)
trap cleanup EXIT INT TERM HUP
```

### 6. Порівняльний приклад реалізації задачі

Порівняємо типовий сценарій збору діагностики двома мовами: з використанням башизмів та у строгому переносному стилі POSIX sh.

:::tabs
```bash
#!/usr/bin/env bash
# Непереносний варіант: використовує розширення GNU Bash
set -euo pipefail

declare -A SERVICES=( [nginx]="/var/log/nginx" [db]="/var/log/postgresql" )
declare -a LOG_FILES=()

read_logs() {
    local svc=$1
    local dir=${SERVICES[$svc]}
    
    [[ -d "$dir" ]] || { echo "Пропуск $svc: нема каталогу"; return 0; }
    
    while IFS= read -r -d '' file; do
        LOG_FILES+=("$file")
    done < <(find "$dir" -maxdepth 1 -name "*.log" -print0)
}

for s in "${!SERVICES[@]}"; do
    read_logs "$s"
done

echo -n "Знайдено файлів: ${#LOG_FILES[@]} ... "
grep -P '^\d{4}-\d{2}-\d{2}.*(ERROR|FATAL)' "${LOG_FILES[@]}" \
    | sed -i 's/token=[^ ]+/token=***/g' report.txt
echo "Завершено."
```
```sh
#!/bin/sh
# Гарантовано переносний варіант: працює на dash, ash, FreeBSD sh, macOS
set -eu
export LC_ALL=C
export LC_COLLATE=C
(set -o pipefail 2>/dev/null) && set -o pipefail || true

# Замість масиву: позиційні параметри пари "служба:шлях"
set -- "nginx:/var/log/nginx" "db:/var/log/postgresql"

TMP_LIST=$(mktemp "${TMPDIR:-/tmp}/logs.XXXXXX")
TMP_REPORT=$(mktemp "${TMPDIR:-/tmp}/rep.XXXXXX")

cleanup() {
    status=$?
    rm -f "$TMP_LIST" "$TMP_REPORT"
    exit "$status"
}
trap cleanup EXIT INT TERM HUP

# Обхід пар без використання асоціативних масивів
for pair in "$@"; do
    svc="${pair%%:*}"
    dir="${pair#*:}"
    
    if [ -d "$dir" ]; then
        # Переносне обмеження глибини каталогу без -maxdepth
        find "$dir" -path "$dir/*/*" -prune -o -type f -name "*.log" -print >> "$TMP_LIST"
    else
        printf 'Пропуск %s: нема каталогу %s\n' "$svc" "$dir" >&2
    fi
done

file_count=0
if [ -s "$TMP_LIST" ]; then
    file_count=$(wc -l < "$TMP_LIST" | tr -d '[:space:]')
fi
printf 'Знайдено файлів: %s ... ' "$file_count"

if [ "$file_count" -gt 0 ]; then
    # Переносний ERE regex замість Perl -P
    xargs grep -E '^[0-9]{4}-[0-9]{2}-[0-9]{2}.*(ERROR|FATAL)' < "$TMP_LIST" \
        | sed 's/token=[^ ]*/token=***/g' > "$TMP_REPORT"
    mv -f "$TMP_REPORT" report.txt
fi

printf 'Завершено.\n'
```
:::

Переносний варіант повністю позбавлений залежностей від версії інтерпретатора, не спирається на наявність GNU Coreutils і гарантує детерміноване виконання у будь-якому оточенні POSIX-сумісної операційної системи.
