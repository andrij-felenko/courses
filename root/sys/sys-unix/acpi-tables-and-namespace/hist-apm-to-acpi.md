# 📜 Від APM до ACPI: як операційна система забрала контроль над залізом у прошивки

Коли в першій половині 1990-х років портативні комп'ютери почали масово виходити на ринок, розробники зіткнулися з новою фундаментальною перешкодою: операційна система MS-DOS чи ранній Linux поняття не мали, як зменшити споживання енергії процесором чи вимкнути живлення неактивного жорсткого диска. Щоб розв'язати цю проблему, компанії Intel та Microsoft у 1992 році створили стандарт APM (Advanced Power Management). Проте перехід від APM 1992 року до стандарту ACPI, розробленого у 1996 році консорціумом Intel, Microsoft, Toshiba, HP та Phoenix, виявився не просто еволюцією API, а радикальною зміною архітектурної парадигми: відповідальність за керування живленням і конфігурацією обладнання остаточно перейшла від закритих 16-бітних переривань BIOS до ядра операційної системи в рамках концепції OSPM (OS-directed Power Management).

## Архітектурна модель APM та її фундаментальні обмеження

У системі з APM вся логіка підтримання енергозбереження містилася всередині прошивки BIOS материнської плати. Операційна система зверталася до BIOS через переривання `INT 15h` (у 16-бітному реальному режимі) або через спеціальні точки входу реального/захищеного режиму (APM BIOS entry points).

З точки зору операційної системи APM виглядала як чорна скринька. Коли системний планувальник (scheduler) ядра бачив, що в черзі виконання немає готових процесів, він викликав функцію `APM CPU Idle` через переривання. Прошивка BIOS перехоплювала керування, виконувала команду `HLT` на процесорі або знижувала його тактову частоту, а при появі переривання від таймера чи клавіатури повертала керування ОС.

```
+------------------------------------+
|  Операційна система (OS / Kernel)  |
+------------------------------------+
                  |  Виклики INT 15h (CPU Idle, Suspend)
                  v
+------------------------------------+
|             APM BIOS               | <--- Повна логіка керування
+------------------------------------+      (Таймери неактивності,
                  |                         Регістри чіпсета)
                  v
+------------------------------------+
|         Апаратне забезпечення      |
+------------------------------------+
```

Цей підхід мав три критичні архітектурні дефекти, які зробили його непридатним для багатозадачних та багатопроцесорних систем:

1. **Відсутність контексту пристроїв в операційній системі:** BIOS не мав уяви про те, що саме робить операційна система. Наприклад, якщо користувач запускав довготривалий фоновий обчислювальний процес без вводу з клавіатури, таймер неактивності всередині APM BIOS міг вирішити, що система простоює, і примусово присипляв жорсткий диск або переводив систему в режим сну (Suspend).
2. **Неможливість паралельної обробки у SMP (Symmetric Multiprocessing):** APM створювалася для одноядерних процесорів x86. BIOS виконував виклики у монопольному режимі з блокуванням переривань, що робило неможливим безпечний виклик APM з кількох процесорних ядер одночасно без ризику взаємних блокувань (deadlocks) у коді прошивки.
3. **Закритість та баги прошивок:** Операційна система не могла змінити алгоритм керування живленням. Якщо виробник материнської плати робив помилку у коді BIOS `INT 15h`, система незворотно зависала при спробі відновлення роботи (Resume). Розробники ядра Linux не мали доступу до коду BIOS і не могли виправити помилку у користувацькому просторі чи через оновлення ядра.

## Поява PnP BIOS та накопичення технічного боргу

Паралельно з APM у 1993 році з'явився стандарт Plug and Play BIOS (PnP BIOS). Його метою було вирішення проблеми конфліктів ресурсів (I/O портів, ліній переривань IRQ та каналів DMA) при підключенні нових карт розширення ISA та PCI.

PnP BIOS надавав операційній системі виклики для читання конфігураційних структур системних пристроїв (System Device Nodes). Проте PnP BIOS використовував той самий механізм реального/16-бітного захищеного режиму, що й APM. Щоб прочитати конфігурацію материнської плати, ядро Linux 2.0 мусило створювати тимчасові 16-бітні сегменти коду та даних у таблиці GDT (Global Descriptor Table) і перемикати контекст процесора.

Оскільки APM керував живленням, а PnP BIOS — ресурсами пристроїв, між ними виникали конфлікти: PnP BIOS міг перерозподілити лінії IRQ, про які APM BIOS не знав, що призводило до втрати подій пробудження пристроїв.

## Альянс 1996 року та маніфест OSPM

У грудні 1996 року консорціум у складі Intel, Microsoft, Toshiba, HP та Phoenix опублікував першу версію специфікації ACPI 1.0. Головною ідеєю стандарту стало формування концепції **OSPM (OS-directed Configuration and Power Management)**.

Головний принцип OSPM звучав так: *Прошивка комп'ютера повинна бути пасивним описувачем заліза, а операційна система — єдиним інтелектуальним центральним контролером.*

```
+------------------------------------+
|  Операційна система (OSPM Kernel)  | <--- Єдиний центр прийняття рішень
+------------------------------------+      (Scheduler, Drivers, Policy)
       |                      |
       | Читання              | Виконання AML / Запис у регістри
       v                      v
+--------------+      +-------------------------------+
| ACPI Tables  |      |   ACPICA (Interpreter & HW)   |
+--------------+      +-------------------------------+
       ^                      |
       | Завантаження         v
+--------------+      +-------------------------------+
|  UEFI / BIOS |      |    Апаратне забезпечення      |
+--------------+      +-------------------------------+
```

Замість того, щоб містити виконуваний 16-бітний машинозалежний код у прошивці, ACPI розділив взаємодію на два шари:

1. **Статичні структури даних (Static Tables):** Описують жорстку конфігурацію материнської плати (адреси APIC, бази PCI Express, розміщення регістрів живлення) на момент старту.
2. **Машинно-незалежний байт-код (AML):** Надає операційній системі безпечні абстрактні методи для увімкнення, вимкнення, зміни станів живлення та обробки подій без прямого доступу до приватних регістрів чіпсета.

## Опір виробників та еволюція ACPI

Перехід від APM до ACPI виявився болісним для екосистеми PC. У період з 1998 по 2004 рік більшість випущених материнських плат містили викривлені, недокомпільовані або відверто помилкові DSDT-таблиці. Виробники тестували ACPI AML-код лише на конкретних версіях Windows (Windows 98 SE або Windows XP). Якщо AML-код бачив, що операційна система не повідомляє про себе як Windows, він міг відмовитися вмикати живлення Wi-Fi адаптера або тачпада.

Саме для подолання цієї проблеми Лінус Торвальдс та розробники підсистеми ACPI у Linux створили механізми маскування підсистеми OS через метод `_OSI` (Operating System Interface). Драйвер ACPI у Linux за замовчуванням відповідає «Так» на запити AML-коду щодо сумісності з `Windows 2001`, `Windows 2006` та `Windows 2015`, змушуючи таблиці прошивки виконувати правильні гілки ініціалізації заліза.

З появою ACPI 2.0 (2000 рік) додалася підтримка 64-бітних адрес (XSDT), 64-бітних систем x86_64 та серверних архітектур IA-64 (Itanium). Далі ACPI 3.0 та 4.0 додали підтримку NUMA-топологій (SRAT/SLIT), гарячого підключення процесорів і пам'яті (CPU/Memory Hotplug), а в ACPI 5.0 (2011) та ACPI 6.x (2015-2024) стандарт поширився на архітектури ARM64 (AArch64) та RISC-V.

Таким чином, ACPI остаточно усунув APM та PnP BIOS з комп'ютерної індустрії, перетворивши ядро операційної системи на повновладного господаря системного заліза.
