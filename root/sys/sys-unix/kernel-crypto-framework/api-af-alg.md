# 📋 Інтерфейс сокетів AF_ALG та структури контрольних повідомлень

Інтерфейс `AF_ALG` (Address Family Algorithm) надає допуск до підсистеми Kernel Crypto API з простору користувача через стандартні системні виклики мережевих сокетів POSIX (`socket`, `bind`, `setsockopt`, `accept`, `sendmsg`, `recvmsg`). Це дозволяє програмам у просторі користувача застосовувати апаратно прискорені та FIPS-сертифіковані ядерні реалізації без того, щоб секретні ключі й дані проходили ще й через проміжні користувацькі бібліотеки.

## 1. Константи та адресація (`struct sockaddr_alg`)

Створення керівного сокета виконується викликом `socket(AF_ALG, SOCK_SEQPACKET, 0)`, де `AF_ALG` має числове значення `38` (ідентичне константі `PF_ALG`). Керівний сокет виступає у ролі фабрики контекстів і самі криптографічні дані через нього не передаються.

Прив'язка сокета до конкретного типу та назви алгоритму здійснюється через структуру `struct sockaddr_alg`, визначену в системному заголовку `<linux/if_alg.h>`:

```c
struct sockaddr_alg {
    __u16   salg_family;    /* Завжди AF_ALG (38) */
    __u8    salg_type[14];  /* Тип: "hash", "skcipher", "aead", "rng", "akcipher" */
    __u32   salg_feat;      /* Прапорці особливостей (типово 0) */
    __u32   salg_mask;      /* Маска бітів, які беруться до уваги (типово 0) */
    __u8    salg_name[64];  /* Назва алгоритму: "sha256", "cbc(aes)", "gcm(aes)" */
};
```

Поля `salg_type` та `salg_name` є нуль-термінованими рядками ASCII. Якщо ядро не має зареєстрованого драйвера для вказаної комбінації типу та імені, системний виклик `bind()` повертає помилку `-ENOENT`: пошук у реєстрі не дав результату навіть після спроби автозавантажити модуль.

Прапорці `salg_feat` та `salg_mask` дозволяють звузити пошук алгоритму в ядрі. Наприклад, встановлення прапорця `CRYPTO_ALG_ASYNC` у `salg_feat` та `salg_mask` вимагає від ядра саме асинхронної реалізації — зазвичай це апаратний драйвер на кшталт Intel QAT, хоча асинхронну обгортку над програмним кодом дає й шаблон `cryptd`. Якщо жодної асинхронної реалізації для цього імені немає, виклик `bind()` завершується помилкою.

## 2. Налаштування параметрів через `setsockopt()`

Конфігурація ключів шифрування та супутніх параметрів виконується на рівні сокета `SOL_ALG` (числове значення `279`):

| Опція `setsockopt` | Опис та тип даних | Призначення та механізм перевірки |
| :--- | :--- | :--- |
| `ALG_SET_KEY` | Масив байтів `u8[]` | Встановлення симетричного ключа шифрування чи HMAC-ключа. Ядро перевіряє довжину ключа відносно `min_keysize` та `max_keysize` драйвера. |
| `ALG_SET_KEY_BY_KEY_SERIAL` (ядра 6.x) | Ідентифікатор `key_serial_t` | Передача ключа із підсистеми `Kernel Keyring` (типи `user`, `logon`, `encrypted`, `trusted`) без появи самого секрету в просторі користувача; без права пошуку на ключ — `-EPERM`. |
| `ALG_SET_AEAD_AUTHSIZE` | Число `unsigned int` | Встановлення довжини тегу автентифікації у байтах для режимів AEAD (наприклад, 16 байтів для GCM). |

Виклик `accept()` на керівному сокеті не очікує мережевого підключення, а створює новий робочий файловий дескриптор. Цей дескриптор інкапсулює окремий екземпляр трансформації (`struct crypto_tfm`) та власні буфери стану. Якщо клієнт не має належних прав або вичерпано ліміти файлових дескрипторів, виклик повертає `-EMFILE` або `-ENFILE`. Робочий сокет успадковує ключі та конфігурацію від керівного сокета на момент здійснення `accept()`.

## 3. Контрольні повідомлення `sendmsg()` (Ancillary Data)

Передача вектора ініціалізації (IV), напрямку операції та довжини додаткових даних здійснюється через допоміжні дані (ancillary data / `cmsghdr`) у системному виклику `sendmsg()` до робочого сокета.

Структури та константи контрольних повідомлень:

```c
/* Контрольне повідомлення для вектора ініціалізації (IV) */
struct af_alg_iv {
    __u32   ivlen;      /* Довжина IV у байтах (наприклад, 16 для AES-CBC) */
    __u8    iv[0];      /* Блок IV (гнучкий масив байтів) */
};

/* Напрямок операції (передається як __u32 у макросі CMSG_DATA) */
#define ALG_OP_DECRYPT  0
#define ALG_OP_ENCRYPT  1

/* Нумерація спільна для optname у setsockopt() і для cmsg_type (рівень SOL_ALG) */
#define ALG_SET_KEY           1 /* setsockopt: ключ байтами */
#define ALG_SET_IV            2 /* Приймає struct af_alg_iv + байти вектора ініціалізації */
#define ALG_SET_OP            3 /* Приймає __u32: ALG_OP_ENCRYPT або ALG_OP_DECRYPT */
#define ALG_SET_AEAD_ASSOCLEN 4 /* Приймає __u32: довжина автентифікованих даних (AAD) */
#define ALG_SET_AEAD_AUTHSIZE 5 /* setsockopt: довжина тегу автентифікації */
```

Кожне контрольне повідомлення пакується за допомогою стандартних макросів `CMSG_FIRSTHDR`, `CMSG_NXTHDR` та `CMSG_DATA`. Напрямок задають явно: свіжостворений робочий сокет має `ALG_OP_DECRYPT` (значення 0), а далі зберігає напрямок від попереднього повідомлення. Якщо довжина IV у `af_alg_iv` не відповідає вимогам драйвера (наприклад, не дорівнює 16 байтам для AES-CBC), системний виклик `sendmsg()` повертає помилку `-EINVAL`.

У режимах шифрування із перевіркою автентичності (AEAD, наприклад AES-GCM або AES-CCM), структура передачі включає асоційовані дані (Associated Authenticated Data, AAD). Довжина AAD передається через контрольне повідомлення `ALG_SET_AEAD_ASSOCLEN`. У буфері даних, який надсилається до сокета, спочатку розміщуються AAD-байти, а за ними — корисне навантаження: при шифруванні це відкритий текст, при розшифруванні — шифротекст із тегом автентифікації в кінці. При зчитуванні результату через `recvmsg()` ядро повертає спершу ті самі AAD, а за ними — зашифровані дані з доданим тегом (при розшифруванні — перевірений відкритий текст), тож буфер читання має вміщати суму всіх трьох частин.

## 4. Безкопіювальний зсув даних (`splice`)

Для обробки великих файлів чи потоків даних без копіювання пам'яті між простором користувача та ядра `AF_ALG` підтримує системні виклики `splice()` та `vmsplice()`. Дані з файлового дескриптора джерела перенаправляються у конвеєр (pipe), звідки викликом `splice(pipe_fd, NULL, op_fd, NULL, len, SPLICE_F_MORE)` вони передаються безпосередньо у сторінки пам'яті криптографічного сокета. Це усуває копіювання даних у буфер користувача — самі системні виклики й перемикання в ядро при цьому нікуди не зникають.

## 5. Деталізований довідник кодів помилок

- `ENOENT` (`-2`): Запитаний алгоритм або тип у `salg_name` / `salg_type` не зареєстрований у ядрі або відповідний модуль ядра відсутній і не може бути автозавантажений.
- `EKEYREJECTED` (`-129`): Переданий ключ відхилено внутрішньою перевіркою `crypto_setkey()` (некоректна довжина ключа або використання заборонено FIPS-політикою).
- `EBADMSG` (`-74`): Помилка перевірки цілісності тегу автентифікації під час розшифрування у режимах AEAD (текст або тег пошкоджено, або передано хибний ключ). Розшифрованого тексту ядро в цьому разі не віддає.
- `EBUSY` (`-16`): Черга апаратного криптографічного прискорювача переповнена, і запит відхилено без блокування.
- `EINPROGRESS` (`-115`): Операцію прийнято до асинхронного виконання; результат буде надано через функцію зворотного виклику або при наступному читанні з сокета.
- `EACCES` / `EPERM` (`-13` / `-1`): Доступ до створення сокета `AF_ALG` або встановлення ключа заборонено політикою LSM (SELinux / AppArmor) або фільтром seccomp.
- `EINVAL` (`-22`): Некоректні параметри виклику (невірно вказана довжина IV, відсутність обов'язкового прапорця напрямку операції або неправильне вирівнювання буфера).
