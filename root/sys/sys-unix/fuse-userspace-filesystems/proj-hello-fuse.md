# ⚙️ Найменший справжній демон: файлова система, вміст якої ніде не лежить

Зберемо на `libfuse 3` файлову систему, у якій не зберігається жоден байт: усе, що вона показує, вона рахує в мить, коли її про це спитали. Користі з неї ніякої — зате крізь неї добре видно те, чого не видно крізь `sshfs`: скільки питань ядро насправді ставить на кожну вашу команду в оболонці і чому цих питань завжди більше, ніж здається.

## Задача

Змонтувати теку, у якій лежить ось таке:

```
/
├── hello        стала стрічка
├── now          поточний час, узятий у мить читання
├── stats        скільки викликів демон уже обслужив
└── squares/
    ├── 1        «1 · 1 = 1»
    ├── …
    └── 12       «12 · 12 = 144»
```

Ніякої підкладки на диску, ніякої бази. Файл `stats` тут не для краси: він показує лічильники власних викликів демона, тобто дає змогу поміряти ціну кожної команди, не вмикаючи налагоджувальний вивід.

## Ідея: чотири операції й одна функція вмісту

`libfuse` дає два інтерфейси. **Низькорівневий** говорить тими самими поняттями, що й протокол ядра: номери об'єктів, лічильники посилань, окрема відповідь на `lookup` і окрема на `forget`. **Високорівневий** (`struct fuse_operations`) бере цей облік на себе: він тримає власне дерево імен, сам роздає й забирає номери — а вам показує звичні **шляхи**. Для системи, яку хочеться бачити наскрізь, другий підходить якнайкраще: код виходить коротким рівно настільки, щоб у ньому не було нічого, крім суті.

Обов'язкових операцій рівно чотири, і кожна обов'язкова з власної причини.

**`getattr`** — без неї не працює нічого. Перш ніж хоч щось зробити з ім'ям, ядро мусить дізнатися, чи воно існує і що це таке; [розбір шляху](topic:sys-unix/path-resolution) складається саме з таких питань, поставлених по одному на кожен складник шляху. Немає `getattr` — ядро не дістане навіть кореня, і точка монтування буде мертвою.

**`readdir`** — а от без неї файлова система не зникає. `cat /tmp/gen/hello` працюватиме й далі, бо для нього досить `getattr` і `read`. Зникне лише **перелік**: `ls` покаже порожньо. Це добре видно на розрізі, який у Unix проходить усередині поняття «каталог»: [«які тут є імена» і «що це за ім'я» — два різні питання](topic:sys-unix/directory-as-mapping), і відповідає на них різний код.

**`open`** — формально не обов'язкова: не реалізуєте — libfuse дозволить відкривати все підряд. Але це єдине місце, де ви бачите режим відкриття до першого байта (і можете відмовити на запис), і єдине, де можна сказати ядру, як поводитися з кешем саме для цього дескриптора.

**`read`** — власне байти.

Тепер головне рішення. Вміст обчислюваний, отже, він живе у **функції**. І тут чигає пастка, на якій спотикається мало не кожна саморобна файлова система: `getattr` оголошує `st_size`, а `read` віддає байти, і ці двоє мусять збігатися. Ядро вірить оголошеному розміру беззастережно: за звичайного, кешованого читання воно не спитає жодного байта за його межею, а те, що ви віддали понад нього, відкине. Оголосили менше, ніж віддаєте, — `cat` покаже обрізаний файл; більше — доповнений нулями.

Звідси правило, яке варто взяти собі назавжди: **вміст малює одна функція, і `getattr`, і `read` кличуть саме її**. `getattr` малює й повертає довжину, `read` малює й віддає потрібний шматок. Зайва робота тут дешевша за розбіжність.

Лишається випадок, коли довжину не можна пообіцяти навіть собі, — коли вміст міняється сам собою. У нас такі `now` і `stats`: поки ядро тримає закешовану відповідь `getattr`, лічильник устигне перейти з 99 на 100, і рядок стане на байт довший. Для такого є прапорець `direct_io`: він каже ядру не тримати цей файл у [кеші сторінок](topic:sys-unix/page-cache-durability) і не обмежувати читання оголошеним розміром, а передавати запити наскрізь, доки демон не поверне менше, ніж просили. Саме так поводяться файли в [/proc](topic:sys-unix/proc-reading-process-and-kernel-state): вони показують нульовий розмір, а читаються нормально.

## Код

Один файл, чотири операції, жодної залежності, крім самої `libfuse`.

```c
#define FUSE_USE_VERSION 31

#include <fuse.h>

#include <errno.h>
#include <fcntl.h>
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <time.h>
#include <unistd.h>

#define SQUARES  12          /* скільки файлів у каталозі squares/ */
#define MAXBODY  256         /* найдовший можливий вміст, із запасом */

static const char HELLO[] = "Привіт із простору користувача!\n";

enum { C_GETATTR, C_READDIR, C_OPEN, C_READ, C_LAST };

static pthread_mutex_t g_lock = PTHREAD_MUTEX_INITIALIZER;
static unsigned long   g_calls[C_LAST];   /* під g_lock */
static time_t          g_born;            /* мить запуску демона */

static void tick(int which)
{
    pthread_mutex_lock(&g_lock);
    g_calls[which]++;
    pthread_mutex_unlock(&g_lock);
}

/* ─── вміст ──────────────────────────────────────────────────────────────
   Одна функція малює вміст будь-якого файлу. Нею користується і read()
   (щоб віддати байти), і getattr() (щоб дізнатися st_size) — інакше
   оголошений розмір і справжній вміст рано чи пізно розійдуться.         */

/* «/squares/N» → N, якщо N у межах; інакше 0 */
static int square_of(const char *path)
{
    char *end;
    long  n;

    if (strncmp(path, "/squares/", 9) != 0)
        return 0;
    n = strtol(path + 9, &end, 10);
    if (end == path + 9 || *end != '\0' || n < 1 || n > SQUARES)
        return 0;
    return (int)n;
}

/* Повертає довжину вмісту в байтах або -ENOENT, якщо такого файлу немає. */
static int render(const char *path, char *body)
{
    int n = square_of(path);

    if (n != 0)
        return snprintf(body, MAXBODY, "%d · %d = %d\n", n, n, n * n);

    if (strcmp(path, "/hello") == 0)
        return snprintf(body, MAXBODY, "%s", HELLO);

    if (strcmp(path, "/now") == 0) {
        struct timespec ts;
        struct tm       tm;
        char            stamp[32];

        clock_gettime(CLOCK_REALTIME, &ts);
        localtime_r(&ts.tv_sec, &tm);
        strftime(stamp, sizeof stamp, "%Y-%m-%d %H:%M:%S", &tm);
        return snprintf(body, MAXBODY, "%s.%03ld\n", stamp,
                        ts.tv_nsec / 1000000);
    }

    if (strcmp(path, "/stats") == 0) {
        unsigned long c[C_LAST];

        pthread_mutex_lock(&g_lock);
        memcpy(c, g_calls, sizeof c);
        pthread_mutex_unlock(&g_lock);
        return snprintf(body, MAXBODY,
                        "getattr %lu\nreaddir %lu\nopen    %lu\nread    %lu\n",
                        c[C_GETATTR], c[C_READDIR], c[C_OPEN], c[C_READ]);
    }

    return -ENOENT;
}

/* Файли, довжина яких міняється сама собою, поки ніхто не дивиться. */
static int is_volatile(const char *path)
{
    return strcmp(path, "/now") == 0 || strcmp(path, "/stats") == 0;
}

/* ─── операції ─────────────────────────────────────────────────────────── */

static int gen_getattr(const char *path, struct stat *st,
                       struct fuse_file_info *fi)
{
    char body[MAXBODY];
    int  len;

    (void)fi;
    tick(C_GETATTR);

    memset(st, 0, sizeof *st);
    st->st_uid = getuid();
    st->st_gid = getgid();
    /* Сталому вмісту — сталий час зміни: тоді ядро має право тримати кеш.
       Мінливому — свіжий: це для ядра сигнал, що вміст оновився.          */
    st->st_atime = st->st_mtime = st->st_ctime =
        is_volatile(path) ? time(NULL) : g_born;

    if (strcmp(path, "/") == 0) {
        st->st_mode  = S_IFDIR | 0555;
        st->st_nlink = 3;      /* «.», запис у батьках і «squares/..» */
        return 0;
    }
    if (strcmp(path, "/squares") == 0) {
        st->st_mode  = S_IFDIR | 0555;
        st->st_nlink = 2;      /* підкаталогів немає */
        return 0;
    }

    len = render(path, body);
    if (len < 0)
        return len;            /* саме -ENOENT, зі знаком мінус */

    st->st_mode  = S_IFREG | 0444;
    st->st_nlink = 1;
    st->st_size  = len;
    return 0;
}

/* Один запис у відповідь на readdir. Коли ядро просило READDIRPLUS,
   віддаємо повні атрибути; коли ні — воно однаково візьме з цієї
   структури тип файлу, і цього досить, щоб «ls» не питав окремо
   про кожне ім'я.                                                        */
static void put(void *buf, fuse_fill_dir_t filler, int plus,
                const char *name, const char *full)
{
    struct stat st;

    if (gen_getattr(full, &st, NULL) != 0)
        return;
    filler(buf, name, &st, 0,
           plus ? FUSE_FILL_DIR_PLUS : FUSE_FILL_DIR_DEFAULTS);
}

static int gen_readdir(const char *path, void *buf, fuse_fill_dir_t filler,
                       off_t offset, struct fuse_file_info *fi,
                       enum fuse_readdir_flags flags)
{
    int  plus = (flags & FUSE_READDIR_PLUS) != 0;
    char name[16], full[64];
    int  i;

    (void)offset;
    (void)fi;
    tick(C_READDIR);

    filler(buf, ".",  NULL, 0, FUSE_FILL_DIR_DEFAULTS);
    filler(buf, "..", NULL, 0, FUSE_FILL_DIR_DEFAULTS);

    if (strcmp(path, "/") == 0) {
        put(buf, filler, plus, "hello",   "/hello");
        put(buf, filler, plus, "now",     "/now");
        put(buf, filler, plus, "stats",   "/stats");
        put(buf, filler, plus, "squares", "/squares");
        return 0;
    }
    if (strcmp(path, "/squares") == 0) {
        for (i = 1; i <= SQUARES; i++) {
            snprintf(name, sizeof name, "%d", i);
            snprintf(full, sizeof full, "/squares/%d", i);
            put(buf, filler, plus, name, full);
        }
        return 0;
    }
    return -ENOENT;
}

static int gen_open(const char *path, struct fuse_file_info *fi)
{
    char body[MAXBODY];

    tick(C_OPEN);

    if (render(path, body) < 0)
        return -ENOENT;
    if ((fi->flags & O_ACCMODE) != O_RDONLY)
        return -EACCES;
    /* Довжину цих файлів наперед не пообіцяєш — хай ядро не кешує їх
       і не обрізає читання за оголошеним розміром.                       */
    if (is_volatile(path))
        fi->direct_io = 1;
    return 0;
}

static int gen_read(const char *path, char *buf, size_t size, off_t offset,
                    struct fuse_file_info *fi)
{
    char body[MAXBODY];
    int  len;

    (void)fi;
    tick(C_READ);

    len = render(path, body);
    if (len < 0)
        return len;

    if (offset >= (off_t)len)
        return 0;                        /* кінець файлу */
    if ((off_t)size > len - offset)
        size = (size_t)(len - offset);

    memcpy(buf, body + offset, size);
    return (int)size;
}

static const struct fuse_operations gen_ops = {
    .getattr = gen_getattr,
    .readdir = gen_readdir,
    .open    = gen_open,
    .read    = gen_read,
};

int main(int argc, char *argv[])
{
    g_born = time(NULL);
    return fuse_main(argc, argv, &gen_ops, NULL);
}
```

`main` тут майже порожній не з лінощів: `fuse_main` сама розбирає командний рядок — знаходить у ньому точку монтування, розпізнає `-f`, `-d`, `-s` і всі `-o …`, кличе `fusermount3`, приймає від нього дескриптор `/dev/fuse` і крутить цикл «запит — виклик вашої функції — відповідь», доки файлову систему не відмонтують.

## Збирання, монтування, перевірка

Заголовки й бібліотека знаходяться через `pkg-config` — окремий пакунок для розробки зветься `libfuse3-dev` у Debian і похідних, `fuse3-devel` у Fedora:

```sh
$ cc -Wall -Wextra -O2 -pthread genfs.c -o genfs $(pkg-config --cflags --libs fuse3)
```

`pkg-config --cflags fuse3` віддає, серед іншого, `-D_FILE_OFFSET_BITS=64` і шлях до заголовків `fuse3`. Перше не косметика: без нього `off_t` на 32-бітних системах буде 32-бітним, а розклад структур у бібліотеці — 64-бітним, і програма зламається на файлах понад два гігабайти ([про це саме розходження](topic:sys-unix/large-file-support)).

Монтуємо. Ключ `-f` тримає демона на передньому плані — про нього окремо нижче:

```sh
$ mkdir -p /tmp/gen
$ ./genfs -f /tmp/gen
```

І в іншому вікні:

```sh
$ ls -l /tmp/gen
-r--r--r-- 1 ann ann 59 сер  7 12:04 hello
-r--r--r-- 1 ann ann 24 сер  7 12:04 now
dr-xr-xr-x 2 ann ann  0 сер  7 12:04 squares
-r--r--r-- 1 ann ann 41 сер  7 12:04 stats

$ cat /tmp/gen/hello
Привіт із простору користувача!

$ cat /tmp/gen/squares/7
7 · 7 = 49

$ cat /tmp/gen/now
2026-08-07 12:04:31.882
$ cat /tmp/gen/now
2026-08-07 12:04:33.114
```

Дрібниця, помітна відразу: у рядку `hello` тридцять один знак і перевід рядка, а `ls` показує 59. Розмір у Unix — це байти, а не літери, і кирилиця в UTF-8 займає по два байти на знак. Якби `getattr` порахував знаки, `cat` показав би обрізаний рядок — та сама розбіжність між оголошеним і справжнім, тільки підкрадається з іншого боку.

Відмонтувати:

```sh
$ fusermount3 -u /tmp/gen
```

## Що ядро питає насправді

Досі ми дивилися на файлову систему ззовні, очима оболонки. Увімкнімо налагоджувальний вивід — `-d` друкує кожне повідомлення, що йде через `/dev/fuse`, і сам вмикає `-f`:

```sh
$ ./genfs -d /tmp/gen
```

Ось що з'являється на `cat /tmp/gen/hello` (скорочено — лишено тільки істотне):

```
unique: 30, opcode: LOOKUP (1), nodeid: 1
LOOKUP /hello
   NODEID: 4
   unique: 30, success, outsize: 144
unique: 32, opcode: OPEN (14), nodeid: 4
   unique: 32, success, outsize: 32
unique: 34, opcode: READ (15), nodeid: 4, offset: 0, size: 4096
   READ[0] 59 bytes
   unique: 34, success, outsize: 75
unique: 36, opcode: FLUSH (25), nodeid: 4
unique: 38, opcode: RELEASE (18), nodeid: 4
```

Три речі варто прочитати уважно.

По-перше, **`cat` попросив 59 байтів, а ядро попросило 4096**. Воно й не могло інакше: звичайне читання йде через кеш сторінок, а кеш сторінок оперує сторінками. Демон повернув 59 — коротка відповідь означає «далі нічого немає», і ядро цим задовольнилося.

По-друге, **`cat` викликає `fstat()` на відкритому дескрипторі, а `FUSE_GETATTR` у виводі немає**. Атрибути вже приїхали у відповіді на `LOOKUP` — та відповідь на 144 байти містить і номер об'єкта, і повний набір атрибутів, і два строки придатності. Доки строк не минув (типово секунда), ядро відповідає на `stat` самотужки.

По-третє, і це головне: **`LOOKUP` — це теж виклик вашого `getattr`**. Високорівневий шар `libfuse` зводить кілька різних питань ядра до однієї вашої функції: і «знайди в цьому каталозі таке ім'я», і «дай атрибути об'єкта, номер якого я вже знаю», і заповнення атрибутів усередині переліку каталогу. Ось звідки береться відчуття, що `getattr` кличуть надто часто, — його справді кличуть частіше, ніж є викликів `stat()` у програмі.

![Ліворуч три повідомлення ядра — FUSE_LOOKUP «у каталозі nodeid=2 знайди ім'я 7», FUSE_GETATTR «атрибути об'єкта, номер якого вже відомий» і FUSE_READDIRPLUS «усі імена каталогу разом з атрибутами». Три стрілки сходяться до середньої рамки: високорівневий шар libfuse тримає власне дерево імен і перекладає nodeid у шлях. З неї одна стрілка веде праворуч до єдиної функції gen_getattr, яка заповнює st_mode, st_nlink і st_size. Унизу порівняння для команди ls -l у каталозі з дванадцяти файлів: звичайний READDIR дає 16 повідомлень через межу і 25 викликів getattr, READDIRPLUS дає 4 повідомлення і 13 викликів](img/getattr-funnel.svg)

*Три різні питання ядра приходять в одну вашу функцію. Тому «скільки разів викликали мій `getattr`» і «скільки разів перетнули межу» — два різні числа, і зменшувати їх доводиться різними засобами.*

Полічимо `ls -l /tmp/gen/squares`. Дванадцять файлів, і жодного з них ядро ще не знає.

Якщо ядро просить **звичайний `READDIR`**, воно отримує самі імена (і, якщо ви їх дали, типи). Далі `ls` викликає `lstat()` на кожному імені — і кожен такий виклик обертається окремим `LOOKUP`. Разом: `LOOKUP` каталогу, `OPENDIR`, `READDIR`, дванадцять `LOOKUP`, `RELEASEDIR` — **шістнадцять повідомлень через межу**. А вашу функцію `getattr` покличуть двадцять п'ять разів: один раз на сам каталог, дванадцять разів усередині `readdir` (ми ж малюємо тип для кожного запису) і ще дванадцять на `LOOKUP`.

Якщо ядро просить **`READDIRPLUS`**, воно бере з однієї відповіді і імена, і атрибути, і відразу заводить у себе записи про ці об'єкти. Дванадцять `LOOKUP` зникають: `LOOKUP` каталогу, `OPENDIR`, `READDIRPLUS`, `RELEASEDIR` — **чотири повідомлення**. Викликів вашого `getattr` — тринадцять.

Найважливіше в цьому порівнянні — що два числа падають по-різному. Викликів вашої функції поменшало вдвічі, а перетинів межі — вчетверо. Дорого коштує саме друге, тому `readdirplus` і придумали.

Ядро вибирає між ними не навмання й не назавжди: домовленість `FUSE_READDIRPLUS_AUTO` дає йому право дивитися, чи справді за переліком ідуть звертання до атрибутів. Ідуть — воно й далі просить `plus`; програма лише перебирає імена й нікуди не заглядає — воно вертається до звичайного `READDIR`, бо відповіді з атрибутами товщі й записів у одне повідомлення влазить менше. У коді ви бачите вибір ядра прямо: `flags & FUSE_READDIR_PLUS`.

Перевірити всю цю арифметику можна не читаючи налагоджувального виводу — для цього ми й тримаємо `stats`:

```sh
$ cat /tmp/gen/stats
getattr 23
readdir 2
open    5
read    9

$ ls -l /tmp/gen/squares > /dev/null
$ cat /tmp/gen/stats
getattr 37
readdir 3
open    6
read    11
```

Абсолютні числа у вас будуть інші — важлива різниця. Чотирнадцять нових `getattr` — це тринадцять на `ls` і ще один на пошук самого `stats`, бо між двома знімками минуло більше секунди й ядро перепитало його ім'я. Два нових `read` на один `cat` — теж не помилка: перший віддає всі байти, а `cat`, отримавши коротку відповідь, робить іще один `read()` — переконатися, що далі кінець файлу. Кешованому файлові цей другий виклик обслужило б само ядро, але `stats` іде повз кеш, тож обидва доходять до демона.

І ще одне, з чого варто посміятися й запам'ятати: читання `stats` саме змінює `stats`. Числа, які ви бачите, уже враховують те читання, яким ви їх дивитеся.

А тепер повторіть `ls -l /tmp/gen/squares` двічі підряд, швидко. Другого разу різниця буде близька до нуля: імена й атрибути ще лежать у ядрі, строк їхньої придатності не минув. Зачекайте секунду — і числа знову побіжать. Це та сама `attr_timeout`, і на власному демоні її видно як на долоні: змонтуйте з `-o attr_timeout=0` — і кожен `ls` знову коштуватиме повного набору викликів, скільки б разів ви його не повторили.

## Пастки

**`st_mode` і `st_nlink` — не косметика, а обов'язок.** Занулили `struct stat` і забули поставити тип — ядро отримало об'єкт, який не є ні файлом, ні каталогом, ні посиланням. Запасного варіанта в нього немає: відповідь на пошук імені проходить перевірку `fuse_invalid_attr()`, і об'єкт із невідомим типом відкидається з помилкою `EIO` ще до того, як ядро заведе для нього [inode](topic:sys-unix/inode-model). Ви бачите загадкове «Помилка вводу-виводу» на файлі, якого ніхто не читав.

Із `st_nlink` тонше. Для каталогу правильне значення — **два плюс кількість підкаталогів**: сам себе через «`.`», запис у батьківському каталозі, і по одному «`..`» від кожного нащадка. Тому в нашому корені стоїть трійка, а в `squares` — двійка. Байдужість тут карається не відразу: є родина обхідників дерева, які за цим числом вирішують, чи лишилися ще підкаталоги, — оголосили каталогові з нащадками двійку, і такий обхідник у них не зайде. Помилка, яку потім шукають годинами, бо «все ж працює, крім `find`».

**Помилка повертається як від'ємне число — і не будь-яке.** Домовленість високорівневого API проста: функція повертає `0` або `-errno`. Ніякого `errno` як змінної, ніякого `-1` як позначки невдачі. Звичний для C рефлекс `return -1;` тут означає буквально `-EPERM`, і замість «Немає такого файлу» користувач читає «Операція не дозволена» — і йде перевіряти права, яких ви не встановлювали. Додатне значення ще гірше: воно не помилка, і ядро таку відповідь просто не приймає. Тому в коді вище `render` віддає саме `-ENOENT`, а `getattr` передає це значення далі як є ([про домовленості з `errno`](topic:sf-apps/errno)).

**Ваші функції кличуть із кількох потоків одночасно.** Без `-s` `fuse_main` крутить багатопотоковий цикл: ядро віддає запити пулові робітників, і два `getattr` виконуються паралельно, не питаючи вашої згоди. Усе, що спільне, треба захищати — у нас це лічильники під `g_lock`. Помилку тут майже неможливо помітити на власній машині вручну; вона вилазить під навантаженням і виглядає як «іноді неправильне число» ([гонки й замки](topic:sf-tasks/data-races-locks)). Правило на щодня: **налагоджуйте під `-s`, а перевіряйте без нього**, бо однопотоковий режим приховує саме той клас вад, який шукати найдорожче.

**`-f` і `-d` — не для краси.** Без `-f` `fuse_main` перетворює процес на справжнього [демона](topic:sys-unix/daemonize): відв'язується від термінала, закриває стандартні потоки, іде у фон. Ваш `printf` після цього йде в нікуди, налагоджувач губить процес, а щоб зупинити демона, його треба ще знайти. `-f` лишає його на передньому плані з живим виводом і працює під `gdb` як звичайна програма. `-d` до того ж друкує кожне повідомлення протоколу й сам вмикає `-f`. Друга пара очей — [`strace`](topic:sys-unix/syscall-tracing) на процесі демона: там видно ті самі `read` і `write` на дескрипторі `/dev/fuse`, тільки сирими байтами.

**Демон не сміє нічого писати у власну точку монтування.** Виглядає як безглузда помилка, а робиться легко: шлях до журналу зібрали з конфігурації, і він випадково опинився під тією текою, яку демон щойно змонтував. Далі механізм невблаганний: демон робить `write()`, ядро перетворює це на запит FUSE й приспиняє того, хто його зробив, — чекаючи на відповідь від нього ж. Це [взаємне блокування](topic:sf-tasks/deadlock) на одному учасникові.

Багатопотоковість цю пастку не рятує, а маскує. Заблокується не весь демон, а один потік із пулу; система працює далі й виглядає здоровою — доки такі записи не з'їдять пул до останнього робітника. Тому це не «іноді зависає», а міна з відкладеним спрацюванням. `libfuse` про свою частку дбає: ідучи у фон, вона робить `chdir("/")`, щоб демон не тримав робочою текою те, що збирається змонтувати. Про решту дбаєте ви — і не тільки про журнал: шлях для дампа пам'яті, вивід `strace -o`, тимчасові файли й оболонка, з якої ви запустили демона, стоячи всередині його ж точки монтування.

**Відмонтовувати треба `fusermount3 -u`.** Звичайний `umount` вимагає прав адміністратора, бо [підключення й відключення файлових систем — дія привілейована](topic:sys-unix/mount-model); `fusermount3` для того й існує, щоб цю дію міг зробити той, хто монтував, і тільки над своєю точкою монтування:

```sh
$ fusermount3 -u /tmp/gen
```

Демона, запущеного з `-f`, можна просто перервати з клавіатури: `libfuse` перехоплює сигнал і відмонтовує сама. А от якщо демон помер від `kill -9`, точка монтування лишиться на місці, і кожен виклик у ній повертатиме `ENOTCONN` — прибирає це той самий `fusermount3 -u`. Коли він упирається в «пристрій зайнято», винен хтось, хто тримає в цій теці відкритий файл або робочий каталог: знайти його — `fuser -m /tmp/gen`, відчепити наосліп — `fusermount3 -uz` (відв'язати зараз, дочистити, коли всі підуть). Найпростіше ж один раз додати `-o auto_unmount`, і помічник прибиратиме за демоном сам.
