# 📋 Специфікація каталогів drop-in, директив та інструментів аудиту

<preknowlist>
- [Файлова система FHS](root:sys-unix/fhs-layout) — стандарт розміщення системних каталогів та пріоритети `/etc`, `/run`, `/usr/lib`.
- [Юніти та менеджер служб systemd](root:sys-unix/systemd-model) — структура юнітів, секції та синтаксис директив.
</preknowlist>

Сучасна операційна система Linux уніфікує правила завантаження, злиття, сортування та маскування конфігураційних файлів у всіх ключових підсистемах ядра та простору користувача. Нижче наведено зведену нормативну специфікацію шляхів пошуку, синтаксису директив, семантики злиття та інтерфейсу діагностичних інструментів.

## 1. Реєстр конфігураційних каталогів за підсистемами

Усі системні компоненти реалізують трирівневу модель пріоритетів: каталог адміністратора `/etc/` має перевагу над динамічним рантаймом `/run/`, а той — над незмінними дефолтами постачальника в `/usr/lib/` (або `/usr/share/` для окремих архітектурно-незалежних пакетів). Окремі утиліти додатково перевіряють каталог `/usr/local/lib/` між `/run/` та `/usr/lib/`.

```
/etc/  →  /run/  →  /usr/local/lib/  →  /usr/lib/
```

| Підсистема | Шлях адміністратора (`/etc`) | Шлях рантайму (`/run`) | Шлях постачальника (`/usr/lib`) | Розширення | Семантика злиття |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **systemd юніти** | `/etc/systemd/system/` | `/run/systemd/system/` | `/usr/lib/systemd/system/` | `.service`, `.socket`, `.target` | Повне затінення основного файлу за іменем |
| **systemd drop-in** | `/etc/systemd/system/<unit>.d/` | `/run/systemd/system/<unit>.d/` | `/usr/lib/systemd/system/<unit>.d/` | `*.conf` | Конкатенація секцій та правил у пам'яті |
| **sysctl параметри** | `/etc/sysctl.d/` | `/run/sysctl.d/` | `/usr/lib/sysctl.d/` | `*.conf` | Останнє лексикографічне значення перемагає |
| **udev правила** | `/etc/udev/rules.d/` | `/run/udev/rules.d/` | `/usr/lib/udev/rules.d/` | `*.rules` | Послідовна обробка; блокування через `:=` |
| **tmpfiles.d** | `/etc/tmpfiles.d/` | `/run/tmpfiles.d/` | `/usr/lib/tmpfiles.d/` | `*.conf` | Перше валідне правило для шляху перемагає |
| **sysusers.d** | `/etc/sysusers.d/` | `/run/sysusers.d/` | `/usr/lib/sysusers.d/` | `*.conf` | Перше визначення UID/користувача перемагає |
| **modules-load.d** | `/etc/modules-load.d/` | `/run/modules-load.d/` | `/usr/lib/modules-load.d/` | `*.conf` | Об'єднання унікального списку модулів ядра |
| **modprobe.d** | `/etc/modprobe.d/` | `/run/modprobe.d/` | `/usr/lib/modprobe.d/` | `*.conf` | Останнє правило для опцій, аліасів і softdep |
| **environment.d** | `/etc/environment.d/` | `/run/environment.d/` | `/usr/lib/environment.d/` | `*.conf` | Останнє значення змінної середовища |
| **binfmt.d** | `/etc/binfmt.d/` | `/run/binfmt.d/` | `/usr/lib/binfmt.d/` | `*.conf` | Реєстрація сигнатур бінарників у ядрі |
| **logrotate.d** | `/etc/logrotate.d/` | — | `/usr/share/logrotate/` | `*` (довільне) | Ізольовані блоки ротації для кожного журналу |
| **sudoers.d** | `/etc/sudoers.d/` | — | — | `*` (без крапок) | Послідовне зчитування правил доступу |
| **pam.d** | `/etc/pam.d/` | `/run/pam.d/` | `/usr/lib/pam.d/` | `*` (ім'я сервісу) | Повне затінення стека автентифікації |

## 2. Специфікація обробки правил за підсистемами

### Підсистема systemd: ієрархія drop-in та шаблони екземплярів

Парсер службового менеджера `systemd` підтримує три рівні підключення додаткових конфігураційних фрагментів drop-in:

1. **Індивідуальні доповнення юніта**: розміщуються у підкаталозі `<name>.<type>.d/*.conf` (наприклад, `/etc/systemd/system/nginx.service.d/override.conf`). Застосовуються виключно до цього конкретного юніта.
2. **Типові групові доповнення**: розміщуються у каталозі `<type>.d/*.conf` (наприклад, `/etc/systemd/system/service.d/10-global-limits.conf` або `socket.d/10-buffers.conf`). Директиви з цих файлів автоматично застосовуються до **всіх** юнітів відповідного типу в системі.
3. **Шаблони екземплярів (Instantiated Units)**: для параметризованих служб виду `app@instance.service` парсер шукає конфігурацію у трьох місцях послідовно:
   - `app@.service.d/*.conf` — загальні доповнення для всіх екземплярів цього шаблону.
   - `app@instance.service.d/*.conf` — точкові доповнення саме для екземпляра `instance`.

```text
СХЕМА ЗВЕДЕННЯ ШАБЛОННОГО ЮНІТА:
/usr/lib/systemd/system/app@.service                (Базовий шаблон)
  + /etc/systemd/system/service.d/*.conf            (Групові правила для всіх служб)
  + /etc/systemd/system/app@.service.d/*.conf       (Правила для всіх app@)
  + /etc/systemd/system/app@worker1.service.d/*.conf(Правила тільки для worker1)
```

#### Скалярні директиви
Для директив з одиничним значенням нове входження безумовно замінює попереднє значення у внутрішній структурі юніта:

```ini
# /usr/lib/systemd/system/app.service
[Service]
Restart=on-failure
MemoryMax=1G
TimeoutStartSec=30s

# /etc/systemd/system/app.service.d/10-override.conf
[Service]
MemoryMax=4G        # Замінює 1G на 4G
TimeoutStartSec=60s # Замінює 30s на 60s
```

#### Спискові директиви та механізм повного скидання
Директиви, що формують масиви рядків (`Environment=`, `ReadWritePaths=`, `ReadOnlyPaths=`, `ExecStartPre=`, `ExecStart=`, `ExecStop=`), за замовчуванням конкатенуються. Нове значення додається в кінець внутрішнього списку:

```ini
# Початковий юніт містить:
Environment="DB_HOST=127.0.0.1"

# Drop-in файл додає:
Environment="DB_PORT=5432"

# Результат у пам'яті процесу:
# Змінні DB_HOST=127.0.0.1 та DB_PORT=5432 доступні процесу одночасно
```

Для повної заміни списку застосовується директива з **порожнім значенням**:

```ini
# /etc/systemd/system/app.service.d/20-exec.conf
[Service]
ExecStart=                           # Очищує весь попередній масив команд
ExecStart=/opt/custom/bin/app --prod # Встановлює нову єдину команду старту
```

> [!WARNING]
> Для юнітів типу `Type=simple`, `Type=exec`, `Type=notify`, `Type=idle` наявність двох команд `ExecStart=` без проміжного очищення викликає фатальну помилку синтаксису під час завантаження юніта (`systemd[1]: app.service: More than one ExecStart= could be found for service. Refusing to run.`). Для юнітів `Type=oneshot` дозволено вказувати кілька команд `ExecStart=`, і вони виконуватимуться послідовно.

### Підсистема udev: правила пристроїв та блокування оператором `:=`
Файли правил `udev` зчитуються з каталогів `/etc/udev/rules.d/*.rules`, `/run/udev/rules.d/*.rules` та `/usr/lib/udev/rules.d/*.rules` у лексикографічному порядку:

1. **Оператор присвоєння (`=`)**: встановлює значення ключа, яке може бути перезаписане наступними правилами з вищими числовими префіксами.
2. **Оператор додавання (`+=`)**: додає запис до списку (наприклад, `TAG+="systemd"`, `SYMLINK+="disk/by-id/custom"`).
3. **Оператор фінального блокування (`:=`)**: встановлює остаточне значення ключа. Будь-які спроби змінити це значення в наступних правилах або drop-in файлах будуть проігноровані:

```udev
# 10-local-disk.rules (в /etc/udev/rules.d)
# Встановлює групу 'storage' та блокує її від подальших змін системними правилами:
KERNEL=="sd[a-z]*", GROUP:="storage", MODE:="0660"
```

### Підсистема sysctl: параметри ядра Linux
Утиліта `systemd-sysctl` збирає файли конфігурації з `/etc/sysctl.d/*.conf`, `/run/sysctl.d/*.conf` та `/usr/lib/sysctl.d/*.conf`. 
- Усі однойменні файли затіняються за правилом найвищого пріоритету каталогу.
- Решта файлів сортується за зростанням числових префіксів (`00-` → `99-`).
- Якщо один і той самий параметр ядра (наприклад, `net.ipv4.ip_forward`) визначено у кількох файлах, остаточне значення визначається останнім зчитаним рядком.
- Дозволяється використання як точкової нотації (`net.ipv4.conf.all.rp_filter = 1`), так і нотації шляхів файлової системи procfs (`net/ipv4/conf/all/rp_filter = 1`).

### Підсистеми modules-load.d та modprobe.d: завантаження та параметризація модулів ядра
Управління модулями ядра розділене на два незалежні конфігураційні рівні:

1. **`modules-load.d/` (Автоматичне завантаження)**:
   Файли у `/etc/modules-load.d/*.conf`, `/run/modules-load.d/*.conf` та `/usr/lib/modules-load.d/*.conf` містять простий перелік імен модулів ядра, які мають бути завантажені на ранньому етапі ініціалізації службою `systemd-modules-load.service`. Кожен рядок містить одну назву модуля. Порожні рядки та рядки, що починаються з `#` або `;`, ігноруються.
2. **`modprobe.d/` (Параметри та політики завантаження утиліти modprobe)**:
   Файли конфігурації утиліти `modprobe` підтримують наступний набір директив:
   - `options <модуль> <параметр1>=<значення1>`: передає параметри ініціалізації драйверу ядра.
   - `alias <псевдонім> <реальний_модуль>`: створює псевдонім для автозавантаження за вимогою підсистем ядра.
   - `blacklist <модуль>`: вимикає внутрішні автоаліаси модуля, запобігаючи автоматичному підтягуванню драйвера при виявленні обладнання (проте дозволяє ручне завантаження).
   - `install <модуль> /bin/true` (або `/bin/false`): техніка повного блокування драйвера. Команда підміняє системний виклик завантаження модуля викликом фіктивної утиліти, унеможливлюючи завантаження навіть при явному виклику `modprobe`.
   - `softdep <модуль> pre: <модуль_A> post: <модуль_B>`: декларує м'які залежності між слабозв'язаними драйверами пристроїв.

### Підсистема environment.d: змінні оточення
Каталоги `/etc/environment.d/*.conf`, `/run/environment.d/*.conf` та `/usr/lib/environment.d/*.conf` використовуються менеджером користувацьких сесій `systemd --user` та генератором `systemd-environment-d-generator`. 
- Формат складається з рядків виду `KEY=VALUE`.
- Підтримується підстановка раніше визначених змінних: `PATH=$PATH:/opt/custom/bin`.
- Значення, встановлені у `/etc/environment.d/`, експортуються в оточення всіх користувацьких служб та графічних сесій.

### Підсистема binfmt.d: реєстрація бінарних форматів
Каталоги `/etc/binfmt.d/*.conf`, `/run/binfmt.d/*.conf` та `/usr/lib/binfmt.d/*.conf` дозволяють реєструвати інтерпретатори для чужорідних бінарних форматів у віртуальній файловій системі `/proc/sys/fs/binfmt_misc` ядра Linux.
- Використовується для прозорого запуску бінарників Windows через Wine або архітектур ARM/RISC-V через емулятор QEMU.
- Формат рядка містить сигнатуру файлу, маску та шлях до бінарного транслятора.

### Підсистема sudoers.d та вимоги безпеки
Файли у каталозі `/etc/sudoers.d/` підключаються за допомогою директиви `@includedir /etc/sudoers.d` в основному файлі `/etc/sudoers`:
- **Обмеження прав доступу**: кожен файл у каталозі `/etc/sudoers.d/` зобов'язаний мати вісімковий режим доступу `0440` (або `0400`) і належати користувачу `root:root`. Файли з правами запису для інших користувачів або груп ігноруються з міркувань безпеки.
- **Фільтрація імен**: утиліта `sudo` автоматично ігнорує файли, назва яких закінчується на `~` (резервні копії редакторів), містить крапку (`.`), або починається з символу `#`.

### Підсистема pam.d: модулі автентифікації
Каталоги `/etc/pam.d/`, `/run/pam.d/` та `/usr/lib/pam.d/` визначають ланцюги автентифікації (PAM-стеки) для кожної системної служби (`login`, `sshd`, `sudo`, `systemd-user`).
- Повне затінення: наявність файлу `/etc/pam.d/sshd` повністю вимикає завантаження однойменного файлу з `/usr/lib/pam.d/sshd`.
- Кожен файл описує чотири типи модулів: `auth` (перевірка пароля/ключа), `account` (валідація терміну дії облікового запису), `password` (зміна пароля) та `session` (підготовка оточення користувача, монтування каталогів через `pam_systemd.so`).
- Підтримується модульне підключення спільних конфігурацій через директиви `@include common-auth`, `@include common-session`.

## 3. Інтерфейс утиліти аудиту systemd-delta

Утиліта `systemd-delta` інспектує стан усіх трирівневих конфігурацій і drop-in каталогів, визначаючи ступінь відхилення (дрейфу) поточної конфігурації машини від початкового заводського образу.

### Основні типи станів

```text
[OVERRIDDEN] /etc/sysctl.d/50-net.conf → /usr/lib/sysctl.d/50-net.conf
             Файл в /etc повністю затінив файл постачальника з тим самим ім'ям.

[EXTENDED]   /usr/lib/systemd/system/nginx.service
             ↳ /etc/systemd/system/nginx.service.d/10-limits.conf
             Базовий юніт розширено додатковими фрагментами drop-in.

[MASKED]     /etc/systemd/system/bluetooth.service → /dev/null
             Юніт або файл конфігурації замасковано створенням посилання на /dev/null.

[REDIRECTED] /etc/systemd/system/default.target → /usr/lib/systemd/system/multi-user.target
             Символьне посилання в /etc перенаправляє запит на інший юніт.

[EQUIVALENT] /etc/udev/rules.d/99-custom.rules → /usr/lib/udev/rules.d/99-custom.rules
             Файл в /etc повністю ідентичний за вмістом файлу постачальника.
```

### Командний рядок утиліти

```bash
# Повний звіт про всі конфігураційні зміни системи
systemd-delta

# Фільтрація лише замаскованих та перевизначених файлів
systemd-delta --type=masked,overridden

# Показ конкретного diff для змінених файлів
systemd-delta --diff=yes

# Перевірка лише конкретної підсистеми
systemd-delta sysctl.d/
systemd-delta udev/rules.d/
```

## 4. Команди оперативного управління юнітами через systemctl

| Команда | Опис операції |
| :--- | :--- |
| `systemctl cat <unit>` | Виводить повний об'єднаний вміст основного юніта та всіх його drop-in фрагментів. |
| `systemctl edit <unit>` | Створює та відкриває drop-in файл `/etc/systemd/system/<unit>.d/override.conf` у текстовому редакторі. Після збереження автоматично виконує `systemctl daemon-reload`. |
| `systemctl edit --full <unit>` | Копіює повний базовий юніт із `/usr/lib/` у `/etc/systemd/system/<unit>` для повного затінення. |
| `systemctl mask <unit>` | Створює символьне посилання `/etc/systemd/system/<unit> -> /dev/null`, унеможливлюючи запуск служби. |
| `systemctl unmask <unit>` | Видаляє символьне посилання на `/dev/null` з `/etc/systemd/system/`. |
| `systemctl revert <unit>` | Видаляє всі локальні правки з `/etc/systemd/system/` (повний файл та каталог `<unit>.d/`), повертаючи юніт до заводського стану. |
