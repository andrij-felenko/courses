# Конфіг як текст: /etc проти дефолтів у /usr і каталоги drop-in

<preknowlist>
- [Файлова система FHS](root:sys-unix/fhs-layout) — стандарт розміщення системних каталогів (`/usr`, `/etc`, `/var`, `/run`) та поділ на незмінні й змінні дані.
- [Пакетний менеджер](root:sys-unix/package-manager-model) — модель встановлення пакунків, відстеження конфігураційних файлів та конфлікти оновлення.
- [Юніти та менеджер служб systemd](root:sys-unix/systemd-model) — декларативна модель юнітів, життєвий цикл служб та завантаження директив.
- [Управління тимчасовими файлами tmpfiles.d](root:sys-unix/tmpfiles-d-runtime-volatile-files) — створення й очищення волотильних каталогів у `/run` до старту служб.
</preknowlist>

Оновлення системного пакунка веб-сервера чи демона автентифікації у традиційному дистрибутиві Linux раптово зупиняє роботу автоматизованого конвеєра або пошкоджує робочу конфігурацію машини, щойно системний адміністратор змінює хоча б один рядок у стандартному файлі налаштувань. Якщо утиліта пакетного менеджера (як-от `dpkg` чи `rpm`) виявляє розбіжність контрольної суми файлу у каталозі `/etc`, вона не здатна автоматично вирішити, чи слід зберегти ручні правки адміністратора, чи застосувати новий зразок конфігурації від постачальника з оновленими параметрами безпеки та синтаксичними змінами. У результаті автоматизоване розгортання зависає в очікуванні інтерактивного вводу або породжує на диску приховані дублікати конфігурацій, залишаючи вузол у невизначеному стані.

Коренем цієї проблеми є змішування двох принципово різних типів даних у єдиному просторі імен каталогу `/etc`: базових заводських дефолтів, що поставляються розробниками операційної системи, та індивідуальних правок, внесених системним адміністратором конкретного сервера. Вирішення цієї кризи вимагало повного переосмислення стандартів розміщення конфігураційних файлів, впровадження трирівневої ієрархії каталогів, модульних структур доповнень (англ. *drop-in directories*) та розробки безстанової архітектури операційної системи (англ. *Stateless Systems*).

## 1. Проблема «забрудненого» /etc та криза оновлення дистрибутивів

В історичній традиції Unix каталог `/etc` (від лат. *et cetera* — «і решта») вважався єдиним універсальним сховищем для всіх системних текстових конфігурацій. Кожен програмний пакет під час інсталяції копіював у цей каталог власні монолітні файли налаштувань: `/etc/sysctl.conf` для параметрів ядра, `/etc/security/limits.conf` для лімітів ресурсів, `/etc/sudoers` для прав суперкористувача або `/etc/nginx/nginx.conf` для веб-сервера.

```text
ТРАДИЦІЙНИЙ МОНОЛІТНИЙ КАТАЛОГ /etc (ЗМІШАНИЙ СТАН):
/etc/
├── sysctl.conf          ← 100 рядків дефолтів постачальника + 2 локальні правки адміна
├── ssh/sshd_config      ← Змінено рядок "Port 2222" (хеш-сума файлу змінилася)
├── sudoers              ← Монолітний файл із правами доступу
└── nginx/nginx.conf     ← Дефолтна структура віртуальних хостів
```

Коли адміністратор відкривав текстовий редактор і змінював мережевий порт у `/etc/ssh/sshd_config`, весь файл розміром у сотні рядків переходив зі стану «чистий пакетний дефолт» у стан «локально модифікований об'єкт». Пакетний менеджер відстежував цей факт через збережені криптографічні хеші (хеш-суми `md5` або `sha256` у базі даних `dpkg` чи заголовках RPM).

### Механіка пакетних конфліктів (.dpkg-dist та .rpmnew)

Під час чергового релізу дистрибутива постачальник оновлював базовий конфігураційний файл, наприклад вимикаючи застарілі алгоритми шифрування або змінюючи синтаксис директив. При встановленні оновлення алгоритм пакетного менеджера стикався з класичною проблемою тристороннього злиття (англ. *three-way merge*):
- **Версія A (Base)**: оригінальний файл конфігурації старої версії пакета.
- **Версія B (Mine)**: поточний файл на диску з локальними правками адміністратора.
- **Версія C (Theirs)**: новий файл конфігурації з оновленого пакета.

```text
       [Версія A: Базовий дефолт постачальника v1.0]
                      /                      \
                     /                        \
                    v                          v
[Версія B: Локальні правки адміна]    [Версія C: Новий дефолт постачальника v2.0]
                    \                          /
                     \                        /
                      v                      v
                  [ КОНФЛІКТ ТРИСТОРОННЬОГО ЗЛИТТЯ ]
```

Оскільки текстові конфігурації не є формалізованим кодом і часто містять коментарі та специфічне форматування, автоматичне текстове злиття утилітами на кшталт `patch` чи `diff3` регулярно призводило до синтаксичних помилок. Пакетні менеджери обирали одну з двох стратегій відмови:

1. **Інтерактивне блокування (Debian/Ubuntu `dpkg`)**:
   У базі даних `/var/lib/dpkg/status` утиліта зберігала список файлів із маркером `conffiles` та їхні контрольні суми. Якщо поточний хеш на диску не збігався зі збереженим, процес оновлення зупинявся й вимагав вибору одного з варіантів у терміналі (`[Y/I/N/O/D/Z]`). Це повністю блокувало автоматичні конвеєри CI/CD, хмарні ініціалізації через `cloud-init` та засоби автоматизації (Ansible, Puppet, Chef). Якщо адміністратор налаштовував неінтерактивний режим зі збереженням старої версії (`DPKG_FORCE_CONFOLD`), новий файл оновлення записувався поруч як `sshd_config.dpkg-dist`. У результаті нові обов'язкові параметри безпеки просто ігнорувалися.
2. **Тихе роздвоєння (Red Hat/Fedora/SUSE `rpm`)**:
   Пакетний менеджер RPM використовував прапорці файлів у заголовках пакетів: `%config(noreplace)` або `%config`. Якщо файл було модифіковано, менеджер пакетів без запитань залишав модифікований файл користувача, а новий зразок зберігав поруч із суфіксом `sshd_config.rpmnew` (або навпаки — перезаписував робочий файл, зберігаючи стару версію як `sshd_config.rpmsave`). Нові критичні директиви безпеки залишалися у файлі `.rpmnew` і ніколи не застосовувалися демоном.

### Втрата видимості локального стану

Змішування дефолтів і правок у `/etc` створювало явище «забрудненого каталогу» (англ. *polluted /etc*). На свіжовстановленій системі каталог `/etc` містив понад 2000 файлів загальним обсягом у десятки мегабайтів. 

Адміністратор або автоматизована система аудиту не мали простого способу відповісти на базові інженерні питання:
- Які саме файли в системі було змінено вручну, а які є точними копіями заводських дефолтів?
- Які параметри відрізняються від базового образу дистрибутива?
- Як безпечно повернути конкретну службу до початкового заводського стану без повного перевстановлення всієї операційної системи?

Детальний аналіз того, як Unix-спільнота намагалася подолати цю кризу через скрипти `run-parts` та каталоги `/etc/default/`, висвітлено у [нарисі про еволюцію від монолітних конфігурацій до модульних доповнень](root:sys-unix/config-files-and-drop-ins/hist-from-monolith-to-dropins.md).

## 2. Трирівнева ієрархія конфігурацій: /usr/lib -> /run -> /etc

Для кардинального вирішення проблеми пакетних колізій сучасні стандарти Linux (зокрема FHS 3.0 та системний менеджер `systemd`) запровадили суворе архітектурне розділення конфігураційного простору на **три незалежні рівні**.

Кожен рівень має власного власника, власне призначення та чітко визначений пріоритет у ланцюгу обробки:

```text
РІВЕНЬ 3: /etc/        ──► Найвищий пріоритет (Адміністратор вузла, RW, диск)
                              ▲
                              │ затіняє / перекриває
                              │
РІВЕНЬ 2: /run/        ──► Середній пріоритет (Динамічний рантайм, tmpfs, ОЗП)
                              ▲
                              │ затіняє / перекриває
                              │
РІВЕНЬ 1: /usr/lib/    ──► Найнижчий пріоритет (Постачальник дистрибутива, RO, образ ОС)
```

```
/etc  >  /run  >  /usr/lib
```

### 1. Рівень постачальника: `/usr/lib/` (Vendor Defaults)
Каталог `/usr/lib/` (або `/usr/share/` для окремих архітектурно-незалежних утиліт) містить фабричні, незмінні конфігураційні файли, що постачаються розробниками дистрибутива та авторами пакунків. 
- **Права доступу**: монтується у режимі «лише для читання» (Read-Only) у сучасних захищених образах.
- **Власник**: пакетний менеджер операційної системи.
- **Правило інженерної гігієни**: системному адміністратору суворо заборонено редагувати файли в `/usr/lib/` вручну, оскільки будь-яке пакетне оновлення без попередження перезапише ці файли новішими версіями.

### 2. Рівень динамічного рантайму: `/run/` (Transient Runtime)
Каталог `/run/` монтується як волотильна файлова система в оперативній пам'яті (`tmpfs`). Він призначений для розміщення конфігурацій, які генеруються програмно під час завантаження або під час роботи системи.
- **Джерела даних**: генератори `systemd` (англ. *systemd generators*), сценарії раннього завантаження `initramfs`, агенти конфігурації віртуальних машин (`cloud-init`), мережеві демони DHCP або контейнерні рушії.
- **Життєвий цикл**: існує виключно до вимкнення живлення або перезавантаження вузла. Жоден файл із `/run/` не зберігається на постійному диску.
- **Пріоритет**: правила у `/run/` мають вищий пріоритет за заводські дефолти в `/usr/lib/`, що дозволяє хмарним агентам динамічно налаштовувати параметри системи без модифікації дискових розділів.

### 3. Рівень локального адміністратора: `/etc/` (Admin Overrides)
Каталог `/etc/` розміщується на постійному файловому накопичувачі й за сучасною парадигмою є **виключною власністю системного адміністратора**.
- **Вміст**: містить лише ті файли та параметри, які були явно створені або змінені людиною чи системою оркестрації (Ansible, Terraform).
- **Пріоритет**: найвищий у системі. Будь-який файл або директива у `/etc/` безумовно перекриває відповідні налаштування з `/run/` та `/usr/lib/`.
- **Оновлення системи**: пакетний менеджер ніколи не перезаписує та не створює файли у `/etc/`, якщо сервіс підтримує трирівневу схему. Оновлення пакунків змінює виключно файли у `/usr/lib/`, завдяки чому виключається сама можливість виникнення конфліктів `.dpkg-dist` чи `.rpmnew`.

![Трирівнева ієрархія конфігураційних каталогів та результуючий потік параметрів](/root/sys/sys-unix/config-files-and-drop-ins/img/three-tier-config-hierarchy.svg)
*Трирівнева ієрархія пріоритетів (/etc > /run > /usr/lib), затінення однойменних файлів та маскування через /dev/null.*

## 3. Механіка каталогів .d/ та drop-in файлів

Розділення на три каталоги вирішує проблему заміни цілих файлів, але не відповідає на виклик точкових правок. Якщо адміністратору потрібно змінити лише один параметр демона (наприклад, збільшити ліміт пам'яті `MemoryMax=4G` у юніті `nginx.service`), копіювання всього 60-рядкового юніта з `/usr/lib/systemd/system/nginx.service` у `/etc/systemd/system/nginx.service` призведе до того, що майбутні оновлення директив безпеки постачальника перестануть надходити до цього юніта.

Для вирішення цієї задачі було стандартизовано концепцію **каталогів доповнень (drop-in directories)**, які позначаються суфіксом `.d/`.

### Принцип роботи drop-in у systemd

Замість клонування основного файлу конфігурації, системний адміністратор створює підкаталог з назвою конфігураційного об'єкта та суфіксом `.d`, наприклад `/etc/systemd/system/app.service.d/`. У цей каталог поміщаються невеликі текстові файли-фрагменти (англ. *snippets*) з розширенням `.conf`.

```text
СТРУКТУРА DROP-IN КАТАЛОГУ:
/usr/lib/systemd/system/app.service               ← Базовий файл постачальника
/etc/systemd/system/app.service.d/
├── 10-resource-limits.conf                       ← Фрагмент: обмеження пам'яті та CPU
└── 20-custom-exec.conf                           ← Фрагмент: зміна бінарника запуску
```

Під час парсингу службовий менеджер виконує наступну послідовність операцій:
1. Завантажує базовий юніт із `/usr/lib/systemd/system/app.service`.
2. Сканує всі три каталоги drop-in у порядку пріоритету:
   - `/usr/lib/systemd/system/app.service.d/*.conf`
   - `/run/systemd/system/app.service.d/*.conf`
   - `/etc/systemd/system/app.service.d/*.conf`
3. Об'єднує всі знайдені секції (`[Unit]`, `[Service]`, `[Install]`) у єдину структуру даних у пам'яті ядра процесу PID 1.

![Механізм злиття та перевизначення директив через drop-in файли](/root/sys/sys-unix/config-files-and-drop-ins/img/dropin-merging-and-override.svg)
*Об'єднання основного юніта постачальника та фрагментів drop-in: заміна скалярних значень та скидання списків через ExecStart=.*

### Правила злиття директив: скаляри проти списків

Під час злиття конфігураційних фрагментів парсер застосовує два чітких правила залежно від внутрішнього типу директиви:

#### 1. Скалярні директиви (Scalar Directives)
Директиви, що описують одиничні значення (рядки, числа, логічні прапорці `yes`/`no`), діють за принципом **«останнє прочитане значення перемагає»**. Якщо базовий юніт містить `Restart=on-failure`, а drop-in файл містить `Restart=always`, значення у внутрішній структурі юніта замінюється на `always`.

#### 2. Спискові директиви та синтаксис очищення (List Directives & Reset)
Директиви, що можуть повторюватися і формують масиви (наприклад, `Environment=`, `ReadWritePaths=`, `ExecStartPre=`, `ExecStart=`), за замовчуванням **накопичують значення**. Кожен новий рядок у drop-in файлі додає елемент до списку:

```ini
# /usr/lib/systemd/system/app.service
[Service]
Environment=PORT=8080

# /etc/systemd/system/app.service.d/env.conf
[Service]
Environment=METRICS=9090
# У результаті служба отримає ОБИДВІ змінні: PORT=8080 та METRICS=9090
```

Якщо адміністратору потрібно **повністю замінити** команду запуску `ExecStart=`, просте додавання нового рядка `ExecStart=/opt/bin/custom-app` створить неприпустиму ситуацію: для простих служб (`Type=simple` або `Type=exec`) наявність кількох директив `ExecStart` призведе до помилки конфігурації та відмови старту юніта.

Для очищення раніше накопиченого списку директив використовується синтаксис **порожнього присвоєння**:

```ini
# /etc/systemd/system/app.service.d/20-custom-exec.conf
[Service]
ExecStart=                           # ПОРОЖНЄ ЗНАЧЕННЯ: повністю очищує список команд
ExecStart=/opt/custom/bin/app --prod # Встановлює нову єдину команду запуску
```

Порожній виклик `ExecStart=` скидає внутрішній вектор команд до нуля, після чого наступний рядок додає нове значення як єдиний виконуваний бінарник.

### Модульні каталоги в інших підсистемах ядра та дистрибутива

Механіка `.d` каталогів вийшла далеко за межі менеджера ініціалізації й застосовується практично в усіх базових компонентах Linux:

1. **`sysctl.d/` (Параметри ядра)**:
   Каталоги `/etc/sysctl.d/*.conf`, `/run/sysctl.d/*.conf` та `/usr/lib/sysctl.d/*.conf` дозволяють окремим службам декларувати необхідні параметри ядра Linux. Наприклад, пакунок маршрутизатора копіює `/usr/lib/sysctl.d/50-routing.conf` із директивою `net.ipv4.ip_forward = 1`, не вимагаючи редагування глобального файлу.
2. **`udev/rules.d/` (Правила диспетчера пристроїв)**:
   Правила обробки апаратних подій ядра зчитуються з `/etc/udev/rules.d/*.rules`, `/run/udev/rules.d/*.rules` та `/usr/lib/udev/rules.d/*.rules`.
3. **`sudoers.d/` (Права суперкористувача)**:
   Утиліта `sudo` підтримує директиву `@includedir /etc/sudoers.d`.
   
   > 🔧 **Історичний нюанс із `#includedir`**:
   > У традиційному синтаксисі `/etc/sudoers` символ `#` позначає коментар. Коли розробники `sudo` додали підтримку каталогів, вони використали префікс `#includedir`, де решітка була частиною ключового слова, а не коментарем. Це викликало часті помилки недосвідчених адміністраторів, які видаляли `#`, вважаючи директиву закоментованою. У сучасних версіях `sudo` додано однозначний синтаксис `@includedir`. Крім того, `sudo` ігнорує файли в `sudoers.d`, які містять крапку у назві (наприклад, `user.bak`), щоб уникнути виконання тимчасових файлів редакторів.

4. **`tmpfiles.d/` та `sysusers.d/`**:
   Декларативні підсистеми створення волотильних каталогів та системних користувачів, які повністю винесли імперативні скрипти з пакетних менеджерів.

Повний зведений реєстр усіх конфігураційних каталогів та підтримуваних директив наведено у [специфікації каталогів drop-in у підсистемах Linux](root:sys-unix/config-files-and-drop-ins/api-dropin-hierarchy-spec.md).

## 4. Порядок завантаження, затінення та маскування

Коли утиліта або системний демон зчитує конфігураційний каталог, обробка виконується за чіткими правилами лексикографічного впорядкування, колізій імен та блокування.

### Лексикографічне сортування за таблицею ASCII

Усі файли, відібрані з конфігураційних каталогів, об'єднуються в єдиний пул і сортуються за зростанням числових кодів символів їхніх імен (англ. *lexicographical / ASCII order*).

Для явного контролю черговості виконання застосовується угода про **числові префікси**:
- `00-` ... `19-`: рання базова конфігурація, системні дефолти найнижчого рівня.
- `20-` ... `49-`: налаштування проміжних підсистем та мережевих служб.
- `50-` ... `89-`: прикладні сервіси та стандартні дистрибутивні політики.
- `90-` ... `99-`: локальні фінальні правки адміністратора, що мають виконатися останніми.

```text
ПОРЯДОК ОБРОБКИ ЗА ASCII:
"01-early.conf"  -> ASCII 0x30, 0x31 (виконується першим)
"10-base.conf"   -> ASCII 0x31, 0x30
"50-vendor.conf" -> ASCII 0x35, 0x30
"99-local.conf"  -> ASCII 0x39, 0x39 (виконується останнім, перемагає у скалярах)
```

Для підсистем із послідовною моделлю (як-от `sysctl` чи `modprobe`), де кожне наступне правило перезаписує попереднє, файл `99-local.conf` має найвищий пріоритет застосування параметрів.

### Механізм затінення за базовим іменем (Basename Shadowing)

Якщо два або більше файлів у різних рівнях ієрархії мають **абсолютно однакове базове ім'я** (наприклад, `/etc/sysctl.d/50-security.conf` та `/usr/lib/sysctl.d/50-security.conf`), алгоритм парсера застосовує правило **затінення (shadowing)**:
- Файл із каталогу з вищим пріоритетом (`/etc`) завантажується повністю.
- Однойменний файл із каталогу з нижчим пріоритетом (`/usr/lib`) **повністю ігнорується**. Їхній вміст не об'єднується — файл у `/etc` стає абсолютною заміною.

Це дозволяє системному адміністратору перевизначити комплектний дистрибутивний конфігураційний файл, створивши у `/etc/` файл із такою самою назвою.

### Механізм маскування через /dev/null (Masking)

Якщо адміністратор бажає повністю скасувати або деактивувати певний конфігураційний файл постачальника чи цілу системну службу, простого видалення файлу з `/etc` недостатньо: демон знову побачить файл у `/usr/lib/` і продовжить його використання.

Для повного вимкнення застосовується техніка **маскування (masking)**:
У каталозі вищого пріоритету (`/etc/`) створюється символьне посилання з тим самим іменем, яке вказує на псевдопристрій порожнечі `/dev/null`:

```bash
# Маскування правила утиліти udev з постачальницького рівня
ln -s /dev/null /etc/udev/rules.d/80-net-setup-link.rules

# Маскування системної служби через systemctl
systemctl mask bluetooth.service
# Створює посилання: /etc/systemd/system/bluetooth.service -> /dev/null
```

```text
ДЕТЕКЦІЯ МАСКУВАННЯ ПАРСЕРОМ:
1. lstat("/etc/systemd/system/bluetooth.service") ──► Це Symlink? ──► ТАК
2. readlink() повертає "/dev/null"                ──► МАСКОВАНО!
3. Парсер повністю вилучає об'єкт з плану виконання.
```

#### Різниця між порожнім файлом і маскуванням
- **Порожній файл (0 байтів)**: файл розміром 0 байтів у `/etc/sysctl.d/50-net.conf` є звичайним регулярним файлом. Він затіняє файл у `/usr/lib`, і парсер успішно обробляє його як валідний порожній конфіг (жоден параметр не виставляється).
- **Символьне посилання на `/dev/null`**: сигналізує парсеру про явний намір адміністратора «заборонити даний об'єкт». Для юнітів `systemd` замасковану службу неможливо запустити навіть вручну командою `systemctl start` (повертається помилка `Unit bluetooth.service is masked`).

Для зняття маскування та повернення до заводських налаштувань достатньо просто видалити створене посилання з `/etc`:

```bash
# Повне відновлення заводського стану юніта
systemctl unmask bluetooth.service
# або універсальне повернення до дефолтів постачальника:
systemctl revert bluetooth.service
```

Команда `systemctl revert` автоматично видаляє як затіняючий юніт, так і всі пов'язані drop-in каталоги з `/etc/systemd/system/`, миттєво відновлюючи чистий стан з `/usr/lib/`.

Детальний програмний розбір алгоритму обходу ієрархій та детекції маскування наведено у [проєкті розробки сканера конфігураційних каталогів](root:sys-unix/config-files-and-drop-ins/proj-dropin-scanner-engine.md).

## 5. Безстанова архітектура (Stateless Systems) та заводське скидання

Розподіл конфігурацій на незмінні дефолти в `/usr/lib` та локальні правки в `/etc` уможливив реалізацію концепції **повністю безстанової операційної системи (Stateless Linux)**.

У класичній системі видалення вмісту `/etc` перетворювало комп'ютер на неробочий набір файлів (англ. *bricked system*), оскільки зникали файли `/etc/passwd`, `/etc/fstab`, конфігурації мережі та ініціалізації. У безстановій системі вся необхідна для старту функціональність міститься виключно у каталозі `/usr`.

```text
КОМПОНЕНТИ БЕЗСТАНОВОЇ СИСТЕМИ:
/usr/     ──► Незмінний базовий образ (Read-Only, підписаний вендором, dm-verity)
/etc/     ──► Порожній на старті. Заповнюється виключно локальною дельтою
/var/     ──► Постійні дані додатків (бази даних, логи). Ініціалізується автоматично
/run/     ──► Волотильний стан (tmpfs у пам'яті)
```

![Життєвий цикл безстанової системи та процедура Factory Reset](/root/sys/sys-unix/config-files-and-drop-ins/img/stateless-system-factory-reset.svg)
*Життєвий цикл безстанової системи (Stateless Linux): чистий старт з порожнім /etc, динамічний синтез стану та процедура Factory Reset.*

### Завантаження вузла з порожнім `/etc`

Коли безстанова система стартує з абсолютно порожнім кореневим каталогом `/etc` (розмір 0 байтів, жодного файлу на диску), системний менеджер автоматично ініціалізує мінімально необхідний стан:

1. **Детекція першого завантаження**: `systemd` виявляє відсутність файлу `/etc/machine-id` і автоматично генерує унікальний ідентифікатор хоста, монтуючи корінь або записуючи значення у файл.
2. **Декларативний синтез користувачів (`systemd-sysusers`)**:
   Утиліта зчитує описи системних користувачів із `/usr/lib/sysusers.d/*.conf` і автоматично створює записи для `root`, `systemd-network`, `dbus` у нових файлах `/etc/passwd` та `/etc/shadow`.
3. **Підготовка структури каталогів (`systemd-tmpfiles --create`)**:
   Утиліта зчитує правила з `/usr/lib/tmpfiles.d/*.conf` і створює необхідну ієрархію каталогів у `/var` (`/var/log`, `/var/lib`, `/var/cache`) з правильними правами доступу POSIX та контекстами безпеки.
4. **Активація системних пресетів (`systemd-presets`)**:
   Менеджер служб зчитує дистрибутивні політики з `/usr/lib/systemd/system-preset/*.preset` і автоматично створює необхідні символьні посилання активації служб у `/etc/systemd/system/multi-user.target.wants/`.

Після завершення цих кроків система переходить у повністю робочий стан за заводськими дефолтами без єдиного ручного втручання.

### Процедура повного заводського скидання (Factory Reset)

Завдяки відокремленню стану від програмного коду процедура скидання налаштувань комп'ютера або сервера до заводського стану (англ. *Factory Reset*) зводиться до простого очищення двох каталогів:

```bash
# Повне скидання системи до заводського стану постачальника
rm -rf /etc/* /var/*
reboot
```

Під час наступного старту система знову змонтує недоторканий образ `/usr`, запустить механізми автоініціалізації й підніме абсолютно чистий вузол без слідів попередніх користувачів, тимчасових файлів чи змінених конфігурацій.

### Незмінні операційні системи на базі системних образів

Безстанова модель є фундаментом сучасних незмінних операційних систем (англ. *Immutable / Image-based OS*): **Fedora Silverblue / CoreOS**, **Flatcar Container Linux**, **Ubuntu Core**, **SteamOS** та мобільних ОС на базі Linux (Android).

У таких системах розділ `/usr` монтується у режимі «лише для читання» (Read-Only), часто з верифікацією цілісності кожного блоку через криптографічний механізм ядра `dm-verity`. Оновлення операційної системи відбувається не порядковим оновленням окремих пакетів, а атомарною підміною всього кореневого образу `/usr` за схемою A/B розділів або за допомогою технологій розгортання на кшталт `ostree`.

Оскільки всі локальні правки зосереджені виключно у `/etc`, оновлення системного образу `/usr` проходить зі 100% гарантією успіху без ризику пошкодження користувацьких налаштувань.

### Інспекція конфігураційного дрейфу через systemd-delta

Для контролю стану налаштувань та аудиту того, наскільки поточна конфігурація машини відхилилася від чистого образу постачальника, використовується утиліта `systemd-delta`. Вона інспектує всі три рівні (`/etc`, `/run`, `/usr/lib`) і виводить структурований звіт про кожен модифікований файл:

```text
$ systemd-delta
[OVERRIDDEN] /etc/sysctl.d/50-default.conf → /usr/lib/sysctl.d/50-default.conf
[EXTENDED]   /usr/lib/systemd/system/nginx.service
             ↳ /etc/systemd/system/nginx.service.d/10-limits.conf
[MASKED]     /etc/systemd/system/bluetooth.service → /dev/null
[REDIRECTED] /etc/systemd/system/default.target → /usr/lib/systemd/system/multi-user.target

4 overridden configuration files found.
```

Утиліта миттєво підсвічує:
- `[OVERRIDDEN]`: файли, де адмін повністю затінив дефолт постачальника цілим власним файлом.
- `[EXTENDED]`: служби, що використовують точкові модульні доповнення через каталоги `.d/`.
- `[MASKED]`: служби та файли правил, вимкнені через посилання на `/dev/null`.
- `[REDIRECTED]`: символьні перенаправлення юнітів.

Використання прапорця `systemd-delta --diff=yes` виводить построковий diff між заводським файлом у `/usr/lib/` та його модифікованою версією у `/etc/`, забезпечуючи повну прозорість конфігураційного стану вузла.

## 6. Інженерні компроміси та підводні камені

Перехід на трирівневу модель та каталоги drop-in усунув хронічні проблеми пакетних оновлень, проте створив нові специфічні виклики, які необхідно враховувати під час проєктування систем:

1. **Застарілі демони (Legacy Software)**:
   Програми, розроблені за класичними стандартами Unix (наприклад, окремі версії BIND DNS чи ISC DHCP), жорстко закодовані на зчитування виключно файлу `/etc/named.conf` і не підтримують пошук дефолтів у `/usr/lib` або каталоги `.d/`. Для інтеграції такого ПЗ у безстанову модель дистрибутиви використовують спеціальні генератори `systemd` або юніти `systemd-tmpfiles`, які під час першого старту копіюють мінімальний шаблон із `/usr/share/factory/etc/` у `/etc/`.
2. **Прихований порядок виконання у drop-in каталогах**:
   Якщо кілька незалежних пакунків або модулів Ansible додають власні фрагменти конфігурації у каталог `/etc/sysctl.d/`, неправильний вибір числових префіксів може призвести до неочевидних багів. Наприклад, якщо файл `10-custom.conf` встановлює `net.ipv4.tcp_rmem = 4096 87380 6291456`, а встановлений пізніше пакет оптимізації мережі кладе файл `50-tune.conf` зі старим значенням `net.ipv4.tcp_rmem = 4096 87380 4194304`, правило з префіксом `50-` мовчки затре налаштування адміністратора через лексикографічний порядок ASCII. Інженерним правилом є використання високих префіксів (`90-` ... `99-`) для локальних правок хоста.
3. **Очищення списків у юнітах**:
   Найпоширенішою помилкою при написанні drop-in файлів для сервісів `systemd` залишається забування рядка скидання списку `ExecStart=`. Без порожнього присвоєння демон відмовляється стартувати через спробу призначення кількох команд запуску, що часто призводить до збоїв у продакшн-середовищах під час спроб зміни бінарних шляхів або прапорців запуску.

> 🔧 **Підсумок архітектури**:
> Розділення конфігурації на незмінні дефолти постачальника у `/usr/lib/`, динамічний рантайм у `/run/` та локальну дельту адміністратора у `/etc/` разом із механізмом drop-in файлів перетворило текстову конфігурацію Linux із крихкого моноліту на модульну, стійку до конфліктів систему, готову до автоматизованого хмарного масштабування та безстанової експлуатації.
