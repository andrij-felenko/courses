# 📜 Історія версіонування: від a.out до GNU Symbol Versioning

Еволюція зв'язування спільних бібліотек у Unix-подібних операційних системах — це багатодесятилітня історія пошуку компромісу між продуктивністю виконання, раціональним використанням фізичної пам'яті та бінарною стабільністю виконання системних програм. На зорі розвитку операційної системи Unix (1970-ті роки, Bell Laboratories) системи використовували виключно статичне зв'язування. Кожен виконуваний файл містив у собі повну автономну копію системних функцій `printf`, `malloc`, `fopen` та інших процедур, отриманих з архівних бібліотек `libc.a`. Це забезпечувало абсолютну автономність бінарних файлів, проте зі зростанням складності програмного забезпечення призвело до важкої перевитрати дискового простору та оперативної пам'яті: одна й та сама функція `printf` дублювалася у пам'яті стільки разів, скільки процесів було запущено в системі.

Перші спроби впровадити спільні (динамічні) бібліотеки у Unix System V Release 3 (SVR3) та BSD у середині 1980-х років наочно підкреслили нову проблему: як оновити реалізацію системного коду без необхідності повної перекомпіляції сотен залежних утиліт і як гарантувати, що оновлення не зламає вже скомпільовані бінарні файли.

## Ера a.out та фіксованих адрес (1980-ті — початок 1990-х)

У перших операційних системах SunOS 4.x та перших дистрибутивах Linux (1991–1995 рр.) використовувався формат виконуваних файлів `a.out` (assembler output). Спільні бібліотеки у форматі `a.out` мали первісну та вкрай обмежену архітектуру:

1. **Фіксовані віртуальні адреси в пам'яті:** Кожна спільна бібліотека у форматі `a.out` мусила заздалегідь зарезервувати для себе чітко визначену, фіксовану область у віртуальному просторі адрес процесів. Наприклад, системна бібліотека `libc.so` жорстко прив'язувалася до адреси `0x60000000`, а графічна бібліотека `libX11.so` — до адреси `0x60100000`. Це вимагало наявності глобального системного реєстру адрес у дистрибутиві (файл `/etc/image.so`). Якщо дві бібліотеки перекривалися в адресах, система не могла їх завантажити одночасно.
2. **Майданчики стрибків (Jump Tables):** Для збереження адресної сумісності виклики функцій у бінарниках спрямовувалися не безпосередньо на код функції, а через глобальну таблицю стрибків, розміщену на самому початку списку сегментів бібліотеки. Якщо розробники випускали нову патч-версію бібліотеки, вони мали суворо зберігати порядок функцій у таблиці стрибків. Нові функції додавалися виключно наприкінці таблиці.

Версіонування у форматі `a.out` обмежувалося найпростішим іменуванням файлів: `libfoo.so.1.2`. Найменші зміни у внутрішній структурі даних (наприклад, додавання поля у `struct FILE`) або зміна порядкового номера у таблиці стрибків призводили до фатальних збоїв, оскільки операційна система та завантажувач не мали жодного механізму для автоматичної перевірки сумісності окремих функцій чи структур даних.

## Великий перехід на ELF та криза libc5/libc6 (1995–1997)

У 1995–1996 роках спільнота Linux здійснює масштабний та болісний перехід з застарілого формату `a.out` на новий формат ELF (Executable and Linkable Format), запозичений із Unix System V Release 4 (SVR4). Формат ELF фундаментально змінив підхід до зв'язування: він приніс концепцію позиційно-незалежного коду (Position-Independent Code, PIC), таблиці GOT (Global Offset Table) та PLT (Procedure Linkage Table), а також динамічну секцію `.dynamic`. 

Саме у форматі ELF уперше з'явився механізм `DT_SONAME` — логічна мітка мажорної версії бібліотеки, яка записувалася у заголовок бінарного файла й дозволяла відокремити ім'я файлу на диску від бінарного контракту залежності.

Проте найдраматичнішим моментом у історії Linux-бібліотек стала криза переходу з бібліотеки `libc5` (останньої мажорної версії Linux C Library на базі форку FSG) на `glibc2` (GNU C Library 2.0, яка в системі мала SONAME `libc.so.6`). У 1997 році розробники дистрибутивів (Slackware, Red Hat, Debian) зіштовхнулися з тим, що `libc5` та `glibc2` мали повністю несумісні бінарні структури даних. Зокрема, у `glibc2` було фундаментально змінено внутрішній макет `struct FILE`, типи даних для роботи з файловими дескрипторами `fd_set`, розміри типів даних `off_t` для підтримки великих файлів (>2 ГБ) та розмір типу `dev_t`.

Програми, скомпільовані під `libc5`, хаотично падали з помилками аварійного завершення (`Segmentation Fault`), якщо вони випадково викликали функції з оновленої `glibc2`. Використання поля `DT_SONAME` стало єдиним порятунком екосистеми: воно дозволило встановити у систему дві версії бібліотеки паралельно:

```text
/lib/libc.so.5 -> libc.so.5.4.44 (для застарілих бінарників)
/lib/libc.so.6 -> libc-2.0.7.so  (для нових скомпільованих програм)
```

Завдяки розмежуванню за тегом `DT_SONAME` старі бінарники продовжували просити у завантажувача `libc.so.5`, а нові — `libc.so.6`. Це врятувало Linux від повного колапсу сумісності, проте викрило інше обмеження: `DT_SONAME` діяв на рівні всієї бібліотеки. Зміна хоча б однієї функції вимагала зміни мажорного номера SONAME, що призводило до потреби глобальної перекомпіляції усього дистрибутиву (Mass Rebuild).

## Винайдення Symbol Versioning: Sun Microsystems та Ульріх Дреппер

Для розв'язання проблеми точкової, гранулярної сумісності окремих функцій компанія Sun Microsystems у 1995 році розробила технологію Symbol Versioning для операційної системи Solaris 2.5. Інженери Sun створили синтаксис файлів мапування (mapfiles) та розширили компонувальник `ld`, що дозволило прив'язувати версійний штамп не до файлу в цілому, а до кожного окремого експортованого символу у таблиці `.dynsym`.

У 1998 році Ульріх Дреппер (Ulrich Drepper), головний архітектор GNU C Library (`glibc`) та провідний розробник утиліт `binutils`, детально вивчив досвід Sun Microsystems, адаптував і суттєво розширив цей підхід для інструментарію GNU toolchain (`gcc`, `ld`, `ld.so`). Дреппер запропонував концепцію декількох версій одного й того самого символу в одному бінарному файлі спільній бібліотеці за допомогою суфіксів у таблиці символів:

- `@VERSION` — застаріла версія символу, яка зберігається виключно для забезпечення виконання вже скомпільованих бінарних файлів.
- `@@VERSION` — версія за замовчуванням, з якою автоматично зв'язуються всі нові додатки під час компіляції.

Для підтримки цієї схеми у специфікацію форматів ELF для Linux було додано нові секції `.gnu.version`, `.gnu.version_d` та `.gnu.version_r`.

Впровадження GNU Symbol Versioning у `glibc 2.1` у 1999 році стало поворотним моментом у історії Linux. Завдяки цій технології розробники `glibc` змогли протягом більше ніж 25 років зберігати абсолютну зворотну бінарну сумісність. Бінарний файл, скомпільований у 2001 році на системі Red Hat Linux 7.1 проти `glibc 2.2.5`, у 2026 році без жодних модифікацій успішно запускається на найсучаснішому kernel 6.x та Ubuntu 26.04: динамічний завантажувач `ld.so` зчитує мітку `GLIBC_2.2.5` з бінарника і точково підключає його до відповідних історичних функцій усередині `libc.so.6`.
