# 📋 persistent-data: структури та інтерфейс ядра

Бібліотека ядра `dm-persistent-data` (розташована в дереві вихідних кодів ядра Linux за шляхом `drivers/md/persistent-data/`) надає набір низькорівневих інтерфейсів мовою C для створення, модифікації та транзакційного збереження B-дерев і бітових карт виділення блоків безпосередньо на сирому блоковому пристрої. Цей програмний шар є спільним фундаментом для цілей тонкого виділення (`dm-thin`), кешування на швидких накопичувачах (`dm-cache`), відстеження змінених блоків (`dm-era`) та фонового клонування томів (`dm-clone`).

## 1. Менеджер блоків: `dm-block-manager.h`

Менеджер блоків (`struct dm_block_manager`) інкапсулює роботу з фізичним або логічним пристроєм метаданих. Він керує кешуванням блоків фіксованого розміру 4 КіБ (`DM_BM_BLOCK_SIZE = 4096`), блокуваннями паралельного доступу, валідацією контрольних сум та чергами скидання буферів.

### Структура валідатора блоку

Кожен підтип метаданих (вузол B-дерева, індексний блок карти простору, суперблок) реєструє власний валідатор `struct dm_block_validator`. Ядро викликає його методи автоматично під час зчитування блоку з носія та безпосередньо перед відправкою буфера контролеру введення-виведення:

```c
struct dm_block_validator {
    const char *name;
    void (*prepare_for_write)(struct dm_block_validator *v,
                              struct dm_block *b,
                              size_t block_size);
    int (*check)(struct dm_block_validator *v,
                 struct dm_block *b,
                 size_t block_size);
};
```

Функція `prepare_for_write` виконує розрахунок контрольної суми CRC32c для корисного навантаження блоку (за винятком перших чотирьох байтів, де зберігається сама сума) і записує результат у заголовок перед передачею біо-запиту в чергу диска.

Метод `check` викликається після завершення операції дискового читання. Він перевіряє магічне число типу метаданих, відповідність збереженого номера блоку його фізичній адресі на диску та валідність контрольної суми CRC32c. Якщо перевірка зазнає невдачі, функція повертає `-EIO` або `-EILSEQ`, що сигналізує про пошкодження носія або неповний запис.

### Функції життєвого циклу менеджера блоків

- `struct dm_block_manager *dm_block_manager_create(struct block_device *bdev, unsigned max_held_per_thread);` — створює новий екземпляр менеджера блоків над вказаним блоковим пристроєм `bdev`. Параметр `max_held_per_thread` задає верхню межу кількості одночасно утримуваних буферів для одного потоку, що захищає ядро від вичерпання пулу пам'яті.
- `void dm_block_manager_destroy(struct dm_block_manager *bm);` — завершує роботу менеджера блоків, очікує завершення всіх активних операцій введення-виведення та звільняє виділені буфери кешу.

### Ключові виклики доступу до блоків

| Сигнатура функції | Призначення та правила використання |
| :--- | :--- |
| `int dm_bm_read_lock(struct dm_block_manager *bm, dm_block_t b, struct dm_block_validator *v, struct dm_block **result);` | Захоплює розділене (shared) блокування читання для блоку `b`. Якщо блок відсутній у RAM-кеші, ініціює дискове читання з перевіркою валідатором `v`. При помилці читання повертає від'ємний код помилки (`-EIO`). |
| `int dm_bm_write_lock_zero(struct dm_block_manager *bm, dm_block_t b, struct dm_block_validator *v, struct dm_block **result);` | Захоплює ексклюзивне блокування запису для щойно виділеного блоку `b` та занулює його пам'ять. Дискове читання не виконується, оскільки блок вважається новим. |
| `int dm_bm_write_lock(struct dm_block_manager *bm, dm_block_t b, struct dm_block_validator *v, struct dm_block **result);` | Захоплює ексклюзивне блокування запису для наявного блоку `b` з обов'язковим попереднім зчитуванням його поточного стану з носія або кешу. |
| `void dm_bm_unlock(struct dm_block *b);` | Звільняє блокування буфера та зменшує лічильник посилань буфера в кеші. Якщо буфер було позначено брудним, він залишається в черзі на запис. |
| `int dm_bm_flush(struct dm_block_manager *bm);` | Примусово скидає всі брудні буфери метаданих на блоковий пристрій та надсилає апаратний бар'єр скидання кешу носія (`REQ_PREFLUSH`). |
| `void *dm_block_data(struct dm_block *b);` | Повертає прямий вказівник на 4096 байтів даних блоку в оперативній пам'яті ядра. |
| `dm_block_t dm_block_location(struct dm_block *b);` | Повертає 64-бітний номер фізичного блоку на пристрої метаданих. |

Правило інваріантності: потік ядра, який захопив блокування через `dm_bm_read_lock` або `dm_bm_write_lock`, зобов'язаний звільнити його викликом `dm_bm_unlock` перед поверненням керування або переходом до тривалого очікування. Недотримання цього правила призводить до взаємного блокування (англ. *deadlock*) пулу метаданих.

## 2. Менеджер простору (Space Map): `dm-space-map.h`

Інтерфейс `struct dm_space_map` абстрагує операції обліку зайнятих блоків та відстеження 32-бітних лічильників спільних посилань (`refcount`). Для блоків даних використовується реалізація `dm-space-map-disk`, а для самих блоків метаданих — `dm-space-map-metadata`.

```c
struct dm_space_map {
    void (*destroy)(struct dm_space_map *sm);
    int (*extend)(struct dm_space_map *sm, dm_block_t extra_blocks);
    int (*get_nr_blocks)(struct dm_space_map *sm, dm_block_t *count);
    int (*get_nr_free)(struct dm_space_map *sm, dm_block_t *count);
    int (*get_count)(struct dm_space_map *sm, dm_block_t b, uint32_t *result);
    int (*set_count)(struct dm_space_map *sm, dm_block_t b, uint32_t count);
    int (*commit)(struct dm_space_map *sm);
    int (*inc_block)(struct dm_space_map *sm, dm_block_t b);
    int (*dec_block)(struct dm_space_map *sm, dm_block_t b);
    int (*new_block)(struct dm_space_map *sm, dm_block_t *b);
    int (*root_size)(struct dm_space_map *sm, size_t *result);
    int (*copy_root)(struct dm_space_map *sm, void *copy_to_here_le, size_t len);
};
```

### Поведінка та семантика викликів Space Map

- `inc_block`: атомарно збільшує лічильник посилань на блок `b`. Якщо блок мав `refcount = 0`, він переходить у зайнятий стан (`refcount = 1`). Якщо лічильник перевищує поріг 2, значення виноситься у вторинне B-дерево переповнення.
- `dec_block`: зменшує лічильник посилань на одиницю. Коли значення досягає `0`, блок маркується як вільний у бітовій карті для майбутніх алокацій.
- `new_block`: виконує пошук першого вільного біта у бітових картах, встановлює для нього `refcount = 1` і записує знайдений фізичний номер у `*b`.
- `commit`: скидає стан змінених бітових карт та індексних блоків у підготовлені тіньові блоки пристрою метаданих у рамках поточної транзакції.
- `extend`: динамічно збільшує діапазон відстежуваних блоків на `extra_blocks` при розширенні фізичного пулу накопичувачів.

## 3. Copy-on-Write B-дерева: `dm-btree.h`

B-дерева бібліотеки `dm-persistent-data` оптимізовано під блоковий розмір 4 КіБ і підтримку довільної кількості рівнів індексації (1D або 2D ключі). Усі операції модифікації реалізують тіньове копіювання при записі.

### Конфігурація дерева `struct dm_btree_info`

```c
struct dm_btree_value_type {
    void *context;
    size_t size;
    void (*inc)(void *context, const void *value);
    void (*dec)(void *context, const void *value);
    int (*equal)(void *context, const void *value1, const void *value2);
};

struct dm_btree_info {
    struct dm_transaction_manager *tm;
    unsigned levels;
    struct dm_btree_value_type value_type;
};
```

Поле `levels` визначає кількість вимірів ключа. Для одновимірного B-дерева (наприклад, відображення блоків у кеші `dm-cache`) значення `levels = 1`, а ключем є `uint64_t`. Для дворівневих ієрархій `dm-thin` значення `levels = 2`, де перший рівень адресується ідентифікатором віртуального пристрою `dev_id`, а другий — логічним номером блоку `logical_block`.

Структура `value_type` визначає поведінку значень листка:
- `size`: розмір корисного значення у байтах (типово 8 байтів для адреси блоку даних та прапорців).
- `inc`: функція зворотного виклику для збільшення лічильника посилань блоку даних, коли вузол дерева дублюється при створенні знімка.
- `dec`: зворотний виклик для зменшення лічильника посилань при видаленні ключа або перезаписі діапазону.

### Операції над B-деревом

| Функція | Опис дії |
| :--- | :--- |
| `int dm_btree_empty(struct dm_btree_info *info, dm_block_t *root);` | Ініціалізує нове порожнє B-дерево з одним кореневим листком і повертає номер виділеного блоку кореня у `*root`. |
| `int dm_btree_insert(struct dm_btree_info *info, dm_block_t root, uint64_t *keys, void *value, dm_block_t *new_root);` | Вставляє нову або замінює наявну пару ключ-значення. Створює тіньові копії всіх вузлів від кореня до листка та повертає новий корінь у `*new_root`. |
| `int dm_btree_lookup(struct dm_btree_info *info, dm_block_t root, uint64_t *keys, void *value_le);` | Виконує двійковий пошук у вузлах дерева. Повертає `0` при успіху та записує корисне навантаження у буфер `value_le`. Якщо ключ відсутній, повертає `-ENODATA`. |
| `int dm_btree_remove(struct dm_btree_info *info, dm_block_t root, uint64_t *keys, dm_block_t *new_root);` | Видаляє запис із дерева зі зменшенням лічильників посилань на відповідні блоки даних і повертає оновлений корінь дерева. |
| `int dm_btree_del(struct dm_btree_info *info, dm_block_t root);` | Рекурсивно декрементує лічильники посилань усіх вузлів і значень у дереві, повністю звільняючи структуру на диску. |

## 4. Транзакційний менеджер: `dm-transaction-manager.h`

Менеджер транзакцій (`struct dm_transaction_manager`) координує спільну роботу менеджера блоків, карти простору метаданих та B-дерев, забезпечуючи сувору двофазну фіксацію змін.

```c
int dm_tm_create_with_sm(struct dm_block_manager *bm,
                         dm_block_t sb_location,
                         struct dm_transaction_manager **tm,
                         struct dm_space_map **sm);

int dm_tm_open_with_sm(struct dm_block_manager *bm,
                       dm_block_t sb_location,
                       void *root_sm,
                       size_t root_sm_size,
                       struct dm_transaction_manager **tm,
                       struct dm_space_map **sm);

int dm_tm_shadow_block(struct dm_transaction_manager *tm,
                       dm_block_t orig,
                       struct dm_block_validator *v,
                       struct dm_block **result,
                       int *inc_children);

int dm_tm_new_block(struct dm_transaction_manager *tm,
                    struct dm_block_validator *v,
                    struct dm_block **result);

int dm_tm_commit(struct dm_transaction_manager *tm,
                 struct dm_block *root_block);
```

### Семантика транзакційних методів

- `dm_tm_shadow_block`: ключовий метод тінювання. Він аналізує, чи належить блок `orig` поточній відкритій транзакції. Якщо блок уже був створений або скопійований у цій же транзакції, функція повертає прямий доступ на запис. Якщо ж блок належить зафіксованому минулому стану, менеджер виділяє новий вільний 4 КіБ блок через `sm-metadata`, копіює туди вміст `orig`, встановлює прапорець модифікації та повертає новий дескриптор буфера у `*result`.
- `dm_tm_new_block`: виділяє абсолютно новий блок метаданих із нульовим заповненням для розширення вузлів дерева.
- `dm_tm_commit`: виконує двофазну фіксацію. На першій фазі фіксуються зміни карти простору метаданих, а менеджер блоків виконує `dm_bm_flush()`. На другій фазі оновлений суперблок записується на диск за допомогою запиту з прапорцем примусового доступу до носія (`REQ_FUA`).

## 5. Формат суперблоку `dm-thin` на диску

Суперблок займає перші 4096 байтів пристрою метаданих (фізичний блок 0) і має таку структуру:

```c
struct thin_disk_superblock {
    __le32 csum;                  /* CRC32c сума від байта 4 до кінця блоку */
    __le32 flags;                 /* Прапорці стану пулу (наприклад, NEEDS_CHECK = 1) */
    __le64 blocknr;               /* Фізичний номер блоку (завжди 0) */
    __u8   uuid[16];              /* Унікальний ідентифікатор пулу LVM */
    __le64 magic;                 /* Магічне число: 0xf0051002 (THIN_SUPERBLOCK_MAGIC) */
    __le32 version;               /* Версія формату метаданих */
    __le32 time;                  /* Глобальна часова мітка останнього знімка */

    __le64 trans_id;              /* Монотонний 64-бітний лічильник поколінь транзакцій */
    __le64 metadata_free_blocks;  /* Кількість доступних вільних блоків метаданих */
    __le64 data_mapping_root;     /* Фізичний блок кореня B-дерева відображень */
    __le64 device_details_root;   /* Фізичний блок кореня B-дерева параметрів пристроїв */
    __le64 data_block_size;       /* Розмір блоку даних у 512-байтних секторах */

    __u8   metadata_space_map_root[128]; /* Корінь карти простору метаданих */
    __u8   data_space_map_root[128];     /* Корінь карти простору блоків даних */
} __packed;
```

Якщо поле `flags` містить біт `THIN_FEATURE_NEEDS_CHECK` (числове значення 1), ядро відмовляється відкривати пул у режимі читання-запису доти, доки утиліта `thin_check` не підтвердить валідність усіх структур даних і не очистить цей прапорець.

## 6. Утиліти простору користувача (`thin-provisioning-tools`)

Утиліти взаємодіють із блоковим пристроєм метаданих напряму, коли пул `dm-thin` призупинено за допомогою команди `dmsetup suspend` або повністю деактивовано:

| Команда | Основні опції | Призначення та наслідки виконання |
| :--- | :--- | :--- |
| `thin_check` | `--clear-needs-check-flag`, `-q`, `--auto-repair` | Перевіряє цілісність B-дерев, валідність контрольних сум CRC32c і відповідність лічильників у картах простору. За успішної перевірки знімає аварійний прапорець `NEEDS_CHECK`. |
| `thin_dump` | `-f xml`, `--repair`, `-m <trans_id>` | Вивантажує повний стан метаданих пулу у структурований текстовий формат XML для аналізу, ручного редагування або резервного копіювання. |
| `thin_restore` | `-i <file.xml> -o <dev_metadata>` | Відновлює двійкові структури метаданих на новому або очищеному розділі накопичувача з XML-дампу. |
| `thin_repair` | `-i <bad_meta> -o <good_meta>` | Виконує глибоке сканування пошкодженого носія, обходить усі вцілілі вузли B-дерев і реконструює валідний суперблок на новому блоковому пристрої. |
| `thin_metadata_size` | `-b <block_size> -s <pool_size> -m <max_thins>` | Розраховує мінімально рекомендований обсяг розділу метаданих для заданого розміру пулу та кількості віртуальних томів. |

Утиліта `thin_check` повинна виконуватися перед кожним монтуванням пулу після нештатної зупинки операційної системи. Скрипти ініціалізації LVM2 автоматично викликають `thin_check` під час активації тонких груп томів.
