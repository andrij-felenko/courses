# 📜 Історія виникнення та еволюції допоміжного вектора (auxv)

Еволюція механізму передачі системного контексту від ядра Linux та UNIX-систем до рантайму користувацького простору пройшла шлях від первинних специфікацій System V Release 4 ABI наприкінці 1980-х років до запровадження сучасних підсистем безпеки, vDSO та розширень апаратної рандомізації у 64-бітних операційних системах. Передача метаданих виконання розвивалася паралельно з вимогами динамічного зв'язування та апаратного захисту пам'яті.

---

## 1. Витоки: перехід від `a.out` до ELF та стандартизація System V SVR4

У ранніх Unix-подібних операційних системах (включаючи класичні версії BSD та перші версії Linux на базі форматів `a.out` та `COFF`) модель передачі параметрів процесу під час виконання системного виклику `execve` була максимально спрощеною. Ядро розміщувало у вершині стек-фрейму лише лічильник аргументів `argc`, масив вказівників `argv` на аргументи командного рядка та масив `envp` із параметрами середовища.

Цієї інформації було цілком достатньо для статично зв'язаних бінарних файлів. Код програми розміщувався за фіксованими віртуальними адресами у пам'яті, сформованими ще на етапі компіляції, а всі виклики ядра здійснювалися через класичні програмні переривання (наприклад, `int 0x80` на архітектурі x86).

Проте наприкінці 1980-х років консорціум Unix System Laboratories (USL) розробив специфікацію **System V Release 4 (SVR4) ABI**, яка ввела новий формат виконуваних файлів — **ELF (Executable and Linkable Format)**, а також концепцію динамічного завантаження поділюваних бібліотек через інтерпретатор `ld.so`.

Динамічне зв'язування висунуло принципово нову вимогу: динамічний завантажувач у користувацькому просторі повинен був негайно після старту дізнатися, де саме ядро розташувало виконуваний файл, який розмір системної сторінки пам'яті, та де знаходяться таблиці заголовків програми (`Program Headers`). Робити для кожного з цих параметрів окремий системний виклик під час кожного запуску будь-якої програми створювало б неприпустиме навантаження на систему та істотно сповільнювало старт процесів.

Рішенням інженерів SVR4 стало розширення початкової структури стек-фрейму: одразу за нульовим термінатором масиву `envp` ядро почало записувати послідовний масив пар «ключ-значення» — **допоміжний вектор (auxiliary vector, `auxv`)**.

---

## 2. Інтеграція у Linux 1.2 / 2.0 та розвиток vDSO

Під час історичного переходу операційної системи Linux з застарілого формата `a.out` на `ELF` у середині 1990-х років (версії ядра 1.2 та 2.0) розробники ядра (включаючи Лінуса Торвальдса та розробників GNU C Library) повністю адаптували специфікацію auxv.

З появою процесорів Pentium II та Pentium III з'ясувалося, що виклик ядра через класичне програмне переривання `int 0x80` є надто повільним через глибокі конвеєри нових процесорів. Компанія Intel запровадила швидкі інструкції `SYSENTER` / `SYSEXIT`, а AMD — `SYSCALL` / `SYSRET`.

Щоб дозволити користувацькому простору викликати системні функції через найшвидший механізм, доступний на конкретному обладнанні, ядро Linux ввело вектор **`AT_SYSINFO`** (а згодом **`AT_SYSINFO_EHDR`**). Завдяки `AT_SYSINFO_EHDR` ядро почало передавати у користувацький простір віртуальну адресу динамічно спроєктованої бібліотеки **vDSO (virtual dynamic shared object)**. Це дозволило glibc виконувати системні виклики часу (на кшталт `clock_gettime`) взагалі без перемикання контексту ядра.

## 3. Епоха системного захисту: `AT_SECURE` та `AT_RANDOM`

У 2000-х роках із зростанням кількості атак на переповнення буфера та підміну поділюваних бібліотек допоміжний вектор перетворився на ключовий канал ініціалізації систем захисту операційної системи:

1. **Захист Setuid/Setgid та привілейованих процесів (`AT_SECURE`)**: Зловмисники намагалися підставити власні шкідливі бібліотеки при запуску привілейованих програм через змінні оточення `LD_PRELOAD` або `LD_LIBRARY_PATH`. Ядро почало розраховувати прапорець `AT_SECURE` під час системного виклику `execve`. Якщо бінарний файл має біти `setuid`/`setgid` або розширені атрибути файлової системи `capabilities`, ядро виставляє `AT_SECURE = 1`. Побачивши цей прапорець, динамічний лінкер очищає потенційно небезпечні змінні середовища ще до старту програми.
2. **Рандомізація стека та захист від переповнення (`AT_RANDOM`)**: З появою механізму **Stack Canaries** компілятор додає контрольне значення перед адресою повернення з функції. Щоб канарейка була непередбачуваною для атакуючого, ядро генерує 16 байтів якісної криптографічної ентропії у ядрі та передає вказівник на них через вектор `AT_RANDOM`.

## 4. Сучасний стан: 64-бітний ARM64, BTI, MTE та майбутнє

У сучасних ядрах Linux (версії 5.x та 6.x) допоміжний вектор продовжує активний розвиток:
- На 64-бітній архітектурі ARM64 через вектори `AT_HWCAP` та `AT_HWCAP2` ядро повідомляє рантайму про підтримку інструкцій захисту потоку виконання **BTI (Branch Target Identification)** та апаратного тегування пам'яті **MTE (Memory Tagging Extension)**.
- Додано вектор `AT_MINSIGSTKSZ` для динамічного визначення мінімального розміру стека обробника сигналів з урахуванням розширених векторних регістрів AVX-512 та SVE.

Таким чином, бінарна структура допоміжного вектора, розроблена понад 30 років тому для SVR4, виявилася надзвичайно гнучкою і продовжує залишатися фундаментальним каналом передачі метаданих між ядром Linux та користувацьким простором.
