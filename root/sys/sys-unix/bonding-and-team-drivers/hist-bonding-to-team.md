# 📜 Історія агрегації каналів у Linux: від Beowulf до teamd

Розвиток агрегації каналів у операційній системі Linux відображає еволюцію всієї мережевої інфраструктури — від ізольованих обчислювальних кластерів кінця 1990-х років до масштабних віртуалізованих дата-центрів та хмарних платформ XXI століття. Потреба в об'єднанні кількох фізичних мережевих адаптерів виникла з фундаментального архітектурного дисбалансу: обчислювальна потужність процесорів зростала значно швидше, ніж пропускна здатність поодиноких мережевих інтерфейсів Fast Ethernet (100 Мбіт/с).

---

## 1. Ера кластерів Beowulf та виникнення Bonding (1994–1999)

Витоки агрегації мережевих каналів у Linux сягають 1994 року, коли у Центрі космічних польотів імені Годдарда (NASA Goddard Space Flight Center) Томас Стерлінг (Thomas Sterling) та Дональд Беккер (Donald Becker) заснували проект **Beowulf**. Ідея полягала у створенні суперкомп'ютерів із дешевшого масового комерційного обладнання (COTS — Commercial Off-The-Shelf) під управлінням операційної системи Linux.

Проте під час масштабування кластерів до сотень обчислювальних вузлів розробники зіткнулися з жорстким мережевим обмеженням. Високошвидкісні спецмережі (наприклад, Myrinet або ATM) коштували десятки тисяч доларів за порт, тоді як звичайні карти Fast Ethernet (100 Мбіт/с) були дешевими, але швидко ставали вузьким місцем при обміні даними між вузлами під час паралельних розрахунків.

У 1999 році Дональд Беккер, який на той час уже створив більшість мережевих драйверів для ядра Linux, разом із колегами розробив перший варіант драйвера **Bonding** для ядра Linux 2.2. Початковий драйвер створювався виключно для реалізації режиму з круговим обслуговуванням пакетів (Round-Robin, пізніше отримав назву Mode 0). Схема була гранично простою: віртуальний пристрій перехоплював вихідні Ethernet-кадри від мережевого стеку і почергово відправляв їх через перший або другий фізичний мережевий адаптер PCI.

Це дозволило подвоїти смугу пропускання між кластерними вузлами без купівлі коштовного спецобладнання. Драйвер швидко інтегрували до експериментальної гілки ядра Linux 2.3, а згодом він увійшов до стабільного випуску Linux 2.4.

## 2. Корпоративна еволюція та стандартизація LACP (2000–2008)

Із масовим виходом операційної системи Linux на ринок корпоративних серверів вимоги до агрегації каналів кардинально змінилися. Просте кругове розподілення пакетів (Round-Robin) виявилося вкрай деструктивним для глобального протоколу TCP. Оскільки пакети одного й того самого TCP-з'єднання проходили через різні фізичні кабелі й порти комутаторів із мікроскопічними різницями у затримках, вони часто надходили до одержувача з порушенням послідовності (out-of-order delivery). Мережевий стек приймача сприймав це як втрату пакетів, надсилав повторні підтвердження (ACK) та різко зменшував розмір ковзного вікна TCP (congestion window), що призводило до катастрофічного падіння реальної швидкості передачі даних.

Для вирішення цієї проблеми розробники ядра Linux (зокрема Віллі Тарро — Willy Tarreau, та пізніше Джай Кумар — Jay Kumar з корпорації Intel) суттєво переробили драйвер bonding для ядра Linux 2.6. У драйвер було додано підтримку нових режимів:

- **Active-Backup (Mode 1)**: для забезпечення високої доступності серверів без вимог до налаштування комутаторів.
- **Balance-XOR (Mode 2)**: хешування MAC-адрес джерела й призначення для збереження послідовності пакетів у межах однієї сесії.
- **802.3ad LACP (Mode 4)**: повна реалізація стандарту IEEE 802.3ad з автоматичним узгодженням через керуючі кадри LACPDU.
- **Balance-TLB (Mode 5)** та **Balance-ALB (Mode 6)**: адаптивне балансування вихідного та вхідного трафіку без підтримки з боку комутатора шляхом динамічного перехоплення та підміни ARP-відповідей.

Впровадження стандарту LACP у ядрі Linux дозволило інтегрувати Linux-сервери до корпоративних мереж на базі професійного обладнання Cisco (EtherChannel), Juniper, HP та Extreme Networks. Модуль `bonding.ko` став монолітним стандартом де-факто, розрісшись до понад 15 000 рядків коду на мові C всередині ядра.

## 3. Архітектурна криза монолітного Bonding (2010–2012)

До 2010 року стрімкий розвиток віртуалізації (KVM, Xen), впровадження багаточергових мережевих карт (Multi-queue NICs) та поява мережевих фабрик дата-центрів виявили глибокі архітектурні обмеження монолітного драйвера `bonding.ko`.

Оскільки весь код — від низькорівневого розподілу пакетів до складних автоматів станів LACPDU, ARP-опитувачів, парсерів sysfs та обробників гарячого підключення портів — знаходився безпосередньо у просторі ядра (kernel space), підсистема зіткнулася з низкою системних проблем:

1. **Складність відлагодження та розширення**: Будь-яка помилка або витік пам'яті в автоматі станів LACP чи моніторі зв'язку призводила до аварійного падіння всього ядра (kernel panic). Додавання нових алгоритмів балансування вимагало правки ядра та тривалого циклу рев'ю у списку розсилки Linux Kernel Mailing List (LKML).
2. **Блокування та масштабованість**: Усі операції над портами та списком slave-пристроїв захищалися спільними блокуваннями ядра (`RCU` та `rtnl_lock`). На багатоядерних серверах із сотнями віртуальних мережевих інтерфейсів це створювало серйозні затримки на блокуваннях (lock contention).
3. **Обмеженість моніторингу**: MII та ARP монітори ядра не мали гнучкості для перевірки складних умов доступності (наприклад, перевірка зв'язку через IPv6 Neighbor Solicitation або виклики зовнішніх скриптів перевірки доступності HTTP-шлюзу).

## 4. Виникнення Teamd та розділення обов'язків (2012)

У 2012 році на конференціях Linux Netdev розробник Red Hat Іржі Пірко (Jiri Pirko) запропонував радикально новий підхід до агрегації каналів, представивши проект **Network Teaming** (`libteam` / `teamd`).

Замість монолітного ядра Пірко застосував класичний принцип UNIX: відокремлення тракту даних (Data Path) від тракту керування (Control Path):

```
  +-----------------------------------------------------------------+
  | USER SPACE: teamd Daemon (Control Path)                         |
  | - LACP State Machine                                            |
  | - Link Watchers (ethtool, arp_ping, nsna)                       |
  | - JSON Configuration & DBus / Unix Socket IPC                   |
  +-----------------------------------------------------------------+
                                  ^
                                  | Generic Netlink (genl)
                                  v
  +-----------------------------------------------------------------+
  | KERNEL SPACE: team.ko Driver (Fast Data Path)                   |
  | - High-performance packet forwarding                            |
  | - BPF (eBPF) hash execution                                     |
  | - Rx/Tx handlers without heavy locks                            |
  +-----------------------------------------------------------------+
```

- **В ядрі Linux** було створено лаконічний та максимально оптимізований модуль `team.ko`. Він виконував єдину задачу: швидко приймати пакети від верхнього рівня та комутувати їх на підпорядковані порти згідно з вказівками.
- **У просторі користувача** було виведено демон `teamd`. Повна логіка LACP, моніторинг лінків (MII, ARP, NS/NA), обробка подій та керування конфігурацією перейшли в юзерспейс. Спілкування між `teamd` та ядром реалізували через протокол Generic Netlink (`genl`).

Демон `teamd` приніс конфігурацію у зручному форматі JSON, розширюваність через плагіни (runners) та можливість використання Berkeley Packet Filter (BPF) для довільного балансування трафіку на основі будь-яких полів заголовка пакету.

## 5. Сучасний стан та співіснування

Архітектура Team увійшла до офіційного ядра Linux 3.3 і була прийнята як стандартний інструмент агрегації у дистрибутивах Red Hat Enterprise Linux 7 та 8. 

Проте класичний драйвер Bonding не занепав. Спільнота розробників ядра Linux виконала величезну роботу з рефакторингу `bonding.ko`: з ядра вилучили застарілі механізми, додали повну підтримку `rtnetlink` та інтегрували сучасні інструменти типу eBPF та hardware offloading через підсистему `switchdev`.

Сьогодні обидві технології співіснують у Linux: класичний Bonding залишається універсальним, бездемонним та надзвичайно надійним рішенням для простих конфігурацій, тоді як Team продемонстрував шлях еволюції системних мережевих служб у бік модульності та переносу керування в простір користувача.
