У конвеєрі автоматизованого розгортання інфраструктури нічний сценарій виконує рутинну операцію очищення тимчасових артефактів збірки за допомогою інструкції `rm -rf "${BUILD_STAGING_DIR}/*"`. За кілька рядків до цього виклик зовнішньої утиліти запиту хмарного сховища завершився з аварійним кодом `1` через тимчасовий збій мережевого з'єднання, і змінна `BUILD_STAGING_DIR` залишилася неініціалізованою. Оскільки командна оболонка за замовчуванням продовжує лінійне виконання після будь-яких помилок, інтерпретатор підставив порожній рядок замість відсутнього шляху, розгорнув команду до вигляду `rm -rf "/*"` і без жодного попередження знищив кореневу файлову систему віртуального сервера.

Така поведінка є прямим наслідком історичної концепції Unix-оболонки, що проектувалася в 1970-х роках як інтерактивне діалогове середовище. Коли системний адміністратор у терміналі вводить команду `grep`, яка не знаходить збігів і повертає код `1`, або робить одрук в імені файлу, термінал не повинен аварійно закриватися. Всепрощаючий режим, у якому будь-які помилки зовнішніх утиліт ігноруються, а невідомі змінні тихо замінюються на порожні рядки, забезпечував зручність роботи людини за консоллю. Проте коли цей самий інтерпретатор почали використовувати для безпілотного виконання критичних сценаріїв оркестрації, системного адміністрування та обробки фінансових транзакцій, дозволена модель перетворилася на джерело прихованих катастроф.

Перетворення командної оболонки на надійне середовище виконання вимагає перемикання інтерпретатора в «суворий режим» (Strict Mode). Цей режим реалізується за допомогою комбінації прапорців `set -euo pipefail` та контролю змінної роздільників `IFS`. Суворий режим запроваджує принцип детермінованої ранньої відмови (Fail-Fast): будь-яка неперехоплена помилка команди, звернення до неініціалізованої змінної або збій у будь-якій ланці конвеєра негайно переривають виконання сценарію. Ознайомитися з історичним контекстом та еволюцією цих механізмів від Bourne Shell до стандартів POSIX можна в [історії становлення суворого режиму](root:sys-unix/set-e-and-strict-mode/hist-unofficial-bash-strict-mode.md).

## Анатомія дозволеного режиму: чому оболонка ігнорує збої за замовчуванням

Головна відмінність командної оболонки від класичних компільованих систем полягає у відсутності статичного аналізу типів, попередньої лінковки символів та вбудованої моделі обробки винятків (Exceptions). Командний інтерпретатор працює як прямий посередник між текстом програми та ядром операційної системи. Кожен рядок сценарію перетворюється на вузол абстрактного синтаксичного дерева, виконання якого зводиться до ланцюжка системних викликів: створення анонімного каналу `pipe(2)`, дублювання файлових дескрипторів `dup2(2)`, клонування процесу `fork(2)` та завантаження виконуваного образу через `execve(2)`.

Коли дочірній процес завершує свою роботу — чи то внаслідок успішного виконання системного виклику `exit(0)`, чи через аварійне падіння з кодом `1` або знищення сигналом ядра — операційна система передає батьківській оболонці 8-бітне ціле число через виклик `waitpid(2)`. Інтерпретатор зберігає це число у спеціальній змінній `$?`.

```bash
# Класичний ланцюжок прихованої катастрофи в дозволеному режимі
cd /var/log/application_backups  # Каталог відсутній: cd повертає статус 1
rm -rf *                         # Оболонка ігнорує $? і стирає поточний каталог!
```

У дозволеному режимі ядро оболонки не вважає ненульовий статус приводом для паніки. Для інтерактивного парсера будь-який код повернення — це легітимний результат виконання команди. Інтерпретатор оновлює `$?` і негайно переходить до зчитування та виконання наступного рядка коду. Якщо перша інструкція зазнала збою через відсутність каталогу чи помилку прав доступу, наступна деструктивна операція `rm -rf *` виконується в поточному каталозі процесу, спричиняючи незворотну втрату даних.

Захищений режим ліквідує цю сліпоту за допомогою трьох взаємопов'язаних механізмів:

1. **`set -e` (`errexit`):** зупиняє скрипт, якщо будь-яка команда повертає статус, відмінний від `0`.
2. **`set -u` (`nounset`):** генерує фатальну помилку при спробі розгортання змінної, якій не було присвоєно значення.
3. **`set -o pipefail`:** змушує конвеєри повертати код помилки найправішої команди, що зазнала збою, замість статусу останнього процесу.

## Механіка `set -e` (`errexit`): правила негайної зупинки та пастки придушення

Прапорець `set -e` (або довга форма `set -o errexit`) активує внутрішній режим інтерпретатора, за якого будь-яка проста команда, що повернула ненульовий статус, спричиняє негайне переривання виконання всього сценарію. Концептуально це еквівалентно автоматичному додаванню перевірки `|| exit $?` після кожної командної інструкції.

У вихідному коді інтерпретатора Bash (файл `execute_cmd.c`) цей механізм реалізовано через глобальну змінну `exit_immediately_on_error`. Щоразу, коли завершується виконання вузла синтаксичного дерева, функція `execute_command_internal()` перевіряє значення `$?`. Якщо код не дорівнює нулю і прапорець `exit_immediately_on_error` активний, оболонка не повертає керування циклу парсингу, а викликає функцію аварійного завершення `exit_shell(last_command_exit_value)`.

Проте пряма реалізація такого правила унеможливила б роботу більшості стандартних алгоритмів: перевірки умов у розгалуженнях, циклів очікування подій та логічних ланцюжків обробки помилок. Тому стандарт POSIX запровадив складну систему винятків, відому як правила придушення `errexit`.

### Правила придушення `errexit` за стандартом POSIX

Стандарт POSIX визначає точні синтаксичні контексти, у яких прапорець `set -e` **повністю придушується**, а ненульовий код виходу передається керуючим конструкціям без зупинки скрипту:

1. **Команди перевірки умов у розгалуженнях і циклах:** команди, які виконуються безпосередньо як умова в блоках `if condition; then`, `while condition; do` або `until condition; do`. Якщо утиліта `grep` повертає `1` (рядок не знайдено), інтерпретатор сприймає цей статус як булеве значення «хибність» і спрямовує виконання в гілку `else`, не завершуючи процес.
2. **Ліва частина логічних операторів `||` та `&&`:** у виразі `cmd1 || cmd2` аварійне завершення `cmd1` не зупиняє скрипт, оскільки оператор `||` декларує наявність альтернативного коду. Якщо `cmd1` повертає статус `!= 0`, інтерпретатор передає керування `cmd2`. Проте для правої частини (`cmd2`) придушення не діє: якщо `cmd2` також завершиться з помилкою, `set -e` негайно перерве скрипт.
3. **Команди під дією оператора заперечення `!`:** у виразі `! cmd` ненульовий код завершення `cmd` інвертується ядром оболонки на `0`, що формально вважається успішним завершенням інструкції.

### Підступна пастка: виклик функцій усередині умовних блоків

Найнебезпечніший крайовий випадок `set -e` виникає при виклику користувацьких функцій у ролі умовних перевірок. Згідно зі специфікацією POSIX, якщо функція викликається як умова розгалуження `if func; then` або як лівий операнд `func || fallback`, **режим `set -e` автоматично вимикається для ВСІХ команд усередині тіла цієї функції**:

```bash
#!/usr/bin/env bash
set -e

deploy_service() {
    echo "Початок розгортання..."
    cp /non/existent/config.json /etc/app/config.json  # Помилка: файл не існує!
    echo "Конфігурацію скопійовано."
    systemctl restart my_app
}

# Виклик функції всередині умови if:
if deploy_service; then
    echo "Розгортання пройшло успішно!"
else
    echo "Збій розгортання!"
fi
```

У цьому прикладі розробник очікує, що команда `cp` зазнає збою, `set -e` перерве виконання функції `deploy_service`, і блок `if` перейде у гілку `else`.

На практиці інтерпретатор, зустрівши функцію в ролі перевірки умови, встановлює внутрішній прапорець ігнорування `errexit` на весь час виконання її тіла. Команда `cp` зазнає збою з кодом `1`, але оболонка мовчки ігнорує аварію, друкує «Конфігурацію скопійовано» і намагається перезапустити службу з відсутнім конфігураційним файлом! Якщо фінальна команда `systemctl` поверне `0`, функція поверне успішний статус, і скрипт повідомить про успіх операції, яка насправді зруйнувала працездатність вузла.

Щоб уникнути цієї пастки, функції, які виконують складні послідовності команд, ніколи не слід викликати безпосередньо всередині умовних виразів `if func; then` або `func || fallback`. Функцію викликають окремим рядком, або всередині самої функції здійснюють явну перевірку кожної критичної інструкції.

### Маскування помилок командою `local` та підстановкою команд

Ще одна поширена пастка Bash — поєднання оголошення локальної змінної через вбудовану команду `local` та присвоєння їй результату підстановки команди `$(...)`:

```bash
#!/usr/bin/env bash
set -e

fetch_user_data() {
    # КРИТИЧНА ПОМИЛКА: local повертає власний код виходу!
    local payload=$(curl --fail -s https://api.internal.network/users)
    echo "Отримано дані: ${payload}"
}
```

Утиліта `curl` зазнає невдачі через мережевий таймаут і завершується з аварійним кодом `22`. Проте рядок `local payload=$(curl ...)` виконується інтерпретатором у дві фази:
1. Запуск підстановки команди `$(curl ...)`, що повертає статус `22`;
2. Виконання вбудованої команди `local payload=...`.

Вбудована команда `local` успішно виділяє пам'ять у локальному фреймі функції й повертає статус `0`. Цей нульовий статус безумовно перезаписує змінну `$?`. Інтерпретатор вважає інструкцію успішною, і `set -e` не спрацьовує.

Ідіоматичний підхід вимагає роздільного оголошення змінної та присвоєння їй динамічного значення:

```bash
fetch_user_data_safe() {
    local payload
    payload=$(curl --fail -s https://api.internal.network/users)  # Тут set -e спрацює надійно
    echo "Отримано дані: ${payload}"
}
```

### Успадкування прапорця `errexit` у підоболонках: `shopt -s inherit_errexit`

Історично в інтерпретаторі Bash підоболонки, створені через підстановку команд `$(cmd)`, не успадковували активний стан прапорця `set -e`. Коли процес форкався для виконання вкладеного виразу, внутрішня функція ініціалізації підоболонки скидала `exit_immediately_on_error = 0`, дотримуючись застарілої поведінки ранніх версій Bourne Shell. Якщо всередині `$(cmd1; cmd2)` перша команда зазнавала збою, підоболонка продовжувала виконувати `cmd2`, повертаючи статус останньої операції.

Починаючи з версії **Bash 4.4**, розробники впровадили опцію:

```bash
shopt -s inherit_errexit
```

Ця опція гарантує, що всі підстановки команд безумовно підпорядковуються правилу негайної зупинки `set -e`. Повний перелік параметрів оболонки, опцій `shopt` та системних змінних наведено у [довіднику прапорців та змінних інтроспекції](root:sys-unix/set-e-and-strict-mode/api-shell-strict-mode-flags.md).

## Механіка `set -u` (`nounset`): захист від неініціалізованих змінних

Прапорець `set -u` (або `set -o nounset`) переводить інтерпретатор у режим суворого контролю простору імен. Коли прапорець активний, механізм розгортання параметрів (Parameter Expansion) змінює свою поведінку під час обробки змінних. Якщо скрипт намагається прочитати змінну, якій не було присвоєно значення і яка відсутня у системному масиві середовища `envp[]`, оболонка негайно генерує повідомлення про помилку в потік `stderr`:

```
bash: TARGET_DIR: unbound variable
```

Після виводу повідомлення процес негайно завершує роботу з кодом `1`.

### Катастрофічні сценарії та типографічні одруки

Найвідоміший приклад потреби в `set -u` — захист від випадкового видалення системних каталогів під час очищення робочих папок збірки:

```bash
# Небезпечний фрагмент без set -u:
TARGET_DIRECTORY="/tmp/build_cache"

# Розробник припустився одруку в назві змінної:
rm -rf "${TARGET_DIRCTORY}/*"
```

Без прапорця `set -u` інтерпретатор тихо замінює `${TARGET_DIRCTORY}` на порожній рядок. Команда перетворюється на `rm -rf "/*"`. Якщо скрипт виконується з привілеями суперкористувача `root`, операційна система повністю знищується.

За увімкненого `set -u` інтерпретатор зупиняє роботу ще на фазі розгортання рядка, блокуючи виконання системного виклику `unlinkat(2)` та запобігаючи руйнуванню файлової системи.

### Ідіоми безпечного доступу та значення за замовчуванням

Суворий режим вимагає явного декларування змінних, значення яких можуть бути відсутніми (необов'язкові конфігураційні параметри, позиційні аргументи `$1`, `$2`):

```bash
# 1. Використання значення за замовчуванням, якщо змінна не встановлена:
PORT="${APP_PORT:-8080}"

# 2. Присвоєння значення за замовчуванням самій змінній (якщо вона відсутня):
: "${CONFIG_PATH:=/etc/app/config.yaml}"

# 3. Безпечне читання позиційного аргументу командного рядка:
TARGET_ENV="${1:-production}"

# 4. Явна генерація фатального повідомлення про обов'язковий параметр:
DB_PASSWORD="${DATABASE_PASSWORD:?Помилка: змінна DATABASE_PASSWORD обов'язкова для запуску!}"
```

Конструкція `${VAR:-default}` є базовим інструментом безпечного доступу: вона повертає `default`, якщо змінна `VAR` не ініціалізована або містить порожній рядок, не провокуючи помилку `unbound variable`.

### Особливості роботи з масивами та позиційними параметрами

У ранніх версіях Bash (до версії 4.3) розгортання порожнього індексованого масиву `${ARRAY[@]}` під прапорцем `set -u` помилково вважалося зверненням до невизначеної змінної та призводило до аварійного завершення програми. У сучасних версіях Bash порожній масив коректно розгортається в нуль аргументів. Проте для абсолютної переносності між різними POSIX-середовищами застосовують шаблон умовного розгортання:

```bash
# Переносний шаблон ітерації по масиву під set -u:
for item in ${empty_list[@]+"${empty_list[@]}"}; do
    process_item "${item}"
done
```

Для асоціативних масивів перевірку наявності ключа завжди виконують через унарний оператор перевірки встановлення змінної `[[ -v assoc_array["key"] ]]` замість прямого читання значення `${assoc_array["key"]}`. Пряме звернення до неіснуючого ключа асоціативного масиву під дією `set -u` викликає фатальну помилку інтерпретатора.

## Механіка `set -o pipefail`: подолання сліпоти конвеєрів

Конвеєри (Pipelines) — фундаментальний механізм Unix, що реалізує паралельну потокову обробку даних. Під час виконання виразу `cmd1 | cmd2 | cmd3` ядро Unix створює кілька процесів, з'єднаних односпрямованими кільцевими буферами пам'яті ядра розміром 64 КБ (у Linux).

За замовчуванням стандарт POSIX визначає статус завершення всього конвеєра як код виходу **останньої (найправішої) команди**:

```
Статус конвеєра (cmd1 | cmd2 | cmd3) = Код виходу cmd3
```

Це правило створює критичну вразливість, якщо проміжний етап конвеєра є фільтром, архіватором чи утилітою запису журналу.

![Обробка статусів конвеєра та прапорець pipefail](/root/sys/sys-unix/set-e-and-strict-mode/img/pipeline-exit-status-and-pipefail.svg)
*Послідовність обробки кодів завершення процесів у конвеєрі: за замовчуванням інтерпретатор перевіряє лише останню команду, тоді як set -o pipefail аналізує весь масив PIPESTATUS.*

### Прихована катастрофа створення резервних копій

Розглянемо створення резервної копії бази даних утилітою `mysqldump`:

```bash
#!/usr/bin/env bash
set -e  # Прапорець errexit увімкнено!

# Створення резервної копії бази даних
mysqldump -u root -p"wrong_password" production_db | gzip > /backups/production.sql.gz

echo "Резервне копіювання успішно завершено!"
```

У цьому сценарії виникає прихований збій:
1. Команда `mysqldump` зазнає аварії через помилку авторизації, спрямовує текст помилки в `stderr`, генерує **0 байтів** у `stdout` і завершується з кодом `1`.
2. Утиліта `gzip` зчитує 0 байтів з анонімного каналу, формує валідний заголовок порожнього архіву розміром 20 байтів і завершується з кодом успіху `0`.
3. Оболонка зчитує код повернення останньої команди (`gzip`), бачить статус `0` і вважає конвеєр успішним.
4. Прапорець `set -e` не спрацьовує. Сценарій рапортує про успішне створення копії, завантажуючи пошкоджений файл у сховище.

### Принцип роботи `set -o pipefail` та масив `PIPESTATUS`

Активація прапорця `set -o pipefail` кардинально змінює алгоритм агрегації статусів:

> **Правило `pipefail`:** якщо хоча б одна команда в конвеєрі завершилася з ненульовим кодом, підсумковим статусом конвеєра стає код повернення **останньої (найправішої) команди, що зазнала невдачі**. Якщо всі команди завершилися успішно, конвеєр повертає `0`.

Під дією `pipefail` статус конвеєра стане рівним `1` (код помилки `mysqldump`). Прапорець `set -e` негайно зафіксує аварію та перерве виконання скрипту, запобігши створенню фальшивого бекапу.

Для інтроспекції стану всіх процесів конвеєра інтерпретатор Bash оновлює спеціальний масив:

```bash
${PIPESTATUS[@]}
```

Цей масив містить коди виходу всіх команд останнього виконаного конвеєра переднього плану:

```bash
cat /etc/hosts | grep "api_server" | awk '{print $1}'
# Якщо cat повернув 0, grep повернув 1 (не знайдено), awk повернув 0:
echo "Статуси етапів: ${PIPESTATUS[0]} ${PIPESTATUS[1]} ${PIPESTATUS[2]}"
# Виведе: Статуси етапів: 0 1 0
```

> ⚠️ **Важлива особливість:** масив `PIPESTATUS` перезаписується **першою ж наступною інструкцією**. Будь-який виклик (навіть `echo $?`) затирає збережені коди. Для надійного аналізу масив слід зберігати в локальну змінну одразу після виконання конвеєра: `pipe_codes=("${PIPESTATUS[@]}")`.

### Взаємодія `pipefail` із сигналом `SIGPIPE` (код `141`)

Використання `set -o pipefail` виявляє несподівану поведінку в конвеєрах, де одна з утиліт навмисно завершує роботу раніше за джерело даних:

```bash
#!/usr/bin/env bash
set -euo pipefail

# Читання перших трьох рядків із великого файлу
cat /var/log/huge_access.log | head -n 3
```

Коли утиліта `head` зчитує 3 рядки з каналу, вона негайно викликає `exit(0)`. Під час завершення процесу ядро автоматично закриває його відкриті дескриптори, зокрема дескриптор читання анонімного каналу.

У цей момент процес `cat` продовжує зчитувати гігабайтний файл із диска і намагається виконати наступний системний виклик `write(fd, buffer, count)` у канал, де лічильник зчитувачів (`pipe->readers`) дорівнює нулю. Згідно зі стандартами POSIX, запис у канал без читачів не може бути заблокований чи виконаний: ядро операційної системи генерує системний сигнал **`SIGPIPE`** (номер сигналу `13`) і надсилає його процесу `cat`.

Оскільки утиліта `cat` не встановлює власного обробника для `SIGPIPE`, застосовується стандартна дія сигналу (`SIG_DFL`) — негайне знищення процесу. Інтерпретатор Bash фіксує аварійне завершення дочірнього процесу за сигналом і формує код повернення за формулою:

```
Статус cat = 128 + Номер сигналу = 128 + 13 = 141
```

Без прапорця `pipefail` скрипт успішно продовжив би роботу, оскільки фінальна команда `head` повернула успішний код `0`. Проте під дією `set -o pipefail` ненульовий статус `141` стає підсумковим кодом усього конвеєра, і прапорець `set -e` аварійно перериває роботу всього сценарію!

Для безпечної обробки такої ситуації у місцях, де дострокове переривання зчитування є штатним поведінковим патерном, використовують явну перевірку статусу завершення через масив `PIPESTATUS`:

```bash
# Безпечна обробка можливого SIGPIPE:
cat /var/log/huge_access.log | head -n 3 || {
    status=$?
    if [[ ${status} -ne 141 ]]; then
        echo "Справжня помилка читання файлу: ${status}" >&2
        exit "${status}"
    fi
}
```

## Змінна `IFS=$'\n\t'`: розщеплення слів, пробіли та межі застосування

Змінна `IFS` (Internal Field Separator) визначає набір символів, які інтерпретатор використовує для поділу рядків на окремі аргументи під час фази **розщеплення слів (Word Splitting)** та роботи вбудованої команди `read`. За замовчуванням змінна `IFS` містить три символи: пробіл, табуляцію та символ нового рядка (`$' \t\n'`).

### Чому видалення пробілу з `IFS` було популярним

У класичній публікації Аарона Максвелла рекомендувалося на початку скрипту перевизначати `IFS`:

```bash
IFS=$'\n\t'
```

Логіка полягала в захисті від випадкового розщеплення імен файлів або рядків, що містять пробіли, якщо розробник забув взяти змінну в подвійні лапки:

```bash
# Припустимо, у каталозі є файл "Monthly Report 2026.pdf"
file="Monthly Report 2026.pdf"

# Зі стандартним IFS незалапкована змінна розпадеться на 3 аргументи:
# process_file "Monthly" "Report" "2026.pdf"

# З IFS=$'\n\t' (без пробілу) змінна залишиться єдиним аргументом:
process_file ${file}
```

### Небезпеки та побічні ефекти глобальної модифікації `IFS`

Сучасний інженерний консенсус застерігає від безконтрольного глобального перевизначення `IFS=$'\n\t'`. Зміна глобального `IFS` руйнує стандартну семантику мови оболонки:

1. **Руйнування циклів зі списками:** конструкція `for item in "alpha beta gamma"; do` перестає ділити рядок на слова і виконує тіло циклу один раз для всього рядка.
2. **Збій утиліти `read` для розбору полів:** команда `read -r user group shell <<< "root admin /bin/bash"` більше не розбиває потік на три окремі змінні за пробілами.
3. **Несумісність із бібліотечними функціями:** якщо скрипт підключає зовнішні модулі через `source`, вони розраховують на стандартний `IFS` і зазнають прихованих помилок.

### Сучасна альтернатива: лапки, масиви та локальний `IFS`

Замість глобальної мутації `IFS` сучасний стандарт розробки надійних сценаріїв вимагає трьох обов'язкових правил:

* **Завжди брати змінні в подвійні лапки:** `"$variable"` гарантує захист від розщеплення слів незалежно від значення `IFS`.
* **Використовувати нативні масиви Bash:** списки аргументів слід зберігати виключно в масивах `files=("$@")`, а читання виводу утиліт виконувати через команду `readarray -t` (або `mapfile -t`).
* **Локалізувати дію `IFS`:** перевизначати `IFS` лише для конкретного виклику команди `read` безпосередньо в рядку виконання:

```bash
# Локальне перевизначення IFS діє ВИКЛЮЧНО на команду read:
while IFS= read -r log_entry; do
    process_entry "${log_entry}"
done < /var/log/system.log
```

## Сучасна архітектура обробки помилок та відмовостійких сценаріїв

Сам по собі прапорець `set -e` забезпечує детерміновану зупинку, але створює проблему незавершених транзакцій: аварійний обрив виконання залишає заблоковані дескриптори, відкриті сокети та тимчасові файли на диску.

Побудова промислового сценарію вимагає комбінування суворого режиму із системними пастками сигналів `trap`.

```bash
#!/usr/bin/env bash
# ==============================================================================
# Сучасна преамбула надійного виробничого сценарію
# ==============================================================================
set -euo pipefail
set -E                               # Успадкування trap ERR функціями та subshells
shopt -s inherit_errexit 2>/dev/null || true  # Успадкування errexit у $(...)

# 1. Реєстрація гарантованого прибирання ресурсів
TEMP_DIR=""

cleanup() {
    local exit_code=$?
    set +e  # Вимикаємо errexit, щоб помилки видалення не блокували вихід
    if [[ -n "${TEMP_DIR:-}" && -d "${TEMP_DIR}" ]]; then
        rm -rf "${TEMP_DIR}"
    fi
    exit "${exit_code}"
}

trap cleanup EXIT
trap 'exit 130' INT   # Коректне завершення по Ctrl+C
trap 'exit 143' TERM  # Коректне завершення по kill/systemd
```

### Трасування помилок через `trap ... ERR` та `set -E`

За замовчуванням пастка `trap '...' ERR` діє лише на верхньому рівні скрипту і не викликається всередині функцій чи підоболонок. Прапорець `set -E` (або `set -o errtrace`) поширює обробник `ERR` на всі рівні вкладеності. Це дозволяє реалізувати повноцінну реконструкцію стека викликів (Call Stack Backtrace) у разі виникнення аварії:

```bash
# Обробник аварійного збою з виводом стека викликів
on_error() {
    local exit_code="$1"
    local line_no="$2"
    local cmd="${BASH_COMMAND}"

    echo "==========================================================" >&2
    echo "[ПОМИЛКА] Скрипт зазнав аварії з кодом ${exit_code}" >&2
    echo "[ПОМИЛКА] Команда: '${cmd}' на рядку ${line_no}" >&2
    echo "----------------------------------------------------------" >&2
    echo "Стек викликів:" >&2

    local i=0
    while caller "${i}" >/dev/null 2>&1; do
        local frame
        frame="$(caller "${i}")"
        echo "  [${i}] ${frame}" >&2
        (( i++ ))
    done
    echo "==========================================================" >&2
}

trap 'on_error $? $LINENO' ERR
```

### Штатна обробка очікуваних помилок під дією `set -e`

Якщо в коді є команда, ненульовий статус якої є штатним результатом і не повинен викликати аварійне переривання скрипту (наприклад, перевірка наявності запису через `grep`), використовують ідіому явного збереження статусу:

```bash
# Ідіома 1: Явне збереження коду повернення через логічне "АБО"
status=0
grep -q "admin_user" /etc/passwd || status=$?

if [[ ${status} -eq 0 ]]; then
    echo "Користувача знайдено."
elif [[ ${status} -eq 1 ]]; then
    echo "Користувача не знайдено (штатна ситуація)."
else
    echo "Критичний збій доступу до файлу: ${status}" >&2
    exit "${status}"
fi

# Ідіома 2: Використання всередині блоку if (errexit автоматично придушується)
if grep -q "admin_user" /etc/passwd; then
    echo "Знайдено."
fi
```

Повнофункціональний приклад виробничого сценарію, що об'єднує всі вищезазначені патерни, обробку аргументів та управління життєвим циклом ресурсів, наведено у [шаблоні відмовостійкого сценарію](root:sys-unix/set-e-and-strict-mode/proj-resilient-script-template.md).

## Інженерний чеклист надійності сценаріїв

1. **Обов'язкова преамбула:** розміщуйте `set -euo pipefail` на початку кожного файлу сценарію одразу після шебангу `#!/usr/bin/env bash`.
2. **Роздільне оголошення змінних:** ніколи не пишіть `local var=$(cmd)` в один рядок; завжди розділяйте на `local var` та `var=$(cmd)`.
3. **Ізоляція викликів складних функцій:** уникайте викликів функцій усередині виразів `if func; then` або `func || fallback`, якщо ці функції розраховують на дію `set -e` для власних внутрішніх інструкцій.
4. **Обов'язкове взяття в лапки:** усі змінні та результати підстановки команд повинні бути захищені подвійними лапками `"${var}"`, `"${array[@]}"`.
5. **Гарантоване очищення ресурсів:** реєструйте обробник `trap cleanup EXIT` одразу після створення будь-яких тимчасових файлів чи блокувань, вимикаючи `set +e` всередині самого тіла функції прибирання.
6. **Контроль `SIGPIPE`:** пам'ятайте, що утиліти на кшталт `head` у хвості конвеєра під `pipefail` повертають статус `141`, який потребує усвідомленої обробки.
