# ⚙️ Шаблон відмовостійкого сценарію: суворий режим, трасування помилок та безпечне прибирання

Цей проектний шаблон містить закінчену архітектурну основу для написання промислових сценаріїв Bash, призначених для роботи в конвеєрах неперервної інтеграції (CI/CD), системах керування конфігураціями та безпілотної автоматизації інфраструктури. Його відкривають як практичний еталон комбінування суворого режиму (`set -euo pipefail`), трасування викликів при збоях (`trap ... ERR`), гарантованого прибирання тимчасових ресурсів (`trap ... EXIT`) та безпечного розбору аргументів командного рядка.

---

## 1. Архітектурні вимоги до виробничого сценарію

Сценарій корпоративного рівня повинен задовольняти чотири обов'язкові інженерні вимоги, які відрізняють надійне програмне забезпечення від одноразових командних скриптів:

1. **Детермінована рання відмова (Fail-Fast):** будь-який неперехоплений збій зовнішньої програми, звернення до неініціалізованої змінної або падіння утиліти всередині конвеєра повинні негайно зупиняти виконання, унеможливлюючи лавиноподібне пошкодження файлової системи чи баз даних.
2. **Інтроспекція місця аварії (Traceability):** при виникненні помилки сценарій зобов'язаний вивести в потік `stderr` точний стек викликів (файл, рядок, ім'я функції) та текст команди, що спричинила збій, щоб черговий інженер міг локалізувати проблему без повторного запуску в ручному режимі.
3. **Гарантоване звільнення ресурсів (Idempotent Cleanup):** тимчасові каталоги, сокети, дескриптори блокувань та фонові дочірні процеси мають видалятися за будь-якого сценарію завершення роботи — як у разі штатного успіху, так і в разі аварії чи отримання сигналів `SIGINT` (`Ctrl+C`) або `SIGTERM`.
4. **Ізоляція стану та безпека змінних:** глобальні константи мають бути захищені від випадкового перезапису ключовим словом `readonly`, а функції повинні інкапсулювати власні змінні через ключове слово `local` з роздільним оголошенням та присвоєнням.

## 2. Повний вихідний код відмовостійкого шаблону

Нижче наведено повністю робочий, автономний сценарій `resilient_task_runner.sh`, готовий до використання як основа для будь-яких завдань системної автоматизації.

```bash
#!/usr/bin/env bash
# ==============================================================================
# НАЗВА: resilient_task_runner.sh
# ОПИС:  Виробничий шаблон сценарію з повною підтримкою Strict Mode,
#        стековим трасуванням помилок та автоматичним очищенням ресурсів.
# ==============================================================================

# 1. Активація захисного режиму виконання
set -euo pipefail
set -E                               # Успадкування trap ERR у функціях та підоболонках
shopt -s inherit_errexit 2>/dev/null || true  # Успадкування set -e у $(...) (Bash 4.4+)

# 2. Оголошення глобальних констант середовища
readonly SCRIPT_NAME="$(basename "${BASH_SOURCE[0]}")"
readonly SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd -P)"
readonly TIMESTAMP="$(date '+%Y-%m-%d %H:%M:%S')"

# Глобальна змінна для відстеження тимчасового робочого каталогу
WORK_DIR=""

# 3. Функції форматованого логування в stderr (не ламають потік stdout)
log_info() {
    printf "[%s] [INFO]  %s\n" "$(date '+%Y-%m-%d %H:%M:%S')" "$*" >&2
}

log_warn() {
    printf "[%s] [WARN]  %s\n" "$(date '+%Y-%m-%d %H:%M:%S')" "$*" >&2
}

log_error() {
    printf "[%s] [ERROR] %s\n" "$(date '+%Y-%m-%d %H:%M:%S')" "$*" >&2
}

# 4. Обробник аварійного стану та реконструкція стека викликів
handle_error() {
    local exit_code="$1"
    local line_no="$2"
    local failed_cmd="${BASH_COMMAND:-unknown}"

    log_error "=========================================================="
    log_error "АВАРІЙНА ЗУПИНКА СЦЕНАРІЮ"
    log_error "Команда: '${failed_cmd}'"
    log_error "Статус помилки: ${exit_code}"
    log_error "Місце збою: файл ${BASH_SOURCE[1]:-${SCRIPT_NAME}}, рядок ${line_no}"
    log_error "----------------------------------------------------------"
    log_error "Стек викликів (Call Stack Backtrace):"

    local frame=0
    while caller "${frame}" >/dev/null 2>&1; do
        local frame_info
        frame_info="$(caller "${frame}")"
        local c_line c_func c_file
        read -r c_line c_func c_file <<< "${frame_info}"
        log_error "  [${frame}] ${c_file}:${c_line} -> ${c_func}()"
        (( frame++ ))
    done
    log_error "=========================================================="
}

# 5. Гарантоване очищення тимчасових ресурсів (Idempotent Cleanup)
cleanup() {
    local exit_status=$?
    # Тимчасово вимикаємо errexit, щоб помилки при видаленні файлів не блокували вихід
    set +e

    if [[ -n "${WORK_DIR:-}" && -d "${WORK_DIR}" ]]; then
        log_info "Видалення тимчасового каталогу: ${WORK_DIR}"
        rm -rf "${WORK_DIR}"
    fi

    if [[ ${exit_status} -eq 0 ]]; then
        log_info "Сценарій успішно завершив роботу."
    else
        log_warn "Сценарій завершився з аварійним кодом: ${exit_status}"
    fi

    exit "${exit_status}"
}

# 6. Реєстрація системних пасток
trap 'handle_error $? $LINENO' ERR
trap cleanup EXIT
trap 'log_warn "Отримано сигнал SIGINT (Ctrl+C). Зупинка..."; exit 130' INT
trap 'log_warn "Отримано сигнал SIGTERM. Завершення процесу..."; exit 143' TERM

# 7. Допоміжні функції безпечного виконання

# Виконання команди, падіння якої є очікуваним і не повинно переривати скрипт
run_optional() {
    local status=0
    "$@" || status=$?
    return "${status}"
}

# 8. Розбір та валідація аргументів командного рядка
print_usage() {
    cat <<EOF
Використання: ${SCRIPT_NAME} [ОПЦІЇ]

Опції:
  -t, --target DIR     Цільовий каталог для обробки (обов'язковий)
  -b, --batch-size N   Розмір пакетної обробки (за замовчуванням: 50)
  -v, --verbose        Увімкнути детальний режим (set -x)
  -h, --help           Показати цю довідку та вийти
EOF
}

parse_arguments() {
    TARGET_DIR=""
    BATCH_SIZE=50
    VERBOSE=0

    while [[ $# -gt 0 ]]; do
        case "$1" in
            -t|--target)
                [[ $# -ge 2 ]] || { log_error "Опція '$1' вимагає аргументу"; exit 1; }
                TARGET_DIR="$2"
                shift 2
                ;;
            -b|--batch-size)
                [[ $# -ge 2 ]] || { log_error "Опція '$1' вимагає аргументу"; exit 1; }
                BATCH_SIZE="$2"
                shift 2
                ;;
            -v|--verbose)
                VERBOSE=1
                shift
                ;;
            -h|--help)
                print_usage
                exit 0
                ;;
            *)
                log_error "Невідомий параметр: $1"
                print_usage
                exit 1
                ;;
        esac
    done

    # Валідація обов'язкових параметрів
    if [[ -z "${TARGET_DIR}" ]]; then
        log_error "Помилка: параметр --target є обов'язковим."
        print_usage
        exit 1
    fi

    # Валідація числового формату batch-size
    if ! [[ "${BATCH_SIZE}" =~ ^[1-9][0-9]*$ ]]; then
        log_error "Помилка: --batch-size має бути додатним цілим числом (отримано: '${BATCH_SIZE}')."
        exit 1
    fi

    if [[ ${VERBOSE} -eq 1 ]]; then
        log_info "Активація режиму динамічного трасування xtrace (set -x)"
        set -x
    fi
}

# 9. Бізнес-логіка сценарію
process_data_payload() {
    local source_dir="$1"
    local batch_limit="$2"

    log_info "Створення ізольованого робочого середовища..."
    WORK_DIR="$(mktemp -d "/tmp/task_runner_XXXXXX")"
    log_info "Робочий каталог створено: ${WORK_DIR}"

    local staging_file="${WORK_DIR}/staging.data"
    local output_archive="${WORK_DIR}/result.tar.gz"

    log_info "Генерація тестових даних у ${staging_file}..."
    printf "record_%04d,value_%d\n" {1..100} 42 > "${staging_file}"

    log_info "Виконання фільтрації через конвеєр із перевіркою pipefail..."
    # Конвеєр безпечно контролюється set -o pipefail
    grep "record_" "${staging_file}" \
        | head -n "${batch_limit}" \
        | gzip -c > "${output_archive}"

    # Безпечне читання статусу останньої операції
    log_info "Розмір згенерованого архіву: $(wc -c < "${output_archive}") байтів"

    log_info "Перевірка обробки помилок, що не є фатальними..."
    if run_optional grep -q "non_existent_key" "${staging_file}"; then
        log_info "Ключ знайдено."
    else
        log_info "Очікувано: ключ не знайдено, статус 1 безпечно оброблено без зупинки скрипту."
    fi
}

# 10. Точка входу в програму (Main Entry Point)
main() {
    log_info "Ініціалізація сценарію '${SCRIPT_NAME}'..."
    parse_arguments "$@"

    log_info "Початок обробки для цілі: '${TARGET_DIR}', розмір пакета: ${BATCH_SIZE}"
    process_data_payload "${TARGET_DIR}" "${BATCH_SIZE}"
    log_info "Усі операції успішно завершено."
}

# Запуск головної функції з передачею всіх параметрів
main "$@"
```

## 3. Покроковий розбір життєвого циклу та внутрішніх механізмів

Розглянемо, як саме окремі компоненти шаблону взаємодіють між собою під час виконання програми та реагують на типові критичні ситуації.

### Фаза 1: Ініціалізація та налаштування ядра інтерпретатора

На самому початку скрипту виконується інструкція `set -euo pipefail`. Цей рядок встановлює базові інваріанти для всього процесу: будь-яке звернення до відсутньої змінної або збій утиліти негайно перериває процес. Додатковий виклик `set -E` змушує всі майбутні функції успадковувати обробник `ERR`, що є обов'язковою умовою для коректної роботи діагностичного трасування.

Рядок `shopt -s inherit_errexit 2>/dev/null || true` активує успадкування режиму зупинки у підстановках команд `$(...)`. Оскільки ця опція з'явилася лише у Bash 4.4, перенаправлення `2>/dev/null` та захисний хвіст `|| true` гарантують, що скрипт не впаде під час запуску на застарілих системах (наприклад, macOS із попередньо встановленим Bash 3.2).

### Фаза 2: Механізм розмотування стека викликів (Stack Unwinding)

Функція `handle_error` використовує вбудовану команду Bash `caller`. Команда `caller <frame>` повертає рядок із трьох елементів: номер рядка у вихідному коді, назву функції та ім'я файлу. Цикл `while caller "${frame}"` ітерується від вершини стека викликів (поточна функція, що зазнала збою) до кореневого рівня виконання.

Змінна `${BASH_COMMAND}` містить точний текст останньої інструкції, яка завершилася з ненульовим статусом. Завдяки цьому системний адміністратор у логах бачить не просто загальне повідомлення про збій, а точний виклик програми разом з усіма розгорнутими аргументами та послідовністю вкладених функцій.

### Фаза 3: Гарантоване очищення та захист від блокувань

Пастка `trap cleanup EXIT` є найнадійнішим способом звільнення системних ресурсів. Псевдосигнал `EXIT` генерується ядром інтерпретатора завжди, коли процес завершує роботу — чи то внаслідок штатного виходу `exit 0`, чи через аварійне спрацювання `set -e`, чи в результаті фатального винятку `set -u`.

Критично важливим елементом функції `cleanup` є інструкція `set +e` на першому рядку її тіла. Якщо під час видалення тимчасового каталогу `rm -rf "${WORK_DIR}"` виникне незначна помилка доступу (наприклад, файл зайнятий стороннім процесом), прапорець `set -e` без `set +e` міг би аварійно обірвати виконання самої функції очищення. Це призвело б до того, що наступні інструкції з вивільнення сокетів або видалення файлів блокувань залишилися б невиконаними.

Крім того, перевірка `[[ -n "${WORK_DIR:-}" && -d "${WORK_DIR}" ]]` захищає систему від випадкового виклику `rm -rf ""` або `rm -rf "/"`, якщо аварія сталася на ранньому етапі роботи до ініціалізації шляху `WORK_DIR`.

## 4. Патерни безпечного виконання вкладених операцій

Під час роботи в суворому режимі часто виникає потреба виконати команду, ненульовий статус якої є очікуваним і не свідчить про системну аварію (наприклад, перевірка наявності процесу через `pgrep` або пошук шаблону в файлі через `grep`).

Шаблон пропонує універсальну функцію-обгортку `run_optional`:

```bash
run_optional() {
    local status=0
    "$@" || status=$?
    return "${status}"
}
```

Завдяки конструкції `"$@" || status=$?` невдале виконання команди не призводить до спрацювання `set -e`, оскільки ліва частина оператора `||` підпадає під правила придушення POSIX. Функція повертає реальний код завершення утиліти, який можна безпечно перевірити у стандартному блоці `if` або зберегти для подальшого аналізу.

Такий підхід дозволяє зберегти загальну суворість виконання сценарію, локалізуючи точки контрольованої обробки статусів виходу без необхідності тимчасового вимкнення та повторного увімкнення `set +e` / `set -e`.
