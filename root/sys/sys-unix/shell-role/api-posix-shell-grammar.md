# 📋 Довідник граматики, послідовності підстановок та пріоритетів виконання POSIX shell

Цей довідник містить нормативну специфікацію порядку виконання та синтаксичного розбору команд у сумісних з POSIX.1-2017/POSIX.2 оболонках (`sh`, `bash`, `dash`, `zsh`). У ньому систематизовано послідовність етапів підстановок (expansions), ієрархію пошуку команд, класифікацію вбудованих утиліт, таблицю метасимволів, вирази модифікації параметрів, правила екранування лапками, розширені оператори перенаправлення та специфікацію статусів завершення процесів.

Довідник призначений для швидкого звернення під час проектирування системних сценаріїв автоматизації, налагодження складних командних конвеєрів та аналізу поведінки інтерпретаторів у спірних синтаксичних ситуаціях. Розуміння цих нормативних правил дозволяє запобігти витокам пам'яті, прихованим помилкам розбиття на слова та некоректній обробці сигналів операційної системи.

## 1. Послідовність етапів розширення (POSIX Expansion Pipeline)

Коли оболонка отримує проаналізовану командну стрічку, аргументи проходять через суворо визначену послідовність семи фаз розширення. Порядок фаз має критичне значення: результати попереднього етапу стають вхідними даними для наступного. Будь-яка зміна порядку обробки зламала б сумісність сценаріїв між різними дистрибутивами Unix та Linux.

| Фаза | Назва розширення | Англійська назва | Синтаксичний маркер | Опис та механізм |
| :--- | :--- | :--- | :--- | :--- |
| **1** | Розширення фігурних дужок | Brace Expansion | `{a,b}`, `{1..5}` | Породжує список слів. *Примітка:* Розширення bash/zsh, відсутнє в чистому POSIX.2, виконується найпершим. |
| **2** | Розширення тильди | Tilde Expansion | `~`, `~user` | Замінюється на абсолютний шлях до домашнього каталогу (`$HOME` або з `/etc/passwd`). |
| **3** | Підстановка параметрів, команд та арифметики | Parameter, Command, Arithmetic Expansion | `$VAR`, `${V:-def}`, `$(cmd)`, `` `cmd` ``, `$((1+2))` | Одночасне розширення змінних, виконання під-оболонок для збору `stdout` та обчислення цілочисельних виразів. |
| **4** | Розбиття на слова | Word Splitting | `$IFS` (space, tab, newline) | Результати фази 3 розбиваються на окремі аргументи за символами із змінної `IFS`. **Не виконується**, якщо змінна взята в подвійні лапки `"$VAR"`. |
| **5** | Розширення шляхів | Pathname Expansion (Globbing) | `*`, `?`, `[...]` | Перетворює шаблони у сортований список шляхів до існуючих файлів у VFS. |
| **6** | Видалення лапок | Quote Removal | `'...'`, `"..."`, `\` | Видаляє службові лапки та екрануючі символи, які захищали текст на попередніх етапах. |
| **7** | Перенаправлення | Redirection Setup | `<`, `>`, `>>`, `2>&1` | Налаштування файлових дескрипторів дочірнього процесу перед викликом `execve()`. |

Порушення розбиття на слова на фазі 4 є найпоширенішим джерелом уразливостей та помилок виконання в сценаріях оболонки. Якщо значення змінної містить пробіли (наприклад, ім'я файла `my file.txt`), невжиття подвійних лапок `"$VAR"` призведе до того, що на фазі 4 команда отримає два окремих аргументи `my` та `file.txt` замість одного цілісного шляху.

Спеціальна змінна `IFS` (Internal Field Separator) визначає, які саме символи розглядаються як роздільники слів на фазі 4. За умовчанням `IFS` містить пробіл, табуляцію та символ нового рядка. Якщо `IFS` обнулено (`IFS=''`), розбиття на слова вимикається повністю навіть для незалапкованих змінних.

## 2. Модифікатори розширення параметрів (Parameter Expansion Modifiers)

POSIX визначає точний набір синтаксичних модифікаторів для безпечної маніпуляції значеннями змінних без виклику зовнішніх утиліт `sed` чи `awk`.

| Синтаксис виразу | Назва операції | Логіка обробки значення |
| :--- | :--- | :--- |
| `${VAR:-default}` | Використання значення за умовчанням | Якщо `VAR` не встановлено або порожньо, повертає `default`. Сама `VAR` не змінюється. |
| `${VAR:=default}` | Присвоєння значення за умовчанням | Якщо `VAR` не встановлено або порожньо, присвоює їй `default` і повертає це значення. |
| `${VAR:?error_msg}` | Перевірка обов'язковості | Якщо `VAR` не встановлено або порожньо, друкує `error_msg` у `stderr` і перериває сценарій. |
| `${VAR:+alternative}` | Альтернативне значення | Якщо `VAR` встановлено і не порожньо, повертає `alternative`; інакше повертає порожній рядок. |
| `${#VAR}` | Довжина рядка | Повертає кількість символів у значенні змінної `VAR`. |
| `${VAR%pattern}` | Видалення найкоротшого суфікса | Видаляє найкоротший збіг з шаблоном `pattern` у кінці значення. |
| `${VAR%%pattern}` | Видалення найдовшого суфікса | Видаляє найдовший збіг з шаблоном `pattern` у кінці значення. |
| `${VAR#pattern}` | Видалення найкоротшого префікса | Видаляє найкоротший збіг з шаблоном `pattern` на початку значення. |
| `${VAR##pattern}` | Видалення найдовшого префікса | Видаляє найдовший збіг з шаблоном `pattern` на початку значення. |

Використання операторів `${VAR%pattern}` та `${VAR##pattern}` є стандартизованим способом вилучення розширення файла чи базового імені шляху у POSIX-скриптах без виклику утиліт `basename` та `dirname`, що економить виклики `fork()`.

## 3. Спеціальні параметри та змінні середовища POSIX

POSIX визначає групу зарезервованих односимвольних параметрів, які відображають поточний стан виконання оболонки. Ці параметри доступні лише для читання.

| Параметр | Назва та призначення | Системний механізм формування |
| :--- | :--- | :--- |
| `$PID` / `$$` | Ідентифікатор процесу оболонки (PID). | Зберігає PID головного процесу оболонки. Не змінюється у під-оболонках (subshells). |
| `$!` | PID останнього фонового процесу. | Формується при запуску команди з оператором `&`. |
| `$?` | Код виходу останньої виконаної команди. | Отримується через системний виклик `waitpid()` та макрос `WEXITSTATUS`. |
| `$-` | Прапорці поточного режиму оболонки. | Відображає активні опції (наприклад, `i` для інтерактивного режиму, `e` для `set -e`). |
| `$#` | Кількість позиційних параметрів. | Кількість аргументів, переданих скрипту або функції (`$1`, `$2`, ...). |
| `$*` | Усі позиційні параметри як один рядок. | У подвійних лапках `"$*"` об'єднує аргументи через перший символ змінної `IFS`. |
| `$@` | Усі позиційні параметри як окремі слова. | У подвійних лапках `"$@"` розгортається у список окремих залапкованих елементів `"$1" "$2" ...`. |

Відмінність між `"$*"` та `"$@"` є фундаментальною при передачі аргументів між функціями: використання `"$@"` гарантує, що аргументи з пробілами не будуть розбиті на фазі Word Splitting і не втратять свої межі.

## 4. Ієрархія пошуку та пріоритет виконання команд

Коли оболонка обробляє перше слово розширеної команди, вона шукає його значення відповідно до суворої пріоритетної драбини. Пошук припиняється на першому знайденому рівні, що дозволяє системному адміністраторові або розробнику перевизначати стандартну поведінку утиліт через псевдоніми або функції оболонки.

```
[ Початок пошуку команди ]
           │
           ▼
┌──────────────────────────┐   Так   ┌────────────────────────────────┐
│ 1. Alias (Псевдонім)     │────────►│ Виконується заміна тексту      │
└──────────────────────────┘         └────────────────────────────────┘
           │ Ні
           ▼
┌──────────────────────────┐   Так   ┌────────────────────────────────┐
│ 2. Keyword (Ключ. слово) │────────►│ Виконується керуюча структура  │
└──────────────────────────┘         │ (if, for, while, case, [[ ])   │
           │ Ні                      └────────────────────────────────┘
           ▼
┌──────────────────────────┐   Так   ┌────────────────────────────────┐
│ 3. Function (Функція)    │────────►│ Виконується тіло функції у     │
└──────────────────────────┘         │ контексті поточного процесу    │
           │ Ні                      └────────────────────────────────┘
           ▼
┌──────────────────────────┐   Так   ┌────────────────────────────────┐
│ 4. Special Builtin       │────────►│ Виконується вбудована команда  │
└──────────────────────────┘         │ (зміна стану оболонки / abort) │
           │ Ні                      └────────────────────────────────┘
           ▼
┌──────────────────────────┐   Так   ┌────────────────────────────────┐
│ 5. Regular Builtin       │────────►│ Виконується стандартна         │
└──────────────────────────┘         │ вбудована команда оболонки     │
           │ Ні                      └────────────────────────────────┘
           ▼
┌──────────────────────────┐   Так   ┌────────────────────────────────┐
│ 6. External PATH Binary  │────────►│ Створюється fork() -> execve() │
└──────────────────────────┘         └────────────────────────────────┘
           │ Ні
           ▼
[ Помилка: command not found (exit status 127) ]
```

### Деталізація категорій команд та їх відмінності

POSIX ділить вбудовані інструменти оболонки на дві принципово різні категорії, що мають різний вплив на стійкість сценаріїв до помилок та механіку їх переривання:

| Категорія | Приклади | Місце виконання | Вплив на стан оболонки при помилці |
| :--- | :--- | :--- | :--- |
| **Special Builtins** | `exec`, `eval`, `export`, `readonly`, `set`, `shift`, `trap`, `unset`, `.` (source) | Поточний процес | Синтаксична помилка або помилка виконання **примусово завершує** всю неінтерактивну оболонку. |
| **Regular Builtins** | `cd`, `echo`, `pwd`, `read`, `alias`, `test`, `kill`, `bg`, `fg`, `umask` | Поточний процес | Помилка повертає ненульовий статус `$?`, але **не перериває** виконання сценарію. |
| **Mandatory POSIX Utilities** | `ls`, `grep`, `sed`, `awk`, `cat`, `find`, `cp`, `mv` | Новий процес (`fork`) | Виконуються як окремі бинарні файли в просторі користувача з пошуком у `PATH`. |

Різниця між спеціальними та звичайними вбудованими командами критична для системних скриптів: якщо команда `export` зазнає синтаксичної помилки у неінтерактивному сценарії, POSIX-оболонка негайно припинить виконання всього скрипта, тоді як помилка у виконанні `cd` лише встановить статус `$? = 1`, дозволивши наступним командам виконатися.

## 5. Обробка сигналів та вбудована команда trap

Вбудована команда `trap` дозволяє оболонці перехоплювати сигнали ядра Linux і виконувати задані кодові блоки перед завершенням процесу.

| Формат команди trap | Призначення та механізм виконання |
| :--- | :--- |
| `trap 'cmd' SIGNAL` | Встановлює обробник `cmd` для сигналу `SIGNAL`. При отриманні сигналу оболонка виконує `cmd`. |
| `trap - SIGNAL` | Скидає обробник сигналу `SIGNAL` до стандартного системного значення за умовчанням. |
| `trap '' SIGNAL` | Налаштовує ігнорування сигналу `SIGNAL` (сигнал відкидається оболонкою та її нащадками). |
| `trap 'cmd' EXIT` | Псевдо-сигнал `EXIT`: виконує `cmd` при будь-якому завершенні оболонки (нормальному чи за `exit`). |
| `trap 'cmd' ERR` | Псевдо-сигнал `ERR` (bash/zsh): виконує `cmd` кожного разу, коли команда повертає ненульовий статус. |

Псевдо-сигнал `EXIT` є найважливішим інструментом забезпечення гарантованого очищення тимчасових файлів та каналів у системних сценаріях, аналогом деструкторів у мовах об'єктно-орієнтованого програмування.

## 6. Розширені оператори перенаправлення вводу-виводу

окрім базових операторів `<`, `>` та `>>`, POSIX визначає розширену граматику маніпуляції файловими дескрипторами.

| Оператор | Повна назва | Системний механізм ядра |
| :--- | :--- | :--- |
| `N>file` | Перенаправлення дескриптора N | Відкриває `file` via `open()` і дублює отриманий FD на місце дескриптора `N` via `dup2()`. |
| `M>&N` | Дублювання виводу M у N | Копіює посилання дескриптора N у дескриптор M. Наприклад, `2>&1` спрямовує stderr у stdout. |
| `N<&-` | Закриття дескриптора N | Закриває дескриптор N (`close(N)`), унеможливлюючи подальше читання чи запис. |
| `N>|file` | Примусовий перезапис | Перезаписує `file`, ігноруючи встановлену опцію оболонки `set -o noclobber`. |
| `<<EOF` | Here-Document | Створює тимчасовий анонімний файл у пам'яті/VFS, записує текст до `EOF` і спрямовує його у stdin. |
| `<<-EOF` | Here-Document з табуляцією | Аналогічно `<<EOF`, але автоматично видаляє початкові символи табуляції з кожного рядка. |

При використанні конструкції `2>&1 >out.txt` порядок має вирішальне значення: спочатку stderr дублюється на поточний stdout (термінал), а потім stdout перенаправляється у файл. У результаті stderr залишиться виводитися на термінал! Для спрямування обох потоків у файл вірний порядок є `>out.txt 2>&1`.

## 7. Таблиця метасимволів та операторів керування

POSIX визначає роздільну здатність символів у командному рядку за двома категоріями: **метасимволи** (відокремлюють токени) та **оператори керування** (визначають потік виконання та групування процесів).

| Символ / Оператор | Категорія | Функціональне призначення |
| :--- | :--- | :--- |
| `|` | Control Operator | Створює канал (pipe) між stdout лівої команди та stdin правої. |
| `&&` | Control Operator | Логічний І (AND): праворуч виконується лише якщо ліва повернула exit status `0`. |
| `||` | Control Operator | Логічний АБО (OR): праворуч виконується лише якщо ліва повернула exit status `!= 0`. |
| `;` | Control Operator | Послідовне виконання команд в одному процесі. |
| `&` | Control Operator | Фонове виконання: команда запускається в окремій групі процесів без очікування. |
| `( ... )` | Control Operator | Виконання блоку команд у під-оболонці (subshell — окремий `fork()`). |
| `{ ...; }` | Control Operator | Групування команд у поточному процесі оболонки. |
| `<`, `>`, `>>` | Redirection Operator | Перенаправлення stdin (`<`), створення/перезапис stdout (`>`), допис у stdout (`>>`). |
| `<&`, `>&` | Redirection Operator | Дублювання файлових дескрипторів (`2>&1` — спрямувати stderr у stdout). |

Метасимволи (такі як пробіл, табуляція, новий рядок, `|`, `&`, `;`, `(`, `)`, `<`, `>`) є синтаксичними кордонами для лексичного аналізатора. Будь-яка спроба використати ці символи як вміст аргументів вимагає їх обов'язкового екранування через `\` або взяття в одинарні/подвійні лапки.

Оператор групування у круглись дужках `( command )` примусово виконує кодовий блок у під-оболонці, викликаючи `fork()`. Натомість фігурні дужки `{ command; }` виконують кодовий блок у поточному процесі оболонки без створення нового процесу.

## 8. Коди виходу та обробка завершення процесів (Exit Status Specifications)

Згідно з POSIX, код виходу процесу є 8-бітним цілим числом без знака у діапазоні від `0` до `255`, яке зберігається у системній змінній оболонки `$?`. Ядро Linux передає код виходу через макроси системного виклику `waitpid()`.

| Статус `$?` | Значення та причина | Джерело формування |
| :--- | :--- | :--- |
| `0` | Успішне завершення (Success / True). | Повернуто `exit(0)` або `return 0`. |
| `1` .. `125` | Помилка утиліти або невірні аргументи. | Визначено самою утилітою (наприклад, `grep` не знайшов збігу -> `1`). |
| `126` | Команду знайдено, але файл **не є виконуваним** (Permission denied). | Оболонка при спробі `execve()` (помилка `EACCES`). |
| `127` | Команду **не знайдено** у каталогах `PATH` (Command not found). | Оболонка при спробі `execve()` (помилка `ENOENT`). |
| `128 + N` | Процес вбито сигналом ядра номер `N`. | Сформовано оболонкою на основі `waitpid()` макросу `WTERMSIG(status)`. |

### Спеціальні випадки сигнатур виходу (128 + N)
- `130` (`128 + 2`): Процес перервано сигналом `SIGINT` (натискання `Ctrl+C`).
- `137` (`128 + 9`): Процес примусово вбито сигналом `SIGKILL` (Out-Of-Memory killer або `kill -9`).
- `143` (`128 + 15`): Процес завершено сигналом `SIGTERM` (стандартне завершення роботи від systemd/docker).

Розуміння конвенції `128 + N` дозволяє сценаріям точно розрізняти звичайні програмні помилки (коди 1..125) від примусового переривання процесу зовнішніми сигнатурними подіями операційної системи.
