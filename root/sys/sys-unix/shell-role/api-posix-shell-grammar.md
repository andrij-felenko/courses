## 1. Формальна граматика POSIX Shell (IEEE Std 1003.1 §2.10)

Синтаксичний аналізатор POSIX-оболонки транслює потік лексичних токенів у дерево виконання на основі контекстно-вільної граматики LALR(1). Граматика визначає ієрархію синтаксичних одиниць: від найпростіших слів та операторів перенаправлення до конвеєрів, логічних списків та складених керуючих структур.

### Продукційні правила граматики (Yacc / EBNF)

Нижче наведено нормативну формальну граматику командної мови POSIX у нотації БGeneral/Yacc:

```yacc
/* Повна програма або командний рядок */
complete_commands : complete_commands newline_list complete_command
                  | complete_command
                  | /* порожньо */
                  ;

complete_command  : list separator_op
                  | list
                  ;

list              : list separator_op and_or
                  | and_or
                  ;

/* Логічні оператори І (&&) та АБО (||) */
and_or            : pipeline
                  | and_or AND_IF linebreak pipeline
                  | and_or OR_IF  linebreak pipeline
                  ;

/* Конвеєр команд */
pipeline          : pipe_sequence
                  | Bang pipe_sequence
                  ;

pipe_sequence     : command
                  | pipe_sequence '|' linebreak command
                  ;

/* Команда: проста, складена або визначення функції */
command           : simple_command
                  | compound_command
                  | compound_command redirect_list
                  | function_definition
                  ;

/* Проста команда: префікси (присвоєння/редиректи), ім'я, аргументи */
simple_command    : cmd_prefix cmd_word cmd_suffix
                  | cmd_prefix cmd_word
                  | cmd_prefix
                  | cmd_name cmd_suffix
                  | cmd_name
                  ;

cmd_name          : WORD ; /* Застосовується перевірка на зарезервоване слово */
cmd_word          : WORD ;

cmd_prefix        : io_redirect
                  | cmd_prefix io_redirect
                  | ASSIGNMENT_WORD
                  | cmd_prefix ASSIGNMENT_WORD
                  ;

cmd_suffix        : io_redirect
                  | cmd_suffix io_redirect
                  | WORD
                  | cmd_suffix WORD
                  ;

/* Складені команди */
compound_command  : brace_group
                  | subshell
                  | for_clause
                  | case_clause
                  | if_clause
                  | while_clause
                  | until_clause
                  ;

subshell          : '(' compound_list ')' ;
brace_group       : '{' compound_list '}' ;

/* Визначення функції */
function_definition : fname '(' ')' linebreak function_body ;
function_body       : compound_command
                    | compound_command redirect_list
                    ;
fname               : NAME ;

/* Списки перенаправлень */
redirect_list     : io_redirect
                  | redirect_list io_redirect
                  ;

io_redirect       : io_file
                  | IO_NUMBER io_file
                  | io_here
                  | IO_NUMBER io_here
                  ;

io_file           : '<'       filename
                  | '<&'      filename
                  | '>'       filename
                  | '>&'      filename
                  | '>>'      filename
                  | '<>'      filename
                  | '>|'      filename
                  ;

io_here           : DLESS     here_end
                  | DLESSDASH here_end
                  ;
```

### Пріоритет синтаксичних операторів

Оператори мови оболонки мають чітку ієрархію зв'язування від найвищого пріоритету до найнижчого:

1. **Оператори перенаправлення (`<`, `>`, `>>`, `<&`, `>&`, `>|`, `<<`, `<<-`, `<>`):** зв'язуються безпосередньо з окремою простою або складеною командою.
2. **Оператор конвеєра (`|`):** об'єднує суміжні команди у ланцюг потокової передачі даних. Має вищий пріоритет за логічні та розділові оператори.
3. **Логічні оператори списків (`&&`, `||`):** лівоасоціативні оператори з однаковим пріоритетом. Виконуються зліва направо з короткою оцінкою (short-circuit evaluation).
4. **Асинхронні та послідовні роздільники (`;`, `&`, `\n`):** мають найнижчий пріоритет, розділяючи повністю сформовані ланцюги `and_or`.

```
┌─────────────────────────────────────────────────────────────┐
│  Пріоритет 1 (Найвищий): Перенаправлення FD (<, >, >>, >&)  │
└──────────────────────────────┬──────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────┐
│  Пріоритет 2: Конвеєр процесів (|)                          │
└──────────────────────────────┬──────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────┐
│  Пріоритет 3: Логічні оператори І/АБО (&&, ||)              │
└──────────────────────────────┬──────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────┐
│  Пріоритет 4 (Найнижчий): Роздільники команд (;, &, \n)     │
└─────────────────────────────────────────────────────────────┘
```

## 2. Лексичний аналіз, токенізація та розпізнавання слів (IEEE Std 1003.1 §2.3)

Лексичний аналізатор (сканер) перетворює потік вхідних символів на послідовність токенів. Токенізація виконується за алгоритмом кінцевого автомата, регламентованим 10 правилами стандарту POSIX §2.3.

### 10 правил токенізації POSIX

1. **Кінець вводу (EOF):** Якщо досягнуто кінця вводу, поточний токен (якщо він формувався) завершується і повертається.
2. **Символи екранування (`\`, `'`, `"`):** Якщо зчитується зворотний слеш, одинарна або подвійна лапка, лексер переходить у стан цитування, накопичуючи символи до закриття відповідної лапки.
3. **Маркери розширення (`$`, `` ` ``, `(`):** Початок підстановки параметрів, виклику команд або арифметики призводить до рекурсивного накопичення всього внутрішнього виразу до відповідної закриваючої дужки `}` або `)`.
4. **Операторні метасимволи (`|`, `&`, `;`, `<`, `>`, `(`, `)`):**
   - Якщо символ може продовжити поточний оператор (наприклад, другий `&` для `&&`, другий `|` для `||`, другий `;` для `;;`, або `>` для `>>`), він додається до оператора.
   - Якщо символ не може продовжити поточний токен, накопичений токен завершується, а операторний символ стає початком нового токена.
5. **Попередній токен-оператор:** Якщо попередній токен був розпізнаний як оператор, він негайно повертається синтаксичному аналізатору.
6. **Розділові пробільні символи (пробіл, табуляція):** Якщо поточний символ є пробілом або табуляцією:
   - Якщо формувався токен, він завершується і передається парсеру.
   - Пробільний символ відкидається (не накопичується).
7. **Звичайні символи:** Символ додається до буфера поточного слова.
8. **Розпізнавання числових дескрипторів (`IO_NUMBER`):** Якщо токен складається виключно з десяткових цифр і за ним **безпосередньо** слідує символ `<` або `>`, токен класифікується не як слово `WORD`, а як числовий дескриптор введення-виведення `IO_NUMBER`.
9. **Конструювання слова:** Якщо жодне з попередніх правил не спрацювало, символ накопичується як частина `WORD`.
10. **Контекстна класифікація зарезервованих слів:** Щойно токен-слово `WORD` сформовано, лексер перевіряє таблицю зарезервованих слів з урахуванням граматичного контексту.

### Контекстні правила розпізнавання зарезервованих слів (Keywords)

Слова `if`, `then`, `else`, `elif`, `fi`, `do`, `done`, `case`, `esac`, `while`, `until`, `for`, `{`, `}`, `!`, `in` розпізнаються як ключові слова тільки за суворих умов:

- Токен не містить лапок і не є результатом підстановки змінних (розширення не породжують ключових слів).
- Токен стоїть першим словом простої команди (після `;`, `&`, `\n`, `&&`, `||`, `|`, `(`).
- Токен слідує за зарезервованими словами, що вимагають інструкції: після `then`, `else`, `elif`, `do`.
- Токен `in` розпізнається як ключове слово виключно у заголовках конструкцій `for name in ...` та `case word in ...`.
- Токен `}` розпізнається як зарезервоване слово лише на початку команди. Саме тому фігурна дужка вимагає перед собою роздільника `;` або нового рядка: `{ cmd; }` є валідним, тоді як `{ cmd }` спричиняє синтаксичну помилку, бо `}` трактується як звичайний аргумент команди `cmd`.

```
Синтаксично валідно:       { echo "hello"; }
                                         ▲
                         Роздільник ';' відокремлює '}' у позицію нової команди

Синтаксична помилка:       { echo "hello" }
                                          ▲
                         '}' сприймається як аргумент утиліти echo!
```

### Механізм розкриття псевдонімів (Alias Substitution)

Якщо розпізнаний токен є першим словом команди і збігається з зареєстрованим псевдонімом (`alias`):
1. Тіло псевдоніма підставляється у вхідний потік лексера на місце поточного слова.
2. Сканування тексту псевдоніма починається повторно (рекурсивна токенізація).
3. Якщо останній символ значення псевдоніма є пробілом або табуляцією, наступне за ним слово також піддається перевірці на розкриття псевдонімів.
4. Оболонка веде стек активних аліасів для запобігання нескінченному циклу: якщо псевдонім розгортається сам у себе (`alias ls='ls -color'`), повторне розкриття того самого імені блокується.

## 3. Складені команди: синтаксис та семантика виконання (IEEE Std 1003.1 §2.9)

Складені команди управляють потоком виконання та групуванням процесів. Кожна складена команда має статус завершення, що дорівнює коду виходу останньої виконаної внутрішньої команди.

### Умовне розгалуження: `if ... then ... elif ... else ... fi`

Синтаксис:
```bash
if compound-list
then
    compound-list
[elif compound-list
then
    compound-list]...
[else
    compound-list]
fi
```

- Оболонка виконує `compound-list` після `if`.
- Якщо код виходу `$? == 0`, виконується блок `then`.
- Якщо `$? != 0`, послідовно перевіряються секції `elif`. Якщо жодна умова не повернула `0`, виконується блок `else`.
- Якщо жодна умова не справдилася і блок `else` відсутній, конструкція `if` повертає статус `0`.

### Цикл ітерації: `for name [in word ...] do compound-list done`

Синтаксис:
```bash
for variable [in word1 word2 ... wordN]
do
    compound-list
done
```

- Слова після `in` розгортаються (підстановки полів, шляхів тощо) **один раз** перед початком циклу.
- Якщо секцію `in word...` опущено, цикл за замовчуванням ітерує по позиційних параметрах: `in "$@"`.
- Змінній `variable` по черзі присвоюється кожне слово, і виконується `compound-list`.
- Статус виходу: код виходу останньої виконаної команди в тілі, або `0`, якщо список слів був порожнім.

### Цикли з передумовою: `while` та `until`

Синтаксис:
```bash
while condition-list do body-list done
until condition-list do body-list done
```

- `while`: Виконує `condition-list`. Якщо `$? == 0`, виконує `body-list` і повторює ітерацію. Цикл завершується, коли `condition-list` повертає ненульовий статус.
- `until`: Виконує `condition-list`. Якщо `$? != 0`, виконує `body-list` і повторює ітерацію. Цикл завершується, коли `condition-list` повертає статус `0`.
- Якщо тіло циклу не виконувалося жодного разу, статус завершення дорівнює `0`.

### Селектор за шаблонами: `case word in pattern) list ;; esac`

Синтаксис:
```bash
case word in
    [(] pattern1 [| pattern2]... )
        compound-list
        ;;
    [(] pattern3 )
        compound-list
        ;&   # Розширення POSIX.1-2024 / bash: fallthrough без перевірки
        ;;
    [(] pattern4 )
        compound-list
        ;;&  # Розширення POSIX.1-2024 / bash: продовження тестування наступних патернів
        ;;
esac
```

- Слово `word` піддається підстановці параметрів, арифметики та вилученню лапок (розширення шляхів не виконується).
- Патерни перевіряються зверху вниз за правилами зіставлення файлових шаблонів (fnmatch: `*`, `?`, `[...]`).
- Оператор `;;` припиняє виконання всієї конструкції `case`.
- Оператор `;&` (fallthrough) безумовно передає керування на тіло наступного блоку.
- Оператор `;;&` перевіряє наступні шаблони у списку.

### Під-оболонка `( list )` проти групування в поточному процесі `{ list; }`

| Критерій | Під-оболонка `( list )` | Блок групування `{ list; }` |
| :--- | :--- | :--- |
| **Системний процес** | Створюється новий дочірній процес через `fork()`. | Виконується в **поточному** процесі оболонки. |
| **Зміна середовища** | Змінні, `cd`, `umask`, `trap` діють лише всередині під-оболонки і безслідно зникають після її завершення. | Будь-які зміни змінних та стану залишаються в поточному процесі. |
| **Синтаксичні межі** | Круглі дужки є операторами: пробіли навколо `(` та `)` **не потрібні**. | Фігурні дужки є зарезервованими словами: потрібні **пробіли** та роздільник `;` перед `}`. |
| **Продуктивність** | Накладні витрати на дублювання таблиць сторінок процесу (`fork`). | Нульові накладні витрати на рівні ядра. |

## 4. Пріоритети перенаправлення та механіка дескрипторів (IEEE Std 1003.1 §2.7)

Перенаправлення вводу-виводу переконфігурує таблицю файлових дескрипторів процесу. Стандарт POSIX встановлює фундаментальний закон: **перенаправлення обчислюються суворо зліва направо у порядку їх появи в командному рядку**.

### Покроковий системний аналіз: `2>&1 >file` проти `>file 2>&1`

Різниця у порядку операторів є найвідомішою пасткою системного адміністрування:

```
Сценарій А:  command 2>&1 >output.txt
Сценарій Б:  command >output.txt 2>&1
```

Нижче наведено покрокову трансформацію таблиці файлових дескрипторів процесу в ядрі Linux:

#### Сценарій А: `command 2>&1 >output.txt` (Помилка: stderr лишається на терміналі)

1. **Початковий стан процесу:**
   - `FD 0` -> `/dev/pts/1` (stdin)
   - `FD 1` -> `/dev/pts/1` (stdout)
   - `FD 2` -> `/dev/pts/1` (stderr)
2. **Крок 1 (`2>&1`):** Оболонка виконує системний виклик `dup2(1, 2)`. Дескриптор `2` тепер посилається на ту саму структуру відкритого файла (Open File Description) у ядрі, на яку вказує `FD 1` (термінал `/dev/pts/1`).
3. **Крок 2 (`>output.txt`):** Оболонка відкриває файл via `open("output.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666)` -> повертається тимчасовий `FD 3`. Виконується `dup2(3, 1)` і `close(3)`. Дескриптор `1` тепер посилається на `output.txt`.
4. **Результат:** `FD 1` пише у файл, але `FD 2` продовжує писати у термінал `/dev/pts/1`!

```
[Початковий стан]
FD 1 ──────► [ /dev/pts/1 ]
FD 2 ──────► [ /dev/pts/1 ]

[Крок 1: 2>&1] -> dup2(1, 2)
FD 1 ──────► [ /dev/pts/1 ]
FD 2 ──────► [ /dev/pts/1 ] (копія посилання FD 1 на термінал)

[Крок 2: >output.txt] -> open() + dup2(3, 1)
FD 1 ──────► [ Файл output.txt ]
FD 2 ──────► [ /dev/pts/1 ]  <--- ПОМИЛКА: stderr не потрапив у файл!
```

#### Сценарій Б: `command >output.txt 2>&1` (Коректно: обидва потоки у файлі)

1. **Початковий стан процесу:** `FD 1` -> `/dev/pts/1`, `FD 2` -> `/dev/pts/1`.
2. **Крок 1 (`>output.txt`):** Відкривається файл -> `FD 3`. Виконується `dup2(3, 1)` і `close(3)`. Дескриптор `1` перемикається на `output.txt`.
3. **Крок 2 (`2>&1`):** Виконується `dup2(1, 2)`. Дескриптор `2` копіює посилання з `FD 1`, яке **вже вказує** на `output.txt`.
4. **Результат:** І `FD 1`, і `FD 2` вказують на одну й ту саму відкриту файлову позицію в ядрі.

```
[Початковий стан]
FD 1 ──────► [ /dev/pts/1 ]
FD 2 ──────► [ /dev/pts/1 ]

[Крок 1: >output.txt] -> open() + dup2(3, 1)
FD 1 ──────► [ Файл output.txt ]
FD 2 ──────► [ /dev/pts/1 ]

[Крок 2: 2>&1] -> dup2(1, 2)
FD 1 ──────► [ Файл output.txt ]
FD 2 ──────► [ Файл output.txt ]  <--- ПРАВИЛЬНО: обидва потоки у файлі
```

### Повна таблиця операторів перенаправлення

| Оператор | Повна назва | Системні виклики ядра | Опис та семантика |
| :--- | :--- | :--- | :--- |
| `[N]<file` | Читання з файла | `open(file, O_RDONLY)` + `dup2(fd, N)` | Відкриває файл на читання у дескриптор `N` (дефолт `0`). |
| `[N]>file` | Запис у файл | `open(file, O_WRONLY\|O_CREAT\|O_TRUNC)` + `dup2` | Створює/обнуляє файл для дескриптора `N` (дефолт `1`). |
| `[N]>>file` | Допис у файл | `open(file, O_WRONLY\|O_CREAT\|O_APPEND)` + `dup2` | Відкриває файл в режимі додавання в кінець. |
| `[N]>|file` | Примусовий перезапис | `open(file, O_WRONLY\|O_CREAT\|O_TRUNC)` + `dup2` | Ігнорує опцію захисту від перезапису `set -C` (`noclobber`). |
| `[N]<>file` | Читання та запис | `open(file, O_RDWR\|O_CREAT)` + `dup2` | Відкриває файл одночасно на читання і запис у дескриптор `N`. |
| `[M]<&N` | Дублювання читання | `dup2(N, M)` | Копіює дескриптор читання `N` у `M` (дефолт `0`). |
| `[M]>&N` | Дублювання запису | `dup2(N, M)` | Копіює дескриптор запису `N` у `M` (дефолт `1`). |
| `[N]<&-` | Закриття FD на читання | `close(N)` | Закриває дескриптор введення `N` (дефолт `0`). |
| `[N]>&-` | Закриття FD на запис | `close(N)` | Закриває дескриптор виведення `N` (дефолт `1`). |
| `[N]<<EOF` | Here-Document | `pipe()` або `memfd_create()` + `write()` | Передає вбудований блок тексту на вхід дескриптора `N`. |
| `[N]<<-EOF` | Here-Doc зі стрипом | Аналогічно `<<`, але з видаленням провідних `\t` | Видаляє початкові табуляції (ASCII `0x09`) з кожного рядка. |
| `[N]<<<str` | Here-String | `pipe()` + `write(str)` + `dup2()` | Передає розгорнутий рядок `str` у дескриптор `N` (bash/zsh). |

### Перенаправлення у вбудованих командах (Збереження та відновлення FD)

Коли перенаправлення застосовується до вбудованої команди (`cd`, `echo`, `read`, `exec`), яка виконується в поточному процесі оболонки без виклику `fork()`, оболонка зобов'язана зберегти оригінальні дескриптори:

1. **Збереження:** Оболонка створює резервну копію дескриптора за межами стандартного діапазону: `saved_stdout = fcntl(1, F_DUPFD_CLOEXEC, 10)`.
2. **Перенаправлення:** Виконується `dup2(target_fd, 1)`.
3. **Виконання:** Викликається внутрішня функція вбудованої утиліти.
4. **Відновлення:** Виконується `dup2(saved_stdout, 1)` та `close(saved_stdout)`.

Винятком є спеціальна вбудована команда `exec <file >file`: вона **не відновлює** дескриптори, змінюючи їх для всього подальшого життєвого циклу поточної оболонки.

## 5. Послідовність етапів розширення (POSIX Expansion Pipeline)

Коли командний рядок розібрано на слова, аргументи проходять через суворо визначену послідовність 7 фаз розширення (IEEE Std 1003.1 §2.6).

```
┌─────────────────────────────────────────────────────────────┐
│ 1. Brace Expansion: {a,b,c} (bash/zsh розширення)           │
└──────────────────────────────┬──────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. Tilde Expansion: ~ -> /home/user                         │
└──────────────────────────────┬──────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. Parameter, Command & Arithmetic: $VAR, $(cmd), $((1+2))   │
│    (Виконуються паралельно зліва направо у кожному слові)   │
└──────────────────────────────┬──────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 4. Word Splitting: розбиття нелапкованого виводу за $IFS    │
└──────────────────────────────┬──────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 5. Pathname Expansion (Globbing): *.txt, [a-z]              │
└──────────────────────────────┬──────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 6. Quote Removal: видалення службових ', ", \               │
└──────────────────────────────┬──────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 7. Redirection Setup: open(), dup2(), close()               │
└─────────────────────────────────────────────────────────────┘
```

### Модифікатори розширення параметрів (Parameter Expansions)

POSIX регламентує набір операторів для безпечної обробки змінних без запуску зовнішніх процесів:

| Синтаксис виразу | Назва операції | Логіка обробки значення |
| :--- | :--- | :--- |
| `${VAR:-default}` | Значення за умовчанням | Якщо `VAR` не встановлено або порожньо, повертає `default`. Змінна не змінюється. |
| `${VAR:=default}` | Присвоєння за умовчанням | Якщо `VAR` не встановлено або порожньо, присвоює їй `default` і повертає його. |
| `${VAR:?error_msg}` | Перевірка обов'язковості | Якщо `VAR` не встановлено або порожньо, друкує `error_msg` у `stderr` і перериває скрипт. |
| `${VAR:+alternative}` | Альтернативне значення | Якщо `VAR` встановлено і не порожньо, повертає `alternative`; інакше повертає порожній рядок. |
| `${#VAR}` | Довжина рядка | Повертає кількість символів (в юнікоді або байтах залежно від `LC_CTYPE`). |
| `${VAR#pattern}` | Видалення найкоротшого префікса | Видаляє найкоротший збіг з шаблоном `pattern` на початку значення. |
| `${VAR##pattern}` | Видалення найдовшого префікса | Видаляє найдовший збіг з шаблоном `pattern` на початку значення. |
| `${VAR%pattern}` | Видалення найкоротшого суфікса | Видаляє найкоротший збіг з шаблоном `pattern` у кінці значення. |
| `${VAR%%pattern}` | Видалення найдовшого суфікса | Видаляє найдовший збіг з шаблоном `pattern` у кінці значення. |

*Примітка щодо двокрапки:* Якщо у виразах `:-`, `:=`, `:?`, `:+` прибрати двокрапку (наприклад, `${VAR-default}`), перевірка здійснюватиметься **лише на факт встановлення** змінної (`unset`), ігноруючи встановлені порожні рядки (`VAR=""`).

### Спеціальні параметри POSIX

| Параметр | Назва та призначення | Механізм формування |
| :--- | :--- | :--- |
| `$$` | PID поточної оболонки. | PID батьківського процесу; зберігає первинне значення навіть у під-оболонках. |
| `$!` | PID останнього асинхронного процесу. | Формується системним викликом `fork()` при запуску команди з оператором `&`. |
| `$?` | Код виходу останньої команди. | Отримується через `waitpid()` та макрос `WEXITSTATUS` / `WTERMSIG`. |
| `$-` | Прапорці поточного режиму. | Відображає активні опції інтерпретатора (наприклад, `ims` або `e`). |
| `$#` | Кількість позиційних параметрів. | Кількість аргументів у поточному стеку функцій або скрипта (`$1`, `$2`...). |
| `$*` | Усі параметри як один рядок. | У подвійних лапках `"$*"` склеює елементи через перший символ `$IFS` (за замовчуванням пробіл). |
| `$@` | Усі параметри як окремі слова. | У подвійних лапках `"$@"` розгортається у точний список слів `"$1" "$2" ... "$N"`. |
| `$0` | Ім'я оболонки або файлу скрипта. | Передається як нульовий аргумент масиву `argv[0]` при виклику `execve()`. |

### Правила екранування лапками (Quoting Rules)

- **Одинарні лапки (`'...'`):** Повністю блокують будь-яку інтерпретацію символів. Всередині одинарних лапок не можна вставити одинарну лапку навіть через `\'`.
- **Подвійні лапки (`"..."`):** Блокують розбиття на слова (Word Splitting) та розширення шляхів (Globbing), але **дозволяють**:
  - Розширення параметрів (`$VAR`, `${VAR}`)
  - Підстановку команд (`$(cmd)`, `` `cmd` ``)
  - Арифметичні підстановки (`$((expr))`)
  - Екранування символів `\$`, `\"`, `` \` ``, `\\`, `\newline` зворотним слешем.
- **Зворотний слеш (`\`):** Екранує наступний символ. Якщо стоїть безпосередньо перед новим рядком (`\\n`), видаляє символ переходу на новий рядок, склеюючи рядки коду в один.
- **ANSI-C лапки (`$'...'` — POSIX.1-2024 / bash / zsh):** Інтерпретують C-подібні керівні послідовності (`\n`, `\t`, `\r`, `\xHH`, `\uHHHH`).

### Спеціальні проти регулярних вбудованих команд

POSIX чітко розмежовує вбудовані утиліти на дві категорії з різною системною семантикою:

| Категорія | Список команд | Вплив синтаксичної помилки | Вплив змін середовища |
| :--- | :--- | :--- | :--- |
| **Special Builtins** | `break`, `: `, `continue`, `.`, `eval`, `exec`, `exit`, `export`, `readonly`, `return`, `set`, `shift`, `times`, `trap`, `unset` | **Примусово завершує** всю неінтерактивну оболонку (скрипт падає). | Присвоєння змінних перед командою (`VAR=val exec ...`) **залишаються** у середовищі оболонки назавжди. |
| **Regular Builtins** | `alias`, `bg`, `cd`, `command`, `false`, `fc`, `fg`, `getopts`, `hash`, `jobs`, `kill`, `pwd`, `read`, `test`, `true`, `type`, `ulimit`, `umask`, `unalias`, `wait` | Повертає ненульовий код `$?`, але **не перериває** скрипт. | Присвоєння змінних перед командою (`VAR=val cd ...`) діють **тільки на час виконання** цієї команди. |

### Обробка сигналів та вбудована команда trap

Вбудована команда `trap` реєструє обробники асинхронних подій ОС:

| Формат команди | Призначення та системна поведінка |
| :--- | :--- |
| `trap 'action' SIGNAL...` | Реєструє виконання рядка `action` при отриманні одного з перелічених сигналів. |
| `trap - SIGNAL...` | Скидає обробник сигналу до стандартної системної поведінки за умовчанням (`SIG_DFL`). |
| `trap '' SIGNAL...` | Налаштовує ігнорування сигналу (`SIG_IGN`). Сигнал блокується і не доходить до оболонки. |
| `trap 'action' EXIT` | Псевдо-сигнал `0` (`EXIT`): виконується гарантовано при виході з оболонки (нормальному чи через `exit`). |
| `trap 'action' ERR` | Псевдо-сигнал `ERR` (bash/zsh): спрацьовує кожного разу, коли команда повертає `$? != 0`. |

## 7. Внутрішні структури AST та архітектура синтаксичних дерев

Сучасні оболонки реалізують один із двох підходів до синтаксичного розбору:
- **Генератори парсерів LALR(1) / Bison (`bash`):** Використовують формальну Yacc-граматику зі складними зворотними викликами лексера (lexical feedback) для розрізнення контексту зарезервованих слів та Here-документів.
- **Ручний рекурсивний спуск (Recursive Descent — `dash`, `zsh`, `ksh93`):** Будують дерево розбору безпосередньо взаємно-рекурсивними функціями, що забезпечує мінімальний розмір двійкового файлу та максимальну швидкість парсингу.

Нижче наведено репрезентацію вузлів абстрактного синтаксичного дерева (AST), що використовуються в ядрах сучасних командних інтерпретаторів:

```c
#include <sys/types.h>

/* Типи вузлів синтаксичного дерева */
enum node_type {
    NODE_COMMAND,    /* Проста команда */
    NODE_PIPELINE,   /* Конвеєр (|) */
    NODE_AND_OR,     /* Логічний оператор (&&, ||) */
    NODE_SUBSHELL,   /* Блок під-оболонки ( () ) */
    NODE_IF,         /* Умовний оператор if/then/else */
    NODE_FOR,        /* Цикл for */
    NODE_WHILE       /* Цикл while/until */
};

/* Опис перенаправлення */
struct redirect {
    int src_fd;              /* Цільовий FD (наприклад, 2 для 2>&1) */
    int dup_fd;              /* Джерельний FD для дублювання, або -1 */
    int flags;               /* Прапорці open(): O_RDONLY, O_WRONLY тощо */
    char *filename;          /* Шлях до файлу або Here-doc буфер */
    struct redirect *next;   /* Наступне перенаправлення у списку */
};

/* Спільний заголовок усіх вузлів AST */
struct ast_node {
    enum node_type type;
};

/* Вузол простої команди */
struct cmd_node {
    enum node_type type;     /* NODE_COMMAND */
    int argc;                /* Кількість слів-аргументів */
    char **argv;             /* Масив аргументів [cmd, arg1, NULL] */
    struct redirect *redirs; /* Зв'язний список перенаправлень */
};

/* Вузол конвеєра */
struct pipe_node {
    enum node_type type;     /* NODE_PIPELINE */
    int cmd_count;           /* Кількість команд у конвеєрі */
    struct ast_node **cmds;  /* Масив дочірніх вузлів */
    int is_background;       /* Прапорець фонового виконання (&) */
};

/* Вузол бінарного логічного оператора */
struct and_or_node {
    enum node_type type;     /* NODE_AND_OR */
    int is_or;               /* 0 для &&, 1 для || */
    struct ast_node *left;   /* Лівий операнд */
    struct ast_node *right;  /* Правий операнд */
};

/* Вузол умовного оператора if */
struct if_node {
    enum node_type type;     /* NODE_IF */
    struct ast_node *test;   /* Умова (блок після if) */
    struct ast_node *then_b; /* Блок then */
    struct ast_node *else_b; /* Блок else/elif (або NULL) */
};
```

### Управління пам'яттю AST та відновлення після помилок

Реальні оболонки (`dash`, `bash`) використовують арени виділення пам'яті (Region-Based Memory Management / Arena Allocator):
- Усі вузли AST, рядки та списки перенаправлень виділяються у тимчасовому пулі пам'яті поточного циклу REPL.
- При виявленні синтаксичної помилки або отриманні сигналу переривання парсер викликає `siglongjmp()`, миттєво відкочуючи стек виконання.
- Вся виділена для AST пам'ять звільняється одним викликом скидання покажчика пулу арени `arena_reset()`, що повністю усуває небезпеку витоку пам'яті без потреби індивідуального обходу вузлів через `free()`.

## 8. Коди виходу та статуси завершення (IEEE Std 1003.1 §2.8)

Код виходу процесу є 8-бітним беззнаковим цілим числом у діапазоні `0..255`, збереженим у системній змінній `$?`. Ядро Linux формує статус у системному виклику `waitpid(pid, &status, 0)`:

| Статус `$?` | Категорія завершення | Джерело та семантика |
| :--- | :--- | :--- |
| `0` | Успіх (Success / True) | Процес викликав `exit(0)` або повернув `0` з `main()`. |
| `1 .. 125` | Помилка програми | Визначається самою утилітою (наприклад, `grep` не знайшов збігу -> `1`). |
| `126` | Відмова у доступі (`EACCES`) | Команду знайдено в `PATH`, але файл **не має прав на виконання** або є каталогом. |
| `127` | Файл не знайдено (`ENOENT`) | Команду **не знайдено** у жодному з каталогів `$PATH` або відсутній динамічний лінкер ELF. |
| `128 + N` | Аварійне завершення сигналом | Процес вбито сигналом ядра з номером `N`. Обчислюється як `128 + WTERMSIG(status)`. |

### Стандартні коди завершення за сигналами (128 + N)

- `130` (`128 + 2`): Процес перервано користувачем сигналом `SIGINT` (`Ctrl+C`).
- `137` (`128 + 9`): Процес негайно знищено ядром через сигнал `SIGKILL` (Out-Of-Memory Killer або `kill -9`).
- `141` (`128 + 13`): Сигнал зламаного каналу `SIGPIPE` (спроба запису в конвеєр, читач якого вже закрив дескриптор).
- `143` (`128 + 15`): Процес завершено сигналом `SIGTERM` (штатний запит на зупинку від `systemd`, `init` або `kill`).
