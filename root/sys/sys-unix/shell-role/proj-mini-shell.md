# ⚙️ Мінімальний оркестратор процесів: реалізація ядра REPL мовами C та C++

Командна оболонка функціонує як користувацький оркестратор процесів та компілятор потоків даних: вона перетворює текстовий рядок користувача на граф процесів операційної системи, об'єднаних неіменованими каналами передачі байтів. Для реалізації такого ядра потрібна скоординована взаємодія системних викликів створення процесів (`fork`), заміни образу виконуваного коду (`execvp`), маніпуляції таблицею файлових дескрипторів (`pipe`, `dup2`, `close`), синхронізації життєвого циклу (`waitpid`) та розмежування прав на керування терміналом між групами процесів.

Нижче наведено паралельну реалізацію міні-оболонки мовами POSIX C та ідіоматичним C++20 з RAII-ізоляцією системних ресурсів.

## 1. Архітектура та структура ядра міні-оболонки

Ядро інтерактивної оболонки працює у нескінченному циклі REPL (Read-Eval-Print Loop). Цей цикл забезпечує повний життєвий цикл обробки користувацького введення:

```
                  ┌────────────────────────────────────────┐
                  │          Користувацьке введення         │
                  └───────────────────┬────────────────────┘
                                      │
                                      ▼
                        ┌───────────────────────────┐
                        │ Read (Читання та парсинг)  │
                        └─────────────┬─────────────┘
                                      │
                         Розбиття на токени та пошук '|'
                                      │
                                      ▼
                        ┌───────────────────────────┐
                        │   Eval (Оркестрація)      │
                        └─────────────┬─────────────┘
                                      │
                 ┌────────────────────┴────────────────────┐
                 ▼                                         ▼
     ┌───────────────────────┐                 ┌───────────────────────┐
     │  Вбудована команда    │                 │   Зовнішня команда    │
     │     (cd, exit)        │                 │    (fork + execvp)    │
     └───────────┬───────────┘                 └───────────┬───────────┘
                 │                                         │
        Виконання у батьку                     Створення каналів та нащадків
                 │                                         │
                 │                                         ▼
                 │                             ┌───────────────────────┐
                 │                             │   Wait (Синхронізація)│
                 │                             └───────────┬───────────┘
                 │                                         │
                 │                               waitpid() та збір $?
                 │                                         │
                 └────────────────────┬────────────────────┘
                                      │
                                      ▼
                        ┌───────────────────────────┐
                        │ Loop (Наступна ітерація)  │
                        └───────────────────────────┘
```

1. **Read (Читання та лексичний розбір):** Оболонка виводить запрошення командного рядка `mini-shell> ` і вичитує буфер введення через `fgets()` (у C) або `std::getline()` (у C++). Рядок сканується на наявність метасимволу конвеєра `|`.
   - У C-реалізації рядок модифікується на місці: символ `|` замінюється нульовим байтом `\0`, що ділить первинний буфер на два ізольовані C-рядки (ліву та праву команди). Далі функція `strtok()` розбиває кожну частину на масив покажчиків `char* args[]` за роздільниками пробілів та табуляцій.
   - У C++ реалізації використовується потоковий парсинг через `std::istringstream` та виділення підрядків `std::string_view` / `substr()`, що гарантує відсутність руйнівної мутації та безпеку роботи з динамічними рядками `std::string`.
2. **Eval (Диспетчеризація та виконання):**
   - **Порожнє введення:** якщо користувач натиснув лише `Enter`, оболонка негайно переходить до наступної ітерації циклу.
   - **Вбудовані команди (Builtins):** команди `cd` та `exit` перехоплюються до створення будь-яких нащадків і виконуються безпосередньо у батьківському процесі.
   - **Одиночна зовнішня команда:** створюється один дочірній процес via `fork()`, який заміщує свою пам'ять утилітою через `execvp()`.
   - **Конвеєр із двох команд (`cmd1 | cmd2`):** оболонка створює неіменований канал ядра `pipe()`, після чого здійснює два послідовні виклики `fork()`. Перший нащадок спрямовує свій стандартний вивід у канал, другий — читає стандартне введення з каналу.
3. **Wait (Синхронізація та очищення дескрипторів):** Батьківський процес закриває власні дескриптори каналу і блокується на викликах `waitpid()`, очікуючи на завершення дочірніх процесів та забираючи їхні коди повернення з таблиці процесів ядра.

## 3. Життєвий цикл процесу: низькорівнева механіка fork(2), execvp(3) та waitpid(2)

Створення та виконання програм в операційних системах сімейства POSIX навмисно розділено на два незалежні системні виклики: клонування існуючого процесу (`fork`) та завантаження нового бінарного образу в адресний простір (`execve`/`execvp`).

```
Батьківський процес (Shell)
       │
       ├────► fork() ─────────────────────────────┐
       │      Повертає PID нащадка                │  Повертає 0
       │                                          ▼
       │                             Дочірній процес (Child)
       │                                    │
       │                                    ├────► dup2() / close()
       │                                    │      (налаштування FD 0, 1, 2)
       │                                    │
       │                                    ├────► execvp("grep", args)
       │                                    │      (заміна образу пам'яті ELF)
       │                                    ▼
       ├────► waitpid(pid, &status, ...)    Нова програма виконується
       │      (блокування батька)                  │
       │                                           ▼
       │                             exit(code) або смерть від сигналу
       │                                           │
       ▼                                           ▼
Батько прокидається, ◄────────────── Стан EXIT_ZOMBIE (task_struct)
зчитує статус завершення
та очищає запис у таблиці процесів
```

### Клонування через fork(2)
Системний виклик `fork()` створює точну копію викликаючого процесу. Ядро Linux дублює структуру дескриптора процесу `task_struct`, виділяючи для нащадка новий унікальний числовий ідентифікатор PID.

- **Оптимізація Copy-on-Write (CoW):** Ядро не копіює всю фізичну оперативну пам'ять батька в момент виклику `fork()`. Замість цього воно дублює таблиці сторінок пам'яті (Page Tables) і позначає всі сторінки як доступні лише для читання (Read-Only). Фізичне копіювання окремої сторінки розміром 4 КіБ відбувається апаратно через переривання сторінкового збою (Page Fault) лише тоді, коли один із процесів намагається виконати операцію запису в цю сторінку. Оскільки дочірній процес оболонки майже відразу викликає `execvp()`, витрати на копіювання пам'яті практично дорівнюють нулю.
- **Успадкування таблиці файлових дескрипторів:** Дочірній процес отримує точну копію масиву дескрипторів батька. Дескриптори в обох процесах вказують на ті самі системні структури відкритих файлів `struct file` у VFS ядра. Лічильник посилань `f_count` для кожного відкритого файла інкрементується на 1.
- **Успадкування контексту:** Дочірній процес успадковує поточний робочий каталог (CWD), маску створення файлів `umask`, змінні середовища `environ` та встановлені маски сигналів `sigprocmask`.

### Заміна образу через execvp(3)
Функція `execvp(const char *file, char *const argv[])` є обгорткою бібліотеки C над базовим системним викликом `execve(2)`.

- **Повне оновлення адресного простору:** Ядро знищує старий адресний простір дочірнього процесу (сегменти коду `.text`, ініціалізованих даних `.data`, неініціалізованих змінних `.bss`, купу та стек). На їхнє місце завантажуються секції виконуваного бінарного файлу формату ELF (Executable and Linkable Format), налаштовується новий стек із переданими аргументами `argv` та змінними середовища `envp`, а покажчик інструкцій процесора встановлюється на точку входу програми `_start`.
- **Збереження файлових дескрипторів:** Дескриптори, які були відкриті до виклику `execvp()`, залишаються відкритими і в новому виконуваному образі (якщо для них не було явно встановлено прапорець `FD_CLOEXEC` через `fcntl` або `O_CLOEXEC` при відкритті). Саме ця властивість дозволяє оболонці налаштувати введення-виведення через `dup2()` до виклику `execvp()`, завдяки чому новостворена програма прозоро читає або пише у сконфігуровані канали.
- **Пошук за змінною PATH:** Префікс `p` у назві `execvp` означає автоматичний обхід каталогів, зазначених у змінній середовища `PATH` (наприклад, `/usr/bin:/bin`). Функція послідовно пробує сформувати шлях `/usr/bin/cmd`, `/bin/cmd` і викликати `execve`. Якщо шлях містить символ слеша `/` (наприклад, `./my_prog` або `/bin/ls`), пошук за `PATH` не виконується, а файл відкривається безпосередньо.
- **Поведінка при помилці:** У разі успішного завантаження образу `execvp()` ніколи не повертає керування, оскільки коду, який його викликав, більше не існує в пам'яті. Повернення значення `-1` відбувається виключно у разі фатальної помилки:
  - `ENOENT` — файл команди не знайдено в жодному з каталогів `PATH`.
  - `EACCES` — відсутні права на виконання бінарного файлу або права на читання каталогу.
  - `ENOEXEC` — файл має права виконання, але не є ELF-бінарником і не містить валідного shebang-рядка `#!/bin/sh`.
  
  У разі невдачі `execvp()` дочірній процес оболонки зобов'язаний негайно викликати системний виклик `_exit(127)` або `exit(127)`, щоб запобігти паралельному виконанню коду батьківської оболонки двома процесами.

### Синхронізація та інспекція статусів через waitpid(2)
Системний виклик `waitpid(pid_t pid, int *status, int options)` призупиняє виконання батьківського процесу до зміни стану цільового нащадка.

- **Анатомія зомбі-процесів (Zombie / defunct):** Коли дочірній процес завершує своє виконання via `exit(code)`, ядро негайно звільняє всі зайняті ним сторінки пам'яті, закриває відкриті файлові дескриптори та звільняє системні ресурси. Проте сам дескриптор процесу `task_struct` не видаляється з таблиці процесів ядра. Процес переходить у термінальний стан `EXIT_ZOMBIE` (`defunct`). Ядро зберігає запис про нього лише для того, щоб батьківський процес міг прочитати код виходу через `waitpid()`. Якщо батьківська оболонка ніколи не викликає `waitpid()`, зомбі-процеси накопичуються в пам'яті ядра, що зрештою призводить до вичерпання таблиці PID (PID exhaustion) і неможливості створити будь-який новий процес у системі.
- **Розкодування статусу завершення:** Змінна `status`, яку заповнює ядро, є бітовою маскою, для аналізу якої стандарт POSIX надає обов'язкові макроси:
  - `WIFEXITED(status)` — повертає істину, якщо процес завершився штатно (через `exit()` або `return` з функції `main`).
  - `WEXITSTATUS(status)` — видобуває молодші 8 біт коду виходу (значення `0..255`), переданого у виклик `exit(code)`.
  - `WIFSIGNALED(status)` — повертає істину, якщо процес було аварійно вбито необробленим сигналом операційної системи (наприклад, `SIGKILL` або `SIGSEGV`).
  - `WTERMSIG(status)` — повертає числовий номер сигналу, який спричинив загибель процесу.
  - `WIFSTOPPED(status)` — повертає істину, якщо дочірній процес не загинув, а був тимчасово призупинений сигналом зупинки (`SIGTSTP`, `SIGSTOP`, `SIGTTIN`, `SIGTTOU`).
  - `WSTOPSIG(status)` — повертає номер сигналу, який призупинив процес.
  - `WIFCONTINUED(status)` — повертає істину, якщо процес відновив виконання після отримання сигналу `SIGCONT`.
- **Прапорці керування очікуванням:**
  - `0` — блокуюче очікування остаточного завершення нащадка.
  - `WUNTRACED` — змушує `waitpid()` негайно розблокуватися і повернути статус, якщо дочірній процес було зупинено сигналами керування завданнями (`Ctrl+Z` / `SIGTSTP`). Без цього прапорця `waitpid()` продовжував би блокувати оболонку, імітуючи зависання.
  - `WCONTINUED` — змушує `waitpid()` повернути статус, якщо зупинений процес було відновлено у фоні через `kill -CONT <PID>`.
  - `WNOHANG` — неблокуючий режим: `waitpid()` повертає `0`, якщо стан нащадка ще не змінився. Застосовується в інтерактивних оболонках для асинхронного збору статусів фонових завдань перед виведенням чергового запрошення командного рядка.

## 4. Взаємодія з терміналом, групами процесів та сигналами

У наївній реалізації оболонки натискання комбінації клавіш `Ctrl+C` у терміналі призводить до одночасного аварійного завершення як запущеної користувацької програми, так і самого процесу оболонки. Це відбувається через специфіку доставки термінальних сигналів ядра.

```
                            Термінал (/dev/pts/X)
                                      │
                     Натискання клавіш Ctrl+C (0x03)
                                      │
                                      ▼
                        Драйвер лінії (Line Discipline)
                                      │
                   Надсилання SIGINT передньоплановій групі
                                      │
                 ┌────────────────────┴────────────────────┐
                 ▼                                         ▼
   ┌───────────────────────────┐             ┌───────────────────────────┐
   │ Нащадок (cmd, PGID = 200) │             │  Оболонка (PGID = 100)    │
   │      Foreground Group     │             │     Background Group      │
   └─────────────┬─────────────┘             └─────────────┬─────────────┘
                 │                                         │
        Отримує SIGINT                            Ігнорує сигнал
        і завершує роботу                         і зберігає працездатність
```

### Сегрегація груп процесів via setpgid(2)
Кожен процес у системі належить до певної групи процесів (Process Group), що ідентифікується числом PGID (Process Group ID). Драйвер термінала зв'язується з однією конкретною групою — передньоплановою (Foreground Process Group).

Коли користувач натискає `Ctrl+C` (байт `0x03`, `ETX`) або `Ctrl+Z` (байт `0x1A`, `SUB`), термінальний драйвер ядра генерує відповідні сигнали `SIGINT` або `SIGTSTP` і розсилає їх **усім процесам передньопланової групи**.

Щоб захистити оболонку від знищення:
1. Батьківська оболонка виносить запущений дочірній процес (або всі процеси конвеєра) в окрему нову групу процесів via `setpgid(pid, pgid)`. Зазвичай як PGID передається PID першого процесу конвеєра (`setpgid(pid, pid)`).
2. **Усунення стану гонки (Race Condition):** Системний виклик `setpgid()` має викликатися двічі:
   - у дочірньому процесі після `fork()`, але перед викликом `execvp()`;
   - у батьківському процесі одразу після повернення з `fork()`.
   
   Подвійний виклик усуває стан гонки планувальника ядра: якщо батьківський процес спробує передати термінал групі нащадка via `tcsetpgrp()`, або нащадок виконає `execvp()` до того, як батько налаштує групу, операційна система поверне помилку неіснуючого PGID (`EPERM` / `ESRCH`).

### Передача керування терміналом via tcsetpgrp(3)
Після виділення нащадка в окрему групу оболонка передає йому монопольне володіння терміналом:

```
/* Передача терміналу дочірній групі процесів */
tcsetpgrp(STDIN_FILENO, child_pgid);
```

Тепер натискання будь-яких керуючих комбінацій клавіш транслюється ядром виключно нащадкам. Після того, як дочірня група завершує роботу або призупиняється, батьківська оболонка повертає термінал собі:

```
/* Повернення терміналу батьківській оболонці */
tcsetpgrp(STDIN_FILENO, getpgrp());
```

### Маскування та успадкування сигналів
Під час ініціалізації інтерактивна оболонка зобов'язана змінити диспозицію критичних сигналів через системний виклик `sigaction(2)` або `signal(2)`:

- `signal(SIGINT, SIG_IGN)` та `signal(SIGQUIT, SIG_IGN)` — запобігають перериванню циклу REPL оболонки.
- `signal(SIGTSTP, SIG_IGN)` — захищає оболонку від зупинки при спробі призупинити команду.
- `signal(SIGTTIN, SIG_IGN)` та `signal(SIGTTOU, SIG_IGN)` — **критично важливе налаштування**. Коли фоновий процес намагається записати дані в термінал або змінити конфігурацію термінала via `tcsetpgrp()`, ядро надсилає його групі сигнал `SIGTTOU`. Якщо оболонка не ігноруватиме `SIGTTOU`, виклик `tcsetpgrp()` негайно призупинить саму оболонку.

**Відновлення у нащадках:** Успадковані обробники сигналів, налаштовані як `SIG_IGN`, залишаються проігнорованими навіть після завантаження нового бінарника через `execvp()`. Тому дочірній процес у проміжку між `fork()` та `execvp()` зобов'язаний явно скинути обробники `SIGINT`, `SIGQUIT`, `SIGTSTP`, `SIGTTIN`, `SIGTTOU` у стан за замовчуванням `SIG_DFL`, інакше запущена утиліта (наприклад, текстовий редактор або тривалий скрипт) не зможе реагувати на переривання користувача.

## 5. Механіка асинхронного конвеєра: буферизація ядра, dup2 та життєвий цикл каналів

Конвеєр (pipeline) у Unix — це ланцюг процесів, з'єднаних неіменованими каналами ядра (pipes), де стандартний вивід попереднього процесу стає стандартним введенням наступного.

```
       ┌─────────────────────────┐               ┌─────────────────────────┐
       │   Дочірній процес 1     │               │   Дочірній процес 2     │
       │       (cmd1)            │               │       (cmd2)            │
       │                         │               │                         │
       │  STDOUT (FD 1) ─────────┼───────┐       │                         │
       └─────────────────────────┘       │       │  STDIN (FD 0) ◄─────────┼───────┐
                                         │       └─────────────────────────┘       │
                                         ▼                                         │
                         ┌───────────────────────────────┐                         │
                         │       Канал ядра (Pipe)       │                         │
                         │ ┌───────────────────────────┐ │                         │
                         │ │ Буфер кільцевої черги VFS │ │                         │
                         │ │ (місткість 64 КіБ ядра)   │ │                         │
                         │ └───────────────────────────┘ │                         │
                         │  pipefd[1]         pipefd[0]  │                         │
                         │ (Вхід запису)     (Вихід для) ├─────────────────────────┘
                         └───────▲──────────── читання) ─┘
                                 │
                 Батьківський процес закриває
                 обидва дескриптори pipefd[0]
                 та pipefd[1] у своєму просторі!
```

### Створення каналу via pipe(2)
Системний виклик `pipe(int pipefd[2])` запитує у ядра створення односпрямованого каналу передачі даних:
- `pipefd[0]` — файловий дескриптор, відкритий виключно для читання (Read End).
- `pipefd[1]` — файловий дескриптор, відкритий виключно для запису (Write End).

У ядрі Linux канал реалізовано як кільцевий буфер сторінок пам'яті у віртуальній файловій системі `pipefs`. За замовчуванням місткість буфера становить 65 536 байтів (16 сторінок по 4 КіБ). Константа `PIPE_BUF` (4096 байтів у Linux) гарантує, що записи розміром до 4 КіБ виконуються ядром атомарно: байти від різних процесів-письменників не перемішуються між собою.

### Комутація дескрипторів через dup2(2)
Системний виклик `dup2(int oldfd, int newfd)` атомарно призначає дескриптору `newfd` вказівник на той самий відкритий системний файл, що й у `oldfd`. Якщо `newfd` уже був відкритий (наприклад, `STDOUT_FILENO` = 1 вказував на термінал), ядро безпечно закриває його і здійснює заміну за одну неподільну операцію.

Для організації конвеєра `cmd1 | cmd2`:
1. У першому дочірньому процесі (`cmd1`):
   ```
   dup2(pipefd[1], STDOUT_FILENO); /* FD 1 тепер пише у канал */
   close(pipefd[0]);               /* Закриваємо невикористовуваний читач */
   close(pipefd[1]);               /* Закриваємо дублікат дескриптора запису */
   ```
2. У другому дочірньому процесі (`cmd2`):
   ```
   dup2(pipefd[0], STDIN_FILENO);  /* FD 0 тепер читає з каналу */
   close(pipefd[0]);               /* Закриваємо дублікат дескриптора читання */
   close(pipefd[1]);               /* Закриваємо невикористовуваний дескриптор запису */
   ```

### Небезпека висячих дескрипторів запису (Dangling Write Ends)
Після успішного створення обох нащадків батьківська оболонка зобов'язана негайно виконати:
```
close(pipefd[0]);
close(pipefd[1]);
```

Якщо батьківський процес забуде закрити дескриптор `pipefd[1]`, лічильник посилань ядра `f_count` на кінець запису каналу залишатиметься рівним щонайменше `1` (одне посилання тримає батько). 

Коли процес `cmd1` повністю завершить свою роботу і закриє свій `stdout`, процес `cmd2` вичитає всі залишки даних із кільцевого буфера. Наступний системний виклик `read(STDIN_FILENO, buf, count)` не поверне значення `0` (EOF), оскільки з точки зору ядра в системі все ще існує відкритий дескриптор запису в цей канал (у батьківській оболонці). У результаті процес `cmd2` назавжди зависне у стані очікування читання з порожнього каналу (`TASK_INTERRUPTIBLE`), а конвеєр заблокує всю оболонку.

Аналогічно, якщо сам процес `cmd2` не закриє свою копію `pipefd[1]`, він сам для себе виступатиме відкритим письменником і ніколи не отримає EOF.

### Зламаний канал (Broken Pipe) та сигнал SIGPIPE
Якщо процес-читач `cmd2` аварійно падає або завершується раніше, ніж процес-письменник `cmd1` встигає згенерувати всі дані (класичний приклад — команда `yes | head -n 5`, де `head` закриває `stdin` після вичитування 5 рядків), канал стає «зламаним» (Broken Pipe).

Коли `cmd1` намагається виконати системний виклик `write(STDOUT_FILENO, data, len)` у канал, де лічильник активних читачів дорівнює нулю:
1. Ядро генерує і надсилає процесу `cmd1` сигнал `SIGPIPE`.
2. За замовчуванням дія сигналу `SIGPIPE` — негайне завершення процесу. Це запобігає марному навантаженню процесора програмами, результати роботи яких більше нікому читати.
3. Якщо програма перехоплює або ігнорує `SIGPIPE` (`signal(SIGPIPE, SIG_IGN)`), системний виклик `write()` повертає помилку `-1`, а системна змінна `errno` встановлюється у значення `EPIPE`.

## 6. Ідіоматичні відмінності: захист ресурсів у C++ за допомогою RAII

У традиційній реалізації мовою C будь-яка помилка системного виклику (наприклад, невдача другого `fork()` або помилка парсингу аргументів) вимагає ретельного ручного закриття дескрипторів та очищення динамічної пам'яті через розгалужені ланцюги переходів `goto cleanup;`.

У C++ реалізації оркестратора застосовано патерн RAII (Resource Acquisition Is Initialization), який гарантує детерміноване вивільнення системних ресурсів ядра на рівні мовних інваріантів:

```
Життєвий цикл UniqueFd:

Створення:
  UniqueFd fd{pipe_raw[1]}; ──► Володіння файловим дескриптором ядра Linux
                                    │
                                    ├─── Копіювання заборонено: operator=(const UniqueFd&) = delete
                                    │
                                    ├─── Переміщення: UniqueFd other = std::move(fd);
                                    │    (старий об'єкт скидається в -1, володіння переходить)
                                    │
Вихід з області видимості:          ▼
  { ... }                   ──► ~UniqueFd() автоматично викликає ::close(fd_)
                                (навіть при генерації винятків або return)
```

### Анатомія класу UniqueFd
Клас `UniqueFd` інкапсулює цілочисельний дескриптор POSIX і реалізує такі гарантії:
1. **Заборона копіювання (No Copying):** Конструктор копіювання та оператор присвоєння копіюванням видалені (`= delete`). Це унеможливлює випадкове створення двох об'єктів з одним числовим номером дескриптора, що призвело б до фатальної системної помилки подвійного закриття (`double close hazard`).
2. **Семантика переміщення (Move Semantics):** Конструктор та оператор переміщення передають володіння дескриптором новому об'єкту, скидаючи внутрішній дескриптор донора у безпечне недійсне значення `-1`.
3. **Детермінований деструктор:** Деструктор `~UniqueFd()` викликає системний виклик `::close(fd_)` лише у випадку, якщо `fd_ >= 0`. Це забезпечує виняткову безпеку (Exception Safety): дескриптор буде гарантовано закрито ядром при будь-якому розкручуванні стека (Stack Unwinding).
4. **Метод release():** Дозволяє явно відмовитися від володіння ресурсом (наприклад, після виклику `dup2()` або перед `execvp()`), не виконуючи операцію `close()`.

### Безпечна конвертація аргументів через ExecArgs
Системний виклик `execvp()` вимагає як аргумент масив покажчиків типу `char* const*`, завершений покажчиком `NULL`. Зберігання аргументів у вигляді сучасних контейнерів `std::vector<std::string>` забезпечує автоматичне керування динамічною пам'яттю, але не є безпосередньо сумісним з C ABI.

Допоміжний клас `ExecArgs` будує плаский вектор сумісних покажчиків `std::vector<char*>`, надійно фіксуючи завершальний `nullptr`. Оскільки вектор покажчиків посилається на незмінні внутрішні буфери `c_str()` вхідного вектора рядків, створення масиву аргументів виконується за один прохід без дублювання текстових даних у пам'яті.

## 7. Інспекція роботи оркестратора в Linux: procfs та системні трасування

Роботу створеного міні-оркестратора можна перевірити та провалідувати за допомогою стандартних інструментів системного аналізу Linux.

### Перевірка топології процесів через pstree
Якщо під час виконання тривалого конвеєра (наприклад, `cat /dev/urandom | base64`) в іншому терміналі виконати утиліту `pstree`, можна побачити сформовану ієрархію процесів:

```bash
pstree -p $(pgrep mini_shell)
```

Вивід демонструє, що обидва процеси конвеєра є прямими нащадками оболонки і функціонують паралельно:
```
mini_shell(14230)─┬─cat(14231)
                  └─base64(14232)
```

### Інспекція файлових дескрипторів у /proc/PID/fd
Зазирнувши у віртуальну файлову систему `procfs` для кожного з дочірніх процесів, можна наочно перевірити комутацію потоків:

```bash
ls -l /proc/14231/fd /proc/14232/fd
```

```
/proc/14231/fd: (cat)
lrwx------ 1 user user 64 0 -> /dev/pts/2
l-wx------ 1 user user 64 1 -> pipe:[894125]
lrwx------ 1 user user 64 2 -> /dev/pts/2

/proc/14232/fd: (base64)
lr-x------ 1 user user 64 0 -> pipe:[894125]
lrwx------ 1 user user 64 1 -> /dev/pts/2
lrwx------ 1 user user 64 2 -> /dev/pts/2
```

Числовий ідентифікатор `pipe:[894125]` показує, що стандартний вивід першого процесу (FD 1) та стандартне введення другого процесу (FD 0) вказують на один і той самий анонімний inode каналу ядра.

### Трасування системних викликів через strace
Запуск оболонки під трасувальником `strace` дозволяє відстежити точну послідовність викликів ядра під час оркестрації конвеєра:

```bash
strace -f -e trace=clone,fork,execve,pipe,pipe2,dup2,close,wait4 ./mini_shell
```

Послідовність подій у лозі трасувальника відображає системний алгоритм:
1. `pipe2([3, 4], 0) = 0` — ядро виділяє пару дескрипторів каналу (FD 3 для читання, FD 4 для запису).
2. `clone(...) = 14231` — створення першого дочірнього процесу.
3. `[pid 14231] dup2(4, 1) = 1` — перший нащадок перенаправляє FD 4 на `stdout`.
4. `[pid 14231] close(3) = 0; close(4) = 0` — закриття оригінальних дескрипторів каналу в нащадку.
5. `[pid 14231] execve("/usr/bin/cat", ...)` — заміна образу першого нащадка.
6. `clone(...) = 14232` — створення другого дочірнього процесу.
7. `[pid 14232] dup2(3, 0) = 0` — другий нащадок перенаправляє FD 3 на `stdin`.
8. `[pid 14232] close(3) = 0; close(4) = 0` — закриття дескрипторів каналу в другому нащадку.
9. `[pid 14232] execve("/usr/bin/base64", ...)` — заміна образу другого нащадка.
10. `close(3) = 0; close(4) = 0` — **батьківський процес закриває свої копії дескрипторів каналу**.
11. `wait4(14231, ...) = 14231` та `wait4(14232, ...) = 14232` — батьківський процес синхронізується з обома процесами конвеєра.
