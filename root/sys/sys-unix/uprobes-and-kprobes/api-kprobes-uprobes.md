# 📋 Інтерфейс kprobes та uprobes: C API, tracefs та eBPF

Цей довідник містить повний опис низькорівневого інтерфейсу програмної інструментації Linux: структури даних ядра, системні функції реєстрації, формат псевдофайлової системи `tracefs` та макроси бібліотеки `libbpf` для створення eBPF-зондів.

## 1. Системний C API ядра (Kernel Programmatic Interface)

Програмний інтерфейс ядра використовується при розробці модулів ядра Linux, які вимагають прямого доступу до регістрів процесора та контексту виконання без проміжного шару eBPF. Для роботи з зондами підключаються заголовкові файли `<linux/kprobes.h>` та `<linux/ptrace.h>`.

### Внутрішня структура `struct kprobe`

Головною структурою даних, яка описує один зонд у ядрі, є `struct kprobe`. Вона містить як конфігураційні параметри, вказані розробником, так і службові поля ядра для керування списком зондів та збереження оригінального машинного коду:

:::code api-kprobes-uprobes/c/vnutrishnia-struktura.c

Поле `symbol_name` дозволяє вказувати функцію за її експортованим ім'ям у ядрі. Якщо назва вказана, ядро під час реєстрації самостійно виконує пошук віртуальної адреси через підсистему `kallsyms`. Якщо розробник знає точну адресу в пам'яті, вона передається через поле `addr`, а `symbol_name` залишається `NULL`. Поле `offset` використовується для вставки зонда не на початок функції, а на конкретну інструкцію всередині її тіла.

Поле `ainsn` (architecture-specific instruction) містить архітектурно-залежний буфер OOL-виконання. Для x86_64 це структура `struct arch_specific_insn`, що містить скопійовані байти інструкції та відкориговані зміщення для відносної адресації `RIP`. Поле `flags` зберігає внутрішній стан зонду, наприклад прапорець `KPROBE_FLAG_DISABLED` (зонд деактивовано) або `KPROBE_FLAG_OPTIMIZED` (зонд успішно оптимізовано через 5-байтовий `JMP`).

### Сигнатури обробників та робота з регістрами

Обробники зонду отримують вказівник на зареєстровану структуру `struct kprobe` та сохранені регістри процесора у вигляді структури `struct pt_regs`:

```c
/* Pre-handler отримує вказівник на зонд та збережені регістри процесора */
int pre_handler(struct kprobe *p, struct pt_regs *regs);

/* Post-handler отримує також прапорці стану інструкції */
void post_handler(struct kprobe *p, struct pt_regs *regs, unsigned long flags);
```

Функція `pre_handler` викликається безпосередньо перед тим, як процесор виконає інструкцію, на яку встановлено зонд. Якщо `pre_handler` повертає 0, ядро продовжує нормальний процес виконання (виконує оригінальну інструкцію з OOL-буфера). Якщо повертається ненульове значення, ядро пропускає виконання оригінальної інструкції. Це дозволяє розробникам ядра використовувати kprobes для модифікації потоку виконання або емуляції інструкцій.

Функція `post_handler` викликається одразу після того, як оригінальна інструкція виконана з OOL-буфера, але до того, як потік повернувся в основний код. Вона надає доступ до стану прапорців процесора `EFLAGS` та модифікованих регістрів після виконання інструкції.

### Функції реєстрації та скасування зондів

Для активації зондів у ядрі застосовуються функції системного API:

```c
/* Реєстрація одиночного kprobe. Повертає 0 при успіху або від'ємний код помилки */
int register_kprobe(struct kprobe *p);

/* Скасування реєстрації зонду та відновлення оригінального байта пам'яті */
void unregister_kprobe(struct kprobe *p);

/* Масова реєстрація масиву зондів для зменшення накладних витрат на блокування */
int register_kprobes(struct kprobe **kps, int num);
void unregister_kprobes(struct kprobe **kps, int num);
```

При виконанні `register_kprobe` ядро здійснює перевірку безпеки віртуальної адреси. Адреса не повинна належати до критичних обробників переривань або системних функцій трасування (відмічених макросом `NOKPROBE_SYMBOL`). Після перевірки ядро виділяє OOL-буфер, копіює оригінальну інструкцію та атомарно замінює перший байт коду на `0xCC` через внутрішню функцію `text_poke_bp()`.

### Структура `struct kretprobe`

Для перехоплення значень, що повертаються з функцій ядра, використовується розширена структура `struct kretprobe`:

:::code api-kprobes-uprobes/c/struktura-struct-kretprobe.c

Поле `maxactive` визначає, скільки примірників виклику функції може трасуватися одночасно в багатопотоковому середовищі. Якщо параметр `maxactive` встановлено у 0, ядро автоматично вибирає значення на основі кількості ядер процесора (`NR_CPUS`). Якщо кількість одночасних викликів перевищує `maxactive`, додаткові виклики ігноруються, а лічильник `nmissed` збільшується.

Поле `entry_handler` дозволяє зберегти довільний контекст у пам'яті примірника `kretprobe_instance` під час входу у функцію. Цей контекст зчитується в `handler` при виході з функції, що зручно для передачі мітки часу входу без використання глобальних хеш-карт.

## 2. Псевдофайловий інтерфейс `tracefs` (`/sys/kernel/tracing`)

Для швидкого створення та налаштування зондів без написання C-коду ядра Linux пропонує текстовий інтерфейс `tracefs`, змонтований у системі за адресою `/sys/kernel/tracing` (або `/sys/kernel/debug/tracing`).

### Синтаксис керування kprobe_events

Файл `/sys/kernel/tracing/kprobe_events` приймає рядочки команд для створення та видалення зондів ядра:

```text
p[:[GRP/]EVENT] [MOD:]SYM[+OFF]|MEMADDR [FETCHARGS]  - Встановлення kprobe
r[MAXACTIVE][:[GRP/]EVENT] [MOD:]SYM[+OFF] [FETCHARGS] - Встановлення kretprobe
-:[GRP/]EVENT                                         - Видалення зонду
```

Префікс `p` задає звичайний зонд входу (kprobe), префікс `r` задає зонд повернення (kretprobe). Вимоги до синтаксису:
- `GRP`: Назва групи подій (за замовчуванням `kprobes`).
- `EVENT`: Унікальне ім'я події, яке створить відповідну директорію у `/sys/kernel/tracing/events/GRP/EVENT`.
- `SYM`: Ім'я символу ядра або завантаженого модуля (наприклад, `vfs_read` або `ext4:ext4_file_write`).

Параметри `FETCHARGS` дозволяють зчитувати регістри процесора та локальні змінні пам'яті:
- `%REG`: Зчитування значення регістра CPU (наприклад, `%ax`, `%di`, `%si`, `%dx`).
- `+OFF(%REG)`: Дереференсинг вказівника зі зміщенням у байтах (наприклад, `+0(%si)`).
- `@ADDR`: Читання з абсолютної віртуальної адреси пам'яті.
- `STRING`: Інтерпретація вказівника як рядка з нульовим завершенням (`char *`).
- `u8`, `u16`, `u32`, `u64`, `s8`, `s16`, `s32`, `s64`: Явне приведення типів даних.

Приклади послідовного керування зондами з консолі bash:

:::code api-kprobes-uprobes/sh/syntaksys-keruvannia.sh

### Синтаксис керування uprobe_events

Файл `/sys/kernel/tracing/uprobe_events` використовується для динамічного створення зондів у просторі користувача:

```text
p[:[GRP/]EVENT] PATH:OFFSET [FETCHARGS]   - Встановлення uprobe
r[:[GRP/]EVENT] PATH:OFFSET [FETCHARGS]   - Встановлення uretprobe
```

Аргумент `PATH` вказує на абсолютний шлях до бінарного ELF-файла або спільної бібліотеки у файловій системі. Аргумент `OFFSET` задає 16-нсткове зміщення необхідної інструкції від початку файла на диску.

Приклади команд налаштування uprobes у bash:

:::code api-kprobes-uprobes/sh/syntaksys-keruvannia-2.sh

Після створення події у `uprobe_events` ядро створює унікальний ідентифікатор події у файлі `/sys/kernel/tracing/events/uprobes/libc_malloc/id`. Цей ID використовується низькорівневими системними викликами `perf_event_open()` для прив'язки eBPF-програм до створення трасувального контексту.

## 3. Інтерфейс eBPF та бібліотеки `libbpf`

Сучасний підхід до розробки систем спостережуваності покладається на бібліотеку `libbpf`, яка надає декларативні макроси та автоматично підключає BPF-програми до зондів.

### Декларативні макроси секцій `SEC()`

Файл eBPF-програми описує точки прикріплення за допомогою спеціальних макросів макетування секцій `SEC()`:

| Макрос секції | Опис призначення | Приклад використання |
| :--- | :--- | :--- |
| `SEC("kprobe/<sym>")` | Перехоплення входу у функцію ядра `<sym>` | `SEC("kprobe/do_sys_openat2")` |
| `SEC("kretprobe/<sym>")` | Перехоплення виходу з функції ядра `<sym>` | `SEC("kretprobe/do_sys_openat2")` |
| `SEC("uprobe/<path>:<off>")` | Вхід у функцію простору користувача | `SEC("uprobe/bash_readline")` |
| `SEC("uretprobe/<path>:<off>")` | Вихід з функції простору користувача | `SEC("uretprobe/bash_readline")` |
| `SEC("fentry/<sym>")` | Оптимізований вхід (fprobe/ftrace, Linux 5.5+) | `SEC("fentry/do_sys_openat2")` |
| `SEC("fexit/<sym>")` | Оптимізований вихід (fprobe/ftrace, Linux 5.5+) | `SEC("fexit/do_sys_openat2")` |

### Допоміжні BPF-функції читання пам'яті та регістрів

Оскільки BPF-програма виконується в ізольованому середовищі ядра, вона не може напряму роздереференсити довільний вказівник. Для безпечного читання пам'яті застосовуються спеціальні функції BPF helper API:

:::code api-kprobes-uprobes/c/dopomizhni-bpf-funktsii.h

Функція `bpf_probe_read_user_str` автоматично перевіряє межі віртуальних сторінок простору користувача, запобігає сторінковим збоям (page faults) та повертає кількість зчитаних байтів.

### Спеціалізовані макроси аргументів `BPF_KPROBE` та `BPF_UPROBE`

Для вилучення аргументів за назвами типів замість ручного зчитування з `struct pt_regs` `libbpf` пропонує макроси автоматичного декодування:

:::code api-kprobes-uprobes/c/spetsializovani-makrosy.c

## 4. Коди помилок та обмеження системного API

При виконанні системних викликів реєстрації зондів операційна система може повертати такі коди помилок:

- `-EINVAL`: Некоректна віртуальна адреса, символ не знайдено у `/proc/kallsyms`, або адреса вказує на середину інструкції. Виникає також у разі спроби встановити uprobe за некоректним зміщенням файлу.
- `-ENOENT`: Указаний виконуваний файл чи спільна бібліотека відсутня на диску.
- `-EILSEQ`: Спроба встановити зонд на чорний список зондування (`NOKPROBE_SYMBOL`), де інструментація спричинить нескінченну рекурсію переривань `#BP`.
- `-EBUSY`: На цю інструкцію вже встановлено зонд іншим механізмом, який не підтримує спільний доступ (наприклад, конфлікт із фазою оптимізації Optprobe).
- `-ENOMEM`: Недостатньо пам'яті ядра для виділення OOL-буфера або примірника `kretprobe_instance`.
- `-E2BIG`: Значення `maxactive` для `kretprobe` перевищує допустимий системний ліміт.

Урахування цих кодів помилок є критичним для забезпечення надійності промислових агентів спостережуваності, які повинні коректно обробляти відсутність символів у старих версіях ядер або захищеність певних підсистем.
