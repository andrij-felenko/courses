# 📋 Діагностичний контракт GStreamer: змінні, рівні, спостерігачі

Повний перелік того, чим у GStreamer керують діагностикою ззовні: змінні середовища, рівні й категорії журналу, прапорці скидання графа, спостерігачі, прапорці штатних утиліт і коди потоку, які видно в рядках журналу. Звірено з офіційною документацією й заголовками ядра (`gstinfo.h`, `gstdebugutils.h`, `gstpad.h`). Тримати це в голові немає сенсу — на відміну від коду конвеєра, ці ручки чіпають раз на місяць і щоразу заново згадують синтаксис.

## Передумова: збірка з увімкненою діагностикою

Усе, що нижче, працює лише тоді, коли бібліотеку зібрано **без** `GST_DISABLE_GST_DEBUG`. У збірці з вимкненою діагностикою макроси журналу й скидання графа розкриваються в порожнечу просто в препроцесорі — код компілюється, змінні середовища читаються ніким, і жодного попередження не буде. Пакунки звичайних дистрибутивів зібрані з діагностикою; урізані вбудовані збірки — часто ні.

Перевірка займає одну команду:

```sh
gst-inspect-1.0 --gst-debug-help    # список усіх категорій із типовими рівнями
```

Якщо друкується таблиця категорій — діагностика на місці. Якщо опції нема або список порожній, далі можна не читати: жодна змінна нижче нічого не змінить. З коду те саме питання ставить `gst_debug_is_active()`.

## `GST_DEBUG`: граматика рядка

```
GST_DEBUG=[глобальний_рівень][,шаблон:рівень][,шаблон:рівень]…
```

- Перший елемент **без двокрапки** — рівень для всіх категорій одразу.
- `шаблон` — ім'я категорії або маска з `*`: `videodec*:5`, `*sink*:6`, `*:2`.
- `рівень` — число 0–9 або ім'я рівня (`WARNING`, `DEBUG`, `TRACE`) — імена приймаються з 1.2.
- Правила застосовуються так, що **пізніший запис перекриває раніший** для тих самих категорій. Тому загальний рівень ставлять першим, а прицільні — після нього.

```sh
GST_DEBUG=2,GST_CAPS:5,qtdemux:6          # усім 2, узгодженню 5, демультиплексору 6
GST_DEBUG=*:WARNING,*sink*:DEBUG          # те саме іменами рівнів
GST_DEBUG=2 GST_DEBUG_FILE=/tmp/gst-%p.log gst-launch-1.0 …
```

Змінна читається один раз під час `gst_init()`, тож виставляти її треба до запуску процесу — це звичайне [оточення процесу](root:sys-unix/argv-and-environment), яке дитина успадковує від того, хто її запустив, і змінити його зсередини вже запущеної чужої програми неможливо.

## Рівні: що саме потрапляє в журнал

| № | ім'я (`GstDebugLevel`) | що пише | ціна |
| --- | --- | --- | --- |
| 0 | `GST_LEVEL_NONE` | нічого | нуль |
| 1 | `GST_LEVEL_ERROR` | фатальні дефекти, після яких елемент не працює; майже завжди в парі з повідомленням `ERROR` на шині | нуль |
| 2 | `GST_LEVEL_WARNING` | те, що пішло не так, але робота триває: невдала спроба, відсутній ресурс, відкат до запасного шляху | майже нуль |
| 3 | `GST_LEVEL_FIXME` | місця, які самі автори позначили як недороблені; корисно, коли поведінка дивна, а помилки нема | майже нуль |
| 4 | `GST_LEVEL_INFO` | рідкі події налаштування: створення елементів, завантаження плагінів, зафіксовані caps | низька |
| 5 | `GST_LEVEL_DEBUG` | усе, що трапляється **не** на кожен буфер: переходи станів, узгодження, події, запити | помітна |
| 6 | `GST_LEVEL_LOG` | усе, що трапляється **на кожен** буфер | конвеєр реального часу перестає встигати |
| 7 | `GST_LEVEL_TRACE` | найчастіше змінне: лічильники посилань, блокування; сюди ж пишуть спостерігачі | те саме, помножене |
| 8 | — | не використовується, лишене на майбутнє | — |
| 9 | `GST_LEVEL_MEMDUMP` | шістнадцяткові дампи вмісту буферів | гігабайти за хвилини |

Рівень 8 у переліку справді порожній: `GST_LEVEL_MEMDUMP` дорівнює 9, а вісімку зарезервовано для майбутніх рівнів.

## Категорії ядра

Категорію задає той, хто пише рядок журналу. Категорії ядра описують підсистеми, наскрізні для всіх елементів.

| категорія | про що вона |
| --- | --- |
| `GST_CAPS` | побудова, перетин і фіксація [caps](root:sys-media/caps-negotiation) — саме тут видно порожній перетин форматів |
| `GST_PADS` | створення падів, з'єднання, встановлення функцій |
| `GST_ELEMENT_PADS` | пади з боку елемента: додано, вилучено, запитано |
| `GST_STATES` | переходи станів кожного елемента й конвеєра |
| `GST_EVENT` | події вздовж і проти течії: `SEGMENT`, `EOS`, `FLUSH`, `QOS` |
| `GST_MESSAGE` | повідомлення, які елементи кладуть на шину |
| `GST_BUS` | доставка цих повідомлень слухачеві |
| `GST_BUFFER` | створення й звільнення буферів |
| `GST_MEMORY` | шматки пам'яті під буферами, відображення й копії |
| `GST_SCHEDULING` | режим руху даних: проштовхування чи витягування |
| `GST_ELEMENT_FACTORY` | пошук фабрики за назвою й створення примірників |
| `GST_PLUGIN_LOADING` | завантаження бібліотек плагінів |
| `GST_REGISTRY` | сканування тек і кеш реєстру — «звідки взялися ці елементи» |
| `GST_CLOCK` | вибір годинника й обчислення часу подачі |
| `GST_QOS` | запізнення й викинуті кадри |
| `GST_PERFORMANCE` | місця, де довелося зробити дорогу річ: копію, перетворення, вирівнювання |
| `GST_REFCOUNTING` | лічильники посилань на об'єктах |
| `GST_TRACER` | канал виводу спостерігачів |
| `default` | усе, що не отримало власної категорії |

`GST_PERFORMANCE` вартий окремої згадки: конвеєр, який «чомусь їсть процесор», на рівні 5 цієї категорії сам зізнається, де саме він копіює кадр замість передати посилання.

**Категорії елементів.** Кожен плагін реєструє власну категорію, названу як сам елемент: `qtdemux`, `v4l2src`, `rtspsrc`, `x264enc`. Крім того, базові класи мають свої — `basesrc`, `basesink`, `basetransform`, `videodecoder`, — і саме в них живе більшість логіки, спільної для сотень елементів. Окремий випадок: `queue` веде дві категорії, і цікавіша не `queue`, а `queue_dataflow` — рух буферів усередині черги, включно з блокуванням на повній.

Повний перелік категорій **саме вашої** збірки з їхніми типовими рівнями друкує `--gst-debug-help` — вигадувати назви не треба.

## Куди йде вивід

Журнал за замовчуванням іде в стандартний потік помилок (див. [три потоки](root:sys-unix/standard-streams)), і це важливо для перенаправлення: `>` його не спіймає, потрібне `2>` або `2>&1`.

| змінна | значення | що робить |
| --- | --- | --- |
| `GST_DEBUG_FILE` | шлях | пише журнал у файл замість `stderr`; у шаблоні працюють `%p` — pid процесу і `%r` — випадкове число |
| `GST_DEBUG_NO_COLOR` | будь-яке | вимикає розфарбування |
| `GST_DEBUG_COLOR_MODE` | `on`/`auto`, `off`/`disable`, `unix` | те саме докладніше: `unix` змушує використовувати ANSI-послідовності навіть там, де їх не було б (файл, консоль Windows) |
| `GST_DEBUG_OPTIONS` | `pretty-tags` (типово), `full-tags` | як друкувати теґи медіа: скорочено чи повністю |
| `GST_DEBUG_DUMP_DOT_DIR` | тека | вмикає скидання графа (див. нижче) |

Шаблон `%p` вирішує єдину, зате постійну проблему: кілька процесів із однаковим `GST_DEBUG_FILE` пишуть в один файл упереміш і затирають одне одного. `GST_DEBUG_FILE=/tmp/gst-%p.log` дає кожному процесу свій файл.

## Керування журналом із коду

Те саме, що роблять змінні, доступне як API — це єдиний спосіб для пристрою, де змінну середовища виставити нікому, а `stderr` веде в нікуди.

| функція | що робить |
| --- | --- |
| `void gst_debug_set_active (gboolean active)` | глобальний вимикач усієї підсистеми |
| `gboolean gst_debug_is_active (void)` | чи зібрано з діагностикою і чи вона ввімкнена |
| `void gst_debug_set_default_threshold (GstDebugLevel level)` | глобальний рівень |
| `GstDebugLevel gst_debug_get_default_threshold (void)` | поточний глобальний рівень |
| `void gst_debug_set_threshold_for_name (const gchar *name, GstDebugLevel level)` | рівень одній категорії |
| `void gst_debug_unset_threshold_for_name (const gchar *name)` | зняти окреме правило |
| `void gst_debug_set_threshold_from_string (const gchar *list, gboolean reset)` | той самий рядок, що й у `GST_DEBUG`; `reset=TRUE` спершу скидає всі правила |
| `void gst_debug_add_log_function (GstLogFunction func, gpointer user_data, GDestroyNotify notify)` | додає власний приймач рядків |
| `guint gst_debug_remove_log_function (GstLogFunction func)` | прибирає його; повертає, скільки прибрано |
| `void gst_debug_set_colored (gboolean colored)` | розфарбування ввімк/вимк |
| `void gst_debug_set_color_mode (GstDebugColorMode mode)` | `GST_DEBUG_COLOR_MODE_OFF` (0), `_ON` (1), `_UNIX` (2) |
| `const gchar * gst_debug_level_get_name (GstDebugLevel level)` | ім'я рівня рядком |
| `GSList * gst_debug_get_all_categories (void)` | усі зареєстровані категорії |

Типовий приймач за замовчуванням — `gst_debug_log_default`; його прибирають, коли треба забрати весь журнал собі:

```c
static void my_log (GstDebugCategory *cat, GstDebugLevel level,
                    const gchar *file, const gchar *function, gint line,
                    GObject *object, GstDebugMessage *message, gpointer data)
{
  syslog (LOG_DEBUG, "%s %s:%d %s",
          gst_debug_category_get_name (cat), file, line,
          gst_debug_message_get (message));
}

gst_debug_remove_log_function (gst_debug_log_default);
gst_debug_add_log_function (my_log, NULL, NULL);
gst_debug_set_threshold_from_string ("2,GST_STATES:5", TRUE);
```

> 🔧 **Навіщо це.** На пристрої без термінала журнал GStreamer інакше просто зникає: `stderr` закритий або перенаправлений у `/dev/null`, а файлова система здебільшого лише для читання. Власний приймач віддає ті самі рядки в системний журнал, у кільцевий буфер у пам'яті чи в мережу — і робить діагностику доступною там, де змінних середовища виставити нікому.

Власна категорія для свого коду заводиться двома макросами — тоді ваші повідомлення керуються тим самим `GST_DEBUG`, що й бібліотечні:

```c
GST_DEBUG_CATEGORY_STATIC (my_cat);
#define GST_CAT_DEFAULT my_cat
/* один раз при старті: */
GST_DEBUG_CATEGORY_INIT (my_cat, "myapp", 0, "мій застосунок");
/* далі будь-де: */
GST_INFO ("камера відкрита: %s", path);
```

## Скидання графа

| що | значення |
| --- | --- |
| `GST_DEBUG_DUMP_DOT_DIR` | тека, куди складати `.dot`; **не створюється автоматично** — нема теки, нема файлів і нема попередження |
| `GST_DEBUG_BIN_TO_DOT_FILE (bin, details, name)` | обгортка над `gst_debug_bin_to_dot_file()` |
| `GST_DEBUG_BIN_TO_DOT_FILE_WITH_TS (bin, details, name)` | те саме, але з часовою міткою в імені — виклики не затирають один одного |
| `gchar * gst_debug_bin_to_dot_data (GstBin *bin, GstDebugGraphDetails details)` | той самий опис рядком у пам'ять, без файлу |

Обидва макроси в збірці без діагностики розкриваються в порожній вираз, тому обкладати їх умовною компіляцією не треба.

Прапорці подробиць (`GstDebugGraphDetails`) складаються побітово:

```
SHOW_MEDIA_TYPE          = 1     тип даних підписом на ребрі
SHOW_CAPS_DETAILS        = 2     повні caps з усіма полями
SHOW_NON_DEFAULT_PARAMS  = 4     властивості, змінені від типових
SHOW_STATES              = 8     стан кожного елемента
SHOW_FULL_PARAMS         = 16    усі властивості, включно з типовими
SHOW_ALL                 = 15    = 1 + 2 + 4 + 8  (БЕЗ повних параметрів!)
SHOW_VERBOSE             = 0xffffffff   усе, включно з 16
```

Пастка в передостанньому рядку: `SHOW_ALL` — це `(1<<4)-1`, тобто перші чотири прапорці, і `SHOW_FULL_PARAMS` до нього **не** входить, хоч назва обіцяє протилежне. Коли треба побачити всі властивості всіх елементів, потрібен `SHOW_VERBOSE`.

Перетворення в картинку — сторонньою утилітою з пакета Graphviz:

```sh
dot -Tsvg pipeline.dot -o pipeline.svg     # або -Tpng
```

## `GST_TRACERS`: спостерігачі

Спостерігач — це модуль, який чіпляється до внутрішніх точок бібліотеки й пише свої числа в категорію `GST_TRACER`. Тому вмикають його завжди **двома** змінними: одна каже, що завантажити, друга — пропускає його вивід у журнал.

```
GST_TRACERS="ім'я(параметр=значення,параметр=значення);інше_ім'я"
GST_DEBUG=GST_TRACER:7
```

Спостерігачі розділяються крапкою з комою, параметри всередині дужок — комою; списки беруться в лапки.

| спостерігач | параметри | що дає |
| --- | --- | --- |
| `latency` | `flags=pipeline`(1)`+element`(2)`+reported`(4) | заміряну [затримку](root:sys-media/latency-and-buffering): наскрізну, поелементну й ту, яку елементи самі про себе оголосили |
| `leaks` | `filters="GstBuffer,GstEvent"`, `check-refs=true`, `stack-traces-flags=none`\|`full` | перелік об'єктів GStreamer, живих на момент виходу |
| `stats` | — | зведення потоку буферів, подій, повідомлень і запитів |
| `rusage` | — | час процесора й пам'ять процесу через `getrusage()` |
| `log` | — | самі перехоплені виклики, як вони йдуть |

Перелік залежить від версії — що є саме у вашій збірці, каже `gst-inspect-1.0 coretracers`.

```sh
GST_DEBUG=GST_TRACER:7 GST_TRACERS="latency(flags=pipeline+element)" gst-launch-1.0 …
GST_DEBUG=GST_TRACER:7 GST_TRACERS='leaks(filters="GstBuffer",check-refs=true)' ./myapp
```

Спостерігач `leaks` уміє звітувати не лише на виході: якщо визначено змінну `GST_LEAKS_TRACER_SIG`, він ставить обробники [сигналів](root:sys-unix/signal-model) — `SIGUSR1` друкує всі живі об'єкти просто зараз, `SIGUSR2` ставить контрольну точку й далі показує різницю з нею. Це єдиний спосіб зловити повільний витік у процесі, який працює тижнями й до виходу не доходить ніколи.

Вивід `stats` призначений не для читання очима: журнал із ним пропускають крізь `gst-stats-1.0`, який зводить рядки в таблицю по елементах.

## Плагіни й реєстр

| змінна | значення | що робить |
| --- | --- | --- |
| `GST_PLUGIN_PATH_1_0` (або `GST_PLUGIN_PATH`) | теки через `:` (`;` на Windows) | де шукати плагіни **перед** системними теками |
| `GST_PLUGIN_SYSTEM_PATH_1_0` | теки через `:` | системні теки; **порожній рядок** вимикає системне сканування взагалі |
| `GST_REGISTRY_1_0` (або `GST_REGISTRY`) | шлях до файлу | окремий файл кешу реєстру |
| `GST_REGISTRY_FORK` | `no` | не відгалужувати процес для сканування — потрібно під зневаджувачем і під valgrind |
| `GST_REGISTRY_UPDATE` | `no` | не оновлювати реєстр, брати кеш як є |
| `GST_REGISTRY_MODE` | 1–4 вісімкові цифри (з 1.20) | права доступу на файл реєстру |
| `GST_PLUGIN_FEATURE_RANK` | `назва:ранг` через кому (з 1.18) | перевизначає ранг фабрики, не чіпаючи збірку |

Ранги: `NONE` = 0, `MARGINAL` = 64, `SECONDARY` = 128, `PRIMARY` = 256, `MAX` — стеля; приймаються і назви, і числа. Саме за рангом автоматичні добірники обирають між двома [придатними елементами](root:sys-media/plugin-model), тож `GST_PLUGIN_FEATURE_RANK=vah264dec:MAX` — це спосіб змусити `decodebin` узяти апаратний декодер, не переписуючи ані рядка коду.

Змінні з суфіксом `_1_0` мають перевагу над версіями без суфікса: у системі, де поруч живуть кілька гілок GStreamer, це рятує від того, щоб одна не читала теки іншої.

## Прапорці утиліт

Опції з префіксом `--gst-` обробляє сам `gst_init()`, а не утиліта. Тому **ваша власна програма** отримує їх безкоштовно — досить передати `argc`/`argv` у `gst_init()`, і вона почне розуміти `--gst-debug-level` нарівні зі штатними інструментами.

**Спільні для всіх:**

| прапорець | що робить |
| --- | --- |
| `--gst-debug=СПИСОК` | те саме, що `GST_DEBUG`, лише командним рядком |

## `GstFlowReturn` у рядках журналу

Коли елемент зупиняє потік, у журналі й у зневаджувальному рядку помилки з'являється текстова назва разом із числом — саме в такому вигляді: `reason not-negotiated (-4)`. Ось увесь набір.

| число | константа | назва в тексті | що сталося |
| --- | --- | --- | --- |
| 0 | `GST_FLOW_OK` | `ok` | дані пройшли |
| −1 | `GST_FLOW_NOT_LINKED` | `not-linked` | пад, у який штовхали, ні до чого не приєднаний |
| −2 | `GST_FLOW_FLUSHING` | `flushing` | пад скидає дані (перемотка, зупинка) — очікувана відмова, не помилка |
| −3 | `GST_FLOW_EOS` | `eos` | кінець потоку |
| −4 | `GST_FLOW_NOT_NEGOTIATED` | `not-negotiated` | сторони не домовилися про формат |
| −5 | `GST_FLOW_ERROR` | `error` | фатальна помилка; елемент зобов'язаний покласти на шину `ERROR` із подробицями |
| −6 | `GST_FLOW_NOT_SUPPORTED` | `not-supported` | операція не підтримується |
| 100, 101, 102 | `GST_FLOW_CUSTOM_SUCCESS`, `_1`, `_2` | `custom-success` | успіх, значення якого визначає сам елемент |
| −100, −101, −102 | `GST_FLOW_CUSTOM_ERROR`, `_1`, `_2` | `custom-error` | помилка, значення якої визначає сам елемент |

Знак — це і є класифікація: нуль і додатні означають, що передавання відбулося, від'ємні — що ні. При цьому `−1` і `−2` бібліотека вважає **очікуваними** відмовами: вони штатно трапляються під час розбирання конвеєра й перемотки, і елемент від них не зобов'язаний скаржитися на шину. Усе, що від `−3` і нижче, — уже помилкові випадки.

## Мінімальний набір команд

Три рядки, з яких починається будь-яка діагностика, від дешевшого до дорожчого:

```sh
# 1. побачити узгоджені формати й повідомлення шини — майже безкоштовно
GST_DEBUG=2 gst-launch-1.0 -v -m <конвеєр>

# 2. подробиці налаштування у файл, окремий на кожен процес, без кольору
GST_DEBUG=2,GST_STATES:5,GST_CAPS:5 GST_DEBUG_NO_COLOR=1 \
  GST_DEBUG_FILE=/tmp/gst-%p.log <програма>

# 3. граф конвеєра на кожній зміні стану
mkdir -p /tmp/dots && GST_DEBUG_DUMP_DOT_DIR=/tmp/dots gst-launch-1.0 <конвеєр>
```
