Коли мікроконтролер керує гальмівною системою автомобіля або стабілізацією польотного контролера, кожна операція мусить завершуватися за строго гарантований інтервал часу. Виклик стандартної бібліотечної функції `malloc()` у такій системі становить приховану загрозу: її внутрішній алгоритм може переглядати сотні розрізнених фрагментів пам'яті у пошуках вільного місця. Якщо сьогодні виділення триває 12 мікросекунд, а завтра під час сплеску навантаження — 480 мікросекунд, система втрачає детермінізм (від лат. *determinare* — «визначати», «обмежувати»), пропускає дедлайн переривання й зазнає аварії.

Друга небезпека — зовнішня фрагментація (від лат. *fragmentum* — «уламок», «частка»). Мікроконтролер може мати 64 кілобайти сумарно вільної оперативної пам'яті, але якщо цей простір посічений на тисячі дрібних ізольованих проміжків по 32 байти, спроба виділити суцільний буфер на 1024 байти для мережевого пакета завершиться фатальною помилкою нестачі пам'яті (`NULL`).

Операційні системи загального призначення вирішують цю проблему через віртуальну пам'ять і таблиці сторінок процесора (MMU). Проте мікроконтролери архітектур ARM Cortex-M, Xtensa чи RISC-V зазвичай позбавлені MMU: вони працюють виключно з фізичними адресами, де кожен виділений блок має бути фізично суцільним.

Щоб розв'язати цей конфлікт між гнучкістю та надійністю, операційна система реального часу FreeRTOS відмовилася від універсального алокатора (від лат. *allocare* — «виділяти частку», «розміщувати»). Замість однієї компромісної схеми розробникам запропоновано п'ять еталонних реалізацій (`heap_1.c`–`heap_5.c`), кожна з яких оптимізована під конкретний клас задач і рівень вимог до надійності.

### Анатомія проблеми: Чому універсальний malloc відмовляє у RTOS

Стандартна функція `malloc()` із бібліотек на кшталт Newlib чи dlmalloc створювалася для настільних комп'ютерів із гігабайтами пам'яті, де головним критерієм була середня пропускна здатність, а не найгірший час відгуку (worst-case execution time, WCET).

У вбудованих системах реального часу стандартний розподільник зазнає невдачі через чотири фундаментальні фактори:

1. **Недетермінованість часу пошуку:** Загальний розподільник обходить дерево або список вільних ділянок. У найгіршому випадку, коли пам'ять сильно посічена, час пошуку підхожого блока пропорційний кількості фрагментів `O(N)`. Це вносить непередбачуваний джиттер у роботу високопріоритетних задач.
2. **Відсутність потокобезпечності без блокування ядра:** Стандартні бібліотеки `libc` не знають про задачі FreeRTOS. Без спеціальних хуків одночасний виклик `malloc()` із двох потоків руйнує службові покажчики кучі. Введення м'ютексів захищає дані, але створює загрозу інверсії пріоритетів.
3. **Незворотне падіння за зовнішньої фрагментації:** На відміну від серверних ОС, де фрагментація кучі процесу усувається перезапуском процесу або скиданням пам'яті в swap, мікроконтролер виконує єдину прошивку роками. Навіть мізерний рівень фрагментації призводить до відмови пристрою після кількох місяців безперервної роботи.
4. **Накладні витрати на вирівнювання та службові заголовки (внутрішня фрагментація):** Процесори Cortex-M та Xtensa вимагають, щоб 32-бітні значення розміщувалися за адресами, кратними 4, а 64-бітні числа з рухомою комою або операції подвійного завантаження `LDRD`/`STRD` — за адресами, кратними 8 (макрос `portBYTE_ALIGNMENT`). Якщо алокатор додає заголовок і вирівнює корисне навантаження, запит на 1 байт може фізично споживати 16 або 24 байти кучі.

### heap_1: Лінійний бамп-алокатор без звільнення

У критичних галузях із жорсткою сертифікацією надійності (авіоніка DO-178C, автопром ISO 26262, промислова автоматика IEC 61508) динамічне виділення та звільнення пам'яті під час штатної роботи взагалі заборонено стандартами. Будь-який виклик `free()` несе ризик накопичення фрагментації, поведінку якої неможливо перевірити на всіх комбінаціях тривалої експлуатації пристрою.

Схема `heap_1.c` створена спеціально для систем, де динамічні об'єкти (задачі, черги, семафори, таймери) створюються виключно на етапі запуску прошивки перед стартом планувальника `vTaskStartScheduler()`, а після цього існують вічно до знеструмлення пристрою.

![Лінійний алокатор heap_1: бамп-покажчик зміщення всередині статичного масиву ucHeap](/root/sys/sys-fw/freertos-heap/img/heap1-bump-pointer.svg)
*Механіка heap_1: покажчик зміщення xNextFreeByte монотонно зростає під час кожного запиту; виклик vPortFree() є порожньою заглушкою.*

В основі `heap_1` лежить єдиний статично виділений масив байтів:

:::tabs
```c
/* Статичний буфер та бамп-покажчик зміщення у heap_1.c */
static uint8_t ucHeap[ configTOTAL_HEAP_SIZE ];
static size_t xNextFreeByte = ( size_t ) 0;
```
```cpp
#include <array>
#include <cstddef>
#include <cstdint>

template <std::size_t HeapSizeBytes>
class BumpAllocatorState {
public:
    static inline std::array<std::uint8_t, HeapSizeBytes> heap_storage{};
    static inline std::size_t next_free_byte{0};
};
```
:::

Коли програма викликає `pvPortMalloc(xWantedSize)`, алокатор виконує три елементарні кроки:
1. Вирівнює `xWantedSize` до кратності `portBYTE_ALIGNMENT` (зазвичай 8 байтів для забезпечення коректного доступу до 64-бітних чисел на 32-бітних шинах).
2. Перевіряє умову захисту від переповнення та виходу за межі: `(xNextFreeByte + xWantedSize) <= configTOTAL_HEAP_SIZE`.
3. Зберігає поточну адресу `&ucHeap[xNextFreeByte]`, збільшує зміщення `xNextFreeByte += xWantedSize` і повертає збережену адресу.

Часова складність `pvPortMalloc()` становить строго `O(1)` — рівно кілька процесорних інструкцій без жодного циклу, що гарантує абсолютний часовий детермінізм.

Функція звільнення пам'яті в `heap_1.c` реалізована як порожня заглушка:

:::tabs
```c
void vPortFree( void *pv )
{
    ( void ) pv;
    /* У heap_1 звільнення пам'яті принципово не підтримується */
}
```
```cpp
namespace rtos::heap1 {

constexpr void deallocate(void* /*ptr*/) noexcept
{
    // За правилами heap_1 повернення пам'яті є no-op
}

} // namespace rtos::heap1
```
:::

> 🔧 **Навіщо це.** Завдяки відсутності `vPortFree()` схема `heap_1` гарантує математично нульову фрагментацію пам'яті. У ній фізично неможливі витоки пам'яті в робочому циклі чи пошкодження списків вільних блоків.

### heap_2: Best-Fit без злиття сусідніх блоків

Коли система вимагає періодичного створення та видалення об'єктів однакового розміру (наприклад, видалення завершеної задачі з фіксованим стеком або вивільнення мережевого пакета стандартизованої довжини), лінійного бампа недостатньо.

Схема `heap_2.c` запроваджує зв'язний список вільних блоків. Вільні ділянки пам'яті описуються службовим заголовком і зв'язуються в однозв'язний список, відсортований за **зростанням розміру блока** (алгоритм Best-Fit, тобто «найкраще припасування»):

:::tabs
```c
typedef struct A_BLOCK_LINK
{
    struct A_BLOCK_LINK *pxNextFreeBlock; /* Вказівник на наступний вільний блок */
    size_t xBlockSize;                    /* Розмір цього вільного блока */
} BlockLink_t;
```
```cpp
#include <cstddef>

struct BlockLink {
    BlockLink* next_free{nullptr};
    std::size_t block_size{0};
};
```
:::

Коли надходить запит на виділення `xWantedSize`:
1. Алокатор обходить список від голови (`xStart`) і зупиняється на **першому ж блоці**, чий розмір `xBlockSize >= xWantedSize`. Оскільки список упорядковано за розміром, цей знайдений блок автоматично є найменшим із тих, що задовольняють запит. Це мінімізує залишок від розрізання.
2. Якщо знайдений блок більший за запитаний розмір щонайменше на `heapMINIMUM_BLOCK_SIZE`, блок розщеплюється на дві частини: перша повертається клієнту, а залишок вставляється назад у вільний список на відповідну позицію за своїм новим розміром.

Під час виклику `vPortFree(pv)` звільнений блок повертається у вільний список, знову займаючи позицію відповідно до свого розміру.

![Порівняння фрагментації між heap_2 та злиттям блоків у heap_4](/root/sys/sys-fw/freertos-heap/img/heap2-vs-heap4-fragmentation.svg)
*Фатальна вада heap_2: сусідні вільні блоки A та B не зливаються в один, що блокує виділення більшого блока, тоді як heap_4 автоматично зшиває їх.*

Головна архітектурна вада `heap_2` — **відсутність механізму злиття (coalescing)**. Якщо програма виділить два суміжних блоки по 200 байтів, а потім звільнить обидва, у списку `heap_2` з'являться два окремих вільних блоки по 200 байтів. Якщо наступної миті програма запросить 350 байтів, `heap_2` відповість відмовою (`NULL`), хоча фізично в пам'яті є 400 неперервних вільних байтів!

Через це `heap_2` вважається застарілою схемою. Вона ефективна лише тоді, коли всі динамічні блоки в системі мають один або два фіксованих розміри. За довільних розмірів `heap_2` швидко перетворює пам'ять на «шахівницю» дрібних незшиваних ділянок.

### heap_3: Обгортка над стандартною бібліотекою C

Схема `heap_3.c` не виділяє власних масивів у RAM. Вона є тонкою обгорткою над стандартними функціями `malloc()` та `free()`, що постачаються разом із компіляторним середовищем (Newlib, glibc, IAR DLib тощо).

Проблема стандартного `malloc()` полягає в тому, що він не є потокобезпечним (thread-safe): одночасний виклик `malloc()` із двох різних задач FreeRTOS призведе до одночасного читання й запису внутрішніх вказівників кучі компілятора та її фатального руйнування.

Щоб запобігти цьому, `heap_3.c` тимчасово вимикає перемикання контексту задач на час виконання коду стандартної бібліотеки:

:::tabs
```c
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"

void *pvPortMalloc( size_t xWantedSize )
{
    void *pvReturn;

    /* Призупиняємо планувальник: перемикання задач заблоковано */
    vTaskSuspendAll();
    {
        pvReturn = malloc( xWantedSize );
    }
    /* Відновлюємо планувальник */
    ( void ) xTaskResumeAll();

    return pvReturn;
}

void vPortFree( void *pv )
{
    if( pv != NULL )
    {
        vTaskSuspendAll();
        {
            free( pv );
        }
        ( void ) xTaskResumeAll();
    }
}
```
```cpp
#include <memory>
#include <concepts>
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"

namespace rtos::heap3 {

template <typename T, typename... Args>
[[nodiscard]] std::unique_ptr<T, void(*)(T*)> make_unique_task_safe(Args&&... args)
{
    vTaskSuspendAll();
    void* raw_mem = std::malloc(sizeof(T));
    xTaskResumeAll();

    if (!raw_mem) {
        return {nullptr, [](T*){}};
    }

    T* object = ::new (raw_mem) T(std::forward<Args>(args)...);

    return {
        object,
        [](T* ptr) noexcept {
            if (ptr) {
                ptr->~T();
                vTaskSuspendAll();
                std::free(static_cast<void*>(ptr));
                xTaskResumeAll();
            }
        }
    };
}

} // namespace rtos::heap3
```
:::

Ціна такого підходу:
- **Втрата контролю над часом виконання:** тривалість роботи `malloc()` залежить від реалізації бібліотеки C і може мати значну дисперсію.
- **Джиттер планувальника:** зупинка планувальника через `vTaskSuspendAll()` затримує перемикання на високопріоритетні задачі, збільшуючи затримку реакції системи.
- **Збільшення розміру коду:** стандартний `malloc()` тягне за собою важкий апарат підтримки платформи із системними викликами `sbrk()`.

### heap_4: First-Fit з автоматичним злиттям суміжних блоків

Схема `heap_4.c` є найпопулярнішим алокатором загального призначення для більшості класичних мікроконтролерних проєктів FreeRTOS. Вона розв'язує проблему фрагментації за допомогою механізму **злиття суміжних вільних блоків** (англ. *coalescing*, від лат. *coalescere* — «зростатися», «з'єднуватися в одне»).

На відміну від `heap_2`, вільний список `heap_4` впорядкований строго за **зростанням фізичних адрес пам'яті** (`pxNextFreeBlock` завжди вказує на блок із вищою адресою).

![Анатомія виділеного блока пам'яті та службового заголовка BlockLink_t у FreeRTOS](/root/sys/sys-fw/freertos-heap/img/block-link-anatomy.svg)
*Внутрішня будова блока: 8-байтний службовий заголовок передує корисним даним; старший біт розміру служить прапорцем зайнятості.*

#### Економія пам'яті: старший біт як тег стану (xBlockAllocatedBit)

Кожен блок пам'яті містить заголовок `BlockLink_t`. У 32-бітній системі вказівник займає 4 байти, а поле розміру `xBlockSize` — ще 4 байти (разом 8 байтів). Додавання окремого поля `bool is_allocated` призвело б через вимоги вирівнювання до збільшення заголовка до 12 чи 16 байтів на кожен виділений блок!

Розробники FreeRTOS застосували елегантне рішення: оскільки розмір кучі у мікроконтролерах ніколи не досягає 2 гігабайтів, найстарший біт (MSB) 32-бітного поля `xBlockSize` ніколи не використовується для представлення самого розміру.

Під час ініціалізації кучі обчислюється бітова маска:

:::tabs
```c
static size_t xBlockAllocatedBit = ((size_t) 1) << ((sizeof(size_t) * 8) - 1);
```
```cpp
#include <cstddef>

static constexpr std::size_t block_allocated_bit =
    std::size_t{1} << (sizeof(std::size_t) * 8 - 1);
```
:::

- Якщо блок **виділено клієнту**, найстарший біт його поля `xBlockSize` встановлюється в `1` (`xBlockSize |= xBlockAllocatedBit`).
- Коли блок **вільний** і перебуває у зв'язному списку, його найстарший біт скидається в `0` (`xBlockSize &= ~xBlockAllocatedBit`).

Цей механізм також дає вбудований захист від помилки подвійного звільнення (double-free): якщо функція `vPortFree(pv)` бачить, що біт `xBlockAllocatedBit` уже скинутий у нуль, вона генерує аварійне твердження `configASSERT()` замість руйнування списку.

#### Захист від цілочисельного переповнення

Вразливість цілочисельного переповнення (integer overflow) виникає, коли запитаний розмір `xWantedSize` близький до максимального значення `SIZE_MAX`. Додавання розміру службового заголовка `sizeof(BlockLink_t)` може призвести до переповнення 32-бітного числа та отримання маленького додатного результату.

Алокатор `heap_4` містить явний захисний бар'єр:

:::tabs
```c
if( ( xWantedSize + xHeapStructSize ) > xWantedSize )
{
    xWantedSize += xHeapStructSize;
    /* Безпечне вирівнювання та пошук блока */
}
```
```cpp
#include <cstddef>

if (wanted_size + heap_struct_size > wanted_size) {
    wanted_size += heap_struct_size;
    // Безпечне вирівнювання та пошук блока
}
```
:::

Якщо відбувається переповнення, умова `(xWantedSize + xHeapStructSize) > xWantedSize` не виконується, і функція безпечно повертає `NULL`.

#### Алгоритм виділення First-Fit

Під час виклику `pvPortMalloc()` алокатор виконує пошук First-Fit («перший придатний»):
1. Ітерується списком адрес від найменшої до найбільшої.
2. Обирає **перший же блок**, розмір якого достатній для розміщення `xWantedSize + sizeof(BlockLink_t)`.
3. Якщо знайдений блок значно більший за потрібний розмір, він розрізається: початкова частина маркується бітом `xBlockAllocatedBit` і повертається клієнту (зі зсувом покажчика на величину заголовка), а кінцева частина залишається у списку вільних блоків.

Стратегія First-Fit має приховану перевагу над Best-Fit: вона концентрує дрібні розрізані блоки на початку адресного простору кучі, залишаючи великі непорушені монолітні ділянки пам'яті у верхній частині адресного діапазону.

#### Алгоритм злиття: prvInsertBlockIntoFreeList

Справжня сила `heap_4` проявляється під час повернення блока у `vPortFree()`. Функція `prvInsertBlockIntoFreeList()` вставляє блок у відсортований за адресами список і негайно перевіряє можливість його злиття з лівим і правивим фізичними сусідами.

:::tabs
```c
#include "freertos/FreeRTOS.h"

/* Внутрішній фрагмент алгоритму злиття heap_4.c */
static void prvInsertBlockIntoFreeList( BlockLink_t *pxBlockToInsert )
{
    BlockLink_t *pxIterator;
    uint8_t *puc;

    /* 1. Пошук позиції вставки за адресою: шукаємо блок, адреса якого менша за pxBlockToInsert */
    for( pxIterator = &xStart; pxIterator->pxNextFreeBlock < pxBlockToInsert; pxIterator = pxIterator->pxNextFreeBlock )
    {
        /* Простий прохід списком вперед */
    }

    /* 2. Перевірка злиття з ЛІВИМ сусідом (той, що попереду у списку) */
    puc = ( uint8_t * ) pxIterator;
    if( ( puc + pxIterator->xBlockSize ) == ( uint8_t * ) pxBlockToInsert )
    {
        /* Лівий сусід впритул прилягає до нашого блока: поглинаємо наш блок */
        pxIterator->xBlockSize += pxBlockToInsert->xBlockSize;
        pxBlockToInsert = pxIterator;
    }
    else
    {
        /* Якщо лівий сусід не прилягає, зв'язуємо вказівники */
        pxIterator->pxNextFreeBlock = pxBlockToInsert;
    }

    /* 3. Перевірка злиття з ПРАВИМ сусідом (наступний за адресою) */
    puc = ( uint8_t * ) pxBlockToInsert;
    if( ( puc + pxBlockToInsert->xBlockSize ) == ( uint8_t * ) pxIterator->pxNextFreeBlock )
    {
        if( pxIterator->pxNextFreeBlock != pxEnd )
        {
            /* Правий сусід прилягає до кінця нашого блока: поглинаємо правого сусіда */
            pxBlockToInsert->xBlockSize += pxIterator->pxNextFreeBlock->xBlockSize;
            pxBlockToInsert->pxNextFreeBlock = pxIterator->pxNextFreeBlock->pxNextFreeBlock;
        }
    }
    else
    {
        pxBlockToInsert->pxNextFreeBlock = pxIterator->pxNextFreeBlock;
    }
}
```
```cpp
#include <cstdint>
#include <cstddef>
#include <concepts>

struct FreeBlockHeader {
    FreeBlockHeader* next_free{nullptr};
    std::size_t size{0};

    [[nodiscard]] std::uint8_t* byte_end() noexcept {
        return reinterpret_cast<std::uint8_t*>(this) + size;
    }
};

class AddressOrderedFreeList {
public:
    void insert_and_coalesce(FreeBlockHeader* block_to_insert) noexcept {
        FreeBlockHeader* prev = &head_;

        // 1. Пошук позиції за фізичною адресою
        while (prev->next_free != nullptr && prev->next_free < block_to_insert) {
            prev = prev->next_free;
        }

        // 2. Злиття з лівим сусідом
        if (prev != &head_ && prev->byte_end() == reinterpret_cast<std::uint8_t*>(block_to_insert)) {
            prev->size += block_to_insert->size;
            block_to_insert = prev;
        } else {
            block_to_insert->next_free = prev->next_free;
            prev->next_free = block_to_insert;
        }

        // 3. Злиття з правим сусідом
        if (block_to_insert->next_free != nullptr &&
            block_to_insert->byte_end() == reinterpret_cast<std::uint8_t*>(block_to_insert->next_free)) {
            block_to_insert->size += block_to_insert->next_free->size;
            block_to_insert->next_free = block_to_insert->next_free->next_free;
        }
    }

private:
    FreeBlockHeader head_{};
};
```
:::

Якщо вивільняється блок, оточений вільними ділянками з обох боків, функція за два кроки об'єднує всі три ділянки в єдиний монолітний блок. Це гарантує, що пам'ять автоматично дефрагментується під час кожного виклику `vPortFree()`.

### heap_5: Мультирегіональний розподіл розрізнених банків пам'яті

Сучасні мікроконтролери рідко мають єдиний монолітний блок оперативної пам'яті. Типовий мікроконтролер може мати:
- 64 КБ надшвидкої пам'яті DTCM / SRAM1 за адресою `0x20000000`;
- 128 КБ допоміжної пам'яті SRAM2 за адресою `0x20040000`;
- 8 МБ зовнішньої повільнішої пам'яті SDRAM / PSRAM за адресою `0x60000000`.

Схема `heap_4` не здатна об'єднати ці банки, оскільки вона спирається на єдиний статичний масив `ucHeap`. Якщо створити один покажчик між адресами `0x20040000` та `0x60000000`, алокатор спробує записати дані у «дірку» між банками й викличе апаратний збій шини (Bus Fault).

Схема `heap_5.c` розширює алгоритм `heap_4`, дозволяючи об'єднувати довільну кількість фізично розірваних банків пам'яті в єдиний логічний пул.

![Мультирегіональний розподіл пам'яті heap_5: зв'язування банків через vPortDefineHeapRegions](/root/sys/sys-fw/freertos-heap/img/heap5-multi-region.svg)
*Механізм heap_5: структура HeapRegion_t описує незалежні ділянки пам'яті, які зшиваються в єдиний адресний ланцюг First-Fit.*

#### Залізні правила heap_5

Під час роботи з `heap_5` діють два критичні інваріанти:
1. **Сортування за зростанням адрес:** Регіони в масиві `xHeapRegions` **МУСЯТЬ бути впорядковані строго за зростанням їхніх базових адрес**. Якщо поміняти місцями `0x60000000` та `0x20000000`, внутрішній механізм зв'язування адрес зламається, і ядро впаде в аварійне виключення під час першої спроби виділення пам'яті.
2. **Сентинел-термінатор:** Останній елемент масиву мусить містити `{ NULL, 0 }`. Сентинел (від лат. *sentire* через фр. *sentinelle* — «вартовий», «той, хто стереже межу») вказує функції `vPortDefineHeapRegions()`, де закінчується список регіонів.

### Гетерогенна пам'ять ESP-IDF: Чому FreeRTOS heap_5 виявився замалим

Коли компанія Espressif розробляла екосистему для чипів родини ESP32, класичної моделі `heap_5` виявилося недостатньо. Причина криється в апаратній гетерогенності шинної архітектури SoC ESP32:

1. **IRAM (Instruction RAM):** Пам'ять, підключена до шини інструкцій процесора (I-Bus). Вона здатна виконувати код на повній швидкості без затримок кешу Flash. Проте на ранніх ревізіях чипів непарні байтові звернення до IRAM викликають апаратне виключення: IRAM вимагає строго 32-бітного вирівняного доступу.
2. **DRAM (Data RAM):** Пам'ять на шині даних (D-Bus), яка підтримує побайтові, 16-бітні та 32-бітні операції читання й запису. Сюди поміщаються стеки задач, статичні змінні та структури.
3. **D/IRAM (Dual-purpose RAM):** Спільний фізичний простір RAM, який одночасно відображається і в адресний простір інструкцій, і в адресний простір даних за двома різними віртуальними адресами.
4. **DMA-сумісна SRAM:** Апаратні контролери прямого доступу до пам'яті периферійних модулів (SPI, I2S, Wi-Fi MAC, EMAC) можуть обмінюватися даними лише з внутрішньою пам'яттю SRAM. Вони не можуть здійснювати прямий доступ до зовнішньої шини SPI Flash/PSRAM.
5. **PSRAM (External SPI RAM):** Зовнішня пам'ять обсягом від 2 до 32 мегабайтів, доступ до якої здійснюється через кеш-контролер по шині SPI/QSPI/OPI. Вона ідеальна для великих аудіобуферів або кадрів камери, але повільніша за внутрішню SRAM і непридатна для прямого апаратного DMA.

Якщо в такій архітектурі об'єднати всю пам'ять у єдиний пул `heap_5`, функція `pvPortMalloc(4096)` може випадково повернути вказівник на зовнішню PSRAM для буфера SPI DMA, що призведе до апаратного зависання передавача, або виділити пам'ять під стек обробника переривання в ділянці, з якої неможливо виконувати інструкції під час відключення Flash.

![Архітектура пам'яті ESP-IDF: capability-орієнтована селекція регіонів та TLSF-пули](/root/sys/sys-fw/freertos-heap/img/esp-idf-heap-caps-tlsf.svg)
*Дворівнева архітектура пам'яті ESP-IDF: клієнт запитує апаратні властивості пам'яті через heap_caps_malloc(), а диспетчер спрямовує виклик у відповідний пул TLSF.*

### Алокатор можливостей: heap_caps

Щоб розв'язати проблему апаратної неоднорідності, ESP-IDF замінив стандартний інтерфейс виділення пам'яті на **Capability-Based Allocator** (`heap_caps`).

Замість того, щоб вказувати конкретний адресний діапазон, програміст запитує пам'ять із необхідними **апаратними можливостями (capabilities)** через бітову маску:

:::tabs
```c
void *heap_caps_malloc( size_t size, uint32_t caps );
void  heap_caps_free( void *ptr );
```

#### Основні прапорці можливостей (Capabilities)

| Прапорець | Призначення та обмеження | Типовий сценарій |
|---|---|---|
| `MALLOC_CAP_EXEC` | Пам'ять, із якої процесор може виконувати код (IRAM) | Динамічно згенерований код, хуки ISR, код під час вимкненого Flash |
| `MALLOC_CAP_32BIT` | Пам'ять, що підтримує 32-бітне читання й запис за вирівняними адресами | Апаратні таблиці дескрипторів |
| `MALLOC_CAP_8BIT` | Пам'ять із підтримкою побайтового доступу (DRAM) | Рядки, змінні `char`, сирі байти даних |
| `MALLOC_CAP_DMA` | Внутрішня пам'ять, доступна для апаратних DMA-контролерів | Буфери транзакцій SPI, I2S, дисплеїв, Wi-Fi |
| `MALLOC_CAP_SPIRAM` | Зовнішня пам'ять PSRAM, підключена через SPI-шину | Великі буфери зображень, аудіопотоки, нейромережеві ваги |
| `MALLOC_CAP_INTERNAL` | Виключно швидка внутрішня пам'ять кристала SRAM | Критичні за часом алгоритми, структури ядра |
| `MALLOC_CAP_RETENTION` | Пам'ять, що зберігає свій стан у режимі сну Light Sleep | Буфери контексту пристрою |
| `MALLOC_CAP_RTCRAM` | Пам'ять контролера RTC, яка не стирається в Deep Sleep | Дані лічильників і станів між глибокими перезавантаженнями |

Якщо викликати звичайний `malloc(size)`, ESP-IDF автоматично транслює його у виклик `heap_caps_malloc(size, MALLOC_CAP_DEFAULT)`, де дефолтна маска вимагає звичайну побайтову пам'ять (`MALLOC_CAP_8BIT | MALLOC_CAP_32BIT`).

:::tabs
```c

#include "esp_log.h"

void allocate_hardware_buffers(void)
{
    /* 1. Виділення буфера для швидкого DMA-обміну по SPI (тільки внутрішня RAM!) */
    uint8_t *dma_buffer = (uint8_t *)heap_caps_malloc(4096, MALLOC_CAP_DMA | MALLOC_CAP_INTERNAL);
    if (dma_buffer == NULL) {
        ESP_LOGE(TAG, "Помилка: не вдалося виділити DMA-буфер у внутрішній пам'яті");
        return;
    }

    /* 2. Виділення великого кадрового буфера камери у зовнішній PSRAM */
    uint8_t *frame_buffer = (uint8_t *)heap_caps_malloc(640 * 480 * 2, MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT);
    if (frame_buffer == NULL) {
        ESP_LOGE(TAG, "Помилка: не вдалося знайти місце у зовнішній PSRAM");
        heap_caps_free(dma_buffer);
        return;
    }

    ESP_LOGI(TAG, "Буфери успішно створено: DMA @ %p, Frame @ %p", dma_buffer, frame_buffer);

    /* Звільнення виконується універсальною функцією: алокатор сам знає, якому пулу належить адреса */
    heap_caps_free(frame_buffer);
    heap_caps_free(dma_buffer);
}
```

### Під капотом ESP-IDF: Алгоритм TLSF (Two-Level Segregated Fit)

Всередині системи `heap_caps` кожен фізичний банк пам'яті керується окремим екземпляром незалежного алокатора `multi_heap`. Якщо у стандартному FreeRTOS `heap_4` пошук First-Fit вимагає лінійного проходу списком з часовою складністю `O(N)` (де `N` — кількість вільних фрагментів), то в ESP-IDF як ядро `multi_heap` обрано алгоритм **TLSF (Two-Level Segregated Fit)**.

Алгоритм TLSF (розроблений дослідницькою групою M. Masmano, I. Ripoll, A. Crespo в Політехнічному університеті Валенсії) спроєктовано спеціально для систем жорсткого реального часу:

1. **Гарантований час виконання `O(1)`:** Операції виділення та звільнення виконуються за сталий час незалежно від кількості блоків у купі та ступеня її фрагментації.
2. **Дворівнева матриця розмірів:** Вільні блоки класифікуються за розміром на два рівні:
   - **Перший рівень (First Level, FL):** Степені двійки (блоковий діапазон `[2^n, 2^(n+1)-1]`). Індекс першого рівня обчислюється апаратно: `fl = 31 - __builtin_clz(size)`.
   - **Другий рівень (Second Level, SL):** Кожен степеневий діапазон ділиться лінійно на фіксовану кількість кошиків (зазвичай `2^SLI`, де `SLI = 4` чи `5`, тобто 16 або 32 піддіапазони). Індекс другого рівня обчислюється бітовим зсувом: `sl = (size >> (fl - SLI)) - (1 << SLI)`.
3. **Апаратний пошук за бітовими картами:** Наявність вільних блоків у кожному кошику кодується бітовими масками (`fl_bitmap` та `sl_bitmap[fl]`). Пошук непорожнього кошика, розмір якого гарантовано вмістить запитаний блок, здійснюється за 1-2 процесорні інструкції пошуку встановленого біта (`__builtin_ffs` / `__builtin_clz` на RISC-V/ARM або інструкції `NSA` на Xtensa).
4. **Boundary-Tag злиття за `O(1)`:** Кожен блок має заголовок на початку і підвал (футер) у кінці. Це дозволяє миттєво знайти сусідні блоки за адресою і злити їх за сталий час без потреби обходу зв'язного списку.

Завдяки TLSF навіть за умов сильної фрагментації в ESP-IDF виклик `heap_caps_malloc()` займає лічені десятки наносекунд без пікових затримок.

### Метрики, фрагментація та діагностика витоків пам'яті

Для надійної експлуатації вбудованої системи розробник повинен контролювати не лише залишок пам'яті, а й ступінь її фрагментації.

FreeRTOS та ESP-IDF надають функції для зняття ключових метрик:

1. `xPortGetFreeHeapSize()` / `heap_caps_get_free_size(caps)` — повертає **сумарну кількість вільних байтів**.
2. `heap_caps_get_largest_free_block(caps)` — повертає **розмір найбільшого суцільного вільного блока**.
3. `xPortGetMinimumEverFreeHeapSize()` / `heap_caps_get_minimum_free_size(caps)` — фіксує **історичний мінімум вільної пам'яті** (High Water Mark).

Співвідношення між сумарною вільною пам'яттю та розміром найбільшого блока дозволяє кількісно виміряти зовнішню фрагментацію:

```text
Коефіцієнт фрагментації = 1.0 - (Розмір найбільшого блока / Сумарна вільна пам'ять)
```

Якщо сумарно вільно 100 КБ, а найбільший блок має розмір лише 8 КБ, коефіцієнт фрагментації сягає `1.0 - 8/100 = 0.92` (92%). Це свідчить про те, що незважаючи на 100 КБ вільної RAM, будь-який запит на 10 КБ зазнає невдачі.

Детальні інструменти практичного трасування витоків, перехоплення аварій через `vApplicationMallocFailedHook` та захисного отруєння пам'яті (heap poisoning) наведено в окремому проєктному огляді [⚙️ Діагностика, захист та трасування купи у FreeRTOS та ESP-IDF](root:sys-fw/freertos-heap/proj-heap-diagnostics.md).

### Статичне виділення як радикальна альтернатива

У випадках, коли динамічна купа взагалі є небажаною, FreeRTOS надає паралельний набір функцій статичного виділення (за умови увімкнення `configSUPPORT_STATIC_ALLOCATION = 1`):
- `xTaskCreateStatic()` замість `xTaskCreate()`;
- `xQueueCreateStatic()` замість `xQueueCreate()`;
- `xSemaphoreCreateBinaryStatic()` замість `xSemaphoreCreateBinary()`.

При статичному створенні розробник самостійно надає масив під стек та екземпляр структури TCB у секціях `.bss` або `.data`. Пам'ять резервується на етапі лінкування, а її адреси є фіксованими на весь час роботи програми, що зводить ризик відмови пам'яті до абсолютного нуля.

### Порівняльна матриця алокаторів

| Алокатор | Стратегія пошуку | Підтримка `free()` | Злиття блоків | Часова складність `malloc` | Головне призначення |
|---|---|---|---|---|---|
| **`heap_1`** | Bump (лінійний зсув) | Ні | Не застосовується | **`O(1)`** строго | Сертифіковані системи, статична ініціалізація |
| **`heap_2`** | Best-Fit (за розміром) | Так | Ні | **`O(N)`** | Застарілий; пули однакових буферів |
| **`heap_3`** | Залежить від libc | Так | Залежить від libc | Недетерміновано | Системи з обов'язковим Newlib/glibc |
| **`heap_4`** | First-Fit (за адресою) | Так | Так (eager coalescing) | **`O(N)`** | Стандартні однорідні мікроконтролери |
| **`heap_5`** | First-Fit (мультирегіон) | Так | Так (всередині банків) | **`O(N)`** | Мікроконтролери з розділеними банками SRAM/SDRAM |
| **ESP-IDF** | TLSF + Capabilities | Так | Так (`O(1)` boundary tags) | **`O(1)`** гарантовано | Гетерогенні чипи (ESP32: IRAM/DRAM/PSRAM/DMA) |

### Підсумковий огляд

Динамічна пам'ять у реальному часі вимагає компромісу між швидкістю, передбачуваністю та утилізацією адресного простору:
- Якщо вихідні умови дозволяють зафіксувати всі об'єкти на старті — обирайте **`heap_1`** або статичне виділення FreeRTOS (`xTaskCreateStatic`).
- Для класичних проєктів із неперервним виділенням та звільненням на одному банку пам'яті золотим стандартом є **`heap_4`**.
- Якщо архітектура пристрою містить розрізнені області пам'яті (наприклад, внутрішню SRAM і зовнішню SDRAM), використовуйте **`heap_5`** зі строгим сортуванням адрес регіонів.
- У середовищі ESP-IDF використовуйте **`heap_caps_malloc()`** з явним зазначенням необхідних апаратних властивостей (`MALLOC_CAP_DMA`, `MALLOC_CAP_INTERNAL`, `MALLOC_CAP_SPIRAM`), спираючись на гарантовану константну швидкість алокатора TLSF.
